RFC 8865

T.140 Real-Time Text Conversation over WebRTC Data Channels

RFC 8865

WebRTCデータチャネル上のT.140リアルタイムテキスト会話

Abstract

概要

This document specifies how a Web Real-Time Communication (WebRTC) data channel can be used as a transport mechanism for real-time text using the ITU-T Protocol for multimedia application text conversation (Recommendation ITU-T T.140) and how the Session Description Protocol (SDP) offer/answer mechanism can be used to negotiate such a data channel, referred to as a T.140 data channel. This document updates RFC 8373 to specify its use with WebRTC data channels.

この文書は、ITU-Tのマルチメディアアプリケーションテキスト会話プロトコル（勧告ITU-T T.140）を使用するリアルタイムテキストのトランスポートメカニズムとして、 Webリアルタイム通信（WebRTC）データチャネルをどのように使用できるか、 およびそのようなデータチャネル（T.140データチャネルと呼びます）をネゴシエートするためにセッション記述プロトコル（SDP）のオファー/アンサーメカニズムをどのように使用できるかを規定します。 この文書は、WebRTCデータチャネルでの使用を規定するためにRFC 8373を更新します。

1. Introduction

1. はじめに

The ITU-T Protocol for multimedia application text conversation (Recommendation ITU-T T.140) [T140] defines a protocol for text conversation, also known as real-time text. The transport used for IP networks is the "RTP Payload for Text Conversation" mechanism [RFC4103], based on the Real-time Transport Protocol (RTP) [RFC3550].

ITU-Tのマルチメディアアプリケーションテキスト会話プロトコル（勧告ITU-T T.140）[T140]は、 リアルタイムテキストとも呼ばれるテキスト会話のためのプロトコルを定義しています。 IPネットワークで使用されるトランスポートは、リアルタイム転送プロトコル（RTP）[RFC3550]に基づく 「RTP Payload for Text Conversation」メカニズム[RFC4103]です。

This document specifies how a Web Real-Time Communication (WebRTC) data channel [RFC8831] can be used as a transport mechanism for T.140 and how the Session Description Protocol (SDP) offer/answer mechanism for data channels [RFC8864] can be used to negotiate such a data channel.

この文書は、Webリアルタイム通信（WebRTC）データチャネル[RFC8831]を T.140のトランスポートメカニズムとしてどのように使用できるか、 およびそのようなデータチャネルをネゴシエートするために、データチャネル用のセッション記述プロトコル（SDP）のオファー/アンサーメカニズム[RFC8864]をどのように使用できるかを規定します。

In this document, a T.140 data channel refers to a WebRTC data channel for which the instantiated subprotocol is "t140" and where the channel is negotiated using the SDP offer/answer mechanism [RFC8864].

この文書では、T.140データチャネルとは、インスタンス化されたサブプロトコルが"t140"であり、 SDPのオファー/アンサーメカニズム[RFC8864]を使用してネゴシエートされるWebRTCデータチャネルを指します。

NOTE: The decision to transport real-time text using a WebRTC data channel instead of using RTP-based transport [RFC4103] is motivated by use case "U-C 5: Real-time text chat during an audio and/or video call with an individual or with multiple people in a conference"; see Section 3.2 of [RFC8831].

注: RTPベースのトランスポート[RFC4103]を使用する代わりに、WebRTCデータチャネルを使用してリアルタイムテキストを転送するという決定は、 ユースケース「U-C 5: Real-time text chat during an audio and/or video call with an individual or with multiple people in a conference」 （個人または会議の複数の参加者との音声通話やビデオ通話中のリアルタイムテキストチャット）に動機付けられています。 [RFC8831]のSection 3.2を参照してください。

The brief notation "T.140" is used as a name for the text conversation protocol according to [T140].

[T140]に従ったテキスト会話プロトコルの名前として、「T.140」という短い表記を使用します。

Real-time text is intended to be entered by human users via a keyboard, handwriting recognition, voice recognition, or any other input method. The rate of character entry is usually at a level of a few characters per second or less.

リアルタイムテキストは、人間のユーザーがキーボード、手書き認識、音声認識、その他の入力方法で入力することを想定しています。 文字の入力速度は、通常は毎秒数文字以下の水準です。

Section 3 defines the generic data channel properties for a T.140 data channel, and Section 4 defines how they are conveyed in an SDP 'dcmap' attribute. While this document defines how to negotiate a T.140 data channel using the SDP offer/answer mechanism [RFC8864], the generic T.140 and gateway considerations defined in Sections 3, 5, and 6 of this document can also be applied when a T.140 data channel is established using another mechanism (e.g., the mechanism defined in [RFC8832]). Section 5 of [RFC8864] defines the mapping between the SDP 'dcmap' attribute parameters and the protocol parameters used in [RFC8832].

Section 3ではT.140データチャネルの汎用的なデータチャネルプロパティーを定義し、 Section 4ではそれらをSDPの'dcmap'属性でどのように伝達するかを定義します。 この文書はSDPのオファー/アンサーメカニズム[RFC8864]を使用してT.140データチャネルをネゴシエートする方法を定義していますが、 この文書のセクション3、5、 6で定義する汎用的なT.140とゲートウェイに関する考慮事項は、 別のメカニズム（たとえば、[RFC8832]で定義されたメカニズム）を使用してT.140データチャネルを確立する場合にも適用できます。 [RFC8864]のSection 5は、 SDPの'dcmap'属性パラメーターと、[RFC8832]で使用されるプロトコルパラメーターとの対応付けを定義しています。

This document updates [RFC8373] by defining how the SDP 'hlang-send' and 'hlang-recv' attributes are used for the "application/webrtc-datachannel" media type.

この文書は、SDPの'hlang-send'属性と'hlang-recv'属性を"application/webrtc-datachannel"メディアタイプに対してどのように使用するかを定義することにより、 [RFC8373]を更新します。

NOTE: T.140 requires the transport channel to provide transmission of real-time text without duplication and in original order. Therefore, T.140 does not specify reliable and ordered transmission of T.140 data on the application layer. Instead, when RTP-based transport is used, the RTP sequence number is used to detect packet loss and out-of-order packets, and a redundancy mechanism is used to achieve reliable delivery of T.140 data. By using the WebRTC data channel's reliable and in-order transmission features [RFC8831] for the T.140 data channel, there is no need for a redundancy mechanism or a mechanism to detect data loss and out-of-order delivery at the application level. The latency characteristics of the T.140 data channel are also regarded as sufficient to meet the application requirements of T.140.

注: T.140は、トランスポートチャネルが重複なしで元の順序どおりにリアルタイムテキストを送信することを要求しています。 そのため、T.140はアプリケーション層でのT.140データの信頼性のある順序どおりの送信を規定していません。 代わりに、RTPベースのトランスポートを使用する場合は、RTPシーケンス番号を使用してパケットロスと順序の乱れたパケットを検出し、 冗長化メカニズムを使用してT.140データの信頼性のある配送を実現します。 T.140データチャネルにWebRTCデータチャネルの信頼性のある順序どおりの送信機能[RFC8831]を使用することにより、 アプリケーションレベルで冗長化メカニズムや、データの損失と順序の乱れた配送を検出するメカニズムが不要になります。 また、T.140データチャネルの遅延特性は、T.140のアプリケーション要件を満たすのに十分であるとみなされています。

4. SDP Considerations

4. SDPに関する考慮事項

The generic SDP considerations, including the SDP offer/answer procedures [RFC3264], for negotiating a WebRTC data channel are defined in [RFC8864]. This section, and its subsections, define the SDP considerations that are specific to a T.140 data channel, identified by the 'subprotocol' attribute parameter, with a "t140" parameter value, in the 'dcmap' attribute.

WebRTCデータチャネルをネゴシエートするための、SDPのオファー/アンサー手順[RFC3264]を含む汎用的なSDPに関する考慮事項は、 [RFC8864]で定義されています。 このセクションとそのサブセクションでは、'dcmap'属性内の'subprotocol'属性パラメーターのパラメーター値"t140"によって識別されるT.140データチャネルに固有の、SDPに関する考慮事項を定義します。

4.1. Use of the 'dcmap' Attribute

4.1. 'dcmap'属性の使用

An offerer and answerer MUST, in each offer and answer, include an SDP 'dcmap' attribute [RFC8864] in the SDP media description ("m=" section) [RFC4566] describing the Stream Control Transmission Protocol (SCTP) association [RFC4960] used to realize the T.140 data channel.

オファー側とアンサー側は、各オファーとアンサーにおいて、T.140データチャネルを実現するために使用するストリーム制御伝送プロトコル（SCTP）アソシエーション[RFC4960]を記述する SDPメディア記述（"m="セクション）[RFC4566]に、 SDPの'dcmap'属性[RFC8864]を含めなければなりません（MUST）。

The offerer and answerer MUST include the 'subprotocol' attribute parameter, with a "t140" parameter value, in the 'dcmap' attribute.

オファー側とアンサー側は、'dcmap'属性に、パラメーター値が"t140"である'subprotocol'属性パラメーターを含めなければなりません（MUST）。

The offerer and answerer MAY include the 'priority' attribute parameter and the 'label' attribute parameter in the 'dcmap' attribute value, as specified in [RFC8864].

オファー側とアンサー側は、[RFC8864]で規定されているように、 'dcmap'属性値に'priority'属性パラメーターと'label'属性パラメーターを含めてもよいです（MAY）。

NOTE: As specified in [RFC8831], when a data channel is negotiated using the mechanism defined in [RFC8832], the 'label' attribute parameter value has to be the same in both directions. That rule also applies to data channels negotiated using the mechanism defined in this document.

注: [RFC8831]で規定されているように、 [RFC8832]で定義されたメカニズムを使用してデータチャネルをネゴシエートする場合、 'label'属性パラメーターの値は両方向で同じである必要があります。 この規則は、この文書で定義するメカニズムを使用してネゴシエートされるデータチャネルにも適用されます。

The offerer and answerer MUST NOT include the 'max-retr' or 'max-time' attribute parameter in the 'dcmap' attribute. If either of those attribute parameters is received in an offer, the answerer MUST reject the offer. If either of those attribute parameters is received in an answer, the offerer MUST NOT accept the answer. Instead, the answerer MUST take appropriate actions, e.g., by sending a new offer without a T.140 data channel or by terminating the session.

オファー側とアンサー側は、'dcmap'属性に'max-retr'属性パラメーターや'max-time'属性パラメーターを含めてはなりません（MUST NOT）。 これらの属性パラメーターのいずれかをオファーで受信した場合、アンサー側はそのオファーを拒否しなければなりません（MUST）。 これらの属性パラメーターのいずれかをアンサーで受信した場合、オファー側はそのアンサーを受け入れてはなりません（MUST NOT）。 代わりに、アンサー側は、たとえばT.140データチャネルを含まない新しいオファーを送信したり、セッションを終了したりするなど、適切な措置を講じなければなりません（MUST）。

If the 'ordered' attribute parameter is included in the 'dcmap' attribute, it MUST be assigned the value 'true'.

'dcmap'属性に'ordered'属性パラメーターが含まれる場合、その値は'true'でなければなりません（MUST）。

Below is an example of the 'dcmap' attribute for a T.140 data channel with stream id=3 and without any label:

以下は、ストリームID=3でラベルのないT.140データチャネルに対する'dcmap'属性の例です。

a=dcmap:3 subprotocol="t140"

a=dcmap:3 subprotocol="t140"

4.2. Use of the 'dcsa' Attribute

4.2. 'dcsa'属性の使用

An offerer and answerer can, in each offer and answer, include one or more SDP 'dcsa' attributes [RFC8864] in the "m=" section describing the SCTP association used to realize the T.140 data channel.

オファー側とアンサー側は、各オファーとアンサーにおいて、T.140データチャネルを実現するために使用するSCTPアソシエーションを記述する"m="セクションに、 1つ以上のSDPの'dcsa'属性[RFC8864]を含めることができます。

If an offerer or answerer receives a 'dcsa' attribute that contains an SDP attribute whose usage has not been defined for a T.140 data channel, the offerer or answerer should ignore the 'dcsa' attribute, following the rules in Section 6.7 of [RFC8864].

T.140データチャネルに対する使用方法が定義されていないSDP属性を含む'dcsa'属性を受信した場合、 オファー側またはアンサー側は、[RFC8864]のSection 6.7の規則に従って、その'dcsa'属性を無視すべきです。

4.2.1. Maximum Character Transmission Rate

4.2.1. 最大文字送信レート

A 'dcsa' attribute can contain the SDP 'fmtp' attribute, which is used to indicate a maximum character transmission rate [RFC4103]. The 'cps' attribute parameter is used to indicate the maximum character transmission rate that the endpoint that includes the attribute is able to receive, and the value is used as a mean value in characters per second over any 10-second interval.

'dcsa'属性には、最大文字送信レート[RFC4103]を示すために使用されるSDPの'fmtp'属性を含めることができます。 'cps'属性パラメーターは、その属性を含めたエンドポイントが受信できる最大文字送信レートを示すために使用され、 その値は、任意の10秒間における毎秒の文字数の平均値として使用されます。

If the 'fmtp' attribute is included, the 'format' attribute parameter value MUST be set to 't140'.

'fmtp'属性を含める場合、'format'属性パラメーターの値は't140'に設定しなければなりません（MUST）。

If no 'fmtp' attribute with a 'cps' attribute parameter is included, the default value of 30 applies [RFC4103].

'cps'属性パラメーターを持つ'fmtp'属性が含まれていない場合は、デフォルト値の30が適用されます[RFC4103]。

The offerer and answerer MAY modify the 'cps' attribute parameter value in subsequent offers and answers.

オファー側とアンサー側は、後続のオファーとアンサーで'cps'属性パラメーターの値を変更してもよいです（MAY）。

This document does not define any other usage of the 'fmtp' attribute for a T.140 channel. If an offerer or answerer receives a 'dcsa' attribute that contains an 'fmtp' attribute that is not set according to the procedure above, the offerer or answerer MUST ignore the 'dcsa' attribute.

この文書は、T.140チャネルに対する'fmtp'属性のその他の使用方法は定義しません。 上記の手順に従って設定されていない'fmtp'属性を含む'dcsa'属性を受信した場合、オファー側またはアンサー側はその'dcsa'属性を無視しなければなりません（MUST）。

NOTE: The 'cps' attribute parameter is especially useful when a T.140 data channel endpoint is acting as a gateway (Section 6) and is interworking with a T.140 transport mechanism that has restrictions on how many characters can be sent per second.

注: 'cps'属性パラメーターは、T.140データチャネルのエンドポイントがゲートウェイとして動作し（Section 6）、 1秒あたりに送信できる文字数に制限のあるT.140トランスポートメカニズムと相互接続している場合に特に有用です。

If an endpoint receives text at a higher rate than it can handle, e.g., because the sending endpoint does not support the 'cps' attribute parameter, it SHOULD either (1) indicate to the sending endpoint that it is not willing to receive more text, using the direction attributes (Section 4.2.3) or (2) use a flow-control mechanism to reduce the rate. However, in certain applications, e.g., emergency services, it is important to regain human interaction as soon as possible, and it might therefore be more appropriate to simply discard the received overflow, insert a mark for loss [T140ad1], and continue to process the received text as soon as possible.

たとえば送信側エンドポイントが'cps'属性パラメーターをサポートしていないなどの理由で、エンドポイントが処理できるよりも高いレートでテキストを受信した場合、 そのエンドポイントは、(1) 方向属性（Section 4.2.3）を使用して、これ以上テキストを受信する意思がないことを送信側エンドポイントに示すか、 (2) フロー制御メカニズムを使用してレートを下げるかのいずれかを行うべきです（SHOULD）。 ただし、緊急サービスなどの特定のアプリケーションでは、人間同士のやりとりをできるだけ早く回復することが重要であるため、 受信したあふれた分を単に破棄し、損失を示すマーク[T140ad1]を挿入して、受信したテキストの処理をできるだけ早く継続するほうが適切な場合があります。

NOTE: At the time of writing this specification, the standardized API for WebRTC data channels does not support flow control. Should such support be available at some point, a receiving endpoint might use it in order to slow down the rate of text received from the sending endpoint.

注: この仕様の執筆時点では、WebRTCデータチャネル用の標準化されたAPIはフロー制御をサポートしていません。 将来そのようなサポートが利用可能になった場合、受信側エンドポイントは、送信側エンドポイントから受信するテキストのレートを下げるためにそれを使用できるでしょう。

4.2.2. Real-Time Text Conversation Languages

4.2.2. リアルタイムテキスト会話の言語

'dcsa' attributes can contain the SDP 'hlang-send' and 'hlang-recv' attributes [RFC8373] to negotiate the language to be used for the real-time text conversation.

'dcsa'属性には、リアルタイムテキスト会話で使用する言語をネゴシエートするために、 SDPの'hlang-send'属性と'hlang-recv'属性[RFC8373]を含めることができます。

For a T.140 data channel, the modality is "written" [RFC8373].

T.140データチャネルの場合、モダリティーは"written"です[RFC8373]。

4.2.3. Real-Time Text Direction

4.2.3. リアルタイムテキストの方向

'dcsa' attributes can contain the SDP 'sendonly', 'recvonly', 'sendrecv', and 'inactive' attributes [RFC4566] to negotiate the direction in which text can be transmitted in a real-time text conversation.

'dcsa'属性には、リアルタイムテキスト会話においてテキストを送信できる方向をネゴシエートするために、 SDPの'sendonly'属性、'recvonly'属性、'sendrecv'属性、'inactive'属性[RFC4566]を含めることができます。

NOTE: A WebRTC data channel is always bidirectional. The usage of the 'dcsa' attribute only affects the direction in which implementations are allowed to transmit text on a T.140 data channel.

注: WebRTCデータチャネルは常に双方向です。 'dcsa'属性の使用は、実装がT.140データチャネル上でテキストを送信することを許可される方向にのみ影響します。

The offer/answer rules for the direction attributes are based on the rules for unicast streams defined in [RFC3264], as described below. Note that the rules only apply to the direction attributes.

方向属性に関するオファー/アンサーの規則は、以下で説明するように、[RFC3264]で定義されたユニキャストストリームの規則に基づいています。 これらの規則は方向属性にのみ適用されることに注意してください。

Session-level direction attributes [RFC4566] have no impact on a T.140 data channel.

セッションレベルの方向属性[RFC4566]は、T.140データチャネルには影響しません。

4.2.3.1. Generating an Offer
4.2.3.1. オファーの生成

If the offerer wishes to both send and receive text on a T.140 data channel, it SHOULD mark the data channel as sendrecv with a 'sendrecv' attribute inside a 'dcsa' attribute. If the offerer does not explicitly mark the data channel, an implicit 'sendrecv' attribute inside a 'dcsa' attribute is applied by default.

オファー側がT.140データチャネル上でテキストの送信と受信の両方を行いたい場合、 'dcsa'属性内の'sendrecv'属性によって、そのデータチャネルをsendrecvとしてマークするべきです（SHOULD）。 オファー側がデータチャネルを明示的にマークしない場合は、デフォルトで、'dcsa'属性内の暗黙の'sendrecv'属性が適用されます。

If the offerer wishes to only send text on a T.140 data channel, it MUST mark the data channel as sendonly with a 'sendonly' attribute inside a 'dcsa' attribute.

オファー側がT.140データチャネル上でテキストの送信のみを行いたい場合、 'dcsa'属性内の'sendonly'属性によって、そのデータチャネルをsendonlyとしてマークしなければなりません（MUST）。

If the offerer wishes to only receive text on a T.140 data channel, it MUST mark the data channel as recvonly with a 'recvonly' attribute inside a 'dcsa' attribute.

オファー側がT.140データチャネル上でテキストの受信のみを行いたい場合、 'dcsa'属性内の'recvonly'属性によって、そのデータチャネルをrecvonlyとしてマークしなければなりません（MUST）。

If the offerer wishes to neither send nor receive text on a T.140 data channel, it MUST mark the data channel as inactive with an 'inactive' attribute inside a 'dcsa' attribute.

オファー側がT.140データチャネル上でテキストの送信も受信も行いたくない場合、 'dcsa'属性内の'inactive'属性によって、そのデータチャネルをinactiveとしてマークしなければなりません（MUST）。

If the offerer has marked a data channel as sendrecv (or if the offerer did not explicitly mark the data channel) or recvonly, it MUST be prepared to receive T.140 data as soon as the state of the T.140 data channel allows it.

オファー側がデータチャネルをsendrecvとしてマークした場合（またはオファー側がデータチャネルを明示的にマークしなかった場合）、あるいはrecvonlyとしてマークした場合、 オファー側は、T.140データチャネルの状態が許す限りすぐにT.140データを受信できるよう準備しなければなりません（MUST）。

4.2.3.2. Generating an Answer
4.2.3.2. アンサーの生成

When the answerer accepts an offer and marks the direction of the text in the corresponding answer, the direction is based on the marking (or the lack of explicit marking) in the offer.

アンサー側がオファーを受け入れ、対応するアンサーでテキストの方向をマークする場合、その方向はオファーにおけるマーク（または明示的なマークがないこと）に基づきます。

If the offerer either explicitly marked the data channel as sendrecv or did not mark the data channel, the answerer SHOULD mark the data channel as sendrecv, sendonly, recvonly, or inactive with a 'sendrecv', 'sendonly', 'recvonly', or 'inactive' attribute, respectively, inside a 'dcsa' attribute. If the answerer does not explicitly mark the data channel, an implicit 'sendrecv' attribute inside a 'dcsa' attribute is applied by default.

オファー側がデータチャネルを明示的にsendrecvとしてマークしたか、データチャネルをマークしなかった場合、 アンサー側は、'dcsa'属性内の'sendrecv'属性、'sendonly'属性、'recvonly'属性、'inactive'属性によって、 そのデータチャネルをそれぞれsendrecv、sendonly、recvonly、inactiveとしてマークするべきです（SHOULD）。 アンサー側がデータチャネルを明示的にマークしない場合は、デフォルトで、'dcsa'属性内の暗黙の'sendrecv'属性が適用されます。

If the offerer marked the data channel as sendonly, the answerer MUST mark the data channel as recvonly or inactive with a 'recvonly' or 'inactive' attribute, respectively, inside a 'dcsa' attribute.

オファー側がデータチャネルをsendonlyとしてマークした場合、アンサー側は、'dcsa'属性内の'recvonly'属性または'inactive'属性によって、 そのデータチャネルをそれぞれrecvonlyまたはinactiveとしてマークしなければなりません（MUST）。

If the offerer marked the data channel as recvonly, the answerer MUST mark the data channel as sendonly or inactive with a 'sendonly' or 'inactive' attribute, respectively, inside a 'dcsa' attribute.

オファー側がデータチャネルをrecvonlyとしてマークした場合、アンサー側は、'dcsa'属性内の'sendonly'属性または'inactive'属性によって、 そのデータチャネルをそれぞれsendonlyまたはinactiveとしてマークしなければなりません（MUST）。

If the offerer marked the data channel as inactive, the answerer MUST mark the data channel as inactive with an 'inactive' attribute inside a 'dcsa' attribute.

オファー側がデータチャネルをinactiveとしてマークした場合、アンサー側は、'dcsa'属性内の'inactive'属性によって、 そのデータチャネルをinactiveとしてマークしなければなりません（MUST）。

If the answerer has marked a data channel as sendrecv or recvonly, it MUST be prepared to receive data as soon as the state of the T.140 data channel allows transmission of data.

アンサー側がデータチャネルをsendrecvまたはrecvonlyとしてマークした場合、 アンサー側は、T.140データチャネルの状態がデータの送信を許す限りすぐにデータを受信できるよう準備しなければなりません（MUST）。

4.2.3.3. Offerer Receiving an Answer
4.2.3.3. オファー側によるアンサーの受信

When the offerer receives an answer to the offer and the answerer has marked a data channel as sendrecv (or the answerer did not mark the data channel) or recvonly in the answer, the offerer can start sending T.140 data as soon as the state of the T.140 data channel allows it. If the answerer has marked the data channel as inactive or sendonly, the offerer MUST NOT send any T.140 data.

オファー側がオファーに対するアンサーを受信し、アンサー側がアンサーでデータチャネルをsendrecvとしてマークした場合（またはアンサー側がデータチャネルをマークしなかった場合）、 あるいはrecvonlyとしてマークした場合、オファー側は、T.140データチャネルの状態が許す限りすぐにT.140データの送信を開始できます。 アンサー側がデータチャネルをinactiveまたはsendonlyとしてマークした場合、オファー側はT.140データを一切送信してはなりません（MUST NOT）。

If the answerer has not marked the direction of a T.140 data channel in accordance with the procedures above, it is RECOMMENDED that the offerer not process that scenario as an error situation but rather assume that the answerer might both send and receive T.140 data on the data channel.

アンサー側が上記の手順に従ってT.140データチャネルの方向をマークしていない場合、 オファー側はその状況をエラーとして処理せず、アンサー側がそのデータチャネル上でT.140データの送信と受信の両方を行う可能性があるとみなすことが推奨されます（RECOMMENDED）。

4.2.3.4. Modifying the Text Direction
4.2.3.4. テキストの方向の変更

If an endpoint wishes to modify a previously negotiated text direction in an ongoing session, it MUST initiate an offer that indicates the new direction, following the rules in Section 4.2.3.1. If the answerer accepts the offer, it follows the procedures in Section 4.2.3.2.

進行中のセッションにおいて、以前にネゴシエートしたテキストの方向を変更したい場合、 エンドポイントは、Section 4.2.3.1の規則に従って、新しい方向を示すオファーを開始しなければなりません（MUST）。 アンサー側がそのオファーを受け入れる場合、アンサー側はSection 4.2.3.2の手順に従います。

5. T.140 Considerations

5. T.140に関する考慮事項

5.1. Session-Layer Functions

5.1. セッション層の機能

Section 6.1 of [T140] describes the generic T.140 session control functions at a high level, in a manner that is independent of the signaling protocol. The list below describes how the functions are realized when using a T.140 data channel.

[T140]のセクション6.1では、汎用的なT.140セッション制御機能を、シグナリングプロトコルに依存しない形で大まかに説明しています。 以下のリストでは、T.140データチャネルを使用する場合にそれらの機能がどのように実現されるかを説明します。

Prepare session:
An endpoint can indicate its support of T.140 data channels using signaling-specific means (e.g., using SIP OPTIONS [RFC3261]) or by indicating the support in an offer or answer (Section 4).
Initiate session:
An offer is used to request the establishment of a T.140 data channel (Section 4).
Accept session:
An answer is used to accept a request to establish a T.140 data channel (Section 4).
Deny session:
An answer is used to reject a request to establish a T.140 data channel, using the generic procedures for rejecting a data channel [RFC8864].
Disconnect session:
An offer or answer is used to disable a previously established T.140 data channel, using the generic procedures for closing a data channel [RFC8864].
Data:
Data is sent on an established T.140 data channel (Section 5.2).
セッションの準備（Prepare session）:
エンドポイントは、シグナリング固有の手段（たとえば、SIP OPTIONS [RFC3261]の使用）によって、 またはオファーやアンサーでサポートを示すこと（Section 4）によって、T.140データチャネルのサポートを示すことができます。
セッションの開始（Initiate session）:
T.140データチャネルの確立を要求するためにオファーを使用します（Section 4）。
セッションの受け入れ（Accept session）:
T.140データチャネルの確立の要求を受け入れるためにアンサーを使用します（Section 4）。
セッションの拒否（Deny session）:
データチャネルを拒否するための汎用的な手順[RFC8864]を使用して、 T.140データチャネルの確立の要求を拒否するためにアンサーを使用します。
セッションの切断（Disconnect session）:
データチャネルを閉じるための汎用的な手順[RFC8864]を使用して、 以前に確立したT.140データチャネルを無効にするためにオファーまたはアンサーを使用します。
データ（Data）:
データは、確立されたT.140データチャネル上で送信されます（Section 5.2）。

5.2. Data Encoding and Sending

5.2. データの符号化と送信

T.140 text is encoded and framed as T140blocks [RFC4103].

T.140テキストは、T140block[RFC4103]として符号化され、フレーム化されます。

Each T140block is sent on the SCTP stream [RFC4960] used to realize the T.140 data channel using standard T.140 transmission procedures [T140]. One or more T140blocks can be sent in a single SCTP user message [RFC4960]. Unlike RTP-based transport for real-time text [RFC4103], T.140 data channels do not use redundant transmission of text; this is because the T.140 data channel achieves robust transmission by using the "reliable" mode of the data channel.

各T140blockは、標準のT.140送信手順[T140]を使用して、 T.140データチャネルを実現するために使用するSCTPストリーム[RFC4960]上で送信されます。 1つ以上のT140blockを単一のSCTPユーザーメッセージ[RFC4960]で送信できます。 リアルタイムテキストのRTPベースのトランスポート[RFC4103]とは異なり、T.140データチャネルはテキストの冗長送信を使用しません。 これは、T.140データチャネルが、データチャネルの"reliable"モードを使用することによって堅牢な送信を実現しているためです。

Data-sending procedures conform to [T140].

データ送信手順は[T140]に準拠します。

See Section 8 of [T140] for coding details.

符号化の詳細については、[T140]のセクション8を参照してください。

NOTE: The T.140 coding details contain information on optional control codes for controlling the presentation; these control codes may not be supported by the presentation level of the receiving application. The receiving application is expected to handle reception of such T.140 control codes appropriately (e.g., ignore and skip them) even if their effect on the presentation is not supported.

注: T.140の符号化の詳細には、表示を制御するための任意の制御コードに関する情報が含まれています。 これらの制御コードは、受信側アプリケーションの表示レベルでサポートされていない場合があります。 受信側アプリケーションは、表示への効果がサポートされていない場合でも、そのようなT.140制御コードの受信を適切に処理する（たとえば、無視して読み飛ばす）ことが期待されます。

5.3. Data Buffering

5.3. データのバッファリング

As described in [T140], buffering can be used to reduce overhead, with the maximum assigned transmission interval of T140blocks from the buffer being 500 ms as long as there is text to send.

[T140]で説明されているように、オーバーヘッドを減らすためにバッファリングを使用できます。 その場合、送信するテキストがある限り、バッファーからのT140blockの送信間隔として割り当てる最大値は500ミリ秒です。

Buffering MAY also be used for staying within the maximum character transmission rate (Section 4.2).

最大文字送信レート（Section 4.2）の範囲内に収めるためにバッファリングを使用してもよいです（MAY）。

An implementation needs to take the user requirements for smooth flow and low latency in real-time text conversation into consideration when assigning a transmission interval. It is RECOMMENDED to use the default transmission interval of 300 ms [RFC4103], for T.140 data channels. Implementers might also use lower values for specific applications requiring low latency, taking the increased overhead into consideration.

実装は、送信間隔を割り当てる際に、リアルタイムテキスト会話における滑らかな流れと低遅延というユーザーの要件を考慮する必要があります。 T.140データチャネルでは、デフォルトの送信間隔である300ミリ秒[RFC4103]を使用することが推奨されます（RECOMMENDED）。 実装者は、オーバーヘッドの増加を考慮したうえで、低遅延を必要とする特定のアプリケーションに対してより小さい値を使用することもできます。

5.4. Loss of T140blocks

5.4. T140blockの損失

In the case of network failure or congestion, T.140 data channels might fail and get torn down. If this happens but the session is sustained, it is RECOMMENDED that implementations try to reestablish the T.140 data channels. As a T.140 data channel does not provide a mechanism for the receiver to identify retransmitted T140blocks after channel reestablishment, the sending endpoint MUST NOT retransmit T140blocks. Similarly, a receiver SHOULD indicate to the user that a channel has been reestablished and text might have been lost. This MAY be done by inserting the missing text markers [T140ad1] or in any other way evident to the user.

ネットワーク障害や輻輳が発生した場合、T.140データチャネルが失敗し、切断される可能性があります。 これが発生してもセッションが維持されている場合、実装はT.140データチャネルの再確立を試みることが推奨されます（RECOMMENDED）。 T.140データチャネルは、チャネルの再確立後に再送されたT140blockを受信者が識別するためのメカニズムを提供しないため、 送信側エンドポイントはT140blockを再送してはなりません（MUST NOT）。 同様に、受信者は、チャネルが再確立され、テキストが失われた可能性があることをユーザーに示すべきです（SHOULD）。 これは、欠落テキストマーカー[T140ad1]を挿入することによって、 またはユーザーにとって明らかなその他の方法によって行ってもよいです（MAY）。

NOTE: If the SCTP association [RFC4960] used to realize the T.140 data channel fails and gets torn down, it needs to be reestablished before the T.140 data channel can be reestablished. After the T.140 data channel is reestablished, the procedures defined in this section apply, regardless of whether only the T.140 data channel or the whole SCTP association got torn down.

注: T.140データチャネルを実現するために使用するSCTPアソシエーション[RFC4960]が失敗して切断された場合、 T.140データチャネルを再確立する前に、そのSCTPアソシエーションを再確立する必要があります。 T.140データチャネルが再確立された後は、切断されたのがT.140データチャネルだけか、SCTPアソシエーション全体かにかかわらず、このセクションで定義する手順が適用されます。

5.5. Multi-party Considerations

5.5. マルチパーティーに関する考慮事項

If an implementation needs to support multi-party scenarios, the implementation needs to support multiple simultaneous T.140 data channels, one for each remote party. At the time of writing this document, this is true even in scenarios where each participant communicates via a centralized conference server. This is because, unlike RTP media, WebRTC data channels and the T.140 protocol do not support the indication of the source of T.140 data. The 'label' attribute parameter in the SDP 'dcmap' attribute (Section 4.1) can be used by the offerer to provide additional information about each T.140 data channel and help implementations to distinguish between them.

実装がマルチパーティーのシナリオをサポートする必要がある場合、実装はリモートの参加者ごとに1つずつ、複数のT.140データチャネルを同時にサポートする必要があります。 この文書の執筆時点では、各参加者が集中型の会議サーバーを介して通信するシナリオであっても、このことが当てはまります。 これは、RTPメディアとは異なり、WebRTCデータチャネルとT.140プロトコルがT.140データの送信元の表示をサポートしていないためです。 オファー側は、SDPの'dcmap'属性の'label'属性パラメーター（Section 4.1）を使用して、 各T.140データチャネルに関する追加情報を提供し、実装がそれらを区別するのを助けることができます。

NOTE: Future extensions to T.140 or the T140block might permit the indication of the source of T.140 data, in which case it might be possible to use a single T.140 data channel to transport data from multiple remote sources. The usage of a single T.140 data channel, without any protocol extensions, would require the conference server to only forward real-time text from one source at any given time and, for example, include human-readable text labels in the real-time text stream that indicate the source whenever the conference server switches the source. This would allow the receiver to present real-time text from different sources separately. The procedures for such a mechanism are outside the scope of this document.

注: T.140やT140blockに対する将来の拡張によって、T.140データの送信元を示せるようになるかもしれません。 その場合、単一のT.140データチャネルを使用して、複数のリモートの送信元からのデータを転送できる可能性があります。 プロトコル拡張なしで単一のT.140データチャネルを使用する場合、会議サーバーは、任意の時点で1つの送信元からのリアルタイムテキストのみを転送し、 たとえば、会議サーバーが送信元を切り替えるたびに、送信元を示す人間が読めるテキストラベルをリアルタイムテキストストリームに含める必要があるでしょう。 これにより、受信者は異なる送信元からのリアルタイムテキストを別々に表示できます。 そのようなメカニズムの手順は、この文書の範囲外です。

6. Gateway Considerations

6. ゲートウェイに関する考慮事項

A number of real-time text transports and protocols have been defined for both packet-switched and circuit-switched networks. Many are based on the ITU-T T.140 protocol at the application and presentation levels [T140]. At the time of writing this document, some mechanisms are no longer used, as the technologies they use have been obsoleted, while others are still in use.

パケット交換ネットワークと回線交換ネットワークの両方に対して、多数のリアルタイムテキストのトランスポートとプロトコルが定義されています。 その多くは、アプリケーションレベルと表示レベルでITU-T T.140プロトコル[T140]に基づいています。 この文書の執筆時点では、使用している技術が廃止されたためにもう使用されていないメカニズムもあれば、現在も使用されているメカニズムもあります。

When performing interworking between T.140 data channels and real-time text in other transports and protocols, a number of factors need to be considered. At the time of writing this document, the most common IP-based real-time text transport is the RTP-based mechanism defined in [RFC4103]. While this document does not define a complete interworking solution, the list below provides some guidance and considerations to take into account when designing a gateway for interworking between T.140 data channels and RTP-based T.140 transport:

T.140データチャネルと、他のトランスポートやプロトコルにおけるリアルタイムテキストとの間で相互接続を行う場合、多くの要因を考慮する必要があります。 この文書の執筆時点で、最も一般的なIPベースのリアルタイムテキストのトランスポートは、[RFC4103]で定義されたRTPベースのメカニズムです。 この文書は完全な相互接続ソリューションを定義していませんが、以下のリストでは、T.140データチャネルとRTPベースのT.140トランスポートとの間で相互接続を行うゲートウェイを設計する際に考慮すべきガイダンスと考慮事項を示します。

  • For each T.140 data channel, there is an RTP stream for real-time text [RFC4103]. Redundancy is by default declared and used on the RTP stream. There is no redundancy on the T.140 data channel, but the reliable property [RFC8864] is set on it.
  • During a normal text flow, T140blocks received from one network are forwarded towards the other network. Keepalive traffic is handled by lower layers on the T.140 data channel. A gateway might have to extract keepalives from incoming RTP streams and MAY generate keepalives on outgoing RTP streams.
  • If the gateway detects or suspects loss of data on the RTP stream and the lost data has not been retrieved using a redundancy mechanism, the gateway SHOULD insert the T.140 missing text marker [T140ad1] in the data sent on the outgoing T.140 data channel.
  • If the gateway detects that the T.140 data channel has failed and got torn down, once the data channel has been reestablished the gateway SHOULD insert the T.140 missing text marker [T140ad1] in the data sent on the outgoing RTP stream if it detects or suspects that data sent by the remote T.140 data channel endpoint was lost.
  • If the gateway detects that the T.140 data channel has failed and got torn down, once the data channel has been reestablished the gateway SHOULD insert the T.140 missing text marker [T140ad1] in the data sent on the outgoing T.140 data channel if it detects or suspects that data sent or to be sent on the T.140 data channel was lost during the failure.
  • The gateway MUST indicate the same text transmission direction (Section 4.2.3) on the T.140 data channel and the RTP stream.
  • 各T.140データチャネルに対して、リアルタイムテキスト用のRTPストリーム[RFC4103]が1つ存在します。 RTPストリームでは、デフォルトで冗長性が宣言され、使用されます。 T.140データチャネルには冗長性はありませんが、信頼性（reliable）プロパティー[RFC8864]が設定されます。
  • 通常のテキストの流れでは、一方のネットワークから受信したT140blockは、もう一方のネットワークに向けて転送されます。 T.140データチャネルでは、キープアライブのトラフィックは下位層によって処理されます。 ゲートウェイは、受信するRTPストリームからキープアライブを取り出す必要がある場合があり、送信するRTPストリームでキープアライブを生成してもよいです（MAY）。
  • ゲートウェイがRTPストリーム上のデータの損失を検出または疑い、失われたデータが冗長化メカニズムを使用して回復されていない場合、 ゲートウェイは、送信するT.140データチャネル上で送信するデータにT.140の欠落テキストマーカー[T140ad1]を挿入するべきです（SHOULD）。
  • T.140データチャネルが失敗して切断されたことをゲートウェイが検出した場合、データチャネルが再確立された後で、 リモートのT.140データチャネルのエンドポイントが送信したデータが失われたことを検出または疑うならば、 ゲートウェイは、送信するRTPストリーム上で送信するデータにT.140の欠落テキストマーカー[T140ad1]を挿入するべきです（SHOULD）。
  • T.140データチャネルが失敗して切断されたことをゲートウェイが検出した場合、データチャネルが再確立された後で、 T.140データチャネル上で送信した、または送信する予定だったデータが障害中に失われたことを検出または疑うならば、 ゲートウェイは、送信するT.140データチャネル上で送信するデータにT.140の欠落テキストマーカー[T140ad1]を挿入するべきです（SHOULD）。
  • ゲートウェイは、T.140データチャネルとRTPストリームで同じテキスト送信方向（Section 4.2.3）を示さなければなりません（MUST）。

NOTE: In order for the gateway to insert a missing text marker or perform other actions that require that the gateway have access to the T.140 data, the T.140 data cannot be encrypted end to end between the T.140 data channel endpoint and the RTP endpoint. At the time of writing this document, no mechanism to provide such end-to-end encryption is defined.

注: ゲートウェイが欠落テキストマーカーを挿入したり、ゲートウェイがT.140データにアクセスする必要があるその他の動作を行ったりするためには、 T.140データチャネルのエンドポイントとRTPエンドポイントとの間で、T.140データをエンドツーエンドで暗号化することはできません。 この文書の執筆時点では、そのようなエンドツーエンドの暗号化を提供するメカニズムは定義されていません。

NOTE: The guidance and considerations above are for two-party connections. At the time of writing this specification, a multi-party solution for RTP-based T.140 transport had not yet been specified. Once such a solution is specified, it might have an impact on the above interworking guidance and considerations.

注: 上記のガイダンスと考慮事項は、2者間の接続を対象としています。 この仕様の執筆時点では、RTPベースのT.140トランスポートに対するマルチパーティーのソリューションはまだ規定されていませんでした。 そのようなソリューションが規定されると、上記の相互接続のガイダンスと考慮事項に影響を与える可能性があります。

7. Update to RFC 8373

7. RFC 8373の更新

This document updates [RFC8373] by defining how the SDP 'hlang-send' and 'hlang-recv' attributes are used for the "application/webrtc-datachannel" media type.

この文書は、SDPの'hlang-send'属性と'hlang-recv'属性を"application/webrtc-datachannel"メディアタイプに対してどのように使用するかを定義することにより、 [RFC8373]を更新します。

SDP offerers and answerers MUST NOT include the attributes directly in the "m=" section associated with the "application/webrtc-datachannel" media type. Instead, the attributes MUST be associated with individual data channels, using the SDP 'dcsa' attribute. A specification that defines a subprotocol that uses the attributes MUST specify the modality for that subprotocol, or how to retrieve the modality if the subprotocol supports multiple modalities. The subprotocol is indicated using the SDP 'dcmap' attribute.

SDPのオファー側とアンサー側は、"application/webrtc-datachannel"メディアタイプに関連付けられた"m="セクションに、これらの属性を直接含めてはなりません（MUST NOT）。 代わりに、これらの属性は、SDPの'dcsa'属性を使用して個々のデータチャネルに関連付けなければなりません（MUST）。 これらの属性を使用するサブプロトコルを定義する仕様は、そのサブプロトコルのモダリティーを規定するか、サブプロトコルが複数のモダリティーをサポートする場合はモダリティーを取得する方法を規定しなければなりません（MUST）。 サブプロトコルは、SDPの'dcmap'属性を使用して示されます。

8. Security Considerations

8. セキュリティーに関する考慮事項

The generic WebRTC security considerations are defined in [RFC8826] and [RFC8827].

WebRTCの汎用的なセキュリティーに関する考慮事項は、[RFC8826]と[RFC8827]で定義されています。

The generic security considerations for WebRTC data channels are defined in [RFC8831]. As data channels are always encrypted by design, the T.140 data channels will also be encrypted.

WebRTCデータチャネルの汎用的なセキュリティーに関する考慮事項は、[RFC8831]で定義されています。 データチャネルは設計上常に暗号化されるため、T.140データチャネルも暗号化されます。

The generic security considerations for negotiating data channels using the SDP offer/answer mechanism are defined in [RFC8864]. There are no additional security considerations specific to T.140 data channels.

SDPのオファー/アンサーメカニズムを使用してデータチャネルをネゴシエートする場合の汎用的なセキュリティーに関する考慮事項は、[RFC8864]で定義されています。 T.140データチャネルに固有の追加のセキュリティーに関する考慮事項はありません。

When performing interworking between T.140 data channels and RTP-based T.140 transport [RFC4103], in order for a gateway to insert a missing text marker or perform other actions that require that the gateway have access to the T.140 data, the T.140 data cannot be encrypted end to end between the T.140 data channel endpoint and the RTP endpoint.

T.140データチャネルとRTPベースのT.140トランスポート[RFC4103]との間で相互接続を行う場合、 ゲートウェイが欠落テキストマーカーを挿入したり、ゲートウェイがT.140データにアクセスする必要があるその他の動作を行ったりするためには、 T.140データチャネルのエンドポイントとRTPエンドポイントとの間で、T.140データをエンドツーエンドで暗号化することはできません。
