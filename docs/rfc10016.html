RFC 10016

System-Defined Configuration

RFC 10016

システム定義の設定

Abstract

概要

The Network Management Datastore Architecture (NMDA) in RFC 8342 defines several configuration datastores holding configuration. The contents of these configuration datastores are controlled by clients. This document introduces the concept of a system configuration datastore holding configuration controlled by the system on which a server is running. The system configuration can be referenced (e.g., leafref) by configuration explicitly created by clients.

RFC 8342のネットワーク管理データストアアーキテクチャー（Network Management Datastore Architecture: NMDA）は、設定を保持するいくつかの設定データストアを定義しています。 これらの設定データストアの内容はクライアントによって制御されます。 この文書は、サーバーが動作しているシステムによって制御される設定を保持する、システム設定データストアの概念を導入します。 システム設定は、クライアントによって明示的に作成された設定から（たとえばleafrefによって）参照できます。

This document updates RFC 8342.

この文書はRFC 8342を更新します。

1. Introduction

1. はじめに

The Network Management Datastore Architecture (NMDA) [RFC8342] defines system configuration as the configuration that is supplied by the device itself and appears in <operational> when it is in use (see Figure 2 in [RFC8342]).

ネットワーク管理データストアアーキテクチャー（NMDA）[RFC8342]は、システム設定を、デバイス自体によって提供され、使用中の場合に<operational>に現れる設定として定義しています（[RFC8342]の図2を参照）。

However, there is a desire from operators to enable a server to better expose the system configuration, regardless of whether it is in use. For example, some implementations define the system configuration that must be referenced to be active. Network Configuration Protocol (NETCONF) / RESTCONF clients can benefit from a standard mechanism to retrieve what system configuration is available on a server.

しかし、運用者からは、使用中であるかどうかにかかわらず、サーバーがシステム設定をよりよく公開できるようにしたいという要望があります。 たとえば、一部の実装は、有効になるためには参照されなければならないシステム設定を定義しています。 ネットワーク設定プロトコル（NETCONF）やRESTCONFのクライアントは、サーバー上でどのようなシステム設定が利用可能かを取得するための標準的なメカニズムから恩恵を受けることができます。

Some servers allow the descendant nodes of system-defined configuration to be configured or modified. For example, the system configuration may contain an almost empty physical interface, whose existence in the system configuration is tied to the presence of particular hardware, while the client needs to be able to add, modify, or remove a number of descendant nodes. Some descendant nodes may not be modifiable (e.g., the interface "type" set by the system).

一部のサーバーでは、システム定義の設定の子孫ノードを設定または変更できます。 たとえば、システム設定には、ほとんど空の物理インターフェースが含まれている場合があります。システム設定におけるその存在は特定のハードウェアの存在に結び付いていますが、クライアントはいくつかの子孫ノードを追加、変更、または削除できる必要があります。 一部の子孫ノードは変更できない場合があります（たとえば、システムによって設定されたインターフェースの「type」）。

This document updates the NMDA defined in [RFC8342] with a read-only conventional configuration datastore called "system" to expose system-defined configuration. The solution enables configuration explicitly created by the clients to reference nodes defined in <system>, override system-provided values, and configure descendant nodes of system-defined configuration.

この文書は、[RFC8342]で定義されているNMDAを更新し、システム定義の設定を公開するために、「system」と呼ばれる読み取り専用の従来型設定データストアを追加します。 この解決策により、クライアントによって明示的に作成された設定が、<system>で定義されたノードを参照したり、システムが提供する値を上書きしたり、システム定義の設定の子孫ノードを設定したりできるようになります。

The solution defined in this document requires the use of NMDA for both clients and servers. Conformance to this document requires NMDA servers implement the "ietf-system-datastore" YANG module (Section 7).

この文書で定義する解決策では、クライアントとサーバーの両方がNMDAを使用する必要があります。 この文書に準拠するには、NMDAサーバーが「ietf-system-datastore」YANGモジュール（Section 7）を実装する必要があります。

1.1. Terminology

1.1. 用語

This document assumes that the reader is familiar with the contents of [RFC6241], [RFC7950], [RFC8342], and [RFC8525] and uses terminologies from those documents. The terms "device" and "server" are used interchangeably in this document.

この文書は、読者が[RFC6241]、[RFC7950]、[RFC8342]、および[RFC8525]の内容に精通していることを前提としており、それらの文書の用語を使用します。 この文書では、「デバイス」と「サーバー」という用語は同じ意味で使用されます。

The following terms are defined in this document:

この文書では、次の用語を定義します：

system configuration:
[RFC8342] defines it as "Configuration that is supplied by the device itself". The definition herein refines that definition to represent configuration present in the system configuration datastore (regardless of whether it is applied or referenced). It may also be referred to as "system-defined configuration" or "system-provided configuration" throughout this document. The system configuration discussed in this document cannot be deletable; configuration provided by the server that is deletable is outside the scope of this document.
system configuration datastore:
This is a configuration datastore holding configuration provided by the system itself. This datastore is referred to as "<system>".
システム設定（system configuration）：
[RFC8342]はこれを「デバイス自体によって提供される設定」と定義しています。 ここでの定義は、その定義を改良し、（適用されているか参照されているかにかかわらず）システム設定データストアに存在する設定を表すものとします。 この文書全体を通して、これは「システム定義の設定（system-defined configuration）」または「システムが提供する設定（system-provided configuration）」とも呼ばれることがあります。 この文書で議論するシステム設定は削除できません。サーバーによって提供される削除可能な設定は、この文書の範囲外です。
システム設定データストア（system configuration datastore）：
システム自体によって提供される設定を保持する設定データストアです。 このデータストアは「<system>」と呼ばれます。

This document redefines the term "conventional configuration datastore" in Section 3 of [RFC8342] to add "system" to the list of conventional configuration datastores:

この文書は、従来型設定データストアのリストに「system」を追加するために、[RFC8342]のSection 3の用語「従来型設定データストア（conventional configuration datastore）」を再定義します：

conventional configuration datastore:
One of the following set of configuration datastores: <running>, <startup>, <candidate>, <system>, and <intended>. These datastores share a common datastore schema, and protocol operations allow copying data between these datastores. The term "conventional" is chosen as a generic umbrella term for these datastores. Note that while protocol operations allow copying data between conventional datastores, the read-only nature of datastores such as <system> and <intended> restricts clients from copying data into them.
system node:
This is an instance in the data tree that is provided by the system itself. System node may also be called "system-defined node" or "system-provided node" throughout this document.
referenced node:

A referenced node is one of the following:

  • Targets of leafref values defined via the "path" statement.

  • Targets of "instance-identifier" type values.

  • Nodes present in an XPath expression of "when" constraints.

  • Nodes present in an XPath expression of "must" constraints.

  • Nodes defined to satisfy the "mandatory true" constraints.

  • Nodes defined to satisfy the "min-elements" constraints.

従来型設定データストア（conventional configuration datastore）：
次の設定データストアの集合のうちの1つです：<running>、<startup>、<candidate>、<system>、および<intended>。 これらのデータストアは共通のデータストアスキーマを共有し、プロトコル操作によってこれらのデータストア間でデータをコピーできます。 「従来型（conventional）」という用語は、これらのデータストアを総称する一般的な用語として選ばれています。 プロトコル操作によって従来型データストア間でデータをコピーできますが、<system>や<intended>などのデータストアは読み取り専用であるため、クライアントはそれらにデータをコピーできないことに注意してください。
システムノード（system node）：
システム自体によって提供される、データツリー内のインスタンスです。 この文書全体を通して、システムノードは「システム定義のノード（system-defined node）」または「システムが提供するノード（system-provided node）」とも呼ばれることがあります。
参照されるノード（referenced node）：

参照されるノードとは、次のいずれかです：

  • 「path」文によって定義されたleafrefの値の対象。

  • 「instance-identifier」型の値の対象。

  • 「when」制約のXPath式に現れるノード。

  • 「must」制約のXPath式に現れるノード。

  • 「mandatory true」制約を満たすために定義されたノード。

  • 「min-elements」制約を満たすために定義されたノード。

1.3. Updates to RFC 8342

1.3. RFC 8342の更新

This document updates [RFC8342] to define a configuration datastore called "system" that holds system configuration (Section 3). It also redefines the term "conventional configuration datastore" from [RFC8342] to include "system" in the list.

この文書は[RFC8342]を更新し、システム設定を保持する「system」と呼ばれる設定データストアを定義します（Section 3）。 また、[RFC8342]の用語「従来型設定データストア」を再定義し、そのリストに「system」を含めます。

To ensure the validity of <intended> when clients interact with system configuration (e.g., configuration provided by clients references system configuration) and allow the existence of system-defined templates and inactive system configuration, configuration in <running> is merged with <system> to create the contents of <intended> after the configuration transformations (e.g., template expansion or removal of inactive configuration defined in [RFC8342]) have been performed, as described in Section 4. Specifications in [RFC8342] related to the processing of system configuration are updated by the mechanism defined in this document.

クライアントがシステム設定とやり取りする場合（たとえば、クライアントが提供する設定がシステム設定を参照する場合）に<intended>の妥当性を確保し、システム定義のテンプレートや非アクティブなシステム設定の存在を許容するために、Section 4で説明するように、設定の変換（たとえば、[RFC8342]で定義されているテンプレートの展開や非アクティブな設定の削除）が実行された後に、<running>の設定が<system>とマージされて<intended>の内容が作成されます。 システム設定の処理に関連する[RFC8342]の規定は、この文書で定義するメカニズムによって更新されます。

Additionally, this document also updates the definition of the "intended" origin metadata annotation identity defined in Section 5.3.4 of [RFC8342]. The "intended" identity of the origin value defined in [RFC8342] represents the origin of configuration provided by <intended>. This document updates that definition as the origin source of configuration explicitly provided by clients and allows a subset of configuration in <intended> that flows from <system> yet is not configured or overridden explicitly in <running> to use "system" as its origin value. As per Section 5.3.4 of [RFC8342], all configuration with the origin value being reported as "intended" MUST originate from <running>, which includes any configuration in <system> that has been copied into <running>. Configuration that is in <system> and not also present in <running> MUST be reported as origin "system" in <operational>.

さらに、この文書は、[RFC8342]のSection 5.3.4で定義されている「intended」origin（オリジン）メタデータアノテーションのアイデンティティーの定義も更新します。 [RFC8342]で定義されているoriginの値の「intended」アイデンティティーは、<intended>によって提供される設定の出所を表します。 この文書はその定義を、クライアントによって明示的に提供される設定の出所の源として更新し、<system>から流れてきたものの<running>で明示的に設定または上書きされていない<intended>内の設定のサブセットについて、originの値として「system」を使用することを認めます。 [RFC8342]のSection 5.3.4のとおり、originの値が「intended」として報告されるすべての設定は、<running>に由来しなければなりません（MUST）。これには、<running>にコピーされた<system>内の設定も含まれます。 <system>にあり、<running>には存在しない設定は、<operational>においてorigin「system」として報告されなければなりません（MUST）。

2. Kinds of System Configuration

2. システム設定の種類

This document defines two types of system configuration: configuration that is always present and configuration that is conditionally present. These types of system configuration are described in Sections 2.1 and 2.2, respectively.

この文書は、2種類のシステム設定を定義します：常に存在する設定と、条件付きで存在する設定です。 これらの種類のシステム設定については、それぞれセクション2.1と2.2で説明します。

2.1. Always Present

2.1. 常に存在するもの

The always-present system configuration is generated in <system> when the device is powered on, irrespective of whether physical resources are present or whether a special functionality is enabled. An example of an always-present system configuration is an always-existing loopback interface.

常に存在するシステム設定は、物理リソースが存在するかどうかや特別な機能が有効になっているかどうかにかかわらず、デバイスの電源が入ったときに<system>に生成されます。 常に存在するシステム設定の例は、常に存在するループバックインターフェースです。

2.2. Conditionally Present

2.2. 条件付きで存在するもの

The conditionally present system configuration is generated in <system> based on specific conditions being met in a system. For example, if a physical resource is present (e.g., an interface card is inserted), the system automatically detects it and loads the associated configuration; when the physical resource is not present (an interface card is removed), the system configuration will automatically be removed from <system>. Another example is when a special functionality (e.g., a license or feature) is enabled, specific configuration may be created by the system.

条件付きで存在するシステム設定は、システム内で特定の条件が満たされたことに基づいて<system>に生成されます。 たとえば、物理リソースが存在する場合（たとえば、インターフェースカードが挿入された場合）、システムは自動的にそれを検出し、関連する設定をロードします。物理リソースが存在しない場合（インターフェースカードが取り外された場合）、システム設定は自動的に<system>から削除されます。 別の例として、特別な機能（たとえば、ライセンスや機能）が有効になった場合に、システムによって特定の設定が作成されることがあります。

3. The System Configuration Datastore (<system>)

3. システム設定データストア（<system>）

Following guidelines for defining datastores in Appendix A of [RFC8342], this document introduces a new datastore resource named "system" that represents the system configuration. NMDA servers compliant with this document MUST implement a system configuration datastore, and they SHOULD also implement <intended>.

[RFC8342]のAppendix Aのデータストアを定義するためのガイドラインに従い、この文書は、システム設定を表す「system」という名前の新しいデータストアリソースを導入します。 この文書に準拠するNMDAサーバーは、システム設定データストアを実装しなければなりません（MUST）。また、<intended>も実装すべきです（SHOULD）。

4. Conceptual Model of Datastores

4. データストアの概念モデル

Clients may provide configuration nodes that reference nodes defined in <system>, override system-provided values, and configure descendant nodes of system-defined configuration in <running>, as detailed in Section 6.

Section 6で詳しく説明するように、クライアントは、<running>において、<system>で定義されたノードを参照したり、システムが提供する値を上書きしたり、システム定義の設定の子孫ノードを設定したりする設定ノードを提供することがあります。

To ensure the validity of <intended>, configuration in <running> is merged with <system> to become <intended>, in which process, configuration appearing in <running> takes precedence over the same node in <system>. Since it is unspecified how to merge configuration before transformations, if <system> or <running> includes configuration that requires further transformation (e.g., template expansion or removal of inactive configuration defined in [RFC8342]) before it can be applied, configuration transformations MUST be performed independently on each datastore before <running> is merged with <system>.

<intended>の妥当性を確保するために、<running>の設定は<system>とマージされて<intended>になります。このプロセスでは、<running>に現れる設定が、<system>内の同じノードよりも優先されます。 変換前の設定をどのようにマージするかは規定されていないため、<system>または<running>に、適用される前にさらなる変換（たとえば、[RFC8342]で定義されているテンプレートの展開や非アクティブな設定の削除）が必要な設定が含まれている場合、<running>を<system>とマージする前に、各データストアで独立して設定の変換を実行しなければなりません（MUST）。

Whenever configuration in <system> changes, the server MUST also immediately update and validate <intended>.

<system>の設定が変更されるたびに、サーバーは<intended>も直ちに更新して検証しなければなりません（MUST）。

As a result, Figure 2 in Section 5 of [RFC8342] is updated with the below conceptual model of datastores that incorporates the system configuration datastore. For completeness, this model also includes <factory-default> introduced in [RFC8808].

その結果、[RFC8342]のSection 5の図2は、システム設定データストアを組み込んだ以下のデータストアの概念モデルで更新されます。 完全を期すために、このモデルには[RFC8808]で導入された<factory-default>も含まれています。

Configuration in <system> cannot be deleted by clients (e.g., a list entry can never be removed from <system> through protocol operations), even though a node defined in <system> may be overridden in <running>. If the system initializes a value for a particular leaf that is overridden by the client with a different value in <running> (Section 6.3), and if the node in <running> is removed at a later time, the system-initialized value defined in <system> appears in <intended> and may come into use eventually if applied successfully.

<system>で定義されたノードが<running>で上書きされることはあっても、<system>の設定をクライアントが削除することはできません（たとえば、プロトコル操作によって<system>からリストのエントリーを削除することは決してできません）。 システムが特定のリーフの値を初期化し、それがクライアントによって<running>で異なる値で上書きされ（Section 6.3）、その後<running>のそのノードが削除された場合、<system>で定義されたシステムによって初期化された値が<intended>に現れ、正常に適用されれば最終的に使用されることがあります。

Configuration may disappear from <system> due to, e.g., resources no longer available. In such cases, configuration for missing resources can still remain in <running> and <intended>, but it will not be applied and appear in <operational>. This is further clarified in Section 5.3.2 of [RFC8342].

たとえばリソースが利用できなくなったなどの理由で、設定が<system>から消えることがあります。 そのような場合、存在しないリソースに対する設定は<running>と<intended>に残ることがありますが、適用されることはなく、<operational>にも現れません。 これについては[RFC8342]のSection 5.3.2でさらに明確にされています。

5. Static Characteristics

5. 静的な特性

5.1. Read-Only to Clients

5.1. クライアントにとって読み取り専用

The system datastore is read-only (i.e., edits towards <system> directly MUST be denied), though the client may be allowed to provide configuration that overrides the value of a system-initialized node (see Section 6.3).

システムデータストアは読み取り専用です（つまり、<system>に対する直接の編集は拒否されなければなりません（MUST））。ただし、クライアントは、システムによって初期化されたノードの値を上書きする設定を提供することが許可される場合があります（Section 6.3を参照）。

5.2. No Changes to <operational>

5.2. <operational>への変更なし

This work does not change the definition of <operational> nor does it impact the contents of <operational>, as specified in [RFC8342]. It clarifies origin reporting, i.e., the origin of nodes sourced from <system> is reported as "system" unless explicitly configured or overridden in <running>. <system> enables system-defined nodes to be defined like configuration, i.e., made visible to clients in order for being referenced or configurable prior to present in <operational>. "config false" nodes are out of scope; hence, existing "config false" nodes are not impacted by this work.

この作業は、<operational>の定義を変更せず、[RFC8342]で規定されている<operational>の内容にも影響を与えません。 これはoriginの報告を明確にするものです。つまり、<system>に由来するノードのoriginは、<running>で明示的に設定または上書きされていない限り、「system」として報告されます。 <system>により、システム定義のノードを設定のように定義できます。つまり、<operational>に存在する前に、参照されたり設定可能になったりするようにクライアントから見えるようにできます。 「config false」のノードは範囲外です。したがって、既存の「config false」のノードはこの作業の影響を受けません。

6. Dynamic Behaviors

6. 動的な振る舞い

6.1. May Change via Software Upgrades or Resource Changes

6.1. ソフトウェアのアップグレードやリソースの変更による変化の可能性

The contents of <system> MAY change dynamically under various conditions, such as license change, software upgrade, and system-controlled resources change (see Section 2.2). The updates of system configuration may be obtained through YANG notifications [RFC8639] [RFC8641] (e.g., on-change notification).

<system>の内容は、ライセンスの変更、ソフトウェアのアップグレード、システムが制御するリソースの変更など（Section 2.2を参照）、さまざまな条件の下で動的に変化してもよいです（MAY）。 システム設定の更新は、YANG通知[RFC8639] [RFC8641]（たとえば、変更時通知）を通じて取得できます。

If system configuration changes (e.g., during a software upgrade), <running> SHOULD remain a valid configuration data tree. Any mechanisms to achieve this are outside the scope of this document.

システム設定が変化した場合（たとえば、ソフトウェアのアップグレード中）、<running>は有効な設定データツリーのままであるべきです（SHOULD）。 これを実現するためのメカニズムはこの文書の範囲外です。

6.2. システム設定の参照

Clients may create configuration data in <running> that references nodes in <system>. Some implementations may define system nodes solely as a convenience for clients to reference. It is also possible for the clients to define their customized nodes for reference.

クライアントは、<system>内のノードを参照する設定データを<running>に作成することがあります。 一部の実装では、クライアントが参照するための便宜としてのみシステムノードを定義する場合があります。 クライアントが参照のために独自にカスタマイズしたノードを定義することも可能です。

Appendix A.1では、クライアントがシステム定義のノードを参照する例を示します。

6.3. Overriding System Configuration

6.3. システム設定の上書き

Although <system> is read-only, in some cases, a server may allow some parts of system configuration (e.g., a leaf's value) to be overridden (note the distinction between <system> and system configuration). Overriding of system configuration is achieved by the client writing configuration data in <running>, which overrides the values of matched configuration nodes at the corresponding level in <system>. Configurations defined in <running> take precedence over system configuration nodes in <system> if the server allows the nodes to be overridden (some implementations may have immutable system configuration that is identified by the server using an immutable metadata annotation; see [YANG-FLAG] for details), regardless of whether a system-instantiated value changes subsequently.

<system>は読み取り専用ですが、場合によっては、サーバーがシステム設定の一部（たとえば、リーフの値）の上書きを許可することがあります（<system>とシステム設定の区別に注意してください）。 システム設定の上書きは、クライアントが<running>に設定データを書き込むことで実現され、これにより<system>内の対応するレベルにある一致する設定ノードの値が上書きされます。 サーバーがノードの上書きを許可している場合（一部の実装には、サーバーが不変メタデータアノテーションを使用して識別する不変のシステム設定がある場合があります。詳細は[YANG-FLAG]を参照してください）、システムによってインスタンス化された値がその後変更されるかどうかにかかわらず、<running>で定義された設定が<system>内のシステム設定ノードよりも優先されます。

Appendix A.2 provides an example of a client overriding a system-instantiated leaf's value.

Appendix A.2では、クライアントがシステムによってインスタンス化されたリーフの値を上書きする例を示します。

6.4. システム設定の子孫ノードの設定

A server may also allow a client to add nodes to a list entry in <system> by writing those additional nodes in <running>. Those additional data nodes may not exist in <system> (i.e., an addition rather than an override).

サーバーは、クライアントが<running>に追加のノードを書き込むことで、<system>内のリストのエントリーにノードを追加することを許可する場合もあります。 これらの追加のデータノードは、<system>には存在しない場合があります（つまり、上書きではなく追加です）。

9. Operational Considerations

9. 運用上の考慮事項

System configuration exists regardless of whether the server implements <system> or not. The introduction of <system> provides a standardized way to expose system configuration within NMDA.

システム設定は、サーバーが<system>を実装しているかどうかにかかわらず存在します。 <system>の導入により、NMDA内でシステム設定を公開する標準化された方法が提供されます。

NMDA clients that are not aware of <system> will continue to operate correctly. They will interact only with datastores such as <running>, <candidate>, <intended>, and <operational> as before. The presence of <system> does not change the fundamental behavior for such legacy clients. Operators should be aware that to fully leverage the capabilities defined in this document, client applications need to be updated to recognize and interact with <system>.

<system>を認識しないNMDAクライアントは、引き続き正しく動作します。 それらのクライアントは、これまでどおり<running>、<candidate>、<intended>、<operational>などのデータストアとのみやり取りします。 <system>の存在は、そのような従来のクライアントの基本的な動作を変更しません。 運用者は、この文書で定義されている機能を十分に活用するには、クライアントアプリケーションを更新して<system>を認識し、<system>とやり取りできるようにする必要があることを認識しておくべきです。

10. Security Considerations

10. セキュリティーに関する考慮事項

10.1. Considerations for the "ietf-system-datastore" YANG Module

10.1. 「ietf-system-datastore」YANGモジュールに関する考慮事項

This section is modeled after the template described in Section 3.7.1 of [RFC9907].

このセクションは、[RFC9907]のSection 3.7.1で説明されているテンプレートに倣っています。

The "ietf-system-datastore" YANG module defines a data model that is designed to be accessed via YANG-based management protocols, such as the Network Configuration Protocol (NETCONF) [RFC6241] and RESTCONF [RFC8040]. These YANG-based management protocols (1) have to use a secure transport layer and (2) have to use mutual authentication (e.g., Secure Shell (SSH) [RFC4252], TLS [TLS1.3], and QUIC [RFC9000]).

「ietf-system-datastore」YANGモジュールは、ネットワーク設定プロトコル（NETCONF）[RFC6241]やRESTCONF[RFC8040]などのYANGベースの管理プロトコルを介してアクセスされるように設計されたデータモデルを定義します。これらのYANGベースの管理プロトコルは、(1) 安全なトランスポート層を使用する必要があり、(2) 相互認証（たとえば、Secure Shell（SSH）[RFC4252]、TLS[TLS1.3]、QUIC[RFC9000]）を使用する必要があります。

The Network Configuration Access Control Model (NACM) [RFC8341] provides the means to restrict access for particular NETCONF or RESTCONF users to a preconfigured subset of all available NETCONF or RESTCONF protocol operations and content.

ネットワーク設定アクセス制御モデル（Network Configuration Access Control Model: NACM）[RFC8341]は、特定のNETCONFユーザーやRESTCONFユーザーのアクセスを、利用可能なすべてのNETCONFプロトコルやRESTCONFプロトコルの操作とコンテンツのうち、事前に設定されたサブセットに制限する手段を提供します。

The YANG module only defines an identity that uses the "ds:conventional" identity as its base. The module by itself does not expose any sensitive data nodes that are writable or that contain read-only state, and there are no particularly sensitive RPC or action operations. As such, there are no additional security issues related to the YANG module that need to be considered.

このYANGモジュールは、「ds:conventional」アイデンティティーをベースとして使用するアイデンティティーを定義するだけです。 このモジュール自体は、書き込み可能な、または読み取り専用の状態を含む機密性の高いデータノードを公開せず、特に機密性の高いRPCやアクションの操作もありません。 そのため、このYANGモジュールに関連して考慮する必要がある追加のセキュリティー上の問題はありません。

10.2. Considerations for System Configuration

10.2. システム設定に関する考慮事項

The system datastore, while read-only to clients, may contain sensitive information such as hardware identifiers, security policies, and critical system resources. Read access to sensitive system nodes and subtrees within the datastore MUST be controlled to prevent unauthorized disclosure. Implementations are strongly advised to log all access attempts to sensitive system configuration for audit purposes.

システムデータストアは、クライアントにとっては読み取り専用ですが、ハードウェア識別子、セキュリティーポリシー、重要なシステムリソースなどの機密情報を含む場合があります。 認可されていない開示を防ぐために、データストア内の機密性の高いシステムノードやサブツリーへの読み取りアクセスを制御しなければなりません（MUST）。 実装は、監査の目的で、機密性の高いシステム設定へのすべてのアクセスの試みをログに記録することが強く推奨されます。

Furthermore, while <system> cannot be modified directly, system configuration may be overridden as a merging result (Section 6.3). An attacker may configure a leaf that shadows a sensitive node in <system>. Misconfiguration in <running> could lead to unintended system behavior, including security policy bypass and availability risks. Unauthorized modification to sensitive contents MUST be prevented to avoid those negative effects on the network.

さらに、<system>は直接変更できませんが、システム設定はマージの結果として上書きされる場合があります（Section 6.3）。攻撃者は、<system>内の機密性の高いノードを覆い隠すリーフを設定する可能性があります。 <running>の設定ミスは、セキュリティーポリシーの回避や可用性のリスクを含む、意図しないシステムの動作につながる可能性があります。 ネットワークへのそのような悪影響を避けるために、機密性の高い内容への認可されていない変更を防がなければなりません（MUST）。
