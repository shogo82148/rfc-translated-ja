RFC 606

Host Names On-line

RFC 606

オンラインのホスト名

Abstract

概要

Now that we finally have an official list of host names, it seems about time to put an end to the absurd situation where each site on the network must maintain a different, generally out-of-date, host list for the use of its own operating system or user programs.

ようやくホスト名の公式な一覧ができたので、ネットワーク上の各サイトが、自分のオペレーティングシステムやユーザープログラムで使うために、それぞれ異なる、たいていは古くなったホスト一覧を管理しなければならないというばかげた状況に、そろそろ終止符を打つべきときだと思います。

For example, each of the TENEX sites to which I have access ( SRI-ARC, BBN-TENEX, USC-ISI, and PARC-MAXC) has a slightly different mapping between host names and host addresses: none is complete, and I believe each one differs in some way from the official List.

たとえば、私がアクセスできるTENEXサイト（SRI-ARC、BBN-TENEX、USC-ISI、PARC-MAXC）は、それぞれホスト名とホストアドレスとの対応づけが少しずつ異なっています。完全なものは1つもなく、どれも何らかの点で公式の一覧と違っていると思います。

Since the NIC has responsibility for maintaining the official list, lt seems appropriate for them to maintain an on-line file, accessible to anyone, which Lists names and host addresses ( and certain other information which I will suggest in a moment) in an easily machine-readable form.

公式の一覧を管理する責任はNICにあるので、名前とホストアドレス（および、このあとすぐ提案するその他のいくつかの情報）を機械で読みやすい形式で列挙した、誰でもアクセスできるオンラインのファイルをNICが管理するのが適切だと思われます。

This rules out, in my opinion, providing this information only in the form of an NLS structured file, since there are no facilities for accessing such files from the network and since many sites would not want to accommodate themselves to this structure even if there were.

私の考えでは、これによって、この情報をNLSの構造化ファイルの形式でしか提供しないという選択肢は除外されます。ネットワークからそのようなファイルにアクセスする手段がないうえ、たとえあったとしても、多くのサイトはこの構造に合わせたいとは思わないでしょう。

The file I have in mind would be devoted principally to that information needed by programs, as opposed to people, since the ; former want their information in compact, easily parsed form, whereas the latter appreciate more verbose expression and more sophisticated facilities for browsing or querying. Therefore, I propose that the following information be included in such a file:

私が考えているファイルは、人ではなくプログラムが必要とする情報を主に扱うものです。プログラムはコンパクトで解析しやすい形式の情報を求めるのに対し、人はより冗長な表現や、閲覧や問い合わせのためのより高度な機能を好むからです。そこで、このようなファイルに次の情報を含めることを提案します。

Of course, the official name and host address for each host. This would be the primary content of each entry.

もちろん、各ホストの公式名とホストアドレス。これは各エントリーの主要な内容になります。

Some information about the options of the various protocols supported by the host, including ( for FTP ) the preferred byte size and ( for TELNET) the preferred duplex mode. The former can have an enormous effect on the efficiency of file transfers. Since the new TELNET allows negotiation of options, the list need not be complete or accurate.

ホストがサポートしているさまざまなプロトコルのオプションに関する情報。たとえば、（FTPについては）望ましいバイトサイズ、（TELNETについては）望ましい二重モード（duplex mode）などです。前者はファイル転送の効率に非常に大きな影響を与えることがあります。新しいTELNETではオプションのネゴシエーションができるので、この一覧は完全でも正確でもなくてかまいません。

The function o f the host vis-a-vis the network ( user, server, TIP, etc.). This may aid NCPs in deciding whether to poll the host or give useful information for statistical purposes ( e.g. I would like to make my NCP collect statistics on traffic with TIPs vs. other hosts).

ネットワークに対するホストの機能（ユーザー、サーバー、TIPなど）。これは、NCPがそのホストをポーリングするかどうかを判断する助けになったり、統計のための有用な情報になったりするかもしれません（たとえば、私は自分のNCPに、TIPとそれ以外のホストとのトラフィックの統計を集めさせたいと思っています）。

Since the file will be generated centrally by a single program, but used widely by a variety of programs, it follows that its format should be organized for ease of interrogation at the expense of ease of construction. I feel a reasonable way to achieve this is to store it as an ASCII text file with the logical structure of a "property list".

このファイルは1つのプログラムによって集中的に生成されますが、さまざまなプログラムによって広く使われるので、その形式は作りやすさを犠牲にしてでも問い合わせやすさを優先して構成すべきです。そのための妥当な方法は、「属性リスト（property list）」の論理構造を持つASCIIテキストファイルとして格納することだと思います。

In other words, aside from the two basic facts in each entry ( name and address), the information will be expressed in the form of <attribute, value> pairs rather than having the attribute be recognized by format, position, etc.

つまり、各エントリーの2つの基本的な事項（名前とアドレス）を除き、情報は、属性を書式や位置などで識別するのではなく、<attribute, value>（属性と値）の組の形で表します。

l don't believe it matters a great deal exactly how this file is formatted, so I will make a suggestion in the hope that no one cares enough to protest it. ( This has never worked before in the history of the network, but it' s still worth a try ) The following is the proposed syntax of the file.

このファイルの正確な書式はさほど重要ではないと思うので、誰もわざわざ異議を唱えないことを願いつつ1つ提案します（これまでネットワークの歴史でこれがうまくいったことはありませんが、それでも試す価値はあります）。以下が、提案するファイルの構文です。

<host-name-file> ::= <entry> | <host-name-file> <entry>

<entry> ::= <data-part> <end-of-line>

<host-name-file> ::= <entry> | <host-name-file> <entry>

<entry> ::= <data-part> <end-of-line>

Note that this produces a blank line after the <data-part>.

これにより、<data-part>のあとに空行ができることに注意してください。

<data-part> ::= <basic-part> | <data-part> <attribute-item>
<basic-part> ::= <host-name> , <host-address> <end-of-line>
<attribute-item> ::= <attribute-name> = <attribute-value>
<end-of-line>

<data-part> ::= <basic-part> | <data-part> <attribute-item>
<basic-part> ::= <host-name> , <host-address> <end-of-line>
<attribute-item> ::= <attribute-name> = <attribute-value>
<end-of-line>

This leaves the following terms undefined:

これで、次の項が未定義のまま残ります。

<end-of-line>: I don't know what end-of-line indication is in favor in the network community these days. I personally favor carriage-return followed by line-feed. TENEX tends to use the single character octal 37, which is totally non-standard and inappropriate for this application.

<end-of-line>：最近のネットワークコミュニティーで、どの行末の表し方が好まれているのかはわかりません。私個人としては、復帰（carriage-return）のあとに改行（line-feed）が続くものを好みます。TENEXは8進数の37という1文字を使う傾向がありますが、これはまったく標準的でなく、この用途には不適切です。

<host-name>: an official host name as specified in the recent RFC 597 (NIC 20826) by NJN and JAKE. It is my understanding that these names are restricted to letters, digits, hyphens, and parentheses ( including the network name).

<host-name>：NJNとJAKEによる最近のRFC 597（NIC 20826）で規定された公式のホスト名。私の理解では、これらの名前は英字、数字、ハイフン、かっこ（ネットワーク名を含む）に限られます。

<host-address>: a decimal host address, relative to its own network ( I would assume). There has been no general discussion of multi-network addressing -- although there is apparently an unpublicized Internetworking Protocol experiment in progress -- and some other convention may be more desirable.

<host-address>：（おそらく）そのホスト自身のネットワークにおける10進数のホストアドレス。複数ネットワークにまたがるアドレス指定については、一般的な議論はまだ行われていません。公表されていないインターネットワーキングプロトコルの実験が進行中のようではありますが、何か別の規則のほうが望ましいかもしれません。

<attribute-name>: an arbitrary name containing only letters, digits, and hyphens. We will have to agree on some names like BEST-FTP-BYTE-SIZE (?), but I am willing to let the NIC pick them.

<attribute-name>：英字、数字、ハイフンだけを含む任意の名前。BEST-FTP-BYTE-SIZE（?）のような名前をいくつか合意する必要があるでしょうが、それはNICに選んでもらってかまいません。

<attribute-value>: an arbitrary string not containing <end--of-line>, whose interpretation depends in general on the attribute. For example, there might be an attribute SERVERS whose value was a list of the servers customarily run by the site.

<attribute-value>：<end--of-line>を含まない任意の文字列で、その解釈は一般に属性によって決まります。たとえば、そのサイトで通常動かしているサーバーの一覧を値とするSERVERSという属性があってもよいでしょう。

The following are some specific attributes that I think would be worthwhile:

以下は、あると役に立つと思われる具体的な属性です。

NICKNAMES -- value is a list of acceptable nicknames for the host. Any system that provides name-to-address translation is encouraged ( although of course not required) to accept these names as alternatives to the official host name.

NICKNAMES：値は、そのホストの受け入れ可能なニックネームの一覧です。名前からアドレスへの変換を提供するシステムは、公式のホスト名の代わりとしてこれらの名前を受け付けることが推奨されます（もちろん必須ではありません）。

FTP-BYTE-SIZES -- value is a list of the byte sizes supported by the FTP server. The first byte size is the one which leads to the least computational overhead ( e.g. 36 for PDP-1O's, 32 for 36O's).

FTP-BYTE-SIZES：値は、FTPサーバーがサポートしているバイトサイズの一覧です。最初のバイトサイズが、計算のオーバーヘッドが最も少なくなるものです（たとえば、PDP-10では36、360では32）。

ECHOING -- value is L or R depending on whether the host expects the terminal to echo ( Remote) or expects to do its own echoing (Local).

ECHOING：値はLかRです。ホストが端末にエコーさせることを期待している（Remote）か、ホスト自身でエコーすることを期待している（Local）かによって決まります。

Note that no attribute is actually required and that the values under a given attribute need not be complete. In other words, this list is meant not to replace option negotiation, word-of-mouth, or any other means bo which one host discovers the properties of another, but merely to provide an alternate source of information which can be accessed in a simple and uniform way.

実際に必須の属性は1つもなく、ある属性の値も完全である必要はないことに注意してください。つまり、この一覧は、オプションのネゴシエーションや口コミなど、あるホストが別のホストの特性を知るための手段を置き換えるものではなく、単純かつ一様な方法でアクセスできる別の情報源を提供することだけを目的としています。

I realize that there is a time-honored pitfall associated with suggestions such as the present one: it represents a specific solution to a specific problem, and as such may not be compatible with or form a reasonable basis for more general solutions to more general problems. However, ( 1) this particular problem has been irking me and others I have spoken to for well over a year, and it is really absurd that it should have gone unsolved this Long; (2) no one seems particularly interested in solving any more general problem.

今回のような提案には昔からの落とし穴があることは承知しています。つまり、特定の問題に対する特定の解決策であるため、より一般的な問題に対するより一般的な解決策とは両立しなかったり、その妥当な基礎にはならなかったりするかもしれません。しかし、（1）この問題は、私や私が話をした人たちを1年以上もいらだたせており、これほど長く解決されずにきたのは実にばかげています。（2）より一般的な問題を解決することに特に関心を持っている人はいないようです。

Except the Datacomputer: PLEASE, if there is an easy way to accomplish the same function through the Datacomputer, someone write un RFC specifying it.

ただしDatacomputerは別です。どうかお願いです。Datacomputerを使って同じ機能を簡単に実現する方法があるなら、誰かそれを規定するRFCを書いてください。
