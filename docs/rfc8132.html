RFC 8132

PATCH and FETCH Methods for the Constrained Application Protocol (CoAP)

RFC 8132

制約のあるアプリケーションプロトコル（CoAP）のためのPATCHメソッドとFETCHメソッド

Abstract

概要

The methods defined in RFC 7252 for the Constrained Application Protocol (CoAP) only allow access to a complete resource, not to parts of a resource. In case of resources with larger or complex data, or in situations where resource continuity is required, replacing or requesting the whole resource is undesirable. Several applications using CoAP need to access parts of the resources.

RFC 7252で制約のあるアプリケーションプロトコル（Constrained Application Protocol、CoAP）のために定義されたメソッドでは、リソース全体へのアクセスしかできず、リソースの一部にはアクセスできません。データが大きい、または複雑なリソースの場合や、リソースの連続性が求められる状況では、リソース全体を置き換えたり要求したりするのは望ましくありません。CoAPを使用するいくつかのアプリケーションは、リソースの一部にアクセスする必要があります。

This specification defines the new CoAP methods, FETCH, PATCH, and iPATCH, which are used to access and update parts of a resource.

この仕様は、リソースの一部へのアクセスと更新に使用する新しいCoAPメソッドであるFETCH、PATCH、iPATCHを定義します。

1. Introduction

1. はじめに

Similar to HTTP, the GET method defined in [RFC7252] for the Constrained Application Protocol (CoAP) only allows the specification of a URI and request parameters in CoAP options, not the transfer of a request payload detailing the request. This leads some applications to use POST where a cacheable, idempotent, safe request is actually desired.

HTTPと同様に、制約のあるアプリケーションプロトコル（CoAP）のために[RFC7252]で定義されたGETメソッドでは、URIとCoAPオプションのリクエストパラメーターを指定できるだけで、リクエストの詳細を記述したリクエストペイロードを転送することはできません。そのため、実際にはキャッシュ可能で冪等かつ安全なリクエストが望ましい場面で、POSTを使用するアプリケーションもあります。

Again, similar to the original specification of HTTP, the PUT method defined in [RFC7252] only allows a complete resource to be replaced. This also leads applications to use POST where a cacheable, possibly idempotent request is actually desired.

同じく、HTTPの当初の仕様と同様に、[RFC7252]で定義されたPUTメソッドでは、リソース全体を置き換えることしかできません。このことからも、実際にはキャッシュ可能で、場合によっては冪等なリクエストが望ましい場面で、アプリケーションがPOSTを使用することになります。

The present specification adds new CoAP methods: FETCH, to perform the equivalent of a GET with a request body; and the twin methods, PATCH and iPATCH, to modify parts of a CoAP resource.

この仕様は、新しいCoAPメソッドとして、リクエストボディー付きのGETに相当する処理を行うFETCHと、CoAPリソースの一部を変更するための対となるメソッドであるPATCHとiPATCHを追加します。

1.1. FETCH

1.1. FETCH

The CoAP GET method [RFC7252] is used to obtain the representation of a resource, where the resource is specified by a URI and additional request parameters can also shape the representation. This has been modeled after the HTTP GET operation and the REST model in general.

CoAPのGETメソッド[RFC7252]は、リソースの表現を取得するために使用します。このとき、リソースはURIで指定され、追加のリクエストパラメーターによって表現を形作ることもできます。これは、HTTPのGET操作と、より一般的にはRESTモデルをモデルとしています。

In HTTP, a resource is often used to search for information, and existing systems varyingly use the HTTP GET and POST methods to perform a search. Often, a POST method is used solely so that a larger set of parameters to the search can be supplied in the request body than can comfortably be transferred in the URI with a GET request. [HTTP-SEARCH] proposes a SEARCH method that is similar to GET in most properties but enables sending a request body, as is done with POST. The FETCH method defined in the present specification is inspired by [HTTP-SEARCH], which updates the definition and semantics of the HTTP SEARCH request method previously defined by [RFC5323]. However, there is no intention to limit FETCH to search-type operations, and the resulting properties may not be the same as those of HTTP SEARCH.

HTTPでは、情報を検索するためにリソースがよく使用され、既存のシステムは検索を行うためにHTTPのGETメソッドとPOSTメソッドをさまざまに使い分けています。多くの場合、POSTメソッドが使用されるのは、GETリクエストでURIに収めて無理なく転送できるよりも大きな検索パラメーターの集合を、リクエストボディーで渡せるようにするためだけです。[HTTP-SEARCH]は、ほとんどの性質がGETに似ていながら、POSTと同じようにリクエストボディーを送信できるSEARCHメソッドを提案しています。この仕様で定義するFETCHメソッドは、以前に[RFC5323]で定義されたHTTPのSEARCHリクエストメソッドの定義とセマンティクスを更新する[HTTP-SEARCH]から着想を得ています。ただし、FETCHを検索型の操作に限定する意図はなく、結果として得られる性質がHTTPのSEARCHと同じになるとは限りません。

A major problem with GET is that the information that controls the request needs to be bundled up in some unspecified way into the URI. Using the request body for this information has a number of advantages:

GETの大きな問題は、リクエストを制御する情報を、何らかの規定されていない方法でURIにまとめて詰め込む必要があることです。この情報にリクエストボディーを使用することには、多くの利点があります。

  • The client can specify a media type (and a content coding) that enables the server to unambiguously interpret the request parameters in the context of that media type. Also, the request body is not limited by the character set limitations of URIs, which enables a more natural (and more efficient) representation of certain domain-specific parameters.
  • The request parameters are not limited by the maximum size of the URI. In HTTP, that is a problem, as the practical limit for this size varies. In CoAP, another problem is that the block-wise transfer is not available for transferring large URI options in multiple rounds.
  • クライアントはメディアタイプ（とコンテンツコーディング）を指定でき、それによってサーバーは、そのメディアタイプのコンテキストでリクエストパラメーターを曖昧さなく解釈できます。また、リクエストボディーにはURIの文字集合の制約がかからないため、特定のドメイン固有のパラメーターをより自然な（そしてより効率的な）形で表現できます。
  • リクエストパラメーターが、URIの最大サイズによって制限されません。HTTPでは、このサイズの実際上の上限がまちまちであることが問題になります。CoAPでは、大きなURIオプションを複数回に分けて転送するためにブロック単位転送が使えないことも問題になります。

As an alternative to using GET, many implementations make use of the POST method to perform extended requests (even if they are semantically idempotent, safe, and even cacheable) to be able to pass along the input parameters within the request payload as opposed to using the request URI.

GETを使用する代わりに、多くの実装は、リクエストURIを使う代わりにリクエストペイロードの中で入力パラメーターを渡せるように、（セマンティクス上は冪等かつ安全で、キャッシュ可能でさえある場合でも）拡張されたリクエストを行うためにPOSTメソッドを利用しています。

The FETCH method provides a solution that spans the gap between the use of GET and POST. As with POST, the input to the FETCH operation is passed along within the payload of the request rather than as part of the request URI. Unlike POST, however, the semantics of the FETCH method are more specifically defined.

FETCHメソッドは、GETとPOSTの使い分けの隙間を埋める解決策を提供します。POSTと同様に、FETCH操作への入力は、リクエストURIの一部としてではなく、リクエストのペイロードの中で渡されます。しかし、POSTとは異なり、FETCHメソッドのセマンティクスはより具体的に定義されています。

1.2. PATCH and iPATCH

1.2. PATCHとiPATCH

PATCH is also specified for HTTP in [RFC5789]. Most of the motivation for PATCH described in [RFC5789] also applies here. iPATCH is the idempotent version of PATCH.

PATCHは、HTTP向けにも[RFC5789]で規定されています。[RFC5789]で説明されているPATCHの動機のほとんどは、ここでも当てはまります。iPATCHは、PATCHの冪等版です。

The PUT method exists to overwrite a resource with completely new contents and cannot be used to perform partial changes. When using PUT for partial changes, proxies and caches, and even clients and servers, may get confused as to the result of the operation. PATCH was not adopted in an early design stage of CoAP; however, it has become necessary with the arrival of applications that require partial updates to resources (e.g., [COAP-MGMNT]). Using PATCH avoids transferring all data associated with a resource in case of modifications, thereby not burdening the constrained communication medium.

PUTメソッドは、リソースをまったく新しい内容で上書きするために存在しており、部分的な変更を行うためには使用できません。部分的な変更にPUTを使用すると、プロキシーやキャッシュ、さらにはクライアントやサーバーまでもが、操作の結果について混乱する可能性があります。PATCHはCoAPの初期の設計段階では採用されませんでしたが、リソースの部分的な更新を必要とするアプリケーション（たとえば[COAP-MGMNT]）の登場によって必要になりました。PATCHを使用すると、変更時にリソースに関連するすべてのデータを転送せずに済むため、制約のある通信媒体に負担をかけません。

This document relies on knowledge of the PATCH specification for HTTP [RFC5789]. This document provides extracts from [RFC5789] to make independent reading possible.

この文書は、HTTPのPATCHの仕様[RFC5789]の知識を前提としています。この文書単独で読めるように、この文書には[RFC5789]からの抜粋を載せています。

この文書は、[RFC5789]と[RFC7252]で定義された用語を使用します。

2. FETCH Method

2. FETCHメソッド

The CoAP FETCH method is used to obtain a representation of a resource, specified by a number of request parameters. Unlike the CoAP GET method, which requests that a server return a representation of the resource identified by the effective request URI (as defined by [RFC7252]), the FETCH method is used by a client to ask the server to produce a representation as described by the request parameters (including the request options and the payload) based on the resource specified by the effective request URI. The payload returned in response to a FETCH cannot be assumed to be a complete representation of the resource identified by the effective request URI, i.e., it cannot be used by a cache as a payload to be returned by a GET request.

CoAPのFETCHメソッドは、いくつかのリクエストパラメーターによって指定されたリソースの表現を取得するために使用します。CoAPのGETメソッドは、（[RFC7252]で定義されている）実効リクエストURIによって識別されるリソースの表現を返すようサーバーに要求するものですが、それとは異なり、FETCHメソッドは、実効リクエストURIで指定されたリソースに基づいて、リクエストパラメーター（リクエストオプションとペイロードを含む）が記述するとおりの表現を生成するよう、クライアントがサーバーに依頼するために使用します。FETCHへのレスポンスとして返されるペイロードが、実効リクエストURIによって識別されるリソースの完全な表現であるとみなすことはできません。つまり、GETリクエストに対して返すペイロードとしてキャッシュがそれを使用することはできません。

Together with the request options, the body of the request (which may be constructed from multiple payloads using the block protocol [RFC7959]) defines the request parameters. With the FETCH method, implementations may submit a request body of any media type that is defined with the semantics of selecting information from a resource in such a FETCH request; it is outside the scope of this document how information about media types admissible for the specific resource is obtained by the client (although we can hint that form relations [CORE-APP] might be a preferred way). It is RECOMMENDED that any discovery method that allows a client to find out that the server supports FETCH also provides information regarding what FETCH payload media types are applicable.

リクエストオプションとともに、リクエストのボディー（ブロックプロトコル[RFC7959]を使用して複数のペイロードから構成されることもあります）がリクエストパラメーターを定義します。FETCHメソッドでは、実装は、そのようなFETCHリクエストにおいてリソースから情報を選択するセマンティクスが定義されている任意のメディアタイプのリクエストボディーを送信できます。特定のリソースで受け付けられるメディアタイプに関する情報をクライアントがどのように取得するかは、この文書の範囲外です（ただし、フォーム関係（form relation）[CORE-APP]が好ましい方法かもしれないことは示唆しておきます）。サーバーがFETCHをサポートしていることをクライアントが知ることができるディスカバリー方法はいずれも、どのFETCHペイロードのメディアタイプが適用可能かについての情報も提供することが推奨されます（RECOMMENDED）。

FETCH requests are both safe and idempotent with regards to the resource identified by the request URI. That is, the performance of a FETCH is not intended to alter the state of the targeted resource. (However, while processing a FETCH request, a server can be expected to allocate computing and memory resources or even create additional server resources through which the response to the search can be retrieved.)

FETCHリクエストは、リクエストURIによって識別されるリソースに関して、安全かつ冪等です。つまり、FETCHの実行は、ターゲットリソースの状態を変更することを意図していません。（ただし、FETCHリクエストの処理中に、サーバーが計算リソースやメモリーリソースを割り当てたり、さらには検索へのレスポンスを取得するための追加のサーバーリソースを作成したりすることは予想されます。）

A successful response to a FETCH request is expected to provide some indication as to the final disposition of the requested operation. If a successful response includes a body payload, the payload is expected to describe the results of the FETCH operation.

FETCHリクエストへの成功レスポンスは、要求された操作が最終的にどうなったかを何らかの形で示すことが期待されます。成功レスポンスにボディーペイロードが含まれる場合、そのペイロードはFETCH操作の結果を記述することが期待されます。

Depending on the response code as defined by [RFC7252], the response to a FETCH request is cacheable; the request body is part of the cache key. Specifically, 2.05 (Content) response codes (the responses for which are cacheable) are a typical way to respond to a FETCH request. (Note that this aspect differs markedly from [HTTP-SEARCH] and also that caches that cannot use the request payload as part of the cache key will not be able to cache responses to FETCH requests at all.) The Max-Age option in the response has equivalent semantics to its use in a GET.

[RFC7252]で定義されているレスポンスコードに応じて、FETCHリクエストへのレスポンスはキャッシュ可能です。リクエストボディーはキャッシュキーの一部です。具体的には、2.05（Content）レスポンスコード（そのレスポンスはキャッシュ可能です）は、FETCHリクエストに応答する典型的な方法です。（この点は[HTTP-SEARCH]とは著しく異なること、また、リクエストペイロードをキャッシュキーの一部として使用できないキャッシュは、FETCHリクエストへのレスポンスをまったくキャッシュできないことに注意してください。）レスポンス中のMax-Ageオプションは、GETで使用する場合と同等のセマンティクスを持ちます。

The semantics of the FETCH method change to a "conditional FETCH" if the request message includes an If-Match or If-None-Match option [RFC7252]. A conditional FETCH requests that the query be performed only under the circumstances described by the conditional option(s). It is important to note, however, that such conditions are evaluated against the state of the target resource itself as opposed to the results of the FETCH operation.

リクエストメッセージにIf-MatchオプションまたはIf-None-Matchオプション[RFC7252]が含まれる場合、FETCHメソッドのセマンティクスは「条件付きFETCH」に変わります。条件付きFETCHは、条件オプションが記述する状況の下でのみクエリーを実行するよう要求します。ただし、そのような条件は、FETCH操作の結果ではなく、ターゲットリソースそのものの状態に対して評価されることに注意することが重要です。

2.1. Response Codes

2.1. レスポンスコード

FETCH for CoAP adopts the response codes as specified in Sections 5.9 and 12.1.2 of [RFC7252] as well as the additional response codes mentioned in Section 2.2.

CoAPのFETCHは、[RFC7252]のセクション5.9と12.1.2で規定されているレスポンスコードに加えて、セクション2.2で述べる追加のレスポンスコードを採用します。

2.2. Error Handling

2.2. エラー処理

A FETCH request may fail under certain known conditions. Beyond the conditions already defined in [RFC7252] for GET, noteworthy ones are:

FETCHリクエストは、既知の特定の条件下で失敗することがあります。GETについて[RFC7252]ですでに定義されている条件のほかに、注目すべきものは次のとおりです。

Malformed FETCH payload:
If a server determines that the payload provided with a FETCH request is not properly formatted, it can return a 4.00 (Bad Request) CoAP error. The definition of a malformed payload depends upon the CoAP Content-Format specified with the request.
Unsupported FETCH payload:
In case a client sends a payload that is inappropriate for the resource identified by the Request-URI, the server can return a 4.15 (Unsupported Content-Format) CoAP error. The server can determine if the payload is supported by checking the CoAP Content-Format specified with the request.
Unprocessable request:
This situation occurs when the payload of a FETCH request is determined to be valid (i.e., well-formed and supported) but the server is unable to or is incapable of processing the request. The server can return a 4.22 (Unprocessable Entity) CoAP error. In situations when the server has insufficient computing resources to complete the request successfully, it can return a 4.13 (Request Entity Too Large) CoAP error (see also below). If there are more specific errors that provide additional insight into the problem, then those should be used.
Request too large:
If the payload of the FETCH request is larger than a CoAP server can process, then it can return the 4.13 (Request Entity Too Large) CoAP error.
不正な形式のFETCHペイロード（Malformed FETCH payload）:
FETCHリクエストとともに提供されたペイロードが適切な形式になっていないとサーバーが判断した場合、サーバーは4.00（Bad Request）CoAPエラーを返すことができます。不正な形式のペイロードの定義は、リクエストで指定されたCoAPのContent-Formatによって異なります。
サポートされていないFETCHペイロード（Unsupported FETCH payload）:
Request-URIによって識別されるリソースにふさわしくないペイロードをクライアントが送信した場合、サーバーは4.15（Unsupported Content-Format）CoAPエラーを返すことができます。サーバーは、リクエストで指定されたCoAPのContent-Formatを確認することによって、そのペイロードがサポートされているかどうかを判断できます。
処理できないリクエスト（Unprocessable request）:
この状況は、FETCHリクエストのペイロードが有効である（つまり、正しい形式でサポートされている）と判断されたものの、サーバーがそのリクエストを処理できない、または処理する能力がない場合に発生します。サーバーは4.22（Unprocessable Entity）CoAPエラーを返すことができます。リクエストを正常に完了するための計算リソースがサーバーに不足している状況では、サーバーは4.13（Request Entity Too Large）CoAPエラーを返すことができます（後述の項目も参照してください）。問題についてさらに詳しい情報を与える、より具体的なエラーがある場合は、そちらを使用すべきです。
大きすぎるリクエスト（Request too large）:
FETCHリクエストのペイロードが、CoAPサーバーが処理できるよりも大きい場合、サーバーは4.13（Request Entity Too Large）CoAPエラーを返すことができます。

It is possible that other error situations not mentioned here are encountered by a CoAP server while processing the FETCH request. In these situations, other appropriate CoAP response codes can also be returned.

ここで述べていないほかのエラー状況に、CoAPサーバーがFETCHリクエストの処理中に遭遇する可能性もあります。そのような状況では、ほかの適切なCoAPレスポンスコードを返すこともできます。

2.3. Option Numbers

2.3. オプション番号

FETCH for CoAP adopts the option numbers as specified in Sections 5.10 and 12.2 of [RFC7252].

CoAPのFETCHは、[RFC7252]のセクション5.10と12.2で規定されているオプション番号を採用します。

Generally, options defined for GET act in an analogous way for FETCH. Two specific cases are called out in the rest of this section.

一般に、GETについて定義されたオプションは、FETCHでも同様に作用します。このセクションの残りの部分では、2つの具体的なケースを取り上げます。

2.3.1. The Content-Format Option

2.3.1. Content-Formatオプション

A FETCH request MUST include a Content-Format option (see Section 5.10.3 of [RFC7252]) to specify the media type and content coding of the request body. (Typically, the media type will have been specifically designed to specify details for a selection or a search on a resource.)

FETCHリクエストは、リクエストボディーのメディアタイプとコンテンツコーディングを指定するために、Content-Formatオプション（[RFC7252]のセクション5.10.3を参照）を含めなければなりません（MUST）。（通常、そのメディアタイプは、リソースに対する選択や検索の詳細を指定するために特別に設計されたものになるでしょう。）

2.3.2. The ETag Option

2.3.2. ETagオプション

The ETag option on a FETCH result has the same semantics as defined in Section 5.10.6 of [RFC7252]. In particular, its use as a response option describes the "tagged representation", which for FETCH is the same as the "selected representation". The FETCH payload is input to that selection process and therefore needs to be part of the cache key. Similarly, the use of ETag as a request option can elicit a 2.03 (Valid) response if the representation associated with the ETag would still be selected by the FETCH request (including its payload).

FETCHの結果に付けられたETagオプションは、[RFC7252]のセクション5.10.6で定義されているのと同じセマンティクスを持ちます。特に、レスポンスオプションとして使用した場合は「タグ付けされた表現（tagged representation）」を記述し、これはFETCHの場合は「選択された表現（selected representation）」と同じです。FETCHのペイロードはその選択プロセスへの入力であるため、キャッシュキーの一部である必要があります。同様に、ETagをリクエストオプションとして使用すると、ETagに関連付けられた表現が（ペイロードを含む）FETCHリクエストによってなお選択されるのであれば、2.03（Valid）レスポンスを引き出すことができます。

2.4. Working with Observe

2.4. Observeとの併用

The Observe option [RFC7641] can be used with a FETCH request as it can be used with a GET request.

Observeオプション[RFC7641]は、GETリクエストで使用できるのと同じように、FETCHリクエストでも使用できます。

2.5. Working with Block

2.5. Blockとの併用

The Block1 option [RFC7959] can be used with a FETCH request as it would be used with a POST request; the Block2 option can then be used as it would with GET or POST.

Block1オプション[RFC7959]は、POSTリクエストで使用するのと同じように、FETCHリクエストでも使用できます。そして、Block2オプションは、GETやPOSTの場合と同じように使用できます。

2.6. Building FETCH Requests

2.6. FETCHリクエストの構築

One property of FETCH that may be non-obvious is that a FETCH request cannot be generated from a link alone; the client also needs a way to generate the request payload. Again, form relations [CORE-APP] may be able to fill parts of this gap.

FETCHの性質のうち、自明ではないかもしれないものの1つは、FETCHリクエストをリンクだけからは生成できないことです。クライアントには、リクエストペイロードを生成する手段も必要です。ここでも、フォーム関係[CORE-APP]がこのギャップの一部を埋められるかもしれません。

3. PATCH and iPATCH Methods

3. PATCHメソッドとiPATCHメソッド

The PATCH and iPATCH methods request that a set of changes described in the request payload be applied to the target resource of the request. The set of changes is represented in a format identified by a media type. If the Request-URI does not point to an existing resource, the server MAY create a new resource with that URI, depending on the PATCH document type (whether it can logically modify a null resource) and permissions, as well as other conditions such as the degree of control the server gives clients in creating new entries in its URI space (see also Section 3.4). Creation of a new resource would result in a 2.01 (Created) response code dependent on the PATCH document type.

PATCHメソッドとiPATCHメソッドは、リクエストペイロードに記述された変更の集合を、リクエストのターゲットリソースに適用するよう要求します。変更の集合は、メディアタイプによって識別される形式で表現されます。Request-URIが既存のリソースを指していない場合、サーバーは、PATCH文書の種類（論理的に空（null）のリソースを変更できるかどうか）や権限、そしてサーバーがURI空間に新しいエントリーを作成する際にクライアントにどの程度の制御を与えるかといったほかの条件（セクション3.4も参照）に応じて、そのURIで新しいリソースを作成してもよいです（MAY）。新しいリソースを作成すると、PATCH文書の種類に応じて2.01（Created）レスポンスコードを返すことになります。

Restrictions to a PATCH or iPATCH request can be made by including the If-Match or If-None-Match options in the request (see Sections 5.10.8.1 and 5.10.8.2 of [RFC7252]). If the resource could not be created or modified, then an appropriate error response code SHOULD be sent.

PATCHリクエストまたはiPATCHリクエストに制限を設けるには、リクエストにIf-MatchオプションまたはIf-None-Matchオプションを含めます（[RFC7252]のセクション5.10.8.1と5.10.8.2を参照）。リソースを作成または変更できなかった場合は、適切なエラーレスポンスコードを送信すべきです（SHOULD）。

The difference between the PUT and PATCH requests is documented in [RFC5789]. When a request is intended to effect a partial update of a given resource, clients cannot use PUT while supplying just the update, but they might be able to use PATCH or iPATCH.

PUTリクエストとPATCHリクエストの違いは[RFC5789]に記載されています。あるリソースの部分的な更新を行うことを意図したリクエストでは、クライアントは更新部分だけを渡してPUTを使用することはできませんが、PATCHやiPATCHを使用できる場合があります。

The PATCH method is "not safe" and "not idempotent", as is the HTTP PATCH method specified in [RFC5789].

PATCHメソッドは、[RFC5789]で規定されているHTTPのPATCHメソッドと同様に、「安全ではなく（not safe）」、「冪等ではありません（not idempotent）」。

The iPATCH method is not safe but idempotent, as with the CoAP PUT method specified in Section 5.8.3 of [RFC7252].

iPATCHメソッドは、[RFC7252]のセクション5.8.3で規定されているCoAPのPUTメソッドと同様に、安全ではありませんが冪等です。

A client can mark a request as idempotent by using the iPATCH method instead of the PATCH method. This is the only difference between the two. The indication of idempotence may enable the server to keep less state about the interaction; some constrained servers may only implement the iPATCH variant for this reason.

クライアントは、PATCHメソッドの代わりにiPATCHメソッドを使用することによって、リクエストが冪等であることを示せます。これが両者の唯一の違いです。冪等であることが示されることで、サーバーはやり取りについて保持する状態を減らせる場合があります。この理由から、制約のあるサーバーの中には、iPATCHの方だけを実装するものもあるでしょう。

PATCH and iPATCH are both atomic. The server MUST apply the entire set of changes atomically and never provide a partially modified representation to a concurrently executed GET request. Given the constrained nature of the servers, most servers will only execute CoAP requests consecutively, thus preventing a concurrent partial overlapping of request modifications. In other words, modifications MUST NOT be applied to the server state when an error occurs or when only a partial execution is possible on the resources present in the server.

PATCHとiPATCHはいずれもアトミックです。サーバーは、変更の集合全体をアトミックに適用し、同時に実行されるGETリクエストに対して部分的に変更された表現を決して提供しないようにしなければなりません（MUST）。サーバーには制約があるという性質上、ほとんどのサーバーはCoAPリクエストを1つずつ順番に実行するだけなので、リクエストによる変更が同時に部分的に重なることは防がれます。言い換えると、エラーが発生した場合や、サーバーに存在するリソースに対して部分的な実行しかできない場合には、変更をサーバーの状態に適用してはなりません（MUST NOT）。

The atomicity applies to a single server. When a PATCH or iPATCH request is multicast to a set of servers, each server can either execute all required modifications or not. It is not required that all servers execute all modifications or none. An Atomic Commit protocol that provides multiple server atomicity is out of scope.

アトミック性は単一のサーバーに適用されます。PATCHリクエストまたはiPATCHリクエストがサーバーの集合にマルチキャストされた場合、各サーバーは、要求されたすべての変更を実行するか、まったく実行しないかのどちらかにできます。すべてのサーバーが、すべての変更を実行するか、まったく実行しないかのどちらかになることは要求されていません。複数のサーバーにわたるアトミック性を提供するアトミックコミット（Atomic Commit）プロトコルは範囲外です。

A PATCH or iPATCH response can invalidate a cache in a similar manner to the PUT response. For the successful (2.xx) response codes, PATCH or iPATCH have the following caching behavior:

PATCHレスポンスまたはiPATCHレスポンスは、PUTレスポンスと同様の方法でキャッシュを無効化できます。成功（2.xx）レスポンスコードについて、PATCHまたはiPATCHのキャッシュの振る舞いは次のとおりです。

  • A 2.01 (Created) response invalidates any cache entry for the resource indicated by the Location-* options; the payload is a representation of the action result.
  • A 2.04 (Changed) response invalidates any cache entry for the target resource; the payload is a representation of the action result.
  • 2.01（Created）レスポンスは、Location-*オプションによって示されるリソースのキャッシュエントリーをすべて無効化します。ペイロードは、アクションの結果の表現です。
  • 2.04（Changed）レスポンスは、ターゲットリソースのキャッシュエントリーをすべて無効化します。ペイロードは、アクションの結果の表現です。

There is no guarantee that a resource can be modified with PATCH or iPATCH. Servers MUST ensure that a received PATCH body is appropriate for the type of resource identified by the target resource of the request.

リソースをPATCHやiPATCHで変更できるという保証はありません。サーバーは、受信したPATCHボディーが、リクエストのターゲットリソースによって識別されるリソースの種類に適したものであることを確認しなければなりません（MUST）。

It is RECOMMENDED that any discovery method that allows a client to find out that the server supports one of PATCH and iPATCH also provide information regarding what PATCH payload media types are applicable and which of the two methods are implemented by the server for each of these media types.

サーバーがPATCHとiPATCHのいずれかをサポートしていることをクライアントが知ることができるディスカバリー方法はいずれも、どのPATCHペイロードのメディアタイプが適用可能か、そしてそれらのメディアタイプのそれぞれについて2つのメソッドのどちらをサーバーが実装しているかについての情報も提供することが推奨されます（RECOMMENDED）。

Servers that do not rely on the idempotence of iPATCH can easily support both PATCH and iPATCH, and it is RECOMMENDED they do so. This is inexpensive to do, as, for iPATCH, there is no requirement on the server to check that the client's intention that the request be idempotent is fulfilled (although there is diagnostic value in that check, so a less-constrained implementation may want to perform it).

iPATCHの冪等性に依存しないサーバーは、PATCHとiPATCHの両方を容易にサポートでき、そうすることが推奨されます（RECOMMENDED）。iPATCHについては、リクエストが冪等であるというクライアントの意図が満たされているかをサーバーが確認する要件はないため、これは安価に実現できます（ただし、その確認には診断上の価値があるので、制約の少ない実装ではその確認を行いたい場合もあるでしょう）。

3.4. Error Handling

3.4. エラー処理

A PATCH or iPATCH request may fail under certain known conditions. These situations should be dealt with as expressed below.

PATCHリクエストまたはiPATCHリクエストは、既知の特定の条件下で失敗することがあります。そのような状況には、以下に述べるように対処すべきです。

Malformed PATCH or iPATCH payload:
If a server determines that the payload provided with a PATCH or iPATCH request is not properly formatted, it can return a 4.00 (Bad Request) CoAP error. The definition of a malformed payload depends upon the CoAP Content-Format specified with the request.
Unsupported PATCH or iPATCH payload:
In case a client sends a payload that is inappropriate for the resource identified by the Request-URI, the server can return a 4.15 (Unsupported Content-Format) CoAP error. The server can determine if the payload is supported by checking the CoAP Content-Format specified with the request.
Unprocessable request:

This situation occurs when the payload of a PATCH request is determined to be valid (i.e., well-formed and supported) but the server is unable to or is incapable of processing the request. The server can return a 4.22 (Unprocessable Entity) CoAP error. More specific scenarios might include situations such as:

  • the server has insufficient computing resources to complete the request successfully -- 4.13 (Request Entity Too Large) CoAP response code (see below); or
  • the resource specified in the request becomes invalid by applying the payload -- 4.09 (Conflict) CoAP response code (see "Conflicting state" below)).

In case there are more specific errors that provide additional insight into the problem, then those should be used.

Resource not found:
The 4.04 (Not Found) error should be returned if the payload of a PATCH request cannot be applied to a non-existent resource.
Failed precondition:
In case the client uses the conditional If-Match or If-None-Match option to define a precondition for the PATCH request, and that precondition fails, then the server can return the 4.12 (Precondition Failed) CoAP error.
Request too large:
If the payload of the PATCH request is larger than a CoAP server can process, then it can return the 4.13 (Request Entity Too Large) CoAP error.
Conflicting state:
If the modification specified by a PATCH or iPATCH request causes the resource to enter an inconsistent state that the server cannot resolve, the server can return the 4.09 (Conflict) CoAP response. The server SHOULD generate a payload that includes enough information for a user to recognize the source of the conflict. The server MAY return the actual resource state to provide the client with the means to create a new consistent resource state. Such a situation might be encountered when a structural modification is applied to a configuration data store but the structures being modified do not exist.
Concurrent modification:
Resource-constrained devices might need to process requests in the order they are received. In case requests are received concurrently to modify the same resource but they cannot be queued, the server can return a 5.03 (Service Unavailable) CoAP response code.
Conflict handling failure:
If the modification implies the reservation of resources or the wait time for conditions to become true leads to a too-long request execution time, the server can return a 5.03 (Service Unavailable) response code.
不正な形式のPATCHまたはiPATCHペイロード（Malformed PATCH or iPATCH payload）:
PATCHリクエストまたはiPATCHリクエストとともに提供されたペイロードが適切な形式になっていないとサーバーが判断した場合、サーバーは4.00（Bad Request）CoAPエラーを返すことができます。不正な形式のペイロードの定義は、リクエストで指定されたCoAPのContent-Formatによって異なります。
サポートされていないPATCHまたはiPATCHペイロード（Unsupported PATCH or iPATCH payload）:
Request-URIによって識別されるリソースにふさわしくないペイロードをクライアントが送信した場合、サーバーは4.15（Unsupported Content-Format）CoAPエラーを返すことができます。サーバーは、リクエストで指定されたCoAPのContent-Formatを確認することによって、そのペイロードがサポートされているかどうかを判断できます。
処理できないリクエスト（Unprocessable request）:

この状況は、PATCHリクエストのペイロードが有効である（つまり、正しい形式でサポートされている）と判断されたものの、サーバーがそのリクエストを処理できない、または処理する能力がない場合に発生します。サーバーは4.22（Unprocessable Entity）CoAPエラーを返すことができます。より具体的なシナリオとしては、次のような状況が考えられます。

  • リクエストを正常に完了するための計算リソースがサーバーに不足している -- 4.13（Request Entity Too Large）CoAPレスポンスコード（後述の項目を参照）。または、
  • ペイロードを適用することによって、リクエストで指定されたリソースが無効になる -- 4.09（Conflict）CoAPレスポンスコード（後述の「競合状態（Conflicting state）」を参照））。

問題についてさらに詳しい情報を与える、より具体的なエラーがある場合は、そちらを使用すべきです。

リソースが見つからない（Resource not found）:
PATCHリクエストのペイロードを存在しないリソースに適用できない場合は、4.04（Not Found）エラーを返すべきです。
事前条件の失敗（Failed precondition）:
クライアントが条件付きのIf-MatchオプションまたはIf-None-Matchオプションを使用してPATCHリクエストの事前条件を定義し、その事前条件が満たされなかった場合、サーバーは4.12（Precondition Failed）CoAPエラーを返すことができます。
大きすぎるリクエスト（Request too large）:
PATCHリクエストのペイロードが、CoAPサーバーが処理できるよりも大きい場合、サーバーは4.13（Request Entity Too Large）CoAPエラーを返すことができます。
競合状態（Conflicting state）:
PATCHリクエストまたはiPATCHリクエストで指定された変更によって、サーバーが解決できない不整合な状態にリソースが陥る場合、サーバーは4.09（Conflict）CoAPレスポンスを返すことができます。サーバーは、ユーザーが競合の原因を認識できるだけの十分な情報を含むペイロードを生成すべきです（SHOULD）。サーバーは、新しい整合性のあるリソース状態を作成する手段をクライアントに与えるために、実際のリソース状態を返してもよいです（MAY）。このような状況は、構成データストアに構造的な変更が適用されたものの、変更対象の構造が存在しない場合に起こる可能性があります。
同時の変更（Concurrent modification）:
リソースに制約のあるデバイスは、リクエストを受信した順に処理する必要があるかもしれません。同じリソースを変更するリクエストを同時に受信したものの、それらをキューに入れられない場合、サーバーは5.03（Service Unavailable）CoAPレスポンスコードを返すことができます。
競合処理の失敗（Conflict handling failure）:
変更がリソースの予約を伴う場合、または条件が真になるまでの待ち時間によってリクエストの実行時間が長くなりすぎる場合、サーバーは5.03（Service Unavailable）レスポンスコードを返すことができます。

It is possible that other error situations not mentioned here are encountered by a CoAP server while processing the PATCH request. In these situations, other appropriate CoAP status codes can also be returned.

ここで述べていないほかのエラー状況に、CoAPサーバーがPATCHリクエストの処理中に遭遇する可能性もあります。そのような状況では、ほかの適切なCoAPステータスコードを返すこともできます。

4. The New Set of CoAP Methods

4. CoAPメソッドの新しい集合

Adding three new methods to CoAP's existing four may seem like a major change. However, FETCH and the two PATCH variants fit well into the REST paradigm and have been anticipated on the HTTP side. Adding both a non-idempotent and an idempotent PATCH variant allows interoperability with HTTP's PATCH method to be kept and allows the use/indication of an idempotent PATCH when that is possible, which saves significant effort on the server side.

CoAPの既存の4つのメソッドに3つの新しいメソッドを追加することは、大きな変更に見えるかもしれません。しかし、FETCHと2つのPATCHの変種はRESTのパラダイムによく合致しており、HTTP側でも予期されていたものです。冪等ではないPATCHの変種と冪等なPATCHの変種の両方を追加することで、HTTPのPATCHメソッドとの相互運用性を保つことができ、かつ可能な場合には冪等なPATCHを使用する（冪等であることを示す）ことができるので、サーバー側の労力を大幅に削減できます。

5. Security Considerations

5. セキュリティーに関する考慮事項

This section analyzes the possible threats to the CoAP FETCH and PATCH or iPATCH methods. It is meant to inform protocol and application developers about the security limitations of CoAP FETCH and PATCH or iPATCH as described in this document.

このセクションでは、CoAPのFETCHメソッドと、PATCHメソッドまたはiPATCHメソッドに対して考えられる脅威を分析します。このセクションは、この文書で説明するCoAPのFETCHと、PATCHまたはiPATCHのセキュリティー上の限界を、プロトコルやアプリケーションの開発者に知らせることを目的としています。

The FETCH method is subject to the same general security considerations as all CoAP methods as described in Section 11 of [RFC7252]. Specifically, the security considerations for FETCH are closest to those of GET, except that the FETCH request carries a payload that may need additional protection. The payload of a FETCH request may reveal more detailed information about the specific portions of a resource of interest to the requester than a GET request for the entire resource would; this may mean that confidentiality protection of the request by Datagram Transport Layer Security (DTLS) or other means is needed for FETCH where it wouldn't be needed for GET.

FETCHメソッドには、[RFC7252]のセクション11で説明されている、すべてのCoAPメソッドに共通する一般的なセキュリティーに関する考慮事項が当てはまります。具体的には、FETCHのセキュリティーに関する考慮事項はGETのものに最も近いですが、FETCHリクエストは追加の保護が必要になる可能性のあるペイロードを運ぶ点が異なります。FETCHリクエストのペイロードは、リソース全体に対するGETリクエストよりも、要求者が関心を持っているリソースの特定の部分についての詳しい情報を明らかにする可能性があります。そのため、GETでは必要ない場合でも、FETCHではデータグラムトランスポート層セキュリティー（DTLS）などの手段によるリクエストの機密性保護が必要になる場合があります。

The PATCH and iPATCH methods are subject to the same general security considerations as all CoAP methods as described in Section 11 of [RFC7252]. The specific security considerations for PATCH or iPATCH are nearly identical to the security considerations for PUT [RFC7252]; the security considerations of Section 5 of [RFC5789] also apply to PATCH and iPATCH. Specifically, there is likely to be a need for authorizing requests (possibly through access control and/or authentication) and for ensuring that data is not corrupted through transport errors or through accidental overwrites. The mechanisms used for PUT can be used for PATCH or iPATCH as well.

PATCHメソッドとiPATCHメソッドには、[RFC7252]のセクション11で説明されている、すべてのCoAPメソッドに共通する一般的なセキュリティーに関する考慮事項が当てはまります。PATCHまたはiPATCHに固有のセキュリティーに関する考慮事項は、PUT[RFC7252]のセキュリティーに関する考慮事項とほぼ同じです。また、[RFC5789]のセクション5のセキュリティーに関する考慮事項も、PATCHとiPATCHに当てはまります。具体的には、（おそらくはアクセス制御や認証、またはその両方によって）リクエストを認可することと、トランスポートのエラーや誤った上書きによってデータが破損しないようにすることが必要になる可能性が高いでしょう。PUTに使用されるメカニズムは、PATCHやiPATCHにも同様に使用できます。

The new methods defined in the present specification are secured following the CoAP recommendations for the existing methods as specified in Section 9 of [RFC7252]. When additional security techniques are standardized for CoAP (e.g., Object Security), these techniques are then also available for securing the new methods.

この仕様で定義する新しいメソッドは、[RFC7252]のセクション9で規定されている既存のメソッドに対するCoAPの推奨事項に従って保護されます。CoAPのために追加のセキュリティー技術（たとえばオブジェクトセキュリティー（Object Security））が標準化されれば、それらの技術は新しいメソッドの保護にも使用できるようになります。
