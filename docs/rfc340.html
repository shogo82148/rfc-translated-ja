RFC 340

Proposed Telnet Changes

RFC 340

Telnetの変更案

Abstract

概要

The proposed change to the TELNET protocol calling for one standard protocol and dropping the idea of minimum implementation seems reasonable at this time.

1つの標準プロトコルを定め、最小限の実装という考え方をやめるというTELNETプロトコルへの変更案は、現時点では妥当だと思われます。

I suggest that both Data Types and Hide Your Input be kept for the following reasons:

私は、次の理由から、Data TypesとHide Your Inputの両方を残すことを提案します。

Data Types:

Data Types（データ型）：

The objection stating that switching out of ASCII results in an irreversible change and loss of control can be met by requiring other codes to provide to a return to ASCII. Each other code may have its own return code, however, it may not always be employed. Other codes are important for alphanumeric terminals that have special devices attached. Several potential cases can be cited:

ASCIIから切り替えると元に戻せない変更となり、制御を失うという反対意見には、他のコードにASCIIへ戻る手段を用意するよう求めることで対処できます。他のコードにはそれぞれ独自の復帰コードがあるかもしれませんが、それが常に使われるとは限りません。他のコードは、特殊な装置を接続した英数字端末にとって重要です。考えられる例をいくつか挙げます。

  1. Cal comp plotter attached to a teletype has logic permitting a program to turn the plotter on and off. When operating I believe it uses an 8 bit code which could conflict with Telnet signals.
  2. Numerically controlled machines, either controlled from a user terminal or code prepared by a HOST computer to be punched on the paper tape punch at a teletype way require the use of an arbitrary 8 bit code.
  3. Experiments controlled from alphanumeric terminal or sensor data collected through a cal-comp like connection may require the use of a full 8 bit code.
  1. テレタイプに接続したCal compプロッターには、プログラムからプロッターをオン・オフできるロジックがあります。私の考えでは、これは動作中に、Telnetの信号と衝突しうる8ビットのコードを使います。
  2. 数値制御の工作機械では、ユーザー端末から制御する場合も、ホストコンピューターで用意したコードをテレタイプの紙テープパンチで穿孔する場合も、任意の8ビットコードを使う必要があるかもしれません。
  3. 英数字端末から制御する実験や、cal-compのような接続を通じて収集するセンサーデータでは、完全な8ビットコードを使う必要があるかもしれません。

In these cases a transparent data type with a provision for a return to ASCII mode seems desirable.

これらの場合、ASCIIモードに戻る手段を備えた透過的なデータ型が望ましいと思われます。

Hide Your Input:

Hide Your Input（入力の非表示）：

As more and more use of data base systems in the network is considered, the need for and importance of using access keys, passwords, etc. grows. The fact that it is difficult to select the length of input to be hidden is not a persuasive argument. Potential solutions seem to exist, e.g. the protocol could provide for accepting length statements from the user program, data base system, operating system, etc. and in default of this, use a default length representing the server system expected optimum length.

ネットワーク内でデータベースシステムの利用がますます検討されるにつれて、アクセスキーやパスワードなどを使う必要性と重要性が高まっています。非表示にする入力の長さを選ぶのが難しいという事実は、説得力のある反論ではありません。解決策はあると思われます。たとえば、ユーザープログラム、データベースシステム、オペレーティングシステムなどから長さの指定を受け付けられるようにプロトコルで定め、それがない場合は、サーバーシステムが想定する最適な長さを表すデフォルトの長さを使うことができます。
