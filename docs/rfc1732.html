RFC 1732

IMAP4 Compatibility with IMAP2 and IMAP2bis

RFC 1732

IMAP4とIMAP2およびIMAP2bisとの互換性

Status of This Memo

このメモのステータス

This memo provides information for the Internet community. This memo does not specify an Internet standard of any kind. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーに情報を提供するものです。いかなる種類のインターネット標準も規定するものではありません。このメモの配布は無制限です。

Introduction

はじめに

This is a summary of hints and recommendations to enable an IMAP4 implementation to interoperate with implementations that conform to earlier specifications. None of these hints and recommendations are required by the IMAP4 specification; implementors must decide for themselves whether they want their implementation to fail if it encounters old software.

この文書は、IMAP4の実装が、以前の仕様に準拠した実装と相互運用できるようにするためのヒントと推奨事項をまとめたものです。これらのヒントや推奨事項は、いずれもIMAP4の仕様で要求されているものではありません。古いソフトウェアに遭遇したときに自分の実装を失敗させたいかどうかは、実装者自身が決めなければなりません。

IMAP4 has been designed to be upwards compatible with earlier specifications. For the most part, IMAP4 facilities that were not in earlier specifications should be invisible to clients unless the client asks for the facility.

IMAP4は、以前の仕様と上位互換性を持つように設計されています。ほとんどの場合、以前の仕様になかったIMAP4の機能は、クライアントがその機能を要求しない限り、クライアントからは見えないはずです。

In some cases, older servers may support some of the capabilities listed as being "new in IMAP4" as experimental extensions to the IMAP2 protocol described in RFC 1176.

場合によっては、古いサーバーが、「IMAP4で新しく導入された」とされている機能の一部を、RFC 1176で説明されているIMAP2プロトコルの実験的な拡張としてサポートしていることがあります。

This information may not be complete; it reflects current knowledge of server and client implementations as well as "folklore" acquired in the evolution of the protocol.

この情報は完全ではないかもしれません。この情報は、サーバーとクライアントの実装に関する現時点での知見と、プロトコルの発展の過程で得られた「言い伝え」を反映したものです。

IMAP4 client interoperability with old servers

IMAP4クライアントと古いサーバーとの相互運用性

In general, a client should be able to discover whether an IMAP2 server supports a facility by trial-and-error; if an attempt to use a facility generates a BAD response, the client can assume that the server does not support the facility.

一般に、クライアントは、IMAP2サーバーがある機能をサポートしているかどうかを試行錯誤によって発見できるはずです。ある機能を使おうとしてBADレスポンスが返された場合、クライアントは、サーバーがその機能をサポートしていないとみなすことができます。

A quick way to check whether a server implementation supports the IMAP4 specification is to try the CAPABILITY command. An OK response that includes the IMAP4 capability value indicates a server that supports IMAP4; a BAD response or one without the IMAP4 capability value indicates an older server.

サーバーの実装がIMAP4の仕様をサポートしているかどうかを手早く確認するには、CAPABILITYコマンドを試します。IMAP4というケイパビリティーを含むOKレスポンスは、そのサーバーがIMAP4をサポートしていることを示します。BADレスポンスや、IMAP4というケイパビリティーを含まないレスポンスは、古いサーバーであることを示します。

The following is a list of facilities that are only in IMAP4, and suggestions for how new clients might interoperate with old servers:

以下は、IMAP4にしかない機能と、新しいクライアントが古いサーバーと相互運用するための方法の提案の一覧です。

CAPABILITY command
A BAD response to this command indicates that the server implements IMAP2 (or IMAP2bis) and not IMAP4.
AUTHENTICATE command.
Use the LOGIN command.
LSUB and LIST commands
Try the RFC 1176 FIND command.
* in a sequence
Use the number of messages in the mailbox from the EXISTS unsolicited response.
SEARCH extensions (character set, additional criteria)
Reformulate the search request using only the searching options listed in search_old in the IMAP4 grammar. This may entail doing multiple searches to achieve the desired results.
BODYSTRUCTURE fetch data item
Try to fetch the non-extensible BODY data item.
body section number 0
Fetch the entire message and extract the header.
RFC822.HEADER.LINES and RFC822.HEADER.LINES.NOT fetch data items
Use RFC822.HEADER and remove the unwanted information.
BODY.PEEK[section], RFC822.PEEK, and RFC822.TEXT.PEEK fetch data items
Use the corresponding non-PEEK versions and manually clear the \Seen flag as necessary.
UID fetch data item and the UID commands
No equivalent capabilitity exists in older servers.
FLAGS.SILENT, +FLAGS.SILENT, and -FLAGS.SILENT store data items
Use the corresponding non-SILENT versions and ignore the untagged FETCH responses which com eback.
CAPABILITYコマンド
このコマンドに対するBADレスポンスは、そのサーバーがIMAP4ではなくIMAP2（またはIMAP2bis）を実装していることを示します。
AUTHENTICATEコマンド。
LOGINコマンドを使用します。
LSUBコマンドとLISTコマンド
RFC 1176のFINDコマンドを試します。
シーケンス中の*
非請求（unsolicited）のEXISTSレスポンスから得られる、メールボックス内のメッセージ数を使用します。
SEARCHの拡張（文字セット、追加の検索条件）
IMAP4の文法のsearch_oldに列挙されている検索オプションだけを使って、検索リクエストを組み立て直します。目的の結果を得るために、複数回の検索が必要になる場合があります。
BODYSTRUCTUREフェッチデータ項目
拡張可能でないBODYデータ項目のフェッチを試します。
ボディーのセクション番号0
メッセージ全体をフェッチして、ヘッダーを取り出します。
RFC822.HEADER.LINESとRFC822.HEADER.LINES.NOTフェッチデータ項目
RFC822.HEADERを使用し、不要な情報を取り除きます。
BODY.PEEK[section]、RFC822.PEEK、RFC822.TEXT.PEEKフェッチデータ項目
対応するPEEKなしの版を使用し、必要に応じて\Seenフラグを手動で解除します。
UIDフェッチデータ項目とUIDコマンド
古いサーバーには同等の機能はありません。
FLAGS.SILENT、+FLAGS.SILENT、-FLAGS.SILENTストアデータ項目
対応するSILENTなしの版を使用し、返ってくるタグなしのFETCHレスポンスを無視します。

The following IMAP4 facilities were introduced in the experimental IMAP2bis revisions to RFC-1176, and may be present in a server that does not support the CAPABILITY command:

以下のIMAP4の機能は、RFC-1176に対する実験的な改訂であるIMAP2bisで導入されたものであり、CAPABILITYコマンドをサポートしていないサーバーにも存在する場合があります。

CREATE, DELETE, and RENAME commands
To test whether these commands are present, try a CREATE INBOX command. If the response is NO, these commands are supported by the server. If the response is BAD, they are not. Older servers without the CREATE capability may support implicit creation of a mailbox by a COPY command with a non-existant name as the destination.
APPEND command
To test whether this command is present, try to append a zero-length stream to a mailbox name that is known not to exist (or at least, highly unlikely to exist) on the remote system.
SUBSCRIBE and UNSUBSCRIBE commands
Try the form of these commands with the optional MAILBOX keyword.
EXAMINE command
Use the SELECT command instead.
flags and internal date argument to APPEND command
Try the APPEND without any flag list and internal date arguments.
BODY, BODY[section], and FULL fetch data items
Use RFC822.TEXT and ALL instead. Server does not support MIME.
PARTIAL command
Use the appropriate FETCH command and ignore the unwanted data.
CREATE、DELETE、RENAMEコマンド
これらのコマンドが存在するかどうかを確かめるには、CREATE INBOXコマンドを試します。レスポンスがNOであれば、サーバーはこれらのコマンドをサポートしています。レスポンスがBADであれば、サポートしていません。CREATEの機能を持たない古いサーバーは、存在しない名前を宛先としたCOPYコマンドによるメールボックスの暗黙的な作成をサポートしている場合があります。
APPENDコマンド
このコマンドが存在するかどうかを確かめるには、リモートシステム上に存在しないことがわかっている（または、少なくとも存在する可能性が非常に低い）メールボックス名に、長さゼロのストリームを追加することを試します。
SUBSCRIBEコマンドとUNSUBSCRIBEコマンド
省略可能なMAILBOXキーワードを付けた形式のコマンドを試します。
EXAMINEコマンド
代わりにSELECTコマンドを使用します。
APPENDコマンドのフラグ引数と内部日付引数
フラグリストと内部日付の引数を付けずにAPPENDを試します。
BODY、BODY[section]、FULLフェッチデータ項目
代わりにRFC822.TEXTとALLを使用します。サーバーはMIMEをサポートしていません。
PARTIALコマンド
適切なFETCHコマンドを使用し、不要なデータを無視します。

IMAP4 client implementations must accept all responses and data formats documented in the IMAP4 specification, including those labeled as obsolete. This includes the COPY and STORE unsolicited responses and the old format of dates and times. In particular, client implementations must not treat a date/time as a fixed format string; nor may they assume that the time begins at a particular octet.

IMAP4クライアントの実装は、IMAP4の仕様に記載されているすべてのレスポンスとデータ形式を、廃止とされているものも含めて受け入れなければなりません。これには、非請求のCOPYレスポンスとSTOREレスポンスや、古い形式の日付と時刻が含まれます。特に、クライアントの実装は、日付／時刻を固定形式の文字列として扱ってはなりません。また、時刻が特定のオクテットから始まると想定してもなりません。

IMAP4 client implementations must not depend upon the presence of any server extensions that are not in the base IMAP4 specification.

IMAP4クライアントの実装は、IMAP4の基本仕様にないサーバー拡張の存在に依存してはなりません。

The experimental IMAP2bis version specified that the TRYCREATE special information token is sent as a separate unsolicited OK response instead of inside the NO response.

実験的なIMAP2bisの版では、TRYCREATEという特別な情報トークンは、NOレスポンスの中ではなく、別個の非請求のOKレスポンスとして送られると規定されていました。

The FIND BBOARDS, FIND ALL.BBOARDS, and BBOARD commands of RFC 1176 are removed from IMAP4. There is no equivalent to the bboard commands, which provided a separate namespace with implicit restrictions on what may be done in that namespace.

RFC 1176のFIND BBOARDS、FIND ALL.BBOARDS、BBOARDコマンドは、IMAP4から削除されています。bboardコマンドは、その名前空間で何ができるかについて暗黙的な制約がある別個の名前空間を提供していましたが、これに相当するものはありません。

Older server implementations may automatically create the destination mailbox on COPY if that mailbox does not already exist. This was how a new mailbox was created in older specifications. If the server does not support the CREATE command (see above for how to test for this), it will probably create a mailbox on COPY.

古いサーバーの実装は、COPYの際に宛先のメールボックスがまだ存在しなければ、そのメールボックスを自動的に作成する場合があります。以前の仕様では、これが新しいメールボックスを作成する方法でした。サーバーがCREATEコマンドをサポートしていない場合（これを確かめる方法は上記を参照）、おそらくCOPYの際にメールボックスを作成します。

Older server implementations may not preserve flags or internal dates on COPY. Some server implementations may not permit the preservation of certain flags on COPY or their setting with APPEND as site policy.

古いサーバーの実装は、COPYの際にフラグや内部日付を保持しない場合があります。サーバーの実装によっては、サイトのポリシーとして、COPYの際に特定のフラグを保持することや、APPENDで特定のフラグを設定することを許可しない場合があります。

IMAP4 server interoperability with old clients

IMAP4サーバーと古いクライアントとの相互運用性

In general, there should be no interoperation problem between a server conforming to the IMAP4 specification and a well-written client that conforms to an earlier specification. Known problems are noted below:

一般に、IMAP4の仕様に準拠したサーバーと、以前の仕様に準拠したよくできたクライアントとの間には、相互運用上の問題はないはずです。既知の問題を以下に記します。

  • Poor wording in the description of the CHECK command in earlier specifications implied that a CHECK command is the way to get the current number of messages in the mailbox. This is incorrect. A CHECK command does not necessarily result in an EXISTS response. Clients must remember the most recent EXISTS value sent from the server, and should not generate unnecessary CHECK commands.
  • An incompatibility exists with COPY in IMAP4. COPY in IMAP4 servers does not automatically create the destination mailbox if that mailbox does not already exist. This may cause problems with old clients that expect automatic mailbox creation in COPY.
  • The PREAUTH unsolicited response is new in IMAP4. It is highly unlikely that an old client would ever see this response.
  • The format of dates and times has changed due to the impending end of the century. Clients that fail to accept a four-digit year or a signed four-digit timezone value will not work properly with IMAP4.
  • An incompatibility exists with the use of "\" in quoted strings. This is best avoided by using literals instead of quoted strings if "\" or <"> is embedded in the string.
  • 以前の仕様のCHECKコマンドの説明は言葉足らずであり、CHECKコマンドがメールボックス内の現在のメッセージ数を取得する方法であるかのように読めました。これは誤りです。CHECKコマンドによって必ずしもEXISTSレスポンスが返されるとは限りません。クライアントは、サーバーから送られた最新のEXISTSの値を覚えておかなければならず、不要なCHECKコマンドを生成すべきではありません。
  • IMAP4のCOPYには非互換性があります。IMAP4サーバーのCOPYは、宛先のメールボックスがまだ存在しない場合でも、そのメールボックスを自動的に作成しません。このことは、COPYでメールボックスが自動的に作成されることを期待している古いクライアントで問題を引き起こす可能性があります。
  • 非請求のPREAUTHレスポンスは、IMAP4で新しく導入されたものです。古いクライアントがこのレスポンスを目にすることは、まずありません。
  • 世紀の終わりが近づいていることから、日付と時刻の形式が変更されました。4桁の年や、符号付きの4桁のタイムゾーン値を受け入れられないクライアントは、IMAP4では正しく動作しません。
  • 引用符付き文字列での「\」の使い方には非互換性があります。文字列に「\」や<">が埋め込まれている場合は、引用符付き文字列の代わりにリテラルを使うことで、この問題を避けるのが最善です。
