RFC 1426

SMTP Service Extension for 8bit-MIMEtransport

RFC 1426

8bit-MIMEtransportのためのSMTPサービス拡張

Status of This Memo

このメモのステータス

This RFC specifies an IAB standards track protocol for the Internet community, and requests discussion and suggestions for improvements. Please refer to the current edition of the "IAB Official Protocol Standards" for the standardization state and status of this protocol. Distribution of this memo is unlimited.

このRFCは、インターネットコミュニティーのためのIAB標準化過程のプロトコルを規定し、改善のための議論と提案を求めるものです。このプロトコルの標準化の状態とステータスについては、「IAB Official Protocol Standards」の最新版を参照してください。このメモの配布は無制限です。

1. Abstract

1. 概要

This memo defines an extension to the SMTP service whereby an SMTP content body containing octets outside of the US ASCII octet range (hex 00-7F) may be relayed using SMTP.

このメモは、US ASCIIのオクテット範囲（16進数で00～7F）外のオクテットを含むSMTPのコンテンツ本体をSMTPを使って中継できるようにする、SMTPサービスの拡張を定義します。

2. Introduction

2. はじめに

Although SMTP is widely and robustly deployed, various extensions have been requested by parts of the Internet community. In particular, a significant portion of the Internet community wishes to exchange messages in which the content body consists of a MIME message [3] containing arbitrary octet-aligned material. This memo uses the mechanism described in [5] to define an extension to the SMTP service whereby such contents may be exchanged. Note that this extension does NOT eliminate the possibility of an SMTP server limiting line length; servers are free to implement this extension but nevertheless set a line length limit no lower than 1000 octets.

SMTPは広く堅牢に展開されていますが、インターネットコミュニティーの一部からさまざまな拡張が要望されてきました。特に、インターネットコミュニティーのかなりの部分が、任意のオクテット単位のデータを含むMIMEメッセージ[3]からなるコンテンツ本体を持つメッセージを交換したいと望んでいます。このメモは、[5]で説明されている仕組みを使って、そのようなコンテンツを交換できるようにするSMTPサービスの拡張を定義します。この拡張は、SMTPサーバーが行の長さを制限する可能性を排除するものでは「ない」ことに注意してください。サーバーはこの拡張を実装しつつ、1000オクテットを下回らない範囲で行の長さの制限を設定してもかまいません。

3. Framework for the 8bit MIME Transport Extension

3. 8ビットMIMEトランスポート拡張の枠組み

The 8bit MIME transport extension is laid out as follows:

8ビットMIMEトランスポート拡張の概要は次のとおりです。

  1. the name of the SMTP service extension defined here is 8bit-MIMEtransport;
  2. the EHLO keyword value associated with the extension is 8BITMIME;
  3. no parameter is used with the 8BITMIME EHLO keyword;

  4. one optional parameter using the keyword BODY is added to the MAIL FROM command. The value associated with this parameter is a keyword indicating whether a 7bit message (in strict compliance with [1]) or a MIME message (in strict compliance with [3]) with arbitrary octet content is being sent. The syntax of the value is as follows, using the ABNF notation of [2]:

         body-value ::= "7BIT" / "8BITMIME"
  5. no additional SMTP verbs are defined by this extension; and,
  6. the next section specifies how support for the extension affects the behavior of a server and client SMTP.
  1. ここで定義するSMTPサービス拡張の名前は8bit-MIMEtransportです。
  2. この拡張に関連付けられたEHLOキーワードの値は8BITMIMEです。
  3. 8BITMIME EHLOキーワードにはパラメーターを使用しません。

  4. キーワードBODYを使う省略可能なパラメーターを1つ、MAIL FROMコマンドに追加します。このパラメーターに関連付けられた値は、（[1]に厳密に準拠した）7ビットのメッセージと、（[3]に厳密に準拠した）任意のオクテットの内容を持つMIMEメッセージのどちらを送信しているのかを示すキーワードです。この値の構文は、[2]のABNF記法を使って次のように表します。

         body-value ::= "7BIT" / "8BITMIME"
  5. この拡張では、SMTPの動詞（verb）を新たに定義しません。
  6. 次のセクションでは、この拡張のサポートがサーバーSMTPとクライアントSMTPの動作にどのように影響するかを規定します。

4. The 8bit-MIMEtransport service extension

4. 8bit-MIMEtransportサービス拡張

When a client SMTP wishes to submit (using the MAIL command) a content body consisting of a MIME message containing arbitrary octet-aligned material, it first issues the EHLO command to the server SMTP. If the server SMTP responds with code 250 to the EHLO command, and the response includes the EHLO keyword value 8BITMIME, then the server SMTP is indicating that it supports the extended MAIL command and will accept MIME messages containing arbitrary octet-aligned material.

クライアントSMTPが、任意のオクテット単位のデータを含むMIMEメッセージからなるコンテンツ本体を（MAILコマンドを使って）送信したい場合、まずサーバーSMTPにEHLOコマンドを発行します。サーバーSMTPがEHLOコマンドにコード250で応答し、その応答にEHLOキーワードの値8BITMIMEが含まれていれば、サーバーSMTPは拡張されたMAILコマンドをサポートし、任意のオクテット単位のデータを含むMIMEメッセージを受け付けることを示しています。

The extended MAIL command is issued by a client SMTP when it wishes to transmit a content body consisting of a MIME message containing arbitrary octet-aligned material. The syntax for this command is identical to the MAIL command in [1], except that a BODY parameter must appear after the address.

拡張されたMAILコマンドは、任意のオクテット単位のデータを含むMIMEメッセージからなるコンテンツ本体をクライアントSMTPが送信したいときに発行します。このコマンドの構文は、アドレスの後にBODYパラメーターが現れなければならないことを除いて、[1]のMAILコマンドと同じです。

The complete syntax of this extended command is defined in [5]. The esmtp-keyword is BODY and the syntax for esmtp-value is given by the syntax for body-value shown above.

この拡張されたコマンドの完全な構文は[5]で定義されています。esmtp-keywordはBODYであり、esmtp-valueの構文は上で示したbody-valueの構文で与えられます。

The value associated with the BODY parameter indicates whether the content body which will be passed using the DATA command consists of a MIME message containing some arbitrary octet-aligned material ("8BITMIME") or is encoded entirely in accordance with [1] ("7BIT").

BODYパラメーターに関連付けられた値は、DATAコマンドを使って渡されるコンテンツ本体が、任意のオクテット単位のデータを含むMIMEメッセージ（「8BITMIME」）からなるのか、それとも全体が[1]に従ってエンコードされている（「7BIT」）のかを示します。

A server which supports the 8-bit MIME transport service extension shall preserve all bits in each octet passed using the DATA command.

8ビットMIMEトランスポートサービス拡張をサポートするサーバーは、DATAコマンドを使って渡される各オクテットのすべてのビットを保持することになります。

Naturally, the usual SMTP data-stuffing algorithm applies so that a content which contains the five-character sequence of

当然ながら、通常のSMTPのデータスタッフィングのアルゴリズムが適用されるので、次の5文字の並びを含むコンテンツや、

            <CR> <LF> <DOT> <CR> <LF>

            <CR> <LF> <DOT> <CR> <LF>

or a content that begins with the three-character sequence of

次の3文字の並びで始まるコンテンツが、

            <DOT> <CR> <LF>

            <DOT> <CR> <LF>

does not prematurely terminate the transfer of the content. Further, it should be noted that the CR-LF pair immediately preceeding the final dot is considered part of the content. Finally, although the content body contains arbitrary octet-aligned material, the length of each line (number of octets between two CR-LF pairs), is still subject to SMTP server line length restrictions (which may allow as few as 1000 octets on a single line).

コンテンツの転送を途中で終了させることはありません。さらに、最後のドットの直前にあるCR-LFの組はコンテンツの一部とみなされることに注意してください。最後に、コンテンツ本体が任意のオクテット単位のデータを含んでいても、各行の長さ（2つのCR-LFの組の間のオクテット数）は、依然としてSMTPサーバーの行の長さの制限（1行あたり1000オクテットしか許さない場合もある）の対象となります。

Once a server SMTP supporting the 8bit-MIMEtransport service extension accepts a content body containing octets with the high-order (8th) bit set, the server SMTP must deliver or relay the content in such a way as to preserve all bits in each octet.

8bit-MIMEtransportサービス拡張をサポートするサーバーSMTPが、上位（8番目の）ビットがセットされたオクテットを含むコンテンツ本体をいったん受け付けたら、サーバーSMTPは各オクテットのすべてのビットを保持するようにコンテンツを配送または中継しなければなりません。

If a server SMTP does not support the 8-bit MIME transport extension (either by not responding with code 250 to the EHLO command, or by not including the EHLO keyword value 8BITMIME in its response), then the client SMTP must not, under any circumstances, attempt to transfer a content which contains characters outside the US ASCII octet range (hex 00-7F).

サーバーSMTPが（EHLOコマンドにコード250で応答しないか、応答にEHLOキーワードの値8BITMIMEを含めないことによって）8ビットMIMEトランスポート拡張をサポートしていない場合、クライアントSMTPは、いかなる状況でも、US ASCIIのオクテット範囲（16進数で00～7F）外の文字を含むコンテンツの転送を試みてはなりません。

A client SMTP has two options in this case: first, it may implement a gateway transformation to convert the message into valid 7bit MIME, or second, or may treat this as a permanent error and handle it in the usual manner for delivery failures. The specifics of the transformation from 8bit MIME to 7bit MIME are not described by this RFC; the conversion is nevertheless constrained in the following ways:

この場合、クライアントSMTPには2つの選択肢があります。1つ目は、メッセージを有効な7ビットMIMEに変換するゲートウェイ変換を実装することです。2つ目は、これを永続的なエラーとして扱い、配送失敗の通常の方法で処理することです。8ビットMIMEから7ビットMIMEへの変換の詳細はこのRFCでは説明しませんが、変換には次のような制約があります。

  1. it must cause no loss of information; MIME transport encodings must be employed as needed to insure this is the case, and
  2. the resulting message must be valid 7bit MIME.
  1. 情報を失ってはなりません。そのために、必要に応じてMIMEのトランスポートエンコーディングを使用しなければなりません。
  2. 変換結果のメッセージは有効な7ビットMIMEでなければなりません。

5. Usage Example

5. 使用例

The following dialogue illustrates the use of the 8bit-MIMEtransport service extension:

次の対話は、8bit-MIMEtransportサービス拡張の使用例を示しています。

       S: <wait for connection on TCP port 25>
       C: <open connection to server>
       S: 220 dbc.mtview.ca.us SMTP service ready
       C: EHLO ymir.claremont.edu
       S: 250-dbc.mtview.ca.us says hello
       S: 250 8BITMIME
       C: MAIL FROM:<ned@ymir.claremont.edu> BODY=8BITMIME
       S: 250 <ned@ymir.claremont.edu>... Sender and 8BITMIME ok
       C: RCPT TO:<mrose@dbc.mtview.ca.us>
       S: 250 <mrose@dbc.mtview.ca.us>... Recipient ok
       C: DATA
       S: 354 Send 8BITMIME message, ending in CRLF.CRLF.
        ...
       C: .
       S: 250 OK
       C: QUIT
       S: 250 Goodbye

       S: <wait for connection on TCP port 25>
       C: <open connection to server>
       S: 220 dbc.mtview.ca.us SMTP service ready
       C: EHLO ymir.claremont.edu
       S: 250-dbc.mtview.ca.us says hello
       S: 250 8BITMIME
       C: MAIL FROM:<ned@ymir.claremont.edu> BODY=8BITMIME
       S: 250 <ned@ymir.claremont.edu>... Sender and 8BITMIME ok
       C: RCPT TO:<mrose@dbc.mtview.ca.us>
       S: 250 <mrose@dbc.mtview.ca.us>... Recipient ok
       C: DATA
       S: 354 Send 8BITMIME message, ending in CRLF.CRLF.
        ...
       C: .
       S: 250 OK
       C: QUIT
       S: 250 Goodbye

6. Security Considerations

6. セキュリティーに関する考慮事項

This RFC does not discuss security issues and is not believed to raise any security issues not already endemic in electronic mail and present in fully conforming implementations of [1].

このRFCではセキュリティーの問題を議論しません。また、電子メールにもともと存在し、[1]に完全に準拠した実装にすでに存在するもの以外のセキュリティーの問題を引き起こすことはないと考えられます。
