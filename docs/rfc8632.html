RFC 8632

A YANG Data Model for Alarm Management

RFC 8632

アラーム管理のためのYANGデータモデル

Abstract

概要

This document defines a YANG module for alarm management. It includes functions for alarm-list management, alarm shelving, and notifications to inform management systems. There are also operations to manage the operator state of an alarm and administrative alarm procedures. The module carefully maps to relevant alarm standards.

この文書は、アラーム管理のためのYANGモジュールを定義します。 このモジュールには、アラームリストの管理、アラームの棚上げ、および管理システムに情報を伝えるための通知の機能が含まれています。 また、アラームの運用者状態を管理するための操作や、アラームの管理上の手続きのための操作もあります。 このモジュールは、関連するアラーム標準に注意深く対応付けられています。

1. Introduction

1. はじめに

This document defines a YANG module [RFC7950] for alarm management. The purpose is to define a standardized alarm interface for network devices that can be easily integrated into management applications. The model is also applicable as a northbound alarm interface in the management applications.

この文書は、アラーム管理のためのYANGモジュール[RFC7950]を定義します。 その目的は、管理アプリケーションに容易に統合できる、ネットワーク機器向けの標準化されたアラームインターフェイスを定義することです。 このモデルは、管理アプリケーションにおけるノースバウンドのアラームインターフェイスとしても適用できます。

Alarm monitoring is a fundamental part of monitoring the network. Raw alarms from devices do not always tell the status of the network services or necessarily point to the root cause. However, being able to feed alarms to the alarm-management application in a standardized format is a starting point for performing higher-level network assurance tasks.

アラームの監視は、ネットワーク監視の基本的な部分です。 機器から得られる生のアラームは、ネットワークサービスの状態を常に伝えるとは限らず、また必ずしも根本原因を指し示すわけでもありません。 しかし、標準化された形式でアラームをアラーム管理アプリケーションに渡せるようにすることは、より高いレベルのネットワーク保証タスクを実行するための出発点となります。

The design of the module is based on experience from using and implementing available alarm standards from ITU [X.733], 3GPP [ALARMIRP], and ANSI [ISA182].

このモジュールの設計は、ITU [X.733]、3GPP [ALARMIRP]、ANSI [ISA182]の既存のアラーム標準を使用および実装した経験に基づいています。

The following terms are used within this document:

この文書では次の用語を使用します。

Alarm (the general concept):
An alarm signifies an undesirable state in a resource that requires corrective action.
Fault:
A fault is the underlying cause of an undesired behavior. There is no trivial one-to-one mapping between faults and alarms. One fault may result in several alarms in case the system lacks root-cause and correlation capabilities. An alarm might not have an underlying fault as a cause. For example, imagine a bad Mean Opinion Score (MOS) alarm from a Voice over IP (VOIP) probe and the cause being non-optimal QoS configuration.
Alarm Type:
An alarm type identifies a possible unique alarm state for a resource. Alarm types are names to identify the state like "link-alarm", "jitter-violation", and "high-disk-utilization".
Resource:
A fine-grained identification of the alarming resource, for example, an interface and a process.
Alarm Instance:
The alarm state for a specific resource and alarm type, for example, ("GigabitEthernet0/15", "link-alarm"). An entry in the alarm list.
Cleared Alarm:
A cleared alarm is an alarm where the system considers the undesired state to be cleared. Operators cannot clear alarms; clearance is managed by the system. For example, a "linkUp" notification can be considered a clear condition for a "linkDown" state.
Closed Alarm:
Operators can close alarms irrespective of the alarm being cleared or not. A closed alarm indicates that the alarm does not need attention because either the corrective action has been taken or it can be ignored for other reasons.
Alarm Inventory:
A list of all possible alarm types on a system.
Alarm Shelving:
Blocking alarms according to specific criteria.
Corrective Action:
An action taken by an operator or automation routine in order to minimize the impact of the alarm or resolve the root cause.
Management System:
The alarm-management application that consumes the alarms, i.e., acts as a client.
System:
The system that implements this YANG module, i.e., acts as a server. This corresponds to a network device or a management application that provides a northbound alarm interface.
アラーム（Alarm、一般的な概念）：
アラームは、是正措置を必要とする、リソースの望ましくない状態を表します。
障害（Fault）：
障害とは、望ましくない振る舞いの根本的な原因です。 障害とアラームの間に自明な1対1の対応関係はありません。 システムに根本原因分析や相関分析の能力がない場合、1つの障害から複数のアラームが発生することがあります。 アラームが原因となる障害を持たない場合もあります。 たとえば、VoIP（Voice over IP）プローブから悪いMOS（Mean Opinion Score）のアラームが上がり、その原因が最適でないQoS設定である場合を考えてみてください。
アラームタイプ（Alarm Type）：
アラームタイプは、リソースの一意なアラーム状態になりうるものを識別します。 アラームタイプは、「link-alarm」、「jitter-violation」、「high-disk-utilization」のように状態を識別する名前です。
リソース（Resource）：
アラームを発しているリソースのきめ細かい識別です。たとえば、インターフェイスやプロセスです。
アラームインスタンス（Alarm Instance）：
特定のリソースとアラームタイプについてのアラーム状態です。たとえば、（"GigabitEthernet0/15"、"link-alarm"）です。 アラームリストの1エントリーです。
クリアされたアラーム（Cleared Alarm）：
クリアされたアラームとは、望ましくない状態が解消されたとシステムがみなしたアラームです。 運用者はアラームをクリアできません。クリアはシステムによって管理されます。 たとえば、「linkUp」通知は「linkDown」状態のクリア条件とみなすことができます。
クローズされたアラーム（Closed Alarm）：
運用者は、アラームがクリアされたかどうかにかかわらず、アラームをクローズできます。 クローズされたアラームは、是正措置がすでに講じられたか、その他の理由で無視できるために、そのアラームに注意を払う必要がないことを示します。
アラームインベントリー（Alarm Inventory）：
システム上で発生しうるすべてのアラームタイプのリストです。
アラームの棚上げ（Alarm Shelving）：
特定の基準に従ってアラームをブロックすることです。
是正措置（Corrective Action）：
アラームの影響を最小限に抑えたり、根本原因を解決したりするために、運用者または自動化ルーチンが行うアクションです。
管理システム（Management System）：
アラームを消費するアラーム管理アプリケーションです。つまり、クライアントとして動作します。
システム（System）：
このYANGモジュールを実装するシステムです。つまり、サーバーとして動作します。 これは、ネットワーク機器、またはノースバウンドのアラームインターフェイスを提供する管理アプリケーションに相当します。

この文書で使用するツリー図は、[RFC8340]で定義されている表記法に従います。

2. Objectives

2. 目的

The objectives for the design of the alarm data model are:

アラームデータモデルの設計における目的は次のとおりです。

  • Users find it simple to use. If a system supports this module, it shall be straightforward to integrate it into a YANG-based alarm manager.
  • Alarms are viewed as states on resources and not as discrete notifications.
  • A precise definition of "alarm" is provided in order to exclude general events that should not be forwarded as alarm notifications.
  • Precise identification of alarm types and alarm instances is provided.
  • A management system should be able to pull all available alarm types from a system, i.e., read the alarm inventory from a system. This makes it possible to prepare alarm operators with corresponding alarm instructions.
  • Alarm-usability requirements are addressed; see Appendix G. While IETF and telecom standards have addressed alarms mostly from a protocol perspective, the process industry has published several relevant standards addressing requirements for a useful alarm interface; see [EEMUA] and [ISA182]. This document defines usability requirements as well as a YANG data model.
  • Mapping to [X.733], which is a requirement for some alarm systems, is achievable. Still, keep some of the X.733 concepts out of the core model in order to make the model small and easy to understand.
  • ユーザーが簡単に使えると感じること。 システムがこのモジュールをサポートしていれば、それをYANGベースのアラームマネージャーに統合するのは簡単であるはずです。
  • アラームを、個別の通知としてではなく、リソースの状態として捉えること。
  • アラームとして転送すべきではない一般的なイベントを除外するために、「アラーム」の正確な定義を示すこと。
  • アラームタイプとアラームインスタンスを正確に識別できるようにすること。
  • 管理システムが、利用可能なすべてのアラームタイプをシステムから取得できる、つまりシステムからアラームインベントリーを読み取れるようにすること。 これにより、アラームの運用者に、対応するアラーム手順書を準備しておくことが可能になります。
  • アラームのユーザビリティー要件に対処すること。Appendix Gを参照してください。 IETFや通信分野の標準は主にプロトコルの観点からアラームを扱ってきましたが、プロセス産業は、有用なアラームインターフェイスの要件を扱った関連する標準をいくつか発行しています。[EEMUA]と[ISA182]を参照してください。 この文書は、YANGデータモデルに加えてユーザビリティー要件も定義します。
  • 一部のアラームシステムで要件となっている[X.733]への対応付けが実現可能であること。 ただし、モデルを小さく理解しやすいものにするため、X.733の概念の一部はコアモデルの外に置きます。

3. Alarm Data Model Concepts

3. アラームデータモデルの概念

This section defines the fundamental concepts behind the data model. This section is rooted in the works of Vallin et. al [ALARMSEM].

このセクションでは、データモデルの背後にある基本的な概念を定義します。 このセクションは、Vallinらの研究[ALARMSEM]に基づいています。

3.1. Alarm Definition

3.1. アラームの定義

An alarm signifies an undesirable state in a resource that requires corrective action.

アラームは、是正措置を必要とする、リソースの望ましくない状態を表します。

There are two main things to remember from this definition:

この定義から覚えておくべき主な点は2つあります。

  1. It focuses on leaving out events and logging information in general. Alarms should only be used for undesired states that require action.
  2. It also focuses on alarms as a state on a resource, not the notifications that report the state changes.
  1. イベントやログ情報全般を除外することに重点を置いています。 アラームは、対処を必要とする望ましくない状態にのみ使用すべきです。
  2. また、状態の変化を報告する通知ではなく、リソースの状態としてのアラームに重点を置いています。

See Appendix F for information on how this definition relates to other alarm standards.

この定義が他のアラーム標準とどのように関係するかについては、Appendix Fを参照してください。

3.2. Alarm Type

3.2. アラームタイプ

This document defines an alarm type with an alarm-type id and an alarm-type qualifier.

この文書では、アラームタイプをアラームタイプIDとアラームタイプ修飾子によって定義します。

The alarm-type id is modeled as a YANG identity. With YANG identities, new alarm types can be defined in a distributed fashion. YANG identities are hierarchical, which means that a hierarchy of alarm types can be defined.

アラームタイプIDはYANGアイデンティティーとしてモデル化されます。 YANGアイデンティティーを使用すると、新しいアラームタイプを分散的に定義できます。 YANGアイデンティティーは階層的であり、これはアラームタイプの階層を定義できることを意味します。

Standards and vendors should define their own alarm-type identities based on this definition.

標準化団体やベンダーは、この定義に基づいて独自のアラームタイプのアイデンティティーを定義すべきです。

The use of YANG identities means that all possible alarms are identified at design time. This explicit declaration of alarm types makes it easier to allow for alarm qualification reviews and preparation of alarm actions and documentation.

YANGアイデンティティーを使用するということは、発生しうるすべてのアラームが設計時に識別されることを意味します。 このようにアラームタイプを明示的に宣言することで、アラームの妥当性のレビューや、アラームへの対処手順と文書の準備が容易になります。

There are occasions where the alarm types are not known at design time. An example is a system with digital inputs that allows users to connect detectors, such as smoke detectors, to the inputs. In this case, it is a configuration action that says certain connectors are fire alarms, for example.

設計時にアラームタイプがわからない場合もあります。 たとえば、デジタル入力を備え、ユーザーが煙感知器などの感知器をその入力に接続できるシステムがあります。 この場合、たとえば特定のコネクターが火災報知器であることを示すのは設定作業です。

In order to allow for dynamic addition of alarm types, the alarm data model permits further qualification of the identity-based alarm type using a string. A potential drawback of this is that there is a significant risk that alarm operators will receive alarm types as a surprise. They do not know how to resolve the problem since a defined alarm procedure does not necessarily exist. To avoid this risk, the system MUST publish all possible alarm types in the alarm inventory; see Section 4.2.

アラームタイプを動的に追加できるように、アラームデータモデルでは、アイデンティティーに基づくアラームタイプを文字列によってさらに修飾することを許可しています。 この方法の潜在的な欠点は、アラームの運用者が予期しないアラームタイプを受け取るリスクがかなり高いことです。 定義されたアラーム手順が存在するとは限らないため、運用者は問題の解決方法がわかりません。 このリスクを避けるために、システムは発生しうるすべてのアラームタイプをアラームインベントリーで公開しなければなりません（MUST）。Section 4.2を参照してください。

A vendor or standards organization can define their own alarm-type hierarchy. The example below shows a hierarchy based on X.733 event types:

ベンダーや標準化団体は、独自のアラームタイプ階層を定義できます。 以下の例は、X.733のイベントタイプに基づく階層を示しています。

  import ietf-alarms {
    prefix al;
  }
  identity vendor-alarms {
    base al:alarm-type;
  }
  identity communications-alarm {
    base vendor-alarms;
  }
  identity link-alarm {
    base communications-alarm;
  }


  import ietf-alarms {
    prefix al;
  }
  identity vendor-alarms {
    base al:alarm-type;
  }
  identity communications-alarm {
    base vendor-alarms;
  }
  identity link-alarm {
    base communications-alarm;
  }

アラームタイプは抽象的なものにできます。 抽象アラームタイプは、階層的なアラームタイプを定義するための基底として使用されます。 具象アラームタイプはアラーム状態に使用され、アラームインベントリーに現れます。 具象アラームタイプには2種類あります。

  1. The last subordinate identity in the "alarm-type-id" hierarchy is concrete, for example, "alarm-identity.environmental-alarm.smoke". In this example, "alarm-identity" and "environmental-alarm" are abstract YANG identities, whereas "smoke" is a concrete YANG identity.
  2. The YANG identity hierarchy is abstract, and the concrete alarm type is defined by the dynamic alarm-qualifier string, for example, "alarm-identity.environmental-alarm.external-detector" with alarm-type-qualifier "smoke".
  1. 「alarm-type-id」階層の最下位のアイデンティティーが具象的なもの。たとえば、「alarm-identity.environmental-alarm.smoke」です。 この例では、「alarm-identity」と「environmental-alarm」は抽象YANGアイデンティティーであり、「smoke」は具象YANGアイデンティティーです。
  2. YANGアイデンティティーの階層は抽象的で、具象アラームタイプは動的なアラーム修飾子の文字列によって定義されるもの。たとえば、alarm-type-qualifierが「smoke」である「alarm-identity.environmental-alarm.external-detector」です。

サーバーは、動的に定義されるアラームタイプの数を最小限に抑えるよう努めるべきです（SHOULD）。

3.3. Identifying the Alarming Resource

3.3. アラームを発しているリソースの識別

It is of vital importance to be able to refer to the alarming resource. This reference must be as fine-grained as possible. If the alarming resource exists in the data tree, an instance-identifier MUST be used with the full path to the object.

アラームを発しているリソースを参照できることは極めて重要です。 この参照は可能な限りきめ細かくなければなりません。 アラームを発しているリソースがデータツリー内に存在する場合は、そのオブジェクトへの完全なパスを持つinstance-identifierを使用しなければなりません（MUST）。

When the module is used in a controller/orchestrator/manager, the original device resource identification can be modified to include the device in the path. The details depend on how devices are identified and are out of scope for this specification.

このモジュールをコントローラー／オーケストレーター／マネージャーで使用する場合、元の機器のリソース識別を変更して、パスにその機器を含めることができます。 詳細は機器の識別方法に依存し、この仕様の範囲外です。

Example:

例：

  • The original device alarm might identify the resource as "/dev:interfaces/dev:interface[dev:name='FastEthernet1/0']".
  • The resource identification in the manager could look something like: "/mgr:devices/mgr:device[mgr:name='xyz123']/dev:interfaces/dev:interface[dev:name='FastEthernet1/0']"
  • 元の機器のアラームは、リソースを「/dev:interfaces/dev:interface[dev:name='FastEthernet1/0']」として識別するかもしれません。
  • マネージャーにおけるリソース識別は、「/mgr:devices/mgr:device[mgr:name='xyz123']/dev:interfaces/dev:interface[dev:name='FastEthernet1/0']」のようになるかもしれません。

This module also allows for alternate naming of the alarming resource if it is not available in the data tree.

このモジュールでは、アラームを発しているリソースがデータツリー内で利用できない場合に、そのリソースに別の名前を付けることもできます。

3.4. Identifying Alarm Instances

3.4. アラームインスタンスの識別

A primary goal of the alarm data model is to remove any ambiguity in how alarm notifications are mapped to an update of an alarm instance. The X.733 [X.733] and 3GPP [ALARMIRP] documents were not clear on this point. This alarm data model states that the tuple (resource, alarm-type identifier, and alarm-type qualifier) corresponds to a single alarm instance. This means that alarm notifications for the same resource and same alarm type are matched to update the same alarm instance. These three leafs are therefore used as the key in the alarm list:

アラームデータモデルの主な目標は、アラーム通知がアラームインスタンスの更新にどのように対応付けられるかについての曖昧さをなくすことです。 X.733 [X.733]と3GPP [ALARMIRP]の文書は、この点が明確ではありませんでした。 このアラームデータモデルでは、タプル（リソース、アラームタイプ識別子、アラームタイプ修飾子）が単一のアラームインスタンスに対応すると定めます。 これは、同じリソースと同じアラームタイプに関するアラーム通知が照合され、同じアラームインスタンスを更新することを意味します。 したがって、これら3つのリーフがアラームリストのキーとして使用されます。

  list alarm {
    key "resource alarm-type-id alarm-type-qualifier";
    ...
  }


  list alarm {
    key "resource alarm-type-id alarm-type-qualifier";
    ...
  }

3.5. Alarm Lifecycle

3.5. アラームのライフサイクル

The alarm model clearly separates the resource alarm lifecycle from the operator and administrative lifecycles of an alarm.

このアラームモデルは、リソースのアラームライフサイクルを、アラームの運用者ライフサイクルおよび管理ライフサイクルから明確に分離しています。

  • resource alarm lifecycle: the alarm instrumentation that controls alarm raise, clearance, and severity changes.
  • operator alarm lifecycle: operators acting upon alarms with actions like acknowledging and closing. Closing an alarm implies that the operator considers the corrective action performed. Operators can also shelve (block/filter) alarms in order to avoid nuisance alarms.
  • administrative alarm lifecycle: purging (deleting) unwanted alarms and compressing the alarm status-change list. This module exposes operations to manage the administrative lifecycle. The server may also perform these operations based on other policies, but how that is done is out of scope for this document.
  • リソースのアラームライフサイクル：アラームの発生、クリア、重大度の変化を制御するアラームの計装です。
  • 運用者のアラームライフサイクル：運用者が、確認応答やクローズなどのアクションによってアラームに対処することです。 アラームをクローズすることは、運用者が是正措置を実施済みとみなしていることを意味します。 運用者は、迷惑アラームを避けるために、アラームを棚上げ（ブロック／フィルター）することもできます。
  • 管理上のアラームライフサイクル：不要なアラームのパージ（削除）と、アラームのステータス変更リストの圧縮です。 このモジュールは、管理ライフサイクルを管理するための操作を公開します。 サーバーは、他のポリシーに基づいてこれらの操作を実行することもありますが、その方法はこの文書の範囲外です。

A server SHOULD describe how long it retains cleared/closed alarms until they are manually purged or if it has an automatic removal policy. How this is done is outside the scope of this document.

サーバーは、クリアまたはクローズされたアラームを手動でパージされるまでどのくらいの期間保持するか、あるいは自動削除ポリシーがあるかどうかを記述すべきです（SHOULD）。 その方法はこの文書の範囲外です。

3.5.1. Resource Alarm Lifecycle

3.5.1. リソースのアラームライフサイクル

From a resource perspective, an alarm can, for example, have the following lifecycle: raise, change severity, change severity, clear, being raised again, etc. All of these status changes can have different alarm texts generated by the instrumentation. Two important things to note:

リソースの観点からは、アラームはたとえば、発生、重大度の変化、重大度の変化、クリア、再発生などのライフサイクルをたどります。 これらのステータス変更にはすべて、計装によって生成される異なるアラームテキストを持たせることができます。 注意すべき重要な点が2つあります。

  1. Alarms are not deleted when they are cleared. Deleting alarms is an administrative process. The "ietf-alarms" YANG module defines an action "purge-alarms" that deletes alarms.
  2. Alarms are not cleared by operators; only the underlying instrumentation can clear an alarm. Operators can close alarms.
  1. アラームはクリアされても削除されません。 アラームの削除は管理上のプロセスです。 「ietf-alarms」YANGモジュールは、アラームを削除するアクション「purge-alarms」を定義しています。
  2. アラームは運用者によってクリアされることはありません。アラームをクリアできるのは、その基盤となる計装だけです。 運用者はアラームをクローズできます。

The YANG tree representation below illustrates the resource-oriented lifecycle:

以下のYANGツリー表現は、リソース指向のライフサイクルを示しています。

  +--ro alarm* [resource alarm-type-id alarm-type-qualifier]
     ...
     +--ro is-cleared                 boolean
     +--ro last-raised                yang:date-and-time
     +--ro last-changed               yang:date-and-time
     +--ro perceived-severity         severity
     +--ro alarm-text                 alarm-text
     +--ro status-change* [time] {alarm-history}?
        +--ro time                    yang:date-and-time
        +--ro perceived-severity      severity-with-clear
        +--ro alarm-text              alarm-text


  +--ro alarm* [resource alarm-type-id alarm-type-qualifier]
     ...
     +--ro is-cleared                 boolean
     +--ro last-raised                yang:date-and-time
     +--ro last-changed               yang:date-and-time
     +--ro perceived-severity         severity
     +--ro alarm-text                 alarm-text
     +--ro status-change* [time] {alarm-history}?
        +--ro time                    yang:date-and-time
        +--ro perceived-severity      severity-with-clear
        +--ro alarm-text              alarm-text

For every status change from the resource perspective, a row is added to the "status-change" list, if the server implements the feature "alarm-history". The feature "alarm-history" is optional to implement, since keeping the alarm history may have an impact on the server's memory resources.

サーバーが機能「alarm-history」を実装している場合、リソースの観点からのステータス変更ごとに、「status-change」リストに行が追加されます。 アラーム履歴を保持するとサーバーのメモリー資源に影響を与える可能性があるため、機能「alarm-history」の実装は任意です。

The last status values are also represented as leafs for the alarm. Note well that the alarm severity does not include "cleared"; alarm clearance is a boolean flag.

最新のステータス値は、アラームのリーフとしても表現されます。 アラームの重大度には「cleared」が含まれないことに十分注意してください。アラームのクリアはブール値のフラグです。

Therefore, an alarm can look like this: (("GigabitEthernet0/25", "link-alarm",""), false, 2018-04-08T08:20:10.00Z, 2018-04-08T08:20:10.00Z, major, "Interface GigabitEthernet0/25 down").

したがって、アラームは次のようになります：(("GigabitEthernet0/25", "link-alarm",""), false, 2018-04-08T08:20:10.00Z, 2018-04-08T08:20:10.00Z, major, "Interface GigabitEthernet0/25 down")。

3.5.2. Operator Alarm Lifecycle

3.5.2. 運用者のアラームライフサイクル

Operators can act upon alarms using the set-operator-state action:

運用者は、set-operator-stateアクションを使用してアラームに対処できます。

  +--ro alarm* [resource alarm-type-id alarm-type-qualifier]
     ...
     +--ro operator-state-change* [time] {operator-actions}?
     |  +--ro time        yang:date-and-time
     |  +--ro operator    string
     |  +--ro state       operator-state
     |  +--ro text?       string
     +---x set-operator-state {operator-actions}?
        +---w input
           +---w state    writable-operator-state
           +---w text?    string


  +--ro alarm* [resource alarm-type-id alarm-type-qualifier]
     ...
     +--ro operator-state-change* [time] {operator-actions}?
     |  +--ro time        yang:date-and-time
     |  +--ro operator    string
     |  +--ro state       operator-state
     |  +--ro text?       string
     +---x set-operator-state {operator-actions}?
        +---w input
           +---w state    writable-operator-state
           +---w text?    string

The operator state for an alarm can be "none", "ack", "shelved", and "closed". Alarm deletion (using the action "purge-alarms") can use this state as a criterion. For example, a closed alarm is an alarm where the operator has performed any required corrective actions. Closed alarms are good candidates for being purged.

アラームの運用者状態は、「none」、「ack」、「shelved」、「closed」のいずれかです。 アラームの削除（アクション「purge-alarms」を使用）では、この状態を基準として使用できます。 たとえば、クローズされたアラームとは、運用者が必要な是正措置をすべて実施したアラームです。 クローズされたアラームは、パージの有力な候補です。

3.5.3. Administrative Alarm Lifecycle

3.5.3. 管理上のアラームライフサイクル

Deleting alarms from the alarm list is considered an administrative action. This is supported by the "purge-alarms" action. The "purge-alarms" action takes a filter as input. The filter selects alarms based on the operator and resource alarm lifecycle such as "all closed cleared alarms older than a time specification". The server may also perform these operations based on other policies, but how that is done is out of scope for this document.

アラームリストからアラームを削除することは、管理上のアクションとみなされます。 これは「purge-alarms」アクションによってサポートされます。 「purge-alarms」アクションは、入力としてフィルターを受け取ります。 フィルターは、「指定した時刻より古い、クローズされクリアされたすべてのアラーム」のように、運用者とリソースのアラームライフサイクルに基づいてアラームを選択します。 サーバーは、他のポリシーに基づいてこれらの操作を実行することもありますが、その方法はこの文書の範囲外です。

Purged alarms are removed from the alarm list. Note well that if the alarm resource state changes after a purge, the alarm will reappear in the alarm list.

パージされたアラームは、アラームリストから削除されます。 パージ後にアラームのリソース状態が変化すると、そのアラームはアラームリストに再び現れることに十分注意してください。

Alarms can be compressed. Compressing an alarm deletes all entries in the alarm's "status-change" list except for the last status change. A client can perform this using the "compress-alarms" action. The server may also perform these operations based on other policies, but how that is done is out of scope for this document.

アラームは圧縮できます。 アラームを圧縮すると、そのアラームの「status-change」リストのエントリーのうち、最後のステータス変更以外のすべてが削除されます。 クライアントは「compress-alarms」アクションを使用してこれを実行できます。 サーバーは、他のポリシーに基づいてこれらの操作を実行することもありますが、その方法はこの文書の範囲外です。

3.6. Root Cause, Impacted Resources, and Related Alarms

3.6. 根本原因、影響を受けるリソース、関連するアラーム

The alarm data model does not mandate any requirements for the system to support alarm correlation or root-cause and service-impact analysis. However, if such features are supported, this section describes how the results of such analysis are represented in the data model. These parts of the model are optional. The module supports three scenarios:

アラームデータモデルは、アラーム相関、根本原因分析、サービス影響分析をサポートすることをシステムに義務付けてはいません。 ただし、そのような機能がサポートされている場合に、そうした分析の結果をデータモデルでどのように表現するかを、このセクションで説明します。 モデルのこれらの部分は任意です。 このモジュールは3つのシナリオをサポートします。

Root-cause analysis:
An alarm can indicate candidate root-cause resources, for example, a database issue alarm referring to a full-disk partition.
Service-impact analysis:
An alarm can refer to potential impacted resources, for example, an interface alarm referring to impacted network services.
Alarm correlation:
Dependencies between alarms; several alarms can be grouped as relating to each other, for example, a streaming media alarm relating to a high-jitter alarm.
根本原因分析：
アラームは、根本原因の候補となるリソースを示すことができます。たとえば、ディスクが満杯になったパーティションを参照する、データベースの問題に関するアラームです。
サービス影響分析：
アラームは、影響を受ける可能性のあるリソースを参照できます。たとえば、影響を受けるネットワークサービスを参照する、インターフェイスのアラームです。
アラーム相関：
アラーム間の依存関係です。複数のアラームを互いに関連するものとしてグループ化できます。たとえば、高ジッターのアラームに関連するストリーミングメディアのアラームです。

Different systems have varying degrees of alarm correlation and analysis capabilities, and the intent of the alarm data model is to enable any capability, including none.

システムによってアラーム相関や分析の能力の程度はさまざまであり、アラームデータモデルの意図は、能力がまったくない場合も含め、どのような能力でも扱えるようにすることです。

The general principle of this alarm data model is to limit the amount of alarms. In many cases, several resources are affected for a given underlying problem. A full disk will of course impact databases and applications as well. The recommendation is to have a single alarm for the underlying problem and list the affected resources in the alarm rather than having separate alarms for each resource.

このアラームデータモデルの一般原則は、アラームの量を制限することです。 多くの場合、ある根本的な問題によって複数のリソースが影響を受けます。 ディスクが満杯になれば、当然データベースやアプリケーションにも影響します。 推奨されるのは、リソースごとに個別のアラームを出すのではなく、根本的な問題に対して単一のアラームを出し、影響を受けるリソースをそのアラームに列挙することです。

The alarm has one leaf-list to identify a possible "impacted-resource" and a leaf-list to identify a possible "root-cause-resource". These serve as hints only. It is up to the client application to use this information to present the overall status. Using the disk-full example, a good alarm would be to use the hard-disk partition as the alarming resource and add the database and applications into the "impacted-resource" leaf-list.

アラームには、影響を受ける可能性のある「impacted-resource」を識別するリーフリストと、根本原因である可能性のある「root-cause-resource」を識別するリーフリストが1つずつあります。 これらはヒントとしてのみ機能します。 この情報を使用して全体的な状態をどのように提示するかは、クライアントアプリケーション次第です。 ディスク満杯の例では、ハードディスクのパーティションをアラームを発しているリソースとし、データベースとアプリケーションを「impacted-resource」リーフリストに追加するのがよいアラームでしょう。

A system should always strive to identify the resource that can be acted upon as the "resource" leaf. The "impacted-resource" leaf-list shall be used to identify any side effects of the alarm. The impacted resources cannot be acted upon to fix the problem. The disk full example above illustrates the principle; you cannot fix the underlying issue by database operations. However, you need to pay attention to the database to perform any operations that limit the impact of the problem.

システムは常に、対処の対象となりうるリソースを「resource」リーフとして識別するよう努めるべきです。 「impacted-resource」リーフリストは、アラームの副作用を識別するために使用することになります。 影響を受けるリソースに対処しても問題は解決できません。 上記のディスク満杯の例がこの原則を示しています。データベースの操作では根本的な問題を解決できません。 しかし、問題の影響を抑えるための操作を行うには、データベースに注意を払う必要があります。

On some occasions, the system might not be capable of detecting the root cause, the resource that can be acted upon. The instrumentation in this case only monitors the side effect and raises an alarm to indicate a situation requiring attention. The instrumentation still might identify possible candidates for the root-cause resource. In this case, the "root-cause-resource" leaf-list can be used to indicate the candidate root-cause resources. An example of this kind of alarm might be an active test tool that detects a Service Level Agreement (SLA) violation on a VPN connection and identifies the devices along the chain as candidate root causes.

場合によっては、システムが根本原因、つまり対処の対象となりうるリソースを検出できないことがあります。 この場合、計装は副作用を監視するだけで、注意を要する状況を示すためにアラームを発生させます。 それでも計装は、根本原因のリソースとなりうる候補を識別できる場合があります。 この場合、「root-cause-resource」リーフリストを使用して、根本原因の候補となるリソースを示すことができます。 この種のアラームの例としては、VPNコネクション上のサービスレベル合意（SLA）違反を検出し、経路上の機器を根本原因の候補として識別するアクティブテストツールが考えられます。

The alarm data model also supports a way to associate different alarms with each other using the "related-alarm" list. This list enables the server to inform the client that certain alarms are related to other alarms.

アラームデータモデルは、「related-alarm」リストを使用して異なるアラームを互いに関連付ける方法もサポートしています。 このリストにより、サーバーは、特定のアラームが他のアラームに関連していることをクライアントに伝えることができます。

Note well that this module does not prescribe any dependencies or preference between the above alarm correlation mechanisms. Different systems have different capabilities, and the above described mechanisms are available to support the instrumentation features.

このモジュールは、上記のアラーム相関のメカニズム間の依存関係や優先順位を何も規定していないことに十分注意してください。 システムによって能力は異なり、上記のメカニズムは計装の機能をサポートするために利用できるものです。

3.7. Alarm Shelving

3.7. アラームの棚上げ

Alarm shelving is an important function in order for alarm-management applications and operators to stop superfluous alarms. A shelved alarm implies that any alarms fulfilling these criteria are ignored (blocked/filtered). Shelved alarms appear in a dedicated shelved-alarm list; thus, they can be filtered out so that the main alarm list only contains entries of interest. Shelved alarms do not generate notifications, but the shelved-alarm list is updated with any alarm-state changes.

アラームの棚上げは、アラーム管理アプリケーションや運用者が余計なアラームを止めるための重要な機能です。 アラームを棚上げするということは、その基準を満たすアラームがすべて無視（ブロック／フィルター）されることを意味します。 棚上げされたアラームは専用の棚上げアラームリストに現れます。したがって、メインのアラームリストに関心のあるエントリーだけが含まれるように、それらを除外できます。 棚上げされたアラームは通知を生成しませんが、棚上げアラームリストはアラーム状態の変化に応じて更新されます。

Alarm shelving is optional to implement, since matching alarms against shelf criteria may have an impact on the server's processing resources.

アラームをシェルフの基準と照合するとサーバーの処理資源に影響を与える可能性があるため、アラームの棚上げの実装は任意です。

3.8. Alarm Profiles

3.8. アラームプロファイル

Alarm profiles are used to configure further information to an alarm type. This module supports configuring severity levels overriding the system-default levels. This corresponds to the Alarm Severity Assignment Profile (ASAP) functionality in M.3100 [M.3100] and M.3160 [M.3160]. Other standard or enterprise modules can augment this list with further alarm-type information.

アラームプロファイルは、アラームタイプに追加の情報を設定するために使用されます。 このモジュールは、システムのデフォルトのレベルを上書きする重大度レベルの設定をサポートします。 これは、M.3100 [M.3100]とM.3160 [M.3160]のアラーム重大度割り当てプロファイル（ASAP）機能に相当します。 他の標準モジュールや企業のモジュールは、このリストを拡張（augment）して、アラームタイプに関するさらなる情報を追加できます。

4.1. Alarm Control

4.1. アラームの制御

The "/alarms/control/notify-status-changes" leaf controls whether notifications are sent for all state changes, only raise and clear, or only notifications more severe than a configured level. This feature, in combination with alarm shelving, corresponds to the ITU Alarm Report Control functionality; see Appendix F.2.4.

「/alarms/control/notify-status-changes」リーフは、すべての状態変化について通知を送信するか、発生とクリアについてのみ送信するか、設定されたレベルよりも重大な通知のみを送信するかを制御します。 この機能は、アラームの棚上げと組み合わせることで、ITUのアラーム報告制御（Alarm Report Control）機能に相当します。Appendix F.2.4を参照してください。

Every alarm has a list of status changes. The length of this list is controlled by "/alarms/control/max-alarm-status-changes". When the list is full and a new entry created, the oldest entry is removed.

すべてのアラームは、ステータス変更のリストを持ちます。 このリストの長さは「/alarms/control/max-alarm-status-changes」によって制御されます。 リストが満杯のときに新しいエントリーが作成されると、最も古いエントリーが削除されます。

4.2. Alarm Inventory

4.2. アラームインベントリー

The alarm inventory represents all possible alarm types that may occur in the system. A management system may use this to build alarm procedures. The alarm inventory is relevant for the following reasons:

  • システムは定義されたすべてのアラームタイプのアイデンティティーを実装しているとは限らず、また一部のアラームのアイデンティティーは抽象的です。

アラームタイプ修飾子を使用して動的なアラームタイプを追加するメカニズムは、このリストにデータを投入しなければなりません（MUST）。

4.5. The Shelved-Alarm List

4.5. 棚上げアラームリスト

The shelved-alarm list has the same structure as the alarm list above. It shows all the alarms that match the shelving criteria "/alarms/control/alarm-shelving".

棚上げアラームリストは、上記のアラームリストと同じ構造を持ちます。 棚上げの基準「/alarms/control/alarm-shelving」に一致するすべてのアラームを示します。

4.6. Alarm Profiles

4.6. アラームプロファイル

Alarm profiles, "/alarms/alarm-profile", is a list of configurable alarm types. The list supports configurable alarm severity levels in the container "alarm-severity-assignment-profile". If an alarm matches the configured alarm type, it MUST use the configured severity level(s) instead of the system default. This configuration MUST also be represented in the alarm inventory.

アラームプロファイル「/alarms/alarm-profile」は、設定可能なアラームタイプのリストです。 このリストは、コンテナー「alarm-severity-assignment-profile」で、設定可能なアラームの重大度レベルをサポートします。 アラームが設定されたアラームタイプに一致する場合、そのアラームはシステムのデフォルトではなく、設定された重大度レベルを使用しなければなりません（MUST）。 この設定は、アラームインベントリーにも反映しなければなりません（MUST）。

  +--rw alarm-profile*
          [alarm-type-id alarm-type-qualifier-match resource]
          {alarm-profile}?
     +--rw alarm-type-id                        alarm-type-id
     +--rw alarm-type-qualifier-match           string
     +--rw resource                             resource-match
     +--rw description                          string
     +--rw alarm-severity-assignment-profile
             {severity-assignment}?
        +--rw severity-level*    severity


  +--rw alarm-profile*
          [alarm-type-id alarm-type-qualifier-match resource]
          {alarm-profile}?
     +--rw alarm-type-id                        alarm-type-id
     +--rw alarm-type-qualifier-match           string
     +--rw resource                             resource-match
     +--rw description                          string
     +--rw alarm-severity-assignment-profile
             {severity-assignment}?
        +--rw severity-level*    severity

4.7. Operations

4.7. 操作

The alarm data model supports the following actions to manage the alarms:

アラームデータモデルは、アラームを管理するための次のアクションをサポートします。

"/alarms/alarm-list/purge-alarms":
Delete alarms from the "alarm-list" according to specific criteria, for example, all cleared alarms older than a specific date.
"/alarms/alarm-list/compress-alarms":
Compress the "status-change" list for the alarms.
"/alarms/alarm-list/alarm/set-operator-state":
Change the operator state for an alarm. For example, an alarm can be acknowledged by setting the operator state to "ack".
"/alarms/shelved-alarm-list/purge-shelved-alarms":
Delete alarms from the "shelved-alarm-list" according to specific criteria, for example, all alarms older than a specific date.
"/alarms/shelved-alarm-list/compress-shelved-alarms":
Compress the "status-change" list for the alarms.
「/alarms/alarm-list/purge-alarms」：
特定の基準に従って「alarm-list」からアラームを削除します。たとえば、特定の日付より古い、クリアされたすべてのアラームです。
「/alarms/alarm-list/compress-alarms」：
アラームの「status-change」リストを圧縮します。
「/alarms/alarm-list/alarm/set-operator-state」：
アラームの運用者状態を変更します。 たとえば、運用者状態を「ack」に設定することで、アラームに確認応答できます。
「/alarms/shelved-alarm-list/purge-shelved-alarms」：
特定の基準に従って「shelved-alarm-list」からアラームを削除します。たとえば、特定の日付より古いすべてのアラームです。
「/alarms/shelved-alarm-list/compress-shelved-alarms」：
アラームの「status-change」リストを圧縮します。

4.8. Notifications

4.8. 通知

The alarm data model supports a general notification to report alarm-state changes. It carries all relevant parameters for the alarm-management application.

アラームデータモデルは、アラーム状態の変化を報告するための汎用的な通知をサポートします。 この通知は、アラーム管理アプリケーションに関連するすべてのパラメーターを運びます。

There is also a notification to report that an operator changed the operator state on an alarm, like acknowledged.

また、運用者がアラームの運用者状態を変更した（たとえば確認応答した）ことを報告するための通知もあります。

If the alarm inventory is changed, for example, a new card type is inserted, a notification will tell the management application that new alarm types are available.

たとえば新しい種類のカードが挿入されるなどしてアラームインベントリーが変更された場合、新しいアラームタイプが利用可能になったことを通知によって管理アプリケーションに伝えます。

5. Relationship to the ietf-hardware YANG Module

5. ietf-hardware YANGモジュールとの関係

RFC 8348 [RFC8348] defines the "ietf-hardware" YANG data model for the management of hardware. The "alarm-state" in RFC 8348 is a summary of the alarm severity levels that may be active on the specific hardware component. It does not say anything about how alarms are reported, and it doesn't provide any details of the alarms.

RFC 8348 [RFC8348]は、ハードウェア管理のための「ietf-hardware」YANGデータモデルを定義しています。 RFC 8348の「alarm-state」は、特定のハードウェアコンポーネント上で有効になっている可能性のあるアラームの重大度レベルの要約です。 アラームがどのように報告されるかについては何も述べておらず、アラームの詳細も提供しません。

The mapping between the alarm YANG data model, prefix "al", and the "alarm-state" in RFC 8348, prefix "hw", is as follows:

プレフィックスが「al」であるアラームYANGデータモデルと、プレフィックスが「hw」であるRFC 8348の「alarm-state」との対応関係は次のとおりです。

"al:resource":
Corresponds to an entry in the list "/hw:hardware/hw:component/".
"al:is-cleared":
No bit set in "/hw:hardware/hw:component/hw:state/hw:alarm-state".
"al:perceived-severity":
Corresponding bit set in "/hw:hardware/hw:component/hw:state/hw:alarm-state".
"al:operator-state-change/al:state":
If the alarm is acknowledged by the operator, the bit "hw:under-repair" is set in "/hw:hardware/hw:component/hw:state/hw:alarm-state".
「al:resource」：
リスト「/hw:hardware/hw:component/」のエントリーに対応します。
「al:is-cleared」：
「/hw:hardware/hw:component/hw:state/hw:alarm-state」でビットがセットされていないことに対応します。
「al:perceived-severity」：
「/hw:hardware/hw:component/hw:state/hw:alarm-state」で対応するビットがセットされていることに対応します。
「al:operator-state-change/al:state」：
運用者がアラームに確認応答した場合、「/hw:hardware/hw:component/hw:state/hw:alarm-state」でビット「hw:under-repair」がセットされます。

     Main features of this module include:

       * Alarm list:

     notification).  An alarm type is a possible alarm state for a
     resource.  For example, the tuple:

       ('link-alarm', 'GigabitEthernet0/25')

    "This module defines an interface for managing alarms.  Main
     inputs to the module design are the 3GPP Alarm Integration
     Reference Point (IRP), ITU-T X.733, and ANSI/ISA-18.2 alarm
     standards.

     Main features of this module include:

       * Alarm list:
                 A list of all alarms.  Cleared alarms stay in
                 the list until explicitly purged.

       * Operator actions on alarms:
                 Acknowledging and closing alarms.

       * Administrative actions on alarms:
                 Purging alarms from the list according to specific
                 criteria.

       * Alarm inventory:
                 A management application can read all
                 alarm types implemented by the system.

       * Alarm shelving:
                 Shelving (blocking) alarms according
                 to specific criteria.

       * Alarm profiles:
                 A management system can attach further
                 information to alarm types, for example,
                 overriding system-default severity
                 levels.

     This module uses a stateful view on alarms.  An alarm is a state
     for a specific resource (note that an alarm is not a
     notification).  An alarm type is a possible alarm state for a
     resource.  For example, the tuple:

       ('link-alarm', 'GigabitEthernet0/25')

     is an alarm of type 'link-alarm' on the resource
     'GigabitEthernet0/25'.

     Alarm types are identified using YANG identities and an optional
     string-based qualifier.  The string-based qualifier allows for
     dynamic extension of the statically defined alarm types.  Alarm
     types identify a possible alarm state and not the individual
     notifications.  For example, the traditional 'link-down' and
     'link-up' notifications are two notifications referring to the
     same alarm type 'link-alarm'.

     With this design, there is no ambiguity about how alarm and
     alarm clear correlation should be performed; notifications that
     report the same resource and alarm type are considered updates
     of the same alarm, e.g., clearing an active alarm or changing
     the severity of an alarm.  The instrumentation can update the
     severity and alarm text on an existing alarm.  The above alarm
     example can therefore look like the following:

       (('link-alarm', 'GigabitEthernet0/25'),
        warning,
        'interface down while interface admin state is up')

     the underlying resource, like clear, and updates from an
     operator, like acknowledging or closing an alarm:

       (('link-alarm', 'GigabitEthernet0/25'),
        warning,
        'interface down while interface admin state is up',
        cleared,
        closed)

     given time is supported.

7. The X.733 Mapping Module

7. X.733対応付けモジュール

Many alarm systems are based on the X.733 [X.733] and X.736 [X.736] alarm standards. This module "ietf-alarms-x733" augments the alarm inventory, the alarm lists, and the alarm notification with X.733 and X.736 parameters.

多くのアラームシステムは、X.733 [X.733]およびX.736 [X.736]のアラーム標準に基づいています。 このモジュール「ietf-alarms-x733」は、アラームインベントリー、アラームリスト、アラーム通知を、X.733とX.736のパラメーターで拡張（augment）します。

The module also supports a feature whereby the alarm manager can configure the mapping from alarm types to X.733 "event-type" and "probable-cause" parameters. This might be needed when the default mapping provided by the system is in conflict with other management systems or not considered correct.

このモジュールは、アラームマネージャーがアラームタイプからX.733の「event-type」パラメーターと「probable-cause」パラメーターへの対応付けを設定できる機能もサポートしています。 これは、システムが提供するデフォルトの対応付けが他の管理システムと矛盾する場合や、正しくないとみなされる場合に必要になるかもしれません。

Note that the term "resource" in this document is synonymous to the ITU term "managed object".

この文書における用語「リソース（resource）」は、ITUの用語「管理オブジェクト（managed object）」と同義であることに注意してください。

This YANG module references [RFC6991], [X.721], [X.733], and [X.736].

このYANGモジュールは、[RFC6991]、[X.721]、[X.733]、[X.736]を参照しています。

9. Security Considerations

9. セキュリティーに関する考慮事項

The YANG modules specified in this document define a schema for data that is designed to be accessed via network management protocols such as NETCONF [RFC6241] or RESTCONF [RFC8040]. The lowest NETCONF layer is the secure transport layer, and the mandatory-to-implement secure transport is Secure Shell (SSH) [RFC6242]. The lowest RESTCONF layer is HTTPS, and the mandatory-to-implement secure transport is TLS [RFC8446].

この文書で規定するYANGモジュールは、NETCONF [RFC6241]やRESTCONF [RFC8040]などのネットワーク管理プロトコルを介してアクセスされるように設計されたデータのスキーマを定義します。 NETCONFの最下層はセキュアなトランスポート層であり、実装必須のセキュアなトランスポートはSSH（Secure Shell）[RFC6242]です。 RESTCONFの最下層はHTTPSであり、実装必須のセキュアなトランスポートはTLS [RFC8446]です。

The Network Configuration Access Control Model (NACM) [RFC8341] provides the means to restrict access for particular NETCONF or RESTCONF users to a preconfigured subset of all available NETCONF or RESTCONF protocol operations and content.

ネットワーク設定アクセス制御モデル（NACM）[RFC8341]は、特定のNETCONFユーザーまたはRESTCONFユーザーのアクセスを、利用可能なすべてのNETCONFまたはRESTCONFのプロトコル操作とコンテンツのうち、事前に設定されたサブセットに制限する手段を提供します。

The list of alarms itself may be potentially sensitive from a security perspective, in that it potentially gives an attacker an authoritative picture of the (broken) state of the network.

アラームのリスト自体が、セキュリティーの観点から機密性の高いものになる可能性があります。攻撃者に、ネットワークの（故障した）状態についての信頼できる全体像を与える可能性があるためです。

There are a number of data nodes defined in the YANG modules that are writable/creatable/deletable (i.e., config true, which is the default). These data nodes may be considered sensitive or vulnerable in some network environments. Write operations (e.g., edit-config) to these data nodes without proper protection can have a negative effect on network operations. These are the subtrees and data nodes in the "ietf-alarms" module and their sensitivity/vulnerability:

YANGモジュールで定義されているデータノードの多くは、書き込み／作成／削除が可能です（つまり、デフォルトであるconfig trueです）。 これらのデータノードは、一部のネットワーク環境では機密性が高い、または脆弱であるとみなされる場合があります。 適切な保護なしにこれらのデータノードへの書き込み操作（たとえば、edit-config）を行うと、ネットワークの運用に悪影響を及ぼす可能性があります。 以下に、「ietf-alarms」モジュールのサブツリーとデータノード、およびその機密性／脆弱性を示します。

"/alarms/control/notify-status-changes":
This leaf controls whether an alarm should notify based on various state changes. Unauthorized access to this leaf could have a negative impact on operational procedures relying on fine-grained alarm-state change reporting.
"/alarms/control/alarm-shelving/shelf":
This list controls the shelving (blocking) of alarms. Unauthorized access to this list could jeopardize the alarm-management procedures, since these alarms will not be notified or be part of the alarm list.
"/alarms/control/alarm-profile/alarm-severity-assignment-profile":
This list controls the severity levels of an alarm. Unauthorized access to this could, for example, downgrade the severity of an alarm and thereby have a negative impact on the alarm-monitoring process.
「/alarms/control/notify-status-changes」：
このリーフは、さまざまな状態変化に基づいてアラームを通知すべきかどうかを制御します。 このリーフへの不正アクセスは、きめ細かいアラーム状態変化の報告に依存する運用手順に悪影響を与える可能性があります。
「/alarms/control/alarm-shelving/shelf」：
このリストは、アラームの棚上げ（ブロック）を制御します。 対象のアラームは通知されず、アラームリストにも含まれなくなるため、このリストへの不正アクセスはアラーム管理の手順を危険にさらす可能性があります。
「/alarms/control/alarm-profile/alarm-severity-assignment-profile」：
このリストは、アラームの重大度レベルを制御します。 これへの不正アクセスは、たとえばアラームの重大度を下げ、それによってアラーム監視のプロセスに悪影響を与える可能性があります。

Some of the RPC operations in this YANG module may be considered sensitive or vulnerable in some network environments. It is thus important to control access to these operations. These are the operations and their sensitivity/vulnerability:

このYANGモジュールのRPC操作の一部は、一部のネットワーク環境では機密性が高い、または脆弱であるとみなされる場合があります。 したがって、これらの操作へのアクセスを制御することが重要です。 以下に、それらの操作とその機密性／脆弱性を示します。

"/alarms/alarm-list/purge-alarms":
This action deletes alarms from the alarm list. Unauthorized use of this action could jeopardize the alarm-management procedures since the deleted alarms may be vital for the alarm-management application.
"/alarms/alarm-list/alarm/set-operator-state":
This action can be used by the operator to indicate the level of human intervention on an alarm. Unauthorized use of this action could result in alarms being ignored by operators.
「/alarms/alarm-list/purge-alarms」：
このアクションは、アラームリストからアラームを削除します。 削除されたアラームはアラーム管理アプリケーションにとって不可欠である可能性があるため、このアクションの不正使用はアラーム管理の手順を危険にさらす可能性があります。
「/alarms/alarm-list/alarm/set-operator-state」：
このアクションは、運用者がアラームに対する人間の介入の程度を示すために使用できます。 このアクションの不正使用により、運用者がアラームを無視してしまう可能性があります。

F.2. Data Model

F.2. データモデル

This section describes how this YANG alarm data model relates to other standard data models. Note well that we cover other data models for alarm interfaces but not other standards such as SDO-specific alarms.

このセクションでは、このYANGアラームデータモデルが他の標準データモデルとどのように関係するかを説明します。 ここで扱うのはアラームインターフェイスのための他のデータモデルであり、SDO固有のアラームなどの他の標準は扱わないことに十分注意してください。

F.2.1. X.733

F.2.1. X.733

X.733 has acted as a base for several alarm data models over the years. The YANG alarm data model differs in the following ways:

X.733は長年にわたって、いくつかのアラームデータモデルの基盤となってきました。 YANGアラームデータモデルは、次の点で異なります。

  • X.733 models the alarm list as a list of notifications. The YANG alarm data model defines the alarm list as the current alarm states for the resources, which is generated from the state change reporting notifications.
  • In X.733, an alarm can have the severity level "clear". In the YANG alarm data model, "clear" is not a severity level; it is a separate state of the alarm. An alarm can have the following states, for example, (major, cleared) and (minor, not cleared).
  • X.733 uses a flat, globally defined enumerated "probable-cause" to identify alarm types. This alarm data model uses a hierarchical YANG identity: "alarm-type". This enables delegation of alarm types within organizations. It also enables management to reason about abstract alarm types corresponding to base identities; see Section 3.2.
  • The YANG alarm data model has not included the majority of the X.733 alarm attributes. Rather, these are defined in an augmenting module [X.733] if "strict" X.733 compliance is needed.
  • X.733は、アラームリストを通知のリストとしてモデル化しています。 YANGアラームデータモデルは、アラームリストをリソースの現在のアラーム状態として定義しており、これは状態変化を報告する通知から生成されます。
  • X.733では、アラームは重大度レベル「clear」を持つことができます。 YANGアラームデータモデルでは、「clear」は重大度レベルではなく、アラームの独立した状態です。 アラームは、たとえば（major、cleared）や（minor、not cleared）といった状態を持つことができます。
  • X.733は、アラームタイプを識別するために、グローバルに定義されたフラットな列挙型「probable-cause」を使用します。 このアラームデータモデルは、階層的なYANGアイデンティティー「alarm-type」を使用します。 これにより、組織内でアラームタイプを委任できます。 また、管理側が、基底アイデンティティーに対応する抽象アラームタイプについて推論することも可能になります。Section 3.2を参照してください。
  • YANGアラームデータモデルには、X.733のアラーム属性の大部分は含まれていません。 それらは、「厳密な」X.733準拠が必要な場合のために、拡張（augment）するモジュール[X.733]で定義されています。

F.2.2. The Alarm MIB (RFC 3877)

F.2.2. アラームMIB（RFC 3877）

The MIB in RFC 3877 takes a different approach; rather than defining a concrete data model for alarms, it defines a model to map existing SNMP-managed objects and notifications into alarm states and alarm notifications. This was necessary since MIBs were already defined with both managed objects and notifications indicating alarms, for example, "linkUp" and "linkDown" notifications in combination with "ifAdminState" and "ifOperState". So, RFC 3877 cannot really be compared to the alarm YANG module in that sense.

RFC 3877のMIBは異なるアプローチを取っています。アラームの具体的なデータモデルを定義するのではなく、既存のSNMP管理オブジェクトと通知をアラーム状態とアラーム通知に対応付けるモデルを定義しています。 これが必要だったのは、MIBにはすでに、アラームを示す管理オブジェクトと通知の両方が定義されていたためです。たとえば、「linkUp」通知と「linkDown」通知を「ifAdminState」と「ifOperState」と組み合わせたものです。 したがって、その意味でRFC 3877をアラームYANGモジュールと比較することは実際にはできません。

The Alarm MIB maps existing MIB definitions into alarms, such as "alarmModelTable". The upside of that is that an SNMP Manager can, at runtime, read the possible alarm types. This corresponds to the "alarmInventory" in the alarm YANG module.

アラームMIBは、「alarmModelTable」などの既存のMIB定義をアラームに対応付けます。 その利点は、SNMPマネージャーが実行時に発生しうるアラームタイプを読み取れることです。 これは、アラームYANGモジュールの「alarmInventory」に相当します。

F.2.3. 3GPP Alarm IRP

F.2.3. 3GPP Alarm IRP

The 3GPP Alarm IRP is an evolution of X.733. Main differences between the alarm YANG module and 3GPP are as follows:

3GPP Alarm IRPはX.733を発展させたものです。 アラームYANGモジュールと3GPPの主な違いは次のとおりです。

  • 3GPP keeps the majority of the X.733 attributes, but the alarm YANG module does not.
  • 3GPP introduced overlapping and possibly conflicting keys for alarms, alarmId, and (managed object, event type, probable cause, specific problem). (See Example 3 in Annex C of [ALARMIRP]). In the YANG alarm data model, the key for identifying an alarm instance is clearly defined by ("resource", "alarm-type-id", "alarm-type-qualifier"). See also Section 3.4 for more information.
  • The alarm YANG module clearly separates the resource/instrumentation lifecycle from the operator lifecycle. 3GPP allows operators to set the alarm severity to clear; this is not allowed by this module. Rather, an operator closes an alarm, which does not affect the severity.
  • 3GPPはX.733の属性の大部分を保持していますが、アラームYANGモジュールは保持していません。
  • 3GPPは、アラームに対して、重複し、矛盾する可能性のあるキーを導入しました。alarmIdと、（管理オブジェクト、イベントタイプ、推定原因、特定問題）です。 （[ALARMIRP]のAnnex CのExample 3を参照してください）。 YANGアラームデータモデルでは、アラームインスタンスを識別するためのキーは（「resource」、「alarm-type-id」、「alarm-type-qualifier」）によって明確に定義されています。 詳しくはSection 3.4も参照してください。
  • アラームYANGモジュールは、リソース／計装のライフサイクルを運用者のライフサイクルから明確に分離しています。 3GPPでは運用者がアラームの重大度をclearに設定できますが、このモジュールではそれは許可されていません。 代わりに、運用者はアラームをクローズします。これは重大度には影響しません。

F.2.4. G.7710

F.2.4. G.7710

G.7710 is different than the previously referenced alarm standards. It does not define a data model for alarm reporting. It defines common equipment management function requirements including alarm instrumentation. The scope is transport networks.

G.7710は、これまでに参照したアラーム標準とは異なります。 アラーム報告のためのデータモデルを定義していません。 アラームの計装を含む、機器に共通する管理機能の要件を定義しています。 対象範囲はトランスポートネットワークです。

The requirements in G.7710 correspond to features in the alarm YANG module in the following way:

G.7710の要件は、アラームYANGモジュールの機能に次のように対応します。

  • Alarm Severity Assignment Profile (ASAP): the alarm profile "/alarms/alarm-profile/".
  • Alarm Reporting Control (ARC): alarm shelving "/alarms/control/alarm-shelving/" and the ability to control alarm notifications "/alarms/control/notify-status-changes". Alarm shelving corresponds to the use case of turning off alarm reporting for a specific resource, which is the NALM (No ALarM) state in M.3100.
  • アラーム重大度割り当てプロファイル（ASAP）：アラームプロファイル「/alarms/alarm-profile/」です。
  • アラーム報告制御（ARC）：アラームの棚上げ「/alarms/control/alarm-shelving/」と、アラーム通知を制御する機能「/alarms/control/notify-status-changes」です。 アラームの棚上げは、特定のリソースについてアラーム報告をオフにするユースケースに相当し、これはM.3100のNALM（No ALarM）状態です。

アラームは生成されますが、運用者に無視されます。 「迷惑」アラーム（チャタリングアラームや一過性のアラーム）、故障したハードウェア、冗長なアラーム、連鎖的なアラーム、誤ったアラーム設定、合理化されていないアラームです。アラームが真のアラームではなくログ情報を表しています。 是正のための対応を必要とするという、アラームの厳密な定義です。Table 3のアラームの要件を参照してください。
アラームが発生しても、運用者がどう対応すればよいかわかりません。 不十分なアラーム対応手順と、明確に定義されていないアラームタイプです。 アラームインベントリーに、すべてのアラームタイプと是正措置が列挙されています。Table 3のアラームの要件を参照してください。
何も問題がないときでも、アラーム画面がアラームでいっぱいになっています。 迷惑アラーム、古くなったアラーム、稼働していない機器からのアラームです。 アラームの定義とアラームの棚上げです。
障害発生時に、運用者が大量のアラームにさらされ、どれが最も重要かわかりません。 アラームの誤った優先順位付けです。高度なアラーム技法（たとえば、状態ベースのアラーム）を使用していないことです。 状態ベースのアラームモデルとアラームレートの要件です。それぞれ表4と表5を参照してください。

Vendors SHOULD make sure that the following rules are used in designing the alarm interface:

ベンダーは、アラームインターフェイスの設計において次の規則が使用されるようにするべきです（SHOULD）。

  1. Rationalize the alarms in the system to ensure that every alarm is necessary, has a purpose, and follows the cardinal rule that it requires an operator response. Adheres to the rules of Table 3.
  2. Audit the quality of the alarms. Talk with the operators about how well the alarm information supports them. Do they know what to do in the event of an alarm? Are they able to quickly diagnose the problem and determine the corrective action? Does the alarm text adhere to the requirements in Table 3?
  3. Analyze and benchmark the performance of the system and compare it to the recommended metrics in Tables 4 and 5. Start by identifying nuisance alarms, as well as standing alarms at normal state and startup.
  1. システム内のアラームを合理化して、すべてのアラームが必要であり、目的を持ち、運用者による対応を必要とするという基本原則に従うようにします。 Table 3の規則に従います。
  2. アラームの品質を監査します。 アラーム情報が運用者をどの程度うまく支援しているかについて、運用者と話し合います。 運用者はアラーム発生時に何をすべきかわかっているでしょうか。 問題をすばやく診断し、是正措置を決定できるでしょうか。 アラームのテキストはTable 3の要件に従っているでしょうか。
  3. システムの性能を分析およびベンチマークし、表4と表5の推奨メトリックと比較します。 まず、迷惑アラームと、正常状態および起動時の常駐アラームを特定することから始めます。
