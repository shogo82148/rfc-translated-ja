RFC 9613

Requirements for Solutions that Support MPLS Network Actions (MNAs)

RFC 9613

MPLSネットワークアクション（MNA）をサポートするソリューションの要件

Abstract

概要

This document specifies requirements for the development of MPLS Network Actions (MNAs) that affect the forwarding or other processing of MPLS packets. These requirements are informed by a number of proposals for additions to the MPLS information in the labeled packet to allow such actions to be performed, either by a transit or terminating Label Switching Router (i.e., the Label Edge Router - LER).

この文書は、MPLSパケットの転送やそのほかの処理に影響を与えるMPLSネットワークアクション（MPLS Network Action、MNA）を開発するための要件を規定します。 これらの要件は、中継ラベルスイッチングルーター（Label Switching Router）または終端ラベルスイッチングルーター（つまり、ラベルエッジルーター（Label Edge Router、LER））がそのようなアクションを実行できるように、ラベル付きパケット内のMPLS情報に追加を行う多くの提案を踏まえたものです。

1. Introduction

1. はじめに

There is significant interest in developing the MPLS data plane to address the requirements of new use cases [MNA-USECASES]. This requires a general mechanism, termed MPLS Network Actions (MNAs), to allow the network to make a forwarding or processing decision based on information other than the top label and Traffic Class (TC) bits, and to also make use of the Network Action Indicator (NAI) and ancillary data (MNA information). These use cases require the definition of extensions to the MPLS architecture and label-stack operations that can be used across these use cases in order to minimize implementation complexity and promote interoperability and extensibility. These protocol extensions need to conform to the existing MPLS architecture as specified by [RFC3031], [RFC3032], and [RFC6790].

新しいユースケース[MNA-USECASES]の要件に対処するためにMPLSデータプレーンを発展させることに、大きな関心が寄せられています。 そのためには、最上位のラベルとトラフィッククラス（Traffic Class、TC）ビット以外の情報に基づいてネットワークが転送や処理の判断を行えるようにし、さらにネットワークアクション指示子（Network Action Indicator、NAI）と付随データ（MNA情報）も利用できるようにする、MPLSネットワークアクション（MPLS Network Action、MNA）と呼ばれる汎用的な仕組みが必要です。 これらのユースケースでは、実装の複雑さを最小限に抑え、相互運用性と拡張性を促進するために、これらのユースケース全体で使用できるMPLSアーキテクチャーとラベルスタック操作の拡張を定義する必要があります。 これらのプロトコル拡張は、[RFC3031]、[RFC3032]、[RFC6790]で規定されている既存のMPLSアーキテクチャーに準拠する必要があります。

Note that the MPLS architecture specified in [RFC3031] describes a mechanism for forwarding MPLS packets through a network without requiring any analysis of the MPLS packet payload's network layer header by intermediate nodes (Label Switching Routers - LSRs). Formally, inspection may only occur at network ingress (the Label Edge Router - LER) where the MPLS packet is assigned to a Forwarding Equivalence Class (FEC).

[RFC3031]で規定されているMPLSアーキテクチャーは、中間ノード（ラベルスイッチングルーター（Label Switching Router、LSR））がMPLSパケットのペイロードのネットワーク層ヘッダーを解析することなく、ネットワークを通じてMPLSパケットを転送する仕組みを記述していることに注意してください。 形式的には、検査が行われてよいのは、MPLSパケットが転送等価クラス（Forwarding Equivalence Class、FEC）に割り当てられるネットワークの入口（ラベルエッジルーター（Label Edge Router、LER））だけです。

This document specifies the requirements for solutions that encode MNAs and ancillary data that may be needed to process those actions. These requirements are informed by a number of proposals to allow additions to the MPLS information in the labeled packet so that such actions can be performed, either by a transit or terminating LSR. It is anticipated that these will result in two types of solution specifications:

この文書は、MNAと、それらのアクションを処理するために必要となる可能性のある付随データをエンコードするソリューションの要件を規定します。 これらの要件は、中継LSRまたは終端LSRがそのようなアクションを実行できるように、ラベル付きパケット内のMPLS情報への追加を可能にする多くの提案を踏まえたものです。 その結果、次の2種類のソリューション仕様が作られると予想されます。

MNA solution specification:
A specification that describes a common protocol that supports all forms of MNAs.
Network Action solution specifications:
One or more specifications describing the protocol extensions for the MNA solution to address a use case.
MNAソリューション仕様（MNA solution specification）：
あらゆる形態のMNAをサポートする共通プロトコルを記述する仕様。
ネットワークアクションソリューション仕様（Network Action solution specifications）：
ユースケースに対処するための、MNAソリューションに対するプロトコル拡張を記述する1つ以上の仕様。

The term 'solutions', in isolation, refers to both MNA and Network Action solutions. The requirements constrain the MNA solution design to enable interoperability between implementations.

単独で「ソリューション」という用語を使った場合は、MNAソリューションとネットワークアクションソリューションの両方を指します。 これらの要件は、実装間の相互運用性を実現するために、MNAソリューションの設計を制約します。

1.1. Terminology

1.1. 用語

Network Action (NA):
An operation to be performed on an MPLS packet or as a consequence of an MPLS packet being processed by a router. An NA may affect router state or MPLS packet forwarding, or it may affect the MPLS packet in some other way.
Network Action Indicator (NAI):
An indication in the MPLS packet that a certain NA is to be performed.
Ancillary Data (AD):

Data in an MPLS packet associated with a given NA that may be used as input to process the NA or may result from processing the NA. Ancillary data may be associated with:

  • Both the control or maintenance information and the data traffic carried by the Label Switched Path (LSP).

  • Only the control or maintenance information.

  • Only the data traffic carried by the LSP.

In-Stack Data:
Ancillary data carried within the MPLS label stack.
Post-Stack Data:
Ancillary data carried in an MPLS packet between the bottom of the MPLS label stack and the first octet of the user payload. This document does not prescribe whether post-stack data precedes or follows any other post-stack header such as a Control Word or Associated Channel Header (ACH).
Scope:
The set of nodes that should perform a given action.
ネットワークアクション（Network Action、NA）：
MPLSパケットに対して実行される操作、またはMPLSパケットがルーターによって処理された結果として実行される操作。 NAは、ルーターの状態やMPLSパケットの転送に影響を与える場合もあれば、そのほかの方法でMPLSパケットに影響を与える場合もあります。
ネットワークアクション指示子（Network Action Indicator、NAI）：
特定のNAを実行すべきことを示す、MPLSパケット内の表示。
付随データ（Ancillary Data、AD）：

MPLSパケット内のデータで、特定のNAに関連付けられており、そのNAを処理するための入力として使われるか、そのNAを処理した結果として生じるもの。 付随データは、次のいずれかに関連付けられる場合があります。

  • 制御情報または保守情報と、ラベルスイッチドパス（Label Switched Path、LSP）で運ばれるデータトラフィックの両方。

  • 制御情報または保守情報のみ。

  • LSPで運ばれるデータトラフィックのみ。

スタック内データ（In-Stack Data）：
MPLSラベルスタック内で運ばれる付随データ。
スタック後データ（Post-Stack Data）：
MPLSパケット内で、MPLSラベルスタックの底とユーザーペイロードの最初のオクテットの間で運ばれる付随データ。 この文書は、スタック後データが、コントロールワードや関連チャネルヘッダー（Associated Channel Header、ACH）などのほかのポストスタックヘッダーの前に来るか後ろに来るかを規定しません。
スコープ（Scope）：
特定のアクションを実行すべきノードの集合。

2. Requirements Language

2. 要件言語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

Although this document is not a protocol specification, this convention is adopted for clarity of description of requirements.

この文書はプロトコル仕様ではありませんが、要件の記述を明確にするためにこの規則を採用しています。

3. MPLS Network Action Requirements

3. MPLSネットワークアクションの要件

This document specifies requirements on MNAs and the technology to support them in MPLS, such as NAIs, the associated AD, and the alert mechanism to indicate to an LSR that NAIs are present in an MPLS packet.

この文書は、MNAと、それをMPLSでサポートするための技術（NAI、関連するAD、MPLSパケットにNAIが存在することをLSRに示すアラートメカニズムなど）に対する要件を規定します。

The requirements are for the behavior of the protocol mechanisms and procedures that constitute building blocks out of which indicators for a NA and associated ancillary data are constructed. It does not specify the detailed actions and processing of any NAs or ancillary data by an LSR or LER.

これらの要件は、NAの指示子とそれに関連する付随データを構成するための構成要素となる、プロトコルの仕組みと手順の振る舞いに対するものです。 LSRやLERによるNAや付随データの詳細なアクションや処理は規定しません。

The size of the ancillary data carried post-stack end to end in an MPLS packet is a matter for agreement between the ingress and egress provider edges (PEs), and is not part of these requirements. Since in-stack ancillary data and per-hop post-stack data need to be parsed and processed by transit LSRs along the Label Switched Path (LSP), requirements on the size of such ancillary data are documented in the following sections.

MPLSパケット内でスタック後にエンドツーエンドで運ばれる付随データのサイズは、入口と出口のプロバイダーエッジ（PE）の間で合意すべき事項であり、これらの要件には含まれません。 スタック内の付随データとホップごとのスタック後データは、ラベルスイッチドパス（LSP）に沿った中継LSRで解析され処理される必要があるため、そのような付随データのサイズに関する要件は、以降のセクションで記述します。

3.1. General Requirements

3.1. 一般的な要件

  1. Any solutions MUST maintain the properties of extensibility, flexibility, and efficiency inherent in the split between the control plane context and simple data plane used in MPLS and the specification SHOULD describe how this is achieved.

  2. Any solutions to these requirements MUST be based on and MUST NOT restrict the generality of the MPLS architecture [RFC3031] [RFC3032] [RFC5331].

  3. If extensions to the MPLS data plane are required, they MUST be consistent with the MPLS architecture [RFC3031] [RFC3032] [RFC5331].

  4. Solutions meeting the requirements set out in this document MUST be able to coexist with existing MPLS mechanisms.

  5. Subject to the constraints in these requirements, a Network Action solution MAY carry MNA information in-stack, post-stack, or both in-stack and post-stack.

  6. Solution specifications MUST NOT require an implementation to support in-stack ancillary data, unless the implementation chooses to support an NA that uses in-stack ancillary data.

  7. Solution specifications MUST NOT require an implementation to support post-stack ancillary data, unless the implementation chooses to support an NA that uses post-stack ancillary data.

  8. The design of any MNA solution MUST minimize the amount of processing required to parse the label stack at an LSR.

  9. Solutions MUST minimize any additions to the size of the MPLS label stack.

  10. Solution specifications that increase the size of the MPLS label stack in a way that is not controlled by the ingress LER MUST discuss the consequences.

  11. Solution specifications MUST discuss the ECMP consequences of the design.

  12. A Network Action solution MUST NOT expose information to the LSRs that is not already exposed to the LER.

  13. The design of any NA MUST NOT expose any information that a user of any service using the LSP considers confidential [RFC6973] [RFC3552].

  14. Solution specifications MUST document any new security considerations that they introduce.

  15. An MNA solution MUST allow MPLS packets carrying NAI and ancillary data (where it exists) to coexist with MPLS packets that do not carry this information on the same LSP.

  1. いかなるソリューションも、MPLSで使われている制御プレーンのコンテキストと単純なデータプレーンとの分離に本来備わっている、拡張性、柔軟性、効率性という特性を維持しなければなりません（MUST）。 また、仕様はこれをどのように実現するかを記述すべきです（SHOULD）。

  2. これらの要件に対するいかなるソリューションも、MPLSアーキテクチャー[RFC3031] [RFC3032] [RFC5331]に基づいていなければなりません（MUST）。 また、その汎用性を制限してはなりません（MUST NOT）。

  3. MPLSデータプレーンの拡張が必要な場合、その拡張はMPLSアーキテクチャー[RFC3031] [RFC3032] [RFC5331]と一貫していなければなりません（MUST）。

  4. この文書で示す要件を満たすソリューションは、既存のMPLSの仕組みと共存できなければなりません（MUST）。

  5. これらの要件の制約の範囲内で、ネットワークアクションソリューションは、MNA情報をスタック内、スタック後、またはスタック内とスタック後の両方で運んでもよいです（MAY）。

  6. ソリューション仕様は、実装がスタック内の付随データを使うNAをサポートすることを選択しない限り、スタック内の付随データのサポートを実装に要求してはなりません（MUST NOT）。

  7. ソリューション仕様は、実装がスタック後の付随データを使うNAをサポートすることを選択しない限り、スタック後の付随データのサポートを実装に要求してはなりません（MUST NOT）。

  8. いかなるMNAソリューションの設計も、LSRでラベルスタックを解析するために必要な処理量を最小限にしなければなりません（MUST）。

  9. ソリューションは、MPLSラベルスタックのサイズの増加を最小限にしなければなりません（MUST）。

  10. 入口LERが制御しない方法でMPLSラベルスタックのサイズを増加させるソリューション仕様は、その影響について議論しなければなりません（MUST）。

  11. ソリューション仕様は、その設計がECMPに与える影響について議論しなければなりません（MUST）。

  12. ネットワークアクションソリューションは、LERにまだ公開されていない情報をLSRに公開してはなりません（MUST NOT）。

  13. いかなるNAの設計も、そのLSPを使うサービスのユーザーが機密とみなす情報を公開してはなりません（MUST NOT）[RFC6973] [RFC3552]。

  14. ソリューション仕様は、それがもたらす新たなセキュリティーに関する考慮事項をすべて文書化しなければなりません（MUST）。

  15. MNAソリューションは、NAIと（存在する場合は）付随データを運ぶMPLSパケットが、それらの情報を運ばないMPLSパケットと同じLSP上で共存できるようにしなければなりません（MUST）。

3.2. Requirements on the MNA Alert Mechanism

3.2. MNAアラートメカニズムに対する要件

  1. An MNA solution specification MUST define how a node determines whether NAIs are present in the MPLS packet.

  2. Special Purpose Labels (SPLs) are a mechanism of last resort; therefore, an MNA solution specification that defines their use MUST minimize the number of new SPLs that are allocated.

  1. MNAソリューション仕様は、MPLSパケットにNAIが存在するかどうかをノードがどのように判断するかを定義しなければなりません（MUST）。

  2. 特殊用途ラベル（Special Purpose Label、SPL）は最後の手段となる仕組みです。 したがって、SPLの使用を定義するMNAソリューション仕様は、割り当てる新しいSPLの数を最小限にしなければなりません（MUST）。

3.3. Requirements on Network Actions

3.3. ネットワークアクションに対する要件

  1. It is RECOMMENDED that an MNA solution include support for NAs for Private Use (see Section 4.1 of [RFC8126]).

  2. Network Action solution specifications MUST define if the NA needs to be processed as a part of the immediate forwarding operation and whether MPLS packet misordering is allowed to occur as a result of the time taken to process the NA.

  3. If a Network Action solution specification allows more than one scope for an NA, it MUST define a mechanism to indicate the precedence of the scopes or any combination of the scopes.

  4. If a network action requires an NAI with in-stack ancillary data that needs to be imposed at an LSR on an LSP, then the Network Action solution MUST specify how this is achieved in all circumstances.

  5. If a network action requires an NAI with post-stack ancillary data to be imposed at an LSR on an LSP, then the Network Action solution specification MUST describe how this is achieved in all circumstances.

  1. MNAソリューションには、プライベート使用（Private Use）のためのNAのサポートを含めることが推奨されます（RECOMMENDED）（[RFC8126]のSection 4.1を参照）。

  2. ネットワークアクションソリューション仕様は、NAを即時の転送操作の一部として処理する必要があるかどうか、および、NAの処理にかかる時間の結果としてMPLSパケットの順序の入れ替わりが起きてよいかどうかを定義しなければなりません（MUST）。

  3. ネットワークアクションソリューション仕様がNAに対して複数のスコープを許可する場合、その仕様は、スコープ間またはスコープの任意の組み合わせ間の優先順位を示す仕組みを定義しなければなりません（MUST）。

  4. あるネットワークアクションが、LSP上のLSRで付与する必要があるスタック内の付随データを伴うNAIを必要とする場合、ネットワークアクションソリューションは、あらゆる状況でこれをどのように実現するかを規定しなければなりません（MUST）。

  5. あるネットワークアクションが、LSP上のLSRで付与されるスタック後の付随データを伴うNAIを必要とする場合、ネットワークアクションソリューション仕様は、あらゆる状況でこれをどのように実現するかを記述しなければなりません（MUST）。

3.4. Requirements on Network Action Indicators

3.4. ネットワークアクション指示子に対する要件

  1. Insertion, parsing, processing, and disposition of NAIs SHOULD make use of existing MPLS data plane operations.

  2. Without constraining the mechanism, an MNA solution MUST enable a node inserting or modifying NAIs to determine if the target of the NAI, or any other LSR that may expose the NAI, can accept and process an MPLS packet containing the NAI.

  3. An NAI MUST NOT be imposed for delivery to a node unless it is known that the node supports processing the NAI.

  4. The NAI design MUST support setting the scope of network actions.

  5. A given Network Action solution specification MUST define which scope or scopes are applicable to the associated NAI.

  6. An MNA solution specification SHOULD define the support of NAIs for both Point-to-Point (P2P) and Point-to-Multipoint (P2MP) paths, but the Network Action solution specification MAY limit a specific NAI to only one of these path types if there is a clear reason to do so.

  7. An MNA solution specification defining data plane mechanisms for NAIs MUST be consistent across different control plane protocols.

  8. An MNA solution MUST allow the deployed MPLS control and management planes to determine the ability of downstream LSRs to accept and/or process a given NAI.

  9. An MNA solution MUST allow indicators for multiple network actions in the same MPLS packet.

  10. An MNA solution specification MUST NOT require an implementation to process all NAIs present in an MPLS packet.

  11. NAIs MUST only be inserted at LSRs that push a label onto the stack, but they can be processed by LSRs along the path of the LSP. Two examples of LSRs that push a label onto the stack are head-end LSRs and points of local repair (PLRs).

  12. If a network action requires in-stack ancillary data, the NAI that indicates this network action MUST be present in the label stack.

  13. All NAIs MUST be encoded in a manner consistent with [RFC3031].

  14. If there is post-stack ancillary data for an NAI that is present in the label stack, it MUST be possible to infer the presence of the ancillary data without having to parse below the bottom of the label stack.

  15. Any processing that removes an NAI from the label stack MUST also remove all associated ancillary data from the MPLS packet unless the ancillary data is required by any remaining NAIs.

  16. MNA solution specifications MUST request that IANA create registries and make allocations from those registries for NAIs as necessary to ensure unambiguous identification of standardized network actions. An MNA solution specification MAY request that IANA reserve a range of a registry for Private Use.

  17. A Network Action solution specification MUST state where the NAIs are to be placed in the MPLS packet, that is whether they are placed in-stack or post-stack.

  1. NAIの挿入、解析、処理、処分には、既存のMPLSデータプレーンの操作を利用すべきです（SHOULD）。

  2. MNAソリューションは、その仕組みを制約することなく、NAIを挿入または変更するノードが、NAIの対象、またはNAIを露出させる可能性のあるほかのLSRが、そのNAIを含むMPLSパケットを受け入れて処理できるかどうかを判断できるようにしなければなりません（MUST）。

  3. ノードがNAIの処理をサポートしていることがわかっている場合を除き、そのノードへの配送のためにNAIを付与してはなりません（MUST NOT）。

  4. NAIの設計は、ネットワークアクションのスコープの設定をサポートしなければなりません（MUST）。

  5. 個々のネットワークアクションソリューション仕様は、関連するNAIにどのスコープが適用できるかを定義しなければなりません（MUST）。

  6. MNAソリューション仕様は、ポイントツーポイント（Point-to-Point、P2P）パスとポイントツーマルチポイント（Point-to-Multipoint、P2MP）パスの両方について、NAIのサポートを定義すべきです（SHOULD）。 ただし、明確な理由がある場合、ネットワークアクションソリューション仕様は、特定のNAIをこれらのパス種別の一方だけに制限してもよいです（MAY）。

  7. NAIのためのデータプレーンの仕組みを定義するMNAソリューション仕様は、異なる制御プレーンプロトコル間で一貫していなければなりません（MUST）。

  8. MNAソリューションは、展開されているMPLSの制御プレーンと管理プレーンが、下流のLSRが特定のNAIを受け入れられるかどうか、または処理できるかどうか（あるいはその両方）を判断できるようにしなければなりません（MUST）。

  9. MNAソリューションは、同じMPLSパケット内に複数のネットワークアクションの指示子を含められるようにしなければなりません（MUST）。

  10. MNAソリューション仕様は、MPLSパケット内に存在するすべてのNAIを処理することを実装に要求してはなりません（MUST NOT）。

  11. NAIは、スタックにラベルをプッシュするLSRでのみ挿入しなければなりません（MUST）。 ただし、NAIはLSPのパスに沿ったLSRで処理することができます。 スタックにラベルをプッシュするLSRの例としては、ヘッドエンドLSRとローカル修復ポイント（Point of Local Repair、PLR）の2つがあります。

  12. あるネットワークアクションがスタック内の付随データを必要とする場合、そのネットワークアクションを示すNAIはラベルスタック内に存在しなければなりません（MUST）。

  13. すべてのNAIは、[RFC3031]と一貫した方法でエンコードしなければなりません（MUST）。

  14. ラベルスタック内に存在するNAIに対してスタック後の付随データがある場合、ラベルスタックの底より下を解析しなくても、その付随データの存在を推測できるようにしなければなりません（MUST）。

  15. ラベルスタックからNAIを取り除く処理は、残っているNAIのいずれかが付随データを必要としない限り、関連するすべての付随データもMPLSパケットから取り除かなければなりません（MUST）。

  16. MNAソリューション仕様は、標準化されたネットワークアクションを曖昧さなく識別できるように、必要に応じて、IANAにレジストリーの作成と、そのレジストリーからのNAIの割り当てを依頼しなければなりません（MUST）。 MNAソリューション仕様は、レジストリーの一部の範囲をプライベート使用のために予約するようIANAに依頼してもよいです（MAY）。

  17. ネットワークアクションソリューション仕様は、MPLSパケット内のどこにNAIを配置するか、つまりスタック内に配置するのかスタック後に配置するのかを明記しなければなりません（MUST）。

3.5. Requirements on Ancillary Data

3.5. 付随データに対する要件

  1. Network Action solution specifications MUST state whether ancillary data is required to fulfill the action and whether it is in-stack and/or post-stack.

  2. Network Action solution specifications MUST state if in-stack or post-stack ancillary data that is already present in the MPLS packet MAY be rewritten by an LSR.

  3. Solutions for in-stack ancillary data MUST be able to coexist with and MUST NOT obsolete existing MPLS mechanisms. Such solutions MUST be described in a Standards Track RFC.

  4. Network Action solutions MUST take care to limit the quantity of in-stack ancillary data to the minimum amount required.

  5. A Network Action solution SHOULD NOT use post-stack ancillary data unless the size of that ancillary data could prevent the coexistence of the network action with other in-use MPLS network functions if it were inserted into the label stack.

  6. The structure of the NAI and any associated ancillary data MUST enable skipping of unknown NAIs and any associated AD.

  7. Any MNA solution specification MUST describe whether the solution can coexist with existing post-stack data mechanisms (e.g., control words and the Generic Associated Channel Header [RFC5586]), and if so how coexistence operates.

  8. An MNA solution MUST allow an LER that inserts ancillary data to determine whether each node that needs to process the ancillary data can read the required distance into the MPLS packet at that node (compare with the mechanism in [RFC9088]).

  9. For scoped in-stack or post-stack ancillary data, any MNA solution MUST allow an LER inserting NAIs whose network actions make use of that ancillary data to determine if the NAI and ancillary data will be processed by LSRs within the scope along the path. Such a solution may need to determine if LSRs along the path can process a specific type of AD implied by the NAI at the depth in the stack that it will be presented to the LSR.

  10. A mechanism MUST exist to notify an egress LER of the presence of ancillary data so that it can dispose of it appropriately.

  11. In-stack ancillary data MUST only be inserted in conjunction with an operation conforming with [RFC3031].

  12. Post-stack ancillary data MUST only be inserted in conjunction with an operation conforming with [RFC3031].

  13. Processing of ancillary data below a swapped label MAY include rewriting the ancillary data.

  14. If a Network Action solution needs to change the size of the ancillary data, its specification MUST analyze the implications on MPLS packet forwarding and specify how these are addressed.

  15. Not more than one Standards Track solution specification SHOULD be defined for encoding in-stack ancillary data.

  16. Not more than one Standards Track solution specification SHOULD be defined for encoding post-stack ancillary data.

  1. ネットワークアクションソリューション仕様は、アクションを遂行するために付随データが必要かどうか、および、それがスタック内とスタック後のどちらにあるのか（あるいは両方にあるのか）を明記しなければなりません（MUST）。

  2. ネットワークアクションソリューション仕様は、MPLSパケット内にすでに存在するスタック内またはスタック後の付随データを、LSRが書き換えてもよいです（MAY）かどうかを明記しなければなりません（MUST）。

  3. スタック内の付随データのためのソリューションは、既存のMPLSの仕組みと共存できなければなりません（MUST）。 また、既存のMPLSの仕組みを廃止してはなりません（MUST NOT）。 そのようなソリューションは、標準化過程のRFCで記述しなければなりません（MUST）。

  4. ネットワークアクションソリューションは、スタック内の付随データの量を必要最小限に抑えるよう注意しなければなりません（MUST）。

  5. ネットワークアクションソリューションは、付随データをラベルスタックに挿入するとそのサイズのために、ほかの使用中のMPLSネットワーク機能とそのネットワークアクションとの共存が妨げられるおそれがある場合を除いて、スタック後の付随データを使用すべきではありません（SHOULD NOT）。

  6. NAIとそれに関連する付随データの構造は、未知のNAIとそれに関連するADを読み飛ばせるようにしなければなりません（MUST）。

  7. いかなるMNAソリューション仕様も、そのソリューションが既存のスタック後データの仕組み（たとえば、コントロールワードや汎用関連チャネルヘッダー[RFC5586]）と共存できるかどうか、また共存できる場合はどのように共存するのかを記述しなければなりません（MUST）。

  8. MNAソリューションは、付随データを挿入するLERが、その付随データを処理する必要のある各ノードが、そのノードにおいてMPLSパケット内の必要な深さまで読み取れるかどうかを判断できるようにしなければなりません（MUST）（[RFC9088]の仕組みと比較してください）。

  9. スコープを持つスタック内またはスタック後の付随データについて、いかなるMNAソリューションも、その付随データを利用するネットワークアクションのNAIを挿入するLERが、パスに沿ったスコープ内のLSRによってNAIと付随データが処理されるかどうかを判断できるようにしなければなりません（MUST）。 そのようなソリューションでは、パスに沿ったLSRが、NAIによって暗示される特定の種類のADを、それがLSRに提示されるスタック内の深さで処理できるかどうかを判断する必要がある場合があります。

  10. 出口LERが付随データを適切に処分できるように、付随データの存在を出口LERに通知する仕組みが存在しなければなりません（MUST）。

  11. スタック内の付随データは、[RFC3031]に準拠した操作と併せてのみ挿入しなければなりません（MUST）。

  12. スタック後の付随データは、[RFC3031]に準拠した操作と併せてのみ挿入しなければなりません（MUST）。

  13. スワップされたラベルの下にある付随データの処理には、付随データの書き換えを含めてもよいです（MAY）。

  14. ネットワークアクションソリューションが付随データのサイズを変更する必要がある場合、その仕様は、MPLSパケットの転送への影響を分析し、それにどのように対処するかを規定しなければなりません（MUST）。

  15. スタック内の付随データをエンコードするための標準化過程のソリューション仕様は、多くとも1つだけ定義すべきです（SHOULD）。

  16. スタック後の付随データをエンコードするための標準化過程のソリューション仕様は、多くとも1つだけ定義すべきです（SHOULD）。

5. Security Considerations

5. セキュリティーに関する考慮事項

Solutions designed according to the requirements in this document may introduce new security considerations to MPLS, whose forwarding plane on its own does not provide any built-in security mechanisms [RFC5920].

この文書の要件に従って設計されたソリューションは、MPLSに新たなセキュリティーに関する考慮事項をもたらす可能性があります。 MPLSの転送プレーンは、それ自体では組み込みのセキュリティーの仕組みを何も提供しません[RFC5920]。

In particular, such solutions may embed information derived from the MPLS payload in the MPLS headers. This may expose data that a user of the MPLS-based service might otherwise assume is opaque to the MPLS network. Furthermore, an LSR may insert information into the labeled packet such that the forwarding behavior is no longer purely a function of the top label or another label with forwarding context. Instead, the forwarding behavior may be the result of a more complex heuristic. This creates an implicit trust relationship between the LSR whose forwarding behavior is being changed and the upstream LSR inserting the data causing that change.

特に、そのようなソリューションは、MPLSペイロードから得られた情報をMPLSヘッダーに埋め込む場合があります。 これにより、MPLSベースのサービスのユーザーが本来であればMPLSネットワークにとって不透明であると想定しているデータが露出する可能性があります。 さらに、LSRがラベル付きパケットに情報を挿入することで、転送の振る舞いが、もはや最上位のラベル、または転送コンテキストを持つ別のラベルだけで決まるものではなくなる可能性があります。 代わりに、転送の振る舞いは、より複雑なヒューリスティックの結果となる場合があります。 これにより、転送の振る舞いが変更されるLSRと、その変更を引き起こすデータを挿入する上流のLSRとの間に、暗黙の信頼関係が生まれます。

Several requirements above address some of these considerations. The MNA framework [MNA-FRAMEWORK] also provides security considerations resulting from any extensions to the MPLS architecture, and these SHOULD be taken together with the security considerations herein.

上記のいくつかの要件は、これらの考慮事項の一部に対処しています。 MNAフレームワーク[MNA-FRAMEWORK]も、MPLSアーキテクチャーに対するあらゆる拡張から生じるセキュリティーに関する考慮事項を示しており、それらはここでのセキュリティーに関する考慮事項と併せて考慮すべきです（SHOULD）。

Individual solution specifications meeting the requirements in this document MUST address any security considerations introduced by the MNA design.

この文書の要件を満たす個々のソリューション仕様は、MNAの設計によってもたらされるあらゆるセキュリティーに関する考慮事項に対処しなければなりません（MUST）。
