RFC 9802

Use of the HSS and XMSS Hash-Based Signature Algorithms in Internet X.509 Public Key Infrastructure

RFC 9802

インターネットX.509公開鍵基盤におけるHSSおよびXMSSハッシュベース署名アルゴリズムの使用

Abstract

概要

This document specifies algorithm identifiers and ASN.1 encoding formats for the following stateful Hash-Based Signature (HBS) schemes: Hierarchical Signature System (HSS), eXtended Merkle Signature Scheme (XMSS), and XMSSMT (a multi-tree variant of XMSS). This specification applies to the Internet X.509 Public Key Infrastructure (PKI) when digital signatures are used to sign certificates and certificate revocation lists (CRLs).

この文書は、次のステートフルハッシュベース署名（Hash-Based Signature: HBS）方式のためのアルゴリズム識別子とASN.1エンコード形式を規定します: 階層型署名システム（Hierarchical Signature System: HSS）、拡張マークル署名方式（eXtended Merkle Signature Scheme: XMSS）、およびXMSSMT（XMSSのマルチツリー版）。 この仕様は、証明書および証明書失効リスト（CRL）に署名するためにデジタル署名を使用する場合のインターネットX.509公開鍵基盤（PKI）に適用されます。

1. Introduction

1. はじめに

Stateful Hash-Based Signature (HBS) schemes such as the Hierarchical Signature System (HSS), eXtended Merkle Signature Scheme (XMSS), and XMSSMT combine Merkle trees with One-Time Signatures (OTS). This is done in order to provide digital signature schemes that remain secure even when quantum computers become available. Their theoretic security is well understood and depends only on the security of the underlying hash function. As such, they can serve as an important building block for quantum computer resistant information and communication technology.

階層型署名システム（HSS）、拡張マークル署名方式（XMSS）、XMSSMTなどのステートフルハッシュベース署名（HBS）方式は、マークル木とワンタイム署名（One-Time Signature: OTS）を組み合わせたものです。 これは、量子コンピューターが利用可能になっても安全であり続けるデジタル署名方式を提供するためです。 これらの理論的な安全性はよく理解されており、基盤となるハッシュ関数の安全性のみに依存します。 そのため、これらは量子コンピューター耐性のある情報通信技術のための重要な構成要素となりえます。

A stateful HBS private key consists of a finite collection of OTS keys, along with state information that tracks the usage of these keys to ensure the security of the scheme. Only a limited number of messages can be signed, and the private key's state must be updated and persisted after signing to prevent reuse of OTS keys. While the right selection of algorithm parameters would allow a private key to sign a virtually unbounded number of messages (e.g., 260), this is at the cost of a larger signature size and longer signing time. Because the private key in stateful HBS schemes is stateful and the number of signatures that can be generated is limited, these schemes may be unsuitable for use in interactive protocols. However, in some use cases, the deployment of stateful HBS schemes may be appropriate. Such use cases are described and discussed in Section 3.

ステートフルHBSの秘密鍵は、有限個のOTS鍵の集まりと、方式の安全性を確保するためにこれらの鍵の使用状況を追跡する状態情報から構成されます。 署名できるメッセージの数は限られており、OTS鍵の再利用を防ぐために、署名後に秘密鍵の状態を更新して永続化する必要があります。 アルゴリズムパラメーターを適切に選択すれば、1つの秘密鍵で事実上無制限の数のメッセージ（たとえば260）に署名できるようになりますが、その代償として署名サイズが大きくなり、署名時間が長くなります。 ステートフルHBS方式の秘密鍵は状態を持ち、生成できる署名の数が限られているため、これらの方式は対話型プロトコルでの使用には適さない場合があります。 しかし、ユースケースによっては、ステートフルHBS方式の導入が適切な場合もあります。 そのようなユースケースについてはSection 3で説明し、議論します。

3. Use Cases of Stateful HBS Schemes in X.509

3. X.509におけるステートフルHBS方式のユースケース

As described in the Security Considerations in Section 10, it is imperative that stateful HBS implementations do not reuse OTS signatures. This makes stateful HBS algorithms inappropriate for general use cases. The exact conditions under which stateful HBS certificates may be used is left to certificate policies [RFC3647]. However, the intended use of stateful HBS schemes as described by [SP800208] can be used as a guideline:

Section 10のセキュリティーに関する考慮事項で説明しているように、ステートフルHBSの実装がOTS署名を再利用しないことが不可欠です。 このため、ステートフルHBSアルゴリズムは一般的なユースケースには適しません。 ステートフルHBS証明書を使用してよい厳密な条件は、証明書ポリシー [RFC3647] に委ねられます。 しかし、[SP800208]で説明されているステートフルHBS方式の想定用途を指針として用いることができます:

stateful HBS schemes are primarily intended for applications with the following characteristics: 1) it is necessary to implement a digital signature scheme in the near future; 2) the implementation will have a long lifetime; and 3) it would not be practical to transition to a different digital signature scheme once the implementation has been deployed.
ステートフルHBS方式は、主に次の特徴を持つアプリケーションを対象としています: 1) 近い将来にデジタル署名方式を実装する必要がある、2) 実装の寿命が長い、3) 実装を導入した後に別のデジタル署名方式へ移行することが現実的でない。

In addition, since a stateful HBS private key can only generate a finite number of signatures, use cases for stateful HBS public keys in certificates should have a predictable range of the number of signatures that will be generated, falling safely below the maximum number of signatures that a private key can generate.

さらに、ステートフルHBSの秘密鍵は有限個の署名しか生成できないため、証明書にステートフルHBS公開鍵を使用するユースケースでは、生成される署名の数が予測可能な範囲にあり、秘密鍵が生成できる署名の最大数を十分に下回っているべきです。

Use cases where stateful HBS public keys in certificates may be appropriate due to the relatively small number of signatures generated and the signer's ability to enforce security restrictions on the signing environment include:

生成される署名の数が比較的少なく、署名者が署名環境にセキュリティー上の制限を課すことができるため、証明書にステートフルHBS公開鍵を使用することが適切となりうるユースケースには、次のものがあります:

  • Firmware signing (see Section 1.1 of [SP800208], [CNSA2.0], and Section 6.7 of [BSI])

  • Software signing ([CNSA2.0] and [ANSSI])

  • Certification Authority (CA) certificates

  • ファームウェアの署名（[SP800208]のセクション1.1、[CNSA2.0]、および[BSI]のセクション6.7を参照）

  • ソフトウェアの署名（[CNSA2.0]および[ANSSI]）

  • 認証局（CA）証明書

In each of these cases, the operator tightly controls their secured signing environment and can mitigate OTS key reuse by employing state management strategies such as those in Section 10. Also, for secure private key backup and restoration, adequate mechanisms have to be implemented (see Section 11).

いずれの場合も、運用者は保護された署名環境を厳密に管理しており、Section 10にあるような状態管理戦略を採用することでOTS鍵の再利用を緩和できます。 また、秘密鍵の安全なバックアップとリストアのために、適切な仕組みを実装する必要があります（Section 11を参照）。

Generally speaking, stateful HBS public keys are not appropriate for use in end-entity certificates, however, in the firmware and software signing cases, signature generation will often be more tightly controlled. Some manufactures use common and well-established key formats like X.509 for their code signing and update mechanisms. Also, there are multi-party Internet of Things (IoT) ecosystems where publicly trusted code signing certificates are useful.

一般に、ステートフルHBS公開鍵はエンドエンティティー証明書での使用には適しませんが、ファームウェアやソフトウェアの署名の場合には、署名生成がより厳密に管理されていることが多くあります。 一部の製造業者は、コード署名や更新の仕組みにX.509のような一般的で確立された鍵形式を使用しています。 また、公的に信頼されたコード署名証明書が有用な、複数の当事者が関わるモノのインターネット（IoT）エコシステムも存在します。

In general, root CAs [RFC4949] generate signatures in a more secure environment and issue fewer certificates than subordinate CAs [RFC4949]. This makes the use of stateful HBS public keys more appropriate in root CA certificates than in subordinate CA certificates. However, if a subordinate CA can match the security and signature count restrictions of a root CA, for example, if the subordinate CA only issues code-signing certificates, then using a stateful HBS public key in the subordinate CA certificate may be practical.

一般に、ルートCA [RFC4949] は、下位CA [RFC4949] よりも安全な環境で署名を生成し、発行する証明書の数も少なくなります。 このため、ステートフルHBS公開鍵の使用は、下位CA証明書よりもルートCA証明書においてより適切です。 ただし、下位CAがルートCAのセキュリティーおよび署名数の制限に匹敵できる場合、たとえば下位CAがコード署名証明書のみを発行する場合には、下位CA証明書でステートフルHBS公開鍵を使用することが現実的な場合もあります。

4. Algorithm Identifiers and Parameters

4. アルゴリズム識別子とパラメーター

In this document, we define new Object Identifiers (OIDs) for identifying the different stateful hash-based signature algorithms. An additional OID is defined in [RFC9708] and repeated here for convenience.

この文書では、さまざまなステートフルハッシュベース署名アルゴリズムを識別するための新しいオブジェクト識別子（OID）を定義します。 追加のOIDが[RFC9708]で定義されており、便宜のためにここで再掲します。

The AlgorithmIdentifier type is defined in [RFC5912] as follows:

AlgorithmIdentifier型は、[RFC5912]で次のように定義されています:

AlgorithmIdentifier{ALGORITHM-TYPE, ALGORITHM-TYPE:AlgorithmSet} ::=
        SEQUENCE {
            algorithm   ALGORITHM-TYPE.&id({AlgorithmSet}),
            parameters  ALGORITHM-TYPE.
                   &Params({AlgorithmSet}{@algorithm}) OPTIONAL
        }

AlgorithmIdentifier{ALGORITHM-TYPE, ALGORITHM-TYPE:AlgorithmSet} ::=
        SEQUENCE {
            algorithm   ALGORITHM-TYPE.&id({AlgorithmSet}),
            parameters  ALGORITHM-TYPE.
                   &Params({AlgorithmSet}{@algorithm}) OPTIONAL
        }

NOTE: The above syntax is from [RFC5912] and is compatible with the 2021 ASN.1 syntax [X680]. See [RFC5280] for the 1988 ASN.1 syntax.

注記: 上記の構文は[RFC5912]のものであり、2021年版ASN.1構文 [X680] と互換性があります。 1988年版ASN.1構文については[RFC5280]を参照してください。

The fields in AlgorithmIdentifier have the following meanings:

AlgorithmIdentifierのフィールドは次の意味を持ちます:

algorithm:
this identifies the cryptographic algorithm with an OID.
parameters:
these are optional and are the associated parameters for the algorithm identifier in the algorithm field.
algorithm:
これはOIDによって暗号アルゴリズムを識別します。
parameters:
これらは省略可能であり、algorithmフィールドのアルゴリズム識別子に関連するパラメーターです。

The parameters field of the AlgorithmIdentifier for HSS, XMSS, and XMSSMT public keys MUST be absent.

HSS、XMSS、およびXMSSMT公開鍵のAlgorithmIdentifierのparametersフィールドは省略しなければなりません（MUST）。

4.1. HSS Algorithm Identifier

4.1. HSSアルゴリズム識別子

The OID and public key algorithm identifier for HSS is defined in [RFC9708]. The definitions are repeated here for reference.

HSSのOIDと公開鍵アルゴリズム識別子は[RFC9708]で定義されています。 参考のため、ここでその定義を再掲します。

The AlgorithmIdentifier for an HSS public key MUST use the id-alg-hss-lms-hashsig OID.

HSS公開鍵のAlgorithmIdentifierは、id-alg-hss-lms-hashsig OIDを使用しなければなりません（MUST）。

   id-alg-hss-lms-hashsig  OBJECT IDENTIFIER ::= {
      iso(1) member-body(2) us(840) rsadsi(113549) pkcs(1) pkcs9(9)
      smime(16) alg(3) 17 }

   id-alg-hss-lms-hashsig  OBJECT IDENTIFIER ::= {
      iso(1) member-body(2) us(840) rsadsi(113549) pkcs(1) pkcs9(9)
      smime(16) alg(3) 17 }

Note that the id-alg-hss-lms-hashsig algorithm identifier is also referred to as id-alg-mts-hashsig. This synonym is based on the terminology used in an early draft of the document that became [RFC8554].

id-alg-hss-lms-hashsigアルゴリズム識別子は、id-alg-mts-hashsigとも呼ばれることに注意してください。 この別名は、[RFC8554]となった文書の初期のドラフトで使われていた用語に基づいています。

The public key and signature values identify the hash function and the height used in the HSS tree. [RFC8554] and [SP800208] define these values, and additional identifiers can be registered in the "Leighton-Micali Signatures (LMS)" registry [IANA-LMS].

公開鍵と署名の値は、HSSツリーで使用されるハッシュ関数と高さを識別します。 [RFC8554]と[SP800208]がこれらの値を定義しており、追加の識別子は「Leighton-Micali Signatures (LMS)」レジストリー [IANA-LMS] に登録できます。

5. Public Key Identifiers

5. 公開鍵識別子

Certificates conforming to [RFC5280] can convey a public key for any public key algorithm. The certificate indicates the algorithm through an algorithm identifier. An algorithm identifier consists of an OID and optional parameters.

[RFC5280]に準拠する証明書は、任意の公開鍵アルゴリズムの公開鍵を伝達できます。 証明書は、アルゴリズム識別子によってアルゴリズムを示します。 アルゴリズム識別子は、OIDと省略可能なパラメーターから構成されます。

[RFC8554] defines the encoding of HSS public keys, and [RFC8391] defines the encodings of XMSS and XMSSMT public keys. When used in a SubjectPublicKeyInfo type, the subjectPublicKey BIT STRING contains these encodings of the public key.

[RFC8554]はHSS公開鍵のエンコーディングを定義し、[RFC8391]はXMSSおよびXMSSMT公開鍵のエンコーディングを定義しています。 SubjectPublicKeyInfo型で使用する場合、subjectPublicKey BIT STRINGには公開鍵のこれらのエンコーディングが格納されます。

This document defines ASN.1 [X680] OCTET STRING types for encoding the public keys when not used in a SubjectPublicKeyInfo. The OCTET STRING is mapped to a subjectPublicKey (a value of type BIT STRING) as follows: the most significant bit of the OCTET STRING value becomes the most significant bit of the BIT STRING value, and so on; the least significant bit of the OCTET STRING becomes the least significant bit of the BIT STRING.

この文書は、SubjectPublicKeyInfoで使用しない場合に公開鍵をエンコードするためのASN.1 [X680] OCTET STRING型を定義します。 OCTET STRINGは、次のようにsubjectPublicKey（BIT STRING型の値）に対応付けられます: OCTET STRING値の最上位ビットがBIT STRING値の最上位ビットとなり、以下同様に、OCTET STRINGの最下位ビットがBIT STRINGの最下位ビットとなります。

7. Signature Algorithms

7. 署名アルゴリズム

The same OIDs used to identify HSS, XMSS, and XMSSMT public keys are also used to identify their respective signatures. When these algorithm identifiers appear in the algorithm field of an AlgorithmIdentifier, the encoding MUST omit the parameters field. That is, the AlgorithmIdentifier SHALL be a SEQUENCE of one component, one of the OIDs defined in the following subsections.

HSS、XMSS、およびXMSSMT公開鍵を識別するのと同じOIDが、それぞれの署名の識別にも使用されます。 これらのアルゴリズム識別子がAlgorithmIdentifierのalgorithmフィールドに現れる場合、エンコーディングはparametersフィールドを省略しなければなりません（MUST）。 つまり、AlgorithmIdentifierは、後続のサブセクションで定義するOIDのいずれか1つを唯一の構成要素とするSEQUENCEとすることになります（SHALL）。

When the signature algorithm identifiers described in this document are used to create a signature on a message, no digest algorithm is applied to the message before signing. That is, the full data to be signed is signed rather than a digest of the data.

この文書で説明する署名アルゴリズム識別子を使用してメッセージに署名を作成する場合、署名前にメッセージにダイジェストアルゴリズムは適用されません。 つまり、データのダイジェストではなく、署名対象のデータ全体に署名します。

10. Security Considerations

10. セキュリティーに関する考慮事項

The security requirements of [SP800208] MUST be taken into account.

[SP800208]のセキュリティー要件を考慮しなければなりません（MUST）。

As stateful HBS private keys can only generate a limited number of signatures, a user needs to be aware of the total number of signatures they intend to generate in their use case; otherwise, they risk exhausting the number of OTS keys in their private key.

ステートフルHBSの秘密鍵は限られた数の署名しか生成できないため、ユーザーは自身のユースケースで生成しようとする署名の総数を把握しておく必要があります。 そうしなければ、秘密鍵内のOTS鍵を使い果たすおそれがあります。

For stateful HBS schemes, it is crucial to stress the importance of correct state management. If an attacker were able to obtain signatures for two different messages created using the same OTS key, then it would become computationally feasible for that attacker to create forgeries [BH16]. As noted in [MCGREW] and [ETSI-TR-103-692], extreme care needs to be taken in order to avoid the risk that an OTS key will be reused accidentally. This is a new requirement that most developers will not be familiar with and requires careful handling.

ステートフルHBS方式では、正しい状態管理の重要性を強調することが極めて重要です。 攻撃者が同じOTS鍵を使用して作成された2つの異なるメッセージの署名を入手できた場合、その攻撃者が偽造を作成することが計算上可能になります [BH16]。 [MCGREW]と[ETSI-TR-103-692]で述べられているように、OTS鍵が誤って再利用されるリスクを避けるために、細心の注意を払う必要があります。 これはほとんどの開発者にとってなじみのない新しい要件であり、慎重な取り扱いが必要です。

Various strategies for a correct state management can be applied:

正しい状態管理のために、さまざまな戦略を適用できます:

  • Implement a record of all signatures generated by a key pair associated with a stateful HBS instance, for example, by logging the OTS key indexes as signatures are generated. This record may be stored outside the device that is used to generate the signature. Check the record to prevent OTS key reuse before a new signature is released. If OTS key reuse is detected, freeze all new signature generation by the private key, re-audit previously released signatures (possibly revoking the private key if previously released signatures showed OTS key reuse), and perform a post-failure audit.

  • Use a stateful HBS instance only for a moderate number of signatures such that it is always practical to keep a consistent record and be able to unambiguously trace back all generated signatures.

  • Apply the state reservation strategy described in Section 5 of [MCGREW], where upcoming states are reserved in advance by the signer. In this way, the number of state synchronizations between nonvolatile and volatile memory is reduced.

  • ステートフルHBSインスタンスに関連付けられた鍵ペアによって生成されたすべての署名の記録を実装します。 たとえば、署名を生成する際にOTS鍵のインデックスをログに記録します。 この記録は、署名の生成に使用するデバイスの外部に保存してもかまいません。 新しい署名を公開する前に記録を確認し、OTS鍵の再利用を防ぎます。 OTS鍵の再利用が検出された場合は、その秘密鍵による新しい署名の生成をすべて凍結し、以前に公開した署名を再監査し（以前に公開した署名にOTS鍵の再利用が見つかった場合は、秘密鍵を失効させることもありえます）、障害後の監査を実施します。

  • 一貫した記録を保持し、生成されたすべての署名を明確にさかのぼって追跡することが常に現実的にできるよう、ステートフルHBSインスタンスは適度な数の署名にのみ使用します。

  • [MCGREW]のセクション5で説明されている状態予約戦略を適用します。 この戦略では、署名者がこれから使う状態を事前に予約します。 これにより、不揮発性メモリーと揮発性メモリーの間の状態同期の回数が削減されます。

11. Backup and Restore Management

11. バックアップとリストアの管理

Certificate authorities have high demands in order to ensure the availability of signature generation throughout the validity period of signing key pairs.

認証局には、署名鍵ペアの有効期間を通じて署名生成の可用性を確保するという高い要求があります。

Some usual backup and restore strategies when using a stateless signature scheme (e.g., SLH-DSA) are to:

ステートレスな署名方式（たとえばSLH-DSA）を使用する場合の一般的なバックアップとリストアの戦略には、次のようなものがあります:

  • duplicate private keying material and operate redundant signing devices.
  • store and safeguard a copy of the private keying material such that it can be used to set up a new signing device in case of technical difficulties.
  • 秘密鍵の鍵情報を複製し、冗長な署名デバイスを運用する。
  • 技術的な問題が生じた場合に新しい署名デバイスをセットアップするために使用できるよう、秘密鍵の鍵情報のコピーを保管して保護する。

For stateful HBS schemes, such straightforward backup and restore strategies will lead to OTS reuse with high probability as a correct state management is not guaranteed. Strategies for maintaining availability and keeping a correct state are described in Section 7 of [SP800208] and [S-HBS].

ステートフルHBS方式では、正しい状態管理が保証されないため、このような単純なバックアップとリストアの戦略は高い確率でOTSの再利用につながります。 可用性を維持しつつ正しい状態を保つための戦略は、[SP800208]のセクション7と[S-HBS]で説明されています。
