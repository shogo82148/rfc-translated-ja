RFC 8615

Well-Known Uniform Resource Identifiers (URIs)

RFC 8615

ウェルノウンURI（Well-Known Uniform Resource Identifiers）

Abstract

概要

This memo defines a path prefix for "well-known locations", "/.well-known/", in selected Uniform Resource Identifier (URI) schemes.

このメモは、一部のURI（Uniform Resource Identifier）スキームにおける「ウェルノウンロケーション（well-known location）」のためのパスプレフィックス「/.well-known/」を定義します。

In doing so, it obsoletes RFC 5785 and updates the URI schemes defined in RFC 7230 to reserve that space. It also updates RFC 7595 to track URI schemes that support well-known URIs in their registry.

これにあたり、このメモはRFC 5785を廃止し、その空間を予約するためにRFC 7230で定義されたURIスキームを更新します。また、ウェルノウンURIをサポートするURIスキームをレジストリーで追跡するために、RFC 7595も更新します。

1. Introduction

1. はじめに

Some applications on the Web require the discovery of information about an origin [RFC6454] (sometimes called "site-wide metadata") before making a request. For example, the Robots Exclusion Protocol (http://www.robotstxt.org) specifies a way for automated processes to obtain permission to access resources; likewise, the Platform for Privacy Preferences [P3P] tells user agents how to discover privacy policy before interacting with an origin server.

Web上の一部のアプリケーションでは、リクエストを行う前に、オリジン[RFC6454]に関する情報（「サイト全体のメタデータ」と呼ばれることもあります）を発見する必要があります。たとえば、ロボット排除プロトコル（Robots Exclusion Protocol、http://www.robotstxt.org）は、自動化されたプロセスがリソースにアクセスする許可を得る方法を規定しています。同様に、P3P（Platform for Privacy Preferences）[P3P]は、オリジンサーバーとやり取りする前にプライバシーポリシーを発見する方法をユーザーエージェントに伝えます。

While there are several ways to access per-resource metadata (e.g., HTTP header fields, PROPFIND in Web Distributed Authoring and Versioning (WebDAV) [RFC4918]), the perceived overhead (either in terms of client-perceived latency and/or deployment difficulties) associated with them often precludes their use in these scenarios.

リソースごとのメタデータにアクセスする方法はいくつかありますが（たとえば、HTTPヘッダーフィールドや、WebDAV（Web Distributed Authoring and Versioning）[RFC4918]のPROPFIND）、それらに伴うと考えられるオーバーヘッド（クライアントが感じるレイテンシーと配備の難しさのいずれかまたは両方の点で）のために、こうした場面ではそれらを使えないことがよくあります。

At the same time, it has become more popular to use HTTP as a substrate for non-Web protocols. Sometimes, such protocols need a way to locate one or more resources on a given host.

同時に、Web以外のプロトコルの基盤としてHTTPを使うことが広まってきました。そのようなプロトコルでは、あるホスト上の1つ以上のリソースの場所を特定する方法が必要になることがあります。

When this happens, one solution is to designate a "well-known location" for data or services related to the origin overall, so that it can be easily located. However, this approach has the drawback of risking collisions, both with other such designated "well-known locations" and with resources that the origin has created (or wishes to create). Furthermore, defining well-known locations usurps the origin's control over its own URI space [RFC7320].

このような場合の解決策の1つは、オリジン全体に関係するデータやサービスのために「ウェルノウンロケーション（well-known location）」を指定して、それらを簡単に見つけられるようにすることです。しかし、この方法には、同じように指定された他の「ウェルノウンロケーション」や、オリジンが作成した（または作成したい）リソースと衝突するリスクがあるという欠点があります。さらに、ウェルノウンロケーションを定義することは、オリジンが自身のURI空間に対して持つ制御権を奪うことになります[RFC7320]。

To address these uses, this memo reserves a path prefix in HTTP, HTTPS, WebSocket (WS), and Secure WebSocket (WSS) URIs for these "well-known locations", "/.well-known/". Future specifications that need to define a resource for such metadata can register their use to avoid collisions and minimise impingement upon origins' URI space.

こうした用途に対処するために、このメモは、HTTP、HTTPS、WebSocket（WS）、Secure WebSocket（WSS）のURIにおいて、これらの「ウェルノウンロケーション」のためのパスプレフィックス「/.well-known/」を予約します。そのようなメタデータのためのリソースを定義する必要がある将来の仕様は、衝突を避け、オリジンのURI空間への侵害を最小限に抑えるために、その使用を登録できます。

Well-known URIs can also be used with other URI schemes, but only when those schemes' definitions explicitly allow it.

ウェルノウンURIは他のURIスキームでも使用できますが、それはそのスキームの定義が明示的に許可している場合に限られます。

3. Well-Known URIs

3. ウェルノウンURI

A well-known URI is a URI [RFC3986] whose path component begins with the characters "/.well-known/", provided that the scheme is explicitly defined to support well-known URIs.

ウェルノウンURIとは、パスコンポーネントが文字列「/.well-known/」で始まるURI[RFC3986]です。ただし、そのスキームがウェルノウンURIをサポートすると明示的に定義されている場合に限ります。

For example, if an application registers the name 'example', the corresponding well-known URI on 'http://www.example.com/' would be 'http://www.example.com/.well-known/example'.

たとえば、あるアプリケーションが「example」という名前を登録した場合、'http://www.example.com/' 上の対応するウェルノウンURIは 'http://www.example.com/.well-known/example' になります。

This specification updates the "http" [RFC7230] and "https" [RFC7230] schemes to support well-known URIs. Other existing schemes can use the appropriate process for updating their definitions; for example, [RFC8307] does so for the "ws" and "wss" schemes. The "Uniform Resource Identifier (URI) Schemes" registry tracks which schemes support well-known URIs; see Section 5.2.

この仕様は、「http」[RFC7230]スキームと「https」[RFC7230]スキームを更新して、ウェルノウンURIをサポートするようにします。他の既存のスキームは、その定義を更新するための適切なプロセスを使用できます。たとえば、[RFC8307]は「ws」スキームと「wss」スキームについてそれを行っています。どのスキームがウェルノウンURIをサポートしているかは、「Uniform Resource Identifier (URI) Schemes」レジストリーで追跡されます。Section 5.2を参照してください。

Applications that wish to mint new well-known URIs MUST register them, following the procedures in Section 5.1, subject to the following requirements.

新しいウェルノウンURIを作成したいアプリケーションは、以下の要件に従い、Section 5.1の手続きに沿ってそれを登録しなければなりません（MUST）。

Registered names MUST conform to the "segment-nz" production in [RFC3986]. This means they cannot contain the "/" character.

登録する名前は、[RFC3986]の「segment-nz」生成規則に従わなければなりません（MUST）。つまり、名前に「/」文字を含めることはできません。

Registered names for a specific application SHOULD be correspondingly precise; "squatting" on generic terms is not encouraged. For example, if the Example application wants a well-known location for metadata, an appropriate registered name might be "example-metadata" or even "example.com-metadata", not "metadata".

特定のアプリケーションのために登録する名前は、それに応じて的確であるべきです（SHOULD）。一般的な用語を「占拠（squatting）」することは推奨されません。たとえば、Exampleというアプリケーションがメタデータのためのウェルノウンロケーションを必要とする場合、適切な登録名は「metadata」ではなく、「example-metadata」や、さらには「example.com-metadata」などになるでしょう。

At a minimum, a registration will reference a specification that defines the format and associated media type(s) to be obtained by dereferencing the well-known URI, along with the URI scheme(s) that the well-known URI can be used with. If no URI schemes are explicitly specified, "http" and "https" are assumed.

登録では、少なくとも、ウェルノウンURIを参照解決して得られる形式と、それに関連するメディアタイプを定義した仕様を参照し、あわせてそのウェルノウンURIを使用できるURIスキームも示します。URIスキームが明示的に指定されていない場合は、「http」と「https」とみなされます。

Typically, applications will use the default port for the given scheme; if an alternative port is used, it MUST be explicitly specified by the application in question.

通常、アプリケーションはそのスキームのデフォルトポートを使用します。代替のポートを使用する場合は、そのアプリケーションがそれを明示的に指定しなければなりません（MUST）。

Registrations MAY also contain additional information, such as the syntax of additional path components, query strings, and/or fragment identifiers to be appended to the well-known URI, or protocol-specific details (e.g., HTTP [RFC7231] method handling).

登録には、ウェルノウンURIに付加される追加のパスコンポーネント、クエリー文字列、フラグメント識別子の構文や、プロトコル固有の詳細（たとえば、HTTP [RFC7231]のメソッドの扱い）といった追加情報を含めてもよいです（MAY）。

Note that this specification defines neither how to determine the hostname to use to find the well-known URI for a particular application, nor the scope of the metadata discovered by dereferencing the well-known URI; both should be defined by the application itself.

この仕様では、特定のアプリケーションのウェルノウンURIを見つけるために使用するホスト名をどのように決定するかも、ウェルノウンURIを参照解決して発見したメタデータの適用範囲も定義していないことに注意してください。どちらもアプリケーション自身が定義すべきです。

Also, this specification does not define a format or media type for the resource located at "/.well-known/", and clients should not expect a resource to exist at that location.

また、この仕様は「/.well-known/」に置かれるリソースの形式やメディアタイプを定義しておらず、クライアントはその場所にリソースが存在することを期待すべきではありません。

Well-known URIs are rooted in the top of the path's hierarchy; they are not well-known by definition in other parts of the path. For example, "/.well-known/example" is a well-known URI, whereas "/foo/.well-known/example" is not.

ウェルノウンURIはパス階層の最上位を起点とします。パスのそれ以外の部分にあるものは、定義上ウェルノウンではありません。たとえば、「/.well-known/example」はウェルノウンURIですが、「/foo/.well-known/example」はそうではありません。

See also Section 4 for Security Considerations regarding well-known locations.

ウェルノウンロケーションに関するセキュリティー上の考慮事項については、Section 4も参照してください。

3.1. Registering Well-Known URIs

3.1. ウェルノウンURIの登録

The "Well-Known URIs" registry is located at <https://www.iana.org/assignments/well-known-uris/>. Registration requests can be made by following the instructions located there or by sending an email to the <wellknown-uri-review@ietf.org> mailing list.

「Well-Known URIs」レジストリーは<https://www.iana.org/assignments/well-known-uris/>にあります。登録リクエストは、そこにある説明に従うか、<wellknown-uri-review@ietf.org>メーリングリストに電子メールを送ることで行えます。

Registration requests consist of at least the following information:

登録リクエストは、少なくとも次の情報で構成されます。

URI suffix:
The name requested for the well-known URI, relative to "/.well-known/"; e.g., "example".
Change controller:
For Standards Track RFCs, state "IETF". For others, give the name of the responsible party. Other details (e.g., email address, home page URI) may also be included.
Specification document(s):
Reference to the document that specifies the field, preferably including a URI that can be used to retrieve a copy of the document. An indication of the relevant sections may also be included, but is not required.
Status:
One of "permanent" or "provisional". See guidance below.
Related information:
Optionally, citations to additional documents containing further relevant information.
URIサフィックス：
ウェルノウンURIとして要求する名前で、「/.well-known/」からの相対で表します。例：「example」
変更管理者：
標準化過程のRFCの場合は「IETF」と記載します。それ以外の場合は、責任者の名前を記載します。その他の詳細（たとえば、電子メールアドレス、ホームページのURI）を含めることもできます。
仕様文書：
そのフィールドを規定する文書への参照で、文書のコピーを取得するために使用できるURIを含めることが望まれます。関連するセクションを示すこともできますが、必須ではありません。
ステータス：
「permanent」または「provisional」のいずれかです。下記の指針を参照してください。
関連情報：
任意で、さらに関連する情報を含む追加の文書への引用を記載します。

General requirements for registered values are described in Section 3.

登録する値に関する一般的な要件はSection 3で説明しています。

Values defined by Standards Track RFCs and other open standards (in the sense of [RFC2026], Section 7.1.1) have a status of "permanent". Other values can also be registered as permanent, if the experts find that they are in use, in consultation with the community. Other values should be registered as "provisional".

標準化過程のRFCおよびその他のオープン標準（[RFC2026], Section 7.1.1の意味での）で定義された値のステータスは「permanent」です。その他の値も、専門家がコミュニティーと協議したうえで、それが使用されていると判断した場合には、permanentとして登録できます。それ以外の値は「provisional」として登録すべきです。

Provisional entries can be removed by the experts if -- in consultation with the community -- the experts find that they are not in use. The experts can change a provisional entry's status to permanent; in doing so, the experts should consider how widely used a value is and consult the community beforehand.

provisionalのエントリーは、専門家がコミュニティーと協議したうえで、それが使用されていないと判断した場合には、専門家によって削除されることがあります。専門家はprovisionalのエントリーのステータスをpermanentに変更できます。その際、専門家はその値がどの程度広く使われているかを考慮し、事前にコミュニティーと協議すべきです。

Note that "consult the community" above refers to those responsible for the URI scheme(s) in question. Generally, this would take place on the mailing list(s) of the appropriate Working Group(s) (possibly concluded), or on <art@ietf.org> if no such list exists.

上記の「コミュニティーと協議」とは、対象となるURIスキームの責任者との協議を指すことに注意してください。一般に、これは適切なワーキンググループ（終了している場合もあります）のメーリングリストで行われ、そのようなリストが存在しない場合は<art@ietf.org>で行われます。

Well-known URIs can be registered by third parties (including the expert(s)), if the expert(s) determine that an unregistered well-known URI is widely deployed and not likely to be registered in a timely manner otherwise. Such registrations still are subject to the requirements defined, including the need to reference a specification.

登録されていないウェルノウンURIが広く配備されており、他の方法ではタイムリーに登録される見込みがないと専門家が判断した場合には、そのウェルノウンURIを第三者（専門家を含む）が登録できます。そのような登録も、仕様を参照する必要性を含め、定義された要件に従います。

4. Security Considerations

4. セキュリティーに関する考慮事項

Applications minting new well-known URIs, as well as administrators deploying them, will need to consider several security-related issues, including (but not limited to) exposure of sensitive data, denial-of-service attacks (in addition to normal load issues), server and client authentication, vulnerability to DNS rebinding attacks, and attacks where limited access to a server grants the ability to affect how well-known URIs are served.

新しいウェルノウンURIを作成するアプリケーションや、それを配備する管理者は、セキュリティーに関連するいくつかの問題を考慮する必要があります。これには、機密データの露出、サービス拒否攻撃（通常の負荷の問題に加えて）、サーバーとクライアントの認証、DNSリバインディング攻撃に対する脆弱性、サーバーへの限定的なアクセスによってウェルノウンURIの提供のされ方に影響を与えられるようになる攻撃などが含まれます（ただし、これらに限りません）。

[RFC3552] contains some examples of potential security considerations that may be relevant to application protocols and administrators deploying them.

[RFC3552]には、アプリケーションプロトコルや、それを配備する管理者に関係する可能性のあるセキュリティー上の考慮事項の例がいくつか含まれています。

4.1. Protecting Well-Known Resources

4.1. ウェルノウンリソースの保護

Because well-known locations effectively represent the entire origin, server operators should appropriately control the ability to write to them. This is especially true when more than one entity is co-located on the same origin. Even for origins that are controlled by and represent a single entity, due care should be taken to assure that write access to well-known locations is not granted unwittingly, either externally through server configuration or locally through implementation permissions (e.g., on a filesystem).

ウェルノウンロケーションは事実上オリジン全体を代表するため、サーバーの運用者はそこへ書き込む能力を適切に制御すべきです。これは、複数のエンティティーが同じオリジンに同居している場合には特に当てはまります。単一のエンティティーが制御し、それを代表するオリジンであっても、ウェルノウンロケーションへの書き込みアクセスが、外部からはサーバーの設定を通じて、内部からは実装の権限（たとえば、ファイルシステム上の権限）を通じて、意図せず許可されることのないよう、十分な注意を払うべきです。

4.2. Interaction with Web Browsing

4.2. Webブラウジングとの相互作用

Applications using well-known URIs for "http" or "https" URLs need to be aware that well-known resources will be accessible to Web browsers, and therefore are able to be manipulated by content obtained from other parts of that origin. If an attacker is able to inject content (e.g., through a Cross-Site Scripting vulnerability), they will be able to make potentially arbitrary requests to the well-known resource.

「http」や「https」のURLに対してウェルノウンURIを使用するアプリケーションは、ウェルノウンリソースがWebブラウザーからアクセス可能であり、したがってそのオリジンの他の部分から取得したコンテンツによって操作されうることに注意する必要があります。攻撃者が（たとえば、クロスサイトスクリプティングの脆弱性を通じて）コンテンツを注入できる場合、攻撃者はウェルノウンリソースに対して潜在的に任意のリクエストを行えることになります。

HTTP and HTTPS also use origins as a security boundary for many other mechanisms, including (but not limited to) cookies [RFC6265], Web Storage [WEBSTORAGE], and various capabilities.

HTTPとHTTPSは、Cookie [RFC6265]、Webストレージ[WEBSTORAGE]、さまざまな能力など、他の多くのメカニズムでも（ただし、これらに限りません）、オリジンをセキュリティー境界として使用しています。

An application that defines well-known locations should not assume that it has sole access to these mechanisms or that it is the only application using the origin. Depending on the nature of the application, mitigations can include:

ウェルノウンロケーションを定義するアプリケーションは、自分がこれらのメカニズムに単独でアクセスできるとか、自分がそのオリジンを使用している唯一のアプリケーションであるとか、仮定すべきではありません。アプリケーションの性質によっては、緩和策として次のようなものが考えられます。

  • Encrypting sensitive information
  • Allowing flexibility in the use of identifiers (e.g., cookie names) to avoid collisions with other applications
  • Using the 'HttpOnly' flag on cookies to assure that cookies are not exposed to browser scripting languages [RFC6265]
  • Using the 'Path' parameter on cookies to assure that they are not available to other parts of the origin [RFC6265]
  • Using X-Content-Type-Options: nosniff [FETCH] to assure that content under attacker control can't be coaxed into a form that is interpreted as active content by a Web browser
  • 機密情報を暗号化する
  • 他のアプリケーションとの衝突を避けるために、識別子（たとえば、Cookie名）の使い方に柔軟性を持たせる
  • Cookieがブラウザーのスクリプト言語に公開されないように、Cookieに「HttpOnly」フラグを使用する[RFC6265]
  • Cookieがオリジンの他の部分から利用できないように、Cookieに「Path」パラメーターを使用する[RFC6265]
  • 攻撃者の制御下にあるコンテンツが、Webブラウザーによってアクティブコンテンツとして解釈される形式に仕立てられることのないよう、X-Content-Type-Options: nosniff [FETCH]を使用する

Other good practices include:

その他の優れたプラクティスには次のものがあります。

  • Using an application-specific media type in the Content-Type header field, and requiring clients to fail if it is not used
  • Using Content-Security-Policy [CSP] to constrain the capabilities of active content (such as HTML [HTML5]), thereby mitigating Cross-Site Scripting attacks
  • Using Referrer-Policy [REFERRER-POLICY] to prevent sensitive data in URLs from being leaked in the Referer request header field
  • Avoiding use of compression on any sensitive information (e.g., authentication tokens, passwords), as the scripting environment offered by Web browsers allows an attacker to repeatedly probe the compression space; if the attacker has access to the path of the communication, they can use this capability to recover that information.
  • Content-Typeヘッダーフィールドでアプリケーション固有のメディアタイプを使用し、それが使用されていない場合はクライアントが失敗するよう要求する
  • Content-Security-Policy [CSP]を使用して（HTML [HTML5]のような）アクティブコンテンツの能力を制限し、それによってクロスサイトスクリプティング攻撃を緩和する
  • Referrer-Policy [REFERRER-POLICY]を使用して、URL内の機密データがRefererリクエストヘッダーフィールドで漏洩するのを防ぐ
  • 機密情報（たとえば、認証トークン、パスワード）に対して圧縮を使用しないようにする。Webブラウザーが提供するスクリプト環境では、攻撃者が圧縮空間を繰り返し探ることができるためです。攻撃者が通信経路にアクセスできる場合、この能力を使ってその情報を復元できます。

4.3. Scoping Applications

4.3. アプリケーションの適用範囲

This memo does not specify the scope of applicability for the information obtained from a well-known URI, and does not specify how to discover a well-known URI for a particular application.

このメモは、ウェルノウンURIから取得した情報の適用範囲を規定しておらず、特定のアプリケーションのウェルノウンURIを発見する方法も規定していません。

Individual applications using this mechanism must define both aspects; if this is not specified, security issues can arise from implementation deviations and confusion about boundaries between applications.

このメカニズムを使用する個々のアプリケーションは、この両方の側面を定義する必要があります。これが規定されていない場合、実装間の相違や、アプリケーション間の境界に関する混乱から、セキュリティー上の問題が生じる可能性があります。

Applying metadata discovered in a well-known URI to resources other than those co-located on the same origin risks administrative as well as security issues. For example, allowing "https://example.com/.well-known/example" to apply policy to "https://department.example.com", "https://www.example.com", or even "https://www.example.com:8000" assumes a relationship between hosts where there might be none, thereby giving control to a potential attacker.

ウェルノウンURIで発見したメタデータを、同じオリジンに同居するリソース以外のリソースに適用すると、セキュリティー上の問題だけでなく管理上の問題も生じるリスクがあります。たとえば、「https://example.com/.well-known/example」が「https://department.example.com」、「https://www.example.com」、さらには「https://www.example.com:8000」にポリシーを適用することを許可すると、関係が存在しないかもしれないホスト間に関係があると仮定することになり、その結果、潜在的な攻撃者に制御を与えてしまいます。

Likewise, specifying that a well-known URI on a particular hostname is to be used to bootstrap a protocol can cause a large number of undesired requests. For example, if a well-known HTTPS URI is used to find policy about a separate service such as email, it can result in a flood of requests to Web servers, even if they don't implement the well-known URI. Such undesired requests can resemble a denial-of-service attack.

同様に、特定のホスト名上のウェルノウンURIをプロトコルのブートストラップに使用すると規定すると、大量の望ましくないリクエストが発生する可能性があります。たとえば、電子メールのような別のサービスに関するポリシーを見つけるためにウェルノウンHTTPS URIを使用すると、WebサーバーがそのウェルノウンURIを実装していない場合でも、Webサーバーへのリクエストが殺到する可能性があります。そのような望ましくないリクエストは、サービス拒否攻撃に似たものになりえます。

4.4. Hidden Capabilities

4.4. 隠れた能力

Applications using well-known locations should consider that some server administrators might be unaware of their existence (especially on operating systems that hide directories whose names begin with "."). This means that if an attacker has write access to the .well-known directory, they would be able to control its contents, possibly without the administrator realising it.

ウェルノウンロケーションを使用するアプリケーションは、一部のサーバー管理者がその存在に気づいていない可能性があることを考慮すべきです（特に、名前が「.」で始まるディレクトリーを隠すオペレーティングシステムの場合）。これは、攻撃者が.well-knownディレクトリーへの書き込みアクセス権を持っている場合、おそらく管理者が気づかないうちに、その内容を制御できてしまうことを意味します。

Appendix A. Frequently Asked Questions

Appendix A. よくある質問

Aren't well-known locations bad for the Web?
They are, but for various reasons -- both technical and social -- they are sometimes necessary. This memo defines a "sandbox" for them, to reduce the risks of collision and to minimise the impact upon preexisting URIs on sites.
Why "/.well-known?"
It's short, descriptive, and according to search indices, not widely used.
What impact does this have on existing mechanisms, such as P3P and robots.txt?
None, until they choose to use this mechanism.
Why aren't per-directory well-known locations defined?
Allowing every URI path segment to have a well-known location (e.g., "/images/.well-known/") would increase the risks of colliding with a preexisting URI on a site, and generally these solutions are found not to scale well because they're too "chatty".
ウェルノウンロケーションはWebにとって良くないものではありませんか？
そのとおりですが、技術的および社会的なさまざまな理由から、それが必要になることもあります。このメモは、衝突のリスクを減らし、サイト上の既存のURIへの影響を最小限に抑えるために、それらのための「サンドボックス」を定義します。
なぜ「/.well-known」なのですか？
短く、内容を表しており、検索インデックスによればあまり使われていないからです。
P3Pやrobots.txtなどの既存のメカニズムにはどのような影響がありますか？
それらがこのメカニズムを使用することを選択しない限り、影響はありません。
なぜディレクトリーごとのウェルノウンロケーションは定義されないのですか？
すべてのURIパスセグメントがウェルノウンロケーション（たとえば、「/images/.well-known/」）を持てるようにすると、サイト上の既存のURIと衝突するリスクが高まります。また、一般に、そのような解決策はやり取りが多すぎる（「chatty」である）ため、うまくスケールしないことがわかっています。
