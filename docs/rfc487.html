RFC 487

Free File Transfer

RFC 487

自由なファイル転送

Abstract

概要

In the past several months, many people have commented to me about their difficulty in transferring files. The hang up appears to be with systems that have some flavor of security, but on which the user has no access privileges. Specifically, the FTP server demands a user and password before it will grant any system access. The loophole which people have been using is the MAIL FILE facility, which is both limited in scope and intended for other purposes.

ここ数か月の間に、ファイル転送の難しさについて多くの人から意見をもらいました。問題は、何らかのセキュリティーの仕組みがあるものの、利用者がアクセス権限を持っていないシステムにあるようです。具体的には、FTPサーバーは、システムへのアクセスを一切許可する前に、ユーザー名とパスワードを要求します。人々がこれまで使ってきた抜け道はMAIL FILE機能ですが、これは適用範囲が限られており、本来は別の目的のためのものです。

A frequently used model for file protection is to define three levels of user access: 1) only the user himself; 2) all users in a group; 3) everyone. Up until now, "everyone" has meant anyone already granted logon privileges. A new class is, perhaps, needed to cover everyone, exclusive of whether or not they are logged on.

ファイル保護によく使われるモデルは、ユーザーのアクセスに3つのレベルを定義するものです。1）ユーザー本人のみ、2）グループ内のすべてのユーザー、3）全員。これまで「全員」とは、すでにログオン権限を与えられている人すべてを意味していました。ログオンしているかどうかにかかわらず全員を対象とする、新しい区分がおそらく必要です。

With all this in mind, I propose the following course of action:

以上のことを踏まえ、次の方針を提案します。

If a user connects to an FTP server and makes a file request without supplying a user name-password, the server should then examine the file access parameters. If the file is listed as accessible to anyone, then the transfer should be allowed to proceed.

ユーザーがFTPサーバーに接続し、ユーザー名とパスワードを提示せずにファイルを要求した場合、サーバーはファイルのアクセスパラメーターを調べるべきです。そのファイルが誰でもアクセス可能となっていれば、転送の続行を許可すべきです。

This scheme can be implemented so as not to yield file creations privileges - for example, store commands can be implemented via an append mechanism. If I wanted a file sent to me I could create an empty file with unlimited append access. I would then inform the foreign user to store (append?) to that file.

この方式は、ファイルの作成権限を与えないように実装できます。たとえば、保存（store）コマンドは追記（append）の仕組みによって実装できます。ファイルを送ってもらいたい場合、私は無制限に追記できる空のファイルを作成します。そして、相手側のユーザーに、そのファイルへ保存（追記？）するよう伝えます。

The problem of accounting is somewhat more complex. Clearly, storing a file in a user's directory can be charged to that user. When retrieving a file from a general system directory, there is no "user" specified, and overhead may have to be billed. The former case involved both CPU time for transfer and secondary storage charges for storing the new file. In the latter case, only CPU charges are involved, and these may be sufficiently small to not cause a major problem.

課金の問題はもう少し複雑です。ユーザーのディレクトリーにファイルを保存する場合は、明らかにそのユーザーに課金できます。システムの一般ディレクトリーからファイルを取得する場合は、「ユーザー」が指定されていないので、オーバーヘッドとして請求せざるを得ないかもしれません。前者の場合は、転送のためのCPU時間と、新しいファイルを保存するための二次記憶の料金の両方がかかります。後者の場合はCPUの料金だけがかかり、これは大きな問題にならない程度に小さいかもしれません。

BBN TENEX has agreed to modify their FTP server to allow general access transfers as described above. Specific details for usage will be available when installation is complete. I urge other systems to make this service available, if only on an experimental basis. The success of such an experiment will be judged by the reaction of the general user community and the uses to which FTP is put.

BBN TENEXは、上で説明したような一般アクセスの転送を許可するよう、自身のFTPサーバーを変更することに同意しました。具体的な使い方の詳細は、導入が完了したら公開します。ほかのシステムにも、たとえ実験的なものであっても、このサービスを提供するよう強く求めます。このような実験の成否は、一般のユーザーコミュニティーの反応と、FTPがどのような用途に使われるかによって判断されるでしょう。

NOTE: Bob Clements tells me that the BBN TENEX implementation will probably require a user name of something like "FREE" or "ANONYMOUS", but not require a password.

注記: Bob Clementsによると、BBN TENEXの実装では、おそらく「FREE」や「ANONYMOUS」のようなユーザー名が必要になりますが、パスワードは必要ないとのことです。
