RFC 8410

Algorithm Identifiers for Ed25519, Ed448, X25519, and X448 for Use in the Internet X.509 Public Key Infrastructure

RFC 8410

インターネットX.509公開鍵基盤で使用するためのEd25519、Ed448、X25519、X448のアルゴリズム識別子

Abstract

概要

This document specifies algorithm identifiers and ASN.1 encoding formats for elliptic curve constructs using the curve25519 and curve448 curves. The signature algorithms covered are Ed25519 and Ed448. The key agreement algorithms covered are X25519 and X448. The encoding for public key, private key, and Edwards-curve Digital Signature Algorithm (EdDSA) structures is provided.

この文書は、curve25519曲線とcurve448曲線を使用する楕円曲線の構成要素のためのアルゴリズム識別子とASN.1エンコーディング形式を規定します。対象とする署名アルゴリズムはEd25519とEd448です。対象とする鍵合意アルゴリズムはX25519とX448です。公開鍵、秘密鍵、エドワーズ曲線デジタル署名アルゴリズム（EdDSA）の構造のエンコーディングを示します。

1. Introduction

1. はじめに

In [RFC7748], the elliptic curves curve25519 and curve448 are described. They are designed with performance and security in mind. The curves may be used for Diffie-Hellman and digital signature operations.

[RFC7748]では、楕円曲線curve25519とcurve448について説明しています。これらの曲線は、性能とセキュリティーを念頭に置いて設計されています。これらの曲線は、ディフィー・ヘルマン（Diffie-Hellman）操作とデジタル署名操作に使用できます。

[RFC7748] describes the operations on these curves for the Diffie-Hellman operation. A convention has developed that when these two curves are used with the Diffie-Hellman operation, they are referred to as X25519 and X448. This RFC defines the ASN.1 Object Identifiers (OIDs) for the operations X25519 and X448 along with the associated parameters. The use of these OIDs is described for public and private keys.

[RFC7748]は、ディフィー・ヘルマン操作のためのこれらの曲線上の操作を説明しています。これら2つの曲線をディフィー・ヘルマン操作で使用する場合は、X25519およびX448と呼ぶという慣例ができています。このRFCは、X25519操作とX448操作のためのASN.1オブジェクト識別子（OID）を、関連するパラメーターとともに定義します。これらのOIDの使い方を、公開鍵と秘密鍵について説明します。

In [RFC8032] the elliptic curve signature system Edwards-curve Digital Signature Algorithm (EdDSA) is described along with a recommendation for the use of the curve25519 and curve448. EdDSA has defined two modes: the PureEdDSA mode without prehashing and the HashEdDSA mode with prehashing. The convention used for identifying the algorithm/curve combinations is to use "Ed25519" and "Ed448" for the PureEdDSA mode. This document does not provide the conventions needed for the prehash versions of the signature algorithm. The use of the OIDs is described for public keys, private keys and signatures.

[RFC8032]では、楕円曲線署名方式であるエドワーズ曲線デジタル署名アルゴリズム（EdDSA）が、curve25519とcurve448の使用に関する推奨とともに説明されています。EdDSAは2つのモードを定義しています。事前ハッシュを行わないPureEdDSAモードと、事前ハッシュを行うHashEdDSAモードです。アルゴリズムと曲線の組み合わせを識別するための慣例として、PureEdDSAモードには「Ed25519」と「Ed448」を使用します。この文書は、署名アルゴリズムの事前ハッシュ版に必要な慣例は規定しません。これらのOIDの使い方を、公開鍵、秘密鍵、署名について説明します。

[RFC8032] additionally defines the concept of a context. Contexts can be used to differentiate signatures generated for different purposes with the same key. The use of contexts is not defined in this document for the following reasons:

[RFC8032]は、さらにコンテキストという概念も定義しています。コンテキストを使うと、同じ鍵で異なる目的のために生成された署名を区別できます。次の理由により、この文書ではコンテキストの使用を定義しません。

  • The current implementations of Ed25519 do not support the use of contexts; thus, if specified, it will potentially delay the use of these algorithms further.
  • EdDSA is the only IETF algorithm that currently supports the use of contexts; however, there is a possibility that there will be confusion between which algorithms need to have separate keys and which do not. This may result in a decrease of security for those other algorithms.
  • There are still ongoing discussions among the cryptographic community about how effective the use of contexts is for preventing attacks.
  • There needs to be discussions about the correct way to identify when context strings are to be used. It is not clear if different OIDs should be used for different contexts or the OID should merely note that a context string needs to be provided.
  • 現在のEd25519の実装は、コンテキストの使用をサポートしていません。そのため、コンテキストを規定すると、これらのアルゴリズムの利用がさらに遅れる可能性があります。
  • 現在コンテキストの使用をサポートしているIETFのアルゴリズムはEdDSAだけです。しかし、どのアルゴリズムが別々の鍵を必要とし、どのアルゴリズムが必要としないのかについて、混乱が生じる可能性があります。その結果、それ以外のアルゴリズムのセキュリティーが低下するおそれがあります。
  • コンテキストの使用が攻撃の防止にどの程度有効であるかについて、暗号コミュニティーではまだ議論が続いています。
  • コンテキスト文字列をいつ使用するのかを識別する正しい方法について、議論が必要です。コンテキストごとに異なるOIDを使用すべきなのか、それとも単にコンテキスト文字列を提供する必要があることをOIDで示すべきなのかは明らかではありません。

3. Curve25519 and Curve448 Algorithm Identifiers

3. Curve25519とCurve448のアルゴリズム識別子

Certificates conforming to [RFC5280] can convey a public key for any public key algorithm. The certificate indicates the algorithm through an algorithm identifier. An algorithm identifier consists of an OID and optional parameters.

[RFC5280]に準拠した証明書は、任意の公開鍵アルゴリズムの公開鍵を運ぶことができます。証明書は、アルゴリズム識別子によってアルゴリズムを示します。アルゴリズム識別子は、OIDと省略可能なパラメーターから構成されます。

The AlgorithmIdentifier type, which is included for convenience, is defined as follows:

便宜のために掲載するAlgorithmIdentifier型は、次のように定義されています。

AlgorithmIdentifier  ::=  SEQUENCE  {
    algorithm   OBJECT IDENTIFIER,
    parameters  ANY DEFINED BY algorithm OPTIONAL
}

AlgorithmIdentifier  ::=  SEQUENCE  {
    algorithm   OBJECT IDENTIFIER,
    parameters  ANY DEFINED BY algorithm OPTIONAL
}

The fields in AlgorithmIdentifier have the following meanings:

AlgorithmIdentifierのフィールドは、次の意味を持ちます。

  • algorithm identifies the cryptographic algorithm with an object identifier. Four such OIDs are defined below.
  • parameters, which are optional, are the associated parameters for the algorithm identifier in the algorithm field.
  • algorithmは、オブジェクト識別子によって暗号アルゴリズムを識別します。そのようなOIDを以下で4つ定義します。
  • parametersは省略可能なフィールドで、algorithmフィールドのアルゴリズム識別子に関連するパラメーターです。

In this document, we define four new OIDs for identifying the different curve/algorithm pairs: the curves being curve25519 and curve448 and the algorithms being ECDH and EdDSA in pure mode. For all of the OIDs, the parameters MUST be absent.

この文書では、異なる曲線とアルゴリズムの組を識別するために、4つの新しいOIDを定義します。曲線はcurve25519とcurve448であり、アルゴリズムはECDHとピュアモードのEdDSAです。すべてのOIDについて、パラメーターは存在しない必要があります（MUST）。

It is possible to find systems that require the parameters to be present. This can be due to either a defect in the original 1997 syntax or a programming error where developers never got input where this was not true. The optimal solution is to fix these systems; where this is not possible, the problem needs to be restricted to that subsystem and not propagated to the Internet.

パラメーターが存在することを要求するシステムが見つかる場合があります。これは、もともとの1997年の構文の欠陥か、パラメーターが存在しない入力を開発者が一度も受け取らなかったことによるプログラミングエラーのいずれかが原因である可能性があります。最適な解決策は、そのようなシステムを修正することです。それができない場合は、問題をそのサブシステムに閉じ込め、インターネットに波及させないようにする必要があります。

The same algorithm identifiers are used for identifying a public key, a private key, and a signature (for the two EdDSA related OIDs). Additional encoding information is provided below for each of these locations.

公開鍵、秘密鍵、署名（EdDSA関連の2つのOIDの場合）の識別には、同じアルゴリズム識別子を使用します。これらの各場所に関するエンコーディングの追加情報は、以下で示します。

id-X25519    OBJECT IDENTIFIER ::= { 1 3 101 110 }
id-X448      OBJECT IDENTIFIER ::= { 1 3 101 111 }
id-Ed25519   OBJECT IDENTIFIER ::= { 1 3 101 112 }
id-Ed448     OBJECT IDENTIFIER ::= { 1 3 101 113 }

id-X25519    OBJECT IDENTIFIER ::= { 1 3 101 110 }
id-X448      OBJECT IDENTIFIER ::= { 1 3 101 111 }
id-Ed25519   OBJECT IDENTIFIER ::= { 1 3 101 112 }
id-Ed448     OBJECT IDENTIFIER ::= { 1 3 101 113 }

4. Subject Public Key Fields

4. サブジェクト公開鍵のフィールド

In the X.509 certificate, the subjectPublicKeyInfo field has the SubjectPublicKeyInfo type, which has the following ASN.1 syntax:

X.509証明書において、subjectPublicKeyInfoフィールドはSubjectPublicKeyInfo型を持ち、その型は次のASN.1構文を持ちます。

SubjectPublicKeyInfo  ::=  SEQUENCE  {
    algorithm         AlgorithmIdentifier,
    subjectPublicKey  BIT STRING
}

SubjectPublicKeyInfo  ::=  SEQUENCE  {
    algorithm         AlgorithmIdentifier,
    subjectPublicKey  BIT STRING
}

The fields in SubjectPublicKeyInfo have the following meanings:

SubjectPublicKeyInfoのフィールドは、次の意味を持ちます。

  • algorithm is the algorithm identifier and parameters for the public key (see above).
  • subjectPublicKey contains the byte stream of the public key. The algorithms defined in this document always encode the public key as an exact multiple of 8 bits.
  • algorithmは、公開鍵のアルゴリズム識別子とパラメーターです（上記を参照）。
  • subjectPublicKeyには、公開鍵のバイトストリームが入ります。この文書で定義するアルゴリズムは、常に公開鍵をちょうど8ビットの倍数としてエンコードします。

Both [RFC7748] and [RFC8032] define the public key value as being a byte string. It should be noted that the public key is computed differently for each of these documents; thus, the same private key will not produce the same public key.

[RFC7748]と[RFC8032]はどちらも、公開鍵の値をバイト文字列として定義しています。公開鍵の計算方法はこれらの文書でそれぞれ異なることに注意してください。そのため、同じ秘密鍵から同じ公開鍵が得られるわけではありません。

The following is an example of a public key encoded using the textual encoding defined in [RFC7468].

次は、[RFC7468]で定義されたテキストエンコーディングを使用してエンコードした公開鍵の例です。

-----BEGIN PUBLIC KEY-----
MCowBQYDK2VwAyEAGb9ECWmEzf6FQbrBZ9w7lshQhqowtrbLDFw4rXAxZuE=
-----END PUBLIC KEY-----

-----BEGIN PUBLIC KEY-----
MCowBQYDK2VwAyEAGb9ECWmEzf6FQbrBZ9w7lshQhqowtrbLDFw4rXAxZuE=
-----END PUBLIC KEY-----

5. Key Usage Bits

5. 鍵用途ビット

The intended application for the key is indicated in the keyUsage certificate extension.

鍵の用途は、keyUsage証明書拡張で示されます。

If the keyUsage extension is present in a certificate that indicates id-X25519 or id-X448 in SubjectPublicKeyInfo, then the following MUST be present:

SubjectPublicKeyInfoでid-X25519またはid-X448を示す証明書にkeyUsage拡張が存在する場合、次の値が存在しなければなりません（MUST）。

        keyAgreement;

        keyAgreement;

one of the following MAY also be present:

また、次のいずれか1つが存在してもよいです（MAY）。

          encipherOnly; or
          decipherOnly.

          encipherOnly; or
          decipherOnly.

If the keyUsage extension is present in an end-entity certificate that indicates id-Ed25519 or id-Ed448, then the keyUsage extension MUST contain one or both of the following values:

id-Ed25519またはid-Ed448を示すエンドエンティティー証明書にkeyUsage拡張が存在する場合、keyUsage拡張は次の値の一方または両方を含まなければなりません（MUST）。

        nonRepudiation; and
        digitalSignature.

        nonRepudiation; and
        digitalSignature.

If the keyUsage extension is present in a certification authority certificate that indicates id-Ed25519 or id-Ed448, then the keyUsage extension MUST contain one or more of the following values:

id-Ed25519またはid-Ed448を示す認証局の証明書にkeyUsage拡張が存在する場合、keyUsage拡張は次の値のうち1つ以上を含まなければなりません（MUST）。

       nonRepudiation;
       digitalSignature;
       keyCertSign; and
       cRLSign.

       nonRepudiation;
       digitalSignature;
       keyCertSign; and
       cRLSign.

6. EdDSA Signatures

6. EdDSA署名

Signatures can be placed in a number of different ASN.1 structures. The top level structure for a certificate is given below as being illustrative of how signatures are frequently encoded with an algorithm identifier and a location for the signature.

署名は、さまざまなASN.1構造に配置できます。署名がアルゴリズム識別子と署名の格納場所とともにどのようにエンコードされることが多いかを示す例として、証明書の最上位の構造を以下に示します。

   Certificate  ::=  SEQUENCE  {
        tbsCertificate       TBSCertificate,
        signatureAlgorithm   AlgorithmIdentifier,
        signatureValue       BIT STRING  }

   Certificate  ::=  SEQUENCE  {
        tbsCertificate       TBSCertificate,
        signatureAlgorithm   AlgorithmIdentifier,
        signatureValue       BIT STRING  }

The same algorithm identifiers are used for signatures as are used for public keys. When used to identify signature algorithms, the parameters MUST be absent.

署名には、公開鍵に使用するものと同じアルゴリズム識別子を使用します。署名アルゴリズムの識別に使用する場合、パラメーターは存在しない必要があります（MUST）。

The data to be signed is prepared for EdDSA. Then, a private key operation is performed to generate the signature value. This value is the opaque value ENC(R) || ENC(S) described in Section 3.3 of [RFC8032]. The octet string representing the signature is encoded directly in the BIT STRING without adding any additional ASN.1 wrapping. For the Certificate structure, the signature value is wrapped in the "signatureValue" BIT STRING field.

署名するデータをEdDSA用に準備します。次に、秘密鍵の操作を実行して署名値を生成します。この値は、[RFC8032]のセクション3.3で説明されている不透明な値ENC(R) || ENC(S)です。署名を表すオクテット文字列は、ASN.1によるラッピングを追加せずに、BIT STRINGに直接エンコードします。Certificate構造の場合、署名値は「signatureValue」BIT STRINGフィールドに包まれます。

7. Private Key Format

7. 秘密鍵の形式

"Asymmetric Key Packages" [RFC5958] describes how to encode a private key in a structure that both identifies what algorithm the private key is for and allows for the public key and additional attributes about the key to be included as well. For illustration, the ASN.1 structure OneAsymmetricKey is replicated below. The algorithm-specific details of how a private key is encoded are left for the document describing the algorithm itself.

「Asymmetric Key Packages」[RFC5958]は、秘密鍵がどのアルゴリズム用であるかを識別するとともに、公開鍵や鍵に関する追加の属性も含めることができる構造で秘密鍵をエンコードする方法を説明しています。説明のために、ASN.1構造OneAsymmetricKeyを以下に再掲します。秘密鍵をどのようにエンコードするかというアルゴリズム固有の詳細は、そのアルゴリズム自体を記述する文書に委ねられています。

OneAsymmetricKey ::= SEQUENCE {
   version Version,
   privateKeyAlgorithm PrivateKeyAlgorithmIdentifier,
   privateKey PrivateKey,
   attributes [0] IMPLICIT Attributes OPTIONAL,
   ...,
   [[2: publicKey [1] IMPLICIT PublicKey OPTIONAL ]],
   ...
}

PrivateKey ::= OCTET STRING

PublicKey ::= BIT STRING

OneAsymmetricKey ::= SEQUENCE {
   version Version,
   privateKeyAlgorithm PrivateKeyAlgorithmIdentifier,
   privateKey PrivateKey,
   attributes [0] IMPLICIT Attributes OPTIONAL,
   ...,
   [[2: publicKey [1] IMPLICIT PublicKey OPTIONAL ]],
   ...
}

PrivateKey ::= OCTET STRING

PublicKey ::= BIT STRING

For the keys defined in this document, the private key is always an opaque byte sequence. The ASN.1 type CurvePrivateKey is defined in this document to hold the byte sequence. Thus, when encoding a OneAsymmetricKey object, the private key is wrapped in a CurvePrivateKey object and wrapped by the OCTET STRING of the "privateKey" field.

この文書で定義する鍵では、秘密鍵は常に不透明なバイト列です。このバイト列を保持するために、この文書ではASN.1型CurvePrivateKeyを定義します。したがって、OneAsymmetricKeyオブジェクトをエンコードする場合、秘密鍵はCurvePrivateKeyオブジェクトに包まれ、さらに「privateKey」フィールドのOCTET STRINGに包まれます。

CurvePrivateKey ::= OCTET STRING

CurvePrivateKey ::= OCTET STRING

To encode an EdDSA, X25519, or X448 private key, the "privateKey" field will hold the encoded private key. The "privateKeyAlgorithm" field uses the AlgorithmIdentifier structure. The structure is encoded as defined above. If present, the "publicKey" field will hold the encoded key as defined in [RFC7748] and [RFC8032].

EdDSA、X25519、またはX448の秘密鍵をエンコードするには、「privateKey」フィールドにエンコードした秘密鍵を格納します。「privateKeyAlgorithm」フィールドにはAlgorithmIdentifier構造を使用します。この構造は、上記で定義したとおりにエンコードします。「publicKey」フィールドが存在する場合、このフィールドには[RFC7748]と[RFC8032]で定義されたとおりにエンコードした鍵を格納します。

The following is an example of a private key encoded using the textual encoding defined in [RFC7468].

次は、[RFC7468]で定義されたテキストエンコーディングを使用してエンコードした秘密鍵の例です。

-----BEGIN PRIVATE KEY-----
MC4CAQAwBQYDK2VwBCIEINTuctv5E1hK1bbY8fdp+K06/nwoy/HU++CXqI9EdVhC
-----END PRIVATE KEY-----

-----BEGIN PRIVATE KEY-----
MC4CAQAwBQYDK2VwBCIEINTuctv5E1hK1bbY8fdp+K06/nwoy/HU++CXqI9EdVhC

8. Human-Readable Algorithm Names

8. 人間が読めるアルゴリズム名

For the purpose of consistent cross-implementation naming, this section establishes human-readable names for the algorithms specified in this document. Implementations SHOULD use these names when referring to the algorithms. If there is a strong reason to deviate from these names -- for example, if the implementation has a different naming convention and wants to maintain internal consistency -- it is encouraged to deviate as little as possible from the names given here.

実装間で一貫した名前を付けるために、このセクションでは、この文書で規定するアルゴリズムの人間が読める名前を定めます。実装は、これらのアルゴリズムを参照する際にこれらの名前を使用すべきです（SHOULD）。これらの名前から逸脱する強い理由がある場合（たとえば、実装が異なる命名規則を持っていて、内部の一貫性を保ちたい場合）でも、ここで示す名前からの逸脱はできるだけ小さくすることが推奨されます。

Use the string "ECDH" when referring to a public key of type "X25519" or "X448" when the curve is not known or relevant.

曲線が不明であるか重要でない場合に、「X25519」型または「X448」型の公開鍵を参照するときは、文字列「ECDH」を使用してください。

When the curve is known, use the more specific string of "X25519" or "X448".

曲線がわかっている場合は、より具体的な文字列「X25519」または「X448」を使用してください。

Use the string "EdDSA" when referring to a signing public key or signature when the curve is not known or relevant.

曲線が不明であるか重要でない場合に、署名用の公開鍵または署名を参照するときは、文字列「EdDSA」を使用してください。

When the curve is known, use a more specific string. For the id-Ed25519 value use the string "Ed25519". For id-Ed448, use "Ed448".

曲線がわかっている場合は、より具体的な文字列を使用してください。id-Ed25519の値には文字列「Ed25519」を使用してください。id-Ed448には「Ed448」を使用してください。

12. Security Considerations

12. セキュリティーに関する考慮事項

The security considerations of [RFC5280], [RFC7748], and [RFC8032] apply accordingly.

[RFC5280]、[RFC7748]、[RFC8032]のセキュリティーに関する考慮事項が、それぞれ適用されます。

The procedures for going from a private key to a public key are different when used with Diffie-Hellman versus when used with Edwards Signatures. This means that the same public key cannot be used for both ECDH and EdDSA.

秘密鍵から公開鍵を求める手順は、ディフィー・ヘルマンで使用する場合とエドワーズ署名で使用する場合とで異なります。つまり、同じ公開鍵をECDHとEdDSAの両方に使用することはできません。

Appendix A. Invalid Encodings

付録A. 無効なエンコーディング

There are a number of things that need to be dealt with when a new key part is decoded and imported into the system. A partial list of these includes:

新しい鍵の一部をデコードしてシステムにインポートする際には、対処が必要な事項がいくつかあります。その一部を次に挙げます。

  • ASN.1 encoding errors: Two items are highlighted here. First, the use of an OCTET STRING rather than a BIT STRING for the public key. The use of OCTET STRING was a copy error that existed in a previous draft version of this document; the structure is correct in [RFC5958]. However, any early implementation may have this wrong. Second, the value of the version field is required to be 0 if the publicKey is absent and 1 if present. This is called out in [RFC5958], but was not duplicated above.
  • Key encoding errors: Both [RFC7748] and [RFC8032] have formatting requirements for keys that need to be enforced. In some cases, the enforcement is done at the time of importing, for example, doing masking or a mod p operation. In other cases, the enforcement is done by rejecting the keys and having an import failure.
  • Key mismatch errors: If a public key is provided, it may not agree with the private key because either it is wrong or the wrong algorithm was used.
  • ASN.1エンコーディングエラー: ここでは2つの項目を取り上げます。1つ目は、公開鍵にBIT STRINGではなくOCTET STRINGを使用することです。OCTET STRINGの使用は、この文書の以前のドラフト版に存在した転記ミスです。構造は[RFC5958]では正しく記載されています。しかし、初期の実装の中にはこれを誤っているものがあるかもしれません。2つ目は、versionフィールドの値は、publicKeyが存在しない場合は0、存在する場合は1であることが要求されている点です。これは[RFC5958]で明記されていますが、上記では再掲していません。
  • 鍵エンコーディングエラー: [RFC7748]と[RFC8032]はどちらも、鍵に対して強制する必要がある形式上の要件を定めています。場合によっては、インポート時に、たとえばマスク処理やmod p演算を行うことで要件を強制します。それ以外の場合は、鍵を拒否してインポートを失敗させることで要件を強制します。
  • 鍵の不一致エラー: 公開鍵が提供されている場合、その公開鍵が誤っているか、誤ったアルゴリズムが使用されたために、秘密鍵と一致しない場合があります。
