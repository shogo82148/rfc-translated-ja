RFC 10078

Problem Statement, Gap Analysis, and Requirements for Intra-Domain Source Address Validation

RFC 10078

ドメイン内送信元アドレス検証の問題提起、ギャップ分析、および要件

Abstract

概要

Source Address Validation (SAV) is an important means to mitigate IP source address spoofing (RFC 2827). This document analyzes the gaps in current operational mechanisms for intra-domain SAV. It also identifies the properties that new intra-domain SAV mechanisms are expected to provide.

送信元アドレス検証（Source Address Validation、SAV）は、IP送信元アドレスのなりすまし（RFC 2827）を緩和するための重要な手段です。この文書は、ドメイン内SAVのために現在運用されているメカニズムのギャップを分析します。また、新しいドメイン内SAVメカニズムが提供することを期待される特性を明らかにします。

1. Introduction

1. はじめに

Source Address Validation (SAV) defends against IP source address spoofing [RFC2827]. Network operators can enforce SAV at the following levels (see [RFC5210]):

送信元アドレス検証（Source Address Validation、SAV）は、IP送信元アドレスのなりすまし[RFC2827]を防ぎます。ネットワーク運用者は、次のレベルでSAVを実施できます（[RFC5210]を参照）。

  • IP SAV in the access network

  • IP SAV at intra-AS/ingress point

  • IP SAV in the inter-AS case (neighboring Autonomous System (AS))

  • アクセスネットワークにおけるIP SAV

  • AS内/イングレスポイントにおけるIP SAV

  • AS間（隣接する自律システム（Autonomous System、AS））の場合のIP SAV

Some access networks have already deployed SAV mechanisms. These mechanisms are typically deployed on switches in the access network and prevent hosts connected to those switches from using the source address of another host on the Internet [RFC5210]. Mechanisms include:

一部のアクセスネットワークでは、すでにSAVメカニズムが導入されています。これらのメカニズムは通常、アクセスネットワーク内のスイッチに導入され、それらのスイッチに接続されたホストがインターネット上の別のホストの送信元アドレスを使用することを防ぎます[RFC5210]。メカニズムには次のものがあります。

  • Source Address Validation Improvement (SAVI) Solution for DHCP [RFC7513]

  • IP Source Guard (IPSG) based on DHCP snooping [IPSG]

  • Cable Source-Verify [cable-verify]

  • DHCPのための送信元アドレス検証改善（Source Address Validation Improvement、SAVI）ソリューション[RFC7513]

  • DHCPスヌーピングに基づくIP Source Guard（IPSG）[IPSG]

  • Cable Source-Verify [cable-verify]

However, access-network SAV mechanisms are not universally deployed [CAIDA-spoofer]. Therefore, intra-domain (i.e., intra-AS) SAV and inter-domain (i.e., inter-AS) SAV are required [RFC5210]. For the purpose of this document, intra-domain SAV is defined as follows:

しかし、アクセスネットワークのSAVメカニズムは、あまねく導入されているわけではありません[CAIDA-spoofer]。そのため、ドメイン内（つまりAS内）SAVとドメイン間（つまりAS間）SAVが必要です[RFC5210]。この文書の目的のために、ドメイン内SAVを次のように定義します。

The AS validates the source addresses of data traffic that it originates directly or indirectly. Intra-domain SAV is applied at external interfaces (on routers) facing entities that are not deployed as neighboring ASes and are therefore not covered by inter-domain SAV. For example, as illustrated in Figure 1, an entity can be a single host, a set of hosts, or a customer network with no AS that manages one or more IP prefixes. The entity may source traffic using prefixes assigned by the AS or its own Bring Your Own IP (BYOIP) prefixes. From the perspective of other ASes, such traffic is originated by the AS.

ASは、自身が直接または間接的に発信するデータトラフィックの送信元アドレスを検証します。ドメイン内SAVは、隣接ASとして配置されておらず、そのためドメイン間SAVの対象とならないエンティティーに面した（ルーター上の）外部インターフェイスで適用されます。たとえば、Figure 1に示すように、エンティティーは、単一のホスト、ホストの集合、または1つ以上のIPプレフィックスを管理するASを持たない顧客ネットワークでありえます。エンティティーは、ASから割り当てられたプレフィックス、または自身のBring Your Own IP（BYOIP）プレフィックスを使用してトラフィックを送信する場合があります。ほかのASから見ると、そのようなトラフィックはそのASが発信したものです。

SAV on traffic received on external interfaces facing a neighboring AS is considered inter-domain SAV, regardless of whether the neighboring AS uses a public Autonomous System Number (ASN) or a private ASN. SAV on internal interfaces (e.g., interfaces between Router 1 and Router 3 in Figure 1) is also outside the scope of this document. This is because routers inside the same AS are generally assumed to be trusted, so SAV on internal interfaces provides limited additional benefit when SAV is already applied at external interfaces. In addition, techniques such as fast reroute can make SAV at internal interfaces technically challenging.

隣接ASに面した外部インターフェイスで受信したトラフィックに対するSAVは、隣接ASがパブリックな自律システム番号（Autonomous System Number、ASN）を使用しているかプライベートASNを使用しているかにかかわらず、ドメイン間SAVとみなされます。内部インターフェイス（たとえば、Figure 1のルーター1とルーター3の間のインターフェイス）でのSAVも、この文書の範囲外です。これは、同じAS内のルーターは一般に信頼できると想定されているため、外部インターフェイスですでにSAVが適用されている場合、内部インターフェイスでのSAVによる追加の利点は限られるからです。加えて、高速リルート（fast reroute）などの技術によって、内部インターフェイスでのSAVは技術的に困難になる場合があります。

Intra-domain SAV is applied at interfaces "*" and "X".

ドメイン内SAVは、インターフェイス「*」および「X」で適用されます。

This document analyzes the gaps in current operational mechanisms for intra-domain SAV. It also identifies the properties that new intra-domain SAV mechanisms are expected to provide.

この文書は、ドメイン内SAVのために現在運用されているメカニズムのギャップを分析します。また、新しいドメイン内SAVメカニズムが提供することを期待される特性を明らかにします。

1.1. Terminology

1.1. 用語

SAV Rule:

The rule that indicates the validity of a specific source IP address or source IP prefix per router interface. It is used by a router to make SAV decisions.

Improper Block:

The validation results in packets with legitimate source addresses being blocked improperly due to inaccurate SAV rules. (The terms "improper block" and "false positive" are used synonymously.)

Improper Permit:

The validation results in packets with spoofed source addresses being permitted improperly due to inaccurate SAV rules. (The terms "improper permit" and "false negative" are used synonymously.)

Proper Block:

The validation results in packets with spoofed source addresses being blocked.

Proper Permit:

The validation results in packets with legitimate source addresses being permitted.

SAV-specific Information:

The information specialized for SAV rule generation.

Direct Server Return (DSR):

A traffic delivery model commonly used by Content Delivery Networks (CDNs) that use anycast service addresses while delivering data from edge locations that do not announce those addresses. In such deployments, a request is received by the anycast server or location, but the response is sent directly by another server (i.e., the edge location) with the anycast service address as the source address, rather than the address used to reach the edge server. This can create a legitimate hidden-prefix scenario.

SAVルール（SAV Rule）:

ルーターのインターフェイスごとに、特定の送信元IPアドレスまたは送信元IPプレフィックスの正当性を示すルールです。ルーターがSAVの判定を行うために使用します。

不適切なブロック（Improper Block）:

不正確なSAVルールが原因で、正当な送信元アドレスを持つパケットが不適切にブロックされる検証結果です。（「不適切なブロック（improper block）」と「偽陽性（false positive）」という用語は同義に使用します。）

不適切な許可（Improper Permit）:

不正確なSAVルールが原因で、なりすました送信元アドレスを持つパケットが不適切に許可される検証結果です。（「不適切な許可（improper permit）」と「偽陰性（false negative）」という用語は同義に使用します。）

適切なブロック（Proper Block）:

なりすました送信元アドレスを持つパケットがブロックされる検証結果です。

適切な許可（Proper Permit）:

正当な送信元アドレスを持つパケットが許可される検証結果です。

SAV固有情報（SAV-specific Information）:

SAVルールの生成に特化した情報です。

Direct Server Return（DSR）:

エニーキャストのサービスアドレスを使用しつつ、それらのアドレスを広告しないエッジロケーションからデータを配信するコンテンツ配信ネットワーク（Content Delivery Network、CDN）でよく使われるトラフィック配信モデルです。このような導入形態では、リクエストはエニーキャストのサーバーまたはロケーションで受信されますが、レスポンスは別のサーバー（つまりエッジロケーション）から直接送信され、その送信元アドレスはエッジサーバーに到達するために使用されるアドレスではなく、エニーキャストのサービスアドレスになります。これにより、正当な隠れたプレフィックスのシナリオが生じることがあります。

2. Problem Statement

2. 問題提起

The problems of existing intra-domain SAV mechanisms can be characterized along three dimensions: improper block, improper permit, and operational overhead:

既存のドメイン内SAVメカニズムの問題は、不適切なブロック、不適切な許可、運用上のオーバーヘッドという3つの観点で特徴づけることができます。

Improper block:
Existing intra-domain SAV mechanisms may block data packets using legitimate source addresses when the applied SAV rules are inaccurate.
Improper permit:
Existing intra-domain SAV mechanisms may permit data packets using spoofed source addresses when the applied SAV rules are inaccurate.
Operational overhead:
Existing intra-domain SAV mechanisms may require operator involvement to determine and update SAV rules. This overhead depends on how much manual effort is needed to keep the SAV rules up to date.
不適切なブロック:
適用されたSAVルールが不正確な場合、既存のドメイン内SAVメカニズムは、正当な送信元アドレスを使用するデータパケットをブロックすることがあります。
不適切な許可:
適用されたSAVルールが不正確な場合、既存のドメイン内SAVメカニズムは、なりすました送信元アドレスを使用するデータパケットを許可することがあります。
運用上のオーバーヘッド:
既存のドメイン内SAVメカニズムでは、SAVルールを決定し更新するために運用者の関与が必要になることがあります。このオーバーヘッドは、SAVルールを最新の状態に保つためにどれだけの手作業が必要かに依存します。

In this document, these three dimensions are used to analyze the gaps in existing intra-domain SAV mechanisms.

この文書では、これら3つの観点を用いて、既存のドメイン内SAVメカニズムのギャップを分析します。

3. Current Operational Intra-Domain SAV Mechanisms

3. 現在運用されているドメイン内SAVメカニズム

Although [RFC2827] and [RFC3704] specify several ingress filtering methods primarily intended for inter-domain SAV, some of these methods have also been applied to intra-domain SAV in operational practice. This section introduces the mechanisms currently used to implement intra-domain SAV.

[RFC2827]と[RFC3704]は、主にドメイン間SAVを意図したいくつかのイングレスフィルタリング手法を規定していますが、これらの手法の一部は、運用の実務においてドメイン内SAVにも適用されています。このセクションでは、ドメイン内SAVを実装するために現在使用されているメカニズムを紹介します。

  • Access Control Lists (ACLs) can be used as SAV filters [RFC2827] to check the source address of each packet against a set of permitted or prohibited prefixes. When applied on a router interface, each Access Control Entry (ACE) used for SAV filtering specifies both matching conditions (i.e., prefixes) and the corresponding action (e.g., permit or deny), and packets are processed accordingly.

  • Strict unicast Reverse Path Forwarding (uRPF) [RFC3704] provides an automated SAV filter by validating the source address of each packet against the router's local Forwarding Information Base (FIB). A packet is accepted only if (i) the FIB contains a prefix covering the source address and (ii) the FIB entry's outgoing interface matches the packet's incoming interface. Otherwise, the packet is discarded.

  • Loose uRPF [RFC3704] also relies on the local FIB for validation but only checks for the presence of a covering prefix. A packet is accepted if the FIB contains a prefix that covers the source address, regardless of the incoming interface.

  • アクセス制御リスト（Access Control List、ACL）は、各パケットの送信元アドレスを許可または禁止するプレフィックスの集合と照合するSAVフィルター[RFC2827]として使用できます。ルーターのインターフェイスに適用する場合、SAVフィルタリングに使用される各アクセス制御エントリー（Access Control Entry、ACE）は、一致条件（つまりプレフィックス）と対応するアクション（たとえば許可または拒否）の両方を指定し、パケットはそれに従って処理されます。

  • ストリクトユニキャストリバースパス転送（strict unicast Reverse Path Forwarding、uRPF）[RFC3704]は、各パケットの送信元アドレスをルーターのローカルの転送情報ベース（Forwarding Information Base、FIB）と照合して検証することで、自動化されたSAVフィルターを提供します。パケットが受け入れられるのは、(i) 送信元アドレスをカバーするプレフィックスがFIBに含まれ、かつ (ii) そのFIBエントリーの出力インターフェイスがパケットの入力インターフェイスと一致する場合だけです。そうでない場合、パケットは破棄されます。

  • ルーズuRPF [RFC3704]も検証にローカルのFIBを利用しますが、カバーするプレフィックスが存在するかどうかだけを確認します。入力インターフェイスにかかわらず、送信元アドレスをカバーするプレフィックスがFIBに含まれていれば、パケットは受け入れられます。

4. Gap Analysis

4. ギャップ分析

This section analyzes the gaps of the current operational intra-domain SAV mechanisms.

このセクションでは、現在運用されているドメイン内SAVメカニズムのギャップを分析します。

ACLs can be used on interfaces facing a customer network with no AS or a set of hosts to permit only packets whose source addresses belong to specific prefixes. To ensure correct filtering behavior, the ACLs used for SAV filtering need to be updated when the permitted prefixes change; otherwise, packets may be improperly permitted or blocked. In ACL-based SAV deployments, keeping these ACLs up to date can introduce operational challenges when operators need to detect prefix changes and determine and apply the corresponding ACL updates.

ACLは、ASを持たない顧客ネットワークやホストの集合に面したインターフェイスで、送信元アドレスが特定のプレフィックスに属するパケットだけを許可するために使用できます。正しいフィルタリング動作を確保するには、許可するプレフィックスが変わったときに、SAVフィルタリングに使用するACLを更新する必要があります。そうしないと、パケットが不適切に許可またはブロックされる可能性があります。ACLに基づくSAVの導入では、運用者がプレフィックスの変更を検出し、対応するACLの更新を決定して適用する必要がある場合、これらのACLを最新の状態に保つことが運用上の課題となることがあります。

As described in Section 3 and also noted in [RFC3704], loose uRPF sacrifices directionality when validating source addresses of data packets. Since its rules are overly permissive, any spoofed packet with a source address present in the FIB may be permitted by loose uRPF (i.e., an improper permit problem).

Section 3で説明したように、また[RFC3704]でも指摘されているように、ルーズuRPFはデータパケットの送信元アドレスを検証する際に方向性を犠牲にしています。そのルールは許容範囲が広すぎるため、FIBに存在する送信元アドレスを持つなりすましパケットは、どれもルーズuRPFで許可される可能性があります（つまり、不適切な許可の問題）。

Strict uRPF may block legitimate traffic in the asymmetric routing or hidden prefix scenarios (see Sections 4.1 and 4.2). It may mistakenly consider a valid incoming interface as invalid, resulting in legitimate packets being blocked (i.e., an improper block problem).

ストリクトuRPFは、非対称ルーティングや隠れたプレフィックスのシナリオ（セクション4.1および4.2を参照）で、正当なトラフィックをブロックする可能性があります。ストリクトuRPFは有効な入力インターフェイスを誤って無効とみなすことがあり、その結果、正当なパケットがブロックされます（つまり、不適切なブロックの問題）。

The following subsections describe two specific gap scenarios for intra-domain SAV.

以下のサブセクションでは、ドメイン内SAVにおける2つの具体的なギャップのシナリオを説明します。

4.1. Asymmetric Routing Scenario

4.1. 非対称ルーティングのシナリオ

Asymmetric routing means a packet traverses from a source to a destination in one path and takes a different path when it returns to the source. Asymmetric routing can occur due to routing policy, traffic engineering, etc.

非対称ルーティングとは、パケットが送信元から宛先へある経路を通り、送信元へ戻るときには別の経路を通ることを意味します。非対称ルーティングは、ルーティングポリシーやトラフィックエンジニアリングなどによって発生することがあります。

For example, a customer network with no AS connected to multiple routers of the AS may need to perform load balancing on incoming traffic, thereby resulting in asymmetric routing. Figure 2 illustrates an example of asymmetric routing. The customer network owns prefix 2001:db8::/55 and connects to two routers of the AS, Router 1 and Router 2. Router 1, Router 2, and Router 3 exchange routing information via the intra-domain routing protocol. To achieve load balancing for inbound traffic, the customer network expects traffic destined for 2001:db8:0::/56 to enter through Router 1 and traffic destined for 2001:db8:0:100::/56 to enter through Router 2. To this end, Router 1 advertises 2001:db8:0::/56 and Router 2 advertises 2001:db8:0:100::/56 through the intra-domain routing protocol. Figure 2 also shows the corresponding FIB entries of Router 1 and Router 2 for the two prefixes.

たとえば、ASの複数のルーターに接続された、ASを持たない顧客ネットワークは、入力トラフィックの負荷分散を行う必要がある場合があり、その結果として非対称ルーティングが生じます。Figure 2に非対称ルーティングの例を示します。顧客ネットワークはプレフィックス2001:db8::/55を所有し、ASの2つのルーターであるルーター1とルーター2に接続しています。ルーター1、ルーター2、ルーター3は、ドメイン内ルーティングプロトコルを介してルーティング情報を交換します。インバウンドトラフィックの負荷分散を実現するために、顧客ネットワークは、2001:db8:0::/56宛てのトラフィックがルーター1から入り、2001:db8:0:100::/56宛てのトラフィックがルーター2から入ることを期待しています。この目的のために、ルーター1は2001:db8:0::/56を、ルーター2は2001:db8:0:100::/56を、ドメイン内ルーティングプロトコルを通じて広告します。Figure 2には、2つのプレフィックスに対応するルーター1とルーター2のFIBエントリーも示しています。

The legitimate traffic originated from the customer network with source addresses in 2001:db8:0:100::/56 will be improperly blocked by strict uRPF on Router 1.

2001:db8:0:100::/56内の送信元アドレスを持つ、顧客ネットワークから発信された正当なトラフィックは、ルーター1のストリクトuRPFによって不適切にブロックされます。

Although the customer network does not expect to receive inbound traffic for 2001:db8:0:100::/56 via Router 1, it can send outbound traffic with source addresses in that prefix through Router 1. As a result, data packets between the customer network and Router 1 may follow asymmetric paths. Arrows in Figure 2 indicate the direction of traffic flow.

顧客ネットワークは、2001:db8:0:100::/56宛てのインバウンドトラフィックをルーター1経由で受信することを期待していませんが、そのプレフィックス内の送信元アドレスを持つアウトバウンドトラフィックをルーター1経由で送信することはできます。その結果、顧客ネットワークとルーター1の間のデータパケットは、非対称な経路をたどることがあります。Figure 2の矢印は、トラフィックの流れの方向を示しています。

If Router 1 enforces strict uRPF by checking the FIB entry for the prefix 2001:db8:0:100::/56, the corresponding SAV rule would only allow packets with a source address from 2001:db8:0:100::/56 that arrive via Router 3. Consequently, when the customer network sends packets with a source address in 2001:db8:0:100::/56 to Router 1, strict uRPF would improperly drop these legitimate packets. Similarly, if Router 2 enforces strict uRPF, it would improperly block legitimate packets from the customer network that use source addresses within the prefix 2001:db8:0::/56.

ルーター1がプレフィックス2001:db8:0:100::/56のFIBエントリーを確認してストリクトuRPFを実施すると、対応するSAVルールは、2001:db8:0:100::/56の送信元アドレスを持ちルーター3経由で到着したパケットだけを許可します。その結果、顧客ネットワークが2001:db8:0:100::/56内の送信元アドレスを持つパケットをルーター1に送信すると、ストリクトuRPFはこれらの正当なパケットを不適切に破棄します。同様に、ルーター2がストリクトuRPFを実施すると、プレフィックス2001:db8:0::/56内の送信元アドレスを使用する顧客ネットワークからの正当なパケットを不適切にブロックします。

4.2. Hidden Prefix Scenario

4.2. 隠れたプレフィックスのシナリオ

The intra-domain hidden prefix scenario refers to situations in which a host or a customer network with no AS legitimately originates traffic using source addresses that are not visible to the intra-domain routing protocol within the domain.

ドメイン内の隠れたプレフィックスのシナリオとは、ホストまたはASを持たない顧客ネットワークが、ドメイン内のドメイン内ルーティングプロトコルからは見えない送信元アドレスを使用して、正当にトラフィックを発信する状況を指します。

  • A host (for example, a cloud server instance operated by a tenant) may originate traffic using a source address not allocated by the AS operator. This can occur in deployments such as DSR, where return traffic is sent directly from the server using a service IP address that is not part of the operator's internal routing view.

  • A customer network with no AS may originate traffic using source addresses that are not advertised to the AS operator. This can occur in scenarios such as DSR deployments or when the customer network uses address space assigned by another provider (e.g., in multi-homing or hybrid connectivity scenarios), and such prefixes are not propagated within the operator's intra-domain routing system.

  • ホスト（たとえば、テナントが運用するクラウドサーバーのインスタンス）は、ASの運用者が割り当てていない送信元アドレスを使用してトラフィックを発信することがあります。これは、DSRのような導入形態で発生する可能性があります。DSRでは、戻りのトラフィックが、運用者の内部ルーティングのビューに含まれないサービスIPアドレスを使用してサーバーから直接送信されます。

  • ASを持たない顧客ネットワークは、ASの運用者に広告されていない送信元アドレスを使用してトラフィックを発信することがあります。これは、DSRの導入のようなシナリオや、顧客ネットワークが別のプロバイダーから割り当てられたアドレス空間を使用する場合（たとえば、マルチホーミングやハイブリッド接続のシナリオ）で、そのようなプレフィックスが運用者のドメイン内ルーティングシステム内に伝播されないときに発生する可能性があります。

For ACL-based SAV, enforcing correct filtering in these scenarios requires authoritative information that explicitly specifies which source addresses the host or the customer network is authorized to use. In practice, such authoritative information is often missing. Strict uRPF and loose uRPF also fail in hidden prefix scenarios. They will drop packets from hidden prefixes because the source addresses are absent from the router's FIB or are received from unexpected interfaces.

ACLに基づくSAVでは、これらのシナリオで正しいフィルタリングを実施するために、ホストまたは顧客ネットワークがどの送信元アドレスの使用を認可されているかを明示的に指定する権威ある情報が必要です。実際には、そのような権威ある情報が欠けていることがよくあります。ストリクトuRPFとルーズuRPFも、隠れたプレフィックスのシナリオでは機能しません。送信元アドレスがルーターのFIBに存在しないか、予期しないインターフェイスから受信されるため、これらは隠れたプレフィックスからのパケットを破棄してしまいます。

5. Requirements for New SAV Mechanisms

5. 新しいSAVメカニズムに対する要件

This section identifies five requirements that can inform the design of new intra-domain SAV mechanisms. These requirements describe the properties that new mechanisms are expected to provide in order to improve upon existing mechanisms but do not make assumptions about how those properties are achieved. They do not mandate or justify any specific extension to routing or other protocols and therefore cannot be used to directly initiate standards-track protocol changes.

このセクションでは、新しいドメイン内SAVメカニズムの設計の参考となる5つの要件を示します。これらの要件は、既存のメカニズムを改善するために新しいメカニズムが提供することを期待される特性を記述するものであり、それらの特性をどのように実現するかについては何も仮定しません。これらの要件は、ルーティングやその他のプロトコルに対する特定の拡張を義務づけたり正当化したりするものではないため、標準化過程のプロトコル変更を直接開始するために使用することはできません。

Existing intra-domain SAV mechanisms have problems in terms of validation accuracy and operational overhead. Current uRPF-based mechanisms derive SAV decisions solely from routing or forwarding state, which is intended to express reachability rather than authorization of source address usage. More generally, current mechanisms lack authoritative information specifically intended for SAV that can be consistently and automatically consumed by SAV mechanisms. As a result, uRPF-based mechanisms may not provide accurate validation in scenarios such as asymmetric routing or hidden prefixes (Section 4). Existing ACL-based SAV deployments may have limited applicability in dynamic environments when they rely on operator-driven ACL maintenance. These problems motivate the first two requirements below (in Sections 5.1 and 5.2). The remaining three requirements (in Sections 5.3, 5.4, and 5.5) are motivated by deployment and operational considerations.

既存のドメイン内SAVメカニズムには、検証の正確さと運用上のオーバーヘッドの点で問題があります。現在のuRPFに基づくメカニズムは、SAVの判定をルーティングまたは転送の状態だけから導き出しますが、これらの状態は送信元アドレスの使用の認可ではなく到達可能性を表すためのものです。より一般的には、現在のメカニズムには、SAVメカニズムが一貫して自動的に利用できる、SAV専用の権威ある情報が欠けています。その結果、uRPFに基づくメカニズムは、非対称ルーティングや隠れたプレフィックスなどのシナリオ（Section 4）で正確な検証を提供できない場合があります。既存のACLに基づくSAVの導入は、運用者主導のACLの保守に依存している場合、動的な環境での適用性が限られることがあります。これらの問題が、以下の最初の2つの要件（セクション5.1および5.2）の動機となっています。残りの3つの要件（セクション5.3、5.4、および5.5）は、導入と運用上の考慮事項に基づくものです。

5.1. Accurate Validation

5.1. 正確な検証

Any new intra-domain SAV mechanism must improve SAV accuracy over existing intra-domain SAV mechanisms. This improvement can be reflected in reduced improper blocks (false positives), reduced improper permits (false negatives), or both. Furthermore, it must seek to mitigate improper blocks and improve the ability to reject spoofed traffic in the gap scenarios described in Section 4. To support this, additional information beyond the local FIB, such as SAV-specific information, may be needed to make validation decisions and generate accurate SAV rules.

新しいドメイン内SAVメカニズムはいずれも、既存のドメイン内SAVメカニズムよりもSAVの正確さを向上させなければなりません。この向上は、不適切なブロック（偽陽性）の削減、不適切な許可（偽陰性）の削減、またはその両方として表れえます。さらに、新しいメカニズムは、Section 4で説明したギャップのシナリオにおいて、不適切なブロックを緩和し、なりすましトラフィックを拒否する能力を向上させることを目指さなければなりません。これを支えるために、検証の判定を行い正確なSAVルールを生成するには、SAV固有情報など、ローカルのFIB以外の追加情報が必要になる場合があります。

5.2. Automatic Updates

5.2. 自動更新

Any new intra-domain SAV mechanism must be capable of automatically collecting and processing relevant information and updating the corresponding SAV rules in response to relevant information changes. Automation helps reduce operational complexity and maintenance overhead while allowing some initial configuration to improve SAV accuracy. This ensures the mechanism is deployable in practical networks without introducing an excessive management burden.

新しいドメイン内SAVメカニズムはいずれも、関連する情報を自動的に収集・処理し、関連する情報の変化に応じて対応するSAVルールを更新できなければなりません。自動化は、SAVの正確さを向上させるためのある程度の初期設定を許容しつつ、運用の複雑さと保守のオーバーヘッドを削減するのに役立ちます。これにより、過度な管理負担をもたらすことなく、メカニズムを実際のネットワークに導入できるようになります。

5.3. Incremental Deployment Support

5.3. 段階的な導入のサポート

Any new intra-domain SAV mechanism must support incremental deployment and provide measurable benefits even when deployed on only a subset of external interfaces facing hosts or customer networks with no AS.

新しいドメイン内SAVメカニズムはいずれも、段階的な導入をサポートし、ホストまたはASを持たない顧客ネットワークに面した外部インターフェイスの一部にしか導入されていない場合でも、測定可能な利点を提供しなければなりません。

5.4. No Adverse Impact on Routing Convergence and Fast Reroute

5.4. ルーティングの収束と高速リルートへの悪影響がないこと

If any new intra-domain SAV mechanism requires disseminating SAV-specific information among intra-domain routers via a protocol, it must not adversely affect the convergence of existing routing protocols or the operation of fast-reroute mechanisms.

新しいドメイン内SAVメカニズムが、プロトコルを介してドメイン内のルーター間でSAV固有情報を配布する必要がある場合、そのメカニズムは、既存のルーティングプロトコルの収束や高速リルートのメカニズムの動作に悪影響を与えてはなりません。

5.5. Authentication of Information Used for SAV

5.5. SAVに使用する情報の認証

Any new intra-domain SAV mechanism must use information that is authenticated or trusted, either through verification of its integrity and authenticity or via an established trust relationship with the information source.

新しいドメイン内SAVメカニズムはいずれも、完全性と真正性の検証によって、または情報源との確立された信頼関係によって、認証された情報または信頼できる情報を使用しなければなりません。

6. Security Considerations

6. セキュリティーに関する考慮事項

This document discusses the problems with existing intra-domain SAV practices and identifies informational requirements for new intra-domain SAV mechanisms. As it does not specify any new protocol/mechanism or protocol extension, it does not introduce new security considerations.

この文書は、既存のドメイン内SAVの実践における問題を議論し、新しいドメイン内SAVメカニズムに対する情報提供のための要件を示すものです。新しいプロトコル/メカニズムやプロトコル拡張を規定するものではないため、新たなセキュリティーに関する考慮事項はもたらしません。
