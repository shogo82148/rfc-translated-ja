RFC 8781

Discovering PREF64 in Router Advertisements

RFC 8781

ルーター広告でのPREF64の発見

Abstract

概要

This document specifies a Neighbor Discovery option to be used in Router Advertisements (RAs) to communicate prefixes of Network Address and Protocol Translation from IPv6 clients to IPv4 servers (NAT64) to hosts.

この文書は、IPv6クライアントからIPv4サーバーへのネットワークアドレス・プロトコル変換（NAT64）のプレフィックスをホストに伝えるために、ルーター広告（RA）で使用する近隣探索オプションを規定します。

1. Introduction

1. はじめに

NAT64 [RFC6146] with DNS Extensions for Network Address Translation from IPv6 clients to IPv4 servers (DNS64) [RFC6147] is a widely deployed mechanism to provide IPv4 access on IPv6-only networks. In various scenarios, the host must be aware of the NAT64 prefix in use by the network. This document specifies a Neighbor Discovery [RFC4861] option to be used in Router Advertisements (RAs) to communicate NAT64 prefixes to hosts.

NAT64 [RFC6146]と、IPv6クライアントからIPv4サーバーへのネットワークアドレス変換のためのDNS拡張（DNS64）[RFC6147]の組み合わせは、IPv6のみのネットワークでIPv4へのアクセスを提供するために広く展開されているメカニズムです。 さまざまなシナリオにおいて、ホストはネットワークで使用されているNAT64プレフィックスを知っている必要があります。 この文書は、NAT64プレフィックスをホストに伝えるために、ルーター広告（RA）で使用する近隣探索[RFC4861]オプションを規定します。

1.2. 用語

NAT64:

A message used by IPv6 routers to advertise their presence together with various link and Internet parameters [RFC4861];
PREF64（またはNAT64プレフィックス）：
IPv6アドレスの合成に使用されるIPv6プレフィックス[RFC6146]。

IPv6クライアントからIPv4サーバーへのネットワークアドレス・プロトコル変換[RFC6146]。

IPv6ルーターが、さまざまなリンクパラメーターやインターネットパラメーターとともに自身の存在を広告するために使用するメッセージ[RFC4861]。

DNS64: a mechanism for synthesizing AAAA records from A records [RFC6147];

DNS64：AレコードからAAAAレコードを合成するためのメカニズム[RFC6147]。

2. Use Cases for Communicating the NAT64 Prefix to Hosts

2. NAT64プレフィックスをホストに伝えるユースケース

On networks employing NAT64, it is useful for hosts to know the NAT64 prefix for several reasons, including the following:

NAT64を採用しているネットワークでは、次のようないくつかの理由から、ホストがNAT64プレフィックスを知っていると便利です。

  • Enabling DNS64 functions on end hosts. In particular:

    • Local DNSSEC validation (DNS64 in stub-resolver mode). As discussed in [RFC6147], Section 2, the stub resolver in the host "will try to obtain (real) AAAA RRs, and in case they are not available, the DNS64 function will synthesize AAAA RRs for internal usage." Therefore, to perform the DNS64 function, the stub resolver needs to know the NAT64 prefix. This is required in order to use DNSSEC on a NAT64 network.
    • Trusted DNS server. AAAA synthesis is required for the host to be able to use a DNS server not provided by the network (e.g., a DNS-over-TLS [RFC7858] or DNS-over-HTTPS [RFC8484] server with which the host has an existing trust relationship).
    • Networks with no DNS64 server. Hosts that support AAAA synthesis and are aware of the NAT64 prefix in use do not need the network to perform the DNS64 function at all.

  • Enabling NAT64 address-translation functions on end hosts. For example:

    • IPv4 address literals on an IPv6-only host. As described in [RFC8305], Section 7.1, IPv6-only hosts connecting to IPv4 address literals can translate the IPv4 literal to an IPv6 literal.
    • 464XLAT [RFC6877]. 464XLAT requires the host be aware of the NAT64 prefix.

  • エンドホストでDNS64機能を有効にするため。具体的には次のとおりです。

    • ローカルでのDNSSEC検証（スタブリゾルバーモードのDNS64）。 [RFC6147], Section 2で論じられているように、ホストのスタブリゾルバーは「（本物の）AAAA RRの取得を試み、それが利用できない場合には、DNS64機能が内部で使用するためのAAAA RRを合成」します。 したがって、DNS64機能を実行するには、スタブリゾルバーがNAT64プレフィックスを知っている必要があります。 これは、NAT64ネットワークでDNSSECを使用するために必要です。
    • 信頼できるDNSサーバー。 ネットワークが提供していないDNSサーバー（たとえば、ホストがすでに信頼関係を持っているDNS-over-TLS [RFC7858]サーバーやDNS-over-HTTPS [RFC8484]サーバー）をホストが使用できるようにするには、AAAAの合成が必要です。
    • DNS64サーバーのないネットワーク。 AAAAの合成をサポートし、使用中のNAT64プレフィックスを知っているホストは、ネットワークにDNS64機能を実行してもらう必要がまったくありません。

  • エンドホストでNAT64のアドレス変換機能を有効にするため。たとえば次のとおりです。

    • IPv6のみのホストでのIPv4アドレスリテラル。 [RFC8305], Section 7.1で説明されているように、IPv4アドレスリテラルに接続するIPv6のみのホストは、IPv4リテラルをIPv6リテラルに変換できます。
    • 464XLAT [RFC6877]。 464XLATでは、ホストがNAT64プレフィックスを知っている必要があります。

3. Why Include the NAT64 Prefix in Router Advertisements?

3. なぜルーター広告にNAT64プレフィックスを含めるのか？

Fate sharing:
NAT64 requires routing to be configured. IPv6 routing configuration requires receiving an IPv6 RA [RFC4861]. Therefore, using RAs to provide hosts with the NAT64 prefix ensures that NAT64 reachability information shares the fate of the rest of the network configuration on the host.
Atomic configuration:
Including the NAT64 prefix in the RA minimizes the number of packets required to configure a host. Only one packet (an RA) is required to complete the network configuration. This speeds up the process of connecting to a network that supports NAT64/DNS64. It also simplifies host implementation by removing the possibility that the host can have an incomplete Layer 3 configuration (e.g., IPv6 addresses and prefixes, but no NAT64 prefix).
Updatability:
It is possible to change the NAT64 prefix at any time, because when it changes, it is possible to notify hosts by sending a new RA.
Deployability:
All IPv6 hosts and networks are required to support Neighbor Discovery [RFC4861] so just a minor extension to the existing implementation is required. Other options, such as [RFC7225], require implementing other protocols (e.g., Port Control Protocol (PCP) [RFC7225]), which could be considered an obstacle for deployment.
運命共有：
NAT64では、ルーティングが設定されている必要があります。 IPv6のルーティング設定には、IPv6 RAの受信が必要です[RFC4861]。 したがって、RAを使用してホストにNAT64プレフィックスを提供すると、NAT64の到達可能性情報が、ホストのその他のネットワーク設定と運命を共有することが保証されます。
アトミックな設定：
RAにNAT64プレフィックスを含めると、ホストの設定に必要なパケット数が最小になります。 ネットワーク設定を完了するのに必要なパケットは1つ（RA）だけです。 これにより、NAT64/DNS64をサポートするネットワークへの接続処理が高速になります。 また、ホストが不完全なレイヤー3の設定（たとえば、IPv6アドレスとプレフィックスはあるがNAT64プレフィックスはない状態）を持つ可能性がなくなるので、ホストの実装が単純になります。
更新可能性：
NAT64プレフィックスが変わったときには新しいRAを送信することでホストに通知できるので、NAT64プレフィックスはいつでも変更できます。
展開の容易さ：
すべてのIPv6ホストとネットワークは近隣探索[RFC4861]をサポートすることが求められているので、既存の実装に小さな拡張を加えるだけで済みます。 [RFC7225]のような他の選択肢では、他のプロトコル（たとえば、ポート制御プロトコル（PCP）[RFC7225]）の実装が必要であり、これは展開の障害になると考えられます。

4. Option Format

4. オプションの形式

Fields:

フィールド：

Type:
8-bit identifier of the PREF64 option type (38)
Length:
8-bit unsigned integer. The length of the option (including the Type and Length fields) is in units of 8 octets. The sender MUST set the length to 2. The receiver MUST ignore the PREF64 option if the Length field value is not 2.
Scaled Lifetime:
13-bit unsigned integer. The maximum time in units of 8 seconds over which this NAT64 prefix MAY be used. See Section 4.1 for the Scaled Lifetime field processing rules.
PLC (Prefix Length Code):
3-bit unsigned integer. This field encodes the NAT64 Prefix Length defined in [RFC6052]. The PLC field values 0, 1, 2, 3, 4, and 5 indicate the NAT64 prefix length of 96, 64, 56, 48, 40, and 32 bits, respectively. The receiver MUST ignore the PREF64 option if the Prefix Length Code field is not set to one of those values.
Highest 96 bits of the Prefix:
96-bit unsigned integer. Contains bits 0 - 95 of the NAT64 prefix.
Type：
PREF64オプションタイプの8ビットの識別子（38）
Length：
8ビットの符号なし整数。 オプションの長さ（TypeフィールドとLengthフィールドを含む）を8オクテット単位で表します。 送信者は長さを2に設定しなければなりません（MUST）。 受信者は、Lengthフィールドの値が2でない場合、PREF64オプションを無視しなければなりません（MUST）。
Scaled Lifetime：
13ビットの符号なし整数。 8秒単位で表した最大時間であり、その間、このNAT64プレフィックスを使用してもよいです（MAY）。 Scaled Lifetimeフィールドの処理規則についてはSection 4.1を参照してください。
PLC（Prefix Length Code、プレフィックス長コード）：
3ビットの符号なし整数。 このフィールドは、[RFC6052]で定義されているNAT64プレフィックス長をエンコードします。 PLCフィールドの値0、1、2、3、4、5は、それぞれ96、64、56、48、40、32ビットのNAT64プレフィックス長を示します。 受信者は、Prefix Length Codeフィールドがこれらの値のいずれにも設定されていない場合、PREF64オプションを無視しなければなりません（MUST）。
Highest 96 bits of the Prefix：
96ビットの符号なし整数。NAT64プレフィックスのビット0～95を含みます。

4.1. Scaled Lifetime Processing

4.1. Scaled Lifetimeの処理

It would be highly undesirable for the NAT64 prefix to have a lifetime shorter than the Router Lifetime, which is defined in Section 4.2 of [RFC4861] as a 16-bit unsigned integer. If the NAT64 prefix lifetime is not at least equal to the default Router Lifetime, it might lead to scenarios in which the NAT64 prefix lifetime expires before the arrival of the next unsolicited RA. Therefore, the Scaled Lifetime encodes the NAT64 prefix lifetime in units of 8 seconds. The receiver MUST multiply the Scaled Lifetime value by 8 (for example, by a logical left shift) to calculate the maximum time in seconds the prefix MAY be used. The maximum lifetime of the NAT64 prefix is thus 65528 seconds. To ensure that the NAT64 prefix does not expire before the default router, it is NOT RECOMMENDED to configure default Router Lifetimes greater than 65528 seconds when using this option. A lifetime of 0 indicates that the prefix SHOULD NOT be used anymore.

NAT64プレフィックスの有効期間が、[RFC4861]のSection 4.2で16ビットの符号なし整数として定義されているRouter Lifetimeよりも短いことは、非常に望ましくありません。 NAT64プレフィックスの有効期間が少なくともデフォルトのRouter Lifetimeと等しくない場合、次の非請求RAが届く前にNAT64プレフィックスの有効期間が切れるというシナリオにつながるおそれがあります。 そのため、Scaled LifetimeはNAT64プレフィックスの有効期間を8秒単位でエンコードします。 受信者は、Scaled Lifetimeの値に8を掛けて（たとえば、論理左シフトによって）、プレフィックスを使用できる最大時間を秒単位で計算しなければなりません（MUST）。 プレフィックスは、この時間の間使用してもよいです（MAY）。 したがって、NAT64プレフィックスの有効期間の最大値は65528秒です。 NAT64プレフィックスがデフォルトルーターよりも先に期限切れにならないようにするため、このオプションを使用する場合に、65528秒より大きいデフォルトのRouter Lifetimeを設定することは推奨されません（NOT RECOMMENDED）。 有効期間0は、そのプレフィックスをもう使用すべきではありません（SHOULD NOT）という意味です。

By default, the value of the Scaled Lifetime field SHOULD be set to the lesser of 3 x MaxRtrAdvInterval [RFC4861] divided by 8, or 8191.

デフォルトでは、Scaled Lifetimeフィールドの値は、3 x MaxRtrAdvInterval [RFC4861]を8で割った値と8191のうち、小さいほうに設定すべきです（SHOULD）。

Router vendors SHOULD allow administrators to specify nonzero lifetime values that are not divisible by 8. In such cases, the router SHOULD round the provided value up to the nearest integer that is divisible by 8 and smaller than 65536, then divide the result by 8 (or perform a logical right shift by 3) and set the Scaled Lifetime field to the resulting value. If a nonzero lifetime value that is to be divided by 8 (or subjected to a logical right shift by 3) is less than 8, then the Scaled Lifetime field SHOULD be set to 1. This last step ensures that lifetimes under 8 seconds are encoded as a nonzero Scaled Lifetime.

ルーターベンダーは、8で割り切れない0以外の有効期間の値を管理者が指定できるようにすべきです（SHOULD）。 そのような場合、ルーターは、指定された値を、8で割り切れて65536より小さい最も近い整数に切り上げ、その結果を8で割り（または3ビットの論理右シフトを行い）、得られた値をScaled Lifetimeフィールドに設定すべきです（SHOULD）。 8で割られる（または3ビットの論理右シフトを受ける）0以外の有効期間の値が8未満の場合、Scaled Lifetimeフィールドは1に設定すべきです（SHOULD）。 この最後の手順により、8秒未満の有効期間が0以外のScaled Lifetimeとしてエンコードされることが保証されます。

5. Usage Guidelines

5. 使用上のガイドライン

This option specifies exactly one NAT64 prefix for all IPv4 destinations. If the network operator wants to route different parts of the IPv4 address space to different NAT64 devices, this can be accomplished by routing more specific subprefixes of the NAT64 prefix to those devices. For example, suppose an operator is using the [RFC1918] address space 10.0.0.0/8 internally. That operator might want to route 10.0.0.0/8 through NAT64 device A, and the rest of the IPv4 space through NAT64 device B. If the operator's NAT64 prefix is 2001:db8:a:b::/96, then the operator can route 2001:db8:a:b::a00:0/104 to NAT64 A and 2001:db8:a:b::/96 to NAT64 B.

このオプションは、すべてのIPv4宛先に対してちょうど1つのNAT64プレフィックスを指定します。 ネットワーク運用者がIPv4アドレス空間の異なる部分を異なるNAT64装置にルーティングしたい場合は、NAT64プレフィックスのより特定的なサブプレフィックスをそれらの装置にルーティングすることで実現できます。 たとえば、ある運用者が[RFC1918]のアドレス空間10.0.0.0/8を内部で使用しているとします。 その運用者は、10.0.0.0/8をNAT64装置A経由で、残りのIPv4空間をNAT64装置B経由でルーティングしたいかもしれません。 運用者のNAT64プレフィックスが2001:db8:a:b::/96であれば、運用者は2001:db8:a:b::a00:0/104をNAT64 Aに、2001:db8:a:b::/96をNAT64 Bにルーティングできます。

This option may appear more than once in an RA (e.g., when gracefully renumbering the network from one NAT64 prefix to another). Host behavior with regard to synthesizing IPv6 addresses from IPv4 addresses SHOULD follow the recommendations given in Section 3 of [RFC7050], limited to the NAT64 prefixes that have a nonzero lifetime.

このオプションは、1つのRAに複数回現れることがあります（たとえば、あるNAT64プレフィックスから別のNAT64プレフィックスへネットワークを穏やかにリナンバリングする場合）。 IPv4アドレスからIPv6アドレスを合成することに関するホストの振る舞いは、0以外の有効期間を持つNAT64プレフィックスに限定して、[RFC7050]のSection 3の推奨事項に従うべきです（SHOULD）。

In a network (or a provisioning domain) that provides both IPv4 and NAT64, it may be desirable for certain IPv4 addresses not to be translated. An example might be private address ranges that are local to the network/provisioning domain and that should not be reached through the NAT64. This type of configuration cannot be conveyed to hosts using this option, or through other NAT64 prefix provisioning mechanisms such as [RFC7050] or [RFC7225]. This problem does not apply in IPv6-only networks: the host in an IPv6-only network does not have an IPv4 address and cannot reach any IPv4 destinations without the NAT64.

IPv4とNAT64の両方を提供するネットワーク（またはプロビジョニングドメイン）では、特定のIPv4アドレスを変換しないことが望ましい場合があります。 その例として、ネットワークやプロビジョニングドメインにローカルで、NAT64を経由して到達すべきではないプライベートアドレス範囲が考えられます。 この種の設定は、このオプションを使っても、[RFC7050]や[RFC7225]のような他のNAT64プレフィックスのプロビジョニングメカニズムを使っても、ホストに伝えることはできません。 この問題はIPv6のみのネットワークには当てはまりません。IPv6のみのネットワークのホストはIPv4アドレスを持たず、NAT64なしではどのIPv4宛先にも到達できないからです。

5.1. Handling Multiple NAT64 Prefixes

5.1. 複数のNAT64プレフィックスの扱い

In some cases, a host may receive multiple NAT64 prefixes from different sources. Possible scenarios include (but are not limited to):

場合によっては、ホストが異なる情報源から複数のNAT64プレフィックスを受信することがあります。 考えられるシナリオには次のようなものがあります（ただし、これらに限定されません）。

  • the host is using multiple mechanisms to discover PREF64 prefixes (e.g., by using PCP [RFC7225]) and/or resolving an IPv4-only fully qualified domain name [RFC7050] in addition to receiving the PREF64 RA option);
  • the PREF64 option presents in a single RA more than once;
  • the host receives multiple RAs with different PREF64 prefixes on a given interface.
  • ホストが、PREF64プレフィックスを発見するために複数のメカニズムを使用している（たとえば、PREF64 RAオプションの受信に加えて、PCP [RFC7225]を使用したり、IPv4のみの完全修飾ドメイン名[RFC7050]を解決したりしている）。
  • 1つのRAにPREF64オプションが複数回現れる。
  • ホストが、あるインターフェイスで異なるPREF64プレフィックスを持つ複数のRAを受信する。

When multiple PREF64s are discovered via the RA PREF64 Option (either the Option presents more than once in a single RA or multiple RAs are received), host behavior with regard to synthesizing IPv6 addresses from IPv4 addresses SHOULD follow the recommendations given in Section 3 of [RFC7050], limited to the NAT64 prefixes that have a nonzero lifetime.

RA PREF64オプションによって複数のPREF64が発見された場合（1つのRAにオプションが複数回現れる場合、または複数のRAを受信した場合のいずれか）、IPv4アドレスからIPv6アドレスを合成することに関するホストの振る舞いは、0以外の有効期間を持つNAT64プレフィックスに限定して、[RFC7050]のSection 3の推奨事項に従うべきです（SHOULD）。

When different PREF64s are discovered using multiple mechanisms, hosts SHOULD select one source of information only. The RECOMMENDED order is:

複数のメカニズムを使用して異なるPREF64が発見された場合、ホストは1つの情報源だけを選択すべきです（SHOULD）。 優先順位は次のとおりにすることが推奨されます（RECOMMENDED）。

  • PCP-discovered prefixes [RFC7225], if supported;
  • PREF64s discovered via the RA Option;
  • PREF64s resolving an IPv4-only fully qualified domain name [RFC7050]
  • PCPで発見されたプレフィックス[RFC7225]（サポートされている場合）
  • RAオプションによって発見されたPREF64
  • IPv4のみの完全修飾ドメイン名[RFC7050]の解決によって得られたPREF64

Note: If the network provides PREF64s via both this RA Option and [RFC7225], hosts that receive the PREF64 via the RA Option may choose to use it immediately (before waiting for the PCP to complete); therefore, some traffic may not reflect any more detailed configuration provided by the PCP.

注：ネットワークがこのRAオプションと[RFC7225]の両方でPREF64を提供している場合、RAオプションでPREF64を受信したホストは、（PCPの完了を待たずに）すぐにそれを使用することを選択するかもしれません。 そのため、一部のトラフィックには、PCPによって提供されるより詳細な設定が反映されない場合があります。

The host SHOULD treat the PREF64 as being specific to the network interface it was received on. Hosts that are aware of Provisioning Domain (PvD, [RFC7556]) MUST treat the PREF64 as being scoped to the implicit or explicit PvD.

ホストは、PREF64を、それを受信したネットワークインターフェイスに固有のものとして扱うべきです（SHOULD）。 プロビジョニングドメイン（PvD、[RFC7556]）を認識しているホストは、PREF64を、暗黙的または明示的なPvDにスコープされたものとして扱わなければなりません（MUST）。

5.2. PREF64 Consistency

5.2. PREF64の一貫性

Section 6.2.7 of [RFC4861] recommends that routers inspect RAs sent by other routers to ensure that all routers onlink advertise consistent information. Routers SHOULD inspect valid PREF64 options received on a given link and verify the consistency. Detected inconsistencies indicate that one or more routers might be misconfigured. Routers SHOULD log such cases to system or network management. Routers SHOULD check and compare the following information:

[RFC4861]のSection 6.2.7は、リンク上のすべてのルーターが一貫した情報を広告していることを確認するために、ルーターが他のルーターから送信されたRAを検査することを推奨しています。 ルーターは、あるリンクで受信した有効なPREF64オプションを検査し、その一貫性を検証すべきです（SHOULD）。 不一致が検出された場合、1つ以上のルーターの設定が誤っている可能性があることを示します。 ルーターは、そのような場合をシステム管理やネットワーク管理に記録すべきです（SHOULD）。 ルーターは、次の情報をチェックして比較すべきです（SHOULD）。

  • set of PREF64s with a nonzero lifetime;
  • set of PREF64s with a zero lifetime.
  • 0以外の有効期間を持つPREF64の集合
  • 有効期間が0のPREF64の集合

Routers that are aware of PvD ([RFC7556]) MUST only compare information scoped to the same implicit or explicit PvD.

PvD（[RFC7556]）を認識しているルーターは、同じ暗黙的または明示的なPvDにスコープされた情報だけを比較しなければなりません（MUST）。

7. Security Considerations

7. セキュリティーに関する考慮事項

Because RAs are required in all IPv6 configuration scenarios, on IPv6-only networks, RAs must already be secured -- e.g., by deploying an RA-Guard [RFC6105]. Providing all configuration in RAs reduces the attack surface to be targeted by malicious attackers trying to provide hosts with invalid configuration, as compared to distributing the configuration through multiple different mechanisms that need to be secured independently.

RAはすべてのIPv6設定シナリオで必要となるため、IPv6のみのネットワークでは、RAはすでに（たとえば、RA-Guard [RFC6105]を展開することによって）保護されているはずです。 すべての設定をRAで提供すると、それぞれ個別に保護する必要がある複数の異なるメカニズムを通じて設定を配布する場合と比べて、ホストに無効な設定を与えようとする悪意のある攻撃者に狙われる攻撃対象領域が小さくなります。

If a host is provided with an incorrect NAT64 prefix, the IPv6-only host might not be able to communicate with IPv4-only destinations. Connectivity to destinations reachable over IPv6 would not be impacted just by providing a host with an incorrect prefix; however, if attackers are capable of sending rogue RAs, they can perform denial-of-service or man-in-the-middle attacks, as described in [RFC6104].

ホストに誤ったNAT64プレフィックスが提供された場合、IPv6のみのホストはIPv4のみの宛先と通信できなくなる可能性があります。 ホストに誤ったプレフィックスを提供するだけでは、IPv6で到達可能な宛先への接続性には影響しません。 しかし、攻撃者が不正なRAを送信できる場合、[RFC6104]で説明されているように、サービス拒否攻撃や中間者攻撃を実行できます。

The security measures that must already be in place to ensure that RAs are only received from legitimate sources eliminate the problem of NAT64 prefix validation described in Section 3.1 of [RFC7050].

RAが正当な送信元からのみ受信されることを保証するためにすでに導入されているはずのセキュリティー対策によって、[RFC7050]のSection 3.1で説明されているNAT64プレフィックスの検証の問題は解消されます。
