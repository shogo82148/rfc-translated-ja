RFC 8204

Benchmarking Virtual Switches in the Open Platform for NFV (OPNFV)

RFC 8204

Open Platform for NFV（OPNFV）における仮想スイッチのベンチマーク

Abstract

概要

This memo describes the contributions of the Open Platform for NFV (OPNFV) project on Virtual Switch Performance (VSPERF), particularly in the areas of test setups and configuration parameters for the system under test. This project has extended the current and completed work of the Benchmarking Methodology Working Group in the IETF and references existing literature. The Benchmarking Methodology Working Group has traditionally conducted laboratory characterization of dedicated physical implementations of internetworking functions. Therefore, this memo describes the additional considerations when virtual switches are implemented on general-purpose hardware. The expanded tests and benchmarks are also influenced by the OPNFV mission to support virtualization of the "telco" infrastructure.

このメモは、Open Platform for NFV（OPNFV）の仮想スイッチ性能（Virtual Switch Performance、VSPERF）プロジェクトの貢献を、特にテストのセットアップと被試験システムの設定パラメーターの分野について説明します。このプロジェクトは、IETFのベンチマーク方法論ワーキンググループ（Benchmarking Methodology Working Group）の現在の作業と完了した作業を拡張し、既存の文献を参照しています。ベンチマーク方法論ワーキンググループは従来、インターネットワーキング機能を専用の物理装置で実装したものについて、実験室での特性評価を行ってきました。そのため、このメモでは、仮想スイッチを汎用ハードウェア上に実装する場合の追加の考慮事項を説明します。拡張されたテストとベンチマークは、「telco」（通信事業者）のインフラストラクチャーの仮想化を支援するというOPNFVの使命からも影響を受けています。

1. Introduction

1. はじめに

The Benchmarking Methodology Working Group (BMWG) has traditionally conducted laboratory characterization of dedicated physical implementations of internetworking functions. The black-box benchmarks of throughput, latency, forwarding rates, and others have served our industry for many years. Now, Network Function Virtualization (NFV) has the goal of transforming how internetwork functions are implemented and therefore has garnered much attention.

ベンチマーク方法論ワーキンググループ（Benchmarking Methodology Working Group、BMWG）は従来、インターネットワーキング機能を専用の物理装置で実装したものについて、実験室での特性評価を行ってきました。スループット、レイテンシー、転送レートなどのブラックボックスベンチマークは、長年にわたって私たちの業界に貢献してきました。現在、ネットワーク機能仮想化（Network Function Virtualization、NFV）は、インターネットワーク機能の実装方法を変革することを目標としており、そのため大きな注目を集めています。

A virtual switch (vSwitch) is an important aspect of the NFV infrastructure; it provides connectivity between and among physical network functions and virtual network functions. As a result, there are many vSwitch benchmarking efforts but few specifications to guide the many new test design choices. This is a complex problem and an industry-wide work in progress. In the future, several of BMWG's fundamental specifications will likely be updated as more testing experience helps to form consensus around new methodologies, and BMWG should continue to collaborate with all organizations that share the same goal.

仮想スイッチ（vSwitch）はNFVインフラストラクチャーの重要な要素であり、物理ネットワーク機能と仮想ネットワーク機能の間や相互の接続性を提供します。その結果、vSwitchのベンチマークの取り組みは数多くありますが、テスト設計における数多くの新しい選択の指針となる仕様はほとんどありません。これは複雑な問題であり、業界全体で進行中の作業です。今後、より多くのテストの経験が新しい方法論に関するコンセンサスの形成に役立つにつれて、BMWGの基本的な仕様のいくつかは更新される可能性が高く、BMWGは同じ目標を共有するすべての組織と協力し続けるべきです。

This memo describes the contributions of the Open Platform for NFV (OPNFV) project on Virtual Switch Performance (VSPERF) characterization through the Danube 3.0 (fourth) release [DanubeRel] to the chartered work of the BMWG (with stable references to their test descriptions). This project has extended the current and completed work of the BMWG IETF and references existing literature. For example, the most often referenced RFC is [RFC2544] (which depends on [RFC1242]), so the foundation of the benchmarking work in OPNFV is common and strong. The recommended extensions are specifically in the areas of test setups and configuration parameters for the system under test.

このメモは、Open Platform for NFV（OPNFV）の仮想スイッチ性能（VSPERF）の特性評価プロジェクトが、Danube 3.0（4番目の）リリース[DanubeRel]までに、BMWGの憲章に定められた作業に対して行った貢献を（それらのテストの説明への安定した参照とともに）説明します。このプロジェクトは、IETFのBMWGの現在の作業と完了した作業を拡張し、既存の文献を参照しています。たとえば、最も頻繁に参照されているRFCは[RFC2544]（これは[RFC1242]に依存します）であり、OPNFVにおけるベンチマーク作業の基盤は共通していて強固です。推奨される拡張は、特にテストのセットアップと被試験システムの設定パラメーターの分野に関するものです。

See [VSPERFhome] for more background and the OPNFV website for general information [OPNFV].

詳しい背景については[VSPERFhome]を、一般的な情報についてはOPNFVのWebサイト[OPNFV]を参照してください。

The authors note that OPNFV distinguishes itself from other open source compute and networking projects through its emphasis on existing "telco" services as opposed to cloud computing. There are many ways in which telco requirements have different emphasis on performance dimensions when compared to cloud computing: support for and transfer of isochronous media streams is one example.

著者らは、OPNFVが、クラウドコンピューティングではなく既存の「telco」（通信事業者）のサービスを重視する点で、ほかのオープンソースのコンピューティングやネットワーキングのプロジェクトと一線を画していることに注目しています。クラウドコンピューティングと比べて、通信事業者の要件が性能のどの側面を重視するかが異なる点は数多くあります。等時性（isochronous）メディアストリームのサポートと転送はその一例です。

2. Scope

2. 範囲

The primary purpose and scope of the memo is to describe key aspects of vSwitch benchmarking, particularly in the areas of test setups and configuration parameters for the system under test, and extend the body of extensive BMWG literature and experience. Initial feedback indicates that many of these extensions may be applicable beyond this memo's current scope (to hardware switches in the NFV infrastructure and to virtual routers, for example). Additionally, this memo serves as a vehicle to include more detail and relevant commentary from BMWG and other open source communities under BMWG's chartered work to characterize the NFV infrastructure.

このメモの主な目的と範囲は、vSwitchのベンチマークの主要な側面を、特にテストのセットアップと被試験システムの設定パラメーターの分野について説明し、BMWGの広範な文献と経験の蓄積を拡張することです。初期のフィードバックによれば、これらの拡張の多くは、このメモの現在の範囲を超えて（たとえば、NFVインフラストラクチャー内のハードウェアスイッチや仮想ルーターにも）適用できる可能性があります。さらに、このメモは、NFVインフラストラクチャーの特性評価を行うというBMWGの憲章に定められた作業のもとで、BMWGやほかのオープンソースコミュニティーからのより詳細な情報や関連する論評を盛り込むための手段にもなります。

The benchmarking covered in this memo should be applicable to many types of vSwitches and remain vSwitch agnostic to a great degree. There has been no attempt to track and test all features of any specific vSwitch implementation.

このメモで扱うベンチマークは、多くの種類のvSwitchに適用でき、かなりの程度までvSwitchに依存しないものであるべきです。特定のvSwitch実装のすべての機能を追跡してテストしようとはしていません。

3. Benchmarking Considerations

3. ベンチマークに関する考慮事項

This section highlights some specific considerations (from [RFC8172]) related to benchmarks for virtual switches. The OPNFV project is sharing its present view on these areas as they develop their specifications in the Level Test Design (LTD) document as defined by [IEEE829].

このセクションでは、仮想スイッチのベンチマークに関連するいくつかの具体的な考慮事項（[RFC8172]より）を取り上げます。OPNFVプロジェクトは、[IEEE829]で定義されているレベルテスト設計（Level Test Design、LTD）文書で仕様を策定しながら、これらの分野に関する現時点での見解を共有しています。

3.1. Comparison with Physical Network Functions

3.1. 物理ネットワーク機能との比較

To compare the performance of virtual designs and implementations with their physical counterparts, identical benchmarks are needed. BMWG has developed specifications for many physical network functions. The BMWG has recommended reusing existing benchmarks and methods in [RFC8172], and the OPNFV LTD expands on them as described here. A key configuration aspect for vSwitches is the number of parallel CPU cores required to achieve comparable performance with a given physical device or whether some limit of scale will be reached before the vSwitch can achieve the comparable performance level.

仮想の設計や実装の性能を、それに対応する物理的なものと比較するには、同一のベンチマークが必要です。BMWGは、多くの物理ネットワーク機能の仕様を策定してきました。BMWGは[RFC8172]で既存のベンチマークと方法を再利用することを推奨しており、OPNFVのLTDは、ここで説明するようにそれらを拡張しています。vSwitchの設定の重要な側面は、ある物理デバイスと同等の性能を達成するために必要な並列CPUコアの数、あるいはvSwitchが同等の性能レベルを達成する前に何らかの規模の限界に達するかどうかです。

It's unlikely that the virtual switch will be the only application running on the SUT, so CPU utilization, cache utilization, and memory footprint should also be recorded for the virtual implementations of internetworking functions. However, internally measured metrics such as these are not benchmarks; they may be useful for the audience (e.g., operations) to know and may also be useful if there is a problem encountered during testing.

仮想スイッチがSUT上で実行される唯一のアプリケーションになる可能性は低いため、インターネットワーキング機能の仮想実装については、CPU使用率、キャッシュ使用率、メモリーフットプリントも記録すべきです。ただし、このような内部で測定されたメトリックはベンチマークではありません。これらは、読者（たとえば運用担当者）が知るのに役立つかもしれず、テスト中に問題が発生した場合にも役立つかもしれません。

Benchmark comparability between virtual and physical/hardware implementations of equivalent functions will likely place more detailed and exact requirements on the "testing systems" (in terms of stream generation, algorithms to search for maximum values, and their configurations). This is another area for standards development to appreciate; however, this is a topic for a future document.

同等の機能の仮想実装と物理／ハードウェア実装の間でベンチマークを比較可能にするには、「テストシステム」に対して、（ストリームの生成、最大値を探索するアルゴリズム、およびそれらの設定の観点で）より詳細かつ厳密な要件を課すことになるでしょう。これも標準の策定において認識すべき分野ですが、これは今後の文書のトピックです。

3.2. Continued Emphasis on Black-Box Benchmarks

3.2. ブラックボックスベンチマークの継続的な重視

External observations remain essential as the basis for benchmarks. Internal observations with a fixed specification and interpretation will be provided in parallel to assist the development of operations procedures when the technology is deployed.

ベンチマークの基盤として、外部からの観測は引き続き不可欠です。固定された仕様と解釈による内部の観測は、その技術が展開されたときの運用手順の策定を支援するために並行して提供されます。

3.3. New Configuration Parameters

3.3. 新しい設定パラメーター

A key consideration when conducting any sort of benchmark is trying to ensure the consistency and repeatability of test results. When benchmarking the performance of a vSwitch, there are many factors that can affect the consistency of results; one key factor is matching the various hardware and software details of the SUT. This section lists some of the many new parameters that this project believes are critical to report in order to achieve repeatability.

どのような種類のベンチマークを実施する場合でも、重要な考慮事項は、テスト結果の一貫性と再現性を確保しようとすることです。vSwitchの性能のベンチマークを行う場合、結果の一貫性に影響を与えうる要因は数多くあります。重要な要因の1つは、SUTのさまざまなハードウェアとソフトウェアの詳細を一致させることです。このセクションでは、再現性を達成するために報告することが重要であるとこのプロジェクトが考える、数多くの新しいパラメーターのいくつかを列挙します。

It has been the goal of the project to produce repeatable results, and a large set of the parameters believed to be critical is provided so that the benchmarking community can better appreciate the increase in configuration complexity inherent in this work. The parameter set below is assumed sufficient for the infrastructure in use by the VSPERF project to obtain repeatable results from test to test.

再現可能な結果を出すことがこのプロジェクトの目標であり、ベンチマークのコミュニティーがこの作業に本質的に伴う設定の複雑さの増大をよりよく理解できるように、重要であると考えられるパラメーターの大きな集合を示します。以下のパラメーターの集合は、VSPERFプロジェクトが使用しているインフラストラクチャーにおいて、テストごとに再現可能な結果を得るのに十分であると想定しています。

Hardware details (platform, processor, memory, and network) including:

ハードウェアの詳細（プラットフォーム、プロセッサー、メモリー、ネットワーク）。次のものを含みます。

  • BIOS version, release date, and any configurations that were modified
  • Power management at all levels (ACPI sleep states, processor package, OS, etc.)
  • CPU microcode level
  • Number of enabled cores
  • Number of cores used for the test
  • Memory information (type and size)
  • Memory DIMM configurations (quad rank performance may not be the same as dual rank) in size, frequency, and slot locations
  • Number of physical NICs and their details (manufacturer, versions, type, and the PCI slot they are plugged into)
  • NIC interrupt configuration (and any special features in use)
  • PCI configuration parameters (payload size, early ACK option, etc.)
  • BIOSのバージョン、リリース日、変更したすべての設定
  • すべてのレベルの電源管理（ACPIのスリープ状態、プロセッサーパッケージ、OSなど）
  • CPUのマイクロコードのレベル
  • 有効になっているコアの数
  • テストに使用するコアの数
  • メモリーの情報（種類と容量）
  • メモリーのDIMM構成（クアッドランクの性能はデュアルランクと同じでないことがあります）。容量、周波数、スロット位置

3.4. Flow Classification

3.4. フローの分類

Virtual switches group packets into flows by processing and matching particular packet or frame header information, or by matching packets based on the input ports. Thus, a flow can be thought of as a sequence of packets that have the same set of header field values or have arrived on the same physical or logical port. Performance results can vary based on the parameters the vSwitch uses to match for a flow. The recommended flow classification parameters for any vSwitch performance tests are: the input port (physical or logical), the source MAC address, the destination MAC address, the source IP address, the destination IP address, and the Ethernet protocol type field (although classification may take place on other fields, such as source and destination transport port numbers). It is essential to increase the flow timeout time on a vSwitch before conducting any performance tests that do not intend to measure the flow setup time (see Section 3 of [RFC2889]). Normally, the first packet of a particular stream will install the flow in the virtual switch, which introduces additional latency; subsequent packets of the same flow are not subject to this latency if the flow is already installed on the vSwitch.

仮想スイッチは、パケットやフレームのヘッダーの特定の情報を処理して照合することで、または入力ポートに基づいてパケットを照合することで、パケットをフローにグループ化します。したがって、フローは、ヘッダーフィールドの値の集合が同じであるパケット、または同じ物理ポートか論理ポートに到着したパケットの並びと考えることができます。性能の結果は、vSwitchがフローの照合に使用するパラメーターによって変わる可能性があります。vSwitchの性能テストで推奨されるフロー分類パラメーターは、入力ポート（物理または論理）、送信元MACアドレス、宛先MACアドレス、送信元IPアドレス、宛先IPアドレス、イーサネットのプロトコルタイプフィールドです（ただし、送信元と宛先のトランスポートポート番号など、ほかのフィールドで分類が行われることもあります）。フローのセットアップ時間を測定することを意図しない性能テストを実施する前に、vSwitchのフローのタイムアウト時間を長くすることが不可欠です（[RFC2889]のセクション3を参照してください）。通常、特定のストリームの最初のパケットが仮想スイッチにフローをインストールし、これによってレイテンシーが追加されます。同じフローの後続のパケットは、そのフローがすでにvSwitchにインストールされていれば、このレイテンシーの影響を受けません。

The metrics gathered from this test will serve as a key comparison point for vSwitch bypass technologies performance and vSwitch performance.

    • Benchmarking with isolated resources alone and with other resources (both hardware and software) disabled; for example, vSwitch and VM are SUT.
    • Benchmarking with isolated resources alone, thus leaving some resources unused.

  2. Next Steps:

    • Limited sharing
    • Production scenarios

  1. ベースライン：

4. VSPERF Specification Summary

4. VSPERFの仕様の概要

The overall specification in preparation is referred to as a Level Test Design (LTD) document, which will contain a suite of performance tests. The base performance tests in the LTD are based on the pre-existing specifications developed by the BMWG to test the performance of physical switches. These specifications include:

準備中の仕様全体はレベルテスト設計（LTD）文書と呼ばれ、一連の性能テストを含む予定です。LTDの基本的な性能テストは、物理スイッチの性能をテストするためにBMWGが策定した既存の仕様に基づいています。これらの仕様には次のものがあります。

  • Benchmarking Methodology for Network Interconnect Devices [RFC2544]
  • Benchmarking Methodology for LAN Switching [RFC2889]
  • Device Reset Characterization [RFC6201]
  • Packet Delay Variation Applicability Statement [RFC5481]
  • Benchmarking Methodology for Network Interconnect Devices（ネットワーク相互接続デバイスのベンチマーク方法論）[RFC2544]
  • Benchmarking Methodology for LAN Switching（LANスイッチングのベンチマーク方法論）[RFC2889]
  • Device Reset Characterization（デバイスのリセットの特性評価）[RFC6201]
  • Packet Delay Variation Applicability Statement（パケット遅延変動の適用性に関する声明）[RFC5481]

The two most recent RFCs above ([RFC6201] and [RFC5481]) are being applied in benchmarking for the first time and represent a development challenge for test equipment developers. Fortunately, many members of the testing system community have engaged on the VSPERF project, including an open source test system.

上記のうち最も新しい2つのRFC（[RFC6201]と[RFC5481]）は、ベンチマークに初めて適用されるものであり、テスト機器の開発者にとって開発上の課題となります。幸いなことに、オープンソースのテストシステムを含め、テストシステムのコミュニティーの多くのメンバーがVSPERFプロジェクトに参加しています。

In addition to this, the LTD also reuses the terminology defined by:

これに加えて、LTDは次の文書で定義されている用語も再利用しています。

  • Benchmarking Terminology for LAN Switching Devices [RFC2285]
  • Benchmarking Terminology for LAN Switching Devices（LANスイッチングデバイスのベンチマークの用語）[RFC2285]

It is recommended that these references be included in future benchmarking specifications:

今後のベンチマークの仕様には、次の参考文献を含めることを推奨します。

  • Methodology for IP Multicast Benchmarking [RFC3918]
  • Packet Reordering Metrics [RFC4737]
  • Methodology for IP Multicast Benchmarking（IPマルチキャストのベンチマークの方法論）[RFC3918]
  • Packet Reordering Metrics（パケットの順序入れ替わりのメトリック）[RFC4737]

As one might expect, the most fundamental internetworking characteristics of throughput and latency remain important when the switch is virtualized, and these benchmarks figure prominently in the specification.

予想されるとおり、スイッチが仮想化されても、スループットとレイテンシーという最も基本的なインターネットワーキングの特性は依然として重要であり、これらのベンチマークは仕様の中で大きな位置を占めています。

When considering characteristics important to "telco" network functions, additional performance metrics are needed. In this case, the project specifications have referenced metrics from the IETF IP Performance Metrics (IPPM) literature. This means that the latency test described in [RFC2544] is replaced by measurement of a metric derived from IPPM's [RFC7679], where a set of statistical summaries will be provided (mean, max, min, and percentiles). Further metrics planned to be benchmarked include packet delay variation as defined by [RFC5481], reordering, burst behaviour, DUT availability, DUT capacity, and packet loss in long-term testing at the throughput level, where some low level of background loss may be present and characterized.

「telco」（通信事業者）のネットワーク機能にとって重要な特性を考慮すると、追加の性能メトリックが必要です。この場合、プロジェクトの仕様では、IETFのIP性能メトリック（IP Performance Metrics、IPPM）の文献のメトリックを参照しています。これは、[RFC2544]で説明されているレイテンシーのテストを、IPPMの[RFC7679]から派生したメトリックの測定に置き換え、統計的な要約の集合（平均、最大、最小、パーセンタイル）を提供するということです。ベンチマークを予定しているさらなるメトリックには、[RFC5481]で定義されているパケット遅延変動、順序の入れ替わり、バーストの挙動、DUTの可用性、DUTの容量、そしてスループットのレベルでの長期テストにおけるパケット損失があります。長期テストでは、低いレベルのバックグラウンドの損失が存在し、その特性が評価される場合があります。

Tests have been designed to collect the metrics below:

以下のメトリックを収集するテストが設計されています。

  • Throughput tests are designed to measure the maximum forwarding rate (in frames per second, fps) and bit rate (in Mbps) for a constant load (as defined by [RFC1242]) without traffic loss.
  • Packet and frame-delay distribution tests are designed to measure the average minimum and maximum packet (and/or frame) delay for constant loads.
  • Packet delay tests are designed to understand latency distribution for different packet sizes and to uncover outliers over an extended test run.
  • Scalability tests are designed to understand how the virtual switch performs with an increasing number of flows, number of active ports, configuration complexity of the forwarding logic, etc.
  • Stream performance tests (with TCP or UDP) are designed to measure bulk data transfer performance, i.e., how fast systems can send and receive data through the switch.
  • Control-path and data-path coupling tests are designed to understand how closely the data path and the control path are coupled, as well as the effect of this coupling on the performance of the DUT (for example, delay of the initial packet of a flow).
  • CPU and memory consumption tests are designed to understand the virtual switch's footprint on the system and are conducted as auxiliary measurements with the benchmarks above. They include CPU utilization, cache utilization, and memory footprint.
  • The so-called "soak" tests, where the selected test is conducted over a long period of time (with an ideal duration of 24 hours but only long enough to determine that stability issues exist when found; there is no requirement to continue a test when a DUT exhibits instability over time). The key performance characteristics and benchmarks for a DUT are determined (using short duration tests) prior to conducting soak tests. The purpose of soak tests is to capture transient changes in performance, which may occur due to infrequent processes, memory leaks, or the low-probability coincidence of two or more processes. The stability of the DUT is the paramount consideration, so performance must be evaluated periodically during continuous testing, and this results in use of frame rate metrics [RFC2889] instead of throughput [RFC2544] (which requires stopping traffic to allow time for all traffic to exit internal queues), for example.
  • スループットテストは、一定負荷（[RFC1242]で定義されているもの）において、トラフィックの損失なしで最大の転送レート（フレーム毎秒、fps）とビットレート（Mbps）を測定するように設計されています。
  • パケットとフレームの遅延分布のテストは、一定負荷におけるパケット（および／またはフレーム）の平均、最小、最大の遅延を測定するように設計されています。
  • パケット遅延のテストは、さまざまなパケットサイズのレイテンシー分布を把握し、長時間のテスト実行における外れ値を明らかにするように設計されています。
  • スケーラビリティーのテストは、フローの数、アクティブなポートの数、転送ロジックの設定の複雑さなどが増加するにつれて、仮想スイッチがどのように動作するかを把握するように設計されています。
  • ストリーム性能のテスト（TCPまたはUDPによる）は、バルクデータの転送性能、つまりシステムがスイッチを介してどれだけ速くデータを送受信できるかを測定するように設計されています。
  • コントロールパスとデータパスの結合のテストは、データパスとコントロールパスがどの程度密に結合しているか、およびこの結合がDUTの性能に与える影響（たとえば、フローの最初のパケットの遅延）を把握するように設計されています。
  • CPUとメモリーの消費のテストは、システム上での仮想スイッチのフットプリントを把握するように設計されており、上記のベンチマークとともに補助的な測定として実施されます。これには、CPU使用率、キャッシュ使用率、メモリーフットプリントが含まれます。
  • いわゆる「ソーク（soak）」テスト。これは、選択したテストを長期間にわたって実施するものです（理想的な継続時間は24時間ですが、安定性の問題が見つかった場合にその存在を確認できるだけの長さがあれば十分です。DUTが時間の経過とともに不安定さを示した場合に、テストを継続する必要はありません）。DUTの主要な性能特性とベンチマークは、ソークテストを実施する前に（短時間のテストを使用して）決定します。ソークテストの目的は、まれにしか動作しないプロセス、メモリーリーク、2つ以上のプロセスが低い確率で同時に発生することなどによって生じる可能性のある、性能の一時的な変化を捉えることです。DUTの安定性が最も重要な考慮事項であるため、継続的なテスト中に性能を定期的に評価する必要があります。その結果、たとえば、スループット[RFC2544]（すべてのトラフィックが内部のキューから出るまでの時間を確保するためにトラフィックを停止する必要があります）の代わりに、フレームレートのメトリック[RFC2889]を使用することになります。

Additional test specification development should include:

今後のテスト仕様の策定には、次のものを含めるべきです。

  • Request/response performance tests (with TCP or UDP), which measure the transaction rate through the switch.
  • Noisy neighbor tests, in order to understand the effects of resource sharing on the performance of a virtual switch.
  • Tests derived from examination of ETSI NFV Draft GS IFA003 requirements [IFA003] on characterization of acceleration technologies applied to vSwitches.
  • リクエスト／レスポンスの性能テスト（TCPまたはUDPによる）。これは、スイッチを介したトランザクションレートを測定します。
  • ノイジーネイバー（noisy neighbor）のテスト。リソースの共有が仮想スイッチの性能に与える影響を把握するためのものです。
  • vSwitchに適用される高速化技術の特性評価に関するETSI NFVのDraft GS IFA003の要件[IFA003]を検討して導き出されたテスト。

The flexibility of deployment of a virtual switch within a network means that it is necessary to characterize the performance of a vSwitch in various deployment scenarios. The deployment scenarios under consideration are shown in the following figures:

6. Security Considerations

6. セキュリティーに関する考慮事項

Benchmarking activities as described in this memo are limited to technology characterization of a Device Under Test/System Under Test (DUT/SUT) using controlled stimuli in a laboratory environment with dedicated address space and the constraints specified in the sections above.

このメモで説明するベンチマーク活動は、専用のアドレス空間と上記のセクションで規定した制約のもと、実験室環境で制御された刺激を用いて行う被試験デバイス／被試験システム（DUT/SUT）の技術の特性評価に限定されます。

The benchmarking network topology will be an independent test setup and MUST NOT be connected to devices that may forward the test traffic into a production network or misroute traffic to the test management network.

ベンチマークのネットワークトポロジーは独立したテスト環境であり、テストトラフィックを本番ネットワークに転送したり、トラフィックをテスト管理ネットワークに誤ってルーティングしたりする可能性のあるデバイスに接続してはなりません（MUST NOT）。

Further, benchmarking is performed on a "black-box" basis and relies solely on measurements observable external to the DUT/SUT.

さらに、ベンチマークは「ブラックボックス」ベースで実施され、DUT/SUTの外部から観測可能な測定のみに依存します。

Special capabilities SHOULD NOT exist in the DUT/SUT specifically for benchmarking purposes. Any implications for network security arising from the DUT/SUT SHOULD be identical in the lab and in production networks.

ベンチマークの目的に特化した特別な機能がDUT/SUTに存在すべきではありません（SHOULD NOT）。DUT/SUTに起因するネットワークセキュリティーへの影響は、実験室でも本番ネットワークでも同一であるべきです（SHOULD）。
