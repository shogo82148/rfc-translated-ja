RFC 8408

Conveying Path Setup Type in PCE Communication Protocol (PCEP) Messages

RFC 8408

PCE通信プロトコル（PCEP）メッセージでのパス設定タイプの伝達

Abstract

概要

A Path Computation Element (PCE) can compute Traffic Engineering (TE) paths through a network; these paths are subject to various constraints. Currently, TE paths are Label Switched Paths (LSPs) that are set up using the RSVP-TE signaling protocol. However, other TE path setup methods are possible within the PCE architecture. This document proposes an extension to the PCE Communication Protocol (PCEP) to allow support for different path setup methods over a given PCEP session.

パス計算要素（PCE: Path Computation Element）は、ネットワークを通るトラフィックエンジニアリング（TE）パスを計算できます。これらのパスにはさまざまな制約が課されます。現在、TEパスは、RSVP-TEシグナリングプロトコルを使って設定されるラベルスイッチパス（LSP）です。しかし、PCEアーキテクチャーでは、ほかのTEパス設定方法も可能です。この文書は、PCE通信プロトコル（PCEP）の拡張を提案し、あるPCEPセッション上で異なるパス設定方法をサポートできるようにします。

1. Introduction

1. はじめに

[RFC5440] describes the PCE Communication Protocol (PCEP) for communication between a Path Computation Client (PCC) and a Path Computation Element (PCE) or between a PCE and a PCE. A PCC requests, from a PCE, a path subject to various constraints and optimization criteria. The PCE responds to the PCC with a hop-by-hop path in an Explicit Route Object (ERO). The PCC uses the ERO to set up the path in the network.

[RFC5440]は、パス計算クライアント（PCC: Path Computation Client）とパス計算要素（PCE）との間、またはPCEとPCEとの間の通信のためのPCE通信プロトコル（PCEP）を記述しています。PCCは、さまざまな制約と最適化基準に従うパスをPCEに要求します。PCEは、明示的経路オブジェクト（ERO: Explicit Route Object）にホップバイホップのパスを入れてPCCに応答します。PCCはEROを使って、ネットワーク内にパスを設定します。

[RFC8231] specifies extensions to PCEP that allow a PCC to delegate its LSPs to a PCE. The PCE can then update the state of LSPs delegated to it. In particular, the PCE may modify the path of an LSP by sending a new ERO. The PCC uses this ERO to reroute the LSP in a make-before-break fashion. [RFC8281] specifies a mechanism that allows a PCE to dynamically instantiate an LSP on a PCC by sending the ERO and the characteristics of the LSP. The PCC creates the LSP using the ERO and other attributes sent by the PCE.

[RFC8231]は、PCCが自身のLSPをPCEに委任できるようにするPCEPの拡張を規定しています。これにより、PCEは自身に委任されたLSPの状態を更新できます。特に、PCEは新しいEROを送ることでLSPのパスを変更することがあります。PCCはこのEROを使って、メイクビフォアブレイク（make-before-break）方式でLSPを再ルーティングします。[RFC8281]は、PCEがEROとLSPの特性を送ることで、PCC上にLSPを動的にインスタンス化できるようにするメカニズムを規定しています。PCCは、EROと、PCEから送られたその他の属性を使ってLSPを作成します。

So far, PCEP and its extensions have assumed that the TE paths are label switched and are established via the RSVP-TE signaling protocol. However, other methods of LSP setup are possible in the PCE architecture (see [RFC4655] and [RFC4657]). This document generalizes PCEP to allow other LSP setup methods to be used. It defines two new TLVs and specifies the base procedures to facilitate this:

これまで、PCEPとその拡張は、TEパスがラベルスイッチされ、RSVP-TEシグナリングプロトコルによって確立されることを前提としてきました。しかし、PCEアーキテクチャーでは、ほかのLSP設定方法も可能です（[RFC4655]と[RFC4657]を参照）。この文書は、ほかのLSP設定方法を使えるようにPCEPを一般化します。この文書は、これを実現するために、2つの新しいTLVを定義し、基本的な手順を規定します。

  • The PATH-SETUP-TYPE-CAPABILITY TLV allows a PCEP speaker to announce which LSP setup methods it supports when the PCEP session is established.
  • The PATH-SETUP-TYPE TLV allows a PCEP speaker to specify which setup method should be used for a given LSP. When multiple path setup types are deployed in a network, a given PCEP session may have to simultaneously support more than one path setup type. A PCEP speaker uses the PATH-SETUP-TYPE TLV to explicitly indicate the intended path setup type in the appropriate PCEP messages, unless the path setup type is RSVP-TE (which is assumed to be the path setup type if no other setup type is indicated). This is so that both the PCC and the PCE can take the necessary steps to set up the path.
  • PATH-SETUP-TYPE-CAPABILITY TLVにより、PCEPスピーカーは、PCEPセッションの確立時に、自身がサポートするLSP設定方法を通知できます。
  • PATH-SETUP-TYPE TLVにより、PCEPスピーカーは、あるLSPにどの設定方法を使うべきかを指定できます。ネットワークに複数のパス設定タイプが展開されている場合、あるPCEPセッションが複数のパス設定タイプを同時にサポートしなければならないことがあります。PCEPスピーカーは、パス設定タイプがRSVP-TEである場合（ほかの設定タイプが示されていなければ、パス設定タイプはRSVP-TEであるとみなされます）を除き、適切なPCEPメッセージ内でPATH-SETUP-TYPE TLVを使って、意図するパス設定タイプを明示的に示します。これは、PCCとPCEの両方が、パスの設定に必要な手順を取れるようにするためです。

This document defines a path setup type code for RSVP-TE. When a new path setup type (other than RSVP-TE) is introduced for setting up a path, a path setup type code and, optionally, a sub-TLV pertaining to the new path setup type will be defined by the document that specifies the new path setup type.

この文書は、RSVP-TE用のパス設定タイプコードを定義します。パスを設定するために（RSVP-TE以外の）新しいパス設定タイプを導入する場合、パス設定タイプコードと、必要に応じてその新しいパス設定タイプに関するサブTLVは、その新しいパス設定タイプを規定する文書で定義されます。

3. Path Setup Type Capability TLV

3. パス設定タイプ能力TLV

A PCEP speaker indicates which PSTs it supports during the PCEP initialization phase using the following process. When the PCEP session is created, it sends an Open message with an OPEN object containing the PATH-SETUP-TYPE-CAPABILITY TLV. The format of this TLV is as follows.

PCEPスピーカーは、PCEPの初期化フェーズの間に、次の手順で自身がサポートするPSTを示します。PCEPセッションが作成されると、PCEPスピーカーは、PATH-SETUP-TYPE-CAPABILITY TLVを含むOPENオブジェクトを持つOpenメッセージを送信します。このTLVの形式は次のとおりです。

The TLV Type is 34. Its Reserved field MUST be set to zero by the sender and MUST be ignored by the receiver. The other fields in the TLV are as follows.

このTLVのタイプは34です。Reservedフィールドは、送信者がゼロに設定しなければなりません（MUST）。また、受信者はこれを無視しなければなりません（MUST）。TLVのその他のフィールドは次のとおりです。

Length:
The total length in bytes of the remainder of the TLV, that is, excluding the Type and Length fields.
Num of PSTs:
The number of PSTs in the following list, excluding padding.
List of PSTs:

A list of the PSTs that the PCEP speaker supports. Each PST is a single byte in length. Duplicate entries in this list MUST be ignored. The PCEP speaker MUST pad the list with zeros so that it is a multiple of four bytes in length. This document defines the following PST value:

  • PST = 0: Path is set up using the RSVP-TE signaling protocol
Optional sub-TLVs:
A list of sub-TLVs associated with the supported PSTs. Each PST has zero or one sub-TLVs associated with it, and each sub-TLV is associated with exactly one PST. Each sub-TLV MUST obey the rules for TLV formatting defined in [RFC5440]. That is, each sub-TLV is padded to a four-byte alignment, and the Length field of each sub-TLV does not include the padding bytes. This document does not define any sub-TLVs; an example sub-TLV can be found in [PCEP-EXTENSIONS].
Length:
TLVの残りの部分、つまりTypeフィールドとLengthフィールドを除いた部分の合計長（バイト単位）。
Num of PSTs:
後に続くリスト内のPSTの数。パディングは含みません。
List of PSTs:

PCEPスピーカーがサポートするPSTのリスト。各PSTの長さは1バイトです。このリスト内の重複したエントリーは無視しなければなりません（MUST）。PCEPスピーカーは、リストの長さが4バイトの倍数になるようにゼロでパディングしなければなりません（MUST）。この文書は、次のPST値を定義します。

  • PST = 0: パスはRSVP-TEシグナリングプロトコルを使って設定されます
Optional sub-TLVs:
サポートするPSTに関連付けられたサブTLVのリスト。各PSTには0個または1個のサブTLVが関連付けられ、各サブTLVはちょうど1つのPSTに関連付けられます。各サブTLVは、[RFC5440]で定義されているTLVの書式の規則に従わなければなりません（MUST）。つまり、各サブTLVは4バイト境界にそろうようにパディングされ、各サブTLVのLengthフィールドにはパディングのバイトは含まれません。この文書はサブTLVを定義しません。サブTLVの例は[PCEP-EXTENSIONS]にあります。

A PCEP speaker MUST check that this TLV is correctly formatted, as follows.

PCEPスピーカーは、次のとおり、このTLVの形式が正しいことを確認しなければなりません（MUST）。

  • If there are no sub-TLVs, then the TLV Length field MUST be equal to four bytes plus the size of the PST list, excluding any padding bytes.
  • If there are sub-TLVs, then the TLV Length field MUST be equal to four bytes plus the size of the PST list (rounded up to the nearest multiple of four) plus the size of the appended sub-TLVs, excluding any padding bytes in the final sub-TLV.
  • The Num of PSTs field MUST be greater than zero.
  • サブTLVがない場合、TLVのLengthフィールドは、4バイトにPSTリストのサイズ（パディングのバイトを除く）を加えた値に等しくなければなりません（MUST）。
  • サブTLVがある場合、TLVのLengthフィールドは、4バイトに、PSTリストのサイズ（4の倍数に切り上げたもの）と、後に付加されたサブTLVのサイズ（最後のサブTLVのパディングのバイトを除く）を加えた値に等しくなければなりません（MUST）。
  • Num of PSTsフィールドはゼロより大きくなければなりません（MUST）。

If a PCEP speaker receives a PATH-SETUP-TYPE-CAPABILITY TLV that violates these rules, then the PCEP speaker MUST send a PCErr message with Error-Type = 10 (Reception of an invalid object) and Error-value = 11 (Malformed object) and MUST close the PCEP session. The PCEP speaker MAY include the malformed OPEN object in the PCErr message as well.

PCEPスピーカーは、これらの規則に違反するPATH-SETUP-TYPE-CAPABILITY TLVを受信した場合、Error-Type = 10（Reception of an invalid object）とError-value = 11（Malformed object）を持つPCErrメッセージを送信しなければなりません（MUST）。また、PCEPセッションを閉じなければなりません（MUST）。PCEPスピーカーは、不正な形式のOPENオブジェクトをPCErrメッセージに含めてもよいです（MAY）。

If a PCEP speaker receives an OPEN object with more than one PATH-SETUP-TYPE-CAPABILITY TLV, then it MUST ignore all but the first instance of this TLV.

PCEPスピーカーは、複数のPATH-SETUP-TYPE-CAPABILITY TLVを持つOPENオブジェクトを受信した場合、このTLVの最初のインスタンス以外をすべて無視しなければなりません（MUST）。

The absence of the PATH-SETUP-TYPE-CAPABILITY TLV from the OPEN object is equivalent to a PATH-SETUP-TYPE-CAPABILITY TLV containing a single PST value of 0 (Path is set up using the RSVP-TE signaling protocol) and no sub-TLVs. A PCEP speaker MAY omit the PATH-SETUP-TYPE-CAPABILITY TLV if the only PST it supports is RSVP-TE. If a PCEP speaker supports other PSTs besides RSVP-TE, then it SHOULD include the PATH-SETUP-TYPE-CAPABILITY TLV in its OPEN object.

OPENオブジェクトにPATH-SETUP-TYPE-CAPABILITY TLVがないことは、単一のPST値0（パスはRSVP-TEシグナリングプロトコルを使って設定されます）を含み、サブTLVを含まないPATH-SETUP-TYPE-CAPABILITY TLVがあることと同等です。PCEPスピーカーは、サポートするPSTがRSVP-TEだけの場合、PATH-SETUP-TYPE-CAPABILITY TLVを省略してもよいです（MAY）。PCEPスピーカーがRSVP-TE以外のPSTもサポートする場合、PCEPスピーカーは、OPENオブジェクトにPATH-SETUP-TYPE-CAPABILITY TLVを含めるべきです（SHOULD）。

If a PCEP speaker does not recognize the PATH-SETUP-TYPE-CAPABILITY TLV, it will ignore the TLV in accordance with [RFC5440].

PCEPスピーカーは、PATH-SETUP-TYPE-CAPABILITY TLVを認識しない場合、[RFC5440]に従ってそのTLVを無視します。

4. Path Setup Type TLV

4. パス設定タイプTLV

When a PCEP session is used to set up TE paths using different methods, the corresponding PCE and PCC must be aware of the path setup method used. This means that a PCE must be able to specify paths in the correct format, and a PCC must be able to take control-plane and forwarding-plane actions appropriate to the PST.

PCEPセッションを使って異なる方法でTEパスを設定する場合、対応するPCEとPCCは、使われるパス設定方法を認識している必要があります。つまり、PCEは正しい形式でパスを指定できる必要があり、PCCはPSTに適したコントロールプレーンと転送プレーンの動作を取れる必要があります。

The PATH-SETUP-TYPE TLV is an optional TLV associated with the Request Parameters (RP) [RFC5440] and the Stateful PCE Request Parameters (SRP) [RFC8231] objects. Its format is shown in Figure 2. The TLV type is 28. Its Reserved field MUST be set to zero. The one-byte PST field contains the PST as defined for the PATH-SETUP-TYPE-CAPABILITY TLV.

PATH-SETUP-TYPE TLVは、リクエストパラメーター（RP: Request Parameters）オブジェクト[RFC5440]とステートフルPCEリクエストパラメーター（SRP: Stateful PCE Request Parameters）オブジェクト[RFC8231]に関連付けられる任意のTLVです。その形式を図2に示します。このTLVのタイプは28です。Reservedフィールドはゼロに設定しなければなりません（MUST）。1バイトのPSTフィールドには、PATH-SETUP-TYPE-CAPABILITY TLVについて定義したPSTが入ります。

The absence of the PATH-SETUP-TYPE TLV is equivalent to a PATH-SETUP-TYPE TLV with a PST value of 0 (Path is set up using the RSVP-TE signaling protocol). A PCEP speaker MAY omit the TLV if the PST is RSVP-TE. If the RP or SRP object contains more than one PATH-SETUP-TYPE TLV, only the first TLV MUST be processed, and the rest MUST be ignored.

PATH-SETUP-TYPE TLVがないことは、PST値が0（パスはRSVP-TEシグナリングプロトコルを使って設定されます）のPATH-SETUP-TYPE TLVがあることと同等です。PCEPスピーカーは、PSTがRSVP-TEである場合、このTLVを省略してもよいです（MAY）。RPオブジェクトまたはSRPオブジェクトに複数のPATH-SETUP-TYPE TLVが含まれている場合、最初のTLVだけを処理しなければなりません（MUST）。残りのTLVは無視しなければなりません（MUST）。

If a PCEP speaker does not recognize the PATH-SETUP-TYPE TLV, it will ignore the TLV in accordance with [RFC5440] and use RSVP-TE to set up the path.

PCEPスピーカーは、PATH-SETUP-TYPE TLVを認識しない場合、[RFC5440]に従ってそのTLVを無視し、RSVP-TEを使ってパスを設定します。

5. Operation

5. 動作

During the PCEP initialization phase, if a PCEP speaker receives a PATH-SETUP-TYPE-CAPABILITY TLV from its peer, it MUST assume that the peer supports only the PSTs listed in the TLV. If the PCEP speaker and its peer have no PSTs in common, then the PCEP speaker MUST send a PCErr message with Error-Type = 21 (Invalid traffic engineering path setup type) and Error-value = 2 (Mismatched path setup type) and close the PCEP session.

PCEPの初期化フェーズの間に、PCEPスピーカーがピアからPATH-SETUP-TYPE-CAPABILITY TLVを受信した場合、PCEPスピーカーは、ピアがそのTLVに列挙されたPSTだけをサポートするとみなさなければなりません（MUST）。PCEPスピーカーとそのピアに共通するPSTがない場合、PCEPスピーカーは、Error-Type = 21（Invalid traffic engineering path setup type）とError-value = 2（Mismatched path setup type）を持つPCErrメッセージを送信し、PCEPセッションを閉じなければなりません（MUST）。

If the peer has sent no PATH-SETUP-TYPE-CAPABILITY TLV, then the PCEP speaker MUST infer that the peer supports path setup using at least RSVP-TE. The PCEP speaker MAY also infer that the peer supports other path setup types, but the means of inference are outside the scope of this document.

ピアがPATH-SETUP-TYPE-CAPABILITY TLVを送信していない場合、PCEPスピーカーは、ピアが少なくともRSVP-TEを使ったパス設定をサポートしていると推測しなければなりません（MUST）。PCEPスピーカーは、ピアがほかのパス設定タイプもサポートしていると推測してもよいです（MAY）が、その推測の手段はこの文書の範囲外です。

When a PCC sends a PCReq message to a PCE [RFC5440], it MUST include the PATH-SETUP-TYPE TLV in the RP object, unless the intended PST is RSVP-TE (in which case it MAY omit the PATH-SETUP-TYPE TLV). If the PCE is capable of expressing the path in a format appropriate to the intended PST, it MUST use the appropriate ERO format in the PCRep message.

PCCは、PCEにPCReqメッセージ[RFC5440]を送信するとき、意図するPSTがRSVP-TEである場合（この場合、PATH-SETUP-TYPE TLVを省略してもよいです（MAY））を除き、RPオブジェクトにPATH-SETUP-TYPE TLVを含めなければなりません（MUST）。PCEは、意図するPSTに適した形式でパスを表現できる場合、PCRepメッセージで適切なERO形式を使用しなければなりません（MUST）。

When a PCE sends a PCRep message to a PCC [RFC5440], it MUST include the PATH-SETUP-TYPE TLV in the RP object, unless the PST is RSVP-TE (in which case it MAY omit the PATH-SETUP-TYPE TLV). If the PCE does not support the intended PST, it MUST send a PCErr message with Error-Type = 21 (Invalid traffic engineering path setup type) and Error-value = 1 (Unsupported path setup type) and close the PCEP session. If the PSTs corresponding to the PCReq and PCRep messages do not match, the PCC MUST send a PCErr message with Error-Type = 21 (Invalid traffic engineering path setup type) and Error-value = 2 (Mismatched path setup type) and close the PCEP session.

PCEは、PCCにPCRepメッセージ[RFC5440]を送信するとき、PSTがRSVP-TEである場合（この場合、PATH-SETUP-TYPE TLVを省略してもよいです（MAY））を除き、RPオブジェクトにPATH-SETUP-TYPE TLVを含めなければなりません（MUST）。PCEは、意図されたPSTをサポートしていない場合、Error-Type = 21（Invalid traffic engineering path setup type）とError-value = 1（Unsupported path setup type）を持つPCErrメッセージを送信し、PCEPセッションを閉じなければなりません（MUST）。PCReqメッセージとPCRepメッセージに対応するPSTが一致しない場合、PCCは、Error-Type = 21（Invalid traffic engineering path setup type）とError-value = 2（Mismatched path setup type）を持つPCErrメッセージを送信し、PCEPセッションを閉じなければなりません（MUST）。

When a stateful PCE sends a PCUpd message [RFC8231] or a PCInitiate message [RFC8281] to a PCC, it MUST include the PATH-SETUP-TYPE TLV in the SRP object, unless the intended PST is RSVP-TE (in which case it MAY omit the PATH-SETUP-TYPE TLV). If the PCC does not support the PST associated with the PCUpd or PCInitiate message, it MUST send a PCErr message with Error-Type = 21 (Invalid traffic engineering path setup type) and Error-value = 1 (Unsupported path setup type) and close the PCEP session.

ステートフルPCEは、PCCにPCUpdメッセージ[RFC8231]またはPCInitiateメッセージ[RFC8281]を送信するとき、意図するPSTがRSVP-TEである場合（この場合、PATH-SETUP-TYPE TLVを省略してもよいです（MAY））を除き、SRPオブジェクトにPATH-SETUP-TYPE TLVを含めなければなりません（MUST）。PCCは、PCUpdメッセージまたはPCInitiateメッセージに関連付けられたPSTをサポートしていない場合、Error-Type = 21（Invalid traffic engineering path setup type）とError-value = 1（Unsupported path setup type）を持つPCErrメッセージを送信し、PCEPセッションを閉じなければなりません（MUST）。

When a PCC sends a PCRpt message to a stateful PCE [RFC8231], it MUST include the PATH-SETUP-TYPE TLV in the SRP object, unless the PST is RSVP-TE (in which case it MAY omit the PATH-SETUP-TYPE TLV). The PCC MUST include the SRP object in the PCRpt message if the PST is not RSVP-TE, even when the SRP-ID-number is the reserved value of 0x00000000. If the PCRpt message is triggered by a PCUpd or PCInitiate message, then the PST that the PCC indicates in the PCRpt message MUST match the PST that the stateful PCE intended in the PCUpd or PCInitiate message. If it does not match, then the PCE MUST send a PCErr message with Error-Type = 21 (Invalid traffic engineering path setup type) and Error-value = 2 (Mismatched path setup type) and close the PCEP session.

PCCは、ステートフルPCEにPCRptメッセージ[RFC8231]を送信するとき、PSTがRSVP-TEである場合（この場合、PATH-SETUP-TYPE TLVを省略してもよいです（MAY））を除き、SRPオブジェクトにPATH-SETUP-TYPE TLVを含めなければなりません（MUST）。PSTがRSVP-TEでない場合、PCCは、SRP-ID-numberが予約済みの値0x00000000であっても、PCRptメッセージにSRPオブジェクトを含めなければなりません（MUST）。PCRptメッセージがPCUpdメッセージまたはPCInitiateメッセージを契機として送られる場合、PCCがPCRptメッセージで示すPSTは、ステートフルPCEがPCUpdメッセージまたはPCInitiateメッセージで意図したPSTと一致しなければなりません（MUST）。一致しない場合、PCEは、Error-Type = 21（Invalid traffic engineering path setup type）とError-value = 2（Mismatched path setup type）を持つPCErrメッセージを送信し、PCEPセッションを閉じなければなりません（MUST）。

6. Manageability Considerations

6. 管理性に関する考慮事項

This document generalizes PCEP to allow path setup methods other than RSVP-TE to be used by the network (but does not define any new path setup types besides RSVP-TE). It is possible that, in a given network, multiple path setup methods will be used. It is also possible that not all devices will support the same set of path setup methods. Managing networks that combine multiple path setup methods may therefore raise some challenges from a configuration and observability point of view.

この文書は、ネットワークがRSVP-TE以外のパス設定方法を使えるようにPCEPを一般化します（ただし、RSVP-TE以外の新しいパス設定タイプは定義しません）。あるネットワークでは、複数のパス設定方法が使われる可能性があります。また、すべての装置が同じパス設定方法の集合をサポートするとは限りません。そのため、複数のパス設定方法を組み合わせたネットワークを管理する際には、設定と可観測性の観点からいくつかの課題が生じる可能性があります。

Each document that defines a new path setup type in the "PCEP Path Setup Types" registry (Section 8.2) must include a Manageability Considerations section. The Manageability Considerations section must explain how operators can manage PCEP with the new path setup type. It must address the following questions, which are generally applicable when working with multiple path setup types in PCEP.

「PCEP Path Setup Types」レジストリー（セクション8.2）で新しいパス設定タイプを定義する各文書には、管理性に関する考慮事項のセクションが含まれていなければなりません。管理性に関する考慮事項のセクションでは、運用者が新しいパス設定タイプでPCEPをどのように管理できるかを説明しなければなりません。このセクションでは、次の問いに答えなければなりません。これらは、PCEPで複数のパス設定タイプを扱う際に一般的に当てはまるものです。

  • What are the criteria for when devices will use the new path setup type in PCEP, and how can the operator control this?
  • How can the network be migrated to the new path setup type, and are there any backwards-compatibility issues that operators need to be aware of?
  • Are paths set up using the new path setup type intended to coexist with other paths over the long term, and if so, how is this situation managed with PCEP?
  • How can operators verify the correct operation of PCEP in the network with respect to the new path setup type? Which fault conditions must be reported to the operators?
  • Are there any existing management interfaces (such as YANG models) that must be extended to model the operation of PCEP in the network with respect to the new path setup type?
  • 装置がPCEPで新しいパス設定タイプを使う基準は何か、また運用者はそれをどのように制御できるか。
  • ネットワークを新しいパス設定タイプにどのように移行できるか、また運用者が認識しておく必要のある後方互換性の問題はあるか。
  • 新しいパス設定タイプを使って設定されたパスは、ほかのパスと長期的に共存することを意図しているか。そうであれば、PCEPでその状況をどのように管理するか。
  • 運用者は、新しいパス設定タイプに関して、ネットワーク内のPCEPが正しく動作していることをどのように検証できるか。どのような障害状態を運用者に報告しなければならないか。
  • 新しいパス設定タイプに関するネットワーク内のPCEPの動作をモデル化するために、拡張しなければならない既存の管理インターフェイス（YANGモデルなど）はあるか。

See [RFC5706] for further guidance on how to write Manageability Considerations sections in Standards Track documents.

標準化過程の文書における管理性に関する考慮事項のセクションの書き方についての詳しい指針は、[RFC5706]を参照してください。

7. Security Considerations

7. セキュリティーに関する考慮事項

The security considerations described in [RFC5440] and [RFC8281] are applicable to this specification. No additional security measure is required.

[RFC5440]と[RFC8281]に記載されているセキュリティーに関する考慮事項は、この仕様にも当てはまります。追加のセキュリティー対策は必要ありません。

Note that if the security mechanisms of [RFC5440] and [RFC8281] are not used, then the protocol described in this document could be attacked in the following new way. An attacker, using a TCP man-in-the-middle attack, could inject error messages into the PCEP session when a particular PST is (or is not) used. Doing this could potentially force the use of a specific PST, which may allow the attacker to subsequently attack a weakness in that PST.

なお、[RFC5440]と[RFC8281]のセキュリティーメカニズムを使わない場合、この文書で記述するプロトコルは、次のような新しい方法で攻撃される可能性があります。攻撃者は、TCPの中間者攻撃を使って、特定のPSTが使われている（または使われていない）ときにPCEPセッションにエラーメッセージを注入できる可能性があります。これにより、特定のPSTの使用を強制できる可能性があり、その結果、攻撃者がそのPSTの弱点を突いて攻撃できるようになる可能性があります。
