RFC 8186

Support of the IEEE 1588 Timestamp Format in a Two-Way Active Measurement Protocol (TWAMP)

RFC 8186

双方向アクティブ測定プロトコル（TWAMP）におけるIEEE 1588タイムスタンプ形式のサポート

Abstract

概要

This document describes an OPTIONAL feature for active performance measurement protocols that allows use of the Precision Time Protocol timestamp format defined in IEEE 1588v2, as an alternative to the Network Time Protocol that is currently used.

この文書は、アクティブな性能測定プロトコルのための機能を記述します。この機能は選択できます（OPTIONAL）。この機能により、現在使われているネットワークタイムプロトコル（Network Time Protocol）の代わりに、IEEE 1588v2で定義されている高精度時刻プロトコル（Precision Time Protocol）のタイムスタンプ形式を使用できるようになります。

1. Introduction

1. はじめに

The One-Way Active Measurement Protocol (OWAMP) [RFC4656] defines that only the NTP format [RFC5905] of a timestamp can be used in the OWAMP-Test protocol. The Two-Way Active Measurement Protocol (TWAMP) [RFC5357] adopted the OWAMP-Test packet format and extended it by adding a format for a reflected test packet. Both the sender's and reflector's packets timestamps are expected to follow the 64-bit-long NTP format [RFC5905]. NTP, when used over the Internet, typically achieves clock accuracy within 5 ms to 100 ms. Surveys conducted recently suggest that 90% of devices achieve accuracy better than 100 ms and 99% of devices achieve accuracy better than 1 sec. It should be noted that NTP synchronizes clocks on the control plane, not on data plane. Distribution of clock within a node may be supported by an independent NTP domain or via interprocess communication in a multiprocessor distributed system. Any of the mentioned solutions will be subject to additional queuing delays that negatively affect data-plane clock accuracy.

単方向アクティブ測定プロトコル（One-Way Active Measurement Protocol、OWAMP）[RFC4656]は、OWAMP-Testプロトコルではタイムスタンプの形式としてNTP形式[RFC5905]だけを使用できると定めています。双方向アクティブ測定プロトコル（Two-Way Active Measurement Protocol、TWAMP）[RFC5357]は、OWAMP-Testのパケット形式を採用し、反射されたテストパケットの形式を追加してそれを拡張しました。送信者のパケットと反射者のパケットのどちらのタイムスタンプも、64ビット長のNTP形式[RFC5905]に従うことが想定されています。インターネット上で使用する場合、NTPは一般に5ミリ秒から100ミリ秒以内の時計の精度を達成します。最近実施された調査では、90%の機器が100ミリ秒よりも良い精度を、99%の機器が1秒よりも良い精度を達成していることが示唆されています。NTPが時計を同期するのはコントロールプレーン上であり、データプレーン上ではないことに注意すべきです。ノード内での時計の配信は、独立したNTPドメインによって、またはマルチプロセッサーの分散システムにおけるプロセス間通信を介して、サポートされることがあります。前述のいずれの解決策でも、追加のキューイング遅延が生じ、データプレーンの時計の精度に悪影響を与えます。

The Precision Time Protocol (PTP) [IEEE.1588] has gained wide support since the development of OWAMP and TWAMP. PTP, using on-path support and other mechanisms, allows sub-microsecond clock accuracy. PTP is now supported in multiple implementations of fast-forwarding engines; thus, accuracy achieved by PTP is the accuracy of the clock in the data plane. Having an option to use a more accurate clock as a source of timestamps for IP performance measurements is one of the advantages of this specification. Another advantage is realized by simplification of hardware in the data plane. To support OWAMP or TWAMP, test protocol timestamps must be converted from PTP to NTP. That requires resources, use of microcode or additional processing elements, that are always limited. To address this, this document proposes optional extensions to Control and Test protocols to support use of the IEEE 1588v2 timestamp format as an optional alternative to the NTP timestamp format.

高精度時刻プロトコル（Precision Time Protocol、PTP）[IEEE.1588]は、OWAMPとTWAMPが開発されて以降、広くサポートされるようになりました。PTPは、経路上のサポートやその他のメカニズムを使用することで、1マイクロ秒未満の時計の精度を実現します。PTPは現在、高速転送エンジンの複数の実装でサポートされています。したがって、PTPによって達成される精度は、データプレーンにおける時計の精度です。IP性能測定のタイムスタンプの源として、より正確な時計を使用する選択肢があることは、この仕様の利点の1つです。もう1つの利点は、データプレーンのハードウェアの簡素化によって実現されます。OWAMPやTWAMPをサポートするには、テストプロトコルのタイムスタンプをPTPからNTPに変換する必要があります。それにはリソース、つまりマイクロコードや追加の処理要素の使用が必要ですが、それらは常に限られています。この問題に対処するため、この文書は、NTPタイムスタンプ形式のオプションの代替としてIEEE 1588v2タイムスタンプ形式の使用をサポートする、制御プロトコルとテストプロトコルへのオプションの拡張を提案します。

One of the goals of this specification is not only to allow endpoints of a test session to use a timestamp format other than NTP, but to support backwards compatibility with nodes that do not yet support this extension.

この仕様の目標の1つは、テストセッションのエンドポイントがNTP以外のタイムスタンプ形式を使用できるようにすることだけでなく、この拡張をまだサポートしていないノードとの後方互換性をサポートすることです。

2. OWAMP and TWAMP Extensions

2. OWAMPとTWAMPの拡張

OWAMP connection establishment follows the procedure defined in Section 3.1 of [RFC4656] and additional steps in TWAMP described in Section 3.1 of [RFC5357]. In these procedures, the Modes field has been used to identify and select specific communication capabilities. At the same time, the Modes field has been recognized and used as an extension mechanism [RFC6038]. The new feature requires one bit position for the Server and Control-Client to negotiate which timestamp format can be used in some or all test sessions invoked with this control connection. The endpoint of the test session, Session-Sender and Session-Receiver (for OWAMP) or Session-Reflector (for TWAMP), that supports this extension MUST be capable of interpreting the NTP and PTPv2 timestamp formats. If the endpoint does not support this extension, then the value of the PTPv2 Timestamp flag MUST be 0 because it is in Must Be Zero field. If the value of the PTPv2 Timestamp flag is 0, then the advertising node can use and interpret only the NTP timestamp format. Implementations of OWAMP and/or TWAMP MAY provide a configuration knob to bypass the timestamp format negotiation process and use the locally configured values instead.

OWAMPの接続確立は、[RFC4656]のセクション3.1で定義されている手順と、[RFC5357]のセクション3.1で説明されているTWAMPの追加の手順に従います。これらの手順では、特定の通信能力を識別して選択するためにModesフィールドが使用されてきました。同時に、Modesフィールドは拡張メカニズムとして認識され、使用されています[RFC6038]。この新しい機能では、この制御接続で開始される一部またはすべてのテストセッションでどのタイムスタンプ形式を使用できるかをServerとControl-Clientがネゴシエーションするために、1つのビット位置が必要です。この拡張をサポートするテストセッションのエンドポイント、つまりSession-SenderとSession-Receiver（OWAMPの場合）またはSession-Reflector（TWAMPの場合）は、NTPとPTPv2のタイムスタンプ形式を解釈できなければなりません（MUST）。エンドポイントがこの拡張をサポートしていない場合、PTPv2 TimestampフラグはMust Be Zeroフィールドの中にあるため、その値は0でなければなりません（MUST）。PTPv2 Timestampフラグの値が0の場合、広告しているノードはNTPタイムスタンプ形式だけを使用して解釈できます。OWAMPやTWAMPの実装は、タイムスタンプ形式のネゴシエーション手順を迂回して、代わりにローカルに設定された値を使用するための設定項目を提供してもよいです（MAY）。

Use of PTPv2 Timestamp flags is discussed in the following subsections. For details on the assigned values and bit positions, see the Section 3.

PTPv2 Timestampフラグの使用については、以降のサブセクションで説明します。割り当てられた値とビット位置の詳細については、セクション3を参照してください。

2.1. Timestamp Format Negotiation in OWAMP Connection Setup

2.1. OWAMPの接続セットアップにおけるタイムスタンプ形式のネゴシエーション

In OWAMP-Test [RFC4656], the Session-Receiver and/or Fetch-Client interpret collected timestamps. Thus, the Server uses the Modes field timestamp format to indicate which formats the Session-Receiver is capable of interpreting. The Control-Client inspects values set by the Server for timestamp formats and sets values in the Modes field of the Set-Up-Response message according to the timestamp formats the Session-Sender can use. The rules for setting timestamp flags in the Modes field in Server Greeting and Set-Up-Response messages and interpreting them are as follows:

OWAMP-Test [RFC4656]では、収集されたタイムスタンプを解釈するのはSession-ReceiverやFetch-Clientです。そのため、Serverは、Modesフィールドのタイムスタンプ形式を使用して、Session-Receiverがどの形式を解釈できるかを示します。Control-Clientは、Serverがタイムスタンプ形式に設定した値を調べ、Session-Senderが使用できるタイムスタンプ形式に従ってSet-Up-ResponseメッセージのModesフィールドに値を設定します。Server GreetingメッセージとSet-Up-ResponseメッセージのModesフィールドにタイムスタンプのフラグを設定する規則と、それらを解釈する規則は次のとおりです。

  • If the Session-Receiver supports this extension, then the Server that establishes test sessions on its behalf MUST set the PTPv2 Timestamp flag to 1 in the Server Greeting message per the requirement listed in Section 2. Otherwise, the PTPv2 Timestamp flag will be set to 0 to indicate that the Session-Receiver interprets only the NTP format.
  • If the Control-Client receives a greeting message with the PTPv2 Timestamp flag set to 0, then the Session-Sender MUST use the NTP format for the timestamp in the test session, and the Control-Client SHOULD set the PTPv2 Timestamp flag to 0 in accordance with [RFC4656]. If the Session-Sender cannot use NTP timestamps, then the Control-Client SHOULD close the TCP connection associated with the OWAMP-Control session.
  • If the Control-Client receives a greeting message with the PTPv2 Timestamp flag set to 1 and the Session-Sender can set the timestamp in PTPv2 format, then the Control-Client MUST set the PTPv2 Timestamp flag to 1 in the Modes field in the Set-Up-Response message and the Session-Sender MUST use PTPv2 timestamp format.
  • If the Session-Sender doesn't support this extension and can set the timestamp in NTP format only, then the PTPv2 Timestamp flag in the Modes field in the Set-Up-Response message will be set to 0 as part of the Must Be Zero field and the Session-Sender will use the NTP format.
  • Session-Receiverがこの拡張をサポートしている場合、そのSession-Receiverに代わってテストセッションを確立するServerは、セクション2に挙げた要件に従って、Server GreetingメッセージのPTPv2 Timestampフラグを1に設定しなければなりません（MUST）。そうでない場合、Session-ReceiverがNTP形式だけを解釈することを示すために、PTPv2 Timestampフラグは0に設定されます。
  • Control-ClientがPTPv2 Timestampフラグが0に設定されたグリーティングメッセージを受信した場合、Session-Senderはテストセッションのタイムスタンプに対してNTP形式を使用しなければなりません（MUST）。また、Control-Clientは[RFC4656]に従ってPTPv2 Timestampフラグを0に設定すべきです（SHOULD）。Session-SenderがNTPタイムスタンプを使用できない場合、Control-ClientはOWAMP-Controlセッションに関連付けられたTCP接続を閉じるべきです（SHOULD）。
  • Control-ClientがPTPv2 Timestampフラグが1に設定されたグリーティングメッセージを受信し、かつSession-SenderがPTPv2形式でタイムスタンプを設定できる場合、Control-ClientはSet-Up-ResponseメッセージのModesフィールドのPTPv2 Timestampフラグを1に設定しなければなりません（MUST）。そして、Session-SenderはPTPv2タイムスタンプ形式を使用しなければなりません（MUST）。
  • Session-Senderがこの拡張をサポートしておらず、NTP形式でしかタイムスタンプを設定できない場合、Set-Up-ResponseメッセージのModesフィールドのPTPv2 Timestampフラグは、Must Be Zeroフィールドの一部として0に設定され、Session-SenderはNTP形式を使用します。

If OWAMP-Control uses Fetch-Session commands, then selection and use of one timestamp format or another is a local decision for both Session-Sender and Session-Receiver.

OWAMP-ControlがFetch-Sessionコマンドを使用する場合、どちらのタイムスタンプ形式を選択して使用するかは、Session-SenderとSession-Receiverの両方にとってローカルな判断です。

2.2. Timestamp Format Negotiation in TWAMP Connection Setup

2.2. TWAMPの接続セットアップにおけるタイムスタンプ形式のネゴシエーション

In TWAMP-Test [RFC5357], the Session-Sender interprets collected timestamps. Hence, in the Modes field, a Server advertises timestamp formats that the Session-Reflector can use in the TWAMP-Test message. The choice of the timestamp format to be used by the Session-Sender is a local decision. The Control-Client inspects the Modes field and sets timestamp flag values to indicate the format that will be used by the Session-Reflector. The rules of setting and interpreting flag values are as follows:

TWAMP-Test [RFC5357]では、収集されたタイムスタンプを解釈するのはSession-Senderです。そのため、Serverは、Session-ReflectorがTWAMP-Testメッセージで使用できるタイムスタンプ形式をModesフィールドで広告します。Session-Senderが使用するタイムスタンプ形式の選択はローカルな判断です。Control-Clientは、Modesフィールドを調べ、Session-Reflectorが使用する形式を示すためにタイムスタンプのフラグの値を設定します。フラグの値を設定する規則と解釈する規則は次のとおりです。

  • The Server MUST set the PTPv2 Timestamp flag value to 1 in its greeting message if the Session-Reflector can set the timestamp in the PTPv2 format. Otherwise, the PTPv2 Timestamp flag MUST be set to 0.
  • If the value of the PTPv2 Timestamp flag in the received Server Greeting message is 0, then the Session-Reflector does not support this extension and will use the NTP timestamp format. The Control-Client SHOULD set the PTPv2 Timestamp flag to 0 in the Set-Up-Response message in accordance with [RFC4656].
  • The Control-Client MUST set the PTPv2 Timestamp flag value to 1 in the Modes field in the Set-Up-Response message if the Server advertised that the Session-Reflector has the ability to use the PTPv2 format for timestamps. Otherwise, the flag MUST be set to 0.
  • If the value of the PTPv2 Timestamp flag in the Set-Up-Response message is 0, then that means that the Session-Sender can only interpret the NTP timestamp format. Therefore, the Session-Reflector MUST use the NTP timestamp format. If the Session-Reflector does not support the NTP format, then the Server MUST close the TCP connection associated with the TWAMP-Control session.
  • Session-ReflectorがPTPv2形式でタイムスタンプを設定できる場合、ServerはグリーティングメッセージのPTPv2 Timestampフラグの値を1に設定しなければなりません（MUST）。そうでない場合、PTPv2 Timestampフラグは0に設定しなければなりません（MUST）。
  • 受信したServer GreetingメッセージのPTPv2 Timestampフラグの値が0の場合、Session-Reflectorはこの拡張をサポートしておらず、NTPタイムスタンプ形式を使用します。Control-Clientは、[RFC4656]に従って、Set-Up-ResponseメッセージのPTPv2 Timestampフラグを0に設定すべきです（SHOULD）。
  • Session-ReflectorがPTPv2形式をタイムスタンプに使用できることをServerが広告した場合、Control-ClientはSet-Up-ResponseメッセージのModesフィールドのPTPv2 Timestampフラグの値を1に設定しなければなりません（MUST）。そうでない場合、このフラグは0に設定しなければなりません（MUST）。
  • Set-Up-ResponseメッセージのPTPv2 Timestampフラグの値が0の場合、それはSession-SenderがNTPタイムスタンプ形式しか解釈できないことを意味します。したがって、Session-ReflectorはNTPタイムスタンプ形式を使用しなければなりません（MUST）。Session-ReflectorがNTP形式をサポートしていない場合、ServerはTWAMP-Controlセッションに関連付けられたTCP接続を閉じなければなりません（MUST）。

2.3. OWAMP-Test and TWAMP-Test Updates

2.3. OWAMP-TestとTWAMP-Testの更新

Participants of a test session need to indicate which timestamp format is being used. Currently, the Z field in the Error Estimate defined in Section 4.1.2 of [RFC4656] is used for this purpose. However, this document extends the Error Estimate to indicate the format of a collected timestamp, in addition to the estimate of error and synchronization. This specification also changes the semantics of the Z bit field (the field between S and Scale fields) to be referred to as the Timestamp format; the value MUST be set as follows:

テストセッションの参加者は、どのタイムスタンプ形式が使用されているかを示す必要があります。現在、この目的には[RFC4656]のセクション4.1.2で定義されているError EstimateのZフィールドが使用されています。しかし、この文書はError Estimateを拡張し、誤差と同期の推定に加えて、収集されたタイムスタンプの形式も示すようにします。また、この仕様は、Zビットフィールド（SフィールドとScaleフィールドの間のフィールド）の意味を変更し、Timestamp formatと呼ぶことにします。その値は次のように設定しなければなりません（MUST）。

  • 0 - NTP 64-bit format of a timestamp.
  • 1 - PTPv2-truncated format of a timestamp.
  • 0 - タイムスタンプのNTP 64ビット形式。
  • 1 - タイムスタンプのPTPv2切り詰め形式。

As a result of this value of the Z field from the Error Estimate, the Sender Error Estimate (in TWAMP) or Send Error Estimate (in OWAMP) and Receive Error Estimate SHOULD NOT be ignored and MUST be used when calculating delay and delay-variation metrics based on collected timestamps.

Error EstimateのZフィールドがこのような値をとる結果として、Sender Error Estimate（TWAMPの場合）またはSend Error Estimate（OWAMPの場合）とReceive Error Estimateは無視されるべきではありません（SHOULD NOT）。これらは、収集されたタイムスタンプに基づいて遅延と遅延変動のメトリックを計算する際に使用しなければなりません（MUST）。

2.3.1. Consideration for TWAMP Light Mode

2.3.1. TWAMP Lightモードに関する考慮事項

This document does not specify how the Session-Sender and Session-Reflector in TWAMP Light mode are informed of the timestamp format to be used. It is assumed that, for example, configuration could be used to direct the Session-Sender and Session-Reflector to use the timestamp format per their capabilities and rules listed in Section 2.2.

この文書は、TWAMP LightモードのSession-SenderとSession-Reflectorに、使用するタイムスタンプ形式をどのように通知するかを規定しません。たとえば、Session-SenderとSession-Reflectorに対して、それぞれの能力とセクション2.2に挙げた規則に従ったタイムスタンプ形式を使用するよう指示するために、設定を使用できることが想定されています。

4. Security Considerations

4. セキュリティーに関する考慮事項

Use of a particular timestamp format in a test session does not appear to introduce any additional security threat to hosts that communicate with OWAMP and/or TWAMP as defined in [RFC4656] and [RFC5357], respectively. The security considerations that apply to any active measurement of live networks are relevant here as well. See the Security Considerations sections in [RFC4656] and [RFC5357].

テストセッションで特定のタイムスタンプ形式を使用することは、[RFC4656]と[RFC5357]でそれぞれ定義されているOWAMPやTWAMPで通信するホストに対して、新たなセキュリティー上の脅威をもたらさないと考えられます。稼働中のネットワークのアクティブ測定全般に適用されるセキュリティーに関する考慮事項は、ここでも同様に関係します。[RFC4656]と[RFC5357]のセキュリティーに関する考慮事項のセクションを参照してください。
