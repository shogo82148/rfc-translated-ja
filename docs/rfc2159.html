1. Introduction

1. はじめに

This document contains the definitions, originally contained in RFC 1494, on how to carry CCITT G3Fax in MIME, and how to translate it to its X.400 representation.

この文書は、もともとRFC 1494に含まれていた、CCITT G3FaxをMIMEで運ぶ方法と、それをX.400の表現に変換する方法の定義を収めたものです。

NOTE: At the moment, this format does not seem appropriate for a "general purpose image format for the Internet", if such a beast can exist. It exists only to carry information that is already in G3 Fax format, and may be usefully converted to other formats when used in specific contexts.

注：現時点では、この形式は「インターネットのための汎用画像形式」（そのような代物が存在しうるとしての話ですが）としては適切ではないと思われます。この形式は、すでにG3 Fax形式になっている情報を運ぶためだけに存在するものであり、特定の文脈で使う場合には、ほかの形式に変換すると有用なこともあります。

2. The image/g3fax content-type

2. image/g3faxコンテンツタイプ

This content-type is defined to carry G3 Facsimile byte streams.

このコンテンツタイプは、G3ファクシミリのバイトストリームを運ぶために定義されています。

In general, a G3Fax image contains 3 pieces of information:

一般に、G3Fax画像には次の3つの情報が含まれます。

  1. A set of flags indicating the particular coding scheme. CCITT Recommendation T.30 defines how the flags are transmitted over telephones. In this medium, the flags are carried as parameters in the MIME content-type header field.
  2. A structure that divides the bits into pages. CCITT recommendation T.4 describes a "return to command mode" string; this is used here to indicate page breaks.
  3. For each page, a sequence of bits that form the encoding of the image. CCITT recommendation T.4 defines the bit image format. This is used without change. The highest bit of the first byte is the first bit of the T.4 bitstream.
  1. 特定の符号化方式を示すフラグの集合。CCITT勧告T.30は、電話回線でフラグを伝送する方法を定義しています。この媒体では、フラグはMIMEのcontent-typeヘッダーフィールドのパラメーターとして運ばれます。
  2. ビットをページに分割する構造。CCITT勧告T.4は「コマンドモードへの復帰（return to command mode）」文字列について記述しています。ここでは、これを改ページを示すために使います。
  3. ページごとの、画像の符号化を構成するビット列。CCITT勧告T.4がビットイメージの形式を定義しています。これは変更せずにそのまま使います。先頭バイトの最上位ビットが、T.4ビットストリームの最初のビットです。

2.1. G3Fax Parameters

2.1. G3Faxのパラメーター

The following parameters are defined:

次のパラメーターが定義されています。

  1. page-length - possible values: A4, B4 and Unlimited
  2. page-width - possible values: A3, A4, B4
  3. encoding - possible values: 1-dimensional, 2-dimensional, Uncompressed
  4. resolution - possible values: Fine, Coarse
  5. DCS - a bit string, represented in Base64.
  6. pages - an integer, giving the number of pages in the document
  1. page-length - 取りうる値：A4、B4、Unlimited
  2. page-width - 取りうる値：A3、A4、B4
  3. encoding - 取りうる値：1-dimensional、2-dimensional、Uncompressed
  4. resolution - 取りうる値：Fine、Coarse
  5. DCS - Base64で表現したビット文字列。
  6. pages - 文書のページ数を示す整数。

If nothing is specified, the default parameter settings are:

何も指定しない場合、パラメーターのデフォルト設定は次のとおりです。

   page-length=A4
   page-width=A4
   encoding=1-dimensional
   resolution=Coarse

   page-length=A4
   page-width=A4
   encoding=1-dimensional
   resolution=Coarse

これらの値の表現を1ビットのフラグとみなすこともできます（ただし誤解を招きます）。これらは、T.30の制御文字列とX.400のG3FacsimileParametersの次のビットに対応します。

The reason for the different bit numbers is that X.400 counts bits in an octet from the MSB down to the LSB, while T.30 uses the opposite numbering scheme.

ビット番号が異なるのは、X.400がオクテット内のビットをMSBからLSBに向かって数えるのに対し、T.30は逆の番号付けを使うためです。

If any bit but these are set in the Device Control String, the DCS parameter should be supplied.

デバイス制御文字列（Device Control String）にこれら以外のビットが立っている場合は、DCSパラメーターを指定すべきです。

2.2. Content Encoding

2.2. コンテンツのエンコーディング

X.400 defines the g3-facsimile data stream as a SEQUENCE of BIT STRINGs. Each BIT STRING is a page of facsimile image data, encoded as defined by Recommendation T.4. The following content encoding is reversible between MIME and X.400 and ensures that page breaks are honored in the MIME representation.

X.400は、g3-facsimileのデータストリームをBIT STRINGのSEQUENCEとして定義しています。各BIT STRINGはファクシミリ画像データの1ページであり、勧告T.4の定義に従って符号化されています。次のコンテンツエンコーディングは、MIMEとX.400の間で可逆であり、MIMEの表現でも改ページが守られることを保証します。

An EOL is defined as a bit sequence of

EOLは、次のビット列として定義されます。

    000000000001 (eleven zeroes and a one).

    000000000001 (eleven zeroes and a one).

Each page of the message is delimited by a sequence of six (6) EOLs that MUST start on a byte boundary. The image bit stream is padded with zeroes as needed to achieve this alignment.

メッセージの各ページは、6個のEOLの並びで区切られます。この並びはバイト境界から始まらなければなりません（MUST）。この位置合わせのために、画像のビットストリームには必要に応じて0を詰めます。

Searching for the boundary is a matter of searching for the byte sequence (HEX) 00 10 01 00 10 01 00 10 01, which cannot occur inside the image.

境界を探すには、バイト列（16進）00 10 01 00 10 01 00 10 01を探せば済みます。このバイト列は画像の内部には現れません。

See Section 7.5 for the algorithm on conversion between this encoding and the X.400 encoding.

このエンコーディングとX.400のエンコーディングの間の変換アルゴリズムについては、セクション7.5を参照してください。

The Base64 content-transfer-encoding is appropriate for carrying this content-type.

このコンテンツタイプを運ぶには、Base64のcontent-transfer-encodingが適しています。

3. g3-facsimile - image/g3fax

X.400 Body part:

Conversion Type:

X.400のボディーパート：
g3-facsimile
MIMEのContent-Type：
image/g3fax
変換の種類：
ほぼバイト単位のコピー

Comments:

コメント：

The Parameters of the X.400 G3Fax body part are mapped to the corresponding Parameters on the MIME Image/G3Fax body part and vice versa. Note that:

X.400のG3Faxボディーパートのパラメーターは、MIMEのImage/G3Faxボディーパートの対応するパラメーターに対応付けられ、その逆も同様です。次の点に注意してください。

  1. If fineResolution is not specified, pixels will be twice as tall as they are wide
  2. If any bit not corresponding to a specially named option is set in the G3Fax NonBasicParameters, the "DCS" parameter must be used.
  3. Interworking is not guaranteed if any bit apart from those specially named are used in the NonBasicParameters
  1. fineResolutionが指定されていない場合、画素の高さは幅の2倍になります。
  2. 名前の付いた特定のオプションに対応しないビットがG3FaxのNonBasicParametersに立っている場合は、「DCS」パラメーターを使わなければなりません。
  3. 名前の付いた特定のビット以外のビットがNonBasicParametersで使われている場合、相互接続は保証されません。

From X.400 to G3Fax, the body is created in the following way:

X.400からG3Faxへの変換では、本体を次のように作成します。

  1. Any trailing EOL markers on each bitstring is removed. The bit order is changed to conform to the most common Internet encoding (highest bit of first byte = first bit of the G3Fax). The bitstring is padded to a byte boundary.
  2. 6 consecutive EOL markers are appended to each bitstring.
  3. The padded bitstrings are concatenated together
  1. 各ビット文字列の末尾にあるEOLマーカーを取り除きます。ビットの順序を、インターネットで最も一般的なエンコーディング（先頭バイトの最上位ビット＝G3Faxの最初のビット）に合うように変更します。ビット文字列にはバイト境界まで詰め物をします。
  2. 各ビット文字列に、6個の連続したEOLマーカーを追加します。
  3. 詰め物をしたビット文字列を連結します。

An EOL marker is the bit sequence 000000000001 (11 zeroes and a one).

EOLマーカーは、ビット列000000000001（11個の0と1個の1）です。

From G3Fax to X.400, the body is created in the following way:

G3FaxからX.400への変換では、本体を次のように作成します。

  1. The body is split into bitstrings at each occurrence of 6 consecutive EOL markers. Trailing EOLs must NOT be removed, since the X.400 Implementor Guide recommends that each page should end with 6 consecutive EOLs. (This is a change from RFC 1494).
  2. Each bitstring is made into an ASN.1 BITSTRING, reversing the order of bits within each byte to conforom to the X.400 Implementors Guide recommendation for bit order in the G3Fax body part.
  3. The bitstrings are made into an ASN.1 SEQUENCE, which forms the body of the G3Fax body part.
  1. 本体を、6個の連続したEOLマーカーが現れるたびに区切ってビット文字列に分割します。X.400 Implementor Guideは各ページを6個の連続したEOLで終えることを推奨しているので、末尾のEOLを取り除いてはなりません（これはRFC 1494からの変更点です）。
  2. 各ビット文字列をASN.1のBITSTRINGにします。その際、G3Faxボディーパートのビット順序に関するX.400 Implementors Guideの推奨に合わせるため、各バイト内のビットの順序を逆にします。
  3. ビット文字列をASN.1のSEQUENCEにします。これがG3Faxボディーパートの本体になります。

4. Usability of G3Fax body parts

4. G3Faxボディーパートの使い勝手

This section is not part of the proposed standard, but is intended as guidance for people implementing G3Fax handling, so that they know a little about what to expect.

このセクションは提案標準（proposed standard）の一部ではありません。G3Faxの処理を実装する人が、何が起こりうるかを少しでも把握できるようにするためのガイダンスです。

The DCS bitstring is a LONG thing; the T.30 Recommendation (1993) gives 67 bits with specific functions, SG8 Report R33 extends this to 75 bits, and Report R41 (approved in 1995) extends it to 79 bits. (For curiosity - bit 68 says that the coding is JPEG; bit 27 is "error correcting mode). No sane implementor will send such things without being able to negotiate them down if the recipient doesn't support it, but there is no guarantee that messages with such bits set in the DCS won't arrive through X.400.

DCSのビット文字列は「長い」ものです。T.30勧告（1993年）は特定の機能を持つ67ビットを規定しており、SG8 Report R33はこれを75ビットに、Report R41（1995年承認）は79ビットに拡張しています（参考までに、ビット68は符号化がJPEGであることを、ビット27は「誤り訂正モード」を示します）。まともな実装者であれば、受信者がそれをサポートしていない場合に交渉で引き下げる手段がないまま、こうしたものを送ることはないでしょう。しかし、DCSにそのようなビットが立ったメッセージがX.400経由で届かないという保証はありません。

The ISO P2 profile from 1995 [PROFILE] says that the profile makes support for reception of two-dimensional and fine-resolution mandatory if g3-facsimile is supported at all. Research by Andrew Gordon of Net-Tel indicates that it is easy for an access unit to support fine resolution, unlimited length and B4 length, while support for B4 width is nearly impossible, and A3 width is hard.

1995年のISO P2プロファイル[PROFILE]によれば、このプロファイルでは、g3-facsimileを少しでもサポートするのであれば、2次元符号化と高解像度（fine resolution）の受信のサポートが必須になります。Net-TelのAndrew Gordonの調査によると、アクセスユニットにとって、高解像度、無制限の長さ、B4の長さをサポートするのは容易ですが、B4の幅のサポートはほぼ不可能であり、A3の幅は困難です。

Another interesting point is that some fax machines have trouble if the scan lines do not contain exactly the declared number of pixels on each scan line, so "omitting right-hand white space" is likely to give trouble.

もう1つ興味深い点として、走査線ごとの画素数が宣言された数とちょうど一致しないと問題を起こすファクス機があります。そのため、「右側の空白の省略」は問題を引き起こす可能性があります。

5. Security Considerations

5. セキュリティーに関する考慮事項

There are no known security issues specific to the FAX body part.

FAXボディーパートに固有の既知のセキュリティー問題はありません。
