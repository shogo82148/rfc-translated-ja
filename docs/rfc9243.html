1. Introduction

1. はじめに

DHCPv6 [RFC8415] is used for supplying configuration and other relevant parameters to clients in IPv6 networks. This document defines YANG [RFC7950] modules for the configuration and management of DHCPv6 'elements' (servers, relays, and clients), using the Network Configuration Protocol (NETCONF) [RFC6241] or RESTCONF [RFC8040].

DHCPv6[RFC8415]は、IPv6ネットワークのクライアントに設定やその他の関連するパラメーターを提供するために使用されます。 この文書は、ネットワーク構成プロトコル（NETCONF）[RFC6241]またはRESTCONF[RFC8040]を使用して、DHCPv6の「要素」（サーバー、リレー、クライアント）を設定および管理するためのYANG[RFC7950]モジュールを定義します。

Separate modules are defined for each element. Additionally, a 'common' module contains typedefs and groupings used by all of the element modules. Appendix A provides XML examples for each of the element modules and shows their interaction.

要素ごとに別々のモジュールが定義されています。 さらに、「common」モジュールには、すべての要素モジュールで使用されるtypedefとグルーピングが含まれています。 Appendix Aでは、各要素モジュールのXMLの例を示し、それらの相互作用を説明します。

The relay and client modules provide configuration that is applicable to devices' interfaces. This is done by importing the 'ietf-interfaces' YANG module [RFC8343] and using interface-refs to the relevant interface(s).

リレーモジュールとクライアントモジュールは、デバイスのインターフェイスに適用される設定を提供します。 これは、「ietf-interfaces」YANGモジュール[RFC8343]をインポートし、関連するインターフェイスへのinterface-refを使用することで行います。

It is worth noting that as DHCPv6 is itself a client configuration protocol, it is not the intention of this document to provide a replacement for the allocation of DHCPv6-assigned addressing and parameters by using NETCONF/YANG. The DHCPv6 client module is intended for the configuration and monitoring of the DHCPv6 client function and does not replace DHCPv6 address and parameter configuration.

DHCPv6はそれ自体がクライアント設定プロトコルであるため、この文書は、NETCONF/YANGを使用してDHCPv6で割り当てられるアドレスやパラメーターの割り当てを置き換えることを意図していない点に注意してください。 DHCPv6クライアントモジュールは、DHCPv6クライアント機能の設定と監視を目的としたものであり、DHCPv6によるアドレスやパラメーターの設定を置き換えるものではありません。

The YANG modules in this document adopt the Network Management Datastore Architecture (NMDA) [RFC8342].

この文書のYANGモジュールは、ネットワーク管理データストアアーキテクチャー（NMDA）[RFC8342]を採用しています。

1.1. Scope

1.1. 範囲

[RFC8415] describes the current version of the DHCPv6 base protocol specification. A large number of additional specifications have also been published, extending DHCPv6 element functionality and adding new options. The YANG modules contained in this document do not attempt to capture all of these extensions and additions; rather, they model the DHCPv6 functions and options covered in [RFC8415]. A focus has also been given on the extensibility of the modules so that they are easy to augment to add additional functionality as required by a particular implementation or deployment scenario.

[RFC8415]は、DHCPv6の基本プロトコル仕様の現在のバージョンについて記述しています。 DHCPv6要素の機能を拡張したり、新しいオプションを追加したりする追加の仕様も多数公開されています。 この文書に含まれるYANGモジュールは、これらの拡張や追加のすべてを取り込もうとするものではなく、[RFC8415]で扱われているDHCPv6の機能とオプションをモデル化します。 また、特定の実装や展開シナリオで必要となる追加の機能を加えるためにモジュールを容易に拡張（augment）できるよう、モジュールの拡張性にも重点を置いています。

1.2. Extensibility of the DHCPv6 Server YANG Module

1.2. DHCPv6サーバーYANGモジュールの拡張性

The modules in this document only attempt to model DHCPv6-specific behavior and do not cover the configuration and management of functionality relevant for specific server implementations. The level of variance between implementations is too great to attempt to standardize them in a way that is useful without being restrictive.

この文書のモジュールは、DHCPv6固有の振る舞いをモデル化することだけを試みており、特定のサーバー実装に関係する機能の設定と管理は扱いません。 実装間の差異が大きすぎるため、制約を課すことなく有用な形でそれらを標準化することはできません。

However, it is recognized that implementation-specific configuration and management is also an essential part of DHCP deployment and operations. To resolve this, Appendix C contains an example YANG module for the configuration of implementation-specific functions, illustrating how this functionality can be augmented into the main 'ietf-dhcpv6-server.yang' module.

しかし、実装固有の設定と管理もDHCPの展開と運用に不可欠な部分であることは認識されています。 これを解決するために、Appendix Cには、実装固有の機能を設定するためのYANGモジュールの例が含まれており、この機能をメインの「ietf-dhcpv6-server.yang」モジュールに拡張（augment）する方法を示しています。

In DHCPv6, the concept of 'class selection' for messages received by the server is common. This is the identification and classification of messages based on a number of parameters so that the correct provisioning information can be supplied, for example, by allocating a prefix from the correct pool or supplying a set of options relevant for a specific vendor's client implementation. During the development of this document, implementations were researched and the findings were that while this function is common to all, the method for configuring and implementing this function differs greatly. Therefore, configuration of the class selection function has been omitted from the DHCPv6 server module to allow implementors to define their own suitable YANG modules. Appendix D provides an example of this, which demonstrates how this can be integrated with the main 'ietf-dhcpv6-server.yang' module.

DHCPv6では、サーバーが受信したメッセージに対する「クラス選択」という概念が一般的です。 これは、たとえば正しいプールからプレフィックスを割り当てたり、特定のベンダーのクライアント実装に関連するオプションのセットを提供したりするなど、正しいプロビジョニング情報を提供できるように、いくつかのパラメーターに基づいてメッセージを識別および分類することです。 この文書の策定中に実装を調査した結果、この機能はすべての実装に共通しているものの、この機能を設定および実装する方法は大きく異なることがわかりました。 したがって、実装者が独自の適切なYANGモジュールを定義できるように、クラス選択機能の設定はDHCPv6サーバーモジュールから省かれています。 Appendix Dではこの例を示し、これをメインの「ietf-dhcpv6-server.yang」モジュールと統合する方法を説明します。

1.2.1. DHCPv6 Option Definitions

1.2.1. DHCPv6オプションの定義

A large number of DHCPv6 options have been created in addition to those defined in [RFC8415]. As implementations differ widely as to which DHCPv6 options they support, the following approach has been taken to defining options: only the DHCPv6 options defined in [RFC8415] are included in this document.

[RFC8415]で定義されているもの以外にも、多数のDHCPv6オプションが作成されています。 どのDHCPv6オプションをサポートするかは実装によって大きく異なるため、オプションの定義には次のアプローチを採用しました。すなわち、[RFC8415]で定義されているDHCPv6オプションだけをこの文書に含めます。

Of these, only the options that require operator configuration are modeled. For example, OPTION_IA_NA (3) is created by the DHCP server when requested by the client. The contents of the fields in the option are based on a number of input configuration parameters that the server will apply when it receives the request (e.g., the T1/T2 timers that are relevant for the pool of addresses). As a result, there are no fields that are directly configurable for the option, so it is not modeled.

そのうち、運用者による設定が必要なオプションだけをモデル化しています。 たとえば、OPTION_IA_NA（3）は、クライアントから要求されたときにDHCPサーバーによって作成されます。 このオプションのフィールドの内容は、サーバーがリクエストを受信したときに適用するいくつかの入力設定パラメーター（たとえば、アドレスのプールに関連するT1/T2タイマー）に基づいています。 その結果、このオプションには直接設定可能なフィールドがないため、モデル化していません。

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

3. DHCPv6 Tree Diagrams

3. DHCPv6のツリー図

3.1. DHCPv6 Server Tree Diagram

3.1. DHCPv6サーバーのツリー図

The tree diagram in Figure 1 provides an overview of the DHCPv6 server module. The tree also includes the common functions module defined in Section 4.1.

Figure 1のツリー図は、DHCPv6サーバーモジュールの概要を示しています。 このツリーには、Section 4.1で定義されている共通機能モジュールも含まれています。

Descriptions of important nodes:
enabled:
This enables/disables the function of the DHCPv6 server.
dhcpv6-server:
This container holds the server's DHCPv6-specific configuration.
server-duid:
Each server must have a DHCP Unique Identifier (DUID) to identify itself to clients. A DUID consists of a 2-octet type field and an arbitrary length (of no more than 128 octets) content field. Currently, there are four DUID types defined in [RFC8415] and [RFC6355]. The DUID may be configured using the format for one of these types or using the 'unstructured' format. The DUID type definitions are imported from the 'ietf-dhcpv6-common.yang' module. [IANA-HARDWARE-TYPES] and [IANA-PEN] are referenced for the relevant DUID types.
vendor-config:
This container is provided as a location for additional implementation-specific YANG nodes for the configuration of the device to be augmented. See Appendix C for an example of such a module.
option-sets:
The server can be configured with multiple option-sets. These are groups of DHCPv6 options with common parameters that may be supplied to clients on request. The 'option-set-id' field is used to reference an option-set elsewhere in the server's configuration.
option-set:
This holds configuration parameters for DHCPv6 options. The initial set of applicable option definitions are defined here, and additional options that are also relevant to the relay and/or client are imported from the 'ietf-dhcpv6-common' module. Where needed, other DHCPv6 option modules can be augmented as they are defined. The complete list of DHCPV6 options is located at [IANA-DHCPV6-OPTION-CODES].
class-selector:
This is provided as a location for additional implementation-specific YANG nodes for vendor-specific class selector nodes to be augmented. See Appendix D for an example of this.
allocation-ranges:
A hierarchical model is used for the allocation of addresses and prefixes. The top-level 'allocation-ranges' container holds global configuration parameters. Under this, the 'allocation-range' list is used for specifying IPv6 prefixes and additional prefix-specific parameters.
address-pools:
This is used for Identity Association for Non-temporary Addresses (IA_NA) and Identity Association for Temporary Addresses (IA_TA) pool allocations with a container for defining host reservations. State information about active leases from each pool is also located here.
prefix-pools:
This defines pools to be used for prefix delegation to clients. Static host reservations can also be configured. As prefix delegation is not supported by all DHCPv6 server implementations, it is enabled by a feature statement.
重要なノードの説明：
enabled:
DHCPv6サーバーの機能を有効化／無効化します。
dhcpv6-server:
このコンテナーは、サーバーのDHCPv6固有の設定を保持します。
server-duid:
各サーバーは、クライアントに対して自身を識別するためのDHCP固有識別子（DUID）を持つ必要があります。 DUIDは、2オクテットのタイプフィールドと、任意の長さ（128オクテット以下）のコンテンツフィールドで構成されます。 現在、[RFC8415]と[RFC6355]で4つのDUIDタイプが定義されています。 DUIDは、これらのタイプのいずれかの形式、または「unstructured」形式を使用して設定できます。 DUIDタイプの定義は、「ietf-dhcpv6-common.yang」モジュールからインポートされます。 関連するDUIDタイプについては、[IANA-HARDWARE-TYPES]と[IANA-PEN]を参照しています。
vendor-config:
このコンテナーは、デバイスの設定のための実装固有のYANGノードを追加で拡張（augment）する場所として提供されています。 そのようなモジュールの例については、Appendix Cを参照してください。
option-sets:
サーバーには、複数のオプションセットを設定できます。 オプションセットは、共通のパラメーターを持つDHCPv6オプションのグループであり、要求に応じてクライアントに提供できます。 「option-set-id」フィールドは、サーバーの設定の他の場所からオプションセットを参照するために使用されます。
option-set:
DHCPv6オプションの設定パラメーターを保持します。 適用可能なオプション定義の初期セットはここで定義されており、リレーやクライアントにも関係する追加のオプションは「ietf-dhcpv6-common」モジュールからインポートされます。 必要に応じて、他のDHCPv6オプションモジュールが定義され次第、それらを拡張（augment）できます。 DHCPV6オプションの完全なリストは、[IANA-DHCPV6-OPTION-CODES]にあります。
class-selector:
ベンダー固有のクラスセレクターノードのための実装固有のYANGノードを追加で拡張（augment）する場所として提供されています。 この例については、Appendix Dを参照してください。
allocation-ranges:
アドレスとプレフィックスの割り当てには、階層モデルが使用されます。 最上位の「allocation-ranges」コンテナーは、グローバルな設定パラメーターを保持します。 その下の「allocation-range」リストは、IPv6プレフィックスとプレフィックス固有の追加パラメーターを指定するために使用されます。
address-pools:
一時的でないアドレスのためのアイデンティティーアソシエーション（IA_NA）と一時アドレスのためのアイデンティティーアソシエーション（IA_TA）のプール割り当てに使用され、ホスト予約を定義するためのコンテナーを持ちます。 各プールのアクティブなリースに関する状態情報もここにあります。
prefix-pools:
クライアントへのプレフィックス委任に使用するプールを定義します。 静的なホスト予約も設定できます。 プレフィックス委任はすべてのDHCPv6サーバー実装でサポートされているわけではないため、featureステートメントによって有効化されます。
Information about RPCs:
delete-address-lease:
This allows the deletion of a lease for an individual IPv6 address from the server's lease database. Per [BCP18], if available, a language identifier should be included in the output message.
delete-prefix-lease:
This allows the deletion of a lease for an individual IPv6 prefix from the server's lease database. Per [BCP18], if available, a language identifier should be included in the output message.
RPCに関する情報：
delete-address-lease:
サーバーのリースデータベースから、個々のIPv6アドレスのリースを削除できるようにします。 [BCP18]に従い、可能であれば、出力メッセージには言語識別子を含めるべきです。
delete-prefix-lease:
サーバーのリースデータベースから、個々のIPv6プレフィックスのリースを削除できるようにします。 [BCP18]に従い、可能であれば、出力メッセージには言語識別子を含めるべきです。
Information about notifications:
address/prefix-pool-utilization-threshold-exceeded:
This is raised when the number of leased addresses or prefixes in a pool exceeds the configured usage threshold.
invalid-client-detected:
This is raised when the server detects an invalid client. A description of the error and message type that has generated the notification can be included.
decline-received:
This is raised when a DHCPv6 Decline message is received from a client.
non-success-code-sent:
This is raised when there is a status message for a failure. Status codes are drawn from [IANA-DHCPV6-STATUS-CODES].
通知に関する情報：
address/prefix-pool-utilization-threshold-exceeded:
プール内でリースされたアドレスまたはプレフィックスの数が、設定された使用率のしきい値を超えたときに発生します。
invalid-client-detected:

The tree diagram in Figure 3 provides an overview of the DHCPv6 client module. The tree also includes the common functions module defined in Section 4.1.

Descriptions of important nodes:
enabled:
This globally enables/disables all DHCPv6 client functions.
dhcpv6-client:
This container holds the client's DHCPv6-specific configuration.
client-if:
As a client may have multiple interfaces requesting configuration over DHCP, they are configured in a list. The 'if-name' leaf is the key and is an interface-ref to the applicable interface defined by the 'ietf-interfaces' YANG module.
enabled:
This enables/disables all DHCPv6 client function for the specific interface.
client-duid/interface-duid:
The DUID is used to identify the client to servers and relays. A DUID consists of a 2-octet type field and an arbitrary length (1-128 octets) content field. Currently, there are four DUID types defined in [RFC8415] and [RFC6355]. The DUID may be configured using the format for one of these types or using the 'unstructured' format. A DUID only needs to be configured if the client is requesting addresses and/or prefixes from the server. Presence of the 'client-duid' or 'interface-duid' leaves is conditional on at least one of the 'non-temp-addr', 'temp-addr', or 'prefix-delegation' features being enabled. Additionally, if the 'anon-profile' [RFC7844] feature is enabled, a unique DUID can be configured per a DHCP-enabled interface using the 'interface-duid' leaf; otherwise, there is a global 'client-duid' leaf.
client-configured-options:
This holds configuration parameters for DHCPv6 options that can be sent by the client. The initial set of applicable option definitions are defined here, and additional options that are also relevant to the relay and/or server are imported from the 'ietf-dhcpv6-common' module. Where needed, other DHCPv6 option modules can be augmented as they are defined. The complete list of DHCPV6 options is located at [IANA-DHCPV6-OPTION-CODES].
ia-na, ia-ta, ia-pd:
These contain configuration nodes relevant for requesting one or more of each of the lease types. Read-only nodes related to the active leases for each type are also located here, drawing the status codes from [IANA-DHCPV6-STATUS-CODES]. As these lease types may not be supported by all DHCPv6 client implementations, they are enabled via individual feature statements. Stateless DHCP (Section 6.1 of [RFC8415]) is configured when all address and prefix features are disabled.

dhcpv6-client:
このコンテナーは、クライアントのDHCPv6固有の設定を保持します。
client-if:
クライアントはDHCP経由で設定を要求するインターフェイスを複数持つことがあるため、それらはリストで設定されます。 「if-name」リーフはキーであり、「ietf-interfaces」YANGモジュールで定義されている該当するインターフェイスへのinterface-refです。
enabled:
特定のインターフェイスについて、すべてのDHCPv6クライアント機能を有効化／無効化します。
client-duid/interface-duid:
DUIDは、サーバーとリレーに対してクライアントを識別するために使用されます。 DUIDは、2オクテットのタイプフィールドと、任意の長さ（1〜128オクテット）のコンテンツフィールドで構成されます。 現在、[RFC8415]と[RFC6355]で4つのDUIDタイプが定義されています。 DUIDは、これらのタイプのいずれかの形式、または「unstructured」形式を使用して設定できます。 DUIDタイプの定義は、「ietf-dhcpv6-common.yang」モジュールからインポートされます。 関連するDUIDタイプについては、[IANA-HARDWARE-TYPES]と[IANA-PEN]を参照しています。 DUIDを設定する必要があるのは、クライアントがサーバーにアドレスやプレフィックスを要求する場合だけです。 「client-duid」リーフまたは「interface-duid」リーフが存在するのは、「non-temp-addr」、「temp-addr」、「prefix-delegation」の機能のうち少なくとも1つが有効になっている場合に限られます。 さらに、「anon-profile」[RFC7844]機能が有効になっている場合は、「interface-duid」リーフを使用して、DHCPが有効なインターフェイスごとに一意のDUIDを設定できます。そうでない場合は、グローバルな「client-duid」リーフがあります。
client-configured-options:
クライアントが送信できるDHCPv6オプションの設定パラメーターを保持します。 適用可能なオプション定義の初期セットはここで定義されており、リレーやサーバーにも関係する追加のオプションは「ietf-dhcpv6-common」モジュールからインポートされます。 必要に応じて、他のDHCPv6オプションモジュールが定義され次第、それらを拡張（augment）できます。 DHCPV6オプションの完全なリストは、[IANA-DHCPV6-OPTION-CODES]にあります。
ia-na, ia-ta, ia-pd:

Information about notifications:
invalid-ia-detected:
This is raised when the identity association of the client can be proved to be invalid. Possible conditions include duplicated address, illegal address, etc.
retransmission-failed:
This is raised when the retransmission mechanism defined in [RFC8415] has failed.
通知に関する情報：

5. Security Considerations

5. セキュリティーに関する考慮事項

The YANG modules specified in this document define schemas for data that is designed to be accessed via network management protocols such as NETCONF [RFC6241] or RESTCONF [RFC8040]. The lowest NETCONF layer is the secure transport layer, and the mandatory-to-implement secure transport is Secure Shell (SSH) [RFC6242]. The lowest RESTCONF layer is HTTPS, and the mandatory-to-implement secure transport is TLS [RFC8446].

この文書で規定するYANGモジュールは、NETCONF[RFC6241]やRESTCONF[RFC8040]などのネットワーク管理プロトコルを介してアクセスされるように設計されたデータのスキーマを定義します。 NETCONFの最下層はセキュアなトランスポート層であり、実装必須のセキュアなトランスポートはセキュアシェル（SSH）[RFC6242]です。 RESTCONFの最下層はHTTPSであり、実装必須のセキュアなトランスポートはTLS[RFC8446]です。

The Network Configuration Access Control Model (NACM) [RFC8341] provides the means to restrict access for particular NETCONF or RESTCONF users to a preconfigured subset of all available NETCONF or RESTCONF protocol operations and content.

ネットワーク構成アクセス制御モデル（NACM）[RFC8341]は、特定のNETCONFユーザーやRESTCONFユーザーのアクセスを、利用可能なすべてのNETCONFプロトコル操作やRESTCONFプロトコル操作とコンテンツのうち、事前に設定されたサブセットに制限する手段を提供します。

There are a number of data nodes defined in these YANG modules that are writable/creatable/deletable (i.e., config true, which is the default). These data nodes may be considered sensitive or vulnerable in some network environments. Write operations (e.g., edit-config) to these data nodes without proper protection can have a negative effect on network operations. These are the subtrees and data nodes in the 'ieft-dhcpv6-server.yang' module and their sensitivity/vulnerability:

これらのYANGモジュールには、書き込み可能／作成可能／削除可能な（つまり、デフォルトであるconfig trueの）データノードが多数定義されています。 これらのデータノードは、一部のネットワーク環境では機密性が高い、または脆弱であると考えられる場合があります。 適切な保護なしにこれらのデータノードに対して書き込み操作（たとえば、edit-config）を行うと、ネットワークの運用に悪影響を及ぼす可能性があります。 「ieft-dhcpv6-server.yang」モジュールのサブツリーとデータノード、およびそれらの機密性／脆弱性は次のとおりです。

  • Denial-of-Service (DoS) attacks, such as disabling the DHCP server service or removing address/prefix pool configuration:

    • (dhc6-srv/vendor-config)
    • (dhc6-srv/allocation-ranges)

  • Various attacks based on reconfiguring the contents of DHCPv6 options, leading to several types of security or privacy threats.     • (dhc6-srv/allocation-ranges)

The module is constructed as follows:

このモジュールは次のように構成されています。

  • The module is named using a meaningful, shortened version of the document name in which the DHCP option format is specified.
  • A separate grouping is used to define each option.
  • The name of the option is taken from the registered IANA name for the option, with an '-option' suffix added.
  • The description field is taken from the relevant option code name and number.
  • The reference section is the number and name of the RFC in which the DHCPv6 option is defined.
  • The remaining fields match the fields in the DHCP option. They are in the same order as defined in the DHCP option. Wherever possible, the format that is defined for the DHCP field should be matched by the relevant YANG type.
  • Fields that can have multiple entries or instances are defined using list or leaf-list nodes.
  • モジュールの名前には、DHCPオプションの形式が規定されている文書の名前を、意味のある形で短くしたものを使用します。
  • 各オプションの定義には、それぞれ別のグルーピングを使用します。
  • オプションの名前は、IANAに登録されたそのオプションの名前に「-option」という接尾辞を付けたものとします。
  • descriptionフィールドは、関連するオプションコードの名前と番号から取ります。
  • referenceセクションは、そのDHCPv6オプションが定義されているRFCの番号と名前です。
  • 残りのフィールドは、DHCPオプションのフィールドと一致させます。 それらは、DHCPオプションで定義されているのと同じ順序で並べます。 可能な限り、DHCPのフィールドに定義されている形式に、対応するYANGの型を一致させるべきです。
  • 複数のエントリーやインスタンスを持つことができるフィールドは、listノードまたはleaf-listノードを使用して定義します。

The example module defines additional server attributes, such as name and description. Storage for leases is configured using a lease-storage container. Appendix D. Example Definition of Class-Selector Configuration

Appendix D. クラスセレクター設定の定義例

The module "ietf-example-dhcpv6-class-selector" provides an example of how vendor-specific class selection configuration can be modeled and integrated with the "ietf-dhcpv6-server" module defined in this document.

モジュール「ietf-example-dhcpv6-class-selector」は、ベンダー固有のクラス選択の設定をモデル化し、この文書で定義する「ietf-dhcpv6-server」モジュールと統合する方法の例を示しています。

The example module defines "client-class-names" with associated matching rules. A client can be classified based on the "client-id", "interface-id" (ingress interface of the client's messages), packet's source or destination address, relay link address, relay link interface-id, and more. Actually, there are endless methods for classifying clients. So this standard does not try to provide full specification for class selection; it only shows an example of how it could be defined.

このモジュール例では、関連付けられたマッチング規則を持つ「client-class-names」を定義します。 クライアントは、「client-id」、「interface-id」（クライアントのメッセージの受信インターフェイス）、パケットの送信元アドレスまたは宛先アドレス、リレーのリンクアドレス、リレーのリンクのinterface-idなどに基づいて分類できます。 実際のところ、クライアントを分類する方法は無数にあります。 そのため、この標準はクラス選択の完全な仕様を提供しようとはせず、それをどのように定義できるかの例を示すだけにとどめています。

At the end of the example, augment statements are used to add the defined class selector rules into the overall DHCPv6 addressing hierarchy. This is done in two main parts:

この例の最後では、augmentステートメントを使用して、定義したクラスセレクターの規則をDHCPv6のアドレス指定の階層全体に追加しています。 これは主に次の2つの部分で行います。

  • the augmented class-selector configuration in the main DHCPv6 Server configuration
  • client-class leafrefs augmented to "allocation-range", "address-pool", and "pd-pool", pointing to the "client-class-name" that is required
  • メインのDHCPv6サーバー設定に拡張（augment）されたclass-selectorの設定
  • 「allocation-range」、「address-pool」、「pd-pool」に拡張（augment）され、必要な「client-class-name」を指すclient-classのleafref

The mechanism is as follows: class is associated to a client based on rules, and then a client is allowed to get an address(es) or a prefix(es) from a given allocation-range/pool if the class name matches.

このメカニズムは次のとおりです。規則に基づいてクライアントにクラスが関連付けられ、クラス名が一致する場合に、クライアントは指定されたallocation-range/poolからアドレスやプレフィックスを取得できるようになります。
