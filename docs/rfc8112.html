RFC 8112

Locator/ID Separation Protocol Delegated Database Tree (LISP-DDT) Referral Internet Groper (RIG)

RFC 8112

ロケーター/ID分離プロトコルの委任データベースツリー（LISP-DDT）のリファラルインターネットグローパー（RIG）

Abstract

概要

A simple tool called the Locator/ID Separation Protocol Delegated Database Tree (LISP-DDT) Referral Internet Groper (RIG), also referred to in this document as "rig", can be used to query the LISP- DDT hierarchy. This document describes how the "rig" tool works.

ロケーター/ID分離プロトコルの委任データベースツリー（Locator/ID Separation Protocol Delegated Database Tree、LISP-DDT）のリファラルインターネットグローパー（Referral Internet Groper、RIG）と呼ばれる単純なツール（この文書では「rig」とも呼びます）を使用して、LISP-DDTの階層に問い合わせることができます。この文書では、「rig」ツールの動作について説明します。

1. Introduction

1. はじめに

"The Locator/ID Separation Protocol (LISP)" [RFC6830] specifies an architecture and mechanism for replacing the semantics of an address currently used by IP with two separate namespaces: Endpoint Identifiers (EIDs), used within sites; and Routing Locators (RLOCs), used on the transit networks that make up the Internet infrastructure. To achieve this separation, LISP defines protocol mechanisms for mapping from EIDs to RLOCs. In addition, LISP assumes the existence of a database to store and propagate those mappings globally. This document focuses on the LISP Delegated Database Tree (LISP-DDT) [RFC8111] mapping database system.

「ロケーター/ID分離プロトコル（The Locator/ID Separation Protocol、LISP）」[RFC6830]は、現在IPで使用されているアドレスのセマンティクスを、2つの別々の名前空間で置き換えるためのアーキテクチャーとメカニズムを規定しています。その2つとは、サイト内で使用されるエンドポイントID（Endpoint Identifier、EID）と、インターネット基盤を構成するトランジットネットワーク上で使用されるルーティングロケーター（Routing Locator、RLOC）です。この分離を実現するために、LISPは、EIDからRLOCへのマッピングのためのプロトコルメカニズムを定義しています。さらに、LISPは、それらのマッピングをグローバルに格納して伝搬するデータベースが存在することを前提としています。この文書は、LISP委任データベースツリー（LISP Delegated Database Tree、LISP-DDT）[RFC8111]のマッピングデータベースシステムに焦点を当てます。

The "rig" tool is a manual management tool to query the LISP-DDT mapping database hierarchy. It can be run by all devices that implement LISP, including Ingress Tunnel Routers (ITRs), Egress Tunnel Routers (ETRs), Proxy ITRs (PITRs), Proxy ETRs (PETRs), Map-Resolvers, Map-Servers, and LISP-DDT nodes, as well as by a host system at either a LISP-capable or non-LISP-capable site.

「rig」ツールは、LISP-DDTのマッピングデータベースの階層に問い合わせるための、手動の管理ツールです。このツールは、入口トンネルルーター（Ingress Tunnel Router、ITR）、出口トンネルルーター（Egress Tunnel Router、ETR）、プロキシーITR（PITR）、プロキシーETR（PETR）、Map-Resolver、Map-Server、LISP-DDTノードを含む、LISPを実装するすべてのデバイスで実行できます。また、LISPに対応したサイトとLISPに対応していないサイトのどちらにあるホストシステムでも実行できます。

The LISP-DDT "rig" tool is similar to the "LISP Internet Groper" ("lig") tool [RFC6835] in that they are both diagnostic tools to query a database. However, the "rig" tool is used to find Map-Servers serving an EID-prefix, specifically within a LISP-DDT mapping database framework. And "lig" can be used on top of any mapping database system to retrieve locators used for packet encapsulation.

LISP-DDTの「rig」ツールは、どちらもデータベースに問い合わせるための診断ツールであるという点で、「LISPインターネットグローパー（LISP Internet Groper）」（「lig」）ツール[RFC6835]に似ています。ただし、「rig」ツールは、特にLISP-DDTのマッピングデータベースの枠組みの中で、EID-prefixを提供するMap-Serverを見つけるために使用されます。一方、「lig」は、任意のマッピングデータベースシステム上で、パケットのカプセル化に使用されるロケーターを取得するために使用できます。

3. Definitions of Terms

3. 用語の定義

Endpoint Identifier (EID):
a 32-bit (for IPv4) or 128-bit (for IPv6) value (or an address encoded per [RFC8060]) used in the source and destination address fields of the first (innermost) LISP header of a packet. The host obtains a destination EID the same way it obtains a destination address today -- for example, through a Domain Name System (DNS) [RFC1034] lookup or a Session Initiation Protocol (SIP) [RFC3261] exchange. The source EID is obtained via existing mechanisms used to set a host's "local" IP address. An EID used on the public Internet must have the same properties as any other IP address used in that manner; this means, among other things, that it must be globally unique. An EID is allocated to a host from an EID-prefix block associated with the site where the host is located. An EID can be used by a host to refer to other hosts. EIDs MUST NOT be used as LISP RLOCs. Note that EID blocks MAY be assigned in a hierarchical manner, independent of the network topology, to facilitate scaling of the mapping database. In addition, an EID block assigned to a site may have site-local structure (subnetting) for routing within the site; this structure is not visible to the global routing system. In theory, the bit string that represents an EID for one device can represent an RLOC for a different device. As the architecture is realized, if a given bit string is both an RLOC and an EID, it must refer to the same entity in both cases. When used in "discussions" with other Locator/ID separation proposals, a LISP EID will be called an "LEID". Throughout this document, any references to "EID" refer to an LEID.
Extended EID (XEID):
a LISP EID, optionally extended with a non-zero Instance ID (IID) if the EID is intended for use in a context where it may not be a unique value, such as in a Virtual Private Network where private address space [RFC1918] is used. See Section 5.5 of [RFC6830] for more discussion of IIDs.
Routing Locator (RLOC):
an IPv4 [RFC791] or IPv6 [RFC2460] address of an Egress Tunnel Router (ETR). An RLOC is the output of an EID-to-RLOC mapping lookup. An EID maps to one or more RLOCs. Typically, RLOCs are numbered from topologically aggregatable blocks that are assigned to a site at each point to which it attaches to the global Internet; where the topology is defined by the connectivity of provider networks, RLOCs can be thought of as Provider-Assigned (PA) addresses. Multiple RLOCs can be assigned to the same ETR device or to multiple ETR devices at a site.
DDT node:
a network infrastructure component responsible for specific XEID-prefix(es) and for the delegation of more-specific sub-prefixes to other DDT nodes.
DDT client:
a network infrastructure component that sends DDT Map-Request messages and implements the iterative following of Map-Referral results. Typically, a DDT client will be a Map-Resolver (as defined by [RFC6833]), but it is also possible for an ITR to implement DDT client functionality. A DDT client can be a device that is originating "rig" requests.
DDT Map-Server:
a DDT node that also implements Map-Server functionality (forwarding Map-Requests and/or returning Map-Replies if offering a proxy Map-Reply service) for a subset of its delegated prefixes. Map-Server functions, including proxying Map-Replies, are described in [RFC6833].
DDT Map-Resolver:
a network infrastructure element that accepts a Map-Request, adds the XEID to its lookup queue, then queries one or more DDT nodes for the requested EID, following returned referrals until it receives one with the MS-ACK action code [RFC8111]. This indicates that the Map-Request has been sent to a Map-Server that will forward it to an ETR that, in turn, will provide a Map-Reply to the original sender. A DDT Map-Resolver maintains both (1) a cache of Map-Referral message results (termed the "referral cache") containing RLOCs for DDT nodes responsible for XEID-prefixes of interest and (2) a lookup queue of XEIDs that are being resolved through iterative querying of DDT nodes.
Encapsulated Map-Request:
a LISP Map-Request that is carried within an Encapsulated Control Message (ECM) and that has an additional LISP header prepended. Sent to UDP destination port 4342. The "outer" addresses are globally routable IP addresses, also known as RLOCs. Used by an ITR when sending a Map-Request to a Map-Resolver and by a Map-Server when forwarding a Map-Request to an ETR as documented in [RFC6833].
Map-Referral:
a LISP message sent by a DDT node when it receives a DDT Map-Request for an XEID that matches a configured XEID-prefix delegation. A non-Negative Map-Referral message includes a "referral" -- a set of RLOCs for DDT nodes that have more information about the sub-prefix; a DDT client "follows the referral" by sending another DDT Map-Request to one of those RLOCs to obtain either an answer or another referral to DDT nodes responsible for a more-specific XEID-prefix.
Authoritative XEID-prefix:
an XEID-prefix delegated to a DDT node and for which the DDT node may provide further delegations of more-specific sub-prefixes.
エンドポイントID（Endpoint Identifier、EID）：
パケットの最初の（最も内側の）LISPヘッダーの送信元アドレスフィールドと宛先アドレスフィールドで使用される、32ビット（IPv4の場合）または128ビット（IPv6の場合）の値（または[RFC8060]に従ってエンコードされたアドレス）です。ホストは、今日宛先アドレスを取得するのと同じ方法で、たとえばドメインネームシステム（DNS）[RFC1034]の検索やセッション開始プロトコル（SIP）[RFC3261]のやり取りを通じて、宛先EIDを取得します。送信元EIDは、ホストの「ローカル」IPアドレスを設定するために使用される既存のメカニズムを通じて取得されます。公衆インターネット上で使用されるEIDは、そのように使用されるほかのIPアドレスと同じ性質を持つ必要があります。これは特に、EIDがグローバルに一意である必要があることを意味します。EIDは、ホストが位置するサイトに関連付けられたEID-prefixブロックからホストに割り当てられます。EIDは、ホストがほかのホストを参照するために使用できます。EIDをLISPのRLOCとして使用してはなりません（MUST NOT）。マッピングデータベースのスケーリングを容易にするために、EIDブロックをネットワークトポロジーとは独立に階層的な方法で割り当ててもよいです（MAY）。さらに、サイトに割り当てられたEIDブロックは、サイト内でのルーティングのためにサイトローカルな構造（サブネット化）を持つことがあります。この構造は、グローバルなルーティングシステムからは見えません。理論的には、あるデバイスのEIDを表すビット列が、別のデバイスのRLOCを表すこともありえます。アーキテクチャーが実現される際、あるビット列がRLOCでもありEIDでもある場合、そのビット列はどちらの場合も同じ実体を指す必要があります。ほかのロケーター/ID分離の提案との「議論」において使用する場合、LISPのEIDは「LEID」と呼ばれます。この文書全体を通じて、「EID」への言及はすべてLEIDを指します。
拡張EID（Extended EID、XEID）：
LISPのEIDであり、そのEIDが一意の値とは限らないコンテキスト（たとえば、プライベートアドレス空間[RFC1918]が使用される仮想プライベートネットワーク）で使用されることを意図している場合は、0以外のインスタンスID（Instance ID、IID）で拡張されることもあります。IIDのさらなる議論については、[RFC6830]のセクション5.5を参照してください。
ルーティングロケーター（Routing Locator、RLOC）：
出口トンネルルーター（ETR）のIPv4アドレス[RFC791]またはIPv6アドレス[RFC2460]です。RLOCは、EIDからRLOCへのマッピングの検索の出力です。EIDは、1つ以上のRLOCにマッピングされます。通常、RLOCは、サイトがグローバルインターネットに接続する各地点でそのサイトに割り当てられた、トポロジー的に集約可能なブロックから番号付けされます。トポロジーがプロバイダーネットワークの接続性によって定義される場合、RLOCはプロバイダー割り当て（Provider-Assigned、PA）アドレスとみなすことができます。複数のRLOCを、同じETRデバイスに割り当てることも、サイトの複数のETRデバイスに割り当てることもできます。
DDTノード（DDT node）：
特定のXEID-prefixと、より詳細なサブプレフィックスのほかのDDTノードへの委任とを担当する、ネットワーク基盤コンポーネントです。
DDTクライアント（DDT client）：
DDT Map-Requestメッセージを送信し、Map-Referralの結果を反復的にたどる処理を実装するネットワーク基盤コンポーネントです。通常、DDTクライアントは（[RFC6833]で定義される）Map-Resolverですが、ITRがDDTクライアントの機能を実装することもできます。DDTクライアントは、「rig」リクエストを発信するデバイスである場合もあります。
DDT Map-Server：
委任されたプレフィックスのサブセットに対して、Map-Serverの機能（Map-Requestの転送と、プロキシーMap-Replyサービスを提供している場合はMap-Replyの返送の一方または両方）も実装するDDTノードです。Map-Replyのプロキシーを含むMap-Serverの機能は、[RFC6833]で説明されています。
DDT Map-Resolver：
Map-Requestを受け付け、そのXEIDを自身の検索キューに追加し、リクエストされたEIDについて1つ以上のDDTノードに問い合わせ、MS-ACKアクションコード[RFC8111]を持つリファラルを受信するまで、返されたリファラルをたどるネットワーク基盤要素です。MS-ACKは、Map-RequestがMap-Serverに送信されたことを示します。そのMap-ServerはMap-RequestをETRに転送し、そのETRが元の送信者にMap-Replyを提供します。DDT Map-Resolverは、（1）関心のあるXEID-prefixを担当するDDTノードのRLOCを含む、Map-Referralメッセージの結果のキャッシュ（「リファラルキャッシュ（referral cache）」と呼びます）と、（2）DDTノードへの反復的な問い合わせによって解決中のXEIDの検索キューの両方を保持します。
カプセル化されたMap-Request（Encapsulated Map-Request）：
カプセル化制御メッセージ（Encapsulated Control Message、ECM）内で運ばれ、追加のLISPヘッダーが先頭に付加されたLISPのMap-Requestです。UDP宛先ポート4342に送信されます。「外側」のアドレスはグローバルにルーティング可能なIPアドレスであり、RLOCとも呼ばれます。[RFC6833]に記載されているように、ITRがMap-ResolverにMap-Requestを送信する際や、Map-ServerがETRにMap-Requestを転送する際に使用されます。
Map-Referral：
設定されたXEID-prefixの委任に一致するXEIDについてのDDT Map-Requestを受信したときに、DDTノードが送信するLISPメッセージです。ネガティブでないMap-Referralメッセージには「リファラル」、すなわち、そのサブプレフィックスについてより多くの情報を持つDDTノードのRLOCのセットが含まれます。DDTクライアントは、答えか、より詳細なXEID-prefixを担当するDDTノードへの別のリファラルのいずれかを得るために、それらのRLOCの1つに別のDDT Map-Requestを送信することによって「リファラルをたどり」ます。
権威XEID-prefix（Authoritative XEID-prefix）：
DDTノードに委任されたXEID-prefixであり、そのDDTノードがより詳細なサブプレフィックスのさらなる委任を提供できるものです。

4. Basic Overview

4. 基本的な概要

LISP-DDT [RFC8111] is a hierarchical distributed database that embodies the delegation of authority to provide mappings from LISP EIDs to RLOCs. It is a statically defined distribution of the EID namespace among a set of LISP-speaking servers called "DDT nodes". Each DDT node is configured as "authoritative" for one or more EID-prefixes, along with the set of RLOCs for Map-Servers or "child" DDT nodes to which more-specific EID-prefixes are delegated.

LISP-DDT [RFC8111]は、LISPのEIDからRLOCへのマッピングを提供する権限の委任を体現した、階層的な分散データベースです。これは、「DDTノード」と呼ばれる、LISPを話すサーバーの集合の間でEID名前空間を静的に定義して分散したものです。各DDTノードは、1つ以上のEID-prefixに対して「権威を持つ」ものとして設定され、あわせて、より詳細なEID-prefixの委任先であるMap-Serverまたは「子」DDTノードのRLOCのセットも設定されます。

Map-Resolvers send Map-Requests to the DDT hierarchy and maintain referral caches by receiving Map-Referral messages from DDT nodes. Map-Resolvers follow the DDT hierarchy for a given EID lookup based on the EID-prefix and delegation referrals contained in the Map-Referral messages. The "rig" tool is intended to perform the same operation as that of a Map-Resolver but to also be used as a management tool for the network administrator.

Map-Resolverは、DDT階層にMap-Requestを送信し、DDTノードからMap-Referralメッセージを受信することによってリファラルキャッシュを保持します。Map-Resolverは、Map-Referralメッセージに含まれるEID-prefixと委任のリファラルに基づいて、あるEIDの検索のためにDDT階層をたどります。「rig」ツールは、Map-Resolverと同じ操作を実行するとともに、ネットワーク管理者のための管理ツールとしても使用されることを意図しています。

When the "rig" command is run, an Encapsulated Control Message Map-Request is sent for a destination EID. When a LISP-DDT Map-Referral is returned, the contents are displayed to the user. The information displayed includes:

「rig」コマンドを実行すると、宛先EIDに対するカプセル化制御メッセージのMap-Requestが送信されます。LISP-DDTのMap-Referralが返されると、その内容がユーザーに表示されます。表示される情報には次のものが含まれます。

  • A delegated EID-prefix configured in a DDT node or a configured site EID-prefix in a DDT Map-Server that matches the requested EID.

  • The type of DDT node that sent the Map-Referral.

  • The action code and TTL set by the sender of the Map-Referral.

  • The referral RLOC addresses from the Map-Referral message.

  • A round-trip-time estimate for the ECM-Map-Request / Map-Referral message exchange.

  • DDTノードに設定された委任EID-prefix、またはDDT Map-Serverに設定されたサイトのEID-prefixのうち、リクエストされたEIDに一致するもの。

  • Map-Referralを送信したDDTノードの種類。

  • Map-Referralの送信者が設定したアクションコードとTTL。

  • Map-Referralメッセージに含まれるリファラルのRLOCアドレス。

  • ECM-Map-RequestとMap-Referralのメッセージ交換の往復時間の推定値。

A possible syntax for a "rig" command MAY be:

「rig」コマンドの構文は、たとえば次のようにしてもよいです（MAY）。

rig [instance-id <iid>] <eid> to <ddt-node> [follow-all-referrals]

rig [instance-id <iid>] <eid> to <ddt-node> [follow-all-referrals]

Parameter descriptions:

パラメーターの説明：

[instance-id <iid>]:
<iid> is the IID portion of the XEID used as a VPN identifier or for other future purposes. When the DDT hierarchy is not configured with IIDs, this argument is omitted from the command line.
<eid>:
<eid> is either a Fully Qualified Domain Name or a destination EID that is being queried in the LISP-DDT mapping database.
<ddt-node>:
<ddt-node> is the RLOC address of any DDT node in the DDT hierarchy. This can be the DDT root node, a DDT transit node, or a DDT Map-Server.
[follow-all-referrals]:
When this keyword is used, each referral RLOC is queried so "rig" can descend the entire DDT hierarchy starting from the node <ddt-node>. When this keyword is not used, one of the referral RLOCs will be selected to descend a branch of the DDT hierarchy.
[instance-id <iid>]：
<iid>は、VPN識別子として、または将来のほかの目的のために使用される、XEIDのIIDの部分です。DDT階層にIIDが設定されていない場合、この引数はコマンドラインから省略されます。
<eid>：
<eid>は、完全修飾ドメイン名、またはLISP-DDTのマッピングデータベースで問い合わせ対象となっている宛先EIDのいずれかです。
<ddt-node>：
<ddt-node>は、DDT階層内の任意のDDTノードのRLOCアドレスです。これは、DDTルートノード、DDTトランジットノード、DDT Map-Serverのいずれでもかまいません。
[follow-all-referrals]：
このキーワードを使用すると、リファラルの各RLOCに問い合わせが行われ、「rig」はノード<ddt-node>から始まるDDT階層全体をたどることができます。このキーワードを使用しない場合は、リファラルのRLOCの1つが選択され、DDT階層の1つの枝をたどります。

The "rig" utility not only shows branches of the delegation hierarchy but can also report:

「rig」ユーティリティーは、委任階層の枝を表示するだけでなく、次のことも報告できます。

  • When a DDT Map-Server would forward a Map-Request to the ETRs at a registered LISP site. This is known as an "MS-ACK" action.

  • When a DDT Map-Server sends a Negative Map-Referral indicating that a requested EID is configured but not registered to the mapping database system. This is known as an "MS-NOT-REGISTERED" action.

  • When a DDT node is sending referrals for a transit or leaf node in the hierarchy. These are known as "NODE-REFERRAL" and "MS-REFERRAL" actions, respectively.

  • When a DDT node finds a hole in the address space that has not been allocated or configured in the delegation hierarchy. This is typically associated with a hole in a DDT node's configured authoritative prefix. This is known as a "DELEGATION-HOLE" action.

  • When a DDT node finds a hole in the address space that has not been allocated or configured in the delegation hierarchy at all. This is typically associated with a hole that is outside of a DDT node's authoritative prefix. This is known as a "NOT-AUTHORITATIVE" action.

  • DDT Map-Serverが、登録済みのLISPサイトのETRにMap-Requestを転送する場合。これは「MS-ACK」アクションとして知られています。

  • DDT Map-Serverが、リクエストされたEIDは設定されているがマッピングデータベースシステムに登録されていないことを示すネガティブMap-Referralを送信する場合。これは「MS-NOT-REGISTERED」アクションとして知られています。

  • DDTノードが、階層内のトランジットノードまたは葉ノードへのリファラルを送信している場合。これらはそれぞれ「NODE-REFERRAL」アクション、「MS-REFERRAL」アクションとして知られています。

  • DDTノードが、委任階層において割り当ても設定もされていない、アドレス空間内の穴を見つけた場合。これは通常、DDTノードに設定された権威を持つプレフィックス内の穴に関連します。これは「DELEGATION-HOLE」アクションとして知られています。

  • DDTノードが、委任階層においてまったく割り当ても設定もされていない、アドレス空間内の穴を見つけた場合。これは通常、DDTノードの権威を持つプレフィックスの外側にある穴に関連します。これは「NOT-AUTHORITATIVE」アクションとして知られています。

Refer to [RFC8111] for more details about Map-Referral actions.

Map-Referralのアクションの詳細については、[RFC8111]を参照してください。

5. Implementation Details

5. 実装の詳細

The Cisco LISP prototype implementations on IOS and NX-OS have "rig" support for IPv4 and IPv6 EIDs in either the default instance or a non-zero IID.

IOSとNX-OS上のCiscoのLISPプロトタイプ実装は、デフォルトインスタンスと0以外のIIDのどちらにおいても、IPv4とIPv6のEIDに対する「rig」をサポートしています。

The IOS syntax is:

IOSの構文は次のとおりです。

rig [instance-id <iid>] <eid> to <ddt-node> [follow-all-referrals]

rig [instance-id <iid>] <eid> to <ddt-node> [follow-all-referrals]

The NX-OS syntax is:

NX-OSの構文は次のとおりです。

rig [instance-id <iid>] { <hostname> | {<eid> | <eid6>} }
                        to { <ddt-hostname> | {<ddt> | <ddt6>} }

rig [instance-id <iid>] { <hostname> | {<eid> | <eid6>} }
                        to { <ddt-hostname> | {<ddt> | <ddt6>} }

6. Security Considerations

6. セキュリティーに関する考慮事項

The use of "rig" does not affect the security of the LISP infrastructure, as it is simply a tool that facilitates diagnostic querying. See [RFC6830], [RFC6833], [RFC7835], and [RFC8111] for descriptions of the security properties of the LISP infrastructure.

「rig」は診断のための問い合わせを容易にするツールにすぎないため、「rig」の使用はLISP基盤のセキュリティーに影響を与えません。LISP基盤のセキュリティー特性の説明については、[RFC6830]、[RFC6833]、[RFC7835]、[RFC8111]を参照してください。

LISP "rig" provides easy access to the information in the public mapping database. Therefore, it is important to protect the mapping information for private use. This can be provided by disallowing access to specific mapping entries or placing such entries in a private mapping database system.

LISPの「rig」は、公開マッピングデータベース内の情報への容易なアクセスを提供します。したがって、プライベートな用途のマッピング情報を保護することが重要です。これは、特定のマッピングエントリーへのアクセスを禁止するか、そのようなエントリーをプライベートなマッピングデータベースシステムに置くことによって実現できます。
