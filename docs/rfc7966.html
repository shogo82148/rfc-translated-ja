RFC 7966

Security at the Attribute-Value Pair (AVP) Level for Non-neighboring Diameter Nodes: Scenarios and Requirements

RFC 7966

隣接していないDiameterノード間の属性値ペア（AVP）レベルのセキュリティー: シナリオと要件

Abstract

概要

This specification specifies requirements for providing Diameter security at the level of individual Attribute-Value Pairs (AVPs).

この仕様は、個々の属性値ペア（Attribute-Value Pair、AVP）のレベルでDiameterのセキュリティーを提供するための要件を規定します。

1. Introduction

1. はじめに

The Diameter base protocol specification [2] defines security protection between neighboring Diameter peers. Diameter mandates that peer connections must be protected by Transport Layer Security (TLS) [6] for TCP, by Datagram TLS (DTLS) [7] for the Stream Control Transmission Protocol (SCTP), or by security mechanisms that are independent of Diameter (such as IPsec [5]). These security protocols offer a wide range of security properties, including entity authentication, data-origin authentication, integrity protection, confidentiality protection, and replay protection. They also support a large number of cryptographic algorithms, algorithm negotiation, and different types of credentials. It should be understood that TLS/DTLS/IPsec in the Diameter context does not provide end-to-end security unless the Diameter nodes are direct peers, i.e., neighboring Diameter nodes. The current Diameter security is realized hop by hop.

Diameter基本プロトコルの仕様[2]は、隣接するDiameterピア間のセキュリティー保護を定義しています。Diameterでは、ピア間のコネクションを、TCPの場合はトランスポート層セキュリティー（Transport Layer Security、TLS）[6]で、ストリーム制御伝送プロトコル（Stream Control Transmission Protocol、SCTP）の場合はDatagram TLS（DTLS）[7]で、あるいはDiameterとは独立したセキュリティーメカニズム（IPsec[5]など）で保護しなければならないと定めています。これらのセキュリティープロトコルは、エンティティー認証、データ発信元認証、完全性保護、機密性保護、リプレイ保護など、幅広いセキュリティー特性を提供します。また、多数の暗号アルゴリズム、アルゴリズムのネゴシエーション、さまざまな種類のクレデンシャルもサポートしています。Diameterの文脈におけるTLS/DTLS/IPsecは、Diameterノード同士が直接のピア、すなわち隣接するDiameterノードでない限り、エンドツーエンドのセキュリティーを提供しないことを理解しておくべきです。現在のDiameterのセキュリティーは、ホップバイホップで実現されています。

The need to also offer additional security protection of AVPs between non-neighboring Diameter nodes was recognized very early in the work on Diameter. This led to work on Diameter security using the Cryptographic Message Syntax (CMS) [3]. However, due to the lack of deployment interest at that time (and the complexity of the developed solution), the specification was never completed.

隣接していないDiameterノード間でもAVPに追加のセキュリティー保護を提供する必要性は、Diameterの作業のごく初期から認識されていました。これを受けて、暗号メッセージ構文（Cryptographic Message Syntax、CMS）を使ったDiameterのセキュリティーに関する作業[3]が行われました。しかし、当時は展開への関心が乏しかった（そして開発された解決策が複雑だった）ため、その仕様が完成することはありませんでした。

In the meanwhile, Diameter had received a lot of deployment interest from the cellular operator community, and because of the sophistication of those deployments, the need for protecting Diameter AVPs between non-neighboring nodes resurfaced. Since the early 2000s (when the work on [3] was discontinued), the Internet community has seen advances in cryptographic algorithms (for example, authenticated encryption algorithms), and new security building blocks have been developed.

その間に、Diameterはセルラー事業者のコミュニティーから展開への大きな関心を集めるようになり、そうした展開が高度化したことで、隣接していないノード間でDiameterのAVPを保護する必要性が再び浮上しました。2000年代初頭（[3]の作業が中止されたころ）以降、インターネットコミュニティーでは暗号アルゴリズム（たとえば、認証付き暗号アルゴリズム）が進歩し、新しいセキュリティーの構成要素が開発されてきました。

This document specifies requirements for developing a solution to protect Diameter AVPs between non-neighboring Diameter nodes.

この文書は、隣接していないDiameterノード間でDiameterのAVPを保護する解決策を開発するための要件を規定します。

2. 用語

The key words 'MUST', 'MUST NOT', 'REQUIRED', 'SHALL', 'SHALL NOT', 'SHOULD', 'SHOULD NOT', 'RECOMMENDED', 'MAY', and 'OPTIONAL' in this document are to be interpreted as described in RFC 2119 [1].

この文書におけるキーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、「要求されています（REQUIRED）」、「することになります（SHALL）」、「することはありません（SHALL NOT）」、「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、「推奨されます（RECOMMENDED）」、「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、RFC 2119[1]で説明されているように解釈されます。

This document reuses terminology from the Diameter base specification [2].

この文書は、Diameter基本仕様[2]の用語を再利用します。

In the figures below, AVP refers to an unprotected AVP, and {AVP}k refers to an AVP that experiences security protection (using key "k") without further distinguishing between integrity and confidentiality protection.

以下の図において、AVPは保護されていないAVPを指し、{AVP}kは（鍵「k」を使って）セキュリティー保護を受けたAVPを指します。完全性保護と機密性保護はそれ以上区別しません。

The following terms are also used in this document:

この文書では、次の用語も使います。

AAA broker
An entity that manages Authentication, Authorization, and Accounting (AAA) traffic between roaming partner networks.
AAA broker network
A network operated by a AAA broker, which consists of necessary AAA functions to provide AAA brokering services for its customer AAA networks.
Diameter firewall
A Diameter firewall is a proxy (or a relay) agent that acts similarly to conventional IP traffic firewalls but only at the Diameter AVP and command level. A Diameter firewall may, for example, discard AVPs that violate security policy, thus preventing them from traversing the firewall. The Diameter firewall may even discard entire Diameter messages based on the security policy.
AAAブローカー（AAA broker）
ローミングパートナーのネットワーク間で、認証、認可、課金（Authentication, Authorization, and Accounting、AAA）のトラフィックを管理するエンティティー。
AAAブローカーネットワーク（AAA broker network）
AAAブローカーが運用するネットワークであり、顧客のAAAネットワークにAAAのブローカリングサービスを提供するのに必要なAAA機能で構成されます。
Diameterファイアウォール（Diameter firewall）
Diameterファイアウォールは、従来のIPトラフィックのファイアウォールと同様に動作しますが、DiameterのAVPとコマンドのレベルでのみ動作するプロキシー（または中継）エージェントです。たとえば、Diameterファイアウォールは、セキュリティーポリシーに違反するAVPを破棄して、それらがファイアウォールを通過できないようにすることがあります。Diameterファイアウォールは、セキュリティーポリシーに基づいてDiameterメッセージ全体を破棄することさえあります。

3. Security Threats

3. セキュリティー上の脅威

This section describes various security threats that raise the need for protecting Diameter Attribute-Value Pairs (AVPs). Figure 1 illustrates an example of a Diameter-based roaming architecture in which Diameter clients within the visited networks need to interact with Diameter servers in the home domain. AAA domains are interconnected using a Diameter-based AAA interconnection network labeled as "AAA broker network".

このセクションでは、Diameterの属性値ペア（Attribute-Value Pair、AVP）を保護する必要性を生じさせるさまざまなセキュリティー上の脅威について説明します。図1は、訪問先ネットワーク内のDiameterクライアントがホームドメインのDiameterサーバーとやり取りする必要がある、Diameterベースのローミングアーキテクチャーの例を示しています。AAAドメイン同士は、「AAAブローカーネットワーク（AAA broker network）」と名付けられたDiameterベースのAAA相互接続ネットワークを使って相互に接続されています。

Eavesdropping:

Some Diameter applications carry information that is only intended for consumption by end points, either by the Diameter client or by the Diameter server but not by intermediaries. As an example, consider the Diameter Extensible Authentication Protocol (EAP) application [4] that allows the transport of keying material between the Diameter server to the Diameter client (using the EAP-Master-Session-Key AVP) for the protection of the air interface (i.e., the wireless link) between the end device (such as a mobile phone; not shown in the figure) and the Network Access Server (NAS). The content of the EAP-Master-Session-Key AVP should benefit from protection against eavesdropping by intermediaries. Other AVPs (for example, those listed in Section 13.3 of [2]) might also carry sensitive personal data that, when collected by intermediaries, allow for traffic analysis.

In the context of the deployment shown in Figure 1, the adversary could, for example, be in the AAA broker network.

Injection and Manipulation:

The Diameter base protocol specification mandates security protection between neighboring nodes, but Diameter agents may be compromised or misconfigured and inject or manipulate AVPs. To detect such actions, additional security protection needs to be applied at the Diameter layer.

Nodes that could launch such an attack are any Diameter agents along the end-to-end communication path.

Impersonation:

Imagine a case where a Diameter message from Example.net contains information claiming to be from Example.org. This would either require strict verification at the edge of the AAA broker network or cryptographic assurance at the Diameter layer to prevent a successful impersonation attack.

Any Diameter realm could launch such an attack aiming for financial benefits or to disrupt service availability.

盗聴（Eavesdropping）:

Diameterアプリケーションの中には、エンドポイント、つまりDiameterクライアントまたはDiameterサーバーだけが利用することを意図し、仲介者が利用することは意図していない情報を運ぶものがあります。例として、Diameterの拡張認証プロトコル（Extensible Authentication Protocol、EAP）アプリケーション[4]を考えてみます。このアプリケーションでは、エンドデバイス（携帯電話など。図には示していません）とネットワークアクセスサーバー（Network Access Server、NAS）の間のエアインターフェイス（つまり無線リンク）を保護するために、（EAP-Master-Session-Key AVPを使って）DiameterサーバーからDiameterクライアントへ鍵素材を転送できます。EAP-Master-Session-Key AVPの内容は、仲介者による盗聴から保護されるべきものです。他のAVP（たとえば、[2]のセクション13.3に挙げられているもの）も、機密性の高い個人データを運ぶ可能性があり、仲介者がそれを収集するとトラフィック分析が可能になります。

図1に示した展開の文脈では、攻撃者はたとえばAAAブローカーネットワーク内にいる可能性があります。

挿入と改ざん（Injection and Manipulation）:

Diameter基本プロトコルの仕様は、隣接するノード間のセキュリティー保護を義務付けていますが、Diameterエージェントが侵害されたり設定を誤ったりして、AVPを挿入または改ざんすることがあります。そのような行為を検出するには、Diameter層で追加のセキュリティー保護を適用する必要があります。

このような攻撃を仕掛けうるノードは、エンドツーエンドの通信経路上にあるあらゆるDiameterエージェントです。

なりすまし（Impersonation）:

Example.netからのDiameterメッセージに、Example.orgからのものであると主張する情報が含まれている場合を想像してください。なりすまし攻撃の成功を防ぐには、AAAブローカーネットワークの境界での厳密な検証か、Diameter層での暗号学的な保証のいずれかが必要になります。

金銭的な利益を狙って、あるいはサービスの可用性を損なうために、どのDiameterレルムもこのような攻撃を仕掛ける可能性があります。

4. Scenarios for Diameter AVP-Level Protection

4. DiameterのAVPレベルの保護のシナリオ

This scenario outlines a number of cases for deploying security protection of individual Diameter AVPs.

このシナリオでは、個々のDiameter AVPのセキュリティー保護を展開するいくつかのケースの概要を示します。

In the first scenario, shown in Figure 2, end-to-end security protection is provided between the Diameter client and the Diameter server with any number of intermediate Diameter agents. Diameter AVPs exchanged between these two Diameter nodes may be protected end to end (notation '{AVP}k') or unprotected (notation 'AVP').

図2に示す1つ目のシナリオでは、DiameterクライアントとDiameterサーバーの間に任意の数の中間Diameterエージェントがある状態で、両者の間でエンドツーエンドのセキュリティー保護を提供します。これら2つのDiameterノード間で交換されるDiameter AVPは、エンドツーエンドで保護される（表記「{AVP}k」）場合もあれば、保護されない（表記「AVP」）場合もあります。

In the second scenario, shown in Figure 3, a Diameter proxy acts on behalf of the Diameter client with regard to security protection. It applies security protection to outgoing Diameter AVPs and verifies incoming AVPs. Typically, the proxy enforcing the security protection belongs to the same domain as the Diameter client/server without end-to-end security features.

図3に示す2つ目のシナリオでは、セキュリティー保護に関して、DiameterプロキシーがDiameterクライアントの代わりに動作します。このプロキシーは、送出するDiameter AVPにセキュリティー保護を適用し、受信したAVPを検証します。通常、セキュリティー保護を実施するプロキシーは、エンドツーエンドのセキュリティー機能を持たないDiameterクライアント/サーバーと同じドメインに属します。

In the third scenario, shown in Figure 4, a Diameter proxy acts on behalf of the Diameter server.

図4に示す3つ目のシナリオでは、DiameterプロキシーがDiameterサーバーの代わりに動作します。

The fourth and the final scenario (see Figure 5) is a combination of the middle-to-end and the end-to-middle scenarios shown in Figures 3 and 4. From a deployment point of view, this scenario is easier to accomplish for two reasons. First, Diameter clients and Diameter servers remain unmodified. This ensures that no modifications are needed to the installed Diameter infrastructure, except for the security-enabled proxies, obviously. Second, the key management is also simplified since a fewer number of keys need to be negotiated and provisioned. The assumption here is that the number of security-enabled proxies would be significantly less than unprotected Diameter nodes in the installed base.

4つ目にして最後のシナリオ（図5を参照）は、図3と図4に示したミドルツーエンドとエンドツーミドルのシナリオを組み合わせたものです。展開の観点からは、このシナリオは2つの理由で実現しやすくなります。第一に、DiameterクライアントとDiameterサーバーは変更されないままです。これにより、当然ながらセキュリティー機能を有効にしたプロキシーを除いて、導入済みのDiameterインフラストラクチャーに変更を加える必要がなくなります。第二に、ネゴシエートしてプロビジョニングする必要のある鍵の数が少なくなるため、鍵管理も簡単になります。ここでは、セキュリティー機能を有効にしたプロキシーの数は、導入済みの保護されていないDiameterノードの数よりもかなり少なくなると想定しています。

5. Requirements

5. 要件

Requirement #1:

The solution MUST support an extensible set of cryptographic algorithms.

Motivation: Solutions MUST be able to evolve to adapt to evolving cryptographic algorithms and security requirements. This may include the provision of a modular mechanism to allow cryptographic algorithms to be updated without substantial disruption to deployed implementations.

Requirement #2:

The solution MUST support confidentiality, integrity, and data-origin authentication. Solutions for integrity protection MUST work in a backwards-compatible way with existing Diameter applications and therefore be able to traverse legacy proxy and relay agents.

Requirement #3:

The solution MUST support replay protection.

Requirement #4:

The solution MUST support the ability to delegate security functionality to another entity.

Motivation: As described in Section 4, the ability to let a Diameter proxy perform security services on behalf of all clients within the same administrative domain is important for incremental deployability. The same applies to the other communication side where a load balancer terminates security services for the servers it interfaces.

Requirement #5:

The solution MUST be able to selectively apply its cryptographic protection to certain Diameter AVPs.

Motivation: Some Diameter applications assume that certain AVPs are added, removed, or modified by intermediaries. As such, it must be possible to apply security protection selectively.

Furthermore, there are AVPs that must not be confidentiality protected but may still be integrity protected, such as those required for Diameter message routing.

Requirement #6:

The solution MUST define a mandatory-to-implement cryptographic algorithm.

Motivation: For interoperability purposes, it is beneficial to have a mandatory-to-implement cryptographic algorithm specified (unless profiles for specific usage environments specify otherwise).

Requirement #7:

The solution MUST support symmetric keys and asymmetric keys.

Motivation: Symmetric and asymmetric cryptographic algorithms provide different security services. Asymmetric algorithms, for example, allow non-repudiation services to be offered.

Requirement #8:

A solution for dynamic key management MUST be included in the overall solution framework.

However, it is assumed that no "new" key management protocol needs to be developed; instead, existing ones are reused, if at all possible. Rekeying could be triggered by (a) management actions and (b) expiring keying material.

要件1:

解決策は、拡張可能な暗号アルゴリズムのセットをサポートしなければなりません（MUST）。

動機: 解決策は、進化する暗号アルゴリズムとセキュリティー要件に適応するように発展できる必要があります（MUST）。これには、展開済みの実装に大きな混乱を与えることなく暗号アルゴリズムを更新できるようにする、モジュール化されたメカニズムを提供することが含まれるかもしれません。

要件2:

解決策は、機密性、完全性、データ発信元認証をサポートしなければなりません（MUST）。完全性保護の解決策は、既存のDiameterアプリケーションと後方互換性のある方法で動作し、それによってレガシーなプロキシーエージェントや中継エージェントを通過できる必要があります（MUST）。

要件3:

解決策は、リプレイ保護をサポートしなければなりません（MUST）。

要件4:

解決策は、セキュリティー機能を別のエンティティーに委任する機能をサポートしなければなりません（MUST）。

動機: セクション4で説明したように、同じ管理ドメイン内のすべてのクライアントの代わりにDiameterプロキシーにセキュリティーサービスを実行させられることは、段階的に展開できるようにするうえで重要です。通信の反対側でも同様で、ロードバランサーが、自身がつなぐサーバーのためにセキュリティーサービスを終端します。

要件5:

解決策は、暗号による保護を特定のDiameter AVPに選択的に適用できなければなりません（MUST）。

動機: Diameterアプリケーションの中には、特定のAVPが仲介者によって追加、削除、または変更されることを前提としているものがあります。そのため、セキュリティー保護を選択的に適用できる必要があります。

さらに、Diameterメッセージのルーティングに必要なAVPのように、機密性保護をしてはならないが、完全性保護はしてもよいAVPもあります。

要件6:

解決策は、実装必須の暗号アルゴリズムを定義しなければなりません（MUST）。

動機: 相互運用性のために、（特定の利用環境向けのプロファイルが別途規定しない限り）実装必須の暗号アルゴリズムを規定しておくことが有益です。

要件7:

解決策は、対称鍵と非対称鍵をサポートしなければなりません（MUST）。

動機: 対称暗号アルゴリズムと非対称暗号アルゴリズムは、異なるセキュリティーサービスを提供します。たとえば、非対称アルゴリズムを使うと、否認防止サービスを提供できます。

要件8:

解決策のフレームワーク全体に、動的な鍵管理の解決策を含めなければなりません（MUST）。

ただし、「新しい」鍵管理プロトコルを開発する必要はなく、可能な限り既存のものを再利用することを想定しています。鍵の更新は、(a)管理操作と(b)鍵素材の有効期限切れによって引き起こされることが考えられます。

6. Security Considerations

6. セキュリティーに関する考慮事項

This entire document focuses on the discussion of new functionality for securing Diameter AVPs selectively between non-neighboring nodes.

この文書全体が、隣接していないノード間でDiameter AVPを選択的に保護するための新しい機能の議論に焦点を当てています。

Various security threats are mitigated by selectively applying security protection for individual Diameter AVPs. Without protection, there is the possibility for password sniffing, confidentiality violation, and AVP insertion, deletion, or modification. Additionally, applying a digital signature offers non-repudiation capabilities, a feature not yet available in today's Diameter deployment. Modification of certain Diameter AVPs may not necessarily be the act of malicious behavior but could also be the result of misconfiguration. An over-aggressively configured firewalling Diameter proxy may also remove certain AVPs. In most cases, data-origin authentication and integrity protection of AVPs will provide the most benefits for existing deployments with minimal overhead and (potentially) operate in a full-backwards compatible manner.

個々のDiameter AVPにセキュリティー保護を選択的に適用することで、さまざまなセキュリティー上の脅威が緩和されます。保護がなければ、パスワードの盗聴、機密性の侵害、AVPの挿入・削除・変更が起こる可能性があります。さらに、デジタル署名を適用すると否認防止の機能が得られますが、これは今日のDiameterの展開ではまだ利用できない機能です。特定のDiameter AVPの変更は、必ずしも悪意のある振る舞いによるものではなく、設定の誤りの結果である可能性もあります。過度に積極的に設定された、ファイアウォール機能を持つDiameterプロキシーが、特定のAVPを削除することもあります。ほとんどの場合、AVPのデータ発信元認証と完全性保護は、既存の展開に対して最小限のオーバーヘッドで最大の利点をもたらし、（場合によっては）完全に後方互換性のある方法で動作します。
