RFC 8590

Change Poll Extension for the Extensible Provisioning Protocol (EPP)

RFC 8590

拡張可能なプロビジョニングプロトコル（EPP）の変更ポーリング拡張

Abstract

概要

This document describes an Extensible Provisioning Protocol (EPP) extension for notifying clients of operations on client-sponsored objects that were not initiated by the client through EPP. These operations may include contractual or policy requirements including, but not limited to, regular batch processes, customer support actions, Uniform Domain-Name Dispute-Resolution Policy (UDRP) or Uniform Rapid Suspension (URS) actions, court-directed actions, and bulk updates based on customer requests. Since the client is not directly involved or knowledgable of these operations, the extension is used along with an EPP object mapping to provide the resulting state of the postoperation object, and optionally a preoperation object, with the operation metadata of what, when, who, and why.

この文書は、クライアントがスポンサーとなっているオブジェクトに対して、そのクライアントがEPPを通じて開始したのではない操作が行われたことをクライアントに通知するための、拡張可能なプロビジョニングプロトコル（EPP）の拡張について説明します。これらの操作には、契約上またはポリシー上の要件が含まれる場合があり、その例として、定期的なバッチ処理、カスタマーサポートの対応、統一ドメイン名紛争処理方針（UDRP）や統一迅速停止（URS）の措置、裁判所の命令による措置、顧客の依頼に基づく一括更新などがありますが、これらに限定されません。クライアントはこれらの操作に直接関与しておらず、また把握もしていないため、この拡張はEPPのオブジェクトマッピングと組み合わせて使用され、操作後のオブジェクトの結果の状態と、任意で操作前のオブジェクトを、何が、いつ、誰によって、なぜ行われたのかという操作のメタデータとともに提供します。

1. Introduction

1. はじめに

This document describes an extension mapping for version 1.0 of the Extensible Provisioning Protocol (EPP) [RFC5730]. This mapping, an extension to EPP object mappings like the EPP domain name mapping [RFC5731], is used to notify clients of operations they are not directly involved in, on objects that the client sponsors. It is up to server policy to determine what transform operations and clients to notify. Using this extension, clients can more easily keep their systems in sync with the objects stored in the server. When a change occurs that a client needs to be notified of, a poll message can be inserted by the server for consumption by the client using the EPP <poll> command and response defined in [RFC5730]. The extension supports including a "before" operation poll message and an "after" operation poll message. The extension only extends the EPP <poll> response in [RFC5730] and does not extend the EPP <poll> command. Please refer to [RFC5730] for information and examples of the EPP <poll> command.

この文書は、拡張可能なプロビジョニングプロトコル（EPP）[RFC5730]のバージョン1.0に対する拡張マッピングについて説明します。このマッピングは、EPPドメイン名マッピング[RFC5731]のようなEPPオブジェクトマッピングに対する拡張であり、クライアントがスポンサーとなっているオブジェクトに対して、そのクライアントが直接関与していない操作が行われたことをクライアントに通知するために使用します。どの変換操作をどのクライアントに通知するかは、サーバーのポリシーによって決まります。この拡張を使用すると、クライアントは自身のシステムを、サーバーに保存されているオブジェクトと同期した状態に保ちやすくなります。クライアントに通知する必要のある変更が発生したとき、サーバーはポーリングメッセージを挿入でき、クライアントは[RFC5730]で定義されているEPPの<poll>コマンドとレスポンスを使用してそれを受け取ります。この拡張は、操作の「before」のポーリングメッセージと「after」のポーリングメッセージを含めることをサポートします。この拡張は、[RFC5730]のEPPの<poll>レスポンスのみを拡張し、EPPの<poll>コマンドは拡張しません。EPPの<poll>コマンドに関する情報と例については、[RFC5730]を参照してください。

2. Object Attributes

2. オブジェクトの属性

This extension adds additional elements to EPP object mappings like the EPP domain name mapping [RFC5731]. Only those new elements are described here.

この拡張は、EPPドメイン名マッピング[RFC5731]のようなEPPオブジェクトマッピングに要素を追加します。ここでは、それらの新しい要素についてのみ説明します。

2.1. Operation

2.1. 操作

An operation consists of any transform operation that impacts objects that the client sponsors and should be notified of. The <changePoll:operation> element defines the operation. The OPTIONAL "op" attribute is an identifier, represented in the 7-bit US-ASCII character set defined in [RFC20], that is used to define a sub- operation or the name of a "custom" operation. The enumerated list of <changePoll:operation> values is:

操作とは、クライアントがスポンサーとなっているオブジェクトに影響を与え、クライアントに通知すべきあらゆる変換操作のことです。<changePoll:operation>要素は操作を定義します。選択可能な（OPTIONAL）「op」属性は、[RFC20]で定義されている7ビットUS-ASCII文字セットで表される識別子であり、サブ操作や「custom」操作の名前を定義するために使用します。<changePoll:operation>の値の列挙リストは次のとおりです。

"create":
Create operation as defined in [RFC5730].
"delete":
Delete operation as defined in [RFC5730]. If the delete operation results in an immediate purge of the object, then the "op" attribute MUST be set to "purge".
"renew":
Renew operation as defined in [RFC5730].
"transfer":
Transfer operation as defined in [RFC5730] that MUST set the "op" attribute with one of the possible transfer-type values; these include "request", "approve", "cancel", or "reject".
"update":
Update operation as defined in [RFC5730].
"restore":
Restore operation as defined in [RFC3915] that MUST set the "op" attribute with one of the possible restore-type values; these include "request" or "report".
"autoRenew":
Auto renew operation executed by the server.
"autoDelete":
Auto delete operation executed by the server. If the "autoDelete" operation results in an immediate purge of the object, then the "op" attribute MUST be set to "purge".
"autoPurge":
Auto purge operation executed by the server when removing the object after it has had the status "pendingDelete".
"custom":
Custom operation that MUST set the "op" attribute with the custom operation name. The custom operations supported are up to server policy.
"create":
[RFC5730]で定義されている作成操作です。
"delete":
[RFC5730]で定義されている削除操作です。削除操作の結果としてオブジェクトが即座にパージされる場合、「op」属性は「purge」に設定しなければなりません（MUST）。
"renew":
[RFC5730]で定義されている更新（renew）操作です。
"transfer":
[RFC5730]で定義されている移管操作です。この操作では、「op」属性に、移管の種類を表す値のいずれかを設定しなければなりません（MUST）。その値には「request」、「approve」、「cancel」、「reject」があります。
"update":
[RFC5730]で定義されている変更（update）操作です。
"restore":
[RFC3915]で定義されている復元操作です。この操作では、「op」属性に、復元の種類を表す値のいずれかを設定しなければなりません（MUST）。その値には「request」と「report」があります。
"autoRenew":
サーバーが実行する自動更新操作です。
"autoDelete":
サーバーが実行する自動削除操作です。「autoDelete」操作の結果としてオブジェクトが即座にパージされる場合、「op」属性は「purge」に設定しなければなりません（MUST）。
"autoPurge":
ステータスが「pendingDelete」になった後のオブジェクトを除去する際に、サーバーが実行する自動パージ操作です。
"custom":
カスタム操作です。この操作では、「op」属性にカスタム操作の名前を設定しなければなりません（MUST）。どのカスタム操作をサポートするかは、サーバーのポリシーによって決まります。

2.2. State

2.2. 状態

The state attribute reflects the state of the object "before" or "after" the operation. The state is defined using the OPTIONAL "state" attribute of the <changePoll:changeData> element, with the possible values "before" or "after" and a default value of "after". The server MAY support both the "before" state and the "after" state of the operation by using one poll message for the "before" state and one poll message for the "after" state. The "before" state poll message MUST be inserted into the message queue prior to the "after" state poll message.

状態属性は、操作の「before（前）」または「after（後）」のオブジェクトの状態を反映します。状態は、<changePoll:changeData>要素の選択可能な（OPTIONAL）「state」属性を使用して定義し、取りうる値は「before」または「after」で、デフォルト値は「after」です。サーバーは、「before」の状態に1つのポーリングメッセージを、「after」の状態に1つのポーリングメッセージを使用することで、操作の「before」の状態と「after」の状態の両方をサポートしてもよいです（MAY）。「before」の状態のポーリングメッセージは、「after」の状態のポーリングメッセージよりも前にメッセージキューへ挿入しなければなりません（MUST）。

For operations in Section 2.1 that don't have an "after" state, the server MUST use the "before" state poll message. For example, for the "delete" operation with the "op" attribute set to "purge", or the "autoPurge" operation, the server includes the state of the object prior to being purged in the "before" state poll message.

Section 2.1の操作のうち「after」の状態を持たないものについては、サーバーは「before」の状態のポーリングメッセージを使用しなければなりません（MUST）。たとえば、「op」属性が「purge」に設定された「delete」操作や「autoPurge」操作の場合、サーバーはパージされる前のオブジェクトの状態を「before」の状態のポーリングメッセージに含めます。

For operations in Section 2.1 that don't have a "before" state, the server MUST use the "after" state poll message. For example, for the "create" operation, the server includes the state of the object after creation in the "after" state poll message.

Section 2.1の操作のうち「before」の状態を持たないものについては、サーバーは「after」の状態のポーリングメッセージを使用しなければなりません（MUST）。たとえば、「create」操作の場合、サーバーは作成後のオブジェクトの状態を「after」の状態のポーリングメッセージに含めます。

2.3. Who

2.3. 実行者

The <changePoll:who> element defines who executed the operation, for audit purposes. It is a free-form value that is meant strictly for audit purposes and not to drive client-side logic. The scheme used for the possible set of <changePoll:who> element values is up to server policy. The server MAY identify the <changePoll:who> element value based on:

<changePoll:who>要素は、監査を目的として、誰が操作を実行したのかを定義します。これは自由形式の値であり、厳密に監査の目的のためだけのものであって、クライアント側のロジックを駆動するためのものではありません。<changePoll:who>要素が取りうる値の集合にどのような方式を用いるかは、サーバーのポリシーによって決まります。サーバーは、次のものに基づいて<changePoll:who>要素の値を定めてもよいです（MAY）。

"Identifier":
Unique user identifier of the user that executed the operation. An example is "ClientX".
"Name":
Name of the user that executed the operation. An example is "John Doe".
"Role":
Role of the user that executed operation. An example is "CSR" for a Customer Support Representative or "Batch" for a server batch.
"Identifier":
操作を実行したユーザーの一意なユーザー識別子です。例は「ClientX」です。
"Name":
操作を実行したユーザーの名前です。例は「John Doe」です。
"Role":
操作を実行したユーザーの役割です。例としては、カスタマーサポート担当者（Customer Support Representative）を表す「CSR」や、サーバーのバッチを表す「Batch」があります。

2.4. Dates and Times

2.4. 日付と時刻

Date and time attribute values MUST be represented in Universal Coordinated Time (UTC) using the Gregorian calendar. The extended date-time form using uppercase "T" and "Z" characters defined in [W3C.REC-xmlschema-2-20041028] MUST be used to represent date-time values, as XML Schema does not support truncated date-time forms or lowercase "T" and "Z" characters.

3. EPP Command Mapping

3. EPPコマンドのマッピング

A detailed description of the EPP syntax and semantics can be found in the EPP core protocol specification [RFC5730].

EPPの構文とセマンティクスの詳細な説明は、EPPのコアプロトコル仕様[RFC5730]にあります。

3.1. EPP Query Commands

3.1. EPPクエリーコマンド

EPP provides three commands to retrieve object information: <check> to determine if an object is known to the server, <info> to retrieve detailed information associated with an object, and <transfer> to retrieve object-transfer status information.

EPPは、オブジェクトの情報を取得するための3つのコマンドを提供しています。オブジェクトがサーバーに知られているかどうかを判断する<check>、オブジェクトに関連付けられた詳細な情報を取得する<info>、オブジェクトの移管ステータス情報を取得する<transfer>です。

3.1.1. EPP <check> Command

3.1.1. EPP <check>コマンド

This extension does not add any elements to the EPP <check> command or <check> response described in [RFC5730].

この拡張は、[RFC5730]で説明されているEPPの<check>コマンドや<check>レスポンスに要素を追加しません。

3.1.2. EPP <info> Command

3.1.2. EPP <info>コマンド

This extension does not add any elements to the EPP <info> command described in [RFC5730].

この拡張は、[RFC5730]で説明されているEPPの<info>コマンドに要素を追加しません。

The sponsoring client will then receive the state of the object with operation detail like what, who, when, and why the object was changed. The <changePoll:changeData> element contains the operation detail along with an indication of whether the object reflects the state before or after the operation as defined in Section 2.2. The <changePoll:changeData> element includes the operation detail with the following child elements:

この拡張は、[RFC5730]で説明されているEPPのポーリングレスポンスに、EPPオブジェクトマッピングの操作（Section 2.1）の操作詳細を追加します。これは、EPPオブジェクトマッピングのinfoレスポンスの拡張です。EPPオブジェクトマッピングで定義されているオブジェクトに対して、スポンサークライアント以外のクライアントが変換操作を行った場合、その結果として、操作詳細を含むEPPポーリングメッセージを挿入するために、オブジェクトの<info>レスポンスを拡張する場合があります（MAY）。これにより、スポンサークライアントは、オブジェクトが何を、誰が、いつ、なぜ変更されたのかといった操作詳細とともに、オブジェクトの状態を受け取ります。<changePoll:changeData>要素は、操作詳細に加えて、Section 2.2で定義されているように、オブジェクトが操作前と操作後のどちらの状態を反映しているかを示す情報を含みます。<changePoll:changeData>要素は、次の子要素で操作詳細を含みます。

<changePoll:operation>:
Transform operation executed on the object, as defined in Section 2.1.
<changePoll:date>:
Date and time when the operation was executed.
<changePoll:svTRID>:
Server transaction identifier of the operation.
<changePoll:who>:
Who executed the operation, as defined in Section 2.3.
<changePoll:caseId>:

OPTIONAL case identifier associated with the operation. The required "type" attribute defines the type of case. The OPTIONAL "name" attribute is an identifier, represented in the 7-bit US-ASCII character set defined in [RFC20], that is used to define the name of the "custom" case type. The enumerated list of case types is:

udrp:
A Uniform Domain-Name Dispute-Resolution Policy (UDRP) case.
urs:
A Uniform Rapid Suspension (URS) case.
custom:
A custom case that is defined using the "name" attribute.
<changePoll:reason>:
OPTIONAL reason for executing the operation. If present, this element contains the server-specific text to help explain the reason the operation was executed. This text MUST be represented in the response language previously negotiated with the client; an OPTIONAL "lang" attribute MAY be present to identify the language if the negotiated value is something other than the default value of "en" (English).
<changePoll:operation>:
Section 2.1で定義されている、オブジェクトに対して実行された変換操作です。
<changePoll:date>:
操作が実行された日付と時刻です。
<changePoll:svTRID>:
操作のサーバートランザクション識別子です。
<changePoll:who>:
Section 2.3で定義されている、操作を実行した者です。
<changePoll:caseId>:

操作に関連付けられた選択可能な（OPTIONAL）案件識別子です。必須の「type」属性は案件の種類を定義します。選択可能な（OPTIONAL）「name」属性は、[RFC20]で定義されている7ビットUS-ASCII文字セットで表される識別子であり、「custom」の案件の種類の名前を定義するために使用します。案件の種類の列挙リストは次のとおりです。

udrp:
統一ドメイン名紛争処理方針（UDRP）の案件です。
urs:
統一迅速停止（URS）の案件です。
custom:
「name」属性を使用して定義するカスタムの案件です。
<changePoll:reason>:
操作を実行した選択可能な（OPTIONAL）理由です。この要素が存在する場合、操作が実行された理由の説明に役立つ、サーバー固有のテキストを含みます。このテキストは、事前にクライアントとネゴシエートしたレスポンス言語で表現しなければなりません（MUST）。ネゴシエートした値がデフォルト値の「en」（英語）以外である場合は、言語を識別するために選択可能な（OPTIONAL）「lang」属性が存在してもよいです（MAY）。

3.2. EPP変換コマンド
