RFC 8987

DHCPv6 Prefix Delegating Relay Requirements

RFC 8987

DHCPv6プレフィックス委任リレーの要件

Abstract

概要

This document describes operational problems that are known to occur when using DHCPv6 relays with prefix delegation. These problems can prevent successful delegation and result in routing failures. To address these problems, this document provides necessary functional requirements for operating DHCPv6 relays with prefix delegation.

この文書は、DHCPv6リレーをプレフィックス委任とともに使用する際に発生することが知られている運用上の問題について説明します。 これらの問題は、委任の成功を妨げ、ルーティングの障害を引き起こす可能性があります。 これらの問題に対処するため、この文書は、プレフィックス委任とともにDHCPv6リレーを運用するために必要な機能要件を示します。

It is recommended that any network operator using DHCPv6 prefix delegation with relays ensure that these requirements are followed on their networks.

リレーを介してDHCPv6プレフィックス委任を使用するネットワークオペレーターは、自身のネットワークでこれらの要件が守られていることを確認することが推奨されます。

1. Introduction

1. はじめに

For Internet service providers that offer native IPv6 access with prefix delegation to their customers, a common deployment architecture is to have a DHCPv6 relay agent function located in the ISP's Layer 3 customer edge device and a separate, centralized DHCPv6 server infrastructure. [RFC8415] describes the functionality of a DHCPv6 relay, and Section 19.1.3 of [RFC8415] mentions this deployment scenario, but it does not provide details for all of the functional requirements that the relay needs to fulfill to operate deterministically in this deployment scenario.

顧客にプレフィックス委任を伴うネイティブIPv6アクセスを提供するインターネットサービスプロバイダー（ISP）では、ISPのレイヤー3カスタマーエッジデバイスにDHCPv6リレーエージェント機能を配置し、それとは別に集中型のDHCPv6サーバー基盤を置くことが、一般的な展開アーキテクチャーです。 [RFC8415]はDHCPv6リレーの機能を説明しており、[RFC8415]のSection 19.1.3はこの展開シナリオに言及していますが、この展開シナリオでリレーが決定的に動作するために満たす必要のある機能要件のすべてについては詳細を示していません。

A DHCPv6 relay agent for prefix delegation is a function commonly implemented in routing devices, but implementations vary in their functionality and client/server interworking. This can result in operational problems such as messages not being forwarded by the relay or unreachability of the delegated prefixes. This document provides a set of requirements for devices implementing a relay function for use with prefix delegation.

プレフィックス委任のためのDHCPv6リレーエージェントは、ルーティングデバイスに一般的に実装されている機能ですが、その機能やクライアントとサーバーの相互動作は実装によって異なります。 これにより、リレーがメッセージを転送しない、委任されたプレフィックスに到達できないといった運用上の問題が発生する可能性があります。 この文書は、プレフィックス委任で使用するリレー機能を実装するデバイスに対する一連の要件を示します。

The mechanisms for a relay to inject routes (including aggregated ones) on its network-facing interface based on prefixes learned from a server via DHCP prefix delegation (DHCP-PD) are out of scope of the document.

DHCPプレフィックス委任（DHCP-PD）を介してサーバーから学習したプレフィックスに基づいて、リレーがネットワーク側のインターフェイスに経路（集約された経路を含む）を注入する仕組みは、この文書の範囲外です。

Multi-hop DHCPv6 relaying is not affected. The requirements in this document are solely applicable to the DHCP relay agent co-located with the first-hop router to which the DHCPv6 client requesting the prefix is connected, so no changes to any subsequent relays in the path are needed.

マルチホップのDHCPv6リレーは影響を受けません。 この文書の要件は、プレフィックスを要求するDHCPv6クライアントが接続されているファーストホップルーターと同じ場所に配置されたDHCPリレーエージェントにのみ適用されるため、経路上の後続のリレーに変更は必要ありません。

2. Terminology

2. 用語

2.1. General

2.1. 一般

This document uses the terminology defined in [RFC8415]. However, when defining the functional elements for prefix delegation, [RFC8415], Section 4.2 defines the term "delegating router" as:

この文書は、[RFC8415]で定義されている用語を使用します。 ただし、[RFC8415], Section 4.2は、プレフィックス委任の機能要素を定義する際に、「委任ルーター（delegating router）」という用語を次のように定義しています。

The router that acts as a DHCP server and responds to requests for delegated prefixes.
DHCPサーバーとして動作し、委任プレフィックスの要求に応答するルーター。

This document is concerned with deployment scenarios in which the DHCPv6 relay and DHCPv6 server functions are separated, so the term "delegating router" is not used. Instead, a new term is introduced to describe the relaying function:

この文書は、DHCPv6リレーとDHCPv6サーバーの機能が分離されている展開シナリオを対象としているため、「委任ルーター」という用語は使用しません。 その代わりに、リレー機能を説明するための新しい用語を導入します。

Delegating relay:
A delegating relay acts as an intermediate device, forwarding DHCPv6 messages containing IA_PD and IAPREFIX options between the client and server. The delegating relay does not implement a DHCPv6 server function. The delegating relay is also responsible for routing traffic for the delegated prefixes.
委任リレー（Delegating relay）：
委任リレーは中間デバイスとして動作し、IA_PDオプションとIAPREFIXオプションを含むDHCPv6メッセージをクライアントとサーバーの間で転送します。 委任リレーはDHCPv6サーバー機能を実装しません。 委任リレーは、委任されたプレフィックス宛てのトラフィックのルーティングも担います。

Where the term "relay" is used on its own within this document, it should be understood to be a delegating relay unless specifically stated otherwise.

この文書の中で「リレー」という用語が単独で使用されている場合は、特に明記されていない限り、委任リレーを指すものと理解してください。

In CableLabs DOCSIS environments, the Cable Modem Termination System (CMTS) would be considered a delegating relay with respect to Customer Premises Devices (CPEs) ([DOCSIS_3.1], Section 5.2.7.2). A Broadband Network Gateway (BNG) in a DSL-based access network may be a delegating relay if it does not implement a local DHCPv6 server function ([TR-092], Section 4.10).

CableLabsのDOCSIS環境では、ケーブルモデム終端システム（CMTS）は、顧客宅内機器（CPE）に対する委任リレーとみなされます（[DOCSIS_3.1]、セクション5.2.7.2）。 DSLベースのアクセスネットワークにおけるブロードバンドネットワークゲートウェイ（BNG）は、ローカルのDHCPv6サーバー機能を実装していない場合、委任リレーとなることがあります（[TR-092]、セクション4.10）。

[RFC8415] defines the "DHCP server" (or "server") as:

[RFC8415]は、「DHCPサーバー」（または「サーバー」）を次のように定義しています。

A node that responds to requests from clients. It may or may not be on the same link as the client(s). Depending on its capabilities, if it supports prefix delegation it may also feature the functionality of a delegating router.
クライアントからの要求に応答するノード。 クライアントと同じリンク上にある場合もあれば、そうでない場合もあります。 その能力に応じて、プレフィックス委任をサポートしている場合には、委任ルーターの機能も備えていることがあります。

This document serves the deployment cases where a DHCPv6 server is not located on the same link as the client (necessitating the delegating relay). The server supports prefix delegation and is capable of leasing prefixes to clients, but it is not responsible for other functions required of a delegating router, such as managing routes for the delegated prefixes.

この文書は、DHCPv6サーバーがクライアントと同じリンク上に配置されていない（したがって委任リレーが必要となる）展開事例を対象とします。 サーバーはプレフィックス委任をサポートし、クライアントにプレフィックスをリースできますが、委任されたプレフィックスの経路の管理など、委任ルーターに求められるその他の機能は担いません。

The term "requesting router" has previously been used to describe the DHCP client requesting prefixes for use. This document adopts the terminology of [RFC8415] and uses "DHCP client" or "client" interchangeably for this element.

「要求ルーター（requesting router）」という用語は、使用するプレフィックスを要求するDHCPクライアントを表すために以前から使われてきました。 この文書は[RFC8415]の用語を採用し、この要素を指して「DHCPクライアント」と「クライアント」を同じ意味で使用します。

2.2. Topology

2.2. トポロジー

The following diagram shows the deployment topology relevant to this document.

次の図は、この文書に関係する展開トポロジーを示しています。

The client requests prefixes via the downlink interface of the delegating relay. The resulting prefixes will be used for addressing the client network. The delegating relay is responsible for forwarding DHCP messages, including prefix delegation requests and responses between the client and server. Messages are forwarded from the delegating relay to the server using multicast or unicast via the operator uplink interface.

クライアントは、委任リレーのダウンリンクインターフェイスを介してプレフィックスを要求します。 得られたプレフィックスは、クライアントネットワークのアドレス付けに使用されます。 委任リレーは、クライアントとサーバーの間で、プレフィックス委任の要求と応答を含むDHCPメッセージを転送する役割を担います。 メッセージは、オペレーターのアップリンクインターフェイスを介して、マルチキャストまたはユニキャストで委任リレーからサーバーへ転送されます。

The delegating relay provides the operator's Layer 3 edge towards the client and is responsible for routing traffic to and from clients connected to the client network using addresses from the delegated prefixes.

委任リレーは、クライアントに向けたオペレーターのレイヤー3エッジとなり、委任されたプレフィックスのアドレスを使用してクライアントネットワークに接続されたクライアントとの間のトラフィックをルーティングする役割を担います。

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

3. Problems Observed with Existing Delegating Relay Implementations

3. 既存の委任リレー実装で観測された問題

The following sections of the document describe problems that have been observed with delegating relay implementations in commercially available devices.

この文書の以降のセクションでは、市販のデバイスに搭載された委任リレー実装で観測された問題について説明します。

3.1. DHCP Messages Not Being Forwarded by the Delegating Relay

3.1. 委任リレーによってDHCPメッセージが転送されない

Delegating relay implementations have been observed not to forward messages between the client and server. This generally occurs if a client sends a message that is unexpected by the delegating relay. For example, the delegating relay already has an active PD lease entry for an existing client on a port. A new client is connected to this port and sends a Solicit message. The delegating relay then drops the Solicit messages until either it receives a DHCP Release message from the original client or the existing lease times out. This causes a particular problem when a client device needs to be replaced due to a failure.

委任リレーの実装が、クライアントとサーバーの間でメッセージを転送しないことが観測されています。 これは一般に、委任リレーが想定していないメッセージをクライアントが送信した場合に発生します。 たとえば、委任リレーが、あるポート上の既存のクライアントに対するアクティブなPDリースエントリーをすでに持っているとします。 新しいクライアントがこのポートに接続され、Solicitメッセージを送信します。 すると委任リレーは、元のクライアントからDHCP Releaseメッセージを受信するか、既存のリースがタイムアウトするまで、Solicitメッセージを破棄します。 これは、故障によってクライアントデバイスを交換する必要がある場合に、特に問題となります。

In addition to dropping messages, in some cases, the delegating relay will generate error messages and send them to the client, e.g., "NoBinding" messages being sent in the event that the delegating relay does not have an active delegated prefix lease.

メッセージを破棄することに加えて、場合によっては、委任リレーがエラーメッセージを生成してクライアントに送信することもあります。 たとえば、委任リレーがアクティブな委任プレフィックスのリースを持っていない場合に「NoBinding」メッセージが送信されます。

3.2. Delegating Relay Loss of State on Reboot

3.2. 再起動時の委任リレーの状態の喪失

For proper routing of client traffic, the delegating relay requires a corresponding routing table entry for each active prefix delegated to a connected client. A delegating relay that does not store this state persistently across reboots will not be able to forward traffic to the client's delegated leases until the state is reestablished through new DHCP messages.

クライアントのトラフィックを適切にルーティングするために、委任リレーは、接続されたクライアントに委任されたアクティブなプレフィックスごとに、対応するルーティングテーブルのエントリーを必要とします。 再起動をまたいでこの状態を永続的に保存しない委任リレーは、新しいDHCPメッセージによって状態が再確立されるまで、クライアントに委任されたリース宛てのトラフィックを転送できません。

3.3. Multiple Delegated Prefixes for a Single Client

3.3. 単一のクライアントに対する複数の委任プレフィックス

DHCPv6 [RFC8415] allows a client to include more than one instance of OPTION_IA_PD in messages in order to request multiple prefix delegations by the server. If configured for this, the server supplies one (or more) instance of OPTION_IAPREFIX for each received instance of OPTION_IA_PD, each containing information for a different delegated prefix.

DHCPv6 [RFC8415]では、サーバーに複数のプレフィックス委任を要求するために、クライアントがメッセージにOPTION_IA_PDのインスタンスを複数含めることができます。 そのように設定されている場合、サーバーは受信したOPTION_IA_PDのインスタンスごとに1つ（または複数）のOPTION_IAPREFIXのインスタンスを提供し、それぞれに異なる委任プレフィックスの情報が含まれます。

In some delegating relay implementations, only a single delegated prefix per DHCP Unique Identifier (DUID) is supported. In those cases, only one IPv6 route for one of the delegated prefixes is installed, meaning that other prefixes delegated to a client are unreachable.

一部の委任リレー実装では、DHCP固有識別子（DUID）ごとに1つの委任プレフィックスしかサポートされていません。 その場合、委任プレフィックスのうちの1つに対するIPv6経路だけがインストールされるため、クライアントに委任されたほかのプレフィックスには到達できなくなります。

3.4. Dropping Messages from Devices with Duplicate MAC Addresses and DUIDs

3.4. MACアドレスとDUIDが重複するデバイスからのメッセージの破棄

It is an operational reality that client devices with duplicate Media Access Control (MAC) addresses and/or DUIDs exist and have been deployed. In some networks, the operational costs of locating and swapping out such devices are prohibitive.

メディアアクセス制御（MAC）アドレスやDUIDが重複するクライアントデバイスが存在し、展開されているというのが運用上の現実です。 一部のネットワークでは、そのようなデバイスを特定して交換するための運用コストが非常に高くつきます。

Delegating relays have been observed to restrict forwarding client messages originating from one client DUID to a single interface. In this case, if the same client DUID appears from a second client on another interface while there is already an active lease, messages originating from the second client are dropped, causing the second client to be unable to obtain a prefix delegation.

委任リレーが、1つのクライアントDUIDから発信されたクライアントメッセージの転送を、単一のインターフェイスに制限することが観測されています。 この場合、すでにアクティブなリースが存在する状態で、別のインターフェイス上の2台目のクライアントから同じクライアントDUIDが現れると、2台目のクライアントから発信されたメッセージは破棄され、2台目のクライアントはプレフィックス委任を受けられなくなります。

It should be noted that in some access networks, the MAC address and/or DUID are used as part of device identification and authentication. In such networks, enforcing uniqueness of the MAC address and/or DUID is a necessary function and is not considered a problem.

なお、一部のアクセスネットワークでは、MACアドレスやDUIDがデバイスの識別と認証の一部として使用されていることに注意してください。 そのようなネットワークでは、 MACアドレスやDUIDの一意性を強制することは必要な機能であり、問題とはみなされません。

3.5. Forwarding Loops between Client and Relay

3.5. クライアントとリレーの間の転送ループ

If the client loses information about an active prefix lease it has been delegated while the lease entry and associated route are still active in the delegating relay, then the relay will forward traffic to the client. The client will return this traffic to the relay, which is the client's default gateway (learned via a Router Advertisement (RA)). The loop will continue until either the client is successfully reprovisioned via DHCP or the lease ages out in the relay.

委任リレーでリースエントリーと関連する経路がまだアクティブであるのに、クライアントが自身に委任されたアクティブなプレフィックスリースに関する情報を失った場合、リレーはクライアントにトラフィックを転送します。 クライアントは、このトラフィックを、（ルーター広告（RA）によって学習した）クライアントのデフォルトゲートウェイであるリレーに送り返します。 このループは、クライアントがDHCPを介して再プロビジョニングに成功するか、リレーでリースが期限切れになるまで続きます。

4. Requirements for Delegating Relays

4. 委任リレーに対する要件

To resolve the problems described in Section 3 and to preempt other undesirable behavior, the following section of the document describes a set of functional requirements for the delegating relay.

Section 3で説明した問題を解決し、その他の望ましくない動作を未然に防ぐために、この文書の次のセクションでは、委任リレーに対する一連の機能要件を説明します。

In addition, relay implementers are reminded that [RFC8415] makes it clear that relays MUST forward packets that either contain message codes it may not understand (Section 19 of [RFC8415]) or options that it does not understand (Section 16 of [RFC8415]).

また、リレーの実装者は、理解できない可能性のあるメッセージコードを含むパケット（[RFC8415]のSection 19）や、理解できないオプションを含むパケット（[RFC8415]のSection 16）をリレーが転送しなければなりません（MUST）と[RFC8415]が明記していることに留意してください。

4.1. General Requirements

4.1. 一般的な要件

  1. The delegating relay MUST forward messages bidirectionally between the client and server without changing the contents of the message.
  2. The relay MUST allow for multiple prefixes to be delegated for the same client IA_PD. These delegations may have different lifetimes.
  3. The relay MUST allow for multiple prefixes (with or without separate IA_PDs) to be delegated to a single client connected to a single interface, identified by its DHCPv6 Client Identifier (DUID).
  4. A delegating relay may have one or more interfaces on which it acts as a relay, as well as one or more interfaces on which it does not (for example, in an ISP, it might act as a relay on all southbound interfaces but not on the northbound interfaces). The relay SHOULD allow the same client identifier (DUID) to have active delegated prefix leases on more than one interface simultaneously unless client DUID uniqueness is necessary for the functioning or security of the network. This is to allow client devices with duplicate DUIDs to function on separate broadcast domains.
  5. The maximum number of simultaneous prefixes delegated to a single client MUST be configurable.
  6. The relay MUST implement a mechanism to limit the maximum number of active prefix delegations on a single port for all client identifiers and IA_PDs. This value MUST be configurable.
  7. It is RECOMMENDED that delegating relays support at least 8 active delegated leases per client device and use this as the default limit.
  8. The delegating relay MUST update the lease lifetimes based on the client's reply messages it forwards to the client and only expire the delegated prefixes when the valid lifetime has elapsed.
  9. On receipt of a Release message from the client, the delegating relay MUST expire the active leases for each of the IA_PDs in the message.
  1. 委任リレーは、メッセージの内容を変更せずに、クライアントとサーバーの間で双方向にメッセージを転送しなければなりません（MUST）。
  2. リレーは、同じクライアントのIA_PDに対して複数のプレフィックスが委任されることを許容しなければなりません（MUST）。 これらの委任は、それぞれ異なるライフタイムを持つことがあります。
  3. リレーは、単一のインターフェイスに接続され、DHCPv6クライアント識別子（DUID）によって識別される単一のクライアントに対して、（個別のIA_PDの有無にかかわらず）複数のプレフィックスが委任されることを許容しなければなりません（MUST）。
  4. 委任リレーは、リレーとして動作する1つ以上のインターフェイスと、リレーとして動作しない1つ以上のインターフェイスを持つことがあります（たとえばISPでは、すべての南向きインターフェイスではリレーとして動作し、北向きインターフェイスではリレーとして動作しないことがあります）。 クライアントのDUIDの一意性がネットワークの機能やセキュリティーのために必要でない限り、リレーは、同じクライアント識別子（DUID）が複数のインターフェイス上で同時にアクティブな委任プレフィックスのリースを持つことを許容すべきです（SHOULD）。 これは、DUIDが重複するクライアントデバイスが、別々のブロードキャストドメインで機能できるようにするためです。
  5. 単一のクライアントに同時に委任されるプレフィックスの最大数は、設定可能でなければなりません（MUST）。
  6. リレーは、すべてのクライアント識別子とIA_PDを対象として、単一のポート上のアクティブなプレフィックス委任の最大数を制限する仕組みを実装しなければなりません（MUST）。 この値は設定可能でなければなりません（MUST）。
  7. 委任リレーは、クライアントデバイスごとに少なくとも8つのアクティブな委任リースをサポートし、これをデフォルトの上限として使用することが推奨されます（RECOMMENDED）。
  8. 委任リレーは、クライアントに転送するクライアント宛ての応答メッセージに基づいてリースのライフタイムを更新し、有効ライフタイムが経過したときにのみ委任プレフィックスを失効させなければなりません（MUST）。
  9. クライアントからReleaseメッセージを受信したとき、委任リレーは、そのメッセージに含まれる各IA_PDのアクティブなリースを失効させなければなりません（MUST）。

4.2. Routing Requirements

4.2. ルーティングの要件

  1. The relay MUST maintain a local routing table that is dynamically updated with leases and the associated next hops as they are delegated to clients. When a delegated prefix is released or expires, the associated route MUST be removed from the relay's routing table.
  2. The delegating relay's routing entry MUST use the same prefix length for the delegated prefix as given in the IA_PD.
  3. The relay MUST provide a mechanism to dynamically update ingress filters permitting ingress traffic sourced from client delegated leases and blocking packets from invalid source prefixes. This is to implement anti-spoofing as described in [BCP38]. The delegating relay's ingress filter entry MUST use the same prefix length for the delegated prefix as given in the IA_PD.
  4. The relay MAY provide a mechanism to dynamically advertise delegated leases into a routing protocol as they are learned. If such a mechanism is implemented, when a delegated lease is released or expires, the delegated route MUST be withdrawn from the routing protocol. The mechanism by which the routes are inserted and deleted is out of the scope of this document.

  5. To prevent routing loops, the relay SHOULD implement a configurable policy to drop potential looping packets received on any DHCP-PD client-facing interfaces.

    The policy SHOULD be configurable on a per-client or per-destination basis.

    Looping packets are those with a destination address in a prefix delegated to a client connected to that interface, as follows:

    • For point-to-point links, when the packet's ingress and egress interfaces match.
    • For multi-access links, when the packet's ingress and egress interface match, and the source link-layer and next-hop link-layer addresses match.

    An ICMPv6 Type 1, Code 6 (Destination Unreachable, reject route to destination) error message MAY be sent as per [RFC4443], Section 3.1. The ICMP policy SHOULD be configurable.

  1. リレーは、リースがクライアントに委任されるたびに、そのリースと関連するネクストホップで動的に更新されるローカルのルーティングテーブルを維持しなければなりません（MUST）。 委任プレフィックスが解放されるか期限切れになった場合、関連する経路をリレーのルーティングテーブルから削除しなければなりません（MUST）。
  2. 委任リレーのルーティングエントリーは、委任プレフィックスに対して、IA_PDで与えられたものと同じプレフィックス長を使用しなければなりません（MUST）。
  3. リレーは、クライアントに委任されたリースを送信元とする入力トラフィックを許可し、無効な送信元プレフィックスからのパケットを遮断する入力フィルターを動的に更新する仕組みを提供しなければなりません（MUST）。 これは、[BCP38]で説明されているなりすまし対策を実装するためです。 委任リレーの入力フィルターのエントリーは、委任プレフィックスに対して、IA_PDで与えられたものと同じプレフィックス長を使用しなければなりません（MUST）。
  4. リレーは、委任されたリースを学習した時点で、それらをルーティングプロトコルに動的に広告する仕組みを提供してもよいです（MAY）。 そのような仕組みが実装されている場合、委任されたリースが解放されるか期限切れになったときには、委任された経路をルーティングプロトコルから取り下げなければなりません（MUST）。 経路を挿入および削除する仕組みは、この文書の範囲外です。

  5. ルーティングループを防ぐために、リレーは、DHCP-PDのクライアント側インターフェイスで受信した、ループする可能性のあるパケットを破棄する設定可能なポリシーを実装すべきです（SHOULD）。

    このポリシーは、クライアントごとまたは宛先ごとに設定可能であるべきです（SHOULD）。

    ループするパケットとは、そのインターフェイスに接続されたクライアントに委任されたプレフィックス内の宛先アドレスを持つパケットのうち、次のものです。

    • ポイントツーポイントリンクの場合、パケットの入力インターフェイスと出力インターフェイスが一致するもの。
    • マルチアクセスリンクの場合、パケットの入力インターフェイスと出力インターフェイスが一致し、かつ送信元のリンク層アドレスとネクストホップのリンク層アドレスが一致するもの。

    [RFC4443], Section 3.1に従って、ICMPv6のType 1、Code 6（Destination Unreachable、reject route to destination）のエラーメッセージを送信してもよいです（MAY）。 ICMPのポリシーは設定可能であるべきです（SHOULD）。

4.3. Service Continuity Requirements

4.3. サービス継続性の要件

  1. To preserve active client prefix delegations across relay restarts, the relay SHOULD implement at least one of the following:

    • Implement DHCPv6 Bulk Leasequery as defined in [RFC5460].
    • Store active prefix delegations in persistent storage so they can be reread after the reboot.
  2. If a client's next-hop link-local address becomes unreachable (e.g., due to a link-down event on the relevant physical interface), routes for the client's delegated prefixes MUST be retained by the delegating relay unless they are released or removed due to expiring DHCP timers. This is to reestablish routing for the delegated prefix if the client next hop becomes reachable without the delegated prefixes needing to be relearned.
  3. The relay SHOULD implement DHCPv6 Active Leasequery as defined in [RFC7653] to keep the local lease database in sync with the DHCPv6 server.

  1. リレーの再起動をまたいでクライアントのアクティブなプレフィックス委任を保持するために、リレーは次のうち少なくとも1つを実装すべきです（SHOULD）。

    • [RFC5460]で定義されているDHCPv6 Bulk Leasequeryを実装する。
    • 再起動後に再読み込みできるように、アクティブなプレフィックス委任を永続ストレージに保存する。
  2. クライアントのネクストホップのリンクローカルアドレスに（たとえば、該当する物理インターフェイスのリンクダウンイベントによって）到達できなくなった場合でも、委任リレーは、クライアントの委任プレフィックスの経路が解放されるか、DHCPタイマーの満了によって削除されない限り、それらの経路を保持しなければなりません（MUST）。 これは、委任プレフィックスを再学習する必要なしに、クライアントのネクストホップに再び到達できるようになったときに、委任プレフィックスのルーティングを再確立するためです。
  3. リレーは、ローカルのリースデータベースをDHCPv6サーバーと同期させておくために、[RFC7653]で定義されているDHCPv6 Active Leasequeryを実装すべきです（SHOULD）。

4.4. Operational Requirements

4.4. 運用上の要件

  1. The relay SHOULD implement an interface allowing the operator to view the active delegated prefixes. This SHOULD provide information about the delegated lease and client details such as the client identifier, next-hop address, connected interface, and remaining lifetimes.
  2. The relay SHOULD provide a method for the operator to clear active bindings for an individual lease, client, or all bindings on a port.
  3. To facilitate troubleshooting of operational problems between the delegating relay and other elements, it is RECOMMENDED that a time synchronization protocol be used by the delegating relays and DHCP servers.
  1. リレーは、オペレーターがアクティブな委任プレフィックスを参照できるインターフェイスを実装すべきです（SHOULD）。 このインターフェイスは、委任されたリースに関する情報と、クライアント識別子、ネクストホップアドレス、接続されているインターフェイス、残りのライフタイムなどのクライアントの詳細情報を提供すべきです（SHOULD）。
  2. リレーは、オペレーターが個々のリースやクライアントのアクティブなバインディング、またはポート上のすべてのバインディングを消去する手段を提供すべきです（SHOULD）。
  3. 委任リレーとその他の要素との間の運用上の問題のトラブルシューティングを容易にするために、委任リレーとDHCPサーバーが時刻同期プロトコルを使用することが推奨されます（RECOMMENDED）。

6. Security Considerations

6. セキュリティーに関する考慮事項

This document does not add any new security considerations beyond those mentioned in Section 4 of [RFC8213] and Section 22 of [RFC8415].

この文書は、[RFC8213]のSection 4と[RFC8415]のSection 22で述べられているもの以外に、新たなセキュリティーに関する考慮事項を追加しません。

If the delegating relay implements [BCP38] filtering, then the filtering rules will need to be dynamically updated as delegated prefixes are leased.

委任リレーが[BCP38]のフィルタリングを実装する場合、委任プレフィックスがリースされるのに合わせて、フィルタリングルールを動的に更新する必要があります。

[RFC8213] describes a method for securing traffic between the relay agent and server by sending DHCP messages over an IPsec tunnel. It is RECOMMENDED that this be implemented by the delegating relay.

[RFC8213]は、IPsecトンネル上でDHCPメッセージを送信することによって、リレーエージェントとサーバーの間のトラフィックを保護する方法を説明しています。 委任リレーがこれを実装することが推奨されます（RECOMMENDED）。

Failure to implement requirement G-6 may have specific security implications, such as a resource depletion attack on the relay.

要件G-6を実装しないと、リレーに対するリソース枯渇攻撃など、特有のセキュリティー上の影響が生じる可能性があります。

The operational requirements in Section 4.4 may introduce additional security considerations. It is RECOMMENDED that the operational security practices described in [RFC4778] be implemented.

Section 4.4の運用上の要件は、追加のセキュリティーに関する考慮事項をもたらす可能性があります。 [RFC4778]で説明されている運用上のセキュリティープラクティスを実施することが推奨されます（RECOMMENDED）。
