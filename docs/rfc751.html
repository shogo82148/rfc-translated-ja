RFC 751

Survey of FTP mail and MLFL

RFC 751

FTPのMAILとMLFLの調査

Abstract

概要

Two surveys of Arpanet Server hosts were run between September 20, 1978 and December 11, 1978. The intent was to determine the response of the host's Server FTP program to:

1978年9月20日から1978年12月11日にかけて、ARPANETのサーバーホストを対象に2つの調査を実施しました。その目的は、次の操作に対するホストのサーバーFTPプログラムの応答を調べることでした。

  1. An attempt to mail to an unknown recipient at that host. The purpose of this survey was two-fold. First, to determine whether the host accepts mail for unknown recipients at all, and second, what response the host gives if it does not accept such mail.
  2. An attempt to mail to a known recipient using the MLFL command rather than the usual MAIL command. This survey was undertaken to determine the extent of support for the MLFL command among Server hosts, and the sort of reply received if the Server does not support MLFL. MLFL is potentially a 'better' form of communication than mail as the message is sent over a data connection rather than the command connection. Using the data connection eliminates the 'end-of-mail' marker and 'command reader' problems sometimes encountered over the command connection.
  1. そのホストの未知の受信者宛てにメールを送ろうとする操作。この調査の目的は2つありました。1つ目は、そのホストが未知の受信者宛てのメールをそもそも受け付けるかどうかを調べること、2つ目は、そのようなメールを受け付けない場合にホストがどのような応答を返すかを調べることです。
  2. 通常のMAILコマンドではなくMLFLコマンドを使って、既知の受信者宛てにメールを送ろうとする操作。この調査は、サーバーホストの間でMLFLコマンドがどの程度サポートされているかと、サーバーがMLFLをサポートしていない場合にどのような応答が返されるかを調べるために行いました。MLFLでは、メッセージがコマンドコネクションではなくデータコネクションで送られるので、MLFLはメールよりも「優れた」通信形式になりうるものです。データコネクションを使えば、コマンドコネクションで時々起こる「メールの終わり（end-of-mail）」の目印や「コマンド読み取り部（command reader）」の問題を解消できます。

The ground rules of the survey were that all sites listed as Servers in the MIT/SAIL Host table were surveyed. In many cases, a host listed as a Server would not respond to an ICP at any time during the period of the survey. Once a host responded with what seemed to me to be a 'definitive' answer, I marked it as such and stopped surveying it.

調査の基本ルールは、MIT/SAILのホストテーブルにサーバーとして記載されているすべてのサイトを調査するというものでした。多くの場合、サーバーとして記載されているホストは、調査期間中のどの時点でもICPに応答しませんでした。あるホストが私にとって「決定的」と思える答えを返したら、そのホストをそのように記録し、それ以上の調査をやめました。

MLFL Survey

MLFLの調査

The algorithm used was to ICP to socket 3 of the server (the standard old-FTP socket). Once a 300 response was received, I sent the MLFL command. Where I had the name of a real mailbox at a site (a Header-person, for example) I used that, otherwise the name "**". If a site asked for a password (response 504) after the MLFL command I gave "USER NETML" "PASS NETML" and retried the MLFL. If the server replied with a 255 SOCK command, I listened for the data-connection to be established. When it was, I transferred the mail file. Interestingly enough, most sites implement an RFC queueing algorithm that will allow the user site to attempt to establish the data-connection from its end.

使用した手順は、サーバーのソケット3（標準の旧FTPソケット）にICPを行うというものです。300応答を受信したら、MLFLコマンドを送信しました。そのサイトの実在するメールボックスの名前（たとえばHeader-person）がわかっている場合はそれを使い、そうでない場合は「**」という名前を使いました。MLFLコマンドの後にサイトがパスワードを求めてきた場合（応答504）は、「USER NETML」「PASS NETML」を送ってからMLFLを再試行しました。サーバーが255 SOCKコマンドで応答した場合は、データコネクションが確立されるのを待ちました。確立されたら、メールファイルを転送しました。興味深いことに、ほとんどのサイトは、ユーザーサイトが自分の側からデータコネクションの確立を試みられるようにするRFCのキューイングアルゴリズムを実装しています。

Complete FTP scripts may be found, if you are interested, on MIT-DM, file NETDOC;MLFL SURVEY.

興味があれば、完全なFTPスクリプトがMIT-DMのファイルNETDOC;MLFL SURVEYにあります。
