RFC 644

On the Problem of Signature Authentication for Network Mail

RFC 644

ネットワークメールにおける署名の認証の問題について

Abstract

概要

This note describes the problem of signature authentication for network mail, presents a general approach to the problem and proposes a specific implementation of that approach.

このノートでは、ネットワークメールにおける署名の認証の問題を説明し、その問題に対する一般的なアプローチを示し、そのアプローチの具体的な実装を提案します。

1. The Problem

1. 問題

The problem we wish to consider is:

ここで検討したい問題は次のとおりです。

How can the recipient of a network mail message be "certain" that the signature (e.g., the name in the "FROM" field) is authentic; that is, that the message is really from whom it claims to be?

ネットワークメールのメッセージの受信者は、署名（たとえば「FROM」フィールドにある名前）が本物であること、つまり、メッセージが本当に名乗っているとおりの人物から送られたものであることを、どうすれば「確信」できるでしょうか？

We are interested in the problem of signature authenticity in the network context. For purposes of this note we shall assume a solution to the signature authentication problem for local mail (i.e., messages from one user to another within a single host). That is, we assume that for any host, either the host regards the problem as important and has a mechanism for guaranteeing signatures on local mail or that the host does not regard the problem as important and does not guarantee signature authentication. It should become clear how this assumption relates to our approach to the network signature problem.

ここで関心があるのは、ネットワークという文脈における署名の真正性の問題です。このノートでは、ローカルメール（つまり、1つのホスト内でのあるユーザーから別のユーザーへのメッセージ）の署名の認証の問題については、解決策があるものとします。つまり、どのホストについても、ホストがこの問題を重要だとみなしてローカルメールの署名を保証する仕組みを持っているか、ホストがこの問題を重要だとみなさず署名の認証を保証していないかのどちらかであると仮定します。この仮定が、ネットワークにおける署名の問題に対するここでのアプローチとどう関係するかは、いずれ明らかになるはずです。

We shall discuss our approach using the following simple model for network mail:

ここでは、ネットワークメールについての次の単純なモデルを使って、このアプローチを議論します。

To send net mail a user invokes a mail sending process (SP) on his local host (SH). The process SP acts on behalf of the user to deliver the message to an appropriate mailbox at the receiving host (RH). It does that by interacting with a receiving process (RP) that runs on host RH. RP accepts the message from SP and deposits it in the appropriate mailbox.

ネットメールを送るために、ユーザーは自分のローカルホスト（SH）でメール送信プロセス（SP）を起動します。プロセスSPはユーザーに代わって、受信ホスト（RH）の適切なメールボックスにメッセージを配送します。そのために、SPはホストRHで動作する受信プロセス（RP）とやり取りします。RPはSPからメッセージを受け取り、適切なメールボックスに格納します。

In the current implementation of network mail, the receiving process RP is typically an FTP server process. For the current TENEX implementation the mail sending process SP is either a process running SNDMSG or a "background" MAILER process which sends "queued" (previously posted but undelivered) mail.

現在のネットワークメールの実装では、受信プロセスRPは通常FTPサーバープロセスです。現在のTENEXの実装では、メール送信プロセスSPは、SNDMSGを実行しているプロセスか、「キューに入れられた」（以前に投函されたがまだ配送されていない）メールを送る「バックグラウンド」のMAILERプロセスのどちらかです。

2. An Approach

2. アプローチ

We seek a solution which will allow RP, the receiving process, to mark the signature on messages it receives as authenticated or not with respect to SH, the sending host. If RP can so mark incoming messages, a user reading his mail at RH would be able to see the signature on each message as authenticated or not with respect to the host of origin. The authenticity of the signature on a piece of mail is understood to be responsibility of the originating host. The credibility a user gives a particular message which is marked as authentic can be based on the user's own estimate of the source host's user authentication and access control mechanisms.

ここで求めているのは、受信プロセスであるRPが、受信したメッセージの署名に、送信ホストであるSHに関して認証済みかどうかの印を付けられるようにする解決策です。RPが着信メッセージにそのような印を付けられれば、RHで自分のメールを読むユーザーは、各メッセージの署名が送信元のホストに関して認証済みかどうかを確認できるようになります。メールの署名の真正性は、送信元のホストの責任であると理解されます。認証済みの印が付いた特定のメッセージをユーザーがどの程度信用するかは、送信元ホストのユーザー認証とアクセス制御の仕組みについてのユーザー自身の評価に基づいて決めることができます。

The success of this approach depends upon two things:

このアプローチが成功するかどうかは、次の2つにかかっています。

  1. Users develop estimates of the security of various host user authentication and access control mechanisms. We have seen that users who are concerned about data privacy and security are already doing this within the ARPANET.
  2. The existence of a mechanism which RP, the receiving process, can use to distinguish mail authenticated with respect to the sending host from mail that has not been authenticated by the sending host. That is, a mechanism is required which will allow a properly authorized (by the sending host) mail sending process to identify itself as such to the mail receiving process. The receiving process can then mark mail from such an authenticated process as authentic. Nonauthorized processes (e.g., a user process attempting to pose as an authorized mail sending process) may try to send mail to mailboxes at RH; in such a case the receiving process has the option of refusing to accept the message or accepting them marking them as unauthenticated.
  1. ユーザーが、さまざまなホストのユーザー認証とアクセス制御の仕組みの安全性について評価を持つようになること。データのプライバシーとセキュリティーを気にかけるユーザーは、ARPANET内ですでにこれを行っていることがわかっています。
  2. 受信プロセスであるRPが、送信ホストに関して認証されたメールと、送信ホストによって認証されていないメールとを区別するのに使える仕組みが存在すること。つまり、（送信ホストによって）正しく認可されたメール送信プロセスが、メール受信プロセスに対して自身がそうであることを示せるようにする仕組みが必要です。そうすれば、受信プロセスは、そのような認証されたプロセスからのメールに認証済みの印を付けられます。認可されていないプロセス（たとえば、認可されたメール送信プロセスになりすまそうとするユーザープロセス）が、RHのメールボックスにメールを送ろうとするかもしれません。その場合、受信プロセスは、メッセージの受け入れを拒否するか、メッセージを受け入れて未認証の印を付けるかを選べます。

3. Proposed Implementation of Approach

3. アプローチの実装の提案

The use of passwords is one possible way to accomplish sending process authentication. Only an authorized sending process would know the password and thus be able to properly identify itself to a mail receiving process. We reject the password mechanism as operationally impractical for the following reasons:

パスワードの使用は、送信プロセスの認証を実現する方法の1つとして考えられます。認可された送信プロセスだけがパスワードを知っており、それによってメール受信プロセスに対して自身を正しく示すことができる、というものです。しかし、次の理由から、パスワードの仕組みは運用上実用的でないとして採用しません。

  1. Use of a password requires that the password be stored in the sending program or be accessible to it in some way thereby increasing the likelihood that the privacy of such a password will be compromised.
  2. If a password is compromised, it must be changed at both sending and receiving hosts; a synchronization problem.
  3. Truly secure mail would probably require passwords for each pair of hosts; this requires N*N passwords for an N host network.
  1. パスワードを使うには、パスワードを送信プログラムに格納するか、何らかの方法で送信プログラムからアクセスできるようにする必要があり、それによってパスワードの秘密が漏れる可能性が高まります。
  2. パスワードが漏れた場合は、送信ホストと受信ホストの両方でパスワードを変更しなければなりません。これは同期の問題です。
  3. 本当に安全なメールを実現するには、おそらくホストの組ごとにパスワードが必要になります。これは、N台のホストからなるネットワークではN*N個のパスワードが必要になることを意味します。

As an alternative to the use of passwords as a means for process authentication, we propose that authentication be based on the communication path itself between the sending and receiving process. In the ARPANET, a communication path is uniquely identified by its two ends: the send host-socket pair and the receive host-socket pair. A process can accurately determine the host-socket pair at the remote end of a communication path. We propose that the receiving process consider the sending process to be a properly authorized (by the sending host) sender of mail only if the sending end of the communication path is (one of) the socket(s) reserved for transmission of authenticated mail. The mail sending socket(s) would be reserved by prior host agreement.

プロセスを認証する手段としてパスワードを使う代わりに、送信プロセスと受信プロセスの間の通信経路そのものに基づいて認証することを提案します。ARPANETでは、通信経路はその両端、つまり送信側のホストとソケットの組と受信側のホストとソケットの組によって一意に識別されます。プロセスは、通信経路のリモート側の端にあるホストとソケットの組を正確に特定できます。そこで、通信経路の送信側の端が、認証済みメールの送信用に予約されたソケット（の1つ）である場合に限り、受信プロセスが送信プロセスを（送信ホストによって）正しく認可されたメールの送信者とみなすことを提案します。メール送信用のソケットは、ホスト間の事前の合意によって予約されます。

The responsibility of the sending host is to allow only authorized mail sending processes to access the mail sending socket(s). The responsibility of the user concerned about the authenticity of his mail is to understand that mail marked as authentic means that the sending host has determined the identity of the sender and that the signature on such mail is only as good or bad as the user authentication and access control procedures of the sending host.

送信ホストの責任は、認可されたメール送信プロセスだけがメール送信用のソケットにアクセスできるようにすることです。自分のメールの真正性を気にかけるユーザーの責任は、認証済みの印が付いたメールとは、送信ホストが送信者の身元を確認したという意味であり、そのようなメールの署名の信頼性は送信ホストのユーザー認証とアクセス制御の手順の良し悪しで決まることを理解することです。

4. Additional Remarks

4. 補足

  1. The use of sockets for process authentication is not a new concept within the ARPANET. By host agreement, the TELNET logger process responds to connections to socket #1, the FTP logger process to socket #3, etc. In fact, the privacy of net mail depends upon how well the host controls access to the FTP logger socket; that is, the authenticity of the mail receiving process is based upon that fact that it is the process reached by ICP'ing to socket #3. This note proposes that the same mechanism be used to provide authentication of mail sending processes.

  2. Planned TENEX Experiment

    A set of sockets has been assigned for mail transmission. They are (all numbers are decimal)

               ICP "from" socket - 232
           FTP user command sockets:  receive, send = 234, 235
           Default data transfer (user, send) socket = 237

    We intend to modify the TENEX mail sending, receiving and reading software as suggested above. Mail sent by TENEX to remote hosts which is authentic (with respect to TENEX) will be sent by initiating the ICP to the remote FTP server socket 232. Mail received from remote hosts will be marked as authentic only if the ICP to the TENEX FTP server was initiated from remote socket 232. The TENEX mail reading software will indicate for each message whether or not the signature on the message was source authenticated.

  3. Contention for the Mail Sending Socket

    Depending upon the implementation of the sending host's NCP and its mail net sending software, it may be the case that several users concurrently sending network mail may be competing for the single ICP "from" socket. If socket contention turns out to be a serious problem in practice, a set of ICP "from" sockets could be reserved for authenticated network mail.

  4. The local mail signature authentication problem is nearly independent of the network mail signature authentication problem as we have discussed it. For example, the following observations can be made:

    1. The local users of a host which does not authenticate local mail probably should not expect the host to reliably deliver authenticated network mail to them. Because local mail is not authenticated, it is likely that a malicious local user could add to other users' mail boxes forged messages which are formatted identically to net mail and are marked as authentic in the way the host's mail receiving process marks mail.
    2. A host that has strong user authentication procedures and authenticates local mail is not necessarily a reliable source of authenticated network mail. In order to be a reliable source, it must limit access to the net mail transmission socket(s) to authorized mail sending processes.
    3. A host which does not support local authentic mail could be a reliable source of authentic net mail.
  1. プロセスの認証にソケットを使うことは、ARPANETでは新しい概念ではありません。ホスト間の合意により、TELNETのロガープロセスはソケット#1への接続に、FTPのロガープロセスはソケット#3への接続に応答する、といった具合です。実際、ネットメールの秘匿性は、ホストがFTPのロガーのソケットへのアクセスをどれだけうまく制御しているかにかかっています。つまり、メール受信プロセスの真正性は、それがソケット#3へのICPによって到達するプロセスであるという事実に基づいています。このノートは、同じ仕組みをメール送信プロセスの認証にも使うことを提案します。

  2. TENEXでの実験の計画

    メールの送信用に一連のソケットが割り当てられています。それは次のとおりです（数値はすべて10進数です）。

               ICP "from" socket - 232
           FTP user command sockets:  receive, send = 234, 235
           Default data transfer (user, send) socket = 237

    TENEXのメールの送信、受信、閲覧のソフトウェアを、上で提案したように変更するつもりです。TENEXからリモートホストに送られる（TENEXに関して）認証済みのメールは、リモートのFTPサーバーへのICPをソケット232から開始することで送られます。リモートホストから受信したメールは、TENEXのFTPサーバーへのICPがリモートのソケット232から開始された場合に限り、認証済みの印が付けられます。TENEXのメール閲覧ソフトウェアは、各メッセージについて、そのメッセージの署名が送信元で認証されたものかどうかを示します。

  3. メール送信用ソケットの競合

    送信ホストのNCPとネットメール送信ソフトウェアの実装によっては、ネットワークメールを同時に送信する複数のユーザーが、単一のICPの「from」ソケットを奪い合うことがあるかもしれません。ソケットの競合が実際に深刻な問題になるようであれば、認証済みのネットワークメール用に一連のICPの「from」ソケットを予約することもできます。

  4. ローカルメールにおける署名の認証の問題は、ここで議論してきたネットワークメールにおける署名の認証の問題とはほぼ独立しています。たとえば、次のことがいえます。

    1. ローカルメールを認証しないホストのローカルユーザーは、おそらく、そのホストが認証済みのネットワークメールを確実に配送してくれることを期待すべきではありません。ローカルメールは認証されないので、悪意のあるローカルユーザーが、ネットメールと同じ形式で、ホストのメール受信プロセスが付けるのと同じ方法で認証済みの印が付いた偽造メッセージを、ほかのユーザーのメールボックスに追加できる可能性が高いからです。
    2. 強力なユーザー認証の手順を持ち、ローカルメールを認証するホストが、必ずしも認証済みのネットワークメールの信頼できる送信元であるとは限りません。信頼できる送信元であるためには、ネットメールの送信用ソケットへのアクセスを、認可されたメール送信プロセスに限定しなければなりません。
    3. ローカルの認証済みメールをサポートしていないホストでも、認証済みのネットメールの信頼できる送信元になりえます。
