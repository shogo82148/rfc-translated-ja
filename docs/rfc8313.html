Use of Multicast across Inter-domain Peering Points

RFC 8313

ドメイン間ピアリングポイントを越えたマルチキャストの使用

Abstract

概要

This document examines the use of Source-Specific Multicast (SSM) across inter-domain peering points for a specified set of deployment scenarios. The objectives are to (1) describe the setup process for multicast-based delivery across administrative domains for these scenarios and (2) document supporting functionality to enable this process.

この文書は、特定の展開シナリオ群について、ドメイン間ピアリングポイントを越えたソース固有マルチキャスト（SSM）の使用を検討します。 目的は、（1）これらのシナリオにおいて管理ドメインを越えたマルチキャストベースの配送を設定する手順を説明すること、および（2）この手順を可能にするための支援機能を文書化することです。

1. Introduction

1. はじめに

Content and data from several types of applications (e.g., live video streaming, software downloads) are well suited for delivery via multicast means. The use of multicast for delivering such content or other data offers significant savings in terms of utilization of resources in any given administrative domain. End User (EU) demand for such content or other data is growing. Often, this requires transporting the content or other data across administrative domains via inter-domain peering points.

いくつかの種類のアプリケーション（たとえば、ライブビデオストリーミング、ソフトウェアのダウンロード）のコンテンツやデータは、マルチキャストによる配送に適しています。 このようなコンテンツやその他のデータの配送にマルチキャストを使用すると、どの管理ドメインにおいてもリソースの利用の点で大幅な節約になります。 このようなコンテンツやその他のデータに対するエンドユーザー（EU）の需要は増え続けています。 多くの場合、そのためにはドメイン間ピアリングポイントを介して、管理ドメインを越えてコンテンツやその他のデータを転送する必要があります。

The objectives of this document are twofold:

この文書の目的は2つあります。

  • Describe the technical process and establish guidelines for setting up multicast-based delivery of application content or other data across inter-domain peering points via a set of use cases (where "Use Case 3.1" corresponds to Section 3.1, "Use Case 3.2" corresponds to Section 3.2, etc.).
  • Catalog all required exchanges of information between the administrative domains to support multicast-based delivery. This enables operators to initiate necessary processes to support inter-domain peering with multicast.
  • 一連のユースケース（「ユースケース3.1」はセクション3.1に、「ユースケース3.2」はセクション3.2に対応する、など）を通じて、ドメイン間ピアリングポイントを越えたアプリケーションコンテンツやその他のデータのマルチキャストベースの配送を設定するための技術的な手順を説明し、ガイドラインを確立すること。
  • マルチキャストベースの配送をサポートするために管理ドメイン間で必要となる情報交換をすべて列挙すること。 これにより、運用者は、マルチキャストを用いたドメイン間ピアリングをサポートするのに必要な手続きを開始できます。

The scope and assumptions for this document are as follows:

この文書の範囲と前提は次のとおりです。

  • Administrative Domain 1 (AD-1) sources content to one or more EUs in one or more Administrative Domain 2 (AD-2) entities. AD-1 and AD-2 want to use IP multicast to allow support for large and growing EU populations, with a minimum amount of duplicated traffic to send across network links.

    • This document does not detail the case where EUs are originating content. To support that additional service, it is recommended that some method (outside the scope of this document) be used by which the content from EUs is transmitted to the application in AD-1 and AD-1 can send out the traffic as IP multicast. From that point on, the descriptions in this document apply, except that they are not complete because they do not cover the transport or operational aspects of the leg from the EU to AD-1.
    • This document does not detail the case where AD-1 and AD-2 are not directly connected to each other and are instead connected via one or more other ADs (as opposed to a peering point) that serve as transit providers. The cases described in this document where tunnels are used between AD-1 and AD-2 can be applied to such scenarios, but SLA ("Service Level Agreement") control, for example, would be different. Additional issues will likely exist as well in such scenarios. This topic is left for further study.
  • For the purposes of this document, the term "peering point" refers to a network connection ("link") between two administrative network domains over which traffic is exchanged between them. This is also referred to as a Network-to-Network Interface (NNI). Unless otherwise noted, it is assumed that the peering point is a private peering point, where the network connection is a physically or virtually isolated network connection solely between AD-1 and AD-2. The other case is that of a broadcast peering point, which is a common option in public Internet Exchange Points (IXPs). See Section 4.2.4 for more details.
  • AD-1 is enabled with native multicast. A peering point exists between AD-1 and AD-2.
  • It is understood that several protocols are available for this purpose, including Protocol-Independent Multicast - Sparse Mode (PIM-SM) and Protocol-Independent Multicast - Source-Specific Multicast (PIM-SSM) [RFC7761], the Internet Group Management Protocol (IGMP) [RFC3376], and Multicast Listener Discovery (MLD) [RFC3810].
  • As described in Section 2, the source IP address of the (so-called "(S,G)") multicast stream in the originating AD (AD-1) is known. Under this condition, using PIM-SSM is beneficial, as it allows the receiver's upstream router to send a join message directly to the source without the need to invoke an intermediate Rendezvous Point (RP). The use of SSM also presents an improved threat mitigation profile against attack, as described in [RFC4609]. Hence, in the case of inter-domain peering, it is recommended that only SSM protocols be used; the setup of inter-domain peering for ASM (Any-Source Multicast) is out of scope for this document.
  • The rest of this document assumes that PIM-SSM and BGP are used across the peering point, plus Automatic Multicast Tunneling (AMT) [RFC7450] and/or Generic Routing Encapsulation (GRE), according to the scenario in question. The use of other protocols is beyond the scope of this document.
  • AMT is set up at the peering point if either the peering point or AD-2 is not multicast enabled. It is assumed that an AMT relay will be available to a client for multicast delivery. The selection of an optimal AMT relay by a client is out of scope for this document. Note that using AMT is necessary only when native multicast is unavailable in the peering point (Use Case 3.3) or in the downstream administrative domain (Use Cases 3.4 and 3.5).
  • It is assumed that the collection of billing data is done at the application level and is not considered to be a networking issue. The settlements process for EU billing and/or inter-provider billing is out of scope for this document.
  • Inter-domain network connectivity troubleshooting is only considered within the context of a cooperative process between the two domains.

  • 管理ドメイン1（AD-1）は、1つ以上の管理ドメイン2（AD-2）のエンティティー内にいる1つ以上のEUにコンテンツを送出します。 AD-1とAD-2は、ネットワークリンクを越えて送信する重複トラフィックを最小限に抑えつつ、大規模で増え続けるEUの集団をサポートできるように、IPマルチキャストを使用したいと考えています。

    • この文書は、EUがコンテンツを発信する場合については詳述しません。 その追加のサービスをサポートするには、EUからのコンテンツをAD-1内のアプリケーションに送信し、AD-1がそのトラフィックをIPマルチキャストとして送出できるような何らかの方法（この文書の範囲外）を使用することが推奨されます。 そこから先はこの文書の説明が適用されますが、EUからAD-1までの区間の転送や運用の側面を扱っていないため、完全ではありません。
    • この文書は、AD-1とAD-2が互いに直接接続されておらず、代わりにトランジットプロバイダーとして機能する1つ以上の他のAD（ピアリングポイントではなく）を介して接続されている場合については詳述しません。 この文書で説明する、AD-1とAD-2の間でトンネルを使用する場合は、このようなシナリオにも適用できますが、たとえばSLA（「サービスレベル合意（Service Level Agreement）」）の制御は異なるでしょう。 このようなシナリオには、ほかにも課題がある可能性が高いです。 このトピックは今後の検討課題とします。
  • この文書では、「ピアリングポイント（peering point）」という用語は、2つの管理ネットワークドメインの間のネットワーク接続（「リンク」）で、それらの間でトラフィックが交換されるものを指します。 これはネットワーク間インターフェイス（NNI）とも呼ばれます。 特に断りのない限り、ピアリングポイントはプライベートピアリングポイント、すなわちネットワーク接続がAD-1とAD-2の間だけで物理的または仮想的に分離されたネットワーク接続であるものと想定します。 もう1つのケースはブロードキャストピアリングポイントで、これはパブリックなインターネットエクスチェンジポイント（IXP）でよく使われる選択肢です。 詳細についてはセクション4.2.4を参照してください。
  • AD-1ではネイティブマルチキャストが有効になっています。 AD-1とAD-2の間にはピアリングポイントが存在します。
  • この目的に使用できるプロトコルとして、Protocol-Independent Multicast - Sparse Mode（PIM-SM）とProtocol-Independent Multicast - Source-Specific Multicast（PIM-SSM）[RFC7761]、Internet Group Management Protocol（IGMP）[RFC3376]、Multicast Listener Discovery（MLD）[RFC3810]など、いくつかのプロトコルがあることは理解されています。
  • セクション2で説明するように、発信元のAD（AD-1）におけるマルチキャストストリーム（いわゆる「(S,G)」）の送信元IPアドレスは既知です。 この条件のもとでは、PIM-SSMを使用すると、受信者の上流ルーターが中間のランデブーポイント（RP）を介さずに送信元へ直接参加メッセージ（join message）を送信できるため、有益です。 また、[RFC4609]で説明されているように、SSMを使用すると攻撃に対する脅威緩和の特性も改善されます。 したがって、ドメイン間ピアリングの場合はSSMプロトコルのみを使用することが推奨されます。 ASM（Any-Source Multicast）のためのドメイン間ピアリングの設定は、この文書の範囲外です。
  • この文書の残りの部分では、ピアリングポイントを越えてPIM-SSMとBGPを使用し、さらに対象のシナリオに応じてAutomatic Multicast Tunneling（AMT）[RFC7450]またはGeneric Routing Encapsulation（GRE）、あるいはその両方を使用することを前提とします。 その他のプロトコルの使用は、この文書の範囲外です。
  • ピアリングポイントとAD-2のいずれかでマルチキャストが有効になっていない場合は、ピアリングポイントでAMTを設定します。 クライアントは、マルチキャスト配送のためにAMTリレーを利用できるものと想定します。 クライアントによる最適なAMTリレーの選択は、この文書の範囲外です。 AMTの使用が必要になるのは、ピアリングポイント（ユースケース3.3）または下流の管理ドメイン（ユースケース3.4と3.5）でネイティブマルチキャストが利用できない場合だけであることに注意してください。
  • 課金データの収集はアプリケーションレベルで行われ、ネットワーキングの問題とはみなさないものと想定します。 EUへの課金やプロバイダー間の課金、あるいはその両方の精算プロセスは、この文書の範囲外です。
  • ドメイン間のネットワーク接続性のトラブルシューティングは、2つのドメイン間の協力的なプロセスという文脈の中でのみ考慮します。

This document also attempts to identify ways by which the peering process can be improved. Development of new methods for improvement is beyond the scope of this document.

この文書は、ピアリングのプロセスを改善できる方法を特定することも試みます。 改善のための新しい方法の開発は、この文書の範囲外です。

2. Overview of Inter-domain Multicast Application Transport

2. ドメイン間マルチキャストアプリケーション転送の概要

A multicast-based application delivery scenario is as follows:

マルチキャストベースのアプリケーション配送のシナリオは次のとおりです。

  • Two independent administrative domains are interconnected via a peering point.

  • The peering point is either multicast enabled (end-to-end native multicast across the two domains) or connected by one of two possible tunnel types:

    • A GRE tunnel [RFC2784] allowing multicast tunneling across the peering point, or
    • AMT [RFC7450].
  • A service provider controls one or more application sources in AD-1 that will send multicast IP packets via one or more (S,G)s (multicast traffic flows; see Section 4.2.1 if you are unfamiliar with IP multicast). It is assumed that the service being provided is suitable for delivery via multicast (e.g., live video streaming of popular events, software downloads to many devices) and that the packet streams will be carried by a suitable multicast transport protocol.
  • An EU controls a device connected to AD-2, which runs an application client compatible with the service provider's application source.
  • The application client joins appropriate (S,G)s in order to receive the data necessary to provide the service to the EU. The mechanisms by which the application client learns the appropriate (S,G)s are an implementation detail of the application and are out of scope for this document.
  • 2つの独立した管理ドメインが、ピアリングポイントを介して相互接続されています。

  • ピアリングポイントは、マルチキャストが有効になっている（2つのドメインにまたがるエンドツーエンドのネイティブマルチキャスト）か、次の2種類のトンネルのいずれかで接続されています。

    • ピアリングポイントを越えたマルチキャストのトンネリングを可能にするGREトンネル[RFC2784]、または
    • AMT[RFC7450]。
  • サービスプロバイダーは、1つ以上の(S,G)（マルチキャストトラフィックフロー。IPマルチキャストになじみがない場合はセクション4.2.1を参照してください）を介してマルチキャストIPパケットを送信する、AD-1内の1つ以上のアプリケーションソースを制御します。 提供されるサービスはマルチキャストによる配送に適しており（たとえば、人気のあるイベントのライブビデオストリーミング、多数のデバイスへのソフトウェアのダウンロード）、パケットストリームは適切なマルチキャストトランスポートプロトコルによって運ばれるものと想定します。
  • EUは、AD-2に接続されたデバイスを制御します。 このデバイスでは、サービスプロバイダーのアプリケーションソースと互換性のあるアプリケーションクライアントが動作しています。
  • アプリケーションクライアントは、EUにサービスを提供するのに必要なデータを受信するために、適切な(S,G)に参加します。 アプリケーションクライアントが適切な(S,G)を知るメカニズムは、アプリケーションの実装の詳細であり、この文書の範囲外です。

The assumption here is that AD-1 has ultimate responsibility for delivering the multicast-based service on behalf of the content source(s). All relevant interactions between the two domains described in this document are based on this assumption.

ここでの前提は、AD-1がコンテンツソースに代わってマルチキャストベースのサービスを配送する最終的な責任を負うということです。 この文書で説明する2つのドメイン間の関連するやり取りはすべて、この前提に基づいています。

Note that AD-2 may be an independent network domain (e.g., a Tier 1 network operator domain). Alternately, AD-2 could also be an enterprise network domain operated by a single customer of AD-1. The peering point architecture and requirements may have some unique aspects associated with enterprise networks; see Section 3.

AD-2は、独立したネットワークドメイン（たとえば、Tier 1のネットワーク運用者のドメイン）である場合があることに注意してください。 あるいは、AD-2は、AD-1の単一の顧客が運用する企業ネットワークのドメインである可能性もあります。 ピアリングポイントのアーキテクチャーと要件には、企業ネットワークに関連する固有の側面がある場合があります。 セクション3を参照してください。

The use cases describing various architectural configurations for multicast distribution, along with associated requirements, are described in Section 3. Section 4 contains a comprehensive list of pertinent information that needs to be exchanged between the two domains in order to support functions to enable application transport.

マルチキャスト配信のさまざまなアーキテクチャー構成を説明するユースケースは、関連する要件とともにセクション3で説明します。 セクション4には、アプリケーションの転送を可能にする機能をサポートするために2つのドメイン間で交換する必要のある関連情報の包括的な一覧があります。

3. Inter-domain Peering Point Requirements for Multicast

3. マルチキャストのためのドメイン間ピアリングポイントの要件

The transport of applications using multicast requires that the inter-domain peering point be enabled to support such a process. This section presents five use cases for consideration.

マルチキャストを使用してアプリケーションを転送するには、ドメイン間ピアリングポイントがそのような処理をサポートできるようになっている必要があります。 このセクションでは、検討のために5つのユースケースを示します。

3.1. Native Multicast

3.1. ネイティブマルチキャスト

This use case involves end-to-end native multicast between the two administrative domains, and the peering point is also native multicast enabled. See Figure 1.

このユースケースでは、2つの管理ドメイン間でエンドツーエンドのネイティブマルチキャストを使用し、ピアリングポイントでもネイティブマルチキャストが有効になっています。 図1を参照してください。

Advantages of this configuration:

この構成の利点は次のとおりです。

  • Most efficient use of bandwidth in both domains.
  • Fewer devices in the path traversed by the multicast stream when compared to an AMT-enabled peering point.
  • 両方のドメインで帯域幅を最も効率的に使用できます。
  • AMTを有効にしたピアリングポイントと比べて、マルチキャストストリームが通過するパス上のデバイスが少なくなります。

From the perspective of AD-1, the one disadvantage associated with native multicast to AD-2 instead of individual unicast to every EU in AD-2 is that it does not have the ability to count the number of EUs as well as the transmitted bytes delivered to them. This information is relevant from the perspective of customer billing and operational logs. It is assumed that such data will be collected by the application layer. The application-layer mechanisms for generating this information need to be robust enough so that all pertinent requirements for the source provider and the AD operator are satisfactorily met. The specifics of these methods are beyond the scope of this document.

AD-1の観点から見ると、AD-2内のすべてのEUへの個別のユニキャストではなくAD-2へのネイティブマルチキャストを使用することに伴う1つの欠点は、EUの数や、EUに配送された送信バイト数を数えることができないことです。 この情報は、顧客への課金や運用ログの観点から重要です。 このようなデータは、アプリケーション層で収集するものと想定します。 この情報を生成するアプリケーション層のメカニズムは、ソースプロバイダーとADの運用者の関連する要件をすべて十分に満たせるほど堅牢である必要があります。 これらの方法の詳細は、この文書の範囲外です。

Architectural guidelines for this configuration are as follows:

この構成のアーキテクチャー上のガイドラインは次のとおりです。

  1. Dual homing for peering points between domains is recommended as a way to ensure reliability with full BGP table visibility.
  2. If the peering point between AD-1 and AD-2 is a controlled network environment, then bandwidth can be allocated accordingly by the two domains to permit the transit of non-rate-adaptive multicast traffic. If this is not the case, then the multicast traffic must support congestion control via any of the mechanisms described in Section 4.1 of [BCP145].
  3. The sending and receiving of multicast traffic between two domains is typically determined by local policies associated with each domain. For example, if AD-1 is a service provider and AD-2 is an enterprise, then AD-1 may support local policies for traffic delivery to, but not traffic reception from, AD-2. Another example is the use of a policy by which AD-1 delivers specified content to AD-2 only if such delivery has been accepted by contract.
  4. It is assumed that relevant information on multicast streams delivered to EUs in AD-2 is collected by available capabilities in the application layer. The precise nature and formats of the collected information will be determined by directives from the source owner and the domain operators.
  1. BGPテーブル全体の可視性を保ちつつ信頼性を確保する方法として、ドメイン間のピアリングポイントのデュアルホーミングが推奨されます。
  2. AD-1とAD-2の間のピアリングポイントが管理されたネットワーク環境である場合、2つのドメインはそれに応じて帯域幅を割り当て、レート適応型でないマルチキャストトラフィックの通過を許可できます。 そうでない場合、マルチキャストトラフィックは、[BCP145]のセクション4.1で説明されているいずれかのメカニズムによる輻輳制御をサポートする必要があります。
  3. 2つのドメイン間のマルチキャストトラフィックの送受信は、通常、各ドメインに関連付けられたローカルポリシーによって決まります。 たとえば、AD-1がサービスプロバイダーで、AD-2が企業である場合、AD-1は、AD-2へのトラフィックの配送はサポートするものの、AD-2からのトラフィックの受信はサポートしないローカルポリシーを持つことがあります。 別の例としては、AD-1が、契約によって配送が合意されている場合に限り、指定されたコンテンツをAD-2に配送するというポリシーを使用することが挙げられます。
  4. AD-2内のEUに配送されるマルチキャストストリームに関する関連情報は、アプリケーション層で利用可能な機能によって収集されるものと想定します。 収集される情報の正確な性質や形式は、ソースの所有者とドメインの運用者からの指示によって決まります。

3.2. Peering Point Enabled with GRE Tunnel

3.2. GREトンネルを有効にしたピアリングポイント

The peering point is not native multicast enabled in this use case. There is a GRE tunnel provisioned over the peering point. See Figure 2.

このユースケースでは、ピアリングポイントでネイティブマルチキャストが有効になっていません。 ピアリングポイント上にGREトンネルがプロビジョニングされています。 図2を参照してください。

In this case, interconnection I1 between AD-1 and AD-2 in Figure 2 is multicast enabled via a GRE tunnel [RFC2784] between the two BRs and encapsulating the multicast protocols across it.

この場合、図2におけるAD-1とAD-2の間の相互接続I1は、2つのBRの間のGREトンネル[RFC2784]によってマルチキャストが有効になり、そのトンネルを越えてマルチキャストプロトコルがカプセル化されます。

Normally, this approach is chosen if the uBR physically connected to the peering link cannot or should not be enabled for IP multicast. This approach may also be beneficial if the BR and uBR are the same device but the peering link is a broadcast domain (IXP); see Section 4.2.4.

通常、この方法は、ピアリングリンクに物理的に接続されたuBRでIPマルチキャストを有効にできない場合、または有効にすべきでない場合に選択されます。 この方法は、BRとuBRが同じデバイスであっても、ピアリングリンクがブロードキャストドメイン（IXP）である場合にも有益な場合があります。 セクション4.2.4を参照してください。

The routing configuration is basically unchanged: instead of running BGP (SAFI-2) ("SAFI" stands for "Subsequent Address Family Identifier") across the native IP multicast link between AD-1 and AD-2, BGP (SAFI-2) is now run across the GRE tunnel.

ルーティングの設定は基本的に変わりません。 AD-1とAD-2の間のネイティブIPマルチキャストリンクを越えてBGP（SAFI-2）（「SAFI」は「Subsequent Address Family Identifier」の略です）を実行する代わりに、GREトンネルを越えてBGP（SAFI-2）を実行するようになります。

Advantages of this configuration:

この構成の利点は次のとおりです。

  • Highly efficient use of bandwidth in both domains, although not as efficient as the fully native multicast use case (Section 3.1).
  • Fewer devices in the path traversed by the multicast stream when compared to an AMT-enabled peering point.
  • Ability to support partial and/or incremental IP multicast deployments in AD-1 and/or AD-2: only the path or paths between the AS/BR (AD-1) and the BR/EU (AD-2) need to be multicast enabled. The uBRs may not support IP multicast or enabling it could be seen as operationally risky on that important edge node, whereas dedicated BR nodes for IP multicast may (at least initially) be more acceptable. The BR can also be located such that only parts of the domain may need to support native IP multicast (e.g., only the core in AD-1 but not edge networks towards the uBR).
  • GRE is an existing technology and is relatively simple to implement.
  • 完全にネイティブなマルチキャストのユースケース（セクション3.1）ほどではないものの、両方のドメインで帯域幅を非常に効率的に使用できます。
  • AMTを有効にしたピアリングポイントと比べて、マルチキャストストリームが通過するパス上のデバイスが少なくなります。
  • AD-1とAD-2の一方または両方で、部分的または段階的なIPマルチキャストの展開をサポートできます。 マルチキャストを有効にする必要があるのは、AS/BR（AD-1）とBR/EU（AD-2）の間のパスだけです。 uBRがIPマルチキャストをサポートしていない場合や、その重要なエッジノードでIPマルチキャストを有効にすることが運用上危険とみなされる場合がありますが、IPマルチキャスト専用のBRノードであれば（少なくとも当初は）受け入れられやすいでしょう。 また、ドメインの一部だけがネイティブIPマルチキャストをサポートすればよいようにBRを配置することもできます（たとえば、AD-1のコアだけで、uBRに向かうエッジネットワークではサポートしない）。
  • GREは既存の技術であり、実装が比較的簡単です。

Disadvantages of this configuration:

この構成の欠点は次のとおりです。

  • Per Use Case 3.1, current router technology cannot count the number of EUs or the number of bytes transmitted.
  • The GRE tunnel requires manual configuration.
  • The GRE tunnel must be established prior to starting the stream.
  • The GRE tunnel is often left pinned up.
  • ユースケース3.1と同様に、現在のルーター技術ではEUの数や送信バイト数を数えることができません。
  • GREトンネルには手動での設定が必要です。
  • GREトンネルは、ストリームを開始する前に確立しておく必要があります。
  • GREトンネルは、張られたままにされることがよくあります。

Architectural guidelines for this configuration include the following:

この構成のアーキテクチャー上のガイドラインには次のものがあります。

Guidelines (a) through (d) are the same as those described in Use Case 3.1. Two additional guidelines are as follows:

ガイドライン（a）から（d）は、ユースケース3.1で説明したものと同じです。 追加のガイドラインが2つあり、それらは次のとおりです。

  1. GRE tunnels are typically configured manually between peering points to support multicast delivery between domains.
  2. It is recommended that the GRE tunnel (tunnel server) configuration in the source network be such that it only advertises the routes to the application sources and not to the entire network. This practice will prevent unauthorized delivery of applications through the tunnel (for example, if the application (e.g., content) is not part of an agreed-upon inter-domain partnership).
  1. GREトンネルは通常、ドメイン間のマルチキャスト配送をサポートするために、ピアリングポイント間で手動で設定されます。
  2. ソースネットワークにおけるGREトンネル（トンネルサーバー）の設定は、ネットワーク全体への経路ではなく、アプリケーションソースへの経路だけを広告するようにすることが推奨されます。 このようにすると、トンネルを介したアプリケーションの許可されていない配送（たとえば、そのアプリケーション（たとえばコンテンツ）が合意済みのドメイン間パートナーシップに含まれていない場合）を防止できます。

3.3. Peering Point Enabled with AMT - Both Domains Multicast Enabled

3.3. AMTを有効にしたピアリングポイント - 両方のドメインでマルチキャストが有効な場合

It is assumed that both administrative domains in this use case are native multicast enabled here; however, the peering point is not.

このユースケースでは、両方の管理ドメインでネイティブマルチキャストが有効になっているものの、ピアリングポイントでは有効になっていないものと想定します。

The peering point is enabled with AMT. The basic configuration is depicted in Figure 3.

ピアリングポイントではAMTが有効になっています。 基本的な構成を図3に示します。

Advantages of this configuration:

この構成の利点は次のとおりです。

  • Highly efficient use of bandwidth in AD-1.

  • AMT is an existing technology and is relatively simple to implement. Attractive properties of AMT include the following:

    • Dynamic interconnection between the gateway-relay pair across the peering point.
    • Ability to serve clients and servers with differing policies.
  • AD-1で帯域幅を非常に効率的に使用できます。

  • AMTは既存の技術であり、実装が比較的簡単です。 AMTの魅力的な特性には次のものがあります。

    • ピアリングポイントを越えた、ゲートウェイとリレーのペアの間の動的な相互接続。
    • 異なるポリシーを持つクライアントやサーバーに対応できること。

Disadvantages of this configuration:

この構成の欠点は次のとおりです。

  • Per Use Case 3.1 (AD-2 is native multicast), current router technology cannot count the number of EUs or the number of bytes transmitted to all EUs.
  • Additional devices (AMT gateway and relay pairs) may be introduced into the path if these services are not incorporated into the existing routing nodes.
  • Currently undefined mechanisms for the AG to automatically select the optimal AR.
  • ユースケース3.1と同様に（AD-2はネイティブマルチキャストです）、現在のルーター技術では、EUの数や、すべてのEUへの送信バイト数を数えることができません。
  • これらのサービスが既存のルーティングノードに組み込まれていない場合、追加のデバイス（AMTゲートウェイとリレーのペア）がパスに導入されることがあります。
  • AGが最適なARを自動的に選択するためのメカニズムは、現在のところ定義されていません。

Architectural guidelines for this configuration are as follows:

この構成のアーキテクチャー上のガイドラインは次のとおりです。

Guidelines (a) through (d) are the same as those described in Use Case 3.1. In addition,

ガイドライン（a）から（d）は、ユースケース3.1で説明したものと同じです。 それに加えて、

  1. It is recommended that AMT relay and gateway pairs be configured at the peering points to support multicast delivery between domains. AMT tunnels will then configure dynamically across the peering points once the gateway in AD-2 receives the (S,G) information from the EU.
  1. ドメイン間のマルチキャスト配送をサポートするために、ピアリングポイントにAMTリレーとゲートウェイのペアを設定することが推奨されます。 そうすれば、AD-2内のゲートウェイがEUから(S,G)情報を受け取った時点で、ピアリングポイントを越えてAMTトンネルが動的に設定されます。

3.4. Peering Point Enabled with AMT - AD-2 Not Multicast Enabled

3.4. AMTを有効にしたピアリングポイント - AD-2でマルチキャストが有効でない場合

In this AMT use case, AD-2 is not multicast enabled. Hence, the interconnection between AD-2 and the EU is also not multicast enabled. This use case is depicted in Figure 4.

このAMTのユースケースでは、AD-2でマルチキャストが有効になっていません。 したがって、AD-2とEUの間の相互接続でもマルチキャストは有効になっていません。 このユースケースを図4に示します。

This use case is equivalent to having unicast distribution of the application through AD-2. The total number of AMT tunnels would be equal to the total number of EUs requesting the application. The peering point thus needs to accommodate the total number of AMT tunnels between the two domains. Each AMT tunnel can provide the data usage associated with each EU.

このユースケースは、AD-2を通じてアプリケーションをユニキャストで配信するのと同等です。 AMTトンネルの総数は、アプリケーションを要求するEUの総数と等しくなります。 したがって、ピアリングポイントは、2つのドメイン間のAMTトンネルの総数を収容する必要があります。 各AMTトンネルは、各EUに関連付けられたデータ使用量を提供できます。

Advantages of this configuration:

この構成の利点は次のとおりです。

  • Efficient use of bandwidth in AD-1 (the closer the AR is to the uBR, the more efficient).
  • Ability of AD-1 to introduce content delivery based on IP multicast, without any support by network devices in AD-2: only the application side in the EU device needs to perform AMT gateway library functionality to receive traffic from the AMT relay.
  • Allows AD-2 to "upgrade" to Use Case 3.5 (see Section 3.5) at a later time, without any change in AD-1 at that time.

  • AMT is an existing technology and is relatively simple to implement. Attractive properties of AMT include the following:

    • Dynamic interconnection between the AMT gateway-relay pair across the peering point.
    • Ability to serve clients and servers with differing policies.
  • Each AMT tunnel serves as a count for each EU and is also able to track data usage (bytes) delivered to the EU.
  • AD-1で帯域幅を効率的に使用できます（ARがuBRに近いほど効率的になります）。
  • AD-1は、AD-2内のネットワークデバイスによるサポートなしに、IPマルチキャストに基づくコンテンツ配送を導入できます。 AMTリレーからトラフィックを受信するためにAMTゲートウェイのライブラリー機能を実行する必要があるのは、EUのデバイス内のアプリケーション側だけです。
  • AD-2は、その時点でAD-1に何の変更も加えることなく、後からユースケース3.5（セクション3.5を参照）に「アップグレード」できます。

  • AMTは既存の技術であり、実装が比較的簡単です。 AMTの魅力的な特性には次のものがあります。

    • ピアリングポイントを越えた、AMTゲートウェイとリレーのペアの間の動的な相互接続。
    • 異なるポリシーを持つクライアントやサーバーに対応できること。
  • 各AMTトンネルが各EUの数として機能し、EUに配送されたデータ使用量（バイト数）も追跡できます。

Disadvantages of this configuration:

この構成の欠点は次のとおりです。

  • Additional devices (AMT gateway and relay pairs) are introduced into the transport path.
  • Assuming multiple peering points between the domains, the EU gateway needs to be able to find the "correct" AMT relay in AD-1.
  • 追加のデバイス（AMTゲートウェイとリレーのペア）が転送パスに導入されます。
  • ドメイン間に複数のピアリングポイントがあると想定すると、EUのゲートウェイは、AD-1内の「正しい」AMTリレーを見つけられる必要があります。

Architectural guidelines for this configuration are as follows:

この構成のアーキテクチャー上のガイドラインは次のとおりです。

Guidelines (a) through (c) are the same as those described in Use Case 3.1. In addition,

ガイドライン（a）から（c）は、ユースケース3.1で説明したものと同じです。 それに加えて、

  1. It is necessary that proper procedures be implemented such that the AMT gateway at the EU device is able to find the correct AMT relay for each (S,G) content stream. Standard mechanisms for that selection are still subject to ongoing work. This includes the use of anycast gateway addresses, anycast DNS names, or explicit configuration that maps (S,G) to a relay address; or letting the application in the EU/G provide the relay address to the embedded AMT gateway function.
  2. The AMT tunnel's capabilities are expected to be sufficient for the purpose of collecting relevant information on the multicast streams delivered to EUs in AD-2.
  1. EUのデバイスにあるAMTゲートウェイが、各(S,G)コンテンツストリームに対する正しいAMTリレーを見つけられるように、適切な手順を実装する必要があります。 その選択のための標準的なメカニズムについては、まだ作業が続いています。 これには、エニーキャストのゲートウェイアドレス、エニーキャストのDNS名、(S,G)をリレーアドレスに対応付ける明示的な設定の使用、またはEU/G内のアプリケーションが組み込みのAMTゲートウェイ機能にリレーアドレスを提供するようにすることが含まれます。
  2. AMTトンネルの能力は、AD-2内のEUに配送されるマルチキャストストリームに関する関連情報を収集する目的には十分であると見込まれます。

3.5. AD-2 Not Multicast Enabled - Multiple AMT Tunnels through AD-2

3.5. AD-2でマルチキャストが有効でない場合 - AD-2を通る複数のAMTトンネル

Figure 5 illustrates a variation of Use Case 3.4:

図5は、ユースケース3.4の変形を示しています。

Use Case 3.4 results in several long AMT tunnels crossing the entire network of AD-2 linking the EU device and the AMT relay in AD-1 through the peering point. Depending on the number of EUs, there is a likelihood of an unacceptably high amount of traffic due to the large number of AMT tunnels -- and unicast streams -- through the peering point. This situation can be alleviated as follows:

ユースケース3.4では、ピアリングポイントを通ってEUのデバイスとAD-1内のAMTリレーを結ぶ、AD-2のネットワーク全体を横断する長いAMTトンネルがいくつもできます。 EUの数によっては、ピアリングポイントを通る多数のAMTトンネル（およびユニキャストストリーム）のために、トラフィックが許容できないほど大量になる可能性があります。 この状況は、次のようにして緩和できます。

  • Provisioning of strategically located AMT nodes in AD-2. An AMT node comprises co-location of an AMT gateway and an AMT relay. No change is required by AD-1, as compared to Use Case 3.4. This can be done whenever AD-2 sees fit (e.g., too much traffic across the peering point).
  • One such node is on the AD-2 side of the peering point (AMT node AGAR1 in Figure 5).
  • A single AMT tunnel established across the peering point linking the AMT relay in AD-1 to the AMT gateway in AMT node AGAR1 in AD-2.
  • AMT tunnels linking AMT node AGAR1 at the peering point in AD-2 to other AMT nodes located at the edges of AD-2: e.g., AMT tunnel I2 linking the AMT relay in AGAR1 to the AMT gateway in AMT node AGAR2 (Figure 5).
  • AMT tunnels linking an EU device (via a gateway client embedded in the device) and an AMT relay in an appropriate AMT node at the edge of AD-2: e.g., I3 linking the EU gateway in the device to the AMT relay in AMT node AGAR2.
  • In the simplest option (not shown), AD-2 only deploys a single AGAR1 node and lets the EU/G build AMT tunnels directly to it. This setup already solves the problem of replicated traffic across the peering point. As soon as there is a need to support more AMT tunnels to the EU/G, then additional AGAR2 nodes can be deployed by AD-2.
  • AD-2内に、戦略的に配置したAMTノードをプロビジョニングします。 AMTノードは、AMTゲートウェイとAMTリレーを同じ場所に配置したものです。 ユースケース3.4と比べて、AD-1には変更は必要ありません。 これは、AD-2が適切と判断したとき（たとえば、ピアリングポイントを越えるトラフィックが多すぎるとき）にいつでも実施できます。
  • そのようなノードの1つは、ピアリングポイントのAD-2側にあります（図5のAMTノードAGAR1）。
  • ピアリングポイントを越えて確立された単一のAMTトンネルが、AD-1内のAMTリレーと、AD-2内のAMTノードAGAR1にあるAMTゲートウェイを結びます。

4.1.1. Bandwidth Management

4.1.1. 帯域幅の管理

Like IP unicast traffic, IP multicast traffic carried across non-controlled networks must comply with congestion control principles as described in [BCP41] and as explained in detail for UDP IP multicast in [BCP145].

IPユニキャストトラフィックと同様に、管理されていないネットワークを越えて運ばれるIPマルチキャストトラフィックは、[BCP41]で説明され、UDPのIPマルチキャストについては[BCP145]で詳しく説明されている輻輳制御の原則に従う必要があります。

Non-controlled networks (such as the Internet) are networks where there is no policy for managing bandwidth other than best effort with a fair share of bandwidth under congestion. As a simplified rule of thumb, complying with congestion control principles means reducing bandwidth under congestion in a way that is fair to competing (typically TCP) flows ("rate adaptive").

管理されていないネットワーク（インターネットなど）とは、輻輳時に帯域幅を公平に分け合うベストエフォート以外に、帯域幅を管理するポリシーがないネットワークです。 簡略化した経験則としては、輻輳制御の原則に従うとは、競合する（通常はTCPの）フローに対して公平な方法で、輻輳時に帯域幅を減らすこと（「レート適応型（rate adaptive）」）を意味します。

In many instances, multicast content delivery evolves from intra-domain deployments where it is handled as a controlled network service and does not comply with congestion control principles. It was given a reserved amount of bandwidth and admitted to the network so that congestion never occurs. Therefore, the congestion control issue should be given specific attention when evolving to an inter-domain peering deployment.

多くの場合、マルチキャストによるコンテンツ配送は、管理されたネットワークサービスとして扱われ輻輳制御の原則に従わない、ドメイン内での展開から発展してきました。 そこでは、輻輳が決して起こらないように、予約された量の帯域幅が与えられ、ネットワークへの流入が許可されていました。 したがって、ドメイン間ピアリングでの展開へと発展させる際には、輻輳制御の問題に特別な注意を払うべきです。

In the case where end-to-end IP multicast traffic passes across the network of two ADs (and their subsidiaries/customers), both ADs must agree on a consistent traffic-management policy. If, for example, AD-1 sources non-congestion-aware IP multicast traffic and AD-2 carries it as best-effort traffic across links shared with other Internet traffic (subject to congestion), this will not work: under congestion, some amount of that traffic will be dropped, often rendering the remaining packets as undecodable garbage clogging up the network in AD-2; because this traffic is not congestion aware, the loss does not reduce this rate. Competing traffic will not get their fair share under congestion, and EUs will be frustrated by the extremely bad quality of both their IP multicast traffic and other (e.g., TCP) traffic. Note that this is not an IP multicast technology issue but is solely a transport-layer / application-layer issue: the problem would just as likely happen if AD-1 were to send non-rate-adaptive unicast traffic -- for example, legacy IPTV video-on-demand traffic, which is typically also non-congestion aware. Note that because rate adaptation in IP unicast video is commonplace today due to the availability of ABR (Adaptive Bitrate) video, it is very unlikely that this will happen in reality with IP unicast.

エンドツーエンドのIPマルチキャストトラフィックが2つのAD（およびその子会社や顧客）のネットワークを通過する場合、両方のADは一貫したトラフィック管理ポリシーについて合意する必要があります。 たとえば、AD-1が輻輳を考慮しないIPマルチキャストトラフィックを送出し、AD-2がそれを他のインターネットトラフィックと共有するリンク（輻輳の影響を受ける）を越えてベストエフォートのトラフィックとして運ぶ場合、これはうまくいきません。 輻輳時にはそのトラフィックの一部が破棄され、多くの場合、残りのパケットはデコードできないゴミとなってAD-2のネットワークを詰まらせます。 このトラフィックは輻輳を考慮しないので、損失によってこのレートが下がることはありません。 競合するトラフィックは輻輳時に公平な割り当てを得られず、EUは、IPマルチキャストトラフィックとその他の（たとえばTCPの）トラフィックの両方の品質がきわめて悪いことに不満を抱くでしょう。 これはIPマルチキャスト技術の問題ではなく、もっぱらトランスポート層・アプリケーション層の問題であることに注意してください。 AD-1がレート適応型でないユニキャストトラフィック（たとえば、通常はやはり輻輳を考慮しない、レガシーなIPTVのビデオオンデマンドのトラフィック）を送信した場合にも、同じように問題が起こりえます。 ただし、ABR（アダプティブビットレート）ビデオが利用できるようになったことで、今日ではIPユニキャストのビデオでのレート適応は一般的であるため、IPユニキャストで実際にこれが起こる可能性は非常に低いことに注意してください。

While the rules for traffic management apply whether IP multicast is tunneled or not, the one feature that can make AMT tunnels more difficult is the unpredictability of bandwidth requirements across underlying links because of the way they can be used: with native IP multicast or GRE tunnels, the amount of bandwidth depends on the amount of content -- not the number of EUs -- and is therefore easier to plan for. AMT tunnels terminating in the EU/G, on the other hand, scale with the number of EUs. In the vicinity of the AMT relay, they can introduce a very large amount of replicated traffic, and it is not always feasible to provision enough bandwidth for all possible EUs to get the highest quality for all their content during peak utilization in such setups -- unless the AMT relays are very close to the EU edge. Therefore, it is also recommended that IP multicast rate adaptation be used, even inside controlled networks, when using AMT tunnels directly to the EU/G.

トラフィック管理の規則はIPマルチキャストがトンネリングされているかどうかにかかわらず適用されますが、AMTトンネルをより難しくしうる1つの特徴は、その使われ方のために、下位のリンクを越える帯域幅の要件が予測しにくいことです。 ネイティブIPマルチキャストやGREトンネルでは、帯域幅の量はEUの数ではなくコンテンツの量に依存するため、計画を立てやすくなります。 一方、EU/Gで終端するAMTトンネルは、EUの数に比例して増えます。 AMTリレーの近くでは、AMTトンネルによって非常に大量の複製トラフィックが発生する可能性があり、このような構成では、AMTリレーがEUのエッジに非常に近い場合を除き、ピーク利用時にすべてのEUがすべてのコンテンツを最高品質で得られるだけの十分な帯域幅をプロビジョニングすることは、必ずしも現実的ではありません。 したがって、EU/Gへ直接AMTトンネルを使用する場合は、管理されたネットワークの内部であっても、IPマルチキャストのレート適応を使用することも推奨されます。

Note that rate-adaptive IP multicast traffic in general does not mean that the sender is reducing the bitrate but rather that the EUs that experience congestion are joining to a lower-bitrate (S,G) stream of the content, similar to ABR streaming over TCP. Therefore, migration from a non-rate-adaptive bitrate to a rate-adaptive bitrate in IP multicast will also change the dynamic (S,G) join behavior in the network, resulting in potentially higher performance requirements for IP multicast protocols (IGMP/PIM), especially on the last hops where dynamic changes occur (including AMT gateways/relays): in non-rate-adaptive IP multicast, only "channel change" causes state change, but in rate-adaptive multicast, congestion also causes state change.

一般に、レート適応型のIPマルチキャストトラフィックとは、送信者がビットレートを下げることを意味するのではなく、輻輳を経験したEUが、TCP上のABRストリーミングと同様に、そのコンテンツのより低いビットレートの(S,G)ストリームに参加することを意味することに注意してください。 したがって、IPマルチキャストにおいてレート適応型でないビットレートからレート適応型のビットレートに移行すると、ネットワーク内の動的な(S,G)参加の振る舞いも変わり、その結果、IPマルチキャストプロトコル（IGMP/PIM）に対する性能要件が、特に動的な変化が発生する最後のホップ（AMTゲートウェイ・リレーを含む）で高くなる可能性があります。 レート適応型でないIPマルチキャストでは「チャネルの変更」だけが状態の変化を引き起こしますが、レート適応型のマルチキャストでは輻輳も状態の変化を引き起こします。

Even though not fully specified in this document, peerings that rely on GRE/AMT tunnels may be across one or more transit ADs instead of an exclusive (non-shared, L1/L2) path. Unless those transit ADs are explicitly contracted to provide other than "best effort" transit for the tunneled traffic, the tunneled IP multicast traffic must be rate adaptive in order to not violate BCP 41 across those transit ADs.

この文書では完全には規定しませんが、GREやAMTのトンネルに依存するピアリングは、専用の（共有されない、L1/L2の）パスではなく、1つ以上のトランジットADを越える場合があります。 それらのトランジットADが、トンネリングされたトラフィックに対して「ベストエフォート」以外のトランジットを提供することを明示的に契約していない限り、それらのトランジットADにおいてBCP 41に違反しないように、トンネリングされたIPマルチキャストトラフィックはレート適応型である必要があります。

4.2. Routing Aspects and Related Guidelines

4.2. ルーティングの側面と関連するガイドライン

The main objective for multicast delivery routing is to ensure that the EU receives the multicast stream from the "most optimal" source [INF_ATIS_10], which typically:

マルチキャスト配送のルーティングの主な目的は、EUが「最も最適な」ソース[INF_ATIS_10]からマルチキャストストリームを受信できるようにすることです。 このソースは通常、次のようなものです。

  • Maximizes the multicast portion of the transport and minimizes any unicast portion of the delivery, and
  • Minimizes the overall combined route distance of the network(s).
  • 転送のうちマルチキャストの部分を最大化し、配送のうちユニキャストの部分を最小化するもの、かつ
  • ネットワーク全体を合わせた経路の距離を最小化するもの。

This routing objective applies to both native multicast and AMT; the actual methodology of the solution will be different for each. Regardless, the routing solution is expected to:

このルーティングの目的は、ネイティブマルチキャストとAMTの両方に当てはまりますが、解決策の実際の方法はそれぞれで異なります。 いずれにせよ、ルーティングの解決策には次のことが期待されます。

  • Be scalable,
  • Avoid or minimize new protocol development or modifications, and
  • Be robust enough to achieve high reliability and to automatically adjust to changes and problems in the multicast infrastructure.
  • スケーラブルであること。
  • 新しいプロトコルの開発や変更を避けるか、最小限に抑えること。
  • 高い信頼性を実現し、マルチキャストインフラストラクチャーにおける変化や問題に自動的に適応できるほど堅牢であること。

For both native and AMT environments, having a source as close as possible to the EU network is most desirable; therefore, in some cases, an AD may prefer to have multiple sources near different peering points. However, that is entirely an implementation issue.

ネイティブとAMTのいずれの環境でも、ソースがEUのネットワークにできるだけ近いことが最も望ましいです。 そのため、場合によっては、ADは異なるピアリングポイントの近くに複数のソースを置くことを好むかもしれません。 ただし、それは完全に実装の問題です。

4.2.1. Native Multicast Routing Aspects

4.2.1. ネイティブマルチキャストのルーティングの側面

Native multicast simply requires that the administrative domains coordinate and advertise the correct source address(es) at their network interconnection peering points (i.e., BRs). An example of multicast delivery via a native multicast process across two administrative domains is as follows, assuming that the interconnecting peering points are also multicast enabled:

ネイティブマルチキャストでは、管理ドメインが、ネットワーク相互接続のピアリングポイント（つまりBR）において正しいソースアドレスを調整して広告するだけで済みます。 相互接続するピアリングポイントでもマルチキャストが有効になっていると仮定すると、2つの管理ドメインを越えたネイティブマルチキャストの処理によるマルチキャスト配送の例は次のとおりです。

  • Appropriate information is obtained by the EU client, who is a subscriber to AD-2 (see Use Case 3.1). This information is in the form of metadata, and it contains instructions directing the EU client to launch an appropriate application if necessary, as well as additional information for the application about the source location and the group (or stream) ID in the form of (S,G) data. The "S" portion provides the name or IP address of the source of the multicast stream. The metadata may also contain alternate delivery information, such as specifying the unicast address of the stream.

  • The client uses the join message with (S,G) to join the multicast stream [RFC4604]. To facilitate this process, the two ADs need to do the following:

    • Advertise the source ID(s) over the peering points.
    • Exchange such relevant peering point information as capacity and utilization.
    • Implement compatible multicast protocols to ensure proper multicast delivery across the peering points.
  • AD-2の加入者であるEUのクライアントが、適切な情報を取得します（ユースケース3.1を参照）。 この情報はメタデータの形式をとり、必要に応じて適切なアプリケーションを起動するようにEUのクライアントに指示する命令と、ソースの場所とグループ（またはストリーム）IDに関する(S,G)データの形式によるアプリケーション向けの追加情報を含みます。 「S」の部分は、マルチキャストストリームのソースの名前またはIPアドレスを示します。 メタデータには、ストリームのユニキャストアドレスの指定など、代替の配送情報も含まれる場合があります。

  • クライアントは、(S,G)を伴う参加メッセージを使用してマルチキャストストリームに参加します[RFC4604]。 この処理を円滑に進めるために、2つのADは次のことを行う必要があります。

    • ピアリングポイント上でソースIDを広告します。
    • 容量や利用率など、ピアリングポイントに関連する情報を交換します。
    • ピアリングポイントを越えた適切なマルチキャスト配送を確実にするために、互換性のあるマルチキャストプロトコルを実装します。

4.2.2. GRE Tunnel over Interconnecting Peering Point

4.2.2. 相互接続するピアリングポイント上のGREトンネル

If the interconnecting peering point is not multicast enabled and both ADs are multicast enabled, then a simple solution is to provision a GRE tunnel between the two ADs; see Use Case 3.2 (Section 3.2). The termination points of the tunnel will usually be a network engineering decision but generally will be between the BRs or even between the AD-2 BR and the AD-1 source (or source access router). The GRE tunnel would allow end-to-end native multicast or AMT multicast to traverse the interface. Coordination and advertisement of the source IP are still required.

相互接続するピアリングポイントでマルチキャストが有効になっておらず、両方のADでマルチキャストが有効になっている場合、簡単な解決策は、2つのAD間にGREトンネルをプロビジョニングすることです。 ユースケース3.2（セクション3.2）を参照してください。 トンネルの終端点は通常、ネットワークエンジニアリング上の判断になりますが、一般にはBR間、あるいはAD-2のBRとAD-1のソース（またはソースのアクセスルーター）の間になります。 GREトンネルにより、エンドツーエンドのネイティブマルチキャストやAMTマルチキャストがインターフェイスを通過できるようになります。 それでも、ソースIPの調整と広告は必要です。

The two ADs need to follow the same process as the process described in Section 4.2.1 to facilitate multicast delivery across the peering points.

ピアリングポイントを越えたマルチキャスト配送を円滑に進めるために、2つのADはセクション4.2.1で説明したのと同じ処理に従う必要があります。

4.2.3. Routing Aspects with AMT Tunnels

4.2.3. AMTトンネルにおけるルーティングの側面

Unlike native multicast (with or without GRE), an AMT multicast environment is more complex. It presents a two-layered problem in that there are two criteria that should be simultaneously met:

（GREの有無にかかわらず）ネイティブマルチキャストとは異なり、AMTマルチキャストの環境はより複雑です。 同時に満たすべき基準が2つあるという点で、2層の問題があります。

  • Find the closest AMT relay to the EU that also has multicast connectivity to the content source, and
  • Minimize the AMT unicast tunnel distance.
  • コンテンツソースへのマルチキャスト接続性も持つ、EUに最も近いAMTリレーを見つけること、かつ
  • AMTのユニキャストトンネルの距離を最小化すること。

There are essentially two components in the AMT specification:

AMTの仕様には、基本的に2つのコンポーネントがあります。

AMT relays:
These serve the purpose of tunneling UDP multicast traffic to the receivers (i.e., endpoints). The AMT relay will receive the traffic natively from the multicast media source and will replicate the stream on behalf of the downstream AMT gateways, encapsulating the multicast packets into unicast packets and sending them over the tunnel toward the AMT gateways. In addition, the AMT relay may collect various usage and activity statistics. This results in moving the replication point closer to the EU and cuts down on traffic across the network. Thus, the linear costs of adding unicast subscribers can be avoided. However, unicast replication is still required for each requesting endpoint within the unicast-only network.
AMT gateway:
The gateway will reside on an endpoint; this could be any type of IP host, such as a Personal Computer (PC), mobile phone, Set-Top Box (STB), or appliances. The AMT gateway receives join and leave requests from the application via an Application Programming Interface (API). In this manner, the gateway allows the endpoint to conduct itself as a true multicast endpoint. The AMT gateway will encapsulate AMT messages into UDP packets and send them through a tunnel (across the unicast-only infrastructure) to the AMT relay.
AMTリレー：
AMTリレーは、UDPマルチキャストトラフィックを受信者（つまりエンドポイント）へトンネリングする役割を果たします。 AMTリレーは、マルチキャストメディアソースからトラフィックをネイティブに受信し、下流のAMTゲートウェイに代わってストリームを複製します。 その際、マルチキャストパケットをユニキャストパケットにカプセル化し、トンネルを介してAMTゲートウェイに向けて送信します。 さらに、AMTリレーは、さまざまな使用状況や活動の統計情報を収集する場合があります。 これにより、複製点がEUに近づき、ネットワークを横断するトラフィックが削減されます。 したがって、ユニキャストの加入者を追加することによる線形のコストを回避できます。 ただし、ユニキャストのみのネットワーク内では、要求する各エンドポイントに対するユニキャストの複製が依然として必要です。
AMTゲートウェイ：
ゲートウェイはエンドポイント上に置かれます。 エンドポイントは、パーソナルコンピューター（PC）、携帯電話、セットトップボックス（STB）、家電機器など、どのような種類のIPホストでもかまいません。 AMTゲートウェイは、アプリケーションプログラミングインターフェイス（API）を介して、アプリケーションから参加・離脱のリクエストを受け取ります。 このようにして、ゲートウェイはエンドポイントが真のマルチキャストエンドポイントとして振る舞えるようにします。 AMTゲートウェイは、AMTメッセージをUDPパケットにカプセル化し、（ユニキャストのみのインフラストラクチャーを越えて）トンネルを通じてAMTリレーへ送信します。

The simplest AMT use case (Section 3.3) involves peering points that are not multicast enabled between two multicast-enabled ADs. An AMT tunnel is deployed between an AMT relay on the AD-1 side of the peering point and an AMT gateway on the AD-2 side of the peering point. One advantage of this arrangement is that the tunnel is established on an as-needed basis and need not be a provisioned element. The two ADs can coordinate and advertise special AMT relay anycast addresses with, and to, each other. Alternately, they may decide to simply provision relay addresses, though this would not be an optimal solution in terms of scalability.

最も単純なAMTのユースケース（セクション3.3）は、マルチキャストが有効な2つのADの間で、マルチキャストが有効になっていないピアリングポイントを扱います。 ピアリングポイントのAD-1側にあるAMTリレーと、ピアリングポイントのAD-2側にあるAMTゲートウェイの間に、AMTトンネルを展開します。 この構成の利点の1つは、トンネルが必要に応じて確立され、プロビジョニングされた要素である必要がないことです。 2つのADは、特別なAMTリレーのエニーキャストアドレスを互いに調整し、相手に広告できます。 あるいは、単にリレーアドレスをプロビジョニングすることにしてもかまいませんが、スケーラビリティーの点では最適な解決策ではありません。

Use Cases 3.4 and 3.5 describe AMT situations that are more complicated, as AD-2 is not multicast enabled in these two cases. For these cases, the EU device needs to be able to set up an AMT tunnel in the most optimal manner. There are many methods by which relay selection can be done, including the use of DNS-based queries and static lookup tables [RFC7450]. The choice of the method is implementation dependent and is up to the network operators. Comparison of various methods is out of scope for this document and is left for further study.

ユースケース3.4と3.5では、これら2つの場合にAD-2でマルチキャストが有効になっていないため、より複雑なAMTの状況を説明しています。 これらの場合、EUのデバイスは、最も最適な方法でAMTトンネルを設定できる必要があります。 リレーの選択を行う方法は、DNSベースのクエリーや静的なルックアップテーブル[RFC7450]の使用など、数多くあります。 方法の選択は実装依存であり、ネットワーク運用者に委ねられます。 さまざまな方法の比較は、この文書の範囲外であり、今後の検討課題とします。

An illustrative example of a relay selection based on DNS queries as part of an anycast IP address process is described here for Use Cases 3.4 and 3.5 (Sections 3.4 and 3.5). Using an anycast IP address for AMT relays allows all AMT gateways to find the "closest" AMT relay -- the nearest edge of the multicast topology of the source. Note that this is strictly illustrative; the choice of the method is up to the network operators. The basic process is as follows:

ここでは、ユースケース3.4と3.5（セクション3.4と3.5）について、エニーキャストIPアドレスの処理の一部としてDNSクエリーに基づいてリレーを選択する例を説明します。 AMTリレーにエニーキャストIPアドレスを使用すると、すべてのAMTゲートウェイが「最も近い」AMTリレー、すなわちソースのマルチキャストトポロジーの最も近いエッジを見つけられます。 これはあくまでも例示であり、方法の選択はネットワーク運用者に委ねられることに注意してください。 基本的な処理は次のとおりです。

  • Appropriate metadata is obtained by the EU client application. The metadata contains instructions directing the EU client to an ordered list of particular destinations to seek the requested stream and, for multicast, specifies the source location and the group (or stream) ID in the form of (S,G) data. The "S" portion provides the URI (name or IP address) of the source of the multicast stream, and the "G" identifies the particular stream originated by that source. The metadata may also contain alternate delivery information such as the address of the unicast form of the content to be used -- for example, if the multicast stream becomes unavailable.
  • Using the information from the metadata and, possibly, information provisioned directly in the EU client, a DNS query is initiated in order to connect the EU client / AMT gateway to an AMT relay.
  • Query results are obtained and may return an anycast address or a specific unicast address of a relay. Multiple relays will typically exist. The anycast address is a routable "pseudo-address" shared among the relays that can gain multicast access to the source.
  • If a specific IP address unique to a relay was not obtained, the AMT gateway then sends a message (e.g., the discovery message) to the anycast address such that the network is making the routing choice of a particular relay, e.g., the relay that is closest to the EU. Details are outside the scope of this document. See [RFC4786].
  • The contacted AMT relay then returns its specific unicast IP address (after which the anycast address is no longer required). Variations may exist as well.
  • The AMT gateway uses that unicast IP address to initiate a three-way handshake with the AMT relay.
  • The AMT gateway provides the (S,G) information to the AMT relay (embedded in AMT protocol messages).
  • The AMT relay receives the (S,G) information and uses it to join the appropriate multicast stream, if it has not already subscribed to that stream.
  • The AMT relay encapsulates the multicast stream into the tunnel between the relay and the gateway, providing the requested content to the EU.
  • EUのクライアントアプリケーションが、適切なメタデータを取得します。 メタデータには、要求されたストリームを探すための特定の宛先の順序付きリストへEUのクライアントを向かわせる命令が含まれ、マルチキャストの場合は、ソースの場所とグループ（またはストリーム）IDを(S,G)データの形式で指定します。 「S」の部分は、マルチキャストストリームのソースのURI（名前またはIPアドレス）を示し、「G」はそのソースが発信する特定のストリームを識別します。 メタデータには、使用するコンテンツのユニキャスト形式のアドレスなど、代替の配送情報（たとえば、マルチキャストストリームが利用できなくなった場合のためのもの）も含まれる場合があります。
  • メタデータからの情報と、場合によってはEUのクライアントに直接プロビジョニングされた情報を使用して、EUのクライアント・AMTゲートウェイをAMTリレーに接続するためのDNSクエリーが開始されます。
  • クエリーの結果が得られます。 結果として、エニーキャストアドレス、またはリレーの特定のユニキャストアドレスが返される場合があります。 通常、複数のリレーが存在します。 エニーキャストアドレスは、ソースへのマルチキャストアクセスを得られるリレーの間で共有される、ルーティング可能な「疑似アドレス」です。
  • リレーに固有の特定のIPアドレスが得られなかった場合、AMTゲートウェイはエニーキャストアドレスにメッセージ（たとえば、ディスカバリーメッセージ）を送信し、特定のリレー（たとえば、EUに最も近いリレー）のルーティング上の選択をネットワークに行わせます。 詳細はこの文書の範囲外です。 [RFC4786]を参照してください。
  • 連絡を受けたAMTリレーは、自身の特定のユニキャストIPアドレスを返します（その後はエニーキャストアドレスは不要になります）。 ほかのやり方もありえます。
  • AMTゲートウェイは、そのユニキャストIPアドレスを使用して、AMTリレーとの3ウェイハンドシェイクを開始します。
  • AMTゲートウェイは、（AMTプロトコルのメッセージに埋め込んで）(S,G)情報をAMTリレーに提供します。
  • AMTリレーは(S,G)情報を受け取り、そのストリームにまだ加入していない場合は、それを使用して適切なマルチキャストストリームに参加します。
  • AMTリレーは、マルチキャストストリームをリレーとゲートウェイの間のトンネルにカプセル化し、要求されたコンテンツをEUに提供します。

4.2.4. Public Peering Routing Aspects

4.2.4. パブリックピアリングのルーティングの側面

Figure 6 shows an example of a broadcast peering point.

図6に、ブロードキャストピアリングポイントの例を示します。

A broadcast peering point is an L2 subnet connecting three or more ADs. It is common in IXPs and usually consists of Ethernet switch(es) operated by the IXP connecting to BRs operated by the ADs.

ブロードキャストピアリングポイントとは、3つ以上のADを接続するL2サブネットです。 IXPでよく見られ、通常は、ADが運用するBRに接続する、IXPが運用するイーサネットスイッチで構成されます。

In an example setup domain, AD-2a peers with AD-1a and wants to receive IP multicast from it. Likewise, AD-2b peers with AD-1b and wants to receive IP multicast from it.

設定例のドメインでは、AD-2aはAD-1aとピアリングし、AD-1aからIPマルチキャストを受信したいと考えています。 同様に、AD-2bはAD-1bとピアリングし、AD-1bからIPマルチキャストを受信したいと考えています。

Assume that one or more IP multicast (S,G) traffic streams can be served by both AD-1a and AD-1b -- for example, because both AD-1a and AD-1b contact this content from the same content source.

1つ以上のIPマルチキャストの(S,G)トラフィックストリームを、AD-1aとAD-1bの両方が提供できると仮定します。 たとえば、AD-1aとAD-1bの両方が同じコンテンツソースからこのコンテンツを取得している場合です。

In this case, AD-2a and AD-2b can no longer control which upstream domain -- AD-1a or AD-1b -- will forward this (S,G) into the LAN. The AD-2a BR requests the (S,G) from the AD-1a BR, and the AD-2b BR requests the same (S,G) from the AD-1b BR. To avoid duplicate packets, an (S,G) can be forwarded by only one router onto the LAN; PIM-SM / PIM-SSM detects requests for duplicate transmissions and resolves them via the so-called "assert" protocol operation, which results in only one BR forwarding the traffic. Assume that this is the AD-1a BR. AD-2b will then receive unexpected multicast traffic from a provider with whom it does not have a mutual agreement for that traffic. Quality issues in EUs behind AD-2b caused by AD-1a will cause a lot of issues related to responsibility and troubleshooting.

この場合、AD-2aとAD-2bは、どちらの上流ドメイン（AD-1aまたはAD-1b）がこの(S,G)をLANに転送するかを制御できなくなります。 AD-2aのBRはAD-1aのBRに(S,G)をリクエストし、AD-2bのBRはAD-1bのBRに同じ(S,G)をリクエストします。 重複したパケットを避けるため、(S,G)をLANに転送できるルーターは1つだけです。 PIM-SM・PIM-SSMは重複した送信のリクエストを検出し、いわゆる「assert」プロトコル操作によってそれを解決します。 その結果、トラフィックを転送するBRは1つだけになります。 それがAD-1aのBRであると仮定します。 すると、AD-2bは、そのトラフィックについて相互の合意を結んでいないプロバイダーから、予期しないマルチキャストトラフィックを受信することになります。 AD-1aが原因でAD-2bの背後にいるEUで品質の問題が起こると、責任の所在やトラブルシューティングに関する多くの問題が生じます。

In light of these technical issues, we describe, via the following options, how IP multicast can be carried across broadcast peering point LANs:

こうした技術的な問題を踏まえ、ブロードキャストピアリングポイントのLANを越えてIPマルチキャストを運ぶ方法を、次の選択肢を通じて説明します。

  1. IP multicast is tunneled across the LAN. Any of the GRE/AMT tunneling solutions mentioned in this document are applicable. This is the one case where a GRE tunnel between the upstream BR (e.g., AD-1a) and downstream BR (e.g., AD-2a) is specifically recommended, as opposed to tunneling across uBRs (which are not the actual BRs).
  2. The LAN has only one upstream AD that is sourcing IP multicast, and native IP multicast is used. This is an efficient way to distribute the same IP multicast content to multiple downstream ADs. Misbehaving downstream BRs can still disrupt the delivery of IP multicast from the upstream BR to other downstream BRs; therefore, strict rules must be followed to prohibit such a case. The downstream BRs must ensure that they will always consider only the upstream BR as a source for multicast traffic: e.g., no BGP SAFI-2 peerings between the downstream ADs across the peering point LAN, so that the upstream BR is the only possible next hop reachable across this LAN. Also, routing policies can be configured to avoid falling back to using SAFI-1 (unicast) routes for IP multicast if unicast BGP peering is not limited in the same way.
  3. The LAN has multiple upstream ADs, but they are federated and agree on a consistent policy for IP multicast traffic across the LAN. One policy is that each possible source is only announced by one upstream BR. Another policy is that sources are redundantly announced (the problematic case mentioned in the example in Figure 6 above), but the upstream domains also provide mutual operational insight to help with troubleshooting (outside the scope of this document).
  1. IPマルチキャストをLANを越えてトンネリングします。 この文書で述べたGRE・AMTのトンネリングの解決策は、いずれも適用可能です。 これは、（実際のBRではない）uBRを越えてトンネリングするのではなく、上流のBR（たとえばAD-1a）と下流のBR（たとえばAD-2a）の間のGREトンネルが特に推奨される唯一のケースです。
  2. LANにはIPマルチキャストを送出する上流のADが1つだけあり、ネイティブIPマルチキャストを使用します。 これは、同じIPマルチキャストコンテンツを複数の下流のADに配信する効率的な方法です。 不正な振る舞いをする下流のBRは、上流のBRから他の下流のBRへのIPマルチキャストの配送を妨害できてしまいます。 したがって、そのような事態を防ぐために、厳格な規則に従う必要があります。 下流のBRは、常に上流のBRだけをマルチキャストトラフィックのソースとみなすようにする必要があります。 たとえば、ピアリングポイントのLANを越えた下流のAD間のBGP SAFI-2ピアリングを行わず、上流のBRがこのLANを越えて到達可能な唯一のネクストホップとなるようにします。 また、ユニキャストのBGPピアリングが同じように制限されていない場合に、IPマルチキャストのためにSAFI-1（ユニキャスト）の経路を使用するようにフォールバックしないよう、ルーティングポリシーを設定できます。
  3. LANには上流のADが複数ありますが、それらは連携しており、LANを越えるIPマルチキャストトラフィックについて一貫したポリシーに合意しています。 1つのポリシーは、ソースとなりうるものをそれぞれ1つの上流のBRだけが告知するというものです。 もう1つのポリシーは、ソースを冗長的に告知する（上記の図6の例で述べた問題のあるケース）ものの、上流のドメインがトラブルシューティングを助けるために運用上の知見を相互に提供する（この文書の範囲外）というものです。

4.3. Back-Office Functions - Provisioning and Logging Guidelines

4.3. バックオフィス機能 - プロビジョニングとロギングに関するガイドライン

"Back office" refers to the following:

「バックオフィス（back office）」とは、次のものを指します。

  • Servers and content-management systems that support the delivery of applications via multicast and interactions between ADs.
  • Functionality associated with logging, reporting, ordering, provisioning, maintenance, service assurance, settlement, etc.
  • マルチキャストによるアプリケーションの配送とAD間のやり取りをサポートする、サーバーやコンテンツ管理システム。
  • ロギング、報告、発注、プロビジョニング、保守、サービス保証、精算などに関連する機能。

4.3.1. Provisioning Guidelines

4.3.1. プロビジョニングに関するガイドライン

Resources for basic connectivity between ADs' providers need to be provisioned as follows:

ADのプロバイダー間の基本的な接続性のためのリソースは、次のようにプロビジョニングする必要があります。

  • Sufficient capacity must be provisioned to support multicast-based delivery across ADs.
  • Sufficient capacity must be provisioned for connectivity between all supporting back offices of the ADs as appropriate. This includes activating proper security treatment for these back-office connections (gateways, firewalls, etc.) as appropriate.
  • AD間のマルチキャストベースの配送をサポートするのに十分な容量をプロビジョニングする必要があります。
  • 必要に応じて、ADの支援を行うすべてのバックオフィス間の接続性のために十分な容量をプロビジョニングする必要があります。 これには、必要に応じて、これらのバックオフィスの接続（ゲートウェイ、ファイアウォールなど）に対して適切なセキュリティー対策を有効にすることが含まれます。

Provisioning aspects related to multicast-based inter-domain delivery are as follows.

マルチキャストベースのドメイン間配送に関連するプロビジョニングの側面は次のとおりです。

The ability to receive a requested application via multicast is triggered via receipt of the necessary metadata. Hence, this metadata must be provided to the EU regarding the multicast URL -- and unicast fallback if applicable. AD-2 must enable the delivery of this metadata to the EU and provision appropriate resources for this purpose.

要求されたアプリケーションをマルチキャストで受信できるようになるきっかけは、必要なメタデータの受信です。 したがって、マルチキャストのURL（および、該当する場合はユニキャストへのフォールバック）に関するこのメタデータをEUに提供する必要があります。 AD-2は、このメタデータのEUへの配送を可能にし、この目的のために適切なリソースをプロビジョニングする必要があります。

It is assumed that native multicast functionality is available across many ISP backbones, peering points, and access networks. If, however, native multicast is not an option (Use Cases 3.4 and 3.5), then:

ネイティブマルチキャストの機能は、多くのISPのバックボーン、ピアリングポイント、アクセスネットワークで利用可能であると想定します。 しかし、ネイティブマルチキャストという選択肢がない場合（ユースケース3.4と3.5）は、次のようになります。

  • The EU must have a multicast client to use AMT multicast obtained from either (1) the application source (per agreement with AD-1) or (2) AD-1 or AD-2 (if delegated by the application source).
  • If provided by AD-1 or AD-2, then the EU could be redirected to a client download site. (Note: This could be an application source site.) If provided by the application source, then this source would have to coordinate with AD-1 to ensure that the proper client is provided (assuming multiple possible clients).
  • Where AMT gateways support different application sets, all AD-2 AMT relays need to be provisioned with all source and group addresses for streams it is allowed to join.
  • DNS across each AD must be provisioned to enable a client gateway to locate the optimal AMT relay (i.e., longest multicast path and shortest unicast tunnel) with connectivity to the content's multicast source.
  • EUは、AMTマルチキャストを使用するためのマルチキャストクライアントを持っている必要があります。 このクライアントは、（1）（AD-1との合意に基づき）アプリケーションソース、または（2）（アプリケーションソースから委任された場合）AD-1かAD-2のいずれかから入手します。
  • AD-1またはAD-2が提供する場合は、EUをクライアントのダウンロードサイトにリダイレクトできます。 （注：これはアプリケーションソースのサイトでもかまいません。） アプリケーションソースが提供する場合、（複数のクライアントがありうると仮定して）適切なクライアントが提供されるように、このソースはAD-1と調整する必要があるでしょう。
  • AMTゲートウェイが異なるアプリケーションの組をサポートする場合、AD-2のすべてのAMTリレーには、参加が許可されているストリームのすべてのソースアドレスとグループアドレスをプロビジョニングする必要があります。
  • クライアントのゲートウェイが、コンテンツのマルチキャストソースへの接続性を持つ最適なAMTリレー（つまり、マルチキャストのパスが最も長く、ユニキャストのトンネルが最も短いもの）を見つけられるように、各ADでDNSをプロビジョニングする必要があります。

Provisioning aspects related to operations and customer care are as follows.

運用とカスタマーケアに関連するプロビジョニングの側面は次のとおりです。

It is assumed that each AD provider will provision operations and customer care access to their own systems.

各ADのプロバイダーは、自身のシステムへの運用とカスタマーケアのアクセスをプロビジョニングするものと想定します。

AD-1's operations and customer care functions must be able to see enough of what is happening in AD-2's network or in the service provided by AD-2 to verify their mutual goals and operations, e.g., to know how the EUs are being served. This can be done in two ways:

AD-1の運用とカスタマーケアの機能は、相互の目標と運用を検証するために（たとえば、EUがどのようにサービスを受けているかを知るために）、AD-2のネットワークやAD-2が提供するサービスで起きていることを十分に把握できる必要があります。 これには2つの方法があります。

  • Automated interfaces are built between AD-1 and AD-2 such that operations and customer care continue using their own systems. This requires coordination between the two ADs, with appropriate provisioning of necessary resources.
  • AD-1's operations and customer care personnel are provided direct access to AD-2's systems. In this scenario, additional provisioning in these systems will be needed to provide necessary access. The two ADs must agree on additional provisioning to support this option.
  • 運用とカスタマーケアが自身のシステムを使い続けられるように、AD-1とAD-2の間に自動化されたインターフェイスを構築します。 これには、必要なリソースを適切にプロビジョニングした上で、2つのAD間の調整が必要です。
  • AD-1の運用とカスタマーケアの担当者に、AD-2のシステムへの直接のアクセスを提供します。 このシナリオでは、必要なアクセスを提供するために、これらのシステムで追加のプロビジョニングが必要になります。 2つのADは、この選択肢をサポートするための追加のプロビジョニングについて合意する必要があります。

4.3.2. Inter-domain Authentication Guidelines

4.3.2. ドメイン間認証に関するガイドライン

All interactions between pairs of ADs can be discovered and/or associated with the account(s) utilized for delivered applications. Supporting guidelines are as follows:

ADのペア間のすべてのやり取りは、配送されるアプリケーションに使用されるアカウントから発見できるか、そのアカウントに関連付けることができるか、あるいはその両方が可能です。 支援のためのガイドラインは次のとおりです。

  • A unique identifier is recommended to designate each master account.
  • AD-2 is expected to set up "accounts" (a logical facility generally protected by credentials such as login passwords) for use by AD-1. Multiple accounts, and multiple types or partitions of accounts, can apply, e.g., customer accounts, security accounts.
  • 各マスターアカウントを指定するために、一意な識別子を使うことが推奨されます。
  • AD-2は、AD-1が使用するための「アカウント」（一般にログインパスワードなどのクレデンシャルによって保護される論理的な仕組み）を設定することが期待されます。 たとえば、顧客アカウントやセキュリティーアカウントなど、複数のアカウントや、複数の種類または区分のアカウントが該当する場合があります。

The reason to specifically mention the need for AD-1 to initiate interactions with AD-2 (and use some account for that), as opposed to the opposite, is based on the recommended workflow initiated by customers (see Section 4.4): the customer contacts the content source, which is part of AD-1. Consequently, if AD-1 sees the need to escalate the issue to AD-2, it will interact with AD-2 using the aforementioned guidelines.

逆ではなく、AD-1がAD-2とのやり取りを開始する（そしてそのために何らかのアカウントを使用する）必要性に特に言及する理由は、顧客が開始する推奨のワークフロー（セクション4.4を参照）に基づいています。 顧客は、AD-1の一部であるコンテンツソースに連絡します。 その結果、AD-1が問題をAD-2にエスカレーションする必要があると判断した場合、AD-1は前述のガイドラインを使用してAD-2とやり取りします。

4.3.3. Log-Management Guidelines

4.3.3. ログ管理に関するガイドライン

Successful delivery (in terms of user experience) of applications or content via multicast between pairs of interconnecting ADs can be improved through the ability to exchange appropriate logs for various workflows -- troubleshooting, accounting and billing, optimization of traffic and content transmission, optimization of content and application development, and so on.

相互接続するADのペア間でのマルチキャストによるアプリケーションやコンテンツの配送の成功度（ユーザー体験の観点から見たもの）は、トラブルシューティング、アカウンティングと課金、トラフィックとコンテンツ送信の最適化、コンテンツとアプリケーション開発の最適化など、さまざまなワークフローのために適切なログを交換できるようにすることで向上させることができます。

Specifically, AD-1 take over primary responsibility for customer experience on behalf of the content source, with support from AD-2 as needed. The application/content owner is the only participant who has, and needs, full insight into the application level and can map the customer application experience to the network traffic flows -- which, with the help of AD-2 or logs from AD-2, it can then analyze and interpret.

具体的には、AD-1は、必要に応じてAD-2の支援を受けながら、コンテンツソースに代わって顧客体験に対する主要な責任を引き受けます。 アプリケーション・コンテンツの所有者は、アプリケーションレベルについての完全な知見を持ち、かつそれを必要とする唯一の参加者であり、顧客のアプリケーション体験をネットワークのトラフィックフローに対応付けることができます。 そして、AD-2の助けやAD-2からのログを使って、それを分析し解釈できます。

The main difference between unicast delivery and multicast delivery is that the content source can infer a lot more about downstream network problems from a unicast stream than from a multicast stream: the multicast stream is not per EU, except after the last replication, which is in most cases not in AD-1. Logs from the application, including the receiver side at the EU, can provide insight but cannot help to fully isolate network problems because of the IP multicast per-application operational state built across AD-1 and AD-2 (aka the (S,G) state and any other operational-state features, such as Diffserv QoS).

ユニキャスト配送とマルチキャスト配送の主な違いは、コンテンツソースが、マルチキャストストリームよりもユニキャストストリームから、下流のネットワークの問題についてはるかに多くのことを推測できることです。 マルチキャストストリームは、最後の複製の後を除いてEUごとのものではなく、その最後の複製はほとんどの場合AD-1内にはありません。 EUの受信側を含むアプリケーションからのログは知見を提供できますが、AD-1とAD-2にまたがって構築されるアプリケーションごとのIPマルチキャストの運用状態（いわゆる(S,G)状態や、Diffserv QoSなどのその他の運用状態の機能）のために、ネットワークの問題を完全に切り分ける助けにはなりません。

See Section 7 for more discussion regarding the privacy considerations of the model described here.

ここで説明するモデルのプライバシーに関する考慮事項についての詳しい議論は、セクション7を参照してください。

Different types of logs are known to help support operations in AD-1 when provided by AD-2. This could be done as part of AD-1/AD-2 contracts. Note that except for implied multicast-specific elements, the options listed here are not unique or novel for IP multicast, but they are more important for services novel to the operators than for operationally well-established services (such as unicast). We therefore detail them as follows:

AD-2が提供するさまざまな種類のログは、AD-1における運用の支援に役立つことが知られています。 これは、AD-1とAD-2の契約の一部として行うことができます。 暗黙のマルチキャスト固有の要素を除き、ここに挙げる選択肢はIPマルチキャストに固有のものでも新しいものでもありませんが、運用面で十分に確立されたサービス（ユニキャストなど）よりも、運用者にとって新しいサービスにとってより重要であることに注意してください。 そのため、これらを次のように詳しく説明します。

  • Usage information logs at an aggregate level.
  • Usage failure instances at an aggregate level.
  • Grouped or sequenced application access: performance, behavior, and failure at an aggregate level to support potential application-provider-driven strategies. Examples of aggregate levels include grouped video clips, web pages, and software-download sets.
  • Security logs, aggregated or summarized according to agreement (with additional detail potentially provided during security events, by agreement).
  • Access logs (EU), when needed for troubleshooting.
  • Application logs ("What is the application doing?"), when needed for shared troubleshooting.
  • Syslogs (network management), when needed for shared troubleshooting.
  • 集約レベルの使用情報のログ。
  • 集約レベルの使用失敗の事例。
  • グループ化または順序付けされたアプリケーションアクセス：アプリケーションプロバイダー主導の戦略を支援するための、集約レベルの性能、振る舞い、失敗。 集約レベルの例としては、グループ化されたビデオクリップ、ウェブページ、ソフトウェアのダウンロードの組が挙げられます。
  • 合意に従って集約または要約されたセキュリティーログ（合意により、セキュリティーイベントの発生時に追加の詳細が提供される可能性もあります）。
  • トラブルシューティングに必要な場合の、アクセスログ（EU）。
  • 共同のトラブルシューティングに必要な場合の、アプリケーションログ（「アプリケーションは何をしているか？」）。
  • 共同のトラブルシューティングに必要な場合の、Syslog（ネットワーク管理）。

The two ADs may supply additional security logs to each other, as agreed upon in contract(s). Examples include the following:

2つのADは、契約で合意したとおりに、追加のセキュリティーログを互いに提供する場合があります。 例としては次のものがあります。

  • Information related to general security-relevant activity, which may be of use from a protection or response perspective: types and counts of attacks detected, related source information, related target information, etc.
  • Aggregated or summarized logs according to agreement (with additional detail potentially provided during security events, by agreement).
  • 保護や対応の観点から役立つ可能性のある、一般的なセキュリティー関連の活動に関する情報：検出された攻撃の種類と数、関連する送信元の情報、関連する標的の情報など。
  • 合意に従って集約または要約されたログ（合意により、セキュリティーイベントの発生時に追加の詳細が提供される可能性もあります）。

4.4. Operations - Service Performance and Monitoring Guidelines

4.4. 運用 - サービスの性能と監視に関するガイドライン

"Service performance" refers to monitoring metrics related to multicast delivery via probes. The focus is on the service provided by AD-2 to AD-1 on behalf of all multicast application sources (metrics may be specified for SLA use or otherwise). Associated guidelines are as follows:

「サービスの性能（service performance）」とは、プローブによるマルチキャスト配送に関連するメトリックの監視を指します。 焦点となるのは、すべてのマルチキャストアプリケーションソースに代わってAD-2がAD-1に提供するサービスです（メトリックは、SLAでの使用などのために規定される場合があります）。 関連するガイドラインは次のとおりです。

  • Both ADs are expected to monitor, collect, and analyze service performance metrics for multicast applications. AD-2 provides relevant performance information to AD-1; this enables AD-1 to create an end-to-end performance view on behalf of the multicast application source.
  • Both ADs are expected to agree on the types of probes to be used to monitor multicast delivery performance. For example, AD-2 may permit AD-1's probes to be utilized in the AD-2 multicast service footprint. Alternately, AD-2 may deploy its own probes and relay performance information back to AD-1.
  • 両方のADは、マルチキャストアプリケーションのサービス性能のメトリックを監視、収集、分析することが期待されます。 AD-2は関連する性能情報をAD-1に提供します。 これにより、AD-1はマルチキャストアプリケーションソースに代わって、エンドツーエンドの性能の全体像を作成できます。
  • 両方のADは、マルチキャスト配送の性能を監視するために使用するプローブの種類について合意することが期待されます。 たとえば、AD-2は、AD-2のマルチキャストサービスの提供範囲内でAD-1のプローブを利用することを許可する場合があります。 あるいは、AD-2が自身のプローブを展開し、性能情報をAD-1に中継する場合もあります。

"Service monitoring" generally refers to a service (as a whole) provided on behalf of a particular multicast application source provider. It thus involves complaints from EUs when service problems occur. EUs direct their complaints to the source provider; the source provider in turn submits these complaints to AD-1. The responsibility for service delivery lies with AD-1; as such, AD-1 will need to determine where the service problem is occurring -- in its own network or in AD-2. It is expected that each AD will have tools to monitor multicast service status in its own network.

「サービスの監視（service monitoring）」とは、一般に、特定のマルチキャストアプリケーションソースのプロバイダーに代わって提供される（全体としての）サービスを指します。 したがって、サービスの問題が発生した際のEUからの苦情も対象になります。 EUはソースプロバイダーに苦情を申し立て、ソースプロバイダーはそれらの苦情をAD-1に伝えます。 サービス配送の責任はAD-1にあるため、AD-1は、サービスの問題が自身のネットワークとAD-2のどちらで発生しているのかを判断する必要があります。 各ADは、自身のネットワーク内のマルチキャストサービスの状態を監視するツールを持っていることが期待されます。

  • Both ADs will determine how best to deploy multicast service monitoring tools. Typically, each AD will deploy its own set of monitoring tools, in which case both ADs are expected to inform each other when multicast delivery problems are detected.
  • AD-2 may experience some problems in its network. For example, for the AMT use cases (Sections 3.3, 3.4, and 3.5), one or more AMT relays may be experiencing difficulties. AD-2 may be able to fix the problem by rerouting the multicast streams via alternate AMT relays. If the fix is not successful and multicast service delivery degrades, then AD-2 needs to report the issue to AD-1.

  • When a problem notification is received from a multicast application source, AD-1 determines whether the cause of the problem is within its own network or within AD-2. If the cause is within AD-2, then AD-1 supplies all necessary information to AD-2. Examples of supporting information include the following:

    • Kind(s) of problem(s).
    • Starting point and duration of problem(s).
    • Conditions in which one or more problems occur.
    • IP address blocks of affected users.
    • ISPs of affected users.
    • Type of access, e.g., mobile versus desktop.
    • Network locations of affected EUs.

  • Both ADs conduct some form of root-cause analysis for multicast service delivery problems. Examples of various factors for consideration include:

    • Verification that the service configuration matches the product features.
    • Correlation and consolidation of the various customer problems and resource troubles into a single root-service problem.
    • Prioritization of currently open service problems, giving consideration to problem impacts, SLAs, etc.
    • Conducting service tests, including tests performed once or a series of tests over a period of time.
    • Analysis of test results.
    • Analysis of relevant network fault or performance data.
    • Analysis of the problem information provided by the customer.
  • Once the cause of the problem has been determined and the problem has been fixed, both ADs need to work jointly to verify and validate the success of the fix.
  • 両方のADは、マルチキャストサービスの監視ツールを展開する最善の方法を決定します。 通常、各ADは自身の監視ツールの一式を展開します。 その場合、両方のADは、マルチキャスト配送の問題を検出したときに互いに通知することが期待されます。
  • AD-2は、自身のネットワークで何らかの問題を経験することがあります。 たとえば、AMTのユースケース（セクション3.3、3.4、3.5）では、1つ以上のAMTリレーで障害が起きている場合があります。 AD-2は、代替のAMTリレーを経由するようにマルチキャストストリームの経路を変更することで、問題を解決できる場合があります。 解決に成功せず、マルチキャストサービスの配送品質が低下した場合、AD-2はその問題をAD-1に報告する必要があります。

  • マルチキャストアプリケーションソースから問題の通知を受け取ると、AD-1は、問題の原因が自身のネットワーク内にあるのかAD-2内にあるのかを判断します。 原因がAD-2内にある場合、AD-1は必要なすべての情報をAD-2に提供します。 支援のための情報の例としては、次のものがあります。

    • 問題の種類。
    • 問題の開始時点と継続時間。
    • 1つ以上の問題が発生する条件。
    • 影響を受けたユーザーのIPアドレスブロック。
    • 影響を受けたユーザーのISP。
    • アクセスの種類（たとえば、モバイルかデスクトップか）。
    • 影響を受けたEUのネットワーク上の場所。

  • 両方のADは、マルチキャストサービスの配送の問題について、何らかの形で根本原因の分析を行います。 考慮すべきさまざまな要因の例には、次のものがあります。

    • サービスの設定が製品の機能と一致していることの検証。
    • 顧客のさまざまな問題とリソースの障害を相関させ、単一の根本的なサービスの問題に集約すること。
    • 問題の影響やSLAなどを考慮した、現在未解決のサービスの問題の優先度付け。
    • 1回だけ行うテストや、一定期間にわたる一連のテストを含む、サービステストの実施。
    • テスト結果の分析。
    • 関連するネットワークの障害データや性能データの分析。
    • 顧客から提供された問題の情報の分析。
  • 問題の原因が特定され、問題が解決されたら、両方のADは協力して、解決が成功したことを検証し確認する必要があります。

4.5. Client Reliability Models / Service Assurance Guidelines

4.5. クライアントの信頼性モデル・サービス保証に関するガイドライン

There are multiple options for instituting reliability architectures. Most are at the application level. Both ADs should work these options out per their contract or agreement and also with the multicast application source providers.

信頼性のアーキテクチャーを導入するための選択肢は複数あります。 そのほとんどはアプリケーションレベルのものです。 両方のADは、契約や合意に従って、またマルチキャストアプリケーションソースのプロバイダーとも協力して、これらの選択肢を検討すべきです。

Network reliability can also be enhanced by the two ADs if they provision alternate delivery mechanisms via unicast means.

2つのADがユニキャストによる代替の配送メカニズムをプロビジョニングすれば、ネットワークの信頼性を高めることもできます。

4.6. Application Accounting Guidelines

4.6. アプリケーションのアカウンティングに関するガイドライン

Application-level accounting needs to be handled differently in the application than in IP unicast, because the source side does not directly deliver packets to individual receivers. Instead, this needs to be signaled back by the receiver to the source.

ソース側は個々の受信者に直接パケットを配送しないため、アプリケーションレベルのアカウンティングは、IPユニキャストの場合とは異なる方法でアプリケーション内で扱う必要があります。 代わりに、受信者からソースに通知を返す必要があります。

For network transport diagnostics, AD-1 and AD-2 should have mechanisms in place to ensure proper accounting for the volume of bytes delivered through the peering point and, separately, the number of bytes delivered to EUs.

ネットワーク転送の診断のために、AD-1とAD-2は、ピアリングポイントを通じて配送されたバイト量と、それとは別にEUに配送されたバイト数を適切にアカウンティングするためのメカニズムを備えておくべきです。

5. Troubleshooting and Diagnostics

5. トラブルシューティングと診断

Any service provider supporting multicast delivery of content should be able to collect diagnostics as part of multicast troubleshooting practices and resolve network issues accordingly. Issues may become apparent or identifiable through either (1) network monitoring functions or (2) problems reported by customers, as described in Section 4.4.

コンテンツのマルチキャスト配送をサポートするサービスプロバイダーは、マルチキャストのトラブルシューティングの実践の一環として診断情報を収集し、それに応じてネットワークの問題を解決できるべきです。 問題は、セクション4.4で説明したように、（1）ネットワーク監視機能、または（2）顧客から報告された問題のいずれかによって、明らかになったり特定可能になったりします。

It is recommended that multicast diagnostics be performed, leveraging established operational practices such as those documented in [MDH-05]. However, given that inter-domain multicast creates a significant interdependence of proper networking functionality between providers, there exists a need for providers to be able to signal (or otherwise alert) each other if there are any issues noted by either one.

[MDH-05]に記載されているような確立された運用上の慣行を活用して、マルチキャストの診断を行うことが推奨されます。 ただし、ドメイン間マルチキャストではプロバイダー間で適切なネットワーキング機能が大きく相互依存することを考えると、いずれかのプロバイダーが何らかの問題に気づいた場合に、プロバイダーが互いに通知（あるいは何らかの方法で警告）できる必要があります。

For troubleshooting purposes, service providers may also wish to allow limited read-only administrative access to their routers to their AD peers. Access to active troubleshooting tools -- especially [Traceroute] and the tools discussed in [Mtrace-v2] -- is of specific interest.

トラブルシューティングの目的で、サービスプロバイダーは、ADのピアに対して自身のルーターへの限定的な読み取り専用の管理アクセスを許可したいと考える場合もあります。 能動的なトラブルシューティングツール（特に[Traceroute]や[Mtrace-v2]で議論されているツール）へのアクセスは特に関心を集めています。

Another option is to include this functionality in the IP multicast receiver application on the EU device and allow these diagnostics to be remotely used by support operations. Note, though, that AMT does not allow the passing of traceroute or mtrace requests; therefore, troubleshooting in the presence of AMT does not work as well end to end as it can with native (or even GRE-encapsulated) IP multicast, especially with regard to traceroute and mtrace. Instead, troubleshooting directly on the actual network devices is then more likely necessary.

別の選択肢は、この機能をEUのデバイス上のIPマルチキャスト受信アプリケーションに組み込み、サポート運用部門がこれらの診断を遠隔から使用できるようにすることです。 ただし、AMTはtracerouteやmtraceのリクエストを通過させないことに注意してください。 そのため、AMTが存在する場合のトラブルシューティングは、特にtracerouteとmtraceに関して、ネイティブ（あるいはGREでカプセル化された）IPマルチキャストの場合ほどエンドツーエンドではうまく機能しません。 代わりに、実際のネットワークデバイス上で直接トラブルシューティングを行う必要性が高くなります。

The specifics of notifications and alerts are beyond the scope of this document, but general guidelines are similar to those described in Section 4.4. Some general communications issues are as follows.

通知や警告の詳細はこの文書の範囲外ですが、一般的なガイドラインはセクション4.4で説明したものと同様です。 一般的なコミュニケーションの課題として、次のものがあります。

  • Appropriate communications channels will be established between the customer service and operations groups from both ADs to facilitate information-sharing related to diagnostic troubleshooting.
  • A default resolution period may be considered to resolve open issues. Alternately, mutually acceptable resolution periods could be established, depending on the severity of the identified trouble.
  • 診断のためのトラブルシューティングに関する情報共有を円滑にするため、両方のADのカスタマーサービスグループと運用グループの間に適切なコミュニケーションチャネルを確立します。
  • 未解決の問題を解決するために、デフォルトの解決期間を検討してもよいでしょう。 あるいは、特定された障害の深刻度に応じて、相互に受け入れ可能な解決期間を設定することもできます。

6. Security Considerations

6. セキュリティーに関する考慮事項

6.1. DoS Attacks (against State and Bandwidth)

6.1. DoS攻撃（状態と帯域幅に対するもの）

Reliable IP multicast operations require some basic protection against DoS (Denial of Service) attacks.

信頼性の高いIPマルチキャストの運用には、DoS（サービス拒否）攻撃に対する何らかの基本的な保護が必要です。

SSM IP multicast is self-protecting against attacks from illicit sources; such traffic will not be forwarded beyond the first-hop router, because that would require (S,G) membership reports from the receiver. Only valid traffic from sources will be forwarded, because RPF ("Reverse Path Forwarding") is part of the protocols. One can say that protection against spoofed source traffic performed in the style of [BCP38] is therefore built into PIM-SM / PIM-SSM.

SSMのIPマルチキャストは、不正な送信元からの攻撃に対して自己防衛的です。 そのようなトラフィックを転送するには受信者からの(S,G)メンバーシップレポートが必要になるため、最初のホップのルーターより先には転送されません。 RPF（「Reverse Path Forwarding」）がプロトコルの一部であるため、送信元からの正当なトラフィックだけが転送されます。 したがって、[BCP38]の方式で行われる、送信元を詐称したトラフィックに対する保護は、PIM-SM・PIM-SSMに組み込まれていると言えます。

Receivers can attack SSM IP multicast by originating such (S,G) membership reports. This can result in a DoS attack against state through the creation of a large number of (S,G) states that create high control-plane load or even inhibit the later creation of a valid (S,G). In conjunction with collaborating illicit sources, it can also result in the forwarding of traffic from illicit sources.

受信者は、そのような(S,G)メンバーシップレポートを発信することで、SSMのIPマルチキャストを攻撃できます。 これにより、多数の(S,G)状態を作成して、コントロールプレーンに高い負荷をかけたり、さらには後で正当な(S,G)を作成するのを妨げたりする、状態に対するDoS攻撃になる可能性があります。 不正な送信元と共謀すると、不正な送信元からのトラフィックが転送される結果になる可能性もあります。

Today, these types of attacks are usually mitigated by explicitly defining the set of permissible (S,G) on, for example, the last-hop routers in replicating IP multicast to EUs (e.g., via (S,G) access control lists applied to IGMP/MLD membership state creation). Each AD (say, "ADi") is expected to know what sources located in ADi are permitted to send and what their valid (S,G)s are. ADi can therefore also filter invalid (S,G)s for any "S" located inside ADi, but not sources located in another AD.

今日、この種の攻撃は通常、たとえばEUへIPマルチキャストを複製する最後のホップのルーター上で、許可される(S,G)の集合を明示的に定義することで（たとえば、IGMP・MLDのメンバーシップ状態の作成に適用する(S,G)アクセス制御リストによって）緩和されています。 各AD（たとえば「ADi」とします）は、ADi内にあるどのソースが送信を許可されているか、そしてその正当な(S,G)が何であるかを知っていることが期待されます。 したがって、ADiは、ADi内にある任意の「S」について無効な(S,G)をフィルタリングすることもできますが、別のADにあるソースについてはできません。

In the peering case, without further information, AD-2 is not aware of the set of valid (S,G) from AD-1, so this set needs to be communicated via operational procedures from AD-1 to AD-2 to provide protection against this type of DoS attack. Future work could signal this information in an automated way: BGP extensions, DNS resource records, or backend automation between AD-1 and AD-2. Backend automation is, in the short term, the most viable solution: unlike BGP extensions or DNS resource records, backend automation does not require router software extensions. Observation of traffic flowing via (S,G) state could also be used to automate the recognition of invalid (S,G) state created by receivers in the absence of explicit information from AD-1.

ピアリングの場合、それ以上の情報がなければ、AD-2はAD-1からの正当な(S,G)の集合を知りません。 そのため、この種のDoS攻撃に対する保護を提供するには、運用手順によってAD-1からAD-2にこの集合を伝える必要があります。 将来の作業により、BGPの拡張、DNSのリソースレコード、AD-1とAD-2の間のバックエンドの自動化といった方法で、この情報を自動的に伝えられるようになるかもしれません。 短期的には、バックエンドの自動化が最も現実的な解決策です。 BGPの拡張やDNSのリソースレコードとは異なり、バックエンドの自動化にはルーターのソフトウェアの拡張が必要ないためです。 AD-1からの明示的な情報がない場合に、受信者が作成した無効な(S,G)状態の認識を自動化するために、(S,G)状態を経由して流れるトラフィックの観測を使用することもできます。

The second type of DoS attack through (S,G) membership reports exists when the attacking receiver creates too much valid (S,G) state and the traffic carried by these (S,G)s congests bandwidth on links shared with other EUs. Consider the uplink to a last-hop router connecting to 100 EUs. If one EU joins to more multicast content than what fits into this link, then this would also impact the quality of the same content for the other 99 EUs. If traffic is not rate adaptive, the effects are even worse.

(S,G)メンバーシップレポートによる2つ目の種類のDoS攻撃は、攻撃する受信者が正当な(S,G)状態を過剰に作成し、これらの(S,G)が運ぶトラフィックが他のEUと共有するリンクの帯域幅を輻輳させる場合に発生します。 100のEUに接続する最後のホップのルーターへのアップリンクを考えてみましょう。 1つのEUがこのリンクに収まる以上のマルチキャストコンテンツに参加すると、他の99のEUに対する同じコンテンツの品質にも影響を与えることになります。 トラフィックがレート適応型でない場合、影響はさらに深刻になります。

The mitigation technique is the same as what is often employed for unicast: policing of the per-EU total amount of traffic. Unlike unicast, though, this cannot be done anywhere along the path (e.g., on an arbitrary bottleneck link); it has to happen at the point of last replication to the different EU. Simple solutions such as limiting the maximum number of joined (S,G)s per EU are readily available; solutions that take consumed bandwidth into account are available as vendor-specific features in routers. Note that this is primarily a non-peering issue in AD-2; it only becomes a peering issue if the peering link itself is not big enough to carry all possible content from AD-1 or, as in Use Case 3.4, when the AMT relay in AD-1 is that last replication point.

緩和の手法は、ユニキャストでよく採用されるものと同じで、EUごとのトラフィック総量のポリシングです。 ただし、ユニキャストとは異なり、これはパス上の任意の場所（たとえば、任意のボトルネックリンク上）で行うことはできず、個々のEUへの最後の複製点で行う必要があります。 EUごとに参加する(S,G)の最大数を制限するといった簡単な解決策はすぐに利用できます。 消費される帯域幅を考慮する解決策は、ルーターのベンダー固有の機能として利用できます。 これは主にAD-2内のピアリング以外の問題であることに注意してください。 ピアリングの問題になるのは、ピアリングリンク自体がAD-1からのすべての可能なコンテンツを運ぶのに十分な大きさでない場合か、ユースケース3.4のようにAD-1内のAMTリレーがその最後の複製点である場合だけです。

Limiting the amount of (S,G) state per EU is also a good first measure to prohibit too much undesired "empty" state from being built (state not carrying traffic), but it would not suffice in the case of DDoS attacks, e.g., viruses that impact a large number of EU devices.

EUごとの(S,G)状態の量を制限することは、望ましくない「空の」状態（トラフィックを運んでいない状態）が過剰に構築されるのを防ぐための最初の対策としても有効ですが、たとえば多数のEUのデバイスに影響を与えるウイルスのようなDDoS攻撃の場合には十分ではありません。

6.2. Content Security

6.2. コンテンツのセキュリティー

Content confidentiality, DRM (Digital Rights Management), authentication, and authorization are optional, based on the content delivered. For content that is "FTA" (Free To Air), the following considerations can be ignored, and content can be sent unencrypted and without EU authentication and authorization. Note, though, that the mechanisms described here may also be desirable for the application source to better track users even if the content itself would not require it.

コンテンツの機密性、DRM（デジタル著作権管理）、認証、認可は、配送されるコンテンツに応じて任意です。 「FTA」（Free To Air）のコンテンツについては、以下の考慮事項は無視でき、コンテンツは暗号化せずに、EUの認証や認可なしに送信できます。 ただし、ここで説明するメカニズムは、コンテンツ自体がそれを必要としない場合でも、アプリケーションソースがユーザーをよりよく追跡するために望ましい場合もあることに注意してください。

For inter-domain content, there are at least two models for content confidentiality, including (1) DRM authentication and authorization and (2) EU authentication and authorization:

ドメイン間のコンテンツについては、コンテンツの機密性に関して、（1）DRMによる認証と認可、（2）EUの認証と認可を含め、少なくとも2つのモデルがあります。

  • In the classical (IP)TV model, responsibility is per domain, and content is and can be passed on unencrypted. AD-1 delivers content to AD-2; AD-2 can further process the content, including features like ad insertion, and AD-2 is the sole point of contact regarding the contact for its EUs. In this document, we do not consider this case because it typically involves service aspects operated by AD-2 that are higher than the network layer; this document focuses on the network-layer AD-1/AD-2 peering case but not the application-layer peering case. Nevertheless, this model can be derived through additional work beyond what is described here.
  • The other model is the one in which content confidentiality, DRM, EU authentication, and EU authorization are end to end: responsibilities of the multicast application source provider and receiver application. This is the model assumed here. It is also the model used in Internet "Over the Top" (OTT) video delivery. Below, we discuss the threats incurred in this model due to the use of IP multicast in AD-1 or AD-2 and across the peering point.
  • 従来の（IP）TVモデルでは、責任はドメインごとにあり、コンテンツは暗号化されずに受け渡されており、またそうすることができます。 AD-1はAD-2にコンテンツを配送し、AD-2は広告の挿入などの機能を含めてコンテンツをさらに処理でき、AD-2はそのEUにとって唯一の連絡窓口となります。 このケースは通常、ネットワーク層より上位の、AD-2が運用するサービスの側面を含むため、この文書では考慮しません。 この文書は、ネットワーク層でのAD-1とAD-2のピアリングのケースに焦点を当てており、アプリケーション層のピアリングのケースは扱いません。 とはいえ、このモデルは、ここで説明する内容を超えた追加の作業によって導き出すことができます。
  • もう1つのモデルは、コンテンツの機密性、DRM、EUの認証、EUの認可がエンドツーエンドで行われる、すなわちマルチキャストアプリケーションソースのプロバイダーと受信アプリケーションの責任となるモデルです。 これがここで想定するモデルです。 また、これはインターネットの「Over the Top」（OTT）のビデオ配送で使用されているモデルでもあります。 以下では、AD-1またはAD-2内やピアリングポイントを越えてIPマルチキャストを使用することによって、このモデルで生じる脅威について議論します。

End-to-end encryption enables end-to-end EU authentication and authorization: the EU may be able to join (via IGMP/MLD) and receive the content, but it can only decrypt it when it receives the decryption key from the content source in AD-1. The key is the authorization. Keeping that key to itself and prohibiting playout of the decrypted content to non-copy-protected interfaces are typical DRM features in that receiver application or EU device operating system.

エンドツーエンドの暗号化により、EUのエンドツーエンドの認証と認可が可能になります。 EUは（IGMP・MLDによって）参加してコンテンツを受信できるかもしれませんが、AD-1内のコンテンツソースから復号鍵を受け取ったときにしかコンテンツを復号できません。 鍵が認可そのものです。 その鍵を外部に漏らさないことや、復号したコンテンツをコピー保護されていないインターフェイスへ再生出力するのを禁止することは、その受信アプリケーションやEUのデバイスのオペレーティングシステムにおける典型的なDRMの機能です。

End-to-end encryption is continuously attacked. Keys may be subject to brute-force attacks so that content can potentially be decrypted later, or keys are extracted from the EU application/device and shared with other unauthenticated receivers. One important class of content is where the value is in live consumption, such as sports or other event (e.g., concert) streaming. Extraction of keying material from compromised authenticated EUs and sharing with unauthenticated EUs are not sufficient. It is also necessary for those unauthenticated EUs to get a streaming copy of the content itself. In unicast streaming, they cannot get such a copy from the content source (because they cannot authenticate), and, because of asymmetric bandwidths, it is often impossible to get the content from compromised EUs to a large number of unauthenticated EUs. EUs behind classical "16 Mbps down, 1 Mbps up" ADSL links are the best example. With increasing broadband access speeds, unicast peer-to-peer copying of content becomes easier, but it likely will always be easily detectable by the ADs because of its traffic patterns and volume.

エンドツーエンドの暗号化は絶えず攻撃されています。 鍵が総当たり攻撃を受けて、コンテンツが後で復号される可能性があったり、鍵がEUのアプリケーションやデバイスから抽出され、認証されていない他の受信者と共有されたりします。 コンテンツの重要な分類の1つは、スポーツやその他のイベント（たとえばコンサート）のストリーミングのように、ライブで消費することに価値があるものです。 侵害された認証済みのEUから鍵素材を抽出し、認証されていないEUと共有するだけでは十分ではありません。 認証されていないEUは、コンテンツ自体のストリーミングのコピーも入手する必要があります。 ユニキャストのストリーミングでは、認証されていないEUは（認証できないため）コンテンツソースからそのようなコピーを入手できず、また非対称な帯域幅のために、侵害されたEUから多数の認証されていないEUへコンテンツを届けることは多くの場合不可能です。 従来の「下り16Mbps、上り1Mbps」のADSLリンクの背後にいるEUが、その最たる例です。 ブロードバンドアクセスの速度が向上するにつれて、ユニキャストによるコンテンツのピアツーピアのコピーは容易になりますが、そのトラフィックのパターンと量から、ADは常に容易に検出できるでしょう。

When IP multicast is being used without additional security, AD-2 is not aware of which EU is authenticated for which content. Any unauthenticated EU in AD-2 could therefore get a copy of the encrypted content without triggering suspicion on the part of AD-2 or AD-1 and then either (1) live-decode it, in the presence of the compromised authenticated EU and key-sharing or (2) decrypt it later, in the presence of federated brute-force key-cracking.

追加のセキュリティーなしにIPマルチキャストを使用している場合、AD-2は、どのEUがどのコンテンツについて認証されているかを知りません。 したがって、AD-2内の認証されていないEUは、AD-2やAD-1に疑われることなく暗号化されたコンテンツのコピーを入手でき、その後、（1）侵害された認証済みのEUと鍵の共有がある場合はライブでデコードするか、（2）連携した総当たりによる鍵の解読がある場合は後で復号することができます。

To mitigate this issue, the last replication point that is creating (S,G) copies to EUs would need to permit those copies only after authentication of the EUs. This would establish the same authenticated "EU only" copy that is used in unicast.

この問題を緩和するには、EUへの(S,G)のコピーを作成する最後の複製点が、EUの認証後にのみそれらのコピーを許可する必要があるでしょう。 これにより、ユニキャストで使われるのと同じ、認証された「EU専用」のコピーが確立されます。

Schemes for per-EU IP multicast authentication/authorization (and, as a result, non-delivery or copying of per-content IP multicast traffic) have been built in the past and are deployed in service providers for intra-domain IPTV services, but no standards exist for this. For example, there is no standardized RADIUS attribute for authenticating the IGMP/MLD filter set, but such implementations exist. The authors of this document are specifically also not aware of schemes where the same authentication credentials used to get the encryption key from the content source could also be used to authenticate and authorize the network-layer IP multicast replication for the content. Such schemes are technically not difficult to build and would avoid creating and maintaining a separate network traffic-forwarding authentication/authorization scheme decoupled from the end-to-end authentication/authorization system of the application.

EUごとのIPマルチキャストの認証・認可（および、その結果としての、コンテンツごとのIPマルチキャストトラフィックの非配送やコピー）の方式は、過去に構築され、ドメイン内のIPTVサービスのためにサービスプロバイダーに展開されていますが、これについての標準は存在しません。 たとえば、IGMP・MLDのフィルターセットを認証するための標準化されたRADIUS属性はありませんが、そのような実装は存在します。 この文書の著者らは、特に、コンテンツソースから暗号化鍵を入手するために使用するのと同じ認証クレデンシャルを、そのコンテンツのネットワーク層でのIPマルチキャストの複製の認証と認可にも使用できるような方式も知りません。 そのような方式を構築することは技術的には難しくなく、アプリケーションのエンドツーエンドの認証・認可システムから切り離された、ネットワークのトラフィック転送のための別個の認証・認可方式を作成し維持することを避けられるでしょう。

If delivery of such high-value content in conjunction with the peering described here is desired, the short-term recommendations are for sources to clearly isolate the source and group addresses used for different content bundles, communicate those (S,G) patterns from AD-1 to AD-2, and let AD-2 leverage existing per-EU authentication/authorization mechanisms in network devices to establish filters for (S,G) sets to each EU.

ここで説明したピアリングと組み合わせて、そのような価値の高いコンテンツを配送することが望まれる場合、短期的な推奨事項は、ソースが異なるコンテンツのバンドルに使用するソースアドレスとグループアドレスを明確に分離し、それらの(S,G)のパターンをAD-1からAD-2に伝え、AD-2にネットワークデバイスの既存のEUごとの認証・認可のメカニズムを活用させて、各EUに対する(S,G)の集合のフィルターを確立することです。

6.3. Peering Encryption

6.3. ピアリングの暗号化

Encryption at peering points for multicast delivery may be used per agreement between AD-1 and AD-2.

AD-1とAD-2の間の合意に従って、マルチキャスト配送のためにピアリングポイントで暗号化を使用する場合があります。

In the case of a private peering link, IP multicast does not have attack vectors on a peering link different from those of IP unicast, but the content owner may have defined strict constraints against unauthenticated copying of even the end-to-end encrypted content; in this case, AD-1 and AD-2 can agree on additional transport encryption across that peering link. In the case of a broadcast peering connection (e.g., IXP), transport encryption is again the easiest way to prohibit unauthenticated copies by other ADs on the same peering point.

プライベートピアリングリンクの場合、ピアリングリンク上でのIPマルチキャストの攻撃ベクトルはIPユニキャストのものと変わりませんが、コンテンツの所有者が、エンドツーエンドで暗号化されたコンテンツであっても認証されていないコピーに対する厳格な制約を定めている場合があります。 この場合、AD-1とAD-2は、そのピアリングリンクを越える追加のトランスポート暗号化について合意できます。 ブロードキャストのピアリング接続（たとえばIXP）の場合も、同じピアリングポイント上の他のADによる認証されていないコピーを防ぐには、やはりトランスポート暗号化が最も簡単な方法です。

If peering is across a tunnel that spans intermittent transit ADs (not discussed in detail in this document), then encryption of that tunnel traffic is recommended. It not only prohibits possible "leakage" of content but also protects the information regarding what content is being consumed in AD-2 (aggregated privacy protection).

ピアリングが、断続的なトランジットADにまたがるトンネルを越えて行われる場合（この文書では詳しく議論しません）、そのトンネルのトラフィックを暗号化することが推奨されます。 これは、コンテンツの「漏洩」の可能性を防ぐだけでなく、AD-2内でどのコンテンツが消費されているかに関する情報も保護します（集約されたプライバシー保護）。

See Section 6.4 for reasons why the peering point may also need to be encrypted for operational reasons.

運用上の理由からピアリングポイントの暗号化も必要になる場合がある理由については、セクション6.4を参照してください。

6.4. Operational Aspects

6.4. 運用上の側面

Section 4.3.3 discusses the exchange of log information, and Section 7 discusses the exchange of program information. All these operational pieces of data should by default be exchanged via authenticated and encrypted peer-to-peer communication protocols between AD-1 and AD-2 so that only the intended recipients in the peers' AD have access to it. Even exposure of the least sensitive information to third parties opens up attack vectors. Putting valid (S,G) information, for example, into DNS (as opposed to passing it via secured channels from AD-1 to AD-2) to allow easier filtering of invalid (S,G) information would also allow attackers to more easily identify valid (S,G) information and change their attack vector.

セクション4.3.3ではログ情報の交換について、セクション7では番組情報の交換について議論しています。 これらの運用上のデータはすべて、ピアのAD内の意図された受信者だけがアクセスできるように、デフォルトでは、AD-1とAD-2の間で認証され暗号化されたピアツーピアの通信プロトコルによって交換されるべきです。 最も機密性の低い情報であっても、第三者に露出すると攻撃ベクトルが生じます。 たとえば、無効な(S,G)情報のフィルタリングを容易にするために、（保護されたチャネルを介してAD-1からAD-2に渡すのではなく）正当な(S,G)情報をDNSに置くと、攻撃者も正当な(S,G)情報をより容易に特定し、攻撃ベクトルを変えられるようになってしまいます。

From the perspective of the ADs, security is most critical for log information, as it provides operational insight into the originating AD but also contains sensitive user data.

ADの観点からは、ログ情報のセキュリティーが最も重要です。 ログ情報は、発信元のADについての運用上の知見を提供するだけでなく、ユーザーの機密データも含むためです。

Sensitive user data exported from AD-2 to AD-1 as part of logs could be as much as the equivalent of 5-tuple unicast traffic flow accounting (but not more, e.g., no application-level information). As mentioned in Section 7, in unicast, AD-1 could capture these traffic statistics itself because this is all about traffic flows (originated by AD-1) to EU receivers in AD-2, and operationally passing it from AD-2 to AD-1 may be necessary when IP multicast is used because of the replication taking place in AD-2.

ログの一部としてAD-2からAD-1にエクスポートされるユーザーの機密データは、最大で、ユニキャストのトラフィックフローの5タプルのアカウンティングに相当する程度になる可能性があります（ただし、それ以上ではなく、たとえばアプリケーションレベルの情報は含みません）。 セクション7で述べるように、ユニキャストでは、これはすべて（AD-1が発信する）AD-2内のEUの受信者へのトラフィックフローに関するものなので、AD-1はこれらのトラフィック統計を自分で取得できます。 一方、IPマルチキャストを使用する場合は、AD-2内で複製が行われるため、運用上、それをAD-2からAD-1に渡す必要がある場合があります。

Nevertheless, passing such traffic statistics inside AD-1 from a capturing router to a backend system is likely less subject to third-party attacks than passing it "inter-domain" from AD-2 to AD-1, so more diligence needs to be applied to secure it.

とはいえ、そのようなトラフィック統計をAD-1の内部で取得元のルーターからバックエンドシステムに渡すほうが、AD-2からAD-1に「ドメイン間」で渡すよりも、第三者からの攻撃を受けにくいと考えられます。 そのため、後者を保護するには、より多くの注意を払う必要があります。

If any protocols used for the operational exchange of information are not easily secured at the transport layer or higher (because of the use of legacy products or protocols in the network), then AD-1 and AD-2 can also consider ensuring that all operational data exchanges go across the same peering point as the traffic and use network-layer encryption of the peering point (as discussed previously) to protect it.

運用上の情報交換に使用するプロトコルが、（ネットワーク内でレガシーな製品やプロトコルを使用しているために）トランスポート層以上で容易に保護できない場合、AD-1とAD-2は、すべての運用データの交換がトラフィックと同じピアリングポイントを通るようにし、（前述のとおり）ピアリングポイントのネットワーク層の暗号化を使用してそれを保護することも検討できます。

End-to-end authentication and authorization of EUs may involve some kind of token authentication and are done at the application layer, independently of the two ADs. If there are problems related to the failure of token authentication when EUs are supported by AD-2, then some means of validating proper operation of the token authentication process (e.g., validating that backend servers querying the multicast application source provider's token authentication server are communicating properly) should be considered. Implementation details are beyond the scope of this document.

EUのエンドツーエンドの認証と認可には、何らかのトークン認証が含まれる場合があり、これらは2つのADとは独立してアプリケーション層で行われます。 AD-2がEUをサポートしている際にトークン認証の失敗に関連する問題がある場合は、トークン認証の処理が適切に動作していることを検証する何らかの手段（たとえば、マルチキャストアプリケーションソースのプロバイダーのトークン認証サーバーに問い合わせるバックエンドサーバーが適切に通信していることの検証）を検討すべきです。 実装の詳細は、この文書の範囲外です。

In the event of a security breach, the two ADs are expected to have a mitigation plan for shutting down the peering point and directing multicast traffic over alternative peering points. It is also expected that appropriate information will be shared for the purpose of securing the identified breach.

セキュリティー侵害が発生した場合に備えて、2つのADは、ピアリングポイントを停止し、マルチキャストトラフィックを代替のピアリングポイントに振り向けるための緩和計画を持っていることが期待されます。 また、特定された侵害に対処する目的で、適切な情報が共有されることも期待されます。

7. Privacy Considerations

7. プライバシーに関する考慮事項

The described flow of information about content and EUs as described in this document aims to maintain privacy:

この文書で説明する、コンテンツとEUに関する情報の流れは、プライバシーを維持することを目指しています。

AD-1 is operating on behalf of (or owns) the content source and is therefore part of the content-consumption relationship with the EU. The privacy considerations between the EU and AD-1 are therefore generally the same (with one exception; see below) as they would be if no IP multicast was used, especially because end-to-end encryption can and should be used for any privacy-conscious content.

AD-1は、コンテンツソースに代わって運用している（またはコンテンツソースを所有している）ため、EUとのコンテンツ消費の関係の一部です。 したがって、EUとAD-1の間のプライバシーに関する考慮事項は、（1つの例外を除き。下記を参照）IPマルチキャストを使用しない場合と一般に同じです。 特に、プライバシーに配慮すべきコンテンツについては、エンドツーエンドの暗号化を使用でき、また使用すべきであるためです。

Information related to inter-domain multicast transport service is provided to AD-1 by the AD-2 operators. AD-2 is not required to gain additional insight into the user's behavior through this process other than what it would already have without service collaboration with AD-1, unless AD-1 and AD-2 agree on it and get approval from the EU.

ドメイン間マルチキャスト転送サービスに関連する情報は、AD-2の運用者がAD-1に提供します。 AD-1とAD-2がそれに合意してEUの承認を得ない限り、AD-2は、AD-1とのサービスの連携がなくてもすでに持っているであろう以上の、ユーザーの振る舞いに関する追加の知見を、このプロセスを通じて得る必要はありません。

For example, if it is deemed beneficial for the EU to get support directly from AD-2, then it would generally be necessary for AD-2 to be aware of the mapping between content and network (S,G) state so that AD-2 knows which (S,G) to troubleshoot when the EU complains about problems with specific content. The degree to which this dissemination is done by AD-1 explicitly to meet privacy expectations of EUs is typically easy to assess by AD-1. Two simple examples are as follows:

たとえば、EUがAD-2から直接サポートを受けることが有益であると判断された場合、EUが特定のコンテンツの問題について苦情を申し立てたときにAD-2がどの(S,G)のトラブルシューティングを行えばよいかを知るためには、一般に、AD-2がコンテンツとネットワークの(S,G)状態の対応関係を把握している必要があるでしょう。 EUのプライバシーへの期待に応えるためにAD-1がこの情報をどの程度明示的に配布するかは、通常、AD-1にとって評価が容易です。 簡単な例を2つ挙げます。

  • For a sports content bundle, every EU will happily click on the "I approve that the content program information is shared with your service provider" button, to ensure best service reliability, because service-conscious AD-2 would likely also try to ensure that high-value content, such as the (S,G) for the Super Bowl, would be the first to receive care in the case of network issues.
  • If the content in question was content for which the EU expected more privacy, the EU should prefer a content bundle that included this content in a large variety of other content, have all content end-to-end encrypted, and not share programming information with AD-2, to maximize privacy. Nevertheless, the privacy of the EU against AD-2 observing traffic would still be lower than in the equivalent setup using unicast, because in unicast, AD-2 could not correlate which EUs are watching the same content and use that to deduce the content. Note that even the setup in Section 3.4, where AD-2 is not involved in IP multicast at all, does not provide privacy against this level of analysis by AD-2, because there is no transport-layer encryption in AMT; therefore, AD-2 can correlate by on-path traffic analysis who is consuming the same content from an AMT relay from both the (S,G) join messages in AMT and the identical content segments (that were replicated at the AMT relay).
  • スポーツのコンテンツのバンドルの場合、最高のサービス信頼性を確保するために、すべてのEUが喜んで「コンテンツの番組情報をあなたのサービスプロバイダーと共有することを承認します」ボタンをクリックするでしょう。 サービスを重視するAD-2は、ネットワークの問題が発生した場合に、スーパーボウルの(S,G)のような価値の高いコンテンツが真っ先に対処されるようにもしようとするはずだからです。
  • 対象のコンテンツが、EUがより高いプライバシーを期待するコンテンツであった場合、EUは、プライバシーを最大化するために、このコンテンツを他の多種多様なコンテンツの中に含むコンテンツのバンドルを選び、すべてのコンテンツをエンドツーエンドで暗号化し、番組情報をAD-2と共有しないことを選ぶべきです。 それでも、トラフィックを観測するAD-2に対するEUのプライバシーは、ユニキャストを使用する同等の構成よりも低くなります。 ユニキャストでは、AD-2は、どのEUが同じコンテンツを視聴しているかを相関させ、それを使ってコンテンツを推測することができないためです。 AD-2がIPマルチキャストにまったく関与しないセクション3.4の構成であっても、AD-2によるこのレベルの分析に対するプライバシーは提供されないことに注意してください。 AMTにはトランスポート層の暗号化がないため、AD-2は、AMTにおける(S,G)の参加メッセージと、（AMTリレーで複製された）同一のコンテンツのセグメントの両方から、経路上のトラフィック分析によって、誰がAMTリレーから同じコンテンツを消費しているかを相関させることができます。

In summary, because only content to be consumed by multiple EUs is carried via IP multicast here and all of that content can be end-to-end encrypted, the only privacy consideration specific to IP multicast is for AD-2 to know or reconstruct what content an EU is consuming. For content for which this is undesirable, some form of protections as explained above are possible, but ideally, the model described in Section 3.4 could be used in conjunction with future work, e.g., adding Datagram Transport Layer Security (DTLS) encryption [RFC6347] between the AMT relay and the EU.

まとめると、ここでIPマルチキャストによって運ばれるのは複数のEUが消費するコンテンツだけであり、そのコンテンツはすべてエンドツーエンドで暗号化できるため、IPマルチキャストに固有のプライバシーに関する考慮事項は、AD-2が、EUがどのコンテンツを消費しているかを知ったり再構成したりできることだけです。 これが望ましくないコンテンツについては、上で説明したような何らかの形の保護が可能ですが、理想的には、セクション3.4で説明したモデルを、将来の作業（たとえば、AMTリレーとEUの間にデータグラムトランスポート層セキュリティー（DTLS）による暗号化[RFC6347]を追加すること）と組み合わせて使用できるでしょう。

Note that IP multicast by nature would permit the EU's privacy against the content source operator because, unlike unicast, the content source does not natively know which EU is consuming which content: in all cases where AD-2 provides replication, only AD-2 knows this directly. This document does not attempt to describe a model that maintains such a level of privacy against the content source; rather, we describe a model that only protects against exposure to intermediate parties -- in this case, AD-2.

IPマルチキャストは本質的に、コンテンツソースの運用者に対するEUのプライバシーを保てることに注意してください。 ユニキャストとは異なり、コンテンツソースは、どのEUがどのコンテンツを消費しているかを本来知らないためです。 AD-2が複製を行うすべてのケースで、これを直接知っているのはAD-2だけです。 この文書は、コンテンツソースに対してそのようなレベルのプライバシーを維持するモデルを説明しようとはしていません。 むしろ、中間の当事者（この場合はAD-2）への露出に対してのみ保護するモデルを説明しています。
