RFC 472

Illinois' reply to Maxwell's Request for Graphics Information, NIC Document 14925

RFC 472

Maxwellのグラフィックス情報の要請に対するIllinoisからの回答（NIC文書14925）

Abstract

概要

This is a reply to Craig Maxwell's (UCLA-NMC) "Request for graphics information" of 3/7/73. Further details can be obtained by contacting me directly.

これは、Craig Maxwell（UCLA-NMC）の1973年3月7日付けの「Request for graphics information」に対する回答です。詳細については、私に直接お問い合わせください。

To date, our work in graphics has been primarily centered about support for several applications groups. To make the generation of beam-oriented graphics as painless as possible for these groups, our policy for supporting this type of graphics has been to emulate as closely as possible the CALCOMP plotter support package on the host machine, but with NGP0 output. (Presently, before the resulting NGP can be sent to some of our peripherals, e.g., Gould 4800, it must be converted to device specifics. With the advent of ANTS MARK II and a PDP-11/45, all conversions will be handled locally, so all graphics flowing into our system will be NGP). We find this approach very labor-saving, even at the present slightly kludgey level.

これまでのところ、私たちのグラフィックスの作業は、主にいくつかのアプリケーショングループの支援を中心としてきました。これらのグループにとってビーム指向のグラフィックスの生成をできるだけ楽にするため、この種のグラフィックスを支援する方針として、ホストマシン上のCALCOMPプロッター支援パッケージを、出力をNGP0にしたうえでできるだけ忠実にエミュレートすることにしてきました。（現在は、生成されたNGPを一部の周辺機器、たとえばGould 4800に送る前に、デバイス固有の形式に変換する必要があります。ANTS MARK IIとPDP-11/45が導入されれば、すべての変換はローカルで処理されるようになり、私たちのシステムに流入するグラフィックスはすべてNGPになります。）現在のやや場当たり的な水準であっても、この方法は非常に手間を省けるものだと感じています。

We also have some grey-scale work taking place on our GOULD and IMLAC. One group is processing satellite pictures on Illiac and will soon need grey-scale output, another is producing natural-resource maps, and a third is generating holograms. No standardization plans have been made for grey scale work, but if an acceptable standard is established, we will most likely use it.

また、GOULDとIMLACでグレースケールの作業も行っています。あるグループはIlliacで衛星写真を処理しており、まもなくグレースケール出力が必要になります。別のグループは天然資源の地図を作成しており、3つ目のグループはホログラムを生成しています。グレースケールの作業については標準化の計画はありませんが、受け入れられる標準が確立されれば、おそらくそれを使用するでしょう。

A small group, including myself, is currently planning an interactive graphics system. The system will use multiple hosts, possibly using a remote E&S machine for rotation, scaling, etc. We have a number of large hurdles that have to be jumped before we can do anything, though. Several of these are not graphics-specific, such as process-controlled FTP, inter-process coordination among hosts, and others. We had intended to let efficiency dictate the format of intermediate results shipped via the Net, with standardization being applied where it is helpful for minimizing effort. Since the system will be highly interactive and will also manipulate grey-scale data, we will need a higher level of graphics protocol to handle the user interface. A "proto-prototype" system is being used now to do some simple manipulations of meteorological data (e.g., contouring, 3-D plotting) with an IMLAC passively displaying the NGP0 pictures created. Soon, I hope to finish an IMLAC program that will handle some interaction with the mouse/keyset. I have decided to implement the following (outgoing) commands.

私を含む小さなグループが、現在、対話型のグラフィックスシステムを計画しています。このシステムは複数のホストを使用し、回転や拡大縮小などにはリモートのE&Sのマシンを使うかもしれません。ただし、何かができるようになる前に、越えなければならない大きなハードルがいくつもあります。そのうちのいくつかは、プロセス制御によるFTPや、ホスト間でのプロセス間の連携など、グラフィックスに固有のものではありません。ネットを介して送られる中間結果の形式は効率によって決め、労力を最小限に抑えるのに役立つところで標準化を適用するつもりでした。このシステムは高度に対話的であり、グレースケールのデータも扱うため、ユーザーインターフェイスを処理するには、より高いレベルのグラフィックスプロトコルが必要になります。現在、「試作品の前段階」のシステムを使って、気象データの簡単な操作（たとえば、等高線の描画や3次元のプロット）を行っており、作成されたNGP0の画像はIMLACで受動的に表示しています。近いうちに、マウスやキーセットによる対話の一部を処理するIMLACのプログラムを完成させたいと考えています。私は、次の（送出する）コマンドを実装することにしました。

MOVE
beam to mouse position
DRAW
from last to present beam position.
TEXT
at present beam position.
UNDO
the last command (to facilitate freehand drawing and backspacing in TEXT).
MOVE
ビームをマウスの位置に移動します。
DRAW
直前のビームの位置から現在のビームの位置まで描画します。
TEXT
現在のビームの位置にテキストを描きます。
UNDO
直前のコマンドを取り消します（フリーハンドでの描画や、TEXTでのバックスペースを容易にするため）。

Other commands may be implemented as needed to do what people want to do, at least until an adequate interaction standard comes along.

少なくとも適切な対話の標準が現れるまでは、人々が行いたいことを行えるよう、必要に応じてほかのコマンドを実装するかもしれません。

Note that there is implicit in the UNDO command the assumption that the other end of the line possesses a certain amount of memory and intelligence. Two possible philosophies for standardizing interaction are that (1) all "nodes" ("generators" or "users" of data) understand some set of commands and possess at least a certain amount of intelligence, and (2) a distinction is made between "displays" and "computers" (quotes because the line is fuzzy). I favor the first for its generality, but I suggest that the lowest level of interactive graphics might want to use the second for ease of implementation with unintelligent devices, e.g., COMPUTEK 400's. (I do not mean to imply in (1) that the actual "computer" would not have a larger vocabulary than the actual "display" --this is inevitable with higher level capabilities in the protocol).

UNDOコマンドには、回線の相手側がある程度の記憶と知能を備えているという前提が暗に含まれていることに注意してください。対話を標準化するための考え方としては、(1)すべての「ノード」（データの「生成者」または「利用者」）が何らかのコマンドの集合を理解し、少なくともある程度の知能を備えている、というものと、(2)「ディスプレイ」と「コンピューター」を区別する（その境界があいまいなのでかぎかっこを付けています）、というものの2つが考えられます。私は汎用性の点で1つ目のほうを好みますが、対話型グラフィックスの最も低いレベルでは、知能を持たないデバイス、たとえばCOMPUTEK 400での実装を容易にするために、2つ目を使いたくなるかもしれないと思います。（(1)で、実際の「コンピューター」が実際の「ディスプレイ」より大きな語彙を持たない、と言うつもりはありません。プロトコルにより高いレベルの機能があれば、それは避けられないことです。）

Since we have almost no local computing power for applications work, all our graphics computation is done remotely (our work has been primarily at UCSD (B6700), USC-ISI (TENEX), and UCLA-CCN (360)). Because we do our work at scattered sites and are basically economic of labor (pronounced "lazy"), we have a lot to gain by standards and will be glad to cooperate as much as possible with standardization efforts.

私たちには、アプリケーションの作業に使えるローカルの計算能力がほとんどないため、グラフィックスの計算はすべてリモートで行っています（私たちの作業は主に、UCSD（B6700）、USC-ISI（TENEX）、UCLA-CCN（360）で行ってきました）。私たちは散在するサイトで作業しており、基本的に労力を節約する（発音すると「怠け者」）ので、標準から得られるものは多く、標準化の取り組みにはできる限り喜んで協力します。

Steve Bunch

Steve Bunch
