RFC 932

Subnetwork addressing scheme

RFC 932

サブネットワークのアドレッシング方式

Status of This Memo

このメモのステータス

This RFC suggests a proposed protocol for the ARPA-Internet community, and requests discussion and suggestions for improvements. Distribution of this memo is unlimited.

このRFCは、ARPAインターネットコミュニティーに向けてプロトコルを提案し、議論と改善のための提案を求めるものです。このメモの配布は無制限です。

INTRODUCTION

はじめに

Several recent RFCs have discussed the need for a "subnet" structure within the internet addressing scheme, and have proposed strategies for "subnetwork" addressing and routing. In particular, Jeff Mogul in his RFC-917, "Internet Subnets", describes an addressing scheme in which a variable number of the leading bits of the host portion of the address are used to identify the subnet. The drawback to this scheme is that it is necessary to modify the host implementation in order to implement it. While the modification is a simple one, it is necessary to retrofit it into all implementations, including those which are already in the field. (See RFC-917 by Mogul for various alternative approaches to this problem, such as using Address Resolution Protocol.)

最近のいくつかのRFCでは、インターネットのアドレッシング方式の中に「サブネット」構造が必要であることが議論され、「サブネットワーク」のアドレッシングとルーティングの戦略が提案されています。特に、Jeff MogulはRFC-917「Internet Subnets」で、アドレスのホスト部の先頭の可変個のビットを使ってサブネットを識別するアドレッシング方式を説明しています。この方式の欠点は、これを実装するためにホストの実装を修正する必要があることです。修正は単純なものですが、すでに現場で使われているものも含めて、すべての実装に後から組み込む必要があります。（アドレス解決プロトコル（Address Resolution Protocol）を使う方法など、この問題に対するさまざまな別のアプローチについては、MogulによるRFC-917を参照してください。）

This RFC proposes an alternative addressing scheme for subnets which, in most cases, requires no modification to host software whatsoever. The drawbacks of this scheme are that the total number of subnets in any one network are limited, and that modification is required to all gateways.

このRFCは、ほとんどの場合にホストのソフトウェアにまったく修正を必要としない、サブネットのための別のアドレッシング方式を提案します。この方式の欠点は、1つのネットワーク内のサブネットの総数が制限されることと、すべてのゲートウェイに修正が必要になることです。

THE PROPOSAL

提案

In this scheme, the individual subnets of a network are numbered using Class C addresses. Since it is necessary with this scheme that a Class C address used to number a subnet be distinguishable from a Class C address used to number an isolated network, we will reserve for subnetworks the upper half of the Class C address space, in other words all those Class C addresses for which the high order bit is on. When a network is to be organized as a series of subnetworks, a block of these reserved Class C addresses will be assigned to that network, specifically a block of 256 addresses having the two first bytes identical. Thus, the various subnetworks of a network are distinguished by the third byte of the Internet address. (This addressing scheme implies the limitation that there can only be 256 subnetworks in a net. If more networks are required, two blocks will have to be allocated, and the total viewed as two separate networks.)

この方式では、ネットワークの個々のサブネットにクラスCアドレスを使って番号を付けます。この方式では、サブネットの番号付けに使うクラスCアドレスを、孤立したネットワークの番号付けに使うクラスCアドレスと区別できる必要があるため、クラスCアドレス空間の上半分、言い換えると最上位ビットが立っているすべてのクラスCアドレスを、サブネットワーク用に予約します。あるネットワークを一連のサブネットワークとして構成する場合は、予約されたこれらのクラスCアドレスのブロック、具体的には先頭の2バイトが同一である256個のアドレスのブロックを、そのネットワークに割り当てます。したがって、あるネットワークのさまざまなサブネットワークは、インターネットアドレスの3バイト目によって区別されます。（このアドレッシング方式には、1つのネットワークに256個までしかサブネットワークを置けないという制限があります。それより多くのネットワークが必要な場合は、2つのブロックを割り当て、全体を2つの別々のネットワークとみなす必要があります。）

The gateways and hosts attached to this subnetted network use these addresses as ordinary Class C addresses. Thus, no modification to any host software is required for hosts attached to a subnetwork.

このサブネット化されたネットワークに接続されたゲートウェイとホストは、これらのアドレスを通常のクラスCアドレスとして使用します。したがって、サブネットワークに接続されたホストでは、ホストのソフトウェアにまったく修正を必要としません。

For gateways not directly attached to the subnetted network, it is an unacceptable burden to separately store the routing information to each of the subnets. The goal of any subnet addressing scheme is to provide a strategy by which distant gateways can store routing information for the network as a whole. In this scheme, since the first two bytes of the address is the same for every subnet in the network, those first two bytes can be stored and manipulated as if they are a single Class B address by a distant gateway. These addresses, which can be used either as a Class B or Class C address as appropriate, have been informally called Class "B 1/2" addresses.

サブネット化されたネットワークに直接接続されていないゲートウェイにとって、各サブネットへのルーティング情報を個別に格納することは、受け入れがたい負担です。あらゆるサブネットのアドレッシング方式の目標は、遠くのゲートウェイがネットワーク全体についてのルーティング情報を格納できるような戦略を提供することです。この方式では、アドレスの先頭の2バイトはネットワーク内のすべてのサブネットで同じなので、遠くのゲートウェイは、その先頭の2バイトを1つのクラスBアドレスであるかのように格納して操作できます。これらのアドレスは、必要に応じてクラスBアドレスとしてもクラスCアドレスとしても使えるもので、非公式に「クラスB 1/2」アドレスと呼ばれています。

In more detail, a gateway would treat Class C addresses as follows under the scheme. First, test to see whether the high order bit of the address is on. If not, the address is an ordinary Class C address and should be treated as such.

より詳しく言うと、この方式の下では、ゲートウェイはクラスCアドレスを次のように扱います。まず、アドレスの最上位ビットが立っているかどうかを調べます。立っていなければ、そのアドレスは通常のクラスCアドレスであり、そのように扱うべきです。

If the bit is on, this Class C address identifies a subnet of a network. Test to see if this gateway is attached to that network. If so, treat the address as an ordinary Class C address.

そのビットが立っていれば、このクラスCアドレスはあるネットワークのサブネットを識別しています。このゲートウェイがそのネットワークに接続されているかどうかを調べます。接続されていれば、そのアドレスを通常のクラスCアドレスとして扱います。

If the gateway is not attached to the network containing that subnetwork, discard the third byte of the Class C address and treat the resulting two bytes as a Class B address. Note that there can be no conflict between this two-byte pattern and an ordinary Class B address, because the first bits of this address are not those of a valid Class B address, but rather those of a Class C address.

ゲートウェイが、そのサブネットワークを含むネットワークに接続されていなければ、クラスCアドレスの3バイト目を捨て、残りの2バイトをクラスBアドレスとして扱います。この2バイトのパターンと通常のクラスBアドレスとが衝突することはないことに注意してください。このアドレスの先頭のビットは、有効なクラスBアドレスのものではなく、クラスCアドレスのものだからです。

OPTIMIZATIONS

最適化

If a network grows to more than 256 subnetworks, it will be necessary to design two distinct blocks of special Class C addresses, and to view this aggregate as two separate networks. However, the gateways of these two networks can, by proper design, run a joint routing algorithm which maintains optimal routes between the two halves, even if they are connected together by a number of gateways.

ネットワークが256を超えるサブネットワークに成長した場合は、特別なクラスCアドレスの別個のブロックを2つ用意し、この集合体を2つの別々のネットワークとみなす必要があります。しかし、適切に設計すれば、これら2つのネットワークのゲートウェイは、たとえ多数のゲートウェイで相互に接続されていても、2つの半分の間の最適な経路を維持する共同のルーティングアルゴリズムを実行できます。

Indeed, in general it is possible for gateways that are not directly attached to a subnetworked network to be specially programmed to remember the individual Class C addresses, if doing so provides greatly improved network efficiency in some particular case.

実際、一般に、サブネットワーク化されたネットワークに直接接続されていないゲートウェイであっても、特定の場合にネットワークの効率が大きく改善されるのであれば、個々のクラスCアドレスを記憶するように特別にプログラムすることができます。

It was stated earlier that no modification to the host software is necessary to implement this scheme. There is one case in which a minor modification may prove helpful. Consider the case of a distant host, not immediately attached to this subnetworked network. That host, even though at a distance, will nonetheless maintain separate routing entries for each of the distinct subnetwork addresses about which it has any knowledge. For most hosts, storing this information for each subnet represents no problem, because most implementations do not try to remember routing information about every network address in the Internet, but only those addresses that are of current interest. If, however, for some reason the host has a table which attempts to remember routing information about every Internet address it has ever seen, than that host should be programmed to understand the gateway's algorithm for collapsing the addresses of distant subnets from three bytes to two. However, it is not a recommended implementation strategy for the host to maintain this degree of routing information, so under normal circumstances, the host need not be concerned with the C to B conversion.

先に、この方式を実装するためにホストのソフトウェアを修正する必要はないと述べました。ただし、ちょっとした修正が役立つかもしれない場合が1つあります。このサブネットワーク化されたネットワークに直接接続されていない、遠くのホストの場合を考えてみてください。そのホストは、遠くにあるにもかかわらず、知っている個々のサブネットワークアドレスごとに別々のルーティングエントリーを維持します。ほとんどのホストにとって、この情報をサブネットごとに格納することは問題になりません。ほとんどの実装は、インターネットのすべてのネットワークアドレスについてのルーティング情報を記憶しようとはせず、現在関心のあるアドレスについてのものだけを記憶するからです。しかし、何らかの理由で、そのホストがこれまでに見たすべてのインターネットアドレスについてのルーティング情報を記憶しようとするテーブルを持っている場合は、遠くのサブネットのアドレスを3バイトから2バイトにまとめるゲートウェイのアルゴリズムを理解するように、そのホストをプログラムすべきです。とはいえ、ホストがこの程度のルーティング情報を維持することは推奨される実装戦略ではないので、通常の状況では、ホストはCからBへの変換を気にする必要はありません。

DRAWBACK

欠点

The major drawback of this scheme is that any implementation storing large tables of addresses must be changed to know the "B 1/2" conversion rule. Most importantly, all gateways must be programmed to know this rule. Thus, adoption of this scheme will require a scheduled mandatory change by every gateway implementation. The difficulty of organizing this is unknown.

この方式の主な欠点は、アドレスの大きなテーブルを格納する実装はすべて、「B 1/2」の変換規則を知るように変更しなければならないことです。もっとも重要なのは、すべてのゲートウェイがこの規則を知るようにプログラムしなければならないことです。したがって、この方式を採用するには、すべてのゲートウェイの実装が計画的かつ強制的に変更を行う必要があります。これをとりまとめることがどれほど難しいかはわかりません。

OTHER VARIATIONS

その他のバリエーション

It is possible to imagine other variations on the patterns of collapsing addresses. For example, 256 Class B addresses could be gathered together and collapsed into one Class A address. However, since the first three bits of the resulting Class A address would be constrained, this would permit only 32 such subnetted networks to exist. A more interesting alternative would be to permit the collapse of Class C addresses into a single Class A address. It is not entirely obvious the best way of organizing the sub-fields of this address, but this combination would permit a few very large nets of subnets to be assembled within the Internet.

アドレスをまとめるパターンについては、ほかのバリエーションも考えられます。たとえば、256個のクラスBアドレスを集めて、1つのクラスAアドレスにまとめることもできます。しかし、その結果できるクラスAアドレスの先頭の3ビットは制約を受けるので、このようなサブネット化されたネットワークは32個しか存在できません。より興味深い別の方法は、クラスCアドレスを1つのクラスAアドレスにまとめられるようにすることです。このアドレスのサブフィールドをどう構成するのが最善かは必ずしも明らかではありませんが、この組み合わせによって、インターネット内に少数のごく大規模なサブネットのネットワークを構築できるようになります。

The most interesting variation of "B 1/2" addresses is to increase the number of bits used to identify the subnet by taking bits from the resulting Class B address. For example, if 10 bits were used to identify the subnet (providing 1024 subnets per network), then the gateway, when forming the equivalent address, would not only drop the third byte but also mask the last two bits of the B address. Since the first three bits of the address are constrained, this would leave 13 bits for the network number, or 8192 possible subnetworked networks. This number is not as large as would be desirable, so it is clear that selecting the size of the subnet field is an important compromise.

「B 1/2」アドレスのもっとも興味深いバリエーションは、結果として得られるクラスBアドレスからビットを借りて、サブネットの識別に使うビット数を増やすことです。たとえば、サブネットの識別に10ビットを使う（ネットワークあたり1024個のサブネットを提供する）場合、ゲートウェイは、等価なアドレスを作るときに、3バイト目を捨てるだけでなく、Bアドレスの最後の2ビットもマスクします。アドレスの先頭の3ビットは制約を受けるので、ネットワーク番号には13ビット、つまりサブネットワーク化されたネットワークとして8192個が残ることになります。この数は望ましいほど大きくはないので、サブネットフィールドのサイズの選択が重要な妥協点であることは明らかです。

Danny Cohen has suggested that this scheme should be fully generalized so that the boundaries between the network, subnetwork, and host field be arbitrarily movable. The problem in such a generalization is to determine how the gateway is to maintain the table or algorithm which permits the collapsing of the address to occur. This RFC proposes that, in the short run, only one single form of "B 1/2" addresses be implemented as an Internet subnet standard.

Danny Cohenは、ネットワーク、サブネットワーク、ホストのフィールドの境界を任意に移動できるよう、この方式を完全に一般化すべきだと提案しています。このような一般化における問題は、アドレスをまとめられるようにするためのテーブルやアルゴリズムを、ゲートウェイがどのように維持するかを決めることです。このRFCは、当面は「B 1/2」アドレスの単一の形式だけを、インターネットのサブネット標準として実装することを提案します。
