RFC 7410

A Property Types Registry for the Authentication-Results Header Field

RFC 7410

Authentication-Resultsヘッダーフィールドのためのプロパティータイプのレジストリー

Abstract

概要

This document updates RFC 7001 by creating a registry for property types in the Authentication-Results header field, used in email authentication work, rather than limiting participants to using the original, small set of fixed values.

この文書は、電子メール認証の作業で使われるAuthentication-Resultsヘッダーフィールドのプロパティータイプについて、参加者が元の小さな固定値の集合だけを使うように制限するのではなく、そのためのレジストリーを作成することで、RFC 7001を更新します。

1. Introduction

1. はじめに

[RFC7001] defines the email Authentication-Results header field that presents the results of an authentication effort in a machine-readable format. The header field creates a place to collect the output from authentication processes that are disjoint from later processes that might use the output, such as analysis, filtering, or sorting mechanisms.

[RFC7001]は、認証の試みの結果を機械可読な形式で示す、電子メールのAuthentication-Resultsヘッダーフィールドを定義しています。このヘッダーフィールドは、認証プロセスからの出力を集める場所となります。認証プロセスは、その出力を使う可能性のある後続のプロセス（分析、フィルタリング、ソートの仕組みなど）とは切り離されています。

The specification in that document enumerated a small set of types of properties that can be reported using this mechanism. There has emerged a desire to report types of properties about a message through this mechanism. Accordingly, this document updates the specification to allow for additional property types ("ptypes") beyond the original set and creates a registry where new ones can be listed and their defining documents referenced.

その文書の仕様では、この仕組みを使って報告できるプロパティーのタイプを小さな集合として列挙していました。その後、この仕組みを通じてメッセージに関するその他のタイプのプロパティーを報告したいという要望が出てきました。そこでこの文書は、元の集合を超えるプロパティータイプ（"ptype"）を追加できるように仕様を更新し、新しいプロパティータイプを列挙してその定義文書を参照できるレジストリーを作成します。

2. Updated "ptype" Definition

2. "ptype"の定義の更新

Advanced Backus Naur Form (ABNF) is defined in [RFC5234].

拡張バッカス・ナウア記法（ABNF）は[RFC5234]で定義されています。

The ABNF in Section 2.2 of [RFC7001] is updated as follows:

[RFC7001]のセクション2.2のABNFを次のように更新します。

    ptype = Keyword
          ; indicates whether the property being evaluated was
          ; a parameter to an [SMTP] command, was a value taken
          ; from a message header field, was some property of
          ; the message body, or was some other property evaluated by
          ; the receiving Message Transfer Agent (MTA)

    ptype = Keyword
          ; 評価対象のプロパティーが、[SMTP]コマンドのパラメーター
          ; だったのか、メッセージヘッダーフィールドから取った値
          ; だったのか、メッセージ本文の何らかのプロパティーだったのか、
          ; それとも受信側のメッセージ転送エージェント（MTA）が評価
          ; したその他のプロパティーだったのかを示す

The ABNF token "Keyword" is defined in Section 4.1.2 of [RFC5321].

ABNFのトークン"Keyword"は、[RFC5321]のセクション4.1.2で定義されています。

Legal values of "ptype" are as defined in the IANA "Email Authentication Property Types" registry (see Section 3). The initial values are as follows, matching those defined in [RFC7001]:

"ptype"の正当な値は、IANAの"Email Authentication Property Types"レジストリー（セクション3を参照）で定義されているとおりです。初期値は、[RFC7001]で定義されているものと同じく、次のとおりです。

body:
Indicates information that was extracted from the body of the message. This might be an arbitrary string of bytes, a hash of a string of bytes, a Uniform Resource Identifier, or some other content of interest.
header:
Indicates information that was extracted from the header of the message. This might be the value of a header field or some portion of a header field.
policy:
A local policy mechanism was applied that augments or overrides the result returned by the authentication mechanism. See Section 2.3 of [RFC7001].
smtp:
Indicates information that was extracted from an SMTP command that was used to relay the message.
body:
メッセージの本文から抽出された情報であることを示します。これは、任意のバイト列、バイト列のハッシュ、URI（Uniform Resource Identifier）、またはその他の関心のある内容である可能性があります。
header:
メッセージのヘッダーから抽出された情報であることを示します。これは、ヘッダーフィールドの値、またはヘッダーフィールドの一部である可能性があります。
policy:
認証メカニズムが返した結果を補強または上書きするローカルポリシーの仕組みが適用されたことを示します。[RFC7001]のセクション2.3を参照してください。
smtp:
メッセージの中継に使われたSMTPコマンドから抽出された情報であることを示します。

When a consumer of this header field encounters a "ptype" that it does not understand, it ignores the result reported with that "ptype".

このヘッダーフィールドの利用者は、理解できない"ptype"に遭遇した場合、その"ptype"で報告された結果を無視します。

IANAは、既存の"Email Authentication Parameters"レジストリーの中に、"Email Authentication Property Types"サブレジストリーを作成しました。このレジストリーへのエントリーは、[RFC5226]で説明されているExpert Reviewの規則に従います。レジストリーの各エントリーには、次の値が必要です。

  • The "ptype" token to be registered, which must fit within the ABNF described in Section 2.

  • 定義文書への参照（任意）。これは推奨されますが、必須ではありません。

4. Security Considerations

4. セキュリティーに関する考慮事項

It is unknown how legacy code, which expects one of a fixed set of "ptype" tokens, will handle new tokens as they begin to appear. There are typically two options: prevent delivery of the message, or ignore those portions of the field that use unknown "ptype" tokens and allow processing of the message to continue.

固定された"ptype"トークンの集合のいずれかを想定しているレガシーなコードが、新しいトークンが現れ始めたときにそれをどう扱うかはわかりません。典型的には2つの選択肢があります。メッセージの配送を阻止するか、未知の"ptype"トークンを使っているフィールドの部分を無視してメッセージの処理を続行させるかです。

The choice comes down to whether the consumer considers it a threat when there are unknown "ptypes" present. The semantics of the report are unknown; the report might be indicating the message is authentic, fraudulent, or that a test failed to complete. The report itself is not actionable because it cannot be understood, and only its presence is certain.

どちらを選ぶかは、未知の"ptype"が存在するときに、利用者がそれを脅威と見なすかどうかにかかっています。その報告の意味はわかりません。報告は、メッセージが本物であることを示しているかもしれませんし、不正であることや、テストが完了しなかったことを示しているかもしれません。報告そのものは理解できないので、それに基づいて行動することはできず、確かなのはそれが存在することだけです。

Generally, the advice in this situation is to ignore unknown "ptypes". It is anticipated that a new property type evaluated by earlier handling agents would also result in the filtering of messages by those agents until consumers can be updated to interpret them.

一般に、この状況での助言は、未知の"ptype"を無視することです。前段の処理エージェントが評価した新しいプロパティータイプによって、利用者がそれを解釈できるように更新されるまでの間、それらのエージェントによってメッセージがフィルタリングされることにもなると予想されます。
