RFC 9193

Sensor Measurement Lists (SenML) Fields for Indicating Data Value Content-Format

RFC 9193

データ値のContent-Formatを示すためのSensor Measurement Lists（SenML）フィールド

Abstract

概要

The Sensor Measurement Lists (SenML) media types support multiple types of values, from numbers to text strings and arbitrary binary Data Values. In order to facilitate processing of binary Data Values, this document specifies a pair of new SenML fields for indicating the content format of those binary Data Values, i.e., their Internet media type, including parameters as well as any content codings applied.

Sensor Measurement Lists（SenML）メディアタイプは、数値からテキスト文字列、任意のバイナリーデータ値まで、複数の種類の値をサポートしています。 バイナリーデータ値の処理を容易にするために、この文書では、それらのバイナリーデータ値のコンテンツフォーマット、すなわちパラメーターや適用されたコンテンツコーディングを含むインターネットメディアタイプを示すための、1組の新しいSenMLフィールドを規定します。

1. Introduction

1. はじめに

The Sensor Measurement Lists (SenML) media types [RFC8428] can be used to send various kinds of data. In the example given in Figure 1, a temperature value, an indication whether a lock is open, and a Data Value (with SenML field "vd") read from a Near Field Communication (NFC) reader is sent in a single SenML Pack. The example is given in SenML JSON representation, so the "vd" (Data Value) field is encoded as a base64url string (without padding), as per Section 5 of [RFC8428].

Sensor Measurement Lists（SenML）メディアタイプ[RFC8428]は、さまざまな種類のデータを送信するために使用できます。 Figure 1の例では、温度の値、錠が開いているかどうかの表示、そして近距離無線通信（NFC）リーダーから読み取ったデータ値（SenMLフィールド"vd"）が、1つのSenMLパックで送信されています。 この例はSenML JSON表現で示されているため、[RFC8428]のSection 5に従い、"vd"（データ値）フィールドは（パディングなしの）base64url文字列としてエンコードされています。

The receiver is expected to know how to interpret the data in the "vd" field based on the context, e.g., the name of the data source and out-of-band knowledge of the application. However, this context may not always be easily available to entities processing the SenML Pack, especially if the Pack is propagated over time and via multiple entities. To facilitate automatic interpretation, it is useful to be able to indicate an Internet media type and, optionally, content codings right in the SenML Record.

受信者は、データソースの名前やアプリケーションに関する帯域外の知識などのコンテキストに基づいて、"vd"フィールドのデータを解釈する方法を知っていることが期待されます。 しかし、SenMLパックを処理するエンティティーにとって、このコンテキストが常に容易に入手できるとは限りません。 パックが時間をかけて、複数のエンティティーを経由して伝搬される場合には特にそうです。 自動的な解釈を容易にするために、インターネットメディアタイプと、オプションでコンテンツコーディングを、SenMLレコードの中で直接示せると便利です。

The Constrained Application Protocol (CoAP) Content-Format (Section 12.3 of [RFC7252]) provides this information in the form of a single unsigned integer. For instance, [RFC8949] defines the Content-Format number 60 for Content-Type application/cbor. Enclosing this Content-Format number in the Record is illustrated in Figure 2. All registered CoAP Content-Format numbers are listed in the "CoAP Content-Formats" registry [IANA.core-parameters], as specified by Section 12.3 of [RFC7252]. Note that, at the time of writing, the structure of this registry only provides for zero or one content coding; nothing in the present document needs to change if the registry is extended to allow sequences of content codings.

Constrained Application Protocol（CoAP）のContent-Format（[RFC7252]のSection 12.3）は、この情報を1つの符号なし整数の形式で提供します。 たとえば、[RFC8949]は、Content-Type application/cborに対してContent-Format番号60を定義しています。 このContent-Format番号をレコードに含める例をFigure 2に示します。 登録されているすべてのCoAP Content-Format番号は、[RFC7252]のSection 12.3で規定されているとおり、"CoAP Content-Formats"レジストリー[IANA.core-parameters]に列挙されています。 なお、この文書の執筆時点では、このレジストリーの構造は0個または1個のコンテンツコーディングしか想定していません。 このレジストリーがコンテンツコーディングの並びを許すように拡張されても、この文書で変更が必要になる点はありません。

In this example SenML Record, the Data Value contains a string "foo" and a number 42 encoded in a Concise Binary Object Representation (CBOR) [RFC8949] array. Since the example above uses the JSON format of SenML, the Data Value containing the binary CBOR value is base64 encoded (Section 5 of [RFC4648]). The Data Value after base64 decoding is shown with CBOR diagnostic notation in Figure 3.

このSenMLレコードの例では、データ値に、Concise Binary Object Representation（CBOR）[RFC8949]の配列としてエンコードされた文字列"foo"と数値42が含まれています。 上の例ではSenMLのJSON形式を使用しているため、バイナリーのCBOR値を含むデータ値はbase64エンコード（[RFC4648]のSection 5）されています。 base64デコード後のデータ値を、CBOR診断表記でFigure 3に示します。

1.1. Evolution

1.1. 進化

As with SenML in general, there is no expectation that the creator of a SenML Pack knows (or has negotiated with) each consumer of that Pack, which may be very remote in space and particularly in time. This means that the SenML creator in general has no way to know whether the consumer knows:

SenML全般と同様に、SenMLパックの作成者が、そのパックの各消費者を知っている（あるいは各消費者とネゴシエーションしている）ことは想定されていません。 消費者は、空間的に、特に時間的に、非常に遠く離れているかもしれません。 つまり、SenMLの作成者には一般に、消費者が次のものを知っているかどうかを知る方法がありません。

  • each specific Media-Type-Name used,
  • each parameter and each parameter value used,
  • each content coding in use, and
  • each Content-Format number in use for a combination of these.
  • 使用されている個々のMedia-Type-Name
  • 使用されている個々のパラメーターとパラメーター値
  • 使用されている個々のコンテンツコーディング
  • これらの組み合わせに対して使用されている個々のContent-Format番号

What SenML, as well as the new fields defined here, guarantees is that a recipient implementation knows when it needs to be updated to understand these field values and the values controlled by them; registries are used to evolve these name spaces in a controlled way. SenML Packs can be processed by a consumer while not understanding all the information in them, and information can generally be preserved in this processing such that it is useful for further consumers.

SenML、およびここで定義する新しいフィールドが保証するのは、これらのフィールド値とそれによって制御される値を理解するために、いつ更新が必要になるかを受信者の実装が知っていることです。 これらの名前空間を制御された方法で進化させるために、レジストリーが使用されます。 消費者は、SenMLパックの中のすべての情報を理解していなくても、それを処理できます。 また、この処理の際には一般に情報を保持できるため、その情報はさらに後の消費者にとっても役に立ちます。

2. Terminology

2. 用語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

Media type:
A registered label for representations (byte strings) prepared for interchange [RFC1590] [RFC6838], identified by a Media-Type-Name.
Media-Type-Name:
A combination of a type-name and a subtype-name registered in [IANA.media-types], as per [RFC6838], conventionally identified by the two names separated by a slash.
Content-Type:
A Media-Type-Name, optionally associated with parameters (Section 5 of [RFC2045], separated from the Media-Type-Name and from each other by a semicolon). In HTTP and many other protocols, it is used in a Content-Type header field.
Content coding:
A name registered in the "HTTP Content Coding Registry" [IANA.http-parameters], as specified by Sections 16.6.1 and 18.6 of [RFC9110], indicating an encoding transformation with semantics further specified in Section 8.4.1 of [RFC9110]. Confusingly, in HTTP, content coding values are found in a header field called "Content-Encoding"; however, "content coding" is the correct term for the process and the registered values.
Content format:
The combination of a Content-Type and zero or more content codings, identified by (1) a numeric identifier defined in the "CoAP Content-Formats" registry [IANA.core-parameters], as per Section 12.3 of [RFC7252] (referred to as Content-Format number), or (2) a Content-Format-String.
Content-Format-String:
The string representation of the combination of a Content-Type and zero or more content codings.
Content-Format-Spec:
The string representation of a content format; either a Content-Format-String or the (decimal) string representation of a Content-Format number.
メディアタイプ（Media type）:
交換のために用意された表現（バイト文字列）に対する登録済みのラベルです[RFC1590] [RFC6838]。Media-Type-Nameによって識別されます。
Media-Type-Name:
[RFC6838]に従って[IANA.media-types]に登録された、タイプ名（type-name）とサブタイプ名（subtype-name）の組み合わせです。 慣例として、2つの名前をスラッシュで区切って表します。
Content-Type:
Media-Type-Nameに、オプションでパラメーター（[RFC2045]のSection 5。Media-Type-Nameとの間、およびパラメーター同士の間はセミコロンで区切ります）を関連付けたものです。 HTTPやその他の多くのプロトコルでは、Content-Typeヘッダーフィールドで使用されます。
コンテンツコーディング（Content coding）:
[RFC9110]のセクション16.6.1と18.6で規定されているとおりに"HTTP Content Coding Registry"[IANA.http-parameters]に登録された名前で、エンコーディング変換を示します。 その変換のセマンティクスは[RFC9110]のSection 8.4.1でさらに規定されています。 紛らわしいことに、HTTPではコンテンツコーディングの値は"Content-Encoding"という名前のヘッダーフィールドに含まれます。 しかし、その処理と登録される値を表す正しい用語は「コンテンツコーディング」です。
コンテンツフォーマット（Content format）:
Content-Typeと0個以上のコンテンツコーディングの組み合わせです。 (1) [RFC7252]のSection 12.3に従って"CoAP Content-Formats"レジストリー[IANA.core-parameters]で定義された数値識別子（Content-Format番号と呼びます）、または(2) Content-Format-Stringによって識別されます。
Content-Format-String:
Content-Typeと0個以上のコンテンツコーディングの組み合わせを文字列で表現したものです。
Content-Format-Spec:
コンテンツフォーマットを文字列で表現したものです。 Content-Format-String、またはContent-Format番号の（10進数の）文字列表現のいずれかです。

Readers should also be familiar with the terms and concepts discussed in [RFC8428].

読者は、[RFC8428]で説明されている用語と概念にも精通している必要があります。

3. SenML Content-Format ("ct") Field

3. SenML Content-Format（"ct"）フィールド

When a SenML Record contains a Data Value field ("vd"), the Record MAY also include a Content-Format indication field, using label "ct". The value of this field is a Content-Format-Spec, i.e., one of the following:

SenMLレコードがデータ値フィールド（"vd"）を含む場合、そのレコードはラベル"ct"を使用したContent-Format表示フィールドも含めてよいです（MAY）。 このフィールドの値はContent-Format-Specです。 すなわち、次のいずれかです。

  • a CoAP Content-Format number in decimal form with no leading zeros (except for the value "0" itself). This value represents an unsigned integer in the range of 0-65535, similar to the "ct" attribute defined in Section 7.2.1 of [RFC7252] for CoRE Link Format [RFC6690].
  • a Content-Format-String containing a Content-Type and zero or more content codings (see below).
  • 先頭にゼロを付けない（値"0"そのものを除く）10進数形式のCoAP Content-Format番号。 この値は0〜65535の範囲の符号なし整数を表し、CoRE Link Format[RFC6690]のために[RFC7252]のSection 7.2.1で定義されている"ct"属性と同様です。
  • Content-Typeと0個以上のコンテンツコーディングを含むContent-Format-String（後述）。

The syntax of this field is formally defined in Section 6.

このフィールドの構文はSection 6で形式的に定義されています。

The CoAP Content-Format number provides a simple and efficient way to indicate the type of the data. Since some Internet media types and their content coding and parameter alternatives do not have assigned CoAP Content-Format numbers, using Content-Type and zero or more content codings is also allowed. Both methods use a string value in the "ct" field to keep its data type consistent across uses. When the "ct" field contains only digits, it is interpreted as a CoAP Content-Format number.

CoAP Content-Format番号は、データの種類を示すための簡単で効率的な方法を提供します。 一部のインターネットメディアタイプや、そのコンテンツコーディングとパラメーターの選択肢にはCoAP Content-Format番号が割り当てられていないため、Content-Typeと0個以上のコンテンツコーディングを使用することも許されています。 どちらの方法でも、用途によらずデータ型を一貫させるために、"ct"フィールドには文字列値を使用します。 "ct"フィールドが数字だけを含む場合は、CoAP Content-Format番号として解釈されます。

To indicate that one or more content codings are used with a Content-Type, each of the content coding values is appended to the Content-Type value (media type and parameters, if any), separated by an "@" sign, in the order of when the content codings were applied (the same order as in Section 8.4 of [RFC9110]). For example (using a content coding value of "deflate", as defined in Section 8.4.1.2 of [RFC9110]):

Content-Typeとともに1つ以上のコンテンツコーディングが使用されていることを示すには、各コンテンツコーディングの値を"@"記号で区切って、Content-Typeの値（メディアタイプと、もしあればパラメーター）の後ろに付加します。 その順序は、コンテンツコーディングが適用された順序（[RFC9110]のSection 8.4と同じ順序）です。 たとえば、（[RFC9110]のSection 8.4.1.2で定義されているコンテンツコーディングの値"deflate"を使用すると）次のようになります。

text/plain; charset=utf-8@deflate

text/plain; charset=utf-8@deflate

If no "@" sign is present after the media type and parameters, then no content coding has been specified, and the "identity" content coding is used -- no encoding transformation is employed.

メディアタイプとパラメーターの後に"@"記号がない場合は、コンテンツコーディングが指定されておらず、"identity"コンテンツコーディングが使用されます。 つまり、エンコーディング変換は行われません。

4. SenML Base Content-Format ("bct") Field

4. SenML Base Content-Format（"bct"）フィールド

The Base Content-Format field, label "bct", provides a default value for the Content-Format field (label "ct") within its range. The range of the base field includes the Record containing it, up to (but not including) the next Record containing a "bct" field, if any, or up to the end of the Pack otherwise. The process of resolving (Section 4.6 of [RFC8428]) this base field is performed by adding its value with the label "ct" to all Records in this range that carry a "vd" field but do not already contain a Content-Format ("ct") field.

ラベル"bct"を持つBase Content-Formatフィールドは、その範囲内のContent-Formatフィールド（ラベル"ct"）のデフォルト値を提供します。 このベースフィールドの範囲は、それを含むレコードから始まり、"bct"フィールドを含む次のレコードがあればその直前まで（そのレコードは含みません）、なければパックの終わりまでです。 このベースフィールドを解決する処理（[RFC8428]のSection 4.6）は、この範囲内で"vd"フィールドを持ち、まだContent-Format（"ct"）フィールドを含んでいないすべてのレコードに、その値をラベル"ct"で追加することによって行われます。

Figure 4 shows a variation of Figure 2 with multiple records, with the "nfc-reader" records resolving to the base field value "60" and the "iris-photo" record overriding this with the "image/png" media type (actual data left out for brevity).

Figure 4は、Figure 2を複数のレコードを含むように変えたものです。 "nfc-reader"のレコードはベースフィールドの値"60"に解決され、"iris-photo"のレコードはこれを"image/png"メディアタイプで上書きしています（簡潔さのため、実際のデータは省略しています）。

5. Examples

5. 例

The following examples are valid values for the "ct" and "bct" fields (explanation/comments in parentheses):

以下は、"ct"フィールドと"bct"フィールドの有効な値の例です（括弧内は説明やコメントです）。

  • "60" (CoAP Content-Format number for "application/cbor")
  • "0" (CoAP Content-Format number for "text/plain" with parameter "charset=utf-8")
  • "application/json" (JSON Content-Type -- equivalent to "50" CoAP Content-Format number)
  • "application/json@deflate" (JSON Content-Type with "deflate" as content coding -- equivalent to "11050" CoAP Content-Format number)
  • "application/json@deflate@aes128gcm" (JSON Content-Type with "deflate" followed by "aes128gcm" as content codings)
  • "text/csv" (Comma-Separated Values (CSV) [RFC4180] Content-Type)
  • "text/csv;header=present@gzip" (CSV with header row, using "gzip" as content coding)
  • "60"（"application/cbor"に対するCoAP Content-Format番号）
  • "0"（パラメーター"charset=utf-8"付きの"text/plain"に対するCoAP Content-Format番号）
  • "application/json"（JSONのContent-Type。CoAP Content-Format番号"50"と等価）
  • "application/json@deflate"（コンテンツコーディングとして"deflate"を使用したJSONのContent-Type。CoAP Content-Format番号"11050"と等価）
  • "application/json@deflate@aes128gcm"（コンテンツコーディングとして"deflate"、続いて"aes128gcm"を使用したJSONのContent-Type）
  • "text/csv"（Comma-Separated Values（CSV）[RFC4180]のContent-Type）
  • "text/csv;header=present@gzip"（ヘッダー行付きのCSVで、コンテンツコーディングとして"gzip"を使用）

6. ABNF

6. ABNF

This specification provides a formal definition of the syntax of Content-Format-Spec strings using ABNF notation [RFC5234], which contains three new rules and a number of rules collected and adapted from various RFCs [RFC9110] [RFC6838] [RFC5234] [RFC8866].

この仕様では、ABNF記法[RFC5234]を使用して、Content-Format-Spec文字列の構文の形式的な定義を示します。 この定義には、3つの新しい規則と、さまざまなRFC[RFC9110] [RFC6838] [RFC5234] [RFC8866]から集めて調整した多数の規則が含まれます。

7. Security Considerations

7. セキュリティーに関する考慮事項

The indication of a media type in the data does not exempt a consuming application from properly checking its inputs. Also, the ability for an attacker to supply crafted SenML data that specifies media types chosen by the attacker may expose vulnerabilities of handlers for these media types to the attacker. This includes "decompression bombs", compressed data that is crafted to decompress to extremely large data items.

データの中でメディアタイプが示されていても、消費側のアプリケーションが入力を適切に検査しなくてよいことにはなりません。 また、攻撃者が選んだメディアタイプを指定する細工されたSenMLデータを攻撃者が供給できると、それらのメディアタイプのハンドラーの脆弱性が攻撃者にさらされる可能性があります。 これには、極端に大きなデータ項目に展開されるように細工された圧縮データである「解凍爆弾（decompression bomb）」が含まれます。
