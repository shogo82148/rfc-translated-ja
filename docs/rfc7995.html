RFC 7995

PDF Format for RFCs

RFC 7995

RFCのためのPDF形式

Abstract

概要

This document discusses options and requirements for the PDF rendering of RFCs in the RFC Series, as outlined in RFC 6949. It also discusses the use of PDF for Internet-Drafts, and available or needed software tools for producing and working with PDF.

この文書は、RFC 6949で概説されているとおり、RFCシリーズにおけるRFCのPDFレンダリングのためのオプションと要件について議論します。また、インターネットドラフトでのPDFの使用や、PDFを作成し扱うために利用可能なソフトウェアツールや必要とされるソフトウェアツールについても議論します。

1. Introduction

1. はじめに

The RFC Series is evolving, as outlined in [RFC6949]. Future documents will use a canonical format, XML, with renderings in various formats, including PDF.

RFCシリーズは、[RFC6949]で概説されているとおり進化しています。今後の文書は正規フォーマットとしてXMLを使用し、PDFを含むさまざまな形式でレンダリングされます。

Because PDF has a wide range of capabilities and alternatives, not all PDFs are "equal". For example, visually similar documents could consist of scanned or rasterized images, or include text layout options, hyperlinks, embedded fonts, and digital signatures. (See [APP-PDF] for a history of PDF.)

PDFには幅広い機能と選択肢があるため、すべてのPDFが「同等」というわけではありません。たとえば、見た目が似ている文書でも、スキャンされた画像やラスター化された画像で構成されていることもあれば、テキストのレイアウトオプション、ハイパーリンク、埋め込みフォント、デジタル署名を含んでいることもあります（PDFの歴史については[APP-PDF]を参照してください）。

This document explains some of the relevant options and makes recommendations, for both the RFC Series and Internet-Drafts.

この文書は、関連するオプションのいくつかを説明し、RFCシリーズとインターネットドラフトの両方に対して推奨事項を示します。

The PDF format and the tools to manipulate it are not as well known as those for the other RFC formats, at least in the IETF community. This document discusses some of the processes for creating and using PDFs using both open source and commercial products.

PDF形式とそれを操作するツールは、少なくともIETFコミュニティーにおいては、他のRFC形式のものほどよく知られていません。この文書は、オープンソース製品と商用製品の両方を使ってPDFを作成し利用するためのプロセスのいくつかについて議論します。

The details described in this document are expected to change based on experience gained in implementing the new publication toolsets. Revised documents will be published capturing those changes as the toolsets are completed. Other implementers must not expect those changes to remain backwards-compatible with the details described in this document.

この文書で説明する詳細は、新しい公開用ツールセットを実装する中で得られた経験に基づいて変更されることが見込まれます。ツールセットが完成するにつれて、それらの変更を反映した改訂版の文書が公開される予定です。他の実装者は、それらの変更がこの文書で説明する詳細との後方互換性を保つことを期待してはいけません。

2. Choosing PDF Versions and Standards

2. PDFのバージョンと標準の選択

PDF [PDF] has gone through several revisions, primarily for the addition of features. PDF features have generally been added in a way that older viewers "fail gracefully", but even so, the older the PDF version produced, the more legacy viewers will support that version but the fewer features will be enabled.

PDF [PDF]は、主に機能の追加のために何度か改訂されてきました。PDFの機能は一般に、古いビューアーが「穏やかに失敗する（fail gracefully）」ように追加されてきましたが、それでも、生成するPDFのバージョンが古いほど、そのバージョンをサポートするレガシーなビューアーは多くなる一方で、有効になる機能は少なくなります。

As PDF has evolved a broad set of capabilities, additional standards for PDF files are applicable. These standards establish ground rules that are important for specific applications. For example, PDF/X was specifically designed for Prepress digital data exchange, with careful attention to color management and printing instructions. The PDF/E standard was designed for engineering documents with dynamic workflows (where a document continues to be revised after publication) and allows interactive media (including animation and 3D).

PDFが幅広い機能を持つように進化するにつれて、PDFファイルに適用できる追加の標準が生まれました。これらの標準は、特定の用途にとって重要な基本ルールを定めています。たとえば、PDF/Xは、カラーマネジメントと印刷指示に細心の注意を払った、印刷前工程（プリプレス）のデジタルデータ交換のために特別に設計されました。PDF/E標準は、動的なワークフロー（公開後も文書の改訂が続くもの）を伴うエンジニアリング文書のために設計されており、インタラクティブなメディア（アニメーションや3Dを含む）を使用できます。

Two additional standards families are important to the RFC format, though: long-term preservation (PDF/A), and user accessibility (PDF/UA [PDFUA]). These then have sub-profiles (PDF/A-1, PDF/A-2 [PDFA2], PDF/A-3 [PDFA3]), each of which has conformance levels. These standards are then supported by various software libraries and tools.

しかし、RFC形式にとって重要なのは、長期保存（PDF/A）とユーザーアクセシビリティー（PDF/UA [PDFUA]）という、さらに2つの標準ファミリーです。これらにはさらにサブプロファイル（PDF/A-1、PDF/A-2 [PDFA2]、PDF/A-3 [PDFA3]）があり、それぞれに適合レベルがあります。そして、これらの標準はさまざまなソフトウェアライブラリーやツールによってサポートされています。

It is effective and useful to use these standards to capture PDF for RFC requirements, and they will make the PDF files useful in workflows that expect them.

これらの標準を使ってRFCに対するPDFの要件を表すのは効果的かつ有用であり、それによって、これらの標準を前提とするワークフローでPDFファイルが役立つようになります。

Recommendations:

推奨事項：

  • Use PDF 1.7; although relatively recent, it is well supported by widely available viewers.
  • For RFCs, require PDF/A-3 with conformance level "U". This captures the archivability and long-term stability of PDF 1.7 files, mandatory Unicode mapping (Sections 14.8.2.4.2 ("Unicode Mapping in Tagged PDF") and 9.10.2 ("Mapping Character Codes to Unicode Values") of [PDF]), and many of the requirement features.
  • Use PDF/A-3 for embedding additional data (including the XML source file) in RFCs and Internet-Drafts.
  • Use PDF/UA for user accessibility.
  • PDF 1.7を使用します。比較的新しいものの、広く入手可能なビューアーで十分にサポートされています。
  • RFCには、適合レベル「U」のPDF/A-3を要求します。これにより、PDF 1.7ファイルのアーカイブ性と長期的な安定性、必須のUnicodeマッピング（[PDF]のセクション14.8.2.4.2（「Unicode Mapping in Tagged PDF」）とセクション9.10.2（「Mapping Character Codes to Unicode Values」））、および要件となる機能の多くを満たせます。
  • RFCとインターネットドラフトに追加のデータ（XMLソースファイルを含む）を埋め込むには、PDF/A-3を使用します。
  • ユーザーアクセシビリティーのためにPDF/UAを使用します。

3. Options and Requirements for PDF RFCs

3. PDF RFCのオプションと要件

This section lays out options and requirements for PDFs produced by the RFC Editor for RFCs. There are two subsections: Section 3.1 covers "visible" requirements related to how the PDF normally appears when it is viewed with a PDF viewer; Section 3.2 covers "invisible" options and requirements, which primarily affect the ability to process PDFs in other ways but do not ordinarily control the way the document appears. (Of course, a viewer UI might display processing capabilities, such as showing whether a document has been digitally signed.)

このセクションでは、RFCエディターがRFCのために作成するPDFのオプションと要件を示します。このセクションには2つのサブセクションがあります。Section 3.1では、PDFビューアーで表示したときにPDFが通常どのように見えるかに関する「可視」の要件を扱います。Section 3.2では、「不可視」のオプションと要件を扱います。これらは主に、PDFを他の方法で処理できるかどうかに影響しますが、通常は文書の見え方を左右しません（もちろん、ビューアーのUIが、文書がデジタル署名されているかどうかを示すなど、処理に関する機能を表示することはあります）。

In many cases, the choice of PDF requirements is heavily influenced by the capabilities of available tools to create PDFs. Most of the discussion of tooling is to be found in Appendix C.

多くの場合、PDFの要件の選択は、PDFを作成するために利用可能なツールの機能に大きく左右されます。ツールに関する議論のほとんどはAppendix Cにあります。

3.1. "Visible" Requirements

3.1. 「可視」の要件

PDF supports rich visible layout of fixed-sized pages.

PDFは、固定サイズのページに対する豊かな可視のレイアウトをサポートします。

3.1.1. General Visible Requirements

3.1.1. 可視の要件全般

For a consistent "look" of RFCs and good style, the PDFs produced by the RFC Editor should have a clear, consistent, identifiable, and easy-to-read style. They should print well on the widest range of printers and should look good on displays of varying resolution.

RFCの「見た目」を一貫させ、良好なスタイルとするために、RFCエディターが作成するPDFは、明瞭で一貫性があり、識別しやすく、読みやすいスタイルを持つべきです。できるだけ幅広いプリンターできれいに印刷でき、さまざまな解像度のディスプレイで見栄えがよいものであるべきです。

3.1.2. Page Size and Margins

3.1.2. ページサイズと余白

PDF files are laid out for a particular size of page and margins. There are two paper sizes in common use: "US Letter" (8.5x11 inches, 216x279 mm, in popular use in North America) and "A4" (210x297 mm, 8.27x11.7 inches, standard for the rest of the world). Usually, PDF printing software is used in a "shrink to fit" mode where the printing is adjusted to fit the paper in the printer. There is some controversy, but the argument that A4 is an international standard is compelling. However, if the margins and header positioning are chosen appropriately, the document can be printed without any scaling.

PDFファイルは、特定のページサイズと余白に合わせてレイアウトされます。一般に使われている用紙サイズは2つあります。「US Letter」（8.5×11インチ、216×279 mm、北米で広く使用）と「A4」（210×297 mm、8.27×11.7インチ、それ以外の地域で標準）です。通常、PDFの印刷ソフトウェアは、プリンターの用紙に合わせて印刷を調整する「縮小して全体を表示（shrink to fit）」モードで使われます。異論もありますが、A4が国際標準であるという主張には説得力があります。ただし、余白とヘッダーの位置を適切に選べば、文書をまったく拡大縮小せずに印刷できます。

Recommendation:
The Internet-Draft and RFC processors should produce A4 size by default. However, the margins and header positioning need to be chosen to look good on both paper sizes without scaling. Following the advice found in [RFC2346], this means that we should use A4 portrait mode with left and right margins of 20 mm, and top and bottom margins of 33 mm.
推奨事項：
インターネットドラフトとRFCの処理系は、デフォルトでA4サイズを生成すべきです。ただし、余白とヘッダーの位置は、拡大縮小せずにどちらの用紙サイズでも見栄えがよくなるように選ぶ必要があります。[RFC2346]にある助言に従うと、これは、左右の余白を20 mm、上下の余白を33 mmとしたA4縦向きを使うべきであることを意味します。

3.1.3. Headers and Footers

3.1.3. ヘッダーとフッター

Page headers and footers are part of the page layout. There are a variety of options. Note that page headers and footers in PDF can be typeset in a way that the entire (longer) title might fit.

ページのヘッダーとフッターは、ページレイアウトの一部です。さまざまなオプションがあります。PDFのページヘッダーとフッターは、（より長い）タイトル全体が収まるように組版できることに注意してください。

Recommendation:
Page headers and footers should contain information similar to the headings in the current text versions of documents, including page numbers, title, author, and date. However, the page headers and footers should be typeset in a way so as to be unobtrusive. The page headers and footers should be placed into the PDF in such a way that they do not interfere with screen readers.
推奨事項：
ページのヘッダーとフッターには、ページ番号、タイトル、著者、日付など、現在のテキスト版の文書の見出しと同様の情報を含めるべきです。ただし、ページのヘッダーとフッターは目立たないように組版すべきです。ページのヘッダーとフッターは、スクリーンリーダーの妨げにならないようにPDFに配置すべきです。

3.1.4. Paragraph Numbering

3.1.4. 段落番号

One common feature of the Internet-Draft output formats is optional visible paragraph numbers, to aid in discussions. In the PDF, and thus in the printed rendition, it is possible to make paragraph numbers unobtrusive and even to impinge on the margins.

インターネットドラフトの出力形式に共通する機能の1つに、議論の助けとなる、表示を選択できる段落番号があります。PDFでは、したがって印刷物でも、段落番号を目立たないようにし、余白にはみ出させることさえできます。

Recommendation:
When the XML "editing=yes" option has been chosen, show paragraph numbers in the right margin, typeset in a way so as to be unobtrusive. (The right margin instead of the left margin prevents the paragraph numbers from being confused with the section numbers.) If possible, the paragraph numbers should be coded in such a way that they do not interfere with screen readers.
推奨事項：
XMLの「editing=yes」オプションが選択されている場合は、段落番号を右余白に、目立たないように組版して表示します（左余白ではなく右余白にすることで、段落番号がセクション番号と混同されるのを防ぎます）。可能であれば、段落番号はスクリーンリーダーの妨げにならないようにコード化すべきです。

3.1.5. Paged Content Layout

3.1.5. ページ単位のコンテンツレイアウト

By its nature, PDF is paginated, so pagination issues must be considered. This is reflected in two areas: running headers and footers, and how text is laid out on a page for optimal reading.

PDFは本質的にページ分割されているため、ページ分割の問題を考慮しなければなりません。これは2つの領域に表れます。柱（running header）とフッター、そして最適に読めるようにテキストをページ上にどうレイアウトするかです。

Appendix B describes the process of creating a paged document from running text such that related material is present on the same page together and artifacts of pagination don't interfere with easy reading of the document.

Appendix Bでは、関連する内容が同じページにまとまり、ページ分割による不具合が文書の読みやすさを妨げないように、連続したテキストからページ分割された文書を作成するプロセスを説明しています。

Layout engines differ in the quality of the algorithms used to automate these processes. In some cases, the automated processes require some manual assistance to ensure, for example, that a text line intended as a heading is "kept" with the text for which it is a heading.

レイアウトエンジンによって、これらのプロセスを自動化するために使われるアルゴリズムの品質は異なります。場合によっては、自動化されたプロセスに多少の手作業による支援が必要になります。たとえば、見出しとして意図されたテキスト行が、その見出しの対象となるテキストと「一緒に保たれる（kept）」ようにするためです。

Recommendations:

推奨事項：

  • Headers and footers should be printed on each page. The information should include the RFC number or Internet-Draft name, the page number, the category (e.g., Informational), a shortened version of the authors' names, the date of the RFC or Internet-Draft, and the short form of the document title.

  • Choose a layout engine so that

    • manual intervention is minimized
    • widow and orphan processing is automatic
    • heading and title contiguation is automatic
  • ヘッダーとフッターを各ページに印刷すべきです。その情報には、RFC番号またはインターネットドラフト名、ページ番号、カテゴリー（たとえばInformational）、著者名の短縮版、RFCまたはインターネットドラフトの日付、文書タイトルの短縮形を含めるべきです。

  • 次のようになるレイアウトエンジンを選択します。

    • 手作業による介入が最小限になる
    • ウィドウとオーファンの処理が自動で行われる
    • 見出しとタイトルを続けて配置する処理が自動で行われる

3.1.6. Typeface Choices

3.1.6. 書体の選択

A PDF may refer to a font by name, or it may use an embedded font. When a font is not embedded, a PDF viewer will attempt to locate a locally installed font of the same name. If it cannot find an exact match, it will find a "close match". If a close match is not available, it will fall back to something implementation dependent and usually undesirable.

PDFは、フォントを名前で参照することも、埋め込みフォントを使用することもできます。フォントが埋め込まれていない場合、PDFビューアーは、ローカルにインストールされている同じ名前のフォントを探そうとします。完全に一致するものが見つからなければ「近いもの」を探します。近いものも利用できない場合は、実装依存の、たいていは望ましくないものにフォールバックします。

In addition, the PDF/A standards mandate the embedding of fonts. Instead of using additional software to embed the fonts, the software generating the PDF files should produce PDF/A-conforming files directly, thus ensuring that all glyphs include Unicode mappings and embedded fonts from the outset.

さらに、PDF/A標準はフォントの埋め込みを義務付けています。フォントを埋め込むために追加のソフトウェアを使うのではなく、PDFファイルを生成するソフトウェアがPDF/Aに適合したファイルを直接生成すべきです。そうすることで、最初からすべてのグリフにUnicodeマッピングと埋め込みフォントが含まれることを保証できます。

If the HTML version of the document is being visually mimicked, the font(s) chosen should have both variable-width and constant-width components, as well as bold and italic representations.

文書のHTML版の見た目をまねる場合、選択するフォントには、可変幅と固定幅の両方の構成要素に加え、太字と斜体の表現もあるべきです。

The typefaces used by Internet-Drafts and by RFCs need not be identical.

インターネットドラフトとRFCで使用する書体は、同一である必要はありません。

Few fonts have glyphs for the entire repertoire of Unicode characters; for this purpose, the PDF generation tool may need a set of fonts and a way of choosing them. The RFC Editor is defining where Unicode characters may be used within RFCs [RFC7997].

Unicode文字のレパートリー全体のグリフを持つフォントはほとんどありません。そのため、PDF生成ツールには、フォントのセットとそれらを選択する方法が必要になる場合があります。RFCエディターは、RFC内のどこでUnicode文字を使用できるかを定めているところです[RFC7997]。

Typefaces are typically licensed, and in many cases there is a fee for use by PDF creation tools; however, there is usually no fee for display or print of the embedded fonts.

書体は通常ライセンスされており、多くの場合、PDF作成ツールで使用するには料金がかかります。ただし、埋め込まれたフォントを表示または印刷する場合には、通常は料金はかかりません。

Recommendations:

推奨事項：

  • For consistent viewing, all fonts should be embedded. The fonts used must be available for use by the IETF community. Some discussion of available typefaces can be found in Appendix C.4.
  • The choice of typefaces with respect to serif, sans-serif, monospace, etc., should follow the recommendations for HTML and CSS renderings ("CSS" refers to a Cascading Style Sheet) [RFC7992] and [RFC7993].
  • The range of Unicode characters allowed in the XML source for Internet-Drafts and RFCs may be bounded by the availability of embeddable fonts with appropriate glyphs [RFC7997].
  • 一貫した表示のために、すべてのフォントを埋め込むべきです。使用するフォントは、IETFコミュニティーが利用できるものでなければなりません。利用可能な書体についての議論はAppendix C.4にあります。
  • セリフ、サンセリフ、等幅などに関する書体の選択は、HTMLおよびCSS（「CSS」はカスケーディングスタイルシートを指します）によるレンダリングに対する推奨事項[RFC7992]と[RFC7993]に従うべきです。
  • インターネットドラフトとRFCのXMLソースで許可されるUnicode文字の範囲は、適切なグリフを持つ埋め込み可能なフォントが利用できるかどうかによって制限される場合があります[RFC7997]。

3.1.7. Hyphenation and Line Breaks

3.1.7. ハイフネーションと改行

Typically, when doing page layout of running text, especially with narrow page width and long words, layout processors of English text often have the option of either hyphenating words or using existing hyphens as a place to introduce word breaks. However, inserting line breaks mid-word can be harmful when the "word" is actually a sequence of characters representing a protocol element or protocol sequence.

一般に、連続したテキストのページレイアウトを行う場合、特にページ幅が狭く単語が長い場合には、英語テキストのレイアウト処理系は、単語をハイフネーションするか、既存のハイフンを単語の区切り位置として使うかを選べることがよくあります。しかし、その「単語」が実際にはプロトコル要素やプロトコルシーケンスを表す文字の並びである場合、単語の途中に改行を挿入すると害を及ぼすことがあります。

Recommendation:
Avoid introducing hyphenated line breaks mid-word into the visual display, consistent with requirements for plain text and HTML.
推奨事項：
プレーンテキストとHTMLに対する要件と一貫させて、表示上、単語の途中にハイフン付きの改行を入れないようにします。

3.1.8. Hyperlinks

3.1.8. ハイパーリンク

PDF supports hyperlinks to sections of the same document and also to sections of other documents.

PDFは、同じ文書のセクションへのハイパーリンクと、他の文書のセクションへのハイパーリンクをサポートします。

The conversion to PDF can generate:

PDFへの変換では、次のものを生成できます。

  • hyperlinks within the document
  • hyperlinks to other RFCs and Internet-Drafts
  • hyperlinks to external locations
  • hyperlinks within a table of contents
  • hyperlinks within an index
  • 文書内のハイパーリンク
  • 他のRFCやインターネットドラフトへのハイパーリンク
  • 外部の場所へのハイパーリンク
  • 目次内のハイパーリンク
  • 索引内のハイパーリンク

Recommendations:

推奨事項：

  • All hyperlinks available in the HTML rendition of the RFC should also be visible and active in the PDF produced. This includes both internal hyperlinks and hyperlinks to external resources.
  • The table of contents, including page numbers, is useful when printed. Section numbers and page numbers in the table of contents should also be hyperlinked to their respective sections in the body of the document.
  • As specified in Section 4.8.6.2 ("Referencing RFCs") of [RFC7322], hyperlinks to RFCs from the references section should point to the RFC "info" page (e.g., <https://www.rfc-editor.org/info/rfc7322>), which then links to the various formats available.
  • Hyperlinks to Internet-Drafts from the references section should point to the Datatracker entry page for the draft, which then links to the various formats available.
  • RFCのHTMLレンダリングで利用できるすべてのハイパーリンクは、生成されたPDFでも表示され、有効であるべきです。これには、内部のハイパーリンクと外部リソースへのハイパーリンクの両方が含まれます。
  • ページ番号を含む目次は、印刷したときに役立ちます。目次のセクション番号とページ番号も、文書本文内のそれぞれのセクションにハイパーリンクされているべきです。
  • [RFC7322]のセクション4.8.6.2（「Referencing RFCs」）で規定されているとおり、参考文献セクションからRFCへのハイパーリンクは、RFCの「info」ページ（たとえば<https://www.rfc-editor.org/info/rfc7322>）を指すべきです。そのページから、利用可能なさまざまな形式へのリンクが張られています。
  • 参考文献セクションからインターネットドラフトへのハイパーリンクは、そのドラフトのDatatrackerのエントリーページを指すべきです。そのページから、利用可能なさまざまな形式へのリンクが張られています。

3.1.9. Similarity to Other Outputs

3.1.9. 他の出力との類似性

There is some advantage to having the PDF files look like the text or HTML renderings of the same document. Even so, there are several options. The PDF

PDFファイルを、同じ文書のテキストまたはHTMLのレンダリングと同じような見た目にすることには、いくつかの利点があります。それでも、いくつかの選択肢があります。PDFは

  1. could look like the text version of the document, or
  2. could look like the text version of the document but with pictures rendered as pictures instead of using their ASCII art equivalent, or
  3. could look like the HTML version.
  1. 文書のテキスト版のような見た目にできる、または
  2. 文書のテキスト版のような見た目にしつつ、図をASCIIアートの相当物ではなく図としてレンダリングできる、または
  3. HTML版のような見た目にできる。
Recommendation:
The PDF rendition should look like the HTML rendition, at least in spirit. Some differences from the HTML rendition would include different typeface and size (chosen for printing), page numbers in the table of contents and index, and the use of page headers and footers.
推奨事項：
PDFのレンダリングは、少なくとも精神においてはHTMLのレンダリングのような見た目にすべきです。HTMLのレンダリングとの違いとしては、（印刷用に選ばれた）異なる書体とサイズ、目次と索引のページ番号、ページのヘッダーとフッターの使用などが挙げられます。

Most of the choices used for the renderings per [RFC7992] and [RFC7993] are thus applicable. See those documents for specifics on the rendering of the specific XML elements. Some notes:

したがって、[RFC7992]と[RFC7993]によるレンダリングで使われている選択のほとんどが適用できます。特定のXML要素のレンダリングの詳細については、それらの文書を参照してください。いくつか注記します。

  • Every place in the document that would receive an HTML ID would be given an identical PDF named destination. In addition, a named destination will be created for each page with the form "pg-#", as in "pg-35".
  • No pilcrows are generated or made visible.
  • The table of contents (generated if the XML's <rfc> element's tocInclude attribute has the value "true") [RFC7991] will have the section number linked to the section start but will also include a page number that is linked to the corresponding page. The section title and the page number will be separated by a visually appropriate separator, and the page numbers will be aligned with each other.
  • The index (generated if the XML's <rfc> element's indexInclude attribute has the value "true") will have the section number linked to that section named destination but will also include a page number that is linked to the page named destination.
  • The running header in one line (on page 2 and all subsequent pages) has the RFC number on the left (RFC NNNN), the (possibly shortened form) title centered, and the date (Month Year) on the right. The text is rendered in a way that is visually unobtrusive.
  • The running footer in one line (on all pages) has the author's last name on the left, category centered, and the page number on the right ([Page N]). The text is rendered in a way that is visually unobtrusive.
  • We should not attempt to replicate in PDF the feature of the HTML format that includes a dynamic block that displays up-to-date information on updates, obsoletions, and errata.
  • HTMLのIDを受け取る文書内のすべての場所には、同一のPDFの名前付き転送先（named destination）が与えられます。さらに、各ページに対して「pg-35」のように「pg-#」の形式の名前付き転送先が作成されます。
  • 段落記号（pilcrow）は生成されず、表示もされません。
  • 目次（XMLの<rfc>要素のtocInclude属性の値が「true」の場合に生成されます）[RFC7991]では、セクション番号がセクションの先頭にリンクされますが、対応するページにリンクされたページ番号も含まれます。セクションのタイトルとページ番号は視覚的に適切な区切りで分けられ、ページ番号は互いに揃えられます。
  • 索引（XMLの<rfc>要素のindexInclude属性の値が「true」の場合に生成されます）では、セクション番号がそのセクションの名前付き転送先にリンクされますが、ページの名前付き転送先にリンクされたページ番号も含まれます。
  • 1行の柱（2ページ目以降のすべてのページ）には、左側にRFC番号（RFC NNNN）、中央に（短縮形である可能性のある）タイトル、右側に日付（Month Year）を置きます。このテキストは視覚的に目立たないようにレンダリングされます。
  • 1行のフッター（すべてのページ）には、左側に著者の姓、中央にカテゴリー、右側にページ番号（[Page N]）を置きます。このテキストは視覚的に目立たないようにレンダリングされます。
  • 更新、廃止、正誤表に関する最新の情報を表示する動的なブロックを含むというHTML形式の機能を、PDFで再現しようとすべきではありません。

3.2. "Invisible" Options and Requirements

3.2. 「不可視」のオプションと要件

PDF offers a number of features that improve the utility of PDF files in a variety of workflows, at the cost of extra effort in the xml2rfc conversion process; the trade-offs may be different for the RFC Editor production of RFCs and for Internet-Drafts.

PDFには、さまざまなワークフローにおけるPDFファイルの有用性を高める多くの機能がありますが、その代わりにxml2rfcの変換プロセスで余分な作業が必要になります。そのトレードオフは、RFCエディターによるRFCの作成とインターネットドラフトとで異なる場合があります。

3.2.1. Internal Text Representation

3.2.1. 内部のテキスト表現

The contents of a PDF file can be represented in many ways. The PDF file could be generated:

PDFファイルの内容は、さまざまな方法で表現できます。PDFファイルは次のように生成される可能性があります。

  • as an image of the visual representation, such as a JPEG image of the word "IETF". That is, there might be no internal representation of letters, words, or paragraphs at all.
  • placing individual characters in position on the page, such as saying "put an 'F' here," then "put a 'T' before it," then "put an 'E' before that," then "put an 'I' before that" to render the word "IETF". That is, there might be no internal representation of words or paragraphs at all.
  • placing words in position on the page, such as keeping the characters of the word "IETF" together. That is, there might be no internal representation of paragraphs at all.
  • ensuring that the running order of text in the content stream matches the logical reading order. That is, a sentence such as "The Internet Engineering Task Force (IETF) supports the Internet." would be kept together as a sentence, and multiple sentences within a paragraph would be kept together.
  • 「IETF」という単語のJPEG画像のような、見た目を表す画像として。つまり、文字、単語、段落の内部表現がまったく存在しない可能性があります。
  • 「IETF」という単語をレンダリングするために、「ここに'F'を置く」、次に「その前に'T'を置く」、次に「その前に'E'を置く」、次に「その前に'I'を置く」というように、個々の文字をページ上の位置に配置することで。つまり、単語や段落の内部表現がまったく存在しない可能性があります。
  • 「IETF」という単語の文字をまとめておくなど、単語をページ上の位置に配置することで。つまり、段落の内部表現がまったく存在しない可能性があります。
  • コンテンツストリーム内のテキストの並び順が、論理的な読み順と一致するようにすることで。つまり、「The Internet Engineering Task Force (IETF) supports the Internet.」のような文は1つの文としてまとめられ、段落内の複数の文もまとめられます。

All of these end up with essentially the same visual representation of the output. However, each level has trade-offs for auxiliary uses, such as searching or indexing, commenting and annotation, and accessibility (text-to-speech). Keeping the running order of text in the content stream in the proper order supports all of these auxiliary uses.

これらはいずれも、出力の見た目は本質的に同じになります。しかし、それぞれの段階には、検索や索引付け、コメントや注釈、アクセシビリティー（テキスト読み上げ）といった補助的な用途に関するトレードオフがあります。コンテンツストリーム内のテキストの並び順を適切な順序に保つと、これらの補助的な用途のすべてをサポートできます。

In addition, the "role map" feature of PDF (Section 14.7.3 ("Structure Types") of [PDF]) would allow for the mapping of the logical tags found in the original XML into tags in the PDF.

さらに、PDFの「ロールマップ（role map）」機能（[PDF]のセクション14.7.3（「Structure Types」））を使うと、元のXMLにある論理的なタグをPDFのタグにマッピングできます。

Recommendations:

推奨事項：

  • Text in content streams should follow the XML document's logical order (in the order of tags) to the extent possible. This will provide optimal reuse by software that does not understand Tagged PDF. (PDF/UA requires this.)
  • It might be possible to use the "role map" annotation to capture enough of the xml2rfc source structure, to the point where it is possible to reconstruct the XML source structure completely. However, there is not a compelling case to do so over embedding the original XML, as described in Section 3.2.7.
  • コンテンツストリーム内のテキストは、可能な限りXML文書の論理的な順序（タグの順序）に従うべきです。これにより、タグ付きPDF（Tagged PDF）を理解しないソフトウェアでも最適に再利用できます（PDF/UAはこれを要求しています）。
  • 「ロールマップ」の注釈を使って、XMLソースの構造を完全に再構築できるほどにxml2rfcのソースの構造を十分に捉えることも可能かもしれません。しかし、Section 3.2.7で説明しているように元のXMLを埋め込む方法よりも、そうすべきだという説得力のある理由はありません。

3.2.2. Unicode Support

3.2.2. Unicodeのサポート

PDF itself does not require the use of Unicode. Text is represented as a sequence of glyphs that can then be mapped to Unicode.

PDF自体はUnicodeの使用を要求しません。テキストはグリフの並びとして表現され、それをUnicodeにマッピングできます。

Recommendations:

推奨事項：

  • PDF files generated must have the full text, as it appears in the original XML.
  • Unicode normalization may occur.
  • Text within SVG for SVG images should also have Unicode mappings.
  • Alt-text for images should also support Unicode.
  • 生成されるPDFファイルは、元のXMLに現れるとおりの全文を持たなければなりません。
  • Unicode正規化が行われてもかまいません。
  • SVG画像のSVG内のテキストにもUnicodeマッピングがあるべきです。
  • 画像の代替テキストもUnicodeをサポートすべきです。

3.2.3. Image Processing (Artwork)

3.2.3. 画像処理（アートワーク）

The XML allows both ASCII art and SVG to be used for artwork.

XMLでは、アートワークにASCIIアートとSVGの両方を使用できます。

Recommendations:

推奨事項：

  • If both ASCII art and SVG are available for a picture, the SVG artwork should be preferred over the ASCII artwork.
  • ASCII artwork must be rendered using a monospace font.
  • 図にASCIIアートとSVGの両方が利用できる場合は、ASCIIアートワークよりもSVGアートワークを優先すべきです。
  • ASCIIアートワークは等幅フォントを使ってレンダリングしなければなりません。

3.2.4. Text Description of Images (Alt-Text)

3.2.4. 画像のテキストによる説明（代替テキスト）

Guidelines for the accessibility of PDF <http://www.w3.org/TR/WCAG20-TECHS/PDF1.html> recommend that images, formulas, and other non-text items provide textual alternatives, using the "/Alt" Tag in PDF to provide human-readable text that can be vocalized by text-to-speech technology.

PDFのアクセシビリティーに関するガイドライン<http://www.w3.org/TR/WCAG20-TECHS/PDF1.html>では、画像、数式、その他のテキスト以外の項目に対して、PDFの「/Alt」タグを使ってテキストによる代替を提供し、テキスト読み上げ技術で音声化できる人間が読めるテキストを提供することを推奨しています。

Recommendation:
Any alt-text for artwork and figures available in the XML source should be stored using the PDF /Alt property. Internet-Draft authors and the RFC Editor should ensure that alt-text for all SVG or images is included within the XML source.
推奨事項：
XMLソースで利用できるアートワークと図の代替テキストはすべて、PDFの/Altプロパティーを使って格納すべきです。インターネットドラフトの著者とRFCエディターは、すべてのSVGまたは画像の代替テキストがXMLソース内に含まれるようにすべきです。

3.2.5. Metadata Support

3.2.5. メタデータのサポート

Metadata encodes information about the document authors, the document series, date created, etc. Having this metadata within the PDF file allows it to be used by search engines, viewers, and other reuse tools. PDF supports embedded metadata in a variety of ways, including using the Extensible Metadata Platform (XMP) [XMP]. The RFC Editor maintains metadata about an RFC on its info page.

メタデータは、文書の著者、文書のシリーズ、作成日などに関する情報をエンコードします。このメタデータをPDFファイル内に持つことで、検索エンジン、ビューアー、その他の再利用ツールがそれを利用できるようになります。PDFは、Extensible Metadata Platform（XMP）[XMP]の使用を含め、さまざまな方法でメタデータの埋め込みをサポートしています。RFCエディターは、RFCに関するメタデータをそのinfoページで管理しています。

Recommendation:
The PDFs generated should have all of the metadata from the XML version embedded directly as XMP metadata, including the author, date, the document series, and a URL for where the document can be retrieved. This information should be consistent with the RFC Editor info page at the time of publication.
推奨事項：
生成されるPDFには、著者、日付、文書のシリーズ、文書を取得できる場所のURLを含め、XML版のすべてのメタデータをXMPメタデータとして直接埋め込むべきです。この情報は、公開時点のRFCエディターのinfoページと一致しているべきです。

3.2.6. Document Structure Support

3.2.6. 文書構造のサポート

PDF supports an "outline" feature where sections of the document are marked; this could be used in addition to the table of contents as a navigation aid.

PDFは、文書のセクションに印を付ける「アウトライン」機能をサポートしています。これは、目次に加えてナビゲーションの補助として使用できます。

The section structure of an RFC can be mapped into the PDF elements for the document structure. This will allow the bookmark feature of PDF readers to be used to quickly access sections of the document.

RFCのセクション構造は、文書構造を表すPDFの要素にマッピングできます。これにより、PDFリーダーのブックマーク機能を使って、文書のセクションにすばやくアクセスできるようになります。

Recommendation:
The section structure of an RFC should be mapped into the PDF elements for the document structure. This would include section headings for the boilerplate sections, such as the Abstract, the Status of This Memo section, the table of contents, and the Author's Address section, plus the obvious section headings that are normally included in the table of contents. If possible, this should be done in a way that the same fragment identifiers for the HTML version of the RFC will work for the PDF version.
推奨事項：
RFCのセクション構造は、文書構造を表すPDFの要素にマッピングすべきです。これには、アブストラクト、「このメモのステータス」セクション、目次、著者の連絡先セクションといったボイラープレートのセクションの見出しに加え、通常は目次に含まれる当然のセクション見出しも含まれます。可能であれば、RFCのHTML版と同じフラグメント識別子がPDF版でも機能するように行うべきです。

3.2.7. Embedded Files

3.2.7. 埋め込みファイル

PDF has the capability of including other files; the files may be labeled by both a media type and a role, the AFRelationship key [PDFA3]. In this way, the PDF file also acts as a container.

PDFには他のファイルを含める機能があります。ファイルには、メディアタイプと役割（AFRelationshipキー[PDFA3]）の両方でラベルを付けられます。このようにして、PDFファイルはコンテナとしても機能します。

Embedded content may be compressed.

埋め込まれたコンテンツは圧縮できます。

Many PDF viewers support the ability to view and extract embedded files, although this capability is not universal.

多くのPDFビューアーは埋め込みファイルを表示および抽出する機能をサポートしていますが、この機能は普遍的なものではありません。

Embedding content in the PDF file allows the PDF to act as a complete package that can be transformed, archived, and digitally signed. (Some sample code illustrating how items can be attached to a PDF file and subsequently extracted can be found at <https://github.com/Aiybe/xmptest>.) Useful possibilities:

PDFファイルにコンテンツを埋め込むことで、PDFは、変換、アーカイブ、デジタル署名が可能な完全なパッケージとして機能できるようになります（PDFファイルに項目を添付し、後で抽出する方法を示すサンプルコードが<https://github.com/Aiybe/xmptest>にあります）。有用な可能性は次のとおりです。

  • Embed the source XML input file itself within the PDF. If the source SVG and images for illustrations are also embedded, this would make the PDF file totally self-referential.
  • Embed directly extractable components that are useful for independent processing, including ABNF, MIBs, and source code for reference implementations. This capability might be supported through other mechanisms from the XML source files but could also be supported within the PDF.
  • Finding, extracting, and embedding other components may require additional markup to clearly identify them and additional review to ensure the correctness of embedded files that are not visible.
  • ソースのXML入力ファイルそのものをPDF内に埋め込みます。図のソースSVGと画像も埋め込めば、PDFファイルは完全に自己参照的なものになります。
  • ABNF、MIB、リファレンス実装のソースコードなど、独立した処理に役立つ、直接抽出可能な構成要素を埋め込みます。この機能は、XMLソースファイルから他の仕組みによってサポートすることもできますが、PDF内でサポートすることもできます。
  • 他の構成要素を見つけ、抽出し、埋め込むには、それらを明確に識別するための追加のマークアップや、表示されない埋め込みファイルの正確さを確かめるための追加のレビューが必要になる場合があります。

Recommendations:

推奨事項：

  • Embed the XML source and all illustrations, for RFCs, as a standard feature for xml2rfc's PDF output.
  • If possible, make this a standard feature for Internet-Drafts as well.
  • Named <sourcecode> entries should be embedded.
  • Bitmap images (SVG sources, JPEGs, PNGs, etc.) should be embedded.
  • RFCについては、xml2rfcのPDF出力の標準機能として、XMLソースとすべての図を埋め込みます。
  • 可能であれば、インターネットドラフトでもこれを標準機能にします。
  • 名前付きの<sourcecode>エントリーを埋め込むべきです。
  • ビットマップ画像（SVGソース、JPEG、PNGなど）を埋め込むべきです。

3.3. Digital Signatures

3.3. デジタル署名

The RFC Editor and staff are at times called to provide evidence that a particular RFC is the "original" and has not been modified; digital signatures can provide that verification. As signatures also apply to embedded content, embedding the XML source will provide a way of signing the source XML that was used to produce the PDF file as well.

RFCエディターとそのスタッフは、ある特定のRFCが「オリジナル」であり改変されていないという証拠の提出を求められることがあります。デジタル署名はその検証を提供できます。署名は埋め込まれたコンテンツにも適用されるため、XMLソースを埋め込むことで、PDFファイルの作成に使われたソースXMLにも署名する方法が得られます。

PDF has supported digital signatures since PDF 1.2, and there are multiple methods and options available for signing PDF files. The method chosen for the signing of Internet-Drafts and RFCs will be determined by separate policy.

PDFはPDF 1.2以降デジタル署名をサポートしており、PDFファイルに署名するための複数の方法とオプションが利用できます。インターネットドラフトとRFCの署名に選択される方法は、別のポリシーによって決定されます。

If PDF digital signatures are chosen, the authors suggest the following:

PDFのデジタル署名が選択された場合、著者らは次のことを提案します。

  • PDF documents generated by the Internet-Draft upload tools should be signed with no restrictions on what can be done to the documents afterwards.
  • If Internet-Drafts are allowed to be uploaded in PDF form by an individual, the signature being added should be set in the same way as that noted in the previous paragraph. A PDF that would not allow the IETF Secretariat to re-sign it in that fashion should be rejected.
  • PDF documents generated by the RFC Editor should be signed and certified, and restrictions placed on them to only allow additional signatures and comments (markup) to be added.
  • インターネットドラフトのアップロードツールが生成するPDF文書には、その後に文書に対して行えることに何の制限も設けずに署名すべきです。
  • 個人がインターネットドラフトをPDF形式でアップロードすることが許可される場合、付加される署名は、前の段落で述べたのと同じ方法で設定すべきです。IETF事務局がそのような方法で再署名できないPDFは拒否すべきです。
  • RFCエディターが生成するPDF文書には、署名と認証（certify）を行い、追加の署名とコメント（マークアップ）の付加だけを許可する制限をかけるべきです。

4. Security Considerations

4. セキュリティーに関する考慮事項

The following security considerations apply:

次のセキュリティーに関する考慮事項が適用されます。

Threats:

脅威：

  • There is a risk that user-submitted Internet-Drafts in PDF might contain malware that targets a vulnerability in one of the deployed PDF consumers (readers, printers, validation tools, etc.) in use.
  • There is a small risk that a PDF production toolset might itself have some vulnerability by which it could be tricked into producing malware-bearing PDF files.
  • Section 7 of [RFC3778] describes some additional security considerations for PDF, although this specification is intended to avoid features (like scripting) that might trigger some of those concerns.
  • ユーザーが提出したPDF形式のインターネットドラフトに、使用中のPDF利用ソフトウェア（リーダー、プリンター、検証ツールなど）のいずれかの脆弱性を狙ったマルウェアが含まれているリスクがあります。
  • PDF作成用のツールセット自体に何らかの脆弱性があり、それを悪用されてマルウェアを含むPDFファイルを生成させられるという小さなリスクがあります。
  • [RFC3778]のセクション7では、PDFに関する追加のセキュリティーに関する考慮事項をいくつか説明しています。ただし、この仕様は、それらの懸念の一部を引き起こす可能性のある機能（スクリプトなど）を避けることを意図しています。

Mitigations:

緩和策：

  • The toolsets for producing PDFs need careful security reviews before deploying broadly.
  • If users are allowed to submit Internet-Drafts in PDF, such PDF files should be examined carefully for conformance to this specification, as well as any known exploits of deployed PDF software.
  • PDFを作成するためのツールセットは、広く展開する前に、注意深いセキュリティーレビューが必要です。
  • ユーザーがPDF形式でインターネットドラフトを提出することが許可される場合、そのようなPDFファイルは、この仕様への適合性と、展開されているPDFソフトウェアの既知のエクスプロイトについて、注意深く検査すべきです。

Appendix A. History and Current Use of PDF with RFCs and Internet-Drafts

Appendix A. RFCとインターネットドラフトにおけるPDFの歴史と現在の使用状況

NOTE: This section is meant as an overview to give some background.

注：このセクションは、背景を説明するための概要として意図されています。

A.1. RFCs

A.1. RFC

The RFC Series has for a long time accepted Postscript renderings of RFCs, either in addition to or instead of the text renderings of those same RFCs. These have usually been produced when there was a complicated figure or mathematics within the document. For example, consider the figures and mathematics found in RFCs 1119 and 1142, and compare the figures found in the text version of RFC 3550 with those in the Postscript version. The RFC Editor has provided a PDF rendering of RFCs. Usually, this has been a print of the text file that does not take advantage of any of the broader PDF functionality, unless there was a Postscript version of the RFC, which would then be used by the RFC Editor to generate the PDF.

RFCシリーズは長い間、RFCのテキストレンダリングに加えて、またはその代わりに、同じRFCのPostScriptレンダリングを受け入れてきました。これらは通常、文書内に複雑な図や数式がある場合に作成されてきました。たとえば、RFC 1119とRFC 1142にある図や数式を見てください。また、RFC 3550のテキスト版にある図とPostScript版にある図を比較してみてください。RFCエディターはRFCのPDFレンダリングを提供してきました。通常、これはテキストファイルを印刷したもので、PDFのより幅広い機能を何も活用していません。ただし、RFCのPostScript版がある場合は、RFCエディターがそれを使ってPDFを生成していました。

A.2. Internet-Drafts

A.2. インターネットドラフト

In addition to PDFs generated and published by the RFC Editor, the IETF tools community has also long supported PDF for Internet-Drafts. Most RFCs start with Internet-Drafts, edited by individual authors. The Internet-Drafts submission tool at <https://datatracker.ietf.org/submit/> accepts PDF and Postscript files in addition to the (required) text submission and (currently optional) XML. If a PDF wasn't submitted for a particular version of an Internet-Draft, the tools would generate one from the Postscript, HTML, or text.

RFCエディターが生成し公開するPDFに加えて、IETFのツールコミュニティーも長い間、インターネットドラフトでPDFをサポートしてきました。ほとんどのRFCは、個々の著者が編集するインターネットドラフトから始まります。<https://datatracker.ietf.org/submit/>にあるインターネットドラフト提出ツールは、（必須の）テキストの提出と（現在は任意の）XMLに加えて、PDFファイルとPostScriptファイルを受け付けます。インターネットドラフトの特定のバージョンについてPDFが提出されなかった場合、ツールはPostScript、HTML、またはテキストからPDFを生成していました。

Appendix B. Paged Content Layout Quality

Appendix B. ページ単位のコンテンツレイアウトの品質

The process of creating a paged document from running text typically involves ensuring that related material is present on the same page together and that artifacts of pagination don't interfere with easy reading of the document. Typical high-quality layout processors do several things:

連続したテキストからページ分割された文書を作成するプロセスでは通常、関連する内容が同じページにまとまり、ページ分割による不具合が文書の読みやすさを妨げないようにします。典型的な高品質のレイアウト処理系は、次のようないくつかのことを行います。

Widow and Orphan Management:
Widows and orphans (<https://en.wikipedia.org/wiki/Widows_and_orphans>) should be avoided automatically (unless the entire paragraph is only one line). Ensure that a page break does not occur after the first line of a paragraph (orphans), if necessary, using slightly longer page sizes. Similarly, ensure that a page break does not occur before the last line of a paragraph (widows).
Keep Section Heading Contiguous:
Do not insert a page break immediately after a section heading. If there isn't room on a page for the first (two) lines of a section after the section heading, insert a page break before the heading.
Avoid Splitting Artwork:
Figures should not be split from figure titles. If possible, keep the figure on the same page as the (first) mention of the figure.
Headers for Long Tables after Page Breaks:
Another common option in producing paginated documents is to include the column headings of a table if the table cannot be displayed on a single page. Similarly, tables should not be split from the table titles.
keepWithNext and keepWithPrevious:
The XML attributes "keepWithNext" and "keepWithPrevious" should be used and followed whenever possible.
Whitespace Preservation:
The Unicode Points for XML entities such as Non-Breaking Space (nbsp) and Non-Breaking Hyphen (nbhy) should be followed as directed whenever possible.
ウィドウとオーファンの管理：
ウィドウとオーファン（<https://en.wikipedia.org/wiki/Widows_and_orphans>）は、自動的に回避すべきです（段落全体が1行しかない場合を除きます）。必要であればページサイズを少し長くしてでも、段落の最初の行の後で改ページが起こらないようにします（オーファン）。同様に、段落の最後の行の前で改ページが起こらないようにします（ウィドウ）。
セクション見出しを続けて配置する：
セクション見出しの直後に改ページを挿入しないでください。セクション見出しの後に、そのセクションの最初の（2）行を置く余地がページにない場合は、見出しの前に改ページを挿入します。
アートワークの分割を避ける：
図を図のタイトルから分離すべきではありません。可能であれば、図をその図に（最初に）言及している箇所と同じページに置きます。
改ページ後の長い表のヘッダー：
ページ分割された文書を作成する際のもう1つの一般的なオプションは、表が1ページに収まらない場合に表の列見出しを含めることです。同様に、表を表のタイトルから分離すべきではありません。
keepWithNextとkeepWithPrevious：
XMLの属性「keepWithNext」と「keepWithPrevious」は、可能な限り使用し、それに従うべきです。
空白の保持：
ノーブレークスペース（nbsp）やノーブレークハイフン（nbhy）などのXMLエンティティーのUnicodeコードポイントには、可能な限り指示どおりに従うべきです。

Appendix C. Tooling

Appendix C. ツール

This section discusses tools for viewing, comparing, creating, manipulating, and transforming PDF files, including those currently in use by the RFC Editor and Internet-Drafts, as well as outlining available PDF tools for various processes.

このセクションでは、RFCエディターとインターネットドラフトで現在使われているものを含め、PDFファイルを表示、比較、作成、操作、変換するためのツールについて議論し、さまざまなプロセスで利用可能なPDFツールの概要を示します。

C.1. PDF Viewers

C.1. PDFビューアー

As with most file formats, PDF files are experienced through a reader or viewer of PDF files. For most of the common platforms in use (iOS, OS X, Windows, Android, ChromeOS, Kindle) and for most browsers (Edge, Safari, Chrome, Firefox), PDF viewing is built in. In addition there are many PDF viewers available for download and installation.

ほとんどのファイル形式と同様に、PDFファイルはPDFファイルのリーダーやビューアーを通じて閲覧されます。一般に使われているプラットフォームのほとんど（iOS、OS X、Windows、Android、ChromeOS、Kindle）とほとんどのブラウザー（Edge、Safari、Chrome、Firefox）には、PDFの表示機能が組み込まれています。さらに、ダウンロードしてインストールできるPDFビューアーも数多くあります。

PDF viewers vary in capabilities, and it is important to note which PDF viewers support the features utilized in PDF RFCs and Internet-Drafts (features such as links, digital signatures, Tagged PDF, and others mentioned in Section 3).

PDFビューアーの機能はさまざまであり、PDF形式のRFCとインターネットドラフトで利用される機能（リンク、デジタル署名、タグ付きPDF、その他Section 3で言及した機能など）をどのPDFビューアーがサポートしているかに注意することが重要です。

C.2. Printers

C.2. プリンター

While almost all viewers also support the printing of PDF files, printing is one of the most important use cases for PDFs. Some printers have direct PDF support.

ほとんどすべてのビューアーはPDFファイルの印刷もサポートしていますが、印刷はPDFの最も重要なユースケースの1つです。PDFを直接サポートしているプリンターもあります。

C.3. PDF Generation Libraries

C.3. PDF生成ライブラリー

Because the xml2rfc format is a unique format, software for converting XML source documents to the various formats will be needed, including PDF generation.

xml2rfc形式は独自の形式であるため、XMLソース文書をさまざまな形式に変換するソフトウェアが必要になり、そこにはPDFの生成も含まれます。

One promising direction is suggested in <http://greenbytes.de/tech/webdav/rfc2629xslt/rfc2629xslt.html#output.pdf.fop>: using XSLT (Extensible Stylesheet Language Transformations) to generate XSL-FO (XSL Formatting Objects); XSL-FO is then processed by a FOP (Formatting Objects Processor) such as Apache FOP.

有望な方向性の1つが<http://greenbytes.de/tech/webdav/rfc2629xslt/rfc2629xslt.html#output.pdf.fop>で提案されています。それは、XSLT（Extensible Stylesheet Language Transformations）を使ってXSL-FO（XSL Formatting Objects）を生成するというものです。そのXSL-FOを、Apache FOPなどのFOP（Formatting Objects Processor）で処理します。

Several libraries are also available for generating PDF signatures. The choice of library to use for xml2pdf will depend on many factors: programming language, quality of implementation, quality of PDF generated, support, cost, availability, and so forth.

PDFの署名を生成するためのライブラリーもいくつか利用できます。xml2pdfにどのライブラリーを使うかの選択は、プログラミング言語、実装の品質、生成されるPDFの品質、サポート、コスト、入手しやすさなど、多くの要因に左右されます。

C.5. Other Tools

C.5. その他のツール

In addition to generating and viewing PDF, other categories of PDF tools are available and may be useful both during specification development and for published RFCs. These include tools for comparing two PDFs, checkers that could be used to validate the results of conversion, reviewing and commentary tools that attach annotations to PDF files, and digital signature creation and validation.

PDFの生成と表示に加えて、他の種類のPDFツールも利用でき、仕様の策定中と公開済みのRFCの両方で役立つ可能性があります。これには、2つのPDFを比較するツール、変換結果の検証に使えるチェッカー、PDFファイルに注釈を付けるレビューツールやコメントツール、デジタル署名の作成と検証などが含まれます。

Validation of an arbitrary author-generated PDF file would be quite difficult; there are few PDF validation tools. However, if RFCs and Internet-Drafts are generated by conversion from XML via xml2rfc, then explicit validation of PDF and adherence to expected profiles would mainly be useful to ensure that xml2rfc has functioned properly.

著者が生成した任意のPDFファイルの検証は非常に難しいでしょう。PDFの検証ツールはほとんどありません。しかし、RFCとインターネットドラフトがxml2rfcを介してXMLからの変換によって生成されるのであれば、PDFの明示的な検証と想定されるプロファイルへの準拠は、主にxml2rfcが正しく機能したことを確認するのに役立つでしょう。

Recommendation:
Discourage (but allow) submission of a PDF representation for Internet-Drafts. In most cases, the PDF for an Internet-Draft should be produced automatically when XML is submitted, with an opportunity to verify the conversion.
推奨事項：
インターネットドラフトのPDF表現の提出は、推奨しない（ただし許可する）ようにします。ほとんどの場合、インターネットドラフトのPDFは、XMLが提出されたときに自動的に作成し、変換結果を確認する機会を設けるべきです。
