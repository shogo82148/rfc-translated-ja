RFC 44

Comments on NWG/RFC 33 and 36

RFC 44

NWG/RFC 33および36へのコメント

Abstract

概要

Generally, we are satisfied with the suggestions for the new Host-to-Host protocol. However, we think that a few refinements may be helpful.

全体として、私たちは新しいホスト間（Host-to-Host）プロトコルについての提案に満足しています。しかし、いくつかの改良が役に立つかもしれないと考えています。

  1. It seems that there are two cases of reconnection:

    1. Reconnect from a socket in a local Host to another socket in the local Host. This was referred to in RFC #33 as "switch". The local sockets can belong to different processes (such as the "Login" process switching a connection to another process just created) or can belong to the same process (such as a process that accepts calls for connections on a particular socket, and after a connection is established switches to another of his sockets).
    2. Reconnect from a socket at a local Host to a socket in a foreign Host.

    We suggest separation of these two cases for the following reasons:

    1. Reconnection in Case 1 is necessary and useful, while the usefulness of Case 2 is still in doubt.
    2. Case 1 is simple to implement (at least conceptually) while Case 2 involves an elaborate mechanism of commands because of the asynchronous nature of the network (four out of nine commands were suggested to handle Case 2 in RFC #36).

    Thus we think that at least in the first usage of the Host-to-Host protocol reconnection in Case 2 should be left out. An additional system call (not a command) is therefore needed to permit Case 1, which is SWITCH <socket 1> <socket 2>.

  2. The CLOSE command as suggested in RFC #36 seems to be used for two purposes: block a connection and abort a connection. To avoid ambiguity it would be desirable to have two commands: BLOCK and CLOSE. As suggested in RFC #36, the response for both commands can be the SUSPEND command which acknowledges the reception of BLOCK or CLOSE commands.
  3. After a connection has been established, we see no reason for keeping the "foreign socket" in a local connection table. Since there is a one-to-one correspondence between a link number of the foreign Host and a foreign socket number, we can use the link number in the commands. Thus, except for the RFC command, all commands can use link numbers and therefore eliminate a 40-bit foreign socket number in every entry of the connection table (size being critical for some Hosts). We note that if connections will be multiplexed over links as suggested in RFC #38, then the foreign socket would be needed in the connection table.
  4. In RFC#33 the term PORT was introduced. Although this is private to every Host, we have a comment. If ports are used such that there is a one-to-one correspondence between a port for some user and a socket, then ports are completely redundant. However, a Host may wish to multiplex ports over connections, in which case an additional mechanism is needed.

  1. 再接続には2つのケースがあるようです。

    1. ローカルホストのソケットから、同じローカルホストの別のソケットへの再接続。これはRFC #33では「切り替え（switch）」と呼ばれていました。ローカルのソケットは、異なるプロセスに属する場合（たとえば、「Login」プロセスが、作成したばかりの別のプロセスに接続を切り替える場合）もあれば、同じプロセスに属する場合（たとえば、特定のソケットで接続の呼び出しを受け付け、接続が確立した後で自分の別のソケットに切り替えるプロセスの場合）もあります。
    2. ローカルホストのソケットから、外部ホストのソケットへの再接続。

    私たちは、次の理由から、これら2つのケースを分けることを提案します。

    1. ケース1の再接続は必要かつ有用ですが、ケース2の有用性はまだ疑わしいです。
    2. ケース1は（少なくとも概念的には）実装が簡単ですが、ケース2はネットワークの非同期的な性質のために、コマンドによる複雑なメカニズムを必要とします（RFC #36では、9個のコマンドのうち4個がケース2を扱うために提案されていました）。

    したがって、少なくともホスト間プロトコルの最初の使用においては、ケース2の再接続は除外すべきだと考えます。そのため、ケース1を可能にするために、SWITCH <socket 1> <socket 2>というシステムコール（コマンドではありません）を追加する必要があります。

  2. RFC #36で提案されたCLOSEコマンドは、接続のブロックと接続の中断という2つの目的に使われているようです。曖昧さを避けるために、BLOCKとCLOSEという2つのコマンドがあることが望ましいでしょう。RFC #36で提案されているように、どちらのコマンドに対する応答も、BLOCKコマンドまたはCLOSEコマンドの受信を確認するSUSPENDコマンドとすることができます。
  3. 接続が確立された後は、ローカルの接続テーブルに「外部ソケット（foreign socket）」を保持しておく理由はないと考えます。外部ホストのリンク番号と外部ソケット番号は1対1に対応しているので、コマンドではリンク番号を使用できます。したがって、RFCコマンドを除くすべてのコマンドでリンク番号を使用でき、接続テーブルのすべてのエントリーから40ビットの外部ソケット番号をなくすことができます（ホストによってはサイズが重要です）。なお、RFC #38で提案されているように接続がリンク上で多重化される場合は、接続テーブルに外部ソケットが必要になることに注意してください。
  4. RFC#33では、ポート（PORT）という用語が導入されました。これは各ホストに固有のものですが、1つコメントがあります。あるユーザーのポートとソケットが1対1に対応するようにポートを使用するのであれば、ポートは完全に冗長です。しかし、ホストが接続上でポートを多重化したい場合もあり、その場合には追加のメカニズムが必要になります。

To summarize the last four comments, we suggest that in the initial version the following system calls and commands will be used (most of them in RFC 33 and 36).

ここまでの4つのコメントをまとめると、最初のバージョンでは次のシステムコールとコマンドを使用することを提案します（そのほとんどはRFC 33と36にあるものです）。

System Calls:

システムコール:

  1. INITIATE <my socket> <your socket>
  2. ACCEPT <my socket>
  3. SWITCH <socket 1> <socket 2>
  4. LISTEN <my socket>
  5. CLOSE <my socket>
  6. TRANSMIT <my socket> <address>
  1. INITIATE <my socket> <your socket>
  2. ACCEPT <my socket>
  3. SWITCH <socket 1> <socket 2>
  4. LISTEN <my socket>
  5. CLOSE <my socket>
  6. TRANSMIT <my socket> <address>

Commands:

コマンド:

Commands 0, 1, 3, 4 as in RFC #36 (pp.5) and in addition:

RFC #36（5ページ）にあるコマンド0、1、3、4に加えて、次のコマンドを使用します。

  1. BLOCK: BLK <link>
  2. CLOSE: CLS <link>
  1. BLOCK: BLK <link>
  2. CLOSE: CLS <link>

  1. In addition to the above it seems necessary to decide on the following issues one way or the other together with the first version of the protocol (perhaps by setting a date for people to express their preferences and decide accordingly). All of these issues were mentioned in the meeting at UCLA on March 17, 1970, but were put aside.

    1. "Double padding" - when a message does not end on a word boundary. Two possible solutions were mentioned:

      1. Hosts provide their padding in addition to the IMP's padding (double padding).
      2. Hosts make sure that all messages end on a word boundary by shifting their messages (when necessary) and adjusting the "marking" accordingly.

    2. "Echoing" - there are three apparent possibilities:

      1. Echoing
      2. No echoing
      3. Optional Echoing - possibly a bit in the "Leader" can be used to designate this option.
    3. "Code Conversion" - originally, BB&N suggested doing the conversion in the IMPs using ASCII-8 as the common code. This was rejected, mainly because of claims that ASCII-8 is not large enough for some uses, such as graphics. Also conversion in the IMPs may slow them down and take up space which could be used for buffers. We feel that it is very desirable to have a common code (even when the conversion is not done by the IMPs), such that all incoming text messages are in the same code and only one conversion table is needed. Outgoing text messages should be converted into this common code. Obviously, the option "no translation" should be possible for the purpose of binary data or data that is not representable in the common code. Since every known code can be considered to be too restrictive for some purposes, we suggest adopting a Network Common Code (NCC), and use all of the 256 possible characters (for 8-bit code) to include the "important" part of the union of the codes used throughout the network.

  2. Our preference to the above issues is as follows:

    1. "Double padding" -it turns out to be easy for us to get our messages to be sent on a word boundary by shifting the leader of a message (and adjusting the "marking" accordingly) rather than the data. Thus we will prefer solution V.1.b).
    2. "Echoing" - we prefer no echoing. We think that character echoing should be managed locally.
    3. "Code Conversion" we prefer a Network Common Code. Initially, ASCII-8 can be used, and then expanded according to the needs of the Network.

  1. 上記に加えて、プロトコルの最初のバージョンとあわせて、次の問題についてどちらかに決める必要があるようです（たとえば、各自が希望を表明する期日を設け、それに従って決めるなど）。これらの問題はすべて1970年3月17日のUCLAでの会合で話題に上りましたが、保留とされました。

    1. 「二重パディング（Double padding）」 - メッセージがワード境界で終わらない場合の問題です。2つの解決策が挙げられました。

      1. ホストが、IMPのパディングに加えて独自のパディングを付ける（二重パディング）。
      2. ホストが、（必要に応じて）メッセージをシフトし、それに合わせて「マーキング（marking）」を調整することで、すべてのメッセージがワード境界で終わるようにする。

    2. 「エコー（Echoing）」 - 明らかに3つの可能性があります。

      1. エコーする
      2. エコーしない
      3. オプションのエコー - 「リーダー（Leader）」の1ビットを使ってこのオプションを指定できるかもしれません。
    3. 「コード変換（Code Conversion）」 - もともとBB&Nは、ASCII-8を共通コードとして使い、IMPで変換を行うことを提案しました。この案は、主にASCII-8はグラフィックスなど一部の用途には十分な大きさではないという主張によって却下されました。また、IMPで変換を行うとIMPの速度が落ち、バッファーに使えたはずの領域を消費するおそれもあります。私たちは、（IMPが変換を行わない場合でも）共通コードを持ち、受信するすべてのテキストメッセージが同じコードになり、変換テーブルが1つで済むようにすることが非常に望ましいと考えています。送信するテキストメッセージは、この共通コードに変換すべきです。当然ながら、バイナリーデータや共通コードで表現できないデータのために、「変換なし」のオプションも可能であるべきです。既知のコードはどれも何らかの用途には制限が強すぎるとみなされうるので、私たちはネットワーク共通コード（NCC: Network Common Code）を採用し、（8ビットのコードで）可能な256文字すべてを使って、ネットワーク全体で使用されているコードの和集合のうち「重要な」部分を含めることを提案します。

  2. 上記の問題に対する私たちの希望は次のとおりです。

    1. 「二重パディング」 - 私たちにとっては、データではなくメッセージのリーダーをシフトする（そしてそれに合わせて「マーキング」を調整する）ことで、メッセージがワード境界で送られるようにするのが簡単だとわかりました。したがって、解決策V.1.b)を希望します。
    2. 「エコー」 - エコーしないことを希望します。文字のエコーはローカルで管理すべきだと考えます。
    3. 「コード変換」 - ネットワーク共通コードを希望します。最初はASCII-8を使用し、その後ネットワークの必要に応じて拡張できます。
