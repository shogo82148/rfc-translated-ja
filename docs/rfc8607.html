Calendaring Extensions to WebDAV (CalDAV): Managed Attachments

RFC 8607

Calendaring Extensions to WebDAV（CalDAV）：管理された添付ファイル

Abstract

概要

This specification adds an extension to the Calendaring Extensions to WebDAV (CalDAV) to allow attachments associated with iCalendar data to be stored and managed on the server.

この仕様は、iCalendarデータに関連付けられた添付ファイルをサーバー上に保存して管理できるようにするため、Calendaring Extensions to WebDAV（CalDAV）に拡張を追加します。

This specification documents existing code deployed by multiple vendors. It is published as an Informational specification rather than Standards Track due to its noncompliance with multiple best current practices of HTTP.

この仕様は、複数のベンダーが展開している既存のコードを文書化したものです。この仕様はHTTPの複数のベストカレントプラクティスに準拠していないため、標準化過程（Standards Track）ではなく情報提供（Informational）の仕様として公開されています。

1. Introduction

1. はじめに

The iCalendar [RFC5545] data format is used to represent calendar data and is used with iCalendar Transport-independent Interoperability Protocol (iTIP) [RFC5546] to handle scheduling operations between calendar users.

iCalendar [RFC5545]データ形式は、カレンダーデータを表現するために使用され、カレンダーユーザー間のスケジューリング操作を処理するためにiCalendar Transport-independent Interoperability Protocol（iTIP）[RFC5546]とともに使用されます。

[RFC4791] defines the Calendaring Extensions to WebDAV (CalDAV), based on HTTP [RFC7230], for accessing calendar data stored on a server.

[RFC4791]は、サーバー上に保存されたカレンダーデータにアクセスするための、HTTP [RFC7230]にもとづくCalendaring Extensions to WebDAV（CalDAV）を定義しています。

Calendar users often want to include attachments with their calendar data events or tasks (for example, a copy of a presentation or the meeting agenda). iCalendar provides an "ATTACH" property whose value is either the inline Base64 encoded attachment data or a URL specifying the location of the attachment data.

カレンダーユーザーは、カレンダーデータのイベントやタスクに添付ファイル（たとえば、プレゼンテーションのコピーや会議のアジェンダ）を含めたいことがよくあります。iCalendarは「ATTACH」プロパティーを提供しており、その値は、インラインでBase64エンコードされた添付ファイルのデータか、添付ファイルのデータの場所を指定するURLのいずれかです。

Use of inline attachment data is not ideal with CalDAV because the data would need to be uploaded to the server each time a change to the calendar data is made, even minor changes such as a change to the summary. Whilst a client could choose to use a URL value instead, the problem then becomes where and how the client discovers an appropriate URL to use and how it ensures that only those attendees listed in the event or task are able to access it.

インラインの添付ファイルのデータを使用することは、CalDAVでは理想的ではありません。カレンダーデータに変更を加えるたびに、それが概要（summary）の変更のような小さな変更であっても、そのデータをサーバーにアップロードする必要があるからです。クライアントは代わりにURL値を使用することを選択できますが、その場合は、使用する適切なURLをクライアントがどこでどのように発見するのか、そしてイベントやタスクに列挙された出席者だけがそれにアクセスできることをどのように保証するのかが問題になります。

This specification solves this problem by having the client send the attachment to the server, separately from the iCalendar data, and having the server add appropriate "ATTACH" properties in the iCalendar data as well as manage access privileges. The server can also provide additional information to the client about each attachment in the iCalendar data, such as the size and an identifier.

この仕様は、クライアントが添付ファイルをiCalendarデータとは別にサーバーに送信し、サーバーがiCalendarデータに適切な「ATTACH」プロパティーを追加するとともにアクセス特権を管理するようにすることで、この問題を解決します。サーバーは、iCalendarデータ内の各添付ファイルに関する追加情報（サイズや識別子など）をクライアントに提供することもできます。

1.1. Rationale for Informational Status

1.1. 情報提供（Informational）とする理由

Although this extension to CalDAV has wide deployment, its design does not comply with some of the best current practices of HTTP, namely:

CalDAVに対するこの拡張は広く展開されていますが、その設計はHTTPのベストカレントプラクティスのいくつかに準拠していません。具体的には次のとおりです。

  • All operations on attachments are modeled as HTTP POST operations, where the actual type of operation is specified using a query parameter instead of using separate HTTP POST, PUT, and DELETE methods where appropriate.
  • Specific query strings are hardwired into the protocol in violation of Section 2.4 of [RFC7320].
  • 添付ファイルに対するすべての操作はHTTP POST操作としてモデル化されており、必要に応じてHTTPのPOST、PUT、DELETEメソッドを使い分けるのではなく、実際の操作の種類をクエリーパラメーターで指定します。
  • [RFC7320]のSection 2.4に違反して、特定のクエリー文字列がプロトコルに固定的に組み込まれています。

Additionally, this extension misuses the Content-Disposition header field [RFC6266] as a request header field to convey a filename for an attachment rather than using an existing request header field suitable for that purpose, such as "Slug" (see Section 9.7 of [RFC5023]).

さらに、この拡張は、添付ファイルのファイル名を伝えるために、その目的に適した既存のリクエストヘッダーフィールド（「Slug」など。[RFC5023]のSection 9.7を参照）を使用するのではなく、Content-Dispositionヘッダーフィールド[RFC6266]をリクエストヘッダーフィールドとして誤用しています。

Rather than creating interoperability problems with deployed code by updating the design of this extension to be compliant with best current practices and to allow this specification to be placed on the Standards Track, it was decided to simply document how existing implementations interoperate and to publish the document as Informational.

この拡張の設計をベストカレントプラクティスに準拠するように更新し、この仕様を標準化過程（Standards Track）に載せられるようにすることで展開済みのコードとの相互運用性の問題を生み出すのではなく、既存の実装がどのように相互運用しているかを単に文書化し、この文書を情報提供（Informational）として公開することが決定されました。

3. Overview

3. 概要

There are four main operations a client needs to perform with attachments for calendar data: add, update, remove, and retrieve. The first three operations are carried out by the client issuing an HTTP POST request on the calendar object resource to which the attachment is associated and specifying the appropriate "action" query parameter (see Section 3.3). In the case of the remove operation, the client can alternatively directly update the calendar object resource and remove the relevant "ATTACH" properties (see Section 3.9). The retrieve operation is accomplished by simply issuing an HTTP GET request targeting the attachment URI specified by the calendar resource's "ATTACH" property (see Section 3.10).

クライアントがカレンダーデータの添付ファイルに対して行う必要のある主な操作は、追加、更新、削除、取得の4つです。最初の3つの操作は、クライアントが、添付ファイルが関連付けられているカレンダーオブジェクトリソースに対して、適切な「action」クエリーパラメーター（Section 3.3を参照）を指定したHTTP POSTリクエストを発行することで実行されます。削除操作の場合は、代わりにクライアントがカレンダーオブジェクトリソースを直接更新して、該当する「ATTACH」プロパティーを削除することもできます（Section 3.9を参照）。取得操作は、カレンダーリソースの「ATTACH」プロパティーで指定された添付ファイルURIをターゲットとするHTTP GETリクエストを発行するだけで実現できます（Section 3.10を参照）。

iCalendar data stored in a CalDAV calendar object resource can contain multiple components when recurrences are involved. In such a situation, the client needs to be able to target a specific recurrence instance or multiple instances when adding or deleting attachments. As a result, the POST request needs to provide a way for the client to specify which recurrence instances should be targeted for the attachment operation. This is accomplished through use of additional query parameters on the POST Request-URI.

CalDAVのカレンダーオブジェクトリソースに保存されたiCalendarデータは、繰り返しが関係する場合、複数のコンポーネントを含むことがあります。そのような状況では、クライアントは添付ファイルを追加または削除する際に、特定の繰り返しインスタンスまたは複数のインスタンスをターゲットにできる必要があります。そのため、POSTリクエストは、添付ファイルの操作のターゲットとすべき繰り返しインスタンスをクライアントが指定する方法を提供する必要があります。これは、POSTのRequest-URIに追加のクエリーパラメーターを使用することで実現されます。

3.1. Requirements

3.1. 要件

A server that supports the features described in this specification is REQUIRED to support the CalDAV "calendar-access" [RFC4791] features.

この仕様で説明する機能をサポートするサーバーは、CalDAVの「calendar-access」[RFC4791]機能をサポートすることが要求されています（REQUIRED）。

In addition, such a server SHOULD support the "return=representation" Prefer header field [RFC7240] preference on successful HTTP PUT and POST requests targeting existing calendar object resources by returning the new representation of that calendar resource (including its new ETag header field value) in the response.

さらに、そのようなサーバーは、既存のカレンダーオブジェクトリソースをターゲットとするHTTPのPUTおよびPOSTリクエストが成功したときに、そのカレンダーリソースの新しい表現（新しいETagヘッダーフィールド値を含む）をレスポンスで返すことで、Preferヘッダーフィールド[RFC7240]の「return=representation」優先設定（preference）をサポートすべきです（SHOULD）。

3.2. Discovering Support for Managed Attachments

3.2. 管理された添付ファイルのサポートの発見

A server supporting the features described in this specification MUST include "calendar-managed-attachments" as a token in the DAV response header field (as defined in Section 10.1 of [RFC4918]) from an OPTIONS request on a calendar home collection.

この仕様で説明する機能をサポートするサーバーは、カレンダーホームコレクションに対するOPTIONSリクエストへのレスポンスのDAVヘッダーフィールド（[RFC4918]のSection 10.1で定義）に、トークンとして「calendar-managed-attachments」を含めなければなりません（MUST）。

A server might choose not to support the storing of managed attachments on a per-recurrence-instance basis (i.e., they can only be added to all instances as a whole). If that is the case, the server MUST also include "calendar-managed-attachments-no-recurrence" as a token in the DAV response header field from an OPTIONS request on a calendar home collection. When that field is present, clients MUST NOT attempt any managed attachment operations that target specific recurrence instances.

サーバーは、管理された添付ファイルを繰り返しインスタンスごとに保存すること（つまり、添付ファイルはすべてのインスタンス全体に対してのみ追加できる）をサポートしないことを選択する場合があります。その場合、サーバーは、カレンダーホームコレクションに対するOPTIONSリクエストへのレスポンスのDAVヘッダーフィールドに、トークンとして「calendar-managed-attachments-no-recurrence」も含めなければなりません（MUST）。そのフィールドが存在する場合、クライアントは、特定の繰り返しインスタンスをターゲットとする管理された添付ファイルの操作を試みてはなりません（MUST NOT）。

3.3. POST Request for Managing Attachments

3.3. 添付ファイルを管理するためのPOSTリクエスト

An HTTP POST request is used to add, update, or remove attachments. These requests are subject to the preconditions listed in Section 3.11. The Request-URI will contain various query parameters to specify the behavior.

添付ファイルの追加、更新、削除にはHTTP POSTリクエストを使用します。これらのリクエストには、Section 3.11に列挙する事前条件が適用されます。Request-URIには、振る舞いを指定するためのさまざまなクエリーパラメーターが含まれます。

3.3.1. action Query Parameter

3.3.1. actionクエリーパラメーター

The "action" query parameter is used to identify which attachment operation the client is requesting. This parameter MUST be present once on each POST request used to manage attachments. One of these three values MUST be used:

「action」クエリーパラメーターは、クライアントがどの添付ファイルの操作を要求しているかを識別するために使用されます。このパラメーターは、添付ファイルを管理するために使用する各POSTリクエストに1回だけ存在しなければなりません（MUST）。次の3つの値のいずれかを使用しなければなりません（MUST）。

attachment-add:
Indicates an operation that is adding an attachment to a calendar object resource. See Section 3.4 for more details.
attachment-update:
Indicates an operation that is updating an existing attachment on a calendar object resource. See Section 3.5 for more details.
attachment-remove:
Indicates an operation that is removing an attachment from a calendar object resource. See Section 3.6 for more details.
attachment-add:
カレンダーオブジェクトリソースに添付ファイルを追加する操作であることを示します。詳細はSection 3.4を参照してください。
attachment-update:
カレンダーオブジェクトリソース上の既存の添付ファイルを更新する操作であることを示します。詳細はSection 3.5を参照してください。
attachment-remove:
カレンダーオブジェクトリソースから添付ファイルを削除する操作であることを示します。詳細はSection 3.6を参照してください。

Example:

例：

https://calendar.example.com/events/1.ics?action=attachment-add

https://calendar.example.com/events/1.ics?action=attachment-add

3.3.2. rid Query Parameter

3.3.2. ridクエリーパラメーター

The "rid" query parameter is used to identify which recurrence instances are being targeted by the client for the attachment operation. This query parameter MUST contain one or more items, separated by commas (denoted in ASCII as "0x2C"). The item values can be in one of two forms:

「rid」クエリーパラメーターは、クライアントが添付ファイルの操作のターゲットとしている繰り返しインスタンスを識別するために使用されます。このクエリーパラメーターは、カンマ（ASCIIで「0x2C」と表記）で区切られた1つ以上の項目を含まなければなりません（MUST）。項目の値は、次の2つの形式のいずれかです。

Master instance:
The value "M" (case insensitive) refers to the "master" recurrence instance, i.e., the component that does not include a "RECURRENCE-ID" property. This item MUST be present only once.
Specific instance:
A specific iCalendar instance is targeted by using its "RECURRENCE-ID" value as the item value. That value MUST correspond to the "RECURRENCE-ID" value as stored in the calendar object resource (i.e., without any conversion to UTC). If multiple items of this form are used, they MUST be unique values. For example, to target a recurrence defined by property RECURRENCE-ID;TZID=America/Montreal:20111022T160000, the query parameter rid=20111022T160000 would be used.
マスターインスタンス：

3.4. Adding Attachments

3.4. 添付ファイルの追加

To add an attachment to an existing calendar object resource, the following needs to occur:

既存のカレンダーオブジェクトリソースに添付ファイルを追加するには、次のことを行う必要があります。

  1. The client issues a POST request targeted at the calendar object resource structured as follows:

    1. The Request-URI will include an "action" query parameter with the value "attachment-add" (see Section 3.3.1).
    2. If all recurrence instances are having an attachment added, the "rid" query parameter is not present in the Request-URI. If one or more specific recurrence instances are targeted, then the Request-URI will include a "rid" query parameter containing the list of instances (see Section 3.3.2).
    3. The body of the request contains the data for the attachment.
    4. The client MUST include a valid Content-Type header field describing the media type of the attachment (as required by HTTP).
    5. The client SHOULD include a Content-Disposition header field [RFC6266] with a "type" parameter set to "attachment", and a "filename" parameter that indicates the name of the attachment. Note that the use of Content-Disposition as a request header field is nonstandard and specific to this protocol.
    6. The client MAY include a Prefer header field [RFC7240] with the "return=representation" preference to request that the modified calendar object resource be returned as the body of a successful response to the POST request.

  2. When the server receives the POST request, it does the following:

    1. Validates that any recurrence instances referred to via the "rid" query parameter are valid for the calendar object resource being targeted.
    2. Stores the supplied attachment data into a resource and generates an appropriate URI for clients to access the resource.
    3. For each affected recurrence instance in the calendar object resource targeted by the request, adds an "ATTACH" property whose value is the URI of the stored attachment. The "ATTACH" property MUST contain a "MANAGED-ID" property parameter whose value is a unique identifier (within the context of the server as a whole). The "ATTACH" property SHOULD contain an "FMTTYPE" property parameter whose value matches the Content-Type header field value from the request. The "ATTACH" property SHOULD contain a "FILENAME" property parameter whose value matches the value of the Content-Disposition header field "filename" parameter value from the request, taking into account the restrictions expressed in Section 4.2. The "ATTACH" property SHOULD include a "SIZE" property parameter whose value represents the size in octets of the attachment. If a specified recurrence instance does not have a matching component in the calendar object resource, then the server MUST modify the calendar object resource to include an overridden component with the appropriate "RECURRENCE-ID" property.
    4. Upon successful creation of the attachment resource, and modification of the targeted calendar object resource, it MUST return an appropriate HTTP success status response and include a "Cal-Managed-ID" header field containing the "MANAGED-ID" property parameter value of the newly created "ATTACH" property. The client can use the "Cal-Managed-ID" header field value to correlate the attachment with "ATTACH" properties added to the calendar object resource. If the client included a Prefer header field with the "return=representation" preference in the request, the server SHOULD return the modified calendar object resource as the body of the response. Otherwise, the server can expect that the client will reload the calendar object resource with a subsequent GET request to refresh any local cache.

  1. クライアントは、カレンダーオブジェクトリソースをターゲットとし、次のように構成したPOSTリクエストを発行します。

    1. Request-URIには、値「attachment-add」を持つ「action」クエリーパラメーターが含まれます（Section 3.3.1を参照）。
    2. すべての繰り返しインスタンスに添付ファイルを追加する場合、Request-URIに「rid」クエリーパラメーターは存在しません。1つ以上の特定の繰り返しインスタンスをターゲットとする場合、Request-URIには、インスタンスのリストを含む「rid」クエリーパラメーターが含まれます（Section 3.3.2を参照）。
    3. リクエストのボディーには添付ファイルのデータが含まれます。
    4. クライアントは、（HTTPが要求するとおり）添付ファイルのメディアタイプを記述する有効なContent-Typeヘッダーフィールドを含めなければなりません（MUST）。
    5. クライアントは、「type」パラメーターを「attachment」に設定し、添付ファイルの名前を示す「filename」パラメーターを持つContent-Dispositionヘッダーフィールド[RFC6266]を含めるべきです（SHOULD）。Content-Dispositionをリクエストヘッダーフィールドとして使用することは非標準であり、このプロトコルに固有であることに注意してください。
    6. クライアントは、変更されたカレンダーオブジェクトリソースをPOSTリクエストに対する成功レスポンスのボディーとして返すよう要求するために、「return=representation」優先設定を持つPreferヘッダーフィールド[RFC7240]を含めてもよいです（MAY）。

  2. サーバーは、POSTリクエストを受信すると、次のことを行います。

    1. 「rid」クエリーパラメーターで参照されている繰り返しインスタンスが、ターゲットとなるカレンダーオブジェクトリソースにとって有効であることを検証します。
    2. 提供された添付ファイルのデータをリソースに保存し、クライアントがそのリソースにアクセスするための適切なURIを生成します。
    3. リクエストのターゲットとなるカレンダーオブジェクトリソース内の影響を受ける各繰り返しインスタンスについて、保存された添付ファイルのURIを値とする「ATTACH」プロパティーを追加します。「ATTACH」プロパティーは、（サーバー全体のコンテキストで）一意な識別子を値とする「MANAGED-ID」プロパティーパラメーターを含まなければなりません（MUST）。「ATTACH」プロパティーは、リクエストのContent-Typeヘッダーフィールド値と一致する値を持つ「FMTTYPE」プロパティーパラメーターを含むべきです（SHOULD）。「ATTACH」プロパティーは、Section 4.2で述べる制限を考慮したうえで、リクエストのContent-Dispositionヘッダーフィールドの「filename」パラメーター値と一致する値を持つ「FILENAME」プロパティーパラメーターを含むべきです（SHOULD）。「ATTACH」プロパティーは、添付ファイルのサイズをオクテット単位で表す値を持つ「SIZE」プロパティーパラメーターを含むべきです（SHOULD）。指定された繰り返しインスタンスに一致するコンポーネントがカレンダーオブジェクトリソースに存在しない場合、サーバーは、適切な「RECURRENCE-ID」プロパティーを持つオーバーライドされたコンポーネントを含むようにカレンダーオブジェクトリソースを変更しなければなりません（MUST）。
    4. 添付ファイルリソースの作成と、ターゲットとなるカレンダーオブジェクトリソースの変更が成功したら、サーバーは、適切なHTTPの成功ステータスのレスポンスを返し、新しく作成された「ATTACH」プロパティーの「MANAGED-ID」プロパティーパラメーター値を含む「Cal-Managed-ID」ヘッダーフィールドを含めなければなりません（MUST）。クライアントは、「Cal-Managed-ID」ヘッダーフィールド値を使用して、添付ファイルと、カレンダーオブジェクトリソースに追加された「ATTACH」プロパティーとを対応付けることができます。クライアントがリクエストに「return=representation」優先設定を持つPreferヘッダーフィールドを含めていた場合、サーバーは、変更されたカレンダーオブジェクトリソースをレスポンスのボディーとして返すべきです（SHOULD）。そうでない場合、サーバーは、クライアントがローカルキャッシュを更新するために後続のGETリクエストでカレンダーオブジェクトリソースを再読み込みすると想定できます。

3.5. Updating Attachments

3.5. 添付ファイルの更新

When an attachment is updated, the server MUST change the associated "MANAGED-ID" property parameter and MAY change the "ATTACH" property value. With this approach, clients are able to determine when an attachment has been updated by some other client by looking for a change to either the "ATTACH" property value or the "MANAGED-ID" property parameter value.

添付ファイルが更新されたとき、サーバーは関連付けられた「MANAGED-ID」プロパティーパラメーターを変更しなければなりません（MUST）。また、「ATTACH」プロパティー値を変更してもよいです（MAY）。この方法により、クライアントは、「ATTACH」プロパティー値または「MANAGED-ID」プロパティーパラメーター値のいずれかの変更を探すことで、ほかのクライアントによって添付ファイルが更新されたことを判断できます。

To change the data of an existing managed attachment in a calendar object resource, the following needs to occur:

カレンダーオブジェクトリソース内の既存の管理された添付ファイルのデータを変更するには、次のことを行う必要があります。

  1. The client issues a POST request targeted at the calendar object resource structured as follows:

    1. The Request-URI will include an "action" query parameter with the value "attachment-update" (see Section 3.3.1).
    2. The Request-URI will include a "managed-id" query parameter with the value matching that of the "MANAGED-ID" property parameter for the "ATTACH" property being updated (see Section 3.3.3).
    3. The body of the request contains the updated data for the attachment.
    4. The client MUST include a valid Content-Type header field describing the media type of the attachment (as required by HTTP).
    5. The client SHOULD include a Content-Disposition header field [RFC6266] with a "type" parameter set to "attachment", and a "filename" parameter that indicates the name of the attachment.
    6. The client MAY include a Prefer header field [RFC7240] with the "return=representation" preference to request that the modified calendar object resource be returned as the body of a successful response to the POST request.

  2. When the server receives the POST request, it does the following:

    1. Validates that the "managed-id" query parameter is valid for the calendar object resource.
    2. Updates the content of the attachment resource corresponding to that "managed-id" value with the supplied attachment data.
    3. For each affected recurrence instance in the calendar object resource targeted by the request, updates the "ATTACH" property whose "MANAGED-ID" property parameter value matches the "managed-id" query parameter. The "MANAGED-ID" property parameter value is changed to allow other clients to detect the update, and the property value (attachment URI) might also be changed. The "ATTACH" property SHOULD contain a "FMTTYPE" property parameter whose value matches the Content-Type header field value from the request; this could differ from the original value if the media type of the updated attachment is different. The "ATTACH" property SHOULD contain a "FILENAME" property parameter whose value matches the Content-Disposition header field "filename" parameter value from the request, taking into account the restrictions expressed in Section 4.2. The "ATTACH" property SHOULD include a "SIZE" property parameter whose value represents the size in octets of the updated attachment.
    4. Upon successful update of the attachment resource, and modification of the targeted calendar object resource, it MUST return an appropriate HTTP success status response and include a "Cal-Managed-ID" header field containing the new value of the "MANAGED-ID" property parameter. The client can use the "Cal-Managed-ID" header field value to correlate the attachment with "ATTACH" properties added to the calendar object resource. If the client included a Prefer header field with the "return=representation" preference in the request, the server SHOULD return the modified calendar object resource as the body of the response. Otherwise, the server can expect that the client will reload the calendar object resource with a subsequent GET request to refresh any local cache.

  1. クライアントは、カレンダーオブジェクトリソースをターゲットとし、次のように構成したPOSTリクエストを発行します。

    1. Request-URIには、値「attachment-update」を持つ「action」クエリーパラメーターが含まれます（Section 3.3.1を参照）。
    2. Request-URIには、更新する「ATTACH」プロパティーの「MANAGED-ID」プロパティーパラメーターの値と一致する値を持つ「managed-id」クエリーパラメーターが含まれます（Section 3.3.3を参照）。
    3. リクエストのボディーには、添付ファイルの更新されたデータが含まれます。
    4. クライアントは、（HTTPが要求するとおり）添付ファイルのメディアタイプを記述する有効なContent-Typeヘッダーフィールドを含めなければなりません（MUST）。
    5. クライアントは、「type」パラメーターを「attachment」に設定し、添付ファイルの名前を示す「filename」パラメーターを持つContent-Dispositionヘッダーフィールド[RFC6266]を含めるべきです（SHOULD）。
    6. クライアントは、変更されたカレンダーオブジェクトリソースをPOSTリクエストに対する成功レスポンスのボディーとして返すよう要求するために、「return=representation」優先設定を持つPreferヘッダーフィールド[RFC7240]を含めてもよいです（MAY）。

  2. サーバーは、POSTリクエストを受信すると、次のことを行います。

    1. 「managed-id」クエリーパラメーターが、カレンダーオブジェクトリソースにとって有効であることを検証します。
    2. その「managed-id」値に対応する添付ファイルリソースのコンテンツを、提供された添付ファイルのデータで更新します。
    3. リクエストのターゲットとなるカレンダーオブジェクトリソース内の影響を受ける各繰り返しインスタンスについて、「MANAGED-ID」プロパティーパラメーター値が「managed-id」クエリーパラメーターと一致する「ATTACH」プロパティーを更新します。ほかのクライアントが更新を検出できるように「MANAGED-ID」プロパティーパラメーター値は変更されます。また、プロパティー値（添付ファイルURI）も変更される場合があります。「ATTACH」プロパティーは、リクエストのContent-Typeヘッダーフィールド値と一致する値を持つ「FMTTYPE」プロパティーパラメーターを含むべきです（SHOULD）。更新された添付ファイルのメディアタイプが異なる場合、これは元の値とは異なる可能性があります。「ATTACH」プロパティーは、Section 4.2で述べる制限を考慮したうえで、リクエストのContent-Dispositionヘッダーフィールドの「filename」パラメーター値と一致する値を持つ「FILENAME」プロパティーパラメーターを含むべきです（SHOULD）。「ATTACH」プロパティーは、更新された添付ファイルのサイズをオクテット単位で表す値を持つ「SIZE」プロパティーパラメーターを含むべきです（SHOULD）。
    4. 添付ファイルリソースの更新と、ターゲットとなるカレンダーオブジェクトリソースの変更が成功したら、サーバーは、適切なHTTPの成功ステータスのレスポンスを返し、「MANAGED-ID」プロパティーパラメーターの新しい値を含む「Cal-Managed-ID」ヘッダーフィールドを含めなければなりません（MUST）。クライアントは、「Cal-Managed-ID」ヘッダーフィールド値を使用して、添付ファイルと、カレンダーオブジェクトリソースに追加された「ATTACH」プロパティーとを対応付けることができます。クライアントがリクエストに「return=representation」優先設定を持つPreferヘッダーフィールドを含めていた場合、サーバーは、変更されたカレンダーオブジェクトリソースをレスポンスのボディーとして返すべきです（SHOULD）。そうでない場合、サーバーは、クライアントがローカルキャッシュを更新するために後続のGETリクエストでカレンダーオブジェクトリソースを再読み込みすると想定できます。

3.6. Removing Attachments via POST

3.6. POSTによる添付ファイルの削除

To remove an existing attachment from a calendar object, the following needs to occur:

カレンダーオブジェクトから既存の添付ファイルを削除するには、次のことを行う必要があります。

  1. The client issues a POST request targeted at the calendar object resource structured as follows:

    1. The Request-URI will include an "action" query parameter with the value "attachment-remove" (see Section 3.3.1).
    2. If all recurrence instances are having an attachment removed, the "rid" query parameter is not present in the Request-URI. If one or more specific recurrence instances are targeted, then the Request-URI will include a "rid" query parameter containing the list of instances (see Section 3.3.2).
    3. The Request-URI will include a "managed-id" query parameter with the value matching that of the "MANAGED-ID" property parameter for the "ATTACH" property being removed (see Section 3.3.3).
    4. The body of the request will be empty.
    5. The client MAY include a Prefer header field [RFC7240] with the "return=representation" preference to request that the modified calendar object resource be returned as the body of a successful response to the POST request.

  2. When the server receives the POST request, it does the following:

    1. Validates that any recurrence instances referred to via the "rid" query parameter are valid for the calendar object resource being targeted.
    2. Validates that the "managed-id" query parameter is valid for the calendar object resource and specific instances being targeted.
    3. For each affected recurrence instance in the calendar object resource targeted by the request, removes the matching "ATTACH" property. Note that if a specified recurrence instance does not have a matching component in the calendar object resource, then the server MUST modify the calendar object resource to include an overridden component with the appropriate "RECURRENCE-ID" property and the matching "ATTACH" property removed. This latter case is actually valid only if the master component does include the referenced "ATTACH" property.
    4. If the attachment resource is no longer referenced by any instance of the calendar object resource, it can delete the attachment resource to free up storage space.
    5. Upon successful removal of the attachment resource and modification of the targeted calendar object resource, it MUST return an appropriate HTTP success status response. If the client included a Prefer header field with the "return=representation" preference in the request, the server SHOULD return the modified calendar object resource as the body of the response. Otherwise, the server can expect that the client will reload the calendar object resource with a subsequent GET request to refresh any local cache.

  1. クライアントは、カレンダーオブジェクトリソースをターゲットとし、次のように構成したPOSTリクエストを発行します。

    1. Request-URIには、値「attachment-remove」を持つ「action」クエリーパラメーターが含まれます（Section 3.3.1を参照）。
    2. すべての繰り返しインスタンスから添付ファイルを削除する場合、Request-URIに「rid」クエリーパラメーターは存在しません。1つ以上の特定の繰り返しインスタンスをターゲットとする場合、Request-URIには、インスタンスのリストを含む「rid」クエリーパラメーターが含まれます（Section 3.3.2を参照）。
    3. Request-URIには、削除する「ATTACH」プロパティーの「MANAGED-ID」プロパティーパラメーターの値と一致する値を持つ「managed-id」クエリーパラメーターが含まれます（Section 3.3.3を参照）。
    4. リクエストのボディーは空です。
    5. クライアントは、変更されたカレンダーオブジェクトリソースをPOSTリクエストに対する成功レスポンスのボディーとして返すよう要求するために、「return=representation」優先設定を持つPreferヘッダーフィールド[RFC7240]を含めてもよいです（MAY）。

  2. サーバーは、POSTリクエストを受信すると、次のことを行います。

    1. 「rid」クエリーパラメーターで参照されている繰り返しインスタンスが、ターゲットとなるカレンダーオブジェクトリソースにとって有効であることを検証します。
    2. 「managed-id」クエリーパラメーターが、ターゲットとなるカレンダーオブジェクトリソースと特定のインスタンスにとって有効であることを検証します。
    3. リクエストのターゲットとなるカレンダーオブジェクトリソース内の影響を受ける各繰り返しインスタンスについて、一致する「ATTACH」プロパティーを削除します。指定された繰り返しインスタンスに一致するコンポーネントがカレンダーオブジェクトリソースに存在しない場合、サーバーは、適切な「RECURRENCE-ID」プロパティーを持ち、一致する「ATTACH」プロパティーを削除したオーバーライドされたコンポーネントを含むようにカレンダーオブジェクトリソースを変更しなければなりません（MUST）。この後者のケースは、実際にはマスターコンポーネントが参照される「ATTACH」プロパティーを含んでいる場合にのみ有効です。
    4. 添付ファイルリソースがカレンダーオブジェクトリソースのどのインスタンスからも参照されなくなった場合、サーバーは、ストレージ領域を解放するためにその添付ファイルリソースを削除できます。
    5. 添付ファイルリソースの削除と、ターゲットとなるカレンダーオブジェクトリソースの変更が成功したら、サーバーは、適切なHTTPの成功ステータスのレスポンスを返さなければなりません（MUST）。クライアントがリクエストに「return=representation」優先設定を持つPreferヘッダーフィールドを含めていた場合、サーバーは、変更されたカレンダーオブジェクトリソースをレスポンスのボディーとして返すべきです（SHOULD）。そうでない場合、サーバーは、クライアントがローカルキャッシュを更新するために後続のGETリクエストでカレンダーオブジェクトリソースを再読み込みすると想定できます。

In the following example, the client deletes an existing attachment by passing its "managed-id" value in the request. The Prefer header field [RFC7240] is not set in the request so the calendar object resource data is not returned in the response.

次の例では、クライアントが既存の添付ファイルの「managed-id」値をリクエストで渡して、その添付ファイルを削除しています。リクエストにPreferヘッダーフィールド[RFC7240]が設定されていないため、レスポンスでカレンダーオブジェクトリソースのデータは返されません。

Host: cal.example.com
Content-Length: 0

POST /events/64.ics?action=attachment-remove&managed-id=98S HTTP/1.1
Host: cal.example.com
Content-Length: 0

>> Response <<

>> レスポンス <<

Content-Length: 0

3.7. Adding Existing Managed Attachments via PUT

3.7. PUTによる既存の管理された添付ファイルの追加

Clients can make use of existing managed attachments by adding the corresponding "ATTACH" property to calendar object resources (subject to the restrictions described in Section 3.12.2).

クライアントは、対応する「ATTACH」プロパティーをカレンダーオブジェクトリソースに追加することで、既存の管理された添付ファイルを利用できます（Section 3.12.2で説明する制限に従います）。

If a managed attachment is used in more than calendar resource, servers SHOULD NOT change either the "MANAGED-ID" property parameter value or the "ATTACH" property value for these attachments; this ensures that clients do not have to download the attachment data again if they already have it cached. Additionally, servers SHOULD validate "SIZE" property parameter values and replace incorrect values with the actual sizes of existing attachments.

管理された添付ファイルが複数のカレンダーリソースで使用されている場合、サーバーは、それらの添付ファイルの「MANAGED-ID」プロパティーパラメーター値も「ATTACH」プロパティー値も変更すべきではありません（SHOULD NOT）。これにより、クライアントは、添付ファイルのデータをすでにキャッシュしている場合に、それを再度ダウンロードする必要がなくなります。さらに、サーバーは「SIZE」プロパティーパラメーター値を検証し、正しくない値を既存の添付ファイルの実際のサイズで置き換えるべきです（SHOULD）。

These PUT requests are subject to the preconditions listed in Section 3.11.

これらのPUTリクエストには、Section 3.11に列挙する事前条件が適用されます。

3.8. Updating Attachments via PUT

3.8. PUTによる添付ファイルの更新

Servers MUST NOT allow clients to update attachment data directly via a PUT on the attachment URI (or via any other HTTP method that modifies content). Instead, attachments can only be updated via use of POST requests on the calendar data.

サーバーは、添付ファイルURIに対するPUT（またはコンテンツを変更するその他のHTTPメソッド）によって、クライアントが添付ファイルのデータを直接更新することを許可してはなりません（MUST NOT）。代わりに、添付ファイルは、カレンダーデータに対するPOSTリクエストを使用することでのみ更新できます。

3.9. Removing Attachments via PUT

3.9. PUTによる添付ファイルの削除

Clients can remove attachments by simply rewriting the calendar object resource data to remove the appropriate "ATTACH" properties. Servers MUST NOT allow clients to delete attachments directly via a DELETE request on the attachment URI.

クライアントは、カレンダーオブジェクトリソースのデータを書き換えて該当する「ATTACH」プロパティーを削除するだけで、添付ファイルを削除できます。サーバーは、添付ファイルURIに対するDELETEリクエストによって、クライアントが添付ファイルを直接削除することを許可してはなりません（MUST NOT）。

3.10. Retrieving Attachments

3.10. 添付ファイルの取得

Clients retrieve attachments by issuing an HTTP GET request using the value of the corresponding "ATTACH" property as the Request-URI, taking into account the substitution mechanism associated with the "CALDAV:managed-attachments-server-URL" property (see Section 6.1).

クライアントは、「CALDAV:managed-attachments-server-URL」プロパティー（Section 6.1を参照）に関連する置換メカニズムを考慮したうえで、対応する「ATTACH」プロパティーの値をRequest-URIとして使用するHTTP GETリクエストを発行することで、添付ファイルを取得します。

3.12. Additional Considerations

3.12. その他の考慮事項

3.12.1. Quotas

3.12.1. クォータ

The WebDAV Quotas specification [RFC4331] defines two live WebDAV properties (DAV:quota-available-bytes and DAV:quota-used-bytes) to communicate storage quota information to clients. Server implementations MAY choose to include managed attachment sizes when calculating the amount of storage used by a particular resource.

WebDAVクォータの仕様[RFC4331]は、ストレージのクォータ情報をクライアントに伝えるための2つのWebDAVライブプロパティー（DAV:quota-available-bytesとDAV:quota-used-bytes）を定義しています。サーバーの実装は、特定のリソースが使用しているストレージ量を計算する際に、管理された添付ファイルのサイズを含めることを選択してもよいです（MAY）。

3.12.2. Access Control

3.12.2. アクセス制御

Access to the managed attachments referenced in a calendar object resource SHOULD be restricted to only those calendar users who have access to that calendar object either directly or indirectly (via being an attendee who would receive a scheduling message).

カレンダーオブジェクトリソースで参照されている管理された添付ファイルへのアクセスは、そのカレンダーオブジェクトに直接、または（スケジューリングメッセージを受け取る出席者であることを介して）間接的にアクセスできるカレンダーユーザーだけに制限されるべきです（SHOULD）。

When accessing a managed attachment, clients SHOULD be prepared to authenticate with the server storing the attachment resource. The credentials required to access the managed attachment store could be different from the ones used to access the CalDAV server.

管理された添付ファイルにアクセスする際、クライアントは、添付ファイルリソースを保存しているサーバーに対して認証を行う準備をしておくべきです（SHOULD）。管理された添付ファイルのストアにアクセスするために必要なクレデンシャルは、CalDAVサーバーにアクセスするために使用するものとは異なる場合があります。

This specification only allows organizers of scheduled events to add managed attachments. Servers MUST prevent attendees of scheduled events from adding, updating, or removing managed attachments. In addition, the server MUST prevent a calendar user from reusing a managed attachment (based on its "managed-id" value), unless that user is the one who originally created the managed attachment.

この仕様では、スケジュールされたイベントの主催者だけが管理された添付ファイルを追加できます。サーバーは、スケジュールされたイベントの出席者が管理された添付ファイルを追加、更新、削除することを防止しなければなりません（MUST）。さらに、サーバーは、カレンダーユーザーが管理された添付ファイルを（その「managed-id」値にもとづいて）再利用することを、そのユーザーがその管理された添付ファイルを最初に作成したユーザーでない限り、防止しなければなりません（MUST）。

3.12.3. Redirects

3.12.3. リダイレクト

For POST requests that add or update attachment data, the server MAY issue a 307 (Temporary Redirect) [RFC7231] or 308 (Permanent Redirect) [RFC7538] response to require the client to reissue the POST request using a different Request-URI. As a result, clients SHOULD use the "100-continue" expectation defined in Section 5.1.1 of [RFC7231]. Using this mechanism ensures that, if a redirect does occur, the client does not needlessly send the attachment data.

添付ファイルのデータを追加または更新するPOSTリクエストに対して、サーバーは、別のRequest-URIを使用してPOSTリクエストを再発行するようクライアントに求めるために、307（Temporary Redirect）[RFC7231]または308（Permanent Redirect）[RFC7538]レスポンスを発行してもよいです（MAY）。そのため、クライアントは、[RFC7231]のSection 5.1.1で定義されている「100-continue」期待（expectation）を使用すべきです（SHOULD）。このメカニズムを使用することで、リダイレクトが発生した場合でも、クライアントが添付ファイルのデータを不必要に送信しないことが保証されます。

3.12.4. Processing Time

3.12.4. 処理時間

Clients can expect servers to take a while to respond to POST requests that include large attachment bodies. Servers SHOULD use the 102 (Processing) interim response defined in Section 10.1 of [RFC2518] to keep the client connection alive if the POST request will take significant time to complete.

クライアントは、大きな添付ファイルのボディーを含むPOSTリクエストに対して、サーバーが応答するまでにしばらく時間がかかることを想定できます。POSTリクエストの完了に長い時間がかかる場合、サーバーは、クライアントのコネクションを維持するために、[RFC2518]のSection 10.1で定義されている102（Processing）中間レスポンスを使用すべきです（SHOULD）。

3.12.5. Automatic Cleanup by Servers

3.12.5. サーバーによる自動クリーンアップ

Servers MAY automatically remove attachment data, for example, to regain the storage taken by unused attachments or as the result of a virus scanning. When doing so, they SHOULD NOT modify calendar data referencing those attachments. Instead, they SHOULD respond with 410 (Gone) to any request on the removed attachment URI.

サーバーは、たとえば、使用されていない添付ファイルが占めるストレージを取り戻すため、またはウイルススキャンの結果として、添付ファイルのデータを自動的に削除してもよいです（MAY）。その場合、サーバーは、それらの添付ファイルを参照しているカレンダーデータを変更すべきではありません（SHOULD NOT）。代わりに、削除された添付ファイルURIに対するあらゆるリクエストに410（Gone）で応答すべきです（SHOULD）。

3.12.6. Sending Scheduling Messages with Attachments

3.12.6. 添付ファイルを含むスケジューリングメッセージの送信

When a managed attachment is added, updated, or removed from a calendar object resource, the server MUST ensure that a scheduling message is sent to update any attendees with the changes, as per [RFC6638].

管理された添付ファイルがカレンダーオブジェクトリソースに追加、更新、またはカレンダーオブジェクトリソースから削除されたとき、サーバーは、[RFC6638]に従って、変更内容ですべての出席者を更新するためのスケジューリングメッセージが送信されることを保証しなければなりません（MUST）。

3.12.7. Migrating Calendar Data

3.12.7. カレンダーデータの移行

When exporting calendar data from a CalDAV server supporting managed attachments, clients SHOULD remove all "MANAGED-ID" property parameters from "ATTACH" properties in the calendar data. Similarly, when importing calendar data from another source, clients SHOULD remove any "MANAGED-ID" property parameters on "ATTACH" properties (failure to do so will likely result in the server removing those properties automatically).

7. Security Considerations

7. セキュリティーに関する考慮事項

The security considerations in [RFC4791] and [RFC4918] apply to this extension. Additionally, servers need to be aware that a client could attack underlying storage by POSTing extremely large attachments and could attack processing time by uploading a recurring event with a large number of overrides and then repeatedly adding, updating, and deleting attachments.

[RFC4791]と[RFC4918]のセキュリティーに関する考慮事項は、この拡張にも適用されます。さらに、サーバーは、クライアントが極端に大きな添付ファイルをPOSTすることで基盤となるストレージを攻撃したり、多数のオーバーライドを持つ繰り返しイベントをアップロードしてから添付ファイルの追加、更新、削除を繰り返すことで処理時間を攻撃したりする可能性があることを認識しておく必要があります。

Malicious content could be introduced into the calendar server by way of a managed attachment, and propagated to many end users via scheduling. Servers SHOULD check managed attachments for malicious or inappropriate content. Upon detecting such content, servers SHOULD remove the attachment following the rules described in Section 3.12.5.

悪意のあるコンテンツが、管理された添付ファイルを介してカレンダーサーバーに持ち込まれ、スケジューリングによって多くのエンドユーザーに広まる可能性があります。サーバーは、管理された添付ファイルに悪意のあるコンテンツや不適切なコンテンツがないか確認すべきです（SHOULD）。そのようなコンテンツを検出した場合、サーバーは、Section 3.12.5で説明する規則に従って添付ファイルを削除すべきです（SHOULD）。

Appendix A. 繰り返しイベントを含む例

In the following example, the organizer of a recurring meeting makes an unsuccessful attempt to add an agenda (HTML attachment) to the corresponding calendar resource with a conditional request. Note that the client includes both the Expect and Prefer header fields in the request, thereby preventing itself from needlessly sending the attachment data and requesting that the current resource be returned in the failure response (see Section 3.2 of [RFC8144]).

次の例では、繰り返し会議の主催者が、条件付きリクエストを使用して、対応するカレンダーリソースにアジェンダ（HTMLの添付ファイル）を追加しようとして失敗しています。クライアントがリクエストにExpectヘッダーフィールドとPreferヘッダーフィールドの両方を含めていることに注意してください。これにより、クライアントは添付ファイルのデータを不必要に送信することを避けるとともに、失敗レスポンスで現在のリソースを返すよう要求しています（[RFC8144]のSection 3.2を参照）。
