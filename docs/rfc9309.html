RFC 9309

Robots Exclusion Protocol

RFC 9309

ロボット排除プロトコル

Abstract

概要

This document specifies and extends the "Robots Exclusion Protocol" method originally defined by Martijn Koster in 1994 for service owners to control how content served by their services may be accessed, if at all, by automatic clients known as crawlers. Specifically, it adds definition language for the protocol, instructions for handling errors, and instructions for caching.

この文書は、サービスが提供するコンテンツに対してクローラーと呼ばれる自動化されたクライアントがアクセスしてもよいかどうか、またどのようにアクセスしてもよいかをサービスの所有者が制御するために、Martijn Kosterが1994年に最初に定義した「ロボット排除プロトコル（Robots Exclusion Protocol）」の方式を規定し、拡張します。具体的には、プロトコルの定義言語、エラー処理の手順、キャッシュの手順を追加します。

1. Introduction

1. はじめに

This document applies to services that provide resources that clients can access through URIs as defined in [RFC3986]. For example, in the context of HTTP, a browser is a client that displays the content of a web page.

この文書は、[RFC3986]で定義されているURIを通じてクライアントがアクセスできるリソースを提供するサービスに適用されます。たとえば、HTTPの文脈では、ブラウザーはWebページのコンテンツを表示するクライアントです。

Crawlers are automated clients. Search engines, for instance, have crawlers to recursively traverse links for indexing as defined in [RFC8288].

クローラー（crawler）は自動化されたクライアントです。たとえば検索エンジンは、インデックスを作成するために[RFC8288]で定義されているリンクを再帰的にたどるクローラーを持っています。

It may be inconvenient for service owners if crawlers visit the entirety of their URI space. This document specifies the rules originally defined by the "Robots Exclusion Protocol" [ROBOTSTXT] that crawlers are requested to honor when accessing URIs.

クローラーがURI空間の全体を訪れると、サービスの所有者にとって不都合な場合があります。この文書は、「ロボット排除プロトコル（Robots Exclusion Protocol）」[ROBOTSTXT]で最初に定義された、URIにアクセスする際にクローラーが従うよう求められる規則を規定します。

These rules are not a form of access authorization.

これらの規則は、アクセス認可の一形態ではありません。

1.1. 要件言語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

2. Specification

2. 仕様

2.1. Protocol Definition

2.1. プロトコルの定義

The protocol language consists of rule(s) and group(s) that the service makes available in a file named "robots.txt" as described in Section 2.3:

プロトコル言語は、Section 2.3で説明するように、サービスが「robots.txt」という名前のファイルで提供する規則（rule）とグループ（group）から構成されます：

Rule:
A line with a key-value pair that defines how a crawler may access URIs. See Section 2.2.2.
Group:
One or more user-agent lines that are followed by one or more rules. The group is terminated by a user-agent line or end of file. See Section 2.2.1. The last group may have no rules, which means it implicitly allows everything.
規則：
クローラーがURIにどのようにアクセスしてもよいかを定義する、キーと値のペアを含む行です。Section 2.2.2を参照してください。
グループ：
1つ以上のuser-agent行と、それに続く1つ以上の規則です。グループは、user-agent行またはファイルの終わりで終了します。Section 2.2.1を参照してください。最後のグループには規則がない場合があり、これは暗黙的にすべてを許可することを意味します。

2.2.1. The User-Agent Line

2.2.1. User-Agent行

Crawlers set their own name, which is called a product token, to find relevant groups. The product token MUST contain only uppercase and lowercase letters ("a-z" and "A-Z"), underscores ("_"), and hyphens ("-"). The product token SHOULD be a substring of the identification string that the crawler sends to the service. For example, in the case of HTTP [RFC9110], the product token SHOULD be a substring in the User-Agent header. The identification string SHOULD describe the purpose of the crawler. Here's an example of a User-Agent HTTP request header with a link pointing to a page describing the purpose of the ExampleBot crawler, which appears as a substring in the User-Agent HTTP header and as a product token in the robots.txt user-agent line:

クローラーは、関連するグループを見つけるために、プロダクトトークン（product token）と呼ばれる自身の名前を設定します。プロダクトトークンには、大文字と小文字のアルファベット（「a-z」と「A-Z」）、アンダースコア（「_」）、ハイフン（「-」）のみを含めなければなりません（MUST）。プロダクトトークンは、クローラーがサービスに送信する識別文字列の部分文字列であるべきです（SHOULD）。たとえば、HTTP [RFC9110]の場合、プロダクトトークンはUser-Agentヘッダーの部分文字列であるべきです（SHOULD）。識別文字列は、クローラーの目的を説明すべきです（SHOULD）。以下は、ExampleBotクローラーの目的を説明するページを指すリンクを含むUser-Agent HTTPリクエストヘッダーの例です。ExampleBotは、User-Agent HTTPヘッダーの部分文字列として、またrobots.txtのuser-agent行のプロダクトトークンとして現れます：

Note that the product token (ExampleBot) is a substring of the User-Agent HTTP header.

プロダクトトークン（ExampleBot）がUser-Agent HTTPヘッダーの部分文字列であることに注意してください。

Crawlers MUST use case-insensitive matching to find the group that matches the product token and then obey the rules of the group. If there is more than one group matching the user-agent, the matching groups' rules MUST be combined into one group and parsed according to Section 2.2.2.

クローラーは、大文字と小文字を区別しない照合を使用してプロダクトトークンに一致するグループを見つけ、そのグループの規則に従わなければなりません（MUST）。user-agentに一致するグループが複数ある場合、一致したグループの規則は1つのグループに結合し、Section 2.2.2に従って解析しなければなりません（MUST）。

If no matching group exists, crawlers MUST obey the group with a user-agent line with the "*" value, if present.

一致するグループが存在しない場合、クローラーは、値が「*」のuser-agent行を持つグループがあれば、それに従わなければなりません（MUST）。

If no group matches the product token and there is no group with a user-agent line with the "*" value, or no groups are present at all, no rules apply.

プロダクトトークンに一致するグループがなく、値が「*」のuser-agent行を持つグループもない場合、またはグループがまったく存在しない場合は、どの規則も適用されません。

2.2.2. The "Allow" and "Disallow" Lines

2.2.2. 「Allow」行と「Disallow」行

These lines indicate whether accessing a URI that matches the corresponding path is allowed or disallowed.

これらの行は、対応するパスに一致するURIへのアクセスが許可されているか、許可されていないかを示します。

To evaluate if access to a URI is allowed, a crawler MUST match the paths in "allow" and "disallow" rules against the URI. The matching SHOULD be case sensitive. The matching MUST start with the first octet of the path. The most specific match found MUST be used. The most specific match is the match that has the most octets. Duplicate rules in a group MAY be deduplicated. If an "allow" rule and a "disallow" rule are equivalent, then the "allow" rule SHOULD be used. If no match is found amongst the rules in a group for a matching user-agent or there are no rules in the group, the URI is allowed. The /robots.txt URI is implicitly allowed.

URIへのアクセスが許可されているかを評価するために、クローラーは「allow」規則と「disallow」規則のパスをURIと照合しなければなりません（MUST）。照合では大文字と小文字を区別すべきです（SHOULD）。照合はパスの最初のオクテットから開始しなければなりません（MUST）。見つかったもののうち最も具体的な一致を使用しなければなりません（MUST）。最も具体的な一致とは、オクテット数が最も多い一致のことです。グループ内の重複した規則は、重複を除去してもよいです（MAY）。「allow」規則と「disallow」規則が同等である場合は、「allow」規則を使用すべきです（SHOULD）。一致するuser-agentのグループの規則の中に一致が見つからない場合、またはグループに規則がない場合、そのURIは許可されます。/robots.txtのURIは暗黙的に許可されます。

Octets in the URI and robots.txt paths outside the range of the ASCII coded character set, and those in the reserved range defined by [RFC3986], MUST be percent-encoded as defined by [RFC3986] prior to comparison.

URIおよびrobots.txtのパスに含まれる、ASCII符号化文字集合の範囲外のオクテットと、[RFC3986]で定義されている予約範囲内のオクテットは、比較の前に[RFC3986]の定義に従ってパーセントエンコードしなければなりません（MUST）。

If a percent-encoded ASCII octet is encountered in the URI, it MUST be unencoded prior to comparison, unless it is a reserved character in the URI as defined by [RFC3986] or the character is outside the unreserved character range. The match evaluates positively if and only if the end of the path from the rule is reached before a difference in octets is encountered.

URI内でパーセントエンコードされたASCIIオクテットに遭遇した場合、それが[RFC3986]で定義されているURIの予約文字であるか、その文字が非予約文字の範囲外である場合を除き、比較の前にデコードしなければなりません（MUST）。オクテットの差異に遭遇する前に規則のパスの終わりに到達した場合に限り、照合は一致と評価されます。

たとえば：

The crawler SHOULD ignore "disallow" and "allow" rules that are not in any group (for example, any rule that precedes the first user-agent line).

クローラーは、どのグループにも属さない「disallow」規則と「allow」規則（たとえば、最初のuser-agent行より前にある規則）を無視すべきです（SHOULD）。

Implementors MAY bridge encoding mismatches if they detect that the robots.txt file is not UTF-8 encoded.

実装者は、robots.txtファイルがUTF-8でエンコードされていないことを検出した場合、エンコーディングの不一致を吸収してもよいです（MAY）。

2.2.4. Other Records

2.2.4. その他のレコード

Crawlers MAY interpret other records that are not part of the robots.txt protocol -- for example, "Sitemaps" [SITEMAPS]. Crawlers MAY be lenient when interpreting other records. For example, crawlers may accept common misspellings of the record.

クローラーは、robots.txtプロトコルの一部ではないその他のレコード（たとえば「Sitemaps」[SITEMAPS]）を解釈してもよいです（MAY）。クローラーは、その他のレコードを寛容に解釈してもよいです（MAY）。たとえば、クローラーはレコードのよくあるスペルミスを受け入れることがあります。

Parsing of other records MUST NOT interfere with the parsing of explicitly defined records in Section 2. For example, a "Sitemaps" record MUST NOT terminate a group.

その他のレコードの解析は、Section 2で明示的に定義されたレコードの解析を妨げてはなりません（MUST NOT）。たとえば、「Sitemaps」レコードでグループを終了させてはなりません（MUST NOT）。

2.3. Access Method

2.3. アクセス方法

The rules MUST be accessible in a file named "/robots.txt" (all lowercase) in the top-level path of the service. The file MUST be UTF-8 encoded (as defined in [RFC3629]) and Internet Media Type "text/plain" (as defined in [RFC2046]).

規則は、サービスのトップレベルのパスにある「/robots.txt」（すべて小文字）という名前のファイルでアクセスできなければなりません（MUST）。このファイルは、（[RFC3629]で定義されている）UTF-8でエンコードされ、（[RFC2046]で定義されている）インターネットメディアタイプ「text/plain」でなければなりません（MUST）。

As per [RFC3986], the URI of the robots.txt file is:

[RFC3986]に従うと、robots.txtファイルのURIは次のとおりです：

"scheme:[//authority]/robots.txt"

"scheme:[//authority]/robots.txt"

For example, in the context of HTTP or FTP, the URI is:

たとえば、HTTPまたはFTPの文脈では、URIは次のとおりです：

          https://www.example.com/robots.txt

          ftp://ftp.example.com/robots.txt

          https://www.example.com/robots.txt

          ftp://ftp.example.com/robots.txt

2.3.1. Access Results

2.3.1. アクセス結果

2.3.1.1. Successful Access
2.3.1.1. アクセスの成功

If the crawler successfully downloads the robots.txt file, the crawler MUST follow the parseable rules.

クローラーがrobots.txtファイルのダウンロードに成功した場合、クローラーは解析可能な規則に従わなければなりません（MUST）。

2.3.1.2. Redirects
2.3.1.2. リダイレクト

It's possible that a server responds to a robots.txt fetch request with a redirect, such as HTTP 301 or HTTP 302 in the case of HTTP. The crawlers SHOULD follow at least five consecutive redirects, even across authorities (for example, hosts in the case of HTTP).

サーバーがrobots.txtの取得リクエストに対して、HTTPの場合のHTTP 301やHTTP 302のようなリダイレクトで応答する可能性があります。クローラーは、オーソリティー（たとえば、HTTPの場合はホスト）をまたぐ場合であっても、少なくとも5回の連続したリダイレクトをたどるべきです（SHOULD）。

If a robots.txt file is reached within five consecutive redirects, the robots.txt file MUST be fetched, parsed, and its rules followed in the context of the initial authority.

5回以内の連続したリダイレクトでrobots.txtファイルに到達した場合、そのrobots.txtファイルを取得して解析し、最初のオーソリティーの文脈でその規則に従わなければなりません（MUST）。

If there are more than five consecutive redirects, crawlers MAY assume that the robots.txt file is unavailable.

連続したリダイレクトが5回を超える場合、クローラーはrobots.txtファイルが利用不可（unavailable）であるとみなしてもよいです（MAY）。

2.3.1.3. "Unavailable" Status
2.3.1.3. 「利用不可（Unavailable）」ステータス

"Unavailable" means the crawler tries to fetch the robots.txt file and the server responds with status codes indicating that the resource in question is unavailable. For example, in the context of HTTP, such status codes are in the 400-499 range.

「利用不可（Unavailable）」とは、クローラーがrobots.txtファイルを取得しようとし、サーバーが対象のリソースを利用できないことを示すステータスコードで応答することを意味します。たとえば、HTTPの文脈では、そのようなステータスコードは400〜499の範囲にあります。

If a server status code indicates that the robots.txt file is unavailable to the crawler, then the crawler MAY access any resources on the server.

サーバーのステータスコードが、robots.txtファイルをクローラーが利用できないことを示している場合、クローラーはサーバー上の任意のリソースにアクセスしてもよいです（MAY）。

2.3.1.4. "Unreachable" Status
2.3.1.4. 「到達不能（Unreachable）」ステータス

If the robots.txt file is unreachable due to server or network errors, this means the robots.txt file is undefined and the crawler MUST assume complete disallow. For example, in the context of HTTP, server errors are identified by status codes in the 500-599 range.

サーバーまたはネットワークのエラーによりrobots.txtファイルに到達できない場合、これはrobots.txtファイルが未定義であることを意味し、クローラーはすべてが許可されていない（complete disallow）とみなさなければなりません（MUST）。たとえば、HTTPの文脈では、サーバーエラーは500〜599の範囲のステータスコードで識別されます。

If the robots.txt file is undefined for a reasonably long period of time (for example, 30 days), crawlers MAY assume that the robots.txt file is unavailable as defined in Section 2.3.1.3 or continue to use a cached copy.

robots.txtファイルが十分に長い期間（たとえば30日間）未定義である場合、クローラーは、robots.txtファイルがSection 2.3.1.3で定義されている利用不可の状態であるとみなすか、キャッシュされたコピーを引き続き使用してもよいです（MAY）。

2.3.1.5. Parsing Errors
2.3.1.5. 解析エラー

Crawlers MUST try to parse each line of the robots.txt file. Crawlers MUST use the parseable rules.

クローラーは、robots.txtファイルの各行を解析しようとしなければなりません（MUST）。クローラーは、解析可能な規則を使用しなければなりません（MUST）。

2.4. Caching

2.4. キャッシュ

Crawlers MAY cache the fetched robots.txt file's contents. Crawlers MAY use standard cache control as defined in [RFC9111]. Crawlers SHOULD NOT use the cached version for more than 24 hours, unless the robots.txt file is unreachable.

クローラーは、取得したrobots.txtファイルの内容をキャッシュしてもよいです（MAY）。クローラーは、[RFC9111]で定義されている標準的なキャッシュ制御を使用してもよいです（MAY）。robots.txtファイルに到達できない場合を除き、クローラーはキャッシュされたバージョンを24時間を超えて使用すべきではありません（SHOULD NOT）。

2.5. Limits

2.5. 制限

Crawlers SHOULD impose a parsing limit to protect their systems; see Section 3. The parsing limit MUST be at least 500 kibibytes [KiB].

クローラーは、自身のシステムを保護するために解析の制限を設けるべきです（SHOULD）。Section 3を参照してください。解析の制限は、少なくとも500キビバイト[KiB]でなければなりません（MUST）。

3. Security Considerations

3. セキュリティーに関する考慮事項

The Robots Exclusion Protocol is not a substitute for valid content security measures. Listing paths in the robots.txt file exposes them publicly and thus makes the paths discoverable. To control access to the URI paths in a robots.txt file, users of the protocol should employ a valid security measure relevant to the application layer on which the robots.txt file is served -- for example, in the case of HTTP, HTTP Authentication as defined in [RFC9110].

ロボット排除プロトコルは、有効なコンテンツのセキュリティー対策の代わりにはなりません。robots.txtファイルにパスを列挙すると、それらのパスが公開され、発見可能になります。robots.txtファイル内のURIパスへのアクセスを制御するには、プロトコルの利用者は、robots.txtファイルが提供されるアプリケーション層に適した有効なセキュリティー対策（たとえば、HTTPの場合は[RFC9110]で定義されているHTTP認証）を採用すべきです。

To protect against attacks against their system, implementors of robots.txt parsing and matching logic should take the following considerations into account:

システムに対する攻撃から保護するために、robots.txtの解析と照合のロジックの実装者は、次の考慮事項を考慮に入れるべきです：

Memory management:
Section 2.5 defines the lower limit of bytes that must be processed, which inherently also protects the parser from out-of-memory scenarios.
Invalid characters:
Section 2.2 defines a set of characters that parsers and matchers can expect in robots.txt files. Out-of-bound characters should be rejected as invalid, which limits the available attack vectors that attempt to compromise the system.
Untrusted content:
Implementors should treat the content of a robots.txt file as untrusted content, as defined by the specification of the application layer used. For example, in the context of HTTP, implementors should follow the Security Considerations section of [RFC9110].
メモリー管理：
Section 2.5は、処理しなければならないバイト数の下限を定義しており、これは本質的に、パーサーをメモリー不足の状況から保護することにもなります。
無効な文字：
Section 2.2は、パーサーと照合器がrobots.txtファイル内に現れると想定できる文字の集合を定義しています。範囲外の文字は無効として拒否すべきです。これにより、システムを侵害しようとする攻撃ベクトルが制限されます。
信頼できないコンテンツ：
実装者は、robots.txtファイルの内容を、使用するアプリケーション層の仕様で定義されているとおりに、信頼できないコンテンツとして扱うべきです。たとえば、HTTPの文脈では、実装者は[RFC9110]の「Security Considerations」セクションに従うべきです。

5. Examples

5. 例

5.1. Simple Example

5.1. 簡単な例

The following example shows:

次の例は、以下を示しています：

*:
A group that's relevant to all user agents that don't have an explicitly defined matching group. It allows access to the URLs with the /publications/ path prefix, and it restricts access to the URLs with the /example/ path prefix and to all URLs with a .gif suffix. The "*" character designates any character, including the otherwise-required forward slash; see Section 2.2.
foobot:
A regular case. A single user agent followed by rules. The crawler only has access to two URL path prefixes on the site -- /example/page.html and /example/allowed.gif. The rules of the group are missing the optional space character, which is acceptable as defined in Section 2.2.
barbot and bazbot:
A group that's relevant for more than one user agent. The crawlers are not allowed to access the URLs with the /example/page.html path prefix but otherwise have unrestricted access to the rest of the URLs on the site.
quxbot:
An empty group at the end of the file. The crawler has unrestricted access to the URLs on the site.
*:
明示的に定義された一致するグループを持たないすべてのユーザーエージェントに関係するグループです。/publications/というパスプレフィックスを持つURLへのアクセスを許可し、/example/というパスプレフィックスを持つURLと、.gifという接尾辞を持つすべてのURLへのアクセスを制限します。「*」文字は、本来なら必須であるスラッシュを含む任意の文字を表します。Section 2.2を参照してください。
foobot:
通常のケースです。1つのユーザーエージェントの後に規則が続きます。このクローラーは、サイト上の2つのURLパスプレフィックス（/example/page.htmlと/example/allowed.gif）にのみアクセスできます。このグループの規則には省略可能な空白文字がありませんが、これはSection 2.2で定義されているとおり許容されます。
barbotとbazbot：
複数のユーザーエージェントに関係するグループです。これらのクローラーは、/example/page.htmlというパスプレフィックスを持つURLへのアクセスは許可されていませんが、それ以外のサイト上のURLには制限なくアクセスできます。
quxbot:
ファイルの末尾にある空のグループです。このクローラーは、サイト上のURLに制限なくアクセスできます。
            User-Agent: *
            Disallow: *.gif$
            Disallow: /example/
            Allow: /publications/

            User-Agent: foobot
            Disallow:/
            Allow:/example/page.html
            Allow:/example/allowed.gif

            User-Agent: barbot
            User-Agent: bazbot
            Disallow: /example/page.html

            User-Agent: quxbot

            EOF

            User-Agent: *
            Disallow: *.gif$
            Disallow: /example/
            Allow: /publications/

            User-Agent: foobot
            Disallow:/
            Allow:/example/page.html
            Allow:/example/allowed.gif

            User-Agent: barbot
            User-Agent: bazbot
            Disallow: /example/page.html

            User-Agent: quxbot

            EOF

5.2. Longest Match

5.2. 最長一致

The following example shows that in the case of two rules, the longest one is used for matching. In the following case, /example/page/disallowed.gif MUST be used for the URI example.com/example/page/disallow.gif.

次の例は、2つの規則がある場合に、最も長い規則が照合に使用されることを示しています。次の場合、URI example.com/example/page/disallow.gifには/example/page/disallowed.gifを使用しなければなりません（MUST）。

            User-Agent: foobot
            Allow: /example/page/
            Disallow: /example/page/disallowed.gif

            User-Agent: foobot
            Allow: /example/page/
            Disallow: /example/page/disallowed.gif
