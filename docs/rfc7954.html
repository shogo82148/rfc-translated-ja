RFC 7954

Locator/ID Separation Protocol (LISP) Endpoint Identifier (EID) Block

RFC 7954

ロケーター/ID分離プロトコル（LISP）エンドポイント識別子（EID）ブロック

Abstract

概要

This document directs IANA to allocate a /32 IPv6 prefix for use with the Locator/ID Separation Protocol (LISP). The prefix will be used for local intra-domain routing and global endpoint identification, by sites deploying LISP as Endpoint Identifier (EID) addressing space.

この文書は、ロケーター/ID分離プロトコル（Locator/ID Separation Protocol、LISP）で使用する/32のIPv6プレフィックスを割り当てるようIANAに指示します。 このプレフィックスは、LISPを展開するサイトによって、エンドポイント識別子（Endpoint Identifier、EID）のアドレス空間として、ローカルなドメイン内ルーティングとグローバルなエンドポイント識別に使用されます。

1. Introduction

1. はじめに

This document directs the IANA to allocate a /32 IPv6 prefix for use with the Locator/ID Separation Protocol (LISP [RFC6830]), LISP Map-Server ([RFC6833]), LISP Alternative Topology (LISP+ALT [RFC6836]) (or other) mapping systems, and LISP Interworking ([RFC6832]).

この文書は、ロケーター/ID分離プロトコル（LISP [RFC6830]）、LISP Map-Server（[RFC6833]）、LISP代替トポロジー（LISP+ALT [RFC6836]）（またはその他の）マッピングシステム、およびLISPインターワーキング（[RFC6832]）で使用する/32のIPv6プレフィックスを割り当てるようIANAに指示します。

This block will be used as global Endpoint Identifier (EID) space.

このブロックは、グローバルなエンドポイント識別子（Endpoint Identifier、EID）空間として使用されます。

2. Definition of Terms

2. 用語の定義

The present document does not introduce any new terms with respect to the set of LISP Specifications ([RFC6830], [RFC6831], [RFC6832], [RFC6833], [RFC6834], [RFC6835], [RFC6836], [RFC6837]), but it assumes that the reader is familiar with the LISP terminology. [LISP-INTRO] provides an introduction to the LISP technology, including its terminology.

この文書は、一連のLISP仕様（[RFC6830]、[RFC6831]、[RFC6832]、[RFC6833]、[RFC6834]、[RFC6835]、[RFC6836]、[RFC6837]）に対して新しい用語を導入しませんが、読者がLISPの用語に精通していることを前提としています。 [LISP-INTRO]は、用語を含むLISP技術の入門を提供しています。

3. Rationale and Intent

3. 根拠と意図

Discussion within the LISP working group led to the identification of several scenarios in which the existence of a LISP-specific address block brings technical benefits. The most relevant scenarios are described below:

LISPワーキンググループ内での議論により、LISP固有のアドレスブロックが存在することで技術的な利点がもたらされるいくつかのシナリオが特定されました。 最も関連性の高いシナリオを以下に示します。

Early LISP destination detection:
With the current specifications, there is no direct way to detect whether or not a certain destination is in a LISP domain without performing a LISP mapping lookup. For instance, if an Ingress Tunnel Router (ITR) is sending packets to all types of destinations (i.e., non-LISP destinations, LISP destinations not in the IPv6 EID block, and LISP destinations in the IPv6 EID block), the only way to understand whether or not to encapsulate the traffic is to perform a cache lookup and, in case of a LISP cache miss, send a Map-Request to the mapping system. In the meanwhile (while waiting for the Map-Reply), packets may be dropped to avoid excessive buffering.
Avoid penalizing non-LISP traffic:
In certain circumstances, it might be desirable to configure a router using LISP features to natively forward all packets that do not have a destination address in the block and, hence, no lookup whatsoever is performed and packets destined to non-LISP sites are not penalized in any manner.
Traffic Engineering:
In some deployment scenarios, it might be desirable to apply different traffic-engineering policies for LISP and non-LISP traffic. A LISP-specific EID block would allow improved traffic-engineering capabilities with respect to LISP vs. non-LISP traffic. In particular, LISP traffic might be identified without having to use Deep Packet Inspection (DPI) techniques in order to parse the encapsulated packet. Instead, performing a simple inspection of the outer header is sufficient.
Transition Mechanism:
The existence of a LISP-specific EID block may prove useful in transition scenarios. A non-LISP domain would ask for an allocation in the LISP EID block and use it to deploy LISP in its network. Such allocation would not be announced in the BGP routing infrastructure (cf. Section 4). This approach will allow non-LISP domains to avoid fragmenting their already allocated non-LISP addressing space, which may lead to BGP routing table inflation since it may (rightfully) be announced in the BGP routing infrastructure.
Limit the impact on the BGP routing infrastructure:
As described in the previous scenario, LISP adopters will avoid fragmenting their addressing space, since fragmentation would negatively impact the BGP routing infrastructure. Adopters will use addressing space from the EID block, which might be announced in large aggregates and in a tightly controlled manner only by Proxy Tunnel Routers (PxTRs).
LISPの宛先の早期検出：
現在の仕様では、LISPマッピングの検索を行わずに、ある宛先がLISPドメイン内にあるかどうかを直接検出する方法はありません。 たとえば、入口トンネルルーター（Ingress Tunnel Router、ITR）があらゆる種類の宛先（つまり、非LISPの宛先、IPv6 EIDブロックにないLISPの宛先、およびIPv6 EIDブロックにあるLISPの宛先）にパケットを送信している場合、トラフィックをカプセル化すべきかどうかを判断する唯一の方法は、キャッシュの検索を行い、LISPキャッシュミスの場合はマッピングシステムにMap-Requestを送信することです。 その間（Map-Replyを待っている間）、過剰なバッファリングを避けるためにパケットが破棄される場合があります。
非LISPトラフィックへの不利益の回避：
状況によっては、LISPの機能を使用するルーターを、宛先アドレスがこのブロック内にないすべてのパケットをネイティブに転送するように設定することが望ましい場合があります。 そうすれば、検索はまったく行われず、非LISPサイト宛てのパケットはいかなる形でも不利益を受けません。
トラフィックエンジニアリング：
展開シナリオによっては、LISPトラフィックと非LISPトラフィックに異なるトラフィックエンジニアリングポリシーを適用することが望ましい場合があります。 LISP固有のEIDブロックがあれば、LISPトラフィックと非LISPトラフィックに関するトラフィックエンジニアリングの能力が向上するでしょう。 特に、カプセル化されたパケットを解析するためにディープパケットインスペクション（Deep Packet Inspection、DPI）の技術を使用しなくても、LISPトラフィックを識別できる可能性があります。 代わりに、外側のヘッダーを簡単に検査するだけで十分です。
移行メカニズム：
LISP固有のEIDブロックの存在は、移行シナリオで有用であることがわかるかもしれません。 非LISPドメインは、LISP EIDブロック内の割り当てを要求し、それを使用して自身のネットワークにLISPを展開することになるでしょう。 そのような割り当ては、BGPルーティングインフラストラクチャーでは広報されません（セクション4を参照）。 このアプローチにより、非LISPドメインは、すでに割り当てられている非LISPのアドレス空間の断片化を避けることができます。 そのアドレス空間は（正当に）BGPルーティングインフラストラクチャーで広報される可能性があるため、断片化するとBGPルーティングテーブルの肥大化につながる可能性があります。
BGPルーティングインフラストラクチャーへの影響の抑制：
前のシナリオで説明したように、断片化はBGPルーティングインフラストラクチャーに悪影響を与えるため、LISPの採用者は自身のアドレス空間の断片化を避けることになるでしょう。 採用者はEIDブロックのアドレス空間を使用することになり、そのアドレス空間はプロキシートンネルルーター（Proxy Tunnel Router、PxTR）によってのみ、大きな集約単位で、厳密に管理された方法で広報される可能性があります。

It is worth mentioning that new use cases may arise in the future, due to new and unforeseen scenarios.

新しい予期しないシナリオにより、将来新しいユースケースが生じる可能性があることにも言及しておく価値があります。

Furthermore, the use of a dedicated address block allows for tighter control over the traffic in the initial experimental phase (especially filtering), while facilitating its large-scale deployment.

さらに、専用のアドレスブロックを使用することで、初期の実験段階においてトラフィックをより厳密に制御（特にフィルタリング）できると同時に、その大規模な展開も容易になります。

[RFC3692] considers assigning experimental and testing numbers useful; having a reserved IPv6 prefix enables this practice. The present document follows the guidelines provided in [RFC3692], with one exception. [RFC3692] suggests the use of values similar to those called "Private Use" in [RFC5226], which by definition are not unique. One purpose of the present request to IANA is to guarantee uniqueness to the EID block. The lack thereof would result in a lack of real utility of a reserved IPv6 prefix.

[RFC3692]は、実験用およびテスト用の番号を割り当てることを有用だとみなしています。 予約済みのIPv6プレフィックスがあれば、この慣行が可能になります。 この文書は、1つの例外を除いて、[RFC3692]で示されたガイドラインに従います。 [RFC3692]は、[RFC5226]で「Private Use」と呼ばれるものに類似した値を使用することを提案していますが、それらは定義上一意ではありません。 IANAに対する今回の要求の目的の1つは、EIDブロックの一意性を保証することです。 一意性がなければ、予約済みのIPv6プレフィックスは実際には役に立たなくなってしまいます。

4. Expected Use

4. 想定される用途

Sites planning to deploy LISP may request a prefix in the IPv6 EID block. Such prefixes will be used for routing and endpoint identification inside the site requesting it. Mappings related to such a prefix, or part of it, will be made available through the mapping system in use and registered to one or more Map-Server(s).

LISPの展開を計画しているサイトは、IPv6 EIDブロック内のプレフィックスを要求できます。 そのようなプレフィックスは、それを要求したサイト内でのルーティングとエンドポイントの識別に使用されます。 そのようなプレフィックス、またはその一部に関するマッピングは、使用中のマッピングシステムを通じて利用可能になり、1つ以上のMap-Serverに登録されます。

The EID block must be used for LISP experimentation and must not be advertised in the form of more specific route advertisements in the non-LISP inter-domain routing environment. Interworking between the EID block sub-prefixes and the non-LISP Internet is done according to the techniques described in [RFC6832] and [RFC7215].

EIDブロックはLISPの実験に使用する必要があり、非LISPのドメイン間ルーティング環境において、より詳細な経路広告の形で広告してはいけません。 EIDブロックのサブプレフィックスと非LISPのインターネットとの間のインターワーキングは、[RFC6832]と[RFC7215]で説明されている技術に従って行われます。

As the LISP adoption progresses, the EID block may potentially have a reduced impact on the BGP routing infrastructure, compared to the case of having the same number of adopters using global unicast space allocated by Regional Internet Registries (RIRs) ([MobiArch2007]). From a short-term perspective, the EID block offers potentially large aggregation capabilities since it is announced by Proxy Tunnel Routers (PxTRs), possibly concentrating several contiguous prefixes. This trend should continue with even lower impact from a long-term perspective, because more aggressive aggregation can be used, potentially leading to using fewer PxTRs announcing the whole EID block ([FIABook2010]).

LISPの採用が進むにつれて、同じ数の採用者が地域インターネットレジストリー（Regional Internet Registry、RIR）によって割り当てられたグローバルユニキャスト空間を使用する場合と比較して、EIDブロックがBGPルーティングインフラストラクチャーに与える影響は小さくなる可能性があります（[MobiArch2007]）。 短期的な観点では、EIDブロックはプロキシートンネルルーター（PxTR）によって広報され、場合によっては複数の連続したプレフィックスをまとめることになるため、大きな集約能力を提供する可能性があります。 長期的な観点では、より積極的な集約を使用できるため、この傾向はさらに影響を小さくしながら続くはずであり、EIDブロック全体を広報するPxTRの数を減らすことにつながる可能性があります（[FIABook2010]）。

The EID block will be used only at the configuration level, so it is recommended not to hard-code the IPv6 EID block in the router hardware in any way. This prevents locking out sites that may want to switch to LISP while keeping their own IPv6 prefix, which is not in the IPv6 EID block. Furthermore, in the case of a future permanent allocation, the allocated prefix may differ from the experimental temporary prefix allocated during the experimentation phase.

EIDブロックは設定のレベルでのみ使用されるため、IPv6 EIDブロックをルーターのハードウェアにいかなる形でもハードコードしないことが推奨されます。 これにより、IPv6 EIDブロックに含まれない自身のIPv6プレフィックスを維持したままLISPに切り替えたいサイトを締め出すことを防げます。 さらに、将来恒久的な割り当てが行われる場合、割り当てられるプレフィックスは、実験段階で割り当てられた実験用の一時的なプレフィックスとは異なる可能性があります。

With the exception of the Proxy Ingress Tunnel Router (PITR) case (described in Section 8), prefixes out of the EID block must not be announced in the BGP routing infrastructure.

セクション8で説明するプロキシー入口トンネルルーター（Proxy Ingress Tunnel Router、PITR）の場合を除き、EIDブロックから切り出したプレフィックスをBGPルーティングインフラストラクチャーで広報してはいけません。

5. Block Dimension

5. ブロックのサイズ

The working group reached consensus on an initial allocation of a /32 prefix. The reason of such consensus is manifold:

ワーキンググループは、/32プレフィックスを初期割り当てとすることでコンセンサスに達しました。 このコンセンサスの理由は多岐にわたります。

  • The working group agreed that the /32 prefix is sufficiently large to cover initial allocation and requests for prefixes in the EID space in the next few years for very large-scale experimentation and deployment.
  • As a comparison, it is worth mentioning that the current LISP Beta Network ([BETA]) is using a /32 prefix, with more than 250 sites using a /48 sub-prefix. Hence, a /32 prefix appears sufficiently large to allow the current deployment to scale up and be open for interoperation with independent deployments using the EIDs in the new /32 prefix.
  • A /32 prefix is sufficiently large to allow deployment of independent (commercial) LISP-enabled networks by third parties, but may as well boost LISP experimentation and deployment.
  • The use of a /32 prefix is in line with previous similar prefix allocation for tunneling protocols ([RFC3056]).
  • ワーキンググループは、/32プレフィックスが、今後数年間の非常に大規模な実験と展開のための初期割り当てと、EID空間内のプレフィックスの要求をまかなうのに十分な大きさであることに合意しました。
  • 比較として、現在のLISPベータネットワーク（[BETA]）は/32プレフィックスを使用しており、250を超えるサイトが/48のサブプレフィックスを使用していることに言及しておく価値があります。 したがって、/32プレフィックスは、現在の展開を拡大し、新しい/32プレフィックスのEIDを使用する独立した展開との相互運用に開かれたものにするのに十分な大きさであると思われます。
  • /32プレフィックスは、第三者による独立した（商用の）LISP対応ネットワークの展開を可能にするのに十分な大きさであり、同時にLISPの実験と展開を促進する可能性もあります。
  • /32プレフィックスの使用は、トンネリングプロトコルのための過去の同様のプレフィックス割り当て（[RFC3056]）と一致しています。

6. 3+3 Allocation Plan

6. 3+3割り当て計画

Per this document, IANA has initially assigned a /32 prefix out of the IPv6 addressing space for use as EID in LISP.

この文書に基づき、IANAは当初、LISPのEIDとして使用するために、IPv6アドレス空間から/32プレフィックスを割り当てました。

IANA allocated the requested address space in September 2016 for a duration of 3 (three) years (through September 2019), with an option to extend this period by 3 (three) more years (until September 2022). By the end of the first period, the IETF will provide a decision on whether to transform the prefix into a permanent assignment or to put it back in the free pool (see Section 7 for more information).

IANAは、要求されたアドレス空間を2016年9月に3年間（2019年9月まで）割り当て、この期間をさらに3年間（2022年9月まで）延長するオプションを設けました。 最初の期間の終わりまでに、IETFは、このプレフィックスを恒久的な割り当てに変更するか、フリープールに戻すかの決定を下します（詳細についてはセクション7を参照）。

In the first case, i.e., if the IETF decides to transform the block into a permanent allocation, the EID block allocation period will be extended for three years (until September 2022) to give the IETF time to define the final size of the EID block and create a transition plan. The transition of the EID block into a permanent allocation might pose policy issues (as recognized in [RFC2860], Section 4.3); therefore, discussion with the IANA, the RIR communities, and the IETF community will be necessary to determine the appropriate policy for permanent EID-block allocation and management. Note as well that the final permanent allocation may differ from the initial experimental assignment; hence, it is recommended not to hard-code the experimental EID block on LISP-capable devices in any way.

前者の場合、つまりIETFがブロックを恒久的な割り当てに変更することを決定した場合、IETFがEIDブロックの最終的なサイズを定め、移行計画を作成する時間を確保するために、EIDブロックの割り当て期間は3年間（2022年9月まで）延長されます。 EIDブロックの恒久的な割り当てへの移行は、（[RFC2860], セクション4.3で認識されているように）ポリシー上の問題を引き起こす可能性があります。 したがって、恒久的なEIDブロックの割り当てと管理のための適切なポリシーを決定するには、IANA、RIRコミュニティー、およびIETFコミュニティーとの議論が必要になります。 また、最終的な恒久的割り当ては初期の実験的な割り当てとは異なる可能性があることにも注意してください。 したがって、実験用のEIDブロックをLISP対応機器にいかなる形でもハードコードしないことが推奨されます。

In the latter case, i.e., if the IETF decides to terminate the experimental-use EID block, all temporary prefix allocations in this address range must expire and be released by September 2019, so that the entire /32 is returned to the free pool.

後者の場合、つまりIETFが実験用のEIDブロックを終了することを決定した場合、/32全体がフリープールに戻されるように、このアドレス範囲内のすべての一時的なプレフィックス割り当ては2019年9月までに失効し、解放されなければなりません。

The allocation and management of the EID block for the initial 3-year period (and the optional 3 more years) is detailed in [RFC7955].

最初の3年間（およびオプションの追加の3年間）におけるEIDブロックの割り当てと管理については、[RFC7955]で詳しく説明されています。

7. Allocation Lifetime

7. 割り当ての有効期間

If no explicit action is carried out by the end of the experiment (by September 2019), it is automatically considered that there was not sufficient interest in having a permanent allocation; therefore, the address block will be returned to the free pool.

実験の終了まで（2019年9月まで）に明示的なアクションが何も行われなかった場合、恒久的な割り当てに対する十分な関心がなかったものと自動的にみなされます。 したがって、そのアドレスブロックはフリープールに戻されます。

Otherwise, if the LISP working group recognizes that there is value in having a permanent allocation, then explicit action is needed.

そうではなく、LISPワーキンググループが恒久的な割り当てに価値があると認めた場合は、明示的なアクションが必要です。

In order to trigger the process for a permanent allocation, a document is required. Such a document has to articulate the rationale for why a permanent allocation would be beneficial. More specifically, the document has to detail the experience gained during experimentation and all of the technical benefits provided by the use of a LISP-specific prefix. Such technical benefits are expected to lay in the scenarios described in Section 3. However, new and unforeseen benefits may appear during experimentation. The description should be sufficiently articulate that the needed size of the permanent allocation can be estimated. However, note that, as explained in Section 6, it is up to IANA to decide which address block will be used as a permanent allocation and that such a block may be different from the temporary experimental allocation.

恒久的な割り当てのプロセスを開始するには、文書が必要です。 そのような文書は、恒久的な割り当てがなぜ有益であるかの根拠を明確に述べなければなりません。 より具体的には、その文書は、実験中に得られた経験と、LISP固有のプレフィックスを使用することでもたらされるすべての技術的な利点を詳しく説明しなければなりません。 そのような技術的な利点は、セクション3で説明したシナリオの中にあると予想されます。 ただし、実験中に新しい予期しない利点が現れる可能性もあります。 その説明は、恒久的な割り当てに必要なサイズを見積もることができるほど十分に明確であるべきです。 ただし、セクション6で説明したように、どのアドレスブロックを恒久的な割り当てとして使用するかを決定するのはIANAであり、そのブロックは一時的な実験用の割り当てとは異なる可能性があることに注意してください。

8. Routing Considerations

8. ルーティングに関する考慮事項

In order to provide connectivity between the Legacy Internet and LISP sites, PITRs announcing large aggregates (ideally one single, large aggregate) of the IPv6 EID block could be deployed. By doing so, PITRs will attract traffic destined for LISP sites in order to encapsulate and forward it toward the specific destination LISP site. Routers in the Legacy Internet must treat announcements of prefixes from the IPv6 EID block as normal announcements, applying best current practices for traffic engineering and security.

レガシーインターネットとLISPサイトの間の接続性を提供するために、IPv6 EIDブロックの大きな集約（理想的には単一の大きな集約）を広報するPITRを展開できます。 そうすることで、PITRはLISPサイト宛てのトラフィックを引き寄せ、それをカプセル化して特定の宛先LISPサイトに向けて転送します。 レガシーインターネットのルーターは、IPv6 EIDブロックのプレフィックスの広報を通常の広報として扱い、トラフィックエンジニアリングとセキュリティーに関する現在のベストプラクティスを適用しなければなりません。

Even in a LISP site, not all routers need to run LISP elements. In particular, routers that are not at the border of the local domain, used only for intra-domain routing, do not need to provide any specific LISP functionality but must be able to route traffic using addresses in the IPv6 EID block.

LISPサイト内であっても、すべてのルーターがLISPの要素を実行する必要はありません。 特に、ローカルドメインの境界になく、ドメイン内ルーティングにのみ使用されるルーターは、LISP固有の機能を提供する必要はありませんが、IPv6 EIDブロック内のアドレスを使用してトラフィックをルーティングできなければなりません。

For the above-mentioned reasons, routers that do not run any LISP element must not include any special handling code or hardware for addresses in the IPv6 EID block. In particular, it is recommended that the default router configuration not handle such addresses in any special way. Doing differently could prevent communication between the Legacy Internet and LISP sites or even break local intra-domain connectivity.

上記の理由により、LISPの要素を一切実行しないルーターは、IPv6 EIDブロック内のアドレスに対する特別な処理を行うコードやハードウェアを含めてはいけません。 特に、ルーターのデフォルト設定ではそのようなアドレスを特別な方法で扱わないことが推奨されます。 そうしないと、レガシーインターネットとLISPサイトの間の通信が妨げられたり、ローカルなドメイン内の接続性が損なわれたりする可能性があります。

9. Security Considerations

9. セキュリティーに関する考慮事項

This document does not introduce new security threats in the LISP architecture nor in the legacy Internet architecture.

この文書は、LISPアーキテクチャーにもレガシーインターネットのアーキテクチャーにも、新しいセキュリティー上の脅威をもたらしません。

10. IANA Considerations

10. IANAに関する考慮事項

IANA has assigned a /32 IPv6 prefix for use as the global EID space for LISP using a hierarchical allocation as outlined in [RFC5226] and summarized in Table 1. The assigned block is from the 2001:5 global unicast space.

IANAは、[RFC5226]で概説され、表1にまとめられている階層的な割り当てを用いて、LISPのグローバルEID空間として使用する/32のIPv6プレフィックスを割り当てました。 割り当てられたブロックは、2001:5のグローバルユニキャスト空間からのものです。

IANA is not requested to issue an AS0 Route Origin Attestation (ROA [RFC6491]), because the global EID space is be used for routing purposes.

グローバルEID空間はルーティングの目的で使用されるため、IANAはAS0のルートオリジン証明（Route Origin Attestation、ROA [RFC6491]）を発行するよう要求されてはいません。

The reserved address space is requested for an initial 3-year period starting in September 2016 (until September 2019), with an option to extend it by three years (until September 2022) upon the decision of the IETF (see Sections 6 and 7). Following the policies outlined in [RFC5226], upon IETF Review, the decision should be made on whether to have a permanent EID block assignment by September 2019. If no explicit action is taken or, if the IETF Review outcome is that it is not worth having a reserved prefix as a global EID space, the whole /32 will be taken out from the "IANA IPv6 Special-Purpose Address Registry" and put back in the free pool managed by IANA.

予約されたアドレス空間は、2016年9月から始まる最初の3年間（2019年9月まで）を対象に要求されており、IETFの決定により3年間（2022年9月まで）延長するオプションがあります（セクション6と7を参照）。 [RFC5226]で概説されているポリシーに従い、IETFレビューを経て、2019年9月までに恒久的なEIDブロックの割り当てを行うかどうかを決定すべきです。 明示的なアクションが何も行われなかった場合、またはIETFレビューの結果、グローバルEID空間として予約済みのプレフィックスを持つ価値がないとされた場合、/32全体が「IANA IPv6 Special-Purpose Address Registry」から取り除かれ、IANAが管理するフリープールに戻されます。

Allocation and management of the global EID space is detailed in [RFC7955]. Nevertheless, all prefix allocations out of this space must be temporary and no allocation must go beyond September 2019 unless the IETF Review decides for a permanent global EID space assignment.

グローバルEID空間の割り当てと管理については、[RFC7955]で詳しく説明されています。 いずれにせよ、IETFレビューで恒久的なグローバルEID空間の割り当てが決定されない限り、この空間から切り出したプレフィックスの割り当てはすべて一時的なものでなければならず、2019年9月を超える割り当てがあってはいけません。
