RFC 8191

Home Network Prefix Renumbering in Proxy Mobile IPv6 (PMIPv6)

RFC 8191

プロキシーモバイルIPv6（PMIPv6）におけるホームネットワークプレフィックスのリナンバリング

Abstract

概要

In the basic Proxy Mobile IPv6 (PMIPv6) specification, a Mobile Node (MN) is assigned with a Home Network Prefix (HNP) during its initial attachment, and the MN configures its Home Address (HoA) with the HNP. During the movement of the MN, the HNP remains unchanged to keep ongoing communications associated with the HoA. However, the current PMIPv6 specification does not specify related operations when HNP renumbering has occurred (e.g., due to change of service provider or site topology, etc.). In this document, a solution to support HNP renumbering is proposed, as an optional extension of the PMIPv6 specification.

基本的なプロキシーモバイルIPv6（PMIPv6）の仕様では、モバイルノード（Mobile Node、MN）は最初の接続時にホームネットワークプレフィックス（Home Network Prefix、HNP）を割り当てられ、MNはそのHNPを使って自身のホームアドレス（Home Address、HoA）を設定します。MNの移動中、HoAに関連付けられた進行中の通信を維持するために、HNPは変わらないままです。しかし、現在のPMIPv6の仕様では、HNPのリナンバリングが発生した場合（例: サービスプロバイダーやサイトのトポロジーの変更などによるもの）の関連する操作を規定していません。この文書では、PMIPv6の仕様のオプションの拡張として、HNPのリナンバリングをサポートする解決策を提案します。

1. Introduction

1. はじめに

At the time of writing, network managers prefer Provider-Independent (PI) addressing for IPv6 to attempt to minimize the need for future possible renumbering. However, a widespread use of PI addresses will cause Border Gateway Protocol (BGP) scaling problems [RFC7010]. It is thus desirable to develop tools and practices that make IPv6 renumbering a simpler process to reduce demand for IPv6 PI space [RFC6879]. In this document, we aim to support HNP renumbering when the HNP in PMIPv6 [RFC5213] is not a PI prefix.

この文書の執筆時点では、ネットワーク管理者は、将来起こり得るリナンバリングの必要性を最小限に抑えようとして、IPv6ではプロバイダー非依存（Provider-Independent、PI）アドレッシングを好んでいます。しかし、PIアドレスが広く使われると、ボーダーゲートウェイプロトコル（Border Gateway Protocol、BGP）のスケーリングの問題を引き起こします[RFC7010]。そのため、IPv6のPI空間の需要を減らすために、IPv6のリナンバリングをより簡単なプロセスにするツールと慣行を開発することが望まれます[RFC6879]。この文書では、PMIPv6 [RFC5213]のHNPがPIプレフィックスでない場合に、HNPのリナンバリングをサポートすることを目指します。

1.1. 要件言語

2. Usage Scenarios

2. 利用シナリオ

There are a number of reasons why HNP renumbering support in PMIPv6 is useful, and some scenarios are identified below:

PMIPv6でHNPのリナンバリングをサポートすることが有用である理由は数多くあり、いくつかのシナリオを以下に示します。

Scenario 1:
the HNP set used by a PMIPv6 service provider is assigned by a different Internet Service Provider (ISP), and then HNP renumbering MAY occur if the PMIPv6 service provider switches to a different ISP.
Scenario 2:
multiple Local Mobility Anchors (LMAs) MAY be deployed by the same PMIPv6 service provider, and then each LMA MAY serve for a specific HNP set. In this case, the HNP of an MN MAY change if the serving LMA is changed to another LMA that does not inherit the assigned HNP set [RFC6463].
Scenario 3:
PMIPv6 HNP renumbering MAY be caused by the rebuilding of the network architecture as the companies split, merge, grow, relocate, or reorganize. For example, the PMIPv6 service provider MAY reorganize its network topology.
シナリオ1:
PMIPv6サービスプロバイダーが使用するHNPの集合が、別のインターネットサービスプロバイダー（Internet Service Provider、ISP）によって割り当てられている場合です。このとき、PMIPv6サービスプロバイダーが別のISPに切り替えると、HNPのリナンバリングが発生する場合があります（MAY）。
シナリオ2:
同じPMIPv6サービスプロバイダーが複数のローカルモビリティーアンカー（Local Mobility Anchor、LMA）を配備する場合があります（MAY）。その場合、各LMAは特定のHNPの集合を受け持つ場合があります（MAY）。このとき、サービスを提供しているLMAが、割り当てられたHNPの集合を引き継がない別のLMAに変更されると、MNのHNPが変わる場合があります（MAY）[RFC6463]。
シナリオ3:
企業の分割、合併、成長、移転、再編に伴うネットワークアーキテクチャーの再構築によって、PMIPv6のHNPのリナンバリングが引き起こされる場合があります（MAY）。たとえば、PMIPv6サービスプロバイダーは自身のネットワークトポロジーを再編する場合があります（MAY）。

In Scenario 1, we assume that only the HNP is renumbered, while the serving LMA remains unchanged; this is the basic scenario considered in this document. In Scenarios 2 and 3, more complex situations MAY result; for example, HNP renumbering MAY occur due to the switchover of a serving LMA.

シナリオ1では、サービスを提供しているLMAは変わらず、HNPだけがリナンバリングされると仮定します。これがこの文書で検討する基本的なシナリオです。シナリオ2と3では、より複雑な状況になる場合があります（MAY）。たとえば、サービスを提供しているLMAの切り替えによって、HNPのリナンバリングが発生する場合があります（MAY）。

In the Mobile IPv6 (MIPv6) protocol, when an HNP changes, the Home Agent (HA) will actively notify its MN about the new prefix, and then the renumbering of the Home Network Address (HoA) can be well supported [RFC6275]. In basic PMIPv6, the PMIPv6 binding is triggered by a Mobile Access Gateway (MAG), which detects the attachment of the MN. A scheme is also needed for the LMA to immediately initiate the PMIPv6 binding state refreshment during the HNP renumbering process. Although this issue is also mentioned in Section 6.12 of [RFC5213], the related solution has not been specified.

モバイルIPv6（MIPv6）プロトコルでは、HNPが変わると、ホームエージェント（Home Agent、HA）が新しいプレフィックスについて能動的にMNに通知するので、ホームネットワークアドレス（Home Network Address、HoA）のリナンバリングを適切にサポートできます[RFC6275]。基本的なPMIPv6では、PMIPv6のバインディングは、MNの接続を検出するモバイルアクセスゲートウェイ（Mobile Access Gateway、MAG）によってトリガーされます。HNPのリナンバリングのプロセス中に、LMAがPMIPv6のバインディング状態の更新をただちに開始するための仕組みも必要です。この問題は[RFC5213]のセクション6.12でも言及されていますが、関連する解決策は規定されていません。

3. HNP Renumbering Procedure

3. HNPのリナンバリングの手順

When HNP renumbering happens in PMIPv6, the LMA MUST notify the MAG about the new HNP, and then the MAG MUST announce the new HNP to the attached MN accordingly. Also, the LMA and the MAG MUST update the routing states for the HNP and the related addresses. To support this procedure, [RFC7077] can be adopted; it specifies an asynchronous update from the LMA to the MAG about specific session parameters. This document considers the following two cases:

PMIPv6でHNPのリナンバリングが起こると、LMAは新しいHNPについてMAGに通知しなければなりません（MUST）。そして、MAGはそれに応じて、接続しているMNに新しいHNPを告知しなければなりません（MUST）。また、LMAとMAGは、HNPと関連するアドレスについてのルーティング状態を更新しなければなりません（MUST）。この手順をサポートするために、[RFC7077]を採用できます。これは、特定のセッションパラメーターについてのLMAからMAGへの非同期の更新を規定しています。この文書では、次の2つの場合を検討します。

  1. HNP is renumbered under the same LMA

    In this case, the LMA remains unchanged as in Scenarios 1 and 3. The steps are shown in Figure 1.

    • When a PMIPv6 service provider renumbers the HNP set under the same LMA, the serving LMA SHOULD initiate the HNP renumbering operation. The LMA allocates a new HNP for the related MN.
    • The LMA sends the Update Notification (UPN) message to the MAG to update the HNP information. If the Dynamic Host Configuration Protocol (DHCP) is used to allocate the address, the DHCP infrastructure MUST also be notified about the new HNP.
    • Once the MAG receives this UPN message, it recognizes that the related MN has the new HNP. Then, the MAG MUST notify the MN about the new HNP with a Router Advertisement (RA) message or allocate a new address within the new HNP through a DHCP procedure.
    • After the MN obtains the HNP information through the RA message, it deletes the old HoA and configures a new HoA with the newly allocated HNP.
    • When the new HNP is announced or the new address is configured to the MN successfully, the MAG MUST update the related binding and routing states. Then, the MAG sends back the Update Notification Acknowledgement (UPA) message to the LMA for the notification of successful update of the HNP, related binding state, and routing state. Then, the LMA updates the routing and binding information corresponding to the MN in order to replace the old HNP with the new one.

  2. HNP renumbering is caused by the LMA switchover

    Since the HNP is assigned by the LMA, HNP renumbering MAY be caused by the LMA switchover, as in Scenarios 2 and 3.

    The LMA information is the basic configuration information of the MAG. When the LMA changes, the related profile SHOULD be updated by the service provider. In this way, the MAG initiates the binding registration to the MN's new LMA as specified in [RFC5213]. When HNP renumbering is caused in this case, the new HNP information is sent by the LMA during the new binding procedure. Accordingly, the MAG withdraws the old HNP of the MN and announces the new HNP to the MN, similar to the case when the HNP is renumbered under the same LMA.

  1. HNPが同じLMAの下でリナンバリングされる場合

    この場合、シナリオ1と3のように、LMAは変わりません。手順を図1に示します。

    • PMIPv6サービスプロバイダーが同じLMAの下でHNPの集合をリナンバリングする場合、サービスを提供しているLMAがHNPのリナンバリング操作を開始すべきです（SHOULD）。LMAは、関係するMNに新しいHNPを割り当てます。
    • LMAは、HNPの情報を更新するために、Update Notification（UPN）メッセージをMAGに送信します。アドレスの割り当てに動的ホスト構成プロトコル（Dynamic Host Configuration Protocol、DHCP）を使う場合、DHCPのインフラストラクチャーにも新しいHNPについて通知しなければなりません（MUST）。
    • MAGは、このUPNメッセージを受信すると、関係するMNが新しいHNPを持つことを認識します。そして、MAGは、ルーター広告（Router Advertisement、RA）メッセージで新しいHNPについてMNに通知するか、DHCPの手順によって新しいHNPの範囲内の新しいアドレスを割り当てなければなりません（MUST）。
    • MNは、RAメッセージによってHNPの情報を得たあと、古いHoAを削除し、新しく割り当てられたHNPで新しいHoAを設定します。
    • 新しいHNPの告知、または新しいアドレスのMNへの設定が成功したら、MAGは関連するバインディング状態とルーティング状態を更新しなければなりません（MUST）。次に、MAGは、HNP、関連するバインディング状態、ルーティング状態の更新が成功したことを通知するために、Update Notification Acknowledgement（UPA）メッセージをLMAに送り返します。そして、LMAは、古いHNPを新しいHNPに置き換えるために、そのMNに対応するルーティング情報とバインディング情報を更新します。

  2. HNPのリナンバリングがLMAの切り替えによって引き起こされる場合

    HNPはLMAによって割り当てられるので、シナリオ2と3のように、HNPのリナンバリングがLMAの切り替えによって引き起こされる場合があります（MAY）。

    LMAの情報は、MAGの基本的な設定情報です。LMAが変わったときは、サービスプロバイダーが関連するプロファイルを更新すべきです（SHOULD）。こうすることで、MAGは[RFC5213]で規定されているとおりに、MNの新しいLMAへのバインディング登録を開始します。この場合にHNPのリナンバリングが引き起こされると、新しいHNPの情報は、新しいバインディングの手順の中でLMAから送られます。それに応じて、MAGは、HNPが同じLMAの下でリナンバリングされる場合と同様に、MNの古いHNPを取り下げ、新しいHNPをMNに告知します。

4. Session Connectivity

4. セッションの接続性

HNP renumbering MAY cause the disconnection of the ongoing communications of the MN. Basically, there are two modes to manage the session connectivity during HNP renumbering.

HNPのリナンバリングは、MNの進行中の通信の切断を引き起こす場合があります（MAY）。基本的に、HNPのリナンバリング中のセッションの接続性を管理するモードは2つあります。

  1. Soft mode

    The LMA will temporarily maintain the state of the old HNP during the HNP renumbering (after the UPA reception) in order to redirect the packets to the MN before the MN reconnects the ongoing session and notifies the Correspondent Node (CN) about its new HoA. This mode is aiming to reduce packet loss during HNP renumbering, but the binding state corresponding to the old HNP SHOULD be marked, for example, as transient binding [RFC6058]. Also, the LMA MUST stop broadcasting the routing information about the old HNP if the old HNP is no longer anchored at this LMA.

  2. Hard mode

    If HNP renumbering happens with the switchover of the LMA, hard mode is RECOMMENDED to keep the protocol simple. In this mode, the LMA deletes the binding state of the old HNP after it receives the UPA message from the MAG, and the LMA silently discards the packets destined to the old HNP.

  1. ソフトモード

    LMAは、MNが進行中のセッションを再接続し、新しいHoAについて通信相手ノード（Correspondent Node、CN）に通知する前にパケットをMNにリダイレクトするために、HNPのリナンバリング中（UPAの受信後）、古いHNPの状態を一時的に維持します。このモードは、HNPのリナンバリング中のパケットロスを減らすことを目的としていますが、古いHNPに対応するバインディング状態には、たとえば一時的バインディング（transient binding）[RFC6058]として印を付けるべきです（SHOULD）。また、古いHNPがもはやこのLMAにアンカーされていない場合、LMAは古いHNPについてのルーティング情報のブロードキャストを停止しなければなりません（MUST）。

  2. ハードモード

    HNPのリナンバリングがLMAの切り替えを伴って起こる場合、プロトコルを簡潔に保つために、ハードモードが推奨されます（RECOMMENDED）。このモードでは、LMAは、MAGからUPAメッセージを受信したあとに古いHNPのバインディング状態を削除し、古いHNP宛てのパケットを黙って破棄します。

5. Message Format

5. メッセージフォーマット

  1. UPN message

    In the UPN message sent from the LMA to the MAG, the notification reason is set to 2 (UPDATE-SESSION-PARAMETERS). Besides, the HNP Option [RFC5213] containing the new HNP and the Mobile Node Identifier Option [RFC4283] (which identifies the MN) are contained as Mobility Options of UPN. The order of the HNP Option and Mobile Node Identifier Option in the UPN message is not mandated here.

  2. UPA message

    The MAG sends this message in order to acknowledge that it has received an UPN message with the (A) flag set and to indicate the status after processing the message. If the MAG did not successfully renumber the HNP, which is required in the UPN message, the UPA message has the Status Code set to 128 (FAILED-TO-UPDATE-SESSION-PARAMETERS), and the subsequent operation of the LMA is PMIPv6 service provider specific.

  3. RA message

    When the RA message is used by the MAG to advise the new HNP, it contains two Prefix Information Options [RFC4861] [RFC4862]. In the first Prefix Information Option, the old HNP is carried, and the related Preferred Lifetime is set to 0. In the second Prefix Information Option, the new HNP is carried with the Valid Lifetime, and Preferred Lifetime set to larger than 0.

  4. DHCP message

    When the DHCP is used in PMIPv6 to configure the addresses for the MN, new IPv6 address or addresses (e.g., the HoA) will be generated based on the new HNP, and the related DHCP procedure is also triggered by the reception of the UPN message [RFC3315].

  1. UPNメッセージ

    LMAからMAGに送られるUPNメッセージでは、通知の理由（notification reason）を2（UPDATE-SESSION-PARAMETERS）に設定します。さらに、新しいHNPを含むHNPオプション[RFC5213]と、（MNを識別する）Mobile Node Identifierオプション[RFC4283]を、UPNのモビリティーオプションとして含めます。UPNメッセージ内のHNPオプションとMobile Node Identifierオプションの順序は、ここでは規定しません。

  2. UPAメッセージ

    MAGは、(A)フラグがセットされたUPNメッセージを受信したことを確認応答し、そのメッセージを処理したあとの状態を示すために、このメッセージを送信します。UPNメッセージで要求されたHNPのリナンバリングにMAGが成功しなかった場合、UPAメッセージのStatus Codeは128（FAILED-TO-UPDATE-SESSION-PARAMETERS）に設定され、その後のLMAの動作はPMIPv6サービスプロバイダーに固有のものとなります。

  3. RAメッセージ

    MAGが新しいHNPを知らせるためにRAメッセージを使う場合、そのメッセージには2つのプレフィックス情報オプション[RFC4861] [RFC4862]が含まれます。1つ目のプレフィックス情報オプションでは、古いHNPを運び、関連するPreferred Lifetimeを0に設定します。2つ目のプレフィックス情報オプションでは、新しいHNPを運び、Valid LifetimeとPreferred Lifetimeを0より大きい値に設定します。

  4. DHCPメッセージ

    PMIPv6でMNのアドレスを設定するためにDHCPを使う場合、新しいHNPに基づいて1つまたは複数の新しいIPv6アドレス（例: HoA）が生成され、関連するDHCPの手順もUPNメッセージの受信によってトリガーされます[RFC3315]。

6. Other Issues

6. その他の問題

In order to maintain the reachability of the MN, the Domain Name System (DNS) resource record corresponding to this MN MAY need to be updated when the HNP of the MN changes [RFC3007]. However, this is beyond the scope of this document.

MNの到達可能性を維持するために、MNのHNPが変わったときに、そのMNに対応するドメインネームシステム（Domain Name System、DNS）のリソースレコードを更新する必要がある場合があります（MAY）[RFC3007]。ただし、これはこの文書の範囲外です。

7. Security Considerations

7. セキュリティーに関する考慮事項

The UPN and UPA messages in this document MUST be protected using end-to-end security association(s) offering integrity and data origin authentication as specified in [RFC5213] and [RFC7077].

この文書のUPNメッセージとUPAメッセージは、[RFC5213]と[RFC7077]で規定されているとおり、完全性とデータ発信元認証を提供するエンドツーエンドのセキュリティーアソシエーションを使って保護しなければなりません（MUST）。

When HNP renumbering is triggered, a new HNP SHOULD be allocated to the MN. The LMA MUST follow the procedure of PMIPv6 to make sure that only an authorized HNP can be assigned for the MN. In this way, the LMA is ready to be the topological anchor point of the new HNP, which is for that MN's exclusive use.

HNPのリナンバリングがトリガーされたときは、新しいHNPをMNに割り当てるべきです（SHOULD）。LMAは、認可されたHNPだけがMNに割り当てられることを確実にするために、PMIPv6の手順に従わなければなりません（MUST）。こうすることで、LMAは、そのMN専用の新しいHNPのトポロジー上のアンカーポイントとなる準備が整います。

Per [RFC4862], if the Valid Lifetime in a Prefix Information Option is set to less than 2 hours in an unauthenticated RA, it is ignored. Thus, when the old HNP that is being deprecated is included in an RA from the MAG, the Valid Lifetime SHOULD be set to 2 hours (and the Preferred Lifetime set to 0) for an unauthenticated RA. However, if the legality of the signaling messages exchanged between MAG and MN can be guaranteed, it MAY be acceptable to also set the Valid Lifetime to 0 for an unauthenticated RA.

[RFC4862]によれば、認証されていないRAにおいて、プレフィックス情報オプションのValid Lifetimeが2時間未満に設定されている場合、それは無視されます。したがって、廃止されようとしている古いHNPがMAGからのRAに含まれる場合、認証されていないRAでは、Valid Lifetimeを2時間に（そしてPreferred Lifetimeを0に）設定するべきです（SHOULD）。ただし、MAGとMNの間でやり取りされるシグナリングメッセージの正当性を保証できる場合は、認証されていないRAについて、Valid Lifetimeも0に設定することが許容される場合があります（MAY）。
