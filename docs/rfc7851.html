Peer-to-Peer (P2P) Overlay Diagnostics

RFC 7851

ピアツーピア（P2P）オーバーレイの診断

Abstract

概要

This document describes mechanisms for Peer-to-Peer (P2P) overlay diagnostics. It defines extensions to the REsource LOcation And Discovery (RELOAD) base protocol to collect diagnostic information and details the protocol specifications for these extensions. Useful diagnostic information for connection and node status monitoring is also defined. The document also describes the usage scenarios and provides examples of how these methods are used to perform diagnostics.

この文書は、ピアツーピア（P2P）オーバーレイの診断のためのメカニズムを記述します。 この文書は、診断情報を収集するためのREsource LOcation And Discovery（RELOAD）基本プロトコルの拡張を定義し、これらの拡張のプロトコル仕様を詳述します。 接続とノードの状態の監視に役立つ診断情報も定義します。 また、この文書は、利用シナリオを記述し、これらの方法を使って診断を実施する例を示します。

1. Introduction

1. はじめに

In the last few years, overlay networks have rapidly evolved and emerged as a promising platform for deployment of new applications and services in the Internet. One of the reasons overlay networks are seen as an excellent platform for large-scale distributed systems is their resilience in the presence of failures. This resilience has three aspects: data replication, routing recovery, and static resilience. Routing recovery algorithms are used to repopulate the routing table with live nodes when failures are detected. Static resilience measures the extent to which an overlay can route around failures even before the recovery algorithm repairs the routing table. Both routing recovery and static resilience rely on accurate and timely detection of failures.

ここ数年で、オーバーレイネットワークは急速に進化し、インターネットにおける新しいアプリケーションやサービスを展開するための有望なプラットフォームとして台頭してきました。 オーバーレイネットワークが大規模分散システムの優れたプラットフォームとみなされている理由の1つは、障害が存在する状況での回復力です。 この回復力には、データの複製、ルーティングの回復、静的な回復力という3つの側面があります。 ルーティング回復アルゴリズムは、障害が検出されたときに、生きているノードでルーティングテーブルを再構成するために使われます。 静的な回復力は、回復アルゴリズムがルーティングテーブルを修復する前であっても、オーバーレイが障害を迂回してルーティングできる程度を表します。 ルーティングの回復と静的な回復力はどちらも、障害の正確かつ適時の検出に依存しています。

There are a number of situations in which some nodes in a Peer-to-Peer (P2P) overlay may malfunction or behave badly. For example, these nodes may be disabled, congested, or may be misrouting messages. The impact of these malfunctions on the overlay network may be a degradation of quality of service provided collectively by the peers in the overlay network or an interruption of the overlay services. It is desirable to identify malfunctioning or badly behaving peers through diagnostic tools and exclude or reject them from the P2P system. Node failures may also be caused by failures of underlying layers. For example, recovery from an incorrect overlay topology may be slow when the speed at which IP routing recovers after link failures is very slow. Moreover, if a backbone link fails and the failover is slow, the network may be partitioned, leading to partitions of overlay topologies and inconsistent routing results between different partitioned components.

ピアツーピア（P2P）オーバーレイ内の一部のノードが、誤動作したり不正な振る舞いをしたりする状況は数多くあります。 たとえば、これらのノードは、機能停止していたり、輻輳していたり、メッセージを誤ってルーティングしていたりする可能性があります。 こうした誤動作がオーバーレイネットワークに与える影響としては、オーバーレイネットワーク内のピアが全体として提供するサービス品質の低下や、オーバーレイサービスの中断が考えられます。 診断ツールによって、誤動作しているピアや不正な振る舞いをしているピアを特定し、P2Pシステムから排除または拒否できることが望まれます。 ノードの障害は、下位層の障害によって引き起こされることもあります。 たとえば、リンク障害後のIPルーティングの回復速度が非常に遅い場合、誤ったオーバーレイトポロジーからの回復が遅くなる可能性があります。 さらに、バックボーンリンクに障害が発生し、フェイルオーバーが遅い場合、ネットワークが分断され、オーバーレイトポロジーの分断や、分断された異なる部分の間でのルーティング結果の不整合につながる可能性があります。

Some keep-alive algorithms based on periodic probe and acknowledge mechanisms enable accurate and timely detection of failures of one node's neighbors [Overlay-Failure-Detection], but these algorithms by themselves can only detect the disabled neighbors using the periodic method. This may not be sufficient for the service provider operating the overlay network.

定期的なプローブと確認応答のメカニズムに基づくいくつかのキープアライブアルゴリズムを使うと、あるノードの隣接ノードの障害を正確かつ適時に検出できます[Overlay-Failure-Detection]。 しかし、これらのアルゴリズムは、それ自体では、定期的な方法を使って機能停止した隣接ノードを検出することしかできません。 これは、オーバーレイネットワークを運用するサービスプロバイダーにとって十分ではない場合があります。

A P2P overlay diagnostic framework supporting periodic and on-demand methods for detecting node failures and network failures is desirable. This document describes a general P2P overlay diagnostic extension to the base protocol RELOAD [RFC6940] and is intended as a complement to keep-alive algorithms in the P2P overlay itself. Readers are advised to consult [P2PSIP-CONCEPTS] for further background on the problem domain.

ノードの障害とネットワークの障害を検出するための定期的な方法とオンデマンドの方法をサポートする、P2Pオーバーレイ診断フレームワークが望まれます。 この文書は、基本プロトコルであるRELOAD[RFC6940]に対する汎用的なP2Pオーバーレイ診断の拡張を記述します。 この拡張は、P2Pオーバーレイ自体のキープアライブアルゴリズムを補完することを意図しています。 問題領域に関するさらなる背景については、[P2PSIP-CONCEPTS]を参照することを読者に勧めます。

2. Terminology

2. 用語

This document uses the concepts defined in RELOAD [RFC6940]. In addition, the following terms are used in the document:

この文書は、RELOAD[RFC6940]で定義されている概念を使用します。 さらに、この文書では次の用語を使用します。

overlay hop:
One overlay hop is one portion of path between the initiator node and the destination peer in a RELOAD overlay. Each time packets are passed to the next node in the RELOAD overlay, one overlay hop occurs.
underlay hop:
An underlay hop is one portion of the path between source and destination in the IP layer. Each time packets are passed to the next IP-layer device, an underlay hop occurs.
オーバーレイホップ（overlay hop）:
1つのオーバーレイホップは、RELOADオーバーレイにおけるイニシエーターノードと宛先ピアとの間の経路の一区間です。 パケットがRELOADオーバーレイ内の次のノードに渡されるたびに、1つのオーバーレイホップが発生します。
アンダーレイホップ（underlay hop）:
アンダーレイホップは、IP層における送信元と宛先との間の経路の一区間です。 パケットが次のIP層デバイスに渡されるたびに、1つのアンダーレイホップが発生します。

この文書におけるキーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 [RFC2119]に記載されているとおりに解釈されるものとします。

3. Diagnostic Scenarios

3. 診断のシナリオ

P2P systems are self-organizing, and ideally the setup and configuration of individual P2P nodes requires no network management in the traditional sense. However, users of an overlay as well as P2P service providers may contemplate usage scenarios where some monitoring and diagnostics are required. We present a simple connectivity test and some useful diagnostic information that may be used in such diagnostics.

P2Pシステムは自己組織化するものであり、理想的には、個々のP2Pノードのセットアップと設定に従来の意味でのネットワーク管理は必要ありません。 しかし、オーバーレイのユーザーやP2Pサービスプロバイダーは、何らかの監視と診断が必要となる利用シナリオを想定することがあります。 ここでは、そのような診断で使用できる、簡単な接続性テストといくつかの有用な診断情報を示します。

The common usage scenarios for P2P diagnostics can be broadly categorized in three classes:

P2P診断の一般的な利用シナリオは、大きく3つの種類に分類できます。

  1. Automatic diagnostics built into the P2P overlay routing protocol. Nodes perform periodic checks of known neighbors and remove those nodes from the routing tables that fail to respond to connectivity checks [Handling_Churn_in_a_DHT]. Unresponsive nodes may only be temporarily disabled, for example, due to a local cryptographic processing overload, disk processing overload, or link overload. It is therefore useful to repeat the connectivity checks to see nodes have recovered and can be again placed in the routing tables. This process is known as 'failed node recovery' and can be optimized as described in the paper "Handling Churn in a DHT" [Handling_Churn_in_a_DHT].
  2. Diagnostics used by a particular node to follow up on an individual user complaint or failure. For example, a technical support staff member may use a desktop sharing application (with the permission of the user) to remotely determine the health of, and possible problems with, the malfunctioning node. Part of the remote diagnostics may consist of simple connectivity tests with other nodes in the P2P overlay and retrieval of statistics from nodes in the overlay. The simple connectivity tests are not dependent on the type of P2P overlay. Note that other tests may be required as well, including checking the health and performance of the user's computer or mobile device and checking the bandwidth of the link connecting the user to the Internet.
  3. P2P system-wide diagnostics used to check the overall health of the P2P overlay network. These include checking the consumption of network bandwidth, checking for the presence of problem links, and checking for abusive or malicious nodes. This is not a trivial problem and has been studied in detail for content and streaming P2P overlays [Diagnostic_Framework] and has not been addressed in earlier documents. While this is a difficult problem, a great deal of information that can help in diagnosing these problems can be obtained by obtaining basic diagnostic information for peers and the network. This document provides a framework for obtaining this information.
  1. P2Pオーバーレイのルーティングプロトコルに組み込まれた自動診断。 ノードは既知の隣接ノードを定期的にチェックし、接続性チェックに応答しないノードをルーティングテーブルから削除します[Handling_Churn_in_a_DHT]。 応答しないノードは、たとえば、ローカルの暗号処理の過負荷、ディスク処理の過負荷、リンクの過負荷のために、一時的に機能停止しているだけかもしれません。 したがって、接続性チェックを繰り返して、ノードが回復してルーティングテーブルに再び登録できるかどうかを確認することが有用です。 このプロセスは「障害ノードの回復（failed node recovery）」として知られており、論文「Handling Churn in a DHT」[Handling_Churn_in_a_DHT]で説明されているように最適化できます。
  2. 個々のユーザーからの苦情や障害を追跡調査するために、特定のノードが使用する診断。 たとえば、テクニカルサポートのスタッフは、（ユーザーの許可を得て）デスクトップ共有アプリケーションを使用し、誤動作しているノードの健全性や考えられる問題をリモートで判断するかもしれません。 リモート診断の一部は、P2Pオーバーレイ内の他のノードとの簡単な接続性テストや、オーバーレイ内のノードからの統計情報の取得で構成されることがあります。 簡単な接続性テストは、P2Pオーバーレイの種類に依存しません。 ユーザーのコンピューターやモバイルデバイスの健全性と性能のチェックや、ユーザーをインターネットに接続するリンクの帯域幅のチェックなど、他のテストも必要になる場合があることに注意してください。
  3. P2Pオーバーレイネットワーク全体の健全性をチェックするために使用する、P2Pシステム全体の診断。 これには、ネットワーク帯域幅の消費のチェック、問題のあるリンクの存在のチェック、不正なノードや悪意のあるノードのチェックが含まれます。 これは自明な問題ではなく、コンテンツおよびストリーミングのP2Pオーバーレイについては詳細に研究されていますが[Diagnostic_Framework]、これまでの文書では扱われていません。 これは難しい問題ですが、ピアとネットワークの基本的な診断情報を取得することで、これらの問題の診断に役立つ多くの情報を得られます。 この文書は、この情報を取得するためのフレームワークを提供します。

4. Data Collection Mechanisms

4. データ収集のメカニズム

4.1. Overview of Operations

4.1. 動作の概要

The diagnostic mechanisms described in this document are primarily intended to detect and locate failures or monitor performance in P2P overlay networks. It provides mechanisms to detect and locate malfunctioning or badly behaving nodes including disabled nodes, congested nodes, and misrouting peers. It provides a mechanism to detect direct connectivity or connectivity to a specified node, a mechanism to detect the availability of specified resource records, and a mechanism to discover P2P overlay topology and the underlay topology failures.

この文書で記述する診断メカニズムは、主に、P2Pオーバーレイネットワークにおける障害を検出して位置を特定すること、または性能を監視することを目的としています。 このメカニズムは、機能停止したノード、輻輳したノード、誤ったルーティングをするピアなど、誤動作しているノードや不正な振る舞いをしているノードを検出して位置を特定するメカニズムを提供します。 また、直接の接続性や指定したノードへの接続性を検出するメカニズム、指定したリソースレコードの可用性を検出するメカニズム、P2Pオーバーレイトポロジーを把握し、アンダーレイトポロジーの障害を発見するメカニズムを提供します。

The RELOAD diagnostics extensions define two mechanisms to collect data. The first is an extension to the RELOAD Ping mechanism that allows diagnostic data to be queried from a node as well as to diagnose the path to that node. The second is a new method, PathTrack, for collecting diagnostic information iteratively. Payloads for these mechanisms allowing diagnostic data to be collected and represented are presented, and additional error codes are introduced. Essentially, this document reuses the RELOAD specification [RFC6940] and extends it to introduce the new diagnostics methods. The extensions strictly follow how RELOAD specifies message routing, transport, NAT traversal, and other RELOAD protocol features.

RELOAD診断拡張は、データを収集するための2つのメカニズムを定義します。 1つ目は、RELOADのPingメカニズムの拡張で、ノードに診断データを問い合わせたり、そのノードまでの経路を診断したりできるようにするものです。 2つ目は、診断情報を反復的に収集するための新しいメソッドPathTrackです。 これらのメカニズムで診断データを収集して表現できるようにするペイロードを示し、追加のエラーコードを導入します。 本質的に、この文書はRELOADの仕様[RFC6940]を再利用し、それを拡張して新しい診断メソッドを導入します。 この拡張は、RELOADがメッセージのルーティング、トランスポート、NATトラバーサル、その他のRELOADプロトコルの機能をどのように規定しているかに厳密に従います。

This document primarily describes how to detect and locate failures including disabled nodes, congested nodes, misrouting behaviors, and underlying network faults in P2P overlay networks through a simple and efficient mechanism. This mechanism is modeled after the ping/traceroute paradigm: ping [RFC792] is used for connectivity checks, and traceroute is used for hop-by-hop fault localization as well as path tracing. This document specifies a "ping-like" mode (by extending the RELOAD Ping method to gather diagnostics) and a "traceroute-like" mode (by defining the new PathTrack method) for diagnosing P2P overlay networks.

この文書は主に、単純で効率的なメカニズムを通じて、P2Pオーバーレイネットワークにおける障害（機能停止したノード、輻輳したノード、誤ったルーティングの振る舞い、下位のネットワークの故障など）を検出して位置を特定する方法を記述します。 このメカニズムは、ping/tracerouteの枠組みをモデルにしています。 ping[RFC792]は接続性チェックに使用され、tracerouteはホップバイホップでの故障箇所の特定や経路の追跡に使用されます。 この文書は、P2Pオーバーレイネットワークを診断するための、「pingのような」モード（RELOADのPingメソッドを拡張して診断情報を収集するもの）と、「tracerouteのような」モード（新しいPathTrackメソッドを定義するもの）を規定します。

One way these tools can be used is to detect the connectivity to the specified node or the availability of the specified resource record through the extended Ping operation. Once the overlay network receives some alarms about overlay service degradation or interruption, a Ping is sent. If the Ping fails, one can then send a PathTrack to determine where the fault lies.

これらのツールの使い方の1つは、拡張されたPing操作によって、指定したノードへの接続性や指定したリソースレコードの可用性を検出することです。 オーバーレイネットワークがオーバーレイサービスの劣化や中断に関する何らかの警告を受け取ると、Pingが送信されます。 Pingが失敗した場合は、続いてPathTrackを送信して、故障がどこにあるかを特定できます。

The diagnostic information can only be provided to authorized nodes. Some diagnostic information can be provided to all the participants in the P2P overlay, and some other diagnostic information can only be provided to the nodes authorized by the local or overlay policy. The authorization depends on the type of the diagnostic information and the administrative considerations and is application specific.

診断情報は、認可されたノードにのみ提供できます。 一部の診断情報はP2Pオーバーレイのすべての参加者に提供できますが、それ以外の診断情報は、ローカルまたはオーバーレイのポリシーによって認可されたノードにのみ提供できます。 認可は、診断情報の種類と管理上の考慮事項に依存し、アプリケーション固有です。

This document considers the general administrative scenario based on diagnostic Kind, where a whole overlay can authorize a certain kind of diagnostic information to a small list of particular nodes (e.g., administrative nodes). That means if a node gets the authorization to access a diagnostic Kind, it can access that information from all nodes in the overlay network. It leaves the scenario where a particular node authorizes its diagnostic information to a particular list of nodes out of scope. This could be achieved by extension of this document if there is a requirement in the near future. The default policy or access rule for a type of diagnostic information is "deny" unless specified in the diagnostics extension document. As the RELOAD protocol already requires that each message carries the message signature of the sender, the receiver of the diagnostics requests can use the signature to identify the sender. It can then use the overlay configuration file with this signature to determine which types of diagnostic information that node is authorized for.

この文書では、診断Kindに基づく一般的な管理シナリオを検討します。 このシナリオでは、オーバーレイ全体として、ある種類の診断情報へのアクセスを特定の少数のノード（たとえば、管理ノード）のリストに認可できます。 つまり、あるノードが診断Kindにアクセスする認可を得た場合、そのノードはオーバーレイネットワーク内のすべてのノードからその情報にアクセスできます。 特定のノードが自身の診断情報へのアクセスを特定のノードのリストに認可するシナリオは、範囲外とします。 近い将来に要件が生じた場合は、この文書の拡張によってこれを実現できるでしょう。 診断拡張の文書で規定されていない限り、ある種類の診断情報に対するデフォルトのポリシーまたはアクセスルールは「拒否（deny）」です。 RELOADプロトコルはすでに各メッセージが送信者のメッセージ署名を持つことを要求しているので、診断リクエストの受信者はその署名を使って送信者を識別できます。 受信者はさらに、この署名とともにオーバーレイ設定ファイルを使って、そのノードがどの種類の診断情報について認可されているかを判断できます。

In the remainder of this section we define mechanisms for collecting data, as well as the specific protocol extensions (message extensions, new methods, and error codes) required to collect this information. In Section 5 we discuss the format of the data collected, and in Section 6 we discuss detailed message processing.

このセクションの残りの部分では、データを収集するためのメカニズムと、この情報を収集するのに必要な具体的なプロトコル拡張（メッセージ拡張、新しいメソッド、エラーコード）を定義します。 セクション5では収集するデータの形式について、セクション6ではメッセージ処理の詳細について説明します。

It is important to note that the mechanisms described in this document do not guarantee that the information collected is in fact related to the previous failures. However, using the information from previous traversed nodes, the user (or management system) may be able to infer the problem. Symmetric routing can be achieved by using the Via List [RFC6940] (or an alternate DHT routing algorithm), but the response path is not guaranteed to be the same.

この文書で記述するメカニズムは、収集した情報が実際に以前の障害に関連していることを保証しないことに注意することが重要です。 しかし、以前に通過したノードからの情報を使うことで、ユーザー（または管理システム）は問題を推測できるかもしれません。 対称ルーティングは、Viaリスト[RFC6940]（または別のDHTルーティングアルゴリズム）を使うことで実現できますが、レスポンスの経路が同じになることは保証されません。

4.3. "Traceroute-like" Behavior: The PathTrack Method

4.3. 「tracerouteのような」振る舞い: PathTrackメソッド

We define a simple PathTrack method for retrieving diagnostic information iteratively.

診断情報を反復的に取得するための単純なPathTrackメソッドを定義します。

The operation of this request is shown below in Figure 2. The initiator node A asks its neighbor B which is the next hop peer to the destination ID, and B returns a message with the next hop peer C information, along with optional diagnostic information for B to the initiator node. Then the initiator node A asks the next hop peer C (direct response routing [RFC7263] or via symmetric routing) to return next hop peer D information and diagnostic information of C. Unless a failure prevents the message from being forwarded, this step can be repeated until the request reaches responsible peer D for the destination ID and retrieves the diagnostic information of peer D.

There have been proposals that RouteQuery and a series of Fetch requests can be used to replace the PathTrack mechanism; however, in the presence of high rates of churn, such an operation would not, strictly speaking, provide identical results, as the path may change between RouteQuery and Fetch operations. While obviously the path could change between steps of PathTrack as well, with a single message rather than two messages for query and fetch, less inconsistency is likely, and thus the use of a single message is preferred.

RouteQueryと一連のFetchリクエストを使ってPathTrackメカニズムを置き換えられるという提案がありました。 しかし、チャーンの発生率が高い状況では、RouteQuery操作とFetch操作の間で経路が変化する可能性があるため、そのような操作は厳密に言えば同一の結果をもたらしません。 もちろんPathTrackのステップ間でも経路が変化する可能性はありますが、問い合わせと取得のための2つのメッセージではなく1つのメッセージを使うほうが不整合が少なくなると考えられるため、1つのメッセージを使うことが好まれます。

Given that in a typical diagnostic scenario the peer sending the PathTrack request desires to obtain information about the current path to the destination, in the event that successive calls to PathTrack return different paths, the results should be discarded and the request resent, ensuring that the second request traverses the appropriate path.

典型的な診断シナリオでは、PathTrackリクエストを送信するピアは宛先までの現在の経路に関する情報を得たいと考えるので、連続したPathTrackの呼び出しが異なる経路を返した場合は、結果を破棄してリクエストを再送し、2回目のリクエストが適切な経路を通過するようにすべきです。

4.3.1. New RELOAD Request: PathTrack

4.3.1. 新しいRELOADリクエスト: PathTrack

This document defines a new RELOAD method, PathTrack, to retrieve the diagnostic information from the intermediate peers along the routing path. At each step of the PathTrack request, the responsible peer responds to the initiator node with requested status information. Status information can include a peer's congestion state, processing power, available bandwidth, the number of entries in its neighbor table, uptime, identity, network address information, and next hop peer information.

この文書は、ルーティング経路上の中間ピアから診断情報を取得するための新しいRELOADメソッドPathTrackを定義します。 PathTrackリクエストの各ステップで、担当ピアは要求された状態情報をイニシエーターノードに応答します。 状態情報には、ピアの輻輳状態、処理能力、利用可能な帯域幅、隣接テーブルのエントリー数、稼働時間、アイデンティティー、ネットワークアドレス情報、ネクストホップピアの情報を含めることができます。

A PathTrack request specifies which diagnostic information is requested using a DiagnosticsRequest data structure, which is defined and discussed in detail in Section 5.1. Base information is requested by setting the appropriate flags in the data structure in the request. If all flags are clear (no bits are set), then the PathTrack request is only used for requesting the next hop information. In this case, the iterative mode of PathTrack is degraded to a RouteQuery method that is only used for checking the liveness of the peers along the routing path. The PathTrack request can be routed using direct response routing or other routing methods chosen by the initiator node.

PathTrackリクエストは、DiagnosticsRequestデータ構造体を使って、どの診断情報を要求するかを指定します。 このデータ構造体は、セクション5.1で定義し、詳しく説明します。 基本情報は、リクエスト内のデータ構造体で適切なフラグを設定することで要求します。 すべてのフラグがクリアされている（どのビットもセットされていない）場合、PathTrackリクエストはネクストホップの情報を要求するためだけに使われます。 この場合、PathTrackの反復モードは、ルーティング経路上のピアの生存確認にのみ使用されるRouteQueryメソッドに格下げされます。 PathTrackリクエストは、直接応答ルーティングや、イニシエーターノードが選択した他のルーティング方法を使ってルーティングできます。

5. 診断のデータ構造体

Both the extended Ping method and PathTrack method use the following common diagnostics data structures to collect data. Two common structures are defined: DiagnosticsRequest for requesting data and DiagnosticsResponse for returning the information.

5.1. DiagnosticsRequest Data Structure

5.1. DiagnosticsRequestデータ構造体

The DiagnosticsRequest data structure is used to request diagnostic information and has the following form:

DiagnosticsRequestデータ構造体は、診断情報を要求するために使用され、次の形式をとります。

       enum{ (2^16-1) } DiagnosticKindId;

       struct{
           DiagnosticKindId kind;
           opaque  diagnostic_extension_contents<0..2^32-1>;
       }DiagnosticExtension;

       struct{
           uint64 expiration;
           uint64 timestamp_initiated;
           uint64 dMFlags;
           uint32 ext_length;
           DiagnosticExtension diagnostic_extensions_list<0..2^32-1>;
        }DiagnosticsRequest;

       enum{ (2^16-1) } DiagnosticKindId;

       struct{
           DiagnosticKindId kind;
           opaque  diagnostic_extension_contents<0..2^32-1>;
       }DiagnosticExtension;

       struct{

The fields in the DiagnosticsRequest are as follows:

DiagnosticsRequestのフィールドは次のとおりです。

expiration:
The time when the request will expire represented as the number of milliseconds elapsed since midnight Jan 1, 1970 UTC (not counting leap seconds). This will have the same values for seconds as standard UNIX time or POSIX time. More information can be found at "Unix time" in Wikipedia [UnixTime]. This value MUST have a value between 1 and 600 seconds in the future. This value is used to prevent replay attacks.
timestamp_initiated:
The time when the diagnostics request was initiated, represented as the number of milliseconds elapsed since midnight Jan 1, 1970 UTC (not counting leap seconds). This will have the same values for seconds as standard UNIX time or POSIX time.
dMFlags:

A mandatory field that is an unsigned 64-bit integer indicating which base diagnostic information the request initiator node is interested in. The initiator sets different bits to retrieve different kinds of diagnostic information. If dMFlags is set to zero, then no base diagnostic information is conveyed in the PathTrack response. If dMFlags is set to all "1"s, then all base diagnostic information values are requested. A request may set any number of the flags to request the corresponding diagnostic information.

Note this memo specifies the initial set of flags; the flags can be extended. The dMflags indicate general diagnostic information. The mapping between the bits in the dMFlags and the diagnostic Kind ID presented is as described in Section 9.1.

ext_length:
The length of the extended diagnostic request information in bytes. If the value is greater than or equal to 1, then some extended diagnostic information is being requested on the assumption this information will be included in the response if the recipient understands the extended request and is willing to provide it. The specific diagnostic information requested is defined in the diagnostic_extensions_list below. A value of zero indicates no extended diagnostic information is being requested. The value of ext_length MUST NOT be negative. Note that it is not the length of the entire DiagnosticsRequest data structure, but of the data making up the diagnostic_extensions_list.
diagnostic_extensions_list:

Consists of one or more DiagnosticExtension structures (see below) documenting additional diagnostic information being requested. Each DiagnosticExtension consists of the following fields:

kind:
A numerical code indicating the type of extension diagnostic information (see Section 9.2). Note that kinds 0xf000 - 0xfffe are reserved for overlay specific diagnostics and may be used without IANA registration for local diagnostic information. Kinds from 0x0000 to 0x003f MUST NOT be indicated in the diagnostic_extensions_list in the message request, as they may be represented using the dMFlags in a much simpler (and more space efficient) way.
diagnostic_extension_contents:
The opaque data containing the request for this particular extension. This data is extension dependent.
expiration:
リクエストが期限切れになる時刻。 1970年1月1日午前0時（UTC）からの経過ミリ秒数（うるう秒は数えない）で表します。 秒の値は、標準のUNIX時間またはPOSIX時間と同じになります。 詳しい情報は、Wikipediaの「Unix time」[UnixTime]にあります。 この値は、1秒から600秒先までの間の値でなければなりません（MUST）。 この値はリプレイ攻撃を防ぐために使用します。
timestamp_initiated:
診断リクエストが開始された時刻。 1970年1月1日午前0時（UTC）からの経過ミリ秒数（うるう秒は数えない）で表します。 秒の値は、標準のUNIX時間またはPOSIX時間と同じになります。
dMFlags:

リクエストのイニシエーターノードがどの基本診断情報に関心を持っているかを示す、符号なし64ビット整数の必須フィールド。 イニシエーターは、異なる種類の診断情報を取得するために異なるビットをセットします。 dMFlagsが0に設定されている場合、PathTrackレスポンスで基本診断情報は伝達されません。 dMFlagsがすべて「1」に設定されている場合、すべての基本診断情報の値が要求されます。 リクエストは、対応する診断情報を要求するために、任意の数のフラグをセットできます。

このメモはフラグの初期セットを規定するものであり、フラグは拡張できることに注意してください。 dMflagsは一般的な診断情報を示します。 dMFlagsのビットと、示される診断Kind IDとの対応は、セクション9.1で説明するとおりです。

ext_length:
拡張診断リクエスト情報のバイト単位の長さ。 値が1以上の場合、何らかの拡張診断情報が要求されており、受信者が拡張リクエストを理解し、それを提供する意思がある場合には、この情報がレスポンスに含まれることが想定されています。 要求される具体的な診断情報は、後述のdiagnostic_extensions_listで定義します。 値が0の場合、拡張診断情報が要求されていないことを示します。 ext_lengthの値は負であってはなりません（MUST NOT）。 これはDiagnosticsRequestデータ構造体全体の長さではなく、diagnostic_extensions_listを構成するデータの長さであることに注意してください。
diagnostic_extensions_list:

要求される追加の診断情報を記述する、1つ以上のDiagnosticExtension構造体（下記参照）で構成されます。 各DiagnosticExtensionは次のフィールドで構成されます。

kind:
拡張診断情報の種類を示す数値コード（セクション9.2を参照）。 kind 0xf000～0xfffeはオーバーレイ固有の診断のために予約されており、ローカルな診断情報のためにIANAへの登録なしで使用できることに注意してください。 0x0000から0x003fまでのkindは、dMFlagsを使ってはるかに単純な（そしてより空間効率の良い）方法で表現できるため、メッセージリクエストのdiagnostic_extensions_listで示してはなりません（MUST NOT）。
diagnostic_extension_contents:
この特定の拡張に対するリクエストを含む不透明なデータ。 このデータは拡張に依存します。

5.2. DiagnosticsResponseデータ構造体

The DiagnosticsResponse data structure is used to return the diagnostic information and has the following form:

DiagnosticsResponseデータ構造体は、診断情報を返すために使用され、次の形式をとります。

            enum { (2^16-1) } DiagnosticKindId;

                DiagnosticKindId kind;

            struct{
                uint64 expiration;

The fields in the DiagnosticsResponse are as follows:

DiagnosticsResponseのフィールドは次のとおりです。

expiration:
The time when the response will expire represented as the number of milliseconds elapsed since midnight Jan 1, 1970 UTC (not counting leap seconds). This will have the same values for seconds as standard UNIX time or POSIX time. This value MUST have a value between 1 and 600 seconds in the future.
timestamp_initiated:
This value is copied from the diagnostics request message. The benefit of containing such a value in the response message is that the initiator node does not have to maintain the state.
timestamp_received:
The time when the diagnostic request was received represented as the number of milliseconds elapsed since midnight Jan 1, 1970 UTC (not counting leap seconds). This will have the same values for seconds as standard UNIX time or POSIX time.
hop_counter:
This field only appears in diagnostic responses. It MUST be exactly copied from the TTL field of the forwarding header in the received request. This information is sent back to the request initiator, allowing it to compute the number of hops that the message traversed in the overlay.
ext_length:
The length of the returned DiagnosticInfo information in bytes. If the value is greater than or equal to 1, then some extended diagnostic information (as specified in the DiagnosticsRequest) was available and is being returned. In that case, this value indicates the length of the returned information. A value of zero indicates no extended diagnostic information is included either because none was requested or the request could not be accommodated. The value of ext_length MUST NOT be negative. Note that it is not the length of the entire DiagnosticsRequest data structure but of the data making up the diagnostic_info_list.
diagnostic_info_list:

consists of one or more DiagnosticInfo structures containing the requested diagnostic_info_contents. The fields in the DiagnosticInfo structure are as follows:

kind:
A numeric code indicating the type of information being returned. For base data requested using the dMFlags, this code corresponds to the dMFlag set and is described in Section 5.1. For diagnostic extensions, this code will be identical to the value of the DiagnosticKindId set in the "kind" field of the DiagnosticExtension of the request. See Section 9.2.
diagnostic_info_contents:
Data containing the value for the diagnostic information being reported. Various kinds of diagnostic information can be retrieved. Please refer to Section 5.3 for details of the diagnostic Kind ID for the base diagnostic information that may be reported.
expiration:
レスポンスが期限切れになる時刻。 1970年1月1日午前0時（UTC）からの経過ミリ秒数（うるう秒は数えない）で表します。 秒の値は、標準のUNIX時間またはPOSIX時間と同じになります。 この値は、1秒から600秒先までの間の値でなければなりません（MUST）。
timestamp_initiated:
この値は、診断リクエストメッセージからコピーされます。 このような値をレスポンスメッセージに含める利点は、イニシエーターノードが状態を保持する必要がないことです。
timestamp_received:
診断リクエストが受信された時刻。 1970年1月1日午前0時（UTC）からの経過ミリ秒数（うるう秒は数えない）で表します。 秒の値は、標準のUNIX時間またはPOSIX時間と同じになります。
hop_counter:
このフィールドは診断レスポンスにのみ現れます。 受信したリクエストのフォワーディングヘッダーのTTLフィールドから正確にコピーしなければなりません（MUST）。 この情報はリクエストのイニシエーターに送り返され、イニシエーターはメッセージがオーバーレイ内で通過したホップ数を計算できます。
ext_length:
返されるDiagnosticInfo情報のバイト単位の長さ。 値が1以上の場合、（DiagnosticsRequestで指定された）何らかの拡張診断情報が利用可能であり、それが返されています。 その場合、この値は返される情報の長さを示します。 値が0の場合、何も要求されなかったか、リクエストに応えられなかったために、拡張診断情報が含まれていないことを示します。 ext_lengthの値は負であってはなりません（MUST NOT）。 これはDiagnosticsRequestデータ構造体全体の長さではなく、diagnostic_info_listを構成するデータの長さであることに注意してください。
diagnostic_info_list:

要求されたdiagnostic_info_contentsを含む、1つ以上のDiagnosticInfo構造体で構成されます。 DiagnosticInfo構造体のフィールドは次のとおりです。

kind:
返される情報の種類を示す数値コード。 dMFlagsを使って要求された基本データの場合、このコードはセットされたdMFlagに対応し、セクション5.1で説明しています。 診断拡張の場合、このコードは、リクエストのDiagnosticExtensionの「kind」フィールドに設定されたDiagnosticKindIdの値と同一になります。 セクション9.2を参照してください。
diagnostic_info_contents:
報告される診断情報の値を含むデータ。 さまざまな種類の診断情報を取得できます。 報告される可能性のある基本診断情報の診断Kind IDの詳細については、セクション5.3を参照してください。

5.3. dMFlags and Diagnostic Kind ID Types

5.3. dMFlagsと診断Kind IDの種類

The dMFlags field described above is a 64-bit field that allows initiator nodes to identify up to 62 items of base information to request in a request message (the first and last flags being reserved). The dMFlags also reserves all "0"s, which means nothing is requested, and all "1"s, which means everything is requested. But at the same time, the first and last bits cannot be used for other purposes, and they MUST be set to 0 when other particular diagnostic Kind IDs are requested. When the requested base information is returned in the response, the value of the diagnostic Kind ID will correspond to the numeric field marked in the dMFlags in the request. The values for the dMFlags are defined in Section 9.1 and the diagnostic Kind IDs are defined in Section 9.2. The information contained for each value is described in this section. Access to each kind of diagnostic information MUST NOT be allowed unless compliant to the rules defined in Section 7.

前述のdMFlagsフィールドは64ビットのフィールドで、イニシエーターノードはリクエストメッセージで要求する基本情報を最大62項目まで指定できます（最初と最後のフラグは予約されています）。 dMFlagsは、何も要求しないことを意味するすべて「0」の値と、すべてを要求することを意味するすべて「1」の値も予約しています。 ただし同時に、最初と最後のビットは他の目的には使用できず、他の特定の診断Kind IDを要求する場合には0に設定しなければなりません（MUST）。 要求された基本情報がレスポンスで返される場合、診断Kind IDの値は、リクエストのdMFlagsでマークされた数値フィールドに対応します。 dMFlagsの値はセクション9.1で、診断Kind IDはセクション9.2で定義します。 各値に含まれる情報は、このセクションで説明します。 各種類の診断情報へのアクセスは、セクション7で定義するルールに準拠しない限り、許可してはなりません（MUST NOT）。

STATUS_INFO (8 bits):

A single-value element containing an unsigned byte representing whether or not the node is in congestion status. An example usage of STATUS_INFO is for congestion-aware routing. In this scenario, each peer has to update its congestion status periodically. An intermediate peer in the Distributed Hash Table (DHT) network will choose its next hop according to both the DHT routing algorithm and the status information. This is done to avoid increasing load on congested peers. The rightmost 4 bits are used and other bits MUST be cleared to "0"s for future use.

There are 16 levels of congestion status, with 0x00 representing zero load and 0x0f representing congestion. This document does not provide a specific method for congestion and leaves this decision to each overlay implementation. One possible option for an overlay implementation would be to take node's CPU/memory/bandwidth usage percentage in the past 600 seconds and normalize the highest value to the range from 0x00 to 0x0f. An overlay implementation can also decide to not use all the 16 values from 0x00 to 0x0f. A future document may define an objective measure or specific algorithm for this.

ROUTING_TABLE_SIZE (32 bits):
A single-value element containing an unsigned 32-bit integer representing the number of peers in the peer's routing table. The administrator of the overlay may be interested in statistics of this value for reasons such as routing efficiency.
PROCESS_POWER (64 bits):
A single-value element containing an unsigned 64-bit integer specifying the processing power of the node with MIPS as the unit. Fractional values are rounded up.
UPSTREAM_BANDWIDTH (64 bits):
A single-value element containing an unsigned 64-bit integer specifying the upstream network bandwidth (provisioned or maximum, not available) of the node with units of kbit/s. Fractional values are rounded up. For multihomed hosts, this should be the link used to send the response.
DOWNSTREAM_BANDWIDTH (64 bits):
A single-value element containing an unsigned 64-bit integer specifying the downstream network bandwidth (provisioned or maximum, not available) of the node with kbit/s as the unit. Fractional values are rounded up. For multihomed hosts, this should be the link the request was received from.
SOFTWARE_VERSION:
A single-value element containing a US-ASCII string that identifies the manufacture, model, operating system information, and the version of the software. Given that there are a very large number of peers in some networks, and no peer is likely to know all other peer's software, this information may be very useful to help determine if the cause of certain groups of misbehaving peers is related to specific software versions. While the format is peer defined, a suggested format is as follows: "ApplicationProductToken (Platform; OS-or-CPU) VendorProductToken (VendorComment)", for example, "MyReloadApp/1.0 (Unix; Linux x86_64) libreload-java/0.7.0 (Stonyfish Inc.)". The string is a C-style string and MUST be terminated by "\0"."\0" MUST NOT be included in the string itself to prevent confusion with the delimiter.
MACHINE_UPTIME (64 bits):
A single-value element containing an unsigned 64-bit integer specifying the time the node's underlying system has been up (in seconds).
APP_UPTIME (64 bits):
A single-value element containing an unsigned 64-bit integer specifying the time the P2P application has been up (in seconds).
MEMORY_FOOTPRINT (64 bits):
A single-value element containing an unsigned 64-bit integer representing the memory footprint of the peer program in kilobytes (1024 bytes). Fractional values are rounded up.
DATASIZE_STORED (64 bits):
An unsigned 64-bit integer representing the number of bytes of data being stored by this node.
INSTANCES_STORED:
An array element containing the number of instances of each kind stored. The array is indexed by Kind-ID. Each entry is an unsigned 64-bit integer.
MESSAGES_SENT_RCVD:
An array element containing the number of messages sent and received. The array is indexed by method code. Each entry in the array is a pair of unsigned 64-bit integers (packed end to end) representing sent and received.
EWMA_BYTES_SENT (32 bits):

A single-value element containing an unsigned 32-bit integer representing an exponential weighted average of bytes sent per second by this peer:

   sent = alpha x sent_present + (1 - alpha) x sent_last

where sent_present represents the bytes sent per second since the last calculation and sent_last represents the last calculation of bytes sent per second. A suitable value for alpha is 0.8 (or another value as determined by the implementation). This value is calculated every five seconds (or another time period as determined by the implementation). The value for the very first time period should simply be the average of bytes sent in that time period.

EWMA_BYTES_RCVD (32 bits):

A single-value element containing an unsigned 32-bit integer representing an exponential weighted average of bytes received per second by this peer:

   rcvd = alpha x rcvd_present + (1 - alpha) x rcvd_last

where rcvd_present represents the bytes received per second since the last calculation and rcvd_last represents the last calculation of bytes received per second. A suitable value for alpha is 0.8 (or another value as determined by the implementation). This value is calculated every five seconds (or another time period as determined by the implementation). The value for the very first time period should simply be the average of bytes received in that time period.

UNDERLAY_HOP (8 bits):
Indicates the IP-layer hops from the intermediate peer, which receives the diagnostics message to the next-hop peer for this message. (Note: RELOAD does not require the intermediate peers to look into the message body. So, here we use PathTrack to gather underlay hops for diagnostics purpose).
BATTERY_STATUS (8 bits):
The leftmost bit is used to indicate whether this peer is using a battery or not. If this bit is clear (set to "0"), then the peer is using a battery for power. The other 7 bits are to be determined by specific applications.
STATUS_INFO（8ビット）:

ノードが輻輳状態にあるかどうかを表す符号なしバイトを含む単一値の要素。 STATUS_INFOの使用例として、輻輳を考慮したルーティングがあります。 このシナリオでは、各ピアは自身の輻輳状態を定期的に更新する必要があります。 分散ハッシュテーブル（DHT）ネットワーク内の中間ピアは、DHTのルーティングアルゴリズムと状態情報の両方に従ってネクストホップを選択します。 これは、輻輳しているピアの負荷が増えるのを避けるために行います。 右端の4ビットが使用され、他のビットは将来の使用のために「0」にクリアしなければなりません（MUST）。

輻輳状態には16段階のレベルがあり、0x00は負荷ゼロを、0x0fは輻輳を表します。 この文書は輻輳についての具体的な方法を提供せず、この判断を各オーバーレイの実装に任せます。 オーバーレイの実装で考えられる選択肢の1つは、過去600秒間におけるノードのCPU/メモリー/帯域幅の使用率をとり、最も高い値を0x00から0x0fまでの範囲に正規化することです。 オーバーレイの実装は、0x00から0x0fまでの16個の値をすべては使用しないと決めることもできます。 将来の文書で、このための客観的な尺度や具体的なアルゴリズムを定義するかもしれません。

ROUTING_TABLE_SIZE（32ビット）:
ピアのルーティングテーブル内のピア数を表す、符号なし32ビット整数を含む単一値の要素。 オーバーレイの管理者は、ルーティングの効率などの理由から、この値の統計に関心を持つかもしれません。
PROCESS_POWER（64ビット）:
MIPSを単位としてノードの処理能力を指定する、符号なし64ビット整数を含む単一値の要素。 端数は切り上げます。
UPSTREAM_BANDWIDTH（64ビット）:
kbit/sを単位としてノードの上り方向のネットワーク帯域幅（利用可能な帯域幅ではなく、プロビジョニングされた帯域幅または最大帯域幅）を指定する、符号なし64ビット整数を含む単一値の要素。 端数は切り上げます。 マルチホームのホストの場合、これはレスポンスの送信に使われるリンクのものであるべきです。
DOWNSTREAM_BANDWIDTH（64ビット）:
kbit/sを単位としてノードの下り方向のネットワーク帯域幅（利用可能な帯域幅ではなく、プロビジョニングされた帯域幅または最大帯域幅）を指定する、符号なし64ビット整数を含む単一値の要素。 端数は切り上げます。 マルチホームのホストの場合、これはリクエストを受信したリンクのものであるべきです。
SOFTWARE_VERSION:
製造元、モデル、オペレーティングシステムの情報、ソフトウェアのバージョンを識別するUS-ASCII文字列を含む単一値の要素。 一部のネットワークには非常に多数のピアが存在し、どのピアも他のすべてのピアのソフトウェアを知っている可能性は低いことを考えると、この情報は、特定の誤動作するピアのグループの原因が特定のソフトウェアバージョンに関係しているかどうかを判断するのに非常に役立つかもしれません。 形式はピアが定義するものですが、推奨される形式は次のとおりです。 「ApplicationProductToken (Platform; OS-or-CPU) VendorProductToken (VendorComment)」。 たとえば、「MyReloadApp/1.0 (Unix; Linux x86_64) libreload-java/0.7.0 (Stonyfish Inc.)」のようになります。 この文字列はC形式の文字列であり、「\0」で終端しなければなりません（MUST）。 区切り文字との混同を防ぐため、「\0」を文字列自体に含めてはなりません（MUST NOT）。
MACHINE_UPTIME（64ビット）:
ノードの下位のシステムが稼働している時間（秒単位）を指定する、符号なし64ビット整数を含む単一値の要素。
APP_UPTIME（64ビット）:
P2Pアプリケーションが稼働している時間（秒単位）を指定する、符号なし64ビット整数を含む単一値の要素。
MEMORY_FOOTPRINT（64ビット）:
ピアのプログラムのメモリーフットプリントをキロバイト（1024バイト）単位で表す、符号なし64ビット整数を含む単一値の要素。 端数は切り上げます。
DATASIZE_STORED（64ビット）:
このノードが格納しているデータのバイト数を表す符号なし64ビット整数。
INSTANCES_STORED:
格納されている各kindのインスタンス数を含む配列要素。 配列はKind-IDでインデックス付けされます。 各エントリーは符号なし64ビット整数です。
MESSAGES_SENT_RCVD:
送信および受信したメッセージ数を含む配列要素。 配列はメソッドコードでインデックス付けされます。 配列の各エントリーは、送信数と受信数を表す符号なし64ビット整数のペア（端から端まで詰めたもの）です。
EWMA_BYTES_SENT（32ビット）:

このピアが1秒あたりに送信したバイト数の指数加重平均を表す、符号なし32ビット整数を含む単一値の要素。

   sent = alpha x sent_present + (1 - alpha) x sent_last

ここで、sent_presentは前回の計算以降の1秒あたりの送信バイト数を表し、sent_lastは1秒あたりの送信バイト数の前回の計算結果を表します。 alphaの適切な値は0.8（または実装が決定する別の値）です。 この値は5秒ごと（または実装が決定する別の期間ごと）に計算されます。 最初の期間の値は、単にその期間に送信されたバイト数の平均とすべきです。

EWMA_BYTES_RCVD（32ビット）:

このピアが1秒あたりに受信したバイト数の指数加重平均を表す、符号なし32ビット整数を含む単一値の要素。

   rcvd = alpha x rcvd_present + (1 - alpha) x rcvd_last

ここで、rcvd_presentは前回の計算以降の1秒あたりの受信バイト数を表し、rcvd_lastは1秒あたりの受信バイト数の前回の計算結果を表します。 alphaの適切な値は0.8（または実装が決定する別の値）です。 この値は5秒ごと（または実装が決定する別の期間ごと）に計算されます。 最初の期間の値は、単にその期間に受信されたバイト数の平均とすべきです。

UNDERLAY_HOP（8ビット）:
診断メッセージを受信した中間ピアから、このメッセージのネクストホップピアまでのIP層のホップ数を示します。 （注: RELOADは、中間ピアがメッセージボディーの中を調べることを要求していません。 そのため、ここでは診断の目的でPathTrackを使ってアンダーレイのホップ数を収集します。）
BATTERY_STATUS（8ビット）:
左端のビットは、このピアがバッテリーを使用しているかどうかを示すために使用します。 このビットがクリアされている（「0」に設定されている）場合、ピアは電源としてバッテリーを使用しています。 残りの7ビットは、特定のアプリケーションによって決定されます。

6. Message Processing

6. メッセージ処理

6.1. Message Creation and Transmission

6.1. メッセージの作成と送信

When constructing either a Ping message with diagnostic extensions or a PathTrack message, the sender first creates and populates a DiagnosticsRequest data structure. The timestamp_initiated field is set to the current time, and the expiration field is constructed based on this time. The sender includes the dMFlags field in the structure, setting any number (including all) of the flags to request particular diagnostic information. The sender MAY leave all the bits unset, thereby requesting no particular diagnostic information.

診断拡張付きのPingメッセージまたはPathTrackメッセージのどちらかを構築する場合、送信者はまずDiagnosticsRequestデータ構造体を作成して値を設定します。 timestamp_initiatedフィールドは現在時刻に設定し、expirationフィールドはこの時刻に基づいて構築します。 送信者は構造体にdMFlagsフィールドを含め、特定の診断情報を要求するために任意の数の（すべてを含む）フラグをセットします。 送信者は、すべてのビットをセットしないままにして、特定の診断情報を何も要求しないようにしてもよいです（MAY）。

The sender MAY also include diagnostic extensions in the DiagnosticsRequest data structure to request additional information.

送信者は、追加の情報を要求するために、DiagnosticsRequestデータ構造体に診断拡張を含めてもよいです（MAY）。

If the sender includes any extensions, it MUST calculate the length of these extensions and set the ext_length field to this value. If no extensions are included, the sender MUST set ext_length to zero.

送信者は、何らかの拡張を含める場合、それらの拡張の長さを計算し、ext_lengthフィールドをこの値に設定しなければなりません（MUST）。 拡張を含めない場合、送信者はext_lengthを0に設定しなければなりません（MUST）。

The format of the DiagnosticRequest data structure and its fields MUST follow the restrictions defined in Section 5.1.

DiagnosticRequestデータ構造体とそのフィールドの形式は、セクション5.1で定義する制約に従わなければなりません（MUST）。

When constructing a Ping message with diagnostic extensions, the sender MUST create a MessageExtension structure as defined in RELOAD [RFC6940], setting the value of type to 0x2 and the value of critical to FALSE. The value of extension_contents MUST be a DiagnosticsRequest structure as defined above. The message MAY be directed to a particular NodeID or ResourceID but MUST NOT be sent to the broadcast NodeID.

診断拡張付きのPingメッセージを構築する場合、送信者は、RELOAD[RFC6940]で定義されているMessageExtension構造体を作成し、typeの値を0x2に、criticalの値をFALSEに設定しなければなりません（MUST）。 extension_contentsの値は、上記で定義したDiagnosticsRequest構造体でなければなりません（MUST）。 メッセージは、特定のNodeIDまたはResourceIDに宛ててもよいです（MAY）。 ただし、ブロードキャストNodeIDに送信してはなりません（MUST NOT）。

When constructing a PathTrack message, the sender MUST set the message_code for the RELOAD MessageContents structure to path_track_req 0x27. The request field of the PathTrackReq MUST be set to the DiagnosticsRequest data structure defined above. The destination field MUST be set to the desired destination, which MAY be either a NodeID or ResourceID but SHOULD NOT be the broadcast NodeID.

PathTrackメッセージを構築する場合、送信者は、RELOADのMessageContents構造体のmessage_codeをpath_track_req 0x27に設定しなければなりません（MUST）。 PathTrackReqのrequestフィールドは、上記で定義したDiagnosticsRequestデータ構造体に設定しなければなりません（MUST）。 destinationフィールドは、目的の宛先に設定しなければなりません（MUST）。 宛先はNodeIDとResourceIDのどちらでもよいです（MAY）が、ブロードキャストNodeIDにすべきではありません（SHOULD NOT）。

6.2. Message Processing: Intermediate Peers

6.2. メッセージ処理: 中間ピア

When a request arrives at a peer, if the peer's responsible ID space does not cover the destination ID of the request, then the peer MUST continue processing this request according to the overlay specified routing mode from RELOAD protocol.

リクエストがピアに到着したとき、そのピアが担当するIDの空間がリクエストの宛先IDを含まない場合、ピアは、RELOADプロトコルのオーバーレイで規定されたルーティングモードに従ってこのリクエストの処理を続行しなければなりません（MUST）。

In P2P overlay, error responses to a message can be generated by either an intermediate peer or the responsible peer. When a request is received at a peer, the peer may find connectivity failures or malfunctioning peers through the predefined rules of the overlay network, e.g., by analyzing the Via List or underlay error messages. In this case, the intermediate peer returns an error response to the initiator node, reporting any malfunction node information available in the error message payload. All error responses generated MUST contain the appropriate error code.

P2Pオーバーレイでは、メッセージに対するエラーレスポンスは、中間ピアと担当ピアのどちらでも生成できます。 ピアでリクエストを受信したとき、ピアは、オーバーレイネットワークの事前に定義されたルールによって（たとえば、Viaリストやアンダーレイのエラーメッセージを分析することによって）、接続性の障害や誤動作しているピアを見つけることがあります。 この場合、中間ピアはイニシエーターノードにエラーレスポンスを返し、利用可能な誤動作ノードの情報をエラーメッセージのペイロードで報告します。 生成されるすべてのエラーレスポンスは、適切なエラーコードを含まなければなりません（MUST）。

Each intermediate peer receiving a Ping message with extensions (and that understands the extension) or receiving a PathTrack request / response MUST check the expiration value (Unix time format) to determine if the message is expired. If the message expired, the intermediate peer MUST generate a response with error code 0x17 "Error_Message_Expired", return the response to the initiator node, and discard the message.

拡張付きのPingメッセージを受信した（そしてその拡張を理解する）各中間ピア、またはPathTrackリクエスト/レスポンスを受信した各中間ピアは、expirationの値（Unix時間形式）をチェックして、メッセージが期限切れかどうかを判断しなければなりません（MUST）。 メッセージが期限切れの場合、中間ピアは、エラーコード0x17「Error_Message_Expired」のレスポンスを生成し、そのレスポンスをイニシエーターノードに返し、メッセージを破棄しなければなりません（MUST）。

The intermediate peer MUST return an error response with the error code 0x15 "Error_Underlay_Destination_Unreachable" when it receives an ICMP message with "Destination Unreachable" information after forwarding the received request to the destination peer.

中間ピアは、受信したリクエストを宛先ピアに転送した後に「Destination Unreachable」情報を含むICMPメッセージを受信した場合、エラーコード0x15「Error_Underlay_Destination_Unreachable」のエラーレスポンスを返さなければなりません（MUST）。

The intermediate peer MUST return an error response with the error code 0x16 "Error_Underlay_Time_Exceeded" when it receives an ICMP message with "Time Exceeded" information after forwarding the received request.

中間ピアは、受信したリクエストを転送した後に「Time Exceeded」情報を含むICMPメッセージを受信した場合、エラーコード0x16「Error_Underlay_Time_Exceeded」のエラーレスポンスを返さなければなりません（MUST）。

The peer MUST return an error response with error code 0x18 "Error_Upstream_Misrouting" when it finds its upstream peer disobeys the routing rules defined in the overlay. The immediate upstream peer information MUST also be conveyed to the initiator node.

ピアは、上流ピアがオーバーレイで定義されたルーティングルールに従っていないことを発見した場合、エラーコード0x18「Error_Upstream_Misrouting」のエラーレスポンスを返さなければなりません（MUST）。 直近の上流ピアの情報もイニシエーターノードに伝えなければなりません（MUST）。

The peer MUST return an error response with error code 0x19 "Error_Loop_Detected" when it finds a loop through the analysis of the Via List.

ピアは、Viaリストの分析によってループを発見した場合、エラーコード0x19「Error_Loop_Detected」のエラーレスポンスを返さなければなりません（MUST）。

The peer MUST return an error response with error code 0x1a "Error_TTL_Hops_Exceeded" when it finds that the TTL field value is no more than 0 when forwarding.

ピアは、転送時にTTLフィールドの値が0以下であることを発見した場合、エラーコード0x1a「Error_TTL_Hops_Exceeded」のエラーレスポンスを返さなければなりません（MUST）。

6.3. Message Response Creation

6.3. メッセージレスポンスの作成

When a diagnostic request message arrives at a peer, it is responsible for the destination ID specified in the forwarding header, and assuming it understands the extension (in the case of Ping) or the new request type PathTrack, it MUST follow the specifications defined in RELOAD to form the response header, and perform the following operations:

診断リクエストメッセージがピアに到着し、そのピアがフォワーディングヘッダーで指定された宛先IDの担当であり、かつ（Pingの場合は）拡張を、または新しいリクエストタイプPathTrackを理解していると仮定すると、そのピアは、RELOADで定義されている仕様に従ってレスポンスヘッダーを形成し、次の操作を実行しなければなりません（MUST）。

  • When constructing a PathTrack response, the sender MUST set the message_code for the RELOAD MessageContents structure to path_track_ans 0x28.
  • The receiver MUST check the expiration value (Unix time format) in the DiagnosticsRequest to determine if the message is expired. If the message is expired, the peer MUST generate a response with the error code 0x17 "Error_Message_Expired", return the response to the initiator node, and discard the message.
  • If the message is not expired, the receiver MUST construct a DiagnosticsResponse structure as follows: 1) the TTL value from the forwarding header is copied to the hop_counter field of the DiagnosticsResponse structure (note that the default value for TTL at the beginning represents 100 hops unless the overlay configuration has overridden the value), and 2) the receiver generates a Unix time format timestamp for the current time of day and places it in the timestamp_received field and constructs a new expiration time and places it in the expiration field of the DiagnosticsResponse.
  • The destination peer MUST check if the initiator node has the authority to request specific types of diagnostic information, and if appropriate, append the diagnostic information requested in the dMFlags and diagnostic_extensions (if any) using the diagnostic_info_list field to the DiagnosticsResponse structure. If any information is returned, the receiver MUST calculate the length of the response and set ext_length appropriately. If no diagnostic information is returned, ext_length MUST be set to zero.
  • The format of the DiagnosticResponse data structure and its fields MUST follow the restrictions defined in Section 5.2.
  • In the event of an error, an error response containing the error code followed by the description (if they exist) MUST be created and sent to the sender. If the initiator node asks for diagnostic information that they are not authorized to query, the receiving peer MUST return an error response with the error code 2 "Error_Forbidden".
  • PathTrackレスポンスを構築する場合、送信者は、RELOADのMessageContents構造体のmessage_codeをpath_track_ans 0x28に設定しなければなりません（MUST）。
  • 受信者は、DiagnosticsRequest内のexpirationの値（Unix時間形式）をチェックして、メッセージが期限切れかどうかを判断しなければなりません（MUST）。 メッセージが期限切れの場合、ピアは、エラーコード0x17「Error_Message_Expired」のレスポンスを生成し、そのレスポンスをイニシエーターノードに返し、メッセージを破棄しなければなりません（MUST）。
  • メッセージが期限切れでない場合、受信者は次のようにDiagnosticsResponse構造体を構築しなければなりません（MUST）。 1) フォワーディングヘッダーのTTLの値を、DiagnosticsResponse構造体のhop_counterフィールドにコピーします（オーバーレイの設定でその値が上書きされていない限り、TTLの初期のデフォルト値は100ホップを表すことに注意してください）。 2) 受信者は、現在時刻のUnix時間形式のタイムスタンプを生成してtimestamp_receivedフィールドに格納し、新しい有効期限を構築してDiagnosticsResponseのexpirationフィールドに格納します。
  • 宛先ピアは、イニシエーターノードが特定の種類の診断情報を要求する権限を持っているかどうかをチェックし、適切であれば、dMFlagsとdiagnostic_extensions（存在する場合）で要求された診断情報を、diagnostic_info_listフィールドを使ってDiagnosticsResponse構造体に追加しなければなりません（MUST）。 何らかの情報を返す場合、受信者はレスポンスの長さを計算し、ext_lengthを適切に設定しなければなりません（MUST）。 診断情報を返さない場合、ext_lengthは0に設定しなければなりません（MUST）。
  • DiagnosticResponseデータ構造体とそのフィールドの形式は、セクション5.2で定義する制約に従わなければなりません（MUST）。
  • エラーが発生した場合は、エラーコードとそれに続く説明（存在する場合）を含むエラーレスポンスを作成し、送信者に送信しなければなりません（MUST）。 イニシエーターノードが問い合わせを認可されていない診断情報を要求した場合、受信したピアは、エラーコード2「Error_Forbidden」のエラーレスポンスを返さなければなりません（MUST）。

6.4. Interpreting Results

6.4. 結果の解釈

The initiator node, as well as the responding peer, may compute the overlay One-Way-Delay time through the value in timestamp_received and the timestamp_initiated field. However, for a single hop measurement, the traditional measurement methods (IP-layer ping) MUST be used instead of the overlay layer diagnostics methods.

イニシエーターノードと応答するピアは、timestamp_receivedの値とtimestamp_initiatedフィールドから、オーバーレイの片方向遅延（One-Way-Delay）時間を計算できます。 ただし、単一ホップの測定には、オーバーレイ層の診断方法ではなく、従来の測定方法（IP層のping）を使用しなければなりません（MUST）。

The P2P overlay network using the diagnostics methods specified in this document MUST enforce time synchronization with a central time server. The Network Time Protocol [RFC5905] can usually maintain time to within tens of milliseconds over the public Internet and can achieve better than one millisecond accuracy in local area networks under ideal conditions. However, this document does not specify the choice for time resolution and synchronization, leaving it to the implementation.

この文書で規定する診断方法を使用するP2Pオーバーレイネットワークは、中央のタイムサーバーとの時刻同期を強制しなければなりません（MUST）。 ネットワークタイムプロトコル[RFC5905]は、通常、公衆インターネット上では数十ミリ秒以内の精度で時刻を維持でき、理想的な条件下のローカルエリアネットワークでは1ミリ秒よりも高い精度を達成できます。 ただし、この文書は時刻の分解能と同期の選択を規定せず、実装に任せます。

The initiator node receiving the Ping response may check the hop_counter field and compute the overlay hops to the destination peer for the statistics of connectivity quality from the perspective of overlay hops.

Pingレスポンスを受信したイニシエーターノードは、hop_counterフィールドをチェックして宛先ピアまでのオーバーレイホップ数を計算し、オーバーレイホップの観点から接続品質の統計をとることができます。

7. オーバーレイ設定による認可

Different level of access control can be made for different users/nodes. For example, diagnostic information A can be accessed by nodes 1 and 2, but diagnostic information B can only be accessed by node 2.

ユーザーやノードごとに異なるレベルのアクセス制御を行うことができます。 たとえば、診断情報Aにはノード1と2がアクセスできるが、診断情報Bにはノード2しかアクセスできない、といったことです。

The overlay configuration file MUST contain the following XML elements for authorizing a node to access the relative diagnostic Kinds.

オーバーレイ設定ファイルは、ノードが関連する診断Kindにアクセスすることを認可するために、次のXML要素を含まなければなりません（MUST）。

diagnostic-kind:
This has the attribute "kind" with the hexadecimal number indicating the diagnostic Kind ID. This attribute has the same value with Section 9.2 and at least one subelement "access-node".

This element contains one hexadecimal number indicating a NodeID, and the node with this NodeID is allowed to access the diagnostic "kind" under the same diagnostic-kind element.
diagnostic-kind:
この要素は、診断Kind IDを示す16進数を値とする属性「kind」を持ちます。 この属性はセクション9.2と同じ値を持ちます。 また、この要素は少なくとも1つの子要素「access-node」を持ちます。
access-node:
この要素は、NodeIDを示す16進数を1つ含みます。 このNodeIDを持つノードは、同じdiagnostic-kind要素の下にある診断「kind」へのアクセスを許可されます。

8. Security Considerations

8. セキュリティーに関する考慮事項

The authorization for diagnostic information must be designed with care to prevent it becoming a method to retrieve information for both attacks. It should also be noted that attackers can use diagnostics to analyze overlay information to attack certain key peers. For example, diagnostic information might be used to fingerprint a peer where the peer will lose its anonymity characteristics, but anonymity might be very important for some P2P overlay networks, and defenses against such fingerprinting are probably very hard. As such, networks where anonymity is of very high importance may find implementation of diagnostics problematic or even undesirable, despite the many advantages it offers. As this document is a RELOAD extension, it follows RELOAD message header and routing specifications. The common security considerations described in the base document [RFC6940] are also applicable to this document. Overlays may define their own requirements on who can collect/share diagnostic information.

診断情報に対する認可は、それが両方の攻撃のための情報を取得する手段にならないよう、注意して設計する必要があります。 攻撃者が診断を使ってオーバーレイの情報を分析し、特定の重要なピアを攻撃できることにも注意すべきです。 たとえば、診断情報はピアのフィンガープリントを取るために使われる可能性があり、そうなるとピアは匿名性という特性を失います。 しかし、P2Pオーバーレイネットワークによっては匿名性が非常に重要な場合があり、そのようなフィンガープリンティングに対する防御はおそらく非常に困難です。 そのため、匿名性が非常に重視されるネットワークでは、診断には多くの利点があるにもかかわらず、その実装が問題である、あるいは望ましくないと判断されることさえあるかもしれません。 この文書はRELOADの拡張であるため、RELOADのメッセージヘッダーとルーティングの仕様に従います。 基本文書[RFC6940]で記述されている共通のセキュリティーに関する考慮事項は、この文書にも適用されます。 オーバーレイは、誰が診断情報を収集/共有できるかについて、独自の要件を定義できます。

Appendix A. Examples

付録A. 例

Below, we sketch how these metrics can be used.

以下では、これらの指標をどのように使用できるかを概説します。

A.1. Example 1

A.1. 例1

A peer may set EWMA_BYTES_SENT and EWMA_BYTES_RCVD flags in the PathTrackReq to its direct neighbors. A peer can use EWMA_BYTES_SENT and EWMA_BYTES_RCVD of another peer to infer whether it is acting as a media relay. It may then choose not to forward any requests for media relay to this peer. Similarly, among the various candidates for filling up a routing table, a peer may prefer a peer with a large UPTIME value, small RTT, and small LAST_CONTACT value.

ピアは、直接の隣接ノードへのPathTrackReqでEWMA_BYTES_SENTフラグとEWMA_BYTES_RCVDフラグをセットできます。 ピアは、別のピアのEWMA_BYTES_SENTとEWMA_BYTES_RCVDを使って、そのピアがメディアリレーとして動作しているかどうかを推測できます。 そのうえで、メディアリレーのリクエストをこのピアに転送しないことを選択できます。 同様に、ルーティングテーブルを埋めるためのさまざまな候補の中から、ピアは、UPTIMEの値が大きく、RTTが小さく、LAST_CONTACTの値が小さいピアを優先できます。

A.2. Example 2

A.2. 例2

A peer may set the STATUS_INFO Flag in the PathTrackReq to a remote destination peer. The overlay has its own threshold definition for congestion. The peer can obtain knowledge of all the status information of the intermediate peers along the path, then it can choose other paths to that node for the subsequent requests.

ピアは、リモートの宛先ピアへのPathTrackReqでSTATUS_INFOフラグをセットできます。 オーバーレイは、輻輳に関する独自のしきい値の定義を持っています。 ピアは、経路上の中間ピアのすべての状態情報を知ることができ、その後のリクエストでは、そのノードへの別の経路を選択できます。

A.3. Example 3

A.3. 例3

A peer may use Ping to evaluate the average overlay hops to other peers by sending PingReq to a set of random resource or node IDs in the overlay. A peer may adjust its timeout value according to the change of average overlay hops.

ピアは、オーバーレイ内のランダムなリソースIDまたはノードIDの集合にPingReqを送信することで、Pingを使って他のピアまでの平均オーバーレイホップ数を評価できます。 ピアは、平均オーバーレイホップ数の変化に応じて、タイムアウト値を調整できます。

Appendix B. Problems with Generating Multiple Responses on Path

付録B. 経路上で複数のレスポンスを生成することの問題点

An earlier draft version of this document considered an approach where a response was generated by each intermediate peer as the message traversed the overlay. This approach was discarded. One reason this approach was discarded was that it could provide a DoS mechanism, whereby an attacker could send an arbitrary message claiming to be from a spoofed "sender" the real sender wished to attack. As a result of sending this one message, many messages would be generated and sent back to the spoofed "sender" -- one from each intermediate peer on the message path. While authentication mechanisms could reduce some risk of this attack, it still resulted in a fundamental break from the request-response nature of the RELOAD protocol, as multiple responses are generated to a single request. Although one request with responses from all the peers in the route will be more efficient, it was determined to be too great a security risk and a deviation from the RELOAD architecture.

この文書の以前のドラフト版では、メッセージがオーバーレイを通過する際に各中間ピアがレスポンスを生成するアプローチを検討していました。 このアプローチは破棄されました。 このアプローチが破棄された理由の1つは、それがDoSのメカニズムを提供しうることでした。 つまり、攻撃者は、本当の送信者が攻撃したいと考える、なりすました「送信者」からのものであると主張する任意のメッセージを送信できてしまいます。 この1つのメッセージを送信した結果として、多数のメッセージ（メッセージの経路上の各中間ピアから1つずつ）が生成され、なりすまされた「送信者」に送り返されることになります。 認証メカニズムによってこの攻撃のリスクをある程度減らすことはできますが、1つのリクエストに対して複数のレスポンスが生成されるため、RELOADプロトコルのリクエスト-レスポンスという性質から根本的に逸脱することになります。 経路上のすべてのピアからのレスポンスを伴う1つのリクエストのほうが効率的ではありますが、セキュリティーリスクが大きすぎ、RELOADアーキテクチャーからの逸脱も大きすぎると判断されました。
