RFC 10053

A Framework for Computing-Aware Traffic Steering (CATS)

RFC 10053

Computing-Aware Traffic Steering（CATS）のためのフレームワーク

Abstract

概要

This document describes a framework for Computing-Aware Traffic Steering (CATS). Specifically, the document identifies a set of CATS functional components, describes their interactions, and provides illustrative workflows of the control and data planes. The framework covers only the case of a single service provider.

この文書は、Computing-Aware Traffic Steering（CATS）のためのフレームワークについて説明します。具体的には、この文書は、CATSの機能コンポーネントの集合を特定し、それらの相互作用を説明し、コントロールプレーンとデータプレーンのワークフローの例を示します。このフレームワークは、単一のサービスプロバイダーの場合のみを対象とします。

1. Introduction

1. はじめに

Computing service architectures evolved from a single service site to multiple, sometimes collaborative, service sites to address various issues such as long response times or suboptimal utilization of service and network resources (e.g., resource under-utilization or exhaustion).

コンピューティングサービスのアーキテクチャーは、長い応答時間や、サービスとネットワークのリソースの最適でない利用（たとえば、リソースの過少利用や枯渇）などのさまざまな問題に対処するために、単一のサービスサイトから、複数の（場合によっては協調する）サービスサイトへと進化しました。

The underlying networking infrastructures that include computing resources usually provide relatively static service dispatching (e.g., the selection of the service instances for a request). In such infrastructures, service-specific traffic is often directed to the closest service site from a routing perspective without considering the actual network state (e.g., traffic congestion conditions) or the service site state.

コンピューティングリソースを含む基盤となるネットワークインフラストラクチャーは、通常、比較的静的なサービスディスパッチ（たとえば、リクエストに対するサービスインスタンスの選択）を提供します。このようなインフラストラクチャーでは、サービス固有のトラフィックは、実際のネットワークの状態（たとえば、トラフィックの輻輳状況）やサービスサイトの状態を考慮せずに、ルーティングの観点で最も近いサービスサイトに向けられることがよくあります。

As described in [RFC10054], traffic steering that takes into account computing resource metrics would benefit several services, including latency-sensitive services such as immersive services that rely upon the use of augmented reality or virtual reality (AR/VR) techniques. This document provides an architectural framework that aims at facilitating the making of compute- and network-aware traffic steering decisions in dynamic networking environments with variable computing service resources.

[RFC10054]で説明されているように、コンピューティングリソースのメトリックを考慮したトラフィックステアリングは、拡張現実や仮想現実（AR/VR）の技術の使用に依存するイマーシブサービスなどの遅延に敏感なサービスを含む、いくつかのサービスに利益をもたらします。この文書は、コンピューティングサービスのリソースが変動する動的なネットワーク環境において、コンピューティングとネットワークを考慮したトラフィックステアリングの判断を容易にすることを目的としたアーキテクチャーのフレームワークを提供します。

Today, organizations often distribute user services across on-premises and cloud service provider networks. To support both redundancy and responsiveness, the Computing-Aware Traffic Steering (CATS) framework supports single or multiple service instances providing one given service, which may exist in one or more service sites. Clients access service instances via client-facing service functions known as service contact instances. A single service site may host one or multiple service contact instances. A single service site may have limited computing resources available at a given time, whereas the various service sites may experience different resource availability issues over time. Therefore, steering traffic among different service sites can address resource limitations in a specific service site.

今日、組織はユーザーサービスをオンプレミスとクラウドサービスプロバイダーのネットワークに分散させることがよくあります。冗長性と応答性の両方をサポートするために、Computing-Aware Traffic Steering（CATS）フレームワークは、ある1つのサービスを提供する単一または複数のサービスインスタンスをサポートし、それらは1つ以上のサービスサイトに存在する場合があります。クライアントは、サービスコンタクトインスタンスと呼ばれるクライアント向けのサービス機能を介してサービスインスタンスにアクセスします。単一のサービスサイトは、1つまたは複数のサービスコンタクトインスタンスをホストできます。単一のサービスサイトでは、ある時点で利用可能なコンピューティングリソースが限られている場合があり、一方でさまざまなサービスサイトは時間とともに異なるリソースの可用性の問題を経験する場合があります。したがって、異なるサービスサイト間でトラフィックを誘導することで、特定のサービスサイトにおけるリソースの制限に対処できます。

Steering in CATS aims to select the appropriate service contact instance to service a request according to a set of network and computing metrics. This selection may not reveal the actual service instance that a client will invoke (e.g., in hierarchical or recursive contexts). Therefore, the metrics of the service contact instance may be aggregate metrics from multiple service instances.

CATSにおけるステアリングは、ネットワークとコンピューティングのメトリックの集合に従って、リクエストを処理するのに適切なサービスコンタクトインスタンスを選択することを目的としています。この選択によって、クライアントが呼び出す実際のサービスインスタンスが明らかになるとは限りません（たとえば、階層的または再帰的な文脈の場合）。したがって、サービスコンタクトインスタンスのメトリックは、複数のサービスインスタンスからの集約メトリックである場合があります。

The CATS framework is an overlay framework for the selection of the suitable service contact instances from a set of candidates. The overlay is realized by means of encapsulation between CATS‑Forwarders. A combination of networking and computing metrics determines the exact characterization of services as "suitable" or not.

CATSフレームワークは、候補の集合から適切なサービスコンタクトインスタンスを選択するためのオーバーレイフレームワークです。オーバーレイは、CATS‑Forwarder間のカプセル化によって実現されます。ネットワークとコンピューティングのメトリックの組み合わせによって、サービスが「適切」であるかどうかの正確な特徴付けが決まります。

Furthermore, this document describes a workflow of the main CATS procedures (Section 4) executed in both the control and data planes. The framework covers only the case of a single service provider.

さらに、この文書は、コントロールプレーンとデータプレーンの両方で実行される主要なCATSの手順のワークフロー（Section 4）について説明します。このフレームワークは、単一のサービスプロバイダーの場合のみを対象とします。

This document assumes that CATS functional elements are hosted in a provider network. As such, it is out of scope to discuss deployment options where such elements are co-located with a client.

この文書は、CATSの機能要素がプロバイダーのネットワーク内でホストされていることを前提としています。そのため、そのような要素がクライアントと同じ場所に配置される展開の選択肢について議論することは範囲外です。

It is out of the scope of this document to provide a comprehensive list of CATS realization techniques or assess how existing mechanisms meet all CATS requirements.

CATSの実現技術の包括的なリストを提供したり、既存のメカニズムがCATSのすべての要件をどのように満たすかを評価したりすることは、この文書の範囲外です。

2. Terminology

2. 用語

This document makes use of the following terms:

この文書では、次の用語を使用します：

Client:

An endpoint that connects to a service provider network.

Flow:

A logical grouping of packets during a time interval, identified by some fields from the packet header, such as the 5-tuple transport coordinates (source address and destination address, source and destination port numbers, and protocol). Flow identification should also cover contexts where port numbers are not present (non-initial fragments, IP Encapsulating Security Payload (ESP) [RFC4303], etc.).

Computing-Aware Traffic Steering (CATS):

A traffic engineering approach [RFC9522] that takes into account the dynamic nature of computing resources (e.g., compute and storage) and network state to optimize service-specific traffic forwarding towards a given service contact instance. The CATS framework leverages various metrics to enable CATS policies.

Metric:

A quantitative measure that provides suitable input to a selection mechanism for CATS decision making. It can be a network metric or a computing metric.

Computing metric:

A metric specific to the computing resources in the underlying CATS systems as opposed to other metrics, such as network metrics. Examples of computing metrics are discussed in [CATS-METRICS].

Service:

An offering that is made available by a service provider by orchestrating a set of resources (networking, compute, storage, etc.).

The service provider retains control of internal resources and the service logic. For example, these resources may be:

  • Exposed by one or multiple processes.

  • Provided by virtual instances, physical instances, or a combination thereof.

  • Hosted within the same or distinct nodes.

  • Hosted within the same or multiple service sites.

  • Chained to provide a service using a variety of means.

How a service provider structures its services remains out of the scope of CATS.

Service providers may provide the same service in many locations; each of them constitutes a service instance.

Computing service:

A service offered to a client by a service provider by orchestrating a set of computing resources.

CATS Service ID (CS-ID):

An identifier representing a service, which the clients use to access it. See Section 3.2.

Service instance:

A collection of running resources that are orchestrated following a service logic. When invoked by a client request, these resources will collectively provide the intended service.

A service provider may enable many service instances that adhere to the same service logic to provide the same service.

A service instance runs in a service site and one or more instances may service clients' requests.

Service site:

A location that hosts the resources that implement one or more service instances.

A service site may be a node or a set of nodes.

Service contact instance:

A client-facing function that is responsible for receiving requests in the context of a given service.

A service contact instance can handle one or more service instances.

Steering beyond a service contact instance is hidden to both clients and CATS components.

A service contact instance processes a client's service request according to the service logic (e.g., handle locally or solicit backend resources).

A service contact instance is reachable via at least one Egress CATS‑Forwarder.

Clients may access a service via multiple service contact instances running at the same or different locations (service sites).

A service contact instance may dispatch service requests to one or more service instances (e.g., a service contact instance that behaves as a service load balancer).

CATS Service Contact Instance ID (CSCI-ID):

An identifier of a specific service contact instance. See Section 3.2.

Service request:

A request to access or invoke a specific service. CATS‑Forwarders steer a service request to a service contact instance.

Clients generate service requests using service-specific protocols.

Clients send service requests to a service instance (identified by a CS-ID), without explicit knowledge of CATS‑Forwarders.

CATS‑Forwarder:

A network entity that steers traffic specific to a service request towards a service contact instance according to forwarding decisions supplied by a CATS Path Selector (C-PS), which may or may not be part of a CATS‑Forwarder.

A CATS‑Forwarder may behave as an Ingress or Egress CATS‑Forwarder. See Section 3.4.6.

Ingress CATS‑Forwarder:

An entity that steers service-specific traffic along a CATS-computed path that leads to an Egress CATS- Forwarder. Such an Egress CATS‑Forwarder connects to the most suitable service site that hosts the service contact instance selected to satisfy the initial service request.

Egress CATS‑Forwarder:

An entity located at the end of a CATS-computed path, which connects to a service site.

CATS Path Selector (C-PS):

A functional entity that selects paths towards service sites and instances (and thus service contact instances) in order to accommodate the requirements of service requests. The path selection engine takes into account the service and network status information. See Section 3.4.4.

CATS Service Metric Agent (C-SMA):

A functional entity that is responsible for collecting service capabilities and status and for reporting them to a C-PS. See Section 3.4.2.

CATS Network Metric Agent (C-NMA):

A functional entity that is responsible for collecting network capabilities and status and for reporting them to a C-PS. See Section 3.4.3.

CATS Traffic Classifier (C-TC):

A functional entity that is responsible for determining which packets belong to a traffic flow for a specific service request. It coordinates with the Ingress CATS‑Forwarder so that such packets are placed onto a path computed by the C-PS that leads to the selected service contact instance. See Section 3.4.5.

クライアント（Client）：

サービスプロバイダーのネットワークに接続するエンドポイント。

フロー（Flow）：

ある時間間隔の間のパケットの論理的なグループであり、5タプルのトランスポート座標（送信元アドレスと宛先アドレス、送信元と宛先のポート番号、およびプロトコル）など、パケットヘッダーのいくつかのフィールドによって識別されます。フローの識別は、ポート番号が存在しない文脈（最初でないフラグメント、IP Encapsulating Security Payload（ESP）[RFC4303]など）もカバーすべきです。

Computing-Aware Traffic Steering (CATS):

特定のサービスコンタクトインスタンスに向けたサービス固有のトラフィックの転送を最適化するために、コンピューティングリソース（たとえば、計算とストレージ）の動的な性質とネットワークの状態を考慮するトラフィックエンジニアリングのアプローチ[RFC9522]。CATSフレームワークは、CATSのポリシーを可能にするためにさまざまなメトリックを活用します。

メトリック（Metric）：

CATSの意思決定のための選択メカニズムに適切な入力を提供する定量的な尺度。ネットワークメトリックの場合も、コンピューティングメトリックの場合もあります。

コンピューティングメトリック（Computing metric）：

ネットワークメトリックなどの他のメトリックとは対照的に、基盤となるCATSシステムのコンピューティングリソースに固有のメトリック。コンピューティングメトリックの例は[CATS-METRICS]で議論されています。

サービス（Service）：

サービスプロバイダーが、リソース（ネットワーク、計算、ストレージなど）の集合を編成することによって利用可能にする提供物。

サービスプロバイダーは、内部のリソースとサービスロジックの制御を保持します。たとえば、これらのリソースは次のようなものである場合があります：

  • 1つまたは複数のプロセスによって公開される。

  • 仮想インスタンス、物理インスタンス、またはその組み合わせによって提供される。

  • 同じノードまたは別個のノード内でホストされる。

  • 同じサービスサイトまたは複数のサービスサイト内でホストされる。

  • さまざまな手段を使用してサービスを提供するために連結される。

サービスプロバイダーがそのサービスをどのように構成するかは、CATSの範囲外のままです。

サービスプロバイダーは同じサービスを多くの場所で提供する場合があり、そのそれぞれがサービスインスタンスを構成します。

コンピューティングサービス（Computing service）：

サービスプロバイダーがコンピューティングリソースの集合を編成することによってクライアントに提供するサービス。

CATS Service ID (CS-ID):

サービスを表す識別子であり、クライアントはそれを使用してサービスにアクセスします。Section 3.2を参照してください。

サービスインスタンス（Service instance）：

サービスロジックに従って編成された実行中のリソースの集まり。クライアントのリクエストによって呼び出されると、これらのリソースが一緒になって意図されたサービスを提供します。

サービスプロバイダーは、同じサービスを提供するために、同じサービスロジックに従う多くのサービスインスタンスを有効にする場合があります。

サービスインスタンスはサービスサイトで実行され、1つ以上のインスタンスがクライアントのリクエストを処理する場合があります。

サービスサイト（Service site）：

1つ以上のサービスインスタンスを実装するリソースをホストする場所。

サービスサイトは、1つのノードまたはノードの集合である場合があります。

サービスコンタクトインスタンス（Service contact instance）：

特定のサービスの文脈においてリクエストを受信する責任を負う、クライアント向けの機能。

サービスコンタクトインスタンスは、1つ以上のサービスインスタンスを扱うことができます。

サービスコンタクトインスタンスより先のステアリングは、クライアントとCATSのコンポーネントの両方から隠されています。

サービスコンタクトインスタンスは、サービスロジックに従ってクライアントのサービスリクエストを処理します（たとえば、ローカルで処理するか、バックエンドのリソースを要求します）。

サービスコンタクトインスタンスには、少なくとも1つのEgress CATS‑Forwarderを介して到達できます。

クライアントは、同じ場所または異なる場所（サービスサイト）で実行されている複数のサービスコンタクトインスタンスを介してサービスにアクセスする場合があります。

サービスコンタクトインスタンスは、サービスリクエストを1つ以上のサービスインスタンスにディスパッチする場合があります（たとえば、サービスのロードバランサーとして振る舞うサービスコンタクトインスタンス）。

CATS Service Contact Instance ID (CSCI-ID):

特定のサービスコンタクトインスタンスの識別子。Section 3.2を参照してください。

サービスリクエスト（Service request）：

特定のサービスにアクセスまたは呼び出すためのリクエスト。CATS‑Forwarderはサービスリクエストをサービスコンタクトインスタンスに誘導します。

クライアントは、サービス固有のプロトコルを使用してサービスリクエストを生成します。

クライアントは、CATS‑Forwarderについて明示的に知ることなく、（CS-IDによって識別される）サービスインスタンスにサービスリクエストを送信します。

CATS‑Forwarder:

CATS Path Selector（C-PS）によって提供される転送の判断に従って、サービスリクエストに固有のトラフィックをサービスコンタクトインスタンスに向けて誘導するネットワークエンティティー。C-PSはCATS‑Forwarderの一部である場合もそうでない場合もあります。

CATS‑Forwarderは、Ingress CATS‑ForwarderまたはEgress CATS‑Forwarderとして振る舞う場合があります。Section 3.4.6を参照してください。

Ingress CATS‑Forwarder:

Egress CATS‑Forwarderにつながる、CATSによって計算されたパスに沿って、サービス固有のトラフィックを誘導するエンティティー。そのようなEgress CATS‑Forwarderは、最初のサービスリクエストを満たすために選択されたサービスコンタクトインスタンスをホストする、最も適切なサービスサイトに接続します。

Egress CATS‑Forwarder:

CATSによって計算されたパスの終端に位置し、サービスサイトに接続するエンティティー。

CATS Path Selector (C-PS):

サービスリクエストの要件に対応するために、サービスサイトとインスタンス（したがってサービスコンタクトインスタンス）に向かうパスを選択する機能エンティティー。パス選択エンジンは、サービスとネットワークの状態情報を考慮に入れます。Section 3.4.4を参照してください。

CATS Service Metric Agent (C-SMA):

サービスの能力と状態を収集し、それらをC-PSに報告する責任を負う機能エンティティー。Section 3.4.2を参照してください。

CATS Network Metric Agent (C-NMA):

ネットワークの能力と状態を収集し、それらをC-PSに報告する責任を負う機能エンティティー。Section 3.4.3を参照してください。

CATS Traffic Classifier (C-TC):

どのパケットが特定のサービスリクエストのトラフィックフローに属するかを判断する責任を負う機能エンティティー。そのようなパケットが、選択されたサービスコンタクトインスタンスにつながるC-PSによって計算されたパスに乗せられるように、Ingress CATS‑Forwarderと連携します。Section 3.4.5を参照してください。

3. CATS Framework and Components

3. CATSのフレームワークとコンポーネント

3.1. Assumptions

3.1. 前提

CATS assumes that a service might be provided by one or multiple service instances. Such instances may be hosted within the same or distinct service sites. A given service is represented by the same service identifier (Section 3.2). CATS does not make any additional assumptions about these instances other than that they are reachable via one or multiple service contact instances.

CATSは、サービスが1つまたは複数のサービスインスタンスによって提供される可能性があることを前提としています。そのようなインスタンスは、同じサービスサイトまたは別個のサービスサイト内でホストされる場合があります。特定のサービスは、同じサービス識別子（Section 3.2）によって表されます。CATSは、これらのインスタンスが1つまたは複数のサービスコンタクトインスタンスを介して到達可能であること以外に、それらについて追加の仮定をしません。

3.2. CATS Identifiers

3.2. CATSの識別子

CATS uses the following identifiers:

CATSは次の識別子を使用します：

CATS Service ID (CS-ID):

An identifier (ID) representing a service, which the clients use to access it. Such an ID identifies all the instances of a given service, regardless of their locations.

The CS-ID is independent of which service contact instance serves the service request.

Service requests are spread over the service contact instances that can accommodate them, considering the location of the initiator of the service request and the availability (in terms of resource/traffic load, for example) of the service instances resource wise, among other considerations like traffic congestion conditions.

CATS Service Contact Instance ID (CSCI-ID):

An identifier of a specific service contact instance.

This document makes no assumptions about the structure or semantics of this identifier. One example of such an ID is a unicast IP address, which uniquely identifies the location of a service instance.

CATS Service ID (CS-ID):

サービスを表す識別子（ID）であり、クライアントはそれを使用してサービスにアクセスします。そのようなIDは、場所にかかわらず、特定のサービスのすべてのインスタンスを識別します。

CS-IDは、どのサービスコンタクトインスタンスがサービスリクエストを処理するかに依存しません。

サービスリクエストは、サービスリクエストの開始者の場所や、サービスインスタンスのリソース面での（たとえばリソース/トラフィックの負荷の観点での）可用性を、トラフィックの輻輳状況などの他の考慮事項とともに考慮して、それらを受け入れることのできるサービスコンタクトインスタンスに分散されます。

CATS Service Contact Instance ID (CSCI-ID):

特定のサービスコンタクトインスタンスの識別子。

この文書は、この識別子の構造やセマンティクスについて何も仮定しません。そのようなIDの一例は、サービスインスタンスの場所を一意に識別するユニキャストIPアドレスです。

3.3. Framework Overview

3.3. フレームワークの概要

A high-level view of the CATS framework, without expanding the functional entities in the network, is illustrated in Figure 1.

ネットワーク内の機能エンティティーを展開せずにCATSフレームワークを高レベルで示したものをFigure 1に示します。

For the sake of illustration, "Service Instance" is shown as a single box in Figure 1. However, this does not imply that a service instance is hosted in a single node. Whether a service instance is realized by invoking resources within the same node or by chaining resources exposed by several nodes is deployment specific.

説明のため、Figure 1では「Service Instance」を単一のボックスとして示しています。しかし、これはサービスインスタンスが単一のノードでホストされることを意味するものではありません。サービスインスタンスが同じノード内のリソースを呼び出すことで実現されるか、複数のノードによって公開されるリソースを連結することで実現されるかは、展開に固有です。

The following planes are defined:

次のプレーンが定義されています：

  • CATS Management Plane: Responsible for monitoring, configuring, and maintaining CATS network devices.

  • CATS Control Plane: Responsible for scheduling services based on computing and network information. It is also responsible for making decisions about how packets should be forwarded by involved forwarding nodes and communicating such decisions to the CATS Data Plane for execution.

  • CATS Data Plane: Responsible for computing-aware forwarding, including classifying packets, steering them onto chosen paths towards selected service contact instances, and forwarding the packets along the paths to the service contact instances.

  • CATS管理プレーン：CATSのネットワークデバイスの監視、設定、および保守に責任を負います。

  • CATSコントロールプレーン：コンピューティングとネットワークの情報に基づいてサービスをスケジューリングすることに責任を負います。また、関与する転送ノードによってパケットをどのように転送すべきかの判断を行い、実行のためにその判断をCATSデータプレーンに伝えることにも責任を負います。

  • CATSデータプレーン：パケットの分類、選択されたサービスコンタクトインスタンスに向けた選択されたパスへのパケットの誘導、およびサービスコンタクトインスタンスへのパスに沿ったパケットの転送を含む、コンピューティングを考慮した転送に責任を負います。

Depending on implementation and deployment, these planes may consist of several functional components, and the details will be described in the following sections. For example, the control plane may consist of C-PS, C-NMA, etc. The data plane may consist of CATS‑Forwarders, C-TC, etc.

実装と展開に応じて、これらのプレーンはいくつかの機能コンポーネントで構成される場合があり、その詳細は以下のセクションで説明します。たとえば、コントロールプレーンはC-PS、C-NMAなどで構成される場合があります。データプレーンはCATS‑Forwarder、C-TCなどで構成される場合があります。

3.4. CATS Functional Components

3.4. CATSの機能コンポーネント

CATS nodes make forwarding decisions for a given service request that has been received from a client according to the capabilities and status information of both service contact instances and the network. The main CATS functional components and their interactions are shown in Figure 2. These components are described in the subsections that follow.

CATSのノードは、サービスコンタクトインスタンスとネットワークの両方の能力と状態の情報に従って、クライアントから受信した特定のサービスリクエストに対する転送の判断を行います。主要なCATSの機能コンポーネントとそれらの相互作用をFigure 2に示します。これらのコンポーネントについては、以下のサブセクションで説明します。

3.4.1. Service Sites, Service Instances, and Service Contact Instances

3.4.1. サービスサイト、サービスインスタンス、およびサービスコンタクトインスタンス

Service sites are locations that host resources (including computing resources) that are required to offer a service.

サービスサイトは、サービスを提供するために必要なリソース（コンピューティングリソースを含む）をホストする場所です。

A compute service (e.g., for face recognition purposes or a game server) is identified by a CATS Service ID (CS-ID). The CS-ID does not need to be globally unique but must be sufficiently unique to unambiguously identify the service at all of the components of a CATS system.

計算サービス（たとえば、顔認識の目的やゲームサーバーのためのもの）は、CATS Service ID（CS-ID）によって識別されます。CS-IDはグローバルに一意である必要はありませんが、CATSシステムのすべてのコンポーネントでサービスを曖昧さなく識別できるだけの十分な一意性を持たなければなりません。

A single service can be represented and accessed via several contact instances that run in the same or different regions of a network.

単一のサービスは、ネットワークの同じ領域または異なる領域で実行されるいくつかのコンタクトインスタンスを介して表現およびアクセスできます。

As service instances are accessed via a service contact instance, a client will not see the service instances but only the service contact instance.

サービスインスタンスはサービスコンタクトインスタンスを介してアクセスされるため、クライアントにはサービスインスタンスは見えず、サービスコンタクトインスタンスのみが見えます。

Figure 2 shows two CATS nodes ("CATS‑Forwarder 1" and "CATS‑Forwarder 3") that provide access to service contact instances. These nodes behave as Egress CATS‑Forwarders (Section 3.4.6).

Figure 2は、サービスコンタクトインスタンスへのアクセスを提供する2つのCATSノード（「CATS‑Forwarder 1」と「CATS‑Forwarder 3」）を示しています。これらのノードは、Egress CATS‑Forwarder（Section 3.4.6）として振る舞います。

  • Note: "Egress" is used here in reference to the direction of the service request placement. The directionality is called to explicitly identify the exit node of the CATS infrastructure.

  • 注記：ここでの「Egress」は、サービスリクエストの配置の方向に関して使用されています。この方向性は、CATSインフラストラクチャーの出口ノードを明示的に識別するために呼ばれています。

3.4.2. CATS Service Metric Agent (C-SMA)

3.4.2. CATS Service Metric Agent（C-SMA）

The CATS Service Metric Agent (C-SMA) is a functional component that gathers information about service sites and server resources, as well as the status of the different service instances. A C-SMA may be co-located or located adjacent to a service contact instance, hosted by or adjacent to an Egress CATS‑Forwarder (Section 3.4.6), etc. There may be one or more C-SMAs in a deployment.

CATS Service Metric Agent（C-SMA）は、サービスサイトとサーバーのリソース、およびさまざまなサービスインスタンスの状態に関する情報を収集する機能コンポーネントです。C-SMAは、サービスコンタクトインスタンスと同じ場所または隣接して配置されたり、Egress CATS‑Forwarder（Section 3.4.6）によってホストされたりそれに隣接して配置されたりする場合があります。展開内には1つ以上のC-SMAが存在する場合があります。

Figure 2 shows one C-SMA embedded in "CATS‑Forwarder 3" and another C-SMA that is adjacent to "CATS‑Forwarder 1".

Figure 2は、「CATS‑Forwarder 3」に組み込まれた1つのC-SMAと、「CATS‑Forwarder 1」に隣接するもう1つのC-SMAを示しています。

3.4.3. CATS Network Metric Agent (C-NMA)

3.4.3. CATS Network Metric Agent（C-NMA）

The CATS Network Metric Agent (C-NMA) is a functional component that gathers information about the state of the underlay network. The C-NMAs may be implemented as standalone components or may be hosted by other components, such as CATS‑Forwarders or CATS Path Selectors (C-PSes) (Section 3.4.4).

CATS Network Metric Agent（C-NMA）は、アンダーレイネットワークの状態に関する情報を収集する機能コンポーネントです。C-NMAは、独立したコンポーネントとして実装される場合もあれば、CATS‑ForwarderやCATS Path Selector（C-PS）（Section 3.4.4）などの他のコンポーネントによってホストされる場合もあります。

C-NMA is likely to leverage existing techniques (e.g., [RFC7471], [RFC8570], and [RFC8571]).

C-NMAは、既存の技術（たとえば、[RFC7471]、[RFC8570]、[RFC8571]）を活用する可能性が高いです。

Figure 2 shows a single, standalone C-NMA within the underlay network. There may be one or more C-NMAs for an underlay network.

Figure 2は、アンダーレイネットワーク内の単一の独立したC-NMAを示しています。アンダーレイネットワークには1つ以上のC-NMAが存在する場合があります。

3.4.4. CATS Path Selector (C-PS)

3.4.4. CATS Path Selector（C-PS）

The C-SMAs and C-NMAs share the collected information with C-PSes, which use such information to select the Egress CATS‑Forwarders (and potentially the service contact instances) that the traffic should be forwarded to for a given service request. C-PSes also determine the best paths (possibly using tunnels) to forward traffic, according to various criteria that include network state and traffic congestion conditions. The collected information is encoded into one or more metrics that feed the C-PS path selection logic. Such information also includes CS-IDs and possibly CSCI-IDs.

C-SMAとC-NMAは収集した情報をC-PSと共有し、C-PSはその情報を使用して、特定のサービスリクエストについてトラフィックを転送すべきEgress CATS‑Forwarder（および場合によってはサービスコンタクトインスタンス）を選択します。C-PSはまた、ネットワークの状態やトラフィックの輻輳状況などのさまざまな基準に従って、トラフィックを転送するための最適なパスを（場合によってはトンネルを使用して）決定します。収集された情報は、C-PSのパス選択ロジックに入力される1つ以上のメトリックにエンコードされます。そのような情報には、CS-IDと場合によってはCSCI-IDも含まれます。

There might be one or more C-PSes used to select CATS paths in a CATS infrastructure.

CATSインフラストラクチャーでは、CATSのパスを選択するために1つ以上のC-PSが使用される場合があります。

A C-PS can be integrated into CATS‑Forwarders (e.g., "C-PS#1" in Figure 2) or may be deployed as a standalone component (e.g., "C-PS#2" in Figure 2). Generally, a standalone C-PS can be a functional component of a centralized controller (e.g., a Path Computation Element (PCE) [RFC4655] or a Software-Defined Networking (SDN) controller [RFC7149] [RFC7426]).

C-PSは、CATS‑Forwarderに統合される場合（たとえばFigure 2の「C-PS#1」）もあれば、独立したコンポーネントとして展開される場合（たとえばFigure 2の「C-PS#2」）もあります。一般に、独立したC-PSは、集中型コントローラー（たとえば、Path Computation Element（PCE）[RFC4655]やSoftware-Defined Networking（SDN）コントローラー[RFC7149] [RFC7426]）の機能コンポーネントにできます。

Refer to Section 4.2 for a discussion on metric distribution (including interaction with routing protocols).

メトリックの配布（ルーティングプロトコルとのやり取りを含む）に関する議論については、Section 4.2を参照してください。

3.4.5. CATS Traffic Classifier (C-TC)

3.4.5. CATS Traffic Classifier（C-TC）

The CATS Traffic Classifier (C-TC) is a functional component that is responsible for associating incoming packets from clients with service requests. C-TCs also ensure that packets that are bound to a specific service contact instance are all forwarded towards that same service contact instance, as instructed by a C-PS. To that aim, a C-TC uses CS-IDs (or their resolution of CS-ID to network locators) to classify service requests. Refer to Section 5.1 for more details about required provisioning actions.

CATS Traffic Classifier（C-TC）は、クライアントからの受信パケットをサービスリクエストに関連付ける責任を負う機能コンポーネントです。C-TCはまた、C-PSの指示に従って、特定のサービスコンタクトインスタンスに結び付けられたパケットがすべて同じサービスコンタクトインスタンスに向けて転送されることを保証します。そのために、C-TCは、CS-ID（またはCS-IDのネットワークロケーターへの解決結果）を使用してサービスリクエストを分類します。必要なプロビジョニングの操作の詳細については、Section 5.1を参照してください。

CS-IDs may be carried in packets if mechanisms such as TLS Server Name Indication (SNI) extensions (Section 3 of [RFC6066]) are used. Such exposure is not possible if extensions such as [RFC9849] are used. Relying upon non-volatile and explicit signals (e.g., [RFC8558]) is thus encouraged for efficient classification rules. Note that once classified, packets will be encapsulated as described in Section 4.3.

TLSのServer Name Indication（SNI）拡張（[RFC6066]のSection 3）などのメカニズムが使用されている場合、CS-IDはパケット内で運ばれる場合があります。[RFC9849]などの拡張が使用されている場合、そのような露出は不可能です。したがって、効率的な分類規則のために、不揮発性で明示的なシグナル（たとえば[RFC8558]）に依存することが推奨されます。いったん分類されたパケットは、Section 4.3で説明するようにカプセル化されることに注意してください。

C-TCs are typically hosted in CATS‑Forwarders.

C-TCは通常、CATS‑Forwarderでホストされます。

3.4.6. CATS-Forwarders

3.4.6. CATS-Forwarders

Ingress CATS‑Forwarders are responsible for steering service-specific traffic along a CATS-computed path that leads to an Egress CATS‑Forwarder. Egress CATS‑Forwarders are the elements that behave as an egress for service requests that are forwarded over a CATS infrastructure.

Ingress CATS‑Forwarderは、Egress CATS‑Forwarderにつながる、CATSによって計算されたパスに沿って、サービス固有のトラフィックを誘導する責任を負います。Egress CATS‑Forwarderは、CATSインフラストラクチャー上で転送されるサービスリクエストの出口として振る舞う要素です。

A service site that hosts service instances may be connected to one or more Egress CATS‑Forwarders (e.g., multi-homing design). If a C-PS has selected a specific service contact instance and the C-TC has marked the traffic with the CSCI-ID related information, the Egress CATS‑Forwarder then forwards the traffic to the relevant service contact instance accordingly.

サービスインスタンスをホストするサービスサイトは、1つ以上のEgress CATS‑Forwarderに接続される場合があります（たとえば、マルチホーミングの設計）。C-PSが特定のサービスコンタクトインスタンスを選択し、C-TCがトラフィックにCSCI-IDに関連する情報をマークした場合、Egress CATS‑Forwarderはそれに応じてトラフィックを関連するサービスコンタクトインスタンスに転送します。

In some cases, the choice of the service contact instance may be left open to the Egress CATS‑Forwarder (i.e., traffic is marked only with the CS-ID). In such cases, the Egress CATS‑Forwarder selects a service contact instance using its knowledge of service and network capabilities as well as the current load as observed by the CATS‑Forwarder, among other considerations. In the absence of an explicit policy, an Egress CATS‑Forwarder must make sure to forward all packets that pertain to a given service request towards the same service contact instance.

場合によっては、サービスコンタクトインスタンスの選択がEgress CATS‑Forwarderに委ねられることがあります（つまり、トラフィックにはCS-IDのみがマークされます）。そのような場合、Egress CATS‑Forwarderは、サービスとネットワークの能力に関する知識や、CATS‑Forwarderが観測した現在の負荷などを考慮して、サービスコンタクトインスタンスを選択します。明示的なポリシーがない場合、Egress CATS‑Forwarderは、特定のサービスリクエストに関係するすべてのパケットが同じサービスコンタクトインスタンスに向けて転送されるようにしなければなりません。

Note that, depending on the design considerations and service requirements, per-service contact instance computing-related metrics or aggregated per-site computing-related metrics (and a combination thereof) can be used by a C-PS. Using aggregated per-site computing-related metrics appears as a preferred option scalability wise, but it relies on Egress CATS‑Forwarders that connect to various service contact instances to select the proper service contact instance. An Egress CATS‑Forwarder may choose to aggregate the metrics from different sites as well. In this case, the Egress CATS‑Forwarder will choose the best site by itself when the packets arrive at it.

設計上の考慮事項とサービス要件に応じて、サービスコンタクトインスタンスごとのコンピューティング関連のメトリック、またはサイトごとに集約されたコンピューティング関連のメトリック（およびその組み合わせ）をC-PSが使用できることに注意してください。サイトごとに集約されたコンピューティング関連のメトリックを使用することは、スケーラビリティーの点では望ましい選択肢であるように見えますが、適切なサービスコンタクトインスタンスを選択するために、さまざまなサービスコンタクトインスタンスに接続するEgress CATS‑Forwarderに依存することになります。Egress CATS‑Forwarderは、異なるサイトからのメトリックを集約することも選択できます。この場合、Egress CATS‑Forwarderは、パケットが到着したときに自ら最適なサイトを選択します。

3.4.7. Underlay Infrastructure

3.4.7. アンダーレイインフラストラクチャー

The "underlay infrastructure" in Figure 2 indicates an IP and/or MPLS network that is not necessarily CATS aware. The CATS paths that are computed by a C-PS will be distributed among the CATS‑Forwarders (Section 3.4.6) and will not affect the underlay nodes. Underlay nodes are typically P routers (Section 5.3.1 of [RFC4026]).

Figure 2の「アンダーレイインフラストラクチャー」は、必ずしもCATSを認識していないIPネットワークおよび/またはMPLSネットワークを示します。C-PSによって計算されたCATSのパスは、CATS‑Forwarder（Section 3.4.6）の間で配布され、アンダーレイのノードには影響しません。アンダーレイのノードは、通常Pルーター（[RFC4026]のSection 5.3.1）です。

4. CATS Framework Workflow

4. CATSフレームワークのワークフロー

The following subsections provide an overview of a typical CATS workflow. In order to enable CATS in a given domain, some provisioning is needed; see more details in Section 5.1. Section 5.3 describes several deployment options (distributed, centralized, and hybrid models) to accommodate a variety of contexts.

以下のサブセクションでは、典型的なCATSのワークフローの概要を示します。特定のドメインでCATSを有効にするには、いくつかのプロビジョニングが必要です。詳細についてはSection 5.1を参照してください。Section 5.3では、さまざまな文脈に対応するためのいくつかの展開の選択肢（分散型、集中型、およびハイブリッドのモデル）について説明します。

4.1. Service Announcement

4.1. サービスの告知

A service is associated by the service provider with a unique identifier called a CS-ID. A CS-ID may be a network identifier, such as an IP address. The mapping of CS-IDs to network identifiers may be learned through a name resolution service (e.g., DNS [RFC1034]). Note that the CATS framework does not assume or preclude any specific name resolution service.

サービスは、サービスプロバイダーによって、CS-IDと呼ばれる一意な識別子に関連付けられます。CS-IDは、IPアドレスなどのネットワーク識別子である場合があります。CS-IDからネットワーク識別子へのマッピングは、名前解決サービス（たとえばDNS[RFC1034]）を通じて学習される場合があります。CATSフレームワークは、特定の名前解決サービスを前提とすることも排除することもないことに注意してください。

4.2. Metrics Distribution

4.2. メトリックの配布

As described in Section 3.4, a C-SMA collects both computing-related capabilities and metrics and associates them with a CS-ID that identifies the service. The C-SMA may aggregate the metrics for multiple service contact instances, maintain them separately, or both.

Section 3.4で説明したように、C-SMAはコンピューティング関連の能力とメトリックの両方を収集し、それらをサービスを識別するCS-IDに関連付けます。C-SMAは、複数のサービスコンタクトインスタンスのメトリックを集約することも、それらを個別に保持することも、その両方を行うこともできます。

The C-SMA then advertises CS-IDs along with metrics to related C-PSes in the network. Depending on the deployment choice, CS-IDs with metrics may be distributed in different ways. Refer to Section 5.4 for more deployment considerations.

その後、C-SMAは、ネットワーク内の関連するC-PSに、CS-IDをメトリックとともに広告します。展開の選択に応じて、メトリックを伴うCS-IDはさまざまな方法で配布される場合があります。展開に関するさらなる考慮事項については、Section 5.4を参照してください。

The computing metrics include computing-related metrics and potentially other service-specific metrics like the number of clients that access the service contact instance at any given time, etc.

コンピューティングメトリックには、コンピューティング関連のメトリックと、場合によっては、任意の時点でサービスコンタクトインスタンスにアクセスしているクライアントの数などの他のサービス固有のメトリックが含まれます。

Computing metrics may change very frequently (e.g., see Section 5.3 of [RFC10054] for a discussion). How frequently such information is distributed is to be determined as part of the specification of any communication protocol (including routing protocols) that may be used to distribute the information. Various options can be considered, such as (but not limited to) interval-based updates, threshold-triggered updates, policy-based updates, or using normalized metrics.

コンピューティングメトリックは非常に頻繁に変化する場合があります（たとえば、議論については[RFC10054]のSection 5.3を参照してください）。そのような情報をどのくらいの頻度で配布するかは、その情報を配布するために使用される可能性のある通信プロトコル（ルーティングプロトコルを含む）の仕様の一部として決定されます。間隔ベースの更新、しきい値でトリガーされる更新、ポリシーベースの更新、または正規化されたメトリックの使用など（ただしこれらに限定されません）、さまざまな選択肢を検討できます。

Additionally, the C-NMA collects network-related capabilities and metrics. These may be collected and distributed by existing measurement protocols and/or routing protocols, although extensions to such protocols may be required to carry additional information (e.g., link latency). The C-NMA distributes the network metrics to the C-PSes so that they can use the combination of service and network metrics to determine the best Egress CATS‑Forwarder to provide access to a service contact instance and invoke the compute function required by a service request. Similar to computing-related metrics, the network-related metrics can be distributed using distributed, centralized, or hybrid schemes. This document does not describe such details since this is deployment specific.

さらに、C-NMAはネットワーク関連の能力とメトリックを収集します。これらは、既存の測定プロトコルやルーティングプロトコルによって収集および配布される場合がありますが、追加の情報（たとえばリンクの遅延）を運ぶためにそのようなプロトコルの拡張が必要になる場合があります。C-NMAはネットワークメトリックをC-PSに配布し、C-PSはサービスとネットワークのメトリックの組み合わせを使用して、サービスコンタクトインスタンスへのアクセスを提供し、サービスリクエストが必要とする計算機能を呼び出すのに最適なEgress CATS‑Forwarderを決定できます。コンピューティング関連のメトリックと同様に、ネットワーク関連のメトリックは、分散型、集中型、またはハイブリッドの方式を使用して配布できます。これは展開に固有であるため、この文書ではそのような詳細は説明しません。

Network metrics may also change over time. Dynamic routing protocols may take advantage of some information or capabilities to prevent the network from being flooded with state change information (e.g., Partial Route Computation (PRC) of OSPFv3 [RFC5340]). C-NMAs should also be configured or instructed like C-SMAs to determine when and how often updates should be notified to the C-PSes.

ネットワークメトリックも時間とともに変化する場合があります。動的ルーティングプロトコルは、ネットワークが状態変化の情報であふれることを防ぐために、何らかの情報や機能（たとえば、OSPFv3[RFC5340]の部分経路計算（PRC））を活用する場合があります。C-NMAも、C-SMAと同様に、更新をいつ、どのくらいの頻度でC-PSに通知すべきかを判断するように設定または指示されるべきです。

4.3. Service Access Processing

4.3. サービスアクセスの処理

A C-PS selects paths that lead to Egress CATS‑Forwarders according to both service and network metrics that were advertised. A C-PS may be collocated with an Ingress CATS‑Forwarder or logically centralized (in the centralized or hybrid models (Section 5.3)).

C-PSは、広告されたサービスとネットワークの両方のメトリックに従って、Egress CATS‑Forwarderにつながるパスを選択します。C-PSは、Ingress CATS‑Forwarderと同じ場所に配置される場合もあれば、（集中型またはハイブリッドのモデル（Section 5.3）において）論理的に集中化される場合もあります。

This document does not specify any specific algorithm for path selection purposes to be supported by C-PSes so as not to constrain the CATS framework to one possible selection only. Instead, it is expected that a service request or local policy may feed the C-PS with appropriate information on that selection logic that takes the suitable metric information as input and the selected service contact instance as output. Such appropriate information may be utilized to differentiate selection mechanisms to enable service-specific selections.

CATSフレームワークを1つの選択方法のみに制約しないように、この文書は、C-PSがサポートすべきパス選択のための特定のアルゴリズムを規定しません。代わりに、サービスリクエストやローカルポリシーが、適切なメトリック情報を入力とし、選択されたサービスコンタクトインスタンスを出力とする選択ロジックに関する適切な情報をC-PSに与えることが期待されます。そのような適切な情報は、サービス固有の選択を可能にするために、選択メカニズムを区別するのに利用できます。

Note that a service request to access the service may consist of one or more service packets (e.g., Session Initiation Protocol (SIP) [RFC3261], HTTP [RFC9112], IPv6 [RFC8200], Segment Routing over IPv6 (SRv6) [RFC8754] [RFC8986], or Real-Time Streaming Protocol (RTSP) [RFC7826]) that carry the CS-ID and potential parameters. When a matching classification entry maintained by a C-TC is found for the packets, the Ingress CATS‑Forwarder encapsulates and forwards them to the C-PS selected Egress CATS‑Forwarder. When these packets reach the Egress CATS‑Forwarder, the outer header of the possible overlay encapsulation will be removed and the inner packets will be sent to the relevant service contact instance.

サービスにアクセスするためのサービスリクエストは、CS-IDと潜在的なパラメーターを運ぶ1つ以上のサービスパケット（たとえば、Session Initiation Protocol（SIP）[RFC3261]、HTTP[RFC9112]、IPv6[RFC8200]、Segment Routing over IPv6（SRv6）[RFC8754] [RFC8986]、またはReal-Time Streaming Protocol（RTSP）[RFC7826]）で構成される場合があることに注意してください。C-TCが保持する一致する分類エントリーがパケットについて見つかった場合、Ingress CATS‑Forwarderはそれらをカプセル化し、C-PSが選択したEgress CATS‑Forwarderに転送します。これらのパケットがEgress CATS‑Forwarderに到達すると、オーバーレイのカプセル化の外側のヘッダーが削除され、内側のパケットが関連するサービスコンタクトインスタンスに送信されます。

4.4. Service Contact Instance Affinity

4.4. サービスコンタクトインスタンスのアフィニティー

Service contact instance affinity means that packets that belong to a flow associated with a service request should always be sent to the same service contact instance. Furthermore, packets of a given flow should be forwarded along the same path to avoid misordering and to prevent the introduction of unpredictable latency variations. A CATS framework implementation must ensure that service instance selection and path steering decisions remain consistent for a flow. Specifically, the same Egress CATS‑Forwarder needs to be solicited to forward the packets.

サービスコンタクトインスタンスのアフィニティーとは、サービスリクエストに関連付けられたフローに属するパケットが常に同じサービスコンタクトインスタンスに送信されるべきであることを意味します。さらに、順序の乱れを避け、予測不能な遅延の変動が持ち込まれるのを防ぐために、特定のフローのパケットは同じパスに沿って転送されるべきです。CATSフレームワークの実装は、サービスインスタンスの選択とパスのステアリングの判断がフローについて一貫したままであることを保証しなければなりません。具体的には、パケットを転送するために同じEgress CATS‑Forwarderを利用する必要があります。

Ensuring service affinity for flows is a feature that can be configured on the C-PS when the service is deployed (i.e., all flows bound to a service) or determined at the time of newly formulated service requests (i.e., a specific flow).

フローのサービスアフィニティーを保証することは、サービスが展開される時点で（つまり、サービスに結び付けられたすべてのフローについて）C-PSで設定することも、新たにサービスリクエストが作成された時点で（つまり、特定のフローについて）決定することもできる機能です。

Note that different services may have different notions of what constitutes a "flow", and thus may identify a flow differently. Typically, a flow is identified by the 5-tuple transport coordinates (source address and destination address, source and destination port numbers, and protocol). However, for instance, an RTP video stream may use different port numbers for video and audio channels: In that case, affinity may be identified as a combination of the two 5-tuple flow identifiers so that both flows are addressed to the same service contact instance.

異なるサービスは「フロー」を構成するものについて異なる概念を持つ場合があり、したがってフローを異なる方法で識別する場合があることに注意してください。通常、フローは5タプルのトランスポート座標（送信元アドレスと宛先アドレス、送信元と宛先のポート番号、およびプロトコル）によって識別されます。しかし、たとえば、RTPのビデオストリームは、ビデオとオーディオのチャネルに異なるポート番号を使用する場合があります。その場合、両方のフローが同じサービスコンタクトインスタンスに宛てられるように、アフィニティーは2つの5タプルのフロー識別子の組み合わせとして識別される場合があります。

Hence, when specifying a protocol to communicate information about service contact instance affinity to C-TCs in particular, the protocol should support flexible mechanisms for identifying flows. Or, from a more general perspective, there should be a mechanism to specify and identify the set of packets that are subject to a service contact instance affinity.

したがって、特にサービスコンタクトインスタンスのアフィニティーに関する情報をC-TCに伝えるためのプロトコルを規定する場合、そのプロトコルはフローを識別するための柔軟なメカニズムをサポートすべきです。あるいは、より一般的な観点からは、サービスコンタクトインスタンスのアフィニティーの対象となるパケットの集合を指定および識別するためのメカニズムが存在すべきです。

More importantly, the means for identifying a flow for ensuring instance affinity should be application independent to avoid the need for service-specific instance affinity methods. However, service contact instance affinity information may be configurable on a per-service basis. For each service, the information can include the flow or packet identification type and means, affinity timeout value, etc.

さらに重要なことに、インスタンスのアフィニティーを保証するためにフローを識別する手段は、サービス固有のインスタンスアフィニティーの方法が必要にならないように、アプリケーションから独立しているべきです。ただし、サービスコンタクトインスタンスのアフィニティーの情報は、サービスごとに設定可能な場合があります。各サービスについて、その情報には、フローまたはパケットの識別のタイプと手段、アフィニティーのタイムアウト値などを含めることができます。

This document does not introduce any mechanism for defining or enforcing service contact instance affinity.

この文書は、サービスコンタクトインスタンスのアフィニティーを定義または強制するためのメカニズムを導入しません。

5. Operational Considerations

5. 運用上の考慮事項

5.1. Provisioning of CATS Components

5.1. CATSコンポーネントのプロビジョニング

Enabling CATS in a network can be done incrementally. That is, not all ingress routers (Provider Edges (PEs), typically) need to be upgraded to support CATS.

ネットワークでのCATSの有効化は段階的に行うことができます。つまり、すべての入口ルーター（通常はプロバイダーエッジ（PE））をCATSをサポートするようにアップグレードする必要はありません。

In addition to the CATS steering policies that are communicated by a C-PS to an Ingress CATS‑Forwarder, some provisioning tasks are required. These include, but are not limited to:

C-PSからIngress CATS‑Forwarderに伝えられるCATSのステアリングポリシーに加えて、いくつかのプロビジョニングのタスクが必要です。これには次のものが含まれますが、これらに限定されません：

  • Providing C-PS elements with the locators of available Ingress CATS‑Forwarders/C-TCs. Such locators may also be discovered from the network.

  • Supplying information needed to connect C-PS elements with C-NMAs and C-SMAs.

  • Allocating identifiers CS-ID/CSCI-ID and binding them to specific service contact instances.

  • Providing C-PS elements with the set of optimization metrics (per service) and an optimization policy.

  • Configuring specific encapsulation capabilities of CATS‑Forwarders for use, including any credentials for mutual authentication between peer CATS‑Forwarders.

  • Resetting the classification table of C-TC elements.

  • Providing C-TCs with initial classification rules based on the classification capabilities (Section 5.2).

  • Setting the traffic counters at CATS‑Forwarders to ease correlation between both Ingress and Egress CATS‑Forwarders. Such a correlation is needed to help identify issues induced by the underlying encapsulation.

  • 利用可能なIngress CATS‑Forwarder/C-TCのロケーターをC-PS要素に提供すること。そのようなロケーターは、ネットワークから発見される場合もあります。

  • C-PS要素をC-NMAおよびC-SMAと接続するために必要な情報を提供すること。

  • 識別子CS-ID/CSCI-IDを割り当て、それらを特定のサービスコンタクトインスタンスに結び付けること。

  • （サービスごとの）最適化メトリックの集合と最適化ポリシーをC-PS要素に提供すること。

  • ピアのCATS‑Forwarder間の相互認証のためのクレデンシャルを含め、使用するCATS‑Forwarderの特定のカプセル化機能を設定すること。

  • C-TC要素の分類テーブルをリセットすること。

  • 分類機能（Section 5.2）に基づいて、C-TCに初期の分類規則を提供すること。

  • Ingress CATS‑ForwarderとEgress CATS‑Forwarderの間の相関を容易にするために、CATS‑Forwarderでトラフィックカウンターを設定すること。そのような相関は、基盤となるカプセル化によって引き起こされる問題を特定するのに役立てるために必要です。

Provisioning includes configuration as well as distribution through protocols. Specifically, the above tasks can be enabled using a variety of means (NETCONF [RFC6241], IPFIX [RFC7011], RESTCONF [RFC8040], YANG notifications [RFC8639], etc.). It is out of scope to discuss required CATS extensions to these protocols.

プロビジョニングには、設定と、プロトコルによる配布の両方が含まれます。具体的には、上記のタスクは、さまざまな手段（NETCONF[RFC6241]、IPFIX[RFC7011]、RESTCONF[RFC8040]、YANG通知[RFC8639]など）を使用して可能にできます。これらのプロトコルに必要なCATSの拡張について議論することは範囲外です。

5.2. Supervision of CATS Components and CATS OAM

5.2. CATSコンポーネントの監督とCATSのOAM

Also, companion supervision and Operations, Administration, and Maintenance (OAM) tools are needed to drive CATS provisioning but also to assess the overall CATS operations. These include, but are not limited to:

また、CATSのプロビジョニングを推進するとともに、CATSの全体的な運用を評価するために、付随する監督ツールや運用・管理・保守（OAM）ツールも必要です。これには次のものが含まれますが、これらに限定されません：

  • Exposing classification capabilities of C-TC elements.

  • Exposing encapsulation capabilities supported by CATS‑Forwarders.

  • Retrieving the active classification table of C-TC elements.

  • Retrieving active steering rules in CATS‑Forwarders.

  • Retrieving active installed policies in C-PSes.

  • Retrieving the traffic counters at CATS‑Forwarders to ease correlation between both Ingress and Egress CATS‑Forwarders.

  • Enabling OAM tools to check the correct behavior of various entities (e.g., classification rules, steering rules, and forwarding behavior). See also Section 5.5.

  • Enabling OAM tools for performance measurement.

  • C-TC要素の分類機能を公開すること。

  • CATS‑Forwarderがサポートするカプセル化機能を公開すること。

  • C-TC要素のアクティブな分類テーブルを取得すること。

  • CATS‑Forwarderのアクティブなステアリング規則を取得すること。

  • C-PSにインストールされたアクティブなポリシーを取得すること。

  • Ingress CATS‑ForwarderとEgress CATS‑Forwarderの間の相関を容易にするために、CATS‑Forwarderでトラフィックカウンターを取得すること。

  • さまざまなエンティティーの正しい振る舞い（たとえば、分類規則、ステアリング規則、転送の振る舞い）を確認するためのOAMツールを有効にすること。Section 5.5も参照してください。

  • 性能測定のためのOAMツールを有効にすること。

5.3. Deployment Considerations

5.3. 展開に関する考慮事項

This document does not make any assumptions about how the various CATS functional elements are implemented and deployed. Concretely, whether a CATS deployment follows a fully distributed design or relies upon a mix of centralized (e.g., a centralized C-PS) and distributed CATS functions (e.g., C-TCs) is deployment specific, which may reflect the preferences and policies of the (CATS) service provider. The deployment can also be informed by specific use case requirements [RFC10054].

この文書は、CATSのさまざまな機能要素がどのように実装および展開されるかについて、何も仮定しません。具体的には、CATSの展開が完全に分散された設計に従うか、集中型（たとえば集中型のC-PS）と分散型（たとえばC-TC）のCATS機能の組み合わせに依存するかは展開に固有であり、（CATSの）サービスプロバイダーの好みとポリシーを反映する場合があります。展開は、特定のユースケースの要件[RFC10054]によって決まる場合もあります。

For example, in a centralized design, both the computing-related metrics from the C-SMAs and the network metrics are collected by a (logically) centralized path computation logic (e.g., a PCE). In this case, the CATS computation logic may process incoming service requests to compute paths to service contact instances. More generally, the paths might be computed before a service request comes. Based on the metrics and computed paths, the C-PS can select the most appropriate path and then synchronize with C-TCs.

たとえば、集中型の設計では、C-SMAからのコンピューティング関連のメトリックとネットワークメトリックの両方が、（論理的に）集中化されたパス計算ロジック（たとえばPCE）によって収集されます。この場合、CATSの計算ロジックは、受信したサービスリクエストを処理して、サービスコンタクトインスタンスへのパスを計算する場合があります。より一般的には、パスはサービスリクエストが来る前に計算される場合があります。メトリックと計算されたパスに基づいて、C-PSは最も適切なパスを選択し、C-TCと同期できます。

According to the method of distributing and collecting the computing metrics, three deployment models can be considered for the deployment of the CATS framework:

コンピューティングメトリックを配布および収集する方法に応じて、CATSフレームワークの展開には3つの展開モデルを考えることができます：

Distributed model:

Computing metrics are distributed among network devices directly using distributed protocols without interactions with a centralized control element (e.g., network controller). The service scheduling function is performed by the CATS‑Forwarders in the distributed model; therefore, the C-PS is integrated into an Ingress CATS‑Forwarder.

Centralized model:

Computing metrics are collected by centralized control elements. These elements then compute the forwarding path for service requests and sync up with Ingress CATS‑Forwarders. In this model, C-PS is implemented in a centralized control element.

Hybrid model:

This is a combination of distributed and centralized models.

A part of computing metrics is distributed among involved network devices, and others may be collected by a centralized control element. For example, some static information (e.g., capabilities information) can be distributed among network devices since they are quite stable (i.e., change infrequently). Frequently changing information (e.g., resource utilization) can be collected by a centralized control element to avoid frequent flooding in the distributed control plane. Service scheduling functions can be performed by a centralized control element, Ingress CATS‑Forwarders (co-located with a C-PS), or both depending on the specific deployment policies.

When path computation is distributed, centralized control elements have to communicate the path information they collect to Ingress CATS‑Forwarders (co-located with a C-PS) so that they take into account the full set of metrics for service scheduling.

分散モデル：

コンピューティングメトリックは、集中型の制御要素（たとえばネットワークコントローラー）とのやり取りなしに、分散型のプロトコルを使用してネットワークデバイス間で直接配布されます。分散モデルでは、サービスのスケジューリング機能はCATS‑Forwarderによって実行されます。したがって、C-PSはIngress CATS‑Forwarderに統合されます。

集中モデル：

コンピューティングメトリックは、集中型の制御要素によって収集されます。これらの要素は、その後サービスリクエストの転送パスを計算し、Ingress CATS‑Forwarderと同期します。このモデルでは、C-PSは集中型の制御要素に実装されます。

ハイブリッドモデル：

これは、分散モデルと集中モデルの組み合わせです。

コンピューティングメトリックの一部は関与するネットワークデバイス間で配布され、その他は集中型の制御要素によって収集される場合があります。たとえば、一部の静的な情報（たとえば能力の情報）は、非常に安定している（つまり、めったに変化しない）ため、ネットワークデバイス間で配布できます。頻繁に変化する情報（たとえばリソースの使用率）は、分散型のコントロールプレーンでの頻繁なフラッディングを避けるために、集中型の制御要素によって収集できます。サービスのスケジューリング機能は、特定の展開ポリシーに応じて、集中型の制御要素、（C-PSと同じ場所に配置された）Ingress CATS‑Forwarder、またはその両方によって実行できます。

パスの計算が分散されている場合、集中型の制御要素は、Ingress CATS‑Forwarder（C-PSと同じ場所に配置されたもの）がサービスのスケジューリングのためにメトリックの完全な集合を考慮できるように、収集したパス情報をそれらに伝える必要があります。

Examples to illustrate these models are provided in Appendix A.

これらのモデルを説明する例をAppendix Aに示します。

The framework covers only the case of a single service provider. Deployment considerations about the case of multiple service providers are out of scope.

このフレームワークは、単一のサービスプロバイダーの場合のみを対象とします。複数のサービスプロバイダーの場合の展開に関する考慮事項は範囲外です。

5.4. Implementation Considerations on Using CATS Metrics

5.4. CATSメトリックの使用に関する実装上の考慮事項

Advertising per-instance computing-related metrics instead of aggregating them into per-site advertisements has scalability implications on involved CATS elements. Special care should be considered by providers when enabling per-instance metric distribution.

コンピューティング関連のメトリックをサイトごとの広告に集約する代わりにインスタンスごとに広告することは、関与するCATS要素のスケーラビリティーに影響を与えます。インスタンスごとのメトリックの配布を有効にする際には、プロバイダーは特別な注意を払うべきです。

Computing metrics need to be normalized (i.e., convert metric values with or without units into unitless scores), aggregated, or a combination thereof in order to soften the scalability impact while providing sufficient detail for effective CATS decision making. For example, see [CATS-METRICS] for a discussion on metrics and distribution approaches.

効果的なCATSの意思決定のために十分な詳細を提供しつつスケーラビリティーへの影響を和らげるために、コンピューティングメトリックは、正規化（つまり、単位の有無にかかわらずメトリックの値を単位のないスコアに変換すること）、集約、またはその組み合わせを行う必要があります。たとえば、メトリックと配布のアプローチに関する議論については[CATS-METRICS]を参照してください。

Depending on the resources and processing capabilities of CATS components, the normalization and aggregation functions can be located in different CATS components. An approach is to implement the normalization and aggregation functions located away from C-PSes, especially when C-PSes are co-located with CATS‑Forwarders. With this in mind, the normalization and aggregation functions of CATS metrics can be placed at service contact instances or C-SMAs.

CATSコンポーネントのリソースと処理能力に応じて、正規化と集約の機能は異なるCATSコンポーネントに配置できます。1つのアプローチは、特にC-PSがCATS‑Forwarderと同じ場所に配置されている場合に、正規化と集約の機能をC-PSから離れた場所に実装することです。これを念頭に置くと、CATSメトリックの正規化と集約の機能は、サービスコンタクトインスタンスまたはC-SMAに配置できます。

When C-SMAs are co-located with CATS‑Forwarders where there are limited resources for processing, the placement of normalization functions in a C-SMA may bring too much overhead and may influence the routing efficiency. Therefore, this document suggests implementing the normalization function at the service contact instances. Regarding the aggregation functions, it can be implemented in a C-SMA or the service contact instances.

C-SMAが処理のためのリソースが限られているCATS‑Forwarderと同じ場所に配置されている場合、正規化機能をC-SMAに配置すると、オーバーヘッドが大きくなりすぎ、ルーティングの効率に影響を与える可能性があります。したがって、この文書では、正規化機能をサービスコンタクトインスタンスに実装することを提案します。集約機能については、C-SMAまたはサービスコンタクトインスタンスに実装できます。

In order to ensure consistent CATS decisions, the same normalization and aggregation functions must be enabled in all involved CATS components. Also, in the case that service contact instances and C-SMAs are provided by different vendors, it is necessary to use the same common normalization and aggregation functions, so that the service contact instance selection result can be fair among all the service contact instances. To that aim, a set of normalization and aggregation functions must be standardized. To accommodate contexts where multiple functions are supported, CATS implementations must expose a configuration parameter to control the activation of normalization and aggregation functions.

一貫したCATSの判断を保証するために、関与するすべてのCATSコンポーネントで同じ正規化と集約の機能が有効になっていなければなりません。また、サービスコンタクトインスタンスとC-SMAが異なるベンダーによって提供される場合、すべてのサービスコンタクトインスタンス間でサービスコンタクトインスタンスの選択結果が公平になるように、同じ共通の正規化と集約の機能を使用する必要があります。そのために、正規化と集約の機能の集合は標準化されなければなりません。複数の機能がサポートされる文脈に対応するために、CATSの実装は、正規化と集約の機能の有効化を制御するための設定パラメーターを公開しなければなりません。

5.5. Verifying Correct Operations

5.5. 正しい動作の検証

A CATS implementation must log error events for better network management and operation. The means to assess the reachability and trace CATS paths should be supported.

CATSの実装は、より良いネットワークの管理と運用のために、エラーイベントをログに記録しなければなりません。到達可能性を評価し、CATSのパスをトレースするための手段がサポートされるべきです。

5.6. Impact on Network Operations

5.6. ネットワーク運用への影響

Computing metrics are collected and distributed in CATS. A new function needs to be deployed to manage the cooperation between network elements and computing elements. For example, this function may be provided by an orchestrator connecting with C-SMA and C-NMA. This might bring more complexity of the network management, especially if this function is not leveraged for other purposes beyond CATS.

CATSでは、コンピューティングメトリックが収集および配布されます。ネットワーク要素とコンピューティング要素の間の連携を管理するために、新しい機能を展開する必要があります。たとえば、この機能は、C-SMAとC-NMAに接続するオーケストレーターによって提供される場合があります。これは、特にこの機能がCATS以外の目的に活用されない場合、ネットワーク管理の複雑さを増す可能性があります。

6. Security Considerations

6. セキュリティーに関する考慮事項

The computing resource information changes over time very frequently, especially with the creation and termination of service instances. When such information is carried in a routing protocol, too many updates may affect network stability. This issue could be exploited by an attacker (e.g., by spawning and deleting service instances very rapidly). CATS solutions must support guards against such misbehaviors. For example, these solutions should support aggregation techniques, dampening mechanisms, and threshold-triggered distribution updates.

コンピューティングリソースの情報は、特にサービスインスタンスの作成と終了に伴って、時間とともに非常に頻繁に変化します。そのような情報がルーティングプロトコルで運ばれる場合、更新が多すぎるとネットワークの安定性に影響を与える可能性があります。この問題は、攻撃者によって（たとえば、サービスインスタンスを非常に急速に生成および削除することで）悪用される可能性があります。CATSのソリューションは、そのような不正な振る舞いに対する防御をサポートしなければなりません。たとえば、これらのソリューションは、集約の手法、ダンピングのメカニズム、およびしきい値でトリガーされる配布の更新をサポートすべきです。

The information distributed by the C-SMAs and C-NMAs may be sensitive. Such information could indeed disclose intelligence about the network and the location of compute resources hosted in service sites. This information may be used by an attacker to identify weak spots in an operator's network. Furthermore, such information may be modified by an attacker, resulting in disrupted service delivery for the clients, even including misdirection of traffic to an attacker's service implementation. CATS solutions must support authentication and integrity-protection mechanisms between C-SMAs/C-NMAs and C-PSes and between C-PSes and Ingress CATS‑Forwarders. Also, C-SMAs need to support a mechanism to authenticate the services for which they provide information to C-PS computation logics, among other CATS functions.

C-SMAとC-NMAによって配布される情報は、機密性が高い場合があります。そのような情報は、実際にネットワークやサービスサイトでホストされているコンピューティングリソースの場所に関する情報を開示する可能性があります。この情報は、攻撃者がオペレーターのネットワークの弱点を特定するために使用される可能性があります。さらに、そのような情報は攻撃者によって変更される可能性があり、その結果、クライアントに対するサービスの提供が中断されたり、トラフィックが攻撃者のサービス実装に誤って向けられたりすることさえあります。CATSのソリューションは、C-SMA/C-NMAとC-PSの間、およびC-PSとIngress CATS‑Forwarderの間で、認証と完全性保護のメカニズムをサポートしなければなりません。また、C-SMAは、とりわけ、C-PSの計算ロジックに情報を提供する対象のサービスを認証するためのメカニズムをサポートする必要があります。

This document focuses on the scenario of a single service provider. Hence, security considerations relevant to deployment with multiple service providers are out of scope.

この文書は、単一のサービスプロバイダーのシナリオに焦点を当てています。したがって、複数のサービスプロバイダーによる展開に関連するセキュリティーに関する考慮事項は範囲外です。

7. Privacy Considerations

7. プライバシーに関する考慮事項

CATS solutions must support preventing on-path nodes in the underlay infrastructure from fingerprinting and tracking clients (e.g., determining which client accesses which service). More generally, personal data must not be exposed to external parties by CATS beyond what is carried in the packet that was originally issued by a client.

CATSのソリューションは、アンダーレイインフラストラクチャー内の経路上のノードがクライアントのフィンガープリンティングや追跡（たとえば、どのクライアントがどのサービスにアクセスしているかの判断）を行うことの防止をサポートしなければなりません。より一般的には、クライアントによって最初に発行されたパケットで運ばれるものを超えて、CATSによって個人データが外部の当事者に公開されてはなりません。

CATS involves user-related data (e.g., access patterns or service requests) across service sites. Identifying a service site does not necessarily identify the service that is being invoked (typically, a service site may host many services, let alone that service instances may be relocated to other sites). However, when unambiguous correlation can be established between a service request and a service site, the binding of a service request and a service contact instance is sensitive, and such information should be encrypted.

CATSには、サービスサイトにまたがるユーザー関連のデータ（たとえば、アクセスパターンやサービスリクエスト）が関わります。サービスサイトを識別することは、必ずしも呼び出されているサービスを識別することにはなりません（通常、サービスサイトは多くのサービスをホストする場合があり、ましてやサービスインスタンスが他のサイトに移動される場合もあります）。しかし、サービスリクエストとサービスサイトの間に曖昧さのない相関関係を確立できる場合、サービスリクエストとサービスコンタクトインスタンスの結び付きは機密性が高く、そのような情報は暗号化されるべきです。

To prevent the information leaking between CATS components, the C-PS computed path information should be encrypted in distribution. The specific encryption method may be applied at the network layer, transport layer, or application layer depending on the implementation. As such, the exact implementation details are out of the scope of this document.

CATSコンポーネント間での情報の漏洩を防ぐために、C-PSが計算したパス情報は、配布の際に暗号化されるべきです。具体的な暗号化方式は、実装に応じて、ネットワーク層、トランスポート層、またはアプリケーション層で適用される場合があります。そのため、正確な実装の詳細はこの文書の範囲外です。

This document focuses on the scenario of a single service provider. Hence, privacy considerations relevant to deployment with multiple service providers are out of scope.

この文書は、単一のサービスプロバイダーのシナリオに焦点を当てています。したがって、複数のサービスプロバイダーによる展開に関連するプライバシーに関する考慮事項は範囲外です。

For more discussions about privacy, refer to [RFC6462] and [RFC6973].

プライバシーに関するさらなる議論については、[RFC6462]と[RFC6973]を参照してください。

Appendix A. Deployment Examples

Appendix A. 展開の例

This section provides examples to illustrate CATS metrics distribution. These examples are not deployment recommendations.

このセクションでは、CATSメトリックの配布を説明するための例を示します。これらの例は展開の推奨事項ではありません。

The following example mainly describes a per-instance computing-related metric distribution for illustration purposes. Such information may be aggregated into a single advertisement.

次の例では、説明のために、主にインスタンスごとのコンピューティング関連のメトリックの配布について説明します。そのような情報は、単一の広告に集約される場合があります。

A.1. Distributed Model

A.1. 分散モデル

Figure 3 shows an example of how CATS metrics can be disseminated in the distributed model.

Figure 3は、分散モデルでCATSメトリックをどのように広めることができるかの例を示しています。

There is a client attached to the network via "CATS‑Forwarder 1". There are three service contact instances of the service with "CS-ID 1": two service contact instances with CSCI-IDs "1" and "2", respectively, are located at "Service Site 2" attached via "CATS‑Forwarder 2"; the third service contact instance is located at "Service Site 3" attached via "CATS‑Forwarder 3" and with "CSCI-ID 3". There is also a second service with "CS-ID 2" with only one service contact instance located at "Service Site 3".

「CATS‑Forwarder 1」を介してネットワークに接続されたクライアントがあります。「CS-ID 1」のサービスには3つのサービスコンタクトインスタンスがあります。CSCI-IDがそれぞれ「1」と「2」である2つのサービスコンタクトインスタンスは、「CATS‑Forwarder 2」を介して接続された「Service Site 2」に配置されています。3つ目のサービスコンタクトインスタンスは、「CATS‑Forwarder 3」を介して接続された「Service Site 3」に配置されており、「CSCI-ID 3」を持ちます。また、「CS-ID 2」の2つ目のサービスもあり、そのサービスコンタクトインスタンスは「Service Site 3」に配置された1つだけです。

The C-SMA collocated with "CATS‑Forwarder 2" distributes the computing metrics for both service contact instances (i.e., (CS-ID 1, CSCI-ID 1) and (CS-ID 1, CSCI-ID 2)). Similarly, the C-SMA located at "Service Site 3" advertises the computing metrics for the two services hosted by "Service Site 3". The C-SMA may distribute the computing metrics to the Egress "CATS‑Forwarder 3". Then, the computing metrics can be redistributed by the Egress CATS‑Forwarder to the Ingress CATS‑Forwarder. The C-SMA also may directly distribute the computing metrics to the Ingress CATS‑Forwarder.

「CATS‑Forwarder 2」と同じ場所に配置されたC-SMAは、両方のサービスコンタクトインスタンス（つまり、(CS-ID 1, CSCI-ID 1)と(CS-ID 1, CSCI-ID 2)）のコンピューティングメトリックを配布します。同様に、「Service Site 3」に配置されたC-SMAは、「Service Site 3」でホストされている2つのサービスのコンピューティングメトリックを広告します。C-SMAは、コンピューティングメトリックをEgressの「CATS‑Forwarder 3」に配布する場合があります。その後、コンピューティングメトリックは、Egress CATS‑ForwarderによってIngress CATS‑Forwarderに再配布される場合があります。C-SMAは、コンピューティングメトリックをIngress CATS‑Forwarderに直接配布する場合もあります。

The computing metrics advertisements are processed by the C-PS hosted by "CATS‑Forwarder 1". The C-PS also processes network metric advertisements sent by the C-NMA. All metrics are used by the C-PS to select the most relevant path that leads to the Egress CATS‑Forwarder according to the initial client's service request, the service that is requested ("CS-ID 1" or "CS-ID 2"), the state of the service contact instances as reported by the metrics, and the state of the network.

コンピューティングメトリックの広告は、「CATS‑Forwarder 1」でホストされているC-PSによって処理されます。C-PSは、C-NMAから送信されたネットワークメトリックの広告も処理します。すべてのメトリックは、C-PSが、最初のクライアントのサービスリクエスト、要求されたサービス（「CS-ID 1」または「CS-ID 2」）、メトリックによって報告されたサービスコンタクトインスタンスの状態、およびネットワークの状態に従って、Egress CATS‑Forwarderにつながる最も適切なパスを選択するために使用されます。

In the case of distributing aggregated per-site computing-related metrics, the per-instance CSCI-ID information will not be included in the advertisement. Instead, a per-site CSCI-ID may be used in case multiple sites are connected to the Egress CATS‑Forwarder to explicitly indicate the site from where the aggregated metrics come.

サイトごとに集約されたコンピューティング関連のメトリックを配布する場合、インスタンスごとのCSCI-IDの情報は広告に含まれません。代わりに、複数のサイトがEgress CATS‑Forwarderに接続されている場合には、集約されたメトリックがどのサイトから来たのかを明示的に示すために、サイトごとのCSCI-IDを使用できます。

A.2. Centralized Model

A.2. 集中モデル

An example of metrics distribution in the centralized model is illustrated in Figure 4.

集中モデルにおけるメトリックの配布の例をFigure 4に示します。

The C-SMA collocated with "CATS‑Forwarder 2" distributes the computing metrics for both service contact instances (i.e., (CS-ID 1, CSCI-ID 1) and (CS-ID 1, CSCI-ID 2)) to the centralized C-PS. In this case, the C-PS is a logically centralized element deployed separately with the "CATS‑Forwarder 1". Similarly, the C-SMA located at "Service Site 3" advertises the computing metrics for the two services hosted by "Service Site 3" to the centralized C-PS as well. Furthermore, the C-PS receives the network metrics sent from the C-NMA. All metrics are used by the C-PS to select the most relevant path that leads to the Egress CATS‑Forwarder. The selected paths will be sent from the C-PS to "CATS‑Forwarder 1" to indicate traffic steering.

「CATS‑Forwarder 2」と同じ場所に配置されたC-SMAは、両方のサービスコンタクトインスタンス（つまり、(CS-ID 1, CSCI-ID 1)と(CS-ID 1, CSCI-ID 2)）のコンピューティングメトリックを集中型のC-PSに配布します。この場合、C-PSは、「CATS‑Forwarder 1」とは別に展開された論理的に集中化された要素です。同様に、「Service Site 3」に配置されたC-SMAも、「Service Site 3」でホストされている2つのサービスのコンピューティングメトリックを集中型のC-PSに広告します。さらに、C-PSはC-NMAから送信されたネットワークメトリックを受信します。すべてのメトリックは、C-PSが、Egress CATS‑Forwarderにつながる最も適切なパスを選択するために使用されます。選択されたパスは、トラフィックのステアリングを指示するために、C-PSから「CATS‑Forwarder 1」に送信されます。

A.3. Hybrid Model

A.3. ハイブリッドモデル

An example of metrics distribution in the hybrid model is illustrated in Figure 5.

ハイブリッドモデルにおけるメトリックの配布の例をFigure 5に示します。

For example, the metrics 1, 2, and 3 associated with the "CS-ID 1" are collected by the centralized C-PS, and the metrics 4 and 5 are distributed via distributed protocols to the Ingress CATS‑Forwarder directly. For a service with "CS-ID 2", all the metrics are collected by the centralized C-PS. The CATS-computed path result will be distributed to the Ingress CATS‑Forwarders from the C-PS by considering both the metrics from the C-SMA and C-NMA. Furthermore, the Ingress CATS‑Forwarder may also have some ability to compute the path for subsequent packets accessing the same service.

たとえば、「CS-ID 1」に関連付けられたメトリック1、2、および3は集中型のC-PSによって収集され、メトリック4と5は分散型のプロトコルを介してIngress CATS‑Forwarderに直接配布されます。「CS-ID 2」のサービスについては、すべてのメトリックが集中型のC-PSによって収集されます。CATSによって計算されたパスの結果は、C-SMAとC-NMAの両方からのメトリックを考慮して、C-PSからIngress CATS‑Forwarderに配布されます。さらに、Ingress CATS‑Forwarderは、同じサービスにアクセスする後続のパケットのパスを計算する何らかの能力を持つ場合もあります。
