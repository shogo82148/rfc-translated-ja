RFC 8434

Requirements for Parallel NFS (pNFS) Layout Types

RFC 8434

並列NFS（pNFS）レイアウトタイプの要件

Abstract

概要

This document defines the requirements that individual Parallel NFS (pNFS) layout types need to meet in order to work within the pNFS framework as defined in RFC 5661. In so doing, this document aims to clearly distinguish between requirements for pNFS as a whole and those specifically directed to the pNFS file layout. The lack of a clear separation between the two sets of requirements has been troublesome for those specifying and evaluating new layout types. In this regard, this document updates RFC 5661.

この文書は、RFC 5661で定義されているpNFSフレームワーク内で動作するために、個々の並列NFS（Parallel NFS、pNFS）レイアウトタイプが満たす必要のある要件を定義します。そうすることで、この文書は、pNFS全体に対する要件と、pNFSファイルレイアウトに特に向けられた要件とを明確に区別することを目指します。この2組の要件が明確に分離されていないことは、新しいレイアウトタイプを規定したり評価したりする人々にとって厄介な問題となっていました。この点に関して、この文書はRFC 5661を更新します。

1. Introduction

1. はじめに

The concept of "layout type" has a central role in the definition and implementation of Parallel NFS (pNFS) (see [RFC5661]). Clients and servers implementing different layout types behave differently in many ways while conforming to the overall pNFS framework defined in [RFC5661] and this document. Layout types may differ as to:

「レイアウトタイプ（layout type）」という概念は、並列NFS（Parallel NFS、pNFS）の定義と実装において中心的な役割を担っています（[RFC5661]を参照）。異なるレイアウトタイプを実装するクライアントとサーバーは、[RFC5661]とこの文書で定義されたpNFSフレームワーク全体に準拠しながらも、多くの点で異なる振る舞いをします。レイアウトタイプは、次の点で異なる場合があります。

  • The method used to do I/O operations directed to data storage devices.
  • The requirements for communication between the metadata server (MDS) and the storage devices.
  • The means used to ensure that I/O requests are only processed when the client holds an appropriate layout.
  • The format and interpretation of nominally opaque data fields in pNFS-related NFSv4.x data structures.
  • データストレージデバイスに向けたI/O操作を行うために使用する方法
  • メタデータサーバー（MDS）とストレージデバイスとの間の通信に関する要件
  • クライアントが適切なレイアウトを保持している場合にのみI/Oリクエストが処理されることを保証するために使用する手段
  • pNFS関連のNFSv4.xデータ構造において、名目上は不透明なデータフィールドの形式と解釈

Each layout type will define the needed details for its usage in the specification for that layout type; layout type specifications are always Standards Track RFCs. Except for the file layout type defined in Section 13 of [RFC5661], existing layout types are defined in their own Standards Track documents, and it is anticipated that new layout types will be defined in similar documents.

各レイアウトタイプは、その使用に必要な詳細を、そのレイアウトタイプの仕様で定義します。レイアウトタイプの仕様は、常に標準化過程のRFCです。[RFC5661]のセクション13で定義されたファイルレイアウトタイプを除き、既存のレイアウトタイプはそれぞれ独自の標準化過程の文書で定義されており、新しいレイアウトタイプも同様の文書で定義されることが想定されています。

The file layout type was defined in the Network File System (NFS) version 4.1 protocol specification [RFC5661]. The block layout type was defined in [RFC5663], and the object layout type was defined in [RFC5664]. Subsequently, the Small Computer System Interface (SCSI) layout type was defined in [RFC8154].

ファイルレイアウトタイプは、ネットワークファイルシステム（NFS）バージョン4.1プロトコルの仕様[RFC5661]で定義されました。ブロックレイアウトタイプは[RFC5663]で、オブジェクトレイアウトタイプは[RFC5664]で定義されました。その後、SCSI（Small Computer System Interface）レイアウトタイプが[RFC8154]で定義されました。

Some implementers have interpreted the text in Sections 12 ("Parallel NFS (pNFS)") and 13 ("NFSv4.1 as a Storage Protocol in pNFS: the File Layout Type") of [RFC5661] as applying only to the file layout type. Because Section 13 was not covered in a separate Standards Track document such as those for both the block and object layout types, there was some confusion as to the responsibilities of both the metadata server and the data servers (DSs) that were laid out in Section 12.

一部の実装者は、[RFC5661]のセクション12（「Parallel NFS (pNFS)」）とセクション13（「NFSv4.1 as a Storage Protocol in pNFS: the File Layout Type」）の記述を、ファイルレイアウトタイプにのみ適用されるものと解釈してきました。セクション13は、ブロックレイアウトタイプやオブジェクトレイアウトタイプのような別個の標準化過程の文書で扱われていなかったため、セクション12で示されたメタデータサーバーとデータサーバー（DS）の双方の責任について、いくらかの混乱がありました。

As a consequence, authors of new specifications (see [RFC8435] and [Lustre]) may struggle to meet the requirements to be a pNFS layout type. This document gathers the requirements from all of the original Standards Track documents regarding layout type and then specifies the requirements placed on all layout types independent of the particular type chosen.

その結果、新しい仕様の著者（[RFC8435]と[Lustre]を参照）は、pNFSレイアウトタイプとなるための要件を満たすのに苦労する可能性があります。この文書は、レイアウトタイプに関する元の標準化過程の文書すべてから要件を集め、選択された特定のタイプに依存しない、すべてのレイアウトタイプに課される要件を規定します。

2. Definitions

2. 定義

control communication requirement:
the specification for information on layouts, stateids, file metadata, and file data that must be communicated between the metadata server and the storage devices. There is a separate set of requirements for each layout type.
control protocol:
the particular mechanism that an implementation of a layout type would use to meet the control communication requirement for that layout type. This need not be a protocol as normally understood. In some cases, the same protocol may be used as both a control protocol and storage protocol.
storage protocol:
the protocol used by clients to do I/O operations to the storage device. Each layout type specifies the set of storage protocols.
loose coupling:
when the control protocol is a storage protocol.
tight coupling:
an arrangement in which the control protocol is one designed specifically for control communication. It may be either a proprietary protocol adapted specifically to a particular metadata server or a protocol based on a Standards Track document.
(file) data:
that part of the file system object that contains the data to be read or written. It is the contents of the object rather than the attributes of the object.
data server (DS):

a pNFS server that provides the file's data when the file system object is accessed over a file-based protocol. Note that this usage differs from that in [RFC5661], which applies the term in some cases even when other sorts of protocols are being used. Depending on the layout, there might be one or more data servers over which the data is striped. While the metadata server is strictly accessed over the NFSv4.1 protocol, the data server could be accessed via any file access protocol that meets the pNFS requirements.

See Section 2.1 for a comparison of this term and "storage device".

storage device:
the target to which clients may direct I/O requests when they hold an appropriate layout. Note that each data server is a storage device but that some storage device are not data servers. See Section 2.1 for further discussion.
fencing:
the process by which the metadata server prevents the storage devices from processing I/O from a specific client to a specific file.
layout:

the information a client uses to access file data on a storage device. This information includes specification of the protocol (layout type) and the identity of the storage devices to be used.

The bulk of the contents of the layout are defined in [RFC5661] as nominally opaque, but individual layout types are responsible for specifying the format of the layout data.

layout iomode:
a grant of either read-only or read/write I/O to the client.
layout stateid:
a 128-bit quantity returned by a server that uniquely defines the layout state provided by the server for a specific layout that describes a layout type and file (see Section 12.5.2 of [RFC5661]). Further, Section 12.5.3 of [RFC5661] describes differences in handling between layout stateids and other stateid types.
layout type:
a specification of both the storage protocol used to access the data and the aggregation scheme used to lay out the file data on the underlying storage devices.
recalling a layout:
a graceful recall, via a callback, of a specific layout by the metadata server to the client. Graceful here means that the client would have the opportunity to flush any WRITEs, etc., before returning the layout to the metadata server.
revoking a layout:
an invalidation of a specific layout by the metadata server. Once revocation occurs, the metadata server will not accept as valid any reference to the revoked layout, and a storage device will not accept any client access based on the layout.
(file) metadata:
the part of the file system object that contains various descriptive data relevant to the file object, as opposed to the file data itself. This could include the time of last modification, access time, EOF position, etc.
metadata server (MDS):
the pNFS server that provides metadata information for a file system object. It is also responsible for generating, recalling, and revoking layouts for file system objects, for performing directory operations, and for performing I/O operations to regular files when the clients direct these to the metadata server itself.
stateid:
a 128-bit quantity returned by a server that uniquely defines the set of locking-related state provided by the server. Stateids may designate state related to open files, byte-range locks, delegations, or layouts.
制御通信要件（control communication requirement）：
メタデータサーバーとストレージデバイスとの間で通信されなければならない、レイアウト、stateid、ファイルメタデータ、ファイルデータに関する情報の仕様です。レイアウトタイプごとに別々の要件の組があります。
制御プロトコル（control protocol）：
レイアウトタイプの実装が、そのレイアウトタイプの制御通信要件を満たすために使用する特定のメカニズムです。これは、通常の意味でのプロトコルである必要はありません。場合によっては、同じプロトコルが制御プロトコルとストレージプロトコルの両方として使用されることもあります。
ストレージプロトコル（storage protocol）：
クライアントがストレージデバイスに対してI/O操作を行うために使用するプロトコルです。各レイアウトタイプは、ストレージプロトコルの集合を規定します。
疎結合（loose coupling）：
制御プロトコルがストレージプロトコルである場合です。
密結合（tight coupling）：
制御プロトコルが、制御通信のために特別に設計されたものである構成です。これは、特定のメタデータサーバーに特化して適合させた独自のプロトコルの場合もあれば、標準化過程の文書に基づくプロトコルの場合もあります。
（ファイル）データ（(file) data）：
ファイルシステムオブジェクトのうち、読み書きされるデータを含む部分です。これは、オブジェクトの属性ではなく、オブジェクトの内容です。
データサーバー（data server、DS）：

ファイルシステムオブジェクトがファイルベースのプロトコルでアクセスされる場合に、ファイルのデータを提供するpNFSサーバーです。この用法は、他の種類のプロトコルが使用される場合にもこの用語を適用することがある[RFC5661]での用法とは異なることに注意してください。レイアウトによっては、データがストライプ化される先のデータサーバーが1つ以上存在する場合があります。メタデータサーバーには厳密にNFSv4.1プロトコルでアクセスしますが、データサーバーには、pNFSの要件を満たす任意のファイルアクセスプロトコルでアクセスできます。

この用語と「ストレージデバイス」の比較については、セクション2.1を参照してください。

ストレージデバイス（storage device）：
クライアントが適切なレイアウトを保持している場合に、I/Oリクエストを向けてもよい対象です。各データサーバーはストレージデバイスですが、一部のストレージデバイスはデータサーバーではないことに注意してください。詳しい議論についてはセクション2.1を参照してください。
フェンシング（fencing）：
特定のクライアントから特定のファイルへのI/Oをストレージデバイスが処理しないように、メタデータサーバーが防ぐ処理です。
レイアウト（layout）：

クライアントがストレージデバイス上のファイルデータにアクセスするために使用する情報です。この情報には、プロトコル（レイアウトタイプ）の指定と、使用するストレージデバイスの識別情報が含まれます。

レイアウトの内容の大部分は[RFC5661]で名目上は不透明なものとして定義されていますが、レイアウトデータの形式を規定する責任は個々のレイアウトタイプにあります。

レイアウトiomode（layout iomode）：
読み取り専用または読み書きのいずれかのI/Oをクライアントに許可するものです。
レイアウトstateid（layout stateid）：
レイアウトタイプとファイルを記述する特定のレイアウトについて、サーバーが提供するレイアウト状態を一意に定義する、サーバーが返す128ビットの量です（[RFC5661]のセクション12.5.2を参照）。さらに、[RFC5661]のセクション12.5.3は、レイアウトstateidと他の種類のstateidとの扱いの違いを説明しています。
レイアウトタイプ（layout type）：
データにアクセスするために使用するストレージプロトコルと、基盤となるストレージデバイス上にファイルデータを配置するために使用する集約方式の両方の仕様です。
レイアウトのリコール（recalling a layout）：
メタデータサーバーがクライアントに対して、コールバックを介して特定のレイアウトを穏当にリコールすることです。ここでの「穏当に（graceful）」とは、クライアントがレイアウトをメタデータサーバーに返却する前に、WRITEなどをフラッシュする機会を持てることを意味します。
レイアウトの取り消し（revoking a layout）：
メタデータサーバーによる特定のレイアウトの無効化です。取り消しが行われると、メタデータサーバーは取り消されたレイアウトへの参照を有効なものとして受け入れず、ストレージデバイスはそのレイアウトに基づくクライアントのアクセスを受け入れません。
（ファイル）メタデータ（(file) metadata）：
ファイルシステムオブジェクトのうち、ファイルデータそのものではなく、ファイルオブジェクトに関連するさまざまな記述的データを含む部分です。これには、最終更新時刻、アクセス時刻、EOF位置などが含まれる場合があります。
メタデータサーバー（metadata server、MDS）：
ファイルシステムオブジェクトのメタデータ情報を提供するpNFSサーバーです。メタデータサーバーは、ファイルシステムオブジェクトのレイアウトの生成、リコール、取り消し、ディレクトリー操作の実行、そしてクライアントが通常のファイルへのI/O操作をメタデータサーバー自身に向けた場合のその実行にも責任を負います。
stateid：
サーバーが提供するロック関連の状態の集合を一意に定義する、サーバーが返す128ビットの量です。stateidは、オープンされたファイル、バイト範囲ロック、委任、またはレイアウトに関連する状態を指定する場合があります。

2.1. Use of the Terms "Data Server" and "Storage Device"

2.1. 「データサーバー」と「ストレージデバイス」という用語の使用

In [RFC5661], the terms "data server" and "storage device" are used somewhat inconsistently:

[RFC5661]では、「データサーバー（data server）」と「ストレージデバイス（storage device）」という用語の使い方にやや一貫性がありません。

  • In Section 12, where pNFS in general is discussed, the term "storage device" is used.
  • In Section 13, where the file layout type is discussed, the term "data server" is used.
  • In other sections, the term "data server" is used, even in contexts where the storage access type is not NFSv4.1 or any other file access protocol.
  • pNFS全般を論じているセクション12では、「ストレージデバイス」という用語が使われています。
  • ファイルレイアウトタイプを論じているセクション13では、「データサーバー」という用語が使われています。
  • その他のセクションでは、ストレージのアクセスタイプがNFSv4.1やその他のファイルアクセスプロトコルではない文脈でも、「データサーバー」という用語が使われています。

As this document deals with pNFS in general, it uses the more generic term "storage device" in preference to "data server". The term "data server" is used only in contexts in which a file server is used as a storage device. Note that every data server is a storage device, but storage devices that use protocols that are not file access protocols (such as NFS) are not data servers.

この文書はpNFS全般を扱うため、「データサーバー」よりも、より一般的な用語である「ストレージデバイス」を優先して使用します。「データサーバー」という用語は、ファイルサーバーがストレージデバイスとして使用される文脈でのみ使用します。すべてのデータサーバーはストレージデバイスですが、ファイルアクセスプロトコル（NFSなど）ではないプロトコルを使用するストレージデバイスはデータサーバーではないことに注意してください。

Since a given storage device may support multiple layout types, a given device can potentially act as a data server for some set of storage protocols while simultaneously acting as a storage device for others.

あるストレージデバイスが複数のレイアウトタイプをサポートする場合があるため、あるデバイスが、一部のストレージプロトコルに対してはデータサーバーとして動作し、同時に他のストレージプロトコルに対してはストレージデバイスとして動作する可能性があります。

2.2. Requirements Language

2.2. 要件言語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

This document differs from most Standards Track documents in that it specifies requirements for those defining future layout types rather than defining the requirements for implementations directly. This document makes clear whether:

この文書は、実装に対する要件を直接定義するのではなく、将来のレイアウトタイプを定義する人々に対する要件を規定する点で、ほとんどの標準化過程の文書とは異なります。この文書は、次のどれに当たるかを明確にします。

  1. any particular requirement applies to implementations.
  2. any particular requirement applies to those defining layout types.
  3. the requirement is a general requirement that implementations need to conform to, with the specific means left to layout type definitions type to specify.
  1. 特定の要件が実装に適用されるのか。
  2. 特定の要件がレイアウトタイプを定義する人々に適用されるのか。
  3. その要件が、実装が準拠する必要のある一般的な要件であり、具体的な手段はレイアウトタイプの定義に委ねられているのか。

3. The Control Protocol

3. 制御プロトコル

A layout type has to meet the requirements that apply to the interaction between the metadata server and the storage device such that they present to the client a consistent view of stored data and locking state (Section 12.2.6 of [RFC5661]). Particular implementations may satisfy these requirements in any manner they choose, and the mechanism chosen need not be described as a protocol. Specifications defining layout types need to clearly show how implementations can meet the requirements discussed below, especially with respect to those that have security implications. In addition, such specifications may find it necessary to impose requirements on implementations of the layout type to ensure appropriate interoperability.

レイアウトタイプは、メタデータサーバーとストレージデバイスがクライアントに対して格納されたデータとロック状態の一貫したビューを提示するように、両者の相互作用に適用される要件を満たさなければなりません（[RFC5661]のセクション12.2.6）。個々の実装は、これらの要件を任意の方法で満たしてかまいません。また、選択したメカニズムをプロトコルとして記述する必要はありません。レイアウトタイプを定義する仕様は、以下で論じる要件、特にセキュリティーに影響する要件を実装がどのように満たせるかを明確に示す必要があります。さらに、そのような仕様では、適切な相互運用性を確保するために、そのレイアウトタイプの実装に要件を課す必要が生じる場合もあります。

In some cases, there may be no control protocol other than the storage protocol. This is often described as using a "loosely coupled" model. In such cases, the assumption is that the metadata server, storage devices, and client may be changed independently and that the implementation requirements in the layout type specification need to ensure this degree of interoperability. This model is used in the block and object layout type specification.

場合によっては、ストレージプロトコル以外に制御プロトコルが存在しないこともあります。これは、しばしば「疎結合」モデルを使用していると表現されます。そのような場合、メタデータサーバー、ストレージデバイス、クライアントはそれぞれ独立に変更される可能性があり、レイアウトタイプの仕様における実装要件がこの程度の相互運用性を確保する必要がある、という前提になります。このモデルは、ブロックレイアウトタイプとオブジェクトレイアウトタイプの仕様で使用されています。

In other cases, it is assumed that there will be a purpose-built control protocol that may be different for different implementations of the metadata server and data server. The assumption here is that the metadata server and data servers are designed and implemented as a unit and interoperability needs to be assured between clients and metadata-data server pairs, developed independently. This is the model used for the file layout.

その他の場合では、メタデータサーバーとデータサーバーの実装ごとに異なる可能性がある、専用の制御プロトコルが存在することが想定されます。ここでの前提は、メタデータサーバーとデータサーバーが一体として設計・実装され、相互運用性は、独立に開発されたクライアントとメタデータ・データサーバーの組との間で確保される必要がある、というものです。これはファイルレイアウトで使用されているモデルです。

Another possibility is for the definition of a control protocol to be specified in a Standards Track document. There are two subcases to consider:

もう1つの可能性は、制御プロトコルの定義を標準化過程の文書で規定することです。考慮すべき下位のケースが2つあります。

  • A new layout type includes a definition of a particular control protocol whose use is obligatory for metadata servers and storage devices implementing the layout type. In this case, the interoperability model is similar to the first case above, and the defining document should assure interoperability among metadata servers, storage devices, and clients developed independently.
  • A control protocol is defined in a Standards Track document that meets the control protocol requirements for one of the existing layout types. In this case, the new document's job is to assure interoperability between metadata servers and storage devices developed separately. The existing definition document for the selected layout type retains the function of assuring interoperability between clients and a given collection of metadata servers and storage devices. In this context, implementations that implement the new protocol are treated in the same way as those that use an internal control protocol or a functional equivalent.
  • 新しいレイアウトタイプが特定の制御プロトコルの定義を含み、そのレイアウトタイプを実装するメタデータサーバーとストレージデバイスにはその使用が義務付けられている場合です。この場合、相互運用性のモデルは上記の最初のケースと同様であり、定義する文書は、独立に開発されたメタデータサーバー、ストレージデバイス、クライアントの間の相互運用性を確保すべきです。
  • 既存のレイアウトタイプのいずれかに対する制御プロトコルの要件を満たす制御プロトコルが、標準化過程の文書で定義される場合です。この場合、新しい文書の役割は、別々に開発されたメタデータサーバーとストレージデバイスの間の相互運用性を確保することです。選択されたレイアウトタイプの既存の定義文書は、クライアントと、メタデータサーバーおよびストレージデバイスの特定の集まりとの間の相互運用性を確保する機能を引き続き担います。この文脈では、新しいプロトコルを実装する実装は、内部の制御プロトコルまたはそれと機能的に同等のものを使用する実装と同じように扱われます。

An example of this last case is the SCSI layout type [RFC8154], which extends the block layout type. The block layout type had a requirement for fencing of clients but did not present a way for the control protocol (in this case, the SCSI storage protocol) to fence the client. The SCSI layout type remedies that in [RFC8154] and, in effect, has a tightly coupled model.

この最後のケースの例が、ブロックレイアウトタイプを拡張したSCSIレイアウトタイプ[RFC8154]です。ブロックレイアウトタイプには、クライアントのフェンシングに関する要件がありましたが、制御プロトコル（この場合はSCSIストレージプロトコル）がクライアントをフェンスする方法は示されていませんでした。SCSIレイアウトタイプは[RFC8154]でこれを改善しており、事実上、密結合モデルとなっています。

3.1. Control Protocol Requirements

3.1. 制御プロトコルの要件

The requirements of interactions between the metadata server and the storage devices are:

メタデータサーバーとストレージデバイスとの間の相互作用に関する要件は次のとおりです。

  1. The metadata server MUST be able to service the client's I/O requests if the client decides to make such requests to the metadata server instead of to the storage device. The metadata server must be able to retrieve the data from the constituent storage devices and present it back to the client. A corollary to this is that even though the metadata server has successfully given the client a layout, the client MAY still send I/O requests to the metadata server.

  2. The metadata server MUST be able to restrict access to a file on the storage devices when it revokes a layout. The metadata server typically would revoke a layout whenever a client fails to respond to a recall or a client's lease is expired due to non-renewal. It might also revoke the layout as a means of enforcing a change in locking state or access permissions that the storage device cannot directly enforce.

    Effective revocation may require client cooperation in using a particular stateid (file layout) or principal (e.g., flexible file layout) when performing I/O.

    In contrast, there is no requirement to restrict access to a file on the storage devices when a layout is recalled. It is only after the metadata server determines that the client is not gracefully returning the layout and starts the revocation that this requirement is enforced.

  3. A pNFS implementation MUST NOT allow the violation of NFSv4.1's access controls: Access Control Lists (ACLs) and file open modes. Section 12.9 of [RFC5661] specifically lays this burden on the combination of clients, storage devices, and the metadata server. However, the specification of the individual layout type might create requirements as to how this is to be done. This may include a possible requirement for the metadata server to update the storage device so that it can enforce security.

    The file layout requires the storage device to enforce access whereas the flexible file layout requires both the storage device and the client to enforce security.

  4. Interactions between locking and I/O operations MUST obey existing semantic restrictions. In particular, if an I/O operation would be invalid when directed at the metadata server, it is not to be allowed when performed on the storage device.

    For the block and SCSI layouts, as the storage device is not able to reject the I/O operation, the client is responsible for enforcing this requirement.

  5. Any disagreement between the metadata server and the data server as to the value of attributes such as modify time, the change attribute, and the EOF position MUST be of limited duration with clear means of resolution of any discrepancies being provided. Note the following:

    1. Discrepancies need not be resolved unless any client has accessed the file in question via the metadata server, typically by performing a GETATTR.
    2. A particular storage device might be striped, and as such, its local view of the EOF position does not match the global EOF position.
    3. Both clock skew and network delay can lead to the metadata server and the storage device having different values of the time attributes. As long as those differences can be accounted for in what is presented to the client in a GETATTR, then no violation results.
    4. A LAYOUTCOMMIT requires that changes in attributes resulting from operations on the storage device need to be reflected in the metadata server by the completion of the operation.
  1. クライアントがI/Oリクエストをストレージデバイスではなくメタデータサーバーに送ることにした場合、メタデータサーバーはそのリクエストを処理できなければなりません（MUST）。メタデータサーバーは、構成要素であるストレージデバイスからデータを取得し、それをクライアントに返すことができなければなりません。この帰結として、メタデータサーバーがクライアントにレイアウトを正常に与えた後であっても、クライアントはI/Oリクエストをメタデータサーバーに送信してもよいです（MAY）。

  2. メタデータサーバーは、レイアウトを取り消す際に、ストレージデバイス上のファイルへのアクセスを制限できなければなりません（MUST）。メタデータサーバーは通常、クライアントがリコールに応答しない場合や、更新されないためにクライアントのリースが期限切れになった場合に、レイアウトを取り消します。また、ストレージデバイスが直接強制できないロック状態やアクセス許可の変更を強制する手段として、レイアウトを取り消すこともあります。

    効果的な取り消しのためには、I/Oを行う際に特定のstateid（ファイルレイアウト）やプリンシパル（たとえばフレキシブルファイルレイアウト）を使用するという、クライアントの協力が必要になる場合があります。

    対照的に、レイアウトがリコールされたときに、ストレージデバイス上のファイルへのアクセスを制限するという要件はありません。この要件が強制されるのは、クライアントがレイアウトを穏当に返却していないとメタデータサーバーが判断し、取り消しを開始した後だけです。

  3. pNFSの実装は、NFSv4.1のアクセス制御、すなわちアクセス制御リスト（ACL）とファイルのオープンモードへの違反を許してはなりません（MUST NOT）。[RFC5661]のセクション12.9は、この負担を、クライアント、ストレージデバイス、メタデータサーバーの組み合わせに明確に課しています。ただし、個々のレイアウトタイプの仕様が、これをどのように行うかについての要件を作り出す場合があります。これには、ストレージデバイスがセキュリティーを強制できるように、メタデータサーバーがストレージデバイスを更新するという要件が含まれる可能性があります。

    ファイルレイアウトではストレージデバイスがアクセスを強制する必要がありますが、フレキシブルファイルレイアウトではストレージデバイスとクライアントの両方がセキュリティーを強制する必要があります。

  4. ロックとI/O操作の間の相互作用は、既存のセマンティクス上の制約に従わなければなりません（MUST）。特に、あるI/O操作がメタデータサーバーに向けられた場合に無効となるのであれば、その操作はストレージデバイス上で実行される場合にも許可されません。

    ブロックレイアウトとSCSIレイアウトでは、ストレージデバイスがI/O操作を拒否できないため、この要件を強制する責任はクライアントにあります。

  5. 更新時刻、change属性、EOF位置などの属性の値についてメタデータサーバーとデータサーバーの間に食い違いがある場合、その期間は限定されたものでなければなりません（MUST）。また、食い違いを解消する明確な手段が提供されていなければなりません。次の点に注意してください。

    1. いずれかのクライアントが、通常はGETATTRを実行することによって、メタデータサーバーを介して当該ファイルにアクセスしない限り、食い違いを解消する必要はありません。
    2. 特定のストレージデバイスがストライプ化されている場合があり、その場合、そのデバイスのローカルなEOF位置のビューはグローバルなEOF位置と一致しません。
    3. クロックのずれとネットワーク遅延のどちらも、メタデータサーバーとストレージデバイスが異なる時刻属性の値を持つ原因となりえます。それらの差が、GETATTRでクライアントに提示される内容の中で考慮されうる限り、違反にはなりません。
    4. LAYOUTCOMMITでは、ストレージデバイス上の操作によって生じた属性の変更が、その操作の完了までにメタデータサーバーに反映される必要があります。

These requirements may be satisfied in different ways by different layout types. As an example, while the file layout type uses the stateid to fence off the client, there is no requirement that other layout types use this stateid approach.

これらの要件は、レイアウトタイプによって異なる方法で満たされる場合があります。たとえば、ファイルレイアウトタイプはstateidを使用してクライアントをフェンスしますが、他のレイアウトタイプがこのstateidによる方法を使用するという要件はありません。

Each new Standards Track document for a layout type MUST address how the client, metadata server, and storage devices are to interact to meet these requirements.

レイアウトタイプに関する新しい標準化過程の文書はそれぞれ、これらの要件を満たすためにクライアント、メタデータサーバー、ストレージデバイスがどのように相互作用するのかを扱わなければなりません（MUST）。

3.2. Previously Undocumented Protocol Requirements

3.2. これまで文書化されていなかったプロトコルの要件

While not explicitly stated as requirements in Section 12 of [RFC5661], the existing layout types do have more requirements that they need to enforce.

[RFC5661]のセクション12では要件として明示されていませんが、既存のレイアウトタイプには、強制する必要のある要件がさらにあります。

The client has these obligations when making I/O requests to the storage devices:

クライアントは、ストレージデバイスにI/Oリクエストを行う際に、次の義務を負います。

  1. Clients MUST NOT perform I/O to the storage device if they do not have layouts for the files in question.
  2. Clients MUST NOT perform I/O operations outside of the specified ranges in the layout segment.
  3. Clients MUST NOT perform I/O operations that would be inconsistent with the iomode specified in the layout segments it holds.
  1. クライアントは、当該ファイルのレイアウトを持っていない場合、ストレージデバイスに対してI/Oを行ってはなりません（MUST NOT）。
  2. クライアントは、レイアウトセグメントで指定された範囲の外でI/O操作を行ってはなりません（MUST NOT）。
  3. クライアントは、自身が保持するレイアウトセグメントで指定されたiomodeと矛盾するI/O操作を行ってはなりません（MUST NOT）。

Under the file layout type, the storage devices are able to reject any request made not conforming to these requirements. This may not be possible for other known layout types, which puts the burden of enforcing such violations solely on the client. For these layout types:

ファイルレイアウトタイプでは、ストレージデバイスは、これらの要件に従っていないリクエストを拒否できます。これは他の既知のレイアウトタイプでは不可能な場合があり、その場合、そのような違反を防ぐ負担はクライアントだけにかかります。そのようなレイアウトタイプについては、次のとおりです。

  1. The metadata server MAY use fencing operations to the storage devices to enforce layout revocation against the client.
  2. The metadata server MUST allow the clients to perform data I/O against it, even if it has already granted the client a layout. A layout type might discourage such I/O, but it cannot forbid it.
  3. The metadata server MUST be able to do storage allocation, whether that is to create, delete, extend, or truncate files.
  1. メタデータサーバーは、クライアントに対するレイアウトの取り消しを強制するために、ストレージデバイスへのフェンシング操作を使用してもよいです（MAY）。
  2. メタデータサーバーは、すでにクライアントにレイアウトを付与している場合であっても、クライアントが自身に対してデータI/Oを行うことを許可しなければなりません（MUST）。レイアウトタイプはそのようなI/Oを推奨しないことはできますが、禁止することはできません。
  3. メタデータサーバーは、ファイルの作成、削除、拡張、切り詰めのいずれであっても、ストレージの割り当てを行えなければなりません（MUST）。

The means to address these requirements will vary with the layout type. A control protocol will be used to effect these; the control protocol could be a purpose-built one, one identical to the storage protocol, or a new Standards Track control protocol.

これらの要件に対処する手段は、レイアウトタイプによって異なります。これらを実現するために制御プロトコルが使用されます。制御プロトコルは、専用のもの、ストレージプロトコルと同一のもの、または新しい標準化過程の制御プロトコルのいずれかになりえます。

3.3. Editorial Requirements

3.3. 編集上の要件

This section discusses how the protocol requirements discussed above need to be addressed in documents specifying a new layout type. Depending on the interoperability model for the layout type in question, this may involve the imposition of layout-type-specific requirements that ensure appropriate interoperability of pNFS components that are developed separately.

このセクションでは、上で論じたプロトコルの要件を、新しいレイアウトタイプを規定する文書でどのように扱う必要があるかを論じます。対象のレイアウトタイプの相互運用性モデルによっては、これには、別々に開発されたpNFSのコンポーネントの適切な相互運用性を確保するための、レイアウトタイプ固有の要件を課すことが含まれる場合があります。

The specification of the layout type needs to make clear how the client, metadata server, and storage device act together to meet the protocol requirements discussed previously. If the document does not impose implementation requirements sufficient to ensure that these semantic requirements are met, it is not appropriate for publication as an RFC from the IETF stream.

レイアウトタイプの仕様は、前述のプロトコルの要件を満たすために、クライアント、メタデータサーバー、ストレージデバイスがどのように連携するのかを明確にする必要があります。文書が、これらのセマンティクス上の要件が満たされることを確保するのに十分な実装要件を課していない場合、その文書はIETFストリームのRFCとして発行するのに適切ではありません。

Some examples include:

いくつかの例を挙げます。

  • If the metadata server does not have a means to invalidate a stateid issued to the storage device to keep a particular client from accessing a specific file, then the layout type specification has to document how the metadata server is going to fence the client from access to the file on that storage device.
  • If the metadata server implements mandatory byte-range locking when accessed directly by the client, then the layout type specification must require that this also be done when data is read or written using the designated storage protocol.
  • 特定のクライアントが特定のファイルにアクセスできないようにするために、ストレージデバイスに対して発行したstateidを無効化する手段をメタデータサーバーが持たない場合、レイアウトタイプの仕様は、そのストレージデバイス上のファイルへのアクセスからメタデータサーバーがどのようにクライアントをフェンスするのかを文書化しなければなりません。
  • クライアントから直接アクセスされた場合にメタデータサーバーが強制バイト範囲ロックを実装しているのであれば、レイアウトタイプの仕様は、指定されたストレージプロトコルを使用してデータが読み書きされる場合にもこれが行われることを要求しなければなりません。

4. Specifications of Original Layout Types

4. 元のレイアウトタイプの仕様

This section discusses how the original layout types interact with Section 12 of [RFC5661], which enumerates the requirements of pNFS layout type specifications. It is not normative with regards to the file layout type presented in Section 13 of [RFC5661], the block layout type [RFC5663], and the object layout type [RFC5664]. These are discussed here only to illuminate the updates Section 3 of this document makes to Section 12 of [RFC5661].

このセクションでは、元のレイアウトタイプが、pNFSレイアウトタイプの仕様の要件を列挙している[RFC5661]のセクション12とどのように関わるのかを論じます。このセクションは、[RFC5661]のセクション13で示されたファイルレイアウトタイプ、ブロックレイアウトタイプ[RFC5663]、オブジェクトレイアウトタイプ[RFC5664]に関して規範的なものではありません。これらをここで論じるのは、この文書のセクション3が[RFC5661]のセクション12に対して行う更新を明らかにするためだけです。

4.1. File Layout Type

4.1. ファイルレイアウトタイプ

Because the storage protocol is a subset of NFSv4.1, the semantics of the file layout type comes closest to the semantics of NFSv4.1 in the absence of pNFS. In particular, the stateid and principal used for I/O MUST have the same effect and be subject to the same validation on a data server as it would have if the I/O were being performed on the metadata server itself. The same set of validations are applied whether or not pNFS is in effect.

ストレージプロトコルがNFSv4.1のサブセットであるため、ファイルレイアウトタイプのセマンティクスは、pNFSがない場合のNFSv4.1のセマンティクスに最も近くなります。特に、I/Oに使用されるstateidとプリンシパルは、データサーバー上で、そのI/Oがメタデータサーバー自身で実行された場合と同じ効果を持ち、同じ検証を受けなければなりません（MUST）。pNFSが有効かどうかにかかわらず、同じ一連の検証が適用されます。

While for most implementations, the storage devices can do the following validations that are each presented as a "SHOULD" and not a "MUST" in [RFC5661]:

ほとんどの実装では、ストレージデバイスは次の検証を行うことができますが、これらは[RFC5661]ではそれぞれ「MUST」ではなく「SHOULD」として示されています。

  1. client holds a valid layout,
  2. client I/O matches the layout iomode, and
  3. client does not go out of the byte ranges,
  1. クライアントが有効なレイアウトを保持していること
  2. クライアントのI/Oがレイアウトのiomodeと一致していること
  3. クライアントがバイト範囲の外に出ないこと

Actually, the first point is presented in [RFC5661] as both:

実際には、1点目は[RFC5661]で次の両方として示されています。

"MUST":

in Section 13.6

As described in Section 12.5.1, a client MUST NOT send an I/O to a data server for which it does not hold a valid layout; the data server MUST reject such an I/O.

"SHOULD":

in Section 13.8

The iomode need not be checked by the data servers when clients perform I/O. However, the data servers SHOULD still validate that the client holds a valid layout and return an error if the client does not.

「MUST」：

セクション13.6で

セクション12.5.1で説明しているように、クライアントは、有効なレイアウトを保持していないデータサーバーにI/Oを送信してはなりません（MUST NOT）。データサーバーはそのようなI/Oを拒否しなければなりません（MUST）。

「SHOULD」：

セクション13.8で

クライアントがI/Oを行う際に、データサーバーがiomodeを確認する必要はありません。ただし、データサーバーは、クライアントが有効なレイアウトを保持していることを引き続き検証し、保持していない場合はエラーを返すべきです（SHOULD）。

It should be noted that it is just these layout-specific checks that are optional, not the normal file access semantics. The storage devices MUST make all of the required access checks on each READ or WRITE I/O as determined by the NFSv4.1 protocol. If the metadata server would deny a READ or WRITE operation on a file due to its ACL, mode attribute, open access mode, open deny mode, mandatory byte-range locking state, or any other attributes and state, the storage device MUST also deny the READ or WRITE operation. Also, while the NFSv4.1 protocol does not mandate export access checks based on the client's IP address, if the metadata server implements such a policy, then that counts as such state as outlined above.

選択可能なのはこれらのレイアウト固有のチェックだけであり、通常のファイルアクセスのセマンティクスではないことに注意すべきです。ストレージデバイスは、NFSv4.1プロトコルで定められているとおり、各READまたはWRITEのI/Oに対して、必要なアクセスチェックをすべて行わなければなりません（MUST）。ファイルのACL、mode属性、オープンのアクセスモード、オープンの拒否モード、強制バイト範囲ロックの状態、その他の属性や状態のために、メタデータサーバーがそのファイルに対するREADまたはWRITE操作を拒否するのであれば、ストレージデバイスもそのREADまたはWRITE操作を拒否しなければなりません（MUST）。また、NFSv4.1プロトコルはクライアントのIPアドレスに基づくエクスポートのアクセスチェックを義務付けていませんが、メタデータサーバーがそのようなポリシーを実装している場合、それは上で概説したような状態に該当します。

The data filehandle provided by the PUTFH operation to the data server provides sufficient context to enable the data server to ensure that the client has a valid layout for the I/O being performed for the subsequent READ or WRITE operation in the compound.

PUTFH操作によってデータサーバーに提供されるデータファイルハンドルは、COMPOUND内の後続のREADまたはWRITE操作で実行されるI/Oについて、クライアントが有効なレイアウトを持っていることをデータサーバーが確認できるのに十分なコンテキストを提供します。

Finally, the data server can check the stateid presented in the READ or WRITE operation to see if that stateid has been rejected by the metadata server; if so, the data server will cause the I/O to be fenced. Whilst it might just be the open owner or lock owner on that client being fenced, the client should take the NFS4ERR_BAD_STATEID error code to mean it has been fenced from the file and contact the metadata server.

最後に、データサーバーは、READまたはWRITE操作で提示されたstateidを確認して、そのstateidがメタデータサーバーによって拒否されているかどうかを調べることができます。拒否されている場合、データサーバーはそのI/Oをフェンスします。フェンスされているのはそのクライアント上のopen ownerやlock ownerだけかもしれませんが、クライアントはNFS4ERR_BAD_STATEIDエラーコードを、そのファイルからフェンスされたことを意味するものと受け取り、メタデータサーバーに連絡すべきです。

4.2. Block Layout Type

4.2. ブロックレイアウトタイプ

With the block layout type, the storage devices are generally not able to enforce file-based security. Typically, storage area network (SAN) disk arrays and SAN protocols provide coarse-grained access control mechanisms (e.g., Logical Unit Number (LUN) mapping and/or masking), with a target granularity of disks rather than individual blocks and a source granularity of individual hosts rather than of users or owners. Access to block storage is logically at a lower layer of the I/O stack than NFSv4. Since NFSv4 security is not directly applicable to protocols that access such storage directly, Section 2.1 of [RFC5663] specifies that:

ブロックレイアウトタイプでは、ストレージデバイスは一般に、ファイルベースのセキュリティーを強制できません。通常、ストレージエリアネットワーク（SAN）のディスクアレイとSANプロトコルは、粒度の粗いアクセス制御メカニズム（たとえば、論理ユニット番号（LUN）のマッピングやマスキング）を提供しますが、その対象の粒度は個々のブロックではなくディスク単位であり、アクセス元の粒度はユーザーやオーナーではなく個々のホスト単位です。ブロックストレージへのアクセスは、論理的にはNFSv4よりも下位のI/Oスタックの層にあります。NFSv4のセキュリティーは、そのようなストレージに直接アクセスするプロトコルには直接適用できないため、[RFC5663]のセクション2.1は次のように規定しています。

in environments where pNFS clients cannot be trusted to enforce such policies, pNFS block layout types SHOULD NOT be used.

pNFSクライアントがそのようなポリシーを強制することを信頼できない環境では、pNFSブロックレイアウトタイプを使用すべきではありません（SHOULD NOT）。

Due to these granularity issues, the security burden has been shifted from the storage devices to the client. Those deploying implementations of this layout type need to be sure that the client implementation can be trusted. This is not a new sort of requirement in the context of SAN protocols. In such environments, the client is expected to provide block-based protection.

こうした粒度の問題のため、セキュリティーの負担はストレージデバイスからクライアントに移されています。このレイアウトタイプの実装を導入する人々は、クライアントの実装が信頼できることを確認する必要があります。これは、SANプロトコルの文脈では新しい種類の要件ではありません。そのような環境では、クライアントがブロックベースの保護を提供することが期待されています。

This shift of the burden also extends to locks and layouts. The storage devices are not able to enforce any of these, and the burden is pushed to the client to make the appropriate checks before sending I/O to the storage devices. For example, the server may use a layout iomode only allowing reading to enforce a mandatory read-only lock. In such cases, the client has to support that use by not sending WRITEs to the storage devices. The fundamental issue here is that the storage device is treated by this layout type in the same fashion as a local disk device. Once the client has access to the storage device, it is able to perform both READ and WRITE I/O to the entire storage device. The byte ranges in the layout, any locks, the layout iomode, etc., can only be enforced by the client. Therefore, the client is required to provide that enforcement.

この負担の移行は、ロックとレイアウトにも及びます。ストレージデバイスはこれらのいずれも強制できないため、ストレージデバイスにI/Oを送信する前に適切なチェックを行う負担はクライアントに押し付けられます。たとえば、サーバーは、強制的な読み取り専用ロックを強制するために、読み取りのみを許可するレイアウトiomodeを使用する場合があります。そのような場合、クライアントは、ストレージデバイスにWRITEを送信しないことで、その使い方に対応しなければなりません。ここでの根本的な問題は、このレイアウトタイプではストレージデバイスがローカルディスクデバイスと同じように扱われることです。クライアントがストレージデバイスにアクセスできるようになると、クライアントはストレージデバイス全体に対してREADとWRITEの両方のI/Oを実行できます。レイアウト内のバイト範囲、あらゆるロック、レイアウトiomodeなどは、クライアントによってしか強制できません。したがって、クライアントがその強制を行うことが要求されます。

In the context of fencing off of the client upon revocation of a layout, these limitations come into play again, i.e., the granularity of the fencing can only be at the level of the host and logical unit. Thus, if one of a client's layouts is revoked by the server, it will effectively revoke all of the client's layouts for files located on the storage units comprising the logical volume. This may extend to the client's layouts for files in other file systems. Clients need to be prepared for such revocations and reacquire layouts as needed.

レイアウトの取り消し時にクライアントをフェンスするという文脈でも、これらの制限が再び問題になります。すなわち、フェンシングの粒度は、ホストと論理ユニットのレベルにしかなりえません。したがって、クライアントのレイアウトの1つがサーバーによって取り消されると、事実上、論理ボリュームを構成するストレージユニット上にあるファイルに対する、そのクライアントのすべてのレイアウトが取り消されます。これは、他のファイルシステム内のファイルに対するクライアントのレイアウトにまで及ぶ場合があります。クライアントは、そのような取り消しに備え、必要に応じてレイアウトを再取得する必要があります。

4.3. Object Layout Type

4.3. オブジェクトレイアウトタイプ

With the object layout type, security checks occur during the allocation of the layout. The client will typically ask for layouts covering all of the file and may do so for either READ or READ/WRITE. This enables it to do subsequent I/O operations without the need to obtain layouts for specific byte ranges. At that time, the metadata server should verify permissions against the layout iomode, the file mode bits or ACLs, etc. As the client may be acting for multiple local users, it MUST authenticate and authorize the user by issuing respective OPEN and ACCESS calls to the metadata server, similar to having NFSv4 data delegations.

オブジェクトレイアウトタイプでは、セキュリティーのチェックはレイアウトの割り当て時に行われます。クライアントは通常、ファイル全体をカバーするレイアウトを、READまたはREAD/WRITEのいずれかで要求します。これにより、クライアントは、特定のバイト範囲のレイアウトを取得する必要なしに、後続のI/O操作を行うことができます。その時点で、メタデータサーバーは、レイアウトiomode、ファイルのモードビットやACLなどに照らしてアクセス許可を検証すべきです。クライアントは複数のローカルユーザーの代わりに動作している場合があるため、NFSv4のデータ委任を持つ場合と同様に、メタデータサーバーにそれぞれOPEN呼び出しとACCESS呼び出しを発行することで、ユーザーを認証および認可しなければなりません（MUST）。

Upon successful authorization, the client receives within the layout a set of object capabilities allowing it I/O access to the specified objects corresponding to the requested iomode. These capabilities are used to enforce access control and locking semantics at the storage devices. Whenever one of the following occurs on the metadata server, then the metadata server MUST change the capability version attribute on all objects comprising the file in order to invalidate any outstanding capabilities before committing to one of these changes:

認可に成功すると、クライアントはレイアウト内で、要求したiomodeに対応する指定されたオブジェクトへのI/Oアクセスを許可するオブジェクトケイパビリティーの集合を受け取ります。これらのケイパビリティーは、ストレージデバイスでアクセス制御とロックのセマンティクスを強制するために使用されます。メタデータサーバー上で次のいずれかが発生した場合、メタデータサーバーは、これらの変更のいずれかを確定する前に、未処理のケイパビリティーを無効化するために、ファイルを構成するすべてのオブジェクトのケイパビリティーバージョン属性を変更しなければなりません（MUST）。

  • the permissions on the object change,
  • a conflicting mandatory byte-range lock is granted, or
  • a layout is revoked and reassigned to another client.
  • オブジェクトに対するアクセス許可が変更された場合
  • 競合する強制バイト範囲ロックが付与された場合
  • レイアウトが取り消され、別のクライアントに再割り当てされた場合

When the metadata server wishes to fence off a client to a particular object, then it can use the above approach to invalidate the capability attribute on the given object. The client can be informed via the storage device that the capability has been rejected and is allowed to fetch a refreshed set of capabilities, i.e., reacquire the layout.

メタデータサーバーが特定のオブジェクトに対してクライアントをフェンスしたい場合、上記の方法を使用して、そのオブジェクトのケイパビリティー属性を無効化できます。クライアントは、ケイパビリティーが拒否されたことをストレージデバイスを介して知らされることができ、更新されたケイパビリティーの集合を取得すること、すなわちレイアウトを再取得することが許されます。

5. Summary

5. まとめ

In the three original layout types, the burden of enforcing the security of NFSv4.1 can fall to either the storage devices (files), the client (blocks), or the metadata server (objects). Such choices are conditioned by the native capabilities of the storage devices -- if a control protocol can be implemented, then the burden can be shifted primarily to the storage devices.

元の3つのレイアウトタイプでは、NFSv4.1のセキュリティーを強制する負担は、ストレージデバイス（ファイル）、クライアント（ブロック）、メタデータサーバー（オブジェクト）のいずれかにかかります。このような選択は、ストレージデバイスが本来持つ能力によって左右されます。制御プロトコルを実装できるのであれば、負担を主にストレージデバイスに移すことができます。

In the context of this document, we treat the control protocol as a set of requirements. As new layout types are published, the defining documents MUST address:

この文書の文脈では、制御プロトコルを要件の集合として扱います。新しいレイアウトタイプが発行される際には、それを定義する文書は次の事項を扱わなければなりません（MUST）。

  1. The fencing of clients after a layout is revoked.
  2. The security implications of the native capabilities of the storage devices with respect to the requirements of the NFSv4.1 security model.
  1. レイアウトが取り消された後のクライアントのフェンシング
  2. NFSv4.1のセキュリティーモデルの要件に関して、ストレージデバイスが本来持つ能力がセキュリティーに及ぼす影響

In addition, these defining documents need to make clear how other semantic requirements of NFSv4.1 (e.g., locking) are met in the context of the proposed layout type.

さらに、これらの定義する文書は、提案するレイアウトタイプの文脈で、NFSv4.1の他のセマンティクス上の要件（たとえばロック）がどのように満たされるのかを明確にする必要があります。

6. Security Considerations

6. セキュリティーに関する考慮事項

This section does not deal directly with security considerations for existing or new layout types. Instead, it provides a general framework for understating security-related issues within the pNFS framework. Specific security considerations will be addressed in the Security Considerations sections of documents specifying layout types. For example, in Section 3 of [RFC5663], the lack of finer-than-physical disk access control necessitates that the client is delegated the responsibility to enforce the access provided to them in the layout extent that they were granted by the metadata server.

このセクションは、既存または新規のレイアウトタイプに関するセキュリティーの考慮事項を直接扱うものではありません。その代わりに、pNFSフレームワーク内のセキュリティー関連の問題を理解するための一般的な枠組みを提供します。具体的なセキュリティーの考慮事項は、レイアウトタイプを規定する文書のセキュリティーに関する考慮事項のセクションで扱われます。たとえば、[RFC5663]のセクション3では、物理ディスクよりも細かい粒度のアクセス制御がないため、メタデータサーバーから付与されたレイアウトのエクステントで提供されたアクセスを強制する責任を、クライアントに委ねる必要があります。

The layout type specification must ensure that only data access consistent with the NFSV4.1 security model is allowed. It may do this directly, by providing that appropriate checks be performed at the time each access is performed. It may do it indirectly by allowing the client or the storage device to be responsible for making the appropriate checks. In the latter case, I/O access rights are reflected in layouts, and the layout type must provide a way to prevent inappropriate access due to permissions changes between the time a layout is granted and the time the access is performed.

レイアウトタイプの仕様は、NFSv4.1のセキュリティーモデルと整合するデータアクセスだけが許可されることを保証しなければなりません。これは、各アクセスが行われる時点で適切なチェックが実行されるよう定めることで、直接行うことができます。また、適切なチェックを行う責任をクライアントまたはストレージデバイスに持たせることで、間接的に行うこともできます。後者の場合、I/Oのアクセス権はレイアウトに反映され、レイアウトタイプは、レイアウトが付与された時点からアクセスが行われる時点までの間のアクセス許可の変更による不適切なアクセスを防ぐ方法を提供しなければなりません。

The metadata server MUST be able to fence off a client's access to the data file on a storage device. When it revokes the layout, the client's access MUST be terminated at the storage devices. The client has a subsequent opportunity to reacquire the layout and perform the security check in the context of the newly current access permissions.

メタデータサーバーは、ストレージデバイス上のデータファイルへのクライアントのアクセスをフェンスできなければなりません（MUST）。メタデータサーバーがレイアウトを取り消した場合、クライアントのアクセスはストレージデバイスで終了されなければなりません（MUST）。クライアントには、その後、レイアウトを再取得し、新たに現在のものとなったアクセス許可の文脈でセキュリティーチェックを受ける機会があります。
