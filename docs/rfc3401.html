RFC 3401

Dynamic Delegation Discovery System (DDDS) Part One: The Comprehensive DDDS

RFC 3401

動的委任発見システム（DDDS）パート1：DDDSの全体像

Abstract

概要

This document specifies the exact documents that make up the complete Dynamic Delegation Discovery System (DDDS). DDDS is an abstract algorithm for applying dynamically retrieved string transformation rules to an application-unique string.

この文書は、完全な動的委任発見システム（Dynamic Delegation Discovery System、DDDS）を構成する文書を厳密に規定します。DDDSは、動的に取得した文字列変換ルールをアプリケーション固有の文字列に適用するための抽象的なアルゴリズムです。

This document along with RFC 3402, RFC 3403 and RFC 3404 obsolete RFC 2168 and RFC 2915, as well as updates RFC 2276.

この文書は、RFC 3402、RFC 3403、RFC 3404とともに、RFC 2168とRFC 2915を廃止し、RFC 2276を更新します。

Status of This Memo

このメモのステータス

This memo provides information for the Internet community. It does not specify an Internet standard of any kind. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーに情報を提供するものです。いかなる種類のインターネット標準も規定するものではありません。このメモの配布は無制限です。

1. Intended Audience

1. 想定読者

This document and the documents that it references are intended for anyone attempting to implement or understand the generic DDDS algorithm, URI Resolution, ENUM telephone number to URI resolution, and the NAPTR DNS resource record. The reader is warned that reading one of the documents in this series without reading the others will probably lead to misunderstandings and interoperability problems.

この文書とこの文書が参照する文書は、汎用のDDDSアルゴリズム、URI解決、ENUMによる電話番号からURIへの解決、およびNAPTR DNSリソースレコードを実装または理解しようとするすべての人を対象としています。このシリーズの文書のうち1つだけを読み、他の文書を読まないと、おそらく誤解や相互運用性の問題につながることを読者に警告しておきます。

2. Introduction

2. はじめに

The Dynamic Delegation Discovery System is used to implement lazy binding of strings to data, in order to support dynamically configured delegation systems. The DDDS functions by mapping some unique string to data stored within a DDDS Database by iteratively applying string transformation rules until a terminal condition is reached. This document defines the entire DDDS by listing the documents that make up the complete specification at this time.

動的委任発見システム（Dynamic Delegation Discovery System）は、動的に構成される委任システムをサポートするために、文字列からデータへの遅延バインディングを実装するのに使用されます。DDDSは、終了条件に達するまで文字列変換ルールを繰り返し適用することによって、ある一意な文字列を、DDDSデータベース内に格納されたデータにマッピングするよう機能します。この文書は、現時点での完全な仕様を構成する文書を列挙することによって、DDDS全体を定義します。

This document along with RFC 3402, RFC 3403 and RFC 3404 obsoletes RFC 2168 [8] and RFC 2915 [6], as well as updates RFC 2276 [5]. This document will be updated and or obsoleted when changes are made to the DDDS specifications. Thus the reader is strongly encouraged to check the IETF RFC repository for any documents that obsoletes or updates this one.

この文書は、RFC 3402、RFC 3403、RFC 3404とともに、RFC 2168[8]とRFC 2915[6]を廃止し、RFC 2276[5]を更新します。この文書は、DDDSの仕様に変更が加えられたときに、更新または廃止されます。したがって、読者には、この文書を廃止または更新する文書がないか、IETFのRFCリポジトリーを確認することを強く勧めます。

3. The Algorithm

3. アルゴリズム

The DDDS algorithm is defined by RFC 3402 [1]. That document defines the following DDDS concepts:

DDDSアルゴリズムは、RFC 3402[1]で定義されています。その文書は、次のDDDSの概念を定義しています。

  • The basic DDDS vocabulary.
  • The algorithm.
  • The requirements on applications using the algorithm.
  • The requirements on databases that store DDDS rules.
  • DDDSの基本的な用語。
  • アルゴリズム。
  • アルゴリズムを使用するアプリケーションに対する要件。
  • DDDSルールを格納するデータベースに対する要件。

RFC 3402 is the actual DDDS Algorithm specification. But the specification by itself is useless without some additional document that defines how and why the algorithm is used. These documents are called Applications and do not actually make up part of the DDDS core specification. Applications require databases in which to store their Rules. These databases are called DDDS Databases and are usually specified in separate documents. But again, these Database specifications are not included in the DDDS core specification itself.

RFC 3402は、実際のDDDSアルゴリズムの仕様です。しかし、この仕様単体では、アルゴリズムをどのように、なぜ使用するのかを定義する追加の文書がなければ役に立ちません。これらの文書はアプリケーション（Application）と呼ばれ、実際にはDDDSのコア仕様の一部を構成するものではありません。アプリケーションには、そのルールを格納するデータベースが必要です。これらのデータベースはDDDSデータベース（DDDS Database）と呼ばれ、通常は別の文書で規定されます。ただし、これらのデータベースの仕様も、やはりDDDSのコア仕様自体には含まれません。

4. DDDS Applications

4. DDDSアプリケーション

No implementation can begin without an Application specification, as this is what provides the concrete instantiation details for the DDDS Algorithm. Without them the DDDS is nothing more than a general algorithm. Application documents define the following:

アプリケーションの仕様がなければ、実装を始めることはできません。DDDSアルゴリズムを具体的にインスタンス化するための詳細を提供するのは、アプリケーションの仕様だからです。アプリケーションの仕様がなければ、DDDSは一般的なアルゴリズムにすぎません。アプリケーションの文書は、次のものを定義します。

  • the Application Unique String (the thing the delegation rules act on).
  • the First Well Known Rule (the Rule that says where the process starts).
  • the list of valid Databases (you can't just use any Database).
  • the final expected output.
  • アプリケーション固有文字列（Application Unique String、委任ルールが作用する対象）。
  • 最初の既知ルール（First Well Known Rule、処理がどこから始まるかを示すルール）。
  • 有効なデータベースのリスト（任意のデータベースを使用できるわけではありません）。
  • 最終的に期待される出力。

Some sample Applications are documented in:

アプリケーションのいくつかの例は、次の文書に記述されています。

  • "E.164 number and DNS" (RFC 2916) [7]. This Application uses the DDDS to map a telephone number to service endpoints such as SIP or email.
  • "Dynamic Delegation Discovery System (DDDS) Part Four: The Uniform Resource Identifiers (URI) Resolution Application" (RFC 3404) [3]. This Application uses the DDDS to resolve any URI to a set of endpoints or 'resolvers' that can give additional information about the URI independent of its particular URI scheme.
  • 「E.164 number and DNS」（RFC 2916）[7]。このアプリケーションは、DDDSを使用して、電話番号をSIPや電子メールなどのサービスエンドポイントにマッピングします。
  • 「Dynamic Delegation Discovery System (DDDS) Part Four: The Uniform Resource Identifiers (URI) Resolution Application」（RFC 3404）[3]。このアプリケーションは、DDDSを使用して、任意のURIを、そのURIスキームに依存せずにURIに関する追加情報を提供できるエンドポイントまたは「リゾルバー（resolver）」の集合に解決します。

5. Currently Standardized Databases

5. 現在標準化されているデータベース

Any DDDS Application must use some type of DDDS Database. Database documents define the following:

DDDSアプリケーションは、何らかの種類のDDDSデータベースを使用しなければなりません。データベースの文書は、次のものを定義します。

  • the general spec for how the Database works.
  • formats for Keys.
  • formats for Rules.
  • Key lookup process.
  • rule insertion procedures.
  • collision avoidance measures.
  • データベースがどのように動作するかの一般的な仕様。
  • キーの形式。
  • ルールの形式。
  • キーの検索処理。
  • ルールの挿入手順。
  • 衝突回避の方策。

A Database cannot be used on its own; there must be at least one Application that uses it. Multiple Databases and Applications are defined, and some Databases will support multiple Applications. However, not every Application uses each Database, and vice versa. Thus, compliance is defined by the combination of a Database and Application specification.

データベースは単独では使用できません。それを使用するアプリケーションが少なくとも1つ存在しなければなりません。複数のデータベースとアプリケーションが定義されており、一部のデータベースは複数のアプリケーションをサポートします。ただし、すべてのアプリケーションがそれぞれのデータベースを使用するわけではなく、その逆も同様です。したがって、準拠は、データベースの仕様とアプリケーションの仕様の組み合わせによって定義されます。

One sample Database specification is documented in:

データベースの仕様の例の1つは、次の文書に記述されています。

  • "Dynamic Delegation Discovery System (DDDS) Part Three: The Domain Name System (DNS) Database" (RFC 3402) [1]. (This document is the official specification for the NAPTR DNS Resource Record.)
  • 「Dynamic Delegation Discovery System (DDDS) Part Three: The Domain Name System (DNS) Database」（RFC 3402）[1]。（この文書は、NAPTR DNSリソースレコードの公式な仕様です。）

6. Security Considerations

6. セキュリティーに関する考慮事項

Any known security issues that arise from the use of algorithms and databases must be specified in the respective specifications. They must be completely and fully described. It is not required that the database and algorithms be secure or that it be free from risks, but that the known risks be identified. Publication of a new database type or algorithm does require a security review, and the security considerations section should be subject to continuing evaluation. Additional security considerations should be addressed by publishing revised versions of the database and algorithm specifications.

アルゴリズムとデータベースの使用から生じる既知のセキュリティー上の問題は、それぞれの仕様で規定しなければなりません。それらは完全かつ十分に記述されなければなりません。データベースとアルゴリズムが安全であることやリスクがないことは要求されませんが、既知のリスクが明らかにされていることは要求されます。新しい種類のデータベースやアルゴリズムを公開するにはセキュリティーレビューが必要であり、セキュリティーに関する考慮事項のセクションは継続的な評価の対象とすべきです。追加のセキュリティーに関する考慮事項には、データベースとアルゴリズムの仕様の改訂版を公開することで対処すべきです。

7. IANA Considerations

7. IANAに関する考慮事項

While this document itself does not create any new requirements for the IANA, the documents in this series create many varied requirements. The IANA Considerations sections in those documents should be reviewed by the IANA to determine the complete set of new registries and requirements. Any new algorithms, databases or applications should take great care in what they require the IANA to do in the future.

この文書自体はIANAに対する新しい要件を作成しませんが、このシリーズの文書は多くのさまざまな要件を作成します。新しいレジストリーと要件の完全な集合を判断するために、IANAはそれらの文書のIANAに関する考慮事項のセクションをレビューすべきです。新しいアルゴリズム、データベース、アプリケーションは、将来IANAに何を要求するかについて、細心の注意を払うべきです。
