RFC 295

Report of the Protocol Workshop, 12 October, 1971

RFC 295

プロトコルワークショップの報告（1971年10月12日）

Introduction

はじめに

This is a report on the decisions reached at the protocol workshop held in conjunction with the Network Working Group meeting held in Cambridge from 10 to 14 October, 1971.

これは、1971年10月10日から14日にかけてケンブリッジで開かれたNetwork Working Groupの会合にあわせて開催されたプロトコルワークショップで決まった事項の報告です。

The workshop addressed itself to protocols of four types: IMP-Host, Host-Host, Initial Connection, and Process-Process.

ワークショップでは、IMP-ホスト、ホスト-ホスト、初期接続（Initial Connection）、プロセス-プロセスの4種類のプロトコルを取り上げました。

IMP-Host Protocol

IMP-ホストプロトコル

The idea of IMP provided status reports to be exchanged via new IMP-Host protocol messages was discussed and rejected because it was felt that the level of state information which could be reported was not sufficient to be worth the trouble of implementing this mechanism.

IMPが提供するステータス報告を新しいIMP-ホストプロトコルのメッセージでやり取りするという案について議論しましたが、報告できる状態情報の水準では、この仕組みを実装する手間に見合わないと考えられたため、却下されました。

Host-Host Protocol

ホスト-ホストプロトコル

The Host-Host Protocol was discussed and several problems were brought to light, among them were the following listed together with the group's recommendations.

ホスト-ホストプロトコルについて議論し、いくつかの問題が明らかになりました。そのうちのいくつかを、グループの推奨事項とともに次に挙げます。

The GVB - RET mechanism may prove useful sometime in the future so it will be retained though no one appears to be using it now, however spontaneous RET commands are explicitly prohibited.

GVB - RETの仕組みは、現在は誰も使っていないようですが、将来いつか役に立つかもしれないので残します。ただし、自発的なRETコマンドは明示的に禁止します。

The ECO - ERP commands are useful and should be supported, but spontaneous ERP commands are explicitly prohibited. A further restriction is that a second ECO will not be sent until the first ECO has been answered. Note that any of the following may be an answer to an ECO: ERP, RST, "Destination dead", or "Incomplete Transmission".

ECO - ERPコマンドは有用であり、サポートすべきですが、自発的なERPコマンドは明示的に禁止します。さらなる制限として、最初のECOに応答があるまで2つ目のECOは送信しません。ECOへの応答は、ERP、RST、「Destination dead」、「Incomplete Transmission」のいずれでもよいことに注意してください。

The RST - RRP commands are useful, but the proper use of these commands for determining the status of host software is still open for discussion (please direct comments to Jon Postel), however spontaneous RRP commands are explicitly prohibited.

RST - RRPコマンドは有用ですが、ホストのソフトウェアのステータスを判断するためにこれらのコマンドをどう使うのが適切かは、まだ議論の余地があります（意見はJon Postelまでお寄せください）。ただし、自発的なRRPコマンドは明示的に禁止します。

The problem of unmatched CLS commands are discussed and four "solutions" were proposed:

対応のないCLSコマンドの問題について議論し、4つの「解決策」が提案されました。

  • Hold forever
  • Send a RST and clear the entry
  • Clear the entry and possibly mess up a future connection
  • Assign socket numbers in a sequential fashion to reduce the possibility of confusion and clear the entry.
  • いつまでも保持する
  • RSTを送信してエントリーを消去する
  • エントリーを消去し、将来のコネクションを混乱させる可能性を受け入れる
  • 混乱の可能性を減らすためにソケット番号を順番に割り当て、エントリーを消去する

Note that the first two suggestions follow the protocol while the last two do not.

最初の2つの案はプロトコルに従っていますが、最後の2つは従っていないことに注意してください。

The idea of flow control on the control link was suggested. A Request for Comments is to be prepared exploring this idea more fully.

制御リンクでのフロー制御という案が出されました。この案をより詳しく検討するRequest for Commentsを用意する予定です。

The usefulness of the ERR command is compromised if the receiver mearly throws it out. Thus ERR's are to be logged, if at all possible, and checked out with the sending site.

受信側がERRコマンドを単に捨ててしまうと、ERRコマンドの有用性が損なわれます。そのため、ERRは可能な限り記録し、送信元のサイトと確認するものとします。

The NCP document should make clear the implications of queueing or not queueing STR & RTS commands.

NCPの文書では、STRとRTSのコマンドをキューに入れる場合と入れない場合の影響を明確にすべきです。

Initial Connection Protocol

初期接続プロトコル

The Initial Connection Protocol (ICP) was discussed and found to be satisfactory however the following points were stressed:

初期接続プロトコル（Initial Connection Protocol、ICP）について議論し、満足できるものだと判断しましたが、次の点を強調しました。

The socket number sent by the logger (S) must be in agreement with the socket numbers used in the STR & RTS sent by the logger.

ロガーが送信するソケット番号（S）は、ロガーが送信するSTRとRTSで使うソケット番号と一致していなければなりません。

The implications of queueing or not queueing of RTS & STR commands should be made clear in the ICP document. This is particularly important if the user chooses the "listen" option.

RTSとSTRのコマンドをキューに入れる場合と入れない場合の影響を、ICPの文書で明確にすべきです。これは、ユーザーが「listen」オプションを選んだ場合に特に重要です。

Telnet Protocol

Telnetプロトコル

The Telnet committee has been reactivated to consider the following problems:

Telnet委員会を再開し、次の問題を検討することになりました。

  • Clarification of the terminology half duplex, full duplex, character mode, line mode, ASCII, and echoing.
  • Clarification of the end of line convention. Especially to answer the question "Should there be a special end-of-line character?"
  • Clarification of the conditions for leaving Hide-your-input mode.
  • Clarification of the operation of Break and Synch.
  • Specification of a server-to-user Synch.
  • Clarification of the definition of the Network Virtual Terminal.
  • Preparation of a new document defining the Telnet protocol with the above improvements.
  • 半二重、全二重、文字モード、行モード、ASCII、エコーといった用語の明確化
  • 行末の規約の明確化。特に「特別な行末文字を設けるべきか？」という問いに答えること
  • Hide-your-inputモードを抜ける条件の明確化
  • BreakとSynchの動作の明確化
  • サーバーからユーザーへのSynchの規定
  • ネットワーク仮想端末（Network Virtual Terminal）の定義の明確化
  • 上記の改善を加えてTelnetプロトコルを定義する新しい文書の作成

The protocol workshop did agree that:

プロトコルワークショップでは、次のことに合意しました。

  • It is the servers option for disconnection to imply logout or not.
  • It is the servers option for logout to imply disconnection or not.
  • Extra characters used locally to fill the time for format effectors to take effect should not be sent over the network
  • Synch means to examine the data stream from the current point to a data mark (x'80'). If any break type characters (e.g. etx, sub, Break) are found they are to have their normal effect.
  • Upper and lower case are to be available to all Telnet users.
  • 切断がログアウトを意味するかどうかは、サーバーの選択に任せます。
  • ログアウトが切断を意味するかどうかは、サーバーの選択に任せます。
  • 書式制御文字（format effector）が効果を発揮するまでの時間を埋めるためにローカルで使う余分な文字は、ネットワーク上に送信すべきではありません。
  • Synchとは、データストリームを現在の位置からデータマーク（x'80'）まで調べることを意味します。ブレーク系の文字（たとえばetx、sub、Break）が見つかった場合は、それらは通常の効果を持つものとします。
  • すべてのTelnetユーザーが大文字と小文字を使えるようにします。

Data and File Transfer Protocol

データ・ファイル転送プロトコル

The Data and File Transfer Committee will report separately.

データ・ファイル転送委員会（Data and File Transfer Committee）は別途報告します。
