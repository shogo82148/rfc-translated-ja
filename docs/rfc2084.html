RFC 2084

Considerations for Web Transaction Security

RFC 2084

Webトランザクションセキュリティーに関する考慮事項

Abstract

概要

This document specifies the requirements for the provision of security services to the HyperText Transport Protocol. These services include confidentiality, integrity, user authentication, and authentication of servers/services, including proxied or gatewayed services. Such services may be provided as extensions to HTTP, or as an encapsulating security protocol. Secondary requirements include ease of integration and support of multiple mechanisms for providing these services.

この文書は、HyperText Transport Protocolにセキュリティーサービスを提供するための要件を規定します。これらのサービスには、機密性、完全性、ユーザー認証、そしてプロキシーやゲートウェイを経由するサービスを含むサーバー／サービスの認証が含まれます。このようなサービスは、HTTPの拡張として、またはカプセル化するセキュリティープロトコルとして提供できます。副次的な要件には、統合の容易さと、これらのサービスを提供するための複数のメカニズムのサポートが含まれます。

Status of This Memo

このメモのステータス

This memo provides information for the Internet community. This memo does not specify an Internet standard of any kind. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーに情報を提供するものです。このメモは、いかなる種類のインターネット標準も規定するものではありません。このメモの配布は無制限です。

1. Introduction

1. はじめに

The use of the HyperText Transport Protocol [1] to provide specialized or commercial services and personal or private data necessitates the development of secure versions that include privacy and authentication services. Such services may be provided as extensions to HTTP, or as encapsulating security protocols; for the purposes of this document, all such enhancements will be referred to as WTS.

特化したサービスや商用サービス、個人的なデータや私的なデータを提供するためにHyperText Transport Protocol [1]を使うには、プライバシーと認証のサービスを備えた安全なバージョンを開発する必要があります。このようなサービスは、HTTPの拡張として、またはカプセル化するセキュリティープロトコルとして提供できます。この文書では、そのような拡張をすべてWTSと呼びます。

In this document, we specify the requirements for WTS, with the intent of codifying perceived Internet-wide needs, along with existing practice, in a way that aids in the evaluation and development of such protocols.

この文書では、インターネット全体で認識されているニーズを既存の慣行とともに体系化し、そのようなプロトコルの評価と開発に役立てることを意図して、WTSの要件を規定します。

WTS is an enhancement to an object transport protocol. As such, it does not provide independent certification of documents or other data objects outside of the scope of the transfer of said objects. In addition, security at the WTS layer is independent of and orthogonal to security services provided at underlying network layers. It is envisioned that WTS may coexist in a single transaction with such mechanisms, each providing security services at the appropriate level, with at worst some redundancy of service.

WTSは、オブジェクト転送プロトコルの拡張です。そのため、WTSは、文書やその他のデータオブジェクトについて、それらのオブジェクトの転送の範囲外で独立した証明を提供するものではありません。また、WTS層のセキュリティーは、下位のネットワーク層で提供されるセキュリティーサービスとは独立しており、直交しています。WTSは、そのようなメカニズムと1つのトランザクションの中で共存し、それぞれが適切なレベルでセキュリティーサービスを提供し、最悪の場合でもサービスが多少重複するだけになると想定しています。

1.1. Terminology

1.1. 用語

This following terms have specific meaning in the context of this document. The HTTP specification [1] defines additional useful terms.

次の用語は、この文書の文脈で特定の意味を持ちます。HTTPの仕様[1]では、その他の有用な用語が定義されています。

Transaction:
A complete HTTP action, consisting of a request from the client and a response from the server.
Gatewayed Service:
A service accessed, via HTTP or an alternate protocol, by the HTTP server on behalf of the client.
Mechanism:
An specific implementation of a protocol or related subset of features of a protocol.
トランザクション（Transaction）：
クライアントからのリクエストとサーバーからのレスポンスからなる、完全なHTTPアクション。
ゲートウェイ経由のサービス（Gatewayed Service）：
HTTPサーバーがクライアントに代わって、HTTPまたは別のプロトコルを介してアクセスするサービス。
メカニズム（Mechanism）：
プロトコル、またはプロトコルの機能の関連するサブセットの特定の実装。

2. General Requirements

2. 一般的な要件

WTS must define the following services. These services must be provided independently of each other and support the needs of proxies and intermediaries

WTSは次のサービスを定義しなければなりません。これらのサービスは互いに独立して提供され、プロキシーや中継者のニーズをサポートしなければなりません。

  • Confidentiality of the HTTP request and/or response.
  • Data origin authentication and data integrity of the HTTP request and/or response.
  • Non-repudiability of origin for the request and/or response.
  • Transmission freshness of request and/or response.
  • Ease of integration with other features of HTTP.
  • Support of multiple mechanisms for the above services.
  • HTTPリクエストおよび／またはレスポンスの機密性。
  • HTTPリクエストおよび／またはレスポンスのデータ発信元認証とデータ完全性。
  • リクエストおよび／またはレスポンスの発信元の否認防止。
  • リクエストおよび／またはレスポンスの送信の新しさ（freshness）。
  • HTTPの他の機能との統合の容易さ。
  • 上記のサービスのための複数のメカニズムのサポート。

3. Confidentiality

3. 機密性

WTS must be able to provide confidentiality for both requests and responses. Note: because the identity of the object being requested is potentially sensitive, the URI of the request should be confidential; this is particularly critical in the common case of form data or other user input being passed in the URI.

WTSは、リクエストとレスポンスの両方に機密性を提供できなければなりません。注：リクエストされているオブジェクトの識別情報は機密性が高い可能性があるため、リクエストのURIは秘匿されるべきです。これは、フォームデータやその他のユーザー入力がURIで渡されるというよくある場合には特に重要です。

4. Service Authentication

4. サービス認証

WTS should support the authentication of gatewayed services to the client.

WTSは、クライアントに対するゲートウェイ経由のサービスの認証をサポートすべきです。

WTS should support the authentication of the origin HTTP server or gatewayed services regardless of intermediary proxy or caching servers.

WTSは、中間のプロキシーサーバーやキャッシュサーバーの有無にかかわらず、オリジンHTTPサーバーやゲートウェイ経由のサービスの認証をサポートすべきです。

To allow user privacy, WTS must support service authentication with user anonymity.

ユーザーのプライバシーを可能にするため、WTSはユーザーの匿名性を保ったサービス認証をサポートしなければなりません。

Because the identity of the object being requested is potentially sensitive, service authentication should occur before any part of the request, including the URI of the requested object, is passed. In cases where the authentication process depends on the URI (or other header data) of the request, such as gatewayed services, the minimum necessary information to identify the entity to be authenticated should be passed.

リクエストされているオブジェクトの識別情報は機密性が高い可能性があるため、サービス認証は、リクエストされたオブジェクトのURIを含め、リクエストのどの部分が渡されるよりも前に行われるべきです。ゲートウェイ経由のサービスのように、認証処理がリクエストのURI（またはその他のヘッダーデータ）に依存する場合は、認証される主体を識別するのに必要最小限の情報を渡すべきです。

5. User Authentication

5. ユーザー認証

WTS must support the authentication of the client to the server.

WTSは、サーバーに対するクライアントの認証をサポートしなければなりません。

WTS should support the authentication of the client to gatewayed services.

WTSは、ゲートウェイ経由のサービスに対するクライアントの認証をサポートすべきです。

WTS should support the authentication of the client to the origin HTTP server regardless of intermediary proxy servers.

WTSは、中間のプロキシーサーバーの有無にかかわらず、オリジンHTTPサーバーに対するクライアントの認証をサポートすべきです。

6. Integrity

6. 完全性

WTS must provide assurance of the integrity of the HTTP transaction, including the HTTP headers and data objects of both client requests and server responses.

WTSは、クライアントのリクエストとサーバーのレスポンスの両方のHTTPヘッダーとデータオブジェクトを含め、HTTPトランザクションの完全性を保証しなければなりません。

7. Integration

7. 統合

In order to support integration with current and future versions of HTTP, and to provide extendibility and independence of development, the secure services provided by WTS must be orthogonal to and independent of other services provided by HTTP.

HTTPの現在および将来のバージョンとの統合をサポートし、拡張性と開発の独立性を提供するために、WTSが提供するセキュリティーサービスは、HTTPが提供する他のサービスと直交し、独立していなければなりません。

In accordance with the layered model of network protocols, WTS must be:

ネットワークプロトコルの階層モデルに従い、WTSは次のようでなければなりません。

  • independent of the content or nature of data objects being transported although special attention to reference integrity of hyperlinked objects may be appropriate
  • implementable over a variety of connection schemes and underlying transport protocols
  • 転送されるデータオブジェクトの内容や性質から独立していること。ただし、ハイパーリンクされたオブジェクトの参照の完全性には特別な注意を払うことが適切な場合があります。
  • さまざまな接続方式と下位のトランスポートプロトコルの上で実装可能であること。

8. Multiple Mechanisms

8. 複数のメカニズム

WTS must be compatible with multiple mechanisms for authentication and encryption. Support for multiple mechanisms is required for a number of reasons:

WTSは、認証と暗号化のための複数のメカニズムと互換性がなければなりません。複数のメカニズムのサポートは、次のようないくつかの理由から必要です。

  • Accommodation of variations in site policies, including those due to external restrictions on the availability of cryptographic technologies.
  • Support for a variety of applications and gatewayed services.
  • Support for parallel implementations within and across administrative domains.
  • Accomodation of application-specific performance/security tradeoffs.
  • 暗号技術の利用可能性に対する外部からの制限によるものを含め、サイトのポリシーの違いに対応するため。
  • さまざまなアプリケーションとゲートウェイ経由のサービスをサポートするため。
  • 管理ドメイン内および管理ドメイン間での並行した実装をサポートするため。
  • アプリケーション固有の性能とセキュリティーのトレードオフに対応するため。

To allow interoperability across domains, and to support the transition to new/upgraded mechanisms, WTS should provide negotiation of authentication and encryption mechanisms.

ドメインをまたいだ相互運用性を可能にし、新しい／アップグレードされたメカニズムへの移行をサポートするために、WTSは認証と暗号化のメカニズムのネゴシエーションを提供すべきです。
