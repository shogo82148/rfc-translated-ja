RFC 451

Tentative Proposal for a Unified User Level Protocol

RFC 451

統一ユーザーレベルプロトコルの暫定的な提案

Abstract

概要

Now that proposals for expansions to the Telnet Protocol are in vogue again (RFC's 426 and 435, for example), I'd like to promote some discussion of a particular favorite of my own. Please note that this is presented as a tentative proposal: it's an attempt to consider the desirability of a new approach, not a rigorous specification. To begin somewhat obliquely, for some time I've felt that we (the NWG) have fallen into a trap in regard to the Initial Connection Protocol. The point is that even though the ICP gives us the ability to define a "family" of ICPlets by varying the contact socket, there's no compelling reason why we should do so. That we have done so in the FTP and RJEP I view as unfortunate--but also undesirable and unnecessary.

Telnetプロトコルの拡張の提案がふたたび流行している（たとえば、RFC 426と435）ので、私自身が特に気に入っている案について議論を促したいと思います。これは暫定的な提案として示すものであることに注意してください。厳密な仕様ではなく、新しいアプローチが望ましいかどうかを検討する試みです。少し遠回りに始めると、私はしばらく前から、私たち（NWG）は初期接続プロトコル（Initial Connection Protocol）に関して罠に陥っていると感じていました。要点は、ICPによってコンタクトソケットを変えることでICPの小さな変種（ICPlet）の「ファミリー」を定義できるとしても、そうしなければならない説得力のある理由はないということです。FTPとRJEPでそうしてしまったことは不幸なことであり、さらに望ましくなく、不要でもあったと私は考えています。

To take the "undesirable" aspects first, consider the following: If we continue to define a new contact socket for every new "user level" protocol we come up with, we'll continue to need another new mechanism (process, procedure, or patch) to respond to requests for connection for each new protocol. By Occam's Razor (or the principle of economy of mechanism, if you prefer), this is a bad thing. Irrespective of the relative difficulty of implementing such mechanisms on the various Hosts, to implement them at all leads to a kind of conceptual clutter. Further, a different kind of confusion is introduced by the notion which some of our number seem to be entertaining, that the "later" user level protocols such as FTP are somehow still another level of abstraction up from Telnet. So it seems to me that we could spare ourselves a lot of bother, both practical and theoretical, if we could avoid spawning contact sockets needlessly.

まず「望ましくない」という面から取り上げて、次のことを考えてみてください。私たちが考え出す新しい「ユーザーレベル」のプロトコルのたびに新しいコンタクトソケットを定義し続けると、新しいプロトコルごとに接続要求に応答するための別の新しいメカニズム（プロセス、プロシージャー、パッチ）が必要になり続けます。オッカムの剃刀（お好みならメカニズムの経済性の原則）によれば、これは悪いことです。さまざまなホストでそのようなメカニズムを実装するのが相対的にどれほど難しいかにかかわらず、それらを実装すること自体が、ある種の概念的な散らかりをもたらします。さらに、FTPのような「後発の」ユーザーレベルのプロトコルは、Telnetからさらにもう1段上の抽象化レベルにあるのだという、私たちの何人かが抱いているらしい考えによって、別の種類の混乱が持ち込まれています。ですから、コンタクトソケットをむやみに増やすことを避けられれば、実際的にも理論的にも多くの面倒を省けるように私には思えます。

Turning to the "unnecessary" aspects, I think that even if the case against the current approach isn't completely convincing the case for a particular alternative might be. So to show that the multiple contact socket ICP is unnecessary, I'll try to show that what I call the "unified user level protocol" (UULP) is better. The first thing to notice is that all the "later" protocols "speak Telnet". This is sensible: Telnet works, by and large. Why not make use of it? Right. But why not make even more use of it? In view of the fact that FTP, RJEP, and even the initiating part of the Network Graphics Protocol, are really just ways of letting a user say to a Server "I don't know what you call it on your system, but please perform the whatever function (push or pull a file, start or stop a batch job, funnel some of my output through the Network Virtual Graphics Terminal module) for me now, why not simply put hooks in Telnet to indicate that a Network Generic Function is wanted instead of a Host-specific one at a given point in time? Then everybody can come in through Telnet in ways that are already known (and usually debugged and optimized) and fan out to other services through a single mechanism, where that single mechanism can be whatever is most appropriate to a particular Host. This view has the additional virtue of keeping the Host "Answering Service"-equivalent processes out of the act when new protocols come along -- where by Answering Service, I mean that process which manages logins in general for a given Host. This process is, of course, a particularly sensitive one on those systems which worry about accounting and security.

「不要」という面に目を向けると、現在のアプローチに反対する論拠が完全には説得力を持たないとしても、特定の代替案を支持する論拠には説得力があるかもしれないと考えます。そこで、複数のコンタクトソケットを使うICPが不要であることを示すために、私が「統一ユーザーレベルプロトコル（unified user level protocol、UULP）」と呼ぶものの方が優れていることを示してみます。最初に気づくべきことは、「後発の」プロトコルはすべて「Telnetを話す」ということです。これは理にかなっています。Telnetは概してうまく動作しています。それを利用しない手はありません。そのとおりです。では、なぜもっと活用しないのでしょうか。FTP、RJEP、さらにはネットワークグラフィックスプロトコル（Network Graphics Protocol）の開始部分でさえ、実際には、ユーザーがサーバーに「あなたのシステムでそれを何と呼んでいるのかわからないが、とにかくその機能（ファイルの送信や取得、バッチジョブの開始や停止、私の出力の一部をネットワーク仮想グラフィックス端末（Network Virtual Graphics Terminal）モジュールに流し込むこと）を今すぐ私のために実行してほしい」と伝えるための方法にすぎないことを考えると、ある時点でホスト固有の機能ではなくネットワーク汎用機能（Network Generic Function）が求められていることを示すフックを、単純にTelnetに組み込めばよいのではないでしょうか。そうすれば、誰もがすでに知られている（そして通常はデバッグと最適化が済んでいる）方法でTelnetを通って入り、単一のメカニズムを通じてほかのサービスに広がっていけます。その単一のメカニズムは、特定のホストに最も適したものであればどのようなものでもかまいません。この見方には、新しいプロトコルが登場したときに、ホストの「応答サービス（Answering Service）」に相当するプロセスを関与させずに済むという利点もあります。ここで応答サービスとは、あるホストでのログイン全般を管理するプロセスのことです。もちろん、課金やセキュリティーを気にするシステムでは、このプロセスは特に繊細なものです。

That's all probably a bit vague. Perhaps some idea of how I think the UULP would work will cast some light on what I think it is. What's needed is a way of letting the Server know that it's being given a generic command (I decline to call it a Network Virtual command, but I'm afraid that might be what I mean) like "STOR" or "RETR" rather than a local command like "who" or "sys". What could be simpler than defining a Telnet Control Code (TCC) for "Network Generic Function Follows"? So if the Server Telnet receives a command line beginning with the NGF TCC (say, 277 octal), it just feeds the line to the appropriate process or procedure (depending on the structure of its operating system). This approach also offers a handy way of communicating back the fact that a particular protocol or piece thereof isn't available: define a TCC for "Unimplemented Generic Function". This feels a lot cleaner than having a close on socket 3 mean anything from "no FTP Server exists here" to "the FTP Server happens to be busy."

ここまでの話はおそらく少し曖昧でしょう。UULPがどのように動作すると私が考えているかを少し示せば、それが何であると私が考えているかが少しはわかるかもしれません。必要なのは、「who」や「sys」のようなローカルコマンドではなく、「STOR」や「RETR」のような汎用コマンド（これをネットワーク仮想コマンドと呼ぶのは控えますが、私が言いたいのはそういうことかもしれません）が与えられていることを、サーバーに知らせる方法です。「ネットワーク汎用機能が続く（Network Generic Function Follows）」を表すTelnet制御コード（Telnet Control Code、TCC）を定義するより簡単なことがあるでしょうか。そうすれば、サーバーTelnetは、NGF TCC（たとえば8進数の277）で始まるコマンド行を受信したら、その行を（オペレーティングシステムの構造に応じて）適切なプロセスやプロシージャーに渡すだけです。このアプローチでは、特定のプロトコルやその一部が利用できないことを返す便利な方法も得られます。「未実装の汎用機能（Unimplemented Generic Function）」を表すTCCを定義すればよいのです。これは、ソケット3でのクローズが「ここにはFTPサーバーが存在しない」から「FTPサーバーがたまたまビジーである」までのあらゆる意味を持つよりも、ずっとすっきりしているように感じます。

Notice that the UULP automatically provides the answer to such objections as the one Braden raises in RFC 430, that "there is no mechanism within the FTP for _changing_ a password. A user shouldn't have to use a different protocol ... to merely change his password". With the UULP, any system which has a password changing ability would have it available for all user level protocols because all of its abilities are made available by the generic login. This seems clearly superior to having to retrofit afterthought after afterthought to the various user level protocols as we come to realize that life is more convenient when we get away from the view that each protocol lives in its own island universe. I understand that one of the main motivations for going the multiple contact socket route was to avoid syntactic (and semantic) conflicts between the protocol and the particular Host's "normal" command processor; however, locking ourselves in to special command processors exclusively is awfully procrustean. So instead of cutting off the limbs to fit the bed, why not use the UULP to expand the bed.

UULPが、BradenがRFC 430で提起した「FTPにはパスワードを_変更する_メカニズムがない。ユーザーが単にパスワードを変更するためだけに別のプロトコル…を使わなければならないのはおかしい」といった異議への答えを自動的に提供することに注目してください。UULPでは、パスワードを変更する機能を持つシステムなら、その機能をすべてのユーザーレベルのプロトコルで利用できるようになります。システムのすべての機能が汎用のログインによって利用可能になるからです。各プロトコルがそれぞれ独立した孤立宇宙に存在しているという見方から離れたほうが楽になると気づくたびに、さまざまなユーザーレベルのプロトコルに後知恵を次々と付け足していかなければならないよりも、これは明らかに優れているように思えます。複数のコンタクトソケットという道を選んだ主な動機の1つは、プロトコルと特定のホストの「通常の」コマンドプロセッサーとの間の構文上（および意味上）の衝突を避けることだったと理解しています。しかし、特別なコマンドプロセッサーだけに自らを閉じ込めるのは、ひどくプロクルステス的です。ですから、ベッドに合わせて手足を切り落とすのではなく、UULPを使ってベッドを広げてはどうでしょうか。

Although this is a tentative proposal and not meant to be a detailed design spec, one elaboration suggests itself which might make the general idea more attractive: For ease of implementation on some systems, it would probably be a good idea to define additional TCC's for "Begin User Protocol". That is, the user side starts the FTP by sending the "Begin FTP" Telnet Control Code, waits for the Server to send either the same code or the one for "Unimplemented Generic Function", and then proceeds (or not) to send STOR's and RETR's and the like. (It could also follow the "I will"/"I won't" style discipline of RFC 435 if we like.) Probably each line is preceded by the Network Generic Function TCC so that systems which don't pass input off to some other process can still distinguish between input to the system command processor and input to the procedure(s) which perform(s) the protocol in question, although perhaps it would be preferable to have an "End Protocol" TCC.

これは暫定的な提案であり、詳細な設計仕様を意図したものではありませんが、全体的な考えをより魅力的にするかもしれない詳細化が1つ思い浮かびます。システムによっては実装を容易にするために、「ユーザープロトコル開始（Begin User Protocol）」を表す追加のTCCを定義するのがおそらくよいでしょう。つまり、ユーザー側は「FTP開始（Begin FTP）」Telnet制御コードを送信してFTPを開始し、サーバーが同じコードか「未実装の汎用機能」のコードを送信するのを待ち、それから（場合によっては）STORやRETRなどを送信していきます。（望むなら、RFC 435の「I will」／「I won't」形式の規律に従うこともできます。）入力をほかのプロセスに渡さないシステムでも、システムのコマンドプロセッサーへの入力と、該当するプロトコルを実行するプロシージャーへの入力とを区別できるように、おそらく各行の前にネットワーク汎用機能TCCを置くことになるでしょう。もっとも、「プロトコル終了（End Protocol）」TCCを用意するほうが望ましいかもしれません。

Now, I'm the first to admit that what makes sense to me, on my system, may not make sense on somebody else's. But it does seem plausible to me that the unified user level protocol I've sketched here ought to be no harder to implement than the multiple contact socket (MCS) ICP is. And the advantages of the UULP over the MCS ICP in terms of ease of extension and (at least in my mind, if not in this paper) clarity make it seem worthwhile to consider further. So rather than try to refine it here, let me simply ask for comments both on the general notion and on the necessary iteration of the design from sketch to spec. (The Multics scenario in ICCC booklet shows how to get "mail" to me, for those who don't feel like RFCing or phoning.)

さて、私のシステムで私にとって理にかなっていることが、ほかの人のシステムでは理にかなっていないかもしれないことは、真っ先に認めます。しかし、ここで概略を示した統一ユーザーレベルプロトコルは、複数コンタクトソケット（multiple contact socket、MCS）ICPと比べて実装が難しくないはずだというのは、もっともらしく思えます。そして、拡張の容易さと（この論文ではともかく、少なくとも私の頭の中では）明快さの点で、UULPにはMCS ICPに対する利点があるので、さらに検討する価値があるように思えます。そこで、ここで練り上げようとするのではなく、全体的な考え方と、概略から仕様へと設計を繰り返し改善していく必要があることの両方について、単にコメントをお願いしたいと思います。（RFCを書いたり電話をしたりする気にならない人のために、ICCCの小冊子にあるMulticsのシナリオに、私に「メール」を送る方法が示されています。）
