RFC 17

Some Questions Re: HOST-IMP Protocol

RFC 17

HOST-IMPプロトコルに関するいくつかの質問

Abstract

概要

  1. Automatic deletion of links, as indicated in BBN 1822, page 11, seems bad:

    1. Link use may be dependent upon human use of a time share terminal - indefinite time between messages.

    2. Program using link may be slow due to:

      1. Busy HOST (many jobs)
      2. Much local I/O and/or CPU time between messages - is it that, if a HOST's user fails to use a link for 15 seconds, the HOST network program must generate a dummy message merely to keep the link open?
  2. Steve Crocker, HOST Software, 1969 Apr 7, asks on page 2: "Can a HOST, as opposed to its IMP, control RFNM's?" BBN, Report No. 1837, 1969 Jul, says on page 2: "The principal function of the (IMP) program...includes...generating of RFNM's..." What if an IMP generates an RFNM and then discovers it cannot, for some reason, complete timely delivery of the last received message to its HOST? This seems especially pressing since I don't recall seeing anywhere an IMP constraint upon HOSTs that they must accept incoming messages within some specified maximum time.
  3. A HOST has to be prepared to repeat transmissions of a message into network (see, e.g., Page 17, BBN 1822) therefore why the special discardable NOP message (Page 12, BBN 1822).
  4. "Arbitrary delays," middle paragraph, page 23, BBN 1822, seems inconsistent with automatic link deletion questioned in 1 above. Normally the times involved differ by many orders of magnitude but a high priority non-network HOST responsibility could delay next bit for a long time.

  1. BBN 1822の11ページに示されているリンクの自動削除は、よくないように思われます。

    1. リンクの使用は、人間がタイムシェアリング端末を使用することに依存している場合があります。つまり、メッセージ間の時間は不定です。

    2. リンクを使用するプログラムは、次の理由で遅くなる場合があります。

      1. HOSTが混んでいる（多数のジョブがある）
      2. メッセージ間に多くのローカルI/OやCPU時間を要する。HOSTのユーザーが15秒間リンクを使用しなかった場合、HOSTのネットワークプログラムは、リンクを開いたままにしておくためだけにダミーのメッセージを生成しなければならないということでしょうか？
  2. Steve Crockerは、HOST Software（1969年4月7日）の2ページで「IMPではなくHOSTがRFNMを制御できるか？」と問うています。BBNのReport No. 1837（1969年7月）は、2ページで「（IMP）プログラムの主な機能には、……RFNMの生成……が含まれる」と述べています。IMPがRFNMを生成した後で、何らかの理由により、最後に受信したメッセージを自身のHOSTへ適時に配送し終えられないことがわかったらどうなるのでしょうか？HOSTは受信メッセージを規定の最大時間内に受け付けなければならないという、IMPがHOSTに課す制約をどこかで見た覚えがないので、これは特に差し迫った問題のように思われます。
  3. HOSTは、ネットワークへのメッセージの送信を繰り返す準備をしておかなければなりません（たとえば、BBN 1822の17ページを参照）。それなのに、なぜ破棄可能な特別なNOPメッセージ（BBN 1822の12ページ）があるのでしょうか。
  4. BBN 1822の23ページの中ほどの段落にある「任意の遅延（Arbitrary delays）」は、上記1で疑問を呈したリンクの自動削除と矛盾するように思われます。通常、関係する時間は何桁も異なりますが、ネットワーク以外の優先度の高いHOSTの責務によって、次のビットが長時間遅れる可能性があります。

Bolt Beranek and Newman Inc

Network Working Group
Request for Comments: 17a
R. Kahn
Bolt Beranek and Newman Inc
1969年8月

THE FOLLOWING COMMENTS ARE IN RESPONSE TO JOHN KREZNAR'S QUESTIONS WHICH WERE RAISED IN NWG:- 17

以下のコメントは、NWG:- 17で提起されたJOHN KREZNARの質問に対する回答です。

The deletion of a link entry from an IMP's link table will, in general, have no effect upon a Host transmission (or reception) at that IMP's site. Let us distinguish between non-use of a link in-between messages and non-use of a link due to Host program delays in the middle of transmitting or receiving a message. When the Host transmits a message on a link for which an entry is not in the link table, one will simply be inserted there. There is no need for "dummy" Host messages to keep a link "open" since a link is effectively always open. Only if the link table becomes full immediately after an entry is deleted (a situation we do not expect to occur) is there a possibility of resulting delay.

IMPのリンクテーブルからリンクのエントリーを削除しても、一般に、そのIMPのサイトにおけるHostの送信（または受信）には何の影響もありません。メッセージとメッセージの間でリンクが使われていないことと、メッセージの送信中または受信中にHostのプログラムが遅れたためにリンクが使われていないことを区別しましょう。Hostが、リンクテーブルにエントリーがないリンクでメッセージを送信すると、そこにエントリーが単に挿入されます。リンクは実質的に常に開いているので、リンクを「開いた」ままにしておくための「ダミー」のHostメッセージは必要ありません。エントリーが削除された直後にリンクテーブルが満杯になった場合（これは起こらないと想定している状況です）にだけ、結果として遅延が生じる可能性があります。

Arbitrary delays introduced by Host programs are also not inconsistent with the link entry deletion procedure. A link is blocked when the first access of the link table is made during transmission from the source IMP and is unblocked when the RFNM returns. Only non-blocked transmit link entries are deleted after 30 seconds of disuse. The statement on page 23 referencing arbitrary delays was only intended to have hardware implications insofar as the Host/IMP interface is designed to transfer bits asynchronously between the Host and the IMP.

Hostのプログラムによって生じる任意の遅延も、リンクのエントリーの削除手順と矛盾しません。リンクは、送信元IMPからの送信中にリンクテーブルに最初にアクセスしたときにブロックされ、RFNMが戻ってきたときにブロックが解除されます。30秒間使用されなかった後に削除されるのは、ブロックされていない送信リンクのエントリーだけです。23ページの任意の遅延に言及した記述は、Host/IMPインターフェイスがHostとIMPの間でビットを非同期に転送するように設計されている限りにおいて、ハードウェアに関する意味合いを持たせることだけを意図したものでした。

A RFNM is returned from the destination IMP to the source IMP when a message reaches the head of the destination IMP's output queue to the Host (i.e. just before a message is sent to the Host). If a destination IMP cannot then deliver that full message to the Host, at most one more message may possibly arrive at that IMP due to the premature release of the RFNM. The new message will subsequently take its place at the end of the output queue to the Host thus guaranteeing the preservation of the proper message arrival sequence.

RFNMは、メッセージが宛先IMPのHostへの出力キューの先頭に達したとき（つまり、メッセージがHostに送られる直前）に、宛先IMPから送信元IMPに返されます。そのときに宛先IMPがそのメッセージ全体をHostに配送できない場合でも、RFNMを早めに解放したことによってそのIMPに届く可能性があるメッセージは、多くても1つだけです。その新しいメッセージはその後、Hostへの出力キューの末尾に並ぶので、メッセージの正しい到着順序が保たれることが保証されます。

The NOP message is a special control message which is available for use during initiation of communication between the Host and its IMP. The Host may, of course, decline to send NOP messages during this period, but the first received message after IMP startup or after the Host ready indicator has gone on, may be discarded by the IMP. We do not require a Host to be prepared to repeat transmissions into the network.

NOPメッセージは、HostとそのIMPの間で通信を開始する際に使用できる特別な制御メッセージです。もちろん、Hostはこの期間にNOPメッセージを送らないこともできますが、IMPの起動後、またはHostの準備完了表示がオンになった後に最初に受信したメッセージは、IMPによって破棄される場合があります。私たちは、Hostにネットワークへの送信を繰り返す準備をしておくことを求めてはいません。

R.E. Kahn
BOLT BERANEK AND NEWMAN INC.
