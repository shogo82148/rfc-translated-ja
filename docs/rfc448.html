RFC 448

Print files in FTP

RFC 448

FTPにおける印刷ファイル

INTRODUCTION

はじめに

Many of those who contributed to the definition of the FTP and RJE protocols have expressed varying degrees of uncertainty or unhappiness with the "print file" type in FTP. This RFC is intended to review the problem of print files in preparation for the forthcoming FTP meeting. Originally drafted on the basis of RFC 385, this RFC has been updated to reflect the terminology of the latest FTP document 454. (Changing the terminology doesn't solve the problem!)

FTPとRJEのプロトコルの定義に貢献した人々の多くが、FTPの「印刷ファイル（print file）」タイプについて、程度の差こそあれ不確かさや不満を表明しています。このRFCは、近く開催されるFTP会議に備えて、印刷ファイルの問題を検討することを目的としています。このRFCはもともとRFC 385に基づいて起草されましたが、最新のFTP文書である454の用語を反映するように更新しました。（用語を変えても問題は解決しません！）

It turns out that the Network RJE protocol as presently defined (see NIC 12112) seems to force a particular interpretation of print files in FTP and in fact, this interpretation is probably different from the one assumed by most FTP implementors.

現在定義されているネットワークRJEプロトコル（NIC 12112を参照）は、FTPにおける印刷ファイルの特定の解釈を強いているように見えます。そして実際のところ、この解釈は、ほとんどのFTP実装者が想定しているものとはおそらく異なります。

VERTICAL FORMAT CONTROL

垂直書式制御

What is a print file? Presumably it is a file which is intended to be sent (eventually) to a printer process to create a hard copy. Many operating systems (particularly those which are batch-processing oriented) allow the programmer to include control codes within a file to be printed, to control the vertical format of the printed page--for example, single/double line spacing, overprinting, and page ejection. A "print file" is one which includes such vertical format control ("VFC") information. There are three common ways for printer processes to determine VFC:

印刷ファイルとは何でしょうか？おそらく、ハードコピーを作成するために（最終的に）プリンタープロセスに送られることを意図したファイルのことでしょう。多くのオペレーティングシステム（特にバッチ処理指向のもの）では、印刷されるページの垂直書式（たとえば、1行送り/2行送り、重ね打ち、改ページ）を制御するために、プログラマーが印刷するファイルの中に制御コードを含めることができます。「印刷ファイル」とは、そのような垂直書式制御（「VFC」：vertical format control）の情報を含むファイルのことです。プリンタープロセスがVFCを決定する一般的な方法は3つあります。

CASE N: Non-Print File
The file contains no VFC information. The printer process applies a standard format (e.g., single space, standard vertical margins) if the file is printed.
CASE T: Print File with ASCII Format Effectors
The file is "Telnet-like", containing the ASCII controls CR, LF, and FF to provide VFC.
CASE A: Print File with ASA (Fortran) VFC
The first character of each record is a VFC code; see RFC 454 for the codes.
場合N：非印刷ファイル
ファイルはVFCの情報を含みません。ファイルが印刷される場合、プリンタープロセスは標準の書式（たとえば、1行送り、標準の上下余白）を適用します。
場合T：ASCIIの書式制御文字を含む印刷ファイル
ファイルは「Telnetに似た」ものであり、VFCを提供するためにASCIIの制御文字CR、LF、FFを含みます。
場合A：ASA（Fortran）のVFCを含む印刷ファイル
各レコードの最初の文字がVFCコードです。コードについてはRFC 454を参照してください。

Assuming there are to be print files in FTP, these _three_ cases need to be considered. These three cases are explicitly included within the RJE protocol as "transmission" modes; we have borrowed the RJE labels N,T, and A from NIC #12112. The current FTP (RFC 454) seems to provide only _two_ cases: _unformatted_ and _print_file_. It is unclear from RFC 454 how these two FTP formats are related to the three VFC cases. For example, it is unclear whether the FTP format is meant to be a property of the file as transferred over the Network or of the file as stored by the server.

FTPに印刷ファイルがあるとするならば、これら_3つの_場合を考慮する必要があります。これら3つの場合は、RJEプロトコルに「伝送」モードとして明示的に含まれています。RJEのラベルN、T、AはNIC #12112から借用しました。現在のFTP（RFC 454）は、_unformatted_と_print_file_の_2つの_場合しか提供していないようです。RFC 454からは、これら2つのFTPのフォーマットが3つのVFCの場合とどのように関係するのかが明らかではありません。たとえば、FTPのフォーマットが、ネットワーク上で転送されるファイルの属性なのか、サーバーが格納するファイルの属性なのかが明らかではありません。

As I understand it, the Tenex system supports only case T. The distinction between Case N and Case T is not always clear, however. If a Tenex file which contains only the CR LF combination of format effectors is printed, it may be considered Case N where CR LF delimits a logical record, and where the standard format is to begin printing each record on a new line. The RJE protocol uses this ambiguity to advantage; see below.

私の理解では、Tenexシステムは場合Tだけをサポートしています。しかし、場合Nと場合Tの区別は必ずしも明確ではありません。書式制御文字としてCR LFの組み合わせだけを含むTenexのファイルが印刷される場合、それは、CR LFが論理レコードを区切り、標準の書式では各レコードを新しい行から印刷する、場合Nとみなせるかもしれません。RJEプロトコルは、この曖昧さをうまく利用しています。後述します。

The IBM operating systems, on the other hand, support Cases N and A. The "output writer" process which drives the printer must know whether or not a file to be printed contains ASA VFC, so the system distinguishes internally between "print files" (Case A) and non-print files (Case N). The "print file" attribute is normally attached to a print file when it is created. For example, the language processors typically create print files for their "printer" output streams.

一方、IBMのオペレーティングシステムは、場合Nと場合Aをサポートしています。プリンターを駆動する「出力ライター（output writer）」プロセスは、印刷するファイルがASAのVFCを含むかどうかを知る必要があるため、システムは内部で「印刷ファイル」（場合A）と非印刷ファイル（場合N）を区別しています。「印刷ファイル」属性は、通常、印刷ファイルの作成時に付与されます。たとえば、言語プロセッサーは通常、「プリンター」出力ストリーム用に印刷ファイルを作成します。

Hence, when CCN's server FTP executes a STOR command, it must decide whether or not the new file is to be marked with the internal print file attribute. As noted earlier, FTP does not explicitly distinguish the three possible cases. We must either add some additional assumptions or server-dependent information outside FTP, or we must add a new format to FTP.

したがって、CCNのサーバーFTPがSTORコマンドを実行するとき、新しいファイルに内部の印刷ファイル属性を付けるかどうかを決めなければなりません。前述のとおり、FTPは3つの可能な場合を明示的に区別しません。FTPの外部で何らかの追加の仮定やサーバーに依存する情報を加えるか、FTPに新しいフォーマットを追加するかのどちらかが必要です。

IMPLICATIONS OF RJE

RJEからの帰結

To send an output ("printer") file to a user host, the RJE server will cause his FTP user process to send the file with the following attributes*:

出力（「プリンター」）ファイルをユーザーホストに送信するために、RJEサーバーは自身のFTPユーザープロセスに、次の属性*でファイルを送信させます。

*Note: Making the obvious conversion from RFC 385 to RFC 454 terminology.

*注：RFC 385からRFC 454の用語への自明な変換を行っています。

 VFC Case      |     FORMat            |     STRUcture
-------------------------------------------------------------------
  N            |     Unformatted       |     Record structure
               |     -                 |     -
  T            |     Unformatted       |     File structure
               |     -                 |     -
  A            |     Print File        |     Record structure
               |     -                 |     -

 VFC Case      |     FORMat            |     STRUcture
-------------------------------------------------------------------
  N            |     Unformatted       |     Record structure
               |     -                 |     -
  T            |     Unformatted       |     File structure
               |     -                 |     -
  A            |     Print File        |     Record structure
               |     -                 |     -

Thus, the authors of RJE intended to use the _structure_ attribute to resolve Cases N and T. This is perhaps a reasonable choice, but we should understand the consequences and make them explicit within the FTP document.

したがって、RJEの作者は、場合Nと場合Tを区別するために_structure_属性を使うことを意図していました。これはおそらく妥当な選択ですが、その帰結を理解し、FTPの文書の中で明示すべきです。

Assume for the moment that we want to maintain perfect consistency between FTP and RJE. An FTP server which uses ASA VFC internally should convert _every_ (Unformatted, Unstructured) file it receives to an internal print file! That is, the file must be mapped into a set of physical lines (which are really logical records internally), and an ASA VFC character must be appended to the beginning of each line before it is stored. Note that this implies that the default file structure in FTP should be changed to _record_structure_. (This reinforces the point made by Wayne Hathaway in RFC 414 that if a Tenex user transmits a source file to an IBM host and expects to manipulate it in some useful way, he'd better send it with _record_ structure.)

ここで、FTPとRJEの間の完全な一貫性を維持したいと仮定してみましょう。内部でASAのVFCを使用するFTPサーバーは、受信した_すべての_（Unformatted、Unstructured）ファイルを、内部の印刷ファイルに変換すべきです！つまり、ファイルは物理的な行（実際には内部的には論理レコード）の集合に対応づけられなければならず、格納する前に各行の先頭にASAのVFC文字を付け加えなければなりません。これは、FTPのデフォルトのファイル構造を_record_structure_（レコード構造）に変更すべきだということを意味している点に注意してください。（これは、TenexのユーザーがソースファイルをIBMのホストに送信し、それを何らかの有用な方法で操作することを期待するならば、_record_構造で送信したほうがよいという、Wayne HathawayがRFC 414で指摘した点を補強するものです。）

ANOTHER CHOICE

別の選択肢

If the loss of (unformatted, unstructured) as a simple default case is too offensive, we can simply change FTP to include three formats corresponding to Cases N, A, and T. RJE would be changed correspondingly.

単純なデフォルトの場合としての（unformatted、unstructured）を失うことがあまりに受け入れがたいのであれば、場合N、A、Tに対応する3つのフォーマットを含むようにFTPを変更するだけでもかまいません。RJEもそれに対応して変更することになります。

Steve Wolfe、Jon Postel、Eric Harslemとの議論は、FTPにおける印刷ファイルの問題を明確にするのにとても役立ちました。
