RFC 10019

Zeroconf Multicast Address Allocation Problem Statement and Requirements

RFC 10019

ゼロコンフィグレーションのマルチキャストアドレス割り当ての問題提起と要件

Abstract

概要

This document surveys current problems with existing protocols for automatically assigning multicast IP addresses in zero-configuration (zeroconf) networking environments. It addresses key challenges, such as link-layer address collisions, hardware limitations, multicast snooping inefficiencies, and the need to avoid manual configuration. Based on these challenges, it derives requirements for a lightweight, decentralized solution for dynamically allocating unique multicast group addresses without central coordination.

この文書は、ゼロコンフィグレーション（zeroconf）のネットワーク環境においてマルチキャストIPアドレスを自動的に割り当てるための既存のプロトコルにおける現在の問題を調査します。リンク層アドレスの衝突、ハードウェアの制限、マルチキャストスヌーピングの非効率性、手動設定を避ける必要性など、主要な課題を取り上げます。これらの課題に基づいて、中央での調整なしに一意のマルチキャストグループアドレスを動的に割り当てるための、軽量で分散型の解決策に対する要件を導き出します。

The document presents explicit requirements covering discovery, allocation, conflict detection and resolution, and lease management. It also evaluates considerations specific to IPv6 and IPv4 multicast address ranges, and identifies approaches that are unsuited for zeroconf deployment. This foundation serves as a reference for developing future solutions for multicast address allocation that operate autonomously within local networks.

この文書は、発見、割り当て、衝突の検出と解決、およびリース管理を対象とする明示的な要件を示します。また、IPv6とIPv4のマルチキャストアドレス範囲に固有の考慮事項を評価し、zeroconfでの展開に適さないアプローチを特定します。この基盤は、ローカルネットワーク内で自律的に動作するマルチキャストアドレス割り当てのための将来の解決策を開発するための参照として役立ちます。

1. Introduction

1. はじめに

Multicast communication is commonly used in networks that need to distribute data from one sender to multiple receivers efficiently. In some environments, such as small or isolated networks, multicast operate without centralized servers or manual configuration. These are referred to as zero-configuration (zeroconf) multicast networks.

マルチキャスト通信は、1つの送信者から複数の受信者にデータを効率的に配信する必要があるネットワークで一般的に使用されています。小規模なネットワークや孤立したネットワークなど、一部の環境では、マルチキャストは中央集権的なサーバーや手動設定なしで動作します。これらはゼロコンフィグレーション（zeroconf）マルチキャストネットワークと呼ばれます。

One example of such an environment is marine networks, which typically include a mix of sensors, controls, and displays. These networks vary in complexity depending on the size and design of the vessel. Devices may range from low-cost temperature or fluid sensors to high-bandwidth sources such as radar, sonar, or video feeds. Many marine networks are built on a single subnet and rely on Layer 2 Ethernet switches to connect devices.

そのような環境の一例は船舶ネットワークであり、通常はセンサー、制御装置、ディスプレイが混在しています。これらのネットワークの複雑さは、船舶の大きさや設計によってさまざまです。デバイスは、低コストの温度センサーや液体センサーから、レーダー、ソナー、ビデオフィードなどの高帯域幅のソースまで多岐にわたります。多くの船舶ネットワークは単一のサブネット上に構築されており、デバイスを接続するためにレイヤー2のイーサネットスイッチに依存しています。

In these networks, multicast is the most efficient method for distributing sensor data to multiple displays. However, challenges arise when high-bandwidth multicast streams overload links to low-bandwidth devices. Cost-effective switches often do not support source-specific multicast (SSM) because their address table only maps destination Media Access Control (MAC) addresses. Instead, each multicast stream is assigned a unique destination multicast IP address, and IGMP/MLD snooping [RFC4541] is used to control multicast delivery. This method introduces limitations, especially in environments where switch hardware lacks advanced multicast filtering capabilities.

これらのネットワークでは、マルチキャストは、センサーデータを複数のディスプレイに配信するための最も効率的な方法です。しかし、高帯域幅のマルチキャストストリームが低帯域幅のデバイスへのリンクに過負荷をかけると、課題が生じます。コスト効率の高いスイッチは、アドレステーブルが宛先のメディアアクセス制御（MAC）アドレスしか対応付けないため、ソース固有マルチキャスト（SSM）をサポートしていないことがよくあります。代わりに、各マルチキャストストリームには一意の宛先マルチキャストIPアドレスが割り当てられ、マルチキャストの配信を制御するためにIGMP/MLDスヌーピング[RFC4541]が使用されます。この方法には、特にスイッチのハードウェアに高度なマルチキャストフィルタリング機能がない環境では、制限があります。

While marine networks illustrate these issues well, the challenges they face are not unique. Many other zeroconf multicast environments, such as industrial automation, small-scale audio-visual (AV) systems, or ad hoc sensor networks, share similar constraints.

船舶ネットワークはこれらの問題をよく示していますが、それらが直面する課題は特有のものではありません。産業オートメーション、小規模なオーディオビジュアル（AV）システム、アドホックなセンサーネットワークなど、他の多くのzeroconfマルチキャスト環境も同様の制約を共有しています。

The Multicast Address Dynamic Client Allocation Protocol (MADCAP) [RFC2730] is a method for multicast IP address allocation, but its server-based model does not suit a zeroconf environment. [RFC3306] and [RFC4489] both discuss similar approaches to host-based multicast IPv6 address allocation, but neither adequately prevents link-layer address collisions. Although [RFC3307] establishes a framework to avoid multicast address collisions at both IPv6 and link layers, additional refinement is needed to put this into practice (see Section 4).

マルチキャストアドレス動的クライアント割り当てプロトコル（Multicast Address Dynamic Client Allocation Protocol: MADCAP）[RFC2730]はマルチキャストIPアドレスを割り当てるための方法ですが、そのサーバーベースのモデルはzeroconf環境には適していません。[RFC3306]と[RFC4489]はどちらもホストベースのマルチキャストIPv6アドレスの割り当てに対する同様のアプローチを議論していますが、いずれもリンク層アドレスの衝突を十分に防いでいません。[RFC3307]はIPv6層とリンク層の両方でマルチキャストアドレスの衝突を避けるためのフレームワークを確立していますが、これを実践に移すにはさらなる改良が必要です（Section 4を参照）。

This document outlines the problem space for zeroconf multicast address allocation, describes the key limitations of current protocols, details sources of link-layer address collisions, and defines a set of requirements for decentralized, zero-configuration multicast address allocation solutions. Multicast applications deployed in a zeroconf environment can use these solutions to dynamically allocate multicast group addresses. The manner in which a multicast group address is used after allocation is outside the scope of this document.

この文書は、zeroconfマルチキャストアドレス割り当ての問題空間を概説し、現在のプロトコルの主な制限を説明し、リンク層アドレスの衝突の原因を詳しく述べ、分散型のゼロコンフィグレーションのマルチキャストアドレス割り当ての解決策に対する一連の要件を定義します。zeroconf環境に展開されたマルチキャストアプリケーションは、これらの解決策を使用してマルチキャストグループアドレスを動的に割り当てることができます。割り当て後にマルチキャストグループアドレスがどのように使用されるかは、この文書の範囲外です。

The organization of IPv6 multicast and immense volume of possible multicast addresses makes IPv6 well-suited for zeroconf multicast networks. However, IPv4 is still considered by this document for networks where transitioning to IPv6 remains impractical.

IPv6マルチキャストの構成と、可能なマルチキャストアドレスの膨大な量により、IPv6はzeroconfマルチキャストネットワークに適しています。しかし、この文書では、IPv6への移行がいまだ現実的でないネットワークのために、IPv4も考慮します。

2. Link-Layer Address Collisions

2. リンク層アドレスの衝突

Link-layer address collisions are a key concern in multicast networks, particularly when devices rely on zero-configuration operation. Collisions occur when two or more multicast groups are assigned the same link-layer (MAC) address, leading to performance or forwarding issues. This section outlines three scenarios where such collisions can cause problems.

リンク層アドレスの衝突は、特にデバイスがゼロコンフィグレーションの動作に依存している場合、マルチキャストネットワークにおける重要な懸念事項です。衝突は、2つ以上のマルチキャストグループに同じリンク層（MAC）アドレスが割り当てられた場合に発生し、パフォーマンスや転送の問題につながります。このセクションでは、そのような衝突が問題を引き起こす可能性のある3つのシナリオを概説します。

First, many host network interfaces allow filtering of multicast traffic directly in hardware. When an application joins a multicast group, the host network stack typically programs the hardware to accept only traffic for that group. However, if two groups share the same link-layer address, the network interface cannot distinguish them. The network stack is then forced to process unwanted traffic in software, reducing performance and increasing CPU usage.

第一に、多くのホストのネットワークインターフェースでは、マルチキャストトラフィックをハードウェアで直接フィルタリングできます。アプリケーションがマルチキャストグループに参加すると、ホストのネットワークスタックは通常、そのグループのトラフィックのみを受け入れるようにハードウェアをプログラムします。しかし、2つのグループが同じリンク層アドレスを共有している場合、ネットワークインターフェースはそれらを区別できません。その場合、ネットワークスタックは不要なトラフィックをソフトウェアで処理せざるを得なくなり、パフォーマンスが低下し、CPU使用率が増加します。

Second, link-layer address collisions reduce the benefit of using multicast snooping switches on a network. Section 4 of [RFC4541] indicates some switches forward multicast traffic based solely on the link-layer address, without considering the network-layer group (see the results for Q2 and Q3). Although the survey is outdated, switches with these limitations still exist in some of the target deployments. In such cases, if two multicast streams share the same MAC address, traffic may be sent to devices that did not request it. This is especially problematic when low-bandwidth links are overwhelmed by high-bandwidth streams. Additional concerns related to the overlap of IPv6 and link-layer addresses are discussed in Section 3 of [RFC4541].

第二に、リンク層アドレスの衝突は、ネットワークでマルチキャストスヌーピングスイッチを使用することの利点を減らします。[RFC4541]のSection 4は、一部のスイッチがネットワーク層のグループを考慮せずに、リンク層アドレスのみに基づいてマルチキャストトラフィックを転送することを示しています（Q2とQ3の結果を参照）。その調査は古いものですが、そのような制限を持つスイッチは、対象となる展開の一部に依然として存在しています。そのような場合、2つのマルチキャストストリームが同じMACアドレスを共有していると、トラフィックがそれを要求していないデバイスに送信される可能性があります。これは、低帯域幅のリンクが高帯域幅のストリームによって圧倒される場合に特に問題となります。IPv6アドレスとリンク層アドレスの重複に関連する追加の懸念事項については、[RFC4541]のSection 3で議論されています。

Third, the internal design of some switches can also contribute to collisions. For example, certain switch implementations use a hash table with fixed buckets to store forwarding entries based on MAC addresses (see [US6690667B1]). If multiple addresses hash to the same location and the bucket fills up, additional entries may be dropped or rejected, resulting in forwarding failures.

第三に、一部のスイッチの内部設計も衝突の一因となる可能性があります。たとえば、特定のスイッチの実装では、MACアドレスに基づく転送エントリーを保存するために、固定のバケットを持つハッシュテーブルを使用しています（[US6690667B1]を参照）。複数のアドレスが同じ位置にハッシュされ、バケットがいっぱいになると、追加のエントリーが破棄または拒否され、転送の失敗につながる可能性があります。

These examples highlight why a collision-resistant multicast address allocation mechanism is essential in zeroconf environments. The success of this approach depends on the capabilities of the hardware (such as the number of addresses supported by the filters in host network interfaces and the size of the tables maintained in switches/routers) and on the number of multicast groups that are subscribed to by a particular receiver. When the number of entries in the filter tables exceeds availability, a typical fallback mechanism is to bypass the filter entirely and flood traffic to the receiver. This subsequently incurs a per-packet cost for any software-based filtering that is needed.

これらの例は、zeroconf環境において衝突に強いマルチキャストアドレス割り当てのメカニズムが不可欠である理由を浮き彫りにしています。このアプローチの成否は、ハードウェアの能力（ホストのネットワークインターフェースのフィルターがサポートするアドレスの数や、スイッチ/ルーターで維持されるテーブルのサイズなど）と、特定の受信者が購読するマルチキャストグループの数に依存します。フィルターテーブルのエントリーの数が利用可能な量を超えると、典型的なフォールバックのメカニズムは、フィルターを完全に迂回して受信者にトラフィックをフラッディングすることです。その結果、必要となるソフトウェアベースのフィルタリングに対してパケットごとのコストが発生します。

3. Solution Requirements

3. 解決策の要件

A solution intended for decentralized, zero-configuration multicast IP address assignment is expected to operate in dynamic, infrastructure-free environments. To be effective in such contexts, the solution needs to exhibit the following characteristics:

分散型のゼロコンフィグレーションのマルチキャストIPアドレスの割り当てを意図した解決策は、動的でインフラストラクチャーのない環境で動作することが期待されます。そのような状況で効果的であるためには、解決策は次の特性を示す必要があります：

  1. Unique Address Assignment: Use of the solution SHALL result in a unique address being assigned to the multicast group at both the network and link layers.
  2. Resilience to Single Points of Failure: The solution SHALL be designed to minimize introduction of a single point of failure, ensuring that operation continues even if individual devices or links become unavailable.
  3. Zero User Configuration: It SHALL operate without requiring user or administrator configuration, allowing seamless deployment in unmanaged networks.
  4. Coexistence with Multicast Address Allocation Solutions: The design SHALL allow coexistence with other multicast IP address allocation solutions, including both manual assignment and existing dynamic protocols.
  5. Single-Subnet Operation: It SHALL support operation within a single IP subnet, which is typical in link-local or isolated network environments.
  6. No External Connectivity: The solution SHALL NOT require Internet access or connectivity to external infrastructure.
  7. Supports Multiple Host Applications: It SHALL support multiple applications on the same host, each independently allocating multicast addresses and transmitting to those addresses.
  8. Collision Detection and Resolution: The solution SHALL include mechanisms to detect and resolve multicast address collisions at both the network and link layers.
  1. 一意のアドレスの割り当て：解決策を使用することで、ネットワーク層とリンク層の両方でマルチキャストグループに一意のアドレスが割り当てられるようにすることになります（SHALL）。
  2. 単一障害点に対する耐性：解決策は、単一障害点の導入を最小限に抑え、個々のデバイスやリンクが利用できなくなっても動作が継続することを保証するように設計することになります（SHALL）。
  3. ユーザー設定が不要：ユーザーや管理者による設定を必要とせずに動作し、管理されていないネットワークにシームレスに展開できるようにすることになります（SHALL）。
  4. マルチキャストアドレス割り当ての解決策との共存：設計は、手動による割り当てと既存の動的なプロトコルの両方を含む、他のマルチキャストIPアドレス割り当ての解決策との共存を可能にすることになります（SHALL）。
  5. 単一サブネットでの動作：リンクローカルまたは孤立したネットワーク環境で典型的な、単一のIPサブネット内での動作をサポートすることになります（SHALL）。
  6. 外部接続性が不要：解決策は、インターネットへのアクセスや外部のインフラストラクチャーへの接続性を必要とすることはありません（SHALL NOT）。
  7. 複数のホストアプリケーションのサポート：同じホスト上の複数のアプリケーションが、それぞれ独立してマルチキャストアドレスを割り当て、それらのアドレスに送信することをサポートすることになります（SHALL）。
  8. 衝突の検出と解決：解決策は、ネットワーク層とリンク層の両方でマルチキャストアドレスの衝突を検出して解決するメカニズムを含めるようにすることになります（SHALL）。

Note: In rare cases, collisions may arise after a temporary network partition, when different parts of the network allocate the same multicast address independently. Upon reconnection, such collisions SHALL be detectable and resolved gracefully by ensuring that conflicting streams are migrated to unique addresses.

注：まれに、ネットワークの異なる部分が独立して同じマルチキャストアドレスを割り当てることで、一時的なネットワークの分断の後に衝突が生じる場合があります。再接続時に、そのような衝突は検出可能であり、競合するストリームを一意のアドレスに移行させることで適切に解決されるようにすることになります（SHALL）。

In addition to the above, the following characteristics are considered desirable, but are left as recommendations to allow for flexibility in solution design:

上記に加えて、次の特性は望ましいと考えられますが、解決策の設計に柔軟性を持たせるために推奨事項として残されています：

  1. Multi-Subnet Support: Operation across multiple subnets is beneficial in more complex or routed environments and SHOULD be supported.
  2. Standards Compatibility: The solution SHOULD aim to minimize the need for changes to existing protocols or standards that affect backwards compatibility or deployment in existing networks.
  3. Cross-Platform Availability: It SHOULD use capabilities that are widely available across host platforms and operating systems.
  4. Minimal Dependency on Manufacturing Data: It SHOULD avoid reliance on preloaded configuration or device-specific manufacturing data.
  5. Low Overhead: The solution SHOULD minimize the volume and frequency of network traffic generated during normal operation.
  6. Advertisement: The solution SHOULD describe a mechanism for advertising and discovering multicast addresses allocated for an application.
  7. Network Topology: To allow compatibility with a variety of networks, the solution SHOULD work independently of the dynamics of the underlying topology and adjacencies.
  1. 複数サブネットのサポート：複数のサブネットにまたがる動作は、より複雑な環境やルーティングされる環境で有益であり、サポートされるべきです（SHOULD）。
  2. 標準との互換性：解決策は、後方互換性や既存のネットワークでの展開に影響を与える、既存のプロトコルや標準への変更の必要性を最小限に抑えることを目指すべきです（SHOULD）。
  3. クロスプラットフォームでの利用可能性：ホストのプラットフォームやオペレーティングシステムで広く利用可能な機能を使用すべきです（SHOULD）。
  4. 製造データへの依存を最小限にすること：事前にロードされた設定やデバイス固有の製造データへの依存を避けるべきです（SHOULD）。
  5. 低いオーバーヘッド：解決策は、通常の動作中に生成されるネットワークトラフィックの量と頻度を最小限に抑えるべきです（SHOULD）。
  6. 広告：解決策は、アプリケーションのために割り当てられたマルチキャストアドレスを広告し、発見するためのメカニズムを説明すべきです（SHOULD）。
  7. ネットワークトポロジー：さまざまなネットワークとの互換性を可能にするために、解決策は、基礎となるトポロジーと隣接関係の動態とは独立して動作すべきです（SHOULD）。

4. IPv6 Considerations

4. IPv6に関する考慮事項

The rules for IPv6 multicast addresses, described in [RFC3307], are comprehensive and well-organized. These rules must be followed by any solution allocating IPv6 multicast addresses, including solutions that meet the requirements defined in this document. However, some aspects of the organization of [RFC3307] need to be improved to ensure that a zeroconf multicast address assignment solution can coexist with other IPv6 multicast address assignment protocols.

[RFC3307]で説明されているIPv6マルチキャストアドレスの規則は、包括的でよく整理されています。これらの規則は、この文書で定義する要件を満たす解決策を含め、IPv6マルチキャストアドレスを割り当てるあらゆる解決策が従わなければなりません。しかし、zeroconfのマルチキャストアドレス割り当ての解決策が他のIPv6マルチキャストアドレス割り当てのプロトコルと共存できるようにするためには、[RFC3307]の構成のいくつかの側面を改善する必要があります。

For example, Section 2 of [RFC3307] explains that the last 32 bits of an IPv6 multicast address, called the group ID, are mapped directly to the Ethernet MAC address. Different parts of the group ID range are assigned based on how the address is allocated. Section 4.3 of [RFC3307] describes two ways to assign group IDs dynamically: one where a server assigns addresses, and another where hosts assign addresses themselves. However, both methods use the same group ID range, which creates a risk of address collisions if both are used at the same time.

たとえば、[RFC3307]のSection 2は、グループIDと呼ばれるIPv6マルチキャストアドレスの最後の32ビットが、イーサネットMACアドレスに直接対応付けられることを説明しています。グループIDの範囲のさまざまな部分は、アドレスの割り当て方法に基づいて割り当てられます。[RFC3307]のSection 4.3は、グループIDを動的に割り当てる2つの方法を説明しています。1つはサーバーがアドレスを割り当てる方法で、もう1つはホストが自らアドレスを割り当てる方法です。しかし、どちらの方法も同じグループIDの範囲を使用するため、両方を同時に使用するとアドレスの衝突のリスクが生じます。

An additional concern is that the group IDs used for this dynamic range overlap with the range used for Solicited-Node multicast addresses, a special type of multicast used by IPv6 for neighbor discovery (see Section 2.7.1 of [RFC4291]). This overlap increases the risk of unintentional conflicts with link-layer addresses.

追加の懸念事項は、この動的な範囲に使用されるグループIDが、IPv6が近隣探索に使用する特別な種類のマルチキャストである要請ノード（Solicited-Node）マルチキャストアドレスに使用される範囲と重複していることです（[RFC4291]のSection 2.7.1を参照）。この重複により、リンク層アドレスとの意図しない競合のリスクが高まります。

Note that [RFC3307] focuses on 48-bit addresses on Ethernet, but similar issues would be seen on any medium that generates link-layer multicast addresses by truncating an IPv6 multicast address.

[RFC3307]はイーサネット上の48ビットアドレスに焦点を当てていますが、IPv6マルチキャストアドレスを切り詰めることでリンク層のマルチキャストアドレスを生成するあらゆる媒体で同様の問題が見られることに注意してください。

5. IPv4 Considerations

5. IPv4に関する考慮事項

In IPv4, multicast addresses can sometimes cause conflicts at the data link layer. For example, as explained in Section 6.4 of [RFC1112], this happens with Ethernet because only the lower 23 bits of an IPv4 multicast address are used to generate the Ethernet multicast address. Since an IPv4 multicast address is 32 bits and starts with a fixed 4-bit prefix (leaving 28 bits), this means up to 2(28-23) = 32 different multicast IP addresses can map to the same Ethernet address. As a result, devices may receive multicast traffic they didn't ask for.

IPv4では、マルチキャストアドレスがデータリンク層で競合を引き起こすことがあります。たとえば、[RFC1112]のSection 6.4で説明されているように、イーサネットでは、IPv4マルチキャストアドレスの下位23ビットのみがイーサネットのマルチキャストアドレスの生成に使用されるため、これが発生します。IPv4マルチキャストアドレスは32ビットで、固定の4ビットのプレフィックスで始まる（28ビットが残る）ため、最大2(28-23) = 32個の異なるマルチキャストIPアドレスが同じイーサネットアドレスに対応付けられる可能性があることを意味します。その結果、デバイスは要求していないマルチキャストトラフィックを受信する可能性があります。

The address allocation guidelines in [RFC5771] did not account for this type of collision when they were created. Because of this limitation, the recommended approach for new designs that need dynamic multicast IP address assignment is to use IPv6 instead of IPv4.

[RFC5771]のアドレス割り当てのガイドラインは、作成された時点ではこの種類の衝突を考慮していませんでした。この制限のため、動的なマルチキャストIPアドレスの割り当てが必要な新しい設計に推奨されるアプローチは、IPv4の代わりにIPv6を使用することです。

However, if using IPv4 is necessary, then multicast addresses SHOULD be chosen carefully from within the Administratively Scoped Block (239.0.0.0/8). Additionally, solutions for zeroconf multicast address allocation SHOULD try to avoid using addresses that may already be in use by other applications on the same network, to minimize the risk of conflicts.

しかし、IPv4を使用する必要がある場合は、マルチキャストアドレスを管理スコープブロック（239.0.0.0/8）の中から慎重に選択すべきです（SHOULD）。さらに、zeroconfのマルチキャストアドレス割り当ての解決策は、競合のリスクを最小限に抑えるために、同じネットワーク上の他のアプリケーションによってすでに使用されている可能性のあるアドレスの使用を避けるようにすべきです（SHOULD）。

Zeroconf coexistence with other IPv4 multicast address allocation solutions may not be possible; in that case, it may be necessary to require manual configuration or to limit the solutions that are deployed.

zeroconfと他のIPv4マルチキャストアドレス割り当ての解決策との共存は不可能な場合があります。その場合、手動設定を要求するか、展開する解決策を制限する必要があるかもしれません。

6. Security Considerations

6. セキュリティーに関する考慮事項

Zeroconf multicast address allocation mechanisms are vulnerable to accidental or malicious address collisions, which may lead to denial of service or misdirection of traffic. Solutions derived from these requirements SHALL include measures for collision detection and conflict resolution [REQ-8], and SHOULD include measures to prevent unauthorized address use. Specific security mechanisms are outside the scope of this document.

zeroconfのマルチキャストアドレス割り当てのメカニズムは、偶発的または悪意のあるアドレスの衝突に対して脆弱であり、サービス拒否やトラフィックの誤った誘導につながる可能性があります。これらの要件から導かれる解決策は、衝突の検出と競合の解決のための対策を含めるようにすることになります（SHALL）[REQ-8]。また、アドレスの認可されていない使用を防ぐための対策を含めるべきです（SHOULD）。具体的なセキュリティーメカニズムはこの文書の範囲外です。

Appendix A. Excluded Solutions

Appendix A. 除外された解決策

The way multicast IP addresses are mapped to link-layer multicast addresses is already defined in existing standards, such as [RFC1112] for IPv4 over Ethernet and [RFC2464] for IPv6 over Ethernet. These standards specify a fixed prefix used in creating the Ethernet multicast address. Changing this prefix would open the door to new solutions, but those are not being considered here for practical reasons.

マルチキャストIPアドレスをリンク層のマルチキャストアドレスに対応付ける方法は、イーサネット上のIPv4については[RFC1112]、イーサネット上のIPv6については[RFC2464]など、既存の標準ですでに定義されています。これらの標準は、イーサネットのマルチキャストアドレスの作成に使用される固定のプレフィックスを規定しています。このプレフィックスを変更すれば新しい解決策への道が開けますが、実用上の理由からここではそれらを検討していません。

One idea is to reduce the size of the fixed prefix, which would leave more bits available for the group ID. This would make address collisions less likely. Another idea is to create a new protocol that dynamically maps multicast IP addresses to link-layer addresses, similar to how DHCP assigns IP addresses. This protocol could work locally on a subnet, and routers could adjust the mapping for incoming multicast traffic at the network edge.

1つのアイデアは、固定のプレフィックスのサイズを縮小することで、それによりグループIDに使用できるビットが増えます。これにより、アドレスの衝突が起こりにくくなります。もう1つのアイデアは、DHCPがIPアドレスを割り当てるのと同様に、マルチキャストIPアドレスをリンク層アドレスに動的に対応付ける新しいプロトコルを作成することです。このプロトコルはサブネット上でローカルに動作でき、ルーターはネットワークのエッジで受信するマルチキャストトラフィックに対する対応付けを調整できます。

However, these ideas would require significant changes to how network devices handle multicast traffic. Since existing hardware and operating systems are built around the current standards, it's unlikely that such changes would be widely supported anytime soon.

しかし、これらのアイデアでは、ネットワークデバイスがマルチキャストトラフィックを処理する方法に大幅な変更が必要になります。既存のハードウェアとオペレーティングシステムは現在の標準を中心に構築されているため、そのような変更がすぐに広くサポートされる可能性は低いです。

Another potential solution for IPv4 was to assign 32 separate, non-overlapping address ranges to avoid collisions altogether (e.g., assign 224.0.0.254, 224.128.0.254, 225.0.0.254, etc.). However, this was rejected because [RFC5771] discourages new allocations, given how limited the IPv4 multicast address space already is.

IPv4に対するもう1つの潜在的な解決策は、衝突を完全に避けるために、重複しない32個の別個のアドレス範囲を割り当てる（たとえば、224.0.0.254、224.128.0.254、225.0.0.254などを割り当てる）ことでした。しかし、IPv4マルチキャストアドレス空間がすでにどれほど限られているかを考慮して[RFC5771]が新しい割り当てを推奨していないため、これは却下されました。
