A Voucher Artifact for Bootstrapping Protocols

RFC 8366

ブートストラッププロトコルのためのバウチャーアーティファクト

Abstract

概要

This document defines a strategy to securely assign a pledge to an owner using an artifact signed, directly or indirectly, by the pledge's manufacturer. This artifact is known as a "voucher".

この文書は、プレッジの製造業者が直接または間接的に署名したアーティファクトを使用して、プレッジを所有者に安全に割り当てるための戦略を定義します。 このアーティファクトは「バウチャー（voucher）」と呼ばれます。

This document defines an artifact format as a YANG-defined JSON document that has been signed using a Cryptographic Message Syntax (CMS) structure. Other YANG-derived formats are possible. The voucher artifact is normally generated by the pledge's manufacturer (i.e., the Manufacturer Authorized Signing Authority (MASA)).

この文書は、アーティファクトの形式として、暗号メッセージ構文（Cryptographic Message Syntax、CMS）構造を使用して署名された、YANGで定義されたJSON文書を定義します。 YANGから派生したほかの形式も可能です。 バウチャーアーティファクトは、通常、プレッジの製造業者（すなわち、製造業者認可署名機関（Manufacturer Authorized Signing Authority、MASA））によって生成されます。

This document only defines the voucher artifact, leaving it to other documents to describe specialized protocols for accessing it.

この文書はバウチャーアーティファクトのみを定義し、それにアクセスするための特化したプロトコルの記述はほかの文書に委ねます。

1. Introduction

1. はじめに

This document defines a strategy to securely assign a candidate device (pledge) to an owner using an artifact signed, directly or indirectly, by the pledge's manufacturer, i.e., the Manufacturer Authorized Signing Authority (MASA). This artifact is known as the "voucher".

この文書は、プレッジの製造業者、すなわち製造業者認可署名機関（Manufacturer Authorized Signing Authority、MASA）が直接または間接的に署名したアーティファクトを使用して、候補デバイス（プレッジ）を所有者に安全に割り当てるための戦略を定義します。 このアーティファクトは「バウチャー（voucher）」と呼ばれます。

The voucher artifact is a JSON [RFC8259] document that conforms with a data model described by YANG [RFC7950], is encoded using the rules defined in [RFC8259], and is signed using (by default) a CMS structure [RFC5652].

バウチャーアーティファクトは、YANG [RFC7950]で記述されたデータモデルに準拠し、[RFC8259]で定義された規則を使用してエンコードされ、（デフォルトでは）CMS構造[RFC5652]を使用して署名された、JSON [RFC8259]文書です。

The primary purpose of a voucher is to securely convey a certificate, the "pinned-domain-cert", that a pledge can use to authenticate subsequent interactions. A voucher may be useful in several contexts, but the driving motivation herein is to support secure bootstrapping mechanisms. Assigning ownership is important to bootstrapping mechanisms so that the pledge can authenticate the network that is trying to take control of it.

バウチャーの主な目的は、プレッジがその後のやり取りを認証するために使用できる証明書である「pinned-domain-cert」を、安全に伝達することです。 バウチャーはいくつかの文脈で有用な場合がありますが、ここでの主な動機は、セキュアなブートストラップのメカニズムをサポートすることです。 所有権の割り当ては、プレッジが自分を制御しようとしているネットワークを認証できるようにするために、ブートストラップのメカニズムにとって重要です。

The lifetimes of vouchers may vary. In some bootstrapping protocols, the vouchers may include a nonce restricting them to a single use, whereas the vouchers in other bootstrapping protocols may have an indicated lifetime. In order to support long lifetimes, this document recommends using short lifetimes with programmatic renewal, see Section 6.1.

バウチャーの有効期間はさまざまです。 あるブートストラッププロトコルでは、バウチャーにノンスを含めて単一の使用に限定する場合がありますが、ほかのブートストラッププロトコルでは、バウチャーに有効期間が示される場合があります。 長い有効期間をサポートするために、この文書では、短い有効期間とプログラムによる更新を組み合わせて使用することを推奨します。セクション6.1を参照してください。

This document only defines the voucher artifact, leaving it to other documents to describe specialized protocols for accessing it. Some bootstrapping protocols using the voucher artifact defined in this document include: [ZERO-TOUCH], [SECUREJOIN], and [KEYINFRA]).

この文書はバウチャーアーティファクトのみを定義し、それにアクセスするための特化したプロトコルの記述はほかの文書に委ねます。 この文書で定義するバウチャーアーティファクトを使用するブートストラッププロトコルには、[ZERO-TOUCH]、[SECUREJOIN]、[KEYINFRA]などがあります。

2. Terminology

2. 用語

This document uses the following terms:

この文書では、次の用語を使用します。

Artifact:
Used throughout to represent the voucher as instantiated in the form of a signed structure.
Domain:
The set of entities or infrastructure under common administrative control. The goal of the bootstrapping protocol is to enable a pledge to discover and join a domain.
Imprint:
The process where a device obtains the cryptographic key material to identify and trust future interactions with a network. This term is taken from Konrad Lorenz's work in biology with new ducklings: "during a critical period, the duckling would assume that anything that looks like a mother duck is in fact their mother" [Stajano99theresurrecting]. An equivalent for a device is to obtain the fingerprint of the network's root certification authority certificate. A device that imprints on an attacker suffers a similar fate to a duckling that imprints on a hungry wolf. Imprinting is a term from psychology and ethology, as described in [imprinting].
Join Registrar (and Coordinator):
A representative of the domain that is configured, perhaps autonomically, to decide whether a new device is allowed to join the domain. The administrator of the domain interfaces with a join registrar (and Coordinator) to control this process. Typically, a join registrar is "inside" its domain. For simplicity, this document often refers to this as just "registrar".
MASA (Manufacturer Authorized Signing Authority):
The entity that, for the purpose of this document, signs the vouchers for a manufacturer's pledges. In some bootstrapping protocols, the MASA may have an Internet presence and be integral to the bootstrapping process, whereas in other protocols the MASA may be an offline service that has no active role in the bootstrapping process.
Owner:
The entity that controls the private key of the "pinned-domain-cert" certificate conveyed by the voucher.
Pledge:
The prospective device attempting to find and securely join a domain. When shipped, it only trusts authorized representatives of the manufacturer.
Registrar:
See join registrar.
TOFU (Trust on First Use):
Where a pledge device makes no security decisions but rather simply trusts the first domain entity it is contacted by. Used similarly to [RFC7435]. This is also known as the "resurrecting duckling" model.
Voucher:
A signed statement from the MASA service that indicates to a pledge the cryptographic identity of the domain it should trust.
Artifact:
アーティファクト（artifact）は、この文書全体を通して、署名された構造の形でインスタンス化されたバウチャーを表すために使用されます。
Domain:
共通の管理制御下にあるエンティティーまたはインフラストラクチャーの集合（ドメイン）です。 ブートストラッププロトコルの目標は、プレッジがドメインを発見して参加できるようにすることです。
Imprint:
デバイスが、ネットワークとの将来のやり取りを識別して信頼するための暗号鍵素材を取得する処理（刷り込み）です。 この用語は、コンラート・ローレンツによる生まれたばかりのアヒルの子に関する生物学の研究から取られています。「臨界期の間、アヒルの子は母アヒルのように見えるものは何でも実際に自分の母親であると思い込む」[Stajano99theresurrecting]。 デバイスにとってこれに相当するのは、ネットワークのルート認証局の証明書のフィンガープリントを取得することです。 攻撃者に刷り込まれたデバイスは、飢えた狼に刷り込まれたアヒルの子と同様の運命をたどります。 [imprinting]で説明されているように、刷り込みは心理学と動物行動学の用語です。
Join Registrar (and Coordinator):
新しいデバイスがドメインへの参加を許可されるかどうかを決定するように（おそらく自律的に）設定された、ドメインの代表者です。 ドメインの管理者は、この処理を制御するためにジョインレジストラー（およびコーディネーター）とやり取りします。 通常、ジョインレジストラーはそのドメインの「内側」にあります。 簡単にするために、この文書ではこれを単に「レジストラー」と呼ぶことがよくあります。
MASA (Manufacturer Authorized Signing Authority):
この文書の目的において、製造業者のプレッジに対するバウチャーに署名するエンティティー（製造業者認可署名機関）です。 あるブートストラッププロトコルでは、MASAはインターネット上に存在してブートストラップ処理に不可欠な役割を果たす場合がありますが、ほかのプロトコルでは、MASAはブートストラップ処理で能動的な役割を持たないオフラインのサービスである場合があります。
Owner:
バウチャーによって伝達される「pinned-domain-cert」証明書の秘密鍵を管理するエンティティー（所有者）です。
Pledge:
ドメインを見つけて安全に参加しようとしている、見込みのデバイス（プレッジ）です。 出荷時には、製造業者の認可された代表者のみを信頼します。
Registrar:
ジョインレジストラーを参照してください。
TOFU (Trust on First Use):
プレッジデバイスがセキュリティー上の判断を何も行わず、単に最初に接触してきたドメインのエンティティーを信頼すること（初回使用時の信頼）です。 [RFC7435]と同様の意味で使用します。 これは「蘇るアヒルの子（resurrecting duckling）」モデルとしても知られています。
Voucher:
プレッジが信頼すべきドメインの暗号学的アイデンティティーをプレッジに示す、MASAサービスからの署名付きの声明（バウチャー）です。

4. Survey of Voucher Types

4. バウチャーの種類の概観

A voucher is a cryptographically protected statement to the pledge device authorizing a zero-touch "imprint" on the join registrar of the domain. The specific information a voucher provides is influenced by the bootstrapping use case.

バウチャーは、ドメインのジョインレジストラーへのゼロタッチの「刷り込み」を認可する、プレッジデバイスに対する暗号学的に保護された声明です。 バウチャーが提供する具体的な情報は、ブートストラップのユースケースによって左右されます。

The voucher can impart the following information to the join registrar and pledge:

バウチャーは、ジョインレジストラーとプレッジに次の情報を伝えることができます。

Assertion Basis:
Indicates the method that protects the imprint (this is distinct from the voucher signature that protects the voucher itself). This might include manufacturer-asserted ownership verification, assured logging operations, or reliance on pledge endpoint behavior such as secure root of trust of measurement. The join registrar might use this information. Only some methods are normatively defined in this document. Other methods are left for future work.
Authentication of Join Registrar:
Indicates how the pledge can authenticate the join registrar. This document defines a mechanism to pin the domain certificate. Pinning a symmetric key, a raw key, or "CN-ID" or "DNS-ID" information (as defined in [RFC6125]) is left for future work.
Anti-Replay Protections:
Time- or nonce-based information to constrain the voucher to time periods or bootstrap attempts.
Assertion Basis:
刷り込みを保護する方法を示します（これは、バウチャー自体を保護するバウチャーの署名とは別のものです）。 これには、製造業者が主張する所有権の検証、保証されたログ記録の操作、または測定のセキュアなルートオブトラストのようなプレッジのエンドポイントの振る舞いへの依存などが含まれる場合があります。 ジョインレジストラーは、この情報を使用する場合があります。 この文書で規範的に定義するのは一部の方法だけです。 ほかの方法は今後の作業に委ねます。
Authentication of Join Registrar:
プレッジがジョインレジストラーを認証する方法を示します。 この文書では、ドメイン証明書をピン留めするメカニズムを定義します。 対称鍵、生の鍵、または（[RFC6125]で定義されている）「CN-ID」や「DNS-ID」の情報のピン留めは、今後の作業に委ねます。
Anti-Replay Protections:
バウチャーを期間またはブートストラップの試行に制限するための、時刻またはノンスに基づく情報です。

Audit Voucher:
An Audit Voucher is named after the logging assertion mechanisms that the registrar then "audits" to enforce local policy. The registrar mitigates a MiTM registrar by auditing that an unknown MiTM registrar does not appear in the log entries. This does not directly prevent the MiTM but provides a response mechanism that ensures the MiTM is unsuccessful. The advantage is that actual ownership knowledge is not required on the MASA service.
Nonceless Audit Voucher:
An Audit Voucher without a validity period statement. Fundamentally, it is the same as an Audit Voucher except that it can be issued in advance to support network partitions or to provide a permanent voucher for remote deployments.
Ownership Audit Voucher:
An Audit Voucher where the MASA service has verified the registrar as the authorized owner. The MASA service mitigates a MiTM registrar by refusing to generate Audit Vouchers for unauthorized registrars. The registrar uses audit techniques to supplement the MASA. This provides an ideal sharing of policy decisions and enforcement between the vendor and the owner.
Ownership ID Voucher:
Named after inclusion of the pledge's CN-ID or DNS-ID within the voucher. The MASA service mitigates a MiTM registrar by identifying the specific registrar (via WebPKI) authorized to own the pledge.
Bearer Voucher:
A Bearer Voucher is named after the inclusion of a registrar ID wildcard. Because the registrar identity is not indicated, this voucher type must be treated as a secret and protected from exposure as any 'bearer' of the voucher can claim the pledge device. Publishing a nonceless bearer voucher effectively turns the specified pledge into a "TOFU" device with minimal mitigation against MiTM registrars. Bearer vouchers are out of scope.
Audit Voucher:
監査バウチャー（Audit Voucher）は、レジストラーがローカルポリシーを適用するためにその後「監査」する、ログ記録による主張のメカニズムにちなんで名付けられています。 レジストラーは、未知のMiTMレジストラーがログエントリーに現れないことを監査することで、MiTMレジストラーの脅威を軽減します。 これはMiTMを直接防ぐものではありませんが、MiTMが成功しないことを保証する対応メカニズムを提供します。 利点は、MASAサービス側で実際の所有権の情報を必要としないことです。
Nonceless Audit Voucher:
有効期間の記述を持たない監査バウチャー（ノンスなし監査バウチャー）です。 基本的には監査バウチャーと同じですが、ネットワークの分断をサポートしたり、遠隔地への展開のために恒久的なバウチャーを提供したりするために、事前に発行できる点が異なります。
Ownership Audit Voucher:
MASAサービスが、レジストラーを認可された所有者として検証済みである監査バウチャー（所有権監査バウチャー）です。 MASAサービスは、認可されていないレジストラーに対して監査バウチャーの生成を拒否することで、MiTMレジストラーの脅威を軽減します。 レジストラーは、MASAを補完するために監査の手法を使用します。 これにより、ポリシーの決定と適用が、ベンダーと所有者の間で理想的に分担されます。
Ownership ID Voucher:
所有権IDバウチャー（Ownership ID Voucher）は、バウチャー内にプレッジのCN-IDまたはDNS-IDを含めることにちなんで名付けられています。 MASAサービスは、プレッジを所有することを認可された特定のレジストラーを（WebPKIを介して）識別することで、MiTMレジストラーの脅威を軽減します。
Bearer Voucher:
ベアラーバウチャー（Bearer Voucher）は、レジストラーIDのワイルドカードを含めることにちなんで名付けられています。 レジストラーのアイデンティティーが示されないため、バウチャーの「ベアラー（持参人）」であれば誰でもプレッジデバイスの所有を主張できることから、この種類のバウチャーは秘密として扱い、露出から保護しなければなりません。 ノンスなしのベアラーバウチャーを公開すると、指定されたプレッジは、MiTMレジストラーに対する緩和策が最小限しかない「TOFU」デバイスに事実上なってしまいます。 ベアラーバウチャーは範囲外です。

5. Voucher Artifact

5. バウチャーアーティファクト

The voucher's primary purpose is to securely assign a pledge to an owner. The voucher informs the pledge which entity it should consider to be its owner.

バウチャーの主な目的は、プレッジを所有者に安全に割り当てることです。 バウチャーは、どのエンティティーを自分の所有者とみなすべきかをプレッジに知らせます。

This document defines a voucher that is a JSON-encoded instance of the YANG module defined in Section 5.3 that has been, by default, CMS signed.

この文書では、セクション5.3で定義するYANGモジュールのJSONエンコードされたインスタンスであって、デフォルトではCMSで署名されたものとして、バウチャーを定義します。

This format is described here as a practical basis for some uses (such as in NETCONF), but more to clearly indicate what vouchers look like in practice. This description also serves to validate the YANG data model.

ここでこの形式を説明するのは、（NETCONFなどにおける）いくつかの用途のための実用的な基盤とするためでもありますが、それ以上に、バウチャーが実際にどのようなものになるかを明確に示すためです。 この説明は、YANGデータモデルを検証する役割も果たします。

Future work is expected to define new mappings of the voucher to Concise Binary Object Representation (CBOR) (from JSON) and to change the signature container from CMS to JSON Object Signing and Encryption (JOSE) or CBOR Object Signing and Encryption (COSE). XML or ASN.1 formats are also conceivable.

今後の作業では、（JSONから）簡潔なバイナリーオブジェクト表現（Concise Binary Object Representation、CBOR）へのバウチャーの新しいマッピングを定義し、署名のコンテナーをCMSからJSONオブジェクト署名・暗号化（JSON Object Signing and Encryption、JOSE）またはCBORオブジェクト署名・暗号化（CBOR Object Signing and Encryption、COSE）に変更することが期待されています。 XMLやASN.1の形式も考えられます。

This document defines a media type and a filename extension for the CMS-encoded JSON type. Future documents on additional formats would define additional media types. Signaling is in the form of a MIME Content-Type, an HTTP Accept: header, or more mundane methods like use of a filename extension when a voucher is transferred on a USB key.

この文書では、CMSでエンコードされたJSONの種類に対するメディアタイプとファイル名の拡張子を定義します。 追加の形式に関する今後の文書では、追加のメディアタイプを定義することになるでしょう。 シグナリングは、MIMEのContent-Type、HTTPのAccept:ヘッダー、あるいはバウチャーをUSBキーで転送する場合のファイル名の拡張子の使用のような、より平凡な方法の形で行われます。

5.4. CMS Format Voucher Artifact

5.4. CMS形式のバウチャーアーティファクト

The IETF evolution of PKCS#7 is CMS [RFC5652]. A CMS-signed voucher, the default type, contains a ContentInfo structure with the voucher content. An eContentType of 40 indicates that the content is a JSON-encoded voucher.

PKCS#7をIETFで発展させたものがCMS [RFC5652]です。 デフォルトの種類であるCMS署名付きバウチャーには、バウチャーのコンテンツを持つContentInfo構造が含まれます。 eContentTypeが40であることは、コンテンツがJSONでエンコードされたバウチャーであることを示します。

The signing structure is a CMS SignedData structure, as specified by Section 5.1 of [RFC5652], encoded using ASN.1 Distinguished Encoding Rules (DER), as specified in ITU-T X.690 [ITU.X690.2015].

署名の構造は、[RFC5652]のセクション5.1で規定されているCMSのSignedData構造であり、ITU-T X.690 [ITU.X690.2015]で規定されているASN.1の識別符号化規則（Distinguished Encoding Rules、DER）を使用してエンコードされます。

To facilitate interoperability, Section 8.3 in this document registers the media type "application/voucher-cms+json" and the filename extension ".vcj".

相互運用性を促進するために、この文書のセクション8.3では、メディアタイプ「application/voucher-cms+json」とファイル名の拡張子「.vcj」を登録します。

The CMS structure MUST contain a 'signerInfo' structure, as described in Section 5.1 of [RFC5652], containing the signature generated over the content using a private key trusted by the recipient. Normally, the recipient is the pledge and the signer is the MASA. Another possible use could be as a "signed voucher request" format originating from the pledge or registrar toward the MASA. Within this document, the signer is assumed to be the MASA.

CMS構造には、[RFC5652]のセクション5.1で説明されている「signerInfo」構造を含めなければなりません（MUST）。この構造には、受信者が信頼する秘密鍵を使用してコンテンツに対して生成された署名が含まれます。 通常、受信者はプレッジであり、署名者はMASAです。 ほかに考えられる用途として、プレッジまたはレジストラーからMASAに向けて発信される「署名付きバウチャーリクエスト」の形式として使用することもできるでしょう。 この文書の中では、署名者はMASAであると仮定します。

Note that Section 5.1 of [RFC5652] includes a discussion about how to validate a CMS object, which is really a PKCS7 object (cmsVersion=1). Intermediate systems (such the Bootstrapping Remote Secure Key Infrastructures (BRSKI) registrar) that might need to evaluate the voucher in flight MUST be prepared for such an older format. No signaling is necessary, as the manufacturer knows the capabilities of the pledge and will use an appropriate format voucher for each pledge.

[RFC5652]のセクション5.1には、CMSオブジェクト（実際にはPKCS7オブジェクト（cmsVersion=1））を検証する方法に関する議論が含まれていることに注意してください。 転送中のバウチャーを評価する必要があるかもしれない中間システム（ブートストラップリモートセキュア鍵インフラストラクチャー（Bootstrapping Remote Secure Key Infrastructures、BRSKI）のレジストラーなど）は、そのような古い形式に備えなければなりません（MUST）。 製造業者はプレッジの能力を把握しており、プレッジごとに適切な形式のバウチャーを使用するため、シグナリングは必要ありません。

The CMS structure SHOULD also contain all of the certificates leading up to and including the signer's trust anchor certificate known to the recipient. The inclusion of the trust anchor is unusual in many applications, but third parties cannot accurately audit the transaction without it.

CMS構造には、受信者が知っている署名者のトラストアンカー証明書までの（それを含む）すべての証明書も含めるべきです（SHOULD）。 トラストアンカーを含めることは多くのアプリケーションでは一般的ではありませんが、それがなければ第三者はトランザクションを正確に監査できません。

The CMS structure MAY also contain revocation objects for any intermediate certificate authorities (CAs) between the voucher issuer and the trust anchor known to the recipient. However, the use of CRLs and other validity mechanisms is discouraged, as the pledge is unlikely to be able to perform online checks and is unlikely to have a trusted clock source. As described below, the use of short-lived vouchers and/or a pledge-provided nonce provides a freshness guarantee.

CMS構造には、バウチャーの発行者と受信者が知っているトラストアンカーとの間にある中間認証局（CA）に対する失効オブジェクトを含めてもよいです（MAY）。 ただし、プレッジはオンラインでのチェックを実行できる可能性が低く、信頼できる時刻源を持っている可能性も低いため、CRLやその他の有効性確認のメカニズムの使用は推奨されません。 後で説明するように、有効期間の短いバウチャーやプレッジが提供するノンスを使用することで、新しさが保証されます。

6. Design Considerations

6. 設計上の考慮事項

6.1. Renewals Instead of Revocations

6.1. 失効の代わりに更新を

The lifetimes of vouchers may vary. In some bootstrapping protocols, the vouchers may be created and consumed immediately, whereas in other bootstrapping solutions, there may be a significant time delay between when a voucher is created and when it is consumed. In cases when there is a time delay, there is a need for the pledge to ensure that the assertions made when the voucher was created are still valid.

バウチャーの有効期間はさまざまです。 あるブートストラッププロトコルでは、バウチャーは作成されてすぐに消費される場合がありますが、ほかのブートストラップのソリューションでは、バウチャーが作成されてから消費されるまでに大幅な時間の遅れがある場合があります。 時間の遅れがある場合、プレッジは、バウチャーの作成時に行われた主張が依然として有効であることを確認する必要があります。

A revocation artifact is generally used to verify the continued validity of an assertion such as a PKIX certificate, web token, or a "voucher". With this approach, a potentially long-lived assertion is paired with a reasonably fresh revocation status check to ensure that the assertion is still valid. However, this approach increases solution complexity, as it introduces the need for additional protocols and code paths to distribute and process the revocations.

一般に、失効アーティファクトは、PKIX証明書、Webトークン、または「バウチャー」などの主張が引き続き有効であることを検証するために使用されます。 このアプローチでは、長期間有効である可能性がある主張と、適度に新しい失効状態のチェックとを組み合わせることで、主張が依然として有効であることを確認します。 しかし、このアプローチでは、失効情報を配布して処理するための追加のプロトコルとコードパスが必要になるため、ソリューションの複雑さが増します。

Addressing the shortcomings of revocations, this document recommends instead the use of lightweight renewals of short-lived non-revocable vouchers. That is, rather than issue a long-lived voucher, where the 'expires-on' leaf is set to some distant date, the expectation is for the MASA to instead issue a short-lived voucher, where the 'expires-on' leaf is set to a relatively near date, along with a promise (reflected in the 'last-renewal-date' field) to reissue the voucher again when needed. Importantly, while issuing the initial voucher may incur heavyweight verification checks ("Are you who you say you are?" "Does the pledge actually belong to you?"), reissuing the voucher should be a lightweight process, as it ostensibly only updates the voucher's validity period. With this approach, there is only the one artifact, and only one code path is needed to process it; there is no possibility of a pledge choosing to skip the revocation status check because, for instance, the OCSP Responder is not reachable.

失効の欠点に対処するために、この文書では代わりに、失効できない短期間のバウチャーを軽量に更新することを推奨します。 つまり、「expires-on」リーフを遠い日付に設定した長期間のバウチャーを発行するのではなく、MASAは代わりに、「expires-on」リーフを比較的近い日付に設定した短期間のバウチャーを、必要なときにバウチャーを再発行するという約束（「last-renewal-date」フィールドに反映されます）とともに発行することが期待されます。 重要なのは、最初のバウチャーの発行には重い検証チェック（「あなたは名乗っているとおりの人物ですか？」「そのプレッジは本当にあなたのものですか？」）が伴う場合がありますが、バウチャーの再発行は、表向きはバウチャーの有効期間を更新するだけなので、軽量な処理であるべきだということです。 このアプローチでは、アーティファクトは1つだけであり、それを処理するためのコードパスも1つだけで済みます。たとえばOCSPレスポンダーに到達できないといった理由で、プレッジが失効状態のチェックを省略することを選択する可能性はありません。

While this document recommends issuing short-lived vouchers, the voucher artifact does not restrict the ability to create long-lived voucher, if required; however, no revocation method is described.

この文書では有効期間の短いバウチャーの発行を推奨していますが、バウチャーアーティファクトは、必要であれば長期間のバウチャーを作成することを制限しません。ただし、失効の方法は説明しません。

Note that a voucher may be signed by a chain of intermediate CAs leading up to the trust anchor certificate known by the pledge. Even though the voucher itself is not revocable, it may still be revoked, per se, if one of the intermediate CA certificates is revoked.

バウチャーは、プレッジが知っているトラストアンカー証明書に至る中間CAのチェーンによって署名される場合があることに注意してください。 バウチャー自体は失効できなくても、中間CA証明書のいずれかが失効した場合には、バウチャーもそれ自体として失効する場合があります。

6.2. Voucher Per Pledge

6.2. プレッジごとのバウチャー

The solution described herein originally enabled a single voucher to apply to many pledges, using lists of regular expressions to represent ranges of serial-numbers. However, it was determined that blocking the renewal of a voucher that applied to many devices would be excessive when only the ownership for a single pledge needed to be blocked. Thus, the voucher format now only supports a single serial-number to be listed.

ここで説明するソリューションは、もともと、シリアル番号の範囲を表す正規表現のリストを使用して、単一のバウチャーを多くのプレッジに適用できるようにしていました。 しかし、単一のプレッジの所有権だけをブロックする必要がある場合に、多くのデバイスに適用されるバウチャーの更新をブロックするのは過剰であると判断されました。 そのため、現在のバウチャーの形式は、単一のシリアル番号の記載のみをサポートしています。

7. Security Considerations

7. セキュリティーに関する考慮事項

7.1. Clock Sensitivity

7.1. 時計への依存

An attacker could use an expired voucher to gain control over a device that has no understanding of time. The device cannot trust NTP as a time reference, as an attacker could control the NTP stream.

攻撃者は、期限切れのバウチャーを使用して、時刻を理解しないデバイスの制御を奪う可能性があります。 攻撃者がNTPのストリームを制御する可能性があるため、デバイスは時刻の基準としてNTPを信頼できません。

There are three things to defend against this: 1) devices are required to verify that the expires-on field has not yet passed, 2) devices without access to time can use nonces to get ephemeral vouchers, and 3) vouchers without expiration times may be used, which will appear in the audit log, informing the security decision.

これに対する防御策は3つあります。1）デバイスには、expires-onフィールドの時刻がまだ過ぎていないことを検証することが求められます。2）時刻にアクセスできないデバイスは、ノンスを使用して一時的なバウチャーを取得できます。3）有効期限のないバウチャーを使用することもでき、それは監査ログに記録されて、セキュリティー上の判断に情報を提供します。

This document defines a voucher format that contains time values for expirations, which require an accurate clock in order to be processed correctly. Vendors planning on issuing vouchers with expiration values must ensure that devices have an accurate clock when shipped from manufacturing facilities and take steps to prevent clock tampering. If it is not possible to ensure clock accuracy, then vouchers with expirations should not be issued.

この文書では、有効期限の時刻の値を含むバウチャーの形式を定義していますが、それを正しく処理するには正確な時計が必要です。 有効期限の値を持つバウチャーの発行を計画しているベンダーは、製造施設からの出荷時にデバイスが正確な時計を持っていることを保証し、時計の改ざんを防ぐ手段を講じなければなりません。 時計の正確さを保証できない場合は、有効期限のあるバウチャーを発行すべきではありません。

7.2. Protect Voucher PKI in HSM

7.2. HSMでのバウチャーPKIの保護

Pursuant the recommendation made in Section 6.1 for the MASA to be deployed as an online voucher signing service, it is RECOMMENDED that the MASA's private key used for signing vouchers is protected by a hardware security module (HSM).

MASAをオンラインのバウチャー署名サービスとして展開するというセクション6.1の推奨に従い、バウチャーの署名に使用するMASAの秘密鍵は、ハードウェアセキュリティーモジュール（HSM）によって保護されることが推奨されます（RECOMMENDED）。

7.3. Test Domain Certificate Validity When Signing

7.3. 署名時のドメイン証明書の有効性のテスト

If a domain certificate is compromised, then any outstanding vouchers for that domain could be used by the attacker. The domain administrator is clearly expected to initiate revocation of any domain identity certificates (as is normal in PKI solutions).

ドメイン証明書が侵害された場合、そのドメインに対する未使用のバウチャーはすべて攻撃者に使用される可能性があります。 （PKIソリューションでは通常のことですが）ドメインの管理者は、当然、ドメインのアイデンティティー証明書の失効を開始することが期待されます。

Similarly,they are expected to contact the MASA to indicate that an outstanding (presumably short lifetime) voucher should be blocked from automated renewal. Protocols for voucher distribution are RECOMMENDED to check for revocation of domain identity certificates before the signing of vouchers.

同様に、管理者は、未使用の（おそらく有効期間の短い）バウチャーの自動更新をブロックすべきであることを示すために、MASAに連絡することが期待されます。 バウチャー配布のためのプロトコルは、バウチャーに署名する前にドメインのアイデンティティー証明書の失効をチェックすることが推奨されます（RECOMMENDED）。

7.4. YANG Module Security Considerations

7.4. YANGモジュールのセキュリティーに関する考慮事項

The YANG module specified in this document defines the schema for data that is subsequently encapsulated by a CMS signed-data content type, as described in Section 5 of [RFC5652]. As such, all of the YANG modeled data is protected from modification.

この文書で規定するYANGモジュールは、[RFC5652]のセクション5で説明されているように、その後CMSのsigned-dataコンテンツタイプによってカプセル化されるデータのスキーマを定義します。 そのため、YANGでモデル化されたデータはすべて改変から保護されます。

Implementations should be aware that the signed data is only protected from external modification; the data is still visible. This potential disclosure of information doesn't affect security so much as privacy. In particular, adversaries can glean information such as which devices belong to which organizations and which CRL Distribution Point and/or OCSP Responder URLs are accessed to validate the vouchers. When privacy is important, the CMS signed-data content type SHOULD be encrypted, either by conveying it via a mutually authenticated secure transport protocol (e.g., TLS [RFC5246]) or by encapsulating the signed-data content type with an enveloped-data content type (Section 6 of [RFC5652]), though details for how to do this are outside the scope of this document.

実装者は、署名されたデータは外部からの改変から保護されているだけで、データは依然として見えることを認識しておくべきです。 このような情報の潜在的な漏えいは、セキュリティーよりもむしろプライバシーに影響します。 特に、敵対者は、どのデバイスがどの組織に属しているか、バウチャーを検証するためにどのCRL配布ポイントやOCSPレスポンダーのURLにアクセスしているか、といった情報を収集できます。 プライバシーが重要な場合、CMSのsigned-dataコンテンツタイプは、相互認証されたセキュアなトランスポートプロトコル（たとえばTLS [RFC5246]）を介して伝達するか、signed-dataコンテンツタイプをenveloped-dataコンテンツタイプ（[RFC5652]のセクション6）でカプセル化することによって、暗号化されるべきです（SHOULD）。ただし、その方法の詳細はこの文書の範囲外です。

The use of YANG to define data structures, via the 'yang-data' statement, is relatively new and distinct from the traditional use of YANG to define an API accessed by network management protocols such as NETCONF [RFC6241] and RESTCONF [RFC8040]. For this reason, these guidelines do not follow template described by Section 3.7 of [YANG-GUIDE].

「yang-data」ステートメントを介してYANGを使用してデータ構造を定義することは比較的新しく、NETCONF [RFC6241]やRESTCONF [RFC8040]などのネットワーク管理プロトコルによってアクセスされるAPIを定義するという従来のYANGの使い方とは異なります。 そのため、これらのガイドラインは、[YANG-GUIDE]のセクション3.7で説明されているテンプレートには従っていません。
