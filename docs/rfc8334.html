Launch Phase Mapping for the Extensible Provisioning Protocol (EPP)

RFC 8334

拡張可能なプロビジョニングプロトコル（EPP）のためのローンチフェーズマッピング

Abstract

概要

This document describes an Extensible Provisioning Protocol (EPP) extension mapping for the provisioning and management of domain name registrations and applications during the launch of a domain name registry.

この文書は、ドメイン名レジストリーのローンチ期間中に、ドメイン名の登録と申請をプロビジョニングおよび管理するための、拡張可能なプロビジョニングプロトコル（EPP）の拡張マッピングについて説明します。

1. Introduction

1. はじめに

This document describes an extension mapping for version 1.0 of the Extensible Provisioning Protocol (EPP) [RFC5730]. This EPP mapping specifies a flexible schema that can be used to implement several common use cases related to the provisioning and management of domain name registrations and applications during the launch of a domain name registry.

この文書は、拡張可能なプロビジョニングプロトコル（EPP）[RFC5730]のバージョン1.0に対する拡張マッピングについて説明します。このEPPマッピングは、ドメイン名レジストリーのローンチ期間中のドメイン名の登録と申請のプロビジョニングおよび管理に関連する、いくつかの一般的なユースケースを実装するために使用できる柔軟なスキーマを規定します。

It is typical for domain registries to operate in special modes as they begin operation to facilitate allocation of domain names, often according to special rules. This document uses the term "launch phase" and the shorter form "launch" to refer to such a period. Multiple launch phases and multiple models are supported to enable the launch of a domain name registry. Server policy determines what is supported and validated. Communication of the server policy is typically performed using an out-of-band mechanism that is not specified in this document.

ドメインレジストリーは、運用開始時にドメイン名の割り当てを容易にするため、多くの場合は特別な規則に従った特別なモードで運用するのが一般的です。この文書では、そのような期間を指すために「ローンチフェーズ（launch phase）」という用語と、その短縮形である「ローンチ（launch）」を使用します。ドメイン名レジストリーのローンチを可能にするために、複数のローンチフェーズと複数のモデルをサポートします。何をサポートし、何を検証するかは、サーバーポリシーによって決まります。サーバーポリシーの伝達は通常、この文書では規定しない帯域外のメカニズムを使用して行われます。

The EPP domain name mapping [RFC5731] is designed for the steady-state operation of a registry. During a launch period, the model in place may be different from what is defined in the EPP domain name mapping [RFC5731]. For example, registries often accept multiple applications for the same domain name during the "sunrise" launch phase, referred to as a Launch Application. A Launch Registration refers to a registration made during a launch phase when the server uses a "first-come, first-served" model. Even in a "first-come, first-served" model, additional steps and information might be required, such as trademark information. In addition, RFC 7848 [RFC7848] defines a registry interface for the Trademark Claims or "claims" launch phase that includes support for presenting a Trademark Claims Notice to the registrant. This document proposes an extension to the domain name mapping in order to provide a uniform interface for the management of Launch Applications and Launch Registrations in launch phases.

EPPドメイン名マッピング[RFC5731]は、レジストリーの定常状態の運用向けに設計されています。ローンチ期間中に採用されるモデルは、EPPドメイン名マッピング[RFC5731]で定義されているものとは異なる場合があります。たとえば、レジストリーは「sunrise」ローンチフェーズの間に、同じドメイン名に対する複数の申請を受け付けることがよくあります。これをローンチ申請（Launch Application）と呼びます。ローンチ登録（Launch Registration）は、サーバーが「先着順（first-come, first-served）」モデルを使用している場合に、ローンチフェーズ中に行われる登録を指します。「先着順」モデルであっても、商標情報などの追加の手順や情報が必要になる場合があります。さらに、RFC 7848 [RFC7848]は、商標クレーム（Trademark Claims）または「claims」ローンチフェーズのためのレジストリーインターフェイスを定義しており、これには登録者に商標クレーム通知（Trademark Claims Notice）を提示するためのサポートが含まれます。この文書は、ローンチフェーズにおけるローンチ申請とローンチ登録を管理するための統一されたインターフェイスを提供するために、ドメイン名マッピングに対する拡張を提案します。

2. Object Attributes

2. オブジェクト属性

This extension adds additional elements to the EPP domain name mapping [RFC5731]. Only those new elements are described here.

この拡張は、EPPドメイン名マッピング[RFC5731]に要素を追加します。ここでは、それらの新しい要素についてのみ説明します。

2.1. Application Identifier

2.1. 申請識別子

Servers MAY allow multiple applications, referred to as a Launch Application, of the same domain name during its launch phase operations. Upon receiving a valid <domain:create> command to create a Launch Application, the server MUST create an application object corresponding to the request, assign an application identifier for the Launch Application, set the pendingCreate status [RFC5731], and return the application identifier to the client with the <launch:applicationID> element. In order to facilitate correlation, all subsequent launch operations on the Launch Application MUST be qualified by the previously assigned application identifier using the <launch:applicationID> element.

サーバーは、ローンチフェーズの運用中に、同じドメイン名に対する複数の申請（ローンチ申請と呼びます）を許可してもよいです（MAY）。ローンチ申請を作成する有効な<domain:create>コマンドを受信すると、サーバーはリクエストに対応する申請オブジェクトを作成し、ローンチ申請に申請識別子を割り当て、pendingCreateステータス[RFC5731]を設定し、<launch:applicationID>要素で申請識別子をクライアントに返さなければなりません（MUST）。相関付けを容易にするために、そのローンチ申請に対する以降のすべてのローンチ操作は、<launch:applicationID>要素を使用して、以前に割り当てられた申請識別子で修飾しなければなりません（MUST）。

2.2. Validator Identifier

2.2. 検証者識別子

The Validator Identifier is unique to the server and is the identifier for a Trademark Validator, which validates marks and has a repository of validated marks. The OPTIONAL "validatorID" attribute is used to define the Validator Identifier of the Trademark Validator. Registries MAY support more than one third-party Trademark Validator. The unique set of Validator Identifier values supported by the server is up to server policy. The Internet Corporation for Assigned Names and Numbers (ICANN) Trademark Clearinghouse (TMCH) is the default Trademark Validator and is reserved for the Validator Identifier of "tmch". If the ICANN TMCH is not used or multiple Trademark Validators are used, the Validator Identifier MUST be defined using the "validatorID" attribute.

検証者識別子（Validator Identifier）はサーバー内で一意であり、マークを検証し、検証済みマークのリポジトリーを持つ商標検証者（Trademark Validator）の識別子です。選択可能な（OPTIONAL）「validatorID」属性は、商標検証者の検証者識別子を定義するために使用されます。レジストリーは、複数の第三者の商標検証者をサポートしてもよいです（MAY）。サーバーがサポートする検証者識別子の値の一意な集合は、サーバーポリシー次第です。Internet Corporation for Assigned Names and Numbers（ICANN）のTrademark Clearinghouse（TMCH）はデフォルトの商標検証者であり、検証者識別子「tmch」として予約されています。ICANN TMCHを使用しない場合、または複数の商標検証者を使用する場合は、「validatorID」属性を使用して検証者識別子を定義しなければなりません（MUST）。

The Validator Identifier MAY be related to one or more issuer identifiers of the <mark:id> and <smd:id> elements defined in [RFC7848]. Both the Validator Identifier and the Issuer Identifier used MUST be unique in the server. If the ICANN TMCH is not used or multiple Trademark Validators are used, the server MUST define the list of supported validator identifiers and MUST make this information available to clients using a mutually acceptable, out-of-band mechanism.

検証者識別子は、[RFC7848]で定義されている<mark:id>要素と<smd:id>要素の1つ以上の発行者識別子に関連付けられてもよいです（MAY）。使用する検証者識別子と発行者識別子は、どちらもサーバー内で一意でなければなりません（MUST）。ICANN TMCHを使用しない場合、または複数の商標検証者を使用する場合、サーバーはサポートする検証者識別子のリストを定義しなければなりません（MUST）。また、相互に受け入れ可能な帯域外のメカニズムを使用して、この情報をクライアントが利用できるようにしなければなりません（MUST）。

The Validator Identifier may define a non-Trademark Validator that supports a form of claims, where claims and a Validator Identifier can be used for purposes beyond trademarks.

検証者識別子は、ある形式のクレームをサポートする、商標以外の検証者を定義することもできます。この場合、クレームと検証者識別子は商標以外の目的に使用できます。

2.3. Launch Phases

2.3. ローンチフェーズ

The server MAY support multiple launch phases sequentially or simultaneously. The <launch:phase> element MUST be included by the client to define the target launch phase of the command. The server SHOULD validate the phase and MAY validate the sub-phase of the <launch:phase> element against the active phase and OPTIONAL sub-phase of the server, and return an EPP error result code of 2306 [RFC5730] if there is a mismatch.

サーバーは、複数のローンチフェーズを順次または同時にサポートしてもよいです（MAY）。クライアントは、コマンドの対象となるローンチフェーズを定義するために、<launch:phase>要素を含めなければなりません（MUST）。サーバーは、<launch:phase>要素のフェーズをサーバーのアクティブなフェーズに対して検証すべきです（SHOULD）。また、<launch:phase>要素のサブフェーズをサーバーの選択可能な（OPTIONAL）サブフェーズに対して検証してもよいです（MAY）。不一致がある場合、サーバーはEPPエラー結果コード2306 [RFC5730]を返します。

The following launch phase values are defined:

次のローンチフェーズの値を定義します。

sunrise:
The phase during which trademark holders can submit registrations or applications with trademark information that can be validated by the server.
landrush:
A post-"sunrise" launch phase when non-trademark holders are allowed to register domain names with steps taken to address a large volume of initial registrations.
claims:
The phase, as defined in Section 2.3.1, in which a claims notice must be displayed to a prospective registrant of a domain name that matches trademarks.
open:
A phase that is also referred to as "steady state". Servers may require additional trademark protection during this phase.
custom:
A custom server launch phase that is defined using the "name" attribute.
sunrise：
商標保有者が、サーバーによって検証可能な商標情報を伴う登録または申請を提出できるフェーズです。
landrush：
「sunrise」の後のローンチフェーズで、商標保有者以外がドメイン名を登録することが許可され、初期の大量の登録に対処するための手順がとられます。
claims：
セクション2.3.1で定義するフェーズで、このフェーズでは、商標に一致するドメイン名の登録希望者にクレーム通知を表示しなければなりません。
open：
「定常状態（steady state）」とも呼ばれるフェーズです。サーバーは、このフェーズの間に追加の商標保護を要求することがあります。
custom：
「name」属性を使用して定義される、サーバー独自のローンチフェーズです。

For extensibility, the <launch:phase> element includes an OPTIONAL "name" attribute that can define a sub-phase or the full name of the phase when the <launch:phase> element has the "custom" value. For example, the "claims" launch phase could have two sub-phases that include "landrush" and "open".

拡張性のために、<launch:phase>要素には選択可能な（OPTIONAL）「name」属性があり、サブフェーズを定義したり、<launch:phase>要素の値が「custom」の場合にフェーズの完全な名前を定義したりできます。たとえば、「claims」ローンチフェーズに、「landrush」と「open」の2つのサブフェーズを持たせることができます。

Launch phases MAY overlap to support the "claims" launch phase, defined in Section 2.3.1, and to support a traditional "landrush" launch phase. The overlap of the "claims" and "landrush" launch phases SHOULD be handled by setting "claims" as the <launch:phase> value and setting "landrush" as the sub-phase with the "name" attribute. For example, the <launch:phase> element should be <launch:phase name="landrush">claims</launch:phase>.

セクション2.3.1で定義する「claims」ローンチフェーズをサポートし、かつ従来の「landrush」ローンチフェーズをサポートするために、ローンチフェーズは重複してもよいです（MAY）。「claims」と「landrush」のローンチフェーズの重複は、<launch:phase>の値として「claims」を設定し、「name」属性でサブフェーズとして「landrush」を設定することで処理すべきです（SHOULD）。たとえば、<launch:phase>要素は<launch:phase name="landrush">claims</launch:phase>となるはずです。

2.3.1. Trademark Claims Phase

2.3.1. 商標クレームフェーズ

The Trademark Claims Phase is when a claims notice must be displayed to a prospective registrant of a domain name that matches trademarks. See [ICANN-TMCH] for additional details of trademark claims handling. The source of the trademarks is a Trademark Validator, and the source of the claims notice information is a Claims Notice Information Service (CNIS), which may be directly linked to a Trademark Validator. The client interfaces with 1) the server to determine if a trademark exists for a domain name, 2) a CNIS to get the claims notice information, and 3) the server to pass the claims notice acceptance information in a create command. This document supports the Trademark Claims Phase in two ways, including:

商標クレームフェーズ（Trademark Claims Phase）とは、商標に一致するドメイン名の登録希望者にクレーム通知を表示しなければならない期間のことです。商標クレームの処理に関する詳細については、[ICANN-TMCH]を参照してください。商標の情報源は商標検証者であり、クレーム通知情報の情報源はクレーム通知情報サービス（Claims Notice Information Service、CNIS）です。CNISは商標検証者と直接結び付いている場合があります。クライアントは、1）ドメイン名に対して商標が存在するかどうかを判断するためにサーバーと、2）クレーム通知情報を取得するためにCNISと、3）作成コマンドでクレーム通知の承諾情報を渡すためにサーバーと、やり取りします。この文書は、次の2つの方法で商標クレームフェーズをサポートします。

Claims Check Form:
Is defined in Section 3.1.1 and is used to determine whether or not there are any matching trademarks for a domain name. If there is at least one matching trademark that exists for the domain name, a claims key is returned. The mapping of domain names and the claims keys is based on an out-of-band interface between the server and the Trademark Validator. The CNIS associated with the claims key Validator Identifier (Section 2.2) MUST accept the claims key as the basis for retrieving the claims information.
Claims Create Form:
Is defined in Section 3.3.2 and is used to pass the claims notice acceptance information in a create command. The notice identifier (<launch:noticeID>) format, validation rules, and server processing is up to the interface between the server and the Trademark Validator. The CNIS associated with the Validator Identifier (Section 2.2) MUST generate a notice identifier compliant with the <launch:noticeID> element.
クレーム確認形式（Claims Check Form）：
セクション3.1.1で定義しており、ドメイン名に一致する商標があるかどうかを判断するために使用します。ドメイン名に一致する商標が少なくとも1つ存在する場合は、クレームキーが返されます。ドメイン名とクレームキーの対応付けは、サーバーと商標検証者の間の帯域外のインターフェイスに基づきます。クレームキーの検証者識別子（セクション2.2）に関連付けられたCNISは、クレーム情報を取得するための基礎としてクレームキーを受け入れなければなりません（MUST）。
クレーム作成形式（Claims Create Form）：

2.4. Status Values

2.4. ステータス値

A Launch Application or Launch Registration object MAY have a launch status value. The <launch:status> element is used to convey the launch status pertaining to the object, beyond what is specified in the object mapping. A Launch Application or Launch Registration MUST set the "pendingCreate" status [RFC5731] if a launch status is supported and is not one of the final statuses ("allocated" and "rejected").

ローンチ申請またはローンチ登録のオブジェクトは、ローンチステータス値を持ってもよいです（MAY）。<launch:status>要素は、オブジェクトマッピングで規定されている内容を超えて、オブジェクトに関するローンチステータスを伝えるために使用されます。ローンチステータスがサポートされており、かつそれが最終ステータス（「allocated」と「rejected」）のいずれでもない場合、ローンチ申請またはローンチ登録には「pendingCreate」ステータス[RFC5731]を設定しなければなりません（MUST）。

The following status values are defined using the required "s" attribute:

必須の「s」属性を使用して、次のステータス値を定義します。

pendingValidation:
The initial state of a newly created application or registration object. The application or registration requires validation, but the validation process has not yet completed.
validated:
The application or registration meets relevant registry rules.
invalid:
The application or registration does not validate according to registry rules. Server policies permitting, it may transition back into "pendingValidation" for revalidation, after modifications are made to ostensibly correct attributes that caused the validation failure.
pendingAllocation:
The allocation of the application or registration is pending based on the results of some out-of-band process (for example, an auction).
allocated:
The object corresponding to the application or registration has been provisioned. This is a possible end state of an application or registration object.
rejected:
The application or registration object was not provisioned. This is a possible end state of an application or registration object.
custom:
A custom status that is defined using the "name" attribute.
pendingValidation：
新しく作成された申請または登録のオブジェクトの初期状態です。申請または登録は検証を必要としていますが、検証プロセスはまだ完了していません。
validated：
申請または登録は、関連するレジストリーの規則を満たしています。
invalid：
申請または登録は、レジストリーの規則に従った検証に合格しません。サーバーポリシーが許す場合、検証の失敗の原因となった属性を修正するための変更を加えた後に、再検証のために「pendingValidation」に戻ることがあります。
pendingAllocation：
申請または登録の割り当ては、何らかの帯域外のプロセス（たとえば、オークション）の結果に基づいて保留されています。
allocated：
申請または登録に対応するオブジェクトがプロビジョニングされました。これは、申請または登録のオブジェクトにありうる最終状態です。
rejected：
申請または登録のオブジェクトはプロビジョニングされませんでした。これは、申請または登録のオブジェクトにありうる最終状態です。
custom：
「name」属性を使用して定義される独自のステータスです。

Each status value MAY be accompanied by a string of human-readable text that describes the rationale for the status applied to the object. The OPTIONAL "lang" attribute, as defined in [RFC5646], MAY be present to identify the language if the negotiated value is something other than the default value of "en" (English).

各ステータス値には、オブジェクトに適用されたステータスの理由を説明する、人間が読めるテキストの文字列を付けてもよいです（MAY）。ネゴシエートされた値がデフォルト値の「en」（英語）以外の場合は、言語を識別するために、[RFC5646]で定義されている選択可能な（OPTIONAL）「lang」属性が存在してもよいです（MAY）。

For extensibility, the <launch:status> element includes an OPTIONAL "name" attribute that can define a sub-status or the full name of the status when the status value is "custom". The server SHOULD use one of the non-"custom" status values.

拡張性のために、<launch:status>要素には選択可能な（OPTIONAL）「name」属性があり、サブステータスを定義したり、ステータス値が「custom」の場合にステータスの完全な名前を定義したりできます。サーバーは、「custom」以外のステータス値のいずれかを使用すべきです（SHOULD）。

Status values MAY be skipped. For example, an application or registration MAY immediately start at the "allocated" status, or an application or registration MAY skip the "pendingAllocation" status. If the launch phase does not require validation of a request, an application or registration MAY immediately skip to "pendingAllocation".

ステータス値は省略してもよいです（MAY）。たとえば、申請または登録は、いきなり「allocated」ステータスから始まってもよいです（MAY）。また、申請または登録は「pendingAllocation」ステータスを省略してもよいです（MAY）。ローンチフェーズでリクエストの検証が不要な場合、申請または登録は、ただちに「pendingAllocation」に進んでもよいです（MAY）。

2.6. Mark Validation Models

2.6. マーク検証モデル

A server MUST support at least one of the following models for validating trademark information:

サーバーは、商標情報を検証するための次のモデルの少なくとも1つをサポートしなければなりません（MUST）。

code:
Use of a mark code by itself to validate that the mark matches the domain name. This model is supported using the <launch:codeMark> element with just the <launch:code> element.
mark:
The mark information is passed without any other validation element. The server will use some custom form of validation to validate that the mark information is authentic. This model is supported using the <launch:codeMark> element with just the <mark:mark> (Section 2.6.2) element.
code with mark:
A code is used along with the mark information by the server to validate the mark utilizing an external party. The code represents some form of secret that matches the mark information passed. This model is supported using the <launch:codeMark> element that contains both the <launch:code> and the <mark:mark> (Section 2.6.2) elements.
signed mark:
The mark information is digitally signed as described in the Digital Signature section (Section 2.6.3). The digital signature can be directly validated by the server using the public key of the external party that created the signed mark using its private key. This model is supported using the <smd:signedMark> (Section 2.6.3.1) and <smd:encodedSignedMark> (Section 2.6.3.2) elements.
code：
マークがドメイン名に一致することを検証するために、マークコードを単独で使用します。このモデルは、<launch:code>要素だけを含む<launch:codeMark>要素を使用してサポートされます。
mark：
マーク情報を、他の検証要素なしで渡します。サーバーは、マーク情報が本物であることを検証するために、何らかの独自の形式の検証を使用します。このモデルは、<mark:mark>（セクション2.6.2）要素だけを含む<launch:codeMark>要素を使用してサポートされます。
code with mark：
サーバーが外部の当事者を利用してマークを検証するために、マーク情報とともにコードを使用します。コードは、渡されたマーク情報に一致する、ある種の秘密を表します。このモデルは、<launch:code>要素と<mark:mark>（セクション2.6.2）要素の両方を含む<launch:codeMark>要素を使用してサポートされます。
signed mark：
マーク情報は、デジタル署名のセクション（セクション2.6.3）で説明するようにデジタル署名されています。デジタル署名は、自身の秘密鍵を使用して署名付きマークを作成した外部の当事者の公開鍵を使用して、サーバーが直接検証できます。このモデルは、<smd:signedMark>（セクション2.6.3.1）要素と<smd:encodedSignedMark>（セクション2.6.3.2）要素を使用してサポートされます。

More than one <launch:codeMark>, <smd:signedMark> (Section 2.6.3.1), or <smd:encodedSignedMark> (Section 2.6.3.2) element MAY be specified. The maximum number of marks per domain name is up to server policy.

<launch:codeMark>、<smd:signedMark>（セクション2.6.3.1）、または<smd:encodedSignedMark>（セクション2.6.3.2）要素は、複数指定してもよいです（MAY）。ドメイン名あたりのマークの最大数は、サーバーポリシー次第です。

3. EPP Command Mapping

3. EPPコマンドマッピング

A detailed description of the EPP syntax and semantics can be found in the EPP core protocol specification [RFC5730]. The command mappings described here are specifically for use in the Launch Phase Extension.

EPPの構文とセマンティクスの詳細な説明は、EPPのコアプロトコル仕様[RFC5730]にあります。ここで説明するコマンドマッピングは、特にローンチフェーズ拡張で使用するためのものです。

This mapping is designed to be flexible, requiring only a minimum set of required elements.

このマッピングは柔軟になるように設計されており、必須の要素は最小限の集合だけです。

While it is meant to serve several use cases, it does not prescribe any interpretation by the client or server. Such processing is typically highly policy dependent and therefore specific to implementations.

このマッピングはいくつかのユースケースに対応することを意図していますが、クライアントやサーバーによる解釈を規定するものではありません。そのような処理は通常、ポリシーに大きく依存するため、実装固有のものです。

Operations on application objects are done via one or more of the existing EPP commands defined in the EPP domain name mapping [RFC5731]. Registries MAY choose to support a subset of the operations.

申請オブジェクトに対する操作は、EPPドメイン名マッピング[RFC5731]で定義されている既存のEPPコマンドの1つ以上を介して行われます。レジストリーは、それらの操作の一部だけをサポートすることを選択してもよいです（MAY）。

3.1. EPP <check> Command

3.1. EPP <check>コマンド

There are three forms of the extension to the EPP <check> command: the Claims Check Form (Section 3.1.1), the Availability Check Form (Section 3.1.2), and the Trademark Check Form (Section 3.1.3). The <launch:check> element "type" attribute defines the form, with the value of "claims" for the Claims Check Form (Section 3.1.1), "avail" for the Availability Check Form (Section 3.1.2), and "trademark" for the Trademark Check Form (Section 3.1.3). The default value of the "type" attribute is "claims". The forms supported by the server is determined by server policy. The server MUST return an EPP error result code of 2307 [RFC5730] if it receives a check form that is not supported.

EPP <check>コマンドに対する拡張には、クレーム確認形式（Claims Check Form、セクション3.1.1）、可用性確認形式（Availability Check Form、セクション3.1.2）、商標確認形式（Trademark Check Form、セクション3.1.3）の3つの形式があります。<launch:check>要素の「type」属性で形式を定義し、その値は、クレーム確認形式（セクション3.1.1）では「claims」、可用性確認形式（セクション3.1.2）では「avail」、商標確認形式（セクション3.1.3）では「trademark」です。「type」属性のデフォルト値は「claims」です。サーバーがサポートする形式は、サーバーポリシーによって決まります。サポートしていない確認形式を受信した場合、サーバーはEPPエラー結果コード2307 [RFC5730]を返さなければなりません（MUST）。

3.1.1. Claims Check Form

3.1.1. クレーム確認形式

The Claims Check Form defines a new command called the Claims Check Command that is used to determine whether or not there are any matching trademarks, in the specified launch phase, for each domain name passed in the command, that require the use of the "Claims Create Form" on a Domain Create Command. The availability check information defined in the EPP domain name mapping [RFC5731] MUST NOT be returned for the Claims Check Command. This form is the default form and MAY be explicitly identified by setting the <launch:check> "type" attribute to "claims".

クレーム確認形式は、クレーム確認コマンド（Claims Check Command）と呼ぶ新しいコマンドを定義します。このコマンドは、コマンドで渡された各ドメイン名について、指定されたローンチフェーズにおいて、ドメイン作成コマンド（Domain Create Command）で「クレーム作成形式（Claims Create Form）」の使用を必要とする一致する商標があるかどうかを判断するために使用されます。クレーム確認コマンドに対しては、EPPドメイン名マッピング[RFC5731]で定義されている可用性確認の情報を返してはなりません（MUST NOT）。この形式はデフォルトの形式であり、<launch:check>の「type」属性を「claims」に設定することで明示的に識別してもよいです（MAY）。

Instead of returning whether the domain name is available, the Claims Check Command will return whether or not at least one matching trademark exists for the domain name, which requires the use of the "Claims Create Form" on a Domain Create Command. If there is at least one matching trademark that exists for the domain name, a <launch:claimKey> element is returned. The client MAY then use the value of the <launch:claimKey> element to obtain information needed to generate the Trademark Claims Notice from the Trademark Validator based on the Validator Identifier (Section 2.2). The unique notice identifier of the Trademark Claims Notice MUST be passed in the <launch:noticeID> element of the extension to the Create Command (Section 3.3).

クレーム確認コマンドは、ドメイン名が利用可能かどうかを返す代わりに、ドメイン作成コマンドで「クレーム作成形式」の使用を必要とする一致する商標が、そのドメイン名に対して少なくとも1つ存在するかどうかを返します。ドメイン名に一致する商標が少なくとも1つ存在する場合は、<launch:claimKey>要素が返されます。その後クライアントは、<launch:claimKey>要素の値を使用して、検証者識別子（セクション2.2）に基づく商標検証者から、商標クレーム通知を生成するために必要な情報を取得してもよいです（MAY）。商標クレーム通知の一意な通知識別子は、作成コマンドに対する拡張（セクション3.3）の<launch:noticeID>要素で渡さなければなりません（MUST）。

The availability check information defined in the EPP domain name mapping [RFC5731] MUST NOT be returned for the Trademark Check Command. This form MUST be identified by setting the <launch:check> "type" attribute to "trademark".

商標確認形式は、商標確認コマンド（Trademark Check Command）と呼ぶ新しいコマンドを定義します。このコマンドは、サーバーのアクティブなローンチフェーズや、ドメイン作成コマンドで「クレーム作成形式」が必要かどうかとは無関係に、コマンドで渡された各ドメイン名に一致する商標があるかどうかを判断するために使用されます。商標確認コマンドに対しては、EPPドメイン名マッピング[RFC5731]で定義されている可用性確認の情報を返してはなりません（MUST NOT）。この形式は、<launch:check>の「type」属性を「trademark」に設定することで識別しなければなりません（MUST）。

3.3. EPP <create> Command

3.3. EPP <create>コマンド

There are four forms of the extension to the EPP <create> command that include the Sunrise Create Form (Section 3.3.1), the Claims Create Form (Section 3.3.2), the General Create Form (Section 3.3.3), and the Mixed Create Form (Section 3.3.4). The form used is dependent on the supported launch phases (Section 2.3) as defined below.

EPP <create>コマンドに対する拡張には、サンライズ作成形式（Sunrise Create Form、セクション3.3.1）、クレーム作成形式（Claims Create Form、セクション3.3.2）、一般作成形式（General Create Form、セクション3.3.3）、混合作成形式（Mixed Create Form、セクション3.3.4）の4つの形式があります。使用する形式は、次に定義するように、サポートされているローンチフェーズ（セクション2.3）に依存します。

sunrise:
The EPP <create> command with the "sunrise" launch phase is used to submit a registration with trademark information that can be verified by the server with the <domain:name> value. The Sunrise Create Form (Section 3.3.1) is used for the "sunrise" launch phase.
landrush:
The EPP <create> command with the "landrush" launch phase MAY use the General Create Form (Section 3.3.3) to explicitly specify the phase and optionally define the expected type of object to create.
claims:
The EPP <create> command with the "claims" launch phase is used to pass the information associated with the presentation and acceptance of the claims notice. The Claims Create Form (Section 3.3.2) is used, and the General Create Form (Section 3.3.3) MAY be used for the "claims" launch phase.
open:
The EPP <create> command with the "open" launch phase is undefined, but the form supported is up to server policy. The Claims Create Form (Section 3.3.2) MAY be used to pass the information associated with the presentation and acceptance of the claims notice if required for the domain name.
custom:
The EPP <create> command with the "custom" launch phase is undefined, but the form supported is up to server policy.
sunrise：
「sunrise」ローンチフェーズのEPP <create>コマンドは、サーバーが<domain:name>の値で検証できる商標情報を伴う登録を提出するために使用されます。「sunrise」ローンチフェーズには、サンライズ作成形式（セクション3.3.1）を使用します。
landrush：
「landrush」ローンチフェーズのEPP <create>コマンドは、フェーズを明示的に指定し、必要に応じて作成するオブジェクトの期待される種類を定義するために、一般作成形式（セクション3.3.3）を使用してもよいです（MAY）。
claims：
「claims」ローンチフェーズのEPP <create>コマンドは、クレーム通知の提示と承諾に関連する情報を渡すために使用されます。「claims」ローンチフェーズでは、クレーム作成形式（セクション3.3.2）を使用し、一般作成形式（セクション3.3.3）を使用してもよいです（MAY）。
open：
「open」ローンチフェーズのEPP <create>コマンドは定義されていませんが、サポートする形式はサーバーポリシー次第です。ドメイン名に必要な場合は、クレーム通知の提示と承諾に関連する情報を渡すために、クレーム作成形式（セクション3.3.2）を使用してもよいです（MAY）。
custom：
「custom」ローンチフェーズのEPP <create>コマンドは定義されていませんが、サポートする形式はサーバーポリシー次第です。

3.3.1. Sunrise Create Form

3.3.1. サンライズ作成形式

The Sunrise Create Form of the extension to the EPP domain name mapping [RFC5731] includes the verifiable trademark information that the server uses to match against the domain name to authorize the domain create. A server MUST support one of four models in Mark Validation Models (Section 2.6) to verify the trademark information passed by the client.

EPPドメイン名マッピング[RFC5731]に対する拡張のサンライズ作成形式には、ドメインの作成を認可するためにサーバーがドメイン名との照合に使用する、検証可能な商標情報が含まれます。サーバーは、クライアントから渡された商標情報を検証するために、マーク検証モデル（セクション2.6）の4つのモデルのいずれかをサポートしなければなりません（MUST）。

A <launch:create> element is sent along with the regular <create> domain command. The <launch:create> element has an OPTIONAL "type" attribute that defines the expected type of object ("application" or "registration") to create. The server SHOULD validate the "type" attribute, when passed, against the type of object that will be created, and return an EPP error result code of 2306 [RFC5730] if the type is incorrect. The <launch:create> element contains the following child elements:

<launch:create>要素は、通常の<create>ドメインコマンドとともに送信されます。<launch:create>要素には、作成するオブジェクトの期待される種類（「application」または「registration」）を定義する、選択可能な（OPTIONAL）「type」属性があります。「type」属性が渡された場合、サーバーはそれを作成されるオブジェクトの種類に対して検証すべきです（SHOULD）。種類が正しくない場合は、EPPエラー結果コード2306 [RFC5730]を返します。<launch:create>要素には、次の子要素が含まれます。

<launch:phase>:
The identifier for the launch phase. The server SHOULD validate the value according to Section 2.3.
<launch:codeMark> or <smd:signedMark> or <smd:encodedSignedMark>:
<launch:codeMark>:
Zero or more <launch:codeMark> elements. The <launch:codeMark> child elements are defined in "<launch:codeMark> Element" (Section 2.6.1).
<smd:signedMark>:
Zero or more <smd:signedMark> elements. The <smd:signedMark> child elements are defined in "<smd:signedMark> Element" (Section 2.6.3.1).
<smd:encodedSignedMark>:
Zero or more <smd:encodedSignedMark> elements. The <smd:encodedSignedMark> child elements are defined in "<smd:encodedSignedMark> Element" (Section 2.6.3.2).
<launch:phase>：
ローンチフェーズの識別子です。サーバーは、セクション2.3に従ってこの値を検証すべきです（SHOULD）。
<launch:codeMark>、<smd:signedMark>、または<smd:encodedSignedMark>：
<launch:codeMark>：
0個以上の<launch:codeMark>要素です。<launch:codeMark>の子要素は、「<launch:codeMark>要素」（セクション2.6.1）で定義しています。
<smd:signedMark>：
0個以上の<smd:signedMark>要素です。<smd:signedMark>の子要素は、「<smd:signedMark>要素」（セクション2.6.3.1）で定義しています。
<smd:encodedSignedMark>：
0個以上の<smd:encodedSignedMark>要素です。<smd:encodedSignedMark>の子要素は、「<smd:encodedSignedMark>要素」（セクション2.6.3.2）で定義しています。

3.5. EPP <delete> Command

3.5. EPP <delete>コマンド

This extension defines additional elements to extend the EPP <delete> command to be used in conjunction with the domain name mapping.

この拡張は、ドメイン名マッピングと組み合わせて使用する、EPP <delete>コマンドを拡張するための追加の要素を定義します。

A client MUST NOT pass the extension on an EPP <delete> command to a server that does not support Launch Applications. A server that does not support Launch Applications during its launch phase MUST return an EPP error result code of 2102 [RFC5730] when receiving an EPP <delete> command with the extension.

クライアントは、ローンチ申請をサポートしていないサーバーに対して、EPP <delete>コマンドでこの拡張を渡してはなりません（MUST NOT）。ローンチフェーズ中にローンチ申請をサポートしていないサーバーは、この拡張付きのEPP <delete>コマンドを受信したときに、EPPエラー結果コード2102 [RFC5730]を返さなければなりません（MUST）。

Registry policies permitting, clients MAY withdraw an application by submitting an EPP <delete> command along with a <launch:delete> element to indicate the application object to be deleted. The <launch:delete> element contains the following child elements:

レジストリーのポリシーが許す場合、クライアントは、削除する申請オブジェクトを示す<launch:delete>要素とともにEPP <delete>コマンドを送信することで、申請を取り下げてもよいです（MAY）。<launch:delete>要素には、次の子要素が含まれます。

<launch:phase>:
The phase during which the application was submitted or is associated with. The server SHOULD validate the value and return an EPP error result code of 2306 [RFC5730] if it is invalid.
<launch:applicationID>:
The application identifier for which the client wishes to delete.
<launch:phase>：
申請が提出されたフェーズ、またはそれが関連付けられているフェーズです。サーバーはこの値を検証すべきです（SHOULD）。値が無効な場合は、EPPエラー結果コード2306 [RFC5730]を返します。
<launch:applicationID>：
クライアントが削除したい申請の申請識別子です。

6. Security Considerations

6. セキュリティーに関する考慮事項

The mapping extensions described in this document do not provide any security services beyond those described by EPP [RFC5730], the EPP domain name mapping [RFC5731], and protocol layers used by EPP. The security considerations described in these other specifications apply to this specification as well.

この文書で説明するマッピング拡張は、EPP [RFC5730]、EPPドメイン名マッピング[RFC5731]、およびEPPが使用するプロトコル層で説明されているもの以上のセキュリティーサービスを提供しません。これらの他の仕様で説明されているセキュリティーに関する考慮事項は、この仕様にも適用されます。

Updates to, and deletion of, an application object MUST be restricted to clients authorized to perform the said operation on the object.

申請オブジェクトの更新と削除は、そのオブジェクトに対して当該操作を実行する権限を与えられたクライアントに制限しなければなりません（MUST）。

Information contained within an application, or even the mere fact that an application exists, may be confidential. Any attempt to operate on an application object by an unauthorized client MUST be rejected with an EPP 2201 (authorization error) return code. Server policy may allow an <info> operation with filtered output by clients other than the sponsoring client, in which case the <domain:infData> and <launch:infData> responses SHOULD be filtered to include only fields that are publicly accessible.

申請に含まれる情報や、申請が存在するという事実そのものでさえも、機密である場合があります。権限のないクライアントによる申請オブジェクトへの操作の試みは、すべてEPP 2201（認可エラー）の戻りコードで拒否しなければなりません（MUST）。サーバーポリシーによっては、スポンサークライアント以外のクライアントに対して、出力をフィルタリングした<info>操作を許可する場合があります。その場合、<domain:infData>と<launch:infData>のレスポンスは、公開されているフィールドだけを含むようにフィルタリングすべきです（SHOULD）。
