RFC 1722

RIP Version 2 Protocol Applicability Statement

RFC 1722

RIPバージョン2プロトコルの適用性声明

Abstract

概要

As required by Routing Protocol Criteria (RFC 1264), this report defines the applicability of the RIP-2 protocol within the Internet. This report is a prerequisite to advancing RIP-2 on the standards track.

ルーティングプロトコルの基準（Routing Protocol Criteria、RFC 1264）が求めるとおり、この報告書は、インターネットにおけるRIP-2プロトコルの適用性を定義します。この報告書は、RIP-2を標準化過程で前進させるための前提条件です。

Status of This Memo

このメモのステータス

This document specifies an Internet standards track protocol for the Internet community, and requests discussion and suggestions for improvements. Please refer to the current edition of the "Internet Official Protocol Standards" (STD 1) for the standardization state and status of this protocol. Distribution of this memo is unlimited.

この文書は、インターネットコミュニティーのためのインターネット標準化過程（Internet Standards Track）のプロトコルを規定し、改善のための議論と提案を求めるものです。このプロトコルの標準化の状態とステータスについては、「Internet Official Protocol Standards」（STD 1）の最新版を参照してください。このメモの配布は無制限です。

2. Introduction

2. はじめに

This report describes how RIP-2 may be useful within the Internet. In essence, the environments in which RIP-2 is the IGP of choice is a superset of the environments in which RIP-1, as defined in RFC 1058 [1], has traditionally been used. It is important to remember that RIP-2 is an extension to RIP-1; RIP-2 is not a new protocol. Thus, the operational aspects of distance-vector routing protocols, and RIP-1 in particular, within an autonomous system are well understood.

この報告書は、インターネットにおいてRIP-2がどのように役立ちうるかを説明します。要するに、RIP-2がIGPとして選ばれる環境は、RFC 1058[1]で定義されたRIP-1が従来使われてきた環境の上位集合です。RIP-2はRIP-1の拡張であり、新しいプロトコルではないことを覚えておくことが重要です。したがって、自律システム内での距離ベクトル型ルーティングプロトコル、特にRIP-1の運用面については、よく理解されています。

It should be noted that RIP-2 is not intended to be a substitute for OSPF in large autonomous systems; the restrictions on AS diameter and complexity which applied to RIP-1 also apply to RIP-2. Rather, RIP-2 allows the smaller, simpler, distance-vector protocol to be used in environments which require authentication or the use of variable length subnet masks, but are not of a size or complexity which require the use of the larger, more complex, link-state protocol.

RIP-2は、大規模な自律システムにおいてOSPFの代わりとなることを意図したものではないことに注意すべきです。RIP-1に適用されていたASの直径と複雑さに関する制約は、RIP-2にも適用されます。むしろRIP-2は、認証や可変長サブネットマスクの使用を必要とするものの、より大規模で複雑なリンクステート型プロトコルを必要とするほどの規模や複雑さはない環境で、より小さく単純な距離ベクトル型プロトコルを使えるようにするものです。

The remainder of this report describes how each of the extensions to RIP-1 may be used to increase the overall usefullness of RIP-2.

この報告書の残りの部分では、RIP-1に対する各拡張を使って、RIP-2の全体的な有用性をどのように高められるかを説明します。

3. Extension Applicability

3. 拡張の適用性

3.1. Subnet Masks

3.1. サブネットマスク

The original impetus behind the creation of RIP-2 was the desire to include subnet masks in the routing information exchanged by RIP. This was needed because subnetting was not defined when RIP was first created. As long as the subnet mask was fixed for a network, and well known by all the nodes on that network, a heuristic could be used to determine if a route was a subnet route or a host route. With the advent of variable length subnetting, CIDR, and supernetting, it was no longer possible for a heuristic to reasonably distinguish between network, subnet, and host routes.

RIP-2を作成したそもそもの動機は、RIPで交換されるルーティング情報にサブネットマスクを含めたいということでした。RIPが最初に作られたときにはサブネット化が定義されていなかったため、これが必要になりました。ネットワークのサブネットマスクが固定されていて、そのネットワーク上のすべてのノードによく知られている限りは、経路がサブネット経路なのかホスト経路なのかを判断するのにヒューリスティックを使えました。可変長サブネット化、CIDR、スーパーネット化が登場すると、ヒューリスティックでネットワーク経路、サブネット経路、ホスト経路を合理的に区別することはもはやできなくなりました。

By using the 32-bit field immediately following the IP address in a RIP routing entry, it became possible to positively identify a route's type. In fact, one could go so far as to say that the inclusion of the subnet mask effictively creates a 64-bit address which eliminates the network, subnet, host distinction.

RIPのルーティングエントリーでIPアドレスの直後にある32ビットのフィールドを使うことで、経路の種類を確実に識別できるようになりました。実際、サブネットマスクを含めることは、ネットワーク、サブネット、ホストの区別をなくす64ビットのアドレスを事実上作り出す、とまで言うこともできます。

Therefore, the inclusion of subnet masks in RIP-2 allows it to be used in an AS which requires precise knowledge of the subnet mask for a given route, but does not otherwise require OSPF.

したがって、RIP-2にサブネットマスクが含まれることにより、特定の経路のサブネットマスクを正確に知る必要はあるものの、それ以外にはOSPFを必要としないASでRIP-2を使えます。

3.2. Next Hop

3.2. ネクストホップ

The purpose of the Next Hop field is to eliminate packets being routed through extra hops in the system. It is particularly useful when RIP is not being run on all of the routers on a network. Consider the following example topology:

Next Hopフィールドの目的は、システム内でパケットが余分なホップを経由してルーティングされるのをなくすことです。これは、ネットワーク上のすべてのルーターでRIPが動作しているわけではない場合に特に役立ちます。次のトポロジーの例を考えてみます。

   -----   -----         -----   -----
   |IR1|   |IR2|         |XR1|   |XR2|
   --+--   --+--         --+--   --+--
     |       |             |       |
   --+-------+-------------+-------+--
     |--------RIP-2--------|

   -----   -----         -----   -----
   |IR1|   |IR2|         |XR1|   |XR2|
   --+--   --+--         --+--   --+--
     |       |             |       |
   --+-------+-------------+-------+--
     |--------RIP-2--------|

The Internal Routers (IR1 and IR2) are only running RIP-2. The External Routers (XR1 and XR2) are both running BGP, for example; however, only XR1 is running BGP and RIP-2. Since XR2 is not running RIP-2, the IRs will not know of its existance and will never use it as a next hop, even if it is a better next hop than XR1. Of course, XR1 knows this and can indicate, via the Next Hop field, that XR2 is the better next hop for some routes.

内部ルーター（IR1とIR2）ではRIP-2だけが動作しています。外部ルーター（XR1とXR2）ではどちらも、たとえばBGPが動作していますが、BGPとRIP-2の両方が動作しているのはXR1だけです。XR2ではRIP-2が動作していないため、IRはXR2の存在を知らず、たとえXR2がXR1よりも良いネクストホップであっても、XR2をネクストホップとして使うことはありません。もちろん、XR1はこのことを知っており、一部の経路についてはXR2のほうが良いネクストホップであることをNext Hopフィールドで示せます。

Another use for Next Hop has also been found. Consider the following example topology:

Next Hopの別の用途も見つかっています。次のトポロジーの例を考えてみます。

        -----
        |COR|
        -----
        /   \
       /     \
   -----     -----     -----
   |RO1|-----|RO2|=====| R |
   -----     -----     -----

        -----
        |COR|
        -----
        /   \
       /     \
   -----     -----     -----
   |RO1|-----|RO2|=====| R |
   -----     -----     -----

The three links between the Central Office Router (COR) and the Remote Office routers (RO1 and RO2) are all Dial-On-Demand (DOD) links. The link between RO2 and R is a fixed link. Once all of the routers have been initialized, the only routes they know about are the configured static routes for the DOD links. Assume that connections between COR and RO1, and COR and RO2 are established and RIP information is passing between the routers. RO1 will ignore COR's route to RO2 because it already has a better one; however, it will learn to reach R via COR.

本社ルーター（Central Office Router、COR）と支社ルーター（Remote Office router、RO1とRO2）の間の3つのリンクは、すべてダイヤルオンデマンド（DOD）リンクです。RO2とRの間のリンクは固定リンクです。すべてのルーターが初期化された時点では、ルーターが知っている経路は、DODリンク用に設定された静的経路だけです。CORとRO1の間、およびCORとRO2の間の接続が確立され、ルーター間でRIP情報がやり取りされているとします。RO1は、すでにより良い経路を持っているため、CORからのRO2への経路を無視しますが、COR経由でRに到達することを学習します。

If we assume that RO1 and RO2 are only capable of establishing one link at a time, then RO1 will not be able to reach RO2; however, RO1 will be able to reach R. Worse still, if we assume that traffic stops and the DOD links drop due to inactivity, an attempt by RO1 to reach R will trigger the dialing of two links (through COR). Of course, once RO1 establishes a link to RO2, the problem corrects itself because the new route to R is one hop shorter.

RO1とRO2が一度に1つのリンクしか確立できないとすると、RO1はRO2に到達できなくなりますが、Rには到達できます。さらに悪いことに、トラフィックが止まり、DODリンクが無通信により切断されたとすると、RO1がRに到達しようとすると、（COR経由で）2つのリンクのダイヤルが引き起こされます。もちろん、RO1がRO2へのリンクを確立すれば、Rへの新しい経路のほうが1ホップ短いため、この問題は自然に解消されます。

To correct this problem, the routers may use the Next Hop field to indicate their next hop. Consider the following route advertisements during the period described above (before the RO1/RO2 link has ever been established):

この問題を正すために、ルーターはNext Hopフィールドを使って自身のネクストホップを示すことができます。上で説明した期間（RO1/RO2リンクが一度も確立されていない間）における、次の経路広告を考えてみます。

Table 1

RO2 COR R 0 1
COR RO1 RO2 0 1

When R01 receives the two routes from COR, it will ignore the route for RO2, as mentioned above. However, since R is not in RO1's routing table, it will add it using a next hop of RO2 (because RO2 is directly connected, after a fashion). Note that COR does count itself in R's metric; this is less than accurate, but entirely safe and correctable (when the RO1/RO2 link comes up). Suppose, now, that the RO1/RO2 link did not exist. RO1 would ignore the specification of RO2 as the next hop to R and use COR, as it would if no Next Hop had been specified.

R01がCORから2つの経路を受信すると、前述のとおり、RO2への経路は無視します。しかし、RはRO1のルーティングテーブルにないため、RO1はRO2をネクストホップとしてその経路を追加します（RO2は、ある意味で直接接続されているからです）。CORはRのメトリックに自身を数えていることに注意してください。これは正確とは言えませんが、まったく安全であり、（RO1/RO2リンクが確立されたときに）修正できます。ここで、RO1/RO2リンクが存在しなかったとします。その場合、RO1はRへのネクストホップとしてRO2が指定されていることを無視し、Next Hopが指定されていなかった場合と同じようにCORを使います。

Note that this is not a recursive algorithm; it only works to eliminate a single extra hop from the path. There are methods by which this mechanism might be extended to include larger optimizations, but the potential to create routing loops has not been sufficiently analyzed to specify them here.

これは再帰的なアルゴリズムではないことに注意してください。これは、パスから余分なホップを1つだけ取り除くためにしか機能しません。この仕組みを拡張して、より大きな最適化を含める方法はありますが、ルーティングループを生じる可能性が十分に分析されていないため、ここでは規定しません。

3.3. Authentication

3.3. 認証

The need for authentication in a routing protocol is obvious. It is not usually important to conceal the information in the routing messages, but it is essential to prevent the insertion of bogus routing information into the routers. So, while the authentication mechanism specified in RIP-2 is less than ideal, it does prevent anyone who cannot directly access the network (i.e., someone who cannot sniff the routing packets to determine the password) from inserting bogus routing information.

ルーティングプロトコルにおける認証の必要性は明らかです。通常、ルーティングメッセージ内の情報を秘匿することは重要ではありませんが、偽のルーティング情報がルーターに挿入されるのを防ぐことは不可欠です。そのため、RIP-2で規定された認証の仕組みは理想的とは言えないものの、ネットワークに直接アクセスできない者（つまり、ルーティングパケットを盗聴してパスワードを割り出すことができない者）が偽のルーティング情報を挿入することは確かに防ぎます。

However, the specification does allow for additional types of authentication to be incorporated into the protocol. Unfortunately, because of the original format of RIP packets, the amount of space available for providing authentication information is only 16 octets.

とはいえ、この仕様では、追加の種類の認証をプロトコルに組み込むこともできます。残念ながら、RIPパケットの元のフォーマットのために、認証情報を提供するために使える領域は16オクテットしかありません。

3.4. Multicasting

3.4. マルチキャスト

The RIP-2 protocol provides for the IP multicasting of periodic advertisements. This feature was added to decrease the load on systems which do not support RIP-2. It also provides a mechanism whereby RIP-1 routers will never receive RIP-2 routes. This is a feature when correct use of an advertised route depends on knowing the precise subnet mask, which would be ignored by a RIP-1 router.

RIP-2プロトコルは、定期的な広告をIPマルチキャストで送ることを可能にしています。この機能は、RIP-2をサポートしないシステムの負荷を減らすために追加されました。また、RIP-1ルーターがRIP-2の経路を決して受信しないようにする仕組みも提供します。これは、広告された経路を正しく使うには正確なサブネットマスクを知る必要があるものの、RIP-1ルーターはそのサブネットマスクを無視してしまう場合に役立つ機能です。

4. Conclusion

4. 結論

Because the basic protocol is unchanged, RIP-2 is as correct a routing protocol as RIP-1. The enhancements make RIP-2 useful in environments which RIP-1 could not handle, but which do not necessitate the use of OSPF by virtue of requirements which RIP-2 does not satisfy.

基本的なプロトコルは変わっていないため、RIP-2はRIP-1と同程度に正しいルーティングプロトコルです。これらの拡張により、RIP-2は、RIP-1では対応できないものの、RIP-2が満たさない要件のためにOSPFを使う必要があるわけではない環境で役立つものになります。
