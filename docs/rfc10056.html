RFC 10056

Common YANG Data Types for Traffic Engineering

RFC 10056

トラフィックエンジニアリングのための共通YANGデータ型

Abstract

概要

This document defines a collection of commonly used Traffic Engineering (TE) specific data types, identities, and groupings in YANG data modeling language. These derived common data types, identities, and groupings are intended to be imported by other modules that model configuration and state for TE constructs, such as TE topologies, TE tunnels, TE policies, TE paths, TE Label Switched Paths (LSPs), and TE interfaces.

この文書は、トラフィックエンジニアリング（TE）に固有の、よく使われるデータ型、アイデンティティー、グルーピングの集合を、YANGデータモデリング言語で定義します。 これらの派生した共通のデータ型、アイデンティティー、グルーピングは、TEトポロジー、TEトンネル、TEポリシー、TEパス、TEラベルスイッチパス（LSP）、TEインターフェイスなどのTE構成要素の設定と状態をモデル化する他のモジュールによってインポートされることを意図しています。

This document obsoletes RFC 8776.

この文書はRFC 8776を廃止します。

1. Introduction

1. はじめに

YANG [RFC6020] [RFC7950] is a data modeling language used to model configuration data, state data, Remote Procedure Calls, and notifications for network management protocols such as the Network Configuration Protocol (NETCONF) [RFC6241] or RESTCONF [RFC8040]. The YANG language supports a small set of built-in data types and provides mechanisms to derive other types from the built-in types.

YANG[RFC6020][RFC7950]は、ネットワーク構成プロトコル（NETCONF）[RFC6241]やRESTCONF[RFC8040]などのネットワーク管理プロトコルのための設定データ、状態データ、リモートプロシージャーコール、通知をモデル化するために使われるデータモデリング言語です。YANG言語は少数の組み込みデータ型をサポートしており、組み込み型から他の型を派生させる仕組みを提供しています。

This document introduces a collection of commonly used Traffic Engineering (TE) data types derived from the built-in YANG data types. The derived data types, identities, and groupings form common definitions applicable to modeling TE features in models defined outside of this document. These derived common data types, identities, and groupings are intended to be imported by other modules that model TE constructs, such as TE topologies, TE tunnels, TE policies, TE paths, TE Label Switched Paths (LSPs), and TE interfaces. Nevertheless, these common definitions can be used by any other module per the guidance in Sections 4.12 and 4.13 of [RFC9907]. An importing module is not required to use all the definitions provided by the types module.

この文書は、YANGの組み込みデータ型から派生した、よく使われるトラフィックエンジニアリング（TE）のデータ型の集合を導入します。 派生したデータ型、アイデンティティー、グルーピングは、この文書の外で定義されるモデルにおいてTEの機能をモデル化する際に適用できる共通の定義を形成します。 これらの派生した共通のデータ型、アイデンティティー、グルーピングは、TEトポロジー、TEトンネル、TEポリシー、TEパス、TEラベルスイッチパス（LSP）、TEインターフェイスなどのTE構成要素をモデル化する他のモジュールによってインポートされることを意図しています。 とはいえ、これらの共通の定義は、[RFC9907]のセクション4.12と4.13のガイダンスに従って、他のどのモジュールからでも使用できます。 インポートするモジュールは、型モジュールが提供するすべての定義を使用する必要はありません。

Note: Some groupings defined in this document include "default" statements, contrary to the guidelines in Section 4.13 of [RFC9907]. This is due to the fact that they were already defined in [RFC8776] and removing "default" statements is not a backward compatible change, as defined in Section 11 of [RFC7950].

注：この文書で定義されている一部のグルーピングには、[RFC9907]のセクション4.13のガイドラインに反して、「default」ステートメントが含まれています。 これは、それらのグルーピングがすでに[RFC8776]で定義されており、「default」 ステートメントを削除することは、[RFC7950]のセクション11で定義されている後方互換性のある変更ではないためです。

This document adds new common data types, identities, and groupings to both the "ietf-te-types" and the "ietf-te-packet-types" YANG modules and obsoletes [RFC8776]. For further details, refer to Appendix B.

この文書は、「ietf-te-types」と「ietf-te-packet-types」の両方のYANGモジュールに新しい共通のデータ型、アイデンティティー、グルーピングを追加し、[RFC8776]を廃止します。詳細については、付録Bを参照してください。

3. Overview

3. 概要

This document defines two YANG modules for common TE types: "ietf-te-types" (Section 4) for TE generic types and "ietf-te-packet-types" (Section 5) for packet-specific types. Other technology-specific TE types are outside the scope of this document.

この文書は、共通のTE型のための2つのYANGモジュールを定義します。TEの汎用的な型のための「ietf-te-types」（セクション4）と、パケット固有の型のための「ietf-te-packet-types」（セクション5）です。その他の技術固有のTE型は、この文書の範囲外です。

3.1. TE Types Module Contents

3.1. TE型モジュールの内容

The "ietf-te-types" module (Section 4) contains TE types that are commonly used across multiple TE technology-specific modules.

「ietf-te-types」モジュール（セクション4）には、複数のTE技術固有のモジュールにわたって共通に使われるTE型が含まれています。

3.1.1. アイデンティティー

link-protection-type:

A base identity for supported link protection types as defined in [RFC4872].

restoration-scheme-type:

A base identity for supported LSP restoration schemes as defined in [RFC4872].

protection-external-commands:

A base identity for supported protection-related external commands used for troubleshooting purposes as defined in [RFC4872], [RFC6368], [RFC7271], and [RFC4427].

association-type:

A base identity for supported LSP association types as defined in [RFC6780], [RFC4872], [RFC4873], and [RFC8800].

objective-function-type:

A base identity for supported path objective functions as defined in [RFC5541].

te-tunnel-type:

A base identity for supported TE tunnel types as defined in [RFC3209] and [RFC4875].

lsp-encoding-types:

A base identity for supported LSP encoding types as defined in [RFC3471], [RFC4328], and [RFC6004]. These defined identities also include technology-specific LSP encoding types for backward compatibility with [RFC8776].

Additional technology-specific LSP encoding types can be defined in technology-specific modules.

lsp-protection-type:

A base identity for supported LSP protection types as defined in [RFC4872] and [RFC4873].

switching-capabilities:

A base identity for supported interface switching capabilities as defined in [RFC3471], [RFC6002], [RFC6004], [RFC7074], and [RFC7138]. These defined identities also include technology-specific interface switching capabilities for backward compatibility with [RFC8776].

Additional technology-specific interface switching capabilities can be defined in technology-specific modules.

resource-affinities-type:

A base identity for supported attribute filters associated with a tunnel that must be satisfied for a link to be acceptable as defined in [RFC3209] and [RFC2702].

path-metric-type:

A base identity for supported path metric types as defined in [RFC3630], [RFC3785], [RFC5440], [RFC7471], [RFC8233], [RFC8570], and [RFC9933].

The unit of the path metric value is interpreted in the context of the path metric type. The derived identities MUST describe the unit and maximum value of the path metric types they define.

For example, the measurement unit is not applicable for the number of hops metric ('path-metric-hop'). Conversely, the bound of the 'path-metric-loss', defined in "ietf-te-packet-types", is defined in multiples of the basic unit 0.000003% as described in [RFC7471] and [RFC8570].

lsp-provisioning-error-reason:

A base identity for indicating LSP provisioning error reasons. No standard LSP provisioning error reasons are defined in this document.

path-computation-error-reason:

A base identity for indicating path computation error reasons as defined in Section 3.1.1.1.

protocol-origin-type:

A base identity for the type of protocol origin as defined in Section 3.1.1.2.

svec-objective-function-type:

A base identity for supported Synchronization Vector (SVEC) objective functions as defined in [RFC5541], [RFC8685], and [RFC8880].

svec-metric-type:

A base identity for supported SVEC metric types as defined in [RFC5541].

path-attribute-flags:

サポートされるLSPパスフラグのための基底アイデンティティーです。これらのフラグは[RFC3209]、[RFC4090]、[RFC4736]、[RFC5712]、[RFC4920]、[RFC5420]、[RFC7570]、[RFC4875]、[RFC5151]、[RFC5150]、[RFC6001]、[RFC6790]、[RFC7260]、[RFC8001]、[RFC8149]、[RFC8169]で定義されています。

link-protection-type:

[RFC4872]で定義されている、サポートされるリンク保護タイプのための基底アイデンティティーです。

restoration-scheme-type:

[RFC4872]で定義されている、サポートされるLSP復元方式のための基底アイデンティティーです。

protection-external-commands:

トラブルシューティングの目的で使われる、サポートされる保護関連の外部コマンドのための基底アイデンティティーです。これらのコマンドは[RFC4872]、[RFC6368]、[RFC7271]、[RFC4427]で定義されています。

association-type:

サポートされるLSPアソシエーションタイプのための基底アイデンティティーです。これらのタイプは[RFC6780]、[RFC4872]、[RFC4873]、[RFC8800]で定義されています。

objective-function-type:

[RFC5541]で定義されている、サポートされるパス計算の目的関数のための基底アイデンティティーです。

te-tunnel-type:

[RFC3209]と[RFC4875]で定義されている、サポートされるTEトンネルタイプのための基底アイデンティティーです。

lsp-encoding-types:

[RFC3471]、[RFC4328]、[RFC6004]で定義されている、サポートされるLSPエンコーディングタイプのための基底アイデンティティーです。これらの定義済みのアイデンティティーには、[RFC8776]との後方互換性のために、技術固有のLSPエンコーディングタイプも含まれています。

追加の技術固有のLSPエンコーディングタイプは、技術固有のモジュールで定義できます。

lsp-protection-type:

[RFC4872]と[RFC4873]で定義されている、サポートされるLSP保護タイプのための基底アイデンティティーです。

switching-capabilities:

サポートされるインターフェイススイッチング能力のための基底アイデンティティーです。これらの能力は[RFC3471]、[RFC6002]、[RFC6004]、[RFC7074]、[RFC7138]で定義されています。これらの定義済みのアイデンティティーには、[RFC8776]との後方互換性のために、技術固有のインターフェイススイッチング能力も含まれています。

追加の技術固有のインターフェイススイッチング能力は、技術固有のモジュールで定義できます。

resource-affinities-type:

[RFC3209]と[RFC2702]で定義されている、リンクが受け入れ可能であるために満たされなければならない、トンネルに関連付けられたサポートされる属性フィルターのための基底アイデンティティーです。

path-metric-type:

サポートされるパスメトリックタイプのための基底アイデンティティーです。これらのタイプは[RFC3630]、[RFC3785]、[RFC5440]、[RFC7471]、[RFC8233]、[RFC8570]、[RFC9933]で定義されています。

パスメトリック値の単位は、パスメトリックタイプのコンテキストで解釈されます。派生アイデンティティーは、それが定義するパスメトリックタイプの単位と最大値を記述しなければなりません（MUST）。

lsp-provisioning-error-reason:

LSPのプロビジョニングエラーの理由を示すための基底アイデンティティーです。この文書では、標準のLSPプロビジョニングエラーの理由は定義しません。

path-computation-error-reason:

セクション3.1.1.1で定義されている、パス計算エラーの理由を示すための基底アイデンティティーです。

protocol-origin-type:

セクション3.1.1.2で定義されている、プロトコルオリジンのタイプのための基底アイデンティティーです。

svec-objective-function-type:

[RFC5541]、[RFC8685]、[RFC8880]で定義されている、サポートされる同期ベクトル（Synchronization Vector: SVEC）の目的関数のための基底アイデンティティーです。

svec-metric-type:

[RFC5541]で定義されている、サポートされるSVECメトリックタイプのための基底アイデンティティーです。

3.1.1.1. Path Computation Errors
3.1.1.1. パス計算エラー

The "ietf-te-types" module contains the YANG reusable identities for indicating path computation error reasons as defined in [RFC5440], [RFC5441], [RFC5520], [RFC5557], [RFC8306], and [RFC8685].

「ietf-te-types」モジュールには、パス計算エラーの理由を示すための再利用可能なYANGアイデンティティーが含まれています。これらの理由は[RFC5440]、[RFC5441]、[RFC5520]、[RFC5557]、[RFC8306]、[RFC8685]で定義されています。

It also defines the following additional YANG reusable identities for indicating the following path computation error reasons:

また、次のパス計算エラーの理由を示すための、追加の再利用可能なYANGアイデンティティーも定義しています。

path-computation-error-no-topology:

A base identity for indicating the path computation error when there is no topology with the provided topology identifier.

path-computation-error-no-dependent-server:

A base identity for indicating the path computation error when one or more dependent path computation servers are unavailable.

The dependent path computation server could be a Backward-Recursive PCE-based Computation (BRPC) downstream PCE, as defined in [RFC5441], or a child PCE, as defined in [RFC8685].

path-computation-error-no-topology:

指定されたトポロジー識別子を持つトポロジーが存在しない場合のパス計算エラーを示すための基底アイデンティティーです。

path-computation-error-no-dependent-server:

1つ以上の依存するパス計算サーバーが利用できない場合のパス計算エラーを示すための基底アイデンティティーです。

依存するパス計算サーバーは、[RFC5441]で定義されている後方再帰PCEベース計算（Backward-Recursive PCE-based Computation: BRPC）の下流PCEである場合もあれば、[RFC8685]で定義されている子PCEである場合もあります。

The derived identities are defined in the "ietf-te-types" module, instead of an IANA-maintained module, because of error reasons that:

派生アイデンティティーは、IANAが管理するモジュールではなく「ietf-te-types」モジュールで定義されています。これは、エラーの理由が次のようなものであるためです。

  1. are applicable only to the TE YANG modules and not to Path Computation Element Communication Protocol (PCEP) environments (e.g., path-computation-error-no-topology);

  2. are technology-specific, which are better defined in technology-specific YANG modules;

  3. match more than one PCEP number in order to hide the details of the underlay PCE architecture (e.g., path-computation-error-no-dependent-server).

  1. TE YANGモジュールにのみ適用でき、パス計算要素通信プロトコル（PCEP）の環境には適用できないもの（たとえば、path-computation-error-no-topology）

  2. 技術固有であり、技術固有のYANGモジュールで定義するほうがよいもの

  3. アンダーレイのPCEアーキテクチャーの詳細を隠すために、複数のPCEPの番号に対応するもの（たとえば、path-computation-error-no-dependent-server）

In addition to identities for protocols like PCEP [RFC5440] and BGP [RFC9012], the module defines the following identity for tunnels created via an Application Programming Interface (API):

プロトコルオリジンは、コントローラーがTEトンネルをインスタンス化するために使用するプロトコルまたは仕組みを識別します。 これをモデル化するために、「ietf-te-types」モジュールは再利用可能なYANGアイデンティティーの集合を提供します。 このモジュールは、PCEP[RFC5440]やBGP[RFC9012]などのプロトコルのためのアイデンティティーに加えて、アプリケーションプログラミングインターフェイス（API）を介して作成されたトンネルのための次のアイデンティティーを定義します。

protocol-origin-api:

protocol-origin-api:

3.1.2. Data Types

3.1.2. データ型

The "ietf-te-types" module contains the following YANG reusable data types:

「ietf-te-types」モジュールには、次の再利用可能なYANGデータ型が含まれています。

te-ds-class:

A type representing the Differentiated Services (DS) Class-Type of traffic as defined in [RFC4124].

te-label-direction:

An enumerated type for specifying the forward or reverse direction of a label.

te-hop-type:

An enumerated type for specifying that a hop is loose or strict.

te-global-id:

A type representing the identifier that uniquely identifies an operator, which can be either a provider or a client. The definition of this type is taken from Section 3 of [RFC6370] and Section 3 of [RFC5003]. This attribute type is used solely to provide a globally unique context for TE topologies.

te-node-id:

A type representing the identifier for a node in a TE topology. The identifier is represented either as 4 octets in dotted-quad notation or as 16 octets in an IPv6 address notation [RFC5952].

This attribute MAY be mapped to the Router Address TLV described in Section 2.4.1 of [RFC3630], the TE Router ID described in Section 6.2 of [RFC6827], the TE Router ID TLV described in Section 4.3 of [RFC5305], or the TE Router ID TLV described in Section 3.2.1 of [RFC6119].

The reachability of such a TE node MAY be achieved by a mechanism such as that described in Section 6.2 of [RFC6827].

te-topology-id:

A type representing the identifier for a topology. It is optional to have one or more prefixes at the beginning, separated by colons. The prefixes can be "network-types" as defined in the "ietf-network" module in [RFC8345], to help the user better understand the topology before further inquiry is made.

te-tp-id:

A type representing the identifier of a TE interface Link Termination Point (LTP) on a specific TE node where the TE link connects. This attribute is mapped to a local or remote link identifier [RFC3630] [RFC5305].

te-path-disjointness:

A type representing the different resource disjointness options for a TE tunnel path as defined in [RFC4872].

admin-groups:

A union type for a TE link's classic administrative groups, as defined in [RFC3630] and [RFC5305], or extended administrative groups, as defined in [RFC7308].

srlg:

A type representing the SRLG as defined in [RFC4203] and [RFC5307].

te-metric:

A type representing the TE metric as defined in [RFC3785].

te-recovery-status:

An enumerated type for the different status of a recovery action as defined in [RFC6378] and [RFC4427].

te-link-access-type:

An enumerated type for the different TE link access types as defined in [RFC3630].

te-ds-class:

[RFC4124]で定義されている、トラフィックの差別化サービス（DS）クラスタイプ（Class-Type）を表す型です。

te-label-direction:

ラベルの順方向または逆方向を指定するための列挙型です。

te-hop-type:

ホップがルーズ（loose）かストリクト（strict）かを指定するための列挙型です。

te-global-id:

運用者（プロバイダーまたはクライアントのいずれか）を一意に識別する識別子を表す型です。この型の定義は[RFC6370]のセクション3と[RFC5003]のセクション3から引用しています。この属性型は、TEトポロジーにグローバルに一意なコンテキストを提供するためだけに使われます。

te-node-id:

TEトポロジー内のノードの識別子を表す型です。識別子は、ドット区切りの4オクテットの表記、またはIPv6アドレス表記[RFC5952]の16オクテットのいずれかで表されます。

この属性は、[RFC3630]のセクション2.4.1で説明されているRouter Address TLV、[RFC6827]のセクション6.2で説明されているTE Router ID、[RFC5305]のセクション4.3で説明されているTE Router ID TLV、または[RFC6119]のセクション3.2.1で説明されているTE Router ID TLVにマッピングしてもよいです（MAY）。

そのようなTEノードの到達可能性は、[RFC6827]のセクション6.2で説明されているような仕組みによって実現してもよいです（MAY）。

te-topology-id:

トポロジーの識別子を表す型です。先頭にコロンで区切られた1つ以上のプレフィックスを付けることは任意です。プレフィックスには、さらなる問い合わせを行う前にユーザーがトポロジーをよりよく理解できるように、[RFC8345]の「ietf-network」モジュールで定義されている「network-types」を使用できます。

te-tp-id:

TEリンクが接続する特定のTEノード上の、TEインターフェイスのリンク終端点（Link Termination Point: LTP）の識別子を表す型です。この属性は、ローカルまたはリモートのリンク識別子[RFC3630][RFC5305]にマッピングされます。

te-path-disjointness:

[RFC4872]で定義されている、TEトンネルのパスに対するさまざまなリソース非共有（disjointness）のオプションを表す型です。

admin-groups:

TEリンクの、[RFC3630]と[RFC5305]で定義されている従来型の管理グループ、または[RFC7308]で定義されている拡張管理グループのためのunion型です。

srlg:

[RFC4203]と[RFC5307]で定義されているSRLGを表す型です。

te-metric:

[RFC3785]で定義されているTEメトリックを表す型です。

te-recovery-status:

[RFC6378]と[RFC4427]で定義されている、回復動作のさまざまなステータスのための列挙型です。

te-link-access-type:

[RFC3630]で定義されている、さまざまなTEリンクアクセスタイプのための列挙型です。

7. Security Considerations

7. セキュリティーに関する考慮事項

This section is modeled after the template described in Section 3.7.1 of [RFC9907].

このセクションは、[RFC9907]のセクション3.7.1で説明されているテンプレートに基づいています。

The "ietf-te-types" and the "ietf-te-packet-types" YANG modules define data models that are designed to be accessed via YANG-based management protocols, such as Network Configuration Protocol (NETCONF) [RFC6241] and RESTCONF [RFC8040]. These YANG-based management protocols (1) have to use a secure transport layer (e.g., Secure Shell (SSH) [RFC4252], TLS [RFC9846], and QUIC [RFC9000]) and (2) have to use mutual authentication.

「ietf-te-types」と「ietf-te-packet-types」のYANGモジュールは、ネットワーク構成プロトコル（NETCONF）[RFC6241]やRESTCONF[RFC8040]などのYANGベースの管理プロトコルを介してアクセスされるように設計されたデータモデルを定義します。 これらのYANGベースの管理プロトコルは、（1）安全なトランスポート層（たとえば、セキュアシェル（SSH）[RFC4252]、TLS[RFC9846]、QUIC[RFC9000]）を使用する必要があり、（2）相互認証を使用する必要があります。

The Network Configuration Access Control Model (NACM) [RFC8341] provides the means to restrict access for particular NETCONF or RESTCONF users to a preconfigured subset of all available NETCONF or RESTCONF protocol operations and content.

ネットワーク構成アクセス制御モデル（NACM）[RFC8341]は、特定のNETCONFまたはRESTCONFのユーザーのアクセスを、利用可能なすべてのNETCONFまたはRESTCONFのプロトコル操作とコンテンツのうち、事前に設定されたサブセットに制限する手段を提供します。

The YANG modules define a set of identities, types, and groupings. These nodes are intended to be reused by other YANG modules. The modules by themselves do not expose any data nodes that are writable, data nodes that contain read-only state, or RPCs. As such, there are no additional security issues related to the YANG modules that need to be considered.

これらのYANGモジュールは、アイデンティティー、型、グルーピングの集合を定義します。 これらのノードは、他のYANGモジュールで再利用されることを意図しています。 これらのモジュール自体は、書き込み可能なデータノード、読み取り専用の状態を含むデータノード、RPCのいずれも公開しません。 そのため、これらのYANGモジュールに関連して考慮する必要のある追加のセキュリティー上の問題はありません。

Modules that use the groupings that are defined in this document should identify the corresponding security considerations. For example, using 'explicit-route-hop', 'record-route-state' or 'te-topology-identifier' (which includes the 'client-id') groupings may expose sensitive topology information.

この文書で定義されているグルーピングを使用するモジュールは、対応するセキュリティーに関する考慮事項を明らかにすべきです。 たとえば、'explicit-route-hop'、'record-route-state'、'te-topology-identifier'（'client-id'を含む）のグルーピングを使用すると、機密性の高いトポロジー情報が公開される可能性があります。

      このコンテナーの名前は'explicit-route-objects'に変更されました。このグルーピングは既存のIETF RFCで定義されているどのYANGデータモデルでもまだ使われていないため、この変更はIETF標準のYANGデータモデルには影響しません。

  • generic-path-metric-bounds;

    [RFC8776]ですでに定義されている次のリーフが、'optimization-metric-entry'グルーピングで更新されました。

    • metric-type;

      基底アイデンティティーは次のように更新されました。

      • 許可される派生アイデンティティーの集合を増やす

      • この集合から'path-metric-optimize-includes'と'path-metric-optimize-excludes'のアイデンティティーを取り除く（バグ修正）

  • generic-path-optimization;

    'generic-path-optimization'グルーピングに、次の新しいリーフが追加されました。

    • tiebreaker.

    [RFC8776]ですでに定義されている次のコンテナーは非推奨になりました。

    • tiebreakers.

The following identities, already defined in [RFC8776], have been obsoleted in the "ietf-te-types" module for bug fixing:

[RFC8776]ですでに定義されている次のアイデンティティーは、バグ修正のために「ietf-te-types」モジュールで廃止されました。

  • of-minimize-agg-bandwidth-consumption (the 'svec-of-minimize-agg-bandwidth-consumption' identity should be used instead);

  • of-minimize-load-most-loaded-link (the 'svec-of-minimize-load-most-loaded-link' identity should be used instead);

  • of-minimize-cost-path-set (the 'svec-of-minimize-cost-path-set' identity should be used instead);

  • lsp-protection-reroute-extra (the 'restoration-scheme-rerouting' identity should be used instead);

  • lsp-protection-reroute (the 'restoration-scheme-rerouting' identity should be used instead).

  • of-minimize-agg-bandwidth-consumption（代わりに'svec-of-minimize-agg-bandwidth-consumption'アイデンティティーを使用すべきです）

  • of-minimize-load-most-loaded-link（代わりに'svec-of-minimize-load-most-loaded-link'アイデンティティーを使用すべきです）

  • of-minimize-cost-path-set（代わりに'svec-of-minimize-cost-path-set'アイデンティティーを使用すべきです）
