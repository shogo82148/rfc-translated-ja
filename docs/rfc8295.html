EST (Enrollment over Secure Transport) Extensions

RFC 8295

EST（Enrollment over Secure Transport）の拡張

Abstract

概要

The EST (Enrollment over Secure Transport) protocol defines the Well-Known URI (Uniform Resource Identifier) -- /.well-known/est -- along with a number of other path components that clients use for PKI (Public Key Infrastructure) services, namely certificate enrollment (e.g., /simpleenroll). This document defines a number of other PKI services as additional path components -- specifically, firmware and trust anchors as well as symmetric, asymmetric, and encrypted keys. This document also specifies the PAL (Package Availability List), which is an XML (Extensible Markup Language) file or JSON (JavaScript Object Notation) object that clients use to retrieve packages available and authorized for them. This document extends the EST server path components to provide these additional services.

EST（Enrollment over Secure Transport）プロトコルは、ウェルノウンURI（Uniform Resource Identifier）である/.well-known/estと、クライアントがPKI（公開鍵基盤）サービス、すなわち証明書の登録（例: /simpleenroll）に使用するいくつかの他のパスコンポーネントを定義しています。この文書は、その他のいくつかのPKIサービスを追加のパスコンポーネントとして定義します。具体的には、ファームウェアとトラストアンカー、そして対称鍵、非対称鍵、暗号化された鍵です。この文書はまた、PAL（パッケージ可用性リスト、Package Availability List）も規定します。PALは、クライアントが自身に対して利用可能かつ認可されたパッケージを取得するために使用するXML（Extensible Markup Language）ファイルまたはJSON（JavaScript Object Notation）オブジェクトです。この文書は、これらの追加サービスを提供するためにESTサーバーのパスコンポーネントを拡張します。

1. Introduction

1. はじめに

The EST (Enrollment over Secure Transport) protocol [RFC7030] defines the Well-Known URI (Uniform Resource Identifier) -- /.well-known/est -- to support selected services related to the PKI (Public Key Infrastructure), with such PCs (path components) as simple enrollment with /simpleenroll, rekey or renew with /simplereenroll, etc. A server that wishes to support additional PKI-related services and other security-related packages could use the same .well-known URI by defining additional PCs. This document defines six such PCs:

EST（Enrollment over Secure Transport）プロトコル[RFC7030]は、PKI（公開鍵基盤）に関連する特定のサービスをサポートするために、ウェルノウンURI（Uniform Resource Identifier）である/.well-known/estを定義しており、/simpleenrollによる単純な登録、/simplereenrollによる鍵の再生成または更新などのPC（パスコンポーネント）を備えています。PKI関連の追加サービスやその他のセキュリティー関連のパッケージをサポートしたいサーバーは、追加のPCを定義することで、同じ.well-known URIを使用できます。この文書は、そのようなPCを6つ定義します。

  • /pal - The PAL (Package Availability List) provides a list of all known packages available and authorized for a client. By accessing the service provided by this PC first, the client can walk through the PAL and download all the packages necessary to begin operating securely. The PAL essentially points to other PCs, including the PCs defined in this document as well as those defined in [RFC7030] (e.g., /cacerts, /simpleenroll, /simplereenroll, /fullcmc, /serverkeygen, and /csrattrs). The /pal PC is described in Section 2.
  • /eecerts - EE (End-Entity) certificates [RFC5280] are needed by the client when they invoke a security protocol for communicating with a peer (i.e., they become operational and do something meaningful as opposed to just communicating with the infrastructure). If the infrastructure knows the certificate(s) needed by the client, then providing the peer's certificate avoids the client having to discover the peer's certificate. This service is not meant to be a general-purpose repository to which clients query a "repository" and then get a response; this is purely a push mechanism. The /eecerts PC is described in Section 3.
  • /crls - CRLs (Certificate Revocation Lists) and ARLs (Authority Revocation Lists) [RFC5280] are also needed by the client when they validate certificate paths. CRLs (and ARLs) from TAs (Trust Anchors) and intermediate CAs (Certification Authorities) are needed to validate the certificates used to generate the client's certificate or the peer's certificate, which is provided by the /eecerts PC, and providing them saves the client from having to "discover" them and then retrieve them. CRL "discovery" is greatly aided by the inclusion of the CRL Distribution Point certificate extension [RFC5280], but this extension is not always present in certificates and requires another connection to retrieve them. Like the /eecerts PC, this service is not meant to be a general-purpose repository to which clients query a repository and then get a response; this is purely a push mechanism. The /crls PC is described in Section 4.
  • /symmetrickeys - In some cases, clients use symmetric keys [RFC6031] when communicating with their peers. If the client's peers are known by the server a priori, then providing them saves the client or an administrator from later having to find, retrieve, and install them. Like the /eecerts and /crls PCs, this service is not meant to be a general-purpose repository to which clients query a repository and then get a response; this is purely a push mechanism for the keys themselves. However, things do not always go as planned, and clients need to inform the server about any errors. If things did go well, then the client, if requested, needs to provide a receipt [RFC7191]. The /symmetrickeys and /symmetrickeys/return PCs are described in Section 5.
  • /firmware - Some client firmware and software support automatic update mechanisms, and some do not. For those that do not, the /firmware PC provides a mechanism for the infrastructure to inform the client that firmware and software updates [RFC4108] are available. Because updates do not always go as planned and because sometimes the server needs to know whether the firmware was received and processed, this PC also provides a mechanism to return errors and receipts. The /firmware and /firmware/return PCs are defined in Section 6.
  • /tamp - To control the TAs in client TA databases, servers use the /tamp PC to request that clients retrieve TAMP (Trust Anchor Management Protocol) query, update, and adjust packages [RFC5934], and clients use the /tamp/return PC to return TAMP responses, confirms, and errors [RFC5934]. The /tamp and /tamp/return PCs are defined in Section 7.
  • /pal - PAL（パッケージ可用性リスト、Package Availability List）は、クライアントに対して利用可能かつ認可された既知のすべてのパッケージの一覧を提供します。このPCが提供するサービスに最初にアクセスすることで、クライアントはPALをたどり、安全に運用を開始するために必要なすべてのパッケージをダウンロードできます。PALは本質的に他のPCを指し示すものであり、それにはこの文書で定義するPCと、[RFC7030]で定義されているPC（例: /cacerts、/simpleenroll、/simplereenroll、/fullcmc、/serverkeygen、/csrattrs）が含まれます。/pal PCについてはセクション2で説明します。
  • /eecerts - EE（エンドエンティティー、End-Entity）証明書[RFC5280]は、クライアントがピアと通信するためにセキュリティープロトコルを起動するとき（つまり、単にインフラストラクチャーと通信するだけでなく、運用状態に入って何か意味のあることを行うとき）に、クライアントが必要とするものです。クライアントが必要とする証明書をインフラストラクチャーが知っている場合、ピアの証明書を提供することで、クライアントがピアの証明書を探し出す必要がなくなります。このサービスは、クライアントが「リポジトリー」に問い合わせてレスポンスを得るような汎用のリポジトリーを意図したものではありません。これは純粋にプッシュメカニズムです。/eecerts PCについてはセクション3で説明します。
  • /crls - CRL（証明書失効リスト、Certificate Revocation List）とARL（認証局失効リスト、Authority Revocation List）[RFC5280]も、クライアントが証明書パスを検証するときに必要とするものです。TA（トラストアンカー）や中間CA（認証局）のCRL（およびARL）は、クライアントの証明書や、/eecerts PCによって提供されるピアの証明書を生成するために使用された証明書を検証するために必要です。それらを提供することで、クライアントはそれらを「探し出し」てから取得する手間を省けます。CRLの「探索」は、CRL配布ポイント（CRL Distribution Point）証明書拡張[RFC5280]が含まれていれば大いに助けられますが、この拡張は常に証明書に存在するとは限らず、またそれらを取得するために別の接続が必要になります。/eecerts PCと同様に、このサービスは、クライアントがリポジトリーに問い合わせてレスポンスを得るような汎用のリポジトリーを意図したものではありません。これは純粋にプッシュメカニズムです。/crls PCについてはセクション4で説明します。
  • /symmetrickeys - 場合によっては、クライアントはピアと通信する際に対称鍵[RFC6031]を使用します。クライアントのピアをサーバーが事前に知っている場合、サーバーがその対称鍵を提供することで、クライアントや管理者が後でそれらを探し、取得し、インストールする手間を省けます。/eecerts PCや/crls PCと同様に、このサービスは、クライアントがリポジトリーに問い合わせてレスポンスを得るような汎用のリポジトリーを意図したものではありません。これは鍵そのものについての純粋なプッシュメカニズムです。しかし、物事が常に計画どおりに進むとは限らず、クライアントはエラーがあればサーバーに通知する必要があります。うまくいった場合は、要求されていれば、クライアントは受領証[RFC7191]を提供する必要があります。/symmetrickeys PCと/symmetrickeys/return PCについてはセクション5で説明します。
  • /firmware - クライアントのファームウェアやソフトウェアには、自動更新メカニズムをサポートしているものもあれば、そうでないものもあります。サポートしていないものに対しては、/firmware PCが、ファームウェアやソフトウェアの更新[RFC4108]が利用可能であることをインフラストラクチャーがクライアントに通知するためのメカニズムを提供します。更新は常に計画どおりに進むとは限らず、またサーバーがファームウェアが受信され処理されたかどうかを知る必要がある場合もあるため、このPCはエラーと受領証を返すためのメカニズムも提供します。/firmware PCと/firmware/return PCはセクション6で定義します。
  • /tamp - クライアントのTAデータベース内のTAを制御するために、サーバーは/tamp PCを使用して、クライアントがTAMP（トラストアンカー管理プロトコル、Trust Anchor Management Protocol）のクエリー、更新、調整のパッケージ[RFC5934]を取得するよう要求し、クライアントは/tamp/return PCを使用して、TAMPのレスポンス、確認（confirm）、エラー[RFC5934]を返します。/tamp PCと/tamp/return PCはセクション7で定義します。

This document also extends the /est/serverkeygen PC [RFC7030] to support the following (see Section 8):

この文書はまた、次のことをサポートするために/est/serverkeygen PC[RFC7030]を拡張します（セクション8を参照）。

  • Returning asymmetric key package receipts and errors [RFC7191].
  • Encapsulating returned asymmetric keys in additional CMS (Cryptographic Message Syntax) content types [RFC7193].
  • Returning server-generated public key pairs encapsulated in PKCS #12 (Public Key Cryptography Standard #12) [RFC7292].
  • 非対称鍵パッケージの受領証とエラー[RFC7191]を返すこと。
  • 返される非対称鍵を、追加のCMS（暗号メッセージ構文、Cryptographic Message Syntax）コンテンツタイプ[RFC7193]にカプセル化すること。
  • サーバーが生成した公開鍵ペアを、PKCS #12（Public Key Cryptography Standard #12）[RFC7292]にカプセル化して返すこと。

While the motivation is to provide packages to clients during enrollment so that they can perform securely after enrollment, the services defined in this specification can be used after enrollment.

動機は、登録の後にクライアントが安全に動作できるよう、登録の間にクライアントにパッケージを提供することにありますが、この仕様で定義するサービスは登録の後にも使用できます。

In addition to the definitions found in [RFC7030], the following definitions are used in this document:

[RFC7030]にある定義に加えて、この文書では次の定義を使用します。

Agent:
An entity that performs functions on behalf of a client. Agents can service a) one or more clients on the same network as the server, b) clients on non-IP-based networks, or c) clients that have a non-electronic air gap [RFC4949] between themselves and the server. Interactions between the agent and client in the last two cases are beyond the scope of this document. Before an agent can service clients, the agent must have a trust relationship with the server (i.e., be authorized to act on behalf of clients).
Client:
A device that ultimately consumes and uses the packages to enable communications. In other words, the client is the endpoint for the packages, and an agent may have one or more clients. To avoid confusion, this document henceforth uses the term "client" to refer to both agents and clients.
Package:

An object that contains one or more content types. There are numerous types of packages, e.g., packages for asymmetric keys, symmetric keys, encrypted keys, CRLs, firmware, and TAMP. See Section 2.1.1. All of these packages are digitally signed by their creator and encapsulated in a CMS signed-data [RFC5652] [RFC6268] (except the public key certificates and CRLs that are already digitally signed by a CA): firmware receipts and errors; TAMP responses, confirms, and errors; and "key package" receipts and errors that can be optionally signed. Certificates and CRLs are included in a package that uses signed-data, which is often referred to as a "degenerate CMS", or as a "certs-only" [RFC5751] [RFC6268] or "crls-only" message (see Section 4.2), but no signature or content is present -- hence the names "certs-only" and "crls-only".

Note: As per [RFC7030], the creator may or may not be the EST server or the EST CA.

エージェント（Agent）:
クライアントに代わって機能を実行するエンティティー。エージェントは、a) サーバーと同じネットワーク上にある1つ以上のクライアント、b) IPベースでないネットワーク上のクライアント、c) 自身とサーバーとの間に非電子的なエアギャップ[RFC4949]があるクライアントにサービスを提供できます。後者2つの場合におけるエージェントとクライアントの間のやり取りは、この文書の範囲外です。エージェントがクライアントにサービスを提供できるようになる前に、エージェントはサーバーとの信頼関係を持っていなければなりません（つまり、クライアントに代わって行動することを認可されていなければなりません）。
クライアント（Client）:
通信を可能にするために、最終的にパッケージを消費し使用するデバイス。言い換えれば、クライアントはパッケージのエンドポイントであり、エージェントは1つ以上のクライアントを持つことがあります。混乱を避けるため、この文書では以降、エージェントとクライアントの両方を指して「クライアント」という用語を使用します。
パッケージ（Package）:

1つ以上のコンテンツタイプを含むオブジェクト。パッケージには多くの種類があり、たとえば、非対称鍵、対称鍵、暗号化された鍵、CRL、ファームウェア、TAMPのためのパッケージがあります。セクション2.1.1を参照してください。これらのパッケージはすべて、作成者によってデジタル署名され、CMSのsigned-data[RFC5652][RFC6268]にカプセル化されます（ただし、CAによってすでにデジタル署名されている公開鍵証明書とCRLは除きます）。また例外として、ファームウェアの受領証とエラー、TAMPのレスポンス、確認、エラー、そして「鍵パッケージ」の受領証とエラーは、オプションで署名できます。証明書とCRLは、signed-dataを使用するパッケージに含められます。これはしばしば「縮退CMS（degenerate CMS）」、あるいは「certs-only」[RFC5751][RFC6268]メッセージまたは「crls-only」メッセージ（セクション4.2を参照）と呼ばれますが、署名もコンテンツも存在しません。そのため「certs-only」や「crls-only」という名前が付いています。

注記: [RFC7030]にあるとおり、作成者はESTサーバーやEST CAである場合もあれば、そうでない場合もあります。

2. Locate Available Packages

2. 利用可能なパッケージの特定

The PAL (Package Availability List) is either an XML (Extensible Markup Language) [XML] or JSON (JavaScript Object Notation) [RFC8259] object available through the /pal PC, which furnishes the following information to clients:

PAL（パッケージ可用性リスト、Package Availability List）は、/pal PCを通じて利用可能なXML（Extensible Markup Language）[XML]またはJSON（JavaScript Object Notation）[RFC8259]のオブジェクトであり、クライアントに次の情報を提供します。

  • Advertisements for available packages that can be retrieved from the server;
  • Notifications to begin public key certificate management or to return package receipts and errors; and
  • Advertisement for another PAL.
  • サーバーから取得できる利用可能なパッケージの告知
  • 公開鍵証明書の管理を開始すること、またはパッケージの受領証とエラーを返すことの通知

After being configured (see Section 1.4), the client can use this service to retrieve its PAL (see Section 2.1), which, if properly constructed (see Section 2.3), allows the client to determine some or all of the security-related packages needed for bootstrapping. Each PAL entry refers to other PCs (as defined in this document and in [RFC7030]) that clients use to a) retrieve packages that are available to them (e.g., CA certificates, firmware, trust anchors, symmetric keys, and asymmetric keys) or b) receive notifications to initiate public key certificate enrollment. PAL entries can also be used to notify clients that they are to return receipts or errors for certain packages (see Section 2.1.1). Placing these entries after entries that clients used to retrieve the packages is the same as requesting receipts in the originally distributed package. Figure 1 provides a ladder diagram for the /pal PC protocol flow. Appendix A provides a detailed example.

設定が済んだ後（セクション1.4を参照）、クライアントはこのサービスを使用して自身のPALを取得できます（セクション2.1を参照）。PALが適切に構築されていれば（セクション2.3を参照）、クライアントはブートストラップに必要なセキュリティー関連のパッケージの一部またはすべてを判断できます。各PALエントリーは他のPC（この文書と[RFC7030]で定義されているもの）を指し示し、クライアントはそれらを使用して、a) 自身が利用可能なパッケージ（例: CA証明書、ファームウェア、トラストアンカー、対称鍵、非対称鍵）を取得するか、b) 公開鍵証明書の登録を開始するための通知を受け取ります。PALエントリーは、特定のパッケージについての受領証やエラーを返すようクライアントに通知するために使用することもできます（セクション2.1.1を参照）。これらのエントリーを、クライアントがパッケージを取得するために使用したエントリーの後に配置することは、最初に配布したパッケージの中で受領証を要求することと同じです。図1は、/pal PCのプロトコルフローのラダー図を示しています。付録Aに詳細な例を示します。

PALs are designed to support an arbitrary number of entries, but for PALs that need to be divided for any reason, there is a special PAL entry type that constitutes a collection of "PAL package types". Package type 0001 ("Additional PAL value present") refers to another PAL. See Sections 2.1 and 2.1.1. If present, the 0001 package type is always last because other entries after it are ignored. Also, in order to avoid needlessly dereferencing URIs, the 0001 package type cannot be the only PAL entry. In addition to using the PAL during bootstrapping, clients can be configured to periodically poll the server to determine if updated packages are available for them. Note that the mechanism to configure how often clients poll the server is beyond the scope of this document. However, there are some services that support indicating when a client should retry its request (e.g., simple enrollment and re-enroll responses include the Retry-After header [RFC7030]).

PALは任意の数のエントリーをサポートするように設計されていますが、何らかの理由で分割する必要があるPALのために、「PALパッケージタイプ」の集まりを構成する特別なPALエントリータイプがあります。パッケージタイプ0001（"Additional PAL value present"）は、別のPALを参照します。セクション2.1と2.1.1を参照してください。存在する場合、0001パッケージタイプは常に最後に置かれます。その後のエントリーは無視されるためです。また、URIを不必要に逆参照することを避けるため、0001パッケージタイプを唯一のPALエントリーにすることはできません。ブートストラップの間にPALを使用することに加えて、クライアントは、自身に対して更新されたパッケージが利用可能かどうかを判断するために、定期的にサーバーをポーリングするように設定できます。クライアントがサーバーをポーリングする頻度を設定するメカニズムは、この文書の範囲外であることに注意してください。ただし、クライアントがいつリクエストを再試行すべきかを示すことをサポートしているサービスもあります（例: 単純な登録と再登録のレスポンスにはRetry-Afterヘッダー[RFC7030]が含まれます）。

前述のとおり、PALはXMLとJSONの2つの形式をサポートしています。クライアントは、サーバーに接続するときにHTTPのAcceptヘッダー[RFC7231]を含めて、XMLとJSONのどちらをサポートしているかを示します。

The client MUST authenticate the server as specified in [RFC7030], and the client MUST check the server's authorization as specified in [RFC7030].

クライアントは、[RFC7030]で規定されているとおりにサーバーを認証しなければなりません（MUST）。また、クライアントは、[RFC7030]で規定されているとおりにサーバーの認可を確認しなければなりません（MUST）。

The server MUST authenticate the client as specified in [RFC7030], and the server MUST check the client's authorization as specified in [RFC7030].

サーバーは、[RFC7030]で規定されているとおりにクライアントを認証しなければなりません（MUST）。また、サーバーは、[RFC7030]で規定されているとおりにクライアントの認可を確認しなければなりません（MUST）。

PAL support is OPTIONAL. It is shown in figures throughout this document, but clients need not support the PAL to access services offered by the server.

PALのサポートは選択できます（OPTIONAL）。この文書の図の中では全体を通じてPALを示していますが、クライアントは、サーバーが提供するサービスにアクセスするためにPALをサポートする必要はありません。

2.1. PAL Format

2.1. PALの形式

Each PAL is composed of zero or more entries. Each entry is composed of four fields -- type, date, size, and info -- whose semantics follow:

各PALは0個以上のエントリーで構成されます。各エントリーは、type、date、size、infoの4つのフィールドで構成され、その意味は次のとおりです。

Note: Both XML elements and JSON values are described below. XML elements are enclosed in angle brackets (<>), and JSON values are enclosed in single quotes (''). When described together, they are enclosed in square brackets ([]) separated by a vertical bar (|).

注記: 以下では、XML要素とJSON値の両方を説明します。XML要素は山かっこ（<>）で囲み、JSON値は一重引用符（''）で囲みます。両方をまとめて説明する場合は、縦棒（|）で区切って角かっこ（[]）で囲みます。

  • [<type> | 'type'] uniquely identifies each package that a client may retrieve from the server with a 4-digit string. [<type> | 'type'] MUST be present. The PAL package types are defined in Section 2.1.1.

  • [<date> | 'date'] indicates one of the following:

    • The date and time that the client last successfully downloaded the identified package from the server. [<date> | 'date'] MUST be represented as Generalized Time with 20 characters: YYYY-MM-DDTHH:MM:SSZ; <date> matches the dateTime production in "canonical representation" [XMLSCHEMA]; 'date' is a string. Implementations SHOULD NOT rely on time resolution finer than seconds and MUST NOT generate time instants that specify leap seconds.

    • The omission of [<date> | 'date'] indicates the following:

      • There is no indication that the client has successfully downloaded the identified package, or
      • The PAL entry corresponds to a pointer to the next PAL, or the server is requesting a package from the client (e.g., certification request, receipt, error).
  • [<size> | 'size'] indicates the size in bytes of the package; <size> is a nonNegativeInteger, and 'size' is a number. A package size of zero (i.e., "0" without the quotes) indicates that the client needs to begin a transaction, return an error, or return a receipt. [<size> | 'size'] MUST be present.
  • [<info> | 'info'] provides an SKI (Subject Key Identifier), a DN (Distinguished Name), an Issuer and Serial Number tuple, or a URI, i.e., it is a choice between these four items, all of which are defined in [RFC5280]. When a URI [RFC3986] is included, [<uri> | 'uri'] indicates the location where the identified package can be retrieved. When a DN, an SKI, or an Issuer Name and Serial Number tuple is included, it points to a certificate that is the subject of the notification (i.e., the certificate to be rekeyed or renewed); [<dn> | 'dn'] is encoded as a string with the format defined in [RFC4514]; <ski> is a hexBinary, and 'ski' is a string of hex digits (i.e., 0-9, a-f, and A-F); [<iasn> | 'iasn'] includes both [<issuer> | 'issuer'] and [<serial> | 'serial'] as a complexType in XML and an object in JSON. [<issuer> | 'issuer'] is a DN encoded as a string with the format defined in [RFC4514]; <serial> is a positiveInteger, and 'serial' is a number. [<info> | 'info'] MUST be present, and [<info> | 'info'] MUST include exactly one [<dn> | 'dn'], [<ski> | 'ski'], [<iasn> | 'iasn'], or [<uri> | 'uri'].
  • [<type> | 'type']は、クライアントがサーバーから取得できる各パッケージを、4桁の文字列で一意に識別します。[<type> | 'type']は存在しなければなりません（MUST）。PALパッケージタイプはセクション2.1.1で定義します。

  • [<date> | 'date']は、次のいずれかを示します。

    • クライアントが、識別されたパッケージをサーバーから最後にダウンロードすることに成功した日時。[<date> | 'date']は、20文字のGeneralized Time（YYYY-MM-DDTHH:MM:SSZ）として表現しなければなりません（MUST）。<date>は「正準表現（canonical representation）」[XMLSCHEMA]のdateTime生成規則に一致し、'date'は文字列です。実装は、秒より細かい時間分解能に依存すべきではありません（SHOULD NOT）。また、うるう秒を指定する時刻を生成してはなりません（MUST NOT）。

    • [<date> | 'date']が省略されている場合は、次のことを示します。

      • クライアントが識別されたパッケージのダウンロードに成功したことを示すものがない。または、
      • PALエントリーが次のPALへのポインターに対応している。あるいは、サーバーがクライアントにパッケージ（例: 証明書リクエスト、受領証、エラー）を要求している。
  • [<size> | 'size']は、パッケージのサイズをバイト単位で示します。<size>はnonNegativeIntegerであり、'size'は数値です。パッケージサイズが0（つまり、引用符なしの"0"）の場合、クライアントがトランザクションを開始するか、エラーを返すか、受領証を返す必要があることを示します。[<size> | 'size']は存在しなければなりません（MUST）。
  • [<info> | 'info']は、SKI（サブジェクト鍵識別子、Subject Key Identifier）、DN（識別名、Distinguished Name）、発行者名とシリアル番号の組（Issuer and Serial Number tuple）、またはURIを提供します。つまり、これら4つの項目からの選択であり、そのすべてが[RFC5280]で定義されています。URI[RFC3986]が含まれる場合、[<uri> | 'uri']は、識別されたパッケージを取得できる場所を示します。DN、SKI、または発行者名とシリアル番号の組が含まれる場合、それは通知の対象となる証明書（つまり、鍵の再生成または更新の対象となる証明書）を指し示します。[<dn> | 'dn']は[RFC4514]で定義されている形式の文字列としてエンコードされます。<ski>はhexBinaryであり、'ski'は16進数字（つまり、0-9、a-f、A-F）の文字列です。[<iasn> | 'iasn']は、[<issuer> | 'issuer']と[<serial> | 'serial']の両方を、XMLではcomplexTypeとして、JSONではオブジェクトとして含みます。[<issuer> | 'issuer']は、[RFC4514]で定義されている形式の文字列としてエンコードされたDNです。<serial>はpositiveIntegerであり、'serial'は数値です。[<info> | 'info']は存在しなければなりません（MUST）。また、[<info> | 'info']は、[<dn> | 'dn']、[<ski> | 'ski']、[<iasn> | 'iasn']、[<uri> | 'uri']のうちちょうど1つを含まなければなりません（MUST）。

Clients are often limited by the size of objects they can consume; the PAL is not immune to these limitations. As opposed to picking a limit for all clients, a special package type (0001) is defined (see Section 2.1.1) to indicate that another PAL is available. Servers can use this value to limit the size of the PALs provided to clients. The mechanism for servers to know client PAL size limits is beyond the scope of this document; one possible solution is through provisioned information.

クライアントは、消費できるオブジェクトのサイズによって制限されることがよくあります。PALもこうした制限と無縁ではありません。すべてのクライアントに対して1つの上限を選ぶのではなく、別のPALが利用可能であることを示すために特別なパッケージタイプ（0001）を定義しています（セクション2.1.1を参照）。サーバーはこの値を使用して、クライアントに提供するPALのサイズを制限できます。サーバーがクライアントのPALサイズの上限を知るためのメカニズムはこの文書の範囲外です。考えられる解決策の1つは、プロビジョニングされた情報によるものです。

2.2. Request PAL

2.2. PALの要求

Clients request their PAL with an HTTP GET [RFC7231], using an operation path of "/pal". Clients indicate whether they would prefer XML or JSON by including the HTTP Accept header [RFC7231] with either "application/xml" or "application/json", respectively.

クライアントは、"/pal"という操作パスを使用して、HTTP GET[RFC7231]で自身のPALを要求します。クライアントは、HTTPのAcceptヘッダー[RFC7231]に"application/xml"または"application/json"のいずれかを含めることで、XMLとJSONのどちらを希望するかをそれぞれ示します。

2.3. Provide PAL

2.3. PALの提供

If the server has a PAL for the client, the server response MUST contain an HTTP 200 response code with a Content-Type of "application/xml" [RFC7303] or "application/json" [RFC8259].

サーバーがクライアントのためのPALを持っている場合、サーバーのレスポンスは、Content-Typeが"application/xml"[RFC7303]または"application/json"[RFC8259]であるHTTP 200レスポンスコードを含まなければなりません（MUST）。

When the server constructs a PAL, an order of precedence for PAL offerings is based on the following rationale:

サーバーがPALを構築するとき、PALで提供する項目の優先順位は、次の根拠に基づきます。

  • /cacerts and /crls packages are the most important because they support validation decisions on certificates used to sign and encrypt other listed PAL items.
  • /csrattrs are the next in importance, since they provide information that the server would like the client to include in its certificate enrollment request.

  • /simpleenroll, /simplereenroll, and /fullcmc packages are next in importance, since they can impact a certificate used by the client to sign CMS content or a certificate to establish keys for encrypting content exchanged with the client.

    • A client engaged in certificate management SHOULD accept and process CA-provided transactions as soon as possible to avoid undue delays that might lead to protocol failure.

  • /symmetrickeys, /firmware, /tamp, and /eecerts packages containing keys and other types of products are last. Precedence SHOULD be given to packages that the client has not previously downloaded. The items listed in a PAL may not identify all of the packages available for a device. This can be for any of the following reasons:

    • The server may temporarily withhold some outstanding PAL items to simplify client processing.
    • If a CA has more than one certificate ready for the client, the server will provide a notice for one at a time. Pending notices will be serviced in order, according to the date when the certificate will be used (earliest date first).
  • /cacertsパッケージと/crlsパッケージが最も重要です。これらは、PALに列挙された他の項目の署名や暗号化に使用される証明書についての検証の判断をサポートするためです。
  • /csrattrsが次に重要です。これは、サーバーがクライアントに証明書登録要求に含めてほしい情報を提供するためです。

  • /simpleenrollパッケージ、/simplereenrollパッケージ、/fullcmcパッケージがその次に重要です。これらは、クライアントがCMSコンテンツに署名するために使用する証明書や、クライアントとやり取りするコンテンツを暗号化するための鍵を確立する証明書に影響を与える可能性があるためです。

    • 証明書管理に従事しているクライアントは、プロトコルの失敗につながりかねない過度の遅延を避けるため、CAが提供するトランザクションをできるだけ早く受け入れて処理すべきです（SHOULD）。

  • 鍵やその他の種類の製品を含む/symmetrickeysパッケージ、/firmwareパッケージ、/tampパッケージ、/eecertsパッケージは最後です。クライアントがまだダウンロードしていないパッケージを優先すべきです（SHOULD）。PALに列挙された項目は、デバイスに対して利用可能なすべてのパッケージを特定していないことがあります。これは、次のいずれかの理由によるものです。

    • サーバーは、クライアントの処理を単純にするために、未処理のPAL項目の一部を一時的に保留することがあります。
    • CAがクライアントのために準備できている証明書が複数ある場合、サーバーは一度に1つずつ通知を提供します。保留中の通知は、証明書が使用される日付に従って（日付が早いものから）順番に処理されます。

When rejecting a request, the server specifies either an HTTP 4xx error or an HTTP 5xx error.

リクエストを拒否する場合、サーバーはHTTP 4xxエラーまたはHTTP 5xxエラーのいずれかを指定します。

All other return codes are handled as specified in Section 4.2.3 of [RFC7030] (i.e., 202 handling and all other HTTP response codes).

その他のすべてのリターンコードは、[RFC7030]のセクション4.2.3で規定されているとおりに処理されます（つまり、202の処理と、その他のすべてのHTTPレスポンスコード）。

3. Distribute EE Certificates

3. EE証明書の配布

Numerous mechanisms exist for clients to query repositories for certificates. The service provided by the /eecerts PC is different in that it is not a general-purpose query for client certificates; instead, it allows the server to provide peer certificates to a client that the server knows through an out-of-band mechanism that the client will be communicating with. For example, a router being provisioned that connects to two peers can be provisioned with not only its certificate but also with the peers' certificates.

4. Distribute CRLs and ARLs

4. CRLとARLの配布

CRLs (and ARLs) are needed in many instances to perform certificate path validation [RFC5280]. They can be obtained from repositories if their location is provided in the certificate. However, the client needs to parse the certificate and perform an additional round trip to retrieve them. Providing CRLs during bootstrapping obviates the need for the client to parse the certificate and aids those clients who might be unable to retrieve the CRL. Clients are free to obtain CRLs on which they rely from sources other than the server (e.g., a local directory). The /crls PC allows servers to distribute CRLs at the same time that clients retrieve their certificate(s) and CA certificate(s) as well as peer certificates.

CRL（およびARL）は、多くの場合、証明書パスの検証[RFC5280]を行うために必要です。CRLの場所が証明書に記載されていれば、リポジトリーから取得できます。しかし、クライアントは証明書を解析し、CRLを取得するために追加のラウンドトリップを行う必要があります。ブートストラップの間にCRLを提供することで、クライアントが証明書を解析する必要がなくなり、CRLを取得できない可能性のあるクライアントの助けにもなります。クライアントは、自身が依拠するCRLをサーバー以外の情報源（例: ローカルディレクトリー）から自由に取得できます。/crls PCにより、サーバーは、クライアントが自身の証明書やCA証明書、さらにピアの証明書を取得するのと同時に、CRLを配布できます。

The server need not authenticate or authorize the client for distributing a CRL, because the package contents are already signed by a CA (i.e., the CRLs in a crls-only message have already been signed by a CA). The message flow is as depicted in Figure 2 but with "CRL(s)" instead of "EE Cert(s)".

パッケージの内容はすでにCAによって署名されているため（つまり、crls-onlyメッセージ内のCRLはすでにCAによって署名されているため）、CRLを配布するにあたって、サーバーがクライアントを認証または認可する必要はありません。メッセージフローは図2に示したとおりですが、"EE Cert(s)"の代わりに"CRL(s)"となります。

クライアントは、"/crls"という操作パスを使用して、HTTP GET[RFC7231]でCRLを要求します。

4.2. CRL Response

4.2. CRLのレスポンス

The response, and the processing of that response, are identical to what is described in Section 4.1.3 of [RFC7030], except that instead of providing the issued certificate one of more CRLs are returned in the crls-only message.

レスポンスとそのレスポンスの処理は、[RFC7030]のセクション4.1.3で説明されているものと同じです。ただし、発行された証明書を提供する代わりに、1つ以上のCRLがcrls-onlyメッセージで返されます。

Clients MUST reject CRLs that do not validate to an authorized TA.

クライアントは、認可されたTAまで検証できないCRLを拒否しなければなりません（MUST）。

5. Symmetric Keys, Receipts, and Errors

5. 対称鍵、受領証、エラー

In addition to public keys, clients often need one or more symmetric keys to communicate with their peers. The /symmetrickeys PC allows the server to distribute symmetric keys to clients.

クライアントは、公開鍵に加えて、ピアと通信するために1つ以上の対称鍵を必要とすることがよくあります。/symmetrickeys PCにより、サーバーはクライアントに対称鍵を配布できます。

Distribution of keys does not always work as planned, and clients need a way to inform the server that something has gone wrong; they also need a way to inform the server, if asked, that the distribution process has successfully completed. The /symmetrickeys/return PC allows clients to provide errors and receipts.

鍵の配布は常に計画どおりに機能するとは限らず、クライアントには、何か問題が起きたことをサーバーに通知する手段が必要です。また、求められた場合には、配布プロセスが正常に完了したことをサーバーに通知する手段も必要です。/symmetrickeys/return PCにより、クライアントはエラーと受領証を提供できます。

Clients MUST authenticate the server, and clients MUST check the server's authorization.

クライアントはサーバーを認証しなければなりません（MUST）。また、クライアントはサーバーの認可を確認しなければなりません（MUST）。

The server MUST authenticate clients, and the server MUST check the client's authorization.

サーバーはクライアントを認証しなければなりません（MUST）。また、サーバーはクライアントの認可を確認しなければなりません（MUST）。

HTTP GET [RFC7231] is used when the server provides the key to the client (see Section 5.1), using the /symmetrickeys PC; HTTP POST [RFC7231] is used when the client provides a receipt (see Section 5.2) or an error (see Section 5.2) to the server with the /symmetrickeys/return PC.

サーバーが/symmetrickeys PCを使用してクライアントに鍵を提供するとき（セクション5.1を参照）には、HTTP GET[RFC7231]を使用します。クライアントが/symmetrickeys/return PCを使用してサーバーに受領証（セクション5.2を参照）またはエラー（セクション5.2を参照）を提供するときには、HTTP POST[RFC7231]を使用します。

5.1. Symmetric Keys

5.1. 対称鍵

Servers use /symmetrickeys to provide symmetric keys to clients; the symmetric key package is defined in [RFC6031].

サーバーは、/symmetrickeysを使用してクライアントに対称鍵を提供します。対称鍵パッケージは[RFC6031]で定義されています。

As with the /serverkeygen PC defined in [RFC7030], the default method for distributing the symmetric key uses the encryption mode of the negotiated TLS cipher suite. Keys are not protected by preferred key-wrapping methods such as AES Key Wrap [RFC3394] or AES Key Wrap with Padding [RFC5649], because encryption of the symmetric key beyond that provided by TLS is OPTIONAL. Therefore, the cipher suite used to return the symmetric key MUST offer cryptographic strength that is commensurate with the symmetric key being delivered to the client. The cipher suite used MUST NOT have the NULL encryption algorithm, as this will disclose the unprotected symmetric key. It is strongly RECOMMENDED that servers always return encrypted symmetric keys.

5.1.2. Symmetric Key Response

If the request is successful, the server response MUST have an HTTP 200 response code with a Content-Type of "application/cms" [RFC7193]. The returned content varies:

  • If additional encryption and origin authentication are employed, the content associated with application/cms is a DER-encoded signed-data that encapsulates an enveloped-data that encapsulates a signed-data that further encapsulates a symmetric key package.
  • If CCC (CMS Content Constraints) [RFC6010] is supported, the content associated with application/cms is a DER-encoded encrypted key package [RFC6032]. 8. Asymmetric Keys, Receipts, and Errors

8. 非対称鍵、受領証、エラー

[RFC7030] defines the /serverkeygen PC to support server-side generation of asymmetric keys. Keys are returned as either a) an unprotected PKCS #8 when additional security beyond TLS is not employed or b) a CMS asymmetric key package content type that is encapsulated in a signed-data content type that is further encapsulated in an enveloped-data content type when additional security beyond TLS is requested.

[RFC7030]は、非対称鍵のサーバー側での生成をサポートするために/serverkeygen PCを定義しています。鍵は、a) TLS以上の追加のセキュリティーを用いない場合は、保護されていないPKCS #8として、b) TLS以上の追加のセキュリティーが要求された場合は、signed-dataコンテンツタイプにカプセル化され、それがさらにenveloped-dataコンテンツタイプにカプセル化されたCMS非対称鍵パッケージコンテンツタイプとして返されます。

Some implementations prefer the use of other CMS content types to encapsulate the asymmetric key package. This document extends the content types that can be returned; see Section 8.1.

実装によっては、非対称鍵パッケージをカプセル化するために他のCMSコンテンツタイプを使用することを好むものもあります。この文書は、返すことができるコンテンツタイプを拡張します。セクション8.1を参照してください。

[RFC7191] defines content types for key package receipts and errors. This document defines the /serverkeygen/return PC to add support for returning receipts and errors for asymmetric key packages; see Section 8.2.

[RFC7191]は、鍵パッケージの受領証とエラーのためのコンテンツタイプを定義しています。この文書は、非対称鍵パッケージについての受領証とエラーを返すことのサポートを追加するために、/serverkeygen/return PCを定義します。セクション8.2を参照してください。

PKCS #12 [RFC7292] (sometimes referred to as "PFX" (Personal Information Exchange) or "P12") is often used to distribute asymmetric private keys and associated certificates. This document extends the /serverkeygen PC to allow servers to distribute server-generated asymmetric private keys and the associated certificate to clients using PKCS #12; see Section 8.3.

PKCS #12[RFC7292]（"PFX"（Personal Information Exchange）や"P12"と呼ばれることもあります）は、非対称秘密鍵とそれに関連する証明書を配布するためによく使用されます。この文書は、サーバーが生成した非対称秘密鍵とそれに関連する証明書を、サーバーがPKCS #12を使用してクライアントに配布できるように、/serverkeygen PCを拡張します。セクション8.3を参照してください。

8.1. Asymmetric Key Encapsulation

8.1. 非対称鍵のカプセル化

CMS supports a number of content types to encapsulate other CMS content types; [RFC7030] includes one such possibility. Note that when only relying on TLS the returned key is not a CMS content type. This document extends the CMS content types that can be returned.

CMSは、他のCMSコンテンツタイプをカプセル化するためのコンテンツタイプをいくつもサポートしています。[RFC7030]にはそのような可能性の1つが含まれています。TLSのみに依存する場合、返される鍵はCMSコンテンツタイプではないことに注意してください。この文書は、返すことができるCMSコンテンツタイプを拡張します。

If the client supports CCC [RFC6010], then the client can indicate that it supports encapsulated asymmetric keys in the encrypted key package [RFC5958] by including the encrypted key package's OID in a content type attribute [RFC2985] in the CSR (Certificate Signing Request) -- aka the certification request -- that it provides to the server. If the client knows a priori that the server supports the encrypted key package content type, then the client need not include the content type attribute in the CSR.

クライアントがCCC[RFC6010]をサポートしている場合、クライアントは、サーバーに提供するCSR（証明書署名要求、Certificate Signing Request）、別名、証明書リクエストの中のコンテンツタイプ属性[RFC2985]に暗号化鍵パッケージのOIDを含めることで、暗号化鍵パッケージ[RFC5958]にカプセル化された非対称鍵をサポートしていることを示すことができます。サーバーが暗号化鍵パッケージのコンテンツタイプをサポートしていることをクライアントが事前に知っている場合、クライアントはCSRにコンテンツタイプ属性を含める必要はありません。

In all instances defined herein, the Content-Type is "application/cms" [RFC7193]. The optional encapsulatingContent and innerContent parameters SHOULD be included with the Content-Type to indicate the protection afforded to the returned asymmetric key package.

ここで定義するすべての場合において、Content-Typeは"application/cms"[RFC7193]です。返される非対称鍵パッケージに施された保護を示すため、オプションのencapsulatingContentパラメーターとinnerContentパラメーターをContent-Typeに含めるべきです（SHOULD）。

If additional encryption and origin authentication are employed, the content associated with application/cms is a DER-encoded signed-data that encapsulates an enveloped-data that encapsulates a signed-data that further encapsulates an asymmetric key package.

追加の暗号化と発信元認証を用いる場合、application/cmsに関連付けられたコンテンツは、DERエンコードされたsigned-dataであり、それがenveloped-dataをカプセル化し、そのenveloped-dataがsigned-dataをカプセル化し、そのsigned-dataがさらに非対称鍵パッケージをカプセル化します。

If CCC is supported and additional encryption is employed, the content associated with application/cms is a DER-encoded encrypted key package [RFC6032] content type that encapsulates a signed-data that further encapsulates an asymmetric key package.

CCCがサポートされていて、追加の暗号化を用いる場合、application/cmsに関連付けられたコンテンツは、DERエンコードされた暗号化鍵パッケージ[RFC6032]コンテンツタイプであり、それがsigned-dataをカプセル化し、そのsigned-dataがさらに非対称鍵パッケージをカプセル化します。

If CCC is supported and if additional encryption and additional origin authentication are employed, the content associated with application/cms is a DER-encoded signed-data that encapsulates an encrypted key package content type that encapsulates a signed-data that further encapsulates an asymmetric key package.

CCCがサポートされていて、追加の暗号化と追加の発信元認証を用いる場合、application/cmsに関連付けられたコンテンツは、DERエンコードされたsigned-dataであり、それが暗号化鍵パッケージコンテンツタイプをカプセル化し、その暗号化鍵パッケージがsigned-dataをカプセル化し、そのsigned-dataがさらに非対称鍵パッケージをカプセル化します。

The encrypted key package [RFC6032] provides three choices to encapsulate keys: EncryptedData, EnvelopedData, and AuthEnvelopedData, with EnvelopedData being the mandatory-to-implement choice.

暗号化鍵パッケージ[RFC6032]は、鍵をカプセル化するための3つの選択肢、EncryptedData、EnvelopedData、AuthEnvelopedDataを提供しており、そのうちEnvelopedDataが実装必須の選択肢です。

When rejecting a request, the server specifies either an HTTP 4xx error or an HTTP 5xx error.

リクエストを拒否する場合、サーバーはHTTP 4xxエラーまたはHTTP 5xxエラーのいずれかを指定します。

If an asymmetric key package or an encrypted key package is digitally signed, the client MUST reject it if the digital signature does not validate back to an authorized TA.

非対称鍵パッケージまたは暗号化鍵パッケージがデジタル署名されている場合、そのデジタル署名が認可されたTAまで遡って検証できなければ、クライアントはそれを拒否しなければなりません（MUST）。

Note: Absent a policy on the client side requiring a signature, a malicious EST server can simply strip the signature, thus bypassing that check. In that case, this requirement is merely a sanity check, serving to detect mis-signed packages or misconfigured clients.

注記: クライアント側に署名を要求するポリシーがない場合、悪意のあるESTサーバーは単に署名を取り除くことで、そのチェックを回避できます。その場合、この要件は、誤って署名されたパッケージや設定を誤ったクライアントを検出するのに役立つ、単なる健全性チェックにすぎません。

[RFC3370], [RFC5753], [RFC5754], [RFC6033], [RFC6161], and [RFC6162] provide algorithm details for use when protecting the asymmetric key package and encrypted key package.

[RFC3370]、[RFC5753]、[RFC5754]、[RFC6033]、[RFC6161]、[RFC6162]は、非対称鍵パッケージと暗号化鍵パッケージを保護する際に使用するアルゴリズムの詳細を提供しています。

8.3. PKCS #12

8.3. PKCS #12

PFX is widely deployed and supports protecting keys in the same fashion as CMS, but it does so differently.

PFXは広く展開されており、CMSと同じように鍵を保護することをサポートしていますが、その方法は異なります。

8.3.1. Server-Side Key Generation Request

8.3.1. サーバー側での鍵生成のリクエスト

Similar to the other server-generated asymmetric keys provided through the /serverkeygen PC:

/serverkeygen PCを通じて提供される、サーバーが生成した他の非対称鍵と同様に、次のようになります。

  • The certificate request is HTTPS POSTed and is the same format as for the "/simpleenroll" and "/simplereenroll" path extensions with the same content type.
  • In all respects, the server SHOULD treat the CSR as it would any enroll or re-enroll CSR; the only distinction here is that the server MUST ignore the public key values and signature in the CSR. These are included in the request only to allow the reuse of existing codebases for generating and parsing such requests.
  • 証明書リクエストはHTTPSでPOSTされ、"/simpleenroll"パス拡張および"/simplereenroll"パス拡張と同じ形式であり、同じコンテンツタイプを持ちます。
  • サーバーは、あらゆる点で、CSRを他の登録または再登録のCSRと同じように扱うべきです（SHOULD）。ここでの唯一の違いは、サーバーがCSR内の公開鍵の値と署名を無視しなければならない（MUST）ことです。これらがリクエストに含まれているのは、そのようなリクエストを生成および解析するための既存のコードベースを再利用できるようにするためだけです。

PBE (password-based encryption) shrouding of PKCS #12 is supported, and this specification makes no attempt to alter this de facto standard. As such, there is no support of the DecryptKeyIdentifier specified in [RFC7030] for use with PKCS #12 (i.e., "enveloping" is not supported). Note: The use of PBE requires that the password be distributed to the client; methods to distribute this password are beyond the scope of this document.

PKCS #12のPBE（パスワードベース暗号化、password-based encryption）による隠蔽（shrouding）はサポートされており、この仕様はこの事実上の標準を変更しようとはしません。そのため、PKCS #12で使用するための、[RFC7030]で規定されているDecryptKeyIdentifierはサポートされません（つまり、「エンベロープ化（enveloping）」はサポートされません）。注記: PBEを使用するには、パスワードをクライアントに配布する必要があります。このパスワードを配布する方法は、この文書の範囲外です。

8.3.2. Server-Side Key Generation Response

8.3.2. サーバー側での鍵生成のレスポンス

If the request is successful, the server response MUST have an HTTP 200 response code with a Content-Type of "application/pkcs12" [PKCS12] that consists of a base64-encoded DER-encoded [X.690] PFX [RFC7292].

リクエストが成功した場合、サーバーのレスポンスは、Content-Typeが"application/pkcs12"[PKCS12]であるHTTP 200レスポンスコードを持たなければなりません（MUST）。そのコンテンツは、DERエンコード[X.690]されたPFX[RFC7292]をbase64エンコードしたものです。

Note that this response is different than the response returned as described in Section 4.4.2 of [RFC7030], because here the private key and the certificate are included in the same PFX.

このレスポンスは、[RFC7030]のセクション4.4.2で説明されているとおりに返されるレスポンスとは異なることに注意してください。ここでは秘密鍵と証明書が同じPFXに含まれるためです。

When rejecting a request, the server MUST specify either an HTTP 4xx error or an HTTP 5xx error. The response data's Content-Type MAY be "text/plain" [RFC2046] to convey human-readable error messages.

リクエストを拒否する場合、サーバーはHTTP 4xxエラーまたはHTTP 5xxエラーのいずれかを指定しなければなりません（MUST）。人間が読めるエラーメッセージを伝えるために、レスポンスデータのContent-Typeを"text/plain"[RFC2046]にしてもよいです（MAY）。

For immediately rejected requests, CMC works well. If the server prematurely closes the connection, then the procedures in Section 6.3.1 of [RFC7230] apply. Appendix B. Additional CSR Attributes

付録B. 追加のCSR属性

This is an informative appendix.

これは参考情報の付録です。

In some cases, the client is severely limited in its ability to encode and decode ASN.1 objects. If the client knows that a "csr" template is being provided during enrollment, then it can peel the returned CSR attribute, generate its keys, place the public key in the certification request, and then sign the request. To accomplish this, the server returns a pKCS7PDU attribute [RFC2985] in the /csrattrs (the following is "pseudo ASN.1" and is only meant to show the fields needed to accomplish returning a template certification request):

場合によっては、クライアントのASN.1オブジェクトをエンコードおよびデコードする能力が大きく制限されていることがあります。登録の間に"csr"テンプレートが提供されることをクライアントが知っていれば、クライアントは返されたCSR属性をはがし、自身の鍵を生成し、公開鍵を証明書リクエストに配置してから、リクエストに署名できます。これを実現するために、サーバーは/csrattrsでpKCS7PDU属性[RFC2985]を返します（以下は「疑似ASN.1」であり、テンプレートの証明書リクエストを返すことを実現するのに必要なフィールドを示すことだけを目的としています）。

  pKCS7PDU ATTRIBUTE ::= {
    WITH SYNTAX ContentInfo
    ID pkcs-9-at-pkcs7PDU
    }

  pKCS7PDU ATTRIBUTE ::= {
    WITH SYNTAX ContentInfo
    ID pkcs-9-at-pkcs7PDU
    }

  pkcs-9-at-pkcs7PDU OBJECT IDENTIFIER ::= {
    iso(1) member-body(2) us(840) rsadsi(113549) pkcs(1) pkcs9(9)
    pkcs-9-at(25) 5
    }

  pkcs-9-at-pkcs7PDU OBJECT IDENTIFIER ::= {
    iso(1) member-body(2) us(840) rsadsi(113549) pkcs(1) pkcs9(9)
    pkcs-9-at(25) 5
    }

The ContentInfo is a PKIData:

ContentInfoはPKIDataです。

  PKIData ::= SEQUENCE {
    reqSequence        SEQUENCE SIZE(0..MAX) OF TaggedRequest
    }

  PKIData ::= SEQUENCE {
    reqSequence        SEQUENCE SIZE(0..MAX) OF TaggedRequest
    }

Where TaggedRequest is a choice between the PKCS #10 or Certificate Request Message Format (CRMF) requests.

ここで、TaggedRequestは、PKCS #10とCRMF（Certificate Request Message Format）のリクエストのどちらかを選択するものです。

  TaggedRequest ::= CHOICE {
    tcr               [0] TaggedCertificationRequest,
    crm               [1] CertReqMsg
    }

  TaggedRequest ::= CHOICE {
    tcr               [0] TaggedCertificationRequest,
    crm               [1] CertReqMsg
    }

Or, the ContentInfo can be a signed-data content type that further encapsulates a PKIData.

あるいは、ContentInfoは、さらにPKIDataをカプセル化するsigned-dataコンテンツタイプであることもできます。
