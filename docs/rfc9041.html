RFC 9041

Updating the MPLS Label Switched Paths (LSPs) Ping Parameters IANA Registry

RFC 9041

MPLSラベルスイッチパス（LSP）Ping Parameters IANAレジストリーの更新

Abstract

概要

This document updates RFCs 8029 and 8611, both of which define IANA registries for MPLS Label Switched Path (LSP) Ping. In particular, the registration procedure "Private Use" (previously known as "Vendor Private Use") has been changed to "First Come First Served" for the TLV and sub-TLV registries.

この文書は、どちらもMPLSラベルスイッチパス（LSP）PingのIANAレジストリーを定義しているRFC 8029とRFC 8611を更新します。 特に、TLVおよびサブTLVのレジストリーについて、登録手続き「Private Use」（以前は「Vendor Private Use」と呼ばれていたもの）を「First Come First Served」に変更しました。

It also updates the description of the procedures for the responses sent when an unknown or erroneous code point is found. The updates are to clarify and align this namespace with recent developments, e.g., aligning terminology with RFC 8126 instead of the now obsoleted RFC 5226 (both titled "Guidelines for Writing an IANA Considerations Section in RFCs").

また、未知または誤ったコードポイントが見つかったときに送信される応答の手続きに関する記述も更新します。 これらの更新は、この名前空間を明確にし、最近の動向に合わせるためのものです。 たとえば、用語を現在は廃止されたRFC 5226ではなくRFC 8126（どちらも表題は「Guidelines for Writing an IANA Considerations Section in RFCs」）に合わせます。

1. Introduction

1. はじめに

There were a number of reasons to start the work that has led to this document, e.g.,

この文書につながる作業を始めた理由はいくつかあります。たとえば、次のようなものです。

  • When the LSP Ping registry was created, it was incorrectly assumed that code points allocated by Experimental RFCs would be "experimental" code points; a code point made available in a public IANA registry is not limited by the type of RFC that made the allocation: it is available for use in any type of document.
  • The number of "experimental" code points was also too large as compared to what is normally allocated for "Experimental Use".
  • The words "mandatory" and "optional" are used differently in [RFC8029] than in other RFCs. For example, [RFC8029] talks about mandatory TLVs to indicate that it is mandatory to take a certain action if the TLV is found in a message but is not recognized. Other RFCs use "mandatory TLV" to indicate a TLV that must be present in a message.
  • LSP Pingレジストリーが作成されたとき、Experimental RFCによって割り当てられたコードポイントは「実験的」コードポイントになると誤って想定されていました。公開されているIANAレジストリーで利用可能になったコードポイントは、その割り当てを行ったRFCの種類によって制限されるものではなく、どの種類の文書でも使用できます。
  • また、「実験的」コードポイントの数が、通常「Experimental Use」に割り当てられる数と比べて多すぎました。
  • 「mandatory（必須）」と「optional（任意）」という語は、[RFC8029]では他のRFCとは異なる意味で使われています。たとえば、[RFC8029]は、メッセージ内でTLVが見つかったもののそれを認識できない場合に、ある動作をとることが必須であることを示すために、必須TLVという言い方をしています。他のRFCでは、「必須TLV」はメッセージ内に存在しなければならないTLVを示すために使われます。

Over time, there have been attempts to administratively update some of the registries, but it was soon decided that an RFC was needed. Other, often minor, potential updates were found, e.g., reserving the value 0 (zero) in registries where that is possible.

これまでに、いくつかのレジストリーを管理上の手続きで更新しようとする試みがありましたが、すぐにRFCが必要だと判断されました。また、可能なレジストリーで値0（ゼロ）を予約するなど、ほかにも（多くは小さな）更新の候補が見つかりました。

[RFC8029] contains updates to the "Multiprotocol Label Switching (MPLS) Label Switched Paths (LSPs) Ping Parameters" IANA namespace [IANA-LSP-PING].

[RFC8029]には、「Multiprotocol Label Switching (MPLS) Label Switched Paths (LSPs) Ping Parameters」IANA名前空間[IANA-LSP-PING]に対する更新が含まれています。

[RFC8611] created LSP Ping IANA registries that match [RFC8126]. This document further clarifies the entries in those registries and makes the definitions more precise.

[RFC8611]は、[RFC8126]に合致するLSP Ping IANAレジストリーを作成しました。この文書は、それらのレジストリーのエントリーをさらに明確にし、定義をより正確にします。

This document updates [RFC8029] and [RFC8611] by updating two groups of registries as follows:

この文書は、次のように2つのグループのレジストリーを更新することで、[RFC8029]と[RFC8611]を更新します。

First, the "Message Types" [IANA-MT], "Reply Modes" [IANA-RM], and "Return Codes" [IANA-RC] registries are updated. The changes to these registries are minor.

1つ目に、「Message Types」[IANA-MT]、「Reply Modes」[IANA-RM]、「Return Codes」[IANA-RC]の各レジストリーを更新します。これらのレジストリーへの変更は軽微なものです。

Second, this document updates the TLV and sub-TLV registries listed below:

2つ目に、この文書は以下に挙げるTLVおよびサブTLVのレジストリーを更新します。

  • "TLVs", [IANA-TLV-reg]
  • "Sub-TLVs for TLV Types 1, 16, and 21", [IANA-Sub-1-16-21]
  • "Sub-TLVs for TLV Type 6", [IANA-Sub-6]
  • "Sub-TLVs for TLV Type 11", [IANA-Sub-11]
  • "Sub-TLVs for TLV Type 20", [IANA-Sub-20]
  • "Sub-TLVs for TLV Type 23", [IANA-Sub-23]
  • "Sub-TLVs for TLV Type 27", [IANA-Sub-27]
  • "TLVs", [IANA-TLV-reg]
  • "Sub-TLVs for TLV Types 1, 16, and 21", [IANA-Sub-1-16-21]
  • "Sub-TLVs for TLV Type 6", [IANA-Sub-6]
  • "Sub-TLVs for TLV Type 11", [IANA-Sub-11]
  • "Sub-TLVs for TLV Type 20", [IANA-Sub-20]
  • "Sub-TLVs for TLV Type 23", [IANA-Sub-23]
  • "Sub-TLVs for TLV Type 27", [IANA-Sub-27]

It should be noted that [RFC8029] was published before [RFC8126] and uses outdated terminology for some registration procedures, e.g., "Vendor Private Use". [RFC8611] was published after [RFC8126] and uses its recommended terminology, e.g., "Private Use". However, now both "Vendor Private Use" and "Private Use" have been removed and replaced with "First Come First Served" (FCFS) code points.

[RFC8029]は[RFC8126]より前に発行されたため、一部の登録手続きについて「Vendor Private Use」のような古い用語を使っていることに注意してください。[RFC8611]は[RFC8126]より後に発行されたため、そこで推奨されている「Private Use」のような用語を使っています。しかし現在では、「Vendor Private Use」と「Private Use」はどちらも削除され、「First Come First Served」（FCFS）のコードポイントに置き換えられています。

One reason to change from code points allocated by Vendor Private Use or Private Use is that such code points are allowed in production networks. Theoretically, it is possible that two vendors might use the same code point value with different meanings. If such a code is ever deployed in the same network, this could cause protocol issues that would be hard to debug.

Vendor Private UseやPrivate Useによって割り当てられるコードポイントをやめる理由の1つは、そのようなコードポイントが本番ネットワークでの使用を許されていることです。理論上は、2つのベンダーが同じコードポイント値を異なる意味で使う可能性があります。そのようなコードが同じネットワークに展開された場合、デバッグが困難なプロトコル上の問題を引き起こすおそれがあります。

With FCFS code points, this will not happen. Vendors that have existing code using Vendor Private Use or Private Use code points should register those code points as FCFS code points as soon as this document is published as an RFC.

FCFSのコードポイントであれば、このようなことは起こりません。Vendor Private UseやPrivate Useのコードポイントを使う既存のコードを持つベンダーは、この文書がRFCとして発行されたらすぐに、それらのコードポイントをFCFSのコードポイントとして登録すべきです。

The "Sub-TLVs for TLV Type 9" subregistry is not updated.

「Sub-TLVs for TLV Type 9」サブレジストリーは更新しません。

Third, according to [RFC8029], some code points (TLVs and sub-TLVs) are called "mandatory" or "optional". Contrary to how other RFCs use these words, indicating that it is mandatory or optional to include the code points in a message, [RFC8029] uses these words to indicate that an action might or might not be mandatory. This document updates [RFC8029] to drop the words "mandatory" and "optional", and the text is changed to focus on what should be done.

3つ目に、[RFC8029]によると、一部のコードポイント（TLVおよびサブTLV）は「mandatory（必須）」または「optional（任意）」と呼ばれています。他のRFCではこれらの語をメッセージにコードポイントを含めることが必須か任意かを示すために使いますが、それとは異なり、[RFC8029]は、ある動作が必須であるかどうかを示すためにこれらの語を使っています。この文書は[RFC8029]を更新して「mandatory」と「optional」という語を使わないようにし、何をすべきかに焦点を当てた記述に変更します。

1.2. 用語

This section lists terms that are used when discussing the hierarchy of IANA registries (Section 1.2.1), and abbreviations used in IANA registries are updated in this document (Section 1.2.2).

このセクションでは、IANAレジストリーの階層について述べる際に使用する用語（Section 1.2.1）と、この文書で更新するIANAレジストリーで使われている略語（Section 1.2.2）を挙げます。

1.2.1. Terminology Used in This Document

1.2.1. この文書で使用する用語

Terms related to IANA registries are used as follows in this document:

この文書では、IANAレジストリーに関連する用語を次のように使います。

Namespace
A namespace is a top-level registry. An example could be "Multiprotocol Label Switching (MPLS) Label Switched Paths (LSPs) Ping Parameters" [IANA-LSP-PING]. A namespace is most often a container for registries that hold code points that share some affinity.
Registry
An IANA registry holds code points and lists the registration procedures and allocation for these code points. One example would be the "TLVs" registry [IANA-TLV-reg].
Subregistry
A subregistry is used when a code point, or a set of code points allocated in a single registry, needs "sub-code-points" scoped by the code point or the set of code points. An example of a subregistry that holds code points for more than one TLV is "Sub-TLVs for TLV Types 1, 16, and 21" [IANA-Sub-1-16-21].
名前空間（Namespace）
名前空間は、最上位のレジストリーです。例としては「Multiprotocol Label Switching (MPLS) Label Switched Paths (LSPs) Ping Parameters」[IANA-LSP-PING]が挙げられます。名前空間は、多くの場合、何らかの関連性を持つコードポイントを保持するレジストリーの入れ物です。
レジストリー（Registry）
IANAレジストリーは、コードポイントを保持し、それらのコードポイントの登録手続きと割り当てを列挙します。例としては「TLVs」レジストリー[IANA-TLV-reg]が挙げられます。
サブレジストリー（Subregistry）
サブレジストリーは、あるコードポイント、または1つのレジストリーで割り当てられたコードポイントの集合が、そのコードポイントまたはコードポイントの集合をスコープとする「サブコードポイント」を必要とする場合に使用します。複数のTLVのコードポイントを保持するサブレジストリーの例としては、「Sub-TLVs for TLV Types 1, 16, and 21」[IANA-Sub-1-16-21]があります。

2. Updating the Message Types, Reply Modes, and Return Codes Registries

2. Message Types、Reply Modes、Return Codesの各レジストリーの更新

The following changes have been made to the "Message Types" [IANA-MT], "Reply Modes" [IANA-RM], and "Return Codes" [IANA-RC] registries.

「Message Types」[IANA-MT]、「Reply Modes」[IANA-RM]、「Return Codes」[IANA-RC]の各レジストリーに次の変更を加えました。

  • In the listing of assigned code points, the term "Vendor Private Use" is changed to "Private Use" for the 252-255 range. The registration procedures have been updated to reflect this.
  • The registration procedure "Specification Required" is changed to "RFC Required" and the note "Experimental RFC needed" is removed for the 192-247 range.
  • A small set of four code points (248-251) for Experimental Use is added by reducing the "RFC Required" range. The registration procedures have been updated to reflect this.
  • A note "Reserved, not to be assigned" has been added for the registration procedures of the "Private Use" and "Experimental Use" ranges.

  • In the lists that capture the assignment status, the fields that are reserved, i.e., 0 (zero), Private Use, and Experimental Use, are clearly marked as such.

    • Note that in the "Return Codes" registry [IANA-RC], the code point "0" has already been assigned. This assignment is not changed, and in this registry, the code point "0" continues to be assigned as "No Return Code".
  • 割り当て済みコードポイントの一覧において、252〜255の範囲について「Vendor Private Use」という用語を「Private Use」に変更します。登録手続きもこれを反映するように更新しました。
  • 192〜247の範囲について、登録手続き「Specification Required」を「RFC Required」に変更し、「Experimental RFC needed」という注記を削除します。
  • 「RFC Required」の範囲を縮小して、Experimental Use用に4つのコードポイント（248〜251）からなる小さな集合を追加します。登録手続きもこれを反映するように更新しました。
  • 「Private Use」と「Experimental Use」の範囲の登録手続きに、「Reserved, not to be assigned」という注記を追加しました。

  • 割り当て状況を記録する一覧では、予約済みのフィールド、すなわち0（ゼロ）、Private Use、Experimental Useを、そのことがわかるように明示します。

    • 「Return Codes」レジストリー[IANA-RC]では、コードポイント「0」がすでに割り当てられていることに注意してください。この割り当ては変更せず、このレジストリーではコードポイント「0」は引き続き「No Return Code」として割り当てられます。

The new registration procedures, the registry layouts, and the new assignments for these registries are found in Section 6.1.

これらのレジストリーの新しい登録手続き、レジストリーのレイアウト、新しい割り当ては、Section 6.1にあります。

3. Updating the TLV and Sub-TLV Registries

3. TLVおよびサブTLVのレジストリーの更新

3.1. General Principles for the LSP Ping TLV and Sub-TLV Registries

3.1. LSP PingのTLVおよびサブTLVのレジストリーに関する一般原則

The following principles apply to the processing of any TLV from any of the LSP Ping TLV and sub-TLV IANA registries.

LSP PingのTLVおよびサブTLVのIANAレジストリーのいずれかに含まれるTLVを処理する際には、次の原則が適用されます。

  • All TLVs and sub-TLVs with a type in the range 0-32767 require a response if they are not recognized.
  • All TLVs and sub-TLVs in the range 32768-65535 can be silently dropped if they are not recognized. Alternatively, the receiver may step over the unrecognized TLV or send an error message.

3.1.1. Unrecognized Experimental Use TLVs and Sub-TLVs

3.1.1. 認識できないExperimental UseのTLVおよびサブTLV

Unrecognized TLVs and sub-TLVs in the Experimental Use and FCFS ranges are handled as any other unrecognized TLV or sub-TLV.

Experimental UseおよびFCFSの範囲にある認識できないTLVおよびサブTLVは、他の認識できないTLVまたはサブTLVと同様に扱います。

  • If the unrecognized TLV or sub-TLV is from the Experimental Use range (31740-31743) or from the FCFS range (31744-32767), a Return Code of 2 ("One or more of the TLVs was not understood") must be sent in the echo response.
  • If a TLV or sub-TLV from the Experimental Use range (64508-64511) or from the FCFS range (64512-65535) is unrecognized, then the receiver can silently drop the TLV. Alternatively, the receiver may step over the unrecognized TLV or send an error message.
  • 認識できないTLVまたはサブTLVがExperimental Useの範囲（31740〜31743）またはFCFSの範囲（31744〜32767）のものである場合、エコー応答でReturn Code 2（「One or more of the TLVs was not understood」）を送信しなければなりません。
  • Experimental Useの範囲（64508〜64511）またはFCFSの範囲（64512〜65535）のTLVまたはサブTLVを認識できない場合、受信者はそのTLVを黙って破棄できます。あるいは、受信者は認識できないTLVを読み飛ばすことも、エラーメッセージを送信することもできます。

The IETF does not prescribe how recognized or unrecognized Experimental Use and Private Use TLVs and sub-TLVs are handled in experimental or private networks; that is up to the agency running the experimental or the private network. The statement above describes how standards-compliant implementations must treat the unrecognized TLVs and sub-TLVs from these ranges.

IETFは、実験的ネットワークやプライベートネットワークにおいて、認識できる、または認識できないExperimental UseおよびPrivate UseのTLVおよびサブTLVをどのように扱うかを規定しません。それは、その実験的ネットワークまたはプライベートネットワークを運用する組織に委ねられます。上記の記述は、標準に準拠した実装がこれらの範囲の認識できないTLVおよびサブTLVをどのように扱わなければならないかを説明するものです。

4. Updates to Related RFCs

4. 関連するRFCの更新

Some referenced RFCs use the concept "mandatory TLVs" and "mandatory sub-TLVs" to indicate that, if a TLV or sub-TLV of the range 0-32767 in a message is not understood, an error message needs to be sent in response.

参照されている一部のRFCでは、メッセージ内の0〜32767の範囲のTLVまたはサブTLVを理解できない場合に応答としてエラーメッセージを送信する必要があることを示すために、「必須TLV（mandatory TLVs）」および「必須サブTLV（mandatory sub-TLVs）」という概念を使っています。

The same RFCs use "optional TLVs" and "optional sub-TLVs" to mean TLVs or sub-TLVs that can be silently ignored if not recognized.

同じRFCでは、認識できない場合に黙って無視できるTLVまたはサブTLVを意味するために、「任意TLV（optional TLVs）」および「任意サブTLV（optional sub-TLVs）」という用語を使っています。

Since other RFCs use "mandatory TLVs" and "mandatory sub-TLVs" to indicate TLVs and sub-TLVs that must be present in a message, we want to discontinue the use of "mandatory" to indicate TLVs and sub-TLVs that require an error message in response if not understood. The changes to the RFCs below align with this practice.

他のRFCでは、「必須TLV」および「必須サブTLV」を、メッセージ内に存在しなければならないTLVおよびサブTLVを示すために使っているため、理解できない場合に応答としてエラーメッセージを必要とするTLVおよびサブTLVを示すために「mandatory」を使うことはやめたいと考えています。以下のRFCに対する変更は、この方針に沿ったものです。
