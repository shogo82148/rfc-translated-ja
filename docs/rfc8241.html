RFC 8241

Interface to the Routing System (I2RS) Security-Related Requirements

RFC 8241

ルーティングシステムへのインターフェイス（I2RS）のセキュリティー関連の要件

Abstract

概要

This document presents security-related requirements for the Interface to the Routing System (I2RS) protocol, which provides a new interface to the routing system described in the I2RS architecture document (RFC 7921). The I2RS protocol is implemented by reusing portions of existing IETF protocols and adding new features to them. One such reuse is of the security features of a secure transport (e.g., Transport Layer Security (TLS), Secure SHell (SSH) Protocol, Datagram TLS (DTLS)) such as encryption, message integrity, mutual peer authentication, and anti-replay protection. The new I2RS features to consider from a security perspective are as follows: a priority mechanism to handle multi-headed write transactions, an opaque secondary identifier that identifies an application using the I2RS client, and an extremely constrained read-only non-secure transport.

この文書は、ルーティングシステムへのインターフェイス（Interface to the Routing System、I2RS）プロトコルのセキュリティー関連の要件を示します。I2RSプロトコルは、I2RSアーキテクチャー文書（RFC 7921）で説明されている、ルーティングシステムへの新しいインターフェイスを提供します。 I2RSプロトコルは、既存のIETFプロトコルの一部を再利用し、それらに新しい機能を追加することによって実装されます。 そのような再利用の1つが、安全なトランスポート（例: Transport Layer Security（TLS）、Secure SHell（SSH）プロトコル、Datagram TLS（DTLS））のセキュリティー機能（暗号化、メッセージの完全性、相互ピア認証、リプレイ攻撃対策など）の再利用です。 セキュリティーの観点から考慮すべきI2RSの新しい機能は次のとおりです。マルチヘッドの書き込みトランザクションを処理するための優先度メカニズム、I2RSクライアントを使用するアプリケーションを識別する不透明な二次識別子、そして極めて制約された読み取り専用の安全でないトランスポートです。

1. Introduction

1. はじめに

The Interface to the Routing System (I2RS) protocol provides read and write access to information and state within the routing system. An I2RS client interacts with one or more I2RS agents to collect information from network routing systems. [RFC7921] describes the architecture of this interface, and this document assumes the reader is familiar with this architecture and its definitions.

ルーティングシステムへのインターフェイス（Interface to the Routing System、I2RS）プロトコルは、ルーティングシステム内の情報と状態に対する読み取りおよび書き込みのアクセスを提供します。 I2RSクライアントは、1つ以上のI2RSエージェントとやり取りして、ネットワークのルーティングシステムから情報を収集します。 [RFC7921]はこのインターフェイスのアーキテクチャーを説明しており、この文書は、読者がこのアーキテクチャーとその定義に精通していることを前提としています。

The I2RS interface is instantiated by the I2RS protocol connecting an I2RS client and an I2RS agent associated with a routing system. The I2RS protocol is implemented by reusing portions of existing IETF protocols and adding new features to them. As a reuse protocol, it can be considered a higher-layer protocol because it can be instantiated in multiple management protocols (e.g., NETCONF [RFC6241] or RESTCONF [RFC8040]) operating over a secure transport. These protocols are what provide its security.

I2RSインターフェイスは、I2RSクライアントと、ルーティングシステムに関連付けられたI2RSエージェントとを接続するI2RSプロトコルによって具体化されます。 I2RSプロトコルは、既存のIETFプロトコルの一部を再利用し、それらに新しい機能を追加することによって実装されます。 再利用型のプロトコルとして、I2RSプロトコルは、安全なトランスポート上で動作する複数の管理プロトコル（例: NETCONF [RFC6241]やRESTCONF [RFC8040]）の中で具体化できるため、上位層プロトコルとみなすことができます。 これらのプロトコルが、I2RSプロトコルのセキュリティーを提供するものです。

This document is part of a suite of documents outlining requirements for the I2RS protocol, which also includes the following:

この文書は、I2RSプロトコルの要件を概説する一連の文書の一部であり、この一連の文書には次のものも含まれます。

  • "An Architecture for the Interface to the Routing System" [RFC7921]
  • "I2RS Ephemeral State Requirements" [RFC8242]
  • "Interface to the Routing System (I2RS) Traceability: Framework and Information Model" (which discusses traceability) [RFC7923]
  • "Requirements for Subscription to YANG Datastores" (which highlights the publication/subscription requirements) [RFC7922]
  • 「An Architecture for the Interface to the Routing System」[RFC7921]
  • 「I2RS Ephemeral State Requirements」[RFC8242]
  • 「Interface to the Routing System (I2RS) Traceability: Framework and Information Model」（追跡可能性について論じています）[RFC7923]
  • 「Requirements for Subscription to YANG Datastores」（パブリケーション／サブスクリプションの要件を取り上げています）[RFC7922]

Since the I2RS "higher-layer" protocol changes the interface to the routing systems, it is important that implementers understand the new security requirements for the environment the I2RS protocol operates in. A summary of the I2RS protocol security environment is found in the I2RS architecture [RFC7921].

I2RSの「上位層」プロトコルはルーティングシステムへのインターフェイスを変えるため、実装者は、I2RSプロトコルが動作する環境に対する新しいセキュリティー要件を理解することが重要です。 I2RSプロトコルのセキュリティー環境の概要は、I2RSアーキテクチャー[RFC7921]にあります。

I2RS reuses the secure transport protocols (TLS, SSH, DTLS) that support encryption, message integrity, peer authentication, and key distribution protocols. Optionally, implementers may utilize Authentication, Authorization, and Accounting (AAA) protocols (Radius over TLS or Diameter over TLS) to securely distribute identity information.

I2RSは、暗号化、メッセージの完全性、ピア認証、および鍵配布プロトコルをサポートする安全なトランスポートプロトコル（TLS、SSH、DTLS）を再利用します。 オプションとして、実装者は、アイデンティティー情報を安全に配布するために、認証・認可・アカウンティング（Authentication, Authorization, and Accounting、AAA）プロトコル（Radius over TLSまたはDiameter over TLS）を利用できます。

Section 2 highlights some of the terminology and concepts that the reader is required to be familiar with.

セクション2では、読者が精通している必要のある用語と概念のいくつかを取り上げます。

Section 3 provides an overview of security features and protocols being reused (Section 3.1), lists the new security features being required (Section 3.2), and explores how existing and new security features and protocols would be paired with existing IETF management protocols (Section 3.3).

セクション3では、再利用されるセキュリティー機能とプロトコルの概要を示し（セクション3.1）、必要とされる新しいセキュリティー機能を列挙し（セクション3.2）、既存および新規のセキュリティー機能とプロトコルが既存のIETF管理プロトコルとどのように組み合わされるかを検討します（セクション3.3）。

The new features I2RS extends to these protocols are a priority mechanism to handle multi-headed writes, an opaque secondary identifier to allow traceability of an application utilizing a specific I2RS client to communicate with an I2RS agent, and non-secure transport constrained to be used only for read-only data, which may include publicly available data (e.g., public BGP events, public telemetry information, web service availability) and some legacy data.

I2RSがこれらのプロトコルに対して拡張する新しい機能は、マルチヘッドの書き込みを処理するための優先度メカニズム、特定のI2RSクライアントを利用してI2RSエージェントと通信するアプリケーションの追跡可能性を可能にする不透明な二次識別子、そして読み取り専用データにのみ使用するよう制約された安全でないトランスポートです。この読み取り専用データには、公開されているデータ（例: 公開のBGPイベント、公開のテレメトリー情報、Webサービスの可用性）と一部のレガシーデータが含まれる場合があります。

Section 4 provides the I2RS protocol security requirements of several security features. Protocols designed to be I2RS higher-layer protocols need to fulfill these security requirements.

セクション4では、いくつかのセキュリティー機能に関するI2RSプロトコルのセキュリティー要件を示します。 I2RS上位層プロトコルとして設計されるプロトコルは、これらのセキュリティー要件を満たす必要があります。

3. Security Features and Protocols: Reused and New

3. セキュリティー機能とプロトコル: 再利用するものと新しいもの

3.1. Security Protocols Reused by the I2RS Protocol

3.1. I2RSプロトコルが再利用するセキュリティープロトコル

I2RS requires a secure transport protocol and key distribution protocols. The secure transport for I2RS requires one to provide peer authentication. In addition, the features required for I2RS messages are confidentiality, authentication, and replay protection. According to [RFC8095], the secure transport protocols that support peer authentication, confidentiality, data integrity, and replay protection are the following:

I2RSは、安全なトランスポートプロトコルと鍵配布プロトコルを必要とします。 I2RSの安全なトランスポートには、ピア認証を提供することが求められます。 さらに、I2RSメッセージに求められる機能は、機密性、認証、およびリプレイ保護です。 [RFC8095]によれば、ピア認証、機密性、データ完全性、およびリプレイ保護をサポートする安全なトランスポートプロトコルは次のとおりです。

  1. TLS [RFC5246] over TCP or Stream Control Transmission Protocol (SCTP)
  2. DTLS over UDP with replay detection and an anti-DoS stateless cookie mechanism required for the I2RS protocol and the DTLS options of record-size negotiation and conveyance of the Don't Fragment (DF) bit are set for IPv4, or no fragmentation extension headers for IPv6 to be optional in deployments are allowed by the I2RS protocol
  3. HTTP over TLS (over TCP or SCTP)
  4. HTTP over DTLS (with the requirements and optional features specified above in item 2)
  1. TCPまたはStream Control Transmission Protocol（SCTP）上のTLS [RFC5246]
  2. UDP上のDTLS。I2RSプロトコルには、リプレイ検出とDoS対策のステートレスなクッキーメカニズムが必要です。また、I2RSプロトコルでは、レコードサイズのネゴシエーションとIPv4でのDon't Fragment（DF）ビットの伝達というDTLSのオプション、またはIPv6でフラグメンテーション拡張ヘッダーを使用しないことを、展開においてオプションとすることが認められます
  3. HTTP over TLS（TCPまたはSCTP上）
  4. HTTP over DTLS（上記の項目2で規定した要件とオプション機能を伴うもの）

As detailed in Section 3.3, the following protocols would need to be extended to provide confidentiality, data integrity, peer authentication, and key distribution and to run over a secure transport (TLS or DTLS):

セクション3.3で詳しく述べるように、次のプロトコルは、機密性、データ完全性、ピア認証、および鍵配布を提供し、安全なトランスポート（TLSまたはDTLS）上で動作するように拡張する必要があります。

  • IP Flow Information Export (IPFIX) over SCTP, TCP, or UDP
  • Forwarding and Control Element Separation (ForCES) Transport Mapping Layer (TML) over SCTP
  • SCTP、TCP、またはUDP上のIP Flow Information Export（IPFIX）
  • SCTP上のForwarding and Control Element Separation（ForCES）Transport Mapping Layer（TML）

The specific type of key management protocols an I2RS secure transport uses depends on the transport. Key management protocols utilized for the I2RS protocols SHOULD support automatic rotation.

I2RSの安全なトランスポートが使用する鍵管理プロトコルの具体的な種類は、そのトランスポートに依存します。 I2RSプロトコルに利用する鍵管理プロトコルは、自動的なローテーションをサポートするべきです（SHOULD）。

An I2RS implementer may use AAA protocols over secure transport to distribute the identities for the I2RS client, I2RS agent, and role-authorization information. Two AAA protocols are as follows: Diameter [RFC6733] and Radius [RFC2865]. To provide I2RS peer identities with the best security, the AAA protocols MUST be run over a secure transport (Diameter over secure transport (TLS over TCP) [RFC6733]), Radius over a secure transport (TLS) [RFC6614]).

I2RSの実装者は、I2RSクライアント、I2RSエージェントのアイデンティティーとロール認可の情報を配布するために、安全なトランスポート上のAAAプロトコルを使用できます。 2つのAAAプロトコルとして、Diameter [RFC6733]とRadius [RFC2865]があります。 I2RSピアのアイデンティティーに最良のセキュリティーを提供するために、AAAプロトコルは安全なトランスポート上で動作させなければなりません（MUST）（安全なトランスポート（TLS over TCP）上のDiameter [RFC6733]）、安全なトランスポート（TLS）上のRadius [RFC6614]）。

3.2. New Features Related to Security

3.2. セキュリティーに関連する新しい機能

The new features are priority, an opaque secondary identifier, and a non-secure protocol for read-only data constrained to specific standard usages. The I2RS protocol allows multi-headed control by several I2RS clients. This multi-headed control is based on the assumption that the operator deploying the I2RS clients, I2RS agents, and the I2RS protocol will coordinate the read, write, and notification scope so the I2RS clients will not contend for the same write scope. However, just in case there is an unforeseen overlap of I2RS clients attempting to write a particular piece of data, the I2RS architecture [RFC7921] provides the concept of each I2RS client having a priority. The I2RS client with the highest priority will have its write succeed. This document specifies requirements for this new concept of priority (see Section 4.3).

新しい機能は、優先度、不透明な二次識別子、および特定の標準的な用途に制約された読み取り専用データのための安全でないプロトコルです。 I2RSプロトコルは、複数のI2RSクライアントによるマルチヘッド制御（multi-headed control）を可能にします。 このマルチヘッド制御は、I2RSクライアント、I2RSエージェント、およびI2RSプロトコルを展開する運用者が、読み取り、書き込み、および通知のスコープを調整し、I2RSクライアントが同じ書き込みスコープを奪い合わないようにするという前提に基づいています。 しかし、特定のデータを書き込もうとするI2RSクライアントが予期せず重なる場合に備えて、I2RSアーキテクチャー[RFC7921]は、各I2RSクライアントが優先度を持つという概念を提供しています。 最も高い優先度を持つI2RSクライアントの書き込みが成功します。 この文書は、この優先度という新しい概念に対する要件を規定します（セクション4.3を参照）。

The opaque secondary identifier identifies an application that uses communication from the I2RS client to I2RS agent to manage the routing system. The secondary identifier is opaque to the I2RS protocol. In order to protect personal privacy, the secondary identifier should not contain identifiable personal information.

不透明な二次識別子は、ルーティングシステムを管理するためにI2RSクライアントからI2RSエージェントへの通信を使用するアプリケーションを識別します。 二次識別子は、I2RSプロトコルにとって不透明です。 個人のプライバシーを保護するために、二次識別子には個人を特定できる情報を含めるべきではありません。

The last new feature related to I2RS security is the ability to allow nonconfidential data to be transferred over a non-secure transport. It is expected that most I2RS data models will describe information that will be transferred with confidentiality. Therefore, any model that transfers data over a non-secure transport is marked. The use of a non-secure transport is optional, and an implementer SHOULD create knobs that allow data marked as nonconfidential to be sent over a secure transport.

I2RSセキュリティーに関連する最後の新しい機能は、機密でない（nonconfidential）データを安全でないトランスポート上で転送できるようにする機能です。 ほとんどのI2RSデータモデルは、機密性を保って転送される情報を記述することが想定されています。 そのため、安全でないトランスポート上でデータを転送するモデルにはすべて、その旨が示されます。 安全でないトランスポートの使用はオプションであり、実装者は、機密でないとされたデータを安全なトランスポート上で送信できるようにするノブを作成すべきです（SHOULD）。

Nonconfidential data can only be data with read-scope or notification-scope transmission of events. Nonconfidential data cannot have write-scope or notification-scope configuration. Examples of nonconfidential data would be the telemetry information that is publicly known (e.g., BGP route-views data or website status data) or some legacy data (e.g., interface) that cannot be transported using secure transport. The IETF I2RS data models MUST indicate (in the model) the specific data that is nonconfidential.

機密でないデータは、読み取りスコープのデータ、または通知スコープでのイベントの送信のデータに限られます。 機密でないデータは、書き込みスコープや通知スコープの設定を持つことはできません。 機密でないデータの例としては、一般に知られているテレメトリー情報（例: BGPのroute-viewsのデータやWebサイトのステータスのデータ）や、安全なトランスポートを使用して転送することができない一部のレガシーデータ（例: インターフェイス）が挙げられます。 IETFのI2RSデータモデルは、機密でない特定のデータを（モデルの中で）示さなければなりません（MUST）。

Most I2RS data models will expect that the information described in the model will be transferred with confidentiality.

ほとんどのI2RSデータモデルは、モデルで記述される情報が機密性を保って転送されることを想定しています。

4.1. I2RS Peer (Agent and Client) Identity Authentication

4.1. I2RSピア（エージェントとクライアント）のアイデンティティー認証

Requirements:

要件:

SEC-REQ-01:
All I2RS clients and agents MUST have an identity and at least one unique identifier for each party in the I2RS protocol context.
SEC-REQ-02:
The I2RS protocol MUST utilize these identifiers for mutual identification of the I2RS client and agent.
SEC-REQ-03:
Identifier distribution and the loading of these identifiers into the I2RS agent and client SHOULD occur outside the I2RS protocol prior to the I2RS protocol establishing a connection between I2RS client and agent. AAA protocols MAY be used to distribute these identifiers, but other mechanism can be used.
SEC-REQ-01:
すべてのI2RSクライアントとエージェントは、アイデンティティーと、I2RSプロトコルのコンテキストにおける各当事者のための少なくとも1つの一意な識別子を持たなければなりません（MUST）。
SEC-REQ-02:
I2RSプロトコルは、I2RSクライアントとエージェントの相互識別のためにこれらの識別子を利用しなければなりません（MUST）。
SEC-REQ-03:
識別子の配布と、I2RSエージェントおよびクライアントへのこれらの識別子のロードは、I2RSプロトコルがI2RSクライアントとエージェントの間の接続を確立する前に、I2RSプロトコルの外部で行われるべきです（SHOULD）。 これらの識別子の配布にはAAAプロトコルを使用してもよいです（MAY）が、他のメカニズムを使用することもできます。

Explanation:

説明:

These requirements are for I2RS peer (I2RS agent and client) authentication. A secure transport (e.g., TLS) will authenticate based on these identities, but these identities are for the I2RS management layer. A AAA protocol distributing I2RS identity information SHOULD transport its information over a secure transport.

これらの要件は、I2RSピア（I2RSエージェントとクライアント）の認証のためのものです。 安全なトランスポート（例: TLS）はこれらのアイデンティティーに基づいて認証を行いますが、これらのアイデンティティーはI2RS管理層のためのものです。 I2RSのアイデンティティー情報を配布するAAAプロトコルは、その情報を安全なトランスポート上で転送すべきです（SHOULD）。

4.2. Identity Validation before Role-Based Message Actions

4.2. ロールに基づくメッセージアクションの前のアイデンティティー検証

Requirements:

要件:

SEC-REQ-04:
An I2RS agent receiving a request from an I2RS client MUST confirm that the I2RS client has a valid identity.
SEC-REQ-05:
An I2RS client receiving an I2RS message over a secure transport MUST confirm that the I2RS agent has a valid identifier.
SEC-REQ-06:
An I2RS agent receiving an I2RS message over a non-secure transport MUST confirm that the content is suitable for transfer over such a transport.
SEC-REQ-04:
I2RSクライアントからリクエストを受信したI2RSエージェントは、そのI2RSクライアントが有効なアイデンティティーを持っていることを確認しなければなりません（MUST）。
SEC-REQ-05:
安全なトランスポート上でI2RSメッセージを受信したI2RSクライアントは、I2RSエージェントが有効な識別子を持っていることを確認しなければなりません（MUST）。
SEC-REQ-06:
安全でないトランスポート上でI2RSメッセージを受信したI2RSエージェントは、その内容がそのようなトランスポート上での転送に適していることを確認しなければなりません（MUST）。

Explanation:

説明:

Each I2RS client has a scope based on its identity and the security roles (read, write, or events) associated with that identity, and that scope must be considered in processing an I2RS message sent on a communication channel. An I2RS communication channel may utilize multiple transport sessions or establish a transport session and then close the transport session. Therefore, it is important that the I2RS peers operate utilizing valid peer identities when a message is processed rather than checking if a transport session exists.

各I2RSクライアントは、そのアイデンティティーと、そのアイデンティティーに関連付けられたセキュリティーロール（読み取り、書き込み、またはイベント）に基づくスコープを持ち、通信チャネル上で送信されたI2RSメッセージを処理する際には、そのスコープを考慮しなければなりません。 I2RS通信チャネルは、複数のトランスポートセッションを利用することも、トランスポートセッションを確立してからそのトランスポートセッションを閉じることもあります。 そのため、I2RSピアは、トランスポートセッションが存在するかどうかを確認するのではなく、メッセージが処理される時点で有効なピアのアイデンティティーを利用して動作することが重要です。

During the time period when a secure transport session is active, the I2RS agent SHOULD assume that the I2RS client's identity remains valid. Similarly, while a secure connection exists that included validating the I2RS agent's identity and a message is received via that connection, the I2RS client SHOULD assume that the I2RS agent's identity remains valid.

安全なトランスポートセッションがアクティブである期間中、I2RSエージェントは、I2RSクライアントのアイデンティティーが有効なままであるとみなすべきです（SHOULD）。 同様に、I2RSエージェントのアイデンティティーの検証を含む安全な接続が存在し、その接続を介してメッセージを受信した場合、I2RSクライアントは、I2RSエージェントのアイデンティティーが有効なままであるとみなすべきです（SHOULD）。

The definition of what constitutes a valid identity or a valid identifier MUST be defined by the I2RS protocol.

何が有効なアイデンティティーまたは有効な識別子にあたるかの定義は、I2RSプロトコルによって定義されなければなりません（MUST）。

4.3. Peer Identity, Priority, and Client Redundancy

4.3. ピアのアイデンティティー、優先度、およびクライアントの冗長性

Requirements:

要件:

SEC-REQ-07:
Each I2RS identifier MUST be associated with just one priority.
SEC-REQ-08:
Each identifier is associated with one secondary identifier during a particular I2RS transaction (e.g., read/write sequence), but the secondary identifier may vary during the time a connection between the I2RS client and I2RS agent is active.
SEC-REQ-07:
各I2RS識別子は、ただ1つの優先度に関連付けられなければなりません（MUST）。
SEC-REQ-08:
各識別子は、特定のI2RSトランザクション（例: 読み取り／書き込みのシーケンス）の間は1つの二次識別子に関連付けられますが、I2RSクライアントとI2RSエージェントの間の接続がアクティブである期間中に、二次識別子が変わることがあります。

Explanation:

説明:

The I2RS architecture also allows multiple I2RS clients with unique identities to connect to an I2RS agent (see Section 7.8 of [RFC7921]). The I2RS deployment using multiple clients SHOULD coordinate this multi-headed control of I2RS agents by I2RS clients so no conflict occurs in the write scope. However, in the case of conflict on a write-scope variable, the error resolution mechanisms defined by the I2RS architecture multi-headed control (Section 7.8 of [RFC7921]) allow the I2RS agent to deterministically choose one I2RS client. The I2RS client with highest priority is given permission to write the variable, and the second client receives an error message.

I2RSアーキテクチャーでは、一意なアイデンティティーを持つ複数のI2RSクライアントが1つのI2RSエージェントに接続することも認められています（[RFC7921]のセクション7.8を参照）。 複数のクライアントを使用するI2RSの展開では、書き込みスコープで競合が発生しないように、I2RSクライアントによるI2RSエージェントのこのマルチヘッド制御を調整すべきです（SHOULD）。 しかし、書き込みスコープの変数で競合が発生した場合には、I2RSアーキテクチャーのマルチヘッド制御（[RFC7921]のセクション7.8）で定義されたエラー解決メカニズムにより、I2RSエージェントは決定論的に1つのI2RSクライアントを選択できます。 最も高い優先度を持つI2RSクライアントにその変数を書き込む許可が与えられ、2番目のクライアントはエラーメッセージを受け取ります。

A single I2RS client may be associated with multiple applications with different tasks (e.g., weekly configurations or emergency configurations). The secondary identity is an opaque value that the I2RS client passes to the I2RS agent so that this opaque value can be placed in the tracing file or event stream to identify the application using the communication from I2RS client to agent. The I2RS client is trusted to simply assert the secondary identifier.

単一のI2RSクライアントが、異なるタスク（例: 週次の設定や緊急時の設定）を持つ複数のアプリケーションに関連付けられることがあります。 二次アイデンティティーは、I2RSクライアントがI2RSエージェントに渡す不透明な値であり、この不透明な値をトレースファイルやイベントストリームに記録して、I2RSクライアントからエージェントへの通信を使用しているアプリケーションを識別できるようにします。 I2RSクライアントは、単に二次識別子を表明するものとして信頼されます。

One example of the use of the secondary identity is the situation where an operator of a network has two applications that use an I2RS client. The first application is a weekly configuration application that uses the I2RS protocol to change configurations. The second application allows operators to makes emergency changes to routers in the network. Both of these applications use the same I2RS client to write to an I2RS agent. In order for traceability to determine which application (weekly configuration or emergency) wrote some configuration changes to a router, the I2RS client sends a different opaque value for each of the applications. The weekly configuration secondary opaque value could be "xzzy-splot" and the emergency secondary opaque value could be "splish-splash".

二次アイデンティティーの使用例の1つは、ネットワークの運用者が、I2RSクライアントを使用する2つのアプリケーションを持っている状況です。 1つ目のアプリケーションは、I2RSプロトコルを使用して設定を変更する週次設定アプリケーションです。 2つ目のアプリケーションは、運用者がネットワーク内のルーターに緊急の変更を加えられるようにするものです。 これらのアプリケーションはどちらも、同じI2RSクライアントを使用してI2RSエージェントに書き込みを行います。 どのアプリケーション（週次設定か緊急時か）がルーターに設定変更を書き込んだのかを追跡可能性によって判断できるように、I2RSクライアントはアプリケーションごとに異なる不透明な値を送信します。 週次設定の二次的な不透明な値は「xzzy-splot」、緊急時の二次的な不透明な値は「splish-splash」とすることができます。

A second example is if the I2RS client is used for the monitoring of critical infrastructure. The operator of a network using the I2RS client may desire I2RS client redundancy where the monitoring application with the I2RS client is deployed on two different boxes with the same I2RS client identity (see Section 4.3 of [RFC7921]). These two monitoring applications pass to the I2RS client whether the application is the primary or back-up application, and the I2RS client passes this information in the I2RS secondary identifier, as the figure below shows. The primary application's secondary identifier is "primary-monitoring", and the back-up application secondary identifier is "backup-monitoring". The I2RS tracing information will include the secondary identifier information along with the transport information in the tracing file in the agent.

2つ目の例は、I2RSクライアントが重要インフラストラクチャーの監視に使用される場合です。 I2RSクライアントを使用するネットワークの運用者は、I2RSクライアントを持つ監視アプリケーションを、同じI2RSクライアントアイデンティティーで2つの異なる機器に展開するという、I2RSクライアントの冗長性を望むかもしれません（[RFC7921]のセクション4.3を参照）。 これら2つの監視アプリケーションは、そのアプリケーションがプライマリーとバックアップのどちらのアプリケーションであるかをI2RSクライアントに渡し、次の図に示すように、I2RSクライアントはこの情報をI2RSの二次識別子に入れて渡します。 プライマリーアプリケーションの二次識別子は「primary-monitoring」、バックアップアプリケーションの二次識別子は「backup-monitoring」です。 I2RSのトレース情報には、エージェント内のトレースファイルにおいて、トランスポートの情報とともに二次識別子の情報が含まれます。

4.4. Multi-Channel Transport: Secure and Non-Secure

4.4. マルチチャネルトランスポート: 安全なものと安全でないもの

Requirements:

要件:

SEC-REQ-09:
The I2RS protocol MUST be able to transfer data over a secure transport and optionally MAY be able to transfer data over a non-secure transport. The default transport is a secure transport, and this secure transport is mandatory to implement in all I2RS agents and in any I2RS client that a) performs a write scope transaction that is sent to the I2RS agent or b) configures an Event Scope transaction. This secure transport is mandatory to use on any I2RS client's Write transaction or the configuration of an Event Scope transaction.
SEC-REQ-10:
The secure transport MUST provide data confidentiality, data integrity, and practical replay prevention.
SEC-REQ-11:
The I2RS client and I2RS agent SHOULD implement mechanisms that mitigate DoS attacks. This means the secure transport must support DoS prevention. For the non-secure transport, the I2RS higher-layer protocol MUST contain a transport management layer that considers the detection of DoS attacks and provides a warning over a secure transport channel.
SEC-REQ-12:
A secure transport MUST be associated with a key management solution that can guarantee that only the entities having sufficient privileges can get the keys to encrypt/decrypt the sensitive data.
SEC-REQ-13:
A machine-readable mechanism to indicate that a data model contains nonconfidential data MUST be provided. A non-secure transport MAY be used to publish only read-scope or notification-scope data if the associated data model indicates that the data in question is nonconfidential.
SEC-REQ-14:
The I2RS protocol MUST be able to support multiple secure transport sessions providing protocol and data communication between an I2RS agent and client. However, a single connection between I2RS agent and client MAY elect to use a single secure transport session or a single non-secure transport session conforming to the requirements above.
SEC-REQ-15:
Deployment configuration knobs SHOULD be created to allow operators to send "nonconfidential" read scope (data or event streams) over a secure transport.
SEC-REQ-16:
The I2RS protocol makes use of both secure and non-secure transports, but this use MUST NOT be done in any way that weakens the secure transport protocol used in the I2RS protocol or other contexts that do not have this requirement for mixing secure and non-secure modes of operation.
SEC-REQ-09:
I2RSプロトコルは、安全なトランスポート上でデータを転送できる必要があります（MUST）。 また、オプションとして、安全でないトランスポート上でデータを転送できてもよいです（MAY）。 デフォルトのトランスポートは安全なトランスポートであり、この安全なトランスポートは、すべてのI2RSエージェントと、a）I2RSエージェントに送信される書き込みスコープのトランザクションを実行する、またはb）イベントスコープ（Event Scope）のトランザクションを設定する、すべてのI2RSクライアントにおいて実装必須です。 この安全なトランスポートは、I2RSクライアントの書き込み（Write）トランザクションや、イベントスコープのトランザクションの設定には必ず使用しなければなりません。
SEC-REQ-10:
安全なトランスポートは、データ機密性、データ完全性、および実用的なリプレイ防止を提供しなければなりません（MUST）。
SEC-REQ-11:
I2RSクライアントとI2RSエージェントは、DoS攻撃を緩和するメカニズムを実装すべきです（SHOULD）。 これは、安全なトランスポートがDoS防止をサポートしなければならないことを意味します。 安全でないトランスポートについては、I2RS上位層プロトコルは、DoS攻撃の検出を考慮し、安全なトランスポートチャネル上で警告を提供するトランスポート管理層を含まなければなりません（MUST）。
SEC-REQ-12:
安全なトランスポートは、十分な権限を持つエンティティーだけが機密データの暗号化／復号のための鍵を取得できることを保証できる鍵管理ソリューションに関連付けられなければなりません（MUST）。
SEC-REQ-13:
データモデルが機密でないデータを含むことを示す、機械可読なメカニズムが提供されなければなりません（MUST）。 関連するデータモデルが、該当するデータが機密でないことを示している場合、安全でないトランスポートを、読み取りスコープまたは通知スコープのデータの公開に限って使用してもよいです（MAY）。
SEC-REQ-14:
I2RSプロトコルは、I2RSエージェントとクライアントの間でプロトコルとデータの通信を提供する、複数の安全なトランスポートセッションをサポートできる必要があります（MUST）。 ただし、I2RSエージェントとクライアントの間の単一の接続では、上記の要件に準拠した単一の安全なトランスポートセッションまたは単一の安全でないトランスポートセッションを使用することを選択してもよいです（MAY）。
SEC-REQ-15:
運用者が「機密でない」読み取りスコープ（データまたはイベントストリーム）を安全なトランスポート上で送信できるようにするための、展開時の設定ノブを作成すべきです（SHOULD）。
SEC-REQ-16:
I2RSプロトコルは安全なトランスポートと安全でないトランスポートの両方を利用しますが、この利用は、I2RSプロトコルで使用される安全なトランスポートプロトコルや、安全な動作モードと安全でない動作モードを混在させるというこの要件を持たない他のコンテキストで使用される安全なトランスポートプロトコルを弱めるような方法で行ってはなりません（MUST NOT）。

Explanation:

説明:

The I2RS architecture defines three scopes: read, write, and notification. Non-secure data can only be used for read and notification scopes of "nonconfidential data". The configuration of ephemeral data in the I2RS agent uses write scope either for data or for configuration of event notification streams. The requirement to use secure transport for configuration prevents accidental or malevolent entities from altering the I2RS routing system through the I2RS agent.

I2RSアーキテクチャーは、読み取り、書き込み、および通知の3つのスコープを定義しています。 安全でないデータは、「機密でないデータ」の読み取りスコープと通知スコープにのみ使用できます。 I2RSエージェントにおけるエフェメラルデータの設定では、データに対して、またはイベント通知ストリームの設定に対して、書き込みスコープを使用します。 設定に安全なトランスポートを使用するという要件により、偶発的なエンティティーや悪意のあるエンティティーが、I2RSエージェントを通じてI2RSルーティングシステムを改変することを防ぎます。

It is anticipated that the passing of most I2RS ephemeral state operational statuses SHOULD be done over a secure transport.

想定では、I2RSのエフェメラル状態の運用ステータスの受け渡しのほとんどは、安全なトランスポート上で行われるべきです（SHOULD）。

In most circumstances, the secure transport protocol will be associated with a key management system. Most deployments of the I2RS protocol will allow for automatic key management systems. Since the data models for the I2RS protocol will control key routing functions, it is important that deployments of I2RS use automatic key management systems.

ほとんどの状況において、安全なトランスポートプロトコルは鍵管理システムに関連付けられます。 I2RSプロトコルのほとんどの展開では、自動的な鍵管理システムを利用できるでしょう。 I2RSプロトコルのデータモデルは重要なルーティング機能を制御することになるため、I2RSの展開では自動的な鍵管理システムを使用することが重要です。

Per BCP 107 [RFC4107], while key management systems SHOULD be automatic, the systems MAY be manual in the following scenarios:

BCP 107 [RFC4107]によれば、鍵管理システムは自動であるべきです（SHOULD）が、次のシナリオでは手動であってもよいです（MAY）。

  1. The environment has limited bandwidth or high round-trip times.
  2. The information being protected has low value.
  3. The total volume of traffic over the entire lifetime of the long-term session key will be very low.
  4. The scale of the deployment is limited.
  1. 環境の帯域幅が限られているか、ラウンドトリップ時間が長い。
  2. 保護される情報の価値が低い。
  3. 長期のセッション鍵の存続期間全体にわたるトラフィックの総量が非常に少ない。
  4. 展開の規模が限られている。

Operators deploying the I2RS protocol selecting manual key management SHOULD consider both short- and medium-term plans. Deploying automatic systems initially may save effort in the long term.

I2RSプロトコルを展開し、手動の鍵管理を選択する運用者は、短期と中期の両方の計画を検討すべきです（SHOULD）。 最初から自動的なシステムを展開することで、長期的には労力を節約できる場合があります。

4.5. Management Protocol Security

4.5. 管理プロトコルのセキュリティー

Requirements:

要件:

SEC-REQ-17:
In a critical infrastructure, certain data within routing elements is sensitive and read/write operations on such data SHOULD be controlled in order to protect its confidentiality. To achieve this, higher-layer protocols MUST utilize a secure transport, and they SHOULD provide access-control functions to protect confidentiality of the data.
SEC-REQ-18:

An integrity protection mechanism for I2RS MUST be provided that will be able to ensure the following:

  1. the data being protected is not modified without detection during its transportation,
  2. the data is actually from where it is expected to come from, and
  3. the data is not repeated from some earlier interaction the higher-layer protocol (best effort).

The I2RS higher-layer protocol operating over a secure transport provides this integrity. The I2RS higher-layer protocol operating over a non-secure transport SHOULD provide some way for the client receiving nonconfidential read-scoped or event-scoped data over the non-secure connection to detect when the data integrity is questionable; and in the event of a questionable data integrity, the I2RS client should disconnect the non-secure transport connection.

SEC-REQ-19:
The I2RS higher-layer protocol MUST provide a mechanism for message traceability (requirements in [RFC7922]) that supports the tracking higher-layer functions run across secure connection or a non-secure transport.
SEC-REQ-17:
重要インフラストラクチャーにおいては、ルーティング要素内の特定のデータは機密性が高く、そのようなデータに対する読み取り／書き込み操作は、その機密性を保護するために制御されるべきです（SHOULD）。 これを実現するために、上位層プロトコルは安全なトランスポートを利用しなければなりません（MUST）。 また、上位層プロトコルは、データの機密性を保護するためのアクセス制御機能を提供すべきです（SHOULD）。
SEC-REQ-18:

次のことを保証できる、I2RSのための完全性保護メカニズムが提供されなければなりません（MUST）。

  1. 保護されているデータが、その転送中に検出されることなく改変されないこと
  2. データが、実際に送信元として期待される場所から来ていること
  3. データが、上位層プロトコルの以前のやり取りから繰り返されたものではないこと（ベストエフォート）

安全なトランスポート上で動作するI2RS上位層プロトコルは、この完全性を提供します。 安全でないトランスポート上で動作するI2RS上位層プロトコルは、安全でない接続上で機密でない読み取りスコープまたはイベントスコープのデータを受信するクライアントが、データの完全性が疑わしい場合にそれを検出できるようにする何らかの方法を提供すべきです（SHOULD）。 そして、データの完全性が疑わしい場合には、I2RSクライアントは安全でないトランスポートの接続を切断すべきです。

SEC-REQ-19:
I2RS上位層プロトコルは、安全な接続または安全でないトランスポート上で実行される上位層の機能の追跡をサポートする、メッセージの追跡可能性のためのメカニズム（要件は[RFC7922]にあります）を提供しなければなりません（MUST）。

Explanation:

説明:

Most carriers do not want a router's configuration and data-flow statistics to be known by hackers or their competitors. While carriers may share peering information, most carriers do not share configuration and traffic statistics. To achieve this, the I2RS higher-layer protocol (e.g., NETCONF) requires access control (NETCONF Access Control Model [RFC6536]) for sensitive data needs to be provided; and the confidentiality protection on such data during transportation needs to be enforced.

ほとんどの通信事業者は、ルーターの設定やデータフローの統計情報がハッカーや競合他社に知られることを望みません。 通信事業者はピアリング情報を共有することはあっても、ほとんどの通信事業者は設定やトラフィックの統計情報を共有しません。 これを実現するために、I2RS上位層プロトコル（例: NETCONF）では、機密データに対するアクセス制御（NETCONF Access Control Model [RFC6536]）を提供する必要があり、また、そのようなデータの転送中の機密性保護を実施する必要があります。

Integrity of data is important even if the I2RS protocol is sending nonconfidential data over a non-secure connection. The ability to trace I2RS protocol messages that enact I2RS transactions provides a minimal aid to helping operators check how messages enact transactions on a secure or non-secure transport. Contextual checks on specific nonconfidential data sent over a non-secure connection may indicate the data has been modified.

I2RSプロトコルが安全でない接続上で機密でないデータを送信している場合であっても、データの完全性は重要です。 I2RSトランザクションを実行するI2RSプロトコルのメッセージを追跡できることは、安全なトランスポートまたは安全でないトランスポート上でメッセージがどのようにトランザクションを実行するかを運用者が確認するための、最小限の助けになります。 安全でない接続上で送信された特定の機密でないデータに対するコンテキストのチェックによって、データが改変されたことがわかる場合があります。

4.6. Role-Based Data Model Security

4.6. ロールベースのデータモデルのセキュリティー

In order to make access control more manageable, the I2RS architecture [RFC7921] specifies a "role" to categorize users into a group (rather than handling them individually) for access-control purposes (role-based access control). Therefore, an I2RS role specifies the access control for a group as being read, write, or notification.

アクセス制御をより管理しやすくするために、I2RSアーキテクチャー[RFC7921]は、アクセス制御の目的で（ユーザーを個別に扱うのではなく）ユーザーをグループに分類するための「ロール」を規定しています（ロールベースアクセス制御）。 したがって、I2RSのロールは、グループに対するアクセス制御を、読み取り、書き込み、または通知として規定します。

SEC-REQ-20:
The rules around what I2RS security role is permitted to access and manipulate what information over a secure transport (which protects the data in transit) SHOULD ensure that data of any level of sensitivity is reasonably protected from being observed by those without permission to view it, so that privacy requirements are met.
SEC-REQ-21:
Role security MUST work when multiple transport connections are being used between the I2RS client and agent as the I2RS architecture [RFC7921] describes.
Sec-REQ-22:
If an I2RS agent or client is tightly correlated with a person, then the I2RS protocol and data models SHOULD provide additional security that protects the person's privacy.
SEC-REQ-20:
どのI2RSセキュリティーロールが、（転送中のデータを保護する）安全なトランスポート上でどの情報にアクセスし操作することを許可されるかに関する規則は、プライバシー要件が満たされるように、あらゆる機密性レベルのデータが、閲覧する許可を持たない者に観察されることから適切に保護されることを保証すべきです（SHOULD）。
SEC-REQ-21:
I2RSアーキテクチャー[RFC7921]が説明しているように、I2RSクライアントとエージェントの間で複数のトランスポート接続が使用されている場合にも、ロールのセキュリティーは機能しなければなりません（MUST）。
Sec-REQ-22:
I2RSエージェントまたはクライアントが個人と密接に関連している場合、I2RSプロトコルとデータモデルは、その個人のプライバシーを保護する追加のセキュリティーを提供すべきです（SHOULD）。

Explanation:

説明:

An I2RS higher-layer protocol uses a management protocol (e.g., NETCONF, RESTCONF) to pass messages in order to enact I2RS transactions. Role security must secure data (sensitive and normal data) in a router even when it is operating over multiple connections at the same time. NETCONF can run over TLS (over TCP or SCTP) or SSH. RESTCONF runs over HTTP over a secure transport (TLS). SCTP [RFC4960] provides security for multiple streams plus end-to-end transport of data. Some I2RS functions may wish to operate over DTLS [RFC6347], which runs over UDP ([RFC768]) and SCTP ([RFC5764]).

I2RS上位層プロトコルは、I2RSトランザクションを実行するためのメッセージを渡すために、管理プロトコル（例: NETCONF、RESTCONF）を使用します。 ロールのセキュリティーは、ルーターが複数の接続上で同時に動作している場合でも、ルーター内のデータ（機密データと通常のデータ）を保護しなければなりません。 NETCONFは、TLS（TCPまたはSCTP上）またはSSH上で動作できます。 RESTCONFは、安全なトランスポート（TLS）上のHTTP上で動作します。 SCTP [RFC4960]は、複数のストリームに対するセキュリティーに加えて、データのエンドツーエンドの転送を提供します。 I2RSの機能の中には、UDP（[RFC768]）およびSCTP（[RFC5764]）上で動作するDTLS [RFC6347]上で動作させたいものもあるかもしれません。

Please note the security of the connection between application and I2RS client is outside of the I2RS protocol or I2RS interface.

アプリケーションとI2RSクライアントの間の接続のセキュリティーは、I2RSプロトコルやI2RSインターフェイスの範囲外であることに注意してください。

While I2RS clients are expected to be related to network devices and not individual people, if an I2RS client ran on a person's phone, then privacy protection to anonymize any data relating to a person's identity or location would be needed.

I2RSクライアントは個々の人ではなくネットワーク機器に関連することが想定されていますが、I2RSクライアントが個人の電話上で動作する場合には、個人のアイデンティティーや位置に関連するあらゆるデータを匿名化するためのプライバシー保護が必要になるでしょう。

A variety of forms of management may set policy on roles: "operator-applied knobs", roles that restrict personal access, data models with specific "privacy roles", and access filters.

さまざまな形態の管理によって、ロールに関するポリシーを設定できます。たとえば、「運用者が適用するノブ」、個人のアクセスを制限するロール、特定の「プライバシーロール」を持つデータモデル、アクセスフィルターなどです。

4.7. Security of the Environment

4.7. 環境のセキュリティー

The security for the implementation of a protocol also considers the protocol environment. Implementers should review the summary of the I2RS security environment in [RFC7921].

プロトコルの実装のセキュリティーでは、プロトコルの環境も考慮します。 実装者は、[RFC7921]にあるI2RSのセキュリティー環境の概要を確認すべきです。
