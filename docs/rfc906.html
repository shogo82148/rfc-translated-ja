RFC 906

Bootstrap Loading using TFTP

RFC 906

TFTPを用いたブートストラップローディング

Status of This Memo

このメモのステータス

It is often convenient to be able to bootstrap a computer system from a communications network. This RFC proposes the use of the IP TFTP protocol for bootstrap loading in this case.

コンピューターシステムを通信ネットワークからブートストラップできると便利なことがよくあります。このRFCは、その場合のブートストラップローディングにIPのTFTPプロトコルを使用することを提案します。

This RFC specifies a proposed protocol for the ARPA Internet community, and requests discussion and suggestions for improvements.

このRFCは、ARPAインターネットコミュニティーのためのプロトコルを提案し、改善のための議論と提案を求めるものです。

Introduction

はじめに

Many computer systems, such as diskless workstations, are bootstrapped by loading one or more code files across a network. Unfortunately, the protocol used to load these initial files has not been standardized - numerous methods have been employed by different computer manufacturers. This can make it difficult, for example, for an installation to support several different kinds of systems on a local-area network. Each different booting mechanism that is used must be supported, for example by implementing a number of servers on one or more host machines. This is in spite of the fact that these heterogeneous systems may be able to communicate freely (all using the same protocol) once they have been booted.

ディスクレスワークステーションなど、多くのコンピューターシステムは、ネットワーク越しに1つ以上のコードファイルをロードすることによってブートストラップされます。残念ながら、これらの最初のファイルをロードするために使われるプロトコルは標準化されておらず、コンピューターメーカーごとにさまざまな方法が採用されてきました。このため、たとえば、ある設置場所でローカルエリアネットワーク上の何種類ものシステムをサポートすることが難しくなる場合があります。使用される起動の仕組みのそれぞれを、たとえば1台以上のホストマシン上に多数のサーバーを実装することによって、サポートしなければなりません。これらの異種のシステムが、いったん起動すれば（すべて同じプロトコルを使って）自由に通信できるかもしれないにもかかわらず、こうなっているのです。

We propose that TFTP (Trivial File Transfer Protocol) [6] be used as a standard protocol for bootstrap loading. This protocol is well-suited for our purpose, being based on the standard Internet Protocol (IP) [4]. It is easily implemented, both in the machines to be booted, and in bootstrap servers elsewhere on the net. (In addition, many popular operating systems already support TFTP servers.) The fact that TFTP is a rather slow protocol is not a serious concern, due to the fact that it need be used only for the primary bootstrap. A secondary bootstrap could use a faster protocol.

私たちは、ブートストラップローディングのための標準プロトコルとして、TFTP（Trivial File Transfer Protocol）[6]を使用することを提案します。このプロトコルは、標準のインターネットプロトコル（IP）[4]に基づいているので、私たちの目的によく適しています。TFTPは、起動されるマシンでも、ネット上のどこか別の場所にあるブートストラップサーバーでも、容易に実装できます。（さらに、多くの普及しているオペレーティングシステムは、すでにTFTPサーバーをサポートしています。）TFTPがかなり遅いプロトコルであることは、深刻な懸念にはなりません。TFTPは一次ブートストラップにだけ使えばよいからです。二次ブートストラップでは、より高速なプロトコルを使用できます。

This RFC describes how system to be booted (called the "booter" below) would use TFTP to load a desired code file. It also describes an existing implementation (in ROM) for Ethernet.

このRFCは、起動されるシステム（以下では「ブーター（booter）」と呼びます）が、TFTPを使って目的のコードファイルをロードする方法を説明します。また、イーサネット向けの既存の（ROMによる）実装についても説明します。

Note that we are specifying only the network protocols that would be used by the booting system. We do not attempt to mandate the method by which a user actually boots a system (such as the format of a command typed at the console). In addition, our proposal does not presuppose the use of any particular data-link level network architecture (although the example that we describe below uses Ethernet).

私たちが規定するのは、起動するシステムが使用するネットワークプロトコルだけであることに注意してください。ユーザーが実際にシステムを起動する方法（コンソールで入力するコマンドの形式など）を義務付けようとはしていません。さらに、私たちの提案は、特定のデータリンクレベルのネットワークアーキテクチャーの使用を前提としていません（ただし、以下で説明する例ではイーサネットを使用しています）。

Network Protocols used by the Booting System

起動するシステムが使用するネットワークプロトコル

To load a file, the booter sends a standard TFTP read request (RRQ) packet, containing the name of the file to be loaded. The file name should not assume any operating system dependent naming conventions (file names containing only alphanumeric characters should suffice). Thereafter, the system receives TFTP DATA packets, and sends TFTP ACK and/or ERROR packets, in accordance with the TFTP specification [6].

ファイルをロードするために、ブーターは、ロードするファイルの名前を含む標準のTFTP読み込み要求（RRQ）パケットを送信します。ファイル名は、オペレーティングシステムに依存する命名規則を前提とすべきではありません（英数字だけを含むファイル名で十分なはずです）。その後、システムは、TFTP仕様[6]に従って、TFTPのDATAパケットを受信し、TFTPのACKパケットやERRORパケットを送信します。

TFTP is implemented using the User Datagram Protocol (UDP) [5], which is in turn implemented using IP. Thus, the booter must be able to receive IP datagrams containing up to 524 octets (excluding the IP header), since TFTP DATA packets can be up to 516 octets long, and UDP headers are 8 octets long. The booting machine is not required to respond to incoming TFTP read or write requests.

TFTPはユーザーデータグラムプロトコル（UDP）[5]を使って実装され、UDPはさらにIPを使って実装されます。したがって、TFTPのDATAパケットは最大516オクテットの長さになり、UDPヘッダーは8オクテットの長さなので、ブーターは（IPヘッダーを除いて）最大524オクテットを含むIPデータグラムを受信できなければなりません。起動するマシンは、受信したTFTPの読み込み要求や書き込み要求に応答する必要はありません。

We allow for the use of two additional protocols. These are ARP (Address Resolution Protocol) [3], and RARP (Reverse Address Resolution Protocol) [1]. The possible use of these protocols is described below. The booter could also use other protocols (such as for name lookup), but they should be IP-based, and an internet standard.

私たちは、さらに2つのプロトコルの使用を認めます。それは、ARP（アドレス解決プロトコル、Address Resolution Protocol）[3]とRARP（逆アドレス解決プロトコル、Reverse Address Resolution Protocol）[1]です。これらのプロトコルの使い方については、以下で説明します。ブーターは（名前の検索などのために）ほかのプロトコルを使用することもできますが、それらはIPベースで、かつインターネット標準であるべきです。

The IP datagram containing the initial TFTP RRQ (and all other IP datagrams sent by the booter) must of course contain both a source internet address and a destination internet address in its IP header. It is frequently the case, however, that the booter does not initially know its own internet address, but only a lower-level (e.g. Ethernet) address. The Reverse Address Resolution Protocol (RARP) [1] may be used by the booter to find its internet address (prior to sending the TFTP RRQ). RARP was motivated by Plummer's Address Resolution Protocol (ARP) [3]. Unlike ARP, which is used to find the 'hardware' address corresponding to a known higher-level protocol (e.g. internet) address, RARP is used to determine a higher-level protocol address, given a known hardware address. RARP uses the same packet format as ARP, and like ARP, can be used for a wide variety of data-link protocols.

最初のTFTP RRQを含むIPデータグラム（およびブーターが送信する他のすべてのIPデータグラム）は、当然、そのIPヘッダーに送信元インターネットアドレスと宛先インターネットアドレスの両方を含んでいなければなりません。しかし、ブーターは最初は自分のインターネットアドレスを知らず、下位レベルの（たとえばイーサネットの）アドレスしか知らないことがよくあります。ブーターは、自分のインターネットアドレスを（TFTP RRQを送信する前に）見つけるために、逆アドレス解決プロトコル（RARP）[1]を使用できます。RARPは、Plummerのアドレス解決プロトコル（ARP）[3]から着想を得たものです。ARPは、既知の上位レベルのプロトコル（たとえばインターネット）のアドレスに対応する「ハードウェア」アドレスを見つけるために使われますが、それとは異なり、RARPは、既知のハードウェアアドレスから上位レベルのプロトコルのアドレスを決定するために使われます。RARPはARPと同じパケット形式を使用し、ARPと同様に、さまざまなデータリンクプロトコルで使用できます。

ARP may also be used. If the destination internet address is known, then an ARP request containing this address may be broadcast, to find a corresponding hardware address to which to send the subsequent TFTP RRQ. It may not matter if this request should fail, because the RRQ can also be broadcast (at the data-link level). However, because such an ARP request packet also contains the sender's (that is, the booter's) internet and hardware addresses, this information is made available to the rest of the local subnet, and could be useful for routing, for instance.

ARPも使用できます。宛先インターネットアドレスがわかっている場合は、そのアドレスを含むARP要求をブロードキャストして、後続のTFTP RRQの送信先となる、対応するハードウェアアドレスを見つけることができます。この要求が失敗しても問題にはならないかもしれません。RRQも（データリンクレベルで）ブロードキャストできるからです。しかし、このようなARP要求パケットには送信者の（つまりブーターの）インターネットアドレスとハードウェアアドレスも含まれているので、この情報がローカルサブネットの他の部分で利用可能になり、たとえばルーティングに役立つ可能性があります。

If a single destination internet address is not known, then a special 'broadcast' internet address could be used as the destination address in the TFTP RRQ, so that it will be received by all 'local' internet hosts. (At this time, however, no standard for internet broadcasting has been officially adopted. [**])

単一の宛先インターネットアドレスがわからない場合は、すべての「ローカル」なインターネットホストが受信できるように、特別な「ブロードキャスト」インターネットアドレスをTFTP RRQの宛先アドレスとして使用できます。（ただし、現時点では、インターネットのブロードキャストに関する標準は正式に採用されていません。[**]）

An Example Implementation

実装例

The author has implemented TFTP booting as specified above. The resulting code resides in ROM. (This implementation is for a Motorola 68000 based workstation, booting over an Ethernet.) A user wishing to boot such a machine types a file name, and (optionally) the internet address of the workstation, and/or the internet address of a server machine from which the file is to be loaded. The bootstrap code proceeds as follows:

著者は、上で規定したTFTPによる起動を実装しました。できあがったコードはROMに格納されています。（この実装は、イーサネット経由で起動するMotorola 68000ベースのワークステーション向けのものです。）このようなマシンを起動したいユーザーは、ファイル名と、（必要に応じて）ワークステーションのインターネットアドレスや、ファイルのロード元となるサーバーマシンのインターネットアドレスを入力します。ブートストラップコードは次のように処理を進めます。

  1. The workstation's Ethernet address is found (by querying the Ethernet interface).
  2. If the internet address of the workstation was not given, then a RARP request is broadcast, in order to find it. If this request fails (that is, times out), then the bootstrap fails.
  3. If the internet address of a server host was given, then broadcast an ARP request to try to find a corresponding Ethernet address. If this fails, or if a server internet address was not given, then the Ethernet broadcast address is used.
  4. If the internet address of a server host was not given, then we use a special internet address that represents a broadcast on the "local subnet", as described in [2]. (This is not an internet standard.)
  5. A TFTP RRQ for the requested file is sent to the Ethernet address found in step (3). The source internet address is that found in step (2), and the destination internet address is that found in step (4).
  1. （イーサネットインターフェイスに問い合わせることによって）ワークステーションのイーサネットアドレスを見つけます。
  2. ワークステーションのインターネットアドレスが与えられていない場合は、それを見つけるためにRARP要求をブロードキャストします。この要求が失敗した（つまり、タイムアウトした）場合は、ブートストラップは失敗します。
  3. サーバーホストのインターネットアドレスが与えられている場合は、ARP要求をブロードキャストして、対応するイーサネットアドレスを見つけようとします。これが失敗した場合や、サーバーのインターネットアドレスが与えられていない場合は、イーサネットのブロードキャストアドレスを使用します。
  4. サーバーホストのインターネットアドレスが与えられていない場合は、[2]で説明されている、「ローカルサブネット」上のブロードキャストを表す特別なインターネットアドレスを使用します。（これはインターネット標準ではありません。）
  5. 要求されたファイルに対するTFTP RRQを、ステップ(3)で見つけたイーサネットアドレスに送信します。送信元インターネットアドレスはステップ(2)で見つけたもので、宛先インターネットアドレスはステップ(4)で見つけたものです。

Note that because several TFTP servers may, in general, reply to the RRQ, we do not abort if a TFTP ERROR packet is received, because this does not preclude the possibility of some other server replying later with the first data packet of the requested file. When the first valid TFTP DATA packet is received in response to the RRQ, the source internet and Ethernet addresses of this packet are used as the destination addresses in subsequent TFTP ACK packets. Should another server later respond with a DATA packet, an ERROR packet is sent back in response.

一般に、複数のTFTPサーバーがRRQに応答する可能性があるので、TFTPのERRORパケットを受信しても中断しないことに注意してください。ERRORパケットを受信しても、別のサーバーが後から要求されたファイルの最初のデータパケットで応答してくる可能性がなくなるわけではないからです。RRQに対する応答として最初の有効なTFTP DATAパケットを受信すると、このパケットの送信元のインターネットアドレスとイーサネットアドレスを、後続のTFTP ACKパケットの宛先アドレスとして使用します。その後に別のサーバーがDATAパケットで応答してきた場合は、その応答としてERRORパケットを送り返します。

An implementation of TFTP booting can take up a lot of space if care is not taken. This can be a significant problem if the code is to fit in a limited amount of ROM. However, the implementation described above consists of less than 4K bytes of code (not counting the Ethernet device driver).

TFTPによる起動の実装は、注意しないと多くの領域を占めてしまうことがあります。コードを限られた量のROMに収めなければならない場合、これは重大な問題になりえます。しかし、上で説明した実装は、（イーサネットのデバイスドライバーを除いて）4Kバイト未満のコードで構成されています。

[**] Editor's Note

[**]編集者注

While there is no standard for an Internet wide broadcast or multicast address, it is strongly recommended that the "all ones" local part of the Internet address be used to indicate a broadcast in a particular network. That is, in class A network 1 the broadcast address would be 1.255.255.255, in class B network 128.1 the broadcast address would be 128.1.255.255, and in class C network 192.1.1 the broadcast address would be 192.1.1.255.

インターネット全体のブロードキャストアドレスやマルチキャストアドレスの標準はありませんが、特定のネットワークにおけるブロードキャストを示すには、インターネットアドレスのローカル部を「すべて1」にしたものを使用することを強く推奨します。つまり、クラスAのネットワーク1ではブロードキャストアドレスは1.255.255.255、クラスBのネットワーク128.1ではブロードキャストアドレスは128.1.255.255、クラスCのネットワーク192.1.1ではブロードキャストアドレスは192.1.1.255となります。
