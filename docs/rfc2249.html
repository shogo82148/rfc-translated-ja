1. Introduction

1. はじめに

This memo defines a portion of the Management Information Base (MIB) for use with network management protocols in the Internet community. Specifically, this memo extends the basic Network Services Monitoring MIB [8] to allow monitoring of Message Transfer Agents (MTAs). It may also be used to monitor MTA components within gateways.

このメモは、インターネットコミュニティーのネットワーク管理プロトコルで使用するための管理情報ベース（Management Information Base: MIB）の一部を定義します。特に、このメモは、メッセージ転送エージェント（Message Transfer Agent: MTA）を監視できるように、基本的なネットワークサービス監視MIB [8]を拡張します。このMIBは、ゲートウェイ内のMTAのコンポーネントを監視するために使用することもできます。

3. The SNMPv2 Network Management Framework

3. SNMPv2ネットワーク管理フレームワーク

The SNMPv2 Network Management Framework consists of seven major components. They are:

SNMPv2ネットワーク管理フレームワークは、7つの主要なコンポーネントで構成されています。それらは次のとおりです。

  • RFC 1902 [1] which defines the SMI, the mechanisms used for describing and naming objects for the purpose of management.
  • RFC 1903 [2] defines textual conventions for SNMPv2.
  • RFC 1904 [3] defines conformance statements for SNMPv2.
  • RFC 1905 [4] defines transport mappings for SNMPv2.
  • RFC 1906 [5] defines the protocol operations used for network access to managed objects.
  • RFC 1907 [6] defines the Management Information Base for SNMPv2.
  • RFC 1908 [7] specifies coexistance between SNMP and SNMPv2.
  • RFC 1902 [1]。SMI、つまり管理の目的でオブジェクトを記述し命名するために使用される仕組みを定義します。
  • RFC 1903 [2]。SNMPv2のテキスト規約を定義します。
  • RFC 1904 [3]。SNMPv2の準拠性ステートメントを定義します。
  • RFC 1905 [4]。SNMPv2のトランスポートマッピングを定義します。
  • RFC 1906 [5]。管理オブジェクトへのネットワークアクセスに使用されるプロトコル操作を定義します。
  • RFC 1907 [6]。SNMPv2の管理情報ベースを定義します。
  • RFC 1908 [7]。SNMPとSNMPv2の共存を規定します。

The Framework permits new objects to be defined for the purpose of experimentation and evaluation.

このフレームワークでは、実験と評価の目的で新しいオブジェクトを定義できます。

3.1. Object Definitions

3.1. オブジェクトの定義

Managed objects are accessed via a virtual information store, termed the Management Information Base or MIB. Objects in the MIB are defined using the subset of Abstract Syntax Notation One (ASN.1) defined in the SMI. In particular, each object type is named by an OBJECT IDENTIFIER, an administratively assigned name. The object type together with an object instance serves to uniquely identify a specific instantiation of the object. For human convenience, we often use a textual string, termed the descriptor, to refer to the object type.

管理オブジェクトには、管理情報ベース（MIB）と呼ばれる仮想的な情報ストアを介してアクセスします。MIBのオブジェクトは、SMIで定義された抽象構文記法1（Abstract Syntax Notation One: ASN.1）のサブセットを使用して定義されます。特に、各オブジェクトタイプは、管理上割り当てられた名前であるOBJECT IDENTIFIERによって命名されます。オブジェクトタイプとオブジェクトインスタンスを合わせることで、オブジェクトの特定のインスタンス化を一意に識別します。人間にとっての便宜のため、オブジェクトタイプを参照する際には、記述子（descriptor）と呼ばれるテキスト文字列をよく使用します。

4. Message Flow Model

4. メッセージフローのモデル

A general model of message flow inside an MTA has to be presented before a MIB can be described. Generally speaking, message flow is modelled as occuring in four steps:

MIBを説明する前に、MTA内部のメッセージフローの一般的なモデルを示す必要があります。一般的に言えば、メッセージフローは次の4つのステップで行われるものとしてモデル化されます。

  1. Messages are received by the MTA from User Agents, Message Stores, other MTAs, and gateways.

  2. The "next hop" for the each message is determined. This is simply the destination the message is to be transmitted to; it may or may not be the final destination of the message.

    Multiple "next hops" may exist for a single message (as a result of either having multiple recipients or distribution list expansion); this may make it necessary to duplicate messages.

  3. If necessary messages are converted into the format that's appropriate for the next hop. Conversion operations may be successful or unsuccessful.
  4. Messages are transmitted to the appropriate destination, which may be a User Agent, Message Store, another MTA, or gateway.
  1. メッセージは、ユーザーエージェント、メッセージストア、他のMTA、およびゲートウェイからMTAによって受信されます。

  2. 各メッセージの「ネクストホップ」が決定されます。これは単に、メッセージが送信される宛先です。それがメッセージの最終的な宛先である場合もあれば、そうでない場合もあります。

    1つのメッセージに対して、（複数の受信者を持つか、配布リストが展開されるかのいずれかの結果として）複数の「ネクストホップ」が存在する場合があります。その場合、メッセージを複製する必要が生じることがあります。

  3. 必要であれば、メッセージはネクストホップに適した形式に変換されます。変換の操作は成功する場合もあれば、失敗する場合もあります。
  4. メッセージは、適切な宛先に送信されます。宛先は、ユーザーエージェント、メッセージストア、別のMTA、またはゲートウェイの場合があります。

Storage of messages in the MTA occurs at some point during this process. However, it is important to note that storage may occur at different and possibly even multiple points during this process. For example, some MTAs expand messages into multiple copies as they are received. In this case (1), (2), and (3) may all occur prior to storage. Other MTAs store messages precisely as they are received and perform all expansions and conversions during retransmission processing. So here only (1) occurs prior to storage. This leads to situations where, in general, a measurement of messages received may not equal a measurement of messages in store, or a measurement of messages stored may not equal a measurement of messages retransmitted, or both.

MTAにおけるメッセージの格納は、この処理の途中のどこかの時点で行われます。しかし、格納は、この処理の途中の異なる時点で、場合によっては複数の時点で行われる可能性があることに注意することが重要です。たとえば、一部のMTAは、メッセージを受信した時点で複数のコピーに展開します。この場合、(1)、(2)、(3)のすべてが格納の前に行われることがあります。他のMTAは、受信したメッセージをそのまま格納し、すべての展開と変換を再送信の処理中に行います。この場合、格納の前に行われるのは(1)だけです。このため、一般に、受信したメッセージの測定値が格納されているメッセージの測定値と等しくならなかったり、格納されたメッセージの測定値が再送信されたメッセージの測定値と等しくならなかったり、その両方が起こったりする状況が生じます。

5. MTA Objects

5. MTAオブジェクト

If there are one or more MTAs on the host, the following MIB may be used to monitor them. Any number of the MTAs on a single host or group of hosts may be monitored. Each MTA is dealt with as a separate network service and has its own applTable entry in the Network Services Monitoring MIB.

ホスト上に1つ以上のMTAがある場合、次のMIBを使用してそれらを監視できます。単一のホストまたはホストのグループ上の任意の数のMTAを監視できます。各MTAは別々のネットワークサービスとして扱われ、ネットワークサービス監視MIBの中に独自のapplTableのエントリーを持ちます。

The MIB described in this document covers only the portion which is specific to the monitoring of MTAs. The network service related part of the MIB is covered in a separate document [8].

この文書で説明するMIBは、MTAの監視に固有の部分のみを対象としています。MIBのうちネットワークサービスに関連する部分は、別の文書[8]で扱われています。

This MIB defines four tables. The first of these contains per-MTA information that isn't specific to any particular part of MTA. The second breaks each MTA down into a collection of separate components called groups. Groups are described in detail in the comments embedded in the MIB below. The third table provides a means of correlating associations tracked by the network services MIB with specific groups within different MTAs. Finally, the fourth table provides a means of tracking any errors encountered during the operation of the MTA. The first two tables must be implemented to conform with this MIB; the last two are optional.

このMIBは4つのテーブルを定義します。1つ目のテーブルには、MTAの特定の部分に固有ではない、MTAごとの情報が含まれます。2つ目のテーブルは、各MTAを、グループと呼ばれる別々のコンポーネントの集まりに分解します。グループについては、以下のMIBに埋め込まれたコメントで詳しく説明しています。3つ目のテーブルは、ネットワークサービスMIBで追跡されるアソシエーションを、さまざまなMTA内の特定のグループと関連付ける手段を提供します。最後に、4つ目のテーブルは、MTAの動作中に発生したエラーを追跡する手段を提供します。このMIBに準拠するには、最初の2つのテーブルを実装する必要があります。最後の2つは省略可能です。

    MAX-ACCESS read-only

    DESCRIPTION
      "A message loop is defined as a situation where the MTA
       decides that a given message will never be delivered to
       one or more recipients and instead will continue to
       loop endlessly through one or more MTAs.  This variable
       counts the number of times the MTA has detected such a
       situation since MTA initialization. Note that the
       mechanism MTAs use to detect loops (e.g. trace field
       counting, count of references to this MTA in a trace
       field, examination of DNS or other directory information,
       etc.), the level at which loops are detected (e.g. per
       message, per recipient, per directory entry, etc.), and

       next and cannot be inferred from this variable."

-- MTAs typically group inbound reception, queue storage, and
-- outbound transmission in some way, rather than accounting for
-- such operations only across the MTA as a whole. In the most
-- extreme case separate information will be maintained for each
-- different entity that receives messages and for each entity
-- the MTA stores messages for and delivers messages to.  Other
-- MTAs may elect to treat all reception equally, all queue
-- storage equally, all deliveries equally, or some combination
-- of this. Overlapped groupings are also possible, where an MTA
-- decomposes its traffic in different ways for different
-- purposes.

-- In any case, a grouping abstraction is an extremely useful for
-- breaking down the activities of an MTA. For purposes of
-- labelling this will be called a "group" in this MIB.

-- Each group contains all the variables needed to monitor all
-- aspects of an MTA's operation.  However, the fact that all
-- groups contain all possible variables does not imply that all
-- groups must use all possible variables. For example, a single
-- group might be used to monitor only one kind of event (inbound
-- processing, outbound processing, or storage). In this sort of
-- configuration all unused counters would be inaccessible; e.g.,
-- returning either a noSuchName error (for an SNMPv1 get), or a
-- noSuchInstance exception (for an SNMPv2 get).

-- Groups can be created at any time after MTA initialization. Once
-- a group is created it should not be deleted or its mtaGroupIndex
-- changed unless the MTA is reinitialized.

-- Groups are not necessarily mutually exclusive. A given event may
-- be recorded by more than one group, a message may be seen as
-- stored by more than one group, and so on.  Groups should be all
-- inclusive, however: if groups are implemented all aspects of an
-- MTA's operation should be registered in at least one group. This
-- freedom lets implementors use different sets of groups to
-- provide differents "views" of an MTA.

-- The possibility of overlap between groups means that summing
-- variables across groups may not produce values equal to those in
-- the mtaTable. mtaTable should always provide accurate information
-- about the MTA as a whole.

-- The term "channel" is often used in MTA implementations; channels
-- are usually, but not always, equivalent to a group. However,
-- this MIB does not use the term "channel" because there is no
-- requirement that an MTA supporting this MIB has to map its
-- "channel" abstraction one-to-one onto the MIB's group abstration.

-- An MTA may create a group or group of groups at any time. Once
-- created, however, an MTA cannot delete an entry for a group from
-- the group table.  Deletation is only allowed when the MTA is
-- reinitialized, and is not required even then.  This restriction
-- is imposed so that monitoring agents can rely on group
-- assignments being consistent across multiple query operations.

-- Groups may be laid out so as to form a hierarchical arrangement,
-- with some groups acting as subgroups for other groups.
-- Alternately, disjoint groups of groups may be used to provide
-- different sorts of "snapshots" of MTA operation.  The
-- mtaGroupHierarchy variable provides an indication of how each
-- group fits into the overall arrangement being used.

-- MTAは通常、受信、キューへの格納、送信といった操作をMTA全体で
-- まとめて集計するのではなく、何らかの方法でグループ化します。
-- 最も極端な場合には、メッセージを受信する個々のエンティティーごと、
-- およびMTAがメッセージを格納して配送する先のエンティティーごとに、
-- 別々の情報が保持されます。その他のMTAは、すべての受信を同等に
-- 扱ったり、すべてのキューへの格納を同等に扱ったり、すべての配送を
-- 同等に扱ったり、それらを組み合わせたりすることを選択できます。
-- 重なり合うグループ化も可能で、その場合MTAは、目的ごとに異なる
-- 方法でトラフィックを分解します。

-- いずれにせよ、グループ化という抽象化は、MTAの活動を分解するのに
-- 非常に役立ちます。名前を付けるため、このMIBではこれを「グループ」
-- と呼びます。

-- 各グループには、MTAの動作のあらゆる側面を監視するために必要な
-- すべての変数が含まれます。しかし、すべてのグループが可能なすべての
-- 変数を含んでいるからといって、すべてのグループが可能なすべての
-- 変数を使用しなければならないわけではありません。たとえば、1つの
-- グループを、1種類のイベント（受信の処理、送信の処理、または格納）
-- だけを監視するために使用することもできます。この種の構成では、
-- 使用されないカウンターはすべてアクセスできなくなります。たとえば、
-- noSuchNameエラー（SNMPv1のgetの場合）またはnoSuchInstance例外
-- （SNMPv2のgetの場合）を返します。

-- グループは、MTAの初期化後いつでも作成できます。いったん作成された
-- グループは、MTAが再初期化されない限り、削除したり、その
-- mtaGroupIndexを変更したりすべきではありません。

-- グループは、必ずしも互いに排他的ではありません。ある1つのイベントが
-- 複数のグループで記録されたり、あるメッセージが複数のグループで
-- 格納されているとみなされたりすることがあります。ただし、グループは
-- すべてを包含すべきです。つまり、グループを実装する場合、MTAの
-- 動作のあらゆる側面が少なくとも1つのグループに記録されるべきです。
-- この自由度により、実装者は異なるグループの集合を使用して、MTAの
-- 異なる「ビュー」を提供できます。

-- グループ間で重なりがありうるため、グループをまたいで変数を合計
-- しても、mtaTableの値と等しくならない場合があります。mtaTableは、
-- 常にMTA全体についての正確な情報を提供すべきです。

-- MTAの実装では「チャネル」という用語がよく使われます。チャネルは
-- 通常はグループと同等ですが、常にそうとは限りません。このMIBを
-- サポートするMTAが、その「チャネル」という抽象化をMIBのグループと
-- いう抽象化に1対1で対応付けなければならないという要件はないため、
-- このMIBでは「チャネル」という用語を使用しません。

-- MTAは、グループやグループのグループをいつでも作成できます。しかし、
-- いったん作成したら、MTAはグループのエントリーをグループテーブル
-- から削除できません。削除はMTAが再初期化されたときにのみ許され、
-- そのときでさえ必須ではありません。この制限は、監視エージェントが、
-- 複数の問い合わせ操作の間でグループの割り当てが一貫していることを
-- 当てにできるようにするために課されています。

-- グループは、一部のグループが他のグループのサブグループとして機能
-- するような、階層的な配置を形成するように配置できます。あるいは、
-- 互いに素なグループのグループを使用して、MTAの動作のさまざまな
-- 種類の「スナップショット」を提供することもできます。
-- mtaGroupHierarchy変数は、使用されている全体の配置の中に各グループ
-- がどのように収まるかを示します。

7. Changes made since RFC 1566

7. RFC 1566からの変更点

The only changes made to this document since it was issued as RFC 1566 [11] are the following:

この文書がRFC 1566 [11]として発行されて以降に加えられた変更は、次のものだけです。

  1. A number of DESCRIPTION fields have been reworded, hopefully making them clearer.
  2. mtaGroupDescription and mtaGroupURL fields have been added. These fields are intended to identify and describe the MTA and the various MTA groups.
  3. The time since the last outbound association attempt is now distinct from the time since the last successfuol outbound association attempt.
  4. Conversion operation counters have been added.
  5. A mechanism to explicitly describe group hierarchies has been added.
  6. A mechanism to count specific sorts of errors has been added.
  7. A field for the ID of the oldest message in a group's queue has been added.
  8. Per-MTA and per-group message loop counters have been added.
  9. A new table has been added to keep track of any errors an MTA encounters.
  1. いくつかのDESCRIPTIONフィールドの表現を見直しました。これにより、より明確になったことを期待しています。
  2. mtaGroupDescriptionフィールドとmtaGroupURLフィールドを追加しました。これらのフィールドは、MTAとさまざまなMTAのグループを識別し説明することを目的としています。
  3. 最後に送信のアソシエーションを試みてからの時間を、最後に送信のアソシエーションの試みが成功してからの時間と区別するようにしました。
  4. 変換操作のカウンターを追加しました。
  5. グループの階層を明示的に記述する仕組みを追加しました。
  6. 特定の種類のエラーを数える仕組みを追加しました。
  7. グループのキュー内で最も古いメッセージのIDのためのフィールドを追加しました。
  8. MTAごとおよびグループごとのメッセージループのカウンターを追加しました。
  9. MTAが遭遇したエラーを追跡するための新しいテーブルを追加しました。

10. Security Considerations

10. セキュリティーに関する考慮事項

This MIB does not offer write access, and as such cannot be used to actively attack a system. However, this MIB does provide passive information about the existance, type, and configuration of applications on a given host that could potentially indicate some sort of vulnerability. Finally, the information MIB provides about network usage could be used to analyze network traffic patterns.

このMIBは書き込みアクセスを提供しないため、システムを能動的に攻撃するために使用することはできません。しかし、このMIBは、特定のホスト上のアプリケーションの存在、種類、構成に関する受動的な情報を提供しており、それが何らかの脆弱性を示す可能性があります。最後に、このMIBが提供するネットワークの使用状況に関する情報は、ネットワークのトラフィックパターンの分析に使用される可能性があります。
