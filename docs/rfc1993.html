RFC 1993

PPP Gandalf FZA Compression Protocol

RFC 1993

PPP Gandalf FZA圧縮プロトコル

Abstract

概要

The Point-to-Point Protocol (PPP) [1] provides a standard method for transporting multi-protocol datagrams over point-to-point links.

ポイントツーポイントプロトコル（PPP：Point-to-Point Protocol）[1]は、ポイントツーポイントリンク上でマルチプロトコルのデータグラムを転送するための標準的な方法を提供します。

The PPP Compression Control Protocol [2] provides a method to negotiate and utilize compression protocols over PPP encapsulated links.

PPP圧縮制御プロトコル（PPP Compression Control Protocol）[2]は、PPPでカプセル化されたリンク上で圧縮プロトコルをネゴシエートして利用するための方法を提供します。

This document describes the use of the Gandalf FZA data compression algorithm [3] for compressing PPP encapsulated packets.

この文書では、PPPでカプセル化されたパケットを圧縮するための、Gandalf FZAデータ圧縮アルゴリズム[3]の使用について説明します。

Status of This Memo

このメモのステータス

This memo provides information for the Internet community. It does not specify an Internet standard. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーに情報を提供するものです。インターネット標準を規定するものではありません。このメモの配布は無制限です。

1. Introduction

1. はじめに

FZA is a high performance LZ [4] derivative that maximizes compression at the expense of memory and CPU. Compression performance can be adjusted based on CPU and memory available.

FZAは、メモリーとCPUを犠牲にして圧縮率を最大化する、LZ [4]から派生した高性能なアルゴリズムです。圧縮性能は、利用可能なCPUとメモリーに基づいて調整できます。

Multiple PPP packets can be combined in a single compressed frame, or a single PPP packet can be spread across multiple frames.

複数のPPPパケットを1つの圧縮フレームにまとめることも、1つのPPPパケットを複数のフレームに分散させることもできます。

2. FZA Packets

2. FZAパケット

Before any FZA packets may be communicated, PPP must reach the Network-Layer Protocol phase.

FZAパケットをやり取りする前に、PPPはネットワーク層プロトコル（Network-Layer Protocol）フェーズに到達していなければなりません。

When the Compression Control Protocol (CCP) has reached the Opened state, and FZA is negotiated as the primary compression algorithm, the PPP Protocol field indicates type hex 00FB (link compressed datagram), or type hex 00FD (compressed datagram).

圧縮制御プロトコル（CCP：Compression Control Protocol）がOpened状態に達し、FZAが主たる圧縮アルゴリズムとしてネゴシエートされると、PPPのProtocolフィールドは16進数の00FB（リンク圧縮データグラム）または16進数の00FD（圧縮データグラム）のタイプを示します。

The maximum length of the FZA datagram transmitted over a PPP link is the same as the maximum length of the Information field of a PPP encapsulated packet.

PPPリンク上で送信されるFZAデータグラムの最大長は、PPPでカプセル化されたパケットのInformationフィールドの最大長と同じです。

Padding
The FZA packets require the negotiation of the Self-Describing-Padding Configuration Option [5] at LCP Link Establishment.
Reliability and Sequencing

The FZA algorithm expects a reliable link, as described in "PPP Reliable Transmission" [6].

FZA expects the packets to be delivered in sequence.

Data Expansion

The maximum expansion of Gandalf FZA is 2:1. However, typical expansion on pre-compressed data is 1.01:1. Expanded data is sent to maintain the integrity of the compression history.

When the expansion exceeds the size of the peer's Maximum Receive Unit for the link, the expanded packet is sent in multiple PPP frames. The compressed data contains an indication of the end of the original packet.

パディング（Padding）
FZAパケットでは、LCPのリンク確立（Link Establishment）時に、自己記述パディング（Self-Describing-Padding）構成オプション[5]のネゴシエーションが必要です。
信頼性と順序（Reliability and Sequencing）

FZAアルゴリズムは、「PPP Reliable Transmission」[6]で説明されているような、信頼性のあるリンクを想定しています。

FZAは、パケットが順序どおりに配送されることを想定しています。

データの膨張（Data Expansion）

Gandalf FZAの最大の膨張率は2:1です。ただし、圧縮済みのデータでの典型的な膨張率は1.01:1です。膨張したデータは、圧縮履歴の完全性を保つために送信されます。

膨張がリンクにおけるピアの最大受信単位（Maximum Receive Unit）の大きさを超える場合、膨張したパケットは複数のPPPフレームで送信されます。圧縮データには、元のパケットの終わりを示す情報が含まれています。

2.1. Packet Format

2.1. パケット形式

A summary of the Gandalf FZA packet format is shown below. The fields are transmitted from left to right.

Gandalf FZAのパケット形式の概要を以下に示します。フィールドは左から右へ送信されます。

+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|         PPP Protocol          |     Compressed Data ...
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|         PPP Protocol          |     Compressed Data ...
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
PPP Protocol

One or two octets. The PPP Protocol field is described in the Point-to-Point Protocol Encapsulation [1].

Type 00FD is used when the PPP multilink protocol is not used, and/or "inside" a multilink bundle. Type 00FB is used "outside" multilink, to compress independently on individual links of a multilink bundle. This value MAY be compressed when LCP Protocol-Field-Compression is negotiated.

Compressed Data

One or more octets. The compressed PPP encapsulated packet(s).

Prior to compression, the uncompressed data begins with the original PPP Protocol number. This value MAY be compressed when LCP Protocol-Field-Compression is negotiated.

The original Protocol number is followed by the original Information field. The length of the original Information field before compression MUST NOT exceed the link Maximum Receive Unit (MRU).

PPP Link Control Protocol packets MUST NOT be sent within compressed data.

PPPプロトコル（PPP Protocol）

1オクテットまたは2オクテットです。PPPのProtocolフィールドについては、ポイントツーポイントプロトコルのカプセル化[1]で説明されています。

タイプ00FDは、PPPマルチリンクプロトコルを使用しない場合や、マルチリンクバンドルの「内側」で使用します。タイプ00FBは、マルチリンクの「外側」で、マルチリンクバンドルの個々のリンクで独立して圧縮するために使用します。LCPのProtocol-Field-Compressionがネゴシエートされている場合、この値を圧縮してもよいです（MAY）。

圧縮データ（Compressed Data）

1オクテット以上です。圧縮された、PPPでカプセル化されたパケットです。

圧縮前の非圧縮データは、元のPPPのProtocol番号で始まります。LCPのProtocol-Field-Compressionがネゴシエートされている場合、この値を圧縮してもよいです（MAY）。

元のProtocol番号の後には、元のInformationフィールドが続きます。圧縮前の元のInformationフィールドの長さは、リンクの最大受信単位（MRU：Maximum Receive Unit）を超えてはなりません（MUST NOT）。

PPPリンク制御プロトコル（Link Control Protocol）のパケットを圧縮データ内で送信してはなりません（MUST NOT）。

3. Configuration Option Format

3. 構成オプションの形式

Description
The CCP Gandalf-FZA Configuration Option negotiates the use of Gandalf FZA on the link. By default or ultimate disagreement, no compression is used.
説明
CCPのGandalf-FZA構成オプションは、リンク上でのGandalf FZAの使用をネゴシエートします。デフォルトでは、または最終的に合意に至らなかった場合は、圧縮は使用されません。

A summary of the Gandalf-FZA Configuration Option format is shown below. The fields are transmitted from left to right.

Gandalf-FZA構成オプションの形式の概要を以下に示します。フィールドは左から右へ送信されます。

+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|     Type      |    Length     |   History   |    Version ...
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|     Type      |    Length     |   History   |    Version ...
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
Type
19
Length
>= 3
History

One octet. The History field specifies the maximum size of the compression history in powers of 2. Valid values range from 12 to 15.

The peer is not required to send as many histories as the implementation indicates that it can accept.

Version

Zero or more octets of additional configuration information. Any implementation that does not implement this information MUST send a Configure-Nak without this field.

The Version field is not present for FZA.

The Version field is a single octet containing the value 1 for FZA+.

タイプ（Type）
19
長さ（Length）
>= 3
履歴（History）

1オクテットです。Historyフィールドは、圧縮履歴の最大サイズを2のべき乗で指定します。有効な値の範囲は12～15です。

ピアは、受け入れ可能であると実装が示した数だけ履歴を送信する必要はありません。

バージョン（Version）

追加の構成情報を表す0オクテット以上のデータです。この情報を実装していない実装は、このフィールドを含まないConfigure-Nakを送信しなければなりません（MUST）。

FZAでは、Versionフィールドは存在しません。

FZA+では、Versionフィールドは値1を含む1オクテットです。
