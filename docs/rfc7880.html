Seamless Bidirectional Forwarding Detection (S-BFD)

RFC 7880

Abstract

This document defines Seamless Bidirectional Forwarding Detection (S-BFD), a simplified mechanism for using BFD with a large proportion of negotiation aspects eliminated, thus providing benefits such as quick provisioning, as well as improved control and flexibility for network nodes initiating path monitoring.

1. Introduction

1. はじめに

Bidirectional Forwarding Detection (BFD), as described in [RFC5880] and related documents, has efficiently generalized the failure detection mechanism for multiple protocols and applications. There are some improvements that can be made to better fit existing technologies. There is a possibility of evolving BFD to better fit new technologies. This document focuses on several aspects of BFD in order to further improve efficiency, expand failure detection coverage, and allow BFD usage for wider scenarios. Additional use cases are listed in [RFC7882].

[RFC5880]および関連文書で説明されている双方向フォワーディング検出（Bidirectional Forwarding Detection、BFD）は、複数のプロトコルやアプリケーションのための障害検出メカニズムを効率的に汎用化しました。既存の技術によりよく適合させるために、いくつかの改善の余地があります。また、新しい技術によりよく適合するようBFDを発展させられる可能性があります。この文書では、効率をさらに改善し、障害検出の対象範囲を広げ、より広いシナリオでBFDを使えるようにするために、BFDのいくつかの側面に焦点を当てます。その他のユースケースは[RFC7882]に挙げられています。

Specifically, this document defines Seamless Bidirectional Forwarding Detection (S-BFD), a simplified mechanism for using BFD with a large proportion of negotiation aspects eliminated, thus providing benefits such as quick provisioning, as well as improved control and flexibility for network nodes initiating path monitoring. S-BFD enables cases benefiting from the use of core BFD technologies in a fashion that leverages existing implementations and protocol machinery while providing a rather simplified and largely stateless infrastructure for continuity testing.

具体的には、この文書はシームレス双方向フォワーディング検出（Seamless Bidirectional Forwarding Detection、S-BFD）を定義します。S-BFDは、ネゴシエーションの側面の大部分を取り除いてBFDを使うための簡素化されたメカニズムであり、迅速なプロビジョニングや、パス監視を開始するネットワークノードにとっての制御性と柔軟性の向上といった利点をもたらします。S-BFDは、導通テストのためのかなり簡素化された、ほぼステートレスな基盤を提供しつつ、既存の実装とプロトコルの仕組みを活用する形で、BFDの中核技術を使うことで利益を得られるケースを可能にします。

One key aspect of the mechanism described in this document eliminates the time between a network node wanting to perform a continuity test and completing the continuity test. In traditional BFD terms, the initial state changes from DOWN to UP are virtually nonexistent. Removal of this "seam" (i.e., time delay) in BFD provides a smooth and continuous operational experience for applications. Therefore, "Seamless BFD" (S-BFD) has been chosen as the name for this mechanism.

この文書で説明するメカニズムの重要な側面の1つは、ネットワークノードが導通テストを実施しようとしてから導通テストを完了するまでの時間をなくすことです。従来のBFDの用語でいえば、DOWNからUPへの初期の状態遷移が事実上存在しません。BFDにおけるこの「継ぎ目（seam）」（すなわち時間遅延）を取り除くことで、アプリケーションに円滑で連続した運用体験を提供します。そのため、このメカニズムの名前として「シームレスBFD（Seamless BFD）」（S-BFD）が選ばれました。

この文書におけるキーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、「要求されています（REQUIRED）」、「することになります（SHALL）」、「することはありません（SHALL NOT）」、「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、「推奨されます（RECOMMENDED）」、「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、RFC 2119 [RFC2119]で説明されているとおりに解釈されるものとします。

The reader is expected to be familiar with the BFD [RFC5880], IP [RFC791] [RFC2460], and MPLS [RFC3031] terms and protocol constructs. The remainder of this section describes several new terms introduced by S-BFD.

読者は、BFD [RFC5880]、IP [RFC791] [RFC2460]、MPLS [RFC3031]の用語とプロトコルの構成要素に精通していることを想定しています。このセクションの残りの部分では、S-BFDで導入されるいくつかの新しい用語を説明します。

  • S-BFD Discriminator - a BFD Discriminator allocated for a local entity. An SBFDReflector listens for S-BFD Discriminators.
  • BFD Discriminator - a BFD Discriminator allocated for an SBFDInitiator.
  • Initiator - a network node hosting an SBFDInitiator.
  • Responder - a network node hosting an SBFDReflector.
  • 従来型BFD（Classical BFD） - [RFC5880]に基づくBFDセッションの種類。

  • S-BFDパケット（S-BFD packet） - BFD制御パケットまたはBFDエコーパケット。

3. Seamless BFD Overview

3. シームレスBFDの概要

An S-BFD module on each network node allocates one or more S-BFD Discriminators for local entities and creates a Reflector BFD session. Allocated S-BFD Discriminators may be advertised by applications (e.g., OSPF/IS-IS). The required result is that applications on other network nodes will know about the S-BFD Discriminators allocated by a remote node to remote entities. The Reflector BFD session, upon receiving an S-BFD Control packet targeted to one of the local S-BFD Discriminator values, is to transmit a response S-BFD Control packet back to the initiator.

各ネットワークノード上のS-BFDモジュールは、ローカルのエンティティーに1つ以上のS-BFDディスクリミネーターを割り当て、リフレクターBFDセッションを作成します。割り当てられたS-BFDディスクリミネーターは、アプリケーション（例：OSPF/IS-IS）によって広告されることがあります。求められる結果は、他のネットワークノード上のアプリケーションが、リモートノードによってリモートのエンティティーに割り当てられたS-BFDディスクリミネーターを知ることです。リフレクターBFDセッションは、ローカルのS-BFDディスクリミネーターの値のいずれかを対象とするS-BFD制御パケットを受信すると、応答のS-BFD制御パケットをイニシエーターに送り返すことになっています。

Once the above setup is complete, any network node that knows about the S-BFD Discriminator allocated by a remote node to a remote entity or entities can quickly perform a continuity test to the remote entity by simply sending S-BFD Control packets with a corresponding S-BFD Discriminator value in the Your Discriminator field.

上記の準備が完了すると、リモートノードによって1つまたは複数のリモートのエンティティーに割り当てられたS-BFDディスクリミネーターを知っているネットワークノードはどれでも、対応するS-BFDディスクリミネーターの値をYour Discriminatorフィールドに入れたS-BFD制御パケットを送信するだけで、リモートのエンティティーに対する導通テストを迅速に実施できます。

This is exemplified in Figure 2.

この例を図2に示します。

An S-BFD module in a system with IS-IS System-ID xxx (Node A) allocates an S-BFD Discriminator 123, and IS-IS advertises the S-BFD Discriminator 123 in an IS-IS TLV. An S-BFD module in a system with IS-IS System-ID yyy (Node D) allocates an S-BFD Discriminator 456, and IS-IS advertises the S-BFD Discriminator 456 in an IS-IS TLV. A Reflector BFD session is created on both network nodes (Node A and Node D). When Node A wants to check the reachability of Node D, Node A can send an S-BFD Control packet destined to Node D with the Your Discriminator field set to 456. When the Reflector BFD session on Node D receives this S-BFD Control packet, then a response S-BFD Control packet is sent back to Node A, which allows Node A to complete the continuity test.

IS-ISのシステムIDがxxxであるシステム（ノードA）のS-BFDモジュールは、S-BFDディスクリミネーター123を割り当て、IS-ISはS-BFDディスクリミネーター123をIS-IS TLVで広告します。IS-ISのシステムIDがyyyであるシステム（ノードD）のS-BFDモジュールは、S-BFDディスクリミネーター456を割り当て、IS-ISはS-BFDディスクリミネーター456をIS-IS TLVで広告します。両方のネットワークノード（ノードAとノードD）にリフレクターBFDセッションが作成されます。ノードAがノードDの到達可能性を確認したいときは、Your Discriminatorフィールドを456に設定した、ノードD宛てのS-BFD制御パケットを送信できます。ノードD上のリフレクターBFDセッションがこのS-BFD制御パケットを受信すると、応答のS-BFD制御パケットがノードAに送り返され、それによってノードAは導通テストを完了できます。

When a node allocates multiple S-BFD Discriminators, how remote nodes determine which of the discriminators is associated with a specific entity is currently unspecified. The use of multiple S-BFD Discriminators by a single network node is therefore discouraged until a means of learning the mapping is defined.

ノードが複数のS-BFDディスクリミネーターを割り当てた場合に、リモートノードがどのディスクリミネーターが特定のエンティティーに関連付けられているかをどのように判断するかは、現時点では規定されていません。そのため、対応関係を知る手段が定義されるまでは、単一のネットワークノードが複数のS-BFDディスクリミネーターを使うことは推奨されません。

4. S-BFD Discriminators

4. S-BFDディスクリミネーター

4.1. S-BFD Discriminator Uniqueness

4.1. S-BFDディスクリミネーターの一意性

One important characteristic of an S-BFD Discriminator is that it MUST be unique within an administrative domain. If multiple network nodes allocate the same S-BFD Discriminator value, then S-BFD Control packets falsely terminating on a wrong network node can result in a Reflector BFD session generating a response back because of a matching Your Discriminator value. This is clearly not desirable.

S-BFDディスクリミネーターの重要な特性の1つとして、S-BFDディスクリミネーターは管理ドメイン内で一意でなければなりません（MUST）。複数のネットワークノードが同じS-BFDディスクリミネーターの値を割り当てると、誤ったネットワークノードに誤って到達したS-BFD制御パケットに対して、Your Discriminatorの値が一致するためにリフレクターBFDセッションが応答を生成して返してしまう可能性があります。これは明らかに望ましくありません。

4.2. Discriminator Pools

4.2. ディスクリミネータープール

This subsection describes a discriminator pool implementation technique to minimize S-BFD Discriminator collisions. This technique will allow an implementation to better satisfy the S-BFD Discriminator uniqueness requirement defined in Section 4.1.

このサブセクションでは、S-BFDディスクリミネーターの衝突を最小限に抑えるための、ディスクリミネータープールによる実装手法を説明します。この手法により、実装はセクション4.1で定義したS-BFDディスクリミネーターの一意性の要件をよりよく満たせるようになります。

  • An SBFDInitiator is to allocate a discriminator from the BFD Discriminator pool. If the system also supports classical BFD (i.e., implements [RFC5880]), then the BFD Discriminator pool SHOULD be shared by SBFDInitiator sessions and classical BFD sessions.
  • An SBFDReflector is to allocate a discriminator from the S-BFD Discriminator pool. The S-BFD Discriminator pool SHOULD be a separate pool from the BFD Discriminator pool.
  • SBFDInitiatorは、BFDディスクリミネータープールからディスクリミネーターを割り当てることになっています。システムが従来型BFDもサポートしている（すなわち[RFC5880]を実装している）場合、BFDディスクリミネータープールはSBFDInitiatorセッションと従来型BFDセッションで共有されるべきです（SHOULD）。
  • SBFDReflectorは、S-BFDディスクリミネータープールからディスクリミネーターを割り当てることになっています。S-BFDディスクリミネータープールは、BFDディスクリミネータープールとは別のプールであるべきです（SHOULD）。

The remainder of this subsection describes the reasons for the suggestions above.

このサブセクションの残りの部分では、上記の提案の理由を説明します。

Locally allocated S-BFD Discriminator values for entities that SBFDReflector sessions are listening for may be arbitrarily allocated or derived from values provided by applications. These values may be protocol IDs (e.g., System-ID, Router-ID) or network targets (e.g., IP address). To avoid derived S-BFD Discriminator values already being assigned to other BFD sessions (i.e., SBFDInitiator sessions and classical BFD sessions), it is RECOMMENDED that the discriminator pool for SBFDReflector sessions be separate from other BFD sessions.

SBFDReflectorセッションが待ち受けるエンティティーに対してローカルで割り当てられるS-BFDディスクリミネーターの値は、任意に割り当てられることも、アプリケーションが提供する値から導出されることもあります。これらの値は、プロトコルのID（例：システムID、ルーターID）であることも、ネットワーク上のターゲット（例：IPアドレス）であることもあります。導出したS-BFDディスクリミネーターの値が他のBFDセッション（すなわちSBFDInitiatorセッションと従来型BFDセッション）にすでに割り当てられている事態を避けるため、SBFDReflectorセッションのためのディスクリミネータープールは他のBFDセッションのものとは別にすることが推奨されます（RECOMMENDED）。

Even when following the "separate discriminator pool" approach, a collision is still possible between different S-BFD applications that may be using different values and algorithms to derive S-BFD Discriminator values. If two applications are using S-BFD for the same purpose (e.g., network reachability), then the colliding S-BFD Discriminator value can be shared. If the two applications are using S-BFD for a different purpose, then the collision must be addressed. The use of multiple S-BFD Discriminators by a single network node, however, is discouraged (see Section 3).

「ディスクリミネータープールを分ける」アプローチに従った場合でも、S-BFDディスクリミネーターの値を導出するのに異なる値やアルゴリズムを使う、異なるS-BFDアプリケーションの間では、依然として衝突が起こりえます。2つのアプリケーションが同じ目的（例：ネットワークの到達可能性）でS-BFDを使っている場合は、衝突したS-BFDディスクリミネーターの値を共有できます。2つのアプリケーションが異なる目的でS-BFDを使っている場合は、衝突に対処する必要があります。ただし、単一のネットワークノードが複数のS-BFDディスクリミネーターを使うことは推奨されません（セクション3を参照）。

5. Reflector BFD Session

5. リフレクターBFDセッション

Each network node creates one or more Reflector BFD sessions. This Reflector BFD session is a session that transmits S-BFD Control packets in response to received S-BFD Control packets with the Your Discriminator field having S-BFD Discriminators allocated for local entities. Specifically, this Reflector BFD session has the following characteristics:

各ネットワークノードは、1つ以上のリフレクターBFDセッションを作成します。このリフレクターBFDセッションは、ローカルのエンティティーに割り当てられたS-BFDディスクリミネーターをYour Discriminatorフィールドに持つS-BFD制御パケットを受信すると、それに応答してS-BFD制御パケットを送信するセッションです。具体的には、このリフレクターBFDセッションは次の特性を持ちます。

  • MUST NOT transmit any S-BFD packets based on local timer expiry.
  • MUST transmit an S-BFD Control packet in response to a received S-BFD Control packet having a valid S-BFD Discriminator in the Your Discriminator field, unless prohibited by local policies (e.g., administrative, security, rate-limiter).
  • MUST be capable of sending only two states: UP and AdminDown.
  • ローカルのタイマーの満了に基づいてS-BFDパケットを送信してはなりません（MUST NOT）。
  • Your Discriminatorフィールドに有効なS-BFDディスクリミネーターを持つS-BFD制御パケットを受信した場合は、ローカルポリシー（例：管理上のもの、セキュリティー、レートリミッター）によって禁止されていない限り、それに応答してS-BFD制御パケットを送信しなければなりません（MUST）。
  • UPとAdminDownの2つの状態だけを送信できるものでなければなりません（MUST）。

One Reflector BFD session may be responsible for handling received S-BFD Control packets targeted to all locally allocated S-BFD Discriminators, or a few Reflector BFD sessions may each be responsible for a subset of locally allocated S-BFD Discriminators. This policy is a local matter and is outside the scope of this document.

1つのリフレクターBFDセッションが、ローカルで割り当てられたすべてのS-BFDディスクリミネーターを対象として受信したS-BFD制御パケットの処理を受け持つこともあれば、いくつかのリフレクターBFDセッションがそれぞれ、ローカルで割り当てられたS-BFDディスクリミネーターの一部を受け持つこともあります。このポリシーはローカルな事項であり、この文書の範囲外です。

Note that incoming S-BFD Control packets may be based on IPv4, IPv6, or MPLS [RFC7881]. Note also that other options are possible and may be defined in future documents. How such S-BFD Control packets reach an appropriate Reflector BFD session is also a local matter and is outside the scope of this document.

届くS-BFD制御パケットは、IPv4、IPv6、MPLS [RFC7881]に基づくことがある点に注意してください。また、他の選択肢も可能であり、将来の文書で定義されることがある点にも注意してください。そのようなS-BFD制御パケットが適切なリフレクターBFDセッションにどのように到達するかも、ローカルな事項であり、この文書の範囲外です。

6. State Variables

6. 状態変数

S-BFD introduces new state variables and modifies the usage of existing ones.

S-BFDは、新しい状態変数を導入し、既存の状態変数の使い方を変更します。

6.1. New State Variables

6.1. 新しい状態変数

A new state variable is added to the base specification in support of S-BFD.

S-BFDをサポートするために、基本仕様に新しい状態変数を1つ追加します。

  • bfd.SessionType: This is a new state variable that describes the type of a particular session. Allowable values for S-BFD sessions are:

    • SBFDInitiator - an S-BFD session on a network node that performs a continuity test to a target entity by sending S-BFD packets.
    • SBFDReflector - an S-BFD session on a network node that listens for incoming S-BFD Control packets to local entities and generates response S-BFD Control packets.

  • bfd.SessionType：これは、個々のセッションの種類を表す新しい状態変数です。S-BFDセッションで許される値は次のとおりです。

    • SBFDInitiator - S-BFDパケットを送信することで、ターゲットのエンティティーに対する導通テストを実施する、ネットワークノード上のS-BFDセッション。
    • SBFDReflector - ローカルのエンティティー宛てに届くS-BFD制御パケットを待ち受け、応答のS-BFD制御パケットを生成する、ネットワークノード上のS-BFDセッション。

The bfd.SessionType variable MUST be initialized to the appropriate type when an S-BFD session is created.

bfd.SessionType変数は、S-BFDセッションの作成時に適切な種類に初期化しなければなりません（MUST）。

6.2. State Variable Initialization and Maintenance

6.2. 状態変数の初期化と維持

State variables (defined in Section 6.8.1 of [RFC5880]) need to be initialized or manipulated differently, depending on the session type.

状態変数（[RFC5880]のセクション6.8.1で定義）は、セッションの種類に応じて異なる方法で初期化または操作する必要があります。

  • bfd.DemandMode: This variable MUST be initialized to 1 for session type SBFDInitiator and MUST be initialized to 0 for session type SBFDReflector. This is done to prevent loops (see Appendix A).
  • bfd.DemandMode：この変数は、セッションの種類がSBFDInitiatorの場合は1に初期化しなければなりません（MUST）。セッションの種類がSBFDReflectorの場合は0に初期化しなければなりません（MUST）。これはループを防ぐためです（付録Aを参照）。

7. S-BFD Procedures

7. S-BFDの手順

7.1. Demultiplexing of S-BFD Control Packet

7.1. S-BFD制御パケットの多重分離

An S-BFD packet MUST be demultiplexed with lower-layer information (e.g., dedicated destination UDP port [RFC7881], associated Channel Type [RFC7885]). The following procedure SHOULD be executed on both initiator and reflector:

S-BFDパケットは、下位層の情報（例：専用の宛先UDPポート[RFC7881]、関連するチャネルタイプ（Channel Type）[RFC7885]）を使って多重分離しなければなりません（MUST）。イニシエーターとリフレクターの両方で、次の手順を実行すべきです（SHOULD）。

  • If the packet is an S-BFD packet

    • If the S-BFD packet is for an SBFDReflector

      • The packet MUST be looked up to locate a corresponding SBFDReflector session based on the value from the Your Discriminator field in the table describing S-BFD Discriminators.

      Else

      • The packet MUST be looked up to locate a corresponding SBFDInitiator session or classical BFD session based on the value from the Your Discriminator field in the table describing BFD Discriminators. If no match, then the received packet MUST be discarded.

        If the session is an SBFDInitiator session

        • The destination of the packet (i.e., the destination IP address) SHOULD be verified as being for itself.

        Else

        • The packet MUST be discarded.

    Else

    • The procedure described in Section 6.8.6 of [RFC5880] MUST be applied.

  • パケットがS-BFDパケットである場合

    • S-BFDパケットがSBFDReflector宛てである場合

      • パケットのYour Discriminatorフィールドの値に基づいてS-BFDディスクリミネーターを記述したテーブルを検索し、対応するSBFDReflectorセッションを特定しなければなりません（MUST）。

      それ以外の場合

      • パケットのYour Discriminatorフィールドの値に基づいてBFDディスクリミネーターを記述したテーブルを検索し、対応するSBFDInitiatorセッションまたは従来型BFDセッションを特定しなければなりません（MUST）。一致するものがない場合、受信したパケットは破棄しなければなりません（MUST）。

        セッションがSBFDInitiatorセッションである場合

        • パケットの宛先（すなわち宛先IPアドレス）が自分自身宛てであることを検証すべきです（SHOULD）。

        それ以外の場合

        • パケットは破棄しなければなりません（MUST）。

    それ以外の場合

    • [RFC5880]のセクション6.8.6で説明されている手順を適用しなければなりません（MUST）。

More details on S-BFD Control packet demultiplexing are provided in relevant S-BFD data-plane documents.

S-BFD制御パケットの多重分離に関する詳細は、関連するS-BFDのデータプレーンの文書で説明されています。

7.2. Responder Procedures

7.2. レスポンダーの手順

A network node that receives S-BFD Control packets transmitted by an initiator is referred to as the responder. The responder, upon reception of S-BFD Control packets, is to verify the validity of the packets, as described in [RFC5880].

イニシエーターが送信したS-BFD制御パケットを受信するネットワークノードを、レスポンダーと呼びます。レスポンダーは、S-BFD制御パケットを受信すると、[RFC5880]で説明されているとおりにパケットの妥当性を検証することになっています。

7.2.1. Responder Demultiplexing

7.2.1. レスポンダーにおける多重分離

An S-BFD packet MUST be demultiplexed with lower-layer information. The following procedure SHOULD be executed by the responder:

S-BFDパケットは、下位層の情報を使って多重分離しなければなりません（MUST）。レスポンダーは次の手順を実行すべきです（SHOULD）。

  • If the Your Discriminator field is not one of the entries allocated for local entities

    • The packet MUST be discarded.

    Else

    • The packet is determined to be handled by a Reflector BFD session responsible for that S-BFD Discriminator.

      If allowable per local policy (e.g., administrative, security, rate-limiter)

      • The chosen Reflector BFD session SHOULD transmit a response BFD Control packet using the procedures described in Section 7.2.2.

  • Your Discriminatorフィールドが、ローカルのエンティティーに割り当てられたエントリーのいずれでもない場合

    • パケットは破棄しなければなりません（MUST）。

    それ以外の場合

    • パケットは、そのS-BFDディスクリミネーターを受け持つリフレクターBFDセッションが処理するものと判断されます。

      ローカルポリシー（例：管理上のもの、セキュリティー、レートリミッター）によって許可される場合

      • 選ばれたリフレクターBFDセッションは、セクション7.2.2で説明する手順を使って、応答のBFD制御パケットを送信すべきです（SHOULD）。

7.2.3. Additional SBFDReflector Behaviors

7.2.3. SBFDReflectorの追加の振る舞い

  • S-BFD Control packets transmitted by the SBFDReflector MUST have Required Min RX Interval set to a value that expresses, in microseconds, the minimum interval between incoming S-BFD Control packets that this SBFDReflector can handle. The SBFDReflector can control how fast SBFDInitiators will be sending S-BFD Control packets to themselves by ensuring that Required Min RX Interval indicates a value based on the current load.
  • When the SBFDReflector receives an S-BFD Control packet from an SBFDInitiator, then the SBFDReflector needs to determine what "state" to send in the response S-BFD Control packet. If the monitored local entity is in service, then the state MUST be set to UP. If the monitored local entity is "temporarily out of service", then the state SHOULD be set to AdminDown.
  • If an SBFDReflector receives an S-BFD Control packet with the Demand (D) bit cleared, the packet MUST be discarded (see Appendix A).
  • SBFDReflectorが送信するS-BFD制御パケットでは、Required Min RX Intervalに、このSBFDReflectorが処理できる、届くS-BFD制御パケットの最小間隔をマイクロ秒単位で表す値を設定しなければなりません（MUST）。SBFDReflectorは、Required Min RX Intervalが現在の負荷に基づく値を示すようにすることで、SBFDInitiatorが自分にS-BFD制御パケットを送信する速さを制御できます。
  • SBFDReflectorがSBFDInitiatorからS-BFD制御パケットを受信したとき、SBFDReflectorは応答のS-BFD制御パケットでどの「状態」を送信するかを決める必要があります。監視対象のローカルのエンティティーが稼働中であれば、状態はUPに設定しなければなりません（MUST）。監視対象のローカルのエンティティーが「一時的に停止中」であれば、状態はAdminDownに設定すべきです（SHOULD）。
  • SBFDReflectorがDemand（D）ビットがクリアされたS-BFD制御パケットを受信した場合、そのパケットは破棄しなければなりません（MUST）（付録Aを参照）。

7.3.3. Additional SBFDInitiator Behaviors

7.3.3. SBFDInitiatorの追加の振る舞い

  • If the SBFDInitiator receives a valid S-BFD Control packet in response to a transmitted S-BFD Control packet to a remote entity, then the SBFDInitiator SHOULD conclude that the S-BFD Control packet reached the intended remote entity.
  • When an SBFDInitiator receives a response S-BFD Control packet, if the state specified is AdminDown, the SBFDInitiator MUST NOT conclude that the reachability of the corresponding remote entity is lost and MUST back off the packet transmission interval for the remote entity to an interval no faster than 1 second.
  • When a sufficient number of S-BFD packets have not arrived as they should, the SBFDInitiator SHOULD declare loss of reachability to the remote entity. The criteria for declaring loss of reachability and the action that would be triggered as a result are outside the scope of this document; the action MAY include logging an error.
  • Regarding the third bullet item, it is critical for an implementation to understand the latency to/from the Reflector BFD session on the responder. In other words, for the very first S-BFD packet transmitted by the SBFDInitiator, an implementation MUST NOT expect a response S-BFD packet to be received for a time equivalent to the sum of the latencies: initiator to responder and responder back to initiator.
  • If the SBFDInitiator receives an S-BFD Control packet with the Demand (D) bit set, the packet MUST be discarded (see Appendix A).
  • SBFDInitiatorが、リモートのエンティティーに送信したS-BFD制御パケットへの応答として有効なS-BFD制御パケットを受信した場合、SBFDInitiatorは、そのS-BFD制御パケットが意図したリモートのエンティティーに到達したと結論づけるべきです（SHOULD）。
  • SBFDInitiatorが応答のS-BFD制御パケットを受信したとき、指定された状態がAdminDownであれば、SBFDInitiatorは、対応するリモートのエンティティーへの到達可能性が失われたと結論づけてはなりません（MUST NOT）。また、そのリモートのエンティティーに対するパケットの送信間隔を、1秒より短くない間隔にまで延ばさなければなりません（MUST）。
  • 届くはずのS-BFDパケットが十分な数だけ届かなかった場合、SBFDInitiatorはリモートのエンティティーへの到達可能性が失われたと宣言すべきです（SHOULD）。到達可能性が失われたと宣言する基準と、その結果として引き起こされる動作は、この文書の範囲外です。その動作にはエラーのログ記録を含めてもよいです（MAY）。
  • 3つ目の項目に関して、実装がレスポンダー上のリフレクターBFDセッションとの間の遅延を把握することは非常に重要です。言い換えれば、SBFDInitiatorが送信するまさに最初のS-BFDパケットについて、実装は、イニシエーターからレスポンダーまでと、レスポンダーからイニシエーターに戻るまでの遅延の合計に相当する時間が経つより前に、応答のS-BFDパケットを受信することを期待してはなりません（MUST NOT）。
  • SBFDInitiatorがDemand（D）ビットがセットされたS-BFD制御パケットを受信した場合、そのパケットは破棄しなければなりません（MUST）（付録Aを参照）。

7.4. Diagnostic Values

7.4. 診断値

The diagnostic value in both directions MAY be set to a certain value, to attempt to communicate further information to both ends. Implementations MAY use the already-existing diagnostic values defined in Section 4.1 of [RFC5880]. However, details regarding this topic are outside the scope of this specification.

両端にさらに情報を伝えようとするために、両方向の診断値を特定の値に設定してもよいです（MAY）。実装は、[RFC5880]のセクション4.1で定義されている既存の診断値を使ってもよいです（MAY）。ただし、この話題に関する詳細はこの仕様の範囲外です。

7.5. The Poll Sequence

7.5. ポーリングシーケンス（Poll Sequence）

The Poll Sequence MAY be used in both directions. The Poll Sequence MUST operate in accordance with [RFC5880]. An SBFDReflector MAY use the Poll Sequence to slow down the rate at which S-BFD Control packets are generated from an SBFDInitiator. This is done by the SBFDReflector, using the procedures described in Section 7.2.3 and setting the Poll (P) bit in the reflected S-BFD Control packet. The SBFDInitiator is to then send the next S-BFD Control packet with the Final (F) bit set. If an SBFDReflector receives an S-BFD Control packet with the P bit set, then the SBFDReflector MUST respond with an S-BFD Control packet with the P bit cleared and the F bit set.

ポーリングシーケンスは両方向で使ってもよいです（MAY）。ポーリングシーケンスは[RFC5880]に従って動作しなければなりません（MUST）。SBFDReflectorは、SBFDInitiatorからS-BFD制御パケットが生成される速度を下げるために、ポーリングシーケンスを使ってもよいです（MAY）。これは、SBFDReflectorがセクション7.2.3で説明した手順を使い、折り返すS-BFD制御パケットのPoll（P）ビットをセットすることで行います。そうすると、SBFDInitiatorは次のS-BFD制御パケットをFinal（F）ビットをセットして送信することになっています。SBFDReflectorがPビットがセットされたS-BFD制御パケットを受信した場合、SBFDReflectorは、Pビットをクリアし、FビットをセットしたS-BFD制御パケットで応答しなければなりません（MUST）。

8. Operational Considerations

8. 運用上の考慮事項

S-BFD provides a smooth and continuous (i.e., seamless) operational experience as an Operations, Administration, and Maintenance (OAM) mechanism for connectivity checking and connection verification. This is achieved by providing a simplified mechanism with a large proportion of negotiation aspects eliminated, resulting in faster and simpler provisioning.

S-BFDは、導通確認と接続検証のための運用・管理・保守（Operations, Administration, and Maintenance、OAM）メカニズムとして、円滑で連続した（すなわちシームレスな）運用体験を提供します。これは、ネゴシエーションの側面の大部分を取り除いた簡素化されたメカニズムを提供することで実現され、その結果、プロビジョニングがより速く簡単になります。

Because of this simplified mechanism, due to a misconfiguration an SBFDInitiator could send S-BFD Control packets to a target that does not exist or that is outside the S-BFD administrative domain. As explained in Section 7.3.1, an SBFDInitiator can be a persistent initiator or a "when needed" one. When an S-BFD persistent SBFDInitiator is used, a deployment SHOULD ensure that S-BFD Control packets do not propagate for an extended period of time outside of the administrative domain that uses it. Further, operational measures SHOULD be taken to determine if responses to S-BFD packets are not sent for an extended period of time and then remediate the situation. These potential concerns are largely mitigated by dynamic advertisement mechanisms for S-BFD and with automation checks before applying configurations.

この簡素化されたメカニズムのため、設定の誤りによって、SBFDInitiatorが存在しないターゲットやS-BFDの管理ドメインの外にあるターゲットにS-BFD制御パケットを送信してしまうことがありえます。セクション7.3.1で説明したように、SBFDInitiatorは永続的なイニシエーターであることも、「必要なときに」動くイニシエーターであることもあります。S-BFDの永続的なSBFDInitiatorを使う場合、デプロイメントでは、S-BFD制御パケットがそれを使う管理ドメインの外に長時間伝播しないことを保証すべきです（SHOULD）。さらに、S-BFDパケットへの応答が長時間送られていないかどうかを判断し、その状況を是正するための運用上の措置を講じるべきです（SHOULD）。これらの潜在的な懸念は、S-BFDのための動的な広告メカニズムや、設定を適用する前の自動化されたチェックによって、大部分が緩和されます。

8.1. Scaling Aspect

8.1. スケーリングの側面

This mechanism brings forth one noticeable difference in terms of the scaling aspect: the number of SBFDReflectors. This specification eliminates the need for egress nodes to have fully active BFD sessions when only one side desires to perform continuity tests. With the introduction of the Reflector BFD concept, egress is no longer required to create any active BFD sessions on a per-path/LSP/function basis. Because of this, the total number of BFD sessions in a network is reduced.

このメカニズムは、スケーリングの側面において、SBFDReflectorの数という1つの顕著な違いをもたらします。この仕様により、一方の側だけが導通テストの実施を望む場合に、出口ノードが完全にアクティブなBFDセッションを持つ必要がなくなります。リフレクターBFDの概念の導入によって、出口はもはやパス／LSP／機能ごとにアクティブなBFDセッションを作成する必要がありません。そのため、ネットワーク内のBFDセッションの総数が減ります。

8.2. Congestion Considerations

8.2. 輻輳に関する考慮事項

When S-BFD performs failure detection, it consumes resources, including bandwidth and CPU processing. To avoid congestion, it is therefore imperative that operators correctly provision the rates at which S-BFD packets are transmitted. When BFD is used across multiple hops, a congestion control mechanism MUST be implemented, and when congestion is detected, the BFD implementation MUST reduce the amount of traffic it generates. The exact mechanism used to detect congestion is outside the scope of this specification but may include the detection of lost BFD Control packets or other means. The SBFDReflector can limit the rate at which SBFDInitiators will be sending S-BFD Control packets by utilizing Required Min RX Interval, but at the expense of detection time (i.e., detection time will increase).

S-BFDは、障害検出を行う際に、帯域幅やCPU処理を含むリソースを消費します。したがって、輻輳を避けるために、運用者がS-BFDパケットを送信するレートを正しくプロビジョニングすることが不可欠です。BFDを複数のホップにわたって使う場合、輻輳制御メカニズムを実装しなければなりません（MUST）。また、輻輳を検出した場合、BFDの実装は生成するトラフィックの量を減らさなければなりません（MUST）。輻輳の検出に使う正確なメカニズムはこの仕様の範囲外ですが、失われたBFD制御パケットの検出やその他の手段が含まれることがあります。SBFDReflectorは、Required Min RX Intervalを利用することで、SBFDInitiatorがS-BFD制御パケットを送信するレートを制限できますが、その代償として検出時間が犠牲になります（すなわち、検出時間が長くなります）。

9. Co-existence with Classical BFD Sessions

9. 従来型BFDセッションとの共存

Demultiplexing requirements for the initial packet are described in Section 7.1. Because of this, the S-BFD mechanism can co-exist with classical BFD sessions.

最初のパケットに対する多重分離の要件は、セクション7.1で説明しています。このため、S-BFDメカニズムは従来型BFDセッションと共存できます。

10. S-BFD Echo Function

10. S-BFDエコー機能

The concept of the S-BFD Echo function is similar to the BFD Echo function described in [RFC5880]. S-BFD Echo packets have the destination of "self"; thus, S-BFD Echo packets are self-generated and self-terminated after traversing a link/path. S-BFD Echo packets are expected to U-turn on the target node in the data plane and MUST NOT be processed by any Reflector BFD sessions on the target node.

S-BFDエコー機能の概念は、[RFC5880]で説明されているBFDエコー機能に似ています。S-BFDエコーパケットの宛先は「自分自身」です。したがって、S-BFDエコーパケットは自分で生成し、リンク／パスを通過した後に自分で終端します。S-BFDエコーパケットは、ターゲットノードのデータプレーンでUターンすることが期待されており、ターゲットノード上のどのリフレクターBFDセッションでも処理されてはなりません（MUST NOT）。

When using the S-BFD Echo function, it is RECOMMENDED that:

S-BFDエコー機能を使う場合、次のようにすることが推奨されます（RECOMMENDED）。

  • Both S-BFD Control packets and S-BFD Echo packets be sent.
  • Both S-BFD Control packets and S-BFD Echo packets have the same semantics in the forward direction to reach the target node.
  • S-BFD制御パケットとS-BFDエコーパケットの両方を送信する。
  • S-BFD制御パケットとS-BFDエコーパケットの両方が、ターゲットノードに到達する順方向で同じセマンティクスを持つ。

In other words, it is not preferable to send just S-BFD Echo packets without also sending S-BFD Control packets. There are two reasons behind this suggestion:

言い換えれば、S-BFD制御パケットを送信せずにS-BFDエコーパケットだけを送信することは好ましくありません。この提案の背景には2つの理由があります。

  • S-BFD Control packets can verify the reachability of the intended target node; this allows one to have confidence that S-BFD Echo packets are U-turning on the expected target node.
  • S-BFD Control packets can detect when the target node is going out of service (i.e., by receiving AdminDown state).
  • S-BFD制御パケットは、意図したターゲットノードへの到達可能性を検証できます。これにより、S-BFDエコーパケットが期待したターゲットノードでUターンしていると確信できます。
  • S-BFD制御パケットは、ターゲットノードが停止しようとしていることを（すなわちAdminDown状態を受信することで）検出できます。

S-BFD Echo packets can be spoofed and can U-turn in a transit node before reaching the expected target node. When the S-BFD Echo function is used, it is RECOMMENDED in this specification that both S-BFD Control packets and S-BFD Echo packets be sent. While the additional use of S-BFD Control packets alleviates these two concerns, some form of authentication MAY still be included.

S-BFDエコーパケットは偽装されることがあり、期待したターゲットノードに到達する前に中継ノードでUターンすることがあります。この仕様では、S-BFDエコー機能を使う場合、S-BFD制御パケットとS-BFDエコーパケットの両方を送信することが推奨されます（RECOMMENDED）。S-BFD制御パケットを追加で使うことでこれら2つの懸念は緩和されますが、それでもなお何らかの形の認証を含めてもよいです（MAY）。

The usage of the Required Min Echo RX Interval field is described in Sections 7.2.2 and 7.3.2. Because of the stateless nature of SBFDReflector sessions, a value specified in the Required Min Echo RX Interval field is not very meaningful to the SBFDReflector. Thus, it is RECOMMENDED that the Required Min Echo RX Interval field simply be set to zero by the SBFDInitiator. The SBFDReflector MAY set the Required Min Echo RX Interval field to an appropriate value to control the rate at which it wants to receive S-BFD Echo packets.

Required Min Echo RX Intervalフィールドの使い方は、セクション7.2.2と7.3.2で説明しています。SBFDReflectorセッションはステートレスという性質を持つため、Required Min Echo RX Intervalフィールドに指定された値は、SBFDReflectorにとってあまり意味がありません。そのため、SBFDInitiatorはRequired Min Echo RX Intervalフィールドを単に0に設定することが推奨されます（RECOMMENDED）。SBFDReflectorは、S-BFDエコーパケットを受信したいレートを制御するために、Required Min Echo RX Intervalフィールドを適切な値に設定してもよいです（MAY）。

The following aspects of S-BFD Echo functions are left as implementation details and are outside the scope of this document:

S-BFDエコー機能に関する次の側面は、実装の詳細として残されており、この文書の範囲外です。

  • Format of the S-BFD Echo packet (e.g., data beyond UDP header).
  • Procedures on when and how to use the S-BFD Echo function.
  • S-BFDエコーパケットのフォーマット（例：UDPヘッダーより後のデータ）。
  • S-BFDエコー機能をいつ、どのように使うかに関する手順。

11. Security Considerations

11. セキュリティーに関する考慮事項

The same security considerations as those described in [RFC5880] apply to this document. Additionally, implementing the following measures will strengthen security aspects of the mechanism described by this document:

[RFC5880]で説明されているものと同じセキュリティーに関する考慮事項が、この文書にも当てはまります。加えて、次の対策を実装することで、この文書で説明するメカニズムのセキュリティー面が強化されます。

  • The SBFDInitiator MAY pick a sequence number to be set in "sequence number" in the Authentication Section, based on the configured authentication mode.
  • The SBFDReflector MUST NOT use the crypto sequence number to make a decision about accepting the packet. This is because the SBFDReflector does not maintain S-BFD peer state and because the SBFDReflector can receive S-BFD packets from multiple SBFDInitiators. Consequently, BFD authentication can be used, but not the sequence number.
  • The SBFDReflector MAY use the Auth Key ID in the incoming packet to verify the Authentication Data.
  • The SBFDReflector MUST accept the packet if authentication is successful.
  • The SBFDReflector MUST compute the Authentication Data and MUST use the same sequence number that it received in the S-BFD Control packet to which it is responding.
  • The SBFDInitiator SHOULD accept an S-BFD Control packet with a sequence number within the permissible range. One potential approach is the procedure explained in [BFD-GEN-AUTH].
  • SBFDInitiatorは、設定された認証モードに基づいて、認証セクション（Authentication Section）の「sequence number」に設定するシーケンス番号を選んでもよいです（MAY）。
  • SBFDReflectorは、パケットを受け入れるかどうかの判断に暗号シーケンス番号を使ってはなりません（MUST NOT）。これは、SBFDReflectorがS-BFDのピアの状態を保持せず、また、SBFDReflectorが複数のSBFDInitiatorからS-BFDパケットを受信しうるためです。したがって、BFD認証は使えますが、シーケンス番号は使えません。
  • SBFDReflectorは、届いたパケットのAuth Key IDを使って、Authentication Dataを検証してもよいです（MAY）。
  • SBFDReflectorは、認証が成功した場合、そのパケットを受け入れなければなりません（MUST）。
  • SBFDReflectorはAuthentication Dataを計算しなければなりません（MUST）。その際、応答する対象のS-BFD制御パケットで受信したのと同じシーケンス番号を使わなければなりません（MUST）。
  • SBFDInitiatorは、許容範囲内のシーケンス番号を持つS-BFD制御パケットを受け入れるべきです（SHOULD）。考えられるアプローチの1つは、[BFD-GEN-AUTH]で説明されている手順です。

Using the above method,

上記の方法を使うと、次のようになります。

  • SBFDReflectors continue to remain stateless, despite using security.
  • SBFDReflectors are not susceptible to replay attacks, as they always respond to S-BFD Control packets irrespective of the sequence number carried.
  • An attacker cannot impersonate the responder, since the SBFDInitiator will only accept S-BFD Control packets that come with the sequence number that it had originally used when sending the S-BFD Control packet.
  • SBFDReflectorは、セキュリティーを使っていても、引き続きステートレスなままです。
  • SBFDReflectorは、運ばれるシーケンス番号にかかわらず常にS-BFD制御パケットに応答するため、リプレイ攻撃の影響を受けません。
  • SBFDInitiatorは、自分がもともとS-BFD制御パケットを送信する際に使ったシーケンス番号を伴うS-BFD制御パケットだけを受け入れるため、攻撃者はレスポンダーになりすますことができません。

Additionally, the use of strong forms of authentication is strongly encouraged for S-BFD. The use of Simple Password authentication [RFC5880] potentially puts other services at risk if S-BFD packets can be intercepted and those password values are reused for other services.

加えて、S-BFDには強力な形式の認証を使うことが強く推奨されます。S-BFDパケットが傍受される可能性があり、かつそのパスワードの値が他のサービスで再利用されている場合、シンプルパスワード認証（Simple Password authentication）[RFC5880]を使うと、他のサービスが危険にさらされる可能性があります。

Considerations related to loop problems are covered in Appendix A.

ループ問題に関する考慮事項は付録Aで扱います。

Appendix A. Loop Problem and Solution

付録A. ループ問題とその解決策

Consider a scenario where we have two nodes and both are S-BFD capable.

2つのノードがあり、どちらもS-BFDに対応しているシナリオを考えます。

 Node A (IP 2001:db8::1) ----------------- Node B (IP 2001:db8::2)
                                 |
                                 |
                      Man in the Middle (MITM)

 Node A (IP 2001:db8::1) ----------------- Node B (IP 2001:db8::2)
                                 |
                                 |
                      Man in the Middle (MITM)

Assume that Node A reserved a discriminator 0x01010101 for target identifier 2001:db8::1 and has a reflector session in listening mode. Similarly, Node B reserved a discriminator 0x02020202 for its target identifier 2001:db8::2 and also has a reflector session in listening mode.

ノードAが、ターゲット識別子2001:db8::1に対してディスクリミネーター0x01010101を予約しており、待ち受けモードのリフレクターセッションを持っているとします。同様に、ノードBが、自身のターゲット識別子2001:db8::2に対してディスクリミネーター0x02020202を予約しており、やはり待ち受けモードのリフレクターセッションを持っているとします。

Suppose that a MITM sends a spoofed packet with My Discriminator = 0x01010101, Your Discriminator = 0x02020202, source IP as 2001:db8::1, and destination IP as 2001:db8::2. When this packet reaches Node B, the reflector session on Node B will swap the discriminators and IP addresses of the received packet and reflect it back, since the Your Discriminator value of the received packet matches the reserved discriminator of Node B. The reflected packet that reached Node A will have My Discriminator = 0x02020202 and Your Discriminator = 0x01010101. Since the Your Discriminator value of the received packet matches the reserved discriminator of Node A, Node A will swap the discriminators and reflect the packet back to Node B. Since the reflectors must set the TTL of the reflected packets to 255, the above scenario will result in an infinite loop because of just one malicious packet injected from the MITM.

中間者（MITM）が、My Discriminator = 0x01010101、Your Discriminator = 0x02020202、送信元IPが2001:db8::1、宛先IPが2001:db8::2である偽装パケットを送信したとします。このパケットがノードBに到達すると、受信したパケットのYour Discriminatorの値がノードBの予約済みディスクリミネーターと一致するため、ノードB上のリフレクターセッションは、受信したパケットのディスクリミネーターとIPアドレスを入れ替えて、パケットを折り返します。ノードAに到達した折り返しパケットは、My Discriminator = 0x02020202、Your Discriminator = 0x01010101となります。受信したパケットのYour Discriminatorの値がノードAの予約済みディスクリミネーターと一致するため、ノードAはディスクリミネーターを入れ替えて、パケットをノードBに折り返します。リフレクターは折り返すパケットのTTLを255に設定しなければならないため、上記のシナリオでは、MITMから注入されたたった1つの悪意あるパケットによって無限ループが発生します。

The solution is to avoid the loop problem by using the D bit (Demand mode bit). The initiator always sets the D bit, and the reflector always clears it. This way, we can determine if a received packet was a reflected packet and avoid reflecting it back.

解決策は、Dビット（デマンドモードビット）を使ってループ問題を回避することです。イニシエーターは常にDビットをセットし、リフレクターは常にDビットをクリアします。こうすることで、受信したパケットが折り返されたパケットであったかどうかを判断でき、それを折り返すことを避けられます。
