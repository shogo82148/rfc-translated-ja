Distributed Node Consensus Protocol

RFC 7787

分散ノードコンセンサスプロトコル

Abstract

概要

This document describes the Distributed Node Consensus Protocol (DNCP), a generic state synchronization protocol that uses the Trickle algorithm and hash trees. DNCP is an abstract protocol and must be combined with a specific profile to make a complete implementable protocol.

この文書は、分散ノードコンセンサスプロトコル（Distributed Node Consensus Protocol: DNCP）について説明します。DNCPは、Trickleアルゴリズムとハッシュツリーを使用する汎用の状態同期プロトコルです。DNCPは抽象的なプロトコルであり、実装可能な完全なプロトコルにするには、特定のプロファイルと組み合わせる必要があります。

1. Introduction

1. はじめに

DNCP is designed to provide a way for each participating node to publish a small set of TLV (Type-Length-Value) tuples (at most 64 KB) and to provide a shared and common view about the data published by every currently bidirectionally reachable DNCP node in a network.

DNCPは、参加している各ノードが小さなTLV（Type-Length-Value）タプルの集合（最大64KB）を公開する方法を提供し、ネットワーク内の現在双方向に到達可能なすべてのDNCPノードが公開したデータについて、共有された共通のビューを提供するように設計されています。

For state synchronization, a hash tree is used. It is formed by first calculating a hash for the data set published by each node, called node data, and then calculating another hash over those node data hashes. The single resulting hash, called network state hash, is transmitted using the Trickle algorithm [RFC6206] to ensure that all nodes share the same view of the current state of the published data within the network. The use of Trickle with only short network state hashes sent infrequently (in steady state, once the maximum Trickle interval per link or unicast connection has been reached) makes DNCP very thrifty when updates happen rarely.

状態の同期には、ハッシュツリーを使用します。ハッシュツリーは、まず各ノードが公開したデータセット（ノードデータと呼びます）のハッシュを計算し、次にそれらのノードデータハッシュに対して別のハッシュを計算することで形成されます。その結果得られる単一のハッシュはネットワーク状態ハッシュと呼ばれ、ネットワーク内で公開されたデータの現在の状態について、すべてのノードが同じビューを共有することを保証するために、Trickleアルゴリズム[RFC6206]を使用して送信されます。短いネットワーク状態ハッシュだけを低頻度で（定常状態では、リンクごとまたはユニキャストコネクションごとのTrickle間隔が最大に達した後に）送信するTrickleを使用することで、更新がまれにしか発生しない場合にDNCPは非常に倹約的になります。

For maintaining liveliness of the topology and the data within it, a combination of Trickled network state, keep-alives, and "other" means of ensuring reachability are used. The core idea is that if every node ensures its peers are present, transitively, the whole network state also stays up to date.

トポロジーとその中のデータの生存性を維持するために、Trickleで送信されるネットワーク状態、キープアライブ、および到達可能性を確保する「その他の」手段を組み合わせて使用します。中心となる考え方は、すべてのノードが自身のピアの存在を確認すれば、推移的に、ネットワーク全体の状態も最新に保たれるというものです。

1.1. Applicability

1.1. 適用範囲

DNCP is useful for cases like autonomous bootstrapping, discovery, and negotiation of embedded network devices like routers. Furthermore, it can be used as a basis to run distributed algorithms like [RFC7596] or use cases as described in Appendix C. DNCP is abstract, which allows it to be tuned to a variety of applications by defining profiles. These profiles include choices of:

DNCPは、ルーターのような組み込みネットワーク機器の自律的なブートストラップ、発見、ネゴシエーションといったケースに役立ちます。さらに、[RFC7596]のような分散アルゴリズムや、付録Cで説明するようなユースケースを実行するための基盤として使用できます。DNCPは抽象的であり、プロファイルを定義することで、さまざまなアプリケーションに合わせて調整できます。プロファイルには、次の選択が含まれます。

unicast transport:
a datagram or stream-oriented protocol (e.g., TCP, UDP, or the Stream Control Transmission Protocol (SCTP)) for generic protocol operation.
optional transport security:
whether and when to use security based on Transport Layer Security (TLS) or Datagram Transport Layer Security (DTLS), if supported over the chosen transport.
optional multicast transport:
a multicast-capable protocol like UDP allowing autonomous peer discovery or more efficient use of multiple access links.
communication scopes:
using either hop by hop only relying on link-local addressing (e.g., for LANs), addresses with broader scopes (e.g., over WANs or the Internet) relying on an existing routing infrastructure, or a combination of both (e.g., to exchange state between multiple LANs over a WAN or the Internet).
payloads:
additional specific payloads (e.g., IANA standardized, enterprise-specific, or private use).
extensions:
possible protocol extensions, either as predefined in this document or specific for a particular use case.
ユニキャストトランスポート：
汎用的なプロトコル操作のための、データグラム指向またはストリーム指向のプロトコル（たとえば、TCP、UDP、またはStream Control Transmission Protocol（SCTP））。
任意のトランスポートセキュリティー：
選択したトランスポート上でサポートされている場合に、Transport Layer Security（TLS）またはDatagram Transport Layer Security（DTLS）に基づくセキュリティーを使用するかどうか、およびいつ使用するか。
任意のマルチキャストトランスポート：
自律的なピア発見や、マルチアクセスリンクのより効率的な使用を可能にする、UDPのようなマルチキャスト対応プロトコル。
通信スコープ：
リンクローカルアドレッシングのみに依存するホップバイホップ（たとえば、LANの場合）、既存のルーティング基盤に依存するより広いスコープのアドレス（たとえば、WANやインターネット経由の場合）、またはその両方の組み合わせ（たとえば、WANやインターネットを介して複数のLAN間で状態を交換する場合）のいずれかを使用します。
ペイロード：
追加の特定のペイロード（たとえば、IANAで標準化されたもの、企業固有のもの、またはプライベート使用のもの）。
拡張：
この文書であらかじめ定義されたもの、または特定のユースケースに固有のもののいずれかの、可能なプロトコル拡張。

However, there are certain cases where the protocol as defined in this document is a less suitable choice. This list provides an overview while the following paragraphs provide more detailed guidance on the individual matters.

ただし、この文書で定義するプロトコルがあまり適さない選択肢となる特定のケースがあります。次の一覧は概要を示すもので、個々の事項についてのより詳細なガイダンスは、その後の段落で示します。

large amounts of data:
nodes are limited to 64 KB of published data.
very dense unicast-only networks:
nodes include information about all immediate neighbors as part of their published data.
predominantly minimal data changes:
node data is always transported as is, leading to a relatively large transmission overhead for changes affecting only a small part of it.
frequently changing data:
DNCP with its use of Trickle is optimized for the steady state and less efficient otherwise.
large amounts of very constrained nodes:
DNCP requires each node to store the entirety of the data published by all nodes.
大量のデータ：
ノードが公開するデータは64KBに制限されます。
非常に密なユニキャストのみのネットワーク：
ノードは、公開するデータの一部として、直接隣接するすべての近隣に関する情報を含めます。
大半が最小限のデータ変更：
ノードデータは常にそのまま転送されるため、ノードデータのごく一部にしか影響しない変更では、送信のオーバーヘッドが比較的大きくなります。
頻繁に変更されるデータ：
Trickleを使用するDNCPは定常状態向けに最適化されており、それ以外の場合は効率が下がります。
非常に制約の厳しい大量のノード：
DNCPでは、各ノードがすべてのノードによって公開されたデータの全体を保存する必要があります。

The topology of the devices is not limited and automatically discovered. When relying on link-local communication exclusively, all links having DNCP nodes need to be at least transitively connected by routers running the protocol on multiple endpoints in order to form a connected network. However, there is no requirement for every device in a physical network to run the protocol. Especially if globally scoped addresses are used, DNCP peers do not need to be on the same or even neighboring physical links. Autonomous discovery features are usually used in local network scenarios; however, with security enabled, DNCP can also be used over unsecured public networks. Network size is restricted merely by the capabilities of the devices, i.e., each DNCP node needs to be able to store the entirety of the data published by all nodes. The data associated with each individual node identifier is limited to about 64 KB in this document; however, protocol extensions could be defined to mitigate this or other protocol limitations if the need arises.

機器のトポロジーは制限されず、自動的に発見されます。リンクローカル通信のみに依存する場合、接続されたネットワークを形成するには、DNCPノードを持つすべてのリンクが、複数のエンドポイントでプロトコルを実行しているルーターによって、少なくとも推移的に接続されている必要があります。ただし、物理ネットワーク内のすべての機器がプロトコルを実行する必要はありません。特にグローバルスコープのアドレスを使用する場合、DNCPピアは同じ物理リンク上にある必要はなく、隣接する物理リンク上にある必要さえありません。自律的な発見機能は通常ローカルネットワークのシナリオで使用されますが、セキュリティーを有効にすれば、DNCPを保護されていない公衆ネットワーク上で使用することもできます。ネットワークの規模は機器の能力によってのみ制限されます。つまり、各DNCPノードは、すべてのノードによって公開されたデータの全体を保存できる必要があります。この文書では、個々のノード識別子に関連付けられたデータは約64KBに制限されていますが、必要が生じた場合には、この制限やその他のプロトコルの制限を緩和するプロトコル拡張を定義できます。

DNCP is most suitable for data that changes only infrequently to gain the maximum benefit from using Trickle. As the network of nodes grows, or the frequency of data changes per node increases, Trickle is eventually used less and less, and the benefit of using DNCP diminishes. In these cases, Trickle just provides extra complexity within the specification and little added value.

Trickleの使用による利点を最大限に得るために、DNCPはまれにしか変更されないデータに最も適しています。ノードのネットワークが大きくなったり、ノードごとのデータ変更の頻度が増えたりするにつれて、Trickleが使用される機会は次第に少なくなり、DNCPを使用する利点は小さくなります。このような場合、Trickleは仕様内に余分な複雑さをもたらすだけで、付加価値はほとんどありません。

The suitability of DNCP for a particular application can be roughly evaluated by considering the expected average network-wide state change interval A_NC_I; it is computed by dividing the mean interval at which a node originates a new TLV set by the number of participating nodes. If keep-alives are used, A_NC_I is the minimum of the computed A_NC_I and the keep-alive interval. If A_NC_I is less than the (application-specific) Trickle minimum interval, DNCP is most likely unsuitable for the application as Trickle will not be utilized most of the time.

特定のアプリケーションに対するDNCPの適合性は、予想されるネットワーク全体の平均状態変更間隔A_NC_Iを考慮することで、大まかに評価できます。A_NC_Iは、ノードが新しいTLVセットを発信する平均間隔を、参加ノードの数で割ることで計算されます。キープアライブを使用する場合、A_NC_Iは、計算したA_NC_Iとキープアライブ間隔の最小値です。A_NC_Iが（アプリケーション固有の）Trickleの最小間隔より小さい場合、ほとんどの時間でTrickleが活用されないため、DNCPはそのアプリケーションには適さない可能性が高いです。

If constant rapid state changes are needed, the preferable choice is to use an additional point-to-point channel whose address or locator is published using DNCP. Nevertheless, if doing so does not raise A_NC_I above the (sensibly chosen) Trickle interval parameters for a particular application, using DNCP is probably not suitable for the application.

常に急速な状態変更が必要な場合は、アドレスやロケーターをDNCPを使用して公開する、追加のポイントツーポイントチャネルを使用するのが望ましい選択です。それでも、そうすることで特定のアプリケーションについてA_NC_Iが（適切に選択された）Trickle間隔パラメーターを上回らない場合、DNCPの使用はおそらくそのアプリケーションには適していません。

Another consideration is the size of the published TLV set by a node compared to the size of deltas in the TLV set. If the TLV set published by a node is very large, and has frequent small changes, DNCP as currently specified in this specification may be unsuitable as it lacks a delta synchronization scheme to keep implementation simple.

もう1つの考慮事項は、ノードが公開するTLVセットのサイズと、TLVセットの差分のサイズの比較です。ノードが公開するTLVセットが非常に大きく、小さな変更が頻繁にある場合、この仕様で現在規定されているDNCPは、実装を単純に保つために差分同期の方式を持たないため、適さない可能性があります。

DNCP can be used in networks where only unicast transport is available. While DNCP uses the least amount of bandwidth when multicast is utilized, even in pure unicast mode, the use of Trickle (ideally with k < 2) results in a protocol with an exponential backoff timer and fewer transmissions than a simpler protocol not using Trickle.

DNCPは、ユニキャストトランスポートしか利用できないネットワークでも使用できます。DNCPはマルチキャストを利用する場合に帯域幅の使用量が最も少なくなりますが、純粋なユニキャストモードでも、Trickleを（理想的にはk < 2で）使用することで、指数バックオフタイマーを持ち、Trickleを使用しない単純なプロトコルよりも送信回数の少ないプロトコルになります。

2. Terminology

2. 用語

DNCP profile
the values for the set of parameters given in Section 9. They are prefixed with DNCP_ in this document. The profile also specifies the set of optional DNCP extensions to be used. For a simple example DNCP profile, see Appendix C.
DNCP-based protocol
a protocol that provides a DNCP profile, according to Section 9, and zero or more TLV assignments from the per-DNCP profile TLV registry as well as their processing rules.
DNCP node
a single node that runs a DNCP-based protocol.
Link
a link-layer media over which directly connected nodes can communicate.
DNCP network
a set of DNCP nodes running a DNCP-based protocol(s) with a matching DNCP profile(s). The set consists of nodes that have discovered each other using the transport method defined in the DNCP profile, via multicast on local links, and/or by using unicast communication.
Node identifier
an opaque fixed-length identifier consisting of DNCP_NODE_IDENTIFIER_LENGTH bytes that uniquely identifies a DNCP node within a DNCP network.
Interface
a node's attachment to a particular link.
Address
an identifier used as the source or destination of a DNCP message flow, e.g., a tuple (IPv6 address, UDP port) for an IPv6 UDP transport.
Endpoint
a locally configured termination point for (potential or established) DNCP message flows. An endpoint is the source and destination for separate unicast message flows to individual nodes and optionally for multicast messages to all thereby reachable nodes (e.g., for node discovery). Endpoints are usually in one of the transport modes specified in Section 4.2.
Endpoint identifier
a 32-bit opaque and locally unique value, which identifies a particular endpoint of a particular DNCP node. The value 0 is reserved for DNCP and DNCP-based protocol purposes and not used to identify an actual endpoint. 3. Overview

3. 概要

DNCP operates primarily using unicast exchanges between nodes, and it may use multicast for Trickle-based shared state dissemination and topology discovery. If used in pure unicast mode with unreliable transport, Trickle is also used between peers.

DNCPは主にノード間のユニキャスト交換を使用して動作し、Trickleベースの共有状態の配布とトポロジーの発見にマルチキャストを使用する場合があります。信頼性のないトランスポートで純粋なユニキャストモードで使用する場合は、ピア間でもTrickleを使用します。

DNCP is based on exchanging TLVs (Section 7) and defines a set of mandatory and optional ones for its operation. They are categorized into TLVs for requesting information (Section 7.1), transmitting data (Section 7.2), and being published as data (Section 7.3). DNCP-based protocols usually specify additional ones to extend the capabilities.

DNCPはTLV（セクション7）の交換に基づいており、その動作のために必須のTLVと任意のTLVの集合を定義します。これらは、情報を要求するためのTLV（セクション7.1）、データを送信するためのTLV（セクション7.2）、データとして公開されるTLV（セクション7.3）に分類されます。DNCPベースのプロトコルは通常、能力を拡張するために追加のTLVを規定します。

DNCP discovers the topology of the nodes in the DNCP network and maintains the liveliness of published node data by ensuring that the publishing node is bidirectionally reachable. New potential peers can be discovered autonomously on multicast-enabled links; their addresses may be manually configured or they may be found by some other means defined in the particular DNCP profile. The DNCP profile may specify, for example, a well-known anycast address or provision the remote address to contact via some other protocol such as DHCPv6 [RFC3315].

DNCPは、DNCPネットワーク内のノードのトポロジーを発見し、公開しているノードが双方向に到達可能であることを確認することで、公開されたノードデータの生存性を維持します。新しい潜在的なピアは、マルチキャストが有効なリンク上で自律的に発見できます。そのアドレスは、手動で設定することも、特定のDNCPプロファイルで定義された他の手段で見つけることもできます。DNCPプロファイルでは、たとえば、ウェルノウンなエニーキャストアドレスを規定したり、DHCPv6[RFC3315]のような他のプロトコルを介して接続先のリモートアドレスをプロビジョニングしたりできます。

A hash tree of height 1, rooted in itself, is maintained by each node to represent the state of all currently reachable nodes (see Section 4.1), and the Trickle algorithm is used to trigger synchronization (see Section 4.3). The need to check peer nodes for state changes is thereby determined by comparing the current root of their respective hash trees, i.e., their individually calculated network state hashes.

各ノードは、現在到達可能なすべてのノードの状態を表すために、自身をルートとする高さ1のハッシュツリーを維持し（セクション4.1を参照）、同期を開始するためにTrickleアルゴリズムを使用します（セクション4.3を参照）。これにより、ピアノードの状態変更を確認する必要があるかどうかは、それぞれのハッシュツリーの現在のルート、つまり個々に計算されたネットワーク状態ハッシュを比較することで判断されます。

Before joining a DNCP network, a node starts with a hash tree that has only one leaf if the node publishes some TLVs, and no leaves otherwise. It then announces the network state hash calculated from the hash tree by means of the Trickle algorithm on all its configured endpoints.

DNCPネットワークに参加する前、ノードは、何らかのTLVを公開している場合は葉が1つだけ、そうでない場合は葉のないハッシュツリーから開始します。その後、ノードは、設定されたすべてのエンドポイント上で、Trickleアルゴリズムによってハッシュツリーから計算したネットワーク状態ハッシュを告知します。

When an update is detected by a node (e.g., by receiving a different network state hash from a peer), the originator of the event is requested to provide a list of the state of all nodes, i.e., all the information it uses to calculate its own hash tree. The node uses the list to determine whether its own information is outdated and -- if necessary -- requests the actual node data that has changed.

ノードが（たとえば、ピアから異なるネットワーク状態ハッシュを受信することによって）更新を検出すると、イベントの発信者に対して、すべてのノードの状態の一覧、つまり発信者が自身のハッシュツリーを計算するために使用するすべての情報を提供するよう要求します。ノードはその一覧を使用して自身の情報が古くなっているかどうかを判断し、必要であれば、変更された実際のノードデータを要求します。

Whenever a node's local copy of any node data and its hash tree are updated (e.g., due to its own or another node's node state changing or due to a peer being added or removed), its Trickle instances are reset, which eventually causes any update to be propagated to all of its peers.

ノードが持つノードデータのローカルコピーとハッシュツリーが（たとえば、自身または他のノードのノード状態の変化や、ピアの追加または削除によって）更新されるたびに、そのノードのTrickleインスタンスはリセットされ、最終的にはすべての更新がそのすべてのピアに伝播されます。

4. Operation

4. 動作

4.1. Hash Tree

4.1. ハッシュツリー

Each DNCP node maintains an arbitrary width hash tree of height 1. The root of the tree represents the overall network state hash and is used to determine whether the view of the network of two or more nodes is consistent and shared. Each leaf represents one bidirectionally reachable DNCP node. Every time a node is added or removed from the topology graph (Section 4.6), it is likewise added or removed as a leaf. At any time, the leaves of the tree are ordered in ascending order of the node identifiers of the nodes they represent.

各DNCPノードは、任意の幅を持つ高さ1のハッシュツリーを維持します。ツリーのルートはネットワーク状態ハッシュ全体を表し、2つ以上のノードが持つネットワークのビューが整合し共有されているかどうかを判断するために使用されます。各葉は、双方向に到達可能な1つのDNCPノードを表します。トポロジーグラフ（セクション4.6）にノードが追加または削除されるたびに、同様に葉として追加または削除されます。ツリーの葉は常に、それが表すノードのノード識別子の昇順に並べられます。

4.1.1. Calculating Network State and Node Data Hashes

4.1.1. ネットワーク状態ハッシュとノードデータハッシュの計算

The network state hash and the node data hashes are calculated using the hash function defined in the DNCP profile (Section 9) and truncated to the number of bits specified therein.

ネットワーク状態ハッシュとノードデータハッシュは、DNCPプロファイル（セクション9）で定義されたハッシュ関数を使用して計算され、そこで指定されたビット数に切り詰められます。

Individual node data hashes are calculated by applying the function and truncation on the respective node's node data as published in the Node State TLV. Such node data sets are always ordered as defined in Section 7.2.3.

個々のノードデータハッシュは、Node State TLVで公開されている各ノードのノードデータに、関数と切り詰めを適用することで計算されます。このようなノードデータセットは、常にセクション7.2.3で定義されているとおりに並べられます。

The network state hash is calculated by applying the function and truncation on the concatenated network state. This state is formed by first concatenating each node's sequence number (in network byte order) with its node data hash to form a per-node datum for each node. These per-node data are then concatenated in ascending order of the respective node's node identifier, i.e., in the order that the nodes appear in the hash tree.

ネットワーク状態ハッシュは、連結したネットワーク状態に関数と切り詰めを適用することで計算されます。この状態は、まず各ノードのシーケンス番号（ネットワークバイトオーダー）とそのノードデータハッシュを連結して、各ノードのノードごとのデータを形成することで作られます。次に、これらのノードごとのデータを、各ノードのノード識別子の昇順、つまりハッシュツリーにノードが現れる順序で連結します。

4.1.2. Updating Network State and Node Data Hashes

4.1.2. ネットワーク状態ハッシュとノードデータハッシュの更新

The network state hash and the node data hashes are updated on-demand and whenever any locally stored per-node state changes. This includes local unidirectional reachability encoded in the published Peer TLVs (Section 7.3.1) and -- when combined with remote data -- results in awareness of bidirectional reachability changes.

ネットワーク状態ハッシュとノードデータハッシュは、必要に応じて、およびローカルに保存されたノードごとの状態が変化するたびに更新されます。これには、公開されたPeer TLV（セクション7.3.1）にエンコードされたローカルの単方向の到達可能性が含まれ、これをリモートのデータと組み合わせることで、双方向の到達可能性の変化を認識できるようになります。

4.2. Data Transport

4.2. データトランスポート

DNCP has few requirements for the underlying transport; it requires some way of transmitting either a unicast datagram or stream data to a peer and, if used in multicast mode, a way of sending multicast datagrams. As multicast is used only to identify potential new DNCP nodes and to send status messages that merely notify that a unicast exchange should be triggered, the multicast transport does not have to be secured. If unicast security is desired and one of the built-in security methods is to be used, support for some TLS-derived transport scheme -- such as TLS [RFC5246] on top of TCP or DTLS [RFC6347] on top of UDP -- is also required. They provide for integrity protection and confidentiality of the node data, as well as authentication and authorization using the schemes defined in "Security and Trust Management" (Section 8). A specific definition of the transport(s) in use and its parameters MUST be provided by the DNCP profile.

DNCPが下位のトランスポートに求める要件はわずかです。ピアにユニキャストデータグラムまたはストリームデータを送信する何らかの方法と、マルチキャストモードで使用する場合は、マルチキャストデータグラムを送信する方法が必要です。マルチキャストは、新しい潜在的なDNCPノードを識別することと、ユニキャスト交換を開始すべきことを通知するだけのステータスメッセージを送信することにのみ使用されるため、マルチキャストトランスポートを保護する必要はありません。ユニキャストのセキュリティーが望まれ、組み込みのセキュリティー方式の1つを使用する場合は、TCP上のTLS[RFC5246]やUDP上のDTLS[RFC6347]のような、TLSから派生した何らかのトランスポート方式のサポートも必要です。これらは、ノードデータの完全性保護と機密性に加えて、「セキュリティーと信頼の管理」（セクション8）で定義する方式を使用した認証と認可を提供します。使用するトランスポートとそのパラメーターの具体的な定義は、DNCPプロファイルで提供しなければなりません（MUST）。

TLVs (Section 7) are sent across the transport as is, and they SHOULD be sent together where, e.g., MTU considerations do not recommend sending them in multiple batches. DNCP does not fragment or reassemble TLVs; thus, it MUST be ensured that the underlying transport performs these operations should they be necessary. If this document indicates sending one or more TLVs, then the sending node does not need to keep track of the packets sent after handing them over to the respective transport, i.e., reliable DNCP operation is ensured merely by the explicitly defined timers and state machines such as Trickle (Section 4.3). TLVs in general are handled individually and statelessly (and thus do not need to be sent in any particular order) with one exception: To form bidirectional peer relationships, DNCP requires identification of the endpoints used for communication. As bidirectional peer relationships are required for validating liveliness of published node data as described in Section 4.6, a DNCP node MUST send a Node Endpoint TLV (Section 7.2.1). When it is sent varies, depending on the underlying transport, but conceptually it should be available whenever processing a Network State TLV:

TLV（セクション7）はトランスポート上でそのまま送信され、たとえばMTUの考慮から複数回に分けて送信することが推奨されない場合は、まとめて送信すべきです（SHOULD）。DNCPはTLVの断片化や再組み立てを行いません。したがって、それらの操作が必要な場合には、下位のトランスポートがそれらを実行することを保証しなければなりません（MUST）。この文書で1つ以上のTLVを送信することが示されている場合、送信するノードは、それぞれのトランスポートに引き渡した後に送信したパケットを追跡する必要はありません。つまり、DNCPの信頼性のある動作は、Trickle（セクション4.3）のような明示的に定義されたタイマーと状態機械によってのみ保証されます。TLVは一般に個別かつステートレスに処理されます（したがって、特定の順序で送信する必要はありません）が、1つの例外があります。双方向のピア関係を形成するために、DNCPでは通信に使用するエンドポイントを識別する必要があります。セクション4.6で説明するように、公開されたノードデータの生存性を検証するために双方向のピア関係が必要であるため、DNCPノードはNode Endpoint TLV（セクション7.2.1）を送信しなければなりません（MUST）。いつ送信するかは下位のトランスポートによって異なりますが、概念的には、Network State TLVを処理するときには常に利用可能であるべきです。

  • If using a stream transport, the TLV MUST be sent at least once per connection but SHOULD NOT be sent more than once.
  • If using a datagram transport, it MUST be included in every datagram that also contains a Network State TLV (Section 7.2.2) and MUST be located before any such TLV. It SHOULD also be included in any other datagram to speed up initial peer detection.
  • ストリームトランスポートを使用する場合、このTLVはコネクションごとに少なくとも1回送信しなければなりません（MUST）。ただし、2回以上送信すべきではありません（SHOULD NOT）。
  • データグラムトランスポートを使用する場合、このTLVは、Network State TLV（セクション7.2.2）も含むすべてのデータグラムに含めなければなりません（MUST）。また、そのようなTLVよりも前に配置しなければなりません（MUST）。最初のピア検出を高速化するために、その他のデータグラムにも含めるべきです（SHOULD）。

Given the assorted transport options as well as potential endpoint configuration, a DNCP endpoint may be used in various transport modes:

多様なトランスポートの選択肢と、潜在的なエンドポイントの設定を考えると、DNCPエンドポイントはさまざまなトランスポートモードで使用される可能性があります。

Unicast:
  • If only reliable unicast transport is used, Trickle is not used at all. Whenever the locally calculated network state hash changes, a single Network State TLV (Section 7.2.2) is sent to every unicast peer. Additionally, recently changed Node State TLVs (Section 7.2.3) MAY be included.
  • If only unreliable unicast transport is used, Trickle state is kept per peer, and it is used to send Network State TLVs intermittently, as specified in Section 4.3.
Multicast+Unicast:
If multicast datagram transport is available on an endpoint, Trickle state is only maintained for the endpoint as a whole. It is used to send Network State TLVs periodically, as specified in Section 4.3. Additionally, per-endpoint keep-alives MAY be defined in the DNCP profile, as specified in Section 6.1.2.
MulticastListen+Unicast:
Just like unicast, except multicast transmissions are listened to in order to detect changes of the highest node identifier. This mode is used only if the DNCP profile supports dense multicast-enabled link optimization (Section 6.2).
Unicast：
  • 信頼性のあるユニキャストトランスポートのみを使用する場合、Trickleはまったく使用しません。ローカルで計算したネットワーク状態ハッシュが変わるたびに、単一のNetwork State TLV（セクション7.2.2）をすべてのユニキャストピアに送信します。さらに、最近変更されたNode State TLV（セクション7.2.3）を含めてもよいです（MAY）。
  • 信頼性のないユニキャストトランスポートのみを使用する場合、Trickleの状態はピアごとに保持され、セクション4.3で規定するように、Network State TLVを断続的に送信するために使用されます。
Multicast+Unicast：
エンドポイント上でマルチキャストデータグラムトランスポートが利用可能な場合、Trickleの状態はエンドポイント全体に対してのみ維持されます。これは、セクション4.3で規定するように、Network State TLVを定期的に送信するために使用されます。さらに、セクション6.1.2で規定するように、エンドポイントごとのキープアライブをDNCPプロファイルで定義してもよいです（MAY）。
MulticastListen+Unicast：
ユニキャストとまったく同じですが、最も大きいノード識別子の変化を検出するために、マルチキャストの送信を受信する点が異なります。このモードは、DNCPプロファイルが密なマルチキャスト対応リンクの最適化（セクション6.2）をサポートしている場合にのみ使用されます。

4.3. Trickle-Driven Status Updates

4.3. Trickle駆動のステータス更新

The Trickle algorithm [RFC6206] is used to ensure protocol reliability over unreliable multicast or unicast transports. For reliable unicast transports, its actual algorithm is unnecessary and omitted (Section 4.2). DNCP maintains multiple Trickle states as defined in Section 5. Each such state can be based on different parameters (see below) and is responsible for ensuring that a specific peer or all peers on the respective endpoint are regularly provided with the node's current locally calculated network state hash for state comparison, i.e., to detect potential divergence in the perceived network state.

Trickleアルゴリズム[RFC6206]は、信頼性のないマルチキャストまたはユニキャストトランスポート上でプロトコルの信頼性を確保するために使用されます。信頼性のあるユニキャストトランスポートの場合、実際のアルゴリズムは不要であり、省略されます（セクション4.2）。DNCPは、セクション5で定義するように、複数のTrickle状態を維持します。そのような各状態は、異なるパラメーター（後述）に基づくことができ、状態の比較のために、つまり認識しているネットワーク状態の潜在的な相違を検出するために、特定のピアまたはそれぞれのエンドポイント上のすべてのピアに、そのノードがローカルで計算した現在のネットワーク状態ハッシュを定期的に提供することを確実にする役割を担います。

Trickle defines 3 parameters: Imin, Imax, and k. Imin and Imax represent the minimum value for I and the maximum number of doublings of Imin, where I is the time interval during which at least k Trickle updates must be seen on an endpoint to prevent local state transmission. The actual suggested Trickle algorithm parameters are DNCP profile specific, as described in Section 9.

Trickleは、Imin、Imax、kの3つのパラメーターを定義します。IminとImaxは、Iの最小値と、Iminを倍にする最大回数を表します。ここで、Iは、ローカルの状態の送信を抑止するために、エンドポイント上で少なくともk個のTrickle更新が観測されなければならない時間間隔です。実際に提案されるTrickleアルゴリズムのパラメーターは、セクション9で説明するように、DNCPプロファイル固有です。

The Trickle state for all Trickle instances defined in Section 5 is considered inconsistent and reset if and only if the locally calculated network state hash changes. This occurs either due to a change in the local node's own node data or due to the receipt of more recent data from another node as explained in Section 4.1. A node MUST NOT reset its Trickle state merely based on receiving a Network State TLV (Section 7.2.2) with a network state hash that is different from its locally calculated one.

セクション5で定義するすべてのTrickleインスタンスのTrickle状態は、ローカルで計算したネットワーク状態ハッシュが変化した場合に限り、不整合とみなされてリセットされます。これは、セクション4.1で説明するように、ローカルノード自身のノードデータの変更か、他のノードからのより新しいデータの受信のいずれかによって発生します。ノードは、ローカルで計算したものとは異なるネットワーク状態ハッシュを持つNetwork State TLV（セクション7.2.2）を受信したことだけに基づいて、Trickle状態をリセットしてはなりません（MUST NOT）。

Every time a particular Trickle instance indicates that an update should be sent, the node MUST send a Network State TLV (Section 7.2.2) if and only if:

特定のTrickleインスタンスが更新を送信すべきことを示すたびに、ノードは、次の場合に限り、Network State TLV（セクション7.2.2）を送信しなければなりません（MUST）。

  • the endpoint is in Multicast+Unicast transport mode, in which case the TLV MUST be sent over multicast.
  • the endpoint is NOT in Multicast+Unicast transport mode, and the unicast transport is unreliable, in which case the TLV MUST be sent over unicast.
  • エンドポイントがMulticast+Unicastトランスポートモードにある場合。この場合、TLVはマルチキャストで送信しなければなりません（MUST）。
  • エンドポイントがMulticast+Unicastトランスポートモードではなく、ユニキャストトランスポートに信頼性がない場合。この場合、TLVはユニキャストで送信しなければなりません（MUST）。

A (sub)set of all Node State TLVs (Section 7.2.3) MAY also be included, unless it is defined as undesirable for some reason by the DNCP profile or to avoid exposure of the node state TLVs by transmitting them within insecure multicast when using secure unicast.

DNCPプロファイルによって何らかの理由で望ましくないと定義されている場合や、安全なユニキャストを使用しているときに安全でないマルチキャストでNode State TLVを送信することでそれらが露出するのを避ける場合を除き、すべてのNode State TLV（セクション7.2.3）の（部分）集合を含めてもよいです（MAY）。

4.4. Processing of Received TLVs

4.4. 受信したTLVの処理

This section describes how received TLVs are processed. The DNCP profile may specify when to ignore particular TLVs, e.g., to modify security properties -- see Section 9 for what may be safely defined to be ignored in a profile. Any 'reply' mentioned in the steps below denotes the sending of the specified TLV(s) to the originator of the TLV being processed. All such replies MUST be sent using unicast. If the TLV being replied to was received via multicast and it was sent to a multiple access link, the reply MUST be delayed by a random time span in [0, Imin/2], to avoid potential simultaneous replies that may cause problems on some links, unless specified differently in the DNCP profile. The sending of replies MAY also be rate limited or omitted for a short period of time by an implementation. However, if the TLV is not forbidden by the DNCP profile, an implementation MUST reply to retransmissions of the TLV with a non-zero probability to avoid starvation, which would break the state synchronization.

このセクションでは、受信したTLVの処理方法を説明します。DNCPプロファイルでは、たとえばセキュリティー特性を変更するために、特定のTLVをいつ無視するかを規定できます。プロファイルで安全に無視するよう定義できるものについては、セクション9を参照してください。以下の手順で言及する「返信」は、処理中のTLVの発信者に、指定されたTLVを送信することを意味します。このような返信はすべて、ユニキャストを使用して送信しなければなりません（MUST）。返信の対象となるTLVがマルチキャストで受信され、マルチアクセスリンクに送信されたものであった場合、DNCPプロファイルで別途規定されていない限り、一部のリンクで問題を引き起こす可能性のある同時返信を避けるために、[0, Imin/2]の範囲のランダムな時間だけ返信を遅延させなければなりません（MUST）。実装は、返信の送信をレート制限したり、短時間省略したりしてもよいです（MAY）。ただし、DNCPプロファイルでそのTLVが禁止されていない場合、実装は、状態の同期を壊すことになる枯渇を避けるために、そのTLVの再送に0でない確率で返信しなければなりません（MUST）。

A DNCP node MUST process TLVs received from any valid (e.g., correctly scoped) address, as specified by the DNCP profile and the configuration of a particular endpoint, whether this address is known to be the address of a peer or not. This provision satisfies the needs of monitoring or other host software that needs to discover the DNCP topology without adding to the state in the network.

DNCPノードは、DNCPプロファイルと特定のエンドポイントの設定で規定されたとおり、任意の有効な（たとえば、スコープが正しい）アドレスから受信したTLVを、そのアドレスがピアのアドレスであるとわかっているかどうかにかかわらず、処理しなければなりません（MUST）。この規定は、ネットワーク内の状態を増やすことなくDNCPトポロジーを発見する必要がある、監視ソフトウェアやその他のホストソフトウェアのニーズを満たします。

Upon receipt of:

次のものを受信したとき：

  • Request Network State TLV (Section 7.1.1): The receiver MUST reply with a Network State TLV (Section 7.2.2) and a Node State TLV (Section 7.2.3) for each node data used to calculate the network state hash. The Node State TLVs SHOULD NOT contain the optional node data part to avoid redundant transmission of node data, unless explicitly specified in the DNCP profile.
  • Request Node State TLV (Section 7.1.2): If the receiver has node data for the corresponding node, it MUST reply with a Node State TLV (Section 7.2.3) for the corresponding node. The optional node data part MUST be included in the TLV.
  • Network State TLV (Section 7.2.2): If the network state hash differs from the locally calculated network state hash, and the receiver is unaware of any particular node state differences with the sender, the receiver MUST reply with a Request Network State TLV (Section 7.1.1). These replies MUST be rate limited to only at most one reply per link per unique network state hash within Imin. The simplest way to ensure this rate limit is a timestamp indicating requests and sending at most one Request Network State TLV (Section 7.1.1) per Imin. To facilitate faster state synchronization, if a Request Network State TLV is sent in a reply, a local, current Network State TLV MAY also be sent.

  • Node State TLV (Section 7.2.3):

    • If the node identifier matches the local node identifier and the TLV has a greater sequence number than its current local value, or the same sequence number and a different hash, the node SHOULD republish its own node data with a sequence number significantly greater than the received one (e.g., 1000) to reclaim the node identifier. This difference is needed in order to ensure that it is higher than any potentially lingering copies of the node state in the network. This may occur normally once due to the local node restarting and not storing the most recently used sequence number. If this occurs more than once or for nodes not republishing their own node data, the DNCP profile MUST provide guidance on how to handle these situations as it indicates the existence of another active node with the same node identifier.

    • If the node identifier does not match the local node identifier, and one or more of the following conditions are true:

      • The local information is outdated for the corresponding node (the local sequence number is less than that within the TLV).
      • The local information is potentially incorrect (the local sequence number matches but the node data hash differs).
      • There is no data for that node altogether.

      Then:

      • If the TLV contains the Node Data field, it SHOULD also be verified by ensuring that the locally calculated hash of the node data matches the content of the H(Node Data) field within the TLV. If they differ, the TLV SHOULD be ignored and not processed further.
      • If the TLV does not contain the Node Data field, and the H(Node Data) field within the TLV differs from the local node data hash for that node (or there is none), the receiver MUST reply with a Request Node State TLV (Section 7.1.2) for the corresponding node.
      • Otherwise, the receiver MUST update its locally stored state for that node (node data based on the Node Data field if present, sequence number, and relative time) to match the received TLV.

    For comparison purposes of the sequence number, a looping comparison function MUST be used to avoid problems in case of overflow. The comparison function a < b <=> ((a - b) % (2^32)) & (2^31) != 0 where (a % b) represents the remainder of a modulo b and (a & b) represents bitwise conjunction of a and b is RECOMMENDED unless the DNCP profile defines another.

  • Any other TLV: TLVs not recognized by the receiver MUST be silently ignored unless they are sent within another TLV (for example, TLVs within the Node Data field of a Node State TLV). TLVs within the Node Data field of the Node State TLV not recognized by the receiver MUST be retained for distribution to other nodes and for calculation of the node data hash as described in Section 7.2.3 but are ignored for other purposes.
  • Request Network State TLV（セクション7.1.1）：受信者は、Network State TLV（セクション7.2.2）と、ネットワーク状態ハッシュの計算に使用した各ノードデータについてのNode State TLV（セクション7.2.3）で返信しなければなりません（MUST）。DNCPプロファイルで明示的に規定されていない限り、ノードデータの冗長な送信を避けるために、Node State TLVには任意のノードデータ部分を含めるべきではありません（SHOULD NOT）。
  • Request Node State TLV（セクション7.1.2）：受信者が対応するノードのノードデータを持っている場合、対応するノードについてのNode State TLV（セクション7.2.3）で返信しなければなりません（MUST）。任意のノードデータ部分をTLVに含めなければなりません（MUST）。
  • Network State TLV（セクション7.2.2）：ネットワーク状態ハッシュがローカルで計算したネットワーク状態ハッシュと異なり、受信者が送信者との特定のノード状態の違いを認識していない場合、受信者はRequest Network State TLV（セクション7.1.1）で返信しなければなりません（MUST）。これらの返信は、Imin内で、リンクごと、一意なネットワーク状態ハッシュごとに、最大1回の返信に制限しなければなりません（MUST）。このレート制限を確保する最も簡単な方法は、要求を示すタイムスタンプを使い、Request Network State TLV（セクション7.1.1）をIminごとに最大1回だけ送信することです。より速い状態の同期を促すために、返信でRequest Network State TLVを送信する場合、ローカルの現在のNetwork State TLVも送信してもよいです（MAY）。

  • Node State TLV（セクション7.2.3）：

    • ノード識別子がローカルのノード識別子と一致し、TLVが現在のローカルの値より大きいシーケンス番号を持つ場合、または同じシーケンス番号で異なるハッシュを持つ場合、ノードは、ノード識別子を取り戻すために、受信したものより大幅に大きい（たとえば1000大きい）シーケンス番号で自身のノードデータを再公開すべきです（SHOULD）。この差は、ネットワーク内に残っている可能性のあるノード状態のコピーよりも大きいことを保証するために必要です。これは、ローカルノードが再起動して、最後に使用したシーケンス番号を保存していなかったために、通常でも1回は発生する可能性があります。これが2回以上発生した場合や、自身のノードデータを再公開していないノードについて発生した場合、それは同じノード識別子を持つ別のアクティブなノードの存在を示しているため、DNCPプロファイルは、このような状況の処理方法に関するガイダンスを提供しなければなりません（MUST）。

    • ノード識別子がローカルのノード識別子と一致せず、かつ次の条件の1つ以上が真である場合：

      • 対応するノードについてのローカルの情報が古い（ローカルのシーケンス番号がTLV内のものより小さい）。
      • ローカルの情報が誤っている可能性がある（ローカルのシーケンス番号は一致するが、ノードデータハッシュが異なる）。
      • そのノードについてのデータがまったくない。

      その場合：

      • TLVにNode Dataフィールドが含まれている場合、ローカルで計算したノードデータのハッシュがTLV内のH(Node Data)フィールドの内容と一致することを確認して、検証もすべきです（SHOULD）。両者が異なる場合、そのTLVは無視して、それ以上処理しないべきです（SHOULD）。
      • TLVにNode Dataフィールドが含まれておらず、TLV内のH(Node Data)フィールドが、そのノードについてのローカルのノードデータハッシュと異なる（またはローカルのノードデータハッシュがない）場合、受信者は、対応するノードについてのRequest Node State TLV（セクション7.1.2）で返信しなければなりません（MUST）。
      • それ以外の場合、受信者は、受信したTLVと一致するように、そのノードについてローカルに保存している状態（Node Dataフィールドがあればそれに基づくノードデータ、シーケンス番号、相対時間）を更新しなければなりません（MUST）。

    シーケンス番号の比較のために、オーバーフロー時の問題を避けるため、循環する比較関数を使用しなければなりません（MUST）。DNCPプロファイルで別の関数を定義していない限り、比較関数a < b <=> ((a - b) % (2^32)) & (2^31) != 0（ここで、(a % b)はaをbで割った剰余を表し、(a & b)はaとbのビットごとの論理積を表します）が推奨されます（RECOMMENDED）。

  • その他のTLV：受信者が認識できないTLVは、別のTLVの中で送信されたもの（たとえば、Node State TLVのNode Dataフィールド内のTLV）でない限り、黙って無視しなければなりません（MUST）。Node State TLVのNode Dataフィールド内の、受信者が認識できないTLVは、他のノードへの配布と、セクション7.2.3で説明するノードデータハッシュの計算のために保持しなければなりません（MUST）が、それ以外の目的では無視されます。

If secure unicast transport is configured for an endpoint, any Node State TLVs received over insecure multicast MUST be silently ignored.

エンドポイントに安全なユニキャストトランスポートが設定されている場合、安全でないマルチキャストで受信したNode State TLVはすべて黙って無視しなければなりません（MUST）。

4.5. Discovering, Adding, and Removing Peers

4.5. ピアの発見、追加、削除

Peer relations are established between neighbors using one or more mutually connected endpoints. Such neighbors exchange information about network state and published data directly, and through transitivity, this information then propagates throughout the network.

ピア関係は、相互に接続された1つ以上のエンドポイントを使用して、近隣間で確立されます。そのような近隣同士は、ネットワーク状態と公開されたデータに関する情報を直接交換し、推移的に、この情報はネットワーク全体に伝播します。

New peers are discovered using the regular unicast or multicast transport defined in the DNCP profile (Section 9). This process is not distinguished from peer addition, i.e., an unknown peer is simply discovered by receiving regular DNCP protocol TLVs from it, and dedicated discovery messages or TLVs do not exist. For unicast-only transports, the individual node's transport addresses are preconfigured or obtained using an external service discovery protocol. In the presence of a multicast transport, messages from unknown peers are handled in the same way as multicast messages from peers that are already known; thus, new peers are simply discovered when sending their regular DNCP protocol TLVs using multicast.

新しいピアは、DNCPプロファイル（セクション9）で定義された通常のユニキャストまたはマルチキャストのトランスポートを使用して発見されます。このプロセスはピアの追加と区別されません。つまり、未知のピアは、そのピアから通常のDNCPプロトコルのTLVを受信することによって単に発見され、専用の発見メッセージやTLVは存在しません。ユニキャストのみのトランスポートの場合、個々のノードのトランスポートアドレスは、事前に設定されるか、外部のサービス発見プロトコルを使用して取得されます。マルチキャストトランスポートがある場合、未知のピアからのメッセージは、既知のピアからのマルチキャストメッセージと同じ方法で処理されます。したがって、新しいピアは、通常のDNCPプロトコルのTLVをマルチキャストで送信したときに単に発見されます。

When receiving a Node Endpoint TLV (Section 7.2.1) on an endpoint from an unknown peer:

エンドポイント上で未知のピアからNode Endpoint TLV（セクション7.2.1）を受信した場合：

  • If received over unicast, the remote node MUST be added as a peer on the endpoint, and a Peer TLV (Section 7.3.1) MUST be created for it.
  • If received over multicast, the node MAY be sent a (possibly rate-limited) unicast Request Network State TLV (Section 7.1.1).
  • ユニキャストで受信した場合、リモートノードをそのエンドポイント上のピアとして追加しなければなりません（MUST）。また、そのピアについてのPeer TLV（セクション7.3.1）を作成しなければなりません（MUST）。
  • マルチキャストで受信した場合、そのノードに（場合によってはレート制限された）ユニキャストのRequest Network State TLV（セクション7.1.1）を送信してもよいです（MAY）。

If keep-alives specified in Section 6.1 are NOT sent by the peer (either the DNCP profile does not specify the use of keep-alives or the particular peer chooses not to send keep-alives), some other existing local transport-specific means (such as Ethernet carrier detection or TCP keep-alive) MUST be used to ensure its presence. If the peer does not send keep-alives, and no means to verify presence of the peer are available, the peer MUST be considered no longer present, and it SHOULD NOT be added back as a peer until it starts sending keep-alives again. When the peer is no longer present, the Peer TLV and the local DNCP peer state MUST be removed. DNCP does not define an explicit message or TLV for indicating the termination of DNCP operation by the terminating node; however, a derived protocol could specify an extension, if the need arises.

セクション6.1で規定するキープアライブをピアが送信しない場合（DNCPプロファイルがキープアライブの使用を規定していないか、特定のピアがキープアライブを送信しないことを選択した場合）、ピアの存在を確認するために、何らかの既存のローカルなトランスポート固有の手段（イーサネットのキャリア検出やTCPキープアライブなど）を使用しなければなりません（MUST）。ピアがキープアライブを送信せず、ピアの存在を検証する手段も利用できない場合、そのピアはもはや存在しないとみなさなければなりません（MUST）。また、キープアライブの送信を再開するまで、ピアとして再び追加すべきではありません（SHOULD NOT）。ピアがもはや存在しない場合、Peer TLVとローカルのDNCPピア状態を削除しなければなりません（MUST）。DNCPは、終了するノードがDNCPの動作の終了を示すための明示的なメッセージやTLVを定義していませんが、必要が生じた場合には、派生プロトコルで拡張を規定できます。

If the local endpoint is in the Multicast-Listen+Unicast transport mode, a Peer TLV (Section 7.3.1) MUST NOT be published for the peers not having the highest node identifier.

ローカルのエンドポイントがMulticast-Listen+Unicastトランスポートモードにある場合、最も大きいノード識別子を持たないピアについてのPeer TLV（セクション7.3.1）を公開してはなりません（MUST NOT）。

4.6. Data Liveliness Validation

4.6. データの生存性の検証

Maintenance of the hash tree (Section 4.1) and thereby network state hash updates depend on up-to-date information on bidirectional node reachability derived from the contents of a topology graph. This graph changes whenever nodes are added to or removed from the network or when bidirectional connectivity between existing nodes is established or lost. Therefore, the graph MUST be updated either immediately or with a small delay shorter than the DNCP profile-defined Trickle Imin whenever:

ハッシュツリー（セクション4.1）の維持と、それによるネットワーク状態ハッシュの更新は、トポロジーグラフの内容から得られる、ノードの双方向の到達可能性に関する最新の情報に依存します。このグラフは、ネットワークにノードが追加または削除されたとき、あるいは既存のノード間の双方向の接続性が確立または喪失されたときに変化します。したがって、次の場合には常に、グラフをただちに、またはDNCPプロファイルで定義されたTrickleのIminより短い小さな遅延で更新しなければなりません（MUST）。

  • A Peer TLV or a whole node is added or removed, or
  • The origination time (in milliseconds) of some node's node data is less than current time - 2^32 + 2^15.
  • Peer TLVまたはノード全体が追加または削除された場合、または
  • あるノードのノードデータの発信時刻（ミリ秒単位）が、現在時刻 - 2^32 + 2^15より小さい場合。

The artificial upper limit for the origination time is used to gracefully avoid overflows of the origination time and allow for the node to republish its data as noted in Section 7.2.3.

発信時刻に人為的な上限を設けるのは、発信時刻のオーバーフローを穏便に回避し、セクション7.2.3で述べるようにノードがデータを再公開できるようにするためです。

The topology graph update starts with the local node marked as reachable and all other nodes marked as unreachable. Other nodes are then iteratively marked as reachable using the following algorithm: A candidate not-yet-reachable node N with an endpoint NE is marked as reachable if there is a reachable node R with an endpoint RE that meets all of the following criteria:

トポロジーグラフの更新は、ローカルノードを到達可能とし、他のすべてのノードを到達不可能としてマークした状態から開始します。次に、以下のアルゴリズムを使用して、他のノードを反復的に到達可能としてマークします。エンドポイントNEを持つ、まだ到達可能でない候補ノードNは、エンドポイントREを持つ到達可能なノードRが存在し、それが次のすべての基準を満たす場合に、到達可能としてマークされます。

  • The origination time (in milliseconds) of R's node data is greater than current time - 2^32 + 2^15.

  • R publishes a Peer TLV with:

    • Peer Node Identifier = N's node identifier
    • Peer Endpoint Identifier = NE's endpoint identifier
    • Endpoint Identifier = RE's endpoint identifier

  • N publishes a Peer TLV with:

    • Peer Node Identifier = R's node identifier
    • Peer Endpoint Identifier = RE's endpoint identifier
    • Endpoint Identifier = NE's endpoint identifier
  • Rのノードデータの発信時刻（ミリ秒単位）が、現在時刻 - 2^32 + 2^15より大きい。

  • Rが次の内容のPeer TLVを公開している：

    • Peer Node Identifier = Nのノード識別子
    • Peer Endpoint Identifier = NEのエンドポイント識別子
    • Endpoint Identifier = REのエンドポイント識別子

  • Nが次の内容のPeer TLVを公開している：

    • Peer Node Identifier = Rのノード識別子
    • Peer Endpoint Identifier = REのエンドポイント識別子
    • Endpoint Identifier = NEのエンドポイント識別子

The algorithm terminates when no more candidate nodes fulfilling these criteria can be found.

このアルゴリズムは、これらの基準を満たす候補ノードがそれ以上見つからなくなった時点で終了します。

DNCP nodes that have not been reachable in the most recent topology graph traversal MUST NOT be used for calculation of the network state hash, be provided to any applications that need to use the whole TLV graph, or be provided to remote nodes. They MAY be forgotten immediately after the topology graph traversal; however, it is RECOMMENDED to keep them at least briefly to improve the speed of DNCP network state convergence. This reduces the number of queries needed to reconverge during both initial network convergence and when a part of the network loses and regains bidirectional connectivity within that time period.

直近のトポロジーグラフの走査で到達可能でなかったDNCPノードを、ネットワーク状態ハッシュの計算に使用したり、TLVグラフ全体を使用する必要のあるアプリケーションに提供したり、リモートノードに提供したりしてはなりません（MUST NOT）。そのようなノードは、トポロジーグラフの走査直後に忘れてもよいです（MAY）が、DNCPネットワーク状態の収束を速めるために、少なくとも短時間は保持することが推奨されます（RECOMMENDED）。これにより、最初のネットワーク収束の際と、ネットワークの一部がその期間内に双方向の接続性を失って回復した際の両方で、再収束に必要なクエリーの数が減ります。

5. Data Model

5. データモデル

This section describes the local data structures a minimal implementation might use. This section is provided only as a convenience for the implementor. Some of the optional extensions (Section 6) describe additional data requirements, and some optional parts of the core protocol may also require more.

このセクションでは、最小限の実装が使用する可能性のあるローカルのデータ構造について説明します。このセクションは、実装者の便宜のためだけに提供されています。任意の拡張（セクション6）の一部は追加のデータ要件を記述しており、コアプロトコルの任意の部分の一部でも、さらに多くのデータが必要になる場合があります。

A DNCP node has:

DNCPノードは次のものを持ちます。

  • A data structure containing data about the most recently sent Request Network State TLVs (Section 7.1.1). The simplest option is keeping a timestamp of the most recent request (required to fulfill reply rate limiting specified in Section 4.4).
  • 最近送信したRequest Network State TLV（セクション7.1.1）に関するデータを含むデータ構造。最も簡単な方法は、最新の要求のタイムスタンプを保持することです（セクション4.4で規定する返信のレート制限を満たすために必要です）。

A DNCP node has the following for every DNCP node in the DNCP network:

DNCPノードは、DNCPネットワーク内のすべてのDNCPノードについて、次のものを持ちます。

  • Node identifier: the unique identifier of the node. The length, how it is produced, and how collisions are handled is up to the DNCP profile.
  • Node data: the set of TLV tuples published by that particular node. As they are transmitted in a particular order (see Node State TLV (Section 7.2.3) for details), maintaining the order within the data structure here may be reasonable.
  • Latest sequence number: the 32-bit sequence number that is incremented any time the TLV set is published. The comparison function used to compare them is described in Section 4.4.
  • Origination time: the (estimated) time when the current TLV set with the current sequence number was published. It is used to populate the Milliseconds Since Origination field in a Node State TLV (Section 7.2.3). Ideally, it also has millisecond accuracy.
  • ノード識別子：ノードの一意な識別子。その長さ、生成方法、衝突の処理方法はDNCPプロファイルに委ねられます。
  • ノードデータ：その特定のノードが公開したTLVタプルの集合。これらは特定の順序で送信されるため（詳細はNode State TLV（セクション7.2.3）を参照）、ここでのデータ構造内でもその順序を維持するのが合理的かもしれません。
  • 最新のシーケンス番号：TLVセットが公開されるたびにインクリメントされる32ビットのシーケンス番号。これらを比較するために使用する比較関数は、セクション4.4で説明しています。
  • 発信時刻：現在のシーケンス番号を持つ現在のTLVセットが公開された（推定）時刻。これは、Node State TLV（セクション7.2.3）のMilliseconds Since Originationフィールドに値を設定するために使用されます。理想的には、ミリ秒の精度も持ちます。

Additionally, a DNCP node has a set of endpoints for which DNCP is configured to be used. For each such endpoint, a node has:

さらに、DNCPノードは、DNCPを使用するように設定されたエンドポイントの集合を持ちます。そのような各エンドポイントについて、ノードは次のものを持ちます。

  • Endpoint identifier: the 32-bit opaque locally unique value identifying the endpoint within a node. It SHOULD NOT be reused immediately after an endpoint is disabled.
  • Trickle instance: the endpoint's Trickle instance with parameters I, T, and c (only on an endpoint in Multicast+Unicast transport mode).
  • エンドポイント識別子：ノード内でエンドポイントを識別する、32ビットの不透明でローカルに一意な値。エンドポイントが無効化された直後に再利用すべきではありません（SHOULD NOT）。
  • Trickleインスタンス：パラメーターI、T、cを持つ、エンドポイントのTrickleインスタンス（Multicast+Unicastトランスポートモードのエンドポイントの場合のみ）。

and one (or more) of the following:

そして、次のうちの1つ（以上）：

  • Interface: the assigned local network interface.
  • Unicast address: the DNCP node it should connect with.
  • Set of addresses: the DNCP nodes from which connections are accepted.
  • インターフェイス：割り当てられたローカルのネットワークインターフェイス。
  • ユニキャストアドレス：接続すべきDNCPノード。
  • アドレスの集合：コネクションを受け入れるDNCPノード。

For each remote (peer, endpoint) pair detected on a local endpoint, a DNCP node has:

ローカルのエンドポイント上で検出されたリモートの（ピア、エンドポイント）のペアごとに、DNCPノードは次のものを持ちます。

  • Node identifier: the unique identifier of the peer.
  • Endpoint identifier: the unique endpoint identifier used by the peer.
  • Peer address: the most recently used address of the peer (authenticated and authorized, if security is enabled).
  • Trickle instance: the particular peer's Trickle instance with parameters I, T, and c (only on an endpoint in unicast mode, when using an unreliable unicast transport).
  • ノード識別子：ピアの一意な識別子。
  • エンドポイント識別子：ピアが使用する一意なエンドポイント識別子。
  • ピアアドレス：ピアが直近に使用したアドレス（セキュリティーが有効な場合は、認証および認可されたもの）。
  • Trickleインスタンス：パラメーターI、T、cを持つ、その特定のピアのTrickleインスタンス（信頼性のないユニキャストトランスポートを使用している場合の、ユニキャストモードのエンドポイントの場合のみ）。

6. Optional Extensions

6. 任意の拡張

This section specifies extensions to the core protocol that a DNCP profile may specify to be used.

このセクションでは、DNCPプロファイルが使用を規定できる、コアプロトコルに対する拡張を規定します。

6.1. Keep-Alives

6.1. キープアライブ

While DNCP provides mechanisms for discovery and adding new peers on an endpoint (Section 4.5), as well as state change notifications, another mechanism may be needed to get rid of old, no longer valid peers if the transport or lower layers do not provide one as noted in Section 4.6.

DNCPは、エンドポイント上で新しいピアを発見して追加するメカニズム（セクション4.5）と状態変更の通知を提供しますが、セクション4.6で述べるように、トランスポートや下位層がそのようなメカニズムを提供しない場合には、古くてもはや有効でないピアを取り除くための別のメカニズムが必要になることがあります。

If keep-alives are not specified in the DNCP profile, the rest of this subsection MUST be ignored.

DNCPプロファイルでキープアライブが規定されていない場合、このサブセクションの残りの部分は無視しなければなりません（MUST）。

A DNCP profile MAY specify either per-endpoint (sent using multicast to all DNCP nodes connected to a multicast-enabled link) or per-peer (sent using unicast to each peer individually) keep-alive support.

DNCPプロファイルでは、エンドポイントごと（マルチキャストが有効なリンクに接続されたすべてのDNCPノードにマルチキャストを使用して送信）、またはピアごと（各ピアに個別にユニキャストを使用して送信）のいずれかのキープアライブのサポートを規定してもよいです（MAY）。

For every endpoint that a keep-alive is specified for in the DNCP profile, the endpoint-specific keep-alive interval MUST be maintained. By default, it is DNCP_KEEPALIVE_INTERVAL. If there is a local value that is preferred for that for any reason (configuration, energy conservation, media type, ...), it can be substituted instead. If a non-default keep-alive interval is used on any endpoint, a DNCP node MUST publish an appropriate Keep-Alive Interval TLV(s) (Section 7.3.2) within its node data.

DNCPプロファイルでキープアライブが規定されているすべてのエンドポイントについて、エンドポイント固有のキープアライブ間隔を維持しなければなりません（MUST）。デフォルトでは、それはDNCP_KEEPALIVE_INTERVALです。何らかの理由（設定、省エネルギー、媒体の種類など）で優先されるローカルの値がある場合は、代わりにそれを使用できます。いずれかのエンドポイントでデフォルト以外のキープアライブ間隔を使用する場合、DNCPノードは、適切なKeep-Alive Interval TLV（セクション7.3.2）を自身のノードデータ内で公開しなければなりません（MUST）。

6.1.1. Data Model Additions

6.1.1. データモデルへの追加

The following additions to the Data Model (Section 5) are needed to support keep-alives:

キープアライブをサポートするには、データモデル（セクション5）に次の追加が必要です。

For each configured endpoint that has per-endpoint keep-alives enabled:

エンドポイントごとのキープアライブが有効になっている、設定された各エンドポイントについて：

  • Last sent: If a timestamp that indicates the last time a Network State TLV (Section 7.2.2) was sent over that interface.
  • 最終送信：そのインターフェイスでNetwork State TLV（セクション7.2.2）を最後に送信した時刻を示すタイムスタンプがある場合はそのタイムスタンプ。

For each remote (peer, endpoint) pair detected on a local endpoint, a DNCP node has:

ローカルのエンドポイント上で検出されたリモートの（ピア、エンドポイント）のペアごとに、DNCPノードは次のものを持ちます。

  • Last contact timestamp: A timestamp that indicates the last time a consistent Network State TLV (Section 7.2.2) was received from the peer over multicast or when anything was received over unicast. Failing to update it for a certain amount of time as specified in Section 6.1.5 results in the removal of the peer. When adding a new peer, it is initialized to the current time.
  • Last sent: If per-peer keep-alives are enabled, a timestamp that indicates the last time a Network State TLV (Section 7.2.2) was sent to that point-to-point peer. When adding a new peer, it is initialized to the current time.
  • 最終接触タイムスタンプ：ピアから整合したNetwork State TLV（セクション7.2.2）をマルチキャストで最後に受信した時刻、または何かをユニキャストで最後に受信した時刻を示すタイムスタンプ。セクション6.1.5で規定する一定の時間これを更新できなかった場合、そのピアは削除されます。新しいピアを追加するときは、現在時刻で初期化されます。
  • 最終送信：ピアごとのキープアライブが有効な場合、そのポイントツーポイントのピアにNetwork State TLV（セクション7.2.2）を最後に送信した時刻を示すタイムスタンプ。新しいピアを追加するときは、現在時刻で初期化されます。

6.1.2. Per-Endpoint Periodic Keep-Alives

6.1.2. エンドポイントごとの定期的なキープアライブ

If per-endpoint keep-alives are enabled on an endpoint in Multicast+Unicast transport mode, and if no traffic containing a Network State TLV (Section 7.2.2) has been sent to a particular endpoint within the endpoint-specific keep-alive interval, a Network State TLV (Section 7.2.2) MUST be sent on that endpoint, and a new Trickle interval started, as specified in step 2 of Section 4.2 of [RFC6206]. The actual sending time SHOULD be further delayed by a random time span in [0, Imin/2].

Multicast+Unicastトランスポートモードのエンドポイントでエンドポイントごとのキープアライブが有効になっていて、エンドポイント固有のキープアライブ間隔内に、Network State TLV（セクション7.2.2）を含むトラフィックが特定のエンドポイントに送信されていない場合、そのエンドポイントでNetwork State TLV（セクション7.2.2）を送信し、[RFC6206]のセクション4.2のステップ2で規定されているように新しいTrickle間隔を開始しなければなりません（MUST）。実際の送信時刻は、さらに[0, Imin/2]の範囲のランダムな時間だけ遅延させるべきです（SHOULD）。

6.1.3. Per-Peer Periodic Keep-Alives

6.1.3. ピアごとの定期的なキープアライブ

If per-peer keep-alives are enabled on a unicast-only endpoint, and if no traffic containing a Network State TLV (Section 7.2.2) has been sent to a particular peer within the endpoint-specific keep-alive interval, a Network State TLV (Section 7.2.2) MUST be sent to the peer, and a new Trickle interval started, as specified in step 2 of Section 4.2 of [RFC6206].

ユニキャストのみのエンドポイントでピアごとのキープアライブが有効になっていて、エンドポイント固有のキープアライブ間隔内に、Network State TLV（セクション7.2.2）を含むトラフィックが特定のピアに送信されていない場合、そのピアにNetwork State TLV（セクション7.2.2）を送信し、[RFC6206]のセクション4.2のステップ2で規定されているように新しいTrickle間隔を開始しなければなりません（MUST）。

6.1.4. Received TLV Processing Additions

6.1.4. 受信したTLVの処理への追加

If a TLV is received over unicast from the peer, the Last contact timestamp for the peer MUST be updated.

ピアからユニキャストでTLVを受信した場合、そのピアの最終接触タイムスタンプを更新しなければなりません（MUST）。

On receipt of a Network State TLV (Section 7.2.2) that is consistent with the locally calculated network state hash, the Last contact timestamp for the peer MUST be updated in order to maintain it as a peer.

ローカルで計算したネットワーク状態ハッシュと整合するNetwork State TLV（セクション7.2.2）を受信したとき、そのピアをピアとして維持するために、ピアの最終接触タイムスタンプを更新しなければなりません（MUST）。

6.1.5. Peer Removal

6.1.5. ピアの削除

For every peer on every endpoint, the endpoint-specific keep-alive interval must be calculated by looking for Keep-Alive Interval TLVs (Section 7.3.2) published by the node, and if none exist, use the default value of DNCP_KEEPALIVE_INTERVAL. If the peer's Last contact timestamp has not been updated for at least a locally chosen potentially endpoint-specific keep-alive multiplier (defaults to DNCP_KEEPALIVE_MULTIPLIER) times the peer's endpoint-specific keep-alive interval, the Peer TLV for that peer and the local DNCP peer state MUST be removed.

すべてのエンドポイント上のすべてのピアについて、そのノードが公開したKeep-Alive Interval TLV（セクション7.3.2）を探してエンドポイント固有のキープアライブ間隔を計算する必要があり、それが存在しない場合はデフォルト値のDNCP_KEEPALIVE_INTERVALを使用します。ピアの最終接触タイムスタンプが、ローカルで選択された（エンドポイント固有である可能性のある）キープアライブ乗数（デフォルトはDNCP_KEEPALIVE_MULTIPLIER）とピアのエンドポイント固有のキープアライブ間隔の積以上の期間更新されていない場合、そのピアについてのPeer TLVとローカルのDNCPピア状態を削除しなければなりません（MUST）。

6.2. Support for Dense Multicast-Enabled Links

6.2. 密なマルチキャスト対応リンクのサポート

This optimization is needed to avoid a state space explosion. Given a large set of DNCP nodes publishing data on an endpoint that uses multicast on a link, every node will add a Peer TLV (Section 7.3.1) for each peer. While Trickle limits the amount of traffic on the link in stable state to some extent, the total amount of data that is added to and maintained in the DNCP network given N nodes on a multicast-enabled link is O(N^2). Additionally, if per-peer keep-alives are used, there will be O(N^2) keep-alives running on the link if the liveliness of peers is not ensured using some other way (e.g., TCP connection lifetime, Layer 2 notification, or per-endpoint keep-alive).

この最適化は、状態空間の爆発を避けるために必要です。リンク上でマルチキャストを使用するエンドポイントでデータを公開する大量のDNCPノードがある場合、すべてのノードが各ピアについてのPeer TLV（セクション7.3.1）を追加します。Trickleは安定状態でのリンク上のトラフィック量をある程度制限しますが、マルチキャスト対応リンク上にN個のノードがある場合、DNCPネットワークに追加され維持されるデータの総量はO(N^2)になります。さらに、ピアごとのキープアライブを使用する場合、ピアの生存性が他の方法（たとえば、TCPコネクションの有効期間、レイヤー2の通知、またはエンドポイントごとのキープアライブ）で確保されていなければ、リンク上でO(N^2)個のキープアライブが実行されることになります。

An upper bound for the number of peers that are allowed for a particular type of link that an endpoint in Multicast+Unicast transport mode is used on SHOULD be provided by a DNCP profile, but it MAY also be chosen at runtime. The main consideration when selecting a bound (if any) for a particular type of link should be whether it supports multicast traffic and whether a too large number of peers case is likely to happen during the use of that DNCP profile on that particular type of link. If neither is likely, there is little point specifying support for this for that particular link type.

If a DNCP profile does not support this extension at all, the rest of this subsection MUST be ignored. This is because when this extension is used, the state within the DNCP network only contains a subset of the full topology of the network. Therefore, every node must be aware of the potential of it being used in a particular DNCP profile.

DNCPプロファイルがこの拡張をまったくサポートしない場合、このサブセクションの残りの部分は無視しなければなりません（MUST）。これは、この拡張を使用すると、DNCPネットワーク内の状態にはネットワークの完全なトポロジーの一部しか含まれないためです。したがって、すべてのノードは、特定のDNCPプロファイルでこの拡張が使用される可能性を認識している必要があります。

If the specified upper bound is exceeded for some endpoint in Multicast+Unicast transport mode and if the node does not have the highest node identifier on the link, it SHOULD treat the endpoint as a unicast endpoint connected to the node that has the highest node identifier detected on the link, therefore transitioning to Multicast-listen+Unicast transport mode. See Section 4.2 for implications on the specific endpoint behavior. The nodes in Multicast-listen+Unicast transport mode MUST keep listening to multicast traffic to both receive messages from the node(s) still in Multicast+Unicast mode and react to nodes with a greater node identifier appearing. If the highest node identifier present on the link changes, the remote unicast address of the endpoints in Multicast-Listen+Unicast transport mode MUST be changed. If the node identifier of the local node is the highest one, the node MUST switch back to, or stay in, Multicast+Unicast mode and form peer relationships with all peers as specified in Section 4.5.

Multicast+Unicastトランスポートモードのあるエンドポイントについて規定された上限を超え、かつノードがリンク上で最も大きいノード識別子を持っていない場合、ノードはそのエンドポイントを、リンク上で検出された最も大きいノード識別子を持つノードに接続されたユニキャストエンドポイントとして扱い、それによってMulticast-listen+Unicastトランスポートモードに移行すべきです（SHOULD）。特定のエンドポイントの振る舞いへの影響については、セクション4.2を参照してください。Multicast-listen+Unicastトランスポートモードのノードは、まだMulticast+Unicastモードにあるノードからのメッセージを受信することと、より大きいノード識別子を持つノードの出現に対応することの両方のために、マルチキャストトラフィックを受信し続けなければなりません（MUST）。リンク上に存在する最も大きいノード識別子が変化した場合、Multicast-Listen+Unicastトランスポートモードのエンドポイントのリモートのユニキャストアドレスを変更しなければなりません（MUST）。ローカルノードのノード識別子が最も大きい場合、ノードはMulticast+Unicastモードに戻るか、またはそのモードにとどまり、セクション4.5で規定するようにすべてのピアとピア関係を形成しなければなりません（MUST）。

8. Security and Trust Management

If specified in the DNCP profile, either DTLS [RFC6347] or TLS [RFC5246] may be used to authenticate and encrypt either some (if specified optional in the profile) or all unicast traffic. The following methods for establishing trust are defined, but it is up to the DNCP profile to specify which ones may, should, or must be supported.

DNCPプロファイルで規定されている場合、DTLS[RFC6347]またはTLS[RFC5246]を使用して、ユニキャストトラフィックの一部（プロファイルで任意と規定されている場合）またはすべてを認証および暗号化できます。信頼を確立するための以下の方法が定義されていますが、どれをサポートしてもよいか、すべきか、しなければならないかを規定するのはDNCPプロファイルです。

8.1. Trust Method Based on Pre-Shared Key

8.1. 事前共有鍵に基づく信頼方式

A trust model based on Pre-Shared Key (PSK) is a simple security management mechanism that allows an administrator to deploy devices to an existing network by configuring them with a predefined key, similar to the configuration of an administrator password or Wi-Fi Protected Access (WPA) key. Although limited in nature, it is useful to provide a user-friendly security mechanism for smaller networks.

事前共有鍵（Pre-Shared Key: PSK）に基づく信頼モデルは、管理者パスワードやWi-Fi Protected Access（WPA）鍵の設定と同様に、あらかじめ定義された鍵を機器に設定することで、管理者が既存のネットワークに機器を展開できるようにする、単純なセキュリティー管理メカニズムです。本質的に限定的ではありますが、小規模なネットワーク向けに使いやすいセキュリティーメカニズムを提供するのに役立ちます。

8.2. PKI-Based Trust Method

8.2. PKIベースの信頼方式

A PKI-based trust model enables more advanced management capabilities at the cost of increased complexity and bootstrapping effort. However, it allows trust to be managed in a centralized manner and is therefore useful for larger networks with a need for an authoritative trust management.

PKIベースの信頼モデルは、複雑さとブートストラップの手間が増える代わりに、より高度な管理能力を実現します。しかし、信頼を集中的に管理できるため、権威ある信頼管理を必要とする大規模なネットワークに役立ちます。

8.3. Certificate-Based Trust Consensus Method

8.3. 証明書ベースの信頼コンセンサス方式

For some scenarios -- such as bootstrapping a mostly unmanaged network -- the methods described above may not provide a desirable trade-off between security and user experience. This section includes guidance for implementing an opportunistic security [RFC7435] method that DNCP profiles can build upon and adapt for their specific requirements.

一部のシナリオ（ほとんど管理されていないネットワークのブートストラップなど）では、上記の方法では、セキュリティーとユーザー体験の間の望ましいトレードオフが得られない場合があります。このセクションには、DNCPプロファイルがその上に構築し、それぞれの要件に合わせて適応させることができる、日和見的セキュリティー（opportunistic security）[RFC7435]の方式を実装するためのガイダンスが含まれます。

The certificate-based consensus model is designed to be a compromise between trust management effort and flexibility. It is based on X.509 certificates and allows each DNCP node to provide a trust verdict on any other certificate, and a consensus is found to determine whether a node using this certificate or any certificate signed by it is to be trusted.

証明書ベースのコンセンサスモデルは、信頼管理の手間と柔軟性との間の妥協点となるように設計されています。これはX.509証明書に基づいており、各DNCPノードが他の任意の証明書について信頼判定を提供できるようにし、この証明書またはそれによって署名された任意の証明書を使用するノードを信頼すべきかどうかを決定するためのコンセンサスが得られます。

A DNCP node not using this security method MUST ignore all announced trust verdicts and MUST NOT announce any such verdicts by itself, i.e., any other normative language in this subsection does not apply to it.

このセキュリティー方式を使用しないDNCPノードは、告知されたすべての信頼判定を無視しなければなりません（MUST）。また、自らそのような判定を告知してはなりません（MUST NOT）。つまり、このサブセクションのその他の規範的な記述は、そのノードには適用されません。

The current effective trust verdict for any certificate is defined as the one with the highest priority from all trust verdicts announced for said certificate at the time.

任意の証明書についての現在の実効信頼判定は、その時点でその証明書について告知されているすべての信頼判定のうち、最も優先度の高いものとして定義されます。

8.3.1. Trust Verdicts

8.3.1. 信頼判定

Trust verdicts are statements of DNCP nodes about the trustworthiness of X.509 certificates. There are 5 possible trust verdicts in order of ascending priority:

信頼判定は、X.509証明書の信頼性に関するDNCPノードの表明です。信頼判定には、優先度の低い順に次の5つがあります。

0 (Neutral):
no trust verdict exists, but the DNCP network should determine one.
1 (Cached Trust):
the last known effective trust verdict was Configured or Cached Trust.
2 (Cached Distrust):
the last known effective trust verdict was Configured or Cached Distrust.
3 (Configured Trust):
trustworthy based upon an external ceremony or configuration.
4 (Configured Distrust):
not trustworthy based upon an external ceremony or configuration.
0（Neutral）：
信頼判定は存在しませんが、DNCPネットワークが判定を決定すべきです。
1（Cached Trust）：
最後に知られている実効信頼判定は、Configured TrustまたはCached Trustでした。
2（Cached Distrust）：
最後に知られている実効信頼判定は、Configured DistrustまたはCached Distrustでした。
3（Configured Trust）：
外部のセレモニーまたは設定に基づき、信頼できます。
4（Configured Distrust）：
外部のセレモニーまたは設定に基づき、信頼できません。

Trust verdicts are differentiated in 3 groups:

信頼判定は、3つのグループに区別されます。

  • Configured verdicts are used to announce explicit trust verdicts a node has based on any external trust bootstrap or predefined relations a node has formed with a given certificate.
  • Cached verdicts are used to retain the last known trust state in case all nodes with configured verdicts about a given certificate have been disconnected or turned off.
  • The Neutral verdict is used to announce a new node intending to join the network, so a final verdict for it can be found.
  • 設定済み（Configured）判定は、外部での信頼のブートストラップや、ノードが特定の証明書との間で形成したあらかじめ定義された関係に基づいて、ノードが持つ明示的な信頼判定を告知するために使用されます。
  • キャッシュ済み（Cached）判定は、特定の証明書について設定済み判定を持つすべてのノードが切断されたり電源を切られたりした場合に備えて、最後に知られている信頼状態を保持するために使用されます。
  • Neutral判定は、ネットワークへの参加を意図している新しいノードを告知し、そのノードについての最終的な判定を見つけられるようにするために使用されます。

The current effective trust verdict for any certificate is defined as the one with the highest priority within the set of trust verdicts announced for the certificate in the DNCP network. A node MUST be trusted for participating in the DNCP network if and only if the current effective trust verdict for its own certificate or any one in its certificate hierarchy is (Cached or Configured) Trust, and none of the certificates in its hierarchy have an effective trust verdict of (Cached or Configured) Distrust. In case a node has a configured verdict, which is different from the current effective trust verdict for a certificate, the current effective trust verdict takes precedence in deciding trustworthiness. Despite that, the node still retains and announces its configured verdict.

任意の証明書についての現在の実効信頼判定は、DNCPネットワーク内でその証明書について告知された信頼判定の集合の中で、最も優先度の高いものとして定義されます。ノードは、自身の証明書またはその証明書階層内のいずれかの証明書についての現在の実効信頼判定が（CachedまたはConfiguredの）Trustであり、かつその階層内のどの証明書も（CachedまたはConfiguredの）Distrustの実効信頼判定を持たない場合に限り、DNCPネットワークへの参加について信頼されなければなりません（MUST）。ノードが、ある証明書について現在の実効信頼判定とは異なる設定済み判定を持っている場合、信頼性の判断においては現在の実効信頼判定が優先されます。それでも、ノードは自身の設定済み判定を保持し、告知し続けます。

8.3.2. Trust Cache

8.3.2. 信頼キャッシュ

Each node SHOULD maintain a trust cache containing the current effective trust verdicts for all certificates currently announced in the DNCP network. This cache is used as a backup of the last known state in case there is no node announcing a configured verdict for a known certificate. It SHOULD be saved to a non-volatile memory at reasonable time intervals to survive a reboot or power outage.

各ノードは、DNCPネットワーク内で現在告知されているすべての証明書についての現在の実効信頼判定を含む、信頼キャッシュを維持すべきです（SHOULD）。このキャッシュは、既知の証明書について設定済み判定を告知しているノードが存在しない場合に備えた、最後に知られている状態のバックアップとして使用されます。再起動や停電を乗り越えるために、適切な時間間隔で不揮発性メモリーに保存すべきです（SHOULD）。

Every time a node (re)joins the network or detects the change of an effective trust verdict for any certificate, it will synchronize its cache, i.e., store new effective trust verdicts overwriting any previously cached verdicts. Configured verdicts are stored in the cache as their respective cached counterparts. Neutral verdicts are never stored and do not override existing cached verdicts.

ノードがネットワークに（再）参加するたび、または任意の証明書についての実効信頼判定の変化を検出するたびに、ノードはキャッシュを同期します。つまり、新しい実効信頼判定を保存し、以前にキャッシュされた判定を上書きします。設定済み判定は、それぞれに対応するキャッシュ済み判定としてキャッシュに保存されます。Neutral判定は決して保存されず、既存のキャッシュ済み判定を上書きしません。

8.3.3. Announcement of Verdicts

8.3.3. 判定の告知

A node SHOULD always announce any configured verdicts it has established by itself, and it MUST do so if announcing the configured verdict leads to a change in the current effective trust verdict for the respective certificate. In absence of configured verdicts, it MUST announce Cached Trust verdicts it has stored in its trust cache, if one of the following conditions applies:

ノードは、自ら確立した設定済み判定を常に告知すべきです（SHOULD）。また、設定済み判定を告知することで、それぞれの証明書についての現在の実効信頼判定が変化する場合は、告知しなければなりません（MUST）。設定済み判定がない場合、次の条件のいずれかに当てはまるならば、ノードは信頼キャッシュに保存しているCached Trust判定を告知しなければなりません（MUST）。

  • The stored trust verdict is Cached Trust, and the current effective trust verdict for the certificate is Neutral or does not exist.
  • The stored trust verdict is Cached Distrust, and the current effective trust verdict for the certificate is Cached Trust.
  • 保存されている信頼判定がCached Trustであり、その証明書についての現在の実効信頼判定がNeutralであるか、存在しない。
  • 保存されている信頼判定がCached Distrustであり、その証明書についての現在の実効信頼判定がCached Trustである。

A node rechecks these conditions whenever it detects changes of announced trust verdicts anywhere in the network.

ノードは、ネットワーク内のどこかで告知された信頼判定の変化を検出するたびに、これらの条件を再確認します。

Upon encountering a node with a hierarchy of certificates for which there is no effective trust verdict, a node adds a Neutral Trust-Verdict TLV to its node data for all certificates found in the hierarchy and publishes it until an effective trust verdict different from Neutral can be found for any of the certificates, or a reasonable amount of time (10 minutes is suggested) with no reaction and no further authentication attempts has passed. Such trust verdicts SHOULD also be limited in rate and number to prevent denial-of-service attacks.

実効信頼判定が存在しない証明書の階層を持つノードに遭遇した場合、ノードは、その階層内で見つかったすべての証明書について、NeutralのTrust-Verdict TLVを自身のノードデータに追加し、いずれかの証明書についてNeutral以外の実効信頼判定が見つかるまで、または反応もそれ以上の認証の試行もないまま妥当な時間（10分を推奨します）が経過するまで、それを公開します。サービス拒否攻撃を防ぐために、このような信頼判定はレートと数も制限すべきです（SHOULD）。

8.3.4. Bootstrap Ceremonies

8.3.4. ブートストラップセレモニー

The following non-exhaustive list of methods describes possible ways to establish trust relationships between DNCP nodes and node certificates. Trust establishment is a two-way process in which the existing network must trust the newly added node, and the newly added node must trust at least one of its peer nodes. It is therefore necessary that both the newly added node and an already trusted node perform such a ceremony to successfully introduce a node into the DNCP network. In all cases, an administrator MUST be provided with external means to identify the node belonging to a certificate based on its fingerprint and a meaningful common name.

以下の網羅的ではない方法の一覧は、DNCPノードとノードの証明書の間に信頼関係を確立するための可能な方法を説明するものです。信頼の確立は双方向のプロセスであり、既存のネットワークが新たに追加されたノードを信頼する必要があり、新たに追加されたノードがそのピアノードの少なくとも1つを信頼する必要があります。したがって、ノードをDNCPネットワークにうまく導入するには、新たに追加されたノードと、すでに信頼されているノードの両方がそのようなセレモニーを実行する必要があります。いずれの場合も、管理者には、フィンガープリントと意味のあるコモンネームに基づいて、証明書がどのノードに属するかを識別する外部の手段を提供しなければなりません（MUST）。

8.3.4.1. Trust by Identification
8.3.4.1. 識別による信頼

A node implementing certificate-based trust MUST provide an interface to retrieve the current set of effective trust verdicts, fingerprints, and names of all certificates currently known and set configured verdicts to be announced. Alternatively, it MAY provide a companion DNCP node or application with these capabilities with which it has a pre-established trust relationship.

証明書ベースの信頼を実装するノードは、現在知られているすべての証明書についての実効信頼判定、フィンガープリント、名前の現在の集合を取得し、告知する設定済み判定を設定するためのインターフェイスを提供しなければなりません（MUST）。代わりに、事前に信頼関係を確立している、これらの能力を持つ補助的なDNCPノードやアプリケーションを提供してもよいです（MAY）。

8.3.4.2. Preconfigured Trust
8.3.4.2. 事前設定による信頼

A node MAY be preconfigured to trust a certain set of node or CA certificates. However, such trust relationships MUST NOT result in unwanted or unrelated trust for nodes not intended to be run inside the same network (e.g., all other devices by the same manufacturer).

ノードは、特定のノード証明書またはCA証明書の集合を信頼するように事前に設定されてもよいです（MAY）。ただし、そのような信頼関係によって、同じネットワーク内で実行することを意図していないノード（たとえば、同じ製造元の他のすべての機器）に対する、望まない、または無関係な信頼が生じてはなりません（MUST NOT）。

8.3.4.3. Trust on Button Press
8.3.4.3. ボタン押下による信頼

A node MAY provide a physical or virtual interface to put one or more of its internal network interfaces temporarily into a mode in which it trusts the certificate of the first DNCP node it can successfully establish a connection with.

ノードは、1つ以上の内部ネットワークインターフェイスを、コネクションを正常に確立できた最初のDNCPノードの証明書を信頼するモードに一時的にするための、物理的または仮想的なインターフェイスを提供してもよいです（MAY）。

8.3.4.4. Trust on First Use
8.3.4.4. 初回使用時の信頼

A node that is not associated with any other DNCP node MAY trust the certificate of the first DNCP node it can successfully establish a connection with. This method MUST NOT be used when the node has already associated with any other DNCP node.

他のどのDNCPノードとも関連付けられていないノードは、コネクションを正常に確立できた最初のDNCPノードの証明書を信頼してもよいです（MAY）。ノードがすでに他のDNCPノードと関連付けられている場合、この方法を使用してはなりません（MUST NOT）。

9. DNCP Profile-Specific Definitions

9. DNCPプロファイル固有の定義

Each DNCP profile MUST specify the following aspects:

各DNCPプロファイルは、次の事項を規定しなければなりません（MUST）。

  • Unicast and optionally a multicast transport protocol(s) to be used. If a multicast-based node and status discovery is desired, a datagram-based transport supporting multicast has to be available.
  • How the chosen transport(s) is secured: Not at all, optionally, or always with the TLS scheme defined here using one or more of the methods, or with something else. If the links with DNCP nodes can be sufficiently secured or isolated, it is possible to run DNCP in a secure manner without using any form of authentication or encryption.
  • Transport protocols' parameters such as port numbers to be used or multicast addresses to be used. Unicast, multicast, and secure unicast may each require different parameters, if applicable.

  • When receiving TLVs, what sort of TLVs are ignored in addition -- as specified in Section 4.4 -- e.g., for security reasons. While the security of the node data published within the Node State TLVs is already ensured by the base specification (if secure unicast transport is used, Node State TLVs are sent only via unicast as multicast ones are ignored on receipt), if a profile adds TLVs that are sent outside the node data, a profile should indicate whether or not those TLVs should be ignored if they are received via multicast or non-secured unicast. A DNCP profile may define the following DNCP TLVs to be safely ignored:

    • Anything received over multicast, except Node Endpoint TLV (Section 7.2.1) and Network State TLV (Section 7.2.2).
    • Any TLVs received over unreliable unicast or multicast at a rate that is that is too high; Trickle will ensure eventual convergence given the rate slows down at some point.
  • How to deal with node identifier collision as described in Section 4.4. Main options are either for one or both nodes to assign new node identifiers to themselves or to notify someone about a fatal error condition in the DNCP network.
  • Imin, Imax, and k ranges to be suggested for implementations to be used in the Trickle algorithm. The Trickle algorithm does not require these to be the same across all implementations for it to work, but similar orders of magnitude help implementations of a DNCP profile to behave more consistently and to facilitate estimation of lower and upper bounds for convergence behavior of the network.
  • Hash function H(x) to be used, and how many bits of the output are actually used. The chosen hash function is used to handle both hashing of node data and producing network state hash, which is a hash of node data hashes. SHA-256 defined in [RFC6234] is the recommended default choice, but a non-cryptographic hash function could be used as well. If there is a hash collision in the network state hash, the network will effectively be partitioned to partitions that believe they are up to date but are actually no longer converged. The network will converge either when some node data anywhere in the network changes or when conflicting Node State TLVs get transmitted across the partition (either caused by "Trickle-Driven Status Updates" (Section 4.3) or as part of the "Processing of Received TLVs" (Section 4.4)). If a node publishes node data with a hash that collides with any previously published node data, the update may not be (fully) propagated, and the old version of node data may be used instead.
  • DNCP_NODE_IDENTIFIER_LENGTH: The fixed length of a node identifier (in bytes).

  • Whether to send keep-alives, and if so, whether it is per-endpoint (requires multicast transport) or per-peer. Keep-alive also has associated parameters:

    • DNCP_KEEPALIVE_INTERVAL: How often keep-alives are to be sent by default (if enabled).
    • DNCP_KEEPALIVE_MULTIPLIER: How many times the DNCP_KEEPALIVE_INTERVAL (or peer-supplied keep-alive interval value) node may not be heard from to be considered still valid. This is just a default used in absence of any other configuration information or particular per-endpoint configuration.
  • Whether to support dense multicast-enabled link optimization (Section 6.2) or not.
  • 使用するユニキャストトランスポートプロトコルと、任意でマルチキャストトランスポートプロトコル。マルチキャストベースのノードおよびステータスの発見が望まれる場合は、マルチキャストをサポートするデータグラムベースのトランスポートが利用可能である必要があります。
  • 選択したトランスポートをどのように保護するか：まったく保護しない、任意で保護する、ここで定義するTLS方式で1つ以上の方法を使用して常に保護する、またはその他の何かで保護する。DNCPノードのあるリンクを十分に保護または隔離できる場合は、いかなる形式の認証や暗号化も使用せずに、安全な方法でDNCPを実行できます。
  • 使用するポート番号や使用するマルチキャストアドレスなどの、トランスポートプロトコルのパラメーター。該当する場合、ユニキャスト、マルチキャスト、安全なユニキャストはそれぞれ異なるパラメーターを必要とする場合があります。

  • TLVを受信する際、たとえばセキュリティー上の理由から、セクション4.4で規定するものに加えてどのような種類のTLVを無視するか。Node State TLV内で公開されるノードデータのセキュリティーは、基本仕様によってすでに確保されています（安全なユニキャストトランスポートを使用する場合、マルチキャストのNode State TLVは受信時に無視されるため、Node State TLVはユニキャストでのみ送信されます）が、プロファイルがノードデータの外で送信されるTLVを追加する場合、プロファイルは、それらのTLVをマルチキャストや保護されていないユニキャストで受信した場合に無視すべきかどうかを示すべきです。DNCPプロファイルでは、次のDNCP TLVを安全に無視してよいと定義できます。

    • Node Endpoint TLV（セクション7.2.1）とNetwork State TLV（セクション7.2.2）を除く、マルチキャストで受信したすべてのもの。
    • 信頼性のないユニキャストまたはマルチキャストで、高すぎるレートで受信したすべてのTLV。レートがいずれ低下すれば、Trickleが最終的な収束を保証します。
  • セクション4.4で説明する、ノード識別子の衝突への対処方法。主な選択肢は、一方または両方のノードが自身に新しいノード識別子を割り当てるか、DNCPネットワーク内の致命的なエラー状態について誰かに通知するかのいずれかです。
  • Trickleアルゴリズムで使用するよう実装に提案する、Imin、Imax、kの範囲。Trickleアルゴリズムが機能するために、これらがすべての実装で同じである必要はありませんが、同程度の桁数にしておくと、DNCPプロファイルの実装がより一貫して振る舞い、ネットワークの収束の振る舞いの下限と上限を見積もりやすくなります。
  • 使用するハッシュ関数H(x)と、出力のうち実際に使用するビット数。選択したハッシュ関数は、ノードデータのハッシュ化と、ノードデータハッシュのハッシュであるネットワーク状態ハッシュの生成の両方に使用されます。[RFC6234]で定義されたSHA-256が推奨されるデフォルトの選択ですが、暗号学的でないハッシュ関数を使用することもできます。ネットワーク状態ハッシュでハッシュの衝突が発生した場合、ネットワークは事実上、自身は最新であると信じているが実際にはもはや収束していないパーティションに分断されます。ネットワークは、ネットワーク内のどこかでノードデータが変更されたとき、または（「Trickle駆動のステータス更新」（セクション4.3）によって、または「受信したTLVの処理」（セクション4.4）の一部として）矛盾するNode State TLVがパーティションをまたいで送信されたときに収束します。ノードが、以前に公開されたノードデータと衝突するハッシュを持つノードデータを公開した場合、その更新は（完全には）伝播されず、代わりに古いバージョンのノードデータが使用される可能性があります。
  • DNCP_NODE_IDENTIFIER_LENGTH：ノード識別子の固定長（バイト単位）。

  • キープアライブを送信するかどうか、送信する場合はエンドポイントごと（マルチキャストトランスポートが必要）かピアごとか。キープアライブには、関連するパラメーターもあります。

    • DNCP_KEEPALIVE_INTERVAL：（有効な場合に）デフォルトでキープアライブを送信する頻度。
    • DNCP_KEEPALIVE_MULTIPLIER：DNCP_KEEPALIVE_INTERVAL（またはピアが提供したキープアライブ間隔の値）の何倍の間、ノードから応答がなくても、まだ有効とみなすか。これは、他の設定情報や、エンドポイントごとの特定の設定がない場合に使用されるデフォルトにすぎません。
  • 密なマルチキャスト対応リンクの最適化（セクション6.2）をサポートするかどうか。

For some guidance on choosing transport and security options, please see Appendix B.

トランスポートとセキュリティーの選択肢の選び方に関するガイダンスについては、付録Bを参照してください。

10. Security Considerations

10. セキュリティーに関する考慮事項

DNCP-based protocols may use multicast to indicate DNCP state changes and for keep-alive purposes. However, no actual published data TLVs will be sent across that channel. Therefore, an attacker may only learn hash values of the state within DNCP and may be able to trigger unicast synchronization attempts between nodes on a local link this way. A DNCP node MUST therefore rate limit its reactions to multicast packets.

DNCPベースのプロトコルは、DNCPの状態変化を示すためと、キープアライブの目的で、マルチキャストを使用する場合があります。ただし、実際に公開されるデータのTLVがそのチャネルを通じて送信されることはありません。したがって、攻撃者が知ることができるのはDNCP内の状態のハッシュ値だけであり、この方法で、ローカルリンク上のノード間のユニキャスト同期の試行を引き起こせる可能性があるにすぎません。したがって、DNCPノードは、マルチキャストパケットへの反応をレート制限しなければなりません（MUST）。

When using DNCP to bootstrap a network, PKI-based solutions may have issues when validating certificates due to potentially unavailable accurate time or due to the inability to use the network to either check Certificate Revocation Lists or perform online validation.

DNCPを使用してネットワークをブートストラップする場合、PKIベースのソリューションでは、正確な時刻が利用できない可能性や、ネットワークを使用して証明書失効リストを確認したりオンラインでの検証を実行したりできないことから、証明書の検証時に問題が発生する可能性があります。

The Certificate-based trust consensus mechanism defined in this document allows for a consenting revocation; however, in case of a compromised device, the trust cache may be poisoned before the actual revocation happens allowing the distrusted device to rejoin the network using a different identity. Stopping such an attack might require physical intervention and flushing of the trust caches.

この文書で定義する証明書ベースの信頼コンセンサスメカニズムは、合意に基づく失効を可能にします。しかし、機器が侵害された場合、実際の失効が行われる前に信頼キャッシュが汚染され、信頼されなくなった機器が別のアイデンティティーを使用してネットワークに再参加できてしまう可能性があります。このような攻撃を止めるには、物理的な介入と信頼キャッシュのフラッシュが必要になるかもしれません。

Appendix A. Alternative Modes of Operation

付録A. 代替の動作モード

Beyond what is described in the main text, the protocol allows for other uses. These are provided as examples.

本文で説明したもの以外にも、このプロトコルは他の用途を可能にします。ここでは、それらを例として示します。

A.1. Read-Only Operation

A.1. 読み取り専用の動作

If a node uses just a single endpoint and does not need to publish any TLVs, full DNCP node functionality is not required. Such a limited node can acquire and maintain a view of the TLV space by implementing the processing logic as specified in Section 4.4. Such node would not need Trickle, peer-maintenance, or even keep-alives at all, as the DNCP nodes' use of it would guarantee eventual receipt of network state hashes, and synchronization of node data, even in the presence of unreliable transport.

ノードが単一のエンドポイントだけを使用し、TLVを公開する必要がない場合、完全なDNCPノードの機能は必要ありません。このような限定されたノードは、セクション4.4で規定する処理ロジックを実装することで、TLV空間のビューを取得し維持できます。このようなノードは、Trickle、ピアの維持、さらにはキープアライブもまったく必要としません。なぜなら、DNCPノードがそれを使用することで、信頼性のないトランスポートが存在する場合でも、ネットワーク状態ハッシュを最終的に受信し、ノードデータを同期することが保証されるからです。

A.2. Forwarding Operation

A.2. 転送の動作

If a node with a pair of endpoints does not need to publish any TLVs, it can detect (for example) nodes with the highest node identifier on each of the endpoints (if any). Any TLVs received from one of them would be forwarded verbatim as unicast to the other node with the highest node identifier.

エンドポイントのペアを持つノードがTLVを公開する必要がない場合、そのノードは（たとえば）各エンドポイント上で最も大きいノード識別子を持つノードを（存在すれば）検出できます。それらの一方から受信したTLVは、最も大きいノード識別子を持つもう一方のノードに、ユニキャストでそのまま転送されます。

Any tinkering with the TLVs would remove guarantees of this scheme working; however, passive monitoring would obviously be fine. This type of simple forwarding cannot be chained, as it does not send anything proactively.

TLVに少しでも手を加えると、この方式が機能する保証はなくなりますが、受動的な監視であれば明らかに問題ありません。この種の単純な転送は、自発的には何も送信しないため、連鎖させることはできません。

Appendix B. DNCP Profile Additional Guidance

付録B. DNCPプロファイルに関する追加のガイダンス

This appendix explains implications of design choices made when specifying the DNCP profile to use particular transport or security options.

この付録では、特定のトランスポートやセキュリティーの選択肢を使用するようにDNCPプロファイルを規定する際の、設計上の選択の影響について説明します。

B.1. Unicast Transport -- UDP or TCP?

B.1. ユニキャストトランスポート：UDPかTCPか

The node data published by a DNCP node is limited to 64 KB due to the 16-bit size of the length field of the TLV it is published within. Some transport choices may decrease this limit; if using, e.g., UDP datagrams for unicast transport, the upper bound of the node data size is whatever the nodes and the underlying network can pass to each other as DNCP does not define its own fragmentation scheme. A profile that chooses UDP has to be limited to small node data (e.g., somewhat smaller than IPv6 default MTU if using IPv6) or specify a minimum that all nodes have to support. Even then, if using non-link-local communications, there is some concern about what middleboxes do to fragmented packets. Therefore, the use of stream transport such as TCP is probably a good idea if either non-link-local communication is desired or fragmentation is expected to cause problems.

DNCPノードが公開するノードデータは、それを公開するTLVの長さフィールドが16ビットであるため、64KBに制限されます。トランスポートの選択によっては、この制限がさらに小さくなる場合があります。たとえば、ユニキャストトランスポートにUDPデータグラムを使用する場合、DNCPは独自の断片化の方式を定義していないため、ノードデータのサイズの上限は、ノードと下位のネットワークが互いに受け渡せるサイズになります。UDPを選択するプロファイルは、小さなノードデータ（たとえば、IPv6を使用する場合はIPv6のデフォルトMTUよりいくらか小さいサイズ）に制限するか、すべてのノードがサポートしなければならない最小値を規定する必要があります。それでも、リンクローカル以外の通信を使用する場合は、断片化されたパケットをミドルボックスがどう扱うかについていくらかの懸念があります。したがって、リンクローカル以外の通信が望まれる場合や、断片化が問題を引き起こすと予想される場合は、TCPのようなストリームトランスポートを使用するのがおそらく良い考えです。

TCP also provides some other facilities, such as a relatively long built-in keep-alive, which in conjunction with connection closes occurring from eventual failed retransmissions may be sufficient to avoid the use of in-protocol keep-alive defined in Section 6.1. Additionally, it is reliable, so there is no need for Trickle on such unicast connections.

TCPは、比較的長い組み込みのキープアライブなど、他の機能も提供します。これは、最終的に再送が失敗したことによって発生するコネクションのクローズと組み合わせることで、セクション6.1で定義するプロトコル内のキープアライブを使用しなくて済むのに十分な場合があります。さらに、TCPは信頼性があるため、そのようなユニキャストコネクションではTrickleは必要ありません。

The major downside of using TCP instead of UDP with DNCP-based profiles lies in the loss of control over the time at which TLVs are received; while unreliable UDP datagrams also have some delay, TLVs within reliable stream transport may be delayed significantly due to retransmissions. This is not a problem if no relative time-dependent information is stored within the TLVs in the DNCP-based protocol; for such a protocol, TCP is a reasonable choice for unicast transport if it is available.

DNCPベースのプロファイルでUDPの代わりにTCPを使用することの主な欠点は、TLVを受信する時刻を制御できなくなることです。信頼性のないUDPデータグラムにもある程度の遅延はありますが、信頼性のあるストリームトランスポート内のTLVは、再送によって大幅に遅延する可能性があります。DNCPベースのプロトコルで、相対的な時間に依存する情報をTLV内に格納しないのであれば、これは問題になりません。そのようなプロトコルでは、TCPが利用可能であれば、TCPはユニキャストトランスポートとして妥当な選択です。

B.2. (Optional) Multicast Transport

B.2. （任意）マルチキャストトランスポート

Multicast is needed for dynamic peer discovery and to trigger unicast exchanges; for that, unreliable datagram transport (=typically UDP) is the only transport option defined within this specification, although DNCP-based protocols may themselves define some other transport or peer discovery mechanism (e.g., based on Multicast DNS (mDNS) or DNS).

マルチキャストは、動的なピア発見とユニキャスト交換の開始のために必要です。そのために、この仕様で定義されている唯一のトランスポートの選択肢は、信頼性のないデータグラムトランスポート（=通常はUDP）です。ただし、DNCPベースのプロトコルは、それ自体で他のトランスポートやピア発見のメカニズム（たとえば、マルチキャストDNS（mDNS）やDNSに基づくもの）を定義できます。

If multicast is used, a well-known address should be specified and for, e.g., IPv6, respectively, the desired address scopes. In most cases, link-local and possibly site-local are useful scopes.

マルチキャストを使用する場合は、ウェルノウンアドレスと、たとえばIPv6の場合はそれぞれ望ましいアドレススコープを規定すべきです。ほとんどの場合、リンクローカルと、場合によってはサイトローカルが有用なスコープです。

B.3. (Optional) Transport Security

B.3. （任意）トランスポートセキュリティー

In terms of provided security, DTLS and TLS are equivalent; they also consume a similar amount of state on the devices. While TLS is on top of a stream protocol, using DTLS also requires relatively long session caching within the DTLS layer to avoid expensive reauthentication/authorization steps if and when any state within the DNCP network changes or per-peer keep-alive (if enabled) is sent.

提供されるセキュリティーの点では、DTLSとTLSは同等です。また、機器上で消費する状態の量も同程度です。TLSはストリームプロトコルの上で動作しますが、DTLSを使用する場合も、DNCPネットワーク内の何らかの状態が変化したときや、ピアごとのキープアライブを（有効な場合に）送信するときに、コストの高い再認証・再認可の手順を避けるために、DTLS層内で比較的長いセッションキャッシュが必要になります。

TLS implementations (at the time of writing the specification) seem more mature and available (as open source) than DTLS ones. This may be due to a long history of use with HTTPS.

（この仕様の執筆時点では）TLSの実装はDTLSの実装よりも成熟しており、（オープンソースとして）入手しやすいようです。これは、HTTPSで長く使用されてきた歴史によるものかもしれません。

Some libraries seem not to support multiplexing between insecure and secure communication on the same port, so specifying distinct ports for secured and unsecured communication may be beneficial.

一部のライブラリーは、同じポート上での安全でない通信と安全な通信の多重化をサポートしていないようなので、保護された通信と保護されていない通信に別々のポートを規定すると有益な場合があります。

Appendix C. Example Profile

付録C. プロファイルの例

This is the DNCP profile of SHSP, an experimental (and for the purposes of this document fictional) home automation protocol. The protocol itself is used to make a key-value store published by each of the nodes available to all other nodes for distributed monitoring and control of a home infrastructure. It defines only one additional TLV type: a key=value TLV that contains a single key=value assignment for publication.

これは、実験的な（そしてこの文書の目的のための架空の）ホームオートメーションプロトコルであるSHSPのDNCPプロファイルです。このプロトコル自体は、家庭のインフラストラクチャーを分散して監視および制御するために、各ノードが公開するキーバリューストアを他のすべてのノードから利用できるようにするために使用されます。追加のTLVタイプは1つだけ定義されています。それは、公開のための単一のkey=valueの割り当てを含むkey=value TLVです。

  • Unicast transport: IPv6 TCP on port EXAMPLE-P1 since only absolute timestamps are used within the key=value data and since it focuses primarily on Linux-based nodes that support both protocols as well. Connections from and to non-link-local addresses are ignored to avoid exposing this protocol outside the secure links.
  • Multicast transport: IPv6 UDP on port EXAMPLE-P2 to link-local scoped multicast address ff02:EXAMPLE. At least one node per link in the home is assumed to facilitate node discovery without depending on any other infrastructure.
  • Security: None. It is to be used only on trusted links (WPA2-x wireless, physically secure wired links).
  • Additional TLVs to be ignored: None. No DNCP security is specified, and no new TLVs are defined outside of node data.
  • Node identifier length (DNCP_NODE_IDENTIFIER_LENGTH): 32 bits that are randomly generated.
  • Node identifier collision handling: Pick new random node identifier.
  • Trickle parameters: Imin = 200 ms, Imax = 7, k = 1. It means at least one multicast per link in 25 seconds in stable state (0.2 * 2^7).
  • Hash function H(x) + length: SHA-256, only 128 bits used. It's relatively fast, and 128 bits should be plenty to prevent random conflicts (64 bits would most likely be sufficient, too).
  • No in-protocol keep-alives (Section 6.1); TCP keep-alive is to be used. In practice, TCP keep-alive is seldom encountered anyway, as changes in network state cause packets to be sent on the unicast connections, and those that fail sufficiently many retransmissions are dropped much before the keep-alive actually would fire.
  • No support for dense multicast-enabled link optimization (Section 6.2); SHSP is a simple protocol for a few nodes (network wide, not even to mention on a single link) and therefore would not provide any benefit.
  • ユニキャストトランスポート：ポートEXAMPLE-P1上のIPv6 TCP。key=valueデータ内では絶対タイムスタンプのみを使用しており、また主に両方のプロトコルをサポートするLinuxベースのノードを対象としているためです。このプロトコルが安全なリンクの外に露出するのを避けるために、リンクローカル以外のアドレスとの間のコネクションは無視されます。
  • マルチキャストトランスポート：リンクローカルスコープのマルチキャストアドレスff02:EXAMPLEへの、ポートEXAMPLE-P2上のIPv6 UDP。他のいかなる基盤にも依存せずにノード発見を容易にするために、家庭内のリンクごとに少なくとも1つのノードがあることを前提とします。
  • セキュリティー：なし。信頼できるリンク（WPA2-xの無線、物理的に安全な有線リンク）でのみ使用されます。
  • 追加で無視するTLV：なし。DNCPのセキュリティーは規定されておらず、ノードデータの外では新しいTLVは定義されていません。
  • ノード識別子の長さ（DNCP_NODE_IDENTIFIER_LENGTH）：ランダムに生成される32ビット。
  • ノード識別子の衝突の処理：新しいランダムなノード識別子を選択します。
  • Trickleのパラメーター：Imin = 200 ms、Imax = 7、k = 1。これは、安定状態では、25秒（0.2 * 2^7）にリンクごとに少なくとも1回のマルチキャストがあることを意味します。
  • ハッシュ関数H(x)と長さ：SHA-256で、128ビットのみを使用します。比較的高速であり、128ビットあれば偶発的な衝突を防ぐのに十分なはずです（64ビットでもおそらく十分でしょう）。
  • プロトコル内のキープアライブはなし（セクション6.1）。TCPキープアライブを使用します。実際には、ネットワーク状態の変化によってユニキャストコネクション上でパケットが送信され、十分な回数の再送に失敗したコネクションはキープアライブが実際に発火するよりもずっと前に切断されるため、いずれにしてもTCPキープアライブが発生することはめったにありません。
  • 密なマルチキャスト対応リンクの最適化（セクション6.2）のサポートはなし。SHSPは（単一のリンク上はもちろん、ネットワーク全体でも）少数のノードのための単純なプロトコルであり、したがって何の利点ももたらさないためです。
