Session Initiation Protocol (SIP) Recording Metadata

RFC 7865

セッション開始プロトコル（SIP）の記録メタデータ

Abstract

概要

Session recording is a critical requirement in many communications environments, such as call centers and financial trading organizations. In some of these environments, all calls must be recorded for regulatory, compliance, and consumer protection reasons. The recording of a session is typically performed by sending a copy of a media stream to a recording device. This document describes the metadata model as viewed by the Session Recording Server (SRS) and the recording metadata format.

セッションの記録（session recording）は、コールセンターや金融取引機関など、多くの通信環境において重要な要件です。 こうした環境の一部では、規制、コンプライアンス、消費者保護の理由から、すべての通話を記録しなければなりません。 セッションの記録は、一般にメディアストリームのコピーを記録装置に送ることで行われます。 この文書では、セッション記録サーバー（Session Recording Server: SRS）から見たメタデータモデルと、記録メタデータのフォーマットについて説明します。

1. Introduction

1. はじめに

Session recording is a critical requirement in many communications environments, such as call centers and financial trading organizations. In some of these environments, all calls must be recorded for regulatory, compliance, and consumer protection reasons. The recording of a session is typically performed by sending a copy of a media stream to a recording device. This document focuses on the recording metadata, which describes the Communication Session (CS). The document describes a metadata model as viewed by the Session Recording Server (SRS) and the recording metadata format, the requirements for which are described in [RFC6341] and the architecture for which is described in [RFC7245].

セッションの記録は、コールセンターや金融取引機関など、多くの通信環境において重要な要件です。 こうした環境の一部では、規制、コンプライアンス、消費者保護の理由から、すべての通話を記録しなければなりません。 セッションの記録は、一般にメディアストリームのコピーを記録装置に送ることで行われます。 この文書は、通信セッション（Communication Session: CS）を記述する記録メタデータに焦点を当てます。 この文書では、セッション記録サーバー（Session Recording Server: SRS）から見たメタデータモデルと、記録メタデータのフォーマットについて説明します。 これらの要件は[RFC6341]で、アーキテクチャーは[RFC7245]で説明されています。

3. Definitions

3. 定義

Metadata model:
A metadata model is an abstract representation of metadata using a Unified Modeling Language (UML) [UML] class diagram.
Metadata classes:
Each block in the model represents a class. A class is a construct that is used as a blueprint to create instances (called "objects") of itself. The description of each class also has a representation of its attributes in a second compartment below the class name.
Attributes:
Attributes represent the elements listed in each of the classes. The attributes of a class are listed in the second compartment below the class name. Each instance of a class conveys values for the attributes of that class. These values get added to the recording's metadata.
Linkages:
Linkages represent the relationship between the classes in the model. Each linkage represents a logical connection between classes (or objects) in class diagrams (or object diagrams). The linkages used in the metadata model of this document are associations.
メタデータモデル（Metadata model）:
メタデータモデルは、統一モデリング言語（Unified Modeling Language: UML）[UML]のクラス図を用いたメタデータの抽象的な表現です。
メタデータクラス（Metadata classes）:
モデル内の各ブロックはクラスを表します。 クラスは、自身のインスタンス（「オブジェクト」と呼びます）を作成するための設計図として使われる構成概念です。 各クラスの記述には、クラス名の下の2番目の区画に、その属性の表現もあります。
属性（Attributes）:
属性は、各クラスに列挙された要素を表します。 クラスの属性は、クラス名の下の2番目の区画に列挙されます。 クラスの各インスタンスは、そのクラスの属性の値を伝えます。 これらの値は、記録のメタデータに追加されます。
リンケージ（Linkages）:
リンケージは、モデル内のクラス間の関係を表します。 各リンケージは、クラス図（またはオブジェクト図）におけるクラス（またはオブジェクト）間の論理的なつながりを表します。 この文書のメタデータモデルで使われるリンケージは関連（association）です。

This document also refers to the terminology defined in [RFC6341].

この文書では、[RFC6341]で定義されている用語も参照します。

The metadata model is a class diagram in UML. The model describes the structure of metadata in general by showing the classes, their attributes, and the relationships among the classes. Each block in the model above represents a class. The linkages between the classes represent the relationships, which can be associations or compositions. The model allows metadata describing CSs to be communicated to the SRS as a series of snapshots, each representing the state as seen by a single SRC at a particular instant in time. Metadata changes from one snapshot to another reflect changes in what is being recorded. For example, if a participant joins a conference, then the SRC sends the SRS a snapshot of metadata having that participant information (with attributes like (Name, AoR) tuple and associate-time). (Note: "AoR" means "Address-of-Record".)

Some of the metadata is not required to be conveyed explicitly from the SRC to the SRS, if it can be obtained contextually by the SRS (e.g., from SIP or Session Description Protocol (SDP) signaling). For example, the 'label' attribute within the 'stream' XML element references an SDP "a=label" attribute that identifies an m-line within the Recording Session (RS) SDP. 5. Recording Metadata Format from SRC to SRS

5. SRCからSRSへの記録メタデータのフォーマット

This section gives an overview of the recording metadata format. Some data from the metadata model is assumed to be made available to the SRS through SDP [RFC4566], and therefore this data is not represented in the XML document format specified in this document. SDP attributes describe different media formats like audio and video. The other metadata attributes, such as participant details, are represented in a new recording-specific XML document of type 'application/rs-metadata+xml'. The SDP "label" attribute [RFC4574] provides an identifier by which a metadata XML document can refer to a specific media description in the SDP sent from the SRC to the SRS.

このセクションでは、記録メタデータのフォーマットの概要を説明します。 メタデータモデルのデータの一部は、SDP[RFC4566]を通じてSRSが利用できることを想定しているため、そのデータはこの文書で規定するXML文書フォーマットでは表現しません。 SDP属性は、音声や映像などのさまざまなメディアフォーマットを記述します。 参加者の詳細など、その他のメタデータ属性は、'application/rs-metadata+xml'型の、記録に固有の新しいXML文書で表現します。 SDPの「label」属性[RFC4574]は、SRCからSRSに送られるSDP内の特定のメディア記述をメタデータXML文書が参照するための識別子を提供します。

The XML document format can be used to represent either the complete metadata or a partial update to the metadata. The latter includes only elements that have changed compared to the previously reported metadata.

このXML文書フォーマットは、完全なメタデータ、またはメタデータの部分的な更新のどちらを表現するのにも使用できます。 後者には、以前に報告したメタデータと比べて変化した要素だけを含めます。

5.1. XML Data Format

5.1. XMLデータフォーマット

Every recording metadata XML document sent from the SRC to the SRS contains a 'recording' element. The 'recording' element acts as a container for all other elements in this XML document. A 'recording' object is an XML document. It has the XML declaration and contains an encoding declaration in the XML declaration, e.g., "<?xml version="1.0" encoding="UTF-8"?>". If the charset parameter of the MIME content type declaration is present and it is different from the encoding declaration, the charset parameter takes precedence.

SRCからSRSに送られるすべての記録メタデータXML文書には、'recording'要素が含まれます。 'recording'要素は、このXML文書内のほかのすべての要素のコンテナーとして機能します。 'recording'オブジェクトはXML文書です。 'recording'オブジェクトはXML宣言を持ち、XML宣言の中にエンコーディング宣言（たとえば「<?xml version="1.0" encoding="UTF-8"?>」）を含みます。 MIMEコンテンツタイプ宣言のcharsetパラメーターが存在し、それがエンコーディング宣言と異なる場合は、charsetパラメーターが優先されます。

Every application conforming to this specification MUST accept the UTF-8 character encoding to ensure minimal interoperability.

この仕様に準拠するすべてのアプリケーションは、最低限の相互運用性を確保するために、UTF-8文字エンコーディングを受け入れなければなりません（MUST）。

Syntax and semantic errors in an XML document should be reported to the originator, using application-specific mechanisms.

XML文書内の構文エラーや意味上のエラーは、アプリケーション固有のメカニズムを用いて送信元に報告すべきです。

RSオブジェクトはXMLスキーマでは'recording'要素を使って表現されます。 'recording'要素は、RS要素の属性を提供するために、そのXML文書が関連付けられているSIP/SDPセッションに依存します。

6.1.1. Attributes

6.1.1. 属性

An RS class has the following attributes:

RSクラスには次の属性があります。

  • start-time - Represents the start time of an RS object.
  • end-time - Represents the end time of an RS object.
  • start-time - RSオブジェクトの開始時刻を表します。
  • end-time - RSオブジェクトの終了時刻を表します。

'start-time' and 'end-time' attribute values are derivable from the Date header (if present in the SIP message) in the RS. In cases where the Date header is not present, 'start-time' is derivable from the time at which the SRS receives the notification of the SIP message to set up the RS, and 'end-time' is derivable from the time at which the SRS receives a disconnect on the RS SIP dialog.

'start-time'属性と'end-time'属性の値は、RS内の（SIPメッセージに存在する場合は）Dateヘッダーから導出できます。 Dateヘッダーが存在しない場合、'start-time'はRSを確立するSIPメッセージの通知をSRSが受信した時刻から、'end-time'はRSのSIPダイアログで切断をSRSが受信した時刻から導出できます。

6.1.2. Linkages

6.1.2. リンケージ

Each instance of an RS has:

RSの各インスタンスは次のものを持ちます。

  • Zero or more instances of CS-Groups.
  • Zero or more instances of CS objects.
  • Zero or more instances of MediaStream objects.
  • 0個以上のCSグループ（CS-Group）のインスタンス
  • 0個以上のCSオブジェクトのインスタンス
  • 0個以上のMediaStreamオブジェクトのインスタンス

Zero instances of CSs and CS-Groups in a 'recording' element are allowed to accommodate persistent recording scenarios. A persistent RS is a SIP dialog that is set up between the SRC and the SRS, even before any CS is set up. The metadata sent from the SRC to the SRS when the persistent RS SIP dialog is set up may not have any CS (and the related CS-Group) elements in the XML, as there may not be a session that is associated to the RS yet. For example, a phone acting as an SRC can set up an RS with the SRS, possibly even before the phone is part of a CS. Once the phone joins a CS, the same RS would be used to convey the CS metadata.

永続的な記録のシナリオに対応するため、'recording'要素内のCSとCSグループのインスタンスが0個であることを許容します。 永続的なRSとは、CSが確立される前からSRCとSRSの間に確立されているSIPダイアログです。 永続的なRSのSIPダイアログが確立されたときにSRCからSRSに送られるメタデータには、まだRSに関連付けられたセッションが存在しない可能性があるため、XML内にCS（および関連するCSグループ）の要素がないことがあります。 たとえば、SRCとして動作する電話機は、その電話機がCSに参加する前からでも、SRSとのRSを確立できます。 電話機がCSに参加すると、同じRSを使ってCSのメタデータが伝えられます。

6.2.2. リンケージ

  • There are one or more RS objects per CS-Group.
  • Each CS-Group object has to be associated with one or more RSs. Here, each RS can be set up by the potentially different SRCs.
  • There are one or more CSs per CS-Group (for example, in cases where the call is transferred). A CS cannot be associated with more than one CS-Group.

6.3.1. Attributes

6.3.1. 属性

A CS class has the following attributes:

CSクラスには次の属性があります。

  • session_id - This attribute is used to uniquely identify an instance of a CS object, namely the 'session' XML element within the metadata XML document. 'session_id' is generated using the rules mentioned in Section 6.10.
  • reason - This represents the reason why a CS was terminated. The value for this attribute is derived from the SIP Reason header [RFC3326] of the CS. There MAY be multiple instances of the 'reason' XML element inside a 'session' element. The 'reason' XML element has 'protocol' as an attribute, which indicates the protocol from which the reason string is derived. The default value for the 'protocol' attribute is "SIP". The 'reason' element can be derived from a SIP Reason header in the CS.
  • sipSessionID - This attribute carries a SIP Session-ID as defined in [SessionID]. Each CS object can have zero or more 'sipSessionID' elements. More than one 'sipSessionID' attribute may be present in a CS. For example, if three participants -- A, B, and C -- are in a conference that has a focus acting as an SRC, the metadata sent from the SRC to the SRS will likely have three 'sipSessionID' elements that correspond to the SIP dialogs that the focus has with each of the three participants.
  • group-ref - A 'group-ref' attribute MAY be present to indicate the group (identified by 'group_id') to which the enclosing session belongs.
  • start-time - This optional attribute represents the start time of the CS as seen by the SRC.
  • stop-time - This optional attribute represents the stop time of the CS as seen by the SRC.
  • session_id - この属性は、CSオブジェクトのインスタンス、すなわちメタデータXML文書内の'session' XML要素を一意に識別するために使われます。 'session_id'は、セクション6.10で述べる規則を使って生成されます。
  • reason - CSが終了した理由を表します。 この属性の値は、CSのSIP Reasonヘッダー[RFC3326]から導出されます。 'session'要素の中には、'reason' XML要素の複数のインスタンスが存在してもよいです（MAY）。 'reason' XML要素は属性として'protocol'を持ち、これは理由の文字列の導出元のプロトコルを示します。 'protocol'属性のデフォルト値は「SIP」です。 'reason'要素は、CS内のSIP Reasonヘッダーから導出できます。
  • sipSessionID - この属性は、[SessionID]で定義されているSIPのSession-IDを運びます。 各CSオブジェクトは、0個以上の'sipSessionID'要素を持つことができます。 1つのCSに複数の'sipSessionID'属性が存在することもあります。 たとえば、3人の参加者（A、B、C）が、SRCとして動作するフォーカスを持つ会議に参加している場合、SRCからSRSに送られるメタデータには、フォーカスが3人の参加者それぞれと持つSIPダイアログに対応する3つの'sipSessionID'要素が含まれるでしょう。
  • group-ref - 'group-ref'属性は、それを囲むセッションが属するグループ（'group_id'で識別される）を示すために存在してもよいです（MAY）。
  • start-time - この省略可能な属性は、SRCから見たCSの開始時刻を表します。
  • stop-time - この省略可能な属性は、SRCから見たCSの停止時刻を表します。

This document does not specify attributes relating to what should happen to a recording of a CS after it has been delivered to the SRS (e.g., how long to retain the recording, what access controls to apply). The SRS is assumed to behave in accordance with its local policy. The ability of the SRC to influence this policy is outside the scope of this document. However, if there are implementations where the SRC desires to specify its own policy preferences, this information could be sent as extension data attached to the CS.

この文書では、CSの記録がSRSに配送された後にその記録をどう扱うべきか（たとえば、記録をどれだけの期間保持するか、どのようなアクセス制御を適用するか）に関する属性は規定しません。 SRSは、そのローカルポリシーに従って動作すると想定しています。 SRCがこのポリシーに影響を与える能力は、この文書の範囲外です。 ただし、SRCが独自のポリシーの希望を指定したい実装がある場合、その情報はCSに付加する拡張データとして送ることができます。

6.3.2. Linkages

6.3.2. リンケージ

A CS is linked to the CS-Group, participant, MediaStream (MS), and RS classes by using the association relationship. The association between the CS and the participant allows the following:

CSは、関連の関係を使って、CSグループ、参加者、MediaStream（MS）、RSの各クラスにリンクされます。 CSと参加者の間の関連によって、次のことが可能になります。

  • A CS will have zero or more participants.
  • A participant is associated with zero or more CSs. This includes participants who are not directly part of any CS. An example of such a case is participants in a pre-mixed media stream. The SRC may have knowledge of such participants but not have any signaling relationship with them. This might arise if one participant in a CS is a conference focus. To summarize, even if the SRC does not have direct signaling relationships with all participants in a CS, it should nevertheless create a participant object for each participant that it knows about.
  • The model also allows participants in a CS that are not participants in the media. An example is the identity of a Third Party Call Control (3pcc) that has initiated a CS to two or more participants in the CS. Another example is the identity of a conference focus. Of course, a focus is probably in the media, but since it may only be there as a mixer, it may not report itself as a participant in any of the media streams.
  • CSは0人以上の参加者を持ちます。
  • 参加者は0個以上のCSに関連付けられます。 これには、どのCSにも直接参加していない参加者も含まれます。 そのような例として、事前にミキシングされたメディアストリームの参加者があります。 SRCは、そのような参加者を知っていても、その参加者とのシグナリング関係を持たないことがあります。 これは、CSの参加者の1人が会議のフォーカスである場合に起こり得ます。 まとめると、SRCは、CSのすべての参加者と直接のシグナリング関係を持たない場合でも、自身が知っている各参加者について参加者オブジェクトを作成すべきです。
  • このモデルでは、CSの参加者であってもメディアの参加者ではないものも許容します。 その例として、CSの2人以上の参加者に対してCSを開始したサードパーティー呼制御（Third Party Call Control: 3pcc）の識別情報があります。 別の例として、会議のフォーカスの識別情報があります。 もちろん、フォーカスはおそらくメディアに関与していますが、ミキサーとしてのみ存在する場合もあるため、どのメディアストリームの参加者としても自身を報告しないことがあります。

The association between the CS and the media stream allows the following:

CSとメディアストリームの間の関連によって、次のことが可能になります。

  • A CS will have zero or more streams.
  • A stream can be associated with at most one CS. A stream in a persistent RS is not required to be associated with any CS before the CS is created, and hence the zero association is allowed.
  • CSは0個以上のストリームを持ちます。
  • ストリームは高々1つのCSに関連付けることができます。 永続的なRSにおけるストリームは、CSが作成される前にはどのCSにも関連付けられている必要がないため、関連が0個であることが許容されます。

The association between the CS and the RS allows the following:

CSとRSの間の関連によって、次のことが可能になります。

  • Each instance of an RS has zero or more instances of CS objects.
  • Each CS has to be associated with one or more RSs. Each RS can be potentially set up by different SRCs.
  • RSの各インスタンスは、0個以上のCSオブジェクトのインスタンスを持ちます。
  • 各CSは、1つ以上のRSに関連付けられていなければなりません。 各RSは、異なるSRCによって確立されている可能性があります。

この文書では、参加者に関するその他の属性（たとえば、参加者の役割や参加者の種類）は規定しません。 これらの属性に関する情報を持つSRCは、SRCからSRSへの'participant' XML要素の拡張データの一部として、その情報を提供できます。

  • A participant will receive zero or more media streams.
  • A participant will send zero or more media streams. (The same participant provides multiple streams, e.g., audio and video.)
  • A media stream will be received by zero or more participants. It is possible, though perhaps unlikely, that a stream is generated but sent only to the SRC and SRS, not to any participant -- for example, in conferencing where all participants are on hold and the SRC is collocated with the focus. Also, a media stream may be received by multiple participants (e.g., "whisper" calls, side conversations).
  • A media stream will be sent by one or more participants (pre-mixed streams).
  • 参加者は0個以上のメディアストリームを受信します。
  • 参加者は0個以上のメディアストリームを送信します。 （同じ参加者が、たとえば音声と映像のように、複数のストリームを提供します。）
  • メディアストリームは0人以上の参加者によって受信されます。 可能性は低いかもしれませんが、ストリームが生成されても、どの参加者にも送られずにSRCとSRSにだけ送られることもあり得ます。 たとえば、すべての参加者が保留中で、SRCがフォーカスと同じ場所にある会議の場合です。 また、メディアストリームが複数の参加者によって受信されることもあります（たとえば、「ウィスパー」通話や、サイドでの会話）。
  • メディアストリームは1人以上の参加者によって送信されます（事前にミキシングされたストリーム）。

An example of a case where a participant receives zero or more streams is where a supervisor may have a side conversation with an agent while the agent converses with a customer.

参加者が0個以上のストリームを受信する場合の例として、エージェントが顧客と会話している間に、スーパーバイザーがそのエージェントとサイドで会話する場合があります。

6.9. Syntax of XML Elements for Date and Time

6.9. 日付と時刻のXML要素の構文

The XML elements 'associate-time', 'disassociate-time', 'start-time', and 'stop-time' contain strings representing the date and time. The value of these elements MUST follow the Instant Messaging and Presence Protocol (IMPP) date-time format [RFC3339]. Timestamps that contain "T" or "Z" MUST use the capitalized forms.

XML要素'associate-time'、'disassociate-time'、'start-time'、'stop-time'は、日付と時刻を表す文字列を含みます。 これらの要素の値は、インスタントメッセージング・プレゼンスプロトコル（Instant Messaging and Presence Protocol: IMPP）の日時フォーマット[RFC3339]に従わなければなりません（MUST）。 「T」または「Z」を含むタイムスタンプは、大文字の形式を使わなければなりません（MUST）。

As a security measure, the 'timestamp' element MUST be included in all tuples, unless the exact time of the status change cannot be determined.

セキュリティー対策として、状態変化の正確な時刻を特定できない場合を除き、すべての組に'timestamp'要素を含めなければなりません（MUST）。

6.10. Format of Unique ID

6.10. 一意なIDのフォーマット

A unique_id is generated in two steps:

unique_idは2つのステップで生成されます。

  • The Universally Unique Identifier (UUID) is created using any of the procedures mentioned in Sections 4.3, 4.4, and 4.5 of [RFC4122]. The algorithm MUST ensure that it does not use any potentially personally identifying information to generate the UUIDs. If implementations are using a Name-Based UUID as defined in Section 4.3 of [RFC4122], a namespace ID generated using the guidance in Section 4.2 or 4.5 of [RFC4122] might be a good choice.
  • The UUID is encoded using base64 as defined in [RFC4648].
  • 汎用一意識別子（Universally Unique Identifier: UUID）を、[RFC4122]のセクション4.3、4.4、4.5で述べられている手順のいずれかを使って作成します。 そのアルゴリズムは、UUIDの生成に個人を特定し得る情報を一切使わないことを保証しなければなりません（MUST）。 実装が[RFC4122]のセクション4.3で定義されている名前ベースのUUIDを使う場合、[RFC4122]のセクション4.2または4.5の指針を使って生成した名前空間IDがよい選択でしょう。
  • UUIDを、[RFC4648]で定義されているbase64を使ってエンコードします。

The above-mentioned unique_id mechanism SHOULD be used for each metadata element. Multiple SRCs can refer to the same element/UUID (how each SRC learns the UUID here is beyond the scope of this document). If two SRCs use the same UUID, they MUST retain the UUID/element mapping. If the SRS detects that a UUID is mapped to more than one element at any point in time, it MUST treat this as an error. For example, the SRS may choose to reject or ignore the portions of metadata where it detects that the same UUID is mapped to an element that is different than the expected element (the SRS learns the mapped UUID when it sees an element for the first time in a metadata instance).

上で述べたunique_idのメカニズムは、各メタデータ要素に使用すべきです（SHOULD）。 複数のSRCが同じ要素/UUIDを参照することがあります（ここで各SRCがUUIDをどのように知るかは、この文書の範囲外です）。 2つのSRCが同じUUIDを使う場合、それらのSRCはUUIDと要素の対応付けを保持しなければなりません（MUST）。 SRSは、あるUUIDがある時点で複数の要素に対応付けられていることを検出した場合、これをエラーとして扱わなければなりません（MUST）。 たとえばSRSは、同じUUIDが期待される要素とは異なる要素に対応付けられていることを検出したメタデータの部分を、拒否または無視することを選択できます（SRSは、メタデータのインスタンス内で要素を初めて見たときに、対応付けられたUUIDを知ります）。

6.11. Metadata Version Indicator

6.11. メタデータのバージョン指示子

The Metadata version is defined to help the SRC and SRS know the version of metadata XML schema used. SRCs and SRSs that support this specification MUST use version 1 in the namespace (urn:ietf:params:xml:ns:recording:1) in all the XML documents. Implementations may not interoperate if the version implemented by the sender is not known by the receiver. No negotiation of versions is provided. The version number has no significance, although documents that update or obsolete this document (possibly including drafts of such documents) should include a higher version number if the metadata XML schema changes.

メタデータのバージョンは、使用されているメタデータXMLスキーマのバージョンをSRCとSRSが知るのに役立つように定義されています。 この仕様をサポートするSRCとSRSは、すべてのXML文書において、名前空間（urn:ietf:params:xml:ns:recording:1）でバージョン1を使用しなければなりません（MUST）。 送信者が実装しているバージョンを受信者が知らない場合、実装どうしが相互運用できないことがあります。 バージョンのネゴシエーションは提供されません。 バージョン番号自体に意味はありませんが、この文書を更新または廃止する文書（そのような文書のドラフトを含む場合があります）は、メタデータXMLスキーマが変更された場合、より大きなバージョン番号を含めるべきです。

10. Security Considerations

10. セキュリティーに関する考慮事項

This document describes an extensive set of metadata that may be recorded by the SRS. Most of the metadata could be considered private data. The procedures mentioned in the Security Considerations section of [RFC7866] MUST be followed by the SRC and the SRS for mutual authentication and to protect the content of the metadata in the RS.

この文書では、SRSによって記録される可能性のある広範なメタデータについて説明しています。 メタデータの大部分は、プライベートなデータとみなされ得ます。 相互認証のため、およびRS内のメタデータの内容を保護するために、SRCとSRSは[RFC7866]のセキュリティーに関する考慮事項のセクションで述べられている手順に従わなければなりません（MUST）。

An SRC MAY, by policy, choose to limit the parts of the metadata sent to the SRS for recording. Also, the policy of the SRS might not require recording all the metadata it receives. For the sake of data minimization, the SRS MUST NOT record additional metadata that is not explicitly required by local policy. Metadata in storage needs to be provided with a level of security that is comparable to that of the recording session.

SRCは、ポリシーによって、記録のためにSRSに送るメタデータの部分を制限することを選択してもよいです（MAY）。 また、SRSのポリシーは、受信したすべてのメタデータの記録を要求しないかもしれません。 データ最小化のため、SRSは、ローカルポリシーによって明示的に要求されていない追加のメタデータを記録してはなりません（MUST NOT）。 保存されたメタデータには、記録セッションのものに匹敵するレベルのセキュリティーを提供する必要があります。
