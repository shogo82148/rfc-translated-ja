RFC 8245

Rules for Designing Protocols Using the Generalized Packet/Message Format from RFC 5444

RFC 8245

RFC 5444の汎用パケット/メッセージフォーマットを使用するプロトコルの設計規則

Abstract

概要

RFC 5444 specifies a generalized Mobile Ad Hoc Network (MANET) packet/message format and describes an intended use for multiplexed MANET routing protocol messages; this use is mandated by RFC 5498 when using the MANET port or protocol number that it specifies. This document updates RFC 5444 by providing rules and recommendations for how the multiplexer operates and how protocols can use the packet/message format. In particular, the mandatory rules prohibit a number of uses that have been suggested in various proposals and that would have led to interoperability problems, to the impediment of protocol extension development, and/or to an inability to use optional generic parsers.

RFC 5444は、汎用のモバイルアドホックネットワーク（Mobile Ad Hoc Network、MANET）パケット/メッセージフォーマットを規定し、多重化されたMANETルーティングプロトコルメッセージの意図された使用法を記述しています。この使用法は、RFC 5498が規定するMANETのポート番号またはプロトコル番号を使用する場合には、RFC 5498によって義務付けられています。この文書は、マルチプレクサーがどのように動作するか、およびプロトコルがパケット/メッセージフォーマットをどのように使用できるかについての規則と推奨事項を提供することによって、RFC 5444を更新します。特に、これらの必須の規則は、さまざまな提案で示唆されてきた使用法のうち、相互運用性の問題、プロトコル拡張の開発の妨げ、またはオプションの汎用パーサーを使用できなくなること（あるいはそれらの組み合わせ）につながったであろういくつかの使用法を禁止します。

1. Introduction

1. はじめに

[RFC5444] specifies a generalized packet/message format that is designed for use by MANET routing protocols.

[RFC5444]は、MANETルーティングプロトコルで使用するために設計された、汎用のパケット/メッセージフォーマットを規定しています。

[RFC5444] was designed following experiences with [RFC3626], which attempted to provide a packet/message format accommodating diverse protocol extensions but did not fully succeed. [RFC5444] was designed as a common building block for use by both proactive and reactive MANET routing protocols.

[RFC5444]は、多様なプロトコル拡張に対応できるパケット/メッセージフォーマットを提供しようとしたものの完全には成功しなかった[RFC3626]での経験を踏まえて設計されました。[RFC5444]は、プロアクティブ型とリアクティブ型の両方のMANETルーティングプロトコルが使用する共通の構成要素として設計されました。

[RFC5498] mandates the use of this packet/message format and of the packet multiplexing process described in an appendix to [RFC5444] by protocols operating over the MANET IP protocol and UDP port numbers that were allocated by [RFC5498].

[RFC5498]は、[RFC5498]によって割り当てられたMANETのIPプロトコル番号およびUDPポート番号上で動作するプロトコルに対して、このパケット/メッセージフォーマットと、[RFC5444]の付録に記述されたパケット多重化プロセスを使用することを義務付けています。

1.1. History and Purpose

1.1. 経緯と目的

Since the publication of [RFC5444] in 2009, several RFCs have been published, including [RFC5497], [RFC6130], [RFC6621], [RFC7181], [RFC7182], [RFC7183], [RFC7188], [RFC7631], and [RFC7722], that use the format of [RFC5444]. The ITU-T recommendation [G9903] also uses the format of [RFC5444] for encoding some of its control signals. In developing these specifications, experience with the use of [RFC5444] has been acquired, specifically with respect to how to write specifications using [RFC5444] so as to ensure forward compatibility of a protocol with future extensions, to enable the creation of efficient messages, and to enable the use of an efficient and generic parser for all protocols using [RFC5444].

2009年に[RFC5444]が公開されて以来、[RFC5444]のフォーマットを使用する、[RFC5497]、[RFC6130]、[RFC6621]、[RFC7181]、[RFC7182]、[RFC7183]、[RFC7188]、[RFC7631]、[RFC7722]を含むいくつかのRFCが公開されています。ITU-Tの勧告[G9903]も、その制御信号の一部をエンコードするために[RFC5444]のフォーマットを使用しています。これらの仕様を策定する中で、[RFC5444]の使用に関する経験が得られました。特に、プロトコルと将来の拡張との前方互換性を確保し、効率的なメッセージを作成できるようにし、[RFC5444]を使用するすべてのプロトコルに対して効率的で汎用的なパーサーを使用できるようにするには、[RFC5444]を使用する仕様をどのように書けばよいかについての経験です。

During the same time period, other suggestions have been made to use [RFC5444] in a manner that would inhibit the development of interoperable protocol extensions, that would potentially lead to inefficiencies, or that would lead to incompatibilities with generic parsers for [RFC5444]. While these uses were not all explicitly prohibited by [RFC5444], they are strongly discouraged. This document is intended to prohibit such uses, to present experiences from designing protocols using [RFC5444], and to provide these as guidelines (with their rationale) for future protocol designs using [RFC5444].

同じ時期に、相互運用可能なプロトコル拡張の開発を妨げたり、非効率につながる可能性があったり、[RFC5444]の汎用パーサーとの非互換性につながったりするような方法で[RFC5444]を使用するという、別の提案もなされてきました。これらの使用法のすべてが[RFC5444]で明示的に禁止されていたわけではありませんが、強く非推奨とされています。この文書は、そのような使用法を禁止し、[RFC5444]を使用したプロトコル設計の経験を示し、それらを[RFC5444]を使用する将来のプロトコル設計のためのガイドライン（その根拠を含む）として提供することを意図しています。

1.2. Features of RFC 5444

1.2. RFC 5444の特徴

[RFC5444] performs two main functions:

[RFC5444]は、主に2つの機能を果たします。

  • It defines a packet/message format for use by MANET routing protocols. As far as [RFC5444] is concerned, it is up to each protocol that uses it to implement the required message parsing and formation. It is natural, especially when implementing more than one such protocol, to implement these processes using protocol-independent packet/message creation and parsing procedures, however, this is not required by [RFC5444]. Some comments in this document might be particularly applicable to such a case, but all that is required is that the messages passed to and from protocols are correctly formatted and that packets containing those messages are correctly formatted as described in the following point.
  • Appendix A of [RFC5444], combined with the intended usage described in Appendix B of [RFC5444], specifies a multiplexing and demultiplexing process whereby an entity that can be referred to as the "RFC 5444 multiplexer" manages packets that travel a single (logical) hop and contain messages that are owned by individual protocols. Note that in this document, the "RFC 5444 multiplexer" is referred to as the "multiplexer", or as the "demultiplexer" when performing that function. A packet can contain messages from more than one protocol. This process is mandated for use on the MANET UDP port and IP protocol (alternative means for the transport of packets) by [RFC5498]. The multiplexer is responsible for creating packets and for parsing Packet Headers, extracting messages, and passing them to the appropriate protocol according to their type (the first octet in the message).
  • MANETルーティングプロトコルで使用するパケット/メッセージフォーマットを定義します。[RFC5444]に関する限り、必要なメッセージの解析と形成を実装するのは、それを使用する各プロトコルの責任です。特に複数のそのようなプロトコルを実装する場合には、プロトコルに依存しないパケット/メッセージの作成手順と解析手順を使ってこれらのプロセスを実装するのが自然ですが、これは[RFC5444]では要求されていません。この文書のいくつかの記述は、そのような場合に特に当てはまるかもしれませんが、要求されているのは、プロトコルとの間で受け渡されるメッセージが正しくフォーマットされていることと、それらのメッセージを含むパケットが次の項目で説明するように正しくフォーマットされていることだけです。
  • [RFC5444]の付録Aは、[RFC5444]の付録Bに記述された意図された使用法と組み合わせて、多重化および多重分離のプロセスを規定しています。このプロセスでは、「RFC 5444マルチプレクサー（RFC 5444 multiplexer）」と呼ぶことのできるエンティティーが、単一の（論理的な）ホップを移動し、個々のプロトコルが所有するメッセージを含むパケットを管理します。この文書では、「RFC 5444マルチプレクサー」を「マルチプレクサー（multiplexer）」と呼び、その機能を実行しているときには「デマルチプレクサー（demultiplexer）」と呼ぶことに注意してください。1つのパケットには、複数のプロトコルのメッセージを含めることができます。このプロセスは、[RFC5498]によって、MANETのUDPポートとIPプロトコル（パケットを転送するための代替手段）で使用することが義務付けられています。マルチプレクサーは、パケットの作成、パケットヘッダー（Packet Header）の解析、メッセージの抽出、およびメッセージをそのタイプ（メッセージの最初のオクテット）に応じて適切なプロトコルに渡すことに責任を負います。

1.2.1. Packet/Message Format

1.2.1. パケット/メッセージフォーマット

Among the characteristics and design objectives of the packet/message format of [RFC5444] are the following:

[RFC5444]のパケット/メッセージフォーマットの特徴と設計目標には、次のものがあります。

  • It is designed for carrying MANET routing protocol control signals.

  • It defines a packet as a Packet Header with a set of Packet TLVs (Type-Length-Value structures), followed by a set of messages. Each message has a well-defined structure consisting of a Message Header (designed for making processing and forwarding decisions) followed by a set of Message TLVs, and a set of (address, type, value) associations using Address Blocks and their Address Block TLVs. The packet/message format from [RFC5444] then enables the use of simple and generic parsing logic for Packet Headers, Message Headers, and message content.

    A packet can include messages from different protocols, such as the Neighborhood Discovery Protocol (NHDP) [RFC6130] and the Optimized Link State Routing Protocol version 2 (OLSRv2) [RFC7181], in a single transmission. This was observed in [RFC3626] to be beneficial, especially in wireless networks where media contention can be significant.

  • Its packets are designed to travel between two neighboring interfaces, which will result in a single decrement of the IPv4 TTL or IPv6 hop limit. The Packet Header and any Packet TLVs can thus convey information relevant to that link (for example, the Packet Sequence Number can be used to count transmission successes across that link). Packets are designed to be constructed for a single-hop transmission; a packet transmission following a successful packet reception is (by design) a new packet that can include all, some, or none of the received messages, plus possibly additional messages either received in separate packets or generated locally at that router. Messages can thus travel more than one hop and are designed to carry end-to-end protocol signals.

  • It supports "internal extensibility" using TLVs; an extension can add information to an existing message without that information rendering the message unparseable or unusable by a router that does not support the extension. An extension is typically of the protocol that created the message to be extended, for example, [RFC7181] adds information to the HELLO messages created by [RFC6130]. However, an extension can also be independent of the protocol; for example, [RFC7182] can add Integrity Check Value (ICV) and timestamp information to any message (or to a packet, thus extending the multiplexer).

    Information, in the form of TLVs, can be added to the message as a whole (such as the integrity information specified in [RFC7182]) or can be associated with specific addresses in the message (such as the Multipoint Relay (MPR) selection and link metric information added to HELLO messages by [RFC7181]). An extension can also add addresses to a message.

  • It uses address aggregation into compact Address Blocks by exploiting commonalities between addresses. In many deployments, addresses (IPv4 and IPv6) used on interfaces share a common prefix that need not be repeated. Using IPv6, several addresses (of the same interface) might have common interface identifiers that need not be repeated.
  • It sets up common namespaces, formats, and data structures for use by different protocols where common parsing logic can be used. For example, [RFC5497] defines a generic TLV format for representing time information (such as interval time or validity time).
  • It contains a minimal Message Header (a maximum of five elements: type, originator, sequence number, hop count, and hop limit) that permit decisions regarding whether to locally process a message or forward a message (thus enabling MANET-wide flooding of a message) without processing the body of the message.
  • MANETルーティングプロトコルの制御信号を運ぶために設計されています。

  • パケットを、一連のパケットTLV（Packet TLV、Type-Length-Value構造）を伴うパケットヘッダーと、それに続く一連のメッセージとして定義しています。各メッセージは明確に定義された構造を持ち、メッセージヘッダー（Message Header、処理と転送の判断を行うために設計されています）と、それに続く一連のメッセージTLV（Message TLV）、およびアドレスブロック（Address Block）とそのアドレスブロックTLV（Address Block TLV）を使用した一連の（アドレス、タイプ、値）の関連付けで構成されます。これにより、[RFC5444]のパケット/メッセージフォーマットでは、パケットヘッダー、メッセージヘッダー、およびメッセージの内容に対して、単純で汎用的な解析ロジックを使用できます。

    パケットには、近隣探索プロトコル（Neighborhood Discovery Protocol、NHDP）[RFC6130]や最適化リンク状態ルーティングプロトコルバージョン2（Optimized Link State Routing Protocol version 2、OLSRv2）[RFC7181]など、異なるプロトコルのメッセージを1回の送信に含めることができます。[RFC3626]では、これが特にメディアの競合が大きくなり得る無線ネットワークにおいて有益であることが観察されました。

  • そのパケットは、隣接する2つのインターフェイス間を移動するように設計されており、その結果、IPv4のTTLまたはIPv6のホップリミットは1回だけ減算されます。したがって、パケットヘッダーとパケットTLVは、そのリンクに関連する情報を伝えることができます（たとえば、パケットシーケンス番号（Packet Sequence Number）を使用して、そのリンクでの送信の成功を数えることができます）。パケットは単一ホップの送信のために構築されるように設計されています。パケットの受信に成功した後のパケット送信は、（設計上）新しいパケットであり、受信したメッセージのすべて、一部を含めることも、まったく含めないこともでき、さらに、別のパケットで受信したメッセージや、そのルーターでローカルに生成したメッセージを追加で含めることもできます。したがって、メッセージは複数のホップを移動でき、エンドツーエンドのプロトコル信号を運ぶように設計されています。

  • TLVを使用した「内部拡張性（internal extensibility）」をサポートしています。拡張は、既存のメッセージに情報を追加でき、その情報によって、その拡張をサポートしていないルーターがそのメッセージを解析できなくなったり使用できなくなったりすることはありません。拡張は通常、拡張されるメッセージを作成したプロトコルの拡張です。たとえば、[RFC7181]は、[RFC6130]が作成するHELLOメッセージに情報を追加します。しかし、拡張はプロトコルから独立していることもできます。たとえば、[RFC7182]は、任意のメッセージに（あるいはパケットに。この場合はマルチプレクサーを拡張することになります）完全性チェック値（Integrity Check Value、ICV）とタイムスタンプの情報を追加できます。

    TLVの形式の情報は、メッセージ全体に対して追加すること（[RFC7182]で規定された完全性情報など）も、メッセージ内の特定のアドレスに関連付けること（[RFC7181]がHELLOメッセージに追加するマルチポイントリレー（Multipoint Relay、MPR）の選択やリンクメトリックの情報など）もできます。拡張は、メッセージにアドレスを追加することもできます。

  • アドレス間の共通性を利用して、アドレスをコンパクトなアドレスブロックに集約します。多くの展開では、インターフェイスで使用されるアドレス（IPv4とIPv6）は、繰り返す必要のない共通のプレフィックスを共有しています。IPv6を使用する場合、（同じインターフェイスの）複数のアドレスが、繰り返す必要のない共通のインターフェイス識別子を持つことがあります。
  • 共通の解析ロジックを使用できるように、異なるプロトコルが使用する共通の名前空間、フォーマット、データ構造を定めます。たとえば、[RFC5497]は、時間情報（間隔時間や有効時間など）を表現するための汎用のTLVフォーマットを定義しています。
  • 最小限のメッセージヘッダー（最大5つの要素：タイプ、発信者、シーケンス番号、ホップカウント、ホップリミット）を含んでおり、メッセージの本体を処理することなく、メッセージをローカルで処理するかどうか、またはメッセージを転送するかどうか（これによりMANET全体へのメッセージのフラッディングが可能になります）を判断できます。

1.2.2. Multiplexing and Demultiplexing

1.2.2. 多重化と多重分離

The multiplexer (and demultiplexer) is defined in Appendix A of [RFC5444]. Its purpose is to allow multiple protocols to share the same IP protocol or UDP port. That sharing was made necessary by the separation of [RFC6130] from [RFC7181] as separate protocols and by the allocation of a single IP protocol and UDP port to all MANET protocols, including those protocols following [RFC5498], which states:

マルチプレクサー（およびデマルチプレクサー）は、[RFC5444]の付録Aで定義されています。その目的は、複数のプロトコルが同じIPプロトコルまたはUDPポートを共有できるようにすることです。この共有が必要になったのは、[RFC6130]と[RFC7181]が別々のプロトコルとして分離されたことと、[RFC5498]に従うプロトコルを含むすべてのMANETプロトコルに単一のIPプロトコルとUDPポートが割り当てられたためです。そのRFCには次のように記述されています。

All interoperable protocols running on these well-known IANA allocations MUST conform to [RFC5444]. [RFC5444] provides a common format that enables one or more protocols to share the IANA allocations defined in this document unambiguously.

これらのよく知られたIANA割り当て上で動作するすべての相互運用可能なプロトコルは、[RFC5444]に準拠しなければなりません（MUST）。[RFC5444]は、1つ以上のプロトコルがこの文書で定義されたIANA割り当てを曖昧さなく共有できるようにする共通のフォーマットを提供します。

The multiplexer is the mechanism in [RFC5444] that enables that sharing.

マルチプレクサーは、その共有を可能にする[RFC5444]のメカニズムです。

The primary purposes of the multiplexer are to:

マルチプレクサーの主な目的は次のとおりです。

  • Accept messages from MANET protocols, which also indicate over which interface(s) the messages are to be sent and to which destination address. The latter can be a unicast address or the "LL-MANET-Routers" link-local multicast address defined in [RFC5498].
  • Collect messages (possibly from multiple protocols) for the same local interface and destination, into packets to be sent one logical hop, and to send packets using the MANET UDP port or IP protocol defined in [RFC5498].
  • Extract messages from received packets and pass them to their owning protocols.
  • MANETプロトコルからメッセージを受け付けます。このとき、メッセージをどのインターフェイスから送信するか、およびどの宛先アドレスに送信するかも示されます。後者は、ユニキャストアドレスか、[RFC5498]で定義された「LL-MANET-Routers」リンクローカルマルチキャストアドレスです。
  • 同じローカルインターフェイスと宛先に向けた（複数のプロトコルからの場合もある）メッセージを集めて、1論理ホップ送信されるパケットにまとめ、[RFC5498]で定義されたMANETのUDPポートまたはIPプロトコルを使用してパケットを送信します。
  • 受信したパケットからメッセージを抽出し、それらを所有するプロトコルに渡します。

The multiplexer's relationship is with the protocols that own the corresponding Message Types. Where those protocols have their own relationships (for example, as extensions), this is the responsibility of the protocols. For example, OLSRv2 [RFC7181] extends the HELLO messages created by NHDP [RFC6130]. However, the multiplexer will deliver HELLO messages to NHDP and will expect to receive HELLO messages from NHDP; the relationship between NHDP and OLSRv2 is between those two protocols.

マルチプレクサーが関係を持つのは、対応するメッセージタイプ（Message Type）を所有するプロトコルです。それらのプロトコルが独自の関係（たとえば、拡張としての関係）を持つ場合、それはプロトコルの責任です。たとえば、OLSRv2 [RFC7181]は、NHDP [RFC6130]が作成するHELLOメッセージを拡張します。しかし、マルチプレクサーはHELLOメッセージをNHDPに配送し、HELLOメッセージをNHDPから受け取ることを期待します。NHDPとOLSRv2の間の関係は、それら2つのプロトコルの間のものです。

The multiplexer is also responsible for the Packet Header, including any Packet Sequence Number and Packet TLVs. It can accept some additional instructions from protocols, can pass additional information to protocols, and will follow some additional rules; see Section 4.4.

マルチプレクサーは、パケットシーケンス番号やパケットTLVを含め、パケットヘッダーにも責任を負います。マルチプレクサーは、プロトコルから追加の指示を受け付けたり、プロトコルに追加の情報を渡したりでき、いくつかの追加の規則に従います。セクション4.4を参照してください。

3. Applicability Statement

3. 適用性に関する声明

This document does not specify a protocol but documents constraints on how to design protocols that use the generic packet/message format defined in [RFC5444] that, if not followed, makes forms of extensions of those protocols impossible, impedes the ability to generate efficient (small) messages, or makes desirable forms of generic parsers impossible. The use of the [RFC5444] format is mandated by [RFC5498] for all protocols running over the MANET protocol and port, defined therein. Thus, the constraints in this document apply to all protocols running over the MANET IP protocol or UDP port. The constraints are strongly recommended for other uses of [RFC5444].

この文書はプロトコルを規定するものではなく、[RFC5444]で定義された汎用のパケット/メッセージフォーマットを使用するプロトコルをどのように設計するかについての制約を文書化したものです。これらの制約に従わない場合、それらのプロトコルのある種の拡張が不可能になったり、効率的な（小さな）メッセージを生成する能力が妨げられたり、望ましい形の汎用パーサーが不可能になったりします。[RFC5444]のフォーマットの使用は、[RFC5498]によって、そこで定義されたMANETのプロトコルとポート上で動作するすべてのプロトコルに対して義務付けられています。したがって、この文書の制約は、MANETのIPプロトコルまたはUDPポート上で動作するすべてのプロトコルに適用されます。これらの制約は、[RFC5444]のその他の使用法に対しても強く推奨されます。

4. Information Transmission

4. 情報の伝送

Protocols need to transmit information from one instance implementing the protocol to another.

プロトコルは、そのプロトコルを実装するあるインスタンスから別のインスタンスへ情報を伝送する必要があります。

4.1. Where to Record Information

4.1. 情報を記録する場所

A protocol has the following choices as to where to put information for transmission:

プロトコルには、伝送する情報をどこに置くかについて、次の選択肢があります。

  • in a TLV to be added to the Packet Header;
  • in a message of a type owned by another protocol; or
  • in a message of a type owned by the protocol.
  • パケットヘッダーに追加するTLVに置く
  • 別のプロトコルが所有するタイプのメッセージに置く
  • そのプロトコルが所有するタイプのメッセージに置く

The first case (a Packet TLV) can only be used when the information is to be carried one hop. It SHOULD only be used either where the information relates to the packet as a whole (for example, packet integrity check values and timestamps, as specified in [RFC7182]) or if the information is expected to have a wider application than a single protocol. A protocol can also request that the Packet Header include Packet Sequence Numbers but does not control those numbers.

1番目のケース（パケットTLV）は、情報を1ホップだけ運ぶ場合にのみ使用できます。これは、情報がパケット全体に関係する場合（たとえば、[RFC7182]で規定されたパケットの完全性チェック値やタイムスタンプ）か、情報が単一のプロトコルよりも広く適用されることが期待される場合にのみ使用されるべきです（SHOULD）。プロトコルは、パケットヘッダーにパケットシーケンス番号を含めるように要求することもできますが、それらの番号を制御することはありません。

The second case (in a message of a type owned by another protocol) is only possible if the adding protocol is an extension to the owning protocol; for example, OLSRv2 [RFC7181] is an extension of NHDP [RFC6130].

2番目のケース（別のプロトコルが所有するタイプのメッセージに置く）は、情報を追加するプロトコルが所有プロトコルの拡張である場合にのみ可能です。たとえば、OLSRv2 [RFC7181]はNHDP [RFC6130]の拡張です。

The third case is the normal case for a new protocol.

3番目のケースは、新しいプロトコルにとって通常のケースです。

A protocol extension can either be simply an update of the protocol (the third case) or be a new protocol that also updates another protocol (the second case). An example of the latter is that OLSRv2 [RFC7181] is a protocol that also extends the HELLO message owned by NHDP [RFC6130]; it is thus an example of both the second and third cases (the latter using the OLSRv2 owned Topology Control (TC) message). An extension to [RFC5444], such as [RFC7182], is considered to be an extension to all protocols. Protocols SHOULD be designed to enable extension by any of these means to be possible, and some of the rules in this document (in Sections 4.6 and 4.8, specifically) are to help facilitate that.

プロトコル拡張は、単にプロトコルの更新である（3番目のケース）場合もあれば、別のプロトコルも更新する新しいプロトコルである（2番目のケース）場合もあります。後者の例として、OLSRv2 [RFC7181]は、NHDP [RFC6130]が所有するHELLOメッセージも拡張するプロトコルです。したがって、これは2番目と3番目の両方のケースの例です（後者はOLSRv2が所有するトポロジー制御（Topology Control、TC）メッセージを使用します）。[RFC7182]のような[RFC5444]の拡張は、すべてのプロトコルの拡張とみなされます。プロトコルは、これらのいずれの手段による拡張も可能になるように設計されるべきです（SHOULD）。この文書のいくつかの規則（具体的にはセクション4.6と4.8）は、それを容易にするためのものです。

4.2. Message and TLV Type Allocation

4.2. メッセージタイプとTLVタイプの割り当て

Protocols SHOULD be conservative in the number of new Message Types that they require, as the total available number of allocatable Message Types is only 224. Protocol design SHOULD consider whether different functions can be implemented by differences in TLVs carried in the same Message Type rather than using multiple Message Types.

割り当て可能なメッセージタイプの総数は224しかないため、プロトコルは、必要とする新しいメッセージタイプの数について控えめであるべきです（SHOULD）。プロトコル設計では、複数のメッセージタイプを使用するのではなく、同じメッセージタイプで運ばれるTLVの違いによって異なる機能を実装できるかどうかを検討するべきです（SHOULD）。

The TLV Type space, although greater than the Message Type space, SHOULD also be used efficiently. The Full Type of a TLV occupies two octets; thus, there are many more available TLV Full Types than there are Message Types. However, in some cases (currently LINK_METRIC from [RFC7181] and ICV and TIMESTAMP from [RFC7182], all in the global TLV Type space), a TLV Type with a complete set of 256 TLV Full Types is defined (but not necessarily allocated).

TLVタイプの空間は、メッセージタイプの空間よりも大きいものの、これも効率的に使用されるべきです（SHOULD）。TLVのフルタイプは2オクテットを占めるため、利用可能なTLVフルタイプはメッセージタイプよりもはるかに多くあります。しかし、いくつかのケース（現在のところ、[RFC7181]のLINK_METRICと、[RFC7182]のICVおよびTIMESTAMPで、いずれもグローバルなTLVタイプ空間にあります）では、256個のTLVフルタイプの完全な集合を持つTLVタイプが定義されています（ただし、必ずしも割り当てられているわけではありません）。

Each Message Type has an associated block of Message-Type-specific TLV Types (128 to 233, each with 256 type extensions) both for Address Block TLV Types and Message TLV Types. TLV Types from within these blocks SHOULD be used in preference to the Message-Type-independent Message TLV Types (0 to 127, each with 256 type extensions) when a TLV is specific to a message.

各メッセージタイプには、アドレスブロックTLVタイプとメッセージTLVタイプの両方について、メッセージタイプ固有のTLVタイプのブロック（128～233、それぞれ256個のタイプ拡張を持ちます）が関連付けられています。TLVがメッセージに固有のものである場合、メッセージタイプに依存しないメッセージTLVタイプ（0～127、それぞれ256個のタイプ拡張を持ちます）よりも、これらのブロック内のTLVタイプが優先して使用されるべきです（SHOULD）。

The Expert Review guidelines in [RFC5444] are updated accordingly, as described in Section 8.

[RFC5444]のExpert Reviewのガイドラインは、セクション8で説明するように、これに応じて更新されます。

4.3. Message Recognition

4.3. メッセージの認識

A message contains a Message Header and a Message Body; note that the Message TLV Block is considered part of the latter. The Message Header contains information whose primary purpose is to decide whether to process the message and whether to forward the message.

メッセージは、メッセージヘッダーとメッセージ本体（Message Body）を含みます。メッセージTLVブロック（Message TLV Block）は後者の一部とみなされることに注意してください。メッセージヘッダーには、主にメッセージを処理するかどうか、およびメッセージを転送するかどうかを判断するための情報が含まれています。

A protocol might need to recognize whether a message, especially a flooded message, is one that it has previously received (for example, to determine whether to process and/or forward it, or to discard it). A message can be recognized as one that has been previously seen if it contains sufficient information in its Message Header. A message MUST be so recognized by the combination of its Message Type, Originator Address, and Message Sequence Number. The inclusion of Message Type allows each protocol to manage its own Message Sequence Numbers and also allows for the possibility that different Message Types can have greatly differing transmission rates. As an example of such use, [RFC7181] contains a general purpose process for managing processing and forwarding decisions, although specifically for use with MPR flooding. (Blind flooding can be handled similarly by assuming that all other routers are MPR selectors; it is not necessary in this case to differentiate between interfaces on which a message is received.)

プロトコルは、メッセージ、特にフラッディングされたメッセージが、以前に受信したものであるかどうかを認識する必要があるかもしれません（たとえば、それを処理または転送する（あるいはその両方を行う）か、それとも破棄するかを判断するため）。メッセージは、そのメッセージヘッダーに十分な情報が含まれていれば、以前に見たものとして認識できます。メッセージは、そのメッセージタイプ、発信者アドレス（Originator Address）、およびメッセージシーケンス番号（Message Sequence Number）の組み合わせによってそのように認識されなければなりません（MUST）。メッセージタイプを含めることで、各プロトコルが独自のメッセージシーケンス番号を管理できるようになり、また、異なるメッセージタイプの送信レートが大きく異なる可能性にも対応できます。このような使用法の例として、[RFC7181]には、処理と転送の判断を管理するための汎用のプロセスが含まれています。ただし、これは特にMPRフラッディングで使用するためのものです。（ブラインドフラッディングも、他のすべてのルーターがMPRセレクターであると仮定することで同様に扱えます。この場合、メッセージを受信したインターフェイスを区別する必要はありません。）

Most protocol information is thus contained in the Message Body. A model of how such information can be viewed is described in Sections 4.5 and 4.6. To use that model, addresses (for example, of neighboring or otherwise known routers) SHOULD be recorded in Address Blocks, not as data in TLVs. Recording addresses in TLV Value fields both breaks the model of addresses as identities and associated information (attributes) and also inhibits address compression. However, in some cases, alternative addresses (e.g., hardware addresses when the Address Block is recording IP addresses) can be carried as TLV Values. Note that a message contains a Message Address Length field that can be used to allow carrying alternative message sizes, but only one length of addresses can be used in a single message, in all Address Blocks and the Originator Address, and is established by the router and protocol generating the message.

したがって、プロトコルの情報のほとんどはメッセージ本体に含まれます。そのような情報をどのように見ることができるかのモデルは、セクション4.5と4.6で説明しています。このモデルを使用するために、アドレス（たとえば、近隣のルーターや、その他の既知のルーターのアドレス）は、TLV内のデータとしてではなく、アドレスブロックに記録されるべきです（SHOULD）。アドレスをTLVの値（Value）フィールドに記録すると、アイデンティティーとしてのアドレスとそれに関連付けられた情報（属性）というモデルが壊れるうえ、アドレスの圧縮も妨げられます。ただし、場合によっては、代替のアドレス（たとえば、アドレスブロックがIPアドレスを記録しているときのハードウェアアドレス）をTLVの値として運ぶことができます。メッセージには、代替のメッセージサイズを運べるようにするために使用できるMessage Address Lengthフィールドが含まれていますが、1つのメッセージでは、すべてのアドレスブロックと発信者アドレスで1つのアドレス長しか使用できず、その長さはメッセージを生成するルーターとプロトコルによって決定されることに注意してください。

4.4. Message Multiplexing and Packets

4.4. メッセージの多重化とパケット

The multiplexer has to handle message multiplexing into packets and the transmission of said packets, as well as packet reception and demultiplexing into messages. The multiplexer and the protocols that use it are subject to the following rules.

マルチプレクサーは、メッセージをパケットに多重化してそのパケットを送信すること、およびパケットを受信してメッセージに多重分離することを扱わなければなりません。マルチプレクサーとそれを使用するプロトコルは、次の規則に従います。

4.4.1. Packet Transmission

4.4.1. パケットの送信

Packets are formed for transmission through the following steps:

パケットは、次の手順によって送信用に形成されます。

  • Outgoing messages are created by their owning protocol and MAY be modified by any extending protocols if the owning protocol permits this. Messages MAY also be forwarded by their owning protocol. It is strongly RECOMMENDED that messages are not modified in the latter case, other than updates to their hop count and hop limit fields, as described in Section 7.1.1 of [RFC5444]. Note that this includes having an identical octet representation, including not allowing a different TLV representation of the same information. This is because it enables end-to-end authentication that ignores (zeros) those two fields (only), as is done in the Message TLV ICV (Integrity Check Value) calculations in [RFC7182]. Protocols MUST document their behavior with regard to modifiability of messages.
  • Outgoing messages are then sent to the multiplexer. The owning protocol MUST indicate which interface(s) the messages are to be sent on and their destination address. Note that packets travel one hop; the destination is therefore either a link-local multicast address (if the packet is being multicast) or the address of the neighbor interface to which the packet is sent.
  • The owning protocol MAY request that messages are kept together in a packet; the multiplexer SHOULD respect this request if at all possible. The multiplexer SHOULD combine messages that are sent on the same interface in a packet, whether from the same or different protocols, provided that in so doing the multiplexer does not cause an IP packet to exceed the current Maximum Transmission Unit (MTU). Note that the multiplexer cannot fragment messages; creating suitably sized messages that will not cause the MTU to be exceeded if sent in a single message packet is the responsibility of the protocol generating the message. If a larger message is created, then only IP fragmentation is available to allow the packet to be sent; this is generally considered undesirable, especially when transmission can be unreliable.
  • The multiplexer MAY delay messages in order to assemble more efficient packets. It MUST respect any constraints on such delays requested by the protocol if it is practical to do so.
  • If requested by a protocol, the multiplexer MUST (and otherwise MAY) include a Packet Sequence Number in the packet. Such a request MUST be respected as long as the protocol is active. Note that the errata to [RFC5444] indicates that the Packet Sequence Number SHOULD be specific to the interface on which the packet is sent. This specification updates [RFC5444] by requiring that this sequence number MUST be specific to that interface and also that separate sequence numbers MUST be maintained for each destination to which packets are sent with included Packet Sequence Numbers. Addition of Packet Sequence Numbers MUST be consistent (i.e., for each interface and destination, the Packet Sequence Number MUST be added to all packets or to none).
  • An extension to the multiplexer MAY add TLVs to the packet. It MAY also add TLVs to the messages, in which case it is considered as also extending the corresponding protocols. For example, [RFC7182] can be used by the multiplexer to add Packet TLVs or Message TLVs, or it can be used by the protocol to add Message TLVs.
  • 送信メッセージは、その所有プロトコルによって作成されます。所有プロトコルが許可する場合には、送信メッセージを拡張プロトコルが変更してもよいです（MAY）。メッセージは、その所有プロトコルによって転送される場合があります（MAY）。後者の場合、[RFC5444]のセクション7.1.1で説明されているホップカウントフィールドとホップリミットフィールドの更新を除いて、メッセージを変更しないことが強く推奨されます（RECOMMENDED）。これには、オクテット表現が同一であること、つまり同じ情報を異なるTLV表現にすることも許可しないことが含まれる点に注意してください。これは、[RFC7182]のメッセージTLVのICV（Integrity Check Value）計算で行われているように、それら2つのフィールド（のみ）を無視する（ゼロにする）エンドツーエンドの認証が可能になるためです。プロトコルは、メッセージの変更可能性に関する自身の動作を文書化しなければなりません（MUST）。
  • 次に、送信メッセージはマルチプレクサーに送られます。所有プロトコルは、メッセージをどのインターフェイスから送信するかと、その宛先アドレスを示さなければなりません（MUST）。パケットは1ホップを移動することに注意してください。したがって、宛先は、リンクローカルマルチキャストアドレス（パケットがマルチキャストされる場合）か、パケットの送信先の近隣インターフェイスのアドレスのいずれかです。
  • 所有プロトコルは、メッセージを1つのパケットにまとめておくように要求してもよいです（MAY）。マルチプレクサーは、可能な限りこの要求を尊重すべきです（SHOULD）。マルチプレクサーは、同じインターフェイスで送信されるメッセージを、同じプロトコルからのものか異なるプロトコルからのものかにかかわらず、1つのパケットにまとめるべきです（SHOULD）。ただし、そうすることによって、IPパケットが現在の最大転送単位（Maximum Transmission Unit、MTU）を超えないことが条件です。マルチプレクサーはメッセージをフラグメント化できないことに注意してください。単一メッセージのパケットで送信した場合にMTUを超えないような適切なサイズのメッセージを作成するのは、そのメッセージを生成するプロトコルの責任です。より大きなメッセージが作成された場合、パケットを送信するために利用できるのはIPフラグメンテーションだけです。これは一般に、特に送信の信頼性が低い可能性がある場合には、望ましくないと考えられています。
  • マルチプレクサーは、より効率的なパケットを組み立てるために、メッセージを遅延させてもよいです（MAY）。マルチプレクサーは、実際的に可能であれば、プロトコルが要求するそのような遅延に関する制約を尊重しなければなりません（MUST）。
  • プロトコルから要求された場合、マルチプレクサーはパケットにパケットシーケンス番号を含めなければなりません（MUST）（要求されていない場合は、含めてもよいです（MAY））。そのような要求は、そのプロトコルがアクティブである限り尊重されなければなりません（MUST）。[RFC5444]の正誤表には、次のことが示されていることに注意してください。パケットシーケンス番号は、そのパケットを送信するインターフェイスに固有であるべきです（SHOULD）。この仕様は[RFC5444]を更新し、次のことを要求します。このシーケンス番号は、そのインターフェイスに固有でなければなりません（MUST）。また、パケットシーケンス番号を含めてパケットを送信する宛先ごとに、別々のシーケンス番号を維持しなければなりません（MUST）。パケットシーケンス番号の追加は一貫していなければなりません（MUST）（つまり、各インターフェイスと宛先について、パケットシーケンス番号はすべてのパケットに追加するか、どのパケットにも追加しないかのいずれかでなければなりません（MUST））。
  • マルチプレクサーの拡張は、パケットにTLVを追加してもよいです（MAY）。また、メッセージにTLVを追加してもよいです（MAY）。その場合、その拡張は対応するプロトコルも拡張しているとみなされます。たとえば、[RFC7182]は、マルチプレクサーがパケットTLVまたはメッセージTLVを追加するために使用することも、プロトコルがメッセージTLVを追加するために使用することもできます。

4.4.2. Packet Reception

4.4.2. パケットの受信

When a packet is received, the following steps are performed by the demultiplexer and by protocols:

パケットを受信すると、デマルチプレクサーとプロトコルによって次の手順が実行されます。

  • The Packet Header and the organization into the messages that it contains MUST be verified by the demultiplexer.
  • The packet and/or the messages it contains MAY also be verified by an extension to the demultiplexer, such as [RFC7182].
  • Each message MUST be sent to its owning protocol or discarded if the Message Type is not recognized. The demultiplexer MUST also make available to the protocol the Packet Header and the source and destination addresses in the IP datagram that included the packet.
  • The demultiplexer MUST remove any Message TLVs that were added by an extension to the multiplexer. The message MUST be passed on to the protocol exactly as received from (another instance of) the protocol. This is, in part, an implementation detail. For example, an implementation of the multiplexer and of [RFC7182] could add a Message TLV either in the multiplexer or in the protocol and remove it in the same place on reception. An implementation MUST ensure that the message passed to a protocol is as it would be passed from that protocol by the same implementation, i.e., that the combined implementation on a router is self-consistent, and that messages included in packets by the multiplexer are independent of this implementation detail.
  • The owning protocol MUST verify each message for correctness; it MUST allow any extending protocol(s) to also contribute to this verification.
  • The owning protocol MUST process each message. In some cases, which will be defined in the protocol specification, this processing will determine that the message will be ignored. Except in the latter case, the owning protocol MUST also allow any extending protocols to process the message.
  • The owning protocol MUST manage the hop count and/or hop limit in the message. It is RECOMMENDED that these are handled as described in Appendix B of [RFC5444]; they MUST be so handled if using hop-count-dependent TLVs such as those defined in [RFC5497].
  • パケットヘッダーと、パケットに含まれるメッセージへの構成は、デマルチプレクサーによって検証されなければなりません（MUST）。
  • パケット、またはパケットに含まれるメッセージ（あるいはその両方）は、[RFC7182]のようなデマルチプレクサーの拡張によっても検証される場合があります（MAY）。
  • 各メッセージは、その所有プロトコルに送られるか、メッセージタイプが認識されない場合には破棄されなければなりません（MUST）。デマルチプレクサーは、パケットヘッダーと、そのパケットを含んでいたIPデータグラムの送信元アドレスと宛先アドレスも、プロトコルが利用できるようにしなければなりません（MUST）。
  • デマルチプレクサーは、マルチプレクサーの拡張によって追加されたメッセージTLVをすべて削除しなければなりません（MUST）。メッセージは、そのプロトコル（の別のインスタンス）から受信したとおりに正確にプロトコルに渡されなければなりません（MUST）。これは、部分的には実装の詳細です。たとえば、マルチプレクサーと[RFC7182]の実装は、メッセージTLVをマルチプレクサーとプロトコルのどちらかで追加し、受信時に同じ場所でそれを削除することができます。実装は、プロトコルに渡されるメッセージが、同じ実装によってそのプロトコルから渡されるメッセージと同じであること、すなわち、ルーター上の組み合わされた実装が自己矛盾しておらず、マルチプレクサーによってパケットに含められるメッセージがこの実装の詳細に依存しないことを保証しなければなりません（MUST）。
  • 所有プロトコルは、各メッセージの正しさを検証しなければなりません（MUST）。所有プロトコルは、拡張プロトコルもこの検証に寄与できるようにしなければなりません（MUST）。
  • 所有プロトコルは、各メッセージを処理しなければなりません（MUST）。プロトコル仕様で定義されるいくつかのケースでは、この処理によってメッセージが無視されることが決定されます。後者の場合を除き、所有プロトコルは、拡張プロトコルもメッセージを処理できるようにしなければなりません（MUST）。
  • 所有プロトコルは、メッセージ内のホップカウントまたはホップリミット（あるいはその両方）を管理しなければなりません（MUST）。これらは[RFC5444]の付録Bで説明されているとおりに扱うことが推奨されます（RECOMMENDED）。[RFC5497]で定義されているもののようなホップカウントに依存するTLVを使用する場合には、そのように扱わなければなりません（MUST）。
4.4.2.1. Other Information
4.4.2.1. その他の情報

In addition to the messages between the multiplexer and the protocols in each direction, the following additional information (summarized from other sections in this specification) can be exchanged.

マルチプレクサーとプロトコルの間での各方向のメッセージに加えて、次の追加情報（この仕様の他のセクションからまとめたもの）を交換できます。

  • The packet source and destination addresses MUST be sent from the demultiplexer to the protocol.
  • The Packet Header, including the Packet Sequence Number, MUST be sent from the (de)multiplexer to the protocol if present. (An implementation MAY choose to only do so or only report the Packet Sequence Number, on request.)
  • A protocol MAY require that all outgoing packets contain a Packet Sequence Number.
  • The interface over which a message is to be sent and its destination address MUST be sent from protocol to multiplexer. The destination address MAY be a multicast address, in particular, the LL-MANET-Routers link-local multicast address defined in [RFC5498].
  • A request to keep messages together in one packet MAY be sent from protocol to multiplexer.
  • A requested maximum message delay MAY be sent from protocol to multiplexer.
  • パケットの送信元アドレスと宛先アドレスは、デマルチプレクサーからプロトコルに送られなければなりません（MUST）。
  • パケットシーケンス番号を含むパケットヘッダーは、存在する場合、（デ）マルチプレクサーからプロトコルに送られなければなりません（MUST）。（実装は、そうすること、またはパケットシーケンス番号だけを報告することを、要求があった場合にのみ行うよう選択してもよいです（MAY）。）
  • プロトコルは、すべての送信パケットにパケットシーケンス番号を含めることを要求してもよいです（MAY）。
  • メッセージを送信するインターフェイスとその宛先アドレスは、プロトコルからマルチプレクサーに送られなければなりません（MUST）。宛先アドレスは、マルチキャストアドレス、特に[RFC5498]で定義されたLL-MANET-Routersリンクローカルマルチキャストアドレスであってもよいです（MAY）。
  • メッセージを1つのパケットにまとめておくための要求を、プロトコルからマルチプレクサーに送ってもよいです（MAY）。
  • 要求する最大メッセージ遅延を、プロトコルからマルチプレクサーに送ってもよいです（MAY）。

The protocol SHOULD also be aware of the MTU that will apply to its messages, if this is available.

また、プロトコルは、利用可能であれば、そのメッセージに適用されるMTUを把握しているべきです（SHOULD）。

4.5. Messages, Addresses, and Attributes

4.5. メッセージ、アドレス、属性

The information in a Message Body, including Message TLVs and Address Block TLVs, consists of:

メッセージTLVとアドレスブロックTLVを含め、メッセージ本体の情報は次のもので構成されます。

  • Attributes of the message, in which each attribute consists of a Full Type, a length, and a Value (of that length).
  • A set of addresses, which are carried in one or more Address Blocks.
  • Attributes of each address, in which each attribute consists of a Full Type, a length, and a Value (of that length).
  • メッセージの属性。各属性は、フルタイプ、長さ、および（その長さの）値（Value）で構成されます。
  • アドレスの集合。これは1つ以上のアドレスブロックで運ばれます。
  • 各アドレスの属性。各属性は、フルタイプ、長さ、および（その長さの）値で構成されます。

Attributes are carried in TLVs. For Message TLVs, the mapping from TLV to attribute is one to one. For Address Block TLVs, the mapping from TLV to attribute is one to many: one TLV can carry attributes for multiple addresses, but only one attribute per address. Attributes for different addresses can be the same or different.

属性はTLVで運ばれます。メッセージTLVの場合、TLVから属性への対応は1対1です。アドレスブロックTLVの場合、TLVから属性への対応は1対多です。1つのTLVで複数のアドレスの属性を運ぶことができますが、アドレスごとに運べる属性は1つだけです。異なるアドレスの属性は、同じであっても異なっていてもかまいません。

[RFC5444] requires that when a TLV Full Type is defined, then it MUST also define how to handle the cases of multiple TLVs of the same type applying to the same information element - i.e., when more than one Packet TLV of the same TLV Full Type is included in the same Packet Header, when more than one Message TLV of the same TLV Full Type is included in the same Message TLV Block, or when more than one Address Block TLV of the same TLV Full Type applies to the same value of any address. It is RECOMMENDED that when defining a new TLV Full Type, a rule of the following form is adopted.

[RFC5444]は次のことを要求しています。TLVフルタイプを定義する場合には、同じ情報要素に適用される同じタイプの複数のTLVのケース、すなわち、同じTLVフルタイプの複数のパケットTLVが同じパケットヘッダーに含まれる場合、同じTLVフルタイプの複数のメッセージTLVが同じメッセージTLVブロックに含まれる場合、または同じTLVフルタイプの複数のアドレスブロックTLVが任意のアドレスの同じ値に適用される場合をどのように扱うかも定義しなければなりません（MUST）。新しいTLVフルタイプを定義する際には、次の形式の規則を採用することが推奨されます（RECOMMENDED）。

  • If used, there MUST be only one TLV of that Full Type associated with the packet (Packet TLV), message (Message TLV), or any value of any address (Address Block TLV).
  • 使用する場合、パケット（パケットTLV）、メッセージ（メッセージTLV）、または任意のアドレスの任意の値（アドレスブロックTLV）に関連付けられるそのフルタイプのTLVは、1つだけでなければなりません（MUST）。

Note that this applies to address values; an address can appear more than once in a message, but the restriction on associating TLVs with addresses covers all copies of that address. It is RECOMMENDED that addresses are not repeated in a message.

これはアドレスの値に適用されることに注意してください。アドレスはメッセージ内に複数回出現することがありますが、TLVをアドレスに関連付けることに関する制限は、そのアドレスのすべてのコピーを対象とします。アドレスはメッセージ内で繰り返さないことが推奨されます（RECOMMENDED）。

A conceptual way to view this information is described in Appendix A.

この情報を捉えるための概念的な方法は、付録Aで説明しています。

4.6. Addresses Require Attributes

4.6. アドレスには属性が必要

It is not mandatory in [RFC5444] to associate an address with attributes using Address Block TLVs. Information about an address could thus, in principle, be carried using:

[RFC5444]では、アドレスブロックTLVを使用してアドレスを属性に関連付けることは必須ではありません。したがって、原理的には、アドレスに関する情報を次のものを使って運ぶこともできます。

  • The simple presence of an address.
  • The ordering of addresses in an Address Block.
  • The use of different meanings for different Address Blocks.
  • アドレスが単に存在すること
  • アドレスブロック内のアドレスの順序
  • 異なるアドレスブロックに異なる意味を持たせること

This specification, however, requires that those methods of carrying information MUST NOT be used for any protocol using [RFC5444]. Information about the meaning of an address MUST only be carried using Address Block TLVs.

しかし、この仕様は次のことを要求します。[RFC5444]を使用するどのプロトコルでも、情報を運ぶこれらの方法を使用してはなりません（MUST NOT）。アドレスの意味に関する情報は、アドレスブロックTLVを使用してのみ運ばなければなりません（MUST）。

In addition, rules for the extensibility of OLSRv2 and NHDP are described in [RFC7188]. This specification extends their applicability to other uses of [RFC5444].

さらに、OLSRv2とNHDPの拡張性に関する規則が[RFC7188]に記述されています。この仕様は、それらの適用範囲を[RFC5444]のその他の使用法にも広げます。

These rules are:

それらの規則は次のとおりです。

  • A protocol MUST NOT assign any meaning to the presence or absence of an address (either in a Message or in a given Address Block in a Message), to the ordering of addresses in an Address Block, or to the division of addresses among Address Blocks.
  • A protocol MUST NOT reject a message based on the inclusion of a TLV of an unrecognized type. The protocol MUST ignore any such TLVs when processing the message. The protocol MUST NOT remove or change any such TLVs if the message is to be forwarded unchanged.
  • A protocol MUST NOT reject a message based on the inclusion of an unrecognized Value in a TLV of a recognized type. The protocol MUST ignore any such Values when processing the message but MUST NOT ignore recognized Values in such a TLV. The protocol MUST NOT remove or change any such TLVs if the message is to be forwarded unchanged.
  • Similar restrictions to the two preceding points apply to the demultiplexer, which also MUST NOT reject a packet based on an unrecognized message; although it will reject any such messages, it MUST deliver any other messages in the packet to their owning protocols.
  • プロトコルは、（メッセージ内、またはメッセージ内の特定のアドレスブロック内での）アドレスの有無、アドレスブロック内のアドレスの順序、またはアドレスブロック間でのアドレスの分割に、いかなる意味も割り当ててはなりません（MUST NOT）。
  • プロトコルは、認識できないタイプのTLVが含まれていることを理由にメッセージを拒否してはなりません（MUST NOT）。プロトコルは、メッセージを処理する際に、そのようなTLVをすべて無視しなければなりません（MUST）。メッセージを変更せずに転送する場合、プロトコルは、そのようなTLVを削除したり変更したりしてはなりません（MUST NOT）。
  • プロトコルは、認識できるタイプのTLVに認識できない値が含まれていることを理由にメッセージを拒否してはなりません（MUST NOT）。プロトコルは、メッセージを処理する際に、そのような値をすべて無視しなければなりません（MUST）。ただし、そのようなTLV内の認識できる値を無視してはなりません（MUST NOT）。メッセージを変更せずに転送する場合、プロトコルは、そのようなTLVを削除したり変更したりしてはなりません（MUST NOT）。
  • 前の2つの項目と同様の制限がデマルチプレクサーにも適用されます。デマルチプレクサーも、認識できないメッセージを理由にパケットを拒否してはなりません（MUST NOT）。デマルチプレクサーは、そのようなメッセージは拒否しますが、パケット内のその他のメッセージは、それらの所有プロトコルに配送しなければなりません（MUST）。

The following points indicate the reasons for these rules based on considerations of extensibility and efficiency.

以下の項目は、拡張性と効率性の考慮に基づいて、これらの規則の理由を示しています。

Assigning a meaning to the presence, absence, or location of an address would reduce the extensibility of the protocol, prevent the approach to information representation described in Appendix A, and reduce the options available for message optimization described in Section 6.

アドレスの存在、不在、または位置に意味を割り当てると、プロトコルの拡張性が低下し、付録Aで説明する情報表現のアプローチが妨げられ、セクション6で説明するメッセージ最適化に利用できる選択肢が減ってしまいます。

To consider how the simple presence of an address conveying information would have restricted the development of an extension, two examples are considered: one actual (included in the base specification, but which could have been added later) and one hypothetical.

アドレスが単に存在することで情報を伝える方式が、拡張の開発をどのように制限したであろうかを検討するために、2つの例を考えます。1つは実際の例（基本仕様に含まれていますが、後から追加することもできたもの）で、もう1つは仮想的な例です。

The basic function of NHDP's HELLO messages [RFC6130] is to indicate that addresses are of neighbors, using the LINK_STATUS and OTHER_NEIGHB TLVs. (The message can also indicate the router's own addresses, which could also serve as a further example.)

NHDPのHELLOメッセージ[RFC6130]の基本的な機能は、LINK_STATUS TLVとOTHER_NEIGHB TLVを使用して、アドレスが近隣のものであることを示すことです。（このメッセージはルーター自身のアドレスを示すこともでき、これもさらなる例として役立つでしょう。）

An extension to NHDP might decide to use the HELLO message to report that an address is one that could be used for a specialized purpose rather than for normal NHDP-based purposes. Such an example already exists in the use of LOST Values in the LINK_STATUS and OTHER_NEIGHB TLVs to report that an address is of a router known not to be a neighbor.

NHDPの拡張では、HELLOメッセージを使用して、あるアドレスが通常のNHDPベースの目的ではなく特別な目的に使用できるものであることを報告すると決めるかもしれません。そのような例はすでに存在しており、LINK_STATUS TLVとOTHER_NEIGHB TLVでLOST値を使用して、あるアドレスが近隣ではないことがわかっているルーターのものであることを報告しています。

A future example could be to indicate that an address is to be added to a "blacklist" of addresses not to be used. This would use a new TLV (or a new Value of an existing TLV, see below). If no other TLVs were attached to such a blacklisted address, then an unmodified implementation of NHDP would ignore that address, as required; if any other TLVs were attached to that address, then that implementation would process that address for those TLVs. Had NHDP been designed so that just the presence of an address indicated a neighbor, this blacklist extension would not be possible, as an unmodified implementation of NHDP would treat all blacklisted addresses as neighbors.

将来の例としては、あるアドレスを、使用してはならないアドレスの「ブラックリスト」に追加することを示すことが考えられます。これには、新しいTLV（または既存のTLVの新しい値。後述）を使用することになるでしょう。そのようにブラックリストに載せられたアドレスに他のTLVが付加されていなければ、変更されていないNHDPの実装は、要求されているとおりにそのアドレスを無視します。そのアドレスに他のTLVが付加されていれば、その実装はそれらのTLVのためにそのアドレスを処理します。もしNHDPが、アドレスが存在するだけで近隣を示すように設計されていたとしたら、変更されていないNHDPの実装はブラックリストに載せられたすべてのアドレスを近隣として扱ってしまうため、このブラックリスト拡張は不可能だったでしょう。

Rejecting a message because it contains an unrecognized TLV Type or an unrecognized TLV Value reduces the extensibility of the protocol.

認識できないTLVタイプや認識できないTLVの値を含むという理由でメッセージを拒否すると、プロトコルの拡張性が低下します。

For example, OLSRv2 [RFC7181] is, among other things, an extension to NHDP. It adds information to addresses in an NHDP HELLO message using a LINK_METRIC TLV. A non-OLSRv2 implementation of NHDP (for example, to support Simplified Multicast Flooding (SMF) [RFC6621]) will still process the HELLO message, ignoring the LINK_METRIC TLVs.

たとえば、OLSRv2 [RFC7181]は、とりわけNHDPの拡張です。OLSRv2は、LINK_METRIC TLVを使用して、NHDPのHELLOメッセージ内のアドレスに情報を追加します。OLSRv2ではないNHDPの実装（たとえば、簡易マルチキャストフラッディング（Simplified Multicast Flooding、SMF）[RFC6621]をサポートするための実装）も、LINK_METRIC TLVを無視して、HELLOメッセージを処理します。

Also, the blacklisting described in the example above could be signaled not with a new TLV but with a new Value of a LINK_STATUS or OTHER_NEIGHB TLV (requiring an IANA allocation as described in [RFC7188]), as is already done in the LOST case.

また、上の例で説明したブラックリスト化は、LOSTの場合にすでに行われているように、新しいTLVではなく、LINK_STATUS TLVまたはOTHER_NEIGHB TLVの新しい値（[RFC7188]で説明されているIANAの割り当てが必要です）によって通知することもできます。

The creation of Multi-Topology OLSRv2 (MT-OLSRv2) [RFC7722], as an extension to OLSRv2 that can interoperate with unextended instances of OLSRv2, would not have been possible without these restrictions (which were applied to NHDP and OLSRv2 by [RFC7188]).

拡張されていないOLSRv2のインスタンスと相互運用できるOLSRv2の拡張としてのマルチトポロジーOLSRv2（Multi-Topology OLSRv2、MT-OLSRv2）[RFC7722]の作成は、これらの制限（[RFC7188]によってNHDPとOLSRv2に適用されたもの）がなければ不可能だったでしょう。

These restrictions do not, however, mean that added information is completely ignored for purposes of the base protocol. Suppose that a faulty implementation of OLSRv2 (including NHDP) creates a HELLO message that assigns two different values of the same link metric to an address, something that is not permitted by [RFC7181]. A receiving OLSRv2-aware implementation of NHDP will reject such a message, even though a receiving OLSRv2-unaware implementation of NHDP will process it. This is because the OLSRv2-aware implementation has access to additional information (that the HELLO message is definitely invalid and the message is best ignored) as it is unknown what other errors it might contain.

しかし、これらの制限は、追加された情報が基本プロトコルの目的のために完全に無視されることを意味するものではありません。OLSRv2（NHDPを含む）の欠陥のある実装が、同じリンクメトリックの2つの異なる値をアドレスに割り当てるHELLOメッセージを作成したとします。これは[RFC7181]では許可されていません。受信側のOLSRv2を認識しないNHDPの実装はそのようなメッセージを処理しますが、受信側のOLSRv2を認識するNHDPの実装はそのメッセージを拒否します。これは、OLSRv2を認識する実装は追加の情報（そのHELLOメッセージが明らかに無効であり、他にどのようなエラーを含んでいるかわからないため、そのメッセージは無視するのが最善であること）にアクセスできるためです。

4.7. TLVs

4.7. TLV

Within a message, the attributes are represented by TLVs. Particularly for Address Block TLVs, different TLVs can represent the same information. For example, using the LINK_STATUS TLV defined in [RFC6130], if some addresses have Value SYMMETRIC and some have Value HEARD, arranged in that order, then this information can be represented using two single-value TLVs or one multivalue TLV. The latter can be used even if the addresses are not so ordered.

メッセージ内では、属性はTLVによって表現されます。特にアドレスブロックTLVについては、異なるTLVで同じ情報を表現できます。たとえば、[RFC6130]で定義されたLINK_STATUS TLVを使用する場合、いくつかのアドレスが値SYMMETRICを持ち、いくつかのアドレスが値HEARDを持ち、その順序で並んでいるなら、この情報は2つの単一値TLV（single-value TLV）または1つの複数値TLV（multivalue TLV）を使用して表現できます。後者は、アドレスがそのような順序で並んでいなくても使用できます。

A protocol MAY use any representation of information using TLVs that convey the required information. A protocol SHOULD use an efficient representation, but this is a quality of implementation issue. A protocol MUST recognize any permitted representation of the information; even if it chooses to, for example, only use multivalue TLVs, it MUST recognize single-value TLVs (and vice versa).

プロトコルは、必要な情報を伝えるTLVを使用した、任意の情報表現を使用してもよいです（MAY）。プロトコルは効率的な表現を使用すべきです（SHOULD）が、これは実装の品質の問題です。プロトコルは、許可されている任意の情報表現を認識しなければなりません（MUST）。たとえば、複数値TLVだけを使用することを選択したとしても、プロトコルは単一値TLVを認識しなければなりません（MUST）（逆の場合も同様です）。

A protocol defining new TLVs MUST respect the naming and organizational rules in [RFC7631]. It SHOULD follow the guidance in [RFC7188], see Section 6.3. (This specification does not, however, relax the application of [RFC7188] where it is mandated.)

新しいTLVを定義するプロトコルは、[RFC7631]の命名規則と構成規則を尊重しなければなりません（MUST）。また、[RFC7188]のガイダンスに従うべきです（SHOULD）。セクション6.3を参照してください。（ただし、この仕様は、[RFC7188]が義務付けられている場合にその適用を緩和するものではありません。）

4.8. Message Integrity

4.8. メッセージの完全性

In addition to not rejecting a message due to unknown TLVs or TLV Values, a protocol MUST NOT reject a message based on the inclusion of a TLV of an unrecognized type. The protocol MUST ignore any such TLVs when processing the message. The protocol MUST NOT remove or change any such TLVs if the message is to be forwarded unchanged. Such behavior may have the following consequences:

未知のTLVやTLVの値を理由にメッセージを拒否しないことに加えて、プロトコルは、認識できないタイプのTLVが含まれていることを理由にメッセージを拒否してはなりません（MUST NOT）。プロトコルは、メッセージを処理する際に、そのようなTLVをすべて無視しなければなりません（MUST）。メッセージを変更せずに転送する場合、プロトコルは、そのようなTLVを削除したり変更したりしてはなりません（MUST NOT）。そのような動作は、次のような結果をもたらす可能性があります。

  • It might disrupt the operation of an extension of which it is unaware. Note that it is the responsibility of a protocol extension to handle interoperation with unextended instances of the protocol. For example, OLSRv2 [RFC7181] adds an MPR_WILLING TLV to HELLO messages (created by NHDP [RFC6130], of which it is an extension) to recognize this case (and for other reasons).
  • It would prevent the operation of end-to-end message authentication using [RFC7182] or any similar mechanism. The use of immutable (apart from hop count and/or hop limit) messages by a protocol is strongly RECOMMENDED for that reason.
  • そのプロトコルが認識していない拡張の動作を妨げるかもしれません。拡張されていないプロトコルのインスタンスとの相互運用を扱うのは、プロトコル拡張の責任であることに注意してください。たとえば、OLSRv2 [RFC7181]は、このケースを認識するために（および他の理由のために）、（OLSRv2が拡張するNHDP [RFC6130]によって作成される）HELLOメッセージにMPR_WILLING TLVを追加します。
  • [RFC7182]または同様のメカニズムを使用したエンドツーエンドのメッセージ認証の動作が妨げられます。そのため、プロトコルが（ホップカウントまたはホップリミット（あるいはその両方）を除いて）不変のメッセージを使用することが強く推奨されます（RECOMMENDED）。

5. Structure

5. 構造

This section concerns the properties of the format defined in [RFC5444] itself, rather than the properties of protocols using it.

このセクションは、[RFC5444]で定義されたフォーマット自体の特性に関するものであり、それを使用するプロトコルの特性に関するものではありません。

The elements defined in [RFC5444] have structures that are managed by a number of flags fields:

[RFC5444]で定義された要素は、いくつかのフラグフィールドによって管理される構造を持っています。

  • Packet flags field (4 bits, 2 used) that manages the contents of the Packet Header.
  • Message flags field (4 bits, 4 used) that manages the contents of the Message Header.
  • Address Block flags field (8 bits, 4 used) that manages the contents of an Address Block.
  • TLV flags field (8 bits, 5 used) that manages the contents of a TLV.
  • パケットヘッダーの内容を管理するパケットフラグフィールド（4ビット、そのうち2ビットを使用）
  • メッセージヘッダーの内容を管理するメッセージフラグフィールド（4ビット、そのうち4ビットを使用）
  • アドレスブロックの内容を管理するアドレスブロックフラグフィールド（8ビット、そのうち4ビットを使用）
  • TLVの内容を管理するTLVフラグフィールド（8ビット、そのうち5ビットを使用）

Note that all of these flags are structural; they specify which elements are present or absent, field lengths, or whether a field has one or multiple values in it.

これらのフラグはすべて構造的なものであることに注意してください。これらのフラグは、どの要素が存在するか存在しないか、フィールドの長さ、またはフィールドが1つの値を持つか複数の値を持つかを指定します。

In the current version of [RFC5444], indicated by version number 0 in the <version> field of the Packet Header, unused bits in these flags fields are stated as "are RESERVED and SHOULD each be cleared ('0') on transmission and SHOULD be ignored on reception". For the avoidance of any compatibility issues, with regard to version number 0, this is updated to "MUST each be cleared ('0') on transmission and MUST be ignored on reception".

パケットヘッダーの<version>フィールドのバージョン番号0で示される[RFC5444]の現在のバージョンでは、これらのフラグフィールドの未使用ビットについて、「予約済み（RESERVED）であり、それぞれ送信時にクリア（'0'）されるべきです（SHOULD）。また、受信時には無視されるべきです（SHOULD）」と記述されています。互換性の問題を避けるため、バージョン番号0に関して、これを「それぞれ送信時にクリア（'0'）されなければなりません（MUST）。また、受信時には無視されなければなりません（MUST）」に更新します。

If a specification updating [RFC5444] introduces new flags in one of the flags fields of a packet, Address Block, or TLV (there being no unused flags in the message flags field), the following rules MUST be followed:

[RFC5444]を更新する仕様が、パケット、アドレスブロック、またはTLVのフラグフィールドのいずれかに新しいフラグを導入する場合（メッセージフラグフィールドには未使用のフラグはありません）、次の規則に従わなければなりません（MUST）。

  • The version number contained in the <version> field of the Packet Header MUST NOT be 0.
  • The new flag(s) MUST indicate the structure of the corresponding packet, Address Block, or TLV. They MUST NOT be used to indicate any other semantics, such as message forwarding behavior.
  • パケットヘッダーの<version>フィールドに含まれるバージョン番号は、0であってはなりません（MUST NOT）。
  • 新しいフラグは、対応するパケット、アドレスブロック、またはTLVの構造を示さなければなりません（MUST）。新しいフラグを、メッセージの転送動作など、その他のセマンティクスを示すために使用してはなりません（MUST NOT）。

An update that would be incompatible with the current specification of [RFC5444] SHOULD NOT be created unless there is a pressing reason for it that cannot be satisfied using the current specification (e.g., by use of a suitable Message TLV or Address Block TLV).

[RFC5444]の現在の仕様と互換性のない更新は、現在の仕様を使用して（たとえば、適切なメッセージTLVまたはアドレスブロックTLVを使用して）満たすことのできない差し迫った理由がない限り、作成されるべきではありません（SHOULD NOT）。

During the development of [RFC5444] (and since publication thereof), some proposals have been made to use these RESERVED flags to specify behavior rather than structure, message forwarding in particular. These proposals were, after due consideration, not accepted for a number of reasons. These reasons include that message forwarding, in particular, is protocol specific; for example, [RFC7181] forwards messages using its MPR mechanism rather than a "blind" flooding mechanism. (These proposals were made during the development of [RFC5444] when there were still unused message flags. Later addition of a 4-bit Message Address Length field later left no unused message flags, but other flags fields still have unused flags.)

[RFC5444]の策定中（およびその公開以降）に、これらの予約済み（RESERVED）フラグを使用して、構造ではなく動作、特にメッセージの転送を指定するという提案がいくつかなされました。これらの提案は、十分な検討の結果、いくつかの理由によって受け入れられませんでした。それらの理由には、特にメッセージの転送はプロトコル固有であることが含まれます。たとえば、[RFC7181]は、「ブラインド」フラッディングメカニズムではなく、そのMPRメカニズムを使用してメッセージを転送します。（これらの提案は、まだ未使用のメッセージフラグがあった[RFC5444]の策定中になされました。その後、4ビットのMessage Address Lengthフィールドが追加されたことで未使用のメッセージフラグはなくなりましたが、その他のフラグフィールドにはまだ未使用のフラグがあります。）

6. Message Efficiency

6. メッセージの効率

The ability to organize addresses into the same or different Address Blocks and to change the order of addresses within an Address Block (as well as the flexibility of the TLV specification) enables avoiding unnecessary repetition of information and can consequently generate smaller messages. There are no algorithms for address organization, compression, or for TLV usage in [RFC5444]; any algorithms that leave the information content unchanged MAY be used when generating a message. See also Appendix B.

アドレスを同じアドレスブロックまたは異なるアドレスブロックに編成し、アドレスブロック内のアドレスの順序を変更できること（およびTLV仕様の柔軟性）によって、情報の不必要な繰り返しを避けることができ、その結果、より小さなメッセージを生成できます。[RFC5444]には、アドレスの編成、圧縮、またはTLVの使用に関するアルゴリズムはありません。メッセージを生成する際には、情報の内容を変えない任意のアルゴリズムを使用してもよいです（MAY）。付録Bも参照してください。

6.1. Address Block Compression

6.1. アドレスブロックの圧縮

[RFC5444] allows the addresses in an Address Block to be compressed. A protocol generating a message SHOULD compress addresses as much as it can.

[RFC5444]では、アドレスブロック内のアドレスを圧縮できます。メッセージを生成するプロトコルは、アドレスを可能な限り圧縮すべきです（SHOULD）。

Addresses in an Address Block consist of a Head, a Mid, and a Tail, where all addresses in an Address Block have the same Head and Tail but different Mids. Each has a length that is greater than or equal to zero, the sum of the lengths being the address length. (The Mid length is deduced from this relationship.) Compression is possible when the Head and/or the Tail have non-zero length. An additional compression is possible when the Tail consists of all zero-valued octets. Expected use cases include IPv4 and IPv6 addresses from within the same prefix and that therefore have a common Head, IPv4 subnets with a common zero-valued Tail, and IPv6 addresses with a common Tail representing an interface identifier as well as having a possible common Head. Note that when, for example, IPv4 addresses have a common Head, their Tail will usually have length zero.

アドレスブロック内のアドレスは、ヘッド（Head）、ミッド（Mid）、テール（Tail）で構成されます。アドレスブロック内のすべてのアドレスは、同じヘッドとテールを持ち、異なるミッドを持ちます。それぞれの長さは0以上であり、それらの長さの合計がアドレス長になります。（ミッドの長さはこの関係から導き出されます。）圧縮は、ヘッドまたはテール（あるいはその両方）の長さが0でない場合に可能です。テールがすべて値0のオクテットで構成されている場合には、さらなる圧縮が可能です。想定される使用例には、同じプレフィックス内のものであるために共通のヘッドを持つIPv4アドレスやIPv6アドレス、共通の値0のテールを持つIPv4サブネット、およびインターフェイス識別子を表す共通のテールを持ち、共通のヘッドも持つ可能性のあるIPv6アドレスがあります。たとえば、IPv4アドレスが共通のヘッドを持つ場合、そのテールの長さは通常0になることに注意してください。

For example:

たとえば、次のようになります。

  • The IPv4 addresses 192.0.2.1 and 192.0.2.2 would, for greatest efficiency, have a 3-octet Head, a 1-octet Mid, and a 0-octet Tail.
  • The IPv6 addresses 2001:DB8:prefix1:interface and 2001:DB8:prefix2:interface that use the same interface identifier but completely different prefixes (except as noted) would, for greatest efficiency, have a 4-octet head, a 4-octet Mid, and an 8-octet Tail. (They could have a larger Head and/or Tail and a smaller Mid if the prefixes have any octets in common.)
  • IPv4アドレス192.0.2.1と192.0.2.2は、効率を最大にするには、3オクテットのヘッド、1オクテットのミッド、0オクテットのテールを持つことになります。
  • 同じインターフェイス識別子を使用するが、（記載されている部分を除いて）完全に異なるプレフィックスを持つIPv6アドレス2001:DB8:prefix1:interfaceと2001:DB8:prefix2:interfaceは、効率を最大にするには、4オクテットのヘッド、4オクテットのミッド、8オクテットのテールを持つことになります。（プレフィックスに共通のオクテットがあれば、より大きなヘッドまたはテール（あるいはその両方）と、より小さなミッドを持つことができます。）

Putting addresses into a message efficiently also requires consideration of the following:

アドレスをメッセージに効率的に入れるには、次のことも考慮する必要があります。

  • The split of the addresses into Address Blocks.
  • The order of the addresses within the Address Blocks.
  • アドレスブロックへのアドレスの分割
  • アドレスブロック内のアドレスの順序

This split and/or ordering is for efficiency only; it does not provide any information. The split of the addresses affects both the address compression and the TLV efficiency (see Section 6.2); the order of the addresses within an Address Block affects only the TLV efficiency. However, using more Address Blocks than needed can increase the message size due to the overhead of each Address Block and the following TLV Block, and/or if additional TLVs are now required.

この分割や順序付けは効率のためだけのものであり、何の情報も提供しません。アドレスの分割は、アドレスの圧縮とTLVの効率の両方に影響します（セクション6.2を参照）。アドレスブロック内のアドレスの順序は、TLVの効率にのみ影響します。ただし、必要以上に多くのアドレスブロックを使用すると、各アドレスブロックとそれに続くTLVブロックのオーバーヘッドによって、または追加のTLVが必要になる場合にはそれによって（あるいはその両方によって）、メッセージサイズが大きくなる可能性があります。

The order of addresses can be as simple as sorting the addresses, but if many addresses have the same TLV Types attached, it might be more useful to put these addresses together, either within the same Address Block as other addresses or in a separate Address Block. A separate Address Block might also improve address compression, for example, if more than one address form is used (such as from independent subnets). An example of the possible use of address ordering is a HELLO message from [RFC6130] that could be generated with local interface addresses first and neighbor addresses later. These could be in separate Address Blocks.

アドレスの順序付けは、アドレスをソートするだけの単純なものでもかまいませんが、多くのアドレスに同じTLVタイプが付加されている場合には、それらのアドレスを、他のアドレスと同じアドレスブロック内でまとめるか、別のアドレスブロックにまとめるほうが有用かもしれません。たとえば、複数の形式のアドレスが使用されている場合（独立したサブネットからのアドレスなど）には、別のアドレスブロックにすることでアドレスの圧縮も改善される可能性があります。アドレスの順序付けの使用例として考えられるのは、[RFC6130]のHELLOメッセージを、ローカルインターフェイスのアドレスを先に、近隣のアドレスを後にして生成することです。これらは別々のアドレスブロックに入れることもできます。

6.2. TLVs

6.2. TLV

When considering TLVs, the main opportunities for creating more efficient messages are in Address Block TLVs rather than Message TLVs. The approaches described here apply to each Address Block.

TLVについて考える場合、より効率的なメッセージを作成する主な機会は、メッセージTLVではなくアドレスブロックTLVにあります。ここで説明するアプローチは、各アドレスブロックに適用されます。

An Address Block TLV provides attributes for one address or a contiguous (as stored in the Address Block) set of addresses (with a special case for when this set is of all of the addresses in the Address Block). When associated with more than one address, a TLV can be single value (associating the same attribute with each address) or multivalue (associating a separate attribute with each address).

アドレスブロックTLVは、1つのアドレス、または（アドレスブロックに格納されている順序で）連続するアドレスの集合に対して属性を提供します（この集合がアドレスブロック内のすべてのアドレスである場合には特別なケースがあります）。複数のアドレスに関連付けられる場合、TLVは単一値（各アドレスに同じ属性を関連付けます）または複数値（各アドレスに別々の属性を関連付けます）にすることができます。

The approach that is simplest to implement is to use multivalue TLVs that cover all affected addresses. However, unless care is taken to order addresses appropriately, these affected addresses might not all be contiguous. Some approaches to this are the following:

最も実装が簡単なアプローチは、影響を受けるすべてのアドレスをカバーする複数値TLVを使用することです。しかし、アドレスを適切に順序付けるよう注意しない限り、影響を受けるこれらのアドレスがすべて連続しているとは限りません。これに対するいくつかのアプローチは次のとおりです。

  • Reorder the addresses. It is, for example, possible (though not straightforward, and beyond the scope of this document to describe exactly how) to order all addresses in HELLO message as specified in [RFC6130] so that all TLVs used only cover contiguous addresses. This is even possible if the MPR TLV specified in OLSRv2 [RFC7181] is added; but it is not possible, in general, if the LINK_METRIC TLV specified in OLSRv2 [RFC7181] is also added.
  • Allow the TLV to span over addresses that do not need the corresponding attribute and use a Value that indicates no information; see Section 6.3.
  • Use more than one TLV. Note that this can be efficient when the TLVs become single-value TLVs. In a typical case where a LINK_STATUS TLV uses only the Values HEARD and SYMMETRIC, with enough addresses sorted appropriately, two single-value TLVs can be more efficient than one multivalue TLV. If only one Value is involved (such as NHDP in a steady state with LINK_STATUS equal to SYMMETRIC in all cases) then one single-value TLV SHOULD always be used.
  • アドレスを並べ替えます。たとえば、使用されるすべてのTLVが連続するアドレスだけをカバーするように、[RFC6130]で規定されたHELLOメッセージ内のすべてのアドレスを順序付けることは可能です（ただし簡単ではなく、その方法を正確に説明することはこの文書の範囲外です）。これは、OLSRv2 [RFC7181]で規定されたMPR TLVが追加された場合でも可能です。しかし、OLSRv2 [RFC7181]で規定されたLINK_METRIC TLVも追加された場合には、一般に不可能です。
  • 対応する属性を必要としないアドレスにもTLVがまたがることを許可し、情報がないことを示す値を使用します。セクション6.3を参照してください。
  • 複数のTLVを使用します。これは、TLVが単一値TLVになる場合に効率的になり得ることに注意してください。LINK_STATUS TLVが値HEARDとSYMMETRICだけを使用する典型的なケースでは、十分な数のアドレスが適切にソートされていれば、2つの単一値TLVのほうが1つの複数値TLVよりも効率的になり得ます。1つの値だけが関係する場合（定常状態のNHDPで、すべてのケースでLINK_STATUSがSYMMETRICに等しい場合など）には、常に1つの単一値TLVが使用されるべきです（SHOULD）。

6.3. TLV Values

6.3. TLVの値

If, for example, an Address Block contains five addresses, the first two and the last two requiring Values assigned using a LINK_STATUS TLV but the third does not, then this can be indicated using two TLVs. It is, however, more efficient to do this with one multivalue LINK_STATUS TLV, assigning the third address the Value UNSPECIFIED (as defined in [RFC7188]). In general, use of UNSPECIFIED Values allows use of fewer TLVs and is thus often an efficiency gain; however, a long run of consecutive UNSPECIFIED Values (more than the overhead of a TLV) can make use of more TLVs more efficient.

たとえば、アドレスブロックに5つのアドレスが含まれており、最初の2つと最後の2つにはLINK_STATUS TLVを使用して割り当てる値が必要ですが、3番目には必要ない場合、これは2つのTLVを使用して示すことができます。しかし、1つの複数値LINK_STATUS TLVを使用し、3番目のアドレスに（[RFC7188]で定義された）値UNSPECIFIEDを割り当てるほうが効率的です。一般に、UNSPECIFIED値を使用すると使用するTLVの数を減らすことができるため、多くの場合効率の向上になります。ただし、連続するUNSPECIFIED値が長く続く（TLVのオーバーヘッドを超える）場合には、より多くのTLVを使用するほうが効率的になることがあります。

Some other TLVs might need a different approach. As noted in [RFC7188], but implicitly permissible before then, the LINK_METRIC TLV (defined in [RFC7181]) has two octet Values whose first four bits are flags indicating whether the metric applies in four cases; if these are all zero, then the metric does not apply in this case, which is thus the equivalent of an UNSPECIFIED Value.

他のいくつかのTLVでは、異なるアプローチが必要になるかもしれません。[RFC7188]で述べられているように（ただし、それ以前から暗黙的に許容されていました）、（[RFC7181]で定義された）LINK_METRIC TLVは2オクテットの値を持ち、その最初の4ビットは、4つのケースのそれぞれでメトリックが適用されるかどうかを示すフラグです。これらがすべて0の場合、メトリックはこのケースでは適用されず、したがってUNSPECIFIED値と同等になります。

[RFC7188] requires that protocols that extend [RFC6130] and [RFC7181] allow unspecified values in TLVs where applicable; it is here RECOMMENDED that all protocols follow that advice. In particular, it is RECOMMENDED that when defining an Address Block TLV with discrete Values, an UNSPECIFIED Value is defined with the same value (255), and a modified approach should be used where possible for other Address Block TLVs (for example, as is done for a LINK_METRIC TLV, though not necessarily using that exact approach).

[RFC7188]は、[RFC6130]と[RFC7181]を拡張するプロトコルに対して、該当する場合にはTLVで未指定の値を許可することを要求しています。ここでは、すべてのプロトコルがその助言に従うことが推奨されます（RECOMMENDED）。特に、離散的な値を持つアドレスブロックTLVを定義する際には、UNSPECIFIED値を同じ値（255）で定義することが推奨されます（RECOMMENDED）。また、その他のアドレスブロックTLVについては、可能であれば修正したアプローチを使用すべきです（たとえば、LINK_METRIC TLVで行われているようなアプローチですが、必ずしもまったく同じアプローチを使用する必要はありません）。

It might be argued that provision of an unspecified value (of any form) to allow an Address Block TLV to cover unaffected addresses is not always necessary because addresses can be reordered to avoid this. However, ordering addresses to avoid this for all TLVs that might be used is not, in general, possible.

アドレスを並べ替えればこれを避けられるため、アドレスブロックTLVが影響を受けないアドレスをカバーできるようにするための（何らかの形式の）未指定の値を用意することは必ずしも必要ではない、という議論もあるかもしれません。しかし、使用される可能性のあるすべてのTLVについてこれを避けるようにアドレスを順序付けることは、一般には不可能です。

In addition, [RFC7188] recommends that if a TLV Value (per address for an Address Block TLV) has a single-length that does not match the defined length for that TLV Type, then the following rules are adopted:

さらに、[RFC7188]は、TLVの値（アドレスブロックTLVの場合はアドレスごとの値）の単一長（single-length）が、そのTLVタイプで定義された長さと一致しない場合には、次の規則を採用することを推奨しています。

  • If the received single-length is greater than the expected single length, then the excess octets MUST be ignored.
  • If the received single-length is less than the expected single length, then the absent octets MUST be considered to have all bits cleared (0).
  • 受信した単一長が期待される単一長よりも大きい場合、超過したオクテットは無視されなければなりません（MUST）。
  • 受信した単一長が期待される単一長よりも小さい場合、欠けているオクテットは、すべてのビットがクリア（0）されているものとみなされなければなりません（MUST）。

This specification RECOMMENDS a similar rule for all protocols defining new TLVs.

この仕様は、新しいTLVを定義するすべてのプロトコルに対して、同様の規則を推奨します。

7. Security Considerations

7. セキュリティーに関する考慮事項

This document does not specify a protocol but provides rules and recommendations for how to design protocols using [RFC5444], whose security considerations apply.

この文書はプロトコルを規定するものではなく、[RFC5444]を使用するプロトコルをどのように設計するかについての規則と推奨事項を提供するものであり、そのRFCのセキュリティーに関する考慮事項が適用されます。

If the recommendation from Section 4.4.1 is followed, which specifies that messages are not modified (except for hop count and hop limit) when forwarded, then the security framework for [RFC5444] (specified in [RFC7182]) can be used in full. If that recommendation is not followed, then the Packet TLVs from [RFC7182] can be used, but the Message TLVs from [RFC7182] cannot be used as intended.

転送時にメッセージを（ホップカウントとホップリミットを除いて）変更しないことを規定するセクション4.4.1の推奨事項に従う場合、（[RFC7182]で規定された）[RFC5444]のセキュリティーフレームワークを完全に使用できます。その推奨事項に従わない場合、[RFC7182]のパケットTLVは使用できますが、[RFC7182]のメッセージTLVは意図したとおりには使用できません。

In either case, a protocol using [RFC5444] MUST document whether it is using [RFC7182] and if so, how.

いずれの場合も、[RFC5444]を使用するプロトコルは、[RFC7182]を使用しているかどうか、および使用している場合はその方法を文書化しなければなりません（MUST）。

Appendix A. Information Representation

付録A. 情報の表現

This section describes a conceptual way to consider the information in a message. It can be used as the basis of an approach to parsing a message from the information that it contains and to creating a message from the information that it is to contain. However, there is no requirement that a protocol does so. This approach can be used either to inform a protocol design or by a protocol (or generic parser) implementer.

このセクションでは、メッセージ内の情報を考えるための概念的な方法を説明します。これは、メッセージに含まれる情報からメッセージを解析したり、メッセージに含める情報からメッセージを作成したりするアプローチの基礎として使用できます。ただし、プロトコルがそうすることは要求されていません。このアプローチは、プロトコル設計に役立てるために使用することも、プロトコル（または汎用パーサー）の実装者が使用することもできます。

A message (excluding the Message Header) can be represented by two, possibly multivalued, maps:

メッセージ（メッセージヘッダーを除く）は、複数の値を持つ可能性のある2つのマップで表現できます。

  • Message: (Full Type) -> (length, Value)
  • Address: (address, Full Type) -> (length, Value)
  • メッセージ：（フルタイプ）->（長さ、値）
  • アドレス：（アドレス、フルタイプ）->（長さ、値）

These maps (plus a representation of the Message Header) can be the basis for a generic representation of information in a message. Such maps can be created by parsing the message or can be constructed using the protocol rules for creating a message and later converted into the octet form of the message specified in [RFC5444].

これらのマップ（とメッセージヘッダーの表現）は、メッセージ内の情報の汎用的な表現の基礎となり得ます。このようなマップは、メッセージを解析することによって作成することも、メッセージを作成するためのプロトコルの規則を使用して構築し、後で[RFC5444]で規定されたメッセージのオクテット形式に変換することもできます。

While of course any implementation of software that represents software in the above form can specify an Application Programming Interface (API) for that software, such an interface is not proposed here. First, a full API would be specific to a programming language. Second, even within the above framework, there are alternative approaches to such an interface. For example, and for illustrative purposes only, consider the alternative address mappings:

もちろん、上記の形式でソフトウェアを表現するソフトウェアの実装は、そのソフトウェアのアプリケーションプログラミングインターフェイス（Application Programming Interface、API）を規定できますが、ここではそのようなインターフェイスは提案しません。第一に、完全なAPIはプログラミング言語に固有のものになります。第二に、上記の枠組みの中でさえ、そのようなインターフェイスには複数の代替のアプローチがあります。たとえば、説明のためだけに、次のような代替のアドレスのマッピングを考えてみます。

  • Input: address and Full Type. Output: list of (length, Value) pairs. Note that for most Full Types, it will be known in advance that this list will have a length of zero or one. The list of addresses that can be used as inputs with non-empty output would need to be provided as a separate output.
  • Input: Full Type. Output: list of (address, length, Value) triples. As this list length can be significant, a possible output will be of one or two iterators that will allow iterating through that list. (One iterator that can detect the end of the list or a pair of iterators specifying a range.)
  • 入力：アドレスとフルタイプ。出力：（長さ、値）のペアのリスト。ほとんどのフルタイプでは、このリストの長さが0または1であることが事前にわかっていることに注意してください。空でない出力が得られる入力として使用できるアドレスのリストは、別の出力として提供する必要があるでしょう。
  • 入力：フルタイプ。出力：（アドレス、長さ、値）の3つ組のリスト。このリストの長さは大きくなり得るため、考えられる出力は、そのリストを反復処理できる1つまたは2つのイテレーターです。（リストの終わりを検出できる1つのイテレーター、または範囲を指定する1組のイテレーターです。）

Additional differences in the interface might relate to, for example, the ordering of output lists.

インターフェイスのその他の違いは、たとえば出力リストの順序に関係するかもしれません。

Appendix B. Automation

付録B. 自動化

There is scope for creating a protocol-independent optimizer for [RFC5444] messages that performs appropriate address re-organization (ordering and Address Block separation) and TLV changes (of number, of being single value or multivalue, and use of unspecified values) to create more compact messages. The possible gain depends on the efficiency of the original message creation and the specific details of the message. Note that this process cannot be TLV Type independent; for example, a LINK_METRIC TLV has a more complicated Value structure than a LINK_STATUS TLV does if using UNSPECIFIED Values.

より小さなメッセージを作成するために、適切なアドレスの再編成（順序付けとアドレスブロックの分離）とTLVの変更（数、単一値か複数値か、および未指定の値の使用）を行う、プロトコルに依存しない[RFC5444]メッセージの最適化器を作成する余地があります。得られる可能性のある利得は、元のメッセージ作成の効率とメッセージの具体的な詳細に依存します。このプロセスはTLVタイプに依存せずに行うことはできないことに注意してください。たとえば、UNSPECIFIED値を使用する場合、LINK_METRIC TLVはLINK_STATUS TLVよりも複雑な値の構造を持っています。

Such a protocol-independent optimizer MAY be used by the router generating a message but MUST NOT be used on a message that is forwarded unchanged by a router.

そのようなプロトコルに依存しない最適化器は、メッセージを生成するルーターが使用してもよいです（MAY）。ただし、ルーターが変更せずに転送するメッセージに対して使用してはなりません（MUST NOT）。
