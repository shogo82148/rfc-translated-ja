RFC 8405

Shortest Path First (SPF) Back-Off Delay Algorithm for Link-State IGPs

RFC 8405

リンクステートIGPのための最短パス優先（SPF）バックオフ遅延アルゴリズム

Abstract

概要

This document defines a standard algorithm to temporarily postpone or "back off" link-state IGP Shortest Path First (SPF) computations. This reduces the computational load and churn on IGP nodes when multiple temporally close network events trigger multiple SPF computations.

この文書は、リンクステートIGPの最短パス優先（SPF）計算を一時的に延期する、つまり「バックオフ」するための標準アルゴリズムを定義します。これにより、時間的に近接した複数のネットワークイベントが複数のSPF計算を引き起こす場合に、IGPノードの計算負荷と変動（churn）が軽減されます。

Having one standard algorithm improves interoperability by reducing the probability and/or duration of transient forwarding loops during the IGP convergence when the IGP reacts to multiple temporally close IGP events.

標準アルゴリズムを1つに定めることで、IGPが時間的に近接した複数のIGPイベントに反応する際に、IGPの収束中に発生する一時的な転送ループの確率や継続時間、あるいはその両方が減少し、相互運用性が向上します。

1. Introduction

1. はじめに

Link-state IGPs, such as IS-IS [ISO10589], OSPF [RFC2328], and OSPFv3 [RFC5340], perform distributed route computation on all routers in the area/level. In order to have consistent routing tables across the network, such distributed computation requires that all routers have the same version of the network topology (Link-State Database (LSDB)) and perform their computation essentially at the same time.

IS-IS [ISO10589]、OSPF [RFC2328]、OSPFv3 [RFC5340]などのリンクステートIGPは、エリア/レベル内のすべてのルーターで分散型の経路計算を行います。ネットワーク全体で一貫したルーティングテーブルを得るために、このような分散計算では、すべてのルーターが同じバージョンのネットワークトポロジー（リンクステートデータベース（LSDB））を持ち、本質的に同時に計算を行う必要があります。

In general, when the network is stable, there is a desire to trigger a new Shortest Path First (SPF) computation as soon as a failure is detected in order to quickly route around the failure. However, when the network is experiencing multiple failures over a short period of time, there is a conflicting desire to limit the frequency of SPF computations, which would allow a reduction in control plane resources used by IGPs and all protocols/subsystems reacting to the attendant route change, such as LDP [RFC5036], RSVP-TE [RFC3209], BGP [RFC4271], Fast Reroute computations (e.g., Loop-Free Alternates (LFAs) [RFC5286]), FIB updates, etc. This also reduces network churn and, in particular, reduces side effects (such as micro-loops [RFC5715]) that ensue during IGP convergence.

一般に、ネットワークが安定しているときは、障害を素早く迂回してルーティングするために、障害が検出されたらすぐに新しい最短パス優先（SPF）計算を開始することが望まれます。しかし、ネットワークが短期間に複数の障害を経験している場合には、SPF計算の頻度を制限したいという相反する要望があります。これにより、IGPと、それに伴う経路変更に反応するすべてのプロトコルやサブシステム（LDP [RFC5036]、RSVP-TE [RFC3209]、BGP [RFC4271]、高速リルートの計算（たとえば、ループフリー代替経路（LFA）[RFC5286]）、FIBの更新など）が使用するコントロールプレーンのリソースを削減できます。また、ネットワークの変動も軽減され、特に、IGPの収束中に生じる副作用（マイクロループ[RFC5715]など）が軽減されます。

To allow for this, IGPs usually implement an SPF Back-Off Delay algorithm that postpones or backs off the SPF computation. However, different implementations chose different algorithms. Hence, in a multi-vendor network, it's not possible to ensure that all routers trigger their SPF computation after the same delay. This situation increases the average and maximum differential delay between routers completing their SPF computation. It also increases the probability that different routers compute their FIBs based on different LSDB versions. Both factors increase the probability and/or duration of micro-loops as discussed in Section 8.

これを可能にするために、IGPは通常、SPF計算を延期する、つまりバックオフするSPFバックオフ遅延アルゴリズムを実装しています。しかし、実装ごとに異なるアルゴリズムが選択されてきました。そのため、マルチベンダーネットワークでは、すべてのルーターが同じ遅延の後にSPF計算を開始することを保証できません。この状況は、SPF計算を完了するルーター間の遅延の差の平均値と最大値を増大させます。また、異なるルーターが異なるバージョンのLSDBに基づいてFIBを計算する確率も高くなります。セクション8で説明するように、これらの要因はいずれも、マイクロループの確率や継続時間、あるいはその両方を増大させます。

This document specifies a standard algorithm to allow multi-vendor networks to have all routers delay their SPF computations for the same duration.

この文書は、マルチベンダーネットワークにおいて、すべてのルーターがSPF計算を同じ時間だけ遅延させられるようにするための標準アルゴリズムを規定します。

2. High-Level Goals

2. 高レベルの目標

The high-level goals of this algorithm are the following:

このアルゴリズムの高レベルの目標は次のとおりです。

  • very fast convergence for a single event (e.g., link failure),
  • paced fast convergence for multiple temporally close IGP events while IGP stability is considered acceptable,
  • delayed convergence when IGP stability is problematic (this will allow the IGP and related processes to conserve resources during the period of instability), and
  • avoidance of having different SPF_DELAY timer values (Section 3) across different routers in the area/level. This requires specific consideration as different routers may receive IGP messages at different intervals, or even in different orders, due to differences both in the distance from the originator of the IGP event and in flooding implementations.
  • 単一のイベント（たとえば、リンク障害）に対する非常に高速な収束
  • IGPの安定性が許容範囲内と考えられる間の、時間的に近接した複数のIGPイベントに対する、ペースを調整した高速な収束
  • IGPの安定性に問題がある場合の、遅延させた収束（これにより、IGPと関連するプロセスは、不安定な期間中にリソースを節約できます）
  • エリア/レベル内の異なるルーター間で、SPF_DELAYタイマーの値（セクション3）が異なる状況の回避。異なるルーターは、IGPイベントの発信元からの距離とフラッディングの実装の両方の違いにより、IGPメッセージを異なる間隔で、あるいは異なる順序で受信することがあるため、この目標には特別な考慮が必要です。

3. Definitions and Parameters

3. 定義とパラメーター

IGP event:
The reception or origination of an IGP LSDB change requiring a new routing table computation. Some examples are a topology change, a prefix change, and a metric change on a link or prefix. Note that locally triggering a routing table computation is not considered an IGP event since other IGP routers are unaware of this occurrence.
IGPイベント：
新しいルーティングテーブルの計算を必要とするIGP LSDBの変更の受信または発信。例として、トポロジーの変更、プレフィックスの変更、リンクまたはプレフィックスのメトリックの変更があります。ローカルでルーティングテーブルの計算を開始することは、ほかのIGPルーターがその発生を知らないため、IGPイベントとはみなされないことに注意してください。

Routing table computation, in this document, is scoped to the IGP; so, this is the computation of the IGP RIB, performed by the IGP, using the IGP LSDB. No distinction is made between the type of computation performed, e.g., full SPF, incremental SPF, or Partial Route Computation (PRC); the type of computation is a local consideration. This document may interchangeably use the terms "routing table computation" and "SPF computation".

この文書におけるルーティングテーブルの計算は、IGPの範囲に限定されます。つまり、IGPがIGP LSDBを使用して行う、IGP RIBの計算のことです。実行される計算の種類（たとえば、完全なSPF、増分SPF、部分経路計算（PRC））は区別しません。計算の種類はローカルで決めることです。この文書では、「ルーティングテーブルの計算（routing table computation）」と「SPF計算（SPF computation）」という用語を区別せずに使うことがあります。

SPF_DELAY:

The delay between the first IGP event triggering a new routing table computation and the start of that routing table computation. It can take the following values:

INITIAL_SPF_DELAY:
A very small delay to quickly handle a single isolated link failure, e.g., 0 milliseconds.
SHORT_SPF_DELAY:
A small delay to provide fast convergence in the case of a single component failure (such as a node failure or Shared Risk Link Group (SRLG) failure) that leads to multiple IGP events, e.g., 50-100 milliseconds.
LONG_SPF_DELAY:
A long delay when the IGP is unstable, e.g., 2 seconds. Note that this allows the IGP network to stabilize.
TIME_TO_LEARN_INTERVAL:
This is the maximum duration typically needed to learn all the IGP events related to a single component failure (such as router failure or SRLG failure), e.g., 1 second. It's mostly dependent on failure detection time variation between all routers that are adjacent to the failure. Additionally, it may depend on the different IGP implementations/parameters across the network and their relation to the origination and flooding of link state advertisements.
HOLDDOWN_INTERVAL:
The time required with no received IGP event before considering the IGP to be stable again and allowing the SPF_DELAY to be restored to INITIAL_SPF_DELAY, e.g., a HOLDDOWN_INTERVAL of 3 seconds. The HOLDDOWN_INTERVAL MUST be defaulted or configured to be longer than the TIME_TO_LEARN_INTERVAL.
SPF_DELAY:

新しいルーティングテーブルの計算を引き起こす最初のIGPイベントから、そのルーティングテーブルの計算を開始するまでの遅延。次の値をとることができます。

INITIAL_SPF_DELAY:
単一の孤立したリンク障害を素早く処理するための非常に小さな遅延。たとえば、0ミリ秒です。
SHORT_SPF_DELAY:
複数のIGPイベントにつながる単一のコンポーネント障害（ノード障害や共有リスクリンクグループ（SRLG）障害など）の場合に、高速な収束を実現するための小さな遅延。たとえば、50～100ミリ秒です。
LONG_SPF_DELAY:
IGPが不安定な場合の長い遅延。たとえば、2秒です。これにより、IGPネットワークが安定できることに注意してください。
TIME_TO_LEARN_INTERVAL:
単一のコンポーネント障害（ルーター障害やSRLG障害など）に関連するすべてのIGPイベントを把握するのに通常必要となる最大の時間です。たとえば、1秒です。これは主に、障害に隣接するすべてのルーター間での障害検出時間のばらつきに依存します。さらに、ネットワーク全体での異なるIGPの実装やパラメーターと、それらがリンクステート広告の発信やフラッディングにどう関係するかにも依存する場合があります。
HOLDDOWN_INTERVAL:
IGPが再び安定したとみなし、SPF_DELAYをINITIAL_SPF_DELAYに戻すまでに必要な、IGPイベントを受信しない時間。たとえば、3秒のHOLDDOWN_INTERVALです。HOLDDOWN_INTERVALは、デフォルト値または設定値がTIME_TO_LEARN_INTERVALより長くなければなりません（MUST）。

4. Principles of the SPF Delay Algorithm

4. SPF遅延アルゴリズムの原則

For the first IGP event, we assume that there has been a single simple change in the network, which can be taken into account using a single routing computation (e.g., link failure, prefix (metric) change), and we optimize for very fast convergence by delaying the initial routing computation for a small interval, INITIAL_SPF_DELAY. Under this assumption, there is no benefit in delaying the routing computation. In a typical network, this is the most common type of IGP event. Hence, it makes sense to optimize this case.

最初のIGPイベントについては、ネットワークで単一の単純な変更が発生し、それが1回のルーティング計算で反映できるもの（たとえば、リンク障害、プレフィックス（メトリック）の変更）であると仮定し、最初のルーティング計算を小さな間隔INITIAL_SPF_DELAYだけ遅延させることで、非常に高速な収束を目指して最適化します。この仮定のもとでは、ルーティング計算を遅延させても利点はありません。一般的なネットワークでは、これが最もよくある種類のIGPイベントです。したがって、この場合を最適化することには意味があります。

If subsequent IGP events are received in a short period of time (TIME_TO_LEARN_INTERVAL), we then assume that a single component failed, but that this failure requires the knowledge of multiple IGP events in order for IGP routing to converge. Under this assumption, we want fast convergence since this is a normal network situation. However, there is a benefit in waiting for all IGP events related to this single component failure: the IGP can then compute the post-failure routing table in a single additional route computation. In this situation, we delay the routing computation by SHORT_SPF_DELAY.

後続のIGPイベントが短期間（TIME_TO_LEARN_INTERVAL）に受信された場合は、単一のコンポーネントに障害が発生したものの、IGPルーティングが収束するには複数のIGPイベントを把握する必要がある障害だと仮定します。この仮定のもとでは、これは通常のネットワークの状況なので、高速な収束が望まれます。しかし、この単一のコンポーネント障害に関連するすべてのIGPイベントを待つことには利点があります。そうすれば、IGPは障害後のルーティングテーブルを1回の追加の経路計算で計算できるからです。この状況では、ルーティング計算をSHORT_SPF_DELAYだけ遅延させます。

If IGP events are still received after TIME_TO_LEARN_INTERVAL from the initial IGP event received in QUIET state (see Section 5.1), then the network is presumably experiencing multiple independent failures. In this case, while waiting for network stability, the computations are delayed for a longer time, which is represented by LONG_SPF_DELAY. This SPF delay is used until no IGP events are received for HOLDDOWN_INTERVAL.

QUIET状態で受信した最初のIGPイベントからTIME_TO_LEARN_INTERVALが経過した後もIGPイベントを受信し続けている場合（セクション5.1を参照）、ネットワークでは複数の独立した障害が発生していると推定されます。この場合、ネットワークが安定するのを待つ間、計算はより長い時間遅延されます。この時間をLONG_SPF_DELAYで表します。このSPF遅延は、HOLDDOWN_INTERVALの間IGPイベントを受信しなくなるまで使用されます。

Note that in order to increase the consistency network wide, the algorithm uses a delay (TIME_TO_LEARN_INTERVAL) from the initial IGP event rather than the number of SPF computations performed. Indeed, as all routers may receive the IGP events at different times, we cannot assume that all routers will perform the same number of SPF computations. For example, assuming that the SPF delay is 50 milliseconds, router R1 may receive three IGP events (E1, E2, E3) in those 50 milliseconds and hence will perform a single routing computation, while another router R2 may only receive two events (E1, E2) in those 50 milliseconds and hence will schedule another routing computation when receiving E3.

ネットワーク全体での一貫性を高めるために、このアルゴリズムは、実行したSPF計算の回数ではなく、最初のIGPイベントからの遅延（TIME_TO_LEARN_INTERVAL）を使用することに注意してください。実際、すべてのルーターがIGPイベントを異なるタイミングで受信する可能性があるため、すべてのルーターが同じ回数のSPF計算を行うとは仮定できません。たとえば、SPF遅延が50ミリ秒であると仮定すると、ルーターR1はその50ミリ秒の間に3つのIGPイベント（E1、E2、E3）を受信し、その結果1回のルーティング計算を行う一方で、別のルーターR2はその50ミリ秒の間に2つのイベント（E1、E2）しか受信せず、その結果E3を受信したときに別のルーティング計算をスケジュールする場合があります。

5. Specification of the SPF Delay State Machine

5. SPF遅延状態機械の仕様

This section specifies the Finite State Machine (FSM) intended to control the timing of the execution of SPF calculations in response to IGP events.

このセクションでは、IGPイベントに応じてSPF計算を実行するタイミングを制御するための有限状態機械（FSM）を規定します。

5.1. State Machine

5.1. 状態機械

The FSM is initialized to the QUIET state with all three timers (SPF_TIMER, HOLDDOWN_TIMER, and LEARN_TIMER) deactivated.

FSMは、3つのタイマー（SPF_TIMER、HOLDDOWN_TIMER、LEARN_TIMER）がすべて非アクティブの状態で、QUIET状態に初期化されます。

The events that may change the FSM states are an IGP event or the expiration of one timer (SPF_TIMER, HOLDDOWN_TIMER, or LEARN_TIMER).

FSMの状態を変更する可能性のあるイベントは、IGPイベントか、いずれかのタイマー（SPF_TIMER、HOLDDOWN_TIMER、LEARN_TIMER）の満了です。

次の図は、状態遷移を簡潔に示しています。

5.2. States

5.2. 状態

The naming and semantics of each state corresponds directly to the SPF delay used for IGP events received in that state. Three states are defined:

各状態の名前とセマンティクスは、その状態で受信したIGPイベントに対して使用するSPF遅延に直接対応しています。次の3つの状態を定義します。

QUIET:
This is the initial state, when no IGP events have occurred for at least HOLDDOWN_INTERVAL since the last routing table computation. The state is meant to handle link failures very quickly.
SHORT_WAIT:
This is the state entered when an IGP event has been received in QUIET state. This state is meant to handle a single component failure requiring multiple IGP events (e.g., node, SRLG).
LONG_WAIT:
This is the state reached after TIME_TO_LEARN_INTERVAL in state SHORT_WAIT. This state is meant to handle multiple independent component failures during periods of IGP instability.
QUIET:
これは初期状態であり、最後のルーティングテーブルの計算から少なくともHOLDDOWN_INTERVALの間、IGPイベントが発生していない状態です。この状態は、リンク障害を非常に素早く処理することを目的としています。
SHORT_WAIT:
これは、QUIET状態でIGPイベントを受信したときに遷移する状態です。この状態は、複数のIGPイベントを必要とする単一のコンポーネント障害（たとえば、ノード、SRLG）を処理することを目的としています。
LONG_WAIT:
これは、SHORT_WAIT状態でTIME_TO_LEARN_INTERVALが経過した後に到達する状態です。この状態は、IGPが不安定な期間中に発生する、複数の独立したコンポーネント障害を処理することを目的としています。

5.3. Timers

5.3. タイマー

SPF_TIMER:
This is the FSM timer that uses the computed SPF delay. Upon expiration, the routing table computation (as defined in Section 3) is performed.
HOLDDOWN_TIMER:
This is the FSM timer that is (re)started when an IGP event is received and set to HOLDDOWN_INTERVAL. Upon expiration, the FSM is moved to the QUIET state.
LEARN_TIMER:
This is the FSM timer that is started when an IGP event is received while the FSM is in the QUIET state. Upon expiration, the FSM is moved to the LONG_WAIT state.
SPF_TIMER:
これは、計算されたSPF遅延を使用するFSMのタイマーです。満了すると、ルーティングテーブルの計算（セクション3で定義）が実行されます。
HOLDDOWN_TIMER:
これは、IGPイベントを受信したときに（再）開始され、HOLDDOWN_INTERVALに設定されるFSMのタイマーです。満了すると、FSMはQUIET状態に移行します。
LEARN_TIMER:
これは、FSMがQUIET状態にあるときにIGPイベントを受信すると開始されるFSMのタイマーです。満了すると、FSMはLONG_WAIT状態に移行します。

5.4. FSM Events

5.4. FSMイベント

This section describes the events and the actions performed in response.

このセクションでは、イベントと、それに応じて実行されるアクションを説明します。

Transition 1: IGP event while in QUIET state

遷移1：QUIET状態でのIGPイベント

Actions on event 1:

イベント1に対するアクション：

  • If SPF_TIMER is not already running, start it with value INITIAL_SPF_DELAY.
  • Start LEARN_TIMER with TIME_TO_LEARN_INTERVAL.
  • Start HOLDDOWN_TIMER with HOLDDOWN_INTERVAL.
  • Transition to SHORT_WAIT state.
  • SPF_TIMERがまだ動作していない場合は、値INITIAL_SPF_DELAYで開始します。
  • LEARN_TIMERをTIME_TO_LEARN_INTERVALで開始します。
  • HOLDDOWN_TIMERをHOLDDOWN_INTERVALで開始します。
  • SHORT_WAIT状態に遷移します。

Transition 2: IGP event while in SHORT_WAIT

遷移2：SHORT_WAITでのIGPイベント

Actions on event 2:

イベント2に対するアクション：

  • Reset HOLDDOWN_TIMER to HOLDDOWN_INTERVAL.
  • If SPF_TIMER is not already running, start it with value SHORT_SPF_DELAY.
  • Remain in current state.
  • HOLDDOWN_TIMERをHOLDDOWN_INTERVALにリセットします。
  • SPF_TIMERがまだ動作していない場合は、値SHORT_SPF_DELAYで開始します。
  • 現在の状態にとどまります。

Transition 3: LEARN_TIMER expiration

遷移3：LEARN_TIMERの満了

Actions on event 3:

イベント3に対するアクション：

  • Transition to LONG_WAIT state.
  • LONG_WAIT状態に遷移します。

Transition 4: IGP event while in LONG_WAIT

遷移4：LONG_WAITでのIGPイベント

Actions on event 4:

イベント4に対するアクション：

  • Reset HOLDDOWN_TIMER to HOLDDOWN_INTERVAL.
  • If SPF_TIMER is not already running, start it with value LONG_SPF_DELAY.
  • Remain in current state.
  • HOLDDOWN_TIMERをHOLDDOWN_INTERVALにリセットします。
  • SPF_TIMERがまだ動作していない場合は、値LONG_SPF_DELAYで開始します。
  • 現在の状態にとどまります。

Transition 5: HOLDDOWN_TIMER expiration while in LONG_WAIT

遷移5：LONG_WAITでのHOLDDOWN_TIMERの満了

Actions on event 5:

イベント5に対するアクション：

  • Transition to QUIET state.
  • QUIET状態に遷移します。

Transition 6: HOLDDOWN_TIMER expiration while in SHORT_WAIT

遷移6：SHORT_WAITでのHOLDDOWN_TIMERの満了

Actions on event 6:

イベント6に対するアクション：

  • Deactivate LEARN_TIMER.
  • Transition to QUIET state.
  • LEARN_TIMERを非アクティブにします。
  • QUIET状態に遷移します。

Transition 7: SPF_TIMER expiration while in QUIET

遷移7：QUIETでのSPF_TIMERの満了

Actions on event 7:

イベント7に対するアクション：

  • Compute SPF.
  • Remain in current state.
  • SPFを計算します。
  • 現在の状態にとどまります。

Transition 8: SPF_TIMER expiration while in SHORT_WAIT

遷移8：SHORT_WAITでのSPF_TIMERの満了

Actions on event 8:

イベント8に対するアクション：

  • Compute SPF.
  • Remain in current state.
  • SPFを計算します。
  • 現在の状態にとどまります。

Transition 9: SPF_TIMER expiration while in LONG_WAIT

遷移9：LONG_WAITでのSPF_TIMERの満了

Actions on event 9:

イベント9に対するアクション：

  • Compute SPF.
  • Remain in current state.
  • SPFを計算します。
  • 現在の状態にとどまります。

6. Parameters

6. パラメーター

All the parameters MUST be configurable at the protocol instance level. They MAY be configurable on a per IGP LSDB basis (e.g., IS-IS level, OSPF area, or IS-IS Level 1 area). All the delays (INITIAL_SPF_DELAY, SHORT_SPF_DELAY, LONG_SPF_DELAY, TIME_TO_LEARN_INTERVAL, and HOLDDOWN_INTERVAL) SHOULD be configurable with a granularity of a millisecond. They MUST be configurable with a granularity of at least a tenth of a second. The configurable range for all the parameters SHOULD be from 0 milliseconds to at least 6000 milliseconds. The HOLDDOWN_INTERVAL MUST be defaulted or configured to be longer than the TIME_TO_LEARN_INTERVAL.

すべてのパラメーターは、プロトコルインスタンスのレベルで設定可能でなければなりません（MUST）。IGP LSDBごと（たとえば、IS-ISのレベル、OSPFのエリア、IS-ISのレベル1エリア）に設定可能であってもよいです（MAY）。すべての遅延（INITIAL_SPF_DELAY、SHORT_SPF_DELAY、LONG_SPF_DELAY、TIME_TO_LEARN_INTERVAL、HOLDDOWN_INTERVAL）は、1ミリ秒の粒度で設定可能であるべきです（SHOULD）。これらは、0.1秒（100ミリ秒）以下の刻み幅で設定可能でなければなりません（MUST）。すべてのパラメーターの設定可能な範囲は、0ミリ秒から少なくとも6000ミリ秒までであるべきです（SHOULD）。HOLDDOWN_INTERVALは、デフォルト値または設定値がTIME_TO_LEARN_INTERVALより長くなければなりません（MUST）。

If this SPF Back-Off algorithm is enabled by default, then in order to have consistent SPF delays between implementations with default configuration, the following default values SHOULD be implemented:

このSPFバックオフアルゴリズムがデフォルトで有効になっている場合、デフォルト設定の実装間でSPF遅延を一貫させるために、次のデフォルト値を実装すべきです（SHOULD）。

   INITIAL_SPF_DELAY         50 ms
   SHORT_SPF_DELAY          200 ms
   LONG_SPF_DELAY          5000 ms
   TIME_TO_LEARN_INTERVAL   500 ms
   HOLDDOWN_INTERVAL      10000 ms

   INITIAL_SPF_DELAY         50 ms
   SHORT_SPF_DELAY          200 ms
   LONG_SPF_DELAY          5000 ms
   TIME_TO_LEARN_INTERVAL   500 ms
   HOLDDOWN_INTERVAL      10000 ms

In order to satisfy the goals stated in Section 2, operators are RECOMMENDED to configure delay intervals such that INITIAL_SPF_DELAY <= SHORT_SPF_DELAY and SHORT_SPF_DELAY <= LONG_SPF_DELAY.

セクション2で述べた目標を満たすために、運用者は、INITIAL_SPF_DELAY <= SHORT_SPF_DELAYかつSHORT_SPF_DELAY <= LONG_SPF_DELAYとなるように遅延間隔を設定することが推奨されます（RECOMMENDED）。

When setting (default) values, one should consider the customers and their application requirements, the computational power of the routers, the size of the network as determined primarily by the number of IP prefixes advertised in the IGP, the frequency and number of IGP events, and the number of protocol reactions/computations triggered by IGP SPF computation (e.g., BGP, Path Computation Element Communication Protocol (PCEP), Traffic Engineering Constrained SPF (CSPF), and Fast Reroute computations). Note that some or all of these factors may change over the life of the network. In case of doubt, it's RECOMMENDED that timer intervals should be chosen conservatively (i.e., longer timer values).

（デフォルト）値を設定する際には、顧客とそのアプリケーションの要件、ルーターの計算能力、主にIGPで広告されるIPプレフィックスの数によって決まるネットワークの規模、IGPイベントの頻度と数、IGPのSPF計算によって引き起こされるプロトコルの反応や計算の数（たとえば、BGP、経路計算エレメント通信プロトコル（PCEP）、トラフィックエンジニアリングの制約付きSPF（CSPF）、高速リルートの計算）を考慮すべきです。これらの要因の一部またはすべてが、ネットワークの運用期間中に変化する可能性があることに注意してください。判断に迷う場合は、タイマー間隔を保守的に（つまり、長めのタイマー値に）選ぶことが推奨されます（RECOMMENDED）。

For the standard algorithm to be effective in mitigating micro-loops, it is RECOMMENDED that all routers in the IGP domain, or at least all the routers in the same area/level, have exactly the same configured values.

標準アルゴリズムがマイクロループの緩和に効果を発揮するためには、IGPドメイン内のすべてのルーター、または少なくとも同じエリア/レベル内のすべてのルーターが、まったく同じ設定値を持つことが推奨されます（RECOMMENDED）。

7. Partial Deployment

7. 部分的な展開

In general, the SPF Back-Off Delay algorithm is only effective in mitigating micro-loops if it is deployed with the same parameters on all routers in the IGP domain or, at least, all routers in an IGP area/level. The impact of partial deployment is dependent on the particular event, the topology, and the algorithm(s) used on other routers in the IGP area/level. In cases where the previous SPF Back-Off Delay algorithm was implemented uniformly, partial deployment will increase the frequency and duration of micro-loops. Hence, it is RECOMMENDED that all routers in the IGP domain, or at least within the same area/level, be migrated to the SPF algorithm described herein at roughly the same time.

一般に、SPFバックオフ遅延アルゴリズムがマイクロループの緩和に効果を発揮するのは、IGPドメイン内のすべてのルーター、または少なくともIGPのエリア/レベル内のすべてのルーターに、同じパラメーターで展開されている場合に限られます。部分的な展開の影響は、個々のイベント、トポロジー、IGPのエリア/レベル内のほかのルーターで使用されているアルゴリズムに依存します。以前のSPFバックオフ遅延アルゴリズムが一様に実装されていた場合、部分的な展開はマイクロループの頻度と継続時間を増大させます。したがって、IGPドメイン内のすべてのルーター、または少なくとも同じエリア/レベル内のすべてのルーターを、ほぼ同時期にこの文書で説明するSPFアルゴリズムに移行することが推奨されます（RECOMMENDED）。

Note that this is not a new consideration; over time, network operators have changed SPF delay parameters in order to accommodate new customer requirements for fast convergence, as permitted by new software and hardware. They may also have progressively replaced an implementation using a given SPF Back-Off Delay algorithm with another implementation using a different one.

これは新しい考慮事項ではないことに注意してください。ネットワーク運用者はこれまでも、新しいソフトウェアやハードウェアで可能になるにつれて、高速な収束に対する顧客の新しい要件に対応するために、SPF遅延パラメーターを変更してきました。また、ある特定のSPFバックオフ遅延アルゴリズムを使用する実装を、別のアルゴリズムを使用する別の実装に段階的に置き換えてきた場合もあるでしょう。

8. Impact on Micro-loops

8. マイクロループへの影響

Micro-loops during IGP convergence are due to a non-synchronized or non-ordered update of FIBs [RFC5715] [RFC6976] [SPF-MICRO]. FIBs are installed after multiple steps, such as flooding of the IGP event across the network, SPF wait time, SPF computation, FIB distribution across line cards, and FIB update. This document only addresses the contribution from the SPF wait time. This standardized procedure reduces the probability and/or duration of micro-loops when IGPs experience multiple temporally close events. It does not prevent all micro-loops; however, it is beneficial and is less complex and costly to implement when compared to full solutions such as Distributed Tunnels [RFC5715], Synchronized FIB Update [RFC5715], or the ordered FIB approach [RFC6976].

IGPの収束中のマイクロループは、FIBの更新が同期していないこと、あるいは順序付けられていないことが原因で発生します[RFC5715] [RFC6976] [SPF-MICRO]。FIBは、ネットワーク全体へのIGPイベントのフラッディング、SPFの待ち時間、SPF計算、ラインカードへのFIBの配布、FIBの更新といった複数のステップを経てインストールされます。この文書は、SPFの待ち時間による寄与のみを扱います。この標準化された手順は、IGPで時間的に近接した複数のイベントが発生した場合のマイクロループの確率や継続時間、あるいはその両方を減少させます。すべてのマイクロループを防ぐわけではありませんが、分散トンネル[RFC5715]、同期FIB更新[RFC5715]、順序付きFIBアプローチ[RFC6976]などの完全な解決策と比べて、有益であり、実装の複雑さとコストも小さくなります。

10. Security Considerations

10. セキュリティーに関する考慮事項

The algorithm presented in this document does not compromise IGP security. An attacker having the ability to generate IGP events would be able to delay the IGP convergence time. The LONG_SPF_DELAY state may help mitigate the effects of Denial-of-Service (DoS) attacks generating many IGP events.

この文書で提示するアルゴリズムは、IGPのセキュリティーを損なうものではありません。IGPイベントを生成する能力を持つ攻撃者は、IGPの収束時間を遅らせることができます。LONG_SPF_DELAY状態は、多数のIGPイベントを生成するサービス拒否（DoS）攻撃の影響を緩和するのに役立つ場合があります。
