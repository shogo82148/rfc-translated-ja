RFC 9748

Updating the NTP Registries

RFC 9748

NTPレジストリーの更新

Abstract

概要

The Network Time Protocol (NTP) and Network Time Security (NTS) documents define a number of registries, collectively called the NTP registries.

ネットワークタイムプロトコル（NTP）とネットワークタイムセキュリティー（NTS）の文書は、総称してNTPレジストリーと呼ばれる、いくつかのレジストリーを定義しています。

Some registries are correct, but some include incorrect assignments and some don't follow common practice. For the sake of completeness, this document reviews all NTP and NTS registries, and corrects the registries where necessary.

一部のレジストリーは正しいものの、誤った割り当てを含むものや、一般的なプラクティスにしたがっていないものもあります。網羅性のために、この文書はすべてのNTPとNTSのレジストリーを見直し、必要に応じてレジストリーを修正します。

This document updates RFCs 5905, 5906, 7821, 7822, and 8573.

この文書は、RFC 5905、5906、7821、7822、8573を更新します。

1. Introduction

1. はじめに

The Network Time Protocol (NTP) and Network Time Security (NTS) documents define a number of registries, collectively called the NTP registries. The NTP registries can all be found at <https://www.iana.org/assignments/ntp-parameters> and the NTS registries can all be found at <https://www.iana.org/assignments/nts>.

ネットワークタイムプロトコル（NTP）とネットワークタイムセキュリティー（NTS）の文書は、総称してNTPレジストリーと呼ばれる、いくつかのレジストリーを定義しています。NTPのレジストリーはすべて<https://www.iana.org/assignments/ntp-parameters>で、NTSのレジストリーはすべて<https://www.iana.org/assignments/nts>で見つけることができます。

Some registries are correct, but some include incorrect assignments and some don't follow common practice. For the sake of completeness, this document reviews all NTP and NTS registries, and corrects the registries where necessary.

一部のレジストリーは正しいものの、誤った割り当てを含むものや、一般的なプラクティスにしたがっていないものもあります。網羅性のために、この文書はすべてのNTPとNTSのレジストリーを見直し、必要に応じてレジストリーを修正します。

The bulk of this document can be divided into two parts:

この文書の大部分は、2つの部分に分けられます。

  • a summary of the relevant registries, including syntax requirements, registration procedures, and the defining documents.

  • a revised format and entries for each registry being modified.

  • 関連するレジストリーの概要。構文の要件、登録手順、および定義している文書を含みます。

  • 変更される各レジストリーの、改訂された形式とエントリー。

2. Existing Registries

2. 既存のレジストリー

This section describes the registries and the rules for them. It is intended to be a short summary of the syntax and registration requirements for each registry. The semantics and protocol processing rules for each registry -- that is, how an implementation acts when sending or receiving any of the fields -- are not described here.

このセクションでは、レジストリーとその規則について説明します。これは、各レジストリーの構文と登録要件の短い要約となることを意図しています。各レジストリーのセマンティクスとプロトコル処理の規則、すなわち、いずれかのフィールドを送信または受信するときに実装がどのように動作するかについては、ここでは説明しません。

2.1. Reference ID and Kiss-o'-Death Registries

2.1. Reference IDとKiss-o'-Deathのレジストリー

[RFC5905] defines two registries: "NTP Reference Identifier Codes" in Section 7.3 and the "NTP Kiss-o'-Death Codes" in Section 7.4. Reference identifiers and kiss codes can be up to four ASCII characters, padded on the right with all-bits-zero if necessary. Entries that start with 0x58, the ASCII letter uppercase X, are reserved for Private or Experimental Use. Both registries are First Come First Served. The registries were created per Section 16 of [RFC5905].

[RFC5905]は、2つのレジストリーを定義しています。セクション7.3の「NTP Reference Identifier Codes」と、セクション7.4の「NTP Kiss-o'-Death Codes」です。reference identifierとkiss codeは最大4文字のASCII文字で、必要に応じて右側をすべてのビットが0の値でパディングします。ASCIIの大文字Xである0x58で始まるエントリーは、Private or Experimental Useのために予約されています。どちらのレジストリーもFirst Come First Servedです。これらのレジストリーは[RFC5905]のSection 16にしたがって作成されました。

2.2. Extension Field Types

2.2. 拡張フィールドのタイプ

Section 7.5 of [RFC5905] defines the on-the-wire format of extension fields but does not create a registry for them.

[RFC5905]のSection 7.5は、拡張フィールドの伝送時の形式を定義していますが、そのためのレジストリーは作成していません。

Section 13 of [RFC5906] mentions the "NTP Extension Field Types" registry, and defines it indirectly by defining 30 extensions (10 each for request, response, and error response). It does not provide a formal definition of the columns in the registry. Section 10 of [RFC5906] splits the Field Type into four subfields, only for use within the Autokey extensions.

[RFC5906]のSection 13は「NTP Extension Field Types」レジストリーに言及し、30個の拡張（リクエスト、レスポンス、エラーレスポンスのそれぞれに10個）を定義することで、間接的にそのレジストリーを定義しています。レジストリーの列の正式な定義は提供していません。[RFC5906]のSection 10は、Autokeyの拡張の中でのみ使用するために、Field Typeを4つのサブフィールドに分割しています。

[RFC7821] adds a new entry, Checksum Complement, to the "NTP Extension Field Types" registry.

[RFC7821]は、「NTP Extension Field Types」レジストリーにChecksum Complementという新しいエントリーを追加しています。

[RFC7822] clarifies the processing rules for Extension Field Types, particularly around the interaction with the Message Authentication Code (MAC) field. NTPv4 packets may contain a MAC that appears where one would expect the next extension field header.

[RFC7822]は、特にメッセージ認証コード（MAC）フィールドとの相互作用に関して、Extension Field Typesの処理規則を明確化しています。NTPv4パケットには、次の拡張フィールドのヘッダーがあると予想される位置にMACが現れることがあります。

[RFC8573] changes the cryptography used in the MAC field.

[RFC8573]は、MACフィールドで使用する暗号を変更しています。

[RFC8915] adds four new entries to the "NTP Extension Field Types" registry.

[RFC8915]は、「NTP Extension Field Types」レジストリーに4つの新しいエントリーを追加しています。

The following problems exist with the current registry:

現在のレジストリーには、次の問題があります。

  • Many of the entries in the "NTP Extension Field Types" registry have swapped some of the nibbles; for example, 0x0302 was listed for Cookie Message Request instead of 0x0203. The errors are due to documentation errors with the original implementation of Autokey. This document marks the erroneous values as reserved, in case there is an implementation using the registered values instead of what the original implementation used. Applications that used those values would have realized that they did not interoperate with the dominant (if not only) implementation at the time. Marking the values as reserved ensures that any such applications continue to work as is.

  • Some values were mistakenly reused.

  • 「NTP Extension Field Types」レジストリーのエントリーの多くは、ニブルの一部が入れ替わっています。たとえば、Cookie Message Requestには0x0203ではなく0x0302が記載されていました。この誤りは、Autokeyの元の実装に関する文書の誤りによるものです。この文書は、元の実装が使用した値の代わりに登録された値を使用している実装がある場合に備えて、誤った値を予約済みとしてマークします。それらの値を使用したアプリケーションは、当時の支配的な（唯一ではないとしても）実装と相互運用できないことに気づいていたはずです。値を予約済みとしてマークすることで、そのようなアプリケーションはそのまま動作し続けられます。

  • 一部の値が誤って再利用されていました。

2.3. Network Time Security Registries

2.3. ネットワークタイムセキュリティーのレジストリー

[RFC8915] defines the NTS protocol. The related registries are listed here for completeness, but there are no changes specified in this document.

[RFC8915]は、NTSプロトコルを定義しています。関連するレジストリーを網羅性のためにここに挙げますが、この文書で規定する変更はありません。

In [RFC8915]:

[RFC8915]では：

Sections 7.1 through 7.5 (inclusive) added entries to existing registries.

セクション7.1からセクション7.5まで（両端を含む）で、既存のレジストリーにエントリーを追加しました。

Section 7.6 created the "Network Time Security Key Establishment Record Types" registry that partitions the range into three different registration policies: IETF Review, Specification Required, and Private or Experimental Use.

セクション7.6では、「Network Time Security Key Establishment Record Types」レジストリーを作成しました。このレジストリーは、範囲をIETF Review、Specification Required、Private or Experimental Useという3つの異なる登録ポリシーに分割しています。

Section 7.7 created the "Network Time Security Next Protocols" registry that similarly partitions the range.

セクション7.7では、同様に範囲を分割した「Network Time Security Next Protocols」レジストリーを作成しました。

Section 7.8 created the "Network Time Security Error Codes" and "Network Time Security Warning Codes" registries. Both registries are partitioned the same way.

セクション7.8では、「Network Time Security Error Codes」レジストリーと「Network Time Security Warning Codes」レジストリーを作成しました。どちらのレジストリーも同じ方法で分割されています。

3. NTP Registry Updates

3. NTPレジストリーの更新

The following general guidelines apply to the NTP registries:

NTPレジストリーには、次の一般的なガイドラインが適用されます。

  • A partition of the "NTP Extension Field Types" registry is reserved for Private or Experimental Use.

  • In the "NTP Reference Identifier Codes" and "NTP Kiss-o'-Death Codes" registries, entries with ASCII fields are now limited to uppercase letters or digits. Fields starting with 0x58, the uppercase letter "X", are reserved for Private or Experimental Use.

  • The policy for each registry is now Specification Required, as defined in [RFC8126], Section 4.6.

  • 「NTP Extension Field Types」レジストリーの一部の区間は、Private or Experimental Useのために予約されています。

  • 「NTP Reference Identifier Codes」レジストリーと「NTP Kiss-o'-Death Codes」レジストリーでは、ASCIIのフィールドを持つエントリーは、大文字または数字に制限されるようになりました。大文字の「X」である0x58で始まるフィールドは、Private or Experimental Useのために予約されています。

  • 各レジストリーのポリシーは、[RFC8126], Section 4.6で定義されているSpecification Requiredになりました。

3.1. Designated Experts

3.1. 指定専門家

The IESG is requested to choose three designated experts (DEs), with approvals from two being required to implement a change. Guidance for the experts is given below.

IESGは3人の指定専門家（DE）を選ぶよう求められており、変更を実施するには2人の承認が必要です。専門家への指針を以下に示します。

The DEs should be familiar with [RFC8126], particularly Section 5. As that reference suggests, the DE should ascertain the existence of a suitable specification and verify that it is publicly available. The DE is also expected to check the clarity of purpose and use of the requested code points.

DEは[RFC8126]、特にセクション5を熟知しているべきです。その参照文献が示唆するように、DEは適切な仕様が存在することを確かめ、それが公開されていることを検証すべきです。DEはまた、要求されたコードポイントの目的と用途が明確であるかを確認することも期待されます。

In addition, the DE is expected to be familiar with this document, specifically the history documented here.

加えて、DEはこの文書、特にここに記録された経緯を熟知していることが期待されます。

4.3. NTP Extension Field Types

4.3. NTP Extension Field Types

The registration procedure has been changed to Specification Required and [RFC5906] and this document have been added as references.

登録手順はSpecification Requiredに変更され、[RFC5906]とこの文書が参照として追加されました。

The following two Notes have been added:

次の2つのNoteが追加されました。

Field Types in the range 0xF000 through 0xFFFF, inclusive, are reserved for experimentation and development. IANA cannot assign them. Both NTS Cookie and Autokey Message Request have the same Field Type; in practice this is not a problem as the field semantics will be determined by other parts of the message.
0xF000から0xFFFFまで（両端を含む）の範囲のField Typeは、実験と開発のために予約されています。IANAはそれらを割り当てることはできません。NTS CookieとAutokey Message Requestはどちらも同じField Typeを持ちますが、フィールドのセマンティクスはメッセージのほかの部分によって決まるため、実際には問題になりません。
The "Reserved for historic reasons" is for differences between the original documentation and implementation of Autokey and marks the erroneous values as reserved, in case there is an implementation that used the registered values instead of what the original implementation used.
「Reserved for historic reasons」は、Autokeyの元の文書と実装の間の相違のためのものであり、元の実装が使用した値の代わりに登録された値を使用した実装がある場合に備えて、誤った値を予約済みとしてマークします。

The columns are defined as follows:

列は次のように定義されています。

Field Type (required):
a two-byte value in hexadecimal.
Meaning (required):
a brief text description of the field type.
Reference (required):
the publication defining the field type.
Field Type (required):
16進数で表した2バイトの値。
Meaning (required):
フィールドタイプの簡潔なテキストによる説明。
Reference (required):
フィールドタイプを定義している出版物。
