RFC 9534

Simple Two-Way Active Measurement Protocol Extensions for Performance Measurement on a Link Aggregation Group

RFC 9534

リンクアグリゲーショングループ上の性能測定のためのSimple Two-Way Active Measurement Protocolの拡張

Abstract

概要

This document extends Simple Two-way Active Measurement Protocol (STAMP) to implement performance measurement on every member link of a Link Aggregation Group (LAG). Knowing the measured metrics of each member link of a LAG enables operators to enforce a performance-based traffic steering policy across the member links.

この文書は、Simple Two-way Active Measurement Protocol（STAMP）を拡張して、リンクアグリゲーショングループ（LAG）のすべてのメンバーリンクで性能測定を実現します。LAGの各メンバーリンクの測定されたメトリックがわかれば、運用者はメンバーリンク間で性能に基づくトラフィックステアリングのポリシーを適用できます。

1. Introduction

1. はじめに

A Link Aggregation Group (LAG), as defined in [IEEE802.1AX], provides mechanisms to combine multiple physical links into a single logical link. This logical link offers higher bandwidth and better resiliency because, if one of the physical member links fails, the aggregate logical link can continue to forward traffic over the remaining operational physical member links.

[IEEE802.1AX]で定義されているリンクアグリゲーショングループ（LAG）は、複数の物理リンクを1つの論理リンクにまとめるメカニズムを提供します。この論理リンクは、より広い帯域幅とより高い回復力を提供します。物理メンバーリンクの1つに障害が発生しても、集約された論理リンクは、残りの稼働中の物理メンバーリンクでトラフィックの転送を継続できるからです。

Usually, when forwarding traffic over a LAG, a hash-based mechanism is used to load balance the traffic across the LAG member links. The link delay might vary between member links because of different transport paths, especially when a LAG is used in a wide area network. To provide low-latency service for time-sensitive traffic, we need to explicitly steer the traffic across the LAG member links based on the link delay, loss, and so on. That requires a solution to measure the performance metrics of each member link of a LAG. Hence, the measured performance metrics can work together with [RFC8668] for traffic steering.

通常、LAGでトラフィックを転送する場合、LAGのメンバーリンク間でトラフィックを負荷分散するためにハッシュベースのメカニズムが使われます。特にLAGを広域ネットワークで使用する場合、伝送パスが異なるために、リンク遅延がメンバーリンクによって異なることがあります。時間に敏感なトラフィックに低遅延のサービスを提供するには、リンクの遅延や損失などに基づいて、LAGのメンバーリンク間でトラフィックを明示的に振り分ける必要があります。そのためには、LAGのすべてのメンバーリンクの性能メトリックを測定する方法が必要です。そうすれば、測定された性能メトリックを、[RFC8668]と組み合わせてトラフィックステアリングに使用できます。

According to the classifications in [RFC7799], [RFC8762] is an active measurement method, and it can complement passive and hybrid methods. It provides a mechanism to measure both one-way and round-trip performance metrics, like delay, delay variation, and packet loss. A STAMP test session over the LAG can be used to measure the performance of a member link using a specially constructed 5-tuple. The session can be used to measure an average of some or all member links of the LAG by varying one or more elements of that 5-tuple. However, without the knowledge of each member link, a STAMP test session cannot measure the performance of every physical member link.

[RFC7799]の分類によれば、[RFC8762]はアクティブ測定方法であり、パッシブ方法やハイブリッド方法を補完できます。STAMPは、遅延、遅延変動、パケット損失など、片方向と往復の両方の性能メトリックを測定するメカニズムを提供します。特別に構成した5タプルを使用すれば、LAG上のSTAMPテストセッションでメンバーリンクの性能を測定できます。その5タプルの1つ以上の要素を変化させることで、このセッションを使ってLAGの一部またはすべてのメンバーリンクの平均を測定できます。しかし、各メンバーリンクについての知識がなければ、STAMPテストセッションはすべての物理メンバーリンクの性能を測定することはできません。

This document extends STAMP to implement performance measurement on every member link of a LAG. It can provide the same metrics as [RFC4656] and [RFC5357] can measure, such as delay, jitter, and packet loss.

この文書は、LAGのすべてのメンバーリンクで性能測定を実現するために、STAMPを拡張します。この拡張では、遅延、ジッター、パケット損失など、[RFC4656]や[RFC5357]で測定できるものと同じメトリックを提供できます。

2. Micro Sessions on a LAG

2. LAG上のマイクロセッション

This document addresses the scenario where a LAG directly connects two nodes. An example of this is in Figure 1, where the LAG consisting of four links connects nodes A and B. The goal is to measure the performance of each link of the LAG.

この文書は、LAGが2つのノードを直接接続するシナリオを扱います。その例をFigure 1に示します。ここでは、4本のリンクからなるLAGがノードAとノードBを接続しています。目標は、LAGの各リンクの性能を測定することです。

To measure the performance metrics of every member link of a LAG, multiple sessions (one session for each member link) need to be established between the two endpoints that are connected by the LAG. These sessions are called "micro sessions" in the remainder of this document. Although micro sessions are in fact STAMP sessions established on member links of a LAG, test packets of micro sessions MUST carry member link information for validation.

LAGのすべてのメンバーリンクの性能メトリックを測定するには、LAGで接続された2つのエンドポイントの間に、複数のセッション（メンバーリンクごとに1つのセッション）を確立する必要があります。この文書の以降の部分では、これらのセッションを「マイクロセッション（micro session）」と呼びます。マイクロセッションは実際にはLAGのメンバーリンク上に確立されたSTAMPセッションですが、マイクロセッションのテストパケットは、検証のためにメンバーリンクの情報を運ばなければなりません（MUST）。

All micro sessions of a LAG share the same Sender IP Address and Receiver IP Address. As for the UDP port, the micro sessions may share the same Sender Port and Receiver Port pair or each micro session may be configured with a different Sender Port and Receiver Port pair. From the operational point of view, the former is simpler and is RECOMMENDED.

LAGのすべてのマイクロセッションは、同じSender IP AddressとReceiver IP Addressを共有します。UDPポートについては、マイクロセッションが同じSender PortとReceiver Portの組を共有することも、マイクロセッションごとに異なるSender PortとReceiver Portの組を設定することもできます。運用の観点からは、前者のほうが単純であり、前者が推奨されます（RECOMMENDED）。

Test packets of a micro session MUST carry the member link information for validation checks. For example, when a micro STAMP Session-Sender receives a reflected test packet, it checks whether the test packet is from the expected member link. The member link information is encoded in the Micro-session ID TLV introduced in Section 3, which also provides a detailed description about member link validation.

マイクロセッションのテストパケットは、検証チェックのためにメンバーリンクの情報を運ばなければなりません（MUST）。たとえば、マイクロSTAMP Session-Senderは、反射されたテストパケットを受信すると、そのテストパケットが期待するメンバーリンクから来たものかどうかを確認します。メンバーリンクの情報は、Section 3で導入するMicro-session ID TLVにエンコードされます。メンバーリンクの検証についての詳しい説明もこのセクションにあります。

A micro STAMP Session-Sender MAY include the [RFC8972] to request information from the micro Session-Reflector. This timestamp might be important for the micro Session-Sender, as it improves the accuracy of network delay measurement by minimizing the impact of egress queuing delays on the measurement.

マイクロSTAMP Session-Senderは、マイクロSession-Reflectorに情報を要求するために[RFC8972]を含めてもよいです（MAY）。このタイムスタンプは、出力キューイング遅延が測定に与える影響を最小化することでネットワーク遅延測定の精度を向上させるため、マイクロSession-Senderにとって重要な場合があります。

3. Member Link Validation

3. メンバーリンクの検証

Test packets MUST carry member link information in the Micro-session ID TLV introduced in this section for validation checks. The micro Session-Sender verifies whether the test packet is received from the expected member link. It also verifies whether the packet is sent from the expected member link at the Reflector side. The micro Session-Reflector verifies whether the test packet is received from the expected member link.

検証チェックのために、テストパケットは、このセクションで導入するMicro-session ID TLVでメンバーリンクの情報を運ばなければなりません（MUST）。マイクロSession-Senderは、テストパケットが期待するメンバーリンクから受信されたかどうかを検証します。また、そのパケットがReflector側で期待するメンバーリンクから送信されたかどうかも検証します。マイクロSession-Reflectorは、テストパケットが期待するメンバーリンクから受信されたかどうかを検証します。

3.1. Micro-session ID TLV

3.1. Micro-session ID TLV

The [RFC8972] extends STAMP test packets with one or more optional TLVs. This document defines the TLV Type (value 11) for the Micro-session ID TLV that carries the micro STAMP Session-Sender member link identifier and Session-Reflector member link identifier in the Sender Micro-session ID field and the Reflector Micro-session ID field, respectively. The format of the Micro-session ID TLV is shown as follows:

[RFC8972]は、1つ以上の選択可能なTLVでSTAMPのテストパケットを拡張します。この文書では、Micro-session ID TLVのためのTLV Type（値11）を定義します。Micro-session ID TLVは、マイクロSTAMP Session-Senderのメンバーリンク識別子とSession-Reflectorのメンバーリンク識別子を、それぞれSender Micro-session IDフィールドとReflector Micro-session IDフィールドで運びます。Micro-session ID TLVの形式を次に示します。

Type (1 octet in length):
This field is defined to indicate this TLV is a Micro-session ID TLV. Value 11 has been allocated by IANA (Section 5).
Length (2 octets in length):
This field is defined to carry the length of the Value field in octets. The Length field value MUST be 4.
Sender Micro-session ID (2 octets in length):
This field is defined to carry the LAG member link identifier of the Sender side. In the future, it may be used generically to cover use cases beyond LAGs. The value of this field MUST be unique within a STAMP session at the Session-Sender.
Reflector Micro-session ID (2 octets in length):
This field is defined to carry the LAG member link identifier of the Reflector side. In the future, it may be used generically to cover use cases beyond LAGs. The value of this field MUST be unique within a STAMP session at the Session-Reflector.
Type（長さ1オクテット）:
このフィールドは、このTLVがMicro-session ID TLVであることを示すために定義されています。値11がIANAによって割り当てられています（Section 5）。
Length（長さ2オクテット）:
このフィールドは、Valueフィールドの長さをオクテット単位で運ぶために定義されています。Lengthフィールドの値は4でなければなりません（MUST）。
Sender Micro-session ID（長さ2オクテット）:
このフィールドは、Sender側のLAGメンバーリンク識別子を運ぶために定義されています。将来的には、LAG以外のユースケースにも汎用的に使われる可能性があります。このフィールドの値は、Session-SenderにおけるSTAMPセッション内で一意でなければなりません（MUST）。
Reflector Micro-session ID（長さ2オクテット）:
このフィールドは、Reflector側のLAGメンバーリンク識別子を運ぶために定義されています。将来的には、LAG以外のユースケースにも汎用的に使われる可能性があります。このフィールドの値は、Session-ReflectorにおけるSTAMPセッション内で一意でなければなりません（MUST）。

3.2. Micro STAMP-Test Procedures

3.2. マイクロSTAMP-Testの手順

The micro STAMP-Test reuses the procedures as defined in Section 4 of [RFC8762] with the following additions.

マイクロSTAMP-Testは、[RFC8762]のセクション4で定義されている手順を再利用し、次の点を追加します。

The micro STAMP Session-Sender MUST send the micro STAMP-Test packets over the member link with which the session is associated. The mapping between a micro STAMP session and the Sender/Reflector member link identifiers can be configured by augmenting the [STAMP-YANG]. The detailed augmentation is not in the scope of this document.

マイクロSTAMP Session-Senderは、マイクロSTAMP-Testパケットを、そのセッションが関連付けられているメンバーリンクで送信しなければなりません（MUST）。マイクロSTAMPセッションとSender/Reflectorのメンバーリンク識別子との対応付けは、[STAMP-YANG]を拡張することで設定できます。拡張の詳細はこの文書の範囲外です。

When sending a test packet, the micro STAMP Session-Sender MUST set the Sender Micro-session ID field with the member link identifier associated with the micro STAMP session. If the Session-Sender knows the Reflector member link identifier, the Reflector Micro-session ID field MUST be set. Otherwise, the Reflector Micro-session ID field MUST be zero. The Reflector member link identifier can be obtained from preconfiguration or learned from data plane (e.g., the reflected test packet). This document does not specify the way to obtain the Reflector member link identifier.

テストパケットを送信するとき、マイクロSTAMP Session-Senderは、Sender Micro-session IDフィールドに、そのマイクロSTAMPセッションに関連付けられたメンバーリンク識別子を設定しなければなりません（MUST）。Session-SenderがReflectorのメンバーリンク識別子を知っている場合、Reflector Micro-session IDフィールドを設定しなければなりません（MUST）。そうでない場合、Reflector Micro-session IDフィールドは0でなければなりません（MUST）。Reflectorのメンバーリンク識別子は、事前設定から取得するか、データプレーン（たとえば、反射されたテストパケット）から学習できます。この文書では、Reflectorのメンバーリンク識別子を取得する方法は規定しません。

When the micro STAMP Session-Reflector receives a test packet, if the Reflector Micro-session ID is not zero, the micro STAMP Session-Reflector MUST use the Reflector member link identifier to check whether it is associated with the micro STAMP session. If the validation fails, the test packet MUST be discarded. If the Reflector Micro-session ID is zero, it will not be verified. If all validations passed, the Session-Reflector sends a reflected test packet to the Session-Sender. The micro STAMP Session-Reflector MUST put the Sender and Reflector member link identifiers that are associated with the micro STAMP session in the Sender Micro-session ID and Reflector Micro-session ID fields, respectively. The Sender member link identifier is copied from the received test packet.

マイクロSTAMP Session-Reflectorがテストパケットを受信したとき、Reflector Micro-session IDが0でなければ、マイクロSTAMP Session-Reflectorは、Reflectorのメンバーリンク識別子を使用して、それがそのマイクロSTAMPセッションに関連付けられているかどうかを確認しなければなりません（MUST）。検証に失敗した場合、そのテストパケットは破棄しなければなりません（MUST）。Reflector Micro-session IDが0の場合、それは検証されません。すべての検証に合格した場合、Session-Reflectorは反射されたテストパケットをSession-Senderに送信します。マイクロSTAMP Session-Reflectorは、そのマイクロSTAMPセッションに関連付けられたSenderとReflectorのメンバーリンク識別子を、それぞれSender Micro-session IDフィールドとReflector Micro-session IDフィールドに入れなければなりません（MUST）。Senderのメンバーリンク識別子は、受信したテストパケットからコピーします。

When receiving a reflected test packet, the micro Session-Sender MUST use the Sender Micro-session ID to validate whether the reflected test packet is correctly received from the expected member link. If the validation fails, the test packet MUST be discarded. The micro Session-Sender MUST use the Reflector Micro-session ID to validate the Reflector's behavior. If the validation fails, the test packet MUST be discarded.

反射されたテストパケットを受信したとき、マイクロSession-Senderは、Sender Micro-session IDを使用して、反射されたテストパケットが期待するメンバーリンクから正しく受信されたかどうかを検証しなければなりません（MUST）。検証に失敗した場合、そのテストパケットは破棄しなければなりません（MUST）。マイクロSession-Senderは、Reflector Micro-session IDを使用してReflectorの振る舞いを検証しなければなりません（MUST）。検証に失敗した場合、そのテストパケットは破棄しなければなりません（MUST）。

Two modes of the STAMP Session-Reflector, stateless and stateful, characterize the expected behavior as described in Section 4 of [RFC8762]. The micro STAMP-Test also supports both stateless and stateful modes. However, the micro STAMP-Test does not introduce any additional state to STAMP, i.e., any procedure with regard to the Micro-session ID is stateless.

[RFC8762]のセクション4で説明されているように、STAMP Session-Reflectorには、期待される振る舞いを特徴づけるステートレスとステートフルの2つのモードがあります。マイクロSTAMP-Testも、ステートレスモードとステートフルモードの両方をサポートします。ただし、マイクロSTAMP-TestはSTAMPに追加の状態を導入しません。すなわち、Micro-session IDに関するすべての手順はステートレスです。

4. Applicability

4. 適用性

The micro STAMP Session-Sender sends micro Session-Sender packets with the Micro-session ID TLV. The micro Session-Reflector checks whether a test packet is received from the member link associated with the correct micro STAMP session if the Reflector Micro-session ID field is set. When reflecting, the micro STAMP Session-Reflector copies the Sender Micro-session ID from the received micro Session-Sender packet to the micro Session-Reflector packet and sets the Reflector Micro-session ID field with the member link identifier that is associated with the micro STAMP session. When receiving the micro Session-Reflector packet, the micro Session-Sender uses the Sender Micro-session ID to check whether the packet is received from the member link associated with the correct micro STAMP session. The micro Session-Sender also use the Reflector Micro-session ID to validate the Reflector's behavior.

マイクロSTAMP Session-Senderは、Micro-session ID TLVを含むマイクロSession-Senderパケットを送信します。マイクロSession-Reflectorは、Reflector Micro-session IDフィールドが設定されている場合、テストパケットが正しいマイクロSTAMPセッションに関連付けられたメンバーリンクから受信されたかどうかを確認します。反射の際、マイクロSTAMP Session-Reflectorは、受信したマイクロSession-SenderパケットからマイクロSession-ReflectorパケットにSender Micro-session IDをコピーし、Reflector Micro-session IDフィールドに、そのマイクロSTAMPセッションに関連付けられたメンバーリンク識別子を設定します。マイクロSession-Reflectorパケットを受信したとき、マイクロSession-Senderは、Sender Micro-session IDを使用して、そのパケットが正しいマイクロSTAMPセッションに関連付けられたメンバーリンクから受信されたかどうかを確認します。マイクロSession-Senderは、Reflector Micro-session IDも使用してReflectorの振る舞いを検証します。

6. Security Considerations

6. セキュリティーに関する考慮事項

The STAMP extension defined in this document is intended for deployment in the LAG scenario where Session-Sender and Session-Reflector are directly connected. As such, it's assumed that a node involved in a STAMP operation has previously verified the integrity of the LAG connection and the identity of its one-hop-away peer node.

この文書で定義するSTAMP拡張は、Session-SenderとSession-Reflectorが直接接続されているLAGのシナリオでの展開を意図しています。そのため、STAMPの動作に関与するノードは、LAG接続の完全性と1ホップ先のピアノードの識別情報を事前に検証済みであることを前提としています。

This document does not introduce any additional security issues, and the security mechanisms defined in [RFC8762] and [RFC8972] apply in this document.

この文書は追加のセキュリティー上の問題を導入せず、この文書には[RFC8762]と[RFC8972]で定義されているセキュリティーメカニズムが適用されます。
