1. INTRODUCTION

1. はじめに

This document specifies the steps a host takes in deciding how to autoconfigure its interfaces in IP version 6. The autoconfiguration process includes creating a link-local address and verifying its uniqueness on a link, determining what information should be autoconfigured (addresses, other information, or both), and in the case of addresses, whether they should be obtained through the stateless mechanism, the stateful mechanism, or both. This document defines the process for generating a link-local address, the process for generating site-local and global addresses via stateless address autoconfiguration, and the Duplicate Address Detection procedure. The details of autoconfiguration using the stateful protocol are specified elsewhere.

この文書は、IPバージョン6においてホストがインターフェイスを自動設定する方法を決定する際の手順を規定します。自動設定のプロセスには、リンクローカルアドレスを作成してリンク上での一意性を検証すること、どの情報を自動設定すべきか（アドレス、その他の情報、またはその両方）を決定すること、そしてアドレスの場合には、それをステートレスな仕組みとステートフルな仕組みのどちら（あるいは両方）で取得すべきかを決定することが含まれます。この文書は、リンクローカルアドレスを生成するプロセス、ステートレスアドレス自動設定によってサイトローカルアドレスとグローバルアドレスを生成するプロセス、および重複アドレス検出の手順を定義します。ステートフルなプロトコルを使用した自動設定の詳細は、別の文書で規定されています。

IPv6 defines both a stateful and stateless address autoconfiguration mechanism. Stateless autoconfiguration requires no manual configuration of hosts, minimal (if any) configuration of routers, and no additional servers. The stateless mechanism allows a host to generate its own addresses using a combination of locally available information and information advertised by routers. Routers advertise prefixes that identify the subnet(s) associated with a link, while hosts generate an "interface identifier" that uniquely identifies an interface on a subnet. An address is formed by combining the two. In the absence of routers, a host can only generate link-local addresses. However, link-local addresses are sufficient for allowing communication among nodes attached to the same link.

IPv6は、ステートフルとステートレスの両方のアドレス自動設定の仕組みを定義しています。ステートレスな自動設定では、ホストの手動の設定は不要で、ルーターの設定は（必要だとしても）最小限で済み、追加のサーバーも必要ありません。ステートレスな仕組みにより、ホストは、ローカルで利用可能な情報とルーターによって広告される情報を組み合わせて、自身のアドレスを生成できます。ルーターはリンクに関連付けられたサブネットを識別するプレフィックスを広告し、ホストはサブネット上のインターフェイスを一意に識別する「インターフェイス識別子」を生成します。アドレスはこの2つを組み合わせることで形成されます。ルーターがない場合、ホストはリンクローカルアドレスしか生成できません。しかし、リンクローカルアドレスは、同じリンクに接続されたノード間の通信を可能にするには十分です。

In the stateful autoconfiguration model, hosts obtain interface addresses and/or configuration information and parameters from a server. Servers maintain a database that keeps track of which addresses have been assigned to which hosts. The stateful autoconfiguration protocol allows hosts to obtain addresses, other configuration information or both from a server. Stateless and stateful autoconfiguration complement each other. For example, a host can use stateless autoconfiguration to configure its own addresses, but use stateful autoconfiguration to obtain other information. Stateful autoconfiguration for IPv6 is the subject of future work [DHCPv6].

ステートフルな自動設定のモデルでは、ホストはインターフェイスのアドレス、設定情報とパラメーター、またはその両方をサーバーから取得します。サーバーは、どのアドレスがどのホストに割り当てられているかを追跡するデータベースを維持します。ステートフルな自動設定のプロトコルにより、ホストはアドレス、その他の設定情報、またはその両方をサーバーから取得できます。ステートレスな自動設定とステートフルな自動設定は互いに補完し合います。たとえば、ホストは、ステートレスな自動設定を使用して自身のアドレスを設定し、ステートフルな自動設定を使用してその他の情報を取得できます。IPv6のステートフルな自動設定は、今後の作業の対象です[DHCPv6]。

The stateless approach is used when a site is not particularly concerned with the exact addresses hosts use, so long as they are unique and properly routable. The stateful approach is used when a site requires tighter control over exact address assignments. Both stateful and stateless address autoconfiguration may be used simultaneously. The site administrator specifies which type of autoconfiguration to use through the setting of appropriate fields in Router Advertisement messages [DISCOVERY].

ステートレスな手法は、アドレスが一意で適切にルーティング可能である限り、ホストが使用する正確なアドレスにサイトが特にこだわらない場合に使用されます。ステートフルな手法は、サイトが正確なアドレスの割り当てをより厳密に管理する必要がある場合に使用されます。ステートフルとステートレスのアドレス自動設定は、同時に使用することもできます。サイトの管理者は、ルーター広告メッセージ[DISCOVERY]の適切なフィールドを設定することで、どの種類の自動設定を使用するかを指定します。

IPv6 addresses are leased to an interface for a fixed (possibly infinite) length of time. Each address has an associated lifetime that indicates how long the address is bound to an interface. When a lifetime expires, the binding (and address) become invalid and the address may be reassigned to another interface elsewhere in the Internet. To handle the expiration of address bindings gracefully, an address goes through two distinct phases while assigned to an interface. Initially, an address is "preferred", meaning that its use in arbitrary communication is unrestricted. Later, an address becomes "deprecated" in anticipation that its current interface binding will become invalid. While in a deprecated state, the use of an address is discouraged, but not strictly forbidden. New communication (e.g., the opening of a new TCP connection) should use a preferred address when possible. A deprecated address should be used only by applications that have been using it and would have difficulty switching to another address without a service disruption.

IPv6アドレスは、固定の（無限の場合もある）期間、インターフェイスに貸し出されます。各アドレスには、そのアドレスがインターフェイスにどれだけ長く結び付けられるかを示す生存期間が関連付けられています。生存期間が満了すると、結び付き（およびアドレス）は無効になり、そのアドレスはインターネット上の別の場所にある別のインターフェイスに再割り当てされる可能性があります。アドレスの結び付きの満了を穏やかに扱うために、アドレスはインターフェイスに割り当てられている間に2つの異なる段階を経ます。最初、アドレスは「推奨（preferred）」であり、任意の通信での使用は制限されません。その後、現在のインターフェイスとの結び付きが無効になることを見越して、アドレスは「非推奨（deprecated）」になります。非推奨の状態にある間、アドレスの使用は推奨されませんが、厳密に禁止されているわけではありません。新しい通信（たとえば、新しいTCP接続を開くこと）では、可能であれば推奨アドレスを使用すべきです。非推奨アドレスは、それをすでに使用していて、サービスを中断せずに別のアドレスに切り替えるのが難しいアプリケーションだけが使用すべきです。

To insure that all configured addresses are likely to be unique on a given link, nodes run a "duplicate address detection" algorithm on addresses before assigning them to an interface. The Duplicate Address Detection algorithm is performed on all addresses, independent of whether they are obtained via stateless or stateful autoconfiguration. This document defines the Duplicate Address Detection algorithm.

設定されたすべてのアドレスが特定のリンク上で一意である可能性が高いことを保証するために、ノードは、アドレスをインターフェイスに割り当てる前に、そのアドレスについて「重複アドレス検出」のアルゴリズムを実行します。重複アドレス検出のアルゴリズムは、ステートレスな自動設定とステートフルな自動設定のどちらで取得されたかにかかわらず、すべてのアドレスについて実行されます。この文書は、重複アドレス検出のアルゴリズムを定義します。

The autoconfiguration process specified in this document applies only to hosts and not routers. Since host autoconfiguration uses information advertised by routers, routers will need to be configured by some other means. However, it is expected that routers will generate link-local addresses using the mechanism described in this document. In addition, routers are expected to successfully pass the Duplicate Address Detection procedure described in this document on all addresses prior to assigning them to an interface.

この文書で規定される自動設定のプロセスは、ホストにのみ適用され、ルーターには適用されません。ホストの自動設定はルーターが広告する情報を使用するため、ルーターは何らかの別の手段で設定する必要があります。しかし、ルーターは、この文書で説明する仕組みを使用してリンクローカルアドレスを生成することが期待されます。さらに、ルーターは、すべてのアドレスについて、インターフェイスに割り当てる前に、この文書で説明する重複アドレス検出の手順に合格することが期待されます。

2節では、この文書全体で使用される用語の定義を示します。3節では、現在の自動設定の手順につながった設計目標を説明します。4節ではプロトコルの概要を示し、5節ではプロトコルを詳細に説明します。

2. TERMINOLOGY

2. 用語

IP
Internet Protocol Version 6. The terms IPv4 and are used only in contexts where necessary to avoid ambiguity.
node
a device that implements IP.
router
a node that forwards IP packets not explicitly addressed to itself.
host
any node that is not a router.
upper layer
a protocol layer immediately above IP. Examples are transport protocols such as TCP and UDP, control protocols such as ICMP, routing protocols such as OSPF, and internet or lower- layer protocols being "tunneled" over (i.e., encapsulated in) IP such as IPX, AppleTalk, or IP itself.
link
a communication facility or medium over which nodes can communicate at the link layer, i.e., the layer immediately below IP. Examples are Ethernets (simple or bridged); PPP links; X.25, Frame Relay, or ATM networks; and internet (or higher) layer "tunnels", such as tunnels over IPv4 or IPv6 itself.
interface
a node's attachment to a link.
packet
an IP header plus payload.
address
an IP-layer identifier for an interface or a set of interfaces.
unicast address
an identifier for a single interface. A packet sent to a unicast address is delivered to the interface identified by that address.
multicast address
an identifier for a set of interfaces (typically belonging to different nodes). A packet sent to a multicast address is delivered to all interfaces identified by that address.
anycast address
an identifier for a set of interfaces (typically belonging to different nodes). A packet sent to an anycast address is delivered to one of the interfaces identified by that address (the "nearest" one, according to the routing protocol's measure of distance). See [ADDR-ARCH].
solicited-node multicast address
a multicast address to which Neighbor Solicitation messages are sent. The algorithm for computing the address is given in [DISCOVERY].
link-layer address
a link-layer identifier for an interface. Examples include IEEE 802 addresses for Ethernet links and E.164 addresses for ISDN links.
link-local address
an address having link-only scope that can be used to reach neighboring nodes attached to the same link. All interfaces have a link-local unicast address.
site-local address
an address having scope that is limited to the local site.
global address
an address with unlimited scope.
communication
any packet exchange among nodes that requires that the address of each node used in the exchange remain the same for the duration of the packet exchange. Examples are a TCP connection or a UDP request- response.
tentative address
an address whose uniqueness on a link is being verified, prior to its assignment to an interface. A tentative address is not considered assigned to an interface in the usual sense. An interface discards received packets addressed to a tentative address, but accepts Neighbor Discovery packets related to Duplicate Address Detection for the tentative address.
preferred address
an address assigned to an interface whose use by upper layer protocols is unrestricted. Preferred addresses may be used as the source (or destination) address of packets sent from (or to) the interface.
deprecated address
An address assigned to an interface whose use is discouraged, but not forbidden. A deprecated address should no longer be used as a source address in new communications, but packets sent from or to deprecated addresses are delivered as expected. A deprecated address may continue to be used as a source address in communications where switching to a preferred address causes hardship to a specific upper-layer activity (e.g., an existing TCP connection).
valid address
a preferred or deprecated address. A valid address may appear as the source or destination address of a packet, and the internet routing system is expected to deliver packets sent to a valid address to their intended recipients.
invalid address
an address that is not assigned to any interface. A valid address becomes invalid when its valid lifetime expires. Invalid addresses should not appear as the destination or source address of a packet. In the former case, the internet routing system will be unable to deliver the packet, in the later case the recipient of the packet will be unable to respond to it.
preferred lifetime
the length of time that a valid address is preferred (i.e., the time until deprecation). When the preferred lifetime expires, the address becomes deprecated.
valid lifetime
the length of time an address remains in the valid state (i.e., the time until invalidation). The valid lifetime must be greater then or equal to the preferred lifetime. When the valid lifetime expires, the address becomes invalid.
interface identifier
a link-dependent identifier for an interface that is (at least) unique per link [ADDR-ARCH]. Stateless address autoconfiguration combines an interface identifier with a prefix to form an address. From address autoconfiguration's perspective, an interface identifier is a bit string of known length. The exact length of an interface identifier and the way it is created is defined in a separate link-type specific document that covers issues related to the transmission of IP over a particular link type (e.g., [IPv6-ETHER]). In many cases, the identifier will be the same as the interface's link- layer address.
IP
インターネットプロトコルバージョン6。IPv4およびという用語は、あいまいさを避けるために必要な文脈でのみ使用されます。
ノード
IPを実装する機器。
ルーター
自身に明示的に宛てられていないIPパケットを転送するノード。
ホスト
ルーターではないすべてのノード。
上位層
IPのすぐ上のプロトコル層。例としては、TCPやUDPなどのトランスポートプロトコル、ICMPなどの制御プロトコル、OSPFなどのルーティングプロトコル、およびIPX、AppleTalk、IP自身など、IP上で「トンネリング」される（すなわち、IPにカプセル化される）インターネット層またはより下位の層のプロトコルがあります。
リンク
ノードがリンク層で通信できる通信設備または媒体、すなわちIPのすぐ下の層。例としては、イーサネット（単純なものまたはブリッジされたもの）、PPPリンク、X.25、フレームリレー、またはATMのネットワーク、そしてIPv4やIPv6自身の上のトンネルなどのインターネット層（またはより上位の層）の「トンネル」があります。
インターフェイス
リンクへのノードの接続点。
パケット
IPヘッダーとペイロード。
アドレス
インターフェイスまたはインターフェイスの集合に対するIP層の識別子。
ユニキャストアドレス
単一のインターフェイスの識別子。ユニキャストアドレスに送信されたパケットは、そのアドレスによって識別されるインターフェイスに配送されます。
マルチキャストアドレス
（通常は異なるノードに属する）インターフェイスの集合の識別子。マルチキャストアドレスに送信されたパケットは、そのアドレスによって識別されるすべてのインターフェイスに配送されます。
エニーキャストアドレス
（通常は異なるノードに属する）インターフェイスの集合の識別子。エニーキャストアドレスに送信されたパケットは、そのアドレスによって識別されるインターフェイスの1つ（ルーティングプロトコルの距離の尺度による「最も近い」もの）に配送されます。[ADDR-ARCH]を参照してください。
要請ノードマルチキャストアドレス
近隣要請メッセージが送信されるマルチキャストアドレス。アドレスを計算するアルゴリズムは[DISCOVERY]に示されています。
リンク層アドレス
インターフェイスのリンク層の識別子。例としては、イーサネットリンクのIEEE 802アドレスや、ISDNリンクのE.164アドレスがあります。
リンクローカルアドレス
同じリンクに接続された近隣のノードに到達するために使用できる、リンクのみのスコープを持つアドレス。すべてのインターフェイスはリンクローカルユニキャストアドレスを持ちます。
サイトローカルアドレス
ローカルサイトに限定されたスコープを持つアドレス。
グローバルアドレス
無制限のスコープを持つアドレス。
通信
ノード間のパケットのやり取りのうち、やり取りで使用される各ノードのアドレスがパケットのやり取りの間同じままであることを必要とするもの。例としては、TCP接続やUDPの要求と応答があります。
仮アドレス（tentative address）
インターフェイスへの割り当ての前に、リンク上での一意性を検証中のアドレス。仮アドレスは、通常の意味ではインターフェイスに割り当てられたとはみなされません。インターフェイスは、仮アドレス宛てに受信したパケットを破棄しますが、その仮アドレスについての重複アドレス検出に関連する近隣探索のパケットは受け入れます。
推奨アドレス（preferred address）
インターフェイスに割り当てられたアドレスのうち、上位層のプロトコルによる使用が制限されていないもの。推奨アドレスは、インターフェイスから（またはインターフェイスへ）送信されるパケットの送信元（または宛先）アドレスとして使用できます。
非推奨アドレス（deprecated address）
インターフェイスに割り当てられたアドレスのうち、使用は推奨されないが禁止されてはいないもの。非推奨アドレスは、新しい通信の送信元アドレスとしてはもはや使用すべきではありませんが、非推奨アドレスから、または非推奨アドレスへ送信されたパケットは期待どおりに配送されます。推奨アドレスに切り替えると特定の上位層の活動（たとえば、既存のTCP接続）に支障が生じる通信では、非推奨アドレスを送信元アドレスとして引き続き使用してもかまいません。
有効なアドレス（valid address）
推奨アドレスまたは非推奨アドレス。有効なアドレスはパケットの送信元アドレスまたは宛先アドレスとして現れることができ、インターネットのルーティングシステムは、有効なアドレスに送信されたパケットを意図された受信者に配送することが期待されます。
無効なアドレス（invalid address）
どのインターフェイスにも割り当てられていないアドレス。有効なアドレスは、その有効生存期間が満了すると無効になります。無効なアドレスは、パケットの宛先アドレスまたは送信元アドレスとして現れるべきではありません。前者の場合、インターネットのルーティングシステムはパケットを配送できず、後者の場合、パケットの受信者はそれに応答できません。
推奨生存期間（preferred lifetime）
有効なアドレスが推奨である期間（すなわち、非推奨になるまでの時間）。推奨生存期間が満了すると、アドレスは非推奨になります。
有効生存期間（valid lifetime）
アドレスが有効な状態にとどまる期間（すなわち、無効になるまでの時間）。有効生存期間は推奨生存期間以上でなければなりません。有効生存期間が満了すると、アドレスは無効になります。
インターフェイス識別子
（少なくとも）リンクごとに一意である、インターフェイスのリンク依存の識別子[ADDR-ARCH]。ステートレスアドレス自動設定は、インターフェイス識別子とプレフィックスを組み合わせてアドレスを形成します。アドレス自動設定の観点からは、インターフェイス識別子は既知の長さのビット列です。インターフェイス識別子の正確な長さと作成方法は、特定のリンクタイプ上でのIPの伝送に関連する問題を扱う、リンクタイプ固有の別の文書（たとえば、[IPv6-ETHER]）で定義されます。多くの場合、識別子はインターフェイスのリンク層アドレスと同じになります。

3. DESIGN GOALS

3. 設計目標

Stateless autoconfiguration is designed with the following goals in mind:

ステートレスな自動設定は、次の目標を念頭に置いて設計されています。

  • Manual configuration of individual machines before connecting them to the network should not be required. Consequently, a mechanism is needed that allows a host to obtain or create unique addresses for each of its interfaces. Address autoconfiguration assumes that each interface can provide a unique identifier for that interface (i.e., an "interface identifier"). In the simplest case, an interface identifier consists of the interface's link-layer address. An interface identifier can be combined with a prefix to form an address.
  • Small sites consisting of a set of machines attached to a single link should not require the presence of a stateful server or router as a prerequisite for communicating. Plug-and-play communication is achieved through the use of link-local addresses. Link-local addresses have a well-known prefix that identifies the (single) shared link to which a set of nodes attach. A host forms a link-local address by appending its interface identifier to the link-local prefix.
  • A large site with multiple networks and routers should not require the presence of a stateful address configuration server. In order to generate site-local or global addresses, hosts must determine the prefixes that identify the subnets to which they attach. Routers generate periodic Router Advertisements that include options listing the set of active prefixes on a link.
  • Address configuration should facilitate the graceful renumbering of a site's machines. For example, a site may wish to renumber all of its nodes when it switches to a new network service provider. Renumbering is achieved through the leasing of addresses to interfaces and the assignment of multiple addresses to the same interface. Lease lifetimes provide the mechanism through which a site phases out old prefixes. The assignment of multiple addresses to an interface provides for a transition period during which both a new address and the one being phased out work simultaneously.
  • System administrators need the ability to specify whether stateless autoconfiguration, stateful autoconfiguration, or both should be used. Router Advertisements include flags specifying which mechanisms a host should use.
  • 個々のマシンをネットワークに接続する前に手動で設定する必要があるべきではありません。したがって、ホストが各インターフェイスについて一意のアドレスを取得または作成できるようにする仕組みが必要です。アドレス自動設定は、各インターフェイスがそのインターフェイスの一意の識別子（すなわち「インターフェイス識別子」）を提供できることを前提とします。最も単純な場合、インターフェイス識別子はインターフェイスのリンク層アドレスからなります。インターフェイス識別子をプレフィックスと組み合わせてアドレスを形成できます。
  • 単一のリンクに接続されたマシンの集まりからなる小規模なサイトでは、通信の前提条件としてステートフルなサーバーやルーターの存在を必要とするべきではありません。プラグアンドプレイの通信は、リンクローカルアドレスの使用によって実現されます。リンクローカルアドレスには、ノードの集まりが接続する（単一の）共有リンクを識別する周知のプレフィックスがあります。ホストは、リンクローカルプレフィックスに自身のインターフェイス識別子を付加することで、リンクローカルアドレスを形成します。
  • 複数のネットワークとルーターを持つ大規模なサイトでは、ステートフルなアドレス設定サーバーの存在を必要とするべきではありません。サイトローカルアドレスやグローバルアドレスを生成するために、ホストは接続先のサブネットを識別するプレフィックスを決定する必要があります。ルーターは、リンク上の有効なプレフィックスの集合を列挙するオプションを含むルーター広告を定期的に生成します。
  • アドレスの設定は、サイトのマシンの番号の付け直しを円滑に行えるようにすべきです。たとえば、サイトは、新しいネットワークサービスプロバイダーに切り替える際に、すべてのノードの番号を付け直したいと考えるかもしれません。番号の付け直しは、インターフェイスへのアドレスの貸し出しと、同じインターフェイスへの複数のアドレスの割り当てによって実現されます。貸し出しの生存期間は、サイトが古いプレフィックスを段階的に廃止するための仕組みを提供します。インターフェイスへの複数のアドレスの割り当てにより、新しいアドレスと段階的に廃止されるアドレスの両方が同時に機能する移行期間が得られます。
  • システム管理者には、ステートレスな自動設定、ステートフルな自動設定、またはその両方のいずれを使用すべきかを指定する能力が必要です。ルーター広告には、ホストがどの仕組みを使用すべきかを指定するフラグが含まれています。

4. PROTOCOL OVERVIEW

4. プロトコルの概要

This section provides an overview of the typical steps that take place when an interface autoconfigures itself. Autoconfiguration is performed only on multicast-capable links and begins when a multicast-capable interface is enabled, e.g., during system startup. Nodes (both hosts and routers) begin the autoconfiguration process by generating a link-local address for the interface. A link-local address is formed by appending the interface's identifier to the well-known link-local prefix.

この節では、インターフェイスが自身を自動設定する際に行われる典型的な手順の概要を示します。自動設定はマルチキャスト可能なリンク上でのみ行われ、マルチキャスト可能なインターフェイスが有効になったとき、たとえばシステムの起動中に開始されます。ノード（ホストとルーターの両方）は、インターフェイスのリンクローカルアドレスを生成することで自動設定のプロセスを開始します。リンクローカルアドレスは、周知のリンクローカルプレフィックスにインターフェイスの識別子を付加することで形成されます。

Before the link-local address can be assigned to an interface and used, however, a node must attempt to verify that this "tentative" address is not already in use by another node on the link. Specifically, it sends a Neighbor Solicitation message containing the tentative address as the target. If another node is already using that address, it will return a Neighbor Advertisement saying so. If another node is also attempting to use the same address, it will send a Neighbor Solicitation for the target as well. The exact number of times the Neighbor Solicitation is (re)transmitted and the delay time between consecutive solicitations is link-specific and may be set by system management.

しかし、リンクローカルアドレスをインターフェイスに割り当てて使用する前に、ノードは、この「仮の」アドレスがリンク上の別のノードによってすでに使用されていないことの検証を試みる必要があります。具体的には、仮アドレスをターゲットとして含む近隣要請メッセージを送信します。別のノードがすでにそのアドレスを使用している場合、そのノードはその旨を伝える近隣広告を返します。別のノードも同じアドレスを使用しようとしている場合、そのノードもそのターゲットについての近隣要請を送信します。近隣要請を（再）送信する正確な回数と連続する要請の間の遅延時間はリンク固有であり、システム管理によって設定できます。

If a node determines that its tentative link-local address is not unique, autoconfiguration stops and manual configuration of the interface is required. To simplify recovery in this case, it should be possible for an administrator to supply an alternate interface identifier that overrides the default identifier in such a way that the autoconfiguration mechanism can then be applied using the new (presumably unique) interface identifier. Alternatively, link-local and other addresses will need to be configured manually.

ノードが自身の仮のリンクローカルアドレスが一意でないと判断した場合、自動設定は停止し、インターフェイスの手動の設定が必要になります。この場合の回復を簡単にするために、管理者がデフォルトの識別子を上書きする代替のインターフェイス識別子を提供し、新しい（おそらく一意な）インターフェイス識別子を使用して自動設定の仕組みを適用できるようにすべきです。あるいは、リンクローカルアドレスやその他のアドレスを手動で設定する必要があります。

Once a node ascertains that its tentative link-local address is unique, it assigns it to the interface. At this point, the node has IP-level connectivity with neighboring nodes. The remaining autoconfiguration steps are performed only by hosts; the (auto)configuration of routers is beyond the scope of this document.

ノードは、自身の仮のリンクローカルアドレスが一意であることを確認すると、それをインターフェイスに割り当てます。この時点で、ノードは近隣のノードとIPレベルの接続性を持ちます。残りの自動設定の手順はホストだけが行います。ルーターの（自動）設定はこの文書の範囲外です。

The next phase of autoconfiguration involves obtaining a Router Advertisement or determining that no routers are present. If routers are present, they will send Router Advertisements that specify what sort of autoconfiguration a host should do. If no routers are present, stateful autoconfiguration should be invoked.

自動設定の次の段階では、ルーター広告を取得するか、ルーターが存在しないことを判断します。ルーターが存在する場合、ルーターは、ホストがどのような種類の自動設定を行うべきかを指定するルーター広告を送信します。ルーターが存在しない場合は、ステートフルな自動設定を呼び出すべきです。

Routers send Router Advertisements periodically, but the delay between successive advertisements will generally be longer than a host performing autoconfiguration will want to wait [DISCOVERY]. To obtain an advertisement quickly, a host sends one or more Router Solicitations to the all-routers multicast group. Router Advertisements contain two flags indicating what type of stateful autoconfiguration (if any) should be performed. A "managed address configuration" flag indicates whether hosts should use stateful autoconfiguration to obtain addresses. An "other stateful configuration" flag indicates whether hosts should use stateful autoconfiguration to obtain additional information (excluding addresses).

ルーターはルーター広告を定期的に送信しますが、連続する広告の間の遅延は、一般に、自動設定を行うホストが待ちたいと考える時間よりも長くなります[DISCOVERY]。広告をすばやく取得するために、ホストは全ルーターマルチキャストグループに1つ以上のルーター要請を送信します。ルーター広告には、どの種類のステートフルな自動設定を（もしあれば）行うべきかを示す2つのフラグが含まれています。「管理アドレス設定（managed address configuration）」フラグは、ホストがアドレスを取得するためにステートフルな自動設定を使用すべきかどうかを示します。「その他のステートフルな設定（other stateful configuration）」フラグは、ホストが（アドレスを除く）追加の情報を取得するためにステートフルな自動設定を使用すべきかどうかを示します。

Router Advertisements also contain zero or more Prefix Information options that contain information used by stateless address autoconfiguration to generate site-local and global addresses. It should be noted that the stateless and stateful address autoconfiguration fields in Router Advertisements are processed independently of one another, and a host may use both stateful and stateless address autoconfiguration simultaneously. One Prefix Information option field, the "autonomous address-configuration flag", indicates whether or not the option even applies to stateless autoconfiguration. If it does, additional option fields contain a subnet prefix together with lifetime values indicating how long addresses created from the prefix remain preferred and valid.

ルーター広告には、ステートレスアドレス自動設定がサイトローカルアドレスとグローバルアドレスを生成するために使用する情報を含む、0個以上のプレフィックス情報オプションも含まれています。ルーター広告のステートレスアドレス自動設定とステートフルアドレス自動設定のフィールドは互いに独立に処理され、ホストはステートフルとステートレスのアドレス自動設定を同時に使用できることに注意すべきです。プレフィックス情報オプションのフィールドの1つである「自律アドレス設定フラグ（autonomous address-configuration flag）」は、そもそもそのオプションがステートレスな自動設定に適用されるかどうかを示します。適用される場合、追加のオプションのフィールドに、サブネットのプレフィックスと、そのプレフィックスから作成されたアドレスがどれだけ長く推奨かつ有効であり続けるかを示す生存期間の値が含まれます。

Because routers generate Router Advertisements periodically, hosts will continually receive new advertisements. Hosts process the information contained in each advertisement as described above, adding to and refreshing information received in previous advertisements.

ルーターはルーター広告を定期的に生成するため、ホストは新しい広告を継続的に受信します。ホストは、各広告に含まれる情報を上記のとおりに処理し、以前の広告で受信した情報に追加したり、それを更新したりします。

For safety, all addresses must be tested for uniqueness prior to their assignment to an interface. In the case of addresses created through stateless autoconfig, however, the uniqueness of an address is determined primarily by the portion of the address formed from an interface identifier. Thus, if a node has already verified the uniqueness of a link-local address, additional addresses created from the same interface identifier need not be tested individually. In contrast, all addresses obtained manually or via stateful address autoconfiguration should be tested for uniqueness individually. To accommodate sites that believe the overhead of performing Duplicate Address Detection outweighs its benefits, the use of Duplicate Address Detection can be disabled through the administrative setting of a per-interface configuration flag.

安全のため、すべてのアドレスは、インターフェイスに割り当てる前に一意性を検査する必要があります。しかし、ステートレスな自動設定によって作成されたアドレスの場合、アドレスの一意性は主にインターフェイス識別子から形成されたアドレスの部分によって決まります。したがって、ノードがすでにリンクローカルアドレスの一意性を検証している場合、同じインターフェイス識別子から作成された追加のアドレスを個別に検査する必要はありません。これに対して、手動で、またはステートフルなアドレス自動設定によって取得されたすべてのアドレスは、個別に一意性を検査すべきです。重複アドレス検出を行うオーバーヘッドがその利点を上回ると考えるサイトに対応するために、インターフェイスごとの設定フラグを管理者が設定することで、重複アドレス検出の使用を無効にできます。

To speed the autoconfiguration process, a host may generate its link-local address (and verify its uniqueness) in parallel with waiting for a Router Advertisement. Because a router may delay responding to a Router Solicitation for a few seconds, the total time needed to complete autoconfiguration can be significantly longer if the two steps are done serially.

自動設定のプロセスを速めるために、ホストは、ルーター広告を待つのと並行して、リンクローカルアドレスを生成（してその一意性を検証）できます。ルーターはルーター要請への応答を数秒遅らせることがあるため、2つの手順を順番に行うと、自動設定を完了するのに必要な合計時間が大幅に長くなる可能性があります。

4.1. Site Renumbering

4.1. サイトの番号の付け直し

Address leasing facilitates site renumbering by providing a mechanism to time-out addresses assigned to interfaces in hosts. At present, upper layer protocols such as TCP provide no support for changing end-point addresses while a connection is open. If an end-point address becomes invalid, existing connections break and all communication to the invalid address fails. Even when applications use UDP as a transport protocol, addresses must generally remain the same during a packet exchange.

アドレスの貸し出しは、ホストのインターフェイスに割り当てられたアドレスをタイムアウトさせる仕組みを提供することで、サイトの番号の付け直しを容易にします。現在、TCPなどの上位層のプロトコルは、接続が開いている間に端点のアドレスを変更することをサポートしていません。端点のアドレスが無効になると、既存の接続は切断され、無効なアドレスへのすべての通信は失敗します。アプリケーションがトランスポートプロトコルとしてUDPを使用する場合でも、一般に、パケットのやり取りの間、アドレスは同じままである必要があります。

Dividing valid addresses into preferred and deprecated categories provides a way of indicating to upper layers that a valid address may become invalid shortly and that future communication using the address will fail, should the address's valid lifetime expire before communication ends. To avoid this scenario, higher layers should use a preferred address (assuming one of sufficient scope exists) to increase the likelihood that an address will remain valid for the duration of the communication. It is up to system administrators to set appropriate prefix lifetimes in order to minimize the impact of failed communication when renumbering takes place. The deprecation period should be long enough that most, if not all, communications are using the new address at the time an address becomes invalid.

有効なアドレスを推奨と非推奨のカテゴリーに分けることで、有効なアドレスが間もなく無効になる可能性があり、通信が終わる前にアドレスの有効生存期間が満了すれば、そのアドレスを使用する今後の通信は失敗することを上位層に示す方法が得られます。このシナリオを避けるために、上位層は、通信の間アドレスが有効であり続ける可能性を高めるように、（十分なスコープのものが存在すると仮定して）推奨アドレスを使用すべきです。番号の付け直しが行われる際の通信の失敗の影響を最小にするように、適切なプレフィックスの生存期間を設定するのはシステム管理者の役目です。非推奨の期間は、アドレスが無効になる時点で、すべてとは言わないまでもほとんどの通信が新しいアドレスを使用しているように十分長くすべきです。

The IP layer is expected to provide a means for upper layers (including applications) to select the most appropriate source address given a particular destination and possibly other constraints. An application may choose to select the source address itself before starting a new communication or may leave the address unspecified, in which case the upper networking layers will use the mechanism provided by the IP layer to choose a suitable address on the application's behalf.

IP層は、上位層（アプリケーションを含む）が、特定の宛先と、場合によってはその他の制約を考慮して、最も適切な送信元アドレスを選択するための手段を提供することが期待されます。アプリケーションは、新しい通信を開始する前に自分で送信元アドレスを選択することも、アドレスを指定しないままにすることもできます。後者の場合、上位のネットワーク層が、IP層の提供する仕組みを使用して、アプリケーションに代わって適切なアドレスを選択します。

Detailed address selection rules are beyond the scope of this document.

アドレスの選択の詳細な規則は、この文書の範囲外です。

5. PROTOCOL SPECIFICATION

5. プロトコルの仕様

Autoconfiguration is performed on a per-interface basis on multicast-capable interfaces. For multihomed hosts, autoconfiguration is performed independently on each interface. Autoconfiguration applies primarily to hosts, with two exceptions. Routers are expected to generate a link-local address using the procedure outlined below. In addition, routers perform Duplicate Address Detection on all addresses prior to assigning them to an interface.

自動設定は、マルチキャスト可能なインターフェイス上で、インターフェイスごとに行われます。マルチホームホストの場合、自動設定は各インターフェイスで独立に行われます。自動設定は主にホストに適用されますが、2つの例外があります。ルーターは、以下に概説する手順を使用してリンクローカルアドレスを生成することが期待されます。さらに、ルーターは、すべてのアドレスについて、インターフェイスに割り当てる前に重複アドレス検出を行います。

5.1. Node Configuration Variables

5.1. ノードの設定変数

A node MUST allow the following autoconfiguration-related variable to be configured by system management for each multicast interface:

ノードは、各マルチキャストインターフェイスについて、次の自動設定関連の変数をシステム管理によって設定できるようにしなければなりません（MUST）。

DupAddrDetectTransmits

DupAddrDetectTransmits

The number of consecutive Neighbor Solicitation messages sent while performing Duplicate Address Detection on a tentative address. A value of zero indicates that Duplicate Address Detection is not performed on tentative addresses. A value of one indicates a single transmission with no follow up retransmissions.

仮アドレスについて重複アドレス検出を行う間に送信される連続した近隣要請メッセージの数。値0は、仮アドレスについて重複アドレス検出を行わないことを示します。値1は、追加の再送なしに1回送信することを示します。

Default: 1, but may be overridden by a link-type specific value in the document that covers issues related to the transmission of IP over a particular link type (e.g., [IPv6-ETHER]).

デフォルト：1。ただし、特定のリンクタイプ上でのIPの伝送に関連する問題を扱う文書（たとえば、[IPv6-ETHER]）のリンクタイプ固有の値によって上書きされる場合があります。

Autoconfiguration also assumes the presence of the variable RetransTimer as defined in [DISCOVERY]. For autoconfiguration purposes, RetransTimer specifies the delay between consecutive Neighbor Solicitation transmissions performed during Duplicate Address Detection (if DupAddrDetectTransmits is greater than 1), as well as the time a node waits after sending the last Neighbor Solicitation before ending the Duplicate Address Detection process.

自動設定は、[DISCOVERY]で定義されている変数RetransTimerが存在することも前提とします。自動設定の目的では、RetransTimerは、重複アドレス検出の間に行われる連続した近隣要請の送信の間の遅延（DupAddrDetectTransmitsが1より大きい場合）と、最後の近隣要請を送信してから重複アドレス検出のプロセスを終了するまでにノードが待つ時間を指定します。

5.2. Autoconfiguration-Related Variables

5.2. 自動設定関連の変数

A host maintains a number of data structures and flags related to autoconfiguration. In the following, we present conceptual variables and show how they are used to perform autoconfiguration. The specific variables are used for demonstration purposes only, and an implementation is not required to have them, so long as its external behavior is consistent with that described in this document.

ホストは、自動設定に関連するいくつかのデータ構造とフラグを維持します。以下では、概念上の変数を示し、それらが自動設定を行うためにどのように使用されるかを示します。具体的な変数は説明のためだけに使用されるものであり、外部から見た振る舞いがこの文書で説明されているものと一致する限り、実装がそれらを持つ必要はありません。

Beyond the formation of a link-local address and using Duplicate Address Detection, how routers (auto)configure their interfaces is beyond the scope of this document.

リンクローカルアドレスの形成と重複アドレス検出の使用を除き、ルーターがインターフェイスをどのように（自動）設定するかは、この文書の範囲外です。

Hosts maintain the following variables on a per-interface basis:

ホストは、インターフェイスごとに次の変数を維持します。

ManagedFlag
Copied from the M flag field (i.e., the "managed address configuration" flag) of the most recently received Router Advertisement message. The flag indicates whether or not addresses are to be configured using the stateful autoconfiguration mechanism. It starts out in a FALSE state.
OtherConfigFlag

Copied from the O flag field (i.e., the "other stateful configuration" flag) of the most recently received Router Advertisement message. The flag indicates whether or not information other than addresses is to be obtained using the stateful autoconfiguration mechanism. It starts out in a FALSE state.

In addition, when the value of the ManagedFlag is TRUE, the value of OtherConfigFlag is implicitely TRUE as well. It is not a valid configuration for a host to use stateful address autoconfiguration to request addresses only, without also accepting other configuration information.

ManagedFlag
最後に受信したルーター広告メッセージのMフラグのフィールド（すなわち「管理アドレス設定」フラグ）からコピーされます。このフラグは、ステートフルな自動設定の仕組みを使用してアドレスを設定するかどうかを示します。初期状態はFALSEです。
OtherConfigFlag

最後に受信したルーター広告メッセージのOフラグのフィールド（すなわち「その他のステートフルな設定」フラグ）からコピーされます。このフラグは、ステートフルな自動設定の仕組みを使用してアドレス以外の情報を取得するかどうかを示します。初期状態はFALSEです。

さらに、ManagedFlagの値がTRUEの場合、OtherConfigFlagの値も暗黙的にTRUEになります。ホストが、その他の設定情報を受け入れずに、アドレスだけを要求するためにステートフルなアドレス自動設定を使用することは、有効な設定ではありません。

A host also maintains a list of addresses together with their corresponding lifetimes. The address list contains both autoconfigured addresses and those configured manually.

ホストは、アドレスの一覧も、対応する生存期間とともに維持します。アドレスの一覧には、自動設定されたアドレスと手動で設定されたアドレスの両方が含まれます。

5.3. Creation of Link-Local Addresses

5.3. リンクローカルアドレスの作成

A node forms a link-local address whenever an interface becomes enabled. An interface may become enabled after any of the following events:

ノードは、インターフェイスが有効になるたびにリンクローカルアドレスを形成します。インターフェイスは、次のいずれかのイベントの後に有効になる可能性があります。

  • The interface is initialized at system startup time.
  • The interface is reinitialized after a temporary interface failure or after being temporarily disabled by system management.
  • The interface attaches to a link for the first time.
  • The interface becomes enabled by system management after having been administratively disabled.
  • システムの起動時にインターフェイスが初期化される。
  • 一時的なインターフェイスの障害の後、またはシステム管理によって一時的に無効にされた後に、インターフェイスが再初期化される。
  • インターフェイスが初めてリンクに接続された。
  • 管理上無効にされていたインターフェイスが、システム管理によって有効にされた。

A link-local address is formed by prepending the well-known link- local prefix FE80::0 [ADDR-ARCH] (of appropriate length) to the interface identifier. If the interface identifier has a length of N bits, the interface identifier replaces the right-most N zero bits of the link-local prefix. If the interface identifier is more than 118 bits in length, autoconfiguration fails and manual configuration is required. Note that interface identifiers will typically be 64-bits long and based on EUI-64 identifiers as described in [ADDR-ARCH].

リンクローカルアドレスは、（適切な長さの）周知のリンクローカルプレフィックスFE80::0[ADDR-ARCH]をインターフェイス識別子の前に付加することで形成されます。インターフェイス識別子の長さがNビットの場合、インターフェイス識別子はリンクローカルプレフィックスの右端のNビットの0を置き換えます。インターフェイス識別子の長さが118ビットを超える場合、自動設定は失敗し、手動の設定が必要になります。インターフェイス識別子は、通常、[ADDR-ARCH]で説明されているとおり、64ビットの長さで、EUI-64識別子に基づくことに注意してください。

A link-local address has an infinite preferred and valid lifetime; it is never timed out.

リンクローカルアドレスの推奨生存期間と有効生存期間は無限であり、タイムアウトすることはありません。

5.4. Duplicate Address Detection

5.4. 重複アドレス検出

Duplicate Address Detection is performed on unicast addresses prior to assigning them to an interface whose DupAddrDetectTransmits variable is greater than zero. Duplicate Address Detection MUST take place on all unicast addresses, regardless of whether they are obtained through stateful, stateless or manual configuration, with the exception of the following cases:

重複アドレス検出は、DupAddrDetectTransmits変数が0より大きいインターフェイスにユニキャストアドレスを割り当てる前に、そのアドレスについて行われます。重複アドレス検出は、次の場合を除き、ステートフル、ステートレス、手動の設定のいずれによって取得されたかにかかわらず、すべてのユニキャストアドレスについて行われなければなりません（MUST）。

  • Duplicate Address Detection MUST NOT be performed on anycast addresses.
  • Each individual unicast address SHOULD be tested for uniqueness. However, when stateless address autoconfiguration is used, address uniqueness is determined solely by the interface identifier, assuming that subnet prefixes are assigned correctly (i.e., if all of an interface's addresses are generated from the same identifier, either all addresses or none of them will be duplicates). Thus, for a set of addresses formed from the same interface identifier, it is sufficient to check that the link- local address generated from the identifier is unique on the link. In such cases, the link-local address MUST be tested for uniqueness, and if no duplicate address is detected, an implementation MAY choose to skip Duplicate Address Detection for additional addresses derived from the same interface identifier.
  • 重複アドレス検出をエニーキャストアドレスについて行ってはなりません（MUST NOT）。
  • 個々のユニキャストアドレスについて一意性を検査すべきです（SHOULD）。しかし、ステートレスアドレス自動設定が使用される場合、サブネットのプレフィックスが正しく割り当てられていると仮定すれば、アドレスの一意性はインターフェイス識別子だけによって決まります（すなわち、インターフェイスのすべてのアドレスが同じ識別子から生成される場合、すべてのアドレスが重複するか、どれも重複しないかのいずれかです）。したがって、同じインターフェイス識別子から形成されたアドレスの集合については、その識別子から生成されたリンクローカルアドレスがリンク上で一意であることを検査すれば十分です。そのような場合、リンクローカルアドレスの一意性を検査しなければなりません（MUST）。また、重複アドレスが検出されなければ、実装は、同じインターフェイス識別子から導出された追加のアドレスについての重複アドレス検出を省略することを選択してもよいです（MAY）。

The procedure for detecting duplicate addresses uses Neighbor Solicitation and Advertisement messages as described below. If a duplicate address is discovered during the procedure, the address cannot be assigned to the interface. If the address is derived from an interface identifier, a new identifier will need to be assigned to the interface, or all IP addresses for the interface will need to be manually configured. Note that the method for detecting duplicates is not completely reliable, and it is possible that duplicate addresses will still exist (e.g., if the link was partitioned while Duplicate Address Detection was performed).

重複するアドレスを検出する手順では、以下で説明するとおり、近隣要請と近隣広告のメッセージを使用します。手順の間に重複アドレスが発見された場合、そのアドレスはインターフェイスに割り当てることができません。アドレスがインターフェイス識別子から導出されている場合は、インターフェイスに新しい識別子を割り当てるか、インターフェイスのすべてのIPアドレスを手動で設定する必要があります。重複を検出する方法は完全に信頼できるものではなく、重複アドレスがそれでも存在する可能性がある（たとえば、重複アドレス検出が行われている間にリンクが分断されていた場合）ことに注意してください。

An address on which the duplicate Address Detection Procedure is applied is said to be tentative until the procedure has completed successfully. A tentative address is not considered "assigned to an interface" in the traditional sense. That is, the interface must accept Neighbor Solicitation and Advertisement messages containing the tentative address in the Target Address field, but processes such packets differently from those whose Target Address matches an address assigned to the interface. Other packets addressed to the tentative address should be silently discarded.

重複アドレス検出の手順が適用されるアドレスは、手順が正常に完了するまで仮（tentative）であるといいます。仮アドレスは、従来の意味では「インターフェイスに割り当てられた」とはみなされません。すなわち、インターフェイスは、Target Addressフィールドに仮アドレスを含む近隣要請と近隣広告のメッセージを受け入れる必要がありますが、そのようなパケットは、Target Addressがインターフェイスに割り当てられたアドレスと一致するパケットとは異なる方法で処理します。仮アドレス宛てのその他のパケットは、黙って破棄すべきです。

It should also be noted that Duplicate Address Detection must be performed prior to assigning an address to an interface in order to prevent multiple nodes from using the same address simultaneously. If a node begins using an address in parallel with Duplicate Address Detection, and another node is already using the address, the node performing Duplicate Address Detection will erroneously process traffic intended for the other node, resulting in such possible negative consequences as the resetting of open TCP connections.

複数のノードが同じアドレスを同時に使用するのを防ぐために、重複アドレス検出はアドレスをインターフェイスに割り当てる前に行う必要があることにも注意すべきです。ノードが重複アドレス検出と並行してアドレスの使用を開始し、別のノードがすでにそのアドレスを使用している場合、重複アドレス検出を行っているノードは別のノード宛てのトラフィックを誤って処理し、その結果、開いているTCP接続のリセットなどの悪影響が生じる可能性があります。

The following subsections describe specific tests a node performs to verify an address's uniqueness. An address is considered unique if none of the tests indicate the presence of a duplicate address within RetransTimer milliseconds after having sent DupAddrDetectTransmits Neighbor Solicitations. Once an address is determined to be unique, it may be assigned to an interface.

以下の小節では、アドレスの一意性を検証するためにノードが行う具体的な検査を説明します。DupAddrDetectTransmits回の近隣要請を送信してからRetransTimerミリ秒以内に、どの検査も重複アドレスの存在を示さなかった場合、アドレスは一意であるとみなされます。アドレスが一意であると判断されると、そのアドレスをインターフェイスに割り当てることができます。

5.4.1. Message Validation

5.4.1. メッセージの検証

A node MUST silently discard any Neighbor Solicitation or Advertisement message that does not pass the validity checks specified in [DISCOVERY]. A solicitation that passes these validity checks is called a valid solicitation or valid advertisement.

ノードは、[DISCOVERY]で規定されている有効性の検査に合格しない近隣要請メッセージまたは近隣広告メッセージを黙って破棄しなければなりません（MUST）。これらの有効性の検査に合格した要請は、有効な要請または有効な広告と呼ばれます。

5.4.2. Sending Neighbor Solicitation Messages

5.4.2. 近隣要請メッセージの送信

Before sending a Neighbor Solicitation, an interface MUST join the all-nodes multicast address and the solicited-node multicast address of the tentative address. The former insures that the node receives Neighbor Advertisements from other nodes already using the address; the latter insures that two nodes attempting to use the same address simultaneously detect each other's presence.

近隣要請を送信する前に、インターフェイスは、全ノードマルチキャストアドレスと仮アドレスの要請ノードマルチキャストアドレスに参加しなければなりません（MUST）。前者は、そのアドレスをすでに使用している他のノードからの近隣広告をノードが受信することを保証します。後者は、同じアドレスを同時に使用しようとしている2つのノードが互いの存在を検出することを保証します。

To check an address, a node sends DupAddrDetectTransmits Neighbor Solicitations, each separated by RetransTimer milliseconds. The solicitation's Target Address is set to the address being checked, the IP source is set to the unspecified address and the IP destination is set to the solicited-node multicast address of the target address.

アドレスを検査するために、ノードはRetransTimerミリ秒ずつ間隔を空けて、DupAddrDetectTransmits回の近隣要請を送信します。要請のTarget Addressは検査されるアドレスに設定され、IPの送信元は未指定アドレスに設定され、IPの宛先はターゲットアドレスの要請ノードマルチキャストアドレスに設定されます。

If the Neighbor Solicitation is the first message to be sent from an interface after interface (re)initialization, the node should delay sending the message by a random delay between 0 and MAX_RTR_SOLICITATION_DELAY as specified in [DISCOVERY]. This serves to alleviate congestion when many nodes start up on the link at the same time, such as after a power failure, and may help to avoid race conditions when more than one node is trying to solicit for the same address at the same time. In order to improve the robustness of the Duplicate Address Detection algorithm, an interface MUST receive and process datagrams sent to the all-nodes multicast address or solicited-node multicast address of the tentative address while delaying transmission of the initial Neighbor Solicitation.

近隣要請がインターフェイスの（再）初期化後にインターフェイスから送信される最初のメッセージである場合、ノードは、[DISCOVERY]で規定されているとおり、0からMAX_RTR_SOLICITATION_DELAYまでのランダムな遅延だけメッセージの送信を遅らせるべきです。これは、停電の後など、多くのノードがリンク上で同時に起動する場合の輻輳を緩和するのに役立ち、複数のノードが同時に同じアドレスについて要請しようとしている場合の競合状態を避けるのにも役立つかもしれません。重複アドレス検出のアルゴリズムの堅牢性を向上させるために、インターフェイスは、最初の近隣要請の送信を遅らせている間、全ノードマルチキャストアドレスまたは仮アドレスの要請ノードマルチキャストアドレスに送信されたデータグラムを受信して処理しなければなりません（MUST）。

5.4.3. Receiving Neighbor Solicitation Messages

5.4.3. 近隣要請メッセージの受信

On receipt of a valid Neighbor Solicitation message on an interface, node behavior depends on whether the target address is tentative or not. If the target address is not tentative (i.e., it is assigned to the receiving interface), the solicitation is processed as described in [DISCOVERY]. If the target address is tentative, and the source address is a unicast address, the solicitation's sender is performing address resolution on the target; the solicitation should be silently ignored. Otherwise, processing takes place as described below. In all cases, a node MUST NOT respond to a Neighbor Solicitation for a tentative address.

インターフェイスで有効な近隣要請メッセージを受信したときのノードの振る舞いは、ターゲットアドレスが仮であるかどうかによって異なります。ターゲットアドレスが仮でない（すなわち、受信インターフェイスに割り当てられている）場合、要請は[DISCOVERY]で説明されているとおりに処理されます。ターゲットアドレスが仮であり、送信元アドレスがユニキャストアドレスである場合、要請の送信者はターゲットについてアドレス解決を行っています。その要請は黙って無視すべきです。それ以外の場合は、以下で説明するとおりに処理が行われます。いずれの場合も、ノードは仮アドレスについての近隣要請に応答してはなりません（MUST NOT）。

If the source address of the Neighbor Solicitation is the unspecified address, the solicitation is from a node performing Duplicate Address Detection. If the solicitation is from another node, the tentative address is a duplicate and should not be used (by either node). If the solicitation is from the node itself (because the node loops back multicast packets), the solicitation does not indicate the presence of a duplicate address.

近隣要請の送信元アドレスが未指定アドレスである場合、その要請は重複アドレス検出を行っているノードからのものです。要請が別のノードからのものである場合、仮アドレスは重複しており、（どちらのノードも）使用すべきではありません。要請がノード自身からのものである（ノードがマルチキャストのパケットをループバックするため）場合、その要請は重複アドレスの存在を示しません。

Implementor's Note: many interfaces provide a way for upper layers to selectively enable and disable the looping back of multicast packets. The details of how such a facility is implemented may prevent Duplicate Address Detection from working correctly. See the Appendix for further discussion.

実装者への注記：多くのインターフェイスは、上位層がマルチキャストのパケットのループバックを選択的に有効化・無効化する方法を提供しています。そのような機能の実装方法の詳細によっては、重複アドレス検出が正しく機能しない場合があります。さらなる議論については付録を参照してください。

The following tests identify conditions under which a tentative address is not unique:

次の検査は、仮アドレスが一意でない条件を識別します。

  • If a Neighbor Solicitation for a tentative address is received prior to having sent one, the tentative address is a duplicate. This condition occurs when two nodes run Duplicate Address Detection simultaneously, but transmit initial solicitations at different times (e.g., by selecting different random delay values before transmitting an initial solicitation).
  • If the actual number of Neighbor Solicitations received exceeds the number expected based on the loopback semantics (e.g., the interface does not loopback packet, yet one or more solicitations was received), the tentative address is a duplicate. This condition occurs when two nodes run Duplicate Address Detection simultaneously and transmit solicitations at roughly the same time.
  • 仮アドレスについての近隣要請を、自分が送信する前に受信した場合、その仮アドレスは重複しています。この条件は、2つのノードが重複アドレス検出を同時に実行しているが、（たとえば、最初の要請を送信する前に異なるランダムな遅延の値を選択したことにより）最初の要請を異なる時刻に送信した場合に発生します。
  • 実際に受信した近隣要請の数が、ループバックの意味に基づいて期待される数を超えた場合（たとえば、インターフェイスがパケットをループバックしないのに、1つ以上の要請を受信した場合）、その仮アドレスは重複しています。この条件は、2つのノードが重複アドレス検出を同時に実行し、ほぼ同時に要請を送信した場合に発生します。

5.4.4. Receiving Neighbor Advertisement Messages

5.4.4. 近隣広告メッセージの受信

On receipt of a valid Neighbor Advertisement message on an interface, node behavior depends on whether the target address is tentative or matches a unicast or anycast address assigned to the interface. If the target address is assigned to the receiving interface, the solicitation is processed as described in [DISCOVERY]. If the target address is tentative, the tentative address is not unique.

インターフェイスで有効な近隣広告メッセージを受信したときのノードの振る舞いは、ターゲットアドレスが仮であるか、それともインターフェイスに割り当てられたユニキャストアドレスまたはエニーキャストアドレスと一致するかによって異なります。ターゲットアドレスが受信インターフェイスに割り当てられている場合、要請は[DISCOVERY]で説明されているとおりに処理されます。ターゲットアドレスが仮である場合、その仮アドレスは一意ではありません。

5.4.5. When Duplicate Address Detection Fails

5.4.5. 重複アドレス検出が失敗した場合

A tentative address that is determined to be a duplicate as described above, MUST NOT be assigned to an interface and the node SHOULD log a system management error. If the address is a link-local address formed from an interface identifier, the interface SHOULD be disabled.

上記のとおりに重複していると判断された仮アドレスを、インターフェイスに割り当ててはなりません（MUST NOT）。また、ノードはシステム管理のエラーを記録すべきです（SHOULD）。アドレスがインターフェイス識別子から形成されたリンクローカルアドレスである場合、インターフェイスを無効にすべきです（SHOULD）。

5.5. Creation of Global and Site-Local Addresses

5.5. グローバルアドレスとサイトローカルアドレスの作成

Global and site-local addresses are formed by appending an interface identifier to a prefix of appropriate length. Prefixes are obtained from Prefix Information options contained in Router Advertisements. Creation of global and site-local addresses and configuration of other parameters as described in this section SHOULD be locally configurable. However, the processing described below MUST be enabled by default.

グローバルアドレスとサイトローカルアドレスは、適切な長さのプレフィックスにインターフェイス識別子を付加することで形成されます。プレフィックスは、ルーター広告に含まれるプレフィックス情報オプションから取得されます。この節で説明するグローバルアドレスとサイトローカルアドレスの作成とその他のパラメーターの設定は、ローカルで設定可能にすべきです（SHOULD）。しかし、以下で説明する処理は、デフォルトで有効にしなければなりません（MUST）。

5.5.1. Soliciting Router Advertisements

5.5.1. ルーター広告の要請

Router Advertisements are sent periodically to the all-nodes multicast address. To obtain an advertisement quickly, a host sends out Router Solicitations as described in [DISCOVERY].

ルーター広告は、全ノードマルチキャストアドレスに定期的に送信されます。広告をすばやく取得するために、ホストは[DISCOVERY]で説明されているとおりにルーター要請を送信します。

5.5.2. Absence of Router Advertisements

5.5.2. ルーター広告がない場合

If a link has no routers, a host MUST attempt to use stateful autoconfiguration to obtain addresses and other configuration information. An implementation MAY provide a way to disable the invocation of stateful autoconfiguration in this case, but the default SHOULD be enabled. From the perspective of autoconfiguration, a link has no routers if no Router Advertisements are received after having sent a small number of Router Solicitations as described in [DISCOVERY].

リンクにルーターがない場合、ホストは、アドレスとその他の設定情報を取得するために、ステートフルな自動設定の使用を試みなければなりません（MUST）。実装は、この場合にステートフルな自動設定の呼び出しを無効にする方法を提供してもよいです（MAY）が、デフォルトでは有効にすべきです（SHOULD）。自動設定の観点からは、[DISCOVERY]で説明されているとおりに少数のルーター要請を送信した後にルーター広告を受信しない場合、リンクにはルーターがありません。

5.5.3. Router Advertisement Processing

5.5.3. ルーター広告の処理

On receipt of a valid Router Advertisement (as defined in [DISCOVERY]), a host copies the value of the advertisement's M bit into ManagedFlag. If the value of ManagedFlag changes from FALSE to TRUE, and the host is not already running the stateful address autoconfiguration protocol, the host should invoke the stateful address autoconfiguration protocol, requesting both address information and other information. If the value of the ManagedFlag changes from TRUE to FALSE, the host should continue running the stateful address autoconfiguration, i.e., the change in the value of the ManagedFlag has no effect. If the value of the flag stays unchanged, no special action takes place. In particular, a host MUST NOT reinvoke stateful address configuration if it is already participating in the stateful protocol as a result of an earlier advertisement.

（[DISCOVERY]で定義されている）有効なルーター広告を受信すると、ホストは広告のMビットの値をManagedFlagにコピーします。ManagedFlagの値がFALSEからTRUEに変わり、ホストがまだステートフルアドレス自動設定のプロトコルを実行していない場合、ホストは、アドレス情報とその他の情報の両方を要求して、ステートフルアドレス自動設定のプロトコルを呼び出すべきです。ManagedFlagの値がTRUEからFALSEに変わった場合、ホストはステートフルアドレス自動設定の実行を続けるべきです。すなわち、ManagedFlagの値の変化は何の影響も及ぼしません。フラグの値が変わらない場合、特別な動作は行われません。特に、ホストは、以前の広告の結果としてすでにステートフルなプロトコルに参加している場合、ステートフルなアドレスの設定を再び呼び出してはなりません（MUST NOT）。

An advertisement's O flag field is processed in an analogous manner. A host copies the value of the O flag into OtherConfigFlag. If the value of OtherConfigFlag changes from FALSE to TRUE, the host should invoke the stateful autoconfiguration protocol, requesting information (excluding addresses if ManagedFlag is set to FALSE). If the value of the OtherConfigFlag changes from TRUE to FALSE, the host should continue running the stateful address autoconfiguration protocol, i.e., the change in the value of OtherConfigFlag has no effect. If the value of the flag stays unchanged, no special action takes place. In particular, a host MUST NOT reinvoke stateful configuration if it is already participating in the stateful protocol as a result of an earlier advertisement.

広告のOフラグのフィールドも同様の方法で処理されます。ホストはOフラグの値をOtherConfigFlagにコピーします。OtherConfigFlagの値がFALSEからTRUEに変わった場合、ホストは、（ManagedFlagがFALSEに設定されている場合はアドレスを除く）情報を要求して、ステートフルな自動設定のプロトコルを呼び出すべきです。OtherConfigFlagの値がTRUEからFALSEに変わった場合、ホストはステートフルアドレス自動設定のプロトコルの実行を続けるべきです。すなわち、OtherConfigFlagの値の変化は何の影響も及ぼしません。フラグの値が変わらない場合、特別な動作は行われません。特に、ホストは、以前の広告の結果としてすでにステートフルなプロトコルに参加している場合、ステートフルな設定を再び呼び出してはなりません（MUST NOT）。

For each Prefix-Information option in the Router Advertisement:

ルーター広告の各プレフィックス情報オプションについて：

  1. If the Autonomous flag is not set, silently ignore the Prefix Information option.
  2. If the prefix is the link-local prefix, silently ignore the Prefix Information option.
  3. If the preferred lifetime is greater than the valid lifetime, silently ignore the Prefix Information option. A node MAY wish to log a system management error in this case.
  4. If the prefix advertised does not match the prefix of an address already in the list, and the Valid Lifetime is not 0, form an address (and add it to the list) by combining the advertised prefix with the link's interface identifier as follows:
  1. Autonomousフラグが設定されていない場合は、そのプレフィックス情報オプションを黙って無視します。
  2. プレフィックスがリンクローカルのプレフィックスである場合は、プレフィックス情報オプションを黙って無視します。
  3. 推奨生存期間が有効生存期間より大きい場合は、そのプレフィックス情報オプションを黙って無視します。この場合、ノードはシステム管理のエラーを記録してもよいです（MAY）。
  4. 広告されたプレフィックスが一覧にすでにあるアドレスのプレフィックスと一致せず、Valid Lifetimeが0でない場合は、次のように、広告されたプレフィックスとリンクのインターフェイス識別子を組み合わせてアドレスを形成（して一覧に追加）します。
   |            128 - N bits               |       N bits           |
   +---------------------------------------+------------------------+
   |            link prefix                |  interface identifier  |
   +----------------------------------------------------------------+

   |            128 - N bits               |       N bits           |
   +---------------------------------------+------------------------+
   |            link prefix                |  interface identifier  |
   +----------------------------------------------------------------+

If the sum of the prefix length and interface identifier length does not equal 128 bits, the Prefix Information option MUST be ignored. An implementation MAY wish to log a system management error in this case. It is the responsibility of the system administrator to insure that the lengths of prefixes contained in Router Advertisements are consistent with the length of interface identifiers for that link type. Note that interface identifiers will typically be 64-bits long and based on EUI-64 identifiers as described in [ADDR-ARCH].

プレフィックス長とインターフェイス識別子の長さの和が128ビットに等しくない場合、プレフィックス情報オプションは無視されなければなりません（MUST）。この場合、実装はシステム管理のエラーを記録してもよいです（MAY）。ルーター広告に含まれるプレフィックスの長さがそのリンクタイプのインターフェイス識別子の長さと一致することを保証するのは、システム管理者の責任です。インターフェイス識別子は、通常、[ADDR-ARCH]で説明されているとおり、64ビットの長さで、EUI-64識別子に基づくことに注意してください。

If an address is formed successfully, the host adds it to the list of addresses assigned to the interface, initializing its preferred and valid lifetime values from the Prefix Information option.

アドレスの形成に成功した場合、ホストはそのアドレスをインターフェイスに割り当てられたアドレスの一覧に追加し、その推奨生存期間と有効生存期間の値をプレフィックス情報オプションから初期化します。

  1. If the advertised prefix matches the prefix of an autoconfigured address (i.e., one obtained via stateless or stateful address autoconfiguration) in the list of addresses associated with the interface, the specific action to perform depends on the Valid Lifetime in the received advertisement and the Lifetime associated with the previously autoconfigured address (which we call StoredLifetime in the discussion that follows):

    1. If the received Lifetime is greater than 2 hours or greater than StoredLifetime, update the stored Lifetime of the corresponding address.
    2. If the StoredLifetime is less than or equal to 2 hours and the received Lifetime is less than or equal to StoredLifetime, ignore the prefix, unless the Router Advertisement from which this Prefix Information option was obtained has been authenticated (e.g., via IPSec [RFC2402]). If the Router Advertisment was authenticated, the StoredLifetime should be set to the Lifetime in the received option.
    3. Otherwise, reset the stored Lifetime in the corresponding address to two hours.

    The above rules address a specific denial of service attack in which a bogus advertisement could contain prefixes with very small Valid Lifetimes. Without the above rules, a single unauthenticated advertisement containing bogus Prefix Information options with short Lifetimes could cause all of a node's addresses to expire prematurely. The above rules insure that legitimate advertisements (which are sent periodically) will "cancel" the short lifetimes before they actually take effect.

  1. 広告されたプレフィックスが、インターフェイスに関連付けられたアドレスの一覧にある自動設定されたアドレス（すなわち、ステートレスまたはステートフルなアドレス自動設定によって取得されたもの）のプレフィックスと一致する場合、行うべき具体的な動作は、受信した広告のValid Lifetimeと、以前に自動設定されたアドレスに関連付けられた生存期間（以下の議論ではStoredLifetimeと呼びます）によって異なります。

    1. 受信した生存期間が2時間より大きいか、StoredLifetimeより大きい場合は、対応するアドレスの格納された生存期間を更新します。
    2. StoredLifetimeが2時間以下で、受信した生存期間がStoredLifetime以下である場合は、このプレフィックス情報オプションを取得したルーター広告が（たとえば、IPSec[RFC2402]によって）認証されていない限り、そのプレフィックスを無視します。ルーター広告が認証されていた場合は、StoredLifetimeを受信したオプションの生存期間に設定すべきです。
    3. それ以外の場合は、対応するアドレスの格納された生存期間を2時間にリセットします。

    上記の規則は、偽の広告に非常に短いValid Lifetimeを持つプレフィックスが含まれる可能性がある、特定のサービス拒否攻撃に対処するものです。上記の規則がなければ、短い生存期間を持つ偽のプレフィックス情報オプションを含む、認証されていない広告が1つあるだけで、ノードのすべてのアドレスが早期に満了してしまう可能性があります。上記の規則により、（定期的に送信される）正当な広告が、短い生存期間が実際に効力を持つ前にそれを「取り消す」ことが保証されます。

5.5.4. Address Lifetime Expiry

5.5.4. アドレスの生存期間の満了

A preferred address becomes deprecated when its preferred lifetime expires. A deprecated address SHOULD continue to be used as a source address in existing communications, but SHOULD NOT be used in new communications if an alternate (non-deprecated) address is available and has sufficient scope. IP and higher layers (e.g., TCP, UDP) MUST continue to accept datagrams destined to a deprecated address since a deprecated address is still a valid address for the interface. An implementation MAY prevent any new communication from using a deprecated address, but system management MUST have the ability to disable such a facility, and the facility MUST be disabled by default.

推奨アドレスは、その推奨生存期間が満了すると非推奨になります。非推奨アドレスは、既存の通信では送信元アドレスとして引き続き使用すべきです（SHOULD）が、代替の（非推奨でない）アドレスが利用可能で十分なスコープを持つ場合は、新しい通信で使用すべきではありません（SHOULD NOT）。非推奨アドレスはまだインターフェイスの有効なアドレスであるため、IPとより上位の層（たとえば、TCP、UDP）は、非推奨アドレス宛てのデータグラムを引き続き受け入れなければなりません（MUST）。実装は、新しい通信が非推奨アドレスを使用するのを防いでもよいです（MAY）。しかし、システム管理はそのような機能を無効にする能力を持たなければなりません（MUST）。また、その機能はデフォルトで無効にしなければなりません（MUST）。

An address (and its association with an interface) becomes invalid when its valid lifetime expires. An invalid address MUST NOT be used as a source address in outgoing communications and MUST NOT be recognized as a destination on a receiving interface.

アドレス（とそのインターフェイスとの関連付け）は、その有効生存期間が満了すると無効になります。無効なアドレスを、送信する通信の送信元アドレスとして使用してはなりません（MUST NOT）。また、受信インターフェイスで宛先として認識してはなりません（MUST NOT）。

5.6. Configuration Consistency

5.6. 設定の一貫性

It is possible for hosts to obtain address information using both stateless and stateful protocols since both may be enabled at the same time. It is also possible that the values of other configuration parameters such as MTU size and hop limit will be learned from both Router Advertisements and the stateful autoconfiguration protocol. If the same configuration information is provided by multiple sources, the value of this information should be consistent. However, it is not considered a fatal error if information received from multiple sources is inconsistent. Hosts accept the union of all information received via the stateless and stateful protocols. If inconsistent information is learned different sources, the most recently obtained values always have precedence over information learned earlier.

ステートレスとステートフルの両方のプロトコルを同時に有効にできるため、ホストは両方を使用してアドレス情報を取得する可能性があります。また、MTUサイズやホップ制限などのその他の設定パラメーターの値を、ルーター広告とステートフルな自動設定のプロトコルの両方から学習する可能性もあります。同じ設定情報が複数の情報源から提供される場合、この情報の値は一貫しているべきです。しかし、複数の情報源から受信した情報が一貫していなくても、致命的なエラーとはみなされません。ホストは、ステートレスなプロトコルとステートフルなプロトコルを介して受信したすべての情報の和集合を受け入れます。異なる情報源から一貫しない情報を学習した場合は、常に最後に取得した値が以前に学習した情報より優先されます。

6. SECURITY CONSIDERATIONS

6. セキュリティーに関する考慮事項

Stateless address autoconfiguration allows a host to connect to a network, configure an address and start communicating with other nodes without ever registering or authenticating itself with the local site. Although this allows unauthorized users to connect to and use a network, the threat is inherently present in the Internet architecture. Any node with a physical attachment to a network can generate an address (using a variety of ad hoc techniques) that provides connectivity.

ステートレスアドレス自動設定により、ホストは、ローカルサイトに自身を登録したり自身を認証したりすることなく、ネットワークに接続し、アドレスを設定し、他のノードとの通信を開始できます。これにより認可されていないユーザーがネットワークに接続して使用することが可能になりますが、この脅威はインターネットのアーキテクチャーに本質的に存在するものです。ネットワークに物理的に接続されたノードはどれも、（さまざまなその場しのぎの技法を使用して）接続性を提供するアドレスを生成できます。

The use of Duplicate Address Detection opens up the possibility of denial of service attacks. Any node can respond to Neighbor Solicitations for a tentative address, causing the other node to reject the address as a duplicate. This attack is similar to other attacks involving the spoofing of Neighbor Discovery messages and can be addressed by requiring that Neighbor Discovery packets be authenticated [RFC2402].

重複アドレス検出の使用は、サービス拒否攻撃の可能性を生じさせます。どのノードも仮アドレスについての近隣要請に応答でき、それによって相手のノードにそのアドレスを重複として拒否させることができます。この攻撃は、近隣探索のメッセージの偽装を伴う他の攻撃と同様であり、近隣探索のパケットの認証[RFC2402]を要求することで対処できます。

9. APPENDIX A: LOOPBACK SUPPRESSION & DUPLICATE ADDRESS DETECTION

9. 付録A：ループバックの抑制と重複アドレス検出

Determining whether a received multicast solicitation was looped back to the sender or actually came from another node is implementation- dependent. A problematic case occurs when two interfaces attached to the same link happen to have the same identifier and link-layer address, and they both send out packets with identical contents at roughly the same time (e.g., Neighbor Solicitations for a tentative address as part of Duplicate Address Detection messages). Although a receiver will receive both packets, it cannot determine which packet was looped back and which packet came from the other node by simply comparing packet contents (i.e., the contents are identical). In this particular case, it is not necessary to know precisely which packet was looped back and which was sent by another node; if one receives more solicitations than were sent, the tentative address is a duplicate. However, the situation may not always be this straightforward.

受信したマルチキャストの要請が送信者にループバックされたものか、実際に別のノードから来たものかを判断する方法は実装に依存します。問題となるのは、同じリンクに接続された2つのインターフェイスがたまたま同じ識別子とリンク層アドレスを持ち、両方がほぼ同時に同一の内容のパケット（たとえば、重複アドレス検出のメッセージの一部としての仮アドレスについての近隣要請）を送信する場合です。受信者は両方のパケットを受信しますが、パケットの内容を単純に比較するだけでは、どのパケットがループバックされたもので、どのパケットが別のノードから来たものかを判断できません（すなわち、内容は同一です）。この特定の場合には、どのパケットがループバックされ、どのパケットが別のノードによって送信されたかを正確に知る必要はありません。送信したよりも多くの要請を受信した場合、その仮アドレスは重複しています。しかし、状況は常にこれほど単純であるとは限りません。

The IPv4 multicast specification [RFC1112] recommends that the service interface provide a way for an upper-layer protocol to inhibit local delivery of packets sent to a multicast group that the sending host is a member of. Some applications know that there will be no other group members on the same host, and suppressing loopback prevents them from having to receive (and discard) the packets they themselves send out. A straightforward way to implement this facility is to disable loopback at the hardware level (if supported by the hardware), with packets looped back (if requested) by software. On interfaces in which the hardware itself suppresses loopbacks, a node running Duplicate Address Detection simply counts the number of Neighbor Solicitations received for a tentative address and compares them with the number expected. If there is a mismatch, the tentative address is a duplicate.

IPv4のマルチキャストの仕様[RFC1112]は、送信ホストがメンバーであるマルチキャストグループに送信されたパケットのローカル配送を上位層のプロトコルが抑止する方法をサービスインターフェイスが提供することを推奨しています。一部のアプリケーションは、同じホスト上に他のグループメンバーがいないことを知っており、ループバックを抑制することで、自身が送信したパケットを受信（して破棄）する必要がなくなります。この機能を実装する単純な方法は、（ハードウェアがサポートしていれば）ハードウェアレベルでループバックを無効にし、（要求された場合は）ソフトウェアでパケットをループバックすることです。ハードウェア自体がループバックを抑制するインターフェイスでは、重複アドレス検出を実行しているノードは、仮アドレスについて受信した近隣要請の数を単に数え、期待される数と比較します。一致しない場合、その仮アドレスは重複しています。

In those cases where the hardware cannot suppress loopbacks, however, one possible software heuristic to filter out unwanted loopbacks is to discard any received packet whose link-layer source address is the same as the receiving interface's. Unfortunately, use of that criteria also results in the discarding of all packets sent by another node using the same link-layer address. Duplicate Address Detection will fail on interfaces that filter received packets in this manner:

しかし、ハードウェアがループバックを抑制できない場合、不要なループバックを除外するためのソフトウェアのヒューリスティックの1つとして、リンク層の送信元アドレスが受信インターフェイスのものと同じである受信パケットを破棄する方法が考えられます。残念ながら、その基準を使用すると、同じリンク層アドレスを使用する別のノードによって送信されたすべてのパケットも破棄されることになります。この方法で受信パケットを除外するインターフェイスでは、重複アドレス検出は失敗します。

  • If a node performing Duplicate Address Detection discards received packets having the same source link-layer address as the receiving interface, it will also discard packets from other nodes also using the same link-layer address, including Neighbor Advertisement and Neighbor Solicitation messages required to make Duplicate Address Detection work correctly. This particular problem can be avoided by temporarily disabling the software suppression of loopbacks while a node performs Duplicate Address Detection.
  • If a node that is already using a particular IP address discards received packets having the same link-layer source address as the interface, it will also discard Duplicate Address Detection-related Neighbor Solicitation messages sent by another node also using the same link-layer address. Consequently, Duplicate Address Detection will fail, and the other node will configure a non-unique address. Since it is generally impossible to know when another node is performing Duplicate Address Detection, this scenario can be avoided only if software suppression of loopback is permanently disabled.
  • 重複アドレス検出を行っているノードが、受信インターフェイスと同じリンク層の送信元アドレスを持つ受信パケットを破棄する場合、同じリンク層アドレスを使用する他のノードからのパケットも破棄することになります。これには、重複アドレス検出を正しく機能させるために必要な近隣広告と近隣要請のメッセージも含まれます。この特定の問題は、ノードが重複アドレス検出を行っている間、ソフトウェアによるループバックの抑制を一時的に無効にすることで回避できます。
  • 特定のIPアドレスをすでに使用しているノードが、インターフェイスと同じリンク層の送信元アドレスを持つ受信パケットを破棄する場合、同じリンク層アドレスを使用する別のノードによって送信された、重複アドレス検出に関連する近隣要請メッセージも破棄することになります。その結果、重複アドレス検出は失敗し、別のノードは一意でないアドレスを設定してしまいます。一般に、別のノードがいつ重複アドレス検出を行っているかを知ることは不可能であるため、このシナリオは、ソフトウェアによるループバックの抑制を恒久的に無効にした場合にのみ回避できます。

Thus, to perform Duplicate Address Detection correctly in the case where two interfaces are using the same link-layer address, an implementation must have a good understanding of the interface's multicast loopback semantics, and the interface cannot discard received packets simply because the source link-layer address is the same as the interfaces.

したがって、2つのインターフェイスが同じリンク層アドレスを使用している場合に重複アドレス検出を正しく行うためには、実装はインターフェイスのマルチキャストのループバックの意味をよく理解している必要があり、インターフェイスは、リンク層の送信元アドレスがインターフェイスのものと同じであるというだけの理由で受信パケットを破棄することはできません。

10. APPENDIX B: CHANGES SINCE RFC 1971

10. 付録B：RFC 1971からの変更点

  • Changed document to use term "interface identifier" rather than "interface token" for consistency with other IPv6 documents.
  • Clarified definition of deprecated address to make clear it is OK to continue sending to or from deprecated addresses.
  • Reworded section 5.4 for clarity (no substantive change).
  • Added rules to Section 5.5.3 Router Advertisement processing to address potential denial-of-service attack when prefixes are advertised with very short Lifetimes.
  • Clarified wording in Section 5.5.4 to make clear that all upper layer protocols must process (i.e., send and receive) packets sent to deprecated addresses.
  • 他のIPv6の文書との一貫性のために、「インターフェイストークン（interface token）」ではなく「インターフェイス識別子（interface identifier）」という用語を使用するように文書を変更しました。
  • 非推奨アドレスの定義を明確にし、非推奨アドレスへの送信や非推奨アドレスからの送信を続けてもよいことを明確にしました。
  • 明確さのために5.4節の文言を変更しました（実質的な変更はありません）。
  • プレフィックスが非常に短い生存期間で広告される場合の潜在的なサービス拒否攻撃に対処するために、5.5.3節のルーター広告の処理に規則を追加しました。
  • 5.5.4節の文言を明確にし、すべての上位層のプロトコルが非推奨アドレスに送信されたパケットを処理（すなわち、送信と受信）しなければならないことを明確にしました。
