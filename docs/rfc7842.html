RFC 7842

Requirements for Improvements to the IETF Email List Archiving, Web-Based Browsing, and Search Tool

RFC 7842

IETFメーリングリストのアーカイブ、Webベースの閲覧、および検索のためのツールの改善に関する要件

Abstract

概要

The web-based IETF email archive search tool based on the requirements captured in RFC 6778 was deployed in January 2014. This memo captures the requirements for a set of improvements that have been identified during its initial years of community use.

RFC 6778でまとめられた要件にもとづくWebベースのIETF電子メールアーカイブ検索ツールは、2014年1月に運用が開始されました。このメモは、コミュニティーで使われ始めてからの数年間に明らかになった、一連の改善のための要件をまとめたものです。

1. Introduction

1. はじめに

The IETF email archive search tool, as specified in [RFC6778]) and available at [mailarch], has been in use for nearly two years. During that time, there have been repeated requests for several improvements. This memo captures the requirements for a concerted development effort to provide those improvements.

[RFC6778]で規定され、[mailarch]で提供されているIETF電子メールアーカイブ検索ツールは、使われ始めてから2年近くになります。その間、いくつかの改善が繰り返し要望されてきました。このメモは、それらの改善を実現するための集中的な開発作業に向けた要件をまとめたものです。

2. List Search and Archive Tool Improvement Requirements

2. リストの検索およびアーカイブツールの改善に関する要件

2.1. Viewing by Thread

2.1. スレッドごとの表示

Currently, when the "Group by Thread" button is selected, the resulting list of messages is flat. It is very hard to tell where a thread starts and stops. This flat view interacts badly with sorting (triggered by clicking on the column headers), leading to results that are confusing and sometimes incorrect.

現在、「Group by Thread」ボタンを選択すると、結果として得られるメッセージの一覧は平坦になります。スレッドがどこで始まりどこで終わるのかを見分けるのは非常に困難です。この平坦な表示は（列見出しをクリックすることで行われる）並べ替えとの相性が悪く、わかりにくく、ときには誤った結果になります。

This effort will:

この取り組みでは、次のことを行います。

  • Modify the message list display, when grouped by thread, to show each thread hierarchically.
  • Modify the sort performed by the clicking on the column headers to sort the overall list first by the parameters in the first message in the thread, and then sort within the thread (ensuring the thread grouping doesn't change based on these sorts). When viewing threads sorted this way, the hierarchy will be flattened, but the thread boundaries will remain visibly distinct.
  • スレッドごとにまとめて表示するときには、各スレッドを階層的に表示するよう、メッセージ一覧の表示を変更します。
  • 列見出しをクリックしたときに行われる並べ替えを、まずスレッドの最初のメッセージのパラメーターで一覧全体を並べ替え、次にスレッド内で並べ替えるよう変更します（これらの並べ替えによってスレッドのまとまりが変わらないようにします）。このように並べ替えたスレッドを表示するときには、階層は平坦になりますが、スレッドの境界は目に見えて区別できるままにします。

2.2. Navigation from the Message List View

2.2. メッセージ一覧ビューからのナビゲーション

This effort will add navigation to the message list view, whether viewing flat search results or viewing by thread, making it simple to:

この取り組みでは、平坦な検索結果を表示している場合でも、スレッドごとに表示している場合でも、メッセージ一覧ビューにナビゲーションを追加し、次のことを簡単に行えるようにします。

  • Navigate to the previous/next message by date in the set of listed messages.
  • Navigate to the previous/next message in a thread, to the first message in a thread, and to the previous/next thread displayed.
  • Navigate to any References or Replies (displayed as Follow-Ups in MHonArc) for the currently selected message. These are derived from the References header field in the displayed message, and the In-Reply-To header field or the last value in the References header field of all other messages in the archive).
  • 一覧に表示されているメッセージの中で、日付順で前後のメッセージに移動すること。
  • スレッド内の前後のメッセージ、スレッドの最初のメッセージ、および表示されている前後のスレッドに移動すること。
  • 現在選択しているメッセージの参照先（References）または返信（Replies）（MHonArcではFollow-Upsとして表示されるもの）に移動すること。これらは、表示しているメッセージのReferencesヘッダーフィールドと、アーカイブ内の他のすべてのメッセージのIn-Reply-ToヘッダーフィールドまたはReferencesヘッダーフィールドの最後の値から導出します。

The UI will make it possible to hide these navigation elements.

UIでは、これらのナビゲーション要素を非表示にできるようにします。

2.3. Navigation from a Single Message

2.3. 単一のメッセージからのナビゲーション

Currently, when viewing a single message, the only option for navigating to related messages is to return to the message list view (either by date or by thread). This is implemented with a new search based only on the details present in the message itself. No information about any search that led to the message is retained.

現在、単一のメッセージを表示しているときに関連するメッセージへ移動する唯一の方法は、（日付順またはスレッドごとの）メッセージ一覧ビューに戻ることです。これは、メッセージ自体に含まれる詳細情報だけにもとづく新たな検索によって実装されています。そのメッセージにたどり着くまでの検索に関する情報は、一切保持されません。

This effort will:

この取り組みでは、次のことを行います。

  • Add navigation to the single message view, enabling transition to previous/next in list and previous/next in thread.
  • Add navigation enabling transition to previous/next in search, if the message page being displayed was arrived at by navigating from the message list view of a search result.
  • Add navigation to any References or Replies (displayed as Follow-Ups in MHonArc). These are derived from the References header field in the displayed message, and the In-Reply-To header field or the last value in the References header field of all other messages in the archive.
  • Make it possible to hide these navigation elements.
  • 単一メッセージビューにナビゲーションを追加し、一覧内の前後、およびスレッド内の前後に移動できるようにします。
  • 表示しているメッセージのページに検索結果のメッセージ一覧ビューから移動してきた場合に、検索結果内の前後に移動できるナビゲーションを追加します。
  • 参照先（References）または返信（Replies）（MHonArcではFollow-Upsとして表示されるもの）へのナビゲーションを追加します。これらは、表示しているメッセージのReferencesヘッダーフィールドと、アーカイブ内の他のすべてのメッセージのIn-Reply-ToヘッダーフィールドまたはReferencesヘッダーフィールドの最後の値から導出します。
  • これらのナビゲーション要素を非表示にできるようにします。

2.4. Message List UI

2.4. メッセージ一覧のUI

It is not sufficiently obvious that the message list panel can be resized. The current handle is not visually distinct enough to signal the capability to the user, leaving many users believing they are restricted to the very short default list, even when viewing on large monitors.

メッセージ一覧パネルのサイズを変更できることが、十分にわかりやすくありません。現在のハンドルは、その機能があることをユーザーに伝えられるほど視覚的に目立たないため、多くのユーザーは、大きなモニターで表示しているときでさえ、非常に短いデフォルトの一覧しか使えないと思い込んでいます。

Additionally, there is a flaw in the code that fetches additional messages when scrolling to the bottom of what's currently displayed. If the message window is large enough that the default number of results does not fill it, no scrollbar appears, and scrolling to the bottom does not fetch additional results.

さらに、現在表示されている内容の一番下までスクロールしたときに追加のメッセージを取得するコードには欠陥があります。メッセージウィンドウが大きく、デフォルトの件数の結果ではウィンドウが埋まらない場合、スクロールバーが表示されず、一番下までスクロールしても追加の結果が取得されません。

The filter by list and filter by from sections to the left of the message list have no values in many circumstances, but it is not obvious why they are missing. One notable condition is when the search result is very large -- computing the values to put in these filters becomes prohibitively expensive. Without foreknowledge of the decisions captured in the code, the behavior seems arbitrary and unintuitive.

メッセージ一覧の左側にあるリストによるフィルターと差出人（from）によるフィルターのセクションは、多くの状況で値が入っていませんが、なぜ値がないのかがわかりにくくなっています。注目すべき状況の1つは、検索結果が非常に大きい場合です。この場合、これらのフィルターに入れる値の計算コストが法外に高くなります。コードに組み込まれた判断を前もって知らなければ、この挙動は恣意的で直感に反するように見えます。

The current view truncates fields, leaving trailing ellipses, when it doesn't need to. This leaves space underutilized on large displays and may make selection (particularly of long email addresses in the filters) much more difficult than it should be. On small displays, the column of filters dominates the display, leaving only a small amount of space for the actual message content.

現在のビューは、その必要がない場合でもフィールドを切り詰め、末尾に省略記号を残します。そのため、大きなディスプレイでは領域が十分に活用されず、（特にフィルター内の長いメールアドレスの）選択が本来よりもはるかに難しくなることがあります。小さなディスプレイでは、フィルターの列が表示の大半を占め、実際のメッセージの内容にはわずかな領域しか残りません。

The current view requires the user to select each message in the message list to get the URI to that message. This makes it difficult to open several messages in different windows, or to build a list of URIs for use in a message or other applications. It is also not obvious that double-clicking a row in the list will open the message in a separate window.

現在のビューでは、メッセージのURIを得るために、ユーザーはメッセージ一覧の各メッセージを選択する必要があります。そのため、複数のメッセージを別々のウィンドウで開いたり、メッセージやその他のアプリケーションで使うためにURIの一覧を作成したりするのが困難です。また、一覧の行をダブルクリックすると別のウィンドウでメッセージが開くことも、わかりにくくなっています。

This effort will:

この取り組みでは、次のことを行います。

  • Make the ability to resize the panels on the message list display easier to find.
  • Account for the size of the message list panel when choosing how many messages to fetch, filling the panel whenever there are enough results to do so.
  • Provide a message explaining any condition leading to filter values not being populated (such as "Refine search to enable 'From' filtering").
  • Allow subjects to fill the column on large displays. Show fully expanded list and email addresses in the pop-ups for the filters.
  • Provide a link on each row of the list to the URL for that row's message.
  • Add an export type that produces a file containing a list of URIs to each message in the list.
  • Add a hint to the UI that double-clicking on a row in the list will open a single-message view of the associated message in a separate view.
  • メッセージ一覧表示のパネルのサイズを変更できる機能を見つけやすくします。
  • 取得するメッセージの件数を決めるときにメッセージ一覧パネルのサイズを考慮し、十分な件数の結果がある場合は常にパネルを埋めるようにします。
  • フィルターの値が入らない原因となる状況を説明するメッセージ（「Refine search to enable 'From' filtering」など）を表示します。
  • 大きなディスプレイでは、件名が列いっぱいに表示されるようにします。フィルターのポップアップでは、リスト名とメールアドレスを省略せずに表示します。
  • 一覧の各行に、その行のメッセージのURLへのリンクを設けます。
  • 一覧内の各メッセージへのURIの一覧を含むファイルを生成するエクスポート形式を追加します。
  • 一覧の行をダブルクリックすると、対応するメッセージの単一メッセージビューが別のビューで開くことを示すヒントをUIに追加します。

2.5. Improve Support for Mobile Devices

2.5. モバイルデバイスのサポートの改善

The current view becomes difficult to use on small displays, particularly phone displays in portrait mode. This effort will:

現在のビューは、小さなディスプレイ、特に縦向きの電話のディスプレイでは使いにくくなります。この取り組みでは、次のことを行います。

  • Add a responsive interface, presenting a useful interface on both small and large displays.
  • レスポンシブなインターフェイスを追加し、小さなディスプレイでも大きなディスプレイでも使いやすいインターフェイスを提供します。

2.6. Improve Use of Display Space

2.6. 表示領域の使い方の改善

The current view underutilizes the available display space. This effort will:

現在のビューは、利用可能な表示領域を十分に活用していません。この取り組みでは、次のことを行います。

  • Make the message content the primary point of each view.
  • Reduce the unused space on the display.
  • Remove the filter column responsively when the display width is small.
  • 各ビューで、メッセージの内容を主役にします。
  • ディスプレイ上の使われていない領域を減らします。
  • ディスプレイの幅が小さいときには、レスポンシブにフィルターの列を取り除きます。

2.7. Use without JavaScript

2.7. JavaScriptを使わない利用

The current web-based archive search tool requires JavaScript to function. This effort will extend the tool to allow users that have disabled JavaScript in their browser to retrieve and navigate through search results using the message list and single message views.

現在のWebベースのアーカイブ検索ツールは、動作するためにJavaScriptを必要とします。この取り組みでは、ブラウザーでJavaScriptを無効にしているユーザーでも、メッセージ一覧ビューと単一メッセージビューを使って検索結果を取得し、その中を移動できるようにツールを拡張します。

This effort will not attempt to preserve all of the functionality provided with JavaScript enabled. In particular, when running with JavaScript disabled, these features will not be available:

この取り組みでは、JavaScriptが有効な場合に提供されるすべての機能を維持しようとはしません。特に、JavaScriptが無効な状態で実行している場合、次の機能は利用できません。

  • Resizing of the message list panels.
  • Dynamically filtering by time, list, or from. (The filter column will not appear).
  • メッセージ一覧パネルのサイズ変更。
  • 時間、リスト、または差出人（from）による動的なフィルタリング（フィルターの列は表示されません）。

2.8. Administration

2.8. 管理

This project will:

このプロジェクトでは、次のことを行います。

  • Add a link from the message view to the admin page for the message when logged in as an administrator.
  • Add correction of the appropriate thread indices to the handling of administrative imports of messages.
  • Implement a redirection handler mapping legacy archive URLs to the appropriate mailarch page.
  • Make the underlying template consistent across all views presented by the tool. In particular, ensure that the correct logo as designated by the IETF Administrative Oversight Committee (IAOC) appears consistently on all views.
  • 管理者としてログインしているときには、メッセージビューからそのメッセージの管理ページへのリンクを追加します。
  • 管理者によるメッセージのインポートの処理に、該当するスレッドインデックスの修正を追加します。
  • 旧来のアーカイブのURLを、対応するmailarchのページに対応付けるリダイレクトハンドラーを実装します。
  • ツールが提示するすべてのビューで、基盤となるテンプレートを統一します。特に、IETF管理監督委員会（IAOC）が指定した正しいロゴが、すべてのビューで一貫して表示されるようにします。

3. Security Considerations

3. セキュリティーに関する考慮事項

The requirements for improvement to the mailarch tool captured in this document do not introduce any exceptional security considerations. They add additional navigation points, and the implementers should consider the impact of rapid navigation using these new mechanisms (see the security considerations of [RFC6778]).

この文書でまとめたmailarchツールの改善に関する要件は、特別なセキュリティー上の考慮事項をもたらすものではありません。これらの要件はナビゲーションの起点を追加するので、実装者は、これらの新しい仕組みを使った高速なナビゲーションの影響を考慮すべきです（[RFC6778]のセキュリティーに関する考慮事項を参照してください）。
