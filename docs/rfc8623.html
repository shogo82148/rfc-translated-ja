RFC 8623

Stateful Path Computation Element (PCE) Protocol Extensions for Usage with Point-to-Multipoint TE Label Switched Paths (LSPs)

RFC 8623

ポイントツーマルチポイントTEラベルスイッチパス（LSP）で使用するためのステートフル経路計算要素（PCE）プロトコル拡張

Abstract

概要

The Path Computation Element (PCE) has been identified as an appropriate technology for the determination of the paths of point-to-multipoint (P2MP) TE Label Switched Paths (LSPs). This document provides extensions required for the Path Computation Element Communication Protocol (PCEP) so as to enable the usage of a stateful PCE capability in supporting P2MP TE LSPs.

経路計算要素（Path Computation Element: PCE）は、ポイントツーマルチポイント（P2MP）TEラベルスイッチパス（LSP）の経路を決定するための適切な技術として認識されています。この文書は、P2MP TE LSPをサポートする際にステートフルPCEの能力を使用できるようにするために必要な、経路計算要素通信プロトコル（Path Computation Element Communication Protocol: PCEP）の拡張を規定します。

1. Introduction

1. はじめに

As per [RFC4655], the Path Computation Element (PCE) is an entity that is capable of computing a network path or route based on a network graph and applying computational constraints. A Path Computation Client (PCC) may make requests to a PCE for paths to be computed.

[RFC4655]によると、経路計算要素（Path Computation Element: PCE）は、ネットワークグラフに基づき、計算上の制約を適用して、ネットワークの経路やルートを計算できるエンティティーです。経路計算クライアント（Path Computation Client: PCC）は、経路の計算をPCEにリクエストできます。

[RFC4875] describes how to set up point-to-multipoint (P2MP) Traffic Engineering Label Switched Paths (TE LSPs) for use in Multiprotocol Label Switching (MPLS) and Generalized MPLS (GMPLS) networks. [RFC5671] examines the applicability of PCE for the path computation for P2MP TE LSPs.

[RFC4875]は、マルチプロトコルラベルスイッチング（MPLS）および一般化MPLS（GMPLS）ネットワークで使用するポイントツーマルチポイント（P2MP）トラフィックエンジニアリングラベルスイッチパス（TE LSP）を設定する方法を説明しています。[RFC5671]は、P2MP TE LSPの経路計算へのPCEの適用可能性を検討しています。

The PCEP is designed as a communication protocol between PCCs and PCEs for point-to-point (P2P) path computations and is defined in [RFC5440]. The extensions of PCEP to request path computation for P2MP TE LSPs are described in [RFC8306].

PCEPは、ポイントツーポイント（P2P）の経路計算のためのPCCとPCEの間の通信プロトコルとして設計されており、[RFC5440]で定義されています。P2MP TE LSPの経路計算をリクエストするためのPCEPの拡張は、[RFC8306]で説明されています。

Stateful PCEs are shown to be helpful in many application scenarios, in both MPLS and GMPLS networks, as illustrated in [RFC8051]. These scenarios apply equally to P2P and P2MP TE LSPs. [RFC8231] provides the fundamental extensions to PCEP needed for stateful PCE to support general functionality for P2P TE LSP. [RFC8281] provides extensions to PCEP needed for stateful PCE-initiated P2P TE LSP. This document complements that work by focusing on PCEP extensions that are necessary in order for the deployment of stateful PCEs to support P2MP TE LSPs. This document describes the setup, maintenance, and teardown of PCE-initiated P2MP LSPs under the stateful PCE model.

[RFC8051]で示されているように、ステートフルPCEはMPLSとGMPLSの両方のネットワークにおいて、多くのアプリケーションシナリオで有用であることが示されています。これらのシナリオは、P2PとP2MPのTE LSPに等しく当てはまります。[RFC8231]は、ステートフルPCEがP2P TE LSPの一般的な機能をサポートするために必要な、PCEPの基本的な拡張を規定しています。[RFC8281]は、ステートフルなPCE起動型のP2P TE LSPに必要なPCEPの拡張を規定しています。この文書は、P2MP TE LSPをサポートするステートフルPCEを展開するために必要なPCEPの拡張に焦点を当てることで、これらの成果を補完します。この文書は、ステートフルPCEモデルにおけるPCE起動型のP2MP LSPの設定、維持、解体について説明します。

3. Supporting P2MP TE LSPs for Stateful PCE

3. ステートフルPCEにおけるP2MP TE LSPのサポート

3.1. Motivation

3.1. 動機

[RFC8051] presents several use cases, demonstrating scenarios that benefit from the deployment of a stateful PCE including optimization, recovery, etc., which are equally applicable to P2MP TE LSPs. [RFC8231] defines the extensions to PCEP needed for stateful operation of P2P TE LSPs. This document complements the previous work by focusing on extensions that are necessary in order for the deployment of stateful PCEs to support P2MP TE LSPs.

[RFC8051]は、最適化や回復など、ステートフルPCEの展開から恩恵を受けるシナリオを示すいくつかのユースケースを提示しており、これらはP2MP TE LSPにも等しく当てはまります。[RFC8231]は、P2P TE LSPのステートフルな運用に必要なPCEPの拡張を定義しています。この文書は、P2MP TE LSPをサポートするステートフルPCEを展開するために必要な拡張に焦点を当てることで、これまでの成果を補完します。

In addition to that, the stateful nature of a PCE simplifies the information conveyed in PCEP messages since it is possible to refer to the LSPs via a PCEP-specific LSP identifier (PLSP-ID) ([RFC8231]). For P2MP, where the size of the message is much larger, this is an added advantage. When using a stateless PCE, a request to modify an existing P2MP tree requires that all the leaves are presented in the PCEP messages along with all the path information. But when using a stateful PCE, the PCEP messages can use a PLSP-ID to represent all information about the LSP that has previously been exchanged in PCEP messages, and it is only necessary to encode the modifications (such as new or removed leaf nodes). The PLSP-ID provides an index into the LSP-DB at the PCE and identifies the LSP at the PCC.

それに加えて、PCEがステートフルであるという性質により、PCEPメッセージで伝達される情報は単純になります。これは、PCEP固有のLSP識別子（PLSP-ID）（[RFC8231]）によってLSPを参照できるからです。メッセージのサイズがはるかに大きくなるP2MPでは、これはさらなる利点となります。ステートレスPCEを使用する場合、既存のP2MPツリーを変更するリクエストでは、すべての経路情報とともにすべてのリーフをPCEPメッセージに含める必要があります。しかし、ステートフルPCEを使用する場合、PCEPメッセージは、以前にPCEPメッセージで交換されたLSPに関するすべての情報をPLSP-IDで表すことができ、変更内容（新しいリーフノードや削除されたリーフノードなど）だけをエンコードすれば済みます。PLSP-IDは、PCEにおいてはLSP-DBへのインデックスとなり、PCCにおいてはLSPを識別します。

In environments where the P2MP TE LSPs placement needs to change in response to application demands, it is useful to support dynamic creation and tear down of P2MP TE LSPs. The ability for a PCE to trigger the creation of P2MP TE LSPs on demand can be seamlessly integrated into a controller-based network architecture where intelligence in the controller can determine when and where to set up paths. Section 3 of [RFC8281] further describes the motivation behind the PCE-Initiation capability, which is equally applicable to P2MP TE LSPs.

アプリケーションの要求に応じてP2MP TE LSPの配置を変更する必要がある環境では、P2MP TE LSPの動的な作成と解体をサポートすると便利です。PCEがオンデマンドでP2MP TE LSPの作成をトリガーする能力は、いつどこで経路を設定するかをコントローラーのインテリジェンスが決定できる、コントローラーベースのネットワークアーキテクチャーにシームレスに統合できます。[RFC8281]のSection 3では、PCE起動（PCE-Initiation）能力の背後にある動機をさらに説明しており、これはP2MP TE LSPにも等しく当てはまります。

3.2. Objectives

3.2. 目的

The objectives for the protocol extensions to support P2MP TE LSPs for stateful PCE are the same as the objectives described in Section 3.2 of [RFC8231].

ステートフルPCEにおいてP2MP TE LSPをサポートするためのプロトコル拡張の目的は、[RFC8231]のSection 3.2で説明されている目的と同じです。

4. Functions to Support P2MP TE LSPs for Stateful PCEs

4. ステートフルPCEでP2MP TE LSPをサポートするための機能

[RFC8231] specifies new functions to support a stateful PCE. It also specifies that a function can be initiated either from a PCC towards a PCE (C-E) or from a PCE towards a PCC (E-C).

[RFC8231]は、ステートフルPCEをサポートするための新しい機能を規定しています。また、機能はPCCからPCEに向けて（C-E）、またはPCEからPCCに向けて（E-C）のいずれかで開始できることも規定しています。

This document extends these functions to support P2MP TE LSPs:

この文書は、P2MP TE LSPをサポートするために、これらの機能を次のように拡張します。

Capability Advertisement (E-C,C-E)
Both the PCC and the PCE must announce during PCEP session establishment that they support Stateful PCE extensions for P2MP using mechanisms defined in Section 5.2.
LSP State Synchronization (C-E)
After the session between the PCC and a stateful PCE with P2MP capability is initialized, the PCE must learn the state of a PCC's P2MP TE LSPs before it can perform path computations or update LSP attributes in a PCC.
LSP Update Request (E-C)
A stateful PCE with P2MP capability requests modification of attributes on a PCC's P2MP TE LSPs.
LSP State Report (C-E)
A PCC sends an LSP state report to a PCE whenever the state of a P2MP TE LSP changes.
LSP Control Delegation (C-E,E-C)
A PCC grants to a PCE the right to update LSP attributes on one or more P2MP TE LSPs; the PCE becomes the authoritative source of the LSP's attributes as long as the delegation is in effect (See Section 5.7 of [RFC8231]); the PCC may withdraw the delegation or the PCE may give up the delegation at any time.
PCE-initiated LSP instantiation (E-C)
A PCE sends an LSP Initiate Message to a PCC to instantiate or delete a P2MP TE LSP [RFC8281].
能力の広告（Capability Advertisement）（E-C、C-E）
PCCとPCEの両方が、Section 5.2で定義されているメカニズムを使用して、P2MP向けのステートフルPCE拡張をサポートしていることをPCEPセッションの確立中に通知する必要があります。
LSP状態同期（LSP State Synchronization）（C-E）
PCCとP2MP能力を持つステートフルPCEとの間のセッションが初期化された後、PCEは、経路計算を実行したりPCCのLSP属性を更新したりする前に、PCCのP2MP TE LSPの状態を学習する必要があります。
LSP更新リクエスト（LSP Update Request）（E-C）
P2MP能力を持つステートフルPCEは、PCCのP2MP TE LSPの属性の変更をリクエストします。
LSP状態報告（LSP State Report）（C-E）
PCCは、P2MP TE LSPの状態が変化するたびに、LSP状態報告をPCEに送信します。
LSP制御の委任（LSP Control Delegation）（C-E、E-C）
PCCは、1つ以上のP2MP TE LSPのLSP属性を更新する権利をPCEに付与します。委任が有効である間、PCEはそのLSPの属性について権威ある情報源となります（[RFC8231]のSection 5.7を参照）。PCCはいつでも委任を取り消すことができ、PCEはいつでも委任を放棄できます。
PCE起動型LSPのインスタンス化（PCE-initiated LSP instantiation）（E-C）
PCEは、P2MP TE LSPをインスタンス化または削除するために、LSP起動メッセージをPCCに送信します[RFC8281]。

5. Architectural Overview of Protocol Extensions

5. プロトコル拡張のアーキテクチャー概要

5.1. Extension of PCEP Messages

5.1. PCEPメッセージの拡張

Two new PCEP messages are defined in [RFC8231] to support stateful PCE for P2P TE LSPs. In this document, these messages are extended as follows to support P2MP TE LSPs.

[RFC8231]では、P2P TE LSPのステートフルPCEをサポートするために2つの新しいPCEPメッセージが定義されています。この文書では、P2MP TE LSPをサポートするために、これらのメッセージを次のように拡張します。

Path Computation State Report (PCRpt)
Each P2MP TE LSP State Report in a PCRpt message contains the actual P2MP TE LSP path attributes, the LSP status, etc. An LSP State Report carried in a PCRpt message is also used in delegation or revocation of control of a P2MP TE LSP to/from a PCE. The extension of PCRpt messages is described in Section 6.1.
Path Computation Update Request (PCUpd)
Each P2MP TE LSP Update Request in a PCUpd message MUST contain all LSP parameters that a PCE wishes to set for a given P2MP TE LSP. An LSP Update Request carried in a PCUpd message is also used to return LSP delegations if at any point the PCE no longer desires control of a P2MP TE LSP. The PCUpd message is described in Section 6.2.
経路計算状態報告（Path Computation State Report: PCRpt）

5.2. Capability Advertisement

5.2. 能力の広告

During the PCEP initialization phase, as per Section 7.1.1 of [RFC8231], PCEP speakers advertise Stateful capability via the STATEFUL-PCE-CAPABILITY TLV in the OPEN object. Various flags are defined for the STATEFUL-PCE-CAPABILITY TLV defined in [RFC8231] and updated in [RFC8281] and [RFC8232].

PCEPの初期化フェーズにおいて、[RFC8231]のSection 7.1.1のとおり、PCEPスピーカーはOPENオブジェクト内のSTATEFUL-PCE-CAPABILITY TLVを介してステートフル能力を広告します。[RFC8231]で定義され、[RFC8281]と[RFC8232]で更新されたSTATEFUL-PCE-CAPABILITY TLVには、さまざまなフラグが定義されています。

Three new flags, N (P2MP-CAPABILITY), M (P2MP-LSP-UPDATE-CAPABILITY), and P (P2MP-LSP-INSTANTIATION-CAPABILITY), are added in this document:

この文書では、N（P2MP-CAPABILITY）、M（P2MP-LSP-UPDATE-CAPABILITY）、P（P2MP-LSP-INSTANTIATION-CAPABILITY）の3つの新しいフラグを追加します。

N (P2MP-CAPABILITY flag - 1 bit)
If set to 1 by a PCC, the N Flag indicates that the PCC is willing to send P2MP LSP State Reports whenever there's a change to the parameters or operational status of the P2MP LSP; if set to 1 by a PCE, the N Flag indicates that the PCE is interested in receiving LSP State Reports whenever there is a parameter or operational status change to the P2MP LSP. The P2MP-CAPABILITY Flag MUST be advertised by both a PCC and a PCE for the P2MP extension (as per this document) of the PCRpt messages to be allowed on a PCEP session.
M (P2MP-LSP-UPDATE-CAPABILITY flag - 1 bit)
If set to 1 by a PCC, the M Flag indicates that the PCC allows modification of P2MP LSP parameters; if set to 1 by a PCE, the M Flag indicates that the PCE is capable of updating P2MP LSP parameters. The P2MP-LSP-UPDATE-CAPABILITY Flag MUST be advertised by both a PCC and a PCE for the P2MP extension (as per this document) of the PCUpd messages to be allowed on a PCEP session.
P (P2MP-LSP-INSTANTIATION-CAPABILITY flag - 1 bit)
If set to 1 by a PCC, the P Flag indicates that the PCC allows instantiation of a P2MP LSP by a PCE. If set to 1 by a PCE, the P flag indicates that the PCE supports P2MP LSP instantiation. The P2MP-LSP-INSTANTIATION-CAPABILITY flag MUST be set by both PCC and PCE in order to support PCE-initiated P2MP LSP instantiation.
N（P2MP-CAPABILITYフラグ - 1ビット）
PCCによって1に設定された場合、Nフラグは、P2MP LSPのパラメーターまたは運用状態が変化するたびに、PCCがP2MP LSP状態報告を送信する意思があることを示します。PCEによって1に設定された場合、Nフラグは、P2MP LSPのパラメーターまたは運用状態が変化するたびに、PCEがLSP状態報告を受信することを望んでいることを示します。PCEPセッション上で（この文書に従った）PCRptメッセージのP2MP拡張を許可するには、PCCとPCEの両方がP2MP-CAPABILITYフラグを広告しなければなりません（MUST）。
M（P2MP-LSP-UPDATE-CAPABILITYフラグ - 1ビット）
PCCによって1に設定された場合、Mフラグは、PCCがP2MP LSPパラメーターの変更を許可することを示します。PCEによって1に設定された場合、Mフラグは、PCEがP2MP LSPパラメーターを更新できることを示します。PCEPセッション上で（この文書に従った）PCUpdメッセージのP2MP拡張を許可するには、PCCとPCEの両方がP2MP-LSP-UPDATE-CAPABILITYフラグを広告しなければなりません（MUST）。
P（P2MP-LSP-INSTANTIATION-CAPABILITYフラグ - 1ビット）
PCCによって1に設定された場合、Pフラグは、PCCがPCEによるP2MP LSPのインスタンス化を許可することを示します。PCEによって1に設定された場合、Pフラグは、PCEがP2MP LSPのインスタンス化をサポートすることを示します。PCE起動型のP2MP LSPのインスタンス化をサポートするには、PCCとPCEの両方がP2MP-LSP-INSTANTIATION-CAPABILITYフラグを設定しなければなりません（MUST）。

A PCEP speaker should continue to advertise the basic P2MP capability via mechanisms as described in [RFC8306].

PCEPスピーカーは、[RFC8306]で説明されているメカニズムを介して、基本的なP2MP能力の広告を引き続き行うべきです。

5.6.3.1. P2MP TE LSPs Instantiation
5.6.3.1. P2MP TE LSPのインスタンス化

The instantiation operation of P2MP TE LSPs is the same as the LSP instantiation operation defined in Section 5.3 of [RFC8281]; this includes the handling of the PLSP-ID, SYMBOLIC-PATH-NAME TLV, etc. The processing rules and use of error codes remain unchanged. The N (P2MP) flag (Section 7.1) MUST be set in the LSP object in the PCInitiate message by the PCE to specify that the instantiation is for P2MP TE LSPs. Like the PLSP-ID (as per [RFC8281]), the P2MP-LSP-IDENTIFIERS TLV SHOULD NOT be included in the LSP object in PCInitiate messages and MUST be ignored on receipt. These identifiers are generated by the PCC on receipt of the PCInitiate message and reported via a PCRpt message to the PCE.

P2MP TE LSPのインスタンス化の操作は、[RFC8281]のSection 5.3で定義されているLSPのインスタンス化の操作と同じです。これには、PLSP-IDやSYMBOLIC-PATH-NAME TLVなどの扱いも含まれます。処理規則とエラーコードの使用法は変わりません。インスタンス化がP2MP TE LSPに対するものであることを示すために、PCEはPCInitiateメッセージのLSPオブジェクトにN（P2MP）フラグ（Section 7.1）を設定しなければなりません（MUST）。（[RFC8281]に従う）PLSP-IDと同様に、P2MP-LSP-IDENTIFIERS TLVはPCInitiateメッセージのLSPオブジェクトに含めるべきではありません（SHOULD NOT）。また、受信時には無視しなければなりません（MUST）。これらの識別子は、PCInitiateメッセージを受信したPCCによって生成され、PCRptメッセージを介してPCEに報告されます。

5.6.3.2. P2MP TE LSPs Deletion
5.6.3.2. P2MP TE LSPの削除

The processing rules and error codes remain unchanged.

P2MP TE LSPの削除の操作は、[RFC8281]のSection 5.4で定義されているLSPの削除の操作と同じです。つまり、削除するLSPのPLSP-IDを運ぶLSPオブジェクトと、Rフラグ（[RFC8281]のSection 5.2に従うLSP-REMOVE）が設定されたステートフルPCEリクエストパラメーター（Stateful PCE Request Parameter: SRP）オブジェクトを含むLSP起動メッセージを送信します。処理規則とエラーコードは変わりません。

5.6.3.3. Adding and Pruning Leaves for the P2MP TE LSP
5.6.3.3. P2MP TE LSPへのリーフの追加と刈り込み

The adding of new leaves and pruning of old leaves for the PCE-initiated P2MP TE LSP MUST be carried in a PCUpd message as per Section 6.2 for P2MP TE LSP extensions. As defined in [RFC8306], leaf type = 1 is used for adding new leaves, and leaf type = 2 is used for pruning old leaves of P2MP END-POINTS Objects.

PCE起動型のP2MP TE LSPに対する新しいリーフの追加と古いリーフの刈り込みは、P2MP TE LSP拡張についてSection 6.2で説明しているとおり、PCUpdメッセージで運ばなければなりません（MUST）。[RFC8306]で定義されているとおり、P2MP END-POINTSオブジェクトでは、新しいリーフの追加にはリーフタイプ = 1を使用し、古いリーフの刈り込みにはリーフタイプ = 2を使用します。

PCC MAY use the Incremental State Update mechanism as described in [RFC4875] to signal the adding and pruning of leaves.

PCCは、リーフの追加と刈り込みをシグナリングするために、[RFC4875]で説明されている増分状態更新（Incremental State Update）メカニズムを使用してもよいです（MAY）。

Section 3.10 of [RFC8306] defines the error-handling procedures when adding new leaves to or removing old leaves from the existing P2MP tree for PCReq messages. The same error handling and error codes are also applicable to the stateful PCE messages as described in this document.

[RFC8306]のSection 3.10は、PCReqメッセージにおいて既存のP2MPツリーに新しいリーフを追加する場合や既存のP2MPツリーから古いリーフを削除する場合のエラー処理手順を定義しています。同じエラー処理とエラーコードは、この文書で説明するステートフルPCEのメッセージにも適用できます。

5.6.3.4. P2MP TE LSPs Delegation and Cleanup
5.6.3.4. P2MP TE LSPの委任とクリーンアップ

P2MP TE LSPの委任とクリーンアップの操作は、[RFC8281]のSection 6で定義されているLSPの委任とクリーンアップの操作と同じです。処理規則とエラーコードは変わりません。

  • New leaves to add (leaf type = 1)
  • Old leaves to remove (leaf type = 2)
  • Old leaves whose path can be modified/reoptimized (leaf type = 3)
  • Old leaves whose path must be left unchanged (leaf type = 4)
  • 追加する新しいリーフ（リーフタイプ = 1）
  • 削除する古いリーフ（リーフタイプ = 2）
  • 経路を変更または再最適化できる古いリーフ（リーフタイプ = 3）
  • 経路を変更せずに残さなければならない古いリーフ（リーフタイプ = 4）

When reporting the status of a P2MP TE LSP, the destinations MUST be grouped in the END-POINTS object based on the operational status (O field in S2LS objects) and leaf type (in END-POINTS objects). This way, leaves of the same type that share the same operational status can be grouped together. For reporting the status of delegated P2MP TE LSPs, leaf type = 3 is used, whereas for nondelegated P2MP TE LSPs, leaf type = 4 is used.

P2MP TE LSPの状態を報告する場合、宛先は、運用状態（S2LSオブジェクトのOフィールド）とリーフタイプ（END-POINTSオブジェクト内）に基づいて、END-POINTSオブジェクト内でグループ化されなければなりません（MUST）。このようにして、同じ運用状態を共有する同じタイプのリーフをまとめてグループ化できます。委任されたP2MP TE LSPの状態の報告にはリーフタイプ = 3を使用し、委任されていないP2MP TE LSPの状態の報告にはリーフタイプ = 4を使用します。

For a delegated P2MP TE LSP, configuration changes are reported via a PCRpt message. For example, for adding new leaves, leaf type = 1 is used in the END-POINTS object, and for removing old leaves, leaf type = 2 is used.

委任されたP2MP TE LSPの場合、設定の変更はPCRptメッセージを介して報告されます。たとえば、新しいリーフを追加する場合はEND-POINTSオブジェクトでリーフタイプ = 1を使用し、古いリーフを削除する場合はリーフタイプ = 2を使用します。

Note that the compatibility with the [RFC8231] definition of <state-report> is preserved. At least one instance of <END-POINTS> MUST be present in this message for P2MP LSP.

[RFC8231]における<state-report>の定義との互換性は維持されていることに注意してください。P2MP LSPの場合、このメッセージには<END-POINTS>のインスタンスが少なくとも1つ存在しなければなりません（MUST）。

Note that the ordering of <end-point-intended-path-pair-list>, <actual-attribute-list>, <end-point-actual-path-pair-list>, and <intended-attribute-list> is done to retain compatibility with state reports for the P2P LSPs as per [RFC8231].

<end-point-intended-path-pair-list>、<actual-attribute-list>、<end-point-actual-path-pair-list>、<intended-attribute-list>の順序は、[RFC8231]に従うP2P LSPの状態報告との互換性を保つためのものであることに注意してください。

During state synchronization, the PCRpt message reports the status of the full P2MP tree.

状態同期の間、PCRptメッセージはP2MPツリー全体の状態を報告します。

The S2LS object MUST be carried in a PCRpt message along with the END-POINTS object when an N (P2MP) flag is set in an LSP object for P2MP TE LSPs. If the S2LS object is missing, the receiving PCE MUST send a PCEP Error (PCErr) message with Error-type=6 ("Mandatory Object missing") and Error-value=13 ("S2LS object missing"). If the END-POINTS object is missing, the receiving PCE MUST send a PCErr message with Error-type=6 ("Mandatory Object missing") and Error-value=3 ("END-POINTS object missing") (defined in [RFC5440].

P2MP TE LSPのためにLSPオブジェクトにN（P2MP）フラグが設定されている場合、S2LSオブジェクトはEND-POINTSオブジェクトとともにPCRptメッセージで運ばなければなりません（MUST）。S2LSオブジェクトがない場合、受信側のPCEは、Error-type=6（"Mandatory Object missing"）およびError-value=13（"S2LS object missing"）を含むPCEPエラー（PCEP Error: PCErr）メッセージを送信しなければなりません（MUST）。END-POINTSオブジェクトがない場合、受信側のPCEは、Error-type=6（"Mandatory Object missing"）およびError-value=3（"END-POINTS object missing"）（[RFC5440]で定義）を含むPCErrメッセージを送信しなければなりません（MUST）。

The S2LS object could be used in conjunction with the intended-path (EXPLICIT_ROUTE object or ERO) as well as the actual-path (RECORD_ROUTE object or RRO); for the same leaf, the state encoded in the S2LS object associated with the actual-path MUST be used over the intended-path.

S2LSオブジェクトは、意図された経路（intended-path、EXPLICIT_ROUTEオブジェクトまたはERO）と実際の経路（actual-path、RECORD_ROUTEオブジェクトまたはRRO）のどちらとも組み合わせて使用できます。同じリーフについては、実際の経路に関連付けられたS2LSオブジェクトにエンコードされた状態を、意図された経路のものより優先して使用しなければなりません（MUST）。

If the E-bit (ERO-Compress bit) was set to 1 in the report, then the path will be formed by an ERO followed by a list of SECONDARY_EXPLICIT_ROUTE Objects (SEROs), or an RRO followed by a list of SECONDARY_RECORD_ROUTE Objects (SRROs).

報告においてEビット（ERO-Compressビット）が1に設定されていた場合、経路は、EROとそれに続くSECONDARY_EXPLICIT_ROUTEオブジェクト（SERO）のリスト、またはRROとそれに続くSECONDARY_RECORD_ROUTEオブジェクト（SRRO）のリストによって形成されます。

7.1. LSPオブジェクトの拡張

The LSP Object is defined in Section 7.3 of [RFC8231]. It specifies the PLSP-ID to uniquely identify an LSP that is constant for the life time of a PCEP session. Similarly, for a P2MP tunnel, the PLSP-ID uniquely identifies a P2MP TE LSP. This document adds the following flags to the LSP Object:

LSPオブジェクトは[RFC8231]のSection 7.3で定義されています。LSPオブジェクトは、PCEPセッションの存続期間中は一定である、LSPを一意に識別するためのPLSP-IDを規定しています。同様に、P2MPトンネルの場合、PLSP-IDはP2MP TE LSPを一意に識別します。この文書は、LSPオブジェクトに次のフラグを追加します。

N (P2MP flag - 1 bit)
If the N flag is set to 1, it indicates that the message is for a P2MP TE LSP.
F (Fragmentation flag - 1 bit)
If the F flag is unset (0), it indicates that the LSP is not fragmented or that it is the last piece of the fragmented LSP. If the F flag is set to 1, it indicates that the LSP is fragmented and that it is not the last piece of the fragmented LSP. The receiver needs to wait for additional fragments until it receives an LSP with the same PLSP-ID and with the F-bit set to 0. See Section 8 for further details.
E (ERO-compression flag - 1 bit)
If the E flag is set to 1, it indicates the route is in compressed format (that is, Secondary Explicit Route Object (SERO) and Secondary Record Route Object (SRRO) objects [RFC8306] are in use).
N（P2MPフラグ - 1ビット）
Nフラグが1に設定されている場合、メッセージがP2MP TE LSPに関するものであることを示します。
F（断片化フラグ - 1ビット）
Fフラグが設定されていない（0）場合、LSPが断片化されていないか、断片化されたLSPの最後の部分であることを示します。Fフラグが1に設定されている場合、LSPが断片化されており、断片化されたLSPの最後の部分ではないことを示します。受信者は、同じPLSP-IDを持ち、Fビットが0に設定されたLSPを受信するまで、追加のフラグメントを待つ必要があります。詳細はSection 8を参照してください。
E（ERO圧縮フラグ - 1ビット）
Eフラグが1に設定されている場合、経路が圧縮された形式であること（つまり、二次明示経路オブジェクト（Secondary Explicit Route Object: SERO）と二次記録経路オブジェクト（Secondary Record Route Object: SRRO）[RFC8306]が使用されていること）を示します。

The flags defined in this section (N, F, and E) are used in PCRpt, PCUpd, or PCInitiate messages. In the case of PCReq and PCRep messages, these flags have no meaning and thus MUST be ignored. The corresponding flags in the RP (Request Parameters) object are used as described in [RFC8306].

このセクションで定義するフラグ（N、F、E）は、PCRpt、PCUpd、またはPCInitiateメッセージで使用されます。PCReqメッセージとPCRepメッセージでは、これらのフラグは意味を持たないため、無視しなければなりません（MUST）。RP（Request Parameters）オブジェクト内の対応するフラグは、[RFC8306]で説明されているとおりに使用されます。

7.1.1. P2MP-LSP-IDENTIFIERS TLV

[RFC8231] specifies the LSP-IDENTIFIERS TLVs to be included in the LSP object. For P2MP TE LSP, this document defines P2MP-LSP-IDENTIFIERS TLVs for the LSP object. There are two P2MP-LSP-IDENTIFIERS TLVs, one for IPv4 and one for IPv6. The P2MP-LSP-IDENTIFIERS TLV MUST be included in the LSP object in a PCRpt message for P2MP TE LSPs. 8. Message Fragmentation

8. メッセージの断片化

The total PCEP message length, including the common header, is (2^16)-1 bytes. In certain scenarios, the P2MP report and update request may not fit into a single PCEP message (e.g., initial report or update). The F flag is used in the LSP object to signal that the initial report, update, or initiate request was too large to fit into a single PCEP message and will be fragmented into multiple messages. In order to identify the single report or update, each message will use the same PLSP-ID. In order to identify that a series of PCInitiate messages represents a single Initiate, each message will use the same PLSP-ID (in this case 0) and SRP-ID-number.

共通ヘッダーを含むPCEPメッセージの全長は(2^16)-1バイトです。特定のシナリオでは、P2MPの報告や更新リクエストが単一のPCEPメッセージに収まらない場合があります（例：最初の報告や更新）。LSPオブジェクト内のFフラグは、最初の報告、更新、または起動リクエストが大きすぎて単一のPCEPメッセージに収まらず、複数のメッセージに断片化されることをシグナリングするために使用されます。単一の報告や更新を識別するために、各メッセージは同じPLSP-IDを使用します。一連のPCInitiateメッセージが単一の起動を表すことを識別するために、各メッセージは同じPLSP-ID（この場合は0）とSRP-ID-numberを使用します。

The fragmentation procedure described below for report or update messages is similar to [RFC8306], which describes request and response message fragmentation.

以下で説明する報告メッセージや更新メッセージの断片化手順は、リクエストメッセージとレスポンスメッセージの断片化を説明している[RFC8306]と同様です。

8.1. Report Fragmentation Procedure

8.1. 報告の断片化手順

If the initial report is too large to fit into a single report message, the PCC will split the report over multiple messages. Each message sent to the PCE, except the last one, will have the F flag set in the LSP object to signify that the report has been fragmented into multiple messages. In order to identify that a series of report messages represents a single report, each message will use the same PLSP-ID.

最初の報告が大きすぎて単一の報告メッセージに収まらない場合、PCCは報告を複数のメッセージに分割します。PCEに送信される各メッセージは、最後のメッセージを除いて、報告が複数のメッセージに断片化されていることを示すために、LSPオブジェクトにFフラグが設定されます。一連の報告メッセージが単一の報告を表すことを識別するために、各メッセージは同じPLSP-IDを使用します。

The Error-Type value 18 ("P2MP Fragmentation Error") is used to report any error associated with the fragmentation of a P2MP PCEP message. A new error-value 2 indicates "Fragmented report failure" and is used if a PCE does not receive the last part of the fragmented message.

Error-Type値18（"P2MP Fragmentation Error"）は、P2MP PCEPメッセージの断片化に関連するあらゆるエラーを報告するために使用されます。新しいerror-value 2は「Fragmented report failure」を示し、PCEが断片化されたメッセージの最後の部分を受信しなかった場合に使用されます。

8.2. Update Fragmentation Procedure

8.2. 更新の断片化手順

Once the PCE computes and updates a path for some or all leaves in a P2MP TE LSP, an update message is sent to the PCC. If the update is too large to fit into a single update message, the PCE will split the update over multiple messages. Each update message sent by the PCE, except the last one, will have the F flag set in the LSP object to signify that the update has been fragmented into multiple messages. In order to identify that a series of update messages represents a single update, each message will use the same PLSP-ID and SRP-ID-number.

PCEがP2MP TE LSP内の一部またはすべてのリーフの経路を計算して更新すると、更新メッセージがPCCに送信されます。更新が大きすぎて単一の更新メッセージに収まらない場合、PCEは更新を複数のメッセージに分割します。PCEが送信する各更新メッセージは、最後のメッセージを除いて、更新が複数のメッセージに断片化されていることを示すために、LSPオブジェクトにFフラグが設定されます。一連の更新メッセージが単一の更新を表すことを識別するために、各メッセージは同じPLSP-IDとSRP-ID-numberを使用します。

The Error-Type value 18 ("P2MP Fragmentation Error") is used to report any error associated with the fragmentation of a P2MP PCEP message. A new error-value 3 indicates "Fragmented update failure" and is used if a PCC does not receive the last part of the fragmented message.

Error-Type値18（"P2MP Fragmentation Error"）は、P2MP PCEPメッセージの断片化に関連するあらゆるエラーを報告するために使用されます。新しいerror-value 3は「Fragmented update failure」を示し、PCCが断片化されたメッセージの最後の部分を受信しなかった場合に使用されます。

8.3. PCInitiate Fragmentation Procedure

8.3. PCInitiateの断片化手順

Once the PCE initiates to set up a P2MP TE LSP, a PCInitiate message is sent to the PCC. If the initiate request is too large to fit into a single PCInitiate message, the PCE will split the initiate request over multiple messages. Each PCInitiate message sent by the PCE, except the last one, will have the F flag set in the LSP object to signify that the PCInitiate has been fragmented into multiple messages. In order to identify that a series of PCInitiate messages represents a single Initiate, each message will use the same PLSP-ID (in this case 0) and SRP-ID-number.

PCEがP2MP TE LSPの設定を起動すると、PCInitiateメッセージがPCCに送信されます。起動リクエストが大きすぎて単一のPCInitiateメッセージに収まらない場合、PCEは起動リクエストを複数のメッセージに分割します。PCEが送信する各PCInitiateメッセージは、最後のメッセージを除いて、PCInitiateが複数のメッセージに断片化されていることを示すために、LSPオブジェクトにFフラグが設定されます。一連のPCInitiateメッセージが単一の起動を表すことを識別するために、各メッセージは同じPLSP-ID（この場合は0）とSRP-ID-numberを使用します。

The Error-Type value 18 ("P2MP Fragmentation Error") is used to report any error associated with the fragmentation of a P2MP PCEP message. A new error-value 4 indicates "Fragmented instantiation failure" and is used if a PCC does not receive the last part of the fragmented message.

Error-Type値18（"P2MP Fragmentation Error"）は、P2MP PCEPメッセージの断片化に関連するあらゆるエラーを報告するために使用されます。新しいerror-value 4は「Fragmented instantiation failure」を示し、PCCが断片化されたメッセージの最後の部分を受信しなかった場合に使用されます。

9. Nonsupport of P2MP TE LSPs for Stateful PCE

9. ステートフルPCEがP2MP TE LSPをサポートしない場合

The PCEP extensions described in this document for stateful PCEs with P2MP capability MUST NOT be used if the PCE has not advertised its stateful capability with P2MP as per Section 5.2. If the PCC supports the extensions as per this document (understands the N (P2MP-CAPABILITY) and M (P2MP-LSP-UPDATE-CAPABILITY) flags in the LSP object) but did not advertise this capability, then upon receipt of a PCUpd message from the PCE, it SHOULD generate a PCErr with error-type 19 ("Invalid Operation"), error-value 12 ("Attempted LSP Update Request for P2MP if active stateful PCE capability for P2MP was not advertised"), and terminate the PCEP session. If the PCE supports the extensions as per this document (understands the N (P2MP-CAPABILITY) flag in the LSP object) but did not advertise this capability, then upon receipt of a PCRpt message from the PCC, it SHOULD generate a PCErr with error-type 19 ("Invalid Operation"), error-value 11 ("Attempted LSP State Report for P2MP if stateful PCE capability for P2MP was not advertised"), and it SHOULD terminate the PCEP session.

PCEがSection 5.2に従ってP2MP対応のステートフル能力を広告していない場合、P2MP能力を持つステートフルPCE向けにこの文書で説明するPCEP拡張を使用してはなりません（MUST NOT）。PCCがこの文書に従った拡張をサポートしている（LSPオブジェクト内のN（P2MP-CAPABILITY）フラグとM（P2MP-LSP-UPDATE-CAPABILITY）フラグを理解する）にもかかわらず、この能力を広告していない場合、PCEからPCUpdメッセージを受信したときには、PCCはerror-type 19（"Invalid Operation"）、error-value 12（"Attempted LSP Update Request for P2MP if active stateful PCE capability for P2MP was not advertised"）のPCErrを生成し、PCEPセッションを終了すべきです（SHOULD）。PCEがこの文書に従った拡張をサポートしている（LSPオブジェクト内のN（P2MP-CAPABILITY）フラグを理解する）にもかかわらず、この能力を広告していない場合、PCCからPCRptメッセージを受信したときには、PCEはerror-type 19（"Invalid Operation"）、error-value 11（"Attempted LSP State Report for P2MP if stateful PCE capability for P2MP was not advertised"）のPCErrを生成すべきです（SHOULD）。また、PCEPセッションを終了すべきです（SHOULD）。

If a Stateful PCE receives a P2MP TE LSP report message and the PCE does not understand the N (P2MP-CAPABILITY) flag in the LSP object, and therefore the PCEP extensions described in this document, then the Stateful PCE would act as per Section 6.1 of [RFC8231] (and consider the PCRpt message as invalid).

ステートフルPCEがP2MP TE LSPの報告メッセージを受信し、そのPCEがLSPオブジェクト内のN（P2MP-CAPABILITY）フラグ、したがってこの文書で説明するPCEP拡張を理解しない場合、そのステートフルPCEは[RFC8231]のSection 6.1に従って動作します（そして、PCRptメッセージを無効なものとみなします）。

The PCEP extensions described in this document for PCC or PCE with the PCE-Initiation capability for P2MP TE LSPs MUST NOT be used if the PCC or PCE has not advertised its stateful capability with Instantiation and P2MP capability as per Section 5.2. If the PCC supports the extensions as per this document (understands the P (P2MP-LSP-INSTANTIATION-CAPABILITY) flag) but did not advertise this capability, then upon receipt of a PCInitiate message from the PCE, it SHOULD generate a PCErr with error-type 19 ("Invalid Operation"), error-value 13 ("Attempted LSP Instantiation Request for P2MP if stateful PCE instantiation capability for P2MP was not advertised"), and terminate the PCEP session.

PCCまたはPCEがSection 5.2に従ってインスタンス化能力とP2MP能力を備えたステートフル能力を広告していない場合、P2MP TE LSPのPCE起動能力を持つPCCまたはPCE向けにこの文書で説明するPCEP拡張を使用してはなりません（MUST NOT）。PCCがこの文書に従った拡張をサポートしている（P（P2MP-LSP-INSTANTIATION-CAPABILITY）フラグを理解する）にもかかわらず、この能力を広告していない場合、PCEからPCInitiateメッセージを受信したときには、PCCはerror-type 19（"Invalid Operation"）、error-value 13（"Attempted LSP Instantiation Request for P2MP if stateful PCE instantiation capability for P2MP was not advertised"）のPCErrを生成し、PCEPセッションを終了すべきです（SHOULD）。

12. Security Considerations

12. セキュリティーに関する考慮事項

The stateful operations on P2MP TE LSPs are more CPU intensive and also utilize more bandwidth on the wire (in comparison to P2P TE LSPs). If a rogue PCC were able to request unauthorized stateful PCE operations, then it may be able to mount a DoS attack against a PCE, which would disrupt the network and deny service to other PCCs. Similarly, an attacker may flood the PCC with PCUpd messages at a rate that exceeds either the PCC's ability to process them or the network's ability to signal the changes by either spoofing messages or compromising the PCE itself.

P2MP TE LSPに対するステートフルな操作は、（P2P TE LSPと比べて）CPU負荷が高く、回線上の帯域幅もより多く使用します。不正なPCCが認可されていないステートフルPCEの操作をリクエストできた場合、PCEに対するDoS攻撃を仕掛けることができる可能性があり、これはネットワークを混乱させ、他のPCCへのサービスを拒否することになります。同様に、攻撃者は、メッセージを偽装するかPCE自体を侵害することによって、PCCの処理能力やネットワークが変更をシグナリングする能力を超えるレートでPCCにPCUpdメッセージを大量に送り付ける可能性があります。

Consequently, it is important that implementations conform to the relevant security requirements as listed below:

したがって、実装は以下に挙げる関連するセキュリティー要件に準拠することが重要です。

  • As per [RFC8231], it is RECOMMENDED that these PCEP extensions only be activated on authenticated and encrypted sessions across PCEs and PCCs belonging to the same administrative authority, using Transport Layer Security (TLS) [RFC8253] as per the recommendations and best current practices in [RFC7525] (unless explicitly set aside in [RFC8253]).
  • Security considerations for path computation requests and responses are as per [RFC8306].
  • Security considerations for stateful operations (such as state report, synchronization, delegation, update, etc.) are as per [RFC8231].
  • Security considerations for the LSP instantiation mechanism are as per [RFC8231].
  • Security considerations as stated in Sections 10.1, 10.6, and 10.7 of [RFC5440] continue to apply.
  • [RFC8231]のとおり、これらのPCEP拡張は、同じ管理権限に属するPCEとPCCの間の、認証および暗号化されたセッション上でのみ有効にすることが推奨されます（RECOMMENDED）。その際には、（[RFC8253]で明示的に除外されていない限り）[RFC7525]の推奨事項とベストカレントプラクティスに従って、トランスポート層セキュリティー（Transport Layer Security: TLS）[RFC8253]を使用します。
  • 経路計算のリクエストとレスポンスに関するセキュリティーの考慮事項は、[RFC8306]に従います。
  • （状態報告、同期、委任、更新などの）ステートフルな操作に関するセキュリティーの考慮事項は、[RFC8231]に従います。
  • LSPのインスタンス化メカニズムに関するセキュリティーの考慮事項は、[RFC8231]に従います。
  • [RFC5440]のセクション10.1、10.6、10.7に記載されているセキュリティーの考慮事項は引き続き適用されます。
