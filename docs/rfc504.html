Workshop Announcement

ワークショップの案内

Title:
Automated Resource Sharing on the ARPANET
Date:
Monday May 21, 1973
Time:
9:00 AM to 5:00 PM
Place:
Bolt Beranek and Newman Inc., Cambridge, Mass.
Hosts:
TENEX and TIP Groups at BBN
題目：
ARPANETにおける自動化されたリソース共有（Automated Resource Sharing on the ARPANET）
日付：
1973年5月21日（月）
時間：
午前9時から午後5時まで
場所：
Bolt Beranek and Newman Inc.（マサチューセッツ州ケンブリッジ）
主催：
BBNのTENEXグループとTIPグループ

Theme:

テーマ：

This workshop will focus on various aspects of the question:

このワークショップでは、次の問いのさまざまな側面に焦点を当てます。

What steps can be taken to automate access to the distributed resources on the ARPANET?

ARPANET上の分散したリソースへのアクセスを自動化するために、どのような手段をとることができるか？

In particular, how can we move from where we are today toward an environment which facilitates resource sharing by moving the burden of dealing with the network from the human user to processes which act on his behalf? Additionally, operating systems themselves perform various operations not directly initiated by human users which could better be performed with the availability of resources on other systems (e.g. file system backup); how can we move toward an environment which facilitates such system-system cooperation?

特に、ネットワークを扱う負担を人間のユーザーから、ユーザーに代わって動作するプロセスへ移すことで、リソース共有を容易にする環境へと、今日の状況からどのように進んでいけるでしょうか？さらに、オペレーティングシステム自体も、人間のユーザーが直接開始したのではないさまざまな操作を行っており、それらは他のシステムのリソースを利用できればもっとうまく行えるかもしれません（たとえば、ファイルシステムのバックアップ）。そのようなシステム間の協調を容易にする環境へと、どのように進んでいけるでしょうか？

Objectives of Workshop:

ワークショップの目的：

  1. To identify and clarify the issues raised by automated resource sharing.

    What are the obstacles preventing more widespread resource sharing on the ARPANET? Are they technical, political, administrative in nature? Is it that there are few resources worth sharing (we don't think so)? Is automated sharing a bad idea (We don't think so)?

  2. To identify resources at various network sites appropriate for automated sharing; and to identify the need for resources which don't but should exist.

  3. To formulate a series of experiments for the purpose of evaluating relative merits and disadvantages of different approaches to automating resource sharing.

    The intent of such experimentation is to gain experience through construction and use of prototype systems which support automated sharing.

  1. 自動化されたリソース共有によって生じる問題を特定し、明確にすること。

    ARPANET上でリソース共有がもっと広まるのを妨げている障害は何でしょうか？それは技術的、政治的、管理上のどの性質のものでしょうか？共有する価値のあるリソースが少ないのでしょうか（私たちはそうは思いません）？自動化された共有は悪い考えなのでしょうか（私たちはそうは思いません）？

  2. ネットワークのさまざまなサイトで、自動化された共有に適したリソースを特定すること。また、存在しないが存在すべきリソースの必要性を明らかにすること。

  3. リソース共有を自動化するためのさまざまなアプローチの相対的な長所と短所を評価する目的で、一連の実験を策定すること。

    そのような実験の意図は、自動化された共有をサポートするプロトタイプシステムの構築と使用を通じて経験を得ることです。

Format of Workshop:

ワークショップの形式：

Morning:

午前：

In order to get the workshop "up to speed", each participant will be expected to give a brief presentation of relevant work he (his site) is currently engaged in, is planning to do, or to identify and discuss issues he feels are relevant to the subject. Time will be allowed for brief discussion after each presentation.

ワークショップを「軌道に乗せる」ために、各参加者には、自分（自分のサイト）が現在取り組んでいる、あるいは計画している関連作業について簡単な発表をしてもらうか、このテーマに関連すると思う問題を挙げて議論してもらいます。各発表のあとには、短い議論の時間を設けます。

Afternoon:

午後：

General discussion of the issues raised during the morning session. Possible subjects for discussion include (but need not be limited to):

午前のセッションで挙がった問題について全体で議論します。議論の題目としては、次のようなものが考えられます（ただし、これらに限定する必要はありません）。

  1. Identification of possible multi-site "services".

    Intersite mail, terminal linking, status information are some examples - what are others?

  2. Identification of resources appropriate for remote utilization.

    File systems, compilers, on-line query systems, manuscript preparation systems are some examples - what are others?

  3. Access to remote resources.

    Possibility of access paths other than the standard logger port. To what extent (if at all) can the access paths to a variety of different resources be standardized? How can resources which may move from Host to Host or may be available on several Hosts be dynamically located and selected for use? The need for (desirability of) a "broadcast ICP".

  4. Problems of accounting for resource utilization.

    Some form of network wide accounting would be a great convenience. For example, it would be nice if a user could use the same account at many (all?) sites. What are the problems (if any) preventing this?

  5. Problems of security and access control.

    Authentication of users/processes attempting to use resources. As with network wide accounts, the ability to use the same name and password at all sites would be convenient. How can a user's password and other sensitive data be protected in such an environment?

    The notion of a third party password validation and user authentication service.

  6. Approaches to automating resource sharing.

    It is possible without difficulty to identify several which on the surface appear to be different:

    1. Multi-site executive programs which make resources accessible to the user at the command language level; e.g. the inter-site, user-user interaction and file maintenance activity supported by the RSEXEC.
    2. A programming language environment designed to facilitate resource sharing; e.g. LISP is a machine independent language - one could imagine a multi-computer LISP system which supported automated resource sharing.
    3. The "collect a resource" approach - identify an Editor here, file storage service there, a compiler somewhere else, etc; and build a "workshop" environment which provides convenient access to these resources.

    What are the relative merits and disadvantages of these approaches? What aspects do these approaches have in common? Is it possible to identify a common base capable of supporting them all?

  7. Protocols to support automated resource sharing.

    It would be inappropriate to attempt to generate a detailed protocol specification at this workshop. However, it is appropriate to discuss the kinds of activity a protocol should support. Existing protocols (excepting Host-Host protocol and possibly, the new TELNET protocol) appear to be oriented toward human users. Automated resource sharing suggests processes acting on behalf of human users to interface to remote resources; this in turn suggests that the protocols should be highly process oriented. For example, because there should be minimal human intervention in error recovery, the protocols should be extremely robust; e.g., include well specified time outs, etc.

  1. 複数のサイトにまたがる「サービス」になりうるものの特定。

    サイト間のメール、端末のリンク、ステータス情報などがその例です。ほかには何があるでしょうか？

  2. リモートからの利用に適したリソースの特定。

    ファイルシステム、コンパイラー、オンライン照会システム、原稿作成システムなどがその例です。ほかには何があるでしょうか？

  3. リモートのリソースへのアクセス。

    標準のロガーポート以外のアクセス経路の可能性。さまざまな異なるリソースへのアクセス経路は、どの程度（そもそも可能であれば）標準化できるでしょうか？ホストからホストへ移動するかもしれないリソースや、複数のホストで利用できるかもしれないリソースを、どのようにして動的に見つけ、選択して使用できるでしょうか？「ブロードキャストICP」の必要性（望ましさ）。

  4. リソース利用の課金の問題。

    何らかの形のネットワーク全体での課金があれば、非常に便利でしょう。たとえば、ユーザーが多くの（すべての？）サイトで同じアカウントを使えればよいでしょう。これを妨げている問題は（もしあるとすれば）何でしょうか？

  5. セキュリティーとアクセス制御の問題。

    リソースを使おうとするユーザーやプロセスの認証。ネットワーク全体でのアカウントと同様に、すべてのサイトで同じ名前とパスワードを使えれば便利でしょう。そのような環境で、ユーザーのパスワードやその他の機密データをどのように保護できるでしょうか？

    第三者によるパスワード検証とユーザー認証のサービスという考え方。

  6. リソース共有を自動化するためのアプローチ。

    表面上は異なるように見えるアプローチを、苦労せずにいくつか挙げることができます。

    1. コマンド言語のレベルでユーザーがリソースにアクセスできるようにする、複数のサイトにまたがるエグゼクティブプログラム。たとえば、RSEXECがサポートしている、サイト間のユーザー同士のやりとりやファイル保守の活動。
    2. リソース共有を容易にするように設計されたプログラミング言語環境。たとえば、LISPはマシンに依存しない言語なので、自動化されたリソース共有をサポートする、複数のコンピューターにまたがるLISPシステムを想像できます。
    3. 「リソースを集める」アプローチ。こちらではエディター、あちらではファイル保存サービス、どこか別の場所ではコンパイラーといったように特定し、それらのリソースへの便利なアクセスを提供する「ワークショップ」環境を構築します。

    これらのアプローチの相対的な長所と短所は何でしょうか？これらのアプローチに共通する側面は何でしょうか？それらすべてをサポートできる共通の基盤を見いだすことはできるでしょうか？

  7. 自動化されたリソース共有をサポートするプロトコル。

    このワークショップで詳細なプロトコル仕様を作ろうとするのは適切ではありません。しかし、プロトコルがサポートすべき活動の種類を議論するのは適切です。既存のプロトコル（ホスト間プロトコルと、おそらく新しいTELNETプロトコルは除きます）は、人間のユーザー向けになっているようです。自動化されたリソース共有では、人間のユーザーに代わってプロセスがリモートのリソースとやりとりすることになり、ひいては、プロトコルが高度にプロセス指向であるべきだということになります。たとえば、エラー回復における人間の介入は最小限であるべきなので、プロトコルは極めて堅牢であるべきです。たとえば、明確に規定されたタイムアウトなどを含めるべきです。

The following questions may be helpful in focusing your thinking:

考えをまとめるには、次の問いが役立つかもしれません。

  • What resources would your site be willing to make available for use in automated resource sharing experiments?
  • Under what conditions would your site be willing or able to participate in such experiments?
  • What administrative and/or technical considerations would prevent your site from entering into a network wide resource sharing agreement?
  • If you employ accounting Procedures that require cost recovery, how, if at all, should they be modified to work in a network resource sharing environment?
  • あなたのサイトは、自動化されたリソース共有の実験で使うために、どのようなリソースを提供してもよいと考えていますか？
  • あなたのサイトは、どのような条件のもとであれば、そのような実験に参加する意思がある、あるいは参加できますか？
  • あなたのサイトがネットワーク全体のリソース共有の協定を結ぶのを妨げるのは、どのような管理上や技術上の考慮事項ですか？
  • コスト回収を必要とする課金手続きを採用している場合、ネットワークでリソースを共有する環境で機能させるには、それをどのように変更すべきでしょうか（そもそも変更すべきでしょうか）？
