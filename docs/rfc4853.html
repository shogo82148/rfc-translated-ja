RFC 4853

Cryptographic Message Syntax (CMS) Multiple Signer Clarification

RFC 4853

暗号メッセージ構文（CMS）の複数署名者に関する明確化

Abstract

概要

This document updates the Cryptographic Message Syntax (CMS), which is published in RFC 3852. This document clarifies the proper handling of the SignedData protected content type when more than one digital signature is present.

この文書は、RFC 3852で公開されている暗号メッセージ構文（Cryptographic Message Syntax、CMS）を更新します。この文書は、複数のデジタル署名が存在する場合のSignedData保護コンテンツタイプの適切な扱いを明確にします。

1. Introduction

1. はじめに

This document updates the Cryptographic Message Syntax [CMS]. The CMS SignedData protected content type allows multiple digital signatures, but the specification is unclear about the appropriate processing by a recipient of such a signed content. This document provides replacement text for a few paragraphs, making it clear that the protected content is validly signed by a given signer, if any of the digital signatures from that signer are valid.

この文書は、暗号メッセージ構文[CMS]を更新します。CMSのSignedData保護コンテンツタイプでは複数のデジタル署名が許されていますが、そのような署名付きコンテンツを受信者がどのように処理するのが適切かについて、仕様は明確ではありません。この文書は、いくつかの段落の置き換えテキストを提供し、ある署名者によるデジタル署名のいずれかが有効であれば、保護されたコンテンツはその署名者によって有効に署名されていることを明確にします。

This property is especially important in two cases. First, when the recipients do not all implement the same digital signature algorithm, a signer can sign the content with several different digital signature algorithms so that each of the recipients can find an acceptable signature. For example, if some recipients support RSA and some recipients support ECDSA, then the signer can generate two signatures, one with RSA and one with ECDSA, so that each recipient will be able to validate one of the signatures. Second, when a community is transitioning one-way hash functions or digital signature algorithms, a signer can sign the content with the older and the newer signature algorithms so that each recipient can find an acceptable signature, regardless of their state in the transition. For example, consider a transition from RSA with SHA-1 to RSA with SHA-256. The signer can generate two signatures, one with SHA-1 and one with SHA-256, so that each recipient will be able to validate at least one of the RSA signatures.

この性質は、2つの場合に特に重要です。1つ目は、受信者全員が同じデジタル署名アルゴリズムを実装しているわけではない場合です。このとき署名者は、受信者がそれぞれ受け入れ可能な署名を見つけられるように、いくつかの異なるデジタル署名アルゴリズムでコンテンツに署名できます。たとえば、RSAをサポートする受信者とECDSAをサポートする受信者がいる場合、署名者はRSAによる署名とECDSAによる署名の2つを生成できます。これにより、各受信者はどちらかの署名を検証できるようになります。2つ目は、コミュニティーが一方向ハッシュ関数やデジタル署名アルゴリズムを移行している最中の場合です。このとき署名者は、移行のどの段階にあっても各受信者が受け入れ可能な署名を見つけられるように、古い署名アルゴリズムと新しい署名アルゴリズムでコンテンツに署名できます。たとえば、SHA-1を使ったRSAから、SHA-256を使ったRSAへの移行を考えてみます。署名者はSHA-1による署名とSHA-256による署名の2つを生成できます。これにより、各受信者は少なくとも1つのRSA署名を検証できるようになります。

3. Update to RFC 3852, Section 5: Signed-data Content Type

3. RFC 3852のセクション5「Signed-data Content Type」の更新

RFC 3852, section 5, the next to the last paragraph says:

RFC 3852のセクション5の最後から2番目の段落は、次のようになっています。

A recipient independently computes the message digest. This message digest and the signer's public key are used to verify the signature value. The signer's public key is referenced either by an issuer distinguished name along with an issuer-specific serial number or by a subject key identifier that uniquely identifies the certificate containing the public key. The signer's certificate can be included in the SignedData certificates field.

受信者は、独自にメッセージダイジェストを計算します。このメッセージダイジェストと署名者の公開鍵を使って、署名値を検証します。署名者の公開鍵は、発行者の識別名（distinguished name）と発行者固有のシリアル番号の組か、公開鍵を含む証明書を一意に識別するサブジェクト鍵識別子（subject key identifier）のいずれかによって参照されます。署名者の証明書は、SignedDataのcertificatesフィールドに含めることができます。

This block of text is replaced with:

このテキストのブロックを、次のテキストに置き換えます。

A recipient independently computes the message digest. This message digest and the signer's public key are used to verify the signature value. The signer's public key is referenced either by an issuer distinguished name along with an issuer-specific serial number or by a subject key identifier that uniquely identifies the certificate containing the public key. The signer's certificate can be included in the SignedData certificates field.

When more than one signature is present, the successful validation of one signature associated with a given signer is usually treated as a successful signature by that signer. However, there are some application environments where other rules are needed. An application that employs a rule other than one valid signature for each signer must specify those rules. Also, where simple matching of the signer identifier is not sufficient to determine whether the signatures were generated by the same signer, the application specification must describe how to determine which signatures were generated by the same signer. Support of different communities of recipients is the primary reason that signers choose to include more than one signature. For example, the signed-data content type might include signatures generated with the RSA signature algorithm and with the ECDSA signature algorithm. This allows recipients to verify the signature associated with one algorithm or the other.

受信者は、独自にメッセージダイジェストを計算します。このメッセージダイジェストと署名者の公開鍵を使って、署名値を検証します。署名者の公開鍵は、発行者の識別名（distinguished name）と発行者固有のシリアル番号の組か、公開鍵を含む証明書を一意に識別するサブジェクト鍵識別子（subject key identifier）のいずれかによって参照されます。署名者の証明書は、SignedDataのcertificatesフィールドに含めることができます。

複数の署名が存在する場合、ある署名者に関連付けられた1つの署名の検証に成功すれば、通常はその署名者による署名が成功したものとして扱われます。ただし、別の規則が必要となるアプリケーション環境もあります。署名者ごとに1つの有効な署名、という規則以外の規則を採用するアプリケーションは、その規則を規定しなければなりません。また、署名者識別子の単純な照合だけでは、署名が同じ署名者によって生成されたかどうかを判断するのに十分でない場合、アプリケーションの仕様は、どの署名が同じ署名者によって生成されたかを判断する方法を記述しなければなりません。署名者が複数の署名を含めることを選ぶ主な理由は、異なる受信者のコミュニティーをサポートすることです。たとえば、signed-dataコンテンツタイプには、RSA署名アルゴリズムで生成された署名とECDSA署名アルゴリズムで生成された署名が含まれることがあります。これにより、受信者はどちらか一方のアルゴリズムに関連付けられた署名を検証できます。

4. Update to RFC 3852, Section 5.1: SignedData Type

4. RFC 3852のセクション5.1「SignedData Type」の更新

RFC 3852, section 5.1, the next to the last paragraph says:

RFC 3852のセクション5.1の最後から2番目の段落は、次のようになっています。

signerInfos is a collection of per-signer information. There MAY be any number of elements in the collection, including zero. The details of the SignerInfo type are discussed in section 5.3. Since each signer can employ a digital signature technique and future specifications could update the syntax, all implementations MUST gracefully handle unimplemented versions of SignerInfo. Further, since all implementations will not support every possible signature algorithm, all implementations MUST gracefully handle unimplemented signature algorithms when they are encountered.

signerInfosは、署名者ごとの情報の集合です。この集合には、ゼロを含め任意の数の要素があってもよいです（MAY）。SignerInfo型の詳細はセクション5.3で説明します。各署名者はデジタル署名の手法を採用でき、将来の仕様で構文が更新される可能性があるので、すべての実装は、実装していないバージョンのSignerInfoを適切に扱わなければなりません（MUST）。さらに、すべての実装があらゆる署名アルゴリズムをサポートするわけではないので、すべての実装は、実装していない署名アルゴリズムに遭遇したときにそれを適切に扱わなければなりません（MUST）。

This block of text is replaced with:

このテキストのブロックを、次のテキストに置き換えます。

signerInfos is a collection of per-signer information. There MAY be any number of elements in the collection, including zero. When the collection represents more than one signature, the successful validation of one of signature from a given signer ought to be treated as a successful signature by that signer. However, there are some application environments where other rules are needed. The details of the SignerInfo type are discussed in section 5.3. Since each signer can employ a different digital signature technique, and future specifications could update the syntax, all implementations MUST gracefully handle unimplemented versions of SignerInfo. Further, since all implementations will not support every possible signature algorithm, all implementations MUST gracefully handle unimplemented signature algorithms when they are encountered.

signerInfosは、署名者ごとの情報の集合です。この集合には、ゼロを含め任意の数の要素があってもよいです（MAY）。この集合が複数の署名を表す場合、ある署名者による署名のうちの1つの検証に成功すれば、その署名者による署名が成功したものとして扱うのが妥当です。ただし、別の規則が必要となるアプリケーション環境もあります。SignerInfo型の詳細はセクション5.3で説明します。各署名者は異なるデジタル署名の手法を採用でき、将来の仕様で構文が更新される可能性があるので、すべての実装は、実装していないバージョンのSignerInfoを適切に扱わなければなりません（MUST）。さらに、すべての実装があらゆる署名アルゴリズムをサポートするわけではないので、すべての実装は、実装していない署名アルゴリズムに遭遇したときにそれを適切に扱わなければなりません（MUST）。

6. Security Considerations

6. セキュリティーに関する考慮事項

The replacement text will reduce the likelihood of interoperability errors during the transition from MD5 and SHA-1 to stronger one-way hash functions, or to better signature algorithms.

この置き換えテキストにより、MD5やSHA-1からより強力な一方向ハッシュ関数へ、あるいはより優れた署名アルゴリズムへ移行する間に、相互運用性のエラーが起こる可能性が低くなります。
