RFC 128

BYTES

RFC 128

バイト

Abstract

概要

It is somewhat unclear what to do with the Byte size parameter now allowed by the 2nd level protocol. I can conceive of an implementation in which the 3rd level programs never see this parameter. Crocker implies in RFC 123 that control of this parameter is given to the 3rd level programs and that both sender and receiver may specify values of the byte size to the NCP.

第2レベルのプロトコルで指定できるようになったバイトサイズパラメーターをどう扱えばよいかは、いくぶん不明確です。第3レベルのプログラムがこのパラメーターをまったく目にしない実装も考えられます。CrockerはRFC 123で、このパラメーターの制御は第3レベルのプログラムに委ねられ、送信側と受信側の両方がNCPに対してバイトサイズの値を指定できることを示唆しています。

There are at least two interpretations if the sender and receiver specify different byte sizes.

送信側と受信側が異なるバイトサイズを指定した場合、少なくとも2つの解釈があります。

  1. The first is that the connection is illegal.

  2. The second is that the NCP must parse the data stream on receipt from the network and into a buffer according to be byte size of the sender, and subsequently parse the data stream on transfer from the buffer to the receiver. In this second case there are two sub cases.

    1. One is to consider bits as the basic unit.

      For example, if the sender specified byte size = 5 and the receiver specified byte size = 3 then

                Receiver                   NCP                    Sender
          -+---+---+---+---+      +--------+      +-----+-----+---
           |000|001|010|011| <--- | Buffer | <--- |00000|10100|11
          -+---+---+---+---+      +--------+      +-----+-----+---
    2. The other is to consider bytes as the significant unit and pad (on the right or left?) or truncate to make things fit, or other transformation.
  1. 1つ目は、そのコネクションは不正であるという解釈です。

  2. 2つ目は、NCPが、ネットワークから受信したデータストリームを送信側のバイトサイズに従って解析してバッファーに入れ、その後、バッファーから受信側へ転送する際にデータストリームを解析しなければならないという解釈です。この2つ目の場合には、さらに2つのサブケースがあります。

    1. 1つは、ビットを基本単位とみなす方法です。

      たとえば、送信側がバイトサイズ = 5を指定し、受信側がバイトサイズ = 3を指定した場合は次のようになります。

                Receiver                   NCP                    Sender
          -+---+---+---+---+      +--------+      +-----+-----+---
           |000|001|010|011| <--- | Buffer | <--- |00000|10100|11
          -+---+---+---+---+      +--------+      +-----+-----+---
    2. もう1つは、バイトを意味のある単位とみなし、収まるように（右か左に？）パディングするか切り詰める、あるいはほかの変換を行う方法です。

At UCLA-Computer Science we are contemplating allowing sender and receiver to specify different byte sizes and consider bits as the basic unit (Case II.A.). This does not rule out our considering the second subcase (Case II.B.). We may allow 3rd level programs to specify a library or user supplied routine to perform the transformation between sender and receiver bytes. Perhaps these transformation routines would be written in the Data Reconfiguration Language.

UCLA-Computer Scienceでは、送信側と受信側が異なるバイトサイズを指定できるようにし、ビットを基本単位とみなす方法（ケースII.A.）を検討しています。これは、2つ目のサブケース（ケースII.B.）を検討することを排除するものではありません。送信側のバイトと受信側のバイトの間の変換を行うために、第3レベルのプログラムがライブラリーまたはユーザーが用意したルーチンを指定できるようにするかもしれません。おそらく、これらの変換ルーチンはData Reconfiguration Languageで書かれることになるでしょう。
