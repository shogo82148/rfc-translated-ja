RFC 202

Possible Deadlock in ICP

RFC 202

ICPで起こりうるデッドロック

Abstract

概要

We have noticed a possible deadlock situation which may arise using the Initial Connection Protocol (ICP) specified in Document #2 (NIC #7101 in the Current Network Protocols Notebook NIC #7104).

Document #2（Current Network Protocols Notebook NIC #7104の中のNIC #7101）で規定されている初期接続プロトコル（Initial Connection Protocol、ICP）を使うときに起こりうるデッドロックの状況に、私たちは気づきました。

If on both sides one RFC is issued and a "wait for match" is required before the second RFC is issued, it is possible that the first RFC's will not match. In particular a deadlock will occur if both sides open their send or both sides open their receive sockets first.

双方がそれぞれ1つの接続要求（RFC）を発行し、2つ目のRFCを発行する前に「一致を待つ」必要がある場合、最初のRFCどうしが一致しない可能性があります。特に、双方が先に送信ソケットを開いた場合、または双方が先に受信ソケットを開いた場合には、デッドロックが発生します。

Briefly the ICP is:

ICPを簡単に示すと、次のとおりです。

<where the original uses a script lowercase letter with a single digit subscript we use the lower case letter followed by {digit} so that script-m-subscript-2 is printed m{2}>

<原文で添字に1桁の数字が付いた筆記体の小文字を使っている箇所は、小文字の後に{数字}を続けて表します。たとえば、筆記体のmに添字2が付いたものはm{2}と表記します>

Server                                User
------                                ----

S1:  Listen on socket L.              U1:  RTS(U, L, l{1})

S2:  Wait for a match.                U2:  Wait for match.

S3:  STR(L, U, s{1})

S4:  Wait for allocation.             U3:  All(l{1}, m{1}, b{1})

S5:  Send data S in s{1} bit          U4:  Receive data S in s{1}
     bytes as allowed by                   bit bytes.
     allocation m{1}, b{1}.

S6:  CLS(L, U)                        U5:  CLS(U, L)

S7:  RTS(S, U+3, l{2})                U6:  STR(U+3, S, s{2})

S8:  STR(S+1, U+2, s{3})              U7:  RTS(U+2, S+1, l{3})

Server                                User
------                                ----

S1:  Listen on socket L.              U1:  RTS(U, L, l{1})

S2:  Wait for a match.                U2:  Wait for match.

S3:  STR(L, U, s{1})

S4:  Wait for allocation.             U3:  All(l{1}, m{1}, b{1})

S5:  Send data S in s{1} bit          U4:  Receive data S in s{1}
     bytes as allowed by                   bit bytes.
     allocation m{1}, b{1}.

S6:  CLS(L, U)                        U5:  CLS(U, L)

S7:  RTS(S, U+3, l{2})                U6:  STR(U+3, S, s{2})

S8:  STR(S+1, U+2, s{3})              U7:  RTS(U+2, S+1, l{3})

"The labels here imply no ordering except that ordering required by the Host-Host Protocol. Note that steps S7 and S8 can be reversed as can U6 and U7. Also, notice that at any time after S2 the server could initiate steps S7 and S8 in parallel with steps S3 through S6, and that at any time after U4 the user could initiate steps U6 and U7 in parallel with step U5."

「ここでのラベルは、ホスト間プロトコル（Host-Host Protocol）が要求する順序以外の順序を意味するものではありません。ステップS7とS8は順序を入れ替えることができ、U6とU7も同様です。また、サーバーはS2以降のいつでも、ステップS3からS6と並行してステップS7とS8を開始でき、ユーザーはU4以降のいつでも、ステップU5と並行してステップU6とU7を開始できることにも注意してください。」

We recommend that the server perform steps 7 and 8 before waiting for the user to perform step 6 or 7. It is also suggested that the user issue the RFC's in steps 6 and 7 without waiting for the server. (If the user is only Listening then both Listens should be issued without waiting for the server.) If for some reason a host must delay between issuing RFC's it must issue the RFC's involving sockets S and U+3 first.

私たちは、サーバーがステップ7と8を実行してから、ユーザーがステップ6または7を実行するのを待つことを推奨します。また、ユーザーはサーバーを待たずにステップ6と7のRFCを発行することを提案します。（ユーザーがListenするだけの場合は、サーバーを待たずに両方のListenを発行すべきです。）何らかの理由でホストがRFCの発行の間に遅延を入れなければならない場合は、ソケットSとU+3に関わるRFCを先に発行しなければなりません。
