RFC 7952

Defining and Using Metadata with YANG

RFC 7952

YANGによるメタデータの定義と使用

Abstract

概要

This document defines a YANG extension that allows for defining metadata annotations in YANG modules. The document also specifies XML and JSON encoding of annotations and other rules for annotating instances of YANG data nodes.

この文書は、YANGモジュールでメタデータアノテーションを定義できるようにするYANG拡張を定義します。また、この文書は、アノテーションのXMLおよびJSONエンコーディングと、YANGデータノードのインスタンスにアノテーションを付けるためのその他の規則も規定します。

1. Introduction

1. はじめに

There is a need to be able to annotate instances of YANG [RFC7950] data nodes with metadata. Typical use cases are as follows:

YANG[RFC7950]データノードのインスタンスに、メタデータでアノテーションを付けられるようにする必要があります。典型的なユースケースは次のとおりです。

  • Complementing regular data model information with instance-specific metadata, comments, etc.
  • Providing information about the rendering of data in user interfaces.
  • Deactivating a subtree in a configuration datastore while keeping the data in place.
  • Network management protocols often use metadata annotations for various purposes in both operation requests and responses. For example, the <edit-config> operation in the Network Configuration Protocol (NETCONF) (see Section 7.2 of [RFC6241]) uses annotations in the form of XML attributes for identifying the location in a configuration datastore and the type of the operation.
  • 通常のデータモデルの情報を、インスタンス固有のメタデータやコメントなどで補完する。
  • ユーザーインターフェイスでのデータの表示に関する情報を提供する。
  • 設定データストア内のサブツリーを、データをその場に残したまま無効化する。
  • ネットワーク管理プロトコルは、操作のリクエストとレスポンスの両方で、さまざまな目的のためにメタデータアノテーションをよく使用します。たとえば、ネットワーク設定プロトコル（NETCONF）の<edit-config>操作（[RFC6241]のセクション7.2を参照）は、設定データストア内の位置と操作の種類を識別するために、XML属性の形式のアノテーションを使用します。

However, metadata annotations could potentially lead to interoperability problems if they are used in an ad hoc fashion by different parties and/or without proper documentation. A sound metadata framework for YANG should therefore satisfy these requirements:

しかし、メタデータアノテーションは、異なる当事者によって場当たり的に使用されたり、適切な文書化なしに使用されたりすると、相互運用性の問題を引き起こす可能性があります。したがって、YANGのための健全なメタデータのフレームワークは、次の要件を満たすべきです。

  1. The set of annotations must be extensible in a decentralized manner so as to allow for defining new annotations without running the risk of collisions with annotations defined and used by others.
  2. The syntax and semantics of annotations must be documented, and the documentation must be easily accessible.
  3. Clients of network management protocols such as NETCONF [RFC6241] or RESTCONF [RESTCONF] must be able to discover all annotations supported by a given server and identify each of them correctly.
  4. Annotations sent by a server should not break clients that don't support them.
  1. アノテーションの集合は、ほかの者が定義して使用するアノテーションと衝突する危険を冒さずに新しいアノテーションを定義できるよう、分散的な方法で拡張可能でなければなりません。
  2. アノテーションの構文とセマンティクスは文書化されなければならず、その文書には容易にアクセスできなければなりません。
  3. NETCONF[RFC6241]やRESTCONF[RESTCONF]などのネットワーク管理プロトコルのクライアントは、あるサーバーがサポートするすべてのアノテーションを発見し、それぞれを正しく識別できなければなりません。
  4. サーバーが送信するアノテーションは、それをサポートしないクライアントを壊すべきではありません。

This document proposes a systematic way to define metadata annotations. For this purpose, the YANG extension "annotation" is defined in the module "ietf-yang-metadata" (Section 7). Other YANG modules importing this module can use the "annotation" statement for defining one or more annotations.

この文書は、メタデータアノテーションを定義するための体系的な方法を提案します。この目的のため、YANG拡張"annotation"をモジュール"ietf-yang-metadata"（セクション7）で定義します。このモジュールをインポートするほかのYANGモジュールは、"annotation"ステートメントを使用して1つ以上のアノテーションを定義できます。

The benefits of defining the metadata annotations in a YANG module are the following:

メタデータアノテーションをYANGモジュールで定義する利点は次のとおりです。

  • Each annotation is bound to a YANG module name and namespace URI. This makes its encoding in instance documents (both XML and JSON) straightforward and consistent with the encoding of YANG data node instances.
  • Annotations defined in IETF Standards Track documents are indirectly registered through IANA in the "YANG Module Names" registry [RFC6020].
  • Annotations are included in the data model. YANG compilers and tools supporting a certain annotation can thus take them into account and modify their behavior accordingly.
  • The semantics of an annotation are defined in the "description" and "reference" statements.
  • An annotation can be declared as conditional by using the "if-feature" statement.
  • The type of each annotation is explicitly specified; any YANG built-in or derived type that is available for leaf or leaf-list data nodes may be specified for annotations as well.
  • 各アノテーションは、YANGモジュール名と名前空間URIに結び付けられます。これにより、インスタンス文書（XMLとJSONの両方）でのアノテーションのエンコーディングが単純になり、YANGデータノードのインスタンスのエンコーディングとも一貫したものになります。
  • IETFの標準化過程の文書で定義されたアノテーションは、"YANG Module Names"レジストリー[RFC6020]を通じて、間接的にIANAに登録されます。
  • アノテーションはデータモデルに含まれます。したがって、特定のアノテーションをサポートするYANGコンパイラーやツールは、それを考慮に入れ、それに応じて振る舞いを変えることができます。
  • アノテーションのセマンティクスは、"description"ステートメントと"reference"ステートメントで定義されます。
  • "if-feature"ステートメントを使用して、アノテーションを条件付きとして宣言できます。
  • 各アノテーションの型は明示的に指定されます。leafまたはleaf-listのデータノードで利用できる任意のYANGの組み込み型または派生型を、アノテーションにも指定できます。

In the XML encoding, XML attributes are a natural instrument for attaching annotations to data node instances. This document deliberately adopts some restrictions in order to remain compatible with the XML encoding of YANG data node instances and limitations of XML attributes. Specifically,

XMLエンコーディングでは、XML属性は、データノードのインスタンスにアノテーションを付加するための自然な手段です。この文書は、YANGデータノードのインスタンスのXMLエンコーディングとの互換性を保ち、XML属性の制限に合わせるため、意図的にいくつかの制約を採用しています。具体的には、次のとおりです。

  • annotations can only be scalar values.
  • annotations cannot be attached to a whole list or leaf-list instance, only to individual list or leaf-list entries.
  • アノテーションはスカラー値にしかできません。
  • アノテーションは、listまたはleaf-listのインスタンス全体には付加できず、listまたはleaf-listの個々のエントリーにのみ付加できます。

Due to the rules for YANG extensions (see Section 6.3.1 of [RFC7950]), annotation definitions posit relatively weak conformance requirements. The alternative of introducing a new built-in YANG statement for defining annotations was considered, but it was seen as a major change to the language that is inappropriate for YANG 1.1, which was chartered as a maintenance revision. After evaluating real-life usage of metadata annotations, it is conceivable that such a new built-in statement might be added in a future revision of YANG.

YANG拡張に関する規則（[RFC7950]のセクション6.3.1を参照）のため、アノテーションの定義が課す準拠要件は比較的弱いものになります。アノテーションを定義するための新しい組み込みYANGステートメントを導入するという代替案も検討されましたが、それは言語に対する大きな変更であり、保守のための改訂として憲章で位置付けられたYANG 1.1には不適切であると判断されました。メタデータアノテーションの実際の使用状況を評価したあとで、そのような新しい組み込みステートメントが将来のYANGの改訂で追加される可能性も考えられます。

2.4. Definitions of New Terms

2.4. 新しい用語の定義

  • annotation: a single item of metadata that is attached to YANG data node instances.
  • metadata: additional information that complements a data tree.
  • metadata object: an object in JSON encoding that contains all annotations attached to a given data node instance.
  • アノテーション（annotation）：YANGデータノードのインスタンスに付加される、メタデータの単一の項目。

3. Defining Annotations in YANG

3. YANGでのアノテーションの定義

Metadata annotations are defined by the YANG extension "md:annotation". This YANG language extension is defined in the module "ietf-yang-metadata" (Section 7).

メタデータアノテーションは、YANG拡張"md:annotation"によって定義されます。このYANG言語拡張は、モジュール"ietf-yang-metadata"（セクション7）で定義されています。

Substatements of "md:annotation" are shown in Table 2. They are all core YANG statements, and the numbers in the second column refer to the corresponding section in [RFC7950] where each statement is described.

"md:annotation"のサブステートメントを表2に示します。これらはすべてYANGの中核となるステートメントであり、2列目の番号は、各ステートメントが記述されている[RFC7950]の対応するセクションを示します。

Table 2: Substatements of "md:annotation"
substatement section in RFC 7950 cardinality
description 7.21.3 0..1
if-feature 7.20.2 0..n
reference 7.21.4 0..1
status 7.21.2 0..1
type 7.6.3 1
units 7.3.3 0..1
表2: "md:annotation"のサブステートメント
サブステートメント RFC 7950のセクション カーディナリティー
description 7.21.3 0..1
if-feature 7.20.2 0..n
reference 7.21.4 0..1
status 7.21.2 0..1
type 7.6.3 1
units 7.3.3 0..1

An annotation carries a single value. The "type" substatement, which MUST be present, takes as an argument the name of an existing built-in or derived type, and the value of the annotation MUST match this type. See Section 7.4 of [RFC7950] for details.

アノテーションは単一の値を持ちます。"type"サブステートメントは必ず存在しなければなりません（MUST）。このサブステートメントは既存の組み込み型または派生型の名前を引数に取り、アノテーションの値はこの型に一致しなければなりません（MUST）。詳細は[RFC7950]のセクション7.4を参照してください。

An annotation can be made conditional by using one or more "if-feature" statements; the annotation is then supported only by servers that advertise the corresponding feature.

1つ以上の"if-feature"ステートメントを使用して、アノテーションを条件付きにできます。その場合、アノテーションは、対応する機能を広告するサーバーだけがサポートします。

The semantics and usage rules for an annotation SHOULD be fully specified in "description", "reference", and "units" statements.

アノテーションのセマンティクスと使用規則は、"description"、"reference"、"units"の各ステートメントで完全に規定されるべきです（SHOULD）。

An annotation MUST NOT change the data tree semantics defined by YANG. For example, it is illegal to define and use an annotation that allows for overriding uniqueness of leaf-list entries.

アノテーションは、YANGが定義するデータツリーのセマンティクスを変更してはなりません（MUST NOT）。たとえば、leaf-listのエントリーの一意性を覆すことを可能にするアノテーションを定義して使用することは不正です。

The "status" statement can be used exactly as it is used for YANG data nodes.

"status"ステートメントは、YANGデータノードで使用する場合とまったく同じように使用できます。

A YANG module containing one or more "md:annotation" statements SHOULD NOT be used for defining data nodes or groupings. Also, derived types, identities, and features SHOULD NOT be defined in such a module unless they are used by the definitions of annotations in that module.

1つ以上の"md:annotation"ステートメントを含むYANGモジュールは、データノードやグルーピングの定義に使用されるべきではありません（SHOULD NOT）。また、派生型、アイデンティティー、機能は、そのモジュール内のアノテーションの定義で使用される場合を除き、そのようなモジュールで定義されるべきではありません（SHOULD NOT）。

3.1. Example Definition

3.1. 定義の例

The following module defines the "last-modified" annotation:

次のモジュールは、"last-modified"アノテーションを定義します。

module example-last-modified {
  namespace "http://example.org/example-last-modified";
  prefix "elm";
  import ietf-yang-types {
    prefix "yang";
  }
  import ietf-yang-metadata {
    prefix "md";
  }
  md:annotation last-modified {
    type yang:date-and-time;
    description
      "This annotation contains the date and time when the
       annotated instance was last modified (or created).";
  }
}

module example-last-modified {
  namespace "http://example.org/example-last-modified";
  prefix "elm";
  import ietf-yang-types {
    prefix "yang";
  }
  import ietf-yang-metadata {
    prefix "md";
  }
  md:annotation last-modified {
    type yang:date-and-time;
    description
      "This annotation contains the date and time when the
       annotated instance was last modified (or created).";
  }
}

4. Using Annotations

4. アノテーションの使用

By advertising a YANG module in which a metadata annotation is defined using the "md:annotation" statement, a server indicates that it is prepared to handle that annotation according to the annotation's definition. That is, an annotation advertised by the server may be attached to an instance of a data node defined in any YANG module that is implemented by the server.

"md:annotation"ステートメントを使用してメタデータアノテーションが定義されているYANGモジュールを広告することで、サーバーは、そのアノテーションの定義に従ってそのアノテーションを扱う用意があることを示します。つまり、サーバーが広告したアノテーションは、そのサーバーが実装する任意のYANGモジュールで定義されたデータノードのインスタンスに付加できます。

Depending on its semantics, an annotation may have an effect only in certain data trees and/or on instances of specific types of data nodes.

アノテーションは、そのセマンティクスによっては、特定のデータツリーでのみ、または特定の種類のデータノードのインスタンスに対してのみ、効果を持つ場合があります。

A client MUST NOT add a specific annotation to data node instances if the server didn't advertise it.

サーバーが広告していない特定のアノテーションを、クライアントがデータノードのインスタンスに追加してはなりません（MUST NOT）。

Due care has to be exercised when introducing annotations in network management systems in order to avoid interoperability problems and software failures caused by a client that does not understand the annotations' semantics. Generally, it is safe for a server to use annotations in the following cases:

アノテーションのセマンティクスを理解しないクライアントが引き起こす相互運用性の問題やソフトウェアの障害を避けるため、ネットワーク管理システムにアノテーションを導入する際には十分な注意を払う必要があります。一般に、次の場合にはサーバーがアノテーションを使用しても安全です。

  • An annotation is an integral part of a built-in or negotiated protocol capability.
  • An annotation contains auxiliary information that is not critical for protocol operation.
  • The client explicitly asks the server, e.g., via a parameter of a protocol operation request, to include an annotation in the response.
  • アノテーションが、組み込みの、またはネゴシエートされたプロトコル能力の不可欠な一部である場合。
  • アノテーションが、プロトコルの動作にとって重要ではない補助的な情報を含む場合。
  • クライアントが、たとえばプロトコル操作のリクエストのパラメーターを通じて、レスポンスにアノテーションを含めるようにサーバーに明示的に求めた場合。

5. The Encoding of Annotations

5. アノテーションのエンコーディング

XML attributes are a natural choice for encoding metadata in XML instance documents. For JSON [RFC7159], there is no generally established method for encoding metadata. This document thus introduces a special encoding method that is consistent with the JSON encoding of YANG data node instances as defined in [RFC7951].

XMLのインスタンス文書でメタデータをエンコードするには、XML属性が自然な選択肢です。JSON[RFC7159]には、メタデータをエンコードするための一般に確立された方法はありません。そのため、この文書は、[RFC7951]で定義されているYANGデータノードのインスタンスのJSONエンコーディングと一貫性のある、特別なエンコーディング方法を導入します。

5.1. XML Encoding

5.1. XMLエンコーディング

Metadata annotations are added to XML-encoded instances of YANG data nodes as XML attributes according to these rules:

メタデータアノテーションは、次の規則に従って、XMLエンコードされたYANGデータノードのインスタンスにXML属性として追加されます。

  • The local name of the attribute SHALL be the same as the name of the annotation specified in the argument of the corresponding "md:annotation" statement.
  • The namespace of the attribute SHALL be identified by the URI that appears as the argument of the "namespace" statement in the YANG module where the annotation is defined. It is RECOMMENDED that the prefix specified by the "prefix" statement in the same module be used in the qualified name of the attribute.
  • The attribute value SHALL be encoded in the same way as the value of a YANG leaf instance having the same type; see Section 9 of [RFC7950].
  • 属性のローカル名は、対応する"md:annotation"ステートメントの引数で指定されたアノテーションの名前と同じにすることになります（SHALL）。
  • 属性の名前空間は、アノテーションが定義されているYANGモジュールの"namespace"ステートメントの引数として現れるURIで識別することになります（SHALL）。属性の修飾名には、同じモジュールの"prefix"ステートメントで指定されたプレフィックスを使用することが推奨されます（RECOMMENDED）。
  • 属性値は、同じ型を持つYANGのleafインスタンスの値と同じ方法でエンコードすることになります（SHALL）。[RFC7950]のセクション9を参照してください。

For example, the "last-modified" annotation defined in Section 3.1 may be encoded as follows:

たとえば、セクション3.1で定義した"last-modified"アノテーションは、次のようにエンコードできます。

<foo xmlns:elm="http://example.org/example-last-modified"
     elm:last-modified="2015-09-16T10:27:35+02:00">
  ...
</foo>

<foo xmlns:elm="http://example.org/example-last-modified"
     elm:last-modified="2015-09-16T10:27:35+02:00">
  ...
</foo>

5.2. JSON Encoding

5.2. JSONエンコーディング

The JSON metadata encoding defined in this section has the following properties:

このセクションで定義するJSONのメタデータエンコーディングには、次の特性があります。

  1. The encoding of YANG data node instances as defined in [RFC7951] does not change.
  2. Namespaces of metadata annotations are encoded in the same way as namespaces of YANG data node instances; see [RFC7951].
  1. [RFC7951]で定義されているYANGデータノードのインスタンスのエンコーディングは変わりません。
  2. メタデータアノテーションの名前空間は、YANGデータノードのインスタンスの名前空間と同じ方法でエンコードされます。[RFC7951]を参照してください。

5.2.1. Metadata Object and Annotations

5.2.1. メタデータオブジェクトとアノテーション

All metadata annotations assigned to a YANG data node instance are encoded as members (name/value pairs) of a single JSON object, henceforth denoted as the metadata object. The placement and name of this object depend on the type of the data node as specified in the following subsections.

YANGデータノードのインスタンスに割り当てられたすべてのメタデータアノテーションは、単一のJSONオブジェクトのメンバー（名前と値のペア）としてエンコードされます。以降、このオブジェクトをメタデータオブジェクトと呼びます。このオブジェクトの配置と名前は、以降のサブセクションで規定するように、データノードの種類によって異なります。

The name of a metadata annotation (as a member of the metadata object) has the following ABNF syntax [RFC5234], where the production for "identifier" is defined in Section 14 of [RFC7950]:

メタデータアノテーションの（メタデータオブジェクトのメンバーとしての）名前は、次のABNF構文[RFC5234]を持ちます。ここで、"identifier"の生成規則は[RFC7950]のセクション14で定義されています。

annotation-name = identifier ":" identifier

annotation-name = identifier ":" identifier

where the left identifier is the name of the YANG module in which the annotation is defined and the identifier on the right is the name of the annotation specified in the argument of the corresponding "md:annotation" statement.

ここで、左側のidentifierはアノテーションが定義されているYANGモジュールの名前であり、右側のidentifierは対応する"md:annotation"ステートメントの引数で指定されたアノテーションの名前です。

Note that unlike member names of YANG data node instances in JSON encoding (see Section 4 of [RFC7951]), for annotations the explicit namespace identifier (module name) must always be present.

JSONエンコーディングにおけるYANGデータノードのインスタンスのメンバー名（[RFC7951]のセクション4を参照）とは異なり、アノテーションでは明示的な名前空間識別子（モジュール名）が常に存在しなければならないことに注意してください。

The value of a metadata annotation SHALL be encoded in exactly the same way as the value of a YANG leaf node having the same type as the annotation; see Section 6 of [RFC7951].

メタデータアノテーションの値は、そのアノテーションと同じ型を持つYANGのleafノードの値とまったく同じ方法でエンコードすることになります（SHALL）。[RFC7951]のセクション6を参照してください。

5.2.2. Adding Annotations to anydata, container, and list Entries

5.2.2. anydata、container、listエントリーへのアノテーションの追加

For a data node instance that is encoded as a JSON object (i.e., a container, list entry, or anydata node), the metadata object is added as a new member of that object with the name "@".

JSONオブジェクトとしてエンコードされるデータノードのインスタンス（つまり、container、listエントリー、またはanydataノード）の場合、メタデータオブジェクトは、そのオブジェクトの新しいメンバーとして"@"という名前で追加されます。

Examples:

例：

  • "cask" is a container or anydata node:
  • "cask"がcontainerまたはanydataノードである場合：
"cask": {
  "@": {
    "example-last-modified:last-modified":
      "2015-09-16T10:27:35+02:00"
  },
  ...
}

"cask": {
  "@": {
    "example-last-modified:last-modified":
      "2015-09-16T10:27:35+02:00"
  },
  ...
}
  • "seq" is a list whose key is "name"; annotation "last-modified" is added only to the first entry:
  • "seq"がキー"name"を持つlistであり、アノテーション"last-modified"を最初のエントリーにだけ追加する場合：
"seq": [
  {
    "@": {
      "example-last-modified:last-modified":
          "2015-09-16T10:27:35+02:00"
    },
    "name": "one",
    ...
  },
  {
    "name": "two",
    ...
  }
]

"seq": [
  {
    "@": {
      "example-last-modified:last-modified":
          "2015-09-16T10:27:35+02:00"
    },
    "name": "one",
    ...
  },
  {
    "name": "two",
    ...
  }
]

5.2.3. Adding Annotations to anyxml and leaf Instances

5.2.3. anyxmlとleafのインスタンスへのアノテーションの追加

For an anyxml or leaf instance, the metadata object is added as a sibling name/value pair whose name is the symbol "@" concatenated with the name of the leaf or anyxml member that is being annotated. The namespace part (module name) is included if and only if it is in the name of the annotated member.

anyxmlまたはleafのインスタンスの場合、メタデータオブジェクトは、兄弟の名前と値のペアとして追加されます。その名前は、記号"@"に、アノテーションを付けるleafまたはanyxmlのメンバーの名前を連結したものです。名前空間の部分（モジュール名）は、アノテーションを付けるメンバーの名前に含まれている場合に限り、含められます。

Examples:

例：

  • "flag" is a leaf node of the "boolean" type defined in module "foo", and we assume that the namespace name has to be expressed in its JSON encoding:
  • "flag"がモジュール"foo"で定義された"boolean"型のleafノードであり、そのJSONエンコーディングでは名前空間名を表す必要があると仮定した場合：
"foo:flag": true,
"@foo:flag": {
  "example-last-modified:last-modified":
    "2015-09-16T10:27:35+02:00"
}

"foo:flag": true,
"@foo:flag": {
  "example-last-modified:last-modified":
    "2015-09-16T10:27:35+02:00"
}
  • "stuff" is an anyxml node:
  • "stuff"がanyxmlノードである場合：
"stuff": [1, null, "three"],
"@stuff": {
  "example-last-modified:last-modified":
    "2015-09-16T10:27:35+02:00"
}

"stuff": [1, null, "three"],
"@stuff": {
  "example-last-modified:last-modified":
    "2015-09-16T10:27:35+02:00"
}

5.2.4. Adding Annotations to leaf-list Entries

5.2.4. leaf-listエントリーへのアノテーションの追加

For a leaf-list entry, which is represented as a JSON array with values of a primitive type, annotations may be assigned to one or more entries by adding a name/array pair as a sibling of the leaf-list entry, where the name is the symbol "@" concatenated with the name of the leaf-list that is being annotated, and the value is a JSON array whose i-th element is the metadata object with annotations assigned to the i-th entry of the leaf-list entry, or null if the i-th entry has no annotations.

leaf-listエントリーはプリミティブ型の値を持つJSON配列として表現されます。leaf-listエントリーの兄弟として名前と配列のペアを追加することで、1つ以上のエントリーにアノテーションを割り当てることができます。その名前は、記号"@"に、アノテーションを付けるleaf-listの名前を連結したものです。その値はJSON配列であり、そのi番目の要素は、leaf-listエントリーのi番目のエントリーに割り当てられたアノテーションを含むメタデータオブジェクトか、i番目のエントリーにアノテーションがない場合はnullです。

Trailing null values in that array, i.e., those following the last non-null metadata object, MAY be omitted.

その配列の末尾のnull値、つまり最後の非nullのメタデータオブジェクトに続くnull値は、省略してもよいです（MAY）。

For example, in the following leaf-list instance with four entries, the "last-modified" annotation is added to the second and third entries in the following way:

たとえば、次の4つのエントリーを持つleaf-listインスタンスでは、"last-modified"アノテーションが2番目と3番目のエントリーに次のように追加されます。

"bibliomod:folio": [6, 3, 7, 8],

6. Representing Annotations in DSDL Schemas

6. DSDLスキーマでのアノテーションの表現

[RFC6110] defines the standard mapping of YANG data models to Document Schema Definition Languages (DSDL) [ISO.19757-1]. This section specifies the mapping for the extension statement "md:annotation" (Section 7), which enables validation of XML instance documents containing metadata annotations.

[RFC6110]は、YANGデータモデルから文書スキーマ定義言語（DSDL）[ISO.19757-1]への標準のマッピングを定義しています。このセクションでは、拡張ステートメント"md:annotation"（セクション7）のマッピングを規定します。これにより、メタデータアノテーションを含むXMLのインスタンス文書を検証できるようになります。

The first step of the DSDL mapping procedure, i.e., the transformation of the YANG data model to the hybrid schema (see Section 6 of [RFC6110]), is modified as follows:

DSDLマッピング手順の最初のステップ、つまりYANGデータモデルからハイブリッドスキーマへの変換（[RFC6110]のセクション6を参照）は、次のように変更されます。

  1. If the data model contains at least one "md:annotation" statement, then a RELAX NG [ISO.19757-2] named pattern definition MUST be added as a child of the root <rng:grammar> element in the hybrid schema. It is RECOMMENDED to use the name "__yang_metadata__" for this named pattern.
  2. A reference to the named pattern described in item 1 MUST be included as a child of every <rng:element> pattern that corresponds to an anydata, container, leaf, leaf-list, or list data node.

  3. Every metadata annotation definition in the form

    md:annotation ARGUMENT {
  ...
}

    is mapped to the following RELAX NG [ISO.19757-2] pattern:

    <rng:optional>
  <rng:attribute name="PREFIX:ARGUMENT">
    ...
  </rng:attribute>
</rng:optional>

    where PREFIX is the prefix bound to the namespace URI of the YANG module that contains the "md:annotation" statement. The above pattern SHALL be inserted as a child of the named pattern described in item 1.

  4. Substatements of "md:annotation" SHALL be mapped to children of the "rng:attribute" pattern exactly as described in Section 10 of [RFC6110].
  1. データモデルに少なくとも1つの"md:annotation"ステートメントが含まれている場合、ハイブリッドスキーマのルートの<rng:grammar>要素の子として、RELAX NG[ISO.19757-2]の名前付きパターンの定義を追加しなければなりません（MUST）。この名前付きパターンには、"__yang_metadata__"という名前を使用することが推奨されます（RECOMMENDED）。
  2. 項目1で説明した名前付きパターンへの参照を、anydata、container、leaf、leaf-list、またはlistのデータノードに対応するすべての<rng:element>パターンの子として含めなければなりません（MUST）。

  3. 次の形式のすべてのメタデータアノテーションの定義は、

    md:annotation ARGUMENT {
  ...
}

    次のRELAX NG[ISO.19757-2]パターンにマッピングされます。

    <rng:optional>
  <rng:attribute name="PREFIX:ARGUMENT">
    ...
  </rng:attribute>
</rng:optional>

    ここで、PREFIXは、"md:annotation"ステートメントを含むYANGモジュールの名前空間URIに結び付けられたプレフィックスです。上記のパターンは、項目1で説明した名前付きパターンの子として挿入することになります（SHALL）。

  4. "md:annotation"のサブステートメントは、[RFC6110]のセクション10で説明されているとおりに、"rng:attribute"パターンの子にマッピングすることになります（SHALL）。

For example, the named pattern (item 1), when constructed only for the "last-modified" annotation, will have the following definition:

たとえば、"last-modified"アノテーションだけについて構築した場合、名前付きパターン（項目1）は次のような定義になります。

<rng:define name="__yang_metadata__">
  <rng:optional>
    <rng:attribute name="elm:last-modified">
      <rng:ref name="ietf-yang-types__date-and-time"/>
    </rng:attribute>
  </rng:optional>
</rng:define>

<rng:define name="__yang_metadata__">
  <rng:optional>
    <rng:attribute name="elm:last-modified">
      <rng:ref name="ietf-yang-types__date-and-time"/>
    </rng:attribute>
  </rng:optional>
</rng:define>

Every "rng:element" pattern that corresponds to an anydata, container, leaf, list, or leaf-list data node will then contain a reference to the above named pattern; for example:

そして、anydata、container、leaf、list、またはleaf-listのデータノードに対応するすべての"rng:element"パターンは、上記の名前付きパターンへの参照を含むことになります。たとえば、次のとおりです。

<rng:element name="foo:bar">
  <rng:ref name="__yang_metadata__"/>
  ...
</rng:element>

<rng:element name="foo:bar">
  <rng:ref name="__yang_metadata__"/>
  ...
</rng:element>

Note that it is not necessary to use such a reference for "rng:element" patterns corresponding to anyxml data nodes because they already permit any XML attributes to be attached to their instances.

anyxmlデータノードに対応する"rng:element"パターンでは、そのインスタンスにすでに任意のXML属性を付加できるため、このような参照を使用する必要はないことに注意してください。

The second step of the DSDL mapping procedure, i.e., the transformation of the hybrid schema to RELAX NG [ISO.19757-2], Schematron [ISO.19757-3], and Document Semantics Renaming Language (DSRL) [ISO.19757-8] schemas, is unaffected by the inclusion of "md:annotation".

DSDLマッピング手順の2番目のステップ、つまりハイブリッドスキーマからRELAX NG[ISO.19757-2]、Schematron[ISO.19757-3]、文書セマンティクス名前変更言語（DSRL）[ISO.19757-8]の各スキーマへの変換は、"md:annotation"を含めても影響を受けません。

9. Security Considerations

9. セキュリティーに関する考慮事項

This document introduces a mechanism for defining metadata annotations in YANG modules and attaching them to instances of YANG data nodes. By itself, this mechanism represents no security threat. Security implications of a particular annotation defined using this mechanism MUST be duly considered and documented in the annotation's definition.

この文書は、YANGモジュールでメタデータアノテーションを定義し、それをYANGデータノードのインスタンスに付加するためのメカニズムを導入します。このメカニズム自体は、セキュリティー上の脅威をもたらしません。このメカニズムを使用して定義される個々のアノテーションのセキュリティー上の影響は、十分に検討し、そのアノテーションの定義の中で文書化しなければなりません（MUST）。

An annotation SHOULD be subject to the same or stricter access control rules as the data node instance to which the annotation is attached. It is RECOMMENDED that security-sensitive or privacy-sensitive data be modeled as regular YANG data nodes rather than annotations.

アノテーションには、そのアノテーションが付加されるデータノードのインスタンスと同等またはそれより厳しいアクセス制御規則を適用すべきです（SHOULD）。セキュリティー上またはプライバシー上の機密性の高いデータは、アノテーションではなく通常のYANGデータノードとしてモデル化することが推奨されます（RECOMMENDED）。
