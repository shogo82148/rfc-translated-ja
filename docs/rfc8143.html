RFC 8143

Using Transport Layer Security (TLS) with Network News Transfer Protocol (NNTP)

RFC 8143

ネットワークニュース転送プロトコル（NNTP）でのトランスポート層セキュリティー（TLS）の使用

Abstract

概要

This document provides recommendations for improving the security of the Network News Transfer Protocol (NNTP) when using Transport Layer Security (TLS). It modernizes the NNTP usage of TLS to be consistent with TLS best current practices. This document updates RFC 4642.

この文書は、トランスポート層セキュリティー（TLS）を使う際のネットワークニュース転送プロトコル（NNTP）のセキュリティーを向上させるための推奨事項を提供します。この文書は、NNTPでのTLSの使い方を、TLSのベストカレントプラクティスと整合するように現代化します。この文書はRFC 4642を更新します。

1. Introduction

1. はじめに

The Network News Transfer Protocol (NNTP) [RFC3977] has been using Transport Layer Security (TLS) [RFC5246] along with its precursor, Secure Sockets Layer (SSL), since at least the year 2000. The use of TLS in NNTP was formalized in [RFC4642], providing implementation recommendations at the same time. In order to address the evolving threat model on the Internet today, this document provides stronger recommendations regarding that use.

ネットワークニュース転送プロトコル（NNTP）[RFC3977]は、少なくとも2000年以来、トランスポート層セキュリティー（TLS）[RFC5246]を、その前身であるセキュアソケットレイヤー（SSL）とともに使ってきました。NNTPでのTLSの使用は[RFC4642]で正式に規定され、同時に実装上の推奨事項も示されました。今日のインターネットにおける進化する脅威モデルに対処するために、この文書はその使用に関してより強い推奨事項を提供します。

In particular, this document updates [RFC4642] by specifying that NNTP implementations and deployments MUST follow the best current practices documented in [BCP195], which currently consists of RFC 7525 ("Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)"). This includes stronger recommendations regarding SSL/TLS protocol versions, fallback to lower versions, TLS negotiation, TLS-level compression, TLS session resumption, cipher suites, public key lengths, forward secrecy, hostname validation, certificate verification, and other aspects of using TLS with NNTP.

特に、この文書は、NNTPの実装と展開が[BCP195]に文書化されているベストカレントプラクティスに従わなければなりません（MUST）と規定することによって、[RFC4642]を更新します。BCP195は現在、RFC 7525（「Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)」）で構成されています。これには、SSL/TLSのプロトコルバージョン、下位バージョンへのフォールバック、TLSネゴシエーション、TLSレベルの圧縮、TLSセッション再開、暗号スイート、公開鍵の長さ、前方秘匿性、ホスト名の検証、証明書の検証、およびNNTPでTLSを使うことのその他の側面に関する、より強い推奨事項が含まれます。

1.1. Conventions Used in This Document

1.1. この文書で使う規則

Any term not defined in this document has the same meaning as it does in [RFC4642] or the NNTP core specification [RFC3977].

この文書で定義していない用語は、[RFC4642]またはNNTPのコア仕様[RFC3977]と同じ意味を持ちます。

When this document uses the term "implicit TLS", it refers to TLS negotiation immediately upon connection on a separate port.

この文書で「暗黙的TLS（implicit TLS）」という用語を使う場合、それは別のポートで接続した直後に行うTLSネゴシエーションを指します。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 [BCP14].

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、「要求されています（REQUIRED）」、「することになります（SHALL）」、「することはありません（SHALL NOT）」、「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、RFC 2119[BCP14]に記載されているとおりに解釈されるものとします。

2. Updates/Changes to RFC 4642

2. RFC 4642の更新／変更

This document updates [RFC4642] in the following aspects:

この文書は、次の点で[RFC4642]を更新します。

  • NNTP implementations and deployments SHOULD disable TLS-level compression (Section 3.3 of RFC 7525 [BCP195]), thus no longer using TLS as a means to provide data compression (contrary to the Abstract and Section 2.2.2 of [RFC4642]).
  • NNTP implementations and deployments SHOULD prefer implicit TLS, and therefore use strict TLS configuration (Section 3.2 of RFC 7525 [BCP195]). That is to say, they SHOULD use a port dedicated to NNTP over TLS and begin the TLS negotiation immediately upon connection (contrary to a dynamic upgrade from unencrypted to TLS-protected traffic via the use of the STARTTLS command, as Section 1 of [RFC4642] was encouraging). Implicit TLS is the preferred way of using TLS with NNTP for the same reasons, transposed to NNTP, as those given in Appendix A of [MUA-STS]. (Note that [MUA-STS] and [RFC4642] have one author in common.)
  • NNTP implementations and deployments MUST NOT negotiate RC4 cipher suites ([RFC7465]); this is contrary to Section 5 of [RFC4642], which required them to implement the TLS_RSA_WITH_RC4_128_MD5 cipher suite so as to ensure that any two NNTP-compliant implementations can be configured to interoperate. This document removes that requirement, so that NNTP client and server implementations follow the recommendations given in Sections 4.2 and 4.2.1 of RFC 7525 [BCP195] instead. The mandatory-to-implement cipher suite or cipher suites depend on the TLS protocol version. For instance, when TLS 1.2 is used, the TLS_RSA_WITH_AES_128_CBC_SHA cipher suite MUST be implemented (Section 9 of [RFC5246]).
  • All NNTP clients and any NNTP server that is known by multiple names MUST support the Server Name Indication (SNI) extension defined in Section 3 of [RFC6066], in conformance with Section 3.6 of RFC 7525 [BCP195]. It was only a "SHOULD" in Section 2.2.2 of [RFC4642].
  • NNTP implementations and deployments MUST follow the rules and guidelines defined in [RFC6125] and [RFC5280] for hostname validation and certificate verification. Part of Section 5 of [RFC4642] is, therefore, rationalized in favor of following those two documents.
  • NNTPの実装と展開は、TLSレベルの圧縮を無効にすべきです（SHOULD）（RFC 7525[BCP195]のセクション3.3）。したがって、（RFC 4642の要旨と[RFC4642]のセクション2.2.2とは異なり）データ圧縮を提供する手段としてTLSを使うことはもはやありません。
  • NNTPの実装と展開は、暗黙的TLSを優先し、したがって厳格なTLS構成を使うべきです（SHOULD）（RFC 7525[BCP195]のセクション3.2）。つまり、NNTPの実装と展開は、NNTP over TLS専用のポートを使い、接続した直後にTLSネゴシエーションを開始すべきです（SHOULD）（[RFC4642]のセクション1が推奨していた、STARTTLSコマンドを使って暗号化されていないトラフィックからTLSで保護されたトラフィックへ動的にアップグレードする方法とは異なります）。暗黙的TLSは、NNTPでTLSを使う方法として優先されるものです。その理由は、[MUA-STS]の付録Aで示されている理由をNNTPに置き換えたものと同じです。（[MUA-STS]と[RFC4642]には共通の著者が1人いることに注意してください。）
  • NNTPの実装と展開は、RC4暗号スイート（[RFC7465]）をネゴシエートしてはなりません（MUST NOT）。これは[RFC4642]のセクション5とは異なります。同セクションは、NNTPに準拠した任意の2つの実装が相互運用するように構成できることを保証するために、TLS_RSA_WITH_RC4_128_MD5暗号スイートを実装することを要求していました。この文書はその要件を削除し、NNTPのクライアントとサーバーの実装が代わりにRFC 7525[BCP195]のセクション4.2と4.2.1で示されている推奨事項に従うようにします。実装必須の暗号スイート（1つまたは複数）は、TLSプロトコルのバージョンに依存します。たとえば、TLS 1.2を使う場合は、TLS_RSA_WITH_AES_128_CBC_SHA暗号スイートを実装しなければなりません（MUST）（[RFC5246]のセクション9）。
  • すべてのNNTPクライアントと、複数の名前で知られているすべてのNNTPサーバーは、RFC 7525[BCP195]のセクション3.6に準拠して、[RFC6066]のセクション3で定義されているServer Name Indication（SNI）拡張をサポートしなければなりません（MUST）。[RFC4642]のセクション2.2.2では、これは「すべきです（SHOULD）」にすぎませんでした。
  • NNTPの実装と展開は、ホスト名の検証と証明書の検証について、[RFC6125]と[RFC5280]で定義されている規則とガイドラインに従わなければなりません（MUST）。したがって、[RFC4642]のセクション5の一部は、これら2つの文書に従うように整理されます。

Appendix A of this document gives detailed changes with regard to the wording of [RFC4642].

この文書の付録Aでは、[RFC4642]の文言に関する詳細な変更を示します。

3. Recommendations

3. 推奨事項

The best current practices documented in [BCP195] apply here. Therefore, NNTP implementations and deployments compliant with this document are REQUIRED to comply with [BCP195] as well.

[BCP195]に文書化されているベストカレントプラクティスは、ここでも適用されます。したがって、この文書に準拠するNNTPの実装と展開は、[BCP195]にも準拠することが要求されています（REQUIRED）。

Instead of repeating those recommendations here, this document mostly provides supplementary information regarding secure implementation and deployment of NNTP technologies.

この文書は、それらの推奨事項をここで繰り返す代わりに、主にNNTP技術の安全な実装と展開に関する補足情報を提供します。

3.1. Compression

3.1. 圧縮

NNTP supports the use of the COMPRESS command, defined in Section 2.2 of [RFC8054], to compress data between an NNTP client and server. Although this NNTP extension might have slightly stronger security properties than TLS-level compression [RFC3749] (since NNTP compression can be activated after authentication has completed, thus reducing the chances that authentication credentials can be leaked via, for instance, a Compression Ratio Info-leak Made Easy (CRIME) attack, as described in Section 2.6 of [CRIME]), this document neither encourages nor discourages the use of the NNTP COMPRESS extension.

NNTPは、NNTPのクライアントとサーバーの間のデータを圧縮するために、[RFC8054]のセクション2.2で定義されているCOMPRESSコマンドの使用をサポートしています。このNNTP拡張は、TLSレベルの圧縮[RFC3749]よりもセキュリティー特性がわずかに強いかもしれません（NNTPの圧縮は認証が完了した後に有効にできるので、たとえば[CRIME]のセクション2.6で説明されているCompression Ratio Info-leak Made Easy（CRIME）攻撃によって認証クレデンシャルが漏洩する可能性が減ります）。それでも、この文書は、NNTPのCOMPRESS拡張の使用を推奨も非推奨もしません。

3.2. Protocol Versions and Security Preferences

3.2. プロトコルバージョンとセキュリティーの設定

NNTP implementations of news servers are encouraged to support options to configure 1) the minimal TLS protocol version to accept and 2) which cipher suites, signature algorithms, or groups (like elliptic curves) to use for incoming connections. Additional options can naturally also be supported. The goal is to enable administrators of news servers to easily and quickly strengthen security, if needed (for instance, by rejecting cipher suites considered unsafe with regard to local policy).

ニュースサーバーのNNTP実装は、受信する接続に対して、1）受け入れるTLSプロトコルの最小バージョンと、2）使用する暗号スイート、署名アルゴリズム、またはグループ（楕円曲線など）を構成するオプションをサポートすることが推奨されます。当然、追加のオプションもサポートできます。その目的は、必要な場合に（たとえば、ローカルポリシーに照らして安全でないとみなされる暗号スイートを拒否することによって）、ニュースサーバーの管理者がセキュリティーを簡単かつ迅速に強化できるようにすることです。

News clients may also support similar options, either configurable by the user or enforced by the news reader.

ニュースクライアントも、ユーザーが構成できるか、ニュースリーダーによって強制される、同様のオプションをサポートしてもかまいません。

3.3. Server Name Indication

3.3. サーバー名表示（Server Name Indication）

The TLS extension for Server Name Indication (SNI) defined in Section 3 of [RFC6066] MUST be implemented by all news clients. It also MUST be implemented by any news server that is known by multiple names. (Otherwise, it is not possible for a server with several hostnames to present the correct certificate to the client.)

[RFC6066]のセクション3で定義されているServer Name Indication（SNI）のためのTLS拡張は、すべてのニュースクライアントが実装しなければなりません（MUST）。また、複数の名前で知られているすべてのニュースサーバーも、それを実装しなければなりません（MUST）。（そうしないと、複数のホスト名を持つサーバーが、クライアントに正しい証明書を提示できません。）

3.4. Prevention of SSL Stripping

3.4. SSLストリッピングの防止

In order to help prevent SSL Stripping attacks (Section 2.1 of [RFC7457]), NNTP implementations and deployments MUST follow the recommendations provided in Section 3.2 of RFC 7525 [BCP195]. Notably, in case implicit TLS is not used, news clients SHOULD attempt to negotiate TLS even if the server does not advertise the STARTTLS capability label in response to the CAPABILITIES command (Section 2.1 of [RFC4642]).

SSLストリッピング攻撃（[RFC7457]のセクション2.1）の防止に役立てるために、NNTPの実装と展開は、RFC 7525[BCP195]のセクション3.2で示されている推奨事項に従わなければなりません（MUST）。特に、暗黙的TLSを使わない場合、ニュースクライアントは、CAPABILITIESコマンドへのレスポンスでサーバーがSTARTTLS能力ラベルを広告していなくても、TLSのネゴシエーションを試みるべきです（SHOULD）（[RFC4642]のセクション2.1）。

3.5. Authenticated Connections

3.5. 認証された接続

[RFC4642] already provides recommendations and requirements for certificate validation in the context of checking the client or the server's identity. Those requirements are strengthened by Appendix A.5 of this document.

[RFC4642]はすでに、クライアントまたはサーバーの識別情報を確認するという文脈での証明書の検証について、推奨事項と要件を提供しています。それらの要件は、この文書の付録A.5によって強化されます。

Wherever possible, it is best to prefer certificate-based authentication (along with Simple Authentication and Security Layer (SASL) [RFC4422]), and ensure that:

可能な限り、（簡易認証セキュリティー層（SASL）[RFC4422]とともに）証明書ベースの認証を優先し、次のことを確実にするのが最善です。

  • Clients authenticate servers.
  • Servers authenticate clients.
  • Servers authenticate other peer servers.
  • クライアントがサーバーを認証すること。
  • サーバーがクライアントを認証すること。
  • サーバーが他のピアサーバーを認証すること。

This document does not mandate certificate-based authentication, although such authentication is strongly preferred. As mentioned in Section 2.2.2 of [RFC4642], the AUTHINFO SASL command (Section 2.4 of [RFC4643]) with the EXTERNAL mechanism (Appendix A of [RFC4422]) MAY be used to authenticate a client once its TLS credentials have been successfully exchanged.

この文書は証明書ベースの認証を義務付けませんが、そのような認証が強く望まれます。[RFC4642]のセクション2.2.2で述べられているように、クライアントのTLSクレデンシャルの交換が成功したら、EXTERNALメカニズム（[RFC4422]の付録A）を指定したAUTHINFO SASLコマンド（[RFC4643]のセクション2.4）を使って、そのクライアントを認証してもよいです（MAY）。

Given the pervasiveness of eavesdropping [RFC7258], even an encrypted but unauthenticated connection might be better than an unencrypted connection (this is similar to the "better-than-nothing security" approach for IPsec [RFC5386], and in accordance with opportunistic security principles [RFC7435]). Encrypted but unauthenticated connections include connections negotiated using anonymous Diffie-Hellman mechanisms or using self-signed certificates, among others.

盗聴が広く行われていることを考えると[RFC7258]、暗号化されているが認証されていない接続であっても、暗号化されていない接続よりはましかもしれません（これは、IPsecの「何もないよりはましなセキュリティー（better-than-nothing security）」というアプローチ[RFC5386]と同様であり、日和見的セキュリティーの原則[RFC7435]にも合致します）。暗号化されているが認証されていない接続には、とりわけ、匿名Diffie-Hellmanメカニズムを使ってネゴシエートされた接続や、自己署名証明書を使ってネゴシエートされた接続が含まれます。

Note: when an NNTP server receives a Netnews article, it MAY add a <diag-match> (Section 3.1.5 of [RFC5536]), which appears as "!!" in the Path header field of that article, to indicate that it verified the identity of the client or peer server. This document encourages the construction of such Path header fields, as described in Section 3.2.1 of [RFC5537].

注: NNTPサーバーは、Netnews記事を受信したとき、クライアントまたはピアサーバーの識別情報を検証したことを示すために、その記事のPathヘッダーフィールドに「!!」として現れる<diag-match>（[RFC5536]のセクション3.1.5）を追加してもよいです（MAY）。この文書は、[RFC5537]のセクション3.2.1で説明されているように、そのようなPathヘッダーフィールドを構築することを推奨します。

3.6. Human Factors

3.6. ヒューマンファクター

NNTP clients SHOULD provide ways for end users (and NNTP servers SHOULD provide ways for administrators) to complete at least the following tasks:

NNTPクライアントは、エンドユーザーが少なくとも次のタスクを完了できる方法を提供すべきです（SHOULD）（また、NNTPサーバーは、管理者がそれらを完了できる方法を提供すべきです（SHOULD））。

  • Determine if a given incoming or outgoing connection is encrypted using a security layer (either using TLS or an SASL mechanism that negotiates a security layer).
  • Be warned if the version of TLS used for encryption of a given stream is not secure enough.
  • If authenticated encryption is used, determine how the connection was authenticated or verified.
  • Be warned if the certificate offered by an NNTP server cannot be verified.
  • Be warned if the cipher suite used to encrypt a connection is not secure enough.
  • Be warned if the certificate changes for a given server.
  • When a security layer is not already in place, be warned if a given server stops advertising the STARTTLS capability label in response to the CAPABILITIES command (Section 2.1 of [RFC4642]), whereas it advertised the STARTTLS capability label during any previous connection within a (possibly configurable) time frame. (Otherwise, a human might not see the warning the first time, and the warning would disappear immediately after that.)
  • Be warned if a failure response to the STARTTLS command is received from the server, whereas the STARTTLS capability label was advertised.
  • 特定の受信または送信の接続が、セキュリティー層（TLS、またはセキュリティー層をネゴシエートするSASLメカニズムのいずれかを使ったもの）を使って暗号化されているかどうかを判断すること。
  • 特定のストリームの暗号化に使われるTLSのバージョンが十分に安全でない場合に、警告を受けること。
  • 認証付き暗号化が使われている場合に、その接続がどのように認証または検証されたかを判断すること。
  • NNTPサーバーが提示した証明書を検証できない場合に、警告を受けること。
  • 接続の暗号化に使われる暗号スイートが十分に安全でない場合に、警告を受けること。
  • 特定のサーバーの証明書が変わった場合に、警告を受けること。
  • セキュリティー層がまだ確立されていないときに、特定のサーバーが、（構成可能な場合もある）一定期間内の以前のいずれかの接続ではSTARTTLS能力ラベルを広告していたにもかかわらず、CAPABILITIESコマンドへのレスポンスでSTARTTLS能力ラベルを広告しなくなった場合（[RFC4642]のセクション2.1）に、警告を受けること。（そうしないと、人間は最初のときに警告を見落とすかもしれず、その後すぐに警告が消えてしまうでしょう。）
  • STARTTLS能力ラベルが広告されていたにもかかわらず、STARTTLSコマンドに対する失敗レスポンスをサーバーから受信した場合に、警告を受けること。

Note that the last two tasks cannot occur when implicit TLS is used, and that the penultimate task helps prevent an attack known as "SSL Stripping" (Section 2.1 of [RFC7457]).

最後の2つのタスクは暗黙的TLSを使う場合には発生しえないこと、および最後から2番目のタスクは「SSLストリッピング（SSL Stripping）」として知られる攻撃（[RFC7457]のセクション2.1）の防止に役立つことに注意してください。

4. Security Considerations

4. セキュリティーに関する考慮事項

Beyond the security considerations already described in [RFC4642], [RFC6125], and [BCP195], the following caveat is worth mentioning when not using implicit TLS: NNTP servers need to ensure that they are not vulnerable to the STARTTLS command injection vulnerability (Section 2.2 of [RFC7457]). Though this command MUST NOT be pipelined, an attacker could pipeline it. Therefore, NNTP servers MUST discard any NNTP command received between the use of STARTTLS and the end of TLS negotiation.

[RFC4642]、[RFC6125]、および[BCP195]ですでに説明されているセキュリティーに関する考慮事項に加えて、暗黙的TLSを使わない場合には、次の注意点に言及する価値があります。NNTPサーバーは、STARTTLSコマンドインジェクションの脆弱性（[RFC7457]のセクション2.2）に対して脆弱でないことを確実にする必要があります。このコマンドはパイプライン化してはなりません（MUST NOT）が、攻撃者はそれをパイプライン化できます。したがって、NNTPサーバーは、STARTTLSの使用からTLSネゴシエーションの終了までの間に受信したNNTPコマンドをすべて破棄しなければなりません（MUST）。

Appendix A. Detailed Changes to RFC 4642

付録A. RFC 4642に対する詳細な変更

This section lists the detailed changes that this document applies to [RFC4642].

このセクションでは、この文書が[RFC4642]に適用する詳細な変更を列挙します。

A.1. Related to TLS-Level Compression

A.1. TLSレベルの圧縮に関するもの

The second sentence in the Abstract in [RFC4642] is replaced with the following text:

[RFC4642]の要旨の2番目の文は、次のテキストで置き換えられます。

The primary goal is to provide encryption for single-link confidentiality purposes, but data integrity, and (optional) certificate-based peer entity authentication are also possible.

主な目的は、単一リンクの機密性のための暗号化を提供することですが、データの完全性と、（省略可能な）証明書ベースのピアエンティティー認証も可能です。

The second sentence of the first paragraph in Section 2.2.2 of [RFC4642] is replaced with the following text:

[RFC4642]のセクション2.2.2の最初の段落の2番目の文は、次のテキストで置き換えられます。

The STARTTLS command is usually used to initiate session security, although it can also be used for client and/or server certificate authentication.

STARTTLSコマンドは通常、セッションのセキュリティーを開始するために使われますが、クライアントとサーバーの一方または両方の証明書認証にも使えます。

A.2. Related to Implicit TLS

A.2. 暗黙的TLSに関するもの

The third and fourth paragraphs in Section 1 of [RFC4642] are replaced with the following text:

[RFC4642]のセクション1の3番目と4番目の段落は、次のテキストで置き換えられます。

TCP port 563 is dedicated to NNTP over TLS, and registered in the IANA Service Name and Transport Protocol Port Number Registry for that usage. NNTP implementations using TCP port 563 begin the TLS negotiation immediately upon connection and then continue with the initial steps of an NNTP session. This immediate TLS negotiation on a separate port (referred to in this document as "implicit TLS") is the preferred way of using TLS with NNTP.

If a host wishes to offer separate servers for transit and reading clients (Section 3.4.1 of [NNTP]), TCP port 563 SHOULD be used for implicit TLS with the reading server, and an unused port of its choice different than TCP port 433 SHOULD be used for implicit TLS with the transit server. The ports used for implicit TLS should be clearly communicated to the clients, and specifically that no plaintext communication occurs before the TLS session is negotiated.

As some existing implementations negotiate TLS via a dynamic upgrade from unencrypted to TLS-protected traffic during an NNTP session on well-known TCP ports 119 or 433, this specification formalizes the STARTTLS command in use for that purpose. However, as already mentioned above, implementations SHOULD use implicit TLS on a separate port.

Note: a common alternative to protect NNTP exchanges with transit servers that do not implement TLS is the use of IPsec with encryption [RFC4301].

TCPポート563はNNTP over TLS専用であり、その用途のためにIANAのService Name and Transport Protocol Port Number Registryに登録されています。TCPポート563を使うNNTP実装は、接続した直後にTLSネゴシエーションを開始し、その後NNTPセッションの最初の手順に進みます。別のポートでのこの即時のTLSネゴシエーション（この文書では「暗黙的TLS（implicit TLS）」と呼びます）は、NNTPでTLSを使う方法として優先されるものです。

ホストが、トランジット用のクライアントと閲覧用のクライアントに別々のサーバーを提供したい場合（[NNTP]のセクション3.4.1）、閲覧用サーバーでの暗黙的TLSにはTCPポート563を使うべきです（SHOULD）。また、トランジット用サーバーでの暗黙的TLSには、TCPポート433以外の、ホストが選択した未使用のポートを使うべきです（SHOULD）。暗黙的TLSに使われるポートは、クライアントに明確に伝えられるべきです。特に、TLSセッションがネゴシエートされる前に平文の通信が行われないことも明確に伝えられるべきです。

既存の実装の中には、ウェルノウンTCPポート119または433でのNNTPセッション中に、暗号化されていないトラフィックからTLSで保護されたトラフィックへの動的なアップグレードによってTLSをネゴシエートするものがあるので、この仕様は、その目的のために使われているSTARTTLSコマンドを正式に規定します。ただし、すでに上で述べたように、実装は別のポートで暗黙的TLSを使うべきです（SHOULD）。

注: TLSを実装していないトランジットサーバーとのNNTPのやり取りを保護するための一般的な代替手段は、暗号化を伴うIPsec[RFC4301]の使用です。

An additional informative reference to [RFC4301] is, therefore, added to Section 7.2 of [RFC4642].

したがって、[RFC4301]への参考文献としての参照が、[RFC4642]のセクション7.2に追加されます。

A.3. Related to RC4 Cipher Suites

A.3. RC4暗号スイートに関するもの

The third paragraph in Section 5 of [RFC4642] is removed. Consequently, NNTP no longer requires the implementation of any cipher suites, other than those prescribed by TLS (Section 9 of [RFC5246]), and Sections 4.2 and 4.2.1 of RFC 7525 [BCP195].

[RFC4642]のセクション5の3番目の段落は削除されます。その結果、NNTPは、TLSが規定するもの（[RFC5246]のセクション9）とRFC 7525[BCP195]のセクション4.2と4.2.1が規定するもの以外の暗号スイートの実装を、もはや要求しません。

A.4. Related to Server Name Indication

A.4. Server Name Indicationに関するもの

The last two sentences of the seventh paragraph in Section 2.2.2 of [RFC4642] are removed. Section 3.6 of RFC 7525 [BCP195] applies.

[RFC4642]のセクション2.2.2の7番目の段落の最後の2つの文は削除されます。RFC 7525[BCP195]のセクション3.6が適用されます。

A.5. Related to Certificate Verification

A.5. 証明書の検証に関するもの

The text between "During the TLS negotiation" and "identity bindings)." in Section 5 of [RFC4642] is replaced with the following text:

[RFC4642]のセクション5の「During the TLS negotiation」から「identity bindings).」までのテキストは、次のテキストで置き換えられます。

During TLS negotiation, the client MUST verify the server's identity in order to prevent man-in-the-middle attacks. The client MUST follow the rules and guidelines defined in [RFC6125], where the reference identifier MUST be the server hostname that the client used to open the connection, and that is also specified in the TLS "server_name" extension [RFC6066]. The following NNTP-specific consideration applies: DNS domain names in server certificates MAY contain the wildcard character "*" as the complete leftmost label within the identifier.

If the match fails, the client MUST follow the recommendations in Section 6.6 of [RFC6125] regarding certificate pinning and fallback.

Beyond server identity checking, clients also MUST apply the procedures specified in [RFC5280] for general certificate validation (e.g., certificate integrity, signing, and path validation).

TLSネゴシエーションの間、クライアントは、中間者攻撃を防ぐために、サーバーの識別情報を検証しなければなりません（MUST）。クライアントは[RFC6125]で定義されている規則とガイドラインに従わなければなりません（MUST）。ここで、参照識別子は、クライアントが接続を開くために使ったサーバーのホスト名であり、かつTLSの「server_name」拡張[RFC6066]でも指定されているものでなければなりません（MUST）。NNTPに固有の次の考慮事項が適用されます。サーバー証明書内のDNSドメイン名は、識別子内の最も左のラベル全体としてワイルドカード文字「*」を含んでもよいです（MAY）。

照合に失敗した場合、クライアントは、証明書ピンニングとフォールバックに関する[RFC6125]のセクション6.6の推奨事項に従わなければなりません（MUST）。

サーバーの識別情報の確認に加えて、クライアントは、一般的な証明書の検証（たとえば、証明書の完全性、署名、およびパスの検証）について[RFC5280]で規定されている手順も適用しなければなりません（MUST）。

Additional normative references to [RFC5280] (replacing [PKI-CERT], which it obsoletes), [RFC6066], and [RFC6125] are, therefore, added to Section 7.1 of [RFC4642].

したがって、[RFC5280]（これが廃止する[PKI-CERT]を置き換えるもの）、[RFC6066]、および[RFC6125]への引用規格としての参照が、[RFC4642]のセクション7.1に追加されます。

A.6. Related to Other Obsolete Wording

A.6. その他の古くなった文言に関するもの

The first two sentences of the seventh paragraph in Section 2.2.2 of [RFC4642] are removed. There is no special requirement for NNTP with regard to TLS Client Hello messages. Section 7.4.1.2 and Appendix E of [RFC5246] apply.

[RFC4642]のセクション2.2.2の7番目の段落の最初の2つの文は削除されます。TLSのClient Helloメッセージに関して、NNTPに特別な要件はありません。[RFC5246]のセクション7.4.1.2と付録Eが適用されます。
