RFC 117

Some Comments on the Official Protocol

RFC 117

公式プロトコルに関するいくつかのコメント

Abstract

概要

Document No. 1 and NWG/RFC No. 107 gave a very detailed description of connection establishment, connection termination and flow control over the Network. Throughout the implementation of the NCP it was discovered that the handling of ERR control commands, messages of types other than 0 (regular), 4 (nop), and 5 (rfnm), and messages with the From-imp bit on are not well discussed so that problems arise when they occur.

Document No. 1とNWG/RFC No. 107は、ネットワーク上のコネクションの確立、コネクションの終了、フロー制御について非常に詳しく説明しました。NCPの実装を通じて、ERR制御コマンド、種類が0（通常）、4（nop）、5（rfnm）以外のメッセージ、From-impビットがオンのメッセージの扱いが十分に議論されておらず、それらが発生したときに問題が生じることがわかりました。

The Protocol is not complete if the above situations are not handled clearly, and the Host-Host Protocol Glitch Cleaning Committee should take this into consideration. In this document, experience with these unfavorable situations and suggestions for handling are given:

上記の状況が明確に扱われていなければプロトコルは完全ではなく、Host-Hostプロトコル不具合整理委員会（Host-Host Protocol Glitch Cleaning Committee）はこれを考慮に入れるべきです。この文書では、これらの好ましくない状況での経験と、その扱い方の提案を示します。

1. ERR Control Commands

1. ERR制御コマンド

In Document No. 1, the following error conditions are described:

Document No. 1では、次のエラー条件が説明されています。

  1. Illegal Op. code.
  2. End of message encountered before all expected parameters.
  3. Bad socket polarity within commands.
  4. Link number not in the range of 0 <= L < 32.
  5. A request (other than RTS/STR) on a non-existent socket.
  6. A request (ALL, GVB, RET, INR, INS) on a non-existent link number.
  7. Transmit over non-existent link number.
  1. 不正なオペコード。
  2. 予期されるすべてのパラメーターの前にメッセージの終わりに達した。
  3. コマンド内のソケットの極性が誤っている。
  4. リンク番号が0 <= L < 32の範囲にない。
  5. 存在しないソケットに対する（RTS/STR以外の）要求。
  6. 存在しないリンク番号に対する要求（ALL、GVB、RET、INR、INS）。
  7. 存在しないリンク番号での送信。

Other error conditions are:

その他のエラー条件は次のとおりです。

  1. A request (GVB, RET, INR, INS) on an existent link, but connection is not established.
  2. Transmit over an existent link, but connection is not established.
  3. ALL or GVB on a send connection.
  4. RET on a receive connection.
  5. An attempt to send more than the allocated number of bits or messages.
  6. ECO, ERP, ERR commands do not have the defined number of bits of data.
  1. 存在するリンクに対する要求（GVB、RET、INR、INS）だが、コネクションが確立されていない。
  2. 存在するリンクでの送信だが、コネクションが確立されていない。
  3. 送信コネクションに対するALLまたはGVB。
  4. 受信コネクションに対するRET。
  5. 割り当てられたビット数またはメッセージ数を超えて送信しようとした。
  6. ECO、ERP、ERRコマンドのデータが定義されたビット数ではない。

In Document No. 1, each site is supposed to document the information on their ERR command. No one has done that so far, and the main reason is we are not sure of what information is important. In NWG/RFC No. 107, the text portion of the ERR Commands is decided to have a fixed length of 80 bits because 80 bits is long enough to hold the longest non-ERR command. In some of the above error conditions, more information than the command itself is desirable. It was noted that these error conditions arise very often in the experimental stage of the NCP. If every NCP is operating properly, none of them should ever occur. The ERR commands are therefore, an excellent debugging tool for the protocol. So it is desirable to define a set of possible error conditions, and for each condition, define a set of arguments in the corresponding ERR command so that enough information is given to tell what's wrong. The suggested arguments for each situation (a - m) are listed below:

Document No. 1では、各サイトが自身のERRコマンドの情報を文書化することになっています。これまで誰もそれを行っておらず、その主な理由は、どの情報が重要なのかがわからないことです。NWG/RFC No. 107では、ERRコマンドのテキスト部分は、ERR以外の最長のコマンドを保持するのに十分な長さである80ビットの固定長にすると決められました。上記のエラー条件のいくつかでは、コマンドそのもの以上の情報があることが望まれます。これらのエラー条件は、NCPの実験段階で非常に頻繁に発生することがわかりました。すべてのNCPが正しく動作していれば、どれも決して発生しないはずです。したがって、ERRコマンドはプロトコルの優れたデバッグツールです。そこで、起こりうるエラー条件の集合を定義し、それぞれの条件について、何が悪いのかを伝えるのに十分な情報が得られるように、対応するERRコマンドの引数の集合を定義することが望まれます。それぞれの状況（a〜m）に対して提案する引数を次に挙げます。

a.
  1. Op. code in error.
  2. Part of message following op. code (A maximum of 72 bits).
b, c, d, e, f.
  1. The command in error.
g.
  1. Link number,
  2. Beginning of message (A maximum of 72 bits),
h.
  1. Command in error.
  2. Socket numbers for the connection.
  3. Status of the connection.
i.
  1. Link number,
  2. Beginning of message (A maximum of 72 bits),
  3. Socket numbers for the connection.
  4. Status of the connection.
j, k.
  1. Command in error.
  2. Socket numbers for the connection.
l.
  1. Link number.
  2. Beginning of message (A maximum of 72 bits).
  3. Number of bits sent.
  4. Number of bits allocated.
  5. Number of messages allocated.
m.
  1. The Command in error.
a.
  1. 誤りのあるオペコード。
  2. オペコードに続くメッセージの部分（最大72ビット）。
b, c, d, e, f.
  1. 誤りのあるコマンド。
g.
  1. リンク番号、
  2. メッセージの先頭（最大72ビット）、
h.
  1. 誤りのあるコマンド。
  2. コネクションのソケット番号。
  3. コネクションの状態。
i.
  1. リンク番号、
  2. メッセージの先頭（最大72ビット）、
  3. コネクションのソケット番号。
  4. コネクションの状態。
j, k.
  1. 誤りのあるコマンド。
  2. コネクションのソケット番号。
l.
  1. リンク番号。
  2. メッセージの先頭（最大72ビット）。
  3. 送信したビット数。
  4. 割り当てられたビット数。
  5. 割り当てられたメッセージ数。
m.
  1. 誤りのあるコマンド。

Each of the ERR commands should have a special error code (8 bits) to tell the error type, an 80-bits field to store the command in error, and additional fields for socket numbers and other information.

各ERRコマンドには、エラーの種類を伝える特別なエラーコード（8ビット）、誤りのあるコマンドを格納する80ビットのフィールド、ソケット番号やその他の情報のための追加のフィールドを持たせるべきです。

2. Imp-to-host messages of types other than 0, 4, and 5.

2. 種類が0、4、5以外のImpからホストへのメッセージ

From the BBN report 1822, the following message types will cause difficulty in the implementation of the Protocol.

BBN report 1822によると、次の種類のメッセージはプロトコルの実装を難しくします。

  1. Type 2 - Imp going down.
  2. Type 7 - Destination host or imp dead.
  3. Type 9 - Incomplete transmission.
  1. Type 2 - Impがダウンしようとしている。
  2. Type 7 - 宛先のホストまたはimpが停止している。
  3. Type 9 - 送信が完了しなかった。

It was discovered that on sending a message to a site whose imp or host is not running, a Type 7 or Type 9 message is returned. This can happen in two situations:

impまたはホストが動作していないサイトにメッセージを送信すると、Type 7またはType 9のメッセージが返されることがわかりました。これは2つの状況で起こりえます。

  1. The foreign host or imp is not up at all.
  2. Some connections have been established, and the foreign host or imp goes down.
  1. 外部のホストまたはimpがまったく起動していない。
  2. いくつかのコネクションが確立された後で、外部のホストまたはimpがダウンした。

The first situation does not cause much problem because the NCP has no entry in its table corresponding to this site.

1つ目の状況は、NCPのテーブルにこのサイトに対応するエントリーがないので、それほど問題になりません。

The second situation is more complicated, because if the table entries for the connections to the dead host are not cleared, by the time this host comes up again, the table entries still exist and the information will be very misleading. One suggestion to solve this problem is:

2つ目の状況はより複雑です。停止したホストへのコネクションのテーブルエントリーを消去しないと、このホストが再び起動したときにもテーブルエントリーが残っていて、その情報が非常に誤解を招くものになるからです。この問題を解決するための提案の1つは次のとおりです。

  1. Whenever a NCP comes up, it send a RESET Control Command to every other site.
  2. Associated with each site there is a bit called the up-bit. If a RESET-reply command is received from some site, the corresponding up-bit is set to 1. Race condition can be avoided by ignoring all messages from sites which have not returned the RESET-reply command.
  3. Messages can only be sent to sites with the up-bit on.
  4. If a RESET control command is received, the Table entries corresponding to the site are cleared, a RESET-reply is immediately returned, and the up-bit for the site is set.
  5. The up-bit is reset to 0 when a Type 7 or Type 9 message is received from a particular site.
  1. NCPは、起動するたびに、他のすべてのサイトにRESET制御コマンドを送信します。
  2. 各サイトにはup-bitと呼ばれるビットが対応付けられています。あるサイトからRESET-replyコマンドを受信すると、対応するup-bitを1に設定します。RESET-replyコマンドを返していないサイトからのメッセージをすべて無視することで、競合状態を避けられます。
  3. メッセージは、up-bitがオンのサイトにだけ送信できます。
  4. RESET制御コマンドを受信すると、そのサイトに対応するテーブルエントリーを消去し、すぐにRESET-replyを返して、そのサイトのup-bitを設定します。
  5. 特定のサイトからType 7またはType 9のメッセージを受信すると、up-bitを0にリセットします。

The above solution will handle the Type 2 messages also. When a host receives a Type 2 message, there is no way for it to tell the other NCP's that its imp is going down. Subsequent messages to this host will return a Type 7 or 9 message. The solution above will then come into effect.

上記の解決策はType 2のメッセージも扱えます。ホストがType 2のメッセージを受信したとき、自身のimpがダウンしようとしていることを他のNCPに伝える方法はありません。その後このホストに送られたメッセージには、Type 7または9のメッセージが返されます。そこで上記の解決策が機能します。

With the introduction of the RESET and RESET-reply Control command, the ECO and ERP control command are no longer important and should be removed.

RESETとRESET-replyの制御コマンドを導入すれば、ECOとERPの制御コマンドはもはや重要ではなくなるので、削除すべきです。

3. Messages with the From-imp bit on.

3. From-impビットがオンのメッセージ

These kinds of messages are not discussed at all. Some statistical measurements have been made on messages with the From-imp bit on. We should classify what these messages represent.

この種のメッセージはまったく議論されていません。From-impビットがオンのメッセージについて、いくつかの統計的な測定が行われています。これらのメッセージが何を表すのかを分類すべきです。
