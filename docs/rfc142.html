RFC 142

Time-out Mechanism in the Host-Host Protocol

RFC 142

Host-Hostプロトコルにおけるタイムアウトの仕組み

Abstract

概要

On sending a message to a foreign site, the following situations can occur:

外部のサイトにメッセージを送信すると、次のような状況が起こりえます。

  1. Destination IMP down - Type 7 message is returned
  2. Destination IMP up but destination IMP-HOST interface is down - Type 7 message is returned.
  3. Destination IMP and IMP-HOST interface up, but IMP-HOST interface is not taking messages - Type 9 message is returned after IMP time-out (ask BBN for time).
  4. Destination IMP and IMP-HOST interface up and IMP-HOST interface is taking messages - Type 5 (rfnm) message is returned.
  1. 宛先のIMPが停止している - タイプ7のメッセージが返されます
  2. 宛先のIMPは稼働しているが、宛先のIMP-HOSTインターフェイスが停止している - タイプ7のメッセージが返されます。
  3. 宛先のIMPとIMP-HOSTインターフェイスは稼働しているが、IMP-HOSTインターフェイスがメッセージを受け取っていない - IMPのタイムアウト（時間はBBNに問い合わせてください）の後に、タイプ9のメッセージが返されます。
  4. 宛先のIMPとIMP-HOSTインターフェイスが稼働していて、IMP-HOSTインターフェイスがメッセージを受け取っている - タイプ5（rfnm）のメッセージが返されます。

A suggestion for handling type 7 and type 9 messages has been made in NWG/RFC #117. In this document we would like to discuss in detail the problem: what should happen to the HOST-HOST protocol on receiving a rfnm?

タイプ7とタイプ9のメッセージの扱い方については、NWG/RFC #117で提案がなされています。この文書では、rfnmを受信したときにHOST-HOSTプロトコルで何が起こるべきか、という問題について詳しく論じたいと思います。

When a NCP sends out a STR or RTS control command on a pair of sockets and gets a rfnm back, this pair of sockets will be in a wait-match state. Everything is fine if a matching RTS or STR, or CLS is returned after a reasonable amount of delay. Trouble will arise when nothing is returned after a long time.

NCPがソケットのペアに対してSTRまたはRTS制御コマンドを送出し、rfnmを受け取ると、このソケットのペアは対応待ち（wait-match）状態になります。妥当な遅延の後に、対応するRTSかSTR、またはCLSが返ってくれば問題はありません。長時間経っても何も返ってこない場合に問題が生じます。

This can happen if the NCP is not running at all but its host is taking in messages (e.g. UCLA's host will receive messages even if the NCP is not running), or if the NCP is running very slowly. The same problem exists on sending out a CLS control command and a matching CLS is never returned. The trouble is that resources are tied up, e.g. sockets, links and table space in the NCP; and one would like to release these resources. In our implementation, when a user does a CLOSE, we can't release the sockets until the matching CLS is returned. This protects us from getting confused if a seconds request is made for the same pair of sockets. This problem can be solved by including a time-out mechanism in the Host-Host protocol. This operates as follows:

これは、NCPがまったく動作していないのに、そのホストがメッセージを受け取っている場合（たとえば、UCLAのホストはNCPが動作していなくてもメッセージを受信します）や、NCPの動作が非常に遅い場合に起こりえます。CLS制御コマンドを送出したのに、対応するCLSが返ってこない場合にも、同じ問題が存在します。問題は、ソケット、リンク、NCP内のテーブル領域などの資源が拘束されたままになることであり、これらの資源を解放したいところです。私たちの実装では、ユーザーがCLOSEを行ったとき、対応するCLSが返ってくるまでソケットを解放できません。これにより、同じソケットのペアに対して2回目の要求が行われたときに混乱することを防いでいます。この問題は、Host-Hostプロトコルにタイムアウトの仕組みを含めることで解決できます。これは次のように動作します。

  1. On sending out a STR or RTS and if you do not get back a matching RTS or STR, or a CLS in T time units a CLS will be sent. After sending the time-out CLS race condition can be avoided by ignoring the matching RTS or STR that arrives before the matching CLS.
  2. On sending out a CLS (any kind, including the time-out CLS), and if you do not get back a matching CLS in T time units, the matching CLS is assumed to have returned. However, if a RTS or STR is sent on the same pair of sockets anytime after the time out and before a CLS is returned, and then we receive the CLS, there is no way to determine whether this returning CLS is for matching the previous CLS or for refusing the RTS or STR. (See the figure for detail). So far we could not solve this race condition except by assigning sequence number to connection throughout the Network which we don't think is a good solution at all. Hence, we would like to bring the attention of the Host-Host Protocol Glitch Cleaning Committe to this problem. The time limit T should be a Network Standard and its value should be decided also.
  1. STRまたはRTSを送出した後、T時間単位以内に対応するRTSかSTR、またはCLSが返ってこなければ、CLSを送信します。タイムアウトのCLSを送信した後は、対応するCLSより前に届いた、対応するRTSまたはSTRを無視することで、競合状態を回避できます。
  2. （タイムアウトのCLSを含め、種類を問わず）CLSを送出した後、T時間単位以内に対応するCLSが返ってこなければ、対応するCLSが返ってきたものとみなします。しかし、タイムアウトの後、CLSが返ってくる前のいずれかの時点で同じソケットのペアに対してRTSまたはSTRが送信され、その後にCLSを受信した場合、この返ってきたCLSが前のCLSに対応するものなのか、RTSまたはSTRを拒否するものなのかを判断する方法はありません（詳細は図を参照してください）。今のところ、ネットワーク全体でコネクションにシーケンス番号を割り当てる以外にこの競合状態を解決できていませんが、それはまったく良い解決策ではないと考えています。そこで、この問題について、Host-Hostプロトコル不具合一掃委員会（Host-Host Protocol Glitch Cleaning Committe）の注意を喚起したいと思います。時間制限Tはネットワーク標準とすべきであり、その値も決めるべきです。
