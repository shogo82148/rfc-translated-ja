RFC 8869

Evaluation Test Cases for Interactive Real-Time Media over Wireless Networks

RFC 8869

無線ネットワーク上の対話型リアルタイムメディアの評価テストケース

Abstract

概要

The Real-time Transport Protocol (RTP) is a common transport choice for interactive multimedia communication applications. The performance of these applications typically depends on a well-functioning congestion control algorithm. To ensure a seamless and robust user experience, a well-designed RTP-based congestion control algorithm should work well across all access network types. This document describes test cases for evaluating performances of candidate congestion control algorithms over cellular and Wi-Fi networks.

リアルタイム転送プロトコル（RTP）は、対話型マルチメディア通信アプリケーションでよく選ばれるトランスポートです。 これらのアプリケーションの性能は、一般に、適切に機能する輻輳制御アルゴリズムに依存します。 途切れのない堅牢なユーザー体験を確保するために、よく設計されたRTPベースの輻輳制御アルゴリズムは、あらゆる種類のアクセスネットワークでうまく機能すべきです。 この文書では、セルラーネットワークおよびWi-Fiネットワーク上で、候補となる輻輳制御アルゴリズムの性能を評価するためのテストケースについて説明します。

1. Introduction

1. はじめに

Wireless networks (both cellular and Wi-Fi [IEEE802.11]) are an integral and increasingly more significant part of the Internet. Typical application scenarios for interactive multimedia communication over wireless include video conferencing calls in a bus or train as well as live media streaming at home. It is well known that the characteristics and technical challenges for supporting multimedia services over wireless are very different from those of providing the same service over a wired network. Although the basic test cases as defined in [RFC8867] have covered many common effects of network impairments for evaluating RTP-based congestion control schemes, they remain to be tested over characteristics and dynamics unique to a given wireless environment. For example, in cellular networks, the base station maintains individual queues per radio bearer per user hence it leads to a different nature of interactions between traffic flows of different users. This contrasts with a typical wired network setting where traffic flows from all users share the same queue at the bottleneck. Furthermore, user mobility patterns in a cellular network differ from those in a Wi-Fi network. Therefore, it is important to evaluate the performance of proposed candidate RTP-based congestion control solutions over cellular mobile networks and over Wi-Fi networks respectively.

無線ネットワーク（セルラーとWi-Fi [IEEE802.11]の両方）は、インターネットに不可欠な、ますます重要性を増している部分です。 無線を介した対話型マルチメディア通信の典型的なアプリケーションシナリオには、バスや電車の中でのビデオ会議通話や、家庭でのライブメディアストリーミングがあります。 無線上でマルチメディアサービスをサポートする際の特性や技術的課題は、有線ネットワーク上で同じサービスを提供する場合とは大きく異なることがよく知られています。 [RFC8867]で定義されている基本的なテストケースは、RTPベースの輻輳制御方式を評価するためのネットワーク障害の一般的な影響の多くを網羅していますが、特定の無線環境に固有の特性や動的な変化のもとでのテストはまだ行われていません。 たとえば、セルラーネットワークでは、基地局がユーザーごと・無線ベアラーごとに個別のキューを保持しているため、異なるユーザーのトラフィックフロー間の相互作用の性質が異なります。 これは、すべてのユーザーからのトラフィックフローがボトルネックで同じキューを共有する、典型的な有線ネットワークの設定とは対照的です。 さらに、セルラーネットワークにおけるユーザーの移動パターンは、Wi-Fiネットワークにおけるものとは異なります。 したがって、提案された候補となるRTPベースの輻輳制御ソリューションの性能を、セルラーモバイルネットワーク上とWi-Fiネットワーク上のそれぞれで評価することが重要です。

[RFC8868] provides guidelines for evaluating candidate algorithms and recognizes the importance of testing over wireless access networks. However, it does not describe any specific test cases for performance evaluation of candidate algorithms. This document describes test cases specifically targeting cellular and Wi-Fi networks.

[RFC8868]は、候補アルゴリズムを評価するためのガイドラインを提供しており、無線アクセスネットワーク上でのテストの重要性を認識しています。 しかし、候補アルゴリズムの性能評価のための具体的なテストケースについては何も説明していません。 この文書では、セルラーネットワークとWi-Fiネットワークを特に対象としたテストケースについて説明します。

2. Cellular Network Specific Test Cases

2. セルラーネットワーク固有のテストケース

A cellular environment is more complicated than its wireline counterpart since it seeks to provide services in the context of variable available bandwidth, location dependencies, and user mobilities at different speeds. In a cellular network, the user may reach the cell edge, which may lead to a significant number of retransmissions to deliver the data from the base station to the destination and vice versa. These radio links will often act as a bottleneck for the rest of the network and will eventually lead to excessive delays or packet drops. An efficient retransmission or link adaptation mechanism can reduce the packet loss probability, but some packet losses and delay variations will remain. Moreover, with increased cell load or handover to a congested cell, congestion in the transport network will become even worse. Besides, there exist certain characteristics that distinguish the cellular network from other wireless access networks such as Wi-Fi. In a cellular network:

セルラー環境は、変動する利用可能帯域幅、位置への依存性、さまざまな速度でのユーザーの移動という状況のもとでサービスを提供しようとするため、有線の環境よりも複雑です。 セルラーネットワークでは、ユーザーがセルの端に到達することがあり、その場合、基地局から宛先へ（またはその逆へ）データを届けるために大量の再送が発生することがあります。 このような無線リンクは、しばしばネットワークの他の部分に対するボトルネックとして機能し、最終的には過大な遅延やパケットの破棄につながります。 効率的な再送やリンクアダプテーションのメカニズムによってパケット損失の確率を下げることはできますが、パケット損失や遅延変動は多少残ります。 さらに、セルの負荷が増加したり、輻輳したセルへハンドオーバーしたりすると、トランスポートネットワークにおける輻輳はさらに悪化します。 加えて、セルラーネットワークをWi-Fiなどの他の無線アクセスネットワークと区別する特性がいくつか存在します。 セルラーネットワークでは次のようになります。

  • The bottleneck is often a shared link with relatively few users.

    • The cost per bit over the shared link varies over time and is different for different users.
    • Leftover/unused resources can be consumed by other greedy users.
  • Queues are always per radio bearer, hence each user can have many such queues.
  • Users can experience both inter- and intra-Radio Access Technology (RAT) handovers (see [HO-def-3GPP] for the definition of "handover").
  • Handover between cells or change of serving cells (as described in [HO-LTE-3GPP] and [HO-UMTS-3GPP]) might cause user plane interruptions, which can lead to bursts of packet losses, delay, and/or jitter. The exact behavior depends on the type of radio bearer. Typically, the default best-effort bearers do not generate packet loss, instead, packets are queued up and transmitted once the handover is completed.
  • The network part decides how much the user can transmit.

  • The cellular network has variable link capacity per user.

    • It can vary as fast as a period of milliseconds.
    • It depends on many factors (such as distance, speed, interference, different flows).
    • It uses complex and smart link adaptation, which makes the link behavior ever more dynamic.
    • The scheduling priority depends on the estimated throughput.
  • Both Quality of Service (QoS) and non-QoS radio bearers can be used.

  • ボトルネックは、多くの場合、比較的少数のユーザーで共有されるリンクです。

    • 共有リンク上のビットあたりのコストは時間とともに変化し、ユーザーごとに異なります。
    • 余った、または未使用のリソースは、他の貪欲なユーザーによって消費される可能性があります。
  • キューは常に無線ベアラーごとにあるため、各ユーザーはそのようなキューを多数持つことができます。
  • ユーザーは、無線アクセス技術（RAT）間のハンドオーバーと、RAT内のハンドオーバーの両方を経験する可能性があります（「ハンドオーバー」の定義については[HO-def-3GPP]を参照してください）。
  • （[HO-LTE-3GPP]および[HO-UMTS-3GPP]で説明されているような）セル間のハンドオーバーやサービングセルの変更は、ユーザープレーンの中断を引き起こすことがあり、それによってパケット損失、遅延、ジッターがバースト的に発生する可能性があります。 正確な挙動は無線ベアラーの種類によって異なります。 通常、デフォルトのベストエフォートベアラーはパケット損失を発生させず、代わりにパケットはキューに入れられ、ハンドオーバーが完了した時点で送信されます。
  • ユーザーがどれだけ送信できるかは、ネットワーク側が決定します。

  • セルラーネットワークのリンク容量は、ユーザーごとに変動します。

    • ミリ秒単位の周期で変動することもあります。
    • 多くの要因（距離、速度、干渉、異なるフローなど）に依存します。
    • 複雑で高度なリンクアダプテーションを使用するため、リンクの挙動はより一層動的になります。
    • スケジューリングの優先度は、推定されたスループットに依存します。
  • サービス品質（QoS）の無線ベアラーと、QoSなしの無線ベアラーのどちらも使用できます。

Hence, a real-time communication application operating over a cellular network needs to cope with a shared bottleneck link and variable link capacity, events like handover, non-congestion-related loss, and abrupt changes in bandwidth (both short term and long term) due to handover, network load, and bad radio coverage. Even though 3GPP has defined QoS bearers [QoS-3GPP] to ensure high-quality user experience, it is still preferable for real-time applications to behave in an adaptive manner.

したがって、セルラーネットワーク上で動作するリアルタイム通信アプリケーションは、共有されたボトルネックリンクと変動するリンク容量、ハンドオーバーのようなイベント、輻輳に関係しない損失、そしてハンドオーバー、ネットワーク負荷、劣悪な無線カバレッジによる帯域幅の急激な変化（短期的なものと長期的なものの両方）に対処する必要があります。 3GPPは高品質なユーザー体験を確保するためにQoSベアラー[QoS-3GPP]を定義していますが、それでもリアルタイムアプリケーションは適応的に振る舞うことが望ましいです。

Different mobile operators deploy their own cellular networks with their own set of network functionalities and policies. Usually, a mobile operator network includes a range of radio access technologies such as 3G and 4G/LTE. Looking at the specifications of such radio technologies, it is evident that only the more recent radio technologies can support the high bandwidth requirements from real-time interactive video applications. Future real-time interactive applications will impose even greater demand on cellular network performance, which makes 4G (and beyond) radio technologies more suitable for such genre of application.

さまざまなモバイル事業者が、それぞれ独自のネットワーク機能とポリシーの組み合わせを持つ独自のセルラーネットワークを展開しています。 通常、モバイル事業者のネットワークには、3Gや4G/LTEなど、さまざまな無線アクセス技術が含まれています。 そのような無線技術の仕様を見ると、リアルタイムの対話型ビデオアプリケーションからの高い帯域幅要件をサポートできるのは、より新しい無線技術だけであることは明らかです。 将来のリアルタイム対話型アプリケーションは、セルラーネットワークの性能にさらに大きな要求を課すことになり、そのため4G（およびそれ以降）の無線技術がそのような種類のアプリケーションにより適したものになります。

The key factors in defining test cases for cellular networks are:

セルラーネットワークのテストケースを定義するうえでの主要な要因は次のとおりです。

  • Shared and varying link capacity
  • Mobility
  • Handover
  • 共有され変動するリンク容量
  • モビリティー
  • ハンドオーバー

However, these factors are typically highly correlated in a cellular network. Therefore, instead of devising separate test cases for individual important events, we have divided the test cases into two categories. It should be noted that the goal of the following test cases is to evaluate the performance of candidate algorithms over the radio interface of the cellular network. Hence, it is assumed that the radio interface is the bottleneck link between the communicating peers and that the core network does not introduce any extra congestion along the path. Consequently, this document has left out of scope the combination of multiple access technologies involving both cellular and Wi-Fi users. In this latter case, the shared bottleneck is likely at the wired backhaul link. These test cases further assume a typical real-time telephony scenario where one real-time session consists of one voice stream and one video stream.

しかし、セルラーネットワークでは、これらの要因は通常、互いに強く相関しています。 そのため、重要なイベントごとに個別のテストケースを考案するのではなく、テストケースを2つのカテゴリーに分けました。 以下のテストケースの目的は、セルラーネットワークの無線インターフェイス上での候補アルゴリズムの性能を評価することである点に注意してください。 したがって、無線インターフェイスが通信するピア間のボトルネックリンクであり、コアネットワークは経路上に余分な輻輳をもたらさないことを前提とします。 その結果、この文書では、セルラーユーザーとWi-Fiユーザーの両方が関与する複数のアクセス技術の組み合わせを範囲外としています。 この後者の場合、共有ボトルネックは有線のバックホールリンクにある可能性が高いです。 これらのテストケースではさらに、1つのリアルタイムセッションが1つの音声ストリームと1つのビデオストリームで構成される、典型的なリアルタイム電話のシナリオを前提とします。

Even though it is possible to carry out tests over operational cellular networks (e.g., LTE/5G), and actually such tests are already available today, these tests cannot in general be carried out in a deterministic fashion to ensure repeatability. The main reason is that these networks are controlled by cellular operators, and there exists various amounts of competing traffic in the same cell(s). In practice, it is only in underground mines that one can carry out near deterministic testing. Even there, it is not guaranteed either as workers in the mines may carry with them their personal mobile phones. Furthermore, the underground mining setting may not reflect typical usage patterns in an urban setting. We, therefore, recommend that a cellular network simulator be used for the test cases defined in this document, for example -- the LTE simulator in [NS-3].

運用中のセルラーネットワーク（たとえばLTE/5G）上でテストを実施することは可能であり、実際にそのようなテストは今日すでに利用可能ですが、これらのテストは一般に、再現性を確保できるような決定論的な方法で実施することはできません。 その主な理由は、これらのネットワークがセルラー事業者によって制御されており、同じセルにさまざまな量の競合トラフィックが存在するためです。 実際には、ほぼ決定論的なテストを実施できるのは地下鉱山の中だけです。 そこでさえ、鉱山の作業員が個人の携帯電話を持ち込んでいる可能性があるため、保証されるわけではありません。 さらに、地下鉱山の環境は、都市環境における典型的な利用パターンを反映していない可能性があります。 したがって、この文書で定義するテストケースには、セルラーネットワークシミュレーター（たとえば[NS-3]のLTEシミュレーター）を使用することを推奨します。

2.1. Varying Network Load

2.1. 変動するネットワーク負荷

The goal of this test is to evaluate the performance of the candidate congestion control algorithm under varying network load. The network load variation is created by adding and removing network users, a.k.a. User Equipment (UE), during the simulation. In this test case, each user/UE in the media session is an endpoint following RTP-based congestion control. User arrivals follow a Poisson distribution proportional to the length of the call, to keep the number of users per cell fairly constant during the evaluation period. At the beginning of the simulation, there should be enough time to warm up the network. This is to avoid running the evaluation in an empty network where network nodes have empty buffers and low interference at the beginning of the simulation. This network initialization period should be excluded from the evaluation period. Typically, the evaluation period starts 30 seconds after test initialization.

3. Wi-Fi Networks Specific Test Cases

3. Wi-Fiネットワーク固有のテストケース

Given the prevalence of Internet access links over Wi-Fi, it is important to evaluate candidate RTP-based congestion control solutions over test cases that include Wi-Fi access links. Such evaluations should highlight the inherently different characteristics of Wi-Fi networks in contrast to their wired counterparts:

Wi-Fiを介したインターネットアクセスリンクが普及していることを考えると、候補となるRTPベースの輻輳制御ソリューションを、Wi-Fiアクセスリンクを含むテストケースで評価することが重要です。 そのような評価では、有線ネットワークと対比して、Wi-Fiネットワークの本質的に異なる特性を浮き彫りにすべきです。

  • The wireless radio channel is subject to interference from nearby transmitters, multipath fading, and shadowing. These effects lead to fluctuations in the link throughput and sometimes an error-prone communication environment.
  • Available network bandwidth is not only shared over the air between concurrent users but also between uplink and downlink traffic due to the half-duplex nature of the wireless transmission medium.
  • Packet transmissions over Wi-Fi are susceptible to contentions and collisions over the air. Consequently, traffic load beyond a certain utilization level over a Wi-Fi network can introduce frequent collisions over the air and significant network overhead, as well as packet drops due to buffer overflow at the transmitters. This, in turn, leads to excessive delay, retransmissions, packet losses, and lower effective bandwidth for applications. Note further that the collision-induced delay and loss patterns are qualitatively different from those caused by congestion over a wired connection.
  • The IEEE 802.11 standard (i.e., Wi-Fi) supports multi-rate transmission capabilities by dynamically choosing the most appropriate modulation and coding scheme (MCS) for the given received signal strength. A different choice in the MCS Index leads to different physical-layer (PHY-layer) link rates and consequently different application-layer throughput.
  • The presence of legacy devices (e.g., ones operating only in IEEE 802.11b) at a much lower PHY-layer link rate can significantly slow down the rest of a modern Wi-Fi network. As discussed in [Heusse2003], the main reason for such anomaly is that it takes much longer to transmit the same packet over a slower link than over a faster link, thereby consuming a substantial portion of air time.
  • Handover from one Wi-Fi Access Point (AP) to another may lead to excessive packet delays and losses during the process.
  • IEEE 802.11e has introduced the Enhanced Distributed Channel Access (EDCA) mechanism to allow different traffic categories to contend for channel access using different random back-off parameters. This mechanism is a mandatory requirement for the Wi-Fi Multimedia (WMM) certification in Wi-Fi Alliance. It allows for prioritization of real-time application traffic such as voice and video over non-urgent data transmissions (e.g., file transfer).
  • 無線チャネルは、近くの送信機からの干渉、マルチパスフェージング、シャドウイングの影響を受けます。 これらの影響により、リンクのスループットが変動し、ときにはエラーが発生しやすい通信環境になります。
  • 利用可能なネットワーク帯域幅は、無線伝送媒体の半二重という性質により、同時に利用するユーザー間で無線上で共有されるだけでなく、アップリンクとダウンリンクのトラフィック間でも共有されます。
  • Wi-Fi上のパケット送信は、無線上での競合や衝突の影響を受けやすいです。 その結果、Wi-Fiネットワーク上で一定の利用率を超えるトラフィック負荷がかかると、無線上で頻繁な衝突と大きなネットワークオーバーヘッドが生じ、また送信機でのバッファーオーバーフローによるパケットの破棄が発生する可能性があります。 これは、ひいては過大な遅延、再送、パケット損失、そしてアプリケーションにとっての実効帯域幅の低下につながります。 さらに、衝突によって引き起こされる遅延と損失のパターンは、有線接続上の輻輳によって引き起こされるものとは質的に異なることにも注意してください。
  • IEEE 802.11標準（すなわちWi-Fi）は、受信信号強度に応じて最も適切な変調・符号化方式（MCS）を動的に選択することにより、マルチレート伝送機能をサポートしています。 MCSインデックスの選択が異なれば、物理層（PHY層）のリンクレートが異なり、その結果アプリケーション層のスループットも異なります。
  • はるかに低いPHY層リンクレートで動作するレガシーデバイス（たとえばIEEE 802.11bでのみ動作するもの）が存在すると、最新のWi-Fiネットワークの残りの部分が大幅に遅くなることがあります。 [Heusse2003]で議論されているように、このような異常の主な理由は、同じパケットを送信するのに、低速なリンクでは高速なリンクよりもはるかに長い時間がかかり、それによってエアタイムのかなりの部分を消費してしまうことです。
  • あるWi-Fiアクセスポイント（AP）から別のAPへのハンドオーバーは、その過程で過大なパケット遅延と損失を引き起こす可能性があります。
  • IEEE 802.11eは、異なるトラフィックカテゴリーが異なるランダムバックオフパラメーターを使用してチャネルアクセスを競合できるようにする、Enhanced Distributed Channel Access（EDCA）メカニズムを導入しました。 このメカニズムは、Wi-Fi AllianceにおけるWi-Fi Multimedia（WMM）認定の必須要件です。 これにより、音声やビデオなどのリアルタイムアプリケーションのトラフィックを、緊急でないデータ送信（たとえばファイル転送）よりも優先させることができます。

In summary, the presence of Wi-Fi access links in different network topologies can exert different impacts on the network performance in terms of application-layer effective throughput, packet loss rate, and packet delivery delay. These, in turn, will influence the behavior of end-to-end real-time multimedia congestion control.

まとめると、さまざまなネットワークトポロジーにおけるWi-Fiアクセスリンクの存在は、アプリケーション層の実効スループット、パケット損失率、パケット配信遅延の観点で、ネットワーク性能にさまざまな影響を及ぼす可能性があります。 そしてこれらは、エンドツーエンドのリアルタイムマルチメディア輻輳制御の挙動に影響を与えます。

Unless otherwise mentioned, the test cases in this section choose the PHY- and MAC-layer parameters based on the IEEE 802.11n standard. Statistics collected from enterprise Wi-Fi networks show that the two dominant physical modes are 802.11n and 802.11ac, accounting for 41% and 58% of connected devices, respectively. As Wi-Fi standards evolve over time -- for instance, with the introduction of the emerging Wi-Fi 6 (based on IEEE 802.11ax) products -- the PHY- and MAC-layer test case specifications need to be updated accordingly to reflect such changes.

特に断りのない限り、このセクションのテストケースでは、IEEE 802.11n標準に基づいてPHY層とMAC層のパラメーターを選択します。 企業のWi-Fiネットワークから収集された統計によると、主要な2つの物理モードは802.11nと802.11acであり、それぞれ接続デバイスの41%と58%を占めています。 Wi-Fi標準は時間とともに進化するため（たとえば、新たに登場したWi-Fi 6（IEEE 802.11axに基づく）製品の導入など）、PHY層とMAC層のテストケース仕様は、そのような変化を反映するように適宜更新する必要があります。

Typically, a Wi-Fi access network connects to a wired infrastructure. Either the wired or the Wi-Fi segment of the network can be the bottleneck. The following sections describe basic test cases for both scenarios separately. The same set of performance metrics as in [RFC8867]) should be collected for each test case.

通常、Wi-Fiアクセスネットワークは有線インフラストラクチャーに接続されます。 ネットワークの有線セグメントとWi-Fiセグメントのどちらもボトルネックになりえます。 以下のセクションでは、両方のシナリオについての基本的なテストケースを個別に説明します。 各テストケースでは、[RFC8867]と同じ性能メトリックの組を収集すべきです。

We recommend carrying out the test cases as defined in this document using a simulator, such as [NS-2] or [NS-3]. When feasible, it is encouraged to perform testbed-based evaluations using Wi-Fi access points and endpoints running up-to-date IEEE 802.11 protocols, such as 802.11ac and the emerging Wi-Fi 6, so as to verify the viability of the candidate schemes.

この文書で定義するテストケースは、[NS-2]や[NS-3]などのシミュレーターを使用して実施することを推奨します。 実施可能な場合は、候補方式の実現可能性を検証するために、802.11acや新たに登場したWi-Fi 6など、最新のIEEE 802.11プロトコルを実行するWi-Fiアクセスポイントとエンドポイントを使用して、テストベッドベースの評価を行うことが推奨されます。

3.1.4. Expected Behavior

3.1.4. 期待される動作

Single uplink RTP-based media flow:
The candidate algorithm is expected to detect the path capacity constraint, to converge to the bottleneck link capacity, and to adapt the flow to avoid unwanted oscillations when the sending bit rate is approaching the bottleneck link capacity. No excessive oscillations in the media rate should be present.
Bidirectional RTP-based media flows:
The candidate algorithm is expected to converge to the bottleneck capacity of the wired path in both directions despite the presence of measurement noise over the Wi-Fi connection. In the presence of background TCP or CBR over UDP traffic, the rate of RTP-based media flows should adapt promptly to the arrival and departure of background traffic flows.
One RTP-based media flow competing with long-lived TCP flow in the uplink direction:
The candidate algorithm is expected to avoid congestion collapse and to stabilize at a fair share of the bottleneck link capacity.
単一のアップリンクのRTPベースのメディアフロー：
候補アルゴリズムには、パス容量の制約を検出し、ボトルネックリンクの容量に収束し、送信ビットレートがボトルネックリンクの容量に近づいたときに不要な振動を避けるようにフローを適応させることが期待されます。 メディアレートに過度の振動があるべきではありません。
双方向のRTPベースのメディアフロー：

3.2.3. Typical Test Scenarios

3.2.3. 典型的なテストシナリオ

This section describes a few test scenarios that are deemed as important for understanding the behavior of a candidate RTP-based congestion control scheme over a Wi-Fi network.

このセクションでは、Wi-Fiネットワーク上での候補となるRTPベースの輻輳制御方式の挙動を理解するうえで重要と考えられる、いくつかのテストシナリオについて説明します。

Multiple RTP-based media flows sharing the wireless downlink:
N=16 (all downlink); M=0. This test case is for studying the impact of contention on the multiple concurrent media flows. For an 802.11n network, given the MCS Index of 11 and the corresponding link rate of 52 Mbps, the total application-layer throughput (assuming reasonable distance, low interference, and infrequent contentions caused by competing streams) is around 20 Mbps. A total of N=16 RTP-based media flows (with a maximum rate of 1.5 Mbps each) are expected to saturate the wireless interface in this experiment. Evaluation of a given candidate scheme should focus on whether the downlink media flows can stabilize at a fair share of the total application-layer throughput.
Multiple RTP-based media flows sharing the wireless uplink:
N=16 (all uplink); M=0. When multiple clients attempt to transmit media packets uplink over the Wi-Fi network, they introduce more frequent contentions and potential collisions. Per-flow throughput is expected to be lower than that in the previous downlink-only scenario. Evaluation of a given candidate scheme should focus on whether the uplink flows can stabilize at a fair share of the total application-layer throughput.
Multiple bidirectional RTP-based media flows:
N=16 (8 uplink and 8 downlink); M=0. The goal of this test is to evaluate the performance of the candidate scheme in terms of bandwidth fairness between uplink and downlink flows.
Multiple bidirectional RTP-based media flows with on-off CBR traffic over UDP:
N=16 (8 uplink and 8 downlink); M=5 (uplink). The goal of this test is to evaluate the adaptation behavior of the candidate scheme when its available bandwidth changes due to the departure of background traffic. The background traffic consists of several (e.g., M=5) CBR flows transported over UDP. These background flows are ON at time t=0-60s and OFF at time t=61-120s.
Multiple bidirectional RTP-based media flows with off-on CBR traffic over UDP:
N=16 (8 uplink and 8 downlink); M=5 (uplink). The goal of this test is to evaluate the adaptation behavior of the candidate scheme when its available bandwidth changes due to the arrival of background traffic. The background traffic consists of several (e.g., M=5) parallel CBR flows transported over UDP. These background flows are OFF at time t=0-60s and ON at times t=61-120s.
Multiple bidirectional RTP-based media flows in the presence of background TCP traffic:
N=16 (8 uplink and 8 downlink); M=5 (uplink). The goal of this test is to evaluate how RTP-based media flows compete against TCP over a congested Wi-Fi network for a given candidate scheme. TCP flows have start time at t=40s and end time at t=80s.
Varying number of RTP-based media flows:
A series of tests can be carried out for the above test cases with different values of N, e.g., N=[4, 8, 12, 16, 20]. The goal of this test is to evaluate how a candidate scheme responds to varying traffic load/demand over a congested Wi-Fi network. The start times of the media flows are randomly distributed within a window of t=0-10s; their end times are randomly distributed within a window of t=110-120s.
無線ダウンリンクを共有する複数のRTPベースのメディアフロー：
N=16（すべてダウンリンク）、M=0。 このテストケースは、複数の同時メディアフローに対する競合の影響を調べるためのものです。 802.11nネットワークでは、MCSインデックスが11で対応するリンクレートが52 Mbpsの場合、アプリケーション層の総スループットは（妥当な距離、低い干渉、競合するストリームによる競合の発生がまれであることを前提とすると）約20 Mbpsです。 この実験では、合計N=16のRTPベースのメディアフロー（それぞれ最大レート1.5 Mbps）が無線インターフェイスを飽和させることが予想されます。 候補方式の評価では、ダウンリンクのメディアフローが、アプリケーション層の総スループットの公平な取り分で安定できるかどうかに焦点を当てるべきです。
無線アップリンクを共有する複数のRTPベースのメディアフロー：
N=16（すべてアップリンク）、M=0。 複数のクライアントがWi-Fiネットワーク上でアップリンク方向にメディアパケットを送信しようとすると、競合がより頻繁になり、衝突の可能性も生じます。 フローあたりのスループットは、前述のダウンリンクのみのシナリオよりも低くなることが予想されます。 候補方式の評価では、アップリンクのフローが、アプリケーション層の総スループットの公平な取り分で安定できるかどうかに焦点を当てるべきです。
複数の双方向のRTPベースのメディアフロー：
N=16（アップリンク8、ダウンリンク8）、M=0。 このテストの目的は、アップリンクとダウンリンクのフロー間の帯域幅の公平性の観点で、候補方式の性能を評価することです。
UDP上のオンオフ型CBRトラフィックを伴う複数の双方向のRTPベースのメディアフロー：
N=16（アップリンク8、ダウンリンク8）、M=5（アップリンク）。 このテストの目的は、バックグラウンドトラフィックの離脱によって利用可能な帯域幅が変化したときの、候補方式の適応動作を評価することです。 バックグラウンドトラフィックは、UDP上で運ばれるいくつか（たとえばM=5）のCBRフローで構成されます。 これらのバックグラウンドフローは、時刻t=0～60sでON、時刻t=61～120sでOFFになります。
UDP上のオフオン型CBRトラフィックを伴う複数の双方向のRTPベースのメディアフロー：
N=16（アップリンク8、ダウンリンク8）、M=5（アップリンク）。 このテストの目的は、バックグラウンドトラフィックの到着によって利用可能な帯域幅が変化したときの、候補方式の適応動作を評価することです。 バックグラウンドトラフィックは、UDP上で運ばれるいくつか（たとえばM=5）の並列なCBRフローで構成されます。 これらのバックグラウンドフローは、時刻t=0～60sでOFF、時刻t=61～120sでONになります。
バックグラウンドのTCPトラフィックが存在する状況での複数の双方向のRTPベースのメディアフロー：
N=16（アップリンク8、ダウンリンク8）、M=5（アップリンク）。 このテストの目的は、ある候補方式について、輻輳したWi-Fiネットワーク上でRTPベースのメディアフローがTCPとどのように競合するかを評価することです。 TCPフローの開始時刻はt=40s、終了時刻はt=80sです。
RTPベースのメディアフローの数の変動：
上記のテストケースについて、Nの値を変えて（たとえばN=[4, 8, 12, 16, 20]）一連のテストを実施できます。 このテストの目的は、輻輳したWi-Fiネットワーク上で、変動するトラフィック負荷/需要に候補方式がどのように応答するかを評価することです。 メディアフローの開始時刻はt=0～10sの時間枠内でランダムに分布し、終了時刻はt=110～120sの時間枠内でランダムに分布します。

3.2.4. Expected Behavior

3.2.4. 期待される動作

Multiple downlink RTP-based media flows:
Each media flow is expected to get its fair share of the total bottleneck link bandwidth. Overall bandwidth usage should not be significantly lower than that experienced by the same number of concurrent downlink TCP flows. In other words, the behavior of multiple concurrent TCP flows will be used as a performance benchmark for this test scenario. The end-to-end delay and packet loss ratio experienced by each flow should be within an acceptable range for real-time multimedia applications.
Multiple uplink RTP-based media flows:
Overall bandwidth usage by all media flows should not be significantly lower than that experienced by the same number of concurrent uplink TCP flows. In other words, the behavior of multiple concurrent TCP flows will be used as a performance benchmark for this test scenario.
Multiple bidirectional RTP-based media flows with dynamic background traffic carrying CBR flows over UDP:
The media flows are expected to adapt in a timely fashion to the changes in available bandwidth introduced by the arrival/departure of background traffic.
Multiple bidirectional RTP-based media flows with dynamic background traffic over TCP:
During the presence of TCP background flows, the overall bandwidth usage by all media flows should not be significantly lower than those achieved by the same number of bidirectional TCP flows. In other words, the behavior of multiple concurrent TCP flows will be used as a performance benchmark for this test scenario. All downlink media flows are expected to obtain similar bandwidth as each other. The throughput of each media flow is expected to decrease upon the arrival of TCP background traffic and, conversely, increase upon their departure. Both reactions should occur in a timely fashion, for example, within 10s of seconds.
Varying number of bidirectional RTP-based media flows:
The test results for varying values of N -- while keeping all other parameters constant -- is expected to show steady and stable per-flow throughput for each value of N. The average throughput of all media flows is expected to stay constant around the maximum rate when N is small, then gradually decrease with increasing value of N till it reaches the minimum allowed rate, beyond which the offered load to the Wi-Fi network exceeds its capacity (i.e., with a very large value of N).
複数のダウンリンクのRTPベースのメディアフロー：
各メディアフローは、ボトルネックリンクの総帯域幅の公平な取り分を得ることが期待されます。 全体の帯域幅使用量は、同じ数の同時ダウンリンクTCPフローの場合と比べて大幅に低くなるべきではありません。 言い換えると、このテストシナリオでは、複数の同時TCPフローの挙動を性能のベンチマークとして使用します。 各フローが経験するエンドツーエンドの遅延とパケット損失率は、リアルタイムマルチメディアアプリケーションにとって許容できる範囲内にあるべきです。
複数のアップリンクのRTPベースのメディアフロー：
すべてのメディアフローによる全体の帯域幅使用量は、同じ数の同時アップリンクTCPフローの場合と比べて大幅に低くなるべきではありません。 言い換えると、このテストシナリオでは、複数の同時TCPフローの挙動を性能のベンチマークとして使用します。
UDP上のCBRフローを運ぶ動的なバックグラウンドトラフィックを伴う複数の双方向のRTPベースのメディアフロー：
メディアフローは、バックグラウンドトラフィックの到着/離脱によって生じる利用可能な帯域幅の変化に、タイムリーに適応することが期待されます。
TCP上の動的なバックグラウンドトラフィックを伴う複数の双方向のRTPベースのメディアフロー：
TCPのバックグラウンドフローが存在する間、すべてのメディアフローによる全体の帯域幅使用量は、同じ数の双方向TCPフローが達成するものと比べて大幅に低くなるべきではありません。 言い換えると、このテストシナリオでは、複数の同時TCPフローの挙動を性能のベンチマークとして使用します。 すべてのダウンリンクのメディアフローは、互いに同程度の帯域幅を得ることが期待されます。 各メディアフローのスループットは、TCPのバックグラウンドトラフィックの到着時に減少し、逆にその離脱時に増加することが期待されます。 どちらの反応もタイムリーに、たとえば数十秒以内に起こるべきです。
双方向のRTPベースのメディアフローの数の変動：
他のすべてのパラメーターを一定に保ったままNの値を変化させたテスト結果では、Nの各値について、一定で安定したフローあたりのスループットが示されることが期待されます。 すべてのメディアフローの平均スループットは、Nが小さいときには最大レート付近で一定に保たれ、その後Nの値が大きくなるにつれて徐々に減少し、許容される最小レートに達することが期待されます。 それを超えると、Wi-Fiネットワークへの提供負荷がその容量を超えます（すなわち、Nの値が非常に大きい場合）。

3.3. Other Potential Test Cases

3.3. その他の潜在的なテストケース

3.3.1. EDCA/WMM usage

3.3.1. EDCA/WMMの使用

The EDCA/WMM mechanism defines prioritized QoS for four traffic classes (or Access Categories). RTP-based real-time media flows should achieve better performance in terms of lower delay and fewer packet losses with EDCA/WMM enabled when competing against non-interactive background traffic such as file transfers. When most of the traffic over Wi-Fi is dominated by media, however, turning on WMM may degrade performance since all media flows now attempt to access the wireless transmission medium more aggressively, thereby causing more frequent collisions and collision-induced losses. This is a topic worthy of further investigation.

EDCA/WMMメカニズムは、4つのトラフィッククラス（またはアクセスカテゴリー）に対して優先順位付けされたQoSを定義します。 ファイル転送のような非対話型のバックグラウンドトラフィックと競合する場合、EDCA/WMMを有効にすると、RTPベースのリアルタイムメディアフローは、遅延の低下とパケット損失の減少という観点で、より良い性能を達成するはずです。 しかし、Wi-Fi上のトラフィックの大部分をメディアが占めている場合、WMMを有効にすると性能が低下する可能性があります。 これは、すべてのメディアフローが無線伝送媒体へよりアグレッシブにアクセスしようとするようになり、その結果、衝突と衝突による損失がより頻繁に発生するためです。 これはさらなる調査に値するトピックです。

3.3.2. Effect of Heterogeneous Link Rates

3.3.2. 異種リンクレートの影響

As discussed in [Heusse2003], the presence of clients operating over slow PHY-layer link rates (e.g., a legacy 802.11b device) connected to a modern network may adversely impact the overall performance of the network. Additional test cases can be devised to evaluate the effect of clients with heterogeneous link rates on the performance of the candidate congestion control algorithm. Such test cases, for instance, can specify that the PHY-layer link rates for all clients span over a wide range (e.g., 2 Mbps to 54 Mbps) for investigating its effect on the congestion control behavior of the real-time interactive applications.

[Heusse2003]で議論されているように、低速なPHY層リンクレートで動作するクライアント（たとえばレガシーな802.11bデバイス）が最新のネットワークに接続されていると、ネットワーク全体の性能に悪影響を及ぼす可能性があります。 異種のリンクレートを持つクライアントが、候補となる輻輳制御アルゴリズムの性能に与える影響を評価するために、追加のテストケースを考案できます。 たとえばそのようなテストケースでは、リアルタイム対話型アプリケーションの輻輳制御の挙動への影響を調べるために、すべてのクライアントのPHY層リンクレートが広い範囲（たとえば2 Mbpsから54 Mbps）にわたるように指定できます。

5. Security Considerations

5. セキュリティーに関する考慮事項

The security considerations in [RFC8868] and the relevant congestion control algorithms apply. The principles for congestion control are described in [RFC2914], and in particular, any new method must implement safeguards to avoid congestion collapse of the Internet.

[RFC8868]および関連する輻輳制御アルゴリズムにおけるセキュリティーに関する考慮事項が適用されます。 輻輳制御の原則は[RFC2914]で説明されており、特に、新しい手法はすべて、インターネットの輻輳崩壊を回避するための安全策を実装しなければなりません。

Given the difficulty of deterministic wireless testing, it is recommended and expected that the tests described in this document would be done via simulations. However, in the case where these test cases are carried out in a testbed setting, the evaluation should take place in a controlled lab environment. In the testbed, the applications, simulators, and network nodes ought to be well-behaved and should not impact the desired results. It is important to take appropriate caution to avoid leaking nonresponsive traffic with unproven congestion avoidance behavior onto the open Internet.

決定論的な無線テストが難しいことを考えると、この文書で説明するテストはシミュレーションによって行うことが推奨され、またそのように期待されます。 ただし、これらのテストケースをテストベッド環境で実施する場合、評価は管理されたラボ環境で行うべきです。 テストベッドでは、アプリケーション、シミュレーター、ネットワークノードは適切に振る舞うべきであり、望ましい結果に影響を与えるべきではありません。 実証されていない輻輳回避動作を持つ、応答しないトラフィックがオープンなインターネットに漏れ出すことを避けるため、適切な注意を払うことが重要です。
