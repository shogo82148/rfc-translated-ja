RFC 6034

Unicast-Prefix-Based IPv4 Multicast Addresses

RFC 6034

ユニキャストプレフィックスに基づくIPv4マルチキャストアドレス

Abstract

概要

This specification defines an extension to the multicast addressing architecture of the IP Version 4 protocol. The extension presented in this document allows for unicast-prefix-based assignment of multicast addresses. By delegating multicast addresses at the same time as unicast prefixes, network operators will be able to identify their multicast addresses without needing to run an inter-domain allocation protocol.

この仕様は、IPバージョン4プロトコルのマルチキャストアドレス体系（addressing architecture）に対する拡張を定義します。この文書で示す拡張により、ユニキャストプレフィックスに基づいてマルチキャストアドレスを割り当てられるようになります。ユニキャストプレフィックスと同時にマルチキャストアドレスを委任することで、ネットワーク運用者は、ドメイン間の割り当てプロトコルを実行することなく、自分のマルチキャストアドレスを特定できるようになります。

1. Introduction

1. はじめに

RFC 3180 [RFC3180] defines an allocation mechanism (called "GLOP") in 233/8 whereby an Autonomous System (AS) number is embedded in the middle 16 bits of an IPv4 multicast address, resulting in 256 multicast addresses per AS. Advantages of this mechanism include the ability to get multicast address space without an inter-domain multicast address allocation protocol, and the ease of determining the AS that was assigned the address for debugging and auditing purposes.

RFC 3180 [RFC3180]は、233/8において、自律システム（AS）番号をIPv4マルチキャストアドレスの中央の16ビットに埋め込む割り当てメカニズム（「GLOP」と呼ばれます）を定義しており、その結果、ASごとに256個のマルチキャストアドレスが得られます。このメカニズムの利点には、ドメイン間のマルチキャストアドレス割り当てプロトコルなしでマルチキャストアドレス空間を取得できることや、デバッグや監査の目的で、そのアドレスが割り当てられたASを容易に特定できることがあります。

Some disadvantages of GLOP include:

GLOPの欠点には、次のようなものがあります。

  • RFC 4893 [RFC4893] expands the size of an AS number to 4 bytes, and GLOP cannot work with 4-byte AS numbers.
  • When an AS covers multiple sites or organizations, administration of the multicast address space within an AS must be handled by other mechanisms, such as manual administrative effort or the Multicast Address Dynamic Client Allocation Protocol (MADCAP) [RFC2730].
  • During debugging, identifying the AS does not immediately identify the correct organization when an AS covers multiple organizations.
  • Only 256 addresses are automatically available per AS, and obtaining any more requires administrative effort.
  • RFC 4893 [RFC4893]はAS番号のサイズを4バイトに拡張しましたが、GLOPは4バイトのAS番号では機能しません。
  • ASが複数のサイトや組織にまたがる場合、AS内のマルチキャストアドレス空間の管理は、手作業による管理や、マルチキャストアドレス動的クライアント割り当てプロトコル（Multicast Address Dynamic Client Allocation Protocol、MADCAP）[RFC2730]などの他のメカニズムで扱わなければなりません。
  • ASが複数の組織にまたがる場合、デバッグ中にASを特定しても、正しい組織をすぐに特定できるわけではありません。
  • ASごとに自動的に利用できるアドレスは256個だけであり、それ以上を取得するには管理上の手間が必要です。

More recently, a mechanism [RFC3306] has been developed for IPv6 that provides a multicast range to every IPv6 subnet, which is at a much finer granularity than an AS. As a result, the first three disadvantages above are avoided (and the last disadvantage does not apply to IPv6 due to the extended size of the address space).

より最近では、IPv6向けに、すべてのIPv6サブネットにマルチキャストの範囲を提供するメカニズム[RFC3306]が開発されました。これはASよりもはるかに細かい粒度です。その結果、上記の最初の3つの欠点は回避されます（また、最後の欠点は、アドレス空間のサイズが拡張されているため、IPv6には当てはまりません）。

Another advantage of providing multicast space to a subnet, rather than just to an entire AS, is that multicast address assignments within the range need only be coordinated within the subnet.

AS全体だけではなくサブネットにマルチキャスト空間を提供することのもう1つの利点は、その範囲内のマルチキャストアドレスの割り当てを、サブネット内でのみ調整すればよいことです。

This document specifies a mechanism similar to [RFC3306], whereby a range of global IPv4 multicast address space is provided to each organization that has unicast address space. A resulting advantage over GLOP is that the mechanisms in IPv4 and IPv6 become more similar.

この文書は、[RFC3306]と同様のメカニズムを規定します。このメカニズムでは、ユニキャストアドレス空間を持つ各組織に、グローバルなIPv4マルチキャストアドレス空間の範囲が提供されます。結果として得られるGLOPに対する利点は、IPv4とIPv6のメカニズムがより似たものになることです。

This document does not obsolete or update RFC 3180, as the mechanism described in RFC 3180 is still required for organizations with prefix allocations more specific than /24. Organizations using RFC 3180 allocations may continue to do so. In fact, it is conceivable that an organization might use both RFC 3180 allocations and the allocation method described in this document.

この文書は、RFC 3180を廃止も更新もしません。RFC 3180で説明されているメカニズムは、/24よりも具体的な（長い）プレフィックスを割り当てられた組織にとって依然として必要だからです。RFC 3180の割り当てを使っている組織は、引き続きそれを使えます。実際、ある組織がRFC 3180の割り当てとこの文書で説明する割り当て方法の両方を使うことも考えられます。

3. Address Space

3. アドレス空間

A multicast address with the prefix 234/8 indicates that the address is a Unicast-Based Multicast (UBM) address. The remaining 24 bits are used as follows:

プレフィックス234/8を持つマルチキャストアドレスは、そのアドレスがユニキャストベースマルチキャスト（Unicast-Based Multicast、UBM）アドレスであることを示します。残りの24ビットは次のように使われます。

Bits:  |   0 thru 7   |         8 thru N        |   N+1 thru 31   |
       +-------+--------------------+-----------------------------+
Value: |     234      |      Unicast Prefix     |    Group ID     |
       +-------+--------------------+-----------------------------+

Bits:  |   0 thru 7   |         8 thru N        |   N+1 thru 31   |
       +-------+--------------------+-----------------------------+
Value: |     234      |      Unicast Prefix     |    Group ID     |
       +-------+--------------------+-----------------------------+

For organizations with a /24 or shorter prefix, the unicast prefix of the organization is appended to the common /8. Any remaining bits may be assigned by any mechanism the organization wishes.

プレフィックス長が/24以下の組織の場合、その組織のユニキャストプレフィックスが共通の/8の後に付加されます。残りのビットは、組織が望む任意のメカニズムで割り当てられます。

For example, an organization that has a /16 prefix assigned might choose to assign multicast addresses manually from the /24 multicast prefix derived from the above method. Alternatively, the organization might choose to delegate the use of multicast addresses to individual subnets that have a /24 or shorter unicast prefix, or it might choose some other method.

たとえば、/16のプレフィックスを割り当てられた組織は、上記の方法で導出される/24のマルチキャストプレフィックスから、マルチキャストアドレスを手作業で割り当てることを選ぶかもしれません。あるいは、その組織は、/24以下のユニキャストプレフィックスを持つ個々のサブネットにマルチキャストアドレスの使用を委任することを選ぶかもしれませんし、他の方法を選ぶかもしれません。

Organizations with a prefix length longer than 24 do not receive any multicast address space from this mechanism; in such cases, another mechanism must be used.

プレフィックス長が24を超える組織は、このメカニズムからマルチキャストアドレス空間を一切受け取りません。そのような場合は、別のメカニズムを使わなければなりません。

Compared to GLOP, an AS will receive more address space via this mechanism if it has more than a /16 for unicast space. An AS will receive less address space than it does from GLOP if it has less than a /16.

GLOPと比べると、ASは、ユニキャスト空間として/16より大きな空間を持っている場合、このメカニズムによってより多くのアドレス空間を受け取ります。ASが/16より小さな空間しか持っていない場合は、GLOPから受け取るよりも少ないアドレス空間しか受け取りません。

The organization that is assigned a UBM address can be determined by taking the multicast address, shifting it left by 8 bits, and identifying who has been assigned the address space covering the resulting unicast address.

UBMアドレスを割り当てられた組織は、マルチキャストアドレスを8ビット左にシフトし、その結果得られるユニキャストアドレスを含むアドレス空間が誰に割り当てられているかを特定することで、判別できます。

The embedded unicast prefix MUST be a global unicast prefix (i.e., no loopback, multicast, link-local, or private-use IP address space). In addition, since global unicast addresses are not permanently assigned, UBM addresses MUST NOT be hard-coded in applications.

埋め込まれるユニキャストプレフィックスは、グローバルユニキャストプレフィックスでなければなりません（MUST）（すなわち、ループバック、マルチキャスト、リンクローカル、プライベート用のIPアドレス空間ではないもの）。さらに、グローバルユニキャストアドレスは恒久的に割り当てられるものではないので、UBMアドレスをアプリケーションにハードコードしてはなりません（MUST NOT）。

4. Examples

4. 例

The following are a few examples of the structure of unicast-prefix-based multicast addresses.

ユニキャストプレフィックスに基づくマルチキャストアドレスの構造の例をいくつか次に示します。

  • Consider an organization that has been assigned the global unicast address space 192.0.2.0/24. This means that organization can use the global multicast address 234.192.0.2 without coordinating with any other entity. Someone who sees this multicast address and wants to find who is using it can mentally shift the address left by 8 bits to get 192.0.2.0, and can then look up who has been assigned unicast address space that includes that address.
  • Consider an organization that has been assigned a larger address space, x.y.0.0/16. This organization can use the global multicast address space 234.x.y.0/24 without coordinating with any other entity, and can assign addresses within this space by any mechanism the organization wishes. Someone who sees a multicast address (say) 234.x.y.10 and wants to find who is using it can mentally shift the address left by 8 bits to get x.y.10.0, and can then look up who has been assigned unicast address space that includes that address.
  • グローバルユニキャストアドレス空間192.0.2.0/24を割り当てられた組織を考えます。これは、その組織が他のエンティティーと調整することなく、グローバルマルチキャストアドレス234.192.0.2を使えることを意味します。このマルチキャストアドレスを見て、誰が使っているかを知りたい人は、頭の中でアドレスを8ビット左にシフトして192.0.2.0を得てから、そのアドレスを含むユニキャストアドレス空間が誰に割り当てられているかを調べられます。
  • より大きなアドレス空間x.y.0.0/16を割り当てられた組織を考えます。この組織は、他のエンティティーと調整することなく、グローバルマルチキャストアドレス空間234.x.y.0/24を使え、組織が望む任意のメカニズムでこの空間内のアドレスを割り当てられます。たとえば234.x.y.10というマルチキャストアドレスを見て、誰が使っているかを知りたい人は、頭の中でアドレスを8ビット左にシフトしてx.y.10.0を得てから、そのアドレスを含むユニキャストアドレス空間が誰に割り当てられているかを調べられます。

5. Security Considerations

5. セキュリティーに関する考慮事項

The same well-known intra-domain security techniques can be applied as with GLOP. Furthermore, when dynamic allocation is used within a prefix, the approach described here may have the effect of reduced exposure to denial-of-service attacks, since the topological area within which nodes compete for addresses within the same prefix is reduced from an entire AS to only within an individual organization or an even smaller area.

GLOPと同じ、よく知られたドメイン内のセキュリティー技術を適用できます。さらに、プレフィックス内で動的な割り当てを使う場合、ここで説明する方式には、サービス拒否攻撃にさらされる危険を減らす効果がある可能性があります。同じプレフィックス内のアドレスをノードが奪い合うトポロジー上の範囲が、AS全体から、個々の組織内だけ、あるいはさらに小さな範囲に縮小されるからです。

6. IANA Considerations

6. IANAに関する考慮事項

IANA has assigned a /8 in the global IPv4 multicast address space for this purpose.

IANAは、この目的のために、グローバルなIPv4マルチキャストアドレス空間内の/8を割り当てました。
