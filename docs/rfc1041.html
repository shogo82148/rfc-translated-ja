RFC 1041

Telnet 3270 Regime Option

RFC 1041

Telnetの3270レジームオプション

Status of This Memo

このメモのステータス

This RFC specifies a proposed standard for the Internet community. Hosts on the Internet, that want to support 3270 data stream within the Telnet protocol, are expected to adopt and implement this standard. Distribution of this memo is unlimited.

このRFCは、インターネットコミュニティーのための標準案を規定します。Telnetプロトコルの中で3270データストリームをサポートしたいインターネット上のホストは、この標準を採用して実装することが期待されます。このメモの配布は無制限です。

1. Command Name and Code

1. コマンド名とコード

3270-REGIME 29

3270-REGIME 29

2. Command Meaning

2. コマンドの意味

IAC WILL 3270-REGIME
Sender is willing to send list of supported 3270 Regimes in a subsequent sub-negotiation.
IAC WON'T 3270-REGIME
Sender refuses to send the list of supported 3270 Regimes.
IAC DO 3270-REGIME
Sender is willing to receive a list of supported 3270 Regimes in a subsequent sub-negotiation.
IAC DON'T 3270-REGIME
Sender refuses to accept the list of supported 3270 Regimes.
IAC SB 3270-REGIME ARE REGIME-LIST IAC SE

Sender sends the list of all possible 3270 Regimes it is able to support. The code for ARE is 1.

REGIME-LIST is an ASCII string which has meaning to both sides of the negotiation. This string may be composed of different terminal type names (as specified in the "Assigned Numbers") which are separated by space character. Terminal type names which have imbedded spaces should escape it with backslash character ('\'). Backslash character imbedded into terminal type name should be escaped with another backslash character.

Empty REGIME-LIST means, that sender is able to support only NVT ASCII terminal as defined in [4].

IAC SB 3270-REGIME IS REGIME IAC SE

Sender is stating the name of the terminal it is willing to support. The code for IS is 0.

REGIME is an ASCII string (possibly empty) which is substring of the received REGIME-LIST string. Empty string means that the sender is willing to support only NVT ASCII terminal as defined in [4].

IAC WILL 3270-REGIME
送信者は、後続のサブネゴシエーションで、サポートする3270レジームの一覧を送信する意思があります。
IAC WON'T 3270-REGIME
送信者は、サポートする3270レジームの一覧を送信することを拒否します。
IAC DO 3270-REGIME
送信者は、後続のサブネゴシエーションで、サポートする3270レジームの一覧を受信する意思があります。
IAC DON'T 3270-REGIME
送信者は、サポートする3270レジームの一覧を受け入れることを拒否します。
IAC SB 3270-REGIME ARE REGIME-LIST IAC SE

送信者は、自身がサポートできる可能性のあるすべての3270レジームの一覧を送信します。AREのコードは1です。

REGIME-LISTは、ネゴシエーションの両側にとって意味を持つASCII文字列です。この文字列は、（「Assigned Numbers」で規定されている）さまざまな端末タイプ名を空白文字で区切って並べたものにできます。空白を含む端末タイプ名では、その空白をバックスラッシュ文字（'\'）でエスケープすべきです。端末タイプ名に含まれるバックスラッシュ文字は、もう1つのバックスラッシュ文字でエスケープすべきです。

空のREGIME-LISTは、送信者が[4]で定義されているNVT ASCII端末しかサポートできないことを意味します。

IAC SB 3270-REGIME IS REGIME IAC SE

送信者は、自身がサポートする意思のある端末の名前を伝えています。ISのコードは0です。

REGIMEは、受信したREGIME-LIST文字列の部分文字列であるASCII文字列（空の場合もあります）です。空文字列は、送信者が[4]で定義されているNVT ASCII端末だけをサポートする意思があることを意味します。

3. Default

3. デフォルト

WON'T 3270-REGIME
3270 Regime will not be established.
DON'T 3270-REGIME
3270 Regime will not be established.
WON'T 3270-REGIME
3270レジームは確立されません。
DON'T 3270-REGIME
3270レジームは確立されません。

4. Motivation for the option

4. このオプションの動機

This option allows a telnet server running VM or MVS to negotiate with the telnet client on the type of data stream (3270 or NVT ASCII) which both sides are willing support.

このオプションを使うと、VMやMVSで動作するtelnetサーバーは、両側が使う意思のあるデータストリームの種類（3270またはNVT ASCII）について、telnetクライアントとネゴシエーションできます。

The main reason for this option is to allow simple and efficient way to:

このオプションの主な目的は、次のことを簡単かつ効率的に行えるようにすることです。

  • state, that both client and server want to exchange 3270 data stream,
  • switch from 3270 Regime into NVT ASCII Regime and back into 3270 Regime,
  • dynamically renegotiate 3270 Regime parameters (like terminal type).
  • クライアントとサーバーの両方が3270データストリームを交換したいことを表明する。
  • 3270レジームからNVT ASCIIレジームに切り替え、また3270レジームに戻す。
  • （端末タイプのような）3270レジームのパラメーターを動的に再ネゴシエーションする。

Support for 3270 data stream requires that both sides:

3270データストリームをサポートするには、両側が次のことをできる必要があります。

  • be able to exchange binary data,
  • be able to put well defined delimiters into inbound/outbound data stream,
  • be able to establish the agreement between client and server on what type of terminal will be used.
  • バイナリーデータを交換できること。
  • インバウンド／アウトバウンドのデータストリームに、明確に定義された区切り文字を入れられること。
  • どの種類の端末を使うかについて、クライアントとサーバーの間で合意を確立できること。

Current implementations requires 3 different options, TERMINALTYPE [1], BINARY [2] and EOR [3], to be successfully negotiated between client and server prior to establishing 3270 Regime. Moreover, it is unclear at what point in this negotiation process, 3270 regime is actually established (whether after TERMINALTYPE or after BINARY or after EOR). Also, order for these negotiations was never specified.

現在の実装では、3270レジームを確立する前に、TERMINALTYPE[1]、BINARY[2]、EOR[3]という3つの異なるオプションのネゴシエーションをクライアントとサーバーの間で成功させる必要があります。さらに、このネゴシエーションの過程のどの時点で3270レジームが実際に確立されるのか（TERMINALTYPEの後なのか、BINARYの後なのか、EORの後なのか）も明確ではありません。また、これらのネゴシエーションの順序も規定されたことがありません。

Subnegotiation for the TERMINALTYPE is possible with only single terminal type at a time.

TERMINALTYPEのサブネゴシエーションでは、一度に1つの端末タイプしか扱えません。

Once 3270 Regime is established, there is no standard of how to get out of this regime back into NVT ASCII mode.

いったん3270レジームが確立されると、このレジームを抜けてNVT ASCIIモードに戻る方法についての標準はありません。

Based on the 3270 Regime requirements, which stated above, we feel that separate negotiation for EOR and BINARY should not be done. Rather, 3270 Regime establishment should imply that:

上で述べた3270レジームの要件に基づき、私たちはEORとBINARYのネゴシエーションを別々に行うべきではないと考えます。むしろ、3270レジームの確立は次のことを意味するべきです。

  • each character in the Telnet data stream should be interpreted as 8 bits of binary data,
  • both sides agreed to use a certain character sequence(Telnet IAC EOR) as a delimiter in inbound/outbound Telnet data stream,
  • both sides agreed on the type of the terminal they are willing to support.
  • Telnetデータストリームの各文字を、8ビットのバイナリーデータとして解釈する。
  • 両側は、インバウンド／アウトバウンドのTelnetデータストリームの区切りとして、特定の文字の並び（Telnet IAC EOR）を使うことに合意している。
  • 両側は、サポートする意思のある端末の種類について合意している。

By providing the list of possible terminals which Telnet client can support, telnet server could select the type of the terminal it can support and pass it back to the Telnet client, thus eliminating multiple TERMINALTYPE negotiations.

Telnetクライアントがサポートできる端末の一覧を提供することで、telnetサーバーは自身がサポートできる端末の種類を選んでTelnetクライアントに返すことができ、TERMINALTYPEのネゴシエーションを何度も行う必要がなくなります。

As stated in [5], "The purpose of the Telnet Protocol is to provide a fairly general, bi-directional, eight-bit byte oriented communication facility." Therefore we feel that such issues as color support, graphics support, extended data streams mapping, etc., do not belong logically to the Telnet protocol, but rather should be considered as a part of a separate protocol which defines 3270 inbound/outbound data stream (see [5], [6], [7], [8]). The purpose of this memo is not to describe (or define) protocols which are used in 3270 Regime, but rather define a new option for the Telnet Protocol, which would allow both sides to negotiate for the 3270 Regime establishment over the telnet connection.

[5]で述べられているように、「Telnetプロトコルの目的は、かなり汎用的で、双方向の、8ビットバイト指向の通信機能を提供することです。」したがって私たちは、カラーのサポート、グラフィックスのサポート、拡張データストリームのマッピングなどの問題は、論理的にはTelnetプロトコルに属するものではなく、3270のインバウンド／アウトバウンドのデータストリームを定義する別のプロトコルの一部として考えるべきだと考えます（[5]、[6]、[7]、[8]を参照）。このメモの目的は、3270レジームで使われるプロトコルを記述（または定義）することではなく、telnetコネクション上で3270レジームの確立について両側がネゴシエーションできるようにする、Telnetプロトコルの新しいオプションを定義することです。

While this options does not include direct negotiation for such things as colors, graphics, structured fields, etc., certain features (like the ability to support colors) may be negotiated indirectly by using certain terminal type names specified in 3270-REGIME subnegotiation.

このオプションには、カラー、グラフィックス、構造化フィールドなどの直接のネゴシエーションは含まれていませんが、3270-REGIMEのサブネゴシエーションで特定の端末タイプ名を指定することで、（カラーをサポートする能力のような）特定の機能を間接的にネゴシエーションできます。

We also feel that such issues as keyboard mapping, whether to have one telnet for both ASCII and 3270 mode or two separate programs, one for ASCII and another for 3270 mode, are implementation dependent and should be considered as a local matter.

また私たちは、キーボードのマッピングや、ASCIIモードと3270モードの両方に1つのtelnetを使うか、ASCII用と3270用の2つの別々のプログラムを使うかといった問題は実装に依存するものであり、ローカルな問題として考えるべきだと考えます。

5. Description of the Option

5. このオプションの説明

WILL and DO commands are used to obtain and grant permission for the subsequent subnegotiation. Both sides must exchange WILL 3270-REGIME and DO 3270-REGIME prior to subnegotiation. The actual exchange of information is done within the option subcommand (IAC SB 3270-REGIME).

WILLコマンドとDOコマンドは、後続のサブネゴシエーションの許可を得たり与えたりするために使われます。両側は、サブネゴシエーションの前にWILL 3270-REGIMEとDO 3270-REGIMEを交換しなければなりません。情報の実際の交換は、オプションのサブコマンド（IAC SB 3270-REGIME）の中で行われます。

Either Telnet client or Telnet server can initialize 3270-REGIME negotiation. However, in order to simplify negotiation, only Telnet client is allowed to send IAC SB 3270-REGIME ARE... IAC SE command, and only Telnet server is allowed to reply with IAC SB 3270-REGIME IS... IAC SE command.

3270-REGIMEのネゴシエーションは、TelnetクライアントとTelnetサーバーのどちらからでも開始できます。ただし、ネゴシエーションを簡単にするため、IAC SB 3270-REGIME ARE... IAC SEコマンドを送信できるのはTelnetクライアントだけであり、IAC SB 3270-REGIME IS... IAC SEコマンドで応答できるのはTelnetサーバーだけです。

Since this negotiation is asymmetric, each time Telnet client/server decide to negotiate/renegotiate this option they have to perform complete negotiation process (DO... WILL... SB 3270-REGIME...).

このネゴシエーションは非対称なので、Telnetクライアント／サーバーがこのオプションのネゴシエーション／再ネゴシエーションを行うことにしたときは、毎回ネゴシエーションの過程全体（DO... WILL... SB 3270-REGIME...）を実行する必要があります。

The following is an example of use of the option:

このオプションの使用例を次に示します。

  1. Host A: IAC DO 3270-REGIME
  2. Host B: IAC WILL 3270-REGIME
  3. Host B: IAC DO 3270-REGIME
  4. Host A: IAC WILL 3270-REGIME
  5. (At this point side which runs Telnet client can start subnegotiation.)
  6. Host A: IAC SB 3270-REGIME ARE 'ibm3279-3 ibm3279-2 ibm3278-3' IAC SE
  7. Host B: IAC SB 3270-REGIME IS 'ibm3279-2' IAC SE
  1. Host A: IAC DO 3270-REGIME
  2. Host B: IAC WILL 3270-REGIME
  3. Host B: IAC DO 3270-REGIME
  4. Host A: IAC WILL 3270-REGIME
  5. （この時点で、Telnetクライアントを動かしている側がサブネゴシエーションを開始できます。）
  6. Host A: IAC SB 3270-REGIME ARE 'ibm3279-3 ibm3279-2 ibm3278-3' IAC SE
  7. Host B: IAC SB 3270-REGIME IS 'ibm3279-2' IAC SE

6. Implementation Suggestions

6. 実装上の提案

If the side is able to support more that one terminal type, then terminal type names are listed in REGIME-LIST from most desirable to least desirable. Other side upon receive of the REGIME-LIST scans it from left to right and finds the first terminal type which it is able to support returns it in REGIME part of the 3270-REGIME IS subnegotiation.

ある側が複数の端末タイプをサポートできる場合、REGIME-LISTには端末タイプ名を最も望ましいものから最も望ましくないものの順に並べます。REGIME-LISTを受信した相手側は、それを左から右に走査し、自身がサポートできる最初の端末タイプを見つけて、3270-REGIME ISサブネゴシエーションのREGIME部分で返します。

The side which wants to switch into NVT ASCII mode should send empty REGIME-LIST. Since empty string is a subset of empty string, the side which receives empty REGIME-LIST should reply with empty REGIME. At that point both sides are switched to NVT ASCII mode.

NVT ASCIIモードに切り替えたい側は、空のREGIME-LISTを送信すべきです。空文字列は空文字列の部分集合なので、空のREGIME-LISTを受信した側は空のREGIMEで応答すべきです。この時点で、両側はNVT ASCIIモードに切り替わります。

It is possible to renegotiate 3270 Regime parameters (like terminal type). Certain precaution should be taken to insure that such renegotiation would not cause switch into NVT ASCII mode. As a possible measure, the side which wants to renegotiate for another terminal should include both the current and the new terminal type names into REGIME-LIST. This way, if the other side is unable to change 3270 Regime terminal type, it will continue to use current terminal type.

（端末タイプのような）3270レジームのパラメーターを再ネゴシエーションすることもできます。そのような再ネゴシエーションによってNVT ASCIIモードに切り替わってしまわないよう、一定の注意を払うべきです。考えられる対策の1つとして、別の端末への再ネゴシエーションを望む側は、現在の端末タイプ名と新しい端末タイプ名の両方をREGIME-LISTに含めるべきです。こうすれば、相手側が3270レジームの端末タイプを変更できない場合でも、現在の端末タイプを使い続けられます。

Since IAC character (255 decimal) is used as a delimiter (together with EOR) in inbound/outbound data stream, care must be taken to escape IAC characters which are part of data stream itself with another IAC character.

IAC文字（10進数で255）は、インバウンド／アウトバウンドのデータストリームで（EORとともに）区切り文字として使われるため、データストリーム自体の一部であるIAC文字は、もう1つのIAC文字でエスケープするよう注意しなければなりません。

To prevent ambiguity in interpreting inbound/outbound data stream during negotiation process the following rules should be observed:

ネゴシエーションの過程でインバウンド／アウトバウンドのデータストリームの解釈があいまいにならないよう、次の規則を守るべきです。

  1. Telnet client should not accept any data from the user as soon as it enters 3270 Regime negotiation.
  2. Telnet client should not send any data to the Telnet server after it sends "3270-REGIME ARE....".
  3. Telnet server should try not to send any data to the telnet client while negotiation is in progress.
  4. Telnet server may reply with "3270-REGIME IS..." to the telnet client only after all outstanding data have been already sent to the Telnet client.
  5. Telnet server can switch from its previous regime to the new regime only after it sends "IAC SB 3270-REGIME IS 'regime' IAC SE" to the telnet client.
  6. Telnet client can switch from its previous regime to the new regime only after it receives "IAC SB 3270-REGIME IS 'regime' IAC SE".
  7. Switch from one regime to another may require flushing of all outstanding data in both telnet client and telnet server.
  1. Telnetクライアントは、3270レジームのネゴシエーションに入ったらすぐに、ユーザーからのデータを受け付けないようにすべきです。
  2. Telnetクライアントは、「3270-REGIME ARE....」を送信した後は、Telnetサーバーにデータを送信すべきではありません。
  3. Telnetサーバーは、ネゴシエーションの進行中はtelnetクライアントにデータを送信しないよう努めるべきです。
  4. Telnetサーバーは、未送信のデータをすべてTelnetクライアントに送信し終えた後でのみ、telnetクライアントに「3270-REGIME IS...」で応答してもかまいません。
  5. Telnetサーバーは、telnetクライアントに「IAC SB 3270-REGIME IS 'regime' IAC SE」を送信した後でのみ、以前のレジームから新しいレジームに切り替えることができます。
  6. Telnetクライアントは、「IAC SB 3270-REGIME IS 'regime' IAC SE」を受信した後でのみ、以前のレジームから新しいレジームに切り替えることができます。
  7. あるレジームから別のレジームへの切り替えでは、telnetクライアントとtelnetサーバーの両方で、未送信のデータをすべてフラッシュする必要がある場合があります。
