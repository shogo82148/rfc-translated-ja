RFC 7946

The GeoJSON Format

RFC 7946

GeoJSONフォーマット

Abstract

概要

GeoJSON is a geospatial data interchange format based on JavaScript Object Notation (JSON). It defines several types of JSON objects and the manner in which they are combined to represent data about geographic features, their properties, and their spatial extents. GeoJSON uses a geographic coordinate reference system, World Geodetic System 1984, and units of decimal degrees.

GeoJSONは、JavaScript Object Notation（JSON）に基づく地理空間データの交換形式です。GeoJSONは、いくつかの種類のJSONオブジェクトと、地理的地物（feature）、その属性、およびその空間的範囲に関するデータを表現するためにそれらを組み合わせる方法を定義します。GeoJSONは、地理座標参照系である世界測地系1984（World Geodetic System 1984）と、10進数の度（decimal degrees）の単位を使用します。

1. Introduction

1. はじめに

GeoJSON is a format for encoding a variety of geographic data structures using JavaScript Object Notation (JSON) [RFC7159]. A GeoJSON object may represent a region of space (a Geometry), a spatially bounded entity (a Feature), or a list of Features (a FeatureCollection). GeoJSON supports the following geometry types: Point, LineString, Polygon, MultiPoint, MultiLineString, MultiPolygon, and GeometryCollection. Features in GeoJSON contain a Geometry object and additional properties, and a FeatureCollection contains a list of Features.

GeoJSONは、JavaScript Object Notation（JSON）[RFC7159]を使用して、さまざまな地理データ構造をエンコードするための形式です。GeoJSONオブジェクトは、空間の領域（Geometry）、空間的に境界づけられたエンティティー（Feature）、またはFeatureのリスト（FeatureCollection）を表すことができます。GeoJSONは、次のジオメトリータイプをサポートします：Point、LineString、Polygon、MultiPoint、MultiLineString、MultiPolygon、およびGeometryCollection。GeoJSONのFeatureは、Geometryオブジェクトと追加のプロパティーを含み、FeatureCollectionはFeatureのリストを含みます。

The format is concerned with geographic data in the broadest sense; anything with qualities that are bounded in geographical space might be a Feature whether or not it is a physical structure. The concepts in GeoJSON are not new; they are derived from preexisting open geographic information system standards and have been streamlined to better suit web application development using JSON.

この形式は、最も広い意味での地理データを扱います。地理空間内で境界づけられた性質を持つものはすべて、物理的な構造物であるかどうかにかかわらず、Featureとなりえます。GeoJSONの概念は新しいものではありません。これらは既存のオープンな地理情報システムの標準に由来しており、JSONを使用したWebアプリケーション開発により適するように簡素化されています。

GeoJSON comprises the seven concrete geometry types defined in the OpenGIS Simple Features Implementation Specification for SQL [SFSQL]: 0-dimensional Point and MultiPoint; 1-dimensional curve LineString and MultiLineString; 2-dimensional surface Polygon and MultiPolygon; and the heterogeneous GeometryCollection. GeoJSON representations of instances of these geometry types are analogous to the well-known binary (WKB) and well-known text (WKT) representations described in that same specification.

GeoJSONは、OpenGIS Simple Features Implementation Specification for SQL [SFSQL]で定義されている7つの具象ジオメトリータイプから構成されます。すなわち、0次元のPointとMultiPoint、1次元の曲線であるLineStringとMultiLineString、2次元の面であるPolygonとMultiPolygon、そして異種混合のGeometryCollectionです。これらのジオメトリータイプのインスタンスのGeoJSON表現は、同じ仕様で説明されているWell-Known Binary（WKB）表現およびWell-Known Text（WKT）表現に類似しています。

GeoJSON also comprises the types Feature and FeatureCollection. Feature objects in GeoJSON contain a Geometry object with one of the above geometry types and additional members. A FeatureCollection object contains an array of Feature objects. This structure is analogous to that of the Web Feature Service (WFS) response to GetFeatures requests specified in [WFSv1] or to a Keyhole Markup Language (KML) Folder of Placemarks [KMLv2.2]. Some implementations of the WFS specification also provide GeoJSON-formatted responses to GetFeature requests, but there is no particular service model or Feature type ontology implied in the GeoJSON format specification.

GeoJSONは、FeatureとFeatureCollectionというタイプも含みます。GeoJSONのFeatureオブジェクトは、上記のジオメトリータイプのいずれかを持つGeometryオブジェクトと、追加のメンバーを含みます。FeatureCollectionオブジェクトは、Featureオブジェクトの配列を含みます。この構造は、[WFSv1]で規定されているGetFeaturesリクエストに対するWeb Feature Service（WFS）のレスポンスや、Keyhole Markup Language（KML）のPlacemarkのFolder [KMLv2.2]の構造に類似しています。WFS仕様の一部の実装は、GetFeatureリクエストに対してGeoJSON形式のレスポンスも提供していますが、GeoJSONフォーマット仕様は特定のサービスモデルやFeatureタイプのオントロジーを前提としていません。

Since its initial publication in 2008 [GJ2008], the GeoJSON format specification has steadily grown in popularity. It is widely used in JavaScript web-mapping libraries, JSON-based document databases, and web APIs.

2008年の最初の公開[GJ2008]以来、GeoJSONフォーマット仕様は着実に普及してきました。GeoJSONは、JavaScriptのWebマッピングライブラリー、JSONベースのドキュメントデータベース、およびWeb APIで広く使用されています。

1.4. Definitions

1.4. 定義

  • JavaScript Object Notation (JSON), and the terms object, member, name, value, array, number, true, false, and null, are to be interpreted as defined in [RFC7159].
  • Inside this document, the term "geometry type" refers to seven case-sensitive strings: "Point", "MultiPoint", "LineString", "MultiLineString", "Polygon", "MultiPolygon", and "GeometryCollection".
  • As another shorthand notation, the term "GeoJSON types" refers to nine case-sensitive strings: "Feature", "FeatureCollection", and the geometry types listed above.
  • The word "Collection" in "FeatureCollection" and "GeometryCollection" does not have any significance for the semantics of array members. The "features" and "geometries" members, respectively, of these objects are standard ordered JSON arrays, not unordered sets.
  • JavaScript Object Notation（JSON）、ならびにobject、member、name、value、array、number、true、false、nullという用語は、[RFC7159]で定義されているとおりに解釈されるものとします。
  • この文書において、「ジオメトリータイプ（geometry type）」という用語は、大文字と小文字を区別する7つの文字列「Point」、「MultiPoint」、「LineString」、「MultiLineString」、「Polygon」、「MultiPolygon」、および「GeometryCollection」を指します。
  • もう1つの略記として、「GeoJSONタイプ（GeoJSON types）」という用語は、大文字と小文字を区別する9つの文字列、すなわち「Feature」、「FeatureCollection」、および上記のジオメトリータイプを指します。
  • 「FeatureCollection」および「GeometryCollection」の「Collection」という語は、配列のメンバーのセマンティクスに対して何の意味も持ちません。これらのオブジェクトのそれぞれの「features」メンバーと「geometries」メンバーは、順序付けられた標準のJSON配列であり、順序のない集合ではありません。

2. GeoJSON Text

2. GeoJSONテキスト

A GeoJSON text is a JSON text and consists of a single GeoJSON object.

GeoJSONテキストはJSONテキストであり、単一のGeoJSONオブジェクトから構成されます。

3. GeoJSON Object

3. GeoJSONオブジェクト

A GeoJSON object represents a Geometry, Feature, or collection of Features.

GeoJSONオブジェクトは、Geometry、Feature、またはFeatureのコレクションを表します。

  • A GeoJSON object is a JSON object.
  • A GeoJSON object has a member with the name "type". The value of the member MUST be one of the GeoJSON types.
  • A GeoJSON object MAY have a "bbox" member, the value of which MUST be a bounding box array (see Section 5).
  • A GeoJSON object MAY have other members (see Section 6).
  • GeoJSONオブジェクトはJSONオブジェクトです。
  • GeoJSONオブジェクトは、「type」という名前のメンバーを持ちます。このメンバーの値は、GeoJSONタイプのいずれかでなければなりません（MUST）。
  • GeoJSONオブジェクトは、「bbox」メンバーを持ってもよいです（MAY）。その値はバウンディングボックスの配列でなければなりません（MUST）（セクション5を参照）。
  • GeoJSONオブジェクトは、その他のメンバーを持ってもよいです（MAY）（セクション6を参照）。

3.1. Geometry Object

3.1. Geometryオブジェクト

A Geometry object represents points, curves, and surfaces in coordinate space. Every Geometry object is a GeoJSON object no matter where it occurs in a GeoJSON text.

Geometryオブジェクトは、座標空間における点、曲線、および面を表します。すべてのGeometryオブジェクトは、GeoJSONテキスト内のどこに出現するかにかかわらず、GeoJSONオブジェクトです。

  • The value of a Geometry object's "type" member MUST be one of the seven geometry types (see Section 1.4).
  • A GeoJSON Geometry object of any type other than "GeometryCollection" has a member with the name "coordinates". The value of the "coordinates" member is an array. The structure of the elements in this array is determined by the type of geometry. GeoJSON processors MAY interpret Geometry objects with empty "coordinates" arrays as null objects.
  • Geometryオブジェクトの「type」メンバーの値は、7つのジオメトリータイプのいずれかでなければなりません（MUST）（セクション1.4を参照）。
  • 「GeometryCollection」以外のタイプのGeoJSON Geometryオブジェクトは、「coordinates」という名前のメンバーを持ちます。「coordinates」メンバーの値は配列です。この配列の要素の構造は、ジオメトリーのタイプによって決まります。GeoJSONプロセッサーは、空の「coordinates」配列を持つGeometryオブジェクトをnullオブジェクトとして解釈してもよいです（MAY）。

3.1.1. Position

3.1.1. 位置（Position）

A position is the fundamental geometry construct. The "coordinates" member of a Geometry object is composed of either:

位置（position）は、ジオメトリーの基本的な構成要素です。Geometryオブジェクトの「coordinates」メンバーは、次のいずれかから構成されます：

  • one position in the case of a Point geometry,
  • an array of positions in the case of a LineString or MultiPoint geometry,
  • an array of LineString or linear ring (see Section 3.1.6) coordinates in the case of a Polygon or MultiLineString geometry, or
  • an array of Polygon coordinates in the case of a MultiPolygon geometry.
  • Pointジオメトリーの場合は、1つの位置
  • LineStringまたはMultiPointジオメトリーの場合は、位置の配列
  • PolygonまたはMultiLineStringジオメトリーの場合は、LineStringまたは線形リング（セクション3.1.6を参照）の座標の配列
  • MultiPolygonジオメトリーの場合は、Polygonの座標の配列

A position is an array of numbers. There MUST be two or more elements. The first two elements are longitude and latitude, or easting and northing, precisely in that order and using decimal numbers. Altitude or elevation MAY be included as an optional third element.

位置は数値の配列です。要素は2つ以上でなければなりません（MUST）。最初の2つの要素は、経度と緯度、または東距（easting）と北距（northing）であり、厳密にこの順序で、10進数を使用します。高度（altitude）または標高（elevation）を、任意の3番目の要素として含めてもよいです（MAY）。

Implementations SHOULD NOT extend positions beyond three elements because the semantics of extra elements are unspecified and ambiguous. Historically, some implementations have used a fourth element to carry a linear referencing measure (sometimes denoted as "M") or a numerical timestamp, but in most situations a parser will not be able to properly interpret these values. The interpretation and meaning of additional elements is beyond the scope of this specification, and additional elements MAY be ignored by parsers.

追加の要素のセマンティクスは規定されておらず曖昧であるため、実装は位置を3つの要素を超えて拡張すべきではありません（SHOULD NOT）。歴史的には、一部の実装が4番目の要素を使用して線形参照の測定値（「M」と表記されることがあります）や数値のタイムスタンプを運んできましたが、ほとんどの状況では、パーサーはこれらの値を適切に解釈できません。追加の要素の解釈と意味はこの仕様の範囲外であり、パーサーは追加の要素を無視してもよいです（MAY）。

A line between two positions is a straight Cartesian line, the shortest line between those two points in the coordinate reference system (see Section 4).

2つの位置の間の線は、デカルト座標における直線であり、座標参照系（セクション4を参照）における2点間の最短の線です。

In other words, every point on a line that does not cross the antimeridian between a point (lon0, lat0) and (lon1, lat1) can be calculated as

言い換えると、点（lon0, lat0）と（lon1, lat1）の間の、反子午線（antimeridian）を横切らない線上のすべての点は、次のように計算できます。

F(lon, lat) = (lon0 + (lon1 - lon0) * t, lat0 + (lat1 - lat0) * t)

F(lon, lat) = (lon0 + (lon1 - lon0) * t, lat0 + (lat1 - lat0) * t)

with t being a real number greater than or equal to 0 and smaller than or equal to 1. Note that this line may markedly differ from the geodesic path along the curved surface of the reference ellipsoid.

ここで、tは0以上1以下の実数です。この線は、準拠楕円体の曲面に沿った測地線の経路とは著しく異なる場合があることに注意してください。

The same applies to the optional height element with the proviso that the direction of the height is as specified in the coordinate reference system.

任意の高さの要素にも同じことが当てはまりますが、高さの方向は座標参照系で規定されているとおりであるという条件が付きます。

Note that, again, this does not mean that a surface with equal height follows, for example, the curvature of a body of water. Nor is a surface of equal height perpendicular to a plumb line.

繰り返しになりますが、これは、高さが等しい面が、たとえば水域の曲率に沿うということを意味するわけではないことに注意してください。また、高さが等しい面は、鉛直線に対して垂直であるわけでもありません。

Examples of positions and geometries are provided in Appendix A, "Geometry Examples".

位置とジオメトリーの例は、付録A「ジオメトリーの例」に示しています。

3.1.6. Polygon

3.1.6. Polygon

To specify a constraint specific to Polygons, it is useful to introduce the concept of a linear ring:

Polygonに固有の制約を規定するために、線形リング（linear ring）の概念を導入すると便利です：

  • A linear ring is a closed LineString with four or more positions.
  • The first and last positions are equivalent, and they MUST contain identical values; their representation SHOULD also be identical.
  • A linear ring is the boundary of a surface or the boundary of a hole in a surface.
  • A linear ring MUST follow the right-hand rule with respect to the area it bounds, i.e., exterior rings are counterclockwise, and holes are clockwise.
  • 線形リングは、4つ以上の位置を持つ閉じたLineStringです。
  • 最初と最後の位置は等価であり、同一の値を含まなければなりません（MUST）。それらの表現も同一であるべきです（SHOULD）。
  • 線形リングは、面の境界、または面の中の穴の境界です。
  • 線形リングは、それが囲む領域に関して右手の法則に従わなければなりません（MUST）。つまり、外側のリングは反時計回り、穴は時計回りです。

Note: the [GJ2008] specification did not discuss linear ring winding order. For backwards compatibility, parsers SHOULD NOT reject Polygons that do not follow the right-hand rule.

注：[GJ2008]の仕様では、線形リングの巻き順については論じていませんでした。後方互換性のため、パーサーは右手の法則に従わないPolygonを拒否すべきではありません（SHOULD NOT）。

Though a linear ring is not explicitly represented as a GeoJSON geometry type, it leads to a canonical formulation of the Polygon geometry type definition as follows:

線形リングはGeoJSONのジオメトリータイプとして明示的には表現されませんが、線形リングにより、Polygonジオメトリータイプの定義を次のように正規の形で定式化できます：

  • For type "Polygon", the "coordinates" member MUST be an array of linear ring coordinate arrays.
  • For Polygons with more than one of these rings, the first MUST be the exterior ring, and any others MUST be interior rings. The exterior ring bounds the surface, and the interior rings (if present) bound holes within the surface.
  • タイプ「Polygon」の場合、「coordinates」メンバーは線形リングの座標配列の配列でなければなりません（MUST）。
  • このようなリングを2つ以上持つPolygonでは、最初のリングは外側のリングでなければなりません（MUST）。それ以外のリングは内側のリングでなければなりません（MUST）。外側のリングは面の境界となり、内側のリングは（存在する場合）面の中の穴の境界となります。

3.1.8. GeometryCollection

3.1.8. GeometryCollection

A GeoJSON object with type "GeometryCollection" is a Geometry object. A GeometryCollection has a member with the name "geometries". The value of "geometries" is an array. Each element of this array is a GeoJSON Geometry object. It is possible for this array to be empty.

タイプ「GeometryCollection」を持つGeoJSONオブジェクトは、Geometryオブジェクトです。GeometryCollectionは、「geometries」という名前のメンバーを持ちます。「geometries」の値は配列です。この配列の各要素はGeoJSON Geometryオブジェクトです。この配列は空でもかまいません。

Unlike the other geometry types described above, a GeometryCollection can be a heterogeneous composition of smaller Geometry objects. For example, a Geometry object in the shape of a lowercase roman "i" can be composed of one point and one LineString.

上で説明した他のジオメトリータイプとは異なり、GeometryCollectionは、より小さなGeometryオブジェクトの異種混合の組み合わせにすることができます。たとえば、小文字のローマ字「i」の形をしたGeometryオブジェクトは、1つの点と1つのLineStringで構成できます。

GeometryCollections have a different syntax from single type Geometry objects (Point, LineString, and Polygon) and homogeneously typed multipart Geometry objects (MultiPoint, MultiLineString, and MultiPolygon) but have no different semantics. Although a GeometryCollection object has no "coordinates" member, it does have coordinates: the coordinates of all its parts belong to the collection. The "geometries" member of a GeometryCollection describes the parts of this composition. Implementations SHOULD NOT apply any additional semantics to the "geometries" array.

GeometryCollectionは、単一タイプのGeometryオブジェクト（Point、LineString、およびPolygon）や、同種のタイプからなるマルチパートのGeometryオブジェクト（MultiPoint、MultiLineString、およびMultiPolygon）とは構文が異なりますが、セマンティクスは変わりません。GeometryCollectionオブジェクトは「coordinates」メンバーを持ちませんが、座標は持ちます。すべての部分の座標がそのコレクションに属します。GeometryCollectionの「geometries」メンバーは、この組み合わせの部分を記述します。実装は、「geometries」配列に追加のセマンティクスを適用すべきではありません（SHOULD NOT）。

To maximize interoperability, implementations SHOULD avoid nested GeometryCollections. Furthermore, GeometryCollections composed of a single part or a number of parts of a single type SHOULD be avoided when that single part or a single object of multipart type (MultiPoint, MultiLineString, or MultiPolygon) could be used instead.

相互運用性を最大化するため、実装はGeometryCollectionの入れ子を避けるべきです（SHOULD）。さらに、単一の部分または単一タイプの複数の部分から構成されるGeometryCollectionは、代わりにその単一の部分、またはマルチパートタイプ（MultiPoint、MultiLineString、またはMultiPolygon）の単一のオブジェクトを使用できる場合には、避けるべきです（SHOULD）。

3.1.9. Antimeridian Cutting

3.1.9. 反子午線での分割

In representing Features that cross the antimeridian, interoperability is improved by modifying their geometry. Any geometry that crosses the antimeridian SHOULD be represented by cutting it in two such that neither part's representation crosses the antimeridian.

反子午線を横切るFeatureを表現する際には、そのジオメトリーを変更することで相互運用性が向上します。反子午線を横切るジオメトリーは、どちらの部分の表現も反子午線を横切らないように2つに分割して表現すべきです（SHOULD）。

For example, a line extending from 45 degrees N, 170 degrees E across the antimeridian to 45 degrees N, 170 degrees W should be cut in two and represented as a MultiLineString.

たとえば、北緯45度・東経170度から反子午線を越えて北緯45度・西経170度まで延びる線は、2つに分割してMultiLineStringとして表現すべきです。

{
    "type": "MultiLineString",
    "coordinates": [
        [
            [170.0, 45.0], [180.0, 45.0]
        ], [
            [-180.0, 45.0], [-170.0, 45.0]
        ]
    ]
}

{
    "type": "MultiLineString",

        [
            [170.0, 45.0], [180.0, 45.0]
        ], [
            [-180.0, 45.0], [-170.0, 45.0]
        ]
    ]
}

A rectangle extending from 40 degrees N, 170 degrees E across the antimeridian to 50 degrees N, 170 degrees W should be cut in two and represented as a MultiPolygon.

北緯40度・東経170度から反子午線を越えて北緯50度・西経170度まで広がる長方形は、2つに分割してMultiPolygonとして表現すべきです。

{

    "coordinates": [
        [
            [
                [180.0, 40.0], [180.0, 50.0], [170.0, 50.0],
                [170.0, 40.0], [180.0, 40.0]
            ]
        ],
        [
            [
                [-170.0, 40.0], [-170.0, 50.0], [-180.0, 50.0],
                [-180.0, 40.0], [-170.0, 40.0]
            ]
        ]
    ]
}

{

    "coordinates": [
        [
            [
                [180.0, 40.0], [180.0, 50.0], [170.0, 50.0],

3.2. Feature Object

3.2. Featureオブジェクト

A Feature object represents a spatially bounded thing. Every Feature object is a GeoJSON object no matter where it occurs in a GeoJSON text.

Featureオブジェクトは、空間的に境界づけられたものを表します。すべてのFeatureオブジェクトは、GeoJSONテキスト内のどこに出現するかにかかわらず、GeoJSONオブジェクトです。

  • A Feature object has a "type" member with the value "Feature".
  • A Feature object has a member with the name "geometry". The value of the geometry member SHALL be either a Geometry object as defined above or, in the case that the Feature is unlocated, a JSON null value.
  • A Feature object has a member with the name "properties". The value of the properties member is an object (any JSON object or a JSON null value).
  • If a Feature has a commonly used identifier, that identifier SHOULD be included as a member of the Feature object with the name "id", and the value of this member is either a JSON string or number.
  • Featureオブジェクトは、値が「Feature」である「type」メンバーを持ちます。
  • Featureオブジェクトは、「geometry」という名前のメンバーを持ちます。geometryメンバーの値は、上で定義したGeometryオブジェクトか、Featureが位置を持たない場合はJSONのnull値の、いずれかとすることになります（SHALL）。
  • Featureオブジェクトは、「properties」という名前のメンバーを持ちます。propertiesメンバーの値はオブジェクト（任意のJSONオブジェクト、またはJSONのnull値）です。
  • Featureが一般に使用される識別子を持つ場合、その識別子を「id」という名前のメンバーとしてFeatureオブジェクトに含めるべきです（SHOULD）。このメンバーの値は、JSONの文字列または数値のいずれかです。

4. Coordinate Reference System

4. 座標参照系

The coordinate reference system for all GeoJSON coordinates is a geographic coordinate reference system, using the World Geodetic System 1984 (WGS 84) [WGS84] datum, with longitude and latitude units of decimal degrees. This is equivalent to the coordinate reference system identified by the Open Geospatial Consortium (OGC) URN urn:ogc:def:crs:OGC::CRS84. An OPTIONAL third-position element SHALL be the height in meters above or below the WGS 84 reference ellipsoid. In the absence of elevation values, applications sensitive to height or depth SHOULD interpret positions as being at local ground or sea level.

すべてのGeoJSON座標の座標参照系は、世界測地系1984（WGS 84）[WGS84]の測地基準系（datum）を使用し、経度と緯度の単位を10進数の度とする地理座標参照系です。これは、Open Geospatial Consortium（OGC）のURN urn:ogc:def:crs:OGC::CRS84で識別される座標参照系と同等です。選択可能な（OPTIONAL）3番目の位置の要素は、WGS 84の準拠楕円体からの上方または下方の高さをメートル単位で表すものとすることになります（SHALL）。標高の値がない場合、高さや深さを考慮するアプリケーションは、位置を現地の地表面または海面にあるものとして解釈すべきです（SHOULD）。

Note: the use of alternative coordinate reference systems was specified in [GJ2008], but it has been removed from this version of the specification because the use of different coordinate reference systems -- especially in the manner specified in [GJ2008] -- has proven to have interoperability issues. In general, GeoJSON processing software is not expected to have access to coordinate reference system databases or to have network access to coordinate reference system transformation parameters. However, where all involved parties have a prior arrangement, alternative coordinate reference systems can be used without risk of data being misinterpreted.

注：代替の座標参照系の使用は[GJ2008]で規定されていましたが、異なる座標参照系の使用は、特に[GJ2008]で規定された方法では、相互運用性の問題があることが判明したため、この版の仕様からは削除されました。一般に、GeoJSONを処理するソフトウェアは、座標参照系のデータベースにアクセスできたり、座標参照系の変換パラメーターにネットワーク経由でアクセスできたりすることは期待されていません。ただし、関係するすべての当事者が事前に取り決めている場合には、データが誤って解釈される危険なしに代替の座標参照系を使用できます。

5. Bounding Box

5. バウンディングボックス

A GeoJSON object MAY have a member named "bbox" to include information on the coordinate range for its Geometries, Features, or FeatureCollections. The value of the bbox member MUST be an array of length 2*n where n is the number of dimensions represented in the contained geometries, with all axes of the most southwesterly point followed by all axes of the more northeasterly point. The axes order of a bbox follows the axes order of geometries.

GeoJSONオブジェクトは、そのGeometry、Feature、またはFeatureCollectionの座標の範囲に関する情報を含めるために、「bbox」という名前のメンバーを持ってもよいです（MAY）。bboxメンバーの値は長さ2*nの配列でなければなりません（MUST）。ここでnは、含まれるジオメトリーで表現されている次元の数であり、配列には最も南西の点のすべての軸の値が並び、その後に最も北東の点のすべての軸の値が続きます。bboxの軸の順序は、ジオメトリーの軸の順序に従います。

The "bbox" values define shapes with edges that follow lines of constant longitude, latitude, and elevation.

「bbox」の値は、経度、緯度、および標高が一定の線に沿った辺を持つ形状を定義します。

Featureにおける2次元のbboxメンバーの例：

5.1. The Connecting Lines

5.1. 結ぶ線

The four lines of the bounding box are defined fully within the coordinate reference system; that is, for a box bounded by the values "west", "south", "east", and "north", every point on the northernmost line can be expressed as

バウンディングボックスの4本の線は、完全に座標参照系の中で定義されます。つまり、値「west」、「south」、「east」、および「north」で囲まれたボックスについて、最も北の線上のすべての点は次のように表すことができます。

(lon, lat) = (west + (east - west) * t, north)

(lon, lat) = (west + (east - west) * t, north)

with 0 <= t <= 1.

ここで、0 <= t <= 1です。

5.2. The Antimeridian

5.2. 反子午線

Consider a set of point Features within the Fiji archipelago, straddling the antimeridian between 16 degrees S and 20 degrees S. The southwest corner of the box containing these Features is at 20 degrees S and 177 degrees E, and the northwest corner is at 16 degrees S and 178 degrees W. The antimeridian-spanning GeoJSON bounding box for this FeatureCollection is

フィジー諸島内にあり、南緯16度から南緯20度の間で反子午線をまたぐ、点のFeatureの集合を考えます。これらのFeatureを含むボックスの南西の角は南緯20度・東経177度にあり、北西の角は南緯16度・西経178度にあります。このFeatureCollectionの、反子午線をまたぐGeoJSONのバウンディングボックスは次のとおりであり、

"bbox": [177.0, -20.0, -178.0, -16.0]

"bbox": [177.0, -20.0, -178.0, -16.0]

and covers 5 degrees of longitude.

経度5度の範囲をカバーします。

同じ緯度帯について、反子午線を横切らない補完的なバウンディングボックスは次のとおりであり、

"bbox": [-178.0, -20.0, 177.0, -16.0]

"bbox": [-178.0, -20.0, 177.0, -16.0]

and covers 355 degrees of longitude.

経度355度の範囲をカバーします。

The latitude of the northeast corner is always greater than the latitude of the southwest corner, but bounding boxes that cross the antimeridian have a northeast corner longitude that is less than the longitude of the southwest corner.

北東の角の緯度は常に南西の角の緯度よりも大きくなりますが、反子午線を横切るバウンディングボックスでは、北東の角の経度が南西の角の経度よりも小さくなります。

北極を含むバウンディングボックスは、北緯「minlat」度・西経180度の南西の角から、北緯90度・東経180度の北東の角まで広がります。地球儀上で見ると、このバウンディングボックスは、「minlat」の緯線で囲まれた球冠に近似します。

"bbox": [-180.0, minlat, 180.0, 90.0]

南極を含むバウンディングボックスは、南緯90度・西経180度の南西の角から、南緯「maxlat」度・東経180度の北東の角まで広がります。

Similarly, a bounding box that just touches the South Pole and forms a slice of an approximate spherical cap when viewed on a globe has the following representation in GeoJSON.

同様に、南極にちょうど接し、地球儀上で見ると近似的な球冠の一切れを形づくるバウンディングボックスは、GeoJSONでは次のように表現されます。

"bbox": [westlon, -90.0, eastlon, maxlat]

"bbox": [westlon, -90.0, eastlon, maxlat]

Implementers MUST NOT use latitude values greater than 90 or less than -90 to imply an extent that is not a spherical cap.

実装者は、球冠ではない範囲を示すために、90より大きい緯度の値や-90より小さい緯度の値を使用してはなりません（MUST NOT）。

6. Extending GeoJSON

6. GeoJSONの拡張

6.1. Foreign Members

6.1. 外部メンバー

Members not described in this specification ("foreign members") MAY be used in a GeoJSON document. Note that support for foreign members can vary across implementations, and no normative processing model for foreign members is defined. Accordingly, implementations that rely too heavily on the use of foreign members might experience reduced interoperability with other implementations.

この仕様で説明されていないメンバー（「外部メンバー（foreign members）」）をGeoJSON文書で使用してもよいです（MAY）。外部メンバーのサポートは実装によって異なる可能性があり、外部メンバーに対する規範的な処理モデルは定義されていないことに注意してください。したがって、外部メンバーの使用に過度に依存する実装では、他の実装との相互運用性が低下する可能性があります。

For example, in the (abridged) Feature object shown below

たとえば、以下に示す（省略した）Featureオブジェクトでは、

{
    "type": "Feature",
    "id": "f1",
    "geometry": {...},
    "properties": {...},
    "title": "Example Feature"
}

{
    "type": "Feature",
    "id": "f1",
    "geometry": {...},
    "properties": {...},
    "title": "Example Feature"
}

the name/value pair of "title": "Example Feature" is a foreign member. When the value of a foreign member is an object, all the descendant members of that object are themselves foreign members.

名前と値のペア「"title": "Example Feature"」が外部メンバーです。外部メンバーの値がオブジェクトである場合、そのオブジェクトの子孫のメンバーもすべて外部メンバーです。

GeoJSON semantics do not apply to foreign members and their descendants, regardless of their names and values. For example, in the (abridged) Feature object below

GeoJSONのセマンティクスは、名前や値にかかわらず、外部メンバーとその子孫には適用されません。たとえば、以下の（省略した）Featureオブジェクトでは、

{
    "type": "Feature",
    "id": "f2",
    "geometry": {...},
    "properties": {...},
    "centerline": {
        "type": "LineString",
        "coordinates": [
            [-170, 10],
            [170, 11]
        ]
    }
}

{
    "type": "Feature",
    "id": "f2",
    "geometry": {...},
    "properties": {...},
    "centerline": {
        "type": "LineString",
        "coordinates": [
            [-170, 10],
            [170, 11]
        ]
    }
}

the "centerline" member is not a GeoJSON Geometry object.

「centerline」メンバーはGeoJSON Geometryオブジェクトではありません。

7. GeoJSON Types Are Not Extensible

7. GeoJSONタイプは拡張できない

Implementations MUST NOT extend the fixed set of GeoJSON types: FeatureCollection, Feature, Point, LineString, MultiPoint, Polygon, MultiLineString, MultiPolygon, and GeometryCollection.

実装は、GeoJSONタイプの固定された集合（FeatureCollection、Feature、Point、LineString、MultiPoint、Polygon、MultiLineString、MultiPolygon、およびGeometryCollection）を拡張してはなりません（MUST NOT）。

7.1. Semantics of GeoJSON Members and Types Are Not Changeable

7.1. GeoJSONのメンバーとタイプのセマンティクスは変更できない

Implementations MUST NOT change the semantics of GeoJSON members and types.

実装は、GeoJSONのメンバーとタイプのセマンティクスを変更してはなりません（MUST NOT）。

The GeoJSON "coordinates" and "geometries" members define Geometry objects. FeatureCollection and Feature objects, respectively, MUST NOT contain a "coordinates" or "geometries" member.

GeoJSONの「coordinates」メンバーと「geometries」メンバーは、Geometryオブジェクトを定義します。FeatureCollectionオブジェクトとFeatureオブジェクトは、それぞれ「coordinates」メンバーや「geometries」メンバーを含んではなりません（MUST NOT）。

The GeoJSON "geometry" and "properties" members define a Feature object. FeatureCollection and Geometry objects, respectively, MUST NOT contain a "geometry" or "properties" member.

GeoJSONの「geometry」メンバーと「properties」メンバーは、Featureオブジェクトを定義します。FeatureCollectionオブジェクトとGeometryオブジェクトは、それぞれ「geometry」メンバーや「properties」メンバーを含んではなりません（MUST NOT）。

The GeoJSON "features" member defines a FeatureCollection object. Feature and Geometry objects, respectively, MUST NOT contain a "features" member.

GeoJSONの「features」メンバーは、FeatureCollectionオブジェクトを定義します。FeatureオブジェクトとGeometryオブジェクトは、それぞれ「features」メンバーを含んではなりません（MUST NOT）。

8. Versioning

8. バージョン管理

The GeoJSON format can be extended as defined here, but no explicit versioning scheme is defined. A specification that alters the semantics of GeoJSON members or otherwise modifies the format does not create a new version of this format; instead, it defines an entirely new format that MUST NOT be identified as GeoJSON.

GeoJSON形式はここで定義されているとおりに拡張できますが、明示的なバージョン管理の方式は定義されていません。GeoJSONのメンバーのセマンティクスを変更したり、その他の方法でこの形式を変更したりする仕様は、この形式の新しいバージョンを作成するのではなく、まったく新しい形式を定義することになります。その形式をGeoJSONとして識別してはなりません（MUST NOT）。

9. Mapping 'geo' URIs

9. 'geo' URIの対応付け

'geo' URIs [RFC5870] identify geographic locations and precise (not uncertain) locations can be mapped to GeoJSON Geometry objects.

'geo' URI [RFC5870]は地理的な場所を識別します。精密な（不確かさのない）場所は、GeoJSON Geometryオブジェクトに対応付けることができます。

For this section, as in [RFC5870], "lat", "lon", "alt", and "unc" are placeholders for 'geo' URI latitude, longitude, altitude, and uncertainty values, respectively.

このセクションでは、[RFC5870]と同様に、「lat」、「lon」、「alt」、および「unc」は、それぞれ'geo' URIの緯度、経度、高度、および不確かさの値のプレースホルダーです。

A 'geo' URI with two coordinates and an uncertainty ('u') parameter that is absent or zero, and a GeoJSON Point geometry may be mapped to each other. A GeoJSON Point is always converted to a 'geo' URI that has no uncertainty parameter.

2つの座標を持ち、不確かさ（'u'）パラメーターが存在しないかゼロである'geo' URIと、GeoJSONのPointジオメトリーとは、相互に対応付けることができます。GeoJSONのPointは、常に不確かさパラメーターを持たない'geo' URIに変換されます。

'geo' URI:

'geo' URI：

geo:lat,lon

geo:lat,lon

GeoJSON:

GeoJSON：

{"type": "Point", "coordinates": [lon, lat]}

{"type": "Point", "coordinates": [lon, lat]}

The mapping between 'geo' URIs and GeoJSON Points that specify elevation is shown below.

'geo' URIと、標高を指定するGeoJSONのPointとの間の対応付けを以下に示します。

'geo' URI:

'geo' URI：

geo:lat,lon,alt

geo:lat,lon,alt

GeoJSON:

GeoJSON：

{"type": "Point", "coordinates": [lon, lat, alt]}

{"type": "Point", "coordinates": [lon, lat, alt]}

GeoJSON has no concept of uncertainty; imprecise or uncertain 'geo' URIs thus cannot be mapped to GeoJSON geometries.

GeoJSONには不確かさの概念がありません。したがって、不正確な、または不確かさのある'geo' URIは、GeoJSONのジオメトリーに対応付けることはできません。

10. Security Considerations

10. セキュリティーに関する考慮事項

GeoJSON shares security issues common to all JSON content types. See [RFC7159], Section 12 for additional information. GeoJSON does not provide executable content.

GeoJSONは、すべてのJSONコンテンツタイプに共通するセキュリティー上の問題を共有しています。詳しい情報については、[RFC7159], セクション12を参照してください。GeoJSONは実行可能なコンテンツを提供しません。

GeoJSON does not provide privacy or integrity services. If sensitive data requires privacy or integrity protection, those must be provided by the transport -- for example, Transport Layer Security (TLS) or HTTPS. There will be cases in which stored data need protection, which is out of scope for this document.

GeoJSONは、プライバシーや完全性のサービスを提供しません。機密データがプライバシーや完全性の保護を必要とする場合、それらはトランスポート（たとえば、Transport Layer Security（TLS）やHTTPS）によって提供されなければなりません。保存されたデータが保護を必要とする場合もありますが、それはこの文書の範囲外です。

As with other geographic data formats, e.g., [KMLv2.2], providing details about the locations of sensitive persons, animals, habitats, and facilities can expose them to unauthorized tracking or injury. Data providers should recognize the risk of inadvertently identifying individuals if locations in anonymized datasets are not adequately skewed or not sufficiently fuzzed [Sweeney] and recognize that the effectiveness of location obscuration is limited by a number of factors and is unlikely to be an effective defense against a determined attack [RFC6772].

他の地理データ形式（たとえば[KMLv2.2]）と同様に、配慮を要する人物、動物、生息地、および施設の場所に関する詳細を提供すると、それらを無許可の追跡や危害にさらす可能性があります。データ提供者は、匿名化されたデータセット内の場所が適切に歪められていなかったり、十分にぼかされていなかったりする場合に、意図せず個人が特定されるリスク[Sweeney]を認識すべきです。また、場所の秘匿の有効性は多くの要因によって制限され、断固とした攻撃に対する効果的な防御にはなりにくいこと[RFC6772]も認識すべきです。

11. 相互運用性に関する考慮事項

11.1. I-JSON

11.1. I-JSON

GeoJSON texts should follow the constraints of Internet JSON (I-JSON) [RFC7493] for maximum interoperability.

相互運用性を最大化するため、GeoJSONテキストはInternet JSON（I-JSON）[RFC7493]の制約に従うべきです。

11.2. Coordinate Precision

11.2. 座標の精度

The size of a GeoJSON text in bytes is a major interoperability consideration, and precision of coordinate values has a large impact on the size of texts. A GeoJSON text containing many detailed Polygons can be inflated almost by a factor of two by increasing coordinate precision from 6 to 15 decimal places. For geographic coordinates with units of degrees, 6 decimal places (a default common in, e.g., sprintf) amounts to about 10 centimeters, a precision well within that of current GPS systems. Implementations should consider the cost of using a greater precision than necessary.

GeoJSONテキストのバイト単位のサイズは相互運用性に関する主要な考慮事項であり、座標値の精度はテキストのサイズに大きな影響を与えます。詳細なPolygonを多数含むGeoJSONテキストは、座標の精度を小数点以下6桁から15桁に増やすと、サイズがほぼ2倍に膨れ上がる可能性があります。単位が度である地理座標では、小数点以下6桁（たとえばsprintfでよく使われるデフォルト）は約10センチメートルに相当し、現在のGPSシステムの精度の範囲に十分収まる精度です。実装は、必要以上の精度を使用することのコストを考慮すべきです。

Furthermore, the WGS 84 [WGS84] datum is a relatively coarse approximation of the geoid, with the height varying by up to 5 m (but generally between 2 and 3 meters) higher or lower relative to a surface parallel to Earth's mean sea level.

さらに、WGS 84 [WGS84]の測地基準系はジオイドの比較的粗い近似であり、地球の平均海面に平行な面に対して、高さは最大5m（ただし一般的には2〜3メートル）上下に変動します。

Appendix B. Changes from the Pre-IETF GeoJSON Format Specification

付録B. IETF以前のGeoJSONフォーマット仕様からの変更

This appendix briefly summarizes non-editorial changes from the 2008 specification [GJ2008].

この付録では、2008年の仕様[GJ2008]からの編集上のものではない変更を簡潔にまとめます。

B.1. Normative Changes

B.1. 規範的な変更

  • Specification of coordinate reference systems has been removed, i.e., the "crs" member of [GJ2008] is no longer used.
  • In the absence of elevation values, applications sensitive to height or depth SHOULD interpret positions as being at local ground or sea level (see Section 4).
  • Implementations SHOULD NOT extend position arrays beyond 3 elements (see Section 3.1.1).
  • A line between two positions is a straight Cartesian line (see Section 3.1.1).
  • Polygon rings MUST follow the right-hand rule for orientation (counterclockwise external rings, clockwise internal rings).
  • The values of a "bbox" array are "[west, south, east, north]", not "[minx, miny, maxx, maxy]" (see Section 5).
  • A Feature object's "id" member is a string or number (see Section 3.2).
  • Extensions MAY be used, but MUST NOT change the semantics of GeoJSON members and types (see Section 6).
  • GeoJSON objects MUST NOT contain the defining members of other types (see Section 7.1).
  • The media type for GeoJSON is "application/geo+json".
  • 座標参照系の指定は削除されました。つまり、[GJ2008]の「crs」メンバーはもはや使用されません。
  • 標高の値がない場合、高さや深さを考慮するアプリケーションは、位置を現地の地表面または海面にあるものとして解釈すべきです（SHOULD）（セクション4を参照）。
  • 実装は、位置の配列を3つの要素を超えて拡張すべきではありません（SHOULD NOT）（セクション3.1.1を参照）。
  • 2つの位置の間の線は、デカルト座標における直線です（セクション3.1.1を参照）。
  • Polygonのリングは、向きについて右手の法則に従わなければなりません（MUST）（外側のリングは反時計回り、内側のリングは時計回り）。
  • 「bbox」配列の値は「[minx, miny, maxx, maxy]」ではなく、「[west, south, east, north]」です（セクション5を参照）。
  • Featureオブジェクトの「id」メンバーは、文字列または数値です（セクション3.2を参照）。
  • 拡張を使用してもよいです（MAY）。ただし、拡張はGeoJSONのメンバーとタイプのセマンティクスを変更してはなりません（MUST NOT）（セクション6を参照）。
  • GeoJSONオブジェクトは、他のタイプを定義するメンバーを含んではなりません（MUST NOT）（セクション7.1を参照）。
  • GeoJSONのメディアタイプは「application/geo+json」です。

B.2. Informative Changes

B.2. 参考情報としての変更

  • The definition of a GeoJSON text has been added.
  • Rules for mapping 'geo' URIs have been added.
  • A recommendation of the I-JSON [RFC7493] constraints has been added.
  • Implementers are cautioned about the effect of excessive coordinate precision on interoperability.
  • Interoperability concerns of GeometryCollections are noted. These objects should be used sparingly (see Section 3.1.8).
  • GeoJSONテキストの定義が追加されました。
  • 'geo' URIを対応付けるための規則が追加されました。
  • I-JSON [RFC7493]の制約に従うことの推奨が追加されました。
  • 過剰な座標の精度が相互運用性に与える影響について、実装者に注意を促しています。
  • GeometryCollectionの相互運用性に関する懸念について言及しています。これらのオブジェクトは控えめに使用すべきです（セクション3.1.8を参照）。

Appendix C. GeoJSON Text Sequences

付録C. GeoJSONテキストシーケンス

All GeoJSON objects defined in this specification -- FeatureCollection, Feature, and Geometry -- consist of exactly one JSON object. However, there may be circumstances in which applications need to represent sets or sequences of these objects (over and above the grouping of Feature objects in a FeatureCollection), e.g., in order to efficiently "stream" large numbers of Feature objects. The definition of such sets or sequences is outside the scope of this specification.

この仕様で定義されているすべてのGeoJSONオブジェクト（FeatureCollection、Feature、およびGeometry）は、ちょうど1つのJSONオブジェクトから構成されます。しかし、アプリケーションがこれらのオブジェクトの集合やシーケンスを（FeatureCollectionによるFeatureオブジェクトのグループ化とは別に）表現する必要がある状況もありえます。たとえば、大量のFeatureオブジェクトを効率的に「ストリーム」するためなどです。そのような集合やシーケンスの定義は、この仕様の範囲外です。

If such a representation is needed, a new media type is required that has the ability to represent these sets or sequences. When defining such a media type, it may be useful to base it on "JavaScript Object Notation (JSON) Text Sequences" [RFC7464], leaving the foundations of how to represent multiple JSON objects to that specification, and only defining how it applies to GeoJSON objects.

そのような表現が必要な場合は、これらの集合やシーケンスを表現する能力を持つ新しいメディアタイプが必要です。そのようなメディアタイプを定義する際には、「JavaScript Object Notation (JSON) Text Sequences」[RFC7464]を基礎とし、複数のJSONオブジェクトを表現する方法の基盤はその仕様に任せて、それをGeoJSONオブジェクトにどう適用するかだけを定義するのが有用な場合があります。
