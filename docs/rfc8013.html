Forwarding and Control Element Separation (ForCES) Inter-FE Logical Functional Block (LFB)

RFC 8013

Forwarding and Control Element Separation（ForCES）のInter-FE論理機能ブロック（LFB）

Abstract

概要

This document describes how to extend the Forwarding and Control Element Separation (ForCES) Logical Functional Block (LFB) topology across Forwarding Elements (FEs) by defining the inter-FE LFB class. The inter-FE LFB class provides the ability to pass data and metadata across FEs without needing any changes to the ForCES specification. The document focuses on Ethernet transport.

この文書では、inter-FE LFBクラスを定義することにより、Forwarding and Control Element Separation（ForCES）の論理機能ブロック（Logical Functional Block、LFB）トポロジーを複数の転送要素（Forwarding Element、FE）にまたがって拡張する方法を説明します。inter-FE LFBクラスは、ForCES仕様に何の変更も必要とせずに、データとメタデータをFE間で受け渡す能力を提供します。この文書では、イーサネットによるトランスポートに焦点を当てます。

1. Introduction

1. はじめに

In the ForCES architecture, a packet service can be modeled by composing a graph of one or more LFB instances. The reader is referred to the details in the ForCES model [RFC5812].

ForCESアーキテクチャーでは、1つ以上のLFBインスタンスからなるグラフを構成することによって、パケットサービスをモデル化できます。詳細については、ForCESモデル[RFC5812]を参照してください。

The ForCES model describes the processing within a single Forwarding Element (FE) in terms of Logical Functional Blocks (LFBs), including provision for the Control Element (CE) to establish and modify that processing sequence, and the parameters of the individual LFBs.

ForCESモデルは、単一の転送要素（Forwarding Element、FE）内の処理を論理機能ブロック（Logical Functional Block、LFB）の観点から記述しており、制御要素（Control Element、CE）がその処理の順序と個々のLFBのパラメーターを確立・変更するための仕組みも含んでいます。

Under some circumstances, it would be beneficial to be able to extend this view and the resulting processing across more than one FE. This may be in order to achieve scale by splitting the processing across elements or to utilize specialized hardware available on specific FEs.

状況によっては、このビューとその結果としての処理を複数のFEにまたがって拡張できると有益な場合があります。これは、処理を複数の要素に分割することで規模を拡大するためであったり、特定のFEで利用できる専用ハードウェアを活用するためであったりします。

Given that the ForCES inter-LFB architecture calls for the ability to pass metadata between LFBs, it is imperative to define mechanisms to extend that existing feature and allow passing the metadata between LFBs across FEs.

ForCESのLFB間アーキテクチャーではLFB間でメタデータを受け渡す能力が求められていることから、その既存の機能を拡張し、FEをまたいでLFB間でメタデータを受け渡せるようにするメカニズムを定義することが不可欠です。

This document describes how to extend the LFB topology across FEs, i.e., inter-FE connectivity without needing any changes to the ForCES definitions. It focuses on using Ethernet as the interconnection between FEs.

この文書では、LFBトポロジーを複数のFEにまたがって拡張する方法、すなわちForCESの定義に何の変更も必要としないFE間の接続性について説明します。この文書では、FE間の相互接続としてイーサネットを使用することに焦点を当てます。

3. Problem Scope and Use Cases

3. 問題の範囲とユースケース

The scope of this document is to solve the challenge of passing ForCES-defined metadata alongside packet data across FEs (be they physical or virtual) for the purpose of distributing the LFB processing.

この文書の範囲は、LFBの処理を分散させる目的で、ForCESで定義されたメタデータをパケットデータとともに（物理か仮想かを問わず）FE間で受け渡すという課題を解決することです。

3.1. Assumptions

3.1. 前提

  • The FEs involved in the inter-FE LFB belong to the same Network Element (NE) and are within a single administrative private network that is in close proximity.
  • The FEs are already interconnected using Ethernet. We focus on Ethernet because it is commonly used for FE interconnection. Other higher transports (such as UDP over IP) or lower transports could be defined to carry the data and metadata, but these cases are not addressed in this document.
  • inter-FE LFBに関与するFEは、同じネットワーク要素（Network Element、NE）に属しており、近接した単一の管理主体によるプライベートネットワーク内にあります。
  • FEは、すでにイーサネットを使用して相互接続されています。イーサネットはFEの相互接続によく使われているため、イーサネットに焦点を当てます。データとメタデータを運ぶために、ほかの上位のトランスポート（UDP over IPなど）や下位のトランスポートを定義することもできますが、それらの場合はこの文書では扱いません。

3.2. Sample Use Cases

3.2. ユースケースの例

To illustrate the problem scope, we present two use cases where we start with a single FE running all the LFBs functionality and then split it into multiple FEs achieving the same end goals.

問題の範囲を説明するために、2つのユースケースを示します。どちらも、すべてのLFBの機能を実行する単一のFEから始めて、それを同じ最終目標を達成する複数のFEに分割します。

3.2.1. Basic IPv4 Router

3.2.1. 基本的なIPv4ルーター

A sample LFB topology depicted in Figure 1 demonstrates a service graph for delivering a basic IPv4-forwarding service within one FE. For the purpose of illustration, the diagram shows LFB classes as graph nodes instead of multiple LFB class instances.

図1に示すLFBトポロジーの例は、1つのFE内で基本的なIPv4転送サービスを提供するためのサービスグラフを示しています。説明のため、この図では複数のLFBクラスインスタンスの代わりに、LFBクラスをグラフのノードとして示しています。

Since the purpose of the illustration in Figure 1 is to showcase how data and metadata are sent down or upstream on a graph of LFB instances, it abstracts out any ports in both directions and talks about a generic ingress and egress LFB. Again, for illustration purposes, the diagram does not show exception or error paths. Also left out are details on Reverse Path Filtering, ECMP, multicast handling, etc. In other words, this is not meant to be a complete description of an IPv4-forwarding application; for a more complete example, please refer to the LFBLibrary document [RFC6956].

図1の図の目的は、データとメタデータがLFBインスタンスのグラフ上で下流または上流にどのように送られるかを示すことなので、両方向のポートはすべて抽象化し、汎用的なイングレスLFBとイグレスLFBについて述べています。また、説明のため、この図では例外やエラーの経路を示していません。リバースパスフィルタリング、ECMP、マルチキャストの処理などの詳細も省いています。言い換えれば、これはIPv4転送アプリケーションの完全な説明を意図したものではありません。より完全な例については、LFBLibraryの文書[RFC6956]を参照してください。

The output of the ingress LFB(s) coming into the IPv4 Validator LFB will have both the IPv4 packets and, depending on the implementation, a variety of ingress metadata such as offsets into the different headers, any classification metadata, physical and virtual ports encountered, tunneling information, etc. These metadata are lumped together as "ingress metadata".

IPv4 Validator LFBに入ってくるイングレスLFBの出力には、IPv4パケットと、実装に応じたさまざまなイングレスメタデータ（たとえば、各ヘッダーへのオフセット、分類メタデータ、通過した物理ポートと仮想ポート、トンネリング情報など）の両方が含まれます。これらのメタデータをまとめて「イングレスメタデータ」と呼びます。

Once the IPv4 validator vets the packet (for example, it ensures that there is no expired TTL), it feeds the packet and inherited metadata into the IPv4 unicast LPM (Longest-Prefix-Matching) LFB.

IPv4 validatorは、パケットを検査すると（たとえば、TTLが期限切れでないことを確認します）、そのパケットと引き継いだメタデータをIPv4ユニキャストLPM（Longest-Prefix-Matching、最長プレフィックス一致）LFBに渡します。

The IPv4 unicast LPM LFB does an LPM lookup on the IPv4 FIB using the destination IP address as a search key. The result is typically a next-hop selector, which is passed downstream as metadata.

IPv4ユニキャストLPM LFBは、宛先IPアドレスを検索キーとして、IPv4 FIBでLPMルックアップを行います。その結果は通常ネクストホップセレクターであり、メタデータとして下流に渡されます。

The NextHop LFB receives the IPv4 packet with associated next-hop (NH) information metadata. The NextHop LFB consumes the NH information metadata and derives a table index from it to look up the next-hop table in order to find the appropriate egress information. The lookup result is used to build the next-hop details to be used downstream on the egress. This information may include any source and destination information (for our purposes, which Media Access Control (MAC) addresses to use) as well as egress ports. (Note: It is also at this LFB where typically, the forwarding TTL-decrementing and IP checksum recalculation occurs.)

NextHop LFBは、関連するネクストホップ（NH）情報メタデータとともにIPv4パケットを受け取ります。NextHop LFBは、NH情報メタデータを消費し、そこからテーブルインデックスを導出してネクストホップテーブルをルックアップし、適切なイグレス情報を見つけます。ルックアップの結果は、イグレスで下流に使用するネクストホップの詳細情報を構築するために使用されます。この情報には、イグレスポートのほか、送信元と宛先の情報（ここでの目的では、どのMedia Access Control（MAC）アドレスを使用するか）が含まれる場合があります。（注: 転送時のTTLの減算とIPチェックサムの再計算が通常行われるのも、このLFBです。）

The details of the egress LFB are considered out of scope for this discussion. Suffice it to say that somewhere within or beyond the Egress LFB, the IPv4 packet will be sent out a port (e.g., Ethernet, virtual or physical).

イグレスLFBの詳細は、この議論の範囲外とします。Egress LFBの内部またはその先のどこかで、IPv4パケットがポート（たとえば、仮想または物理のイーサネット）から送出される、とだけ言っておけば十分です。

3.2.1.1. 基本的なIPv4ルーターの分散

図2は、図1のルーターのLFBトポロジーを2つのFE（たとえば、2つの特定用途向け集積回路（Application-Specific Integrated Circuit、ASIC））に分割する方法の1つを示しています。図2は、IPv4ユニキャストLPM LFBの後でFE間に分割されたLFBトポロジーを示しています。

This document defines the inter-FE LFB, a standard mechanism for encapsulating, generating, receiving, and decapsulating packets and associated metadata FEs over Ethernet.

この文書では、パケットと関連するメタデータをイーサネット上でFE間でカプセル化、生成、受信、カプセル化解除するための標準メカニズムであるinter-FE LFBを定義します。

4. Inter-FE LFB Overview

4. Inter-FE LFBの概要

We address the inter-FE connectivity requirements by defining the inter-FE LFB class. Using a standard LFB class definition implies no change to the basic ForCES architecture in the form of the core LFBs (FE Protocol or Object LFBs). This design choice was made after considering an alternative approach that would have required changes to both the FE Object capabilities (SupportedLFBs) and the LFBTopology component to describe the inter-FE connectivity capabilities as well as the runtime topology of the LFB instances.

FE間の接続性の要件には、inter-FE LFBクラスを定義することで対処します。標準のLFBクラス定義を使用するということは、コアLFB（FE ProtocolまたはObject LFB）という形の基本的なForCESアーキテクチャーに変更がないことを意味します。この設計上の選択は、別のアプローチを検討した上で行われました。その別のアプローチでは、FE間の接続能力とLFBインスタンスの実行時のトポロジーを記述するために、FE Objectの能力（SupportedLFBs）とLFBTopologyコンポーネントの両方の変更が必要になっていたはずです。

4.1. Inserting the Inter-FE LFB ne 15

4.1. Inter-FE LFBの挿入

The distributed LFB topology described in Figure 2 is re-illustrated in Figure 5 to show the topology location where the inter-FE LFB would fit in.

図2で説明した分散LFBトポロジーを、inter-FE LFBが収まるトポロジー上の位置を示すために、図5で改めて図示します。

As can be observed in Figure 5, the same details passed between IPv4 unicast LPM LFB and the IPv4 NH LFB are passed to the egress side of the inter-FE LFB. This information is illustrated as multiplicity of inputs into the egress inter-FE LFB instance. Each input represents a unique set of selection information.

図5からわかるように、IPv4ユニキャストLPM LFBとIPv4 NH LFBの間で受け渡されるのと同じ詳細情報が、inter-FE LFBのイグレス側に渡されます。この情報は、イグレスinter-FE LFBインスタンスへの複数の入力として図示しています。各入力は、選択情報の一意な集合を表します。

The egress of the inter-FE LFB uses the received packet and metadata to select details for encapsulation when sending messages towards the selected neighboring FE. These details include what to communicate as the source and destination FEs (abstracted as MAC addresses as described in Section 5.2); in addition, the original metadata may be passed along with the original IPv4 packet.

inter-FE LFBのイグレスは、受信したパケットとメタデータを使用して、選択された近隣のFEに向けてメッセージを送信する際のカプセル化の詳細を選択します。これらの詳細には、送信元と宛先のFEとして何を伝えるか（セクション5.2で説明するように、MACアドレスとして抽象化されます）が含まれます。さらに、元のメタデータを元のIPv4パケットとともに渡す場合があります。

On the ingress side of the inter-FE LFB, the received packet and its associated metadata are used to decide the packet graph continuation. This includes which of the original metadata and on which next LFB class instance to continue processing. In Figure 5, an IPv4NextHop LFB instance is selected and the appropriate metadata is passed to it.

inter-FE LFBのイングレス側では、受信したパケットとそれに関連するメタデータを使用して、パケットグラフをどう継続するかを決定します。これには、元のメタデータのうちどれを使用し、次のどのLFBクラスインスタンスで処理を継続するかが含まれます。図5では、IPv4NextHop LFBインスタンスが選択され、適切なメタデータがそれに渡されます。

The ingress side of the inter-FE LFB consumes some of the information passed and passes it the IPv4 packet alongside with the ingress and NHinfo metadata to the IPv4NextHop LFB as was done earlier in both Figures 1 and 2.

inter-FE LFBのイングレス側は、渡された情報の一部を消費し、図1と図2の両方で先に行われていたのと同様に、IPv4パケットをイングレスメタデータおよびNHinfoメタデータとともにIPv4NextHop LFBに渡します。

5. Inter-FE Ethernet Connectivity

5. Inter-FEのイーサネット接続性

Section 5.1 describes some of the issues related to using Ethernet as the transport and how we mitigate them.

セクション5.1では、トランスポートとしてイーサネットを使用することに関連するいくつかの問題と、それらをどのように軽減するかを説明します。

Section 5.2 defines a payload format that is to be used over Ethernet. An existing implementation of this specification that runs on top of Linux Traffic Control [linux-tc] is described in [tc-ife].

セクション5.2では、イーサネット上で使用するペイロードフォーマットを定義します。Linux Traffic Control [linux-tc]の上で動作するこの仕様の既存の実装が、[tc-ife]で説明されています。

5.1. Inter-FE Ethernet Connectivity Issues

5.1. Inter-FEのイーサネット接続性の問題

There are several issues that may occur due to using direct Ethernet encapsulation that need consideration.

イーサネットで直接カプセル化することによって発生する可能性があり、考慮が必要な問題がいくつかあります。

5.1.1. MTU Consideration

5.1.1. MTUに関する考慮事項

Because we are adding data to existing Ethernet frames, MTU issues may arise. We recommend:

既存のイーサネットフレームにデータを追加するため、MTUの問題が発生する可能性があります。次のことを推奨します。

  • Using large MTUs when possible (example with jumbo frames).
  • Limiting the amount of metadata that could be transmitted; our definition allows for filtering of select metadata to be encapsulated in the frame as described in Section 6. We recommend sizing the egress port MTU so as to allow space for maximum size of the metadata total size to allow between FEs. In such a setup, the port is configured to "lie" to the upper layers by claiming to have a lower MTU than it is capable of. Setting the MTU can be achieved by ForCES control of the port LFB (or some other configuration. In essence, the control plane when explicitly making a decision for the MTU settings of the egress port is implicitly deciding how much metadata will be allowed. Caution needs to be exercised on how low the resulting reported link MTU could be: for IPv4 packets, the minimum size is 64 octets [RFC791] and for IPv6 the minimum size is 1280 octets [RFC2460].
  • 可能な場合は大きなMTUを使用すること（たとえばジャンボフレームを使用すること）。
  • 送信される可能性のあるメタデータの量を制限すること。この文書の定義では、セクション6で説明するように、フレームにカプセル化するメタデータを選んでフィルタリングできます。FE間で許容するメタデータの合計サイズの最大値の分の余地ができるように、イグレスポートのMTUのサイズを決めることを推奨します。このような構成では、ポートは、実際に対応できるよりも低いMTUを申告することで、上位層に「嘘をつく」ように設定されます。MTUの設定は、ポートLFBのForCESによる制御（またはほかの何らかの設定）によって実現できます。要するに、コントロールプレーンは、イグレスポートのMTU設定を明示的に決定するとき、どれだけのメタデータを許容するかを暗黙的に決定していることになります。結果として報告されるリンクMTUがどこまで低くなりうるかについては注意が必要です。IPv4パケットの場合、最小サイズは64オクテットであり[RFC791]、IPv6の場合、最小サイズは1280オクテットです[RFC2460]。

5.1.2. Quality-of-Service Considerations

5.1.2. サービス品質に関する考慮事項

A raw packet arriving at the inter-FE LFB (from upstream LFB class instances) may have Class-of-Service (CoS) metadata indicating how it should be treated from a Quality-of-Service perspective.

（上流のLFBクラスインスタンスから）inter-FE LFBに到着する生のパケットには、サービス品質（Quality-of-Service）の観点でそのパケットをどのように扱うべきかを示すサービスクラス（Class-of-Service、CoS）メタデータが付いている場合があります。

The resulting Ethernet frame will be eventually (preferentially) treated by a downstream LFB (typically a port LFB instance) and their CoS marks will be honored in terms of priority. In other words, the presence of the inter-FE LFB does not change the CoS semantics.

結果として得られるイーサネットフレームは、最終的に下流のLFB（通常はポートLFBのインスタンス）によって（優先的に）処理され、そのCoSマークは優先度の点で尊重されます。言い換えれば、inter-FE LFBが存在してもCoSのセマンティクスは変わりません。

5.1.3. Congestion Considerations

5.1.3. 輻輳に関する考慮事項

Most of the traffic passing through FEs that utilize the inter-FE LFB is expected to be IP based, which is generally assumed to be congestion controlled [UDP-GUIDE]. For example, if congestion causes a TCP packet annotated with additional ForCES metadata to be dropped between FEs, the sending TCP can be expected to react in the same fashion as if that packet had been dropped at a different point on its path where ForCES is not involved. For this reason, additional inter-FE congestion-control mechanisms are not specified.

inter-FE LFBを利用するFEを通過するトラフィックの大部分はIPベースであると予想され、IPベースのトラフィックは一般に輻輳制御されているとみなされます[UDP-GUIDE]。たとえば、ForCESメタデータが追加されたTCPパケットが輻輳によってFE間で破棄された場合、送信側のTCPは、ForCESが関与しない経路上の別の地点でそのパケットが破棄された場合と同じように反応すると期待できます。このため、FE間の追加の輻輳制御メカニズムは規定しません。

However, the increased packet size due to the addition of ForCES metadata is likely to require additional bandwidth on inter-FE links in comparison to what would be required to carry the same traffic without ForCES metadata. Therefore, traffic engineering SHOULD be done when deploying inter-FE encapsulation.

ただし、ForCESメタデータの追加によってパケットサイズが増えるため、同じトラフィックをForCESメタデータなしで運ぶ場合に必要となる帯域幅と比べて、FE間のリンクで追加の帯域幅が必要になる可能性が高いです。したがって、inter-FEカプセル化を展開する際には、トラフィックエンジニアリングを行うべきです（SHOULD）。

Furthermore, the inter-FE LFB MUST only be deployed within a single network (with a single network operator) or networks of an adjacent set of cooperating network operators where traffic is managed to avoid congestion. These are Controlled Environments, as defined by Section 3.6 of [UDP-GUIDE]. Additional measures SHOULD be imposed to restrict the impact of inter-FE-encapsulated traffic on other traffic; for example:

さらに、inter-FE LFBは、（単一のネットワーク運用者による）単一のネットワーク内、または輻輳を回避するようにトラフィックが管理されている、協調する隣接したネットワーク運用者の集合のネットワーク内でのみ展開しなければなりません（MUST）。これらは、[UDP-GUIDE]のセクション3.6で定義されている制御された環境（Controlled Environment）です。inter-FEカプセル化されたトラフィックがほかのトラフィックに与える影響を制限するための追加の対策を課すべきです（SHOULD）。たとえば、次のようなものです。

  • rate-limiting all inter-FE LFB traffic at an upstream LFB
  • managing circuit breaking [circuit-b]
  • Isolating the inter-FE traffic either via dedicated interfaces or VLANs
  • 上流のLFBで、すべてのinter-FE LFBトラフィックのレートを制限すること
  • サーキットブレーカー[circuit-b]を管理すること
  • 専用のインターフェイスまたはVLANによって、inter-FEトラフィックを分離すること

5.2. Inter-FE Ethernet Encapsulation

5.2. Inter-FEのイーサネットカプセル化

The Ethernet wire encapsulation is illustrated in Figure 6. The process that leads to this encapsulation is described in Section 6. The resulting frame is 32-bit aligned.

イーサネットでのワイヤー上のカプセル化を図6に示します。このカプセル化に至る処理は、セクション6で説明します。結果として得られるフレームは32ビット境界に整列されます。

The Ethernet header (illustrated in Figure 6) has the following semantics:

（図6に示す）イーサネットヘッダーは、次のセマンティクスを持ちます。

  • The Destination MAC Address is used to identify the Destination FEID by the CE policy (as described in Section 6).
  • The Source MAC Address is used to identify the Source FEID by the CE policy (as described in Section 6).
  • The ethertype is used to identify the frame as inter-FE LFB type. Ethertype ED3E (base 16) is to be used.
  • The 16-bit metadata length is used to describe the total encoded metadata length (including the 16 bits used to encode the metadata length).

  • One or more 16-bit TLV-encoded metadatum follows the Metadata length field. The TLV type identifies the metadata ID. ForCES metadata IDs that have been registered with IANA will be used.

    All TLVs will be 32-bit-aligned. We recognize that using a 16-bit TLV restricts the metadata ID to 16 bits instead of a ForCES-defined component ID space of 32 bits if an Index-Length-Value (ILV) is used. However, at the time of publication, we believe this is sufficient to carry all the information we need; the TLV approach has been selected because it saves us 4 bytes per metadatum transferred as compared to the ILV approach.

  • The original packet data payload is appended at the end of the metadata as shown.
  • Destination MAC Addressは、（セクション6で説明するように）CEのポリシーによって宛先のFEIDを識別するために使用されます。
  • Source MAC Addressは、（セクション6で説明するように）CEのポリシーによって送信元のFEIDを識別するために使用されます。
  • イーサタイプは、そのフレームがinter-FE LFBタイプであることを識別するために使用されます。イーサタイプED3E（16進数）を使用します。
  • 16ビットのメタデータ長は、エンコードされたメタデータの全長（メタデータ長をエンコードするために使用する16ビットを含む）を表すために使用されます。

  • Metadata lengthフィールドの後に、16ビットのTLVでエンコードされたメタデータ項目（metadatum）が1つ以上続きます。TLVのタイプはメタデータIDを識別します。IANAに登録されたForCESのメタデータIDを使用します。

    すべてのTLVは32ビット境界に整列されます。16ビットのTLVを使用すると、Index-Length-Value（ILV）を使用する場合の、ForCESで定義された32ビットのコンポーネントID空間ではなく、メタデータIDが16ビットに制限されることは認識しています。しかし、発行時点では、必要なすべての情報を運ぶにはこれで十分であると考えています。TLVのアプローチを選択したのは、ILVのアプローチと比べて、転送するメタデータ項目ごとに4バイトを節約できるためです。

  • 元のパケットデータのペイロードは、図示したとおり、メタデータの末尾に付加されます。

6. Detailed Description of the Ethernet Inter-FE LFB

6. イーサネットInter-FE LFBの詳細な説明

The Ethernet inter-FE LFB has two LFB input port groups and three LFB output ports as shown in Figure 7.

イーサネットinter-FE LFBは、図7に示すように、2つのLFB入力ポートグループと3つのLFB出力ポートを持ちます。

The inter-FE LFB defines two components used in aiding processing described in Section 6.1.

inter-FE LFBは、セクション6.1で説明する処理を補助するために使用する2つのコンポーネントを定義します。

6.1. Data Handling

6.1. データの処理

The inter-FE LFB (instance) can be positioned at the egress of a source FE. Figure 5 illustrates an example source FE in the form of FE1. In such a case, an inter-FE LFB instance receives, via port group EgressInGroup, a raw packet and associated metadata from the preceding LFB instances. The input information is used to produce a selection of how to generate and encapsulate the new frame. The set of all selections is stored in the LFB component IFETable described further below. The processed encapsulated Ethernet frame will go out on OUT1 to a downstream LFB instance when processing succeeds or to the EXCEPTIONOUT port in the case of failure.

inter-FE LFB（のインスタンス）は、送信元FEのイグレスに配置できます。図5は、FE1という形で送信元FEの例を示しています。このような場合、inter-FE LFBインスタンスは、ポートグループEgressInGroupを介して、先行するLFBインスタンスから生のパケットと関連するメタデータを受け取ります。入力された情報は、新しいフレームをどのように生成してカプセル化するかの選択を生み出すために使用されます。すべての選択の集合は、後述するLFBコンポーネントIFETableに格納されます。処理されてカプセル化されたイーサネットフレームは、処理が成功した場合はOUT1から下流のLFBインスタンスに送出され、失敗した場合はEXCEPTIONOUTポートに送出されます。

The inter-FE LFB (instance) can be positioned at the ingress of a receiving FE. Figure 5 illustrates an example destination FE in the form of FE1. In such a case, an inter-FE LFB receives, via an LFB port in the IngressInGroup, an encapsulated Ethernet frame. Successful processing of the packet will result in a raw packet with associated metadata IDs going downstream to an LFB connected on OUT2. On failure, the data is sent out EXCEPTIONOUT.

inter-FE LFB（のインスタンス）は、受信側FEのイングレスに配置できます。図5は、FE1という形で宛先FEの例を示しています。このような場合、inter-FE LFBは、IngressInGroup内のLFBポートを介して、カプセル化されたイーサネットフレームを受け取ります。パケットの処理が成功すると、生のパケットが、関連するメタデータIDとともに、OUT2に接続されたLFBへと下流に送られます。失敗した場合、データはEXCEPTIONOUTに送出されます。

6.1.1. Egress Processing

6.1.1. イグレスの処理

The egress inter-FE LFB receives packet data and any accompanying metadatum at an LFB port of the LFB instance's input port group labeled EgressInGroup.

イグレスinter-FE LFBは、パケットデータとそれに付随するメタデータ項目を、EgressInGroupというラベルの付いたLFBインスタンスの入力ポートグループのLFBポートで受け取ります。

The LFB implementation may use the incoming LFB port (within the LFB port group EgressInGroup) to map to a table index used to look up the IFETable table.

LFBの実装は、（LFBポートグループEgressInGroup内の）入力元のLFBポートを、IFETableテーブルのルックアップに使用するテーブルインデックスに対応付けるために使用してもかまいません。

If the lookup is successful, a matched table row that has the IFEInfo details is retrieved with the tuple (optional IFETYPE, optional StatId, Destination MAC address (DSTFE), Source MAC address (SRCFE), and optional metafilters). The metafilters lists define a whitelist of which metadatum are to be passed to the neighboring FE. The inter-FE LFB will perform the following actions using the resulting tuple:

ルックアップが成功すると、IFEInfoの詳細を持つ一致したテーブル行が、タプル（省略可能なIFETYPE、省略可能なStatId、宛先MACアドレス（DSTFE）、送信元MACアドレス（SRCFE）、省略可能なメタフィルター）として取得されます。メタフィルターのリストは、どのメタデータ項目を近隣のFEに渡すかの許可リスト（whitelist）を定義します。inter-FE LFBは、得られたタプルを使用して次の動作を行います。

  • Increment statistics for packet and byte count observed at the corresponding IFEStats entry.
  • When the MetaFilterList is present, walk each received metadatum and apply it against the MetaFilterList. If no legitimate metadata is found that needs to be passed downstream, then the processing stops and the packet and metadata are sent out the EXCEPTIONOUT port with the exceptionID of EncapTableLookupFailed [RFC6956].
  • Check that the additional overhead of the Ethernet header and encapsulated metadata will not exceed MTU. If it does, increment the error-packet-count statistics and send the packet and metadata out the EXCEPTIONOUT port with the exceptionID of FragRequired [RFC6956].
  • Create the Ethernet header.
  • Set the Destination MAC address of the Ethernet header with the value found in the DSTFE field.
  • Set the Source MAC address of the Ethernet header with the value found in the SRCFE field.
  • If the optional IFETYPE is present, set the ethertype to the value found in IFETYPE. If IFETYPE is absent, then the standard inter-FE LFB ethertype ED3E (base 16) is used.
  • Encapsulate each allowed metadatum in a TLV. Use the metaID as the "type" field in the TLV header. The TLV should be aligned to 32 bits. This means you may need to add a padding of zeroes at the end of the TLV to ensure alignment.
  • Update the metadata length to the sum of each TLV's space plus 2 bytes (a 16-bit space for the Metadata length field).
  • 対応するIFEStatsエントリーで、観測したパケット数とバイト数の統計を増やします。
  • MetaFilterListが存在する場合は、受信した各メタデータ項目を順に調べ、MetaFilterListと照合します。下流に渡す必要のある正当なメタデータが見つからない場合は、処理を中止して、パケットとメタデータを、exceptionIDをEncapTableLookupFailed [RFC6956]としてEXCEPTIONOUTポートに送出します。
  • イーサネットヘッダーとカプセル化したメタデータによる追加のオーバーヘッドがMTUを超えないことを確認します。超える場合は、エラーパケット数の統計を増やして、パケットとメタデータを、exceptionIDをFragRequired [RFC6956]としてEXCEPTIONOUTポートに送出します。
  • イーサネットヘッダーを作成します。
  • イーサネットヘッダーの宛先MACアドレスに、DSTFEフィールドにある値を設定します。
  • イーサネットヘッダーの送信元MACアドレスに、SRCFEフィールドにある値を設定します。
  • 省略可能なIFETYPEが存在する場合は、イーサタイプにIFETYPEにある値を設定します。IFETYPEが存在しない場合は、標準のinter-FE LFBのイーサタイプED3E（16進数）を使用します。
  • 許可された各メタデータ項目をTLVにカプセル化します。TLVヘッダーの「type」フィールドとしてmetaIDを使用します。TLVは32ビット境界に整列させるべきです。つまり、整列を確保するために、TLVの末尾にゼロのパディングを追加する必要がある場合があります。
  • メタデータ長を、各TLVの領域の合計に2バイト（Metadata lengthフィールドのための16ビットの領域）を加えた値に更新します。

The resulting packet is sent to the next LFB instance connected to the OUT1 LFB-port, typically a port LFB.

結果として得られたパケットは、OUT1 LFBポートに接続された次のLFBインスタンス（通常はポートLFB）に送られます。

In the case of a failed lookup, the original packet and associated metadata is sent out the EXCEPTIONOUT port with the exceptionID of EncapTableLookupFailed [RFC6956]. Note that the EXCEPTIONOUT LFB port is merely an abstraction and implementation may in fact drop packets as described above.

ルックアップが失敗した場合、元のパケットと関連するメタデータは、exceptionIDをEncapTableLookupFailed [RFC6956]としてEXCEPTIONOUTポートに送出されます。EXCEPTIONOUT LFBポートは単なる抽象化であり、実装は実際には上記のとおりパケットを破棄する場合があることに注意してください。

6.1.2. Ingress Processing

6.1.2. イングレスの処理

An ingressing inter-FE LFB packet is recognized by inspecting the ethertype, and optionally the destination and source MAC addresses. A matching packet is mapped to an LFB instance port in the IngressInGroup. The IFETable table row entry matching the LFB instance port may have optionally programmed metadata filters. In such a case, the ingress processing should use the metadata filters as a whitelist of what metadatum is to be allowed.

イングレスするinter-FE LFBパケットは、イーサタイプと、省略可能で宛先および送信元のMACアドレスを検査することで認識されます。一致したパケットは、IngressInGroup内のLFBインスタンスポートに対応付けられます。そのLFBインスタンスポートに一致するIFETableテーブルの行エントリーには、省略可能なメタデータフィルターがプログラムされている場合があります。そのような場合、イングレスの処理では、どのメタデータ項目を許可するかの許可リストとしてメタデータフィルターを使用すべきです。

  • Increment statistics for packet and byte count observed.
  • Look at the metadata length field and walk the packet data, extracting the metadata values from the TLVs. For each metadatum extracted, in the presence of metadata filters, the metaID is compared against the relevant IFETable row metafilter list. If the metadatum is recognized and allowed by the filter, the corresponding implementation Metadatum field is set. If an unknown metadatum ID is encountered or if the metaID is not in the allowed filter list, then the implementation is expected to ignore it, increment the packet error statistic, and proceed processing other metadatum.
  • Upon completion of processing all the metadata, the inter-FE LFB instance resets the data point to the original payload (i.e., skips the IFE header information). At this point, the original packet that was passed to the egress inter-FE LFB at the source FE is reconstructed. This data is then passed along with the reconstructed metadata downstream to the next LFB instance in the graph.
  • 観測したパケット数とバイト数の統計を増やします。
  • メタデータ長フィールドを見て、パケットデータを順に調べ、TLVからメタデータの値を抽出します。抽出した各メタデータ項目について、メタデータフィルターが存在する場合は、metaIDを該当するIFETable行のメタフィルターリストと比較します。メタデータ項目が認識され、フィルターで許可されている場合は、実装の対応するMetadatumフィールドを設定します。未知のメタデータ項目IDに遭遇した場合、またはmetaIDが許可されたフィルターリストにない場合、実装はそれを無視し、パケットのエラー統計を増やし、ほかのメタデータ項目の処理を続けることが期待されます。
  • すべてのメタデータの処理が完了すると、inter-FE LFBインスタンスはデータポイントを元のペイロードにリセットする（つまり、IFEヘッダー情報をスキップします）。この時点で、送信元FEでイグレスinter-FE LFBに渡された元のパケットが再構築されます。このデータは、再構築されたメタデータとともに、グラフ内の次のLFBインスタンスへと下流に渡されます。

In the case of a processing failure of either ingress or egress positioning of the LFB, the packet and metadata are sent out the EXCEPTIONOUT LFB port with the appropriate error ID. Note that the EXCEPTIONOUT LFB port is merely an abstraction and implementation may in fact drop packets as described above.

LFBがイングレスとイグレスのどちらに配置されている場合でも、処理が失敗したときは、パケットとメタデータは適切なエラーIDとともにEXCEPTIONOUT LFBポートに送出されます。EXCEPTIONOUT LFBポートは単なる抽象化であり、実装は実際には上記のとおりパケットを破棄する場合があることに注意してください。

6.2. Components

6.2. コンポーネント

There are two LFB components accessed by the CE. The reader is asked to refer to the definitions in Figure 8.

CEがアクセスするLFBコンポーネントは2つあります。図8の定義を参照してください。

The first component, populated by the CE, is an array known as the "IFETable" table. The array rows are made up of IFEInfo structure. The IFEInfo structure constitutes the optional IFETYPE, the optionally present StatId, the Destination MAC address (DSTFE), the Source MAC address (SRCFE), and an optionally present array of allowed metaIDs (MetaFilterList).

1つ目のコンポーネントは、CEによって値が設定される、「IFETable」テーブルと呼ばれる配列です。配列の行はIFEInfo構造体で構成されます。IFEInfo構造体は、省略可能なIFETYPE、省略可能なStatId、宛先MACアドレス（DSTFE）、送信元MACアドレス（SRCFE）、および許可されたmetaIDの省略可能な配列（MetaFilterList）で構成されます。

The second component (ID 2), populated by the FE and read by the CE, is an indexed array known as the "IFEStats" table. Each IFEStats row carries statistics information in the structure bstats.

2つ目のコンポーネント（ID 2）は、FEによって値が設定されてCEによって読み取られる、「IFEStats」テーブルと呼ばれるインデックス付きの配列です。各IFEStatsの行は、構造体bstatsで統計情報を運びます。

A note about the StatId relationship between the IFETable table and the IFEStats table -- an implementation may choose to map between an IFETable row and IFEStats table row using the StatId entry in the matching IFETable row. In that case, the IFETable StatId must be present. An alternative implementation may map an IFETable row to an IFEStats table row at provisioning time. Yet another alternative implementation may choose not to use the IFETable row StatId and instead use the IFETable row index as the IFEStats index. For these reasons, the StatId component is optional.

IFETableテーブルとIFEStatsテーブルの間のStatIdの関係について注記します。実装は、一致したIFETable行のStatIdエントリーを使用して、IFETable行とIFEStatsテーブルの行を対応付けることを選択してもかまいません。その場合、IFETableのStatIdが存在する必要があります。別の実装では、プロビジョニング時にIFETable行をIFEStatsテーブルの行に対応付けてもかまいません。さらに別の実装では、IFETable行のStatIdを使用せず、代わりにIFETable行のインデックスをIFEStatsのインデックスとして使用することを選択してもかまいません。これらの理由から、StatIdコンポーネントは省略可能です。

9. Security Considerations

9. セキュリティーに関する考慮事項

The FEs involved in the inter-FE LFB belong to the same NE and are within the scope of a single administrative Ethernet LAN private network. While trust of policy in the control and its treatment in the datapath exists already, an inter-FE LFB implementation SHOULD support security services provided by Media Access Control Security (MACsec) [ieee8021ae]. MACsec is not currently sufficiently widely deployed in traditional packet processing hardware although it is present in newer versions of the Linux kernel (which will be widely deployed) [linux-macsec]. Over time, we expect that most FEs will be able to support MACsec.

inter-FE LFBに関与するFEは、同じNEに属しており、単一の管理主体によるイーサネットLANのプライベートネットワークの範囲内にあります。制御におけるポリシーとデータパスにおけるその扱いについての信頼はすでに存在しますが、inter-FE LFBの実装は、Media Access Control Security（MACsec）[ieee8021ae]が提供するセキュリティーサービスをサポートすべきです（SHOULD）。MACsecは、新しいバージョンのLinuxカーネル（これは広く展開されることになります）には存在するものの[linux-macsec]、従来のパケット処理ハードウェアでは現在のところ十分に広く展開されていません。時間がたつにつれて、ほとんどのFEがMACsecをサポートできるようになると予想しています。

MACsec provides security services such as a message authentication service and an optional confidentiality service. The services can be configured manually or automatically using the MACsec Key Agreement (MKA) over the IEEE 802.1x [ieee8021x] Extensible Authentication Protocol (EAP) framework. It is expected that FE implementations are going to start with shared keys configured from the control plane but progress to automated key management.

MACsecは、メッセージ認証サービスや省略可能な機密性サービスといったセキュリティーサービスを提供します。これらのサービスは、手動で設定することも、IEEE 802.1x [ieee8021x]の拡張認証プロトコル（Extensible Authentication Protocol、EAP）フレームワーク上のMACsec鍵合意（MACsec Key Agreement、MKA）を使用して自動的に設定することもできます。FEの実装は、まずコントロールプレーンから設定された共有鍵から始め、やがて自動化された鍵管理に移行していくと予想されます。

The following are the MACsec security mechanisms that need to be in place for the inter-FE LFB:

inter-FE LFBのために導入する必要のあるMACsecのセキュリティーメカニズムは次のとおりです。

  • Security mechanisms are NE-wide for all FEs. Once the security is turned on, depending upon the chosen security level (e.g., Authentication, Confidentiality), it will be in effect for the inter-FE LFB for the entire duration of the session.
  • An operator SHOULD configure the same security policies for all participating FEs in the NE cluster. This will ensure uniform operations and avoid unnecessary complexity in policy configuration. In other words, the Security Association Keys (SAKs) should be pre-shared. When using MKA, FEs must identify themselves with a shared Connectivity Association Key (CAK) and Connectivity Association Key Name (CKN). EAP-TLS SHOULD be used as the EAP method.
  • An operator SHOULD configure the strict validation mode, i.e., all non-protected, invalid, or non-verifiable frames MUST be dropped.
  • セキュリティーメカニズムは、すべてのFEに対してNE全体で共通です。セキュリティーを有効にすると、選択したセキュリティーレベル（たとえば、認証、機密性）に応じて、セッションの全期間にわたってinter-FE LFBに対して有効になります。
  • 運用者は、NEクラスター内のすべての参加するFEに対して同じセキュリティーポリシーを設定すべきです（SHOULD）。これにより、一様な運用が保証され、ポリシー設定の不必要な複雑さが回避されます。言い換えれば、セキュリティーアソシエーション鍵（Security Association Key、SAK）は事前共有されるべきです。MKAを使用する場合、FEは、共有された接続アソシエーション鍵（Connectivity Association Key、CAK）と接続アソシエーション鍵名（Connectivity Association Key Name、CKN）で自身を識別する必要があります。EAPメソッドとしてEAP-TLSを使用すべきです（SHOULD）。
  • 運用者は、厳密な検証モードを設定すべきです（SHOULD）。すなわち、保護されていないフレーム、無効なフレーム、検証できないフレームはすべて破棄しなければなりません（MUST）。

It should be noted that given the above choices, if an FE is compromised, an entity running on the FE would be able to fake inter-FE or modify its content, causing bad outcomes.

上記の選択を前提とすると、FEが侵害された場合、そのFE上で動作するエンティティーがinter-FEを偽造したりその内容を改変したりできてしまい、悪い結果を引き起こすことに注意すべきです。
