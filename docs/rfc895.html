RFC 895

Standard for the Transmission of IP Datagrams over Experimental Ethernet Networks

RFC 895

実験用イーサネットネットワーク上でIPデータグラムを伝送するための標準

Status of This Memo

このメモのステータス

This RFC specifies a standard method of encapsulating Internet Protocol (IP) [1] datagrams on an Experimental Ethernet [2]. This RFC specifies a standard protocol for the ARPA Internet community.

このRFCは、実験用イーサネット（Experimental Ethernet）[2]上でインターネットプロトコル（IP）[1]のデータグラムをカプセル化する標準的な方法を規定します。このRFCは、ARPAインターネットコミュニティーのための標準プロトコルを規定します。

Introduction

はじめに

This memo applies to the Experimental Ethernet (3-megabit/second, 8-bit addresses). The procedure for transmission of IP datagrams on the Ethernet (10-megabit/second, 48-bit addresses) is described in [3].

このメモは、実験用イーサネット（3メガビット/秒、8ビットアドレス）に適用されます。イーサネット（10メガビット/秒、48ビットアドレス）上でIPデータグラムを伝送する手順は、[3]で説明されています。

Frame Format

フレーム形式

IP datagrams are transmitted in standard Experimental Ethernet frames. The type field of the Ethernet frame must contain the value 513 (1001 octal). The data field contains the IP header followed immediately by the IP data.

IPデータグラムは、標準的な実験用イーサネットのフレームで伝送されます。イーサネットフレームのタイプフィールドには、値513（8進数で1001）が入っていなければなりません。データフィールドには、IPヘッダーと、その直後に続くIPデータが入ります。

If necessary, the data field should be padded to meet the Experimental Ethernet minimum frame size. This padding is not part of the IP packet and is not included in the total length field of the IP header.

必要であれば、実験用イーサネットの最小フレームサイズを満たすよう、データフィールドをパディングすべきです。このパディングはIPパケットの一部ではなく、IPヘッダーの全長フィールドには含まれません。

The maximum length of an IP datagram sent over an Experimental Ethernet is 1536 octets. Implementations are encouraged to support full-length packets. Gateway implementations MUST be prepared to accept full-length packets and fragment them if necessary. If a system cannot receive full-length packets, it should take steps to discourage others from sending them, such as using the TCP Maximum Segment Size option [4].

実験用イーサネット上で送信されるIPデータグラムの最大長は1536オクテットです。実装は、最大長のパケットをサポートすることが推奨されます。ゲートウェイの実装は、最大長のパケットを受け入れ、必要に応じてそれをフラグメント化する用意がなければなりません（MUST）。最大長のパケットを受信できないシステムは、TCPの最大セグメントサイズ（Maximum Segment Size）オプション[4]を使うなどして、ほかのシステムがそのようなパケットを送信しないようにする手段を講じるべきです。

Note: Datagrams on the Ethernet may be longer than the general Internet default maximum packet size of 576 octets. Hosts connected to an Ethernet should keep this in mind when sending datagrams to hosts not on the same Ethernet. It may be appropriate to send smaller datagrams to avoid unnecessary fragmentation at intermediate gateways. Please see [4] for further information on this point.

注意：イーサネット上のデータグラムは、一般的なインターネットのデフォルトの最大パケットサイズである576オクテットより長くなることがあります。イーサネットに接続されたホストは、同じイーサネット上にないホストにデータグラムを送信する際に、このことを念頭に置くべきです。中間のゲートウェイでの不必要なフラグメント化を避けるため、より小さいデータグラムを送信するのが適切な場合もあります。この点に関する詳しい情報は、[4]を参照してください。

Address Mappings

アドレスマッピング

The mapping between 32-bit Internet addresses to 8-bit Experimental Ethernet addresses can be done several ways.

32ビットのインターネットアドレスから8ビットの実験用イーサネットアドレスへのマッピングは、いくつかの方法で行えます。

The easiest thing to do is to use the last eight bits of host number part of the Internet address as the host's address on the Experimental Ethernet. This is the recommended approach.

最も簡単なのは、インターネットアドレスのホスト番号部分の下位8ビットを、実験用イーサネット上のホストのアドレスとして使う方法です。これが推奨される方法です。

Broadcast Address
The broadcast Internet address (the address on that network with a host part of all binary ones) should be mapped to the broadcast Experimental Ethernet address (address zero).
ブロードキャストアドレス
ブロードキャストのインターネットアドレス（そのネットワーク上で、ホスト部のビットがすべて1であるアドレス）は、実験用イーサネットのブロードキャストアドレス（アドレス0）にマッピングすべきです。

Trailer Formats

トレーラー形式

Some versions of Unix 4.2bsd use a different encapsulation method in order to get better network performance with the VAX virtual memory architecture. Consenting systems on the same Ethernet may use this format between themselves.

Unix 4.2bsdの一部のバージョンは、VAXの仮想メモリーアーキテクチャーでより良いネットワーク性能を得るため、異なるカプセル化方式を使用しています。同じイーサネット上の、合意したシステム同士は、互いの間でこの形式を使用してもかまいません。

No host is required to implement it, and no datagrams in this format should be sent to any host unless the sender has positive knowledge that the recipient will be able to interpret them. Details of the trailer encapsulation may be found in [6].

どのホストもこれを実装することは要求されません。また、受信側がこの形式のデータグラムを解釈できることを送信側が確実に知っている場合を除き、この形式のデータグラムをどのホストにも送信すべきではありません。トレーラーカプセル化の詳細は[6]にあります。

(Note: At the present time Unix 4.2bsd will either always use trailers or never use them (per interface), depending on a boot-time option. This is expected to be changed in the future. Unix 4.2bsd also uses a non-standard Internet broadcast address with a host part of all zeroes, this will also be changed in the future.)

（注意：現時点では、Unix 4.2bsdは、ブート時のオプションに応じて、（インターフェイスごとに）常にトレーラーを使用するか、まったく使用しないかのどちらかです。これは将来変更される見込みです。また、Unix 4.2bsdは、ホスト部のビットがすべて0である非標準のインターネットブロードキャストアドレスを使用していますが、これも将来変更される予定です。）

Byte Order

バイト順序

As described in Appendix B of the Internet Protocol specification [1], the IP datagram is transmitted over the Ethernet as a series of 8-bit bytes.

インターネットプロトコルの仕様[1]の付録Bで説明されているように、IPデータグラムは、8ビットのバイトの列としてイーサネット上で伝送されます。
