1. Introduction

1. はじめに

Available tools for testing TCP implementations are catalogued by this memo. Hopefully disseminating this information will encourage those responsible for building and maintaining TCP to make the best use of available tests. The type of testing the tool provides, the type of tests it is capable of doing, and its availability is enumerated. This document lists only tools which can evaluate one or more TCP implementations, or which can privde some specific results which describe or evaluate the TCP being tested. A number of these tools produce time-sequence plots, see Tim Shepard's thesis [She91] for a general discussion of these plots.

このメモは、TCPの実装をテストするために利用可能なツールを一覧にしたものです。この情報を広めることで、TCPの構築と保守に責任を持つ人々が、利用可能なテストを最大限に活用するよう促されることを期待しています。ツールが提供するテストの種類、実行できるテストの種類、およびその入手可能性を列挙します。この文書は、1つ以上のTCPの実装を評価できるツール、またはテスト対象のTCPを記述または評価するいくつかの具体的な結果を提供できるツールだけを一覧にしています。これらのツールの多くは時系列のプロットを生成します。これらのプロットの一般的な議論については、Tim Shepardの論文[She91]を参照してください。

Each tools is defined as follows:

各ツールは次のように定義されます。

Name
The name associated with the testing tool.
Category
One or more categories of tests which the tools are capable of providing. Categories used are: functional correctness, performance, stress. Functional correctness tests how stringent a TCP implementation is to the RFC specifications. Performance tests how quickly a TCP implementation can send and receive data, etc. Stress tests how a TCP implementation is effected under high load conditions.
Description
A description of the tools construction, and the implementation methodology of the tests.
Automation
What steps are required to complete the test? What human intervention is required?
Availability
How do you retrieve this tool and get more information about it?
Required Environment
Compilers, OS version, etc. required to build and/or run the associated tool.
References
A list of publications relating to the tool, if any.
名前
テストツールに関連付けられた名前。
カテゴリー
ツールが提供できるテストの1つ以上のカテゴリー。使用されるカテゴリーは、機能の正しさ、性能、ストレスです。機能の正しさは、TCPの実装がRFCの仕様にどれだけ厳密に従っているかをテストします。性能は、TCPの実装がどれだけ速くデータを送受信できるかなどをテストします。ストレスは、高負荷の状況下でTCPの実装がどのような影響を受けるかをテストします。
説明
ツールの構成と、テストの実装の方法論の説明。
自動化
テストを完了するためにどのような手順が必要か。どのような人間の介入が必要か。
入手方法
このツールをどのように取得し、それについてのさらなる情報をどのように得るか。
必要な環境
関連するツールのビルドや実行に必要なコンパイラー、OSのバージョンなど。
参考文献
ツールに関連する出版物があれば、その一覧。

2.1. Dbs

2.1. Dbs

Author
Yukio Murayama
Category
Performance / Stress
Description
Dbs is a tool which allows multiple data transfers to be coordinated, and the resulting TCP behavior to be reviewed. Results are presented as ASCII log files.
Automation
Command of execution is driven by a script file.
Availability
See http://www.ai3.net/products/dbs for details of precise OS versions supported, and for download of the source code. Current implementation supports BSDI BSD/OS, Linux, mkLinux, SunOS, IRIX, Ultrix, NEWS OS, HP-UX. Other environments are likely easy to add.
Required Environment
C language compiler, UNIX-style socket API support.
著者
Yukio Murayama
カテゴリー
性能 / ストレス
説明
Dbsは、複数のデータ転送を協調させ、その結果のTCPの振る舞いを確認できるツールです。結果はASCIIのログファイルとして提示されます。
自動化
実行の指令はスクリプトファイルによって駆動されます。
入手方法
サポートされているOSの正確なバージョンの詳細と、ソースコードのダウンロードについては、http://www.ai3.net/products/dbs を参照してください。現在の実装は、BSDI BSD/OS、Linux、mkLinux、SunOS、IRIX、Ultrix、NEWS OS、HP-UXをサポートしています。他の環境を追加するのはおそらく容易です。

2.2. Dummynet

2.2. Dummynet

Author
Luigi Rizzo
Category
Functional Correctness / Performance
Description
Dummynet is a tool which simulates the presence of finite size queues, bandwidth limitations, and communication delays. Dummynet inserts between two layers of the protocol stack (in the current implementation between TCP and IP), simulating the above effects in an operational system. This way experiments can be done using real protocol implementations and real applications, even running on the same host (dummynet also intercepts communications on the loopback interface). Reconfiguration of dummynet parameters (delay, queue size, bandwidth) can be done on the fly by using a sysctl call. The overhead of dummynet is extremely low.
Automation
Requires merging diff files with kernel source code. Command-line driven through the sysctl command to modify kernel variables.
Availability
See http://www.iet.unipi.it/~luigi/research.html or e-mail Luigi Rizzo (l.rizzo@iet.unipi.it). Source code is available for FreeBSD 2.1 and FreeBSD 2.2 (easily adaptable to other BSD-derived systems).
Required Environment
C language compiler, BSD-derived system, kernel source code.
References
[Riz97]
著者
Luigi Rizzo
カテゴリー
機能の正しさ / 性能
説明
Dummynetは、有限サイズのキュー、帯域幅の制限、および通信の遅延の存在をシミュレートするツールです。Dummynetは、プロトコルスタックの2つの層の間（現在の実装ではTCPとIPの間）に挿入され、稼働中のシステムで上記の効果をシミュレートします。こうすることで、同じホスト上で実行する場合であっても（dummynetはループバックインターフェイス上の通信も横取りします）、実際のプロトコルの実装と実際のアプリケーションを使用して実験を行うことができます。dummynetのパラメーター（遅延、キューのサイズ、帯域幅）の再設定は、sysctlの呼び出しを使用してその場で行うことができます。dummynetのオーバーヘッドは非常に低いです。
自動化
差分ファイルをカーネルのソースコードとマージする必要があります。カーネルの変数を変更するためのsysctlコマンドを通じてコマンドラインで駆動されます。
入手方法
http://www.iet.unipi.it/~luigi/research.html を参照するか、Luigi Rizzo（l.rizzo@iet.unipi.it）に電子メールを送ってください。ソースコードは、FreeBSD 2.1とFreeBSD 2.2で利用できます（他のBSD由来のシステムに容易に適応できます）。
必要な環境
C言語のコンパイラー、BSD由来のシステム、カーネルのソースコード。
参考文献
[Riz97]

2.3. Netperf

2.3. Netperf

Author
Rick Jones
Category
Performance
Description
Single connection bandwidth or latency tests for TCP, UDP, and DLPI. Includes provisions for CPU utilization measurement.
Automation
Requires compilation (K&R C sufficient for all but-DHISTOGRAM, may require ANSI C in the future) if starting from source. Execution as child of inetd requires editing of /etc/services and /etc/inetd.conf. Scripts are provided for a quick look (snapshot_script), bulk throughput of TCP and UDP, and latency for TCP and UDP. It is command-line driven.
Availability
See http://www.cup.hp.com/netperf/NetperfPage.html or e-mail Rick Jones (raj@cup.hp.com). Binaries are available here for HP/UX Irix, Solaris, and Win32.
Required Environment
C language compiler, POSIX.1, sockets.
著者
Rick Jones
カテゴリー
性能
説明
TCP、UDP、DLPIのための単一の接続の帯域幅または遅延のテスト。CPUの利用率の測定のための機能が含まれています。
自動化
ソースから始める場合はコンパイルが必要です（-DHISTOGRAMを除くすべてについてはK&R Cで十分ですが、将来はANSI Cが必要になる可能性があります）。inetdの子として実行するには、/etc/servicesと/etc/inetd.confの編集が必要です。簡単に確認するためのスクリプト（snapshot_script）、TCPとUDPのバルクのスループット、およびTCPとUDPの遅延のためのスクリプトが提供されています。コマンドラインで駆動されます。
入手方法
http://www.cup.hp.com/netperf/NetperfPage.html を参照するか、Rick Jones（raj@cup.hp.com）に電子メールを送ってください。HP/UX、Irix、Solaris、Win32用のバイナリーがそこで入手できます。
必要な環境
C言語のコンパイラー、POSIX.1、ソケット。

2.4. NIST Net

2.4. NIST Net

Author
Mark Carson
Category
Functional Correctness / Performance
Description

NIST Net is a network emulator. The tool is packaged as a Linux kernel patch, a kernel module, a set of programming APIs, and command-line and X-based user interfaces.

NIST Net works by turning the system into a "selectively bad" router - incoming packets may be delayed, dropped, duplicated, bandwidth-constrained , etc. Packet delays may be fixed or randomly distributed, with loadable probability distributions. Packet loss may be uniformly distributed (constant loss probability) or congestion-dependent (probability of loss increases with packet queue lengths). Explicit congestion notifications may optionally be sent in place of congestion-dependent loss.

Automation
To control the operation of the emulator, there is an interactive user interface, a non-interactive command-line interface, and a set of APIs. Any or all of these may be used in concert. The interactive interface is suitable for simple, spur-of-the-moment testing, while the command-line or APIs may be used to create scripted, non-interactive tests.
Availability
NIST Net is available for public download from the NIST Net web site, http://www.antd.nist.gov/itg/nistnet/. The web site also has installation instructions and documentation.
Required Environment

NIST Net requires a Linux installtion, with kernel version 2.0.27 - 2.0.33. A kernel source tree and build tools are required to build and install the NIST Net components. Building the X interface requires a version of XFree86 (Current Version is 3.3.2). An Athena-replacement widget set such as neXtaw (http://www.inf.ufrgs.br/~kojima/nextaw/) is also desirable for an improved user interface.

NIST Net should run on any i386-compatible machine capable of running Linux, with one or more interfaces.

著者
Mark Carson
カテゴリー
機能の正しさ / 性能
説明

NIST Netはネットワークのエミュレーターです。このツールは、Linuxのカーネルパッチ、カーネルモジュール、プログラミングAPIの集合、およびコマンドラインとXベースのユーザーインターフェイスとしてパッケージ化されています。

NIST Netは、システムを「選択的に不良な」ルーターに変えることで機能します。受信したパケットは、遅延されたり、破棄されたり、複製されたり、帯域幅を制限されたりします。パケットの遅延は、固定することも、読み込み可能な確率分布を用いてランダムに分布させることもできます。パケットの損失は、一様に分布させる（一定の損失確率）ことも、輻輳に依存させる（パケットのキューの長さとともに損失の確率が増加する）こともできます。必要に応じて、輻輳に依存する損失の代わりに明示的輻輳通知を送信することもできます。

自動化
エミュレーターの動作を制御するために、対話型のユーザーインターフェイス、非対話型のコマンドラインインターフェイス、およびAPIの集合があります。これらのいずれか、またはすべてを組み合わせて使用できます。対話型のインターフェイスは単純でその場限りのテストに適しており、コマンドラインまたはAPIはスクリプト化された非対話型のテストを作成するために使用できます。
入手方法
NIST Netは、NIST NetのWebサイト http://www.antd.nist.gov/itg/nistnet/ から誰でもダウンロードできます。このWebサイトには、インストールの手順と文書もあります。
必要な環境

NIST Netには、カーネルのバージョンが2.0.27から2.0.33のLinuxのインストールが必要です。NIST Netの構成要素をビルドしてインストールするには、カーネルのソースツリーとビルドツールが必要です。Xのインターフェイスをビルドするには、XFree86のバージョン（現在のバージョンは3.3.2）が必要です。ユーザーインターフェイスを改善するために、neXtaw（http://www.inf.ufrgs.br/~kojima/nextaw/）などのAthenaの代替のウィジェットセットもあることが望ましいです。

NIST Netは、1つ以上のインターフェイスを持ち、Linuxを実行できる任意のi386互換のマシンで動作するはずです。

2.5. Orchestra

2.5. Orchestra

Author
Scott Dawson, Farnam Jahanian, and Todd Mitton
Category
Functional Correctness / Performance
Description

This tool is a library which provides the user with an ability to build a protocol layer capable of performing fault injection on protocols. Several fault injection layers have been built using this library, one of which has been used to test different vendor implementations of TCP. This is accomplished by probing the vendor implementation from one machine containing a protocol stack that has been instrumented with Orchestra. A connection is opened from the vendor TCP implementation to the machine which has been instrumented. Faults may then be injected at the Orchestra side of the connection and the vendor TCP's response may be monitored. The most recent version of Orchestra runs inside the X-kernel protocol stack on the OSF MK operating system.

When using Orchestra to test a protocol, the fault injection layer is placed below the target protocol in the protocol stack. This can either be done on one machine on the network, if protocol stacks on the other machines cannot be modified (as in the case of testing TCP), or can be done on all machines on the network (as in the case of testing a protocol under development). Once the fault injection layer is in the protocol stack, all messages sent by and destined for the target protocol pass through it on their way to/from the network. The Orchestra fault injection layer can manipulate these messages. In particular, it can drop, delay, re-order, duplicate, or modify messages. It can also introduce new messages into the system if desired.

The actions of the Orchestra fault injection layer on each message are determined by a script, written in Tcl. This script is interpreted by the fault injection layer when the message enters the layer. The script has access to the header information about the message, and can make decisions based on header values. It can also keep information about previous messages, counters, or any other data which the script writer deems useful. Users of Orchestra may also define their own actions to be taken on messages, written in C, that may be called from the fault injection scripts.

Automation
Scripts can be specified either using a graphical user interface which generates Tcl, or by writing Tcl directly. At this time, post-analysis of the results of the test must also be performed by the user. Essentially this consists of looking at a packet trace that Orchestra generates for (in)correct behavior. Must compile and link fault generated layer with the protocol stack.
Availability
See http://www.eecs.umich.edu/RTCL/projects/orchestra/ or e-mail Scott Dawson (sdawson@eecs.umich.edu).
Required Environment
OSF MK operating system, or X-kernel like network architecture, or adapted to network stack.
References
[DJ94], [DJM96a], [DJM96b]
著者
Scott Dawson、Farnam Jahanian、Todd Mitton
カテゴリー
機能の正しさ / 性能
説明

このツールは、プロトコルに対してフォールトインジェクションを行うことができるプロトコル層を構築する能力をユーザーに提供するライブラリーです。このライブラリーを使用していくつかのフォールトインジェクション層が構築されており、そのうちの1つは、さまざまなベンダーのTCPの実装をテストするために使用されてきました。これは、Orchestraで計装されたプロトコルスタックを含む1台のマシンから、ベンダーの実装を探ることによって実現されます。ベンダーのTCPの実装から、計装されたマシンへの接続が開かれます。その後、接続のOrchestra側でフォールトを注入し、ベンダーのTCPの応答を監視できます。Orchestraの最新バージョンは、OSF MKオペレーティングシステム上のX-kernelのプロトコルスタック内で動作します。

Orchestraを使用してプロトコルをテストする場合、フォールトインジェクション層はプロトコルスタック内の対象のプロトコルの下に配置されます。これは、他のマシンのプロトコルスタックを変更できない場合（TCPをテストする場合のように）はネットワーク上の1台のマシンで行うことも、ネットワーク上のすべてのマシンで行うこと（開発中のプロトコルをテストする場合のように）もできます。フォールトインジェクション層がプロトコルスタック内に入ると、対象のプロトコルによって送信されるメッセージと対象のプロトコル宛てのメッセージはすべて、ネットワークとの間でそこを通過します。Orchestraのフォールトインジェクション層は、これらのメッセージを操作できます。特に、メッセージを破棄、遅延、並べ替え、複製、または変更できます。必要に応じて、新しいメッセージをシステムに持ち込むこともできます。

各メッセージに対するOrchestraのフォールトインジェクション層の動作は、Tclで書かれたスクリプトによって決定されます。このスクリプトは、メッセージが層に入ったときにフォールトインジェクション層によって解釈されます。スクリプトはメッセージのヘッダー情報にアクセスでき、ヘッダーの値に基づいて判断を行うことができます。また、以前のメッセージ、カウンター、またはスクリプトの作成者が有用と考えるその他のデータについての情報を保持することもできます。Orchestraのユーザーは、フォールトインジェクションのスクリプトから呼び出すことができる、Cで書かれた、メッセージに対して行う独自の動作を定義することもできます。

自動化
スクリプトは、Tclを生成するグラフィカルユーザーインターフェイスを使用するか、Tclを直接書くことで指定できます。現時点では、テスト結果の事後分析もユーザーが行わなければなりません。基本的に、これはOrchestraが生成するパケットトレースを見て、（不）正確な振る舞いを確認することで構成されます。フォールトを生成する層をプロトコルスタックとコンパイルしてリンクしなければなりません。
入手方法
http://www.eecs.umich.edu/RTCL/projects/orchestra/ を参照するか、Scott Dawson（sdawson@eecs.umich.edu）に電子メールを送ってください。
必要な環境
OSF MKオペレーティングシステム、X-kernelのようなネットワークアーキテクチャー、またはネットワークスタックに適応させたもの。
参考文献
[DJ94], [DJM96a], [DJM96b]

2.6. Packet Shell

2.6. Packet Shell

Author
Steve Parker and Chris Schmechel
Category
Functional Correctness / Performance
Description

An extensible Tcl/Tk based software toolset for protocol development and testing. Tcl (Tool Command Language) is an embeddable scripting language and Tk is a graphical user interface toolkit based on Tcl. The Packet Shell creates Tcl commands that allow you to create, modify, send, and receive packets on networks. The operations for each protocol are supplied by a dynamic linked library called a protocol library. These libraries are silently linked in from a special directory when the Packet Shell begins execution. The current protocol libraries are: IP, IPv6, IPv6 extensions, ICMP, ICMPv6, Ethernet layer, data layer, file layer (snoop and tcpdump support), socket layer, TCP, TLI.

It includes harness, which is a Tk based graphical user interface for creating test scripts within the Packet Shell. It includes tests for no initial slow start, and retain out of sequence data as TCP test cases mentioned in [PADHV98].

It includes tcpgraph, which is used with a snoop or tcpdump capture file to produce a TCP time-sequence plot using xplot.

Automation
Command-line driven through Tcl commands, or graphical user interface models are available through the harness format.
Availability
See http://playground.sun.com/psh/ or e-mail owner-packet-shell@sunroof.eng.sun.com.
Required Environment
Solaris 2.4 or higher. Porting required for other operating systems.
著者
Steve Parker、Chris Schmechel
カテゴリー
機能の正しさ / 性能
説明

プロトコルの開発とテストのための、拡張可能なTcl/Tkベースのソフトウェアツールセットです。Tcl（Tool Command Language）は埋め込み可能なスクリプト言語であり、TkはTclに基づくグラフィカルユーザーインターフェイスのツールキットです。Packet Shellは、ネットワーク上でパケットを作成、変更、送信、受信できるようにするTclのコマンドを作成します。各プロトコルの操作は、プロトコルライブラリーと呼ばれる動的リンクライブラリーによって提供されます。これらのライブラリーは、Packet Shellが実行を開始するときに、特別なディレクトリーから暗黙のうちにリンクされます。現在のプロトコルライブラリーは、IP、IPv6、IPv6の拡張、ICMP、ICMPv6、Ethernet層、data層、file層（snoopとtcpdumpのサポート）、socket層、TCP、TLIです。

Packet Shellには、Packet Shell内でテストのスクリプトを作成するためのTkベースのグラフィカルユーザーインターフェイスであるharnessが含まれています。[PADHV98]で言及されているTCPのテストケースとして、初期のスロースタートがないことと、順序外のデータを保持することのテストが含まれています。

Packet Shellには、snoopやtcpdumpのキャプチャーファイルとともに使用して、xplotを使用したTCPの時系列のプロットを生成するtcpgraphが含まれています。

自動化
Tclのコマンドを通じてコマンドラインで駆動されるか、harnessの形式を通じてグラフィカルユーザーインターフェイスのモデルが利用できます。
入手方法
http://playground.sun.com/psh/ を参照するか、owner-packet-shell@sunroof.eng.sun.com に電子メールを送ってください。
必要な環境

2.7. Tcpanaly

2.7. Tcpanaly

Author
Vern Paxson
Category
Functional Correctness / Performance
Description

This is a tool for automatically analyzing a TCP implementation's behavior by inspecting packet traces of the TCP's activity. It does so through packet filter traces produced by tcpdump. It has coded within it knowledge of a large number of TCP implementations. Using this, it can determine whether a given trace appears consistent with a given implementation, and, if so, exactly why the TCP chose to transmit each packet at the time it did. If a trace is found inconsistent with a TCP, tcpanaly either diagnoses a likely measurement error present in the trace, or indicates exactly whether the activity in the trace deviates from that of the TCP, which can greatly aid in determining how the traced implementation behaves.

Tcpanaly's category is somewhat difficult to classify, since it attempts to profile the behavior of an implementation, rather than to explicitly test specific correctness or performance issues. However, this profile identifies correctness and performance problems.

Adding new implementations of TCP behavior is possible with tcpanaly through the use of C++ classes.

Automation
Command-line driven and only the traces of the TCP sending and receiving bulk data transfers are needed as input.
Availability
Contact Vern Paxson (vern@ee.lbl.gov).
Required Environment
C++ compiler.
References
[Pax97a]
著者
Vern Paxson
カテゴリー
機能の正しさ / 性能
説明

これは、TCPの活動のパケットトレースを調べることで、TCPの実装の振る舞いを自動的に分析するためのツールです。これは、tcpdumpによって生成されたパケットフィルターのトレースを通じて行われます。このツールには、多数のTCPの実装についての知識が組み込まれています。これを使用して、与えられたトレースが与えられた実装と一貫しているように見えるかどうか、そしてそうであれば、TCPがなぜ各パケットをその時点で送信することを選んだのかを正確に判断できます。トレースがTCPと一貫していないことがわかった場合、tcpanalyは、トレースに存在する可能性の高い測定の誤りを診断するか、トレース内の活動がそのTCPのものから逸脱しているかどうかを正確に示します。これは、トレースされた実装がどのように振る舞うかを判断するのに大いに役立ちます。

tcpanalyは、特定の正しさや性能の問題を明示的にテストするのではなく、実装の振る舞いをプロファイルしようとするため、そのカテゴリーを分類するのはいくぶん困難です。しかし、このプロファイルによって、正しさと性能の問題が特定されます。

C++のクラスを使用することで、tcpanalyにTCPの振る舞いの新しい実装を追加できます。

自動化
コマンドラインで駆動され、入力として必要なのは、バルクのデータ転送を送受信するTCPのトレースだけです。
入手方法
Vern Paxson（vern@ee.lbl.gov）に連絡してください。
必要な環境
C++のコンパイラー。

2.8. Tcptrace

2.8. Tcptrace

Author
Shawn Ostermann
Category
Functional Correctness / Performance
Description

This is a TCP trace file analysis tool. It reads output trace files in the formats of : tcpdump, snoop, etherpeek, and netm.

For each connection, it keeps track of elapsed time, bytes/segments sent and received, retransmissions, round trip times, window advertisements, throughput, etc from simple to very detailed output.

It can also produce three different types of graphs:

Time Sequence Graph (shows the segments sent and ACKs returned as a function of time)

Instantaneous Throughput (shows the instantaneous, averaged over a few segments, throughput of the connection as a function of time).

Round Trip Times (shows the round trip times for the ACKs as a function of time)

Automation
Command-line driven, and uses the xplot program to view the graphs.
Availability
Source code is available, and Solaris binary along with sample traces. See http://jarok.cs.ohiou.edu/software/tcptrace/tcptrace.html or e-mail Shawn Ostermann (ostermann@cs.ohiou.edu).
Required Environment
C compiler, Solaris, FreeBSD, NetBSD, HPUX, Linux.
著者
Shawn Ostermann
カテゴリー
機能の正しさ / 性能
説明

これはTCPのトレースファイルの分析ツールです。tcpdump、snoop、etherpeek、netmの形式の出力トレースファイルを読み込みます。

各接続について、経過時間、送受信されたバイト数とセグメント数、再送、往復時間、ウィンドウの広告、スループットなどを、簡単なものから非常に詳細な出力まで追跡します。

また、3種類の異なるグラフを生成することもできます。

時系列グラフ（送信されたセグメントと返されたACKを時間の関数として示します）

瞬間スループット（数セグメントにわたって平均した、接続の瞬間的なスループットを時間の関数として示します）。

往復時間（ACKの往復時間を時間の関数として示します）

自動化
コマンドラインで駆動され、グラフを表示するためにxplotプログラムを使用します。
入手方法
ソースコードと、サンプルのトレースを伴うSolarisのバイナリーが入手できます。http://jarok.cs.ohiou.edu/software/tcptrace/tcptrace.html を参照するか、Shawn Ostermann（ostermann@cs.ohiou.edu）に電子メールを送ってください。
必要な環境
Cのコンパイラー、Solaris、FreeBSD、NetBSD、HPUX、Linux。

2.10. TReno

This is a TCP throughput measurement tool based on sending UDP or ICMP packets in patterns that are controlled at the user-level so that their timing reflects what would be sent by a TCP that observes proper congestion control (and implements SACK). 著者
Matt Mathis、Jamshid Mahdavi
カテゴリー
性能

4. Security Considerations

4. セキュリティーに関する考慮事項

Network analysis tools are improving at a steady pace. The continuing improvement in these tools such as the ones described make security concerns significant.

ネットワークの分析ツールは着実に改良されています。ここで説明したようなツールの継続的な改良により、セキュリティー上の懸念は重大なものになっています。

Some of the tools could be used to create rogue packets or denial-of-service attacks against other hosts. Also, some of the tools require changes to the kernel (foreign code) and might require root privileges to execute. So you are trusting code that you have fetched from some perhaps untrustworthy remote site. This code could contain malicious code that could present any kind of attack.

一部のツールは、他のホストに対する不正なパケットやサービス拒否攻撃を作り出すために使用される可能性があります。また、一部のツールはカーネルの変更（外部のコード）を必要とし、実行するためにroot権限が必要になる場合があります。つまり、信頼できないかもしれない遠隔のサイトから取得したコードを信頼することになります。このコードには、あらゆる種類の攻撃をもたらす可能性のある悪意のあるコードが含まれている可能性があります。

None of the listed tools evaluate security in any way or form.

一覧にしたツールはいずれも、いかなる方法や形式でもセキュリティーを評価しません。

There are privacy concerns when grabbing packets from the network in that you are now able to read other people's mail, files, etc. This impacts more than just the host running the tool but all traffic crossing the host's physical network.

ネットワークからパケットを取得する際には、他の人のメール、ファイルなどを読むことができるようになるという点で、プライバシー上の懸念があります。これは、ツールを実行しているホストだけでなく、そのホストの物理ネットワークを横断するすべてのトラフィックに影響します。
