RFC 7922

Interface to the Routing System (I2RS) Traceability: Framework and Information Model

RFC 7922

ルーティングシステムへのインターフェイス（I2RS）のトレーサビリティー：フレームワークと情報モデル

Abstract

概要

This document describes a framework for traceability in the Interface to the Routing System (I2RS) and the information model for that framework. It specifies the motivation, requirements, and use cases, and defines an information model for recording interactions between elements implementing the I2RS protocol. This framework provides a consistent tracing interface for components implementing the I2RS architecture to record what was done, by which component, and when. It aims to improve the management of I2RS implementations, and can be used for troubleshooting, auditing, forensics, and accounting purposes.

この文書は、ルーティングシステムへのインターフェイス（Interface to the Routing System、I2RS）におけるトレーサビリティーのフレームワークと、そのフレームワークのための情報モデルについて説明します。この文書は、動機、要件、ユースケースを規定し、I2RSプロトコルを実装する要素間のやり取りを記録するための情報モデルを定義します。このフレームワークは、I2RSアーキテクチャーを実装するコンポーネントに対して、何が、どのコンポーネントによって、いつ行われたかを記録するための一貫したトレースインターフェイスを提供します。このフレームワークはI2RS実装の管理を改善することを目的としており、トラブルシューティング、監査、フォレンジック、アカウンティングの目的に使用できます。

1. Introduction

1. はじめに

The architecture for the Interface to the Routing System [RFC7921] specifies that I2RS clients wishing to retrieve or change the routing state on a routing element MUST authenticate to an I2RS agent. The I2RS client will have a unique identity it provides for authentication, and should provide another opaque identity for applications communicating through it. The programming of routing state will produce a return code containing the results of the specified operation and associated reason(s) for the result. All of this is critical information to be used for understanding the history of I2RS interactions.

ルーティングシステムへのインターフェイスのアーキテクチャー[RFC7921]は、ルーティング要素上のルーティング状態を取得または変更したいI2RSクライアントは、I2RSエージェントに対して認証しなければなりません（MUST）と規定しています。I2RSクライアントは、認証のために提示する一意のアイデンティティーを持ち、さらにそのクライアントを介して通信するアプリケーションのための別の不透明なアイデンティティーを提供するべきです。ルーティング状態のプログラミングは、指定された操作の結果とその結果に関連する理由を含むリターンコードを生成します。これらはすべて、I2RSのやり取りの履歴を理解するために使われる重要な情報です。

This document defines the framework necessary to trace those interactions between the I2RS client and I2RS agent. It goes on to describe use cases for traceability within I2RS. Based on these use cases, the document proposes an information model and reporting requirements to provide for effective recording of I2RS interactions. In this context, effective troubleshooting means being able to identify what operation was performed by a specific I2RS client via the I2RS agent, what was the result of the operation, and when that operation was performed.

この文書は、I2RSクライアントとI2RSエージェントの間のそうしたやり取りをトレースするために必要なフレームワークを定義します。続いて、I2RSにおけるトレーサビリティーのユースケースを説明します。これらのユースケースに基づいて、この文書は、I2RSのやり取りを効果的に記録するための情報モデルと報告の要件を提案します。この文脈において、効果的なトラブルシューティングとは、特定のI2RSクライアントがI2RSエージェントを介してどのような操作を行ったか、その操作の結果はどうだったか、そしてその操作がいつ行われたかを特定できることを意味します。

2. Terminology and Conventions

2. 用語と規則

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119].

この文書におけるキーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、「要求されています（REQUIRED）」、「することになります（SHALL）」、「することはありません（SHALL NOT）」、「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、「推奨されます（RECOMMENDED）」、「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、[RFC2119]に記載されているとおりに解釈されるものとします。

The architecture specification for I2RS [RFC7921] defines additional terms used in this document that are specific to the I2RS domain, such as "I2RS agent", "I2RS client", etc. The reader is expected to be familiar with the terminology and concepts defined in [RFC7921].

I2RSのアーキテクチャー仕様[RFC7921]は、「I2RSエージェント（I2RS agent）」や「I2RSクライアント（I2RS client）」など、この文書で使用するI2RS分野に固有の追加の用語を定義しています。読者は[RFC7921]で定義されている用語と概念に精通していることを前提とします。

3. Motivation

3. 動機

As networks scale and policy becomes an increasingly important part of the control plane that creates and maintains the forwarding state, operational complexity increases as well. I2RS offers more granular and coherent control over policy and control-plane state, but it also removes or reduces the locality of the policy that has been applied to the control plane at any individual forwarding device. The ability to automate and abstract even complex policy-based controls highlights the need for an equally scalable traceability function to provide recording at event-level granularity of the evolution of the routing system compliant with the requirements of I2RS (Section 5 of [RFC7920]).

ネットワークが拡大し、フォワーディング状態を作成・維持するコントロールプレーンにおいてポリシーがますます重要な部分を占めるようになるにつれ、運用の複雑さも増大します。I2RSは、ポリシーとコントロールプレーンの状態に対して、よりきめ細かく一貫性のある制御を提供しますが、その一方で、個々のフォワーディングデバイスにおいてコントロールプレーンに適用されたポリシーの局所性を取り除いたり、減らしたりします。複雑なポリシーベースの制御でさえも自動化・抽象化できるということは、I2RSの要件（[RFC7920]のセクション5）に準拠したルーティングシステムの変遷をイベントレベルの粒度で記録する、同様にスケーラブルなトレーサビリティー機能の必要性を浮き彫りにしています。

4. Use Cases

4. ユースケース

An obvious motivation for I2RS traceability is the need to troubleshoot and identify root causes of problems in these increasingly complex routing systems. For example, since I2RS is a high-throughput multi-channel, full duplex, and highly responsive interface, I2RS clients may be performing a large number of operations on I2RS agents concurrently or at nearly the same time and quite possibly in very rapid succession. As these many changes are made, the network reacts accordingly. These changes might lead to a race condition, performance issues, data loss, or disruption of services. In order to isolate the root cause of these issues, it is critical that a network operator or administrator has visibility into what changes were made via I2RS at a specific time.

I2RSのトレーサビリティーの明白な動機は、ますます複雑化するこうしたルーティングシステムにおいて、問題のトラブルシューティングを行い、その根本原因を特定する必要があることです。たとえば、I2RSは高スループットのマルチチャネル、全二重、かつ応答性の高いインターフェイスであるため、I2RSクライアントは、I2RSエージェントに対して多数の操作を並行して、あるいはほぼ同時に、そしておそらくは非常に短い間隔で連続して実行している可能性があります。こうした多くの変更が行われると、ネットワークはそれに応じて反応します。これらの変更は、競合状態、性能の問題、データの損失、サービスの中断につながるかもしれません。これらの問題の根本原因を切り分けるためには、ネットワーク運用者や管理者が、特定の時刻にI2RSを介してどのような変更が行われたかを把握できることが不可欠です。

Some network environments have strong auditing requirements for configuration and runtime changes. Other environments have policies that require saving logging information for operational or regulatory compliance considerations. These requirements therefore demand that I2RS provides an account of changes made to network element routing systems.

ネットワーク環境によっては、設定や実行時の変更に対して厳格な監査要件があります。また、運用上または規制遵守上の考慮から、ログ情報の保存を要求するポリシーを持つ環境もあります。したがって、これらの要件は、ネットワーク要素のルーティングシステムに対して行われた変更の記録をI2RSが提供することを求めます。

As I2RS becomes increasingly pervasive in routing environments, a traceability model that supports controllable trace log retention using a standardized structured data format offers significant advantages, such as the ability to create common tools supporting automated testing, and facilitates the following use cases:

I2RSがルーティング環境にますます広く普及するにつれ、標準化された構造化データ形式を使用して、制御可能なトレースログの保持をサポートするトレーサビリティーモデルは、自動テストをサポートする共通ツールを作成できるなどの大きな利点をもたらし、次のユースケースを容易にします。

  • real-time monitoring and troubleshooting of router events;
  • automated event correlation, trend analysis, and anomaly detection;
  • offline (manual or tools-based) analysis of router state evolution from the retained trace logs;
  • enhanced network audit, management, and forensic analysis capabilities;
  • improved accounting of routing system operations; and
  • providing a standardized format for incident reporting and test logging.
  • ルーターのイベントのリアルタイムの監視とトラブルシューティング
  • イベントの自動相関分析、傾向分析、異常検知
  • 保持されたトレースログからの、ルーター状態の変遷のオフライン（手動またはツールベース）の分析
  • ネットワークの監査、管理、フォレンジック分析の機能の強化
  • ルーティングシステムの操作のアカウンティングの改善
  • インシデント報告とテストログのための標準化された形式の提供

5. Information Model

5. 情報モデル

These sections describe the I2RS traceability information model and the details about each of the fields to be logged.

以下のセクションでは、I2RSのトレーサビリティー情報モデルと、ログに記録する各フィールドの詳細について説明します。

5.1. I2RS Traceability Framework

5.1. I2RSトレーサビリティーフレームワーク

This section describes a framework for I2RS traceability based on the I2RS Architecture.

このセクションでは、I2RSアーキテクチャーに基づくI2RSトレーサビリティーのフレームワークについて説明します。

5.2. I2RS Trace Log Fields

5.2. I2RSトレースログのフィールド

The following fields comprise an I2RS trace log. These fields ensure that each I2RS interaction can be properly traced back to the client that made the request at a specific point in time.

I2RSトレースログは以下のフィールドで構成されます。これらのフィールドにより、I2RSの各やり取りを、特定の時点でリクエストを行ったクライアントまで適切にさかのぼってトレースできることが保証されます。

The list below describes the fields captured in the I2RS trace log. This list represents a common set of fields that MUST appear in all I2RS trace logs. In addition to these fields, I2RS agent implementations MAY choose to log additional fields such as I2RS client vendor or agent statistics like free memory, performance metrics, etc.

以下のリストでは、I2RSトレースログに取り込まれるフィールドについて説明します。このリストは共通のフィールドの集合を表しており、これらのフィールドはすべてのI2RSトレースログに現れなければなりません（MUST）。これらのフィールドに加えて、I2RSエージェントの実装は、I2RSクライアントのベンダーや、空きメモリー、性能メトリクスなどのエージェントの統計情報といった追加のフィールドをログに記録することを選択してもよいです（MAY）。

Event ID:
This is a unique identifier for each event in the I2RS trace log. An event can be a client authenticating with the agent, a client to agent operation, or a client disconnecting from an agent. Operation events can either be logged atomically upon completion (in which case they will have both a Starting and an Ending Timestamp field) or they can be logged at the beginning of each Request State transition. Since operations can occur from the same client at the same time, it is important to have an identifier that can be unambiguously associated to a specific entry. If each state transition is logged for an operation, the same ID MUST be used for each of the Request State log entries. In this way, the life of a request can be easily followed in the I2RS trace log. Beyond the requirement that the Event ID MUST be unique for each event, the specific type and value is left up to the implementation.
Starting Timestamp:
The specific time at which the I2RS operation enters the specified Request State within the agent. If the log entry covers the entire duration of the request, then this will be the time that it was first received by the agent. This field MUST be present in all entries that specify the beginning of the state transition, as well as those entries that log the entire duration of the request. The time is passed in the full timestamp format [RFC3339], including the date and offset from Coordinated Universal Time (UTC). Given that many I2RS operations can occur in rapid succession, the fractional seconds element of the timestamp MUST be used to provide adequate granularity. Fractional seconds SHOULD be expressed with at least three significant digits in second.microsecond format.
Request State:

The state of the given operation within the I2RS agent state machine at the specified Starting or Ending Timestamps. The I2RS agent SHOULD generate a log entry at the moment a request enters and exits a state. Upon entering a new state, the log entry will have a Starting Timestamp set to the time of entry and no Ending Timestamp. Upon exiting a state, the log entry will have an Ending Timestamp set to the time of exit and no Starting Timestamp. The progression of the request through its various states can be linked using the Event ID. The states can be one of the following values:

PENDING:
The request has been received and queued for processing.
IN PROCESS:
The request is currently being handled by the I2RS agent.
COMPLETED:
The request has reached a terminal point.

Every state transition SHOULD be logged unless doing so will put an undue performance burden on the I2RS agent. However, an entry with the Request State set to COMPLETED MUST be logged for all operations. If the COMPLETED state is the only entry for a given request, then it MUST have both Starting and Ending Timestamps that cover the entire duration of the request from ingress to the agent until completion.

Client Identity:
The I2RS client identity used to authenticate the client to the I2RS agent.
Client Priority:
The I2RS client priority assigned by the access control model that authenticates the client. For example, this can be set by the Network Configuration Protocol (NETCONF) Access Control Model (NACM) as described in [RFC6536].
Secondary Identity:
This is an opaque identity that may be known to the client from a controlling network application. This is used to trace the network application driving the actions of the client. The client may not provide this identity to the agent if there is no external network application driving the client. However, this field MUST be logged even if the client does not provide a Secondary Identity. In that case, the field will be logged with an empty value.
Client Address:
This is the network address of the client that connected to the agent. For example, this may be an IPv4 or an IPv6 address.
Requested Operation:

This is the I2RS operation that was requested to be performed. For example, this may be an add route operation if a route is being inserted into a routing table. This may not be the operation that was actually applied to the agent.

In the case of a client authenticating to the agent, the Requested Operation MUST be "CLIENT AUTHENTICATE". In the case of a client disconnecting from the agent, the Requested Operation MUST be "CLIENT DISCONNECT".

Applied Operation:
This is the I2RS operation that was actually performed. This can differ from the Requested Operation in cases where the agent cannot satisfy the Requested Operation. This field may not be logged unless the Request State is COMPLETED.
Operation Data Present:
This is a Boolean field that indicates whether or not additional per-Operation Data is present.
Requested Operation Data:

This field comprises the data passed to the agent to complete the desired operation. For example, if the operation is a route add operation, the Operation Data would include the route prefix, prefix length, and next-hop information to be inserted as well as the specific routing table to which the route will be added. If Operation Data is provided, then the Operation Data Present field MUST be set to TRUE. Some operations may not provide operation data. In those cases, the Operation Data Present field MUST be set to FALSE, and this field MUST be empty. This may not represent the data that was used for the operation that was actually applied on the agent.

When a client authenticates to the agent, the Requested Operation Data MUST contain the client priority. Other attributes such as credentials used for authentication MAY be logged.

Applied Operation Data:
This field comprises the data that was actually applied as part of the Applied Operation. If the agent cannot satisfy the Requested Operation with the Requested Operation Data, then this field can differ from the Requested Operation Data. This field will be empty unless the Requested Operation Data was specified. This field may not be logged unless the Request State is COMPLETED.
Transaction ID:
The Transaction Identity represents that this particular operation is part of a long-running I2RS transaction that can consist of multiple, related I2RS operations. Using this value, one can relate multiple log entries together as they are part of a single, overall I2RS operation. This is an optional field that may not be logged unless the event is part of a long-running transaction.
Result Code:
This field holds the result of the operation once the Request State is COMPLETED. In the case of Routing Information Base (RIB) operations, this MUST be the return code as specified in Section 4 of [RIBINFO]. The operation may not complete with a result code in the case of a timeout. If the operation fails to complete, it MUST still log the attempted operation with an appropriate result code.
Timeout Occurred:
This is a Boolean field that indicates whether or not a timeout occurred in the operation. When this is true, the value of the Ending Timestamp MUST be set to the time the agent recorded for the timeout occurrence. This field may not be logged unless the Request State is COMPLETED.
Ending Timestamp:
The specific time at which the I2RS operation exits the specified Request State within the I2RS agent. If the log entry covers the entire duration of the request, then this will be the time that the request reached a terminal point within the agent. This field MUST be present in all entries that specify the ending of the state transition, as well as those entries that log the entire duration of the request. The time is passed in the full timestamp format [RFC3339], including the date and offset from Coordinated Universal Time (UTC). See the description for Starting Timestamp above for the proper format of the Ending Timestamp.
End Of Message:
Each log entry SHOULD have an appropriate End Of Message (EOM) indicator. See Section 5.3 below for more details.
Event ID:
これは、I2RSトレースログ内の各イベントに対する一意の識別子です。イベントとは、クライアントによるエージェントへの認証、クライアントからエージェントへの操作、またはクライアントのエージェントからの切断のいずれかです。操作のイベントは、完了時にアトミックに記録される（この場合、Starting TimestampフィールドとEnding Timestampフィールドの両方を持ちます）か、各Request Stateの遷移の開始時に記録されるかのどちらかです。同じクライアントから同時に複数の操作が発生する可能性があるため、特定のエントリーに曖昧さなく関連付けられる識別子を持つことが重要です。ある操作について各状態遷移を記録する場合、Request Stateの各ログエントリーには同じIDを使用しなければなりません（MUST）。こうすることで、I2RSトレースログの中でリクエストのライフサイクルを容易に追跡できます。Event IDが各イベントに対して一意でなければなりません（MUST）という要件以外の、具体的な型や値は実装に任されます。
Starting Timestamp:
I2RSの操作がエージェント内で指定されたRequest Stateに入った具体的な時刻です。ログエントリーがリクエストの全期間を対象とする場合、これはエージェントがリクエストを最初に受信した時刻になります。このフィールドは、状態遷移の開始を示すすべてのエントリーと、リクエストの全期間を記録するエントリーに存在しなければなりません（MUST）。時刻は、日付と協定世界時（UTC）からのオフセットを含む完全なタイムスタンプ形式[RFC3339]で渡されます。多くのI2RSの操作が短い間隔で連続して発生しうることを考慮し、十分な粒度を提供するために、タイムスタンプの小数秒の要素を使用しなければなりません（MUST）。小数秒は、秒.マイクロ秒の形式で、少なくとも3桁の有効数字で表現すべきです（SHOULD）。
Request State:

指定されたStarting TimestampまたはEnding Timestampの時点における、I2RSエージェントの状態機械の中での当該操作の状態です。I2RSエージェントは、リクエストがある状態に入った時点と、その状態から出た時点でログエントリーを生成すべきです（SHOULD）。新しい状態に入ったときのログエントリーは、Starting Timestampに状態に入った時刻が設定され、Ending Timestampを持ちません。ある状態から出たときのログエントリーは、Ending Timestampに状態から出た時刻が設定され、Starting Timestampを持ちません。リクエストがさまざまな状態を経て進んでいく過程は、Event IDを使って関連付けることができます。状態は次のいずれかの値をとります。

PENDING:
リクエストが受信され、処理待ちのキューに入れられています。
IN PROCESS:
リクエストは現在I2RSエージェントによって処理されています。
COMPLETED:
リクエストは終端点に到達しました。

I2RSエージェントに過度な性能上の負担をかけることにならない限り、すべての状態遷移をログに記録すべきです（SHOULD）。ただし、Request StateがCOMPLETEDに設定されたエントリーは、すべての操作についてログに記録しなければなりません（MUST）。COMPLETED状態があるリクエストの唯一のエントリーである場合、そのエントリーは、エージェントへの到着から完了までのリクエストの全期間を対象とするStarting TimestampとEnding Timestampの両方を持たなければなりません（MUST）。

Client Identity:
I2RSエージェントに対してクライアントを認証するために使用されるI2RSクライアントのアイデンティティーです。
Client Priority:
クライアントを認証するアクセス制御モデルによって割り当てられたI2RSクライアントの優先度です。たとえば、これは[RFC6536]で説明されているネットワーク設定プロトコル（NETCONF）アクセス制御モデル（NACM）によって設定できます。
Secondary Identity:
これは、クライアントを制御するネットワークアプリケーションからクライアントに知らされることがある不透明なアイデンティティーです。これは、クライアントの動作を駆動しているネットワークアプリケーションをトレースするために使用されます。クライアントを駆動する外部のネットワークアプリケーションが存在しない場合、クライアントはこのアイデンティティーをエージェントに提供しないかもしれません。しかし、クライアントがSecondary Identityを提供しない場合でも、このフィールドはログに記録しなければなりません（MUST）。その場合、このフィールドは空の値で記録されます。
Client Address:
これは、エージェントに接続したクライアントのネットワークアドレスです。たとえば、これはIPv4アドレスまたはIPv6アドレスである場合があります。
Requested Operation:

これは、実行を要求されたI2RSの操作です。たとえば、ルートをルーティングテーブルに挿入する場合、これはルート追加の操作になるでしょう。これは、実際にエージェントに適用された操作ではないかもしれません。

クライアントがエージェントに対して認証する場合、Requested Operationは「CLIENT AUTHENTICATE」でなければなりません（MUST）。クライアントがエージェントから切断する場合、Requested Operationは「CLIENT DISCONNECT」でなければなりません（MUST）。

Applied Operation:
これは、実際に実行されたI2RSの操作です。エージェントがRequested Operationを満たせない場合、これはRequested Operationと異なることがあります。このフィールドは、Request StateがCOMPLETEDでない限り、ログに記録されないかもしれません。
Operation Data Present:
これは、操作ごとの追加のOperation Dataが存在するかどうかを示すブール型のフィールドです。
Requested Operation Data:

このフィールドは、目的の操作を完了するためにエージェントに渡されたデータで構成されます。たとえば、操作がルート追加の操作である場合、Operation Dataには、挿入するルートのプレフィックス、プレフィックス長、ネクストホップの情報に加えて、ルートを追加する特定のルーティングテーブルが含まれるでしょう。Operation Dataが提供される場合、Operation Data PresentフィールドをTRUEに設定しなければなりません（MUST）。操作によっては、操作データを提供しないものもあります。そのような場合、Operation Data PresentフィールドをFALSEに設定しなければなりません（MUST）。また、このフィールドは空でなければなりません（MUST）。これは、実際にエージェントに適用された操作に使われたデータを表していないかもしれません。

クライアントがエージェントに対して認証する場合、Requested Operation Dataにはクライアントの優先度を含めなければなりません（MUST）。認証に使用されたクレデンシャルなどのその他の属性をログに記録してもよいです（MAY）。

Applied Operation Data:
このフィールドは、Applied Operationの一部として実際に適用されたデータで構成されます。エージェントがRequested Operation DataでRequested Operationを満たせない場合、このフィールドはRequested Operation Dataと異なることがあります。このフィールドは、Requested Operation Dataが指定されていない限り空になります。このフィールドは、Request StateがCOMPLETEDでない限り、ログに記録されないかもしれません。
Transaction ID:
Transaction Identityは、この特定の操作が、関連する複数のI2RSの操作で構成されうる長時間実行のI2RSトランザクションの一部であることを表します。この値を使うと、複数のログエントリーが単一の全体的なI2RSの操作の一部であるとして、それらを互いに関連付けることができます。これは省略可能なフィールドであり、イベントが長時間実行のトランザクションの一部でない限り、ログに記録されないかもしれません。
Result Code:
このフィールドは、Request StateがCOMPLETEDになった時点での操作の結果を保持します。ルーティング情報ベース（Routing Information Base、RIB）の操作の場合、これは[RIBINFO]のセクション4で規定されているリターンコードでなければなりません（MUST）。タイムアウトの場合、操作は結果コードを伴って完了しないかもしれません。操作が完了に失敗した場合でも、試行された操作を適切な結果コードとともにログに記録しなければなりません（MUST）。
Timeout Occurred:
これは、操作においてタイムアウトが発生したかどうかを示すブール型のフィールドです。これが真の場合、Ending Timestampの値には、エージェントがタイムアウトの発生について記録した時刻を設定しなければなりません（MUST）。このフィールドは、Request StateがCOMPLETEDでない限り、ログに記録されないかもしれません。
Ending Timestamp:
I2RSの操作がI2RSエージェント内で指定されたRequest Stateから出た具体的な時刻です。ログエントリーがリクエストの全期間を対象とする場合、これはリクエストがエージェント内で終端点に到達した時刻になります。このフィールドは、状態遷移の終了を示すすべてのエントリーと、リクエストの全期間を記録するエントリーに存在しなければなりません（MUST）。時刻は、日付と協定世界時（UTC）からのオフセットを含む完全なタイムスタンプ形式[RFC3339]で渡されます。Ending Timestampの適切な形式については、前述のStarting Timestampの説明を参照してください。
End Of Message:
各ログエントリーは、適切なメッセージ終端（End Of Message、EOM）指示子を持つべきです（SHOULD）。詳細については後述のセクション5.3を参照してください。

5.3. End of Message Marker

5.3. メッセージ終端マーカー

Because of variability within I2RS trace log fields, implementors MUST use a format-appropriate End Of Message (EOM) indicator in order to signify the end of a particular record. That is, regardless of format, the I2RS trace log MUST provide a distinct way of distinguishing between the end of one record and the beginning of another. For example, in a linear-formatted log (similar to a syslog) the EOM marker may be a newline character. In an XML-formatted log, the schema would provide for element tags that denote the beginning and end of records. In a JSON-formatted log, the syntax would provide record separation (likely by comma-separated array elements).

I2RSトレースログのフィールドには可変性があるため、実装者は、特定のレコードの終わりを示すために、形式に適したメッセージ終端（EOM）指示子を使用しなければなりません（MUST）。つまり、形式にかかわらず、I2RSトレースログは、あるレコードの終わりと別のレコードの始まりを区別するための明確な方法を提供しなければなりません（MUST）。たとえば、（syslogのような）行形式のログでは、EOMマーカーは改行文字になるでしょう。XML形式のログでは、スキーマがレコードの始まりと終わりを示す要素タグを提供するでしょう。JSON形式のログでは、構文がレコードの区切りを（おそらくカンマ区切りの配列要素によって）提供するでしょう。

7. Operational Guidance

7. 運用上のガイダンス

Specific operational procedures regarding temporary log storage, rollover, retrieval, and access of I2RS trace logs is out of scope for this document. Organizations employing I2RS trace logging are responsible for establishing proper operational procedures that are appropriately suited to their specific requirements and operating environment. In this section, we only provide fundamental and generalized operational guidelines that are implementation independent.

I2RSトレースログの一時保存、ロールオーバー、取得、アクセスに関する具体的な運用手順は、この文書の範囲外です。I2RSトレースログを利用する組織は、自らの具体的な要件と運用環境に適した、適切な運用手順を確立する責任があります。このセクションでは、実装に依存しない基本的かつ一般化された運用上のガイドラインのみを示します。

7.1. Trace Log Creation

7.1. トレースログの作成

The I2RS agent interacts with the Routing and Signaling functions of the Routing Element. Since the I2RS agent is responsible for actually making the routing changes on the associated network device, it creates and maintains a log of operations that can be retrieved to troubleshoot I2RS-related impact to the network. Changes that occur to the network element's local configuration outside of the I2RS protocol that preempt I2RS state will only be logged if the network element notifies the I2RS agent.

I2RSエージェントは、ルーティング要素のルーティング機能およびシグナリング機能とやり取りします。I2RSエージェントは、関連するネットワークデバイス上で実際にルーティングの変更を行う役割を担うため、ネットワークに対するI2RS関連の影響をトラブルシューティングするために取得できる操作のログを作成し、維持します。I2RSプロトコルの外部でネットワーク要素のローカル設定に対して発生し、I2RSの状態に優先する変更は、ネットワーク要素がI2RSエージェントに通知した場合にのみログに記録されます。

7.2. Trace Log Temporary Storage

7.2. トレースログの一時保存

The trace information may be temporarily stored either in an in-memory buffer or as a file local to the agent. Care should be given to the number of I2RS operations expected on a given agent so that the appropriate storage medium is used, and to maximize the effectiveness of the log while not impacting the performance and health of the agent. client requests may not always be processed synchronously or within a bounded time period. Consequently, to ensure that trace log fields, such as "Operation" and "Result Code", are part of the same trace log record, buffering of the trace log entries may be required. This buffering may result in additional resource load on the agent and the network element.

トレース情報は、インメモリーのバッファー、またはエージェントのローカルのファイルのいずれかに一時的に保存できます。適切な記憶媒体を使用するとともに、エージェントの性能と健全性に影響を与えずにログの有効性を最大化するために、特定のエージェントで予想されるI2RSの操作の数に注意を払うべきです。クライアントのリクエストは、常に同期的に、または有限の時間内に処理されるとは限りません。その結果、「Operation」や「Result Code」などのトレースログのフィールドが同じトレースログレコードの一部となるようにするために、トレースログのエントリーのバッファリングが必要になる場合があります。このバッファリングにより、エージェントとネットワーク要素に追加のリソース負荷がかかる可能性があります。

Section 7.3 discusses rotating the trace log in order to preserve the operation history without exhausting agent or network device resources. It is perfectly acceptable, therefore, to use both an in-memory buffer for recent operations while rotating or archiving older operations to a local file.

セクション7.3では、エージェントやネットワークデバイスのリソースを使い果たすことなく操作の履歴を保存するために、トレースログをローテーションすることについて説明します。したがって、最近の操作にはインメモリーのバッファーを使用しつつ、古い操作をローカルファイルにローテーションまたはアーカイブするという両方の方法を併用することは、まったく問題ありません。

It is outside the scope of this document to specify the implementation details (i.e., size, throughput, data protection, etc.) for the physical storage of the I2RS log file. In terms of data retention, attention should be paid to the length of time that the I2RS trace log data is kept when that data contains security- or privacy-sensitive attributes. The longer this data is retained, the higher the impact if it were to be leaked. It is also possible that legislation may impose some additional requirements on the minimum and/or maximum durations for which some kinds of data may be retained.

I2RSログファイルの物理的な保存に関する実装の詳細（すなわち、サイズ、スループット、データ保護など）を規定することは、この文書の範囲外です。データの保持に関しては、I2RSトレースログのデータにセキュリティーやプライバシーに関わる機微な属性が含まれる場合、そのデータを保持する期間の長さに注意を払うべきです。このデータを保持する期間が長いほど、それが漏洩した場合の影響は大きくなります。また、法律によって、ある種のデータを保持できる最短期間や最長期間に関して、追加の要件が課される可能性もあります。

7.3. Trace Log Rotation

7.3. トレースログのローテーション

In order to prevent the exhaustion of resources on the I2RS agent or its associated network device, it is RECOMMENDED that the I2RS agent implements trace log rotation. The details on how this is achieved are left to the implementation and are outside the scope of this document. However, it should be possible to do a file rotation based on either the time or size of the current trace log. If file rollover is supported, multiple archived log files should be supported in order to maximize the troubleshooting and accounting benefits of the trace log.

I2RSエージェントやそれに関連するネットワークデバイスのリソースの枯渇を防ぐために、I2RSエージェントがトレースログのローテーションを実装することが推奨されます（RECOMMENDED）。その実現方法の詳細は実装に任されており、この文書の範囲外です。ただし、現在のトレースログの時間またはサイズのいずれかに基づいてファイルのローテーションを行えるようにするべきです。ファイルのロールオーバーをサポートする場合、トレースログのトラブルシューティングとアカウンティングにおける利点を最大化するために、複数のアーカイブされたログファイルをサポートするべきです。

7.4. Trace Log Retrieval

7.4. トレースログの取得

Implementors are free to provide their own, proprietary interfaces and develop custom tools to retrieve and display the I2RS trace log. These may include the display of the I2RS trace log as command-line interface (CLI) output. However, a key intention of defining this information model is to establish a vendor-agnostic and consistent interface to collect I2RS trace data. Correspondingly, retrieval of the data should also be made vendor-agnostic.

実装者は、I2RSトレースログを取得して表示するための独自の専用インターフェイスを提供したり、カスタムツールを開発したりすることが自由にできます。これには、I2RSトレースログをコマンドラインインターフェイス（CLI）の出力として表示することも含まれるでしょう。しかし、この情報モデルを定義する主な意図は、I2RSのトレースデータを収集するための、ベンダーに依存しない一貫したインターフェイスを確立することです。それに応じて、データの取得もベンダーに依存しないものにするべきです。

Despite the fact that export of I2RS trace log information could be an invaluable diagnostic tool for off-box analysis, exporting this information MUST NOT interfere with the ability of the agent to process new incoming operations.

I2RSトレースログ情報のエクスポートは、機器外での分析のための非常に貴重な診断ツールになりえますが、それでもこの情報のエクスポートが、新たに到着する操作を処理するエージェントの能力を妨げてはなりません（MUST NOT）。

The following three sections describe potential ways the trace log can be accessed. The use of I2RS pub/sub for accessing trace log data is mandatory-to-implement, while others are optional.

続く3つのセクションでは、トレースログにアクセスする可能な方法について説明します。トレースログのデータにアクセスするためのI2RS pub/subの使用は実装必須（mandatory-to-implement）であり、その他の方法は省略可能です。

7.4.1. Retrieval via Syslog

7.4.1. Syslogによる取得

The syslog protocol [RFC5424] is a standard way of sending event notification messages from a host to a collector. However, the protocol does not define any standard format for storing the messages, and thus implementors of I2RS tracing would be left to define their own format. So, while the data contained within the syslog message would adhere to this information model, and may be consumable by a human operator, it would not be easily parseable by a machine. Syslog MAY be employed as a means of retrieving or disseminating the I2RS trace log contents.

syslogプロトコル[RFC5424]は、イベント通知メッセージをホストからコレクターへ送信するための標準的な方法です。しかし、このプロトコルはメッセージを保存するための標準形式を何も定義していないため、I2RSトレースの実装者は独自の形式を定義しなければならないことになります。そのため、syslogメッセージに含まれるデータはこの情報モデルに従い、人間の運用者が利用することはできるかもしれませんが、機械で容易に解析できるものにはならないでしょう。Syslogは、I2RSトレースログの内容を取得または配布する手段として使用してもよいです（MAY）。

If syslog is used for trace log retrieval, then existing logging infrastructure and capabilities of syslog [RFC5424] should be leveraged without the need to define or extend existing formats. That is, the various fields described in Section 5.2 SHOULD be modeled and encoded as Structured Data Elements (referred to as "SD-ELEMENT"), as described in Section 6.3.1 of [RFC5424].

トレースログの取得にsyslogを使用する場合、既存の形式を定義したり拡張したりする必要なしに、syslog[RFC5424]の既存のロギング基盤と機能を活用するべきです。つまり、セクション5.2で説明したさまざまなフィールドは、[RFC5424]のセクション6.3.1で説明されているように、構造化データ要素（Structured Data Element、「SD-ELEMENT」と呼ばれます）としてモデル化し、エンコードすべきです（SHOULD）。

7.4.2. Retrieval via I2RS Information Collection

7.4.2. I2RS情報収集による取得

Section 7.7 of the I2RS architecture [RFC7921] defines a mechanism for information collection. The information collected includes obtaining a snapshot of a large amount of data from the network element. It is the intent of I2RS to make this data available in an implementor-agnostic fashion. Therefore, the I2RS trace log SHOULD be made available via the I2RS information collection mechanism either as a single snapshot or via a subscription stream.

I2RSアーキテクチャー[RFC7921]のセクション7.7では、情報収集のためのメカニズムを定義しています。収集される情報には、ネットワーク要素から大量のデータのスナップショットを取得することが含まれます。このデータを実装者に依存しない方法で利用可能にすることがI2RSの意図です。したがって、I2RSトレースログは、単一のスナップショットとして、またはサブスクリプションストリームを介して、I2RSの情報収集メカニズムを通じて利用可能にするべきです（SHOULD）。

7.4.3. Retrieval via I2RS Pub/Sub

7.4.3. I2RS Pub/Subによる取得

Section 7.6 of the I2RS architecture [RFC7921] goes on to describe notification mechanisms for a feed of changes happening within the I2RS layer. Specifically, the requirements for a publish-subscribe system for I2RS are defined in [RFC7923]. I2RS agents MUST support publishing I2RS trace log information to that feed as described in [RFC7923]. Subscribers would then receive a live stream of I2RS interactions in trace log format and could flexibly choose to do a number of things with the log messages. For example, the subscribers could log the messages to a datastore, aggregate, and summarize interactions from a single client, etc. The full range of potential activities is virtually limitless and the details of how they are performed are outside the scope of this document, however.

I2RSアーキテクチャー[RFC7921]のセクション7.6では、さらに、I2RS層内で発生する変更のフィードのための通知メカニズムについて説明しています。具体的には、I2RSのためのパブリッシュ・サブスクライブシステムの要件が[RFC7923]で定義されています。I2RSエージェントは、[RFC7923]で説明されているように、そのフィードへのI2RSトレースログ情報のパブリッシュをサポートしなければなりません（MUST）。そうすれば、サブスクライバーはトレースログ形式でI2RSのやり取りのライブストリームを受信し、ログメッセージを使って行う多くのことを柔軟に選択できるでしょう。たとえば、サブスクライバーは、メッセージをデータストアに記録したり、単一のクライアントからのやり取りを集約して要約したりすることができるでしょう。ただし、考えられる活動の範囲は事実上無限であり、それらをどのように実行するかの詳細はこの文書の範囲外です。

8. Security Considerations

8. セキュリティーに関する考慮事項

The I2RS trace log, like any log file, reveals the state of the entity producing it as well as the identifying information elements and detailed interactions of the system containing it. The information model described in this document does not itself introduce any security issues, but it does define the set of attributes that make up an I2RS log file. These attributes may contain sensitive information, and thus should adhere to the security, privacy, and permission policies of the organization making use of the I2RS log file.

I2RSトレースログは、他のあらゆるログファイルと同様に、それを生成するエンティティーの状態に加えて、それを含むシステムの識別情報要素と詳細なやり取りを明らかにします。この文書で説明する情報モデルそれ自体は、いかなるセキュリティー上の問題ももたらしませんが、I2RSログファイルを構成する属性の集合を定義しています。これらの属性には機微な情報が含まれる可能性があるため、I2RSログファイルを利用する組織のセキュリティー、プライバシー、権限に関するポリシーに従うべきです。

It is outside the scope of this document to specify how to protect the stored log file, but it is expected that adequate precautions and security best practices such as disk encryption, appropriately restrictive file/directory permissions, suitable hardening and physical security of logging entities, mutual authentication, transport encryption, channel confidentiality, and channel integrity if transferring log files. Additionally, the potentially sensitive information contained in a log file SHOULD be adequately anonymized or obfuscated by operators to ensure its privacy.

保存されたログファイルを保護する方法を規定することはこの文書の範囲外ですが、ディスクの暗号化、適切に制限されたファイル／ディレクトリーのパーミッション、ロギングを行うエンティティーの適切なハードニングと物理的セキュリティー、さらにログファイルを転送する場合には相互認証、トランスポートの暗号化、チャネルの機密性、チャネルの完全性といった、十分な予防措置とセキュリティーのベストプラクティスが講じられることが期待されます。さらに、ログファイルに含まれる機微である可能性のある情報は、そのプライバシーを確保するために、運用者が適切に匿名化または難読化すべきです（SHOULD）。
