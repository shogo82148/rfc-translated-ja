RFC 608

Host names on-line

RFC 608

オンラインのホスト名

Abstract

概要

We at the NIC agree with Peter Deutsch's suggestion (in RFC# 606 / NIC# 21246) that the NIC maintain an online ASCII text file of Host names, addresses, and attributes. That suggestion corresponds to one made by Vint Cerf recently, and evidently receives ARPA/IPT support.

NICの私たちは、ホスト名、アドレス、属性のオンラインのASCIIテキストファイルをNICが保守するという、Peter Deutschの提案（RFC# 606 / NIC# 21246）に同意します。この提案は、最近Vint Cerfが行った提案と一致しており、ARPA/IPTの支援も得られているようです。

Jake Feinler at the NIC designed and maintains a source file, in NLS format, that can be used to generate the ASCII file Peter outlined. A program to generate an up to date version of the ASCII file needs to be written at the NIC, and run periodically (weekly, or as the situation warrants). Such a mechanism would allow us, of course, to maintain one source of data and use it for this and other purposes.

NICのJake Feinlerは、Peterが概略を示したASCIIファイルを生成するのに使えるソースファイルをNLS形式で設計し、保守しています。ASCIIファイルの最新版を生成するプログラムをNICで作成し、定期的に（毎週、または状況に応じて）実行する必要があります。もちろん、このような仕組みがあれば、1つのデータソースを保守して、それをこの目的にも他の目的にも使えるようになります。

Our present data includes official Host name, Host address, Host status (user, server, TIP) and certain other information like Technical Liaison, Host computer, operating system, etc.

現在のデータには、公式のホスト名、ホストアドレス、ホストのステータス（ユーザー、サーバー、TIP）と、技術連絡担当者（Technical Liaison）、ホストコンピューター、オペレーティングシステムなどのその他の特定の情報が含まれています。

Provisions exist for including attributes of the type Peter suggested (for example FTP byte size, TELNET duplex mode, echoing mode, and nicknames), but these data are currently NOT in our source file.

Peterが提案した種類の属性（たとえば、FTPのバイトサイズ、TELNETの二重モード、エコーモード、ニックネーム）を含めるための準備はありますが、これらのデータは現在のところソースファイルに含まれて「いません」。

To get things moving, therefore, we propose to do the following things:

そこで、物事を進めるために、次のことを行うことを提案します。

  1. We shall write a program to generate the ASCII file in the syntax described in RFC# 606, namely:

    <host-name-file> ::= <entry> / <host-name-file> <entry>

<entry> ::= <data-part> <end-of-line>

    Note that this produces a blank line after the <data-part>.

    <data-part> ::= <basic-part> / <data-part> <attribute-item>

<basic-part> ::= <host-name> , <host-address> <end-of-line>

<attribute-item> ::= <attribute-name> = <attribute-value> <end-
of-line>

  2. We shall initially include only the following items in each <entry>:

    1. <basic-part>

      in which <host-address> will be a decimal host address, relative to the Host's own Network, and

      in which <host-name> will be the official Host Name, a string obtained through negotiation between the Host and the NIC, governed by these constraints:

      • up to 48 characters drawn from the alphabet (A-Z), digits (0-9), and the minus sign (-) ... specifically, no blank or space characters allowed;
      • no distinction between upper and lower case letters;
      • the first character is a letter;
      • the last character is NOT a minus sign;
      • no other restrictions on content or syntax.

      Note: The Host Name may be prefixed with an Official Network Name of up to 24 characters enclosed in parentheses (). The Network Name designates the Network in which the Host resides.

      (The characters used in the Network Name are drawn from the same character set as those in the Host Name, with the same constraints [except the length] as listed above.)

      The ASCII text file will only contain the Official Network name for Hosts NOT on the ARPANET; for ARPANET Hosts there will be no Network Name prefix.

    2. <attribute-item>

      in which <attribute-name> initially will have the single possible value STATUS, and the corresponding value of <attribute-value> for STATUS will be one of these:

      • SERVER
      • USER
      • TIP
      • UNKNOWN

    3. <end-of-line>

      this will be carriage return followed by line feed (octal 015 followed by octal 12).

  3. Attributes other than those for which <attribute-name> is STATUS will be added in the above format at a later date (to be announced) as the data becomes available to us.

    We agree with Peter that the attribute list should not be construed as replacing option negotiation or any other means by which one Host discovers the properties of another, but merely as an alternative source of information that is simply and easily accessible, in machine-readable form.

    Suggestions for attributes that are worthy of inclusion in the ASCII file of Hostnames are welcome. Please send your suggestions and/or data to Jake Feinler
    FEINLER @ SRI-ARC, or NIC Ident = JAKE

    For completeness, we record here the attribute suggestions given in RFC# 606:

    NICKNAMES -- value is a list of acceptable nicknames for the host. Any system that provides name-to-address translation is encouraged (although of course not required) to accept these names as alternatives to the official host name.

    FTP-BYTE-SIZES -- value is a list of the byte sizes supported by the FTP server. The first byte size is the one which leads to the least computational overhead (e.g. 36 for PDP-10's, 32 for 360's).

    ECHOING -- value is L or R depending on whether the host expects the terminal to echo (Remote) or expects to do its own echoing (Local).

  1. RFC# 606で説明されている構文、すなわち次の構文でASCIIファイルを生成するプログラムを作成します。

    <host-name-file> ::= <entry> / <host-name-file> <entry>

<entry> ::= <data-part> <end-of-line>

    これにより、<data-part>の後に空行ができることに注意してください。

    <data-part> ::= <basic-part> / <data-part> <attribute-item>

<basic-part> ::= <host-name> , <host-address> <end-of-line>

<attribute-item> ::= <attribute-name> = <attribute-value> <end-
of-line>

  2. 当初は、各<entry>に次の項目だけを含めます。

    1. <basic-part>

      ここで、<host-address>は、ホスト自身のネットワークを基準とした10進数のホストアドレスです。

      また、<host-name>は公式のホスト名です。これはホストとNICの間のネゴシエーションによって決まる文字列で、次の制約に従います。

      • 英字（A-Z）、数字（0-9）、マイナス記号（-）から成る48文字以内。特に、空白文字やスペース文字は使えません。
      • 大文字と小文字を区別しません。
      • 最初の文字は英字です。
      • 最後の文字はマイナス記号では「ありません」。
      • 内容や構文に関するその他の制約はありません。

      注: ホスト名の前に、括弧（）で囲んだ24文字以内の公式ネットワーク名を付けることがあります。ネットワーク名は、そのホストが存在するネットワークを示します。

      （ネットワーク名に使う文字は、ホスト名と同じ文字集合から選び、上記と同じ制約［長さを除く］に従います。）

      ASCIIテキストファイルには、ARPANET上に「ない」ホストについてのみ公式ネットワーク名を含めます。ARPANETのホストには、ネットワーク名の接頭辞は付きません。

    2. <attribute-item>

      ここで、<attribute-name>は当初STATUSという値だけをとり、STATUSに対応する<attribute-value>の値は次のいずれかです。

      • SERVER
      • USER
      • TIP
      • UNKNOWN

    3. <end-of-line>

      これは、キャリッジリターンに続くラインフィードです（8進数の015に続く8進数の12）。

  3. <attribute-name>がSTATUSであるもの以外の属性は、データが入手でき次第、後日（日時は追って告知します）、上記の形式で追加します。

    属性の一覧は、オプションのネゴシエーションや、あるホストが別のホストの特性を知るためのその他の手段に代わるものと解釈すべきではなく、機械可読形式で簡単に入手できる代替の情報源にすぎないという点で、私たちはPeterに同意します。

    ホスト名のASCIIファイルに含める価値のある属性の提案を歓迎します。提案やデータは、Jake Feinler宛てに送ってください。
    FEINLER @ SRI-ARC、またはNIC Ident = JAKE

    網羅性のために、RFC# 606で示された属性の提案をここに記録しておきます。

    NICKNAMES：値は、そのホストの受け入れ可能なニックネームの一覧です。名前からアドレスへの変換を提供するシステムは、公式のホスト名の代わりとしてこれらの名前を受け付けることが推奨されます（もちろん必須ではありません）。

    FTP-BYTE-SIZES：値は、FTPサーバーがサポートしているバイトサイズの一覧です。最初のバイトサイズが、計算のオーバーヘッドが最も少なくなるものです（たとえば、PDP-10では36、360では32）。

    ECHOING：値はLかRです。ホストが端末にエコーさせることを期待している（Remote）か、ホスト自身でエコーすることを期待している（Local）かによって決まります。

The ASCII file generated by the NIC will reside at Host OFFICE-1 (Host Address = 43 decimal), and will have the pathname

NICが生成するASCIIファイルは、ホストOFFICE-1（ホストアドレスは10進数で43）に置かれ、次のパス名を持ちます。

<NETINFO>HOSTS.TXT

<NETINFO>HOSTS.TXT

Using this pathname with an FTP process will enable anyone, of course, to retrieve the file for use at any Network Host.

もちろん、このパス名をFTPプロセスで使えば、誰でもこのファイルを取得して、ネットワーク上の任意のホストで使えます。

The login username for FTP can be GUEST,
password ARPA,
account 1.

FTPのログインユーザー名にはGUEST、
パスワードにはARPA、
アカウントには1を使えます。

The file will be in alphanumeric sequence by Host Name.

ファイルは、ホスト名の英数字順に並びます。

The date after which the file will be available at OFFICE-l will be announced via RFC as soon as the file is ready.

ファイルがOFFICE-lで利用可能になる日付は、ファイルの準備ができ次第、RFCで告知します。

We welcome comments on this RFC, on RFC# 606, or on any other aspect of this problem. And we wish to acknowledge the contributions of Vint Cerf, Peter Deutsch, Jake Feinler, and Nancy Neigus in getting the Official Host Name list to happen.

このRFC、RFC# 606、またはこの問題の他のあらゆる側面についてのコメントを歓迎します。また、公式ホスト名一覧の実現に貢献してくれたVint Cerf、Peter Deutsch、Jake Feinler、Nancy Neigusに感謝します。
