RFC 7916

Operational Management of Loop-Free Alternates

RFC 7916

ループフリー代替経路の運用管理

Abstract

概要

Loop-Free Alternates (LFAs), as defined in RFC 5286, constitute an IP Fast Reroute (IP FRR) mechanism enabling traffic protection for IP traffic (and, by extension, MPLS LDP traffic). Following early deployment experiences, this document provides operational feedback on LFAs, highlights some limitations, and proposes a set of refinements to address those limitations. It also proposes required management specifications.

RFC 5286で定義されているループフリー代替経路（Loop-Free Alternate: LFA）は、IPトラフィック（さらにはMPLS LDPトラフィック）のトラフィック保護を可能にするIP高速リルート（IP FRR）メカニズムです。 この文書は、初期の展開経験を踏まえて、LFAに関する運用上のフィードバックを提供し、いくつかの制限を明らかにし、それらの制限に対処するための一連の改良を提案します。 また、必要な管理仕様も提案します。

This proposal is also applicable to remote-LFA solutions.

この提案は、リモートLFAのソリューションにも適用できます。

1. Introduction

1. はじめに

Following the first deployments of Loop-Free Alternates (LFAs), this document provides feedback to the community about the management of LFAs.

ループフリー代替経路（Loop-Free Alternate: LFA）が初めて展開されたことを受けて、この文書はLFAの管理に関するフィードバックをコミュニティーに提供します。

  • Section 3 provides real use cases illustrating some limitations and suboptimal behavior.
  • Section 4 provides requirements for LFA simulations.
  • Section 5 proposes requirements for activation granularity and policy-based selection of the alternate.
  • Section 6 expresses requirements for the operational management of LFAs and, in particular, a policy framework to manage alternates.
  • Section 7 details some operational considerations of LFAs, such as IS-IS overload bit management and troubleshooting information.
  • セクション3では、いくつかの制限と最適でない動作を示す実際のユースケースを示します。
  • セクション4では、LFAのシミュレーションに関する要件を示します。
  • セクション5では、有効化の粒度と、ポリシーに基づく代替経路の選択に関する要件を提案します。
  • セクション6では、LFAの運用管理に関する要件、特に代替経路を管理するためのポリシーフレームワークについて述べます。
  • セクション7では、IS-ISオーバーロードビットの管理やトラブルシューティング情報など、LFAの運用上の考慮事項をいくつか詳しく説明します。

2. Definitions

2. 定義

  • Per-prefix LFA computation: Evaluation for the best alternate is done for each destination prefix, as opposed to the "per-next-hop" simplification technique proposed in Section 3.8 of [RFC5286].
  • PE router: Provider Edge router. These routers connect customers to each other.
  • P router: Provider router. These routers are core routers without customer connections. They provide transit between PE routers, and they form the core network.
  • Core network: subset of the network composed of P routers and links between them.
  • Core link: network link part of the core network, i.e., a link between P routers.
  • Link-protecting LFA: alternate providing protection against link failure.
  • Node-protecting LFA: alternate providing protection against node failure.
  • Connected alternate: alternate adjacent (at the IGP level) to the Point of Local Repair (PLR) (i.e., an IGP neighbor).
  • Remote alternate: alternate that does not share an IGP adjacency with the PLR.
  • プレフィックスごとのLFA計算（per-prefix LFA computation）: 最良の代替経路の評価を、[RFC5286]のセクション3.8で提案されている「ネクストホップごと」の簡略化手法ではなく、宛先プレフィックスごとに行うことです。
  • PEルーター（PE router）: プロバイダーエッジ（Provider Edge）ルーターです。 これらのルーターは顧客同士を接続します。
  • Pルーター（P router）: プロバイダー（Provider）ルーターです。 これらのルーターは、顧客との接続を持たないコアルーターです。 これらはPEルーター間のトランジットを提供し、コアネットワークを形成します。
  • コアネットワーク（core network）: Pルーターとそれらの間のリンクで構成されるネットワークの部分集合です。
  • コアリンク（core link）: コアネットワークの一部であるネットワークリンク、つまりPルーター間のリンクです。
  • リンク保護LFA（link-protecting LFA）: リンク障害に対する保護を提供する代替経路です。
  • ノード保護LFA（node-protecting LFA）: ノード障害に対する保護を提供する代替経路です。
  • 接続代替経路（connected alternate）: ローカル修復点（Point of Local Repair: PLR）に（IGPレベルで）隣接している代替経路、つまりIGP近隣です。
  • リモート代替経路（remote alternate）: PLRとIGP隣接関係を共有していない代替経路です。

3. Operational Issues with Default LFA Tiebreakers

3. デフォルトのLFAタイブレーカーに関する運用上の問題

[RFC5286] introduces the notion of tiebreakers when selecting the LFA among multiple candidate alternate next hops. When multiple LFAs exist, [RFC5286] has favored the selection of the LFA that provides the best coverage against the failure cases. While this is indeed a goal, it is one among multiple goals, and in some deployments this leads to the selection of a suboptimal LFA. The following sections detail real use cases related to such limitations.

[RFC5286]は、複数の候補となる代替ネクストホップの中からLFAを選択する際のタイブレーカーという概念を導入しています。 複数のLFAが存在する場合、[RFC5286]は、障害ケースに対して最良のカバレッジを提供するLFAを選択することを優先してきました。 これは確かに目標の1つではありますが、複数ある目標のうちの1つにすぎず、一部の展開では最適でないLFAが選択される結果になります。 以降のセクションでは、こうした制限に関連する実際のユースケースを詳しく説明します。

Note that the use case for LFA computation per destination (per-prefix LFA) is assumed throughout this analysis. We also assume in the network figures that all IP prefixes are advertised with zero cost.

この分析全体を通して、宛先ごとのLFA計算（プレフィックスごとのLFA）のユースケースを前提としていることに注意してください。 また、ネットワーク図では、すべてのIPプレフィックスがコスト0で広告されていることを前提とします。

3.1. Case 1: PE Router Protecting against Failures within Core Network

3.1. ケース1: コアネットワーク内の障害に対してPEルーターが保護する

In Figure 1, let us consider the traffic flowing from PE1 to PE4. The nominal path is P9-P8-P7-P6-PE4. Let us now consider the failure of link P7-P8. As the P4 primary path to PE4 is P8-P7-P6-PE4, P4 is not an LFA for P8 (because P4 will loop traffic back to P8), and the only available LFA is PE2.

図1において、PE1からPE4へ流れるトラフィックを考えます。 通常時のパスはP9-P8-P7-P6-PE4です。 ここで、リンクP7-P8の障害を考えます。 P4からPE4へのプライマリーパスはP8-P7-P6-PE4であるため、P4はP8にとってのLFAではなく（P4はトラフィックをP8にループさせて戻すため）、利用可能な唯一のLFAはPE2です。

When the core link P8-P7 fails, P8 switches all traffic destined to PE4/PE5 towards the node PE2. Hence, a PE node and PE links are used to protect against the failure of a core link. Typically, PE links have less capacity than core links, and congestion may occur on PE2 links. Note that although PE2 is not directly affected by the failure, its links become congested, and its traffic will suffer from the congestion.

コアリンクP8-P7に障害が発生すると、P8はPE4/PE5宛てのすべてのトラフィックをノードPE2に向けて切り替えます。 したがって、コアリンクの障害に対する保護のために、PEノードとPEリンクが使われることになります。 一般に、PEリンクはコアリンクよりも容量が小さく、PE2のリンクで輻輳が発生する可能性があります。 PE2は障害の影響を直接受けていないにもかかわらず、そのリンクが輻輳し、そのトラフィックが輻輳の影響を受けることに注意してください。

In summary, in the case of P8-P7 link failure, the impact on customer traffic is:

まとめると、P8-P7のリンク障害の場合、顧客トラフィックへの影響は次のとおりです。

  • From PE2's point of view:

    • without LFA: no impact.
    • with LFA: traffic is partially dropped (but possibly prioritized by a QoS mechanism). It must be highlighted that in such a situation, traffic not affected by the failure may be affected by the congestion.

  • From P8's point of view:

    • without LFA: traffic is totally dropped until convergence occurs.
    • with LFA: traffic is partially dropped (but possibly prioritized by a QoS mechanism).

  • PE2の観点から:

    • LFAなし: 影響はありません。
    • LFAあり: トラフィックが部分的に破棄されます（ただし、QoSメカニズムによって優先順位付けされる可能性があります）。 このような状況では、障害の影響を受けていないトラフィックが輻輳の影響を受ける可能性があることを強調しておかなければなりません。

  • P8の観点から:

    • LFAなし: 収束が起こるまでトラフィックが完全に破棄されます。
    • LFAあり: トラフィックが部分的に破棄されます（ただし、QoSメカニズムによって優先順位付けされる可能性があります）。

Besides the congestion aspects of using a PE router as an alternate to protect against a core failure, a service provider may consider this to be a bad routing design and would want to prevent it.

コア障害に対する保護のためにPEルーターを代替経路として使うことによる輻輳の側面に加えて、サービスプロバイダーはこれを悪いルーティング設計とみなし、防ぎたいと考える場合があります。

3.2. Case 2: PE Router Chosen to Protect against Core Failures while P Router LFA Exists

3.2. ケース2: PルーターのLFAが存在するのに、コア障害に対する保護にPEルーターが選ばれる

In Figure 2, let us consider the traffic coming from PE1 to PE4. The nominal path is P9-P8-P7-P10-P6-PE4. Let us now consider the failure of the link P7-P8. For P8, P4 is a link-protecting LFA and PE2 is a node-protecting LFA. PE2 is chosen as the best LFA, due to the better type of protection that it provides. Just as in case 1, this may lead to congestion on PE2 links upon LFA activation.

図2において、PE1からPE4へ向かうトラフィックを考えます。 通常時のパスはP9-P8-P7-P10-P6-PE4です。 ここで、リンクP7-P8の障害を考えます。 P8にとって、P4はリンク保護LFAであり、PE2はノード保護LFAです。 PE2は、より優れた種類の保護を提供するため、最良のLFAとして選ばれます。 ケース1とまったく同様に、これはLFAの発動時にPE2のリンクで輻輳を引き起こす可能性があります。

3.3. Case 3: Suboptimal P Router Alternate Choice

3.3. ケース3: 最適でないPルーターの代替経路の選択

In Figure 3, let us consider the failure of link P1-P3. For destination PE3, P3 has two possible alternates:

図3において、リンクP1-P3の障害を考えます。 宛先PE3について、P3には2つの代替経路の候補があります。

  • P4, which is node-protecting
  • R5, which is link-protecting
  • ノード保護を提供するP4
  • リンク保護を提供するR5

P4 is chosen as the best LFA, due to the better type of protection that it provides. However, for bandwidth capacity reasons, it may not be desirable to use P4. A service provider may prefer to use high-bandwidth links as the preferred LFA. In this example, preferring the shortest path over the type of protection may achieve the expected behavior, but in cases where metrics do not reflect the bandwidth, this technique would not work and some other criteria would need to be involved when selecting the best LFA.

P4は、より優れた種類の保護を提供するため、最良のLFAとして選ばれます。 しかし、帯域幅容量の理由から、P4を使うことが望ましくない場合があります。 サービスプロバイダーは、優先するLFAとして高帯域幅のリンクを使うことを好む場合があります。 この例では、保護の種類よりも最短パスを優先することで期待どおりの動作を実現できるかもしれませんが、メトリックが帯域幅を反映していない場合にはこの手法は機能せず、最良のLFAを選択する際に何らかの別の基準を加える必要があります。

3.4. Case 4: No-Transit LFA Computing Node

3.4. ケース4: 非トランジットのLFA計算ノード

The IS-IS and OSPF protocols define some way to prevent a router from being used for transit.

IS-ISとOSPFのプロトコルは、ルーターがトランジットに使われないようにする何らかの方法を定義しています。

The IS-IS overload bit is defined in [ISO10589], and the OSPF R-bit is defined in [RFC5340]. Also, the OSPF stub router is defined in [RFC6987] as a method to prevent transit on a node by advertising MaxLinkMetric on all non-stub links.

IS-ISのオーバーロードビットは[ISO10589]で定義されており、OSPFのRビットは[RFC5340]で定義されています。 また、OSPFスタブルーターは、すべての非スタブリンクでMaxLinkMetricを広告することによってノードでのトランジットを防ぐ方法として、[RFC6987]で定義されています。

In Figure 4, PE3 has its no-transit condition set (permanently, for design reasons) and wants to protect traffic using an LFA for destination PE2.

図4において、PE3には（設計上の理由により恒久的に）非トランジット条件が設定されており、PE3は宛先PE2へのトラフィックをLFAを使って保護したいと考えています。

On PE3, the loop-free condition is not satisfied: 100 !< 45 + 45. PE1 is thus not considered as an LFA. However, thanks to the no-transit condition on PE3, we know that PE1 will not loop the traffic back to PE3. So, PE1 is an LFA to reach PE2.

PE3では、ループフリー条件が満たされません（100 !< 45 + 45）。 そのため、PE1はLFAとはみなされません。 しかし、PE3の非トランジット条件のおかげで、PE1がトラフィックをPE3にループさせて戻すことはないとわかります。 したがって、PE1はPE2に到達するためのLFAです。

In the case of a no-transit condition set on a node, LFA behavior must be clarified.

ノードに非トランジット条件が設定されている場合のLFAの動作を明確にする必要があります。

4. Need for Coverage Monitoring

4. カバレッジ監視の必要性

As per [RFC6571], LFA coverage depends strongly on the network topology that is in use. Even if the remote-LFA mechanism [RFC7490] significantly extends the coverage of the basic LFA specification, there are still some cases where protection would not be available. As network topologies are constantly evolving (network extension, additional capacity, latency optimization, etc.), the protection coverage may change. Fast Reroute (FRR) functionality may be critical for some services supported by the network; a service provider must always know what type of protection coverage is currently available on the network. Moreover, predicting protection coverage in the event of network topology changes is mandatory.

[RFC6571]によると、LFAのカバレッジは使用しているネットワークトポロジーに強く依存します。 リモートLFAメカニズム[RFC7490]によって基本的なLFA仕様のカバレッジが大幅に拡張されたとしても、保護が利用できないケースはまだ存在します。 ネットワークトポロジーは絶えず進化している（ネットワークの拡張、容量の追加、遅延の最適化など）ため、保護のカバレッジは変化する可能性があります。 高速リルート（Fast Reroute: FRR）の機能は、ネットワークがサポートする一部のサービスにとって重要な場合があります。 サービスプロバイダーは、現在ネットワーク上でどのような種類の保護カバレッジが利用可能であるかを常に把握していなければなりません。 さらに、ネットワークトポロジーが変化した場合の保護カバレッジを予測することは必須です。

Today, network simulation tools associated with "what if" scenarios are often used by service providers for the overall network design (capacity, path optimization, etc.). Sections 7.3, 7.4, and 7.5 of this document propose the addition of LFA information into such tools and within routers, so that a service provider may be able to:

今日、サービスプロバイダーは、ネットワーク全体の設計（容量、パスの最適化など）に、「what if」シナリオを伴うネットワークシミュレーションツールをよく使っています。 この文書のセクション7.3、7.4、7.5では、そのようなツールやルーター内にLFAの情報を追加することを提案しています。 これにより、サービスプロバイダーは次のことができるようになります。

  • evaluate protection coverage after a topology change.
  • adjust the topology change to cover the primary need (e.g., latency optimization, bandwidth increase) as well as LFA protection.
  • constantly monitor the LFA coverage in the live network and receive alerts.
  • トポロジーの変更後に保護カバレッジを評価する。
  • LFAによる保護だけでなく、主たるニーズ（たとえば、遅延の最適化、帯域幅の増加）も満たせるようにトポロジーの変更を調整する。
  • 稼働中のネットワークにおけるLFAのカバレッジを常時監視し、アラートを受け取る。

Documentation of LFA selection algorithms by implementers (default and tuning options) is important in order to make it possible for third-party modules to model these policy-based LFA selection algorithms.

サードパーティーのモジュールがこれらのポリシーに基づくLFA選択アルゴリズムをモデル化できるようにするために、実装者がLFA選択アルゴリズム（デフォルトおよびチューニングオプション）を文書化することが重要です。

5. Need for LFA Activation Granularity

5. LFA有効化の粒度の必要性

As in all FRR mechanisms, an LFA installs backup paths in the Forwarding Information Base (FIB). Depending on the hardware used by a service provider, FIB resources may be critical. Activating LFAs by default on all available components (IGP topologies, interfaces, address families, etc.) may lead to a waste of FIB resources, as generally only a few destinations in a network should be protected (e.g., loopback addresses supporting MPLS services) compared to the number of destinations in the Routing Information Base (RIB).

すべてのFRRメカニズムと同様に、LFAはバックアップパスを転送情報ベース（Forwarding Information Base: FIB）にインストールします。 サービスプロバイダーが使うハードウェアによっては、FIBのリソースが重要になる場合があります。 利用可能なすべてのコンポーネント（IGPトポロジー、インターフェイス、アドレスファミリーなど）でデフォルトでLFAを有効にすると、FIBのリソースが無駄になる可能性があります。 一般に、ネットワーク内で保護すべき宛先（たとえば、MPLSサービスをサポートするループバックアドレス）は、ルーティング情報ベース（Routing Information Base: RIB）内の宛先の数に比べてごくわずかだからです。

Moreover, a service provider may implement multiple different FRR mechanisms in its networks for different applications (e.g., Maximally Redundant Trees (MRTs), TE FRR). In this scenario, an implementation MAY allow the computation of alternates for a specific destination even if the destination is already protected by another mechanism. This will provide redundancy and permit the operator to select the best option for FRR, using a policy language.

さらに、サービスプロバイダーは、異なるアプリケーションのために、複数の異なるFRRメカニズム（たとえば、最大冗長ツリー（Maximally Redundant Trees: MRT）、TE FRR）を自社のネットワークに実装する場合があります。 このシナリオでは、実装は、ある宛先が別のメカニズムによってすでに保護されている場合でも、その宛先に対する代替経路の計算を許可してもよいです（MAY）。 これにより冗長性が得られ、運用者はポリシー言語を使ってFRRの最良の選択肢を選ぶことができるようになります。

Section 6 provides some implementation guidelines.

セクション6では、いくつかの実装ガイドラインを示します。

6. Configuration Requirements

6. 設定に関する要件

Controlling the selection of the best alternate and the granularity of LFA activation is a requirement for service providers. This section defines configuration requirements for LFAs.

最良の代替経路の選択とLFA有効化の粒度を制御することは、サービスプロバイダーにとっての要件です。 このセクションでは、LFAの設定に関する要件を定義します。

6.1. LFA Enabling/Disabling Scope

6.1. LFAの有効化/無効化の範囲

The granularity of LFA activation SHOULD be controlled (as alternate next hops consume memory in the forwarding plane).

（代替ネクストホップはフォワーディングプレーンのメモリーを消費するため、）LFA有効化の粒度は制御されるべきです（SHOULD）。

An implementation of an LFA SHOULD allow its activation, with the following granularities:

LFAの実装は、次の粒度でLFAを有効にできるようにするべきです（SHOULD）。

  • Per routing context: Virtual Routing and Forwarding (VRF), virtual/logical router, global routing table, etc.
  • Per interface.
  • Per protocol instance, topology, area.
  • Per prefix: Prefix protection SHOULD have a higher priority compared to interface protection. This means that if a specific prefix must be protected due to a configuration request, an LFA MUST be computed and installed for that prefix even if the primary outgoing interface is not configured for protection.
  • ルーティングコンテキストごと: 仮想ルーティングおよび転送（Virtual Routing and Forwarding: VRF）、仮想/論理ルーター、グローバルルーティングテーブルなど。
  • インターフェイスごと。
  • プロトコルインスタンス、トポロジー、エリアごと。
  • プレフィックスごと: プレフィックスの保護は、インターフェイスの保護よりも高い優先度を持つべきです（SHOULD）。 つまり、設定上の要求により特定のプレフィックスを保護しなければならない場合、プライマリーの出力インターフェイスが保護の対象として設定されていなくても、そのプレフィックスに対してLFAを計算してインストールしなければなりません（MUST）。

An implementation of an LFA MAY allow its activation, with the following criteria:

LFAの実装は、次の基準でLFAを有効にできるようにしてもよいです（MAY）。

  • Per address family: IPv4 unicast, IPv6 unicast.
  • Per MPLS control plane: For MPLS control planes that inherit routing decisions from the IGP routing protocol, the MPLS data plane may be protected by an LFA. The implementation may allow an operator to control this inheritance of protection from the IP prefix to the MPLS label bound to this prefix. The inheritance of protection will concern IP-to-MPLS, MPLS-to-MPLS, and MPLS-to-IP entries. As an example, LDP and Segment Routing extensions [SEG-RTG-ARCH] for IS-IS and OSPF are control-plane eligible for this inheritance of protection.
  • アドレスファミリーごと: IPv4ユニキャスト、IPv6ユニキャスト。
  • MPLSコントロールプレーンごと: IGPルーティングプロトコルからルーティングの決定を継承するMPLSコントロールプレーンでは、MPLSデータプレーンをLFAで保護できます。 実装は、IPプレフィックスからそのプレフィックスにバインドされたMPLSラベルへのこの保護の継承を、運用者が制御できるようにしてもかまいません。 保護の継承は、IP-to-MPLS、MPLS-to-MPLS、MPLS-to-IPのエントリーに関係します。 たとえば、LDPや、IS-ISとOSPFのセグメントルーティング拡張[SEG-RTG-ARCH]は、この保護の継承の対象となるコントロールプレーンです。

6.2. Policy-Based LFA Selection

6.2. ポリシーに基づくLFAの選択

When multiple alternates exist, the LFA selection algorithm is based on tiebreakers. Current tiebreakers do not provide sufficient control regarding how the best alternate is chosen. This document proposes an enhanced tiebreaker allowing service providers to manage all specific cases:

複数の代替経路が存在する場合、LFAの選択アルゴリズムはタイブレーカーに基づきます。 現在のタイブレーカーでは、最良の代替経路をどのように選ぶかについて十分な制御ができません。 この文書は、サービスプロバイダーがあらゆる個別のケースを管理できるようにする、拡張されたタイブレーカーを提案します。

  1. An LFA implementation SHOULD support policy-based decisions for determining the best LFA.
  2. Policy-based decisions SHOULD be based on multiple criteria, with each criterion having a level of preference.
  3. If the defined policy does not allow the determination of a unique best LFA, an implementation SHOULD pick only one based on its own decision. For load-balancing purposes, an implementation SHOULD also support the election of multiple LFAs.
  4. The policy SHOULD be applicable to a protected interface or a specific set of destinations. In the case of applicability to the protected interface, all destinations primarily routed on that interface SHOULD use the policy for that interface.
  5. The choice of whether or not to dynamically re-evaluate policy (in the event of a policy change) is left to the implementation. If a dynamic approach is chosen, the implementation SHOULD recompute the best LFAs and reinstall them in the FIB without service disruption. If a non-dynamic approach is chosen, the policy would be taken into account upon the next IGP event. In this case, the implementation SHOULD support a command to manually force the recomputation/reinstallation of LFAs.
  1. LFAの実装は、最良のLFAを決定するために、ポリシーに基づく決定をサポートするべきです（SHOULD）。
  2. ポリシーに基づく決定は、それぞれが優先度のレベルを持つ複数の基準に基づくべきです（SHOULD）。
  3. 定義されたポリシーによって一意の最良のLFAを決定できない場合、実装は独自の判断に基づいて1つだけを選ぶべきです（SHOULD）。 負荷分散の目的のために、実装は複数のLFAの選出もサポートするべきです（SHOULD）。
  4. ポリシーは、保護対象のインターフェイスまたは特定の宛先の集合に適用できるべきです（SHOULD）。 保護対象のインターフェイスに適用する場合、そのインターフェイスをプライマリーとしてルーティングされるすべての宛先は、そのインターフェイスのポリシーを使うべきです（SHOULD）。
  5. （ポリシーが変更された場合に）ポリシーを動的に再評価するかどうかの選択は、実装に委ねられます。 動的なアプローチを選んだ場合、実装はサービスを中断することなく最良のLFAを再計算してFIBに再インストールするべきです（SHOULD）。 動的でないアプローチを選んだ場合、ポリシーは次のIGPイベントの際に考慮されることになります。 この場合、実装はLFAの再計算/再インストールを手動で強制するコマンドをサポートするべきです（SHOULD）。

6.2.1. Connected versus Remote Alternates

6.2.1. 接続代替経路とリモート代替経路

In addition to connected LFAs, tunnels (e.g., IP, LDP, RSVP-TE, Segment Routing) to distant routers may be used to complement LFA coverage (tunnel tail used as virtual neighbor). When a router has multiple alternate candidates for a specific destination, it may have connected alternates and remote alternates (reachable via a tunnel). Connected alternates may not always provide an optimal routing path, and it may be preferable to select a remote alternate over a connected alternate. Some uses of tunnels to extend LFA [RFC5286] coverage are described in [RFC7490] and [TI-LFA]. [RFC7490] and [TI-LFA] present some use cases for LDP tunnels and Segment Routing tunnels, respectively. This document considers any type of tunneling techniques to reach remote alternates (IP, Generic Routing Encapsulation (GRE), LDP, RSVP-TE, the Layer 2 Tunneling Protocol (L2TP), Segment Routing, etc.) and does not restrict the remote alternates to the uses presented in these other documents.

接続されたLFAに加えて、離れたルーターへのトンネル（たとえば、IP、LDP、RSVP-TE、セグメントルーティング）を使ってLFAのカバレッジを補完することもできます（トンネルの終端を仮想的な近隣として使います）。 ルーターが特定の宛先に対して複数の代替経路の候補を持つ場合、接続代替経路と（トンネル経由で到達可能な）リモート代替経路を持つことがあります。 接続代替経路が常に最適なルーティングパスを提供するとは限らず、接続代替経路よりもリモート代替経路を選択する方が望ましい場合もあります。 LFA [RFC5286]のカバレッジを拡張するためのトンネルの用途のいくつかは、[RFC7490]と[TI-LFA]で説明されています。 [RFC7490]と[TI-LFA]は、それぞれLDPトンネルとセグメントルーティングトンネルのユースケースをいくつか示しています。 この文書は、リモート代替経路に到達するためのあらゆる種類のトンネリング技術（IP、総称ルーティングカプセル化（Generic Routing Encapsulation: GRE）、LDP、RSVP-TE、レイヤー2トンネリングプロトコル（Layer 2 Tunneling Protocol: L2TP）、セグメントルーティングなど）を対象としており、リモート代替経路をこれらの他の文書で示されている用途に限定しません。

In Figure 1, there is no P router alternate for P8 to reach PE4 or PE5, so P8 is using PE2 as an alternate; this may generate congestion when FRR is activated. Instead, we could have a remote alternate for P8 to protect traffic to PE4 and PE5. For example, a tunnel from P8 to P3 (following the shortest path) can be set up, and P8 would be able to use P3 as a remote alternate to protect traffic to PE4 and PE5. In this scenario, traffic will not use a PE link during FRR activation.

図1では、P8がPE4またはPE5に到達するためのPルーターの代替経路がないため、P8はPE2を代替経路として使っています。 これにより、FRRが発動したときに輻輳が発生する可能性があります。 代わりに、P8がPE4とPE5へのトラフィックを保護するためのリモート代替経路を持つことができます。 たとえば、P8からP3への（最短パスに沿った）トンネルを設定すれば、P8はPE4とPE5へのトラフィックを保護するためのリモート代替経路としてP3を使えるようになります。 このシナリオでは、FRRの発動中にトラフィックがPEリンクを使うことはありません。

When selecting the best alternate, the selection algorithm MUST consider all available alternates (connected or tunnel). For example, with remote LFAs, computation of PQ sets [RFC7490] SHOULD be performed before the selection of the best alternate.

最良の代替経路を選択する際、選択アルゴリズムは利用可能なすべての代替経路（接続またはトンネル）を考慮しなければなりません（MUST）。 たとえば、リモートLFAの場合、PQ集合[RFC7490]の計算は、最良の代替経路を選択する前に実行されるべきです（SHOULD）。

6.2.2. Mandatory Criteria

6.2.2. 必須の基準

An LFA implementation MUST support the following criteria:

LFAの実装は、次の基準をサポートしなければなりません（MUST）。

  • Non-candidate link: A link marked as "non-candidate" will never be used as an LFA.
  • A primary next hop being protected by another primary next hop of the same prefix (ECMP case).
  • Type of protection provided by the alternate: link protection or node protection. In the case of preference for node protection, an implementation SHOULD support fallback to link protection if node protection is not available.
  • Shortest path: lowest IGP metric used to reach the destination.
  • Shared Risk Link Groups (SRLGs) (as defined in Section 3 of [RFC5286]; see also Section 6.2.4.1 for more details).
  • 候補外リンク: 「non-candidate（候補外）」とマークされたリンクは、決してLFAとして使われません。
  • 同じプレフィックスの別のプライマリーネクストホップによって保護されるプライマリーネクストホップ（ECMPの場合）。
  • 代替経路が提供する保護の種類: リンク保護またはノード保護。 ノード保護を優先する場合、実装は、ノード保護が利用できなければリンク保護へのフォールバックをサポートするべきです（SHOULD）。
  • 最短パス: 宛先に到達するために使われる最小のIGPメトリック。
  • 共有リスクリンクグループ（Shared Risk Link Group: SRLG）（[RFC5286]のセクション3で定義されているもの。詳細についてはセクション6.2.4.1も参照してください）。

6.2.3. Additional Criteria

6.2.3. 追加の基準

An LFA implementation SHOULD support the following criteria:

LFAの実装は、次の基準をサポートするべきです（SHOULD）。

  • A downstream alternate: Preference for a downstream path over a non-downstream path SHOULD be configurable.
  • Link coloring with "include", "exclude", and preference-based systems (see Section 6.2.4.2).
  • Link bandwidth (see Section 6.2.4.3).
  • Alternate preference / node coloring (see Section 6.2.4.4).
  • ダウンストリームの代替経路: ダウンストリームでないパスよりもダウンストリームのパスを優先することを、設定可能にするべきです（SHOULD）。
  • 「include（含める）」、「exclude（除外する）」、および優先度に基づく仕組みを備えたリンクカラーリング（セクション6.2.4.2を参照）。
  • リンクの帯域幅（セクション6.2.4.3を参照）。
  • 代替経路の優先度/ノードカラーリング（セクション6.2.4.4を参照）。

6.2.4. Evaluation of Criteria

6.2.4. 基準の評価

6.2.4.1. SRLGs
6.2.4.1. SRLGs

Section 3 of [RFC5286] proposes the reuse of GMPLS IGP extensions to encode SRLGs [RFC5307] [RFC4203]. Section 3 of [RFC5286] also describes the algorithm to compute SRLG protection.

[RFC5286]のセクション3は、SRLGを符号化するためにGMPLSのIGP拡張[RFC5307] [RFC4203]を再利用することを提案しています。 [RFC5286]のセクション3は、SRLG保護を計算するアルゴリズムについても説明しています。

When SRLG protection is computed, an implementation SHOULD allow the following:

SRLG保護を計算する場合、実装は次のことを可能にするべきです（SHOULD）。

  • Exclusion of alternates in violation of SRLGs.

  • Maintenance of a preference system between alternates based on SRLG violations. How the preference system is implemented is out of scope for this document, but here are two examples:

    • Preference based on the number of violations. In this case, more violations = less preferred.
    • Preference based on violation cost. In this case, each SRLG violation has an associated cost. The lower violation costs are preferred.
  • SRLGに違反する代替経路の除外。

  • SRLG違反に基づく代替経路間の優先度の仕組みの維持。 優先度の仕組みをどのように実装するかはこの文書の範囲外ですが、2つの例を示します。

    • 違反の数に基づく優先度。 この場合、違反が多いほど優先度が低くなります。
    • 違反コストに基づく優先度。 この場合、各SRLG違反にはコストが関連付けられています。 違反コストが低いものほど優先されます。

When applying SRLG criteria, the SRLG violation check SHOULD be performed on sources to alternates as well as alternates to destination paths, based on the SRLG set of the primary path. In the case of remote LFAs, PQ-to-destination path attributes would be retrieved from the Shortest Path Tree (SPT) rooted at the PQ.

SRLGの基準を適用する場合、SRLG違反のチェックは、プライマリーパスのSRLG集合に基づいて、送信元から代替経路までのパスと、代替経路から宛先までのパスの両方に対して実行されるべきです（SHOULD）。 リモートLFAの場合、PQから宛先までのパスの属性は、PQをルートとする最短パスツリー（Shortest Path Tree: SPT）から取得されることになります。

6.2.4.2. Link Coloring
6.2.4.2. リンクカラーリング

Link coloring is a powerful system to control the choice of alternates. Link colors are markers that will allow the encoding of properties of a particular link. Protecting interfaces are tagged with colors. Protected interfaces are configured to include some colors with a preference level and exclude others.

リンクカラーリングは、代替経路の選択を制御するための強力な仕組みです。 リンクカラーは、特定のリンクの特性を符号化できるようにするマーカーです。 保護するインターフェイスにはカラーのタグが付けられます。 保護されるインターフェイスは、いくつかのカラーを優先度のレベル付きで含め、その他のカラーを除外するように設定されます。

Link color information SHOULD be signaled in the IGP, and administrative-group IGP extensions [RFC5305] [RFC3630] that are already standardized, implemented, and widely used SHOULD be used for encoding and signaling link colors.

リンクカラーの情報はIGPでシグナリングされるべきです（SHOULD）。 また、リンクカラーの符号化とシグナリングには、すでに標準化され、実装され、広く使われている管理グループのIGP拡張[RFC5305] [RFC3630]を使うべきです（SHOULD）。

In the example in Figure 5, the P1 router is connected to three P routers and two PEs. P1 is configured to protect the P1-P4 link. We assume that, given the topology, all neighbors are candidate LFAs. We would like to enforce a policy in the network where only a core router may protect against the failure of a core link and where high-capacity links are preferred.

図5の例では、ルーターP1は3台のPルーターと2台のPEに接続されています。 P1は、P1-P4リンクを保護するように設定されています。 このトポロジーでは、すべての近隣がLFAの候補であると仮定します。 ここで、コアリンクの障害に対してはコアルーターだけが保護でき、かつ大容量のリンクが優先されるというポリシーを、ネットワークで適用したいとします。

In this example, we can use the proposed link coloring by:

この例では、提案するリンクカラーリングを次のように使うことができます。

  • Marking the PE links with the color RED.
  • Marking the 10 Gbps core link with the color BLUE.
  • Marking the 1 Gbps core link with the color YELLOW.

  • Configuring the protected interface P1->P4 as follows:

    • Include BLUE, preference 200.
    • Include YELLOW, preference 100.
    • Exclude RED.
  • PEリンクをカラーREDでマークする。
  • 10 GbpsのコアリンクをカラーBLUEでマークする。
  • 1 GbpsのコアリンクをカラーYELLOWでマークする。

  • 保護されるインターフェイスP1->P4を次のように設定する。

    • BLUEを含める、優先度200。
    • YELLOWを含める、優先度100。
    • REDを除外する。

Using this, PE links will never be used to protect against P1-P4 link failure, and the 10 Gbps link will be preferred.

これにより、P1-P4リンクの障害に対する保護にPEリンクが使われることはなくなり、10 Gbpsのリンクが優先されます。

The main advantage of this solution is that it can easily be duplicated on other interfaces and other nodes without change. A service provider has only to define the color system (associate a color with a level of significance), as it is done already for TE affinities or BGP communities.

この解決策の主な利点は、ほかのインターフェイスやほかのノードに変更なしで容易に複製できることです。 サービスプロバイダーは、TEアフィニティーやBGPコミュニティーですでに行っているように、カラーの体系を定義する（カラーに重要度のレベルを関連付ける）だけで済みます。

An implementation of link coloring:

リンクカラーリングの実装には、次の要件があります。

  • SHOULD support multiple "include" and "exclude" colors on a single protected interface.
  • SHOULD provide a level of preference between included colors.
  • SHOULD support the configuration of multiple colors on a single protecting interface.
  • 1つの保護されるインターフェイスで、複数の「include」カラーと「exclude」カラーをサポートするべきです（SHOULD）。
  • 含めるカラー間の優先度のレベルを提供するべきです（SHOULD）。
  • 1つの保護するインターフェイスで、複数のカラーの設定をサポートするべきです（SHOULD）。
6.2.4.3. Bandwidth
6.2.4.3. 帯域幅

As mentioned in previous sections, not taking into account the bandwidth of an alternate could lead to congestion during FRR activation. We propose that the bandwidth criteria be based on the link speed information, for the following reasons:

前のセクションで述べたように、代替経路の帯域幅を考慮しないと、FRRの発動中に輻輳が発生する可能性があります。 次の理由から、帯域幅の基準はリンク速度の情報に基づくことを提案します。

  • If a router S has a set of X destinations primarily forwarded to N, using per-prefix LFAs may lead to having a subset of X protected by a neighbor N1, another subset by N2, another subset by Nx, etc.
  • S is not aware of traffic flows to each destination, so in the case of FRR activation, S is not able to evaluate how much traffic will be sent to N1, N2, Nx, etc.
  • ルーターSが、主にNへ転送されるX個の宛先の集合を持つ場合、プレフィックスごとのLFAを使うと、Xのある部分集合が近隣N1によって保護され、別の部分集合がN2によって、さらに別の部分集合がNxによって保護される、といった状況になる可能性があります。
  • Sは各宛先へのトラフィックフローを把握していないため、FRRが発動した場合に、N1、N2、Nxなどにどれだけのトラフィックが送られるかを評価できません。

Based on this, it is not useful to gather available bandwidth on alternate paths, as the router does not know how much bandwidth it requires for protection. The proposed link speed approach provides a good approximation at low cost, as information is easily available.

このことから、ルーターは保護にどれだけの帯域幅が必要かを知らないため、代替パス上の利用可能な帯域幅を収集しても役に立ちません。 提案するリンク速度のアプローチは、情報を容易に入手できるため、低コストで良好な近似を提供します。

The bandwidth criteria of the policy framework SHOULD work in at least the following two ways:

ポリシーフレームワークの帯域幅の基準は、少なくとも次の2つの方法で機能するべきです（SHOULD）。

  • Prune: Exclude an LFA if the link speed to reach it is lower than the link speed of the primary next-hop interface.
  • Prefer: Prefer an LFA based on its bandwidth to reach it compared to the link speed of the primary next-hop interface.
  • 除外（Prune）: LFAに到達するためのリンク速度がプライマリーネクストホップのインターフェイスのリンク速度よりも低い場合、そのLFAを除外します。
  • 優先（Prefer）: プライマリーネクストホップのインターフェイスのリンク速度と比較した、LFAに到達するための帯域幅に基づいて、LFAを優先します。

6.2.5. 代替パスの属性の取得

6.2.5.1. 代替パス

代替パスは、PLRから代替経路までと、代替経路から宛先までという、2つの異なる部分で構成されます。

図7に示すように、代替パスの一部はECMPによって複数のパスに分岐することがあります。

6.2.5.2. Alternate Path Attributes
6.2.5.2. 代替パスの属性

Some criteria listed in the previous sections require the retrieval of some characteristics of the alternate path (SRLG, bandwidth, color, tag, etc.). We call these characteristics "path attributes". A path attribute can record a list of node properties (e.g., node tag) or link properties (e.g., link color).

前のセクションで挙げた基準のいくつかは、代替パスの何らかの特性（SRLG、帯域幅、カラー、タグなど）を取得する必要があります。 これらの特性を「パス属性」と呼びます。 パス属性には、ノードの特性（たとえば、ノードのタグ）またはリンクの特性（たとえば、リンクカラー）のリストを記録できます。

This document defines two types of path attributes:

この文書では、2種類のパス属性を定義します。

  • Cumulative attribute: When a path attribute is cumulative, the implementation SHOULD record the value of the attribute on each element (link and node) along the alternate path. SRLG, link color, and node color are cumulative attributes.
  • Unitary attribute: When a path attribute is unitary, the implementation SHOULD record the value of the attribute only on the first element along the alternate path (first node, or first link). Bandwidth is a unitary attribute.
  • 累積属性（cumulative attribute）: パス属性が累積属性である場合、実装は、代替パスに沿った各要素（リンクとノード）の属性の値を記録するべきです（SHOULD）。 SRLG、リンクカラー、ノードカラーは累積属性です。
  • 単一属性（unitary attribute）: パス属性が単一属性である場合、実装は、代替パスに沿った最初の要素（最初のノードまたは最初のリンク）の属性の値だけを記録するべきです（SHOULD）。 帯域幅は単一属性です。

In Figure 8, N1 is a connected alternate to reach D from S. We consider that all links have a RED color except {R1,R2}, which is BLUE. We consider all links to be 10 Gbps except {N1,R1}, which is 2.5 Gbps. The bandwidth attribute collected for the alternate path will be 10 Gbps. As the attribute is unitary, only the link speed of the first link {S,N1} is recorded. The link color attribute collected for the alternate path will be {RED,RED,BLUE,RED,RED}. As the attribute is cumulative, the value of the attribute on each link along the path is recorded.

図8において、N1はSからDに到達するための接続代替経路です。 {R1,R2}がBLUEであることを除き、すべてのリンクのカラーはREDであるとします。 {N1,R1}が2.5 Gbpsであることを除き、すべてのリンクは10 Gbpsであるとします。 代替パスについて収集される帯域幅属性は10 Gbpsになります。 この属性は単一属性であるため、最初のリンク{S,N1}のリンク速度だけが記録されます。 代替パスについて収集されるリンクカラー属性は{RED,RED,BLUE,RED,RED}になります。 この属性は累積属性であるため、パスに沿った各リンクの属性の値が記録されます。

6.2.5.3. Connected Alternate
6.2.5.3. 接続代替経路

For an alternate path using a connected alternate:

接続代替経路を使う代替パスについては、次のとおりです。

  • Attributes from the PLR to the alternate are retrieved from the interface connected to the alternate. If the alternate is connected through multiple interfaces, the evaluation of attributes SHOULD be done once per interface (each interface is considered as a separate alternate) and once per ECMP group of interfaces (Layer 3 bundle).
  • Path attributes from the alternate to the destination are retrieved from the SPT rooted at the alternate. As the alternate is a connected alternate, the SPT has already been computed to find the alternate, so there is no need for additional computation.
  • PLRから代替経路までの属性は、代替経路に接続されたインターフェイスから取得します。 代替経路が複数のインターフェイスを通じて接続されている場合、属性の評価は、インターフェイスごとに1回（各インターフェイスを別々の代替経路とみなします）と、インターフェイスのECMPグループ（レイヤー3バンドル）ごとに1回行うべきです（SHOULD）。
  • 代替経路から宛先までのパス属性は、代替経路をルートとするSPTから取得します。 代替経路は接続代替経路であるため、SPTは代替経路を見つけるためにすでに計算されており、追加の計算は必要ありません。

In Figure 9, we consider a primary path from S to D, with S using E as the primary next hop. All metrics are considered as 1 except {S,N1} links, which are using a metric of 50. We consider the following SRLGs on links:

図9において、SがEをプライマリーネクストホップとして使う、SからDへのプライマリーパスを考えます。 メトリック50を使う{S,N1}のリンクを除き、すべてのメトリックは1とみなします。 リンクには次のSRLGがあるとします。

  • {S,N1} using i1: SRLG1,SRLG10.
  • {S,N1} using i2: SRLG2,SRLG20.
  • {N1,R1}: SRLG3.
  • {R1,R2}: SRLG4.
  • {R2,D}: SRLG5.
  • {S,E}: SRLG10.
  • {E,D}: SRLG6.
  • i1を使う{S,N1}: SRLG1,SRLG10。
  • i2を使う{S,N1}: SRLG2,SRLG20。
  • {N1,R1}: SRLG3。
  • {R1,R2}: SRLG4。
  • {R2,D}: SRLG5。
  • {S,E}: SRLG10。
  • {E,D}: SRLG6。

S is connected to the alternate using two interfaces: i1 and i2.

Sは、i1とi2の2つのインターフェイスを使って代替経路に接続されています。

If i1 and i2 are not part of an ECMP group, the evaluation of attributes is done once per interface, and each interface is considered as a separate alternate path. Two alternate paths will be available with the associated SRLG attributes:

i1とi2がECMPグループに属していない場合、属性の評価はインターフェイスごとに1回行われ、各インターフェイスは別々の代替パスとみなされます。 関連するSRLG属性を持つ2つの代替パスが利用可能になります。

  • Alternate path #1: {S,N1 using if1,R1,R2,D}: SRLG1,SRLG10,SRLG3,SRLG4,SRLG5.
  • Alternate path #2: {S,N1 using if2,R1,R2,D}: SRLG2,SRLG20,SRLG3,SRLG4,SRLG5.
  • 代替パス#1: {S,N1 using if1,R1,R2,D}: SRLG1,SRLG10,SRLG3,SRLG4,SRLG5。
  • 代替パス#2: {S,N1 using if2,R1,R2,D}: SRLG2,SRLG20,SRLG3,SRLG4,SRLG5。

Alternate path #1 is sharing risks with the primary path and may be pruned, or its preference may be revoked, per user-defined policy.

代替パス#1はプライマリーパスとリスクを共有しているため、ユーザー定義のポリシーに従って、除外されるか、優先度を取り消される可能性があります。

If i1 and i2 are part of an ECMP group, the evaluation of attributes is done once per ECMP group, and the implementation considers a single alternate path {S,N1 using if1|if2,R1,R2,D} with the following SRLG attributes: SRLG1,SRLG10,SRLG2,SRLG20,SRLG3,SRLG4,SRLG5. The alternate path is sharing risks with the primary path and may be pruned, or its preference may be revoked, per user-defined policy.

i1とi2がECMPグループに属している場合、属性の評価はECMPグループごとに1回行われ、実装は、SRLG属性SRLG1,SRLG10,SRLG2,SRLG20,SRLG3,SRLG4,SRLG5を持つ単一の代替パス{S,N1 using if1|if2,R1,R2,D}を考慮します。 この代替パスはプライマリーパスとリスクを共有しているため、ユーザー定義のポリシーに従って、除外されるか、優先度を取り消される可能性があります。

6.2.5.4. Remote Alternate
6.2.5.4. リモート代替経路

For alternate path using a remote alternate (tunnel):

リモート代替経路（トンネル）を使う代替パスについては、次のとおりです。

  • Attributes on the path from the PLR to the alternate are retrieved using the PLR's primary SPT (when using a PQ node from the P-space) or the immediate neighbor's SPT (when using a PQ from the extended P-space). These are then combined with the attributes of the link(s) to reach the immediate neighbor. In both cases, no additional SPT is required.
  • Attributes from the remote alternate to the destination path may be retrieved from the SPT rooted at the remote alternate. An additional forward SPT is required for each remote alternate (PQ node), as indicated in Section 2.3.2 of [REMOTE-LFA-NODE]. In some remote-alternate scenarios, like [TI-LFA], alternate-to-destination path attributes may be obtained using a different technique.
  • PLRから代替経路までのパスの属性は、PLRのプライマリーSPT（P空間のPQノードを使う場合）または直接の近隣のSPT（拡張P空間のPQを使う場合）を使って取得します。 次に、これらを、直接の近隣に到達するためのリンクの属性と組み合わせます。 どちらの場合も、追加のSPTは必要ありません。
  • リモート代替経路から宛先までのパスの属性は、リモート代替経路をルートとするSPTから取得できます。 [REMOTE-LFA-NODE]のセクション2.3.2に示されているように、リモート代替経路（PQノード）ごとに追加のフォワードSPTが必要です。 [TI-LFA]のような一部のリモート代替経路のシナリオでは、代替経路から宛先までのパスの属性を別の手法で取得できる場合があります。

The number of remote alternates may be very high. In the case of remote LFAs, simulations of real-world network topologies have shown that as many as hundreds of PQs are possible. The computational overhead of collecting all path attributes of all such PQs to destination paths could grow beyond reasonable levels.

リモート代替経路の数は非常に多くなる場合があります。 リモートLFAの場合、実世界のネットワークトポロジーのシミュレーションでは、PQが数百にも達しうることが示されています。 そのようなすべてのPQから宛先までのパスのすべてのパス属性を収集する計算オーバーヘッドは、妥当なレベルを超えて増大する可能性があります。

To handle this situation, implementations need to limit the number of remote alternates to be evaluated to a finite number before collecting alternate path attributes and running the policy evaluation. Section 2.3.3 of [REMOTE-LFA-NODE] provides a way to reduce the number of PQs to be evaluated.

この状況に対処するために、実装は、代替パスの属性を収集してポリシーの評価を実行する前に、評価するリモート代替経路の数を有限の数に制限する必要があります。 [REMOTE-LFA-NODE]のセクション2.3.3は、評価するPQの数を減らす方法を提供しています。

Some other remote alternate techniques using static or dynamic tunnels may not require this pruning.

静的または動的なトンネルを使うほかのリモート代替経路の手法では、この除外が必要ない場合もあります。

6.2.5.5. Collecting Attributes in the Case of Multiple Paths
6.2.5.5. 複数のパスがある場合の属性の収集

As described in Section 6.2.5, there may be some situations where an alternate path or part of an alternate path fans out to multiple paths (e.g., ECMP). When collecting path attributes in such a case, an implementation SHOULD consider the union of attributes of each sub-path.

セクション6.2.5で説明したように、代替パスまたは代替パスの一部が複数のパスに分岐する状況（たとえば、ECMP）があり得ます。 そのような場合にパス属性を収集するときは、実装は各サブパスの属性の和集合を考慮するべきです（SHOULD）。

In Figure 7 (in Section 6.2.5.1), S has two alternate paths to reach D. Each alternate path fans out to multiple paths due to ECMP. Consider the following link color attributes: all links are RED except {R1,R3}, which is BLUE. The user wants to use an alternate path with only RED links. The first alternate path {S,N1,R1,R2|R3,R4,D} does not fit the constraint, as {R1,R3} is BLUE. The second alternate path {S,N2,PQ,R5,D} fits the constraint and will be preferred, as it uses only RED links.

（セクション6.2.5.1の）図7では、SにはDに到達するための2つの代替パスがあります。 各代替パスは、ECMPによって複数のパスに分岐します。 次のリンクカラー属性を考えます。 {R1,R3}がBLUEであることを除き、すべてのリンクはREDです。 ユーザーは、REDのリンクだけを使う代替パスを使いたいと考えています。 1番目の代替パス{S,N1,R1,R2|R3,R4,D}は、{R1,R3}がBLUEであるため、この制約を満たしません。 2番目の代替パス{S,N2,PQ,R5,D}は、REDのリンクだけを使うため、この制約を満たし、優先されます。

6.2.6. ECMP LFAs

6.2.6. ECMP LFA

In Figure 11, the primary path from PE1 to PE2 is through P1, using ECMP on two parallel links -- L1 and L2. In the case of standard ECMP behavior, if L1 is failing, the post-convergence next hop would become L2 and ECMP would no longer be in use. If an LFA is activated, as stated in Section 3.4 of [RFC5286], "alternate next-hops may themselves also be primary next-hops, but need not be" and "alternate next-hops should maximize the coverage of the failure cases." In this scenario, there is no alternate providing node protection, so PE1 will prefer L2 as the alternate to protect L1; this makes sense compared to post-convergence behavior.

図11では、PE1からPE2へのプライマリーパスは、2本の並列リンクL1とL2でECMPを使い、P1を経由します。 標準的なECMPの動作の場合、L1に障害が発生すると、収束後のネクストホップはL2になり、ECMPはもはや使われなくなります。 LFAが発動した場合、[RFC5286]のセクション3.4に記載されているように、「alternate next-hops may themselves also be primary next-hops, but need not be（代替ネクストホップ自体がプライマリーネクストホップであってもかまいませんが、そうである必要はありません）」、そして「alternate next-hops should maximize the coverage of the failure cases.（代替ネクストホップは障害ケースのカバレッジを最大化すべきです。）」とされています。 このシナリオでは、ノード保護を提供する代替経路が存在しないため、PE1はL1を保護する代替経路としてL2を優先します。 これは、収束後の動作と比べて理にかなっています。

Consider a different scenario, again referring to Figure 11, where L1 and L2 are configured as a Layer 3 bundle using a local feature and L3/L4 comprise a second Layer 3 bundle. Layer 3 bundles are configured as if a link in the bundle is failing; the traffic must be rerouted out of the bundle. Layer 3 bundles are generally introduced to increase bandwidth between nodes. In a nominal situation, ECMP is still available from PE1 to PE2, but if L1 is failing, the post-convergence next hop would become the ECMP on L3 and L4. In this case, LFA behavior SHOULD be adapted in order to reflect the bandwidth requirement.

再び図11を参照して、別のシナリオを考えます。 ここでは、L1とL2がローカルの機能を使ってレイヤー3バンドルとして設定され、L3/L4が2つ目のレイヤー3バンドルを構成しています。 レイヤー3バンドルは、バンドル内のリンクに障害が発生している場合、トラフィックがバンドルの外へリルートされなければならないように設定されます。 レイヤー3バンドルは、一般にノード間の帯域幅を増やすために導入されます。 通常の状況では、PE1からPE2へのECMPが引き続き利用できますが、L1に障害が発生すると、収束後のネクストホップはL3とL4上のECMPになります。 この場合、帯域幅の要件を反映するために、LFAの動作を調整するべきです（SHOULD）。

We would expect the following FIB entry on PE1:

PE1では次のFIBエントリーが期待されます。

If L1 or L2 is failing, traffic must be switched on the LFA ECMP bundle rather than using the other primary next hop.

L1またはL2に障害が発生している場合、トラフィックは、もう一方のプライマリーネクストホップを使うのではなく、LFAのECMPバンドルに切り替えなければなりません。

As mentioned in Section 3.4 of [RFC5286], protecting a link within an ECMP by another primary next hop is not a MUST. Moreover, as already discussed in this document, maximizing coverage against the failure cases may not be the right approach, and a policy-based choice of an alternate may be preferred.

[RFC5286]のセクション3.4で述べられているように、ECMP内のリンクを別のプライマリーネクストホップで保護することは「MUST」ではありません。 さらに、この文書ですでに議論したように、障害ケースに対するカバレッジを最大化することが正しいアプローチであるとは限らず、ポリシーに基づいて代替経路を選択する方が好ましい場合があります。

An implementation SHOULD allow setting a preference to protect a primary next hop with another primary next hop. An implementation SHOULD also allow setting a preference to protect a primary next hop with a NON-primary next hop. An implementation SHOULD allow the use of an ECMP bundle as an LFA.

実装は、プライマリーネクストホップを別のプライマリーネクストホップで保護するための優先度を設定できるようにするべきです（SHOULD）。 また、実装は、プライマリーネクストホップをプライマリーでない（NON-primary）ネクストホップで保護するための優先度を設定できるようにするべきです（SHOULD）。 実装は、ECMPバンドルをLFAとして使えるようにするべきです（SHOULD）。

7. Operational Aspects

7. 運用上の側面

7.1. No-Transit Condition on LFA Computing Node

7.1. LFA計算ノードにおける非トランジット条件

In Section 3.5 of [RFC5286], the setting of the no-transit condition (through the IS-IS overload bit or the OSPF R-bit) in an LFA computation is only taken into account for the case where a neighbor has the no-transit condition set.

[RFC5286]のセクション3.5では、LFAの計算において（IS-ISオーバーロードビットまたはOSPFのRビットによる）非トランジット条件の設定は、近隣に非トランジット条件が設定されている場合にのみ考慮されます。

In addition to Inequality 1 (Loop-Free Criterion) (Distance_opt(N, D) < Distance_opt(N, S) + Distance_opt(S, D)) [RFC5286], the IS-IS overload bit or the OSPF R-bit of the LFA calculating neighbor (S) SHOULD be taken into account. Indeed, if it has the IS-IS overload bit set or the OSPF R-bit clear, no neighbor will loop traffic back to itself.

不等式1（ループフリー基準）（Distance_opt(N, D) < Distance_opt(N, S) + Distance_opt(S, D)）[RFC5286]に加えて、LFAを計算する近隣（S）のIS-ISオーバーロードビットまたはOSPFのRビットを考慮するべきです（SHOULD）。 実際、SにIS-ISオーバーロードビットが設定されている場合、またはOSPFのRビットがクリアされている場合、どの近隣もトラフィックをSにループさせて戻すことはありません。

An OSPF router acting as a stub router [RFC6987] SHOULD behave as if the R-bit was clear regarding the LFA computation.

スタブルーター[RFC6987]として動作するOSPFルーターは、LFAの計算に関して、Rビットがクリアされているかのように振る舞うべきです（SHOULD）。

7.2. Manual Triggering of FRR

7.2. FRRの手動トリガー

Service providers often perform manual link shutdown (using a router's command-line interface (CLI)) to perform network changes/tests. A manual link shutdown may be done at multiple levels: physical interface, logical interface, IGP interface, Bidirectional Forwarding Detection (BFD) session, etc. In particular, testing or troubleshooting FRR requires that manual shutdown be performed on the remote end of the link, as a local shutdown would not generally trigger FRR.

サービスプロバイダーは、ネットワークの変更やテストを行うために、（ルーターのコマンドラインインターフェイス（command-line interface: CLI）を使って）リンクを手動でシャットダウンすることがよくあります。 リンクの手動シャットダウンは、物理インターフェイス、論理インターフェイス、IGPインターフェイス、双方向フォワーディング検出（Bidirectional Forwarding Detection: BFD）セッションなど、複数のレベルで行うことができます。 特に、FRRのテストやトラブルシューティングでは、ローカルでのシャットダウンでは一般にFRRがトリガーされないため、リンクのリモート側で手動シャットダウンを行う必要があります。

To permit such a situation, an implementation SHOULD support triggering/activating LFA FRR for a given link when a manual shutdown is done on a component that currently supports FRR activation.

このような状況に対応するために、実装は、現在FRRの発動をサポートしているコンポーネントで手動シャットダウンが行われたときに、特定のリンクに対するLFA FRRのトリガー/発動をサポートするべきです（SHOULD）。

An implementation MAY also support FRR activation for a specific interface or a specific prefix on a primary next-hop interface and revert without any action on any running component of the node (links or protocols). In this use case, the FRR activation time needs to be controlled by a timer in case the operator forgot to revert the traffic to the primary path. When the timer expires, the traffic is automatically reverted to the primary path. This will simplify the testing of the FRR path; traffic can then be reverted back to the primary path without causing a global network convergence.

実装は、ノードの稼働中のコンポーネント（リンクやプロトコル）に対して何も操作することなく、特定のインターフェイスまたはプライマリーネクストホップのインターフェイス上の特定のプレフィックスについてFRRを発動させ、元に戻すこともサポートしてもよいです（MAY）。 このユースケースでは、運用者がトラフィックをプライマリーパスに戻し忘れた場合に備えて、FRRの発動時間をタイマーで制御する必要があります。 タイマーが満了すると、トラフィックは自動的にプライマリーパスに戻されます。 これによりFRRパスのテストが簡単になります。 その後、ネットワーク全体の収束を引き起こすことなく、トラフィックをプライマリーパスに戻すことができます。

For example:

たとえば、次のとおりです。

  • If an implementation supports FRR activation upon a BFD session-down event, that implementation SHOULD support FRR activation when a manual shutdown is done on the BFD session. But if an implementation does not support FRR activation upon a BFD session-down event, there is no need for that implementation to support FRR activation upon manual shutdown of a BFD session.
  • If an implementation supports FRR activation upon a physical link-down event (e.g., Rx laser "off" detection, error threshold raised), that implementation SHOULD support FRR activation when a manual shutdown of a physical interface is done. But if an implementation does not support FRR activation upon a physical link-down event, there is no need for that implementation to support FRR activation upon manual shutdown of a physical link.
  • A CLI command may allow switching from the primary path to the FRR path to test the FRR path for a specific interface or prefix. There is no impact on the control plane; only the data plane of the local node may be changed. A similar command may allow switching traffic back from the FRR path to the primary path.
  • 実装がBFDのセッションダウンイベントでのFRRの発動をサポートしている場合、その実装は、BFDセッションで手動シャットダウンが行われたときのFRRの発動をサポートするべきです（SHOULD）。 しかし、実装がBFDのセッションダウンイベントでのFRRの発動をサポートしていない場合、その実装がBFDセッションの手動シャットダウンでのFRRの発動をサポートする必要はありません。
  • 実装が物理的なリンクダウンイベント（たとえば、受信レーザーの「off」の検出、エラーしきい値の超過）でのFRRの発動をサポートしている場合、その実装は、物理インターフェイスの手動シャットダウンが行われたときのFRRの発動をサポートするべきです（SHOULD）。 しかし、実装が物理的なリンクダウンイベントでのFRRの発動をサポートしていない場合、その実装が物理リンクの手動シャットダウンでのFRRの発動をサポートする必要はありません。
  • 特定のインターフェイスまたはプレフィックスについてFRRパスをテストするために、CLIコマンドでプライマリーパスからFRRパスへの切り替えができるようにしてもかまいません。 コントロールプレーンへの影響はなく、変更されうるのはローカルノードのデータプレーンだけです。 同様のコマンドで、トラフィックをFRRパスからプライマリーパスに戻せるようにしてもかまいません。

7.3. Required Local Information

7.3. 必要なローカル情報

The introduction of LFAs in a network requires some enhancements to standard routing information provided by implementations. Moreover, due to "non-100%" coverage, coverage information is also required.

ネットワークにLFAを導入するには、実装が提供する標準的なルーティング情報にいくつかの拡張が必要です。 さらに、カバレッジが「100%ではない」ため、カバレッジの情報も必要です。

Hence, an implementation:

したがって、実装には次の要件があります。

  • MUST be able to display, for every prefix, the primary next hop as well as the alternate next-hop information.
  • MUST provide coverage information per LFA activation domain (area, level, topology, instance, virtual router, address family, etc.).
  • MUST provide the number of protected prefixes as well as non-protected prefixes globally.
  • SHOULD provide the number of protected prefixes as well as non-protected prefixes per link.
  • MAY provide the number of protected prefixes as well as non-protected prefixes per priority if the implementation supports prefix-priority insertion in the RIB/FIB.
  • SHOULD provide a reason for choosing an alternate (policy and criteria) and for excluding an alternate.
  • SHOULD provide the list of non-protected prefixes and the reason why they are not protected (e.g., no protection required, no alternate available).
  • すべてのプレフィックスについて、プライマリーネクストホップと代替ネクストホップの情報を表示できなければなりません（MUST）。
  • LFA有効化ドメイン（エリア、レベル、トポロジー、インスタンス、仮想ルーター、アドレスファミリーなど）ごとのカバレッジ情報を提供しなければなりません（MUST）。
  • 保護されているプレフィックスの数と保護されていないプレフィックスの数を、全体について提供しなければなりません（MUST）。
  • 保護されているプレフィックスの数と保護されていないプレフィックスの数を、リンクごとに提供するべきです（SHOULD）。
  • 実装がRIB/FIBへのプレフィックスの優先度付き挿入をサポートしている場合、保護されているプレフィックスの数と保護されていないプレフィックスの数を、優先度ごとに提供してもよいです（MAY）。
  • 代替経路を選んだ理由（ポリシーと基準）と、代替経路を除外した理由を提供するべきです（SHOULD）。
  • 保護されていないプレフィックスのリストと、それらが保護されていない理由（たとえば、保護が要求されていない、利用可能な代替経路がない）を提供するべきです（SHOULD）。

7.4. Coverage Monitoring

7.4. カバレッジの監視

It is pretty easy to evaluate the coverage of a network in a nominal situation, but topology changes may change the level of coverage. In some situations, the network may no longer be able to provide the required level of protection. Hence, it becomes very important for service providers to receive alerts regarding changes in coverage.

通常の状況でネットワークのカバレッジを評価するのはきわめて簡単ですが、トポロジーの変化によってカバレッジのレベルが変わる可能性があります。 状況によっては、ネットワークが要求されるレベルの保護をもはや提供できなくなる場合もあります。 したがって、サービスプロバイダーがカバレッジの変化に関するアラートを受け取ることは非常に重要になります。

An implementation SHOULD:

実装は、次のようにするべきです（SHOULD）。

  • provide an alert system if total coverage (for a node) is below a defined threshold or when coverage returns to normal.
  • provide an alert system if coverage for a specific link is below a defined threshold or when coverage returns to normal.
  • （ノードについての）全体のカバレッジが定義されたしきい値を下回った場合、またはカバレッジが正常に戻ったときのアラートの仕組みを提供する。
  • 特定のリンクのカバレッジが定義されたしきい値を下回った場合、またはカバレッジが正常に戻ったときのアラートの仕組みを提供する。

An implementation MAY:

実装は、次のようにしてもよいです（MAY）。

  • trigger an alert if a specific destination is not protected anymore or when protection comes back up for this destination.
  • 特定の宛先がもはや保護されなくなった場合、またはその宛先の保護が復旧したときに、アラートをトリガーする。

Although the procedures for providing alerts are beyond the scope of this document, we recommend that implementations consider standard and well-used mechanisms like syslog or SNMP traps.

アラートを提供する手順はこの文書の範囲外ですが、実装はsyslogやSNMPトラップのような標準的でよく使われているメカニズムを検討することを推奨します。

7.5. LFAs and Network Planning

7.5. LFAとネットワーク計画

The operator may choose to run simulations in order to ensure a certain type of full coverage for the whole network or a given subset of the network. This is particularly likely if he operates the network in the sense of the third backbone profile described in Section 4 of [RFC6571]; that is, he seeks to design and engineer the network topology in such a way that a certain level of coverage is always achieved. Obviously, a complete and exact simulation of the IP FRR coverage can only be achieved if the behavior is deterministic and the algorithm used is available to the simulation tool. Thus, an implementation SHOULD:

運用者は、ネットワーク全体またはネットワークの特定の部分集合について、ある種の完全なカバレッジを確保するために、シミュレーションを実行することを選ぶ場合があります。 これは、運用者が[RFC6571]のセクション4で説明されている3番目のバックボーンプロファイルの意味でネットワークを運用している場合、つまり、一定レベルのカバレッジが常に達成されるようにネットワークトポロジーを設計・構築しようとしている場合に、特に当てはまります。 当然ながら、IP FRRのカバレッジの完全かつ正確なシミュレーションは、動作が決定的であり、使われるアルゴリズムをシミュレーションツールが利用できる場合にのみ実現できます。 したがって、実装は次のようにするべきです（SHOULD）。

  • Behave deterministically in its LFA selection process. That is, in the same topology and with the same policy configuration, the implementation MUST always choose the same alternate for a given prefix.
  • Document its behavior. The implementation SHOULD provide enough documentation regarding its behavior to allow an implementer of a simulation tool to foresee the exact choice of the LFA implementation for every prefix in a given topology. This SHOULD take into account all possible policy configuration options. One possible way to document this behavior is to disclose the algorithm used to choose alternates.
  • LFAの選択処理において決定的に振る舞う。 つまり、同じトポロジーで同じポリシー設定の場合、実装は、特定のプレフィックスに対して常に同じ代替経路を選ばなければなりません（MUST）。
  • 自身の動作を文書化する。 実装は、シミュレーションツールの実装者が、特定のトポロジーにおけるすべてのプレフィックスについてLFA実装の選択を正確に予測できるよう、自身の動作に関する十分なドキュメントを提供するべきです（SHOULD）。 これは、可能なすべてのポリシー設定オプションを考慮に入れるべきです（SHOULD）。 この動作を文書化する方法の1つとして、代替経路を選ぶために使うアルゴリズムを開示することが考えられます。

8. Security Considerations

8. セキュリティーに関する考慮事項

The policy mechanism introduced in this document allows the tuning of the selection of the alternate. This is not seen as a security threat, because:

この文書で導入したポリシーメカニズムによって、代替経路の選択を調整できるようになります。 これは、次の理由から、セキュリティー上の脅威とはみなされません。

  • all candidates are already eligible as per [RFC5286] and considered usable.
  • the policy is based on information from the router's own configuration and from the IGP, both of which are considered trusted.
  • すべての候補は、[RFC5286]に従ってすでに適格であり、使用可能とみなされているため。
  • ポリシーは、ルーター自身の設定とIGPからの情報に基づいており、そのどちらも信頼できるとみなされているため。

Hence, this document does not introduce any new security considerations as compared to [RFC5286].

したがって、この文書は、[RFC5286]と比べて新しいセキュリティー上の考慮事項を何も導入しません。

As noted above, the policy mechanism introduced in this document allows the tuning of the selection of the best alternate but does not change the list of alternates that are eligible. As described in Section 7 of [RFC5286], this best alternate "can be used anyway when a different topological change occurs, and hence this can't be viewed as a new security threat."

前述のとおり、この文書で導入したポリシーメカニズムによって最良の代替経路の選択を調整できるようになりますが、適格な代替経路のリストは変わりません。 [RFC5286]のセクション7で説明されているように、この最良の代替経路は「can be used anyway when a different topological change occurs, and hence this can't be viewed as a new security threat.（いずれにしても別のトポロジー変化が起きたときに使われうるものであり、したがって新しいセキュリティー上の脅威とみなすことはできません。）」ものです。
