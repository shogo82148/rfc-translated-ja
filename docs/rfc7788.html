RFC 7788

Home Networking Control Protocol

RFC 7788

ホームネットワーキング制御プロトコル

Abstract

概要

This document describes the Home Networking Control Protocol (HNCP), an extensible configuration protocol, and a set of requirements for home network devices. HNCP is described as a profile of and extension to the Distributed Node Consensus Protocol (DNCP). HNCP enables discovery of network borders, automated configuration of addresses, name resolution, service discovery, and the use of any routing protocol that supports routing based on both the source and destination address.

この文書は、拡張可能な設定プロトコルであるホームネットワーキング制御プロトコル（Home Networking Control Protocol、HNCP）と、ホームネットワーク機器に対する一連の要件を記述します。HNCPは、分散ノードコンセンサスプロトコル（Distributed Node Consensus Protocol、DNCP）のプロファイルおよび拡張として記述されます。HNCPにより、ネットワーク境界の発見、アドレスの自動設定、名前解決、サービス発見、および送信元アドレスと宛先アドレスの両方に基づくルーティングをサポートする任意のルーティングプロトコルの使用が可能になります。

1. Introduction

1. はじめに

The Home Networking Control Protocol (HNCP) is designed to facilitate the sharing of state among home routers to fulfill the needs of the IPv6 homenet architecture [RFC7368], which assumes zero-configuration operation, multiple subnets, multiple home routers, and (potentially) multiple upstream service providers providing (potentially) multiple prefixes to the home network. While RFC 7368 sets no requirements for IPv4 support, HNCP aims to support the dual-stack mode of operation, and therefore the functionality is designed with that in mind. The state is shared as TLVs transported in the DNCP node state among the routers (and potentially advanced hosts) to enable:

ホームネットワーキング制御プロトコル（HNCP）は、IPv6ホームネットアーキテクチャー[RFC7368]の要求を満たすために、ホームルーター間での状態の共有を容易にするよう設計されています。このアーキテクチャーは、ゼロコンフィギュレーションでの運用、複数のサブネット、複数のホームルーター、そして（場合によっては）ホームネットワークに（場合によっては）複数のプレフィックスを提供する複数の上流サービスプロバイダーを想定しています。RFC 7368はIPv4のサポートに関する要件を定めていませんが、HNCPはデュアルスタックでの運用をサポートすることを目指しており、したがって機能はそれを念頭に置いて設計されています。状態は、ルーター（および場合によっては高度なホスト）の間でDNCPノード状態に含めて転送されるTLVとして共有され、次のことを可能にします：

  • Autonomic discovery of network borders (Section 5.3) based on Distributed Node Consensus Protocol (DNCP) topology.

  • Automated portioning of prefixes delegated by the service providers as well as assigned prefixes to both HNCP and non-HNCP routers (Section 6.3) using [RFC7695]. Prefixes assigned to HNCP routers are used to:

    • Provide addresses to non-HNCP aware nodes (using Stateless Address Autoconfiguration (SLAAC) and DHCP).
    • Provide space in which HNCP nodes assign their own addresses (Section 6.4).
  • Internal and external name resolution, as well as multi-link service discovery (Section 8).
  • Other services not defined in this document that do need to share state among homenet nodes and do not cause rapid and constant TLV changes (see the following applicability section).
  • 分散ノードコンセンサスプロトコル（DNCP）のトポロジーに基づく、ネットワーク境界の自律的な発見（セクション5.3）。

  • [RFC7695]を用いた、サービスプロバイダーから委任されたプレフィックスの自動的な分割、およびHNCPルーターと非HNCPルーターの両方へのプレフィックスの割り当て（セクション6.3）。HNCPルーターに割り当てられたプレフィックスは、次の目的で使用されます：

    • HNCPを認識しないノードにアドレスを提供する（ステートレスアドレス自動設定（SLAAC）とDHCPを使用）。
    • HNCPノードが自身のアドレスを割り当てる空間を提供する（セクション6.4）。
  • 内部および外部の名前解決、ならびにマルチリンクでのサービス発見（セクション8）。
  • この文書では定義されていない、ホームネットのノード間で状態を共有する必要があり、かつTLVの急速かつ継続的な変更を引き起こさないその他のサービス（後述の適用性のセクションを参照）。

HNCP is a protocol based on DNCP [RFC7787] and includes a DNCP profile that defines transport and synchronization details for sharing state across nodes defined in Section 3. The rest of the document defines behavior of the services noted above, how the required TLVs are encoded (Section 10), as well as additional requirements on how HNCP nodes should behave (Section 11).

HNCPはDNCP[RFC7787]に基づくプロトコルであり、セクション3で定義する、ノード間で状態を共有するためのトランスポートと同期の詳細を定めるDNCPプロファイルを含みます。この文書の残りの部分では、上記のサービスの振る舞い、必要なTLVのエンコード方法（セクション10）、およびHNCPノードがどのように振る舞うべきかに関する追加の要件（セクション11）を定義します。

1.1. Applicability

1.1. 適用性

While HNCP does not deal with routing protocols directly (except potentially informing them about internal and external interfaces if classification specified in Section 5.3 is used), in homenet environments where multiple IPv6 source prefixes can be present, routing based on the source and destination address is necessary [RFC7368]. Ideally, the routing protocol is also zero configuration (e.g., no need to configure identifiers or metrics), although HNCP can also be used with a manually configured routing protocol.

HNCPはルーティングプロトコルを直接扱いません（セクション5.3で規定する分類を使用する場合に、内部および外部のインターフェイスについてルーティングプロトコルに通知する可能性があることを除きます）。しかし、複数のIPv6送信元プレフィックスが存在しうるホームネット環境では、送信元アドレスと宛先アドレスに基づくルーティングが必要です[RFC7368]。HNCPは手動で設定されたルーティングプロトコルと併用することもできますが、理想的にはルーティングプロトコルもゼロコンフィギュレーション（たとえば、識別子やメトリックの設定が不要）であることが望まれます。

As HNCP uses DNCP as the actual state synchronization protocol, the applicability statement of DNCP applies here as well; HNCP should not be used for any data that changes rapidly and constantly. If such data needs to be published in an HNCP network, 1) a more applicable protocol should be used for those portions, and 2) locators to a server of said protocol should be announced using HNCP instead. An example for this is naming and service discovery (Section 8) for which HNCP only transports DNS server addresses and no actual per-name or per-service data of hosts.

HNCPは実際の状態同期プロトコルとしてDNCPを使用するため、DNCPの適用性に関する記述がここでも適用されます。すなわち、HNCPは急速かつ継続的に変化するデータには使用すべきではありません。そのようなデータをHNCPネットワークで公開する必要がある場合は、1）その部分にはより適したプロトコルを使用すべきであり、2）代わりに、そのプロトコルのサーバーへのロケーターをHNCPを使って告知すべきです。この例として、名前付けとサービス発見（セクション8）があります。この場合、HNCPはDNSサーバーのアドレスのみを転送し、ホストの名前ごとやサービスごとの実際のデータは転送しません。

HNCP TLVs specified within this document, in steady state, stay constant, with one exception: as Delegated-Prefix TLVs (Section 10.2.1) do contain lifetimes, they force republishing of that data every time the valid or preferred lifetimes of prefixes are updated (significantly). Therefore, it is desirable for ISPs to provide large enough valid and preferred lifetimes to avoid unnecessary HNCP state churn in homes, but even given non-cooperating ISPs, the state churn is proportional only to the number of externally received delegated prefixes and not to the home network size, and it should therefore be relatively low.

この文書で規定するHNCPのTLVは、定常状態では一定のままですが、1つ例外があります。Delegated-Prefix TLV（セクション10.2.1）は有効期間を含むため、プレフィックスの有効期間（valid lifetime）または推奨期間（preferred lifetime）が（大幅に）更新されるたびに、そのデータの再公開が必要になります。したがって、家庭内での不要なHNCPの状態の変動を避けるために、ISPが十分に大きな有効期間と推奨期間を提供することが望ましいです。しかし、協力的でないISPであっても、状態の変動は外部から受け取った委任されたプレフィックスの数にのみ比例し、ホームネットワークの規模には比例しないため、比較的少ないはずです。

HNCP assumes a certain level of control over host configuration servers (e.g., DHCP [RFC2131]) on links that are managed by its routers. Some HNCP functionality (such as border discovery or some aspects of naming) might be affected by existing DHCP servers that are not aware of the HNCP-managed network and thus might need to be reconfigured to not result in unexpected behavior.

HNCPは、そのルーターが管理するリンク上のホスト設定サーバー（たとえば、DHCP[RFC2131]）をある程度制御できることを前提としています。HNCPの一部の機能（境界発見や名前付けの一部の側面など）は、HNCPが管理するネットワークを認識していない既存のDHCPサーバーの影響を受ける可能性があるため、予期しない振る舞いを引き起こさないように、そのようなサーバーを再設定する必要があるかもしれません。

While HNCP routers can provide configuration to and receive configuration from non-HNCP routers, they are not able to traverse such devices based solely on the protocol as defined in this document, i.e., HNCP routers that are connected only by different interfaces of a non-HNCP router will not be part of the same HNCP network.

HNCPルーターは、非HNCPルーターに設定を提供したり、非HNCPルーターから設定を受け取ったりできますが、この文書で定義するプロトコルだけに基づいてそのような機器を越えることはできません。すなわち、非HNCPルーターの異なるインターフェイスを介してのみ接続されているHNCPルーター同士は、同じHNCPネットワークの一部にはなりません。

While HNCP is designed to be used by (home) routers, it can also be used by advanced hosts that want to do, e.g., their own address assignment and routing.

HNCPは（ホーム）ルーターで使用されるように設計されていますが、たとえば独自にアドレス割り当てやルーティングを行いたい高度なホストで使用することもできます。

HNCP is link-layer agnostic; if a link supports IPv6 (link-local) multicast and unicast, HNCP will work on it. Trickle retransmissions and keep-alives will handle both packet loss and non-transitive connectivity, ensuring eventual convergence.

HNCPはリンク層に依存しません。リンクがIPv6（リンクローカル）のマルチキャストとユニキャストをサポートしていれば、HNCPはそのリンク上で動作します。Trickleによる再送とキープアライブにより、パケット損失と非推移的な接続性の両方に対処し、最終的な収束を保証します。

3. DNCP Profile

3. DNCPプロファイル

The DNCP profile for HNCP is defined as follows:

HNCPのためのDNCPプロファイルは、次のように定義されます：

  • HNCP uses UDP datagrams on port 8231 as a transport over link-local scoped IPv6, using unicast and multicast (FF02:0:0:0:0:0:0:11 is the HNCP group address). Received datagrams where either or both of the IPv6 source or destination addresses are not link-local scoped MUST be ignored. Replies to multicast and unicast messages MUST be sent to the IPv6 source address and port of the original message. Each node MUST be able to receive (and potentially reassemble) UDP datagrams with a payload of at least 4000 bytes.
  • HNCP operates on multicast-capable interfaces only. HNCP nodes MUST assign a non-zero 32-bit endpoint identifier to each interface for which HNCP is enabled. The value 0 is not used in DNCP TLVs but has a special meaning in HNCP TLVs (see Sections 6.4 and 10.3). These identifiers MUST be locally unique within the scope of the node, and using values equivalent to the IPv6 link-local scope identifiers for the given interfaces are RECOMMENDED.
  • HNCP uses opaque 32-bit node identifiers (DNCP_NODE_IDENTIFIER_LENGTH = 32). A node implementing HNCP SHOULD use a random node identifier. If there is a node identifier collision (as specified in the Node-State TLV handling of Section 4.4 of [RFC7787]), the node MUST immediately generate and use a new random node identifier that is not used by any other node at the time, based on the current DNCP network state.
  • HNCP nodes MUST use the leading 64 bits of the MD5 message digest [RFC1321] as the DNCP hash function H(x) used in building the DNCP hash tree.

  • HNCP nodes MUST use DNCP's per-endpoint keep-alive extension on all endpoints. The following parameters are suggested:

    • Default keep-alive interval (DNCP_KEEPALIVE_INTERVAL): 20 seconds.
    • Multiplier (DNCP_KEEPALIVE_MULTIPLIER): 2.1 on virtually lossless links works fine, as it allows for one lost keep-alive. If used on a lossy link, a considerably higher multiplier, such as 15, should be used instead. In that case, an implementation might prefer shorter keep-alive intervals on that link as well to ensure that the timeout (equal to DNCP_KEEPALIVE_INTERVAL * DNCP_KEEPALIVE_MULTIPLIER) after which entirely lost nodes time out is low enough.

  • HNCP nodes use the following Trickle parameters for the per-interface Trickle instances:

    • k SHOULD be 1, as the timer reset when data is updated, and further retransmissions should handle packet loss. Even on a non-transitive lossy link, the eventual per-endpoint keep-alives should ensure status synchronization occurs.
    • Imin SHOULD be 200 milliseconds but MUST NOT be lower. Note: earliest transmissions may occur at Imin / 2.
    • Imax SHOULD be 7 doublings of Imin [RFC6206] but MUST NOT be lower.
  • HNCP unicast traffic SHOULD be secured using Datagram Transport Layer Security (DTLS) [RFC6347] as described in DNCP if exchanged over unsecured links. UDP on port 8232 is used for this purpose. A node implementing HNCP security MUST support the DNCP Pre-Shared Key (PSK) method, SHOULD support the PKI-based trust method, and MAY support the DNCP certificate-based trust consensus method. [RFC7525] provides guidance on how to securely utilize DTLS.
  • HNCP nodes MUST ignore all Node-State TLVs received via multicast on a link that has DNCP security enabled in order to prevent spoofing of node state changes.
  • HNCPは、リンクローカルスコープのIPv6上のトランスポートとして、ポート8231のUDPデータグラムを使用し、ユニキャストとマルチキャストを使用します（FF02:0:0:0:0:0:0:11がHNCPのグループアドレスです）。IPv6の送信元アドレスと宛先アドレスのいずれか、または両方がリンクローカルスコープでない受信データグラムは、無視しなければなりません（MUST）。マルチキャストメッセージおよびユニキャストメッセージへの返信は、元のメッセージのIPv6送信元アドレスとポートに送信しなければなりません（MUST）。各ノードは、少なくとも4000バイトのペイロードを持つUDPデータグラムを受信（および場合によっては再構築）できる必要があります（MUST）。
  • HNCPは、マルチキャスト対応のインターフェイス上でのみ動作します。HNCPノードは、HNCPが有効になっている各インターフェイスに、0でない32ビットのエンドポイント識別子を割り当てなければなりません（MUST）。値0はDNCPのTLVでは使用されませんが、HNCPのTLVでは特別な意味を持ちます（セクション6.4と10.3を参照）。これらの識別子は、ノードのスコープ内でローカルに一意である必要があります（MUST）。また、該当するインターフェイスのIPv6リンクローカルスコープ識別子と同等の値を使用することが推奨されます（RECOMMENDED）。
  • HNCPは、不透明な32ビットのノード識別子を使用します（DNCP_NODE_IDENTIFIER_LENGTH = 32）。HNCPを実装するノードは、ランダムなノード識別子を使用すべきです（SHOULD）。ノード識別子の衝突（[RFC7787]のセクション4.4のNode-State TLVの処理で規定されているもの）が発生した場合、ノードは、現在のDNCPネットワークの状態に基づいて、その時点で他のどのノードにも使用されていない新しいランダムなノード識別子を直ちに生成して使用しなければなりません（MUST）。
  • HNCPノードは、DNCPハッシュツリーの構築に使用するDNCPハッシュ関数H(x)として、MD5メッセージダイジェスト[RFC1321]の先頭64ビットを使用しなければなりません（MUST）。

  • HNCPノードは、すべてのエンドポイントでDNCPのエンドポイントごとのキープアライブ拡張を使用しなければなりません（MUST）。次のパラメーターを提案します：

    • デフォルトのキープアライブ間隔（DNCP_KEEPALIVE_INTERVAL）：20秒。
    • 乗数（DNCP_KEEPALIVE_MULTIPLIER）：損失がほぼないリンクでは2.1で問題なく機能します。これにより、キープアライブを1回失っても許容されるためです。損失の多いリンクで使用する場合は、代わりに15のようなかなり大きな乗数を使用すべきです。その場合、完全に失われたノードがタイムアウトするまでの時間（DNCP_KEEPALIVE_INTERVAL * DNCP_KEEPALIVE_MULTIPLIERに等しい）を十分に短くするために、実装はそのリンクでのキープアライブ間隔も短くすることを選ぶかもしれません。

  • HNCPノードは、インターフェイスごとのTrickleインスタンスに次のTrickleパラメーターを使用します：

    • kは1であるべきです（SHOULD）。データが更新されるとタイマーがリセットされ、その後の再送がパケット損失に対処するはずだからです。非推移的で損失の多いリンクであっても、最終的にはエンドポイントごとのキープアライブにより状態の同期が確実に行われるはずです。
    • Iminは200ミリ秒であるべきです（SHOULD）。ただし、それより小さくしてはなりません（MUST NOT）。注：最も早い送信はImin / 2の時点で発生する可能性があります。
    • Imaxは、Iminを7回倍にした値[RFC6206]であるべきです（SHOULD）。ただし、それより小さくしてはなりません（MUST NOT）。
  • セキュリティーが確保されていないリンク上でやり取りされる場合、HNCPのユニキャストトラフィックは、DNCPで説明されているように、Datagram Transport Layer Security（DTLS）[RFC6347]を使用して保護すべきです（SHOULD）。この目的には、ポート8232のUDPを使用します。HNCPのセキュリティーを実装するノードは、DNCPの事前共有鍵（PSK）方式をサポートしなければなりません（MUST）。PKIベースの信頼方式はサポートすべきです（SHOULD）。DNCPの証明書ベースの信頼コンセンサス方式はサポートしてもよいです（MAY）。[RFC7525]は、DTLSを安全に利用する方法に関するガイダンスを提供しています。
  • ノード状態の変更のなりすましを防ぐために、HNCPノードは、DNCPのセキュリティーが有効になっているリンク上でマルチキャストを介して受信したすべてのNode-State TLVを無視しなければなりません（MUST）。

4. HNCP Versioning and Router Capabilities

4. HNCPのバージョン管理とルーターの能力

Multiple versions of HNCP based on compatible DNCP profiles may be present in the same network when transitioning between HNCP versions, and for troubleshooting purposes, it might be beneficial to identify the HNCP agent version running. Therefore, each node MUST include an HNCP-Version TLV (Section 10.1) indicating the currently supported version in its node data and MUST ignore (except for DNCP synchronization purposes) any TLVs that have a type greater than 32 and that are published by nodes that didn't also publish an HNCP-Version TLV.

HNCPのバージョン間の移行時には、互換性のあるDNCPプロファイルに基づく複数のバージョンのHNCPが同じネットワーク内に存在する可能性があります。また、トラブルシューティングのために、動作しているHNCPエージェントのバージョンを識別できると有益な場合があります。したがって、各ノードは、現在サポートしているバージョンを示すHNCP-Version TLV（セクション10.1）をノードデータに含めなければなりません（MUST）。また、HNCP-Version TLVを公開していないノードが公開した、タイプが32より大きいTLVは、（DNCPの同期の目的を除き）無視しなければなりません（MUST）。

HNCP routers may also have different capabilities regarding interactions with hosts, e.g., for configuration or service discovery. These are indicated by M, P, H, and L values. The combined "capability value" is a metric indicated by interpreting the bits as an integer, i.e., (M << 12 | P << 8 | H << 4 | L). These values are used to elect certain servers on a Common Link, as described in Section 7. Nodes that are not routers MUST announce the value 0 for all capabilities. Any node announcing the value 0 for a capability is considered to not advertise said capability and thus does not take part in the respective election.

HNCPルーターは、たとえば設定やサービス発見などのホストとのやり取りに関して、異なる能力を持つ場合もあります。これらはM、P、H、Lの値で示されます。組み合わせた「能力値」は、これらのビットを整数として解釈することで示されるメトリック、すなわち(M << 12 | P << 8 | H << 4 | L)です。セクション7で説明するように、これらの値は共通リンク上で特定のサーバーを選出するために使用されます。ルーターでないノードは、すべての能力について値0を告知しなければなりません（MUST）。ある能力について値0を告知するノードは、その能力を広告していないとみなされ、したがってそれぞれの選出には参加しません。

5. Interface Classification

5. インターフェイスの分類

5.1. Interface Categories

5.1. インターフェイスのカテゴリー

HNCP specifies the following categories that interfaces can be configured to be in:

HNCPは、インターフェイスに設定できる次のカテゴリーを規定します：

Internal category:
This declares an interface to be internal, i.e., within the borders of the HNCP network. The interface MUST operate as a DNCP endpoint. Routers MUST forward traffic with appropriate source addresses between their internal interfaces and allow internal traffic to reach external networks. All nodes MUST implement this category, and nodes not implementing any other category implicitly use it as a fixed default.
External category:
This declares an interface to be external, i.e., not within the borders of the HNCP network. The interface MUST NOT operate as a DNCP endpoint. Accessing internal resources from external interfaces is restricted, i.e., the use of Recommended Simple Security Capabilities in Customer Premises Equipments (CPEs) [RFC6092] is RECOMMENDED. HNCP routers SHOULD announce acquired configuration information for use in the network as described in Section 6.2, if the interface appears to be connected to an external network. HNCP routers MUST implement this category.
Leaf category:
This declares an interface used by client devices only. Such an interface uses the Internal category with the exception that it MUST NOT operate as a DNCP endpoint. This category SHOULD be supported by HNCP routers.
Guest category:
This declares an interface used by untrusted client devices only. In addition to the restrictions of the Leaf category, HNCP routers MUST filter traffic from and to the interface such that connected devices are unable to reach other devices inside the HNCP network or query services advertised by them unless explicitly allowed. This category SHOULD be supported by HNCP routers.
Ad Hoc category:
This configures an interface to use the Internal category, but no assumption is made about the link's transitivity. All other interface categories assume transitive connectivity. This affects the Common Link (Section 6.1) definition. Support for this category is OPTIONAL.
Hybrid category:
This declares an interface to use the Internal category while still trying to acquire (external) configuration information on it, e.g., by running DHCP clients. This is useful, e.g., if the link is shared with a non-HNCP router under control and still within the borders of the same network. Detection of this category automatically in addition to manual configuration is out of scope of this document. Support for this category is OPTIONAL.
Internalカテゴリー：
インターフェイスが内部である、すなわちHNCPネットワークの境界内にあることを宣言します。そのインターフェイスは、DNCPエンドポイントとして動作しなければなりません（MUST）。ルーターは、内部インターフェイス間で適切な送信元アドレスを持つトラフィックを転送し、内部のトラフィックが外部ネットワークに到達できるようにしなければなりません（MUST）。すべてのノードはこのカテゴリーを実装しなければなりません（MUST）。他のカテゴリーを実装していないノードは、暗黙的にこのカテゴリーを固定のデフォルトとして使用します。
Externalカテゴリー：
インターフェイスが外部である、すなわちHNCPネットワークの境界内にないことを宣言します。そのインターフェイスは、DNCPエンドポイントとして動作してはなりません（MUST NOT）。外部インターフェイスからの内部リソースへのアクセスは制限されます。すなわち、「Recommended Simple Security Capabilities in Customer Premises Equipments（CPEs）」[RFC6092]を使用することが推奨されます（RECOMMENDED）。インターフェイスが外部ネットワークに接続されているように見える場合、HNCPルーターは、セクション6.2で説明するように、取得した設定情報をネットワーク内で使用するために告知すべきです（SHOULD）。HNCPルーターはこのカテゴリーを実装しなければなりません（MUST）。
Leafカテゴリー：
クライアント機器のみが使用するインターフェイスであることを宣言します。このようなインターフェイスはInternalカテゴリーを使用しますが、例外として、DNCPエンドポイントとして動作してはなりません（MUST NOT）。このカテゴリーは、HNCPルーターがサポートすべきです（SHOULD）。
Guestカテゴリー：
信頼できないクライアント機器のみが使用するインターフェイスであることを宣言します。Leafカテゴリーの制限に加えて、HNCPルーターは、明示的に許可されていない限り、接続された機器がHNCPネットワーク内の他の機器に到達したり、それらが広告するサービスに問い合わせたりできないように、そのインターフェイスとの間のトラフィックをフィルタリングしなければなりません（MUST）。このカテゴリーは、HNCPルーターがサポートすべきです（SHOULD）。
Ad Hocカテゴリー：
インターフェイスがInternalカテゴリーを使用するように設定しますが、リンクの推移性については何も前提としません。他のすべてのインターフェイスカテゴリーは、推移的な接続性を前提とします。これは共通リンク（セクション6.1）の定義に影響します。このカテゴリーのサポートは選択できます（OPTIONAL）。
Hybridカテゴリー：
インターフェイスがInternalカテゴリーを使用しつつ、たとえばDHCPクライアントを実行することによって、そのインターフェイス上で（外部の）設定情報の取得も試みることを宣言します。これは、たとえば、リンクが管理下にあって同じネットワークの境界内にある非HNCPルーターと共有されている場合に有用です。手動設定に加えてこのカテゴリーを自動的に検出することは、この文書の範囲外です。このカテゴリーのサポートは選択できます（OPTIONAL）。

5.2. DHCP-Aided Auto-Detection

5.2. DHCPを利用した自動検出

Auto-detection of interface categories is possible based on interaction with DHCPv4 [RFC2131] and DHCPv6 Prefix Delegation (DHCPv6-PD) [RFC3633] servers on connected links. HNCP defines special DHCP behavior to differentiate its internal servers from external ones in order to achieve this. Therefore, all internal devices (including HNCP nodes) running DHCP servers on links where auto-detection is used by any HNCP node MUST use the following mechanism based on "The User Class Option for DHCP" [RFC3004] and its DHCPv6 counterpart [RFC3315]:

インターフェイスカテゴリーの自動検出は、接続されたリンク上のDHCPv4[RFC2131]サーバーおよびDHCPv6プレフィックス委任（DHCPv6-PD）[RFC3633]サーバーとのやり取りに基づいて行えます。これを実現するために、HNCPは、内部のサーバーと外部のサーバーを区別するための特別なDHCPの振る舞いを定義します。したがって、いずれかのHNCPノードが自動検出を使用しているリンク上でDHCPサーバーを実行しているすべての内部機器（HNCPノードを含む）は、「The User Class Option for DHCP」[RFC3004]およびそのDHCPv6版[RFC3315]に基づく次のメカニズムを使用しなければなりません（MUST）：

  • The device MUST ignore or reject DHCP-Requests containing a DHCP user class consisting of the ASCII string "HOMENET".
  • 機器は、ASCII文字列"HOMENET"からなるDHCPユーザークラスを含むDHCP-Requestを無視または拒否しなければなりません（MUST）。

Not following this rule (e.g., running unmodified DHCP servers) might lead to false positives when auto-detection is used, i.e., HNCP nodes assume an interface to not be internal, even though it was intended to be.

この規則に従わない場合（たとえば、変更されていないDHCPサーバーを実行している場合）、自動検出を使用したときに誤検出が生じる可能性があります。すなわち、HNCPノードは、内部であることが意図されていたインターフェイスを内部ではないとみなしてしまいます。

5.3. Algorithm for Border Discovery

5.3. 境界発見のアルゴリズム

This section defines the interface classification algorithm. It is suitable for both IPv4 and IPv6 (single or dual stack) and detects the category of an interface either automatically or based on a fixed configuration. By determining the category for all interfaces, the network borders are implicitly defined, i.e., all interfaces not belonging to the External category are considered to be within the borders of the network; all others are not.

このセクションでは、インターフェイスの分類アルゴリズムを定義します。このアルゴリズムはIPv4とIPv6（シングルスタックまたはデュアルスタック）の両方に適しており、インターフェイスのカテゴリーを自動的に、または固定の設定に基づいて検出します。すべてのインターフェイスのカテゴリーを決定することで、ネットワーク境界が暗黙的に定義されます。すなわち、Externalカテゴリーに属さないすべてのインターフェイスはネットワークの境界内にあるとみなされ、それ以外はそうではないとみなされます。

The following algorithm MUST be implemented by any node implementing HNCP. However, if the node does not implement auto-detection, only the first and last step are required. The algorithm works as follows, with evaluation stopping at first match:

HNCPを実装するすべてのノードは、次のアルゴリズムを実装しなければなりません（MUST）。ただし、ノードが自動検出を実装していない場合は、最初と最後のステップのみが必要です。アルゴリズムは次のように動作し、最初に一致した時点で評価を終了します：

  1. If a fixed category is configured for an interface, it is used.
  2. If a delegated prefix could be acquired by running a DHCPv6 client, it is considered external. The DHCPv6 client MUST have included a DHCPv6 user class consisting of the ASCII string "HOMENET" in all of its requests.
  3. If an IPv4 address could be acquired by running a DHCPv4 client on the interface, it is considered external. The DHCPv4 client MUST have included a DHCP user class consisting of the ASCII string "HOMENET" in all of its requests.
  4. The interface is considered internal.
  1. インターフェイスに固定のカテゴリーが設定されている場合は、それを使用します。
  2. DHCPv6クライアントを実行して委任されたプレフィックスを取得できた場合は、外部とみなします。DHCPv6クライアントは、すべてのリクエストに、ASCII文字列"HOMENET"からなるDHCPv6ユーザークラスを含めている必要があります（MUST）。
  3. インターフェイス上でDHCPv4クライアントを実行してIPv4アドレスを取得できた場合は、外部とみなします。DHCPv4クライアントは、すべてのリクエストに、ASCII文字列"HOMENET"からなるDHCPユーザークラスを含めている必要があります（MUST）。
  4. インターフェイスは内部とみなします。

Note that as other HNCP nodes will ignore the client due to the User Class option, any server that replies is clearly external (or a malicious internal node).

他のHNCPノードはUser Classオプションによりクライアントを無視するため、応答するサーバーは明らかに外部のもの（または悪意のある内部ノード）であることに注意してください。

An HNCP router SHOULD allow setting the fixed category for each interface that may be connected to either an internal or external device (e.g., an Ethernet port that can be connected to a modem, another HNCP router, or a client). Note that all fixed categories except internal and external cannot be auto-detected and can only be selected using manual configuration.

HNCPルーターは、内部と外部のどちらの機器にも接続される可能性のある各インターフェイス（たとえば、モデム、別のHNCPルーター、またはクライアントに接続できるイーサネットポート）について、固定のカテゴリーを設定できるようにすべきです（SHOULD）。内部と外部以外のすべての固定カテゴリーは自動検出できず、手動設定によってのみ選択できることに注意してください。

An HNCP router using auto-detection on an interface MUST run the appropriately configured DHCP clients as long as the interface without a fixed category is active (including states where auto-detection considers it to be internal) and rerun the algorithm above to react to conditions resulting in a different interface category. The router SHOULD wait for a reasonable time period (5 seconds as a default), during which the DHCP clients can acquire a lease, before treating a newly activated or previously external interface as internal.

インターフェイスで自動検出を使用するHNCPルーターは、固定のカテゴリーを持たないそのインターフェイスがアクティブである限り（自動検出がそのインターフェイスを内部とみなしている状態も含む）、適切に設定されたDHCPクライアントを実行し、異なるインターフェイスカテゴリーとなる状況に対応するために上記のアルゴリズムを再実行しなければなりません（MUST）。新しくアクティブになったインターフェイスや以前は外部だったインターフェイスを内部として扱う前に、ルーターは、DHCPクライアントがリースを取得できる妥当な期間（デフォルトは5秒）待機すべきです（SHOULD）。

6. Autonomous Address Configuration

6. 自律的なアドレス設定

This section specifies how HNCP nodes configure host and node addresses. At first, border routers share information obtained from service providers or local configuration by publishing one or more External-Connection TLVs (Section 10.2). These contain other TLVs such as Delegated-Prefix TLVs (Section 10.2.1) that are then used for prefix assignment. Finally, HNCP nodes obtain addresses either statelessly or using a specific stateful mechanism (Section 6.4). Hosts and non-HNCP routers are configured using SLAAC, DHCP, or DHCPv6-PD.

このセクションでは、HNCPノードがホストとノードのアドレスをどのように設定するかを規定します。まず、境界ルーターは、1つ以上のExternal-Connection TLV（セクション10.2）を公開することで、サービスプロバイダーまたはローカル設定から得た情報を共有します。これらには、Delegated-Prefix TLV（セクション10.2.1）などの他のTLVが含まれており、それらがプレフィックス割り当てに使用されます。最後に、HNCPノードは、ステートレスに、または特定のステートフルなメカニズム（セクション6.4）を使用してアドレスを取得します。ホストと非HNCPルーターは、SLAAC、DHCP、またはDHCPv6-PDを使用して設定されます。

6.1. Common Link

6.1. 共通リンク

HNCP uses the concept of Common Link both in autonomic address configuration and naming and service discovery (Section 8). A Common Link refers to the set of interfaces of nodes that see each other's traffic and presumably also the traffic of all hosts that may use the nodes to, e.g., forward traffic. Common Links are used, e.g., to determine where prefixes should be assigned or which peers participate in the election of a DHCP server. The Common Link is computed separately for each local internal interface, and it always contains the local interface. Additionally, if the local interface is not set to the Ad Hoc category (see Section 5.1), it also contains the set of interfaces that are bidirectionally reachable from the given local interface; that is, every remote interface of a remote node meeting all of the following requirements:

HNCPは、自律的なアドレス設定と、名前付けおよびサービス発見（セクション8）の両方で、共通リンクの概念を使用します。共通リンクとは、互いのトラフィックを見ることができ、さらにおそらく、たとえばトラフィックの転送のためにそれらのノードを使用する可能性のあるすべてのホストのトラフィックも見ることができるノードの、インターフェイスの集合を指します。共通リンクは、たとえば、どこにプレフィックスを割り当てるべきか、どのピアがDHCPサーバーの選出に参加するかを決定するために使用されます。共通リンクはローカルの内部インターフェイスごとに個別に計算され、常にそのローカルインターフェイスを含みます。さらに、ローカルインターフェイスがAd Hocカテゴリー（セクション5.1を参照）に設定されていない場合、共通リンクには、そのローカルインターフェイスから双方向に到達可能なインターフェイスの集合も含まれます。すなわち、次のすべての要件を満たすリモートノードの各リモートインターフェイスです：

  • The local node publishes a Peer TLV with:

    • Peer Node Identifier = remote node's node identifier
    • Peer Endpoint Identifier = remote interface's endpoint identifier
    • Endpoint Identifier = local interface's endpoint identifier

  • The remote node publishes a Peer TLV with:

    • Peer Node Identifier = local node's node identifier
    • Peer Endpoint Identifier = local interface's endpoint identifier
    • Endpoint Identifier = remote interface's endpoint identifier

  • ローカルノードが、次の内容を持つPeer TLVを公開している：

    • Peer Node Identifier = リモートノードのノード識別子
    • Peer Endpoint Identifier = リモートインターフェイスのエンドポイント識別子
    • Endpoint Identifier = ローカルインターフェイスのエンドポイント識別子

  • リモートノードが、次の内容を持つPeer TLVを公開している：

    • Peer Node Identifier = ローカルノードのノード識別子
    • Peer Endpoint Identifier = ローカルインターフェイスのエンドポイント識別子
    • Endpoint Identifier = リモートインターフェイスのエンドポイント識別子

A node MUST be able to detect whether two of its local internal interfaces are connected, e.g., by detecting an identical remote interface being part of the Common Links of both local interfaces.

ノードは、たとえば同一のリモートインターフェイスが両方のローカルインターフェイスの共通リンクに含まれていることを検出するなどして、自身のローカルの内部インターフェイスのうち2つが接続されているかどうかを検出できる必要があります（MUST）。

6.2. External Connections

6.2. 外部接続

Each HNCP router MAY obtain external connection information such as address prefixes, DNS server addresses, and DNS search paths from one or more sources, e.g., DHCPv6-PD [RFC3633], NETCONF [RFC6241], or static configuration. Each individual external connection to be shared in the network is represented by one External-Connection TLV (Section 10.2).

各HNCPルーターは、アドレスプレフィックス、DNSサーバーのアドレス、DNS検索パスなどの外部接続情報を、たとえばDHCPv6-PD[RFC3633]、NETCONF[RFC6241]、静的設定などの1つ以上の情報源から取得してもよいです（MAY）。ネットワーク内で共有される個々の外部接続は、それぞれ1つのExternal-Connection TLV（セクション10.2）で表されます。

Announcements of individual external connections can consist of the following components:

個々の外部接続の告知は、次の構成要素からなります：

Delegated Prefixes:
Address space available for assignment to internal links announced using Delegated-Prefix TLVs (Section 10.2.1). Some address spaces might have special properties that are necessary to understand in order to handle them (e.g., information similar to [RFC6603]). This information is encoded using DHCPv6-Data TLVs (Section 10.2.2) inside the respective Delegated-Prefix TLVs.
Auxiliary Information:
Information about services such as DNS or time synchronization regularly used by hosts in addition to addressing and routing information. This information is encoded using DHCPv6-Data TLVs (Section 10.2.2) and DHCPv4-Data TLVs (Section 10.2.3).
委任されたプレフィックス：
内部リンクへの割り当てに利用可能なアドレス空間で、Delegated-Prefix TLV（セクション10.2.1）を使用して告知されます。アドレス空間によっては、扱うために理解しておく必要のある特別な性質（たとえば、[RFC6603]と同様の情報）を持つ場合があります。この情報は、それぞれのDelegated-Prefix TLVの内部のDHCPv6-Data TLV（セクション10.2.2）を使用してエンコードされます。
補助情報：
アドレス指定やルーティングの情報に加えてホストが通常使用する、DNSや時刻同期などのサービスに関する情報。この情報は、DHCPv6-Data TLV（セクション10.2.2）とDHCPv4-Data TLV（セクション10.2.3）を使用してエンコードされます。

Whenever information about reserved parts (e.g., as specified in [RFC6603]) is received for a delegated prefix, the reserved parts MUST be advertised using Assigned-Prefix TLVs (Section 10.3) with the greatest priority (i.e., 15), as if they were assigned to a Private Link.

委任されたプレフィックスについて予約部分に関する情報（たとえば、[RFC6603]で規定されているもの）を受信した場合は常に、その予約部分を、プライベートリンクに割り当てられているかのように、最大の優先度（すなわち15）でAssigned-Prefix TLV（セクション10.3）を使用して広告しなければなりません（MUST）。

Some connections or delegated prefixes may have a special meaning and are not regularly used for internal or Internet connectivity; instead, they may provide access to special services like VPNs, sensor networks, Voice over IP (VoIP), IPTV, etc. Care must be taken that these prefixes are properly integrated and dealt with in the network, in order to avoid breaking connectivity for devices who are not aware of their special characteristics or to only selectively allow certain devices to use them. Such prefixes are distinguished using Prefix-Policy TLVs (Section 10.2.1.1). Their contents MAY be partly opaque to HNCP nodes, and their identification and usage depends on local policy. However, the following general rules MUST be adhered to:

一部の接続や委任されたプレフィックスは特別な意味を持ち、内部やインターネットへの接続には通常使用されない場合があります。その代わりに、VPN、センサーネットワーク、Voice over IP（VoIP）、IPTVなどの特別なサービスへのアクセスを提供する場合があります。それらの特別な特性を認識していない機器の接続性を壊さないように、あるいは特定の機器にのみ選択的にそれらの使用を許可するために、これらのプレフィックスがネットワーク内で適切に統合され、扱われるように注意する必要があります。このようなプレフィックスは、Prefix-Policy TLV（セクション10.2.1.1）を使用して区別されます。その内容は、HNCPノードにとって部分的に不透明であってもよいです（MAY）。また、その識別と使用方法はローカルポリシーに依存します。ただし、次の一般的な規則には従わなければなりません（MUST）：

  • Special rules apply when making address assignments for prefixes with Prefix-Policy TLVs with type 131, as described in Section 6.3.2.
  • In the presence of any type 1 to 128 Prefix-Policy TLV, the prefix is specialized to reach destinations denoted by any such Prefix-Policy TLV, i.e., in absence of a type 0 Prefix-Policy TLV, it is not usable for general Internet connectivity. An HNCP router MAY enforce this restriction with appropriate packet filter rules.
  • セクション6.3.2で説明するように、タイプ131のPrefix-Policy TLVを持つプレフィックスについてアドレス割り当てを行う場合には、特別な規則が適用されます。
  • タイプ1から128のいずれかのPrefix-Policy TLVが存在する場合、そのプレフィックスは、そのようなPrefix-Policy TLVが示す宛先に到達するための特別なものになります。すなわち、タイプ0のPrefix-Policy TLVがない場合、そのプレフィックスは一般的なインターネット接続には使用できません。HNCPルーターは、適切なパケットフィルター規則によってこの制限を強制してもよいです（MAY）。

6.3. Prefix Assignment

6.3. プレフィックス割り当て

HNCP uses the prefix assignment algorithm [RFC7695] in order to assign prefixes to HNCP internal links and uses some of the terminology (Section 2) defined there. HNCP furthermore defines the Assigned-Prefix TLV (Section 10.3), which MUST be used to announce Published Assigned Prefixes.

HNCPは、HNCPの内部リンクにプレフィックスを割り当てるためにプレフィックス割り当てアルゴリズム[RFC7695]を使用し、そこで定義されている用語の一部（セクション2）を使用します。さらにHNCPは、Assigned-Prefix TLV（セクション10.3）を定義します。公開済み割り当て済みプレフィックスを告知するには、このTLVを使用しなければなりません（MUST）。

6.3.1. Prefix Assignment Algorithm Parameters

6.3.1. プレフィックス割り当てアルゴリズムのパラメーター

All HNCP nodes running the prefix assignment algorithm use the following values for its parameters:

プレフィックス割り当てアルゴリズムを実行するすべてのHNCPノードは、そのパラメーターに次の値を使用します：

Node IDs:
HNCP node identifiers are used. The comparison operation is defined as bitwise comparison.
Set of Delegated Prefixes:
The set of prefixes encoded in Delegated-Prefix TLVs that are not strictly included in prefixes encoded in other Delegated-Prefix TLVs. Note that Delegated-Prefix TLVs included in ignored External-Connection TLVs are not considered. It is dynamically updated as Delegated-Prefix TLVs are added or removed.
Set of Shared Links:
The set of Common Links associated with interfaces with the Internal, Leaf, Guest, or Ad Hoc category. It is dynamically updated as interfaces are added, removed, or switched from one category to another. When multiple interfaces are detected as belonging to the same Common Link, prefix assignment is disabled on all of these interfaces except one.
Set of Private Links:
This document defines Private Links as representing DHCPv6-PD clients or as a mean to advertise prefixes included in the DHCPv6 Exclude Prefix option. Other implementation-specific Private Links may be defined whenever a prefix needs to be assigned for a purpose that does not require a consensus with other HNCP nodes.
Set of Advertised Prefixes:

The set of prefixes included in Assigned-Prefix TLVs advertised by other HNCP nodes (prefixes advertised by the local node are not in this set). The associated Advertised Prefix Priority is the priority specified in the TLV. The associated Shared Link is determined as follows:

  • If the Link Identifier is 0, the Advertised Prefix is not assigned on a Shared Link.
  • If the other node's interface identified by the Link Identifier is included in one of the Common Links used for prefix assignment, it is considered as assigned on the given Common Link.
  • Otherwise, the Advertised Prefix is not assigned on a Shared Link.

Advertised Prefixes as well as their associated priorities and associated Shared Links MUST be updated as Assigned-Prefix TLVs are added, updated, or removed, and as Common Links are modified.

ADOPT_MAX_DELAY:
The default value is 0 seconds (i.e., prefix adoption is done instantly).
BACKOFF_MAX_DELAY:
The default value is 4 seconds.
RANDOM_SET_SIZE:
The default value is 64.
Flooding Delay:
The default value is 5 seconds.
Default Advertised Prefix Priority:
When a new assignment is created or an assignment is adopted -- as specified in the prefix assignment algorithm routine -- the default Advertised Prefix Priority to be used is 2.
ノードID：
HNCPのノード識別子を使用します。比較演算はビット単位の比較として定義されます。
委任済みプレフィックスの集合：
Delegated-Prefix TLVにエンコードされたプレフィックスのうち、他のDelegated-Prefix TLVにエンコードされたプレフィックスに真に含まれないものの集合。無視されたExternal-Connection TLVに含まれるDelegated-Prefix TLVは考慮されないことに注意してください。この集合は、Delegated-Prefix TLVが追加または削除されるのに応じて動的に更新されます。
共有リンクの集合：
Internal、Leaf、Guest、またはAd Hocカテゴリーのインターフェイスに関連付けられた共通リンクの集合。この集合は、インターフェイスが追加、削除、またはあるカテゴリーから別のカテゴリーに切り替えられるのに応じて動的に更新されます。複数のインターフェイスが同じ共通リンクに属していると検出された場合、それらのインターフェイスのうち1つを除くすべてでプレフィックス割り当てが無効になります。
プライベートリンクの集合：
この文書では、プライベートリンクを、DHCPv6-PDクライアントを表すもの、またはDHCPv6 Exclude Prefixオプションに含まれるプレフィックスを広告するための手段として定義します。他のHNCPノードとのコンセンサスを必要としない目的でプレフィックスを割り当てる必要がある場合には、その他の実装固有のプライベートリンクを定義してもかまいません。
広告済みプレフィックスの集合：

他のHNCPノードが広告したAssigned-Prefix TLVに含まれるプレフィックスの集合（ローカルノードが広告したプレフィックスはこの集合に含まれません）。関連付けられる広告済みプレフィックスの優先度は、TLVで指定された優先度です。関連付けられる共有リンクは、次のように決定されます：

  • Link Identifierが0の場合、その広告済みプレフィックスは共有リンク上には割り当てられていません。
  • Link Identifierで識別される他のノードのインターフェイスが、プレフィックス割り当てに使用される共通リンクのいずれかに含まれている場合、そのプレフィックスはその共通リンク上に割り当てられているとみなされます。
  • それ以外の場合、その広告済みプレフィックスは共有リンク上には割り当てられていません。

広告済みプレフィックス、およびそれに関連付けられた優先度と共有リンクは、Assigned-Prefix TLVが追加、更新、または削除されるのに応じて、また共通リンクが変更されるのに応じて更新しなければなりません（MUST）。

ADOPT_MAX_DELAY：
デフォルト値は0秒です（すなわち、プレフィックスの引き継ぎは即座に行われます）。
BACKOFF_MAX_DELAY：
デフォルト値は4秒です。
RANDOM_SET_SIZE：
デフォルト値は64です。
フラッディング遅延：
デフォルト値は5秒です。
デフォルトの広告済みプレフィックスの優先度：
プレフィックス割り当てアルゴリズムのルーチンで規定されているとおりに新しい割り当てが作成されるとき、または割り当てが引き継がれるときに使用する、デフォルトの広告済みプレフィックスの優先度は2です。

6.3.2. Making New Assignments

6.3.2. 新しい割り当ての作成

Whenever the prefix assignment algorithm subroutine (Section 4.1 of [RFC7695]) is run on a Common Link, and whenever a new prefix may be assigned (case 1 of the subroutine: no Best Assignment and no Current Assignment), the decision of whether the assignment of a new prefix is desired MUST follow these rules in order:

プレフィックス割り当てアルゴリズムのサブルーチン（[RFC7695]のセクション4.1）が共通リンク上で実行され、かつ新しいプレフィックスが割り当てられうる場合（サブルーチンのケース1：Best AssignmentもCurrent Assignmentもない場合）は常に、新しいプレフィックスの割り当てが望ましいかどうかの判断は、次の規則に順番に従わなければなりません（MUST）：

  • If the Delegated-Prefix TLV contains a DHCPv6-Data TLV, and the meaning of one of the DHCP options is not understood by the HNCP node, the creation of a new prefix is not desired. This rule applies to TLVs inside Delegated-Prefix TLVs but not to those inside External-Connection TLVs.
  • If the remaining preferred lifetime of the prefix is 0 and there is another delegated prefix of the same IP version used for prefix assignment with a non-zero preferred lifetime, the creation of a new prefix is not desired.
  • If the Delegated-Prefix TLV does not include a Prefix-Policy TLV indicating restrictive assignment (type 131) or if local policy exists to identify it based on, e.g., other Prefix-Policy TLV values and allows assignment, the creation of a new prefix is desired.
  • Otherwise, the creation of a new prefix is not desired.
  • Delegated-Prefix TLVがDHCPv6-Data TLVを含み、かつDHCPオプションのいずれかの意味をHNCPノードが理解できない場合、新しいプレフィックスの作成は望ましくありません。この規則は、Delegated-Prefix TLVの内部のTLVには適用されますが、External-Connection TLVの内部のTLVには適用されません。
  • プレフィックスの残りの推奨期間が0であり、かつプレフィックス割り当てに使用される同じIPバージョンの委任されたプレフィックスで、推奨期間が0でないものが他に存在する場合、新しいプレフィックスの作成は望ましくありません。
  • Delegated-Prefix TLVが制限的な割り当て（タイプ131）を示すPrefix-Policy TLVを含まない場合、またはたとえば他のPrefix-Policy TLVの値に基づいてそれを識別して割り当てを許可するローカルポリシーが存在する場合、新しいプレフィックスの作成は望ましいです。
  • それ以外の場合、新しいプレフィックスの作成は望ましくありません。

If the considered delegated prefix is an IPv6 prefix, and whenever there is at least one available prefix of length 64, a prefix of length 64 MUST be selected unless configured otherwise. In case no prefix of length 64 would be available, a longer prefix MAY be selected even without configuration.

対象の委任されたプレフィックスがIPv6プレフィックスであり、かつ長さ64の利用可能なプレフィックスが少なくとも1つある場合は常に、別途設定されていない限り、長さ64のプレフィックスを選択しなければなりません（MUST）。長さ64のプレフィックスが利用できない場合は、設定がなくても、より長いプレフィックスを選択してもよいです（MAY）。

If the considered delegated prefix is an IPv4 prefix (Section 6.5 details how IPv4-delegated prefixes are generated), a prefix of length 24 SHOULD be preferred.

対象の委任されたプレフィックスがIPv4プレフィックスである場合（IPv4の委任されたプレフィックスの生成方法についてはセクション6.5で詳しく説明します）、長さ24のプレフィックスを優先すべきです（SHOULD）。

In any case, an HNCP router making an assignment MUST support a mechanism suitable to distribute addresses from the considered prefix if the link is intended to be used by clients. In this case, a router assigning an IPv4 prefix MUST announce the L-capability, and a router assigning an IPv6 prefix with a length greater than 64 MUST announce the H-capability as defined in Section 4.

いずれの場合も、割り当てを行うHNCPルーターは、リンクがクライアントによって使用されることを意図している場合、対象のプレフィックスからアドレスを配布するのに適したメカニズムをサポートしなければなりません（MUST）。この場合、IPv4プレフィックスを割り当てるルーターはL-capabilityを告知しなければなりません（MUST）。また、長さが64より大きいIPv6プレフィックスを割り当てるルーターは、セクション4で定義されているH-capabilityを告知しなければなりません（MUST）。

6.3.3. Applying Assignments

6.3.3. 割り当ての適用

The prefix assignment algorithm indicates when a prefix is applied to the respective Common Link. When that happens, each router connected to said link:

プレフィックス割り当てアルゴリズムは、プレフィックスがそれぞれの共通リンクに適用されるタイミングを示します。それが起きたとき、そのリンクに接続されている各ルーターは、次のようにします：

  • MUST forward traffic destined to said prefix to the respective link.
  • MUST participate in the client configuration election as described in Section 7, if the link is intended to be used by clients.
  • MAY add an address from said prefix to the respective network interface as described in Section 6.4, e.g., if it is to be used as source for locally originating traffic.
  • そのプレフィックス宛てのトラフィックを、それぞれのリンクに転送しなければなりません（MUST）。
  • リンクがクライアントによって使用されることを意図している場合、セクション7で説明するクライアント設定のための選出に参加しなければなりません（MUST）。
  • たとえば、ローカルで発信するトラフィックの送信元として使用する場合などに、セクション6.4で説明するように、そのプレフィックスからのアドレスをそれぞれのネットワークインターフェイスに追加してもよいです（MAY）。

6.3.4. DHCPv6 Prefix Delegation

6.3.4. DHCPv6プレフィックス委任

When an HNCP router announcing the P-Capability (Section 4) receives a DHCPv6-PD request from a client, it SHOULD assign one prefix per delegated prefix in the network. This set of assigned prefixes is then delegated to the client, after it has been applied as described in the prefix assignment algorithm. Each DHCPv6-PD client MUST be considered as an independent Private Link, and delegation MUST be based on the same set of delegated prefixes as the one used for Common Link prefix assignments; however, the prefix length to be delegated MAY be smaller than 64.

P-Capability（セクション4）を告知しているHNCPルーターは、クライアントからDHCPv6-PDリクエストを受信したとき、ネットワーク内の委任されたプレフィックスごとに1つのプレフィックスを割り当てるべきです（SHOULD）。この割り当てられたプレフィックスの集合は、プレフィックス割り当てアルゴリズムで説明されているとおりに適用された後、クライアントに委任されます。各DHCPv6-PDクライアントは、独立したプライベートリンクとみなさなければなりません（MUST）。また、委任は、共通リンクのプレフィックス割り当てに使用されるものと同じ委任されたプレフィックスの集合に基づく必要があります（MUST）。ただし、委任するプレフィックスの長さは64より小さくてもよいです（MAY）。

The assigned prefixes MUST NOT be given to DHCPv6-PD clients before they are applied and MUST be withdrawn whenever they are destroyed. As an exception to this rule, in order to shorten delays of processed requests, a router MAY prematurely give out a prefix that is advertised but not yet applied if it does so with a valid lifetime of not more than 30 seconds and ensures removal or correction of lifetimes as soon as possible.

割り当てられたプレフィックスは、適用される前にDHCPv6-PDクライアントに与えてはなりません（MUST NOT）。また、それらが破棄されたときは常に撤回しなければなりません（MUST）。この規則の例外として、処理されたリクエストの遅延を短縮するために、ルーターは、広告済みだがまだ適用されていないプレフィックスを、30秒以下の有効期間で与え、かつできるだけ早く削除または有効期間の修正を確実に行うのであれば、早めに与えてもよいです（MAY）。

6.4. Node Address Assignment

6.4. ノードアドレスの割り当て

This section specifies how HNCP nodes reserve addresses for their own use. Nodes MAY, at any time, try to reserve a new address from any Applied Assigned Prefix. Each HNCP node SHOULD announce an IPv6 address and -- if it supports IPv4 -- MUST announce an IPv4 address, whenever matching prefixes are assigned to at least one of its Common Links. These addresses are published using Node-Address TLVs and used to locally reach HNCP nodes for other services. Nodes SHOULD NOT create and announce more than one assignment per IP version to avoid cluttering the node data with redundant information unless a special use case requires it.

このセクションでは、HNCPノードが自身で使用するアドレスをどのように予約するかを規定します。ノードは、いつでも、任意の適用済み割り当て済みプレフィックスから新しいアドレスの予約を試みてもよいです（MAY）。一致するプレフィックスが自身の共通リンクの少なくとも1つに割り当てられている場合は常に、各HNCPノードはIPv6アドレスを告知すべきです（SHOULD）。また、IPv4をサポートしている場合は、IPv4アドレスを告知しなければなりません（MUST）。これらのアドレスはNode-Address TLVを使用して公開され、他のサービスのためにHNCPノードにローカルに到達するために使用されます。特別なユースケースで必要な場合を除き、冗長な情報でノードデータが散らかるのを避けるために、ノードはIPバージョンごとに2つ以上の割り当てを作成して告知すべきではありません（SHOULD NOT）。

Stateless assignment based on Semantically Opaque Interface Identifiers [RFC7217] SHOULD be used for address assignment whenever possible (e.g., the prefix length is 64), otherwise (e.g., for IPv4 if supported) the following method MUST be used instead: For any assigned prefix for which stateless assignment is not used, the first quarter of the addresses are reserved for HNCP-based address assignments, whereas the last three quarters are left to the DHCP elected router (Section 4 specifies the DHCP server election process). For example, if the prefix 192.0.2.0/24 is assigned and applied to a Common Link, addresses included in 192.0.2.0/26 are reserved for HNCP nodes, and the remaining addresses are reserved for the elected DHCPv4 server.

可能な場合（たとえば、プレフィックス長が64の場合）は常に、アドレス割り当てには、意味的に不透明なインターフェイス識別子（Semantically Opaque Interface Identifiers）[RFC7217]に基づくステートレスな割り当てを使用すべきです（SHOULD）。そうでない場合（たとえば、サポートされている場合のIPv4）は、代わりに次の方法を使用しなければなりません（MUST）：ステートレスな割り当てを使用しない割り当て済みプレフィックスについては、アドレスの最初の4分の1をHNCPベースのアドレス割り当てのために予約し、残りの4分の3をDHCPのために選出されたルーターに任せます（DHCPサーバーの選出プロセスについてはセクション4で規定します）。たとえば、プレフィックス192.0.2.0/24が割り当てられて共通リンクに適用された場合、192.0.2.0/26に含まれるアドレスはHNCPノードのために予約され、残りのアドレスは選出されたDHCPv4サーバーのために予約されます。

HNCP nodes assign addresses to themselves and then (to ensure eventual lack of conflicting assignments) publish the assignments using the Node-Address TLV (Section 10.4).

HNCPノードは、自身にアドレスを割り当て、その後（最終的に割り当ての競合がなくなることを保証するために）Node-Address TLV（セクション10.4）を使用してその割り当てを公開します。

The process of obtaining addresses is specified as follows:

アドレスを取得する処理は、次のように規定されます：

  • A node MUST NOT start advertising an address if it is already advertised by another node.
  • An assigned address MUST be part of an assigned prefix currently applied on a Common Link that includes the interface specified by the endpoint identifier.
  • An address MUST NOT be used unless it has been advertised for at least ADDRESS_APPLY_DELAY consecutive seconds and is still currently being advertised. The default value for ADDRESS_APPLY_DELAY is 3 seconds.
  • Whenever the same address is advertised by more than one node, all but the one advertised by the node with the greatest node identifier MUST be removed.
  • ノードは、すでに他のノードが広告しているアドレスの広告を開始してはなりません（MUST NOT）。
  • 割り当てるアドレスは、エンドポイント識別子で指定されたインターフェイスを含む共通リンクに現在適用されている割り当て済みプレフィックスの一部である必要があります（MUST）。
  • アドレスは、少なくともADDRESS_APPLY_DELAY秒の間連続して広告され、かつ現在も広告されている場合でなければ、使用してはなりません（MUST NOT）。ADDRESS_APPLY_DELAYのデフォルト値は3秒です。
  • 同じアドレスが複数のノードによって広告されている場合は常に、最大のノード識別子を持つノードが広告しているものを除き、すべて削除しなければなりません（MUST）。

6.5. Local IPv4 and ULA Prefixes

6.5. ローカルIPv4プレフィックスとULAプレフィックス

HNCP routers can create a Unique Local Address (ULA) or private IPv4 prefix to enable connectivity between local devices. These prefixes are inserted in HNCP as if they were delegated prefixes of a (virtual) external connection (Section 6.2). The following rules apply:

HNCPルーターは、ローカルの機器間の接続性を実現するために、ユニークローカルアドレス（ULA）プレフィックスまたはプライベートIPv4プレフィックスを作成できます。これらのプレフィックスは、（仮想的な）外部接続（セクション6.2）の委任されたプレフィックスであるかのようにHNCPに挿入されます。次の規則が適用されます：

  • An HNCP router SHOULD create a ULA prefix if there is no other IPv6 prefix with a preferred time greater than 0 in the network. It MAY also do so if there are other delegated IPv6 prefixes, but none of which is locally generated (i.e., without any Prefix-Policy TLV) and has a preferred time greater than 0. However, it MUST NOT do so otherwise. In case multiple locally generated ULA prefixes are present, only the one published by the node with the greatest node identifier is kept among those with a preferred time greater than 0 -- if there is any.
  • An HNCP router MUST create a private IPv4 prefix [RFC1918] whenever it wishes to provide IPv4 Internet connectivity to the network and no other private IPv4 prefix with Internet connectivity currently exists. It MAY also enable local IPv4 connectivity by creating a private IPv4 prefix if no IPv4 prefix exists but MUST NOT do so otherwise. In case multiple IPv4 prefixes are announced, only the one published by the node with the greatest node identifier is kept among those with a Prefix-Policy TLV of type 0 -- if there is any. The router publishing a prefix with Internet connectivity MUST forward IPv4 traffic to the Internet and perform NAT on behalf of the network as long as it publishes the prefix; other routers in the network MAY choose not to.
  • ネットワーク内に推奨期間が0より大きい他のIPv6プレフィックスが存在しない場合、HNCPルーターはULAプレフィックスを作成すべきです（SHOULD）。他に委任されたIPv6プレフィックスが存在しても、そのいずれもローカルで生成されたもの（すなわち、Prefix-Policy TLVを持たないもの）でありかつ推奨期間が0より大きいものでない場合にも、ULAプレフィックスを作成してもよいです（MAY）。ただし、それ以外の場合には作成してはなりません（MUST NOT）。ローカルで生成された複数のULAプレフィックスが存在する場合、推奨期間が0より大きいもの（存在する場合）のうち、最大のノード識別子を持つノードが公開したものだけが維持されます。
  • HNCPルーターは、ネットワークにIPv4のインターネット接続性を提供したい場合で、かつインターネット接続性を持つ他のプライベートIPv4プレフィックスが現在存在しない場合は常に、プライベートIPv4プレフィックス[RFC1918]を作成しなければなりません（MUST）。IPv4プレフィックスが存在しない場合には、プライベートIPv4プレフィックスを作成することでローカルのIPv4接続性を実現してもよいです（MAY）。ただし、それ以外の場合にはそうしてはなりません（MUST NOT）。複数のIPv4プレフィックスが告知されている場合、タイプ0のPrefix-Policy TLVを持つもの（存在する場合）のうち、最大のノード識別子を持つノードが公開したものだけが維持されます。インターネット接続性を持つプレフィックスを公開するルーターは、そのプレフィックスを公開している間、IPv4トラフィックをインターネットに転送し、ネットワークに代わってNATを実行しなければなりません（MUST）。ネットワーク内の他のルーターは、そうしないことを選択してもよいです（MAY）。

Creation of such ULA and IPv4 prefixes MUST be delayed by a random time span between 0 and 10 seconds in which the router MUST scan for others trying to do the same.

このようなULAプレフィックスおよびIPv4プレフィックスの作成は、0から10秒の間のランダムな時間だけ遅延させなければなりません（MUST）。その間、ルーターは同じことを試みている他のルーターを探索しなければなりません（MUST）。

When a new ULA prefix is created, the prefix is selected based on the configuration, using the last non-deprecated ULA prefix, or generated based on [RFC4193].

新しいULAプレフィックスを作成するとき、そのプレフィックスは、設定に基づいて選択するか、最後に使用していた非推奨になっていないULAプレフィックスを使用するか、[RFC4193]に基づいて生成します。

7. Configuration of Hosts and Non-HNCP Routers

7. ホストと非HNCPルーターの設定

HNCP routers need to ensure that hosts and non-HNCP downstream routers on internal links are configured with addresses and routes. Since DHCP clients can usually only bind to one server at a time, a per-link and per-service election takes place.

HNCPルーターは、内部リンク上のホストと下流の非HNCPルーターに、アドレスと経路が設定されるようにする必要があります。DHCPクライアントは通常、一度に1つのサーバーにしかバインドできないため、リンクごと、サービスごとに選出が行われます。

HNCP routers may have different capabilities for configuring downstream devices and providing naming services. Each router MUST therefore indicate its capabilities as specified in Section 4 in order to participate as a candidate in the election.

HNCPルーターは、下流の機器の設定や名前付けサービスの提供について、異なる能力を持つ場合があります。したがって、各ルーターは、選出に候補として参加するために、セクション4で規定するとおりに自身の能力を示さなければなりません（MUST）。

7.1. IPv6 Addressing and Configuration

7.1. IPv6のアドレス指定と設定

In general, Stateless Address Autoconfiguration [RFC4861] is used for client configuration for its low overhead and fast renumbering capabilities. Therefore, each HNCP router sends Router Advertisements on interfaces that are intended to be used by clients and MUST at least include a Prefix Information Option for each Applied Assigned Prefix that it assigned to the respective link in every such advertisement. However, stateful DHCPv6 can be used in addition by administrative choice to, e.g., collect hostnames and use them to provide naming services or whenever stateless configuration is not applicable.

一般に、クライアントの設定には、オーバーヘッドが小さく迅速なリナンバリングが可能であることから、ステートレスアドレス自動設定[RFC4861]が使用されます。したがって、各HNCPルーターは、クライアントによって使用されることを意図したインターフェイス上でルーター広告を送信し、そのようなすべての広告に、少なくとも、それぞれのリンクに自身が割り当てた各適用済み割り当て済みプレフィックスについてのPrefix Informationオプションを含めなければなりません（MUST）。ただし、管理上の選択により、たとえばホスト名を収集してそれを名前付けサービスの提供に使用するために、あるいはステートレスな設定が適用できない場合には常に、ステートフルなDHCPv6を追加で使用できます。

The designated stateful DHCPv6 server for a Common Link (Section 6.1) is elected based on the capabilities described in Section 4. The winner is the router (connected to the Common Link) advertising the greatest H-capability. In case of a tie, Capability Values (Section 4) are compared, and the router with the greatest value is elected. In case of another tie, the router with the greatest node identifier is elected among the routers with tied Capability Values.

共通リンク（セクション6.1）の指定ステートフルDHCPv6サーバーは、セクション4で説明する能力に基づいて選出されます。（共通リンクに接続されているルーターのうち）最大のH-capabilityを広告しているルーターが選ばれます。同点の場合は、能力値（セクション4）を比較し、最大の値を持つルーターが選出されます。さらに同点の場合は、能力値が同じルーターのうち、最大のノード識別子を持つルーターが選出されます。

The elected router MUST serve stateful DHCPv6 and SHOULD provide naming services for acquired hostnames as outlined in Section 8; all other nodes MUST NOT. Stateful addresses SHOULD be assigned in a way that does not hinder fast renumbering even if the DHCPv6 server or client do not support the DHCPv6 reconfigure mechanism, e.g., by only handing out leases from locally generated (ULA) prefixes and prefixes with a length different from 64 and by using low renew and rebind times (i.e., not longer than 5 minutes). In case no router was elected, stateful DHCPv6 is not provided. Routers that cease to be elected DHCP servers SHOULD -- when applicable -- invalidate remaining existing bindings in order to trigger client reconfiguration.

選出されたルーターは、ステートフルなDHCPv6を提供しなければなりません（MUST）。また、セクション8で概説するように、取得したホスト名の名前付けサービスを提供すべきです（SHOULD）。他のすべてのノードは、これらを行ってはなりません（MUST NOT）。ステートフルなアドレスは、DHCPv6サーバーまたはクライアントがDHCPv6の再設定メカニズムをサポートしていない場合でも迅速なリナンバリングを妨げない方法で割り当てるべきです（SHOULD）。たとえば、ローカルで生成された（ULA）プレフィックスと長さが64以外のプレフィックスからのみリースを払い出し、短い更新時間と再バインド時間（すなわち、5分以下）を使用するなどの方法です。ルーターが選出されなかった場合、ステートフルなDHCPv6は提供されません。選出されたDHCPサーバーでなくなったルーターは、該当する場合、クライアントの再設定を促すために、残っている既存のバインディングを無効化すべきです（SHOULD）。

7.2. DHCPv6 for Prefix Delegation

7.2. プレフィックス委任のためのDHCPv6

The designated DHCPv6 server for prefix delegation on a Common Link is elected based on the capabilities described in Section 4. The winner is the router (connected to the Common Link) advertising the greatest P-capability. In case of a tie, Capability Values (Section 4) are compared, and the router with the greatest value is elected. In case of another tie, the router with the greatest node identifier is elected among the routers with tied Capability Values.

共通リンク上のプレフィックス委任のための指定DHCPv6サーバーは、セクション4で説明する能力に基づいて選出されます。（共通リンクに接続されているルーターのうち）最大のP-capabilityを広告しているルーターが選ばれます。同点の場合は、能力値（セクション4）を比較し、最大の値を持つルーターが選出されます。さらに同点の場合は、能力値が同じルーターのうち、最大のノード識別子を持つルーターが選出されます。

The elected router MUST provide prefix delegation services [RFC3633] on the given link (and follow the rules in Section 6.3.4); all other nodes MUST NOT.

選出されたルーターは、そのリンク上でプレフィックス委任サービス[RFC3633]を提供しなければなりません（MUST）（また、セクション6.3.4の規則に従います）。他のすべてのノードは、これを行ってはなりません（MUST NOT）。

7.3. DHCPv4 for Addressing and Configuration

7.3. アドレス指定と設定のためのDHCPv4

The designated DHCPv4 server on a Common Link (Section 6.1) is elected based on the capabilities described in Section 4. The winner is the router (connected to the Common Link) advertising the greatest L-capability. In case of a tie, Capability Values (Section 4) are compared, and the router with the greatest value is elected. In case of another tie, the router with the greatest node identifier is elected among the routers with tied Capability Values.

共通リンク（セクション6.1）上の指定DHCPv4サーバーは、セクション4で説明する能力に基づいて選出されます。（共通リンクに接続されているルーターのうち）最大のL-capabilityを広告しているルーターが選ばれます。同点の場合は、能力値（セクション4）を比較し、最大の値を持つルーターが選出されます。さらに同点の場合は、能力値が同じルーターのうち、最大のノード識別子を持つルーターが選出されます。

The elected router MUST provide DHCPv4 services on the given link; all other nodes MUST NOT. The elected router MUST provide IP addresses from the pool defined in Section 6.4 and MUST announce itself as router [RFC2132] to clients.

選出されたルーターは、そのリンク上でDHCPv4サービスを提供しなければなりません（MUST）。他のすべてのノードは、これを行ってはなりません（MUST NOT）。選出されたルーターは、セクション6.4で定義するプールからIPアドレスを提供しなければなりません（MUST）。また、クライアントに対して自身をルーター[RFC2132]として告知しなければなりません（MUST）。

DHCPv4 lifetimes renew and rebind times (T1 and T2) SHOULD be short (i.e., not longer than 5 minutes) in order to provide reasonable response times to changes. Routers that cease to be elected DHCP servers SHOULD -- when applicable -- invalidate remaining existing bindings in order to trigger client reconfiguration.

変更に対して妥当な応答時間を提供するために、DHCPv4の有効期間の更新時間と再バインド時間（T1とT2）は短く（すなわち、5分以下に）すべきです（SHOULD）。選出されたDHCPサーバーでなくなったルーターは、該当する場合、クライアントの再設定を促すために、残っている既存のバインディングを無効化すべきです（SHOULD）。

7.4. Multicast DNS Proxy

7.4. マルチキャストDNSプロキシー

The designated Multicast DNS (mDNS) [RFC6762] proxy on a Common Link is elected based on the capabilities described in Section 4. The winner is the router (connected to the Common Link) advertising the greatest M-capability. In case of a tie, Capability Values (Section 4) are compared, and the router with the greatest value is elected. In case of another tie, the router with the greatest node identifier is elected among the routers with tied Capability Values.

共通リンク上の指定マルチキャストDNS（mDNS）[RFC6762]プロキシーは、セクション4で説明する能力に基づいて選出されます。（共通リンクに接続されているルーターのうち）最大のM-capabilityを広告しているルーターが選ばれます。同点の場合は、能力値（セクション4）を比較し、最大の値を持つルーターが選出されます。さらに同点の場合は、能力値が同じルーターのうち、最大のノード識別子を持つルーターが選出されます。

The elected router MUST provide an mDNS proxy on the given link and announce it as described in Section 8.

選出されたルーターは、そのリンク上でmDNSプロキシーを提供し、セクション8で説明するようにそれを告知しなければなりません（MUST）。

8. Naming and Service Discovery

8. 名前付けとサービス発見

Network-wide naming and service discovery can greatly improve the user friendliness of a network. The following mechanism provides means to setup and delegate naming and service discovery across multiple HNCP routers.

ネットワーク全体での名前付けとサービス発見は、ネットワークの使いやすさを大きく向上させることができます。次のメカニズムは、複数のHNCPルーターにわたって名前付けとサービス発見を設定し委任する手段を提供します。

Each HNCP router SHOULD provide and advertise a recursive name resolving server to clients that honor the announcements made in Delegated-Zone TLVs (Section 10.5), Domain-Name TLVs (Section 10.6), and Node-Name TLVs (Section 10.7), i.e., delegate queries to the designated name servers and hand out appropriate A, AAAA, and PTR records according to the mentioned TLVs.

各HNCPルーターは、Delegated-Zone TLV（セクション10.5）、Domain-Name TLV（セクション10.6）、およびNode-Name TLV（セクション10.7）による告知に従う再帰的な名前解決サーバーを、クライアントに提供して広告すべきです（SHOULD）。すなわち、そのサーバーは、指定されたネームサーバーにクエリーを委任し、上記のTLVに従って適切なA、AAAA、およびPTRレコードを返します。

Each HNCP router SHOULD provide and announce an auto-generated or user-configured name for each internal Common Link (Section 6.1) for which it is the designated DHCPv4, stateful DHCPv6 server, mDNS proxy, or for which it provides forward or reverse DNS services on behalf of connected devices. This announcement is done using Delegated-Zone TLVs (Section 10.5) and MUST be unique in the whole network. In case of a conflict, the announcement of the node with the greatest node identifier takes precedence, and all other nodes MUST cease to announce the conflicting TLV. HNCP routers providing recursive name resolving services MUST use the included DNS server address within the TLV to resolve names belonging to the zone as if there was an NS record.

各HNCPルーターは、自身が指定DHCPv4サーバー、指定ステートフルDHCPv6サーバー、または指定mDNSプロキシーとなっている内部の共通リンク（セクション6.1）、あるいは接続された機器に代わって正引きまたは逆引きのDNSサービスを提供している内部の共通リンクのそれぞれについて、自動生成された名前またはユーザーが設定した名前を提供し、告知すべきです（SHOULD）。この告知は、Delegated-Zone TLV（セクション10.5）を使用して行われ、ネットワーク全体で一意である必要があります（MUST）。競合が発生した場合は、最大のノード識別子を持つノードの告知が優先され、他のすべてのノードは競合しているTLVの告知を停止しなければなりません（MUST）。再帰的な名前解決サービスを提供するHNCPルーターは、NSレコードがあるかのように、TLVに含まれるDNSサーバーのアドレスを使用して、そのゾーンに属する名前を解決しなければなりません（MUST）。

Each HNCP node SHOULD announce a node name for itself to be easily reachable and MAY announce names on behalf of other devices. Announcements are made using Node-Name TLVs (Section 10.7), and the announced names MUST be unique in the whole network. In case of a conflict, the announcement of the node with the greatest node identifier takes precedence, and all other nodes MUST cease to announce the conflicting TLV. HNCP routers providing recursive name resolving services as described above MUST resolve such announced names to their respective IP addresses as if there were corresponding A/AAAA records.

各HNCPノードは、容易に到達できるように自身のノード名を告知すべきです（SHOULD）。また、他の機器に代わって名前を告知してもよいです（MAY）。告知はNode-Name TLV（セクション10.7）を使用して行われ、告知される名前はネットワーク全体で一意である必要があります（MUST）。競合が発生した場合は、最大のノード識別子を持つノードの告知が優先され、他のすべてのノードは競合しているTLVの告知を停止しなければなりません（MUST）。上記のように再帰的な名前解決サービスを提供するHNCPルーターは、対応するA/AAAAレコードがあるかのように、そのような告知された名前をそれぞれのIPアドレスに解決しなければなりません（MUST）。

Names and unqualified zones are used in an HNCP network to provide naming and service discovery with local significance. A network-wide zone is appended to all single labels or unqualified zones in order to qualify them. ".home" is the default; however, an administrator MAY configure the announcement of a Domain-Name TLV (Section 10.6) for the network to use a different one. In case multiple are announced, the domain of the node with the greatest node identifier takes precedence.

9. Securing Third-Party Protocols

9. 第三者のプロトコルの保護

PSKs are often required to secure (for example) IGPs and other protocols that lack support for asymmetric security. The following mechanism manages PSKs using HNCP to enable bootstrapping of such third-party protocols. The scheme SHOULD NOT be used unless it's in conjunction with secured HNCP unicast transport (i.e., DTLS), as transferring the PSK in plaintext anywhere in the network is a potential risk, especially as the originator may not know about security (and use of DNCP security) on all links. The following rules define how such a PSK is managed and used:

PSKは、（たとえば）IGPや、非対称なセキュリティーのサポートを欠くその他のプロトコルを保護するためにしばしば必要となります。次のメカニズムは、そのような第三者のプロトコルのブートストラップを可能にするために、HNCPを使用してPSKを管理します。ネットワーク内のどこかでPSKを平文で転送することは潜在的なリスクであり、特に発信者がすべてのリンクのセキュリティー（およびDNCPのセキュリティーの使用）について知らない場合があるため、この方式は、保護されたHNCPのユニキャストトランスポート（すなわちDTLS）と組み合わせる場合を除いて使用すべきではありません（SHOULD NOT）。次の規則は、そのようなPSKをどのように管理し使用するかを定義します：

  • If no Managed-PSK TLV (Section 10.8) is currently being announced, an HNCP node using this mechanism MUST create one after a random delay of 0 to 10 seconds with a 32 bytes long random key and add it to its node data.
  • In case multiple nodes announce such a TLV at the same time, all but the one with the greatest node identifier stop advertising it and adopt the remaining one.
  • The node currently advertising the Managed-PSK TLV MUST generate and advertise a new random one whenever an unreachable node is removed from the DNCP topology as described in Section 4.6 of [RFC7787].
  • 現在Managed-PSK TLV（セクション10.8）が告知されていない場合、このメカニズムを使用するHNCPノードは、0から10秒のランダムな遅延の後に、32バイト長のランダムな鍵を持つManaged-PSK TLVを作成し、自身のノードデータに追加しなければなりません（MUST）。
  • 複数のノードがそのようなTLVを同時に告知した場合、最大のノード識別子を持つノードを除くすべてのノードはその広告を停止し、残ったものを採用します。
  • 現在Managed-PSK TLVを広告しているノードは、[RFC7787]のセクション4.6で説明されているように到達不能なノードがDNCPトポロジーから削除されるたびに、新しいランダムなものを生成して広告しなければなりません（MUST）。

PSKs for individual protocols SHOULD be derived from the random PSK using a suitable one-way hashing algorithm (e.g., by using the HMAC-based Key Derivation Function (HKDF) based on HMAC-SHA256 [RFC6234] with the particular protocol name in the info field) so that disclosure of any derived key does not impact other users of the managed PSK. Furthermore, derived PSKs MUST be updated whenever the managed PSK changes.

導出された鍵のいずれかが漏洩しても、管理されたPSKの他の利用者に影響を与えないように、個々のプロトコルのためのPSKは、適切な一方向ハッシュアルゴリズムを使用して（たとえば、infoフィールドに特定のプロトコル名を指定し、HMAC-SHA256[RFC6234]に基づくHMACベースの鍵導出関数（HKDF）を使用して）ランダムなPSKから導出すべきです（SHOULD）。さらに、導出されたPSKは、管理されたPSKが変更されるたびに更新しなければなりません（MUST）。

10. Type-Length-Value Objects

10. Type-Length-Valueオブジェクト

HNCP defines the following TLVs in addition to those defined by DNCP. The same general rules and defaults for encoding as noted in Section 7 of [RFC7787] apply. Note that most HNCP variable-length TLVs also support optional nested TLVs, and they are encoded after the variable-length content, followed by the zero padding of the variable-length content to the next 32-bit boundary.

HNCPは、DNCPで定義されているTLVに加えて、次のTLVを定義します。[RFC7787]のセクション7に記載されているのと同じエンコードの一般規則とデフォルトが適用されます。HNCPの可変長TLVのほとんどは、任意のネストされたTLVもサポートしており、それらは可変長の内容の後に、可変長の内容を次の32ビット境界までゼロでパディングした後に続けてエンコードされることに注意してください。

TLVs defined here are only valid when appearing in their designated context, i.e., only directly within container TLVs mentioned in their definition or -- absent any mentions -- only as top-level TLVs within the node data set. TLVs appearing outside their designated context MUST be ignored.

ここで定義するTLVは、指定されたコンテキストに出現する場合にのみ有効です。すなわち、その定義で言及されているコンテナーTLVの直下にある場合のみ、あるいは言及がない場合はノードデータセット内のトップレベルのTLVとしてのみ有効です。指定されたコンテキストの外に出現したTLVは無視しなければなりません（MUST）。

TLVs encoding IP addresses or prefixes allow encoding both IPv6 and IPv4 addresses and prefixes. IPv6 information is encoded as is, whereas for IPv4, the IPv4-mapped IPv6 addresses format [RFC4291] is used, and prefix lengths are encoded as the original IPv4 prefix length increased by 96.

11. General Requirements for HNCP Nodes

11. HNCPノードに対する一般要件

Each node implementing HNCP is subject to the following requirements:

HNCPを実装する各ノードには、次の要件が課されます：

  • It MUST implement HNCP versioning (Section 4) and interface classification (Section 5).
  • It MUST implement and run the method for securing third-party protocols (Section 9) whenever it uses the security mechanism of HNCP.
  • HNCPのバージョン管理（セクション4）とインターフェイスの分類（セクション5）を実装しなければなりません（MUST）。
  • HNCPのセキュリティーメカニズムを使用する場合は常に、第三者のプロトコルを保護する方法（セクション9）を実装して実行しなければなりません（MUST）。

If the node is acting as a router, then the following requirements apply in addition:

ノードがルーターとして動作している場合は、さらに次の要件が適用されます：

  • It MUST support Autonomous Address Configuration (Section 6) and configuration of hosts and non-HNCP routers (Section 7).
  • It SHOULD implement support for naming and service discovery (Section 8) as defined in this document.
  • It MAY be able to provide connectivity to IPv4 devices using DHCPv4.
  • It SHOULD be able to delegate prefixes to legacy IPv6 routers using DHCPv6-PD (Section 6.3.4).

  • In addition, the normative language of "Basic Requirements for IPv6 Customer Edge Routers" [RFC7084] applies with the following adjustments:

    • The generic requirements G-4 and G-5 are relaxed such that any known default router on any interface is sufficient for a router to announce itself as the default router; similarly, only the loss of all such default routers results in self-invalidation.
    • "WAN-Side Configuration" (Section 4.2) applies to interfaces classified as external.
    • If the Customer Edge (CE) sends a size hint as indicated in WPD-2, the hint MUST NOT be determined by the number of LAN interfaces of the CE but SHOULD instead be large enough to at least accommodate prefix assignments announced for existing delegated or ULA prefixes, if such prefixes exist and unless explicitly configured otherwise.
    • The dropping of packets with a destination address belonging to a delegated prefix mandated in WPD-5 MUST NOT be applied to destinations that are part of any prefix announced using an Assigned-Prefix TLV by any HNCP router in the network.
    • "LAN-Side Configuration" (Section 4.3) applies to interfaces not classified as external.
    • The requirement L-2 to assign a separate /64 to each LAN interface is replaced by the participation in the prefix assignment mechanism (Section 6.3) for each such interface.
    • The requirement L-9 is modified, in that the M flag MUST be set if and only if a router connected to the respective Common Link is advertising a non-zero H-capability. The O flag SHOULD always be set.
    • The requirement L-12 to make DHCPv6 options available is adapted, in that Canonical Encoding Rules (CER) SHOULD publish the subset of options using the DHCPv6-Data TLV in an External-Connection TLV. Similarly, it SHOULD do the same for DHCPv4 options in a DHCPv4-Data TLV. DHCPv6 options received inside an OPTION_IAPREFIX [RFC3633] MUST be published using a DHCPv6-Data TLV inside the respective Delegated-Prefix TLV. HNCP routers SHOULD make relevant DHCPv6 and DHCPv4 options available to clients, i.e., options contained in External-Connection TLVs that also include delegated prefixes from which a subset is assigned to the respective link.
    • The requirement L-13 to deprecate prefixes is applied to all delegated prefixes in the network from which assignments have been made on the respective interface. Furthermore, the Prefix Information Options indicating deprecation MUST be included in Router Advertisements for the remainder of the prefixes' respective valid lifetime but MAY be omitted after at least 2 hours have passed.
  • 自律的なアドレス設定（セクション6）と、ホストと非HNCPルーターの設定（セクション7）をサポートしなければなりません（MUST）。
  • この文書で定義する名前付けとサービス発見（セクション8）のサポートを実装すべきです（SHOULD）。
  • DHCPv4を使用してIPv4機器に接続性を提供できてもよいです（MAY）。
  • DHCPv6-PD（セクション6.3.4）を使用してレガシーなIPv6ルーターにプレフィックスを委任できるべきです（SHOULD）。

  • さらに、「Basic Requirements for IPv6 Customer Edge Routers」[RFC7084]の規範的な記述が、次の調整を加えたうえで適用されます：

    • 一般要件G-4とG-5は、ルーターが自身をデフォルトルーターとして告知するには、いずれかのインターフェイス上に既知のデフォルトルーターが1つでもあれば十分であるように緩和されます。同様に、そのようなデフォルトルーターをすべて失った場合にのみ、自身を無効化します。
    • 「WAN-Side Configuration」（Section 4.2）は、外部に分類されたインターフェイスに適用されます。
    • カスタマーエッジ（CE）がWPD-2で示されているようにサイズのヒントを送信する場合、そのヒントは、CEのLANインターフェイスの数によって決定してはなりません（MUST NOT）。代わりに、明示的に別途設定されていない限り、既存の委任されたプレフィックスまたはULAプレフィックスが存在する場合には、それらについて告知されたプレフィックス割り当てを少なくとも収容できるだけの大きさにすべきです（SHOULD）。
    • WPD-5で義務付けられている、委任されたプレフィックスに属する宛先アドレスを持つパケットの破棄は、ネットワーク内のいずれかのHNCPルーターがAssigned-Prefix TLVを使用して告知したプレフィックスに含まれる宛先には適用してはなりません（MUST NOT）。
    • 「LAN-Side Configuration」（Section 4.3）は、外部に分類されていないインターフェイスに適用されます。
    • 各LANインターフェイスに個別の/64を割り当てるという要件L-2は、そのような各インターフェイスについてプレフィックス割り当てメカニズム（セクション6.3）に参加することに置き換えられます。
    • 要件L-9は変更され、それぞれの共通リンクに接続されているルーターが0でないH-capabilityを広告している場合に限り、Mフラグを設定しなければなりません（MUST）。Oフラグは常に設定すべきです（SHOULD）。
    • DHCPv6オプションを利用可能にするという要件L-12は、次のように適合されます。Canonical Encoding Rules（CER）は、External-Connection TLVの中のDHCPv6-Data TLVを使用してオプションのサブセットを公開すべきです（SHOULD）。同様に、DHCPv4オプションについても、DHCPv4-Data TLVで同じことをすべきです（SHOULD）。OPTION_IAPREFIX[RFC3633]の中で受信したDHCPv6オプションは、それぞれのDelegated-Prefix TLVの中のDHCPv6-Data TLVを使用して公開しなければなりません（MUST）。HNCPルーターは、関連するDHCPv6オプションとDHCPv4オプション、すなわち、それぞれのリンクにそのサブセットが割り当てられている委任されたプレフィックスも含むExternal-Connection TLVに含まれるオプションを、クライアントが利用できるようにすべきです（SHOULD）。
    • プレフィックスを非推奨にするという要件L-13は、それぞれのインターフェイスで割り当てが行われた、ネットワーク内のすべての委任されたプレフィックスに適用されます。さらに、非推奨を示すPrefix Informationオプションは、プレフィックスのそれぞれの有効期間の残りの間、ルーター広告に含めなければなりません（MUST）。ただし、少なくとも2時間が経過した後は省略してもよいです（MAY）。

12. Security Considerations

12. セキュリティーに関する考慮事項

HNCP enables self-configuring networks, requiring as little user intervention as possible. However, this zero-configuration goal usually conflicts with security goals and introduces a number of threats.

HNCPは、ユーザーの介入をできるだけ必要としない自己設定型のネットワークを可能にします。しかし、このゼロコンフィギュレーションという目標は、通常、セキュリティーの目標と相反し、多くの脅威をもたらします。

General security issues for existing home networks are discussed in [RFC7368]. The protocols used to set up addresses and routes in such networks to this day rarely have security enabled within the configuration protocol itself. However, these issues are out of scope for the security of HNCP itself.

既存のホームネットワークに関する一般的なセキュリティーの問題は、[RFC7368]で議論されています。そのようなネットワークでアドレスと経路を設定するために使用されるプロトコルは、今日に至るまで、設定プロトコル自体でセキュリティーが有効になっていることはまれです。ただし、これらの問題はHNCP自体のセキュリティーの範囲外です。

HNCP is a DNCP-based state synchronization mechanism carrying information with varying threat potential. For this consideration, the payloads defined in DNCP and this document are reviewed:

HNCPは、さまざまな脅威の可能性を持つ情報を運ぶ、DNCPベースの状態同期メカニズムです。この考察のために、DNCPとこの文書で定義されているペイロードを検討します：

  • Network topology information such as HNCP nodes and their common links.
  • Address assignment information such as delegated and assigned prefixes for individual links.
  • Naming and service discovery information such as auto-generated or customized names for individual links and nodes.
  • HNCPノードとその共通リンクなどの、ネットワークトポロジー情報。
  • 個々のリンクに対する委任されたプレフィックスや割り当て済みプレフィックスなどの、アドレス割り当て情報。
  • 個々のリンクやノードに対する自動生成された名前やカスタマイズされた名前などの、名前付けとサービス発見の情報。

12.1. Interface Classification

12.1. インターフェイスの分類

As described in Section 5.3, an HNCP node determines the internal or external state on a per-interface basis. A firewall perimeter is set up for the external interfaces, and for internal interfaces, HNCP traffic is allowed, with the exception of the Leaf and Guest subcategories.

セクション5.3で説明したように、HNCPノードは、内部か外部かの状態をインターフェイスごとに決定します。外部インターフェイスにはファイアウォールの境界が設定され、内部インターフェイスでは、LeafとGuestのサブカテゴリーを除き、HNCPトラフィックが許可されます。

Threats concerning automatic interface classification cannot be mitigated by encrypting or authenticating HNCP traffic itself since external routers do not participate in the protocol and often cannot be authenticated by other means. These threats include propagation of forged uplinks in the homenet in order to, e.g., redirect traffic destined to external locations and forged internal status by external routers to, e.g., circumvent the perimeter firewall.

外部のルーターはプロトコルに参加せず、多くの場合、他の手段で認証することもできないため、インターフェイスの自動分類に関する脅威は、HNCPトラフィック自体を暗号化または認証しても緩和できません。これらの脅威には、たとえば外部宛てのトラフィックをリダイレクトするための、ホームネット内での偽造されたアップリンクの伝播や、たとえば境界のファイアウォールを回避するための、外部のルーターによる内部状態の偽装が含まれます。

It is therefore imperative to either secure individual links on the physical or link layer or preconfigure the adjacent interfaces of HNCP routers to an appropriate fixed category in order to secure the homenet border. Depending on the security of the external link, eavesdropping, man-in-the-middle, and similar attacks on external traffic can still happen between a homenet border router and the ISP; however, these cannot be mitigated from inside the homenet. For example, DHCPv4 has defined [RFC3118] to authenticate DHCPv4 messages, but this is very rarely implemented in large or small networks. Further, while PPP can provide secure authentication of both sides of a point-to-point link, it is most often deployed with one-way authentication of the subscriber to the ISP, not the ISP to the subscriber.

したがって、ホームネットの境界を保護するためには、物理層またはリンク層で個々のリンクを保護するか、HNCPルーターの隣接インターフェイスを適切な固定カテゴリーに事前設定することが不可欠です。外部リンクのセキュリティーによっては、ホームネットの境界ルーターとISPとの間で、外部トラフィックに対する盗聴、中間者攻撃、および同様の攻撃が依然として発生する可能性があります。しかし、これらはホームネットの内部からは緩和できません。たとえば、DHCPv4ではDHCPv4メッセージを認証するために[RFC3118]が定義されていますが、これは大規模なネットワークでも小規模なネットワークでもほとんど実装されていません。さらに、PPPはポイントツーポイントリンクの両側の安全な認証を提供できますが、ほとんどの場合、加入者からISPへの一方向の認証で展開されており、ISPから加入者への認証は行われていません。

12.2. Security of Unicast Traffic

12.2. ユニキャストトラフィックのセキュリティー

Once the homenet border has been established, there are several ways to secure HNCP against internal threats like manipulation or eavesdropping by compromised devices on a link that is enabled for HNCP traffic. If left unsecured, attackers may perform arbitrary traffic redirection, eavesdropping, spoofing, or denial-of-service attacks on HNCP services such as address assignment or service discovery, and the protocols are secured using HNCP-derived keys such as routing protocols.

ホームネットの境界が確立されると、HNCPトラフィックが有効になっているリンク上の侵害された機器による改ざんや盗聴などの内部の脅威からHNCPを保護する方法がいくつかあります。保護されていない場合、攻撃者は、アドレス割り当てやサービス発見などのHNCPのサービス、およびルーティングプロトコルなどのHNCPから導出された鍵を使用して保護されるプロトコルに対して、任意のトラフィックのリダイレクト、盗聴、なりすまし、またはサービス拒否攻撃を行う可能性があります。

Detailed interface categories like "Leaf" or "Guest" can be used to integrate not fully trusted devices to various degrees into the homenet by not exposing them to HNCP traffic or by using firewall rules to prevent them from reaching homenet-internal resources.

"Leaf"や"Guest"のような詳細なインターフェイスカテゴリーを使用すると、完全には信頼できない機器を、HNCPトラフィックにさらさないようにしたり、ファイアウォール規則を使用してホームネット内部のリソースに到達できないようにしたりすることで、さまざまな程度でホームネットに統合できます。

On links where this is not practical and lower layers do not provide adequate protection from attackers, DTLS-based secure unicast transport MUST be used to secure traffic.

これが現実的でなく、かつ下位層が攻撃者からの十分な保護を提供しないリンクでは、トラフィックを保護するために、DTLSベースの安全なユニキャストトランスポートを使用しなければなりません（MUST）。

12.3. Other Protocols in the Home

12.3. 家庭内の他のプロトコル

IGPs and other protocols are usually run alongside HNCP; therefore, the individual security aspects of the respective protocols must be considered. It can, however, be summarized that many protocols to be run in the home (like IGPs) provide -- to a certain extent -- similar security mechanisms. Most of these protocols do not support encryption and only support authentication based on Pre-Shared Keys natively. This influences the effectiveness of any encryption-based security mechanism deployed by HNCP as homenet routing information is thus usually not encrypted.

IGPやその他のプロトコルは通常HNCPと並行して実行されるため、それぞれのプロトコルの個別のセキュリティーの側面を考慮する必要があります。ただし、家庭内で実行される多くのプロトコル（IGPなど）は、ある程度、同様のセキュリティーメカニズムを提供していると要約できます。これらのプロトコルのほとんどは暗号化をサポートしておらず、ネイティブには事前共有鍵に基づく認証のみをサポートしています。そのため、ホームネットのルーティング情報は通常暗号化されず、このことはHNCPが展開する暗号化ベースのセキュリティーメカニズムの有効性に影響を与えます。
