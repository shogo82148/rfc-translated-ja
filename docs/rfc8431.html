1. Introduction

1. はじめに

The Interface to the Routing System (I2RS) [RFC7921] provides read and write access to the information and state within the routing process that exists inside the routing elements; this is achieved via protocol message exchange between I2RS clients and I2RS agents associated with the routing system. One of the functions of I2RS is to read and write data of the Routing Information Base (RIB). [I2RS-REQS] introduces a set of RIB use cases. The RIB information model is defined in [RFC8430].

ルーティングシステムへのインターフェイス（I2RS: Interface to the Routing System）[RFC7921]は、ルーティング要素の内部に存在するルーティングプロセス内の情報と状態に対する読み取りおよび書き込みのアクセスを提供します。 これは、I2RSクライアントと、ルーティングシステムに関連付けられたI2RSエージェントとの間のプロトコルメッセージ交換によって実現されます。 I2RSの機能の1つは、ルーティング情報ベース（RIB: Routing Information Base）のデータを読み書きすることです。 [I2RS-REQS]は、一連のRIBのユースケースを紹介しています。 RIB情報モデルは[RFC8430]で定義されています。

This document defines a YANG data model [RFC7950] [RFC6991] for the RIB that satisfies the RIB use cases and aligns with the RIB information model.

この文書は、RIBのユースケースを満たし、RIB情報モデルに沿った、RIBのためのYANGデータモデル[RFC7950] [RFC6991]を定義します。

2.1. RIB Capability

2.1. RIBの能力

RIB capability negotiation is very important because not all of the hardware will be able to support all kinds of nexthops, and there might be a limitation on how many levels of lookup can be practically performed. Therefore, a RIB data model needs to specify a way for an external entity to learn about the functional capabilities of a network device.

すべてのハードウェアがあらゆる種類のネクストホップをサポートできるわけではなく、また実際に実行できるルックアップの段数にも制限がある場合があるため、RIBの能力のネゴシエーションは非常に重要です。 したがって、RIBデータモデルは、外部エンティティーがネットワーク機器の機能的な能力を知るための方法を規定する必要があります。

At the same time, nexthop chains can be used to specify multiple headers over a packet before that particular packet is forwarded. Not every network device will be able to support all kinds of nexthop chains along with the arbitrary number of headers that are chained together. The RIB data model needs a way to expose the nexthop chaining capability supported by a given network device.

同時に、ネクストホップチェーンを使用すると、特定のパケットを転送する前に、そのパケットに複数のヘッダーを付与するよう指定できます。 すべてのネットワーク機器が、あらゆる種類のネクストホップチェーンと、任意の数の連結されたヘッダーをサポートできるわけではありません。 RIBデータモデルには、特定のネットワーク機器がサポートするネクストホップチェーンの能力を公開する方法が必要です。

This module uses the feature and if-feature statements to achieve above capability advertisement.

このモジュールは、上記の能力の通知を実現するために、feature文とif-feature文を使用します。

2.2. Routing Instance and RIB

2.2. ルーティングインスタンスとRIB

A routing instance, in the context of the RIB information model, is a collection of RIBs, interfaces, and routing protocol parameters. A routing instance creates a logical slice of the router and can allow multiple different logical slices, across a set of routers, to communicate with each other. The routing protocol parameters control the information available in the RIBs. More details about a routing instance can be found in Section 2.2 of [RFC8430].

RIB情報モデルの文脈におけるルーティングインスタンスとは、RIB、インターフェイス、ルーティングプロトコルのパラメーターの集合です。 ルーティングインスタンスは、ルーターの論理的なスライスを作り出し、一連のルーターにまたがる複数の異なる論理スライスが相互に通信できるようにします。 ルーティングプロトコルのパラメーターは、RIBで利用可能な情報を制御します。 ルーティングインスタンスの詳細は、[RFC8430]のセクション2.2に記載されています。

2.3. Route

2.3. 経路

A route is essentially a match condition and an action following that match. The match condition specifies the kind of route (e.g., IPv4, MPLS, Media Access Control (MAC), Interface, etc.) and the set of fields to match on.

経路は、本質的にはマッチ条件と、そのマッチに続くアクションです。 マッチ条件は、経路の種類（たとえば、IPv4、MPLS、メディアアクセス制御（MAC）、インターフェイスなど）と、マッチ対象のフィールドの集合を指定します。

A route MUST contain the ROUTE_PREFERENCE attribute (see Section 2.3 of [RFC8430]).

経路はROUTE_PREFERENCE属性を含めなければなりません（MUST）（[RFC8430]のセクション2.3を参照）。

In addition, a route MUST associate with the following status attributes in responses to a RIB writing/reading operation:

さらに、経路は、RIBの書き込み・読み取り操作への応答において、次の状態属性と関連付けられなければなりません（MUST）。

  • Active: Indicates whether a route has at least one fully resolved nexthop and is therefore eligible for installation in the FIB.
  • Installed: Indicates whether the route got installed in the FIB.
  • Reason: Indicates the specific reason that caused the failure, e.g., "Not authorized".
  • Active: 経路が完全に解決されたネクストホップを少なくとも1つ持ち、したがってFIBへのインストールの対象となるかどうかを示します。
  • Installed: 経路がFIBにインストールされたかどうかを示します。
  • Reason: 失敗を引き起こした具体的な理由を示します（たとえば、"Not authorized"）。

In addition, a route can be associated with one or more optional route-attributes (e.g., route-vendor-attributes).

さらに、経路は、1つ以上の任意の経路属性（route-attributes。たとえば、route-vendor-attributes）と関連付けることができます。

A RIB will have a number of routes, so the routes are expressed as a list under a specific RIB. Each RIB has its own route list.

RIBは多数の経路を持つため、経路は特定のRIBの下のリストとして表現されます。 各RIBは独自の経路リストを持ちます。

2.4. Nexthop

2.4. ネクストホップ

A nexthop represents an object resulting from a route lookup. As illustrated in Figure 4 of [RFC8430], to support various use cases (e.g., load-balancing, protection, multicast, or a combination of them), the nexthop is modeled as a multilevel structure and supports recursion. The first level of the nexthop includes the following four types:

ネクストホップは、経路のルックアップの結果として得られるオブジェクトを表します。 [RFC8430]の図4に示されているように、さまざまなユースケース（たとえば、負荷分散、保護、マルチキャスト、またはそれらの組み合わせ）をサポートするため、ネクストホップは多階層の構造としてモデル化されており、再帰をサポートします。 ネクストホップの第1階層には、次の4つのタイプがあります。

  • Base: The "base" nexthop is the foundation of all other nexthop types. It includes the following basic nexthops:

    • nexthop-id
    • IPv4 address
    • IPv6 address
    • egress-interface
    • egress-interface with IPv4 address
    • egress-interface with IPv6 address
    • egress-interface with MAC address
    • logical-tunnel
    • tunnel-encapsulation
    • tunnel-decapsulation
    • rib-name
  • Chain: The "chain" nexthop provides a way to perform multiple operations on a packet by logically combining them.
  • Load-Balance: The "load-balance" nexthop is designed for a load-balance case where it normally will have multiple weighted nexthops.
  • Protection: The "protection" nexthop is designed for a protection scenario where it normally will have primary and standby nexthop.
  • Replicate: The "replicate" nexthop is designed for multiple destinations forwarding.

  • Base: 「base」ネクストホップは、他のすべてのネクストホップタイプの基礎です。 これには、次の基本的なネクストホップが含まれます。

    • nexthop-id
    • IPv4アドレス
    • IPv6アドレス
    • egress-interface
    • IPv4アドレス付きのegress-interface
    • IPv6アドレス付きのegress-interface
    • MACアドレス付きのegress-interface
    • logical-tunnel
    • tunnel-encapsulation
    • tunnel-decapsulation
    • rib-name
  • Chain: 「chain」ネクストホップは、複数の操作を論理的に組み合わせることで、パケットに対してそれらの操作を実行する方法を提供します。
  • Load-Balance: 「load-balance」ネクストホップは、通常、重み付けされた複数のネクストホップを持つ負荷分散のケース向けに設計されています。
  • Protection: 「protection」ネクストホップは、通常、プライマリーとスタンバイのネクストホップを持つ保護のシナリオ向けに設計されています。
  • Replicate: 「replicate」ネクストホップは、複数の宛先への転送向けに設計されています。

2.5. RPC Operations

2.5. RPC操作

This module defines the following RPC operations:

このモジュールは、次のRPC操作を定義します。

  • rib-add: Add a RIB to a routing instance. The following are passed as the input parameters: the name of the RIB, the address family of the RIB, and (optionally) whether the RPF check is enabled. The output is the result of the add operation:

    • true - success
    • false - failed (when failed, the I2RS agent may return the specific reason that caused the failure)

  • rib-delete: Delete a RIB from a routing instance. When a RIB is deleted, all routes installed in the RIB will be deleted. A rib-name is passed as the input parameter. The output is the result of the delete operation:

    • true - success
    • false - failed (when failed, the I2RS agent may return the specific reason that caused the failure)

  • route-add: Add a route or a set of routes to a RIB. The following are passed as the input parameters: the name of the RIB, the route prefix(es), the route-attributes, the route-vendor-attributes, the nexthop, and the "whether to return failure details" indication. Before calling the route-add rpc, it is required to call the nh-add rpc to create and/or return the nexthop identifier. However, in situations when the nexthop already exists and the nexthop-id is known, this action is not expected. The output is a combination of the route operation states while querying the appropriate node in the data tree, which includes:

    • success-count: the number of routes that were successfully added;
    • failed-count: the number of the routes that failed to be added; and,
    • failure-detail: this shows the specific routes that failed to be added.

  • route-delete: Delete a route or a set of routes from a RIB. The following are passed as the input parameters: the name of the RIB, the route prefix(es), and the "whether to return failure details" indication. The output is a combination of route operation states, which includes:

    • success-count: the number of routes that were successfully deleted;
    • failed-count: the number of the routes that failed to be deleted; and,
    • failure-detail: this shows the specific routes that failed to be deleted.

  • route-update: Update a route or a set of routes. The following are passed as the input parameters: the name of the RIB, the route prefix(es), the route-attributes, the route-vendor-attributes, or the nexthop. The match conditions can be either route prefix(es), route-attributes, route-vendor-attributes, or nexthops. The update actions include the following: update the nexthops, update the route-attributes, and update the route-vendor-attributes. The output is a combination of the route operation states, which includes:

    • success-count: the number of routes that were successfully updated;
    • failed-count: the number of the routes that failed to be updated; and,
    • failure-detail: this shows the specific routes that failed to be updated.

  • nh-add: Add a nexthop to a RIB. The following are passed as the input parameters: the name of the RIB and the nexthop. The network node is required to allocate a nexthop identifier to the nexthop. The outputs include the result of the nexthop add operation.

    • true - success (when success, a nexthop identifier will be returned to the I2RS client)
    • false - failed (when failed, the I2RS agent may return the specific reason that caused the failure)

  • nh-delete: Delete a nexthop from a RIB. The following are passed as the input parameters: the name of the RIB and a nexthop or nexthop identifier. The output is the result of the delete operation:

    • true - success
    • false - failed (when failed, the I2RS agent may return the specific reason that caused the failure)

  • rib-add: ルーティングインスタンスにRIBを追加します。 入力パラメーターとして、RIBの名前、RIBのアドレスファミリー、および（任意で）RPFチェックを有効にするかどうかが渡されます。 出力は、追加操作の結果です。

    • true - 成功
    • false - 失敗（失敗した場合、I2RSエージェントは失敗を引き起こした具体的な理由を返すことがあります）

  • rib-delete: ルーティングインスタンスからRIBを削除します。 RIBが削除されると、そのRIBにインストールされたすべての経路が削除されます。 入力パラメーターとしてrib-nameが渡されます。 出力は、削除操作の結果です。

    • true - 成功
    • false - 失敗（失敗した場合、I2RSエージェントは失敗を引き起こした具体的な理由を返すことがあります）

  • route-add: RIBに経路または経路の集合を追加します。 入力パラメーターとして、RIBの名前、経路のプレフィックス、route-attributes、route-vendor-attributes、ネクストホップ、および「失敗の詳細を返すかどうか」の指示が渡されます。 route-add RPCを呼び出す前に、nh-add RPCを呼び出してネクストホップ識別子を作成または取得する必要があります。 ただし、ネクストホップがすでに存在し、nexthop-idが分かっている状況では、この処理は想定されていません。 出力は、データツリー内の適切なノードを問い合わせたときの経路操作の状態の組み合わせであり、次のものを含みます。

    • success-count: 追加に成功した経路の数
    • failed-count: 追加に失敗した経路の数
    • failure-detail: 追加に失敗した具体的な経路を示します。

  • route-delete: RIBから経路または経路の集合を削除します。 入力パラメーターとして、RIBの名前、経路のプレフィックス、および「失敗の詳細を返すかどうか」の指示が渡されます。 出力は経路操作の状態の組み合わせであり、次のものを含みます。

    • success-count: 削除に成功した経路の数
    • failed-count: 削除に失敗した経路の数
    • failure-detail: 削除に失敗した具体的な経路を示します。

  • route-update: 経路または経路の集合を更新します。 入力パラメーターとして、RIBの名前、経路のプレフィックス、route-attributes、route-vendor-attributes、またはネクストホップが渡されます。 マッチ条件は、経路のプレフィックス、route-attributes、route-vendor-attributes、ネクストホップのいずれかです。 更新アクションには、ネクストホップの更新、route-attributesの更新、route-vendor-attributesの更新があります。 出力は経路操作の状態の組み合わせであり、次のものを含みます。

    • success-count: 更新に成功した経路の数
    • failed-count: 更新に失敗した経路の数
    • failure-detail: 更新に失敗した具体的な経路を示します。

  • nh-add: RIBにネクストホップを追加します。 入力パラメーターとして、RIBの名前とネクストホップが渡されます。 ネットワークノードは、そのネクストホップにネクストホップ識別子を割り当てる必要があります。 出力には、ネクストホップの追加操作の結果が含まれます。

    • true - 成功（成功した場合、ネクストホップ識別子がI2RSクライアントに返されます）
    • false - 失敗（失敗した場合、I2RSエージェントは失敗を引き起こした具体的な理由を返すことがあります）

2.6. Notifications

2.6. 通知

Asynchronous notifications are sent by the RIB manager of a network device to an external entity when some event triggers on the network device. An implementation of this RIB data model MUST support sending two kinds of asynchronous notifications.

非同期通知は、ネットワーク機器で何らかのイベントが発生したときに、ネットワーク機器のRIBマネージャーから外部エンティティーに送信されます。 このRIBデータモデルの実装は、2種類の非同期通知の送信をサポートしなければなりません（MUST）。

1. Route change notification:

1. 経路変更通知：

  • Installed (indicates whether the route got installed in the FIB)
  • Active (indicates whether a route has at least one fully resolved nexthop and is therefore eligible for installation in the FIB)
  • Reason (e.g., "Not authorized")
  • Installed（経路がFIBにインストールされたかどうかを示します）
  • Active（経路が完全に解決されたネクストホップを少なくとも1つ持ち、したがってFIBへのインストールの対象となるかどうかを示します）
  • Reason（たとえば、"Not authorized"）

2. Nexthop resolution status notification

2. ネクストホップ解決状態の通知

Nexthops can be fully resolved or unresolved.

ネクストホップは、完全に解決されている場合と、未解決の場合があります。

A resolved nexthop has an adequate level of information to send the outgoing packet towards the destination by forwarding it on an interface to a directly connected neighbor.

解決済みのネクストホップは、直接接続された隣接ノードへのインターフェイス上で転送することにより、送信パケットを宛先に向けて送るのに十分な情報を持っています。

An unresolved nexthop is something that requires the RIB manager to determine the final resolved nexthop. In one example, a nexthop could be an IP address. The RIB manager would resolve how to reach that IP address, e.g., by checking if that particular IP address is reachable by regular IP forwarding, by an MPLS tunnel, or by both. If the RIB manager cannot resolve the nexthop, then the nexthop remains in an unresolved state and is NOT a suitable candidate for installation in the FIB.

未解決のネクストホップとは、RIBマネージャーが最終的に解決されたネクストホップを決定する必要があるものです。 一例として、ネクストホップがIPアドレスである場合があります。 RIBマネージャーは、そのIPアドレスへの到達方法を解決します。 たとえば、その特定のIPアドレスが、通常のIP転送、MPLSトンネル、またはその両方によって到達可能かどうかを確認します。 RIBマネージャーがネクストホップを解決できない場合、そのネクストホップは未解決の状態のままとなり、FIBへのインストールに適した候補にはなりません。

An implementation of this RIB data model MUST support sending route-change notifications whenever a route transitions between the following states:

このRIBデータモデルの実装は、経路が次の状態の間を遷移するたびに、route-change通知の送信をサポートしなければなりません（MUST）。

  • from the active state to the inactive state
  • from the inactive state to the active state
  • from the installed state to the uninstalled state
  • from the uninstalled state to the installed state
  • アクティブ状態から非アクティブ状態へ
  • 非アクティブ状態からアクティブ状態へ
  • インストール済み状態から未インストール状態へ
  • 未インストール状態からインストール済み状態へ

A single notification MAY be used when a route transitions from inactive/uninstalled to active/installed or in the other direction.

経路が非アクティブ・未インストールからアクティブ・インストール済みへ、またはその逆方向に遷移する場合、単一の通知を使用してもよいです（MAY）。

5. Security Considerations

5. セキュリティーに関する考慮事項

The YANG module specified in this document defines a schema for data that is designed to be accessed via network management protocols such as NETCONF [RFC6241] or RESTCONF [RFC8040]. The lowest NETCONF layer is the secure transport layer, and the mandatory-to-implement secure transport is Secure Shell (SSH) [RFC6242]. The lowest RESTCONF layer is HTTPS, and the mandatory-to-implement secure transport is TLS [RFC8446].

この文書で規定するYANGモジュールは、NETCONF [RFC6241]やRESTCONF [RFC8040]などのネットワーク管理プロトコルを介してアクセスされるように設計されたデータのスキーマを定義します。 NETCONFの最下位層はセキュアなトランスポート層であり、実装必須のセキュアなトランスポートはSecure Shell（SSH）[RFC6242]です。 RESTCONFの最下位層はHTTPSであり、実装必須のセキュアなトランスポートはTLS [RFC8446]です。

The NETCONF access control model [RFC8341] provides the means to restrict access for particular NETCONF or RESTCONF users to a preconfigured subset of all available NETCONF or RESTCONF protocol operations and content.

NETCONFアクセス制御モデル[RFC8341]は、特定のNETCONFまたはRESTCONFユーザーのアクセスを、利用可能なすべてのNETCONFまたはRESTCONFのプロトコル操作とコンテンツのうち、事前に設定されたサブセットに制限する手段を提供します。

The YANG module defines information that can be configurable in certain instances, for example, a RIB, a route, a nexthop can be created or deleted by client applications; the YANG module also defines RPCs that can be used by client applications to add/delete RIBs, routes, and nexthops. In such cases, a malicious client could attempt to remove, add, or update a RIB, a route, or a nexthop by creating or deleting corresponding elements in the RIB, route, and nexthop lists, respectively. Removing a RIB or a route could lead to disruption or impact in performance of a service; updating a route may lead to suboptimal path and degradation of service levels as well as possibly disruption of service. For those reasons, it is important that the NETCONF access control model is vigorously applied to prevent misconfiguration by unauthorized clients.

このYANGモジュールは、特定の場合に設定可能な情報を定義しています。 たとえば、RIB、経路、ネクストホップは、クライアントアプリケーションによって作成または削除できます。 また、このYANGモジュールは、クライアントアプリケーションがRIB、経路、ネクストホップを追加・削除するために使用できるRPCも定義しています。 このような場合、悪意のあるクライアントは、RIB、経路、ネクストホップの各リストの対応する要素を作成または削除することにより、RIB、経路、またはネクストホップの削除、追加、または更新を試みる可能性があります。 RIBや経路の削除は、サービスの中断やサービスの性能への影響につながる可能性があります。 経路の更新は、最適でない経路やサービスレベルの低下、さらにはサービスの中断につながる可能性があります。 これらの理由から、権限のないクライアントによる誤設定を防ぐために、NETCONFアクセス制御モデルを厳格に適用することが重要です。

There are a number of data nodes defined in this YANG module that are writable/creatable/deletable (i.e., config true, which is the default). These data nodes may be considered sensitive or vulnerable in some network environments. Write operations (e.g., edit-config) to these data nodes without proper protection can have a negative effect on network operations. These are the subtrees and data nodes and their sensitivity/vulnerability:

このYANGモジュールで定義されているデータノードには、書き込み・作成・削除が可能なもの（つまり、デフォルトであるconfig true）が多数あります。 これらのデータノードは、ネットワーク環境によっては機密性が高い、または脆弱であるとみなされる場合があります。 適切な保護なしにこれらのデータノードに対して書き込み操作（たとえば、edit-config）を行うと、ネットワークの運用に悪影響を及ぼす可能性があります。 サブツリーとデータノード、およびそれらの機密性・脆弱性は次のとおりです。

  • RIB: A malicious client could attempt to remove a RIB from a routing instance, for example, in order to sabotage the services provided by the RIB or to add a RIB to a routing instance (hence, to inject unauthorized traffic into the nexthop).
  • route: A malicious client could attempt to remove or add a route from/to a RIB, for example, in order to sabotage the services provided by the RIB.
  • nexthop: A malicious client could attempt to remove or add a nexthop from/to RIB, which may lead to a suboptimal path, a degradation of service levels, and a possible disruption of service.
  • RIB: 悪意のあるクライアントは、たとえば、RIBが提供するサービスを妨害するためにルーティングインスタンスからRIBを削除したり、ルーティングインスタンスにRIBを追加したり（それによって、ネクストホップに不正なトラフィックを注入したり）しようとする可能性があります。
  • route: 悪意のあるクライアントは、たとえば、RIBが提供するサービスを妨害するために、RIBから経路を削除したり、RIBに経路を追加したりしようとする可能性があります。
  • nexthop: 悪意のあるクライアントは、RIBからネクストホップを削除したり、RIBにネクストホップを追加したりしようとする可能性があり、これは最適でない経路、サービスレベルの低下、さらにはサービスの中断につながる可能性があります。
