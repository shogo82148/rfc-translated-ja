RFC 1298

SNMP over IPX

RFC 1298

IPX上のSNMP

Abstract

概要

This memo defines a convention for encapsulating Simple Network Management Protocol (SNMP) [1] packets over the transport mechanism provided via the Internetwork Packet Exchange (IPX) protocol [2].

このメモは、簡易ネットワーク管理プロトコル（Simple Network Management Protocol: SNMP）[1]のパケットを、インターネットワークパケット交換（Internetwork Packet Exchange: IPX）プロトコル[2]が提供するトランスポートメカニズム上でカプセル化するための規約を定義します。

Editor's Note

編集者注

As stated below and in reference [5], it is strongly advised that for interoperability, SNMP be implemented over UDP/IP and not directly on media or other protocols (such as IPX).

以下および参考文献[5]で述べているように、相互運用性のために、SNMPはメディアや他のプロトコル（IPXなど）の上に直接ではなく、UDP/IP上で実装することを強く推奨します。

Status of This Memo

このメモのステータス

This memo provides information for the Internet community. It does not specify an Internet standard. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーに情報を提供するものです。インターネット標準を規定するものではありません。このメモの配布は無制限です。

1. Introduction

1. はじめに

The SNMP protocol has been specified as the official network management protocol of the Internet. Its widespread acceptance and implementation by developers, both inside and outside the Internet community, is fostering synergetic growth to a variety of protocols and platforms.

SNMPプロトコルは、インターネットの公式なネットワーク管理プロトコルとして規定されています。インターネットコミュニティーの内外の開発者に広く受け入れられ、実装されていることで、さまざまなプロトコルやプラットフォームへの相乗的な広がりが促されています。

This memo addresses the use of SNMP over the IPX protocol, which has become quite widespread principally due to the popularity of Novell NetWare. Roughly equivalent to UDP in function, IPX provides connectionless, unacknowledged datagram service over a variety of physical media and protocols.

このメモでは、IPXプロトコル上でのSNMPの使用を扱います。IPXは、主にNovell NetWareの人気によって非常に広く普及しています。IPXは機能的にはUDPとほぼ同等であり、さまざまな物理メディアやプロトコルの上で、コネクションレスで確認応答のないデータグラムサービスを提供します。

Although modifications have been made elsewhere in the NetWare protocol suite, IPX is identical to the Xerox Internet Datagram Protocol (IDP) [3]. The socket address space authority is administered by Novell.

NetWareのプロトコルスイートの他の部分には変更が加えられていますが、IPXはXerox Internet Datagram Protocol（IDP）[3]と同一です。ソケットアドレス空間の管理権限はNovellが持っています。

The use of SNMP over the UDP transport [4] is today the common mode of operation in the Internet. This specification may be appropriate for some environments in which UDP transport services are not available. SNMP implementors should be aware that the choice of underlying transport may have a significant impact on the interoperability and ubiquity of the management capability in the Internet. Considerations relevant to choosing a transport for use with SNMP are described in [5].

今日のインターネットでは、UDPトランスポート[4]上でSNMPを使用するのが一般的な運用形態です。この仕様は、UDPトランスポートサービスが利用できない一部の環境に適している場合があります。SNMPの実装者は、下位のトランスポートの選択が、インターネットにおける管理能力の相互運用性と普遍性に大きな影響を与える可能性があることに注意すべきです。SNMPで使用するトランスポートの選択に関する考慮事項は[5]で説明されています。

2. Specification

2. 仕様

SNMP packets will always set the Packet Type field in the IPX header to 4 (i.e., Packet Exchange Packet).

SNMPパケットでは、IPXヘッダーのPacket Typeフィールドを常に4（つまり、Packet Exchange Packet）に設定します。

2.1. Socket Assignments

2.1. ソケットの割り当て

SNMP protocol entities will receive GetRequest-PDU, GetNextRequest-PDU, and SetRequest-PDU messages on socket 36879 (Destination Socket field set to hexadecimal 900F), and Trap-PDU messages on socket 36880 (Destination Socket field set to hexadecimal 9010).

SNMPプロトコルエンティティーは、GetRequest-PDU、GetNextRequest-PDU、SetRequest-PDUのメッセージをソケット36879（Destination Socketフィールドを16進数の900Fに設定）で受信し、Trap-PDUのメッセージをソケット36880（Destination Socketフィールドを16進数の9010に設定）で受信します。

GetResponse-PDU messages will be addressed to the IPX address and socket from which the corresponding GetRequest-PDU, GetNextRequest-PDU, or SetRequest-PDU originated.

GetResponse-PDUのメッセージは、対応するGetRequest-PDU、GetNextRequest-PDU、またはSetRequest-PDUの送信元のIPXアドレスとソケットに宛てて送信されます。

2.2. Maximum Packet Length

2.2. 最大パケット長

Although SNMP does not require conformant implementations to accept messages whose length exceed 484 bytes, it is recommended that implementations support a maximum SNMP message size of 546 bytes (the maximum size allowed under IPX). Furthermore, this limit is the maximum packet length guaranteed to traverse IPX routers which do not provide fragmentation. Implementors may choose to use longer packet lengths if the maximum is known, which depends on the intermediate routers and/or intermediate datalink layer protocols.

SNMPは、準拠した実装に対して484バイトを超える長さのメッセージを受け入れることを要求していませんが、実装はSNMPメッセージの最大サイズとして546バイト（IPXで許容される最大サイズ）をサポートすることを推奨します。さらに、この上限は、フラグメンテーションを提供しないIPXルーターを通過できることが保証される最大パケット長です。最大値がわかっている場合、実装者はより長いパケット長を使用することを選択してもかまいません。この最大値は、中間のルーターや中間のデータリンク層プロトコルに依存します。

2.3. The agent-addr Field for the Trap-PDU

2.3. Trap-PDUのagent-addrフィールド

The agent-addr field in a Trap-PDU emitted by an SNMP agent should contain the IpAddress 0.0.0.0. An SNMP manager may ascertain the source of the trap by querying the transport layer.

SNMPエージェントが送出するTrap-PDUのagent-addrフィールドには、IpAddress 0.0.0.0を含めるべきです。SNMPマネージャーは、トランスポート層に問い合わせることで、トラップの送信元を確認できます。

2.4. IPX Transport Address Representation

2.4. IPXトランスポートアドレスの表現

There are occasions when it is necessary to represent a transport service address in a MIB. For instance, the SNMP party MIB [6] uses an OBJECT IDENTIFIER to define the transport domain (IP, IPX, etc.) and an OCTET STRING to represent an address within that domain. The following definitions are provided for use in such a scheme.

MIBの中でトランスポートサービスのアドレスを表現する必要がある場合があります。たとえば、SNMPパーティーMIB[6]は、トランスポートドメイン（IP、IPXなど）を定義するためにOBJECT IDENTIFIERを使用し、そのドメイン内のアドレスを表現するためにOCTET STRINGを使用します。以下の定義は、このような方式で使用するために提供されます。

RFC1298-MIB DEFINITIONS ::= BEGIN

   IMPORTS
     enterprises         FROM RFC1155-SMI;

     novell              OBJECT IDENTIFIER ::= { enterprises 23 }
     transportDomains    OBJECT IDENTIFIER ::= { novell 7 }

     ipxTransportDomain  OBJECT IDENTIFIER ::= { transportDomains 1 }

   -- Authoritatively names the IPX Transport Domain

   IpxTransportAddress ::= OCTET STRING (SIZE (12))

   -- A textual convention denoting a transport service address in
   -- the ipxTransportDomain.  An IpxTransportAddress is 12 octets
   -- long and comprises 3 fields, each in network-byte (high-low)
   -- order.

   -- The first field is 4 octets long and contains the network
   -- number.

   -- The next field is 6 octets long and contains the physical
   -- address of the node.  Since IPX can run over a variety of
   -- subnet architectures, the physical node address may not
   -- require all 6 octets.  As specified in [2], the physical
   -- node address will occupy the least significant portion of
   -- the field and the most significant octets should be set
   -- to zero.

   -- The last field is 2 octets long and contains the socket
   -- number.

END
