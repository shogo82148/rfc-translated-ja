RFC 704

IMP/Host and Host/IMP Protocol Change

RFC 704

IMP/HostおよびHost/IMPプロトコルの変更

Abstract

概要

This note is a revision of RFC 687 and sketches the design of an expansion to the IMP/host and host/IMP protocol which will include among other things the possibility of addressing hosts on more than 63 IMPs. Our intention in this expansion is to correct certain existing limits without fundamental changes in the philosophy of the IMP/host protocol; i.e., while many issues which would represent fundamental changes to the IMP/host protocol are presently under discussion in the world-wide packet-switching community, we are not able to undertake massive fundamental changes on a time scale compatible with the short term needs for network improvement (e.g., already there are 62 IMPs).

このノートはRFC 687の改訂版であり、IMP/hostおよびhost/IMPプロトコルの拡張の設計を概説します。この拡張には、とりわけ、63を超えるIMP上のホストをアドレス指定できるようにすることが含まれます。この拡張における私たちの意図は、IMP/hostプロトコルの基本思想を根本的に変えることなく、既存のいくつかの制限を是正することです。すなわち、IMP/hostプロトコルの根本的な変更となる多くの問題が、現在、世界中のパケット交換コミュニティーで議論されていますが、ネットワーク改善の短期的な必要性に見合う時間スケールで大規模な根本的変更に取り組むことはできません（たとえば、すでにIMPは62台あります）。

The following paragraphs cover each of the major characteristics of the expanded protocol. A knowledge of Section 3 of BBN Report 1822 is assumed. As is discussed below, the expanded protocol is backwards compatible.

以下の段落では、拡張されたプロトコルの主な特徴をそれぞれ取り上げます。BBN Report 1822のセクション3の知識があることを前提とします。後述するように、拡張されたプロトコルは後方互換です。

1. Expanded Leader Size. The leader will be expanded from two to six 16-bit words. This will provide space for necessary field expansions and additions. The expansion of the IMP/host (host/IMP) leader to 96 bits from 32 causes word-boundary problems for some hosts. To be able to deliver messages between two hosts of which one is using the old protocol and the other the new, without shifting the data in the IMP words, it is necessary that the data (i.e. the first bit of the host/host leader) start at an even multiple of 8-bit bytes from the beginning of the entire message. On the other hand, each host prefers (in fact requires, if no shifting is to be performed by the host) that the combined host/IMP (IMP/host) and host/host leaders occupy some integral number of machine words (defined as the smallest sequence of bits that can be independently accessed by the host/IMP interface). With a total host/IMP (IMP/host) and host/host leader of 136 bits, only machines with 8-, 16-, 32-, and 64-bit words will find the leader size suitable. To simplify things for machines with other word lengths, a provision of the protocol permits each host to tell its IMP a number of 16-bit padding words to be inserted between the host/IMP (IMP/host) and host/host leaders. This padding will be stripped off during host-to-IMP processing by the IMP, and added in during IMP-to-host processing. Thus, for instance, 24-bit machines can specify one 16-bit word of padding, and 10- and 36-bit machines can specify five 16-bit words.

1. リーダーサイズの拡張。リーダー（leader）は、16ビットワード2個から6個に拡張されます。これにより、必要なフィールドの拡張と追加のための領域が確保されます。IMP/host（host/IMP）リーダーを32ビットから96ビットに拡張すると、一部のホストではワード境界の問題が生じます。一方が古いプロトコルを、もう一方が新しいプロトコルを使っている2つのホストの間で、IMPのワード内のデータをシフトせずにメッセージを配送できるようにするには、データ（すなわちhost/hostリーダーの最初のビット）が、メッセージ全体の先頭から8ビットバイトのちょうど倍数の位置から始まる必要があります。他方、各ホストは、host/IMP（IMP/host）リーダーとhost/hostリーダーを合わせたものが整数個のマシンワード（host/IMPインターフェイスが独立にアクセスできる最小のビット列として定義されます）を占めることを好みます（ホストがシフトを行わない場合には、実際にそれが必要です）。host/IMP（IMP/host）リーダーとhost/hostリーダーの合計が136ビットの場合、このリーダーサイズが適しているのは、ワード長が8、16、32、64ビットのマシンだけです。それ以外のワード長のマシンのために、このプロトコルには、host/IMP（IMP/host）リーダーとhost/hostリーダーの間に挿入する16ビットのパディングワードの数を、各ホストがIMPに伝えられる規定があります。このパディングは、IMPによるホストからIMPへの処理の際に取り除かれ、IMPからホストへの処理の際に追加されます。したがって、たとえば24ビットのマシンは16ビットワード1個分のパディングを指定でき、10ビットと36ビットのマシンは16ビットワード5個分を指定できます。

2. Expanded Address field. The address field will be expanded to 32 bits, 16 bits of IMP address, 0 bits of host address, and 8 bits for (future) network address. This expansion is adequate for any forseeable ARPA Network growth.

2. アドレスフィールドの拡張。アドレスフィールドは32ビットに拡張され、IMPアドレスに16ビット、ホストアドレスに0ビット、（将来の）ネットワークアドレスに8ビットが割り当てられます。この拡張は、予見できるあらゆるARPAネットワークの成長に十分対応できます。

3. New Message Length Field. A new field will be added which will allow the source host to optionally specify the message length (in bits) to the IMP subnetwork. The IMP subnetwork may be able to use this information (when available) to better utilize network buffer storage. The destination host may also be able to use this information to better utilize its buffer storage. This field will be 16 bits wide. There will be provision for expanding the maximum number of packets per message to 16 from the present 8.

3. 新しいメッセージ長フィールド。送信元ホストがIMPサブネットワークに対してメッセージ長（ビット単位）を任意で指定できるようにする、新しいフィールドを追加します。IMPサブネットワークは、この情報を（利用できる場合に）使って、ネットワークのバッファー記憶領域をより有効に活用できる可能性があります。宛先ホストも、この情報を使って自身のバッファー記憶領域をより有効に活用できる可能性があります。このフィールドは16ビット幅です。また、メッセージあたりの最大パケット数を、現在の8から16に拡張するための規定を設けます。

4. Expanded Handling Type Field. The handling type field which now is used to distinguish between priority and non-priority message streams, etc., will be expanded to eight bits. This expanded field will provide for the possibility of a number of parallel message streams having different handling characteristics between pairs of hosts; e.g., priority, non-priority, varying numbers of packets per message (see below), a message stream requiring guaranteed capacity, etc. Only the old-style priority and non-priority handling types will be available in the initial implementation of the expanded protocol.

4. ハンドリングタイプフィールドの拡張。現在、優先と非優先のメッセージストリームの区別などに使われているハンドリングタイプフィールドを、8ビットに拡張します。この拡張されたフィールドにより、ホストのペア間で、異なる取り扱い特性を持つ複数の並列メッセージストリームを持てるようになります。たとえば、優先、非優先、メッセージあたりのパケット数がさまざまなもの（後述）、保証された容量を必要とするメッセージストリームなどです。拡張されたプロトコルの初期実装で利用できるのは、旧来の優先と非優先のハンドリングタイプだけです。

5. Source Host Control of Packets per Message. The possibility will exist for the source host to specify a message stream which will use a given number of packets per multi-packet message (e.g, two packets per message or five packets per message). Since the IMP network will not have to use eight packet-buffers for reassembly purposes, as at present, this may result in better services for such hosts. This will help users who need both low delay and high throughput. Since this facility is orthogonal to and of lower priority than the address expansion, it will be implemented after the other proposed basic changes.

5. 送信元ホストによるメッセージあたりのパケット数の制御。送信元ホストが、複数パケットからなるメッセージあたりのパケット数を指定したメッセージストリーム（たとえば、メッセージあたり2パケット、あるいはメッセージあたり5パケット）を指定できるようになります。IMPネットワークは、現在のように再組み立てのために8個のパケットバッファーを使う必要がなくなるため、そのようなホストに対してより良いサービスを提供できる可能性があります。これは、低遅延と高スループットの両方を必要とするユーザーの助けになります。この機能はアドレスの拡張とは独立しており、優先度もそれより低いため、他の基本的な変更案の後に実装されます。

6. Unordered (type-3) Message Change. Unordered messages will be indicated by a subtype of the type O message, rather than by a separate message type as at present. This is compatible with the need to check the host access control capabilities of all messages. This will provide a slight backward incompatibility for the three or so hosts which presently use type-3 messages in their research.

6. 順序なし（タイプ3）メッセージの変更。順序なしメッセージは、現在のように別のメッセージタイプで示すのではなく、タイプOメッセージのサブタイプで示すようになります。これは、すべてのメッセージについてホストのアクセス制御能力を確認する必要性と両立します。これにより、現在研究でタイプ3メッセージを使っている3つほどのホストにとっては、わずかに後方互換性が損なわれます。

7. Change in Format of Fake Host Addresses. The For/From IMP bit will be eliminated. The fake host addresses will be the four highest host numbers (e.g., IMP Teletype will be host 252).

7. 疑似ホストアドレスの形式の変更。For/From IMPビットは廃止されます。疑似ホストアドレスは、最も大きい4つのホスト番号になります（たとえば、IMP Teletypeはホスト252になります）。

8. Addition of a Parameter to the IMP to Host NOP. The IMP to host NOP will have added to it a parameter specifying the address (IMP and host number) of the host.

8. IMPからホストへのNOPへのパラメーターの追加。IMPからホストへのNOPに、そのホストのアドレス（IMP番号とホスト番号）を指定するパラメーターが追加されます。

9. Backward Compatibility. The old and new formats will be supported in parallel in the IMPs for the foreseeable future to allow gradual phaseover of host software. A host will be able to specify to its IMP whether the old or new formats are to be used; thus, it will be possible for the host to specify switching back and forth between the two modes for debugging purposes. The specification of the mode to be used will be possible via a proper choice of format in the host to IMP NOP message; the IMP will use the mode of the host to IMP NOP message the IMP has received. Further, a host may select to use either the old or new format without needing to know more about the other format messages than to discard them should they arrive. The IMP will initialize by sending several NOP messages of each type to give the hosts its choice. Although a host not implementing the new format will not be able to address hosts on IMPs with IMP-number greater than 63, the IMPs will wherever possible do the conversion necessary to permit hosts using the old format to communicate with hosts using the new format and the reverse.

9. 後方互換性。ホストのソフトウェアを段階的に移行できるように、予見できる将来にわたって、IMPでは古い形式と新しい形式の両方を並行してサポートします。ホストは、古い形式と新しい形式のどちらを使うかを自身のIMPに指定できるようになります。したがって、ホストはデバッグのために2つのモードを切り替えるよう指定できます。使用するモードの指定は、ホストからIMPへのNOPメッセージの形式を適切に選ぶことで行えます。IMPは、受信したホストからIMPへのNOPメッセージのモードを使用します。さらに、ホストは、もう一方の形式のメッセージについては、到着したら破棄するということ以外に何も知る必要なく、古い形式と新しい形式のどちらかを選んで使用できます。IMPは初期化時に、各タイプのNOPメッセージをいくつか送信して、ホストに選択肢を与えます。新しい形式を実装していないホストは、IMP番号が63を超えるIMP上のホストをアドレス指定できませんが、IMPは、古い形式を使うホストと新しい形式を使うホストが相互に通信できるように、可能な限り必要な変換を行います。

1O. Non-blocking Host Interface. A mechanism will be provided which allows the IMP to refuse a message from a host without blocking the host interface. This mechanism will permit the IMP to gather the necessary resources to send the refused message and then ask the host to resend the message. Finally, the host will be permitted to ask to be able to send a message and be notified when it is possible without requiring the message to actually be sent and refused. Again, as in point 5 above, this facility will be added after the other more basic changes have been implemented.

1O. ノンブロッキングのホストインターフェイス。IMPが、ホストインターフェイスをブロックせずにホストからのメッセージを拒否できるメカニズムを提供します。このメカニズムにより、IMPは、拒否したメッセージを送信するために必要なリソースを集めてから、ホストにメッセージの再送を求めることができます。さらに、ホストは、メッセージを実際に送信して拒否されることなく、メッセージを送信できるかどうかを問い合わせ、送信可能になった時点で通知を受けられるようになります。これも、前述の項目5と同様に、他のより基本的な変更が実装された後に追加されます。

11. Maximum Message Length. The maximum number of bits of data in a single-packet message may be reduced by a few bits.

11. 最大メッセージ長。単一パケットのメッセージに含まれるデータの最大ビット数は、数ビット減る可能性があります。

We are now producing a draft version of the necessary changes to Report 1822 and will circulate it so that host programmers can begin to make their preparations.

現在、Report 1822に必要な変更のドラフト版を作成しており、ホストのプログラマーが準備を始められるように配布する予定です。
