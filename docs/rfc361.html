RFC 361

Deamon Processes on Host 106

RFC 361

Host 106のデーモンプロセス

Abstract

概要

In response to RFCs 347 and 348, ECHO and DISCARD, MIT-DMCG (Host 106) now has deamon processes that will respond to RFCs on sockets 7 and 9.

ECHOとDISCARDに関するRFC 347と348を受けて、MIT-DMCG（Host 106）には、ソケット7と9への接続要求（RFC）に応答するデーモン（deamon）プロセスが用意されました。

A few administrative type decisions were made, to which I would like to solicit comments.

運用上の判断をいくつか下したので、それについてご意見をいただきたいと思います。

First, if our machine is too full to support another deamon process, the pro-offered connection will be refused; that is, a CLS will be sent in response to the RFC on socket 7 or 9. Second, if no activity takes place for two consecutive minutes (no characters received on input, or output blocked waiting for allocation), the connection will be aborted.

第一に、当方のマシンが満杯で、さらにデーモンプロセスを動かせない場合、提示された接続は拒否されます。つまり、ソケット7または9への接続要求（RFC）に対する応答としてCLSが送られます。第二に、2分間続けて何も活動がない場合（入力で文字を1つも受信せず、または出力が割り当て待ちでブロックされている場合）、接続は中断されます。

Does anyone see the need or desirability for the third service in this set: a random character generator? Many systems provide programs like "TTYTST" available over the standard login connection, but there would be no difficulty in creating a server connection (like ECHO) offering just this limited service. I'm sure that it would be useful for new NCPs, as well as statistics gathering.

この一連のサービスに、3つめとしてランダム文字生成器を加える必要性や価値があると考える方はいますか？多くのシステムは「TTYTST」のようなプログラムを標準のログイン接続経由で利用できるようにしていますが、この限られたサービスだけを提供するサーバー接続を（ECHOのように）作るのは難しくないはずです。新しいNCPにとっても、統計の収集にとっても役立つと確信しています。
