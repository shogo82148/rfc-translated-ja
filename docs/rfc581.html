RFC 581

Corrections to RFC 560: Remote Controlled Transmission & Echoing TELNET Option

RFC 581

RFC 560の訂正: リモート制御送信およびエコーのTelnetオプション

Abstract

概要

[This RFC contains corrections to RFC 560 (NIC -- 18492,) which described the Remote Controlled Transmission and Echoing TELNET Option. A completely updated version of 18492 has been journalized and will be included in the Protocols Notebook. These new specifications for RCTE are in NIC document (19859,).]

[このRFCは、リモート制御送信およびエコー（Remote Controlled Transmission and Echoing）のTELNETオプションを記述したRFC 560（NIC -- 18492,）に対する訂正を含みます。18492を全面的に更新した版はJournalに登録済みで、プロトコルノートブック（Protocols Notebook）に収録される予定です。RCTEのこの新しい仕様は、NIC文書（19859,）にあります。]

Section 1 of the RCTE Option specification (18492,2a:gy) was supposed to include the name and code for the option. The code was accidentally left out. That statement should read:

RCTEオプション仕様のセクション1（18492,2a:gy）には、オプションの名前とコードが含まれているはずでした。コードが誤って抜け落ちていました。その記述は次のようになるべきです。

   RCTE  7

   RCTE  7

Section 2 should include the End of Subnegotiation Parameter, at the end of the subnegotiation parameter specification (18492,2b5:gy). All examples in the option specifications, showing RCTE SB commands, should also show the IAC SE parameter. (The revised RCTE specifications have been so changed.) Section 2 should be changed so that it reads:

セクション2では、サブネゴシエーションパラメーターの仕様（18492,2b5:gy）の末尾に、サブネゴシエーション終了（End of Subnegotiation）パラメーターを含めるべきです。オプション仕様の中でRCTE SBコマンドを示している例もすべて、IAC SEパラメーターを示すべきです（改訂版のRCTE仕様ではそのように変更済みです）。セクション2は次のように変更すべきです。

   IAC SB RCTE <cmd> [BC1 BC2] [TC1 TC2] IAC SE

   IAC SB RCTE <cmd> [BC1 BC2] [TC1 TC2] IAC SE

The sample scenario, in Section 5.D (18492,2e4:gy), should be modified to reflect the kind of asynchrony of events that can occur with the RCTE protocol. The updated RCTE specifications (in -- 19859,1e4:gy) now reflects this.

セクション5.D（18492,2e4:gy）のシナリオ例は、RCTEプロトコルで起こりうる事象の非同期性を反映するように修正すべきです。更新されたRCTE仕様（-- 19859,1e4:gy）は、現在これを反映しています。

In RFC 563 (18755,) John Davidson criticizes RCTE's apparent failure to allow Net I/O and server computation to overlap.

RFC 563（18755,）で、John Davidsonは、RCTEではネットワーク入出力とサーバーの計算を並行して行えないように見えることを批判しています。

I agree with John's criticisms and feel that the following should fix the problem:

私はJohnの批判に同意し、次の変更で問題が解決するはずだと考えています。

  1. Change 5.A (18492,2e1)

    from:

    Overview of Interaction

    to:

    Overview of User Terminal Printing Action & Control

  2. Change 5.B.5.a (18492,2e2e1)

    from:

    A Transmission character is one which REQUIRES the User Host to transmit all text accumulated up to and including its occurrence. (For Net efficiency, User hosts are DISCOURAGED from sending before the occurrence of a Transmission character).

    to:

    A Transmission character is one which RECOMMENDS that the Using Host transmit all text accumulated up to and including its occurrence. (For Net efficiency, Using hosts are DISCOURAGED from sending before the occurrence of a Transmission character, as defined at the moment the character is typed).

  3. Change 5.B.5.b (18492,2e2e2)

    from:

    A Break character has the effect of a Transmission character, but also causes the Using host to stop its print/discard action upon the User's input text, until directed to do otherwise by another IAC SB RCTE <cmd> IAC SE command from the Serving host. Break characters therefore define printing units. "Break character" as used in this document does NOT mean Telnet Break character.

    to:

    A Break character REQUIRES that the Using host transmit all text accumulated up to and including its occurrence and also causes the Using host to stop its print/discard action upon the User's input text, until directed to do otherwise by another IAC SB RCTE <cmd> IAC SE command from the Serving host. Break characters therefore define printing units. "Break character" as used in this document does NOT mean Telnet Break character.

  4. Change 5.B.6 (18492,2e2f)

    from:

    Input from the terminal is (hopefully) buffered up to the occurrence of a Transmission or Break character; and the input text is echoed or not echoed, up to the occurrence of a Break Character. The most recent RCTE command determines the echo, Transmission and Break actions.

    to:

    Input from the terminal is (hopefully) buffered into units ending with a Transmission or Break character; and echoing of input text is suspended after the occurrence of a Break Character and until receipt of a Break Reset command from the Serving host. The most recent RCTE Break reset command determines the Break actions.

  5. Change 5.C.4 (18492,2e3d)

    FROM:

    A severe (User) site-dependent problem will be buffering type-ahead input from the terminal. It is possible, especially in the case of TIPS, that the input buffer will overflow often. If the receiving (serving) host will permit, the accumulated text should be transmitted at this point. If the text cannot be transmitted and further typing by the user will result in lost text, the user should be notified.

    to:

    Buffering Problems and Transmission vs. Printing Constraints:

    There are NO mandatory transmission constraints. The Using host is allowed to send a character a time, though this would be a waste of RCTE. The Transmission Classes commands are GUIDELINES, so deviating from them, as when the User's buffer gets full, is allowed.

    Additionally, the Using host may send a Break Class character, without knowing that it is one (as with type-ahead).

    The problem with buffering occurs when printing on the user's terminal must be suspended, after the user has typed a currently valid Break Character and until a Break Reset command is received from the serving host. During this time, the user may be typing merrily along. The text being typed may be SENT, but may not yet be PRINTED.

    The more standard problem of filling the transmission buffer, while awaiting an ALLOC from the Serving host, may also occur, but this problem is well known to implementors and in no way special to RCTE.

    In any case, when the buffer does fill and further text typed by the user will be lost, the user should be notified.

  6. And add 5.C.5, 5.C.6, 5.C.7, 5.C.8, and 5.C.9 as follows:

    1. The Serving and Using hosts must carefully synchronize Break Class Reset commands with the transmission of Break characters. Except at the beginning of an interaction, the Serving host MAY ONLY send a Break Reset command in response to the User host's having sent a Break character as defined at that time. This should establish a one-to-one correspondence between them. (A <cmd> value of zero, in this context, is interpreted as a Break Classes reset to the same class(es) as before.) The Reset command may be preceded by terminal output.

    2. Text should be buffered by the User host until the user types a character which belongs to the transmission class in force at THE MOMENT THE CHARACTER IS TYPED.

    3. Transmission Class Reset commands may be sent by the Serving host at ANY TIME. If they are frequently sent separate from Break Class Reset commands, it will probably be better to exit from RCTE and enter regular character at a time transmission.

    4. It is not immediately clear what the Using host should do with currently buffered text, when a Transmission Classes Reset command is received. The buffering is according to the previous Transmission Classes scheme.

      The Using host clearly should NOT simply wait until a Transmission character (according to the new scheme) is typed.

      Either the buffered text should be rescanned, under the new scheme;

      Or the buffered text should simply be sent as a group. This is the simpler approach, and probably quite adequate.

    5. It is possible to define NO BREAK CHARACTERS except TELNET commands (IAC ...). This might actually be useful, as in the case of transmitting on carriage-return, with the Using host echoing (a controlled half-duplex).

      Having the using host send a Telnet Command will allow the serving host to know when he may reset the Break classes, but the mechanism is awkward and probably should be avoided.

  1. 5.A（18492,2e1）を変更します。

    変更前:

    やりとりの概要

    変更後:

    ユーザー端末の印字動作と制御の概要

  2. 5.B.5.a（18492,2e2e1）を変更します。

    変更前:

    送信文字（Transmission character）とは、その文字までの（その文字を含む）蓄積されたすべてのテキストを送信することをユーザーホストに要求する（REQUIRES）文字です（ネットワークの効率のため、ユーザーホストが送信文字の出現より前に送信することは推奨しません（DISCOURAGED））。

    変更後:

    送信文字（Transmission character）とは、その文字までの（その文字を含む）蓄積されたすべてのテキストを送信することを利用側ホスト（Using Host）に推奨する（RECOMMENDS）文字です（ネットワークの効率のため、利用側ホストが送信文字の出現より前に送信することは推奨しません（DISCOURAGED）。ここでの送信文字は、その文字が入力された時点での定義に従います）。

  3. 5.B.5.b（18492,2e2e2）を変更します。

    変更前:

    ブレーク文字（Break character）は、送信文字と同じ効果を持ちますが、さらに、サービス側ホスト（Serving host）から別のIAC SB RCTE <cmd> IAC SEコマンドで別の指示があるまで、ユーザーの入力テキストに対する印字／破棄の動作を利用側ホストに停止させます。したがって、ブレーク文字は印字の単位を定めます。この文書で使う「ブレーク文字」は、TelnetのBreak文字を意味するものではありません（NOT）。

    変更後:

    ブレーク文字（Break character）は、その文字までの（その文字を含む）蓄積されたすべてのテキストを送信することを利用側ホストに要求し（REQUIRES）、さらに、サービス側ホストから別のIAC SB RCTE <cmd> IAC SEコマンドで別の指示があるまで、ユーザーの入力テキストに対する印字／破棄の動作を利用側ホストに停止させます。したがって、ブレーク文字は印字の単位を定めます。この文書で使う「ブレーク文字」は、TelnetのBreak文字を意味するものではありません（NOT）。

  4. 5.B.6（18492,2e2f）を変更します。

    変更前:

    端末からの入力は、送信文字またはブレーク文字が出現するまで（できれば）バッファリングされます。また、入力テキストは、ブレーク文字が出現するまで、エコーされるかエコーされないかのどちらかです。直近のRCTEコマンドが、エコー、送信、ブレークの動作を決定します。

    変更後:

    端末からの入力は、送信文字またはブレーク文字で終わる単位に（できれば）バッファリングされます。また、入力テキストのエコーは、ブレーク文字が出現した後、サービス側ホストからブレークリセット（Break Reset）コマンドを受信するまで中断されます。直近のRCTEのブレークリセットコマンドが、ブレークの動作を決定します。

  5. 5.C.4（18492,2e3d）を変更します。

    変更前:

    （ユーザー）サイトに依存する深刻な問題は、端末からの先行入力（type-ahead）のバッファリングでしょう。特にTIPの場合は、入力バッファーが頻繁にあふれる可能性があります。受信側（サービス側）ホストが許可するなら、この時点で蓄積されたテキストを送信すべきです。テキストを送信できず、ユーザーがさらに入力するとテキストが失われる場合は、ユーザーに通知すべきです。

    変更後:

    バッファリングの問題と、送信と印字の制約:

    送信に関する必須の制約はありません（NO）。利用側ホストは1文字ずつ送信してもかまいませんが、それではRCTEが無駄になります。送信クラス（Transmission Classes）コマンドは指針（GUIDELINES）なので、ユーザーのバッファーが一杯になったときなどに、それから外れることは許されます。

    さらに、利用側ホストは、ブレーククラスの文字を、それがブレーククラスの文字だと知らずに送信することがあります（先行入力の場合など）。

    バッファリングの問題が起こるのは、ユーザーが現在有効なブレーク文字を入力した後、サービス側ホストからブレークリセットコマンドを受信するまで、ユーザーの端末への印字を中断しなければならない場合です。この間、ユーザーは楽しげに入力を続けているかもしれません。入力中のテキストは、送信（SENT）されてもかまいませんが、まだ印字（PRINTED）されてはなりません。

    サービス側ホストからのALLOCを待つ間に送信バッファーが一杯になるという、より一般的な問題も起こるかもしれませんが、この問題は実装者にはよく知られており、RCTEに特有のものではまったくありません。

    いずれにせよ、バッファーが一杯になり、ユーザーがさらに入力したテキストが失われる場合は、ユーザーに通知すべきです。

  6. さらに、5.C.5、5.C.6、5.C.7、5.C.8、5.C.9を次のように追加します。

    1. サービス側ホストと利用側ホストは、ブレーククラスリセット（Break Class Reset）コマンドとブレーク文字の送信を慎重に同期させなければなりません。やりとりの開始時を除き、サービス側ホストがブレークリセットコマンドを送信してよいのは、その時点で定義されているブレーク文字をユーザーホストが送信したことへの応答としてのみ（MAY ONLY）です。これにより、両者の間に1対1の対応が確立されるはずです（この文脈では、<cmd>の値0は、以前と同じクラスへのブレーククラスのリセットと解釈されます）。リセットコマンドの前に端末出力があってもかまいません。

    2. ユーザーホストは、ユーザーが送信クラスに属する文字を入力するまで、テキストをバッファリングすべきです。ここでの送信クラスは、その文字が入力された時点（THE MOMENT THE CHARACTER IS TYPED）で有効なものです。

    3. サービス側ホストは、送信クラスリセット（Transmission Class Reset）コマンドをいつでも（ANY TIME）送信してかまいません。ブレーククラスリセットコマンドとは別に頻繁に送信するのであれば、RCTEを終了して通常の1文字ずつの送信に入るほうがおそらくよいでしょう。

    4. 送信クラスリセットコマンドを受信したときに、現在バッファリングしているテキストを利用側ホストがどう扱うべきかは、すぐには明らかではありません。バッファリングは以前の送信クラスの方式に従って行われています。

      利用側ホストが、（新しい方式による）送信文字が入力されるまで単に待つべきでない（NOT）ことは明らかです。

      バッファリングしたテキストを新しい方式で再走査するか、

      バッファリングしたテキストを単にひとまとめに送信するかのどちらかにすべきです。後者のほうが単純な方法で、おそらくそれで十分です。

    5. TELNETコマンド（IAC ...）以外にブレーク文字を定義しない（NO BREAK CHARACTERS）ことも可能です。これは、利用側ホストがエコーを行いながら（制御された半二重）、復帰（carriage-return）で送信する場合などに、実際に役立つかもしれません。

      利用側ホストにTelnetコマンドを送信させれば、サービス側ホストはいつブレーククラスをリセットしてよいかを知ることができますが、この仕組みは扱いにくく、おそらく避けるべきです。
