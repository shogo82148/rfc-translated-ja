RFC 381

Three Aids To Improved Network Operation

RFC 381

ネットワーク運用を改善するための3つの方策

1. Scheduled Software Maintenance

1. 定期的なソフトウェア保守

As the ARPA Network has grown larger, we have found it difficult to find times when necessary new software can be slipped into the network without disrupting anyone. For instance, there is always intrasite traffic between the machines at MIT, and there is almost always traffic between the AMES TIP and IMP--the sun never sets on the ARPA Network. To minimize unscheduled disruptions and to simultaneously let us do what we have to do, we propose to schedule 7 A.M. - 8 A.M. eastern time every Tuesday as a time when the IMPs can be reloaded. We will probably not use this period every Tuesday, but we do reserve this period every Tuesday. The above period is in addition to the several hours a month already scheduled at each site for hardware preventative maintenance.

ARPAネットワークが大きくなるにつれ、誰にも迷惑をかけずに必要な新しいソフトウェアをネットワークに入れられる時間を見つけるのが難しくなってきました。たとえば、MITのマシン間には常にサイト内のトラフィックがあり、AMESのTIPとIMPの間にもほぼ常にトラフィックがあります。ARPAネットワークに日が沈むことはないのです。予定外の中断を最小限に抑えつつ、同時に私たちがしなければならない作業を行えるように、毎週火曜日の東部時間午前7時から午前8時を、IMPを再ロードできる時間として予定することを提案します。毎週火曜日にこの時間帯を使うことはおそらくありませんが、毎週火曜日にこの時間帯を確保しておきます。この時間帯は、ハードウェアの予防保守のために各サイトですでに予定されている月数時間とは別のものです。

Because a network user may not know when his machine is scheduled for maintenance or because he may forget and work through the Tuesday morning software period, we propose to generalize the IMP-Going-Down IMP-to-Host control message so it may be used to remind the user. This message (described in detail below) will contain information that the IMP is going down in m times five minutes, for n times 5 minutes, for a given reason. Hosts (and the TIP) should use this information to remind all their Network users that the IMP will be going down after the stated interval.

ネットワークのユーザーは、自分のマシンの保守がいつ予定されているかを知らないかもしれませんし、火曜日の朝のソフトウェア保守の時間帯であることを忘れて作業を続けてしまうかもしれません。そこで、IMPからホストへの制御メッセージであるIMP-Going-Downを一般化して、ユーザーに注意を促すために使えるようにすることを提案します。このメッセージ（詳細は後述）には、IMPがある理由により、5分のm倍の時間が経過した後に、5分のn倍の時間にわたって停止するという情報が含まれます。ホスト（およびTIP）は、この情報を使って、指定された時間が経過した後にIMPが停止することを、そのすべてのネットワークユーザーに知らせるべきです。

Occasionally there is an emergency reason for restarting or reloading an IMP. For instance, while three Hosts at a site are functioning well, one Host cannot communicate with the IMP. This sort of situation sometimes requires the IMP to be restarted. Such a restart will be preceded by several minutes by an IMP-Going-Down Message to allow working users to save their work in such a way that they can restart once the IMP is back up.

ときには、緊急の理由でIMPを再起動または再ロードすることがあります。たとえば、あるサイトの3つのホストは正常に機能しているのに、1つのホストがIMPと通信できないような場合です。このような状況では、IMPの再起動が必要になることがあります。そのような再起動の数分前には、IMP-Going-Downメッセージが送られます。これにより、作業中のユーザーは、IMPが復旧したときに作業を再開できるように、作業内容を保存できます。

In both of these cases, as well as cases where an IMP is performing so poorly that is must be shut down quickly, a type 2 IMP-to-HOST message will be transmitted to the HOST about 30 seconds before the IMP goes down. Finally, of course, there may be occasions when the IMP crashes so quickly that no warning is given, but the IMP will never be intentionally shut down in this way.

これら両方の場合や、IMPの動作が非常に悪いためにすぐに停止しなければならない場合には、IMPが停止する約30秒前に、タイプ2のIMPからホストへのメッセージがホストに送信されます。最後に、もちろん、IMPが警告を出す間もなくクラッシュすることもありえますが、IMPを意図的にこのような形で停止することは決してありません。

2. IMP-to-Host Communication

2. IMPからホストへの通信

There have long been complaints that the IMP-to-Host error messages were not precise enough or were just plain ambiguous. In RFC #312 we proposed some additional error messages. These and other IMP-to-Host message changes will be made on August 14, 1972 and we encourage Hosts to modify their NCP's as appropriate by then. Unmodified NCPs will probably continue to work after this change, but each site should look into this question carefully. The table below lists all the IMP-to-Host messages and clearly indicates the changes which will be made.

IMPからホストへのエラーメッセージは十分に正確でない、あるいは単純にあいまいだという苦情が以前からありました。RFC #312で、私たちはいくつかのエラーメッセージの追加を提案しました。これらの変更と、IMPからホストへのメッセージに関するその他の変更は、1972年8月14日に行われます。ホストは、それまでに必要に応じてNCPを修正することをお勧めします。修正していないNCPも、この変更の後もおそらく動作し続けますが、各サイトはこの問題を注意深く検討すべきです。下の表は、IMPからホストへのすべてのメッセージを一覧にし、行われる変更をはっきりと示しています。

これらの変更は、次のようにまとめられます。

  3. Message type 10 has been added.
  4. Message types 3 and 6 have been discarded.

3. Network News Service

3. ネットワークニュースサービス

We have instituted a Network news service. TIP users get the news by typing the TIP command @NEWS. Users of other Host can get the news by ICPing to socket 15600031 (octal) at the BBN Tenex.

私たちはネットワークニュースサービスを開始しました。TIPのユーザーは、TIPコマンド@NEWSを入力することでニュースを入手できます。その他のホストのユーザーは、BBNのTenexのソケット15600031（8進数）にICPすることでニュースを入手できます。

If you have further suggestions for improving the operation of the Network, we request your comments.

ネットワークの運用を改善するためのさらなる提案があれば、コメントをお寄せください。
