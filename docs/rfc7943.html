RFC 7943

A Method for Generating Semantically Opaque Interface Identifiers (IIDs) with the Dynamic Host Configuration Protocol for IPv6 (DHCPv6)

RFC 7943

IPv6向け動的ホスト構成プロトコル（DHCPv6）を用いて意味的に不透明なインターフェイス識別子（IID）を生成する方法

Abstract

概要

This document describes a method for selecting IPv6 Interface Identifiers that can be employed by Dynamic Host Configuration Protocol for IPv6 (DHCPv6) servers when leasing non-temporary IPv6 addresses to DHCPv6 clients. This method is a DHCPv6 server-side algorithm that does not require any updates to the existing DHCPv6 specifications. The aforementioned method results in stable addresses within each subnet, even in the presence of multiple DHCPv6 servers or DHCPv6 server reinstallments. It is a DHCPv6 variant of the method specified in RFC 7217 for IPv6 Stateless Address Autoconfiguration.

この文書は、IPv6向け動的ホスト構成プロトコル（DHCPv6）サーバーがDHCPv6クライアントに非一時IPv6アドレスをリースする際に使用できる、IPv6インターフェイス識別子の選択方法を説明します。この方法は、既存のDHCPv6仕様の更新を一切必要としない、DHCPv6サーバー側のアルゴリズムです。前述の方法では、複数のDHCPv6サーバーが存在する場合やDHCPv6サーバーを再インストールした場合でも、各サブネット内で安定したアドレスが得られます。これは、IPv6ステートレスアドレス自動設定向けにRFC 7217で規定された方法のDHCPv6版です。

IESG Note

IESG注記

A predecessor to this document was earlier a working group document in the DHC WG. The WG decided to stop further work in this area because such work was not considered useful.

この文書の前身は、以前はDHCワーキンググループのワーキンググループ文書でした。このワーキンググループは、この分野の作業は有用ではないと考えられたため、これ以上の作業を中止することを決定しました。

The proposal described in this document has an unaddressed failure case that makes it unsuitable for use as the mechanism to provide the claimed failover features for DHCPv6 servers. Specifically, when a DHCPv6 client DECLINEs a provided address there is no recovery mechanism described that will result in the DHCPv6 client obtaining a working IPv6 address.

この文書で説明する提案には未対処の障害ケースがあり、DHCPv6サーバーについて主張されているフェイルオーバー機能を提供するメカニズムとして使用するには不適切です。具体的には、DHCPv6クライアントが提供されたアドレスをDECLINEした場合に、DHCPv6クライアントが動作するIPv6アドレスを取得できるようになる回復メカニズムが説明されていません。

1. Introduction

1. はじめに

The benefits of stable IPv6 addresses are discussed in [RFC7721]. Providing address stability across server reinstallations or when a database of previous DHCPv6 address leases is unavailable is of use not only when a DHCPv6 server must be reinstalled or the address-lease database becomes corrupted, but is also of use when implementation constraints (e.g., a DHCPv6 server implementation on an embedded device) make it impossible for a DHCPv6 server implementation to maintain a database of previous DHCPv6 address leases. Additionally, [RFC7031] describes scenarios where multiple DHCPv6 servers are required to run in such a way as to provide increased availability in case of server failures.

安定したIPv6アドレスの利点については[RFC7721]で議論されています。サーバーの再インストールをまたいで、あるいは以前のDHCPv6アドレスリースのデータベースが利用できない場合にアドレスの安定性を提供することは、DHCPv6サーバーを再インストールしなければならない場合やアドレスリースのデータベースが破損した場合に役立つだけでなく、実装上の制約（例: 組み込み機器上のDHCPv6サーバー実装）により、DHCPv6サーバー実装が以前のDHCPv6アドレスリースのデータベースを維持できない場合にも役立ちます。さらに、[RFC7031]は、サーバー障害時の可用性を高めるように複数のDHCPv6サーバーを動作させる必要があるシナリオを説明しています。

This document describes a method for selecting IPv6 Interface Identifiers that can be employed by DHCPv6 servers when leasing non-temporary IPv6 addresses to DHCPv6 clients (i.e., to be employed with IA_NA options). This method is a DHCPv6 server-side algorithm that does not require any updates to the existing DHCPv6 specifications. The aforementioned method has the following properties:

この文書は、DHCPv6サーバーがDHCPv6クライアントに非一時IPv6アドレスをリースする際（すなわち、IA_NAオプションで使用する場合）に使用できる、IPv6インターフェイス識別子の選択方法を説明します。この方法は、既存のDHCPv6仕様の更新を一切必要としない、DHCPv6サーバー側のアルゴリズムです。前述の方法には次の特性があります。

  • The resulting IPv6 addresses remain stable within each subnet for the same network interface of the same client, even when different DHCPv6 servers (implementing this specification) are employed.
  • Predicting the IPv6 addresses that will be generated by the method specified in this document, even with knowledge of the IPv6 addresses generated for other nodes within the same network, becomes very difficult.
  • 結果として得られるIPv6アドレスは、（この仕様を実装した）異なるDHCPv6サーバーを使用する場合でも、同じクライアントの同じネットワークインターフェイスに対して、各サブネット内で安定したままです。
  • 同じネットワーク内の他のノード向けに生成されたIPv6アドレスを知っていたとしても、この文書で規定する方法によって生成されるIPv6アドレスを予測することは非常に困難になります。

The method specified in this document achieves the aforementioned properties by means of a calculated technique as opposed to, e.g., state sharing among DHCPv6 servers. This approach has already been suggested in [RFC7031]. We note that the method described in this document is essentially a DHCPv6 version of the "Method for Generating Semantically Opaque Interface Identifiers with IPv6 Stateless Address Autoconfiguration (SLAAC)" specified in [RFC7217].

この文書で規定する方法は、たとえばDHCPv6サーバー間での状態の共有ではなく、計算による手法によって前述の特性を実現します。このアプローチは、すでに[RFC7031]で提案されています。なお、この文書で説明する方法は、本質的には[RFC7217]で規定された「IPv6ステートレスアドレス自動設定（SLAAC）を用いて意味的に不透明なインターフェイス識別子を生成する方法（Method for Generating Semantically Opaque Interface Identifiers with IPv6 Stateless Address Autoconfiguration (SLAAC)）」のDHCPv6版です。

2. Applicability and Design Goals

2. 適用範囲と設計目標

This document simply describes one possible approach for selecting IPv6 Interface Identifiers to be employed by DHCPv6 servers when leasing non-temporary IPv6 addresses to DHCPv6 clients, with the following properties:

この文書は、DHCPv6サーバーがDHCPv6クライアントに非一時IPv6アドレスをリースする際に使用するIPv6インターフェイス識別子を選択するための、次の特性を持つアプローチの1つを説明するにすぎません。

  • The resulting IPv6 addresses remain stable within each subnet for the same network interface of the same client.
  • The resulting IPv6 addresses cannot be predicted by an attacker without knowledge of a secret key.
  • The resulting IPv6 addresses remain stable across DHCPv6 server reinstallations, or even if a database of previous DHCPv6 address leases is not available.
  • The resulting IPv6 addresses remain stable when different DHCPv6 servers (implementing this specification) are employed on the same network.
  • 結果として得られるIPv6アドレスは、同じクライアントの同じネットワークインターフェイスに対して、各サブネット内で安定したままです。
  • 結果として得られるIPv6アドレスは、秘密鍵を知らない攻撃者には予測できません。
  • 結果として得られるIPv6アドレスは、DHCPv6サーバーの再インストールをまたいでも、また以前のDHCPv6アドレスリースのデータベースが利用できない場合でも、安定したままです。
  • 結果として得られるIPv6アドレスは、同じネットワーク上で（この仕様を実装した）異なるDHCPv6サーバーを使用する場合でも、安定したままです。

We note that the algorithm specified in this document employs a (lightweight) calculated technique (as opposed to, e.g., state sharing among DHCPv6 servers) to achieve address stability in scenarios where multiple DHCPv6 servers are required to run in such a way as to provide increased availability, without the need of an additional protocol to synchronize the lease databases of DHCPv6 servers.

なお、この文書で規定するアルゴリズムは、（軽量な）計算による手法（たとえばDHCPv6サーバー間での状態の共有ではなく）を用いることで、DHCPv6サーバーのリースデータベースを同期させるための追加のプロトコルを必要とすることなく、可用性を高めるように複数のDHCPv6サーバーを動作させる必要があるシナリオにおいてアドレスの安定性を実現します。

Finally, we note that the algorithm in this document is only meant to mitigate IPv6 address-based location tracking, device-specific vulnerability exploitation, and host scanning (please see [RFC7721]). There are a number of ways in which DHCPv6 affects user privacy, which the algorithm specified in this document does not mitigate (and does not intend to). Please see [RFC7844] for a comprehensive discussion of how DHCPv6 may affect user privacy.

最後に、この文書のアルゴリズムは、IPv6アドレスに基づく位置追跡、デバイス固有の脆弱性の悪用、ホストスキャンを緩和することだけを目的としている点に注意してください（[RFC7721]を参照してください）。DHCPv6がユーザーのプライバシーに影響を与える方法は数多くありますが、この文書で規定するアルゴリズムはそれらを緩和しません（また、緩和することを意図してもいません）。DHCPv6がユーザーのプライバシーにどのように影響しうるかについての包括的な議論は、[RFC7844]を参照してください。

3. Method Specification

3. 方法の仕様

Implementations should provide the means for a system administrator to enable or disable the use of this algorithm for generating IPv6 addresses.

実装は、IPv6アドレスを生成するためのこのアルゴリズムの使用をシステム管理者が有効化または無効化できる手段を提供すべきです。

A DHCPv6 server implementing this specification must select the IPv6 addresses to be leased with the following algorithm:

この仕様を実装するDHCPv6サーバーは、次のアルゴリズムでリースするIPv6アドレスを選択しなければなりません。

  1. Compute a random (but stable) identifier with the expression:

    RID = F(Prefix | Client_DUID | IAID | Counter | secret_key)

    Where:

    RID:
    Random (but stable) Identifier
    F():
    A Pseudorandom Function (PRF) that must not be computable from the outside (without knowledge of the secret key). F() must also be difficult to reverse, such that it resists attempts to obtain the secret key, even when given samples of the output of F() and knowledge or control of the other input parameters. F() should produce an output of at least 64 bits. F() could be implemented as a cryptographic hash of the concatenation of each of the function parameters. The default algorithm to be employed for F() should be SHA-256 [FIPS-SHS]. An implementation may provide the means for selecting other algorithms. Note: Message Digest 5 (MD5) [RFC1321] is considered unacceptable for F() [RFC6151].
    Prefix:
    The prefix employed for the local subnet, as a 128-bit unsigned integer in network byte order (with the unused bits set to 0). If multiple servers operate on the same network to provide increased availability, all such DHCPv6 servers must be configured with the same Prefix. It is the administrator's responsibility that the aforementioned requirement is met.
    |:
    An operator representing "concatenation".
    Client_DUID:
    The DHCPv6 Unique Identifier (DUID) value contained in the Client Identifier option received in the DHCPv6 client message. The DUID can be treated as an array of 8-bit unsigned integers.
    IAID:
    The Identity Association Identifier (IAID) value contained in the IA_NA option received in the client message. It must be interpreted as a 32-bit unsigned integer in network byte order.
    secret_key:
    A secret key configured by the DHCPv6 server administrator, which must not be known by the attacker. It must be encoded as an array of 8-bit unsigned integers. An implementation of this specification must provide an interface for viewing and changing the secret key. All DHCPv6 servers leasing addresses from the same address range must employ the same secret key.
    Counter:
    A 32-bit unsigned integer in network byte order that is employed to resolve address conflicts. It must be initialized to 0.

  2. A candidate IPv6 address (IPV6_ADDR) to be leased is obtained by concatenating as many bits as necessary from the RID value computed in the previous step (starting from the least significant bit) to the Prefix employed in the equation above, as follows:

     IPV6_ADDR = IPV6_ADDR_LOW +
             RID % (IPV6_ADDR_HI - IPV6_ADDR_LOW + 1)

    where:

    IPV6_ADDR:
    The candidate IPv6 address to be leased.
    IPV6_ADDR_HI:
    An IPv6 address specifying the upper boundary of the IPv6 address pool from which the DHCPv6 server leases IPv6 addresses. If an address range is not explicitly selected, IPV6_ADDR_HI must be set to the IPv6 address from the Prefix (see the expression above) that has all of the bits of the Interface Identifier set to 1.
    IPV6_ADDR_LOW:
    An IPv6 address specifying the lower boundary of the IPv6 address pool from which the DHCPv6 server leases IPv6 addresses. If an address range is not explicitly selected, IPV6_ADDR_LOW must be set to the IPv6 address from the Prefix (see the expression above) that has all of the bits of the Interface Identifier set to 0.
  3. The Interface Identifier of the selected IPv6 address must be compared against the reserved IPv6 Interface Identifiers [RFC5453] [IANA-RESERVED-IID]. In the event that an unacceptable identifier has been generated, the Counter variable should be incremented by 1, and a new IPv6 address should be computed with the updated Counter value.
  4. If the resulting address is not available (e.g., there is a conflicting binding), the DHCPv6 server should increment the Counter variable, and a new Interface Identifier and IPv6 address should be computed with the updated Counter value.

  1. 次の式でランダムな（ただし安定した）識別子を計算します。

    RID = F(Prefix | Client_DUID | IAID | Counter | secret_key)

    ここで、

    RID:
    ランダムな（ただし安定した）識別子（Random (but stable) Identifier）
    F():
    （秘密鍵を知らずに）外部から計算できてはならない疑似ランダム関数（PRF）です。F()は逆算することも困難でなければなりません。すなわち、F()の出力のサンプルが与えられ、他の入力パラメーターを知っているか制御できる場合であっても、秘密鍵を得ようとする試みに耐えなければなりません。F()は少なくとも64ビットの出力を生成すべきです。F()は、関数の各パラメーターを連結したものの暗号学的ハッシュとして実装できます。F()に使用するデフォルトのアルゴリズムはSHA-256 [FIPS-SHS]であるべきです。実装は、他のアルゴリズムを選択する手段を提供してもかまいません。注: Message Digest 5（MD5）[RFC1321]は、F()には受け入れられないものとみなされています[RFC6151]。
    Prefix:
    ローカルサブネットに使用するプレフィックスで、ネットワークバイトオーダーの128ビット符号なし整数として表したもの（未使用のビットは0に設定します）です。可用性を高めるために複数のサーバーが同じネットワーク上で動作する場合、そのようなDHCPv6サーバーはすべて同じPrefixで設定されなければなりません。前述の要件が満たされるようにすることは、管理者の責任です。
    |:
    「連結」を表す演算子です。
    Client_DUID:
    DHCPv6クライアントのメッセージで受信したClient Identifierオプションに含まれる、DHCP一意識別子（DUID）の値です。DUIDは8ビット符号なし整数の配列として扱うことができます。
    IAID:
    クライアントのメッセージで受信したIA_NAオプションに含まれる、アイデンティティーアソシエーション識別子（IAID）の値です。これは、ネットワークバイトオーダーの32ビット符号なし整数として解釈されなければなりません。
    secret_key:
    DHCPv6サーバーの管理者が設定する秘密鍵で、攻撃者に知られてはなりません。これは8ビット符号なし整数の配列としてエンコードされなければなりません。この仕様の実装は、秘密鍵を表示および変更するためのインターフェイスを提供しなければなりません。同じアドレス範囲からアドレスをリースするすべてのDHCPv6サーバーは、同じ秘密鍵を使用しなければなりません。
    Counter:
    アドレスの衝突を解決するために使用される、ネットワークバイトオーダーの32ビット符号なし整数です。これは0に初期化されなければなりません。

  2. リースするIPv6アドレスの候補（IPV6_ADDR）は、前のステップで計算したRIDの値から必要な数のビットを（最下位ビットから順に）取り出し、上の式で使用したPrefixに連結することで、次のように得られます。

     IPV6_ADDR = IPV6_ADDR_LOW +
             RID % (IPV6_ADDR_HI - IPV6_ADDR_LOW + 1)

    ここで、

    IPV6_ADDR:
    リースするIPv6アドレスの候補です。
    IPV6_ADDR_HI:
    DHCPv6サーバーがIPv6アドレスをリースするIPv6アドレスプールの上限を指定するIPv6アドレスです。アドレス範囲が明示的に選択されていない場合、IPV6_ADDR_HIは、Prefix（上の式を参照）に属するIPv6アドレスのうち、インターフェイス識別子のすべてのビットが1に設定されたものに設定されなければなりません。
    IPV6_ADDR_LOW:
    DHCPv6サーバーがIPv6アドレスをリースするIPv6アドレスプールの下限を指定するIPv6アドレスです。アドレス範囲が明示的に選択されていない場合、IPV6_ADDR_LOWは、Prefix（上の式を参照）に属するIPv6アドレスのうち、インターフェイス識別子のすべてのビットが0に設定されたものに設定されなければなりません。
  3. 選択したIPv6アドレスのインターフェイス識別子は、予約済みのIPv6インターフェイス識別子[RFC5453] [IANA-RESERVED-IID]と比較されなければなりません。受け入れられない識別子が生成された場合は、Counter変数を1増やし、更新したCounterの値で新しいIPv6アドレスを計算すべきです。
  4. 結果として得られたアドレスが利用できない場合（例: 衝突するバインディングがある場合）、DHCPv6サーバーはCounter変数を増やすべきであり、更新したCounterの値で新しいインターフェイス識別子とIPv6アドレスを計算すべきです。

This document requires that SHA-256 be the default function to be used for F(), such that (all other configuration parameters being the same) different implementations of this specification result in the same IPv6 addresses.

この文書は、（他のすべての設定パラメーターが同じであれば）この仕様の異なる実装が同じIPv6アドレスを生成するように、F()に使用するデフォルトの関数をSHA-256とすることを要求します。

Including the Prefix in the PRF computation causes the Interface Identifier to be different for each address from a different prefix leased to the same client. This mitigates the correlation of activities of multihomed nodes (since each of the corresponding addresses will employ a different Interface Identifier), host tracking (since the network prefix, and therefore the resulting Interface Identifier, will change as the node moves from one network to another), and any other attacks that benefit from predictable Interface Identifiers [RFC7721].

PRFの計算にPrefixを含めることで、同じクライアントにリースされる異なるプレフィックスからのアドレスごとに、インターフェイス識別子が異なるものになります。これにより、マルチホームノードの活動の相関付け（対応するアドレスがそれぞれ異なるインターフェイス識別子を使用するため）、ホストの追跡（ノードがあるネットワークから別のネットワークへ移動すると、ネットワークプレフィックス、ひいては結果として得られるインターフェイス識別子が変わるため）、および予測可能なインターフェイス識別子を利用するその他のあらゆる攻撃[RFC7721]が緩和されます。

As required by [RFC3315], an IAID is associated with each of the client's network interfaces and is consistent across restarts of the DHCPv6 client.

[RFC3315]で要求されているとおり、IAIDはクライアントのネットワークインターフェイスのそれぞれに関連付けられ、DHCPv6クライアントの再起動をまたいで一貫しています。

The Counter parameter provides the means to intentionally cause this algorithm to produce different IPv6 addresses (all other parameters being the same). This can be of use to resolve address conflicts (e.g., the resulting address having a conflicting binding).

Counterパラメーターは、（他のすべてのパラメーターが同じであっても）このアルゴリズムに意図的に異なるIPv6アドレスを生成させる手段を提供します。これは、アドレスの衝突（例: 結果として得られたアドレスに衝突するバインディングがある場合）を解決するのに役立ちます。

Note that the result of F() in the algorithm above is no more secure than the secret key. If an attacker is aware of the PRF that is being used by the DHCPv6 server (which we should expect), and the attacker can obtain enough material (i.e., addresses generated by the DHCPv6 server), the attacker may simply search the entire secret-key space to find matches. To protect against this, the secret key should be of at least 128 bits. Key lengths of at least 128 bits should be adequate.

上記のアルゴリズムにおけるF()の結果は、秘密鍵以上に安全になることはない点に注意してください。DHCPv6サーバーが使用しているPRFを攻撃者が知っており（これは想定しておくべきです）、かつ攻撃者が十分な材料（すなわち、DHCPv6サーバーが生成したアドレス）を入手できる場合、攻撃者は単純に秘密鍵の空間全体を探索して一致するものを見つけられるかもしれません。これを防ぐために、秘密鍵は少なくとも128ビットであるべきです。少なくとも128ビットの鍵長があれば十分なはずです。

Providing a mechanism to display and change the secret_key is crucial for having different DHCPv6 servers produce the same IPv6 addresses and for causing a replacement system to generate the same IPv6 addresses as the system being replaced. We note that since the privacy of the scheme specified in this document relies on the secrecy of the secret_key parameter, implementations should constrain access to the secret_key parameter to the extent practicable (e.g., require superuser privileges to access it). Furthermore, in order to prevent leakages of the secret_key parameter, it should not be used for any other purposes than being a parameter to the scheme specified in this document.

secret_keyを表示および変更するメカニズムを提供することは、異なるDHCPv6サーバーに同じIPv6アドレスを生成させるため、また置き換え後のシステムに置き換え前のシステムと同じIPv6アドレスを生成させるために不可欠です。なお、この文書で規定する方式のプライバシーはsecret_keyパラメーターの秘匿性に依存しているため、実装はsecret_keyパラメーターへのアクセスを実行可能な範囲で制限すべきです（例: アクセスにスーパーユーザー権限を要求する）。さらに、secret_keyパラメーターの漏洩を防ぐために、secret_keyパラメーターは、この文書で規定する方式のパラメーターとして使用する以外の目的に使用すべきではありません。

We note that all of the bits in the resulting Interface Identifiers are treated as "opaque" bits [RFC7136]. For example, the universal/local bit of Modified EUI-64 format identifiers is treated as any other bit of such identifier.

なお、結果として得られるインターフェイス識別子のすべてのビットは、「不透明な」ビットとして扱われます[RFC7136]。たとえば、Modified EUI-64形式の識別子のuniversal/localビットは、そのような識別子の他のビットと同様に扱われます。

4. Security Considerations

4. セキュリティーに関する考慮事項

The method specified in this document results in IPv6 Interface Identifiers (and hence IPv6 addresses) that do not follow any specific pattern. Thus, attacks that rely on predictable Interface Identifiers (such as [RFC7707]) are mitigated.

この文書で規定する方法では、特定のパターンに従わないIPv6インターフェイス識別子（したがってIPv6アドレス）が得られます。そのため、予測可能なインターフェイス識別子に依存する攻撃（[RFC7707]など）が緩和されます。

The method specified in this document neither mitigates nor exacerbates the security considerations for DHCPv6 discussed in [RFC3315] and does not mitigate a range of other privacy implications associated with DHCPv6. Please read [RFC7844] for a comprehensive assessment of the privacy implications of DHCPv6.

この文書で規定する方法は、[RFC3315]で議論されているDHCPv6のセキュリティーに関する考慮事項を緩和も悪化もさせず、またDHCPv6に関連するその他のさまざまなプライバシーへの影響も緩和しません。DHCPv6のプライバシーへの影響についての包括的な評価は、[RFC7844]を参照してください。

Finally, we note that an attacker that is able to attach to each of the links to which the victim attaches would still be able to correlate the activities of the victim across networks.

最後に、被害者が接続する各リンクに接続できる攻撃者であれば、依然としてネットワークをまたいで被害者の活動を相関付けられる点に注意してください。
