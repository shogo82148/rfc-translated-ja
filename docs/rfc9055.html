RFC 9055

Deterministic Networking (DetNet) Security Considerations

RFC 9055

決定論的ネットワーキング（DetNet）のセキュリティーに関する考慮事項

Abstract

概要

A DetNet (deterministic network) provides specific performance guarantees to its data flows, such as extremely low data loss rates and bounded latency (including bounded latency variation, i.e., "jitter"). As a result, securing a DetNet requires that in addition to the best practice security measures taken for any mission-critical network, additional security measures may be needed to secure the intended operation of these novel service properties.

DetNet（決定論的ネットワーク）は、極めて低いデータ損失率や有界遅延（有界な遅延変動、すなわち「ジッター」を含む）など、データフローに対して特定の性能保証を提供します。 その結果、DetNetのセキュリティーを確保するには、あらゆるミッションクリティカルなネットワークで講じられるベストプラクティスのセキュリティー対策に加えて、これらの新しいサービス特性の意図された動作を保護するための追加のセキュリティー対策が必要になる場合があります。

This document addresses DetNet-specific security considerations from the perspectives of both the DetNet system-level designer and component designer. System considerations include a taxonomy of relevant threats and attacks, and associations of threats versus use cases and service properties. Component-level considerations include ingress filtering and packet arrival-time violation detection.

この文書は、DetNetのシステムレベルの設計者とコンポーネントの設計者の両方の観点から、DetNet固有のセキュリティーに関する考慮事項を扱います。 システムに関する考慮事項には、関連する脅威と攻撃の分類、および脅威とユースケースやサービス特性との対応付けが含まれます。 コンポーネントレベルの考慮事項には、イングレスフィルタリングとパケット到着時刻違反の検出が含まれます。

This document also addresses security considerations specific to the IP and MPLS data plane technologies, thereby complementing the Security Considerations sections of those documents.

この文書は、IPおよびMPLSのデータプレーン技術に固有のセキュリティーに関する考慮事項も扱い、それによってそれらの文書のセキュリティーに関する考慮事項のセクションを補完します。

1. Introduction

1. はじめに

A deterministic IP network ("Deterministic Networking Architecture" [RFC8655]) can carry data flows for real-time applications with extremely low data loss rates and bounded latency. The bounds on latency defined by DetNet (as described in [RFC9016]) include both worst-case latency (Maximum Latency, Section 5.9.2 of [RFC9016]) and worst-case jitter (Maximum Latency Variation, Section 5.9.3 of [RFC9016]). Data flows with deterministic properties are well established for Ethernet networks (see Time-Sensitive Networking (TSN), [IEEE802.1BA]); DetNet brings these capabilities to the IP network.

決定論的IPネットワーク（「Deterministic Networking Architecture」[RFC8655]）は、極めて低いデータ損失率と有界遅延（bounded latency）で、リアルタイムアプリケーションのデータフローを運ぶことができます。 DetNetが定義する遅延の上限（[RFC9016]で説明されています）には、最悪ケースの遅延（最大遅延、[RFC9016]のSection 5.9.2）と最悪ケースのジッター（最大遅延変動、[RFC9016]のSection 5.9.3）の両方が含まれます。 決定論的な特性を持つデータフローはイーサネットネットワークではすでに確立されており（Time-Sensitive Networking（TSN）、[IEEE802.1BA]を参照してください）、DetNetはこれらの能力をIPネットワークにもたらします。

Deterministic IP networks have been successfully deployed in real-time Operational Technology (OT) applications for some years; however, such networks are typically isolated from external access, and thus the security threat from external attackers is low. An example of such an isolated network is a network deployed within an aircraft, which is "air gapped" from the outside world. DetNet specifies a set of technologies that enable creation of deterministic flows on IP-based networks of a potentially wide area (on the scale of a corporate network), potentially merging OT traffic with best-effort Information Technology (IT) traffic, and placing OT network components into contact with IT network components, thereby exposing the OT traffic and components to security threats that were not present in an isolated OT network.

決定論的IPネットワークは、リアルタイムの運用技術（Operational Technology、OT）アプリケーションにおいて数年前から展開に成功しています。 しかし、そのようなネットワークは通常、外部からのアクセスから隔離されているため、外部の攻撃者によるセキュリティー上の脅威は小さいです。 そのような隔離されたネットワークの例として、航空機内に展開されたネットワークがあり、これは外界から「エアギャップ」されています。 DetNetは、広域（企業ネットワーク規模）になりうるIPベースのネットワーク上で決定論的なフローを作成できるようにする一連の技術を規定します。 これにより、OTトラフィックがベストエフォートの情報技術（Information Technology、IT）トラフィックと混在し、OTネットワークのコンポーネントがITネットワークのコンポーネントと接触するようになる可能性があります。 その結果、OTトラフィックとOTコンポーネントは、隔離されたOTネットワークには存在しなかったセキュリティー上の脅威にさらされます。

These DetNet (OT-type) technologies may not have previously been deployed on a wide area IP-based network that also carries IT traffic, and thus they can present security considerations that may be new to IP-based wide area network designers; this document provides insight into such system-level security considerations. In addition, designers of DetNet components (such as routers) face new security-related challenges in providing DetNet services, for example, maintaining reliable isolation between traffic flows in an environment where IT traffic co-mingles with critical reserved-bandwidth OT traffic; this document also examines security implications internal to DetNet components.

これらのDetNet（OT型）の技術は、ITトラフィックも運ぶ広域のIPベースのネットワーク上ではこれまで展開されていなかった可能性があります。 そのため、IPベースの広域ネットワークの設計者にとって新しいセキュリティー上の考慮事項をもたらす可能性があります。 この文書は、そのようなシステムレベルのセキュリティーに関する考慮事項についての洞察を提供します。 さらに、DetNetコンポーネント（ルーターなど）の設計者は、DetNetサービスを提供するうえで、セキュリティーに関連する新しい課題に直面します。 たとえば、ITトラフィックが帯域幅予約済みの重要なOTトラフィックと混在する環境において、トラフィックフロー間の確実な分離を維持することです。 この文書では、DetNetコンポーネント内部のセキュリティー上の影響も検討します。

Security is of particularly high importance in DetNet because many of the use cases that are enabled by DetNet [RFC8578] include control of physical devices (power grid devices, industrial controls, building controls, etc.) that can have high operational costs for failure and present potentially attractive targets for cyber attackers.

DetNetでは、セキュリティーが特に重要です。 DetNetによって可能になるユースケース[RFC8578]の多くには、物理デバイス（電力網のデバイス、産業用制御、ビル制御など）の制御が含まれており、それらは故障した場合の運用コストが高く、サイバー攻撃者にとって魅力的な標的となる可能性があるためです。

This situation is even more acute given that one of the goals of DetNet is to provide a "converged network", i.e., one that includes both IT traffic and OT traffic, thus exposing potentially sensitive OT devices to attack in ways that were not previously common (usually because they were under a separate control system or otherwise isolated from the IT network, for example [ARINC664P7]). Security considerations for OT networks are not a new area, and there are many OT networks today that are connected to wide area networks or the Internet; this document focuses on the issues that are specific to the DetNet technologies and use cases.

DetNetの目標の1つが「統合ネットワーク（converged network）」、すなわちITトラフィックとOTトラフィックの両方を含むネットワークを提供することであることを考えると、この状況はさらに深刻です。 これにより、機密性の高いOTデバイスが、以前は一般的でなかった方法で攻撃にさらされる可能性があります（通常、それらは別の制御システムの下にあるか、何らかの形でITネットワークから隔離されていたためです。たとえば[ARINC664P7]）。 OTネットワークのセキュリティーに関する考慮事項は新しい分野ではなく、今日では広域ネットワークやインターネットに接続されているOTネットワークが数多くあります。 この文書は、DetNetの技術とユースケースに固有の問題に焦点を当てます。

Given the above considerations, securing a DetNet starts with a scrupulously well-designed and well-managed engineered network following industry best practices for security at both the data plane and controller plane, as well as for any Operations, Administration, and Maintenance (OAM) implementation; this is the assumed starting point for the considerations discussed herein. Such assumptions also depend on the network components themselves upholding the security-related properties that are to be assumed by DetNet system-level designers; for example, the assumption that network traffic associated with a given flow can never affect traffic associated with a different flow is only true if the underlying components make it so. Such properties, which may represent new challenges to component designers, are also considered herein.

以上の考慮事項を踏まえると、DetNetのセキュリティー確保は、データプレーンとコントローラープレーンの両方、およびあらゆる運用・管理・保守（Operations, Administration, and Maintenance、OAM）の実装について、セキュリティーに関する業界のベストプラクティスに従って、細心の注意を払って適切に設計・管理されたネットワークから始まります。 これが、ここで議論する考慮事項の前提となる出発点です。 このような前提は、DetNetのシステムレベルの設計者が前提とするセキュリティー関連の特性を、ネットワークコンポーネント自体が維持することにも依存します。 たとえば、あるフローに関連付けられたネットワークトラフィックが、別のフローに関連付けられたトラフィックに決して影響を与えないという前提は、基盤となるコンポーネントがそれを実現している場合にのみ成り立ちます。 コンポーネントの設計者にとって新しい課題となる可能性のあるこのような特性も、ここで考慮します。

Starting with a "well-managed network", as noted above, enables us to exclude some of the more powerful adversary capabilities from the Internet Threat Model of [BCP72], such as the ability to arbitrarily drop or delay any or all traffic. Given this reduced attacker capability, we can present security considerations based on attacker capabilities that are more directly relevant to a DetNet.

上で述べたように「適切に管理されたネットワーク」から始めることで、[BCP72]のインターネット脅威モデルにある、より強力な敵対者の能力の一部（任意のトラフィックの一部またはすべてを恣意的に破棄したり遅延させたりする能力など）を除外できます。 このように攻撃者の能力を縮小することで、DetNetにより直接的に関連する攻撃者の能力に基づいて、セキュリティーに関する考慮事項を提示できます。

In this context, we view the "conventional" (i.e., non-time-sensitive) network design and management aspects of network security as being primarily concerned with preventing denial of service, i.e., they must ensure that DetNet traffic goes where it's supposed to and that an external attacker can't inject traffic that disrupts the delivery timing assurance of the DetNet. The time-specific aspects of DetNet security presented here take up where those "conventional" design and management aspects leave off.

この文脈では、ネットワークセキュリティーの「従来の」（すなわち、時間に敏感でない）ネットワーク設計・管理の側面は、主にサービス拒否の防止に関わるものとみなします。 すなわち、それらはDetNetトラフィックが本来行くべきところに行くこと、および外部の攻撃者がDetNetの配送タイミングの保証を妨げるトラフィックを注入できないことを保証しなければなりません。 ここで提示するDetNetセキュリティーの時間に固有の側面は、そうした「従来の」設計・管理の側面が終わったところから始まります。

However, note that "conventional" methods for mitigating (among all the others) denial-of-service attacks (such as throttling) can only be effectively used in a DetNet when their use does not compromise the required time-sensitive or behavioral properties required for the OT flows on the network. For example, a "retry" protocol is typically not going to be compatible with a low-latency (worst-case maximum latency) requirement; however, if in a specific use case and implementation such a retry protocol is able to meet the timing constraints, then it may well be used in that context. Similarly, if common security protocols such as TLS/DTLS or IPsec are to be used, it must be verified that their implementations are able to meet the timing and behavioral requirements of the time-sensitive network as implemented for the given use case. An example of "behavioral properties" might be that dropping of more than a specific number of packets in a row is not acceptable according to the service level agreement.

ただし、（他のあらゆる攻撃の中でも）サービス拒否攻撃を緩和するための「従来の」方法（スロットリングなど）は、ネットワーク上のOTフローに求められる時間に敏感な特性や振る舞いの特性を損なわない場合にのみ、DetNetで効果的に使用できることに注意してください。 たとえば、「再試行」プロトコルは通常、低遅延（最悪ケースの最大遅延）の要件とは両立しません。 しかし、特定のユースケースと実装において、そのような再試行プロトコルがタイミングの制約を満たせるのであれば、その文脈で使用しても差し支えありません。 同様に、TLS/DTLSやIPsecなどの一般的なセキュリティープロトコルを使用する場合は、それらの実装が、特定のユースケース向けに実装された時間に敏感なネットワークのタイミングと振る舞いの要件を満たせることを検証しなければなりません。 「振る舞いの特性」の例としては、サービスレベル契約により、特定の数を超えるパケットが連続して破棄されることは許容されない、といったものが考えられます。

The exact security requirements for any given DetNet are necessarily specific to the use cases handled by that network. Thus, the reader is assumed to be familiar with the specific security requirements of their use cases, for example, those outlined in the DetNet Use Cases [RFC8578] and the Security Considerations sections of the DetNet documents applicable to the network technologies in use, for example, [RFC8939] for an IP data plane and [RFC8964] for an MPLS data plane. Readers can find a general introduction to the DetNet Architecture in [RFC8655], the DetNet Data Plane in [RFC8938], and the Flow Information Model in [RFC9016].

あるDetNetの正確なセキュリティー要件は、必然的に、そのネットワークが扱うユースケースに固有のものになります。 したがって、読者は自身のユースケースに固有のセキュリティー要件に精通していることを前提とします。 たとえば、DetNetのユースケース[RFC8578]で概説されているものや、使用しているネットワーク技術に適用されるDetNet文書のセキュリティーに関する考慮事項のセクション（たとえば、IPデータプレーンについては[RFC8939]、MPLSデータプレーンについては[RFC8964]）です。 DetNetアーキテクチャーの全般的な紹介は[RFC8655]に、DetNetデータプレーンは[RFC8938]に、フロー情報モデルは[RFC9016]にあります。

The DetNet technologies include ways to:

DetNetの技術には、次のことを行う方法が含まれます。

  • Assign data plane resources for DetNet flows in some or all of the intermediate nodes (routers) along the path of the flow
  • Provide explicit routes for DetNet flows that do not dynamically change with the network topology in ways that affect the quality of service received by the affected flow(s)
  • Distribute data from DetNet flow packets over time and/or space to ensure delivery of the data in each packet in spite of the loss of a path
  • フローのパス上にある中間ノード（ルーター）の一部またはすべてにおいて、DetNetフローにデータプレーンのリソースを割り当てる
  • 影響を受けるフローが受けるサービス品質に影響するような形でネットワークトポロジーに応じて動的に変化することのない、明示的な経路をDetNetフローに提供する
  • パスが失われた場合でも各パケット内のデータが確実に配送されるように、DetNetフローのパケットのデータを時間的および／または空間的に分散させる

This document includes sections considering DetNet component design as well as system design. The latter includes a taxonomy and analysis of threats, threat impacts and mitigations, and an association of attacks with use cases (based on Section 11 of [RFC8578]).

この文書には、システム設計だけでなく、DetNetコンポーネントの設計を考慮するセクションも含まれます。 システム設計の部分には、脅威の分類と分析、脅威の影響と緩和策、および（[RFC8578]のSection 11に基づく）攻撃とユースケースの対応付けが含まれます。

This document is based on the premise that there will be a very broad range of DetNet applications and use cases, ranging in size and scope from individual industrial machines to networks that span an entire country [RFC8578]. Thus, no single set of prescriptions (such as exactly which mitigation should be applied to which segment of a DetNet) can be applicable to all of them, and indeed any single one that we might prescribe would inevitably prove impractical for some use case, perhaps one that does not even exist at the time of this writing. Thus, we are not prescriptive here; we are stating the desired end result, with the understanding that most DetNet use cases will necessarily differ from each other, and there is no "one size fits all".

この文書は、個々の産業機械から国全体にまたがるネットワークまで、規模と範囲の点で非常に幅広いDetNetのアプリケーションとユースケースが存在するという前提に基づいています[RFC8578]。 したがって、単一の規定の組（DetNetのどのセグメントにどの緩和策を適用すべきかを正確に定めるものなど）がそれらすべてに適用できることはありません。 実際、私たちが規定しうるどのような単一の規定も、あるユースケース（おそらくこの執筆時点ではまだ存在すらしていないユースケース）にとっては必然的に非現実的なものとなるでしょう。 したがって、ここでは規定的な記述はしません。 ほとんどのDetNetのユースケースは必然的に互いに異なり、「万能の解決策」は存在しないという理解のもとで、望ましい最終結果を述べます。

3. Security Considerations for DetNet Component Design

3. DetNetコンポーネント設計におけるセキュリティーに関する考慮事項

This section provides guidance for implementers of components to be used in a DetNet.

このセクションでは、DetNetで使用されるコンポーネントの実装者向けのガイダンスを提供します。

As noted above, DetNet provides resource allocation, explicit routes, and redundant path support. Each of these has associated security implications, which are discussed in this section, in the context of component design. Detection, reporting and appropriate action in the case of packet arrival-time violations are also discussed.

上で述べたように、DetNetはリソース割り当て、明示的な経路、および冗長パスのサポートを提供します。 これらにはそれぞれ関連するセキュリティー上の影響があり、このセクションではコンポーネント設計の文脈でそれらを議論します。 パケット到着時刻の違反が発生した場合の検出、報告、および適切な対処についても議論します。

3.1. Resource Allocation

3.1. リソース割り当て

3.1.1. Inviolable Flows

3.1.1. 不可侵のフロー

A DetNet system security designer relies on the premise that any resources allocated to a resource-reserved (OT-type) flow are inviolable; in other words, there is no physical possibility within a DetNet component that resources allocated to a given DetNet flow can be compromised by any type of traffic in the network. This includes malicious traffic as well as inadvertent traffic such as might be produced by a malfunctioning component, or due to interactions between components that were not sufficiently tested for interoperability. From a security standpoint, this is a critical assumption, for example, when designing against DoS attacks. In other words, with correctly designed components and security mechanisms, one can prevent malicious activities from impacting other resources.

DetNetシステムのセキュリティー設計者は、リソース予約済みの（OT型の）フローに割り当てられたリソースは不可侵であるという前提に依拠しています。 言い換えれば、DetNetコンポーネント内において、あるDetNetフローに割り当てられたリソースがネットワーク内のいかなる種類のトラフィックによっても侵害される物理的な可能性はない、ということです。 これには、悪意のあるトラフィックだけでなく、誤動作しているコンポーネントが生成するトラフィックや、相互運用性について十分にテストされていないコンポーネント間の相互作用に起因するトラフィックなど、意図しないトラフィックも含まれます。 セキュリティーの観点からは、これは、たとえばDoS攻撃への対策を設計する際の重要な前提です。 言い換えれば、正しく設計されたコンポーネントとセキュリティーメカニズムがあれば、悪意のある活動が他のリソースに影響を与えることを防止できます。

However, achieving the goal of absolutely inviolable flows may not be technically or economically feasible for any given use case, given the broad range of possible use cases (e.g., [RFC8578]) and their associated security considerations as outlined in this document. It can be viewed as a continuum of security requirements, from isolated ultra-low latency systems that may have little security vulnerability (such as an industrial machine) to broadly distributed systems with many possible attack vectors and OT security concerns (such as a utility network). Given this continuum, the design principle employed in this document is to specify the desired end results, without being overly prescriptive in how the results are achieved, reflecting the understanding that no individual implementation is likely to be appropriate for every DetNet use case.

しかし、ありうるユースケースの幅広さ（例：[RFC8578]）と、この文書で概説するそれらに関連するセキュリティーに関する考慮事項を考えると、完全に不可侵のフローという目標を達成することは、あるユースケースにとって技術的にも経済的にも実現可能でない場合があります。 これは、セキュリティー上の脆弱性がほとんどない可能性のある隔離された超低遅延システム（産業機械など）から、多くの攻撃ベクトルとOTセキュリティー上の懸念を持つ広く分散したシステム（公益事業ネットワークなど）まで、セキュリティー要件の連続体とみなすことができます。 この連続体を考慮して、この文書で採用している設計原則は、結果をどのように達成するかについて過度に規定することなく、望ましい最終結果を規定することです。 これは、個々の実装がすべてのDetNetのユースケースに適切である可能性は低いという理解を反映しています。

3.1.2. Design Trade-Off Considerations in the Use Cases Continuum

3.1.2. ユースケースの連続体における設計上のトレードオフに関する考慮事項

For any given DetNet use case and its associated security requirements, it is important for the DetNet system designer to understand the interaction and design trade-offs that inevitably need to be reconciled between the desired end results and the DetNet protocols, as well as the DetNet system and component design.

あるDetNetのユースケースとそれに関連するセキュリティー要件について、DetNetシステムの設計者は、望ましい最終結果とDetNetプロトコルとの間、およびDetNetのシステム設計とコンポーネント設計との間で必然的に調整が必要となる相互作用と設計上のトレードオフを理解することが重要です。

For any given component, as designed for any given use case (or scope of use cases), it is the responsibility of the component designer to ensure that the premise of inviolable flows is supported to the extent that they deem necessary to support their target use cases.

あるユースケース（またはユースケースの範囲）向けに設計されたあるコンポーネントについて、対象とするユースケースをサポートするために必要と考える範囲で不可侵のフローという前提がサポートされることを保証するのは、コンポーネントの設計者の責任です。

For example, the component may include traffic shaping and policing at the ingress to prevent corrupted, malicious, or excessive packets from entering the network, thereby decreasing the likelihood that any traffic will interfere with any DetNet OT flow. The component may include integrity protection for some or all of the header fields such as those used for flow ID, thereby decreasing the likelihood that a packet whose flow ID has been compromised might be directed into a different flow path. The component may verify every single packet header at every forwarding location, or only at certain points. In any of these cases, the component may use dynamic performance analytics (Section 7.7) to cause action to be initiated to address the situation in an appropriate and timely manner, either at the data plane or controller plane, or both in concert. The component's software and hardware may include measures to ensure the integrity of the resource allocation/deallocation process. Other design aspects of the component may help ensure that the adverse effects of malicious traffic are more limited, for example, by protecting network control interfaces or minimizing cascade failures. The component may include features specific to a given use case, such as configuration of the response to a given sequential packet loss count.

たとえば、コンポーネントは、破損した、悪意のある、または過剰なパケットがネットワークに入るのを防ぐために、イングレスでトラフィックシェーピングとポリシングを備えることができます。 これにより、何らかのトラフィックがDetNetのOTフローに干渉する可能性が低くなります。 コンポーネントは、フローIDに使用されるものなど、ヘッダーフィールドの一部またはすべてに対する完全性保護を備えることができます。 これにより、フローIDが侵害されたパケットが別のフローのパスに向けられる可能性が低くなります。 コンポーネントは、すべての転送箇所であらゆるパケットのヘッダーを検証することも、特定の箇所でのみ検証することもできます。 これらのいずれの場合でも、コンポーネントは動的性能分析（Section 7.7）を使用して、データプレーンまたはコントローラープレーン、あるいはその両方の連携により、状況に適切かつ時宜を得た方法で対処するアクションを開始させることができます。 コンポーネントのソフトウェアとハードウェアは、リソースの割り当て／割り当て解除のプロセスの完全性を保証するための対策を備えることができます。 コンポーネントの他の設計上の側面は、たとえばネットワーク制御インターフェイスを保護したり、連鎖的な障害を最小限に抑えたりすることで、悪意のあるトラフィックの悪影響をより限定的にするのに役立つ場合があります。 コンポーネントは、ある連続パケット損失数に対する応答の設定など、特定のユースケースに固有の機能を備えることができます。

Ultimately, due to cost and complexity factors, the security properties of a component designed for low-cost systems may be (by design) far inferior to a component with similar intended functionality, but designed for highly secure or otherwise critical applications, perhaps at substantially higher cost. Any given component is designed for some set of use cases and accordingly will have certain limitations on its security properties and vulnerabilities. It is thus the responsibility of the system designer to assure themselves that the components they use in their design are capable of satisfying their overall system security requirements.

結局のところ、コストと複雑さの要因により、低コストのシステム向けに設計されたコンポーネントのセキュリティー特性は、同様の機能を意図しつつも、高いセキュリティーが求められる、あるいはその他の重要なアプリケーション向けに（おそらく大幅に高いコストで）設計されたコンポーネントよりも、（設計上）はるかに劣る場合があります。 どのようなコンポーネントも何らかのユースケースの組に向けて設計されており、それに応じてセキュリティー特性と脆弱性に一定の制限があります。 したがって、設計で使用するコンポーネントが全体的なシステムのセキュリティー要件を満たせることを確認するのは、システム設計者の責任です。

3.1.3. Documenting the Security Properties of a Component

3.1.3. コンポーネントのセキュリティー特性の文書化

In order for the system designer to adequately understand the security-related behavior of a given component, the designer of any component intended for use with DetNet needs to clearly document the security properties of that component. For example, to address the case where a corrupted packet in which the flow identification information is compromised and thus may incidentally match the flow ID of another ("victim") DetNet flow, resulting in additional unauthorized traffic on the victim, the documentation might state that the component employs integrity protection on the flow identification fields.

システム設計者があるコンポーネントのセキュリティー関連の振る舞いを適切に理解できるように、DetNetでの使用を意図したコンポーネントの設計者は、そのコンポーネントのセキュリティー特性を明確に文書化する必要があります。 たとえば、フロー識別情報が侵害された破損パケットが、たまたま別の（「被害者」の）DetNetフローのフローIDと一致し、その結果、被害者に許可されていない追加のトラフィックが生じるというケースに対処するために、文書には、そのコンポーネントがフロー識別フィールドに完全性保護を採用していると記載することが考えられます。

3.1.4. Fail-Safe Component Behavior

3.1.4. フェイルセーフなコンポーネントの振る舞い

Even when the security properties of a component are understood and well specified, if the component malfunctions, for example, due to physical circumstances unpredicted by the component designer, it may be difficult or impossible to fully prevent malfunction of the network. The degree to which a component is hardened against various types of failures is a distinguishing feature of the component and its design, and the overall system design can only be as strong as its weakest link.

コンポーネントのセキュリティー特性が理解され、適切に規定されている場合でも、たとえばコンポーネントの設計者が予測しなかった物理的な状況によってコンポーネントが誤動作すると、ネットワークの誤動作を完全に防止することは困難または不可能な場合があります。 さまざまな種類の障害に対してコンポーネントがどの程度強化されているかは、そのコンポーネントとその設計を特徴づけるものであり、システム設計全体の強さは、その最も弱い部分の強さにしかなりえません。

However, all networks are subject to this level of uncertainty; it is not unique to DetNet. Having said that, DetNet raises the bar by changing many added latency scenarios from tolerable annoyances to unacceptable service violations. That in turn underscores the importance of system integrity, as well as correct and stable configuration of the network and its nodes, as discussed in Section 1.

しかし、すべてのネットワークがこのレベルの不確実性にさらされており、これはDetNetに固有のものではありません。 とはいえ、DetNetは、遅延が加わる多くのシナリオを、許容できる煩わしさから許容できないサービス違反へと変えることで、ハードルを上げています。 このことは、Section 1で議論したように、システムの完全性、およびネットワークとそのノードの正しく安定した設定の重要性を強調するものです。

3.1.5. Flow Aggregation Example

3.1.5. フロー集約の例

As another example regarding resource allocation implementation, consider the implementation of Flow Aggregation for DetNet flows (as discussed in [RFC8938]). In this example, say there are N flows that are to be aggregated; thus, the bandwidth resources of the aggregate flow must be sufficient to contain the sum of the bandwidth reservation for the N flows. However, if one of those flows were to consume more than its individually allocated bandwidth, this could cause starvation of the other flows. Thus, simply providing and enforcing the calculated aggregate bandwidth may not be a complete solution; the bandwidth for each individual flow must still be guaranteed, for example, via ingress policing of each flow (i.e., before it is aggregated). Alternatively, if by some other means each flow to be aggregated can be trusted not to exceed its allocated bandwidth, the same goal can be achieved.

リソース割り当ての実装に関する別の例として、（[RFC8938]で議論されている）DetNetフローのフロー集約の実装を考えます。 この例では、集約されるフローがN個あるとします。 したがって、集約フローの帯域幅リソースは、N個のフローの帯域幅予約の合計を収容するのに十分でなければなりません。 しかし、それらのフローの1つが個別に割り当てられた帯域幅を超えて消費すると、他のフローが枯渇する可能性があります。 したがって、計算された集約帯域幅を単に提供して強制するだけでは完全な解決策にならない場合があります。 たとえば、各フローのイングレスポリシング（すなわち、集約される前のポリシング）によって、個々のフローの帯域幅を引き続き保証しなければなりません。 あるいは、集約される各フローが割り当てられた帯域幅を超えないことを何らかの別の手段で信頼できるのであれば、同じ目標を達成できます。

3.2. Explicit Routes

3.2. 明示的な経路

The DetNet-specific purpose for constraining the ability of the DetNet to reroute OT traffic is to maintain the specified service parameters (such as upper and lower latency boundaries) for a given flow. For example, if the network were to reroute a flow (or some part of a flow) based exclusively on statistical path usage metrics, or due to malicious activity, it is possible that the new path would have a latency that is outside the required latency bounds that were designed into the original TE-designed path, thereby violating the quality of service for the affected flow (or part of that flow).

DetNetがOTトラフィックを再ルーティングする能力を制約する、DetNet固有の目的は、あるフローについて規定されたサービスパラメーター（遅延の上限と下限など）を維持することです。 たとえば、ネットワークが統計的なパス使用率のメトリックのみに基づいて、あるいは悪意のある活動によって、フロー（またはフローの一部）を再ルーティングした場合、新しいパスの遅延が、元のTE（トラフィックエンジニアリング）で設計されたパスに組み込まれていた必要な遅延の範囲から外れる可能性があり、それによって影響を受けるフロー（またはそのフローの一部）のサービス品質に違反することになります。

However, it is acceptable for the network to reroute OT traffic in such a way as to maintain the specified latency bounds (and any other specified service properties) for any reason, for example, in response to a runtime component or path failure.

しかし、規定された遅延の範囲（およびその他の規定されたサービス特性）を維持するような形であれば、たとえば実行時のコンポーネントやパスの障害への対応など、どのような理由であれ、ネットワークがOTトラフィックを再ルーティングすることは許容されます。

So from a DetNet security standpoint, the DetNet system designer can expect that any component designed for use in a DetNet will deliver the packets within the agreed-upon service parameters. For the component designer, this means that in order for a component to achieve that expectation, any component that is involved in controlling or implementing any change of the initially TE-configured flow routes must prevent rerouting of OT flows (whether malicious or accidental) that might adversely affect delivering the traffic within the specified service parameters.

したがって、DetNetのセキュリティーの観点からは、DetNetシステムの設計者は、DetNetでの使用向けに設計されたコンポーネントは合意されたサービスパラメーターの範囲内でパケットを配送すると期待できます。 コンポーネントの設計者にとってこれが意味するのは、コンポーネントがその期待を達成するために、当初TEで設定されたフローの経路の変更の制御または実施に関与するすべてのコンポーネントは、規定されたサービスパラメーターの範囲内でのトラフィックの配送に悪影響を与える可能性のあるOTフローの再ルーティング（悪意によるものか偶発的なものかを問わず）を防止しなければならない、ということです。

3.3. Redundant Path Support

3.3. 冗長パスのサポート

The DetNet provision for redundant paths (i.e., PREOF, or "Packet Replication, Elimination, and Ordering Functions"), as defined in the DetNet Architecture [RFC8655], provides the foundation for high reliability of a DetNet by virtually eliminating packet loss (i.e., to a degree that is implementation dependent) through hitless redundant packet delivery.

DetNetアーキテクチャー[RFC8655]で定義されている、DetNetの冗長パスの仕組み（すなわち、PREOF、「パケットの複製・除去・順序付けの機能（Packet Replication, Elimination, and Ordering Functions）」）は、無瞬断の冗長パケット配送によってパケット損失を事実上（すなわち、実装に依存する程度まで）なくすことで、DetNetの高い信頼性の基盤を提供します。

Note: At the time of this writing, PREOF is not defined for the IP data plane.

注：この執筆時点では、PREOFはIPデータプレーンについては定義されていません。

It is the responsibility of the system designer to determine the level of reliability required by their use case and to specify redundant paths sufficient to provide the desired level of reliability (in as much as that reliability can be provided through the use of redundant paths). It is the responsibility of the component designer to ensure that the relevant PREOF operations are executed reliably and securely to avoid potentially catastrophic situations for the operational technology relying on them.

ユースケースが必要とする信頼性のレベルを決定し、望ましいレベルの信頼性を提供するのに十分な冗長パスを（冗長パスの使用によってその信頼性を提供できる限りにおいて）規定するのは、システム設計者の責任です。 関連するPREOFの操作が確実かつ安全に実行され、それに依存する運用技術にとって破局的となりうる状況を回避することを保証するのは、コンポーネントの設計者の責任です。

However, note that not all PREOF operations are necessarily implemented in every network; for example, a packet reordering function may not be necessary if the packets are either not required to be in order or if the ordering is performed in some other part of the network.

ただし、すべてのPREOFの操作がすべてのネットワークで必ずしも実装されるわけではないことに注意してください。 たとえば、パケットが順序どおりである必要がない場合や、順序付けがネットワークの他の部分で実行される場合には、パケットの並べ替え機能は必要ないかもしれません。

Ideally, a redundant path for a flow could be specified from end to end; however, given that this is not always possible (as described in [RFC8655]), the system designer will need to consider the resulting end-to-end reliability and security resulting from any given arrangement of network segments along the path, each of which provides its individual PREOF implementation and thus its individual level of reliability and security.

理想的には、フローの冗長パスをエンドツーエンドで規定できるとよいのですが、（[RFC8655]で説明されているように）これは常に可能とは限らないため、システム設計者は、パス上のネットワークセグメントの配置から生じるエンドツーエンドの信頼性とセキュリティーを考慮する必要があります。 各ネットワークセグメントは個別のPREOFの実装を提供しており、したがって個別のレベルの信頼性とセキュリティーを持っています。

At the data plane, the implementation of PREOF depends on the correct assignment and interpretation of packet sequence numbers, as well as the actions taken based on them, such as elimination (including elimination of packets with spurious sequence numbers). Thus, the integrity of these values must be maintained by the component as they are assigned by the DetNet Data Plane Service sub-layer and transported by the Forwarding sub-layer. This is no different than the integrity of the values in any header used by the DetNet (or any other) data plane and is not unique to redundant paths. The integrity protection of header values is technology dependent; for example, in Layer 2 networks, the integrity of the header fields can be protected by using MACsec [IEEE802.1AE-2018]. Similarly, from the sequence number injection perspective, it is no different from any other protocols that use sequence numbers; for particulars of integrity protection via IPsec Authentication Headers, useful insights are provided by Section 3 of [RFC4302].

データプレーンでは、PREOFの実装は、パケットのシーケンス番号の正しい割り当てと解釈、およびそれに基づいて行われるアクション（除去など。偽のシーケンス番号を持つパケットの除去を含みます）に依存します。 したがって、これらの値はDetNetデータプレーンのサービスサブレイヤーによって割り当てられ、転送サブレイヤーによって輸送されるので、コンポーネントはこれらの値の完全性を維持しなければなりません。 これは、DetNet（またはその他の）データプレーンが使用するあらゆるヘッダー内の値の完全性と何ら変わりはなく、冗長パスに固有のものではありません。 ヘッダー値の完全性保護は技術に依存します。 たとえば、レイヤー2ネットワークでは、MACsec [IEEE802.1AE-2018]を使用することでヘッダーフィールドの完全性を保護できます。 同様に、シーケンス番号の注入の観点からも、シーケンス番号を使用する他のプロトコルと何ら変わりはありません。 IPsec認証ヘッダーによる完全性保護の詳細については、[RFC4302]のSection 3が有用な洞察を提供しています。

3.4. Timing (or Other) Violation Reporting

3.4. タイミング（またはその他の）違反の報告

A task of the DetNet system designer is to create a network such that for any incoming packet that arrives with any timing or bandwidth violation, an appropriate action can be taken in order to prevent damage to the system. The reporting step may be accomplished through dynamic performance analysis (see Section 7.7) or by any other means as implemented in one or more components. The action to be taken for any given circumstance within any given application will depend on the use case. The action may involve intervention from the controller plane, or it may be taken "immediately" by an individual component, for example, if a very fast response is required.

DetNetシステム設計者の仕事は、タイミングや帯域幅の違反を伴って到着した受信パケットに対して、システムへの損害を防ぐための適切なアクションを取れるようなネットワークを作ることです。 報告の段階は、動的性能分析（Section 7.7を参照してください）によって、あるいは1つ以上のコンポーネントに実装されたその他の手段によって実現できます。 あるアプリケーションのある状況において取るべきアクションは、ユースケースによって異なります。 アクションには、コントローラープレーンからの介入が含まれる場合もあれば、たとえば非常に高速な応答が必要な場合には、個々のコンポーネントによって「即座に」取られる場合もあります。

The definitions and selections of the actions that can be taken are properties of the components. The component designer implements these options according to their expected use cases, which may vary widely from component to component. Clearly, selecting an inappropriate response to a given condition may cause more problems than it is intending to mitigate; for example, a naive approach might be to have the component shut down the link if a packet arrives outside of its prescribed time window. However, such a simplistic action may serve the attacker better than it serves the network. Similarly, simple logging of such issues may not be adequate since a delay in response could result in material damage, for example, to mechanical devices controlled by the network. Thus, a breadth of possible and effective security-related actions and their configuration is a positive attribute for a DetNet component.

取りうるアクションの定義と選択は、コンポーネントの特性です。 コンポーネントの設計者は、想定するユースケースに応じてこれらの選択肢を実装しますが、それはコンポーネントごとに大きく異なる場合があります。 明らかに、ある状況に対して不適切な応答を選択すると、緩和しようとしている問題よりも多くの問題を引き起こす可能性があります。 たとえば、素朴なアプローチとして、パケットが規定された時間ウィンドウの外に到着した場合にコンポーネントがリンクを停止するというものが考えられます。 しかし、このような単純なアクションは、ネットワークよりも攻撃者に役立ってしまう可能性があります。 同様に、そのような問題を単にログに記録するだけでは不十分な場合があります。 応答の遅れが、たとえばネットワークによって制御される機械装置に、物的な損害をもたらす可能性があるためです。 したがって、ありうる効果的なセキュリティー関連のアクションとその設定の幅広さは、DetNetコンポーネントにとって好ましい属性です。

Some possible violations that warrant detection include cases where a packet arrives:

検出に値する違反として考えられるものには、パケットが次のように到着するケースが含まれます。

  • Outside of its prescribed time window
  • Within its time window but with a compromised timestamp that makes it appear that it is not within its window
  • Exceeding the reserved flow bandwidth
  • 規定された時間ウィンドウの外に到着する
  • 時間ウィンドウ内に到着するが、侵害されたタイムスタンプによってウィンドウ内にないように見える
  • 予約されたフローの帯域幅を超えて到着する

Some possible direct actions that may be taken at the data plane include traffic policing and shaping functions (e.g., those described in [RFC2475]), separating flows into per-flow rate-limited queues, and potentially applying active queue management [RFC7567]. However, if those (or any other) actions are to be taken, the system designer must ensure that the results of such actions do not compromise the continued safe operation of the system. For example, the network (i.e., the controller plane and data plane working together) must mitigate in a timely fashion any potential adverse effect on mechanical devices controlled by the network.

データプレーンで取りうる直接的なアクションとしては、トラフィックのポリシングおよびシェーピングの機能（例：[RFC2475]で説明されているもの）、フローをフローごとにレート制限されたキューに分離すること、および場合によってはアクティブキュー管理[RFC7567]を適用することが考えられます。 ただし、それらの（またはその他の）アクションを取る場合、システム設計者は、そのようなアクションの結果がシステムの継続的な安全な運用を損なわないことを保証しなければなりません。 たとえば、ネットワーク（すなわち、連携して動作するコントローラープレーンとデータプレーン）は、ネットワークによって制御される機械装置への潜在的な悪影響を、時宜を得た方法で緩和しなければなりません。

4. DetNet Security Considerations Compared with Diffserv Security Considerations

4. DiffservのセキュリティーとDetNetのセキュリティーに関する考慮事項の比較

DetNet is designed to be compatible with Diffserv [RFC2474] as applied to IT traffic in the DetNet. DetNet also incorporates the use of the 6-bit value of the Differentiated Services Code Point (DSCP) field of the Type of Service (IPv4) and Traffic Class (IPv6) bytes for flow identification. However, the DetNet interpretation of the DSCP value for OT traffic is not equivalent to the per-hop behavior (PHB) selection behavior as defined by Diffserv.

DetNetは、DetNet内のITトラフィックに適用されるDiffserv [RFC2474]と互換性があるように設計されています。 DetNetはまた、フロー識別のために、Type of Service（IPv4）およびTraffic Class（IPv6）バイトのDifferentiated Services Code Point（DSCP）フィールドの6ビットの値の使用を取り入れています。 しかし、OTトラフィックに対するDSCP値のDetNetでの解釈は、Diffservで定義されているホップごとの振る舞い（per-hop behavior、PHB）の選択の振る舞いとは同等ではありません。

Thus, security considerations for DetNet have some aspects in common with Diffserv, in fact overlapping 100% with respect to IP IT traffic. Security considerations for these aspects are part of the existing literature on IP network security, specifically the Security Considerations sections of [RFC2474] and [RFC2475]. However, DetNet also introduces timing and other considerations that are not present in Diffserv, so the Diffserv security considerations are a subset of the DetNet security considerations.

したがって、DetNetのセキュリティーに関する考慮事項にはDiffservと共通する側面があり、実際、IPのITトラフィックに関しては100%重なります。 これらの側面に関するセキュリティーの考慮事項は、IPネットワークセキュリティーに関する既存の文献、具体的には[RFC2474]と[RFC2475]のセキュリティーに関する考慮事項のセクションの一部となっています。 しかし、DetNetはDiffservには存在しないタイミングやその他の考慮事項も導入しているため、Diffservのセキュリティーに関する考慮事項は、DetNetのセキュリティーに関する考慮事項のサブセットです。

In the case of DetNet OT traffic, the DSCP value is interpreted differently than in Diffserv and contributes to determination of the service provided to the packet. In DetNet, there are similar consequences to Diffserv for lack of detection of, or incorrect handling of, packets with mismarked DSCP values, and many of the points made in the Diffserv Security discussions (Section 6.1 of [RFC2475], Section 7 of [RFC2474], and Section 3.3.2.1 of [RFC6274]) are also relevant to DetNet OT traffic though perhaps in modified form. For example, in DetNet, the effect of an undetected or incorrectly handled maliciously mismarked DSCP field in an OT packet is not identical to affecting the PHB of that packet, since DetNet does not use the PHB concept for OT traffic. Nonetheless, the service provided to the packet could be affected, so mitigation measures analogous to those prescribed by Diffserv would be appropriate for DetNet. For example, mismarked DSCP values should not cause failure of network nodes. The remarks in [RFC2474] regarding IPsec and Tunneling Interactions are also relevant (though this is not to say that other sections are less relevant).

DetNetのOTトラフィックの場合、DSCP値はDiffservとは異なる方法で解釈され、パケットに提供されるサービスの決定に寄与します。 DetNetでは、DSCP値が誤ってマークされたパケットを検出できなかったり、誤って処理したりした場合に、Diffservと同様の結果が生じます。 Diffservのセキュリティーに関する議論（[RFC2475]のSection 6.1、[RFC2474]のSection 7、[RFC6274]のSection 3.3.2.1）で述べられている点の多くは、形を変えてではあるかもしれませんが、DetNetのOTトラフィックにも関連します。 たとえば、DetNetでは、OTパケット内の悪意によって誤ってマークされたDSCPフィールドが検出されなかったり誤って処理されたりした場合の影響は、そのパケットのPHBに影響を与えることと同一ではありません。 DetNetはOTトラフィックにPHBの概念を使用しないためです。 それでもなお、パケットに提供されるサービスが影響を受ける可能性があるため、Diffservで規定されているものに類似した緩和策がDetNetにも適切でしょう。 たとえば、誤ってマークされたDSCP値によってネットワークノードの障害が発生すべきではありません。 IPsecとトンネリングの相互作用に関する[RFC2474]の所見も関連します（ただし、他のセクションの関連性が低いというわけではありません）。

In this discussion, interpretation (and any possible intentional re-marking) of the DSCP values of packets destined for DetNet OT flows is expected to occur at the ingress to the DetNet domain; once inside the domain, maintaining the integrity of the DSCP values is subject to the same handling considerations as any other field in the packet.

この議論において、DetNetのOTフロー宛てのパケットのDSCP値の解釈（および意図的な再マーキングがあればそれも）は、DetNetドメインへのイングレスで行われることが想定されています。 いったんドメイン内に入ると、DSCP値の完全性の維持は、パケット内の他のフィールドと同じ取り扱い上の考慮事項の対象となります。

5. Security Threats

5. セキュリティー上の脅威

This section presents a taxonomy of threats and analyzes the possible threats in a DetNet-enabled network. The threats considered in this section are independent of any specific technologies used to implement the DetNet; Section 10 considers attacks that are associated with the DetNet technologies encompassed by [RFC8938].

このセクションでは、脅威の分類を提示し、DetNetに対応したネットワークにおいてありうる脅威を分析します。 このセクションで考慮する脅威は、DetNetの実装に使用される特定の技術には依存しません。 Section 10では、[RFC8938]が対象とするDetNetの技術に関連する攻撃を考慮します。

We distinguish controller plane threats from data plane threats. The attack surface may be the same, but the types of attacks, as well as the motivation behind them, are different. For example, a Delay attack is more relevant to the data plane than to the controller plane. There is also a difference in terms of security solutions; the way you secure the data plane is often different than the way you secure the controller plane.

ここでは、コントローラープレーンの脅威とデータプレーンの脅威を区別します。 攻撃対象領域は同じかもしれませんが、攻撃の種類とその背後にある動機は異なります。 たとえば、遅延攻撃は、コントローラープレーンよりもデータプレーンにより関係します。 セキュリティーの解決策の点でも違いがあり、データプレーンを保護する方法は、多くの場合、コントローラープレーンを保護する方法とは異なります。

5.1. Threat Taxonomy

5.1. 脅威の分類

This document employs organizational elements of the threat models of [RFC7384] and [RFC7835]. This model classifies attackers based on two criteria:

この文書は、[RFC7384]と[RFC7835]の脅威モデルの構成要素を採用しています。 このモデルは、2つの基準に基づいて攻撃者を分類します。

Internal vs. external:
Internal attackers either have access to a trusted segment of the network or possess the encryption or authentication keys. External attackers, on the other hand, do not have the keys and have access only to the encrypted or authenticated traffic.
On-path vs. off-path:
On-path attackers are located in a position that allows interception, modification, or dropping of in-flight protocol packets, whereas off-path attackers can only attack by generating protocol packets.
内部と外部：
内部の攻撃者は、ネットワークの信頼できるセグメントにアクセスできるか、暗号化鍵または認証鍵を保有しています。 一方、外部の攻撃者は鍵を持たず、暗号化または認証されたトラフィックにのみアクセスできます。
経路上と経路外：
経路上の攻撃者は、転送中のプロトコルパケットの傍受、改変、または破棄が可能な位置にいます。 一方、経路外の攻撃者は、プロトコルパケットを生成することによってのみ攻撃できます。

Regarding the boundary between internal vs. external attackers as defined above, note that in this document we do not make concrete recommendations regarding which specific segments of the network are to be protected in any specific way, for example, via encryption or authentication. As a result, the boundary as defined above is not unequivocally specified here. Given that constraint, the reader can view an internal attacker as one who can operate within the perimeter defined by the DetNet Edge Nodes (as defined in the DetNet Architecture [RFC8655]), allowing that the specifics of what is encrypted or authenticated within this perimeter will vary depending on the implementation.

上で定義した内部の攻撃者と外部の攻撃者の境界について、この文書では、ネットワークのどの特定のセグメントを、どのような特定の方法（たとえば、暗号化や認証）で保護すべきかについて、具体的な推奨事項を示していないことに注意してください。 その結果、上で定義した境界は、ここでは明確には規定されていません。 その制約を踏まえて、読者は、内部の攻撃者を、（DetNetアーキテクチャー[RFC8655]で定義されている）DetNetエッジノードによって定義される境界内で活動できる者とみなすことができます。 ただし、この境界内で何が暗号化または認証されるかの詳細は、実装によって異なります。

Care has also been taken to adhere to Section 5 of [RFC3552], both with respect to which attacks are considered out of scope for this document, and also which are considered to be the most common threats (explored further in Section 5.2). Most of the direct threats to DetNet are active attacks (i.e., attacks that modify DetNet traffic), but it is highly suggested that DetNet application developers take appropriate measures to protect the content of the DetNet flows from passive attacks (i.e., attacks that observe but do not modify DetNet traffic), for example, through the use of TLS or DTLS.

また、この文書の範囲外とみなす攻撃と、最も一般的な脅威とみなす攻撃（Section 5.2でさらに詳しく検討します）の両方に関して、[RFC3552]のSection 5に従うよう注意を払っています。 DetNetに対する直接的な脅威のほとんどは能動的攻撃（すなわち、DetNetトラフィックを改変する攻撃）ですが、DetNetアプリケーションの開発者は、たとえばTLSやDTLSを使用することで、DetNetフローのコンテンツを受動的攻撃（すなわち、DetNetトラフィックを観察するが改変はしない攻撃）から保護するための適切な対策を講じることが強く推奨されます。

DetNet-Service, one of the service scenarios described in [DETNET-SERVICE-MODEL], is the case where a service connects DetNet islands, i.e., two or more otherwise independent DetNets are connected via a link that is not intrinsically part of either network. This implies that there could be DetNet traffic flowing over a non-DetNet link, which may provide an attacker with an advantageous opportunity to tamper with DetNet traffic. The security properties of non-DetNet links are outside of the scope of DetNet Security, but it should be noted that use of non-DetNet services to interconnect DetNets merits security analysis to ensure the integrity of the networks involved.

[DETNET-SERVICE-MODEL]で説明されているサービスシナリオの1つであるDetNet-Serviceは、サービスがDetNetの島々を接続するケース、すなわち、本来は独立した2つ以上のDetNetが、どちらのネットワークにも本質的には属さないリンクを介して接続されるケースです。 これは、DetNetトラフィックが非DetNetリンク上を流れる可能性があることを意味し、攻撃者にDetNetトラフィックを改ざんする好機を与える可能性があります。 非DetNetリンクのセキュリティー特性はDetNetセキュリティーの範囲外ですが、DetNet同士を相互接続するために非DetNetサービスを使用する場合は、関係するネットワークの完全性を確保するためにセキュリティー分析を行う価値があることに注意すべきです。

5.2. Threat Analysis

5.2. 脅威の分析

5.2.1. Delay

5.2.1. 遅延

An attacker can maliciously delay DetNet data flow traffic. By delaying the traffic, the attacker can compromise the service of applications that are sensitive to high delays or to high delay variation. The delay may be constant or modulated.

攻撃者は、DetNetのデータフローのトラフィックを悪意を持って遅延させることができます。 トラフィックを遅延させることで、攻撃者は、大きな遅延や大きな遅延変動に敏感なアプリケーションのサービスを損なうことができます。 遅延は一定の場合もあれば、変調されている場合もあります。

5.2.2. DetNet Flow Modification or Spoofing

5.2.2. DetNetフローの改変またはなりすまし

An attacker can modify some header fields of en route packets in a way that causes the DetNet flow identification mechanisms to misclassify the flow. Alternatively, the attacker can inject traffic that is tailored to appear as if it belongs to a legitimate DetNet flow. The potential consequence is that the DetNet flow resource allocation cannot guarantee the performance that is expected when the flow identification works correctly.

攻撃者は、転送途中のパケットのいくつかのヘッダーフィールドを、DetNetのフロー識別メカニズムがフローを誤分類するような方法で改変できます。 あるいは、攻撃者は、正当なDetNetフローに属しているかのように見えるよう細工したトラフィックを注入できます。 その結果として起こりうるのは、フロー識別が正しく機能した場合に期待される性能を、DetNetフローのリソース割り当てが保証できなくなることです。

5.2.3. Resource Segmentation (Inter-segment Attack) Vulnerability

5.2.3. リソースのセグメント化（セグメント間攻撃）の脆弱性

DetNet components are expected to split their resources between DetNet flows in a way that prevents traffic from one DetNet flow from affecting the performance of other DetNet flows and also prevents non-DetNet traffic from affecting DetNet flows. However, perhaps due to implementation constraints, some resources may be partially shared, and an attacker may try to exploit this property. For example, an attacker can inject traffic in order to exhaust network resources such that DetNet packets that share resources with the injected traffic may be dropped or delayed. Such injected traffic may be part of DetNet flows or non-DetNet traffic.

DetNetコンポーネントは、あるDetNetフローのトラフィックが他のDetNetフローの性能に影響を与えることを防ぎ、また非DetNetトラフィックがDetNetフローに影響を与えることも防ぐような方法で、DetNetフロー間でリソースを分割することが想定されています。 しかし、おそらく実装上の制約により、一部のリソースが部分的に共有される場合があり、攻撃者はこの性質を悪用しようとする可能性があります。 たとえば、攻撃者はネットワークリソースを枯渇させるためにトラフィックを注入し、注入されたトラフィックとリソースを共有するDetNetパケットが破棄されたり遅延したりするようにできます。 そのような注入されたトラフィックは、DetNetフローの一部である場合も、非DetNetトラフィックである場合もあります。

Another example of a Resource Segmentation attack is the case in which an attacker is able to overload the exception path queue on the router, i.e., a "slow path" typically taken by control or OAM packets that are diverted from the data plane because they require processing by a CPU. DetNet OT flows are typically configured to take the "fast path" through the data plane to minimize latency. However, if there is only one queue from the forwarding Application-Specific Integrated Circuit (ASIC) to the exception path, and for some reason the system is configured such that any DetNet packets must be handled on this exception path, then saturating the exception path could result in the delaying or dropping of DetNet packets.

リソースのセグメント化攻撃の別の例として、攻撃者がルーター上の例外パスのキュー、すなわち、CPUによる処理が必要なためにデータプレーンから迂回される制御パケットやOAMパケットが通常通る「スローパス」を過負荷にできるケースがあります。 DetNetのOTフローは通常、遅延を最小限に抑えるために、データプレーンを通る「ファストパス」を通るように設定されます。 しかし、転送用の特定用途向け集積回路（Application-Specific Integrated Circuit、ASIC）から例外パスへのキューが1つしかなく、何らかの理由でDetNetパケットをこの例外パスで処理しなければならないようにシステムが設定されている場合、例外パスを飽和させるとDetNetパケットが遅延したり破棄されたりする可能性があります。

5.2.4. Packet Replication and Elimination

5.2.4. パケットの複製と除去

5.2.4.1. Replication: Increased Attack Surface
5.2.4.1. 複製：攻撃対象領域の増加

Redundancy is intended to increase the robustness and survivability of DetNet flows, and replication over multiple paths can potentially mitigate an attack that is limited to a single path. However, the fact that packets are replicated over multiple paths increases the attack surface of the network, i.e., there are more points in the network that may be subject to attacks.

冗長性はDetNetフローの堅牢性と生存性を高めることを目的としており、複数のパスにわたる複製によって、単一のパスに限定された攻撃を緩和できる可能性があります。 しかし、パケットが複数のパスにわたって複製されるという事実は、ネットワークの攻撃対象領域を増加させます。 すなわち、ネットワーク内に攻撃を受ける可能性のある箇所が増えます。

5.2.4.2. Replication-Related Header Manipulation
5.2.4.2. 複製関連のヘッダーの操作

An attacker can manipulate the replication-related header fields. This capability opens the door for various types of attacks. For example:

攻撃者は、複製関連のヘッダーフィールドを操作できます。 この能力は、さまざまな種類の攻撃への扉を開きます。 たとえば、次のようなものです。

Forward both replicas:
Malicious change of a packet SN (Sequence Number) can cause both replicas of the packet to be forwarded. Note that this attack has a similar outcome to a replay attack.
Eliminate both replicas:
SN manipulation can be used to cause both replicas to be eliminated. In this case, an attacker that has access to a single path can cause packets from other paths to be dropped, thus compromising some of the advantage of path redundancy.
Flow hijacking:
An attacker can hijack a DetNet flow with access to a single path by systematically replacing the SNs on the given path with higher SN values. For example, an attacker can replace every SN value S with a higher value S+C, where C is a constant integer. Thus, the attacker creates a false illusion that the attacked path has the lowest delay, causing all packets from other paths to be eliminated in favor of the attacked path. Once the flow from the compromised path is favored by the eliminating bridge, the flow has effectively been hijacked by the attacker. It is now possible for the attacker to either replace en route packets with malicious packets, or to simply inject errors into the packets, causing the packets to be dropped at their destination.
Amplification:
An attacker who injects packets into a flow that is to be replicated will have their attack amplified through the replication process. This is no different than any attacker who injects packets that are delivered through multicast, broadcast, or other point-to-multi-point mechanisms.
両方の複製を転送させる：
パケットのSN（シーケンス番号）を悪意を持って変更すると、パケットの両方の複製が転送される可能性があります。 この攻撃はリプレイ攻撃と同様の結果をもたらすことに注意してください。
両方の複製を除去させる：
SNの操作を利用して、両方の複製を除去させることができます。 この場合、単一のパスにアクセスできる攻撃者が、他のパスからのパケットを破棄させることができ、パスの冗長性の利点の一部を損なうことになります。
フローの乗っ取り：
単一のパスにアクセスできる攻撃者は、そのパス上のSNを体系的により大きなSN値に置き換えることで、DetNetフローを乗っ取ることができます。 たとえば、攻撃者はすべてのSN値Sを、より大きな値S+C（Cは定数の整数）に置き換えることができます。 これにより、攻撃者は攻撃対象のパスが最も遅延が小さいという偽りの錯覚を作り出し、攻撃対象のパスを優先して他のパスからのすべてのパケットが除去されるようにします。 侵害されたパスからのフローが除去を行うブリッジによって優先されるようになると、そのフローは事実上攻撃者に乗っ取られたことになります。 これで攻撃者は、転送途中のパケットを悪意のあるパケットに置き換えることも、単にパケットにエラーを注入して宛先でパケットが破棄されるようにすることもできます。
増幅：
複製されるフローにパケットを注入する攻撃者は、複製のプロセスを通じて攻撃が増幅されます。 これは、マルチキャスト、ブロードキャスト、またはその他のポイントツーマルチポイントのメカニズムを通じて配送されるパケットを注入する攻撃者と何ら変わりはありません。

5.2.5. Controller Plane

5.2.5. コントローラープレーン

5.2.5.1. Path Choice Manipulation
5.2.5.1. パス選択の操作
5.2.5.1.1. Control or Signaling Packet Modification
5.2.5.1.1. 制御パケットまたはシグナリングパケットの改変

An attacker can maliciously modify en route control packets in order to disrupt or manipulate the DetNet path/resource allocation.

攻撃者は、DetNetのパス／リソース割り当てを妨害または操作するために、転送途中の制御パケットを悪意を持って改変できます。

5.2.5.1.2. Control or Signaling Packet Injection
5.2.5.1.2. 制御パケットまたはシグナリングパケットの注入

An attacker can maliciously inject control packets in order to disrupt or manipulate the DetNet path/resource allocation.

攻撃者は、DetNetのパス／リソース割り当てを妨害または操作するために、制御パケットを悪意を持って注入できます。

5.2.5.1.3. Increased Attack Surface
5.2.5.1.3. 攻撃対象領域の増加

One of the possible consequences of a Path Manipulation attack is an increased attack surface. Thus, when the attack described in the previous subsection is implemented, it may increase the potential of other attacks to be performed.

パス操作攻撃によって起こりうる結果の1つは、攻撃対象領域の増加です。 したがって、前のサブセクションで説明した攻撃が実行されると、他の攻撃が実行される可能性が高まる場合があります。

5.2.5.2. Compromised Controller
5.2.5.2. 侵害されたコントローラー

An attacker can subvert a legitimate controller (or subvert another component such that it represents itself as a legitimate controller) with the result that the network nodes incorrectly believe it is authorized to instruct them.

攻撃者は、正当なコントローラーを乗っ取る（または、別のコンポーネントを乗っ取って正当なコントローラーになりすまさせる）ことができ、その結果、ネットワークノードは、そのコントローラーに自分たちへ指示する権限があると誤って信じることになります。

The presence of a compromised node or controller in a DetNet is not a threat that arises as a result of determinism or time sensitivity; the same techniques used to prevent or mitigate against compromised nodes in any network are equally applicable in the DetNet case. The act of compromising a controller may not even be within the capabilities of our defined attacker types -- in other words, it may not be achievable via packet traffic at all, whether internal or external, on path or off path. It might be accomplished, for example, by a human with physical access to the component, who could upload bogus firmware to it via a USB stick. All of this underscores the requirement for careful overall system security design in a DetNet, given that the effects of even one bad actor on the network can be potentially catastrophic.

DetNet内に侵害されたノードやコントローラーが存在することは、決定論や時間への敏感さの結果として生じる脅威ではありません。 あらゆるネットワークで侵害されたノードを防止または緩和するために使用されるのと同じ手法が、DetNetの場合にも同様に適用できます。 コントローラーを侵害する行為は、ここで定義した攻撃者の種類の能力の範囲内にさえない場合があります。 言い換えれば、内部か外部か、経路上か経路外かにかかわらず、パケットトラフィックによってはまったく達成できない場合があります。 たとえば、コンポーネントに物理的にアクセスできる人間が、USBメモリーを介して偽のファームウェアをアップロードすることによって達成される可能性があります。 ネットワーク上のたった1人の悪意のある行為者の影響でさえ破局的になりうることを考えると、これらすべてが、DetNetにおける慎重なシステム全体のセキュリティー設計の必要性を強調しています。

Security concerns specific to any given controller plane technology used in DetNet will be addressed by the DetNet documents associated with that technology.

DetNetで使用される特定のコントローラープレーン技術に固有のセキュリティー上の懸念は、その技術に関連するDetNet文書で扱われます。

5.2.6. Reconnaissance

5.2.6. 偵察

A passive eavesdropper can identify DetNet flows and then gather information about en route DetNet flows, e.g., the number of DetNet flows, their bandwidths, their schedules, or other temporal or statistical properties. The gathered information can later be used to invoke other attacks on some or all of the flows.

受動的な盗聴者は、DetNetフローを識別し、転送途中のDetNetフローに関する情報（例：DetNetフローの数、帯域幅、スケジュール、その他の時間的または統計的な特性）を収集できます。 収集された情報は、後でフローの一部またはすべてに対して他の攻撃を仕掛けるために使用される可能性があります。

DetNet flows are typically uniquely identified by their 6-tuple, i.e., fields within the L3 or L4 header. However, in some implementations, the flow ID may also be augmented by additional per-flow attributes known to the system, e.g., above L4. For the purpose of this document, we assume any such additional fields used for flow ID are encrypted and/or integrity protected from external attackers. Note however that existing OT protocols designed for use on dedicated secure networks may not intrinsically provide such protection, in which case IPsec or transport-layer security mechanisms may be needed.

DetNetフローは通常、その6タプル、すなわちL3またはL4ヘッダー内のフィールドによって一意に識別されます。 しかし、一部の実装では、システムが把握しているフローごとの追加の属性（例：L4より上位のもの）によってフローIDが拡張される場合もあります。 この文書では、フローIDに使用されるそのような追加のフィールドは、外部の攻撃者から暗号化および／または完全性保護されていることを前提とします。 ただし、専用の安全なネットワークでの使用向けに設計された既存のOTプロトコルは、そのような保護を本質的には提供しない場合があり、その場合はIPsecやトランスポート層のセキュリティーメカニズムが必要になる場合があることに注意してください。

5.2.7. Time-Synchronization Mechanisms

5.2.7. 時刻同期のメカニズム

An attacker can use any of the attacks described in [RFC7384] to attack the synchronization protocol, thus affecting the DetNet service.

攻撃者は、[RFC7384]で説明されている攻撃のいずれかを使用して同期プロトコルを攻撃し、それによってDetNetサービスに影響を与えることができます。

6. Security Threat Impacts

6. セキュリティー上の脅威の影響

When designing security for a DetNet, as with any network, it may be prohibitively expensive or technically infeasible to thoroughly protect against every possible threat. Thus, the security designer must be informed (for example, by an application domain expert such as a product manager) regarding the relative significance of the various threats and their impact if a successful attack is carried out. In this section, we present an example of a possible template for such a communication, culminating in a table (Table 2) that lists a set of threats under consideration, and some values characterizing their relative impact in the context of a given industry. The specific threats, industries, and impact values in the table are provided only as an example of this kind of assessment and its communication; they are not intended to be taken literally.

DetNetのセキュリティーを設計する際には、他のネットワークと同様に、ありうるすべての脅威から徹底的に保護することは、法外なコストがかかるか、技術的に実現不可能な場合があります。 したがって、セキュリティーの設計者は、さまざまな脅威の相対的な重要性と、攻撃が成功した場合のその影響について、（たとえば、プロダクトマネージャーなどのアプリケーションドメインの専門家から）情報を得なければなりません。 このセクションでは、そのような情報伝達のためのテンプレートとして考えられるものの例を示します。 その集大成として、検討対象の一連の脅威と、ある業界の文脈でのそれらの相対的な影響を特徴づけるいくつかの値を列挙した表（Table 2）を示します。 表に示す具体的な脅威、業界、影響の値は、この種の評価とその伝達の例としてのみ提供するものであり、文字どおりに受け取られることを意図したものではありません。

This section considers assessment of the relative impacts of the attacks described in Section 5. In this section, the impacts as described assume that the associated mitigation is not present or has failed. Mitigations are discussed in Section 7.

このセクションでは、Section 5で説明した攻撃の相対的な影響の評価を考慮します。 このセクションで説明する影響は、関連する緩和策が存在しないか、失敗したことを前提としています。 緩和策はSection 7で議論します。

In computer security, the impact (or consequence) of an incident can be measured in loss of confidentiality, integrity, or availability of information. In the case of OT or time sensitive networks (though not to the exclusion of IT or non-time-sensitive networks), the impact of an exploit can also include failure or malfunction of mechanical and/or other physical systems.

コンピューターセキュリティーでは、インシデントの影響（または結果）は、情報の機密性、完全性、または可用性の喪失によって測ることができます。 OTネットワークや時間に敏感なネットワークの場合（ITネットワークや時間に敏感でないネットワークを除外するものではありませんが）、エクスプロイトの影響には、機械システムおよび／またはその他の物理システムの故障や誤動作も含まれえます。

DetNet raises these stakes significantly for OT applications, particularly those that may have been designed to run in an OT-only environment and thus may not have been designed for security in an IT environment with its associated components, services, and protocols.

DetNetは、OTアプリケーション、特にOTのみの環境で動作するように設計されており、そのためにITの環境とそれに関連するコンポーネント、サービス、プロトコルにおけるセキュリティーを考慮して設計されていない可能性のあるOTアプリケーションにとって、こうしたリスクを大幅に高めます。

The extent of impact of a successful vulnerability exploit varies considerably by use case and by industry; additional insight regarding the individual use cases is available from "Deterministic Networking Use Cases" [RFC8578]. Each of those use cases is represented in Table 2, including Pro Audio, Electrical Utilities, Industrial M2M (split into two areas: M2M Data Gathering and M2M Control Loop), and others.

脆弱性のエクスプロイトが成功した場合の影響の大きさは、ユースケースや業界によって大きく異なります。 個々のユースケースに関する追加の洞察は、「Deterministic Networking Use Cases」[RFC8578]から得られます。 これらの各ユースケースは、プロオーディオ、電力事業、産業用M2M（M2Mデータ収集とM2M制御ループの2つの領域に分割）などを含めて、Table 2に示されています。

DetNet dependence maps how much the following DetNet service objectives contribute to impact of failure: time dependency, data integrity, source node integrity, availability, and latency/jitter.

6.1. Delay Attacks

6.1. 遅延攻撃

6.1.1. Data Plane Delay Attacks

6.1.1. データプレーンの遅延攻撃

Note that "Delay attack" also includes the possibility of a "negative delay" or early arrival of a packet, or possibly adversely changing the timestamp value.

「遅延攻撃」には、「負の遅延」すなわちパケットの早期到着や、タイムスタンプの値を不利に変更する可能性も含まれることに注意してください。

Delayed messages in a DetNet link can result in the same behavior as dropped messages in ordinary networks, since the services attached to the DetNet flow are likely to have strict delivery time requirements.

DetNetフローに付随するサービスには厳格な配送時間の要件がある可能性が高いため、DetNetリンクで遅延したメッセージは、通常のネットワークで破棄されたメッセージと同じ振る舞いをもたらす可能性があります。

For a single-path scenario, disruption within the single flow is a real possibility. In a multipath scenario, large delays or instabilities in one DetNet flow can also lead to increased buffer and processor resource consumption at the eliminating router.

単一パスのシナリオでは、単一のフロー内での途絶が現実に起こりえます。 マルチパスのシナリオでは、1つのDetNetフローにおける大きな遅延や不安定さが、除去を行うルーターでのバッファーとプロセッサーのリソース消費の増加につながる可能性もあります。

A data plane Delay attack on a system controlling substantial moving devices, for example, in industrial automation, can cause physical damage. For example, if the network promises a bounded latency of 2 ms for a flow, yet the machine receives it with 5 ms latency, the control loop of the machine may become unstable.

たとえば産業オートメーションにおいて、相当な規模の可動装置を制御するシステムに対するデータプレーンの遅延攻撃は、物理的な損害を引き起こす可能性があります。 たとえば、ネットワークがあるフローに対して2ミリ秒の有界遅延を約束しているにもかかわらず、機械がそれを5ミリ秒の遅延で受信した場合、機械の制御ループが不安定になる可能性があります。

6.1.2. Controller Plane Delay Attacks

6.1.2. コントローラープレーンの遅延攻撃

In and of itself, this is not directly a threat to the DetNet service, but the effects of delaying control messages can have quite adverse effects later.

それ自体はDetNetサービスに対する直接的な脅威ではありませんが、制御メッセージを遅延させることの影響は、後になってかなりの悪影響を及ぼす可能性があります。

  • Delayed teardown can lead to resource leakage, which in turn can result in failure to allocate new DetNet flows, finally giving rise to a denial-of-service attack.
  • Failure to deliver, or severely delaying, controller plane messages adding an endpoint to a multicast group will prevent the new endpoint from receiving expected frames thus disrupting expected behavior.
  • Delaying messages that remove an endpoint from a group can lead to loss of privacy, as the endpoint will continue to receive messages even after it is supposedly removed.
  • 解体の遅延はリソースのリークにつながる可能性があり、それが新しいDetNetフローの割り当ての失敗をもたらし、最終的にはサービス拒否攻撃を引き起こす可能性があります。
  • マルチキャストグループにエンドポイントを追加するコントローラープレーンのメッセージを配送できなかったり、大幅に遅延させたりすると、新しいエンドポイントが期待されるフレームを受信できなくなり、期待される振る舞いが妨げられます。
  • グループからエンドポイントを削除するメッセージを遅延させると、プライバシーの喪失につながる可能性があります。 エンドポイントは、削除されたはずの後もメッセージを受信し続けるためです。

6.2. Flow Modification and Spoofing

6.2. フローの改変となりすまし

6.2.1. Flow Modification

6.2.1. フローの改変

If the contents of a packet header or body can be modified by the attacker, this can cause the packet to be routed incorrectly or dropped, or the payload to be corrupted or subtly modified. Thus, the potential impact of a Modification attack includes disrupting the application as well as the network equipment.

攻撃者がパケットのヘッダーや本体の内容を改変できる場合、パケットが誤ってルーティングされたり破棄されたりする可能性や、ペイロードが破損したり巧妙に改変されたりする可能性があります。 したがって、改変攻撃の潜在的な影響には、アプリケーションとネットワーク機器の両方の妨害が含まれます。

6.2.2. Spoofing

6.2.2. なりすまし

6.2.2.1. Data Plane Spoofing
6.2.2.1. データプレーンのなりすまし

Spoofing data plane messages can result in increased resource consumption on the routers throughout the network as it will increase buffer usage and processor utilization. This can lead to resource exhaustion and/or increased delay.

データプレーンのメッセージのなりすましは、バッファーの使用量とプロセッサーの使用率を増加させるため、ネットワーク全体のルーターでのリソース消費の増加をもたらす可能性があります。 これはリソースの枯渇および／または遅延の増加につながる可能性があります。

If the attacker manages to create valid headers, the false messages can be forwarded through the network, using part of the allocated bandwidth. This in turn can cause legitimate messages to be dropped when the resource budget has been exhausted.

攻撃者が有効なヘッダーを作成することに成功した場合、偽のメッセージは割り当てられた帯域幅の一部を使用してネットワーク内を転送される可能性があります。 その結果、リソースのバジェットが使い果たされると、正当なメッセージが破棄される可能性があります。

Finally, the endpoint will have to deal with invalid messages being delivered to the endpoint instead of (or in addition to) a valid message.

最後に、エンドポイントは、有効なメッセージの代わりに（または有効なメッセージに加えて）エンドポイントに配送される無効なメッセージに対処しなければならなくなります。

6.2.2.2. Controller Plane Spoofing
6.2.2.2. コントローラープレーンのなりすまし

A successful Controller Plane Spoofing attack will potentially have adverse effects. It can do virtually anything from:

コントローラープレーンのなりすまし攻撃が成功すると、悪影響が及ぶ可能性があります。 それにより、事実上次のようなあらゆることが可能になります。

  • modifying existing DetNet flows by changing the available bandwidth
  • adding or removing endpoints from a DetNet flow
  • dropping DetNet flows completely
  • falsely creating new DetNet flows (exhausting the systems resources or enabling DetNet flows that are outside the control of the network engineer)
  • 利用可能な帯域幅を変更して既存のDetNetフローを改変する
  • DetNetフローにエンドポイントを追加したり、DetNetフローからエンドポイントを削除したりする
  • DetNetフローを完全に破棄する
  • 新しいDetNetフローを不正に作成する（システムのリソースを枯渇させたり、ネットワークエンジニアの制御外にあるDetNetフローを有効にしたりする）

6.3. Segmentation Attacks (Injection)

6.3. セグメント化攻撃（注入）

6.3.1. Data Plane Segmentation

6.3.1. データプレーンのセグメント化

Injection of false messages in a DetNet flow could lead to exhaustion of the available bandwidth for that flow if the routers attribute these false messages to the resource budget of that flow.

DetNetフローへの偽のメッセージの注入は、ルーターがこれらの偽のメッセージをそのフローのリソースバジェットに帰属させる場合、そのフローで利用可能な帯域幅の枯渇につながる可能性があります。

In a multipath scenario, injected messages will cause increased processor utilization in elimination routers. If enough paths are subject to malicious injection, the legitimate messages can be dropped. Likewise, it can cause an increase in buffer usage. In total, it will consume more resources in the routers than normal, giving rise to a resource-exhaustion attack on the routers.

マルチパスのシナリオでは、注入されたメッセージにより、除去を行うルーターでのプロセッサーの使用率が増加します。 十分な数のパスが悪意のある注入を受けると、正当なメッセージが破棄される可能性があります。 同様に、バッファーの使用量が増加する可能性もあります。 全体として、ルーターで通常よりも多くのリソースを消費することになり、ルーターに対するリソース枯渇攻撃を引き起こします。

If a DetNet flow is interrupted, the end application will be affected by what is now a non-deterministic flow. Note that there are many possible sources of flow interruptions, for example, but not limited to, such physical-layer conditions as a broken wire or a radio link that is compromised by interference.

DetNetフローが中断されると、エンドアプリケーションは、もはや非決定論的になったフローの影響を受けます。 フローの中断には多くの原因が考えられることに注意してください。 たとえば、断線や干渉によって損なわれた無線リンクなどの物理層の状態がありますが、これらに限定されません。

6.3.2. Controller Plane Segmentation

6.3.2. コントローラープレーンのセグメント化

In a successful Controller Plane Segmentation attack, control messages are acted on by nodes in the network, unbeknownst to the central controller or the network engineer. This has the potential to:

コントローラープレーンのセグメント化攻撃が成功すると、中央のコントローラーやネットワークエンジニアが知らないうちに、ネットワーク内のノードが制御メッセージに基づいて動作します。 これにより、次のことが起こる可能性があります。

  • create new DetNet flows (exhausting resources)
  • drop existing DetNet flows (denial of service)
  • add end stations to a multicast group (loss of privacy)
  • remove end stations from a multicast group (reduction of service)
  • modify the DetNet flow attributes (affecting available bandwidth)
  • 新しいDetNetフローを作成する（リソースの枯渇）
  • 既存のDetNetフローを破棄する（サービス拒否）
  • マルチキャストグループにエンドステーションを追加する（プライバシーの喪失）
  • マルチキャストグループからエンドステーションを削除する（サービスの低下）
  • DetNetフローの属性を改変する（利用可能な帯域幅への影響）

If an attacker can inject control messages without the central controller knowing, then one or more components in the network may get into a state that is not expected by the controller. At that point, if the controller initiates a command, the effect of that command may not be as expected, since the target of the command may have started from a different initial state.

攻撃者が中央のコントローラーに知られることなく制御メッセージを注入できる場合、ネットワーク内の1つ以上のコンポーネントが、コントローラーが想定していない状態になる可能性があります。 その時点でコントローラーがコマンドを開始すると、コマンドの対象が異なる初期状態から始まっている可能性があるため、そのコマンドの効果が期待どおりにならない場合があります。

6.4. Replication and Elimination

6.4. 複製と除去

The Replication and Elimination functions are relevant only to data plane messages as controller plane messages are not subject to multipath routing.

コントローラープレーンのメッセージはマルチパスルーティングの対象ではないため、複製と除去の機能はデータプレーンのメッセージにのみ関係します。

6.4.1. Increased Attack Surface

6.4.1. 攻撃対象領域の増加

The impact of an increased attack surface is that it increases the probability that the network can be exposed to an attacker. This can facilitate a wide range of specific attacks, and their respective impacts are discussed in other subsections of this section.

攻撃対象領域の増加の影響は、ネットワークが攻撃者にさらされる確率が高まることです。 これにより、さまざまな具体的な攻撃が容易になる可能性があり、それぞれの影響については、このセクションの他のサブセクションで議論します。

6.4.2. Header Manipulation at Elimination Routers

6.4.2. 除去を行うルーターでのヘッダーの操作

This attack can potentially cause DoS to the application that uses the attacked DetNet flows or to the network equipment that forwards them. Furthermore, it can allow an attacker to manipulate the network paths and the behavior of the network layer.

この攻撃は、攻撃を受けたDetNetフローを使用するアプリケーションや、それを転送するネットワーク機器に対してDoSを引き起こす可能性があります。 さらに、攻撃者がネットワークのパスやネットワーク層の振る舞いを操作できるようになる可能性があります。

6.5. Control or Signaling Packet Modification

6.5. 制御パケットまたはシグナリングパケットの改変

If control packets are subject to manipulation undetected, the network can be severely compromised.

制御パケットが検出されないまま操作されうる場合、ネットワークは深刻に侵害される可能性があります。

6.6. Control or Signaling Packet Injection

6.6. 制御パケットまたはシグナリングパケットの注入

If an attacker can inject control packets undetected, the network can be severely compromised.

攻撃者が検出されることなく制御パケットを注入できる場合、ネットワークは深刻に侵害される可能性があります。

6.7. Reconnaissance

6.7. 偵察

Of all the attacks, this is one of the most difficult to detect and counter.

これは、あらゆる攻撃の中で最も検出と対処が難しいものの1つです。

An attacker can, at their leisure, observe over time various aspects of the messaging and signaling, learning the intent and purpose of the traffic flows. Then at some later date, possibly at an important time in the operational context, they might launch an attack based on that knowledge.

攻撃者は、時間をかけて、メッセージングとシグナリングのさまざまな側面を好きなだけ観察し、トラフィックフローの意図と目的を知ることができます。 そして後日、おそらく運用の文脈において重要な時期に、その知識に基づいて攻撃を仕掛ける可能性があります。

The flow ID in the header of the data plane messages gives an attacker a very reliable identifier for DetNet traffic, and this traffic has a high probability of going to lucrative targets.

データプレーンのメッセージのヘッダー内のフローIDは、攻撃者にとってDetNetトラフィックの非常に信頼性の高い識別子となり、このトラフィックは価値の高い標的に向かう確率が高いです。

Applications that are ported from a private OT network to the higher visibility DetNet environment may need to be adapted to limit distinctive flow properties that could make them susceptible to reconnaissance.

プライベートなOTネットワークから、より可視性の高いDetNet環境に移植されたアプリケーションは、偵察を受けやすくなる可能性のある特徴的なフローの特性を抑えるように適応させる必要がある場合があります。

6.8. Attacks on Time-Synchronization Mechanisms

6.8. 時刻同期メカニズムへの攻撃

DetNet relies on an underlying time-synchronization mechanism; therefore, a compromised synchronization mechanism may cause DetNet nodes to malfunction. Specifically, DetNet flows may fail to meet their latency requirements and deterministic behavior, thus causing DoS to DetNet applications.

DetNetは基盤となる時刻同期メカニズムに依存しています。 したがって、侵害された同期メカニズムによってDetNetノードが誤動作する可能性があります。 具体的には、DetNetフローが遅延の要件と決定論的な振る舞いを満たせなくなり、DetNetアプリケーションに対するDoSを引き起こす可能性があります。

6.9. Attacks on Path Choice

6.9. パス選択への攻撃

This is covered in part in Section 6.3 (Segmentation Attacks (Injection)) and, as with Replication and Elimination (see Section 6.4), this is relevant for data plane messages.

これはSection 6.3（Segmentation Attacks (Injection)）で部分的に扱っています。 また、複製と除去（Section 6.4を参照してください）と同様に、これはデータプレーンのメッセージに関係します。

7. Security Threat Mitigation

7. セキュリティー上の脅威の緩和

This section describes a set of measures that can be taken to mitigate the attacks described in Section 5. These mitigations should be viewed as a set of tools, any of which can be used individually or in concert. The DetNet component and/or system and/or application designer can apply these tools as necessary based on a system-specific threat analysis.

このセクションでは、Section 5で説明した攻撃を緩和するために講じることのできる一連の対策について説明します。 これらの緩和策は、個別にも組み合わせても使用できる一連のツールとみなすべきです。 DetNetのコンポーネントおよび／またはシステムおよび／またはアプリケーションの設計者は、システム固有の脅威分析に基づいて、必要に応じてこれらのツールを適用できます。

Some of the technology-specific security considerations and mitigation approaches are further discussed in DetNet data plane solution documents, such as [RFC8938], [RFC8939], [RFC8964], [RFC9025], and [RFC9056].

技術固有のセキュリティーに関する考慮事項と緩和のアプローチの一部については、[RFC8938]、[RFC8939]、[RFC8964]、[RFC9025]、[RFC9056]などのDetNetデータプレーンのソリューション文書でさらに議論されています。

7.1. Path Redundancy

7.1. パスの冗長性

Description:

Path redundancy is a DetNet flow that can be forwarded simultaneously over multiple paths. Packet Replication and Elimination [RFC8655] provide resiliency to dropped or delayed packets. This redundancy improves the robustness to failures and to on-path attacks.

Note: At the time of this writing, PREOF is not defined for the IP data plane.

Related attacks:

Path redundancy can be used to mitigate various on-path attacks, including attacks described in Sections 5.2.1, 5.2.2, 5.2.3, and 5.2.7. However, it is also possible that multiple paths may make it more difficult to locate the source of an on-path attacker.

A Delay Modulation attack could result in extensively exercising otherwise unused code paths to expose hidden flaws. Subtle race conditions and memory allocation bugs in error-handling paths are classic examples of this.

説明：

パスの冗長性とは、複数のパス上で同時に転送できるDetNetフローのことです。 パケットの複製と除去[RFC8655]は、破棄されたパケットや遅延したパケットに対する回復力を提供します。 この冗長性により、障害と経路上の攻撃に対する堅牢性が向上します。

注：この執筆時点では、PREOFはIPデータプレーンについては定義されていません。

関連する攻撃：

パスの冗長性は、セクション5.2.1、5.2.2、5.2.3、5.2.7で説明した攻撃を含む、さまざまな経路上の攻撃を緩和するために使用できます。 ただし、複数のパスがあることによって、経路上の攻撃者の発生源を特定することがより困難になる可能性もあります。

遅延変調攻撃によって、通常は使用されないコードパスが大量に実行され、隠れた欠陥が露呈する可能性があります。 エラー処理パスにおける微妙な競合状態やメモリー割り当てのバグは、その典型的な例です。

7.2. Integrity Protection

7.2. 完全性保護

Description:

Integrity protection in the scope of DetNet is the ability to detect if a packet header has been modified (maliciously or otherwise) and if so, take some appropriate action (as discussed in Section 7.7). The decision on where in the network to apply integrity protection is part of the DetNet system design, and the implementation of the protection method itself is a part of a DetNet component design.

The most common technique for detecting header modification is the use of a Message Authentication Code (MAC) (see Section 10 for examples). The MAC can be distributed either in line (included in the same packet) or via a side channel. Of these, the in-line method is generally preferred due to the low latency that may be required on DetNet flows and the relative complexity and computational overhead of a sideband approach.

There are different levels of security available for integrity protection, ranging from the basic ability to detect if a header has been corrupted in transit (no malicious attack) to stopping a skilled and determined attacker capable of both subtly modifying fields in the headers as well as updating an unkeyed checksum. Common for all are the 2 steps that need to be performed in both ends. The first is computing the checksum or MAC. The corresponding verification step must perform the same steps before comparing the provided with the computed value. Only then can the receiver be reasonably sure that the header is authentic.

The most basic protection mechanism consists of computing a simple checksum of the header fields and providing it to the next entity in the packets path for verification. Using a MAC combined with a secret key provides the best protection against Modification and Replication attacks (see Sections 5.2.2 and 5.2.4). This MAC usage needs to be part of a security association that is established and managed by a security association protocol (such as IKEv2 for IPsec security associations). Integrity protection in the controller plane is discussed in Section 7.6. The secret key, regardless of the MAC used, must be protected from falling into the hands of unauthorized users. Once key management becomes a topic, it is important to understand that this is a delicate process and should not be undertaken lightly. BCP 107 [BCP107] provides best practices in this regard.

DetNet system and/or component designers need to be aware of these distinctions and enforce appropriate integrity-protection mechanisms as needed based on a threat analysis. Note that adding integrity-protection mechanisms may introduce latency; thus, many of the same considerations in Section 7.5.1 also apply here.

Packet Sequence Number Integrity Considerations:

The use of PREOF in a DetNet implementation implies the use of a sequence number for each packet. There is a trust relationship between the component that adds the sequence number and the component that removes the sequence number. The sequence number may be end-to-end source to destination, or it may be added/deleted by network edge components. The adder and remover(s) have the trust relationship because they are the ones that ensure that the sequence numbers are not modifiable. Thus, sequence numbers can be protected by using authenticated encryption or by a MAC without using encryption. Between the adder and remover there may or may not be replication and elimination functions. The elimination functions must be able to see the sequence numbers. Therefore, if encryption is done between adders and removers, it must not obscure the sequence number. If the sequence removers and the eliminators are in the same physical component, it may be possible to obscure the sequence number; however, that is a layer violation and is not recommended practice.

Note: At the time of this writing, PREOF is not defined for the IP data plane.

Related attacks:

Integrity protection mitigates attacks related to modification and tampering, including the attacks described in Sections 5.2.2 and 5.2.4.

説明：

DetNetの範囲における完全性保護とは、パケットのヘッダーが（悪意によるものか否かを問わず）改変されたかどうかを検出し、改変された場合に（Section 7.7で議論するような）何らかの適切なアクションを取る能力のことです。 ネットワーク内のどこに完全性保護を適用するかの決定はDetNetのシステム設計の一部であり、保護方法自体の実装はDetNetのコンポーネント設計の一部です。

ヘッダーの改変を検出するための最も一般的な手法は、メッセージ認証コード（Message Authentication Code、MAC）の使用です（例についてはSection 10を参照してください）。 MACは、インライン（同じパケットに含める）またはサイドチャネルを介して配布できます。 これらのうち、DetNetフローで必要とされる可能性のある低遅延と、サイドバンドのアプローチの相対的な複雑さと計算上のオーバーヘッドのため、一般にインラインの方法が好まれます。

完全性保護に利用できるセキュリティーのレベルにはさまざまなものがあり、転送中にヘッダーが破損したかどうか（悪意のある攻撃ではない）を検出する基本的な能力から、ヘッダー内のフィールドを巧妙に改変するとともに鍵なしのチェックサムを更新することもできる、熟練した執拗な攻撃者を阻止するものまであります。 すべてに共通するのは、両端で実行する必要のある2つのステップです。 1つ目は、チェックサムまたはMACの計算です。 対応する検証ステップでは、提供された値と計算された値を比較する前に、同じステップを実行しなければなりません。 そうして初めて、受信者はヘッダーが真正であると合理的に確信できます。

最も基本的な保護メカニズムは、ヘッダーフィールドの単純なチェックサムを計算し、検証のためにパケットのパス上の次のエンティティーに提供することです。 秘密鍵と組み合わせたMACを使用すると、改変攻撃と複製攻撃（セクション5.2.2と5.2.4を参照してください）に対して最良の保護が得られます。 このMACの使用は、セキュリティーアソシエーションプロトコル（IPsecのセキュリティーアソシエーションに対するIKEv2など）によって確立および管理されるセキュリティーアソシエーションの一部である必要があります。 コントローラープレーンにおける完全性保護については、Section 7.6で議論します。 使用するMACにかかわらず、秘密鍵は許可されていないユーザーの手に渡らないように保護しなければなりません。 鍵管理が話題になったら、これは繊細なプロセスであり、軽々しく着手すべきではないことを理解することが重要です。 BCP 107 [BCP107]は、この点に関するベストプラクティスを提供しています。

DetNetのシステムおよび／またはコンポーネントの設計者は、これらの違いを認識し、脅威分析に基づいて、必要に応じて適切な完全性保護メカニズムを適用する必要があります。 完全性保護メカニズムを追加すると遅延が生じる可能性があることに注意してください。 したがって、Section 7.5.1の考慮事項の多くがここにも当てはまります。

パケットのシーケンス番号の完全性に関する考慮事項：

DetNetの実装でPREOFを使用することは、各パケットにシーケンス番号を使用することを意味します。 シーケンス番号を追加するコンポーネントとシーケンス番号を削除するコンポーネントの間には、信頼関係があります。 シーケンス番号は、送信元から宛先までのエンドツーエンドの場合もあれば、ネットワークのエッジのコンポーネントによって追加／削除される場合もあります。 追加するものと削除するものは、シーケンス番号が改変できないことを保証する役割を担うため、信頼関係を持ちます。 したがって、シーケンス番号は、認証付き暗号を使用するか、暗号化を使用せずにMACによって保護できます。 追加するものと削除するものの間には、複製と除去の機能がある場合もない場合もあります。 除去の機能は、シーケンス番号を参照できなければなりません。 したがって、追加するものと削除するものの間で暗号化を行う場合、シーケンス番号を隠してはなりません。 シーケンス番号を削除するものと除去するものが同じ物理コンポーネント内にある場合は、シーケンス番号を隠すことが可能な場合もありますが、それは層の違反であり、推奨される慣行ではありません。

注：この執筆時点では、PREOFはIPデータプレーンについては定義されていません。

関連する攻撃：

完全性保護は、セクション5.2.2と5.2.4で説明した攻撃を含む、改変と改ざんに関連する攻撃を緩和します。

7.3. DetNet Node Authentication

7.3. DetNetノードの認証

Description:
Authentication verifies the identity of DetNet nodes (including DetNet Controller Plane nodes), and this enables mitigation of Spoofing attacks. While integrity protection (Section 7.2) prevents intermediate nodes from modifying information, authentication can provide traffic origin verification, i.e., to verify that each packet in a DetNet flow is from a known source. Although node authentication and integrity protection are two different goals of a security protocol, in most cases, a common protocol (such as IPsec [RFC4301] or MACsec [IEEE802.1AE-2018]) is used for achieving both purposes.
Related attacks:
DetNet node authentication is used to mitigate attacks related to spoofing, including the attacks of Sections 5.2.2 and 5.2.4.
説明：
認証は、DetNetノード（DetNetのコントローラープレーンのノードを含む）の身元を検証するものであり、これによってなりすまし攻撃を緩和できます。 完全性保護（Section 7.2）は中間ノードによる情報の改変を防止しますが、認証はトラフィックの発信元の検証、すなわち、DetNetフロー内の各パケットが既知の送信元からのものであることの検証を提供できます。 ノードの認証と完全性保護はセキュリティープロトコルの2つの異なる目標ですが、ほとんどの場合、両方の目的を達成するために共通のプロトコル（IPsec [RFC4301]やMACsec [IEEE802.1AE-2018]など）が使用されます。
関連する攻撃：
DetNetノードの認証は、セクション5.2.2と5.2.4の攻撃を含む、なりすましに関連する攻撃を緩和するために使用されます。

7.4. Synthetic Traffic Insertion

7.4. 合成トラフィックの挿入

Description:
With some queuing methods such as [IEEE802.1Qch-2017], it is possible to introduce synthetic traffic in order to regularize the timing of packet transmission. (Synthetic traffic typically consists of randomly generated packets injected in the network to mask observable transmission patterns in the flows, which may allow an attacker to gain insight into the content of the flows). This can subsequently reduce the value of passive monitoring from internal threats (see Section 5) as it will be much more difficult to associate discrete events with particular network packets.
Related attacks:
Removing distinctive temporal properties of individual packets or flows can be used to mitigate against reconnaissance attacks (Section 5.2.6). For example, synthetic traffic can be used to maintain constant traffic rate even when no user data is transmitted, thus making it difficult to collect information about the times at which users are active and the times at which DetNet flows are added or removed.
Traffic Insertion Challenges:

Once an attacker is able to monitor the frames traversing a network to such a degree that they can differentiate between best-effort traffic and traffic belonging to a specific DetNet flow, it becomes difficult to not reveal to the attacker whether a given frame is valid traffic or an inserted frame. Thus, having the DetNet components generate and remove the synthetic traffic may or may not be a viable option unless certain challenges are solved; for example, but not limited to:

  • Inserted traffic must be indistinguishable from valid stream traffic from the viewpoint of the attacker.
  • DetNet components must be able to safely identify and remove all inserted traffic (and only inserted traffic).

  • The controller plane must manage where to insert and remove synthetic traffic, but this information must not be revealed to an attacker.

    An alternative design is to have the insertion and removal of synthetic traffic be performed at the application layer rather than by the DetNet itself. For example, the use of RTP padding to reduce information leakage from variable-bit-rate audio transmission via the Secure Real-time Transport Protocol (SRTP) is discussed in [RFC6562].

説明：
[IEEE802.1Qch-2017]などの一部のキューイング方式では、パケット送信のタイミングを規則化するために合成トラフィックを導入できます。 （合成トラフィックは通常、フロー内の観察可能な送信パターンを隠すためにネットワークに注入される、ランダムに生成されたパケットで構成されます。そうした送信パターンによって、攻撃者がフローの内容についての洞察を得られる可能性があるためです。） これにより、個別のイベントを特定のネットワークパケットに関連付けることがはるかに困難になるため、内部の脅威（Section 5を参照してください）による受動的な監視の価値を引き下げることができます。
関連する攻撃：
個々のパケットやフローの特徴的な時間的特性を取り除くことは、偵察攻撃（Section 5.2.6）の緩和に使用できます。 たとえば、合成トラフィックを使用すると、ユーザーデータが送信されていないときでも一定のトラフィックレートを維持できるため、ユーザーがアクティブな時刻や、DetNetフローが追加または削除される時刻に関する情報を収集することが困難になります。
トラフィック挿入の課題：

攻撃者が、ネットワークを通過するフレームを、ベストエフォートのトラフィックと特定のDetNetフローに属するトラフィックとを区別できる程度まで監視できるようになると、あるフレームが有効なトラフィックなのか挿入されたフレームなのかを攻撃者に明かさないことは困難になります。 したがって、DetNetコンポーネントに合成トラフィックを生成および削除させることは、特定の課題が解決されない限り、実行可能な選択肢である場合もそうでない場合もあります。 そうした課題の例として、次のものがありますが、これらに限定されません。

  • 挿入されたトラフィックは、攻撃者の視点からは有効なストリームのトラフィックと区別できないものでなければなりません。
  • DetNetコンポーネントは、挿入されたすべてのトラフィックを（そして挿入されたトラフィックのみを）安全に識別して削除できなければなりません。

  • コントローラープレーンは、合成トラフィックをどこで挿入および削除するかを管理しなければなりませんが、この情報を攻撃者に明かしてはなりません。

    別の設計として、合成トラフィックの挿入と削除を、DetNet自体ではなくアプリケーション層で実行させる方法があります。 たとえば、Secure Real-time Transport Protocol（SRTP）による可変ビットレートの音声送信からの情報漏洩を減らすためにRTPのパディングを使用することが、[RFC6562]で議論されています。

7.5. Encryption

7.5. 暗号化

Description:

Reconnaissance attacks (Section 5.2.6) can be mitigated to some extent through the use of encryption, thereby preventing the attacker from accessing the packet header or contents. Specific encryption protocols will depend on the lower layers that DetNet is forwarded over. For example, IP flows may be forwarded over IPsec [RFC4301], and Ethernet flows may be secured using MACsec [IEEE802.1AE-2018].

However, despite the use of encryption, a reconnaissance attack can provide the attacker with insight into the network, even without visibility into the packet. For example, an attacker can observe which nodes are communicating with which other nodes, including when, how often, and with how much data. In addition, the timing of packets may be correlated in time with external events such as action of an external device. Such information may be used by the attacker, for example, in mapping out specific targets for a different type of attack at a different time.

DetNet nodes do not have any need to inspect the payload of any DetNet packets, making them data agnostic. This means that end-to-end encryption at the application layer is an acceptable way to protect user data.

Note that reconnaissance is a threat that is not specific to DetNet flows; therefore, reconnaissance mitigation will typically be analyzed and provided by a network operator regardless of whether DetNet flows are deployed. Thus, encryption requirements will typically not be defined in DetNet technology-specific specifications, but considerations of using DetNet in encrypted environments will be discussed in these specifications. For example, Section 5.1.2.3 of [RFC8939] discusses flow identification of DetNet flows running over IPsec.

Related attacks:
As noted above, encryption can be used to mitigate reconnaissance attacks (Section 5.2.6). However, for a DetNet to provide differentiated quality of service on a flow-by-flow basis, the network must be able to identify the flows individually. This implies that in a reconnaissance attack, the attacker may also be able to track individual flows to learn more about the system.
説明：

偵察攻撃（Section 5.2.6）は、暗号化を使用して攻撃者がパケットのヘッダーや内容にアクセスできないようにすることで、ある程度緩和できます。 具体的な暗号化プロトコルは、DetNetがその上で転送される下位層によって異なります。 たとえば、IPフローはIPsec [RFC4301]上で転送でき、イーサネットのフローはMACsec [IEEE802.1AE-2018]を使用して保護できます。

しかし、暗号化を使用していても、偵察攻撃は、パケットの中身が見えなくても、攻撃者にネットワークに関する洞察を与える可能性があります。 たとえば、攻撃者は、どのノードがどの他のノードと通信しているか、それがいつ、どのくらいの頻度で、どのくらいのデータ量で行われているかを観察できます。 さらに、パケットのタイミングが、外部デバイスの動作などの外部イベントと時間的に相関している場合があります。 そのような情報は、たとえば、別の時期に別の種類の攻撃を行うための特定の標的を洗い出すために、攻撃者によって使用される可能性があります。

DetNetノードはDetNetパケットのペイロードを検査する必要がまったくないため、データに依存しません。 これは、アプリケーション層でのエンドツーエンドの暗号化が、ユーザーデータを保護するための許容可能な方法であることを意味します。

偵察はDetNetフローに固有の脅威ではないことに注意してください。 したがって、偵察の緩和は通常、DetNetフローが展開されているかどうかにかかわらず、ネットワーク運用者によって分析され、提供されます。 そのため、暗号化の要件は通常、DetNetの技術固有の仕様では定義されませんが、暗号化された環境でDetNetを使用する際の考慮事項はそれらの仕様で議論されます。 たとえば、[RFC8939]のSection 5.1.2.3では、IPsec上で動作するDetNetフローのフロー識別について議論しています。

関連する攻撃：
上で述べたように、暗号化は偵察攻撃（Section 5.2.6）の緩和に使用できます。 しかし、DetNetがフローごとに差別化されたサービス品質を提供するためには、ネットワークがフローを個別に識別できなければなりません。 これは、偵察攻撃において、攻撃者も個々のフローを追跡してシステムについてさらに知ることができる可能性があることを意味します。

7.5.1. Encryption Considerations for DetNet

7.5.1. DetNetにおける暗号化に関する考慮事項

Any compute time that is required for encryption and decryption processing ("crypto") must be included in the flow latency calculations. Thus, cryptographic algorithms used in a DetNet must have bounded worst-case execution times, and these values must be used in the latency calculations. Fortunately, encryption and decryption operations typically are designed to have constant execution times in order to avoid side channel leakage.

暗号化と復号の処理（「暗号処理」）に必要な計算時間は、すべてフローの遅延計算に含めなければなりません。 したがって、DetNetで使用される暗号アルゴリズムは、最悪ケースの実行時間に上限がなければならず、これらの値を遅延計算に使用しなければなりません。 幸いなことに、暗号化と復号の操作は通常、サイドチャネルによる漏洩を回避するために、一定の実行時間を持つように設計されています。

Some cryptographic algorithms are symmetric in encode/decode time (such as AES), and others are asymmetric (such as public key algorithms). There are advantages and disadvantages to the use of either type in a given DetNet context. The discussion in this document relates to the timing implications of crypto for DetNet; it is assumed that integrity considerations are covered elsewhere in the literature.

暗号アルゴリズムには、エンコード／デコードの時間が対称的なもの（AESなど）と、非対称的なもの（公開鍵アルゴリズムなど）があります。 あるDetNetの文脈において、どちらの種類を使用するかには、それぞれ長所と短所があります。 この文書での議論は、DetNetに対する暗号処理のタイミング上の影響に関するものです。 完全性に関する考慮事項は、文献の他の箇所で扱われていることを前提とします。

Asymmetrical crypto is typically not used in networks on a packet-by-packet basis due to its computational cost. For example, if only endpoint checks or checks at a small number of intermediate points are required, asymmetric crypto can be used to authenticate distribution or exchange of a secret symmetric crypto key; a successful check based on that key will provide traffic origin verification as long as the key is kept secret by the participants. TLS (v1.3 [RFC8446], in particular, Section 4.1 ("Key Exchange Messages")) and IKEv2 [RFC6071] are examples of this for endpoint checks.

非対称暗号は、その計算コストのため、通常はネットワークでパケットごとに使用されることはありません。 たとえば、エンドポイントでのチェックや少数の中間地点でのチェックのみが必要な場合、非対称暗号を使用して、秘密の対称暗号鍵の配布または交換を認証できます。 その鍵に基づくチェックが成功すれば、参加者によって鍵が秘密に保たれている限り、トラフィックの発信元の検証が得られます。 TLS（v1.3 [RFC8446]、特にセクション4.1 (「Key Exchange Messages」)）とIKEv2 [RFC6071]は、エンドポイントでのチェックにおけるこの例です。

However, if secret symmetric keys are used for this purpose, the key must be given to all relays, which increases the probability of a secret key being leaked. Also, if any relay is compromised or faulty, then it may inject traffic into the flow. Group key management protocols can be used to automate management of such symmetric keys; for an example in the context of IPsec, see [IPSECME-G-IKEV2].

しかし、この目的で秘密の対称鍵を使用する場合、その鍵をすべての中継者に与えなければならず、秘密鍵が漏洩する確率が高まります。 また、いずれかの中継者が侵害されたり故障したりした場合、その中継者がフローにトラフィックを注入する可能性があります。 グループ鍵管理プロトコルを使用して、そのような対称鍵の管理を自動化できます。 IPsecの文脈での例については、[IPSECME-G-IKEV2]を参照してください。

Alternatively, asymmetric crypto can provide traffic origin verification at every intermediate node. For example, a DetNet flow can be associated with an (asymmetric) keypair, such that the private key is available to the source of the flow and the public key is distributed with the flow information, allowing verification at every node for every packet. However, this is more computationally expensive.

あるいは、非対称暗号によって、すべての中間ノードでトラフィックの発信元の検証を提供できます。 たとえば、DetNetフローを（非対称の）鍵ペアに関連付け、秘密鍵をフローの送信元が利用でき、公開鍵をフロー情報とともに配布することで、すべてのノードですべてのパケットを検証できるようにすることが可能です。 しかし、これは計算コストがより高くなります。

In either case, origin verification also requires replay detection as part of the security protocol to prevent an attacker from recording and resending traffic, e.g., as a denial-of-service attack on flow forwarding resources.

いずれの場合も、発信元の検証には、攻撃者がトラフィックを記録して再送すること（例：フローの転送リソースに対するサービス拒否攻撃として）を防ぐために、セキュリティープロトコルの一部としてリプレイの検出も必要です。

In the general case, cryptographic hygiene requires the generation of new keys during the lifetime of an encrypted flow (e.g., see Section 9 of [RFC4253]), and any such key generation (or key exchange) requires additional computing time, which must be accounted for in the latency calculations for that flow. For modern ECDH (Elliptical Curve Diffie-Hellman) key-exchange operations (such as x25519 [RFC7748]), these operations can be performed in constant (predictable) time; however, this is not universally true (for example, for legacy RSA key exchange [RFC4432]). Thus, implementers should be aware of the time properties of these algorithms and avoid algorithms that make constant-time implementation difficult or impossible.

一般的な場合、暗号の衛生管理として、暗号化されたフローの有効期間中に新しい鍵を生成する必要があり（例：[RFC4253]のSection 9を参照してください）、そのような鍵生成（または鍵交換）には追加の計算時間が必要であり、それをそのフローの遅延計算で考慮しなければなりません。 最新のECDH（楕円曲線ディフィー・ヘルマン）鍵交換の操作（x25519 [RFC7748]など）は、一定の（予測可能な）時間で実行できますが、これは普遍的に当てはまるわけではありません（たとえば、レガシーなRSA鍵交換[RFC4432]の場合）。 したがって、実装者はこれらのアルゴリズムの時間特性を認識し、定数時間の実装を困難または不可能にするアルゴリズムを避けるべきです。

7.6. Control and Signaling Message Protection

7.6. 制御メッセージとシグナリングメッセージの保護

Description:
Control and signaling messages can be protected through the use of any or all of encryption, authentication, and integrity-protection mechanisms. Compared with data flows, the timing constraints for controller and signaling messages may be less strict, and the number of such packets may be fewer. If that is the case in a given application, then it may enable the use of asymmetric cryptography for the signing of both payload and headers for such messages, as well as encrypting the payload. Given that a DetNet is managed by a central controller, the use of a shared public key approach for these processes is well proven. This is further discussed in Section 7.5.1.
Related attacks:
These mechanisms can be used to mitigate various attacks on the controller plane, as described in Sections 5.2.5, 5.2.7, and 5.2.5.1.
説明：
制御メッセージとシグナリングメッセージは、暗号化、認証、完全性保護のメカニズムのいずれかまたはすべてを使用して保護できます。 データフローと比較して、コントローラーメッセージとシグナリングメッセージのタイミングの制約はそれほど厳しくない場合があり、そのようなパケットの数も少ない場合があります。 あるアプリケーションでそうであれば、そのようなメッセージのペイロードとヘッダーの両方の署名、およびペイロードの暗号化に、非対称暗号を使用できる場合があります。 DetNetが中央のコントローラーによって管理されていることを考えると、これらのプロセスに共有された公開鍵のアプローチを使用することは十分に実証されています。 これについては、Section 7.5.1でさらに議論します。
関連する攻撃：
これらのメカニズムは、セクション5.2.5、5.2.7、5.2.5.1で説明したように、コントローラープレーンに対するさまざまな攻撃を緩和するために使用できます。

7.7. Dynamic Performance Analytics

7.7. 動的性能分析

Description:

Incorporating Dynamic Performance Analytics (DPA) implies that the DetNet design includes a performance monitoring system to validate that timing guarantees are being met and to detect timing violations or other anomalies that may be the symptom of a security attack or system malfunction. If this monitoring system detects unexpected behavior, it must then cause action to be initiated to address the situation in an appropriate and timely manner, either at the data plane or controller plane or both in concert.

The overall DPA system can thus be decomposed into the "detection" and "notification" functions. Although the time-specific DPA performance indicators and their implementation will likely be specific to a given DetNet, and as such are nascent technology at the time of this writing, DPA is commonly used in existing networks so we can make some observations on how such a system might be implemented for a DetNet given that it would need to be adapted to address the time-specific performance indicators.

Detection Mechanisms:

Measurement of timing performance can be done via "passive" or "active" monitoring, as discussed below.

Examples of passive monitoring strategies include:

  • Monitoring of queue and buffer levels, e.g., via active queue management (e.g., [RFC7567]).
  • Monitoring of per-flow counters.
  • Measurement of link statistics such as traffic volume, bandwidth, and QoS.
  • Detection of dropped packets.
  • Use of commercially available Network Monitoring tools.

Examples of active monitoring include:

  • In-band timing measurements (such as packet arrival times), e.g., by timestamping and packet inspection.

  • Use of OAM. For DetNet-specific OAM considerations, see [DETNET-IP-OAM] and [DETNET-MPLS-OAM]. Note: At the time of this writing, specifics of DPA have not been developed for the DetNet OAM but could be a subject for future investigation.

    • For OAM for Ethernet specifically, see also Connectivity Fault Management (CFM [IEEE802.1Q]), which defines protocols and practices for OAM for paths through 802.1 bridges and LANs.
  • Out-of-band detection. Following the data path or parts of a data path, for example, Bidirectional Forwarding Detection (BFD, e.g., [RFC5880]).

Note that for some measurements (e.g., packet delay), it may be necessary to make and reconcile measurements from more than one physical location (e.g., a source and destination), possibly in both directions, in order to arrive at a given performance indicator value.

Notification Mechanisms:

Making DPA measurement results available at the right place(s) and time(s) to effect timely response can be challenging. Two notification mechanisms that are in general use are NETCONF/YANG Notifications and the proprietary local telemetry interfaces provided with components from some vendors. The Constrained Application Protocol (CoAP) Observe Option [RFC7641] could also be relevant to such scenarios.

At the time of this writing, YANG Notifications are not addressed by the DetNet YANG documents; however, this may be a topic for future work. It is possible that some of the passive mechanisms could be covered by notifications from non-DetNet-specific YANG modules; for example, if there is OAM or other performance monitoring that can monitor delay bounds, then that could have its own associated YANG data model, which could be relevant to DetNet, for example, some "threshold" values for timing measurement notifications.

At the time of this writing, there is an IETF Working Group for network/performance monitoring (IP Performance Metrics (IPPM)). See also previous work by the completed Remote Network Monitoring Working Group (RMONMIB). See also "An Overview of the IETF Network Management Standards", [RFC6632].

Vendor-specific local telemetry may be available on some commercially available systems, whereby the system can be programmed (via a proprietary dedicated port and API) to monitor and report on specific conditions, based on both passive and active measurements.

Related attacks:

Performance analytics can be used to detect various attacks, including the ones described in Section 5.2.1 (Delay attack), Section 5.2.3 (Resource Segmentation attack), and Section 5.2.7 (Time-Synchronization attack). Once detection and notification have occurred, the appropriate action can be taken to mitigate the threat.

For example, in the case of data plane Delay attacks, one possible mitigation is to timestamp the data at the source and timestamp it again at the destination, and if the resulting latency does not meet the service agreement, take appropriate action. Note that DetNet specifies packet sequence numbering; however, it does not specify use of packet timestamps, although they may be used by the underlying transport (for example, TSN [IEEE802.1BA]) to provide the service.

説明：

動的性能分析（Dynamic Performance Analytics、DPA）を組み込むということは、タイミングの保証が満たされていることを検証し、セキュリティー攻撃やシステムの誤動作の兆候である可能性のあるタイミング違反やその他の異常を検出するための性能監視システムが、DetNetの設計に含まれることを意味します。 この監視システムが予期しない振る舞いを検出した場合、データプレーンまたはコントローラープレーン、あるいはその両方の連携により、状況に適切かつ時宜を得た方法で対処するアクションを開始させなければなりません。

したがって、DPAシステム全体は「検出」と「通知」の機能に分解できます。 時間に固有のDPAの性能指標とその実装は、特定のDetNetに固有のものになる可能性が高く、この執筆時点ではまだ発展途上の技術ですが、DPAは既存のネットワークで一般的に使用されています。 そのため、時間に固有の性能指標に対処するよう適応させる必要があることを踏まえつつ、そのようなシステムをDetNet向けにどのように実装できるかについて、いくつかの見解を述べることができます。

検出メカニズム：

タイミング性能の測定は、以下で議論するように、「受動的」または「能動的」な監視によって行うことができます。

受動的な監視の戦略の例には、次のものがあります。

  • たとえばアクティブキュー管理（例：[RFC7567]）による、キューとバッファーのレベルの監視。
  • フローごとのカウンターの監視。
  • トラフィック量、帯域幅、QoSなどのリンク統計の測定。
  • 破棄されたパケットの検出。
  • 市販のネットワーク監視ツールの使用。

能動的な監視の例には、次のものがあります。

  • たとえばタイムスタンプの付与とパケットの検査による、帯域内でのタイミング測定（パケットの到着時刻など）。

  • OAMの使用。 DetNet固有のOAMに関する考慮事項については、[DETNET-IP-OAM]と[DETNET-MPLS-OAM]を参照してください。 注：この執筆時点では、DetNetのOAMについてDPAの詳細は策定されていませんが、将来の調査の対象となる可能性があります。

    • 特にイーサネットのOAMについては、接続性障害管理（Connectivity Fault Management、CFM [IEEE802.1Q]）も参照してください。 これは、802.1ブリッジとLANを通過するパスのOAMのためのプロトコルと慣行を定義しています。
  • 帯域外での検出。 データパスまたはデータパスの一部をたどるもので、たとえば双方向フォワーディング検出（Bidirectional Forwarding Detection、BFD。例：[RFC5880]）です。

一部の測定（例：パケットの遅延）では、ある性能指標の値を得るために、複数の物理的な場所（例：送信元と宛先）で、場合によっては両方向で、測定を行ってそれらを突き合わせる必要がある場合があることに注意してください。

通知メカニズム：

時宜を得た応答を行うために、DPAの測定結果を適切な場所と時刻に利用可能にすることは、困難な場合があります。 一般に使用されている2つの通知メカニズムは、NETCONF/YANG通知と、一部のベンダーのコンポーネントで提供されている独自のローカルテレメトリーインターフェイスです。 Constrained Application Protocol（CoAP）のObserveオプション[RFC7641]も、このようなシナリオに関連する可能性があります。

この執筆時点では、YANG通知はDetNetのYANG文書では扱われていませんが、これは将来の作業のトピックとなる可能性があります。 受動的なメカニズムの一部は、DetNet固有ではないYANGモジュールからの通知でカバーできる可能性があります。 たとえば、遅延の上限を監視できるOAMやその他の性能監視がある場合、それには独自の関連するYANGデータモデルがある可能性があり、それはDetNetに関連する可能性があります（たとえば、タイミング測定の通知に関するいくつかの「しきい値」の値）。

この執筆時点では、ネットワーク／性能の監視に関するIETFワーキンググループ（IP Performance Metrics（IPPM））があります。 また、すでに完了したRemote Network Monitoringワーキンググループ（RMONMIB）による以前の作業も参照してください。 「An Overview of the IETF Network Management Standards」[RFC6632]も参照してください。

ベンダー固有のローカルテレメトリーが一部の市販のシステムで利用できる場合があります。 それにより、受動的な測定と能動的な測定の両方に基づいて、特定の状態を監視して報告するように（独自の専用ポートとAPIを介して）システムをプログラムできます。

関連する攻撃：

性能分析は、Section 5.2.1（遅延攻撃）、Section 5.2.3（リソースのセグメント化攻撃）、Section 5.2.7（時刻同期攻撃）で説明した攻撃を含む、さまざまな攻撃の検出に使用できます。 検出と通知が行われたら、脅威を緩和するための適切なアクションを取ることができます。

たとえば、データプレーンの遅延攻撃の場合、考えられる緩和策の1つは、送信元でデータにタイムスタンプを付与し、宛先で再度タイムスタンプを付与し、その結果の遅延がサービス契約を満たしていない場合に適切なアクションを取ることです。 DetNetはパケットのシーケンス番号付けを規定していますが、パケットのタイムスタンプの使用は規定していないことに注意してください。 ただし、サービスを提供するために、基盤となるトランスポート（たとえば、TSN [IEEE802.1BA]）によってタイムスタンプが使用される場合があります。

8.1.1. Sub-network Layer

8.1.1. サブネットワーク層

DetNet is expected to run over various transmission mediums, with Ethernet being the first identified. Attacks such as Delay or Reconnaissance might be implemented differently on a different transmission medium; however, the impact on the DetNet as a whole would be essentially the same. We thus conclude that all attacks and impacts that would be applicable to DetNet over Ethernet (i.e., all those named in this document) would also be applicable to DetNet over other transmission mediums.

DetNetはさまざまな伝送媒体上で動作することが想定されており、最初に特定されたのはイーサネットです。 遅延や偵察などの攻撃は、伝送媒体が異なれば異なる方法で実行される可能性がありますが、DetNet全体への影響は本質的に同じです。 したがって、イーサネット上のDetNetに当てはまるすべての攻撃と影響（すなわち、この文書で挙げたすべてのもの）は、他の伝送媒体上のDetNetにも当てはまると結論づけます。

With respect to mitigations, some methods are specific to the Ethernet medium, for example, time-aware scheduling using 802.1Qbv [IEEE802.1Qbv-2015] can protect against excessive use of bandwidth at the ingress -- for other mediums, other mitigations would have to be implemented to provide analogous protection.

緩和策に関しては、一部の方法はイーサネットの媒体に固有のものです。 たとえば、802.1Qbv [IEEE802.1Qbv-2015]を使用した時間を考慮したスケジューリングは、イングレスでの帯域幅の過剰な使用から保護できます。 他の媒体については、同様の保護を提供するために他の緩和策を実装しなければならないでしょう。

8.1.2. Central Administration

8.1.2. 集中管理

A DetNet network can be controlled by a centralized network configuration and control system. Such a system may be in a single central location, or it may be distributed across multiple control entities that function together as a unified control system for the network.

DetNetネットワークは、集中型のネットワーク設定・制御システムによって制御できます。 そのようなシステムは、単一の中央の場所にある場合もあれば、ネットワークの統一された制御システムとして連携して機能する複数の制御エンティティーに分散している場合もあります。

All attacks named in this document that are relevant to controller plane packets (and the controller itself) are relevant to this theme, including Path Manipulation, Path Choice, Control Packet Modification or Injection, Reconnaissance, and Attacks on Time-Synchronization Mechanisms.

この文書で挙げた攻撃のうち、コントローラープレーンのパケット（およびコントローラー自体）に関連するものはすべて、このテーマに関係します。 これには、パス操作、パス選択、制御パケットの改変または注入、偵察、時刻同期メカニズムへの攻撃が含まれます。

8.1.3. Hot Swap

8.1.3. ホットスワップ

A DetNet network is not expected to be "plug and play"; it is expected that there is some centralized network configuration and control system. However, the ability to "hot swap" components (e.g., due to malfunction) is similar enough to "plug and play" that this kind of behavior may be expected in DetNet networks, depending on the implementation.

DetNetネットワークは「プラグアンドプレイ」であることは想定されておらず、何らかの集中型のネットワーク設定・制御システムが存在することが想定されています。 しかし、（たとえば誤動作による）コンポーネントの「ホットスワップ」の能力は「プラグアンドプレイ」に十分に似ているため、実装によっては、DetNetネットワークでこの種の振る舞いが想定される場合があります。

An attack surface related to hot swap is that the DetNet network must at least consider input at runtime from components that were not part of the initial configuration of the network. Even a "perfect" (or "hitless") replacement of a component at runtime would not necessarily be ideal, since presumably one would want to distinguish it from the original for OAM purposes (e.g., to report hot swap of a failed component).

ホットスワップに関連する攻撃対象領域は、DetNetネットワークが、ネットワークの初期設定には含まれていなかったコンポーネントからの実行時の入力を、少なくとも考慮しなければならないという点です。 実行時のコンポーネントの「完全な」（または「無瞬断の」）交換であっても、必ずしも理想的とは限りません。 おそらく、OAMの目的（例：故障したコンポーネントのホットスワップを報告するため）で、交換されたコンポーネントを元のコンポーネントと区別したいと考えられるためです。

This implies that an attack such as Flow Modification, Spoofing, or Inter-segment (which could introduce packets from a "new" component, i.e., one heretofore unknown on the network) could be used to exploit the need to consider such packets (as opposed to rejecting them out of hand as one would do if one did not have to consider introduction of a new component).

これは、フローの改変、なりすまし、セグメント間の攻撃（「新しい」コンポーネント、すなわちこれまでネットワーク上で知られていなかったコンポーネントからのパケットを持ち込む可能性があります）などの攻撃が、そのようなパケットを考慮する必要性（新しいコンポーネントの導入を考慮する必要がなければ行うように、即座に拒否するのではなく）を悪用するために使用される可能性があることを意味します。

To mitigate this situation, deployments should provide a method for dynamic and secure registration of new components, and (possibly manual) deregistration and re-keying of retired components. This would avoid the situation in which the network must accommodate potentially insecure packet flows from unknown components.

この状況を緩和するために、展開においては、新しいコンポーネントを動的かつ安全に登録する方法と、退役したコンポーネントの（場合によっては手動による）登録解除と鍵の再設定の方法を提供すべきです。 これにより、ネットワークが未知のコンポーネントからの安全でない可能性のあるパケットフローを受け入れなければならない状況を回避できます。

Similarly, if the network was designed to support runtime replacement of a clock component, then presence (or apparent presence) and thus consideration of packets from a new such component could affect the network, or the time synchronization of the network, for example, by initiating a new Best Master Clock selection process. These types of attacks should therefore be considered when designing hot-swap-type functionality (see [RFC7384]).

同様に、ネットワークがクロックコンポーネントの実行時の交換をサポートするように設計されている場合、そのような新しいコンポーネントの存在（または見かけ上の存在）、ひいてはそのコンポーネントからのパケットを考慮することが、たとえば新しいベストマスタークロックの選択プロセスを開始することによって、ネットワークやネットワークの時刻同期に影響を与える可能性があります。 したがって、ホットスワップ型の機能を設計する際には、これらの種類の攻撃を考慮すべきです（[RFC7384]を参照してください）。

8.1.4. Data Flow Information Models

8.1.4. データフローの情報モデル

DetNet specifies new YANG data models [DETNET-YANG] that may present new attack surfaces. Per IETF guidelines, security considerations for any YANG data model are expected to be part of the YANG data model specification, as described in [IETF-YANG-SEC].

DetNetは、新しい攻撃対象領域となる可能性のある新しいYANGデータモデル[DETNET-YANG]を規定しています。 IETFのガイドラインに従い、[IETF-YANG-SEC]で説明されているように、YANGデータモデルのセキュリティーに関する考慮事項は、そのYANGデータモデルの仕様の一部となることが想定されています。

8.1.5. L2 and L3 Integration

8.1.5. L2とL3の統合

A DetNet network integrates Layer 2 (bridged) networks (e.g., AVB/TSN LAN) and Layer 3 (routed) networks (e.g., IP) via the use of well-known protocols such as IP, MPLS Pseudowire, and Ethernet. Various DetNet documents address many specific aspects of Layer 2 and Layer 3 integration within a DetNet, and these are not individually referenced here; security considerations for those aspects are covered within those documents or within the related subsections of the present document.

DetNetネットワークは、IP、MPLS疑似ワイヤー、イーサネットなどのよく知られたプロトコルを使用して、レイヤー2（ブリッジ）ネットワーク（例：AVB/TSN LAN）とレイヤー3（ルーティング）ネットワーク（例：IP）を統合します。 さまざまなDetNet文書が、DetNet内でのレイヤー2とレイヤー3の統合の多くの具体的な側面を扱っていますが、ここでは個別に参照しません。 それらの側面に関するセキュリティーの考慮事項は、それらの文書内、またはこの文書の関連するサブセクション内で扱われています。

Please note that although there are no entries in the L2 and L3 Integration line of the Mapping between Themes and Attacks table (Table 5), this does not imply that there could be no relevant attacks related to L2-L3 integration.

テーマと攻撃の対応付けの表（Table 5）のL2とL3の統合の行には項目がありませんが、これはL2とL3の統合に関連する攻撃が存在しえないことを意味するものではないことに注意してください。

8.1.6. End-to-End Delivery

8.1.6. エンドツーエンドの配送

Packets that are part of a resource-reserved DetNet flow are not to be dropped by the DetNet due to congestion. Packets may however be dropped for intended reasons, for example, security measures. For example, consider the case in which a packet becomes corrupted (whether incidentally or maliciously) such that the resulting flow ID incidentally matches the flow ID of another DetNet flow, potentially resulting in additional unauthorized traffic on the latter. In such a case, it may be a security requirement that the system report and/or take some defined action, perhaps when a packet drop count threshold has been reached (see also Section 7.7).

リソース予約済みのDetNetフローの一部であるパケットは、輻輳によってDetNetで破棄されることはありません。 ただし、セキュリティー対策など、意図された理由でパケットが破棄されることはあります。 たとえば、（偶発的か悪意によるものかを問わず）パケットが破損し、その結果のフローIDがたまたま別のDetNetフローのフローIDと一致し、後者のフローに許可されていない追加のトラフィックが生じる可能性があるケースを考えます。 このような場合、おそらくパケットの破棄数がしきい値に達したときに、システムが報告および／または何らかの定義されたアクションを取ることがセキュリティー要件となる場合があります（Section 7.7も参照してください）。

A data plane attack may force packets to be dropped, for example, as a result of a Delay attack, Replication/Elimination attack, or Flow Modification attack.

データプレーンの攻撃によって、たとえば遅延攻撃、複製／除去攻撃、フロー改変攻撃の結果として、パケットが強制的に破棄される可能性があります。

The same result might be obtained by a Controller plane attack, e.g., Path Manipulation or Signaling Packet Modification.

同じ結果が、コントローラープレーンの攻撃（例：パス操作やシグナリングパケットの改変）によって得られる可能性もあります。

An attack may also cause packets that should not be delivered to be delivered, such as by forcing packets from one (e.g., replicated) path to be preferred over another path when they should not be (Replication attack), or by Flow Modification, or Path Choice or Packet Injection. A Time-Synchronization attack could cause a system that was expecting certain packets at certain times to accept unintended packets based on compromised system time or time windowing in the scheduler.

攻撃によって、配送されるべきでないパケットが配送される可能性もあります。 たとえば、ある（例：複製された）パスからのパケットを、本来優先されるべきでないときに別のパスよりも強制的に優先させること（複製攻撃）や、フローの改変、パス選択、パケットの注入によってです。 時刻同期攻撃によって、特定の時刻に特定のパケットを期待していたシステムが、侵害されたシステム時刻やスケジューラーの時間ウィンドウに基づいて、意図しないパケットを受け入れてしまう可能性があります。

8.1.7. Replacement for Proprietary Fieldbuses and Ethernet-Based Networks

8.1.7. 独自のフィールドバスとイーサネットベースのネットワークの置き換え

There are many proprietary "fieldbuses" used in Industrial and other industries, as well as proprietary non-interoperable deterministic Ethernet-based networks. DetNet is intended to provide an open-standards-based alternative to such buses/networks. In cases where a DetNet intersects with such fieldbuses/networks or their protocols, such as by protocol emulation or access via a gateway, new attack surfaces can be opened.

産業分野やその他の業界では、多くの独自の「フィールドバス」や、独自の相互運用性のない決定論的なイーサネットベースのネットワークが使用されています。 DetNetは、そのようなバス／ネットワークに代わる、オープン標準に基づく代替手段を提供することを目的としています。 プロトコルのエミュレーションやゲートウェイを介したアクセスなどによって、DetNetがそのようなフィールドバス／ネットワークやそのプロトコルと交差する場合、新しい攻撃対象領域が開かれる可能性があります。

For example, an Inter-segment or Controller plane attack such as Path Manipulation, Path Choice, or Control Packet Modification/Injection could be used to exploit commands specific to such a protocol or that are interpreted differently by the different protocols or gateway.

たとえば、セグメント間攻撃や、パス操作、パス選択、制御パケットの改変／注入などのコントローラープレーンの攻撃が、そのようなプロトコルに固有のコマンドや、異なるプロトコルやゲートウェイによって異なる解釈をされるコマンドを悪用するために使用される可能性があります。

8.1.8. Deterministic vs. Best-Effort Traffic

8.1.8. 決定論的トラフィックとベストエフォートのトラフィック

Most of the themes described in this document address OT (reserved) DetNet flows -- this item is intended to address issues related to IT traffic on a DetNet.

この文書で説明するテーマのほとんどはOT（予約済み）のDetNetフローを扱っていますが、この項目はDetNet上のITトラフィックに関連する問題を扱うことを目的としています。

DetNet is intended to support coexistence of time-sensitive operational (OT, deterministic) traffic and informational (IT, "best effort") traffic on the same ("unified") network.

DetNetは、時間に敏感な運用（OT、決定論的）トラフィックと情報（IT、「ベストエフォート」）トラフィックが同じ（「統一された」）ネットワーク上で共存することをサポートすることを目的としています。

With DetNet, this coexistence will become more common, and mitigations will need to be established. The fact that the IT traffic on a DetNet is limited to a corporate-controlled network makes this a less difficult problem compared to being exposed to the open Internet; however, this aspect of DetNet security should not be underestimated.

DetNetによってこの共存はより一般的になり、緩和策を確立する必要が出てきます。 DetNet上のITトラフィックが企業によって制御されるネットワークに限定されているという事実により、オープンなインターネットにさらされる場合と比べてこれはそれほど困難な問題ではなくなりますが、DetNetのセキュリティーのこの側面を過小評価すべきではありません。

An Inter-segment attack can flood the network with IT-type traffic with the intent of disrupting the handling of IT traffic and/or the goal of interfering with OT traffic. Presumably, if the DetNet flow reservation and isolation of the DetNet is well designed (better-designed than the attack), then interference with OT traffic should not result from an attack that floods the network with IT traffic.

セグメント間攻撃は、ITトラフィックの処理を妨害する意図および／またはOTトラフィックに干渉する目的で、IT型のトラフィックでネットワークをフラッディングする可能性があります。 おそらく、DetNetフローの予約とDetNetの分離が適切に設計されている（攻撃よりも優れた設計である）なら、ITトラフィックでネットワークをフラッディングする攻撃によってOTトラフィックへの干渉が生じることはないはずです。

The handling of IT traffic (i.e., traffic that by definition is not guaranteed any given deterministic service properties) by the DetNet will by definition not be given the DetNet-specific protections provided to DetNet (resource-reserved) flows. The implication is that the IT traffic on the DetNet network will necessarily have its own specific set of product (component or system) requirements for protection against attacks such as DoS; presumably they will be less stringent than those for OT flows, but nonetheless, component and system designers must employ whatever mitigations will meet the specified security requirements for IT traffic for the given component or DetNet.

DetNetによるITトラフィック（すなわち、定義上、決定論的なサービス特性が何も保証されていないトラフィック）の処理には、定義上、DetNet（リソース予約済みの）フローに提供されるDetNet固有の保護は与えられません。 これが意味するのは、DetNetネットワーク上のITトラフィックには、DoSなどの攻撃に対する保護のための独自の製品（コンポーネントまたはシステム）要件が必然的に存在するということです。 おそらくそれらはOTフローの要件ほど厳しくはないでしょうが、それでもなお、コンポーネントとシステムの設計者は、そのコンポーネントまたはDetNetについてITトラフィックに対して規定されたセキュリティー要件を満たす緩和策を何であれ採用しなければなりません。

The network design as a whole also needs to consider possible application-level dependencies of OT-type applications on services provided by the IT part of the network; for example, does the OT application depend on IT network services such as DNS or OAM? If such dependencies exist, how are malicious packet flows handled? Such considerations are typically outside the scope of DetNet proper, but nonetheless need to be addressed in the overall DetNet network design for a given use case.

ネットワーク設計全体では、OT型のアプリケーションが、ネットワークのIT部分によって提供されるサービスにアプリケーションレベルで依存している可能性も考慮する必要があります。 たとえば、OTアプリケーションは、DNSやOAMなどのITネットワークサービスに依存しているでしょうか。 そのような依存関係が存在する場合、悪意のあるパケットフローはどのように処理されるでしょうか。 そのような考慮事項は通常、DetNet本来の範囲外ですが、それでもなお、あるユースケースのDetNetネットワーク設計全体において対処する必要があります。

8.1.9. Deterministic Flows

8.1.9. 決定論的フロー

Reserved bandwidth data flows (deterministic flows) must provide the allocated bandwidth and must be isolated from each other.

帯域幅が予約されたデータフロー（決定論的フロー）は、割り当てられた帯域幅を提供しなければならず、互いに分離されていなければなりません。

A Spoofing or Inter-segment attack that adds packet traffic to a bandwidth-reserved DetNet flow could cause that flow to occupy more bandwidth than it was allocated, resulting in interference with other DetNet flows.

帯域幅が予約されたDetNetフローにパケットトラフィックを追加するなりすまし攻撃やセグメント間攻撃によって、そのフローが割り当てられた帯域幅を超えて帯域幅を占有し、他のDetNetフローへの干渉をもたらす可能性があります。

A Flow Modification, Spoofing, Header Manipulation, or Control Packet Modification attack could cause packets from one flow to be directed to another flow, thus breaching isolation between the flows.

フローの改変、なりすまし、ヘッダーの操作、または制御パケットの改変の攻撃によって、あるフローのパケットが別のフローに向けられ、フロー間の分離が破られる可能性があります。

8.1.10. Unused Reserved Bandwidth

8.1.10. 使用されていない予約済み帯域幅

If bandwidth reservations are made for a DetNet flow but the associated bandwidth is not used at any point in time, that bandwidth is made available on the network for best-effort traffic. However, note that security considerations for best-effort traffic on a DetNet network is out of scope of the present document, provided that any such attacks on best-effort traffic do not affect performance for DetNet OT traffic.

DetNetフローに対して帯域幅の予約が行われていても、関連する帯域幅がある時点で使用されていない場合、その帯域幅はネットワーク上でベストエフォートのトラフィックに利用可能になります。 ただし、ベストエフォートのトラフィックに対するそのような攻撃がDetNetのOTトラフィックの性能に影響を与えない限り、DetNetネットワーク上のベストエフォートのトラフィックに関するセキュリティーの考慮事項はこの文書の範囲外であることに注意してください。

8.1.11. Interoperability

8.1.11. 相互運用性

The DetNet specifications as a whole are intended to enable an ecosystem in which multiple vendors can create interoperable products, thus promoting component diversity and potentially higher numbers of each component manufactured. Toward that end, the security measures and protocols discussed in this document are intended to encourage interoperability.

DetNetの仕様全体は、複数のベンダーが相互運用可能な製品を作成できるエコシステムを可能にし、それによってコンポーネントの多様性と、各コンポーネントの製造数の増加を促進することを目的としています。 そのために、この文書で議論するセキュリティー対策とプロトコルは、相互運用性を促進することを目的としています。

Given that the DetNet specifications are unambiguously written and that the implementations are accurate, the property of interoperability should not in and of itself cause security concerns; however, flaws in interoperability between components could result in security weaknesses. The network operator, as well as system and component designers, can all contribute to reducing such weaknesses through interoperability testing.

DetNetの仕様が曖昧さなく記述され、実装が正確であれば、相互運用性という特性それ自体がセキュリティー上の懸念を引き起こすことはないはずです。 しかし、コンポーネント間の相互運用性の欠陥は、セキュリティー上の弱点をもたらす可能性があります。 ネットワーク運用者、およびシステムとコンポーネントの設計者は皆、相互運用性テストを通じてそのような弱点の低減に貢献できます。

8.1.12. Cost Reductions

8.1.12. コスト削減

The DetNet network specifications are intended to enable an ecosystem in which multiple vendors can create interoperable products, thus promoting higher numbers of each component manufactured, promoting cost reduction and cost competition among vendors.

DetNetネットワークの仕様は、複数のベンダーが相互運用可能な製品を作成できるエコシステムを可能にし、それによって各コンポーネントの製造数の増加を促進し、ベンダー間のコスト削減とコスト競争を促進することを目的としています。

This envisioned breadth of DetNet-enabled products is in general a positive factor; however, implementation flaws in any individual component can present an attack surface. In addition, implementation differences between components from different vendors can result in attack surfaces (resulting from their interaction) that may not exist in any individual component.

このように想定されるDetNet対応製品の幅広さは、一般的には好ましい要因です。 しかし、個々のコンポーネントにおける実装上の欠陥が攻撃対象領域となる可能性があります。 さらに、異なるベンダーのコンポーネント間の実装の違いによって、個々のコンポーネントには存在しない可能性のある（それらの相互作用から生じる）攻撃対象領域が生じる可能性があります。

Network operators can mitigate such concerns through sufficient product and interoperability testing.

ネットワーク運用者は、十分な製品テストと相互運用性テストを通じて、そのような懸念を緩和できます。

8.1.13. Insufficiently Secure Components

8.1.13. 十分に安全でないコンポーネント

The DetNet network specifications are intended to enable an ecosystem in which multiple vendors can create interoperable products, thus promoting component diversity and potentially higher numbers of each component manufactured. However, this raises the possibility that a vendor might repurpose for DetNet applications a hardware or software component that was originally designed for operation in an isolated OT network and thus may not have been designed to be sufficiently secure, or secure at all, against the sorts of attacks described in this document. Deployment of such a component on a DetNet network that is intended to be highly secure may present an attack surface; thus, the DetNet network operator may need to take specific actions to protect such components, for example, by implementing a secure interface (such as a firewall) to isolate the component from the threats that may be present in the greater network.

DetNetネットワークの仕様は、複数のベンダーが相互運用可能な製品を作成できるエコシステムを可能にし、それによってコンポーネントの多様性と、各コンポーネントの製造数の増加を促進することを目的としています。 しかし、これにより、ベンダーが、もともと隔離されたOTネットワークでの運用向けに設計され、そのためこの文書で説明したような種類の攻撃に対して十分に安全に、あるいはまったく安全に設計されていない可能性のあるハードウェアまたはソフトウェアのコンポーネントを、DetNetアプリケーション向けに転用する可能性が生じます。 高い安全性を意図したDetNetネットワーク上にそのようなコンポーネントを展開すると、攻撃対象領域となる可能性があります。 したがって、DetNetネットワークの運用者は、そのようなコンポーネントを保護するために特定のアクションを取る必要がある場合があります。 たとえば、より大きなネットワークに存在する可能性のある脅威からコンポーネントを隔離するために、安全なインターフェイス（ファイアウォールなど）を実装することです。

8.1.14. DetNet Network Size

8.1.14. DetNetネットワークの規模

DetNet networks range in size from very small, e.g., inside a single industrial machine, to very large, e.g., a Utility Grid network spanning a whole country.

DetNetネットワークの規模は、非常に小さいもの（例：単一の産業機械の内部）から非常に大きいもの（例：国全体にまたがる電力網のネットワーク）までさまざまです。

The size of the network might be related to how the attack is introduced into the network. For example, if the entire network is local, there is a threat that power can be cut to the entire network. If the network is large, perhaps only a part of the network is attacked.

ネットワークの規模は、攻撃がネットワークにどのように持ち込まれるかに関係している可能性があります。 たとえば、ネットワーク全体がローカルにある場合、ネットワーク全体の電源が遮断される脅威があります。 ネットワークが大規模な場合は、おそらくネットワークの一部のみが攻撃されるでしょう。

A Delay attack might be as relevant to a small network as to a large network, although the amount of delay might be different.

遅延攻撃は、遅延の量は異なるかもしれませんが、大規模なネットワークと同様に小規模なネットワークにも関係する可能性があります。

Attacks sourced from IT traffic might be more likely in large networks since more people might have access to the network, presenting a larger attack surface. Similarly, Path Manipulation, Path Choice, and Time-Synchronization attacks seem more likely relevant to large networks.

ITトラフィックに起因する攻撃は、より多くの人がネットワークにアクセスでき、攻撃対象領域が大きくなるため、大規模なネットワークで起こりやすい可能性があります。 同様に、パス操作、パス選択、時刻同期の攻撃は、大規模なネットワークに関係する可能性がより高いと考えられます。

8.1.15. Multiple Hops

8.1.15. 複数のホップ

Large DetNet networks (e.g., a Utility Grid network) may involve many "hops" over various kinds of links, for example, radio repeaters, microwave links, fiber optic links, etc.

大規模なDetNetネットワーク（例：電力網のネットワーク）では、無線中継器、マイクロ波リンク、光ファイバーリンクなど、さまざまな種類のリンクを経由する多くの「ホップ」が関係する場合があります。

An attacker who has knowledge of the operation of a component or device's internal software (such as "device drivers") may be able to take advantage of this knowledge to design an attack that could exploit flaws (or even the specifics of normal operation) in the communication between the various links.

コンポーネントやデバイスの内部ソフトウェア（「デバイスドライバー」など）の動作に関する知識を持つ攻撃者は、その知識を利用して、さまざまなリンク間の通信における欠陥（あるいは通常の動作の詳細でさえ）を悪用する攻撃を設計できる可能性があります。

It is also possible that a large-scale DetNet topology containing various kinds of links may not be in as common use as other more homogeneous topologies. This situation may present more opportunity for attackers to exploit software and/or protocol flaws in or between these components because these components or configurations may not have been sufficiently tested for interoperability (in the way they would be as a result of broad usage). This may be of particular concern to early adopters of new DetNet components or technologies.

また、さまざまな種類のリンクを含む大規模なDetNetのトポロジーは、より均質な他のトポロジーほど一般的には使用されていない可能性もあります。 このようなコンポーネントや構成は、（幅広く使用された結果としてテストされるような形では）相互運用性について十分にテストされていない可能性があるため、この状況は、攻撃者がこれらのコンポーネント内またはコンポーネント間のソフトウェアおよび／またはプロトコルの欠陥を悪用する機会をより多く与える可能性があります。 これは、新しいDetNetコンポーネントや技術を早期に採用する者にとって特に懸念される可能性があります。

Of the attacks we have defined, the ones identified in Section 8.1.14 as germane to large networks are the most relevant.

ここで定義した攻撃のうち、Section 8.1.14で大規模なネットワークに関係するとされたものが最も関係します。

8.1.16. Level of Service

8.1.16. サービスのレベル

A DetNet is expected to provide means to configure the network that include querying network path latency, requesting bounded latency for a given DetNet flow, requesting worst-case maximum and/or minimum latency for a given path or DetNet flow, and so on. It is an expected case that the network cannot provide a given requested service level. In such cases, the network control system should reply that the requested service level is not available (as opposed to accepting the parameter but then not delivering the desired behavior).

DetNetは、ネットワークのパスの遅延の問い合わせ、あるDetNetフローに対する有界遅延の要求、あるパスやDetNetフローに対する最悪ケースの最大遅延および／または最小遅延の要求などを含む、ネットワークを設定する手段を提供することが想定されています。 ネットワークが要求されたサービスレベルを提供できない場合も想定されます。 そのような場合、ネットワーク制御システムは、（パラメーターを受け入れておきながら望ましい振る舞いを提供しないのではなく）要求されたサービスレベルは利用できないと応答すべきです。

Controller plane attacks such as Signaling Packet Modification and Injection could be used to modify or create control traffic that could interfere with the process of a user requesting a level of service and/or the reply from the network.

シグナリングパケットの改変や注入などのコントローラープレーンの攻撃が、ユーザーがサービスのレベルを要求するプロセスおよび／またはネットワークからの応答に干渉する可能性のある制御トラフィックを改変または作成するために使用される可能性があります。

Reconnaissance could be used to characterize flows and perhaps target specific flows for attack via the controller plane as noted in Section 6.7.

Section 6.7で述べたように、偵察は、フローの特徴を把握し、おそらくコントローラープレーンを介した攻撃の標的として特定のフローを狙うために使用される可能性があります。

8.1.17. Bounded Latency

8.1.17. 有界遅延

DetNet provides the expectation of guaranteed bounded latency.

DetNetは、保証された有界遅延への期待をもたらします。

Delay attacks can cause packets to miss their agreed-upon latency boundaries.

遅延攻撃によって、パケットが合意された遅延の範囲を外れる可能性があります。

Time-Synchronization attacks can corrupt the time reference of the system, resulting in missed latency deadlines (with respect to the "correct" time reference).

時刻同期攻撃によってシステムの時刻基準が破損し、その結果、（「正しい」時刻基準に対して）遅延の期限を守れなくなる可能性があります。

8.1.18. Low Latency

8.1.18. 低遅延

Applications may require "extremely low latency"; however, depending on the application, these may mean very different latency values. For example, "low latency" across a Utility Grid network is on a different time scale than "low latency" in a motor control loop in a small machine. The intent is that the mechanisms for specifying desired latency include wide ranges, and that architecturally there is nothing to prevent arbitrarily low latencies from being implemented in a given network.

アプリケーションは「極めて低い遅延」を必要とする場合がありますが、アプリケーションによって、それは大きく異なる遅延の値を意味する場合があります。 たとえば、電力網のネットワーク全体での「低遅延」は、小型の機械のモーター制御ループにおける「低遅延」とは異なる時間スケールのものです。 意図しているのは、望ましい遅延を規定するメカニズムが広い範囲を含み、アーキテクチャー上は、あるネットワークにおいて任意に低い遅延を実装することを妨げるものが何もないことです。

Attacks on the controller plane (as described in the Level of Service theme; see Section 8.1.16) and Delay and Time attacks (as described in the Bounded Latency theme; see Section 8.1.17) both apply here.

（サービスのレベルのテーマで説明した。Section 8.1.16を参照してください）コントローラープレーンへの攻撃と、（有界遅延のテーマで説明した。Section 8.1.17を参照してください）遅延攻撃と時刻攻撃の両方が、ここに当てはまります。

8.1.19. Bounded Jitter (Latency Variation)

8.1.19. 有界ジッター（遅延変動）

DetNet is expected to provide bounded jitter (packet-to-packet latency variation).

DetNetは、有界ジッター（パケット間の遅延変動）を提供することが想定されています。

Delay attacks can cause packets to vary in their arrival times, resulting in packet-to-packet latency variation, thereby violating the jitter specification.

遅延攻撃によってパケットの到着時刻がばらつき、その結果パケット間の遅延変動が生じて、ジッターの仕様に違反する可能性があります。

8.1.20. Symmetrical Path Delays

8.1.20. 対称なパス遅延

Some applications would like to specify that the transit delay time values be equal for both the transmit and return paths.

一部のアプリケーションは、送信パスと戻りパスの両方で通過遅延時間の値が等しくなるように規定したいと考えます。

Delay attacks can cause path delays to materially differ between paths.

遅延攻撃によって、パス遅延がパス間で実質的に異なるものになる可能性があります。

Time-Synchronization attacks can corrupt the time reference of the system, resulting in path delays that may be perceived to be different (with respect to the "correct" time reference) even if they are not materially different.

時刻同期攻撃によってシステムの時刻基準が破損し、その結果、パス遅延が実質的には異ならないにもかかわらず、（「正しい」時刻基準に対して）異なると認識される可能性があります。

8.1.21. Reliability and Availability

8.1.21. 信頼性と可用性

DetNet-based systems are expected to be implemented with essentially arbitrarily high availability (for example, 99.9999% up time, or even 12 nines). The intent is that the DetNet designs should not make any assumptions about the level of reliability and availability that may be required of a given system and should define parameters for communicating these kinds of metrics within the network.

DetNetベースのシステムは、本質的に任意に高い可用性（たとえば、99.9999%の稼働時間、あるいは12ナインでさえ）で実装されることが想定されています。 意図しているのは、DetNetの設計が、あるシステムに要求される可能性のある信頼性と可用性のレベルについて何の前提も置くべきではなく、ネットワーク内でこれらの種類のメトリックを伝達するためのパラメーターを定義すべきだということです。

Any attack on the system, of any type, can affect its overall reliability and availability; thus, in the mapping table (Table 5), we have marked every attack. Since every DetNet depends to a greater or lesser degree on reliability and availability, this essentially means that all networks have to mitigate all attacks, which to a greater or lesser degree defeats the purpose of associating attacks with use cases. It also underscores the difficulty of designing "extremely high reliability" networks.

システムに対するあらゆる種類の攻撃が、その全体的な信頼性と可用性に影響を与える可能性があります。 したがって、対応付けの表（Table 5）では、すべての攻撃に印を付けています。 すべてのDetNetは程度の差こそあれ信頼性と可用性に依存しているため、これは本質的に、すべてのネットワークがすべての攻撃を緩和しなければならないことを意味し、程度の差こそあれ、攻撃をユースケースに対応付けるという目的を損なうことになります。 これはまた、「極めて高い信頼性」のネットワークを設計することの難しさも浮き彫りにしています。

In practice, network designers can adopt a risk-based approach in which only those attacks are mitigated whose potential cost is higher than the cost of mitigation.

実際には、ネットワークの設計者は、潜在的なコストが緩和のコストよりも高い攻撃のみを緩和するという、リスクベースのアプローチを採用できます。

8.1.22. Redundant Paths

8.1.22. 冗長パス

This document expects that each DetNet system will be implemented to some essentially arbitrary level of reliability and/or availability, depending on the use case. A strategy used by DetNet for providing extraordinarily high levels of reliability when justified is to provide redundant paths between which traffic can be seamlessly switched, all the while maintaining the required performance of that system.

この文書は、各DetNetシステムが、ユースケースに応じて、本質的に任意のレベルの信頼性および／または可用性で実装されることを想定しています。 正当な理由がある場合に並外れて高いレベルの信頼性を提供するためにDetNetが使用する戦略は、システムに要求される性能を維持しながら、トラフィックをシームレスに切り替えられる冗長パスを提供することです。

Replication-related attacks are by definition applicable here. Controller plane attacks can also interfere with the configuration of redundant paths.

複製に関連する攻撃は、定義上ここに当てはまります。 コントローラープレーンの攻撃も、冗長パスの設定に干渉する可能性があります。

8.1.23. Security Measures

8.1.23. セキュリティー対策

If any of the security mechanisms that protect the DetNet are attacked or subverted, this can result in malfunction of the network. Thus, the security systems themselves need to be robust against attacks.

DetNetを保護するセキュリティーメカニズムのいずれかが攻撃されたり乗っ取られたりすると、ネットワークの誤動作につながる可能性があります。 したがって、セキュリティーシステム自体が攻撃に対して堅牢である必要があります。

The general topic of protection of security mechanisms is not unique to DetNet; it is identical to the case of securing any security mechanism for any network. This document addresses these concerns only to the extent that they are unique to DetNet.

セキュリティーメカニズムの保護という一般的なトピックはDetNetに固有のものではなく、あらゆるネットワークのあらゆるセキュリティーメカニズムを保護する場合と同じです。 この文書では、これらの懸念を、DetNetに固有である範囲においてのみ扱います。

9. Security Considerations for OAM Traffic

9. OAMトラフィックのセキュリティーに関する考慮事項

This section considers DetNet-specific security considerations for packet traffic that is generated and transmitted over a DetNet as part of OAM (Operations, Administration, and Maintenance). For the purposes of this discussion, OAM traffic falls into one of two basic types:

このセクションでは、OAM（運用・管理・保守）の一部としてDetNet上で生成・送信されるパケットトラフィックに関する、DetNet固有のセキュリティーの考慮事項を検討します。 この議論のために、OAMトラフィックを次の2つの基本的な種類のいずれかに分類します。

  • OAM traffic generated by the network itself. The additional bandwidth required for such packets is added by the network administration, presumably transparent to the customer. Security considerations for such traffic are not DetNet specific (apart from such traffic being subject to the same DetNet-specific security considerations as any other DetNet data flow) and are thus not covered in this document.
  • OAM traffic generated by the customer. From a DetNet security point of view, DetNet security considerations for such traffic are exactly the same as for any other customer data flows.
  • ネットワーク自体によって生成されるOAMトラフィック。 そのようなパケットに必要な追加の帯域幅はネットワーク管理によって追加され、おそらく顧客には透過的です。 そのようなトラフィックに関するセキュリティーの考慮事項は（そのようなトラフィックが他のDetNetデータフローと同じDetNet固有のセキュリティーの考慮事項の対象となることを除けば）DetNetに固有のものではないため、この文書では扱いません。
  • 顧客によって生成されるOAMトラフィック。 DetNetのセキュリティーの観点からは、そのようなトラフィックに関するDetNetのセキュリティーの考慮事項は、他の顧客のデータフローの場合とまったく同じです。

From the perspective of an attack, OAM traffic is indistinguishable from DetNet traffic, and the network needs to be secure against injection, removal, or modification of traffic of any kind, including OAM traffic. A DetNet is sensitive to any form of packet injection, removal, or manipulation, and in this respect DetNet OAM traffic is no different. Techniques for securing a DetNet against these threats have been discussed elsewhere in this document.

攻撃の観点からは、OAMトラフィックはDetNetトラフィックと区別がつかず、ネットワークは、OAMトラフィックを含むあらゆる種類のトラフィックの注入、削除、または改変に対して安全である必要があります。 DetNetは、あらゆる形態のパケットの注入、削除、または操作に敏感であり、この点でDetNetのOAMトラフィックも何ら変わりはありません。 これらの脅威からDetNetを保護するための手法は、この文書の他の箇所で議論しています。

10. DetNet Technology-Specific Threats

10. DetNetの技術固有の脅威

Section 5, Security Threats, describes threats that are independent of a DetNet implementation. This section considers threats specifically related to the IP- and MPLS-specific aspects of DetNet implementations.

Section 5（Security Threats）では、DetNetの実装に依存しない脅威について説明しています。 このセクションでは、DetNetの実装のIPおよびMPLS固有の側面に特に関連する脅威を検討します。

The primary security considerations for the data plane specifically are to maintain the integrity of the data and the delivery of the associated DetNet service traversing the DetNet network.

特にデータプレーンに関する主要なセキュリティーの考慮事項は、データの完全性と、DetNetネットワークを通過する関連するDetNetサービスの配送を維持することです。

The primary relevant differences between IP and MPLS implementations are in flow identification and OAM methodologies.

IPの実装とMPLSの実装の間の主な関連する違いは、フロー識別とOAMの方法論にあります。

As noted in [RFC8655], DetNet operates at the IP layer [RFC8939] and delivers service over sub-layer technologies such as MPLS [RFC8964] and IEEE 802.1 Time-Sensitive Networking (TSN) [RFC9023]. Application flows can be protected through whatever means are provided by the layer and sub-layer technologies. For example, technology-specific encryption may be used for IP flows (IPsec [RFC4301]). For IP-over-Ethernet (Layer 2) flows using an underlying sub-net, MACsec [IEEE802.1AE-2018] may be appropriate. For some use cases, packet integrity protection without encryption may be sufficient.

[RFC8655]で述べられているように、DetNetはIP層[RFC8939]で動作し、MPLS [RFC8964]やIEEE 802.1 Time-Sensitive Networking（TSN）[RFC9023]などのサブレイヤーの技術上でサービスを配送します。 アプリケーションのフローは、その層およびサブレイヤーの技術によって提供されるあらゆる手段を通じて保護できます。 たとえば、IPフローには技術固有の暗号化（IPsec [RFC4301]）を使用できます。 基盤となるサブネットを使用するIP-over-Ethernet（レイヤー2）のフローには、MACsec [IEEE802.1AE-2018]が適切な場合があります。 ユースケースによっては、暗号化なしのパケットの完全性保護で十分な場合があります。

However, if the DetNet nodes cannot decrypt IPsec traffic, then DetNet flow identification for encrypted IP traffic flows must be performed in a different way than it would be for unencrypted IP DetNet flows. The DetNet IP data plane identifies unencrypted flows via a 6-tuple that consists of two IP addresses, the transport protocol ID, two transport protocol port numbers, and the DSCP in the IP header. When IPsec is used, the transport header is encrypted and the next protocol ID is an IPsec protocol, usually Encapsulating Security Payload (ESP), and not a transport protocol, leaving only three components of the 6-tuple, which are the two IP addresses and the DSCP. If the IPsec sessions are established by a controller, then this controller could also transmit (in the clear) the Security Parameter Index (SPI) and thus the SPI could be used (in addition to the pair of IP addresses) for flow identification. Identification of DetNet flows over IPsec is further discussed in Section 5.1.2.3 of [RFC8939].

ただし、DetNetノードがIPsecトラフィックを復号できない場合、暗号化されたIPトラフィックフローのDetNetフロー識別は、暗号化されていないIP DetNetフローの場合とは異なる方法で実行しなければなりません。 DetNetのIPデータプレーンは、2つのIPアドレス、トランスポートプロトコルID、2つのトランスポートプロトコルのポート番号、およびIPヘッダー内のDSCPで構成される6タプルによって、暗号化されていないフローを識別します。 IPsecを使用する場合、トランスポートヘッダーは暗号化され、次のプロトコルIDはトランスポートプロトコルではなくIPsecのプロトコル（通常はEncapsulating Security Payload（ESP））になるため、6タプルのうち2つのIPアドレスとDSCPの3つの要素しか残りません。 IPsecのセッションがコントローラーによって確立される場合、このコントローラーはセキュリティーパラメーターインデックス（Security Parameter Index、SPI）も（平文で）送信でき、したがってSPIを（IPアドレスのペアに加えて）フロー識別に使用できます。 IPsec上のDetNetフローの識別については、[RFC8939]のSection 5.1.2.3でさらに議論されています。

Sections below discuss threats specific to IP and MPLS in more detail.

以下のセクションでは、IPとMPLSに固有の脅威についてより詳しく議論します。

10.1. IP

10.1. IP

IP has a long history of security considerations and architectural protection mechanisms. From a data plane perspective, DetNet does not add or modify any IP header information, so the carriage of DetNet traffic over an IP data plane does not introduce any new security issues that were not there before, apart from those already described in the data-plane-independent threats section (Section 5).

IPには、セキュリティーの考慮事項とアーキテクチャー上の保護メカニズムに関する長い歴史があります。 データプレーンの観点からは、DetNetはIPヘッダーの情報を追加も改変もしないため、IPデータプレーン上でDetNetトラフィックを運ぶことによって、データプレーンに依存しない脅威のセクション（Section 5）ですでに説明したもの以外に、以前には存在しなかった新しいセキュリティー上の問題が生じることはありません。

Thus, the security considerations for a DetNet based on an IP data plane are purely inherited from the rich IP security literature and code/application base, and the data-plane-independent section of this document.

したがって、IPデータプレーンに基づくDetNetのセキュリティーの考慮事項は、豊富なIPセキュリティーの文献とコード／アプリケーションの基盤、およびこの文書のデータプレーンに依存しないセクションから、純粋に受け継がれたものです。

Maintaining security for IP segments of a DetNet may be more challenging than for the MPLS segments of the network given that the IP segments of the network may reach the edges of the network, which are more likely to involve interaction with potentially malevolent outside actors. Conversely, MPLS is inherently more secure than IP since it is internal to routers and it is well known how to protect it from outside influence.

ネットワークのIPセグメントはネットワークのエッジに到達する場合があり、エッジでは悪意を持つ可能性のある外部の行為者とのやり取りが発生する可能性が高いため、DetNetのIPセグメントのセキュリティーを維持することは、ネットワークのMPLSセグメントよりも困難な場合があります。 逆に、MPLSはルーターの内部にあり、外部の影響からそれを保護する方法がよく知られているため、本質的にIPよりも安全です。

Another way to look at DetNet IP security is to consider it in the light of VPN security. As an industry, we have a lot of experience with VPNs running through networks with other VPNs -- it is well known how to secure the network for that. However, for a DetNet, we have the additional subtlety that any possible interaction of one packet with another can have a potentially deleterious effect on the time properties of the flows. So the network must provide sufficient isolation between flows, for example, by protecting the forwarding bandwidth and related resources so that they are available to DetNet traffic, by whatever means are appropriate for the data plane of that network, for example, through the use of queuing mechanisms.

DetNetのIPセキュリティーの別の見方として、VPNのセキュリティーに照らして考えることができます。 業界として、他のVPNが存在するネットワークを通過するVPNについては多くの経験があり、そのためにネットワークを保護する方法はよく知られています。 しかし、DetNetの場合には、あるパケットと別のパケットとのあらゆる相互作用が、フローの時間特性に悪影響を及ぼす可能性があるという、さらなる微妙な点があります。 そのため、ネットワークはフロー間に十分な分離を提供しなければなりません。 たとえば、そのネットワークのデータプレーンに適したあらゆる手段（たとえば、キューイングメカニズムの使用）によって、転送の帯域幅と関連するリソースを保護し、それらをDetNetトラフィックが利用できるようにすることです。

In a VPN, bandwidth is generally guaranteed over a period of time whereas in DetNet, it is not aggregated over time. This implies that any VPN-type protection mechanism must also maintain the DetNet timing constraints.

VPNでは、帯域幅は一般にある期間にわたって保証されますが、DetNetでは時間にわたって集約されることはありません。 これは、VPN型の保護メカニズムも、DetNetのタイミングの制約を維持しなければならないことを意味します。

10.2. MPLS

10.2. MPLS

An MPLS network carrying DetNet traffic is expected to be a "well-managed" network. Given that this is the case, it is difficult for an attacker to pass a raw MPLS-encoded packet into a network because operators have considerable experience at excluding such packets at the network boundaries as well as excluding MPLS packets being inserted through the use of a tunnel.

DetNetトラフィックを運ぶMPLSネットワークは、「適切に管理された」ネットワークであることが想定されています。 その場合、運用者はネットワークの境界でそのようなパケットを排除することや、トンネルの使用によって挿入されるMPLSパケットを排除することについてかなりの経験を持っているため、攻撃者が生のMPLSでエンコードされたパケットをネットワークに渡すことは困難です。

MPLS security is discussed extensively in [RFC5920] ("Security Framework for MPLS and GMPLS Networks") to which the reader is referred.

MPLSのセキュリティーについては[RFC5920]（「Security Framework for MPLS and GMPLS Networks」）で広範に議論されているので、読者はそちらを参照してください。

[RFC6941] builds on [RFC5920] by providing additional security considerations that are applicable to the MPLS-TP extensions appropriate to the MPLS Transport Profile [RFC5921] and thus to the operation of DetNet over some types of MPLS network.

[RFC6941]は[RFC5920]を基礎として、MPLS Transport Profile [RFC5921]に適したMPLS-TP拡張、ひいては一部の種類のMPLSネットワーク上でのDetNetの運用に適用できる、追加のセキュリティーの考慮事項を提供しています。

[RFC5921] introduces to MPLS new Operations, Administration, and Maintenance (OAM) capabilities; a transport-oriented path protection mechanism; and strong emphasis on static provisioning supported by network management systems.

[RFC5921]は、新しい運用・管理・保守（OAM）の能力、トランスポート指向のパス保護メカニズム、およびネットワーク管理システムによってサポートされる静的なプロビジョニングの強い重視を、MPLSに導入しています。

The operation of DetNet over an MPLS network builds on MPLS and pseudowire encapsulation. Thus, for guidance on securing the DetNet elements of DetNet over MPLS, the reader is also referred to the security considerations of [RFC4385], [RFC5586], [RFC3985], [RFC6073], and [RFC6478].

MPLSネットワーク上でのDetNetの運用は、MPLSと疑似ワイヤーのカプセル化を基礎としています。 したがって、MPLS上のDetNetのDetNet要素を保護するためのガイダンスについては、読者は[RFC4385]、[RFC5586]、[RFC3985]、[RFC6073]、[RFC6478]のセキュリティーに関する考慮事項も参照してください。

Having attended to the conventional aspects of network security, it is necessary to attend to the dynamic aspects. The closest experience that the IETF has with securing protocols that are sensitive to manipulation of delay are the two-way time transfer (TWTT) protocols, which are NTP [RFC5905] and the Precision Time Protocol [IEEE1588]. The security requirements for these are described in [RFC7384].

ネットワークセキュリティーの従来の側面に対処したら、動的な側面に対処する必要があります。 遅延の操作に敏感なプロトコルの保護に関してIETFが持つ最も近い経験は、双方向時刻転送（two-way time transfer、TWTT）プロトコル、すなわちNTP [RFC5905]とPrecision Time Protocol [IEEE1588]です。 これらのセキュリティー要件は[RFC7384]で説明されています。

One particular problem that has been observed in operational tests of TWTT protocols is the ability for two closely but not completely synchronized flows to beat and cause a sudden phase hit to one of the flows. This can be mitigated by the careful use of a scheduling system in the underlying packet transport.

TWTTプロトコルの運用テストで観察されている特有の問題の1つは、密接に同期しているが完全には同期していない2つのフローがうなりを生じ、一方のフローに突然の位相変化を引き起こす可能性があることです。 これは、基盤となるパケットトランスポートにおいてスケジューリングシステムを慎重に使用することで緩和できます。

Some investigations into protection of MPLS systems against dynamic attacks exist, such as [MPLS-OPP-ENCRYPT]; perhaps deployment of DetNets will encourage additional such investigations.

動的な攻撃からMPLSシステムを保護することに関する調査として、[MPLS-OPP-ENCRYPT]などがあります。 おそらく、DetNetの展開によって、そのような調査がさらに促進されるでしょう。

13. Privacy Considerations

13. プライバシーに関する考慮事項

Privacy in the context of DetNet is maintained by the base technologies specific to the DetNet and user traffic. For example, TSN can use MACsec, IP can use IPsec, and applications can use IP transport protocol-provided methods, e.g., TLS and DTLS. MPLS typically uses L2/L3 VPNs combined with the previously mentioned privacy methods.

DetNetの文脈におけるプライバシーは、DetNetとユーザートラフィックに固有の基盤技術によって維持されます。 たとえば、TSNはMACsecを、IPはIPsecを使用でき、アプリケーションはIPトランスポートプロトコルが提供する方法（例：TLSやDTLS）を使用できます。 MPLSは通常、L2/L3 VPNを前述のプライバシーの方法と組み合わせて使用します。

However, note that reconnaissance threats such as traffic analysis and monitoring of electrical side channels can still cause there to be privacy considerations even when traffic is encrypted.

ただし、トラフィック分析や電気的なサイドチャネルの監視などの偵察の脅威により、トラフィックが暗号化されている場合でもプライバシーに関する考慮事項が生じうることに注意してください。
