RFC 3590

Source Address Selection for the Multicast Listener Discovery (MLD) Protocol

RFC 3590

マルチキャストリスナー探索（MLD）プロトコルにおける送信元アドレスの選択

Abstract

概要

It has come to light that there is an issue with the selection of a suitable IPv6 source address for Multicast Listener Discovery (MLD) messages when a node is performing stateless address autoconfiguration. This document is intended to clarify the rules on selecting an IPv6 address to use for MLD messages.

ノードがステートレスアドレス自動設定を実行しているときに、マルチキャストリスナー探索（MLD）メッセージに使う適切なIPv6送信元アドレスの選択に問題があることが明らかになりました。この文書は、MLDメッセージに使用するIPv6アドレスの選択規則を明確にすることを目的としています。

1. Introduction

1. はじめに

The original specification of the Multicast Listener Discovery Protocol (MLD) for IPv6 [RFC2710] mandates the use of a link-local IPv6 source address for the transmission of MLD messages. In addition, MLD also requires nodes to send MLD Report messages when joining any IPv6 multicast group (except the All-Nodes address and addresses of scope less than 2).

IPv6のためのマルチキャストリスナー探索プロトコル（MLD）の当初の仕様[RFC2710]は、MLDメッセージの送信にリンクローカルIPv6送信元アドレスを使用することを義務付けています。さらにMLDは、ノードがIPv6マルチキャストグループ（全ノードアドレスとスコープが2未満のアドレスを除く）に参加する際に、MLD Reportメッセージを送信することも要求しています。

These MLD requirements conflict with the use of IPv6 multicast within the Neighbor Discovery Protocol [RFC2461]. For stateless autoconfiguration, as defined in [RFC2462], a node is required to join several IPv6 multicast groups in order to perform Duplicate Address Detection prior to its use. Since the only address the node has is tentative, and cannot be used for communication, it does not have a suitable address to utilize as a source address.

これらのMLDの要件は、近隣探索プロトコル[RFC2461]におけるIPv6マルチキャストの使い方と矛盾します。[RFC2462]で定義されているステートレス自動設定では、ノードはアドレスを使用する前に重複アドレス検出を実行するため、いくつかのIPv6マルチキャストグループに参加する必要があります。そのノードが持つ唯一のアドレスは仮（tentative）のものであって通信には使用できないため、ノードには送信元アドレスとして利用できる適切なアドレスがありません。

This document will clarify the IPv6 source address selection rules for use with MLD when no link-local addresses are available.

この文書は、リンクローカルアドレスが利用できない場合にMLDで使用するIPv6送信元アドレスの選択規則を明確にします。

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、「要求されています（REQUIRED）」、「することになります（SHALL）」、「することはありません（SHALL NOT）」、「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、「推奨されます（RECOMMENDED）」、「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、[RFC2119]に記載されているとおりに解釈されるものとします。

3. Justification

3. 根拠

In [RFC2710], Section 3 requires that all MLD messages be sent with a valid link-local IPv6 source address. However, a node in the process of performing duplicate address detection for its link-local (LL) address will not have one available to use as a source address. For this reason, this document allows the unspecified address to be used as a source address for MLD messages being used during duplicate address detection.

[RFC2710]のセクション3は、すべてのMLDメッセージを有効なリンクローカルIPv6送信元アドレスで送信することを要求しています。しかし、自身のリンクローカル（LL）アドレスの重複アドレス検出を実行中のノードは、送信元アドレスとして使用できるリンクローカルアドレスを持っていません。このため、この文書では、重複アドレス検出中に使われるMLDメッセージの送信元アドレスとして未指定アドレスを使用することを認めます。

The discrepancies in the rules defined in [RFC2710] and [RFC2462] has led to implementation issues. Several IPv6 implementations skip sending MLD Report messages during duplicate address detection because they have no valid link-local address. This leads to operational problems when a node is attached to switches that perform MLD snooping. In this scenario, duplicate address detection (DAD) will complete successfully and collisions can occur once the address is put into use because switches may not have forwarded the DAD messages to all nodes on the link as required. This document fixes this problem by specifying that MLD reports are to be sent using an unspecified source address prior to DAD being started in order to ensure that messages sent to LL multicast addresses (e.g., including MLD) are forwarded to all appropriate nodes as required.

[RFC2710]と[RFC2462]で定義された規則の食い違いは、実装上の問題を引き起こしてきました。いくつかのIPv6実装は、有効なリンクローカルアドレスを持たないという理由で、重複アドレス検出中にMLD Reportメッセージの送信を省略しています。これは、ノードがMLDスヌーピングを実行するスイッチに接続されている場合に運用上の問題を引き起こします。このシナリオでは、要求どおりにスイッチがDADメッセージをリンク上のすべてのノードへ転送していない可能性があるため、重複アドレス検出（DAD）は成功裏に完了してしまい、そのアドレスを使い始めた時点で衝突が起こり得ます。この文書は、LLマルチキャストアドレスに送信されたメッセージ（たとえばMLDを含む）が要求どおりに適切なすべてのノードへ転送されることを保証するため、DADを開始する前に未指定の送信元アドレスを使ってMLDレポートを送信すると規定することで、この問題を解決します。

4. MLD Source Address Selection Guidelines

4. MLDの送信元アドレス選択のガイドライン

An MLD speaking node is required to choose a suitable IPv6 source address for all MLD messages (Report, Done, and Query).

MLDを話すノードは、すべてのMLDメッセージ（Report、Done、Query）に対して適切なIPv6送信元アドレスを選択する必要があります。

MLD Query messages MUST be sent with a valid link-local address as the IPv6 source address. If a node (router or host) receives a query message with an IPv6 source address set to the unspecified address (::), it MUST silently discard the message and SHOULD log a warning.

MLD Queryメッセージは、IPv6送信元アドレスとして有効なリンクローカルアドレスを使って送信しなければなりません（MUST）。ノード（ルーターまたはホスト）が、IPv6送信元アドレスに未指定アドレス（::）が設定されたクエリーメッセージを受信した場合、そのメッセージを黙って破棄しなければなりません（MUST）。また、警告をログに記録すべきです（SHOULD）。

MLD Report and Done messages are sent with a link-local address as the IPv6 source address, if a valid address is available on the interface. If a valid link-local address is not available (e.g., one has not been configured), the message is sent with the unspecified address (::) as the IPv6 source address.

MLD ReportメッセージとDoneメッセージは、インターフェイス上で有効なアドレスが利用できる場合、IPv6送信元アドレスとしてリンクローカルアドレスを使って送信されます。有効なリンクローカルアドレスが利用できない場合（たとえば、まだ設定されていない場合）、メッセージはIPv6送信元アドレスとして未指定アドレス（::）を使って送信されます。

Once a valid link-local address is available, a node SHOULD generate new MLD Report messages for all multicast addresses joined on the interface.

有効なリンクローカルアドレスが利用できるようになったら、ノードはそのインターフェイスで参加しているすべてのマルチキャストアドレスについて、新たにMLD Reportメッセージを生成すべきです（SHOULD）。

Routers receiving an MLD Report or Done message with the unspecified address as the IPv6 source address MUST silently discard the packet without taking any action on the packets contents.

IPv6送信元アドレスが未指定アドレスであるMLD ReportメッセージまたはDoneメッセージを受信したルーターは、パケットの内容に基づく動作を一切行わずに、そのパケットを黙って破棄しなければなりません（MUST）。

Snooping switches MUST manage multicast forwarding state based on MLD Report and Done messages sent with the unspecified address as the IPv6 source address.

スヌーピングスイッチは、IPv6送信元アドレスとして未指定アドレスを使って送信されたMLD ReportメッセージとDoneメッセージに基づいて、マルチキャスト転送状態を管理しなければなりません（MUST）。

5. Source Address Selection Implications

5. 送信元アドレス選択の影響

In RFC 2710, MLD Report and Done messages are required to have an IPv6 source address that is link-local. This memo augments that rule by allowing these messages to contain the unspecified address (::) as the source address.

RFC 2710では、MLD ReportメッセージとDoneメッセージはリンクローカルのIPv6送信元アドレスを持つことが要求されています。このメモは、これらのメッセージが送信元アドレスとして未指定アドレス（::）を含むことを認めることで、この規則を拡張します。

The behavior of RFC 2710 implementations, when receiving a message with a source address of ::, is dependent upon how the implementation treats the unspecified address. That is, these messages will be dropped if the implementation does not consider the unspecified address to be link-local in scope.

送信元アドレスが::のメッセージを受信したときのRFC 2710実装の振る舞いは、その実装が未指定アドレスをどのように扱うかに依存します。つまり、実装が未指定アドレスをリンクローカルスコープとみなさない場合、これらのメッセージは破棄されます。

As the unspecified address is only used when there is no link-local address, RFC 2710 implementations discarding these packets will have no affect on the packet's sender as the use should only be for joining the link-local solicited-node multicast group [RFC2462].

未指定アドレスはリンクローカルアドレスがない場合にのみ使用され、その用途はリンクローカルの要請ノードマルチキャストグループ[RFC2462]への参加に限られるはずなので、RFC 2710実装がこれらのパケットを破棄しても、パケットの送信者には影響がありません。

There is an implication to senders with respect to joining other multicast groups prior to the activation of a link-local address. The dropping of Reports using the unspecified address as a source address could cause a lack of multicast traffic that is expected by the node. This black hole will be temporary until the node can send a Report with a valid link-local address.

リンクローカルアドレスが有効になる前に他のマルチキャストグループへ参加することに関しては、送信者に影響があります。未指定アドレスを送信元アドレスとするReportが破棄されると、ノードが期待しているマルチキャストトラフィックが届かない可能性があります。このブラックホールは、ノードが有効なリンクローカルアドレスを使ってReportを送信できるようになるまでの一時的なものです。

6. Security Considerations

6. セキュリティーに関する考慮事項

General security issues related to MLD are discussed in [RFC2710].

MLDに関連する一般的なセキュリティー問題は、[RFC2710]で議論されています。

For hosts and routers, all received MLD messages from an unspecified source address are silently discarded. This is the required behavior from [RFC2710] and is not changed by this document. Thus, the changes have no new security impacts.

ホストとルーターでは、未指定の送信元アドレスから受信したMLDメッセージはすべて黙って破棄されます。これは[RFC2710]で要求されている振る舞いであり、この文書によって変更されることはありません。したがって、今回の変更によって新たなセキュリティー上の影響は生じません。

In the case of snooping switches, multicast forwarding state will be maintained based on Report and Done messages sent with the unspecified address as the source address. However, the security vulnerabilities in this scenario are similar to those describing forged messages in the security considerations section of [RFC2710].

スヌーピングスイッチの場合、マルチキャスト転送状態は、送信元アドレスとして未指定アドレスを使って送信されたReportメッセージとDoneメッセージに基づいて維持されます。しかし、このシナリオにおけるセキュリティー上の脆弱性は、[RFC2710]のセキュリティーに関する考慮事項のセクションで偽造メッセージについて述べられているものと同様です。
