RFC 8342

Network Management Datastore Architecture (NMDA)

RFC 8342

ネットワーク管理データストアアーキテクチャー（NMDA）

Abstract

概要

Datastores are a fundamental concept binding the data models written in the YANG data modeling language to network management protocols such as the Network Configuration Protocol (NETCONF) and RESTCONF. This document defines an architectural framework for datastores based on the experience gained with the initial simpler model, addressing requirements that were not well supported in the initial model. This document updates RFC 7950.

データストアは、YANGデータモデリング言語で記述されたデータモデルを、ネットワーク設定プロトコル（Network Configuration Protocol: NETCONF）やRESTCONFなどのネットワーク管理プロトコルに結び付ける基本的な概念です。この文書は、当初の単純なモデルで得られた経験に基づいて、当初のモデルでは十分にサポートされていなかった要件に対処する、データストアのためのアーキテクチャーフレームワークを定義します。この文書は、RFC 7950を更新します。

1. Introduction

1. はじめに

This document provides an architectural framework for datastores as they are used by network management protocols such as the Network Configuration Protocol (NETCONF) [RFC6241], RESTCONF [RFC8040], and the YANG data modeling language [RFC7950]. Datastores are a fundamental concept binding network management data models to network management protocols. Agreement on a common architectural model of datastores ensures that data models can be written in a way that is network management protocol agnostic. This architectural framework identifies a set of conceptual datastores, but it does not mandate that all network management protocols expose all these conceptual datastores. This architecture is agnostic with regard to the encoding used by network management protocols.

この文書は、ネットワーク設定プロトコル（NETCONF）[RFC6241]、RESTCONF [RFC8040]などのネットワーク管理プロトコルや、YANGデータモデリング言語[RFC7950]で使用されるデータストアのためのアーキテクチャーフレームワークを提供します。データストアは、ネットワーク管理データモデルをネットワーク管理プロトコルに結び付ける基本的な概念です。データストアの共通のアーキテクチャーモデルについて合意することで、ネットワーク管理プロトコルに依存しない形でデータモデルを記述できるようになります。このアーキテクチャーフレームワークは、一連の概念的なデータストアを特定しますが、すべてのネットワーク管理プロトコルがこれらの概念的なデータストアをすべて公開することを義務付けるものではありません。このアーキテクチャーは、ネットワーク管理プロトコルが使用するエンコーディングには依存しません。

This document updates RFC 7950 by refining the definition of the accessible tree for some XML Path Language (XPath) context (see Section 6.1) and the invocation context of operations (see Section 6.2).

この文書は、一部のXMLパス言語（XPath）コンテキストにおけるアクセス可能なツリーの定義（セクション6.1を参照）と、操作の呼び出しコンテキスト（セクション6.2を参照）を改良することで、RFC 7950を更新します。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、「要求されています（REQUIRED）」、「することになります（SHALL）」、「することはありません（SHALL NOT）」、「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。ただし、ここに示すようにすべて大文字で表示される場合に限ります。

2. Objectives

2. 目的

Network management data objects can often take two different values: the value configured by the user or an application (configuration) and the value that the device is actually using (operational state). These two values may be different for a number of reasons, e.g., system internal interactions with hardware, interaction with protocols or other devices, or simply the time it takes to propagate a configuration change to the software and hardware components of a system. Furthermore, configuration and operational state data objects may have different lifetimes.

ネットワーク管理のデータオブジェクトは、多くの場合、2つの異なる値をとり得ます。ユーザーやアプリケーションが設定した値（設定）と、デバイスが実際に使用している値（運用状態）です。これら2つの値は、さまざまな理由で異なる場合があります。たとえば、システム内部でのハードウェアとのやり取り、プロトコルや他のデバイスとのやり取り、あるいは単に設定変更をシステムのソフトウェアコンポーネントやハードウェアコンポーネントに伝播させるのにかかる時間などです。さらに、設定のデータオブジェクトと運用状態のデータオブジェクトは、有効期間が異なる場合があります。

The original model of datastores required these data objects to be modeled twice in the YANG schema -- as "config true" objects and as "config false" objects. The convention adopted by the interfaces data model [RFC8343] and the IP data model [RFC8344] was to use two separate branches rooted at the root of the data tree: one branch for configuration data objects and one branch for operational state data objects.

データストアの元のモデルでは、これらのデータオブジェクトをYANGスキーマ内で2回、つまり"config true"オブジェクトと"config false"オブジェクトとしてモデル化する必要がありました。インターフェイスデータモデル[RFC8343]とIPデータモデル[RFC8344]が採用した慣習は、データツリーのルートを起点とする2つの別々のブランチを使用するというものでした。一方のブランチは設定のデータオブジェクト用、もう一方のブランチは運用状態のデータオブジェクト用です。

The duplication of definitions and the ad hoc separation of operational state data from configuration data lead to a number of problems. Having configuration and operational state data in separate branches in the data model is operationally complicated and impacts the readability of module definitions. Furthermore, the relationship between the branches is not machine readable, and filter expressions operating on configuration and on related operational state are different.

定義の重複や、運用状態データと設定データのアドホックな分離は、多くの問題につながります。データモデル内で設定データと運用状態データを別々のブランチに置くことは、運用上複雑であり、モジュール定義の可読性にも影響します。さらに、ブランチ間の関係は機械可読ではなく、設定に対して作用するフィルター式と、関連する運用状態に対して作用するフィルター式は異なります。

With the revised architectural model of datastores defined in this document, the data objects are defined only once in the YANG schema but independent instantiations can appear in different datastores, e.g., one for a configured value and another for an operationally used value. This provides a more elegant and simpler solution to the problem.

この文書で定義する改訂版のデータストアのアーキテクチャーモデルでは、データオブジェクトはYANGスキーマ内で一度だけ定義されますが、独立したインスタンスが異なるデータストアに現れることができます。たとえば、設定された値のインスタンスと、運用上使用されている値のインスタンスです。これにより、この問題に対して、よりエレガントで単純な解決策が得られます。

The revised architectural model of datastores supports additional datastores for systems that support more advanced processing chains converting configuration to operational state. For example, some systems support configuration that is not currently used (so-called "inactive configuration") or they support configuration templates that are used to expand configuration data via a common template.

改訂版のデータストアのアーキテクチャーモデルは、設定を運用状態に変換する、より高度な処理チェーンをサポートするシステムのために、追加のデータストアをサポートします。たとえば、一部のシステムは、現在使用されていない設定（いわゆる"非アクティブな設定（inactive configuration）"）をサポートしたり、共通のテンプレートを介して設定データを展開するために使用される設定テンプレートをサポートしたりしています。

3. Terminology

3. 用語

This document defines the following terminology. Some of the terms are revised definitions of terms originally defined in [RFC6241] and [RFC7950] (see also Section 4). The revised definitions are semantically equivalent to the definitions found in [RFC6241] and [RFC7950]. It is expected that the revised definitions provided in this section will replace the definitions in [RFC6241] and [RFC7950] when these documents are revised.

この文書では、次の用語を定義します。一部の用語は、もともと[RFC6241]と[RFC7950]で定義されていた用語の定義を改訂したものです（セクション4も参照してください）。改訂された定義は、[RFC6241]と[RFC7950]にある定義と意味的に同等です。このセクションで示す改訂された定義は、[RFC6241]と[RFC7950]が改訂される際に、それらの文書の定義を置き換えることが想定されています。

  • datastore: A conceptual place to store and access information. A datastore might be implemented, for example, using files, a database, flash memory locations, or combinations thereof. A datastore maps to an instantiated YANG data tree.
  • schema node: A node in the schema tree. The formal definition is provided in RFC 7950.
  • datastore schema: The combined set of schema nodes for all modules supported by a particular datastore, taking into consideration any deviations and enabled features for that datastore.
  • configuration: Data that is required to get a device from its initial default state into a desired operational state. This data is modeled in YANG using "config true" nodes. Configuration can originate from different sources.
  • configuration datastore: A datastore holding configuration.
  • running configuration datastore: A configuration datastore holding the current configuration of the device. It may include configuration that requires further transformations before it can be applied. This datastore is referred to as "<running>".
  • candidate configuration datastore: A configuration datastore that can be manipulated without impacting the device's running configuration datastore and that can be committed to the running configuration datastore. This datastore is referred to as "<candidate>".
  • startup configuration datastore: A configuration datastore holding the configuration loaded by the device into the running configuration datastore when it boots. This datastore is referred to as "<startup>".
  • intended configuration: Configuration that is intended to be used by the device. It represents the configuration after all configuration transformations to <running> have been performed and is the configuration that the system attempts to apply.
  • intended configuration datastore: A configuration datastore holding the complete intended configuration of the device. This datastore is referred to as "<intended>".
  • configuration transformation: The addition, modification, or removal of configuration between the <running> and <intended> datastores. Examples of configuration transformations include the removal of inactive configuration and the configuration produced through the expansion of templates.
  • conventional configuration datastore: One of the following set of configuration datastores: <running>, <startup>, <candidate>, and <intended>. These datastores share a common datastore schema, and protocol operations allow copying data between these datastores. The term "conventional" is chosen as a generic umbrella term for these datastores.
  • conventional configuration: Configuration that is stored in any of the conventional configuration datastores.
  • dynamic configuration datastore: A configuration datastore holding configuration obtained dynamically during the operation of a device through interaction with other systems, rather than through one of the conventional configuration datastores.
  • dynamic configuration: Configuration obtained via a dynamic configuration datastore.
  • learned configuration: Configuration that has been learned via protocol interactions with other systems and that is neither conventional nor dynamic configuration.
  • system configuration: Configuration that is supplied by the device itself.
  • default configuration: Configuration that is not explicitly provided but for which a value defined in the data model is used.
  • applied configuration: Configuration that is actively in use by a device. Applied configuration originates from conventional, dynamic, learned, system, and default configuration.
  • system state: The additional data on a system that is not configuration, such as read-only status information and collected statistics. System state is transient and modified by interactions with internal components or other systems. System state is modeled in YANG using "config false" nodes.
  • operational state: The combination of applied configuration and system state.
  • operational state datastore: A datastore holding the complete operational state of the device. This datastore is referred to as "<operational>".
  • origin: A metadata annotation indicating the origin of a data item.
  • remnant configuration: Configuration that remains part of the applied configuration for a period of time after it has been removed from the intended configuration or dynamic configuration. The time period may be minimal or may last until all resources used by the newly deleted configuration (e.g., network connections, memory allocations, file handles) have been deallocated.
  • データストア（datastore）：情報を格納し、アクセスするための概念的な場所。データストアは、たとえば、ファイル、データベース、フラッシュメモリーの領域、またはそれらの組み合わせを使用して実装されるかもしれません。データストアは、インスタンス化されたYANGデータツリーに対応します。
  • スキーマノード（schema node）：スキーマツリー内のノード。正式な定義はRFC 7950で示されています。
  • データストアスキーマ（datastore schema）：特定のデータストアがサポートするすべてのモジュールのスキーマノードを合わせた集合。そのデータストアの逸脱（deviation）や有効化された機能（feature）も考慮に入れます。
  • 設定（configuration）：デバイスを初期のデフォルト状態から望ましい運用状態にするために必要なデータ。このデータは、YANGでは"config true"ノードを使用してモデル化されます。設定は、さまざまなソースから生じる可能性があります。
  • 設定データストア（configuration datastore）：設定を保持するデータストア。
  • 実行設定データストア（running configuration datastore）：デバイスの現在の設定を保持する設定データストア。適用される前にさらに変換を必要とする設定を含む場合があります。このデータストアは"<running>"と呼ばれます。
  • 候補設定データストア（candidate configuration datastore）：デバイスの実行設定データストアに影響を与えることなく操作でき、実行設定データストアにコミットできる設定データストア。このデータストアは"<candidate>"と呼ばれます。
  • 起動設定データストア（startup configuration datastore）：デバイスが起動するときに実行設定データストアに読み込む設定を保持する設定データストア。このデータストアは"<startup>"と呼ばれます。
  • 意図された設定（intended configuration）：デバイスが使用することを意図した設定。<running>に対するすべての設定変換が実行された後の設定を表し、システムが適用しようとする設定です。
  • 意図された設定データストア（intended configuration datastore）：デバイスの完全な意図された設定を保持する設定データストア。このデータストアは"<intended>"と呼ばれます。
  • 設定変換（configuration transformation）：<running>データストアと<intended>データストアの間での設定の追加、変更、削除。設定変換の例としては、非アクティブな設定の削除や、テンプレートの展開によって生成される設定などがあります。
  • 従来型設定データストア（conventional configuration datastore）：<running>、<startup>、<candidate>、<intended>という設定データストアの集合のいずれか。これらのデータストアは共通のデータストアスキーマを共有し、プロトコル操作によってこれらのデータストア間でデータをコピーできます。"従来型（conventional）"という用語は、これらのデータストアを包括する総称として選ばれました。
  • 従来型設定（conventional configuration）：従来型設定データストアのいずれかに格納されている設定。
  • 動的設定データストア（dynamic configuration datastore）：従来型設定データストアのいずれかを介してではなく、他のシステムとのやり取りを通じて、デバイスの動作中に動的に取得された設定を保持する設定データストア。
  • 動的設定（dynamic configuration）：動的設定データストアを介して取得された設定。
  • 学習された設定（learned configuration）：他のシステムとのプロトコルによるやり取りを介して学習された設定で、従来型設定でも動的設定でもないもの。
  • システム設定（system configuration）：デバイス自体が提供する設定。
  • デフォルト設定（default configuration）：明示的には提供されていないが、データモデルで定義された値が使用される設定。
  • 適用された設定（applied configuration）：デバイスが実際に使用している設定。適用された設定は、従来型設定、動的設定、学習された設定、システム設定、デフォルト設定から生じます。
  • システム状態（system state）：設定ではない、システム上の追加データ。たとえば、読み取り専用のステータス情報や収集された統計情報など。システム状態は一時的なものであり、内部コンポーネントや他のシステムとのやり取りによって変更されます。システム状態は、YANGでは"config false"ノードを使用してモデル化されます。
  • 運用状態（operational state）：適用された設定とシステム状態の組み合わせ。
  • 運用状態データストア（operational state datastore）：デバイスの完全な運用状態を保持するデータストア。このデータストアは"<operational>"と呼ばれます。
  • オリジン（origin）：データ項目のオリジンを示すメタデータアノテーション。
  • 残存設定（remnant configuration）：意図された設定または動的設定から削除された後も、一定期間、適用された設定の一部として残っている設定。この期間はごく短い場合もあれば、新たに削除された設定が使用していたすべてのリソース（たとえば、ネットワークコネクション、メモリー割り当て、ファイルハンドル）が解放されるまで続く場合もあります。

The following additional terms are not datastore specific, but they are commonly used and are thus defined here as well:

次の追加の用語はデータストアに固有のものではありませんが、一般的に使用されるため、ここで定義しておきます。

  • client: An entity that can access YANG-defined data on a server, over some network management protocol.
  • server: An entity that provides access to YANG-defined data to a client, over some network management protocol.
  • notification: A server-initiated message indicating that a certain event has been recognized by the server.
  • remote procedure call: An operation that can be invoked by a client on a server.
  • クライアント（client）：何らかのネットワーク管理プロトコルを介して、サーバー上のYANGで定義されたデータにアクセスできるエンティティー。
  • サーバー（server）：何らかのネットワーク管理プロトコルを介して、YANGで定義されたデータへのアクセスをクライアントに提供するエンティティー。
  • 通知（notification）：特定のイベントをサーバーが認識したことを示す、サーバーが開始するメッセージ。
  • リモートプロシージャーコール（remote procedure call）：クライアントがサーバー上で呼び出すことができる操作。

4. Background

4. 背景

NETCONF [RFC6241] provides the following definitions:

NETCONF [RFC6241]は、次の定義を示しています。

  • datastore: A conceptual place to store and access information. A datastore might be implemented, for example, using files, a database, flash memory locations, or combinations thereof.
  • configuration datastore: The datastore holding the complete set of configuration that is required to get a device from its initial default state into a desired operational state.
  • データストア（datastore）：情報を格納し、アクセスするための概念的な場所。データストアは、たとえば、ファイル、データベース、フラッシュメモリーの領域、またはそれらの組み合わせを使用して実装されるかもしれません。
  • 設定データストア（configuration datastore）：デバイスを初期のデフォルト状態から望ましい運用状態にするために必要な、設定の完全な集合を保持するデータストア。

YANG 1.1 [RFC7950] provides the following refinements when NETCONF is used with YANG (which is the usual case, but note that NETCONF was defined before YANG existed):

YANG 1.1 [RFC7950]は、NETCONFをYANGとともに使用する場合（これは通常のケースですが、NETCONFはYANGが存在する前に定義されたことに注意してください）について、次の改良を示しています。

  • datastore: When modeled with YANG, a datastore is realized as an instantiated data tree.
  • configuration datastore: When modeled with YANG, a configuration datastore is realized as an instantiated data tree with configuration.
  • データストア（datastore）：YANGでモデル化された場合、データストアはインスタンス化されたデータツリーとして実現されます。
  • 設定データストア（configuration datastore）：YANGでモデル化された場合、設定データストアは設定を含むインスタンス化されたデータツリーとして実現されます。

[RFC6244] defined operational state data as follows:

[RFC6244]は、運用状態データを次のように定義しました。

  • Operational state data is a set of data that has been obtained by the system at runtime and influences the system's behavior similar to configuration data. In contrast to configuration data, operational state is transient and modified by interactions with internal components or other systems via specialized protocols.
  • 運用状態データは、システムが実行時に取得したデータの集合であり、設定データと同様にシステムの振る舞いに影響を与えます。設定データとは対照的に、運用状態は一時的なものであり、内部コンポーネントとのやり取りや、専用のプロトコルを介した他のシステムとのやり取りによって変更されます。

Section 4.3.3 of [RFC6244] discusses operational state and mentions, among other things, the option to consider operational state as being stored in another datastore. Section 4.4 of [RFC6244] then concludes that, at the time of its writing, modeling state as distinct leafs and distinct branches is the recommended approach.

[RFC6244]のセクション4.3.3は運用状態について論じており、特に、運用状態を別のデータストアに格納されているものとみなすという選択肢について言及しています。そのうえで[RFC6244]のセクション4.4は、その執筆時点では、状態を別個のリーフおよび別個のブランチとしてモデル化することが推奨されるアプローチであると結論付けています。

Implementation experience and requests from operators [OpState-Reqs] [OpState-Modeling] indicate that the datastore model initially designed for NETCONF and refined by YANG needs to be extended. In particular, the notion of intended configuration and applied configuration has developed.

実装の経験と運用者からの要望[OpState-Reqs] [OpState-Modeling]は、当初NETCONFのために設計されYANGによって改良されたデータストアモデルを拡張する必要があることを示しています。特に、意図された設定と適用された設定という概念が生まれました。

4.1. Original Model of Datastores

4.1. データストアの元のモデル

The following drawing shows the original model of datastores as it is currently used by NETCONF [RFC6241]:

次の図は、現在NETCONF [RFC6241]で使用されている、データストアの元のモデルを示しています。

Note that this diagram simplifies the model: "read-only" (ro) and "read-write" (rw) are to be understood from the client's perspective, at a conceptual level. In NETCONF, for example, support for <candidate> and <startup> is optional, and <running> does not have to be writable. Furthermore, <startup> can only be modified by copying <running> to <startup> in the standardized NETCONF datastore editing model. The RESTCONF protocol does not expose these differences and instead provides only a writable unified datastore, which hides whether edits are done through <candidate>, by directly modifying <running>, or via some other implementation-specific mechanism. RESTCONF also hides how configuration is made persistent. Note that implementations may also have additional datastores that can propagate changes to <running>. NETCONF explicitly mentions so-called "named datastores".

この図はモデルを単純化していることに注意してください。"読み取り専用（read-only）"（ro）と"読み書き可能（read-write）"（rw）は、概念的なレベルで、クライアントの観点から理解されるべきものです。たとえば、NETCONFでは、<candidate>と<startup>のサポートは任意であり、<running>は書き込み可能である必要はありません。さらに、標準化されたNETCONFのデータストア編集モデルでは、<startup>は<running>を<startup>にコピーすることによってのみ変更できます。RESTCONFプロトコルはこれらの違いを公開せず、代わりに書き込み可能な統合データストアだけを提供します。これにより、編集が<candidate>を通じて行われるのか、<running>を直接変更することによって行われるのか、あるいはその他の実装固有のメカニズムを介して行われるのかが隠されます。RESTCONFはまた、設定がどのように永続化されるかも隠します。実装には、<running>に変更を伝播できる追加のデータストアがある場合もあることに注意してください。NETCONFは、いわゆる"名前付きデータストア（named datastores）"について明示的に言及しています。

Some observations:

いくつかの所見を示します。

  • Operational state has not been defined as a datastore, although there were proposals in the past to introduce an operational state datastore.
  • The NETCONF <get> operation returns the contents of <running> together with the operational state. It is therefore necessary that "config false" data be in a different branch than the "config true" data if the operational state can have a different lifetime compared to configuration or if configuration is not immediately or successfully applied.
  • Several implementations have proprietary mechanisms that allow clients to store inactive data in <running>. Inactive data is conceptually removed before validation.
  • Some implementations have proprietary mechanisms that allow clients to define configuration templates in <running>. These templates are expanded automatically by the system, and the resulting configuration is applied internally.
  • Some operators have reported that it is essential for them to be able to retrieve the configuration that has actually been successfully applied, which may be a subset or a superset of the <running> configuration.
  • 過去に運用状態データストアを導入する提案はありましたが、運用状態はデータストアとしては定義されていません。
  • NETCONFの<get>操作は、<running>の内容を運用状態とともに返します。そのため、運用状態の有効期間が設定とは異なる可能性がある場合や、設定が即座に、または正常に適用されない場合には、"config false"データを"config true"データとは別のブランチに置く必要があります。
  • いくつかの実装は、クライアントが<running>に非アクティブなデータを格納できるようにする独自のメカニズムを備えています。非アクティブなデータは、概念的には検証の前に削除されます。
  • 一部の実装は、クライアントが<running>内で設定テンプレートを定義できるようにする独自のメカニズムを備えています。これらのテンプレートはシステムによって自動的に展開され、その結果得られた設定が内部で適用されます。
  • 一部の運用者は、実際に正常に適用された設定を取得できることが不可欠であると報告しています。この設定は、<running>の設定のサブセットである場合もあれば、スーパーセットである場合もあります。

5. Architectural Model of Datastores

5. データストアのアーキテクチャーモデル

Below is a new conceptual model of datastores, extending the original model in order to reflect the experience gained with the original model.

以下は、元のモデルで得られた経験を反映するために元のモデルを拡張した、新しいデータストアの概念モデルです。

5.1. Conventional Configuration Datastores

5.1. 従来型設定データストア

The conventional configuration datastores are a set of configuration datastores that share exactly the same datastore schema, allowing data to be copied between them. The term is meant as a generic umbrella description of these datastores. If a module does not contain any configuration data nodes and it is not needed to satisfy any imports, then it MAY be omitted from the datastore schema for the conventional configuration datastores. The set of datastores include:

従来型設定データストアは、まったく同じデータストアスキーマを共有する設定データストアの集合であり、それらの間でデータをコピーできます。この用語は、これらのデータストアを包括する総称として意図されています。あるモジュールが設定データノードを一切含まず、いずれのインポートを満たすためにも必要とされない場合、そのモジュールを従来型設定データストアのデータストアスキーマから省略してもよいです（MAY）。このデータストアの集合には、次のものが含まれます。

  • <running>
  • <candidate>
  • <startup>
  • <intended>
  • <running>
  • <candidate>
  • <startup>
  • <intended>

Other conventional configuration datastores may be defined in future documents.

将来の文書で、その他の従来型設定データストアが定義される可能性があります。

The flow of data between these datastores is depicted in Section 5.

これらのデータストア間のデータの流れは、セクション5に示しています。

The specific protocols may define explicit operations to copy between these datastores, e.g., NETCONF defines the <copy-config> operation.

個々のプロトコルは、これらのデータストア間でコピーするための明示的な操作を定義する場合があります。たとえば、NETCONFは<copy-config>操作を定義しています。

5.1.1. The Startup Configuration Datastore (<startup>)

5.1.1. 起動設定データストア（<startup>）

The startup configuration datastore (<startup>) is a configuration datastore holding the configuration loaded by the device when it boots. <startup> is only present on devices that separate the startup configuration from the running configuration datastore.

起動設定データストア（<startup>）は、デバイスが起動するときに読み込む設定を保持する設定データストアです。<startup>は、起動設定を実行設定データストアから分離しているデバイスにのみ存在します。

The startup configuration datastore may not be supported by all protocols or implementations.

起動設定データストアは、すべてのプロトコルや実装でサポートされているとは限りません。

On devices that support non-volatile storage, the contents of <startup> will typically persist across reboots via that storage. At boot time, the device loads the saved startup configuration into <running>. To save a new startup configuration, data is copied to <startup> via either implicit or explicit protocol operations.

不揮発性ストレージをサポートするデバイスでは、<startup>の内容は通常、そのストレージを介して再起動後も維持されます。起動時に、デバイスは保存されている起動設定を<running>に読み込みます。新しい起動設定を保存するには、暗黙的または明示的なプロトコル操作を介して、データを<startup>にコピーします。

5.1.2. The Candidate Configuration Datastore (<candidate>)

5.1.2. 候補設定データストア（<candidate>）

The candidate configuration datastore (<candidate>) is a configuration datastore that can be manipulated without impacting the device's current configuration and that can be committed to <running>.

候補設定データストア（<candidate>）は、デバイスの現在の設定に影響を与えることなく操作でき、<running>にコミットできる設定データストアです。

The candidate configuration datastore may not be supported by all protocols or implementations.

候補設定データストアは、すべてのプロトコルや実装でサポートされているとは限りません。

<candidate> does not typically persist across reboots, even in the presence of non-volatile storage. If <candidate> is stored using non-volatile storage, it is reset at boot time to the contents of <running>.

<candidate>は通常、不揮発性ストレージがある場合でも、再起動後には維持されません。<candidate>が不揮発性ストレージを使用して格納されている場合、起動時に<running>の内容にリセットされます。

5.1.3. The Running Configuration Datastore (<running>)

5.1.3. 実行設定データストア（<running>）

The running configuration datastore (<running>) is a configuration datastore that holds the current configuration of the device. It MAY include configuration that requires further transformation before it can be applied, e.g., inactive configuration, or template-mechanism-oriented configuration that needs further expansion. However, <running> MUST always be a valid configuration data tree, as defined in Section 8.1 of [RFC7950].

実行設定データストア（<running>）は、デバイスの現在の設定を保持する設定データストアです。このデータストアには、適用される前にさらに変換を必要とする設定（たとえば、非アクティブな設定や、さらに展開する必要があるテンプレートメカニズム指向の設定）を含めてもよいです（MAY）。ただし、<running>は、[RFC7950]のセクション8.1で定義されているとおり、常に有効な設定データツリーでなければなりません（MUST）。

<running> MUST be supported if the device can be configured via conventional configuration datastores.

デバイスが従来型設定データストアを介して設定できる場合、<running>をサポートしなければなりません（MUST）。

If a device does not have a distinct <startup> and non-volatile storage is available, the device will typically use that non-volatile storage to allow <running> to persist across reboots.

デバイスが別個の<startup>を持たず、不揮発性ストレージが利用できる場合、デバイスは通常、その不揮発性ストレージを使用して、<running>が再起動後も維持されるようにします。

5.1.4. The Intended Configuration Datastore (<intended>)

5.1.4. 意図された設定データストア（<intended>）

The intended configuration datastore (<intended>) is a read-only configuration datastore. It represents the configuration after all configuration transformations to <running> are performed (e.g., template expansion, removal of inactive configuration) and is the configuration that the system attempts to apply.

意図された設定データストア（<intended>）は、読み取り専用の設定データストアです。これは、<running>に対するすべての設定変換（たとえば、テンプレートの展開や非アクティブな設定の削除）が実行された後の設定を表し、システムが適用しようとする設定です。

<intended> is tightly coupled to <running>. Whenever data is written to <running>, the server MUST also immediately update and validate <intended>.

<intended>は<running>と密接に結び付いています。<running>にデータが書き込まれるたびに、サーバーは<intended>もただちに更新して検証しなければなりません（MUST）。

<intended> MAY also be updated independently of <running> if the effect of a configuration transformation changes, but <intended> MUST always be a valid configuration data tree, as defined in Section 8.1 of [RFC7950].

設定変換の効果が変化した場合、<intended>を<running>とは独立して更新してもよいです（MAY）。ただし、<intended>は、[RFC7950]のセクション8.1で定義されているとおり、常に有効な設定データツリーでなければなりません（MUST）。

For simple implementations, <running> and <intended> are identical.

単純な実装では、<running>と<intended>は同一です。

The contents of <intended> are also related to the "config true" subset of <operational>; hence, a client can determine to what extent the intended configuration is currently in use by checking to see whether the contents of <intended> also appear in <operational>.

<intended>の内容は、<operational>の"config true"のサブセットとも関連しています。そのため、クライアントは、<intended>の内容が<operational>にも現れているかどうかを確認することで、意図された設定が現在どの程度使用されているかを判断できます。

<intended> does not persist across reboots; its relationship with <running> makes that unnecessary.

<intended>は再起動後には維持されません。<running>との関係があるため、その必要がないからです。

Currently, there are no standard mechanisms defined that affect <intended> so that it would have different content than <running>, but this architecture allows for such mechanisms to be defined.

現在のところ、<intended>に影響を与えて<running>とは異なる内容を持たせるような標準のメカニズムは定義されていませんが、このアーキテクチャーでは、そのようなメカニズムを定義できます。

One example of such a mechanism is support for marking nodes as inactive in <running>. Inactive nodes are not copied to <intended>. A second example is support for templates, which can perform transformations on the configuration from <running> to the configuration written to <intended>.

そのようなメカニズムの1つの例は、<running>内のノードを非アクティブとしてマークする機能のサポートです。非アクティブなノードは<intended>にはコピーされません。2つ目の例はテンプレートのサポートです。テンプレートは、<running>の設定を<intended>に書き込まれる設定へと変換できます。

5.2. Dynamic Configuration Datastores

5.2. 動的設定データストア

The model recognizes the need for dynamic configuration datastores that are, by definition, not part of the persistent configuration of a device. In some contexts, these have been termed "ephemeral datastores", since the information is ephemeral, i.e., lost upon reboot. The dynamic configuration datastores interact with the rest of the system through <operational>.

このモデルは、定義上、デバイスの永続的な設定の一部ではない、動的設定データストアの必要性を認めています。一部の文脈では、情報が一時的なもの、つまり再起動時に失われるものであることから、これらは"エフェメラルデータストア（ephemeral datastores）"と呼ばれてきました。動的設定データストアは、<operational>を通じてシステムの他の部分とやり取りします。

The datastore schema for a dynamic configuration datastore MAY differ from the datastore schema used for conventional configuration datastores. If a module does not contain any configuration data nodes and it is not needed to satisfy any imports, then it MAY be omitted from the datastore schema for the dynamic configuration datastore.

動的設定データストアのデータストアスキーマは、従来型設定データストアで使用されるデータストアスキーマと異なってもよいです（MAY）。あるモジュールが設定データノードを一切含まず、いずれのインポートを満たすためにも必要とされない場合、そのモジュールを動的設定データストアのデータストアスキーマから省略してもよいです（MAY）。

5.3. The Operational State Datastore (<operational>)

5.3. 運用状態データストア（<operational>）

The operational state datastore (<operational>) is a read-only datastore that consists of all "config true" and "config false" nodes defined in the datastore's schema. In the original NETCONF model, the operational state only had "config false" nodes. The reason for incorporating "config true" nodes here is to be able to expose all operational settings without having to replicate definitions in the data models.

運用状態データストア（<operational>）は、データストアのスキーマで定義されたすべての"config true"ノードと"config false"ノードで構成される読み取り専用のデータストアです。元のNETCONFモデルでは、運用状態には"config false"ノードしかありませんでした。ここで"config true"ノードを取り込む理由は、データモデル内で定義を重複させることなく、すべての運用上の設定値を公開できるようにするためです。

<operational> contains system state and all configuration actually used by the system. This includes all applied configuration from <intended>, learned configuration, system-provided configuration, and default values defined by any supported data models. In addition, <operational> also contains applied configuration from dynamic configuration datastores.

<operational>には、システム状態と、システムが実際に使用しているすべての設定が含まれます。これには、<intended>から適用されたすべての設定、学習された設定、システムが提供する設定、およびサポートされているデータモデルで定義されたデフォルト値が含まれます。さらに、<operational>には、動的設定データストアから適用された設定も含まれます。

The datastore schema for <operational> MUST be a superset of the combined datastore schema used in all configuration datastores, except that configuration data nodes supported in a configuration datastore MAY be omitted from <operational> if a server is not able to accurately report them.

<operational>のデータストアスキーマは、すべての設定データストアで使用されるデータストアスキーマを合わせたもののスーパーセットでなければなりません（MUST）。ただし、設定データストアでサポートされている設定データノードをサーバーが正確に報告できない場合は、それらを<operational>から省略してもよいです（MAY）。

Requests to retrieve nodes from <operational> always return the value in use if the node exists, regardless of any default value specified in the YANG module. If no value is returned for a given node, then this implies that the node is not used by the device.

<operational>からノードを取得するリクエストは、ノードが存在する場合、YANGモジュールで指定されたデフォルト値にかかわらず、常に使用中の値を返します。特定のノードについて値が返されない場合、そのノードはデバイスで使用されていないことを意味します。

The interpretation of what constitutes being "in use" by the system is dependent on both the schema definition and the device implementation. Generally, functionality that is enabled and operational on the system would be considered to be "in use". Conversely, functionality that is neither enabled nor operational on the system is considered not to be "in use"; hence, it SHOULD be omitted from <operational>.

システムによって"使用中（in use）"であるとは何を意味するかの解釈は、スキーマ定義とデバイスの実装の両方に依存します。一般に、システム上で有効化されていて動作している機能は、"使用中"であるとみなされます。逆に、システム上で有効化されてもおらず動作してもいない機能は、"使用中"ではないとみなされます。したがって、そのような機能は<operational>から省略すべきです（SHOULD）。

<operational> SHOULD conform to any constraints specified in the data model, but given the principal aim of returning "in use" values, it is possible that constraints MAY be violated under some circumstances (e.g., an abnormal value is "in use", the structure of a list is being modified, or remnant configuration (see Section 5.3.1) still exists). Note that deviations SHOULD be used when it is known in advance that a device does not fully conform to the <operational> schema.

<operational>は、データモデルで指定された制約に準拠すべきです（SHOULD）。しかし、"使用中"の値を返すことが主な目的であるため、状況によっては制約に違反してもよいです（MAY）（たとえば、異常な値が"使用中"である場合、リストの構造が変更されている最中である場合、残存設定（セクション5.3.1を参照）がまだ存在する場合など）。デバイスが<operational>のスキーマに完全には準拠していないことが事前にわかっている場合は、逸脱を使用すべきです（SHOULD）。

Only semantic constraints MAY be violated. These are the YANG "when", "must", "mandatory", "unique", "min-elements", and "max-elements" statements; and the uniqueness of key values.

意味的な制約に限り、違反してもよいです（MAY）。意味的な制約とは、YANGの"when"、"must"、"mandatory"、"unique"、"min-elements"、"max-elements"の各ステートメントと、キー値の一意性です。

Syntactic constraints MUST NOT be violated, including hierarchical organization, identifiers, and type-based constraints. If a node in <operational> does not meet the syntactic constraints, then it MUST NOT be returned, and some other mechanism should be used to flag the error.

階層構造、識別子、型に基づく制約を含む構文的な制約には、違反してはなりません（MUST NOT）。<operational>内のノードが構文的な制約を満たさない場合、そのノードを返してはなりません（MUST NOT）。そして、そのエラーを示すために何らかの別のメカニズムを使用すべきです。

<operational> does not persist across reboots.

<operational>は再起動後には維持されません。

5.3.1. Remnant Configuration

5.3.1. 残存設定

Changes to configuration may take time to percolate through to <operational>. During this period, <operational> may contain nodes for both the previous and current configuration, as closely as possible tracking the current operation of the device. Such remnant configuration from the previous configuration persists until the system has released resources used by the newly deleted configuration (e.g., network connections, memory allocations, file handles).

設定の変更が<operational>に浸透するまでには時間がかかる場合があります。この期間中、<operational>は、デバイスの現在の動作をできるだけ忠実に追跡するために、以前の設定と現在の設定の両方のノードを含む場合があります。以前の設定から残ったこのような残存設定は、新たに削除された設定が使用していたリソース（たとえば、ネットワークコネクション、メモリー割り当て、ファイルハンドル）をシステムが解放するまで存続します。

Remnant configuration is a common example of where the semantic constraints defined in the data model cannot be relied upon for <operational>, since the system may have remnant configuration whose constraints were valid with the previous configuration and that are not valid with the current configuration. Since constraints on "config false" nodes may refer to "config true" nodes, remnant configuration may force the violation of those constraints.

残存設定は、データモデルで定義された意味的な制約を<operational>について当てにできない場合のよくある例です。システムは、以前の設定では有効であったものの、現在の設定では有効ではない制約を持つ残存設定を持っている可能性があるからです。"config false"ノードに対する制約は"config true"ノードを参照する場合があるため、残存設定によってそれらの制約への違反が強いられる可能性があります。

5.3.2. Missing Resources

5.3.2. 存在しないリソース

Configuration in <intended> can refer to resources that are not available or otherwise not physically present. In these situations, these parts of <intended> are not applied. The data appears in <intended> but does not appear in <operational>.

<intended>内の設定は、利用できない、あるいは物理的に存在しないリソースを参照する場合があります。このような状況では、<intended>のそれらの部分は適用されません。そのデータは<intended>には現れますが、<operational>には現れません。

A typical example is an interface configuration that refers to an interface that is not currently present. In such a situation, the interface configuration remains in <intended> but the interface configuration will not appear in <operational>.

典型的な例は、現在存在しないインターフェイスを参照するインターフェイス設定です。このような状況では、インターフェイス設定は<intended>に残りますが、<operational>には現れません。

Note that configuration validity cannot depend on the current state of such resources, since that would imply that removing a resource might render the configuration invalid. This is unacceptable, especially given that rebooting such a device would cause it to restart with an invalid configuration. Instead, we allow configuration for missing resources to exist in <running> and <intended>, but it will not appear in <operational>.

設定の有効性は、そのようなリソースの現在の状態に依存してはならないことに注意してください。そうすると、リソースを取り除くことで設定が無効になる可能性があることになるからです。これは受け入れられません。特に、そのようなデバイスを再起動すると、無効な設定で再起動することになるからです。代わりに、存在しないリソースに対する設定が<running>と<intended>に存在することを認めますが、その設定は<operational>には現れません。

5.3.3. System-Controlled Resources

5.3.3. システムが制御するリソース

Sometimes, resources are controlled by the device and the corresponding system-controlled data appears in (and disappears from) <operational> dynamically. If a system-controlled resource has matching configuration in <intended> when it appears, the system will try to apply the configuration; this causes the configuration to appear in <operational> eventually (if application of the configuration was successful).

リソースがデバイスによって制御され、対応するシステム制御のデータが<operational>に動的に現れる（そして消える）ことがあります。システムが制御するリソースが現れたときに、それに一致する設定が<intended>にある場合、システムはその設定を適用しようとします。これにより、（設定の適用が成功すれば）最終的にその設定が<operational>に現れます。

5.3.4. Origin Metadata Annotation

5.3.4. オリジンメタデータアノテーション

As configuration flows into <operational>, it is conceptually marked with a metadata annotation [RFC7952] that indicates its origin. The origin applies to all configuration nodes except non-presence containers. The "origin" metadata annotation is defined in Section 7. The values are YANG identities. The following identities are defined:

設定が<operational>に流れ込むとき、その設定には、概念的に、そのオリジンを示すメタデータアノテーション[RFC7952]が付けられます。オリジンは、非プレゼンスコンテナーを除くすべての設定ノードに適用されます。"origin"メタデータアノテーションはセクション7で定義しています。その値はYANGアイデンティティーです。次のアイデンティティーが定義されています。

  • origin: abstract base identity from which the other origin identities are derived.
  • intended: represents configuration provided by <intended>.
  • dynamic: represents configuration provided by a dynamic configuration datastore.
  • system: represents configuration provided by the system itself. Examples of system configuration include applied configuration for an always-existing loopback interface, or interface configuration that is auto-created due to the hardware currently present in the device.
  • learned: represents configuration that has been learned via protocol interactions with other systems, including such protocols as link-layer negotiations, routing protocols, and DHCP.
  • default: represents configuration using a default value specified in the data model, using either values in the "default" statement or any values described in the "description" statement. The default origin is only used when the configuration has not been provided by any other source.
  • unknown: represents configuration for which the system cannot identify the origin.
  • origin：他のオリジンアイデンティティーの派生元となる抽象的な基底アイデンティティー。
  • intended：<intended>によって提供された設定を表します。
  • dynamic：動的設定データストアによって提供された設定を表します。
  • system：システム自体によって提供された設定を表します。システム設定の例としては、常に存在するループバックインターフェイスに適用された設定や、デバイスに現在存在するハードウェアに応じて自動的に作成されるインターフェイス設定などがあります。
  • learned：他のシステムとのプロトコルによるやり取りを介して学習された設定を表します。そのようなプロトコルには、リンク層のネゴシエーション、ルーティングプロトコル、DHCPなどがあります。
  • default：データモデルで指定されたデフォルト値を使用する設定を表します。"default"ステートメント内の値、または"description"ステートメントで説明されている任意の値のいずれかを使用します。defaultオリジンは、設定が他のどのソースからも提供されていない場合にのみ使用されます。
  • unknown：システムがオリジンを特定できない設定を表します。

These identities can be further refined, e.g., there could be separate identities for particular types or instances of dynamic configuration datastores derived from "dynamic".

これらのアイデンティティーはさらに細分化できます。たとえば、"dynamic"から派生した、動的設定データストアの特定の種類やインスタンスごとの別々のアイデンティティーが存在する可能性があります。

For all configuration data nodes in <operational>, the device SHOULD report the origin that most accurately reflects the source of the configuration that is in use by the system.

<operational>内のすべての設定データノードについて、デバイスは、システムが使用している設定のソースを最も正確に反映するオリジンを報告すべきです（SHOULD）。

In cases where it could be ambiguous as to which origin should be used, i.e., where the same data node value has originated from multiple sources, the "description" statement in the YANG module SHOULD be used as guidance for choosing the appropriate origin. For example:

どのオリジンを使用すべきかがあいまいになり得る場合、つまり、同じデータノードの値が複数のソースから生じている場合には、適切なオリジンを選択するためのガイダンスとして、YANGモジュール内の"description"ステートメントを使用すべきです（SHOULD）。たとえば、次のとおりです。

If, for a particular configuration node, the associated YANG "description" statement indicates that a protocol-negotiated value overrides any configured value, then the origin would be reported as "learned", even when a learned value is the same as the configured value.

特定の設定ノードについて、関連付けられたYANGの"description"ステートメントが、プロトコルでネゴシエートされた値が設定された値を上書きすることを示している場合、学習された値が設定された値と同じであっても、オリジンは"learned"として報告されることになります。

Conversely, if, for a particular configuration node, the associated YANG "description" statement indicates that a protocol-negotiated value does not override an explicitly configured value, then the origin would be reported as "intended", even when a learned value is the same as the configured value.

逆に、特定の設定ノードについて、関連付けられたYANGの"description"ステートメントが、プロトコルでネゴシエートされた値が明示的に設定された値を上書きしないことを示している場合、学習された値が設定された値と同じであっても、オリジンは"intended"として報告されることになります。

In the case that a device cannot provide an accurate origin for a particular configuration data node, it SHOULD use the origin "unknown".

デバイスが特定の設定データノードについて正確なオリジンを提供できない場合は、オリジン"unknown"を使用すべきです（SHOULD）。

6. Implications on YANG

6. YANGへの影響

6.1. XPath Context

6.1. XPathコンテキスト

This section updates Section 6.4.1 of RFC 7950.

このセクションは、RFC 7950のセクション6.4.1を更新します。

If a server implements the architecture defined in this document, the accessible trees for some XPath contexts are refined as follows:

サーバーがこの文書で定義するアーキテクチャーを実装している場合、一部のXPathコンテキストにおけるアクセス可能なツリーは、次のように改良されます。

  • If the XPath expression is defined in a substatement to a data node that represents system state, the accessible tree is all operational state in the server. The root node has all top-level data nodes in all modules as children.
  • If the XPath expression is defined in a substatement to a "notification" statement, the accessible tree is the notification instance and all operational state in the server. If the notification is defined on the top level in a module, then the root node has the node representing the notification being defined and all top-level data nodes in all modules as children. Otherwise, the root node has all top-level data nodes in all modules as children.
  • If the XPath expression is defined in a substatement to an "input" statement in an "rpc" or "action" statement, the accessible tree is the RPC or action operation instance and all operational state in the server. The root node has top-level data nodes in all modules as children. Additionally, for an RPC, the root node also has the node representing the RPC operation being defined as a child. The node representing the operation being defined has the operation's input parameters as children.
  • If the XPath expression is defined in a substatement to an "output" statement in an "rpc" or "action" statement, the accessible tree is the RPC or action operation instance and all operational state in the server. The root node has top-level data nodes in all modules as children. Additionally, for an RPC, the root node also has the node representing the RPC operation being defined as a child. The node representing the operation being defined has the operation's output parameters as children.
  • XPath式が、システム状態を表すデータノードのサブステートメント内で定義されている場合、アクセス可能なツリーはサーバー内のすべての運用状態です。ルートノードは、すべてのモジュールのすべてのトップレベルのデータノードを子として持ちます。
  • XPath式が"notification"ステートメントのサブステートメント内で定義されている場合、アクセス可能なツリーは、通知のインスタンスとサーバー内のすべての運用状態です。通知がモジュールのトップレベルで定義されている場合、ルートノードは、定義されている通知を表すノードと、すべてのモジュールのすべてのトップレベルのデータノードを子として持ちます。それ以外の場合、ルートノードは、すべてのモジュールのすべてのトップレベルのデータノードを子として持ちます。
  • XPath式が、"rpc"ステートメントまたは"action"ステートメント内の"input"ステートメントのサブステートメント内で定義されている場合、アクセス可能なツリーは、RPCまたはアクションの操作インスタンスと、サーバー内のすべての運用状態です。ルートノードは、すべてのモジュールのトップレベルのデータノードを子として持ちます。さらに、RPCの場合、ルートノードは、定義されているRPC操作を表すノードも子として持ちます。定義されている操作を表すノードは、その操作の入力パラメーターを子として持ちます。
  • XPath式が、"rpc"ステートメントまたは"action"ステートメント内の"output"ステートメントのサブステートメント内で定義されている場合、アクセス可能なツリーは、RPCまたはアクションの操作インスタンスと、サーバー内のすべての運用状態です。ルートノードは、すべてのモジュールのトップレベルのデータノードを子として持ちます。さらに、RPCの場合、ルートノードは、定義されているRPC操作を表すノードも子として持ちます。定義されている操作を表すノードは、その操作の出力パラメーターを子として持ちます。

6.2. Invocation of Actions and RPCs

6.2. アクションとRPCの呼び出し

This section updates Section 7.15 of RFC 7950.

このセクションは、RFC 7950のセクション7.15を更新します。

Actions are always invoked in the context of the operational state datastore. The node for which the action is invoked MUST exist in the operational state datastore.

アクションは、常に運用状態データストアのコンテキストで呼び出されます。アクションの呼び出し対象となるノードは、運用状態データストアに存在しなければなりません（MUST）。

Note that this document does not constrain the result of invoking an RPC or action in any way. For example, an RPC might be defined to modify the contents of some datastore.

この文書は、RPCやアクションを呼び出した結果をいかなる形でも制約しないことに注意してください。たとえば、あるデータストアの内容を変更するRPCが定義されるかもしれません。

The origin metadata annotation exposes the origin of values in the applied configuration. Origin information may provide hints that certain control-plane protocols are active on a device. Since origin information is tied to applied configuration values, it is only accessible to clients that have the permissions to read the applied configuration values. Security administrators should consider the sensitivity of origin information while defining access control rules.

オリジンメタデータアノテーションは、適用された設定に含まれる値のオリジンを公開します。オリジンの情報は、特定のコントロールプレーンプロトコルがデバイス上で動作していることのヒントを与える場合があります。オリジンの情報は適用された設定の値に結び付いているため、適用された設定の値を読み取る権限を持つクライアントだけがアクセスできます。セキュリティー管理者は、アクセス制御規則を定義する際に、オリジンの情報の機密性を考慮すべきです。

Appendix A. Guidelines for Defining Datastores

付録A. データストアを定義するためのガイドライン

The definition of a new datastore in this architecture should be provided in a document (e.g., an RFC) purposed for defining the datastore. When it makes sense, more than one datastore may be defined in the same document (e.g., when the datastores are logically connected). Each datastore's definition should address the points specified in the subsections below.

このアーキテクチャーにおける新しいデータストアの定義は、そのデータストアを定義することを目的とした文書（たとえば、RFC）で提供されるべきです。意味がある場合（たとえば、データストア同士が論理的に結び付いている場合）には、同じ文書で複数のデータストアを定義してもかまいません。各データストアの定義では、以下のサブセクションで規定する点に対処すべきです。

A.1. Define Which YANG Modules Can Be Used in the Datastore

A.1. データストアで使用できるYANGモジュールを定義する

Not all YANG modules may be used in all datastores. Some datastores may constrain which data models can be used in them. If it is desirable that a subset of all modules can be targeted to the datastore, then the documentation defining the datastore must indicate this.

すべてのYANGモジュールがすべてのデータストアで使用できるとは限りません。一部のデータストアは、そのデータストアで使用できるデータモデルを制限する場合があります。すべてのモジュールのうちの一部だけをデータストアの対象にできるようにすることが望ましい場合、そのデータストアを定義する文書でそのことを示さなければなりません。

A.2. Define Which Subset of YANG-Modeled Data Applies

A.2. YANGでモデル化されたデータのどのサブセットが適用されるかを定義する

By default, the data in a datastore is modeled by all YANG statements in the available YANG modules. However, it is possible to specify criteria that YANG statements must satisfy in order to be present in a datastore. For instance, maybe only "config true" nodes, or "config false" nodes that also have a specific YANG extension, are present in the datastore.

デフォルトでは、データストア内のデータは、利用可能なYANGモジュール内のすべてのYANGステートメントによってモデル化されます。ただし、YANGステートメントがデータストアに存在するために満たさなければならない基準を指定することもできます。たとえば、"config true"ノードだけ、あるいは特定のYANG拡張も持つ"config false"ノードだけがデータストアに存在する、といった場合が考えられます。

A.3. Define How Data Is Actualized

A.3. データがどのように実体化されるかを定義する

The new datastore must specify how it interacts with other datastores.

新しいデータストアは、他のデータストアとどのようにやり取りするかを規定しなければなりません。

For example, the diagram in Section 5 depicts dynamic configuration datastores feeding into <operational>. How this interaction occurs has to be defined by the particular dynamic configuration datastores. In some cases, it may occur implicitly, as soon as the data is put into the dynamic configuration datastore, while in other cases an explicit action (e.g., an RPC) may be required to trigger the application of the datastore's data.

たとえば、セクション5の図は、動的設定データストアが<operational>にデータを供給する様子を示しています。このやり取りがどのように行われるかは、個々の動的設定データストアによって定義されなければなりません。データが動的設定データストアに格納されるとすぐに暗黙的に行われる場合もあれば、データストアのデータの適用をトリガーするために明示的なアクション（たとえば、RPC）が必要になる場合もあります。

A.4. Define Which Protocols Can Be Used

A.4. 使用できるプロトコルを定義する

By default, it is assumed that both the NETCONF and RESTCONF protocols can be used to interact with a datastore. However, it may be that only a specific protocol can be used (e.g., Forwarding and Control Element Separation (ForCES)) or that a subset of all protocol operations or capabilities are available (e.g., no locking or no XPath-based filtering).

デフォルトでは、NETCONFプロトコルとRESTCONFプロトコルの両方を使用してデータストアとやり取りできるものとみなします。ただし、特定のプロトコル（たとえば、Forwarding and Control Element Separation（ForCES））しか使用できない場合や、プロトコルの操作や能力の一部しか利用できない場合（たとえば、ロックやXPathベースのフィルタリングが利用できない場合）もあります。

A.5. Define YANG Identities for the Datastore

A.5. データストアのYANGアイデンティティーを定義する

The datastore must be defined with a YANG identity that uses the "ds:datastore" identity, or one of its derived identities, as its base. This identity is necessary, so that the datastore can be referenced in protocol operations (e.g., <get-data>).

データストアは、"ds:datastore"アイデンティティーまたはその派生アイデンティティーのいずれかを基底として使用するYANGアイデンティティーで定義しなければなりません。このアイデンティティーは、プロトコル操作（たとえば、<get-data>）でデータストアを参照できるようにするために必要です。

The datastore may also be defined with an identity that uses the "or:origin" identity, or one of its derived identities, as its base. This identity is needed if the datastore interacts with <operational>, so that data originating from the datastore can be identified as such via the "origin" metadata attribute defined in Section 7.

データストアは、"or:origin"アイデンティティーまたはその派生アイデンティティーのいずれかを基底として使用するアイデンティティーで定義することもできます。このアイデンティティーは、データストアが<operational>とやり取りする場合に、セクション7で定義される"origin"メタデータ属性を介して、そのデータストアから生じたデータをそれと識別できるようにするために必要です。

これらのガイドラインの使用例は、付録Bに示しています。

C.2.1. Datastores

C.2.1. データストア

Each datastore represents differing views of these nodes. <running> will hold the configuration provided by the operator -- for example, a single BGP peer. <intended> will conceptually hold the data as validated, after the removal of data not intended for validation and after any local template mechanisms are performed. <operational> will show data from <intended> as well as any "config false" nodes.

各データストアは、これらのノードについてそれぞれ異なるビューを表します。<running>は、運用者が提供した設定（たとえば、1つのBGPピア）を保持します。<intended>は、概念的には、検証を意図していないデータの削除後、およびローカルのテンプレートメカニズムの実行後の、検証されたとおりのデータを保持します。<operational>は、<intended>からのデータと、あらゆる"config false"ノードを示します。

C.2.3. Removing a Peer

C.2.3. ピアの削除

Changes to configuration may take time to percolate through the various software components involved. During this period, it is imperative to continue to give an accurate view of the working of the device. <operational> will contain nodes for both the previous and current configuration, as closely as possible tracking the current operation of the device.

設定の変更が、関係するさまざまなソフトウェアコンポーネントに浸透するまでには時間がかかる場合があります。この期間中も、デバイスの動作について正確なビューを提供し続けることが不可欠です。<operational>は、デバイスの現在の動作をできるだけ忠実に追跡するために、以前の設定と現在の設定の両方のノードを含みます。

Consider the scenario where a client removes a BGP peer. When a peer is removed, the operational state will continue to reflect the existence of that peer until the peer's resources are released, including closing the peer's connection. During this period, the current data values will continue to be visible in <operational>, with the "origin" attribute set to indicate the origin of the original data.

One common issue in networking devices is the support of Field Replaceable Units (FRUs) that can be inserted and removed from the device without requiring a reboot or interfering with normal operation. These FRUs are typically interface cards, and the devices support pre-provisioning of these interfaces.

ネットワークデバイスにおけるよくある課題の1つは、再起動を必要とせず、通常の動作を妨げることもなく、デバイスに挿入したりデバイスから取り外したりできる現場交換可能ユニット（Field Replaceable Unit: FRU）のサポートです。これらのFRUは通常インターフェイスカードであり、デバイスはこれらのインターフェイスの事前プロビジョニングをサポートしています。

If a client creates an interface "et-0/0/0" but the interface does not physically exist at this point, then <intended> might contain the following:

クライアントがインターフェイス"et-0/0/0"を作成したものの、その時点でそのインターフェイスが物理的に存在しない場合、<intended>には次の内容が含まれるかもしれません。

  <interfaces>
    <interface>
      <name>et-0/0/0</name>
      <description>Test interface</description>
    </interface>
  </interfaces>

  <interfaces>
    <interface>
      <name>et-0/0/0</name>
      <description>Test interface</description>
    </interface>
  </interfaces>

Since the interface does not exist, this data does not appear in <operational>.

インターフェイスが存在しないため、このデータは<operational>には現れません。

When a FRU containing this interface is inserted, the system will detect it and process the associated configuration. <operational> will contain the data from <intended>, as well as nodes added by the system, such as the current value of the interface's MTU.

このインターフェイスを含むFRUが挿入されると、システムはそれを検出し、関連する設定を処理します。<operational>には、<intended>からのデータに加えて、インターフェイスのMTUの現在の値など、システムによって追加されたノードが含まれます。

  <interfaces xmlns:or="urn:ietf:params:xml:ns:yang:ietf-origin"
              or:origin="or:intended">

<intended>に"lo0"の設定が現れる場合、<operational>はそのデータを、オリジンを"intended"に設定して示します。"ip-address"が提供されていない場合は、システムが提供した値が次のように現れます。

      <description>loopback</description>
      <ip-address or:origin="or:system">127.0.0.1</ip-address>
      <ip-address>::1</ip-address>
    </interface>
  </interfaces>
