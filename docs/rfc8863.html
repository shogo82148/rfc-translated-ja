RFC 8863

Interactive Connectivity Establishment Patiently Awaiting Connectivity (ICE PAC)

RFC 8863

Interactive Connectivity Establishmentにおける接続性の辛抱強い待機（ICE PAC）

Abstract

概要

During the process of establishing peer-to-peer connectivity, Interactive Connectivity Establishment (ICE) agents can encounter situations where they have no candidate pairs to check, and, as a result, conclude that ICE processing has failed. However, because additional candidate pairs can be discovered during ICE processing, declaring failure at this point may be premature. This document discusses when these situations can occur.

ピアツーピアの接続性を確立する過程で、 Interactive Connectivity Establishment（ICE）エージェントは、チェックすべき候補ペアがなく、 その結果ICE処理が失敗したと結論づける状況に遭遇することがあります。 しかし、ICE処理の間に追加の候補ペアが発見される可能性があるため、 この時点で失敗を宣言するのは時期尚早かもしれません。 この文書では、このような状況がどのような場合に起こりうるかを説明します。

This document updates RFCs 8445 and 8838 by requiring that an ICE agent wait a minimum amount of time before declaring ICE failure, even if there are no candidate pairs left to check.

この文書は、チェックすべき候補ペアが残っていない場合でも、 ICEの失敗を宣言する前にICEエージェントが最小限の時間待機することを要求することにより、 RFC 8445およびRFC 8838を更新します。

1. Introduction

1. はじめに

[RFC8445] describes a protocol, Interactive Connectivity Establishment (ICE), for Network Address Translator (NAT) traversal for UDP-based communication.

[RFC8445]は、UDPベースの通信のためのネットワークアドレス変換器（NAT）越えのプロトコルである、 Interactive Connectivity Establishment（ICE）を記述しています。

When using ICE, endpoints will typically exchange ICE candidates, form a list of candidate pairs, and then test each candidate pair to see if connectivity can be established. If the test for a given pair fails, it is marked accordingly, and if all pairs have failed, the overall ICE process typically is considered to have failed.

ICEを使用する場合、エンドポイントは通常、ICE候補を交換し、 候補ペアのリストを作成し、その後各候補ペアをテストして接続性を確立できるかどうかを確認します。 あるペアのテストが失敗した場合、そのペアはそれに応じてマークされ、すべてのペアが失敗した場合、 ICEプロセス全体が失敗したとみなされるのが一般的です。

During the process of connectivity checks, additional candidates may be created as a result of successful inbound checks from the remote peer. Such candidates are referred to as peer-reflexive candidates; once discovered, these candidates will be used to form new candidate pairs, which will be tested like any other. However, there is an inherent problem here; if, before learning about any peer-reflexive candidates, an endpoint runs out of candidate pairs to check, either because it has none or it considers them all to have failed, it will prematurely declare failure and terminate ICE processing. This problem can occur in many common situations.

接続性チェックの過程で、リモートピアからのインバウンドチェックが成功した結果として、 追加の候補が作成されることがあります。 このような候補はピア反射型候補（peer-reflexive candidate）と呼ばれます。 いったん発見されると、これらの候補は新しい候補ペアの作成に使われ、その候補ペアは他の候補ペアと同様にテストされます。 しかし、ここには本質的な問題があります。 ピア反射型候補について知る前に、エンドポイントがチェックすべき候補ペアを使い果たしてしまうと、 それが候補ペアを1つも持っていないためであれ、そのすべてが失敗したとみなしたためであれ、 エンドポイントは時期尚早に失敗を宣言してICE処理を終了してしまいます。 この問題は、多くの一般的な状況で起こる可能性があります。

This specification updates [RFC8445] and [RFC8838] by simply requiring that an ICE agent wait a minimum amount of time before declaring ICE failure, even if there are no candidate pairs to check or all candidate pairs have failed. This delay provides enough time for the discovery of peer-reflexive candidates, which may eventually lead to ICE processing completing successfully.

この仕様は、チェックすべき候補ペアがない場合や、すべての候補ペアが失敗した場合でも、 ICEの失敗を宣言する前にICEエージェントが最小限の時間待機することを単に要求することにより、 [RFC8445]と[RFC8838]を更新します。 この遅延により、ピア反射型候補を発見するための十分な時間が確保され、 最終的にICE処理が正常に完了することにつながる可能性があります。

3. Relevant Scenarios

3. 関連するシナリオ

As noted above, the core problem this specification attempts to address is the situation where even after local gathering and remote candidate signaling have completed, the ICE agent immediately ends up with no valid pairs and no candidate pairs left to check, resulting in a premature ICE failure. This failure is premature because not enough time has elapsed to allow for discovery of peer-reflexive candidates from inbound connectivity checks; if discovered, these candidates are very likely to result in a valid pair.

前述のとおり、この仕様が対処しようとしている中心的な問題は、 ローカルでの収集とリモートの候補のシグナリングが完了した後でも、 ICEエージェントがすぐに有効なペアもチェックすべき候補ペアも残っていない状態になり、 その結果、時期尚早にICEが失敗してしまうという状況です。 この失敗が時期尚早なのは、インバウンドの接続性チェックからピア反射型候補を発見するのに 十分な時間が経過していないためです。 もし発見されれば、これらの候補は有効なペアになる可能性が非常に高いです。

In most ICE scenarios, the lengthy timeouts for connectivity check transactions, typically tens of seconds, will prevent this problem from occurring. However, there are certain specific cases where this problem will frequently occur.

ほとんどのICEシナリオでは、接続性チェックのトランザクションのタイムアウトが通常数十秒と長いため、 この問題は発生しません。 しかし、この問題が頻繁に発生する特定のケースがいくつかあります。

3.1. No Candidates from Peer

3.1. ピアからの候補がない場合

Per [RFC8838], an ICE agent can provide zero candidates of its own. If the agent somehow knows that the remote endpoint is directly reachable, gathering local candidates is unnecessary and will only cause delays; the peer agent can discover the appropriate local candidate via connectivity checks.

[RFC8838]によれば、ICEエージェントは自身の候補を1つも提供しないことができます。 エージェントが何らかの方法でリモートエンドポイントに直接到達可能であることを知っている場合、 ローカル候補の収集は不要であり、遅延を引き起こすだけです。 ピアエージェントは、接続性チェックを通じて適切なローカル候補を発見できます。

However, following the procedures from [RFC8445] strictly will result in immediate ICE failure, since the checklist at the peer agent will be empty.

しかし、[RFC8445]の手順に厳密に従うと、 ピアエージェントのチェックリストが空になるため、即座にICEが失敗してしまいます。

3.2. All Candidates Discarded

3.2. すべての候補が破棄される場合

Even if the ICE agent provides candidates, they may be discarded by the peer agent if it does not know what to do with them. For example, candidates may use an address family that the peer agent does not support (e.g., a host candidate with an IPv6 address in a NAT64 scenario) or that may not be usable for some other reason.

ICEエージェントが候補を提供したとしても、ピアエージェントがそれらの候補をどう扱えばよいかわからない場合、 ピアエージェントによって破棄されることがあります。 たとえば、候補がピアエージェントのサポートしていないアドレスファミリーを使用している場合 （例：NAT64シナリオにおけるIPv6アドレスを持つホスト候補）や、 その他の何らかの理由で使用できない場合があります。

In these scenarios, when the candidates are discarded, the checklist at the peer agent will once again be empty, leading to immediate ICE failure.

これらのシナリオでは、候補が破棄されると、ピアエージェントのチェックリストはやはり空になり、 即座にICEが失敗することになります。

3.3. Immediate Candidate Pair Failure

3.3. 候補ペアが即座に失敗する場合

Section 7.2.5.2 of [RFC8445] describes several situations in which a candidate pair will be considered to have failed, well before the connectivity check transaction timeout.

[RFC8445]のSection 7.2.5.2は、 接続性チェックのトランザクションがタイムアウトするよりもずっと前に、 候補ペアが失敗したとみなされるいくつかの状況を記述しています。

As a result, even if the ICE agent provides usable candidates, the pairs created by the peer agent may fail immediately when checked, e.g., a check to a non-routable address that receives an immediate ICMP error.

その結果、ICEエージェントが使用可能な候補を提供したとしても、 ピアエージェントが作成したペアはチェックした際に即座に失敗することがあります。 たとえば、ルーティング不可能なアドレスへのチェックが、即座にICMPエラーを受け取る場合です。

In this situation, the checklist at the peer agent may contain only failed pairs, resulting in immediate ICE failure.

この状況では、ピアエージェントのチェックリストには失敗したペアしか含まれず、 その結果、即座にICEが失敗することがあります。

4. Update to RFC 8445

4. RFC 8445の更新

In order to avoid the problem raised by this document, the ICE agent needs to wait enough time to allow peer-reflexive candidates to be discovered. Accordingly, when a full ICE implementation begins its ICE processing, as described in [RFC8445], Section 6.1, it MUST set a timer, henceforth known as the "PAC timer" (Patiently Awaiting Connectivity), to ensure that ICE will run for a minimum amount of time before determining failure.

この文書で提起された問題を回避するために、ICEエージェントは、 ピア反射型候補が発見されるのに十分な時間待機する必要があります。 したがって、フルICE実装は、[RFC8445], Section 6.1で説明されているようにICE処理を開始する際、 失敗を判定する前にICEが最小限の時間実行されることを保証するために、 タイマー（以降、「PACタイマー」（Patiently Awaiting Connectivity）と呼びます）を設定しなければなりません（MUST）。

Specifically, the ICE agent will start its timer once it believes ICE connectivity checks are starting. This occurs when the agent has sent the values needed to perform connectivity checks (e.g., the Username Fragment and Password denoted in [RFC8445], Section 5.3) and has received some indication that the remote side is ready to start connectivity checks, typically via receipt of the values mentioned above. Note that the agent will start the timer even if it has not sent or received any ICE candidates.

具体的には、ICEエージェントは、ICE接続性チェックが開始されつつあると判断した時点でタイマーを開始します。 これは、エージェントが接続性チェックを実行するために必要な値 （たとえば、[RFC8445], Section 5.3で示されているユーザー名フラグメントとパスワード）を送信し、 かつ、リモート側が接続性チェックを開始する準備ができていることを示す何らかの指標を受信した時点です。 この指標は通常、前述の値の受信によって得られます。 エージェントは、ICE候補を1つも送受信していない場合でもタイマーを開始することに注意してください。

The RECOMMENDED duration for the PAC timer is equal to the agent's connectivity check transaction timeout, including all retransmissions. When using default values for retransmission timeout (RTO) and Rc, this amounts to 39.5 seconds, as explained in [RFC5389], Section 7.2.1. This timeout value is chosen to roughly coincide with the maximum possible duration of ICE connectivity checks from the remote peer, which, if successful, could create peer-reflexive candidates. Because the ICE agent doesn't know the exact number of candidate pairs and pacing interval in use by the remote side, this timeout value is simply a guess, albeit an educated one. Regardless, for this particular problem, the desired benefits will be realized as long as the agent waits some reasonable amount of time, and, as usual, the application is in the best position to determine what is reasonable for its scenario.

PACタイマーの期間として推奨されます（RECOMMENDED）のは、 すべての再送を含む、エージェントの接続性チェックのトランザクションタイムアウトと等しい値です。 [RFC5389], Section 7.2.1で説明されているように、 再送タイムアウト（RTO）とRcにデフォルト値を使用する場合、これは39.5秒になります。 このタイムアウト値は、リモートピアからのICE接続性チェックの最大継続時間とおおむね一致するように選ばれています。 リモートピアからの接続性チェックが成功すれば、ピア反射型候補が作成される可能性があります。 ICEエージェントは、リモート側が使用している候補ペアの正確な数やペーシング間隔を知らないため、 このタイムアウト値は、根拠のあるものではありますが、単なる推測にすぎません。 いずれにせよ、この特定の問題については、エージェントがある程度妥当な時間待機する限り、 望ましい効果が得られます。 そして、いつものように、そのシナリオにとって何が妥当かを判断するのに最も適した立場にあるのはアプリケーションです。

While the timer is still running, the ICE agent MUST NOT update a checklist state from Running to Failed, even if there are no pairs left in the checklist to check. As a result, the ICE agent will not remove any data streams or set the state of the ICE session to Failed as long as the timer is running.

タイマーがまだ動作している間は、チェックリスト内にチェックすべきペアが残っていない場合でも、 ICEエージェントはチェックリストの状態をRunningからFailedに更新してはなりません（MUST NOT）。 その結果、タイマーが動作している限り、ICEエージェントはデータストリームを削除したり、 ICEセッションの状態をFailedに設定したりすることはありません。

When the timer period eventually elapses, the ICE agent MUST resume typical ICE processing, including setting the state of any checklists to Failed if they have no pairs left to check and handling any consequences as indicated in [RFC8445], Section 8.1.2. Naturally, if there are no such checklists, no action is necessary.

タイマーの期間が最終的に経過したとき、ICEエージェントは通常のICE処理を再開しなければなりません（MUST）。 これには、チェックすべきペアが残っていないチェックリストの状態をFailedに設定することや、 [RFC8445], Section 8.1.2で示されているとおりにその結果を処理することが含まれます。 当然ながら、そのようなチェックリストがない場合は、何もする必要はありません。

One consequence of this behavior is that in cases where ICE should fail, e.g., where both sides provide candidates with unsupported address families, ICE will no longer fail immediately -- it will only fail when the PAC timer expires. However, because most ICE scenarios require an extended period of time to determine failure, the fact that some specific scenarios no longer fail quickly should have minimal application impact, if any.

この動作の結果の1つとして、ICEが失敗すべき場合 （たとえば、双方がサポートされていないアドレスファミリーの候補を提供する場合）に、 ICEはもはや即座には失敗せず、PACタイマーが期限切れになったときに初めて失敗するようになります。 しかし、ほとんどのICEシナリオでは失敗を判定するのに長い時間を要するため、 一部の特定のシナリオで素早く失敗しなくなることがアプリケーションに与える影響は、 仮にあったとしてもごくわずかなはずです。

Note also that the PAC timer is potentially relevant to the ICE nomination procedure described in [RFC8445], Section 8.1.1. That specification does not define a minimum duration for ICE processing prior to nomination of a candidate pair, but in order to select the best candidate pair, ICE needs to run for enough time in order to allow peer-reflexive candidates to be discovered and checked, as noted above. Accordingly, the controlling ICE agent SHOULD wait a sufficient amount of time before nominating candidate pairs, and it MAY use the PAC timer to do so. As always, the controlling ICE agent retains full discretion and MAY decide, based on its own criteria, to nominate pairs prior to the PAC timer period elapsing.

また、PACタイマーは、[RFC8445], Section 8.1.1で説明されているICEのノミネーション手順にも関係する可能性があることに注意してください。 その仕様は、候補ペアのノミネーションに先立つICE処理の最小継続時間を定義していませんが、 最良の候補ペアを選択するためには、前述のとおり、ピア反射型候補が発見されチェックされるのに 十分な時間ICEを実行する必要があります。 したがって、制御側（controlling）ICEエージェントは、候補ペアをノミネートする前に十分な時間待機すべきです（SHOULD）。 また、そのためにPACタイマーを使用してもよいです（MAY）。 いつものように、制御側ICEエージェントは完全な裁量を保持しており、 自身の基準に基づいて、PACタイマーの期間が経過する前にペアをノミネートすることを決定してもよいです（MAY）。

5. Update to RFC 8838

5. RFC 8838の更新

Trickle ICE [RFC8838] considers a similar problem, namely whether an ICE agent should allow a checklist to enter the Failed state if more candidates might still be provided by the remote peer. The solution, specified in [RFC8838], Section 8, is to wait until an end-of-candidates indication has been received before determining ICE failure.

Trickle ICE [RFC8838]は、 同様の問題、すなわち、リモートピアからさらに候補が提供される可能性がある場合に、 ICEエージェントがチェックリストをFailed状態に移行させてよいかどうかという問題を検討しています。 [RFC8838], Section 8で規定されている解決策は、 ICEの失敗を判定する前に、候補終了（end-of-candidates）の指標を受信するまで待機するというものです。

However, for the same reasons described above, the ICE agent may discover peer-reflexive candidates after it has received the end-of-candidates indication, and so the solution proposed by this document MUST still be used even when the ICE agent is using Trickle ICE.

しかし、前述と同じ理由により、ICEエージェントは候補終了の指標を受信した後に ピア反射型候補を発見する可能性があります。 そのため、ICEエージェントがTrickle ICEを使用している場合でも、 この文書で提案する解決策を使用しなければなりません（MUST）。

Note also that sending an end-of-candidates indication is only a SHOULD-strength requirement, which means that ICE agents will need to implement a backup mechanism to decide when all candidates have been received, typically a timer. Accordingly, ICE agents MAY use the PAC timer to also serve as an end-of-candidates fallback.

また、候補終了の指標の送信はすべきです（SHOULD）レベルの要件にすぎないことに注意してください。 これは、ICEエージェントが、すべての候補を受信したのはいつかを判断するためのバックアップの仕組み （通常はタイマー）を実装する必要があることを意味します。 したがって、ICEエージェントは、PACタイマーを候補終了のフォールバックとしても使用してもよいです（MAY）。

6. Security Considerations

6. セキュリティーに関する考慮事項

The security considerations for ICE are defined in [RFC8445]. This specification only recommends that ICE agents wait for a certain period of time before they declare ICE failure; it does not introduce new security considerations.

ICEのセキュリティーに関する考慮事項は、[RFC8445]で定義されています。 この仕様は、ICEエージェントがICEの失敗を宣言する前に一定期間待機することを推奨しているだけであり、 新たなセキュリティーに関する考慮事項をもたらすものではありません。
