RFC 8278

Mobile Access Gateway (MAG) Multipath Options

RFC 8278

モバイルアクセスゲートウェイ（MAG）マルチパスオプション

Abstract

概要

This specification defines extensions to the Proxy Mobile IPv6 (PMIPv6) protocol that allow a mobile access gateway (MAG) to register more than one proxy care-of address (pCoA) with the local mobility anchor (LMA) and to simultaneously establish multiple IP tunnels with the LMA. This capability allows the MAG to utilize all the available access networks to route the mobile node's IP traffic. This document defines the following two new mobility header options: the MAG Multipath Binding option and the MAG Identifier option.

この仕様は、Proxy Mobile IPv6（PMIPv6）プロトコルの拡張を定義します。この拡張により、モバイルアクセスゲートウェイ（mobile access gateway、MAG）は、ローカルモビリティーアンカー（local mobility anchor、LMA）に複数のプロキシー気付アドレス（proxy care-of address、pCoA）を登録し、LMAとの間に複数のIPトンネルを同時に確立できるようになります。この能力により、MAGは利用可能なすべてのアクセスネットワークを使って、モバイルノードのIPトラフィックをルーティングできるようになります。この文書は、MAG Multipath BindingオプションとMAG Identifierオプションという2つの新しいモビリティーヘッダーオプションを定義します。

1. Introduction

1. はじめに

Multihoming support on IP hosts can greatly improve the user experience. With the simultaneous use of multiple access networks, multihoming brings better network connectivity, reliability, and improved quality of communication. The following are some of the goals and benefits of multihoming support:

IPホストでのマルチホーミングのサポートは、ユーザー体験を大きく改善できます。複数のアクセスネットワークを同時に使うことで、マルチホーミングはネットワーク接続性と信頼性を高め、通信品質を改善します。マルチホーミングのサポートの目標と利点には、次のようなものがあります。

  • Redundancy/Fault-Recovery
  • Load balancing
  • Load sharing
  • Preference settings
  • 冗長性／障害回復
  • 負荷分散（load balancing）
  • 負荷共有（load sharing）
  • 優先度の設定

According to [RFC4908], users of small-scale networks can benefit from a mobile and fixed multihomed architecture using mobile IP [RFC6275] and Network Mobility (NEMO) [RFC3963].

[RFC4908]によると、小規模ネットワークのユーザーは、モバイルIP[RFC6275]とネットワークモビリティー（NEMO）[RFC3963]を使った、モバイルと固定のマルチホームアーキテクチャーの恩恵を受けることができます。

The motivation for this work is to extend the PMIPv6 protocol with multihoming extensions [RFC4908] for realizing the following capabilities:

この作業の動機は、次の能力を実現するために、PMIPv6プロトコルをマルチホーミング拡張[RFC4908]で拡張することです。

  • Using GRE as mobile tunneling, possibly with its key extension [RFC5845].
  • Using UDP encapsulation [RFC5844] in order to support NAT traversal in an IPv4 networking environment.
  • Using the prefix delegation mechanism [RFC7148].
  • Using the Vendor Specific Mobility Option [RFC5094], for example, to allow the MAG and LMA to exchange information (e.g., WAN interface QoS metrics), which allows the appropriate traffic-steering decisions to be made.
  • モバイルトンネリングとしてGREを使うこと。場合によってはその鍵拡張[RFC5845]も使います。
  • IPv4ネットワーク環境でのNATトラバーサルをサポートするために、UDPカプセル化[RFC5844]を使うこと。
  • プレフィックス委任メカニズム[RFC7148]を使うこと。
  • ベンダー固有モビリティーオプション（Vendor Specific Mobility Option）[RFC5094]を使うこと。たとえば、MAGとLMAが情報（WANインターフェイスのQoSメトリクスなど）を交換できるようにし、それによって適切なトラフィックステアリングの判断を下せるようにします。

PMIPv6 relies on two mobility entities: the MAG, which acts as the default gateway for the end node (either a mobile or a fixed node) attached to the MAG's access links, and the LMA, which acts as the topological anchor point. IP tunnel is created with any one of the supported encapsulation mode between the MAG and the LMA. Then, the MAG and LMA distribute the end node's traffic over these tunnels. All PMIPv6 operations are performed on behalf of the end node and its correspondent node. Thus, it makes PMIPv6 well adapted to multihomed architecture as considered in [RFC4908]. Taking the LTE and WLAN networking environments as examples, the PMIPv6-based multihomed architecture is depicted in Figure 1. In this example, IP flows, Flow-1 and Flow-3 are routed over Tunnel-1 and Flow-2 is routed over Tunnel-2. However, IP traffic belonging to Flow-4 is distributed on both Tunnel-1 and Tunnel-2 paths.

PMIPv6は2つのモビリティーエンティティーに依存しています。1つはMAGで、MAGのアクセスリンクに接続されたエンドノード（モバイルノードまたは固定ノード）のデフォルトゲートウェイとして動作します。もう1つはLMAで、トポロジー上のアンカーポイントとして動作します。MAGとLMAの間には、サポートされているいずれかのカプセル化モードでIPトンネルが作成されます。そして、MAGとLMAはエンドノードのトラフィックをこれらのトンネルに分散させます。PMIPv6のすべての動作は、エンドノードとその通信相手ノードに代わって実行されます。したがって、PMIPv6は[RFC4908]で検討されているマルチホームアーキテクチャーによく適合します。LTEとWLANのネットワーク環境を例として、PMIPv6ベースのマルチホームアーキテクチャーを図1に示します。この例では、IPフローのうちFlow-1とFlow-3はTunnel-1を経由してルーティングされ、Flow-2はTunnel-2を経由してルーティングされます。一方、Flow-4に属するIPトラフィックは、Tunnel-1とTunnel-2の両方の経路に分散されます。

The current version of PMIPv6 does not allow a MAG to register more than one pCoA to the LMA. In other words, only one MAG/LMA link, i.e., IP-in-IP tunnel, can be used at the same time. This document overcomes this limitation by defining the multiple pCoAs extension for PMIPv6.

現在のバージョンのPMIPv6では、MAGがLMAに複数のpCoAを登録することはできません。言い換えると、同時に使えるMAG／LMA間のリンク（すなわちIP-in-IPトンネル）は1つだけです。この文書は、PMIPv6の複数pCoA拡張を定義することで、この制限を克服します。

3. Overview

3. 概要

3.1. Example Call Flow

3.1. コールフローの例

Figure 2 is the call flow detailing multi-access support with PMIPv6. The MAG in this example scenario is equipped with both WLAN and LTE interfaces and is also configured with the multihoming functionality. The steps of the call flow are as follows:

図2は、PMIPv6によるマルチアクセスのサポートを詳しく示すコールフローです。この例のシナリオのMAGは、WLANとLTEの両方のインターフェイスを備えており、マルチホーミング機能も設定されています。コールフローの手順は次のとおりです。

Steps (1) and (2): The MAG attaches to both WLAN and LTE networks. Then, the MAG obtains two different pCoAs, respectfully.

手順（1）と（2）: MAGはWLANとLTEの両方のネットワークに接続します。そして、MAGはそれぞれ異なる2つのpCoAを取得します。

Step (3): The MAG sends, over the LTE access, a Proxy Binding Update (PBU) message with the new MAG Multipath Binding (MMB) and MAG Network Access Identifier (MAG-NAI) options to the LMA. The request can be for a physical mobile node attached to the MAG or for a logical mobile node configured on the mobile access gateway. A logical mobile node is a logical representation of a mobile node in the form of a configuration that is always enabled on the MAG. The mobility session that is created (i.e., create a Binding Cache Entry (BCE)) on the LMA will be marked with multipath support.

手順（3）: MAGは、LTEアクセスを経由して、新しいMAG Multipath Binding（MMB）オプションとMAG Network Access Identifier（MAG-NAI）オプションを含むProxy Binding Update（PBU）メッセージをLMAに送信します。このリクエストは、MAGに接続された物理的なモバイルノードのためのものである場合も、モバイルアクセスゲートウェイ上に設定された論理的なモバイルノードのためのものである場合もあります。論理的なモバイルノードとは、MAG上で常に有効になっている設定という形でモバイルノードを論理的に表現したものです。LMA上に作成されるモビリティーセッション（すなわち、バインディングキャッシュエントリー（Binding Cache Entry、BCE）の作成）には、マルチパスのサポートが示されます。

Step (4): The LMA sends back a Proxy Binding Acknowledgement (PBA) including the Home Network Prefix (HNP) and other session parameters allocated for that mobility session.

手順（4）: LMAは、ホームネットワークプレフィックス（Home Network Prefix、HNP）と、そのモビリティーセッションに割り当てたその他のセッションパラメーターを含むProxy Binding Acknowledgement（PBA）を返送します。

Step (5): IP tunnel is created between the MAG and the LMA over LTE access with any one of the supported encapsulation modes.

手順（5）: LTEアクセスを経由して、MAGとLMAの間に、サポートされているいずれかのカプセル化モードでIPトンネルが作成されます。

Steps (6) to (8): The MAG repeats steps (3) to (5) on the WLAN access. The MAG includes the HNP, received on step (4) in the PBU. The LMA updates its binding cache by creating a new mobility session for this MAG.

手順（6）〜（8）: MAGはWLANアクセス上で手順（3）〜（5）を繰り返します。MAGは、手順（4）で受信したHNPをPBUに含めます。LMAは、このMAGのための新しいモビリティーセッションを作成して、バインディングキャッシュを更新します。

Steps (9) and (10): The IP hosts MN_1 and MN_2 are assigned IP addresses from the mobile network prefix delegated to the MAG by the LMA.

手順（9）と（10）: IPホストMN_1とMN_2には、LMAがMAGに委任したモバイルネットワークプレフィックスからIPアドレスが割り当てられます。

3.2. Traffic Distribution Schemes

3.2. トラフィック分散方式

When the MAG has registered a multipath binding with the LMA, there will be multiple established overlay tunnels between them. The MAG and the LMA can use any one, or more, of the available tunnel paths for routing the mobile node's IP traffic. This specification does not recommend or define any specific traffic distribution scheme. However, it identifies two well-known approaches that implementations can potentially use. These approaches are per-flow and per-packet traffic distribution schemes.

MAGがLMAにマルチパスバインディングを登録すると、両者の間には確立された複数のオーバーレイトンネルが存在することになります。MAGとLMAは、モバイルノードのIPトラフィックのルーティングに、利用可能なトンネル経路のうち任意の1つ以上を使うことができます。この仕様は、特定のトラフィック分散方式を推奨したり定義したりはしません。ただし、実装が使う可能性のある、よく知られた2つの手法を示します。それは、フローごとのトラフィック分散方式とパケットごとのトラフィック分散方式です。

Per-Flow Traffic Distribution:

フローごとのトラフィック分散:

  • In this approach, the MAG and the LMA associate each of the IP flows (upstream and downstream) with a specific tunnel path. The packets in a given IP flow are always routed on the same overlay tunnel path; they are never split and routed concurrently on more than one tunnel path. It is possible for a given flow to be moved from one tunnel path to another, but the flow is never split. The decision to bind a given IP flow to a specific tunnel path is based on the traffic distribution policy. This traffic distribution policy is either statically configured on both the MAG and the LMA or dynamically negotiated over PMIPv6 signaling. The Flow Binding extension [RFC6089] and Traffic Selectors for Flow Bindings [RFC6088] define the mechanism and the semantics for exchanging the traffic policy between two tunnel peers; the same mechanism and the mobility options are used here.
  • この手法では、MAGとLMAは、IPフロー（上りと下り）のそれぞれを特定のトンネル経路に関連付けます。あるIPフローのパケットは、常に同じオーバーレイトンネル経路でルーティングされます。パケットが分割され、複数のトンネル経路で同時にルーティングされることはありません。あるフローをあるトンネル経路から別のトンネル経路に移すことはできますが、フローが分割されることはありません。あるIPフローを特定のトンネル経路に結び付ける判断は、トラフィック分散ポリシーに基づきます。このトラフィック分散ポリシーは、MAGとLMAの両方に静的に設定されるか、PMIPv6シグナリングを通じて動的にネゴシエートされます。フローバインディング拡張（Flow Binding extension）[RFC6089]とフローバインディングのためのトラフィックセレクター（Traffic Selectors for Flow Bindings）[RFC6088]は、2つのトンネルピアの間でトラフィックポリシーを交換するためのメカニズムとセマンティクスを定義しています。ここでも同じメカニズムとモビリティーオプションを使います。

Per-Packet Traffic Distribution:

パケットごとのトラフィック分散:

  • In this approach, packets belonging to a given IP flow will be split and routed across more than one tunnel path. The exact approach for traffic distribution or the distribution weights is outside the scope of this specification. In a very simplistic approach, assuming that the established tunnel paths have symmetric characteristics, the packets can be equally distributed on all the available tunnel paths. In a different scenario, when the links have different speeds, the chosen approach can be based on weighted distribution (e.g., n:m ratio). However, in any of these chosen approaches, implementations have to be sensitive to issues related to asymmetric link characteristics and the resulting issues such as reordering, buffering, and the impact on application performance. Care must be taken to ensure that there is no negative impact on the application performance due to the use of this approach.
  • この手法では、あるIPフローに属するパケットが複数のトンネル経路に振り分けられ、それぞれの経路でルーティングされます。トラフィック分散の具体的な手法や分散の重みは、この仕様の範囲外です。ごく単純な手法では、確立されたトンネル経路の特性が対称であると仮定して、利用可能なすべてのトンネル経路にパケットを均等に分散できます。別のシナリオとして、リンクの速度が異なる場合には、重み付き分散（例: n:mの比率）に基づく手法を選ぶこともできます。ただし、どの手法を選んだ場合でも、実装はリンク特性の非対称性に関連する問題と、その結果として生じる並べ替え、バッファリング、アプリケーション性能への影響などの問題に注意を払う必要があります。この手法の使用によってアプリケーション性能に悪影響が出ないように注意しなければなりません。

4. Protocol Extensions

4. プロトコル拡張

4.1. MAG Multipath Binding Option

4.1. MAG Multipath Bindingオプション

The MAG Multipath Binding option is a new mobility header option defined for use with PBU and PBA messages exchanged between the LMA and the MAG.

MAG Multipath Bindingオプションは、LMAとMAGの間で交換されるPBUメッセージとPBAメッセージで使うために定義された、新しいモビリティーヘッダーオプションです。

This mobility header option is used for requesting multipath support. It indicates that the MAG is requesting that the LMA register the current CoA associated with the request as one of the many CoAs through which the MAG can be reached. It is also used for carrying the information related to the access network associated with the CoA.

このモビリティーヘッダーオプションは、マルチパスのサポートを要求するために使われます。このオプションは、リクエストに関連付けられた現在のCoAを、MAGに到達可能な多数のCoAのうちの1つとして登録するよう、MAGがLMAに要求していることを示します。また、このオプションは、そのCoAに関連付けられたアクセスネットワークに関する情報を運ぶためにも使われます。

The MAG Multipath Binding option does not have any alignment requirement. Its format is as shown in Figure 3:

MAG Multipath Bindingオプションには、アラインメントの要件はありません。その形式を図3に示します。

Type
Type: MAG Multipath Binding (63)
Length
8-bit unsigned integer indicating the length of the option in octets, excluding the Type and Length fields.
Interface Access-Technology Type (If-ATT)
This 8-bit field identifies the Access-Technology type of the interface through which the mobile node is connected. The permitted values for this are from the Access Technology Type registry <https://www.iana.org/assignments/mobility-parameters/> defined in [RFC5213].
Interface Label (If-Label)

This 8-bit unsigned integer represents the interface label.

The interface label is an identifier configured on the WAN interface of the MAG. All the WAN interfaces of the MAG that are used for sending PBU messages are configured with a label. The labels merely identify the type of WAN interface and are primarily used in application-routing policies. For example, a Wi-Fi interface can be configured with a label "9" and an LTE interface with a label "11". Furthermore, the same label may be configured on two WAN interfaces of similar characteristics (e.g., two Ethernet interfaces with the same label).

Interface labels are signaled from the MAG to the LMA in the PBU messages and both the LMA and MAG will be able to mark each of the dynamically created Binding/Tunnel with the associated label. These labels are used in generating consistent application-routing rules on the both the LMA and the MAG. For example, there can be a policy requiring HTTP packets to be routed over an interface that has the interface label of "9", and if any of the interfaces with interface label "9" are not available, the traffic needs to be routed over the interface with the interface label "11". The MAG and the LMA will be able to apply this routing rule with the exchange of interface labels in PBU messages and by associating the application flows to tunnels with the matching interface labels.

Binding Identifier (BID)

This 8-bit unsigned integer is used for identifying the binding. The permitted values are 1 through 254. The values 0 and 255 are reserved.

The MAG identifies each of the mobile node's bindings with a unique identifier. The MAG includes the identifier in the PBU message; when the PBU request is accepted by the LMA, the resulting binding is associated with this BID in the mobile node's Binding Cache entry.

Bulk Re-registration Flag (B)
If set to a value of (1), this flag notifies the LMA to consider this as a request to update the binding lifetime of all the mobile node's bindings upon accepting this specific request. The (B) flag MUST NOT be set to a value of (1) if the value of the Registration Overwrite (O) flag is set to a value of (1).
Registration Overwrite (O)
This flag, if set to a value of (1), notifies the LMA that upon accepting this request, it should replace all of the mobile node's existing bindings with this binding. This flag MUST NOT be set to a value of (1) if the value of the Bulk Re-registration Flag (B) is set to a value of (1). This flag MUST be set to a value of (0) in De-Registration requests.
Reserved
This field is unused in this specification. The value MUST be set to zero (0) by the sender and MUST be ignored by the receiver.
Type
Type: MAG Multipath Binding（63）
Length
オプションの長さをオクテット単位で示す8ビット符号なし整数です。TypeフィールドとLengthフィールドは含みません。
インターフェイスアクセス技術種別（Interface Access-Technology Type、If-ATT）
この8ビットのフィールドは、モバイルノードが接続しているインターフェイスのアクセス技術種別を識別します。このフィールドに許される値は、[RFC5213]で定義されたAccess Technology Typeレジストリー<https://www.iana.org/assignments/mobility-parameters/>の値です。
インターフェイスラベル（Interface Label、If-Label）

この8ビット符号なし整数は、インターフェイスラベルを表します。

インターフェイスラベルは、MAGのWANインターフェイスに設定される識別子です。PBUメッセージの送信に使われるMAGのすべてのWANインターフェイスには、ラベルが設定されます。ラベルはWANインターフェイスの種類を識別するだけのもので、主にアプリケーションルーティングポリシーで使われます。たとえば、Wi-Fiインターフェイスにはラベル「9」、LTEインターフェイスにはラベル「11」を設定できます。さらに、似た特性を持つ2つのWANインターフェイスに同じラベルを設定することもできます（たとえば、2つのイーサネットインターフェイスに同じラベルを設定する）。

インターフェイスラベルは、PBUメッセージでMAGからLMAに通知されます。LMAとMAGの両方は、動的に作成された各バインディング／トンネルに、関連するラベルを付けることができます。これらのラベルは、LMAとMAGの両方で一貫したアプリケーションルーティングルールを生成するために使われます。たとえば、HTTPパケットをインターフェイスラベル「9」を持つインターフェイス経由でルーティングし、インターフェイスラベル「9」を持つインターフェイスがどれも利用できない場合には、インターフェイスラベル「11」を持つインターフェイス経由でトラフィックをルーティングする必要がある、というポリシーが考えられます。MAGとLMAは、PBUメッセージでインターフェイスラベルを交換し、一致するインターフェイスラベルを持つトンネルにアプリケーションフローを関連付けることで、このルーティングルールを適用できるようになります。

バインディング識別子（Binding Identifier、BID）

この8ビット符号なし整数は、バインディングを識別するために使われます。許される値は1〜254です。値0と255は予約されています。

MAGは、モバイルノードの各バインディングを一意な識別子で識別します。MAGはこの識別子をPBUメッセージに含めます。PBUリクエストがLMAに受け入れられると、結果として得られるバインディングは、モバイルノードのバインディングキャッシュエントリーでこのBIDに関連付けられます。

一括再登録フラグ（Bulk Re-registration Flag、B）
このフラグを値（1）に設定すると、この特定のリクエストを受け入れる際に、これをモバイルノードのすべてのバインディングのバインディングの有効期間を更新するリクエストとして扱うようLMAに通知します。Registration Overwrite（O）フラグの値が（1）に設定されている場合、（B）フラグを値（1）に設定してはなりません（MUST NOT）。
登録上書き（Registration Overwrite、O）
このフラグを値（1）に設定すると、このリクエストを受け入れる際に、モバイルノードの既存のバインディングをすべてこのバインディングで置き換えるようLMAに通知します。Bulk Re-registration Flag（B）の値が（1）に設定されている場合、このフラグを値（1）に設定してはなりません（MUST NOT）。登録解除（De-Registration）リクエストでは、このフラグを値（0）に設定しなければなりません（MUST）。
予約（Reserved）
このフィールドは、この仕様では使用しません。送信者はこの値をゼロ（0）に設定しなければなりません（MUST）。受信者はこの値を無視しなければなりません（MUST）。

4.2. MAG Identifier Option

4.2. MAG Identifierオプション

The MAG Identifier option is a new mobility header option defined for use with PBU and PBA messages exchanged between the LMA and the MAG. This mobility header option is used for conveying the MAG's identity.

MAG Identifierオプションは、LMAとMAGの間で交換されるPBUメッセージとPBAメッセージで使うために定義された、新しいモビリティーヘッダーオプションです。このモビリティーヘッダーオプションは、MAGの識別情報を伝えるために使われます。

This option does not have any alignment requirements.

このオプションには、アラインメントの要件はありません。

Type

Length

Subtype

Reserved

Identifier
A variable-length identifier of the type indicated in the Subtype field.
Type

オプションの長さをオクテット単位で示す8ビット符号なし整数です。TypeフィールドとLengthフィールドは含みません。

4.3. New Status Code for Proxy Binding Acknowledgement

4.3. Proxy Binding Acknowledgementの新しいステータスコード

This document defines the following new Status Code value for use in PBA messages.

この文書は、PBAメッセージで使うための、次の新しいステータスコード（Status Code）の値を定義します。

The LMA SHOULD use this error code when rejecting a PBU message from a MAG requesting a multipath binding. The following is the potential reason for rejecting the request:

LMAは、マルチパスバインディングを要求するMAGからのPBUメッセージを拒否する場合、このエラーコードを使うべきです（SHOULD）。リクエストを拒否する理由として考えられるものは次のとおりです。

  • The LMA does not support multipath binding.
  • LMAがマルチパスバインディングをサポートしていない。

CANNOT_SUPPORT_MULTIPATH_BINDING (Cannot Support Multipath Binding): 180

CANNOT_SUPPORT_MULTIPATH_BINDING（マルチパスバインディングをサポートできない）: 180

4.4. Signaling Considerations

4.4. シグナリングに関する考慮事項

  • The MAG, when requesting multipath support, MUST include the MAG Multipath Binding option (Section 4.1) in each of the PBU messages that it sends through the different WAN interfaces. The inclusion of this option serves as a hint that the MAG is requesting multipath support. Furthermore, the MAG Identifier option MUST also be present in the PBU message.
  • If the MAG is aware that the LMA supports the multipath binding option defined in this specification and if it chooses to use multiple paths, then it can send the PBU packets for each of the paths, either sequentially or concurrently. However, if the MAG is not aware of the LMA capability, then it SHOULD first discover the LMA capability by sending PBU packets with multipath on only one path first. This will ensure that the LMA will not be overwriting the binding of one path with the other path.
  • If the LMA supports multipath capability as defined in this specification and if it enables the same for a mobile node's session per the MAG's request, then the LMA MUST include the Multipath Binding option (Section 4.1) without the MAG-NAI option (Section 4.2) in the corresponding PBA reply.
  • If the LMA is a legacy LMA that does not support this specification, the LMA will skip the MAG Multipath Binding option (and MAG-NAI option) and process the rest of the message as specified in the base PMIPv6 specification ([RFC5213]). Furthermore, the LMA will not include the MAG Multipath Binding option (or the MAG-NAI option) in the PBA message. The MAG, upon receiving the PBA message without the MAG Multipath Binding option, SHOULD disable multipath support for the mobile node.
  • If the mobile node is not authorized for multipath support, then the LMA will reject the request by sending a PBA message with the Status field value set to CANNOT_SUPPORT_MULTIPATH_BINDING (Section 4.3). The LMA MUST echo the MAG Multipath Binding option (without the MAG-NAI option) in the PBA message. The MAG, upon receiving this message, SHOULD disable multipath support for the mobile node.
  • MAGは、マルチパスのサポートを要求する場合、異なるWANインターフェイスを通じて送信する各PBUメッセージに、MAG Multipath Bindingオプション（セクション4.1）を含めなければなりません（MUST）。このオプションが含まれていることは、MAGがマルチパスのサポートを要求していることを示すヒントとなります。さらに、MAG IdentifierオプションもPBUメッセージに存在しなければなりません（MUST）。
  • MAGが、この仕様で定義するマルチパスバインディングオプションをLMAがサポートしていることを知っており、複数の経路を使うことを選んだ場合、MAGは各経路のPBUパケットを順次または同時に送信できます。しかし、MAGがLMAの能力を知らない場合、MAGはまず1つの経路だけでマルチパス付きのPBUパケットを送信して、LMAの能力を最初に発見するべきです（SHOULD）。これにより、LMAがある経路のバインディングを別の経路で上書きしてしまうことがなくなります。
  • LMAがこの仕様で定義するマルチパス能力をサポートしており、MAGのリクエストに従ってモバイルノードのセッションでそれを有効にする場合、LMAは対応するPBA応答に、MAG-NAIオプション（セクション4.2）を含めずにMultipath Bindingオプション（セクション4.1）を含めなければなりません（MUST）。
  • LMAがこの仕様をサポートしないレガシーLMAである場合、LMAはMAG Multipath Bindingオプション（およびMAG-NAIオプション）をスキップし、メッセージの残りの部分を基本のPMIPv6仕様（[RFC5213]）の規定どおりに処理します。さらに、LMAはPBAメッセージにMAG Multipath Bindingオプション（またはMAG-NAIオプション）を含めません。MAGは、MAG Multipath Bindingオプションを含まないPBAメッセージを受信したら、そのモバイルノードのマルチパスのサポートを無効にすべきです（SHOULD）。
  • モバイルノードがマルチパスのサポートを認可されていない場合、LMAは、StatusフィールドをCANNOT_SUPPORT_MULTIPATH_BINDING（セクション4.3）に設定したPBAメッセージを送信して、リクエストを拒否します。LMAは、PBAメッセージでMAG Multipath Bindingオプションを（MAG-NAIオプションを含めずに）エコーしなければなりません（MUST）。MAGは、このメッセージを受信したら、そのモバイルノードのマルチパスのサポートを無効にすべきです（SHOULD）。

6. Security Considerations

6. セキュリティーに関する考慮事項

This specification allows a MAG to establish multiple PMIPv6 tunnels with an LMA by registering a care-of address for each of its connected access networks. This essentially allows the mobile node's IP traffic to be routed through any of the tunnel paths based on the negotiated flow policy. This new capability has no impact on the protocol security. Furthermore, this specification defines two new mobility header options: the MAG Multipath Binding option and the MAG Identifier option. These options are carried like any other mobility header option as specified in [RFC5213]. Therefore, it inherits security guidelines from [RFC5213]. Thus, this specification does not weaken the security of the PMIPv6 Protocol and does not introduce any new security vulnerabilities.

この仕様により、MAGは、接続している各アクセスネットワークについて気付アドレスを登録することで、LMAとの間に複数のPMIPv6トンネルを確立できるようになります。これにより、本質的には、ネゴシエートされたフローポリシーに基づいて、モバイルノードのIPトラフィックを任意のトンネル経路を通じてルーティングできるようになります。この新しい能力は、プロトコルのセキュリティーに影響を与えません。さらに、この仕様は、MAG Multipath BindingオプションとMAG Identifierオプションという2つの新しいモビリティーヘッダーオプションを定義します。これらのオプションは、[RFC5213]で規定されているほかのモビリティーヘッダーオプションと同様に運ばれます。そのため、[RFC5213]のセキュリティーガイドラインを継承します。したがって、この仕様はPMIPv6プロトコルのセキュリティーを弱めることはなく、新しいセキュリティー脆弱性をもたらすこともありません。
