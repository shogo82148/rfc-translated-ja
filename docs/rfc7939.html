RFC 7939

Definition of Managed Objects for the Neighborhood Discovery Protocol

RFC 7939

近隣探索プロトコルの管理オブジェクトの定義

Abstract

概要

This document replaces RFC 6779; it contains revisions and extensions to the original document. It defines a portion of the Management Information Base (MIB) for use with network management protocols in the Internet community. In particular, it describes objects for configuring parameters of the Neighborhood Discovery Protocol (NHDP) process on a router. The extensions described in this document add objects and values to support the NHDP optimization specified in RFC 7466. The MIB module defined in this document, denoted NHDP-MIB, also reports state, performance information, and notifications about NHDP. This additional state and performance information is useful to troubleshoot problems and performance issues during neighbor discovery.

この文書はRFC 6779を置き換えるもので、元の文書に対する改訂と拡張を含みます。この文書は、インターネットコミュニティーのネットワーク管理プロトコルで使用する管理情報ベース（MIB）の一部を定義します。特に、ルーター上の近隣探索プロトコル（Neighborhood Discovery Protocol、NHDP）プロセスのパラメーターを設定するためのオブジェクトを記述します。この文書で記述する拡張は、RFC 7466で規定されたNHDPの最適化をサポートするためのオブジェクトと値を追加します。この文書で定義するMIBモジュールはNHDP-MIBと表記し、NHDPに関する状態、性能情報、通知も報告します。この追加の状態および性能情報は、近隣探索中の問題や性能上の課題のトラブルシューティングに役立ちます。

1. Introduction

1. はじめに

This document defines a portion of the Management Information Base (MIB) for use with network management protocols in the Internet community. In particular, it describes objects for configuring parameters of the Mobile Ad Hoc Network (MANET) Neighborhood Discovery Protocol (NHDP) [RFC6130] process on a router. The MIB module defined in this document, denoted NHDP-MIB, also reports state, performance information, and notifications about NHDP. This additional state and performance information is useful to troubleshoot problems and performance issues during neighbor discovery.

この文書は、インターネットコミュニティーのネットワーク管理プロトコルで使用する管理情報ベース（MIB）の一部を定義します。特に、ルーター上のモバイルアドホックネットワーク（Mobile Ad Hoc Network、MANET）近隣探索プロトコル（NHDP）[RFC6130]プロセスのパラメーターを設定するためのオブジェクトを記述します。この文書で定義するMIBモジュールはNHDP-MIBと表記し、NHDPに関する状態、性能情報、通知も報告します。この追加の状態および性能情報は、近隣探索中の問題や性能上の課題のトラブルシューティングに役立ちます。

1.1. RFC 6779からの変更

この文書は[RFC6779]を廃止し、[RFC6130]のMIBモジュールの仕様として同文書を置き換えます。[RFC6779]に対するこの改訂は、[RFC7466]で規定された[RFC6130]の更新によって必要になったものです。

The MIB module for [RFC6130], specified in this document, captures the new information and states for each symmetric 2-hop neighbor, recorded in the Neighbor Information Base of a router and to be reflected in the appropriate tables, introduced by [RFC7466], specifically:

この文書で規定する[RFC6130]のMIBモジュールは、[RFC7466]で導入された、各対称2ホップ近隣についての新しい情報と状態を取り込みます。これらはルーターの近隣情報ベース（Neighbor Information Base）に記録され、適切なテーブルに反映されるものです。具体的には次のとおりです。

  • Addition of objects nhdpIib2HopSetN2Lost and nhdpIfPerfCounterDiscontinuityTime.

  • オブジェクトnhdpIib2HopSetN2LostとnhdpIfPerfCounterDiscontinuityTimeの追加。
  • nhdp2HopNbrStateへの追加の値（notconsidered）の追加。
  • 完全準拠（full compliance）の記述の改訂。

2. The Internet-Standard Management Framework

2. インターネット標準管理フレームワーク

For a detailed overview of the documents that describe the current Internet-Standard Management Framework, please refer to section 7 of RFC 3410 [RFC3410].

現在のインターネット標準管理フレームワーク（Internet-Standard Management Framework）を記述している文書の詳細な概要については、RFC 3410 [RFC3410]のセクション7を参照してください。

Managed objects are accessed via a virtual information store, termed the Management Information Base or MIB. MIB objects are generally accessed through the Simple Network Management Protocol (SNMP). Objects in the MIB are defined using the mechanisms defined in the Structure of Management Information (SMI). This memo specifies a MIB module that is compliant to the SMIv2, which is described in STD 58, RFC 2578 [RFC2578], STD 58, RFC 2579 [RFC2579] and STD 58, RFC 2580 [RFC2580].

管理オブジェクトには、管理情報ベース（Management Information Base、MIB）と呼ばれる仮想的な情報ストアを介してアクセスします。MIBオブジェクトには、一般にSimple Network Management Protocol（SNMP）を通じてアクセスします。MIB内のオブジェクトは、管理情報構造（Structure of Management Information、SMI）で定義されたメカニズムを使って定義されます。このメモでは、STD 58、RFC 2578 [RFC2578]、STD 58、RFC 2579 [RFC2579]、およびSTD 58、RFC 2580 [RFC2580]で記述されているSMIv2に準拠したMIBモジュールを規定します。

4. Overview

4. 概要

[RFC6130] allows a router to discover and track topological information of routers up to two hops away by virtue of exchanging HELLO messages. This information is useful for routers running various routing and multicast flooding protocols developed within the IETF MANET Working Group.

[RFC6130]は、HELLOメッセージを交換することにより、ルーターが2ホップ先までのルーターのトポロジー情報を発見し、追跡できるようにします。この情報は、IETF MANETワーキンググループで開発されたさまざまなルーティングプロトコルやマルチキャストフラッディングプロトコルを実行するルーターにとって有用です。

4.1. Terms

4.1. 用語

The following definitions apply throughout this document:

この文書全体を通じて、次の定義を適用します。

  • Notification Objects - triggers and associated notification messages allowing for asynchronous tracking of predefined events on the managed router.
  • Configuration Objects - switches, tables, and objects that are initialized to default settings or set through the management interface defined by this MIB module.
  • State Objects - automatically generated values that define the current operating state of the NHDP instance in the router.
  • Performance Objects - automatically generated values that help to assess the performance of the NHDP instance on the router and the overall discovery performance within the MANET.
  • 通知オブジェクト（Notification Objects） - 管理対象のルーター上であらかじめ定義されたイベントを非同期に追跡できるようにするトリガーと、それに関連する通知メッセージ。
  • 設定オブジェクト（Configuration Objects） - デフォルト設定で初期化されるか、このMIBモジュールが定義する管理インターフェイスを通じて設定されるスイッチ、テーブル、オブジェクト。
  • 状態オブジェクト（State Objects） - ルーター内のNHDPインスタンスの現在の動作状態を定義する、自動的に生成される値。
  • 性能オブジェクト（Performance Objects） - ルーター上のNHDPインスタンスの性能と、MANET内の全体的な探索性能の評価に役立つ、自動的に生成される値。

4.2. Notation

4.2. 表記法

The same notations as defined in [RFC6130] are used throughout this document.

この文書全体を通じて、[RFC6130]で定義されているものと同じ表記を使用します。

5. Structure of the MIB Module

5. MIBモジュールの構造

This section presents the structure of the NHDP-MIB module. The MIB module is arranged into the following structure:

このセクションでは、NHDP-MIBモジュールの構造を示します。MIBモジュールは次の構造で構成されています。

  • nhdpNotifications - objects defining NHDP-MIB notifications.

  • nhdpObjects - defining objects within this MIB module. The objects are arranged into the following groups:

    • Configuration Group - defining objects related to the configuration of the NHDP instance on the router.
    • State Group - defining objects that reflect the current state of the NHDP instance running on the router.
    • Performance Group - defining objects that are useful to a management station when characterizing the performance of NHDP on the router and in the MANET.
  • nhdpConformance - defining the minimal and maximal conformance requirements for implementations of this MIB module.
  • nhdpNotifications - NHDP-MIBの通知を定義するオブジェクト。

  • nhdpObjects - このMIBモジュール内のオブジェクトを定義します。オブジェクトは次のグループに分けて構成されています。

    • 設定グループ（Configuration Group） - ルーター上のNHDPインスタンスの設定に関連するオブジェクトを定義します。
    • 状態グループ（State Group） - ルーター上で動作しているNHDPインスタンスの現在の状態を反映するオブジェクトを定義します。
    • 性能グループ（Performance Group） - ルーター上およびMANET内のNHDPの性能を特徴づける際に、管理ステーションにとって有用なオブジェクトを定義します。
  • nhdpConformance - このMIBモジュールの実装に対する最小限および最大限の準拠要件を定義します。

5.1. Notifications

5.1. 通知

This section describes the use of notifications and mechanisms to enhance the ability to manage NHDP routing domains.

このセクションでは、NHDPのルーティングドメインを管理する能力を高めるための、通知の使い方とメカニズムについて説明します。

5.1.1. Introduction

5.1.1. はじめに

Notifications can be emitted by a router running an instance of this specification as a reaction to a specific event. This allows an observer of these events to efficiently determine the source of problems or significant changes of configuration or topology, instead of polling a possibly large number of routers.

この仕様のインスタンスを実行しているルーターは、特定のイベントへの反応として通知を発することができます。これにより、それらのイベントの観測者は、場合によっては多数にのぼるルーターをポーリングする代わりに、問題の発生源や、設定またはトポロジーの重大な変化を効率よく特定できます。

5.1.2. Notification Generation

5.1.2. 通知の生成

When an exception event occurs, the application notifies the local agent, which sends a notification to the appropriate SNMP management stations. The message includes the notification type and may include a list of notification-specific variables. Section 7 contains the notification definitions, which includes the variable lists. At least one IP address of the router that originates the notification is included in the variable list so that the source of the notification may be determined.

例外イベントが発生すると、アプリケーションはローカルエージェントに通知し、ローカルエージェントは適切なSNMP管理ステーションに通知を送信します。メッセージには通知タイプが含まれ、通知固有の変数のリストが含まれる場合もあります。セクション7には、変数リストを含む通知の定義があります。通知の発信元を特定できるように、通知を発信したルーターのIPアドレスが少なくとも1つ、変数リストに含まれます。

5.1.3. Limiting Frequency of Notifications

5.1.3. 通知の頻度の制限

To limit the frequency of notifications, the following additional mechanisms are suggested, similar to those in [RFC4750].

通知の頻度を制限するために、[RFC4750]のものと同様の、次の追加のメカニズムを提案します。

5.1.3.1. Ignoring Initial Activity
5.1.3.1. 初期の活動の無視

The majority of critical events occur when NHDP is first enabled on a router, at which time, the symmetric neighbors and 2-hop neighbors of the router are discovered. During this initial period, a potential flood of notifications is unnecessary since the events are expected. To avoid unnecessary notifications, a router SHOULD NOT originate expected notifications until a predefined and administratively configured time interval has elapsed. It is RECOMMENDED that this time interval be at least 3 times nhdpHelloInterval so that symmetric neighbors are discovered. The suppression window for notifications is started when the nhdpIfStatus transitions from its default value of 'false(2)' to 'true(1)'.

重大なイベントの大部分は、ルーター上でNHDPが最初に有効になったときに発生します。このとき、ルーターの対称近隣と2ホップ近隣が発見されます。この初期期間中は、イベントは想定されたものなので、大量の通知が発生する可能性があっても、それらの通知は不要です。不要な通知を避けるため、ルーターは、あらかじめ定義され管理者によって設定された時間間隔が経過するまで、想定される通知を発信すべきではありません（SHOULD NOT）。対称近隣が発見されるよう、この時間間隔はnhdpHelloIntervalの少なくとも3倍にすることが推奨されます（RECOMMENDED）。通知の抑制ウィンドウは、nhdpIfStatusがデフォルト値の'false(2)'から'true(1)'に遷移したときに開始されます。

5.1.3.2. Throttling Notifications
5.1.3.2. 通知のスロットリング

The mechanism for throttling the notifications is the same as in [RFC4750] (i.e., the number of transmitted notifications per time is bounded).

通知をスロットリングするメカニズムは、[RFC4750]のものと同じです（すなわち、時間あたりに送信される通知の数に上限を設けます）。

Appropriate values for the window time and upper bound are to be administratively configured and depend on the deployment of the MANET. If NHDP is deployed on a lossy, wireless medium, sending too many notifications in a short time interval may lead to collisions and dropped packets. In particular, in dense deployments of routers running NHDP (i.e., where each router has many neighbors), a change of the local topology may trigger many notifications at the same time. [RFC4750] recommends "7 traps with a window time of 10 seconds" as the upper bound. As NHDP is expected to be deployed in more lossy channels than OSPF, it is RECOMMENDED to choose a lower threshold for the number of notifications per time than that. Specifically, it is RECOMMENDED that the threshold value for the objects reflecting the change be set to a value of '10' and the DEFAULT values for these objects within the Notifications Group be set to this value. Further, a time window for the change objects is defined within this MIB module. If the number of occurrences exceeds the change threshold within the previous change window, then it is RECOMMENDED that the notification be sent. Furthermore, it is RECOMMENDED that the value for this window be set to at least 5 times the nhdpHelloInterval.

ウィンドウ時間と上限の適切な値は、管理者によって設定されるもので、MANETの展開形態に依存します。NHDPが損失の多い無線媒体上に展開されている場合、短い時間間隔で過剰な数の通知を送信すると、衝突やパケットの破棄につながる可能性があります。特に、NHDPを実行するルーターが密に展開されている場合（すなわち、各ルーターが多くの近隣を持つ場合）、ローカルトポロジーの変化が同時に多数の通知を引き起こす可能性があります。[RFC4750]は、上限として「ウィンドウ時間10秒あたり7トラップ（7 traps with a window time of 10 seconds）」を推奨しています。NHDPはOSPFよりも損失の多いチャネルで展開されることが想定されるため、時間あたりの通知数のしきい値はそれよりも低く選ぶことが推奨されます（RECOMMENDED）。具体的には、変化を反映するオブジェクトのしきい値を'10'に設定し、通知グループ内のこれらのオブジェクトのDEFAULT値をこの値に設定することが推奨されます（RECOMMENDED）。さらに、変化オブジェクトの時間ウィンドウがこのMIBモジュール内で定義されています。直前の変化ウィンドウ内で発生回数が変化しきい値を超えた場合は、通知を送信することが推奨されます（RECOMMENDED）。さらに、このウィンドウの値はnhdpHelloIntervalの少なくとも5倍に設定することが推奨されます（RECOMMENDED）。

The following objects are used to define the thresholds and time windows for specific notifications defined in the NHDP-MIB module: nhdpNbrStateChangeThreshold, nhdpNbrStateChangeWindow, nhdp2HopNbrStateChangeThreshold, and nhdp2HopNbrStateChangeWindow.

NHDP-MIBモジュールで定義される特定の通知のしきい値と時間ウィンドウを定義するために、次のオブジェクトを使用します: nhdpNbrStateChangeThreshold、nhdpNbrStateChangeWindow、nhdp2HopNbrStateChangeThreshold、nhdp2HopNbrStateChangeWindow。

5.1.3.3. One Notification per Event
5.1.3.3. イベントごとに1つの通知

Similar to the mechanism in [RFC4750], only one notification is sent per event.

[RFC4750]のメカニズムと同様に、1つのイベントにつき1つの通知だけを送信します。

5.2. The Configuration Group

5.2. 設定グループ

The router running NHDP is configured with a set of controls. The authoritative list of configuration controls within the NHDP-MIB module are found within the MIB module itself. Generally, an attempt was made in developing the NHDP-MIB module to support all configuration objects defined in [RFC6130]. For all of the configuration parameters, the same constraints and default values of these parameters as defined in [RFC6130] are followed. Refer to [RFC5148] for guidance on setting jitter-related parameters, e.g., nhdpMaxJitter.

NHDPを実行するルーターは、一連の制御項目によって設定されます。NHDP-MIBモジュール内の設定制御項目の正式な一覧は、MIBモジュール自体の中にあります。一般に、NHDP-MIBモジュールの開発にあたっては、[RFC6130]で定義されているすべての設定オブジェクトをサポートするよう努めました。すべての設定パラメーターについて、[RFC6130]で定義されているものと同じ制約とデフォルト値に従います。ジッター関連のパラメーター（たとえば、nhdpMaxJitter）の設定に関するガイダンスについては、[RFC5148]を参照してください。

5.3. The State Group

5.3. 状態グループ

The State Group reports current state information of a router running NHDP. The NHDP-MIB State Group tables were designed to contain the complete set of state information defined within the information bases specified in Sections 6, 7, and 8 of [RFC6130].

状態グループは、NHDPを実行するルーターの現在の状態情報を報告します。NHDP-MIBの状態グループのテーブルは、[RFC6130]のセクション6、7、8で規定されている情報ベース内で定義された状態情報の完全な集合を含むように設計されています。

Two constructs, i.e., TEXTUAL-CONVENTIONs, are defined to support the tables in the State Group. NHDP stores and indexes information through sets of (dynamically defined) addresses, i.e., address sets. Within SMIv2, it is not possible to index tables with variably defined address sets. Hence, these TEXTUAL-CONVENTIONs are defined to provide a local mapping between NHDP-managed address sets and SMIv2 table indexing. These constructs are the NeighborIfIndex and NeighborRouterIndex. These are locally (to the router) defined, unique identifiers of virtual neighbors and neighbor interfaces. Due to the nature of NHDP, the local router may have identified distinct address sets but is not able to associate these as a single interface. Hence, two or more NeighborIfIndexes pointing to multiple distinct address sets may, in fact, be related to a common neighbor interface. This ambiguity may also hold with respect to the assignment of the NeighborRouterIndex. The local MIB agent is responsible for managing, aggregating, and retiring the defined indexes and for updating MIB tables using these indexes as the local router learns more about its neighbors' topologies. These constructs are used to define indexes to the appropriate State Group tables and to correlate table entries to address sets, virtual neighbor interfaces, and virtual neighbors within the MANET.

状態グループのテーブルをサポートするために、2つの構成要素、すなわちTEXTUAL-CONVENTIONが定義されています。NHDPは、（動的に定義される）アドレスの集合、すなわちアドレスセットを通じて情報を格納し、インデックス付けします。SMIv2では、可変的に定義されるアドレスセットでテーブルをインデックス付けすることはできません。そのため、NHDPが管理するアドレスセットとSMIv2のテーブルのインデックス付けとの間のローカルな対応付けを提供するために、これらのTEXTUAL-CONVENTIONが定義されています。これらの構成要素は、NeighborIfIndexとNeighborRouterIndexです。これらは、仮想的な近隣および近隣インターフェイスの、（ルーターにとって）ローカルに定義された一意な識別子です。NHDPの性質上、ローカルルーターは、別個のアドレスセットを識別していても、それらを単一のインターフェイスとして関連付けられない場合があります。そのため、複数の別個のアドレスセットを指す2つ以上のNeighborIfIndexが、実際には共通の近隣インターフェイスに関係している場合があります。このあいまいさは、NeighborRouterIndexの割り当てについても当てはまる場合があります。ローカルのMIBエージェントは、定義されたインデックスを管理、集約、廃止すること、および、ローカルルーターが近隣のトポロジーについてより多くを学習するにつれて、これらのインデックスを使用するMIBテーブルを更新することに責任を負います。これらの構成要素は、適切な状態グループのテーブルへのインデックスを定義し、テーブルのエントリーを、MANET内のアドレスセット、仮想的な近隣インターフェイス、仮想的な近隣と関連付けるために使用されます。

5.4. The Performance Group

5.4. 性能グループ

The Performance Group reports values relevant to system performance. Unstable neighbors or 2-hop neighbors and frequent changes of sets can have a negative influence on the performance of NHDP. This MIB module defines several objects that can be polled in order to, e.g., calculate histories or monitor frequencies of changes. This may help an observer determining unusual topology changes or other changes that affect stability and reliability of the MANET.

性能グループは、システムの性能に関連する値を報告します。不安定な近隣や2ホップ近隣、および集合の頻繁な変化は、NHDPの性能に悪影響を及ぼす可能性があります。このMIBモジュールは、たとえば履歴を計算したり、変化の頻度を監視したりするためにポーリングできるいくつかのオブジェクトを定義します。これは、観測者が、異常なトポロジーの変化や、MANETの安定性と信頼性に影響するその他の変化を判断するのに役立つ場合があります。

6. 他のMIBモジュールとの関係

This section specifies the relationship of the MIB module contained in this document to other standards, particularly to standards containing other MIB modules. MIB modules and specific definitions imported from MIB modules that SHOULD be implemented in conjunction with the MIB module contained within this document are identified in this section.

このセクションでは、この文書に含まれるMIBモジュールと他の標準、特に他のMIBモジュールを含む標準との関係を規定します。このセクションで示すMIBモジュール、およびMIBモジュールからインポートされる特定の定義は、この文書に含まれるMIBモジュールと合わせて実装されるべきです（SHOULD）。

6.1. Relationship to the SNMPv2-MIB

6.1. SNMPv2-MIBとの関係

The System Group in the SNMPv2-MIB module [RFC3418] is defined as being mandatory for all systems, and the objects apply to the entity as a whole. The System Group provides identification of the management entity and certain other system-wide data. The NHDP-MIB module does not duplicate those objects.

SNMPv2-MIBモジュール[RFC3418]のシステムグループ（System Group）は、すべてのシステムで必須であると定義されており、そのオブジェクトはエンティティー全体に適用されます。システムグループは、管理エンティティーの識別情報と、その他のシステム全体にわたる特定のデータを提供します。NHDP-MIBモジュールは、それらのオブジェクトを重複して定義しません。

6.2. Relationship to Routing Protocol MIB Modules Relying on the NHDP-MIB Module

6.2. NHDP-MIBモジュールに依存するルーティングプロトコルMIBモジュールとの関係

[RFC6130] allows routing protocols to rely on the neighborhood information that is discovered by means of HELLO message exchange. In order to allow for troubleshooting, fault isolation, and management of such routing protocols through a routing protocol MIB module, it may be desired to align the State Group tables of the NHDP-MIB module and the routing protocol MIB module. This is accomplished through the definition of two TEXTUAL-CONVENTIONs in the NHDP-MIB module: the NeighborIfIndex and the NeighborRouterIndex. These object types are used to develop indexes into common NHDP-MIB module and routing protocol State Group tables. These objects are locally significant but should be locally common to the NHDP-MIB module and the routing protocol MIB module implemented on a common networked router. This will allow for improved cross-referencing of information across the two MIB modules.

[RFC6130]は、ルーティングプロトコルが、HELLOメッセージの交換によって発見された近隣情報に依存できるようにします。そのようなルーティングプロトコルのトラブルシューティング、障害の切り分け、管理をルーティングプロトコルMIBモジュールを通じて行えるようにするため、NHDP-MIBモジュールとルーティングプロトコルMIBモジュールの状態グループのテーブルをそろえることが望まれる場合があります。これは、NHDP-MIBモジュールで2つのTEXTUAL-CONVENTION、すなわちNeighborIfIndexとNeighborRouterIndexを定義することで実現されます。これらのオブジェクトタイプは、NHDP-MIBモジュールとルーティングプロトコルに共通の状態グループのテーブルへのインデックスを作成するために使用されます。これらのオブジェクトはローカルにのみ意味を持ちますが、共通のネットワーク接続されたルーター上に実装されたNHDP-MIBモジュールとルーティングプロトコルMIBモジュールとの間では、ローカルに共通であるべきです。これにより、2つのMIBモジュールにまたがる情報の相互参照が改善されます。

6.3. Relationship to the If-MIB

6.3. If-MIBとの関係

The nhdpInterfaceTable in this MIB module describes the configuration of the interfaces of this router that are intended to use MANET control protocols. As such, this table 'sparse augments' the ifTable [RFC2863] specifically when NHDP is to be configured to operate over this interface. The interface is identified by the ifIndex from the Interfaces Group defined in the Interfaces Group MIB module [RFC2863].

このMIBモジュールのnhdpInterfaceTableは、MANETの制御プロトコルを使用することを意図した、このルーターのインターフェイスの設定を記述します。そのため、このテーブルは、特にNHDPがこのインターフェイス上で動作するように設定される場合に、ifTable [RFC2863]を「疎に拡張（sparse augments）」します。インターフェイスは、インターフェイスグループMIBモジュール[RFC2863]で定義されたインターフェイスグループのifIndexによって識別されます。

A conceptual row in the nhdpInterfaceTable exists if and only if either the row has been administratively created or there is an interface on the managed device that supports and runs NHDP. This implies that for each entry in the nhdpInterfaceTable, there is a corresponding entry in the Interface Table where nhdpIfIndex and ifIndex are equal. If that corresponding entry in the Interface Table is deleted, then the entry in nhdpInterfaceTable is automatically deleted, NHDP is disabled on this interface, and all configuration and state information related to this interface is to be removed from memory.

nhdpInterfaceTableの概念的な行は、その行が管理者によって作成された場合、または管理対象デバイス上にNHDPをサポートし実行しているインターフェイスがある場合に限り、存在します。これは、nhdpInterfaceTableの各エントリーについて、nhdpIfIndexとifIndexが等しい、対応するエントリーがインターフェイステーブル（Interface Table）に存在することを意味します。インターフェイステーブル内の対応するエントリーが削除された場合、nhdpInterfaceTable内のエントリーは自動的に削除され、このインターフェイス上のNHDPは無効になり、このインターフェイスに関連するすべての設定と状態情報はメモリーから削除されます。

--
-- TEXTUAL-CONVENTIONs
--
   -- 以下のテーブルへのインデックス付けと、他のMIBモジュール内の
   -- 他のテーブルへのインデックス付けのために、このMIBモジュールでは
   -- 2つの新しいTEXTUAL-CONVENTIONを定義しています。これが必要
   -- だったのは、NHDPは動的なアドレスのタプル、すなわちアドレス
   -- セットに基づいて管理とインデックス付けを行う一方、SMIは
   -- テーブルの行にアクセスするために静的に定義されたインデックスを
   -- 必要とするためです。NeighborIfIndexは、MANET内の別の近隣上の
   -- 発見された仮想インターフェイスを参照する、（ローカルルーターに
   -- とって）一意なインデックスを定義します。NeighborRouterIndexは、
   -- MANET内の発見された仮想近隣を参照する、（ローカルルーターに
   -- とって）一意なインデックスを定義します。
   --
   -- NHDPの性質上、異なるインデックスが共通の近隣インターフェイスや
   -- 共通の近隣ルーターに関係している場合がありますが、NHDPを通じて
   -- 得られた情報では、その時点ではローカルルーターがこれらの仮想
   -- オブジェクト（すなわち、インターフェイスやルーター）を関連付ける
   -- ことができません。ローカルルーターがより多くのトポロジー情報を
   -- 収集するにつれて、仮想インターフェイスや仮想ルーターを関連付け、
   -- これらのインデックスを適切にまとめる場合があります。

   -- 1つのNeighborIfIndexには複数のアドレスを関連付けることが
   -- できます。各NeighborIfIndexは、1つのNeighborRouterIndexに
   -- 関連付けられます。nhdpStateObjGroup全体を通じて、
   -- NeighborIfIndexとNeighborRouterIndexは、対象となる仮想近隣
   -- インターフェイスまたは仮想近隣に関連するIPアドレスの集合を
   -- 定義するために使用されます。


NeighborIfIndex ::= TEXTUAL-CONVENTION
   DISPLAY-HINT "d"
   STATUS       current
   DESCRIPTION
      "An arbitrary, locally unique identifier associated with a
       virtual interface of a discovered NHDP neighbor.
       Due to the nature of NHDP, the local router
       may not know if two distinct addresses belong to the
       same interface of a neighbor or to two different
       interfaces.  As the local router gains more
       knowledge of its neighbors, its local view may change, and
       this table will be updated to reflect the local router's
       current understanding, associating address sets to neighbor
       interfaces.  The local router identifies a virtual neighbor
       interface through the receipt of address lists advertised
       through an NHDP HELLO message.

       All objects of type NeighborIfIndex are assigned by the agent
       out of a common number space.

       The value for each discovered virtual neighbor
       interface may not remain constant from
       one re-initialization of the entity's network management
       agent to the next re-initialization.  If the
       local router gains information associating two virtual
       interfaces on a neighbor as a common interface,
       then the agent MUST aggregate the two address sets to
       a single index chosen from the set of aggregated indexes,
       and it MUST update all tables in this
       MIB module that are indexed by indexes
       of type NeighborIfIndex.  It MAY then reuse freed
       index values following the next agent restart.

       The specific value is meaningful only within a given SNMP
       entity."
    SYNTAX       Unsigned32 (1..2147483647)

NeighborRouterIndex ::= TEXTUAL-CONVENTION
   DISPLAY-HINT "d"
   STATUS       current
   DESCRIPTION
      "An arbitrary, locally unique identifier associated with a
       virtual discovered neighbor (one or two hop).  Due to the
       nature of NHDP, the local router may identify
       multiple virtual neighbors that, in fact, are one and
       the same.  Neighbors that are two hops away with more than
       one advertised address will exhibit this behavior.  As the
       local router's knowledge of its neighbors' topology
       increases, the local router will be able to associate
       multiple virtual neighbor indexes into a single virtual
       neighbor index chosen from the set of aggregated indexes;
       it MUST update all tables in this MIB module indexed by these
       indexes, and it MAY reuse the freed indexes following the
       next agent re-initialization.

       All objects of type NeighborRouterIndex are assigned by
       the agent out of a common number space.

       The NeighborRouterIndex defines a discovered NHDP peer
       virtual neighbor of the local router.
       The value for each discovered virtual neighbor index MUST
       remain constant at least from one re-initialization of
       the entity's network management agent to the next
       re-initialization, except if an application is deleted
       and re-created.

       The specific value is meaningful only within a given SNMP
       entity.  A NeighborRouterIndex value MUST NOT be reused
       until the next agent restart."
    SYNTAX       Unsigned32 (1..2147483647)

8. Security Considerations

8. セキュリティーに関する考慮事項

This MIB module defines objects for the configuration, monitoring, and notification of the Mobile Ad Hoc Network (MANET) Neighborhood Discovery Protocol (NHDP) [RFC6130]. NHDP allows routers to acquire topological information up to two hops away by virtue of exchanging HELLO messages. The information acquired by NHDP may be used by routing protocols. The neighborhood information, exchanged between routers using NHDP, serves these routing protocols as a baseline for calculating paths to all destinations in the MANET, relay set selection for network-wide transmissions, etc.

このMIBモジュールは、モバイルアドホックネットワーク（MANET）近隣探索プロトコル（NHDP）[RFC6130]の設定、監視、通知のためのオブジェクトを定義します。NHDPは、HELLOメッセージを交換することにより、ルーターが2ホップ先までのトポロジー情報を取得できるようにします。NHDPによって取得された情報は、ルーティングプロトコルによって使用される場合があります。NHDPを使用してルーター間で交換される近隣情報は、これらのルーティングプロトコルにとって、MANET内のすべての宛先へのパスの計算や、ネットワーク全体にわたる送信のための中継セットの選択などの基盤となります。

There are a number of management objects defined in this MIB module with a MAX-ACCESS clause of read-write and/or read-create. Such objects may be considered sensitive or vulnerable in some network environments. The support for SET operations in a non-secure environment without proper protection opens devices to attack. These are the tables and objects and their sensitivity/vulnerability:

このMIBモジュールには、MAX-ACCESS句がread-writeまたはread-create（あるいはその両方）である管理オブジェクトが多数定義されています。そのようなオブジェクトは、ネットワーク環境によっては機密である、または脆弱であるとみなされる場合があります。適切な保護のない安全でない環境でSET操作をサポートすると、デバイスが攻撃にさらされます。以下に、これらのテーブルとオブジェクト、およびその機密性・脆弱性を示します。

  • nhdpIfStatus - This writable object turns on or off the NHDP process for the specified interface. If disabled, higher-level protocol functions, e.g., routing, would fail, causing network-wide disruptions.
  • nhdpHelloInterval, nhdpHelloMinInterval, and nhdpRefreshInterval - These writable objects control the rate at which HELLO messages are sent on an interface. If set at too high a rate, this could represent a form of denial-of-service (DoS) attack by overloading interface resources.
  • nhdpHystAcceptQuality, nhdpHystRejectQuality, nhdpInitialQuality, and nhdpInitialPending - These writable objects affect the perceived quality of the NHDP links and hence the overall stability of the network. If improperly set, these settings could result in network-wide disruptions.
  • nhdpInterfaceTable - This table contains writable objects that affect the overall performance and stability of the NHDP process. Failure of the NHDP process would result in network-wide failure. Particularly sensitive objects from this table are discussed in the previous list items. This is the only table in the NHDP-MIB module with writable objects.
  • nhdpIfStatus - この書き込み可能なオブジェクトは、指定されたインターフェイスのNHDPプロセスをオンまたはオフにします。無効にすると、ルーティングなどの上位層のプロトコル機能が失敗し、ネットワーク全体にわたる混乱を引き起こします。
  • nhdpHelloInterval、nhdpHelloMinInterval、nhdpRefreshInterval - これらの書き込み可能なオブジェクトは、インターフェイス上でHELLOメッセージを送信するレートを制御します。レートが高すぎる値に設定されると、インターフェイスのリソースを過負荷にすることによる、一種のサービス拒否（DoS）攻撃となる可能性があります。
  • nhdpHystAcceptQuality、nhdpHystRejectQuality、nhdpInitialQuality、nhdpInitialPending - これらの書き込み可能なオブジェクトは、NHDPリンクの認識される品質に影響し、したがってネットワーク全体の安定性に影響します。不適切に設定されると、これらの設定はネットワーク全体にわたる混乱を招く可能性があります。
  • nhdpInterfaceTable - このテーブルには、NHDPプロセスの全体的な性能と安定性に影響する書き込み可能なオブジェクトが含まれています。NHDPプロセスが失敗すると、ネットワーク全体の障害につながります。このテーブルの中で特に機密性の高いオブジェクトについては、前の各項目で説明しています。これは、NHDP-MIBモジュールの中で書き込み可能なオブジェクトを持つ唯一のテーブルです。

Some of the readable objects in this MIB module (i.e., objects with a MAX-ACCESS other than not-accessible) may be considered sensitive or vulnerable in some network environments. It is thus important to control even GET and/or NOTIFY access to these objects and possibly to even encrypt the values of these objects when sending them over the network via SNMP. These are the tables and objects and their sensitivity/vulnerability:

このMIBモジュールの読み取り可能なオブジェクト（すなわち、MAX-ACCESSがnot-accessible以外のオブジェクト）の一部は、ネットワーク環境によっては機密である、または脆弱であるとみなされる場合があります。したがって、これらのオブジェクトへのGETアクセスやNOTIFYアクセスさえも制御し、場合によってはSNMPを介してネットワーク上で送信する際にこれらのオブジェクトの値を暗号化することさえ重要です。以下に、これらのテーブルとオブジェクト、およびその機密性・脆弱性を示します。

  • nhdpDiscIfSetTable - The object contains information on discovered neighbors, specifically their IP address in the nhdpDiscIfSetIpAddr object. This information provides an adversary broad information on the members of the MANET, located within this single table. This information can be used to expedite attacks on the other members of the MANET without having to go through a laborious discovery process on their own. This object is the index into the table and has a MAX-ACCESS of 'not-accessible'. However, this information can be exposed using SNMP operations.
  • nhdpDiscIfSetTable - このオブジェクトには、発見された近隣に関する情報、具体的にはnhdpDiscIfSetIpAddrオブジェクト内のそれらのIPアドレスが含まれています。この情報は、この単一のテーブルの中で、MANETのメンバーに関する広範な情報を攻撃者に提供します。この情報を使用すると、攻撃者は自ら手間のかかる探索プロセスを経ることなく、MANETの他のメンバーへの攻撃を迅速に進めることができます。このオブジェクトはテーブルへのインデックスであり、MAX-ACCESSは'not-accessible'です。しかし、この情報はSNMP操作を使用して公開される可能性があります。

MANET technology is often deployed to support communications of emergency services or military tactical applications. In these applications, it is imperative to maintain the proper operation of the communications network and to protect sensitive information related to its operation. Therefore, it is RECOMMENDED to provide support for the Transport Security Model (TSM) [RFC5591] in combination with TLS/DTLS [RFC6353].

MANET技術は、緊急サービスや軍事戦術アプリケーションの通信をサポートするために展開されることがよくあります。これらのアプリケーションでは、通信ネットワークの適切な動作を維持し、その運用に関連する機密情報を保護することが不可欠です。したがって、Transport Security Model（TSM）[RFC5591]とTLS/DTLS [RFC6353]を組み合わせたサポートを提供することが推奨されます（RECOMMENDED）。

SNMP versions prior to SNMPv3 did not include adequate security. Even if the network itself is secure (for example by using IPsec), there is no control as to who on the secure network is allowed to access and GET/SET (read/change/create/delete) the objects in this MIB module.

SNMPv3より前のSNMPのバージョンには、十分なセキュリティーが含まれていませんでした。ネットワーク自体が安全であっても（たとえば、IPsecを使用している場合でも）、安全なネットワーク上の誰がこのMIBモジュールのオブジェクトにアクセスしてGET/SET（読み取り／変更／作成／削除）することを許可されるかについては、何の制御もありません。

Implementations SHOULD provide the security features described by the SNMPv3 framework (see [RFC3410]), and implementations claiming compliance to the SNMPv3 standard MUST include full support for authentication and privacy via the User-based Security Model (USM) [RFC3414] with the AES cipher algorithm [RFC3826]. Implementations MAY also provide support for the Transport Security Model (TSM) [RFC5591] in combination with a secure transport such as SSH [RFC5592] or TLS/DTLS [RFC6353].

実装は、SNMPv3フレームワーク（[RFC3410]を参照）で記述されているセキュリティー機能を提供すべきです（SHOULD）。また、SNMPv3標準への準拠を主張する実装は、AES暗号アルゴリズム[RFC3826]を用いたユーザーベースセキュリティーモデル（USM）[RFC3414]による認証とプライバシーを完全にサポートしなければなりません（MUST）。実装は、SSH [RFC5592]やTLS/DTLS [RFC6353]などの安全なトランスポートと組み合わせたTransport Security Model（TSM）[RFC5591]のサポートを提供してもよいです（MAY）。

Further, deployment of SNMP versions prior to SNMPv3 is NOT RECOMMENDED. Instead, it is RECOMMENDED to deploy SNMPv3 and to enable cryptographic security. It is then a customer/operator responsibility to ensure that the SNMP entity giving access to an instance of this MIB module is properly configured to give access to the objects only to those principals (users) that have legitimate rights to indeed GET or SET (change/create/delete) them.

さらに、SNMPv3より前のバージョンのSNMPを展開することは推奨されません（NOT RECOMMENDED）。代わりに、SNMPv3を展開し、暗号によるセキュリティーを有効にすることが推奨されます（RECOMMENDED）。そのうえで、このMIBモジュールのインスタンスへのアクセスを提供するSNMPエンティティーが、オブジェクトを実際にGETまたはSET（変更／作成／削除）する正当な権利を持つプリンシパル（ユーザー）にのみオブジェクトへのアクセスを許可するように適切に設定されていることを確認するのは、顧客／運用者の責任です。

9. Applicability Statement

9. 適用性に関する記述

This document describes objects for configuring parameters of the Mobile Ad Hoc Network (MANET) Neighborhood Discovery Protocol (NHDP) [RFC6130] process on a router. This MIB module, denoted NHDP-MIB, also reports state, performance information, and notifications. This section provides some examples of how this MIB module can be used in MANET network deployments.

この文書は、ルーター上のモバイルアドホックネットワーク（MANET）近隣探索プロトコル（NHDP）[RFC6130]プロセスのパラメーターを設定するためのオブジェクトを記述します。このMIBモジュールはNHDP-MIBと表記し、状態、性能情報、通知も報告します。このセクションでは、MANETネットワークの展開においてこのMIBモジュールをどのように使用できるかの例をいくつか示します。

NHDP is designed to allow routers to automatically discover and track routers one hop remote (denoted "neighbors") and routers two hops remote (denoted "2-hop neighbors"). This information is used by other MANET protocols in operation on the router to perform routing, multicast forwarding, and other functions with ad hoc and mobile networks. In the following, three example scenarios are listed where this MIB module is useful:

NHDPは、ルーターが1ホップ先のルーター（「近隣（neighbors）」と表記）と2ホップ先のルーター（「2ホップ近隣（2-hop neighbors）」と表記）を自動的に発見し、追跡できるように設計されています。この情報は、ルーター上で動作している他のMANETプロトコルが、アドホックネットワークやモバイルネットワークでルーティング、マルチキャスト転送、その他の機能を実行するために使用されます。以下に、このMIBモジュールが役立つ3つのシナリオの例を挙げます。

  • For a Parking Lot Initial Configuration Situation - It is common for the vehicles comprising the MANET being forward deployed at a remote location, e.g., the site of a natural disaster, to be off-loaded in a parking lot where an initial configuration of the networking devices is performed. The configuration is loaded into the devices from a fixed location Network Operations Center (NOC) at the parking lot, and the vehicles are stationary at the parking lot while the configuration changes are made. Standards-based methods for configuration management from the co-located NOC are necessary for this deployment option.
  • For Mobile Vehicles with Low-Bandwidth Satellite Link to a Fixed NOC - Here, the vehicles carrying the MANET routers carry multiple wireless interfaces, one of which is a relatively low-bandwidth, on-the-move satellite connection that interconnects a fix NOC to the nodes of the MANET. Standards-based methods for monitoring and fault management from the fixed NOC are necessary for this deployment option.
  • For Fixed NOC and Mobile Local Manager in Larger Vehicles - for larger vehicles, a hierarchical network management arrangement is useful. Centralized network management is performed from a fixed NOC while local management is performed locally from within the vehicles. Standards-based methods for configuration, monitoring, and fault management are necessary for this deployment option.
  • 駐車場での初期設定の状況 - 遠隔地（たとえば、自然災害の現場）に前方展開されるMANETを構成する車両は、駐車場で荷降ろしされ、そこでネットワーク機器の初期設定が行われることがよくあります。設定は、駐車場にある固定位置のネットワークオペレーションセンター（Network Operations Center、NOC）から機器に読み込まれ、設定の変更が行われる間、車両は駐車場で停止しています。この展開形態では、同じ場所にあるNOCからの、標準に基づく設定管理の方法が必要です。
  • 固定のNOCへの低帯域幅の衛星リンクを持つ移動車両 - この場合、MANETのルーターを搭載した車両は複数の無線インターフェイスを搭載しており、そのうちの1つは、固定のNOCとMANETのノードとを相互接続する、比較的低帯域幅の移動中の衛星接続です。この展開形態では、固定のNOCからの、標準に基づく監視と障害管理の方法が必要です。
  • 大型車両における固定のNOCと移動するローカルマネージャー - 大型車両では、階層的なネットワーク管理の構成が役立ちます。集中的なネットワーク管理は固定のNOCから行われ、ローカルな管理は車両内からローカルに行われます。この展開形態では、標準に基づく設定、監視、障害管理の方法が必要です。
