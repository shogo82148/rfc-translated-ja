RFC 7890

Concepts and Terminology for Peer-to-Peer SIP (P2PSIP)

RFC 7890

ピアツーピアSIP（P2PSIP）の概念と用語

Abstract

概要

This document defines concepts and terminology for using the Session Initiation Protocol in a peer-to-peer environment where the traditional proxy-registrar and message-routing functions are replaced by a distributed mechanism. These mechanisms may be implemented using a Distributed Hash Table or other distributed data mechanism with similar external properties. This document includes a high-level view of the functional relationships between the network elements defined herein, a conceptual model of operations, and an outline of the related problems addressed by the P2PSIP working group, the REsource LOcation And Discovery (RELOAD) protocol, and the SIP usage document defined by the working group.

この文書は、従来のプロキシー・レジストラーの機能とメッセージルーティングの機能を分散メカニズムで置き換えたピアツーピア環境でセッション開始プロトコル（Session Initiation Protocol）を使用するための概念と用語を定義します。これらのメカニズムは、分散ハッシュテーブル（Distributed Hash Table）や、外から見て同様の性質を持つ他の分散データメカニズムを使用して実装できます。この文書には、ここで定義するネットワーク要素間の機能的な関係の大まかな見取り図、動作の概念モデル、そしてP2PSIPワーキンググループ、REsource LOcation And Discovery（RELOAD）プロトコル、およびワーキンググループが定義したSIPの用法の文書が取り組んでいる関連する問題の概要が含まれます。

1. Background

1. 背景

One of the fundamental problems in multimedia communication between Internet nodes is the rendezvous problem, or discovering the host at which a given user can be reached. In the Session Initiation Protocol (SIP) [RFC3261], this problem is expressed as the problem of mapping an Address of Record (AoR) for a user into one or more Contact URIs [RFC3986]. The AoR is a name for the user that is independent of the host or hosts where the user can be contacted, while a Contact URI indicates the host where the user can be contacted.

インターネットのノード間のマルチメディア通信における根本的な問題の1つは、ランデブー問題、つまり特定のユーザーに到達できるホストを発見する問題です。セッション開始プロトコル（Session Initiation Protocol、SIP）[RFC3261]では、この問題は、ユーザーのアドレスオブレコード（Address of Record、AoR）を1つ以上のコンタクトURI（Contact URI）[RFC3986]に対応付ける問題として表されます。AoRは、ユーザーに連絡できるホストとは無関係なユーザーの名前であり、一方コンタクトURIは、ユーザーに連絡できるホストを示します。

In the common SIP-using architectures that we refer to as "Conventional SIP" or "Client/Server SIP", there is a relatively fixed hierarchy of SIP routing proxies and SIP user agents. To deliver a SIP INVITE to the host or hosts at which the user can be contacted, a SIP UA follows the procedures specified in [RFC3263] to determine the IP address of a SIP proxy, and then sends the INVITE to that proxy. The proxy will then, in turn, deliver the SIP INVITE to the hosts where the user can be contacted.

私たちが「従来型SIP（Conventional SIP）」または「クライアント/サーバー型SIP（Client/Server SIP）」と呼ぶ、SIPを使用する一般的なアーキテクチャーでは、SIPルーティングプロキシーとSIPユーザーエージェントの比較的固定された階層があります。ユーザーに連絡できるホストにSIP INVITEを配送するために、SIP UAは[RFC3263]で規定された手順に従ってSIPプロキシーのIPアドレスを決定し、そのプロキシーにINVITEを送信します。次に、そのプロキシーが、ユーザーに連絡できるホストにSIP INVITEを配送します。

This document gives a high-level description of an alternative solution to this problem. In this alternative solution, the relatively fixed hierarchy of Client/Server SIP is replaced by a peer-to-peer overlay network. In this peer-to-peer overlay network, the various mappings of AoRs to Contact URIs are not centralized at proxy/registrar nodes but are instead distributed amongst the peers in the overlay.

この文書は、この問題に対する代替の解決策を大まかに説明します。この代替の解決策では、クライアント/サーバー型SIPの比較的固定された階層が、ピアツーピアのオーバーレイネットワークに置き換えられます。このピアツーピアのオーバーレイネットワークでは、AoRからコンタクトURIへのさまざまな対応付けは、プロキシー/レジストラーのノードに集中するのではなく、オーバーレイ内のピアの間に分散されます。

The details of this alternative solution are specified by the RELOAD protocol [RFC6940], which defines a mechanism for distribution using a Distributed Hash Table (DHT) and specifies the wire protocol, security, and authentication mechanisms needed to convey this information. This DHT protocol was designed specifically with the purpose of enabling a distributed SIP registrar in mind. While designing the protocol, other applications were considered, and then design decisions were made that allow RELOAD to be used in other instances where a DHT is desirable, but only when such decisions did not add undue complexity to the RELOAD protocol. The RELOAD SIP document [P2PSIP] specifies how RELOAD is used with the SIP protocol to enable a distributed, server-less SIP solution.

この代替の解決策の詳細は、RELOADプロトコル[RFC6940]で規定されています。RELOADプロトコルは、分散ハッシュテーブル（Distributed Hash Table、DHT）を使用した分散のメカニズムを定義し、この情報を伝達するのに必要なワイヤープロトコル、セキュリティー、認証のメカニズムを規定しています。このDHTプロトコルは、特に分散SIPレジストラーを可能にする目的を念頭に置いて設計されました。プロトコルの設計中には他のアプリケーションも検討され、DHTが望ましい他の場面でもRELOADを使用できるような設計上の決定がなされました。ただし、それはそのような決定がRELOADプロトコルに過度の複雑さを加えない場合に限られました。RELOAD SIP文書[P2PSIP]は、サーバーを使用しない分散型のSIPの解決策を実現するために、RELOADをSIPプロトコルとともにどのように使用するかを規定しています。

2. High-Level Description

2. 概要

A Peer-to-Peer SIP (P2PSIP) Overlay is a collection of nodes organized in a peer-to-peer fashion for the purpose of enabling real-time communication using the Session Initiation Protocol (SIP). Collectively, the nodes in the Overlay provide a distributed mechanism for mapping names to Overlay locations. This provides for the mapping of Addresses of Record (AoRs) to Contact URIs, thereby providing the "location server" function of [RFC3261]. An Overlay also provides a transport function by which SIP messages can be transported between any two nodes in the Overlay.

ピアツーピアSIP（Peer-to-Peer SIP、P2PSIP）オーバーレイは、セッション開始プロトコル（SIP）を使用したリアルタイム通信を可能にする目的で、ピアツーピア方式で組織されたノードの集まりです。オーバーレイ内のノードは全体として、名前をオーバーレイ内の位置に対応付けるための分散メカニズムを提供します。これにより、アドレスオブレコード（AoR）からコンタクトURIへの対応付けが提供され、それによって[RFC3261]の「ロケーションサーバー（location server）」の機能が提供されます。オーバーレイは、オーバーレイ内の任意の2つのノード間でSIPメッセージを転送できるトランスポート機能も提供します。

A P2PSIP Overlay consists of one or more nodes called "Peers". The nodes in the Overlay collectively run a distributed database algorithm. This distributed database algorithm allows data to be stored on nodes and retrieved in an efficient manner. It may also ensure that a copy of a data item is stored on more than one node, so that the loss of a node does not result in the loss of the data item to the Overlay.

P2PSIPオーバーレイは、「ピア（Peer）」と呼ばれる1つ以上のノードで構成されます。オーバーレイ内のノードは全体として、分散データベースアルゴリズムを実行します。この分散データベースアルゴリズムにより、データをノードに保存し、効率的に取得できます。また、このアルゴリズムは、データ項目のコピーが複数のノードに保存されることを保証して、1つのノードが失われてもオーバーレイからそのデータ項目が失われないようにする場合もあります。

One use of this distributed database is to store the information required to provide the mapping between AoRs and Contact URIs for the distributed location function. This provides a location function within each Overlay that is an alternative to the location functions described in [RFC3263]. However, the model of [RFC3263] is used between Overlays.

この分散データベースの用途の1つは、分散ロケーション機能のために、AoRとコンタクトURIの対応付けを提供するのに必要な情報を保存することです。これにより、[RFC3263]で説明されているロケーション機能の代わりとなるロケーション機能が、各オーバーレイ内で提供されます。ただし、オーバーレイ間では[RFC3263]のモデルが使用されます。

2.1. Services

2.1. サービス

The nature of peer-to-peer computing is that each peer offers services to other peers to allow the overlay to collectively provide larger functions. In P2PSIP, Peers offer both distributed storage and distributed message-routing services, allowing these functions to be implemented across the Overlay. Additionally, the RELOAD protocol offers a simplistic discovery mechanism specific to the Traversal Using Relays around NAT (TURN) [RFC5766] protocol used for NAT traversal. Individual Peers may also offer other services as an enhancement to P2PSIP functionality (for example, to support voicemail) or to support other applications beyond SIP. To support these additional services, Peers may need to store additional information in the Overlay. [RFC7374] describes the mechanism used in P2PSIP for resource discovery.

ピアツーピアコンピューティングの本質は、各ピアが他のピアにサービスを提供し、オーバーレイが全体としてより大きな機能を提供できるようにすることです。P2PSIPでは、ピアは分散ストレージと分散メッセージルーティングの両方のサービスを提供し、これらの機能をオーバーレイ全体にわたって実装できるようにします。さらに、RELOADプロトコルは、NAT越えに使用されるTraversal Using Relays around NAT（TURN）[RFC5766]プロトコルに特化した単純な発見メカニズムを提供します。個々のピアは、P2PSIPの機能の強化として（たとえば、ボイスメールをサポートするために）、あるいはSIP以外の他のアプリケーションをサポートするために、他のサービスを提供することもあります。これらの追加のサービスをサポートするために、ピアはオーバーレイに追加の情報を保存する必要があるかもしれません。[RFC7374]は、P2PSIPでリソースの発見に使用されるメカニズムを説明しています。

2.2. Clients

2.2. クライアント

An Overlay may or may not also include one or more nodes called "Clients". Clients are supported in the RELOAD protocol as peers that have not joined the Overlay, and therefore do not route messages or store information. Clients access the services of the RELOAD protocol by connecting to a Peer that performs operations on the behalf of the Client. Note that in RELOAD, there is no distinct client protocol. Instead, a Client connects using the same protocol, but never joins the Overlay as a Peer. For more information, see [RFC6940].

オーバーレイには、「クライアント（Client）」と呼ばれる1つ以上のノードが含まれる場合も含まれない場合もあります。RELOADプロトコルでは、クライアントはオーバーレイに参加していないピアとしてサポートされるため、メッセージのルーティングや情報の保存は行いません。クライアントは、クライアントに代わって操作を行うピアに接続することで、RELOADプロトコルのサービスにアクセスします。RELOADには独立したクライアントプロトコルがないことに注意してください。代わりに、クライアントは同じプロトコルを使用して接続しますが、ピアとしてオーバーレイに参加することはありません。詳細については[RFC6940]を参照してください。

A special Peer may also be a member of the P2PSIP Overlay and may present the functionality of one or all of a SIP registrar, proxy, or redirect server to conventional SIP devices (i.e., unmodified SIP user agent (UA) or client). In this way, existing, unmodified SIP clients may connect to the P2PSIP network. Note that in the context of P2PSIP, the unmodified SIP client is also sometimes referred to as a "client". These unmodified SIP devices do not speak the RELOAD protocol, and this is a distinct concept from the notion of "Client" discussed in the previous paragraph.

特別なピアがP2PSIPオーバーレイのメンバーとなり、従来のSIPデバイス（つまり、未改変のSIPユーザーエージェント（UA）またはクライアント）に対して、SIPのレジストラー、プロキシー、リダイレクトサーバーのいずれか、またはすべての機能を提供することもあります。このようにして、既存の未改変のSIPクライアントはP2PSIPネットワークに接続できます。P2PSIPの文脈では、未改変のSIPクライアントも「クライアント（client）」と呼ばれる場合があることに注意してください。これらの未改変のSIPデバイスはRELOADプロトコルを話さず、これは前の段落で説明した「クライアント（Client）」の概念とは別の概念です。

2.3. Relationship between P2PSIP and RELOAD

2.3. P2PSIPとRELOADの関係

The RELOAD protocol defined by the P2PSIP working group implements a DHT primarily for use by server-less, peer-to-peer SIP deployments. However, the RELOAD protocol could be used for other applications as well. As such, a "P2PSIP" deployment is generally assumed to be a use of RELOAD to implement distributed SIP, but it is possible that RELOAD is used as a mechanism to distribute other applications, completely unrelated to SIP.

P2PSIPワーキンググループが定義したRELOADプロトコルは、主にサーバーを使用しないピアツーピアのSIPの展開で使用するためのDHTを実装しています。しかし、RELOADプロトコルは他のアプリケーションにも使用できます。そのため、「P2PSIP」の展開は一般に分散SIPを実装するためのRELOADの使用であると想定されますが、SIPとはまったく無関係な他のアプリケーションを分散させるメカニズムとしてRELOADが使用される可能性もあります。

2.4. Relationship between P2PSIP and SIP

2.4. P2PSIPとSIPの関係

Since P2PSIP is about peer-to-peer networks for real-time communication, it is expected that most Peers and Clients will be coupled with SIP entities (although RELOAD may be used for other applications than P2PSIP). For example, one Peer might be coupled with a SIP UA, another might be coupled with a SIP proxy, while a third might be coupled with a SIP-to-PSTN gateway. For such nodes, the Peer or Client portion of the node is logically distinct from the SIP entity portion. However, there is no hard requirement that every P2PSIP node (Peer or Client) be coupled to a SIP entity. As an example, additional Peers could be placed in the Overlay to provide additional storage or redundancy for the RELOAD Overlay, but might not have any direct SIP capabilities.

P2PSIPはリアルタイム通信のためのピアツーピアネットワークに関するものなので、（RELOADはP2PSIP以外のアプリケーションに使用されることもありますが）ほとんどのピアとクライアントはSIPエンティティーと結合されると想定されます。たとえば、あるピアはSIP UAと結合され、別のピアはSIPプロキシーと結合され、さらに3番目のピアはSIP-PSTNゲートウェイと結合されるかもしれません。このようなノードでは、ノードのピアまたはクライアントの部分は、SIPエンティティーの部分とは論理的に別のものです。ただし、すべてのP2PSIPノード（ピアまたはクライアント）がSIPエンティティーと結合されなければならないという厳密な要件はありません。例として、RELOADオーバーレイに追加のストレージや冗長性を提供するために、直接的なSIPの能力を持たない追加のピアをオーバーレイに配置することもできます。

2.5. Relationship between P2PSIP and Other AoR-Dereferencing Approaches

2.5. P2PSIPとAoRを解決する他の手法との関係

As noted above, the fundamental task of P2PSIP is to turn an AoR into a Contact. This task might be approached using zero configuration techniques such as multicast DNS (mDNS) and DNS Service Discovery (DNS-SD) [RFC6762] [RFC6763], Link-Local Multicast Name Resolution [RFC4795], and dynamic DNS [RFC2136].

上で述べたように、P2PSIPの根本的な役割は、AoRをコンタクトに変換することです。この役割には、マルチキャストDNS（mDNS）やDNSサービスディスカバリー（DNS-SD）[RFC6762] [RFC6763]、リンクローカルマルチキャスト名前解決（Link-Local Multicast Name Resolution）[RFC4795]、動的DNS[RFC2136]などのゼロコンフィグレーション技術を使用して取り組むこともできるでしょう。

These alternatives were discussed in the P2PSIP working group, and not pursued as a general solution for a number of reasons related to scalability, the ability to work in a disconnected state, partition recovery, and so on. However, there does seem to be some continuing interest in the possibility of using mDNS and DNS-SD for the bootstrapping of P2PSIP overlays.

これらの代替手法はP2PSIPワーキンググループで議論されましたが、スケーラビリティー、切断された状態で動作する能力、分断からの回復などに関連するいくつかの理由から、汎用的な解決策としては追求されませんでした。しかし、P2PSIPオーバーレイのブートストラップにmDNSとDNS-SDを使用する可能性については、引き続きいくらかの関心があるようです。

2.6. NAT Issues

2.6. NATの問題

Network Address Translators (NATs) are impediments to establishing and maintaining peer-to-peer networks, since NATs hinder direct communication between nodes. Some peer-to-peer network architectures avoid this problem by insisting that all nodes exist in the same address space. However, RELOAD provides capabilities that allow nodes to be located in multiple address spaces interconnected by NATs, to allow RELOAD messages to traverse NATs, and to assist in transmitting application-level messages (for example, SIP messages) across NATs.

ネットワークアドレス変換器（Network Address Translator、NAT）はノード間の直接通信を妨げるため、ピアツーピアネットワークの確立と維持の障害となります。ピアツーピアネットワークのアーキテクチャーの中には、すべてのノードが同じアドレス空間に存在することを要求することで、この問題を回避するものもあります。しかし、RELOADは、NATで相互接続された複数のアドレス空間にノードを配置できるようにし、RELOADメッセージがNATを越えられるようにし、アプリケーションレベルのメッセージ（たとえば、SIPメッセージ）をNATを越えて送信するのを支援する能力を提供します。

次の図は、いくつかのピア、1つのクライアント、そして通常のSIP UAで構成されるP2PSIPオーバーレイを示しています。この図は典型的なP2PSIPオーバーレイを示していますが、他の構成や変形を制限するものではありません。たとえば、プロキシーピアPが通常のSIPプロキシーとも通信することもあるでしょう。この図は、考えられるすべてのアーキテクチャーの変形を網羅することを意図したものではなく、単にP2PSIPの一般的な要素を多く含む展開を示すためのものです。

Here, the large perimeter depicted by "#" represents a stylized view of the Overlay (the actual connections could be a mesh, a ring, or some other structure). Around the periphery of the Overlay rectangle, we have a number of Peers. Each Peer is labeled with its coupled SIP entity -- for example, "Proxy Peer P" means that Peer P is coupled with a SIP proxy. In some cases, a Peer or Client might be coupled with two or more SIP entities. In this diagram, we have a Public Switched Telephone Network (PSTN) gateway coupled with Peer "G", three Peers ("D", "E", and "F") that are each coupled with a UA, a Peer "P" that is coupled with a SIP proxy, an ordinary Peer "Q" with no SIP capabilities, and one Peer "R" that is coupled with a SIP redirector. Note that because these are all Peers, each is responsible for storing Resource Records and transporting messages around the Overlay.

ここで、「#」で描かれた大きな外周は、オーバーレイを様式化して表したものです（実際の接続は、メッシュ、リング、またはその他の構造である可能性があります）。オーバーレイの長方形の周囲には、いくつかのピアがあります。各ピアには、結合されたSIPエンティティーを示すラベルが付けられています。たとえば、「Proxy Peer P」は、ピアPがSIPプロキシーと結合されていることを意味します。場合によっては、ピアやクライアントが2つ以上のSIPエンティティーと結合されることもあります。この図には、ピア「G」と結合された公衆交換電話網（Public Switched Telephone Network、PSTN）ゲートウェイ、それぞれUAと結合された3つのピア（「D」、「E」、「F」）、SIPプロキシーと結合されたピア「P」、SIPの能力を持たない通常のピア「Q」、そしてSIPリダイレクターと結合された1つのピア「R」があります。これらはすべてピアであるため、それぞれがリソースレコードの保存と、オーバーレイ内でのメッセージの転送を担うことに注意してください。

To the left, two of the Peers ("D" and "E") are behind network address translators (NATs). These Peers are included in the P2PSIP Overlay, and thus participate in storing resource records and routing messages, despite being behind the NATs.

左側では、2つのピア（「D」と「E」）がネットワークアドレス変換器（NAT）の背後にあります。これらのピアはP2PSIPオーバーレイに含まれているので、NATの背後にあるにもかかわらず、リソースレコードの保存とメッセージのルーティングに参加します。

On the right side, we have a Client "C", which uses the RELOAD Protocol to communicate with Proxy Peer "Q". The Client "C" uses RELOAD to obtain information from the Overlay, but has not inserted itself into the Overlay, and therefore does not participate in routing messages or storing information.

右側には、RELOADプロトコルを使用してプロキシーピア「Q」と通信するクライアント「C」があります。クライアント「C」は、RELOADを使用してオーバーレイから情報を取得しますが、自分自身をオーバーレイに挿入していないので、メッセージのルーティングや情報の保存には参加しません。

Below the Overlay, we have a conventional SIP UA "A" that is not part of the Overlay, either directly as a Peer or indirectly as a Client. It does not speak the RELOAD P2PSIP protocol and is not participating in the Overlay as a Peer or a Client. Instead, it uses SIP to interact with the Overlay via an adapter Peer or Peers that communicate with the Overlay using RELOAD.

オーバーレイの下には、ピアとして直接的にも、クライアントとして間接的にもオーバーレイの一部ではない、従来型のSIP UA「A」があります。このUAはRELOAD P2PSIPプロトコルを話さず、ピアとしてもクライアントとしてもオーバーレイに参加していません。代わりに、このUAはSIPを使用し、RELOADを使用してオーバーレイと通信するアダプターとなる1つ以上のピアを介して、オーバーレイとやりとりします。

Both the SIP proxy coupled with Peer "P" and the SIP redirector coupled with Peer "R" can serve as adapters between ordinary SIP devices and the Overlay. Each accepts standard SIP requests and resolves the next hop by using the P2PSIP protocol to interact with the routing knowledge of the Overlay, and then processes the SIP requests as appropriate (proxying or redirecting towards the next hop). Note that proxy operation is bidirectional -- the proxy may be forwarding a request from an ordinary SIP device to the Overlay, or from the P2PSIP Overlay to an ordinary SIP device.

ピア「P」と結合されたSIPプロキシーと、ピア「R」と結合されたSIPリダイレクターは、どちらも通常のSIPデバイスとオーバーレイの間のアダプターとして機能できます。それぞれ標準のSIPリクエストを受け付け、P2PSIPプロトコルを使用してオーバーレイのルーティング知識とやりとりすることで次のホップを解決し、その後SIPリクエストを適切に処理します（次のホップに向けてプロキシーまたはリダイレクトします）。プロキシーの動作は双方向であることに注意してください。プロキシーは、通常のSIPデバイスからオーバーレイへリクエストを転送する場合もあれば、P2PSIPオーバーレイから通常のSIPデバイスへリクエストを転送する場合もあります。

The PSTN Gateway at Peer "G" provides a similar sort of adaptation to and from the PSTN.

ピア「G」のPSTNゲートウェイは、PSTNとの間で同様の種類の適応を提供します。

4. Definitions

4. 定義

This section defines a number of concepts that are key to understanding the P2PSIP work.

このセクションでは、P2PSIPの取り組みを理解するうえで鍵となるいくつかの概念を定義します。

Overlay Network:
An overlay network is a computer network that is built on top of another network. Nodes in the overlay can be thought of as being connected by virtual or logical links, each of which corresponds to a path, perhaps through many physical links, in the underlying network. For example, many peer-to-peer networks are overlay networks because they run on top of the Internet. Dial-up Internet is an overlay upon the telephone network.
P2P Network:
A peer-to-peer (or P2P) computer network is a network that relies primarily on the computing power and bandwidth of the participants in the network rather than concentrating it in a relatively low number of servers. P2P networks are typically used for connecting nodes via largely ad hoc connections. Such networks are useful for many purposes. Sharing content files containing audio, video, data, or anything in digital format is very common, and real-time data, such as telephony traffic, is also exchanged using P2P technology. A P2P Network may also be called a "P2P Overlay", a "P2P Overlay Network", or a "P2P Network Overlay", since its organization is not at the physical layer, but is instead "on top of" an existing Internet Protocol network.
P2PSIP:
A suite of communications protocols related to the Session Initiation Protocol (SIP) [RFC3261] that enable SIP to use peer-to-peer techniques for resolving the targets of SIP requests, providing SIP message transport, and providing other SIP-related functions. At present, these protocols include [RFC6940], [RFC7363], [RFC7374], [RFC7851] and [P2PSIP].
User:
A human that interacts with the Overlay through SIP UAs located on Peers and Clients (and perhaps in other ways).
オーバーレイネットワーク（Overlay Network）:
オーバーレイネットワークとは、別のネットワークの上に構築されたコンピューターネットワークです。オーバーレイ内のノードは、仮想的または論理的なリンクで接続されているとみなすことができ、それぞれのリンクは、下位のネットワークにおける、場合によっては多くの物理リンクを経由する経路に対応します。たとえば、多くのピアツーピアネットワークは、インターネットの上で動作するため、オーバーレイネットワークです。ダイヤルアップインターネットは、電話網の上のオーバーレイです。
P2Pネットワーク（P2P Network）:
ピアツーピア（またはP2P）コンピューターネットワークとは、比較的少数のサーバーに計算能力と帯域幅を集中させるのではなく、主にネットワークの参加者の計算能力と帯域幅に依存するネットワークです。P2Pネットワークは通常、ほとんどがアドホックな接続を介してノードを接続するために使用されます。このようなネットワークは多くの目的に役立ちます。音声、動画、データ、その他デジタル形式のあらゆるものを含むコンテンツファイルの共有は非常に一般的であり、電話のトラフィックなどのリアルタイムデータもP2P技術を使用して交換されます。P2Pネットワークの組織は物理層ではなく、既存のインターネットプロトコルのネットワークの「上に」あるため、P2Pネットワークは「P2Pオーバーレイ（P2P Overlay）」、「P2Pオーバーレイネットワーク（P2P Overlay Network）」、「P2Pネットワークオーバーレイ（P2P Network Overlay）」と呼ばれることもあります。
P2PSIP:
セッション開始プロトコル（SIP）[RFC3261]に関連する一連の通信プロトコルで、SIPがSIPリクエストのターゲットの解決、SIPメッセージの転送の提供、その他のSIP関連の機能の提供のためにピアツーピアの技術を使用できるようにするものです。現時点では、これらのプロトコルには[RFC6940]、[RFC7363]、[RFC7374]、[RFC7851]、[P2PSIP]が含まれます。
ユーザー（User）:
ピアやクライアント上にあるSIP UAを通じて（あるいは、場合によっては他の方法で）オーバーレイとやりとりする人間です。

The following terms are defined here only within the scope of P2PSIP. These terms may have conflicting definitions in other bodies of literature. Some draft versions of this document prefixed each term with "P2PSIP" to clarify the term's scope. This prefixing has been eliminated from the text; however, the scoping still applies.

以下の用語は、ここではP2PSIPの範囲内でのみ定義されます。これらの用語は、他の文献では矛盾する定義を持つ可能性があります。この文書のいくつかのドラフト版では、用語の範囲を明確にするために各用語の前に「P2PSIP」を付けていました。本文からこの接頭辞は取り除かれましたが、範囲の限定は引き続き適用されます。

Overlay Name:
A human-friendly name that identifies a specific P2PSIP Overlay. This is in the format of (a portion of) a URI, but may or may not have a related record in the DNS.
Peer:
A node participating in a P2PSIP Overlay that provides storage and transport services to other nodes in that P2PSIP Overlay. Each Peer has a unique identifier, known as a Peer-ID, within the Overlay. Each Peer may be coupled to one or more SIP entities. Within the Overlay, the Peer is capable of performing several different operations, including: joining and leaving the Overlay, transporting SIP messages within the Overlay, storing information on behalf of the Overlay, putting information into the Overlay, and getting information from the Overlay.
Node-ID:
Information that uniquely identifies each Node within a given Overlay. This value is not human-friendly -- in a DHT approach, this is a numeric value in the hash space. These Node-IDs are completely independent of the identifier of any user of a user agent associated with a Peer.
Client:
A node that participates in a P2PSIP Overlay but does not store information or forward messages. A Client can also be thought of as a peer that has not joined the Overlay. Clients can store and retrieve information from the Overlay.
User Name:
A human-friendly name for a user. This name must be unique within the Overlay, but may be unique in a wider scope. User Names are formatted so that they can be used within a URI (likely a SIP URI), perhaps in combination with the Overlay Name.
Service:
A capability contributed by a Peer to an Overlay or to the members of an Overlay. Not all Peers and Clients will offer the same set of services, and P2PSIP provides service discovery mechanisms to locate services.
Service Name:
A unique, human-friendly name for a service.
Resource:
Anything about which information can be stored in the Overlay. Both Users and Services are examples of Resources.
Resource-ID:
A non-human-friendly value that uniquely identifies a resource and that is used as a key for storing and retrieving data about the resource. One way to generate a Resource-ID is by applying a mapping function to some other unique name (e.g., User Name or Service Name) for the resource. The Resource-ID is used by the distributed database algorithm to determine the Peer or Peers that are responsible for storing data for the Overlay.
Resource Record:
A block of data, stored using the distributed database mechanism of the Overlay, that includes information relevant to a specific resource. We presume that there may be multiple types of resource records. Some may hold data about Users, and others may hold data about Services, and the working group may define other types. The types, usages, and formats of the records are a question for future study.
Responsible Peer
The Peer that is responsible for storing the Resource Record for a Resource. In the literature, the term "Root Peer" is also used for this concept.
Peer Protocol:
The protocol spoken between P2PSIP Overlay Peers to share information and organize the P2PSIP Overlay Network. In P2PSIP, this is implemented using the RELOAD protocol [RFC6940].
Client Protocol:
The protocol spoken between Clients and Peers. In P2PSIP and RELOAD, this is syntactically the same protocol as the Peer Protocol. The only difference is that Clients are not routing messages or routing information, and have not (or cannot) insert themselves into the Overlay.
Peer Protocol Connection / P2PSIP Client Protocol Connection:
The Transport Layer Security (TLS), Datagram Transport Layer Security (DTLS), TCP, UDP, or other transport-layer protocol connection over which the RELOAD Peer Protocol messages are transported.
Neighbors:
The set of P2PSIP Peers that a Peer or Client know of directly and can reach without further lookups.
Joining Peer:
A node that is attempting to become a Peer in a particular Overlay.
Bootstrap Peer:
A Peer in the Overlay that is the first point of contact for a Joining Peer. It selects the Peer that will serve as the Admitting Peer and helps the Joining Peer contact the Admitting Peer.
Admitting Peer:
A Peer in the Overlay that helps the Joining Peer join the Overlay. The choice of the Admitting Peer may depend on the Joining Peer (e.g., depend on the Joining Peer's Peer-ID). For example, the Admitting Peer might be chosen as the Peer which is "closest" in the logical structure of the Overlay to the future position of the Joining Peer. The selection of the Admitting Peer is typically done by the Bootstrap Peer. It is allowable for the Bootstrap Peer to select itself as the Admitting Peer.
Bootstrap Server:
A network node used by Joining Peers to locate a Bootstrap Peer. A Bootstrap Server may act as a proxy for messages between the Joining Peer and the Bootstrap Peer. The Bootstrap Server itself is typically a stable host with a DNS name that is somehow communicated (for example, through configuration, specification on a web page, or using DHCP) to Peers that want to join the Overlay. A Bootstrap Server is NOT required to be a Peer or Client, though it may be if desired.
Peer Admission:
The act of admitting a node (the "Joining Peer") into an Overlay as a Peer. After the admission process is over, the Joining Peer is a fully functional Peer of the Overlay. During the admission process, the Joining Peer may need to present credentials to prove that it has sufficient authority to join the Overlay.
Resource Record Insertion:
The act of inserting a P2PSIP Resource Record into the distributed database. Following insertion, the data will be stored at one or more Peers. The data can be retrieved or updated using the Resource-ID as a key.
オーバーレイ名（Overlay Name）:
特定のP2PSIPオーバーレイを識別する、人間にとってわかりやすい名前です。これはURI（の一部）の形式ですが、DNSに関連するレコードがある場合もない場合もあります。
ピア（Peer）:
P2PSIPオーバーレイに参加し、そのP2PSIPオーバーレイ内の他のノードにストレージとトランスポートのサービスを提供するノードです。各ピアは、オーバーレイ内で一意な、ピアID（Peer-ID）と呼ばれる識別子を持ちます。各ピアは、1つ以上のSIPエンティティーと結合されることがあります。オーバーレイ内では、ピアはいくつかの異なる操作を行うことができます。たとえば、オーバーレイへの参加と離脱、オーバーレイ内でのSIPメッセージの転送、オーバーレイに代わっての情報の保存、オーバーレイへの情報の格納、オーバーレイからの情報の取得などです。
ノードID（Node-ID）:
特定のオーバーレイ内で各ノードを一意に識別する情報です。この値は人間にとってわかりやすいものではありません。DHTの手法では、これはハッシュ空間内の数値です。これらのノードIDは、ピアに関連付けられたユーザーエージェントのユーザーの識別子とはまったく無関係です。
クライアント（Client）:
P2PSIPオーバーレイに参加するが、情報の保存やメッセージの転送は行わないノードです。クライアントは、オーバーレイに参加していないピアとみなすこともできます。クライアントは、オーバーレイに情報を保存したり、オーバーレイから情報を取得したりできます。
ユーザー名（User Name）:
ユーザーの、人間にとってわかりやすい名前です。この名前はオーバーレイ内で一意でなければなりませんが、より広い範囲で一意であってもかまいません。ユーザー名は、場合によってはオーバーレイ名と組み合わせて、URI（おそらくSIP URI）の中で使用できるような形式になっています。
サービス（Service）:
ピアがオーバーレイに、またはオーバーレイのメンバーに提供する能力です。すべてのピアとクライアントが同じ一連のサービスを提供するわけではなく、P2PSIPはサービスを見つけるためのサービスディスカバリーのメカニズムを提供します。
サービス名（Service Name）:
サービスの、一意で人間にとってわかりやすい名前です。
リソース（Resource）:
オーバーレイにその情報を保存できるあらゆるものです。ユーザーとサービスはどちらもリソースの例です。
リソースID（Resource-ID）:
リソースを一意に識別し、そのリソースに関するデータの保存と取得のキーとして使用される、人間にとってわかりやすくない値です。リソースIDを生成する方法の1つは、そのリソースの他の何らかの一意な名前（たとえば、ユーザー名やサービス名）に対応付け関数を適用することです。リソースIDは、分散データベースアルゴリズムが、オーバーレイのためにデータを保存する責任を負うピアを決定するために使用されます。
リソースレコード（Resource Record）:
オーバーレイの分散データベースメカニズムを使用して保存される、特定のリソースに関連する情報を含むデータのブロックです。リソースレコードには複数の種類があり得ると想定しています。ユーザーに関するデータを保持するもの、サービスに関するデータを保持するものがあり、ワーキンググループが他の種類を定義することもあります。レコードの種類、用法、形式は、今後の検討課題です。
責任ピア（Responsible Peer）
あるリソースのリソースレコードを保存する責任を負うピアです。文献では、この概念に「ルートピア（Root Peer）」という用語も使用されています。
ピアプロトコル（Peer Protocol）:
情報を共有し、P2PSIPオーバーレイネットワークを組織するために、P2PSIPオーバーレイのピア間で話されるプロトコルです。P2PSIPでは、これはRELOADプロトコル[RFC6940]を使用して実装されます。
クライアントプロトコル（Client Protocol）:
クライアントとピアの間で話されるプロトコルです。P2PSIPとRELOADでは、これは構文上ピアプロトコルと同じプロトコルです。唯一の違いは、クライアントはメッセージやルーティング情報のルーティングを行わず、自分自身をオーバーレイに挿入していない（または挿入できない）ことです。
ピアプロトコル接続（Peer Protocol Connection） / P2PSIPクライアントプロトコル接続（P2PSIP Client Protocol Connection）:
RELOADのピアプロトコルのメッセージが転送される、トランスポート層セキュリティー（Transport Layer Security、TLS）、データグラムトランスポート層セキュリティー（Datagram Transport Layer Security、DTLS）、TCP、UDP、またはその他のトランスポート層プロトコルの接続です。
近隣ピア（Neighbors）:
ピアまたはクライアントが直接知っていて、それ以上の検索なしに到達できるP2PSIPピアの集合です。
参加ピア（Joining Peer）:
特定のオーバーレイでピアになろうとしているノードです。
ブートストラップピア（Bootstrap Peer）:
参加ピアにとって最初の連絡先となる、オーバーレイ内のピアです。ブートストラップピアは、受け入れピアとなるピアを選択し、参加ピアが受け入れピアに連絡するのを支援します。
受け入れピア（Admitting Peer）:
参加ピアがオーバーレイに参加するのを支援する、オーバーレイ内のピアです。受け入れピアの選択は、参加ピアに依存する場合があります（たとえば、参加ピアのピアIDに依存します）。たとえば、オーバーレイの論理構造において、参加ピアの将来の位置に「最も近い」ピアが受け入れピアとして選ばれるかもしれません。受け入れピアの選択は、通常ブートストラップピアによって行われます。ブートストラップピアが自分自身を受け入れピアとして選択することも許されます。
ブートストラップサーバー（Bootstrap Server）:
参加ピアがブートストラップピアを見つけるために使用するネットワークノードです。ブートストラップサーバーは、参加ピアとブートストラップピアの間のメッセージのプロキシーとして動作することもあります。ブートストラップサーバー自体は通常、オーバーレイに参加したいピアに何らかの方法で（たとえば、設定、Webページへの記載、DHCPの使用などによって）伝えられるDNS名を持つ、安定したホストです。ブートストラップサーバーはピアやクライアントである必要はありませんが、望むならそうであってもかまいません。
ピアの受け入れ（Peer Admission）:
ノード（「参加ピア」）をピアとしてオーバーレイに受け入れる行為です。受け入れのプロセスが終わると、参加ピアはオーバーレイの完全に機能するピアになります。受け入れのプロセスの間、参加ピアは、オーバーレイに参加する十分な権限を持っていることを証明するためにクレデンシャルを提示する必要がある場合があります。
リソースレコードの挿入（Resource Record Insertion）:
P2PSIPのリソースレコードを分散データベースに挿入する行為です。挿入の後、データは1つ以上のピアに保存されます。データは、リソースIDをキーとして使用して取得または更新できます。

5. Discussion

5. 議論

5.1. The Distributed Database Function

5.1. 分散データベース機能

A P2PSIP Overlay functions as a distributed database. The database serves as a way to store information about Resources. A piece of information, called a "Resource Record", can be stored by and retrieved from the database using a key associated with the Resource Record called its "Resource-ID". Each Resource must have a unique Resource-ID. In addition to uniquely identifying the Resource, the Resource-ID is also used by the distributed database algorithm to determine the Peer or Peers that store the Resource Record in the Overlay.

P2PSIPオーバーレイは分散データベースとして機能します。このデータベースは、リソースに関する情報を保存する手段として役立ちます。「リソースレコード（Resource Record）」と呼ばれる情報の断片は、そのリソースレコードに関連付けられた「リソースID（Resource-ID）」と呼ばれるキーを使用して、データベースに保存したりデータベースから取得したりできます。各リソースは一意なリソースIDを持たなければなりません。リソースIDは、リソースを一意に識別することに加えて、分散データベースアルゴリズムがオーバーレイ内でリソースレコードを保存するピアを決定するためにも使用されます。

Users are humans that can use the Overlay to do things like making and receiving calls. Information stored in the resource record associated with a user can include things like the full name of the user and the location of the UAs that the user is using (the user's SIP AoR). Full details of how this is implemented using RELOAD are provided in [P2PSIP].

ユーザーは、オーバーレイを使用して発信や着信などを行うことができる人間です。ユーザーに関連付けられたリソースレコードに保存される情報には、ユーザーのフルネームや、ユーザーが使用しているUAの場所（ユーザーのSIP AoR）などが含まれます。RELOADを使用してこれを実装する方法の完全な詳細は[P2PSIP]で示されています。

Before information about a user can be stored in the Overlay, a user needs a User Name. The User Name is a human-friendly identifier that uniquely identifies the user within the Overlay. In RELOAD, users are issued certificates, which in the case of centrally signed certificates, identify the User Name as well as a certain number of Resource-IDs where the user may store their information. For more information, see [RFC6940].

ユーザーに関する情報をオーバーレイに保存できるようになる前に、ユーザーにはユーザー名が必要です。ユーザー名は、オーバーレイ内でユーザーを一意に識別する、人間にとってわかりやすい識別子です。RELOADでは、ユーザーに証明書が発行されます。中央で署名された証明書の場合、その証明書はユーザー名と、ユーザーが自分の情報を保存できる一定数のリソースIDを識別します。詳細については[RFC6940]を参照してください。

The P2PSIP suite of protocols also standardizes information about how to locate services. Services represent actions that a Peer (and perhaps a Client) can do to benefit other Peers and Clients in the Overlay. Information that might be stored in the resource record associated with a service might include the Peers (and perhaps Clients) offering the service. Service discovery for P2PSIP is defined in [RFC7374].

P2PSIPの一連のプロトコルは、サービスを見つける方法に関する情報も標準化しています。サービスは、ピア（および場合によってはクライアント）がオーバーレイ内の他のピアやクライアントの役に立つように実行できる動作を表します。サービスに関連付けられたリソースレコードに保存される情報には、そのサービスを提供するピア（および場合によってはクライアント）が含まれるかもしれません。P2PSIPのサービスディスカバリーは[RFC7374]で定義されています。

Each service has a human-friendly Service Name that uniquely identifies the service. Like User Names, the Service Name is not a Resource-ID, rather the Resource-ID is derived from the service name using some function defined by the distributed database algorithm used by the Overlay.

各サービスは、そのサービスを一意に識別する、人間にとってわかりやすいサービス名を持ちます。ユーザー名と同様に、サービス名はリソースIDではありません。むしろ、リソースIDは、オーバーレイが使用する分散データベースアルゴリズムで定義された何らかの関数を使用して、サービス名から導出されます。

A class of algorithms known as Distributed Hash Tables (DHTs) are one way to implement the distributed database. The RELOAD protocol is extensible and allows many different DHTs to be implemented, but specifies a mandatory-to-implement DHT in the form of a modified Chord DHT. For more information, see [Chord].

分散ハッシュテーブル（DHT）として知られるアルゴリズムの種類は、分散データベースを実装する方法の1つです。RELOADプロトコルは拡張可能であり、多くの異なるDHTを実装できるようにしていますが、実装必須のDHTとして、変更を加えたChord DHTを規定しています。詳細については[Chord]を参照してください。

5.2. Using the Distributed Database Function

5.2. 分散データベース機能の使用

While there are a number of ways the distributed database described in the previous section can be used to establish multimedia sessions using SIP, the basic mechanism defined in the RELOAD protocol and SIP usage is summarized below. This is a very simplistic overview. For more detailed information, please see the RELOAD protocol [RFC6940].

前のセクションで説明した分散データベースを、SIPを使用したマルチメディアセッションの確立に使用する方法はいくつもありますが、RELOADプロトコルとSIPの用法で定義された基本的なメカニズムを以下にまとめます。これは非常に単純化した概要です。より詳細な情報については、RELOADプロトコル[RFC6940]を参照してください。

Contact information for a user is stored in the resource record for that user. Assume that a user is using a device, here called "Peer A", that serves as the contact point for this user. The user adds contact information to this resource record, as authorized by the RELOAD certificate mechanism. The resource record itself is stored with Peer Z in the network, where Peer Z is chosen by the particular distributed database algorithm in use by the Overlay.

ユーザーの連絡先情報は、そのユーザーのリソースレコードに保存されます。ユーザーが、ここでは「ピアA」と呼ぶ、このユーザーの連絡先となるデバイスを使用していると仮定します。ユーザーは、RELOADの証明書メカニズムによって認可されたとおりに、このリソースレコードに連絡先情報を追加します。リソースレコード自体はネットワーク内のピアZに保存されます。ここでピアZは、オーバーレイが使用している特定の分散データベースアルゴリズムによって選ばれます。

When the SIP entity coupled with Peer B has an INVITE message addressed to this user, it retrieves the resource record from Peer Z. It then extracts the contact information for the various Peers that are a contact point for the user, including Peer A, and uses the Overlay to establish a connection to Peer A, including any appropriate NAT traversal (the details of which are not shown).

ピアBと結合されたSIPエンティティーがこのユーザー宛てのINVITEメッセージを持っている場合、そのエンティティーはピアZからリソースレコードを取得します。次に、ピアAを含め、そのユーザーの連絡先となるさまざまなピアの連絡先情報を取り出し、オーバーレイを使用して、適切なNAT越え（詳細は示していません）を含めてピアAへの接続を確立します。

Note that RELOAD is used only to establish the connection. Once the connection is established, messages between the Peers are sent using ordinary SIP.

RELOADは接続の確立にのみ使用されることに注意してください。接続が確立されると、ピア間のメッセージは通常のSIPを使用して送信されます。

This exchange is illustrated in the following figure. The notation "Store(U@A)" is used to show the distributed database operation of updating the resource record for user U with the contract A, and "Fetch(U)" illustrates the distributed database operation of retrieving the resource record for user U. Note that the messages between the Peers A, B, and Z may actually travel via intermediate Peers (not shown) as part of the distributed lookup process or so as to traverse intervening NATs.

このやりとりを次の図に示します。「Store(U@A)」という表記は、ユーザーUのリソースレコードを連絡先Aで更新する分散データベースの操作を示すために使用され、「Fetch(U)」は、ユーザーUのリソースレコードを取得する分散データベースの操作を示します。ピアA、B、Z間のメッセージは、実際には、分散検索のプロセスの一部として、または間にあるNATを越えるために、（図示していない）中間のピアを経由する場合があることに注意してください。

5.3. NAT Traversal

5.3. NAT越え

NAT traversal in P2PSIP using RELOAD treats all Peers as equal and establishes a partial mesh of connections between them. Messages from one Peer to another are routed along the edges in the mesh of connections until they reach their destination. To make the routing efficient and to avoid the use of standard Internet routing protocols, the partial mesh is organized in a structured manner. If the structure is based on any one of a number of common DHT algorithms, then the maximum number of hops between any two Peers is log N, where N is the number of peers in the overlay. Existing connections, along with the Interactive Connectivity Establishment (ICE) NAT traversal techniques [RFC5245], are used to establish new connections between Peers, and also to allow the applications running on Peers to establish a connection to communicate with one another.

RELOADを使用したP2PSIPにおけるNAT越えでは、すべてのピアを対等に扱い、ピア間に接続の部分メッシュを確立します。あるピアから別のピアへのメッセージは、宛先に到達するまで、接続のメッシュの辺に沿ってルーティングされます。ルーティングを効率的にし、標準的なインターネットのルーティングプロトコルの使用を避けるために、部分メッシュは構造化された方法で組織されます。その構造がいくつかある一般的なDHTアルゴリズムのいずれかに基づいている場合、任意の2つのピア間の最大ホップ数はlog Nになります。ここでNはオーバーレイ内のピアの数です。既存の接続は、Interactive Connectivity Establishment（ICE）のNAT越え技術[RFC5245]とともに、ピア間の新しい接続を確立するため、またピア上で動作するアプリケーションが互いに通信するための接続を確立できるようにするために使用されます。

5.4. Locating and Joining an Overlay

5.4. オーバーレイの発見と参加

Before a Peer can attempt to join a P2PSIP Overlay, it must first obtain a Node-ID, configuration information, and optionally a set of credentials. The Node-ID is an identifier that uniquely identifies the Peer within the Overlay, while the credentials show that the Peer is allowed to join the Overlay.

ピアがP2PSIPオーバーレイへの参加を試みる前に、まずノードID、設定情報、そしてオプションで一連のクレデンシャルを取得しなければなりません。ノードIDはオーバーレイ内でピアを一意に識別する識別子であり、一方クレデンシャルは、そのピアがオーバーレイへの参加を許可されていることを示します。

The P2PSIP WG does not impose a particular mechanism for how the Peer-ID and the credentials are obtained, but the RELOAD protocol does specify the format for the configuration information and how this information may be obtained, along with credentials and a Node-ID, from an offline enrollment server.

P2PSIPワーキンググループは、ピアIDとクレデンシャルを取得する方法について特定のメカニズムを課していませんが、RELOADプロトコルは、設定情報の形式と、この情報をクレデンシャルとノードIDとともにオフラインの登録サーバーから取得する方法を規定しています。

Once the configuration information is obtained, RELOAD specifies a mechanism whereby a Peer may obtain a multicast-bootstrap address in the configuration file and broadcast to this address to attempt locating a Bootstrap Peer. Additionally, the Peer may store previous Peers it has seen and attempt using these as Bootstrap Peers, or it may obtain an address for a Bootstrap Peer by some other mechanism. For more information, see the RELOAD protocol.

設定情報が取得されると、ピアが設定ファイル内のマルチキャストブートストラップアドレスを取得し、このアドレスにブロードキャストしてブートストラップピアの発見を試みることができるメカニズムをRELOADは規定しています。さらに、ピアは以前に見たピアを保存しておき、それらをブートストラップピアとして使用することを試みることもでき、また他の何らかのメカニズムによってブートストラップピアのアドレスを取得することもできます。詳細については、RELOADプロトコルを参照してください。

The job of the Bootstrap Peer is simple: refer the Joining Peer to a Peer (called the "Admitting Peer") that will help the Joining Peer join the network. The choice of the Admitting Peer will often depend on the Joining Peer -- for example, the Admitting Peer may be a Peer that will become a neighbor of the Joining Peer in the Overlay. It is possible that the Bootstrap Peer might also serve as the Admitting Peer.

ブートストラップピアの仕事は単純です。参加ピアがネットワークに参加するのを支援するピア（「受け入れピア（Admitting Peer）」と呼ばれます）を参加ピアに紹介することです。受け入れピアの選択は、多くの場合参加ピアに依存します。たとえば、受け入れピアは、オーバーレイ内で参加ピアの近隣となるピアであるかもしれません。ブートストラップピアが受け入れピアを兼ねる可能性もあります。

The Admitting Peer will help the Joining Peer learn about other Peers in the Overlay and establish connections to them as appropriate. The Admitting Peer and/or the other Peers in the Overlay will also do whatever else is required to help the Joining Peer become a fully functional Peer. The details of how this is done will depend on the distributed database algorithm used by the Overlay.

受け入れピアは、参加ピアがオーバーレイ内の他のピアについて知り、必要に応じてそれらのピアへの接続を確立するのを支援します。受け入れピアやオーバーレイ内の他のピアは、参加ピアが完全に機能するピアになるのを支援するために必要なその他のことも行います。これをどのように行うかの詳細は、オーバーレイが使用する分散データベースアルゴリズムに依存します。

At various stages in this process, the Joining Peer may be asked to present its credentials to show that it is authorized to join the Overlay. Similarly, the various Peers contacted may be asked to present their credentials so the Joining Peer can verify that it is really joining the Overlay it wants to.

このプロセスのさまざまな段階で、参加ピアは、オーバーレイへの参加が認可されていることを示すために、クレデンシャルの提示を求められる場合があります。同様に、連絡を受けたさまざまなピアも、参加ピアが自分が参加したいオーバーレイに本当に参加しているのかを検証できるように、クレデンシャルの提示を求められる場合があります。

5.5. Clients and Connecting Unmodified SIP Devices

5.5. クライアントと未改変のSIPデバイスの接続

As mentioned above, in RELOAD, from the perspective of the protocol, Clients are simply peers that do not store information, do not route messages, and have not inserted themselves into the Overlay. The same protocol is used for the actual message exchanged. Note that while the protocol is the same, the Client need not implement all the capabilities of a Peer. If, for example, it never routes messages, it will not need to be capable of processing such messages or understanding a DHT.

上で述べたように、RELOADでは、プロトコルの観点から見ると、クライアントは単に、情報を保存せず、メッセージをルーティングせず、自分自身をオーバーレイに挿入していないピアです。実際にやりとりされるメッセージには同じプロトコルが使用されます。プロトコルは同じですが、クライアントがピアのすべての能力を実装する必要はないことに注意してください。たとえば、クライアントがメッセージをルーティングしないのであれば、そのようなメッセージを処理したりDHTを理解したりできる必要はありません。

For SIP devices, another way to realize this functionality is for a Peer to behave as a proxy/registrar as specified in [RFC3261]. SIP devices then use standard SIP mechanisms to add, update, and remove registrations and to send SIP messages to Peers and other Clients. The authors here refer to these devices simply as a "SIP UA", not a "P2PSIP Client", to distinguish it from the concept described above.

SIPデバイスについて、この機能を実現する別の方法は、ピアが[RFC3261]で規定されたプロキシー/レジストラーとして振る舞うことです。その場合、SIPデバイスは標準のSIPメカニズムを使用して、登録の追加、更新、削除を行い、ピアや他のクライアントにSIPメッセージを送信します。ここでは著者らは、上で説明した概念と区別するために、これらのデバイスを「P2PSIPクライアント（P2PSIP Client）」ではなく、単に「SIP UA」と呼びます。
