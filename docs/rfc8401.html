RFC 8401

Bit Index Explicit Replication (BIER) Support via IS-IS

RFC 8401

IS-ISによるビットインデックス明示的複製（BIER）のサポート

Abstract

概要

This document defines IS-IS extensions to support multicast forwarding using the Bit Index Explicit Replication (BIER) architecture.

この文書は、ビットインデックス明示的複製（Bit Index Explicit Replication: BIER）アーキテクチャーを使用したマルチキャスト転送をサポートするためのIS-IS拡張を定義します。

1. Introduction

1. はじめに

Bit Index Explicit Replication (BIER) [RFC8279] defines an architecture where all intended multicast receivers are encoded as a bitmask in the multicast packet header within different encapsulations such as described in [RFC8296]. A router that receives such a packet will forward the packet based on the bit position in the packet header towards the receiver(s) following a precomputed tree for each of the bits in the packet. Each receiver is represented by a unique bit in the bitmask.

ビットインデックス明示的複製（BIER）[RFC8279]は、意図したすべてのマルチキャスト受信者を、[RFC8296]で説明されているようなさまざまなカプセル化の中で、マルチキャストパケットヘッダー内のビットマスクとして符号化するアーキテクチャーを定義します。このようなパケットを受信したルーターは、パケット内の各ビットについて事前に計算されたツリーに従い、パケットヘッダー内のビット位置に基づいて受信者に向けてパケットを転送します。各受信者は、ビットマスク内の一意なビットで表されます。

This document presents necessary extensions to the currently deployed IS-IS for IP [RFC1195] to support distribution of information necessary for operation of BIER domains and subdomains. This document defines a new TLV to be advertised by every router participating in BIER signaling.

この文書は、BIERドメインとサブドメインの運用に必要な情報の配布をサポートするために、現在展開されているIP用のIS-IS [RFC1195]に必要な拡張を示します。この文書は、BIERのシグナリングに参加するすべてのルーターが広告する新しいTLVを定義します。

This document defines support for MPLS encapsulation as specified in [RFC8296]. Support for other encapsulation types and the use of multiple encapsulation types are outside the scope of this document.

この文書は、[RFC8296]で規定されているMPLSカプセル化のサポートを定義します。その他のカプセル化タイプのサポートや、複数のカプセル化タイプの使用は、この文書の範囲外です。

2. Terminology

2. 用語

Some of the terminology specified in [RFC8279] is replicated here and extended by necessary definitions:

[RFC8279]で規定されている用語の一部をここに再掲し、必要な定義を追加して拡張します。

BIER:
Bit Index Explicit Replication. The overall architecture of forwarding multicast using a bit position.
BIER-OL:
BIER Overlay Signaling. The method for the BFIR to learn about BFERs.
BFR:
Bit Forwarding Router. A router that participates in Bit Index Multipoint Forwarding. A BFR is identified by a unique BFR-prefix in a BIER domain.
BFIR:
Bit Forwarding Ingress Router. The ingress border router that inserts the BitString into the packet. Each BFIR must have a valid BFR-id assigned.
BFER:
Bit Forwarding Egress Router. A router that participates in Bit Index Forwarding as a leaf. Each BFER must be a BFR. Each BFER must have a valid BFR-id assigned.
BFT:
Bit Forwarding Tree used to reach all BFERs in a domain.
BIER subdomain:
A further distinction within a BIER domain identified by its unique subdomain identifier. A BIER subdomain can support multiple BitString Lengths.
BFR-id:
An optional, unique identifier for a BFR within a BIER subdomain.
Invalid BFR-id:
Unassigned BFR-id. The special value 0 is reserved for this purpose.
BAR:
BIER Algorithm. Used to calculate underlay next hops.
IPA:
IGP Algorithm. May be used to modify, enhance, or replace the calculation of underlay paths as defined by the BAR value.
SPF:
Shortest Path First routing calculation based on the IGP link metric.
BIER:
ビットインデックス明示的複製（Bit Index Explicit Replication）。ビット位置を使用してマルチキャストを転送する全体的なアーキテクチャーです。
BIER-OL:
BIERオーバーレイシグナリング（BIER Overlay Signaling）。BFIRがBFERについて知るための方法です。
BFR:
ビット転送ルーター（Bit Forwarding Router）。ビットインデックスマルチポイント転送（Bit Index Multipoint Forwarding）に参加するルーターです。BFRは、BIERドメイン内で一意なBFR-prefixによって識別されます。
BFIR:
ビット転送入口ルーター（Bit Forwarding Ingress Router）。パケットにBitStringを挿入する入口の境界ルーターです。各BFIRには、有効なBFR-idが割り当てられている必要があります。
BFER:
ビット転送出口ルーター（Bit Forwarding Egress Router）。リーフとしてビットインデックス転送（Bit Index Forwarding）に参加するルーターです。各BFERはBFRである必要があります。各BFERには、有効なBFR-idが割り当てられている必要があります。
BFT:
ドメイン内のすべてのBFERに到達するために使用されるビット転送ツリー（Bit Forwarding Tree）です。
BIER subdomain:
BIERサブドメイン。BIERドメイン内をさらに区分したもので、一意なサブドメイン識別子によって識別されます。BIERサブドメインは、複数のBitString長をサポートできます。
BFR-id:
BIERサブドメイン内でBFRを一意に識別する識別子です。割り当ては任意です。
Invalid BFR-id:
無効なBFR-id。割り当てられていないBFR-idです。この目的のために、特別な値0が予約されています。
BAR:
BIERアルゴリズム（BIER Algorithm）。アンダーレイのネクストホップを計算するのに使用します。
IPA:
IGPアルゴリズム（IGP Algorithm）。BARの値で定義されるアンダーレイのパスの計算を修正、拡張、または置き換えるのに使用される場合があります。
SPF:
IGPのリンクメトリックに基づく、最短パス優先（Shortest Path First）のルーティング計算です。

4. Concepts

4. 概念

4.1. BIER Domains and Subdomains

4.1. BIERドメインとサブドメイン

An IS-IS-signaled BIER domain is aligned with the scope of distribution of BFR-prefixes that identify the BFRs within IS-IS. In such a case, IS-IS acts as the supporting BIER underlay.

IS-ISでシグナリングされるBIERドメインは、IS-IS内でBFRを識別するBFR-prefixの配布範囲と一致します。このような場合、IS-ISはBIERを支えるアンダーレイとして機能します。

Within such a domain, the extensions defined in this document advertise BIER information for one or more BIER subdomains. Each subdomain is uniquely identified by a subdomain-id (SD). Each subdomain is associated with a single IS-IS topology (MT) [RFC5120], which may be any of the topologies supported by IS-IS. Local configuration controls which <MT,SD> pairs are supported by a router. The mapping of subdomains to topologies MUST be consistent within the IS-IS flooding domain used to advertise BIER information.

そのようなドメイン内で、この文書で定義する拡張は、1つ以上のBIERサブドメインについてのBIER情報を広告します。各サブドメインは、サブドメインID（subdomain-id: SD）によって一意に識別されます。各サブドメインは、単一のIS-ISトポロジー（MT）[RFC5120]に関連付けられます。このトポロジーは、IS-ISがサポートする任意のトポロジーでかまいません。ルーターがどの<MT,SD>のペアをサポートするかは、ローカルの設定によって制御されます。サブドメインとトポロジーの対応付けは、BIER情報の広告に使用されるIS-ISフラッディングドメイン内で一貫していなければなりません（MUST）。

Each BIER subdomain has as its unique attributes the encapsulation used and the type of tree it uses to forward BIER frames (currently always SPF). Additionally, per supported BitString length in the subdomain, each router will advertise the necessary label ranges to support it.

各BIERサブドメインは、使用するカプセル化と、BIERフレームの転送に使用するツリーの種類（現在は常にSPF）を固有の属性として持ちます。さらに、各ルーターは、サブドメインでサポートするBitString長ごとに、それをサポートするのに必要なラベル範囲を広告します。

4.2. Advertising BIER Information

4.2. BIER情報の広告

BIER information advertisements are associated with a new sub-TLV in the extended reachability TLVs. BIER information is always associated with a host prefix, which MUST be a node address for the advertising node. If this is not the case, the advertisement MUST be ignored. Therefore, the following restrictions apply:

BIER情報の広告は、拡張到達可能性TLV（extended reachability TLV）内の新しいサブTLVに関連付けられます。BIER情報は常にホストプレフィックスに関連付けられ、このプレフィックスは広告するノードのノードアドレスでなければなりません（MUST）。そうでない場合、その広告は無視されなければなりません（MUST）。したがって、次の制約が適用されます。

  • Prefix length MUST be 32 for an IPv4 prefix or 128 for an IPv6 prefix.
  • When the Prefix Attributes Flags sub-TLV [RFC7794] is present, the N flag MUST be set and the R flag MUST NOT be set.
  • BIER sub-TLVs MUST be included when a prefix reachability advertisement is leaked between levels.
  • プレフィックス長は、IPv4プレフィックスの場合は32、IPv6プレフィックスの場合は128でなければなりません（MUST）。
  • Prefix Attributes FlagsサブTLV [RFC7794]が存在する場合、Nフラグは設定されなければなりません（MUST）。また、Rフラグは設定されてはなりません（MUST NOT）。
  • プレフィックス到達可能性の広告がレベル間でリークされる場合は、BIERサブTLVを含めなければなりません（MUST）。

5. Procedures

5. 手順

5.1. Multi-Topology and Subdomain

5.1. マルチトポロジーとサブドメイン

A given subdomain is supported within one and only one topology. All routers in the flooding scope of the BIER sub-TLVs MUST advertise the same subdomain within the same multi-topology. A router receiving an <MT,SD> advertisement that does not match the locally configured pair MUST report a misconfiguration of the received <MT,SD> pair. All received BIER advertisements associated with the conflicting <MT,SD> pair MUST be ignored. Note that in the presence of such a misconfiguration, this will lead to partitioning of the subdomain.

あるサブドメインは、ただ1つのトポロジー内でのみサポートされます。BIERサブTLVのフラッディング範囲内のすべてのルーターは、同じマルチトポロジー内で同じサブドメインを広告しなければなりません（MUST）。ローカルに設定されたペアと一致しない<MT,SD>の広告を受信したルーターは、受信した<MT,SD>ペアの設定誤りを報告しなければなりません（MUST）。矛盾する<MT,SD>ペアに関連付けられた、受信したすべてのBIER広告は無視されなければなりません（MUST）。このような設定誤りがある場合、サブドメインが分断されることに注意してください。

Example:

例:

The following combination of advertisements are valid: <0,0> <0,1>, and <2,2>.

次の広告の組み合わせは有効です: <0,0> <0,1>、<2,2>。

The following combination of advertisements are invalid: <0,0> <0,1>, and <2,0>. Advertisements associated with <0,0> and <2,0> must be ignored.

次の広告の組み合わせは無効です: <0,0> <0,1>、<2,0>。<0,0>と<2,0>に関連付けられた広告は無視する必要があります。

5.2. BFR-id Advertisements

5.2. BFR-idの広告

If a BFER/BFIR is configured with a BFR-id, then it advertises this value in its BIER advertisements. If no BFR-id is configured, then the value "Invalid BFR-id" is advertised. A valid BFR-id MUST be unique within the flooding scope of the BIER advertisements. All BFERs/BFIRs MUST detect advertisement of duplicate valid BFR-IDs for a given <MT,SD>. When such duplication is detected, all of the routers advertising duplicates MUST be treated as if they did not advertise a valid BFR-id. This implies they cannot act as BFER or BFIR in that <MT,SD>.

BFER/BFIRにBFR-idが設定されている場合、そのルーターはBIER広告でこの値を広告します。BFR-idが設定されていない場合は、「Invalid BFR-id」の値を広告します。有効なBFR-idは、BIER広告のフラッディング範囲内で一意でなければなりません（MUST）。すべてのBFER/BFIRは、ある<MT,SD>について、有効なBFR-IDが重複して広告されていることを検出しなければなりません（MUST）。そのような重複が検出された場合、重複を広告しているすべてのルーターは、有効なBFR-idを広告しなかったものとして扱われなければなりません（MUST）。これは、それらのルーターがその<MT,SD>においてBFERまたはBFIRとして動作できないことを意味します。

5.3. Logging Misconfiguration

5.3. 設定誤りのログ記録

Whenever an advertisement is received that violates any of the constraints defined in this document, the receiving router MUST support logging this occurrence. Logging SHOULD be dampened to avoid excessive output.

この文書で定義する制約のいずれかに違反する広告を受信したときは常に、受信したルーターはこの事象のログ記録をサポートしなければなりません（MUST）。過剰な出力を避けるために、ログ記録は抑制されるべきです（SHOULD）。

5.4. Flooding Reduction

5.4. フラッディングの削減

It is expected that changes in the BIER domain information that is advertised by IS-IS occur infrequently. If this expectation is not met for an extended period of time (more than a few seconds of burstiness), changes will increase the number of Link State PDU (LSP) updates and negatively impact performance in the network. Implementations SHOULD protect against this possibility by, for example, dampening updates if they occur over an extended period of time.

IS-ISによって広告されるBIERドメイン情報の変更は、まれにしか発生しないことが想定されています。この想定が長期間にわたって満たされない場合（数秒を超えるバースト）、変更によってリンクステートPDU（Link State PDU: LSP）の更新数が増加し、ネットワークの性能に悪影響を及ぼします。実装は、たとえば長期間にわたって更新が発生する場合にそれを抑制することによって、この可能性から保護すべきです（SHOULD）。

6. Packet Formats

6. パケット形式

All IS-IS BIER information is carried within the TLVs 235, 237, [RFC5120], 135 [RFC5305], or 236 [RFC5308].

IS-ISのBIER情報はすべて、TLV 235、237 [RFC5120]、135 [RFC5305]、または236 [RFC5308]の中で運ばれます。

6.1. BIER Info Sub-TLV

6.1. BIER InfoサブTLV

This sub-TLV carries the information for the BIER subdomains that the router participates in as a BFR. This sub-TLV MAY appear multiple times in a given prefix-reachability TLV -- once for each subdomain supported in the associated topology.

このサブTLVは、ルーターがBFRとして参加するBIERサブドメインの情報を運びます。このサブTLVは、あるプレフィックス到達可能性TLV内に、関連するトポロジーでサポートされるサブドメインごとに1回ずつ、複数回出現してもよいです（MAY）。

The sub-TLV advertises a single <MT,SD> combination followed by optional sub-sub-TLVs as described in the following sections.

7. Security Considerations

7. セキュリティーに関する考慮事項

Security concerns for IS-IS are addressed in [RFC5304] and [RFC5310].

IS-ISのセキュリティーに関する懸念は、[RFC5304]と[RFC5310]で扱われています。

The Security Considerations section of [RFC8279] discusses the possibility of performing a Denial-of-Service (DoS) attack by setting too many bits in the BitString of a BIER-encapsulated packet. However, this sort of DoS attack cannot be initiated by modifying the IS-IS BIER advertisements specified in this document. A BFIR decides which systems are to receive a BIER-encapsulated packet. In making this decision, it is not influenced by the IS-IS control messages. When creating the encapsulation, the BFIR sets one bit in the encapsulation for each destination system. The information in the IS-IS BIER advertisements is used to construct the forwarding tables that map each bit in the encapsulation into a set of next hops for the host that is identified by that bit, but it is not used by the BFIR to decide which bits to set. Hence, an attack on the IS-IS control plane cannot be used to cause this sort of DoS attack.

[RFC8279]のセキュリティーに関する考慮事項のセクションでは、BIERでカプセル化されたパケットのBitStringに過剰な数のビットを設定することで、サービス拒否（Denial-of-Service: DoS）攻撃を行える可能性について議論しています。しかし、この種のDoS攻撃は、この文書で規定するIS-ISのBIER広告を改変することでは開始できません。BIERでカプセル化されたパケットをどのシステムが受信するかは、BFIRが決定します。この決定を行う際、BFIRはIS-ISの制御メッセージの影響を受けません。カプセル化を作成するとき、BFIRは宛先システムごとにカプセル化内のビットを1つ設定します。IS-ISのBIER広告の情報は、カプセル化内の各ビットを、そのビットで識別されるホストへのネクストホップの集合に対応付ける転送テーブルを構築するために使用されますが、どのビットを設定するかを決定するためにBFIRがその情報を使用することはありません。したがって、IS-ISのコントロールプレーンへの攻撃を、この種のDoS攻撃を引き起こすために使用することはできません。

While a BIER-encapsulated packet is traversing the network, a BFR that receives a BIER-encapsulated packet with n bits set in its BitString may have to replicate the packet and forward multiple copies. However, a given bit will only be set in one copy of the packet. This means that each transmitted replica of a received packet has fewer bits set (i.e., is targeted to fewer destinations) than the received packet. This is an essential property of the BIER-forwarding process as defined in [RFC8279]. While a failure of this process might cause a DoS attack (as discussed in the Security Considerations of [RFC8279]), such a failure cannot be caused by an attack on the IS-IS control plane.

BIERでカプセル化されたパケットがネットワークを通過する間、BitStringにnビットが設定された、BIERでカプセル化されたパケットを受信したBFRは、パケットを複製して複数のコピーを転送しなければならない場合があります。しかし、あるビットはパケットの1つのコピーにしか設定されません。つまり、受信したパケットの送信される各レプリカは、受信したパケットよりも設定されているビットが少なくなります（すなわち、より少ない宛先を対象とします）。これは、[RFC8279]で定義されているBIER転送処理の本質的な性質です。この処理の障害は（[RFC8279]のセキュリティーに関する考慮事項で議論されているように）DoS攻撃を引き起こすおそれがありますが、そのような障害をIS-ISのコントロールプレーンへの攻撃によって引き起こすことはできません。

Further discussion of BIER-specific security considerations can be found in [RFC8279].

BIER固有のセキュリティーに関する考慮事項についてのさらなる議論は、[RFC8279]にあります。
