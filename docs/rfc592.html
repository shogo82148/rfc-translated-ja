RFC 592

Some Thoughts on System Design to Facilitate Resource Sharing

RFC 592

資源共有を容易にするシステム設計についての考察

INTRODUCTION

はじめに

There is a growing interest in moving toward more resource sharing on the ARPANET. Some resource sharing has been taking place by having systems open TELNET connections and generating user command strings. I think that this is fine for experimental use, but is not the way we want to operate in real usage. What I believe network system builders should do is to develop mechanisms appropriately designed for computer-computer communication.

ARPANETでの資源共有をさらに進めようという関心が高まっています。これまでも、システムがTELNETコネクションを開いてユーザーのコマンド文字列を生成するという方法で、ある程度の資源共有がおこなわれてきました。これは実験的な利用には問題ないと思いますが、実際の運用で望ましいやり方ではありません。ネットワークシステムの構築者がなすべきことは、コンピューター間の通信のために適切に設計されたメカニズムを開発することだと私は考えています。

SYSTEM INTERCONNECTION, AN APPROACH

システム相互接続のひとつのアプローチ

The goal I would like to see us move toward is to view all systems on the network as offering certain service modules, any subset of which can be combined in building other systems. Each service module would have a well advertised set of primitive service capabilities that it could provide. It would have documented commands at the level of present Telnet or FTP commands for gaining access to its services. It would also have a defined network connection procedure. Then any system builder wanting to avail himself of these services could do so and integrate them into his own user interface environment.

私たちが目指すべきだと私が考える目標は、ネットワーク上のすべてのシステムを、何らかのサービスモジュールを提供するものとみなすことです。そして、それらのサービスモジュールの任意の部分集合を組み合わせて、ほかのシステムを構築できるようにします。各サービスモジュールは、提供できるプリミティブなサービス機能の集合をよく周知しておきます。また、そのサービスを利用するための、現在のTelnetやFTPのコマンドと同程度のレベルの、文書化されたコマンドを備えます。さらに、定められたネットワーク接続手順も備えます。そうすれば、これらのサービスを利用したいシステム構築者は誰でもそれを利用し、自分のユーザーインターフェイス環境に統合できます。

At the present time when a system is built, the system builders tend to see it as a stand alone thing or at most something to be used within a specific environment. What I would like to see fostered is the idea that any system built is not only a stand alone environment but also a network service or set of services. The builders would define not only a user interface for their environment, but also a set of primitives and primitive commands that can be accessed by other systems around the network to get that service performed.

現在、システムを構築する際、システム構築者はそれを単独で完結したもの、あるいはせいぜい特定の環境の中で使われるものとみなしがちです。私が広めたいと考えているのは、構築するシステムはすべて、単独で完結した環境であるだけでなく、ネットワークサービスあるいはサービスの集合でもあるという考え方です。構築者は、自分の環境のユーザーインターフェイスを定義するだけでなく、ネットワーク上のほかのシステムがそのサービスを実行させるためにアクセスできるプリミティブとプリミティブなコマンドの集合も定義します。

For example, we are redesigning the NLS Journal in light of our experience and that of Network Mail as a set of protocols and services. If one looks at the processes of the NLS Journal one can see a number of separate services that could be provided by different network sites or combined in varying combinations by a single site. These being:

たとえば、私たちは自分たちの経験とNetwork Mailの経験を踏まえて、NLS Journalをプロトコルとサービスの集合として再設計しているところです。NLS Journalの処理を見てみると、別々のネットワークサイトが提供することも、単一のサイトがさまざまな組み合わせで組み合わせることもできる、いくつかの独立したサービスがあることがわかります。それらは次のとおりです。

Distribution (identification of addressees and maintainance of the required data bases being a related service), recording (numbering and storing of items), cataloging, and retrieval.

配布（宛先の特定と、必要なデータベースの保守は関連するサービスです）、記録（項目の採番と保存）、目録作成、検索。

At the moment these services are fairly tightly interconnected in the NLS Journal and what we want to do is to decouple them and define their intercommunication by protocols that would allow them to be distributed in different hosts on the network. Mechanisms would also be defined for the several hosts performing similar services around the network to work together cooperatively.

現時点では、これらのサービスはNLS Journalの中でかなり密に結びついています。私たちがやりたいのは、それらを切り離し、ネットワーク上の別々のホストに分散できるようなプロトコルによって相互の通信を定義することです。また、ネットワーク上で同様のサービスを実行する複数のホストが協調して動作するためのメカニズムも定義することになるでしょう。

As a further example, there are also other services that NLS could probably provide such as structured file creation and manipulation; information portrayal online or in hardcopy; database querying etc. However, at the moment the system is not explicitly structured from the point of view that outside systems could come into it anywhere but at the human user interface even though internally it is quite modular. It would be straightforward for us to identify those NLS services that other system builders might possibly be interested in incorporating into their systems with their own user interface and then to do the restructuring and primitive command definition necessary. Other groups building systems on the network could perform a similar examination.

さらに別の例として、NLSはほかにも、構造化ファイルの作成と操作、オンラインまたはハードコピーでの情報の表示、データベースの問い合わせなどのサービスを提供できるでしょう。しかし現時点では、内部的にはかなりモジュール化されているものの、外部のシステムが人間のユーザーインターフェイス以外の場所から入り込めるという観点では、このシステムは明示的に構造化されていません。ほかのシステム構築者が独自のユーザーインターフェイスとともに自分のシステムに組み込むことに関心を持ちそうなNLSのサービスを特定し、そのうえで必要な再構成とプリミティブなコマンドの定義をおこなうことは、私たちにとっては簡単なことでしょう。ネットワーク上でシステムを構築しているほかのグループも、同様の検討をおこなえるでしょう。

CCA, on the other hand as I understand it, has taken this point of view from the beginning, namely building the Datacomputer on the assumption that it is primarily a network resource and is to be used by other systems. BBN is also moving in this direction in the design of Distributed TENEX.

一方、私の理解では、CCAは最初からこの観点を採っています。すなわち、Datacomputerは主としてネットワーク資源であり、ほかのシステムから使われるものだという前提に立って構築しています。BBNもDistributed TENEXの設計において、この方向に進んでいます。

There is nothing new in the above ideas; they come from generalizing past successes we have all had with network protocol development and with good software engineering practices. It will, however, take a change in the thinking of system designers, some concrete examples, and ongoing dialog to make such a design philosophy the normal network way of life.

上記の考え方に新しいものは何もありません。これらは、ネットワークプロトコルの開発や優れたソフトウェア工学の実践において私たち全員が収めてきた過去の成功を一般化したものです。しかし、このような設計思想をネットワークにおける当たり前の流儀にするには、システム設計者の考え方の変化と、いくつかの具体例と、継続的な対話が必要になるでしょう。

SOME FUNCTIONS READY FOR INTERCONNECTION

相互接続の準備が整ったいくつかの機能

The area of dialog support may be the first area ripe to create such a synthesis with the several systems in or coming into existence, each solves part of the problem (with some overlap). The dialog support systems on the network known to me are:

このような統合をおこなう機が最初に熟している分野は、対話支援の分野かもしれません。この分野では、いくつかのシステムがすでに存在するか、登場しつつあり、それぞれが（いくらか重複しながら）問題の一部を解決しています。私が知っているネットワーク上の対話支援システムは次のとおりです。

The NLS Journal (supports recorded and cataloged dialog and linked networks of documents and messages).

NLS Journal（記録され目録化された対話と、文書やメッセージをリンクしたネットワークをサポートします）。

NLS Screen linking and splitting (supports close collaboration of two or more people working together in real time in NLS)

NLSの画面のリンクと分割（NLSでリアルタイムに共同作業する2人以上の人々の緊密な協調をサポートします）

The network wide linking of terminals through BBN's RSEXEC.

BBNのRSEXECによる、ネットワーク全体での端末のリンク。

Tenex Sndmsg and Readmail and other mail systems support nonrecorded dialog and further manipulation of received messages. (Some interconnection between NLS and these facilities has been established).

TenexのSndmsgとReadmail、その他のメールシステムは、記録されない対話と、受信したメッセージに対するさらなる操作をサポートします（NLSとこれらの機能の間には、いくらかの相互接続が確立されています）。

The communication system under design at USC-ISI to support a range of message services.

さまざまなメッセージサービスをサポートするためにUSC-ISIで設計中の通信システム。

The online conferencing system being built by Jim Calvin of Case, John Iseli of Mitre and others supports online conferencing of several members and has facilities to utilize various Tenex subsystems such as TECO and NLS to support conferees.

CaseのJim Calvin、MitreのJohn Iseliらが構築しているオンライン会議システムは、複数のメンバーによるオンライン会議をサポートし、会議参加者を支援するためにTECOやNLSなどのさまざまなTenexサブシステムを利用する機能を備えています。

The Hack system of CASE offers a bulletin board service.

CASEのHackシステムは、掲示板サービスを提供しています。

The Forum system of IFF supports online and distributed in time conferencing and other features.

IFFのForumシステムは、オンライン会議や時間的に分散した会議、その他の機能をサポートしています。

Other areas possibly ripe for synthesis are 1) file and data management, and information retrieval services; 2) editing and hardcopy portrayal with systems like Tenex RUNOFF, SU-AI's PUB and SRI-ARC's Output Processor.

統合の機が熟していると思われるほかの分野は、1) ファイルとデータの管理、および情報検索のサービス、2) TenexのRUNOFF、SU-AIのPUB、SRI-ARCのOutput Processorのようなシステムによる編集とハードコピーの表示です。

If the salient service features, concepts, goals of each could be defined clearly and appropriate service primitives, as per other ARPANET protocols, could be defined for each, anyone wishing to incorporate that service with a user interface appropriate to his environment or philosophy could do so.

それぞれの主要なサービスの特徴、概念、目標を明確に定義でき、ほかのARPANETプロトコルと同様に、それぞれについて適切なサービスプリミティブを定義できれば、自分の環境や思想に合ったユーザーインターフェイスとともにそのサービスを組み込みたい人は誰でもそうできるようになります。

SYSTEM INTERCONNECTION ISSUES RELATED TO THE ABOVE PROPOSAL

上記の提案に関するシステム相互接続の課題

There are many detailed issues related to system interconnection as proposed above. A number seem worth mentioning here.

上記で提案したようなシステム相互接続には、細かな課題がたくさんあります。そのうちのいくつかは、ここで言及しておく価値がありそうです。

1) Types of Network Connections
The number and type of network connections to be opened between classes of cooperating processes can probably be systematized. One of the important elements of the FTP and Graphics protocol efforts was to define the number and type of connections necessary for these classes of transaction. Similar classification and connection definition will be required for other types of processes.
2) Data Structure Translation

The whole area of translation and transfer of data structures more complicated than sequential files needs vigorous thought and protocol development.

Systems built around sequential files are presently dominant on the ARPANET and provide a base for simple useful economical tools. I, however, do not believe that the longer run tool sharing can depend on communication between sequential files, but requires structured files. Experience with NLS tree structured files shows that even this level of structuring may be inadequate for many uses and more sophistication may be required. A similar trend exists in work with computer graphics and generalized data management systems. Developing protocols for handling structured data bases or agreement on common structuring characteristics seems an important need.

3) Responsiveness
Factors influencing responsiveness to users in an environment of heavy geographically separated resource sharing need determination and discussion.
4) Documentation of System Interfaces
It is probably reasonably straightforward to define service interfaces, but they will be useless unless their activating command languages and other conventions are well documented and this documentation is kept up to date.
5) Accounting
A very difficult problem once you interconnect systems at lower levels is to design an appropriate network accounting and banking system that will not cause undue delays in accessing distributed resources.
6) Error Handling
We need to develop mechanisms for passing error signals around when system environments are crossing machine boundaries.
7) Standard Parameter Formats
Data types such as strings, integers, floating point numbers, arrays, pointers, etc. need to have standard representations defined for passing parameters back and forth between machines.
8) HELP at the Procedure Call Level
A HELP mechanism needs to be defined in the protocols to provide information that each designer can translate to his user interface. Standards for requesting HELP information and structuring HELP data bases needs agreement.
1) ネットワークコネクションの種類
協調するプロセスのクラスの間で開くネットワークコネクションの数と種類は、おそらく体系化できるでしょう。FTPとGraphicsプロトコルの取り組みの重要な要素のひとつは、これらのクラスのトランザクションに必要なコネクションの数と種類を定義することでした。ほかの種類のプロセスについても、同様の分類とコネクションの定義が必要になるでしょう。
2) データ構造の変換

シーケンシャルファイルより複雑なデータ構造の変換と転送の分野全体について、精力的な検討とプロトコルの開発が必要です。

現在ARPANETでは、シーケンシャルファイルを中心に構築されたシステムが主流であり、シンプルで有用かつ経済的なツールの基盤となっています。しかし私は、より長期的なツールの共有がシーケンシャルファイル間の通信に依存できるとは考えておらず、構造化ファイルが必要だと考えています。NLSの木構造ファイルでの経験から、このレベルの構造化でさえ多くの用途には不十分であり、さらに高度なものが必要になるかもしれないことがわかっています。コンピューターグラフィックスや汎用データ管理システムの作業にも同様の傾向があります。構造化データベースを扱うためのプロトコルの開発、あるいは共通の構造化の特徴についての合意は、重要なニーズであると思われます。

3) 応答性
地理的に離れた資源を大量に共有する環境において、ユーザーに対する応答性に影響を与える要因を明らかにし、議論する必要があります。
4) システムインターフェイスの文書化
サービスインターフェイスを定義することは、おそらくかなり簡単でしょう。しかし、それを起動するコマンド言語やその他の規約がよく文書化され、その文書が最新の状態に保たれていなければ、サービスインターフェイスは役に立たないでしょう。
5) 課金
システムを低いレベルで相互接続すると、非常に難しい問題になるのが、分散した資源へのアクセスに過度の遅延を生じさせない、適切なネットワークの課金と決済のシステムを設計することです。
6) エラー処理
システム環境がマシンの境界をまたぐ場合に、エラーシグナルを受け渡すためのメカニズムを開発する必要があります。
7) 標準のパラメーター形式
マシン間でパラメーターをやりとりするために、文字列、整数、浮動小数点数、配列、ポインターなどのデータ型について標準の表現を定義する必要があります。
8) 手続き呼び出しレベルでのHELP
各設計者が自分のユーザーインターフェイスに合わせて変換できる情報を提供するために、HELPメカニズムをプロトコルの中で定義する必要があります。HELP情報を要求するための標準と、HELPデータベースを構造化するための標準について、合意が必要です。
