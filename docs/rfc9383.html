SPAKE2+, an Augmented Password-Authenticated Key Exchange (PAKE) Protocol

RFC 9383

SPAKE2+：拡張パスワード認証鍵交換（PAKE）プロトコル

Abstract

概要

This document describes SPAKE2+, a Password-Authenticated Key Exchange (PAKE) protocol run between two parties for deriving a strong shared key with no risk of disclosing the password. SPAKE2+ is an augmented PAKE protocol, as only one party has knowledge of the password. This method is simple to implement, compatible with any prime-order group, and computationally efficient.

この文書では、SPAKE2+について説明します。SPAKE2+は、パスワードを漏洩させる危険なしに強力な共有鍵を導出するために2者の間で実行される、パスワード認証鍵交換（Password-Authenticated Key Exchange; PAKE）プロトコルです。 一方の当事者だけがパスワードを知っているので、SPAKE2+は拡張PAKE（augmented PAKE）プロトコルです。 この方法は実装が簡単で、任意の素数位数の群に対応しており、計算効率が高いです。

1. Introduction

1. はじめに

This document describes SPAKE2+, a Password-Authenticated Key Exchange (PAKE) protocol run between two parties for deriving a strong shared key with no risk of disclosing the password. SPAKE2+ is an augmented PAKE protocol, as only one party makes direct use of the password during the execution of the protocol. The other party only needs a record corresponding to the first party's registration at the time of the protocol execution instead of the password. This record can be computed once, during an offline registration phase. The party using the password directly would typically be a client and would act as a Prover, while the other party would be a server and would act as a Verifier.

この文書では、SPAKE2+について説明します。SPAKE2+は、パスワードを漏洩させる危険なしに強力な共有鍵を導出するために2者の間で実行される、パスワード認証鍵交換（Password-Authenticated Key Exchange; PAKE）プロトコルです。 プロトコルの実行中にパスワードを直接使用するのは一方の当事者だけなので、SPAKE2+は拡張PAKE（augmented PAKE）プロトコルです。 もう一方の当事者は、プロトコルの実行時にパスワードの代わりに、最初の当事者の登録に対応する記録だけを必要とします。 この記録は、オフラインの登録フェーズの間に一度だけ計算できます。 パスワードを直接使用する当事者は、通常はクライアントであり、証明者（Prover）として動作します。 一方、もう一方の当事者はサーバーであり、検証者（Verifier）として動作します。

The protocol is augmented in the sense that it provides some resilience against the compromise or extraction of the registration record. The design of the protocol forces the adversary to recover the password from the record to successfully execute the protocol. Hence, this protocol can be advantageously combined with a salted Password Hashing Function to increase the cost of the recovery and slow down attacks. The record cannot be used directly to successfully run the protocol as a Prover, making this protocol more robust than balanced PAKEs, which don't benefit from Password Hashing Functions to the same extent.

このプロトコルは、登録記録の侵害や抽出に対してある程度の耐性を提供するという意味で拡張されています。 このプロトコルの設計では、敵対者がプロトコルの実行に成功するには、記録からパスワードを復元しなければなりません。 したがって、このプロトコルをソルト付きのパスワードハッシュ関数（Password Hashing Function）と組み合わせることで、復元のコストを増やして攻撃を遅らせるという利点が得られます。 記録を直接使用して証明者としてプロトコルを成功裏に実行することはできません。 そのため、このプロトコルは、パスワードハッシュ関数から同程度の恩恵を受けられない平衡型のPAKE（balanced PAKE）よりも堅牢です。

This augmented property is especially valuable in scenarios where the execution of the protocol is constrained and the adversary cannot query the salt of the Password Hashing Function ahead of the attack. For example, a constraint may be when physical proximity through a local network is required or when a first authentication factor is required for initiation of the protocol.

この拡張された性質は、プロトコルの実行が制約されており、敵対者が攻撃に先立ってパスワードハッシュ関数のソルトを問い合わせることができないシナリオで特に価値があります。 たとえば、ローカルネットワークを介した物理的な近接性が要求される場合や、プロトコルの開始に第1の認証要素が要求される場合が、そのような制約になり得ます。

This document has content split out from a related document, [RFC9382], which specifies SPAKE2. SPAKE2 is a symmetric PAKE protocol, where both parties have knowledge of the password. SPAKE2+ is the asymmetric or augmented version of SPAKE2, wherein only one party has knowledge of the password. SPAKE2+ is specified separately in this document because the use cases for symmetric and augmented PAKEs are different and therefore warrant different technical specifications. Neither SPAKE2 nor SPAKE2+ was selected as the result of the Crypto Forum Research Group (CFRG) PAKE selection competition. However, this password-based key exchange protocol appears in [TDH] and is proven secure in [SPAKE2P-Analysis]. It is compatible with any prime-order group and relies only on group operations, making it simple and computationally efficient. Thus, it was felt that publication was beneficial to make the protocol available for wider consideration.

この文書は、SPAKE2を規定する関連文書[RFC9382]から内容を分割したものです。 SPAKE2は対称PAKEプロトコルであり、両方の当事者がパスワードを知っています。 SPAKE2+はSPAKE2の非対称版、すなわち拡張版であり、一方の当事者だけがパスワードを知っています。 対称PAKEと拡張PAKEではユースケースが異なり、したがって異なる技術仕様が必要になるため、SPAKE2+はこの文書で別途規定します。 SPAKE2とSPAKE2+のいずれも、Crypto Forum Research Group（CFRG）のPAKE選定コンペティションの結果として選定されたものではありません。 しかし、このパスワードベースの鍵交換プロトコルは[TDH]に登場しており、[SPAKE2P-Analysis]で安全性が証明されています。 このプロトコルは任意の素数位数の群に対応しており、群の演算だけに依存しているので、簡単で計算効率が高いです。 そのため、このプロトコルをより広く検討できるようにするために、公開することは有益であると考えられました。

This document was produced outside of the IETF and IRTF and represents the opinions of the authors. Publication of this document as an RFC in the Independent Submissions Stream does not imply endorsement of SPAKE2+ by the IETF or IRTF.

3. Definition of SPAKE2+

3. SPAKE2+の定義

Let G be a group in which the computational Diffie-Hellman (CDH) problem is hard. Suppose G has order p*h where p is a large prime; h will be called the cofactor. Let I be the unit element in G, e.g., the point at infinity if G is an elliptic curve group. We denote the operations in the group additively. We assume that there is a representation of elements of G as byte strings: common choices would be SEC 1 uncompressed or compressed [SEC1] for elliptic curve groups or big-endian integers of a fixed (per-group) length for prime field DH. We fix a generator P of the (large) prime-order subgroup of G. P is specified in the document defining the group, and so we do not repeat it here.

Gを、計算Diffie-Hellman（CDH）問題が困難である群とします。 Gの位数はp*hであるとします。ここで、pは大きな素数であり、hを余因子（cofactor）と呼びます。 IをGの単位元とします。たとえば、Gが楕円曲線群であれば無限遠点です。 群の演算は加法的に表記します。 Gの元はバイト列として表現できるものとします。一般的な選択肢は、楕円曲線群であればSEC1[SEC1]の非圧縮形式または圧縮形式、素体のDHであれば（群ごとに）固定長のビッグエンディアン整数です。 Gの（大きな）素数位数の部分群の生成元Pを固定します。Pはその群を定義している文書で規定されているため、ここでは繰り返しません。

|| denotes concatenation of strings. We also let len(S) denote the length of a string in bytes, represented as an eight-byte little-endian number. Finally, let nil represent an empty string, i.e., len(nil) = 0.

||は文字列の連結を表します。 また、len(S)は文字列のバイト単位の長さを表し、8バイトのリトルエンディアンの数値として表現します。 最後に、nilは空文字列を表します。つまり、len(nil) = 0です。

KDF is a key derivation function that takes as input a salt, input keying material (IKM), info string, and derived key length L to derive a cryptographic key of length L. MAC is a Message Authentication Code algorithm that takes a secret key and message as input to produce an output. Let Hash be a hash function from arbitrary strings to bit strings of a fixed length. Common choices for Hash are SHA256 or SHA512 [RFC6234]. Section 4 specifies variants of KDF, MAC, and Hash suitable for use with the protocols contained herein.

KDFは鍵導出関数であり、ソルト、入力鍵素材（input keying material; IKM）、info文字列、導出する鍵の長さLを入力として受け取り、長さLの暗号鍵を導出します。 MACはメッセージ認証コード（Message Authentication Code）のアルゴリズムであり、秘密鍵とメッセージを入力として受け取り、出力を生成します。 Hashを、任意の文字列から固定長のビット列へのハッシュ関数とします。 Hashの一般的な選択肢は、SHA256またはSHA512[RFC6234]です。 Section 4では、ここに含まれるプロトコルでの使用に適したKDF、MAC、Hashの種類を規定します。

Let there be two parties, a Prover and a Verifier. Their identities, denoted as idProver and idVerifier, may also have digital representations such as Media Access Control addresses or other names (hostnames, usernames, etc.). The parties may share additional data (the context) separate from their identities, which they may want to include in the protocol transcript. One example of additional data is a list of supported protocol versions if SPAKE2+ were used in a higher-level protocol that negotiates the use of a particular PAKE. Another example is the inclusion of the application name. Including these data points would ensure that both parties agree upon the same set of supported protocols and therefore prevents downgrade and cross-protocol attacks. Specification of precise context values is out of scope for this document.

証明者と検証者という2つの当事者がいるとします。 idProverとidVerifierで表される両者のアイデンティティーは、メディアアクセス制御（Media Access Control）アドレスやその他の名前（ホスト名、ユーザー名など）のようなデジタル表現を持つ場合もあります。 両者は、アイデンティティーとは別に追加のデータ（コンテキスト）を共有している場合があり、それをプロトコルのトランスクリプトに含めたいと考えることがあります。 追加のデータの一例は、特定のPAKEの使用をネゴシエートする上位のプロトコルでSPAKE2+を使用する場合の、サポートするプロトコルバージョンの一覧です。 別の例として、アプリケーション名を含めることが挙げられます。 これらのデータを含めることで、両者がサポートするプロトコルの同じ集合について合意することが保証され、したがってダウングレード攻撃やクロスプロトコル攻撃を防げます。 コンテキストの値の厳密な規定は、この文書の範囲外です。

3.1. Protocol Overview

3.1. プロトコルの概要

SPAKE2+ is a two-round protocol that establishes a shared secret with an additional round for key confirmation. Prior to invocation, both parties are provisioned with information such as the input password needed to run the protocol. The registration phase may include communicating identities, protocol version, and other parameters related to the registration record; see Section 3.2 for details.

SPAKE2+は、共有秘密を確立する2ラウンドのプロトコルであり、鍵確認のための追加のラウンドがあります。 呼び出しの前に、両方の当事者には、プロトコルの実行に必要な入力パスワードなどの情報がプロビジョニングされます。 登録フェーズには、アイデンティティー、プロトコルバージョン、および登録記録に関連するその他のパラメーターの通信が含まれる場合があります。詳細についてはSection 3.2を参照してください。

During the first round, the Prover sends a public share, shareP, to the Verifier, which in turn responds with its own public share, shareV. Both parties then derive a shared secret used to produce encryption and authentication keys. The latter are used during the second round for key confirmation. (Section 3.4 details the key derivation and confirmation steps.) In particular, the Verifier sends a key confirmation message, confirmV, to the Prover, which in turn responds with its own key confirmation message, confirmP. (Note that shareV and confirmV MAY be sent in the same message.) Both parties MUST NOT consider the protocol complete prior to receipt and validation of these key confirmation messages.

第1ラウンドでは、証明者が公開共有値（public share）sharePを検証者に送信し、検証者は自身の公開共有値shareVで応答します。 その後、両方の当事者が、暗号化鍵と認証鍵の生成に使用する共有秘密を導出します。 後者は、第2ラウンドで鍵確認に使用されます（鍵の導出と確認の手順についてはSection 3.4で詳しく説明します）。 具体的には、検証者は鍵確認メッセージconfirmVを証明者に送信し、証明者は自身の鍵確認メッセージconfirmPで応答します。 （shareVとconfirmVは同じメッセージで送信してもよいです（MAY）。） 両方の当事者は、これらの鍵確認メッセージを受信して検証するまで、プロトコルが完了したとみなしてはなりません（MUST NOT）。

3.2. Offline Registration

3.2. オフライン登録

The registration phase computes the values w0 and w1, as well as the registration record L=w1*P.  w0 and w1 are derived by hashing the password pw with the identities of the two participants.  w0 and the record L are then shared with the Verifier and stored as part of the registration record associated with the Prover. The Prover SHOULD derive w0 and w1 from the password before the protocol begins. Both w0 and w1 are derived using a function with range [0, p-1], which is modeled as a random oracle in [SPAKE2P-Analysis].

登録フェーズでは、値w0とw1、および登録記録L=w1*Pを計算します。 w0とw1は、パスワードpwを2者の参加者のアイデンティティーとともにハッシュすることで導出します。 その後、w0と記録Lは検証者と共有され、証明者に関連付けられた登録記録の一部として保存されます。 証明者は、プロトコルの開始前にパスワードからw0とw1を導出すべきです（SHOULD）。 w0とw1はどちらも、値域が[0, p-1]である関数を使用して導出します。この関数は、[SPAKE2P-Analysis]ではランダムオラクルとしてモデル化されています。

The registration phase also produces two random elements, M and N, in the prime-order subgroup of G. The algorithm for selecting M and N is defined in Appendix B. Importantly, this algorithm chooses M and N such that their discrete logs are not known. Precomputed values for M and N are listed in Section 4 for each group. Applications MAY use different M and N values, provided they are computed, e.g., using different input seeds to the algorithm in Appendix B, as random elements for which the discrete log is unknown.

登録フェーズでは、Gの素数位数の部分群に属する2つのランダムな元MとNも生成します。 MとNを選択するアルゴリズムはAppendix Bで定義します。 重要な点として、このアルゴリズムは、離散対数が知られていないようにMとNを選択します。 各群について事前に計算したMとNの値をSection 4に示します。 アプリケーションは、離散対数が知られていないランダムな元として計算される限り、異なるMとNの値を使用してもよいです（MAY）。たとえば、Appendix Bのアルゴリズムに異なる入力シードを与えて計算することができます。

Applications using this specification MUST define the method used to compute w0 and w1. For example, it may be necessary to carry out various forms of normalization of the password before hashing [RFC8265]. This section contains requirements and default recommendations for computing w0 and w1.

この仕様を使用するアプリケーションは、w0とw1の計算に使用する方法を定義しなければなりません（MUST）。 たとえば、ハッシュの前に、パスワードに対してさまざまな形式の正規化を行う必要があるかもしれません[RFC8265]。 このセクションには、w0とw1の計算に関する要件と、デフォルトの推奨事項が含まれています。

The RECOMMENDED method for generating w0 and w1 is via a Password-Based Key Derivation Function (PBKDF), which is a function designed to slow down brute-force attackers. Brute-force resistance may be obtained through various computation hardness parameters such as memory or CPU cycles and are typically configurable. The scrypt [RFC7914] function and the Argon2id [RFC9106] function are common examples of PBKDFs. Absent an application-specific profile, RECOMMENDED parameters (N, r, p) for scrypt are (32768,8,1), and RECOMMENDED parameters for Argon2id are in Section 4 of [RFC9106].

w0とw1を生成する方法として、パスワードベースの鍵導出関数（Password-Based Key Derivation Function; PBKDF）を使用することが推奨されます（RECOMMENDED）。PBKDFは、総当たり攻撃者の速度を落とすために設計された関数です。 総当たり攻撃への耐性は、メモリーやCPUサイクルなどのさまざまな計算困難性パラメーターによって得られ、これらは通常は設定可能です。 scrypt[RFC7914]関数とArgon2id[RFC9106]関数は、PBKDFの一般的な例です。 アプリケーション固有のプロファイルがない場合、scryptのパラメーター（N, r, p）としては(32768,8,1)が推奨されます（RECOMMENDED）。Argon2idのパラメーターとしては、[RFC9106]のSection 4に記載されているものが推奨されます（RECOMMENDED）。

Each half of the output of the PBKDF will be interpreted as an integer and reduced modulo p. To control bias, each half must be of length at least ceil(log2(p)) + k bits, with k >= 64. Reducing such integers mod p gives bias at most 2^-k for any p; this bias is negligible for any k >= 64.

PBKDFの出力の各半分は整数として解釈され、pを法として剰余をとります。 偏りを抑えるために、各半分の長さは少なくともceil(log2(p)) + kビットである必要があります。ここで、k >= 64です。 このような整数のmod pをとると、任意のpについて偏りは高々2^-kになります。この偏りは、k >= 64であれば無視できます。

The minimum total output length of the PBKDF then is 2 * (ceil(log2(p)) + k) bits. For example, given the prime order of the P-256 curve, the output of the PBKDF SHOULD be at least 640 bits or 80 bytes.

したがって、PBKDFの出力の最小の合計長は2 * (ceil(log2(p)) + k)ビットです。 たとえば、P-256曲線の素数位数を考えると、PBKDFの出力は少なくとも640ビット、すなわち80バイトであるべきです（SHOULD）。

Given a PBKDF, password pw, and identities idProver and idVerifier, the RECOMMENDED method for computing w0 and w1 is as follows:

PBKDF、パスワードpw、アイデンティティーidProverとidVerifierが与えられた場合、w0とw1を計算する方法として次の方法が推奨されます（RECOMMENDED）。

w0s || w1s = PBKDF(len(pw) || pw ||
                   len(idProver) || idProver ||
                   len(idVerifier) || idVerifier)
w0 = w0s mod p
w1 = w1s mod p

w0s || w1s = PBKDF(len(pw) || pw ||
                   len(idProver) || idProver ||
                   len(idVerifier) || idVerifier)
w0 = w0s mod p
w1 = w1s mod p

If an identity is unknown at the time of computing w0s or w1s, its length is given as zero and the identity itself is represented as an empty octet string. If both idProver and idVerifier are unknown, then their lengths are given as zero and both identities will be represented as empty octet strings.  idProver and idVerifier are included in the transcript TT as part of the protocol flow.

w0sまたはw1sの計算時にアイデンティティーが不明な場合、その長さは0とし、アイデンティティー自体は空のオクテット文字列として表現します。 idProverとidVerifierの両方が不明な場合、それらの長さは0とし、両方のアイデンティティーを空のオクテット文字列として表現します。 idProverとidVerifierは、プロトコルの流れの一部としてトランスクリプトTTに含まれます。

3.3. Online Authentication

3.3. オンライン認証

The online SPAKE2+ protocol runs between the Prover and Verifier to produce a single shared secret upon completion. To begin, the Prover selects x uniformly at random from the integers in [0, p-1], computes the public share shareP=X, and transmits it to the Verifier.

オンラインのSPAKE2+プロトコルは、証明者と検証者の間で実行され、完了時に単一の共有秘密を生成します。 まず、証明者は[0, p-1]の整数から一様ランダムにxを選択し、公開共有値shareP=Xを計算して、検証者に送信します。

x <- [0, p-1]
X = x*P + w0*M

x <- [0, p-1]
X = x*P + w0*M

Upon receipt of X, the Verifier checks the received element for group membership and aborts if X is not in the large prime-order subgroup of G; see Section 6 for details. The Verifier then selects y uniformly at random from the integers in [0, p-1], computes the public share shareV=Y, and transmits it to the Prover. Upon receipt of Y, the Prover checks the received element for group membership and aborts if Y is not in the large prime-order subgroup of G.

Xを受信すると、検証者は受信した元が群に属するかどうかを確認し、XがGの大きな素数位数の部分群に属していない場合は中断します。詳細についてはSection 6を参照してください。 次に、検証者は[0, p-1]の整数から一様ランダムにyを選択し、公開共有値shareV=Yを計算して、証明者に送信します。 Yを受信すると、証明者は受信した元が群に属するかどうかを確認し、YがGの大きな素数位数の部分群に属していない場合は中断します。

y <- [0, p-1]
Y = y*P + w0*N

y <- [0, p-1]
Y = y*P + w0*N

Both participants compute Z and V; Z and V are then shared as common values. The Prover computes:

両方の参加者がZとVを計算します。その後、ZとVは共通の値として共有されます。 証明者は次のように計算します。

Z = h*x*(Y - w0*N)
V = h*w1*(Y - w0*N)

Z = h*x*(Y - w0*N)
V = h*w1*(Y - w0*N)

The Verifier computes:

検証者は次のように計算します。

Z = h*y*(X - w0*M)
V = h*y*L

Z = h*y*(X - w0*M)
V = h*y*L

The multiplication by the cofactor h prevents small subgroup confinement attacks. All proofs of security hold even if the discrete log of the fixed group element N is known to the adversary. In particular, one MAY set N=I, i.e., set N to the unit element in G.

余因子hを掛けることで、小さな部分群への閉じ込め攻撃（small subgroup confinement attack）を防げます。 安全性の証明はすべて、固定された群の元Nの離散対数を敵対者が知っている場合でも成り立ちます。 特に、N=Iに設定してもよいです（MAY）。つまり、NをGの単位元に設定できます。

鍵素材を導出する際には、ZとVの両方をトランスクリプトと組み合わせて使用することが不可欠です。 プロトコルのトランスクリプトのエンコーディングを以下に示します。

Context is an application-specific customization string shared between both parties and MUST precede the remaining transcript. It might contain the name and version number of the higher-level protocol, or simply the name and version number of the application. The context MAY include additional data such as the chosen ciphersuite and PBKDF parameters like the iteration count or salt. The context and its length prefix MAY be omitted.

Contextは、両方の当事者の間で共有されるアプリケーション固有のカスタマイズ文字列です。 Contextは、トランスクリプトの残りの部分より前に置かなければなりません（MUST）。 Contextには、上位のプロトコルの名前とバージョン番号、または単にアプリケーションの名前とバージョン番号が含まれる場合があります。 コンテキストには、選択した暗号スイートや、反復回数やソルトなどのPBKDFのパラメーターといった追加のデータを含めてもよいです（MAY）。 コンテキストとその長さのプレフィックスは省略してもよいです（MAY）。

If an identity is absent, its length is given as zero and the identity itself is represented as an empty octet string. If both identities are absent, then their lengths are given as zero and both are represented as empty octet strings. In applications where identities are not implicit, idProver and idVerifier SHOULD always be non-empty. Otherwise, the protocol risks unknown key-share attacks (discussion of unknown key-share attacks in a specific protocol is given in [RFC8844]).

アイデンティティーが存在しない場合、その長さは0とし、アイデンティティー自体は空のオクテット文字列として表現します。 両方のアイデンティティーが存在しない場合、それらの長さは0とし、両方を空のオクテット文字列として表現します。 アイデンティティーが暗黙的でないアプリケーションでは、idProverとidVerifierは常に空でないべきです（SHOULD）。 そうしないと、プロトコルは未知鍵共有攻撃（unknown key-share attack）の危険にさらされます（特定のプロトコルにおける未知鍵共有攻撃の議論は[RFC8844]にあります）。

Upon completion of this protocol, both parties compute shared secrets K_main, K_shared, K_confirmP, and K_confirmV as specified in Section 3.4. The Verifier MUST send a key confirmation message, confirmV, to the Prover so both parties can confirm that they agree upon these shared secrets. After receipt and verification of the Verifier's confirmation message, the Prover MUST respond with its confirmation message. The Verifier MUST NOT send application data to the Prover until it has received and verified the confirmation message. Key confirmation verification requires recomputation of confirmP or confirmV and checking for equality against the data that was received.

このプロトコルの完了時に、両方の当事者はSection 3.4で規定されているように、共有秘密K_main、K_shared、K_confirmP、K_confirmVを計算します。 両方の当事者がこれらの共有秘密について合意していることを確認できるように、検証者は鍵確認メッセージconfirmVを証明者に送信しなければなりません（MUST）。 検証者の確認メッセージを受信して検証した後、証明者は自身の確認メッセージで応答しなければなりません（MUST）。 検証者は、確認メッセージを受信して検証するまで、証明者にアプリケーションデータを送信してはなりません（MUST NOT）。 鍵確認の検証では、confirmPまたはconfirmVを再計算し、受信したデータと等しいかどうかを確認する必要があります。

3.4. Key Schedule and Key Confirmation

3.4. 鍵スケジュールと鍵確認

The protocol transcript TT, as defined in Section 3.3, is unique and secret to the participants. Both parties use TT to derive the shared symmetric secret K_main from the protocol. The length of K_main is equal to the length of the digest output, e.g., 256 bits for Hash() = SHA-256. The confirmation keys K_confirmP and K_confirmV, as well as the shared key K_shared, are derived from K_main.

Section 3.3で定義したプロトコルのトランスクリプトTTは、一意であり、参加者にとって秘密です。 両方の当事者は、TTを使用して、プロトコルから共有された対称の秘密K_mainを導出します。 K_mainの長さは、ダイジェスト出力の長さと等しくなります。たとえば、Hash() = SHA-256の場合は256ビットです。 確認鍵K_confirmPとK_confirmV、および共有鍵K_sharedは、K_mainから導出します。

K_main = Hash(TT)
K_confirmP || K_confirmV = KDF(nil, K_main, "ConfirmationKeys")
K_shared = KDF(nil, K_main, "SharedKey")

K_main = Hash(TT)
K_confirmP || K_confirmV = KDF(nil, K_main, "ConfirmationKeys")
K_shared = KDF(nil, K_main, "SharedKey")

Neither K_main nor its derived confirmation keys are used for anything except key derivation and confirmation and MUST be discarded after the protocol execution. Applications MAY derive additional keys from K_shared as needed.

K_mainとそこから導出された確認鍵は、鍵の導出と確認以外の用途には使用されず、プロトコルの実行後に破棄しなければなりません（MUST）。 アプリケーションは、必要に応じてK_sharedから追加の鍵を導出してもよいです（MAY）。

The length of each confirmation key is dependent on the MAC function of the chosen ciphersuite. For HMAC, the RECOMMENDED key length is equal to the output length of the digest output, e.g., 256 bits for Hash() = SHA-256. For CMAC-AES, each confirmation key MUST be of length k, where k is the chosen AES key size, e.g., 128 bits for CMAC-AES-128.

各確認鍵の長さは、選択した暗号スイートのMAC関数に依存します。 HMACの場合、鍵長はダイジェスト出力の出力長と等しくすることが推奨されます（RECOMMENDED）。たとえば、Hash() = SHA-256の場合は256ビットです。 CMAC-AESの場合、各確認鍵の長さはkでなければなりません（MUST）。ここで、kは選択したAESの鍵サイズであり、たとえばCMAC-AES-128の場合は128ビットです。

Both endpoints MUST employ a MAC that produces pseudorandom tags for key confirmation. K_confirmP and K_confirmV are symmetric keys used to compute tags confirmP and confirmV over the public key shares received from the other peer earlier.

両方のエンドポイントは、鍵確認のために疑似ランダムなタグを生成するMACを使用しなければなりません（MUST）。 K_confirmPとK_confirmVは、先に相手のピアから受信した公開鍵の共有値に対するタグconfirmPとconfirmVを計算するために使用する対称鍵です。

confirmP = MAC(K_confirmP, shareV)
confirmV = MAC(K_confirmV, shareP)

confirmP = MAC(K_confirmP, shareV)
confirmV = MAC(K_confirmV, shareP)

Once key confirmation is complete, applications MAY use K_shared as an authenticated shared secret as needed. For example, applications MAY derive one or more keys and nonces from K_shared, for use with Authenticated Encryption with Associated Data (AEAD) and subsequent application data encryption.

鍵確認が完了したら、アプリケーションは必要に応じてK_sharedを認証された共有秘密として使用してもよいです（MAY）。 たとえば、アプリケーションは、関連データ付き認証付き暗号（Authenticated Encryption with Associated Data; AEAD）とその後のアプリケーションデータの暗号化に使用するために、K_sharedから1つ以上の鍵とノンスを導出してもよいです（MAY）。

6. Security Considerations

6. セキュリティーに関する考慮事項

SPAKE2+ appears in [TDH] and is proven secure in [SPAKE2P-Analysis].

SPAKE2+は[TDH]に登場しており、[SPAKE2P-Analysis]で安全性が証明されています。

The ephemeral randomness used by the Prover and Verifier MUST be generated using a cryptographically secure Pseudorandom Number Generator (PRNG).

証明者と検証者が使用するエフェメラルな乱数は、暗号学的に安全な疑似乱数生成器（Pseudorandom Number Generator; PRNG）を使用して生成しなければなりません（MUST）。

Elements received from a peer MUST be checked for group membership: failure to properly deserialize and validate group elements can lead to attacks. An endpoint MUST abort the protocol if any received public value is not a member of the large prime-order subgroup of G. Multiplication of a public value V by the cofactor h will yield the identity element I whenever V is an element of a small-order subgroup. Consequently, the Prover and Verifier MUST abort the protocol upon receiving any value V such that V*h = I. Failure to do so may lead to subgroup confinement attacks.

ピアから受信した元については、群に属するかどうかを確認しなければなりません（MUST）。群の元を適切にデシリアライズして検証しないと、攻撃につながる可能性があります。 受信した公開値のいずれかがGの大きな素数位数の部分群に属していない場合、エンドポイントはプロトコルを中断しなければなりません（MUST）。 Vが位数の小さな部分群の元である場合、公開値Vに余因子hを掛けると、常に単位元Iが得られます。 したがって、V*h = Iとなる値Vを受信した場合、証明者と検証者はプロトコルを中断しなければなりません（MUST）。 そうしないと、部分群への閉じ込め攻撃につながる可能性があります。

Appendix B. Algorithm Used for Point Generation

Appendix B. 点の生成に使用したアルゴリズム

This section describes the algorithm that was used to generate the points M and N in Table 1 (Section 4). This algorithm produces M and N such that they are indistinguishable from two random points in the prime-order subgroup of G, where the discrete log of these points is unknown. See [SPAKE2P-Analysis] for additional details on this requirement.

このセクションでは、Table 1（Section 4）の点MとNを生成するために使用したアルゴリズムについて説明します。 このアルゴリズムは、Gの素数位数の部分群における2つのランダムな点と区別できないようにMとNを生成します。このとき、これらの点の離散対数は知られていません。 この要件の詳細については、[SPAKE2P-Analysis]を参照してください。

For each curve in Table 1, we construct a string using the curve OID from [RFC5480] (as an ASCII string) or its name, combined with the needed constant -- for instance, "1.3.132.0.35 point generation seed (M)" for P-521. This string is turned into a series of blocks by hashing with SHA256, and hashing that output again to generate the next 32 bytes, and so on. This pattern is repeated for each group and value, with the string modified appropriately.

Table 1の各曲線について、[RFC5480]の曲線のOID（ASCII文字列として）またはその名前に、必要な定数を組み合わせて文字列を構築します。たとえば、P-521の場合は「1.3.132.0.35 point generation seed (M)」です。 この文字列をSHA256でハッシュし、その出力を再びハッシュして次の32バイトを生成する、というようにして、一連のブロックに変換します。 文字列を適切に変更しながら、このパターンを各群と各値について繰り返します。

A byte string of length equal to that of an encoded group element is constructed by concatenating as many blocks as are required, starting from the first block, and truncating to the desired length. The byte string is then formatted as required for the group. In the case of Weierstrass curves, we take the desired length as the length for representing a compressed point (Section 2.3.4 of [SEC1]) and use the low-order bit of the first byte as the sign bit. In order to obtain the correct format, the value of the first byte is set to 0x02 or 0x03 (clearing the first six bits and setting the seventh bit), leaving the sign bit as it was in the byte string constructed by concatenating hash blocks. For the curves described in [RFC8032], a different procedure is used. For edwards448, the 57-byte input has the least-significant 7 bits of the last byte set to zero, and for edwards25519, the 32-byte input is not modified. For both of the curves described in [RFC8032], the (modified) input is then interpreted as the representation of the group element. If this interpretation yields a valid group element with the correct order (p), the (modified) byte string is the output. Otherwise, the initial hash block is discarded and a new byte string constructed from the remaining hash blocks. The procedure for constructing a byte string of the appropriate length, formatting it as required for the curve, and checking to see if it is a valid point of the correct order is repeated until a valid element is found.

最初のブロックから順に必要な数のブロックを連結し、目的の長さに切り詰めることで、エンコードされた群の元と同じ長さのバイト列を構築します。 次に、このバイト列を群が要求する形式に整形します。 Weierstrass曲線の場合は、圧縮された点を表現するための長さ（[SEC1]のSection 2.3.4）を目的の長さとし、最初のバイトの最下位ビットを符号ビットとして使用します。 正しい形式を得るために、最初のバイトの値を0x02または0x03に設定します（最初の6ビットをクリアし、7番目のビットをセットします）。符号ビットは、ハッシュブロックを連結して構築したバイト列のままにします。 [RFC8032]で説明されている曲線については、異なる手順を使用します。 edwards448では、57バイトの入力の最後のバイトの下位7ビットを0に設定し、edwards25519では、32バイトの入力を変更しません。 [RFC8032]で説明されているどちらの曲線についても、（変更した）入力を群の元の表現として解釈します。 この解釈によって正しい位数（p）を持つ有効な群の元が得られた場合は、（変更した）バイト列を出力とします。 そうでない場合は、最初のハッシュブロックを破棄し、残りのハッシュブロックから新しいバイト列を構築します。 適切な長さのバイト列を構築し、曲線が要求する形式に整形し、それが正しい位数の有効な点であるかどうかを確認する手順を、有効な元が見つかるまで繰り返します。

The following Python snippet generates the above points, assuming an elliptic curve implementation following the interface of Edwards25519Point.stdbase() and Edwards448Point.stdbase() in Appendix A of [RFC8032]:

次のPythonのコード片は、[RFC8032]のAppendix AのEdwards25519Point.stdbase()とEdwards448Point.stdbase()のインターフェイスに従う楕円曲線の実装を前提として、上記の点を生成します。

def iterated_hash(seed, n):
  h = seed
  for i in range(n):
    h = hashlib.sha256(h).digest()
  return h

def bighash(seed, start, sz):
  n = -(-sz // 32)
  hashes = [iterated_hash(seed, i) for i in range(start, start + n)]
  return b''.join(hashes)[:sz]

def canon_pointstr(ecname, s):
  if ecname == 'edwards25519':
    return s
  elif ecname == 'edwards448':
    return s[:-1] + bytes([s[-1] & 0x80])
  else:
    return bytes([(s[0] & 1) | 2]) + s[1:]

def gen_point(seed, ecname, ec):
  for i in range(1, 1000):
    hval = bighash(seed, i, len(ec.encode()))
    pointstr = canon_pointstr(ecname, hval)
    try:
      p = ec.decode(pointstr)
      if p != ec.zero_elem() and p * p.l() == ec.zero_elem():
        return pointstr, i
    except Exception:
      pass
