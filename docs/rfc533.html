RFC 533

MESSAGE-ID NUMBERS

RFC 533

メッセージID番号

Abstract

概要

It has been noted that the IMP message format (specified in BBN Report 1822) constrains network users to low throughputs if messages are to be uniquely identified via the link number. We have recently implemented a change in the IMP/Host protocol which alleviates this difficulty. The link field in the IMP/Host and Host/IMP leaders has been extended to the right by four bits (in other words, it now uses bits 17 to 28 of the leader), and the name of the link field has been changed to the _message-id field_. We expect this field to be used to uniquely identify messages between the IMPs and the Hosts. All 12 bits in the message-id will be returned to the Host in RFNMs, INCOMPLETE TRANSMISSIONs, etc. Note that no ordering is implied by the use of the message-id field.

（BBN Report 1822で規定された）IMPのメッセージ形式では、リンク番号によってメッセージを一意に識別しようとすると、ネットワークのユーザーは低いスループットに制約されることが指摘されています。私たちは最近、この問題を緩和するIMP/ホストプロトコルの変更を実装しました。IMP/ホストおよびホスト/IMPのリーダーにあるリンクフィールドを右に4ビット拡張し（言い換えると、リーダーのビット17から28までを使うようになりました）、リンクフィールドの名前を_メッセージIDフィールド（message-id field）_に変更しました。このフィールドは、IMPとホストの間でメッセージを一意に識別するために使われることを想定しています。メッセージIDの12ビットはすべて、RFNMやINCOMPLETE TRANSMISSIONなどでホストに返されます。メッセージIDフィールドを使っても、順序づけは何も意味しないことに注意してください。

Given that the Host/Host protocol uses the old link field to identify connections, the additional four bits in the new message-id field might well be used to uniquely identify messages on a given connection (i.e., over a given link). Of course, there is no obligation for Hosts to uniquely identify their messages (the IMP subnetwork certainly doesn't care), so this change in the IMP/Host message format is completely backward compatible. In fact, since the receiving Host does not have to look at these extra four bits on arriving messages, the change is completely backward compatible even when senders of messages do use the extra four bits to uniquely identify messages.

ホスト/ホストプロトコルでは、古いリンクフィールドを使ってコネクションを識別しているので、新しいメッセージIDフィールドで追加された4ビットは、特定のコネクション上（つまり、特定のリンク上）のメッセージを一意に識別するのに使うとよいかもしれません。もちろん、ホストには自分のメッセージを一意に識別する義務はありません（IMPのサブネットワークはまったく気にしません）。そのため、このIMP/ホストのメッセージ形式の変更は、完全に後方互換です。実際、受信側のホストは到着したメッセージのこの追加の4ビットを見る必要がないので、メッセージの送信者がこの追加の4ビットを使ってメッセージを一意に識別する場合でも、この変更は完全に後方互換です。

Please store this RFC with your copy of BBN Report 1822 until 1822 is updated.

1822が更新されるまで、このRFCをお手元のBBN Report 1822と一緒に保管してください。
