RFC 72

Proposed Moratorium on Changes to Network Protocol

RFC 72

ネットワークプロトコル変更の一時停止の提案

Abstract

概要

Bill Crowther's RFC No. 67 raised a much more fundamental issue than the question of marking. Any change to presently established protocol is going to involve changes in the hardware/software development efforts that have, in some instances, been going on for over 6 months. In the case of Multics, this effort has yielded programs either complete or in the advanced debugging stages. This is no doubt true for many other sites as well.

Bill CrowtherのRFC No. 67は、マーキングの問題よりもはるかに根本的な問題を提起しました。現在確立しているプロトコルを変更すれば、どんな変更であれ、ハードウェアやソフトウェアの開発作業にも変更が必要になります。その開発作業は、場合によっては6か月を超えて続いています。Multicsの場合、この作業によって、完成したプログラムか、デバッグの最終段階にあるプログラムができあがっています。ほかの多くのサイトでも同じであることは間違いありません。

The arguments being developed here are not that the present protocol is ideal, but rather that everyone has agreed that it is workable and has begun implementation of it. We would therefore like to propose a moratorium on most changes to this protocol for the next 6 months, or however long it takes to get this system running and to observe its characteristics.

ここで展開する主張は、現在のプロトコルが理想的だということではなく、だれもがそれを実用になると合意し、実装を始めているということです。そこで、今後6か月間、またはこのシステムを稼働させてその特性を観察するのに必要な期間、このプロトコルに対するほとんどの変更を一時停止（モラトリアム）することを提案したいと思います。

Specifically this means not making changes that only effect the efficiency or ease of implementation. If a major design problem is uncovered it should still be brought forward for consideration, as could issues that represent extensions to the existing system. But, changes to the details of the present system should not be made.

具体的には、効率や実装の容易さにしか影響しない変更は行わないということです。設計上の大きな問題が見つかった場合は、引き続き検討のために提起すべきです。既存のシステムの拡張にあたる事項も同様に提起してかまいません。しかし、現在のシステムの細部を変更すべきではありません。

There are several points to be made in favor of this argument. The first, and perhaps the most important, is getting the system working as soon as possible. The major benefits of the network will be in the uses to which it is put, and development along those lines cannot really get off its feet until the network is operational. We feel that, although the effort needed to reprogram part of the NCP at a later date will undoubtedly be greater, it will be hidden by the parallel effort then going on involving network usage and higher level network development.

この主張を支持する論点がいくつかあります。1つ目は、そしておそらく最も重要なのは、できるだけ早くシステムを動かすことです。ネットワークの主な恩恵はそれを何に使うかにあり、その方面の開発は、ネットワークが稼働するまでは実際には軌道に乗りません。後日NCPの一部をプログラムし直すのに必要な労力は間違いなく大きくなりますが、そのころにはネットワークの利用やより上位のネットワーク開発に関わる作業が並行して進んでいるため、その労力は目立たなくなると考えます。

Another problem that immediately arises is what should constitute an official change to the protocol. The history of the development of the current protocol shows that once an idea is raised, it is modified many times before it is generally agreeable to all. Thus each new suggestion for change could conceivably retard program development in terms of months.

すぐに生じるもう1つの問題は、何をもってプロトコルの公式な変更とするかです。現在のプロトコルの開発の歴史を見ると、ある考えが提起されてから、それが全員に広く受け入れられるようになるまでに何度も修正されています。したがって、変更の提案が新たに出るたびに、プログラムの開発が何か月も遅れることもありえます。

Finally there is the consideration that an idea may prove unfeasible once actual operation of the network begins. Any one of the currently agreed upon issues may be reopened when full scale testing begins to take place.

最後に、ネットワークの実際の運用が始まってから、ある考えが実現不可能だとわかる場合もあるという点を考慮する必要があります。本格的な試験が始まれば、現在合意されている事項のどれもが再び議論の対象になる可能性があります。

We think that these considerations are important enough to freeze the network protocol unless any problems arise that would make a certain feature unimplementable. Changes then leading simply to greater efficiency would be saved until actual network operation has been tested.

これらの考慮事項は十分に重要であり、ある機能を実装不可能にするような問題が生じない限り、ネットワークプロトコルを凍結すべきだと考えます。単に効率の向上につながるだけの変更は、ネットワークの実際の運用が試験されるまで保留します。

This is not to say that new ideas or arguments should not be brought forward, but that they should be brought forward with the understanding that they are not to be considered for immediate implementation but rather to be discussed with a view toward possible later implementation. This concept might be reflected by titling such documents, "Proposal for Post-Moratorium Changes to ..."

これは、新しい考えや主張を提起すべきではないということではありません。そうした考えや主張は、すぐに実装するために検討するものではなく、後日実装する可能性を視野に入れて議論するものだと理解したうえで提起すべきだということです。この考え方は、そうした文書に「Proposal for Post-Moratorium Changes to ...（一時停止解除後の…の変更の提案）」という表題を付けることで反映できるかもしれません。
