RFC 57

Thoughts and Reflections on NWG/RFC #54

RFC 57

NWG/RFC #54に関する考察と反省

Abstract

概要

In the course of writing NWG/RFC #54 several new ideas became apparent. Since these ideas had not previously been discussed by the NWG, or were sufficiently imprecise, it was decided not to include them in the official protocol proffering. We thought, however, that they might be proper subjects for discussion and later inclusion in the second level protocol.

NWG/RFC #54を執筆する過程で、いくつかの新しいアイデアが明らかになりました。これらのアイデアはこれまでNWGで議論されたことがなかったり、十分に厳密ではなかったりしたため、公式なプロトコルの提案には含めないことにしました。しかし、これらは議論の対象として、また後に第2レベルのプロトコルに含めるものとして適切かもしれないと考えました。

I. Errors and Overflow

I. エラーとオーバーフロー

In line with the discussion in NWG/RFC #48, we felt that two types of errors should be distinguished. One is a real error, such as an RFC composed of two send sockets. This type of error can only be generated by a broken NCP. In the absence of hardware and software bugs, these events should never occur; the correct response upon detection of such an event was outlined in the description of the ERR command in NWG/RFC #54.

NWG/RFC #48での議論に沿って、私たちは2種類のエラーを区別すべきだと考えました。1つは本当のエラーで、たとえば2つの送信ソケットで構成されたRFCです。この種のエラーは、壊れたNCPによってしか生成されません。ハードウェアやソフトウェアのバグがなければ、このような事象は決して発生しないはずです。このような事象を検出したときの正しい応答は、NWG/RFC #54のERRコマンドの説明で概要を示しました。

The other "error" is an overflow condition arising because finite system resources are exhausted. An overflow condition could occur if an RFC was received, but there was no room to create the requisite tables and queues. This is not a real error, in the sense that no one has done anything incorrect (expect perhaps the system planners in not providing sufficient table space, etc.) Further, a recovery procedure can be well defined, and simply entails repeating the request at a future time. Thus, we believe an overflow condition should be distinguished from a real error.

もう1つの「エラー」は、有限のシステム資源が使い果たされたために生じるオーバーフロー状態です。オーバーフロー状態は、RFCを受信したものの、必要なテーブルやキューを作成する余地がない場合に発生する可能性があります。これは、誰も誤ったことをしていない（十分なテーブル空間などを用意しなかったシステム計画者は別かもしれませんが）という意味で、本当のエラーではありません。さらに、回復手順は明確に定義でき、単に後で要求を繰り返すだけで済みます。したがって、オーバーフロー状態は本当のエラーと区別すべきだと私たちは考えます。

In NWG/RFC #54 an overflow condition was reported by returning a CLS, as if the connection had been refused. This sequence performs the necessary functions, and leaves the connection in the correct state, but the initiating user is misinformed. He is deluded into thinking that he was refused by the foreign process, when, in fact, this was not the case. In certain algorithms this difference is crucial.

NWG/RFC #54では、オーバーフロー状態は、あたかもコネクションが拒否されたかのようにCLSを返すことで報告されていました。この手順は必要な機能を果たし、コネクションを正しい状態のままにしますが、開始したユーザーには誤った情報が伝わります。そのユーザーは、実際にはそうではないのに、相手側のプロセスに拒否されたと思い込まされてしまいます。ある種のアルゴリズムでは、この違いは決定的に重要です。

In further defining error conditions, we felt that it would be helpful to specify why the error was detected, in addition to specifying what caused the error. While writing the pseudo-Algol program mentioned in NWG/RFC #55 we differentiated 9 types of errors (listed below). We would, therefore, like to propose the extension of the ERR message to include an 8-bit field following the op code to designate the type of error. This would be followed by the length and text fields, as before. We propose these error types;

エラー状態をさらに定義するにあたり、何がエラーを引き起こしたかに加えて、なぜエラーが検出されたかを規定すると役に立つと考えました。NWG/RFC #55で言及した疑似Algolプログラムを書く中で、私たちは9種類のエラー（以下に列挙）を区別しました。そこで、ERRメッセージを拡張し、オペコードの後にエラーの種類を示す8ビットのフィールドを含めることを提案したいと思います。その後には、これまでどおり長さとテキストのフィールドが続きます。私たちは次のエラーの種類を提案します。

  1. UNSPECIFIED ERROR
  2. HOMOSEX (invalid send/rcv pair in an RFC)
  3. ILLEGAL OP CODE
  4. ILLEGAL LEADER (bad message type, etc.)
  5. ILLEGAL COMMAND SEQUENCE
  6. ILLEGAL SOCKET SPECIFICATION - COMMAND
  7. ILLEGAL COMMAND LENGTH (last command in message was too short)
  8. CONNECTION NOT OPEN - DATA
  9. DATA OVERFLOW (message longer than advertised available buffer space)
  10. ILLEGAL SOCKET SPECIFICATION - DATA (socket does not exist)
  1. UNSPECIFIED ERROR
  2. HOMOSEX（RFC内の送信／受信の組が不正）
  3. ILLEGAL OP CODE
  4. ILLEGAL LEADER（メッセージタイプの誤りなど）
  5. ILLEGAL COMMAND SEQUENCE
  6. ILLEGAL SOCKET SPECIFICATION - COMMAND
  7. ILLEGAL COMMAND LENGTH（メッセージ内の最後のコマンドが短すぎる）
  8. CONNECTION NOT OPEN - DATA
  9. DATA OVERFLOW（メッセージが、通知された利用可能なバッファー空間よりも長い）
  10. ILLEGAL SOCKET SPECIFICATION - DATA（ソケットが存在しない）

In light of the other considerations mentioned earlier, we would also like to propose an additional control command to singify overflow:

先に述べたその他の考慮事項を踏まえ、オーバーフローを示すための追加の制御コマンドも提案したいと思います。

 +-------------+-------------------+---------------------+
 |     OVF     |     my socket     |     your socket     |
 +-------------+-------------------+---------------------+

 +-------------+-------------------+---------------------+
 |     OVF     |     my socket     |     your socket     |
 +-------------+-------------------+---------------------+

The format of the message is similar to that of the CLS message, which it replaces in this context. The socket numbers are 32 bits long and correspond to the socket numbers in the RFC which is being rejected. The semantics of an incoming OVF should be indentical to an incoming CLS; in addition, the user should be informed that he has not been refused but rather has overtaxed the foreign host's resources.

このメッセージの形式は、この文脈でOVFが置き換えるCLSメッセージの形式と似ています。ソケット番号は32ビット長で、拒否されるRFCのソケット番号に対応します。受信したOVFの意味は、受信したCLSと同一にすべきです。それに加えて、ユーザーには、拒否されたのではなく相手側ホストの資源に過大な負担をかけたのだということを知らせるべきです。

An alternative to creating a separate control command can be realized by considering the similarity between a CLS and an OVF. Conceivably, an eight-bit field could be added to the CLS command to define its derivation. We believe, however, that this alternative is conceptually inferior and practically more difficult to implement.

別個の制御コマンドを作成する代わりの方法は、CLSとOVFの類似性を考えることで実現できます。CLSコマンドに8ビットのフィールドを追加して、その由来を定義することも考えられます。しかし、この代替案は概念的に劣っており、実際的にも実装がより難しいと私たちは考えます。

Overflow does not require serious consideration if it is a significantly rare occurrence. We do not believe this will be the case, and we further believe that its absence will be an unnecessary restriction upon the user.

オーバーフローが著しくまれにしか発生しないのであれば、真剣に考慮する必要はありません。私たちはそうはならないと考えており、さらに、それがないことはユーザーにとって不必要な制約になると考えます。

II. Host Up and Host Down

II. ホストの稼働と停止

Significant problems can arise when a host goes down and then attempts to restart. Two cases can easily be distinguished. The first is a "soft" crash, where the system has prior notice that the machine is going down; sufficient time is available to execute pre-recovery procedures. The other case can be termed a "hard" crash, often the result of a system failure. Insignificant warning is usually given; but more important, the state of the machine after recovery is rarely predictable.

ホストが停止してから再起動しようとすると、重大な問題が生じる可能性があります。2つの場合を容易に区別できます。1つ目は「ソフト」クラッシュで、システムはマシンが停止することを事前に知っており、回復前の手順を実行するのに十分な時間があります。もう1つの場合は「ハード」クラッシュと呼ぶことができ、多くはシステム障害の結果です。通常、警告はほとんどありません。さらに重要なことに、回復後のマシンの状態はほとんど予測できません。

When a host returns from a hard crash, the network will be in an undefined state. Very probably the NCP's data structures are destroyed or are meaningless. The network has declared the host dead -- but only to processes which attempted data transmission and were refused. The only alternative for the crashed host is re-initialization of its tables. What are the alternatives for the foreign hosts?

ホストがハードクラッシュから復帰したとき、ネットワークは未定義の状態にあります。NCPのデータ構造は、おそらく破壊されているか無意味になっています。ネットワークはそのホストが停止していると宣言していますが、それはデータ送信を試みて拒否されたプロセスに対してだけです。クラッシュしたホストにとって唯一の選択肢は、テーブルの再初期化です。相手側のホストにとっての選択肢は何でしょうか？

We would like to propose the addition of two control commands: RESET (RST) and RESET REPLY (RSR). Each would consist solely of an op code with no parameters. Upon receipt of an RST, a host would immediately terminate all connections with the sending host, but would not issue any CLS's. The receiver of the RST would also note that the originator of the RST was alive, and would then echo an RSR to the sender. When a host receives an RSR, he sould then note that the echoing host is alive. (The function of RST can be partially simulated if a host will immediately close all relevant table entries upon discovering that another host is down.)

私たちは、RESET（RST）とRESET REPLY（RSR）という2つの制御コマンドの追加を提案したいと思います。どちらもパラメーターを持たないオペコードだけで構成されます。RSTを受信したホストは、送信元ホストとのすべてのコネクションを直ちに終了しますが、CLSは発行しません。RSTの受信者は、RSTの発信者が稼働していることも記録し、送信者にRSRをエコーします。RSRを受信したホストは、エコーしたホストが稼働していることを記録します。（ほかのホストが停止していることを発見したときに、関連するすべてのテーブルエントリーを直ちに閉じるようにすれば、RSTの機能を部分的に模倣できます。）

Thus, after a hard crash, all connections and request for connections are terminated. The RST also informs all foreign hosts that we are again alive, and an RSR is received from every functioning NCP. A host live table (see NWG/RFC #55) can easily be assembled, and establishment of connections can resume.

こうして、ハードクラッシュの後、すべてのコネクションとコネクションの要求は終了します。RSTはまた、私たちが再び稼働していることをすべての相手側ホストに知らせ、機能しているすべてのNCPからRSRが受信されます。ホスト稼働テーブル（NWG/RFC #55を参照）を容易に組み立てることができ、コネクションの確立を再開できます。

Related problems also crop up when we consider attempting to synchronize the network, which may still be carrying messages generated prior to the crash, with an NCP which has an initialized environment. We lack the facilities for unblocking links, discarding messages, etc. -- facilities which this proposal will necessitate. Further interaction with BBN should resolve these difficulties.

クラッシュ前に生成されたメッセージをまだ運んでいるかもしれないネットワークと、初期化された環境を持つNCPとを同期させようとすることを考えると、関連する問題も生じます。私たちには、リンクのブロック解除やメッセージの破棄などの機能がありません。これらは、この提案によって必要となる機能です。BBNとさらにやりとりすることで、これらの困難は解決されるはずです。

The problems associated with "soft" crashes are not nearly as pressing, and they demand more sophisticated (i.e., complex) solutions. Our preliminary experimentation with the network demonstrates that a good initialization and recovery protocol are far more necessary.

「ソフト」クラッシュに関連する問題はそれほど差し迫ったものではなく、より洗練された（つまり複雑な）解決策を必要とします。ネットワークを使った私たちの予備的な実験では、優れた初期化と回復のプロトコルのほうがはるかに必要であることが示されています。

Many of the ideas presented herin wre germinated and/or jelled through conversations with Steve Crocker and Jon Postel. We would also like to acknowledge the assistance of Jim Balter and Charles Kline of UCLA, who devoted a great deal of effort toward helping develop the pseudo-Algol program which was the predecessor of much of our recent documentation.

ここで示したアイデアの多くは、Steve CrockerとJon Postelとの会話を通じて芽生え、あるいは固まったものです。また、UCLAのJim BalterとCharles Klineの支援にも感謝します。彼らは、私たちの最近の文書の多くの前身となった疑似Algolプログラムの開発を手伝うために、多大な労力を注いでくれました。
