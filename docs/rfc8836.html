RFC 8836

Congestion Control Requirements for Interactive Real-Time Media

RFC 8836

対話型リアルタイムメディアのための輻輳制御要件

Abstract

概要

Congestion control is needed for all data transported across the Internet, in order to promote fair usage and prevent congestion collapse. The requirements for interactive, point-to-point real-time multimedia, which needs low-delay, semi-reliable data delivery, are different from the requirements for bulk transfer like FTP or bursty transfers like web pages. Due to an increasing amount of RTP-based real-time media traffic on the Internet (e.g., with the introduction of the Web Real-Time Communication (WebRTC)), it is especially important to ensure that this kind of traffic is congestion controlled.

公平な利用を促し、輻輳崩壊を防ぐために、インターネットを横断して運ばれるすべてのデータには輻輳制御が必要です。 低遅延で半信頼性のデータ配送を必要とする、対話型のポイントツーポイントのリアルタイムマルチメディアに対する要件は、FTPのような大量転送やWebページのようなバースト的な転送に対する要件とは異なります。 インターネット上でRTPベースのリアルタイムメディアトラフィックが増加している（たとえば、Web Real-Time Communication（WebRTC）の導入にともなって）ことから、この種のトラフィックが輻輳制御されるようにすることは特に重要です。

This document describes a set of requirements that can be used to evaluate other congestion control mechanisms in order to figure out their fitness for this purpose, and in particular to provide a set of possible requirements for a real-time media congestion avoidance technique.

この文書は、他の輻輳制御メカニズムがこの目的に適しているかどうかを見極めるためにそれらを評価する際に使用できる一連の要件を記述し、特に、リアルタイムメディアの輻輳回避手法に対して考えられる一連の要件を提供します。

1. Introduction

1. はじめに

Most of today's TCP congestion control schemes were developed with a focus on a use of the Internet for reliable bulk transfer of non-time-critical data, such as transfer of large files. They have also been used successfully to govern the reliable transfer of smaller chunks of data in as short a time as possible, such as when fetching web pages.

今日のTCP輻輳制御方式のほとんどは、大きなファイルの転送など、時間的制約のないデータを信頼性をもって大量転送するというインターネットの使い方に重点を置いて開発されました。 これらの方式は、Webページを取得するときのように、より小さなデータの塊をできるだけ短い時間で信頼性をもって転送することを制御するためにも、うまく使われてきました。

These algorithms have also been used for transfer of media streams that are viewed in a non-interactive manner, such as "streaming" video, where having the data ready when the viewer wants it is important, but the exact timing of the delivery is not.

これらのアルゴリズムは、「ストリーミング」ビデオのように非対話的に視聴されるメディアストリームの転送にも使われてきました。 そこでは、視聴者が望むときにデータが用意されていることは重要ですが、配送の正確なタイミングは重要ではありません。

When handling real-time interactive media, the requirements are different. One needs to provide the data continuously, within a very limited time window (no more delay than hundreds of milliseconds end-to-end). In addition, the sources of data may be able to adapt the amount of data that needs sending within fairly wide margins, but they can be rate limited by the application -- even not always having data to send. They may tolerate some amount of packet loss, but since the data is generated in real time, sending "future" data is impossible, and since it's consumed in real time, data delivered late is commonly useless.

リアルタイムの対話型メディアを扱う場合、要件は異なります。 非常に限られた時間枠の中で（エンドツーエンドで数百ミリ秒を超えない遅延で）、データを継続的に提供する必要があります。 さらに、データの送信元は、送信する必要のあるデータ量をかなり広い幅で調整できる場合がありますが、アプリケーションによってレートが制限されることもあり、送信するデータが常にあるとは限りません。 データの送信元はある程度のパケット損失を許容できる場合がありますが、データはリアルタイムに生成されるので「未来の」データを送ることは不可能であり、またリアルタイムに消費されるので、遅れて配送されたデータは通常役に立ちません。

While the requirements for real-time interactive media differ from the requirements for the other flow types, these other flow types will be present in the network. The congestion control algorithm for real-time interactive media must work properly when these other flow types are present as cross traffic on the network.

リアルタイムの対話型メディアに対する要件は他の種類のフローに対する要件とは異なりますが、これらの他の種類のフローもネットワーク上に存在します。 リアルタイムの対話型メディアのための輻輳制御アルゴリズムは、これらの他の種類のフローがネットワーク上のクロストラフィックとして存在する場合にも、適切に動作しなければなりません。

One particular protocol portfolio being developed for this use case is WebRTC [RFC8825], where one envisions sending multiple flows using the Real-time Transport Protocol (RTP) [RFC3550] between two peers, in conjunction with data flows, all at the same time, without having special arrangements with the intervening service providers. As RTP does not provide any congestion control mechanism, a set of circuit breakers, such as those described in [RFC8083], are required to protect the network from excessive congestion caused by non-congestion-controlled flows. When the real-time interactive media is congestion controlled, it is recommended that the congestion control mechanism operate within the constraints defined by these circuit breakers when a circuit breaker is present and that it should not cause congestion collapse when a circuit breaker is not implemented.

このユースケースのために開発されている具体的なプロトコル群の1つがWebRTC [RFC8825]です。 WebRTCでは、間にあるサービスプロバイダーと特別な取り決めをすることなく、Real-time Transport Protocol（RTP）[RFC3550]を使用する複数のフローを、データフローとともに、すべて同時に2つのピア間で送信することが想定されています。 RTPは輻輳制御メカニズムをまったく提供しないため、輻輳制御されていないフローによって引き起こされる過度の輻輳からネットワークを保護するには、[RFC8083]で説明されているような一連のサーキットブレーカーが必要です。 リアルタイムの対話型メディアが輻輳制御される場合、サーキットブレーカーが存在するときには輻輳制御メカニズムがこれらのサーキットブレーカーによって定義される制約の範囲内で動作すること、そしてサーキットブレーカーが実装されていないときには輻輳崩壊を引き起こさないことが推奨されます。

Given that this use case is the focus of this document, use cases involving non-interactive media such as video streaming and those using multicast/broadcast-type technologies, are out of scope.

このユースケースがこの文書の焦点であることから、ビデオストリーミングのような非対話型メディアを含むユースケースや、マルチキャスト/ブロードキャスト型の技術を使用するユースケースは範囲外です。

The terminology defined in [RFC8825] is used in this memo.

このメモでは、[RFC8825]で定義されている用語を使用します。

1.1. Requirements Language

1.1. 要件言語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119].

この文書におけるキーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119]に記載されているとおりに解釈されるものとします。

2. Requirements

2. 要件

  1. The congestion control algorithm MUST attempt to provide as-low-as-possible-delay transit for interactive real-time traffic while still providing a useful amount of bandwidth. There may be lower limits on the amount of bandwidth that is useful, but this is largely application specific, and the application may be able to modify or remove flows in order to allow some useful flows to get enough bandwidth. For example, although there might not be enough bandwidth for low-latency video+audio, there could be enough for audio only.

    1. Jitter (variation in the bitrate over short timescales) is also relevant, though moderate amounts of jitter will be absorbed by jitter buffers. Transit delay should be considered to track the short-term maximums of delay, including jitter.
    2. The algorithm should provide this as-low-as-possible-delay transit and minimize self-induced latency even when faced with intermediate bottlenecks and competing flows. Competing flows may limit what's possible to achieve.
    3. The algorithm should be resilient to the effects of events, such as routing changes, which may alter or remove bottlenecks or change the bandwidth available, especially if there is a reduction in available bandwidth or increase in observed delay. It is expected that the mechanism reacts quickly to such events to avoid delay buildup. In the context of this memo, a "quick" reaction is on the order of a few RTTs, subject to the constraints of the media codec, but is likely within a second. Reaction on the next RTT is explicitly not required, since many codecs cannot adapt their sending rate that quickly, but at the same time a response cannot be arbitrarily delayed.
    4. The algorithm should react quickly to handle both local and remote interface changes (e.g., WLAN to 3G data) that may radically change the bandwidth available or bottlenecks, especially if there is a reduction in available bandwidth or an increase in bottleneck delay. It is assumed that an interface change can generate a notification to the algorithm.
    5. The real-time interactive media applications can be rate limited. This means the offered loads can be less than the available bandwidth at any given moment and may vary dramatically over time, including dropping to no load and then resuming a high load, such as in a mute/unmute operation. Hence, the algorithm must be designed to handle such behavior from a media source or application. Note that the reaction time between a change in the bandwidth available from the algorithm and a change in the offered load is variable, and it may be different when increasing versus decreasing.
    6. The algorithm is required to avoid building up queues when competing with short-term bursts of traffic (for example, traffic generated by web browsing), which can quickly saturate a local-bottleneck router or link but clear quickly. The algorithm should also react quickly to regain its previous share of the bandwidth when the local bottleneck or link is cleared.
    7. Similarly, periodic bursty flows such as MPEG DASH [MPEG_DASH] or proprietary media streaming algorithms may compete in bursts with the algorithm and may not be adaptive within a burst. They are often layered on top of TCP but use TCP in a bursty manner that can interact poorly with competing flows during the bursts. The algorithm must not increase the already existing delay buildup during those bursts. Note that this competing traffic may be on a shared access link, or the traffic burst may cause a shift in the location of the bottleneck for the duration of the burst.

  2. The algorithm MUST be fair to other flows, both real-time flows (such as other instances of itself) and TCP flows, both long-lived flows and bursts such as the traffic generated by a typical web-browsing session. Note that "fair" is a rather hard-to-define term. It SHOULD be fair with itself, giving a fair share of the bandwidth to multiple flows with similar RTTs, and if possible to multiple flows with different RTTs.

    1. Existing flows at a bottleneck must also be fair to new flows to that bottleneck and must allow new flows to ramp up to a useful share of the bottleneck bandwidth as quickly as possible. A useful share will depend on the media types involved, total bandwidth available, and the user-experience requirements of a particular service. Note that relative RTTs may affect the rate at which new flows can ramp up to a reasonable share.

  3. The algorithm SHOULD NOT starve competing TCP flows and SHOULD, as best as possible, avoid starvation by TCP flows.

    1. The congestion control should prioritize achieving a useful share of the bandwidth depending on the media types and total available bandwidth over achieving as-low-as-possible transit delay, when these two requirements are in conflict.

  4. The algorithm SHOULD adapt as quickly as possible to initial network conditions at the start of a flow. This SHOULD occur whether the initial bandwidth is above or below the bottleneck bandwidth.

    1. The algorithm should allow different modes of adaptation; for example, the startup adaptation may be faster than adaptation later in a flow. It should allow for both slow-start operation (adapt up) and history-based startup (start at a point expected to be at or below channel bandwidth from historical information, which may need to adapt down quickly if the initial guess is wrong). Starting too low and/or adapting up too slowly can cause a critical point in a personal communication to be poor ("Hello!"). Starting too high above the available bandwidth causes other problems for user experience, so there's a tension here. Alternative methods to help startup, such as probing during setup with dummy data, may be useful in some applications; in some cases, there will be a considerable gap in time between flow creation and the initial flow of data. Again, a flow may need to change adaptation rates due to network conditions or changes in the provided flows (such as unmuting or sending data after a gap).

  5. The algorithm SHOULD be stable if the RTP streams are halted or discontinuous (for example, when using Voice Activity Detection).

    1. After stream resumption, the algorithm should attempt to rapidly regain its previous share of the bandwidth; the aggressiveness with which this is done will decay with the length of the pause.

  6. Where possible, the algorithm SHOULD merge information across multiple RTP streams sent between two endpoints when those RTP streams share a common bottleneck, whether or not those streams are multiplexed onto the same ports. This will allow congestion control of the set of streams together instead of as multiple independent streams. It will also allow better overall bandwidth management, faster response to changing conditions, and fairer sharing of bandwidth with other network users.

    1. The algorithm should also share information and adaptation with other non-RTP flows between the same endpoints, such as a WebRTC data channel [RFC8831], when possible.
    2. When there are multiple streams across the same 5-tuple coordinating their bandwidth use and congestion control, the algorithm should allow the application to control the relative split of available bandwidth. The most correlated bandwidth usage would be with other flows on the same 5-tuple, but there may be use in coordinating measurement and control of the local link(s). Use of information about previous flows, especially on the same 5-tuple, may be useful input to the algorithm, especially regarding startup performance of a new flow.

  7. The algorithm SHOULD NOT require any special support from network elements to be able to convey congestion-related information. As much as possible, it SHOULD leverage available information about the incoming flow to provide feedback to the sender. Examples of this information are the packet arrival times, acknowledgements and feedback, packet timestamps, packet losses, and Explicit Congestion Notification (ECN) [RFC3168]; all of these can provide information about the state of the path and any bottlenecks. However, the use of available information is algorithm dependent.

    1. Extra information could be added to the packets to provide more detailed information on actual send times (as opposed to sampling times), but such information should not be required.

  8. Since the assumption here is a set of RTP streams, the backchannel typically SHOULD be done via the RTP Control Protocol (RTCP) [RFC3550]; instead, one alternative would be to include it in a reverse-RTP channel using header extensions.

    1. In order to react sufficiently quickly when using RTCP for a backchannel, an RTP profile such as RTP/AVPF [RFC4585] or RTP/SAVPF [RFC5124] that allows sufficiently frequent feedback must be used. Note that in some cases, backchannel messages may be delayed until the RTCP channel can be allocated enough bandwidth, even under AVPF rules. This may also imply negotiating a higher maximum percentage for RTCP data or allowing solutions to violate or modify the rules specified for AVPF.
    2. Bandwidth for the feedback messages should be minimized using techniques such as those in [RFC5506], to allow RTCP without Sender/Receiver Reports.
    3. Backchannel data should be minimized to avoid taking too much reverse-channel bandwidth (since this will often be used in a bidirectional set of flows). In areas of stability, backchannel data may be sent more infrequently so long as algorithm stability and fairness are maintained. When the channel is unstable or has not yet reached equilibrium after a change, backchannel feedback may be more frequent and use more reverse-channel bandwidth. This is an area with considerable flexibility of design, and different approaches to backchannel messages and frequency are expected to be evaluated.

  9. Flows managed by this algorithm and flows competing against each other at a bottleneck may have different Differentiated Services Code Point (DSCP) [RFC5865] markings depending on the type of traffic or may be subject to flow-based QoS. A particular bottleneck or section of the network path may or may not honor DSCP markings. The algorithm SHOULD attempt to leverage DSCP markings when they're available.

  10. The algorithm SHOULD sense the unexpected lack of backchannel information as a possible indication of a channel-overuse problem and react accordingly to avoid burst events causing a congestion collapse.
  11. The algorithm SHOULD be stable and maintain low delay when faced with Active Queue Management (AQM) algorithms. Also note that these algorithms may apply across multiple queues in the bottleneck or to a single queue.

  1. 輻輳制御アルゴリズムは、有用な量の帯域幅を提供しつつ、対話型リアルタイムトラフィックに対して可能な限り低遅延の転送を提供するよう試みなければなりません（MUST）。 有用な帯域幅の量には下限がある場合がありますが、これは主にアプリケーション固有であり、アプリケーションは、一部の有用なフローが十分な帯域幅を得られるように、フローを変更したり削除したりできる場合があります。 たとえば、低遅延のビデオ＋音声には帯域幅が足りなくても、音声のみであれば十分な場合があります。

    1. ジッター（短い時間スケールでのビットレートの変動）も関係しますが、適度な量のジッターはジッターバッファーによって吸収されます。 転送遅延は、ジッターを含む遅延の短期的な最大値を追跡するものとして考えるべきです。
    2. アルゴリズムは、途中のボトルネックや競合するフローに直面した場合でも、この可能な限り低遅延の転送を提供し、自ら引き起こす遅延を最小化すべきです。 競合するフローによって、達成できることが制限される場合があります。
    3. アルゴリズムは、ボトルネックを変化させたり取り除いたり、利用可能な帯域幅を変えたりする可能性のある、ルーティングの変更などのイベントの影響に対して、特に利用可能な帯域幅が減少したり観測される遅延が増加したりする場合に、耐性を持つべきです。 メカニズムは、遅延の蓄積を避けるために、そのようなイベントに素早く反応することが期待されます。 このメモの文脈では、「素早い」反応とは、メディアコーデックの制約を受けるものの、数RTT程度のオーダーであり、おそらく1秒以内です。 多くのコーデックはそれほど素早く送信レートを調整できないため、次のRTTでの反応は明示的に要求されませんが、同時に、反応を際限なく遅らせることもできません。
    4. アルゴリズムは、利用可能な帯域幅やボトルネックを根本的に変える可能性のある、ローカルとリモート両方のインターフェイスの変更（たとえば、WLANから3Gデータへの変更）に対処するために、特に利用可能な帯域幅が減少したりボトルネックでの遅延が増加したりする場合には、素早く反応すべきです。 インターフェイスの変更によって、アルゴリズムへの通知を生成できることを前提とします。
    5. リアルタイムの対話型メディアアプリケーションは、レートが制限される場合があります。 これは、提供負荷がどの時点においても利用可能な帯域幅を下回る可能性があり、またミュート/ミュート解除の操作のように、負荷がゼロに落ちてから高い負荷に戻ることも含めて、時間とともに劇的に変化する可能性があることを意味します。 したがって、アルゴリズムは、メディアソースやアプリケーションからのそのような振る舞いに対処できるように設計されていなければなりません。 アルゴリズムから得られる利用可能な帯域幅の変化と、提供負荷の変化との間の反応時間は可変であり、増加する場合と減少する場合とで異なる可能性があることに注意してください。
    6. アルゴリズムは、短期的なトラフィックのバースト（たとえば、Webブラウジングによって生成されるトラフィック）と競合する場合に、キューを蓄積させないようにする必要があります。 そのようなバーストは、ローカルのボトルネックとなるルーターやリンクを急速に飽和させることがありますが、すぐに解消されます。 また、アルゴリズムは、ローカルのボトルネックやリンクが解消されたときに、以前の帯域幅の取り分を取り戻すために素早く反応すべきです。
    7. 同様に、MPEG DASH [MPEG_DASH]や独自のメディアストリーミングアルゴリズムのような周期的にバーストするフローは、アルゴリズムとバースト的に競合する場合があり、バーストの中では適応的でない場合があります。 これらはTCPの上に重ねられることが多いですが、バーストの間に競合するフローと好ましくない相互作用をしうる、バースト的なやり方でTCPを使用します。 アルゴリズムは、そのようなバーストの間に、すでに存在する遅延の蓄積を増大させてはなりません。 この競合するトラフィックは共有アクセスリンク上にある場合もあれば、トラフィックのバーストによって、バーストの間ボトルネックの位置が移る場合もあることに注意してください。

  2. アルゴリズムは、リアルタイムフロー（自分自身の他のインスタンスなど）とTCPフローの両方、また長命なフローと典型的なWebブラウジングセッションで生成されるトラフィックのようなバーストの両方を含む、他のフローに対して公平でなければなりません（MUST）。 「公平」はかなり定義しにくい用語であることに注意してください。 アルゴリズムは、類似したRTTを持つ複数のフローに、そして可能であれば異なるRTTを持つ複数のフローにも、帯域幅の公平な取り分を与えることで、自分自身に対して公平であるべきです（SHOULD）。

    1. ボトルネックにおける既存のフローは、そのボトルネックへの新しいフローに対しても公平である必要があり、新しいフローがボトルネックの帯域幅の有用な取り分まで、できるだけ早く立ち上がれるようにする必要があります。 有用な取り分は、関係するメディアタイプ、利用可能な帯域幅の総量、特定のサービスのユーザー体験に関する要件に依存します。 相対的なRTTが、新しいフローが妥当な取り分まで立ち上がる速さに影響する場合があることに注意してください。

  3. アルゴリズムは、競合するTCPフローを枯渇させるべきではありません（SHOULD NOT）。 また、TCPフローによって枯渇させられることを、可能な限り回避するべきです（SHOULD）。

    1. これら2つの要件が衝突する場合、輻輳制御は、可能な限り低い転送遅延を達成することよりも、メディアタイプと利用可能な帯域幅の総量に応じた帯域幅の有用な取り分を達成することを優先すべきです。

  4. アルゴリズムは、フローの開始時に、初期のネットワーク状況にできるだけ素早く適応するべきです（SHOULD）。 この適応は、初期の帯域幅がボトルネックの帯域幅を上回っているか下回っているかにかかわらず、行われるべきです（SHOULD）。

    1. アルゴリズムは、異なる適応モードを許容すべきです。 たとえば、開始時の適応は、フローの後半での適応より速くてもかまいません。 アルゴリズムは、スロースタート動作（上方への適応）と、履歴に基づく開始（過去の情報からチャネルの帯域幅以下であると予想される点から開始するもので、最初の推測が誤っていた場合には素早く下方に適応する必要があるかもしれません）の両方を許容すべきです。 開始点が低すぎたり、上方への適応が遅すぎたりすると、個人間のコミュニケーションにおける重要な時点（「もしもし！」）の品質が悪くなる可能性があります。 利用可能な帯域幅を大きく上回る高すぎる点から開始すると、ユーザー体験に別の問題を引き起こすため、ここには相反する関係があります。 ダミーデータを使ってセットアップ中にプロービングを行うなど、開始を助ける代替手段が一部のアプリケーションでは有用な場合があります。 場合によっては、フローの作成から最初のデータの流れまでに、かなりの時間差があるでしょう。 繰り返しになりますが、フローは、ネットワークの状況や、提供されるフローの変化（ミュート解除や、間隔が空いた後のデータの送信など）によって、適応の速さを変える必要がある場合があります。

  5. アルゴリズムは、RTPストリームが停止したり不連続になったりした場合（たとえば、音声区間検出（Voice Activity Detection）を使用している場合）にも、安定しているべきです（SHOULD）。

    1. ストリームの再開後、アルゴリズムは以前の帯域幅の取り分を急速に取り戻そうと試みるべきです。 これを行う積極性は、一時停止の長さに応じて減衰します。

  6. 可能な場合、2つのエンドポイント間で送信される複数のRTPストリームが共通のボトルネックを共有しているときには、それらのストリームが同じポートに多重化されているかどうかにかかわらず、アルゴリズムはそれらのRTPストリームにまたがって情報を統合するべきです（SHOULD）。 これにより、ストリームの集合を、複数の独立したストリームとしてではなく、まとめて輻輳制御できるようになります。 また、全体的な帯域幅管理の改善、状況の変化へのより速い反応、他のネットワークユーザーとのより公平な帯域幅の共有も可能になります。

    1. 可能な場合、アルゴリズムは、WebRTCデータチャネル[RFC8831]など、同じエンドポイント間の他の非RTPフローとも、情報と適応を共有すべきです。
    2. 同じ5タプル上に、帯域幅の使用と輻輳制御を協調させている複数のストリームがある場合、アルゴリズムは、利用可能な帯域幅の相対的な配分をアプリケーションが制御できるようにすべきです。 帯域幅の使用が最も強く相関するのは同じ5タプル上の他のフローでしょうが、ローカルリンクの測定と制御を協調させることにも有用性があるかもしれません。 以前のフロー、特に同じ5タプル上のフローに関する情報を使用することは、特に新しいフローの開始時の性能に関して、アルゴリズムへの有用な入力となる場合があります。

  7. アルゴリズムは、輻輳に関連する情報を伝えられるようにするために、ネットワーク要素からの特別なサポートを必要とするべきではありません（SHOULD NOT）。 アルゴリズムは、送信者にフィードバックを提供するために、受信するフローについて利用可能な情報をできる限り活用するべきです（SHOULD）。 この情報の例としては、パケットの到着時刻、確認応答とフィードバック、パケットのタイムスタンプ、パケット損失、明示的輻輳通知（ECN）[RFC3168]があります。 これらはすべて、パスとあらゆるボトルネックの状態に関する情報を提供できます。 ただし、利用可能な情報をどのように使用するかはアルゴリズムに依存します。

    1. 実際の送信時刻（サンプリング時刻ではなく）に関するより詳細な情報を提供するために、追加の情報をパケットに付加することもできますが、そのような情報を必須とすべきではありません。

  8. ここではRTPストリームの集合を前提としているため、バックチャネルは通常、RTP Control Protocol（RTCP）[RFC3550]を介して行うべきです（SHOULD）。 その代わりとなる1つの方法としては、ヘッダー拡張を使用して、逆方向のRTPチャネルに含めることが考えられます。

    1. バックチャネルにRTCPを使用する場合に十分に素早く反応するためには、RTP/AVPF [RFC4585]やRTP/SAVPF [RFC5124]のような、十分に頻繁なフィードバックを可能にするRTPプロファイルを使用する必要があります。 場合によっては、AVPFの規則の下であっても、RTCPチャネルに十分な帯域幅を割り当てられるまで、バックチャネルのメッセージが遅延する可能性があることに注意してください。 これは、RTCPデータの最大割合をより高くネゴシエートすることや、AVPFに規定された規則に違反したりその規則を変更したりすることを解決策に許すことを意味する場合もあります。
    2. 送信者レポート/受信者レポートなしのRTCPを可能にするために、[RFC5506]にあるような技術を使用して、フィードバックメッセージのための帯域幅を最小化すべきです。
    3. 逆方向チャネルの帯域幅を消費しすぎないように、バックチャネルのデータは最小化すべきです（これは双方向のフローの集合で使われることが多いためです）。 安定している領域では、アルゴリズムの安定性と公平性が維持される限り、バックチャネルのデータをより低い頻度で送信してもかまいません。 チャネルが不安定な場合や、変化の後にまだ平衡状態に達していない場合には、バックチャネルのフィードバックをより頻繁にし、逆方向チャネルの帯域幅をより多く使ってもかまいません。 これは設計の自由度がかなり大きい領域であり、バックチャネルのメッセージとその頻度に対するさまざまなアプローチが評価されることが期待されます。

  9. このアルゴリズムによって管理されるフローと、ボトルネックで互いに競合するフローは、トラフィックの種類に応じて異なるDifferentiated Services Code Point（DSCP）[RFC5865]のマーキングを持つ場合や、フローベースのQoSの対象となる場合があります。 特定のボトルネックやネットワークパスの区間は、DSCPのマーキングを尊重する場合もあれば、尊重しない場合もあります。 アルゴリズムは、DSCPのマーキングが利用可能な場合には、それを活用するよう試みるべきです（SHOULD）。

  10. アルゴリズムは、バックチャネル情報が予期せず得られないことを、チャネルの過剰使用の問題を示している可能性があるものとして検知し、バーストイベントが輻輳崩壊を引き起こすことを避けるように、それに応じて反応するべきです（SHOULD）。
  11. アルゴリズムは、アクティブキュー管理（AQM）アルゴリズムに直面した場合でも、安定しており、低遅延を維持するべきです（SHOULD）。 また、これらのAQMアルゴリズムは、ボトルネックにおける複数のキューにまたがって適用される場合もあれば、単一のキューに適用される場合もあることに注意してください。

3. Deficiencies of Existing Mechanisms

3. 既存のメカニズムの欠点

Among the existing congestion control mechanisms, TCP Friendly Rate Control (TFRC) [RFC5348] is the one that claims to be suitable for real-time interactive media. TFRC is an equation-based congestion control mechanism that provides a reasonably fair share of bandwidth when competing with TCP flows and offers much lower throughput variations than TCP. This is achieved by a slower response to the available bandwidth change than TCP. TFRC is designed to perform best with applications that have a fixed packet size and do not have a fixed period between sending packets.

既存の輻輳制御メカニズムの中で、リアルタイムの対話型メディアに適していると謳っているのは、TCP Friendly Rate Control（TFRC）[RFC5348]です。 TFRCは方程式ベースの輻輳制御メカニズムであり、TCPフローと競合する際にかなり公平な帯域幅の取り分を提供し、TCPよりもはるかに小さなスループットの変動をもたらします。 これは、利用可能な帯域幅の変化に対してTCPよりもゆっくりと反応することによって実現されています。 TFRCは、固定のパケットサイズを持ち、パケットの送信間隔が固定されていないアプリケーションで最もよく機能するように設計されています。

TFRC detects loss events and reacts to congestion-caused loss by reducing its sending rate. It allows applications to increase the sending rate until loss is observed in the flows. As noted in IAB/IRTF report [RFC7295], large buffers are available in the network elements, which introduce additional delay in the communication. It becomes important to take all possible congestion indications into consideration. Looking at the current Internet deployment, TFRC's biggest deficiency is that it only considers loss events as a congestion indication.

TFRCは損失イベントを検出し、送信レートを下げることによって、輻輳に起因する損失に反応します。 TFRCは、フローで損失が観測されるまで、アプリケーションが送信レートを増加させることを許容します。 IAB/IRTFのレポート[RFC7295]で指摘されているように、ネットワーク要素には大きなバッファーが存在し、それが通信に追加の遅延をもたらします。 考えうるすべての輻輳の兆候を考慮に入れることが重要になります。 現在のインターネットの展開状況を見ると、TFRCの最大の欠点は、損失イベントだけを輻輳の兆候とみなすことです。

A typical real-time interactive communication includes live-encoded audio and video flow(s). In such a communication scenario, an audio source typically needs a fixed interval between packets and needs to vary the segment size of the packets instead of the packet rate in response to congestion; therefore, it sends smaller packets. A variant of TFRC, Small-Packet TFRC (TFRC-SP) [RFC4828], addresses the issues related to such kind of sources. A video source generally varies video frame sizes, can produce large frames that need to be further fragmented to fit into path Maximum Transmission Unit (MTU) size, and has an almost fixed interval between producing frames under a certain frame rate. TFRC is known to be less optimal when using such video sources.

典型的なリアルタイムの対話型通信には、ライブでエンコードされた音声とビデオのフローが含まれます。 そのような通信のシナリオでは、音声の送信元は通常、パケット間に固定の間隔を必要とし、輻輳に応じてパケットレートではなくパケットのセグメントサイズを変える必要があるため、より小さなパケットを送信します。 TFRCの変種であるSmall-Packet TFRC（TFRC-SP）[RFC4828]は、そのような種類の送信元に関連する問題に対処しています。 ビデオの送信元は一般に、ビデオフレームのサイズを変化させ、パスの最大転送単位（MTU）のサイズに収まるようにさらに断片化する必要のある大きなフレームを生成することがあり、一定のフレームレートの下ではほぼ固定の間隔でフレームを生成します。 TFRCは、そのようなビデオの送信元を使用する場合には、あまり最適ではないことが知られています。

There are also some mismatches between TFRC's design assumptions and how the media sources in a typical real-time interactive application work. TFRC is designed to maintain a smooth sending rate; however, media sources can change rates in steps for both rate increase and rate decrease. TFRC can operate in two modes: i) bytes per second and ii) packets per second, where typical real-time interactive media sources operate on bit per second. There are also limitations on how quickly the media sources can adapt to specific sending rates. Modern video encoders can operate in a mode in which they can vary the output bitrate a lot depending on the way they are configured, the current scene they are encoding, and more. Therefore, it is possible that the video source will not always output at an allowable bitrate. TFRC tries to increase its sending rate when transmitting at the maximum allowed rate, and it increases only twice the current transmission rate; hence, it may create issues when the video sources vary their bitrates.

また、TFRCの設計上の前提と、典型的なリアルタイムの対話型アプリケーションにおけるメディアソースの動作との間には、いくつかの不一致があります。 TFRCは滑らかな送信レートを維持するように設計されていますが、メディアソースは、レートの増加と減少のどちらについても、段階的にレートを変えることがあります。 TFRCは、i）バイト毎秒とii）パケット毎秒の2つのモードで動作できますが、典型的なリアルタイムの対話型メディアソースはビット毎秒で動作します。 また、メディアソースが特定の送信レートにどれだけ素早く適応できるかについても制限があります。 最新のビデオエンコーダーは、その設定方法、エンコード中の現在のシーンなどに応じて、出力ビットレートを大きく変化させられるモードで動作できます。 したがって、ビデオの送信元が常に許容されるビットレートで出力するとは限りません。 TFRCは、許容される最大レートで送信しているときに送信レートを増加させようとし、しかも現在の送信レートの2倍までしか増加させないため、ビデオの送信元がビットレートを変化させる場合に問題を引き起こす可能性があります。

Moreover, there are a number of studies on TFRC that show its limitations, including TFRC's unfairness to low statistically multiplexed links, oscillatory behavior, performance issues in highly dynamic loss-rate conditions, and more [CH09].

さらに、統計多重度の低いリンクに対するTFRCの不公平性、振動的な振る舞い、損失率が激しく変動する状況での性能の問題など、TFRCの限界を示す研究が数多くあります[CH09]。

Looking at all these deficiencies, it can be concluded that the requirements for a congestion control mechanism for real-time interactive media cannot be met by TFRC as defined in the standard.

これらすべての欠点を踏まえると、リアルタイムの対話型メディアのための輻輳制御メカニズムに対する要件は、標準で定義されているTFRCでは満たせないと結論付けることができます。

5. Security Considerations

5. セキュリティーに関する考慮事項

An attacker with the ability to delete, delay, or insert messages into the flow can fake congestion signals, unless they are passed on a tamper-proof path. Since some possible algorithms depend on the timing of packet arrival, even a traditional, protected channel does not fully mitigate such attacks.

フローにメッセージを削除、遅延、挿入する能力を持つ攻撃者は、輻輳シグナルが改ざん防止されたパスで渡されない限り、輻輳シグナルを偽造できます。 考えられるアルゴリズムの中にはパケットの到着タイミングに依存するものもあるため、従来の保護されたチャネルであっても、そのような攻撃を完全には緩和できません。

An attack that reduces bandwidth is not necessarily significant, since an on-path attacker could break the connection by discarding all packets. Attacks that increase the perceived available bandwidth are conceivable and need to be evaluated. Such attacks could result in starvation of competing flows and permit amplification attacks.

経路上の攻撃者はすべてのパケットを破棄することによってコネクションを切断できるため、帯域幅を減少させる攻撃は必ずしも重大ではありません。 認識される利用可能な帯域幅を増加させる攻撃は考えられるものであり、評価する必要があります。 そのような攻撃は、競合するフローの枯渇を招き、増幅攻撃を可能にするおそれがあります。

Algorithm designers should consider the possibility of malicious on-path attackers.

アルゴリズムの設計者は、悪意のある経路上の攻撃者の可能性を考慮すべきです。
