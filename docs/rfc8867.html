RFC 8867

Test Cases for Evaluating Congestion Control for Interactive Real-Time Media

RFC 8867

対話型リアルタイムメディアの輻輳制御を評価するためのテストケース

Abstract

概要

The Real-time Transport Protocol (RTP) is used to transmit media in multimedia telephony applications. These applications are typically required to implement congestion control. This document describes the test cases to be used in the performance evaluation of such congestion control algorithms in a controlled environment.

リアルタイム転送プロトコル（RTP）は、マルチメディア電話アプリケーションでメディアを伝送するために使われます。 これらのアプリケーションは通常、輻輳制御の実装が求められます。 この文書では、そのような輻輳制御アルゴリズムの性能を管理された環境で評価する際に使うテストケースについて説明します。

1. Introduction

1. はじめに

This memo describes a set of test cases for evaluating congestion control algorithm proposals in controlled environments for real-time interactive media. It is based on the guidelines enumerated in [RFC8868] and the requirements discussed in [RFC8836]. The test cases cover basic usage scenarios and are described using a common structure, which allows for additional test cases to be added to those described herein to accommodate other topologies and/or the modeling of different path characteristics. The described test cases in this memo should be used to evaluate any proposed congestion control algorithm for real-time interactive media.

このメモでは、リアルタイムの対話型メディア向けに提案された輻輳制御アルゴリズムを、管理された環境で評価するための一連のテストケースについて説明します。 これは、[RFC8868]に列挙されたガイドラインと、[RFC8836]で議論されている要件に基づいています。 テストケースは基本的な利用シナリオを対象としており、共通の構造を使って記述されています。 この構造により、他のトポロジーや異なるパス特性のモデル化に対応するために、ここで説明するテストケースに追加のテストケースを加えることができます。 リアルタイムの対話型メディア向けに提案されるあらゆる輻輳制御アルゴリズムの評価には、このメモで説明するテストケースを使うべきです。

2. Terminology

2. 用語

The terminology defined in RTP [RFC3550], RTP Profile for Audio and Video Conferences with Minimal Control [RFC3551], RTCP Extended Report (XR) [RFC3611], Extended RTP Profile for RTCP-based Feedback (RTP/AVPF) [RFC4585], and Support for Reduced-Size RTCP [RFC5506] applies.

RTP[RFC3550]、 RTP Profile for Audio and Video Conferences with Minimal Control[RFC3551]、RTCP Extended Report (XR)[RFC3611]、Extended RTP Profile for RTCP-based Feedback (RTP/AVPF)[RFC4585]、およびSupport for Reduced-Size RTCP[RFC5506]で定義されている用語を適用します。

3. Structure of Test Cases

3. テストケースの構造

All the test cases in this document follow a basic structure allowing implementers to describe a new test scenario without repeatedly explaining common attributes. The structure includes a general description section that describes the test case and its motivation. Additionally the test case defines a set of attributes that characterize the testbed, for example, the network path between communicating peers and the diverse traffic sources.

この文書のすべてのテストケースは基本的な構造に従っており、実装者は共通の属性を繰り返し説明することなく新しいテストシナリオを記述できます。 この構造には、テストケースとその動機を説明する概要のセクションが含まれます。 さらに、テストケースはテストベッドを特徴付ける一連の属性を定義します。たとえば、通信するピア間のネットワークパスや、さまざまなトラフィックソースなどです。

Define the test case:


General description:
describes the motivation and the goals of the test case.
Expected behavior:
describes the desired rate adaptation behavior.
List of metrics to evaluate the desired behavior:
this indicates the minimum set of metrics (e.g., link utilization, media sending rate) that a proposed algorithm needs to measure to validate the expected rate adaptation behavior. It should also indicate the time granularity (e.g., averaged over 10 ms, 100 ms, or 1 s) for measuring certain metrics. Typical measurement interval is 200 ms.
Define testbed topology:


Every test case needs to define an evaluation testbed topology. Figure 1 shows such an evaluation topology. In this evaluation topology, S1..Sn are traffic sources. These sources generate media traffic and use the congestion control algorithm(s) under investigation. R1..Rn are the corresponding receivers. A test case can have one or more such traffic sources (S) and their corresponding receivers (R). The path from the source to destination is denoted as "forward", and the path from a destination to a source is denoted as "backward". The following basic structure of the test case has been described from the perspective of media-generating endpoints attached on the left-hand side of Figure 1. In this setup, the media flows are transported in the forward direction, and the corresponding feedback/control messages are transported in the backward direction. However, it is also possible to set up the test with media in both forward and backward directions. In that case, unless otherwise specified by the test case, it is expected that the backward path does not introduce any congestion-related impairments and has enough capacity to accommodate both media and feedback/control messages. It should be noted that, depending on the test cases, it is possible to have different path characteristics in either of the directions.

In a testbed environment with real equipment, there may exist a significant amount of unwanted traffic on the portions of the network path between the endpoints. Some of this traffic may be generated by other processes on the endpoints themselves (e.g., discovery protocols) or by other endpoints not presently under test. Such unwanted traffic should be removed or avoided to the greatest extent possible.

Define testbed attributes:


Duration:
defines the duration of the test in seconds.
Path characteristics:

defines the end-to-end transport level path characteristics of the testbed for a particular test case. Two sets of attributes describe the path characteristics, one for the forward path and the other for the backward path. The path characteristics for a particular path direction are applicable to all the sources "S" sending traffic on that path. If only one attribute is specified, it is used for both path directions; however, unless specified the reverse path has no capacity restrictions and no path loss.

Path direction:
forward or backward.
Minimum bottleneck-link capacity:
defines the minimum capacity of the end-to-end path.
Reference bottleneck capacity:
defines a reference value for the bottleneck capacity for test cases with time-varying bottleneck capacities. All bottleneck capacities will be specified as a ratio with respect to the reference capacity value.
One-way propagation delay:
describes the end-to-end latency along the path when network queues are empty, i.e., the time it takes for a packet to go from the sender to the receiver without encountering any queuing delay.
Maximum end-to-end jitter:
defines the maximum jitter that can be observed along the path.
Bottleneck queue type:
for example, "tail drop" [RFC7567], Flow Queue Controlled Delay (FQ-CoDel) [RFC8290], or Proportional Integral controller Enhanced (PIE) [RFC8033].
Bottleneck queue size:
defines the size of queue in terms of queuing time when the queue is full (in milliseconds).
Path loss ratio:
characterizes the non-congested, additive losses to be generated on the end-to-end path. This must describe the loss pattern or loss model used to generate the losses.
Application-related:

defines the traffic source behavior for implementing the test case:

Media traffic source:

defines the characteristics of the media sources. When using more than one media source, the different attributes are enumerated separately for each different media source.

Media type:
Video/Voice.
Media flow direction:
forward, backward, or both.
Number of media sources:
defines the total number of media sources.
Media codec:
Constant Bit Rate (CBR) or Variable Bit Rate (VBR).
Media source behavior:

describes the media encoder behavior. It defines the main parameters that affect the adaptation behavior. This may include but is not limited to the following:

Adaptability:
describes the adaptation options. For example, in the case of video, it defines the following ranges of adaptation: bit rate, frame rate, and video resolution. Similarly, in the case of voice, it defines the range of bit rate adaptation, the sampling rate variation, and the variation in packetization interval.
Output variation:
for a VBR encoder, it defines the encoder output variation from the average target rate over a particular measurement interval. For example, on average the encoder output may vary between 5% to 15% above or below the average target bit rate when measured over a 100 ms time window. The time interval over which the variation is specified must be provided.
Responsiveness to a new bit rate request:
the lag in time between a new bit rate request from the congestion control algorithm and actual rate changes in encoder output. Depending on the encoder, this value may be specified in absolute time (e.g., 10 ms to 1000 ms) or other appropriate metric (e.g., next frame interval time).

More detailed discussions on expected media source behavior, including those from synthetic video traffic sources, can be found in [RFC8593].

Media content:
describes the chosen video scenario. For example, video test sequences are available at [xiph-seq] and [HEVC-seq]. Different video scenarios give different distributions of video frames produced by the video encoder. Hence, it is important to specify the media content used in a particular test. If a synthetic video traffic source [RFC8593] is used, then the synthetic video traffic source needs to be configured according to the characteristics of the media content specified.
Media timeline:
describes the point when the media source is introduced and removed from the testbed. For example, the media source may start transmitting immediately when the test case begins, or after a few seconds.
Startup behavior:
the media starts at a defined bit rate, which may be the minimum, maximum bit rate, or a value in between (in Kbps).
Competing traffic source:

describes the characteristics of the competing traffic source, the different types of competing flows are enumerated in [RFC8868].

Traffic direction:
forward, backward, or both.
Type of sources:
defines the types of competing traffic sources. Types of competing traffic flows are listed in [RFC8868]. For example, the number of TCP flows connected to a web browser, the mean size and distribution of the content downloaded.
Number of sources:
defines the total number of competing sources of each media type per traffic direction.
Congestion control:
enumerates the congestion control used by each type of competing traffic.
Traffic timeline:
describes when the competing traffic starts and ends in the test case.
Additional attributes:
describes attributes essential for implementing a test case that are not included in the above structure. These attributes must be well defined, so that the other implementers of that particular test case are able to implement it easily.
テストケースの定義：


概要：
テストケースの動機と目的を説明します。
期待される動作：
望ましいレート適応の動作を説明します。
期待される動作を評価するためのメトリックの一覧：
これは、期待されるレート適応の動作を検証するために、提案されたアルゴリズムが測定する必要のある最小限のメトリックの集合（たとえば、リンク使用率、メディアの送信レート）を示します。 また、特定のメトリックを測定する時間の粒度（たとえば、10 ms、100 ms、または1 sでの平均）も示すべきです。 典型的な測定間隔は200 msです。
テストベッドのトポロジーの定義：


すべてのテストケースは、評価用のテストベッドのトポロジーを定義する必要があります。 Figure 1は、そのような評価用トポロジーを示しています。 この評価用トポロジーにおいて、S1..Snはトラフィックソースです。 これらのソースはメディアトラフィックを生成し、調査対象の輻輳制御アルゴリズムを使います。 R1..Rnは対応する受信者です。 テストケースには、このようなトラフィックソース（S）とそれに対応する受信者（R）が1つ以上含まれます。 ソースから宛先へのパスを「順方向（forward）」、宛先からソースへのパスを「逆方向（backward）」と表記します。 以下のテストケースの基本構造は、Figure 1の左側に接続されたメディアを生成するエンドポイントの観点から記述しています。 この構成では、メディアフローは順方向に転送され、対応するフィードバック／制御メッセージは逆方向に転送されます。 ただし、順方向と逆方向の両方にメディアを流すテストを構成することもできます。 その場合、テストケースで特に指定がない限り、逆方向のパスは輻輳に関連する障害を発生させず、メディアとフィードバック／制御メッセージの両方を収容するのに十分な容量を持つことが想定されます。 テストケースによっては、どちらの方向にも異なるパス特性を持たせることができる点に注意してください。

実機を使ったテストベッド環境では、エンドポイント間のネットワークパスの一部に、望ましくないトラフィックが大量に存在する場合があります。 このトラフィックの一部は、エンドポイント自体の他のプロセス（たとえば、ディスカバリープロトコル）や、現在テスト対象ではない他のエンドポイントによって生成される可能性があります。 このような望ましくないトラフィックは、可能な限り除去するか回避すべきです。

テストベッドの属性の定義：


継続時間：
テストの継続時間を秒単位で定義します。
パス特性：

特定のテストケースについて、テストベッドのエンドツーエンドのトランスポートレベルのパス特性を定義します。 パス特性は2組の属性で記述され、一方は順方向のパス用、もう一方は逆方向のパス用です。 特定のパス方向のパス特性は、そのパスでトラフィックを送信するすべてのソース「S」に適用されます。 属性が1つしか指定されていない場合、その属性は両方のパス方向に使われます。 ただし、指定がない限り、逆方向のパスには容量の制限もパス損失もありません。

パスの方向：
順方向または逆方向。
最小ボトルネックリンク容量：
エンドツーエンドのパスの最小容量を定義します。
基準ボトルネック容量：
ボトルネック容量が時間とともに変化するテストケースのために、ボトルネック容量の基準値を定義します。 すべてのボトルネック容量は、基準容量の値に対する比率として指定します。
片方向伝搬遅延：
ネットワークのキューが空のときのパスに沿ったエンドツーエンド遅延、すなわち、パケットがキューイング遅延にまったく遭遇せずに送信者から受信者に到達するまでにかかる時間を表します。
最大エンドツーエンドジッター：
パスに沿って観測されうる最大のジッターを定義します。
ボトルネックキューの種類：
たとえば、「テールドロップ（tail drop）」[RFC7567]、 Flow Queue Controlled Delay（FQ-CoDel）[RFC8290]、 またはProportional Integral controller Enhanced（PIE）[RFC8033]です。
ボトルネックキューのサイズ：
キューが満杯のときのキューイング時間（ミリ秒単位）によって、キューのサイズを定義します。
パス損失率：
エンドツーエンドのパス上で発生させる、輻輳によらない付加的な損失を特徴付けます。 これには、損失を発生させるために使う損失パターンまたは損失モデルを記述しなければなりません。
アプリケーション関連：

テストケースを実装するためのトラフィックソースの動作を定義します。

メディアトラフィックソース：

メディアソースの特性を定義します。 複数のメディアソースを使う場合は、異なるメディアソースごとに、それぞれの属性を個別に列挙します。

メディアタイプ：
ビデオ／音声。
メディアフローの方向：
順方向、逆方向、または両方。
メディアソースの数：
メディアソースの総数を定義します。
メディアコーデック：
固定ビットレート（CBR）または可変ビットレート（VBR）。
メディアソースの動作：

メディアエンコーダーの動作を説明します。 これは、適応の動作に影響を与える主なパラメーターを定義します。 これには以下が含まれますが、これらに限定されません。

適応性：
適応の選択肢を説明します。 たとえば、ビデオの場合は、ビットレート、フレームレート、ビデオ解像度という適応の範囲を定義します。 同様に、音声の場合は、ビットレート適応の範囲、サンプリングレートの変動、パケット化間隔の変動を定義します。
出力変動：
VBRエンコーダーの場合、特定の測定間隔における平均目標レートからのエンコーダー出力の変動を定義します。 たとえば、100 msの時間窓で測定した場合、エンコーダー出力は平均すると平均目標ビットレートの上下5%から15%の間で変動することがあります。 変動を規定する時間間隔を示さなければなりません。
新しいビットレート要求への応答性：
輻輳制御アルゴリズムからの新しいビットレート要求と、エンコーダー出力の実際のレート変化との間の時間的な遅れです。 エンコーダーによっては、この値を絶対時間（たとえば、10 msから1000 ms）または他の適切なメトリック（たとえば、次のフレーム間隔の時間）で指定する場合があります。

合成ビデオトラフィックソースによるものも含め、期待されるメディアソースの動作についてのより詳細な議論は、[RFC8593]にあります。

メディアコンテンツ：
選択したビデオシナリオを説明します。 たとえば、ビデオのテストシーケンスは[xiph-seq]や[HEVC-seq]で入手できます。 ビデオシナリオが異なると、ビデオエンコーダーが生成するビデオフレームの分布も異なります。 したがって、特定のテストで使うメディアコンテンツを指定することが重要です。 合成ビデオトラフィックソース[RFC8593]を使う場合は、指定したメディアコンテンツの特性に従って合成ビデオトラフィックソースを設定する必要があります。
メディアのタイムライン：
メディアソースをテストベッドに導入する時点と、テストベッドから取り除く時点を説明します。 たとえば、メディアソースはテストケースの開始直後に送信を始めることもあれば、数秒後に始めることもあります。
起動時の動作：
メディアは定められたビットレートで開始します。これは最小ビットレート、最大ビットレート、またはその間の値（Kbps単位）です。
競合トラフィックソース：

競合トラフィックソースの特性を説明します。 さまざまな種類の競合フローが[RFC8868]に列挙されています。

トラフィックの方向：
順方向、逆方向、または両方。
ソースの種類：
競合トラフィックソースの種類を定義します。 競合トラフィックフローの種類は[RFC8868]に列挙されています。 たとえば、Webブラウザーに接続されたTCPフローの数や、ダウンロードされるコンテンツの平均サイズと分布です。
ソースの数：

5.3. Congested Feedback Link with Bi-directional Media Flows

5.3. 双方向メディアフローでのフィードバックリンクの輻輳

Real-time interactive media uses RTP; hence it is assumed that RTCP, RTP header extension, or such would be used by the congestion control algorithm in the back channel. Due to the asymmetric nature of the link between communicating peers, it is possible for a participating peer to not receive such feedback information due to an impaired or congested back channel (even when the forward channel might not be impaired). This test case is designed to observe the candidate congestion control behavior in such an event.

5.8. Media Pause and Resume

5.8. メディアの一時停止と再開

In this test case, more than one real-time interactive media flow share the link bandwidth, and all flows reach to a steady state by utilizing the link capacity in an optimum way. At this stage, one of the media flows is paused for a moment. This event will result in more available bandwidth for the rest of the flows as they are on a shared link. When the paused media flow resumes, it no longer has the same bandwidth share on the link. It has to make its way through the other existing flows in the link to achieve a fair share of the link capacity. This test case is important specially for real-time interactive media, which consists of more than one media flows and can pause/resume media flows at any point of time during the session. This test case directly addresses requirement 5 in Section 2 of [RFC8836]. One can think of it as a variation of the test case defined in Section 5.4. However, it is different as the candidate algorithms can use different strategies to increase efficiency, for example, in terms of fairness, convergence time, oscillation reduction, etc., by capitalizing on the fact that they have previous information of the link.

このテストケースでは、複数のリアルタイムの対話型メディアフローがリンクの帯域幅を共有し、すべてのフローがリンク容量を最適な方法で利用して定常状態に達します。 この段階で、メディアフローの1つを一時的に停止します。 フローは共有リンク上にあるので、この事象によって残りのフローが利用できる帯域幅が増えます。 一時停止していたメディアフローが再開したとき、そのフローはもはやリンク上で同じ帯域幅の配分を持っていません。 そのフローは、リンク容量の公平な配分を得るために、リンク上の既存の他のフローの間に割り込んでいかなければなりません。 このテストケースは、複数のメディアフローで構成され、セッション中の任意の時点でメディアフローを一時停止／再開できるリアルタイムの対話型メディアにとって特に重要です。 このテストケースは、[RFC8836]のSection 2の要件5に直接対応します。 これはSection 5.4で定義したテストケースの変形と考えることもできます。 しかし、候補のアルゴリズムはリンクに関する以前の情報を持っていることを活用して、たとえば公平性、収束時間、振動の低減などの観点で効率を高めるために異なる戦略を使える点で異なります。

6. Other Potential Test Cases

6. その他の候補となるテストケース

It has been noticed that there are other interesting test cases besides the basic test cases listed above. In many aspects, these additional test cases can help further evaluation of the candidate algorithm. They are listed below.

上記の基本的なテストケース以外にも、興味深いテストケースがあることがわかっています。 これらの追加のテストケースは、多くの面で候補のアルゴリズムのさらなる評価に役立ちます。 以下にそれらを示します。

6.1. Media Flows with Priority

6.1. 優先度付きのメディアフロー

In this test case, media flows will have different priority levels. This is an extension of Section 5.4 where the same test is run with different priority levels imposed on each of the media flows. For example, the first flow (S1) is assigned a priority of 2, whereas the remaining two flows (S2 and S3) are assigned a priority of 1. The candidate algorithm must reflect the relative priorities assigned to each media flow. In this case, the first flow (S1) must arrive at a steady-state rate approximately twice that of the other two flows (S2 and S3).

このテストケースでは、メディアフローはそれぞれ異なる優先度レベルを持ちます。 これはSection 5.4を拡張したもので、各メディアフローに異なる優先度レベルを課して同じテストを実行します。 たとえば、最初のフロー（S1）には優先度2を割り当て、残りの2つのフロー（S2とS3）には優先度1を割り当てます。 候補のアルゴリズムは、各メディアフローに割り当てられた相対的な優先度を反映しなければなりません。 この場合、最初のフロー（S1）は、他の2つのフロー（S2とS3）のおよそ2倍の定常状態のレートに到達しなければなりません。

The candidate algorithm can use a coupled congestion control mechanism [RFC8699] or use a weighted priority scheduler for the bandwidth distribution according to the respective media flow priority or use.

候補のアルゴリズムは、結合輻輳制御メカニズム[RFC8699]を使うこともできますし、各メディアフローの優先度や用途に応じて帯域幅を配分するために重み付き優先度スケジューラーを使うこともできます。

6.2. Explicit Congestion Notification Usage

6.2. 明示的輻輳通知の使用

This test case requires running all the basic test cases with the availability of Explicit Congestion Notification (ECN) [RFC6679] feature enabled. The goal of this test is to exhibit that the candidate algorithms do not fail when ECN signals are available. With ECN signals enabled, the algorithms are expected to perform better than their delay-based variants.

このテストケースでは、明示的輻輳通知（ECN）[RFC6679]の機能を有効にした状態で、すべての基本的なテストケースを実行する必要があります。 このテストの目的は、ECNシグナルが利用可能なときに候補のアルゴリズムが失敗しないことを示すことです。 ECNシグナルを有効にすると、アルゴリズムは遅延ベースの変種よりも良い性能を発揮することが期待されます。

6.3. Multiple Bottlenecks

6.3. 複数のボトルネック

In this test case, one congestion-controlled media flow, S1->R1, traverses a path with multiple bottlenecks. As illustrated in Figure 7, the first flow (S1->R1) competes with the second congestion-controlled media flow (S2->R2) over the link between A and B, which is close to the sender side. Again, that flow (S1->R1) competes with the third congestion-controlled media flow (S3->R3) over the link between C and D, which is close to the receiver side. The goal of this test is to ensure that the candidate algorithms work properly in the presence of multiple bottleneck links on the end-to-end path.

このテストケースでは、1つの輻輳制御されたメディアフローS1->R1が、複数のボトルネックを持つパスを通過します。 Figure 7に示すように、最初のフロー（S1->R1）は、送信者側に近いAとBの間のリンクで、2番目の輻輳制御されたメディアフロー（S2->R2）と競合します。 さらに、そのフロー（S1->R1）は、受信者側に近いCとDの間のリンクで、3番目の輻輳制御されたメディアフロー（S3->R3）と競合します。 このテストの目的は、エンドツーエンドのパス上に複数のボトルネックリンクが存在する場合でも、候補のアルゴリズムが適切に動作することを確認することです。

8. Security Considerations

8. セキュリティーに関する考慮事項

The security considerations in Section 6 of [RFC8868] and the relevant congestion control algorithms apply. The principles for congestion control are described in [RFC2914], and in particular any new method must implement safeguards to avoid congestion collapse of the Internet.

[RFC8868]のSection 6および関連する輻輳制御アルゴリズムのセキュリティーに関する考慮事項が適用されます。 輻輳制御の原則は[RFC2914]で説明されており、特に新しい手法はいずれも、インターネットの輻輳崩壊を避けるための安全策を実装しなければなりません。

The evaluation of the test cases are intended to be run in a controlled lab environment. Hence, the applications, simulators, and network nodes ought to be well-behaved and should not impact the desired results. Moreover, proper measures must be taken to avoid leaking nonresponsive traffic from unproven congestion avoidance techniques onto the open Internet.

テストケースの評価は、管理されたラボ環境で実行することを意図しています。 そのため、アプリケーション、シミュレーター、ネットワークノードは適切に動作し、望ましい結果に影響を与えないようにすべきです。 さらに、実績のない輻輳回避技術による応答しないトラフィックが、オープンなインターネットに漏れ出すことを避けるために、適切な対策を講じなければなりません。
