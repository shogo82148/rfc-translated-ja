RFC 8537

Updates to the Fast Reroute Procedures for Co-routed Associated Bidirectional Label Switched Paths (LSPs)

RFC 8537

同一経路の関連付けられた双方向ラベルスイッチパス（LSP）のための高速リルート手順の更新

Abstract

概要

Resource Reservation Protocol (RSVP) association signaling can be used to bind two unidirectional Label Switched Paths (LSPs) into an associated bidirectional LSP. When an associated bidirectional LSP is co-routed, the reverse LSP follows the same path as its forward LSP. This document updates the fast reroute procedures defined in RFC 4090 to support both single-sided and double-sided provisioned associated bidirectional LSPs. This document also updates the procedure for associating two reverse LSPs defined in RFC 7551 to support co-routed bidirectional LSPs. The fast reroute procedures can ensure that, for the co-routed LSPs, traffic flows on co-routed paths in the forward and reverse directions after a failure event.

リソース予約プロトコル（RSVP）のアソシエーションシグナリングを使用すると、2つの単方向ラベルスイッチパス（LSP）を、関連付けられた双方向LSP（associated bidirectional LSP）に結び付けることができます。関連付けられた双方向LSPが同一経路（co-routed）である場合、逆方向LSPは順方向LSPと同じパスをたどります。この文書は、片側プロビジョニングと両側プロビジョニングの両方の関連付けられた双方向LSPをサポートするために、RFC 4090で定義されている高速リルート手順を更新します。この文書はまた、同一経路の双方向LSPをサポートするために、RFC 7551で定義されている2つの逆方向LSPを関連付ける手順も更新します。この高速リルート手順により、同一経路のLSPについて、障害発生後も順方向と逆方向のトラフィックが同一経路のパスを流れることを保証できます。

1. Introduction

1. はじめに

The Resource Reservation Protocol (RSVP) (Extended) ASSOCIATION Object is specified in [RFC6780] and can be used generically to associate Multiprotocol Label Switching (MPLS) and Generalized MPLS (GMPLS) Traffic Engineering (TE) Label Switched Paths (LSPs). [RFC7551] defines mechanisms for binding two point-to-point (P2P) unidirectional LSPs [RFC3209] into an associated bidirectional LSP. There are two models described in [RFC7551] for provisioning an associated bidirectional LSP: single-sided and double-sided. In both models, the reverse LSP of the bidirectional LSP may or may not be co-routed and follow the same path as its forward LSP.

リソース予約プロトコル（RSVP）の（Extended）ASSOCIATIONオブジェクトは[RFC6780]で規定されており、マルチプロトコルラベルスイッチング（MPLS）および汎用MPLS（GMPLS）のトラフィックエンジニアリング（TE）ラベルスイッチパス（LSP）を関連付けるために汎用的に使用できます。[RFC7551]は、2つのポイントツーポイント（P2P）の単方向LSP[RFC3209]を、関連付けられた双方向LSPに結び付けるためのメカニズムを定義しています。[RFC7551]では、関連付けられた双方向LSPをプロビジョニングするためのモデルとして、片側（single-sided）と両側（double-sided）の2つが説明されています。どちらのモデルでも、双方向LSPの逆方向LSPは、同一経路で順方向LSPと同じパスをたどる場合もあれば、そうでない場合もあります。

In some packet transport networks, there are requirements where the reverse LSP of a bidirectional LSP needs to follow the same path as its forward LSP [RFC6373]. The MPLS Transport Profile (MPLS-TP) [RFC6370] architecture facilitates the co-routed bidirectional LSP by using GMPLS extensions [RFC3473] to achieve congruent paths. However, RSVP association signaling allows enabling co-routed bidirectional LSPs without having to deploy GMPLS extensions in the existing networks. The association signaling also allows taking advantage of the existing TE and fast reroute mechanisms in the network.

一部のパケットトランスポートネットワークでは、双方向LSPの逆方向LSPが順方向LSPと同じパスをたどる必要があるという要件があります[RFC6373]。MPLSトランスポートプロファイル（MPLS-TP）[RFC6370]のアーキテクチャーは、GMPLS拡張[RFC3473]を使用して一致したパスを実現することで、同一経路の双方向LSPを容易にしています。しかし、RSVPのアソシエーションシグナリングを使えば、既存のネットワークにGMPLS拡張を展開しなくても、同一経路の双方向LSPを有効にできます。また、アソシエーションシグナリングを使えば、ネットワーク内の既存のTEおよび高速リルートのメカニズムを活用することもできます。

[RFC4090] defines fast reroute extensions for RSVP-TE LSPs, which are also applicable to the associated bidirectional LSPs. [RFC8271] defines fast reroute procedures for GMPLS signaled bidirectional LSPs such as coordinating bypass tunnel assignments in the forward and reverse directions of the LSP. The mechanisms defined in [RFC8271] are also useful for the fast reroute of associated bidirectional LSPs.

[RFC4090]は、RSVP-TE LSPのための高速リルート拡張を定義しており、これは関連付けられた双方向LSPにも適用できます。[RFC8271]は、LSPの順方向と逆方向でバイパストンネルの割り当てを調整するなど、GMPLSでシグナリングされる双方向LSPのための高速リルート手順を定義しています。[RFC8271]で定義されているメカニズムは、関連付けられた双方向LSPの高速リルートにも役立ちます。

This document updates the fast reroute procedures defined in [RFC4090] to support both single-sided and double-sided provisioned associated bidirectional LSPs. This document also updates the procedure for associating two reverse LSPs defined in [RFC7551] to support co-routed bidirectional LSPs. The fast reroute procedures can ensure that for the co-routed LSPs, traffic flows on co-routed paths in the forward and reverse directions after fast reroute.

この文書は、片側プロビジョニングと両側プロビジョニングの両方の関連付けられた双方向LSPをサポートするために、[RFC4090]で定義されている高速リルート手順を更新します。この文書はまた、同一経路の双方向LSPをサポートするために、[RFC7551]で定義されている2つの逆方向LSPを関連付ける手順も更新します。この高速リルート手順により、同一経路のLSPについて、高速リルート後も順方向と逆方向のトラフィックが同一経路のパスを流れることを保証できます。

1.1. Assumptions and Considerations

1.1. 前提と考慮事項

The following assumptions and considerations apply to this document:

この文書には、次の前提と考慮事項が適用されます：

  • The fast reroute procedure for the unidirectional LSPs is defined in [RFC4090] and is not modified by this document.
  • The fast reroute procedure when using unidirectional bypass tunnels is defined in [RFC4090] and is not modified by this document.
  • This document assumes that the fast reroute bypass tunnels used for protected associated bidirectional LSPs are also associated bidirectional.
  • This document assumes that the fast reroute bypass tunnels used for protected co-routed associated bidirectional LSPs are also co-routed associated bidirectional.
  • The fast reroute procedure to coordinate the bypass tunnel assignment defined in this document may be used for protected associated bidirectional LSPs that are not co-routed but requires that the downstream Point of Local Repair (PLR) and Merge Point (MP) pair of the forward LSP matches the upstream MP and PLR pair of the reverse LSP.
  • Unless otherwise specified in this document, the fast reroute procedures defined in [RFC4090] are used for associated bidirectional LSPs.
  • 単方向LSPのための高速リルート手順は[RFC4090]で定義されており、この文書では変更しません。
  • 単方向のバイパストンネルを使用する場合の高速リルート手順は[RFC4090]で定義されており、この文書では変更しません。
  • この文書は、保護対象の関連付けられた双方向LSPに使用する高速リルートのバイパストンネルも、関連付けられた双方向であることを前提とします。
  • この文書は、保護対象の同一経路の関連付けられた双方向LSPに使用する高速リルートのバイパストンネルも、同一経路の関連付けられた双方向であることを前提とします。
  • この文書で定義する、バイパストンネルの割り当てを調整するための高速リルート手順は、同一経路ではない保護対象の関連付けられた双方向LSPにも使用できます。ただしその場合は、順方向LSPの下流側のローカル修復ポイント（PLR: Point of Local Repair）とマージポイント（MP: Merge Point）の組が、逆方向LSPの上流側のMPとPLRの組と一致している必要があります。
  • この文書で特に規定しない限り、関連付けられた双方向LSPには[RFC4090]で定義されている高速リルート手順を使用します。

2.2. 用語

2.2.1. Forward Unidirectional LSPs

2.2.1. 順方向の単方向LSP

Two reverse unidirectional P2P LSPs are set up in opposite directions between a pair of source and destination nodes to form an associated bidirectional LSP. In the case of single-sided provisioned LSP, the originating LSP with a REVERSE_LSP Object [RFC7551] is identified as a forward unidirectional LSP. In the case of double-sided provisioned LSP, the LSP originating from the higher node address (as source) and terminating on the lower node address (as destination) is identified as a forward unidirectional LSP.

関連付けられた双方向LSPを形成するために、送信元ノードと宛先ノードの組の間で、互いに逆向きの2つの単方向P2P LSPを反対方向に設定します。片側プロビジョニングされたLSPの場合は、REVERSE_LSPオブジェクト[RFC7551]を持つ起点側のLSPを、順方向の単方向LSPとみなします。両側プロビジョニングされたLSPの場合は、大きいほうのノードアドレス（送信元）から始まり、小さいほうのノードアドレス（宛先）で終わるLSPを、順方向の単方向LSPとみなします。

2.2.2. Reverse Co-routed Unidirectional LSPs

2.2.2. 逆方向の同一経路の単方向LSP

Two reverse unidirectional P2P LSPs are set up in opposite directions between a pair of source and destination nodes to form an associated bidirectional LSP. A reverse unidirectional LSP originates on the same node where the forward unidirectional LSP terminates, and it terminates on the same node where the forward unidirectional LSP originates. A reverse co-routed unidirectional LSP traverses along the same path as the forward-direction unidirectional LSP in the opposite direction.

関連付けられた双方向LSPを形成するために、送信元ノードと宛先ノードの組の間で、互いに逆向きの2つの単方向P2P LSPを反対方向に設定します。逆方向の単方向LSPは、順方向の単方向LSPが終端するノードと同じノードから始まり、順方向の単方向LSPが始まるノードと同じノードで終端します。逆方向の同一経路の単方向LSPは、順方向の単方向LSPと同じパスを反対方向にたどります。

3. Problem Statement

3. 問題の記述

As specified in [RFC7551], in the single-sided provisioning case, the RSVP-TE tunnel is configured only on one endpoint node of the bidirectional LSP. An LSP for this tunnel is initiated by the originating endpoint with the (Extended) ASSOCIATION Object containing Association Type set to "Single-Sided Associated Bidirectional LSP" and the REVERSE_LSP Object inserted in the RSVP Path message. The remote endpoint then creates the corresponding reverse TE tunnel and signals the reverse LSP in response using the information from the REVERSE_LSP Object and other objects present in the received RSVP Path message. As specified in [RFC7551], in the double-sided provisioning case, the RSVP-TE tunnel is configured on both endpoint nodes of the bidirectional LSP. Both forward and reverse LSPs are initiated independently by the two endpoints with the (Extended) ASSOCIATION Object containing Association Type set to "Double-Sided Associated Bidirectional LSP". With both single-sided and double-sided provisioned bidirectional LSPs, the reverse LSP may or may not be congruent (i.e., co-routed) and follow the same path as its forward LSP.

[RFC7551]で規定されているように、片側プロビジョニングの場合、RSVP-TEトンネルは双方向LSPの一方のエンドポイントノードだけに設定されます。このトンネルのLSPは、起点側のエンドポイントが、Association Typeを「Single-Sided Associated Bidirectional LSP」に設定した（Extended）ASSOCIATIONオブジェクトと、REVERSE_LSPオブジェクトをRSVP Pathメッセージに挿入して開始します。次に、リモートのエンドポイントが、対応する逆方向のTEトンネルを作成し、受信したRSVP Pathメッセージに含まれるREVERSE_LSPオブジェクトやその他のオブジェクトの情報を使用して、応答として逆方向LSPをシグナリングします。[RFC7551]で規定されているように、両側プロビジョニングの場合、RSVP-TEトンネルは双方向LSPの両方のエンドポイントノードに設定されます。順方向LSPと逆方向LSPはどちらも、Association Typeを「Double-Sided Associated Bidirectional LSP」に設定した（Extended）ASSOCIATIONオブジェクトを使用して、2つのエンドポイントによってそれぞれ独立に開始されます。片側プロビジョニングと両側プロビジョニングのどちらの双方向LSPでも、逆方向LSPは、一致した（つまり、同一経路の）パスで順方向LSPと同じパスをたどる場合もあれば、そうでない場合もあります。

Both single-sided and double-sided associated bidirectional LSPs require solutions to the following issues for fast reroute to ensure co-routing after a failure event.

片側と両側のどちらの関連付けられた双方向LSPでも、障害発生後に同一経路を保証するためには、高速リルートについて次の問題を解決する必要があります。

3.1. Fast Reroute Bypass Tunnel Assignment

3.1. 高速リルートのバイパストンネルの割り当て

In order to ensure that the traffic flows on a co-routed path after a link or node failure on the protected co-routed LSP path, the midpoint PLR nodes need to assign matching bidirectional bypass tunnels for fast reroute. Such bypass assignment requires coordination between the PLR nodes in both the forward and reverse directions when more than one bypass tunnel is present on a PLR node.

保護対象の同一経路のLSPのパス上でリンクまたはノードの障害が発生した後もトラフィックが同一経路のパスを流れることを保証するためには、中間のPLRノードが、高速リルートのために対応する双方向バイパストンネルを割り当てる必要があります。PLRノード上に複数のバイパストンネルが存在する場合、このようなバイパスの割り当てには、順方向と逆方向の両方のPLRノード間の調整が必要です。

As shown in Figure 1, there are two bypass tunnels available: bypass tunnel N (on path B-H-I-C) and bypass tunnel S (on path B-F-G-C). The midpoint PLR nodes B and C need to coordinate bypass tunnel assignment to ensure that traffic in both directions flows through either bypass tunnel N or bypass tunnel S after the link B-C failure.

Figure 1に示すように、利用可能なバイパストンネルは、バイパストンネルN（パスB-H-I-C上）とバイパストンネルS（パスB-F-G-C上）の2つです。中間のPLRノードであるBとCは、リンクB-Cの障害後に両方向のトラフィックがバイパストンネルNとバイパストンネルSのどちらか一方を通って流れることを保証するために、バイパストンネルの割り当てを調整する必要があります。

3.2. Node Protection Bypass Tunnels

3.2. ノード保護バイパストンネル

When using a node protection bypass tunnel with a protected associated bidirectional LSP, after a link failure, the forward and reverse LSP traffic can flow on different node protection bypass tunnels in the upstream and downstream directions.

保護対象の関連付けられた双方向LSPでノード保護バイパストンネルを使用する場合、リンク障害の後、順方向と逆方向のLSPのトラフィックが、上流方向と下流方向で異なるノード保護バイパストンネルを流れる可能性があります。

As shown in Figure 2, after the link B-C failure, the downstream PLR node B reroutes the protected forward LSP1 traffic over bypass tunnel S (on path B-F-G-D) to reach downstream MP node D, whereas the upstream PLR node C reroutes the protected reverse LSP2 traffic over bypass tunnel N (on path C-I-H-A) to reach the upstream MP node A. As a result, the traffic in the forward and reverse directions flows on different bypass tunnels, which can cause the co-routed associated bidirectional LSP to be no longer co-routed. However, unlike GMPLS LSPs, the asymmetry of paths in the forward and reverse directions does not result in RSVP soft-state timeout with the associated bidirectional LSPs.

Figure 2に示すように、リンクB-Cの障害後、下流側のPLRノードBは、保護対象の順方向LSP1のトラフィックを、下流側のMPノードDに到達するようにバイパストンネルS（パスB-F-G-D上）へリルートします。一方、上流側のPLRノードCは、保護対象の逆方向LSP2のトラフィックを、上流側のMPノードAに到達するようにバイパストンネルN（パスC-I-H-A上）へリルートします。その結果、順方向と逆方向のトラフィックは異なるバイパストンネルを流れることになり、同一経路の関連付けられた双方向LSPが同一経路ではなくなる可能性があります。ただし、GMPLS LSPとは異なり、関連付けられた双方向LSPでは、順方向と逆方向でパスが非対称になっても、RSVPのソフトステートのタイムアウトは発生しません。

3.3. Bidirectional LSP Association at Midpoints

3.3. 中間ノードでの双方向LSPの関連付け

In packet transport networks, a restoration LSP is signaled after a link failure on the protected LSP path, and the protected LSP may or may not be torn down [RFC8131]. In this case, multiple forward and reverse LSPs of a co-routed associated bidirectional LSP may be present at midpoint nodes with identical (Extended) ASSOCIATION Objects. This creates an ambiguity at midpoint nodes to identify the correct associated LSP pair for fast reroute bypass assignment (e.g., during the recovery phase of the RSVP graceful restart procedure).

パケットトランスポートネットワークでは、保護対象のLSPのパス上でリンク障害が発生した後に復旧LSPがシグナリングされ、保護対象のLSPは解除される場合もあれば、されない場合もあります[RFC8131]。この場合、同一経路の関連付けられた双方向LSPの複数の順方向LSPと逆方向LSPが、同一の（Extended）ASSOCIATIONオブジェクトを持った状態で中間ノードに存在する可能性があります。そのため、中間ノードでは、高速リルートのバイパス割り当てのために正しい関連付けられたLSPの組を識別する際に、曖昧さが生じます（例：RSVPのグレースフルリスタート手順の回復フェーズ中など）。

As shown in Figure 3, the protected LSPs (LSP1 and LSP2) are an associated LSP pair; similarly, the restoration LSPs (LSP3 and LSP4) are an associated LSP pair. Both pairs belong to the same associated bidirectional LSP and carry identical (Extended) ASSOCIATION Objects. In this example, the midpoint node D may mistakenly associate LSP1 with the reverse LSP4 instead of the reverse LSP2 due to the matching (Extended) ASSOCIATION Objects. This may cause the co-routed associated bidirectional LSP to be no longer co-routed after fast reroute. Since the bypass assignment needs to be coordinated between the forward and reverse LSPs, this can also lead to undesired bypass tunnel assignments.

Figure 3に示すように、保護対象のLSP（LSP1とLSP2）は関連付けられたLSPの組であり、同様に、復旧LSP（LSP3とLSP4）も関連付けられたLSPの組です。どちらの組も同じ関連付けられた双方向LSPに属しており、同一の（Extended）ASSOCIATIONオブジェクトを運びます。この例では、中間ノードDは、（Extended）ASSOCIATIONオブジェクトが一致するために、LSP1を逆方向のLSP2ではなく逆方向のLSP4と誤って関連付けてしまう可能性があります。これにより、同一経路の関連付けられた双方向LSPが、高速リルート後に同一経路ではなくなる可能性があります。バイパスの割り当ては順方向LSPと逆方向LSPの間で調整する必要があるため、これは望ましくないバイパストンネルの割り当てにもつながる可能性があります。

4. Signaling Procedure

4. シグナリング手順

4.1. Associated Bidirectional LSP Fast Reroute

4.1. 関連付けられた双方向LSPの高速リルート

For both single-sided and double-sided associated bidirectional LSPs, the fast reroute procedure specified in [RFC4090] is used. In addition, the mechanisms defined in [RFC8271] are used as follows:

片側と両側のどちらの関連付けられた双方向LSPでも、[RFC4090]で規定されている高速リルート手順を使用します。加えて、[RFC8271]で定義されているメカニズムを次のように使用します：

  • The BYPASS_ASSIGNMENT IPv4 subobject (value 38) and IPv6 subobject (value 39) defined in [RFC8271] are used to coordinate bypass tunnel assignment between the PLR nodes in both the forward and reverse directions (see Figure 1). The BYPASS_ASSIGNMENT and Node-ID address [RFC4561] subobjects MUST be added by the downstream PLR node in the RECORD_ROUTE Object (RRO) of the RSVP Path message of the forward LSP to indicate the local bypass tunnel assignment using the procedure defined in [RFC8271]. The upstream node uses the bypass assignment information (namely, bypass tunnel source address, destination address, and Tunnel ID) in the received RSVP Path message of the protected forward LSP to find the associated bypass tunnel in the reverse direction. The upstream PLR node MUST NOT add the BYPASS_ASSIGNMENT subobject in the RRO of the RSVP Path message of the reverse LSP.
  • The downstream PLR node initiates the bypass tunnel assignment for the forward LSP. The upstream PLR (forward-direction LSP MP) node reflects the associated bypass tunnel assignment for the reverse-direction LSP. The upstream PLR node MUST NOT initiate the bypass tunnel assignment.
  • If the indicated forward bypass tunnel or the associated reverse bypass tunnel is not found, the upstream PLR SHOULD send a Notify message [RFC3473] with Error Code "FRR Bypass Assignment Error" (value 44) and Sub-code "Bypass Tunnel Not Found" (value 1) [RFC8271] to the downstream PLR.
  • If the bypass tunnel cannot be used as described in Section 4.5.3 of [RFC8271], the upstream PLR SHOULD send a Notify message [RFC3473] with Error Code "FRR Bypass Assignment Error" (value 44) and Sub-code "Bypass Assignment Cannot Be Used" (value 0) [RFC8271] to the downstream PLR.
  • After a link or node failure, the PLR nodes in both forward and reverse directions trigger fast reroute independently using the procedures defined in [RFC4090] and send the forward and protected reverse LSP modified RSVP Path messages and traffic over the bypass tunnel. The RSVP Resv signaling of the protected forward and reverse LSPs follows the same procedure as defined in [RFC4090] and is not modified by this document.
  • [RFC8271]で定義されているBYPASS_ASSIGNMENT IPv4サブオブジェクト（値38）とIPv6サブオブジェクト（値39）を使用して、順方向と逆方向の両方のPLRノード間でバイパストンネルの割り当てを調整します（Figure 1を参照）。下流側のPLRノードは、[RFC8271]で定義されている手順を使用してローカルのバイパストンネルの割り当てを示すために、順方向LSPのRSVP PathメッセージのRECORD_ROUTEオブジェクト（RRO）に、BYPASS_ASSIGNMENTサブオブジェクトとNode-IDアドレス[RFC4561]サブオブジェクトを追加しなければなりません（MUST）。上流側のノードは、受信した保護対象の順方向LSPのRSVP Pathメッセージ内のバイパス割り当て情報（つまり、バイパストンネルの送信元アドレス、宛先アドレス、Tunnel ID）を使用して、逆方向の関連付けられたバイパストンネルを見つけます。上流側のPLRノードは、逆方向LSPのRSVP PathメッセージのRROにBYPASS_ASSIGNMENTサブオブジェクトを追加してはなりません（MUST NOT）。
  • 下流側のPLRノードが、順方向LSPのバイパストンネルの割り当てを開始します。上流側のPLR（順方向LSPのMP）ノードは、関連付けられたバイパストンネルの割り当てを逆方向LSPに反映します。上流側のPLRノードは、バイパストンネルの割り当てを開始してはなりません（MUST NOT）。
  • 示された順方向のバイパストンネル、または関連付けられた逆方向のバイパストンネルが見つからない場合、上流側のPLRは、エラーコード「FRR Bypass Assignment Error」（値44）とサブコード「Bypass Tunnel Not Found」（値1）[RFC8271]を含むNotifyメッセージ[RFC3473]を、下流側のPLRに送信すべきです（SHOULD）。
  • [RFC8271]のSection 4.5.3で説明されているようにバイパストンネルを使用できない場合、上流側のPLRは、エラーコード「FRR Bypass Assignment Error」（値44）とサブコード「Bypass Assignment Cannot Be Used」（値0）[RFC8271]を含むNotifyメッセージ[RFC3473]を、下流側のPLRに送信すべきです（SHOULD）。
  • リンクまたはノードの障害の後、順方向と逆方向の両方のPLRノードは、[RFC4090]で定義されている手順を使用してそれぞれ独立に高速リルートを起動し、順方向LSPと保護対象の逆方向LSPの変更されたRSVP Pathメッセージとトラフィックを、バイパストンネル経由で送信します。保護対象の順方向LSPと逆方向LSPのRSVP Resvシグナリングは、[RFC4090]で定義されているのと同じ手順に従い、この文書では変更しません。

4.1.1. Restoring Co-routing with Node Protection Bypass Tunnels

4.1.1. ノード保護バイパストンネルでの同一経路の復元

After fast reroute, the downstream MP node assumes the role of upstream PLR and reroutes the reverse LSP RSVP Path messages and traffic over the bypass tunnel on which the forward LSP RSVP Path messages and traffic are received. This procedure is defined as "restoring co-routing" in [RFC8271]. This procedure is used to ensure that both forward and reverse LSP signaling and traffic flow on the same bidirectional bypass tunnel after fast reroute.

高速リルートの後、下流側のMPノードは上流側のPLRの役割を引き受け、順方向LSPのRSVP Pathメッセージとトラフィックを受信しているバイパストンネル経由で、逆方向LSPのRSVP Pathメッセージとトラフィックをリルートします。この手順は、[RFC8271]で「同一経路の復元（restoring co-routing）」として定義されています。この手順は、高速リルートの後、順方向と逆方向の両方のLSPのシグナリングとトラフィックが同じ双方向バイパストンネルを流れることを保証するために使用します。

As shown in Figure 2, when using a node protection bypass tunnel with protected co-routed LSPs, asymmetry of paths can occur in the forward and reverse directions after a link failure [RFC8271]. In order to restore co-routing, the downstream MP node D (acting as an upstream PLR) MUST trigger the procedure to restore co-routing and reroute the protected reverse LSP2 RSVP Path messages and traffic over the bypass tunnel S (on path D-G-F-B) to the upstream MP node B upon receiving the protected forward LSP modified RSVP Path messages and traffic over the bypass tunnel S (on path D-G-F-B) from node B. The upstream PLR node C stops receiving the RSVP Path messages and traffic for the reverse LSP2 from node D (resulting in RSVP soft-state timeout), and it stops sending the RSVP Path messages for the reverse LSP2 over the bypass tunnel N (on path C-I-H-A) to node A.

Figure 2に示すように、保護対象の同一経路のLSPでノード保護バイパストンネルを使用する場合、リンク障害の後に順方向と逆方向でパスの非対称が発生する可能性があります[RFC8271]。同一経路を復元するために、下流側のMPノードD（上流側のPLRとして動作）は、ノードBからバイパストンネルS（パスD-G-F-B上）経由で保護対象の順方向LSPの変更されたRSVP Pathメッセージとトラフィックを受信したら、同一経路を復元する手順を起動し、保護対象の逆方向LSP2のRSVP Pathメッセージとトラフィックを、バイパストンネルS（パスD-G-F-B上）経由で上流側のMPノードBへリルートしなければなりません（MUST）。上流側のPLRノードCは、ノードDから逆方向LSP2のRSVP Pathメッセージとトラフィックを受信しなくなり（その結果、RSVPのソフトステートのタイムアウトが発生します）、バイパストンネルN（パスC-I-H-A上）経由でノードAへ逆方向LSP2のRSVP Pathメッセージを送信するのをやめます。

4.1.2. Unidirectional Link Failures

4.1.2. 単方向リンク障害

The unidirectional link failures can cause co-routed associated bidirectional LSPs to be no longer co-routed after fast reroute with both link protection and node protection bypass tunnels. However, the unidirectional link failures in the upstream and/or downstream directions do not result in RSVP soft-state timeout with the associated bidirectional LSPs as upstream and downstream PLRs trigger fast reroute independently. The asymmetry of forward and reverse LSP paths due to the unidirectional link failure in the downstream direction can be corrected by using the procedure to restore co-routing specified in Section 4.1.1.

単方向リンク障害は、リンク保護とノード保護のどちらのバイパストンネルを使用した場合でも、高速リルートの後に同一経路の関連付けられた双方向LSPが同一経路ではなくなる原因となる可能性があります。ただし、上流側と下流側のPLRはそれぞれ独立に高速リルートを起動するため、関連付けられた双方向LSPでは、上流方向や下流方向（またはその両方）の単方向リンク障害によってRSVPのソフトステートのタイムアウトが発生することはありません。下流方向の単方向リンク障害による順方向LSPと逆方向LSPのパスの非対称は、Section 4.1.1で規定されている同一経路を復元する手順を使用して修正できます。

4.1.3. Revertive Behavior after Fast Reroute

4.1.3. 高速リルート後の切り戻し動作

When the revertive behavior is desired for a protected LSP after the link is restored, the procedure defined in Section 6.5.2 of [RFC4090] is followed.

リンクが復旧した後に保護対象のLSPで切り戻し動作（revertive behavior）が望まれる場合は、[RFC4090]のSection 6.5.2で定義されている手順に従います。

  • The downstream PLR node starts sending the RSVP Path messages and traffic flow of the protected forward LSP over the restored link and stops sending them over the bypass tunnel [RFC4090].
  • The upstream PLR node (when the protected LSP is present) also starts sending the RSVP Path messages and traffic flow of the protected reverse LSPs over the restored link and stops sending them over the bypass tunnel [RFC4090].
  • For node protection bypass tunnels (see Figure 2), after restoring co-routing, the upstream PLR node D SHOULD start sending RSVP Path messages and traffic for the reverse LSP over the original link (C-D) when it receives the unmodified RSVP Path messages and traffic for the protected forward LSP over it and stops sending them over the bypass tunnel S (on path D-G-F-B).
  • 下流側のPLRノードは、保護対象の順方向LSPのRSVP Pathメッセージとトラフィックフローを、復旧したリンク経由で送信し始め、バイパストンネル経由での送信をやめます[RFC4090]。
  • 上流側のPLRノードも（保護対象のLSPが存在する場合）、保護対象の逆方向LSPのRSVP Pathメッセージとトラフィックフローを、復旧したリンク経由で送信し始め、バイパストンネル経由での送信をやめます[RFC4090]。
  • ノード保護バイパストンネルの場合（Figure 2を参照）、同一経路を復元した後、上流側のPLRノードDは、元のリンク（C-D）経由で保護対象の順方向LSPの変更されていないRSVP Pathメッセージとトラフィックを受信したら、そのリンク経由で逆方向LSPのRSVP Pathメッセージとトラフィックの送信を開始し、バイパストンネルS（パスD-G-F-B上）経由での送信を停止すべきです（SHOULD）。

4.1.4. Bypass Tunnel Provisioning

4.1.4. バイパストンネルのプロビジョニング

Fast reroute bidirectional bypass tunnels can be single-sided or double-sided associated tunnels. For both single-sided and double-sided associated bypass tunnels, the fast reroute assignment policies need to be configured on the downstream PLR nodes of the protected LSPs that initiate the bypass tunnel assignments. For single-sided associated bypass tunnels, these nodes are the originating endpoints of their signaling.

高速リルートの双方向バイパストンネルは、片側または両側の関連付けられたトンネルにできます。片側と両側のどちらの関連付けられたバイパストンネルでも、高速リルートの割り当てポリシーは、バイパストンネルの割り当てを開始する、保護対象のLSPの下流側のPLRノードに設定する必要があります。片側の関連付けられたバイパストンネルの場合、これらのノードは、そのシグナリングの起点となるエンドポイントです。

4.1.5. One-to-One Bypass Tunnel

4.1.5. ワンツーワンのバイパストンネル

The fast reroute signaling procedure defined in this document can be used for both facility backup described in Section 3.2 of [RFC4090] and one-to-one backup described in Section 3.1 of [RFC4090]. As described in Section 4.5.2 of [RFC8271], in the one-to-one backup method, if the associated bidirectional bypass tunnel is already in use at the upstream PLR, it SHOULD send a Notify message [RFC3473] with Error Code "FRR Bypass Assignment Error" (value 44) and Sub-code "One-to-One Bypass Already in Use" (value 2) to the downstream PLR.

この文書で定義する高速リルートのシグナリング手順は、[RFC4090]のSection 3.2で説明されているファシリティーバックアップと、[RFC4090]のSection 3.1で説明されているワンツーワンバックアップの両方に使用できます。[RFC8271]のSection 4.5.2で説明されているように、ワンツーワンバックアップ方式において、関連付けられた双方向バイパストンネルが上流側のPLRですでに使用中である場合、上流側のPLRは、エラーコード「FRR Bypass Assignment Error」（値44）とサブコード「One-to-One Bypass Already in Use」（値2）を含むNotifyメッセージ[RFC3473]を、下流側のPLRに送信すべきです（SHOULD）。

4.2. Bidirectional LSP Association at Midpoints

4.2. 中間ノードでの双方向LSPの関連付け

In order to associate the LSPs unambiguously at a midpoint node (see Figure 3), the endpoint node MUST signal the Extended ASSOCIATION Object and add a unique Extended Association ID for each associated forward and reverse LSP pair forming the bidirectional LSP. An endpoint node MAY set the Extended Association ID to the value formatted according to the structure shown in Appendix A.

中間ノードでLSPを曖昧さなく関連付けるために（Figure 3を参照）、エンドポイントノードは、Extended ASSOCIATIONオブジェクトをシグナリングし、双方向LSPを形成する関連付けられた順方向LSPと逆方向LSPの組ごとに一意のExtended Association IDを追加しなければなりません（MUST）。エンドポイントノードは、Extended Association IDを、Appendix Aに示す構造に従って形式化した値に設定してもよいです（MAY）。

  • For single-sided provisioned bidirectional LSPs [RFC7551], the originating endpoint signals the Extended ASSOCIATION Object with a unique Extended Association ID. The remote endpoint copies the contents of the received Extended ASSOCIATION Object including the Extended Association ID in the RSVP Path message of the reverse LSP's Extended ASSOCIATION Object.
  • For double-sided provisioned bidirectional LSPs [RFC7551], both endpoints need to ensure that the bidirectional LSP has a unique Extended ASSOCIATION Object for each forward and reverse LSP pair by selecting appropriate unique Extended Association IDs signaled by them. A controller can be used to provision a unique Extended Association ID on both endpoints. The procedure for selecting unique Extended Association IDs is outside the scope of this document.
  • 片側プロビジョニングされた双方向LSP[RFC7551]の場合、起点側のエンドポイントは、一意のExtended Association IDを含むExtended ASSOCIATIONオブジェクトをシグナリングします。リモートのエンドポイントは、受信したExtended ASSOCIATIONオブジェクトの内容を、Extended Association IDも含めて、逆方向LSPのRSVP Pathメッセージ内のExtended ASSOCIATIONオブジェクトにコピーします。
  • 両側プロビジョニングされた双方向LSP[RFC7551]の場合、両方のエンドポイントは、それぞれがシグナリングする適切な一意のExtended Association IDを選択することで、双方向LSPが順方向LSPと逆方向LSPの組ごとに一意のExtended ASSOCIATIONオブジェクトを持つことを保証する必要があります。両方のエンドポイントに一意のExtended Association IDをプロビジョニングするために、コントローラーを使用できます。一意のExtended Association IDを選択する手順は、この文書の範囲外です。

5. Compatibility

5. 互換性

This document updates the procedures for fast reroute for associated bidirectional LSPs defined in [RFC4090] and the procedures for associating bidirectional LSPs defined in [RFC7551]. The procedures use the signaling messages defined in [RFC8271]; no new signaling messages are defined in this document. The procedures ensure that for the co-routed LSPs, traffic flows on co-routed paths in the forward and reverse directions after fast reroute. Operators wishing to use this function SHOULD ensure that it is supported on all the nodes on the LSP path. The nodes not supporting this function can cause the traffic to flow on asymmetric paths in the forward and reverse directions of the associated bidirectional LSPs after fast reroute.

この文書は、[RFC4090]で定義されている関連付けられた双方向LSPのための高速リルート手順と、[RFC7551]で定義されている双方向LSPを関連付けるための手順を更新します。これらの手順は[RFC8271]で定義されているシグナリングメッセージを使用し、この文書では新しいシグナリングメッセージを定義しません。これらの手順により、同一経路のLSPについて、高速リルートの後も順方向と逆方向のトラフィックが同一経路のパスを流れることが保証されます。この機能を使用したい運用者は、LSPのパス上のすべてのノードでこの機能がサポートされていることを確認すべきです（SHOULD）。この機能をサポートしていないノードがあると、高速リルートの後、関連付けられた双方向LSPの順方向と逆方向でトラフィックが非対称なパスを流れる原因となる可能性があります。

6. Security Considerations

6. セキュリティーに関する考慮事項

This document updates the signaling mechanisms defined in [RFC4090] and [RFC7551]. It does not introduce any additional security considerations other than those already covered in [RFC4090], [RFC7551], [RFC8271], and the MPLS/GMPLS security framework [RFC5920].

この文書は、[RFC4090]と[RFC7551]で定義されているシグナリングメカニズムを更新します。[RFC4090]、[RFC7551]、[RFC8271]、およびMPLS/GMPLSのセキュリティーフレームワーク[RFC5920]ですでに扱われているもの以外に、セキュリティーに関する考慮事項を追加することはありません。

Appendix A. Extended Association ID

Appendix A. Extended Association ID

The Extended Association ID in the Extended ASSOCIATION Object [RFC6780] can be set to the value formatted according to the structure shown in the following example to uniquely identify associated forward and reverse LSP pairs of an associated bidirectional LSP.

Extended ASSOCIATIONオブジェクト[RFC6780]内のExtended Association IDは、関連付けられた双方向LSPの関連付けられた順方向LSPと逆方向LSPの組を一意に識別するために、次の例に示す構造に従って形式化した値に設定できます。

An example of the IPv4 Extended Association ID format is shown below:

IPv4のExtended Association IDの形式の例を以下に示します：

IPv4 LSP Source Address
IPv4 source address of the forward LSP [RFC3209].
LSP ID
16-bit LSP ID of the forward LSP [RFC3209].
Variable Length ID
Variable length Extended Association ID [RFC6780] inserted by the endpoint node of the associated bidirectional LSP [RFC7551].
IPv4 LSP Source Address
順方向LSPのIPv4送信元アドレス[RFC3209]です。
LSP ID
順方向LSPの16ビットのLSP ID[RFC3209]です。
Variable Length ID
関連付けられた双方向LSP[RFC7551]のエンドポイントノードが挿入する、可変長のExtended Association ID[RFC6780]です。

An example of the IPv6 Extended Association ID format is shown below:

IPv6のExtended Association IDの形式の例を以下に示します：

LSP Source Address
IPv6 source address of the forward LSP [RFC3209].
LSP ID
16-bit LSP ID of the forward LSP [RFC3209].
Variable Length ID
Variable length Extended Association ID [RFC6780] inserted by the endpoint node of the associated bidirectional LSP [RFC7551].
LSP Source Address
順方向LSPのIPv6送信元アドレス[RFC3209]です。
LSP ID
順方向LSPの16ビットのLSP ID[RFC3209]です。
Variable Length ID
関連付けられた双方向LSP[RFC7551]のエンドポイントノードが挿入する、可変長のExtended Association ID[RFC6780]です。

In both IPv4 and IPv6 examples, the Reserved flags MUST be set to 0 on transmission.

IPv4とIPv6のどちらの例でも、Reservedフラグは送信時に0に設定しなければなりません（MUST）。
