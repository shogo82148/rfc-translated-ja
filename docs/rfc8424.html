RFC 8424

Extensions to RSVP-TE for Label Switched Path (LSP) Ingress Fast Reroute (FRR) Protection

RFC 8424

ラベルスイッチパス（LSP）のイングレス高速リルート（FRR）保護のためのRSVP-TEの拡張

Abstract

概要

This document describes extensions to Resource Reservation Protocol - Traffic Engineering (RSVP-TE) for locally protecting the ingress node of a Point-to-Point (P2P) or Point-to-Multipoint (P2MP) Traffic Engineered (TE) Label Switched Path (LSP). It extends the Fast Reroute (FRR) protection for transit nodes of an LSP to the ingress node of the LSP. The procedures described in this document are experimental.

この文書は、ポイントツーポイント（P2P）またはポイントツーマルチポイント（P2MP）のトラフィックエンジニアリング（TE）ラベルスイッチパス（LSP）のイングレスノードをローカルに保護するための、リソース予約プロトコル - トラフィックエンジニアリング（Resource Reservation Protocol - Traffic Engineering: RSVP-TE）の拡張について説明します。 この拡張は、LSPのトランジットノードに対する高速リルート（Fast Reroute: FRR）保護を、LSPのイングレスノードにまで拡張するものです。 この文書で説明する手順は実験的なものです。

1. Introduction

1. はじめに

For an MPLS Traffic Engineered (TE) Label Switched Path (LSP), protecting the failures of its transit nodes using Fast Reroute (FRR) is covered in [RFC4090] for Point-to-Point (P2P) LSPs and [RFC4875] for Point-to-Multipoint (P2MP) LSPs. However, protecting the failure of its ingress node using FRR is not covered in either [RFC4090] or [RFC4875]. The MPLS Transport Profile (MPLS-TP) Linear Protection described in [RFC6378] can provide a protection against the failure of any transit node of an LSP between the ingress node and the egress node of the LSP, but it cannot protect against the failure of the ingress node.

MPLSのトラフィックエンジニアリング（TE）ラベルスイッチパス（LSP）について、そのトランジットノードの障害を高速リルート（Fast Reroute: FRR）を使用して保護する方法は、ポイントツーポイント（P2P）LSPについては[RFC4090]で、ポイントツーマルチポイント（P2MP）LSPについては[RFC4875]で扱われています。 しかし、そのイングレスノードの障害をFRRを使用して保護する方法は、[RFC4090]と[RFC4875]のどちらでも扱われていません。 [RFC6378]で説明されているMPLSトランスポートプロファイル（MPLS-TP）の線形保護（Linear Protection）は、LSPのイングレスノードとイグレスノードの間にある任意のトランジットノードの障害に対する保護を提供できますが、イングレスノードの障害に対しては保護できません。

To protect against the failure of the (primary) ingress node of a primary end-to-end P2MP (or P2P) TE LSP, a typical existing solution is to set up a secondary backup end-to-end P2MP (or P2P) TE LSP. The backup LSP is from a backup ingress node to backup egress nodes (or node). The backup ingress node is different from the primary ingress node. The backup egress nodes (or node) are (or is) different from the primary egress nodes (or node) of the primary LSP. For a P2MP TE LSP, on each of the primary (and backup) egress nodes, a P2P LSP is created from the egress node to its primary (backup) ingress node and configured with Bidirectional Forwarding Detection (BFD). This is used to detect the failure of the primary (backup) ingress node for the receiver to switch to the backup (or primary) egress node to receive the traffic after the primary (or backup) ingress node fails when both the primary LSP and the secondary LSP carry the traffic. In addition, FRR may be used to provide protections against the failures of the transit nodes and the links of the primary and secondary end-to-end TE LSPs.

プライマリーのエンドツーエンドP2MP（またはP2P）TE LSPの（プライマリー）イングレスノードの障害から保護するための、既存の典型的な解決策は、セカンダリーのバックアップ用エンドツーエンドP2MP（またはP2P）TE LSPを設定することです。 バックアップLSPは、バックアップイングレスノードからバックアップイグレスノード（1つまたは複数）へ向かいます。 バックアップイングレスノードはプライマリーイングレスノードとは異なります。 バックアップイグレスノード（1つまたは複数）は、プライマリーLSPのプライマリーイグレスノード（1つまたは複数）とは異なります。 P2MP TE LSPの場合、プライマリー（およびバックアップ）の各イグレスノード上で、そのイグレスノードから対応するプライマリー（バックアップ）イングレスノードへのP2P LSPが作成され、双方向フォワーディング検出（Bidirectional Forwarding Detection: BFD）が設定されます。 これは、プライマリーLSPとセカンダリーLSPの両方がトラフィックを運んでいる場合に、プライマリー（バックアップ）イングレスノードの障害を検出し、プライマリー（またはバックアップ）イングレスノードの障害後に受信者がバックアップ（またはプライマリー）イグレスノードに切り替えてトラフィックを受信できるようにするために使用されます。 さらに、プライマリーとセカンダリーのエンドツーエンドTE LSPのトランジットノードとリンクの障害に対する保護を提供するために、FRRを使用することもあります。

There are a number of issues in this solution:

この解決策には、いくつかの問題があります。

  • It consumes lots of network resources. Double states need to be maintained in the network since two end-to-end TE LSPs are created. Double link bandwidth is reserved and used when both the primary and the secondary end-to-end TE LSPs carry the traffic at the same time.
  • More operations are needed, which include the configuration of two end-to-end TE LSPs and BFDs from each of the egress nodes to its corresponding ingress node.
  • The detection of the failure of the ingress node may not be reliable. Any failure on the path of the BFD from an egress node to an ingress node may cause the BFD to indicate the failure of the ingress node.
  • The speed of protection against the failure of the ingress node may be slow.
  • 大量のネットワークリソースを消費します。 2つのエンドツーエンドTE LSPが作成されるため、ネットワーク内で2倍の状態を維持する必要があります。 プライマリーとセカンダリーのエンドツーエンドTE LSPの両方が同時にトラフィックを運ぶ場合、2倍のリンク帯域幅が予約され、使用されます。
  • より多くの操作が必要です。 これには、2つのエンドツーエンドTE LSPの設定と、各イグレスノードから対応するイングレスノードへのBFDの設定が含まれます。
  • イングレスノードの障害検出の信頼性が低い場合があります。 イグレスノードからイングレスノードへのBFDのパス上でなんらかの障害が発生すると、BFDがイングレスノードの障害を示す場合があります。
  • イングレスノードの障害に対する保護の速度が遅い場合があります。

This specification defines a simple extension to RSVP-TE for local protection (FRR) of the ingress node of a P2MP or P2P LSP to resolve these issues. Ingress local protection and ingress FRR protection will be used interchangeably.

この仕様は、これらの問題を解決するために、P2MPまたはP2P LSPのイングレスノードのローカル保護（FRR）のためのRSVP-TEの単純な拡張を定義します。 イングレスのローカル保護とイングレスのFRR保護は、同じ意味で使用します。

Note that this document is an Experimental RFC. Two different approaches are proposed to transfer the information for ingress protection. They both use the same new INGRESS_PROTECTION object, which is sent in both PATH and RESV messages between a primary ingress and a backup ingress. One approach is the Relay-Message Method (refer to Sections 6.1.1 and 6.2.1), the other is the Proxy-Ingress Method (refer to Sections 6.1.2 and 6.2.2). Each of them has advantages and disadvantages. It is hard to decide which one is used as a standard approach now. It is expected that the experiment on the ingress local protection with these two approaches will provide quantities to help choose one. The quantities include the numbers on control traffic, states, codes, and operations. After one approach is selected, the document will be revised to reflect that selection and any other items learned from the experiment. The revised document is expected to be submitted for publication on the standards track.

この文書は実験的（Experimental）RFCであることに注意してください。 イングレス保護のための情報を伝達する、2つの異なるアプローチが提案されています。 どちらも同じ新しいINGRESS_PROTECTIONオブジェクトを使用し、このオブジェクトはプライマリーイングレスとバックアップイングレスの間でPATHメッセージとRESVメッセージの両方で送信されます。 一方のアプローチはリレーメッセージ方式（Relay-Message Method）（セクション6.1.1と6.2.1を参照）で、もう一方はプロキシーイングレス方式（Proxy-Ingress Method）（セクション6.1.2と6.2.2を参照）です。 それぞれに長所と短所があります。 現時点では、どちらを標準のアプローチとして使用するかを決めるのは困難です。 これら2つのアプローチによるイングレスのローカル保護の実験により、どちらかを選択するのに役立つ定量的なデータが得られることが期待されています。 その定量的なデータには、制御トラフィック、状態、コード、操作の数が含まれます。 一方のアプローチが選択された後、その選択と実験から得られたその他の知見を反映するよう、この文書は改訂されます。 改訂された文書は、標準化過程での発行に向けて提出されることが見込まれています。

1.1. Ingress Local Protection Example

1.1. イングレスのローカル保護の例

Figure 1 shows an example of using a backup P2MP LSP to locally protect the ingress of a primary P2MP LSP, which is from ingress Ia to three egresses: L1, L2, and L3. The backup LSP is from backup ingress Ib to the next hops of ingress Ia: R2 and R4.

図1は、バックアップP2MP LSPを使用して、プライマリーP2MP LSPのイングレスをローカルに保護する例を示しています。 このプライマリーP2MP LSPは、イングレスIaから3つのイグレスL1、L2、L3へ向かうものです。 バックアップLSPは、バックアップイングレスIbから、イングレスIaのネクストホップであるR2とR4へ向かいます。

In normal operations, source S sends the traffic to primary ingress Ia. Ia imports the traffic into the primary LSP.

通常の運用では、送信元SはトラフィックをプライマリーイングレスIaに送信します。 IaはトラフィックをプライマリーLSPに取り込みます。

When source S detects the failure of Ia, it switches the traffic to backup ingress Ib, which imports the traffic from S into the backup LSP to Ia's next hops, R2 and R4, where the traffic is merged into the primary LSP and then sent to egresses L1, L2, and L3.

送信元SはIaの障害を検出すると、トラフィックをバックアップイングレスIbに切り替えます。 Ibは、SからのトラフィックをIaのネクストホップであるR2とR4へ向かうバックアップLSPに取り込みます。 トラフィックはR2とR4でプライマリーLSPに合流し、その後イグレスL1、L2、L3に送信されます。

Note that the backup ingress is one logical hop away from the ingress. A logical hop is a direct link or a tunnel (such as a GRE tunnel) over which RSVP-TE messages may be exchanged.

バックアップイングレスはイングレスから1論理ホップ離れていることに注意してください。 論理ホップとは、RSVP-TEメッセージを交換できる直接リンクまたはトンネル（GREトンネルなど）のことです。

1.2. Ingress Local Protection Overview

1.2. イングレスのローカル保護の概要

There are four parts in ingress local protection:

イングレスのローカル保護には、次の4つの部分があります。

  • setting up the necessary backup LSP forwarding state based on the information received for ingress local protection;
  • detecting the primary ingress failure and providing the fast repair (as discussed in Sections 3 and 4);
  • maintaining the RSVP-TE control-plane state until a global repair is done; and,
  • performing the global repair (see Section 6.4.2).
  • イングレスのローカル保護のために受信した情報に基づいて、必要なバックアップLSPの転送状態を設定すること
  • プライマリーイングレスの障害を検出し、高速修復を提供すること（セクション3と4で説明します）
  • グローバル修復が完了するまで、RSVP-TEのコントロールプレーンの状態を維持すること
  • グローバル修復を実行すること（セクション6.4.2を参照）

The primary ingress of a primary LSP sends the backup ingress the information for ingress protection in a PATH message with a new INGRESS_PROTECTION object. The backup ingress sets up the backup LSP(s) and forwarding state after receiving the necessary information for ingress protection. Then, it sends the primary ingress the status of ingress protection in a RESV message with a new INGRESS_PROTECTION object.

プライマリーLSPのプライマリーイングレスは、新しいINGRESS_PROTECTIONオブジェクトを含むPATHメッセージで、イングレス保護のための情報をバックアップイングレスに送信します。 バックアップイングレスは、イングレス保護に必要な情報を受信した後、バックアップLSPと転送状態を設定します。 その後、バックアップイングレスは、新しいINGRESS_PROTECTIONオブジェクトを含むRESVメッセージで、イングレス保護のステータスをプライマリーイングレスに送信します。

When the primary ingress fails, the backup ingress sends or refreshes the next hops of the primary ingress the PATH messages without any INGRESS_PROTECTION object after verifying the failure. Thus, the RSVP-TE control-plane state of the primary LSP is maintained.

プライマリーイングレスに障害が発生すると、バックアップイングレスは障害を確認した後、INGRESS_PROTECTIONオブジェクトを含まないPATHメッセージを、プライマリーイングレスのネクストホップに送信またはリフレッシュします。 これにより、プライマリーLSPのRSVP-TEのコントロールプレーンの状態が維持されます。

3. Ingress Failure Detection

3. イングレスの障害検出

Exactly how to detect the failure of the ingress is out of scope. However, it is necessary to discuss different modes for detecting the failure because they determine what is the required behavior for the source and backup ingress.

イングレスの障害を具体的にどのように検出するかは範囲外です。 しかし、障害を検出するさまざまなモードについて議論しておく必要があります。 モードによって、送信元とバックアップイングレスに求められる振る舞いが決まるためです。

3.1. Source Detects Failure

3.1. 送信元による障害検出

Source Detects Failure, or Source-Detect for short, means that the source is responsible for "fast detecting" the failure of the primary ingress of an LSP. Fast detecting the failure means detecting the failure in a few or tens of milliseconds. The backup ingress is ready to import the traffic from the source into the backup LSP(s) after the backup LSP(s) is up.

送信元による障害検出（Source Detects Failure、略してSource-Detect）とは、LSPのプライマリーイングレスの障害を「高速に検出する」責任を送信元が負うことを意味します。 障害を高速に検出するとは、数ミリ秒から数十ミリ秒で障害を検出することを意味します。 バックアップイングレスは、バックアップLSPが立ち上がった後、送信元からのトラフィックをバックアップLSPに取り込む準備ができた状態になります。

In normal operations, the source sends the traffic to the primary ingress. When the source detects the failure of the primary ingress, it switches the traffic to the backup ingress, which delivers the traffic to the next hops of the primary ingress through the backup LSP(s), where the traffic is merged into the primary LSP.

通常の運用では、送信元はトラフィックをプライマリーイングレスに送信します。 送信元はプライマリーイングレスの障害を検出すると、トラフィックをバックアップイングレスに切り替えます。 バックアップイングレスは、バックアップLSPを通じてトラフィックをプライマリーイングレスのネクストホップに届け、トラフィックはそこでプライマリーLSPに合流します。

For an LSP, after the primary ingress fails, the backup ingress MUST use a method to verify the failure of the primary ingress before the PATH message for the LSP expires at the next hop of the primary ingress. After verifying the failure, the backup ingress sends/refreshes the PATH message to the next hop through the backup LSP as needed. The method may verify the failure of the primary ingress slowly, such as in seconds.

LSPについて、プライマリーイングレスに障害が発生した後、バックアップイングレスは、プライマリーイングレスのネクストホップでそのLSPのPATHメッセージが期限切れになる前に、なんらかの方法を使用してプライマリーイングレスの障害を確認しなければなりません（MUST）。 障害を確認した後、バックアップイングレスは、必要に応じてバックアップLSPを通じてネクストホップにPATHメッセージを送信またはリフレッシュします。 この方法では、プライマリーイングレスの障害を、たとえば秒単位でゆっくりと確認してもかまいません。

After the primary ingress fails, it will not be reachable after routing convergence. Thus, checking whether the primary ingress (address) is reachable is a possible method.

プライマリーイングレスに障害が発生すると、ルーティングの収束後にはそのプライマリーイングレスに到達できなくなります。 したがって、プライマリーイングレス（のアドレス）に到達可能かどうかを確認することが、1つの方法として考えられます。

When the previously failed primary ingress of a primary LSP becomes available again and the primary LSP has recovered from its primary ingress, the source may switch the traffic to the primary ingress from the backup ingress. An operator may control the traffic switch through using a command on the source node after seeing that the primary LSP has recovered.

プライマリーLSPの、以前に障害が発生したプライマリーイングレスが再び利用可能になり、プライマリーLSPがそのプライマリーイングレスから回復した場合、送信元はトラフィックをバックアップイングレスからプライマリーイングレスに切り替えることがあります。 運用者は、プライマリーLSPが回復したことを確認した後、送信元ノード上でコマンドを使用してトラフィックの切り替えを制御することもできます。

3.2. Backup and Source Detect Failure

3.2. バックアップと送信元による障害検出

Backup and Source Detect Failure, or Backup-Source-Detect for short, means that both the backup ingress and the source are concurrently responsible for fast detecting the failure of the primary ingress.

バックアップと送信元による障害検出（Backup and Source Detect Failure、略してBackup-Source-Detect）とは、バックアップイングレスと送信元の両方が、同時にプライマリーイングレスの障害を高速に検出する責任を負うことを意味します。

Note that one of the differences between Source-Detect and Backup-Source-Detect is the following: in the former, the backup ingress verifies the failure of the primary ingress slowly, such as in seconds; in the latter, the backup ingress detects the failure fast, such as in a few or tens of milliseconds.

Source-DetectとBackup-Source-Detectの違いの1つは次のとおりであることに注意してください。 前者では、バックアップイングレスはプライマリーイングレスの障害を、たとえば秒単位でゆっくりと確認します。 後者では、バックアップイングレスは障害を、たとえば数ミリ秒から数十ミリ秒で高速に検出します。

In normal operations, the source sends the traffic to the primary ingress. It switches the traffic to the backup ingress when it detects the failure of the primary ingress.

通常の運用では、送信元はトラフィックをプライマリーイングレスに送信します。 送信元は、プライマリーイングレスの障害を検出すると、トラフィックをバックアップイングレスに切り替えます。

The backup ingress does not import any traffic from the source into the backup LSP in normal operations. When it detects the failure of the primary ingress, it imports the traffic from the source into the backup LSP to the next hops of the primary ingress, where the traffic is merged into the primary LSP.

通常の運用では、バックアップイングレスは送信元からのトラフィックをバックアップLSPに取り込みません。 バックアップイングレスは、プライマリーイングレスの障害を検出すると、送信元からのトラフィックを、プライマリーイングレスのネクストホップへ向かうバックアップLSPに取り込み、トラフィックはそこでプライマリーLSPに合流します。

The Source-Detect is preferred. It is simpler than the Backup-Source-Detect, which needs both the source and the backup ingress to detect the ingress failure quickly.

Source-Detectのほうが望ましいです。 Source-Detectは、送信元とバックアップイングレスの両方がイングレスの障害を素早く検出する必要があるBackup-Source-Detectよりも単純です。

4. Backup Forwarding State

4. バックアップの転送状態

Before the primary ingress fails, the backup ingress is responsible for creating the necessary backup LSPs. These LSPs might be multiple bypass P2P LSPs that avoid the ingress. Alternately, the backup ingress could choose to use a single backup P2MP LSP as a bypass or detour to protect the primary ingress of a primary P2MP LSP.

プライマリーイングレスに障害が発生する前に、バックアップイングレスは必要なバックアップLSPを作成する責任を負います。 これらのLSPは、イングレスを回避する複数のバイパスP2P LSPであることもあります。 あるいは、バックアップイングレスは、プライマリーP2MP LSPのプライマリーイングレスを保護するために、単一のバックアップP2MP LSPをバイパスまたは迂回路（detour）として使用することを選択することもできます。

The backup ingress may be "off path" or "on path" of an LSP. If a backup ingress is not any node of the LSP, it is off path. If a backup ingress is a next hop of the primary ingress of the LSP, it is on path. When a backup ingress for protecting the primary ingress is configured, the backup ingress MUST not be on the LSP except for if it is the next hop of the primary ingress. If it is on path, the primary forwarding state associated with the primary LSP SHOULD be clearly separated from the backup LSP(s) state.

バックアップイングレスは、LSPの「パス外（off path）」にある場合と「パス上（on path）」にある場合があります。 バックアップイングレスがLSPのどのノードでもない場合、それはパス外です。 バックアップイングレスがLSPのプライマリーイングレスのネクストホップである場合、それはパス上です。 プライマリーイングレスを保護するためのバックアップイングレスを設定する場合、バックアップイングレスは、プライマリーイングレスのネクストホップである場合を除き、LSP上にない必要があります（MUST）。 バックアップイングレスがパス上にある場合、プライマリーLSPに関連付けられたプライマリーの転送状態は、バックアップLSPの状態から明確に分離されるべきです（SHOULD）。

4.1. Forwarding State for Backup LSP

4.1. バックアップLSPの転送状態

A forwarding entry for a backup LSP is created on the backup ingress after the LSP is set up. Depending on the failure-detection mode (e.g., Source-Detect), it may be used to forward received traffic or simply be inactive (e.g., Backup-Source-Detect) until required. In either case, when the primary ingress fails, this entry is used to import the traffic into the backup LSP to the next hops of the primary ingress, where the traffic is merged into the primary LSP.

バックアップLSPの転送エントリーは、LSPが設定された後にバックアップイングレス上に作成されます。 障害検出のモードに応じて、この転送エントリーは、受信したトラフィックの転送に使用される場合（例：Source-Detect）と、必要になるまで単に非アクティブである場合（例：Backup-Source-Detect）があります。 いずれの場合も、プライマリーイングレスに障害が発生すると、このエントリーは、プライマリーイングレスのネクストホップへ向かうバックアップLSPにトラフィックを取り込むために使用され、トラフィックはそこでプライマリーLSPに合流します。

The forwarding entry for a backup LSP is a local implementation issue. In one device, it may have an inactive flag. This inactive forwarding entry is not used to forward any traffic normally. When the primary ingress fails, it is changed to active; thus, the traffic from the source is imported into the backup LSP.

バックアップLSPの転送エントリーは、ローカルな実装の問題です。 ある機器では、転送エントリーが非アクティブフラグを持つことがあります。 この非アクティブな転送エントリーは、通常はトラフィックの転送に使用されません。 プライマリーイングレスに障害が発生すると、このエントリーはアクティブに変更され、送信元からのトラフィックがバックアップLSPに取り込まれます。

5. プロトコル拡張

A new object, INGRESS_PROTECTION, is defined for signaling ingress local protection. The primary ingress of a primary LSP sends the backup ingress this object in a PATH message. In this case, the object contains the information needed to set up ingress protection. The information includes:

  • the Labels and Routes, which indicate the first hops of the primary LSP, each of which is paired with its label; and,

  • バックアップイングレスを示す、バックアップイングレスのIPアドレス（Backup Ingress IP Address）

The backup ingress sends the primary ingress this object in a RESV message. In this case, the object contains the information about the status on the ingress protection.

バックアップイングレスは、このオブジェクトをRESVメッセージでプライマリーイングレスに送信します。 この場合、オブジェクトにはイングレス保護のステータスに関する情報が含まれます。

6. Behavior of Ingress Protection

6. イングレス保護の振る舞い

6.1. Overview

6.1. 概要

There are two different proposed signaling approaches to transfer the information for ingress protection. They both use the same new INGRESS_PROTECTION object. The object is sent in both PATH and RESV messages.

イングレス保護のための情報を伝達する、2つの異なるシグナリングのアプローチが提案されています。 どちらも同じ新しいINGRESS_PROTECTIONオブジェクトを使用します。 このオブジェクトは、PATHメッセージとRESVメッセージの両方で送信されます。

6.1.1. Relay-Message Method

6.1.1. リレーメッセージ方式

The primary ingress relays the information for ingress protection of an LSP to the backup ingress via PATH messages. Once the LSP is created, the ingress of the LSP sends the backup ingress a PATH message with an INGRESS_PROTECTION object with a Label-Routes subobject, which is populated with the next hops and labels. This provides sufficient information for the backup ingress to create the appropriate forwarding state and backup LSP(s).

プライマリーイングレスは、LSPのイングレス保護のための情報を、PATHメッセージを介してバックアップイングレスに中継します。 LSPが作成されると、LSPのイングレスは、ネクストホップとラベルが格納されたLabel-Routesサブオブジェクトを持つINGRESS_PROTECTIONオブジェクトを含むPATHメッセージを、バックアップイングレスに送信します。 これにより、バックアップイングレスが適切な転送状態とバックアップLSPを作成するのに十分な情報が提供されます。

The ingress also sends the backup ingress all the other PATH messages for the LSP with an empty INGRESS_PROTECTION object. An INGRESS_PROTECTION object without any TRAFFIC_DESCRIPTOR subobject is called an empty INGRESS_PROTECTION object. Thus, the backup ingress has access to all the PATH messages needed for modification to refresh the control-plane state after a failure.

イングレスは、そのLSPに関するその他すべてのPATHメッセージも、空のINGRESS_PROTECTIONオブジェクトとともにバックアップイングレスに送信します。 TRAFFIC_DESCRIPTORサブオブジェクトを1つも含まないINGRESS_PROTECTIONオブジェクトを、空のINGRESS_PROTECTIONオブジェクトと呼びます。 これにより、バックアップイングレスは、障害発生後にコントロールプレーンの状態をリフレッシュするために修正が必要なすべてのPATHメッセージにアクセスできます。

The empty INGRESS_PROTECTION object is for efficient processing of ingress protection for a P2MP LSP. A P2MP LSP's primary ingress may have more than one PATH message, each of which is sent to a next hop along a branch of the P2MP LSP. The PATH message along a branch will be selected and sent to the backup ingress with an INGRESS_PROTECTION object containing the TRAFFIC_DESCRIPTOR subobject; all the PATH messages along the other branches will be sent to the backup ingress containing an INGRESS_PROTECTION object without any TRAFFIC_DESCRIPTOR subobject (empty INGRESS_PROTECTION object). For a P2MP LSP, the backup ingress only needs one TRAFFIC_DESCRIPTOR.

空のINGRESS_PROTECTIONオブジェクトは、P2MP LSPのイングレス保護を効率的に処理するためのものです。 P2MP LSPのプライマリーイングレスは、複数のPATHメッセージを持つことがあり、それぞれのPATHメッセージは、P2MP LSPのブランチに沿ってネクストホップに送信されます。 あるブランチに沿ったPATHメッセージが選択され、TRAFFIC_DESCRIPTORサブオブジェクトを含むINGRESS_PROTECTIONオブジェクトとともにバックアップイングレスに送信されます。 他のブランチに沿ったすべてのPATHメッセージは、TRAFFIC_DESCRIPTORサブオブジェクトを含まないINGRESS_PROTECTIONオブジェクト（空のINGRESS_PROTECTIONオブジェクト）を含めてバックアップイングレスに送信されます。 P2MP LSPの場合、バックアップイングレスが必要とするTRAFFIC_DESCRIPTORは1つだけです。

6.1.2. Proxy-Ingress Method

6.1.2. プロキシーイングレス方式

Conceptually, a proxy ingress is created that starts the RSVP signaling. The explicit path of the LSP goes from the proxy ingress to the backup ingress and then to the real ingress. The behavior and signaling for the proxy ingress is done by the real ingress; the use of a proxy-ingress address avoids problems with loop detection. Note that the proxy ingress MUST reside within the same router as the real ingress.

概念的には、RSVPシグナリングを開始するプロキシーイングレスが作成されます。 LSPの明示的なパスは、プロキシーイングレスからバックアップイングレスへ、そして実際のイングレスへと向かいます。 プロキシーイングレスの振る舞いとシグナリングは、実際のイングレスによって行われます。 プロキシーイングレスのアドレスを使用することで、ループ検出に関する問題を回避できます。 プロキシーイングレスは、実際のイングレスと同じルーター内に存在しなければならない（MUST）ことに注意してください。

The backup ingress MUST know the merge points or next hops and their associated labels. This is accomplished by having the RSVP PATH and RESV messages go through the backup ingress, although the forwarding path need not go through the backup ingress. If the backup ingress fails, the ingress simply removes the INGRESS_PROTECTION object and forwards the PATH messages to the LSP's next hop(s). If the ingress has its LSP configured for ingress protection, then the ingress can add the backup ingress and itself to the Explicit Route Object (ERO) and start forwarding the PATH messages to the backup ingress.

バックアップイングレスは、マージポイントまたはネクストホップと、それらに関連付けられたラベルを知っていなければなりません（MUST）。 これは、転送パスがバックアップイングレスを経由する必要はないものの、RSVPのPATHメッセージとRESVメッセージがバックアップイングレスを経由するようにすることで実現されます。 バックアップイングレスに障害が発生した場合、イングレスは単にINGRESS_PROTECTIONオブジェクトを削除し、PATHメッセージをLSPのネクストホップに転送します。 イングレスが自身のLSPをイングレス保護用に設定している場合、イングレスはバックアップイングレスと自分自身を明示的経路オブジェクト（Explicit Route Object: ERO）に追加し、PATHメッセージのバックアップイングレスへの転送を開始できます。

Slightly different behavior can apply for the on-path and off-path cases. In the on-path case, the backup ingress is a next-hop node after the ingress for the LSP. In the off-path case, the backup ingress is not any next-hop node after the ingress for all associated sub-LSPs.

パス上の場合とパス外の場合とでは、わずかに異なる振る舞いが適用されることがあります。 パス上の場合、バックアップイングレスは、そのLSPについてイングレスの次にあるネクストホップノードです。 パス外の場合、バックアップイングレスは、関連するすべてのサブLSPについて、イングレスの次にあるどのネクストホップノードでもありません。

The key advantage of this approach is that it minimizes the special handling code required. Because the backup ingress is on the signaling path, it can receive various notifications. It easily has access to all the PATH messages needed for a modification to be sent to refresh the control-plane state after a failure.

このアプローチの主な利点は、必要となる特別な処理のコードを最小限に抑えられることです。 バックアップイングレスはシグナリングパス上にあるため、さまざまな通知を受信できます。 バックアップイングレスは、障害発生後にコントロールプレーンの状態をリフレッシュするために修正して送信する必要があるすべてのPATHメッセージに、容易にアクセスできます。

6.2. Ingress Behavior

6.2. イングレスの振る舞い

The primary ingress MUST be configured with a couple of pieces of information for ingress protection.

プライマリーイングレスには、イングレス保護のためのいくつかの情報が設定されていなければなりません（MUST）。

  • Backup Ingress Address: The primary ingress MUST know the IP address of the backup ingress it wants to be used before it can use the INGRESS_PROTECTION object.
  • Proxy-Ingress-Id (only needed for Proxy-Ingress Method): The Proxy-Ingress-Id is only used in the RECORD_ROUTE object for recording the proxy ingress. If no Proxy-Ingress-Id is specified, then a local interface address that will not otherwise be included in the RECORD_ROUTE object can be used. A similar technique is used in Section 6.1.1. of [RFC4090].
  • Application Traffic Identifier: The primary ingress and backup ingress MUST both know what application traffic should be directed into the LSP. If a list of prefixes in the TRAFFIC_DESCRIPTOR subobject will not suffice, then a commonly understood Application Traffic Identifier can be sent between the primary ingress and backup ingress. The exact meaning of the identifier should be configured similarly at both the primary ingress and backup ingress. The Application Traffic Identifier is understood within the unique context of the primary ingress and backup ingress.
  • A Connection between Backup Ingress and Primary Ingress: If there is not any direct link between the primary ingress and the backup ingress, a tunnel MUST be configured between them.
  • Backup Ingress Address：プライマリーイングレスは、INGRESS_PROTECTIONオブジェクトを使用できるようになる前に、使用したいバックアップイングレスのIPアドレスを知っていなければなりません（MUST）。
  • Proxy-Ingress-Id（プロキシーイングレス方式でのみ必要）：Proxy-Ingress-Idは、プロキシーイングレスを記録するためにRECORD_ROUTEオブジェクト内でのみ使用されます。 Proxy-Ingress-Idが指定されていない場合は、他の方法ではRECORD_ROUTEオブジェクトに含まれることのないローカルインターフェイスのアドレスを使用できます。 同様の手法が[RFC4090]のセクション6.1.1で使用されています。
  • Application Traffic Identifier：プライマリーイングレスとバックアップイングレスは、どのアプリケーショントラフィックをLSPに向けるべきかを両方とも知っていなければなりません（MUST）。 TRAFFIC_DESCRIPTORサブオブジェクト内のプレフィックスのリストでは不十分な場合は、共通に理解されるApplication Traffic Identifierを、プライマリーイングレスとバックアップイングレスの間で送信できます。 識別子の正確な意味は、プライマリーイングレスとバックアップイングレスの両方で同様に設定されるべきです。 Application Traffic Identifierは、プライマリーイングレスとバックアップイングレスに固有のコンテキスト内で解釈されます。
  • A Connection between Backup Ingress and Primary Ingress：プライマリーイングレスとバックアップイングレスの間に直接リンクがない場合は、それらの間にトンネルを設定しなければなりません（MUST）。

With this additional information, the primary ingress can create and signal the necessary RSVP extensions to support ingress protection.

これらの追加情報により、プライマリーイングレスは、イングレス保護をサポートするために必要なRSVPの拡張を作成してシグナリングできます。

6.2.1. Relay-Message Method

6.2.1. リレーメッセージ方式

To protect the primary ingress of an LSP, the primary ingress MUST do the following after the LSP is up.

LSPのプライマリーイングレスを保護するために、プライマリーイングレスは、LSPが立ち上がった後に次のことを行わなければなりません（MUST）。

  1. Select a PATH message P0 for the LSP.
  2. If the backup ingress is off path (the backup ingress is not the next hop of the primary ingress for P0), then send it a PATH message P0' with the content from P0 and an INGRESS_PROTECTION object; else (the backup ingress is a next hop, i.e., on-path case) add an INGRESS_PROTECTION object into the existing PATH message to the backup ingress (i.e., the next hop). The object contains the TRAFFIC_DESCRIPTOR subobject, the Backup Ingress Address subobject and the Label-Routes subobject. The options field is set to indicate whether a backup P2MP LSP is desired. The Label-Routes subobject contains the next hops of the primary ingress and their labels. Note that for the on-path case, there is an existing PATH message to the backup ingress (i.e., the next hop), and we just add an INGRESS_PROTECTION object into the existing PATH message to be sent to the backup ingress. We do not send a separate PATH message to the backup ingress for this existing PATH message.
  3. For each Pi of the other PATH messages for the LSP, send the backup ingress a PATH message Pi' with the content copied from Pi and an empty INGRESS_PROTECTION object.
  1. LSPのPATHメッセージP0を選択します。
  2. バックアップイングレスがパス外にある（バックアップイングレスがP0についてプライマリーイングレスのネクストホップではない）場合は、P0の内容とINGRESS_PROTECTIONオブジェクトを含むPATHメッセージP0'をバックアップイングレスに送信します。 そうでない（バックアップイングレスがネクストホップである、つまりパス上の）場合は、バックアップイングレス（つまりネクストホップ）への既存のPATHメッセージにINGRESS_PROTECTIONオブジェクトを追加します。 このオブジェクトには、TRAFFIC_DESCRIPTORサブオブジェクト、Backup Ingress Addressサブオブジェクト、Label-Routesサブオブジェクトが含まれます。 optionsフィールドは、バックアップP2MP LSPが希望されるかどうかを示すように設定されます。 Label-Routesサブオブジェクトには、プライマリーイングレスのネクストホップとそれらのラベルが含まれます。 パス上の場合、バックアップイングレス（つまりネクストホップ）への既存のPATHメッセージがあり、バックアップイングレスに送信されるその既存のPATHメッセージにINGRESS_PROTECTIONオブジェクトを追加するだけであることに注意してください。 この既存のPATHメッセージのために、別のPATHメッセージをバックアップイングレスに送信することはありません。
  3. LSPに関するその他の各PATHメッセージPiについて、Piからコピーした内容と空のINGRESS_PROTECTIONオブジェクトを含むPATHメッセージPi'をバックアップイングレスに送信します。

For every PATH message Pj' (i.e., P0'/Pi') to be sent to the backup ingress, it has the same SESSION as Pj (i.e., P0/Pi). If the backup ingress is off path, the primary ingress updates Pj' according to the backup ingress as its next hop before sending it. It adds the backup ingress to the beginning of the ERO and sets RSVP_HOP based on the interface to the backup ingress. The primary ingress MUST NOT set up any forwarding state to the backup ingress if the backup ingress is off path.

バックアップイングレスに送信されるすべてのPATHメッセージPj'（つまりP0'/Pi'）は、Pj（つまりP0/Pi）と同じSESSIONを持ちます。 バックアップイングレスがパス外にある場合、プライマリーイングレスは、Pj'を送信する前に、バックアップイングレスをネクストホップとしてPj'を更新します。 プライマリーイングレスは、EROの先頭にバックアップイングレスを追加し、バックアップイングレスへのインターフェイスに基づいてRSVP_HOPを設定します。 バックアップイングレスがパス外にある場合、プライマリーイングレスはバックアップイングレスへの転送状態を設定してはなりません（MUST NOT）。

6.2.2. Proxy-Ingress Method

6.2.2. プロキシーイングレス方式

The primary ingress is responsible for starting the RSVP signaling for the proxy-ingress node. To do this, the following MUST be done for the RSVP PATH message.

プライマリーイングレスは、プロキシーイングレスノードのRSVPシグナリングを開始する責任を負います。 そのために、RSVPのPATHメッセージについて次のことを行わなければなりません（MUST）。

  1. Compute the EROs for the LSP as normal for the ingress.
  2. If the selected backup ingress node is not the first node on the path (for all sub-LSPs), then insert it at the beginning of the ERO first, then the backup ingress node, and then the ingress node.
  3. In the PATH RECORD_ROUTE Object (RRO), instead of recording the ingress node's address, replace it with the Proxy-Ingress-Id.
  4. Leave the hop (HOP) object populated as usual with information for the ingress node.
  5. Add the INGRESS_PROTECTION object to the PATH message. Include the Backup Ingress Address (IPv4 or IPv6) subobject and the TRAFFIC_DESCRIPTOR subobject. Set or clear the options indicating that a backup P2MP LSP is desired.
  6. Optionally, add the FAST-REROUTE object [RFC4090] to the Path message. Indicate whether one-to-one backup is desired. Indicate whether facility backup is desired.
  7. The RSVP PATH message is sent to the backup node as normal.
  1. イングレスとして通常どおりLSPのEROを計算します。
  2. 選択したバックアップイングレスノードが（すべてのサブLSPについて）パス上の最初のノードでない場合は、EROの先頭にまずそれを挿入し、次にバックアップイングレスノード、次にイングレスノードを挿入します。
  3. PATHのRECORD_ROUTEオブジェクト（RRO）では、イングレスノードのアドレスを記録する代わりに、それをProxy-Ingress-Idに置き換えます。
  4. ホップ（HOP）オブジェクトには、通常どおりイングレスノードの情報を格納したままにします。
  5. PATHメッセージにINGRESS_PROTECTIONオブジェクトを追加します。 Backup Ingress Address（IPv4またはIPv6）サブオブジェクトとTRAFFIC_DESCRIPTORサブオブジェクトを含めます。 バックアップP2MP LSPが希望されることを示すオプションを設定またはクリアします。
  6. 任意で、PathメッセージにFAST-REROUTEオブジェクト[RFC4090]を追加します。 one-to-oneバックアップが希望されるかどうかを示します。 ファシリティーバックアップが希望されるかどうかを示します。
  7. RSVPのPATHメッセージは、通常どおりバックアップノードに送信されます。

If the ingress detects that it can't communicate with the backup ingress, then the ingress SHOULD instead send the PATH message to the next hop indicated in the ERO computed in step 1. Once the ingress detects that it can communicate with the backup ingress, the ingress SHOULD follow steps 1-7 to obtain ingress failure protection.

イングレスは、バックアップイングレスと通信できないことを検出した場合、代わりにステップ1で計算したEROで示されるネクストホップにPATHメッセージを送信すべきです（SHOULD）。 イングレスは、バックアップイングレスと通信できることを検出したら、イングレスの障害に対する保護を得るためにステップ1〜7に従うべきです（SHOULD）。

When the ingress node receives an RSVP PATH message with an INGRESS_PROTECTION object and the object specifies that node as the ingress node and the Previous Hop (PHOP) as the backup ingress node, the ingress node SHOULD remove the INGRESS_PROTECTION object from the PATH message before sending it out. Additionally, the ingress node MUST store that it will install ingress forwarding state for the LSP rather than midpoint forwarding.

イングレスノードが、INGRESS_PROTECTIONオブジェクトを含むRSVPのPATHメッセージを受信し、そのオブジェクトがそのノードをイングレスノードとして、前ホップ（Previous Hop: PHOP）をバックアップイングレスノードとして指定している場合、イングレスノードは、PATHメッセージを送出する前に、そこからINGRESS_PROTECTIONオブジェクトを削除すべきです（SHOULD）。 さらに、イングレスノードは、そのLSPについて中間点（midpoint）の転送ではなくイングレスの転送状態をインストールすることを記憶しなければなりません（MUST）。

When an RSVP RESV message is received by the ingress, it uses the Next Hop (NHOP) to determine whether the message is received from the backup ingress or from a different node. The stored associated PATH message contains an INGRESS_PROTECTION object that identifies the backup ingress node. If the RESV message is not from the backup node, then the ingress forwarding state SHOULD be set up, and the INGRESS_PROTECTION object MUST be added to the RESV before it is sent to the NHOP, which SHOULD be the backup node. If the RESV message is from the backup node, then the LSP SHOULD be considered available for use.

イングレスは、RSVPのRESVメッセージを受信すると、ネクストホップ（Next Hop: NHOP）を使用して、そのメッセージがバックアップイングレスから受信したものか、別のノードから受信したものかを判断します。 保存されている関連するPATHメッセージには、バックアップイングレスノードを識別するINGRESS_PROTECTIONオブジェクトが含まれています。 RESVメッセージがバックアップノードからのものでない場合は、イングレスの転送状態を設定すべきです（SHOULD）。 また、RESVをNHOPに送信する前に、RESVにINGRESS_PROTECTIONオブジェクトを追加しなければなりません（MUST）。 このNHOPはバックアップノードであるべきです（SHOULD）。 RESVメッセージがバックアップノードからのものである場合は、LSPが使用可能であるとみなすべきです（SHOULD）。

If the backup ingress node is on the forwarding path, then a RESV is received with an INGRESS_PROTECTION object and an NHOP that matches the backup ingress. In this case, the ingress node's address will not appear after the backup ingress in the RRO. The ingress node SHOULD set up the ingress forwarding state, just as is done if the ingress node of the LSP weren't protected.

バックアップイングレスノードが転送パス上にある場合、INGRESS_PROTECTIONオブジェクトと、バックアップイングレスに一致するNHOPとを含むRESVを受信します。 この場合、RRO内でバックアップイングレスの後にイングレスノードのアドレスは現れません。 イングレスノードは、LSPのイングレスノードが保護されていない場合とまったく同じように、イングレスの転送状態を設定すべきです（SHOULD）。

6.3. Backup Ingress Behavior

6.3. バックアップイングレスの振る舞い

A Label Edge Router (LER) determines that the ingress local protection is requested for an LSP if the INGRESS_PROTECTION object is included in the PATH message it receives for the LSP. The LER can further determine that it is the backup ingress if one of its addresses is in the Backup Ingress Address subobject of the INGRESS_PROTECTION object. The LER as the backup ingress will assume full responsibility of the ingress after the primary ingress fails. In addition, the LER determines that it is off path if it is not any node of the LSP. The LER determines whether it uses the Relay-Message Method or the Proxy-Ingress Method according to configurations.

ラベルエッジルーター（Label Edge Router: LER）は、LSPについて受信したPATHメッセージにINGRESS_PROTECTIONオブジェクトが含まれている場合、そのLSPについてイングレスのローカル保護が要求されていると判断します。 LERは、自身のアドレスの1つがINGRESS_PROTECTIONオブジェクトのBackup Ingress Addressサブオブジェクト内にある場合、自身がバックアップイングレスであるとさらに判断できます。 バックアップイングレスとしてのLERは、プライマリーイングレスに障害が発生した後、イングレスとしての責任を完全に引き受けます。 さらに、LERは、自身がLSPのどのノードでもない場合、自身がパス外にあると判断します。 LERは、リレーメッセージ方式とプロキシーイングレス方式のどちらを使用するかを、設定に従って決定します。

6.3.1. Backup Ingress Behavior in the Off-Path Case

6.3.1. パス外の場合のバックアップイングレスの振る舞い

The backup ingress considers itself a Point of Local Repair (PLR) and the primary ingress its next hop, and it provides a local protection for the primary ingress. It behaves very similarly to a PLR providing fast reroute where the primary ingress is considered to be the failure point to protect. Where not otherwise specified, the behavior given in [RFC4090] for a PLR applies.

バックアップイングレスは、自身をローカル修復ポイント（Point of Local Repair: PLR）とみなし、プライマリーイングレスをそのネクストホップとみなして、プライマリーイングレスに対するローカル保護を提供します。 バックアップイングレスは、プライマリーイングレスを保護対象の障害点とみなして高速リルートを提供するPLRと非常によく似た振る舞いをします。 特に指定がない限り、[RFC4090]でPLRについて規定されている振る舞いが適用されます。

The backup ingress MUST follow the control options specified in the INGRESS_PROTECTION object and the flags and specifications in the FAST-REROUTE object. This applies to providing a P2MP backup if the "P2MP backup" is set, a one-to-one backup if "one-to-one desired" is set, a facility backup if the "facility backup desired" is set, and backup paths that support both the desired bandwidth and administrative groups that are requested.

バックアップイングレスは、INGRESS_PROTECTIONオブジェクトで指定された制御オプションと、FAST-REROUTEオブジェクト内のフラグと指定に従わなければなりません（MUST）。 これは、「P2MP backup」が設定されている場合にはP2MPバックアップを提供すること、「one-to-one desired」が設定されている場合にはone-to-oneバックアップを提供すること、「facility backup desired」が設定されている場合にはファシリティーバックアップを提供すること、そして要求された帯域幅と管理グループの両方をサポートするバックアップパスを提供することに当てはまります。

If multiple non-empty INGRESS_PROTECTION objects have been received via multiple PATH messages for the same LSP, then the most recent one MUST be the one used.

同じLSPについて、複数のPATHメッセージを介して空でないINGRESS_PROTECTIONオブジェクトを複数受信した場合は、最新のものを使用しなければなりません（MUST）。

The backup ingress creates the appropriate forwarding state for the backup LSP tunnel(s) to the merge point(s).

バックアップイングレスは、マージポイントへのバックアップLSPトンネルのための適切な転送状態を作成します。

When the backup ingress sends a RESV message to the primary ingress, it MUST add an INGRESS_PROTECTION object into the message. It MUST set or clear the flags in the object to report "Ingress local protection available", "Ingress local protection in use", and "bandwidth protection".

バックアップイングレスは、プライマリーイングレスにRESVメッセージを送信するとき、そのメッセージにINGRESS_PROTECTIONオブジェクトを追加しなければなりません（MUST）。 バックアップイングレスは、「Ingress local protection available」、「Ingress local protection in use」、「bandwidth protection」を報告するために、オブジェクト内のフラグを設定またはクリアしなければなりません（MUST）。

If the backup ingress doesn't have a backup LSP tunnel to each of the merge points, it SHOULD clear "Ingress local protection available" and set NUB to the number of the merge points to which there is no backup LSP.

バックアップイングレスが各マージポイントへのバックアップLSPトンネルを持っていない場合、バックアップイングレスは「Ingress local protection available」をクリアし、NUBを、バックアップLSPが存在しないマージポイントの数に設定すべきです（SHOULD）。

When the primary ingress fails, the backup ingress redirects the traffic from a source into the backup P2P LSPs or the backup P2MP LSP transmitting the traffic to the next hops of the primary ingress, where the traffic is merged into the protected LSP.

プライマリーイングレスに障害が発生すると、バックアップイングレスは、送信元からのトラフィックを、プライマリーイングレスのネクストホップへトラフィックを送るバックアップP2P LSPまたはバックアップP2MP LSPにリダイレクトし、トラフィックはそこで保護対象のLSPに合流します。

In this case, the backup ingress MUST keep the PATH message with the INGRESS_PROTECTION object received from the primary ingress and the RESV message with the INGRESS_PROTECTION object to be sent to the primary ingress. The backup ingress MUST set the "local protection in use" flag in the RESV message, which indicates that the backup ingress is actively redirecting the traffic into the backup P2P LSPs or the backup P2MP LSP for locally protecting the primary ingress failure.

この場合、バックアップイングレスは、プライマリーイングレスから受信したINGRESS_PROTECTIONオブジェクトを含むPATHメッセージと、プライマリーイングレスに送信するINGRESS_PROTECTIONオブジェクトを含むRESVメッセージを保持しなければなりません（MUST）。 バックアップイングレスは、RESVメッセージ内の「local protection in use」フラグを設定しなければなりません（MUST）。 このフラグは、プライマリーイングレスの障害をローカルに保護するために、バックアップイングレスがトラフィックをバックアップP2P LSPまたはバックアップP2MP LSPに能動的にリダイレクトしていることを示します。

Note that the RESV message with this piece of information will not be sent to the primary ingress because the primary ingress has failed.

プライマリーイングレスには障害が発生しているため、この情報を含むRESVメッセージはプライマリーイングレスに送信されないことに注意してください。

If the backup ingress has not received any PATH messages from the primary ingress for an extended period of time (e.g., a cleanup timeout interval) and a confirmed primary ingress failure did not occur, then the standard RSVP soft-state removal SHOULD occur. The backup ingress SHALL remove the state for the PATH message from the primary ingress and either tear down the one-to-one backup LSPs for protecting the primary ingress if one-to-one backup is used or unbind the facility backup LSPs if facility backup is used.

バックアップイングレスが長期間（たとえば、クリーンアップタイムアウト間隔）にわたってプライマリーイングレスからPATHメッセージを1つも受信しておらず、かつプライマリーイングレスの障害が確認されていない場合は、標準的なRSVPのソフトステートの削除が行われるべきです（SHOULD）。 バックアップイングレスは、プライマリーイングレスからのPATHメッセージの状態を削除し、one-to-oneバックアップが使用されている場合にはプライマリーイングレスを保護するためのone-to-oneバックアップLSPを解体し、ファシリティーバックアップが使用されている場合にはファシリティーバックアップLSPのバインドを解除することになります（SHALL）。

When the backup ingress receives a PATH message from the primary ingress for locally protecting the primary ingress of a protected LSP, it MUST check to see if any critical information has been changed. If the next hops of the primary ingress are changed, the backup ingress SHALL update its backup LSP(s) accordingly.

バックアップイングレスは、保護対象のLSPのプライマリーイングレスをローカルに保護するためのPATHメッセージをプライマリーイングレスから受信したとき、重要な情報が変更されていないかを確認しなければなりません（MUST）。 プライマリーイングレスのネクストホップが変更されている場合、バックアップイングレスはそれに応じてバックアップLSPを更新することになります（SHALL）。

6.3.1.1. Relay-Message Method
6.3.1.1. リレーメッセージ方式

When the backup ingress receives a PATH message with a non-empty INGRESS_PROTECTION object, it examines the object to learn what traffic associated with the LSP. It determines the next hops to be merged to by examining the Label-Routes subobject in the object.

バックアップイングレスは、空でないINGRESS_PROTECTIONオブジェクトを含むPATHメッセージを受信すると、そのオブジェクトを調べて、どのトラフィックがLSPに関連付けられているかを知ります。 バックアップイングレスは、オブジェクト内のLabel-Routesサブオブジェクトを調べることで、合流先となるネクストホップを決定します。

The backup ingress MUST store the PATH message received from the primary ingress but NOT forward it.

バックアップイングレスは、プライマリーイングレスから受信したPATHメッセージを保存しなければなりません（MUST）が、それを転送はしません（NOT）。

The backup ingress responds with a RESV message to the PATH message received from the primary ingress. If the backup ingress is off path, the LABEL object in the RESV message contains IMPLICIT-NULL. If the INGRESS_PROTECTION object is not "empty", the backup ingress SHALL send the RESV message with the state indicating protection is available after the backup LSP(s) are successfully established.

バックアップイングレスは、プライマリーイングレスから受信したPATHメッセージに対してRESVメッセージで応答します。 バックアップイングレスがパス外にある場合、RESVメッセージ内のLABELオブジェクトにはIMPLICIT-NULLが含まれます。 INGRESS_PROTECTIONオブジェクトが「空」でない場合、バックアップイングレスは、バックアップLSPの確立に成功した後に、保護が利用可能であることを示す状態を含むRESVメッセージを送信することになります（SHALL）。

6.3.1.2. Proxy-Ingress Method
6.3.1.2. プロキシーイングレス方式

When receiving a RESV message for an LSP from a router that is not primary ingress, the backup ingress collects the pair of (IPv4/IPv6 subobject, Label subobject) in the second place to the top pair in the RECORD_ROUTE object of the message. It determines the next hops to be merged according to the set of the pairs collected. If a Label-Routes subobject is included in the INGRESS_PROTECTION object, the included IPv4/IPv6 subobjects are used to filter the set down to the specific next hops where protection is desired. An RESV message MUST have been received before the backup ingress can create or select the appropriate backup LSP.

バックアップイングレスは、プライマリーイングレスではないルーターからLSPのRESVメッセージを受信すると、そのメッセージのRECORD_ROUTEオブジェクト内で、先頭のペアから2番目の位置にある（IPv4/IPv6サブオブジェクト、Labelサブオブジェクト）のペアを収集します。 バックアップイングレスは、収集したペアの集合に従って、合流先となるネクストホップを決定します。 INGRESS_PROTECTIONオブジェクトにLabel-Routesサブオブジェクトが含まれている場合は、含まれているIPv4/IPv6サブオブジェクトを使用して、その集合を保護が希望される特定のネクストホップに絞り込みます。 バックアップイングレスが適切なバックアップLSPを作成または選択できるようになる前に、RESVメッセージを受信していなければなりません（MUST）。

When the backup ingress receives a PATH message with the INGRESS_PROTECTION object, the backup ingress examines the object to learn what traffic associated with the LSP. The backup ingress forwards the PATH message to the ingress node with the normal RSVP changes.

バックアップイングレスは、INGRESS_PROTECTIONオブジェクトを含むPATHメッセージを受信すると、そのオブジェクトを調べて、どのトラフィックがLSPに関連付けられているかを知ります。 バックアップイングレスは、通常のRSVPの変更を加えて、PATHメッセージをイングレスノードに転送します。

When the backup ingress receives a RESV message with the INGRESS_PROTECTION object, the backup ingress records an IMPLICIT-NULL label in the RRO. Then, the backup ingress forwards the RESV message to the ingress node, which is acting for the proxy ingress.

バックアップイングレスは、INGRESS_PROTECTIONオブジェクトを含むRESVメッセージを受信すると、RROにIMPLICIT-NULLラベルを記録します。 その後、バックアップイングレスは、RESVメッセージを、プロキシーイングレスとして動作しているイングレスノードに転送します。

6.3.2. Backup Ingress Behavior in the On-Path Case

6.3.2. パス上の場合のバックアップイングレスの振る舞い

An LER as the backup ingress determines that it is on path if one of its addresses is a next hop of the primary ingress; for the Proxy-Ingress Method, the primary ingress is determined as not its next hop by checking the PATH message with the INGRESS_PROTECTION object received from the primary ingress. The LER on path MUST send the corresponding PATH messages without any INGRESS_PROTECTION object to its next hops. It creates a number of backup P2P LSPs or a backup P2MP LSP from itself to the other next hops (i.e., the next hops other than the backup ingress) of the primary ingress. The other next hops are from the Label-Routes subobject.

バックアップイングレスとしてのLERは、自身のアドレスの1つがプライマリーイングレスのネクストホップである場合、自身がパス上にあると判断します。 プロキシーイングレス方式の場合は、プライマリーイングレスから受信したINGRESS_PROTECTIONオブジェクトを含むPATHメッセージを調べることで、プライマリーイングレスが自身のネクストホップではないと判断されます。 パス上のLERは、対応するPATHメッセージを、INGRESS_PROTECTIONオブジェクトを含めずに自身のネクストホップに送信しなければなりません（MUST）。 LERは、自身からプライマリーイングレスの他のネクストホップ（つまり、バックアップイングレス以外のネクストホップ）への、いくつかのバックアップP2P LSPまたは1つのバックアップP2MP LSPを作成します。 他のネクストホップは、Label-Routesサブオブジェクトから得られます。

It also creates a forwarding entry, which sends/multicasts the traffic from the source to the next hops of the backup ingress along the protected LSP when the primary ingress fails. The traffic is described by the TRAFFIC_DESCRIPTOR.

LERは、プライマリーイングレスに障害が発生したときに、送信元からのトラフィックを、保護対象のLSPに沿ってバックアップイングレスのネクストホップに送信／マルチキャストする転送エントリーも作成します。 そのトラフィックはTRAFFIC_DESCRIPTORによって記述されます。

After setting up all the backup P2P LSPs or the backup P2MP LSP, the backup ingress creates forwarding entry(s) for importing the traffic into the backup LSP(s) from the source when the primary ingress fails. Then, it MUST send the primary ingress a RESV message with an INGRESS_PROTECTION object. The object contains the state of the local protection, such as having the "local protection available" flag set to one, which indicates that the primary ingress is locally protected.

すべてのバックアップP2P LSPまたはバックアップP2MP LSPを設定した後、バックアップイングレスは、プライマリーイングレスに障害が発生したときに送信元からのトラフィックをバックアップLSPに取り込むための転送エントリーを作成します。 その後、バックアップイングレスは、INGRESS_PROTECTIONオブジェクトを含むRESVメッセージをプライマリーイングレスに送信しなければなりません（MUST）。 このオブジェクトにはローカル保護の状態が含まれます。 たとえば、「local protection available」フラグを1に設定することで、プライマリーイングレスがローカルに保護されていることを示します。

When the primary ingress fails, the backup ingress sends/multicasts the traffic from the source to its next hops along the protected LSP and imports the traffic into each of the backup P2P LSPs or to the backup P2MP LSP transmitting the traffic to the other next hops of the primary ingress, where the traffic is merged into a protected LSP.

プライマリーイングレスに障害が発生すると、バックアップイングレスは、送信元からのトラフィックを保護対象のLSPに沿って自身のネクストホップに送信／マルチキャストし、さらにプライマリーイングレスの他のネクストホップへトラフィックを送る各バックアップP2P LSPまたはバックアップP2MP LSPにトラフィックを取り込みます。 トラフィックはそこで保護対象のLSPに合流します。

During the local repair, the backup ingress MUST continue to send the PATH messages to its next hops as before and keep the PATH message with the INGRESS_PROTECTION object received from the primary ingress and the RESV message with the INGRESS_PROTECTION object to be sent to the primary ingress. It MUST set the "local protection in use" flag in the RESV message.

ローカル修復の間、バックアップイングレスは、以前と同様に自身のネクストホップへのPATHメッセージの送信を継続し、プライマリーイングレスから受信したINGRESS_PROTECTIONオブジェクトを含むPATHメッセージと、プライマリーイングレスに送信するINGRESS_PROTECTIONオブジェクトを含むRESVメッセージを保持しなければなりません（MUST）。 バックアップイングレスは、RESVメッセージ内の「local protection in use」フラグを設定しなければなりません（MUST）。

6.3.3. Failure Detection and Refresh PATH Messages

6.3.3. 障害検出とPATHメッセージのリフレッシュ

As described in [RFC4090], it is necessary to refresh the PATH messages via the backup LSP(s). The backup ingress MUST wait to refresh the PATH messages until it can accurately detect that the ingress node has failed. An example of such an accurate detection would be that the IGP has no bidirectional links to the ingress node, or a BFD session to the primary ingress' loopback address has failed and stayed failed after the network has reconverged.

[RFC4090]で説明されているように、バックアップLSPを介してPATHメッセージをリフレッシュする必要があります。 バックアップイングレスは、イングレスノードに障害が発生したことを正確に検出できるまで、PATHメッセージのリフレッシュを待たなければなりません（MUST）。 そのような正確な検出の例としては、IGPにイングレスノードへの双方向リンクが存在しないことや、ネットワークの再収束後に、プライマリーイングレスのループバックアドレスへのBFDセッションが失敗し、失敗したままであることが挙げられます。

As described in Section 6.4.3 of [RFC4090], the backup ingress, acting as PLR, MUST modify and send any saved PATH messages associated with the primary LSP to the corresponding next hops through backup LSP(s). Any PATH message sent will not contain any INGRESS_PROTECTION objects. The RSVP_HOP object in the message contains an IP source address belonging to the backup ingress. The SENDER_TEMPLATE object has the Backup Ingress Address as its tunnel sender address.

[RFC4090]のセクション6.4.3で説明されているように、PLRとして動作するバックアップイングレスは、プライマリーLSPに関連付けられた保存済みのPATHメッセージを修正し、バックアップLSPを通じて対応するネクストホップに送信しなければなりません（MUST）。 送信されるPATHメッセージにはINGRESS_PROTECTIONオブジェクトは含まれません。 メッセージ内のRSVP_HOPオブジェクトには、バックアップイングレスに属するIP送信元アドレスが含まれます。 SENDER_TEMPLATEオブジェクトは、トンネル送信者アドレスとしてバックアップイングレスのアドレス（Backup Ingress Address）を持ちます。

6.4. Revertive Behavior

6.4. 復帰の振る舞い

Upon a failure event in the (primary) ingress of a protected LSP, the protected LSP is locally repaired by the backup ingress. There are a couple of basic strategies for restoring the LSP to a full working path.

保護対象のLSPの（プライマリー）イングレスで障害イベントが発生すると、保護対象のLSPはバックアップイングレスによってローカルに修復されます。 LSPを完全に動作するパスに復元するための基本的な戦略がいくつかあります。

  • Revert to Primary Ingress: When the primary ingress is restored, it resignals each of the LSPs that start from the primary ingress. The traffic for every LSP successfully resignaled is switched back to the primary ingress from the backup ingress.
  • Global Repair by Backup Ingress: After determining that the primary ingress of an LSP has failed, the backup ingress computes a new optimal path, signals a new LSP along the new path, and switches the traffic to the new LSP.
  • Revert to Primary Ingress：プライマリーイングレスは、復旧すると、プライマリーイングレスから始まる各LSPを再シグナリングします。 再シグナリングに成功したすべてのLSPのトラフィックは、バックアップイングレスからプライマリーイングレスに切り戻されます。
  • Global Repair by Backup Ingress：LSPのプライマリーイングレスに障害が発生したと判断した後、バックアップイングレスは、新しい最適なパスを計算し、新しいパスに沿って新しいLSPをシグナリングし、トラフィックを新しいLSPに切り替えます。

6.4.1. Revert to Primary Ingress

6.4.1. プライマリーイングレスへの復帰

If "Revert to Primary Ingress" is desired for a protected LSP, the (primary) ingress of the LSP SHOULD resignal the LSP that starts from the primary ingress after the primary ingress restores. After the LSP is resignaled successfully, the traffic SHOULD be switched back to the primary ingress from the backup ingress on the source node and redirected into the LSP starting from the primary ingress.

保護対象のLSPについて「Revert to Primary Ingress」が希望される場合、LSPの（プライマリー）イングレスは、プライマリーイングレスの復旧後に、プライマリーイングレスから始まるLSPを再シグナリングすべきです（SHOULD）。 LSPの再シグナリングに成功した後、トラフィックは、送信元ノード上でバックアップイングレスからプライマリーイングレスに切り戻され、プライマリーイングレスから始まるLSPにリダイレクトされるべきです（SHOULD）。

The primary ingress can specify the "Revert to Ingress" control option in the INGRESS_PROTECTION object in the PATH messages to the backup ingress. After receiving the "Revert to Ingress" control option, the backup ingress MUST stop sending/refreshing PATH messages for the protected LSP.

プライマリーイングレスは、バックアップイングレスへのPATHメッセージ内のINGRESS_PROTECTIONオブジェクトで「Revert to Ingress」制御オプションを指定できます。 「Revert to Ingress」制御オプションを受信した後、バックアップイングレスは、保護対象のLSPのPATHメッセージの送信／リフレッシュを停止しなければなりません（MUST）。

6.4.2. Global Repair by Backup Ingress

6.4.2. バックアップイングレスによるグローバル修復

When the backup ingress has determined that the primary ingress of the protected LSP has failed (e.g., via the IGP), it can compute a new path and signal a new LSP along the new path so that it no longer relies upon local repair. To do this, the backup ingress MUST use the same tunnel sender address in the SENDER_TEMPLATE object and allocate an LSP ID different from the one of the old LSP as the LSP ID of the new LSP. This allows the new LSP to share resources with the old LSP. Alternately, the backup ingress can create a new LSP with no bandwidth reservation that duplicates the path(s) of the protected LSP, move traffic to the new LSP, delete the protected LSP, and then resignal the new LSP with bandwidth.

バックアップイングレスは、保護対象のLSPのプライマリーイングレスに障害が発生したと（たとえばIGPを介して）判断した場合、ローカル修復に依存しなくて済むように、新しいパスを計算し、新しいパスに沿って新しいLSPをシグナリングできます。 そのために、バックアップイングレスは、SENDER_TEMPLATEオブジェクト内で同じトンネル送信者アドレスを使用し、新しいLSPのLSP IDとして古いLSPのものとは異なるLSP IDを割り当てなければなりません（MUST）。 これにより、新しいLSPは古いLSPとリソースを共有できます。 あるいは、バックアップイングレスは、保護対象のLSPのパスを複製する帯域幅予約なしの新しいLSPを作成し、トラフィックを新しいLSPに移し、保護対象のLSPを削除してから、新しいLSPを帯域幅つきで再シグナリングすることもできます。

8. Compatibility

8. 互換性

This extension reuses and extends semantics and procedures defined in [RFC2205], [RFC3209], [RFC4090], and [RFC4875] to support ingress protection. The new object defined to indicate ingress protection has a Class Number of the form 0bbbbbbb. Per [RFC2205], a node not supporting this extension will not recognize the new Class Number and should respond with an "Unknown Object Class" error. The error message will propagate to the ingress, which can then take action to avoid the incompatible node as a backup ingress or may simply terminate the session.

この拡張は、イングレス保護をサポートするために、[RFC2205]、[RFC3209]、[RFC4090]、[RFC4875]で定義されているセマンティクスと手順を再利用し、拡張します。 イングレス保護を示すために定義された新しいオブジェクトは、0bbbbbbbの形式のクラス番号を持ちます。 [RFC2205]によれば、この拡張をサポートしないノードは新しいクラス番号を認識せず、「Unknown Object Class」エラーで応答するはずです。 エラーメッセージはイングレスまで伝播し、イングレスは、互換性のないノードをバックアップイングレスとして使用しないようにする措置を取ったり、単にセッションを終了したりできます。
