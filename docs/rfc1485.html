RFC 1485

A String Representation of Distinguished Names (OSI-DS 23 (v5))

RFC 1485

識別名の文字列表現（OSI-DS 23 (v5)）

Abstract

概要

The OSI Directory uses distinguished names as the primary keys to entries in the directory. Distinguished Names are encoded in ASN.1. When a distinguished name is communicated between to users not using a directory protocol (e.g., in a mail message), there is a need to have a user-oriented string representation of distinguished name. This specification defines a string format for representing names, which is designed to give a clean representation of commonly used names, whilst being able to represent any distinguished name. Please send comments to the author or to the discussion group <osi-ds@CS.UCL.AC.UK>.

OSIディレクトリーは、ディレクトリー内のエントリーの主キーとして識別名（distinguished name）を使います。識別名はASN.1でエンコードされます。ディレクトリープロトコルを使っていないユーザー間で（たとえばメールメッセージの中で）識別名をやり取りする場合、ユーザー向けの識別名の文字列表現が必要になります。この仕様では、名前を表現するための文字列形式を定義します。この形式は、一般的に使われる名前をすっきりと表現しつつ、任意の識別名を表現できるように設計されています。コメントは、著者または議論グループ<osi-ds@CS.UCL.AC.UK>に送ってください。

1. Why a notation is needed

1. 表記法が必要な理由

Many OSI Applications make use of Distinguished Names (DN) as defined in the OSI Directory, commonly known as X.500 [CCI88]. This specification assumes familiarity with X.500, and the concept of Distinguished Name. It is important to have a common format to be able to unambiguously represent a distinguished name. This might be done to represent a directory name on a business card or in an email message. There is a need for a format to support human to human communication, which must be string based (not ASN.1) and user oriented. This notation is targeted towards a general user oriented system, and in particular to represent the names of humans. Other syntaxes may be more appropriate for other uses of the directory. For example, the OSF Syntax may be more appropriate for some system oriented uses. (The OSF Syntax uses "/" as a separator, and forms names in a manner intended to resemble UNIX filenames).

多くのOSIアプリケーションは、一般にX.500 [CCI88]として知られるOSIディレクトリーで定義されている識別名（Distinguished Name、DN）を利用しています。この仕様は、X.500と識別名の概念を理解していることを前提とします。識別名を曖昧さなく表現できる共通の形式を持つことは重要です。これは、名刺や電子メールのメッセージにディレクトリー名を記載するために使われることがあります。人と人とのコミュニケーションを支援する形式が必要であり、それは（ASN.1ではなく）文字列に基づくユーザー向けのものでなければなりません。この表記法は、一般的なユーザー向けのシステムを対象とし、特に人間の名前を表現することを目的としています。ディレクトリーのほかの用途には、ほかの構文のほうが適している場合があります。たとえば、システム向けの用途によっては、OSF構文のほうが適している場合があります。（OSF構文は区切り文字として「/」を使い、UNIXのファイル名に似せた方法で名前を構成します。）

2. A notation for Distinguished Name

2. 識別名の表記法

2.1. Goals

2.1. 目標

The following goals are laid out:

次の目標を掲げます。

  • To provide an unambiguous representation of a distinguished name
  • To be an intuitive format for the majority of names
  • To be fully general, and able to represent any distinguished name
  • To be amenable to a number of different layouts to achieve an attractive representation.
  • To give a clear representation of the contents of the distinguished name
  • 識別名の曖昧さのない表現を提供すること
  • 大多数の名前に対して直感的な形式であること
  • 完全に汎用的で、任意の識別名を表現できること
  • 見栄えのよい表現を実現するために、さまざまなレイアウトに対応できること
  • 識別名の内容を明確に表現すること

2.2. Informal definition

2.2. 非形式的な定義

This notation is designed to be convenient for common forms of name. Some examples are given. The author's directory distinguished name would be written:

この表記法は、一般的な形式の名前に便利なように設計されています。いくつかの例を示します。著者のディレクトリー識別名は次のように書かれます。

   CN=Steve Hardcastle-Kille, OU=Computer Science, O=University
   College London, C=GB

   CN=Steve Hardcastle-Kille, OU=Computer Science, O=University
   College London, C=GB

This may be folded, perhaps to display in multi-column format. For example:

これは、たとえば複数列の形式で表示するために、折り返してもかまいません。たとえば次のようになります。

   CN=Steve Hardcastle-Kille,
   OU=Computer Science,
   O=University College London,
   C=GB

   CN=Steve Hardcastle-Kille,
   OU=Computer Science,
   O=University College London,
   C=GB

Another name might be:

別の名前は次のようになるでしょう。

   CN=Christian Huitema, O=INRIA, C=FR

   CN=Christian Huitema, O=INRIA, C=FR

Semicolon (";") may be used as an alternate separator.

代わりの区切り文字として、セミコロン（「;」）を使ってもかまいません。

   CN=Christian Huitema; O=INRIA; C=FR

   CN=Christian Huitema; O=INRIA; C=FR

In running text, this would be written as <CN=Christian Huitema; O=INRIA; C=FR>. Another example, shows how different attribute types are handled:

本文中では、これは<CN=Christian Huitema; O=INRIA; C=FR>のように書かれます。次の例は、さまざまな属性型がどのように扱われるかを示しています。

   CN=James Hacker,
   L=Basingstoke,
   O=Widget Inc,
   CN=GB

   CN=James Hacker,
   L=Basingstoke,
   O=Widget Inc,
   CN=GB

Here is an example of a multi-valued Relative Distinguished Name, where the namespace is flat within an organisation, and department is used to disambiguate certain names:

次は複数の値を持つ相対識別名（Relative Distinguished Name）の例です。この例では、組織内の名前空間はフラットで、特定の名前を区別するために部署が使われています。

   OU=Sales + CN=J. Smith, O=Widget Inc., C=US

   OU=Sales + CN=J. Smith, O=Widget Inc., C=US

The final example shows quoting of a comma in an Organisation name:

最後の例は、組織名に含まれるカンマのクォートを示しています。

   CN=L. Eagle, O="Sue, Grabbit and Runn", C=GB

   CN=L. Eagle, O="Sue, Grabbit and Runn", C=GB

2.3. Formal definition

2.3. 形式的な定義

A formal definition can now be given. The structure is specified in a BNF grammar in Figure 1. This BNF uses the grammar defined in RFC 822, with the terminals enclosed in <> [Cro82]. This definition is in an abstract character set, and so may be written in any character set supporting the explicitly defined special characters. The quoting mechanism is used for the following cases:

ここで形式的な定義を示します。構造は図1のBNF文法で規定します。このBNFは、RFC 822で定義されている文法を使い、終端記号を<>で囲みます[Cro82]。この定義は抽象的な文字集合に基づいているため、明示的に定義された特殊文字をサポートする任意の文字集合で書くことができます。クォートの仕組みは、次の場合に使います。

  • Strings containing ",", "+", "="or """, <CR>, "<", ">", "#", or ";".
  • Strings with leading or trailing spaces
  • Strings containing consecutive spaces
  • 「,」、「+」、「=」、「"」、<CR>、「<」、「>」、「#」、「;」のいずれかを含む文字列
  • 先頭または末尾に空白がある文字列
  • 連続する空白を含む文字列

There is an escape mechanism from the normal user oriented form, so that this syntax may be used to print any valid distinguished name. This is ugly. It is expected to be used only in pathological cases. There are two parts to this mechanism:

通常のユーザー向けの形式からのエスケープの仕組みがあり、これによって、この構文を使って任意の有効な識別名を出力できます。これは見苦しいものです。これは異常なケースでのみ使われることを想定しています。この仕組みは2つの部分からなります。

  1. Attributes types are represented in a (big-endian) dotted notation. (e.g., OID.2.6.53).
  2. Attribute values are represented in hexadecimal (e.g., #0A56CF).
  1. 属性型は（ビッグエンディアンの）ドット表記で表現されます（たとえば、OID.2.6.53）。
  2. 属性値は16進数で表現されます（たとえば、#0A56CF）。

The keyword specification is optional in the BNF, but mandatory for this specification. This is so that the same BNF may be used for the related specification on User Friendly Naming [HK93]. When this specification is followed, the attribute type keywords must always be present. A list of valid keywords for well known attribute types used in naming is given in Table 1. This is a list of keywords which must be supported. These are chosen because they appear in common forms of name, and can do so in a place which does not correspond to the default schema used. A register of valid keyworkds is maintained by the IANA.

キーワードの指定はBNFでは省略可能ですが、この仕様では必須です。これは、同じBNFを、ユーザーフレンドリーな命名（User Friendly Naming）に関する関連仕様[HK93]でも使えるようにするためです。この仕様に従う場合、属性型のキーワードは常に存在しなければなりません。命名に使われるよく知られた属性型の有効なキーワードの一覧を表1に示します。これはサポートしなければならないキーワードの一覧です。これらのキーワードは、一般的な形式の名前に現れ、しかも使われているデフォルトのスキーマに対応しない位置に現れることがあるため、選ばれています。有効なキーワードの登録簿はIANAが管理しています。

Only string type attributes are considered, but other attribute syntaxes could be supported locally. It is assumed that the interface will translate from the supplied string into PrintableString or T.61.

文字列型の属性のみを考慮していますが、ほかの属性構文をローカルにサポートすることもできます。インターフェイスが、与えられた文字列をPrintableStringまたはT.61に変換することを前提としています。

The "+" notation is used to specify multi-component RDNs. In this case, the types for attributes in the RDN must be explicit. The name is presented/input in a little-endian order (most significant component last).

「+」表記は、複数の構成要素からなるRDNを指定するために使います。この場合、RDN内の属性の型は明示しなければなりません。名前はリトルエンディアンの順序（最上位の構成要素が最後）で提示または入力されます。

When an address is written in a context where there is a need to delimit the entire address (e.g., in free text), it is recommended that the delimiters <> are used. The terminator > is a special in the notation to facilitate this delimitation.

アドレス全体を区切る必要がある文脈（たとえば自由形式のテキスト）でアドレスを書く場合は、区切り記号<>を使うことを推奨します。この区切りを容易にするために、終端記号>はこの表記法における特殊文字になっています。
