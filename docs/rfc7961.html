Transparent Interconnection of Lots of Links (TRILL): Interface Addresses APPsub-TLV

RFC 7961

TRILL（Transparent Interconnection of Lots of Links）：Interface Addresses APPsub-TLV

Abstract

概要

This document specifies a TRILL (Transparent Interconnection of Lots of Links) IS-IS application sub-TLV that enables the reporting by a TRILL switch of sets of addresses. Each set of addresses reports all of the addresses that designate the same interface (port) and also reports the TRILL switch by which that interface is reachable. For example, a 48-bit MAC (Media Access Control) address, IPv4 address, and IPv6 address can be reported as all corresponding to the same interface reachable by a particular TRILL switch. Such information could be used in some cases to synthesize responses to, or bypass the need for, the Address Resolution Protocol (ARP), the IPv6 Neighbor Discovery (ND) protocol, or the flooding of unknown MAC addresses.

この文書は、TRILLスイッチがアドレスの集合を報告できるようにする、TRILL（Transparent Interconnection of Lots of Links）のIS-ISアプリケーションサブTLVを規定します。 アドレスの各集合は、同じインターフェイス（ポート）を指すすべてのアドレスを報告し、さらにそのインターフェイスに到達可能なTRILLスイッチも報告します。 たとえば、48ビットのMAC（Media Access Control）アドレス、IPv4アドレス、IPv6アドレスが、いずれも特定のTRILLスイッチから到達可能な同じインターフェイスに対応するものとして報告できます。 このような情報は、場合によっては、アドレス解決プロトコル（ARP）、IPv6近隣探索（ND）プロトコル、または未知のMACアドレスのフラッディングに対する応答の合成や、それらの必要性の回避に利用できます。

1. Introduction

1. はじめに

This document specifies a TRILL (Transparent Interconnection of Lots of Links) [RFC6325] IS-IS application sub-TLV (APPsub-TLV) [RFC6823] that enables the convenient representation of sets of addresses where all of the addresses in each set designate the same interface (port). For example, a 48-bit MAC (Media Access Control) [RFC7042] address, IPv4 address, and IPv6 address can be reported as all three designating the same interface. In addition, a Data Label (VLAN or Fine-Grained Label (FGL) [RFC7172]) is specified for the interface, along with the TRILL switch and, optionally, the TRILL switch port from which the interface is reachable. Such information could be used in some cases to synthesize responses to, or bypass the need for, the Address Resolution Protocol (ARP) [RFC826], the IPv6 Neighbor Discovery (ND) [RFC4861] protocol, the Reverse Address Resolution Protocol (RARP) [RFC903], or the flooding of unknown destination MAC addresses [ARPND]. If the information reported is complete, it can also be used to detect and discard packets with forged source addresses.

この文書は、アドレスの集合を簡便に表現できるようにする、TRILL（Transparent Interconnection of Lots of Links）[RFC6325]のIS-ISアプリケーションサブTLV（APPsub-TLV）[RFC6823]を規定します。 各集合内のアドレスは、すべて同じインターフェイス（ポート）を指します。 たとえば、48ビットのMAC（Media Access Control）[RFC7042]アドレス、IPv4アドレス、IPv6アドレスの3つすべてが同じインターフェイスを指すものとして報告できます。 さらに、そのインターフェイスに対して、データラベル（VLANまたはFine-Grained Label（FGL）[RFC7172]）が、そのインターフェイスに到達可能なTRILLスイッチ、およびオプションでTRILLスイッチのポートとともに指定されます。 このような情報は、場合によっては、アドレス解決プロトコル（ARP）[RFC826]、IPv6近隣探索（ND）[RFC4861]プロトコル、逆アドレス解決プロトコル（RARP）[RFC903]、または宛先MACアドレスが未知の場合のフラッディング[ARPND]に対する応答の合成や、それらの必要性の回避に利用できます。 報告される情報が完全であれば、送信元アドレスが偽造されたパケットを検出して破棄するためにも利用できます。

This APPsub-TLV appears inside the TRILL GENINFO TLV specified in the End Station Address Distribution Information (ESADI) RFC [RFC7357] but may also occur in other application contexts. The "directory assistance" TRILL Edge services [DirectoryScheme] are expected to make use of this APPsub-TLV.

このAPPsub-TLVは、End Station Address Distribution Information（ESADI）のRFC [RFC7357]で規定されたTRILL GENINFO TLVの中に現れますが、他のアプリケーションの文脈で現れることもあります。 「ディレクトリー支援（directory assistance）」のTRILLエッジサービス[DirectoryScheme]は、このAPPsub-TLVを利用することが想定されています。

Although in some IETF protocols address field types are represented by an Ethertype [RFC7042] or a hardware address type [RFC5494], only the Address Family Number (AFN) is used in this APPsub-TLV to represent the address field type.

一部のIETFプロトコルでは、アドレスフィールドの種類がEthertype [RFC7042]やハードウェアアドレスタイプ[RFC5494]で表されますが、このAPPsub-TLVでは、アドレスフィールドの種類を表すためにアドレスファミリー番号（Address Family Number、AFN）のみを使用します。

2. Format of the Interface Addresses APPsub-TLV

2. Interface Addresses APPsub-TLVの形式

The Interface Addresses (IA) APPsub-TLV is used to advertise a set of addresses indicating the same interface (port) within a Data Label (VLAN or FGL). It also associates that interface with the TRILL switch and, optionally, the TRILL switch port by which the interface is reachable. These addresses can be in different address families. For example, the IA APPsub-TLV can be used to declare that a particular interface with specified IPv4, IPv6, and 48-bit MAC addresses in some particular Data Label is reachable from a particular TRILL switch. While those three types of addresses are likely to be the only types of interest, any address type for which an AFN has been assigned by IANA can be represented.

Interface Addresses（IA）APPsub-TLVは、データラベル（VLANまたはFGL）内で同じインターフェイス（ポート）を示すアドレスの集合を広告するために使用します。 また、そのインターフェイスを、そのインターフェイスに到達可能なTRILLスイッチ、およびオプションでTRILLスイッチのポートに関連付けます。 これらのアドレスは、異なるアドレスファミリーに属していてもかまいません。 たとえば、IA APPsub-TLVを使用して、特定のデータラベル内で特定のIPv4、IPv6、48ビットMACアドレスを持つ特定のインターフェイスが、特定のTRILLスイッチから到達可能であることを宣言できます。 関心の対象となるアドレスの種類はこの3種類だけである可能性が高いものの、IANAによってAFNが割り当てられているアドレスの種類であれば、どれでも表現できます。

The Template field in a particular IA APPsub-TLV indicates the format of each Address Set it carries. Certain well-known sets of addresses are represented by special values. Other sets of addresses are specified by a list of AFNs. The Template format that uses a list of AFNs provides an explicit pattern for the type and order of addresses in each Address Set in the IA APPsub-TLV that includes that Template.

特定のIA APPsub-TLVのTemplateフィールドは、そのIA APPsub-TLVが運ぶ各Address Setの形式を示します。 よく知られた特定のアドレスの集合は、特別な値で表されます。 それ以外のアドレスの集合は、AFNのリストで指定されます。 AFNのリストを使用するTemplateの形式は、そのTemplateを含むIA APPsub-TLV内の各Address Setについて、アドレスの種類と順序の明示的なパターンを提供します。

A device or application making use of IA APPsub-TLV data is not required to make use of all IA data. For example, a device or application that was only interested in MAC and IPv6 addresses could ignore any IPv4 or other types of address information that was present.

IA APPsub-TLVのデータを利用する装置やアプリケーションが、IAデータのすべてを利用する必要はありません。 たとえば、MACアドレスとIPv6アドレスにしか関心のない装置やアプリケーションは、存在するIPv4やその他の種類のアドレス情報を無視できます。

Figure 1 shows an IA APPsub-TLV as it would appear inside an IS-IS Flooding Scope Link State PDU (FS-LSP) using an extended flooding scope [RFC7356] TLV -- for example, in ESADI [RFC7357]. Within an IS-IS FS-LSP using traditional [ISO-10589] TLVs, the Type and Length would be 1-byte unsigned integers equal to or less than 255, but with an extended TLV, the Type and Length are 2-byte unsigned integers.

図1は、拡張フラッディングスコープ[RFC7356] TLVを使用するIS-ISのFlooding Scope Link State PDU（FS-LSP）内（たとえば、ESADI [RFC7357]内）に現れる場合のIA APPsub-TLVを示しています。 従来の[ISO-10589] TLVを使用するIS-IS FS-LSP内では、TypeとLengthは255以下の1バイトの符号なし整数になりますが、拡張TLVでは、TypeとLengthは2バイトの符号なし整数です。

  • Type: Interface Addresses TRILL APPsub-TLV type; set to 10 (IA-SUBTLV).
  • Length: Variable; minimum 7. If Length is 6 or less or if the APPsub-TLV extends beyond the size of an encompassing TRILL GENINFO TLV or other context, the APPsub-TLV MUST be ignored. For manageability, a counter reflecting the receipt of such malformed IA APPsub-TLVs should be maintained.

  • Addr Sets End: The unsigned integer byte number, within the IA APPsub-TLV value part, of the last byte of the last Address Set, where the first byte is numbered 1. This will be the number of the byte just before the first sub-sub-TLV if any sub-sub-TLVs are present (see Section 3). The processing is as follows:

    • If this field is greater than Length or points to before the end of the Template, the IA APPsub-TLV is corrupt and MUST be discarded.
    • If this field is equal to Length, there are no sub-sub-TLVs.
    • If this field is less than Length, sub-sub-TLVs are parsed as specified in Section 3.

    Note: This field is always 2 bytes in size.

  • Nickname: The nickname (see Section 1.1) of the TRILL switch by which the Address Sets are reachable. If 0, the Address Sets are reachable from the TRILL switch originating the message containing the APPsub-TLV (for example, an ESADI [RFC7357] message).

  • Flags: A byte of flags, as follows:

        0 1 2 3 4 5 6 7
   +-+-+-+-+-+-+-+-+
   |D|L|   RESV    |
   +-+-+-+-+-+-+-+-+
    D:
    Directory flag: If D is 1, the APPsub-TLV contains directory information [RFC7067].
    L:
    Local flag: If L is 1, the APPsub-TLV contains information learned locally by observing ingressed frames [RFC6325]. (Both D and L can be set to 1 in the same IA APPsub-TLV if a TRILL switch had learned an address locally and also advertised it as a directory.)
    RESV:
    Additional reserved flag bits that MUST be sent as zero and ignored on receipt.
  • Confidence: This 8-bit unsigned quantity in the range 0 to 254 indicates the confidence level in the addresses being transported (see Section 4.8.2 of [RFC6325]). A value of 255 is treated as if it was 254.

  • Template: The initial byte of this field is the unsigned integer K. If K has a value from 1 to 31, it indicates that this initial byte is followed by a list of K AFNs that specify the exact structure and order of each Address Set occurring later in the APPsub-TLV. K can be 1, which is the minimum valid value. If K is 0, the IA APPsub-TLV is ignored. If K is 32 to 254, the length of the Template field is 1 byte, and its value is intended to correspond to a particular ordered set of AFNs, some of which are specified below. The value of 255 for K is reserved for future definition and causes the IA APPsub-TLV to be ignored.

    If the Template uses explicit AFNs, it looks like the following, with the number of AFNs, up to 31, equal to K.

          +-+-+-+-+-+-+-+-+
      |  K            |                  (1 byte)
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |  AFN 1                        |  (2 bytes)
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |  AFN 2                        |  (2 bytes)
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |   ...
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |  AFN K                        |  (2 bytes)
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

    For K in the range 32 to 39, values indicate a specific sequence, as specified below. The values of K from 40 to 254 are reserved for future specification. If the value of K is not understood by a receiver of the IA-APPsub-TLV, any Address Sets present are ignored.

    Table 1
    K Addresses in order of occurrence
    32 48-bit MAC
    33 48-bit MAC, IPv4
    34 48-bit MAC, IPv6
    35 48-bit MAC, IPv4, IPv6
    36 48-bit MAC, RBridge port
    37 48-bit MAC, IPv4, RBridge port
    38 48-bit MAC, IPv6, RBridge port
    39 48-bit MAC, IPv4, IPv6, RBridge port

    For ease of decoding, note that for values of K between 32 and 39 inclusive, the 0x01 bit indicates that an IPv4 address is present, the 0x02 bit indicates that an IPv6 address is present, and the 0x04 bit indicates that an RBridge Port ID is present.

  • AFN: A 2-byte Address Family Number. The number of AFNs present is given by K, except that there are no AFNs if K is greater than 31. The AFN sequence specifies the structure of the Address Sets occurring later in the TLV. For example, if the Template size is 2 and the two AFNs present are the AFNs for a 48-bit MAC and an IPv4 address, in that order, then each Address Set present will consist of a 6-byte MAC address followed by a 4-byte IPv4 address. If any AFNs are present that are unknown to the receiving IS and the length of the corresponding address is not provided by a sub-sub-TLV as specified below, the receiving IS will be unable to parse the Address Sets and MUST ignore the IA APPsub-TLV.
  • Address Set: Each Address Set in the APPsub-TLV consists of exactly the same sequence of addresses and types as specified by the Template earlier in the APPsub-TLV. No alignment, other than to a byte boundary, is provided. The addresses in each Address Set are contiguous with no unused bytes between them, and the Address Sets are contiguous with no unused bytes between successive Address Sets. The Address Sets must fit within the TLV. See Section 7 on interpreting certain Address Sets.
  • sub-sub-TLVs: If the Address Sets indicated by Addr Sets End do not completely fill the length of the APPsub-TLV (as indicated by the Length field), then per Section 4 of [RFC5305] the remaining bytes are parsed as sub-sub-TLVs. Any such sub-sub-TLVs that are not known to the receiving TRILL switch are ignored. Should this parsing not be possible -- for example, there is only one remaining byte or an apparent sub-sub-TLV extends beyond the end of the TLV -- the containing IA APPsub-TLV is considered corrupt and is ignored. (Several sub-sub-TLV types are specified in Section 3.)
  • Type: Interface Addresses TRILL APPsub-TLVのタイプです。10（IA-SUBTLV）に設定します。
  • Length: 可変長で、最小値は7です。 Lengthが6以下の場合、またはAPPsub-TLVが、それを包含するTRILL GENINFO TLVやその他の文脈のサイズを超えている場合、そのAPPsub-TLVは無視しなければなりません（MUST）。 管理のために、このような不正な形式のIA APPsub-TLVの受信を反映するカウンターを維持するのがよいでしょう。

  • Addr Sets End: IA APPsub-TLVの値部分の中で、最後のAddress Setの最後のバイトが何バイト目であるかを示す符号なし整数です。最初のバイトを1番とします。 サブサブTLVが存在する場合、これは最初のサブサブTLVの直前のバイトの番号になります（セクション3を参照）。 処理は次のとおりです。

    • このフィールドがLengthより大きい場合、またはTemplateの終わりより前を指している場合、そのIA APPsub-TLVは破損しており、破棄しなければなりません（MUST）。
    • このフィールドがLengthと等しい場合、サブサブTLVはありません。
    • このフィールドがLengthより小さい場合、セクション3で規定するとおりにサブサブTLVを解析します。

    注: このフィールドのサイズは常に2バイトです。

  • Nickname: Address Setに到達可能なTRILLスイッチのニックネーム（セクション1.1を参照）です。 0の場合、Address Setは、そのAPPsub-TLVを含むメッセージ（たとえば、ESADI [RFC7357]メッセージ）を発信したTRILLスイッチから到達可能です。

  • Flags: 次のようなフラグの1バイトです。

        0 1 2 3 4 5 6 7
   +-+-+-+-+-+-+-+-+
   |D|L|   RESV    |
   +-+-+-+-+-+-+-+-+
    D:
    ディレクトリーフラグ: Dが1の場合、そのAPPsub-TLVはディレクトリー情報[RFC7067]を含みます。
    L:
    ローカルフラグ: Lが1の場合、そのAPPsub-TLVは、入力（ingress）されたフレームを観測することによってローカルに学習した情報[RFC6325]を含みます。 （TRILLスイッチがアドレスをローカルに学習し、さらにそれをディレクトリーとして広告した場合には、同じIA APPsub-TLVでDとLの両方を1に設定できます。）
    RESV:
    追加の予約済みフラグビットです。0として送信し、受信時には無視しなければなりません（MUST）。
  • Confidence: 0から254の範囲のこの8ビットの符号なしの値は、運ばれるアドレスの信頼度を示します（[RFC6325]のセクション4.8.2を参照）。 値255は、254であるかのように扱います。

  • Template: このフィールドの最初のバイトは符号なし整数Kです。 Kが1から31の値の場合、この最初のバイトの後に、APPsub-TLV内で後に現れる各Address Setの正確な構造と順序を指定するK個のAFNのリストが続くことを示します。 Kは1でもかまわず、これが有効な最小値です。 Kが0の場合、そのIA APPsub-TLVは無視されます。 Kが32から254の場合、Templateフィールドの長さは1バイトで、その値は順序付けられた特定のAFNの集合に対応することを意図しています。その一部は以下で規定します。 Kの値255は将来の定義のために予約されており、その場合IA APPsub-TLVは無視されます。

    Templateが明示的なAFNを使用する場合、次のようになります。AFNの数は最大31で、Kと等しくなります。

          +-+-+-+-+-+-+-+-+
      |  K            |                  (1 byte)
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |  AFN 1                        |  (2 bytes)
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |  AFN 2                        |  (2 bytes)
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |   ...
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |  AFN K                        |  (2 bytes)
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

    Kが32から39の範囲の場合、値は以下に規定する特定の並びを示します。 40から254のKの値は、将来の仕様のために予約されています。 IA-APPsub-TLVの受信者がKの値を理解できない場合、存在するAddress Setはすべて無視されます。

    表1
    K 出現順のアドレス
    32 48ビットMAC
    33 48ビットMAC、IPv4
    34 48ビットMAC、IPv6
    35 48ビットMAC、IPv4、IPv6
    36 48ビットMAC、RBridgeポート
    37 48ビットMAC、IPv4、RBridgeポート
    38 48ビットMAC、IPv6、RBridgeポート
    39 48ビットMAC、IPv4、IPv6、RBridgeポート

    デコードを容易にするために、32以上39以下のKの値では、0x01のビットがIPv4アドレスの存在を、0x02のビットがIPv6アドレスの存在を、0x04のビットがRBridge Port IDの存在を示すことに注意してください。

  • AFN: 2バイトのアドレスファミリー番号です。 存在するAFNの数はKで与えられます。ただし、Kが31より大きい場合、AFNはありません。 AFNの並びは、TLV内で後に現れるAddress Setの構造を指定します。 たとえば、Templateのサイズが2で、存在する2つのAFNが順に48ビットMACとIPv4アドレスのAFNである場合、存在する各Address Setは、6バイトのMACアドレスとそれに続く4バイトのIPv4アドレスで構成されます。 受信側ISにとって未知のAFNが存在し、かつ対応するアドレスの長さが以下に規定するサブサブTLVによって提供されていない場合、受信側ISはAddress Setを解析できないため、そのIA APPsub-TLVを無視しなければなりません（MUST）。
  • Address Set: APPsub-TLV内の各Address Setは、APPsub-TLV内でそれより前にあるTemplateが指定するものとまったく同じ、アドレスと種類の並びで構成されます。 バイト境界以外へのアラインメントは行いません。 各Address Set内のアドレスは間に未使用のバイトを挟まずに連続しており、Address Setどうしも、連続するAddress Setの間に未使用のバイトを挟まずに連続しています。 Address SetはTLV内に収まる必要があります。 特定のAddress Setの解釈についてはセクション7を参照してください。
  • sub-sub-TLVs: Addr Sets Endが示すAddress SetがAPPsub-TLVの長さ（Lengthフィールドが示すもの）を完全には満たさない場合、[RFC5305]のセクション4に従って、残りのバイトをサブサブTLVとして解析します。 そのようなサブサブTLVのうち、受信側TRILLスイッチにとって未知のものは無視されます。 この解析ができない場合（たとえば、残りが1バイトしかない場合や、サブサブTLVと思われるものがTLVの終わりを超えている場合）、それを含むIA APPsub-TLVは破損しているとみなされ、無視されます。 （いくつかのサブサブTLVのタイプをセクション3で規定します。）

Different IA APPsub-TLVs within the same or different LSPs or other data structures may have different Templates. The same AFN may occur more than once in a Template, and the same address may occur in different Address Sets. For example, a 48-bit MAC address interface might have three different IPv6 addresses. This could be represented by an IA APPsub-TLV whose Template specifically provided for one EUI-48 address and three IPv6 addresses; this might be an efficient format if there were multiple interfaces with that pattern. Alternatively, a Template with one 48-bit MAC and one IPv6 address could be used in an IA APPsub-TLV with three Address Sets each having the same MAC address but different IPv6 addresses; this might be the most efficient format if only one interface had multiple IPv6 addresses and other interfaces had only one IPv6 address.

同じLSPや異なるLSP、またはその他のデータ構造内の異なるIA APPsub-TLVは、異なるTemplateを持っていてもかまいません。 同じAFNがTemplate内に複数回現れてもよく、同じアドレスが異なるAddress Setに現れてもかまいません。 たとえば、48ビットMACアドレスのインターフェイスが、3つの異なるIPv6アドレスを持つ場合があります。 これは、1つのEUI-48アドレスと3つのIPv6アドレスを明示的に規定したTemplateを持つIA APPsub-TLVで表現できます。このパターンを持つインターフェイスが複数ある場合には、これが効率的な形式になるかもしれません。 あるいは、1つの48ビットMACと1つのIPv6アドレスを持つTemplateを、同じMACアドレスと異なるIPv6アドレスをそれぞれ持つ3つのAddress Setを含むIA APPsub-TLVで使用することもできます。複数のIPv6アドレスを持つインターフェイスが1つだけで、他のインターフェイスはIPv6アドレスを1つしか持たない場合には、これが最も効率的な形式になるかもしれません。

In order to be able to parse the Address Sets, a receiving TRILL switch must know at least the size of the address for each AFN or address type the Template specifies; however, the presence of the Addr Sets End field means that the sub-sub-TLVs, if any, can always be located by a receiver. A TRILL switch can be assumed to know the size of the AFNs mentioned in Section 5. Should a TRILL switch wish to include an AFN that some receiving TRILL switch in the campus may not know, it SHOULD include an AFN Size sub-sub-TLV as described in Section 3.1. If an IA APPsub-TLV is received with one or more AFNs in its Template for which the receiving TRILL switch does not know the length and for which an AFN Size sub-sub-TLV is not present, that IA APPsub-TLV MUST be ignored.

Address Setを解析できるようにするためには、受信側TRILLスイッチは、Templateが指定する各AFNまたはアドレスの種類について、少なくともアドレスのサイズを知っている必要があります。ただし、Addr Sets Endフィールドが存在するため、受信者はサブサブTLVがあれば常にその位置を特定できます。 TRILLスイッチは、セクション5で言及されているAFNのサイズを知っていると想定できます。 キャンパス内の一部の受信側TRILLスイッチが知らない可能性のあるAFNをTRILLスイッチが含めたい場合、セクション3.1で説明するAFN SizeサブサブTLVを含めるべきです（SHOULD）。 受信側TRILLスイッチが長さを知らず、かつAFN SizeサブサブTLVが存在しないAFNを、Template内に1つ以上含むIA APPsub-TLVを受信した場合、そのIA APPsub-TLVは無視しなければなりません（MUST）。

For manageability, a counter of ill-formed IA APPsub-TLVs received and ignored due to unknown K, unknown AFN, and the like (as described above) should be maintained.

管理のために、（上で説明したような）未知のK、未知のAFNなどが原因で受信して無視した、不正な形式のIA APPsub-TLVのカウンターを維持するのがよいでしょう。

3. IA APPsub-TLV Sub-sub-TLVs

3. IA APPsub-TLVのサブサブTLV

IA APPsub-TLVs can have sub-sub-TLVs (sub-TLVs of sub-TLVs [RFC5305]) at the end, as specified below. These sub-sub-TLVs occur after the Address Sets. The amount of space available for sub-sub-TLVs is determined from the overall IA APPsub-TLV length and the value of the Addr Sets End byte.

以下で規定するように、IA APPsub-TLVは末尾にサブサブTLV（サブTLVのサブTLV [RFC5305]）を持つことができます。 これらのサブサブTLVはAddress Setの後に現れます。 サブサブTLVに使用できる領域の大きさは、IA APPsub-TLV全体の長さとAddr Sets Endの値から決まります。

There is no ordering restriction on sub-sub-TLVs. Unless otherwise specified, each sub-sub-TLV type can occur zero, one, or many times in an IA APPsub-TLV. Any sub-sub-TLVs for which the Type is unknown are ignored. For manageability, a counter of sub-sub-TLVs received and ignored due to an unknown Type or other reasons, as described below, should be maintained.

サブサブTLVの順序に制限はありません。 特に規定がない限り、各サブサブTLVのタイプは、IA APPsub-TLV内に0回、1回、または何回でも現れることができます。 Typeが未知のサブサブTLVは無視されます。 管理のために、以下で説明するような、未知のTypeやその他の理由で受信して無視したサブサブTLVのカウンターを維持するのがよいでしょう。

The data structures of the sub-sub-TLVs shown below, with 2-byte Types and Lengths, assume that the enclosing IA APPsub-TLV is in an extended LSP TLV [RFC7356] or some non-LSP context. If they were used in an IA APPsub-TLV in a non-extended LSP [ISO-10589], then only 1-byte Types and Lengths could be used. As a result, any sub-sub-TLV types greater than 255 could not be used, and Length would be limited to 255.

以下に示す、2バイトのTypeとLengthを持つサブサブTLVのデータ構造は、それを包含するIA APPsub-TLVが拡張LSP TLV [RFC7356]内、または何らかのLSP以外の文脈にあることを前提としています。 拡張されていないLSP [ISO-10589]内のIA APPsub-TLVで使用する場合は、1バイトのTypeとLengthしか使用できません。 その結果、255より大きいサブサブTLVのタイプは使用できず、Lengthは255までに制限されます。

3.1. AFN Size Sub-sub-TLV

3.1. AFN SizeサブサブTLV

Using this sub-sub-TLV, the originating TRILL switch can specify the size of an address type. This is useful under the following two circumstances:

このサブサブTLVを使用すると、発信元のTRILLスイッチはアドレスの種類のサイズを指定できます。 これは、次の2つの状況で役に立ちます。

  1. One or more AFNs that are unknown to the receiving TRILL switch appear in the Template. If an AFN Size sub-sub-TLV is present for each such AFN, then at least the IA APPsub-TLV can be parsed, and possibly other addresses in each Address Set can still be used.
  2. If an AFN occurs in the Template that represents a variable-length address, this sub-sub-TLV gives its size for all occurrences in that IA APPsub-TLV.
  1. 受信側TRILLスイッチにとって未知のAFNが1つ以上Templateに現れる場合。 そのような各AFNに対してAFN SizeサブサブTLVが存在すれば、少なくともIA APPsub-TLVを解析でき、各Address Set内の他のアドレスを引き続き利用できる可能性があります。
  2. 可変長のアドレスを表すAFNがTemplateに現れる場合。このサブサブTLVは、そのIA APPsub-TLV内でのそのAFNのすべての出現に対するサイズを与えます。

Where each AFN Size Record is structured as follows:

ここで、各AFN Size Recordは次のような構造になっています。

      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |  AFN                          |  (2 bytes)
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |  AdrSize      |                  (1 byte)
      +-+-+-+-+-+-+-+-+

      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |  AFN                          |  (2 bytes)
      +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
      |  AdrSize      |                  (1 byte)
      +-+-+-+-+-+-+-+-+
  • Type: AFN Size sub-sub-TLV type; set to 1 (AFNsz).
  • Length: 3*N, where N is the number of AFN Size Records present. If Length is not a multiple of 3, the sub-sub-TLV MUST be ignored.
  • AFN Size Record(s): Zero or more 3-byte records, each giving the size of an address type identified by an AFN.
  • AFN: The AFN whose length is being specified by the AFN Size Record.
  • AdrSize: The length, in bytes, of addresses specified by the AFN field as an unsigned integer.
  • Type: AFN SizeサブサブTLVのタイプです。1（AFNsz）に設定します。
  • Length: 3*Nです。ここで、Nは存在するAFN Size Recordの数です。 Lengthが3の倍数でない場合、そのサブサブTLVは無視しなければなりません（MUST）。
  • AFN Size Record(s): 0個以上の3バイトのレコードです。各レコードは、AFNで識別されるアドレスの種類のサイズを与えます。
  • AFN: AFN Size Recordによって長さが指定されるAFNです。
  • AdrSize: AFNフィールドで指定されるアドレスの長さを、バイト単位の符号なし整数で表したものです。

An AFN Size sub-sub-TLV for any AFN known to the receiving TRILL switch is compared with the size known to the TRILL switch. If they differ, the IA APPsub-TLV is assumed to be corrupt and MUST be ignored.

受信側TRILLスイッチが知っているAFNに対するAFN SizeサブサブTLVは、そのTRILLスイッチが知っているサイズと比較されます。 両者が異なる場合、そのIA APPsub-TLVは破損しているとみなされ、無視しなければなりません（MUST）。

3.2. Fixed Address Sub-sub-TLV

3.2. Fixed AddressサブサブTLV

There may be cases where, in a particular IA APPsub-TLV, the same address would appear in every Address Set across the IA APPsub-TLV. To avoid wasted space, this sub-sub-TLV can be used to indicate such a fixed address. The address or addresses incorporated into the sets by this sub-sub-TLV are NOT mentioned in the IA APPsub-TLV Template.

特定のIA APPsub-TLVにおいて、同じアドレスがそのIA APPsub-TLV全体のすべてのAddress Setに現れる場合があります。 領域の無駄を避けるため、このサブサブTLVを使用して、そのような固定アドレスを示すことができます。 このサブサブTLVによって集合に組み込まれるアドレスは、IA APPsub-TLVのTemplateには一切記載されません。

  • Type: Data Label sub-sub-TLV type; set to 2 (FIXEDADR).
  • Length: Variable; minimum 2. If Length is 0 or 1, the sub-sub-TLV MUST be ignored.
  • AFN: Address Family Number of the Fixed Address.
  • Fixed Address: The address of the Type indicated by the preceding AFN field that is considered to be part of every Address Set in the IA APPsub-TLV.
  • Type: Data LabelサブサブTLVのタイプです。2（FIXEDADR）に設定します。
  • Length: 可変長で、最小値は2です。 Lengthが0または1の場合、そのサブサブTLVは無視しなければなりません（MUST）。
  • AFN: Fixed Addressのアドレスファミリー番号です。
  • Fixed Address: 直前のAFNフィールドが示すTypeのアドレスで、IA APPsub-TLV内のすべてのAddress Setの一部とみなされるものです。

The Length field implies a size for the Fixed Address. If that size differs from the size of the address type for the given AFN as known by the receiving TRILL switch, the Fixed Address sub-sub-TLV is considered corrupt and MUST be ignored.

Lengthフィールドは、Fixed Addressのサイズを暗に示します。 そのサイズが、受信側TRILLスイッチが知っている、指定されたAFNのアドレスの種類のサイズと異なる場合、そのFixed AddressサブサブTLVは破損しているとみなされ、無視しなければなりません（MUST）。

3.3. Data Label Sub-sub-TLV

3.3. Data LabelサブサブTLV

This sub-sub-TLV indicates the Data Label within which the interfaces listed in the IA APPsub-TLV are reachable. It is useful if the IA APPsub-TLV occurs outside of the context of a message specifying the Data Label or if it is desired and permitted to override that specification. Multiple occurrences of this sub-sub-TLV indicate that the interfaces are reachable in all of the Data Labels given.

このサブサブTLVは、IA APPsub-TLVに列挙されたインターフェイスが到達可能なデータラベルを示します。 これは、IA APPsub-TLVがデータラベルを指定するメッセージの文脈の外に現れる場合や、その指定を上書きすることが望まれ、かつ許可されている場合に役に立ちます。 このサブサブTLVが複数回現れる場合、そのインターフェイスは指定されたすべてのデータラベルで到達可能であることを示します。

  • Type: Data Label sub-TLV type; set to 3 (DATALEN).
  • Length: 2 or 3. If Length is some other value, the sub-sub-TLV MUST be ignored.
  • Data Label: If Length is 2, the bottom 12 bits of the Data Label are a VLAN ID and the top 4 bits are reserved (MUST be sent as zero and ignored on receipt). If Length is 3, the three Data Label bytes contain an FGL [RFC7172].
  • Type: Data LabelサブTLVのタイプです。3（DATALEN）に設定します。
  • Length: 2または3です。 Lengthがそれ以外の値の場合、そのサブサブTLVは無視しなければなりません（MUST）。
  • Data Label: Lengthが2の場合、Data Labelの下位12ビットがVLAN IDで、上位4ビットは予約済みです（0として送信し、受信時には無視しなければなりません（MUST））。 Lengthが3の場合、3バイトのData LabelはFGL [RFC7172]を含みます。

3.4. Topology Sub-sub-TLV

3.4. TopologyサブサブTLV

The presence of this sub-sub-TLV indicates that the interfaces given in the IA APPsub-TLV are reachable in the topology given. It is useful if the IA APPsub-TLV occurs outside of the context of a message indicating the topology or if it is desired and permitted to override that specification. If it occurs multiple times, then the Address Sets are in all of the topologies given.

このサブサブTLVが存在する場合、IA APPsub-TLVに示されたインターフェイスが、指定されたトポロジーで到達可能であることを示します。 これは、IA APPsub-TLVがトポロジーを示すメッセージの文脈の外に現れる場合や、その指定を上書きすることが望まれ、かつ許可されている場合に役に立ちます。 これが複数回現れる場合、Address Setは指定されたすべてのトポロジーに属します。

  • Type: Topology sub-TLV type; set to 4 (TOPOLOGY).
  • Length: 2. If Length is some other value, the sub-sub-TLV MUST be ignored.
  • RESV: 4 reserved bits. MUST be sent as zero and ignored on receipt.
  • Topology: The 12-bit topology number [RFC5120].
  • Type: TopologyサブTLVのタイプです。4（TOPOLOGY）に設定します。
  • Length: 2です。 Lengthがそれ以外の値の場合、そのサブサブTLVは無視しなければなりません（MUST）。
  • RESV: 4ビットの予約済みビットです。 0として送信し、受信時には無視しなければなりません（MUST）。
  • Topology: 12ビットのトポロジー番号[RFC5120]です。

4. Security Considerations

4. セキュリティーに関する考慮事項

The integrity of address mapping and reachability information as well as the correctness of Data Labels (VLANs or FGLs [RFC7172]) are very important. Forged, altered, or incorrect address mapping or data labeling can lead to delivery of packets to the incorrect party, violating security policy. However, this document merely describes a data format and does not provide any explicit mechanisms for securing that information, other than a few simple consistency checks that might detect some corrupted data. Security on the wire, or in storage, for this data is to be provided by the transport or storage used. For example, when transported with ESADI [RFC7357] or RBridge Channel [RFC7178], ESADI security or Channel Tunnel [ChannelTunnel] security mechanisms can be used, respectively.

アドレスのマッピングと到達可能性の情報の完全性、およびデータラベル（VLANまたはFGL [RFC7172]）の正しさは非常に重要です。 偽造された、改変された、または誤ったアドレスのマッピングやデータラベル付けは、パケットが誤った相手に配送される原因となり、セキュリティーポリシーに違反するおそれがあります。 しかし、この文書はデータ形式を説明しているだけであり、破損したデータの一部を検出できるかもしれない少数の単純な一貫性チェックを除いて、その情報を保護するための明示的なメカニズムは提供しません。 このデータの通信路上や保存時のセキュリティーは、使用するトランスポートやストレージによって提供されるべきものです。 たとえば、ESADI [RFC7357]またはRBridge Channel [RFC7178]で運ばれる場合、それぞれESADIのセキュリティーメカニズム、またはChannel Tunnel [ChannelTunnel]のセキュリティーメカニズムを使用できます。

The address mapping and reachability information, if known to be complete and correct, can be used to detect some cases of forged packet source addresses [RFC7067]. In particular, if native traffic from an end station is received by a TRILL switch that would otherwise accept it but authoritative data indicates that the source address should not be reachable from the receiving TRILL switch, that traffic should be discarded. The data format specified in this document may optionally include a TRILL switch Port ID number so that this forged address filtering can be optionally applied with port granularity. For manageability, a counter of frames so discarded should be maintained.

アドレスのマッピングと到達可能性の情報は、完全かつ正しいことがわかっていれば、パケットの送信元アドレスが偽造されている場合の一部を検出するために使用できます[RFC7067]。 特に、エンドステーションからのネイティブトラフィックを、本来ならそれを受け入れるはずのTRILLスイッチが受信したものの、信頼できるデータによれば送信元アドレスが受信側TRILLスイッチから到達可能であるはずがないと示されている場合、そのトラフィックは破棄するのがよいでしょう。 この文書で規定するデータ形式には、オプションでTRILLスイッチのPort ID番号を含めることができるため、この偽造アドレスのフィルタリングをオプションでポート単位の粒度で適用できます。 管理のために、このように破棄したフレームのカウンターを維持するのがよいでしょう。

See [RFC6325] for general TRILL security considerations.

TRILLのセキュリティーに関する一般的な考慮事項については、[RFC6325]を参照してください。

7. Processing Address Sets

7. Address Setの処理

The following processes should be followed in interpreting sets of AFN values in an IA APPsub-TLV to synthesize addresses. These apply whether the AFN values came from sub-sub-TLVs, appeared within an Address Set, or came from both sources. In general, the processing is applied separately to each Address Set as supplemented by any Fixed Address sub-sub-TLVs that are present.

IA APPsub-TLV内のAFN値の集合を解釈してアドレスを合成する際には、以下の処理に従うのがよいでしょう。 これらの処理は、AFN値がサブサブTLVから来たか、Address Set内に現れたか、あるいはその両方から来たかにかかわらず適用されます。 一般に、処理は、存在するFixed AddressサブサブTLVで補われた各Address Setに対して個別に適用されます。

The OUI AFN value is provided so that MAC addresses can be abbreviated if they have the same upper 24 bits. A MAC/24 is a 24-bit suffix intended to be prefixed by an OUI to create a 48-bit MAC address [RFC7042]; in the absence of an OUI, a MAC/24 entry cannot be used. A MAC/40 is a 40-bit suffix intended to be prefixed by an OUI to create a 64-bit MAC address [RFC7042]; in the absence of an OUI, a MAC/40 entry cannot be used.

OUIのAFN値は、上位24ビットが同じMACアドレスを省略して表せるようにするために用意されています。 MAC/24は、OUIを前に付けて48ビットMACアドレス[RFC7042]を作ることを意図した24ビットのサフィックスです。OUIがない場合、MAC/24のエントリーは使用できません。 MAC/40は、OUIを前に付けて64ビットMACアドレス[RFC7042]を作ることを意図した40ビットのサフィックスです。OUIがない場合、MAC/40のエントリーは使用できません。

Typically, an OUI would be provided as a Fixed Address sub-sub-TLV (see Section 3.2) using the OUI AFN, but there is no prohibition against one or more OUIs appearing in an Address Set.

通常、OUIは、OUIのAFNを使用したFixed AddressサブサブTLV（セクション3.2を参照）として提供されますが、1つ以上のOUIがAddress Set内に現れることも禁止されていません。

Each Address Set, after being supplemented by any Fixed Address sub-sub-TLVs, is processed by combining each OUI in the Address Set with each MAC/24 and each MAC/40 address in the Address Set. Depending on how many of each of these address types are present, zero or more 48-bit and/or 64-bit MAC addresses may be synthesized that are subsequently processed as if they had been part of the Address Set. If there are no MAC/24 or MAC/40 addresses present, any OUIs are ignored. If there are no OUIs, any MAC/24s and/or MAC/40s are ignored. If there are K1 OUIs, K2 MAC/24s, and K3 MAC/40s, K1*K2 48-bit MACs are synthesized and K1*K3 64-bit MACs are synthesized.

各Address Setは、Fixed AddressサブサブTLVで補われた後、そのAddress Set内の各OUIを、そのAddress Set内の各MAC/24アドレスおよび各MAC/40アドレスと組み合わせることによって処理されます。 これらの種類のアドレスがそれぞれいくつ存在するかに応じて、0個以上の48ビットMACアドレスと64ビットMACアドレスの一方または両方が合成されることがあり、それらは以降、Address Setの一部であったかのように処理されます。 MAC/24もMAC/40アドレスも存在しない場合、OUIはすべて無視されます。 OUIが存在しない場合、MAC/24とMAC/40はすべて無視されます。 K1個のOUI、K2個のMAC/24、K3個のMAC/40がある場合、K1*K2個の48ビットMACが合成され、K1*K3個の64ビットMACが合成されます。

IPv6/64 is an 8-byte quantity that is the first 64 bits of an IPv6 address. IPv6/64s are ignored unless, after the processing described above in this subsection, there are one or more 48-bit and/or 64-bit MAC addresses in the Address Set to provide the lower 64 bits of the IPv6 address. For this purpose, a 48-bit MAC address is expanded to 64 bits as described in Section 2.2.1 of [RFC7042]. If there are K4 IPv6/64s present and K5 48-bit and 64-bit MAC addresses present, K4*K5 128-bit IPv6 addresses are synthesized.

IPv6/64は、IPv6アドレスの最初の64ビットを表す8バイトの値です。 このサブセクションで上述した処理の後、IPv6アドレスの下位64ビットを提供する48ビットMACアドレスまたは64ビットMACアドレスがAddress Set内に1つ以上存在しない限り、IPv6/64は無視されます。 この目的のために、48ビットMACアドレスは、[RFC7042]のセクション2.2.1で説明されているとおりに64ビットに拡張されます。 K4個のIPv6/64と、合わせてK5個の48ビットMACアドレスおよび64ビットMACアドレスが存在する場合、K4*K5個の128ビットIPv6アドレスが合成されます。

Synthesized addresses are treated as if they had been members of the Address Set.

合成されたアドレスは、Address Setのメンバーであったかのように扱われます。

The Fixed Address sub-sub-TLV causes the IPv6/64 value given to be treated as if it occurred as a fourth entry inside each of the three Address Sets. When there is an IPv6/64 entry and a 48-bit MAC entry, the MAC value is expanded by inserting 0xfffe immediately after the OUI, and the local/global bit is inverted. The resulting Modified EUI-64-bit value is used as the lower 64 bits of the resulting IPv6 address (Section 2.2.1 of [RFC7042]). As a final point, since the 48-bit MAC addresses in these three Address Sets all have the same OUI (the IANA OUI [RFC7042]), it would have been possible to just have a MAC/24 value giving the lower 24 bits of the MAC in each Address Set. The OUI would then be supplied by a second Fixed Address sub-sub-TLV providing the OUI. With N Address Sets, this would have saved 3*N or 9 bytes, at a cost of 9 bytes (2 each for the Type and Length of the sub-sub-TLV, 2 for the OUI AFN, and 3 for the OUI). So, with just three Address Sets, there would be no net savings; however, with a larger number of Address Sets, there would be a net savings.

最後に、これら3つのAddress Set内の48ビットMACアドレスはすべて同じOUI（IANAのOUI [RFC7042]）を持つため、各Address SetにはMACの下位24ビットを与えるMAC/24の値だけを含めることもできました。 その場合、OUIは、OUIを提供する2つ目のFixed AddressサブサブTLVによって供給されます。 N個のAddress Setがある場合、これにより3*Nバイト、すなわち9バイトを節約できますが、9バイト（サブサブTLVのTypeとLengthにそれぞれ2バイト、OUIのAFNに2バイト、OUIに3バイト）のコストがかかります。 したがって、Address Setが3つだけでは正味の節約にはなりませんが、Address Setの数がもっと多ければ正味の節約になります。
