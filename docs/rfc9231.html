RFC 9231

追加のXMLセキュリティーUniform Resource Identifier（URI）

Abstract

概要

This document updates and corrects the IANA "XML Security URIs" registry that lists URIs intended for use with XML digital signatures, encryption, canonicalization, and key management. These URIs identify algorithms and types of information. This document also obsoletes and corrects three errata against RFC 6931.

この文書は、XMLデジタル署名、暗号化、正規化、および鍵管理での使用を意図したURIを列挙するIANAの「XML Security URIs」レジストリーを更新および修正します。これらのURIは、アルゴリズムと情報の種類を識別します。この文書はまた、RFC 6931を廃止し、RFC 6931に対する3件の正誤表を修正します。

1. Introduction

1. はじめに

XML digital signatures, canonicalization, and encryption were standardized by the W3C and by the joint IETF/W3C XMLDSIG working group [W3C] [XMLSEC]. These are now W3C Recommendations and some are also RFCs. They are available as follows:

XMLデジタル署名、正規化、および暗号化は、W3CとIETF/W3C合同のXMLDSIGワーキンググループ[W3C] [XMLSEC]によって標準化されました。これらは現在W3C勧告であり、一部はRFCでもあります。これらは次のとおり入手できます。

These documents and recommendations use URIs [RFC3986] to identify algorithms and keying information types. The W3C has subsequently produced updated XML Signature 1.1 [XMLDSIG11], Canonical XML 1.1 [CANON11], and XML Encryption 1.1 [XMLENC11] versions, as well as a new XML Signature Properties specification [XMLDSIG-PROP].

これらの文書と勧告は、アルゴリズムと鍵情報の種類を識別するためにURI[RFC3986]を使用します。W3Cはその後、更新版であるXML Signature 1.1[XMLDSIG11]、Canonical XML 1.1[CANON11]、およびXML Encryption 1.1[XMLENC11]の各バージョンと、新しいXML Signature Properties仕様[XMLDSIG-PROP]を作成しました。

In addition, the XML Encryption recommendation has been augmented by [GENERIC], which defines algorithms, XML types, and elements necessary to use generic hybrid ciphers in XML security applications. [GENERIC] also provides for a key encapsulation algorithm and a data encapsulation algorithm, with the combination of the two forming the generic hybrid cipher.

さらに、XML暗号化の勧告は[GENERIC]によって拡張されています。[GENERIC]は、XMLセキュリティーアプリケーションで汎用ハイブリッド暗号を使用するために必要なアルゴリズム、XML型、および要素を定義しています。[GENERIC]はまた、鍵カプセル化アルゴリズムとデータカプセル化アルゴリズムも規定しており、この2つの組み合わせが汎用ハイブリッド暗号を構成します。

All camel-case element names (names with both interior upper and lower case letters) herein, such as DigestValue, are from these documents.

この文書に出てくるDigestValueのようなキャメルケースの要素名（内部に大文字と小文字の両方を含む名前）は、すべてこれらの文書に由来します。

This document is an updated convenient reference list of URIs and corresponding algorithms in which there is expressed interest. This document fixes Errata [Err3597], [Err3965], and [Err4004], and obsoletes [RFC6931].

この文書は、関心が表明されているURIとそれに対応するアルゴリズムの、更新された便利な参照リストです。この文書は、正誤表[Err3597]、[Err3965]、および[Err4004]を修正し、[RFC6931]を廃止します。

All of the URIs for algorithms and data types herein are listed in the indexes in Section 4. Of these URIs, those that were added by earlier RFCs or by this document have a subsection in Section 2 or 3. A few URIs defined elsewhere also have a subsection in Section 2 or 3, but most such URIs do not. For example, use of SHA-256 as defined in [XMLENC11] has no subsection here but is included in the indexes in Section 4.

この文書に出てくるアルゴリズムとデータ型のURIは、すべてSection 4の索引に列挙されています。これらのURIのうち、以前のRFCまたはこの文書で追加されたものには、セクション2または3にサブセクションがあります。他で定義されたURIのうちいくつかにもセクション2または3にサブセクションがありますが、そのようなURIのほとんどにはありません。たとえば、[XMLENC11]で定義されているSHA-256の使用については、ここにサブセクションはありませんが、Section 4の索引には含まれています。

Specification in this document of the URI representing an algorithm does not imply endorsement of the algorithm for any particular purpose. A protocol specification, which this is not, generally gives algorithm and implementation requirements for the protocol. Security considerations for algorithms are constantly evolving, as documented elsewhere. This specification simply provides some URIs and relevant formatting when those URIs are used.

この文書でアルゴリズムを表すURIを規定することは、何らかの特定の目的に対してそのアルゴリズムを推奨することを意味しません。プロトコル仕様（この文書はそうではありません）は、一般にそのプロトコルに対するアルゴリズムと実装の要件を定めます。アルゴリズムのセキュリティーに関する考慮事項は、他の文書に記述されているとおり、常に変化しています。この仕様は、単にいくつかのURIと、それらのURIを使用する際の関連する形式を提供するだけです。

This document is not intended to change the algorithm implementation requirements of any IETF or W3C document. Use of terminology from [RFC2119] and [RFC8174] is intended to be only such as is already stated or implied by other authoritative documents.

この文書は、IETFやW3Cのいかなる文書のアルゴリズム実装要件を変更することも意図していません。[RFC2119]と[RFC8174]の用語の使用は、他の権威ある文書ですでに述べられている、または暗示されている範囲にとどめることを意図しています。

Progressing XML Digital Signature [RFC3275] along the Standards Track required removal of any algorithms from the original version [RFC3075] for which there was not demonstrated interoperability. This required removal of the Minimal Canonicalization algorithm, in which there was continued interest. The URI for Minimal Canonicalization was included in [RFC6931] and is included here.

XMLデジタル署名[RFC3275]を標準化過程で進めるためには、元のバージョン[RFC3075]から、相互運用性が実証されなかったアルゴリズムをすべて削除する必要がありました。このため、引き続き関心が寄せられていた最小正規化（Minimal Canonicalization）アルゴリズムが削除されました。最小正規化のURIは[RFC6931]に含まれており、この文書にも含まれています。

XMSS (eXtended Merkle Signature Scheme) and XMSSMT (XMSS Multi-Tree) [RFC8391] are stateful hash-based signature schemes [NIST800-208]. The Elliptic Curve Digital Signature Algorithm (ECDSA) [FIPS186-4] is the elliptic curve analogue of the Digital Signature Algorithm (DSA) signature method, i.e., the Digital Signature Standard (DSS). It takes no explicit parameters. For some detailed specifications of how to use it with SHA hash functions and XML Digital Signature, please see [X9.62] and [RFC4050]. The #sha3-*, #ecdsa-ripemd160, and #ecdsa-whirlpool fragments identify signature methods processed in the same way as specified by the #ecdsa-sha1 fragment, with the exception that a SHA3 function (see Section 2.1.5), RIPEMD160, or Whirlpool (see Section 2.1.4) is used instead of SHA-1.

楕円曲線デジタル署名アルゴリズム（ECDSA）[FIPS186-4]は、デジタル署名アルゴリズム（DSA）署名方式、すなわちデジタル署名標準（DSS）の楕円曲線版です。このアルゴリズムは明示的なパラメーターを取りません。SHAハッシュ関数およびXMLデジタル署名とともに使用する方法の詳細な仕様については、[X9.62]と[RFC4050]を参照してください。#sha3-*、#ecdsa-ripemd160、および#ecdsa-whirlpoolのフラグメントは、SHA-1の代わりにSHA3関数（Section 2.1.5を参照）、RIPEMD160、またはWhirlpool（Section 2.1.4を参照）を使用することを除き、#ecdsa-sha1フラグメントで規定されているのと同じ方法で処理される署名方式を識別します。

Conversion from integer to octet stream must be done according to the I2OSP operation defined in the [RFC8017] specification with the l parameter equal to the size of the base point order of the curve in octets (e.g., 32 for the P-256 curve and 66 for the P-521 curve [FIPS186-4]).

ECDSAアルゴリズムの出力は、通常(r, s)のペアと呼ばれる整数のペアで構成されます。署名値は、値rとsをこの順にオクテットエンコードした結果である2つのオクテットストリームを連結したもののbase64エンコーディングで構成されます。整数からオクテットストリームへの変換は、[RFC8017]仕様で定義されているI2OSP操作に従って行わなければなりません。このとき、lパラメーターは曲線のベースポイントの位数のオクテット単位のサイズに等しくします（たとえば、P-256曲線では32、P-521曲線では66です[FIPS186-4]）。

2.6.8. ChaCha20+Poly1305

2.6.8. ChaCha20+Poly1305 

Identifier:
   http://www.w3.org/2021/04/xmldsig-more#chacha20poly1305

Identifier:
   http://www.w3.org/2021/04/xmldsig-more#chacha20poly1305

ChaCha20+Poly1305 is an Authenticated Encryption with Associated Data (AEAD) algorithm. In addition to a 256-bit key and plain text to be encrypted and authenticated, ChaCha20+Poly1305 takes a 96-bit Nonce and variable-length Additional Authenticated Data (AAD). 2.8.1. HKDF Key Derivation

2.8.1. HKDF鍵導出

This section covers the HMAC-based Extract-and-Expand Key Derivation Function (HKDF [RFC5869]).

このセクションでは、HMACベースの抽出・拡張鍵導出関数（HKDF[RFC5869]）を扱います。

Identifier:
   http://www.w3.org/2021/04/xmldsig-more#hkdf

Identifier:
   http://www.w3.org/2021/04/xmldsig-more#hkdf

HKDF takes as inputs a hash function, an optional non-secret "salt", initial keying material (IKM), optional context and application-specific "info", and the required output keying size. Note that these strictly determine the output so, for example, invoking HKDF at different times but with the same salt, info, initial keying material, and output key size will produce identical output keying material.

HKDFは、入力として、ハッシュ関数、任意の秘密でない「salt」、初期鍵素材（IKM）、任意のコンテキストおよびアプリケーション固有の「info」、そして必要な出力鍵のサイズを取ります。これらは出力を厳密に決定することに注意してください。たとえば、異なる時点でHKDFを呼び出しても、salt、info、初期鍵素材、および出力鍵サイズが同じであれば、同一の出力鍵素材が生成されます。

The inputs can be supplied to HKDF as follows:

入力は次のようにHKDFに与えることができます。

hash function:
The algorithm attribute of a child DigestMethod element.
salt:
The content of a Salt child element of AgreementMethod in hex. If not provided, a string of zero octets as long as the hash function output is used as specified in [RFC5869].
IKM:
The content of an OriginatorKeyInfo child element of AgreementMethod in hex. May be absent in some applications where this is known through some other method.
info:
The content of the KA-Nonce child element of AgreementMethod in hex.
size:
The content of a KeySize child element of AgreementMethod as a decimal number.
ハッシュ関数：
子のDigestMethod要素のalgorithm属性。
salt:
AgreementMethodのSalt子要素の内容（16進数）。与えられない場合は、[RFC5869]で規定されているとおり、ハッシュ関数の出力と同じ長さのゼロオクテットの文字列が使用されます。
IKM:
AgreementMethodのOriginatorKeyInfo子要素の内容（16進数）。これが他の何らかの方法で知られている一部のアプリケーションでは、存在しないこともあります。
info:
AgreementMethodのKA-Nonce子要素の内容（16進数）。
サイズ：
AgreementMethodのKeySize子要素の内容（10進数）。

6. Security Considerations

6. セキュリティーに関する考慮事項

This RFC is concerned with documenting the URIs that designate algorithms and some data types used in connection with XML security. The security considerations vary widely with the particular algorithms, and the general security considerations for XML security are outside of the scope of this document but appear in [XMLDSIG11], [XMLENC11], [CANON10], [CANON11], and [GENERIC].

このRFCは、XMLセキュリティーに関連して使用されるアルゴリズムといくつかのデータ型を指定するURIを文書化することを目的としています。セキュリティーに関する考慮事項は個々のアルゴリズムによって大きく異なり、XMLセキュリティーの一般的なセキュリティーに関する考慮事項はこの文書の範囲外ですが、[XMLDSIG11]、[XMLENC11]、[CANON10]、[CANON11]、および[GENERIC]に記載されています。

[RFC6151] should be consulted before considering the use of MD5 as a DigestMethod or the use of HMAC-MD5 or RSA-MD5 as a SignatureMethod.

MD5をDigestMethodとして使用すること、またはHMAC-MD5やRSA-MD5をSignatureMethodとして使用することを検討する前に、[RFC6151]を参照すべきです。

See [RFC6194] for SHA-1 security considerations.

SHA-1のセキュリティーに関する考慮事項については[RFC6194]を参照してください。

Additional security considerations are given in connection with the description of some algorithms in the body of this document.

追加のセキュリティーに関する考慮事項は、この文書の本文中で、いくつかのアルゴリズムの説明に関連して示されています。

Implementers should be aware that cryptographic algorithms become weaker with time. As new cryptoanalysis techniques are developed and computing performance improves, the work factor to break a particular cryptographic algorithm will decrease. Therefore, cryptographic implementations should be modular, allowing new algorithms to be readily inserted. That is, implementers should be prepared for the set of mandatory-to-implement algorithms for any particular use to change over time. This is sometimes referred to as "algorithm agility" [RFC7696].

実装者は、暗号アルゴリズムが時間とともに弱くなることを認識しておくべきです。新しい暗号解析技術が開発され、計算性能が向上するにつれて、特定の暗号アルゴリズムを破るための作業量は減少します。したがって、暗号の実装はモジュール化し、新しいアルゴリズムを容易に組み込めるようにすべきです。つまり、実装者は、特定の用途に対する実装必須アルゴリズムの集合が時間とともに変化することに備えておくべきです。これは「アルゴリズムの俊敏性（algorithm agility）」と呼ばれることがあります[RFC7696]。

Appendix B. Bad URIs

Appendix B. 不正なURI

[RFC6931] included two bad URIs as shown below. "{Bad}" in the indexes (Sections 4.1 and 4.2) indicates such a bad value. Implementations SHOULD only generate the correct URI but SHOULD understand both the correct and erroneous URI.

[RFC6931]には、以下に示す2つの不正なURIが含まれていました。索引（セクション4.1と4.2）の"{Bad}"は、そのような不正な値を示します。実装は正しいURIのみを生成すべきです（SHOULD）。ただし、正しいURIと誤ったURIの両方を理解すべきです（SHOULD）。

2006/12/xmlc12n11#

2006/12/xmlc12n11#

  • Appears in the indices (Sections 4.1 and 4.2 of [RFC6931]) when it should be "2006/12/xmlc14n11#" (i.e., the "12" inside "xmlc12n11" should have been "14"). This is [Err3965] and is corrected in this document.
  • [RFC6931]の索引（セクション4.1と4.2）に現れていますが、正しくは"2006/12/xmlc14n11#"です（つまり、"xmlc12n11"の中の"12"は"14"であるべきでした）。これは[Err3965]であり、この文書で修正されています。

2007/05/xmldsig-more#rsa-sha224

2007/05/xmldsig-more#rsa-sha224

  • Appears in the indices (Sections 4.1 and 4.2 of [RFC6931]) when it should be "2001/04/xmldsig-more#rsa-sha224". This is [Err4004] and is corrected in this document.
  • [RFC6931]の索引（セクション4.1と4.2）に現れていますが、正しくは"2001/04/xmldsig-more#rsa-sha224"です。これは[Err4004]であり、この文書で修正されています。
