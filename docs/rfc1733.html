Distributed Electronic Mail Models

分散電子メールモデル

There are three fundamental models of client/server email: offline, online, and disconnected use. IMAP4 can be used in any one of these three models.

クライアント／サーバー型の電子メールには、オフライン、オンライン、切断利用（disconnected use）という3つの基本的なモデルがあります。IMAP4は、これら3つのモデルのどれでも使用できます。

The offline model is the most familiar form of client/server email today, and is used by protocols such as POP-3 (RFC 1225) and UUCP. In this model, a client application periodically connects to a server. It downloads all the pending messages to the client machine and deletes these from the server. Thereafter, all mail processing is local to the client. This model is store-and-forward; it moves mail on demand from an intermediate server (maildrop) to a single destination machine.

オフラインモデルは、今日もっともなじみのあるクライアント／サーバー型電子メールの形態で、POP-3（RFC 1225）やUUCPなどのプロトコルで使用されています。このモデルでは、クライアントアプリケーションが定期的にサーバーに接続します。クライアントアプリケーションは、保留中のすべてのメッセージをクライアントマシンにダウンロードし、それらをサーバーから削除します。それ以降、すべてのメール処理はクライアントのローカルで行われます。このモデルは蓄積交換（store-and-forward）型であり、要求に応じて中間サーバー（メールドロップ）から単一の宛先マシンにメールを移動します。

The online model is most commonly used with remote filesystem protocols such as NFS. In this model, a client application manipulates mailbox data on a server machine. A connection to the server is maintained throughout the session. No mailbox data are kept on the client; the client retrieves data from the server as is needed. IMAP4 introduces a form of the online model that requires considerably less network bandwidth than a remote filesystem protocol, and provides the opportunity for using the server for CPU or I/O intensive functions such as parsing and searching.

オンラインモデルは、NFSなどのリモートファイルシステムプロトコルでもっともよく使用されます。このモデルでは、クライアントアプリケーションがサーバーマシン上のメールボックスのデータを操作します。サーバーへの接続はセッションの間ずっと維持されます。クライアントにはメールボックスのデータを保持せず、クライアントは必要に応じてサーバーからデータを取得します。IMAP4は、リモートファイルシステムプロトコルよりもネットワーク帯域幅の必要量がかなり少ない形態のオンラインモデルを導入し、また、解析や検索などのCPUやI/Oを多く使う機能にサーバーを利用する機会を提供します。

The disconnected use model is a hybrid of the offline and online models, and is used by protocols such as PCMAIL (RFC 1056). In this model, a client user downloads some set of messages from the server, manipulates them offline, then at some later time uploads the changes. The server remains the authoritative repository of the messages. The problems of synchronization (particularly when multiple clients are involved) are handled through the means of unique identifiers for each message.

切断利用モデルは、オフラインモデルとオンラインモデルを組み合わせたもので、PCMAIL（RFC 1056）などのプロトコルで使用されています。このモデルでは、クライアントのユーザーがサーバーからいくつかのメッセージをダウンロードし、オフラインでそれらを操作し、その後のある時点で変更内容をアップロードします。サーバーは引き続きメッセージの正式な保管場所です。同期の問題（特に複数のクライアントが関与する場合）は、各メッセージの一意な識別子によって対処します。

Although IMAP4 has its origins as a protocol designed to accommodate the online model, it can support the other two models as well. This makes possible the creation of clients that can be used in any of the three models. For example, a user may wish to switch between the online and disconnected models on a regular basis (e.g. owing to travel).

IMAP4は、もともとオンラインモデルに対応するために設計されたプロトコルですが、他の2つのモデルもサポートできます。これにより、3つのモデルのどれでも使用できるクライアントを作成できます。たとえば、ユーザーは（出張などのために）オンラインモデルと切断利用モデルを定期的に切り替えたい場合があります。

IMAP4 is designed to transmit message data on demand, and to provide the facilities necessary for a client to decide what data it needs at any particular time. There is generally no need to do a wholesale transfer of an entire mailbox or even of the complete text of a message. This makes a difference in situations where the mailbox is large, or when the link to the server is slow.

IMAP4は、要求に応じてメッセージのデータを送信し、クライアントが特定の時点でどのデータを必要とするかを判断するのに必要な機能を提供するように設計されています。一般に、メールボックス全体や、メッセージの完全なテキストでさえ、一括して転送する必要はありません。このことは、メールボックスが大きい場合や、サーバーへのリンクが低速な場合に違いをもたらします。

More specifically, IMAP4 supports server-based RFC 822 and MIME processing. With this information, it is possible for a client to determine in advance whether it wishes to retrieve a particular message or part of a message. For example, a user connected to an IMAP4 server via a dialup link can determine that a message has a 2000 byte text segment and a 40 megabyte video segment, and elect to fetch only the text segment.

より具体的には、IMAP4は、サーバー側でのRFC 822とMIMEの処理をサポートしています。この情報を使用して、クライアントは、特定のメッセージやメッセージの一部を取得したいかどうかを事前に判断できます。たとえば、ダイヤルアップリンクを介してIMAP4サーバーに接続しているユーザーは、あるメッセージが2000バイトのテキスト部分と40メガバイトのビデオ部分を持っていることを確認し、テキスト部分だけを取得することを選べます。

In IMAP4, the client/server relationship lasts only for the duration of the TCP connection. There is no registration of clients. Except for any unique identifiers used in disconnected use operation, the client initially has no knowledge of mailbox state and learns it from the IMAP4 server when a mailbox is selected. This initial transfer is minimal; the client requests additional state data as it needs.

IMAP4では、クライアント／サーバーの関係はTCPコネクションが続いている間だけ持続します。クライアントの登録はありません。切断利用の操作で使用される一意な識別子を除いて、クライアントは最初はメールボックスの状態について何も知らず、メールボックスが選択されたときにIMAP4サーバーからそれを知ります。この最初の転送は最小限であり、クライアントは必要に応じて追加の状態データを要求します。

As noted above, the choice for the location of mailbox data depends upon the model chosen. The location of message state (e.g. whether or not a message has been read or answered) is also determined by the model, and is not necessarily the same as the location of the mailbox data. For example, in the online model message state can be co-located with mailbox data; it can also be located elsewhere (on the client or on a third agent) using unique identifiers to achieve common reference across sessions. The latter is particularly useful with a server that exports public data such as netnews and does not maintain per-user state.

上で述べたように、メールボックスのデータをどこに置くかは、選んだモデルによって決まります。メッセージの状態（たとえば、メッセージが既読か、返信済みか）をどこに置くかもモデルによって決まり、メールボックスのデータの場所と同じであるとは限りません。たとえば、オンラインモデルでは、メッセージの状態をメールボックスのデータと同じ場所に置くことができます。また、一意な識別子を使用してセッションをまたいで共通の参照を実現することで、別の場所（クライアントや第三のエージェント）に置くこともできます。後者は、ネットニュースのような公開データを提供し、ユーザーごとの状態を保持しないサーバーで特に有用です。

The IMAP4 protocol provides the generality to implement these different models. This is done by means of server and (especially) client configuration, and not by requiring changes to the protocol or the implementation of the protocol.

IMAP4プロトコルは、これらの異なるモデルを実装できる汎用性を備えています。これは、プロトコルやプロトコルの実装の変更を必要とするのではなく、サーバーと（特に）クライアントの設定によって実現されます。
