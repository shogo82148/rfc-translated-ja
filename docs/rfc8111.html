Locator/ID Separation Protocol Delegated Database Tree (LISP-DDT)

RFC 8111

ロケーター/ID分離プロトコルの委任データベースツリー（LISP-DDT）

Abstract

概要

This document describes the Locator/ID Separation Protocol Delegated Database Tree (LISP-DDT), a hierarchical distributed database that embodies the delegation of authority to provide mappings from LISP Endpoint Identifiers (EIDs) to Routing Locators (RLOCs). It is a statically defined distribution of the EID namespace among a set of LISP-speaking servers called "DDT nodes". Each DDT node is configured as "authoritative" for one or more EID-prefixes, along with the set of RLOCs for Map-Servers or "child" DDT nodes to which more-specific EID-prefixes are delegated.

この文書では、ロケーター/ID分離プロトコルの委任データベースツリー（Locator/ID Separation Protocol Delegated Database Tree、LISP-DDT）について説明します。これは、LISPのエンドポイントID（EID）からルーティングロケーター（RLOC）へのマッピングを提供する権限の委任を体現した、階層的な分散データベースです。これは、「DDTノード」と呼ばれる、LISPを話すサーバーの集合の間でEID名前空間を静的に定義して分散したものです。各DDTノードは、1つ以上のEID-prefixに対して「権威を持つ」ものとして設定され、あわせて、より詳細なEID-prefixの委任先であるMap-Serverまたは「子」DDTノードのRLOCのセットも設定されます。

1. Introduction

1. はじめに

The Locator/ID Separation Protocol (LISP) [RFC6830] specifies an architecture and mechanism for replacing the addresses currently used by IP with two separate namespaces:

ロケーター/ID分離プロトコル（LISP）[RFC6830]は、現在IPで使用されているアドレスを、2つの別々の名前空間で置き換えるためのアーキテクチャーとメカニズムを規定しています。

  • Endpoint Identifiers (EIDs), used end to end for terminating transport-layer associations, and
  • Routing Locators (RLOCs), which are bound to topological locations and are used for routing and forwarding through the Internet infrastructure.
  • エンドポイントID（Endpoint Identifier、EID）。トランスポート層のアソシエーションを終端するためにエンドツーエンドで使用されます。
  • ルーティングロケーター（Routing Locator、RLOC）。トポロジー上の位置に結び付けられ、インターネット基盤を通じたルーティングと転送に使用されます。

[RFC6833] specifies an interface between a database storing EID-to-RLOC mappings and LISP devices that need this information for packet forwarding. The internal organization of such a database is beyond the scope of [RFC6833]. Multiple architectures of the database have been proposed, each having its advantages and disadvantages (see, for example, [RFC6836] and [RFC6837]).

[RFC6833]は、EIDからRLOCへのマッピングを格納するデータベースと、パケット転送のためにこの情報を必要とするLISPデバイスとの間のインターフェイスを規定しています。そのようなデータベースの内部構成は、[RFC6833]の範囲外です。このデータベースのアーキテクチャーは複数提案されており、それぞれに長所と短所があります（たとえば、[RFC6836]と[RFC6837]を参照してください）。

This document specifies an architecture for a database of LISP EID-to-RLOC mappings, with an emphasis on high scalability. The LISP Delegated Database Tree (LISP-DDT) is a hierarchical distributed database that embodies the delegation of authority to provide mappings, i.e., its internal structure mirrors the hierarchical delegation of address space. It also provides delegation information to Map-Resolvers, which use the information to locate EID-to-RLOC mappings. A Map-Resolver that needs to locate a given mapping will follow a path through the tree-structured database and will contact, one after another, the DDT nodes along that path until it reaches the leaf DDT node(s) authoritative for the mapping it is seeking.

この文書は、高いスケーラビリティーに重点を置いた、LISPのEIDからRLOCへのマッピングのデータベースのアーキテクチャーを規定します。LISP委任データベースツリー（LISP-DDT）は、マッピングを提供する権限の委任を体現した階層的な分散データベースです。つまり、その内部構造はアドレス空間の階層的な委任を反映しています。また、LISP-DDTはMap-Resolverに委任情報を提供し、Map-Resolverはその情報を使用してEIDからRLOCへのマッピングの所在を突き止めます。あるマッピングの所在を突き止める必要があるMap-Resolverは、木構造のデータベースをたどる経路に沿って進み、探しているマッピングに対して権威を持つ葉のDDTノードに到達するまで、その経路上のDDTノードに次々と問い合わせます。

LISP offers a general-purpose mechanism for mapping between EIDs and RLOCs. In organizing a database of EID-to-RLOC mappings, this specification extends the definition of the EID numbering space by logically prepending and appending several fields for purposes of defining the database index key:

LISPは、EIDとRLOCの間のマッピングのための汎用的なメカニズムを提供します。この仕様は、EIDからRLOCへのマッピングのデータベースを構成するにあたり、データベースのインデックスキーを定義するために、いくつかのフィールドを論理的に前後に付加することによって、EIDの番号空間の定義を拡張します。

  • Database-ID (DBID) (16 bits),
  • Instance Identifier (IID) (32 bits),
  • Address Family Identifier (AFI) (16 bits), and
  • EID-prefix (variable, according to the AFI value).
  • データベースID（Database-ID、DBID）（16ビット）
  • インスタンス識別子（Instance Identifier、IID）（32ビット）
  • アドレスファミリー識別子（Address Family Identifier、AFI）（16ビット）
  • EID-prefix（AFIの値に応じた可変長）

The resulting concatenation of these fields is termed an "Extended EID-prefix", or XEID-prefix.

これらのフィールドを連結した結果を、「拡張EID-prefix（Extended EID-prefix）」またはXEID-prefixと呼びます。

LISP-DDT defines a new device type, the DDT node, that is configured as authoritative for one or more XEID-prefixes. It is also configured with the set of more-specific sub-prefixes that are further delegated to other DDT nodes. To delegate a sub-prefix, the "parent" DDT node is configured with the RLOCs of each child DDT node that is authoritative for the sub-prefix. Each RLOC either points to a DDT Map-Server (MS) to which an Egress Tunnel Router (ETR) has registered that sub-prefix or points to another DDT node in the database tree that further delegates the sub-prefix. See [RFC6833] for a description of the functionality of the Map-Server and Map-Resolver. Note that the target of a delegation must always be an RLOC (not an EID) to avoid any circular dependency.

LISP-DDTは、新しいデバイスタイプであるDDTノードを定義します。DDTノードは、1つ以上のXEID-prefixに対して権威を持つものとして設定されます。また、DDTノードには、さらにほかのDDTノードに委任される、より詳細なサブプレフィックスのセットも設定されます。サブプレフィックスを委任するために、「親」DDTノードには、そのサブプレフィックスに対して権威を持つ各子DDTノードのRLOCが設定されます。各RLOCは、出口トンネルルーター（ETR）がそのサブプレフィックスを登録したDDT Map-Server（MS）を指すか、そのサブプレフィックスをさらに委任するデータベースツリー内の別のDDTノードを指します。Map-ServerとMap-Resolverの機能の説明については、[RFC6833]を参照してください。循環的な依存関係を避けるために、委任の対象は常に（EIDではなく）RLOCでなければならないことに注意してください。

To provide a mechanism for traversing the database tree, LISP-DDT defines a new LISP message type, the Map-Referral, which is returned to the sender of a Map-Request when the receiving DDT node can refer the sender to another DDT node that has more detailed information. See Section 6 for the definition of the Map-Referral message.

データベースツリーをたどるメカニズムを提供するために、LISP-DDTは新しいLISPメッセージタイプであるMap-Referralを定義します。Map-Referralは、Map-Requestを受信したDDTノードが、より詳しい情報を持つ別のDDTノードを送信者に紹介できる場合に、Map-Requestの送信者に返されます。Map-Referralメッセージの定義については、セクション6を参照してください。

To find an EID-to-RLOC mapping, a LISP-DDT client, usually a DDT Map-Resolver, starts by sending an Encapsulated Map-Request to a preconfigured DDT node RLOC. The DDT node responds with a Map-Referral message indicating that either (1) it will find the requested mapping to complete processing of the request or (2) the DDT client should contact another DDT node that has more-specific information; in the latter case, the DDT node then sends a new Encapsulated Map-Request to the next DDT node and the process repeats in an iterative manner.

EIDからRLOCへのマッピングを見つけるために、LISP-DDTクライアント（通常はDDT Map-Resolver）は、事前に設定されたDDTノードのRLOCにカプセル化されたMap-Requestを送信することから始めます。DDTノードは、（1）リクエストの処理を完了するために、リクエストされたマッピングを自身が見つけること、または（2）DDTクライアントがより詳細な情報を持つ別のDDTノードに問い合わせるべきであること、のいずれかを示すMap-Referralメッセージで応答します。後者の場合、DDTノードは次のDDTノードに新しいカプセル化されたMap-Requestを送信し、この処理が反復的に繰り返されます。

Conceptually, this is similar to the way that a client of the Domain Name System (DNS) follows referrals (DNS responses that contain only NS records) from a series of DNS servers until it finds an answer.

概念的には、これは、ドメインネームシステム（DNS）のクライアントが、答えを見つけるまで一連のDNSサーバーからのリファラル（NSレコードのみを含むDNSレスポンス）をたどる方法に似ています。

3. Definitions of Terms

3. 用語の定義

Extended EID (XEID):
a LISP EID extended with data uniquely identifying the address space to which it belongs (LISP IID, address family, etc.). See Section 4.1 for a detailed description of XEID data.
Extended EID-prefix (XEID-prefix):
a LISP EID-prefix prepended with XEID data. An XEID-prefix is used as a key index into the DDT database. XEID-prefixes are used to describe database organization and are not seen as a single entity in protocol messages, though messages contain individual fields constituting XEID-prefixes.
DDT node:
a network infrastructure component responsible for specific XEID-prefix(es) and for the delegation of more-specific sub-prefixes to other DDT nodes.
DDT client:
a network infrastructure component that sends DDT Map-Request messages and implements the iterative following of Map-Referral results. Typically, a DDT client will be a Map-Resolver (as defined by [RFC6833]), but it is also possible for an Ingress Tunnel Router (ITR) to implement DDT client functionality.
DDT Map-Server:
a DDT node that also implements Map-Server functionality (forwarding Map-Requests and/or returning Map-Replies if offering a proxy Map-Reply service) for a subset of its delegated prefixes. Map-Server functions, including proxying Map-Replies, are described in [RFC6833].
DDT Map-Server peers:
a list of all DDT Map-Servers performing Map-Server functionality for the same prefix. If peers are configured on a DDT Map-Server, then the latter will provide complete information about the prefix in its Map-Replies; otherwise, the Map-Server will mark the returned reply as potentially incomplete.
DDT Map-Resolver:
a network infrastructure element that implements both DDT client functionality and Map-Resolver functionality as defined by [RFC6833]. A DDT Map-Resolver accepts Map-Requests from ITRs, sends DDT Map-Requests to DDT nodes, and implements the iterative following of Map-Referrals. Note that Map-Resolvers do not respond to clients that sent Map-Requests; they only ensure that the Map-Request has been forwarded to a LISP device (ETR or proxy Map-Server) that will provide an authoritative response to the original requester. A DDT Map-Resolver will typically maintain a cache (termed the "referral cache") of previously received Map-Referral message results containing RLOCs for DDT nodes responsible for XEID-prefixes of interest.
Encapsulated Map-Request:
a LISP Map-Request that is carried within an Encapsulated Control Message and that has an additional LISP header prepended to it. Sent to UDP destination port 4342. The "outer" addresses are globally routable IP addresses, also known as RLOCs. Used by an ITR when sending a Map-Request to a Map-Resolver and by a Map-Server when forwarding a Map-Request to an ETR as documented in [RFC6833].
DDT Map-Request:
an Encapsulated Map-Request sent by a DDT client to a DDT node. The "DDT-originated" flag is set in the encapsulation header, indicating that the DDT node should return Map-Referral messages if the Map-Request EID matches a delegated XEID-prefix known to the DDT node. Section 7.3.1 describes how DDT Map-Requests are sent. Section 5 defines the position of the "DDT-originated" flag in the Encapsulated Control Message header.
Authoritative XEID-prefix:
an XEID-prefix delegated to a DDT node and for which the DDT node may provide further delegations of more-specific sub-prefixes.
Map-Referral:
a LISP message sent by a DDT node in response to a DDT Map-Request for an XEID that matches a configured XEID-prefix delegation. A non-Negative Map-Referral includes a "referral" -- a set of RLOCs for DDT nodes that have information about the more-specific XEID-prefix covering the requested XEID; a DDT client "follows the referral" by sending another DDT Map-Request to one of those RLOCs to obtain either an answer or another referral to DDT nodes responsible for an XEID-prefix that is even more specific. See Sections 7.1 and 7.3.2 for details on the sending and processing of Map-Referral messages.
Negative Map-Referral:
an answer from an authoritative DDT node that there is no mapping for the requested XEID. A Negative Map-Referral is a Map-Referral sent in response to a DDT Map-Request that matches an authoritative XEID-prefix but for which there is no delegation configured (or no ETR registration, if sent by a DDT Map-Server).
Pending Request List:
the set of outstanding requests for which a DDT Map-Resolver has received Encapsulated Map-Requests from its clients seeking EID-to-RLOC mapping for an XEID. Each entry in the list contains additional state needed by the referral-following process, including the XEID, requester(s) of the XEID (typically one or more ITRs), saved information about the last referral received and followed (matching XEID-prefix, action code, RLOC set, index of the last RLOC queried in the RLOC set), and any LISP-Security (LISP-SEC) information [LISP-SEC] that was included in the DDT client Map-Request. An entry in the list may be interchangeably termed a "pending request list entry" or simply a "pending request".
拡張EID（Extended EID、XEID）：
LISPのEIDを、それが属するアドレス空間を一意に識別するデータ（LISPのIID、アドレスファミリーなど）で拡張したものです。XEIDのデータの詳しい説明については、セクション4.1を参照してください。
拡張EID-prefix（Extended EID-prefix、XEID-prefix）：
LISPのEID-prefixの先頭にXEIDのデータを付加したものです。XEID-prefixは、DDTデータベースへのキーインデックスとして使用されます。XEID-prefixはデータベースの構成を説明するために使用されるものであり、プロトコルメッセージ内で単一の実体として現れることはありません。ただし、メッセージには、XEID-prefixを構成する個々のフィールドが含まれます。
DDTノード（DDT node）：
特定のXEID-prefixと、より詳細なサブプレフィックスのほかのDDTノードへの委任とを担当する、ネットワーク基盤コンポーネントです。
DDTクライアント（DDT client）：
DDT Map-Requestメッセージを送信し、Map-Referralの結果を反復的にたどる処理を実装するネットワーク基盤コンポーネントです。通常、DDTクライアントは（[RFC6833]で定義される）Map-Resolverですが、入口トンネルルーター（ITR）がDDTクライアントの機能を実装することもできます。
DDT Map-Server：
委任されたプレフィックスのサブセットに対して、Map-Serverの機能（Map-Requestの転送と、プロキシーMap-Replyサービスを提供している場合はMap-Replyの返送の一方または両方）も実装するDDTノードです。Map-Replyのプロキシーを含むMap-Serverの機能は、[RFC6833]で説明されています。
DDT Map-Serverピア（DDT Map-Server peers）：
同じプレフィックスに対してMap-Serverの機能を実行するすべてのDDT Map-Serverのリストです。DDT Map-Serverにピアが設定されている場合、そのDDT Map-Serverは、自身のMap-Replyでそのプレフィックスに関する完全な情報を提供します。そうでない場合、そのMap-Serverは、返すリプライを不完全な可能性があるものとしてマークします。
DDT Map-Resolver：
DDTクライアントの機能と、[RFC6833]で定義されるMap-Resolverの機能の両方を実装するネットワーク基盤要素です。DDT Map-Resolverは、ITRからMap-Requestを受け付け、DDTノードにDDT Map-Requestを送信し、Map-Referralを反復的にたどる処理を実装します。Map-Resolverは、Map-Requestを送信したクライアントに応答しないことに注意してください。Map-Resolverは、元のリクエスターに権威あるレスポンスを提供するLISPデバイス（ETRまたはプロキシーMap-Server）にMap-Requestが転送されたことを保証するだけです。DDT Map-Resolverは通常、関心のあるXEID-prefixを担当するDDTノードのRLOCを含む、以前に受信したMap-Referralメッセージの結果のキャッシュ（「リファラルキャッシュ（referral cache）」と呼びます）を保持します。
カプセル化されたMap-Request（Encapsulated Map-Request）：
カプセル化制御メッセージ（Encapsulated Control Message）内で運ばれ、追加のLISPヘッダーが先頭に付加されたLISPのMap-Requestです。UDP宛先ポート4342に送信されます。「外側」のアドレスはグローバルにルーティング可能なIPアドレスであり、RLOCとも呼ばれます。[RFC6833]に記載されているように、ITRがMap-ResolverにMap-Requestを送信する際や、Map-ServerがETRにMap-Requestを転送する際に使用されます。
DDT Map-Request：
DDTクライアントがDDTノードに送信するカプセル化されたMap-Requestです。カプセル化ヘッダーには「DDT-originated」フラグが設定されており、Map-RequestのEIDが、DDTノードが知っている委任されたXEID-prefixに一致する場合には、DDTノードがMap-Referralメッセージを返すべきであることを示します。DDT Map-Requestの送信方法はセクション7.3.1で説明します。カプセル化制御メッセージのヘッダー内での「DDT-originated」フラグの位置は、セクション5で定義します。
権威XEID-prefix（Authoritative XEID-prefix）：
DDTノードに委任されたXEID-prefixであり、そのDDTノードがより詳細なサブプレフィックスのさらなる委任を提供できるものです。
Map-Referral：
設定されたXEID-prefixの委任に一致するXEIDについてのDDT Map-Requestへのレスポンスとして、DDTノードが送信するLISPメッセージです。ネガティブでないMap-Referralには「リファラル」、すなわち、リクエストされたXEIDをカバーする、より詳細なXEID-prefixについての情報を持つDDTノードのRLOCのセットが含まれます。DDTクライアントは、答えか、さらに詳細なXEID-prefixを担当するDDTノードへの別のリファラルのいずれかを得るために、それらのRLOCの1つに別のDDT Map-Requestを送信することによって「リファラルをたどり」ます。Map-Referralメッセージの送信と処理の詳細については、セクション7.1と7.3.2を参照してください。
ネガティブMap-Referral（Negative Map-Referral）：
リクエストされたXEIDに対するマッピングが存在しないという、権威を持つDDTノードからの答えです。ネガティブMap-Referralは、権威XEID-prefixに一致するが、委任が設定されていない（DDT Map-Serverが送信する場合は、ETRの登録がない）DDT Map-Requestへのレスポンスとして送信されるMap-Referralです。
保留中リクエストリスト（Pending Request List）：
DDT Map-Resolverが、XEIDについてのEIDからRLOCへのマッピングを求めるカプセル化されたMap-Requestをクライアントから受信した、未解決のリクエストの集合です。リスト内の各エントリーには、リファラルをたどる処理に必要な追加の状態が含まれます。これには、XEID、そのXEIDのリクエスター（通常は1つ以上のITR）、最後に受信してたどったリファラルについて保存された情報（一致したXEID-prefix、アクションコード、RLOCセット、RLOCセット内で最後に問い合わせたRLOCのインデックス）、およびDDTクライアントのMap-Requestに含まれていたLISPセキュリティー（LISP-SEC）の情報[LISP-SEC]があればそれも含まれます。リスト内のエントリーは、「保留中リクエストリストのエントリー（pending request list entry）」、または単に「保留中のリクエスト（pending request）」と呼ぶこともあります。

For definitions of other terms -- notably Map-Request, Map-Reply, ITR, ETR, Map-Server, and Map-Resolver -- please consult the LISP specification [RFC6830] and the LISP Mapping Service specification [RFC6833].

その他の用語、特にMap-Request、Map-Reply、ITR、ETR、Map-Server、Map-Resolverの定義については、LISPの仕様[RFC6830]とLISPマッピングサービスの仕様[RFC6833]を参照してください。

4. Database Organization

4. データベースの構成

4.1. XEID-Prefixes

4.1. XEID-prefix

A DDT database is indexed by Extended EID-prefixes (XEID-prefixes). An XEID-prefix is a LISP EID-prefix, together with data extending it to uniquely identify the address space of the prefix. An XEID-prefix is composed of four binary-encoded fields, ordered by significance: DBID (16 bits), IID (32 bits), AFI (16 bits), and EID-prefix (variable, according to the AFI value). The fields are concatenated, with the most significant fields as listed above.

DDTデータベースは、拡張EID-prefix（XEID-prefix）によってインデックス付けされます。XEID-prefixは、LISPのEID-prefixに、そのプレフィックスのアドレス空間を一意に識別するために拡張するデータを加えたものです。XEID-prefixは、バイナリーでエンコードされた4つのフィールドで構成され、重要度の順に、DBID（16ビット）、IID（32ビット）、AFI（16ビット）、EID-prefix（AFIの値に応じた可変長）と並びます。これらのフィールドは、上に挙げたとおり最も重要なフィールドを上位にして連結されます。

The DBID is the LISP-DDT Database-ID, a 16-bit field provided to allow the definition of multiple databases. Implementations that are compliant with this document must always set this field to 0. Other values of the DBID are reserved for future use.

DBIDはLISP-DDTのデータベースIDであり、複数のデータベースを定義できるようにするために用意された16ビットのフィールドです。この文書に準拠する実装は、このフィールドを常に0に設定しなければなりません。DBIDのその他の値は、将来の使用のために予約されています。

The Instance ID (IID) is a 32-bit value describing the context of the EID-prefix, if the latter is intended for use in an environment where addresses may not be unique, such as in a Virtual Private Network where the [RFC1918] address space is used. See Section 5.5 of [RFC6830] for more discussion of IIDs. Encoding of the IID is specified by [RFC8060].

インスタンスID（IID）は、EID-prefixのコンテキストを記述する32ビットの値であり、EID-prefixが、[RFC1918]のアドレス空間が使用される仮想プライベートネットワークのように、アドレスが一意でない可能性がある環境での使用を意図している場合に用います。IIDについての詳しい議論は、[RFC6830]のセクション5.5を参照してください。IIDのエンコーディングは[RFC8060]で規定されています。

The AFI is a 16-bit value defining the syntax of the EID-prefix. AFI values are assigned by IANA [AFI].

AFIは、EID-prefixの構文を定義する16ビットの値です。AFIの値はIANAによって割り当てられます[AFI]。

4.2. Structure of the DDT Database

4.2. DDTデータベースの構造

The LISP-DDT database for each DDT node is organized as a tree structure that is indexed by XEID-prefixes. Leaves of the database tree describe the delegation of authority between DDT nodes (see Section 4.3 for details regarding delegation and information kept in the database entries).

各DDTノードのLISP-DDTデータベースは、XEID-prefixによってインデックス付けされた木構造として構成されます。データベースツリーの葉は、DDTノード間の権限の委任を記述します（委任とデータベースエントリーに保持される情報の詳細については、セクション4.3を参照してください）。

DDT Map-Requests sent by the DDT client to DDT nodes always contain specific values for the DBID, IID, and AFI; unspecified values or ranges of values are never used for any of these fields. Thus, an XEID-prefix used as a key for searches in the database tree will have a length of at least 64 bits.

DDTクライアントがDDTノードに送信するDDT Map-Requestには、常にDBID、IID、AFIの特定の値が含まれます。これらのフィールドのいずれにも、指定されていない値や値の範囲が使用されることはありません。したがって、データベースツリー内での検索のキーとして使用されるXEID-prefixは、少なくとも64ビットの長さを持ちます。

A DDT node may, for example, be authoritative for a consecutive range of 3-tuples (DBID, IID, AFI) and all associated EID-prefixes, or only for a specific EID-prefix of a single 3-tuple. Thus, XEID-prefixes/keys of the database tree leaves may have lengths less than, equal to, or more than 64 bits.

たとえば、DDTノードは、3つ組（DBID、IID、AFI）の連続する範囲とそれに関連付けられたすべてのEID-prefixに対して権威を持つ場合もあれば、単一の3つ組の特定のEID-prefixに対してのみ権威を持つ場合もあります。したがって、データベースツリーの葉のXEID-prefix/キーは、64ビット未満、64ビットちょうど、または64ビットを超える長さを持つ場合があります。

It is important to note that LISP-DDT does not store actual EID-to-RLOC mappings; it is, rather, a distributed index that can be used to find the devices (ETRs that registered their EIDs with DDT Map-Servers) that can be queried with LISP to obtain those mappings. Changes to EID-to-RLOC mappings are made on the ETRs that define them, not to any DDT node configuration. DDT node configuration changes are only required when branches of the database hierarchy are added, removed, or modified.

LISP-DDTは実際のEIDからRLOCへのマッピングを格納しないことに注意することが重要です。LISP-DDTはむしろ、それらのマッピングを得るためにLISPで問い合わせることができるデバイス（DDT Map-Serverに自身のEIDを登録したETR）を見つけるために使用できる分散インデックスです。EIDからRLOCへのマッピングの変更は、それを定義するETR上で行われ、DDTノードの設定に対しては行われません。DDTノードの設定の変更が必要になるのは、データベース階層の枝が追加、削除、または変更される場合だけです。

4.3. Configuring Prefix Delegation

4.3. プレフィックスの委任の設定

Every DDT node is configured with one or more XEID-prefixes for which it is authoritative, along with a list of delegations of XEID-prefixes to other DDT nodes. A DDT node is required to maintain a list of delegations for all sub-prefixes of its authoritative XEID-prefixes; it also may list "hints", which are prefixes that it knows about that belong to its parents, to the root, or to any other point in the XEID-prefix hierarchy. A delegation (or hint) consists of an XEID-prefix, a set of RLOCs for DDT nodes that have more detailed knowledge of the XEID-prefix, and accompanying security information (for details regarding security information exchange and its use, see Section 10). Those RLOCs are returned in Map-Referral messages when the DDT node receives a DDT Map-Request with an XEID that matches a delegation. A DDT Map-Server will also have a set of sub-prefixes for which it accepts ETR mapping registrations and for which it will forward (or answer, if it provides a proxy Map-Reply service) Map-Requests.

すべてのDDTノードには、自身が権威を持つ1つ以上のXEID-prefixと、ほかのDDTノードへのXEID-prefixの委任のリストが設定されます。DDTノードは、自身が権威を持つXEID-prefixのすべてのサブプレフィックスについて、委任のリストを保持することが求められます。また、DDTノードは「ヒント」を列挙してもかまいません。ヒントとは、そのDDTノードが知っている、親、ルート、またはXEID-prefix階層内のその他の任意の地点に属するプレフィックスです。委任（またはヒント）は、XEID-prefix、そのXEID-prefixについてより詳しい知識を持つDDTノードのRLOCのセット、および付随するセキュリティー情報（セキュリティー情報の交換とその使用の詳細については、セクション10を参照してください）で構成されます。これらのRLOCは、委任に一致するXEIDを含むDDT Map-RequestをDDTノードが受信したときに、Map-Referralメッセージで返されます。DDT Map-Serverは、ETRのマッピング登録を受け付け、Map-Requestを転送する（または、プロキシーMap-Replyサービスを提供している場合は応答する）サブプレフィックスのセットも持ちます。

One or more XEID-prefixes for which a DDT node is authoritative, and the delegation of authority for sub-prefixes, are provided as part of the configuration of the DDT node. Implementations will likely develop a language to express this prefix authority and delegation. Since DDT configuration is static (i.e., not exchanged between DDT nodes as part of the protocol itself), such language is implementation dependent and is outside the scope of this specification.

DDTノードが権威を持つ1つ以上のXEID-prefixと、サブプレフィックスについての権限の委任は、DDTノードの設定の一部として提供されます。実装は、このプレフィックスの権限と委任を表現するための言語を開発することになるでしょう。DDTの設定は静的である（つまり、プロトコル自体の一部としてDDTノード間で交換されない）ため、そのような言語は実装依存であり、この仕様の範囲外です。

4.3.1. The Root DDT Node

4.3.1. ルートDDTノード

The root DDT node is the logical "top" of the distributed database hierarchy. It is authoritative for all XEID-prefixes -- that is, for all valid 3-tuples (DBID, IID, AFI) and their EID-prefixes. A DDT Map-Request that matches no configured XEID-prefix will be referred to the root node (see Section 8 for a formal description of conditions where a DDT Map-Request is forwarded to the root node). The root node in a particular instantiation of LISP-DDT therefore MUST be configured, at a minimum, with delegations for all defined IIDs and AFIs.

ルートDDTノードは、分散データベース階層の論理的な「頂点」です。ルートDDTノードは、すべてのXEID-prefix、つまり、すべての有効な3つ組（DBID、IID、AFI）とそれらのEID-prefixに対して権威を持ちます。設定されたどのXEID-prefixにも一致しないDDT Map-Requestは、ルートノードに紹介されます（DDT Map-Requestがルートノードに転送される条件の形式的な説明については、セクション8を参照してください）。したがって、LISP-DDTの特定のインスタンス化におけるルートノードには、少なくとも、定義されたすべてのIIDとAFIについての委任を設定しなければなりません（MUST）。

6. The Map-Referral Message

6. Map-Referralメッセージ

This specification defines a new LISP message called the Map-Referral message. A Map-Referral message is sent by a DDT node to a DDT client in response to a DDT Map-Request message. See Section 6.4 for a detailed layout of the Map-Referral message fields.

この仕様は、Map-Referralメッセージと呼ばれる新しいLISPメッセージを定義します。Map-Referralメッセージは、DDT Map-Requestメッセージへのレスポンスとして、DDTノードからDDTクライアントに送信されます。Map-Referralメッセージのフィールドの詳しいレイアウトについては、セクション6.4を参照してください。

The message consists of an action code along with delegation information about the XEID-prefix that matches the requested XEID.

このメッセージは、アクションコードと、リクエストされたXEIDに一致するXEID-prefixについての委任情報で構成されます。

6.1. Action Codes

6.1. アクションコード

The action codes are as follows:

アクションコードは次のとおりです。

NODE-REFERRAL (0):
indicates that the replying DDT node has delegated an XEID-prefix that matches the requested XEID to one or more other DDT nodes. The Map-Referral message contains a "map-record" with additional information -- most significantly, the set of RLOCs to which the prefix has been delegated -- that is used by a DDT client to "follow" the referral.
MS-REFERRAL (1):
indicates that the replying DDT node has delegated an XEID-prefix that matches the requested XEID to one or more DDT Map-Servers. It contains the same additional information as a NODE-REFERRAL but is handled slightly differently by the receiving DDT client (see Section 7.3.2).
MS-ACK (2):
indicates that the replying DDT Map-Server received a DDT Map-Request that matches an authoritative XEID-prefix for which it has one or more registered ETRs. This means that the request has been forwarded to one of those ETRs to provide an answer to the querying ITR.
MS-NOT-REGISTERED (3):
indicates that the replying DDT Map-Server received a Map-Request for one of its configured XEID-prefixes that has no ETRs registered.
DELEGATION-HOLE (4):
indicates that the requested XEID matches a non-delegated sub-prefix of the XEID space. This is a non-LISP "hole", which has not been delegated to any DDT Map-Server or ETR. See Section 7.1.2 for details. Also sent by a DDT Map-Server with authoritative configuration covering the requested EID but for which no specific site ETR is configured.
NOT-AUTHORITATIVE (5):
indicates that the replying DDT node received a Map-Request for an XEID for which it is not authoritative and has no configured matching hint referrals. This can occur if a cached referral has become invalid due to a change in the database hierarchy. However, if such a DDT node has a "hint" delegation covering the requested EID, it MAY choose to return NODE-REFERRAL or MS-REFERRAL as appropriate. When returning action code NOT-AUTHORITATIVE, the DDT node MUST provide the EID-prefix received in the request and the TTL MUST be set to 0.
NODE-REFERRAL (0):
応答するDDTノードが、リクエストされたXEIDに一致するXEID-prefixを、ほかの1つ以上のDDTノードに委任していることを示します。Map-Referralメッセージには、追加の情報を持つ「マップレコード（map-record）」が含まれます。この追加の情報のうち最も重要なのは、そのプレフィックスの委任先のRLOCのセットであり、DDTクライアントがリファラルを「たどる」ために使用します。
MS-REFERRAL (1):
応答するDDTノードが、リクエストされたXEIDに一致するXEID-prefixを、1つ以上のDDT Map-Serverに委任していることを示します。NODE-REFERRALと同じ追加の情報を含みますが、受信したDDTクライアントでの扱いがわずかに異なります（セクション7.3.2を参照してください）。
MS-ACK (2):
応答するDDT Map-Serverが、権威を持つXEID-prefixのうち、1つ以上の登録済みのETRを持つものに一致するDDT Map-Requestを受信したことを示します。これは、問い合わせ元のITRに答えを提供するために、そのリクエストがそれらのETRの1つに転送されたことを意味します。
MS-NOT-REGISTERED (3):
応答するDDT Map-Serverが、自身に設定されたXEID-prefixのうち、ETRが登録されていないものについてのMap-Requestを受信したことを示します。
DELEGATION-HOLE (4):
リクエストされたXEIDが、XEID空間の委任されていないサブプレフィックスに一致することを示します。これは、どのDDT Map-ServerにもETRにも委任されていない、非LISPの「穴（hole）」です。詳細はセクション7.1.2を参照してください。また、リクエストされたEIDをカバーする権威を持つ設定がありながら、特定のサイトのETRが設定されていないDDT Map-Serverも、このアクションコードを送信します。
NOT-AUTHORITATIVE (5):
応答するDDTノードが、自身が権威を持たず、一致するヒントのリファラルも設定されていないXEIDについてのMap-Requestを受信したことを示します。これは、データベース階層の変更によって、キャッシュされたリファラルが無効になった場合に起こることがあります。ただし、そのようなDDTノードが、リクエストされたEIDをカバーする「ヒント」の委任を持っている場合は、必要に応じてNODE-REFERRALまたはMS-REFERRALを返すことを選択してもよいです（MAY）。アクションコードNOT-AUTHORITATIVEを返す場合、DDTノードは、リクエストで受信したEID-prefixを提供しなければなりません（MUST）。また、TTLは0に設定しなければなりません（MUST）。

6.2. Referral Set

6.2. リファラルセット

For "positive" action codes (NODE-REFERRAL, MS-REFERRAL, MS-ACK), a DDT node MUST include in the Map-Referral message a list of RLOCs for DDT nodes that are authoritative for the XEID-prefix being returned; a DDT client uses this information to contact one of those DDT nodes as it "follows" a referral.

「肯定的」なアクションコード（NODE-REFERRAL、MS-REFERRAL、MS-ACK）の場合、DDTノードは、返すXEID-prefixに対して権威を持つDDTノードのRLOCのリストをMap-Referralメッセージに含めなければなりません（MUST）。DDTクライアントは、リファラルを「たどる」際に、この情報を使用してそれらのDDTノードの1つに問い合わせます。

6.3. "Incomplete" Flag

6.3. 「Incomplete」フラグ

A DDT node sets the "Incomplete" flag in a Map-Referral message if the Referral Set is incomplete; this is intended to prevent a DDT client from caching a referral with incomplete information. A DDT node MUST set the "Incomplete" flag in the following cases:

DDTノードは、リファラルセットが不完全な場合に、Map-Referralメッセージに「Incomplete」フラグを設定します。これは、不完全な情報を持つリファラルをDDTクライアントがキャッシュしないようにすることを目的としています。DDTノードは、次の場合に「Incomplete」フラグを設定しなければなりません（MUST）。

  • If it is setting action code MS-ACK or MS-NOT-REGISTERED but the matching XEID-prefix is not flagged as "complete" in the configuration. The XEID-prefix configuration on the DDT Map-Server SHOULD be marked as "complete" when the configuration of the XEID-prefix lists all "peer" DDT nodes that are also authoritative for the same XEID-prefix or when it is known that a local DDT node is the only authoritative node for the XEID-prefix.
  • If it is setting action code NOT-AUTHORITATIVE.
  • アクションコードMS-ACKまたはMS-NOT-REGISTEREDを設定するが、一致するXEID-prefixが設定で「complete」としてフラグ付けされていない場合。XEID-prefixの設定に、同じXEID-prefixに対してやはり権威を持つすべての「ピア」DDTノードが列挙されている場合、またはローカルのDDTノードがそのXEID-prefixに対して権威を持つ唯一のノードであることがわかっている場合には、DDT Map-Server上のそのXEID-prefixの設定を「complete」としてマークすべきです（SHOULD）。
  • アクションコードNOT-AUTHORITATIVEを設定する場合。

7. DDT Network Elements and Their Operation

7. DDTのネットワーク要素とその動作

As described above, LISP-DDT introduces a new network element -- the DDT node -- and extends the functionality of Map-Servers and Map-Resolvers to send and receive Map-Referral messages. The operation of each of these devices is described below.

上で説明したように、LISP-DDTは新しいネットワーク要素であるDDTノードを導入し、Map-ServerとMap-Resolverの機能を拡張して、Map-Referralメッセージを送受信するようにします。これらの各デバイスの動作を以下で説明します。

7.1. DDT Node

7.1. DDTノード

When a DDT node receives a DDT Map-Request, it compares the requested XEID against its list of XEID-prefix delegations and its list of authoritative XEID-prefixes, and proceeds as follows:

DDTノードは、DDT Map-Requestを受信すると、リクエストされたXEIDを、自身のXEID-prefixの委任のリストと権威を持つXEID-prefixのリストと比較し、次のように処理を進めます。

7.1.1. Matching of a Delegated Prefix (or Sub-prefix)

7.1.1. 委任されたプレフィックス（またはサブプレフィックス）との一致

If the requested XEID matches one of the DDT node's delegated prefixes, then a Map-Referral message is returned with the matching more-specific XEID-prefix and the set of RLOCs for the referral target DDT nodes, including associated security information (see Section 10 for details on security). If at least one DDT node of the delegation is known to be a DDT Map-Server, then the Map-Referral message SHOULD be sent with action code MS-REFERRAL to indicate to the receiver that LISP-SEC information (if saved in the pending request) SHOULD be included in the next DDT Map-Request; otherwise, the action code NODE-REFERRAL SHOULD be used.

リクエストされたXEIDがDDTノードの委任されたプレフィックスの1つに一致する場合、一致したより詳細なXEID-prefixと、リファラル先のDDTノードのRLOCのセットを、関連するセキュリティー情報（セキュリティーの詳細についてはセクション10を参照してください）とともに含むMap-Referralメッセージが返されます。委任先のDDTノードのうち少なくとも1つがDDT Map-Serverであることがわかっている場合、（保留中のリクエストに保存されていれば）LISP-SECの情報を次のDDT Map-Requestに含めるべきです（SHOULD）ということを受信者に示すために、Map-ReferralメッセージはアクションコードMS-REFERRALで送信すべきです（SHOULD）。そうでない場合は、アクションコードNODE-REFERRALを使用すべきです（SHOULD）。

Note that a matched delegation does not have to be for a sub-prefix of an authoritative prefix; in addition to being configured to delegate sub-prefixes of an authoritative prefix, a DDT node may also be configured with other XEID-prefixes for which it can provide referrals to DDT nodes anywhere in the database hierarchy. This capability to define "shortcut hints" is never required to be configured, but it may be a useful heuristic for reducing the number of iterations needed to find an EID, particularly for private network deployments.

一致した委任は、権威を持つプレフィックスのサブプレフィックスについてのものである必要はないことに注意してください。DDTノードには、権威を持つプレフィックスのサブプレフィックスを委任するよう設定されるだけでなく、データベース階層内の任意の場所にあるDDTノードへのリファラルを提供できるほかのXEID-prefixを設定することもできます。この「ショートカットヒント」を定義する能力は、設定することが求められることは決してありませんが、特にプライベートネットワークでの展開において、EIDを見つけるのに必要な反復の回数を減らすための有用な発見的手法となる場合があります。

Referral hints, if used properly, may reduce the number of referrals a DDT client needs to follow to locate a DDT Map-Server authoritative for the XEID-prefix being resolved. On the other hand, the incorrect use of hints may create circular dependencies (or "referral loops") between DDT nodes. A DDT client MUST be prepared to handle such circular referrals. See Section 7.3.4 for a discussion of referral loops and measures that the DDT client must implement in order to detect circular referrals and prevent infinite looping.

リファラルのヒントは、適切に使用すれば、解決しようとしているXEID-prefixに対して権威を持つDDT Map-Serverを見つけるためにDDTクライアントがたどる必要のあるリファラルの数を減らせる場合があります。一方で、ヒントを誤って使用すると、DDTノード間に循環的な依存関係（または「リファラルループ」）が生じる場合があります。DDTクライアントは、そのような循環的なリファラルを扱えるように準備しなければなりません（MUST）。リファラルループと、循環的なリファラルを検出して無限ループを防ぐためにDDTクライアントが実装しなければならない対策についての議論は、セクション7.3.4を参照してください。

Another danger related to the use of hints is when a DDT deployment spans multiple administrative domains (i.e., different authorities manage DDT nodes in the same DDT database). In this case, an operator managing a DDT node may not be aware of the fact that the node is being referred to by hints. Locator addresses in hints may become stale when referred DDT nodes are taken out of service or change their locator addresses.

ヒントの使用に関連するもう1つの危険は、DDTの展開が複数の管理ドメインにまたがる場合（つまり、同じDDTデータベース内のDDTノードを異なる組織が管理する場合）です。この場合、DDTノードを管理する運用者は、そのノードがヒントによって参照されているという事実に気付かない可能性があります。参照されているDDTノードが運用を停止したり、ロケーターアドレスを変更したりすると、ヒント内のロケーターアドレスが古くなる可能性があります。

7.1.2. Missing Delegation from an Authoritative Prefix

7.1.2. 権威を持つプレフィックスからの委任の欠落

If the requested XEID did not match a configured delegation but does match an authoritative XEID-prefix, then the DDT node MUST return a Negative Map-Referral that uses the least-specific XEID-prefix that does not match any XEID-prefix delegated by the DDT node. The action code is set to DELEGATION-HOLE; this indicates that the XEID is not a LISP destination.

リクエストされたXEIDが、設定された委任には一致しなかったが、権威を持つXEID-prefixには一致する場合、DDTノードは、そのDDTノードが委任したどのXEID-prefixにも一致しない、最も詳細度の低いXEID-prefixを使用したネガティブMap-Referralを返さなければなりません（MUST）。アクションコードはDELEGATION-HOLEに設定されます。これは、そのXEIDがLISPの宛先ではないことを示します。

If the requested XEID did not match either a configured delegation, an authoritative XEID-prefix, or a hint, then a Negative Map-Referral with action code NOT-AUTHORITATIVE MUST be returned.

リクエストされたXEIDが、設定された委任、権威を持つXEID-prefix、ヒントのいずれにも一致しなかった場合、アクションコードNOT-AUTHORITATIVEを持つネガティブMap-Referralを返さなければなりません（MUST）。

7.2. DDT Map-Server

7.2. DDT Map-Server

When a DDT Map-Server receives a DDT Map-Request, its operation is similar to that of a DDT node, with additional processing as follows:

DDT Map-ServerがDDT Map-Requestを受信した場合、その動作はDDTノードと同様ですが、次の追加の処理を行います。

  • If the requested XEID matches a registered XEID-prefix, then the Map-Request is forwarded to one of the destination ETR RLOCs (or the Map-Server sends a Map-Reply, if it is providing a proxy Map-Reply service), and a Map-Referral with action code MS-ACK MUST be returned to the sender of the DDT Map-Request.
  • If the requested XEID matches a configured XEID-prefix for which no ETR registration has been received, then a Negative Map-Referral with action code MS-NOT-REGISTERED MUST be returned to the sender of the DDT Map-Request.
  • リクエストされたXEIDが登録されたXEID-prefixに一致する場合、Map-Requestは宛先のETRのRLOCの1つに転送され（または、Map-ServerがプロキシーMap-Replyサービスを提供している場合は、Map-ServerがMap-Replyを送信し）、アクションコードMS-ACKを持つMap-ReferralをDDT Map-Requestの送信者に返さなければなりません（MUST）。
  • リクエストされたXEIDが、ETRの登録を受信していない、設定されたXEID-prefixに一致する場合、アクションコードMS-NOT-REGISTEREDを持つネガティブMap-ReferralをDDT Map-Requestの送信者に返さなければなりません（MUST）。

7.3. DDT Client

7.3. DDTクライアント

A DDT client queries one or more DDT nodes and uses an iterative process of following returned referrals until it receives one with action code MS-ACK (or an error indication). MS-ACK indicates that the Map-Request has been sent to a Map-Server that will forward it to an ETR that, in turn, will provide a Map-Reply to the locator address in the Map-Request.

DDTクライアントは、1つ以上のDDTノードに問い合わせ、アクションコードMS-ACKを持つリファラル（またはエラー表示）を受信するまで、返されたリファラルをたどる反復的な処理を使用します。MS-ACKは、Map-RequestがMap-Serverに送信され、そのMap-ServerがMap-RequestをETRに転送し、次にそのETRがMap-Request内のロケーターアドレスにMap-Replyを提供することを示します。

DDT client functionality will typically be implemented by DDT Map-Resolvers. Just as would any other Map-Resolver, a DDT Map-Resolver accepts Map-Requests from its clients (typically ITRs) and ensures that those Map-Requests are forwarded to the correct ETR, which generates Map-Replies. However, unlike a Map-Resolver that uses the LISP Alternative Logical Topology (LISP+ALT) mapping system [RFC6836], a DDT Map-Resolver implements DDT client functionality to find the correct ETR to answer a Map-Request; this requires a DDT Map-Resolver to maintain additional state: a Map-Referral cache and a pending request list of XEIDs that are going through the iterative referral process.

DDTクライアントの機能は、通常はDDT Map-Resolverによって実装されます。ほかのMap-Resolverと同様に、DDT Map-Resolverは、クライアント（通常はITR）からMap-Requestを受け付け、それらのMap-Requestが、Map-Replyを生成する正しいETRに転送されることを保証します。ただし、LISP代替論理トポロジー（LISP Alternative Logical Topology、LISP+ALT）のマッピングシステム[RFC6836]を使用するMap-Resolverとは異なり、DDT Map-Resolverは、Map-Requestに答える正しいETRを見つけるためにDDTクライアントの機能を実装します。このため、DDT Map-Resolverは追加の状態、すなわち、Map-Referralキャッシュと、反復的なリファラル処理の途中にあるXEIDの保留中リクエストリストを保持する必要があります。

DDT client functionality may be implemented on ITRs. In this case, the DDT client will not receive a Map-Request from another network element; instead, equivalent information will be provided to the DDT client via a programming interface.

DDTクライアントの機能は、ITR上に実装してもかまいません。この場合、DDTクライアントは別のネットワーク要素からMap-Requestを受信するのではなく、プログラミングインターフェイスを介して同等の情報を受け取ります。

7.3.1. Queuing and Sending DDT Map-Requests

7.3.1. DDT Map-Requestのキューイングと送信

When a DDT client receives a request to resolve an XEID (in the case of a DDT Map-Resolver, this will be in the form of a received Encapsulated Map-Request), it first performs a longest-match search for the XEID in its referral cache. If no match is found or if a negative cache entry is found, then the destination is not in the database; a Negative Map-Reply MUST be returned, and no further processing is performed by the DDT client.

DDTクライアントは、XEIDを解決するリクエスト（DDT Map-Resolverの場合、これは受信したカプセル化されたMap-Requestの形をとります）を受信すると、まずリファラルキャッシュ内でそのXEIDの最長一致検索を実行します。一致するものが見つからない場合、またはネガティブキャッシュエントリーが見つかった場合、その宛先はデータベースに存在しません。ネガティブMap-Replyを返さなければなりません（MUST）。DDTクライアントはそれ以上の処理を行いません。

If a match is found, the DDT client creates a pending request list entry for the XEID and saves the original request (in the case of a DDT Map-Resolver, this will be the original Map-Request minus the encapsulation header) along with other information needed to track progress through the iterative referral process; the "referral XEID-prefix" is also initialized to indicate that no referral has yet been received. The DDT client then creates a DDT Map-Request (which is an Encapsulated Map-Request with the "DDT-originated" flag set in the message header) for the XEID but without any authentication data that may have been included in the original request. It sends the DDT Map-Request to one of the RLOCs in the chosen referral cache entry. The referral cache is initially populated with one or more statically configured entries; additional entries are added when referrals are followed, as described below. A DDT client is not absolutely required to cache referrals, but doing so will decrease latency and reduce lookup delays.

一致するものが見つかった場合、DDTクライアントは、そのXEIDについての保留中リクエストリストのエントリーを作成し、反復的なリファラル処理の進行状況を追跡するのに必要なその他の情報とともに、元のリクエスト（DDT Map-Resolverの場合、これはカプセル化ヘッダーを除いた元のMap-Requestです）を保存します。また、まだリファラルを受信していないことを示すように「リファラルXEID-prefix」を初期化します。次にDDTクライアントは、そのXEIDについてのDDT Map-Request（メッセージヘッダーに「DDT-originated」フラグを設定したカプセル化されたMap-Request）を、元のリクエストに含まれていた可能性のある認証データを一切含めずに作成します。DDTクライアントは、選択したリファラルキャッシュエントリー内のRLOCの1つにそのDDT Map-Requestを送信します。リファラルキャッシュには、最初は静的に設定された1つ以上のエントリーが格納されており、以下で説明するように、リファラルをたどる際に追加のエントリーが加えられます。DDTクライアントがリファラルをキャッシュすることは絶対に必要というわけではありませんが、キャッシュすることでレイテンシーが減少し、検索の遅延が短縮されます。

Note that in normal use on the public Internet, the statically configured initial referral cache for a DDT client should include a "default" entry with RLOCs for either the root DDT node or one or more DDT nodes that contain hints for the root DDT node. If a DDT client does not have such a configuration, it will return a Negative Map-Reply if it receives a query for an EID outside the subset of the mapping database known to it. While this may be desirable on private network deployments or during early transition to LISP when few sites are using it, this behavior is not appropriate when LISP is in general use on the Internet. If DDT message exchanges are authenticated as described in Section 10, then the DDT client MUST also be configured with public keys of DDT nodes pointed to by the "default" cache entry. In this case, the "default" entry will typically be for the root DDT node.

公共のインターネットでの通常の使用では、DDTクライアントの静的に設定された初期のリファラルキャッシュには、ルートDDTノード、またはルートDDTノードについてのヒントを含む1つ以上のDDTノードのいずれかのRLOCを持つ「デフォルト」エントリーを含めるべきであることに注意してください。DDTクライアントにそのような設定がない場合、自身が知っているマッピングデータベースのサブセットの外にあるEIDについての問い合わせを受信すると、DDTクライアントはネガティブMap-Replyを返します。これは、プライベートネットワークでの展開や、LISPを使用しているサイトがほとんどないLISPへの移行の初期段階では望ましい場合もありますが、LISPがインターネットで一般的に使用されている場合には、この振る舞いは適切ではありません。セクション10で説明するようにDDTのメッセージ交換が認証される場合、DDTクライアントには、「デフォルト」キャッシュエントリーが指すDDTノードの公開鍵も設定しなければなりません（MUST）。この場合、「デフォルト」エントリーは通常、ルートDDTノードについてのものになります。

7.3.2. Receiving and Following Referrals

7.3.2. リファラルの受信と追跡

After sending a DDT Map-Request, a DDT client expects to receive a Map-Referral response. If none occurs within the timeout period, the DDT client retransmits the request, sending it to the next RLOC in the referral cache entry if one is available. If all RLOCs have been tried and the maximum number of retransmissions has occurred for each, then the pending request list entry is dequeued and discarded. In this case, the DDT client returns no response to the sender of the original request.

DDT Map-Requestを送信した後、DDTクライアントはMap-Referralレスポンスを受信することを期待します。タイムアウト期間内にレスポンスがない場合、DDTクライアントはリクエストを再送信します。その際、リファラルキャッシュエントリー内に次のRLOCがあれば、そのRLOCに送信します。すべてのRLOCを試し、それぞれについて再送信の最大回数に達した場合、保留中リクエストリストのエントリーはキューから取り除かれ、破棄されます。この場合、DDTクライアントは元のリクエストの送信者にレスポンスを返しません。

A DDT client processes a received Map-Referral message according to each action code:

DDTクライアントは、受信したMap-Referralメッセージを、アクションコードごとに次のように処理します。

NODE-REFERRAL:
The DDT client checks for a possible referral loop as described in Section 7.3.4. If no loop is found, the DDT client saves the prefix returned in the Map-Referral message in the referral cache, updates the saved prefix and saved RLOCs in the pending request list entry, and follows the referral by sending a new DDT Map-Request to one of the DDT node RLOCs listed in the Referral Set; security information saved with the original Map-Request SHOULD NOT be included.
MS-REFERRAL:
The DDT client processes an MS-REFERRAL in the same manner as a NODE-REFERRAL, except that security information saved with the original Map-Request MUST be included in the new Map-Request sent to a Map-Server (see Section 10 for details on security).
MS-ACK:
An MS-ACK is returned by a DDT Map-Server to indicate that it has one or more registered ETRs that can answer a Map-Request for the XEID and the request has been forwarded to one of them (or, if the Map-Server is providing a proxy service for the prefix, then a reply has been sent to the querying ITR). If the pending request did not include saved LISP-SEC information or if that information was already included in the previous DDT Map-Request (sent by the DDT client in response to either an MS-REFERRAL or a previous MS-ACK referral), then the pending request for the XEID is complete; processing of the request stops, and all request state can be discarded. Otherwise, LISP-SEC information is required and has not yet been sent to the authoritative DDT Map-Server; the DDT client MUST resend the DDT Map-Request with LISP-SEC information included, and the pending request queue entry remains until another Map-Referral with action code MS-ACK is received. If the "Incomplete" flag is not set, the prefix is saved in the referral cache.
MS-NOT-REGISTERED:
The DDT Map-Server queried could not process the request because it did not have any ETRs registered for a matching, authoritative XEID-prefix. If the DDT client has not yet tried all of the RLOCs saved with the pending request, then it sends a Map-Request to the next RLOC in that list. If all RLOCs have been tried, then the destination XEID is not registered and is unreachable. The DDT client MUST return a Negative Map-Reply to the requester (or, in the case of a DDT Map-Resolver, to the sender of the original Map-Request). This Map-Reply contains the least-specific XEID-prefix in the range for which this DDT Map-Server is authoritative and in which no registrations exist. The TTL value of the Negative Map-Reply SHOULD be set to 1 minute. A negative referral cache entry is created for the prefix (whose TTL also SHOULD be set to 1 minute), and processing of the request stops.
DELEGATION-HOLE:
The DDT Map-Server queried did not have an XEID-prefix defined that matched the requested XEID, so the XEID does not exist in the mapping database. The DDT client MUST return a Negative Map-Reply to the requester (or, in the case of a DDT Map-Resolver, to the sender of the original Map-Request); this Map-Reply SHOULD indicate the least-specific XEID-prefix matching the requested XEID for which no delegations exist and SHOULD have a TTL value of 15 minutes. A negative referral cache entry is created for the prefix (which also SHOULD have a TTL of 15 minutes), and processing of the pending request stops.
NOT-AUTHORITATIVE:
The DDT Map-Server queried is not authoritative for the requested XEID. This can occur if a cached referral has become invalid due to a change in the database hierarchy. If the DDT client receiving this message can determine that it is using old cached information, it MAY choose to delete that cached information and retry the original Map-Request, starting from its "root" cache entry. If this action code is received in response to a query that did not use cached referral information, then it indicates a database synchronization problem or configuration error. The pending request is silently discarded; i.e., all state for the request that caused this answer is removed, and no answer is returned to the original requester.
NODE-REFERRAL:
DDTクライアントは、セクション7.3.4で説明するように、リファラルループの可能性を確認します。ループが見つからなければ、DDTクライアントは、Map-Referralメッセージで返されたプレフィックスをリファラルキャッシュに保存し、保留中リクエストリストのエントリー内の保存済みのプレフィックスと保存済みのRLOCを更新し、リファラルセットに列挙されたDDTノードのRLOCの1つに新しいDDT Map-Requestを送信することによってリファラルをたどります。元のMap-Requestとともに保存されたセキュリティー情報は含めるべきではありません（SHOULD NOT）。
MS-REFERRAL:
DDTクライアントは、MS-REFERRALをNODE-REFERRALと同じ方法で処理します。ただし、元のMap-Requestとともに保存されたセキュリティー情報を、Map-Serverに送信する新しいMap-Requestに含めなければなりません（MUST）（セキュリティーの詳細についてはセクション10を参照してください）。
MS-ACK:
MS-ACKは、そのXEIDについてのMap-Requestに答えることができる1つ以上の登録済みのETRを自身が持っており、かつそのリクエストがそれらのETRの1つに転送された（または、Map-Serverがそのプレフィックスについてプロキシーサービスを提供している場合は、問い合わせ元のITRにリプライが送信された）ことを示すために、DDT Map-Serverが返します。保留中のリクエストに保存されたLISP-SECの情報が含まれていなかった場合、またはその情報が（MS-REFERRALか以前のMS-ACKリファラルのいずれかへの応答としてDDTクライアントが送信した）以前のDDT Map-Requestにすでに含まれていた場合、そのXEIDについての保留中のリクエストは完了です。リクエストの処理は終了し、リクエストのすべての状態を破棄できます。そうでない場合は、LISP-SECの情報が必要であるにもかかわらず、権威を持つDDT Map-Serverにまだ送信されていません。DDTクライアントは、LISP-SECの情報を含めてDDT Map-Requestを再送信しなければなりません（MUST）。保留中のリクエストのキューエントリーは、アクションコードMS-ACKを持つ別のMap-Referralを受信するまで残ります。「Incomplete」フラグが設定されていなければ、そのプレフィックスはリファラルキャッシュに保存されます。
MS-NOT-REGISTERED:
問い合わせたDDT Map-Serverは、一致する権威を持つXEID-prefixに登録されたETRを1つも持っていなかったため、リクエストを処理できませんでした。DDTクライアントが、保留中のリクエストとともに保存されたRLOCをまだすべて試していない場合は、そのリストの次のRLOCにMap-Requestを送信します。すべてのRLOCを試した場合、その宛先XEIDは登録されておらず、到達不可能です。DDTクライアントは、リクエスター（DDT Map-Resolverの場合は、元のMap-Requestの送信者）にネガティブMap-Replyを返さなければなりません（MUST）。このMap-Replyには、このDDT Map-Serverが権威を持ち、かつ登録が存在しない範囲にある、最も詳細度の低いXEID-prefixが含まれます。ネガティブMap-ReplyのTTL値は1分に設定すべきです（SHOULD）。そのプレフィックスについてネガティブリファラルキャッシュエントリーが作成され（そのTTLも1分に設定すべきです（SHOULD））、リクエストの処理は終了します。
DELEGATION-HOLE:
問い合わせたDDT Map-Serverには、リクエストされたXEIDに一致するXEID-prefixが定義されていなかったため、そのXEIDはマッピングデータベースに存在しません。DDTクライアントは、リクエスター（DDT Map-Resolverの場合は、元のMap-Requestの送信者）にネガティブMap-Replyを返さなければなりません（MUST）。このMap-Replyは、リクエストされたXEIDに一致し、委任が存在しない、最も詳細度の低いXEID-prefixを示すべきです（SHOULD）。また、TTL値は15分にするべきです（SHOULD）。そのプレフィックスについてネガティブリファラルキャッシュエントリーが作成され（そのTTLも15分にするべきです（SHOULD））、保留中のリクエストの処理は終了します。
NOT-AUTHORITATIVE:
問い合わせたDDT Map-Serverは、リクエストされたXEIDに対して権威を持っていません。これは、データベース階層の変更によって、キャッシュされたリファラルが無効になった場合に起こることがあります。このメッセージを受信したDDTクライアントが、自身が古いキャッシュ情報を使用していると判断できる場合、そのキャッシュ情報を削除し、「ルート」キャッシュエントリーから始めて元のMap-Requestを再試行することを選択してもよいです（MAY）。キャッシュされたリファラル情報を使用しなかった問い合わせへの応答としてこのアクションコードを受信した場合、それはデータベースの同期の問題または設定の誤りを示しています。保留中のリクエストは黙って破棄されます。つまり、この答えの原因となったリクエストのすべての状態が削除され、元のリクエスターには答えが返されません。

7.3.3. Handling Referral Errors

7.3.3. リファラルのエラーの処理

Other states are possible, such as a misconfigured DDT node (acting as a proxy Map-Server, for example) returning a Map-Reply to the DDT client; they should be considered errors and logged as such. It is not clear exactly what else the DDT client should do in such cases; one possibility is to remove the pending request list entry and send a Negative Map-Reply to the requester (or, in the case of a DDT Map-Resolver, to the sender of the original Map-Request). Alternatively, if a DDT client detects unexpected behavior by a DDT node, it could mark that node as unusable in its referral cache and update the pending request to try a different DDT node if more than one is listed in the referral cache. In any case, any prefix contained in a Map-Referral message that causes a referral error (including a referral loop) is not saved in the DDT client referral cache.

（たとえばプロキシーMap-Serverとして動作する）設定の誤ったDDTノードがDDTクライアントにMap-Replyを返すなど、ほかの状態も起こり得ます。それらはエラーとみなし、エラーとしてログに記録すべきです。そのような場合にDDTクライアントがほかに何をすべきかは、正確にはわかっていません。1つの可能性は、保留中リクエストリストのエントリーを削除し、リクエスター（DDT Map-Resolverの場合は、元のMap-Requestの送信者）にネガティブMap-Replyを送信することです。あるいは、DDTクライアントがDDTノードの予期しない振る舞いを検出した場合、リファラルキャッシュ内でそのノードを使用不能としてマークし、リファラルキャッシュに複数のDDTノードが列挙されていれば、別のDDTノードを試すように保留中のリクエストを更新することもできます。いずれの場合も、リファラルのエラー（リファラルループを含む）の原因となったMap-Referralメッセージに含まれるプレフィックスは、DDTクライアントのリファラルキャッシュには保存されません。

7.3.4. Referral Loop Detection

7.3.4. リファラルループの検出

In response to a Map-Referral message with action code NODE-REFERRAL or MS-REFERRAL, a DDT client is directed to query a new set of DDT node RLOCs that are expected to have more-specific XEID-prefix information for the requested XEID. To prevent a possible "iteration loop" (following referrals back and forth among a set of DDT nodes without ever finding an answer), a DDT client saves the last received referral XEID-prefix for each pending request and checks to see if a newly received NODE-REFERRAL or MS-REFERRAL message contains a more-specific referral XEID-prefix; an exact or less-specific match of the saved XEID-prefix indicates a referral loop. If a loop is detected, the DDT Map-Resolver handles the request as described in Section 7.3.3. Otherwise, the DDT client saves the most recently received referral XEID-prefix with the pending request when it follows the referral.

アクションコードNODE-REFERRALまたはMS-REFERRALを持つMap-Referralメッセージへの応答として、DDTクライアントは、リクエストされたXEIDについてより詳細なXEID-prefixの情報を持つと期待される、DDTノードのRLOCの新しいセットに問い合わせるよう指示されます。起こり得る「反復ループ」（答えを見つけることなく、DDTノードの集合の間でリファラルを行ったり来たりたどること）を防ぐために、DDTクライアントは、保留中のリクエストごとに最後に受信したリファラルXEID-prefixを保存し、新しく受信したNODE-REFERRALメッセージまたはMS-REFERRALメッセージに、より詳細なリファラルXEID-prefixが含まれているかどうかを確認します。保存済みのXEID-prefixとの完全一致、またはより詳細度の低い一致は、リファラルループを示します。ループが検出された場合、DDT Map-Resolverは、セクション7.3.3で説明するようにリクエストを処理します。そうでない場合、DDTクライアントは、リファラルをたどる際に、最も新しく受信したリファラルXEID-prefixを保留中のリクエストとともに保存します。

As an extra measure to prevent referral loops, it is probably also wise to limit the total number of referrals for any request to some reasonable number; the exact value of that number will be determined during experimental deployment of LISP-DDT but is bounded by the maximum length of the XEID.

リファラルループを防ぐための追加の対策として、どのリクエストについてもリファラルの総数を何らかの妥当な数に制限することも、おそらく賢明です。その数の正確な値は、LISP-DDTの実験的な展開の間に決定されることになりますが、XEIDの最大長によって上限が定まります。

Note that when a DDT client adds an entry to its lookup queue and sends an initial Map-Request for an XEID, the queue entry has no previous referral XEID-prefix; this means that the first DDT node contacted by a DDT Map-Resolver may provide a referral to anywhere in the DDT hierarchy. This, in turn, allows a DDT client to use essentially any DDT node RLOCs for its initial cache entries and depend on the initial referral to provide a good starting point for Map-Requests; there is no need to configure the same set of root DDT nodes on all DDT clients.

DDTクライアントが検索キューにエントリーを追加し、あるXEIDについての最初のMap-Requestを送信するとき、そのキューエントリーには以前のリファラルXEID-prefixがないことに注意してください。これは、DDT Map-Resolverが最初に問い合わせたDDTノードが、DDT階層内の任意の場所へのリファラルを提供できることを意味します。その結果、DDTクライアントは、初期のキャッシュエントリーとして基本的にどのDDTノードのRLOCでも使用でき、最初のリファラルがMap-Requestの適切な出発点を提供することに頼ることができます。すべてのDDTクライアントに同じルートDDTノードのセットを設定する必要はありません。

It responds with a Map-Referral message for 2001:db8:0500::/64, action code DELEGATION-HOLE, to the DDT Map-Resolver. The prefix 2001:db8:0500::/64 is used because it is the least-specific prefix that does match the requested EID but does not match one of the configured delegations (2001:db8:0500:1::/64 and 2001:db8:0500:2::/64).
  3. The DDT Map-Resolver receives the delegation, adds a negative referral cache entry for 2001:db8:0500::/64, dequeues the pending request for 2001:db8:0500::1, and returns a Negative Map-Reply to ITR2.
  1. （2001:db8:0500::1についての）DDT Map-Requestを192.0.2.211に送信します。ITRが発信したカプセル化されたMap-RequestにLISP-SECの署名があった場合は、それを含めます。
  2. 2001:db8:0500::/48に対して権威を持つ192.0.2.211のDDT Map-Serverは、2001:db8:0500::1に一致する委任を持っていません。このDDT Map-Serverは、2001:db8:0500::/64、アクションコードDELEGATION-HOLEのMap-Referralメッセージで、DDT Map-Resolverに応答します。プレフィックス2001:db8:0500::/64が使用されるのは、これが、リクエストされたEIDには一致するが、設定された委任（2001:db8:0500:1::/64と2001:db8:0500:2::/64）のいずれにも一致しない、最も詳細度の低いプレフィックスであるためです。
  3. DDT Map-Resolverは、その委任を受信し、2001:db8:0500::/64についてのネガティブリファラルキャッシュエントリーを追加し、2001:db8:0500::1についての保留中のリクエストをキューから取り除き、ITR2にネガティブMap-Replyを返します。

10. Securing the Database and Message Exchanges

10. データベースとメッセージ交換の保護

This section specifies the DDT security architecture that provides data origin authentication, data integrity protection, and XEID-prefix delegation. Global XEID-prefix authorization is out of scope for this document.

このセクションでは、データ発信元認証、データの完全性保護、XEID-prefixの委任を提供するDDTのセキュリティーアーキテクチャーを規定します。グローバルなXEID-prefixの認可は、この文書の範囲外です。

Each DDT node is configured with one or more public/private key pairs that are used to digitally sign Map-Referral Records for XEID-prefix(es) for which the DDT node is authoritative. In other words, each public/private key pair is associated with the combination of a DDT node and an XEID-prefix for which it is authoritative. Every DDT node is also configured with the public keys of its child DDT nodes. By including the public keys of target child DDT nodes in the Map-Referral Records and signing each Record with the DDT node's private key, a DDT node can securely delegate sub-prefixes of its authoritative XEID-prefixes to its child DDT nodes. A DDT node configured to provide hints must also have the public keys of the DDT nodes to which its hints point. DDT node keys can be encoded using LCAF Type 11 to associate the key to the RLOC of the referred DDT node. If a node has more than one public key, it should sign its Records with at least one of these keys. When a node has N keys, it can sustain up to N-1 key compromises. The revocation mechanism is described in Section 10.2.1.

各DDTノードには、自身が権威を持つXEID-prefixについてのMap-Referralレコードにデジタル署名するために使用する、1つ以上の公開鍵/秘密鍵のペアが設定されます。言い換えると、各公開鍵/秘密鍵のペアは、DDTノードと、そのDDTノードが権威を持つXEID-prefixとの組み合わせに関連付けられます。すべてのDDTノードには、その子DDTノードの公開鍵も設定されます。DDTノードは、対象となる子DDTノードの公開鍵をMap-Referralレコードに含め、各レコードに自身の秘密鍵で署名することによって、自身が権威を持つXEID-prefixのサブプレフィックスを子DDTノードに安全に委任できます。ヒントを提供するように設定されたDDTノードは、そのヒントが指すDDTノードの公開鍵も持っていなければなりません。DDTノードの鍵は、LCAFのType 11を使用してエンコードすることで、紹介先のDDTノードのRLOCに鍵を関連付けることができます。ノードが複数の公開鍵を持つ場合、そのノードは少なくともそれらの鍵の1つで自身のレコードに署名すべきです。ノードがN個の鍵を持つ場合、そのノードはN-1個までの鍵の侵害に耐えることができます。失効のメカニズムはセクション10.2.1で説明します。

Map-Resolvers are configured with one or more trusted public keys, referred to as "trust anchors". Trust anchors are used to authenticate the DDT security infrastructure. Map-Resolvers can discover a DDT node's public key by either (1) having it configured as a trust anchor or (2) obtaining it from the node's parent as part of a signed Map-Referral. When a public key is obtained from a node's parent, it is considered trusted if it is signed by a trust anchor or if it is signed by a key that was previously trusted. Typically, in a Map-Resolver, the root DDT node's public keys should be configured as trust anchors. Once a Map-Resolver authenticates a public key, it locally caches the key along with the associated DDT node RLOC and XEID-prefix for future use.

Map-Resolverには、「トラストアンカー」と呼ばれる、信頼された1つ以上の公開鍵が設定されます。トラストアンカーは、DDTのセキュリティー基盤を認証するために使用されます。Map-Resolverは、（1）DDTノードの公開鍵がトラストアンカーとして設定されている、または（2）署名されたMap-Referralの一部としてノードの親からその公開鍵を取得する、のいずれかによって、DDTノードの公開鍵を発見できます。公開鍵をノードの親から取得した場合、その公開鍵は、トラストアンカーによって署名されているか、以前に信頼された鍵によって署名されていれば、信頼されたものとみなされます。通常、Map-Resolverでは、ルートDDTノードの公開鍵をトラストアンカーとして設定すべきです。Map-Resolverは、公開鍵を認証したら、将来の使用のために、関連するDDTノードのRLOCとXEID-prefixとともにその鍵をローカルにキャッシュします。

10.1. XEID-Prefix Delegation

10.1. XEID-prefixの委任

In order to delegate XEID sub-prefixes to its child DDT nodes, a parent DDT node signs its Map-Referrals. Every signed Map-Referral MUST also include the public keys associated with each child DDT node. Such a signature indicates that the parent DDT node is delegating the specified XEID-prefix to a given child DDT node. The signature is also authenticating the public keys associated with the child DDT nodes, and authorizing them to be used by the child DDT nodes, to provide origin authentication and integrity protection for further delegations and mapping information of the XEID-prefix allocated to the DDT node.

親DDTノードは、XEIDのサブプレフィックスを子DDTノードに委任するために、自身のMap-Referralに署名します。署名されたすべてのMap-Referralには、各子DDTノードに関連付けられた公開鍵も含めなければなりません（MUST）。そのような署名は、親DDTノードが、指定されたXEID-prefixを特定の子DDTノードに委任していることを示します。この署名はまた、子DDTノードに関連付けられた公開鍵を認証し、そのDDTノードに割り当てられたXEID-prefixのさらなる委任とマッピング情報について発信元認証と完全性保護を提供するために、子DDTノードがそれらの公開鍵を使用することを認可するものでもあります。

As a result, for a given XEID-prefix, a Map-Resolver can form an authentication chain from a configured trust anchor (typically the root DDT node) to the leaf nodes (Map-Servers). Map-Resolvers leverage this authentication chain to verify the Map-Referral signatures while walking the DDT tree until they reach a Map-Server authoritative for the given XEID-prefix.

その結果、Map-Resolverは、あるXEID-prefixについて、設定されたトラストアンカー（通常はルートDDTノード）から葉のノード（Map-Server）までの認証チェーンを形成できます。Map-Resolverは、DDTツリーをたどってそのXEID-prefixに対して権威を持つMap-Serverに到達するまでの間、この認証チェーンを活用してMap-Referralの署名を検証します。

10.2. DDT Node Operation

10.2. DDTノードの動作

Upon receiving a Map-Request, the DDT node responds with a Map-Referral as specified in Section 7. For every Record present in the Map-Referral, the DDT node also includes the public keys associated with the Record's XEID-prefix and the RLOCs of the child DDT nodes. Each Record contained in the Map-Referral is signed using the DDT node's private key.

DDTノードは、Map-Requestを受信すると、セクション7で規定されているようにMap-Referralで応答します。DDTノードは、Map-Referralに存在するすべてのレコードについて、そのレコードのXEID-prefixと子DDTノードのRLOCに関連付けられた公開鍵も含めます。Map-Referralに含まれる各レコードは、DDTノードの秘密鍵を使用して署名されます。

10.2.1. DDT Public Key Revocation

10.2.1. DDTの公開鍵の失効

The node that owns a public key can also revoke that public key. For instance, if a parent DDT node advertises a public key for one of its child DDT nodes, the child DDT node can at a later time revoke that key. Since DDT nodes do not keep track of the Map-Resolvers that query them, revocation is done in a pull model, where the Map-Resolver is informed of the revocation of a key only when it queries the node that owns that key. If the parent DDT node is configured to advertise that key, the parent DDT node must also be signaled to remove the key from the Records it advertises for the child DDT node; this is necessary to avoid further distribution of the revoked key.

公開鍵を所有するノードは、その公開鍵を失効させることもできます。たとえば、親DDTノードがその子DDTノードの1つについての公開鍵を広告している場合、その子DDTノードは後でその鍵を失効させることができます。DDTノードは自身に問い合わせるMap-Resolverを追跡しないため、失効はプル型のモデルで行われます。このモデルでは、Map-Resolverは、鍵を所有するノードに問い合わせたときにのみ、その鍵の失効を知らされます。親DDTノードがその鍵を広告するように設定されている場合、子DDTノードについて広告するレコードからその鍵を削除するよう、親DDTノードにも通知しなければなりません。これは、失効した鍵がさらに配布されるのを避けるために必要です。

To securely revoke a key, the DDT node creates a new Record for the associated XEID-prefix and locator, including the revoked key with the R bit set. (See Section 4.7 of [RFC8060] for details regarding the R bit.) The DDT node must also include a signature in the Record that covers this Record; this is computed using the private key corresponding to the key being revoked. Such a Record is termed a "revocation record". By including this Record in its Map-Referrals, the DDT node informs querying Map-Resolvers about the revoked key. A digital signature computed with a revoked key can only be used to authenticate the revocation and SHOULD NOT be used to validate any data. To prevent a compromised key from revoking other valid keys, a given key can only be used to sign a revocation for that specific key; it cannot be used to revoke other keys. This prevents the use of a compromised key to revoke other valid keys as described in [RFC5011]. A revocation record MUST be advertised for a period of time equal to or greater than the TTL value of the Record that initially advertised the key, starting from the time that the advertisement of the key was stopped by removal from the parent DDT node.

鍵を安全に失効させるために、DDTノードは、関連するXEID-prefixとロケーターについての新しいレコードを、Rビットを設定した失効対象の鍵を含めて作成します（Rビットの詳細については、[RFC8060]のセクション4.7を参照してください）。DDTノードは、このレコードを対象とする署名もレコードに含めなければなりません。この署名は、失効させる鍵に対応する秘密鍵を使用して計算されます。そのようなレコードを「失効レコード（revocation record）」と呼びます。DDTノードは、このレコードを自身のMap-Referralに含めることによって、問い合わせてきたMap-Resolverに失効した鍵について知らせます。失効した鍵で計算されたデジタル署名は、失効を認証するためにのみ使用でき、いかなるデータの検証にも使用すべきではありません（SHOULD NOT）。侵害された鍵がほかの有効な鍵を失効させるのを防ぐために、ある鍵は、その特定の鍵自身の失効に署名するためにのみ使用でき、ほかの鍵を失効させるために使用することはできません。これにより、[RFC5011]で説明されているように、侵害された鍵を使用してほかの有効な鍵を失効させることを防ぎます。失効レコードは、親DDTノードからの削除によってその鍵の広告が停止された時点から、最初にその鍵を広告したレコードのTTL値以上の期間にわたって広告しなければなりません（MUST）。

10.3. Map-Server Operation

10.3. Map-Serverの動作

Similar to a DDT node, a Map-Server is configured with one or more public/private key pairs that it must use to sign Map-Referrals.

DDTノードと同様に、Map-Serverには、Map-Referralに署名するために使用しなければならない1つ以上の公開鍵/秘密鍵のペアが設定されます。

However, unlike DDT nodes, Map-Servers do not delegate prefixes and as a result do not need to include keys in the Map-Referrals they generate.

ただし、DDTノードとは異なり、Map-Serverはプレフィックスを委任しないため、自身が生成するMap-Referralに鍵を含める必要はありません。

10.4. Map-Resolver Operation

10.4. Map-Resolverの動作

Upon receiving a Map-Referral, the Map-Resolver MUST first verify the signature(s) by using either a trust anchor or a previously authenticated public key associated with the DDT node sending the Map-Referral. If multiple authenticated keys are associated with the DDT node sending this Map-Referral, the Key Tag field (Section 6.4.1) of the signature can be used to select the correct public key for verifying the signature. If the key tag matches more than one key associated with that DDT node, the Map-Resolver MUST try to verify the signature with all matching keys. For every matching key that is found, the Map-Resolver MUST also verify that the key is authoritative for the XEID-prefix in the Map-Referral Record. If such a key is found, the Map-Resolver MUST use it to verify the associated signature in the Record. If (1) no matching key is found, (2) none of the matching keys is authoritative for the XEID-prefix in the Map-Referral Record, or (3) such a key is found but the signature is not valid, the Map-Referral Record is considered corrupted and MUST be discarded. This may be due to expired keys. The Map-Resolver MAY try other siblings of this node if there is an alternate node that is authoritative for the same prefix. If not, the Map-Resolver CAN query the DDT node's parent to retrieve a valid key. It is good practice to use a counter or timer to avoid repeating this process if the Map-Resolver cannot verify the signature after several attempts.

Map-Resolverは、Map-Referralを受信すると、まず、トラストアンカー、またはMap-Referralを送信したDDTノードに関連付けられた以前に認証済みの公開鍵のいずれかを使用して、署名を検証しなければなりません（MUST）。このMap-Referralを送信したDDTノードに複数の認証済みの鍵が関連付けられている場合、署名のKey Tagフィールド（セクション6.4.1）を使用して、署名を検証するための正しい公開鍵を選択できます。Key Tagが、そのDDTノードに関連付けられた複数の鍵に一致する場合、Map-Resolverは、一致するすべての鍵で署名の検証を試みなければなりません（MUST）。見つかった一致する鍵のそれぞれについて、Map-Resolverは、その鍵がMap-ReferralレコードのXEID-prefixに対して権威を持つことも検証しなければなりません（MUST）。そのような鍵が見つかった場合、Map-Resolverはその鍵を使用して、レコード内の関連する署名を検証しなければなりません（MUST）。（1）一致する鍵が見つからない場合、（2）一致する鍵のいずれもMap-ReferralレコードのXEID-prefixに対して権威を持たない場合、または（3）そのような鍵は見つかったが署名が有効でない場合、そのMap-Referralレコードは破損しているとみなされ、破棄しなければなりません（MUST）。これは、鍵の有効期限切れが原因である可能性があります。同じプレフィックスに対して権威を持つ代替のノードがある場合、Map-Resolverは、このノードのほかの兄弟ノードを試してもよいです（MAY）。そうでない場合、Map-Resolverは、有効な鍵を取得するためにDDTノードの親に問い合わせることができます。何回か試みた後もMap-Resolverが署名を検証できない場合に、この処理を繰り返さないように、カウンターまたはタイマーを使用するのがよいプラクティスです。

Once the signature is verified, the Map-Resolver has verified the XEID-prefix delegation in the Map-Referral. This also means that public keys of the child DDT nodes were authenticated; the Map-Resolver must add these keys to the authenticated keys associated with each child DDT node and XEID-prefix. These keys are considered valid for the duration specified in the Record's TTL field.

署名が検証されると、Map-ResolverはMap-Referral内のXEID-prefixの委任を検証したことになります。これはまた、子DDTノードの公開鍵が認証されたことも意味します。Map-Resolverは、これらの鍵を、各子DDTノードとXEID-prefixに関連付けられた認証済みの鍵に追加しなければなりません。これらの鍵は、レコードのTTLフィールドで指定された期間有効であるとみなされます。

11. Open Issues and Considerations

11. 未解決の問題と考慮事項

There are a number of issues with the organization of the mapping database that need further investigation. Among these are:

マッピングデータベースの構成には、さらなる調査が必要な問題がいくつかあります。それらには次のようなものがあります。

  • Defining an interface to implement interconnection and/or interoperability with other mapping databases, such as LISP+ALT.
  • Additional key structures for use with LISP-DDT, such as key structures to support additional EID formats as defined in [RFC8060].
  • Management of the DDT Map-Resolver referral cache -- in particular, detecting and removing outdated entries.
  • Best practices for either configuring hint referrals or avoiding their use.
  • LISP+ALTなどのほかのマッピングデータベースとの相互接続と相互運用性の一方または両方を実現するためのインターフェイスの定義。
  • LISP-DDTで使用するための追加の鍵構造。たとえば、[RFC8060]で定義されている追加のEID形式をサポートするための鍵構造。
  • DDT Map-Resolverのリファラルキャッシュの管理。特に、古くなったエントリーの検出と削除。
  • ヒントのリファラルを設定する、またはその使用を避けるためのベストプラクティス。

Operational experience will help answer open questions surrounding these and other issues.

運用経験は、これらの問題やその他の問題をめぐる未解決の疑問に答える助けとなるでしょう。

13. Security Considerations

13. セキュリティーに関する考慮事項

Section 10 describes a DDT security architecture that provides data origin authentication, data integrity protection, and XEID-prefix delegation within the DDT infrastructure.

セクション10では、DDT基盤内で、データ発信元認証、データの完全性保護、XEID-prefixの委任を提供するDDTのセキュリティーアーキテクチャーについて説明しています。

Global XEID-prefix authorization is beyond the scope of this document, but the Secure Inter-Domain Routing (SIDR) working group [RFC6480] is developing an infrastructure to support improved security of Internet routing. Further work is required to determine if SIDR's Public Key Infrastructure (PKI) and the distributed repository system it uses for storing and disseminating PKI data objects may also be used by DDT devices to verifiably assert that they are the legitimate holders of a set of XEID-prefixes.

グローバルなXEID-prefixの認可はこの文書の範囲外ですが、セキュアなドメイン間ルーティング（Secure Inter-Domain Routing、SIDR）ワーキンググループ[RFC6480]は、インターネットのルーティングのセキュリティーの向上をサポートする基盤を開発しています。SIDRの公開鍵基盤（PKI）と、PKIのデータオブジェクトを格納して配布するためにそれが使用する分散リポジトリーシステムを、DDTデバイスが一連のXEID-prefixの正当な保有者であることを検証可能な形で主張するためにも使用できるかどうかを判断するには、さらなる作業が必要です。

This document specifies how DDT security and LISP-SEC [LISP-SEC] complement one another to secure the DDT infrastructure, Map-Referral messages, and the Map-Request/Map-Reply protocols. In the future, other LISP security mechanisms may be developed to replace LISP-SEC. Such future security mechanisms should describe how they can be used together with LISP-DDT to provide similar levels of protection.

この文書は、DDTのセキュリティーとLISP-SEC[LISP-SEC]が、DDT基盤、Map-Referralメッセージ、およびMap-Request/Map-Replyプロトコルを保護するために、どのように互いに補完し合うかを規定します。将来、LISP-SECに置き換わる、ほかのLISPのセキュリティーメカニズムが開発される可能性があります。そのような将来のセキュリティーメカニズムは、同程度の保護を提供するために、LISP-DDTとともにどのように使用できるかを記述すべきです。

LISP-SEC can use the DDT public-key infrastructure to secure the transport of LISP-SEC key material (the One-Time Key) from a Map-Resolver to the corresponding Map-Server. For this reason, when LISP-SEC is deployed in conjunction with a LISP-DDT mapping database and the path between the Map-Resolver and Map-Server needs to be protected, DDT security as described in Section 10 should be enabled as well.

LISP-SECは、DDTの公開鍵基盤を使用して、Map-Resolverから対応するMap-ServerへのLISP-SECの鍵素材（ワンタイム鍵（One-Time Key））の転送を保護できます。このため、LISP-SECがLISP-DDTのマッピングデータベースとあわせて展開され、かつMap-ResolverとMap-Serverの間の経路を保護する必要がある場合は、セクション10で説明するDDTのセキュリティーも有効にすべきです。
