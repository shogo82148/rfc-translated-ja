RFC 10018

Multicast and Ethernet VPN with Segment Routing Point-to-Multipoint (P2MP) and Ingress Replication

RFC 10018

セグメントルーティングのポイントツーマルチポイント（P2MP）とイングレスレプリケーションを用いたマルチキャストVPNおよびイーサネットVPN

Abstract

概要

A Point-to-Multipoint (P2MP) tree in a Segment Routing (SR) domain carries traffic from a Root to a set of Leaves. This document specifies extensions to BGP encodings and procedures for P2MP trees and Ingress Replication used in BGP/MPLS IP VPNs and Ethernet VPNs (EVPNs) in an SR domain. This document updates RFCs 6514 and 7988.

セグメントルーティング（SR）ドメインにおけるポイントツーマルチポイント（P2MP）ツリーは、ルート（Root）からリーフ（Leaf）の集合へトラフィックを運びます。 この文書は、SRドメインにおけるBGP/MPLS IP VPNとイーサネットVPN（EVPN）で使用されるP2MPツリーとイングレスレプリケーション（Ingress Replication）のための、BGPのエンコーディングと手順の拡張を規定します。この文書はRFC 6514とRFC 7988を更新します。

1. Introduction

1. はじめに

"Multicast in MPLS/BGP IP VPNs" [RFC6513] and "BGP Encodings and Procedures for Multicast in MPLS/BGP IP VPNs" [RFC6514] specify procedures that allow a network operator to provide Multicast VPN (MVPN) service to its customers. Multicast traffic from a customer is tunneled across the service provider network over Provider Tunnels (P-tunnels). P-tunnels can be instantiated using different transport mechanisms. For example, a service provider network that uses Segment Routing (SR) can use an SR Point-to-Multipoint (P2MP) tree defined by an SR P2MP Policy [RFC9960] or SR P2MP Ingress Replication (IR) to instantiate P-tunnels for MVPN. This document refers to a P-tunnel realized by an SR P2MP Policy as an SR P2MP P-tunnel. SR P2MP P-tunnels can be instantiated for both Segment Routing over MPLS (SR-MPLS) [RFC8660] and Segment Routing over IPv6 (SRv6) [RFC8986] [RFC8754].

「Multicast in MPLS/BGP IP VPNs」[RFC6513]と「BGP Encodings and Procedures for Multicast in MPLS/BGP IP VPNs」[RFC6514]は、ネットワーク運用者が顧客にマルチキャストVPN（MVPN）サービスを提供できるようにする手順を規定しています。 顧客からのマルチキャストトラフィックは、プロバイダートンネル（P-tunnel）上でサービスプロバイダーのネットワークを横断してトンネリングされます。 P-tunnelは、さまざまなトランスポートメカニズムを使用してインスタンス化できます。 たとえば、セグメントルーティング（SR）を使用するサービスプロバイダーのネットワークは、SR P2MPポリシー[RFC9960]によって定義されるSRポイントツーマルチポイント（P2MP）ツリー、またはSR P2MPイングレスレプリケーション（IR）を使用して、MVPNのためのP-tunnelをインスタンス化できます。 この文書では、SR P2MPポリシーによって実現されるP-tunnelをSR P2MP P-tunnelと呼びます。 SR P2MP P-tunnelは、MPLS上のセグメントルーティング（SR-MPLS）[RFC8660]とIPv6上のセグメントルーティング（SRv6）[RFC8986] [RFC8754]の両方に対してインスタンス化できます。

An SR P2MP tree is defined by an SR P2MP Policy [RFC9960] and instantiated via a controller such as a Path Computation Element (PCE). An SR P2MP Policy consists of a Root, a set of Leaf nodes, and a set of candidate paths (CPs) with optional set of constraints and/or optimization objectives to be satisfied by the SR P2MP tree. A CP has zero or more P2MP tree instances (PTIs).

SR P2MPツリーは、SR P2MPポリシー[RFC9960]によって定義され、経路計算エレメント（PCE）などのコントローラーを介してインスタンス化されます。 SR P2MPポリシーは、ルート、リーフノードの集合、および候補パス（CP）の集合で構成され、SR P2MPツリーが満たすべき任意の制約の集合や最適化の目標を伴います。 CPは0個以上のP2MPツリーインスタンス（PTI）を持ちます。

This document specifies extensions to BGP auto-discovery procedures specified in [RFC6514] for P-tunnels constructed with a PTI. Use of Protocol Independent Multicast (PIM) for auto-discovery is outside the scope of this document. Support for customer Bidirectional PIM (BIDIR-PIM) is also outside the scope of this document.

この文書は、PTIで構築されたP-tunnelのために、[RFC6514]で規定されているBGPの自動発見手順の拡張を規定します。 自動発見のためのProtocol Independent Multicast（PIM）の使用はこの文書の範囲外です。 顧客の双方向PIM（BIDIR-PIM）のサポートもこの文書の範囲外です。

This document extends procedures in [RFC7988] for MVPN service with IR over an SR-MPLS data plane with a Service Level Agreement (SLA). New procedures are defined for MVPN service with IR over an SRv6 data plane with or without an SLA.

この文書は、サービスレベル合意（SLA）を伴うSR-MPLSデータプレーン上のIRを用いたMVPNサービスのために、[RFC7988]の手順を拡張します。 SLAを伴う、または伴わないSRv6データプレーン上のIRを用いたMVPNサービスのための新しい手順を定義します。

This document defines new SRv6 Endpoint behaviors [RFC8986] used for MVPN with SR P2MP and IR P-tunnels.

この文書は、SR P2MPとIRのP-tunnelを用いたMVPNに使用される新しいSRv6エンドポイントの振る舞い[RFC8986]を定義します。

For BGP MPLS-Based EVPN specified in [RFC7432] and updated in [RFC9572], P-tunnels are advertised for handling multi-destination traffic. These P-tunnels can be instantiated by SR-MPLS or SRv6 P2MP trees.

[RFC7432]で規定され、[RFC9572]で更新されたBGP MPLSベースのEVPNでは、マルチデスティネーションのトラフィックを処理するためにP-tunnelが広告されます。 これらのP-tunnelは、SR-MPLSまたはSRv6のP2MPツリーによってインスタンス化できます。

The reader is expected to be familiar with [RFC6513] and [RFC6514] for MVPN procedures. For EVPN procedures, refer to [RFC7432].

読者は、MVPNの手順について[RFC6513]と[RFC6514]に精通していることが期待されます。EVPNの手順については、[RFC7432]を参照してください。

Scalability, operational, and troubleshooting considerations for SR P2MP trees and Replication segments are described in [RFC9960] and [RFC9524], respectively. Operations, Administration, and Maintenance (OAM) ping and traceroute procedures for SR P2MP Policy using the SR-MPLS data plane are specified in [RFC9961].

SR P2MPツリーとレプリケーションセグメントのスケーラビリティー、運用、およびトラブルシューティングに関する考慮事項は、それぞれ[RFC9960]と[RFC9524]で説明されています。 SR-MPLSデータプレーンを使用するSR P2MPポリシーのための運用・管理・保守（OAM）のpingとtracerouteの手順は、[RFC9961]で規定されています。

2. SR P2MP P-Tunnel

2. SR P2MP P-Tunnel

For MVPN or EVPN, Provider Edge (PE) routers can steer customer traffic into a P-tunnel realized by an SR-MPLS or SRv6 PTI. An SR PTI is instantiated by a CP of an SR P2MP Policy [RFC9960]. A P-tunnel is signaled in MVPN or EVPN A-D routes using the BGP PMSI Tunnel Attribute (PTA) [RFC6514]. The PTA identifies the P-tunnel that is used to instantiate a PMSI.

MVPNまたはEVPNでは、プロバイダーエッジ（PE）ルーターは、SR-MPLSまたはSRv6のPTIによって実現されるP-tunnelに顧客のトラフィックを誘導できます。SRのPTIは、SR P2MPポリシー[RFC9960]のCPによってインスタンス化されます。 P-tunnelは、BGP PMSIトンネル属性（PTA）[RFC6514]を使用して、MVPNまたはEVPNのA-D経路でシグナリングされます。 PTAは、PMSIをインスタンス化するために使用されるP-tunnelを識別します。

The figure above shows the interaction between the conceptual MVPN or EVPN module and SR P2MP Policy module on an ingress PE. The ingress PE participates in MVPN or EVPN AD procedures and interacts with the SR P2MP Policy module as shown above to create and update the SR P2MP Policy, CP, and the Leaf set of SR P2MP policies. The SR P2MP Policy module interacts with a controller using protocols such as the Path Computation Element Communication Protocol (PCEP) [SR-P2MP-PCEP], BGP, the Network Configuration Protocol (NETCONF), etc., which are outside the scope of this document.

上の図は、イングレスPE上の概念的なMVPNまたはEVPNモジュールとSR P2MPポリシーモジュールの間の相互作用を示しています。 イングレスPEは、MVPNまたはEVPNのAD手順に参加し、上に示したようにSR P2MPポリシーモジュールとやり取りして、SR P2MPポリシー、CP、およびSR P2MPポリシーのリーフの集合を作成および更新します。 SR P2MPポリシーモジュールは、経路計算エレメント通信プロトコル（PCEP）[SR-P2MP-PCEP]、BGP、ネットワーク設定プロトコル（NETCONF）などのプロトコルを使用してコントローラーとやり取りしますが、これらはこの文書の範囲外です。

An ingress PE creates a CP of an SR P2MP Policy in the SR P2MP Policy module upon provisioning of the MVPN or EVPN module for the SR P2MP P-tunnel or based on events or policy, such as mapping MVPN or EVPN flow to a new SR P2MP P-tunnel. This CP can have optional traffic engineering constraints and/or an optimization objective by provisioning or by a local policy. The SR P2MP Policy module signals the CP along with the constraints and optimization objective to the controller using one of the protocols mentioned above. The ingress PE deletes the CP of the SR P2MP Policy from the SR P2MP Policy module when the SR P2MP P-tunnel is not longer required. The SR P2MP Policy module signals deletion of the CP of the SR P2MP Policy to the controller.

イングレスPEは、SR P2MP P-tunnelのためにMVPNまたはEVPNモジュールがプロビジョニングされたとき、またはMVPNやEVPNのフローを新しいSR P2MP P-tunnelに対応付けるなどのイベントやポリシーに基づいて、SR P2MPポリシーモジュールにSR P2MPポリシーのCPを作成します。 このCPは、プロビジョニングまたはローカルポリシーによって、任意のトラフィックエンジニアリングの制約や最適化の目標を持つことができます。 SR P2MPポリシーモジュールは、上記のプロトコルのいずれかを使用して、制約と最適化の目標とともにCPをコントローラーにシグナリングします。 イングレスPEは、SR P2MP P-tunnelがもはや必要なくなったときに、SR P2MPポリシーモジュールからSR P2MPポリシーのCPを削除します。 SR P2MPポリシーモジュールは、SR P2MPポリシーのCPの削除をコントローラーにシグナリングします。

An ingress PE participates in the MVPN or EVPN A-D procedures defined in this document to discover Leaf nodes of an SR P2MP P-tunnel via various A-D routes. The MVPN or EVPN module on the ingress PE updates the Leaf set of the SR P2MP Policy corresponding to the P-tunnel in the SR P2MP Policy module. The SR P2MP Policy module signals the updated Leaf set to the controller using one of the protocols mentioned above.

イングレスPEは、この文書で定義するMVPNまたはEVPNのA-D手順に参加し、さまざまなA-D経路を介してSR P2MP P-tunnelのリーフノードを発見します。 イングレスPE上のMVPNまたはEVPNモジュールは、SR P2MPポリシーモジュールにおいて、P-tunnelに対応するSR P2MPポリシーのリーフの集合を更新します。 SR P2MPポリシーモジュールは、上記のプロトコルのいずれかを使用して、更新されたリーフの集合をコントローラーにシグナリングします。

An egress PE associates an MVPN or EVPN A-D route with an MVPN or EVPN context and informs the SR P2MP Policy module to join the SR P2MP P-tunnel as a Leaf or a Bud node.

イグレスPEは、MVPNまたはEVPNのA-D経路をMVPNまたはEVPNのコンテキストに関連付け、リーフノードまたはバッドノード（Bud node）としてSR P2MP P-tunnelに参加するようSR P2MPポリシーモジュールに通知します。

Given a Leaf set of an SR P2MP Policy and a CP with constraints and an optimization objective, the controller computes and instantiates the PTI on the nodes that are part of the tree by stitching Replication segments [RFC9524] at the Root (ingress PE) node, intermediate replication nodes, and Leaf nodes (egress PEs). A Replication segment of a PTI can be instantiated by various methods such as BGP, PCEP, NETCONF, etc., which are outside the scope of this document. This PTI of the SR P2MP Policy instantiates the P-tunnel advertised by the MVPN or EVPN A-D routes.

SR P2MPポリシーのリーフの集合と、制約および最適化の目標を伴うCPが与えられると、コントローラーは、ルート（イングレスPE）ノード、中間レプリケーションノード、およびリーフノード（イグレスPE）でレプリケーションセグメント[RFC9524]をつなぎ合わせることで、ツリーの一部であるノード上でPTIを計算してインスタンス化します。 PTIのレプリケーションセグメントは、BGP、PCEP、NETCONFなどのさまざまな方法でインスタンス化できますが、これらはこの文書の範囲外です。 SR P2MPポリシーのこのPTIは、MVPNまたはEVPNのA-D経路によって広告されたP-tunnelをインスタンス化します。

The Tree-SID is the unique data plane identifier of the PTI. The Root node encapsulates the payload in the Tree-SID to steer it into the PTI. The Provider (P) routers replicate the encapsulated payload using Replication segments towards the Leaf nodes of the PTI. The Leaf nodes of the PTI dispose the Tree-SID and deliver the payload. A Leaf node derives the MVPN or EVPN instance for delivering the payload from either the Tree-SID or another context encoded in the packet.

Tree-SIDは、PTIの一意のデータプレーン識別子です。 ルートノードは、ペイロードをPTIに誘導するために、ペイロードをTree-SIDでカプセル化します。 プロバイダー（P）ルーターは、レプリケーションセグメントを使用して、カプセル化されたペイロードをPTIのリーフノードに向けて複製します。 PTIのリーフノードは、Tree-SIDを取り除いてペイロードを配送します。 リーフノードは、Tree-SIDまたはパケットにエンコードされた別のコンテキストのいずれかから、ペイロードを配送するためのMVPNまたはEVPNのインスタンスを導出します。

Note that an ingress PE can deliver an MVPN or EVPN payload to the egress PEs using IR over SR-MPLS or SRv6. The SR P2MP Policy module and controller do not participate in IR.

イングレスPEは、SR-MPLSまたはSRv6上のIRを使用して、MVPNまたはEVPNのペイロードをイグレスPEに配送できることに注意してください。 SR P2MPポリシーモジュールとコントローラーはIRには参加しません。

3. MVPN with SR

3. SRを用いたMVPN

MVPN service can be provided using SR P2MP trees or IR over either an SR-MPLS or SRv6 data plane.

MVPNサービスは、SR-MPLSまたはSRv6のいずれかのデータプレーン上で、SR P2MPツリーまたはIRを使用して提供できます。

3.1. SRv6 Multicast Endpoint Behaviors

3.1. SRv6マルチキャストのエンドポイントの振る舞い

The following SRv6 Endpoint behaviors can be associated with the SRv6 Multicast Service SID used for MVPN with SR P2MP and IR P-tunnels.

次のSRv6エンドポイントの振る舞いは、SR P2MPとIRのP-tunnelを用いたMVPNに使用されるSRv6マルチキャストサービスSIDに関連付けることができます。

3.1.1. End.DTMC4: Decapsulation and Specific IPv4 Multicast Table Lookup

3.1.1. End.DTMC4：カプセル化の解除と特定のIPv4マルチキャストテーブルの検索

The "Endpoint with Decapsulation and IPv4 Multicast Table Lookup" behavior (End.DTMC4 for short) is functionally identical to the End.DT4 behavior specified in [RFC8986], except that the forwarding lookup MUST be performed in the IPv4 multicast routing table rather than the IPv4 unicast routing table.

「Endpoint with Decapsulation and IPv4 Multicast Table Lookup」の振る舞い（略してEnd.DTMC4）は、転送の検索をIPv4ユニキャストルーティングテーブルではなくIPv4マルチキャストルーティングテーブルで実行しなければなりません（MUST）という点を除いて、[RFC8986]で規定されているEnd.DT4の振る舞いと機能的に同一です。

This behavior MUST only be associated with the SRv6 Multicast Service SID carried in AFI/SAFI 1/129 (MVPN-IPv4) A-D routes.

この振る舞いは、AFI/SAFI 1/129（MVPN-IPv4）のA-D経路で運ばれるSRv6マルチキャストサービスSIDにのみ関連付けなければなりません（MUST）。

3.1.2. End.DTMC6: Decapsulation and Specific IPv6 Multicast Table Lookup

3.1.2. End.DTMC6：カプセル化の解除と特定のIPv6マルチキャストテーブルの検索

The "Endpoint with Decapsulation and IPv6 Multicast Table Lookup" behavior (End.DTMC6 for short) is functionally identical to the End.DT6 behavior specified in [RFC8986], except that the forwarding lookup MUST be performed in the IPv6 multicast routing table rather than the IPv6 unicast routing table.

「Endpoint with Decapsulation and IPv6 Multicast Table Lookup」の振る舞い（略してEnd.DTMC6）は、転送の検索をIPv6ユニキャストルーティングテーブルではなくIPv6マルチキャストルーティングテーブルで実行しなければなりません（MUST）という点を除いて、[RFC8986]で規定されているEnd.DT6の振る舞いと機能的に同一です。

This behavior MUST only be associated with the SRv6 Multicast Service SID carried in AFI/SAFI 2/129 (MVPN-IPv6) A-D routes.

この振る舞いは、AFI/SAFI 2/129（MVPN-IPv6）のA-D経路で運ばれるSRv6マルチキャストサービスSIDにのみ関連付けなければなりません（MUST）。

3.1.3. End.DTMC46: Decapsulation and Specific IP Multicast Table Lookup

3.1.3. End.DTMC46：カプセル化の解除と特定のIPマルチキャストテーブルの検索

The "Endpoint with Decapsulation and IP Multicast Table Lookup" behavior (End.DTMC46 for short) is functionally identical to the End.DT4 and End.DT6 behaviors specified in [RFC8986], except that the forwarding lookup MUST be performed in the IP multicast routing table rather than in an IP unicast routing table.

「Endpoint with Decapsulation and IP Multicast Table Lookup」の振る舞い（略してEnd.DTMC46）は、転送の検索をIPユニキャストルーティングテーブルではなくIPマルチキャストルーティングテーブルで実行しなければなりません（MUST）という点を除いて、[RFC8986]で規定されているEnd.DT4およびEnd.DT6の振る舞いと機能的に同一です。

This behavior MUST only be associated with the SRv6 Multicast Service SID carried in AFI/SAFI 1/129 (MVPN-IPv4) or 2/129 (MVPN-IPv6) A-D routes.

この振る舞いは、AFI/SAFI 1/129（MVPN-IPv4）または2/129（MVPN-IPv6）のA-D経路で運ばれるSRv6マルチキャストサービスSIDにのみ関連付けなければなりません（MUST）。

3.2. MVPN with SR P2MP P-Tunnel

3.2. SR P2MP P-tunnelを用いたMVPN

[RFC6514] defines procedures for discovering PEs participating in a given MVPN and binding customer multicast flows to specific P-tunnels. This section specifies modifications to these procedures for SR P2MP P-tunnels. The Intra-AS I-PMSI, Inter-AS I-PMSI, and S-PMSI A-D routes have the PTA that specifies the SR P2MP tree P-tunnel. In this section, the term "SR P2MP" refers to both SR-MPLS and SRv6 data planes.

[RFC6514]は、特定のMVPNに参加しているPEを発見し、顧客のマルチキャストフローを特定のP-tunnelに結び付けるための手順を定義しています。 このセクションでは、SR P2MP P-tunnelのためのこれらの手順の変更を規定します。 Intra-AS I-PMSI、Inter-AS I-PMSI、およびS-PMSIのA-D経路は、SR P2MPツリーのP-tunnelを指定するPTAを持ちます。 このセクションでは、「SR P2MP」という用語は、SR-MPLSとSRv6の両方のデータプレーンを指します。

3.2.1. PMSI Tunnel Attribute for SR P2MP P-Tunnel

3.2.1. SR P2MP P-tunnelのためのPMSIトンネル属性

A PTA for an SR P2MP P-tunnel is constructed as specified below.

SR P2MP P-tunnelのためのPTAは、以下に規定するように構築されます。

  • Tunnel Type: One of the following SR P2MP P-tunnel types (from the "P-Multicast Service Interface Tunnel (PMSI Tunnel) Tunnel Types" registry).

    • 0x0C for SR-MPLS P2MP Tree

    • 0x0D for SRv6 P2MP Tree

  • Flags: See Section 3.2.2 for use of the "Leaf Information Required" flag.

  • MPLS Label: See Section 4.1.1.1.

  • Tunnel Identifier: The SR P2MP P-tunnel identifies an SR P2MP Policy with the identifier <Root, Tree-ID> [RFC9960] encoded in the exact order below:

    • Tree-ID: A 32-bit unsigned value that uniquely identifies an SR P2MP Policy at the Root.

    • Root: An IP address identifying the Root of the SR P2MP Policy. This can be either an IPv4 or IPv6 address. The address type can be inferred from the PTA length.

  • Tunnel Type：（「P-Multicast Service Interface Tunnel (PMSI Tunnel) Tunnel Types」レジストリーからの）次のSR P2MP P-tunnelの種類のいずれか。

    • SR-MPLS P2MPツリーの場合は0x0C

    • SRv6 P2MPツリーの場合は0x0D

  • Flags：「Leaf Information Required」フラグの使用についてはSection 3.2.2を参照してください。

  • MPLS Label：Section 4.1.1.1を参照してください。

  • Tunnel Identifier：SR P2MP P-tunnelは、以下の正確な順序でエンコードされた識別子<Root, Tree-ID>[RFC9960]によってSR P2MPポリシーを識別します：

    • Tree-ID：ルートにおいてSR P2MPポリシーを一意に識別する32ビットの符号なしの値。

    • Root：SR P2MPポリシーのルートを識別するIPアドレス。 これはIPv4アドレスまたはIPv6アドレスのいずれかです。 アドレスの種類はPTAの長さから推測できます。

A PTA with a SR P2MP P-tunnel is provisioned with the Tunnel Type for SR-MPLS or SRv6 P2MP trees. An implementation SHOULD advertise a PTA with SR P2MP P-tunnel only when the underlying SR-MPLS or SRv6 data plane is supported. The procedures for provisioning and determination of data plane support for SR-MPLS or SRv6 are outside scope of this document.

SR P2MP P-tunnelを持つPTAは、SR-MPLSまたはSRv6のP2MPツリーのTunnel Typeでプロビジョニングされます。 実装は、基礎となるSR-MPLSまたはSRv6のデータプレーンがサポートされている場合にのみ、SR P2MP P-tunnelを持つPTAを広告すべきです（SHOULD）。 SR-MPLSやSRv6のプロビジョニングとデータプレーンのサポートの判断の手順は、この文書の範囲外です。

A P-tunnel can be segmented or non-segmented (see Section 8 of [RFC6513]). When a P-tunnel is non-segmented, the PTA is created by PE router at the Root of an SR P2MP tree. For segmented P-tunnels, each segment can be instantiated by a different P-tunnel type. If a segment is instantiated using a P2MP tree, the router at the Root of an SR P2MP tree creates the PTA.

P-tunnelは、セグメント化されている場合とセグメント化されていない場合があります（[RFC6513]のSection 8を参照）。 P-tunnelがセグメント化されていない場合、PTAはSR P2MPツリーのルートにあるPEルーターによって作成されます。 セグメント化されたP-tunnelの場合、各セグメントは異なるP-tunnelの種類によってインスタンス化できます。 セグメントがP2MPツリーを使用してインスタンス化される場合、SR P2MPツリーのルートにあるルーターがPTAを作成します。

3.2.1.1. MPLS Label
3.2.1.1. MPLSラベル

When an SR P2MP P-tunnel is not shared across MVPNs, i.e., there is one-to-one association between an MVPN instance and an SR P2MP P-tunnel, the MPLS Label field is set to zero as per [RFC6514] for both SR-MPLS and SRv6. In this case, the SR-MPLS or SRv6 Tree-SID of the PTI of the SR P2MP Policy advertised in the P-tunnel is sufficient to identify the MVPN instance for delivering the payload.

SR P2MP P-tunnelがMVPN間で共有されない場合、つまりMVPNインスタンスとSR P2MP P-tunnelの間に1対1の関連付けがある場合、SR-MPLSとSRv6の両方について、[RFC6514]に従ってMPLS Labelフィールドは0に設定されます。 この場合、P-tunnelで広告されたSR P2MPポリシーのPTIのSR-MPLSまたはSRv6のTree-SIDだけで、ペイロードを配送するためのMVPNインスタンスを識別するのに十分です。

[RFC6514] allows a PE to aggregate two or more MVPNs onto one SR P2MP P-tunnel by advertising the same P-tunnel in PTA of A-D routes of different MVPNs. In this case, the MPLS Label field of the PTA is filled to provide a context bound to a specific MVPN instance as described in sections below. The value in this field is used by egress PEs to identify the MVPN instance for delivering the payload encapsulated in SR-MPLS or SRv6.

[RFC6514]では、PEが異なるMVPNのA-D経路のPTAで同じP-tunnelを広告することで、2つ以上のMVPNを1つのSR P2MP P-tunnelに集約することを認めています。 この場合、以下のセクションで説明するように、特定のMVPNインスタンスに結び付けられたコンテキストを提供するために、PTAのMPLS Labelフィールドが埋められます。 このフィールドの値は、SR-MPLSまたはSRv6でカプセル化されたペイロードを配送するためのMVPNインスタンスを識別するために、イグレスPEによって使用されます。

3.2.1.1.1. SR-MPLS
3.2.1.1.1. SR-MPLS

When an SR P2MP P-tunnel is shared across two or more MVPNs in an SR-MPLS domain, the MPLS Label field of a PTA advertised in an A-D route MUST contain an upstream-assigned MPLS label [RFC5331] [RFC6513] or a label assigned from a global context, such as the Domain-wide Common Block (DCB) as specified in [RFC9573], that the advertising PE has bound to the MVPN.

SR-MPLSドメインにおいてSR P2MP P-tunnelが2つ以上のMVPN間で共有される場合、A-D経路で広告されるPTAのMPLS Labelフィールドには、広告するPEがMVPNに結び付けた、上流で割り当てられたMPLSラベル[RFC5331] [RFC6513]、または[RFC9573]で規定されているドメイン全体の共通ブロック（Domain-wide Common Block: DCB）などのグローバルなコンテキストから割り当てられたラベルが含まれている必要があります（MUST）。

When an ingress PE steers the payload into a shared SR P2MP P-tunnel PTI, this MPLS label MUST be imposed before the MPLS label representing the Tree-SID. The trade-off of sharing an SR P2MP P-tunnel across MVPNs is that two MPLS labels have to be imposed on ingress and disposed on egress.

イングレスPEがペイロードを共有のSR P2MP P-tunnelのPTIに誘導する場合、このMPLSラベルは、Tree-SIDを表すMPLSラベルの前に付与されなければなりません（MUST）。 MVPN間でSR P2MP P-tunnelを共有することのトレードオフは、イングレスで2つのMPLSラベルを付与し、イグレスでそれらを取り除かなければならないことです。

The egress PEs of a shared SR P2MP P-tunnel use the MPLS label to determine the MVPN instance for delivering the payload.

共有のSR P2MP P-tunnelのイグレスPEは、ペイロードを配送するためのMVPNインスタンスを判断するためにMPLSラベルを使用します。

3.2.1.1.2. SRv6
3.2.1.1.2. SRv6

When an SR P2MP P-tunnel is shared across two or more MVPNs in an SRv6 domain [RFC8986], the MPLS Label field of a PTA advertised in an A-D route MUST contain an upstream-assigned SRv6 Multicast Service SID (Section 3.1) that the advertising PE has bound to the MVPN or an SRv6 Multicast Service SID assigned from a global context; this follows same concept of the DCB label as specified in [RFC9573]. The high-order 20 bits of the MPLS Label field carry the whole or a portion of the Function part of the SRv6 Multicast Service SID when the Transposition Scheme of encoding as defined in [RFC9252] is used. When using the Transposition Scheme, the Transposition Length of the SRv6 SID Structure Sub-Sub-TLV of the SRv6 Prefix-SID attribute (see below) MUST be less than or equal to 20 and less than or equal to the Function Length. When the Transposition Scheme is not used, the MPLS Label field MUST be set to zero as per [RFC6514], and Transposition Length MUST be zero.

SRv6ドメイン[RFC8986]においてSR P2MP P-tunnelが2つ以上のMVPN間で共有される場合、A-D経路で広告されるPTAのMPLS Labelフィールドには、広告するPEがMVPNに結び付けた、上流で割り当てられたSRv6マルチキャストサービスSID（Section 3.1）、またはグローバルなコンテキストから割り当てられたSRv6マルチキャストサービスSIDが含まれている必要があります（MUST）。後者は、[RFC9573]で規定されているDCBラベルと同じ概念に従います。[RFC9252]で定義されているエンコーディングの転置方式（Transposition Scheme）を使用する場合、MPLS Labelフィールドの上位20ビットは、SRv6マルチキャストサービスSIDのFunction部分の全体または一部を運びます。 転置方式を使用する場合、SRv6 Prefix-SID属性（以下を参照）のSRv6 SID Structure Sub-Sub-TLVのTransposition Lengthは、20以下かつFunction Length以下でなければなりません（MUST）。 転置方式を使用しない場合、[RFC6514]に従ってMPLS Labelフィールドは0に設定されなければなりません（MUST）。また、Transposition Lengthは0でなければなりません（MUST）。

The advertising ingress PE MUST attach a BGP Prefix-SID attribute [RFC8669] to Intra-AS I-PMSI, Inter-AS I-PMSI, or S-PMSI A-D routes with the SRv6 L3 Service TLV [RFC9252] to signal the SRv6 Multicast Service SID. The SRv6 SID Information Sub-TLV carries the SRv6 Multicast Service SID in the SRv6 SID Value field. The SRv6 Endpoint behavior of the SRv6 SID Information Sub-TLV encodes one of End.DTMC4, End.DTMC6, or End.DTMC46 code point values. The SRv6 SID Structure Sub-Sub-TLV encodes the structure of the SRv6 Multicast Service SID. If the Transposition Scheme is used, the offset and length of SRv6 Multicast Endpoint function of the SRv6 Multicast Service SID is set in the Transposition Length and Transposition Offset fields of this sub-sub-TLV. Otherwise, the Transposition Length and Offset fields MUST be set to zero. The locator (LOC) of an SRv6 Multicast Service SID, which is assigned from a global context, such as DCB, is outside the scope of this document.

広告するイングレスPEは、SRv6マルチキャストサービスSIDをシグナリングするために、SRv6 L3 Service TLV[RFC9252]を伴うBGP Prefix-SID属性[RFC8669]を、Intra-AS I-PMSI、Inter-AS I-PMSI、またはS-PMSIのA-D経路に付加しなければなりません（MUST）。 SRv6 SID Information Sub-TLVは、SRv6 SID ValueフィールドでSRv6マルチキャストサービスSIDを運びます。 SRv6 SID Information Sub-TLVのSRv6エンドポイントの振る舞いには、End.DTMC4、End.DTMC6、またはEnd.DTMC46のいずれかのコードポイント値がエンコードされます。 SRv6 SID Structure Sub-Sub-TLVは、SRv6マルチキャストサービスSIDの構造をエンコードします。 転置方式を使用する場合、SRv6マルチキャストサービスSIDのSRv6マルチキャストエンドポイントの機能のオフセットと長さが、このsub-sub-TLVのTransposition LengthフィールドとTransposition Offsetフィールドに設定されます。 そうでない場合、Transposition LengthフィールドとOffsetフィールドは0に設定されなければなりません（MUST）。 DCBなどのグローバルなコンテキストから割り当てられるSRv6マルチキャストサービスSIDのロケーター（LOC）は、この文書の範囲外です。

The advertising ingress PE, which is the Root node of the shared SR P2MP P-tunnel, MUST encapsulate a payload in an outer IPv6 header with an SRH in which the SRv6 Multicast Service SID MUST be the last segment in the segment list (note the SRv6 Multicast Service SID may be the only segment in the SRH). If the Transposition Scheme is used, the ingress PE MUST merge the Function part of the MPLS Label field of the PTA with the SRv6 SID in the SRv6 SID Information Sub-TLV using the Transposition Offset and Length fields from the SRv6 SID Structure Sub-Sub-TLV to create the SRv6 Multicast Service SID.

共有のSR P2MP P-tunnelのルートノードである広告するイングレスPEは、SRHを伴う外側のIPv6ヘッダーでペイロードをカプセル化しなければなりません（MUST）。また、そのSRHでは、SRv6マルチキャストサービスSIDがセグメントリストの最後のセグメントでなければなりません（MUST）（SRv6マルチキャストサービスSIDがSRH内の唯一のセグメントである場合もあることに注意してください）。 転置方式を使用する場合、イングレスPEは、SRv6 SID Structure Sub-Sub-TLVのTransposition OffsetフィールドとLengthフィールドを使用して、PTAのMPLS LabelフィールドのFunction部分をSRv6 SID Information Sub-TLV内のSRv6 SIDとマージし、SRv6マルチキャストサービスSIDを作成しなければなりません（MUST）。

An egress PE of the shared SR P2MP P-tunnel uses the SRv6 Multicast Service SID in the SRH to determine the MVPN instance in which the customer payload is to be delivered. The egress PE, in the role of Leaf or Bud node of the Replication segment associated with the shared SR P2MP P-tunnel tree, uses the "look at next SID in SRH" behavior [RFC9524] to process the SRv6 Multicast Service SID. An egress PE MUST NOT install the SRv6 Multicast Service SID in its Forwarding Information Base (FIB), i.e., it MUST NOT forward packets based on the Locator portion of the SRv6 Multicast Service SID because the SID is not significant on the ingress PE.

共有のSR P2MP P-tunnelのイグレスPEは、顧客のペイロードを配送すべきMVPNインスタンスを判断するために、SRH内のSRv6マルチキャストサービスSIDを使用します。 共有のSR P2MP P-tunnelツリーに関連付けられたレプリケーションセグメントのリーフノードまたはバッドノードの役割を担うイグレスPEは、SRv6マルチキャストサービスSIDを処理するために「look at next SID in SRH」の振る舞い[RFC9524]を使用します。 イグレスPEは、SRv6マルチキャストサービスSIDを自身の転送情報ベース（FIB）にインストールしてはなりません（MUST NOT）。つまり、SIDはイングレスPE上でしか意味を持たないため、SRv6マルチキャストサービスSIDのロケーター部分に基づいてパケットを転送してはなりません（MUST NOT）。

3.2.2. Auto-Discovery Procedures

3.2.2. 自動発見の手順

MVPN A-D procedures specified in [RFC6514] are used to advertise an SR P2MP P-tunnel and discover the Leaf nodes of the SR P2MP Policy associated with the P-tunnel. This section describes the processing of MVPN A-D routes to create, update, and tear down an SR P2MP Policy of an SR P2MP P-tunnel as described in Section 2.

[RFC6514]で規定されているMVPNのA-D手順は、SR P2MP P-tunnelを広告し、そのP-tunnelに関連付けられたSR P2MPポリシーのリーフノードを発見するために使用されます。 このセクションでは、Section 2で説明したように、SR P2MP P-tunnelのSR P2MPポリシーを作成、更新、および削除するためのMVPNのA-D経路の処理について説明します。

3.2.2.1. Creation of CP of SR P2MP Policy
3.2.2.1. SR P2MPポリシーのCPの作成

A PE interacts with an SR P2MP Policy module to create a CP, with optional traffic engineering constraints and an optional optimization objective, of an SR P2MP Policy when it originates an Intra-AS I-PMSI A-D route [RFC6514], an Inter-AS I-PMSI A-D route for an intra-AS segment [RFC6514], an S-PMSI A-D route [RFC6514], or a "wildcard" S-PMSI A-D route [RFC6625] with a PTA that has an SR P2MP P-tunnel type.

PEは、SR P2MP P-tunnelの種類を持つPTAを伴う、Intra-AS I-PMSI A-D経路[RFC6514]、AS内セグメントのためのInter-AS I-PMSI A-D経路[RFC6514]、S-PMSI A-D経路[RFC6514]、または「ワイルドカード」S-PMSI A-D経路[RFC6625]を生成するときに、SR P2MPポリシーモジュールとやり取りして、任意のトラフィックエンジニアリングの制約と任意の最適化の目標を伴うSR P2MPポリシーのCPを作成します。

The CP of the SR P2MP Policy associated with an SR P2MP P-tunnel is deleted from the SR P2MP Policy module when a PE withdraws the Intra-AS I-PMSI, Inter-AS I-PMSI, or S-PMSI A-D route advertising that P-tunnel.

SR P2MP P-tunnelに関連付けられたSR P2MPポリシーのCPは、PEがそのP-tunnelを広告しているIntra-AS I-PMSI、Inter-AS I-PMSI、またはS-PMSIのA-D経路を取り下げたときに、SR P2MPポリシーモジュールから削除されます。

When a PE originates an Inter-AS I-PMSI or an S-PMSI A-D route with a PTA that has an SR P2MP P-tunnel type, it MUST set the "Leaf Information Required" flag in the PTA.

PEが、SR P2MP P-tunnelの種類を持つPTAを伴うInter-AS I-PMSIまたはS-PMSIのA-D経路を生成する場合、PTAに「Leaf Information Required」フラグを設定しなければなりません（MUST）。

3.2.2.2. Discovery of Leaf Nodes
3.2.2.2. リーフノードの発見

An ingress PE that advertises an MVPN A-D route with a PTA that has an SR P2MP P-tunnel type discovers a Leaf node of the SR P2MP Policy associated with the SR P2MP P-tunnel when it imports an Intra-AS I-PMSI A-D route [RFC6514] or Leaf A-D route [RFC6514] from an egress PE. The ingress PE adds the egress PE as a Leaf node in the SR P2MP Policy module.

SR P2MP P-tunnelの種類を持つPTAを伴うMVPNのA-D経路を広告するイングレスPEは、イグレスPEからIntra-AS I-PMSI A-D経路[RFC6514]またはLeaf A-D経路[RFC6514]をインポートしたときに、そのSR P2MP P-tunnelに関連付けられたSR P2MPポリシーのリーフノードを発見します。 イングレスPEは、そのイグレスPEをSR P2MPポリシーモジュールのリーフノードとして追加します。

An ingress PE removes an egress PE from the Leaf set of the SR P2MP Policy when the egress PE withdraws the Intra-AS I-PMSI or the Leaf A-D route.

イングレスPEは、イグレスPEがIntra-AS I-PMSI経路またはLeaf A-D経路を取り下げたときに、そのイグレスPEをSR P2MPポリシーのリーフの集合から削除します。

An egress PE informs the SR P2MP Policy module to join the SR P2MP Policy as a Leaf or Bud node when it imports an Intra-AS I-PMSI A-D route, an Inter-AS I-PMSI A-D route, or an S-PMSI A-D route from an ingress PE that has a PTA with an SR P2MP P-tunnel type. The egress PE MUST originate a Leaf A-D route if the "Leaf Information Required" flag is set in the PTA.

イグレスPEは、SR P2MP P-tunnelの種類を持つPTAを伴うIntra-AS I-PMSI A-D経路、Inter-AS I-PMSI A-D経路、またはS-PMSI A-D経路をイングレスPEからインポートしたときに、リーフノードまたはバッドノードとしてSR P2MPポリシーに参加するようSR P2MPポリシーモジュールに通知します。 PTAに「Leaf Information Required」フラグが設定されている場合、イグレスPEはLeaf A-D経路を生成しなければなりません（MUST）。

An egress PE withdraws itself as a Leaf or Bud node of the SR P2MP Policy when the ingress PE withdraws an Intra-AS I-PMSI, Inter-AS I-PMSI, or S-PMSI A-D route. The egress PE MUST withdraw the Leaf A-D it had originated earlier in response to the "Leaf Information Required" flag in the PTA.

イグレスPEは、イングレスPEがIntra-AS I-PMSI、Inter-AS I-PMSI、またはS-PMSIのA-D経路を取り下げたときに、SR P2MPポリシーのリーフノードまたはバッドノードとしての自身を取り下げます。 イグレスPEは、PTAの「Leaf Information Required」フラグに応答して以前に生成したLeaf A-Dを取り下げなければなりません（MUST）。

3.3. MVPN with Ingress Replication over SR

3.3. SR上のイングレスレプリケーションを用いたMVPN

A PE can provide MVPN service using IR over SR. The payload is encapsulated in SR-MPLS or SRv6 at an ingress PE and replicated with each copy sent to an egress PE via unicast.

PEは、SR上のIRを使用してMVPNサービスを提供できます。 ペイロードは、イングレスPEでSR-MPLSまたはSRv6でカプセル化されて複製され、各コピーはユニキャストを介してイグレスPEに送信されます。

"Ingress Replication Tunnels in Multicast VPN" [RFC7988] specifies procedures that can be reused to provide MVPN service with IR in an SR domain. A PE advertises Intra-AS I-PMSI A-D, Inter-AS I-PMSI A-D, or Selective PMSI A-D and Leaf A-D routes with the PTA for IR. Egress PEs join as Leaf nodes using Intra-AS I-PMSI A-D or Leaf A-D routes. The procedures of [RFC7988] provide an MVPN IR service with best-effort unicast connectivity.

「Ingress Replication Tunnels in Multicast VPN」[RFC7988]は、SRドメインにおいてIRを用いたMVPNサービスを提供するために再利用できる手順を規定しています。 PEは、IRのためのPTAを伴うIntra-AS I-PMSI A-D、Inter-AS I-PMSI A-D、またはSelective PMSI A-DおよびLeaf A-Dの経路を広告します。 イグレスPEは、Intra-AS I-PMSI A-D経路またはLeaf A-D経路を使用してリーフノードとして参加します。 [RFC7988]の手順は、ベストエフォートのユニキャスト接続性を伴うMVPN IRサービスを提供します。

This document adds procedures for providing an MVPN IR service with an SLA from an ingress PE to an egress PE both for SR-MPLS and SRv6. This document extends the BGP Update message of AFI/SAFI 1/129 (MVPN-IPv4) and 2/129 (MVPN-IPv6) to carry the Color Extended Community as specified in [RFC9012] and the Color-Only Type extension specified in Section 3 of [RFC9830]. An egress PE colors the Leaf or Intra-AS I-PMSI A-D route with a Color Extended Community. The ingress PE replicates MVPN customer payload to the egress PE by steering it into an SR-TE policy according to Section 8 of [RFC9256]. The ingress PE encapsulates the payload packet into a segment list of the matching SR-TE policy to the egress PE along with the IR MPLS label or SRv6 Multicast Service SID received from the egress PE.

この文書は、SR-MPLSとSRv6の両方について、イングレスPEからイグレスPEへのSLAを伴うMVPN IRサービスを提供するための手順を追加します。 この文書は、AFI/SAFI 1/129（MVPN-IPv4）と2/129（MVPN-IPv6）のBGP Updateメッセージを拡張して、[RFC9012]で規定されているColor拡張コミュニティーと、[RFC9830]のSection 3で規定されているColor-Only Type拡張を運ぶようにします。 イグレスPEは、Leaf A-D経路またはIntra-AS I-PMSI A-D経路にColor拡張コミュニティーで色を付けます。 イングレスPEは、[RFC9256]のSection 8に従ってMVPNの顧客のペイロードをSR-TEポリシーに誘導することで、それをイグレスPEに複製します。 イングレスPEは、ペイロードのパケットを、イグレスPEへの一致するSR-TEポリシーのセグメントリストに、イグレスPEから受信したIR MPLSラベルまたはSRv6マルチキャストサービスSIDとともにカプセル化します。

Note that the Color Extended Community is not used with an MVPN SR P2MP P-tunnel. For MVPN with an SR P2MP P-tunnel, the ingress PE dictates the traffic engineering treatment by specifying the constraints and the metric optimization in the CP of the SR P2MP Policy corresponding to the P-tunnel on the ingress PE. This is necessary because packets are replicated in the PTI; therefore, it is not possible to have differing traffic engineering treatment towards each egress PE (Leaf node) of the PTI.

Color拡張コミュニティーは、MVPNのSR P2MP P-tunnelでは使用されないことに注意してください。 SR P2MP P-tunnelを用いたMVPNでは、イングレスPEは、イングレスPE上のP-tunnelに対応するSR P2MPポリシーのCPで制約とメトリックの最適化を指定することで、トラフィックエンジニアリングの扱いを指示します。 これが必要なのは、パケットがPTI内で複製されるため、PTIの各イグレスPE（リーフノード）に向けて異なるトラフィックエンジニアリングの扱いをすることができないからです。

3.3.1. SR-MPLS

3.3.1. SR-MPLS

The PTA carried in Intra-AS I-PMSI A-D, Inter-AS I-PMSI A-D, S-PMSI A-D, and Leaf A-D routes is constructed as specified in [RFC7988].

Intra-AS I-PMSI A-D、Inter-AS I-PMSI A-D、S-PMSI A-D、およびLeaf A-Dの経路で運ばれるPTAは、[RFC7988]で規定されているとおりに構築されます。

MVPN IR service with SLA over SR-MPLS data plane can be provided by using the Color Extended Community as described above. Suppose an egress PE, say PE2, sends Leaf A-D route with Extended Color Community C1 with Color-Only Type 0 and IR label L10 to the ingress PE1. Assume the segment list of SR-TE policy (C1, PE2) at ingress PE1 is <L1, L2, L3>. PE1 will encapsulate the MVPN payload into the MPLS label stack <L1, L2, L3, L10> with L10 as the Bottom-of-Stack (BoS) label.

SR-MPLSデータプレーン上のSLAを伴うMVPN IRサービスは、上で説明したようにColor拡張コミュニティーを使用することで提供できます。 イグレスPE、たとえばPE2が、Color-Only Type 0を伴うColor拡張コミュニティーC1とIRラベルL10を含むLeaf A-D経路をイングレスPE1に送信するとします。 イングレスPE1におけるSR-TEポリシー（C1, PE2）のセグメントリストが<L1, L2, L3>であると仮定します。 PE1は、L10をボトムオブスタック（BoS）ラベルとして、MVPNのペイロードをMPLSラベルスタック<L1, L2, L3, L10>にカプセル化します。

3.3.2. SRv6

3.3.2. SRv6

The procedures specified in [RFC7988], with the modifications defined in this section, are used to provide MVPN IR service over SRv6.

このセクションで定義する変更を加えた[RFC7988]で規定されている手順が、SRv6上でMVPN IRサービスを提供するために使用されます。

The PTA carried in Intra-AS I-PMSI A-D, Inter-AS I-PMSI A-D, Selective PMSI A-D, and Leaf A-D routes is constructed as specified in [RFC7988] with the following modifications:

Intra-AS I-PMSI A-D、Inter-AS I-PMSI A-D、Selective PMSI A-D、およびLeaf A-Dの経路で運ばれるPTAは、次の変更を加えて[RFC7988]で規定されているとおりに構築されます：

  • Tunnel Type: "Ingress Replication" as per [RFC6514].

  • MPLS Label: The high-order 20 bits of this field carry the whole or a portion of the Function part of the SRv6 Multicast Service SID when the Transposition Scheme is used for encoding as defined in [RFC9252]. When using the Transposition Scheme, the Transposition Length of the SRv6 SID Structure Sub-Sub-TLV of the SRv6 Prefix-SID attribute (see below) MUST be less than or equal to 20 and less than or equal to the Function Length. When the Transposition Scheme is not used, the MPLS Label field MUST be set to zero, and Transposition Length MUST be zero.

  • Tunnel Type：[RFC6514]に従った「Ingress Replication」。

  • MPLS Label：[RFC9252]で定義されているエンコーディングのための転置方式を使用する場合、このフィールドの上位20ビットは、SRv6マルチキャストサービスSIDのFunction部分の全体または一部を運びます。 転置方式を使用する場合、SRv6 Prefix-SID属性（以下を参照）のSRv6 SID Structure Sub-Sub-TLVのTransposition Lengthは、20以下かつFunction Length以下でなければなりません（MUST）。 転置方式を使用しない場合、MPLS Labelフィールドは0に設定されなければなりません（MUST）。また、Transposition Lengthは0でなければなりません（MUST）。

Sections RFC7988 and RFC7988 of [RFC7988] describe considerations and procedures for allocating MPLS labels for IR P-tunnels. These considerations also apply to allocation of a SRv6 Multicast Service SID for SRv6 IR.

[RFC7988]のセクションRFC7988とRFC7988では、IRのP-tunnelのためのMPLSラベルの割り当てに関する考慮事項と手順を説明しています。 これらの考慮事項は、SRv6 IRのためのSRv6マルチキャストサービスSIDの割り当てにも適用されます。

To join an SRv6 IR P-tunnel advertised in the PTA of Intra-AS I-PMSI A-D, Inter-AS I-PMSI A-D, or Selective S-PMSI A-D routes, an egress PE constructs a Leaf A-D or Intra-AS I-PMSI A-D route as described in [RFC7988] with the modified PTA above. The egress PE MUST attach a BGP Prefix-SID attribute [RFC8669] with a Leaf A-D or Intra-AS I-PMSI A-D route with the SRv6 L3 Service TLV [RFC9252] to signal the SRv6 Multicast Service SID (Section 3.1). The SRv6 SID Information Sub-TLV carries the SRv6 Multicast Service SID in the SRv6 SID Value field. The SRv6 Endpoint behavior of the SRv6 SID Information Sub-TLV MUST encode one of the End.DTMC4, End.DTMC6, or End.DTMC46 code point values. The SRv6 SID Structure Sub-Sub-TLV encodes the structure of the SRv6 Multicast Service SID. If the Transposition Scheme is used, the offset and length of SRv6 Multicast Endpoint function of the SRv6 Multicast Service SID is set in the Transposition Length and Transposition Offset fields of this sub-sub-TLV. Otherwise, the Transposition Length and Offset fields MUST be set to zero. The BGP Prefix SID attribute with the SRv6 L3 Service TLV in an Intra-AS I-PMSI or Leaf A-D route indicates to the ingress PE that the egress PE supports SRv6.

Intra-AS I-PMSI A-D、Inter-AS I-PMSI A-D、またはSelective S-PMSI A-Dの経路のPTAで広告されたSRv6 IRのP-tunnelに参加するために、イグレスPEは、上記の変更されたPTAを伴うLeaf A-D経路またはIntra-AS I-PMSI A-D経路を[RFC7988]で説明されているように構築します。 イグレスPEは、SRv6マルチキャストサービスSID（Section 3.1）をシグナリングするために、SRv6 L3 Service TLV[RFC9252]を伴うBGP Prefix-SID属性[RFC8669]を、Leaf A-D経路またはIntra-AS I-PMSI A-D経路に付加しなければなりません（MUST）。 SRv6 SID Information Sub-TLVは、SRv6 SID ValueフィールドでSRv6マルチキャストサービスSIDを運びます。 SRv6 SID Information Sub-TLVのSRv6エンドポイントの振る舞いには、End.DTMC4、End.DTMC6、またはEnd.DTMC46のいずれかのコードポイント値をエンコードしなければなりません（MUST）。 SRv6 SID Structure Sub-Sub-TLVは、SRv6マルチキャストサービスSIDの構造をエンコードします。 転置方式を使用する場合、SRv6マルチキャストサービスSIDのSRv6マルチキャストエンドポイントの機能のオフセットと長さが、このsub-sub-TLVのTransposition LengthフィールドとTransposition Offsetフィールドに設定されます。 そうでない場合、Transposition LengthフィールドとOffsetフィールドは0に設定されなければなりません（MUST）。 Intra-AS I-PMSI経路またはLeaf A-D経路におけるSRv6 L3 Service TLVを伴うBGP Prefix SID属性は、イグレスPEがSRv6をサポートしていることをイングレスPEに示します。

The SRv6 Multicast Service SID MUST be routable within the AS of the egress PE. As per [RFC7988], the ingress PE uses the Tunnel Identifier of PTA to determine the unicast tunnel to use in order to send data to the egress PE. For SRv6 IR, the ingress PE MUST use the SRv6 Multicast Service SID to determine the unicast tunnel to be used. For best-effort MVPN IR service or SLA-based MVPN IR service using the IGP Flexible Algorithm, the ingress PE MUST encapsulate the payload in an outer IPv6 header, with the SRv6 Multicast Service SID provided by the egress PE used as the destination address. If the Transposition Scheme is used, the ingress PE MUST merge the Function part of the MPLS Label field of the PTA with SRv6 SID in the SRv6 SID Information Sub-TLV using the Transposition Offset and Length fields from the SRv6 SID Structure Sub-Sub-TLV to create the SRv6 Multicast Service SID.

SRv6マルチキャストサービスSIDは、イグレスPEのAS内でルーティング可能でなければなりません（MUST）。 [RFC7988]に従い、イングレスPEは、イグレスPEにデータを送信するために使用するユニキャストトンネルを判断するために、PTAのTunnel Identifierを使用します。 SRv6 IRの場合、イングレスPEは、使用するユニキャストトンネルを判断するためにSRv6マルチキャストサービスSIDを使用しなければなりません（MUST）。 ベストエフォートのMVPN IRサービス、またはIGP Flexible Algorithmを使用するSLAベースのMVPN IRサービスの場合、イングレスPEは、イグレスPEによって提供されたSRv6マルチキャストサービスSIDを宛先アドレスとして使用して、外側のIPv6ヘッダーでペイロードをカプセル化しなければなりません（MUST）。 転置方式を使用する場合、イングレスPEは、SRv6 SID Structure Sub-Sub-TLVのTransposition OffsetフィールドとLengthフィールドを使用して、PTAのMPLS LabelフィールドのFunction部分をSRv6 SID Information Sub-TLV内のSRv6 SIDとマージし、SRv6マルチキャストサービスSIDを作成しなければなりません（MUST）。

MVPN IR service with SLA over SRv6 can be provided by using the Color Extended Community as described above. Suppose an egress PE, say PE2, sends Leaf A-D route with Extended Color community C1 with Color-Only Type 0 and SRv6 Multicast Service SID S10 to ingress PE1. Assume the segment list of the SR-TE policy (C1, PE2) at ingress PE1 is <S1, S2, S3>. PE1 will encapsulate a payload into an IPv6 header with SRH (PE1, S1) (S10, S3, S2; SL=3) (payload).

SRv6上のSLAを伴うMVPN IRサービスは、上で説明したようにColor拡張コミュニティーを使用することで提供できます。 イグレスPE、たとえばPE2が、Color-Only Type 0を伴うColor拡張コミュニティーC1とSRv6マルチキャストサービスSID S10を含むLeaf A-D経路をイングレスPE1に送信するとします。 イングレスPE1におけるSR-TEポリシー（C1, PE2）のセグメントリストが<S1, S2, S3>であると仮定します。 PE1は、ペイロードをSRHを伴うIPv6ヘッダー (PE1, S1) (S10, S3, S2; SL=3) (payload) にカプセル化します。

4. EVPN with SR

4. SRを用いたEVPN

BGP MPLS-Based EVPN, specified in [RFC7432], specifies the IMET route to support BUM traffic. This IMET route is the equivalent of the MVPN Intra-AS I-PMSI route and is advertised with a PTA as specified in [RFC6514] to advertise the inclusive P-tunnels. [RFC9252] specifies procedures for IMET routes with IR over SRv6.

[RFC7432]で規定されているBGP MPLSベースのEVPNは、BUMトラフィックをサポートするためのIMET経路を規定しています。 このIMET経路はMVPNのIntra-AS I-PMSI経路に相当するもので、包括的なP-tunnelを広告するために、[RFC6514]で規定されているPTAとともに広告されます。 [RFC9252]は、SRv6上のIRを用いたIMET経路の手順を規定しています。

[RFC9572] updates the EVPN BUM procedures to support selective P-tunnels. It defines new BGP route types that are advertised with a PTA, including the S-PMSI A-D and Leaf A-D routes. The S-PMSI and Leaf A-D routes of [RFC9572] are analogous to MVPN S-PMSI and Leaf A-D routes [RFC6514]. Note that support of Inter-AS and Inter-Region segmentation procedures in [RFC9572] with SR P2MP P-tunnels are out of scope of this document.

[RFC9572]は、選択的なP-tunnelをサポートするためにEVPNのBUM手順を更新しています。 これは、S-PMSI A-D経路やLeaf A-D経路を含む、PTAとともに広告される新しいBGP経路タイプを定義しています。 [RFC9572]のS-PMSI経路とLeaf A-D経路は、MVPNのS-PMSI経路とLeaf A-D経路[RFC6514]に類似しています。 SR P2MP P-tunnelを用いた[RFC9572]のAS間および領域間のセグメント化の手順のサポートは、この文書の範囲外であることに注意してください。

Inclusive and selective P-tunnels can be instantiated using SR P2MP trees or IR over SR.

包括的なP-tunnelと選択的なP-tunnelは、SR P2MPツリーまたはSR上のIRを使用してインスタンス化できます。

4.1. EVPN with SR P2MP P-Tunnel

4.1. SR P2MP P-tunnelを用いたEVPN

This section specifies modifications to procedures of [RFC7432] and [RFC9572] for SR P2MP P-tunnels. The IMET, S-PMSI, and Leaf A-D routes have the PTA that specifies the SR P2MP tree P-tunnel. In this section, the term "SR P2MP" refers to both SR-MPLS and SRv6 data planes.

このセクションでは、SR P2MP P-tunnelのための[RFC7432]と[RFC9572]の手順の変更を規定します。 IMET、S-PMSI、およびLeaf A-Dの経路は、SR P2MPツリーのP-tunnelを指定するPTAを持ちます。 このセクションでは、「SR P2MP」という用語は、SR-MPLSとSRv6の両方のデータプレーンを指します。

4.1.1. PMSI Tunnel Attribute for SR P2MP P-Tunnel

4.1.1. SR P2MP P-tunnelのためのPMSIトンネル属性

A PTA for an SR P2MP P-tunnel is constructed as specified in Section 3.2.1, except the MPLS Label and Flags fields are filled as specified in Sections 4.1.1.1 and 4.1.3, respectively.

SR P2MP P-tunnelのためのPTAは、MPLS LabelフィールドとFlagsフィールドがそれぞれセクション4.1.1.1と4.1.3で規定されているように埋められることを除いて、Section 3.2.1で規定されているように構築されます。

4.1.1.1. MPLS Label

4.1.1.1.1. SR-MPLS
4.1.1.1.1. SR-MPLS

When an SR P2MP P-tunnel is not shared across MVPNs, i.e., there is one-to-one association between an EVI and an SR P2MP P-tunnel, the MPLS Label field is set to zero as per [RFC6514]. In this case, the SR-MPLS Tree-SID of the PTI of the SR P2MP Policy advertised in the P-tunnel is sufficient to identify the MVPN instance for delivering the payload.

SR P2MP P-tunnelがMVPN間で共有されない場合、つまりEVIとSR P2MP P-tunnelの間に1対1の関連付けがある場合、[RFC6514]に従ってMPLS Labelフィールドは0に設定されます。 この場合、P-tunnelで広告されたSR P2MPポリシーのPTIのSR-MPLSのTree-SIDだけで、ペイロードを配送するためのMVPNインスタンスを識別するのに十分です。

[RFC7432] and [RFC9572] allow a PE to aggregate two or more EVIs onto one SR P2MP P-tunnel by advertising the same P-tunnel in the PTA of A-D routes of different EVIs. When an SR P2MP P-tunnel is shared across two or more EVIs in an SR-MPLS domain, the MPLS Label field of a PTA advertised in an EVPN A-D route MUST contain an upstream-assigned MPLS label [RFC5331] [RFC6513] or a label assigned from a global context, such as DCB as specified in [RFC9573], that the advertising PE has bound to the EVI. The egress PE uses this label as context to identify the specific EVI for delivering the EVPN payload encapsulated in SR-MPLS. When an ingress PE steers the payload into a shared SR P2MP P-tunnel PTI, this MPLS label MUST be imposed before the MPLS label representing the Tree-SID.

[RFC7432]と[RFC9572]では、PEが異なるEVIのA-D経路のPTAで同じP-tunnelを広告することで、2つ以上のEVIを1つのSR P2MP P-tunnelに集約することを認めています。 SR-MPLSドメインにおいてSR P2MP P-tunnelが2つ以上のEVI間で共有される場合、EVPNのA-D経路で広告されるPTAのMPLS Labelフィールドには、広告するPEがEVIに結び付けた、上流で割り当てられたMPLSラベル[RFC5331] [RFC6513]、または[RFC9573]で規定されているDCBなどのグローバルなコンテキストから割り当てられたラベルが含まれている必要があります（MUST）。 イグレスPEは、SR-MPLSでカプセル化されたEVPNのペイロードを配送するための特定のEVIを識別するためのコンテキストとして、このラベルを使用します。 イングレスPEがペイロードを共有のSR P2MP P-tunnelのPTIに誘導する場合、このMPLSラベルは、Tree-SIDを表すMPLSラベルの前に付与されなければなりません（MUST）。

4.1.1.1.2. SRv6
4.1.1.1.2. SRv6

For SRv6 P2MP, an EVI is identified by an SRv6 SID encoded in the SRH of an IPv6-encapsulated packet from the ingress PE as described later in this section. This is required even if the SR P2MP P-tunnel is not shared across EVIs.

SRv6 P2MPの場合、このセクションで後述するように、EVIは、イングレスPEからのIPv6でカプセル化されたパケットのSRHにエンコードされたSRv6 SIDによって識別されます。 これは、SR P2MP P-tunnelがEVI間で共有されない場合でも必要です。

The advertising ingress PE MUST attach a BGP Prefix-SID attribute [RFC8669] to IMET [RFC9252] or S-PMSI [RFC9572] A-D routes with the SRv6 L2 Service TLV [RFC9252]. The SRv6 SID Information Sub-TLV carries the SID in the SRv6 SID Value field. The SRv6 Endpoint behavior of the SRv6 SID Information Sub-TLV SHOULD be END.DT2M [RFC8986] as per Section 6.3 of [RFC9252]. The SRv6 SID Structure Sub-Sub-TLV encodes the structure of SID. If the Transposition Scheme is used, the offset and length of the SID is set in the Transposition Length and Transposition Offset fields of this sub-sub-TLV. Otherwise, the Transposition Length and Offset fields MUST be set to zero. The LOC of a SID, which is assigned from a global context, such as DCB, is outside the scope of this document.

広告するイングレスPEは、SRv6 L2 Service TLV[RFC9252]を伴うBGP Prefix-SID属性[RFC8669]を、IMET[RFC9252]またはS-PMSI[RFC9572]のA-D経路に付加しなければなりません（MUST）。 SRv6 SID Information Sub-TLVは、SRv6 SID ValueフィールドでSIDを運びます。 SRv6 SID Information Sub-TLVのSRv6エンドポイントの振る舞いは、[RFC9252]のSection 6.3に従ってEND.DT2M[RFC8986]であるべきです（SHOULD）。 SRv6 SID Structure Sub-Sub-TLVは、SIDの構造をエンコードします。 転置方式を使用する場合、SIDのオフセットと長さが、このsub-sub-TLVのTransposition LengthフィールドとTransposition Offsetフィールドに設定されます。 そうでない場合、Transposition LengthフィールドとOffsetフィールドは0に設定されなければなりません（MUST）。 DCBなどのグローバルなコンテキストから割り当てられるSIDのLOCは、この文書の範囲外です。

The MPLS Label field of a PTA advertised in an A-D route MUST contain an upstream-assigned SRv6 SID that the advertising PE has bound to the EVI or an SRv6 SID assigned from a global context; this follows same concept of the DCB label as specified in [RFC9573]. The high-order 20 bits of the MPLS Label field carry the whole or a portion of the Function part of the SRv6 SID when the Transposition Scheme of encoding as defined in [RFC9252] is used. When using the Transposition Scheme, the Transposition Length of the SRv6 SID Structure Sub-Sub-TLV of the SRv6 Prefix-SID attribute MUST be less than or equal to 20 and less than or equal to the Function Length. When the Transposition Scheme is not used, the MPLS Label field MUST be set to zero as per [RFC6514], and Transposition Length MUST be zero.

A-D経路で広告されるPTAのMPLS Labelフィールドには、広告するPEがEVIに結び付けた、上流で割り当てられたSRv6 SID、またはグローバルなコンテキストから割り当てられたSRv6 SIDが含まれている必要があります（MUST）。後者は、[RFC9573]で規定されているDCBラベルと同じ概念に従います。[RFC9252]で定義されているエンコーディングの転置方式を使用する場合、MPLS Labelフィールドの上位20ビットは、SRv6 SIDのFunction部分の全体または一部を運びます。 転置方式を使用する場合、SRv6 Prefix-SID属性のSRv6 SID Structure Sub-Sub-TLVのTransposition Lengthは、20以下かつFunction Length以下でなければなりません（MUST）。 転置方式を使用しない場合、[RFC6514]に従ってMPLS Labelフィールドは0に設定されなければなりません（MUST）。また、Transposition Lengthは0でなければなりません（MUST）。

The advertising ingress PE, which is the Root node of the SR P2MP P-tunnel, MUST encapsulate a payload in an outer IPv6 header with an SRH in which the SRv6 SID (advertised in the BGP Prefix-SID attribute) MUST be the last segment in the segment list (note the SRv6 SID may be the only segment in the SRH). If the Transposition Scheme is used, the ingress PE MUST merge the Function part of the MPLS Label field of the PTA with the SRv6 SID in the SRv6 SID Information Sub-TLV using the Transposition Offset and Length fields from the SRv6 SID Structure Sub-Sub-TLV to create the SRv6 SID. When ESI-based split-horizon filtering is used, the Arg.FE2 (see Section 4.1.2.2) SHOULD be merged with the SRv6 SID by doing a bitwise logical OR operation to create the complete SRv6 SID encoded in the SRH on the ingress PE.

SR P2MP P-tunnelのルートノードである広告するイングレスPEは、SRHを伴う外側のIPv6ヘッダーでペイロードをカプセル化しなければなりません（MUST）。また、そのSRHでは、（BGP Prefix-SID属性で広告された）SRv6 SIDがセグメントリストの最後のセグメントでなければなりません（MUST）（SRv6 SIDがSRH内の唯一のセグメントである場合もあることに注意してください）。 転置方式を使用する場合、イングレスPEは、SRv6 SID Structure Sub-Sub-TLVのTransposition OffsetフィールドとLengthフィールドを使用して、PTAのMPLS LabelフィールドのFunction部分をSRv6 SID Information Sub-TLV内のSRv6 SIDとマージし、SRv6 SIDを作成しなければなりません（MUST）。 ESIベースのスプリットホライズンフィルタリングを使用する場合、イングレスPE上でSRHにエンコードされる完全なSRv6 SIDを作成するために、ビット単位の論理和演算を行うことで、Arg.FE2（Section 4.1.2.2を参照）をSRv6 SIDとマージすべきです（SHOULD）。

An egress PE of the SR P2MP P-tunnel uses the SRv6 SID in the SRH to determine the EVI in which the customer payload is to be delivered. The egress PE, in role of Leaf or Bud node of the Replication segment associated with the SR P2MP P-tunnel tree, uses "look at next SID in SRH" [RFC9524] behavior to process the SRv6 SID. An egress PE MUST NOT install the SRv6 SID in its FIB, i.e., it MUST NOT forward packets based on the Locator portion of the SRv6 SID. The Arg.FE2 of the SID, if present, is used for ESI-based split-horizon filtering as specified in Section 4.1.2.2.

SR P2MP P-tunnelのイグレスPEは、顧客のペイロードを配送すべきEVIを判断するために、SRH内のSRv6 SIDを使用します。 SR P2MP P-tunnelツリーに関連付けられたレプリケーションセグメントのリーフノードまたはバッドノードの役割を担うイグレスPEは、SRv6 SIDを処理するために「look at next SID in SRH」の振る舞い[RFC9524]を使用します。 イグレスPEは、SRv6 SIDを自身のFIBにインストールしてはなりません（MUST NOT）。つまり、SRv6 SIDのロケーター部分に基づいてパケットを転送してはなりません（MUST NOT）。 SIDのArg.FE2が存在する場合、それはSection 4.1.2.2で規定されているESIベースのスプリットホライズンフィルタリングに使用されます。

4.1.2. Split-Horizon Filtering for ES Multihoming

4.1.2. ESマルチホーミングのためのスプリットホライズンフィルタリング

EVPN requires split-horizon filtering with ES multihoming in order to prevent duplicate BUM traffic as described in Section 8.3 of [RFC7432]. This section describes split-horizon filtering procedures with SR P2MP P-tunnels.

EVPNでは、[RFC7432]のSection 8.3で説明されているように、重複したBUMトラフィックを防ぐために、ESマルチホーミングにおいてスプリットホライズンフィルタリングが必要です。 このセクションでは、SR P2MP P-tunnelを用いたスプリットホライズンフィルタリングの手順について説明します。

4.1.2.1. SR-MPLS Filtering
4.1.2.1. SR-MPLSのフィルタリング

The split-horizon procedures specified for P2MP MPLS Label Switched Paths (LSPs) in Section 8.3.1.2 of [RFC7432] are sufficient for SR P2MP P-tunnels. Note for shared SR P2MP P-tunnels, the ESI label is at the bottom of the label stack, followed by an EVI context label and finally the Tree-SID label of the PTI associated with P-tunnel at the top in SR-MPLS encapsulation.

[RFC7432]のSection 8.3.1.2でP2MP MPLSラベルスイッチドパス（LSP）について規定されているスプリットホライズンの手順は、SR P2MP P-tunnelにも十分です。 共有のSR P2MP P-tunnelの場合、SR-MPLSのカプセル化では、ESIラベルがラベルスタックの最下部にあり、その上にEVIのコンテキストラベル、そして最後に最上部にP-tunnelに関連付けられたPTIのTree-SIDラベルがあることに注意してください。

4.1.2.2. SRv6 Filtering
4.1.2.2. SRv6のフィルタリング

For SRv6, the Arg.FE2 argument of End.DT2M SRv6 Endpoint behavior [RFC8986] is used for ESI-based split-horizon filtering. For an SR P2MP P-tunnel, the Arg.FE2 SID argument is an upstream-assigned value assigned by an ingress PE and identifies an ES of origin. This SID Argument is analogous to the upstream-assigned ESI MPLS label specified in Section 8.3 of [RFC7432]. The Arg.FE2 is signaled in the ESI Label field of the ESI Label extended community [RFC7432] and a BGP Prefix-SID attribute with an Ethernet A-D per ES route as specified in Section 6.1.1 of [RFC9252] and expanded further in [RFC9819].

SRv6の場合、ESIベースのスプリットホライズンフィルタリングには、End.DT2M SRv6エンドポイントの振る舞い[RFC8986]のArg.FE2引数が使用されます。 SR P2MP P-tunnelの場合、Arg.FE2 SID引数は、イングレスPEによって割り当てられる上流で割り当てられた値であり、発信元のESを識別します。 このSID引数は、[RFC7432]のSection 8.3で規定されている上流で割り当てられたESI MPLSラベルに類似しています。Arg.FE2は、[RFC9252]のSection 6.1.1で規定され、[RFC9819]でさらに拡張されているように、ESごとのイーサネットA-D経路とともに、ESI Label拡張コミュニティー[RFC7432]のESI LabelフィールドとBGP Prefix-SID属性でシグナリングされます。

The advertised Arg.FE2 is encoded with the SRv6 SID in the SRH by the ingress PE as described in Section 4.1.1.1.2. The egress PE uses the Arg.FE2 of the SRv6 SID, if present, to perform ESI-based split-horizon filtering as specified for the End.DT2M forwarding behavior in Section 4.12 of [RFC8986].

広告されたArg.FE2は、Section 4.1.1.1.2で説明したように、イングレスPEによってSRH内のSRv6 SIDとともにエンコードされます。 イグレスPEは、SRv6 SIDのArg.FE2が存在する場合、それを使用して、[RFC8986]のSection 4.12のEnd.DT2Mの転送の振る舞いについて規定されているとおりにESIベースのスプリットホライズンフィルタリングを実行します。

4.1.3. Auto-Discovery Procedures

4.1.3. 自動発見の手順

EVPN A-D procedures specified in [RFC7432] and [RFC9572] are used to advertise an SR P2MP P-tunnel and discover the Leaf nodes of the SR P2MP Policy associated with the P-tunnel. This section describes the processing of EVPN A-D routes to create, update, and tear down an SR P2MP Policy of an SR P2MP P-tunnel as described in Section 2.

[RFC7432]と[RFC9572]で規定されているEVPNのA-D手順は、SR P2MP P-tunnelを広告し、そのP-tunnelに関連付けられたSR P2MPポリシーのリーフノードを発見するために使用されます。 このセクションでは、Section 2で説明したように、SR P2MP P-tunnelのSR P2MPポリシーを作成、更新、および削除するためのEVPNのA-D経路の処理について説明します。

4.1.3.1. Creation of CP of SR P2MP Policy
4.1.3.1. SR P2MPポリシーのCPの作成

A PE interacts with an SR P2MP Policy module to create a CP, with optional traffic engineering constraints and an optional optimization objective, of an SR P2MP Policy when it originates an IMET A-D route [RFC7432] or an S-PMSI A-D route [RFC9572], with a PTA that has an SR P2MP P-tunnel type.

PEは、SR P2MP P-tunnelの種類を持つPTAを伴うIMET A-D経路[RFC7432]またはS-PMSI A-D経路[RFC9572]を生成するときに、SR P2MPポリシーモジュールとやり取りして、任意のトラフィックエンジニアリングの制約と任意の最適化の目標を伴うSR P2MPポリシーのCPを作成します。

The CP of the SR P2MP Policy associated with an SR P2MP P-tunnel is deleted from the SR P2MP Policy module when a PE withdraws the IMET or S-PMSI A-D route advertising that P-tunnel.

SR P2MP P-tunnelに関連付けられたSR P2MPポリシーのCPは、PEがそのP-tunnelを広告しているIMETまたはS-PMSIのA-D経路を取り下げたときに、SR P2MPポリシーモジュールから削除されます。

When a PE originates an S-PMSI A-D route with a PTA that has an SR P2MP P-tunnel type, it MUST set the "Leaf Information Required" flag in the PTA.

PEが、SR P2MP P-tunnelの種類を持つPTAを伴うS-PMSI A-D経路を生成する場合、PTAに「Leaf Information Required」フラグを設定しなければなりません（MUST）。

4.1.3.2. Discovery of Leaf Nodes
4.1.3.2. リーフノードの発見

An ingress PE that advertises an EVPN A-D route with a PTA that has an SR P2MP P-tunnel type discovers a Leaf node of the SR P2MP Policy associated with the SR P2MP P-tunnel when it imports an IMET A-D route [RFC7432] or Leaf A-D route [RFC9572] from an egress PE. The ingress PE adds the egress PE as a Leaf node in the SR P2MP Policy module.

SR P2MP P-tunnelの種類を持つPTAを伴うEVPNのA-D経路を広告するイングレスPEは、イグレスPEからIMET A-D経路[RFC7432]またはLeaf A-D経路[RFC9572]をインポートしたときに、そのSR P2MP P-tunnelに関連付けられたSR P2MPポリシーのリーフノードを発見します。 イングレスPEは、そのイグレスPEをSR P2MPポリシーモジュールのリーフノードとして追加します。

An ingress PE removes an egress PE from the Leaf set of the SR P2MP Policy when the egress PE withdraws the IMET A-D or the Leaf A-D route.

イングレスPEは、イグレスPEがIMET A-D経路またはLeaf A-D経路を取り下げたときに、そのイグレスPEをSR P2MPポリシーのリーフの集合から削除します。

An egress PE informs the SR P2MP Policy module to join the SR P2MP Policy as a Leaf or Bud node when it imports an IMET A-D route or an S-PMSI A-D route from an ingress PE that has a PTA with an SR P2MP P-tunnel type. The egress PE MUST originate a Leaf A-D route if the "Leaf Information Required" flag is set in the PTA.

イグレスPEは、SR P2MP P-tunnelの種類を持つPTAを伴うIMET A-D経路またはS-PMSI A-D経路をイングレスPEからインポートしたときに、リーフノードまたはバッドノードとしてSR P2MPポリシーに参加するようSR P2MPポリシーモジュールに通知します。 PTAに「Leaf Information Required」フラグが設定されている場合、イグレスPEはLeaf A-D経路を生成しなければなりません（MUST）。

An egress PE withdraws itself as a Leaf or Bud node of the SR P2MP Policy when the ingress PE withdraws an IMET or an S-PMSI A-D route. The egress PE MUST withdraw the Leaf A-D it had originated earlier in response to the "Leaf Information Required" flag in the PTA.

イグレスPEは、イングレスPEがIMETまたはS-PMSIのA-D経路を取り下げたときに、SR P2MPポリシーのリーフノードまたはバッドノードとしての自身を取り下げます。 イグレスPEは、PTAの「Leaf Information Required」フラグに応答して以前に生成したLeaf A-Dを取り下げなければなりません（MUST）。

4.2. EVPN with Ingress Replication over SR

4.2. SR上のイングレスレプリケーションを用いたEVPN

A PE can provide EVPN service using IR over SR. The EVPN payload is encapsulated in SR-MPLS or SRv6 at an ingress PE and replicated with each copy sent to an egress PE via unicast. IR procedures for MPLS are specified for the IMET A-D route in [RFC7432] and the SMET A-D route in [RFC9251]. Procedures for EVPN IR over SRv6 for the IMET A-D route are specified in [RFC9252]. These procedures provide an EVPN IR service with best-effort unicast connectivity.

PEは、SR上のIRを使用してEVPNサービスを提供できます。 EVPNのペイロードは、イングレスPEでSR-MPLSまたはSRv6でカプセル化されて複製され、各コピーはユニキャストを介してイグレスPEに送信されます。 MPLSのためのIRの手順は、IMET A-D経路については[RFC7432]で、SMET A-D経路については[RFC9251]で規定されています。 IMET A-D経路のためのSRv6上のEVPN IRの手順は、[RFC9252]で規定されています。 これらの手順は、ベストエフォートのユニキャスト接続性を伴うEVPN IRサービスを提供します。

This document adds procedures for providing an EVPN IR service with an SLA from an ingress PE to an egress PE both for SR-MPLS and SRv6. This document extends the BGP Update message of AFI/SAFI 25/70 (L2VPN-EVPN) to carry the Color Extended Community as specified in [RFC9012] and the Color-Only Type extension specified in Section 3 of [RFC9830]. An egress PE colors the IMET with a Color Extended Community. The ingress PE replicates EVPN customer payload to the egress PE by steering it into an SR-TE policy according to Section 8 of [RFC9256]. The ingress PE encapsulates the payload packet into a segment list of the matching SR-TE policy to the egress PE along with IR MPLS label or SRv6 End.DT2M SID received from the egress PE.

この文書は、SR-MPLSとSRv6の両方について、イングレスPEからイグレスPEへのSLAを伴うEVPN IRサービスを提供するための手順を追加します。 この文書は、AFI/SAFI 25/70（L2VPN-EVPN）のBGP Updateメッセージを拡張して、[RFC9012]で規定されているColor拡張コミュニティーと、[RFC9830]のSection 3で規定されているColor-Only Type拡張を運ぶようにします。 イグレスPEは、IMETにColor拡張コミュニティーで色を付けます。 イングレスPEは、[RFC9256]のSection 8に従ってEVPNの顧客のペイロードをSR-TEポリシーに誘導することで、それをイグレスPEに複製します。 イングレスPEは、ペイロードのパケットを、イグレスPEへの一致するSR-TEポリシーのセグメントリストに、イグレスPEから受信したIR MPLSラベルまたはSRv6 End.DT2M SIDとともにカプセル化します。

Note that the Color Extended Community is not used with an EVPN SR P2MP P-tunnel. For EVPN with an SR P2MP P-tunnel, the ingress PE dictates the traffic engineering treatment by specifying the constraints and the metric optimization in the CP of the SR P2MP Policy corresponding to the P-tunnel on the ingress PE. This is necessary because packets are replicated in the PTI; therefore, it is not possible to have differing traffic engineering treatment towards each egress PE (Leaf node) of the PTI.

Color拡張コミュニティーは、EVPNのSR P2MP P-tunnelでは使用されないことに注意してください。 SR P2MP P-tunnelを用いたEVPNでは、イングレスPEは、イングレスPE上のP-tunnelに対応するSR P2MPポリシーのCPで制約とメトリックの最適化を指定することで、トラフィックエンジニアリングの扱いを指示します。 これが必要なのは、パケットがPTI内で複製されるため、PTIの各イグレスPE（リーフノード）に向けて異なるトラフィックエンジニアリングの扱いをすることができないからです。

4.2.1. SR-MPLS

4.2.1. SR-MPLS

EVPN IR procedures for MPLS specified in [RFC7432] and [RFC9251] can be extended for EVPN IR over SR-MPLS.

[RFC7432]と[RFC9251]で規定されているMPLSのためのEVPN IRの手順は、SR-MPLS上のEVPN IRのために拡張できます。

EVPN IR service with an SLA over SR-MPLS data plane can be provided by using the Color Extended Community as described above. Suppose an egress PE, say PE2, sends an IMET A-D route with Extended Color Community C1 with Color-Only Type 0 and EVPN BUM label L10 to ingress PE1. Assume the segment list of SR-TE policy (C1, PE2) at ingress PE1 is <L1, L2, L3>. PE1 will encapsulate the MVPN payload into the MPLS label stack <L1, L2, L3, L10> with L10 as the BoS label. Note that the MPLS label stack may have the ESI label at the bottom of the label stack if ESI-based split-horizon filtering is used.

SR-MPLSデータプレーン上のSLAを伴うEVPN IRサービスは、上で説明したようにColor拡張コミュニティーを使用することで提供できます。 イグレスPE、たとえばPE2が、Color-Only Type 0を伴うColor拡張コミュニティーC1とEVPN BUMラベルL10を含むIMET A-D経路をイングレスPE1に送信するとします。 イングレスPE1におけるSR-TEポリシー（C1, PE2）のセグメントリストが<L1, L2, L3>であると仮定します。 PE1は、L10をBoSラベルとして、MVPNのペイロードをMPLSラベルスタック<L1, L2, L3, L10>にカプセル化します。 ESIベースのスプリットホライズンフィルタリングを使用する場合、MPLSラベルスタックの最下部にESIラベルがある場合があることに注意してください。

4.2.2. SRv6

4.2.2. SRv6

EVPN IR procedures for SRv6 are specified in Section 6.3 of [RFC9252] for the IMET A-D route.

SRv6のためのEVPN IRの手順は、IMET A-D経路については[RFC9252]のSection 6.3で規定されています。

A PE can provide EVPN IR service with SLA over SRv6 using the Color Extended Community as described above. Suppose an egress PE, say PE2, sends an IMET A-D route with Extended Color community C1 with Color-Only Type 0 and SRv6 End.DT2M SID S10 to ingress PE1. Assume the segment list of the SR-TE policy (C1, PE2) at ingress PE1 is <S1, S2, S3>. PE1 will encapsulate a payload into an IPv6 header with SRH (PE1, S1) (S10, S3, S2; SL=3) (payload). Note that the End.DT2M SID S10 may also have an Arg.FE2 Argument if ESI-based split-horizon filtering is used.

PEは、上で説明したようにColor拡張コミュニティーを使用することで、SRv6上のSLAを伴うEVPN IRサービスを提供できます。 イグレスPE、たとえばPE2が、Color-Only Type 0を伴うColor拡張コミュニティーC1とSRv6 End.DT2M SID S10を含むIMET A-D経路をイングレスPE1に送信するとします。 イングレスPE1におけるSR-TEポリシー（C1, PE2）のセグメントリストが<S1, S2, S3>であると仮定します。 PE1は、ペイロードをSRHを伴うIPv6ヘッダー (PE1, S1) (S10, S3, S2; SL=3) (payload) にカプセル化します。 ESIベースのスプリットホライズンフィルタリングを使用する場合、End.DT2M SID S10はArg.FE2引数を持つ場合もあることに注意してください。
