A Simulation Model for IP Multicast with RSVP

RFC 2490

RSVPを伴うIPマルチキャストのためのシミュレーションモデル

Abstract

概要

This document describes a detailed model of IPv4 multicast with RSVP that has been developed using the OPNET simulation package [4], with protocol procedures defined in the C language. The model was developed to allow investigation of performance constraints on routing but should have wide applicability in the Internet multicast/resource reservation community. We are making this model publicly available with the intention that it can be used to provide expanded studies of resource-reserved multicasting.

この文書は、OPNETシミュレーションパッケージ[4]を使用して開発された、プロトコルの手順をC言語で定義した、RSVPを伴うIPv4マルチキャストの詳細なモデルを説明します。このモデルは、ルーティングに対する性能上の制約の調査を可能にするために開発されましたが、インターネットのマルチキャスト/リソース予約のコミュニティーで幅広く適用できるはずです。私たちは、リソースが予約されたマルチキャストの研究を拡大するために使用できることを意図して、このモデルを公開します。

1. Background

1. 背景

The successful deployment of IP multicasting [1] and its availability in the Mbone has led to continuing increase in real-time multimedia Internet applications. Because the Internet has traditionally supported only a best-effort quality of service, there is considerable interest to create mechanisms that will allow adequate resources to be reserved in networks using the Internet protocol suite, such that the quality of real-time traffic such as video, voice, and distributed simulation can be sustained at specified levels. The RSVP protocol [2] has been developed for this purpose and is the subject of ongoing implementation efforts. Although the developers of RSVP have used simulation in their design process, no simulation of IPmc with RSVP has been generally available for analysis of the performance and prediction of the behavior of these protocols. The simulation model described here was developed to fill this gap, and is explicitly intended to be made available to the IETF community.

IPマルチキャスト[1]の展開の成功とMboneでのその利用可能性により、リアルタイムのマルチメディアのインターネットアプリケーションが増え続けています。インターネットは伝統的にベストエフォートのサービス品質しかサポートしてこなかったため、映像、音声、分散シミュレーションなどのリアルタイムのトラフィックの品質を規定されたレベルで維持できるように、インターネットプロトコル群を使用するネットワークで十分なリソースを予約できるようにする仕組みを作ることに、かなりの関心が集まっています。RSVPプロトコル[2]はこの目的のために開発されたものであり、実装の取り組みが進行中です。RSVPの開発者は設計の過程でシミュレーションを使用してきましたが、これらのプロトコルの性能の分析と振る舞いの予測のために一般に利用可能な、RSVPを伴うIPmcのシミュレーションはありませんでした。ここで説明するシミュレーションモデルは、この空白を埋めるために開発されたものであり、明示的にIETFコミュニティーに提供することを意図しています。

2. The OPNET Simulation Environment

2. OPNETシミュレーション環境

The Optimized Network Engineering Tools (OPNET) is a commercial simulation product of the MIL3 company of Arlington, VA. It employs a Discrete Event Simulation approach that allows large numbers of closely-spaced events in a sizable network to be represented accurately and efficiently. OPNET uses a modeling approach where networks are built of components interconnected by perfect links that can be degraded at will. Each component's behavior is modeled as a state-transition diagram. The process that takes place in each state is described by a program in the C language. We believe this makes the OPNET-based models relatively easy to port to other modeling environments. This family of models is compatible with OPNET 3.5. The following sections describe the state-transition models and process code for the IPmc and RSVP models we have created using OPNET. Please note that an OPNET layer is not necessarily equivalent to a layer in a network stack, but shares with a stack layer the property that it is a highly modular software element with well defined interfaces.

Optimized Network Engineering Tools（OPNET）は、バージニア州アーリントンのMIL3社の商用シミュレーション製品です。これは離散事象シミュレーションの手法を採用しており、かなりの規模のネットワークで間隔の詰まった多数のイベントを正確かつ効率的に表現できます。OPNETは、任意に劣化させることのできる完全なリンクで相互接続された構成要素でネットワークを構築するモデル化の手法を使用します。各構成要素の振る舞いは状態遷移図としてモデル化されます。各状態で行われる処理は、C言語のプログラムで記述されます。これにより、OPNETに基づくモデルを他のモデル化環境に比較的容易に移植できると私たちは考えています。このモデルのファミリーは、OPNET 3.5と互換性があります。以下の節では、OPNETを使用して作成したIPmcとRSVPのモデルの状態遷移モデルと処理のコードを説明します。OPNETの層は必ずしもネットワークスタックの層と同等ではありませんが、明確に定義されたインターフェイスを持つ高度にモジュール化されたソフトウェア要素であるという性質をスタックの層と共有していることに注意してください。

3. IP Multicast Model

3. IPマルチキャストのモデル

The following processing takes place in the indicated modules. Each subsection below describes in detail a layer in the host and the router that can be simulated with the help of the corresponding OPNET network layer or node layer or the process layer, starting from physical layer.

示されたモジュールで次の処理が行われます。以下の各小節では、物理層から始めて、対応するOPNETのネットワーク層、ノード層、またはプロセス層の助けを借りてシミュレーションできる、ホストとルーターの層を詳細に説明します。

3.1. Address format

3.1. アドレスの形式

The OPNET IP model has only one type of addressing denoted by "X.Y" where X is 24 bits long and Y is 8 bits long, corresponding to an IPv4 Class C network. The X indicates the destination or the source network number and Y indicates the destination or the source node number. In our model X = 500 is reserved for multicast traffic. For multicast traffic the value of Y indicates the group to which the packet belongs.

OPNETのIPモデルには、「X.Y」で表される1種類のアドレス指定しかありません。ここでXは24ビットの長さ、Yは8ビットの長さであり、IPv4のクラスCのネットワークに対応します。Xは宛先または送信元のネットワーク番号を示し、Yは宛先または送信元のノード番号を示します。私たちのモデルでは、X = 500がマルチキャストのトラフィックのために予約されています。マルチキャストのトラフィックの場合、Yの値はパケットが属するグループを示します。

3.2.2 LANサブネット

The router in the subnet is included to route the traffic between the FDDI ring or Ethernet in the corresponding subnet and the external network. The subnet router is connected on one end to Ethernet or FDDI ring and normally also is connected to an area border router on another interface (the area border routers may be connected to more than one backbone router). In the Ethernet all the hosts are connected to the bus, while in FDDI the hosts are interconnected in a ring as illustrated in Figure 2.

図2は、サブネットで使用されるFDDIリングを示しています。サブネットには1つのルーターと1つ以上のホストがあります。サブネット内のルーターは、対応するサブネットのFDDIリングまたはイーサネットと外部のネットワークとの間でトラフィックをルーティングするために含まれています。サブネットのルーターは、一方の端でイーサネットまたはFDDIリングに接続され、通常は別のインターフェイスでエリア境界ルーターにも接続されています（エリア境界ルーターは複数のバックボーンルーターに接続されている場合があります）。図2に示すように、イーサネットではすべてのホストがバスに接続され、FDDIではホストがリングで相互接続されています。

[Figure 2: FDDI Ring Subnet Layer]

［図2：FDDIリングのサブネット層］

FDDI provides general purpose networking at 100 Mb/sec transmission rates for large numbers of communicating stations configured in a ring topology. Use of ring bandwidth is controlled through a timed token rotation protocol, wherein stations must receive a token and meet with a set of timing and priority criteria before transmitting frames. In order to accommodate network applications in which response times are critical, FDDI provides for deterministic availability of ring bandwidth by defining a synchronous transmission service. Asynchronous frame transmission requests dynamically share the remaining ring bandwidth.

FDDIは、リングのトポロジーで構成された多数の通信するステーションのために、100 Mb/秒の伝送レートで汎用的なネットワーキングを提供します。リングの帯域幅の使用は、時間制限付きのトークンの巡回プロトコルによって制御され、ステーションはフレームを送信する前にトークンを受け取り、タイミングと優先度の一連の基準を満たす必要があります。応答時間が重要なネットワークのアプリケーションに対応するために、FDDIは、同期伝送サービスを定義することで、リングの帯域幅の決定論的な利用可能性を提供します。非同期のフレームの送信要求は、残りのリングの帯域幅を動的に共有します。

Ethernet is a bus-based local area network (LAN) technology. The operation of the LAN is managed by a media access protocol (MAC) following the IEEE 802.3 standard, providing Carrier Sense Multiple Access with Collision Detection (CSMA/CD) for the LAN channel.

イーサネットは、バスベースのローカルエリアネットワーク（LAN）の技術です。LANの動作は、IEEE 802.3規格に従うメディアアクセスプロトコル（MAC）によって管理され、LANのチャネルにキャリア検知多重アクセス/衝突検出（CSMA/CD）を提供します。

3.3. Node layer

3.3. ノード層

This section discusses the internal structure of hosts and routers with the help of node level illustrations built using the Node editor of OPNET.

この節では、OPNETのノードエディターを使用して構築したノードレベルの図の助けを借りて、ホストとルーターの内部構造について議論します。

3.3.1 Basic OPNET elements

3.3.1 OPNETの基本要素

The basic elements of a node level illustration are

ノードレベルの図の基本要素は次のとおりです。

  1. Processor nodes: Processor nodes are used for processing incoming packets and generating packets with a specified packet format.
  2. Queue node: Queue nodes are a superset of processor nodes. In addition to the capabilities of processor nodes, queue nodes also have capability to store packets in one or more queues.
  3. Transmitter and Receiver nodes: Transmitters simulate the link behavior effect of packet transmission and Receivers simulate the receiving effects of packet reception. The transmission rate is an attribute of the transmitter and receiving rate is an attribute of the receiver. These values together decide the transmission delay of a packet.
  4. Packet streams: Packet streams are used to interconnect the above described nodes.
  5. Statistic streams: Statistic streams are used to convey information between the different nodes: Processor, Queue, Transmitters and Receivers nodes respectively.
  1. プロセッサーノード：プロセッサーノードは、受信したパケットを処理し、指定されたパケット形式でパケットを生成するために使用されます。
  2. キューノード：キューノードはプロセッサーノードの上位集合です。プロセッサーノードの能力に加えて、キューノードは1つ以上のキューにパケットを格納する能力も持っています。
  3. 送信機ノードと受信機ノード：送信機はパケットの送信のリンクの振る舞いの効果をシミュレートし、受信機はパケットの受信の効果をシミュレートします。伝送レートは送信機の属性であり、受信レートは受信機の属性です。これらの値を合わせて、パケットの伝送遅延が決まります。
  4. パケットストリーム：パケットストリームは、上記で説明したノードを相互接続するために使用されます。
  5. 統計ストリーム：統計ストリームは、異なるノード、すなわちプロセッサー、キュー、送信機、受信機のノードの間で情報を伝えるために使用されます。

3.3.2 Host description

3.3.2 ホストの説明

The host model built using OPNET has a layered structure. Different from the OPNET layers (Network, Node and Process layer) that describe the network at different levels, protocol stack elements are implemented at OPNET nodes. Figure 3 shows the node level structure of a FDDI host.

OPNETを使用して構築したホストのモデルは、階層化された構造を持ちます。ネットワークを異なるレベルで記述するOPNETの層（ネットワーク層、ノード層、プロセス層）とは異なり、プロトコルスタックの要素はOPNETのノードに実装されます。図3は、FDDIのホストのノードレベルの構造を示しています。

[Figure 3: Node Level of Host]

［図3：ホストのノードレベル］

  1. MAC queue node: The MAC interfaces on one side to the physical layer through the transmitter (phy_tx) and receiver (phy_rx) and also provides services to the IP layer. Use of ring bandwidth is controlled through a timed token rotation protocol, wherein hosts must receive a token and meet with a set of timing and priority criteria before transmitting frames. When a frame arrives at the MAC node, the node performs one of the following actions:

    1. If the owner of the frame is this MAC, the MAC layer destroys the frame since the frame has finished circulating through the FDDI ring.
    2. if the frame is destined for this host, the MAC layer makes a copy of the frame, decapsulates the frame and sends the descapsulated frame (packet) to the IP layer. The original frame is transmitted to the next host in the FDDI ring
    3. if the owner of the frame is any other host and the frame is not destined for this host, the frame is forwarded to the adjacent host.
  2. ADDR_TRANS processor node: The next layer above the MAC layer is the addr_trans processor node. This layer provides service to the IP layer by carrying out the function of translating the IP address to physical interface address. This layer accepts packets from the IP layer with the next node information, maps the next node information to a physical address and forwards the packet for transmission. This service is required only in one direction from the IP layer to the MAC layer. Since queuing is not done at this level, a processor node is used to accomplish the address translation function, from IP to MAC address (ARP).
  3. IP queue node: Network routing/forwarding in the hierarchy is implemented here. IP layer provides service for the layers above which are the different higher level protocols by utilizing the services provided by the MAC layer. For packets arriving from the MAC layer, the IP layer decapsulates the packet and forwards the information to an upper layer protocol based upon the value of the protocol ID in the IP header. For packets arriving from upper layer protocols, the IP layer obtains the destination address, calculates the next node address from the routing table, encapsulates it with a IP header and forwards the packet to the addr_trans node with the next node information.

  1. MACキューノード：MACは、一方では送信機（phy_tx）と受信機（phy_rx）を通じて物理層とのインターフェイスとなり、またIP層にサービスを提供します。リングの帯域幅の使用は、時間制限付きのトークンの巡回プロトコルによって制御され、ホストはフレームを送信する前にトークンを受け取り、タイミングと優先度の一連の基準を満たす必要があります。フレームがMACノードに到着すると、ノードは次の動作のいずれかを行います。

    1. フレームの所有者がこのMACである場合、フレームはFDDIリングの巡回を終えたため、MAC層はそのフレームを破棄します。
    2. フレームがこのホスト宛てである場合、MAC層はフレームのコピーを作成し、フレームのカプセル化を解除し、カプセル化を解除したフレーム（パケット）をIP層に送信します。元のフレームはFDDIリングの次のホストに送信されます。
    3. フレームの所有者が他のホストであり、フレームがこのホスト宛てでない場合、フレームは隣接するホストに転送されます。
  2. ADDR_TRANSプロセッサーノード：MAC層の上の次の層は、addr_transプロセッサーノードです。この層は、IPアドレスを物理インターフェイスのアドレスに変換する機能を実行することで、IP層にサービスを提供します。この層は、次のノードの情報を伴うパケットをIP層から受け取り、次のノードの情報を物理アドレスにマッピングし、送信のためにパケットを転送します。このサービスは、IP層からMAC層への一方向でのみ必要です。このレベルではキューイングは行われないため、IPアドレスからMACアドレスへのアドレス変換の機能（ARP）を実現するためにプロセッサーノードが使用されます。
  3. IPキューノード：階層におけるネットワークのルーティング/転送はここで実装されます。IP層は、MAC層が提供するサービスを利用して、その上の層、すなわちさまざまな上位のプロトコルにサービスを提供します。MAC層から到着したパケットについて、IP層はパケットのカプセル化を解除し、IPヘッダーのプロトコルIDの値に基づいて、その情報を上位層のプロトコルに転送します。上位層のプロトコルから到着したパケットについて、IP層は宛先アドレスを取得し、ルーティングテーブルから次のノードのアドレスを計算し、それをIPヘッダーでカプセル化して、次のノードの情報とともにパケットをaddr_transノードに転送します。

The IP node is a queue node. It is in this layer that packets incur delay which simulates the processing capability of a host and queueing for use of the outgoing link. A packet arrival to the IP layer will be queued and experience delay when it finds another packet already being transmitted, plus possibly other packets queued for transmission. The packets arriving at the IP layer are queued and operate with a first-in first-out (FIFO) discipline. The queue size, service rate of the IP layer are both promoted attributes, specified at the simulation run level by the environment file.

IPノードはキューノードです。パケットが遅延を受けるのはこの層であり、これはホストの処理能力と、送信リンクを使用するためのキューイングをシミュレートします。IP層に到着したパケットは、別のパケットがすでに送信中であり、場合によっては他のパケットも送信のためにキューに入っている場合、キューに入れられて遅延を受けます。IP層に到着したパケットはキューに入れられ、先入れ先出し（FIFO）の規律で処理されます。キューのサイズとIP層のサービスレートは、どちらも環境ファイルによってシミュレーションの実行レベルで指定される、上位に公開された属性です。

  1. IGMP processor node: The models described above are standard components available in OPNET libraries. We have added to these the host multicast protocol model IGMP_host, the router multicast model IGMP_gwy, and the unicast best-effort protocol model UBE.
  1. IGMPプロセッサーノード：上記で説明したモデルは、OPNETのライブラリーで利用可能な標準の構成要素です。私たちはこれらに、ホストのマルチキャストプロトコルのモデルIGMP_host、ルーターのマルチキャストのモデルIGMP_gwy、およびユニキャストのベストエフォートのプロトコルのモデルUBEを追加しました。

The IGMP_host node (Figure 4) is a process node. Packets are not queued in this layer. IGMP_host provides unique group management services for the multicast applications utilizing the services provided by the IP layer. IGMP_host maintains a single table which consists of group membership information of the application above the IGMP layer. The function performed by the IGMP_host layer depends upon the type of the packet received and the source of the packet.

IGMP_hostノード（図4）はプロセスノードです。この層ではパケットはキューに入れられません。IGMP_hostは、IP層が提供するサービスを利用して、マルチキャストのアプリケーションのための独自のグループ管理のサービスを提供します。IGMP_hostは、IGMP層の上にあるアプリケーションのグループメンバーシップの情報からなる単一のテーブルを維持します。IGMP_host層が実行する機能は、受信したパケットの種類とパケットの送信元に依存します。

The IGMP_host layer expects certain type of packets from the application layer and from the network:

IGMP_host層は、アプリケーション層とネットワークから特定の種類のパケットを期待します。

  1. Accept join group requests from the application layer (which can be one or more applications): IGMP_host maintains a table which consists of the membership information for each group. When a application sends a join request, it requests to join a specific group N. The membership information is updated. This new group membership information has to be conveyed to the nearest router and to the MAC layer. If the IGMP_host is already a member ofthis group (i.e. if another application above the IGMP_host is a member of the group N), the IGMP_host does not have to send a message to the router or indicate to the MAC layer. If the IGMP_host is not a member currently, the IGMP_host generates a join request for the group N (this is called a "response" in RFC 1112) and forwards it to the IP layer to be sent to the nearest router. In addition the IGMP_host also conveys this membership information to the MAC layer interfacing to the physical layer through the OPNET "statistic wire" connected from the IGMP_host to the MAC layer, so that the MAC layer knows the membership information immediately and begins to accept the frames destined for the group N. (An OPNET statistic wire is a virtual path to send information between OPNET models.)

  2. Accept queries arriving from the nearest router and send responses based on the membership information in the multicast table at the IGMP_host layer: A query is a message from a router inquiring each host on the router's interface about group membership information. When the IGMP_host receives a query, it looks up the multicast group membership table, to determine if any of the host's applications are registered for any group. If any registration exists, the IGMP_host schedules an event to generate a response after a random amount of time corresponding to each active group. The UBE node generates traffic to a randomly generated IP address so as to model competing traffic in the network from applications such as FTP.   2. Data IAT: When the UBE generates data traffic, the interarrival times between data packets is Data IAT. A decrease in the value of Data IAT increases the severity of congestion in the network.
  3. Session-min and Session-max: When the UBE node starts generating data traffic it remains in that session for a random period which is uniformly distributed between Session-min and Session-max.
  4. Multicast Application processor node: The application layer consists of one or more application nodes which are process nodes. These nodes use the services provided by lower layer protocols IGMP, RSVP and IP. The Application layer models the requests and traffic generated by Application layer programs. Attributes of the application layer are:
  5. Session IAT: is the variable used to schedule an event to begin a session. The Application node generates an exponentially distributed random variable with mean Session IAT and begins to generate information for a specific group at that time and also accept packets belonging to that group.
  6. Data IAT: When Application node generates data traffic, the inter arrival time between the packets uses Data IAT variable as the argument. The distribution can be any of the available distribution functions in OPNET.
  7. Session-min and Session-max: When an application joins a session the duration for which the application stays in that session is bounded by Session-min and Session-max. A uniformly distributed random variable between Session-min and Session-max is generated for this purpose. At any given time each node will have zero or one flow(s) of data.

  8. NGRPS: This variable is used by the application generating multicast traffic to bound the value of the group to which an application requests the IGMP to join. The group is selected at random from the range [0,NGRPS-1].

  2. データのIAT：UBEがデータトラフィックを生成するとき、データパケットの間の到着間隔がデータのIATです。データのIATの値を減らすと、ネットワークの輻輳の深刻さが増します。
  3. Session-minとSession-max：UBEノードがデータトラフィックの生成を開始すると、Session-minとSession-maxの間で一様に分布するランダムな期間、そのセッションにとどまります。

  5. セッションのIAT：セッションを開始するイベントをスケジュールするために使用される変数です。アプリケーションのノードは、平均がセッションIATである指数分布の確率変数を生成し、その時刻に特定のグループのための情報の生成を開始し、そのグループに属するパケットの受け入れも開始します。

3.3.3 Router description

3.3.3 ルーターの説明

There are two types of routers in the model, a router serving a subnet and a backbone router. A subnet router has all the functions of a backbone router and in addition also has a interface to the underlying subnet which can be either a FDDI network or a Ethernet subnet. In the following section the subnet router will be discussed in detail.

モデルには、サブネットにサービスを提供するルーターとバックボーンルーターの2種類のルーターがあります。サブネットのルーターはバックボーンルーターのすべての機能を持ち、さらに、FDDIネットワークまたはイーサネットのサブネットのいずれかである基盤となるサブネットへのインターフェイスも持っています。次の節では、サブネットのルーターについて詳細に議論します。

Figure 6 shows the node level model of a subnet router.

図6は、サブネットのルーターのノードレベルのモデルを示しています。

  1. The queueing technique implemented in the router is a combination of input and output queueing. The nodes rx1 to rx10 are the receivers connected to incoming links. The router in Figure 6 has a physical interface to the FDDI ring or Ethernet, which consists of the queue node MAC, transmitter phy_tx, and the receiver phy_rx. The backbone routers will not have a MAC layer. The services provided and the functions of the MAC layer are the same as the MAC layer in the host discussed above.
  1. ルーターに実装されるキューイングの技法は、入力キューイングと出力キューイングの組み合わせです。ノードrx1～rx10は、受信リンクに接続された受信機です。図6のルーターは、FDDIリングまたはイーサネットへの物理インターフェイスを持っており、これはキューノードMAC、送信機phy_tx、および受信機phy_rxで構成されます。バックボーンルーターはMAC層を持ちません。MAC層が提供するサービスと機能は、上記で議論したホストのMAC層と同じです。

There is one major difference between the MAC node in a subnet router and that in a host. The MAC node in a subnet router accepts all arriving multicast packets unlike the MAC in a host which accepts only the multicast packets for groups of which the host is a member. For this reason the statistic wire from the IGMP to MAC layer does not exist in a router (also because a subnet router does not have an application layer).

サブネットのルーターのMACノードとホストのMACノードの間には、1つの大きな違いがあります。ホストのMACは、ホストがメンバーであるグループのマルチキャストのパケットだけを受け入れるのに対し、サブネットのルーターのMACノードは、到着するすべてのマルチキャストのパケットを受け入れます。このため、ルーターには、IGMPからMAC層への統計ワイヤーは存在しません（また、サブネットのルーターにはアプリケーション層がないためでもあります）。

  1. Addr_trans: The link layer in the router hierarchy is the addr_trans processor node which provides the service of translating the IP address to a physical address. The addr_trans node was described above under the host model.
  2. IP layer: The router IP layer which provides services to the upper layer transport protocols and also performs routing based upon the information in the routing table. The IP layer maintains two routing tables and one group membership table.
  1. Addr_trans：ルーターの階層におけるリンク層は、IPアドレスを物理アドレスに変換するサービスを提供するaddr_transプロセッサーノードです。addr_transノードについては、上記のホストのモデルで説明しました。
  2. IP層：上位層のトランスポートプロトコルにサービスを提供し、またルーティングテーブルの情報に基づいてルーティングを行う、ルーターのIP層です。IP層は、2つのルーティングテーブルと1つのグループメンバーシップのテーブルを維持します。

The tables used by the router model are:

ルーターのモデルで使用されるテーブルは次のとおりです。

  1. Unicast routing table: This table is an single array of one dimension, which is used to route packets generated by the UDP process node in the hosts. If no route is known to a particular IP address, the corresponding entry is set to a default route. 2. Multicast routing table: This table is a N by I array where N is the maximum number of multicast groups in the model and I is the number of interfaces in the router. This table is used to route multicast packets. The routing table in a router is set by an upper layer routing protocol (see section 4 below). When the IP layer receives a multicast packet with a session_id corresponding to a session which is utilizing the MOSFP, it looks up the multicast routing table to obtain the next hop. 3. Group membership table: This table is used to maintain group membership information of all the interfaces of the router. This table which is also an N by I array is set by the IGMP layer protocol. The routing protocols use this information in the group membership table to calculate and set the routes in the Multicast routing table.
  1. ユニキャストのルーティングテーブル：このテーブルは、ホストのUDPプロセスノードによって生成されたパケットをルーティングするために使用される、1次元の単一の配列です。特定のIPアドレスへの経路がわからない場合、対応するエントリーはデフォルトの経路に設定されます。2. マルチキャストのルーティングテーブル：このテーブルはN×Iの配列であり、ここでNはモデル内のマルチキャストのグループの最大数、Iはルーターのインターフェイスの数です。このテーブルは、マルチキャストのパケットをルーティングするために使用されます。ルーターのルーティングテーブルは、上位層のルーティングプロトコルによって設定されます（以下の4節を参照）。IP層は、MOSFPを利用しているセッションに対応するsession_idを持つマルチキャストのパケットを受信すると、次ホップを得るためにマルチキャストのルーティングテーブルを調べます。3. グループメンバーシップのテーブル：このテーブルは、ルーターのすべてのインターフェイスのグループメンバーシップの情報を維持するために使用されます。このテーブルもN×Iの配列であり、IGMP層のプロトコルによって設定されます。ルーティングプロトコルは、このグループメンバーシップのテーブルの情報を使用して、マルチキャストのルーティングテーブルの経路を計算して設定します。

Sub-queues: The IP node has three subqueues, which implement queuing based upon the priority of arriving packets from the neighboring routers or the underlying subnet. The queue with index 0 has the highest priority. When a packet arrives at the IP node, the packets are inserted into the appropriate sub-queue based on the priority of their traffic category: control traffic, resource- reserved traffic, or best effort traffic. A non-preemptive priority is used in servicing the packets. After the servicing, packets are sent to the one of the output queues or the MAC. The packets progress through these queues until the transmitter becomes available.

サブキュー：IPノードには3つのサブキューがあり、隣接するルーターや基盤となるサブネットから到着するパケットの優先度に基づくキューイングを実装します。インデックス0のキューが最も高い優先度を持ちます。パケットがIPノードに到着すると、パケットはそのトラフィックのカテゴリー、すなわち制御トラフィック、リソースが予約されたトラフィック、またはベストエフォートのトラフィックの優先度に基づいて、適切なサブキューに挿入されます。パケットの処理には、非プリエンプティブな優先度が使用されます。処理の後、パケットは出力キューの1つまたはMACに送信されます。パケットは、送信機が利用可能になるまでこれらのキューを進みます。

Attributes of the IP node are:

IPノードの属性は次のとおりです。

  1. Unique IP address for each interface (a set of transmitter and receiver constitute an interface).
  2. Service rate: the rate with which packets are serviced at the router.
  3. Queue size: size of each of the sub queues used to store incoming packets based on the priority can be specified individually
  4. Output queues: The output queues perform the function of queueing the packets received by the IP layer when the transmitter is busy. A significant amount of queuing takes place in the output queues only if the throughput of the IP node approaches the transmission capacity of the links. The only attribute of the queue node is:
  1. 各インターフェイスの一意なIPアドレス（送信機と受信機の組がインターフェイスを構成します）。
  2. サービスレート：ルーターでパケットが処理されるレート。
  3. キューのサイズ：優先度に基づいて受信したパケットを格納するために使用される各サブキューのサイズは、個別に指定できます。
  4. 出力キュー：出力キューは、送信機がビジーのときにIP層が受信したパケットをキューに入れる機能を実行します。出力キューで相当量のキューイングが行われるのは、IPノードのスループットがリンクの伝送容量に近づいた場合だけです。キューノードの唯一の属性は次のとおりです。

Queue size: size of the queue in each queue node. If the queue is full when a packet is received, that packet is dropped.

キューのサイズ：各キューノードのキューのサイズ。パケットを受信したときにキューが満杯の場合、そのパケットは破棄されます。

  1. IGMP Node: Also modeled in the router is the IGMP for implementing multicasting, the routing protocol, and RSVP for providing specific QoS setup.
  1. IGMPノード：ルーターでは、マルチキャストを実装するためのIGMP、ルーティングプロトコル、そして特定のQoSのセットアップを提供するためのRSVPもモデル化されています。

  1. IGMP node at a router sends queries at regular intervals on all its interfaces.
  2. When IGMP receives a response to the queries sent, IGMP updates the multicast Group membership table in the IP node and triggers on MOSPF LSA update.
  3. Every time the IGMP sends a query, it also updates the multicast group membership table in the IP node if no response has been received on for the group on any interface, indicating that a interface is no longer a member of that group. This update is done only on entries which indicate an active membership for a group on a interface where the router has not received a response for the last query sent.
  4. The routing protocol (see ection 4 below) uses the information in the group membership table to calculate the routes and update the multicast routing table.
  5. When the IGMP receives a query (an IGMP at router can receive a query from a directly connected neighboring router), the IGMP node creates a response for each of the groups it is a member of on all the interfaces except the one through which the query was received.

  6. The IGMP node on a backbone router is disabled, because IGMP is only used when a router has hosts on its subnet.

  6. IGMPは、ルーターのサブネットにホストがある場合にのみ使用されるため、バックボーンルーターのIGMPノードは無効になっています。

4. RSVPのモデル

The current version of the RSVP model supports only fixed-filter reservation style. The following processing takes place in the indicated modules. The model is current with [2].

RSVPのモデルの現在のバージョンは、固定フィルターの予約スタイルだけをサポートしています。示されたモジュールで次の処理が行われます。このモデルは[2]に対応しています。

4.1. RSVP APPLICATION

4.1. RSVPのアプリケーション

4.1.1 Init

4.1.1 Init

Initializes all variables and loads the distribution functions for Multicast Group IDs, Data, termination of the session. Transit to Idle state after completing all the initializations.

すべての変数を初期化し、マルチキャストのグループID、データ、セッションの終了のための分布関数を読み込みます。すべての初期化を完了した後、Idleの状態に遷移します。

4.1.2 Idle

4.1.2 Idle

This state has transitions to two states, Join and Data_Send. It transit to Join state at the time that the application is scheduled to join a session or terminate the current session, transit to Data_Send state when the application is going to send data.

この状態からは、JoinとData_Sendの2つの状態への遷移があります。アプリケーションがセッションに参加するか現在のセッションを終了するようにスケジュールされた時刻にJoinの状態に遷移し、アプリケーションがデータを送信しようとするときにData_Sendの状態に遷移します。

4.1.3 Join

4.1.3 Join

The Application will send a session call to local RSVP daemon. In response it receives the session Id from the Local daemon. This makes a sender or receiver call. The multicast group id is selected randomly from a uniform distribution. While doing a sender call the application will write all its sender information in a global session directory.

アプリケーションは、ローカルのRSVPデーモンにセッションの呼び出しを送信します。それに応じて、ローカルのデーモンからセッションIDを受け取ります。これにより、送信者または受信者の呼び出しを行います。マルチキャストのグループIDは、一様分布からランダムに選択されます。送信者の呼び出しを行う間、アプリケーションは送信者のすべての情報をグローバルなセッションディレクトリーに書き込みます。

If the application is acting as a receiver it will check for the sender information in the session directory for the multicast group that it wants to join to and make a receive call to the local RSVP daemon. Along with the session and receive calls, it makes an IGMP join call.

アプリケーションが受信者として動作している場合は、参加したいマルチキャストのグループについてセッションディレクトリーの送信者の情報を確認し、ローカルのRSVPデーモンに受信の呼び出しを行います。セッションと受信の呼び出しとともに、IGMPの参加の呼び出しを行います。

If the application chooses to terminate the session to which it was registered, it will send a release call to the local RSVP daemon and a terminate call to IGMP daemon. After completing these functions it will return to the idle state.

アプリケーションが登録されていたセッションの終了を選択した場合は、ローカルのRSVPデーモンに解放の呼び出しを、IGMPデーモンに終了の呼び出しを送信します。これらの機能を完了した後、idleの状態に戻ります。

4.1.4 Data_Send

Creates a data packet and sends it to a multicast destination that it selects. It update a counter to keep track of how many packets that it has sent. This state on default returns to Idle state.

4.2.1 Init

4.2.2 Idle

4.2.3 Arr

4.2.3 Arr

This state checks for the type of the packet arrived and calls the appropriate function depending on the type of message received.

この状態は、到着したパケットの種類を確認し、受信したメッセージの種類に応じて適切な関数を呼び出します。

  1. PathMsgPro: This function was invoked by the Arr state when a path message is received. Before it was called, OSPF routing had been recomputed to get the latest routing table for forwarding the Path Message.
  2. It first checks for a Path state block which has a matching destination address and if the sender port or sender address or destination port does not match the values of the Session object of the Path state block, it sends an path error message and returns. (At present the application does not send any error messages, we print this error message on the console.)
  3. If a PSB is found whose Session Object and Sender Template Object matches with that of the path message received, the current PSB becomes the forwarding PSB.
  4. Search for the PSB whose session and sender template matches the corresponding objects in the path message and whose incoming interface matches the IncInterface. If such a PSB is found and the if the Previous Hop Address, Next Hop Address, and SenderTspec Object doesn't match that of path message then the values of path message is copied into the path state block and Path Refresh Needed flag is turned on. If the Previous Hop Address, Next Hop Address of PSB differs from the path message then the Resv Refresh Needed flag is also turned on, and the Current PSB is made equal to this PSB.
  5. If a matching PSB is not found then a new PSB is created and and Path Refresh Needed Flag is turned on, and the Current PSB is made equal to this PSB.
  6. If Path Refresh Needed Flag is on, Current PSB is copied into forwarding PSB and Path Refresh Sequence is executed. To execute this function called PathRefresh is used. Path Refresh is sent to every interface that is in the outgoing interfaces list of forwarding path state block.
  7. Search for a Reservation State Block whose filter spec object matches with the Sender Template Object of the forwarding PSB and whose Outgoing Interface matches one of the entry in the forwarding PSB's outgoing interface list. If found then a Resv Refresh message to the Previous Hop Address in the forwarding PSB and execute the Update Traffic Control sequence.
  8. PathRefresh: This function is called from PathMsgPro. It creates the Path message sends the message through the outgoing interface that is specified by the PathMsgPro.
  9. ResvMsgPro: This function was invoked by the Arr state when a Resv message is received.
  10. Determine the outgoing interface and check for the PSB whose Source Address and Session Objects match the ones in the Resv message.
  11. If such a PSB is not found then send a ResvErr message saying that No Path Information is available. (We have not implemented this message, we only print an error message on the console.)
  12. Check for incompatible styles and process the flow descriptor list to make reservations, checking the PSB list for the sender information. If no sender information is available through the PSB list then send an Error message saying that No Sender information. For all the matching PSBs found, if the Refresh PHOP list doesn't have the Previous Hop Address of the PSB then add the Previous Hop Address to the Refresh PHOP list.
  13. Check for matching Reservation State Block (RSB) whose Session and Filter Spec Object matches that of Resv message. If no such RSB is found then create a new RSB from the Resv Message and set the NeworMod flag On. Call this RSB as activeRSB. Turn on the Resv Refresh Needed Flag.
  14. If a matching RSB is found, call this as activeRSB and if the FlowSpec and Scope objects of this RSB differ from that of Resv Message copy the Resv message Flowspec and Scope objects to the ActiveRSB and set the NeworMod flag On.
  15. Call the Update Traffic Control Sequence. This is done by calling the function UpdateTrafficControl
  16. If Resv Refresh Needed Flag is On then send a ResvRefresh message for each Previous Hop in the Refresh PHOP List. This is done by calling the ResvRefresh function for every Previous Hop in the Refresh PHOP List.
  17. ResvRefresh: this function is called by both PathMsgPro and ResvMsgPro with RSB and Previous Hop as input. The function constructs the Resv Message from the RSB and sends the message to the Previous Hop.
  18. PathTearPro: This function is invoked by the Arr state when a PathTear message is received.
  19. Search for PSB whose Session Object and Sender Template Object matches that of the arrived PathTear message.
  20. If such a PSB is not found do nothing and return.
  21. If a matching PSB is found, a PathTear message is sent to all the outgoing interfaces that are listed in the Outgoing Interface list of the PSB.
  22. Search for all the RSB whose Filter Spec Object matches the Sender Template Object of the PSB and if the Outgoing Interface of this RSB is listed in the PSB's Outgoing interface list delete the RSB.
  23. Delete the PSB and return.
  24. ResvTearPro: This function is invoked by the Arr state when a ResvTear message is received.
  25. Determine the Outgoing Interface.
  26. Process the flow descriptor list of the arrived ResvTear message.
  27. Check for the RSB whose Session Object, Filter Spec Object matches that of ResvTear message and if there is no such RSB return.
  28. If such an RSB is found and Resv Refresh Needed Flag is on send ResvTear message to all the Previous Hops that are in Refresh PHOP List.
  29. Finally delete the RSB.
  30. ResvConfPro: This function is invoked by the Arr state when a ResvConf message is received. The Resv Confirm is forwarded to the IP address that was in the Resv Confirm Object of the received ResvConf message.
  31. UpdateTrafficControl: This function is called by PathMsgPro and ResvMsgPro and input to this function is RSB.
  32. The RSB list is searched for a matching RSB that matches the Session Object, and Filter Spec Object with the input RSB.
  33. Effective Kernel TC_Flowspec are computed for all these RSB's.
  34. If the Filter Spec Object of the RSB doesn't match the one of the Filter Spec Object in the TC Filter Spec List then add the Filter Spec Object to the TC Filter Spec List.
  35. If the FlowSpec Object of the input RSB is greater than the TC_Flowspec then turn on the Is_Biggest flag.
  36. Search for the matching Traffic Control State Block(TCSB) whose Session Object, Outgoing Interface, and Filter Spec Object matches with those of the Input RSB.
  37. If such a TCSB is not found create a new TCSB.
  38. If matching TCSB is found modify the reservations.
  39. If Is_Biggest flag is on turn on the Resv Refresh Needed Flag flag, else send a ResvConf Message to the IP address in the ResvConfirm Object of the input RSB.

  3. SessionオブジェクトとSender Templateオブジェクトが受信したPathメッセージのものと一致するPSBが見つかった場合、現在のPSBが転送用のPSBになります。
  4. sessionとsender templateがPathメッセージの対応するオブジェクトと一致し、受信インターフェイスがIncInterfaceと一致するPSBを検索します。そのようなPSBが見つかり、Previous Hop Address、Next Hop Address、およびSenderTspecオブジェクトがPathメッセージのものと一致しない場合、Pathメッセージの値がPath状態ブロックにコピーされ、Path Refresh Neededフラグがオンにされます。PSBのPrevious Hop AddressやNext Hop AddressがPathメッセージと異なる場合は、Resv Refresh Neededフラグもオンにされ、Current PSBがこのPSBと等しくされます。
  5. 一致するPSBが見つからない場合は、新しいPSBが作成され、Path Refresh Neededフラグがオンにされ、Current PSBがこのPSBと等しくされます。
  6. Path Refresh Neededフラグがオンの場合、Current PSBが転送用のPSBにコピーされ、Path Refreshのシーケンスが実行されます。これを実行するために、PathRefreshという関数が使用されます。Path Refreshは、転送用のPath状態ブロックの送信インターフェイスのリストにあるすべてのインターフェイスに送信されます。
  7. filter specオブジェクトが転送用のPSBのSender Templateオブジェクトと一致し、Outgoing Interfaceが転送用のPSBの送信インターフェイスのリストのエントリーの1つと一致する予約状態ブロックを検索します。見つかった場合は、転送用のPSBのPrevious Hop AddressにResv Refreshメッセージを送り、Update Traffic Controlのシーケンスを実行します。
  8. PathRefresh：この関数はPathMsgProから呼び出されます。Pathメッセージを作成し、PathMsgProによって指定された送信インターフェイスを通じてメッセージを送信します。
  9. ResvMsgPro：この関数は、Resvメッセージを受信したときにArrの状態によって呼び出されます。
  10. 送信インターフェイスを決定し、Source AddressとSessionオブジェクトがResvメッセージのものと一致するPSBを確認します。
  11. そのようなPSBが見つからない場合は、Path情報が利用できないことを伝えるResvErrメッセージを送信します。（このメッセージは実装しておらず、コンソールにエラーメッセージを出力するだけです。）

  13. SessionとFilter SpecオブジェクトがResvメッセージのものと一致する予約状態ブロック（RSB）を確認します。そのようなRSBが見つからない場合は、Resvメッセージから新しいRSBを作成し、NeworModフラグをオンに設定します。このRSBをactiveRSBと呼びます。Resv Refresh Neededフラグをオンにします。
  14. 一致するRSBが見つかった場合は、これをactiveRSBと呼び、このRSBのFlowSpecとScopeのオブジェクトがResvメッセージのものと異なる場合は、ResvメッセージのFlowspecとScopeのオブジェクトをActiveRSBにコピーし、NeworModフラグをオンに設定します。

  16. Resv Refresh Neededフラグがオンの場合は、Refresh PHOPリストの各Previous HopにResvRefreshメッセージを送信します。これは、Refresh PHOPリストのすべてのPrevious HopについてResvRefresh関数を呼び出すことで行われます。
  17. ResvRefresh：この関数は、PathMsgProとResvMsgProの両方から、RSBとPrevious Hopを入力として呼び出されます。この関数は、RSBからResvメッセージを構築し、そのメッセージをPrevious Hopに送信します。
  18. PathTearPro：この関数は、PathTearメッセージを受信したときにArrの状態によって呼び出されます。
  19. SessionオブジェクトとSender Templateオブジェクトが到着したPathTearメッセージのものと一致するPSBを検索します。
  20. そのようなPSBが見つからない場合は、何もせずに戻ります。
  21. 一致するPSBが見つかった場合は、PSBのOutgoing Interfaceリストに挙げられているすべての送信インターフェイスにPathTearメッセージが送信されます。
  22. Filter SpecオブジェクトがPSBのSender Templateオブジェクトと一致するすべてのRSBを検索し、このRSBのOutgoing InterfaceがPSBの送信インターフェイスのリストに挙げられている場合は、そのRSBを削除します。

  24. ResvTearPro：この関数は、ResvTearメッセージを受信したときにArrの状態によって呼び出されます。

  26. 到着したResvTearメッセージのフロー記述子のリストを処理します。
  27. SessionオブジェクトとFilter SpecオブジェクトがResvTearメッセージのものと一致するRSBを確認し、そのようなRSBがない場合は戻ります。

  29. 最後にRSBを削除します。
  30. ResvConfPro：この関数は、ResvConfメッセージを受信したときにArrの状態によって呼び出されます。Resv Confirmは、受信したResvConfメッセージのResv ConfirmオブジェクトにあったIPアドレスに転送されます。
  31. UpdateTrafficControl：この関数はPathMsgProとResvMsgProによって呼び出され、この関数への入力はRSBです。
  32. RSBのリストから、SessionオブジェクトとFilter Specオブジェクトが入力のRSBと一致するRSBを検索します。
  33. これらすべてのRSBについて、実効的なカーネルのTC_Flowspecが計算されます。
  34. RSBのFilter SpecオブジェクトがTC Filter Specリストの中のFilter Specオブジェクトのいずれとも一致しない場合は、そのFilter SpecオブジェクトをTC Filter Specリストに追加します。
  35. 入力のRSBのFlowSpecオブジェクトがTC_Flowspecより大きい場合は、Is_Biggestフラグをオンにします。
  36. Sessionオブジェクト、Outgoing Interface、およびFilter Specオブジェクトが入力のRSBのものと一致するトラフィック制御状態ブロック（TCSB）を検索します。
  37. そのようなTCSBが見つからない場合は、新しいTCSBを作成します。
  38. 一致するTCSBが見つかった場合は、予約を変更します。
  39. Is_Biggestフラグがオンの場合はResv Refresh Neededフラグをオンにし、そうでない場合は入力のRSBのResvConfirmオブジェクトのIPアドレスにResvConfメッセージを送信します。

5.1. Creation of multicast routing processor node

5.1. マルチキャストルーティングのプロセッサーノードの作成

Interfacing a multicast routing protocol using the OPNET Simulation package requires the creation of a new routing processor node in the node editor and linking it via packet streams. Packet streams are unidirectional links used to interconnect processor nodes, queue nodes, transmitters and receiver nodes. A duplex connection between two nodes is represented by using two unidirectional links to connect the two nodes to and from each other.

OPNETシミュレーションパッケージを使用してマルチキャストルーティングプロトコルをインターフェイスさせるには、ノードエディターで新しいルーティングのプロセッサーノードを作成し、パケットストリームを介してそれをリンクする必要があります。パケットストリームは、プロセッサーノード、キューノード、送信機ノード、受信機ノードを相互接続するために使用される単方向のリンクです。2つのノード間の全二重の接続は、2つの単方向のリンクを使用して2つのノードを相互に接続することで表されます。

A multicast routing processor node is created in the node editor and links are created to and from the processors(duplex connection) that interact with this module, the IGMP processor node and the IP processor node. Within the node editor, a new processor node can be created by selecting the button for processor creation (plain gray node on the node editor control panel) and by clicking on the desired location in the node editor to place the node. Upon creation of the processor node, the name of the processor can be specified by right clicking on the mouse button and entering the name value on the attribute box presented. Links to and from this node are generated by selecting the packet stream button (represented by two gray nodes connected with a solid green arrow on the node editor control panel), left clicking on the mouse button to specify the source of the link and right clicking on the mouse button to mark the destination of the link.

マルチキャストルーティングのプロセッサーノードをノードエディターで作成し、このモジュールとやり取りするプロセッサー、すなわちIGMPプロセッサーノードとIPプロセッサーノードとの間のリンク（全二重の接続）を作成します。ノードエディター内では、プロセッサーの作成のためのボタン（ノードエディターのコントロールパネル上の無地の灰色のノード）を選択し、ノードエディター内の目的の位置をクリックしてノードを配置することで、新しいプロセッサーノードを作成できます。プロセッサーノードの作成時に、マウスのボタンを右クリックし、表示される属性ボックスに名前の値を入力することで、プロセッサーの名前を指定できます。このノードとの間のリンクは、パケットストリームのボタン（ノードエディターのコントロールパネル上で、緑色の実線の矢印で接続された2つの灰色のノードで表されます）を選択し、マウスのボタンを左クリックしてリンクの送信元を指定し、マウスのボタンを右クリックしてリンクの宛先を示すことで生成されます。

5.2. Interfacing processor nodes

5.2. プロセッサーノードのインターフェイス

A duplex connection between two nodes is represented by two uni- directional links interconnecting them providing a bidirectional flow of information or interrupts, as shown in Figure 6. The IP processor node (in the subnet router) interfaces with the multicast routing processor node, the unicast routing processor node, the Resource Reservation processor node(RSVP), the ARP processor node( only on subnet routers and hosts), the IGMP processor node, and finally the MAC processor node (only on subnet routers and hosts) each with a duplex connection with exceptions for ARP and MAC nodes.

マルチキャストルーティングのプロセッサーノードは、IPプロセッサーノードとIGMPプロセッサーノードのそれぞれに全二重の接続でリンクされます。2つのノード間の全二重の接続は、図6に示すように、情報や割り込みの双方向の流れを提供する、それらを相互接続する2つの単方向のリンクで表されます。（サブネットのルーターの）IPプロセッサーノードは、マルチキャストルーティングのプロセッサーノード、ユニキャストルーティングのプロセッサーノード、リソース予約のプロセッサーノード（RSVP）、ARPプロセッサーノード（サブネットのルーターとホストのみ）、IGMPプロセッサーノード、そして最後にMACプロセッサーノード（サブネットのルーターとホストのみ）と、ARPとMACのノードを例外として、それぞれ全二重の接続でインターフェイスします。

5.2.1 Interfacing ARP and MAC processor nodes

5.2.1 ARPとMACのプロセッサーノードのインターフェイス

The service of the ARP node is required only in the direction from the IP layer to the MAC layer(requiring only a unidirectional link from IP processor node to ARP processor node). The MAC processor node on the subnet router receives multicast packets destined for all multicast groups in the subnet, in contrast to the MAC node on subnet hosts which only receives multicast packets destined specifically for its multicast group. The MAC node connects to the IP processor node with a single uni-directional link from it to the IP node.

ARPノードのサービスは、IP層からMAC層への方向でのみ必要です（IPプロセッサーノードからARPプロセッサーノードへの単方向のリンクだけが必要です）。サブネットのルーターのMACプロセッサーノードは、サブネット内のすべてのマルチキャストのグループ宛てのマルチキャストのパケットを受信します。これに対して、サブネットのホストのMACノードは、具体的に自身のマルチキャストのグループ宛てのマルチキャストのパケットだけを受信します。MACノードは、MACノードからIPノードへの単一の単方向のリンクでIPプロセッサーノードに接続します。

5.2.2 Interfacing IGMP, IP, and multicast routing processor nodes

5.2.2 IGMP、IP、およびマルチキャストルーティングのプロセッサーノードのインターフェイス

The IGMP processor node interacts with the multicast routing processor node, unicast routing processor node, and the IP processor node. Because the IGMP node is linked to the IP node, it is thus able to update the group membership table(in this model, the group membership table is represented by the local interface(interface 0) of the multicast routing table data structure) within the IP node. This update triggers a signal to the multicast routing processor node from the IGMP node causing it to reassess the multicast routing table within the IP node. If the change in the group membership table warrants a modification of the multicast routing table, the multicast routing processor node interacts with the IP node to modify the current multicast routing table according to the new group membership information updated by IGMP.

IGMPプロセッサーノードは、マルチキャストルーティングのプロセッサーノード、ユニキャストルーティングのプロセッサーノード、およびIPプロセッサーノードとやり取りします。IGMPノードはIPノードにリンクされているため、IPノード内のグループメンバーシップのテーブル（このモデルでは、グループメンバーシップのテーブルは、マルチキャストのルーティングテーブルのデータ構造のローカルのインターフェイス（インターフェイス0）で表されます）を更新できます。この更新により、IGMPノードからマルチキャストルーティングのプロセッサーノードへの信号が引き起こされ、IPノード内のマルチキャストのルーティングテーブルを再評価させます。グループメンバーシップのテーブルの変更がマルチキャストのルーティングテーブルの変更を必要とする場合、マルチキャストルーティングのプロセッサーノードは、IGMPによって更新された新しいグループメンバーシップの情報に従って現在のマルチキャストのルーティングテーブルを変更するために、IPノードとやり取りします。

5.2.2.1 Modification of group membership table

5.2.2.1 グループメンバーシップのテーブルの変更

The change in the group membership occurs with the decision at a host to leave or join a particular multicast group. The IGMP process on the gateway periodically sends out queries to the IGMP processes on hosts within the subnet in an attempt to determine which hosts currently are receiving packets from particular groups. Not receiving a response for a pending IGMP host query specific to a group indicates to the gateway IGMP that no host belonging to the particular group exists in the subnet. This occurs when the last remaining member of a multicast group in the subnet leaves. In this case the IGMP processor node updates the group membership able and triggers a modification of the multicast routing table by alerting the multicast routing processor node. A prune message specific to the group is initiated and propagated upward establishing a prune state for the interface leading to the present subnet, effectively removing this subnet from the group-specific multicast spanning tree and potentially leading to additional pruning of spanning tree edges as the prune message travels higher up the tree. Joining a multicast group is also managed by the IGMP process which updates the group membership table leading to a possible modification of the multicast routing table.

グループメンバーシップの変更は、ホストが特定のマルチキャストのグループから脱退するか参加するかを決定したときに起こります。ゲートウェイのIGMPのプロセスは、現在どのホストが特定のグループからパケットを受信しているかを判断するために、サブネット内のホストのIGMPのプロセスに定期的に問い合わせを送信します。グループに固有の保留中のIGMPのホストへの問い合わせに対する応答を受信しないことは、その特定のグループに属するホストがサブネット内に存在しないことをゲートウェイのIGMPに示します。これは、サブネット内のマルチキャストのグループの最後に残ったメンバーが脱退したときに発生します。この場合、IGMPプロセッサーノードはグループメンバーシップのテーブルを更新し、マルチキャストルーティングのプロセッサーノードに警告することで、マルチキャストのルーティングテーブルの変更を引き起こします。グループに固有の刈り込み（prune）メッセージが開始されて上方に伝播し、現在のサブネットにつながるインターフェイスについて刈り込みの状態を確立します。これにより、事実上、このサブネットはグループ固有のマルチキャストのスパニングツリーから取り除かれ、刈り込みメッセージがツリーのより上方に進むにつれて、スパニングツリーの辺がさらに刈り込まれる可能性があります。マルチキャストのグループへの参加もIGMPのプロセスによって管理され、IGMPのプロセスはグループメンバーシップのテーブルを更新し、それがマルチキャストのルーティングテーブルの変更につながる可能性があります。

5.2.2.2 Dependency on unicast routing protocol

5.2.2.2 ユニキャストルーティングプロトコルへの依存

The multicast routing protocol is dependent on a unicast routing protocol (RIP or OSPF) to handle multicast routing. The next hop interface to the source of the packet received, or the upstream interface, is determined using the unicast routing protocol to trace the reverse path back to the source of the packet. If the packet received arrived on this upstream interface, then the packet can be propagated downstream through its downstream interfaces (excluding the interface in which the packet was received). Otherwise, the packet is deemed to be a duplicate and dropped, halting the propagation of the packet downstream. This repeated reverse path checking and broadcasting eventually generates the spanning tree for multicast routing of packets. To determine the reverse path forward interface of a received multicast packet propagated up from the IP layer, the multicast routing processor node retrieves a copy of the unicast routing table from the IP processor node and uses it to recalculate the multicast routing table in the IP processor node.

マルチキャストルーティングプロトコルは、マルチキャストルーティングを扱うためにユニキャストルーティングプロトコル（RIPまたはOSPF）に依存しています。受信したパケットの送信元への次ホップのインターフェイス、すなわち上流のインターフェイスは、ユニキャストルーティングプロトコルを使用してパケットの送信元への逆方向のパスをたどることで決定されます。受信したパケットがこの上流のインターフェイスに到着した場合、パケットは（パケットを受信したインターフェイスを除く）下流のインターフェイスを通じて下流に伝播できます。そうでない場合、パケットは重複とみなされて破棄され、パケットの下流への伝播は止められます。この逆方向のパスの確認とブロードキャストの繰り返しにより、最終的にパケットのマルチキャストルーティングのためのスパニングツリーが生成されます。IP層から上に伝播された受信したマルチキャストのパケットの逆方向のパスの転送インターフェイスを決定するために、マルチキャストルーティングのプロセッサーノードは、IPプロセッサーノードからユニキャストのルーティングテーブルのコピーを取得し、それを使用してIPプロセッサーノードのマルチキャストのルーティングテーブルを再計算します。

5.3. Interrupt Generation

5.3. 割り込みの生成

Using the OPNET tools, interrupts to the multicast routing processor node are generated in several ways. One is the arrival of a multicast packet along a packet stream (at the multicast routing processor node) when the packet is received by the MAC node and propagated up the IP node where upon discarding the IP header determination is made as to which upper layer protocol to send the packet. A second type of interrupt generation occurs by remote interrupts from the IGMP process alerting the multicast routing process of an update in the group membership table. A third occurs when the specific source/group (S,G) entry for a multicast packet received at the IP node does not exist in the current multicast routing table and a new entry needs to be created. The IP node generates an interrupt to the multicast routing processor node informing it to create a new source/group entry on the multicast routing table.

OPNETのツールを使用すると、マルチキャストルーティングのプロセッサーノードへの割り込みはいくつかの方法で生成されます。1つは、パケットがMACノードで受信され、IPノードに上に伝播され、そこでIPヘッダーを破棄する際にどの上位層のプロトコルにパケットを送信するかが決定されたときの、（マルチキャストルーティングのプロセッサーノードでの）パケットストリームに沿ったマルチキャストのパケットの到着です。2つ目の種類の割り込みの生成は、グループメンバーシップのテーブルの更新をマルチキャストルーティングのプロセスに警告する、IGMPのプロセスからのリモート割り込みによって発生します。3つ目は、IPノードで受信したマルチキャストのパケットに対する特定の送信元/グループ（S,G）のエントリーが現在のマルチキャストのルーティングテーブルに存在せず、新しいエントリーを作成する必要がある場合に発生します。IPノードは、マルチキャストのルーティングテーブルに新しい送信元/グループのエントリーを作成するよう知らせる割り込みを、マルチキャストルーティングのプロセッサーノードに生成します。

5.3.1 Types of interrupts

5.3.1 割り込みの種類

The process interrupts generated within the OPNET model can be handled by specifying the types of interrupts and the conditions for the interrupts using the interrupt code, integer number representing the condition for a specific interrupt. The conditions for interrupts are specified on the interrupt stream linking the interrupt generating state and the state resulting from the interrupt. For self-interrupts (interrupts occurring among states within the same process), interrupts of type OPC_INTRPT_SELF are used. For remote interrupts (interprocess interrupts), the conditions for specific interrupts are specified from the idle state to the state resulting from the interrupt within the remote process.

OPNETのモデル内で生成されるプロセスの割り込みは、割り込みコード、すなわち特定の割り込みの条件を表す整数を使用して、割り込みの種類と割り込みの条件を指定することで扱うことができます。割り込みの条件は、割り込みを生成する状態と割り込みの結果となる状態をつなぐ割り込みストリーム上で指定されます。自己割り込み（同じプロセス内の状態の間で発生する割り込み）には、OPC_INTRPT_SELFの種類の割り込みが使用されます。リモート割り込み（プロセス間の割り込み）の場合、特定の割り込みの条件は、リモートのプロセス内のidleの状態から割り込みの結果となる状態に向けて指定されます。

The remote interrupts are of type, OPC_INTRPT_REMOTE. A third type of interrupt is the OPC_INTRPT_STRM, which is triggered when packets arrive via a packet stream, indicating its arrival. The condition of this interrupt is also specified from the idle state to the resultant state by the interrupt condition stream defined by a unique interrupt code. For all of these interrupts, the interrupt code is provided within the header block (written in C language) of the interrupted process. When the condition for the interrupt becomes true, a transition is made to the resultant state specified by the interrupt stream.

リモート割り込みの種類はOPC_INTRPT_REMOTEです。3つ目の種類の割り込みはOPC_INTRPT_STRMであり、パケットストリームを介してパケットが到着したときに、その到着を示すために引き起こされます。この割り込みの条件も、一意な割り込みコードで定義された割り込み条件のストリームによって、idleの状態から結果の状態に向けて指定されます。これらすべての割り込みについて、割り込みコードは、割り込まれるプロセスのヘッダーブロック（C言語で書かれます）内で提供されます。割り込みの条件が真になると、割り込みストリームで指定された結果の状態への遷移が行われます。

5.3.2 Conditions for interrupts

5.3.2 割り込みの条件

Several interrupt connections exist to interface the IGMP processor node, IP processor node , and the multicast routing processor node with each other in the present OPNET Simulation Model. Also, the IP processor node interfaces with the unicast routing protocol which interfaces with the IGMP processor node. An OPC_INTRPT_STRM interrupt is generated when a multicast packet arrives via a packet stream from the IP processor node to the multicast routing processor node. A remote interrupt of type, OPC_INTRPT_REMOTE, is generated from the IGMP process to the IP process when a member of a group relinquishes membership from a particular group or a new member is added to a group. This new membership is updated in the group membership table located in the IP node by the IGMP process which also generates a remote interrupt to the multicast routing protocol process, causing a recalculation of the multicast routing table in the IP module.

現在のOPNETシミュレーションモデルでは、IGMPプロセッサーノード、IPプロセッサーノード、およびマルチキャストルーティングのプロセッサーノードを相互にインターフェイスさせるために、いくつかの割り込みの接続が存在します。また、IPプロセッサーノードはユニキャストルーティングプロトコルとインターフェイスし、ユニキャストルーティングプロトコルはIGMPプロセッサーノードとインターフェイスします。マルチキャストのパケットがパケットストリームを介してIPプロセッサーノードからマルチキャストルーティングのプロセッサーノードに到着すると、OPC_INTRPT_STRMの割り込みが生成されます。グループのメンバーが特定のグループのメンバーシップを放棄したとき、または新しいメンバーがグループに追加されたときには、IGMPのプロセスからIPのプロセスへのOPC_INTRPT_REMOTEの種類のリモート割り込みが生成されます。この新しいメンバーシップは、IGMPのプロセスによってIPノード内にあるグループメンバーシップのテーブルで更新され、IGMPのプロセスはマルチキャストルーティングプロトコルのプロセスへのリモート割り込みも生成し、IPモジュール内のマルチキャストのルーティングテーブルの再計算を引き起こします。

5.4. Modifications of modules in the process model

5.4. プロセスモデル内のモジュールの変更

Modifications of routing protocol modules (in fact all of the modules in the process model) are made transparently throughout the network using the OPNET Simulation tools. An addition or modification of a routing module in any subnet will reflect on all the subnets.

ルーティングプロトコルのモジュール（実際にはプロセスモデル内のすべてのモジュール）の変更は、OPNETシミュレーションのツールを使用して、ネットワーク全体で透過的に行われます。任意のサブネットでのルーティングモジュールの追加や変更は、すべてのサブネットに反映されます。

6. OSPFとMOSPFのモデル

OSPFとMOSPFのモデル[5]は、14の状態を含むOSPFのモデルとして実装されています。これらはルーター上にのみ存在します。図10はそのプロセスモデルを示しています。示されたモジュールでは、以下の処理が行われます。

6.1. init

6.1. init

This state initializes all the router variables. Default transition to idle state.

この状態は、ルーターのすべての変数を初期化します。デフォルトでidleの状態に遷移します。

6.2. idle

6.2. idle

This state has several transitions. If a packet arrives it transits to arr state. Depending on interrupts received it will transit to BCOspfLsa, BCMospfLsa, hello_pks state. In future versions, links coming up or down will also cause a transition.

この状態には、いくつかの遷移があります。パケットが到着すると、arrの状態に遷移します。受信した割り込みに応じて、BCOspfLsa、BCMospfLsa、hello_pksの状態に遷移します。将来のバージョンでは、リンクの起動や停止も遷移を引き起こします。

6.3. BCOspfLsa

6.3. BCOspfLsa

This state will create Router, Network, Summary Link State Advertisements and pack all of them into an Link State Update packet. The Link State Update Packet is sent to the IP layer with a destination address of AllSPFRouters.

idleの状態からこの状態への遷移は、条件send_ospf_lsaが真になるたびに実行されます。これは、ネットワークの初期化中と、ospf_lsa_refresh_timoutが発生したときに起こります。この状態は、Router、Network、Summaryのリンク状態広告を作成し、それらすべてをLink State Updateパケットにまとめます。Link State UpdateパケットはAllSPFRoutersの宛先アドレスでIP層に送信されます。

6.4. BCMospfLsa

6.4. BCMospfLsa

Transition to this state from idle state is executed whenever the condition send_mospf_lsa is true. This state will create Group Membership Link State Advertisement and pack them into Mospf Link State Update Packet. This Mospf Link State Update Packet is sent to IP layer with a destination address of AllSPFRouters.

idleの状態からこの状態への遷移は、条件send_mospf_lsaが真になるたびに実行されます。この状態は、Group Membershipのリンク状態広告を作成し、それらをMospf Link State Updateパケットにまとめます。このMospf Link State UpdateパケットはAllSPFRoutersの宛先アドレスでIP層に送信されます。

6.5. arr

6.5. arr

The arr state checks the type of packet that is received upon a packet arrival. It calls the following functions depending on the protocol Id of the packet received.

arrの状態は、パケットの到着時に受信したパケットの種類を確認します。受信したパケットのプロトコルIDに応じて、以下の関数を呼び出します。

  1. OspfPkPro: Depending on the type of OSPF/MOSPF packet received the function calls the following functions.
  2. HelloPk_pro: This function is called whenever a hello packet is received. This function updates the router's neighbor information, which is later used while sending the different LSAs.
  3. OspfLsUpdatePk_pro: This function is called when an OSPF LSA update packet is received (router LSA, network LSA, or summary LSA). If the Router is an Area Border Router or if the LSA belongs to the Area whose Area Id is the Routers Area Id, then it is searched to determine whether this LSA already exists in the Link State database. If it exists and if the existing LSA's LS Sequence Number is less than the received LSA's LS Sequence Number the existing LSA was replaced with the received one. The function processes the Network LSA only if it is a designated router or Area Border Router. It processes the Summary LSA only if the router is a Area Border Router. The function also turns on the trigger ospfspfcalc which is the condition for the transition from arr state to ospfspfcalc.
  4. MospfLsUpdatePk_pro: This function is called when a MOSPF LSA update packet is received. It updates the group membership link state database of the router.
  1. OspfPkPro：受信したOSPF/MOSPFパケットの種類に応じて、この関数は以下の関数を呼び出します。
  2. HelloPk_pro：この関数は、helloパケットを受信するたびに呼び出されます。この関数はルーターの隣接ルーターの情報を更新し、その情報は後でさまざまなLSAを送信する際に使用されます。
  3. OspfLsUpdatePk_pro：この関数は、OSPFのLSA更新パケット（ルーターLSA、ネットワークLSA、またはサマリーLSA）を受信したときに呼び出されます。ルーターがエリア境界ルーターである場合、またはLSAがルーターのエリアIDをエリアIDとするエリアに属している場合は、このLSAがすでにリンク状態データベースに存在するかどうかを判断するために検索されます。存在し、既存のLSAのLSシーケンス番号が受信したLSAのLSシーケンス番号より小さい場合、既存のLSAは受信したものに置き換えられます。この関数は、指定ルーターまたはエリア境界ルーターである場合にのみネットワークLSAを処理します。サマリーLSAは、ルーターがエリア境界ルーターである場合にのみ処理します。この関数はまた、arrの状態からospfspfcalcへの遷移の条件であるトリガーospfspfcalcをオンにします。
  4. MospfLsUpdatePk_pro：この関数は、MOSPFのLSA更新パケットを受信したときに呼び出されます。ルーターのグループメンバーシップのリンク状態データベースを更新します。

6.6. hello_pks

6.6. hello_pks

Hello packets are created and sent with destination address of AllSPFRouters. Default transition to idle state.

helloパケットが作成され、AllSPFRoutersの宛先アドレスで送信されます。デフォルトでidleの状態に遷移します。

6.7. mospfspfcalc

6.7. mospfspfcalc

The following functions are used to calculate the shortest path tree and routing table. This state transit to upstr_node upon detupstrnode condition.

最短パスツリーとルーティングテーブルの計算には、以下の関数が使用されます。この状態は、detupstrnodeの条件でupstr_nodeに遷移します。

  1. CandListInit: Depending upon the SourceNet of the datagram, the candidate lists are initialized.
  2. MospfCandAddPro: The vertex link is examined and if the other end of the link is not a stub network and is not already in the candidate list it is added to the candidate list after calculating the cost to that vertex. If this other end of the link is already on the shortest path tree and the calculated cost is less than the one that shows in the shortest path tree entry update the shortest path tree to show the calculated cost.
  3. MospfSPFTreeCalc: The vertex that is closest to the root that is in the candidate list is added to the shortest path tree and its link is considered for possible inclusions in the candidate list.
  4. MCRoutetableCalc: Multicast routing table is calculated using the information of the MOSPF shortest Path tree.
  1. CandListInit：データグラムのSourceNetに応じて、候補リストが初期化されます。
  2. MospfCandAddPro：頂点のリンクが調べられ、リンクのもう一方の端がスタブネットワークではなく、まだ候補リストにない場合は、その頂点へのコストを計算したあとで候補リストに追加されます。リンクのもう一方の端がすでに最短パスツリー上にあり、計算されたコストが最短パスツリーのエントリーに示されているものより小さい場合は、計算されたコストを示すように最短パスツリーを更新します。
  3. MospfSPFTreeCalc：候補リストの中で根に最も近い頂点が最短パスツリーに追加され、そのリンクが候補リストに含める候補として検討されます。
  4. MCRoutetableCalc：マルチキャストのルーティングテーブルは、MOSPFの最短パスツリーの情報を使用して計算されます。

6.8. ospfspfcalc

6.8. ospfspfcalc

The following functions are used in this state to calculate the shortest path tree and using this information the routing table. Transition to ospfspfcalc state on ospfcalc condition. This is set to one after processing all functions in the state.

この状態では、最短パスツリーを計算し、その情報を使用してルーティングテーブルを計算するために、以下の関数が使用されます。ospfcalcの条件でospfspfcalcの状態に遷移します。これは、この状態のすべての関数を処理したあとで1に設定されます。

  1. OspfCandidateAddPro: This function initializes the candidate list by examining the link state advertisement of the Router. For each link in this advertisement, if the other end of the link is a router or transit network and if it is not already in the shortest-path tree then calculate the distance between these vertices. If the other end of this link is not already on the candidate list or if the distance calculated is less than the value that appears for this other end add the other end of the link to candidate list.
  2. OspfSPTreeBuild: This function pulls each vertex from the candidate list that is closest to the root and adds it to the shortest path tree. In doing so it deletes the vertex from the candidate list. This function continues to do this until the candidate list is empty.
  3. OspfStubLinkPro: In this procedure the stub networks are added to shortest path tree.
  4. OspfSummaryLinkPro: If the router is an Area Border Router the summary links that it has received is examined. The route to the Area border router advertising this summary LSA is examined in the routing table. If one is found a routing table update is done by adding the route to the network specified in the summary LSA and the cost to this route is sum of the cost to area border router advertising this and the cost to reach this network from that area border router.
  5. RoutingTableCalc: This function updates the routing table by examining the shortest path tree data structure.
  1. OspfCandidateAddPro：この関数は、ルーターのリンク状態広告を調べることで候補リストを初期化します。この広告の各リンクについて、リンクのもう一方の端がルーターまたはトランジットネットワークであり、まだ最短パスツリーにない場合は、これらの頂点間の距離を計算します。リンクのもう一方の端がまだ候補リストにない場合、または計算された距離がこのもう一方の端について示されている値より小さい場合は、リンクのもう一方の端を候補リストに追加します。
  2. OspfSPTreeBuild：この関数は、候補リストから根に最も近い頂点を1つずつ取り出し、最短パスツリーに追加します。その際、その頂点を候補リストから削除します。この関数は、候補リストが空になるまでこれを続けます。
  3. OspfStubLinkPro：この手順では、スタブネットワークが最短パスツリーに追加されます。
  4. OspfSummaryLinkPro：ルーターがエリア境界ルーターである場合は、受信したサマリーリンクが調べられます。このサマリーLSAを広告しているエリア境界ルーターへの経路が、ルーティングテーブルの中で調べられます。見つかった場合は、サマリーLSAで指定されたネットワークへの経路を追加することでルーティングテーブルの更新が行われます。この経路へのコストは、これを広告しているエリア境界ルーターへのコストと、そのエリア境界ルーターからこのネットワークに到達するためのコストの合計です。
  5. RoutingTableCalc：この関数は、最短パスツリーのデータ構造を調べることでルーティングテーブルを更新します。

6.9. upstr_node

6.9. upstr_node

This state does not do anything in the present model. It transitions to DABRA state.

現在のモデルでは、この状態は何も行いません。DABRAの状態に遷移します。

6.10. DABRA

6.10. DABRA

If the router is an Area Border Router and the area is the source area then a DABRA message is constructed and send to all the downstream areas. Default transition to idle state.

ルーターがエリア境界ルーターであり、エリアが送信元のエリアである場合は、DABRAメッセージが構築され、すべての下流のエリアに送信されます。デフォルトでidleの状態に遷移します。

7. DVMRP Model

7. DVMRPのモデル

The DVMRP model is implemented based on reference [6], DVMRP version 3. There are nine states. The DVMRP process only exists on Routers. Figure 11 shows the states of the DVMRP process.

DVMRPのモデルは、参考文献[6]のDVMRPバージョン3に基づいて実装されています。9つの状態があります。DVMRPのプロセスはルーター上にのみ存在します。図11はDVMRPのプロセスの状態を示しています。

7.1. Init

7.1. Init

Initialize all variables, routing table and forwarding table and load the simulation parameters. It will transit to the Idle state after completing all the initializations.

すべての変数、ルーティングテーブル、および転送テーブルを初期化し、シミュレーションのパラメーターを読み込みます。すべての初期化が完了したあと、Idleの状態に遷移します。

7.2. Idle

7.2. Idle

The simulation waits for the next scheduled event or remotely invoked event in the Idle State and transit to the state accordingly. In the DVMRP model, Idle State has transitions to Probe_Send, Report_Send, Prune_Send, Graft_Send, Arr_Pkt, Route_Calc and Timer states.

シミュレーションは、Idleの状態で次にスケジュールされたイベントまたはリモートで呼び出されたイベントを待ち、それに応じた状態に遷移します。DVMRPのモデルでは、Idleの状態はProbe_Send、Report_Send、Prune_Send、Graft_Send、Arr_Pkt、Route_Calc、Timerの各状態への遷移を持ちます。

[Figure 11. DVMRP process on routers]

［図11：ルーター上のDVMRPのプロセス］

7.3. Probe_Send State

7.3. Probe_Sendの状態

A DVMRP router sends Probe messages periodically to inform other DVMRP routers that it is operational. A DVMRP router lists all its known neighbors' addresses in the Probe message and sends it to All- DVMRP-Routers address. The routers will not process any message that comes from an unknown neighbor.

DVMRPルーターは、自身が動作していることを他のDVMRPルーターに知らせるために、定期的にProbeメッセージを送信します。DVMRPルーターは、既知のすべての隣接ルーターのアドレスをProbeメッセージに列挙し、All-DVMRP-Routersアドレスに送信します。ルーターは、未知の隣接ルーターから来たメッセージを処理しません。

7.4. Report_Send

7.4. Report_Send

To avoid sending Report at the same time for all DVMRP routers, the interval between two Report messages is uniformly distributed with average 60 seconds. The router lists source router's address, upstream router's address and metric of all sources into the Report message and sends it to All-DVMRP-Routers address.

すべてのDVMRPルーターが同時にReportを送信するのを避けるため、2つのReportメッセージの間隔は平均60秒の一様分布に従います。ルーターは、すべての送信元について、送信元ルーターのアドレス、上流のルーターのアドレス、およびメトリックをReportメッセージに列挙し、All-DVMRP-Routersアドレスに送信します。

7.5. Prune_Send

7.5. Prune_Send

The transition to this state is triggered by the local IGMP process. When a host on the subnetwork drops from a group, the IGMP process asks DVMRP to see if the branch should be pruned.

この状態への遷移は、ローカルのIGMPのプロセスによって引き起こされます。サブネットワーク上のホストがグループから離れると、IGMPのプロセスはDVMRPに枝を刈り込むべきかどうかを確認するよう求めます。

The router obtains the group number from IGMP and checks the IP Multicast membership table to find out if there is any group member that is still in the group. If the router determines that the last host has resigned, it goes through the entire forwarding table to locate all sources for that group. The router sends Prune message, containing source address, group address and prune lifetime, separately for each (source, group) pair and records the row as pruned in the forwarding table.

ルーターはIGMPからグループ番号を取得し、IPマルチキャストのメンバーシップのテーブルを確認して、まだグループに残っているグループのメンバーがいるかどうかを調べます。最後のホストが脱退したと判断した場合、ルーターは転送テーブル全体を調べて、そのグループのすべての送信元を見つけます。ルーターは、（送信元、グループ）の組ごとに個別に、送信元アドレス、グループアドレス、および刈り込みの有効期間を含むPruneメッセージを送信し、転送テーブルのその行を刈り込み済みとして記録します。

7.6. Graft_Send

7.6. Graft_Send

The transition to this state is triggered by the local IGMP process. Once a multicast delivery has been pruned, Graft messages are necessary when a host in the local subnetwork joins into the group. A Graft message sent to the upstream router should be acknowledged hop by hop to the root of the tree guaranteeing end-to-end delivery.

この状態への遷移は、ローカルのIGMPのプロセスによって引き起こされます。マルチキャストの配送がいったん刈り込まれると、ローカルのサブネットワーク内のホストがグループに参加したときにGraftメッセージが必要になります。上流のルーターに送信されたGraftメッセージは、エンドツーエンドの配送を保証するために、ツリーの根までホップごとに確認応答されるべきです。

The router obtains the group number from IGMP and go through the forwarding table to locate all traffic sources for that group. A Graft message will be sent to the upstream router with the source address and group address for each (source, group) pair. The router also setups a timer for each Graft message waiting for an acknowledgement.

ルーターはIGMPからグループ番号を取得し、転送テーブルを調べて、そのグループのすべてのトラフィックの送信元を見つけます。（送信元、グループ）の組ごとに、送信元アドレスとグループアドレスを含むGraftメッセージが上流のルーターに送信されます。ルーターはまた、確認応答を待つGraftメッセージごとにタイマーを設定します。

7.7. Arr_Pkt

7.7. Arr_Pkt

All DVMRP control messages will be sent up to DVMRP layer by IP. The function performed by the DVMRP layer depends upon the type of the message received.

すべてのDVMRPの制御メッセージは、IPによってDVMRP層に上げられます。DVMRP層が行う機能は、受信したメッセージの種類によって異なります。

  1. Probe message: The router checks the neighbors' list in Probe message, update its their status to indicate the availability of its neighbors.
  2. Report message: Based on exchanging report messages, the routers can build the Multicast delivery tree rooted at each source. A function called ReportPkPro will be called to handle all possible situations when receiving a report message. If the message is a poison reverse report and not coming from one of the dependent downstreams, the incoming interface should be added to the router's downstream list. If the message is not a poison reverse report but it came from one of the downstreams, this interface should be deleted from the downstreams list. And then, the router compared the metric got from the message with the metric of the current upstream, if the new metric is less than the older one, the router's upstream interface should be updated.
  3. Prune message: The router extracts the source address, group address and prune lifetime, marks the incoming interface as pruned in the dependent downstream list of the (source, group) pair. If all downstream interfaces have been pruned, the router will send a prune message to its upstream.
  4. Graft message: The router extracts the source and group address, active the incoming interface in the dependent downstream list of the (source, group) pair. If the (source, group) pair has been pruned, the router will reconnect the branch by sending a graft message to its upstream interface.
  5. Graft Acknowledge message: The router extracts the source and group address, clear the graft message timer of the (source, group) pair in the forwarding table.
  1. Probeメッセージ：ルーターはProbeメッセージ内の隣接ルーターのリストを確認し、隣接ルーターが利用可能であることを示すようにその状態を更新します。
  2. Reportメッセージ：Reportメッセージを交換することで、ルーターは各送信元を根とするマルチキャストの配送ツリーを構築できます。Reportメッセージを受信したときに考えられるすべての状況を扱うために、ReportPkProという関数が呼び出されます。メッセージがポイズンリバースのReportであり、依存する下流のいずれかから来たものでない場合は、受信インターフェイスをルーターの下流のリストに追加すべきです。メッセージがポイズンリバースのReportではないが、下流のいずれかから来た場合は、このインターフェイスを下流のリストから削除すべきです。その後、ルーターはメッセージから得たメトリックを現在の上流のメトリックと比較し、新しいメトリックが古いものより小さい場合は、ルーターの上流のインターフェイスを更新すべきです。
  3. Pruneメッセージ：ルーターは送信元アドレス、グループアドレス、および刈り込みの有効期間を取り出し、（送信元、グループ）の組の依存する下流のリストの中で受信インターフェイスを刈り込み済みとしてマークします。すべての下流のインターフェイスが刈り込まれた場合、ルーターは上流にPruneメッセージを送信します。
  4. Graftメッセージ：ルーターは送信元アドレスとグループアドレスを取り出し、（送信元、グループ）の組の依存する下流のリストの中で受信インターフェイスを有効にします。（送信元、グループ）の組が刈り込まれている場合、ルーターは上流のインターフェイスにGraftメッセージを送信することで枝を再接続します。
  5. Graft Acknowledgeメッセージ：ルーターは送信元アドレスとグループアドレスを取り出し、転送テーブルの中の（送信元、グループ）の組のGraftメッセージのタイマーを解除します。

7.8. Route_Calc

7.8. Route_Calc

The transition to this state is triggered by the local IP process. Once the IP receives a packet, it will fire a remote interrupt to the DVMRP and ask the DVMRP to prepare the outgoing interfaces for the packet. The DVMRP process obtains the packet's source address and group address from the IP and checks the (source, group) pairs in the forwarding table to decide the branches that have the group members on the Multicast delivery tree. The Group Membership Table on IP will be updated based on this knowledge.

この状態への遷移は、ローカルのIPのプロセスによって引き起こされます。IPはパケットを受信すると、DVMRPにリモート割り込みを発生させ、パケットの送信インターフェイスを準備するようDVMRPに求めます。DVMRPのプロセスは、IPからパケットの送信元アドレスとグループアドレスを取得し、転送テーブル内の（送信元、グループ）の組を確認して、マルチキャストの配送ツリー上でグループのメンバーを持つ枝を決定します。IP上のグループメンバーシップのテーブルは、この知識に基づいて更新されます。

7.9. Timer

7.9. Timer

This state is activated once every second. It checks the forwarding table, if the Graft message acknowledgment timer is expired, The router will retransmit the Graft message to the upstream. If the prune state lifetime timer is expired, the router will graft this interface so that the downstream router can receive the packets to the group again. The router also checks if the (source, group) pair is pruned by the upstream router, if so, it will send a graft message to the upstream interface.

この状態は1秒に1回起動されます。転送テーブルを確認し、Graftメッセージの確認応答のタイマーが満了している場合、ルーターはGraftメッセージを上流に再送信します。刈り込みの状態の有効期間のタイマーが満了している場合、ルーターは下流のルーターが再びそのグループへのパケットを受信できるように、このインターフェイスを接ぎ木します。ルーターはまた、（送信元、グループ）の組が上流のルーターによって刈り込まれているかどうかを確認し、刈り込まれている場合は上流のインターフェイスにGraftメッセージを送信します。
