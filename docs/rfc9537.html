Redacted Fields in the Registration Data Access Protocol (RDAP) Response

Abstract

概要

This document describes a Registration Data Access Protocol (RDAP) extension for specifying methods of redaction of RDAP responses and explicitly identifying redacted RDAP response fields, using JSONPath as the default expression language.

この文書は、JSONPathをデフォルトの式言語として使用して、RDAPレスポンスの秘匿化（redaction）の方式を指定し、秘匿化されたRDAPレスポンスのフィールドを明示的に識別するための、Registration Data Access Protocol（RDAP）の拡張について説明します。

1. Introduction

1. はじめに

This document describes an RDAP extension for specifying methods of redaction of RDAP responses and explicitly identifying redacted RDAP response fields, using JSONPath as the default expression language. A redacted RDAP field is one that has data removed or replaced in the RDAP response due to server policy, such as the lack of client privilege to receive the field. This extension can be used to identify redacted RDAP fields in any RDAP object class, as defined in [RFC9083], or RDAP fields defined in RDAP extensions. Because an RDAP response may exclude a field due to either the lack of data or the lack of RDAP client privileges, this extension is used to explicitly specify which RDAP fields are not included in the RDAP response due to redaction. It thereby provides a capability for disambiguation between redaction and other possible reasons for data or field absence.

この文書は、JSONPathをデフォルトの式言語として使用して、RDAPレスポンスの秘匿化の方式を指定し、秘匿化されたRDAPレスポンスのフィールドを明示的に識別するための、RDAPの拡張について説明します。秘匿化されたRDAPフィールドとは、フィールドを受け取るためのクライアントの権限がないことなどのサーバーポリシーにより、RDAPレスポンス内でデータが削除または置換されたフィールドのことです。この拡張は、[RFC9083]で定義されている任意のRDAPオブジェクトクラス、またはRDAP拡張で定義されたRDAPフィールドにおいて、秘匿化されたRDAPフィールドを識別するために使用できます。RDAPレスポンスは、データがないこと、またはRDAPクライアントの権限がないことのいずれかによってフィールドを除外する場合があるため、この拡張は、どのRDAPフィールドが秘匿化によってRDAPレスポンスに含まれていないのかを明示的に指定するために使用されます。これにより、秘匿化と、データやフィールドが存在しない他の考えられる理由とを区別するための能力を提供します。

In [RFC9082], RDAP supports both lookup and search queries, where a lookup query responds with a single object and a search query responds with a list of objects. This document applies to redaction of a single object of a lookup response and in each of the objects of a search response.

[RFC9082]では、RDAPはルックアップクエリーと検索クエリーの両方をサポートしています。ルックアップクエリーは単一のオブジェクトで応答し、検索クエリーはオブジェクトのリストで応答します。この文書は、ルックアップレスポンスの単一のオブジェクトの秘匿化と、検索レスポンスの各オブジェクトの秘匿化に適用されます。

JSONPath, as defined in [RFC9535], is used as the default expression language to reference RDAP fields that have been redacted. The redacted JSON fields will be removed, have empty values, have partial values, or be replaced in the RDAP response. JSON is defined by [RFC8259].

[RFC9535]で定義されているJSONPathは、秘匿化されたRDAPフィールドを参照するためのデフォルトの式言語として使用されます。秘匿化されたJSONフィールドは、RDAPレスポンスにおいて、削除されるか、空の値を持つか、部分的な値を持つか、置換されます。JSONは[RFC8259]で定義されています。

3. Redaction Methods

3. 秘匿化の方式

Redaction in RDAP can be handled in multiple ways. The resulting redacted RDAP response MUST comply with the format defined in the RDAP RFCs, such as [RFC9083] and updates. The use of placeholder text for the values of the RDAP fields, such as "XXXX", MUST NOT be used for redaction, since the placeholder text value may not match the format requirements of each of the RDAP fields, which could provide an inconsistent and unreliable redaction signal. This section covers the redaction methods that can be used with the redaction signaling defined in Section 4.2.

RDAPにおける秘匿化は、複数の方法で扱うことができます。秘匿化の結果として得られるRDAPレスポンスは、[RFC9083]とその更新などのRDAPのRFCで定義されている形式に準拠しなければなりません（MUST）。RDAPフィールドの値に「XXXX」などのプレースホルダーテキストを使用することを、秘匿化のために用いてはなりません（MUST NOT）。プレースホルダーテキストの値は各RDAPフィールドの形式要件に一致しない可能性があり、一貫性がなく信頼できない秘匿化のシグナルとなるおそれがあるためです。このセクションでは、Section 4.2で定義する秘匿化のシグナリングとともに使用できる秘匿化の方式について説明します。

RDAP responses, as defined in [RFC9083], include a mix of JSON objects and JSON arrays, where JSON arrays are heavily used for entity objects with [RFC7095]. jCard is a JSON representation of [RFC6350] that inherits its dependency on arrays. An example is the vCard "ADR" property [RFC6350], or the jCard "adr" property [RFC7095], which defines a sequence of address components. According to [RFC6350], when an "ADR" property component value is missing, the associated component separator MUST still be specified. jCard extends the use of arrays with each individual vCard property being represented by an array of three fixed elements, followed by one or more additional elements. The mix of JSON objects and JSON arrays impacts the methods used for redaction in RDAP.

[RFC9083]で定義されているRDAPレスポンスには、JSONオブジェクトとJSON配列が混在しており、JSON配列は[RFC7095]を含むエンティティーオブジェクトで多用されています。jCardは[RFC6350]のJSON表現であり、配列への依存を引き継いでいます。その一例が、住所の構成要素の並びを定義するvCardの「ADR」プロパティー[RFC6350]、すなわちjCardの「adr」プロパティー[RFC7095]です。[RFC6350]によれば、「ADR」プロパティーの構成要素の値が欠けている場合でも、関連する構成要素の区切り文字は指定しなければなりません（MUST）。jCardは配列の使用を拡張しており、個々のvCardプロパティーを、3つの固定要素とそれに続く1つ以上の追加要素からなる配列で表現します。JSONオブジェクトとJSON配列が混在していることは、RDAPにおける秘匿化に使用される方式に影響を与えます。

The redaction of RDAP fields fall into the four categories defined in the following subsections.

RDAPフィールドの秘匿化は、以下のサブセクションで定義する4つのカテゴリーに分類されます。

3.1. Redaction by Removal Method

3.1. 削除による秘匿化方式

The Redaction by Removal Method is when the RDAP field is removed from the RDAP response, which is the default method. The Redaction by Removal Method can be done for all RDAP response fields except for response fields using the position in an array to signal the redacted field (e.g., the JSON arrays used with jCard). RDAP extensions, such as the one described in [RDAP-JSCONTACT], do not have a dependency on the use of positional JSON arrays and are therefore suited for the Redaction by Removal Method.

削除による秘匿化方式（Redaction by Removal Method）は、RDAPフィールドをRDAPレスポンスから削除するもので、これがデフォルトの方式です。削除による秘匿化方式は、配列内の位置を使用して秘匿化されたフィールドを示すレスポンスフィールド（たとえば、jCardで使用されるJSON配列）を除くすべてのRDAPレスポンスフィールドに対して実行できます。[RDAP-JSCONTACT]で説明されているもののようなRDAP拡張は、位置に依存するJSON配列の使用に依存していないため、削除による秘匿化方式に適しています。

When an RDAP object is redacted by removal, all of the RDAP object's child fields are also removed. Only the redacted RDAP object needs to be referenced in the list of redacted fields, as defined in Section 4.2.

RDAPオブジェクトが削除によって秘匿化される場合、そのRDAPオブジェクトのすべての子フィールドも削除されます。Section 4.2で定義する秘匿化されたフィールドのリストでは、秘匿化されたRDAPオブジェクトだけを参照すれば十分です。

RDAPオブジェクトを秘匿化する例として、RDAPレスポンスから管理連絡先を削除し、次の「redacted」メンバーを含めるものがあります：

The Redaction by Removal Method MUST NOT be used to remove an element of an array where the position of the element in the array determines semantic meaning. For example, removal of an individual data field in jCard will result in a non-conformant jCard array definition.

削除による秘匿化方式は、配列内の要素の位置が意味を決定する配列の要素を削除するために使用してはなりません（MUST NOT）。たとえば、jCardの個々のデータフィールドを削除すると、jCard配列の定義に準拠しないものになります。

3.2. Redaction by Empty Value Method

3.2. 空値による秘匿化方式

The Redaction by Empty Value Method is when a redacted field is not removed but its value is set to an empty value, such as "" for a jCard text ("text") property or null for a non-text property. The empty jCard values ("" or null) are referenced in the "redacted" member in place of the jCard property name in an array, such as referencing the "fn" jCard property value at position 3 instead of referencing the "fn" jCard property name at position 0. The Redaction by Empty Value Method MUST be used only when redacting JSON response fields that use the position in an array to signal the redacted field (e.g., jCard arrays). Optional jCard properties MUST use the Section 3.1 to redact the entire property. The required jCard "fn" property, defined in Section 6.2.1 of [RFC6350], MUST use the Redaction by Empty Value Method to redact the property value. Removing the "fn" property would violate [RFC6350], and removing the property value would violate the fixed array positions defined in jCard.

空値による秘匿化方式（Redaction by Empty Value Method）は、秘匿化されたフィールドを削除せずに、その値を空の値に設定するものです。たとえば、jCardのテキスト（「text」）プロパティーであれば""、テキスト以外のプロパティーであればnullに設定します。空のjCardの値（""またはnull）は、「redacted」メンバーにおいて、配列内のjCardプロパティー名の代わりに参照されます。たとえば、位置0にある「fn」jCardプロパティー名を参照する代わりに、位置3にある「fn」jCardプロパティーの値を参照します。空値による秘匿化方式は、配列内の位置を使用して秘匿化されたフィールドを示すJSONレスポンスフィールド（たとえば、jCard配列）を秘匿化する場合にのみ使用しなければなりません（MUST）。省略可能なjCardプロパティーは、プロパティー全体を秘匿化するために、Section 3.1を使用しなければなりません（MUST）。[RFC6350]のSection 6.2.1で定義されている必須のjCard「fn」プロパティーは、プロパティーの値を秘匿化するために空値による秘匿化方式を使用しなければなりません（MUST）。「fn」プロパティーを削除すると[RFC6350]に違反し、プロパティーの値を削除するとjCardで定義されている固定の配列位置に違反します。

3.3. Redaction by Partial Value Method

3.3. 部分値による秘匿化方式

The Redaction by Partial Value Method is when a redacted field is not removed but its value has a portion of the data removed, such as for the "label" or "fn" jCard properties. The partial values are referenced in the "redacted" member in place of the property name in an array, such as referencing the "fn" jCard property value at position 3 instead of referencing the "fn" jCard property name at position 0. The Redaction by Partial Value Method SHOULD be used only when redacting JSON response fields that use a formatted value, where a portion of the value is removed.

部分値による秘匿化方式（Redaction by Partial Value Method）は、秘匿化されたフィールドを削除せずに、その値からデータの一部を削除するものです。たとえば、「label」や「fn」のjCardプロパティーに対して使用します。部分的な値は、「redacted」メンバーにおいて、配列内のプロパティー名の代わりに参照されます。たとえば、位置0にある「fn」jCardプロパティー名を参照する代わりに、位置3にある「fn」jCardプロパティーの値を参照します。部分値による秘匿化方式は、書式化された値を使用するJSONレスポンスフィールドの値の一部を削除して秘匿化する場合にのみ使用すべきです（SHOULD）。

[RFC7095]のSection 3.3.1.3にある「label」jCardプロパティーから「123 Maple Ave\nSuite 901\n」を秘匿化する例：

3.4. Redaction by Replacement Value Method

3.4. 置換値による秘匿化方式

The Redaction by Replacement Value Method is when a redacted field is not removed but its value is replaced with a different value, such as protecting the "email" jCard property value with an anonymized email "text" value or the use of an alternative "uri" value to a web form. Replacing a property value is a form of redaction, since it protects the true property value for privacy reasons.

置換値による秘匿化方式（Redaction by Replacement Value Method）は、秘匿化されたフィールドを削除せずに、その値を別の値に置き換えるものです。たとえば、「email」jCardプロパティーの値を匿名化されたメールアドレスの「text」値で保護したり、Webフォームへの代替の「uri」値を使用したりします。プロパティーの値を置き換えることは、プライバシー上の理由から本当のプロパティーの値を保護するので、秘匿化の一形態です。

4. Redacted RDAP Response

4. 秘匿化されたRDAPレスポンス

4.1. RDAP Conformance

4.1. RDAPへの準拠

RDAP responses that contain values described in this document MUST indicate conformance with this specification by including an "rdapConformance" [RFC9083] value of "redacted". The "redacted" extension identifier is described in Section 6.1.

この文書で説明する値を含むRDAPレスポンスは、「redacted」という「rdapConformance」[RFC9083]の値を含めることにより、この仕様への準拠を示さなければなりません（MUST）。「redacted」拡張識別子についてはSection 6.1で説明します。

4.2. "redacted" Member

4.2. 「redacted」メンバー

The "redacted" member MUST be added to the RDAP response when there is one or more redacted fields. The "redacted" member is included as a member of the object instance in a lookup response, such as the object classes defined in [RFC9083], and as a member of the object instances in a search response.

1つ以上の秘匿化されたフィールドがある場合、「redacted」メンバーをRDAPレスポンスに追加しなければなりません（MUST）。「redacted」メンバーは、[RFC9083]で定義されているオブジェクトクラスなどのルックアップレスポンス内のオブジェクトインスタンスのメンバーとして、および検索レスポンス内のオブジェクトインスタンスのメンバーとして含まれます。

The server, including a redacted signal, provides an unauthorized client additional information related to the existence of data and MAY exclude the redacted members for RDAP fields that are considered a privacy issue in providing a data existence signal. The server MAY choose to publish a redaction policy describing how this extension is implemented for their constituency. The contents of such a policy are outside the scope of this specification.

サーバーは、秘匿化のシグナルを含めることで、権限のないクライアントにデータの存在に関する追加の情報を提供することになります。そのため、データの存在のシグナルを提供することがプライバシー上の問題とみなされるRDAPフィールドについては、redactedメンバーを除外してもよいです（MAY）。サーバーは、この拡張を自身の利用者層に対してどのように実装しているかを説明する秘匿化ポリシーを公開することを選択してもよいです（MAY）。そのようなポリシーの内容は、この仕様の範囲外です。

The "redacted" member contains an array of objects with the following child members:

「redacted」メンバーには、次の子メンバーを持つオブジェクトの配列が含まれます：

"name":
REQUIRED logical name for the redacted field. The logical name used for the redacted field is up to server policy. The logical name is defined using an object with a "type" field denoting a registered redacted name (see Section 6.2) or a "description" field denoting an unregistered redacted name. The registered redacted names and the chosen unregistered names can meet the needs of different RDAP services or industries.
"prePath":
OPTIONAL JSON path expression referencing a redacted JSON field in the pre-redacted response, using the expression language defined by the "pathLang" member. The "prePath" member MAY be set when the redacted field does not exist in the redacted response for the Section 3.1 and the Section 3.4. The "prePath" member MUST NOT be set when the "postPath" member is set.
"postPath":
OPTIONAL JSON path expression referencing a redacted JSON field in the redacted (post-redacted) response, using the expression language defined by the "pathLang" member. The "postPath" member MUST be set when the redacted field does exist in the redacted response for the Section 3.2, the Section 3.3, and the Section 3.4. The "postPath" member MUST NOT be set when the "prePath" member is set.
"replacementPath":
OPTIONAL JSON path expression of the replacement field of the redacted field with the Section 3.4, using the expression language defined by the "pathLang" member.
"pathLang":
OPTIONAL JSON path expression language used, with the default value of "jsonpath" for JSONPath [RFC9535]. Other JSON path expression languages registered with the "redacted expression language" Type in the "RDAP JSON Values" registry MAY be used based on server policy.
"method":

OPTIONAL redaction method used, with one of the following values:

  • "removal" indicating the Section 3.1,
  • "emptyValue" indicating the Section 3.2,
  • "partialValue" indicating the Section 3.3, or
  • "replacementValue" indicating the Section 3.4.

The default value is "removal" when not provided.

"reason":
OPTIONAL human-readable reason(s) for the redacted field in the language defined by the "lang" [RFC9083] member. The default language is "en" if the "lang" [RFC9083] member is not specified. The reason is defined using an object with an OPTIONAL "type" field denoting a registered redacted reason (see Section 6.2) and an OPTIONAL "description" field denoting an unregistered redacted reason. The "description" field MUST NOT be a client processing dependency.
"name":
秘匿化されたフィールドの論理名です。これは要求されています（REQUIRED）。秘匿化されたフィールドに使用する論理名は、サーバーポリシーに委ねられます。論理名は、登録済みの秘匿化名を示す「type」フィールド（Section 6.2を参照）または未登録の秘匿化名を示す「description」フィールドを持つオブジェクトを使用して定義されます。登録済みの秘匿化名と選択された未登録の名前によって、さまざまなRDAPサービスや業界のニーズを満たすことができます。
"prePath":
「pathLang」メンバーで定義された式言語を使用して、秘匿化前のレスポンス内の秘匿化されたJSONフィールドを参照するJSONパス式です。これは選択できます（OPTIONAL）。Section 3.1およびSection 3.4において、秘匿化されたフィールドが秘匿化後のレスポンスに存在しない場合、「prePath」メンバーを設定してもよいです（MAY）。「postPath」メンバーが設定されている場合、「prePath」メンバーを設定してはなりません（MUST NOT）。
"postPath":
「pathLang」メンバーで定義された式言語を使用して、秘匿化された（秘匿化後の）レスポンス内の秘匿化されたJSONフィールドを参照するJSONパス式です。これは選択できます（OPTIONAL）。Section 3.2、Section 3.3、およびSection 3.4において、秘匿化されたフィールドが秘匿化後のレスポンスに存在する場合、「postPath」メンバーを設定しなければなりません（MUST）。「prePath」メンバーが設定されている場合、「postPath」メンバーを設定してはなりません（MUST NOT）。
"replacementPath":
「pathLang」メンバーで定義された式言語を使用した、Section 3.4における秘匿化されたフィールドの置換フィールドのJSONパス式です。これは選択できます（OPTIONAL）。
"pathLang":
使用するJSONパス式言語です。これは選択できます（OPTIONAL）。デフォルト値はJSONPath [RFC9535]を表す「jsonpath」です。「RDAP JSON Values」レジストリーに「redacted expression language」タイプで登録された他のJSONパス式言語を、サーバーポリシーに基づいて使用してもよいです（MAY）。
"method":

使用された秘匿化の方式です。これは選択できます（OPTIONAL）。値は次のいずれかです：

  • Section 3.1を示す「removal」
  • Section 3.2を示す「emptyValue」
  • Section 3.3を示す「partialValue」、または
  • Section 3.4を示す「replacementValue」

指定されていない場合のデフォルト値は「removal」です。

"reason":
「lang」[RFC9083]メンバーで定義された言語による、フィールドが秘匿化された人間が読める形式の理由です。これは選択できます（OPTIONAL）。「lang」[RFC9083]メンバーが指定されていない場合、デフォルトの言語は「en」です。理由は、登録済みの秘匿化理由を示す「type」フィールド（Section 6.2を参照）と、未登録の秘匿化理由を示す「description」フィールドを持つオブジェクトを使用して定義されます。「type」フィールドは選択できます（OPTIONAL）。「description」フィールドも選択できます（OPTIONAL）。「description」フィールドは、クライアントの処理が依存するものであってはなりません（MUST NOT）。

5. JSONPath Considerations

5. JSONPathに関する考慮事項

[RFC9535] is the default JSON path expression language. This section includes JSONPath considerations for clients and servers.

[RFC9535]は、デフォルトのJSONパス式言語です。このセクションでは、クライアントとサーバーにおけるJSONPathに関する考慮事項について説明します。

5.1. JSONPath Client Considerations

5.1. JSONPathのクライアントに関する考慮事項

This section covers considerations for clients that receive responses from servers using JSONPath [RFC9535] to identify redacted RDAP fields with the "prePath", "postPath", or "replacementPath" member of redacted objects in the "redacted" member. The list of JSONPath client considerations include:

このセクションでは、「redacted」メンバー内のredactedオブジェクトの「prePath」、「postPath」、または「replacementPath」メンバーで秘匿化されたRDAPフィールドを識別するためにJSONPath [RFC9535]を使用するサーバーから、レスポンスを受信するクライアントに関する考慮事項について説明します。JSONPathのクライアントに関する考慮事項には、次のものがあります：

  1. When the server is using the Section 3.1 or the Section 3.4 with an alternative field value, the JSONPath expression of the "prePath" member will not resolve successfully with the redacted response. The client can key off the "name" member for display logic related to the redaction.
  1. サーバーがSection 3.1、または代替のフィールド値を用いたSection 3.4を使用している場合、「prePath」メンバーのJSONPath式は、秘匿化されたレスポンスに対しては正しく解決されません。クライアントは、秘匿化に関連する表示ロジックのために「name」メンバーを手がかりにできます。

5.2. JSONPath Server Considerations

5.2. JSONPathのサーバーに関する考慮事項

This section covers considerations for servers using JSONPath [RFC9535] to identify redacted RDAP fields with the "prePath", "postPath", or "replacementPath" member of redacted objects in the "redacted" member. The list of JSONPath considerations include:

このセクションでは、「redacted」メンバー内のredactedオブジェクトの「prePath」、「postPath」、または「replacementPath」メンバーで秘匿化されたRDAPフィールドを識別するためにJSONPath [RFC9535]を使用するサーバーに関する考慮事項について説明します。JSONPathに関する考慮事項には、次のものがあります：

  1. Use absolute paths with the '$' JSONPath element. An example is "$.handle" for the "Registry Domain ID" in a lookup response or "$.domainSearchResults[0].handle" in a search response.
  2. Validate a JSONPath expression with the non-redacted RDAP response when using the "prePath" member, where evaluating the expression results in returning the redacted field.
  3. Reference the removed object field when redacting an entire object by the Section 3.1, where all of the object's child fields are explicitly removed. An example is "$.entities[?(@.roles[0]=='administrative')]" for the entire "Administrative Contact".
  4. Use multiple bases for the redaction of certain content. For example, if server policy is such that all administrative-role entities are redacted and all technical-role entities are redacted, then an entity having both the administrative role and the technical role could be redacted for two different reasons. In this situation, a server is required to include at least one "redacted" entry, but it should consider including a separate "redacted" entry for each applicable basis for redaction to clearly document the server policies that are relevant to redaction in each instance.
  5. Reference the removed field when using the Section 3.1. An example is "$.handle" for the "Registry Domain ID".
  6. Reference index 0 of the jCard property array, which is the jCard "name" property, with a filter expression containing the name of the field when redacting a jCard field using the Section 3.1. An example is "$.entities[?(@.roles[0]=='registrant')].vcardArray[1][?(@[0]=='email')]" for the "Registrant Email".
  7. Reference the jCard field value or values redacted by array index 3 and greater when redacting a jCard field using the Section 3.2. The jCard property array index 3 and greater contain the property values, where the property values set with an empty value are referenced directly in place of the jCard property name. Servers can then systematically redact the jCard field value or values based on the JSONPath expressions, and clients will directly know which jCard property values have been redacted. An example is "$.entities[?(@.roles[0]=='registrant')].vcardArray[1][?(@[0]=='fn')][3]" for the "Registrant Name" or "$.entities[?(@.roles[0]=='registrant')].vcardArray[1][?(@[0]=='adr')][3][5]" for the "Registrant Postal Code".
  8. RDAP extensions should define any special JSONPath considerations required to identify redacted RDAP fields if these considerations are insufficient.
  1. 「$」JSONPath要素を使用した絶対パスを使用します。たとえば、ルックアップレスポンスにおける「Registry Domain ID」には「$.handle」、検索レスポンスでは「$.domainSearchResults[0].handle」を使用します。
  2. 「prePath」メンバーを使用する場合は、秘匿化されていないRDAPレスポンスに対してJSONPath式を検証します。式を評価すると、秘匿化されたフィールドが返されるはずです。
  3. Section 3.1によってオブジェクト全体を秘匿化する場合は、削除されたオブジェクトフィールドを参照します。この場合、オブジェクトのすべての子フィールドが明示的に削除されます。たとえば、「Administrative Contact」全体には「$.entities[?(@.roles[0]=='administrative')]」を使用します。
  4. 特定のコンテンツの秘匿化に対して複数の根拠を使用します。たとえば、サーバーポリシーにより、管理ロールのエンティティーがすべて秘匿化され、技術ロールのエンティティーもすべて秘匿化される場合、管理ロールと技術ロールの両方を持つエンティティーは、2つの異なる理由で秘匿化される可能性があります。このような状況では、サーバーは少なくとも1つの「redacted」エントリーを含める必要がありますが、それぞれの場合における秘匿化に関連するサーバーポリシーを明確に文書化するために、適用される秘匿化の根拠ごとに別々の「redacted」エントリーを含めることを検討すべきです。
  5. Section 3.1を使用する場合は、削除されたフィールドを参照します。たとえば、「Registry Domain ID」には「$.handle」を使用します。
  6. Section 3.1を使用してjCardフィールドを秘匿化する場合は、フィールドの名前を含むフィルター式を用いて、jCardの「name」プロパティーであるjCardプロパティー配列のインデックス0を参照します。たとえば、「Registrant Email」には「$.entities[?(@.roles[0]=='registrant')].vcardArray[1][?(@[0]=='email')]」を使用します。
  7. Section 3.2を使用してjCardフィールドを秘匿化する場合は、配列インデックス3以上によって秘匿化されたjCardフィールドの値を参照します。jCardプロパティー配列のインデックス3以上にはプロパティーの値が含まれており、空の値が設定されたプロパティーの値は、jCardプロパティー名の代わりに直接参照されます。これにより、サーバーはJSONPath式に基づいてjCardフィールドの値を体系的に秘匿化でき、クライアントはどのjCardプロパティーの値が秘匿化されたのかを直接知ることができます。たとえば、「Registrant Name」には「$.entities[?(@.roles[0]=='registrant')].vcardArray[1][?(@[0]=='fn')][3]」、「Registrant Postal Code」には「$.entities[?(@.roles[0]=='registrant')].vcardArray[1][?(@[0]=='adr')][3][5]」を使用します。
  8. これらの考慮事項では不十分な場合、RDAP拡張は、秘匿化されたRDAPフィールドを識別するために必要な特別なJSONPathの考慮事項を定義すべきです。
