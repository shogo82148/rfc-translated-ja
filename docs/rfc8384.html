Transparent Interconnection of Lots of Links (TRILL) Smart Endnodes

RFC 8384

Transparent Interconnection of Lots of Links（TRILL）スマートエンドノード

Abstract

概要

This document addresses the problem of the size and freshness of the endnode learning table in edge Routing Bridges (RBridges), by allowing endnodes to volunteer for endnode learning and encapsulation/decapsulation. Such an endnode is known as a "Smart Endnode". Only the attached edge RBridge can distinguish a "Smart Endnode" from a "normal endnode". The Smart Endnode uses the nickname of the attached edge RBridge, so this solution does not consume extra nicknames. The solution also enables endnodes that are Fine-Grained Label (FGL) aware.

この文書は、エンドノードが自らエンドノード学習とカプセル化／カプセル化解除を引き受けられるようにすることで、エッジルーティングブリッジ（Routing Bridge: RBridge）におけるエンドノード学習テーブルのサイズと鮮度の問題に対処します。このようなエンドノードを「スマートエンドノード（Smart Endnode）」と呼びます。「スマートエンドノード」と「通常のエンドノード」を区別できるのは、接続先のエッジRBridgeだけです。スマートエンドノードは接続先のエッジRBridgeのニックネームを使用するので、この解決策は追加のニックネームを消費しません。この解決策は、細粒度ラベル（Fine-Grained Label: FGL）を認識するエンドノードも可能にします。

1. Introduction

1. はじめに

The IETF TRILL (Transparent Interconnection of Lots of Links) protocol [RFC6325] [RFC7780] provides optimal pair-wise data frame forwarding without configuration, safe forwarding even during periods of temporary loops, and support for multipathing of both unicast and multicast traffic. TRILL accomplishes this by using IS-IS [IS-IS] [RFC7176] link state routing and encapsulating traffic using a header that includes a hop count. Devices that implement TRILL are called "RBridges" (Routing Bridges) or "TRILL Switches".

IETFのTRILL（Transparent Interconnection of Lots of Links）プロトコル[RFC6325] [RFC7780]は、設定なしでの最適なペアワイズのデータフレーム転送、一時的なループが発生している期間中でも安全な転送、ユニキャストとマルチキャストの両方のトラフィックのマルチパス化のサポートを提供します。TRILLは、IS-IS [IS-IS] [RFC7176]のリンクステートルーティングを使用し、ホップカウントを含むヘッダーを使用してトラフィックをカプセル化することで、これを実現します。TRILLを実装するデバイスは「RBridge」（ルーティングブリッジ（Routing Bridge））または「TRILLスイッチ（TRILL Switch）」と呼ばれます。

An RBridge that attaches to endnodes is called an "edge RBridge" or "edge TRILL Switch", whereas one that exclusively forwards encapsulated frames is known as a "transit RBridge" or "transit TRILL Switch". An edge RBridge traditionally is the one that encapsulates a native Ethernet frame with a TRILL header or that receives a TRILL-encapsulated packet and decapsulates the TRILL header. To encapsulate efficiently, the edge RBridge must keep an "endnode table" consisting of (Media Access Control (MAC), Data Label, TRILL egress switch nickname) sets, for those remote MAC addresses in Data Labels currently communicating with endnodes to which the edge RBridge is attached.

エンドノードに接続するRBridgeは「エッジRBridge（edge RBridge）」または「エッジTRILLスイッチ（edge TRILL Switch）」と呼ばれ、カプセル化されたフレームの転送だけを行うRBridgeは「トランジットRBridge（transit RBridge）」または「トランジットTRILLスイッチ（transit TRILL Switch）」と呼ばれます。従来、エッジRBridgeは、ネイティブのイーサネットフレームをTRILLヘッダーでカプセル化するRBridge、またはTRILLカプセル化されたパケットを受信してTRILLヘッダーのカプセル化を解除するRBridgeです。効率的にカプセル化するために、エッジRBridgeは、自身が接続しているエンドノードと現在通信している、データラベル内のリモートMACアドレスについて、（メディアアクセス制御（Media Access Control: MAC）、データラベル、TRILL出口スイッチのニックネーム）の組からなる「エンドノードテーブル」を保持しなければなりません。

These table entries might be configured, received from End Station Address Distribution Information (ESADI) [RFC7357], looked up in a directory [RFC7067], or learned from decapsulating received traffic. If the edge RBridge has attached endnodes communicating with many remote endnodes, this table could become very large. Also, if a MAC address / Data Label pair in the table have moved to a different remote TRILL switch, it might be difficult for the edge RBridge to notice this quickly; and because the edge RBridge is encapsulating to the incorrect egress RBridge, the traffic will get lost.

これらのテーブルエントリーは、設定されたり、エンドステーションアドレス配布情報（End Station Address Distribution Information: ESADI）[RFC7357]から受信されたり、ディレクトリー[RFC7067]で検索されたり、受信したトラフィックのカプセル化解除から学習されたりします。エッジRBridgeに接続しているエンドノードが多数のリモートエンドノードと通信している場合、このテーブルは非常に大きくなる可能性があります。また、テーブル内のMACアドレスとデータラベルのペアが別のリモートTRILLスイッチに移動した場合、エッジRBridgeがそれにすばやく気づくのは難しいかもしれません。そして、エッジRBridgeは誤った出口RBridgeに向けてカプセル化しているため、トラフィックは失われます。

3. Solution Overview

3. 解決策の概要

The Smart Endnode solution defined in this document addresses the problem of the size and freshness of the endnode learning table in edge RBridges. An endnode E, attached to an edge RBridge R, tells R that E would like to be a "Smart Endnode", which means that E will encapsulate and decapsulate the TRILL frame, using R's nickname. Because E uses R's nickname, this solution does not consume extra nicknames.

この文書で定義するスマートエンドノードの解決策は、エッジRBridgeにおけるエンドノード学習テーブルのサイズと鮮度の問題に対処します。エッジRBridge Rに接続しているエンドノードEは、Eが「スマートエンドノード」になりたいことをRに伝えます。これは、EがRのニックネームを使用してTRILLフレームのカプセル化とカプセル化解除を行うことを意味します。EはRのニックネームを使用するので、この解決策は追加のニックネームを消費しません。

Take Figure 1 as the example Smart Endnode scenario: RB1, RB2, and RB3 are the RBridges in the TRILL domain and SE1 and SE2 are the Smart Endnodes that can encapsulate and decapsulate the TRILL packets. RB1 is the edge RB to which SE1 and SE2 have attached. RB1 assigns one of its nicknames to be used by SE1 and SE2.

スマートエンドノードのシナリオの例として、図1を取り上げます。RB1、RB2、RB3はTRILLドメイン内のRBridgeであり、SE1とSE2はTRILLパケットのカプセル化とカプセル化解除ができるスマートエンドノードです。RB1は、SE1とSE2が接続しているエッジRBです。RB1は、自身のニックネームの1つをSE1とSE2が使用するように割り当てます。

Each Smart Endnode, SE1 and SE2, uses RB1's nickname when encapsulating and maintains an endnode table of (MAC, Data Label, TRILL egress switch nickname) for remote endnodes that it (SE1 or SE2) is corresponding with. RB1 does not decapsulate packets destined for SE1 or SE2 and does not learn (MAC, Data Label, TRILL egress switch nickname) for endnodes corresponding with SE1 or SE2, but RB1 does decapsulate and does learn (MAC, Data Label, TRILL egress switch nickname) for any endnodes attached to RB1 that have not declared themselves to be Smart Endnodes.

各スマートエンドノードSE1とSE2は、カプセル化するときにRB1のニックネームを使用し、自身（SE1またはSE2）が通信しているリモートエンドノードについて（MAC、データラベル、TRILL出口スイッチのニックネーム）のエンドノードテーブルを維持します。RB1は、SE1またはSE2宛てのパケットのカプセル化を解除せず、SE1またはSE2と通信しているエンドノードについて（MAC、データラベル、TRILL出口スイッチのニックネーム）を学習しません。しかし、RB1に接続しているエンドノードのうち、自身をスマートエンドノードであると宣言していないものについては、RB1はカプセル化解除と（MAC、データラベル、TRILL出口スイッチのニックネーム）の学習を行います。

Just as an RBridge learns and times out (MAC, Data Label, TRILL egress switch nickname), Smart Endnodes SE1 and SE2 also learn and time out endnode entries. However, SE1 and SE2 might also determine, through ICMP messages or other techniques that an endnode entry is not successfully reaching the destination endnode, and it can be deleted, even if the entry has not timed out.

RBridgeが（MAC、データラベル、TRILL出口スイッチのニックネーム）を学習してタイムアウトさせるのと同じように、スマートエンドノードSE1とSE2もエンドノードエントリーを学習してタイムアウトさせます。ただし、SE1とSE2は、ICMPメッセージやその他の手法によって、あるエンドノードエントリーでは宛先エンドノードに正常に到達できていないと判断することもあり、その場合はエントリーがタイムアウトしていなくても削除できます。

If SE1 wishes to correspond with destination MAC D, and no endnode entry exists, SE1 will encapsulate the packet as an unknown destination, or consult a directory [RFC7067] (just as an RBridge would do if there was no endnode entry).

SE1が宛先MAC Dと通信したいときに、エンドノードエントリーが存在しない場合、SE1はパケットを未知の宛先としてカプセル化するか、ディレクトリー[RFC7067]に問い合わせます（エンドノードエントリーがない場合にRBridgeが行うのと同じです）。

The mechanism in this document is that the Smart Endnode SE1 issues a Smart-Hello, indicating SE1's desire to act as a Smart Endnode, together with the set of MAC addresses and Data Labels that SE1 owns. The Smart-Hello is used to announce the Smart Endnode capability and parameters (such as MAC address, Data Label, etc.). The Smart-Hello is a type of TRILL ES-IS PDU, which is specified in Section 5 of [RFC8171]. The detailed content for a Smart Endnode's Smart-Hello is defined in Section 4.

この文書のメカニズムでは、スマートエンドノードSE1が、SE1が所有するMACアドレスとデータラベルの集合とともに、SE1がスマートエンドノードとして動作したいことを示すSmart-Helloを発行します。Smart-Helloは、スマートエンドノードの能力とパラメーター（MACアドレス、データラベルなど）を通知するために使用されます。Smart-Helloは、[RFC8171]のセクション5で規定されているTRILL ES-IS PDUの一種です。スマートエンドノードのSmart-Helloの詳細な内容はセクション4で定義します。

If RB1 supports having a Smart Endnode neighbor, it also sends Smart-Hellos. The Smart Endnode learns from RB1's Smart-Hellos what RB1's nickname is and which trees RB1 can use when RB1 ingresses multi-destination frames. Although Smart Endnode SE1 transmits Smart-Hellos, it does not transmit or receive Link State PDUs (LSPs) or Extended Level 1 Flooding Scope (E-L1FS) FS LSPs [RFC7780].

RB1は、スマートエンドノードの近隣を持つことをサポートする場合、自身もSmart-Helloを送信します。スマートエンドノードは、RB1のSmart-Helloから、RB1のニックネームが何であるか、およびRB1がマルチデスティネーションフレームの入口となるときにどのツリーを使用できるかを学習します。スマートエンドノードSE1はSmart-Helloを送信しますが、リンクステートPDU（LSP）や拡張レベル1フラッディングスコープ（Extended Level 1 Flooding Scope: E-L1FS）のFS LSP [RFC7780]の送受信は行いません。

Since a Smart Endnode can encapsulate TRILL Data packets, it can cause the Inner.Label to be a Fine-Grained Label [RFC7172]; thus, this method supports FGL-aware endnodes. When and how a Smart Endnode decides to use the FGL instead of VLANs to encapsulate the TRILL Data packet is out of scope in this document.

スマートエンドノードはTRILLデータパケットをカプセル化できるので、Inner.Labelを細粒度ラベル[RFC7172]にできます。したがって、この方法はFGLを認識するエンドノードをサポートします。スマートエンドノードが、TRILLデータパケットをカプセル化するためにVLANではなくFGLを使用することを、いつどのように決定するかは、この文書の範囲外です。

4. Smart-Hello Mechanism between Smart Endnode and RBridge

4. スマートエンドノードとRBridgeの間のSmart-Helloメカニズム

The subsections below describe Smart-Hello messages.

以下のサブセクションでは、Smart-Helloメッセージについて説明します。

4.1. Smart-Hello Encapsulation

4.1. Smart-Helloのカプセル化

Although a Smart Endnode is not an RBridge, does not send LSPs or maintain a copy of the link state database, and does not perform routing calculations, it is required to have a "Hello" mechanism (1) to announce to edge RBridges that it is a Smart Endnode and (2) to tell them what MAC addresses it is handling in what Data Labels. Similarly, an edge RBridge that supports Smart Endnodes needs a message (1) to announce that support, (2) to inform Smart Endnodes what nickname to use for ingress and what nickname(s) can be used as egress nickname in a multi-destination TRILL Data packet, and (3) the list of Smart Endnodes it knows about on that link.

スマートエンドノードはRBridgeではなく、LSPの送信やリンクステートデータベースのコピーの維持を行わず、ルーティング計算も行いませんが、（1）自身がスマートエンドノードであることをエッジRBridgeに通知し、（2）どのデータラベルでどのMACアドレスを扱っているかをエッジRBridgeに伝えるための「Hello」メカニズムを持つ必要があります。同様に、スマートエンドノードをサポートするエッジRBridgeには、（1）そのサポートを通知し、（2）入口にどのニックネームを使用し、マルチデスティネーションのTRILLデータパケットでどのニックネームを出口ニックネームとして使用できるかをスマートエンドノードに知らせ、（3）そのリンク上で自身が把握しているスマートエンドノードの一覧を伝えるためのメッセージが必要です。

The messages sent by Smart Endnodes and by edge RBridges that support Smart Endnodes are called "Smart-Hellos". The Smart-Hello is a type of TRILL ES-IS PDU, which is specified in [RFC8171].

スマートエンドノード、およびスマートエンドノードをサポートするエッジRBridgeが送信するメッセージを「Smart-Hello」と呼びます。Smart-Helloは、[RFC8171]で規定されているTRILL ES-IS PDUの一種です。

The Smart-Hello Payload, both for Smart-Hellos sent by Smart Endnodes and for Smart-Hellos sent by edge RBridges, consists of TRILL IS-IS TLVs as described in the following two subsections. The non-extended format is used so TLVs, sub-TLVs, and APPsub-TLVs have an 8-bit size and type field. Both types of Smart-Hellos MUST include a Smart-Parameters APPsub-TLV as follows inside a TRILL GENINFO TLV:

Smart-Helloのペイロードは、スマートエンドノードが送信するSmart-HelloでもエッジRBridgeが送信するSmart-Helloでも、続く2つのサブセクションで説明するTRILL IS-IS TLVで構成されます。非拡張フォーマットが使用されるので、TLV、サブTLV、APPsub-TLVのサイズフィールドとタイプフィールドは8ビットです。どちらの種類のSmart-Helloも、次のようなSmart-Parameters APPsub-TLVをTRILL GENINFO TLVの中に含めなければなりません（MUST）。

  • Type: APPsub-TLV type Smart-Parameters, value is 22.
  • Length: 4.
  • Holding Time: A time in seconds as an unsigned integer. It has the same meaning as the Holding Time field in IS-IS Hellos [IS-IS]. A Smart Endnode and an edge RBridge supporting Smart Endnodes MUST send a Smart-Hello at least three times during their Holding Time. If no Smart-Hellos are received from a Smart Endnode or edge RBridge within the most recent Holding Time it sent, it is assumed that it is no longer available.
  • Flags: At this time, all of the Flags are reserved and MUST be sent as zero and ignored on receipt.
  • If more than one Smart-Parameters APPsub-TLV appears in a Smart-Hello, the first one is used and any following ones are ignored. If no Smart-Parameters APPsub-TLVs appear in a Smart-Hello, that Smart-Hello is ignored.
  • Type: APPsub-TLVタイプSmart-Parameters。値は22です。
  • Length: 4。
  • Holding Time: 秒単位の時間を表す符号なし整数。IS-IS Hello [IS-IS]のHolding Timeフィールドと同じ意味を持ちます。スマートエンドノード、およびスマートエンドノードをサポートするエッジRBridgeは、自身のHolding Timeの間に少なくとも3回Smart-Helloを送信しなければなりません（MUST）。スマートエンドノードまたはエッジRBridgeが最後に送信したHolding Time以内に、そこからSmart-Helloを受信しなかった場合、それはもう利用できないとみなされます。
  • Flags: 現時点では、すべてのフラグは予約済みであり、送信時には0に設定し、受信時には無視しなければなりません（MUST）。
  • Smart-Helloに複数のSmart-Parameters APPsub-TLVが含まれている場合、最初のものが使用され、それ以降のものは無視されます。Smart-HelloにSmart-Parameters APPsub-TLVが含まれていない場合、そのSmart-Helloは無視されます。

4.2. Edge RBridge's Smart-Hello

4.2. エッジRBridgeのSmart-Hello

The edge RBridge's Smart-Hello contains the following information in addition to the Smart-Parameters APPsub-TLV:

エッジRBridgeのSmart-Helloには、Smart-Parameters APPsub-TLVに加えて次の情報が含まれます。

  • RBridge's nickname. The nickname sub-TLV, specified in Section 2.3.2 in [RFC7176], is reused here carried inside a TLV 242 (IS-IS router capability) in a Smart-Hello frame. If more than one nickname appears in the Smart-Hello, the first one is used and the following ones are ignored.
  • Trees that RB1 can use when ingressing multi-destination frames. The Tree Identifiers sub-TLV, specified in Section 2.3.4 in [RFC7176], is reused here.
  • Smart Endnode neighbor list. The TRILL Neighbor TLV, specified in section 2.5 in [RFC7176], is reused for this purpose.
  • An Authentication TLV MAY also be included.
  • RBridgeのニックネーム。[RFC7176]のセクション2.3.2で規定されているニックネームサブTLVを、ここで再利用し、Smart-HelloフレームのTLV 242（IS-IS router capability）の中に入れて運びます。Smart-Helloに複数のニックネームが含まれている場合、最初のものが使用され、それ以降のものは無視されます。
  • RB1がマルチデスティネーションフレームの入口となるときに使用できるツリー。[RFC7176]のセクション2.3.4で規定されているTree IdentifiersサブTLVを、ここで再利用します。
  • スマートエンドノードの近隣の一覧。この目的のために、[RFC7176]のセクション2.5で規定されているTRILL Neighbor TLVを再利用します。
  • Authentication TLVを含めてもよいです（MAY）。

4.3. Smart Endnode's Smart-Hello

4.3. スマートエンドノードのSmart-Hello

A new APPsub-TLV (Smart-MAC TLV) for use by Smart Endnodes is as defined below. In addition, there will be a Smart-Parameters APPsub-TLV and there MAY be an Authentication TLV in a Smart Endnode Smart-Hello.

スマートエンドノードが使用する新しいAPPsub-TLV（Smart-MAC TLV）を以下で定義します。さらに、スマートエンドノードのSmart-Helloには、Smart-Parameters APPsub-TLVが含まれ、Authentication TLVが含まれる場合があります（MAY）。

If there are several VLANs/FGL Data Labels for that Smart Endnode, the Smart-MAC APPsub-TLV is included several times in the Smart Endnode's Smart-Hello. This APPsub-TLV appears inside a TRILL GENINFO TLV.

そのスマートエンドノードに複数のVLAN／FGLデータラベルがある場合、Smart-MAC APPsub-TLVはスマートエンドノードのSmart-Helloに複数回含まれます。このAPPsub-TLVは、TRILL GENINFO TLVの中に現れます。

  • Type: TRILL APPsub-TLV Type Smart-MAC, value is 23.
  • Length: Total number of bytes contained in the value field of the TLV, that is, the sum of the length of the F/M/RSV/FGL Data Label fields and six times the number of MAC addresses present. So, if there are n MAC addresses, this is 4+6*n.
  • F: 1 bit. If it is set to 1, it indicates that the endnode supports FGL Data Labels [RFC7172], and that this Smart-MAC APPsub-TLV has an FGL in the following VLAN/FGL field. Otherwise, the VLAN/FGL Data Label field is a VLAN ID. (See below for the format of the VLAN/FGL Data Label field).
  • M: 1 bit. If it is set to 1, it indicates multihoming (see Section 6). If it is set to 0, it indicates that the Smart Endnodes are not using multihoming.
  • RSV: 6 bits; reserved for the future use.
  • VLAN/FGL Data Label: 24 bits. If F is 1, this field is a 24-bit FGL Data Label for all subsequent MAC addresses in this APPsub-TLV. Otherwise, if F is 0, the lower 12 bits are the VLAN of all subsequent MAC addresses in this APPsub-TLV, and the upper 12 bits are not used (sent as zero and ignored on receipt). If there is no VLAN/FGL Data Label specified, the VLAN/FGL Data Label is zero.
  • MAC(i): This is a 48-bit MAC address reachable in the Data Label sent by the Smart Endnode that is announcing this APPsub-TLV.
  • Type: TRILL APPsub-TLVタイプSmart-MAC。値は23です。
  • Length: TLVの値フィールドに含まれる合計バイト数。つまり、F／M／RSV／FGL Data Labelフィールドの長さと、含まれるMACアドレスの数の6倍の和です。したがって、MACアドレスがn個ある場合、これは4+6*nになります。
  • F: 1ビット。1に設定されている場合、エンドノードがFGLデータラベル[RFC7172]をサポートしており、このSmart-MAC APPsub-TLVが後続のVLAN/FGLフィールドにFGLを持つことを示します。そうでない場合、VLAN/FGL Data LabelフィールドはVLAN IDです。（VLAN/FGL Data Labelフィールドのフォーマットについては後述します。）
  • M: 1ビット。1に設定されている場合、マルチホーミングを示します（セクション6を参照）。0に設定されている場合、スマートエンドノードがマルチホーミングを使用していないことを示します。
  • RSV: 6ビット。将来の使用のために予約されています。
  • VLAN/FGL Data Label: 24ビット。Fが1の場合、このフィールドは、このAPPsub-TLV内の後続のすべてのMACアドレスに対する24ビットのFGLデータラベルです。そうではなくFが0の場合、下位12ビットはこのAPPsub-TLV内の後続のすべてのMACアドレスのVLANであり、上位12ビットは使用されません（送信時には0にし、受信時には無視します）。VLAN/FGLデータラベルが指定されていない場合、VLAN/FGL Data Labelは0です。
  • MAC(i): このAPPsub-TLVを通知しているスマートエンドノードが送信するデータラベルにおいて到達可能な48ビットのMACアドレスです。

5. Processing Data Packets

5. データパケットの処理

The subsections below specify the processing of Smart Endnode data packets. All TRILL Data packets sent to or from Smart Endnodes are sent in the Designated VLAN [RFC6325] of the local link but do not necessarily have to be VLAN tagged.

以下のサブセクションでは、スマートエンドノードのデータパケットの処理を規定します。スマートエンドノードとの間で送受信されるすべてのTRILLデータパケットは、ローカルリンクの指定VLAN（Designated VLAN）[RFC6325]で送信されますが、必ずしもVLANタグ付きである必要はありません。

5.1. Data-Packet Processing for Smart Endnodes

5.1. スマートエンドノードにおけるデータパケット処理

A Smart Endnode does not issue or receive LSPs or E-L1FS FS LSPs or calculate topology. It does the following:

スマートエンドノードは、LSPやE-L1FSのFS LSPの発行や受信、トポロジーの計算を行いません。スマートエンドノードは次のことを行います。

  • A Smart Endnode maintains an endnode table of (the MAC address of remote endnode, Data Label, the nickname of the edge RBridge's attached) entries of end nodes with which the Smart Endnode is communicating. Entries in this table are populated the same way that an edge RBridge populates the entries in its table:

    • learning from (source MAC address ingress nickname) on packets it decapsulates.
    • by querying a directory [RFC7067].
    • by having some entries configured.
  • When Smart Endnode SE1 wishes to send unicast frame to remote node D, if the (MAC address of remote endnode D, Data Label, nickname) entry is in SE1's endnode table, SE1 encapsulates the ingress nickname as the nickname of the RBridge (RB1), egress nickname as indicated in D's table entry. If D is unknown, SE1 either queries a directory or encapsulates the packet as a multi-destination frame, using one of the trees that RB1 has specified in RB1's Smart-Hello. The mechanism for querying a directory is given in [RFC8171].
  • When SE1 wishes to send a Broadcast, Unknown Unicast, and Multicast (BUM) packet to the TRILL campus, SE1 encapsulates the packet using one of the trees that RB1 has specified.

  • スマートエンドノードは、自身が通信しているエンドノードについて、（リモートエンドノードのMACアドレス、データラベル、接続先エッジRBridgeのニックネーム）のエントリーからなるエンドノードテーブルを維持します。このテーブルのエントリーは、エッジRBridgeが自身のテーブルのエントリーを設定するのと同じ方法で設定されます。

    • カプセル化を解除したパケットの（送信元MACアドレス、入口ニックネーム）から学習する。
    • ディレクトリー[RFC7067]に問い合わせる。
    • 一部のエントリーを設定しておく。
  • スマートエンドノードSE1がリモートノードDにユニキャストフレームを送信したい場合、（リモートエンドノードDのMACアドレス、データラベル、ニックネーム）のエントリーがSE1のエンドノードテーブルにあれば、SE1は、入口ニックネームをRBridge（RB1）のニックネームとし、出口ニックネームをDのテーブルエントリーに示されたものとしてカプセル化します。Dが未知の場合、SE1はディレクトリーに問い合わせるか、RB1がRB1のSmart-Helloで指定したツリーの1つを使用して、パケットをマルチデスティネーションフレームとしてカプセル化します。ディレクトリーに問い合わせるメカニズムは[RFC8171]に記載されています。
  • SE1がTRILLキャンパスにブロードキャスト、未知ユニキャスト、マルチキャスト（Broadcast, Unknown Unicast, and Multicast: BUM）のパケットを送信したい場合、SE1は、RB1が指定したツリーの1つを使用してパケットをカプセル化します。

If the Smart Endnode SE1 sends a multi-destination TRILL Data packet, the destination MAC of the outer Ethernet is the All-RBridges multicast address.

スマートエンドノードSE1がマルチデスティネーションのTRILLデータパケットを送信する場合、外側のイーサネットの宛先MACはAll-RBridgesマルチキャストアドレスです。

The Smart Endnode SE1 need not send Smart-Hellos as frequently as normal RBridges. These Smart-Hellos could be periodically unicast to the Appointed Forwarder RB1. In case RB1 crashes and restarts, or the DRB changes and SE1 receives the Smart-Hello without mentioning SE1, SE1 SHOULD send a Smart-Hello immediately. If RB1 is Appointed Forwarder for any of the VLANs that SE1 claims, RB1 MUST list SE1 in its Smart-Hellos as a Smart Endnode neighbor.

スマートエンドノードSE1は、通常のRBridgeほど頻繁にSmart-Helloを送信する必要はありません。これらのSmart-Helloは、指定フォワーダー（Appointed Forwarder）であるRB1に定期的にユニキャストで送信することもできます。RB1がクラッシュして再起動した場合や、DRBが変わり、SE1がSE1に言及していないSmart-Helloを受信した場合、SE1はただちにSmart-Helloを送信すべきです（SHOULD）。RB1がSE1の主張するいずれかのVLANの指定フォワーダーである場合、RB1は自身のSmart-HelloでSE1をスマートエンドノードの近隣として列挙しなければなりません（MUST）。

5.2. Data-Packet Processing for Edge RBridge

5.2. エッジRBridgeにおけるデータパケット処理

The attached edge RBridge processes and forwards TRILL Data packets based on the endnode property rather than for encapsulation and forwarding the native frames the same way as the traditional RBridges. There are several situations for the edge RBridges as follows:

接続先のエッジRBridgeは、従来のRBridgeと同じ方法でネイティブフレームをカプセル化して転送するのではなく、エンドノードの特性に基づいてTRILLデータパケットを処理し、転送します。エッジRBridgeには、次のようないくつかの状況があります。

  • If receiving an encapsulated unicast TRILL Data packet from a port with a Smart Endnode, with RB1's nickname as ingress, the edge RBridge RB1 forwards the frame to the specified egress nickname, as with any encapsulated frame. However, RB1 SHOULD filter the encapsulation frame based on the inner source MAC and Data Label as specified for the Smart Endnode. If the MAC (or Data Label) is not among the expected entries of the Smart Endnode, the frame would be dropped by the edge RBridge. If the edge RBridge does not perform this check, it makes it easier for a rogue end station to inject bogus TRILL Data packets into the TRILL campus.
  • If receiving a unicast TRILL Data packet with RB1's nickname as egress from the TRILL campus, and the destination MAC address in the enclosed packet is a MAC address that has been listed by a Smart Endnode, RB1 leaves the packet encapsulated to that Smart Endnode. The outer Ethernet destination MAC is the destination Smart Endnode's MAC address, the inner destination MAC address is either the Smart Endnode's MAC address or some other MAC address that the Smart Endnode advertised in its Smart Hello, and the outer Ethernet source MAC address is the RB1's port MAC address. The edge RBridge still decreases the Hop count value by 1, for there is one hop between the RB1 and Smart Endnode.
  • If receiving a multi-destination TRILL Data packet from a port with a Smart Endnode, RBridge RB1 forwards the TRILL encapsulation to the TRILL campus based on the distribution tree indicated by the egress nickname. If the egress nickname does not correspond to a distribution tree, the packet is discarded. If there are any normal endnodes (i.e., endnodes that are not Smart Endnodes) attached to the edge RBridge RB1, RB1 decapsulates the frame and sends the native frame to these ports possibly pruned based on multicast listeners, in addition to forwarding the multi-destination TRILL frame to the rest of the campus.
  • If RB1 receives a native multi-destination data frame, which is sent by an endnode that is not a Smart Endnode, from a port, including hybrid endnodes (Smart Endnodes and endnodes that are not Smart Endnodes), RB1 will encapsulate it as multi-destination TRILL Data packet, and send the encapsulated multi-destination TRILL Data packet out that same port to the Smart Endnodes attached to the port, and also send the encapsulated multi-destination TRILL Data packet to the TRILL campus through other ports.
  • If RB1 receives a multi-destination TRILL Data packet from a remote RBridge, and the exit port includes hybrid endnodes (Smart Endnodes and endnodes that are not Smart Endnodes), it sends two copies of multicast frames out the port, one as native and the other as a TRILL-encapsulated frame. When a Smart Endnode receives a multi-destination TRILL Data packet, it learns the remote (MAC address, Data Label, nickname) entry. A Smart Endnode ignores native data frames. A normal (non-Smart) endnode receives the native frame and learns the remote MAC address and ignores the TRILL Data packet. This transit solution may bring some complexity for the edge RBridge and waste network bandwidth resource, so avoiding the hybrid endnodes scenario by attaching the endnodes that are Smart and non-Smart to different ports is RECOMMENDED.
  • スマートエンドノードがあるポートから、RB1のニックネームを入口とする、カプセル化されたユニキャストのTRILLデータパケットを受信した場合、エッジRBridge RB1は、ほかのカプセル化されたフレームと同様に、指定された出口ニックネームに向けてそのフレームを転送します。ただし、RB1は、そのスマートエンドノードについて指定された内側の送信元MACとデータラベルに基づいて、カプセル化されたフレームをフィルタリングすべきです（SHOULD）。MAC（またはデータラベル）がそのスマートエンドノードの想定されるエントリーに含まれていない場合、そのフレームはエッジRBridgeによって破棄されます。エッジRBridgeがこのチェックを行わない場合、不正なエンドステーションが偽のTRILLデータパケットをTRILLキャンパスに注入しやすくなります。
  • TRILLキャンパスから、RB1のニックネームを出口とするユニキャストのTRILLデータパケットを受信し、内包されたパケットの宛先MACアドレスがスマートエンドノードによって列挙されたMACアドレスである場合、RB1はそのパケットをカプセル化したままそのスマートエンドノードに送ります。外側のイーサネットの宛先MACは宛先スマートエンドノードのMACアドレスであり、内側の宛先MACアドレスはスマートエンドノードのMACアドレスか、スマートエンドノードがSmart Helloで広告したほかのMACアドレスのいずれかであり、外側のイーサネットの送信元MACアドレスはRB1のポートのMACアドレスです。RB1とスマートエンドノードの間には1ホップがあるので、エッジRBridgeはそれでもHop countの値を1減らします。
  • スマートエンドノードがあるポートからマルチデスティネーションのTRILLデータパケットを受信した場合、RBridge RB1は、出口ニックネームが示す配布ツリーに基づいて、TRILLカプセル化されたものをTRILLキャンパスに転送します。出口ニックネームが配布ツリーに対応していない場合、パケットは破棄されます。エッジRBridge RB1に通常のエンドノード（つまり、スマートエンドノードではないエンドノード）が接続している場合、RB1は、マルチデスティネーションのTRILLフレームをキャンパスの残りの部分に転送することに加えて、フレームのカプセル化を解除し、マルチキャストリスナーに基づいて枝刈りされる可能性のあるそれらのポートにネイティブフレームを送信します。
  • ハイブリッドエンドノード（スマートエンドノードと、スマートエンドノードではないエンドノード）を含むポートから、スマートエンドノードではないエンドノードが送信したネイティブのマルチデスティネーションデータフレームをRB1が受信した場合、RB1はそれをマルチデスティネーションのTRILLデータパケットとしてカプセル化し、カプセル化したマルチデスティネーションのTRILLデータパケットを同じポートからそのポートに接続しているスマートエンドノードに送信するとともに、ほかのポートを通じてTRILLキャンパスにも送信します。
  • RB1がリモートRBridgeからマルチデスティネーションのTRILLデータパケットを受信し、出力ポートにハイブリッドエンドノード（スマートエンドノードと、スマートエンドノードではないエンドノード）が含まれる場合、RB1はそのポートからマルチキャストフレームのコピーを2つ送信します。1つはネイティブのもの、もう1つはTRILLカプセル化されたフレームです。スマートエンドノードは、マルチデスティネーションのTRILLデータパケットを受信すると、リモートの（MACアドレス、データラベル、ニックネーム）エントリーを学習します。スマートエンドノードはネイティブのデータフレームを無視します。通常の（スマートでない）エンドノードはネイティブフレームを受信してリモートMACアドレスを学習し、TRILLデータパケットを無視します。この中継の解決策は、エッジRBridgeにある程度の複雑さをもたらし、ネットワーク帯域幅のリソースを浪費する可能性があります。そのため、スマートなエンドノードとスマートでないエンドノードを異なるポートに接続することで、ハイブリッドエンドノードのシナリオを避けることが推奨されます（RECOMMENDED）。

6. Multihoming Scenario

6. マルチホーミングのシナリオ

Multihoming is a common scenario for the Smart Endnode. The Smart Endnode is on a link attached to the TRILL domain in two places: edge RBridges RB1 and RB2. Take Figure 4 as an example. The Smart Endnode SE1 is attached to the TRILL domain by RB1 and RB2 separately. Both RB1 and RB2 could announce their nicknames to SE1.

マルチホーミングは、スマートエンドノードにとって一般的なシナリオです。スマートエンドノードは、エッジRBridge RB1とRB2という2か所でTRILLドメインに接続しているリンク上にあります。例として図4を取り上げます。スマートエンドノードSE1は、RB1とRB2によって別々にTRILLドメインに接続しています。RB1とRB2はどちらも、自身のニックネームをSE1に通知できます。

Smart Endnode SE1 can choose either the nickname of RB1 or RB2 when encapsulating and forwarding a TRILL Data packet. If the active-active load balance is considered for the multihoming scenario, the Smart Endnode SE1 could use both the nickname of RB1 and RB2 to encapsulate and forward TRILL Data packet. SE1 uses RB1's nickname when forwarding through RB1 and RB2's nickname when forwarding through RB2. This will cause MAC flip-flopping (see [RFC7379]) of the endnode table entry in the remote RBridges (or Smart Endnodes). The solution for the MAC flip-flopping issue is to set a multihoming bit in the RSV field of the TRILL Data packet. When remote RBridge RB3 or Smart Endnodes receive a data packet with the multihomed bit set, the endnode entries (SE1's MAC address, label, RB1's nickname) and (SE1's MAC address, label, RB2's nickname) will coexist as endnode entries in the remote RBridge. (An alternative solution would be to use the ESADI protocol to distribute multiple attachments of a MAC address of a multihoming group. The ESADI is deployed among the edge RBridges (see Section 5.3 of [RFC7357]).

スマートエンドノードSE1は、TRILLデータパケットをカプセル化して転送するときに、RB1とRB2のどちらのニックネームを選択することもできます。マルチホーミングのシナリオでアクティブ-アクティブの負荷分散を考慮する場合、スマートエンドノードSE1は、RB1とRB2の両方のニックネームを使用してTRILLデータパケットをカプセル化して転送できます。SE1は、RB1を通じて転送するときにはRB1のニックネームを使用し、RB2を通じて転送するときにはRB2のニックネームを使用します。これにより、リモートRBridge（またはスマートエンドノード）のエンドノードテーブルのエントリーでMACフリップフロップ（[RFC7379]を参照）が発生します。MACフリップフロップの問題の解決策は、TRILLデータパケットのRSVフィールドにマルチホーミングビットを設定することです。リモートRBridge RB3またはスマートエンドノードが、マルチホーミングビットが設定されたデータパケットを受信すると、エンドノードエントリー（SE1のMACアドレス、ラベル、RB1のニックネーム）と（SE1のMACアドレス、ラベル、RB2のニックネーム）は、リモートRBridgeのエンドノードエントリーとして共存します。（別の解決策としては、ESADIプロトコルを使用して、マルチホーミンググループのMACアドレスの複数の接続を配布することが考えられます。ESADIはエッジRBridgeの間に展開されます（[RFC7357]のセクション5.3を参照）。

7. Security Considerations

7. セキュリティーに関する考慮事項

Smart-Hellos can be secured by using Authentication TLVs based on [RFC5310]. If they are not secured, then it is easier for a rogue end station that does not posses the required keying material to be falsely recognized as a valid Smart Endnode.

Smart-Helloは、[RFC5310]に基づくAuthentication TLVを使用して保護できます。保護されていない場合、必要な鍵情報を持たない不正なエンドステーションが、正当なスマートエンドノードであると誤って認識されやすくなります。

For general TRILL Security Considerations, see [RFC6325]. As stated there, since end stations are connected to edge RBridge ports by Ethernet, those ports MAY require end stations to authenticate themselves using [IEEE802.1X] and authenticate and encrypt traffic to/from the RBridge port with [IEEE802.1AE].

TRILLのセキュリティーに関する一般的な考慮事項については、[RFC6325]を参照してください。そこで述べられているように、エンドステーションはイーサネットによってエッジRBridgeのポートに接続されるので、それらのポートは、[IEEE802.1X]を使用してエンドステーションに自身を認証させ、[IEEE802.1AE]を使用してRBridgeのポートとの間のトラフィックを認証および暗号化するよう要求してもよいです（MAY）。

If they misbehave, Smart Endnodes can forge arbitrary ingress and egress nicknames in the TRILL headers of the TRILL Data packets they construct. Decapsulating at egress RBridges or remote Smart Endnodes that believe such a forged ingress nickname would send future traffic destined for the inner-source MAC address of the TRILL data frame to the wrong edge RBridge if data-plane learning is in use. Because of this, an RBridge port should not be configured to support Smart Endnodes unless the end stations on that link are trusted or can be adequately authenticated.

スマートエンドノードは、不正な動作をする場合、自身が構築するTRILLデータパケットのTRILLヘッダー内の入口ニックネームと出口ニックネームを任意に偽造できます。データプレーン学習が使用されている場合、そのような偽造された入口ニックネームを信じた、カプセル化を解除する出口RBridgeまたはリモートのスマートエンドノードは、そのTRILLデータフレームの内側の送信元MACアドレス宛ての以降のトラフィックを、誤ったエッジRBridgeに送信してしまいます。このため、そのリンク上のエンドステーションが信頼できるか、十分に認証できる場合を除いて、RBridgeのポートをスマートエンドノードをサポートするように設定すべきではありません。

As with any end station, Smart Endnodes can forge the outer MAC addresses of packets they send (see Section 6 of [RFC6325].) Because they encapsulate TRILL Data packets, they can also forge inner MAC addresses. The encapsulation performed by Smart Endnodes also means they can send data in any Data Label, which means they must be trusted in order to enforce a security policy based on Data Labels.

ほかのエンドステーションと同様に、スマートエンドノードは自身が送信するパケットの外側のMACアドレスを偽造できます（[RFC6325]のセクション6を参照）。スマートエンドノードはTRILLデータパケットをカプセル化するので、内側のMACアドレスも偽造できます。また、スマートエンドノードがカプセル化を行うということは、任意のデータラベルでデータを送信できることを意味します。つまり、データラベルに基づくセキュリティーポリシーを適用するには、スマートエンドノードが信頼できるものでなければなりません。

The TRILL-Hello is a type of TRILL ES-IS and is defined in [RFC8171]. Receiving and processing TRILL-Hello for RBridges and Smart Endnodes would not bring more security and vulnerability issues than the TRILL ES-IS security defined in [RFC8171].

TRILL-HelloはTRILL ES-ISの一種であり、[RFC8171]で定義されています。RBridgeとスマートエンドノードがTRILL-Helloを受信して処理しても、[RFC8171]で定義されているTRILL ES-ISのセキュリティーを超えるセキュリティーや脆弱性の問題が生じることはありません。

For added security against the compromise of data due to its misdelivery for any reason, including the above, end-to-end encryption and authentication should be considered; that is, encryption and authentication from source end station to destination end station.

上記を含むあらゆる理由による誤配送に起因するデータの侵害に対してセキュリティーを高めるには、エンドツーエンドの暗号化と認証、つまり送信元エンドステーションから宛先エンドステーションまでの暗号化と認証を検討すべきです。

The mechanism described in this document requires Smart Endnodes to be aware of the MAC address(es) of the TRILL edge RBridge(s) to which they are attached and the egress RBridge nickname from which the destination of the packets is reachable. With that information, Smart Endnodes can learn a substantial amount about the topology of the TRILL domain. Therefore, there could be a potential security risk when the Smart Endnodes are not trusted or are compromised.

この文書で説明するメカニズムでは、スマートエンドノードは、自身が接続しているTRILLエッジRBridgeのMACアドレスと、パケットの宛先に到達できる出口RBridgeのニックネームを知っている必要があります。スマートエンドノードは、その情報によってTRILLドメインのトポロジーについてかなり多くのことを知ることができます。したがって、スマートエンドノードが信頼できない場合や侵害されている場合には、潜在的なセキュリティーリスクが生じる可能性があります。
