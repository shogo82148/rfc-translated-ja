RFC 96

An Interactive Network Experiment to Study Modes of Access the Network Information Center

RFC 96

Network Information Centerへのアクセス方式を調べるための対話型ネットワーク実験

1. Introduction

1. はじめに

This NWG/RFC outlines the framework for a simple interactive experiment to study modes of access to the Network Information Center (NIC). A detailed specification for the initial access conventions to the NIC is contained in NWG/RFC 97, NIC (5740,). The initial online service to be provided by the Network Information Center are oriented around the SRI-ARC (ARC) Online System, typewriter version - NLS(T). These services will involve creation, manipulation, searching, and distribution of symbolic material (text initially). The initial Online System was display oriented and considerable development has gone into the study of features required for a comfortable interface to the user. In preparation for use with the Network Information Center, a typewriter oriented version has been developed. Assuming good computer response and a typewriter terminal operating at 30 char/sec, the system provides powerful and comfortable to use capabilities for handling structured textual material.

このNWG/RFCは、Network Information Center（NIC）へのアクセス方式を調べるための簡単な対話型実験の枠組みを概説します。NICへの初期のアクセス規約の詳細な仕様は、NWG/RFC 97、NIC (5740,)に記載されています。Network Information Centerが提供する初期のオンラインサービスは、SRI-ARC（ARC）オンラインシステムのタイプライター版であるNLS(T)を中心としたものです。これらのサービスには、記号的な資料（当初はテキスト）の作成、操作、検索、配布が含まれます。初期のオンラインシステムはディスプレイ向けのもので、ユーザーにとって快適なインターフェイスに必要な機能の研究にかなりの開発が費やされてきました。Network Information Centerでの利用に備えて、タイプライター向けの版が開発されました。コンピューターの応答が良好で、タイプライター端末が30文字/秒で動作すると仮定すれば、このシステムは、構造化されたテキスト資料を扱うための強力で使い勝手のよい機能を提供します。

The question to which the experiment, to be described below, addresses itself is to determine how to extend these capabilities through the network to users at remote sites, possibly operating 10 char/sec and higher speed terminals through fairly heavily loaded systems. This experiment will also provide useful information about the interactive characteristics of the network, and guidelines for designers of other interactive systems to be used with the network. We propose that this experiment will be conducted with the assistance and cooperation of one other site. We estimate that the experiment will require about three calendar months. In order to minimize the resources required for the experiment, we will collect meaningful response time statistics that are easy to obtain with presetly existing metering facilities in the SRI and cooperating site systems, and network performance measuring facilities. We will not conduct formal productivity studies with the users of the connection, but will obtain their subjective impressions on use of the various connection modes. The result will be data indicating the costs and benefits obtained using the types of access described below. We would expect that this information would be useful to sites in determining how they want to implement access to the NIC and other interactive sites.

以下で説明する実験が取り組む問題は、かなり高い負荷のかかったシステムを経由して、10文字/秒やそれより高速な端末を使っている可能性のあるリモートサイトのユーザーに、ネットワークを通じてこれらの機能をどのように提供するかを決めることです。この実験は、ネットワークの対話特性に関する有用な情報や、ネットワークで使われるほかの対話型システムの設計者向けの指針も提供するでしょう。この実験は、ほかの1つのサイトの支援と協力を得て実施することを提案します。実験には暦の上で約3か月かかると見積もっています。実験に必要な資源を最小限に抑えるため、SRIと協力サイトのシステムに現在ある計測機能と、ネットワーク性能の計測機能で容易に得られる、意味のある応答時間の統計を収集します。接続のユーザーを対象とした正式な生産性の調査は行いませんが、さまざまな接続方式を使ったときの主観的な印象をユーザーから聞き取ります。その結果として、以下で説明するアクセス方式を使ったときのコストと利点を示すデータが得られます。この情報は、各サイトがNICやほかの対話型サイトへのアクセスをどのように実装するかを決める際に役立つと期待しています。

During the period of the experiment, other sites will want to access the NIC as they come up on the network. We would recommend a simple approach, such as described in Section 2b, initially with a possible change later if the experiment indicates improved response and/or human factors coupling can be obtained with one of the other approaches, NWG/RFC 97, NIC (5740,) specifies this initial access approach in detail.

実験期間中にも、ほかのサイトはネットワークに接続し次第、NICにアクセスしたいと考えるでしょう。当初はセクション2bで説明するような単純な方法を推奨します。実験によって、ほかの方法のいずれかで応答や人間工学的な結合が改善できるとわかれば、後で変更する可能性があります。NWG/RFC 97、NIC (5740,)は、この初期のアクセス方法を詳しく規定しています。

2. Getting Connected to the Network

2. ネットワークへの接続

2a. Introduction

2a. はじめに

There are three basic approaches to allowing remote sites to connect to the NIC through the network, which we can call User Program Telnet, NLS(T) Front End, Monitor Telnet. Each of these is discussed below. Each approach requires code which will run in the remote host.

リモートサイトがネットワークを通じてNICに接続できるようにする基本的な方法は3つあり、それぞれユーザープログラムTelnet、NLS(T)フロントエンド、モニターTelnetと呼ぶことができます。以下でそれぞれについて説明します。どの方法でも、リモートホストで動作するコードが必要です。

We assume that standard conventions for Telnet programs will be specified by the Network Working Group. In the companion paper (NWG/RFC 97), NIC (5740,)) we include recommended conventions on solving those problems which we are aware exists relative to initial NIC access, although we have tried to specify conventions useful more generally. The NLS(T) Front End Program would interface to the Telnet Program.

Telnetプログラムの標準的な規約は、Network Working Groupが規定するものと想定しています。対になる文書（NWG/RFC 97）、NIC (5740,))では、NICへの初期のアクセスに関して私たちが認識している問題を解決するための推奨規約を示しています。ただし、より一般的にも役立つ規約を規定するよう努めました。NLS(T)フロントエンドプログラムは、Telnetプログラムとのインターフェイスを持つことになります。

We assume that no matter which approach is taken, the software at the ARC end use the information obtained during the connection process to log-in the remote terminal under a general account and will place the terminal user in the NIC version of NLS, which we will call NLS(NIC) for short. The NLS(NIC) will ask the terminal user for his initials. The remote user then has access to all NIC facilities.

どの方法をとる場合でも、ARC側のソフトウェアは、接続処理の間に得た情報を使ってリモート端末を一般アカウントでログインさせ、端末のユーザーをNIC版のNLS（略してNLS(NIC)と呼びます）に入れるものと想定しています。NLS(NIC)は端末のユーザーにイニシャルを尋ねます。その後、リモートユーザーはNICのすべての機能を利用できます。

The initial typewriter oriented system accepts commands of the general form:

初期のタイプライター向けシステムは、次の一般的な形式のコマンドを受け付けます。

   <command words> <operand> <delimiter> ... <operand> <delimiter>

   <command words> <operand> <delimiter> ... <operand> <delimiter>

The <command words> is usually two words, the first to indicate a general operation class, and the second to indicate a general data structure type to be operated on. The <operand>s specify specific data entities to be operated upon, or instructions to adjust NLS parameters.

<command words>は通常2語で、1語目は一般的な操作の種類を示し、2語目は操作対象となる一般的なデータ構造の種類を示します。<operand>は、操作対象となる具体的なデータ実体、またはNLSのパラメーターを調整するための指示を指定します。

The system at ARC is full duplex and allows the user to type the first character of the command words and the system immediately echos the remaining characters as feedback and support for the user. Other feedback is echoed where appropriate. The question we need to answer is what changes in this system will be required to suit it to the network and remote site constraints. We now look at problems existing at the remote sites.

ARCのシステムは全二重で、ユーザーはコマンド語の最初の1文字を入力するだけでよく、システムはユーザーへのフィードバックと支援として残りの文字を即座にエコーします。そのほかのフィードバックも、適切な箇所でエコーされます。答えるべき問題は、このシステムをネットワークとリモートサイトの制約に適合させるにはどのような変更が必要かということです。次に、リモートサイトに存在する問題を見ていきます。

To gain connection to the NIC we assume that the user logs into his local system and calls up a subsystem or cusp. This subsystem or system program, Telnet program will be used to access other sites as well. The remote terminal and its controlling software system can operate in three basic modes as seen by the host subsystems

NICに接続するには、ユーザーが自分のローカルシステムにログインし、サブシステムまたはcuspを呼び出すものと想定します。このサブシステムまたはシステムプログラム、つまりTelnetプログラムは、ほかのサイトへのアクセスにも使われます。リモート端末とそれを制御するソフトウェアシステムは、ホストのサブシステムから見て、3つの基本的なモードで動作できます。

  • Case 1 - Character at a time half duplex
  • Case 2 - Character at a time full duplex
  • Case 3 - Line at a time half duplex
  • ケース1 - 文字単位の半二重
  • ケース2 - 文字単位の全二重
  • ケース3 - 行単位の半二重

Although line at a time is full duplex is a logical possibility, no such approach is in general use and we ignore it in the following discussion.

行単位の全二重も論理的にはありえますが、そのような方法は一般には使われていないため、以下の議論では無視します。

In the discussions to follow, in Section 2b, 2c and 2d, we describe the modes of access which we would like to investigate experimentally. We want to study user reaction with 10 char/sec, 15 char/sec, and 30 char/sec devices.

以下のセクション2b、2c、2dの議論では、実験的に調べたいアクセス方式を説明します。10文字/秒、15文字/秒、30文字/秒の装置でのユーザーの反応を調べたいと考えています。

2b. User Program Telnet

2b. ユーザープログラムTelnet

Consider the above classes of terminal in turn and the ways the Telnet program might handle communications between them and the NIC. The Telnet program might allow both full and half duplex communication as specified by the user.

上記の端末の種類を順に取り上げ、Telnetプログラムがそれらの端末とNICとの間の通信をどのように扱えるかを検討します。Telnetプログラムは、ユーザーの指定に応じて全二重と半二重の両方の通信を可能にできます。

2b1. Case 1 - Character at a Time Full Duplex

2b1. ケース1 - 文字単位の全二重

The simplest approach would be for the Telnet program to take each character received from the terminal (except a special character or character sequence needed to escape back to the terminals host system), convert the code to ASCII and transmit it as a message to NLS(NIC). NLS(NIC) would handle all character echoing and transmit echo messages back to the Telnet for actual transmission to the terminal in the appropriate terminal code. This mode of communication involves full duplex transmission user to user and is probably the severest test of the interactive characteristics of the host-network-host system.

最も単純な方法は、Telnetプログラムが端末から受け取った各文字（端末のホストシステムに戻るためのエスケープに必要な特殊文字や文字列を除く）をASCIIに変換し、メッセージとしてNLS(NIC)に送信するというものです。NLS(NIC)はすべての文字のエコーを処理し、エコーのメッセージをTelnetに送り返します。Telnetはそれを適切な端末コードで実際に端末に送信します。この通信方式は、ユーザーからユーザーまでの全二重伝送を伴い、ホスト・ネットワーク・ホストのシステムの対話特性に対するおそらく最も厳しい試験となります。

Depending on loading at the remote host, on the network, and at ARC, round trip delay for simple character echoing may be several seconds. Experience in communication between the old ARC 940 and a heavily loaded PDP-10 at Utah showed occasional delays on the order of 4 or 5 seconds and longer for single character echoing. Human factors considerations in use of NLS(NIC) indicate that such delays would be frustrating to the user. A more cageful study of this mode of communication should give a base against which to measure the other modes of communication.

リモートホスト、ネットワーク、ARCの負荷によっては、単純な文字のエコーの往復遅延が数秒になる場合があります。旧ARCの940とユタ大学の高負荷のPDP-10との間の通信の経験では、1文字のエコーに4〜5秒、あるいはそれ以上の遅延がときおり生じました。NLS(NIC)の利用における人間工学的な考察によれば、このような遅延はユーザーを苛立たせます。この通信方式をより注意深く調べることで、ほかの通信方式を測定するための基準が得られるはずです。

2b2. Case 2 - Character at a Time Half Duplex

2b2. ケース2 - 文字単位の半二重

There are two subcases which we treat identically:

同じように扱う2つの下位ケースがあります。

  • i) The Telnet program sees a half duplex terminal.
  • ii) The Telnet program sees a full duplex terminal, but provides echoing so as to make the terminal half duplex as seen by NIC.
  • i) Telnetプログラムから半二重の端末が見える場合。
  • ii) Telnetプログラムからは全二重の端末が見えるが、Telnetプログラムがエコーを行うことで、NICからは端末が半二重に見えるようにする場合。

With the character at a time half duplex case the NIC program will operate in two modes:

文字単位の半二重のケースでは、NICのプログラムは2つのモードで動作します。

  • a) short mode
  • b) long mode
  • a) ショートモード
  • b) ロングモード

In short mode the user will type in the command and receive on his terminal only the characters echoed by his system and the NIC response to the command.

ショートモードでは、ユーザーはコマンドを入力し、自分のシステムがエコーした文字と、コマンドに対するNICの応答だけを端末で受け取ります。

In long mode. the user will receive feedback from NIC at an appropriate point in the command. We want to see how novice and experienced users feel about working in these two modes, given the delays in the system response.

ロングモードでは、ユーザーはコマンドの適切な箇所でNICからフィードバックを受け取ります。システムの応答に遅延があることを踏まえて、初心者と熟練したユーザーがこれら2つのモードでの作業をどう感じるかを調べたいと考えています。

2b3. Case 3 - Line at a Time Half Duplex

2b3. ケース3 - 行単位の半二重

From the point of ciew of the NIC this case is essentially the same as Case 2. From the point of ciew of the network this case is a more efficient use fo the network as the messages are longer. This case is also more efficient for the user host system as it will require fewer calls to the Telnet subsystem; response for Case 3 may be better than Case 2.

NICから見れば、このケースは本質的にケース2と同じです。ネットワークから見れば、メッセージが長くなるため、このケースのほうがネットワークを効率よく使えます。また、Telnetサブシステムの呼び出し回数が少なくて済むため、ユーザーのホストシステムにとっても効率がよく、ケース3の応答はケース2よりもよくなる可能性があります。

2c. The NLS(T) Front End

2c. NLS(T)フロントエンド

In this mode of communication, the subsystem which handles communication with the NIC is to perform some of the interactive and other tasks now performed by NLS(T). The type of tasks to be performed are echoing of the characters typed and the additional feedback characters for the full spell out of the command words, parsing of the command string, error handling where appropriate, and the sending of a parsed string as a message to NLS(T). If it should turn out that this mode of communication is the one preferred by sites, we would expect to supply an example version of the Front End program written in some language to serve as a model for implementation. The Network Working Group may want to give further study to a standard language for specifying such programs as indicated in NWG/RFC 51, NIC (4752,).

この通信方式では、NICとの通信を扱うサブシステムが、現在NLS(T)が行っている対話的な処理やその他の処理の一部を行います。行う処理の種類は、入力された文字のエコーとコマンド語を完全に綴るための追加のフィードバック文字のエコー、コマンド文字列の構文解析、適切な場合のエラー処理、構文解析した文字列のメッセージとしてのNLS(T)への送信です。この通信方式が各サイトに好まれるものだとわかった場合には、実装のモデルとなるように、何らかの言語で書いたフロントエンドプログラムの例を提供するつもりです。Network Working Groupは、NWG/RFC 51、NIC (4752,)で示されているように、このようなプログラムを記述するための標準言語についてさらに検討したいと考えるかもしれません。

2d. Monitor Telnet

2d. モニターTelnet

Much of the response delay in the experiments of Section 2b is expected to result from the fact that the Telnet described there is a user program. We will run the experiments of Section 2b with the appropriate Telnet routines resident as a part of the user host monitor.

セクション2bの実験での応答遅延の多くは、そこで説明したTelnetがユーザープログラムであることに起因すると予想されます。そこで、適切なTelnetルーチンをユーザーのホストのモニターの一部として常駐させた状態で、セクション2bの実験を実施します。
