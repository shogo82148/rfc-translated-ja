RFC 8406

Taxonomy of Coding Techniques for Efficient Network Communications

RFC 8406

効率的なネットワーク通信のための符号化技術の分類

Abstract

概要

This document summarizes recommended terminology for Network Coding concepts and constructs. It provides a comprehensive set of terms in order to avoid ambiguities in future IRTF and IETF documents on Network Coding. This document is the product of the Coding for Efficient Network Communications Research Group (NWCRG), and it is in line with the terminology used by the RFCs produced by the Reliable Multicast Transport (RMT) and FEC Framework (FECFRAME) IETF working groups.

この文書は、ネットワーク符号化（Network Coding）の概念と構成要素について推奨する用語をまとめたものです。この文書は、ネットワーク符号化に関する今後のIRTFおよびIETFの文書における曖昧さを避けるために、包括的な用語一式を提供します。この文書は、Coding for Efficient Network Communications Research Group（NWCRG）の成果物であり、IETFのReliable Multicast Transport（RMT）ワーキンググループとFEC Framework（FECFRAME）ワーキンググループが作成したRFCで使われている用語と整合しています。

1. Introduction

1. はじめに

This document is the product of and represents the collaborative work and consensus of the Coding for Efficient Network Communications Research Group (NWCRG); it is not an IETF product and is not a standard. In 2017, the document was discussed during three audio conferences, each of them gathering 6 to 8 key experts; it was co-edited and subjected to an RG Last Call. The general feeling was that the document was ready. Additional information about Network Coding may be found on these NWCRG pages: <https://irtf.org/nwcrg> and <https://datatracker.ietf.org/rg/nwcrg/about/>.

この文書は、Coding for Efficient Network Communications Research Group（NWCRG）の成果物であり、その共同作業とコンセンサスを代表するものです。この文書はIETFの成果物ではなく、標準でもありません。2017年に、この文書は3回の音声会議で議論され、各会議には6～8名の主要な専門家が集まりました。この文書は共同で編集され、RGラストコールにかけられました。全体としては、この文書の準備が整ったという感触でした。ネットワーク符号化に関する追加情報は、NWCRGの次のページで入手できます：<https://irtf.org/nwcrg>および<https://datatracker.ietf.org/rg/nwcrg/about/>。

The literature on Network Coding research and system design, including IETF documentation, led to a rich set of concepts and constructs. This document collects terminology used in the domain, both outside and inside IETF, provides concise definitions, and introduces a high-level taxonomy. Its primary goal is to be useful to IETF and IRTF activities. It is also in line with the terminology already used by the RFCs produced by the Reliable Multicast Transport (RMT) and FEC Framework (FECFRAME) IETF working groups, in particular [RFC5052], [RFC5740], [RFC5775], [RFC6363], and [RFC6726]. This document is also related to IETF work being done in the PAYLOAD and TSVWG WGs (in particular, the extension of FECFRAME to support Sliding Window Codes and the Random Linear Coding (RLC) sliding window FEC scheme) and past work in the AVTCORE and MMUSIC WGs. Note that in the definitions, the "(IETF)" tag indicates that the associated term is already used in IETF documents (Internet-Drafts and RFCs).

IETFの文書を含む、ネットワーク符号化の研究とシステム設計に関する文献によって、豊富な概念と構成要素が生まれました。この文書は、IETFの内外でこの分野において使われている用語を集め、簡潔な定義を示し、高レベルの分類を導入します。この文書の主な目的は、IETFとIRTFの活動に役立つことです。この文書はまた、IETFのReliable Multicast Transport（RMT）ワーキンググループとFEC Framework（FECFRAME）ワーキンググループが作成したRFC、特に[RFC5052]、[RFC5740]、[RFC5775]、[RFC6363]、および[RFC6726]ですでに使われている用語とも整合しています。この文書は、PAYLOADワーキンググループとTSVWGワーキンググループで行われているIETFの作業（特に、スライディングウィンドウ符号をサポートするためのFECFRAMEの拡張と、ランダム線形符号化（Random Linear Coding、RLC）スライディングウィンドウFECスキーム）や、AVTCOREワーキンググループとMMUSICワーキンググループでの過去の作業にも関連しています。なお、定義の中の「(IETF)」タグは、関連する用語がIETFの文書（インターネットドラフトとRFC）ですでに使われていることを示します。

This document focuses on packet transmissions and losses. These losses will typically be triggered by various types of networking issues and/or impairments (e.g., congested routers or intermittent wireless connectivity). The notion of "packet" itself is multiform, depending on the target use case and the notion of network (e.g., in which layer of the protocol stack does the coding middleware operate?). For instance, a "packet" may be a data unit to be carried as a UDP payload because the coding middleware is located between the application and UDP. In another configuration, coding may be applied within an overlay network and the notion of "packet" will be totally different. In any case, the goals of Network Coding can be to improve the network throughput, efficiency, latency, and scalability, as well as to provide resilience to partition, attacks, and eavesdropping (NWCRG charter). Both End-to-End Coding and systems that also perform recoding within intermediate forwarding nodes are considered in this document.

この文書は、パケットの伝送と損失に焦点を当てます。これらの損失は、通常、さまざまな種類のネットワークの問題や障害（たとえば、輻輳したルーターや断続的な無線接続）によって引き起こされます。「パケット」という概念自体は、対象とするユースケースやネットワークの概念（たとえば、符号化ミドルウェアがプロトコルスタックのどの層で動作するのか）によって、さまざまな形をとります。たとえば、符号化ミドルウェアがアプリケーションとUDPの間に位置するために、「パケット」がUDPペイロードとして運ばれるデータ単位である場合があります。別の構成では、オーバーレイネットワーク内で符号化が適用され、「パケット」の概念はまったく異なるものになります。いずれの場合も、ネットワーク符号化の目的は、ネットワークのスループット、効率、遅延、スケーラビリティーを向上させることや、分断、攻撃、盗聴に対する耐性を提供すること（NWCRG憲章）であり得ます。この文書では、エンドツーエンド符号化と、中間の転送ノード内で再符号化も行うシステムの両方を対象とします。

This document does not consider physical-layer transmission issues, physical-layer codes, or error detection: if low-layer error codes detect but fail to correct bit errors, or if an upper-layer checksum (e.g., within IP or UDP) identifies a corrupted packet, then the packet is supposed to be dropped.

この文書では、物理層の伝送の問題、物理層の符号、または誤り検出は考慮しません。下位層の誤り符号がビット誤りを検出したものの訂正できなかった場合や、上位層のチェックサム（たとえば、IPやUDP内のもの）が破損したパケットを識別した場合、そのパケットは破棄されるものとします。

2. General Definitions and Concepts

2. 一般的な定義と概念

This section provides general definitions and concepts that are used throughout this document.

このセクションでは、この文書全体で使われる一般的な定義と概念を示します。

Packet Erasure Channel:
A communication path where packets are either dropped or received without any error. This type of packet drop is referred to as an "erasure" or "loss". The term "channel" must be understood as a generic term for any type of communication technology (e.g., an Ethernet link, a WiFi network, or a full path between two nodes over the Internet). As opposed to the "Erasure" channels, "Error" channels are where one or multiple bit errors may happen during a packet transmission. These "Error" channels are out of scope.
Erasure Correcting Code (ECC) or (IETF) Forward Erasure Correction (FEC):
A code for the Packet Erasure Channel (only). These codes are also called "Application-Level FECs" to highlight that they have been designed for use within the higher layers of the protocol stack to protect against packet losses. As opposed to ECCs/FECs, "Error" correction codes are capable of identifying the presence of bit errors and perhaps correcting them. The "Error" correction codes are out of scope.
End-to-End Coding:
A system where coding is performed at the source or (coding) middlebox, and decoding is performed at the destination(s) or (decoding) middlebox. There is no recoding operation at intermediate nodes. This is the approach followed in the FLUTE/ALC [RFC6726] [RFC5775], NORM [RFC5740], and FECFRAME [RFC6363] protocols.
Network Coding:
A system where coding can be performed at the source as well as at intermediate forwarding nodes (all or a subset of them). End-to-End Coding is regarded as a special case of Network Coding. Depending on the use case, additional assumptions can be made: for instance, the destination knowing the Coding Nodes' topology and coding operations can help during decoding operations.
Packet versus Symbol:
Generally speaking, a Packet is the unit of data that is sent in the Packet Erasure Channel, while a Symbol is the unit of data that is manipulated during the encoding and decoding operations.
Original Payload, Uncoded Payload, Systematic Symbol, or (IETF) Source Symbol:
A unit of data originating from the source that is used as input to encoding operations.
Coded Payload, Coded Symbol, or (IETF) Repair Symbol:
A unit of data that is the result of a coding operation, applied either to Source Symbols or (in case of recoding) Source and/or Repair Symbols. When there is a single Repair Symbol per Repair Packet, a Repair Symbol corresponds to a Repair Packet.
Input Symbol and Output Symbol:
A unit of data that is used as input to an encoding operation or that is generated as output of an encoding operation. At a recoding node, Repair Symbols are also part of the Input Symbols. With Systematic Coding, Source Symbols are also part of the Output Symbols.
(IETF) Encoding Symbol:
A Source or a Repair Symbol.
(En)coding versus Recoding versus Decoding:
(En)coding is an operation that takes Source Symbols as input and produces Encoding Symbols as output. Recoding is an operation that takes Encoding Symbols as input and produces Encoding Symbols as output. Decoding is an operation takes Encoding Symbols as input and produces Source Symbols as output.
(IETF) Source Packet:
A packet originating from the source that contributes to one or more Source Symbols. For instance, an RTP packet as a whole can constitute a Source Symbol. In other situations (e.g., to address variable size packets), a single RTP packet may contribute to various Source Symbols.
(IETF) Repair Packet:
A packet containing one or more Repair Symbols.
パケット消失通信路（Packet Erasure Channel）：
パケットが破棄されるか、誤りなく受信されるかのどちらかである通信経路。この種のパケットの破棄は、「消失（erasure）」または「損失（loss）」と呼ばれます。「通信路（channel）」という用語は、あらゆる種類の通信技術（たとえば、イーサネットリンク、WiFiネットワーク、またはインターネット上の2つのノード間の経路全体）を表す一般的な用語として理解する必要があります。「消失（Erasure）」通信路とは対照的に、「誤り（Error）」通信路は、パケットの伝送中に1つまたは複数のビット誤りが発生する可能性がある通信路です。これらの「誤り」通信路は範囲外です。
消失訂正符号（Erasure Correcting Code、ECC）、または(IETF)前方消失訂正（Forward Erasure Correction、FEC）：
パケット消失通信路（のみ）のための符号。これらの符号は、パケット損失から保護するためにプロトコルスタックの上位層で使用するよう設計されていることを強調するために、「アプリケーションレベルFEC（Application-Level FEC）」とも呼ばれます。ECC/FECとは対照的に、「誤り（Error）」訂正符号は、ビット誤りの存在を識別でき、場合によってはそれを訂正できます。「誤り」訂正符号は範囲外です。
エンドツーエンド符号化（End-to-End Coding）：
送信元または（符号化）ミドルボックスで符号化を行い、宛先または（デコード）ミドルボックスでデコードを行うシステム。中間ノードでは再符号化の操作を行いません。これは、FLUTE/ALC [RFC6726] [RFC5775]、NORM [RFC5740]、およびFECFRAME [RFC6363]の各プロトコルで採用されているアプローチです。
ネットワーク符号化（Network Coding）：
送信元だけでなく、中間の転送ノード（そのすべて、または一部）でも符号化を行うことができるシステム。エンドツーエンド符号化は、ネットワーク符号化の特別な場合とみなされます。ユースケースによっては、追加の前提を置くことができます。たとえば、宛先が符号化ノードのトポロジーと符号化の操作を知っていれば、デコードの操作に役立つ場合があります。
パケットとシンボル（Packet versus Symbol）：
一般的に言えば、パケット（Packet）はパケット消失通信路で送信されるデータの単位であり、シンボル（Symbol）は符号化とデコードの操作の中で扱われるデータの単位です。
元のペイロード（Original Payload）、符号化されていないペイロード（Uncoded Payload）、組織シンボル（Systematic Symbol）、または(IETF)ソースシンボル（Source Symbol）：
送信元から発生し、符号化の操作への入力として使用されるデータの単位。
符号化済みペイロード（Coded Payload）、符号化済みシンボル（Coded Symbol）、または(IETF)修復シンボル（Repair Symbol）：
ソースシンボル、または（再符号化の場合は）ソースシンボルと修復シンボルのいずれかまたは両方に適用された符号化の操作の結果であるデータの単位。修復パケットごとに修復シンボルが1つだけの場合、修復シンボルは修復パケットに対応します。
入力シンボルと出力シンボル（Input Symbol and Output Symbol）：
符号化の操作への入力として使用される、または符号化の操作の出力として生成されるデータの単位。再符号化を行うノードでは、修復シンボルも入力シンボルの一部です。組織符号化では、ソースシンボルも出力シンボルの一部です。
(IETF)符号化シンボル（Encoding Symbol）：
ソースシンボルまたは修復シンボル。
符号化と再符号化とデコード（(En)coding versus Recoding versus Decoding）：
符号化（(En)coding）は、ソースシンボルを入力として受け取り、符号化シンボルを出力として生成する操作です。再符号化（Recoding）は、符号化シンボルを入力として受け取り、符号化シンボルを出力として生成する操作です。デコード（Decoding）は、符号化シンボルを入力として受け取り、ソースシンボルを出力として生成する操作です。
(IETF)ソースパケット（Source Packet）：
送信元から発生し、1つ以上のソースシンボルの元となるパケット。たとえば、RTPパケット全体で1つのソースシンボルを構成できます。別の状況（たとえば、可変サイズのパケットに対処する場合）では、1つのRTPパケットが複数のソースシンボルの元となる場合があります。
(IETF)修復パケット（Repair Packet）：
1つ以上の修復シンボルを含むパケット。

Figure 1 illustrates the relationships between packets (what is sent in the Packet Erasure Channel) and symbols (what is manipulated during encoding and decoding operations) in case of a Systematic Coding at a Coding Node that performs Encoding (rather than Recoding). FEC decoding procedures are similarly performed in the reverse order.

図1は、（再符号化ではなく）符号化を行う符号化ノードにおける組織符号化の場合について、パケット（パケット消失通信路で送信されるもの）とシンボル（符号化とデコードの操作の中で扱われるもの）の関係を示しています。FECのデコード手順も同様に、逆の順序で行われます。

Source Node:
A node that generates one or more Source Flows.
Coding Node:
A node that performs FEC Encoding or Recoding operations. It may be an end host or a middlebox (Encoding case), or a forwarding node (Recoding case).
(IETF) Flow:
A stream of packets logically grouped.
(IETF) Source Flow:
A flow of Source Packets coming from an application on a given host and to which FEC encoding is to be applied, potentially along with other Source Flows. Depending on the use case, Source Flows may come from the same application, from different applications on the same host, or from different applications on different hosts.
(IETF) Repair Flow:
A flow containing Repair Packets after FEC encoding.
ソースノード（Source Node）：
1つ以上のソースフローを生成するノード。
符号化ノード（Coding Node）：
FEC符号化または再符号化の操作を行うノード。符号化ノードは、エンドホストやミドルボックス（符号化の場合）、または転送ノード（再符号化の場合）である場合があります。
(IETF)フロー（Flow）：
論理的にグループ化されたパケットのストリーム。
(IETF)ソースフロー（Source Flow）：
あるホスト上のアプリケーションから来るソースパケットのフローで、場合によっては他のソースフローとともに、FEC符号化を適用する対象となるもの。ユースケースによって、ソースフローは、同じアプリケーションから来る場合も、同じホスト上の異なるアプリケーションから来る場合も、異なるホスト上の異なるアプリケーションから来る場合もあります。
(IETF)修復フロー（Repair Flow）：
FEC符号化の後の修復パケットを含むフロー。

3. Taxonomy of Code Uses

3. 符号の使い方の分類

This section discusses the various ways of using coding, without going into coding details.

このセクションでは、符号化の詳細には立ち入らずに、符号化のさまざまな使い方について説明します。

Source Coding versus Channel Coding:

(see Figure 2) When both terms are used, "Source Coding" usually refers to compression techniques (e.g., audio and video compression) within the upper application that generates the Source Flow. "Channel Coding" refers to FEC encoding in order to improve transmission robustness, for instance, within the lower physical layer (out of scope of this document) or as part of Network Coding. These terms should not be confused with "FEC coding within the Source Node" and "FEC recoding within an intermediate Coding Node", respectively.

Figure 2 shows Network Coding between the application and UDP layers (as with RMT or FECFRAME architectures). Other architectures are possible, for instance, with Network Coding below the transport layer to allow recoding within the network.

Intra-Flow Coding or Single-Source Network Coding:
Process where incoming packets to the Coding Node belong to the same flow.
Inter-Flow Coding or Multi-Source Network Coding:
Process where incoming packets to the Coding Node belong to different flows.
Single-Path Coding:
Network Coding over a route that has a single path from the source to each destination(s). In case of multicast or broadcast traffic, this route is a tree. Coding may be done end to end and/or at intermediate forwarding nodes.
Multi-Path Coding:
Network Coding over a route that has multiple (at least partially) disjoint paths from the source to each given destination. Coding may be done end to end and/or at intermediate forwarding nodes.
情報源符号化と通信路符号化（Source Coding versus Channel Coding）：

（図2を参照してください）両方の用語が使われる場合、「情報源符号化（Source Coding）」は通常、ソースフローを生成する上位のアプリケーション内の圧縮技術（たとえば、音声や動画の圧縮）を指します。「通信路符号化（Channel Coding）」は、伝送の堅牢性を向上させるためのFEC符号化を指し、たとえば、下位の物理層内（この文書の範囲外）のものや、ネットワーク符号化の一部としてのものがあります。これらの用語を、それぞれ「ソースノード内でのFEC符号化」および「中間の符号化ノード内でのFEC再符号化」と混同すべきではありません。

図2は、（RMTやFECFRAMEのアーキテクチャーのように）アプリケーション層とUDP層の間でのネットワーク符号化を示しています。他のアーキテクチャーも可能であり、たとえば、ネットワーク内での再符号化を可能にするために、トランスポート層より下でネットワーク符号化を行うこともできます。

フロー内符号化（Intra-Flow Coding）、または単一送信元ネットワーク符号化（Single-Source Network Coding）：
符号化ノードに入ってくるパケットが同じフローに属する処理。
フロー間符号化（Inter-Flow Coding）、または複数送信元ネットワーク符号化（Multi-Source Network Coding）：
符号化ノードに入ってくるパケットが異なるフローに属する処理。
単一経路符号化（Single-Path Coding）：
送信元から各宛先への経路が1つだけであるルート上でのネットワーク符号化。マルチキャストトラフィックやブロードキャストトラフィックの場合、このルートはツリーになります。符号化は、エンドツーエンドで行われる場合も、中間の転送ノードで行われる場合も、その両方の場合もあります。
マルチパス符号化（Multi-Path Coding）：
送信元から各宛先への、（少なくとも部分的に）互いに素な複数の経路を持つルート上でのネットワーク符号化。符号化は、エンドツーエンドで行われる場合も、中間の転送ノードで行われる場合も、その両方の場合もあります。

4. Coding Details

4. 符号化の詳細

4.1. Coding Types

4.1. 符号化の種類

This section provides a high-level taxonomy of coding techniques. Technical details are discussed in subsequent sections.

このセクションでは、符号化技術の高レベルの分類を示します。技術的な詳細は、後続のセクションで説明します。

Linear Coding:
Linear combination of a set of Input Symbols (i.e., Source and/or Repair Symbols) using a given set of coefficients and resulting in a Repair Symbol. Many linear codes exist that differ from the way coding coefficients are drawn from a Finite Field of a given size.
Random Linear Coding (RLC):
Particular case of Linear Coding using a set of random coding coefficients.
Adaptive Linear Coding:
Linear Coding that utilizes cross-layer adaptation. For instance, an adaptive coding scheme may adapt the generation and transmission of Repair Packets according to the channel variations over time, accounting for the predictive loss of degrees of freedom due to erasures.
Block Coding:
Coding technique where the input Flow(s) must first be segmented into a sequence of blocks; FEC encoding and decoding are performed independently on a per-block basis. The term "Chunk Coding" is sometimes used, where a "Chunk" denotes a block.
Sliding Window Coding or Convolutional Coding:
General class of coding techniques that rely on a sliding encoding window. This is an alternative solution to Block Coding.
Fixed or Elastic Sliding Window Coding:
Coding technique that generates Repair Symbol(s) on the fly, from the set of Source Symbols present in the sliding encoding window at that time, usually by using Linear Coding. The sliding window may be either of fixed size or of variable size over the time (also known as "Elastic Sliding Window"). For instance, the size may depend on acknowledgments sent by the receiver(s) for a particular Source Symbol or Source Packet (received, decoded, or decodable).
Systematic Coding:
A coding technique where Source Symbols are part of the output Flow generated by a Coding Node.
Rateless and Non-rateless Coding:
Rateless Coding can generate an unlimited number of Repair Symbols (in practice, this number can be limited by practical considerations or because of use-case requirements) from a given set of Source Symbols, meaning that the code rate is null. RLC codes are an example of Rateless Codes. Alternately, Non-rateless Coding usually has a predefined maximum number of Repair Symbols that can be generated from a given set of Source Symbols.
線形符号化（Linear Coding）：
与えられた係数の集合を使用して入力シンボル（つまり、ソースシンボルと修復シンボルのいずれかまたは両方）の集合を線形結合し、その結果として修復シンボルを得るもの。符号化係数を所定のサイズの有限体からどのように選ぶかによって異なる、多くの線形符号が存在します。
ランダム線形符号化（Random Linear Coding、RLC）：
ランダムな符号化係数の集合を使用する、線形符号化の特別な場合。
適応線形符号化（Adaptive Linear Coding）：
クロスレイヤー適応を利用する線形符号化。たとえば、適応的な符号化スキームでは、消失による自由度の損失の予測を考慮して、時間の経過に伴う通信路の変動に応じて修復パケットの生成と送信を適応させる場合があります。
ブロック符号化（Block Coding）：
入力フローをまずブロックの列に分割する必要がある符号化技術。FEC符号化とデコードは、ブロックごとに独立して行われます。「チャンク符号化（Chunk Coding）」という用語が使われることもあり、その場合の「チャンク（Chunk）」はブロックを表します。
スライディングウィンドウ符号化（Sliding Window Coding）、または畳み込み符号化（Convolutional Coding）：
スライドする符号化ウィンドウに基づく符号化技術の一般的なクラス。これは、ブロック符号化の代替となる解決策です。
固定または伸縮スライディングウィンドウ符号化（Fixed or Elastic Sliding Window Coding）：
その時点でスライドする符号化ウィンドウ内に存在するソースシンボルの集合から、通常は線形符号化を使用して、修復シンボルをその場で生成する符号化技術。スライディングウィンドウは、固定サイズの場合もあれば、時間とともに変化する可変サイズ（「伸縮スライディングウィンドウ（Elastic Sliding Window）」とも呼ばれます）の場合もあります。たとえば、サイズは、特定のソースシンボルまたはソースパケット（受信済み、デコード済み、またはデコード可能なもの）について受信者が送信する確認応答に依存する場合があります。
組織符号化（Systematic Coding）：
ソースシンボルが、符号化ノードが生成する出力フローの一部となる符号化技術。
レートレス符号化と非レートレス符号化（Rateless and Non-rateless Coding）：
レートレス符号化は、与えられたソースシンボルの集合から無制限の数の修復シンボルを生成できます（実際には、この数は現実的な考慮事項やユースケースの要件によって制限される場合があります）。これは、符号化率がゼロであることを意味します。RLC符号は、レートレス符号の一例です。一方、非レートレス符号化では通常、与えられたソースシンボルの集合から生成できる修復シンボルの最大数があらかじめ決まっています。

4.2. Coding Basics

4.2. 符号化の基本事項

This section discusses and defines low-level coding aspects.

このセクションでは、低レベルの符号化の側面について説明し、定義します。

Code Rate:
In case of a Block Code, the Code Rate is the k/n ratio between the number of Source Symbols, k, and the number of Source plus Repair Symbols, n. With a Sliding Window Code, the Code Rate is defined similarly over a certain time interval, since the Code Rate may change dynamically. By definition, the Code Rate is such that: 0 < Code Rate <= 1. A Code Rate close to 1 indicates that a small number of Repair Symbols have been produced during the encoding process and vice versa.
(En)coding Window:
A set of Source (and Repair in the case of recoding) Symbols used as input to the coding operations. The set of symbols will typically change over time, as the Coding Window slides over the input Flow(s).
(En)coding Window Size:
The number of Source (and Repair in case of recoding) Symbols in the current Encoding Window. This size may change over the time.
Payload Set:
The set of Source and Repair Symbols available (i.e., received or previously decoded) at the receiver and used during FEC decoding operations.
Decoding Window:
The set of Source Symbols (only) that are considered in the current linear system of a receiver, independently of the fact these Source Symbols have been received, decoded, or lost. The Decoding Window will typically change over time, as transmissions and decoding progress, and may be different for different receivers of a session where content is multicast or broadcast.
Decoding Window Size:
The number of Source Symbols (only) in the current Decoding Window. This size may change over time.
Rank of a Payload Set or Rank of the Linear System:
At a receiver, number of linearly independent members of a Payload Set, or equivalently the number of linearly independent equations of the linear system. It is also known as "Degrees of Freedom". The system may be of "full rank" where decoding is possible or "partial rank" where only partial decoding is possible.
Seen Payload or Seen Symbol:
A Source Symbol is Seen when the receiver can compute a linear combination with this symbol and Source Symbols that are strictly more recent (i.e., with logically higher Encoding Symbol Identifiers). Otherwise, the Source Symbol is considered as "Unseen".
Generation or (IETF) Block:
With Block Codes, the set of Source Symbols of the input Flow(s) that are logically grouped into a Block, before doing encoding.
Generation Size, Code Dimension, or (IETF) Block Size:
With Block Codes, the number of Source Symbols, k, belonging to a Block.
Coding Matrix or Generator Matrix:
A matrix G that transforms the set of Input Symbols X into a set of Repair Symbols: Y = X * G. Defining a Generator Matrix is typical with Block Codes. The set of Input Symbols X can consist only of Source Symbols (e.g., with End-to-End Coding) or can consist of Source and Repair Symbols (e.g., with recoding in an intermediate node).
Coding Coefficient:
With Linear Coding, this is a coefficient in a certain Finite Field. This coefficient may be chosen in different ways: for instance, randomly, in a predefined table, or using a predefined algorithm plus a seed.
Coding Vector:
A set of Coding Coefficients used to generate a certain Repair Symbol through Linear Coding. The number of nonzero coefficients in the Coding Vector defines its density.
Finite Field, Galois Field, or Coding Field:
Finite Fields, used in Linear Codes, have the desired property of having all elements (except zero) invertible for the + and * operators, and all operations over any elements do not result in an overflow or underflow. Examples of Finite Fields are prime fields {0..p^m-1}, where p is prime. The most used fields use p=2 and are called binary extension fields {0..2^m-1}, where m often equals 1, 4, or 8 for practical reasons.
Finite Field size or Coding Field size:
The number of elements in a Finite Field. For example, the binary extension field {0..2^m-1} has size q=2^m.
Feedback:
Feedback information sent by a decoding node to a Coding Node (or from a receiver to a source in case of End-to-End Coding). The nature of information contained in a feedback packet varies, depending on the use case. It can provide reception and/or FEC decoding statistics, the list of available Source Packets received or decoded (acknowledgement), the list of lost Source Packets that should be retransmitted (negative acknowledgement), or a number of additional Repair Symbols needed to have a Full Rank Linear System.
符号化率（Code Rate）：
ブロック符号の場合、符号化率は、ソースシンボルの数kと、ソースシンボルと修復シンボルを合わせた数nとの比k/nです。スライディングウィンドウ符号では、符号化率は動的に変化する場合があるため、ある時間間隔にわたって同様に定義されます。定義により、符号化率は0 < 符号化率 <= 1を満たします。符号化率が1に近いことは、符号化の過程で生成された修復シンボルの数が少ないことを示し、逆もまた同様です。
符号化ウィンドウ（(En)coding Window）：
符号化の操作への入力として使用される、ソースシンボル（および再符号化の場合は修復シンボル）の集合。符号化ウィンドウが入力フロー上をスライドするにつれて、このシンボルの集合は通常、時間とともに変化します。
符号化ウィンドウサイズ（(En)coding Window Size）：
現在の符号化ウィンドウ内のソースシンボル（および再符号化の場合は修復シンボル）の数。このサイズは時間とともに変化する場合があります。
ペイロードセット（Payload Set）：
受信者で利用可能な（つまり、受信済み、または以前にデコードされた）、FECのデコードの操作の中で使用されるソースシンボルと修復シンボルの集合。
デコードウィンドウ（Decoding Window）：
受信者の現在の線形システムで考慮される、ソースシンボル（のみ）の集合。これらのソースシンボルが受信されたか、デコードされたか、失われたかには関係しません。デコードウィンドウは通常、伝送とデコードの進行につれて時間とともに変化し、コンテンツがマルチキャストまたはブロードキャストされるセッションでは、受信者ごとに異なる場合があります。
デコードウィンドウサイズ（Decoding Window Size）：
現在のデコードウィンドウ内のソースシンボル（のみ）の数。このサイズは時間とともに変化する場合があります。
ペイロードセットのランク（Rank of a Payload Set）、または線形システムのランク（Rank of the Linear System）：
受信者における、ペイロードセットのうち線形独立なメンバーの数、または同等に、線形システムのうち線形独立な方程式の数。これは「自由度（Degrees of Freedom）」とも呼ばれます。システムは、デコードが可能な「フルランク（full rank）」の場合と、部分的なデコードしかできない「部分ランク（partial rank）」の場合があります。
Seenペイロード（Seen Payload）、またはSeenシンボル（Seen Symbol）：
受信者が、あるソースシンボルと、厳密により新しい（つまり、論理的により大きい符号化シンボル識別子を持つ）ソースシンボルとの線形結合を計算できるとき、そのソースシンボルはSeenです。そうでない場合、そのソースシンボルは「Unseen」とみなされます。
世代（Generation）、または(IETF)ブロック（Block）：
ブロック符号において、符号化を行う前に論理的に1つのブロックにグループ化された、入力フローのソースシンボルの集合。
世代サイズ（Generation Size）、符号の次元（Code Dimension）、または(IETF)ブロックサイズ（Block Size）：
ブロック符号において、ブロックに属するソースシンボルの数k。
符号化行列（Coding Matrix）、または生成行列（Generator Matrix）：
入力シンボルの集合Xを修復シンボルの集合に変換する行列G：Y = X * G。生成行列を定義するのは、ブロック符号で典型的です。入力シンボルの集合Xは、ソースシンボルだけで構成される場合（たとえば、エンドツーエンド符号化の場合）もあれば、ソースシンボルと修復シンボルで構成される場合（たとえば、中間ノードで再符号化を行う場合）もあります。
符号化係数（Coding Coefficient）：
線形符号化において、ある有限体の係数。この係数は、さまざまな方法で選ぶことができます。たとえば、ランダムに選ぶ方法、あらかじめ定義された表から選ぶ方法、あらかじめ定義されたアルゴリズムとシードを使用する方法があります。
符号化ベクトル（Coding Vector）：
線形符号化によってある修復シンボルを生成するために使用される符号化係数の集合。符号化ベクトル内の0でない係数の数が、その密度を定義します。
有限体（Finite Field）、ガロア体（Galois Field）、または符号化体（Coding Field）：
線形符号で使用される有限体は、+と*の演算子について（0を除く）すべての元が可逆であり、かつ任意の元に対するすべての演算がオーバーフローやアンダーフローを起こさないという望ましい性質を持ちます。有限体の例としては、pを素数とする素体{0..p^m-1}があります。最もよく使われる体はp=2のもので、二元拡大体{0..2^m-1}と呼ばれます。実用上の理由から、mは1、4、または8であることが多いです。
有限体のサイズ（Finite Field size）、または符号化体のサイズ（Coding Field size）：
有限体の元の数。たとえば、二元拡大体{0..2^m-1}のサイズはq=2^mです。
フィードバック（Feedback）：
デコードを行うノードから符号化ノードへ（またはエンドツーエンド符号化の場合は受信者から送信元へ）送信されるフィードバック情報。フィードバックパケットに含まれる情報の性質は、ユースケースによって異なります。フィードバックは、受信やFECのデコードの統計情報、受信またはデコードされた利用可能なソースパケットの一覧（確認応答）、再送すべき失われたソースパケットの一覧（否定確認応答）、またはフルランクの線形システムを得るために必要な追加の修復シンボルの数を提供できます。

4.3. Coding in Practice

4.3. 実際の符号化

This section discusses practical aspects. Indeed, a practical solution must specify the exact manner in which encoding and decoding are performed but also detail all the peripheral aspects, for instance, how an encoder informs a decoder about the parameters used to generate a certain Repair Packet (signaling).

このセクションでは、実際的な側面について説明します。実際の解決策では、符号化とデコードを行う正確な方法を規定するだけでなく、周辺のあらゆる側面、たとえば、ある修復パケットの生成に使用したパラメーターをエンコーダーがデコーダーにどのように知らせるか（シグナリング）についても詳しく規定しなければなりません。

(IETF) FEC Scheme:
A specification that defines a particular FEC code as well as the additional protocol aspects required to use this FEC code. In particular, the FEC Scheme defines in-band (e.g., information contained in Source and Repair Packet header or trailers) and out-of-band (e.g., information contained in an SDP description) signaling needed to synchronize encoders and decoders.
Payload Index or (IETF) Encoding Symbol Identifier (ESI):
An identifier of a Source or Repair Symbol. With Block Coding, each symbol of a given block is identified by a unique ESI value. With Sliding Window Coding, a continuous Source Flow and a limited field size to hold the ESI, wrapping to zero is unavoidable and the same integer value will be reused several times.
(IETF) FEC Payload ID:
Information that identifies the contents of a packet with respect to the FEC Scheme. The FEC Payload ID of a packet containing Source Symbol(s) is usually different from that of a packet containing Repair Symbol(s). The FEC Payload ID typically contains at least an ESI.
Coding Vector and Encoding Window Signaling:
With Sliding Window Codes, the FEC Payload ID of a Repair Packet contains information needed and sufficient to identify the Coding Vector and Coding Window. Concerning the Coding Vector, this may consist of a full list of Coding Coefficients (that may or may not be compressed), or a piece of information (e.g., a seed) that can be used to generate the list of Coding Coefficients thanks to a predefined algorithm known by encoders and decoders (e.g., a Pseudorandom Number Generator, or PRNG) or an ESI that points to a given entry in a Generator Matrix in case of a Block Code. Concerning the Coding Window, this may consist of the full list of ESI of symbols in the Coding Window (that may or may not be compressed) or the ESI of the first Source Symbol along with their number (assuming there is no gap).
(IETF)FECスキーム（FEC Scheme）：
特定のFEC符号と、そのFEC符号を使用するために必要な追加のプロトコルの側面を定義する仕様。特に、FECスキームは、エンコーダーとデコーダーを同期させるために必要な、帯域内（たとえば、ソースパケットや修復パケットのヘッダーまたはトレーラーに含まれる情報）および帯域外（たとえば、SDP記述に含まれる情報）のシグナリングを定義します。
ペイロードインデックス（Payload Index）、または(IETF)符号化シンボル識別子（Encoding Symbol Identifier、ESI）：
ソースシンボルまたは修復シンボルの識別子。ブロック符号化では、あるブロックの各シンボルは一意のESI値によって識別されます。スライディングウィンドウ符号化では、ソースフローが連続しており、ESIを保持するフィールドのサイズが限られているため、ゼロに戻ることは避けられず、同じ整数値が何度も再利用されます。
(IETF)FECペイロードID（FEC Payload ID）：
FECスキームに関してパケットの内容を識別する情報。ソースシンボルを含むパケットのFECペイロードIDは、通常、修復シンボルを含むパケットのFECペイロードIDとは異なります。FECペイロードIDには通常、少なくともESIが含まれます。
符号化ベクトルと符号化ウィンドウのシグナリング（Coding Vector and Encoding Window Signaling）：
スライディングウィンドウ符号では、修復パケットのFECペイロードIDに、符号化ベクトルと符号化ウィンドウを識別するために必要かつ十分な情報が含まれます。符号化ベクトルについては、これは符号化係数の完全な一覧（圧縮される場合もされない場合もあります）であることもあれば、エンコーダーとデコーダーが知っているあらかじめ定義されたアルゴリズム（たとえば、疑似乱数生成器（Pseudorandom Number Generator、PRNG））によって符号化係数の一覧を生成するために使用できる情報（たとえば、シード）であることもあれば、ブロック符号の場合は生成行列内の特定のエントリーを指すESIであることもあります。符号化ウィンドウについては、これは符号化ウィンドウ内のシンボルのESIの完全な一覧（圧縮される場合もされない場合もあります）であることもあれば、（欠落がないと仮定して）最初のソースシンボルのESIとシンボルの数であることもあります。
