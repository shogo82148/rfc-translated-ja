RFC 9456

Updates to the TLS Transport Model for SNMP

RFC 9456

SNMPのためのTLSトランスポートモデルの更新

Abstract

概要

This document updates RFC 6353 ("Transport Layer Security (TLS) Transport Model for the Simple Network Management Protocol (SNMP)") to reflect changes necessary to support Transport Layer Security version 1.3 (TLS 1.3) and Datagram Transport Layer Security version 1.3 (DTLS 1.3), which are jointly known as "(D)TLS 1.3". This document is compatible with (D)TLS 1.2 and is intended to be compatible with future versions of SNMP and (D)TLS.

この文書は、RFC 6353（「Transport Layer Security (TLS) Transport Model for the Simple Network Management Protocol (SNMP)」）を更新し、 Transport Layer Securityバージョン1.3（TLS 1.3）とDatagram Transport Layer Securityバージョン1.3（DTLS 1.3）をサポートするために必要な変更を反映します。 これら2つを合わせて「(D)TLS 1.3」と呼びます。 この文書は(D)TLS 1.2と互換性があり、SNMPと(D)TLSの将来のバージョンとも互換性を持つことを意図しています。

This document updates the SNMP-TLS-TM-MIB as defined in RFC 6353.

この文書は、RFC 6353で定義されたSNMP-TLS-TM-MIBを更新します。

1. Introduction

1. はじめに

This document updates and clarifies how the rules of [RFC6353] apply when using Transport Layer Security (TLS) or Datagram Transport Layer Security (DTLS) versions later than 1.2. This document jointly refers to these two protocols as "(D)TLS". The update also emphasizes the requirement in [RFC8996] prohibiting the use of TLS versions prior to TLS 1.2 [RFC5246] when using SNMP. Although the text of this document specifically references SNMPv3 and (D)TLS 1.3, this document may be applicable to future versions of these protocols and is backwards compatible with (D)TLS 1.2.

この文書は、バージョン1.2より後のTransport Layer Security（TLS）またはDatagram Transport Layer Security（DTLS）を使う場合に、[RFC6353]の規則をどのように適用するかを更新し、明確にします。 この文書では、これら2つのプロトコルを合わせて「(D)TLS」と呼びます。 この更新では、SNMPを使う場合にTLS 1.2 [RFC5246]より前のTLSバージョンの使用を禁止する[RFC8996]の要件も強調しています。 この文書の本文では特にSNMPv3と(D)TLS 1.3に言及していますが、この文書はこれらのプロトコルの将来のバージョンにも適用できる可能性があり、(D)TLS 1.2とも後方互換性があります。

1.1. The Internet-Standard Management Framework

1.1. インターネット標準管理フレームワーク

For a detailed overview of the documents that describe the current Internet-Standard Management Framework, please refer to Section 7 of [RFC3410].

現在のインターネット標準管理フレームワーク（Internet-Standard Management Framework）を記述している文書の詳細な概要については、[RFC3410]のSection 7を参照してください。

Managed objects are accessed via a virtual information store, termed the Management Information Base or MIB. MIB objects are generally accessed through the Simple Network Management Protocol (SNMP). Objects in the MIB are defined using the mechanisms defined in the Structure of Management Information (SMI). This memo specifies a MIB module that is compliant to the SMIv2, which is described in RFCs 2578, 2579, and 2580 [STD58].

管理オブジェクトには、管理情報ベース（Management Information Base、MIB）と呼ばれる仮想的な情報ストアを介してアクセスします。 MIBオブジェクトには、一般にSimple Network Management Protocol（SNMP）を通じてアクセスします。 MIB内のオブジェクトは、管理情報構造（Structure of Management Information、SMI）で定義されたメカニズムを使って定義されます。 このメモでは、RFC 2578、2579、2580 [STD58]で記述されているSMIv2に準拠したMIBモジュールを規定します。

1.2. Conventions

1.2. 表記規則

Within this document, the terms "TLS", "DTLS", and "(D)TLS" apply to all versions of the indicated protocols. The term "SNMP" means "SNMPv3" unless a specific version number is indicated. Specific version numbers are used when the text needs to emphasize version numbers.

この文書では、「TLS」、「DTLS」、「(D)TLS」という用語は、示されたプロトコルのすべてのバージョンに適用されます。 「SNMP」という用語は、特定のバージョン番号が示されていない限り「SNMPv3」を意味します。 本文でバージョン番号を強調する必要がある場合には、特定のバージョン番号を使います。

For consistency with SNMP-related specifications, this document favors terminology as defined in [STD62], rather than favoring terminology that is consistent with non-SNMP specifications. This is consistent with the IESG decision to not require that the SNMP terminology be modified to match the usage of other non-SNMP specifications when SNMP was advanced to an Internet Standard. "Authentication" in this document typically refers to the English meaning of "serving to prove the authenticity of" the message, not data source authentication or peer identity authentication. The terms "manager" and "agent" are not used in this document because, in the architecture defined in RFC 3411 [STD62], all SNMP entities have the capability of acting as manager, agent, or both, depending on the SNMP application types supported in the implementation. Where distinction is necessary, the application names of command generator, command responder, notification originator, notification receiver, and proxy forwarder are used. See "An Architecture for Describing Simple Network Management Protocol (SNMP) Management Frameworks" (RFC 3411 [STD62]) for further information.

SNMP関連の仕様との一貫性を保つため、この文書では、SNMP以外の仕様と整合する用語よりも、[STD62]で定義された用語を優先して使います。 これは、SNMPがインターネット標準に昇格した際に、SNMP以外の仕様での用法に合わせてSNMPの用語を変更することを求めないとしたIESGの決定と整合しています。 この文書での「認証（Authentication）」は、通常、メッセージの「真正性を証明するのに役立つ」という英語の意味を指し、データ発信元認証やピアの身元の認証を指すものではありません。 RFC 3411 [STD62]で定義されたアーキテクチャーでは、すべてのSNMPエンティティーは、実装でサポートされているSNMPアプリケーションの種類に応じて、マネージャー、エージェント、またはその両方として動作する能力を持ちます。 そのため、この文書では「マネージャー」と「エージェント」という用語は使いません。 区別が必要な場合には、コマンドジェネレーター、コマンドレスポンダー、通知発信者、通知受信者、プロキシーフォワーダーというアプリケーション名を使います。 詳しくは、「An Architecture for Describing Simple Network Management Protocol (SNMP) Management Frameworks」（RFC 3411 [STD62]）を参照してください。

Throughout this document, the terms "client" and "server" are used to refer to the two ends of the TLS transport connection. The client actively opens the TLS connection, and the server passively listens for the incoming TLS connection. An SNMP entity MAY act as a TLS client, TLS server, or both, depending on the SNMP applications supported.

この文書全体を通じて、「クライアント」と「サーバー」という用語は、TLSトランスポートコネクションの2つの端を指すために使います。 クライアントはTLSコネクションを能動的に開き、サーバーは受信するTLSコネクションを受動的に待ち受けます。 SNMPエンティティーは、サポートするSNMPアプリケーションに応じて、TLSクライアント、TLSサーバー、またはその両方として動作してもよいです（MAY）。

Throughout this document, the term "session" is used to refer to a secure association between two instances of the TLS Transport Model (TLSTM) that permits the transmission of one or more SNMP messages within the lifetime of the session. The TLS protocol also has an internal notion of a session, and although these two concepts of a session are related, when the term "session" is used, this document is referring to the TLSTM's specific session and not directly to the TLS protocol's session.

この文書全体を通じて、「セッション」という用語は、TLSトランスポートモデル（TLS Transport Model、TLSTM）の2つのインスタンス間の安全な関連付けであって、セッションの有効期間内に1つ以上のSNMPメッセージの送信を可能にするものを指すために使います。 TLSプロトコルにも内部的なセッションの概念があり、これら2つのセッションの概念は関連しています。 しかし、「セッション」という用語を使う場合、この文書はTLSTM固有のセッションを指しており、TLSプロトコルのセッションを直接指しているわけではありません。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

2. Changes from RFC 6353

2. RFC 6353からの変更

This document updates [RFC6353]. The changes from [RFC6353] are defined in the following subsections.

この文書は[RFC6353]を更新します。 [RFC6353]からの変更は、以降のサブセクションで定義します。

2.1. TLSTM Fingerprint

2.1. TLSTMフィンガープリント

[RFC6353] defines the SnmpTLSFingerprint textual convention to include the one-octet TLS 1.2 hash algorithm identifier. This one-octet algorithm identifier is only applicable to (D)TLS protocol versions prior to 1.3. The TLS community does not plan to ever add additional values to the "TLS HashAlgorithm" registry [RFC5246], because some might incorrectly infer that using a new hash algorithm with TLS 1.2 would overcome the limitations of TLS 1.2. However, there is still a need within TLSTM to support new values as they are developed.

[RFC6353]は、SnmpTLSFingerprintテキスト表記法（textual convention）を、1オクテットのTLS 1.2ハッシュアルゴリズム識別子を含むものとして定義しています。 この1オクテットのアルゴリズム識別子は、1.3より前のバージョンの(D)TLSプロトコルにしか適用できません。 TLSコミュニティーは、「TLS HashAlgorithm」レジストリー [RFC5246]に今後値を追加する予定はありません。 新しいハッシュアルゴリズムをTLS 1.2で使えばTLS 1.2の限界を克服できると誤って推測する人がいるかもしれないためです。 しかし、TLSTMの中では、新しい値が開発されるのに応じてそれらをサポートする必要が依然としてあります。

This document updates the definition of SnmpTLSFingerprint to clarify that the one-octet algorithm identifier uses the values in the IANA "SNMP-TLSTM HashAlgorithms" registry; this registry is consistent with the IANA "TLS HashAlgorithm" registry for its initial values but can be extended as needed to support new hashing algorithms without implying that the new values can be used by TLS version 1.2. This change allows the reuse of the existing fingerprint textual convention and minimizes the impact to [RFC6353].

この文書は、SnmpTLSFingerprintの定義を更新し、1オクテットのアルゴリズム識別子がIANAの「SNMP-TLSTM HashAlgorithms」レジストリーの値を使うことを明確にします。 このレジストリーの初期値はIANAの「TLS HashAlgorithm」レジストリーと一致していますが、新しい値がTLSバージョン1.2で使えることを意味することなく、新しいハッシュアルゴリズムをサポートするために必要に応じて拡張できます。 この変更により、既存のフィンガープリントのテキスト表記法を再利用でき、[RFC6353]への影響を最小限に抑えられます。

A "Y" in the "Recommended" column (Table 1) indicates that the registered value has been recommended through a formal Standards Action [RFC8126]. Not all parameters defined in Standards Track documents are necessarily marked as "Recommended".

「Recommended」列（Table 1）の「Y」は、登録された値が正式なStandards Action [RFC8126]を通じて推奨されたことを示します。 標準化過程の文書で定義されたパラメーターのすべてが、必ずしも「Recommended」とマークされているわけではありません。

An "N" in the "Recommended" column does not necessarily mean that the value is flawed; rather, it indicates that the item either has not been through the IETF consensus process, has limited applicability, or is intended only for specific use cases.

2.2. Security Level

2.2. セキュリティーレベル

The architecture defined in RFC 3411 [STD62] recognizes three levels of security:

RFC 3411 [STD62]で定義されたアーキテクチャーは、次の3つのセキュリティーレベルを認識しています。

  • without authentication and without privacy (noAuthNoPriv)
  • with authentication but without privacy (authNoPriv)
  • with authentication and with privacy (authPriv)
  • 認証なし、プライバシーなし（noAuthNoPriv）
  • 認証あり、プライバシーなし（authNoPriv）
  • 認証あり、プライバシーあり（authPriv）

Cipher suites for (D)TLS 1.3 defined in [RFC8446] provide both authentication and privacy. Cipher suites defined in [RFC9150] for (D)TLS 1.3 provide only authentication, without any privacy protection. Implementations MAY choose to force (D)TLS 1.3 to only allow cipher suites that provide both authentication and privacy.

[RFC8446]で定義された(D)TLS 1.3の暗号スイートは、認証とプライバシーの両方を提供します。 [RFC9150]で定義された(D)TLS 1.3の暗号スイートは認証のみを提供し、プライバシー保護はまったく提供しません。 実装は、認証とプライバシーの両方を提供する暗号スイートのみを許可するように(D)TLS 1.3を強制することを選択してもよいです（MAY）。

2.3. (D)TLS Version

2.3. (D)TLSのバージョン

[RFC6353] states that TLSTM clients and servers MUST NOT request, offer, or use SSL 2.0. [RFC8996] prohibits the use of (D)TLS versions prior to version 1.2. TLSTM MUST only be used with (D)TLS versions 1.2 and later.

[RFC6353]は、TLSTMのクライアントとサーバーがSSL 2.0を要求、提示、または使用してはなりません（MUST NOT）と述べています。 [RFC8996]は、バージョン1.2より前の(D)TLSの使用を禁止しています。 TLSTMは、バージョン1.2以降の(D)TLSでのみ使用しなければなりません（MUST）。

3. Additional Rules for TLS 1.3

3. TLS 1.3のための追加規則

This document specifies additional rules and clarifications for the use of TLS 1.3. These rules may additionally apply to future versions of TLS.

この文書は、TLS 1.3を使用するための追加の規則と明確化を規定します。 これらの規則は、TLSの将来のバージョンにも追加で適用される可能性があります。

3.1. Zero Round-Trip Time Resumption (0-RTT)

3.1. ゼロラウンドトリップ時間再開（0-RTT）

TLS 1.3 implementations for SNMP MUST NOT enable the 0-RTT mode of session resumption (either sending or accepting) and MUST NOT automatically resend 0-RTT data if it is rejected by the server. 0-RTT is disallowed because there are no "safe" SNMP messages that, if replayed, will be guaranteed to cause no harm at the server side: all incoming notifications or command responses are meant to be acted upon only once. See Section 5 ("Security Considerations") for further details.

SNMPのためのTLS 1.3実装は、セッション再開の0-RTTモードを（送信と受け入れのいずれについても）有効にしてはなりません（MUST NOT）。 また、0-RTTデータがサーバーによって拒否された場合に、それを自動的に再送してはなりません（MUST NOT）。 0-RTTが禁止されるのは、リプレイされてもサーバー側で害を引き起こさないことが保証される「安全な」SNMPメッセージが存在しないためです。 受信するすべての通知やコマンドレスポンスは、一度だけ処理されることを意図しています。 詳しくはSection 5（「Security Considerations」）を参照してください。

TLSTM clients and servers MUST NOT request, offer, or use the 0-RTT mode of TLS 1.3. [RFC8446] removed the renegotiation supported in TLS 1.2 [RFC5246]; for session resumption, it introduced a zero-RTT (0-RTT) mode, saving a round trip at connection setup at the cost of increased risk of replay attacks (it is possible for servers to guard against this attack by keeping track of all the messages received). [RFC8446] requires that a profile be written for any application that wants to use 0-RTT, specifying which messages are "safe to use" with this mode. Within SNMP, there are no messages that are "safe to use" with this mode.

TLSTMのクライアントとサーバーは、TLS 1.3の0-RTTモードを要求、提示、または使用してはなりません（MUST NOT）。 [RFC8446]は、TLS 1.2 [RFC5246]でサポートされていた再ネゴシエーションを削除しました。 セッション再開のために、TLS 1.3はゼロRTT（0-RTT）モードを導入しました。 このモードは、リプレイ攻撃のリスクが増すことと引き換えに、コネクション確立時のラウンドトリップを1回節約します（受信したすべてのメッセージを記録しておくことで、サーバーがこの攻撃を防ぐことは可能です）。 [RFC8446]は、0-RTTを使いたいアプリケーションに対して、どのメッセージがこのモードで「安全に使える」かを規定するプロファイルを書くことを求めています。 SNMPには、このモードで「安全に使える」メッセージはありません。

Renegotiation of sessions is not supported, as it is not supported by TLS 1.3. If a future version of TLS supports renegotiation, this RFC should be updated to indicate whether there are any additional requirements related to its use.

TLS 1.3がセッションの再ネゴシエーションをサポートしていないため、再ネゴシエーションはサポートされません。 TLSの将来のバージョンが再ネゴシエーションをサポートする場合は、その使用に関連する追加の要件があるかどうかを示すために、このRFCを更新すべきです。

3.2. TLS Cipher Suites, Extensions, and Protocol Invariants

3.2. TLSの暗号スイート、拡張、プロトコル不変条件

Section 9 of [RFC8446] requires that, in the absence of application profiles, certain cipher suites, TLS extensions, and TLS protocol invariants be mandatory to implement. This document does not specify an application profile; hence, all the compliance requirements in [RFC8446] apply.

[RFC8446]のSection 9は、アプリケーションプロファイルがない場合に、特定の暗号スイート、TLS拡張、TLSプロトコル不変条件を実装必須とすることを求めています。 この文書はアプリケーションプロファイルを規定しません。 したがって、[RFC8446]の準拠要件がすべて適用されます。

SnmpTLSFingerprint ::= TEXTUAL-CONVENTION
    DISPLAY-HINT "1x:1x"
    STATUS       current
    DESCRIPTION
       "A fingerprint value that can be used to uniquely reference
        other data of potentially arbitrary length.

        An SnmpTLSFingerprint value is composed of a one-octet
        hashing algorithm identifier followed by the fingerprint
        value.  The one-octet identifier value encoded is taken
        from the IANA 'SNMP-TLSTM HashAlgorithms' registry.  The
        remaining octets of the SnmpTLSFingerprint value are
        filled using the results of the hashing algorithm.

        Historically, the one-octet hashing algorithm identifier
        was based on the IANA 'TLS HashAlgorithm' registry
        (RFC 5246); however, this registry is no longer in use for
        TLS 1.3 and above and is not expected to have any new
        registrations added to it.  To allow the fingerprint
        algorithm to support additional hashing algorithms that
        might be used by later versions of (D)TLS, the octet value
        encoded is now taken from the IANA
        'SNMP-TLSTM HashAlgorithms' registry.  The initial values
        within this registry are identical to the values in the
        'TLS HashAlgorithm' registry but can be extended to
        support new hashing algorithms as needed.

        This textual convention allows for a zero-length (blank)
        SnmpTLSFingerprint value for use in tables where the
        fingerprint value MAY be optional.  MIB definitions or

snmpTlstmCertToTSNTable OBJECT-TYPE
    SYNTAX      SEQUENCE OF SnmpTlstmCertToTSNEntry
    MAX-ACCESS  not-accessible
    STATUS      current
    DESCRIPTION
       "This table is used by a (D)TLS server to map the (D)TLS
        client's presented X.509 certificate to a tmSecurityName.

        On an incoming (D)TLS/SNMP connection, the client's
        presented certificate either MUST be validated based on an
        established trust anchor or MUST directly match a
        fingerprint in this table.  This table does not provide
        any mechanisms for configuring the trust anchors; the
        transfer of any needed trusted certificates for path
        validation is expected to occur through an out-of-band
        transfer.

        Once the certificate has been found acceptable (either via
        path validation or by directly matching a fingerprint in
        this table), this table is consulted to determine the
        appropriate tmSecurityName to identify with the remote
        connection.  This is done by considering each active row
        from this table in prioritized order according to its
        snmpTlstmCertToTSNID value.  Each row's
        snmpTlstmCertToTSNFingerprint value determines whether the
        row is a match for the incoming connection:

           1) If the row's snmpTlstmCertToTSNFingerprint value
              identifies the presented certificate, then consider
              the row as a successful match.

           2) If the row's snmpTlstmCertToTSNFingerprint value
              identifies a locally held copy of a trusted CA
              certificate and that CA certificate was used to
              validate the path to the presented certificate, then
              consider the row as a successful match.

        Once a matching row has been found, the
        snmpTlstmCertToTSNMapType value can be used to determine
        how the tmSecurityName to associate with the session
        should be determined.  See the 'snmpTlstmCertToTSNMapType'
        column's DESCRIPTION clause for details on determining the
        tmSecurityName value.  If it is impossible to determine a
        tmSecurityName from the row's data combined with the data
        presented in the certificate, then additional rows MUST be
        searched to look for another potential match.  If a
        resulting tmSecurityName mapped from a given row is not
        compatible with the needed requirements of a
        tmSecurityName (e.g., the VACM imposes a 32-octet-maximum
        length and the certificate-derived securityName could be
        longer), then it MUST be considered an invalid match and
        additional rows MUST be searched to look for another
        potential match.

        If no matching and valid row can be found, the connection
        MUST be closed and SNMP messages MUST NOT be accepted over
        it.

        Missing values of snmpTlstmCertToTSNID are acceptable, and
        implementations SHOULD continue to the
        next-highest-numbered row.  It is RECOMMENDED that
        administrators skip index values to leave room for the
        insertion of future rows (for example, use values of 10
        and 20 when creating initial rows).

        Users are encouraged to make use of certificates with
        subjectAltName fields that can be used as tmSecurityNames.
        This allows all child certificates of a single root CA
        certificate to include a subjectAltName that maps directly
        to a tmSecurityName via a 1:1 transformation.  However,
        this table is flexible, to allow for situations where
        existing deployed certificate infrastructures do not provide
        adequate subjectAltName values for use as tmSecurityNames.
        Certificates MAY also be mapped to tmSecurityNames using
        the CommonName portion of the Subject field.  However, the
        usage of the CommonName field is deprecated, and thus this
        usage is NOT RECOMMENDED.  Direct mapping from each
        individual certificate fingerprint to a tmSecurityName is
        also possible but requires one entry in the table per
        tmSecurityName and requires more management operations to
        completely configure a device."

snmpTlstmAddrTable OBJECT-TYPE
    SYNTAX      SEQUENCE OF SnmpTlstmAddrEntry
    MAX-ACCESS  not-accessible
    STATUS      current
    DESCRIPTION
       "This table is used by a (D)TLS client when a (D)TLS
        connection is being set up using an entry in the
        SNMP-TARGET-MIB.  It extends the SNMP-TARGET-MIB's
        snmpTargetAddrTable so that the client can verify that the
        correct server has been reached.  This verification can
        use either 1) a certificate fingerprint or 2) an
        identity authenticated via certification path validation.

        If there is an active row in this table corresponding to
        the entry in the SNMP-TARGET-MIB that was used to
        establish the connection and the row's
        'snmpTlstmAddrServerFingerprint' column has a non-empty
        value, then the server's presented certificate is compared
        with the snmpTlstmAddrServerFingerprint value (and the
        'snmpTlstmAddrServerIdentity' column is ignored).  If the
        fingerprint matches, the verification has succeeded.  If
        the fingerprint does not match, then the connection MUST
        be closed.

        If the server's presented certificate has passed
        certification path validation (RFC 5280) to a configured
        trust anchor and an active row exists with a zero-length
        snmpTlstmAddrServerFingerprint value, then the
        'snmpTlstmAddrServerIdentity' column contains the expected
        host name.  This expected host name is then compared
        against the server's certificate as follows:

           - Implementations MUST support matching the expected
             host name against a dNSName in the subjectAltName
             extension field and MAY support checking the name
             against the CommonName portion of the subject
             distinguished name.

           - The '*' (ASCII 0x2A) wildcard character is allowed in
             the dNSName of the subjectAltName extension (and in
             CommonName, if used to store the host name), but
             only as the leftmost (least significant) DNS label
             in that value.  This wildcard matches any leftmost
             DNS label in the server name.  That is, the subject
             *.example.com matches the server names a.example.com
             and b.example.com but does not match example.com or
             a.b.example.com.  Implementations MUST support
             wildcards in certificates as specified above but MAY
             provide a configuration option to disable them.

           - If the locally configured name is an
             internationalized domain name, conforming
             implementations MUST convert it to the ASCII
             Compatible Encoding (ACE) format for performing
             comparisons, as specified in Section 7 of RFC 5280.

        If the expected host name fails these conditions, then the
        connection MUST be closed.

        If there is no row in this table corresponding to the
        entry in the SNMP-TARGET-MIB and the server can be
        authorized by another, implementation-dependent means,
        then the connection MAY still proceed."

    DISPLAY-HINT "1x:1x"
    STATUS       current
    DESCRIPTION
       "A fingerprint value that can be used to uniquely reference
        other data of potentially arbitrary length.

        An SnmpTLSFingerprint value is composed of a one-octet
        hashing algorithm identifier followed by the fingerprint
        value.  The one-octet identifier value encoded is taken
        from the IANA 'SNMP-TLSTM HashAlgorithms' registry.  The
        remaining octets of the SnmpTLSFingerprint value are
        filled using the results of the hashing algorithm.

        Historically, the one-octet hashing algorithm identifier
        was based on the IANA 'TLS HashAlgorithm' registry
        (RFC 5246); however, this registry is no longer in use for
        TLS 1.3 and above and is not expected to have any new
        registrations added to it.  To allow the fingerprint
        algorithm to support additional hashing algorithms that
        might be used by later versions of (D)TLS, the octet value
        encoded is now taken from the IANA
        'SNMP-TLSTM HashAlgorithms' registry.  The initial values
        within this registry are identical to the values in the
        'TLS HashAlgorithm' registry but can be extended to
        support new hashing algorithms as needed.

        This textual convention allows for a zero-length (blank)
        SnmpTLSFingerprint value for use in tables where the
        fingerprint value MAY be optional.  MIB definitions or
        implementations MAY refuse to accept a zero-length value
        as appropriate."

snmpTlstmCertToTSNTable OBJECT-TYPE
    SYNTAX      SEQUENCE OF SnmpTlstmCertToTSNEntry
    MAX-ACCESS  not-accessible
    STATUS      current
    DESCRIPTION
       "This table is used by a (D)TLS server to map the (D)TLS
        client's presented X.509 certificate to a tmSecurityName.

        On an incoming (D)TLS/SNMP connection, the client's
        presented certificate either MUST be validated based on an
        established trust anchor or MUST directly match a
        fingerprint in this table.  This table does not provide
        any mechanisms for configuring the trust anchors; the
        transfer of any needed trusted certificates for path
        validation is expected to occur through an out-of-band
        transfer.

        Once the certificate has been found acceptable (either via
        path validation or by directly matching a fingerprint in
        this table), this table is consulted to determine the
        appropriate tmSecurityName to identify with the remote
        connection.  This is done by considering each active row
        from this table in prioritized order according to its
        snmpTlstmCertToTSNID value.  Each row's
        snmpTlstmCertToTSNFingerprint value determines whether the
        row is a match for the incoming connection:

           1) If the row's snmpTlstmCertToTSNFingerprint value
              identifies the presented certificate, then consider
              the row as a successful match.

           2) If the row's snmpTlstmCertToTSNFingerprint value
              identifies a locally held copy of a trusted CA
              certificate and that CA certificate was used to
              validate the path to the presented certificate, then
              consider the row as a successful match.

        Once a matching row has been found, the
        snmpTlstmCertToTSNMapType value can be used to determine
        how the tmSecurityName to associate with the session
        should be determined.  See the 'snmpTlstmCertToTSNMapType'
        column's DESCRIPTION clause for details on determining the
        tmSecurityName value.  If it is impossible to determine a
        tmSecurityName from the row's data combined with the data
        presented in the certificate, then additional rows MUST be
        searched to look for another potential match.  If a
        resulting tmSecurityName mapped from a given row is not
        compatible with the needed requirements of a
        tmSecurityName (e.g., the VACM imposes a 32-octet-maximum
        length and the certificate-derived securityName could be
        longer), then it MUST be considered an invalid match and
        additional rows MUST be searched to look for another
        potential match.

        MUST be closed and SNMP messages MUST NOT be accepted over
        it.

        Missing values of snmpTlstmCertToTSNID are acceptable, and
        implementations SHOULD continue to the
        next-highest-numbered row.  It is RECOMMENDED that
        administrators skip index values to leave room for the
        insertion of future rows (for example, use values of 10
        and 20 when creating initial rows).

        Users are encouraged to make use of certificates with
        subjectAltName fields that can be used as tmSecurityNames.
        This allows all child certificates of a single root CA
        certificate to include a subjectAltName that maps directly
        to a tmSecurityName via a 1:1 transformation.  However,
        this table is flexible, to allow for situations where
        existing deployed certificate infrastructures do not provide
        adequate subjectAltName values for use as tmSecurityNames.
        Certificates MAY also be mapped to tmSecurityNames using
        the CommonName portion of the Subject field.  However, the
        usage of the CommonName field is deprecated, and thus this
        usage is NOT RECOMMENDED.  Direct mapping from each
        individual certificate fingerprint to a tmSecurityName is
        also possible but requires one entry in the table per
        tmSecurityName and requires more management operations to
        completely configure a device."

5. Security Considerations

5. セキュリティーに関する考慮事項

This document updates a transport model that permits SNMP to utilize (D)TLS security services. The security threats and how the TLSTM mitigates these threats are covered throughout this document and in [RFC6353]. Security considerations for TLS are described in Section 10 and Appendix E of TLS 1.3 [RFC8446]. Security considerations for DTLS are described in Section 11 of DTLS 1.3 [RFC9147].

この文書は、SNMPが(D)TLSのセキュリティーサービスを利用できるようにするトランスポートモデルを更新します。 セキュリティー上の脅威と、TLSTMがそれらの脅威をどのように緩和するかについては、この文書全体と[RFC6353]で扱っています。 TLSのセキュリティーに関する考慮事項は、TLS 1.3 [RFC8446]のセクション10と付録Eに記述されています。 DTLSのセキュリティーに関する考慮事項は、DTLS 1.3 [RFC9147]のセクション11に記述されています。

Implementations should consider the latest recommendations on the use of (DTLS), such as those documented in [RFC9325].

実装は、[RFC9325]に記載されているものなど、(D)TLSの使用に関する最新の推奨事項を考慮すべきです。

SNMP versions prior to SNMPv3 did not include adequate security. Even if the network itself is secure (for example, by using IPsec), there is no control as to who on the secure network is allowed to access and GET/SET (read/change/create/delete) the objects in this MIB module.

SNMPv3より前のSNMPバージョンには、十分なセキュリティーが含まれていませんでした。 ネットワーク自体が（たとえばIPsecを使って）安全であったとしても、安全なネットワーク上の誰がこのMIBモジュールのオブジェクトにアクセスしてGET/SET（読み取り、変更、作成、削除）できるかについての制御はありません。

It is RECOMMENDED that only SNMPv3 messages using the Transport Security Model (TSM) or another secure-transport-aware security model be sent over the TLSTM transport.

TLSTMトランスポート上では、トランスポートセキュリティーモデル（Transport Security Model、TSM）またはその他のセキュアトランスポートを認識するセキュリティーモデルを使うSNMPv3メッセージのみを送信することが推奨されます（RECOMMENDED）。

6. IANA Considerations

6. IANAに関する考慮事項

IANA has created a new registry called "SNMP-TLSTM HashAlgorithms" within the "Structure of Management Information (SMI) Numbers (MIB Module Registrations)" group. The description of this registry is "iso.org.dod.internet.mgmt.mib-2.snmpTlstmMIB.snmpTlstmHashAlgorithms (1.3.6.1.2.1.198.4)".

IANAは、「Structure of Management Information (SMI) Numbers (MIB Module Registrations)」グループ内に「SNMP-TLSTM HashAlgorithms」という新しいレジストリーを作成しました。 このレジストリーの説明は「iso.org.dod.internet.mgmt.mib-2.snmpTlstmMIB.snmpTlstmHashAlgorithms (1.3.6.1.2.1.198.4)」です。

The registry has the following fields: Value, Description, Recommended, and References. The range of values is zero to 255, with initial assignments shown in Section 2.1. The "Recommended" column indicates "Y" for hashing algorithms that are Standards Track and are deemed to be acceptable for widely applicable current use and "N" for hashing algorithms that reflect meanings that are not recommended (e.g., they do not provide sufficient security for modern systems, they are not Standards Track, and they have limited applicability). A blank field indicates that no recommendation is made (e.g., because the value is unassigned or left for private use).

このレジストリーには、Value、Description、Recommended、Referencesというフィールドがあります。 値の範囲は0から255で、初期の割り当てはSection 2.1に示しています。 「Recommended」列は、標準化過程にあり、広く適用可能な現在の用途に受け入れられると見なされるハッシュアルゴリズムには「Y」を示します。 推奨されない意味を反映するハッシュアルゴリズム（たとえば、現代のシステムに対して十分なセキュリティーを提供しない、標準化過程ではない、適用範囲が限られている、など）には「N」を示します。 空欄は、推奨がなされていないことを示します（たとえば、値が未割り当てであるか、プライベート使用のために残されているため）。

This registry is expected to be updated infrequently; as such, its values are limited to one octet.

このレジストリーが更新される頻度は低いと予想されます。 そのため、その値は1オクテットに制限されています。

The policy for updates to the "SNMP-TLSTM HashAlgorithms" registry is Expert Review [RFC8126]. Registry requests should be sent to the <mailto:snmp-tlstm-reg-review@ietf.org> mailing list. Registration requests sent to the mailing list for review SHOULD use an appropriate subject (e.g., 'Request to register value in "SNMP-TLSTM HashAlgorithms" registry'). In addition, designated experts should consult with the <mailto:tls-reg-review@ietf.org> mailing list to make sure that any new hash algorithms are considered for inclusion in this registry.

「SNMP-TLSTM HashAlgorithms」レジストリーの更新のポリシーはExpert Review [RFC8126]です。 レジストリーのリクエストは<mailto:snmp-tlstm-reg-review@ietf.org>メーリングリストに送るべきです。 レビューのためにメーリングリストに送られる登録リクエストは、適切な件名（たとえば「Request to register value in "SNMP-TLSTM HashAlgorithms" registry」）を使うべきです（SHOULD）。 さらに、指定専門家は、新しいハッシュアルゴリズムがこのレジストリーに含めることを検討されるよう、<mailto:tls-reg-review@ietf.org>メーリングリストと協議すべきです。

Designated experts SHOULD ascertain the existence of suitable documentation that defines a hash algorithm and SHOULD also verify that the request does not conflict with or duplicate other entries in the registry. The experts should also provide a recommendation as to how the "Recommended" column of the registry should be updated. Only publicly available specifications that represent current industry- accepted practices should receive an assignment of "Y" in the "Recommended" column; all other specific assignments in the registry should receive an assignment of "N". Assignments that are nonspecific (e.g., reserved values) SHOULD NOT receive an assigned value for the "Recommended" column.

指定専門家は、ハッシュアルゴリズムを定義する適切な文書が存在することを確認すべきです（SHOULD）。 また、そのリクエストがレジストリー内の他のエントリーと競合したり重複したりしていないことも検証すべきです（SHOULD）。 専門家は、レジストリーの「Recommended」列をどのように更新すべきかについての推奨も提供すべきです。 現在の業界で受け入れられている慣行を表す、公開されている仕様のみが「Recommended」列に「Y」の割り当てを受けるべきです。 レジストリー内のその他の特定の割り当てはすべて「N」の割り当てを受けるべきです。 特定のものではない割り当て（たとえば予約済みの値）は、「Recommended」列に値の割り当てを受けるべきではありません（SHOULD NOT）。

Within the three-week review period, the designated experts will either approve or deny the registration request, communicating this decision to the review list and IANA. Denials SHOULD include an explanation and, if applicable, suggestions as to how to make the request successful. Registration requests that are undetermined for a period longer than three weeks can be brought to the IESG's attention (using the <mailto:iesg@ietf.org> mailing list) for resolution.

指定専門家は、3週間のレビュー期間内に登録リクエストを承認または拒否し、その決定をレビューリストとIANAに伝えます。 拒否する場合は、説明と、該当する場合はリクエストを成功させる方法についての提案を含めるべきです（SHOULD）。 3週間より長い期間決定されない登録リクエストは、解決のためにIESGに注意を喚起できます（<mailto:iesg@ietf.org>メーリングリストを使います）。

IANA MUST only accept registry updates from the designated experts and SHOULD direct all requests for registration to the review mailing list. While future additions to the "TLS HashAlgorithm" registry (i.e., the registry from which the "SNMP-TLSTM HashAlgorithms" registry was spawned) are not expected, any future additions to the "TLS HashAlgorithm" registry MUST be consistent with the values assigned in the "SNMP-TLSTM HashAlgorithms" registry.

IANAは、指定専門家からのレジストリー更新のみを受け入れなければなりません（MUST）。 また、すべての登録リクエストをレビューメーリングリストに回すべきです（SHOULD）。 「TLS HashAlgorithm」レジストリー（つまり、「SNMP-TLSTM HashAlgorithms」レジストリーの派生元のレジストリー）への今後の追加は予想されていませんが、「TLS HashAlgorithm」レジストリーへの今後の追加は、「SNMP-TLSTM HashAlgorithms」レジストリーで割り当てられた値と整合していなければなりません（MUST）。

It is suggested that multiple designated experts be appointed who are able to represent the perspectives of different applications using this specification, in order to enable broadly informed reviews of registration decisions. In cases where a registration decision could be perceived as creating a conflict of interest for a particular expert, that expert SHOULD defer to the judgment of the other experts.

登録の決定について幅広い情報に基づくレビューを可能にするため、この仕様を使うさまざまなアプリケーションの観点を代表できる複数の指定専門家を任命することが提案されています。 登録の決定が特定の専門家にとって利益相反を生むと受け取られうる場合には、その専門家は他の専門家の判断に従うべきです（SHOULD）。
