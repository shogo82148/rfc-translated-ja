RFC 269

Some Experience with File Transfer

RFC 269

ファイル転送に関するいくつかの経験

Abstract

概要

At UCLA-NMC we have recently completed implementation of a program which utilizes UCSB's storage capability via their Simple Minded File System (See RFC #122 by Jim White for a description of SMFS). The use of the program is detailed in Appendix A.

UCLA-NMCでは最近、UCSBのSimple Minded File System（SMFSの説明については、Jim WhiteによるRFC #122を参照してください）を介してUCSBの記憶領域を利用するプログラムの実装を完了しました。このプログラムの使い方は付録Aで詳しく説明します。

We learned a number of things in the implementation effort and subsequent usage. We think a number of these apply towards the development of a net- word-wide File Transfer Protocol, and we hope to stimulate further dis- cussion of these issues. We discovered some things in the UCSB protocol that we would like to see included in the network-wide protocol, and we see some things that are in the currently proposed net protocol and are unfortunately absent from the UCSB protocol.

私たちは、実装作業とその後の利用を通じて多くのことを学びました。そのうちのいくつかは、ネットワーク全体のファイル転送プロトコルの開発に当てはまると考えており、これらの問題についてさらなる議論が促されることを願っています。UCSBのプロトコルには、ネットワーク全体のプロトコルにも取り入れてほしいと思うものがいくつか見つかりました。また、現在提案されているネットワークのプロトコルにはあるものの、残念ながらUCSBのプロトコルにはないものもいくつかあります。

In the first category, is the UCSB file retrieval procedure. The user specifies among other things, a bit count of the number of bits to be retrieved in the current request.

前者に当てはまるのが、UCSBのファイル取得手順です。ユーザーは、特に、現在の要求で取得するビット数を表すビットカウントを指定します。

Successive RTF commands yield successive pieces of the file. Portions of the file can be spaced over by use of the SPF command. We think that the ability of the user to specify the size of the "chunks" of the file he is about to receive, along with the ability to access any part of the file without having to get the entire file, is definitely an advantage. It makes the user programs easier to write since the problem of parsing the input stream virtually disappears, as the user program knows exactly what to expect at all times. In addition, the one request, one response nature of the protocol avoids the problem of sending a request and then receiving pieces of data of unpredictable size at unknown intervals. The response to each RTF gives the comforting knowledge that "they're still listening". This leads us to believe that there is much to be gained by the adoption of a one request, one response type of protocol. We might point out that for any significant file transfer, this does not seriously cut down on the overall data transfer rate, since a "defaulting" type of approach, as SMFS uses can be used to keep the request messages very small. We also have found the mandatory password scheme of UCSB quite easily used, and any server site, (i.e. a site specifically advertising file storage) can reasonably be expected, in our opinion, to require passwords (see also RFC #238 by R. Braden).

RTFコマンドを続けて発行すると、ファイルの続きの部分が順に得られます。SPFコマンドを使えば、ファイルの一部を読み飛ばすことができます。これから受け取るファイルの「かたまり（chunk）」のサイズをユーザーが指定できることと、ファイル全体を取得しなくてもファイルの任意の部分にアクセスできることは、明らかに利点であると考えています。ユーザープログラムは常に何が来るかを正確に把握しているので、入力ストリームを解析する問題が事実上なくなり、ユーザープログラムを書きやすくなります。さらに、このプロトコルは1つの要求に1つの応答を返す性質を持つため、要求を送信した後に、予測できないサイズのデータ片を不明な間隔で受信するという問題を避けられます。各RTFへの応答によって、「相手はまだ聞いている」と安心できます。このことから、1要求1応答型のプロトコルを採用することで得られるものは大きいと考えています。また、SMFSが使用しているような「デフォルト値を用いる」方式を使えば要求メッセージを非常に小さく保てるので、相当な量のファイル転送であっても、全体のデータ転送速度が大きく低下することはないことも指摘しておきます。さらに、UCSBのパスワード必須の方式は非常に使いやすいことがわかりました。私たちの意見では、どのサーバーサイト（つまり、ファイルの格納を特に宣伝しているサイト）でも、パスワードを要求するのが当然であると考えられます（R. BradenによるRFC #238も参照してください）。

Almost immediately after starting to use SMFS we found a serious lack in one area. There is no way for a user to ask "what files do I have there?" As a matter of fact, the author suspects that there are already several files there which he has "forgotten" about! It is reasonable, perhaps even necessary, for any server to supply a nicely formatted character string describing the files stored there for this password, or user, or whatever division is used. The listing should also contain other pertinent information, such as date created, size etc.

SMFSを使い始めてほとんどすぐに、ある部分に重大な欠落があることに気づきました。ユーザーが「そこにはどのファイルがあるのか？」と問い合わせる方法がないのです。実のところ、著者は、自分が「忘れてしまった」ファイルがすでにいくつかそこにあるのではないかと疑っています！どのサーバーも、このパスワード、ユーザー、あるいはどのような区分であれ、それに対して格納されているファイルを説明する、きれいに整形された文字列を提供するのが妥当であり、おそらく必要でさえあります。その一覧には、作成日やサイズなど、その他の関連情報も含めるべきです。

In the meantime, UCSB is providing the SEX system with valuable "out-of-line on-line" storage, and we look forward to the development of a widely accepted file transfer protocol, implemented on a large number of server sites, hopefully equipped with low cost bulk storage.

当面の間、UCSBはSEXシステムに価値ある「回線外のオンライン（out-of-line on-line）」記憶領域を提供しています。私たちは、広く受け入れられるファイル転送プロトコルが開発され、願わくは低コストの大容量記憶装置を備えた多数のサーバーサイトに実装されることを期待しています。

Appendix A. FXFER

付録A. FXFER

SEX Notebook, Section 23.29, 3 December 71

SEX Notebook、セクション23.29、1971年12月3日

FXFER is a re-entrant program written in Symbol which is used to send a receive file from UCSB, using their Simple Minded File System. For the description of the Network interface to SMFS, see RFC #122 by Jim White.

FXFERは、Symbolで書かれた再入可能なプログラムで、UCSBのSimple Minded File Systemを使って、UCSBとの間でファイルを送受信するために使います。SMFSへのネットワークインターフェイスの説明については、Jim WhiteによるRFC #122を参照してください。

Files are stored there in a paged format identical to the paged format that the tape process uses: <header><data page><data page>... Thus a file which Master lists as having n pages will take 2048 n bytes of storage at UCSB. The user's sign-on initials are used as both the access and modification passwords, so that if a file is sent under on user's sign-on, they can only be retrieved or deleted by him.

ファイルは、テーププロセスが使用するページ形式と同一のページ形式でそこに格納されます: <header><data page><data page>... したがって、Masterがnページあると表示するファイルは、UCSBで2048 nバイトの記憶領域を占めます。ユーザーのサインオンのイニシャルが、アクセス用と変更用の両方のパスワードとして使われます。そのため、あるユーザーのサインオンでファイルが送信された場合、そのファイルを取得したり削除したりできるのはそのユーザーだけです。

Commands

コマンド

PA
Increments "print All" counter. Different settings of this counter yield different levels of program trace output on the console.
NP
No print. This sets the "Print All" counter to zero.
DF FOO
This deletes the file "FOO" located at UCSB.
PF FOO
This sends the file "FOO", pointed to by the user's root directory, to UCSB. Only read access is needed to "FOO".
GF FOO
The file "FOO" located at UCSB is retrieved and put in the user's root (with write access). Note that it must have been sent by the user to have the right password.
RN FOO BAR
Rename the file "FOO" at UCSB to "BAR". The same password restrictions as with PF and GF apply. (Not yet implemented)
ST
Status. Tells what program is doing and how much its done.
X
Exit Program.
PA
「print All」カウンターを増やします。このカウンターの設定値によって、コンソールに出力されるプログラムのトレースのレベルが変わります。
NP
印字なし（No print）。「Print All」カウンターを0に設定します。
DF FOO
UCSBにあるファイル「FOO」を削除します。
PF FOO
ユーザーのルートディレクトリーが指すファイル「FOO」をUCSBに送信します。「FOO」には読み取りアクセス権だけが必要です。
GF FOO
UCSBにあるファイル「FOO」を取得し、（書き込みアクセス権付きで）ユーザーのルートに置きます。正しいパスワードを持つためには、そのファイルがそのユーザーによって送信されたものでなければならないことに注意してください。
RN FOO BAR
UCSBにあるファイル「FOO」の名前を「BAR」に変更します。PFやGFと同じパスワードの制限が適用されます。（未実装）
ST
状態（Status）。プログラムが何をしていて、どこまで進んだかを示します。
X
プログラムを終了します。

If the system and/or UCSB is particularly slow, then UCSBFIL may type a time-out message. At this point the user has the option of continuing, or exiting the program. The message is self-explanatory, as are most of the program's messages.

システムとUCSBのいずれかまたは両方が特に遅い場合、UCSBFILはタイムアウトメッセージを出力することがあります。この時点で、ユーザーは続行するかプログラムを終了するかを選べます。このメッセージは、プログラムのほとんどのメッセージと同様に、説明を読まなくても意味がわかるものです。
