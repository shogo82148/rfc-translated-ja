RTP Payload for Society of Motion Picture and Television Engineers (SMPTE) ST 291-1 Ancillary Data

RFC 8331

米国映画テレビ技術者協会（SMPTE）ST 291-1補助データのためのRTPペイロード

Abstract

概要

This memo describes a Real-time Transport Protocol (RTP) payload format for the Society of Motion Picture and Television Engineers (SMPTE) ancillary space (ANC) data, as defined by SMPTE ST 291-1. SMPTE ANC data is generally used along with professional video formats to carry a range of ancillary data types, including time code, Closed Captioning, and the Active Format Description (AFD).

このメモは、SMPTE ST 291-1で定義されている、米国映画テレビ技術者協会（Society of Motion Picture and Television Engineers、SMPTE）の補助空間（ancillary space、ANC）データのためのリアルタイム転送プロトコル（Real-time Transport Protocol、RTP）のペイロード形式について説明します。SMPTE ANCデータは一般に、タイムコード、クローズドキャプション、アクティブフォーマット記述（Active Format Description、AFD）など、さまざまな種類の補助データを運ぶために、業務用ビデオフォーマットとともに使用されます。

1. Introduction

1. はじめに

This memo describes a Real-time Transport Protocol (RTP) payload format for the Society of Motion Picture and Television Engineers (SMPTE) ancillary space (ANC) data, as defined by SMPTE ST 291-1 [ST291]. ANC data is transmitted in the ancillary space of serial digital video interfaces, the space outside of the active video region of images intended for users to view. Ancillary space roughly corresponds to vertical and horizontal blanking periods of cathode ray tube type displays. ANC data can carry a range of data types, including time code, Closed Captioning, and the Active Format Description (AFD).

このメモは、SMPTE ST 291-1[ST291]で定義されている、米国映画テレビ技術者協会（Society of Motion Picture and Television Engineers、SMPTE）の補助空間（ancillary space、ANC）データのためのリアルタイム転送プロトコル（Real-time Transport Protocol、RTP）のペイロード形式について説明します。ANCデータは、シリアルデジタルビデオインターフェイスの補助空間、すなわち、ユーザーが見ることを意図した画像のアクティブビデオ領域の外側の空間で伝送されます。補助空間は、おおよそ、ブラウン管（陰極線管）型ディスプレイの垂直帰線消去期間と水平帰線消去期間に相当します。ANCデータは、タイムコード、クローズドキャプション、アクティブフォーマット記述（Active Format Description、AFD）など、さまざまな種類のデータを運ぶことができます。

ANC data is generally associated with the carriage of metadata within the bit stream of a Serial Digital Interface (SDI), such as the standard definition (SD) Serial Digital Interface, the 1.5 Gb/s Serial Digital Interface for high definition (HD) television applications, or the 3 Gb/s Signal/Data Serial Interface (SMPTE ST 259 [ST259], SMPTE ST 292-1 [ST292], and SMPTE ST 424 [ST424]).

ANCデータは一般に、シリアルデジタルインターフェイス（Serial Digital Interface、SDI）のビットストリーム内でメタデータを伝送することと結び付けられています。SDIには、標準解像度（SD）シリアルデジタルインターフェイス、高精細（HD）テレビジョンアプリケーション向けの1.5 Gb/sシリアルデジタルインターフェイス、3 Gb/s信号／データシリアルインターフェイス（SMPTE ST 259[ST259]、SMPTE ST 292-1[ST292]、SMPTE ST 424[ST424]）などがあります。

ANC data packet payload definitions for a specific application are specified by a SMPTE Standard, Recommended Practice, Registered Disclosure Document, or by a document generated by another organization, a company, or an individual (an entity). When a payload format is registered with SMPTE, it is identified by a registered data identification word.

特定のアプリケーションのためのANCデータパケットのペイロードの定義は、SMPTE規格（Standard）、推奨実施（Recommended Practice）、登録開示文書（Registered Disclosure Document）、あるいは他の組織、企業、または個人（エンティティー）が作成した文書によって規定されます。ペイロード形式がSMPTEに登録されている場合、そのペイロード形式は登録済みのデータ識別ワードによって識別されます。

This memo describes an RTP payload that supports carriage of ANC data packets that originate from any location within any SMPTE-defined SDI signal. This payload also supports the carriage of ANC data packets that did not originate from an SDI signal. Sufficient information is provided to enable the ANC data packets at the output of the decoder to be restored to their original locations in the serial digital video signal raster (if that is desired). An optional media type parameter allows for the signaling of carriage of one or more types of ANC data as specified by data identification (DID) and secondary data identification (SDID) words. Another optional media type parameter allows for the identification of the Video Payload ID (VPID) code of the source interface of ANC data packets.

このメモでは、SMPTEが定義した任意のSDI信号内の任意の位置を出所とするANCデータパケットの伝送をサポートするRTPペイロードについて説明します。このペイロードは、SDI信号を出所としないANCデータパケットの伝送もサポートします。（望む場合には）デコーダーの出力でANCデータパケットをシリアルデジタルビデオ信号のラスター上の元の位置に復元できるようにするのに十分な情報が提供されます。オプションのメディアタイプパラメーターの1つを使うと、データ識別（data identification、DID）ワードと二次データ識別（secondary data identification、SDID）ワードで指定される1種類以上のANCデータを伝送していることをシグナリングできます。もう1つのオプションのメディアタイプパラメーターを使うと、ANCデータパケットの送信元インターフェイスのビデオペイロードID（Video Payload ID、VPID）コードを識別できます。

Note that the Ancillary Data Flag (ADF) word is not specifically carried in this RTP payload. The ADF might be specified in a document defining an interconnecting digital video interface; otherwise, a default ADF is specified by SMPTE ST 291-1 [ST291].

補助データフラグ（Ancillary Data Flag、ADF）ワードは、このRTPペイロードでは特に伝送されないことに注意してください。ADFは、相互接続するデジタルビデオインターフェイスを定義する文書で規定されている場合があります。そうでない場合は、SMPTE ST 291-1[ST291]でデフォルトのADFが規定されています。

This ANC data payload can be used by itself or used along with a range of RTP video formats. In particular, it has been designed so that it could be used along with "RTP Payload Format for Uncompressed Video" [RFC4175] or "RTP Payload Format for JPEG 2000 Video Streams" [RFC5371].

このANCデータペイロードは、単独で使用することも、さまざまなRTPビデオフォーマットとともに使用することもできます。特に、「RTP Payload Format for Uncompressed Video」[RFC4175]や「RTP Payload Format for JPEG 2000 Video Streams」[RFC5371]とともに使用できるように設計されています。

The data model in this document for the ANC data RTP payload is based on the data model of SMPTE ST 2038 [ST2038], which standardizes the carriage of ANC data packets in an MPEG-2 Transport Stream.

この文書におけるANCデータRTPペイロードのデータモデルは、SMPTE ST 2038[ST2038]のデータモデルに基づいています。SMPTE ST 2038は、MPEG-2トランスポートストリームでのANCデータパケットの伝送を標準化したものです。

2. RTP Payload Format for SMPTE ST 291 Ancillary Data

2. SMPTE ST 291補助データのためのRTPペイロード形式

An example of the format of an RTP packet containing SMPTE ST 291 ANC data is shown below:

SMPTE ST 291 ANCデータを含むRTPパケットのフォーマットの例を以下に示します。

In this example, two ANC data packets are present. The first has four 10-bit User_Data_Words, and the second has five 10-bit User_Data_Words (note that few ANC data packets are this small; thus, this example does not reflect actual defined ANC data packets and does not specifically call out the DIDs and SDIDs). The ANC data packets are located on lines 9 and 10 of the SDI raster.

この例では、2つのANCデータパケットが存在します。1つ目は4個の10ビットのUser_Data_Wordsを持ち、2つ目は5個の10ビットのUser_Data_Wordsを持ちます（これほど小さいANCデータパケットはほとんどないことに注意してください。したがって、この例は実際に定義されたANCデータパケットを反映したものではなく、DIDとSDIDも具体的には示していません）。これらのANCデータパケットは、SDIラスターの9行目と10行目に位置しています。

The term "network byte order" in the payload format SHALL refer to the Data Transmission Order as defined in Appendix B of RFC 791 [RFC0791].

ペイロード形式における「ネットワークバイトオーダー」という用語は、RFC 791[RFC0791]の付録Bで定義されているデータ伝送順序（Data Transmission Order）を指すものとすることになります（SHALL）。

RTP packet header fields SHALL be interpreted as per RFC 3550 [RFC3550], with the following specifics:

RTPパケットヘッダーのフィールドは、RFC 3550[RFC3550]に従って解釈することになります（SHALL）。ただし、具体的には次のとおりです。

Timestamp: 32 bits

The timestamp field is interpreted in a similar fashion to RFC 4175 [RFC4175]:

For progressive scan video, the timestamp denotes the sampling instant of the frame to which the ANC data in the RTP packet belongs. RTP packets MUST NOT include ANC data from multiple frames, and all RTP packets with ANC data belonging to the same frame MUST have the same timestamp.

For interlaced video, the timestamp denotes the sampling instant of the field to which the ANC data in the RTP packet belongs. RTP packets MUST NOT include ANC data packets from multiple fields, and all RTP packets belonging to the same field MUST have the same timestamp.

If the sampling instant does not correspond to an integer value of the clock, the value SHALL be truncated to the next lowest integer with no ambiguity. Section 3.1 describes timestamp clock rates.

Marker bit (M): 1 bit
The marker bit set to "1" indicates the last ANC data RTP packet for a frame (for progressive scan video) or the last ANC data RTP packet for a field (for interlaced video).
Timestamp: 32ビット

タイムスタンプフィールドは、RFC 4175[RFC4175]と同様の方法で解釈されます。

プログレッシブスキャンのビデオでは、タイムスタンプは、RTPパケット内のANCデータが属するフレームのサンプリング時点を表します。RTPパケットは、複数のフレームのANCデータを含んではなりません（MUST NOT）。また、同じフレームに属するANCデータを持つすべてのRTPパケットは、同じタイムスタンプを持たなければなりません（MUST）。

インターレースのビデオでは、タイムスタンプは、RTPパケット内のANCデータが属するフィールドのサンプリング時点を表します。RTPパケットは、複数のフィールドのANCデータパケットを含んではなりません（MUST NOT）。また、同じフィールドに属するすべてのRTPパケットは、同じタイムスタンプを持たなければなりません（MUST）。

サンプリング時点がクロックの整数値に一致しない場合、その値は曖昧さのないように、次に小さい整数に切り捨てたものとすることになります（SHALL）。タイムスタンプのクロックレートについてはセクション3.1で説明します。

Marker bit (M): 1ビット
マーカービットを「1」に設定すると、そのパケットがフレーム（プログレッシブスキャンのビデオの場合）またはフィールド（インターレースのビデオの場合）の最後のANCデータRTPパケットであることを示します。

2.1. Payload Header Definitions

2.1. ペイロードヘッダーの定義

The ANC data RTP payload header fields are defined as:

ANCデータRTPペイロードヘッダーのフィールドは、次のように定義されます。

Extended Sequence Number: 16 bits
The high-order bits of the extended 32-bit sequence number, in network byte order. This is the same as the Extended Sequence Number field in RFC 4175 [RFC4175].
Length: 16 bits
Number of octets of the ANC data RTP payload, beginning with the "C" bit of the first ANC packet data header, as an unsigned integer in network byte order. Note that all word_align fields contribute to the calculation of the Length field.
ANC_Count: 8 bits

This field is the count of the total number of ANC data packets carried in the RTP payload, as an unsigned integer. A single ANC data RTP packet payload cannot carry more than 255 ANC data packets.

If more than 255 ANC data packets need to be carried in a field or frame, additional RTP packets carrying ANC data MAY be sent with the same RTP timestamp but with different sequence numbers. ANC_Count of 0 indicates that there are no ANC data packets in the payload (for example, an RTP packet that carries no actual ANC data packets even though its marker bit indicates the last ANC data RTP packet in a field/frame). If the ANC_Count is 0, the Length will also be 0.

F: 2 bits

These two bits relate to signaling the field specified by the RTP timestamp in an interlaced SDI raster. A value of 0b00 indicates that either the video format is progressive or that no field is specified. A value of 0b10 indicates that the timestamp refers to the first field of an interlaced video signal. A value of 0b11 indicates that the timestamp refers to the second field of an interlaced video signal. The value 0b01 is not valid. Receivers SHOULD ignore an ANC data packet with an F field value of 0b01 and SHOULD process any other ANC data packets with valid F field values that are present in the RTP payload.

Note that some multi-stream SDI interfaces might use multiple interlaced signal streams to transmit progressive images, in which case the "F" bits would refer to the field of the interlaced stream used for transport of the ANC data packet.

reserved: 22 bits
The 22 reserved bits of value "0" follow the F field to ensure that the first ANC data packet header field in the payload begins 32-bit word-aligned with the start of the RTP header to ease implementation.
Extended Sequence Number: 16ビット
拡張された32ビットのシーケンス番号の上位ビットで、ネットワークバイトオーダーで表します。これは、RFC 4175[RFC4175]のExtended Sequence Numberフィールドと同じです。
Length: 16ビット
最初のANCパケットデータヘッダーの「C」ビットから始まるANCデータRTPペイロードのオクテット数で、ネットワークバイトオーダーの符号なし整数で表します。すべてのword_alignフィールドがLengthフィールドの計算に含まれることに注意してください。
ANC_Count: 8ビット

このフィールドは、RTPペイロードで運ばれるANCデータパケットの総数を符号なし整数で表したものです。1つのANCデータRTPパケットのペイロードで運べるANCデータパケットは255個までです。

1つのフィールドまたはフレームで255個を超えるANCデータパケットを運ぶ必要がある場合は、ANCデータを運ぶ追加のRTPパケットを、同じRTPタイムスタンプで、異なるシーケンス番号を付けて送信してもよいです（MAY）。ANC_Countが0の場合、ペイロードにANCデータパケットがないことを示します（たとえば、マーカービットがフィールド／フレーム内の最後のANCデータRTPパケットであることを示しているものの、実際のANCデータパケットを運んでいないRTPパケット）。ANC_Countが0の場合、Lengthも0になります。

F: 2ビット

この2ビットは、インターレースのSDIラスターにおいて、RTPタイムスタンプで指定されるフィールドをシグナリングすることに関係します。値0b00は、ビデオフォーマットがプログレッシブであるか、フィールドが指定されていないかのどちらかを示します。値0b10は、タイムスタンプがインターレースのビデオ信号の第1フィールドを指すことを示します。値0b11は、タイムスタンプがインターレースのビデオ信号の第2フィールドを指すことを示します。値0b01は無効です。受信者は、Fフィールドの値が0b01であるANCデータパケットを無視すべきです（SHOULD）。そして、RTPペイロード内に存在する、有効なFフィールドの値を持つその他のANCデータパケットを処理すべきです（SHOULD）。

一部のマルチストリームSDIインターフェイスでは、プログレッシブ画像を伝送するために複数のインターレース信号ストリームを使用する場合があることに注意してください。その場合、「F」ビットは、ANCデータパケットの伝送に使用されるインターレースストリームのフィールドを指すことになります。

reserved: 22ビット
値「0」の22個の予約済みビットがFフィールドに続きます。これは、実装を容易にするために、ペイロード内の最初のANCデータパケットヘッダーフィールドが、RTPヘッダーの先頭から32ビットワード境界にそろった位置で始まるようにするためです。

For each ANC data packet in the payload, the following ANC data packet header fields MUST be present:

ペイロード内の各ANCデータパケットについて、次のANCデータパケットヘッダーフィールドが存在しなければなりません（MUST）。

C: 1 bit
This flag, when set to "1", indicates that the ANC data corresponds to the color-difference data channel (C). When set to "0", this flag indicates either that the ANC data corresponds to the luma (Y) data channel, that the ANC data source is from an SD signal, or that the ANC data source has no specific luma or color-difference data channels. For ANC data from a multi-stream interface source, the C flag SHALL refer to the channel of the stream used to transport the ANC data packet. For situations where there is no SDI source, if the ANC data type definition specifically requires the use of the C or Y data channel, the C flag SHALL reflect that requirement.
Line_Number: 11 bits

This field contains the digital interface line number that corresponds to the location of the ANC data packet as an unsigned integer in network byte order.

The following special Line_Number values indicate that the location of the ANC data packet is in certain generic vertical regions of the SDI raster:

Table 1
Line_Number ANC data packet generic vertical location
0x7FF Without specific line location within the field or frame
0x7FE On any line in the range from the second line after the line specified for switching, as defined in SMPTE RP 168 [RP168], to the last line before active video, inclusive
0x7FD On a line number larger than can be represented in 11 bits of this field (if needed for future formats)

Note that the lines that are available to convey ANC data are as defined in the applicable sample structure specification (e.g., SMPTE ST 274 [ST274], SMPTE ST 296 [ST296], ITU-R BT.656 [BT656]) and are possibly further restricted per SMPTE RP 168 [RP168].

In multi-stream interfaces, this field refers to the line number that an ANC data packet is carried on within a particular data stream in the interface.

Horizontal_Offset: 12 bits

This field defines the location of the ANC data packet in an SDI raster relative to the start of active video (SAV; a digital synchronizing signal present in SDI interfaces) as an unsigned integer in network byte order. A value of 0 means that the ADF of the ANC data packet begins immediately following SAV. The horizontal offset from SAV is measured in terms of 10-bit words of the indicated data stream and data channel.

The following special Horizontal_Offset values indicate that the location of the ANC data packet is in certain generic horizontal regions of the SDI raster:

Table 2
Horizontal_Offset ANC data packet generic horizontal location
0xFFF Without specific horizontal location
0xFFE Within horizontal ancillary data space (HANC) as defined in SMPTE ST 291-1 [ST291]
0xFFD Within the ancillary data space located between SAV (Start of Active Video) and EAV (End of Active Video) markers of the serial digital interface
0xFFC Horizontal offset is larger than can be represented in the 12 bits of this field (if needed for future formats or for certain low frame rate 720p formats)

In multi-stream interfaces, this field refers to the horizontal location where an ANC data packet is placed on a line carried within a particular data stream in the interface.

Note that HANC data space will generally have higher luma sample numbers than any samples in the active digital line. Also note that SMPTE ST 296 [ST296] (1280 x 720 progressive active images) image sampling systems 7 and 8 (1280 x 720 progressive @ 24 fps and 1280 x 720 progressive @ 23.98 fps respectively) have a luma sample number maximum of 4124. It is unlikely that an actual implementation would have an ANC data packet begin at a Horizontal_Offset beyond 4091 (0xFFB) in these formats; should that occur, the Horizontal_Offset value 0xFFC can be used to signal a horizontal offset larger than can be represented in the field. Further note that the 12-bit field of Horizontal_Offset is kept that size in this memo to maintain easy conversion to/from SMPTE ST 2038 [ST2038], which also has a 12-bit Horizontal_Offset field.

S (Data Stream Flag): 1 bit
This field indicates whether the data stream number of a multi-stream data mapping used to transport the ANC data packet is specified. If the S bit is '0', then the StreamNum field provides no guidance regarding the source data stream number of the ANC data packet. If the S bit is '1', then the StreamNum field carries information regarding the source data stream number of the ANC data packet.
StreamNum: 7 bits

If the S bit (Data Stream Flag) is '1', then the StreamNum field MUST carry identification of the source data stream number of the ANC data packet. If the data stream is numbered, then the StreamNum field SHALL carry the number of the source data stream minus one. If the source multi-stream interface does not have numbered data streams, the following numbers SHALL be used in this field: '0' for link A data stream and '1' for link B data stream. For stereoscopic multi-stream interface formats that do not have numbered streams, the following numbers SHALL be used in this field: '0' for left eye stream and '1' for right eye stream.

Note that in multi-link SDI connections, the physical link that a particular stream utilizes is typically specified by the interface standard. Also note that numbering of data streams is across the interface as a whole. For example, in the SMPTE ST 425-3 dual-link 3 Gb/s interface, the data streams are numbered 1-4 with data streams 1 and 2 on link 1 and data streams 3 and 4 on link 2.

C: 1ビット
このフラグを「1」に設定すると、ANCデータが色差データチャネル（C）に対応することを示します。「0」に設定すると、ANCデータが輝度（Y）データチャネルに対応すること、ANCデータの送信元がSD信号であること、またはANCデータの送信元に特定の輝度データチャネルや色差データチャネルがないことのいずれかを示します。マルチストリームインターフェイスの送信元からのANCデータの場合、Cフラグは、そのANCデータパケットの伝送に使用されるストリームのチャネルを指すものとすることになります（SHALL）。SDIの送信元がない状況では、ANCデータタイプの定義でCデータチャネルまたはYデータチャネルの使用が明確に要求されている場合、Cフラグはその要件を反映することになります（SHALL）。
Line_Number: 11ビット

このフィールドには、ANCデータパケットの位置に対応するデジタルインターフェイスの行番号が、ネットワークバイトオーダーの符号なし整数で格納されます。

次の特別なLine_Numberの値は、ANCデータパケットの位置がSDIラスターの特定の汎用的な垂直領域にあることを示します。

表1

0x7FE SMPTE RP 168[RP168]で定義されている切り替え用に指定された行の2行後から、アクティブビデオの直前の行までの範囲（両端を含む）にある任意の行

マルチストリームインターフェイスでは、このフィールドは、インターフェイス内の特定のデータストリームにおいてANCデータパケットが運ばれる行番号を指します。

Horizontal_Offset: 12ビット

このフィールドは、SDIラスターにおけるANCデータパケットの位置を、アクティブビデオの開始（start of active video、SAV。SDIインターフェイスに存在するデジタル同期信号）からの相対位置として、ネットワークバイトオーダーの符号なし整数で定義します。値0は、ANCデータパケットのADFがSAVの直後から始まることを意味します。SAVからの水平オフセットは、指示されたデータストリームとデータチャネルの10ビットワードを単位として測定されます。

次の特別なHorizontal_Offsetの値は、ANCデータパケットの位置がSDIラスターの特定の汎用的な水平領域にあることを示します。

HANCデータ空間は一般に、アクティブなデジタルラインのどのサンプルよりも大きい輝度サンプル番号を持つことに注意してください。また、SMPTE ST 296[ST296]（1280 x 720プログレッシブのアクティブ画像）の画像サンプリングシステム7と8（それぞれ1280 x 720プログレッシブ@ 24 fpsと1280 x 720プログレッシブ@ 23.98 fps）では、輝度サンプル番号の最大値が4124であることにも注意してください。これらのフォーマットにおいて、実際の実装でANCデータパケットが4091（0xFFB）を超えるHorizontal_Offsetから始まることはまずありません。万一そうなった場合は、Horizontal_Offsetの値0xFFCを使って、このフィールドで表せるよりも大きい水平オフセットであることをシグナリングできます。さらに、このメモでHorizontal_Offsetのフィールドを12ビットのままにしているのは、同じく12ビットのHorizontal_Offsetフィールドを持つSMPTE ST 2038[ST2038]との間の変換を容易に保つためであることにも注意してください。

S (Data Stream Flag): 1ビット
このフィールドは、ANCデータパケットの伝送に使用されるマルチストリームデータマッピングのデータストリーム番号が指定されているかどうかを示します。Sビットが「0」の場合、StreamNumフィールドは、ANCデータパケットの送信元データストリーム番号に関する手がかりを何も提供しません。Sビットが「1」の場合、StreamNumフィールドは、ANCデータパケットの送信元データストリーム番号に関する情報を運びます。
StreamNum: 7ビット

S（Data Stream Flag）ビットが「1」の場合、StreamNumフィールドは、ANCデータパケットの送信元データストリーム番号の識別情報を運ばなければなりません（MUST）。データストリームに番号が付けられている場合、StreamNumフィールドは、送信元データストリームの番号から1を引いた値を運ぶものとすることになります（SHALL）。送信元のマルチストリームインターフェイスのデータストリームに番号が付けられていない場合は、このフィールドで次の番号を使用することになります（SHALL）。リンクAのデータストリームには「0」、リンクBのデータストリームには「1」です。番号付きのストリームを持たない立体視（stereoscopic）マルチストリームインターフェイスのフォーマットでは、このフィールドで次の番号を使用することになります（SHALL）。左目のストリームには「0」、右目のストリームには「1」です。

マルチリンクSDI接続では、特定のストリームが利用する物理リンクは、通常、インターフェイスの規格で規定されていることに注意してください。また、データストリームの番号付けはインターフェイス全体を通して行われることにも注意してください。たとえば、SMPTE ST 425-3のデュアルリンク3 Gb/sインターフェイスでは、データストリームに1～4の番号が付けられ、データストリーム1と2はリンク1に、データストリーム3と4はリンク2にあります。

An ANC data packet with the header fields Line_Number of 0x7FF and Horizontal_Offset of 0xFFF SHALL be considered to be carried without any specific location within the field or frame.

ヘッダーフィールドのLine_Numberが0x7FFで、Horizontal_Offsetが0xFFFであるANCデータパケットは、フィールドまたはフレーム内の特定の位置なしで運ばれているものとすることになります（SHALL）。

For each ANC data packet in the payload, immediately after the ANC data packet header fields, the following data fields MUST be present with the fields DID, SDID, Data_Count, User_Data_Words, and Checksum_Word representing the 10-bit words carried in the ANC data packet, as per SMPTE ST 291-1 [ST291]:

ペイロード内の各ANCデータパケットについて、ANCデータパケットヘッダーフィールドの直後に、次のデータフィールドが存在しなければなりません（MUST）。DID、SDID、Data_Count、User_Data_Words、Checksum_Wordの各フィールドは、SMPTE ST 291-1[ST291]に従ってANCデータパケットで運ばれる10ビットワードを表します。

DID: 10 bits
Data identification word
SDID: 10 bits
Secondary data identification word. Used only for a "Type 2" ANC data packet. Note that in a "Type 1" ANC data packet, this word will actually carry the data block number (DBN).
Data_Count: 10 bits
The lower 8 bits of Data_Count, corresponding to bits b7 (MSB; most significant bit) through b0 (LSB; least significant bit) of the 10-bit Data_Count word, contain the actual count of 10-bit words in User_Data_Words. Bit b8 is the even parity for bits b7 through b0, and bit b9 is the inverse (logical NOT) of bit b8.
User_Data_Words: integer number of 10-bit words
User_Data_Words (UDW) are used to convey information of a type as identified by the DID word or the DID and SDID words. The number of 10-bit words in the UDW is defined by the Data_Count field. The 10-bit words are carried in order starting with the most significant bit and ending with the least significant bit.
Checksum_Word: 10 bits
The Checksum_Word can be used to determine the validity of the ANC data packet from the DID word through the UDW. It consists of 10 bits, where bits b8 (MSB) through b0 (LSB) define the checksum value and bit b9 is the inverse (logical NOT) of bit b8. The checksum value is equal to the nine least significant bits of the sum of the nine least significant bits of the DID word, the SDID word, the Data_Count word, and all User_Data_Words in the ANC data packet. The checksum is initialized to zero before calculation, and any "end carry" resulting from the checksum calculation is ignored.
DID: 10ビット
データ識別ワード
SDID: 10ビット
二次データ識別ワードです。「タイプ2」のANCデータパケットでのみ使用されます。「タイプ1」のANCデータパケットでは、このワードは実際にはデータブロック番号（data block number、DBN）を運ぶことに注意してください。
Data_Count: 10ビット
10ビットのData_Countワードのビットb7（MSB。最上位ビット）からb0（LSB。最下位ビット）に相当するData_Countの下位8ビットには、User_Data_Words内の10ビットワードの実際の個数が格納されます。ビットb8はビットb7からb0の偶数パリティーであり、ビットb9はビットb8の反転（論理否定）です。
User_Data_Words: 10ビットワードの整数個
User_Data_Words（UDW）は、DIDワード、またはDIDワードとSDIDワードによって識別される種類の情報を伝えるために使用されます。UDW内の10ビットワードの個数は、Data_Countフィールドで定義されます。10ビットワードは、最上位ビットから始まり最下位ビットで終わる順序で運ばれます。
Checksum_Word: 10ビット
Checksum_Wordは、DIDワードからUDWまでのANCデータパケットの有効性を判定するために使用できます。これは10ビットで構成され、ビットb8（MSB）からb0（LSB）でチェックサムの値を定義し、ビットb9はビットb8の反転（論理否定）です。チェックサムの値は、ANCデータパケット内のDIDワード、SDIDワード、Data_Countワード、およびすべてのUser_Data_Wordsのそれぞれの下位9ビットの合計の、下位9ビットに等しくなります。チェックサムは計算の前に0に初期化され、チェックサムの計算で生じる「最上位桁からの桁上げ（end carry）」は無視されます。

At the end of each ANC data packet in the payload:

ペイロード内の各ANCデータパケットの末尾には、次のフィールドがあります。

word_align: bits as needed to complete 32-bit word
Word_align contains enough "0" bits as needed to complete the last 32-bit word of an ANC data packet in the RTP payload. If an ANC data packet in the RTP payload ends and is aligned with a word boundary, there is no need to add any word alignment bits. Word align SHALL be used even for the last ANC data packet in an RTP packet. Word align SHALL NOT be used if there are zero ANC data packets being carried in the RTP packet.
word_align: 32ビットワードを埋めるのに必要なビット数
Word_alignには、RTPペイロード内のANCデータパケットの最後の32ビットワードを埋めるのに必要な数の「0」ビットが入ります。RTPペイロード内のANCデータパケットがワード境界にそろって終わる場合は、ワード整列用のビットを追加する必要はありません。ワード整列は、RTPパケット内の最後のANCデータパケットに対しても使用することになります（SHALL）。RTPパケットで運ばれるANCデータパケットが0個の場合、ワード整列を使用することはありません（SHALL NOT）。

When reconstructing an SDI signal based on this payload, it is important to place ANC data packets into the locations indicated by the ANC data packet header fields C, Line_Number and Horizontal_Offset, and also to follow the requirements of Section 7 of SMPTE ST 291-1 [ST291], "Ancillary Data Space Formatting (Component or Composite Interface)", which includes rules on the placement of initial ANC data into allowed spaces as well as the contiguity of ANC data packet sequences within those spaces in order to assure that the resulting ANC data packets in the SDI signal are valid. The optional media type parameter VPID_Code can inform receivers of the type of originating SDI interface. For multi-stream originating interfaces, the StreamNum field can provide information regarding which stream an ANC data packet can be placed in to match the ANC data location in the originating SDI interface.

このペイロードに基づいてSDI信号を再構築する際には、ANCデータパケットを、ANCデータパケットヘッダーのC、Line_Number、Horizontal_Offsetの各フィールドが示す位置に配置することが重要です。また、SMPTE ST 291-1[ST291]のセクション7「Ancillary Data Space Formatting (Component or Composite Interface)」の要件に従うことも重要です。このセクションには、SDI信号内で結果として得られるANCデータパケットが有効であることを保証するために、最初のANCデータを許可された空間に配置することや、その空間内でANCデータパケットの並びを連続させることに関する規則が含まれています。オプションのメディアタイプパラメーターであるVPID_Codeを使うと、元のSDIインターフェイスの種類を受信者に知らせることができます。元のインターフェイスがマルチストリームの場合、StreamNumフィールドは、元のSDIインターフェイスにおけるANCデータの位置と一致させるために、ANCデータパケットをどのストリームに配置できるかに関する情報を提供できます。

Senders of this payload SHOULD transmit available ANC data packets as soon as practical to reduce end-to-end latency, especially if the receivers will be embedding the received ANC data packet into an SDI signal emission. One millisecond is a reasonable upper bound for the amount of time between when an ANC data packet becomes available to a sender and the emission of an RTP payload containing that ANC data packet.

このペイロードの送信者は、エンドツーエンドの遅延を減らすために、利用可能になったANCデータパケットをできるだけ早く送信すべきです（SHOULD）。受信者が受信したANCデータパケットをSDI信号の出力に埋め込む場合は特にそうです。ANCデータパケットが送信者で利用可能になってから、そのANCデータパケットを含むRTPペイロードを送出するまでの時間の上限としては、1ミリ秒が妥当です。

ANC data packets with headers that indicate specific location within a field or frame SHOULD be sent in raster scan order, both in terms of packing position within an RTP packet and in terms of transmission time of RTP packets.

フィールドまたはフレーム内の特定の位置を示すヘッダーを持つANCデータパケットは、RTPパケット内での格納位置とRTPパケットの送信時刻の両方の観点で、ラスタースキャンの順序で送信すべきです（SHOULD）。

4. SDP Considerations

4. SDPに関する考慮事項

The mapping of the above-defined payload format media type and its parameters SHALL be done according to Section 3 of RFC 4855 [RFC4855].

上で定義したペイロード形式のメディアタイプとそのパラメーターのマッピングは、RFC 4855[RFC4855]のセクション3に従って行うものとすることになります（SHALL）。

  • The type name ("video") goes in SDP "m=" as the media name.
  • The subtype name ("smpte291") goes in SDP "a=rtpmap" as the encoding name, followed by a slash ("/") and the rate parameter.
  • The optional parameters VPID_Code and DID_SDID, when present, are included in the "a=fmtp" attribute line of SDP as a semicolon-separated list of parameter=value pairs.
  • タイプ名（「video」）は、メディア名としてSDPの「m=」に入ります。
  • サブタイプ名（「smpte291」）は、エンコーディング名としてSDPの「a=rtpmap」に入り、その後にスラッシュ（「/」）とrateパラメーターが続きます。
  • オプションのパラメーターであるVPID_CodeとDID_SDIDは、存在する場合、parameter=valueのペアをセミコロンで区切ったリストとして、SDPの「a=fmtp」属性行に含まれます。

DID and SDID values SHALL be specified in hexadecimal with a "0x" prefix (such as "0x61"). The ABNF as per RFC 5234 [RFC5234] of the DID_SDID optional parameter SHALL be:

DIDとSDIDの値は、「0x」というプレフィックスを付けた16進数で指定することになります（SHALL）（「0x61」など）。RFC 5234[RFC5234]に従ったDID_SDIDオプションパラメーターのABNFは、次のとおりとすることになります（SHALL）。

        TwoHex = "0x" 1*2(HEXDIG)
        DidSdid = "DID_SDID={" TwoHex "," TwoHex "}"

        TwoHex = "0x" 1*2(HEXDIG)
        DidSdid = "DID_SDID={" TwoHex "," TwoHex "}"

For example, EIA 608 Closed Caption data would be signaled with the parameter DID_SDID={0x61,0x02}. If a DID_SDID parameter is not specified, then the ANC data stream might potentially contain ANC data packets of any type.

たとえば、EIA 608クローズドキャプションのデータは、パラメーターDID_SDID={0x61,0x02}でシグナリングされます。DID_SDIDパラメーターが指定されていない場合、ANCデータストリームには任意の種類のANCデータパケットが含まれている可能性があります。

Multiple DID_SDID parameters can be specified (separated by semicolons) to signal the presence of multiple types of ANC data in the stream. DID_SDID={0x61,0x02};DID_SDID={0x41,0x05}, for example, signals the presence of EIA 608 Closed Captions as well as AFD/Bar Data. Multiple DID_SDID parameters do not imply any particular ordering of the different types of ANC data packets in the stream.

ストリーム内に複数の種類のANCデータが存在することをシグナリングするために、（セミコロンで区切って）複数のDID_SDIDパラメーターを指定できます。たとえば、DID_SDID={0x61,0x02};DID_SDID={0x41,0x05}は、EIA 608クローズドキャプションとAFD/Barデータが存在することをシグナリングします。複数のDID_SDIDパラメーターは、ストリーム内の異なる種類のANCデータパケットの特定の順序を意味するものではありません。

If the optional parameter VPID_Code is present, it SHALL be present only once in the semicolon-separated list, taking a single integer value.

オプションのパラメーターであるVPID_Codeが存在する場合、それはセミコロンで区切られたリスト内に1回だけ存在することになります（SHALL）。その値は単一の整数です。

A sample SDP mapping for ANC data is as follows:

ANCデータのSDPマッピングの例を次に示します。

   m=video 30000 RTP/AVP 112
   a=rtpmap:112 smpte291/90000
   a=fmtp:112 DID_SDID={0x61,0x02};DID_SDID={0x41,0x05};VPID_Code=132

   m=video 30000 RTP/AVP 112
   a=rtpmap:112 smpte291/90000
   a=fmtp:112 DID_SDID={0x61,0x02};DID_SDID={0x41,0x05};VPID_Code=132

In this example, a dynamic payload type 112 is used for ANC data. The 90 kHz RTP timestamp rate is specified in the "a=rtpmap" line after the subtype. In the "a=fmtp:" line, DID 0x61 and SDID 0x02 are specified (registered to EIA 608 Closed Caption Data by SMPTE), and also DID 0x41 and SDID 0x05 (registered to AFD/Bar Data). The VPID_Code is 132 (referring to SMPTE ST 292-1, 720-line video payloads on a 1.5 Gb/s serial digital interface).

この例では、ANCデータに動的ペイロードタイプ112を使用しています。90 kHzのRTPタイムスタンプのレートは、「a=rtpmap」行のサブタイプの後で指定されています。「a=fmtp:」行では、DID 0x61とSDID 0x02（SMPTEによってEIA 608クローズドキャプションデータに登録されているもの）、およびDID 0x41とSDID 0x05（AFD/Barデータに登録されているもの）が指定されています。VPID_Codeは132です（1.5 Gb/sのシリアルデジタルインターフェイス上の720ラインのビデオペイロードであるSMPTE ST 292-1を指します）。

4.1. Grouping ANC Data Streams with Other Media Streams

4.1. ANCデータストリームと他のメディアストリームのグループ化

To indicate the association of an ANC data stream with a particular video stream, implementers MAY group the "m" lines together using Flow Identification ("FID") semantics as defined in RFC 5888 [RFC5888].

ANCデータストリームと特定のビデオストリームとの関連を示すために、実装者は、RFC 5888[RFC5888]で定義されているフロー識別（Flow Identification、「FID」）のセマンティクスを使用して、「m」行をまとめてグループ化してもよいです（MAY）。

A sample SDP mapping for grouping ANC data with video as described in RFC 4175 [RFC4175] is as follows:

RFC 4175[RFC4175]で説明されているビデオとANCデータをグループ化するためのSDPマッピングの例を次に示します。

     v=0
     o=Al 123456 11 IN IP4 host.example.com
     s=Professional Networked Media Test
     i=A test of synchronized video and ANC data
     t=0 0
     a=group:FID V1 M1
     m=video 50000 RTP/AVP 96
     c=IN IP4 233.252.0.1/255
     a=rtpmap:96 raw/90000
     a=fmtp:96 sampling=YCbCr-4:2:2; width=1280; height=720; depth=10
     a=mid:V1
     m=video 50010 RTP/AVP 97
     c=IN IP4 233.252.0.2/255
     a=rtpmap:97 smpte291/90000
     a=fmtp:97 DID_SDID={0x61,0x02};DID_SDID={0x41,0x05}
     a=mid:M1

     v=0
     o=Al 123456 11 IN IP4 host.example.com
     s=Professional Networked Media Test
     i=A test of synchronized video and ANC data
     t=0 0
     a=group:FID V1 M1
     m=video 50000 RTP/AVP 96
     c=IN IP4 233.252.0.1/255
     a=rtpmap:96 raw/90000
     a=fmtp:96 sampling=YCbCr-4:2:2; width=1280; height=720; depth=10
     a=mid:V1
     m=video 50010 RTP/AVP 97
     c=IN IP4 233.252.0.2/255
     a=rtpmap:97 smpte291/90000
     a=fmtp:97 DID_SDID={0x61,0x02};DID_SDID={0x41,0x05}

5. Offer/Answer Model and Declarative Considerations

5. オファー/アンサーモデルと宣言的な利用に関する考慮事項

5.1. Offer/Answer Model

5.1. オファー/アンサーモデル

Receivers might wish to receive ANC data streams with specific DID_SDID parameters. Thus, when offering ANC data streams using the Session Description Protocol (SDP) in an Offer/Answer model [RFC3264], the offerer MAY provide a list of ANC data streams available with specific DID_SDID parameters in the fmtp line. The answerer MAY (1) respond with all or a subset of the streams offered along with fmtp lines with all or a subset of the DID_SDID parameters offered, (2) set the corresponding port number to 0 to decline the smpte291 stream if not in the same media section as a corresponding video stream, or (3) remove the corresponding payload type if the smpte291 stream is in the same media section as a corresponding video stream. There are no restrictions on updating DID_SDID parameters in a subsequent offer.

受信者は、特定のDID_SDIDパラメーターを持つANCデータストリームを受信したい場合があります。そのため、オファー/アンサーモデル[RFC3264]でセッション記述プロトコル（Session Description Protocol、SDP）を使用してANCデータストリームをオファーする際、オファー側は、利用可能なANCデータストリームのリストを、特定のDID_SDIDパラメーターとともにfmtp行で提供してもよいです（MAY）。アンサー側は、（1）オファーされたストリームのすべてまたは一部を、オファーされたDID_SDIDパラメーターのすべてまたは一部を含むfmtp行とともに応答する、（2）smpte291ストリームが対応するビデオストリームと同じメディアセクションにない場合は、対応するポート番号を0に設定してそのストリームを拒否する、（3）smpte291ストリームが対応するビデオストリームと同じメディアセクションにある場合は、対応するペイロードタイプを削除する、のいずれかをしてもよいです（MAY）。後続のオファーでDID_SDIDパラメーターを更新することに制限はありません。

5.2. Declarative SDP Considerations

5.2. 宣言的SDPに関する考慮事項

For declarative use of SDP, nothing specific is defined for this payload format. The configuration given by the SDP MUST be used when sending and/or receiving media in the session.

SDPの宣言的な利用について、このペイロード形式に固有のものは何も定義されていません。セッションでメディアを送信または受信（あるいはその両方）する際には、SDPで与えられた設定を使用しなければなりません（MUST）。

7. Security Considerations

7. セキュリティーに関する考慮事項

RTP packets using the payload format defined in this specification are subject to the security considerations discussed in the RTP specification [RFC3550] and in any applicable RTP profile such as RTP/AVP [RFC3551], RTP/AVPF [RFC4585], RTP/SAVP [RFC3711], or RTP/SAVPF [RFC5124]. However, as "Securing the RTP Protocol Framework: Why RTP Does Not Mandate a Single Media Security Solution" [RFC7202] discusses, it is not the responsibility of an RTP payload format to discuss or mandate what solutions are to be used to meet the basic security goals like confidentiality, integrity, and source authenticity for RTP in general. This responsibility lays on anyone using RTP in an application. They can find guidance on available security mechanisms and important considerations in "Options for Securing RTP Sessions" [RFC7201]. Applications SHOULD use one or more appropriately strong security mechanisms. The rest of this section discusses the security impacting properties of the payload format itself.

この仕様で定義されたペイロード形式を使用するRTPパケットは、RTPの仕様[RFC3550]や、RTP/AVP[RFC3551]、RTP/AVPF[RFC4585]、RTP/SAVP[RFC3711]、RTP/SAVPF[RFC5124]などの適用可能なRTPプロファイルで議論されているセキュリティーに関する考慮事項の対象となります。ただし、「Securing the RTP Protocol Framework: Why RTP Does Not Mandate a Single Media Security Solution」[RFC7202]で議論されているように、RTP全般の機密性、完全性、送信元の真正性などの基本的なセキュリティー目標を満たすためにどのような解決策を使用するかを議論したり義務付けたりするのは、RTPペイロード形式の責任ではありません。この責任は、アプリケーションでRTPを使用するすべての者にあります。利用可能なセキュリティーメカニズムと重要な考慮事項に関するガイダンスは、「Options for Securing RTP Sessions」[RFC7201]で見つけることができます。アプリケーションは、適切な強度を持つセキュリティーメカニズムを1つ以上使用すべきです（SHOULD）。このセクションの残りの部分では、ペイロード形式そのもののセキュリティーに影響する特性について説明します。

To avoid potential buffer overflow attacks, receivers SHOULD validate that the ANC data packets in the RTP payload are of the appropriate length (using the Data_Count field) for the ANC data type specified by DID and SDID. Also, the Checksum_Word SHOULD be checked against the ANC data packet to ensure that its data has not been damaged in transit; note that the Checksum_Word is unlikely to provide a payload integrity check in case of a directed attack.

潜在的なバッファーオーバーフロー攻撃を避けるために、受信者は、RTPペイロード内のANCデータパケットが、DIDとSDIDで指定されたANCデータタイプに対して適切な長さであることを（Data_Countフィールドを使って）検証すべきです（SHOULD）。また、ANCデータパケットのデータが転送中に損傷していないことを確認するために、ANCデータパケットに対してChecksum_Wordを検査すべきです（SHOULD）。ただし、意図的な攻撃に対しては、Checksum_Wordがペイロードの完全性チェックとして機能する可能性は低いことに注意してください。

Some receivers will simply move the ANC data packet bits from the RTP payload into SDI. It might still be a good idea for these "re-embedders" to perform the above-mentioned validity tests to avoid downstream SDI systems from becoming confused by bad ANC data packets, which could be used for a denial-of-service attack.

受信者の中には、ANCデータパケットのビットをRTPペイロードからSDIへ単に移すだけのものもあるでしょう。そのような「再埋め込み器（re-embedder）」であっても、不正なANCデータパケットによって下流のSDIシステムが混乱するのを避けるために、上記の有効性テストを実行するのは良い考えかもしれません。そのような不正なパケットは、サービス拒否攻撃に使用される可能性があるからです。

"Re-embedders" into SDI SHOULD also double check that the Line_Number and Horizontal_Offset lead to the ANC data packet being inserted into a legal area to carry ANC data in the SDI video bit stream of the output video format.

SDIへの「再埋め込み器」は、Line_NumberとHorizontal_Offsetによって、出力ビデオフォーマットのSDIビデオビットストリーム内でANCデータを運ぶことが許される領域にANCデータパケットが挿入されることも、再確認すべきです（SHOULD）。
