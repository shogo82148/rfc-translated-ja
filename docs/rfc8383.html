Transparent Interconnection of Lots of Links (TRILL): Address Flush Message

RFC 8383

Transparent Interconnection of Lots of Links（TRILL）：Address Flushメッセージ

Abstract

概要

The TRILL (Transparent Interconnection of Lots of Links) protocol, by default, learns end station addresses from observing the data plane. In particular, it learns local Media Access Control (MAC) addresses and the edge switch port of attachment from the receipt of local data frames and learns remote MAC addresses and the edge switch port of attachment from the decapsulation of remotely sourced TRILL Data packets.

TRILL（Transparent Interconnection of Lots of Links）プロトコルは、デフォルトでは、データプレーンを観察することによってエンドステーションのアドレスを学習します。具体的には、ローカルのデータフレームの受信からローカルのメディアアクセス制御（MAC）アドレスと接続先のエッジスイッチのポートを学習し、リモートから送信されたTRILLデータパケットのカプセル化解除からリモートのMACアドレスと接続先のエッジスイッチのポートを学習します。

This document specifies a message by which a TRILL switch can explicitly request other TRILL switches to flush certain MAC reachability learned through the decapsulation of TRILL Data packets. This is a supplement to the TRILL automatic address forgetting (see Section 4.8.3 of RFC 6325) and can assist in achieving more rapid convergence in case of topology or configuration change.

この文書は、TRILLデータパケットのカプセル化解除を通じて学習した特定のMAC到達可能性をフラッシュするよう、TRILLスイッチがほかのTRILLスイッチに明示的にリクエストできるメッセージを規定します。これは、TRILLの自動的なアドレスの忘却（RFC 6325のセクション4.8.3を参照）を補うものであり、トポロジーや設定が変化した場合に、より迅速な収束を実現するのに役立ちます。

1. Introduction

1. はじめに

By default, edge TRILL (Transparent Interconnection of Lots of Links) switches [RFC6325] [RFC7780], also called edge Routing Bridges (RBridges), learn end station MAC address reachability from observing the data plane. On receipt of a native frame from an end station, they would learn the local MAC address attachment of the source end station. And on egressing (decapsulating) a remotely originated TRILL Data packet, they learn the remote MAC address and remote attachment TRILL switch. Such learning is all scoped by data label (VLAN or Fine-Grained Label (FGL) [RFC7172]).

デフォルトでは、エッジのTRILL（Transparent Interconnection of Lots of Links）スイッチ[RFC6325] [RFC7780]（エッジのルーティングブリッジ（RBridge）とも呼ばれます）は、データプレーンを観察することによってエンドステーションのMACアドレスの到達可能性を学習します。エンドステーションからネイティブフレームを受信すると、送信元エンドステーションのローカルなMACアドレスの接続を学習します。また、リモートで発信されたTRILLデータパケットを出口処理（カプセル化解除）すると、リモートのMACアドレスと、リモートの接続先TRILLスイッチを学習します。このような学習はすべて、データラベル（VLANまたはFine-Grained Label（FGL）[RFC7172]）をスコープとします。

TRILL has mechanisms for timing out such learning and appropriately clearing it based on some network connectivity and configuration changes; however, there are circumstances under which it would be helpful for a TRILL switch to be able to explicitly flush (purge) certain learned end station reachability information in remote RBridges to achieve more-rapid convergence. Section 6.2 of [RFC4762] is an example of the use of such a mechanism.

TRILLには、このような学習をタイムアウトさせたり、ネットワークの接続性や設定の変化に基づいて適切に消去したりするメカニズムがあります。しかし、より迅速な収束を実現するために、リモートのRBridgeで学習された特定のエンドステーションの到達可能性情報を、TRILLスイッチが明示的にフラッシュ（パージ）できると役に立つ状況があります。[RFC4762]のセクション6.2は、そのようなメカニズムの使用例です。

Another example, based on Appendix A.3 of [RFC6325] ("Wiring Closet Topology"), presents a bridged LAN connected to a TRILL network via multiple RBridge ports. For optimum paths, Appendix A.3.3 suggests configuring the RBridge ports to be like one Spanning Tree Protocol (STP) tree root in the bridged LAN. The Address Flush message in this document could also be triggered in this case when one of the edge RBridges receives Topology Change (TC) information (e.g., TC in STP, Topology Change Notification (TCN) in Multiple Spanning Tree Protocol (MSTP)) in order to rapidly flush the MAC addresses for specific VLANs learned at the other edge RBridge ports.

もう1つの例は、[RFC6325]の付録A.3（「Wiring Closet Topology」）に基づくもので、複数のRBridgeポートを介してTRILLネットワークに接続されたブリッジLANを示しています。最適なパスのために、付録A.3.3では、ブリッジLANにおいてRBridgeポートを1つのスパニングツリープロトコル（STP）ツリーのルートのように設定することを提案しています。この場合にも、エッジRBridgeの1つがトポロジー変更（TC）情報（たとえば、STPにおけるTCや、マルチプルスパニングツリープロトコル（MSTP）におけるトポロジー変更通知（TCN））を受信したときに、ほかのエッジRBridgeポートで学習された特定のVLANのMACアドレスを迅速にフラッシュするために、この文書のAddress Flushメッセージを発動できます。

A TRILL switch can easily flush any locally learned addresses it wants. This document specifies an RBridge Channel Support protocol [RFC7178] message to request flushing address information for specific VLANs or FGLs ([RFC7172]) learned from decapsulating TRILL Data packets.

TRILLスイッチは、ローカルで学習したアドレスであれば、必要なものを容易にフラッシュできます。この文書は、TRILLデータパケットのカプセル化解除から学習された特定のVLANまたはFGL（[RFC7172]）のアドレス情報のフラッシュをリクエストするための、RBridgeチャネルサポートプロトコル[RFC7178]のメッセージを規定します。

2. Address Flush Message Details

2. Address Flushメッセージの詳細

The Address Flush message is an RBridge Channel protocol message [RFC7178].

Address Flushメッセージは、RBridgeチャネルプロトコルメッセージ[RFC7178]です。

The general structure of an RBridge Channel packet on a link between TRILL switches is shown in Figure 1. The Protocol field in the RBridge Channel Header gives the type of RBridge Channel packet and indicates how to interpret the Channel-Protocol-Specific Payload [RFC7178].

TRILLスイッチ間のリンク上のRBridgeチャネルパケットの一般的な構造を図1に示します。RBridgeチャネルヘッダーのProtocolフィールドは、RBridgeチャネルパケットのタイプを示し、Channel-Protocol-Specific Payloadをどのように解釈するかを示します[RFC7178]。

By default, an Address Flush RBridge Channel protocol message applies to addresses within the Data Label that appear right after the Inner Ethernet Addresses. Address Flush protocol messages are usually sent as multi-destination packets (TRILL Header M bit equal to one) so as to reach all TRILL switches offering end station service in the VLAN or FGL specified by that Data Label. Both multi-destination and unicast Address Flush messages SHOULD be sent at priority 6 since they are important control messages but are lower priority than control messages that establish or maintain adjacency.

デフォルトでは、Address Flush RBridgeチャネルプロトコルメッセージは、Inner Ethernet Addressesの直後に現れるデータラベル内のアドレスに適用されます。Address Flushプロトコルメッセージは通常、そのデータラベルで指定されたVLANまたはFGLでエンドステーションサービスを提供しているすべてのTRILLスイッチに届くように、マルチデスティネーションパケット（TRILLヘッダーのMビットが1）として送信されます。マルチデスティネーションとユニキャストのどちらのAddress Flushメッセージも、優先度6で送信されるべきです（SHOULD）。これは、これらのメッセージが重要な制御メッセージではあるものの、隣接関係を確立または維持する制御メッセージよりは優先度が低いためです。

Nevertheless:

ただし、次のとおりです。

  • There are provisions for optionally indicating the Data Label(s) to be flushed for cases where the Address Flush message is sent over a Management VLAN or the like.
  • An Address Flush message can be sent unicast, if it is desired to clear addresses at one TRILL switch only.
  • An Address Flush message can be sent selectively to the RBridges that have at least one access port configured as one of the VLANs or FGLs specified in the Address Flush message payload.
  • Address Flushメッセージが管理VLANなどを介して送信される場合のために、フラッシュするデータラベルを任意で示すための規定があります。
  • 1つのTRILLスイッチでのみアドレスを消去したい場合は、Address Flushメッセージをユニキャストで送信できます。
  • Address Flushメッセージは、Address Flushメッセージのペイロードで指定されたVLANまたはFGLのいずれかとして設定されたアクセスポートを少なくとも1つ持つRBridgeに対して、選択的に送信できます。

Implementations should consider logging Address Flush messages received with appropriate protections against packet storms.

実装は、パケットストームに対する適切な保護を講じたうえで、受信したAddress Flushメッセージをログに記録することを検討すべきです。

2.1. VLAN Block Only Case

2.1. VLANブロックのみの場合

Figure 2 expands the RBridge Channel Header and Channel-Protocol-Specific Payload from Figure 1 for the case of the VLAN-only-based Address Flush message. This form of the Address Flush message is optimized for flushing MAC addresses based on nickname and blocks of VLANs. 0x8946 is the Ethertype assigned by IEEE for the RBridge Channel protocol [RFC7178].

図2は、VLANのみに基づくAddress Flushメッセージの場合について、図1のRBridgeチャネルヘッダーとChannel-Protocol-Specific Payloadを展開したものです。この形式のAddress Flushメッセージは、ニックネームとVLANのブロックに基づいてMACアドレスをフラッシュするように最適化されています。0x8946は、RBridgeチャネルプロトコル[RFC7178]のためにIEEEによって割り当てられたEthertypeです。

The fields in Figure 2 related to the Address Flush message are as follows:

図2のフィールドのうち、Address Flushメッセージに関連するものは次のとおりです。

Channel Protocol:
The RBridge Channel Protocol value allocated for Address Flush (see Section 3).
K-nicks:
The number of nicknames listed as an unsigned integer. If this is zero, the ingress nickname in the TRILL Header [RFC6325] is considered to be the only nickname to which the message applies. If non-zero, it gives the number of nicknames listed right after K-nicks to which the message applies, and, in this non-zero case, the flush does not apply to the ingress nickname in the TRILL Header unless it is also listed. The message flushes address learning due to egressing TRILL Data packets that had an ingress nickname to which the message applies.
Nickname:
A listed nickname to which it is intended that the Address Flush message apply. If an unknown or reserved nickname occurs in the list, it is ignored, but the address flush operation is still executed with the other nicknames. If an incorrect nickname occurs in the list, so that some address learning is flushed that should not have been flushed, the network will still operate correctly; however, it will be less efficient as the incorrectly flushed learning is relearned.
K-VLBs:
The number of VLAN blocks present as an unsigned integer. If this byte is zero, the message is the more general format specified in Section 2.2. If it is non-zero, it gives the number of blocks of VLANs present. Thus, in the VLAN Block address flush case, K-VLBs will be at least one.
RESV:
4 reserved bits. MUST be sent as zero and ignored on receipt.
Start.VLAN, End.VLAN:
These 12-bit fields give the beginning and ending VLAN IDs of a block of VLANs. The block includes both the starting and ending values; so, a block of size one is indicated by setting End.VLAN equal to Start.VLAN. If Start.VLAN is 0x000, it is treated as if it was 0x001. If End.VLAN is 0xFFF, it is treated as if it was 0xFFE. If End.VLAN is smaller than Start.VLAN, considering both as unsigned integers, that VLAN block is ignored, but the address flush operation is still executed with other VLAN blocks in the message. VLAN blocks may overlap, in which case, the address flush operation is applicable to a VLAN covered by any one or more of the blocks in the message.
Channel Protocol：
Address Flushに割り当てられたRBridgeチャネルプロトコルの値（セクション3を参照）。
K-nicks：
列挙されたニックネームの数を表す符号なし整数。これが0の場合、TRILLヘッダー[RFC6325]内の入口ニックネームが、メッセージが適用される唯一のニックネームとみなされます。0以外の場合、K-nicksの直後に列挙された、メッセージが適用されるニックネームの数を示します。この0以外の場合には、TRILLヘッダー内の入口ニックネームも列挙されていない限り、フラッシュはその入口ニックネームには適用されません。このメッセージは、メッセージが適用される入口ニックネームを持つTRILLデータパケットの出口処理によって学習されたアドレスをフラッシュします。
Nickname：
Address Flushメッセージを適用することを意図した、列挙されたニックネーム。未知のニックネームや予約済みのニックネームがリストに現れた場合、それは無視されますが、アドレスフラッシュ操作はほかのニックネームで引き続き実行されます。誤ったニックネームがリストに現れ、フラッシュされるべきでなかったアドレス学習がフラッシュされた場合でも、ネットワークは引き続き正しく動作します。ただし、誤ってフラッシュされた学習が再学習されるため、効率は低下します。
K-VLBs：
存在するVLANブロックの数を表す符号なし整数。このバイトが0の場合、メッセージはセクション2.2で規定する、より汎用的な形式です。0以外の場合、存在するVLANのブロックの数を示します。したがって、VLANブロックによるアドレスフラッシュの場合、K-VLBsは少なくとも1になります。
RESV：
4ビットの予約済みビット。0として送信し、受信時には無視しなければなりません（MUST）。
Start.VLAN、End.VLAN：
これらの12ビットのフィールドは、VLANのブロックの開始と終了のVLAN IDを示します。ブロックには開始値と終了値の両方が含まれます。したがって、サイズ1のブロックは、End.VLANをStart.VLANと等しく設定することで示されます。Start.VLANが0x000の場合、0x001であるかのように扱われます。End.VLANが0xFFFの場合、0xFFEであるかのように扱われます。両方を符号なし整数とみなしてEnd.VLANがStart.VLANより小さい場合、そのVLANブロックは無視されますが、アドレスフラッシュ操作はメッセージ内のほかのVLANブロックで引き続き実行されます。VLANブロックは重なっていてもかまいません。その場合、アドレスフラッシュ操作は、メッセージ内のブロックのいずれか1つ以上に含まれるVLANに適用されます。

This message flushes all addresses in an applicable VLAN learned from egressing TRILL Data packets with an applicable nickname as ingress. To flush addresses for all VLANs, it is easy to specify a block covering all valid VLAN IDs (i.e., from 0x001 to 0xFFE).

このメッセージは、適用対象のニックネームを入口とするTRILLデータパケットの出口処理から学習された、適用対象のVLAN内のすべてのアドレスをフラッシュします。すべてのVLANのアドレスをフラッシュするには、有効なすべてのVLAN ID（つまり、0x001から0xFFEまで）を含むブロックを指定すれば簡単です。

2.2. Extensible Case

2.2. 拡張可能な場合

A more general form of the Address Flush message is provided to support flushing by FGL and more efficient encodings of VLANs and FGLs where using a set of contiguous blocks is cumbersome. It also supports optionally specifying the MAC addresses to clear. This form is extensible.

FGLによるフラッシュをサポートし、また連続するブロックの集合を使うと煩雑になる場合にVLANとFGLをより効率的にエンコードできるように、Address Flushメッセージのより汎用的な形式を提供します。この形式は、クリアするMACアドレスを任意で指定することもサポートします。この形式は拡張可能です。

The extensible case is indicated by a zero in the byte shown in Figure 2 as "K-VLBs" followed by other information encoded as TLVs.

拡張可能な場合は、図2で「K-VLBs」として示されているバイトが0であり、その後にTLVとしてエンコードされたほかの情報が続くことで示されます。

Channel Protocol, K-nicks, Nickname:
These fields are as specified in Section 2.1.
TLVs:
If the byte immediately before the TLVs field, which is the byte labeled "K-VLBs" in Figure 2, is zero, as shown in Figure 3, the remainder of the message consists of TLVs encoded as shown in Figure 4.

In an extensible Address Flush message, when the TLVs are parsed, those TLVs having unknown types are ignored by the receiving RBridge. There may be multiple instances of TLVs with the same Type in the same Address Flush message, and TLVs are not required to be in any particular order.

拡張可能なAddress Flushメッセージでは、TLVが解析されるときに、未知のタイプを持つTLVは受信側のRBridgeによって無視されます。同じAddress Flushメッセージ内に同じTypeのTLVが複数存在してもよく、TLVを特定の順序で並べる必要はありません。

  • All RBridges implementing the Address Flush RBridge Channel protocol message MUST implement types 1 and 2, the VLAN types, and Type 6, which indicates addresses are to be flushed for all Data Labels.
  • RBridges that implement the Address Flush message and implement FGL ingress/egress MUST implement types 3, 4, and 5, the FGL types. (An RBridge that is merely FGL safe [RFC7172], but cannot egress FGL TRILL Data packets, SHOULD ignore the FGL types, as it will not learn any FGL-scoped MAC addresses from the data plane.)
  • RBridges that implement the Address Flush message SHOULD implement types 7 and 8 so that specific MAC addresses can be flushed. If they do not, the effect will be to flush all MAC addresses for the indicated Data Labels, which may be inefficient as any MAC addresses not intended to be flushed will have to be relearned.
  • Address Flush RBridgeチャネルプロトコルメッセージを実装するすべてのRBridgeは、VLANのタイプであるタイプ1と2、およびすべてのデータラベルについてアドレスをフラッシュすることを示すタイプ6を実装しなければなりません（MUST）。
  • Address Flushメッセージを実装し、かつFGLの入口処理／出口処理を実装するRBridgeは、FGLのタイプであるタイプ3、4、5を実装しなければなりません（MUST）。（単にFGLセーフ[RFC7172]であるだけで、FGLのTRILLデータパケットを出口処理できないRBridgeは、データプレーンからFGLをスコープとするMACアドレスを学習することがないため、FGLのタイプを無視すべきです（SHOULD）。）
  • Address Flushメッセージを実装するRBridgeは、特定のMACアドレスをフラッシュできるように、タイプ7と8を実装すべきです（SHOULD）。実装しない場合、示されたデータラベルのすべてのMACアドレスをフラッシュすることになります。フラッシュを意図していなかったMACアドレスも再学習しなければならなくなるため、これは非効率になる可能性があります。

The parsing of the TLVs by a receiving RBridge results in three pieces of information:

受信側のRBridgeがTLVを解析すると、次の3つの情報が得られます。

  1. a flag indicating whether one or more Type 6 TLVs (All Data Labels) were encountered;
  2. a set of Data Labels accumulated from VLAN and/or FGL specifying TLVs in the message; and,
  3. if the MAC address TLV types are implemented, a set of MAC addresses accumulated from MAC-address-specifying TLVs in the message.
  1. タイプ6のTLV（All Data Labels）が1つ以上現れたかどうかを示すフラグ
  2. メッセージ内のVLANやFGLを指定するTLVから集めたデータラベルの集合
  3. MACアドレスのTLVタイプが実装されている場合は、メッセージ内のMACアドレスを指定するTLVから集めたMACアドレスの集合

VLANs/FGLs might be indicated more than once due to overlapping blocks or the like, and a VLAN/FGL is included in the above set of VLANs/FGLs if it occurs in any TLV in the Address Flush message. A MAC address might be indicated more than once due to overlapping blocks or the like, and a particular MAC address is included in the above set of MAC addresses if it occurs in any TLV in the Address Flush message.

VLAN／FGLは、ブロックの重なりなどにより複数回示される場合があり、Address Flushメッセージ内のいずれかのTLVに現れたVLAN／FGLは、上記のVLAN／FGLの集合に含まれます。MACアドレスは、ブロックの重なりなどにより複数回示される場合があり、Address Flushメッセージ内のいずれかのTLVに現れた特定のMACアドレスは、上記のMACアドレスの集合に含まれます。

After the above information has been accumulated by parsing the TLVs, three sets are derived as described below: a set of nicknames, a set of Data Labels, and a set of MAC addresses. The address flush operation at the receiver applies to the cross product of these derived sets. That is, a { Data Label, MAC address, nickname } triple is flushed if and only if the Data Label matches an element in the derived set of Data Labels, the MAC address matches an element in the derived set of MAC address, and the nickname matches an element in the derived set of nicknames. In the case of Data Labels and MAC addresses, a special value of the set, {ALL}, is permitted, which matches all values.

TLVを解析して上記の情報を集めた後、以下で説明するように、ニックネームの集合、データラベルの集合、MACアドレスの集合という3つの集合を導出します。受信側でのアドレスフラッシュ操作は、これらの導出された集合の直積に適用されます。つまり、{ データラベル, MACアドレス, ニックネーム }の3つ組は、データラベルが導出されたデータラベルの集合の要素と一致し、MACアドレスが導出されたMACアドレスの集合の要素と一致し、かつニックネームが導出されたニックネームの集合の要素と一致する場合に限り、フラッシュされます。データラベルとMACアドレスの場合は、すべての値と一致する集合の特別な値{ALL}が認められています。

The sets are derived as follows:

集合は次のように導出されます。

Data Labels set:
If the Type 6 TLV has been encountered, the set is {ALL}, else, if any Data Labels have been accumulated by processing Data Label TLVs (Types 1, 2, 3, 4, and 5), the set is those accumulated Data Labels, else, the Data Labels set is null and the Address Flush message does nothing.
MAC Addresses set:
In the receiver does not implement the MAC address types (Types 7 and 8) or it does implement those types but no MAC addresses are accumulated in parsing the TLVs, then the MAC Address set is {ALL}, else, the MAC Addresses set is the set of MAC addresses accumulated in processing the TLVs.
Nicknames set:
If the K-nicks field in the Address Flush message was zero, then the ingress nickname in the TRILL Header of the message is the sole nickname set member, else, the nicknames set members are the K-nicks nicknames listed in the Address Flush message.
データラベルの集合：
タイプ6のTLVが現れた場合、集合は{ALL}です。そうでなく、データラベルのTLV（タイプ1、2、3、4、5）の処理によって何らかのデータラベルが集められた場合、集合はそれらの集められたデータラベルです。そうでない場合、データラベルの集合は空であり、Address Flushメッセージは何もしません。
MACアドレスの集合：
受信者がMACアドレスのタイプ（タイプ7と8）を実装していない場合、またはそれらのタイプを実装しているがTLVの解析でMACアドレスが1つも集められなかった場合、MACアドレスの集合は{ALL}です。そうでない場合、MACアドレスの集合は、TLVの処理で集められたMACアドレスの集合です。
ニックネームの集合：
Address FlushメッセージのK-nicksフィールドが0だった場合、メッセージのTRILLヘッダー内の入口ニックネームが、ニックネームの集合の唯一の要素です。そうでない場合、ニックネームの集合の要素は、Address Flushメッセージに列挙されたK-nicks個のニックネームです。

The various formats below are provided for encoding efficiency. A block of values is most efficient when there are a number of consecutive values. A bit map is most efficient if there are scattered values within a limited range. And a list of single values is most efficient if there are widely scattered values.

以下のさまざまな形式は、エンコーディングの効率のために用意されています。値のブロックは、連続する値が多数ある場合に最も効率的です。ビットマップは、限られた範囲内に値が散在している場合に最も効率的です。そして、単一の値のリストは、値が広く散在している場合に最も効率的です。

2.2.2. Bit Map of VLANs

2.2.2. VLANのビットマップ

If the TLV Type is 2, the value is a bit map of VLANs as follows:

TLVのTypeが2の場合、値は次のようなVLANのビットマップです。

   +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
   | Type = 2      | Length        |
   +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-
   | RESV  | Start.VLAN            | Bits...
   +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-

   +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
   | Type = 2      | Length        |
   +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-
   | RESV  | Start.VLAN            | Bits...
   +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-

The value portion of the TLV begins with two bytes having the 12-bit starting VLAN ID right justified (the top 4 bits are as specified in Section 2.1 RESV). This is followed by bytes with one bit per VLAN ID. The high order bit of the first byte is for VLAN N. The next-to-the-highest order bit is for VLAN N+1. The low order bit of the first byte is for VLAN N+7. The high order bit of the second byte, if there is a second byte, is for VLAN N+8, and so on. If that bit is a one, the Address Flush message applies to that VLAN. If that bit is a zero, then addresses that have been learned in that VLAN are not flushed. Note that Length MUST be at least 2. If Length is 0 or 1, the TLV is corrupt and the Address Flush message MUST be discarded. VLAN IDs do not wrap around. If there are enough bytes so that some bits correspond to VLAN ID 0xFFF or higher, those bits are ignored, but the message is still processed for bits corresponding to valid VLAN IDs.

TLVの値の部分は、12ビットの開始VLAN IDを右詰めで格納した2バイトで始まります（上位4ビットはセクション2.1のRESVで規定するとおりです）。その後に、VLAN IDごとに1ビットを持つバイトが続きます。最初のバイトの最上位ビットはVLAN N用です。最上位から2番目のビットはVLAN N+1用です。最初のバイトの最下位ビットはVLAN N+7用です。2番目のバイトがある場合、その最上位ビットはVLAN N+8用であり、以下同様です。そのビットが1の場合、Address FlushメッセージはそのVLANに適用されます。そのビットが0の場合、そのVLANで学習されたアドレスはフラッシュされません。Lengthは少なくとも2でなければなりません（MUST）。Lengthが0または1の場合、TLVは破損しており、Address Flushメッセージを破棄しなければなりません（MUST）。VLAN IDは折り返しません。バイトが十分にあって、一部のビットがVLAN ID 0xFFF以上に対応する場合、それらのビットは無視されますが、有効なVLAN IDに対応するビットについてはメッセージが引き続き処理されます。

4. Security Considerations

4. セキュリティーに関する考慮事項

The Address Flush RBridge Channel Protocol itself provides no security assurances or features. However, Address Flush protocol messages can be secured by use of the RBridge Channel Header Extension [RFC7978]. It is RECOMMENDED that all RBridges that implement the Address Flush message be configured to ignore such messages unless they have been secured with an RBridge Channel Header Extension that meets local security policy.

Address Flush RBridgeチャネルプロトコル自体は、セキュリティーの保証や機能を何も提供しません。ただし、Address Flushプロトコルメッセージは、RBridgeチャネルヘッダー拡張[RFC7978]を使用して保護できます。Address Flushメッセージを実装するすべてのRBridgeは、ローカルのセキュリティーポリシーを満たすRBridgeチャネルヘッダー拡張で保護されていない限り、そのようなメッセージを無視するように設定することが推奨されます（RECOMMENDED）。

If RBridges receiving Address Flush messages do not require them to be at least authenticated, they are relatively easy to forge. In that case, such forged Address Flush messages can reduce network efficiency, by purging useful learned information that will have to be relearned. This provides a denial-of-service attack, but cannot cause incorrect operation in the sense that it cannot cause a frame to be improperly delivered.

Address Flushメッセージを受信するRBridgeが、そのメッセージに少なくとも認証を要求しない場合、メッセージの偽造は比較的容易です。その場合、そのような偽造されたAddress Flushメッセージは、再学習が必要になる有用な学習済み情報をパージすることによって、ネットワークの効率を低下させる可能性があります。これはサービス拒否攻撃をもたらしますが、フレームを不適切に配送させることはできないという意味で、誤った動作を引き起こすことはできません。

See [RFC7178] for general RBridge Channel Security Considerations.

RBridgeチャネルのセキュリティーに関する一般的な考慮事項については、[RFC7178]を参照してください。

See [RFC6325] for general TRILL Security Considerations.

TRILLのセキュリティーに関する一般的な考慮事項については、[RFC6325]を参照してください。
