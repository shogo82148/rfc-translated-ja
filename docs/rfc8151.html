Use Cases for Data Center Network Virtualization Overlay Networks

RFC 8151

データセンターのネットワーク仮想化オーバーレイネットワークのユースケース

Abstract

概要

This document describes Network Virtualization over Layer 3 (NVO3) use cases that can be deployed in various data centers and serve different data-center applications.

この文書は、さまざまなデータセンターに展開でき、異なるデータセンターアプリケーションに役立つ、レイヤー3上のネットワーク仮想化（Network Virtualization over Layer 3：NVO3）のユースケースについて説明します。

1. Introduction

1. はじめに

Server virtualization has changed the Information Technology (IT) industry in terms of the efficiency, cost, and speed of providing new applications and/or services such as cloud applications. However, traditional data center (DC) networks have limits in supporting cloud applications and multi-tenant networks [RFC7364]. The goal of data center Network Virtualization over Layer 3 (NVO3) networks is to decouple the communication among tenant systems from DC physical infrastructure networks and to allow one physical network infrastructure to:

サーバーの仮想化は、クラウドアプリケーションなどの新しいアプリケーションやサービスを提供する際の効率、コスト、速度の面で、情報技術（Information Technology：IT）産業を変えてきました。しかし、従来のデータセンター（DC）ネットワークには、クラウドアプリケーションやマルチテナントネットワークをサポートするうえで限界があります[RFC7364]。データセンターにおけるレイヤー3上のネットワーク仮想化（Network Virtualization over Layer 3：NVO3）ネットワークの目標は、テナントシステム間の通信をDCの物理インフラストラクチャーネットワークから切り離し、1つの物理ネットワークインフラストラクチャーで次のことを可能にすることです。

  • carry many NVO3 virtual networks and isolate the traffic of different NVO3 virtual networks on a physical network.
  • provide independent address space in individual NVO3 virtual network such as Media Access Control (MAC) and IP.
  • Support flexible Virtual Machines (VMs) and/or workload placement including the ability to move them from one server to another without requiring VM address changes and physical infrastructure network configuration changes, and the ability to perform a "hot move" with no disruption to the live application running on those VMs.
  • 多数のNVO3仮想ネットワークを運び、物理ネットワーク上で異なるNVO3仮想ネットワークのトラフィックを分離する。
  • 個々のNVO3仮想ネットワークに、メディアアクセス制御（Media Access Control：MAC）やIPなどの独立したアドレス空間を提供する。
  • 仮想マシン（Virtual Machine：VM）やワークロードの柔軟な配置をサポートする。これには、VMのアドレスの変更や物理インフラストラクチャーネットワークの設定の変更を必要とせずに、VMやワークロードをあるサーバーから別のサーバーに移動する能力と、それらのVM上で稼働中のアプリケーションを中断させずに「ホットムーブ（hot move）」を行う能力が含まれる。

These characteristics of NVO3 virtual networks (VNs) help address the issues that cloud applications face in data centers [RFC7364].

NVO3仮想ネットワーク（Virtual Network：VN）のこうした特性は、クラウドアプリケーションがデータセンターで直面する問題[RFC7364]への対処に役立ちます。

Hosts in one NVO3 VN may communicate with hosts in another NVO3 VN that is carried by the same physical network, or different physical network, via a gateway. The use-case examples for the latter are as follows:

あるNVO3 VN内のホストは、同じ物理ネットワークまたは異なる物理ネットワークによって運ばれる別のNVO3 VN内のホストと、ゲートウェイを介して通信することがあります。後者のユースケースの例は次のとおりです。

  1. DCs that migrate toward an NVO3 solution will be done in steps, where a portion of tenant systems in a VN are on virtualized servers while others exist on a LAN.
  2. many DC applications serve Internet users who are on different physical networks;
  3. some applications are CPU bound, such as Big Data analytics, and may not run on virtualized resources.
  1. NVO3ソリューションへ移行するDCでは、移行が段階的に行われます。その間、VN内のテナントシステムの一部は仮想化されたサーバー上にあり、それ以外はLAN上に存在します。
  2. 多くのDCアプリケーションは、異なる物理ネットワーク上にいるインターネットユーザーにサービスを提供します。
  3. ビッグデータ分析のように、CPUがボトルネックとなるアプリケーションもあり、そうしたアプリケーションは仮想化されたリソース上では実行できない場合があります。

The inter-VN policies are usually enforced by the gateway.

VN間のポリシーは、通常、ゲートウェイによって適用されます。

This document describes general NVO3 VN use cases that apply to various data centers. The use cases described here represent the DC provider's interests and vision for their cloud services. The document groups the use cases into three categories from simple to sophisticated in terms of implementation. However, the implementation details of these use cases are outside the scope of this document. These three categories are described below:

この文書では、さまざまなデータセンターに当てはまる一般的なNVO3 VNのユースケースについて説明します。ここで説明するユースケースは、DCプロバイダーのクラウドサービスに対する関心とビジョンを表しています。この文書では、ユースケースを、実装の観点から単純なものから高度なものへと3つのカテゴリーに分類します。ただし、これらのユースケースの実装の詳細は、この文書の範囲外です。3つのカテゴリーを以下に示します。

  • Basic NVO3 VNs (Section 2). All Tenant Systems (TSs) in the network are located within the same DC. The individual networks can be either Layer 2 (L2) or Layer 3 (L3). The number of NVO3 VNs in a DC is much larger than the number that traditional VLAN-based virtual networks [IEEE802.1Q] can support.
  • A virtual network that spans across multiple DCs and/or to customer premises where NVO3 virtual networks are constructed and interconnect other virtual or physical networks outside the DC. An enterprise customer may use a traditional carrier-grade VPN or an IPsec tunnel over the Internet to communicate with its systems in the DC. This is described in Section 3.
  • DC applications or services require an advanced network that contains several NVO3 virtual networks that are interconnected by gateways. Three scenarios are described in Section 4: (1) supporting multiple technologies; (2) constructing several virtual networks as a tenant network; and (3) applying NVO3 to a virtual Data Center (vDC).
  • 基本的なNVO3 VN（セクション2）。ネットワーク内のすべてのテナントシステム（Tenant System：TS）が同じDC内に配置されます。個々のネットワークは、レイヤー2（L2）とレイヤー3（L3）のどちらでもかまいません。DC内のNVO3 VNの数は、従来のVLANベースの仮想ネットワーク[IEEE802.1Q]がサポートできる数よりもはるかに多くなります。
  • 複数のDCにまたがる仮想ネットワーク、および／または顧客の構内にまで及ぶ仮想ネットワーク。そこではNVO3仮想ネットワークが構築され、DC外部の他の仮想ネットワークや物理ネットワークと相互接続します。企業顧客は、DC内の自社のシステムと通信するために、従来のキャリアグレードのVPNや、インターネット上のIPsecトンネルを使用することがあります。これについてはセクション3で説明します。
  • DCのアプリケーションやサービスが、ゲートウェイによって相互接続された複数のNVO3仮想ネットワークを含む高度なネットワークを必要とする場合。セクション4では、(1)複数の技術のサポート、(2)テナントネットワークとしての複数の仮想ネットワークの構築、(3)仮想データセンター（virtual Data Center：vDC）へのNVO3の適用、の3つのシナリオについて説明します。

The document uses the architecture reference model defined in [RFC7365] to describe the use cases.

この文書では、ユースケースを説明するために、[RFC7365]で定義されたアーキテクチャー参照モデルを使用します。

1.2. NVO3 Background

1.2. NVO3の背景

An NVO3 virtual network is in a DC that is implemented based on the NVO3 architecture [RFC8014]. This architecture is often referred to as an overlay architecture. The traffic carried by an NVO3 virtual network is encapsulated at a Network Virtualization Edge (NVE) [RFC8014] and carried by a tunnel to another NVE where the traffic is decapsulated and sent to a destination Tenant System (TS). The NVO3 architecture decouples NVO3 virtual networks from the DC physical network configuration. The architecture uses common tunnels to carry NVO3 traffic that belongs to multiple NVO3 virtual networks.

NVO3仮想ネットワークは、NVO3アーキテクチャー[RFC8014]に基づいて実装された、DC内の仮想ネットワークです。このアーキテクチャーは、しばしばオーバーレイアーキテクチャーと呼ばれます。NVO3仮想ネットワークによって運ばれるトラフィックは、ネットワーク仮想化エッジ（Network Virtualization Edge：NVE）[RFC8014]でカプセル化され、トンネルによって別のNVEに運ばれます。そのNVEでトラフィックはカプセル化解除され、宛先のテナントシステム（TS）に送信されます。NVO3アーキテクチャーは、NVO3仮想ネットワークをDCの物理ネットワークの設定から切り離します。このアーキテクチャーは、複数のNVO3仮想ネットワークに属するNVO3トラフィックを運ぶために、共通のトンネルを使用します。

An NVO3 virtual network may be an L2 or L3 domain. The network provides switching (L2) or routing (L3) capability to support host (i.e., TS) communications. An NVO3 virtual network may be required to carry unicast traffic and/or multicast or broadcast/unknown-unicast (for L2 only) traffic to/from TSs. There are several ways to transport NVO3 virtual network Broadcast, Unknown Unicast, and Multicast (BUM) traffic [NVO3MCAST].

NVO3仮想ネットワークは、L2ドメインの場合もL3ドメインの場合もあります。このネットワークは、ホスト（すなわちTS）の通信をサポートするために、スイッチング（L2）またはルーティング（L3）の能力を提供します。NVO3仮想ネットワークは、TSとの間で、ユニキャストトラフィック、および／またはマルチキャストトラフィックやブロードキャスト／未知ユニキャスト（L2のみ）トラフィックを運ぶことを求められる場合があります。NVO3仮想ネットワークのブロードキャスト、未知ユニキャスト、マルチキャスト（Broadcast, Unknown Unicast, and Multicast：BUM）トラフィックを転送する方法はいくつかあります[NVO3MCAST]。

An NVO3 virtual network provides communications among TSs in a DC. A TS can be a physical server/device or a VM on a server end-device [RFC7365].

NVO3仮想ネットワークは、DC内のTS間の通信を提供します。TSは、物理サーバー／デバイスの場合もあれば、サーバーエンドデバイス上のVMの場合もあります[RFC7365]。

2. DC with a Large Number of Virtual Networks

2. 多数の仮想ネットワークを持つDC

A DC provider often uses NVO3 virtual networks for internal applications where each application runs on many VMs or physical servers and the provider requires applications to be segregated from each other. A DC may run a larger number of NVO3 virtual networks to support many applications concurrently, where a traditional VLAN solution based on IEEE 802.1Q is limited to 4094 VLANs.

DCプロバイダーは、内部アプリケーションのためにNVO3仮想ネットワークをよく使用します。そこでは、各アプリケーションが多数のVMまたは物理サーバー上で実行され、プロバイダーはアプリケーションを互いに分離することを求めます。DCは、多数のアプリケーションを同時にサポートするために、より多くのNVO3仮想ネットワークを運用することがあります。一方、IEEE 802.1Qに基づく従来のVLANソリューションでは、VLANの数は4094に制限されます。

Applications running on VMs may require a different quantity of computing resources, which may result in a computing-resource shortage on some servers and other servers being nearly idle. A shortage of computing resources may impact application performance. DC operators desire VM or workload movement for resource-usage optimization. VM dynamic placement and mobility results in frequent changes of the binding between a TS and an NVE. The TS reachability update mechanisms should take significantly less time than the typical retransmission Timeout window of a reliable transport protocol such as TCP and Stream Control Transmission Protocol (SCTP), so that endpoints' transport connections won't be impacted by a TS becoming bound to a different NVE. The capability of supporting many TSs in a virtual network and many virtual networks in a DC is critical for an NVO3 solution.

VM上で実行されるアプリケーションが必要とするコンピューティングリソースの量はさまざまであるため、一部のサーバーではコンピューティングリソースが不足し、他のサーバーはほとんどアイドル状態になることがあります。コンピューティングリソースの不足は、アプリケーションのパフォーマンスに影響を与える可能性があります。DC運用者は、リソースの使用を最適化するために、VMやワークロードを移動することを望みます。VMの動的な配置とモビリティーにより、TSとNVEの間のバインディングが頻繁に変化します。TSが別のNVEにバインドされることによってエンドポイントのトランスポートコネクションが影響を受けないように、TSの到達可能性を更新するメカニズムにかかる時間は、TCPやStream Control Transmission Protocol（SCTP）などの信頼性のあるトランスポートプロトコルの典型的な再送タイムアウトウィンドウよりも大幅に短くするべきです。1つの仮想ネットワーク内の多数のTSと、1つのDC内の多数の仮想ネットワークをサポートする能力は、NVO3ソリューションにとって極めて重要です。

When NVO3 virtual networks segregate VMs belonging to different applications, DC operators can independently assign MAC and/or IP address space to each virtual network. This addressing is more flexible than requiring all hosts in all NVO3 virtual networks to share one address space. In contrast, typical use of IEEE 802.1Q VLANs requires a single common MAC address space.

NVO3仮想ネットワークが異なるアプリケーションに属するVMを分離する場合、DC運用者は、各仮想ネットワークにMACアドレス空間やIPアドレス空間を独立して割り当てることができます。このアドレス割り当ては、すべてのNVO3仮想ネットワーク内のすべてのホストが1つのアドレス空間を共有することを求めるよりも柔軟です。これに対して、IEEE 802.1Q VLANの典型的な使い方では、単一の共通MACアドレス空間が必要です。

3. DC NVO3 Virtual Network and External Network Interconnection

3. DCのNVO3仮想ネットワークと外部ネットワークの相互接続

Many customers (enterprises or individuals) who utilize a DC provider's compute and storage resources to run their applications need to access their systems hosted in a DC through Internet or Service Providers' Wide Area Networks (WAN). A DC provider can construct a NVO3 virtual network that provides connectivity to all the resources designated for a customer, and it allows the customer to access the resources via a virtual GateWay (vGW). WAN connectivity to the vGW can be provided by VPN technologies such as IPsec VPNs [RFC4301] and BGP/MPLS IP VPNs [RFC4364].

DCプロバイダーのコンピューティングリソースやストレージリソースを利用して自分のアプリケーションを実行する多くの顧客（企業または個人）は、インターネットやサービスプロバイダーの広域ネットワーク（Wide Area Network：WAN）を通じて、DCでホストされている自分のシステムにアクセスする必要があります。DCプロバイダーは、顧客向けに指定されたすべてのリソースへの接続性を提供するNVO3仮想ネットワークを構築でき、そのネットワークにより、顧客は仮想ゲートウェイ（virtual GateWay：vGW）を介してリソースにアクセスできます。vGWへのWAN接続性は、IPsec VPN[RFC4301]やBGP/MPLS IP VPN[RFC4364]などのVPN技術によって提供できます。

If a virtual network spans multiple DC sites, one design using NVO3 is to allow the network to seamlessly span the sites without DC gateway routers' termination. In this case, the tunnel between a pair of NVEs can be carried within other intermediate tunnels over the Internet or other WANs, or an intra-DC tunnel and inter-DC tunnel(s) can be stitched together to form an end-to-end tunnel between the pair of NVEs that are in different DC sites. Both cases will form one NVO3 virtual network across multiple DC sites.

仮想ネットワークが複数のDCサイトにまたがる場合、NVO3を使用する設計の1つは、DCゲートウェイルーターで終端することなく、ネットワークがサイト間をシームレスにまたがれるようにすることです。この場合、NVEのペア間のトンネルを、インターネットや他のWAN上の別の中間トンネル内で運ぶことも、DC内トンネルとDC間トンネルをつなぎ合わせて、異なるDCサイトにあるNVEのペア間のエンドツーエンドトンネルを形成することもできます。どちらの場合も、複数のDCサイトにまたがる1つのNVO3仮想ネットワークが形成されます。

Two use cases are described in the following sections.

以降のセクションでは、2つのユースケースについて説明します。

3.1. DC NVO3 Virtual Network Access via the Internet

3.1. インターネット経由でのDCのNVO3仮想ネットワークへのアクセス

A customer can connect to an NVO3 virtual network via the Internet in a secure way. Figure 1 illustrates an example of this case. The NVO3 virtual network has an instance at NVE1 and NVE2, and the two NVEs are connected via an IP tunnel in the DC. A set of TSs are attached to NVE1 on a server. NVE2 resides on a DC Gateway device. NVE2 terminates the tunnel and uses the VN Identifier (VNID) on the packet to pass the packet to the corresponding vGW entity on the DC GW (the vGW is the default gateway for the virtual network). A customer can access their systems, i.e., TS1 or TSn, in the DC via the Internet by using an IPsec tunnel [RFC4301]. The IPsec tunnel is configured between the vGW and the customer gateway at the customer site. Either a static route or Internal Border Gateway Protocol (IBGP) may be used for prefix advertisement. The vGW provides IPsec functionality such as authentication scheme and encryption; IBGP traffic is carried within the IPsec tunnel. Some vGW features are listed below:

顧客は、インターネット経由で安全な方法でNVO3仮想ネットワークに接続できます。図1にこのケースの例を示します。NVO3仮想ネットワークはNVE1とNVE2にインスタンスを持ち、2つのNVEはDC内でIPトンネルを介して接続されています。TSの集合が、サーバー上のNVE1に接続されています。NVE2はDCゲートウェイデバイス上にあります。NVE2はトンネルを終端し、パケット上のVN識別子（VN Identifier：VNID）を使用して、DC GW上の対応するvGWエンティティー（vGWは仮想ネットワークのデフォルトゲートウェイです）にパケットを渡します。顧客は、IPsecトンネル[RFC4301]を使用して、インターネット経由でDC内の自分のシステム（すなわちTS1やTSn）にアクセスできます。IPsecトンネルは、vGWと顧客サイトの顧客ゲートウェイとの間に設定されます。プレフィックスの広告には、静的経路またはInternal Border Gateway Protocol（IBGP）のどちらかを使用できます。vGWは認証方式や暗号化などのIPsec機能を提供し、IBGPトラフィックはIPsecトンネル内で運ばれます。vGWの機能のいくつかを以下に示します。

  • The vGW maintains the TS/NVE mappings and advertises the TS prefix to the customer via static route or IBGP.
  • Some vGW functions such as the firewall and load-balancer (LB) can be performed by locally attached network appliance devices.
  • If the NVO3 virtual network uses different address space than external users, then the vGW needs to provide the NAT function.
  • More than one IPsec tunnel can be configured for redundancy.
  • The vGW can be implemented on a server or VM. In this case, IP tunnels or IPsec tunnels can be used over the DC infrastructure.
  • DC operators need to construct a vGW for each customer.
  • vGWはTSとNVEのマッピングを維持し、静的経路またはIBGPを介して顧客にTSのプレフィックスを広告します。
  • ファイアウォールやロードバランサー（load-balancer：LB）など、vGWの一部の機能は、ローカルに接続されたネットワークアプライアンスデバイスで実行できます。
  • NVO3仮想ネットワークが外部ユーザーとは異なるアドレス空間を使用する場合、vGWはNAT機能を提供する必要があります。
  • 冗長性のために、複数のIPsecトンネルを設定できます。
  • vGWはサーバーやVM上に実装できます。この場合、DCインフラストラクチャー上でIPトンネルやIPsecトンネルを使用できます。
  • DC運用者は、顧客ごとにvGWを構築する必要があります。

3.2. DC NVO3 Virtual Network and SP WAN VPN Interconnection

3.2. DCのNVO3仮想ネットワークとSPのWAN VPNの相互接続

In this case, an enterprise customer wants to use a Service Provider (SP) WAN VPN [RFC4364] [RFC7432] to interconnect its sites with an NVO3 virtual network in a DC site. The SP constructs a VPN for the enterprise customer. Each enterprise site peers with an SP PE. The DC provider and VPN SP can build an NVO3 virtual network and a WAN VPN independently, and then interconnect them via a local link or a tunnel between the DC GW and WAN PE devices. The control plane interconnection options between the DC and WAN are described in [RFC4364]. Using the option "a" specified in [RFC4364] with VRF-LITE [VRF-LITE], both ASBRs, i.e., DC GW and SP PE, maintain a routing/forwarding table (VRF). Using the option "b" specified in [RFC4364], the DC ASBR and SP ASBR do not maintain the VRF table; they only maintain the NVO3 virtual network and VPN identifier mappings, i.e., label mapping, and swap the label on the packets in the forwarding process. Both option "a" and option "b" allow the se of NVO3 VNs and VPNs using their own identifiers, and two identifiers are mapped at the DC GW. With the option "c" in [RFC4364], the VN and VPN use the same identifier and both ASBRs perform the tunnel stitching, i.e., tunnel segment mapping. Each option has pros and cons [RFC4364] and has been deployed in SP networks depending on the application requirements. BGP is used in these options for route distribution between DCs and SP WANs. Note that if the DC is the SP's DC, the DC GW and SP PE can be merged into one device that performs the interworking of the VN and VPN within an Autonomous System.

このケースでは、企業顧客は、サービスプロバイダー（Service Provider：SP）のWAN VPN[RFC4364] [RFC7432]を使用して、自社のサイトをDCサイト内のNVO3仮想ネットワークと相互接続することを望みます。SPは企業顧客のためにVPNを構築します。企業の各サイトは、SPのPEとピアリングします。DCプロバイダーとVPNのSPは、NVO3仮想ネットワークとWAN VPNをそれぞれ独立して構築し、その後、DC GWとWAN PEデバイスの間のローカルリンクまたはトンネルを介してそれらを相互接続できます。DCとWANの間のコントロールプレーンの相互接続のオプションは、[RFC4364]で説明されています。[RFC4364]で規定されたオプション「a」をVRF-LITE[VRF-LITE]とともに使用する場合、両方のASBR（すなわちDC GWとSP PE）がルーティング／転送テーブル（VRF）を維持します。[RFC4364]で規定されたオプション「b」を使用する場合、DC ASBRとSP ASBRはVRFテーブルを維持しません。これらのASBRは、NVO3仮想ネットワークとVPNの識別子のマッピング（すなわちラベルのマッピング）だけを維持し、転送処理においてパケット上のラベルを交換します。オプション「a」とオプション「b」はどちらも、NVO3 VNとVPNがそれぞれ独自の識別子を使用することを可能にし、2つの識別子はDC GWでマッピングされます。[RFC4364]のオプション「c」では、VNとVPNは同じ識別子を使用し、両方のASBRがトンネルのつなぎ合わせ（すなわちトンネルセグメントのマッピング）を行います。各オプションには長所と短所があり[RFC4364]、アプリケーションの要件に応じてSPのネットワークに展開されてきました。これらのオプションでは、DCとSPのWANの間の経路配布にBGPが使用されます。DCがSPのDCである場合、DC GWとSP PEを1つのデバイスに統合し、そのデバイスで自律システム内のVNとVPNのインターワーキングを行えることに注意してください。

These solutions allow the enterprise networks to communicate with the tenant systems attached to the NVO3 virtual network in the DC without interfering with the DC provider's underlying physical networks and other NVO3 virtual networks in the DC. The enterprise can use its own address space in the NVO3 virtual network. The DC provider can manage which VM and storage elements attach to the NVO3 virtual network. The enterprise customer manages which applications run on the VMs without knowing the location of the VMs in the DC. (See Section 4 for more information.)

これらのソリューションにより、企業ネットワークは、DCプロバイダーの下位の物理ネットワークやDC内の他のNVO3仮想ネットワークに干渉することなく、DC内のNVO3仮想ネットワークに接続されたテナントシステムと通信できます。企業は、NVO3仮想ネットワーク内で独自のアドレス空間を使用できます。DCプロバイダーは、どのVMとストレージ要素をNVO3仮想ネットワークに接続するかを管理できます。企業顧客は、DC内のVMの位置を知ることなく、どのアプリケーションをVM上で実行するかを管理します（詳細についてはセクション4を参照してください）。

Furthermore, in this use case, the DC operator can move the VMs assigned to the enterprise from one sever to another in the DC without the enterprise customer being aware, i.e., with no impact on the enterprise's "live" applications. Such advanced technologies bring DC providers great benefits in offering cloud services, but add some requirements for NVO3 [RFC7364] as well.

さらに、このユースケースでは、DC運用者は、企業顧客に気付かれることなく、すなわち企業の「稼働中の」アプリケーションに影響を与えることなく、企業に割り当てられたVMをDC内のあるサーバーから別のサーバーに移動できます。このような高度な技術は、クラウドサービスを提供するうえでDCプロバイダーに大きな利益をもたらしますが、同時にNVO3に対していくつかの要件を追加します[RFC7364]。

4. DC Applications Using NVO3

4. NVO3を使用するDCアプリケーション

NVO3 technology provides DC operators with the flexibility in designing and deploying different applications in an end-to-end virtualization overlay environment. The operators no longer need to worry about the constraints of the DC physical network configuration when creating VMs and configuring a network to connect them. A DC provider may use NVO3 in various ways, in conjunction with other physical networks and/or virtual networks in the DC. This section highlights some use cases for this goal.

NVO3技術は、エンドツーエンドの仮想化オーバーレイ環境においてさまざまなアプリケーションを設計し展開するうえでの柔軟性を、DC運用者に提供します。運用者は、VMを作成し、それらを接続するネットワークを設定する際に、DCの物理ネットワークの設定による制約を気にする必要がなくなります。DCプロバイダーは、DC内の他の物理ネットワークや仮想ネットワークと組み合わせて、さまざまな方法でNVO3を使用できます。このセクションでは、この目的のためのいくつかのユースケースを取り上げます。

4.1. Supporting Multiple Technologies

4.1. 複数の技術のサポート

Servers deployed in a large DC are often installed at different times, and they may have different capabilities/features. Some servers may be virtualized, while others may not; some may be equipped with virtual switches, while others may not. For the servers equipped with Hypervisor-based virtual switches, some may support a standardized NVO3 encapsulation, some may not support any encapsulation, and some may support a documented encapsulation protocol (e.g., Virtual eXtensible Local Area Network (VXLAN) [RFC7348] and Network Virtualization using Generic Routing Encapsulation (NVGRE) [RFC7637]) or proprietary encapsulations. To construct a tenant network among these servers and the Top-of-Rack (ToR) switches, operators can construct one traditional VLAN network and two virtual networks where one uses VXLAN encapsulation and the other uses NVGRE, and interconnect these three networks via a gateway or virtual GW. The GW performs packet encapsulation/decapsulation translation between the networks.

大規模なDCに展開されるサーバーは、異なる時期に設置されることが多く、異なる能力や機能を持っていることがあります。仮想化されているサーバーもあれば、そうでないサーバーもあります。仮想スイッチを備えているサーバーもあれば、そうでないサーバーもあります。ハイパーバイザーベースの仮想スイッチを備えたサーバーについても、標準化されたNVO3カプセル化をサポートするもの、カプセル化をまったくサポートしないもの、文書化されたカプセル化プロトコル（たとえば、Virtual eXtensible Local Area Network（VXLAN）[RFC7348]やNetwork Virtualization using Generic Routing Encapsulation（NVGRE）[RFC7637]）や独自のカプセル化をサポートするものがあります。これらのサーバーとトップオブラック（Top-of-Rack：ToR）スイッチの間でテナントネットワークを構築するために、運用者は、1つの従来のVLANネットワークと、一方がVXLANカプセル化を、もう一方がNVGREを使用する2つの仮想ネットワークを構築し、これら3つのネットワークをゲートウェイまたは仮想GWを介して相互接続できます。GWは、ネットワーク間でパケットのカプセル化／カプセル化解除の変換を行います。

Another case is that some software of a tenant has high CPU and memory consumption, which only makes sense to run on standalone servers; other software of the tenant may be good to run on VMs. However, provider DC infrastructure is configured to use NVO3 to connect VMs and VLANs [IEEE802.1Q] to physical servers. The tenant network requires interworking between NVO3 and traditional VLAN.

別のケースとして、テナントのソフトウェアの一部がCPUとメモリーを大量に消費するため、スタンドアロンのサーバー上で実行することにしか意味がなく、テナントの他のソフトウェアはVM上で実行するのが適している場合があります。しかし、プロバイダーのDCインフラストラクチャーは、NVO3を使用してVMとVLAN[IEEE802.1Q]を物理サーバーに接続するように設定されています。このテナントネットワークには、NVO3と従来のVLANの間のインターワーキングが必要です。

4.2. DC Applications Spanning Multiple Physical Zones

4.2. 複数の物理ゾーンにまたがるDCアプリケーション

A DC can be partitioned into multiple physical zones, with each zone having different access permissions and running different applications. For example, a three-tier zone design has a front zone (Web tier) with Web applications, a mid zone (application tier) where service applications such as credit payment or ticket booking run, and a back zone (database tier) with Data. External users are only able to communicate with the Web application in the front zone; the back zone can only receive traffic from the application zone. In this case, communications between the zones must pass through one or more security functions in a physical DMZ zone. Each zone can be implemented by one NVO3 virtual network and the security functions in DMZ zone can be used to between two NVO3 virtual networks, i.e., two zones. If network functions (NFs), especially the security functions in the physical DMZ, can't process encapsulated NVO3 traffic, the NVO3 tunnels have to be terminated for the NF to perform its processing on the application traffic.

DCは複数の物理ゾーンに分割でき、各ゾーンは異なるアクセス許可を持ち、異なるアプリケーションを実行します。たとえば、3層のゾーン設計では、Webアプリケーションを持つフロントゾーン（Web層）、クレジット決済やチケット予約などのサービスアプリケーションが実行される中間ゾーン（アプリケーション層）、データを持つバックゾーン（データベース層）があります。外部ユーザーはフロントゾーンのWebアプリケーションとしか通信できず、バックゾーンはアプリケーションゾーンからのトラフィックしか受信できません。この場合、ゾーン間の通信は、物理的なDMZゾーンにある1つ以上のセキュリティー機能を通過する必要があります。各ゾーンは1つのNVO3仮想ネットワークで実装でき、DMZゾーンのセキュリティー機能は2つのNVO3仮想ネットワーク（すなわち2つのゾーン）の間で使用できます。ネットワーク機能（Network Function：NF）、特に物理的なDMZにあるセキュリティー機能が、カプセル化されたNVO3トラフィックを処理できない場合、NFがアプリケーショントラフィックに対して処理を行えるように、NVO3トンネルを終端する必要があります。

4.3. Virtual Data Center (vDC)

4.3. 仮想データセンター（vDC）

An enterprise DC may deploy routers, switches, and network appliance devices to construct its internal network, DMZ, and external network access; it may have many servers and storage running various applications. With NVO3 technology, a DC provider can construct a vDC over its physical DC infrastructure and offer a vDC service to enterprise customers. A vDC at the DC provider site provides the same capability as the physical DC at a customer site. A customer manages its own applications running in its vDC. A DC provider can further offer different network service functions to the customer. The network service functions may include a firewall, DNS, LB, gateway, etc.

企業のDCは、内部ネットワーク、DMZ、外部ネットワークへのアクセスを構築するために、ルーター、スイッチ、ネットワークアプライアンスデバイスを展開することがあり、さまざまなアプリケーションを実行する多数のサーバーとストレージを持つことがあります。NVO3技術を使用すると、DCプロバイダーは、自身の物理DCインフラストラクチャー上にvDCを構築し、企業顧客にvDCサービスを提供できます。DCプロバイダーのサイトにあるvDCは、顧客サイトにある物理DCと同じ能力を提供します。顧客は、自分のvDCで実行される自分のアプリケーションを管理します。DCプロバイダーは、さらにさまざまなネットワークサービス機能を顧客に提供できます。ネットワークサービス機能には、ファイアウォール、DNS、LB、ゲートウェイなどが含まれます。

Figure 2 illustrates one such scenario at the service-abstraction level. In this example, the vDC contains several L2 VNs (L2VNx, L2VNy, L2VNz) to group the tenant systems together on a per-application basis, and one L3 VN (L3VNa) for the internal routing. A network firewall and gateway runs on a VM or server that connects to L3VNa and is used for inbound and outbound traffic processing. An LB is used in L2VNx. A VPN is also built between the gateway and enterprise router. An Enterprise customer runs Web/Mail/Voice applications on VMs within the vDC. The users at the Enterprise site access the applications running in the vDC via the VPN; Internet users access these applications via the gateway/firewall at the DC provider site.

図2は、そのようなシナリオの1つをサービス抽象化のレベルで示しています。この例では、vDCは、アプリケーションごとにテナントシステムをグループ化するための複数のL2 VN（L2VNx、L2VNy、L2VNz）と、内部ルーティングのための1つのL3 VN（L3VNa）を含みます。ネットワークのファイアウォールとゲートウェイは、L3VNaに接続するVMまたはサーバー上で動作し、インバウンドとアウトバウンドのトラフィック処理に使用されます。L2VNxではLBが使用されます。また、ゲートウェイと企業のルーターの間にはVPNが構築されます。企業顧客は、vDC内のVM上でWeb／メール／音声アプリケーションを実行します。企業サイトのユーザーはVPNを介してvDCで実行されるアプリケーションにアクセスし、インターネットユーザーはDCプロバイダーのサイトにあるゲートウェイ／ファイアウォールを介してこれらのアプリケーションにアクセスします。

The enterprise customer decides which applications should be accessible only via the intranet and which should be assessable via both the intranet and Internet, and it configures the proper security policy and gateway function at the firewall/gateway. Furthermore, an enterprise customer may want multi-zones in a vDC (see Section 4.2) for the security and/or the ability to set different QoS levels for the different applications.

企業顧客は、どのアプリケーションをイントラネット経由でのみアクセス可能にし、どのアプリケーションをイントラネットとインターネットの両方からアクセス可能にするかを決定し、ファイアウォール／ゲートウェイで適切なセキュリティーポリシーとゲートウェイ機能を設定します。さらに、企業顧客は、セキュリティーのため、および／または異なるアプリケーションに異なるQoSレベルを設定できるようにするために、vDC内に複数のゾーン（セクション4.2を参照）を持つことを望む場合があります。

The vDC use case requires an NVO3 solution to provide DC operators with an easy and quick way to create an NVO3 virtual network and NVEs for any vDC design, to allocate TSs and assign TSs to the corresponding NVO3 virtual network and to illustrate vDC topology and manage/configure individual elements in the vDC in a secure way.

vDCのユースケースでは、NVO3ソリューションが、DC運用者に対して、任意のvDC設計のためにNVO3仮想ネットワークとNVEを作成し、TSを割り当てて対応するNVO3仮想ネットワークに割り当て、vDCのトポロジーを示し、vDC内の個々の要素を安全な方法で管理／設定するための、簡単で迅速な方法を提供することが求められます。

5. Summary

5. まとめ

This document describes some general NVO3 use cases in DCs. The combination of these cases will give operators the flexibility and capability to design more sophisticated support for various cloud applications.

この文書では、DCにおける一般的なNVO3のユースケースのいくつかについて説明しました。これらのケースを組み合わせることで、運用者は、さまざまなクラウドアプリケーションに対するより高度なサポートを設計する柔軟性と能力を得られます。

DC services may vary, NVO3 virtual networks make it possible to scale a large number of virtual networks in a DC and ensure the network infrastructure not impacted by the number of VMs and dynamic workload changes in a DC.

DCサービスはさまざまですが、NVO3仮想ネットワークにより、DC内の多数の仮想ネットワークへの拡張が可能になり、ネットワークインフラストラクチャーがDC内のVMの数や動的なワークロードの変化に影響されないようにすることができます。

NVO3 uses tunnel techniques to deliver NVO3 traffic over DC physical infrastructure network. A tunnel encapsulation protocol is necessary. An NVO3 tunnel may, in turn, be tunneled over other intermediate tunnels over the Internet or other WANs.

NVO3は、DCの物理インフラストラクチャーネットワーク上でNVO3トラフィックを配送するためにトンネル技術を使用します。トンネルのカプセル化プロトコルが必要です。NVO3トンネルは、さらに、インターネットや他のWAN上の別の中間トンネルを通じてトンネリングされることもあります。

An NVO3 virtual network in a DC may be accessed by external users in a secure way. Many existing technologies can help achieve this.

DC内のNVO3仮想ネットワークには、外部ユーザーが安全な方法でアクセスすることがあります。既存の多くの技術がこれを実現するのに役立ちます。

6. Security Considerations

6. セキュリティーに関する考慮事項

Security is a concern. DC operators need to provide a tenant with a secured virtual network, which means one tenant's traffic is isolated from other tenants' traffic and is not leaked to the underlay networks. Tenants are vulnerable to observation and data modification/injection by the operator of the underlay and should only use operators they trust. DC operators also need to prevent a tenant application attacking their underlay DC networks; further, they need to protect a tenant application attacking another tenant application via the DC infrastructure network. For example, a tenant application attempts to generate a large volume of traffic to overload the DC's underlying network. This can be done by limiting the bandwidth of such communications.

セキュリティーは懸念事項です。DC運用者は、テナントに安全な仮想ネットワークを提供する必要があります。これは、あるテナントのトラフィックが他のテナントのトラフィックから分離され、アンダーレイネットワークに漏洩しないことを意味します。テナントは、アンダーレイの運用者による観察やデータの改ざん／注入に対して脆弱であり、信頼できる運用者だけを利用するべきです。DC運用者はまた、テナントアプリケーションが自身のアンダーレイDCネットワークを攻撃することを防ぐ必要があります。さらに、テナントアプリケーションがDCインフラストラクチャーネットワークを介して別のテナントアプリケーションを攻撃することから保護する必要があります。たとえば、テナントアプリケーションが大量のトラフィックを生成して、DCの下位のネットワークを過負荷にしようとする場合があります。これは、そのような通信の帯域幅を制限することで対処できます。
