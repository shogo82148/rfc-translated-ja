RFC 10004

Certificate Management over CMS (CMC): Compliance Requirements

RFC 10004

CMS上の証明書管理（CMC）：準拠要件

Abstract

概要

This document provides a set of compliance statements about the Certificate Management over CMS (CMC) enrollment protocol. The ASN.1 structures and the transport mechanisms for the CMC enrollment protocol are covered in other documents (RFCs 10002 and 10003). This document provides the information needed to make a compliant version of CMC.

この文書は、CMS上の証明書管理（Certificate Management over CMS: CMC）の登録プロトコルに関する一連の準拠要件を示します。 CMC登録プロトコルのASN.1構造とトランスポートメカニズムは、他の文書（RFC 10002およびRFC 10003）で扱われています。 この文書は、CMCの準拠したバージョンを作成するために必要な情報を提供します。

This document obsoletes RFCs 5274 and 6402.

この文書はRFC 5274とRFC 6402を廃止します。

1. Introduction

1. はじめに

The Certificate Management over CMS (CMC) protocol is designed in terms of a client/server relationship. In the simplest case, the client is the requestor of the certificate (i.e., the End-Entity (EE)) and the server is the issuer of the certificate (i.e., the Certification Authority (CA)). The introduction of a Registration Authority (RA) into the set of agents complicates the picture only slightly. The RA becomes the server with respect to the certificate requestor, and it becomes the client with respect to the certificate issuer. Any number of RAs can be inserted into the picture in this manner.

CMS上の証明書管理（CMC）プロトコルは、クライアント/サーバーの関係に基づいて設計されています。 最も単純な場合、クライアントは証明書のリクエスター（つまり、エンドエンティティー（EE））であり、サーバーは証明書の発行者（つまり、認証局（CA））です。 エージェントの集合に登録局（RA）を導入しても、状況はわずかに複雑になるだけです。 RAは、証明書のリクエスターに対してはサーバーとなり、証明書の発行者に対してはクライアントとなります。 このようにして、任意の数のRAを挿入できます。

The RAs may serve specialized purposes that are not currently covered by this document. One such purpose would be a Key Escrow agent. As such, all certificate requests for encryption keys would be directed through this RA, and it would take appropriate action to do the key archival. Key recovery requests could be defined in the CMC methodology allowing for the Key Escrow agent to perform that operation acting as the final server in the chain of agents.

RAは、現在この文書では扱っていない特殊な目的を果たす場合があります。 そのような目的の1つは鍵エスクローエージェントです。 その場合、暗号化鍵に対するすべての証明書リクエストはこのRAを経由して送られ、RAは鍵のアーカイブを行うための適切なアクションを取ることになります。 鍵の回復リクエストをCMCの方法論の中で定義し、鍵エスクローエージェントがエージェントのチェーンにおける最終サーバーとしてその操作を実行できるようにすることもできます。

If there are multiple RAs in the system, it is considered normal that not all RAs will see all certificate requests. The routing between the RAs may be dependent on the content of the certificate requests involved.

システム内に複数のRAがある場合、すべてのRAがすべての証明書リクエストを目にするわけではないのが普通と考えられます。 RA間のルーティングは、関係する証明書リクエストの内容に依存する場合があります。

This document is divided into six sections, each section specifying the requirements that are specific to a class of agents in the CMC model. These are 1) all entities, 2) all servers, 3) all clients, 4) all EEs, 5) all RAs, and 6) all CAs.

この文書は6つのセクションに分かれており、各セクションはCMCモデルにおけるエージェントの種類に固有の要件を規定しています。 それらは、1) すべてのエンティティー、2) すべてのサーバー、3) すべてのクライアント、4) すべてのEE、5) すべてのRA、6) すべてのCAです。

This document obsoletes RFCs 5274 [CMC-COMPv1] and 6402 [CMC-Updates].

この文書はRFC 5274[CMC-COMPv1]とRFC 6402[CMC-Updates]を廃止します。

2. Terminology

2. 用語

There are several different terms, abbreviations, and acronyms used in this document that we define here for convenience and consistency of usage:

この文書では、いくつかの異なる用語、略語、頭字語を使用します。便宜と使用の一貫性のために、それらをここで定義します：

End-Entity (EE):

Refers to the entity that owns a key pair and for whom a certificate is issued.

Registration Authority (RA) or Local RA (LRA):

Refers to an entity that acts as an intermediary between the EE and the CA. Multiple RAs can exist between the EE and the CA. RAs may perform additional services such as key generation or key archival. This document uses the term RA for both RA and LRA.

Certification Authority (CA):

Refers to the entity that issues certificates.

Client:

Refers to an entity that creates a Public Key Infrastructure (PKI) Request. In this document, both RAs and EEs can be clients.

Server:

Refers to the entities that process PKI Requests and create PKI Responses. In this document, both CAs and RAs can be servers.

PKCS #10:

Refers to the Public Key Cryptography Standard #10 [PKCS10], which defines a certification request syntax.

CRMF:

Refers to the Certificate Request Message Format [CRMF]. CMC uses this certification request syntax defined in this document as part of the protocol.

CMS:

Refers to the Cryptographic Message Syntax [CMS]. This document provides for basic cryptographic services including encryption and signing with and without key management.

PKI Request/Response:

Refers to the requests/responses described in this document. PKI Requests include certification requests, revocation requests, etc. PKI Responses include certs-only messages, failure messages, etc.

Proof-of-Identity:

Refers to the client proving they are who they say that they are to the server.

Proof-of-Possession (POP):

Refers to a value that can be used to prove that the private key corresponding to a public key is in the possession and can be used by an EE. See Section 2.1 of [CMC-STRUCT].

Transport wrapper:

Refers to the outermost CMS wrapping layer.

Entity:

Refers to EE, RA (or LRA), or CA.

HMAC:

Refers to the Hashed Message Authentication Code. CMC uses the ASN.1 module defined in [HMAC-ALGS].

エンドエンティティー（End-Entity: EE）：

鍵ペアを所有し、証明書の発行対象となるエンティティーを指します。

登録局（Registration Authority: RA）またはローカルRA（LRA）：

EEとCAの間の仲介者として機能するエンティティーを指します。 EEとCAの間には複数のRAが存在できます。 RAは、鍵生成や鍵のアーカイブなどの追加のサービスを実行することがあります。 この文書では、RAとLRAの両方を指してRAという用語を使用します。

認証局（Certification Authority: CA）：

証明書を発行するエンティティーを指します。

クライアント：

公開鍵基盤（PKI）Requestを作成するエンティティーを指します。 この文書では、RAとEEの両方がクライアントになりえます。

サーバー：

PKI Requestを処理し、PKI Responseを作成するエンティティーを指します。 この文書では、CAとRAの両方がサーバーになりえます。

PKCS #10：

証明リクエストの構文を定義している、公開鍵暗号標準（Public Key Cryptography Standard）#10[PKCS10]を指します。

CRMF：

証明書リクエストメッセージ形式（Certificate Request Message Format）[CRMF]を指します。 CMCは、この文書で定義されている証明リクエストの構文をプロトコルの一部として使用します。

CMS：

暗号メッセージ構文（Cryptographic Message Syntax）[CMS]を指します。 この文書は、鍵管理を伴う、または伴わない暗号化や署名を含む、基本的な暗号サービスを提供します。

PKI Request/Response：

この文書で説明するリクエスト/レスポンスを指します。 PKI Requestには、証明リクエスト、失効リクエストなどが含まれます。 PKI Responseには、certs-onlyメッセージ、失敗メッセージなどが含まれます。

識別情報の証明（Proof-of-Identity）：

クライアントが、自分が名乗っているとおりの者であることをサーバーに対して証明することを指します。

所有証明（Proof-of-Possession: POP）：

公開鍵に対応する秘密鍵をEEが所有しており、使用できることを証明するために使用できる値を指します。 [CMC-STRUCT]のSection 2.1を参照してください。

トランスポートラッパー：

最も外側のCMSのラッピング層を指します。

エンティティー：

EE、RA（またはLRA）、またはCAを指します。

HMAC：

ハッシュベースのメッセージ認証コード（Hashed Message Authentication Code）を指します。CMCは[HMAC-ALGS]で定義されているASN.1モジュールを使用します。

5. Requirements for All Entities

5. すべてのエンティティーに対する要件

All [CMC-STRUCT] and [CMC-TRANS] compliance statements MUST be adhered to unless specifically stated otherwise in this document.

この文書で特に明記されていない限り、[CMC-STRUCT]と[CMC-TRANS]のすべての準拠要件を遵守しなければなりません（MUST）。

All entities MUST support Full PKI Requests, Simple PKI Responses, and Full PKI Responses. Servers SHOULD support Simple PKI Requests.

すべてのエンティティーは、Full PKI Request、Simple PKI Response、およびFull PKI Responseをサポートしなければなりません（MUST）。 サーバーはSimple PKI Requestをサポートすべきです（SHOULD）。

All entities MUST support the use of the CRMF syntax for certification requests. Support for the PKCS #10 syntax for certification requests SHOULD be implemented by servers.

すべてのエンティティーは、証明リクエストにCRMFの構文を使用することをサポートしなければなりません（MUST）。 証明リクエストのためのPKCS #10の構文のサポートは、サーバーによって実装されるべきです（SHOULD）。

The extendedFailInfo field SHOULD NOT be populated in the CMCStatusInfoV2 object; the failInfo field SHOULD be used to relay this information. If the extendedFailInfo field is used, it is suggested that an additional CMCStatusInfoV2 item exist for the same body part with a failInfo field.

CMCStatusInfoV2オブジェクトのextendedFailInfoフィールドには値を設定すべきではありません（SHOULD NOT）。この情報を伝えるにはfailInfoフィールドを使用すべきです（SHOULD）。 extendedFailInfoフィールドを使用する場合は、同じボディーパートに対してfailInfoフィールドを持つ追加のCMCStatusInfoV2項目が存在することが推奨されます。

All entities MUST implement the HTTP transport mechanism as defined in [CMC-TRANS]. Other transport mechanisms MAY be implemented.

すべてのエンティティーは、[CMC-TRANS]で定義されているHTTPトランスポートメカニズムを実装しなければなりません（MUST）。 その他のトランスポートメカニズムを実装してもよいです（MAY）。

5.1. Cryptographic Algorithm Requirements

5.1. 暗号アルゴリズムの要件

All entities MUST verify RSA-SHA256 signatures in SignedData; (see [CMS-ALG2]). Entities MAY verify other signature algorithms.

すべてのエンティティーは、SignedData内のRSA-SHA256署名を検証しなければなりません（MUST）（[CMS-ALG2]を参照）。 エンティティーは、その他の署名アルゴリズムを検証してもよいです（MAY）。

All entities MUST generate RSA-SHA256 signatures for SignedData; (see [CMS-ALG2]). Other signature algorithms MAY be used for generation.

すべてのエンティティーは、SignedDataに対してRSA-SHA256署名を生成しなければなりません（MUST）（[CMS-ALG2]を参照）。 生成にはその他の署名アルゴリズムを使用してもよいです（MAY）。

All entities MUST support Advanced Encryption Standard (AES) as the content encryption algorithm for EnvelopedData; (see [CMS-AES]). Other content encryption algorithms MAY be implemented.

すべてのエンティティーは、EnvelopedDataのコンテンツ暗号化アルゴリズムとしてAdvanced Encryption Standard（AES）をサポートしなければなりません（MUST）（[CMS-AES]を参照）。 その他のコンテンツ暗号化アルゴリズムを実装してもよいです（MAY）。

All entities MUST support AES-GCM (Galois/Counter Mode) as the authenticated content encryption algorithm for AuthEnvelopedData; (see [CMS-AES-AE]). They MUST also support a 12-octet nonce size and a 12-octet Integrity Check Value (ICV) length. Other content encryption algorithms MAY be implemented.

すべてのエンティティーは、AuthEnvelopedDataの認証付きコンテンツ暗号化アルゴリズムとしてAES-GCM（Galois/Counter Mode）をサポートしなければなりません（MUST）（[CMS-AES-AE]を参照）。 また、12オクテットのノンスサイズと12オクテットの完全性チェック値（ICV）の長さもサポートしなければなりません（MUST）。 その他のコンテンツ暗号化アルゴリズムを実装してもよいです（MAY）。

All entities MUST support RSA as a key transport algorithm for EnvelopedData and AuthEnvelopedData; see [CMS-ALG2]. Other key transport algorithms MAY be implemented.

すべてのエンティティーは、EnvelopedDataとAuthEnvelopedDataの鍵トランスポートアルゴリズムとしてRSAをサポートしなければなりません（MUST）。[CMS-ALG2]を参照してください。 その他の鍵トランスポートアルゴリズムを実装してもよいです（MAY）。

If an entity supports key agreement for EnvelopedData or AuthEnvelopedData, it MUST support Diffie-Hellman (DH); (see [CMS-DH]).

エンティティーがEnvelopedDataまたはAuthEnvelopedDataの鍵合意をサポートする場合、ディフィー・ヘルマン（DH）をサポートしなければなりません（MUST）（[CMS-DH]を参照）。

If an entity supports PasswordRecipientInfo for EnvelopedData, AuthenticatedData, or AuthEnvelopedData, it MUST support Password-Based Key Derivation Function 2 (PBKDF2) [PBKDF2] for key derivation algorithms. It MUST support AES key wrap (see [AES-WRAP]) as the key encryption algorithm.

エンティティーがEnvelopedData、AuthenticatedData、またはAuthEnvelopedDataのPasswordRecipientInfoをサポートする場合、鍵導出アルゴリズムとしてパスワードベースの鍵導出関数2（PBKDF2）[PBKDF2]をサポートしなければなりません（MUST）。 また、鍵暗号化アルゴリズムとしてAES鍵ラップ（[AES-WRAP]を参照）をサポートしなければなりません（MUST）。

If AuthenticatedData is supported, PasswordRecipientInfo MUST be supported.

AuthenticatedDataをサポートする場合は、PasswordRecipientInfoをサポートしなければなりません（MUST）。

Algorithm requirements for the Identity Proof Version 2 control (Section 6.2.1 of [CMC-STRUCT]) are as follows:

Identity Proof Version 2制御（[CMC-STRUCT]のSection 6.2.1）のアルゴリズムの要件は次のとおりです：

  • SHA-256 MUST be implemented for hashAlgId.
  • HMAC-SHA256 MUST be implemented for macAlgId.
  • hashAlgIdに対してSHA-256を実装しなければなりません（MUST）。
  • macAlgIdに対してHMAC-SHA256を実装しなければなりません（MUST）。

Algorithm requirements for the Pop Link Witness Version 2 control (Section 6.3.1.1 of [CMC-STRUCT]) are as follows:

Pop Link Witness Version 2制御（[CMC-STRUCT]のSection 6.3.1.1）のアルゴリズムの要件は次のとおりです：

  • SHA-256 MUST be implemented for keyGenAlgorithm.
  • PBKDF2 [PBKDF2] MAY be implemented for keyGenAlgorithm.
  • HMAC-SHA256 MUST be implemented for macAlgorithm.
  • keyGenAlgorithmに対してSHA-256を実装しなければなりません（MUST）。
  • keyGenAlgorithmに対してPBKDF2[PBKDF2]を実装してもよいです（MAY）。
  • macAlgorithmに対してHMAC-SHA256を実装しなければなりません（MUST）。

Algorithm requirements for the Encrypted POP and Decrypted POP controls (Section 6.7 of [CMC-STRUCT]) are as follows:

Encrypted POP制御とDecrypted POP制御（[CMC-STRUCT]のSection 6.7）のアルゴリズムの要件は次のとおりです：

  • SHA-256 MUST be implemented for witnessAlgID.
  • HMAC-SHA256 MUST be implemented for thePOPAlgID.
  • witnessAlgIDに対してSHA-256を実装しなければなりません（MUST）。
  • thePOPAlgIDに対してHMAC-SHA256を実装しなければなりません（MUST）。

Algorithm requirements for Publish Trust Anchors control (Section 6.15 of [CMC-STRUCT]) are as follows:

Publish Trust Anchors制御（[CMC-STRUCT]のSection 6.15）のアルゴリズムの要件は次のとおりです：

  • SHA-256 MUST be implemented for hashAlgorithm.
  • hashAlgorithmに対してSHA-256を実装しなければなりません（MUST）。

If an EE generates DH keys for certification, it MUST support Section 4 of [DH-POP]. EEs MAY support Section 3 of [DH-POP]. CAs and RAs that do POP verification MUST support Section 4 of [DH-POP] and SHOULD support Section 3 of [DH-POP].

EEが証明のためにDH鍵を生成する場合、[DH-POP]のSection 4をサポートしなければなりません（MUST）。 EEは[DH-POP]のSection 3をサポートしてもよいです（MAY）。 POPの検証を行うCAとRAは、[DH-POP]のSection 4をサポートしなければなりません（MUST）。また、[DH-POP]のSection 3をサポートすべきです（SHOULD）。

EEs that need to use a signature algorithm for keys that cannot produce a signature MUST support Appendix C of [CMC-STRUCT] and MUST support the Encrypted/Decrypted POP controls. CAs and RAs that do POP verification MUST support this signature algorithm and MUST support the Encrypted/Decrypted POP controls.

署名を生成できない鍵に署名アルゴリズムを使用する必要があるEEは、[CMC-STRUCT]のAppendix Cをサポートしなければなりません（MUST）。また、Encrypted/Decrypted POP制御をサポートしなければなりません（MUST）。 POPの検証を行うCAとRAは、この署名アルゴリズムをサポートしなければなりません（MUST）。また、Encrypted/Decrypted POP制御をサポートしなければなりません（MUST）。

For backward compatibility with the previous version of CMC, servers MAY offer the algorithms specified therein, but SHOULD use the CMC requests to identify which certificates should be transitioned to more secure algorithms, if possible.

CMCの以前のバージョンとの後方互換性のために、サーバーはそこで規定されているアルゴリズムを提供してもよいです（MAY）が、可能であれば、どの証明書をより安全なアルゴリズムに移行すべきかを識別するためにCMCリクエストを使用すべきです（SHOULD）。

5.3. CRMF Feature Requirements

5.3. CRMFの機能に対する要件

The following additional restrictions are placed on CRMF features:

CRMFの機能には、次の追加の制限が課されます：

  • The registration control tokens id-regCtrl-regToken and id-regCtrl-authToken MUST NOT be used. No specific CMC feature is used to replace these items, but generally the CMC control's identification and identityProof will perform the same service and are more specifically defined.
  • The control token id-regCtrl-pkiArchiveOptions SHOULD NOT be supported. See Section 3.2.1.3.3 of [CMC-STRUCT] and Section 3.2.1.3.3 of [CMC-STRUCT] for alternative methods.
  • The behavior of id-regCtrl-oldCertID is not presently used. It is replaced by issuing the new certificate and using the id-cmc-publishCert to remove the old certificate from publication. This operation would not normally be accompanied by an immediate revocation of the old certificate; however, that can be accomplished by the id-cmc-revokeRequest control.
  • The id-regCtrl-protocolEncrKey is not used.
  • 登録制御トークンid-regCtrl-regTokenとid-regCtrl-authTokenを使用してはなりません（MUST NOT）。 これらの項目を置き換える特定のCMCの機能は使用されませんが、一般にCMC制御のidentificationとidentityProofが同じサービスを実行し、より具体的に定義されています。
  • 制御トークンid-regCtrl-pkiArchiveOptionsはサポートすべきではありません（SHOULD NOT）。 代替の方法については[CMC-STRUCT]のSection 3.2.1.3.3と[CMC-STRUCT]のSection 3.2.1.3.3を参照してください。
  • id-regCtrl-oldCertIDの動作は現在使用されていません。 これは、新しい証明書を発行し、id-cmc-publishCertを使用して古い証明書を公開から削除することで置き換えられます。 この操作は通常、古い証明書の即時の失効を伴いませんが、それはid-cmc-revokeRequest制御によって実現できます。
  • id-regCtrl-protocolEncrKeyは使用されません。

8. Requirements for EEs

8. EEに対する要件

If an EE implements Diffie-Hellman, it MUST implement either the DH POP Proof-of-Possession as defined in Section 4 of [DH-POP] or the challenge-response POP controls id-cmc-encryptedPOP and id-cmc-decryptedPOP.

EEがディフィー・ヘルマンを実装する場合、[DH-POP]のSection 4で定義されているDH POPによる所有証明、またはチャレンジレスポンスのPOP制御id-cmc-encryptedPOPとid-cmc-decryptedPOPのいずれかを実装しなければなりません（MUST）。

9. Requirements for RAs

9. RAに対する要件

RAs SHOULD be able to do delegated POP. RAs implementing this feature MUST implement the id-cmc-lraPOPWitness control.

RAは委任されたPOPを実行できるべきです（SHOULD）。 この機能を実装するRAは、id-cmc-lraPOPWitness制御を実装しなければなりません（MUST）。

All RAs MUST implement the promotion of the id-aa-cmc-unsignedData as covered in Section 3.2.3 of [CMC-STRUCT].

すべてのRAは、[CMC-STRUCT]のSection 3.2.3で扱われているid-aa-cmc-unsignedDataの昇格を実装しなければなりません（MUST）。

10. Requirements for CAs

10. CAに対する要件

Providing for CAs to work in an environment with RAs is strongly suggested. Implementation of such support is strongly suggested as this permits the delegation of substantial administrative interaction onto an RA rather than at the CA.

CAがRAとともに動作する環境に対応することが強く推奨されます。 これにより、管理上の多くのやり取りをCAではなくRAに委任できるため、そのようなサポートの実装が強く推奨されます。

CAs MUST perform at least minimal checks on all public keys before issuing a certificate. At a minimum, a check for syntax would occur with the POP operation. Additionally, CAs SHOULD perform simple checks for known bad keys such as small subgroups for DSA-SHA1 and DH keys [SMALL-SUB-GROUP] or known bad exponents for RSA keys.

CAは、証明書を発行する前に、すべての公開鍵に対して少なくとも最低限のチェックを実行しなければなりません（MUST）。 最低限、構文のチェックがPOP操作とともに行われることになります。 さらに、CAは、DSA-SHA1鍵やDH鍵の小部分群[SMALL-SUB-GROUP]、RSA鍵の既知の不正な指数など、既知の不正な鍵に対する簡単なチェックを実行すべきです（SHOULD）。

CAs MUST enforce POP checking before issuing any certificate. CAs MAY delegate the POP operation to an RA for those cases where:

CAは、いかなる証明書を発行する前にもPOPのチェックを実施しなければなりません（MUST）。 CAは、次のような場合には、POP操作をRAに委任してもよいです（MAY）：

  1. a challenge/response message pair must be used,
  2. an RA performs escrow of a key and checks for POP in that manner, or
  3. an unusual algorithm is used and that validation is done at the RA.
  1. チャレンジ/レスポンスのメッセージペアを使用しなければならない場合。
  2. RAが鍵のエスクローを行い、その方法でPOPをチェックする場合。または、
  3. 一般的でないアルゴリズムが使用され、その検証がRAで行われる場合。

CAs SHOULD implement both the DH-POP Proof-of-Possession as defined in Section 4 of [DH-POP] and the challenge-response POP controls id-cmc-encryptedPOP and id-cmc-decryptedPOP.

CAは、[DH-POP]のSection 4で定義されているDH-POPによる所有証明と、チャレンジレスポンスのPOP制御id-cmc-encryptedPOPおよびid-cmc-decryptedPOPの両方を実装すべきです（SHOULD）。

11. セキュリティーに関する考慮事項

This document uses [CMC-STRUCT] and [CMC-TRANS] as building blocks. The security sections of those two documents are included by reference.

この文書は[CMC-STRUCT]と[CMC-TRANS]を構成要素として使用しています。 これら2つの文書のセキュリティーのセクションを参照によって含めます。

Knowledge of how an entity is expected to operate is vital in determining which sections of requirements are applicable to that entity. Care needs to be taken in determining which sections apply and fully implementing the necessary code.

エンティティーがどのように動作することが期待されているかを知ることは、そのエンティティーにどの要件のセクションが適用されるかを判断する上で不可欠です。 どのセクションが適用されるかを判断し、必要なコードを完全に実装する際には注意が必要です。

Cryptographic algorithms have and will be broken or weakened. Implementers and users need to check that the cryptographic algorithms listed in this document make sense from a security level. The IETF from time to time may issue documents dealing with the current state of the art. Two examples of such documents are [SMALL-SUB-GROUP] and [HASH-ATTACKS].

暗号アルゴリズムは、これまでも破られたり弱体化したりしてきましたし、今後もそうなるでしょう。 実装者とユーザーは、この文書に列挙されている暗号アルゴリズムがセキュリティーレベルの観点から妥当であることを確認する必要があります。 IETFは、最新の技術動向を扱う文書を随時発行することがあります。 そのような文書の例として[SMALL-SUB-GROUP]と[HASH-ATTACKS]の2つがあります。
