RFC 797

Format for Bitmap files

RFC 797

ビットマップファイルの形式

Abstract

概要

This note describes a proposed format for storing simple bitmaps (one bit per pixel) in a file. These files may be very large and the intent is to use this format for short term storage and passing data between closely coupled programs. The data in the file should be stored in 8-bit bytes (octets). Bitmaps may be any size.

このメモでは、単純なビットマップ（1ピクセルあたり1ビット）をファイルに格納するための形式を提案します。これらのファイルは非常に大きくなることがあり、この形式は短期間の保存や、密接に連携するプログラム間でのデータの受け渡しに使うことを意図しています。ファイル内のデータは8ビットバイト（オクテット）で格納すべきです。ビットマップの大きさに制限はありません。

The first 4 octets of the file gives the width of each line (x direction), and the next 4 octets should give the number of lines of the display (length, y direction). After this is one octet for the x increment and one octet for the y increment. Following these 10 octets is the bitmap itself. The length and width fields are stored most significant octet first.

ファイルの最初の4オクテットは各ラインの幅（x方向）を表し、次の4オクテットはディスプレイのライン数（長さ、y方向）を表します。その後に、xの増分を表す1オクテットと、yの増分を表す1オクテットが続きます。これら10オクテットの後にビットマップ本体が続きます。長さと幅のフィールドは、最上位のオクテットから順に格納します。

The x and y increment octets tell how much space is between pixels. For an ordinary display, both these would be one.

xとyの増分のオクテットは、ピクセルの間隔を表します。通常のディスプレイでは、どちらも1になります。

Each line of the display should be scanned from left to right. The lines should start at the top and work down. Each line in the bitmap should end on an octet boundary. If the width of the display is not divisable by 8, the rest of the last octet should be filled with zeros on the right.

ディスプレイの各ラインは左から右へ走査すべきです。ラインは上から始めて下へと進むべきです。ビットマップの各ラインはオクテット境界で終わるべきです。ディスプレイの幅が8で割り切れない場合、最後のオクテットの残りの右側はゼロで埋めるべきです。

Below is a representation of a bitmap file (each square is one octet):

以下にビットマップファイルの表現を示します（各マスが1オクテットです）。

   ----------------------------------------------------------
   |    1     |    2     |    3     |     4     |     5     |
   |  width   |  width   |  width   |   width   |  length   |
   ----------------------------------------------------------

   ----------------------------------------------------------
   |     6    |     7    |     8    |     9     |     10    |
   |  length  |  length  |  length  |x-increment|y-increment|
   ----------------------------------------------------------

   ----------------------------------------------------------
   |   11     |   12     |   13     |    14     |   15
   |  data    |  data    |  data    |   data    |  data...
   ----------------------------------------------------------

   ----------------------------------------------------------
   |    1     |    2     |    3     |     4     |     5     |
   |  width   |  width   |  width   |   width   |  length   |
   ----------------------------------------------------------

   ----------------------------------------------------------
   |     6    |     7    |     8    |     9     |     10    |
   |  length  |  length  |  length  |x-increment|y-increment|
   ----------------------------------------------------------

   ----------------------------------------------------------
   |   11     |   12     |   13     |    14     |   15
   |  data    |  data    |  data    |   data    |  data...
   ----------------------------------------------------------

For example, bitmaps from the RAPICOM 450 can be in Fine Detail, Quality, or Express Mode. In Fine Detail mode the x-increment and y-increment would be 1, for Quality mode, the x-increment would be 1 and the y-increment would be 2, and for Express mode, the x-increment would be 1 and the y-increment would be 3. For these bitmaps it is intended that each scan line be repeated y-increment times when they are displayed.

たとえば、RAPICOM 450のビットマップには、Fine Detail、Quality、Expressの各モードがあります。Fine Detailモードではx増分とy増分はどちらも1、Qualityモードではx増分が1でy増分が2、Expressモードではx増分が1でy増分が3になります。これらのビットマップでは、表示するときに各走査線をy増分の回数だけ繰り返すことを意図しています。
