RFC 7833

A RADIUS Attribute, Binding, Profiles, Name Identifier Format, and Confirmation Methods for the Security Assertion Markup Language (SAML)

RFC 7833

セキュリティーアサーションマークアップ言語（SAML）のためのRADIUS属性、バインディング、プロファイル、名前識別子形式、および確認方法

Abstract

概要

This document describes the use of the Security Assertion Markup Language (SAML) with RADIUS in the context of the Application Bridging for Federated Access Beyond web (ABFAB) architecture. It defines two RADIUS attributes, a SAML binding, a SAML name identifier format, two SAML profiles, and two SAML confirmation methods. The RADIUS attributes permit encapsulation of SAML Assertions and protocol messages within RADIUS, allowing SAML entities to communicate using the binding. The two profiles describe the application of this binding for ABFAB authentication and assertion Query/Request, enabling a Relying Party to request authentication of, or assertions for, users or machines (clients). These clients may be named using a Network Access Identifier (NAI) name identifier format. Finally, the subject confirmation methods allow requests and queries to be issued for a previously authenticated user or machine without needing to explicitly identify them as the subject. The use of the artifacts defined in this document is not exclusive to ABFAB. They can be applied in any Authentication, Authorization, and Accounting (AAA) scenario, such as network access control.

この文書は、Webを超えた連携アクセスのためのアプリケーションブリッジング（Application Bridging for Federated Access Beyond web、ABFAB）アーキテクチャーの文脈において、セキュリティーアサーションマークアップ言語（Security Assertion Markup Language、SAML）をRADIUSとともに使用する方法を説明します。 この文書は、2つのRADIUS属性、1つのSAMLバインディング、1つのSAML名前識別子形式、2つのSAMLプロファイル、および2つのSAML確認方法を定義します。 RADIUS属性により、SAMLアサーションとプロトコルメッセージをRADIUS内にカプセル化できるようになり、SAMLエンティティーはこのバインディングを使って通信できるようになります。 2つのプロファイルは、ABFABの認証とアサーションのクエリー/リクエストにこのバインディングを適用する方法を説明しており、依拠当事者（Relying Party）がユーザーやマシン（クライアント）の認証、またはそれらに関するアサーションを要求できるようにします。 これらのクライアントには、ネットワークアクセス識別子（Network Access Identifier、NAI）名前識別子形式を使って名前を付けられます。 最後に、サブジェクト確認方法により、以前に認証されたユーザーやマシンをサブジェクトとして明示的に識別することなく、それらに対するリクエストやクエリーを発行できるようになります。 この文書で定義する成果物の使用はABFABに限定されません。 これらは、ネットワークアクセス制御など、あらゆる認証・認可・アカウンティング（Authentication, Authorization, and Accounting、AAA）のシナリオに適用できます。

1. Introduction

1. はじめに

Within the ABFAB (Application Bridging for Federated Access Beyond web) architecture [RFC7831], it is often desirable to convey Security Assertion Markup Language (SAML) Assertions and protocol messages.

ABFAB（Application Bridging for Federated Access Beyond web）アーキテクチャー[RFC7831]では、セキュリティーアサーションマークアップ言語（SAML）のアサーションとプロトコルメッセージを運ぶことが望ましい場面がよくあります。

SAML typically only considers the use of HTTP-based transports, known as bindings [OASIS.saml-bindings-2.0-os], which are primarily intended for use with the SAML V2.0 web browser single sign-on profile [OASIS.saml-profiles-2.0-os]. However, the goal of ABFAB is to extend the applicability of federated identity beyond the web to other applications by building on the Authentication, Authorization, and Accounting (AAA) framework. Consequently, there exists a requirement for SAML to integrate with the AAA framework and with protocols such as RADIUS [RFC2865] and Diameter [RFC6733], in addition to HTTP.

SAMLは通常、バインディング[OASIS.saml-bindings-2.0-os]と呼ばれるHTTPベースのトランスポートの使用しか考慮しておらず、これらは主にSAML V2.0 Webブラウザーシングルサインオンプロファイル[OASIS.saml-profiles-2.0-os]での使用を意図したものです。 しかし、ABFABの目標は、認証・認可・アカウンティング（AAA）フレームワークを基盤として、連携アイデンティティーの適用範囲をWebの外にある他のアプリケーションへと広げることです。 そのため、SAMLには、HTTPに加えて、AAAフレームワークや、RADIUS[RFC2865]やDiameter[RFC6733]などのプロトコルと統合するという要件があります。

In summary, this document specifies:

要約すると、この文書は次のものを規定します。

  • Two RADIUS attributes to encapsulate SAML Assertions and protocol messages, respectively.
  • A SAML RADIUS binding that defines how SAML Assertions and protocol messages can be transported by RADIUS within a SAML exchange.
  • A SAML name identifier format in the form of a Network Access Identifier.
  • A profile of the SAML Authentication Request Protocol that uses the SAML RADIUS binding to effect SAML-based authentication and authorization.
  • A profile of the SAML Assertion Query and Request Protocol that uses the SAML RADIUS binding to effect the query and request of SAML Assertions.
  • Two SAML subject confirmation methods for indicating that a user or machine client is the subject of an assertion.
  • SAMLアサーションとプロトコルメッセージをそれぞれカプセル化するための2つのRADIUS属性。
  • SAMLのやり取りの中で、SAMLアサーションとプロトコルメッセージをRADIUSでどのように転送できるかを定義するSAML RADIUSバインディング。
  • ネットワークアクセス識別子の形をとるSAML名前識別子形式。
  • SAML RADIUSバインディングを使ってSAMLベースの認証と認可を実現する、SAML認証リクエストプロトコルのプロファイル。
  • SAML RADIUSバインディングを使ってSAMLアサーションのクエリーとリクエストを実現する、SAMLアサーションクエリー・リクエストプロトコルのプロファイル。
  • ユーザーまたはマシンのクライアントがアサーションのサブジェクトであることを示すための、2つのSAMLサブジェクト確認方法。

This document adheres to the guidelines stipulated by [OASIS.saml-bindings-2.0-os] and [OASIS.saml-profiles-2.0-os] for defining new SAML bindings and profiles, respectively, and other conventions applied formally or otherwise within SAML. In particular, this document provides a "Required Information" section for the binding (Section 4.1) and profiles (Sections 7.1 and 8.1) that enumerate:

この文書は、新しいSAMLバインディングとプロファイルを定義するためにそれぞれ[OASIS.saml-bindings-2.0-os]と[OASIS.saml-profiles-2.0-os]が定めるガイドラインと、SAML内で正式に、あるいはそれ以外の形で適用されているその他の慣例に従います。 特に、この文書は、バインディング（セクション4.1）とプロファイル（セクション7.1と8.1）について、次のものを列挙する「必要な情報（Required Information）」セクションを設けています。

  • A URI that uniquely identifies the protocol binding or profile.
  • Postal or electronic contact information for the author.
  • A reference to previously defined bindings or profiles that the new binding updates or obsoletes.
  • In the case of a profile, any SAML confirmation method identifiers defined and/or utilized by the profile.
  • プロトコルバインディングまたはプロファイルを一意に識別するURI。
  • 作成者の郵便または電子的な連絡先情報。
  • 新しいバインディングが更新または廃止する、以前に定義されたバインディングまたはプロファイルへの参照。
  • プロファイルの場合は、そのプロファイルが定義または利用する（あるいはその両方の）SAML確認方法識別子。

3. RADIUS SAML Attributes

3. RADIUS SAML属性

The SAML RADIUS binding defined in Section 4 of this document uses two attributes to convey SAML Assertions and protocol messages [OASIS.saml-core-2.0-os]. Owing to the typical size of these structures, these attributes use the "Long Extended Type" format [RFC6929] to encapsulate their data. RADIUS entities MUST NOT include both attributes in the same RADIUS message, as they represent exclusive alternatives to convey SAML information.

この文書のセクション4で定義するSAML RADIUSバインディングは、SAMLアサーションとプロトコルメッセージ[OASIS.saml-core-2.0-os]を運ぶために2つの属性を使用します。 これらの構造は一般にサイズが大きいため、これらの属性はデータのカプセル化に「Long Extended Type」形式[RFC6929]を使用します。 これら2つの属性はSAML情報を運ぶための排他的な選択肢であるため、RADIUSエンティティーは同じRADIUSメッセージに両方の属性を含めてはなりません（MUST NOT）。

4. SAML RADIUS Binding

4. SAML RADIUSバインディング

The SAML RADIUS binding defines how RADIUS [RFC2865] can be used to enable a RADIUS client and server to exchange SAML Assertions and protocol messages.

SAML RADIUSバインディングは、RADIUSクライアントとサーバーがSAMLアサーションとプロトコルメッセージを交換できるようにするために、RADIUS[RFC2865]をどのように使用できるかを定義します。

4.2. Operation

4.2. 動作

In this specification, the Relying Party (RP) MUST trust any statement in the SAML messages from the Identity Provider (IdP) in the same way that it trusts information contained in RADIUS attributes. These entities MUST trust the RADIUS infrastructure to provide integrity of the SAML messages.

この仕様において、依拠当事者（Relying Party、RP）は、RADIUS属性に含まれる情報を信頼するのと同じように、アイデンティティープロバイダー（Identity Provider、IdP）からのSAMLメッセージ内のあらゆる記述を信頼しなければなりません（MUST）。 これらのエンティティーは、SAMLメッセージの完全性を提供するものとしてRADIUSインフラストラクチャーを信頼しなければなりません（MUST）。

Hence, it is REQUIRED that the RADIUS exchange be protected using Transport Layer Security (TLS) encryption for RADIUS [RFC6614] to provide confidentiality and integrity protection, unless alternative methods to ensure them are used, such as IPsec tunnels or a sufficiently secure internal network.

したがって、IPsecトンネルや十分に安全な内部ネットワークなど、機密性と完全性を確保する別の方法を使用する場合を除き、機密性と完全性保護を提供するために、RADIUSのやり取りをRADIUSのためのトランスポート層セキュリティー（TLS）暗号化[RFC6614]を使って保護することが要求されています（REQUIRED）。

Implementations of this profile can take advantage of mechanisms to permit the transport of longer SAML messages over RADIUS transports, such as the support of fragmentation of RADIUS packets [RFC7499] or larger packets for RADIUS over TCP [RADIUS-Large-Pkts].

このプロファイルの実装は、RADIUSパケットの断片化のサポート[RFC7499]や、TCP上のRADIUSのためのより大きなパケット[RADIUS-Large-Pkts]など、より長いSAMLメッセージをRADIUSトランスポートで転送できるようにするメカニズムを活用できます。

There are two system models for the use of SAML over RADIUS. The first is a request-response model, using the RADIUS SAML-Protocol attribute defined in Section 3 to encapsulate the SAML protocol messages.

RADIUS上でSAMLを使用するためのシステムモデルは2つあります。 1つ目はリクエスト・レスポンスモデルで、セクション3で定義するRADIUS SAML-Protocol属性を使ってSAMLプロトコルメッセージをカプセル化します。

  1. The RADIUS client, acting as an RP, transmits a SAML request element within a RADIUS Access-Request message. This message MUST include a single instance of the RADIUS User-Name attribute whose value MUST conform to the Network Access Identifier [RFC7542] scheme. The RP MUST NOT include more than one SAML request element.
  2. The RADIUS server, acting as an IdP, returns a SAML protocol message within a RADIUS Access-Accept or Access-Reject message. These messages necessarily conclude a RADIUS exchange, and therefore this is the only opportunity for the IdP to send a response in the context of this exchange. The IdP MUST NOT include more than one SAML response. An IdP that refuses to perform a message exchange with the RP can silently discard the SAML request (this could subsequently be followed by a RADIUS Access-Reject, as the same conditions that cause the IdP to discard the SAML request may also cause the RADIUS server to fail to authenticate).
  1. RPとして動作するRADIUSクライアントは、RADIUS Access-Requestメッセージ内でSAMLリクエスト要素を送信します。 このメッセージには、RADIUS User-Name属性のインスタンスを1つだけ含めなければなりません（MUST）。 その値は、ネットワークアクセス識別子[RFC7542]の方式に準拠しなければなりません（MUST）。 RPは、2つ以上のSAMLリクエスト要素を含めてはなりません（MUST NOT）。
  2. IdPとして動作するRADIUSサーバーは、RADIUS Access-AcceptメッセージまたはAccess-Rejectメッセージ内でSAMLプロトコルメッセージを返します。 これらのメッセージは必ずRADIUSのやり取りを終了させるため、このやり取りの文脈においてIdPがレスポンスを送信できる機会はこれが唯一です。 IdPは、2つ以上のSAMLレスポンスを含めてはなりません（MUST NOT）。 RPとのメッセージ交換の実行を拒否するIdPは、SAMLリクエストを黙って破棄できます（IdPにSAMLリクエストを破棄させるのと同じ条件によってRADIUSサーバーの認証も失敗する可能性があるため、その後にRADIUS Access-Rejectが続くことがあります）。

The second system model permits a RADIUS server acting as an IdP to use the RADIUS SAML-Assertion attribute defined in Section 3 to encapsulate an unsolicited SAML Assertion. This attribute MUST be included in a RADIUS Access-Accept message. When included, the attribute MUST contain a single SAML Assertion.

2つ目のシステムモデルでは、IdPとして動作するRADIUSサーバーが、セクション3で定義するRADIUS SAML-Assertion属性を使って、要求されていないSAMLアサーションをカプセル化できます。 この属性は、RADIUS Access-Acceptメッセージに含めなければなりません（MUST）。 含める場合、この属性にはSAMLアサーションを1つだけ含めなければなりません（MUST）。

RADIUS servers MUST NOT include both the SAML-Protocol and the SAML-Assertion attribute in the same RADIUS message. If an IdP is producing a response to a SAML request, then the first system model is used. An IdP MAY ignore a SAML request and send an unsolicited assertion using the second system model (that is, using the RADIUS SAML-Assertion attribute).

RADIUSサーバーは、同じRADIUSメッセージにSAML-Protocol属性とSAML-Assertion属性の両方を含めてはなりません（MUST NOT）。 IdPがSAMLリクエストに対するレスポンスを生成する場合は、1つ目のシステムモデルを使用します。 IdPは、SAMLリクエストを無視して、2つ目のシステムモデルを使って（つまり、RADIUS SAML-Assertion属性を使って）要求されていないアサーションを送信してもよいです（MAY）。

In either system model, IdPs SHOULD return a RADIUS State attribute as part of the Access-Accept message so that future SAML queries or requests can be run against the same context of an authentication exchange.

どちらのシステムモデルにおいても、将来のSAMLクエリーやリクエストを認証のやり取りと同じコンテキストに対して実行できるように、IdPはAccess-Acceptメッセージの一部としてRADIUS State属性を返すべきです（SHOULD）。

This binding is intended to be composed with other uses of RADIUS, such as network access. Therefore, other arbitrary RADIUS attributes MAY be used in either the request or response.

このバインディングは、ネットワークアクセスなど、RADIUSの他の用途と組み合わせることを意図しています。 したがって、リクエストとレスポンスのどちらにおいても、他の任意のRADIUS属性を使用してもよいです（MAY）。

In the case of a SAML processing error, the RADIUS server MAY include a SAML response message with an appropriate value for the <samlp:Status> element within the Access-Accept or Access-Reject packet to notify the client. Alternatively, the RADIUS server can respond without a SAML-Protocol attribute.

SAMLの処理エラーが発生した場合、RADIUSサーバーは、クライアントに通知するために、<samlp:Status>要素に適切な値を設定したSAMLレスポンスメッセージをAccess-AcceptパケットまたはAccess-Rejectパケットに含めてもよいです（MAY）。 あるいは、RADIUSサーバーは、SAML-Protocol属性を含めずに応答することもできます。

4.3. Processing of Names

4.3. 名前の処理

SAML entities using profiles making use of this binding will typically possess both the SAML and AAA names of their correspondents. Frequently, these entities will need to apply policies using these names -- for example, when deciding to release attributes. Often, these policies will be security-sensitive, and so it is important that policy is applied on these names consistently.

このバインディングを利用するプロファイルを使用するSAMLエンティティーは、通常、通信相手のSAML名とAAA名の両方を保持しています。 これらのエンティティーは、たとえば属性の開示を決定する場合など、これらの名前を使ってポリシーを適用する必要がしばしばあります。 多くの場合、これらのポリシーはセキュリティー上重要なものであるため、これらの名前に対して一貫してポリシーを適用することが重要です。

4.3.1. AAA Names

4.3.1. AAA名

These rules relate to the processing of AAA names by SAML entities using profiles making use of this binding.

これらの規則は、このバインディングを利用するプロファイルを使用するSAMLエンティティーによるAAA名の処理に関するものです。

  • IdPs SHOULD apply policy based on the RP's identity associated with the RADIUS Access-Request.
  • RPs SHOULD apply policy based on the NAI realm associated with the RADIUS Access-Accept.
  • IdPは、RADIUS Access-Requestに関連付けられたRPのアイデンティティーに基づいてポリシーを適用すべきです（SHOULD）。
  • RPは、RADIUS Access-Acceptに関連付けられたNAIレルムに基づいてポリシーを適用すべきです（SHOULD）。

4.3.2. SAML Names

4.3.2. SAML名

These rules relate to the processing of SAML names by SAML entities using profiles making use of this binding.

これらの規則は、このバインディングを利用するプロファイルを使用するSAMLエンティティーによるSAML名の処理に関するものです。

IdPs MAY apply policy based on the RP's SAML entityID. In such cases, at least one of the following methods is required in order to establish a relationship between the SAML name and the AAA name of the RP:

IdPは、RPのSAML entityIDに基づいてポリシーを適用してもよいです（MAY）。 その場合、SAML名とRPのAAA名との関係を確立するために、次の方法の少なくとも1つが必要です。

  • RADIUS client identity in trusted SAML metadata (as described in Section 4.3.3).
  • RADIUS client identity in trusted digitally signed SAML request.
  • 信頼できるSAMLメタデータ内のRADIUSクライアントのアイデンティティー（セクション4.3.3で説明します）。
  • 信頼できるデジタル署名付きSAMLリクエスト内のRADIUSクライアントのアイデンティティー。

A digitally signed SAML request without the RADIUS client identity is not sufficient, since a malicious RADIUS entity can observe a SAML message and include it in a different RADIUS message without the consent of the issuer of that SAML message. If an IdP were to process the SAML message without confirming that it applied to the RADIUS message, inappropriate policy would be used.

RADIUSクライアントのアイデンティティーを含まないデジタル署名付きSAMLリクエストでは不十分です。 なぜなら、悪意のあるRADIUSエンティティーは、SAMLメッセージを観測し、そのSAMLメッセージの発行者の同意なしに、それを別のRADIUSメッセージに含めることができるからです。 IdPが、SAMLメッセージがそのRADIUSメッセージに適用されるものであることを確認せずにそのSAMLメッセージを処理すると、不適切なポリシーが使用されることになります。

RPs MAY apply policy based on the SAML issuer's entityID. In such cases, at least one of the following methods is required in order to establish a relationship between the SAML name and the AAA name of the IdP:

RPは、SAML発行者のentityIDに基づいてポリシーを適用してもよいです（MAY）。 その場合、SAML名とIdPのAAA名との関係を確立するために、次の方法の少なくとも1つが必要です。

  • RADIUS realm in trusted SAML metadata (as described in Section 4.3.3).
  • RADIUS realm in trusted digitally signed SAML response or assertion.
  • 信頼できるSAMLメタデータ内のRADIUSレルム（セクション4.3.3で説明します）。
  • 信頼できるデジタル署名付きSAMLレスポンスまたはアサーション内のRADIUSレルム。

A digitally signed SAML response alone is not sufficient, for the same reasons as those described above for SAML requests.

SAMLリクエストについて上で説明したのと同じ理由により、デジタル署名付きSAMLレスポンスだけでは不十分です。

7. ABFAB Authentication Profile

7. ABFAB認証プロファイル

In the scenario supported by the ABFAB Authentication Profile, a client controlling a User Agent requests access to an RP. The RP uses RADIUS to authenticate the client. In particular, the RP, acting as a RADIUS client, attempts to validate the client's credentials against a RADIUS server acting as the client's IdP. If the IdP successfully authenticates the client, it produces an authentication assertion that is consumed by the RP. This assertion MAY include a name identifier that can be used between the RP and the IdP to refer to the client.

ABFAB認証プロファイルがサポートするシナリオでは、ユーザーエージェントを操作するクライアントがRPへのアクセスを要求します。 RPは、RADIUSを使ってクライアントを認証します。 具体的には、RADIUSクライアントとして動作するRPが、クライアントのIdPとして動作するRADIUSサーバーに対して、クライアントのクレデンシャルの検証を試みます。 IdPがクライアントの認証に成功すると、IdPはRPが消費する認証アサーションを生成します。 このアサーションには、RPとIdPの間でクライアントを指すために使用できる名前識別子を含めてもよいです（MAY）。

7.2. Profile Overview

7.2. プロファイルの概要

To implement this scenario, this profile of the SAML Authentication Request Protocol MUST be used in conjunction with the SAML RADIUS binding defined in Section 4.

このシナリオを実装するには、SAML認証リクエストプロトコルのこのプロファイルを、セクション4で定義するSAML RADIUSバインディングと組み合わせて使用しなければなりません（MUST）。

This profile is based on the SAML V2.0 web browser single sign-on profile [OASIS.saml-profiles-2.0-os]. There are some important differences; specifically:

このプロファイルは、SAML V2.0 Webブラウザーシングルサインオンプロファイル[OASIS.saml-profiles-2.0-os]に基づいています。 いくつかの重要な違いがあり、具体的には次のとおりです。

Authentication:
This profile does not require the use of any particular authentication method. The ABFAB architecture does require the use of the Extensible Authentication Protocol (EAP) [RFC3579], but this specification may be used in other non-ABFAB scenarios.
Bindings:
This profile does not use HTTP-based bindings. Instead, all SAML protocol messages are transported using the SAML RADIUS binding defined in Section 4. This is intended to reduce the number of bindings that implementations must support to be interoperable.
Requests:
The profile does not permit the RP to name the <saml:Subject> of the <samlp:AuthnRequest>. This is intended to simplify implementation and interoperability.
Responses:
The profile only permits the IdP to return a single SAML message or assertion that MUST contain exactly one authentication statement. Other statements may be included within this assertion at the discretion of the IdP. This is intended to simplify implementation and interoperability.
認証（Authentication）：
このプロファイルは、特定の認証方法の使用を必要としません。 ABFABアーキテクチャーは拡張認証プロトコル（EAP）[RFC3579]の使用を必要としますが、この仕様はABFAB以外のシナリオで使用されることもあります。
バインディング（Bindings）：
このプロファイルは、HTTPベースのバインディングを使用しません。 その代わりに、すべてのSAMLプロトコルメッセージは、セクション4で定義するSAML RADIUSバインディングを使って転送されます。 これは、相互運用可能であるために実装がサポートしなければならないバインディングの数を減らすことを意図しています。
リクエスト（Requests）：
このプロファイルでは、RPが<samlp:AuthnRequest>の<saml:Subject>を指定することを許可しません。 これは、実装と相互運用性を単純にすることを意図しています。
レスポンス（Responses）：
このプロファイルでは、IdPが単一のSAMLメッセージまたはアサーションを返すことだけを許可し、そこにはちょうど1つの認証ステートメントを含めなければなりません（MUST）。 IdPの裁量により、このアサーション内に他のステートメントを含めることもできます。 これは、実装と相互運用性を単純にすることを意図しています。

The following steps are described by the profile. Within an individual step, there may be one or more actual message exchanges.

このプロファイルでは、次の手順を説明します。 個々の手順の中では、実際のメッセージ交換が1回以上行われることがあります。

  1. Client request to RP (Section 7.3.1): In step 1, the client, via a User Agent, makes a request for a secured resource at the RP. The RP determines that no security context for the client exists and initiates the authentication process.
  2. RP issues <samlp:AuthnRequest> to IdP (Section 7.3.2). In step 2, the RP may optionally issue a <samlp:AuthnRequest> message to be delivered to the IdP using the SAML-Protocol RADIUS attribute.
  3. IdP identifies client (Section 7.3.3). In step 3, the client is authenticated and identified by the IdP, while honoring any requirements imposed by the RP in the <samlp:AuthnRequest> message if provided.
  4. IdP issues <samlp:Response> to RP (Section 7.3.4). In step 4, the IdP issues a <samlp:Response> message to the RP using the SAML RADIUS binding. The response either indicates an error or includes a SAML authentication statement in exactly one SAML Assertion. If the RP did not send a <samlp:AuthnRequest>, the IdP issues an unsolicited <samlp:Assertion>, as described in Section 7.4.4.
  5. RP grants or denies access to client (Section 7.3.5). In step 5, having received the response from the IdP, the RP can respond to the client with its own error, or can establish its own security context for the client and return the requested resource.
  1. クライアントからRPへのリクエスト（セクション7.3.1）：手順1では、クライアントがユーザーエージェントを介して、RPにある保護されたリソースへのリクエストを行います。 RPは、そのクライアントのセキュリティーコンテキストが存在しないと判断し、認証処理を開始します。
  2. RPがIdPに<samlp:AuthnRequest>を発行する（セクション7.3.2）。 手順2では、RPは任意で、SAML-Protocol RADIUS属性を使ってIdPに配送される<samlp:AuthnRequest>メッセージを発行することがあります。
  3. IdPがクライアントを識別する（セクション7.3.3）。 手順3では、<samlp:AuthnRequest>メッセージが提供されている場合はその中でRPが課した要件を尊重しながら、IdPがクライアントを認証し識別します。
  4. IdPがRPに<samlp:Response>を発行する（セクション7.3.4）。 手順4では、IdPがSAML RADIUSバインディングを使ってRPに<samlp:Response>メッセージを発行します。 このレスポンスは、エラーを示すか、ちょうど1つのSAMLアサーション内にSAML認証ステートメントを含むかのいずれかです。 RPが<samlp:AuthnRequest>を送信しなかった場合、IdPはセクション7.4.4で説明するように、要求されていない<samlp:Assertion>を発行します。
  5. RPがクライアントへのアクセスを許可または拒否する（セクション7.3.5）。 手順5では、IdPからレスポンスを受信したRPは、独自のエラーでクライアントに応答するか、クライアントのための独自のセキュリティーコンテキストを確立して要求されたリソースを返すことができます。

7.3. Profile Description

7.3. プロファイルの説明

The ABFAB Authentication Profile is a profile of the SAML V2.0 Authentication Request Protocol [OASIS.saml-core-2.0-os]. Where both specifications conflict, the ABFAB Authentication Profile takes precedence.

ABFAB認証プロファイルは、SAML V2.0認証リクエストプロトコル[OASIS.saml-core-2.0-os]のプロファイルです。 両方の仕様が矛盾する場合は、ABFAB認証プロファイルが優先されます。

7.3.1. Client Request to Relying Party

7.3.1. クライアントから依拠当事者へのリクエスト

The profile is initiated by an arbitrary client request to the RP. There are no restrictions on the form of the request. The RP is free to use any means it wishes to associate the subsequent interactions with the original request. The RP, acting as a RADIUS client, attempts to authenticate the client.

このプロファイルは、クライアントからRPへの任意のリクエストによって開始されます。 リクエストの形式に制限はありません。 RPは、後続のやり取りを元のリクエストに関連付けるために、望む任意の手段を自由に使用できます。 RADIUSクライアントとして動作するRPは、クライアントの認証を試みます。

7.3.2. Relying Party Issues <samlp:AuthnRequest> to Identity Provider

7.3.2. 依拠当事者がアイデンティティープロバイダーに<samlp:AuthnRequest>を発行する

The RP uses RADIUS to communicate with the client's IdP. The RP MAY include a <samlp:AuthnRequest> within this RADIUS Access-Request message using the SAML-Protocol RADIUS attribute. The "next hop" destination MAY be the IdP or, alternatively, an intermediate RADIUS proxy.

RPは、RADIUSを使ってクライアントのIdPと通信します。 RPは、SAML-Protocol RADIUS属性を使って、このRADIUS Access-Requestメッセージ内に<samlp:AuthnRequest>を含めてもよいです（MAY）。 「ネクストホップ」の宛先は、IdPであっても、あるいは中間のRADIUSプロキシーであってもよいです（MAY）。

Profile-specific rules for the contents of the <samlp:AuthnRequest> element are given in Section 7.4.1.

<samlp:AuthnRequest>要素の内容に関するプロファイル固有の規則は、セクション7.4.1で示します。

7.3.3. Identity Provider Identifies Client

7.3.3. アイデンティティープロバイダーがクライアントを識別する

The IdP MUST establish the identity of the client using a RADIUS authentication method, or else it will return an error. If the ForceAuthn attribute in the <samlp:AuthnRequest> element (if sent by the RP) is present and true, the IdP MUST freshly establish this identity rather than relying on any existing session state it may have with the client (for example, TLS state that may be used for session resumption). Otherwise, and in all other respects, the IdP may use any method to authenticate the client, subject to the constraints called out in the <samlp:AuthnRequest> message.

IdPは、RADIUS認証方法を使ってクライアントのアイデンティティーを確立しなければなりません（MUST）。 そうできない場合は、エラーを返します。 （RPから送信された場合の）<samlp:AuthnRequest>要素のForceAuthn属性が存在し、かつtrueである場合、IdPは、クライアントとの間に存在する可能性のある既存のセッション状態（たとえば、セッション再開に使用される可能性のあるTLSの状態）に依存するのではなく、このアイデンティティーを新たに確立しなければなりません（MUST）。 それ以外の場合、およびその他のあらゆる点において、IdPは、<samlp:AuthnRequest>メッセージで示された制約に従う限り、任意の方法を使ってクライアントを認証できます。

7.3.4. Identity Provider Issues <samlp:Response> to Relying Party

7.3.4. アイデンティティープロバイダーが依拠当事者に<samlp:Response>を発行する

The IdP MUST conclude the authentication in a manner consistent with the RADIUS authentication result. The IdP MAY issue a <samlp:Response> message to the RP that is consistent with the authentication result, as described in [OASIS.saml-core-2.0-os]. This SAML response is delivered to the RP using the SAML RADIUS binding described in Section 4.

IdPは、RADIUSの認証結果と一致する方法で認証を終了しなければなりません（MUST）。 IdPは、[OASIS.saml-core-2.0-os]で説明されているように、認証結果と一致する<samlp:Response>メッセージをRPに発行してもよいです（MAY）。 このSAMLレスポンスは、セクション4で説明するSAML RADIUSバインディングを使ってRPに配送されます。

Profile-specific rules regarding the contents of the <samlp:Response> element are given in Section 7.4.2.

<samlp:Response>要素の内容に関するプロファイル固有の規則は、セクション7.4.2で示します。

7.3.5. Relying Party Grants or Denies Access to Client

7.3.5. 依拠当事者がクライアントへのアクセスを許可または拒否する

If a <samlp:Response> message is issued by the IdP, the RP MUST process that message and any enclosed assertion elements as described in [OASIS.saml-core-2.0-os]. Any subsequent use of the assertion elements is at the discretion of the RP, subject to any restrictions contained within the assertions themselves or from any previously established out-of-band policy that governs the interaction between the IdP and the RP.

IdPから<samlp:Response>メッセージが発行された場合、RPは、[OASIS.saml-core-2.0-os]で説明されているように、そのメッセージと、そこに含まれるすべてのアサーション要素を処理しなければなりません（MUST）。 その後のアサーション要素の使用はRPの裁量に任されますが、アサーション自体に含まれる制限や、IdPとRPの間のやり取りを規定する、以前に確立された帯域外のポリシーによる制限に従います。

7.4. Use of Authentication Request Protocol

7.4. 認証リクエストプロトコルの使用

This profile is based on the Authentication Request Protocol defined in [OASIS.saml-core-2.0-os]. In the nomenclature of actors enumerated in Section 3.4 of that document, the RP is the requester, the User Agent is the attesting entity, and the client is the subject.

このプロファイルは、[OASIS.saml-core-2.0-os]で定義されている認証リクエストプロトコルに基づいています。 その文書のセクション3.4で列挙されている行為者の呼び方では、RPはリクエスター（requester）、ユーザーエージェントは証明エンティティー（attesting entity）、クライアントはサブジェクト（subject）です。

7.4.1. <samlp:AuthnRequest> Usage

7.4.1. <samlp:AuthnRequest>の使用法

The RP MUST NOT include a <saml:Subject> element in the request. The authenticated RADIUS identity identifies the client to the IdP.

RPは、リクエストに<saml:Subject>要素を含めてはなりません（MUST NOT）。 認証されたRADIUSアイデンティティーが、IdPに対してクライアントを識別します。

An RP MAY include any message content described in Section 3.4.1 of [OASIS.saml-core-2.0-os]. All processing rules are as defined in [OASIS.saml-core-2.0-os].

RPは、[OASIS.saml-core-2.0-os]のセクション3.4.1で説明されている任意のメッセージ内容を含めてもよいです（MAY）。 すべての処理規則は、[OASIS.saml-core-2.0-os]で定義されているとおりです。

If the RP wishes to permit the IdP to establish a new identifier for the client if none exists, it MUST include a <saml:NameIDPolicy> element with the AllowCreate attribute set to "true". Otherwise, only a client for whom the IdP has previously established an identifier usable by the RP can be authenticated successfully.

識別子が存在しない場合にIdPがクライアントの新しい識別子を確立することをRPが許可したい場合、RPは、AllowCreate属性を「true」に設定した<saml:NameIDPolicy>要素を含めなければなりません（MUST）。 そうでない場合は、RPが使用できる識別子をIdPが以前に確立したクライアントだけが、認証に成功できます。

The <samlp:AuthnRequest> message MAY be signed. Authentication and integrity are also provided by the SAML RADIUS binding.

<samlp:AuthnRequest>メッセージには署名してもよいです（MAY）。 認証と完全性は、SAML RADIUSバインディングによっても提供されます。

7.4.2. <samlp:Response> Message Usage

7.4.2. <samlp:Response>メッセージの使用法

If the IdP cannot or will not satisfy the request, it MUST respond with a <samlp:Response> message containing an appropriate error status code or codes and/or respond with a RADIUS Access-Reject message.

IdPがリクエストを満たすことができない、または満たすつもりがない場合、IdPは、適切なエラーステータスコードを含む<samlp:Response>メッセージで応答するか、RADIUS Access-Rejectメッセージで応答するか、あるいはその両方を行わなければなりません（MUST）。

If the IdP wishes to return an error, it MUST NOT include any assertions in the <samlp:Response> message. Otherwise, if the request is successful (or if the response is not associated with a request), the <samlp:Response> element is subject to the following constraints:

IdPがエラーを返したい場合、IdPは<samlp:Response>メッセージにアサーションを含めてはなりません（MUST NOT）。 そうではなく、リクエストが成功した場合（またはレスポンスがリクエストに関連付けられていない場合）、<samlp:Response>要素には次の制約が課されます。

  • It MAY be signed.
  • It MUST contain exactly one assertion. The <saml:Subject> element of this assertion MUST refer to the authenticated RADIUS user.
  • The assertion MUST contain a <saml:AuthnStatement>. Also, the assertion MUST contain a <saml:Subject> element with at least one <saml:SubjectConfirmation> element containing a <saml:ConfirmationMethod> element of urn:ietf:params:abfab:cm:user or urn:ietf:params:abfab:cm:machine that reflects the authentication of the client to the IdP. Since the <samlp:Response> message is in response to a <samlp:AuthnRequest>, the InResponseTo attribute (in both the <saml:SubjectConfirmationData> and <saml:Response> elements) MUST match the request's ID. The <saml:Subject> element MAY use the NAI name identifier format described in Section 5 to establish an identifier between the RP and the IdP.
  • Other conditions MAY be included as requested by the RP or at the discretion of the IdP. The IdP is NOT obligated to honor the requested set of conditions in the <samlp:AuthnRequest>, if any.
  • 署名されていてもよいです（MAY）。
  • ちょうど1つのアサーションを含まなければなりません（MUST）。 このアサーションの<saml:Subject>要素は、認証されたRADIUSユーザーを指さなければなりません（MUST）。
  • アサーションは、<saml:AuthnStatement>を含まなければなりません（MUST）。 また、アサーションは、IdPに対するクライアントの認証を反映した、urn:ietf:params:abfab:cm:userまたはurn:ietf:params:abfab:cm:machineの<saml:ConfirmationMethod>要素を含む<saml:SubjectConfirmation>要素を少なくとも1つ持つ<saml:Subject>要素を含まなければなりません（MUST）。 <samlp:Response>メッセージは<samlp:AuthnRequest>に対するレスポンスであるため、（<saml:SubjectConfirmationData>要素と<saml:Response>要素の両方の）InResponseTo属性は、リクエストのIDと一致しなければなりません（MUST）。 <saml:Subject>要素は、RPとIdPの間で識別子を確立するために、セクション5で説明するNAI名前識別子形式を使用してもよいです（MAY）。
  • RPの要求に応じて、またはIdPの裁量により、他の条件を含めてもよいです（MAY）。 IdPには、<samlp:AuthnRequest>で要求された条件の集合があったとしても、それを尊重する義務はありません（NOT obligated）。

7.4.3. <samlp:Response> Message Processing Rules

7.4.3. <samlp:Response>メッセージの処理規則

The RP MUST do the following:

RPは、次のことを行わなければなりません（MUST）。

  • Assume that the client's identifier implied by a SAML <Subject> element, if present, takes precedence over an identifier implied by the RADIUS User-Name attribute.
  • Verify that the InResponseTo attribute in the "RADIUS State" <saml:SubjectConfirmationData> equals the ID of its original <samlp:AuthnRequest> message, unless the response is unsolicited, in which case the attribute MUST NOT be present.
  • If a <saml:AuthnStatement> used to establish a security context for the client contains a SessionNotOnOrAfter attribute, the security context SHOULD be discarded once this time is reached, unless the RP reestablishes the client's identity by repeating the use of this profile.
  • Verify that any assertions relied upon are valid according to processing rules specified in [OASIS.saml-core-2.0-os].
  • Any assertion that is not valid or whose subject confirmation requirements cannot be met MUST be discarded and MUST NOT be used to establish a security context for the client.
  • SAMLの<Subject>要素が存在する場合、それが示すクライアントの識別子が、RADIUS User-Name属性が示す識別子よりも優先されるものとみなします。
  • 「RADIUS State」の<saml:SubjectConfirmationData>内のInResponseTo属性が、元の<samlp:AuthnRequest>メッセージのIDと等しいことを検証します。 ただし、レスポンスが要求されていないものである場合を除きます。 その場合、この属性は存在してはなりません（MUST NOT）。
  • クライアントのセキュリティーコンテキストを確立するために使用した<saml:AuthnStatement>がSessionNotOnOrAfter属性を含む場合、RPがこのプロファイルを再度使用してクライアントのアイデンティティーを再確立しない限り、その時刻に達した時点でセキュリティーコンテキストを破棄すべきです（SHOULD）。
  • 依拠するすべてのアサーションが、[OASIS.saml-core-2.0-os]で規定されている処理規則に従って有効であることを検証します。
  • 有効でないアサーション、またはサブジェクト確認の要件を満たせないアサーションは、破棄しなければなりません（MUST）。 また、そのようなアサーションをクライアントのセキュリティーコンテキストの確立に使用してはなりません（MUST NOT）。

7.4.4. Unsolicited Responses

7.4.4. 非要請レスポンス

An IdP MAY initiate this profile by delivering an unsolicited assertion to an RP. This MUST NOT contain any <saml:SubjectConfirmationData> elements containing an InResponseTo attribute.

IdPは、要求されていないアサーションをRPに配送することで、このプロファイルを開始してもよいです（MAY）。 このアサーションは、InResponseTo属性を含む<saml:SubjectConfirmationData>要素を含んではなりません（MUST NOT）。

7.4.5. Use of the SAML RADIUS Binding

7.4.5. SAML RADIUSバインディングの使用

It is RECOMMENDED that the RADIUS exchange be protected using TLS encryption for RADIUS [RFC6614] to provide confidentiality and integrity protection.

機密性と完全性保護を提供するために、RADIUSのやり取りをRADIUSのためのTLS暗号化[RFC6614]を使って保護することが推奨されます（RECOMMENDED）。

7.4.6. Use of XML Signatures

7.4.6. XML署名の使用

This profile calls for the use of SAML elements that support XML signatures. To promote interoperability, implementations of this profile MUST NOT require the use of XML signatures. Implementations MAY choose to use XML signatures.

このプロファイルは、XML署名をサポートするSAML要素の使用を求めています。 相互運用性を促進するため、このプロファイルの実装は、XML署名の使用を必要としてはなりません（MUST NOT）。 実装は、XML署名を使用することを選択してもよいです（MAY）。

7.4.7. Metadata Considerations

7.4.7. メタデータに関する考慮事項

There are no metadata considerations particular to this profile, aside from those applying to the use of the RADIUS binding.

RADIUSバインディングの使用に適用されるもの以外に、このプロファイルに特有のメタデータに関する考慮事項はありません。

This profile is identical to the SAML V2.0 Assertion Query/Request Profile, with the following exceptions:

このプロファイルは、次の例外を除き、SAML V2.0アサーションクエリー/リクエストプロファイルと同一です。

  • When processing the SAML request, the IdP MUST give precedence to the client's identifier implied by the RADIUS State attribute, if present, over the identifier implied by the SAML request's <Subject>, if any.
  • In respect to Sections 6.3.1 and 6.5 of [OASIS.saml-profiles-2.0-os], this profile does not consider the use of metadata (as in [OASIS.saml-metadata-2.0-os]). See Section 8.3.4.
  • In respect to Sections 6.3.2, 6.4.1, and 6.4.2 of [OASIS.saml-profiles-2.0-os], this profile additionally stipulates that implementations of this profile MUST NOT require the use of XML signatures. See Section 8.3.3.
  • SAMLリクエストを処理する際、IdPは、RADIUS State属性が存在する場合はそれが示すクライアントの識別子を、SAMLリクエストの<Subject>があればそれが示す識別子よりも優先しなければなりません（MUST）。
  • [OASIS.saml-profiles-2.0-os]のセクション6.3.1と6.5に関して、このプロファイルは（[OASIS.saml-metadata-2.0-os]にあるような）メタデータの使用を考慮しません。 セクション8.3.4を参照してください。
  • [OASIS.saml-profiles-2.0-os]のセクション6.3.2、6.4.1、および6.4.2に関して、このプロファイルはさらに、このプロファイルの実装がXML署名の使用を必要としてはなりません（MUST NOT）と規定します。 セクション8.3.3を参照してください。

8.3.2. Use of the SAML RADIUS Binding

8.3.2. SAML RADIUSバインディングの使用

The RADIUS Access-Request sent by the RP:

RPが送信するRADIUS Access-Requestは、次のとおりです。

  • MUST include an instance of the RADIUS Service-Type attribute, having a value of Authorize-Only.
  • SHOULD include the RADIUS State attribute, where this Query/Request pertains to a previously authenticated client.
  • 値がAuthorize-OnlyであるRADIUS Service-Type属性のインスタンスを含まなければなりません（MUST）。
  • このクエリー/リクエストが以前に認証されたクライアントに関するものである場合は、RADIUS State属性を含めるべきです（SHOULD）。

When processing the SAML request, the IdP MUST give precedence to the client's identifier implied by the RADIUS State attribute over the identifier implied by the SAML request's <Subject>, if any.

SAMLリクエストを処理する際、IdPは、RADIUS State属性が示すクライアントの識別子を、SAMLリクエストの<Subject>があればそれが示す識別子よりも優先しなければなりません（MUST）。

機密性と完全性保護を提供するために、RADIUSのやり取りをRADIUSのためのTLS暗号化[RFC6614]を使って保護することが推奨されます（RECOMMENDED）。

このプロファイルは、XML署名をサポートするSAML要素の使用を求めています。 相互運用性を促進するため、このプロファイルの実装は、XML署名の使用を必要としてはなりません（MUST NOT）。 実装は、XML署名を使用することを選択してもよいです（MAY）。

9. Privacy Considerations

9. プライバシーに関する考慮事項

The profiles defined in this document allow an RP to request specific information about the client and allow an IdP to disclose information about that client. In this sense, IdPs MUST apply policy to decide what information is released to a particular RP. Moreover, the identity of the client is typically hidden from the RP unless provided by the IdP. Conversely, the RP does typically know the realm of the IdP, as it is required to route the RADIUS packets to the right destination.

この文書で定義するプロファイルにより、RPはクライアントに関する特定の情報を要求でき、IdPはそのクライアントに関する情報を開示できます。 この意味で、IdPは、特定のRPにどの情報を開示するかを決定するためにポリシーを適用しなければなりません（MUST）。 さらに、クライアントのアイデンティティーは、IdPが提供しない限り、通常はRPから隠されています。 逆に、RADIUSパケットを正しい宛先にルーティングするために必要であるため、RPは通常、IdPのレルムを知っています。

The kind of information that is released by the IdP can include generic attributes such as affiliation shared by many clients. But even these generic attributes can help to identify a specific client. Other kinds of attributes may also provide an RP with the ability to link the same client between different sessions. Finally, other kinds of attributes might provide a group of RPs with the ability to link the client between them or with personally identifiable information about the client.

IdPが開示する情報の種類には、多くのクライアントが共有する所属などの一般的な属性が含まれることがあります。 しかし、こうした一般的な属性であっても、特定のクライアントの識別に役立つことがあります。 他の種類の属性によって、RPが異なるセッション間で同じクライアントを結び付けられるようになることもあります。 最後に、さらに別の種類の属性によって、RPのグループがそれらの間でクライアントを結び付けられるようになったり、クライアントに関する個人を特定できる情報を得られるようになったりする可能性があります。

These profiles do not directly provide a client with a mechanism to express preferences about what information is released. That information can be expressed out of band, for example, as part of the enrollment process.

これらのプロファイルは、どの情報を開示するかについての希望をクライアントが表明するためのメカニズムを直接には提供しません。 その情報は、たとえば登録手続きの一部として、帯域外で表明できます。

The RP may disclose privacy-sensitive information about itself as part of the request, although this is unlikely in typical deployments.

RPは、リクエストの一部として、自身に関するプライバシー上機微な情報を開示することがありますが、一般的な展開ではその可能性は低いと考えられます。

If RADIUS proxies are used and encryption is not used, the attributes disclosed by the IdP are visible to the proxies. This is a significant privacy exposure in some deployments. Ongoing work is exploring mechanisms for creating TLS connections directly between the RADIUS client and the RADIUS server to reduce this exposure. If proxies are used, the impact of exposing SAML Assertions to the proxies needs to be carefully considered.

RADIUSプロキシーを使用し、暗号化を使用しない場合、IdPが開示した属性はプロキシーから見えてしまいます。 これは、一部の展開においては重大なプライバシー上の露出です。 この露出を減らすために、RADIUSクライアントとRADIUSサーバーの間に直接TLSコネクションを作成するメカニズムが、現在進行中の作業で検討されています。 プロキシーを使用する場合は、SAMLアサーションをプロキシーにさらすことによる影響を慎重に検討する必要があります。

The use of TLS to provide confidentiality for the RADIUS exchange is strongly encouraged. Without this, passive eavesdroppers can observe the assertions.

RADIUSのやり取りに機密性を提供するためにTLSを使用することが強く推奨されます。 これがないと、受動的な盗聴者がアサーションを観測できてしまいます。

10. Security Considerations

10. セキュリティーに関する考慮事項

In this specification, the RP MUST trust any statement in the SAML messages from the IdP in the same way that it trusts information contained in RADIUS attributes. These entities MUST trust the RADIUS infrastructure to provide integrity of the SAML messages.

この仕様において、RPは、RADIUS属性に含まれる情報を信頼するのと同じように、IdPからのSAMLメッセージ内のあらゆる記述を信頼しなければなりません（MUST）。 これらのエンティティーは、SAMLメッセージの完全性を提供するものとしてRADIUSインフラストラクチャーを信頼しなければなりません（MUST）。

Furthermore, the RP MUST apply policy and filter the information based on what information the IdP is permitted to assert and on what trust is reasonable to place in proxies between them.

さらに、RPは、IdPがどの情報を表明することを許可されているか、およびそれらの間にあるプロキシーにどの程度の信頼を置くのが妥当かに基づいて、ポリシーを適用し、情報をフィルタリングしなければなりません（MUST）。

XML signatures and encryption are provided as an OPTIONAL mechanism for end-to-end security. These mechanisms can protect SAML messages from being modified by proxies in the RADIUS infrastructure. These mechanisms are not mandatory to implement. It is believed that ongoing work to provide direct TLS connections between a RADIUS client and RADIUS server will provide similar assurances but better deployability. XML security is appropriate for deployments where end-to-end security is required but proxies cannot be removed or where SAML messages need to be verified at a later time or by parties not involved in the authentication exchange.

XML署名と暗号化は、エンドツーエンドのセキュリティーのための選択可能な（OPTIONAL）メカニズムとして提供されます。 これらのメカニズムは、RADIUSインフラストラクチャー内のプロキシーによる改ざんからSAMLメッセージを保護できます。 これらのメカニズムは実装必須ではありません。 RADIUSクライアントとRADIUSサーバーの間に直接TLSコネクションを提供するための進行中の作業により、同様の保証がより良い展開性とともに提供されると考えられています。 XMLセキュリティーは、エンドツーエンドのセキュリティーが必要であるもののプロキシーを取り除けない展開や、SAMLメッセージを後から、あるいは認証のやり取りに関与していない当事者が検証する必要がある展開に適しています。
