Homenet Profile of the Babel Routing Protocol

RFC 9080

BabelルーティングプロトコルのHomenetプロファイル

Abstract

概要

This document defines the exact subset of the Babel routing protocol and its extensions that is required by an implementation of the Homenet protocol suite, as well as the interactions between the Home Networking Control Protocol (HNCP) and Babel.

この文書は、Homenetプロトコルスイートの実装が必要とするBabelルーティングプロトコルとその拡張の厳密なサブセット、およびホームネットワーキング制御プロトコル（Home Networking Control Protocol、HNCP）とBabelとの相互作用を定義します。

1. Introduction

1. はじめに

The core of the Homenet protocol suite consists of the Home Networking Control Protocol (HNCP) [RFC7788], a protocol used for flooding configuration information and assigning prefixes to links, combined with the Babel routing protocol [RFC8966]. Babel is an extensible, flexible, and modular protocol: minimal implementations of Babel have been demonstrated that consist of a few hundred lines of code, while the "large" implementation includes support for a number of extensions and consists of over ten thousand lines of C code.

Homenetプロトコルスイートの中核は、設定情報のフラッディングとリンクへのプレフィックスの割り当てに使われるプロトコルであるホームネットワーキング制御プロトコル（Home Networking Control Protocol、HNCP）[RFC7788]と、Babelルーティングプロトコル[RFC8966]を組み合わせたもので構成されます。Babelは拡張可能で柔軟、かつモジュール化されたプロトコルです。数百行のコードからなるBabelの最小限の実装が実証されている一方で、「大規模な」実装は多数の拡張のサポートを含んでおり、1万行を超えるCのコードで構成されています。

This document consists of two parts. The first specifies the exact subset of the Babel protocol and its extensions that is required by an implementation of the Homenet protocol suite. The second specifies how HNCP interacts with Babel.

この文書は2つの部分で構成されます。1つ目は、Homenetプロトコルスイートの実装が必要とするBabelプロトコルとその拡張の厳密なサブセットを規定します。2つ目は、HNCPがBabelとどのように相互作用するかを規定します。

1.2. Background

1.2. 背景

The Babel routing protocol and its extensions are defined in a number of documents:

Babelルーティングプロトコルとその拡張は、いくつかの文書で定義されています。

  • RFC 8966 [RFC8966] defines the Babel routing protocol. It allows Babel's control data to be carried either over link-local IPv6 or over IPv4 and in either case allows announcing both IPv4 and IPv6 routes. It leaves link cost estimation, metric computation, and route selection to the implementation. Distinct implementations of Babel [RFC8966] will interoperate, in the sense that they will maintain a set of loop-free forwarding paths. However, if they implement conflicting options, they might not be able to exchange a full set of routes. In the worst case, an implementation that only implements the IPv6 subset of the protocol and an implementation that only implements the IPv4 subset of the protocol will not exchange any routes. In addition, if implementations use conflicting route selection policies, persistent oscillations might occur.
  • The informative Appendix A of [RFC8966] suggests a simple and easy-to-implement algorithm for cost and metric computation that has been found to work satisfactorily in a wide range of topologies.
  • While RFC 8966 does not provide an algorithm for route selection, its Section 3.6 suggests selecting the route with the smallest metric with some hysteresis applied. An algorithm that has been found to work well in practice is described in Section III.E of [DELAY-BASED].
  • Four documents define optional extensions to Babel: authentication based on Hashed Message Authentication Code (HMAC) [RFC8967], source-specific routing [RFC9079], delay-based routing [BABEL-RTT], and ToS-specific (Type of Service) routing [ToS-SPECIFIC]. All of these extensions interoperate with the core protocol as well as with each other.
  • RFC 8966 [RFC8966]は、Babelルーティングプロトコルを定義しています。この文書では、Babelの制御データをリンクローカルIPv6とIPv4のどちらの上でも運ぶことができ、どちらの場合でもIPv4とIPv6の両方の経路をアナウンスできます。リンクコストの推定、メトリックの計算、経路選択は実装に任されています。Babel [RFC8966]の異なる実装同士は、ループのない転送パスの集合を維持するという意味では相互運用できます。しかし、相反するオプションを実装している場合、経路の完全な集合を交換できないことがあります。最悪の場合、プロトコルのIPv6サブセットだけを実装した実装と、プロトコルのIPv4サブセットだけを実装した実装とは、経路をまったく交換しません。さらに、実装同士が相反する経路選択ポリシーを使うと、持続的な振動が発生することがあります。
  • 参考情報である[RFC8966]のAppendix Aは、コストとメトリックの計算のための、単純で実装しやすいアルゴリズムを提案しています。このアルゴリズムは、幅広いトポロジーで満足に機能することがわかっています。
  • RFC 8966は経路選択のアルゴリズムを規定していませんが、そのセクション3.6は、何らかのヒステリシスを適用したうえで最小のメトリックを持つ経路を選択することを提案しています。実際によく機能することがわかっているアルゴリズムは、[DELAY-BASED]のセクションIII.Eで説明されています。
  • 4つの文書が、Babelへの選択可能な拡張を定義しています。ハッシュベースのメッセージ認証コード（HMAC）に基づく認証[RFC8967]、送信元固有ルーティング[RFC9079]、遅延ベースのルーティング[BABEL-RTT]、ToS（Type of Service）固有のルーティング[ToS-SPECIFIC]です。これらの拡張はいずれも、コアプロトコルとも、また互いとも相互運用できます。

2. The Homenet Profile of Babel

2. BabelのHomenetプロファイル

2.1. Requirements

2.1. 要件

  1. A Homenet implementation of Babel MUST encapsulate Babel control traffic in IPv6 packets sent to the IANA-assigned port 6696 and either the IANA-assigned multicast group ff02::1:6 or to a link-local unicast address.

    Rationale: Since Babel is able to carry both IPv4 and IPv6 routes over either IPv4 or IPv6, choosing the protocol used for carrying control traffic is a matter of preference. Since IPv6 has some features that make implementations somewhat simpler and more reliable (notably properly scoped and reasonably stable link-local addresses), we require carrying control data over IPv6.

  2. A Homenet implementation of Babel MUST implement the IPv6 subset of the protocol defined in the body of RFC 8966.

    Rationale: Support for IPv6 routing is an essential component of the Homenet architecture.

  3. A Homenet implementation of Babel SHOULD implement the IPv4 subset of the protocol defined in the body of RFC 8966. Use of other techniques for acquiring IPv4 connectivity (such as multiple layers of NAT) is strongly discouraged.

    Rationale: Support for IPv4 will likely remain necessary for years to come, and even in pure IPv6 deployments, including code for supporting IPv4 has very little cost. Since HNCP makes it easy to assign distinct IPv4 prefixes to the links in a network, it is not necessary to resort to multiple layers of NAT, with all of its problems.

  4. A Homenet implementation of Babel MUST implement source-specific routing for IPv6, as defined in RFC 9079 [RFC9079].

    Rationale: Source-specific routing is an essential component of the Homenet architecture. Source-specific routing for IPv4 is not required, since HNCP arranges things so that a single nonspecific IPv4 default route is announced (Section 6.5 of [RFC7788]).

  5. A Homenet implementation of Babel must use metrics that are of a similar magnitude to the values suggested in Appendix A of [RFC8966]. In particular, it SHOULD assign costs that are no less than 256 to wireless links and SHOULD assign costs between 32 and 196 to lossless wired links.

    Rationale: If two implementations of Babel choose very different values for link costs, combining routers from different vendors will cause suboptimal routing.

  6. A Homenet implementation of Babel SHOULD distinguish between wired and wireless links; if it is unable to determine whether a link is wired or wireless, it SHOULD make the worst-case hypothesis that the link is wireless. It SHOULD dynamically probe the quality of wireless links and derive a suitable metric from its quality estimation. Appendix A of [RFC8966] gives an example of a suitable algorithm.

    Rationale: Support for wireless transit links is a distinguishing feature of Homenet, and one that is requested by our users. In the absence of dynamically computed metrics, the routing protocol attempts to minimise the number of links crossed by a route and therefore prefers long, lossy links to shorter, lossless ones. In wireless networks, "hop-count routing is worst-path routing".

    While it would be desirable to perform link-quality probing on some wired link technologies, notably power-line networks, these kinds of links tend to be difficult or impossible to detect automatically, and we are not aware of any published link-quality algorithms for them. Hence, we do not require link-quality estimation for wired links of any kind.

  1. BabelのHomenet実装は、Babelの制御トラフィックを、IANAが割り当てたポート6696宛てで、IANAが割り当てたマルチキャストグループff02::1:6またはリンクローカルユニキャストアドレスのいずれかに送信されるIPv6パケットにカプセル化しなければなりません（MUST）。

    根拠：BabelはIPv4とIPv6の両方の経路をIPv4とIPv6のどちらの上でも運べるので、制御トラフィックの伝送に使うプロトコルの選択は好みの問題です。IPv6には実装をいくらか単純かつ信頼性の高いものにする機能（特に、適切にスコープが定められ、かなり安定したリンクローカルアドレス）があるため、私たちは制御データをIPv6上で運ぶことを要求します。

  2. BabelのHomenet実装は、RFC 8966の本文で定義されているプロトコルのIPv6サブセットを実装しなければなりません（MUST）。

    根拠：IPv6ルーティングのサポートは、Homenetアーキテクチャーに不可欠な構成要素です。

  3. BabelのHomenet実装は、RFC 8966の本文で定義されているプロトコルのIPv4サブセットを実装すべきです（SHOULD）。IPv4接続性を得るためのほかの技術（多段のNATなど）を使うことは、強く推奨されません。

    根拠：IPv4のサポートは今後何年にもわたって必要であり続ける可能性が高く、純粋なIPv6の展開であっても、IPv4をサポートするコードを含めるコストはごくわずかです。HNCPによってネットワーク内のリンクに別々のIPv4プレフィックスを容易に割り当てられるので、さまざまな問題を伴う多段のNATに頼る必要はありません。

  4. BabelのHomenet実装は、RFC 9079 [RFC9079]で定義されているIPv6の送信元固有ルーティングを実装しなければなりません（MUST）。

    根拠：送信元固有ルーティングは、Homenetアーキテクチャーに不可欠な構成要素です。HNCPは、送信元固有でない単一のIPv4デフォルト経路がアナウンスされるように取り計らう（[RFC7788]のSection 6.5）ので、IPv4の送信元固有ルーティングは要求されません。

  5. BabelのHomenet実装は、[RFC8966]のAppendix Aで提案されている値と同程度の大きさのメトリックを使わなければなりません。特に、無線リンクには256以上のコストを割り当てるべきです（SHOULD）。また、損失のない有線リンクには32から196までのコストを割り当てるべきです（SHOULD）。

    根拠：Babelの2つの実装がリンクコストにまったく異なる値を選ぶと、異なるベンダーのルーターを組み合わせたときに最適でないルーティングが行われます。

  6. BabelのHomenet実装は、有線リンクと無線リンクを区別すべきです（SHOULD）。リンクが有線か無線かを判断できない場合は、そのリンクが無線であるという最悪の場合の仮定を置くべきです（SHOULD）。また、無線リンクの品質を動的に調べ、その品質の推定から適切なメトリックを導出すべきです（SHOULD）。[RFC8966]のAppendix Aは、適切なアルゴリズムの例を示しています。

    根拠：無線のトランジットリンクのサポートはHomenetの際立った特徴であり、ユーザーから求められているものでもあります。動的に計算されるメトリックがない場合、ルーティングプロトコルは経路が通過するリンクの数を最小化しようとするため、短く損失のないリンクよりも長く損失の多いリンクを優先してしまいます。無線ネットワークでは、「ホップ数によるルーティングは最悪のパスによるルーティング」なのです。

    一部の有線リンク技術、特に電力線ネットワークでもリンク品質の調査を行うことが望ましいのですが、こうした種類のリンクは自動的に検出するのが困難または不可能な傾向があり、またそれらのための公開されたリンク品質アルゴリズムを私たちは把握していません。そのため、私たちはどのような種類の有線リンクについてもリンク品質の推定を要求しません。

2.2. Optional Features

2.2. 選択可能な機能

  1. A Homenet implementation of Babel MAY perform route selection by applying hysteresis to route metrics, as suggested in Section 3.6 of [RFC8966] and described in detail in Section III.E of [DELAY-BASED]. However, hysteresis is not required, and the implementation may simply pick the route with the smallest metric.

    Rationale: Hysteresis is only useful in congested and highly dynamic networks. In a typical home network, which is stable and uncongested, the feedback loop that hysteresis compensates for does not occur.

  2. A Homenet implementation of Babel may include support for other extensions to the protocol, as long as they are known to interoperate with both the core protocol and source-specific routing.

    Rationale: A number of extensions to the Babel routing protocol have been defined over the years; however, they are useful in fairly specific situations, such as routing over global-scale overlay networks [BABEL-RTT] or multi-hop wireless networks with multiple radio frequencies [BABEL-Z]. Hence, with the exception of source-specific routing, no extensions are required for Homenet.

  1. BabelのHomenet実装は、[RFC8966]のSection 3.6で提案され、[DELAY-BASED]のセクションIII.Eで詳しく説明されているように、経路のメトリックにヒステリシスを適用して経路選択を行ってもよいです（MAY）。ただし、ヒステリシスは必須ではなく、実装は単に最小のメトリックを持つ経路を選んでもかまいません。

    根拠：ヒステリシスが役に立つのは、輻輳した、非常に動的なネットワークにおいてだけです。安定していて輻輳のない典型的なホームネットワークでは、ヒステリシスが補償するフィードバックループは発生しません。

  2. BabelのHomenet実装は、コアプロトコルと送信元固有ルーティングの両方と相互運用できることがわかっている限り、プロトコルへのほかの拡張のサポートを含めてもかまいません。

    根拠：Babelルーティングプロトコルへの拡張はこれまでに数多く定義されてきましたが、それらはグローバル規模のオーバーレイネットワーク上でのルーティング[BABEL-RTT]や、複数の無線周波数を使うマルチホップ無線ネットワーク[BABEL-Z]など、かなり特定の状況で役に立つものです。そのため、送信元固有ルーティングを除いて、Homenetに必要な拡張はありません。

3. Interactions between HNCP and Babel

3. HNCPとBabelの相互作用

The Homenet architecture cleanly separates configuration, which is done by HNCP, from routing, which is done by Babel. While the coupling between the two protocols is deliberately kept to a minimum, some interactions are unavoidable.

Homenetアーキテクチャーは、HNCPが行う設定と、Babelが行うルーティングとを明確に分離しています。2つのプロトコル間の結合は意図的に最小限に抑えられていますが、いくつかの相互作用は避けられません。

All the interactions between HNCP and Babel consist of HNCP causing Babel to perform an announcement on its behalf (under no circumstances does Babel cause HNCP to perform an action). How this is realised is an implementation detail that is outside the scope of this document; while it could conceivably be done using a private communication channel between HNCP and Babel, in existing implementations, HNCP installs a route in the operating system's kernel that is later picked up by Babel using the existing redistribution mechanisms.

HNCPとBabelの間の相互作用はすべて、HNCPがBabelに自らの代わりにアナウンスを行わせるというものです（どのような状況でも、BabelがHNCPに動作を行わせることはありません）。これをどのように実現するかは、この文書の範囲外の実装の詳細です。HNCPとBabelの間のプライベートな通信チャネルを使って行うことも考えられますが、既存の実装では、HNCPがオペレーティングシステムのカーネルに経路をインストールし、それを後でBabelが既存の再配布メカニズムを使って取り込みます。

3.1. Requirements

3.1. 要件

  1. If an HNCP node receives a DHCPv6 prefix delegation for prefix P and publishes an External-Connection TLV containing a Delegated-Prefix TLV with prefix P and no Prefix-Policy TLV, then it MUST announce a source-specific default route with source prefix P over Babel.

    Rationale: Source-specific routes are the main tool that Homenet uses to enable optimal routing in the presence of multiple IPv6 prefixes. External connections with nontrivial prefix policies are explicitly excluded from this requirement, since their exact behaviour is application specific.

  2. If an HNCP node receives a DHCPv4 lease with an IPv4 address and wins the election for NAT gateway, then it MUST act as a NAT gateway and MUST announce a (nonspecific) IPv4 default route over Babel.

    Rationale: The Homenet stack does not use source-specific routing for IPv4; instead, HNCP elects a single NAT gateway and publishes a single default route towards that gateway ([RFC7788], Section 6.5).

  3. If an HNCP node assigns a prefix P to an attached link and announces P in an Assigned-Prefix TLV, then it MUST announce a route towards P over Babel.

    Rationale: Prefixes assigned to links must be routable within the Homenet.

  1. HNCPノードがプレフィックスPのDHCPv6プレフィックス委任を受け取り、プレフィックスPを持つDelegated-Prefix TLVを含み、Prefix-Policy TLVを含まないExternal-Connection TLVを公開する場合、そのノードは送信元プレフィックスPを持つ送信元固有のデフォルト経路をBabel上でアナウンスしなければなりません（MUST）。

    根拠：送信元固有の経路は、複数のIPv6プレフィックスが存在する場合に最適なルーティングを可能にするためにHomenetが使う主要な手段です。自明でないプレフィックスポリシーを持つ外部接続は、その正確な振る舞いがアプリケーションに固有であるため、この要件から明示的に除外されています。

  2. HNCPノードがIPv4アドレスを含むDHCPv4リースを受け取り、NATゲートウェイの選出で選ばれた場合、そのノードはNATゲートウェイとして動作しなければなりません（MUST）。また、（送信元固有でない）IPv4デフォルト経路をBabel上でアナウンスしなければなりません（MUST）。

    根拠：HomenetスタックはIPv4に送信元固有ルーティングを使いません。代わりに、HNCPは単一のNATゲートウェイを選出し、そのゲートウェイに向かう単一のデフォルト経路を公開します（[RFC7788], Section 6.5）。

  3. HNCPノードが接続されたリンクにプレフィックスPを割り当て、Assigned-Prefix TLVでPをアナウンスする場合、そのノードはPに向かう経路をBabel上でアナウンスしなければなりません（MUST）。

    根拠：リンクに割り当てられたプレフィックスは、Homenet内でルーティング可能でなければなりません。

3.2. Optional Features

3.2. 選択可能な機能

  1. An HNCP node that receives a DHCPv6 prefix delegation MAY announce a nonspecific IPv6 default route over Babel in addition to the source-specific default route mandated by requirement REQ7.

    Rationale: Since the source-specific default route is more specific than the nonspecific default route, the former will override the latter if all nodes implement source-specific routing. Announcing an additional nonspecific route is allowed, since doing that causes no harm and might simplify operations in some circumstances, e.g., when interoperating with a routing protocol that does not support source-specific routing.

  2. An HNCP node that receives a DHCPv4 lease with an IPv4 address and wins the election for NAT gateway SHOULD NOT announce a source-specific IPv4 default route.

    Rationale: Homenet does not require support for IPv4 source-specific routing. Announcing IPv4 source-specific routes will not cause routing pathologies (blackholes or routing loops), but it might cause packets sourced in different parts of the Homenet to follow different paths, with all the confusion that this entails.

  1. DHCPv6プレフィックス委任を受け取ったHNCPノードは、要件REQ7で義務付けられている送信元固有のデフォルト経路に加えて、送信元固有でないIPv6デフォルト経路をBabel上でアナウンスしてもよいです（MAY）。

    根拠：送信元固有のデフォルト経路は送信元固有でないデフォルト経路よりも具体的なので、すべてのノードが送信元固有ルーティングを実装していれば、前者が後者より優先されます。追加で送信元固有でない経路をアナウンスすることは許可されています。そうしても害はなく、状況によっては、たとえば送信元固有ルーティングをサポートしないルーティングプロトコルと相互運用する場合などに、運用を単純にできる可能性があるためです。

  2. IPv4アドレスを含むDHCPv4リースを受け取り、NATゲートウェイの選出で選ばれたHNCPノードは、送信元固有のIPv4デフォルト経路をアナウンスすべきではありません（SHOULD NOT）。

    根拠：HomenetはIPv4の送信元固有ルーティングのサポートを要求しません。IPv4の送信元固有の経路をアナウンスしてもルーティングの異常（ブラックホールやルーティングループ）は発生しませんが、Homenetの異なる部分から送信されたパケットが異なるパスをたどることになり、それに伴うあらゆる混乱を引き起こす可能性があります。

4. Security Considerations

4. セキュリティーに関する考慮事項

Both HNCP and Babel carry their control data in IPv6 packets with a link-local source address, and implementations are required to drop packets sent from a global address. Hence, they are only susceptible to attacks from a directly connected link on which the HNCP and Babel implementations are listening.

HNCPとBabelはどちらも、リンクローカルな送信元アドレスを持つIPv6パケットで制御データを運び、実装はグローバルアドレスから送信されたパケットを破棄することが要求されています。そのため、これらはHNCPとBabelの実装が待ち受けている、直接接続されたリンクからの攻撃だけを受けやすいことになります。

The security of a Homenet network relies on having a set of "Internal", "Ad Hoc", and "Hybrid" interfaces (Section 5.1 of [RFC7788]) that are assumed to be connected to links that are secured at a lower layer. HNCP and Babel packets are only accepted when they originate on these trusted links. "External" and "Guest" interfaces are connected to links that are not trusted, and any HNCP or Babel packets that are received on such interfaces are ignored. ("Leaf" interfaces are a special case since they are connected to trusted links, but HNCP and Babel traffic received on such interfaces is ignored.) This implies that the security of a Homenet network depends on the reliability of the border discovery procedure described in Section 5.3 of [RFC7788].

Homenetネットワークのセキュリティーは、下位層で保護されたリンクに接続されていると想定される「Internal」、「Ad Hoc」、「Hybrid」インターフェイスの集合（[RFC7788]のSection 5.1）を持つことに依存しています。HNCPとBabelのパケットは、これらの信頼されたリンク上で発信された場合にのみ受け入れられます。「External」と「Guest」インターフェイスは信頼されていないリンクに接続されており、そのようなインターフェイスで受信されたHNCPやBabelのパケットはすべて無視されます。（「Leaf」インターフェイスは特殊なケースです。信頼されたリンクに接続されていますが、そのようなインターフェイスで受信されたHNCPとBabelのトラフィックは無視されます。）このことは、Homenetネットワークのセキュリティーが、[RFC7788]のSection 5.3で説明されている境界検出手順の信頼性に依存することを意味します。

If untrusted links are used for transit, which is NOT RECOMMENDED, then any HNCP and Babel traffic that is carried over such links MUST be secured using an upper-layer security protocol. While both HNCP and Babel support cryptographic authentication, at the time of writing, no protocol for autonomous configuration of HNCP and Babel security has been defined.

信頼されていないリンクをトランジットに使う場合（これは推奨されません（NOT RECOMMENDED））、そのようなリンク上で運ばれるHNCPとBabelのトラフィックはすべて、上位層のセキュリティープロトコルを使って保護しなければなりません（MUST）。HNCPとBabelはどちらも暗号学的認証をサポートしていますが、この文書の執筆時点では、HNCPとBabelのセキュリティーを自律的に設定するためのプロトコルは定義されていません。
