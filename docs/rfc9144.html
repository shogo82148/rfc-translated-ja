Comparison of Network Management Datastore Architecture (NMDA) Datastores

RFC 9144

ネットワーク管理データストアアーキテクチャー（NMDA）のデータストアの比較

Abstract

概要

This document defines a Remote Procedure Call (RPC) operation to compare management datastores that comply with the Network Management Datastore Architecture (NMDA).

この文書は、ネットワーク管理データストアアーキテクチャー（Network Management Datastore Architecture: NMDA）に準拠した管理データストアを比較するための、リモートプロシージャーコール（RPC）操作を定義します。

1. Introduction

1. はじめに

The revised NMDA [RFC8342] introduces a set of new datastores that each hold YANG-defined data [RFC7950] and represent a different "viewpoint" on the data that is maintained by a server. New YANG datastores that are introduced include <intended>, which contains validated configuration data that a client application intends to be in effect, and <operational>, which contains operational state data (such as statistics) as well as configuration data that is actually in effect.

改訂されたNMDA[RFC8342]は、新しいデータストアの集合を導入します。各データストアはYANGで定義されたデータ[RFC7950]を保持し、サーバーが維持するデータに対するそれぞれ異なる「視点」を表します。導入された新しいYANGデータストアには、クライアントアプリケーションが有効にすることを意図した、検証済みの設定データを含む<intended>や、（統計などの）運用状態データと実際に有効になっている設定データを含む<operational>があります。

NMDA introduces, in effect, a concept of "lifecycle" for management data, distinguishing between data that is part of a configuration that was supplied by a user, configuration data that has actually been successfully applied and that is part of the operational state, and the overall operational state that includes applied configuration data as well as status and statistics.

NMDAは、事実上、管理データに対する「ライフサイクル」という概念を導入します。これにより、ユーザーが提供した設定の一部であるデータ、実際に正常に適用されて運用状態の一部となっている設定データ、そして適用された設定データに加えてステータスや統計も含む運用状態全体が区別されます。

As a result, data from the same management model can be reflected in multiple datastores. Clients need to specify the target datastore to be specific about which viewpoint of the data they want to access. For example, a client application can differentiate whether they are interested in the configuration that is supplied to a server and is supposed to be in effect or the configuration that has been applied and is actually in effect on the server.

その結果、同じ管理モデルのデータが複数のデータストアに反映されることがあります。クライアントは、データのどの視点にアクセスしたいのかを明確にするために、ターゲットとなるデータストアを指定する必要があります。たとえば、クライアントアプリケーションは、サーバーに提供されて有効になるはずの設定に関心があるのか、それとも適用されてサーバー上で実際に有効になっている設定に関心があるのかを区別できます。

Due to the fact that data can propagate from one datastore to another, it is possible for differences between datastores to occur. Some of this is entirely expected, as there may be a time lag between when a configuration is given to the device and reflected in <intended> until when it actually takes effect and is reflected in <operational>. However, there may be cases when a configuration item that was to be applied may not actually take effect at all or needs an unusually long time to do so. This can be the case due to certain conditions not being met, certain parts of the configuration not propagating because they are considered inactive, resource dependencies not being resolved, or even implementation errors in corner conditions.

データはあるデータストアから別のデータストアへ伝播するため、データストア間に差異が生じる可能性があります。その一部はまったく想定どおりのものです。設定がデバイスに与えられて<intended>に反映されてから、実際に有効になって<operational>に反映されるまでには、時間差がある場合があるからです。しかし、適用されるはずだった設定項目がまったく有効にならなかったり、有効になるまでに異常に長い時間がかかったりする場合もあります。これは、特定の条件が満たされていない、設定の特定の部分が非アクティブとみなされて伝播しない、リソースの依存関係が解決されていない、あるいはまれな条件下での実装のエラーなどが原因で起こりえます。

When the configuration that is in effect is different from the configuration that was applied, many issues can result. It becomes more difficult to operate the network properly due to limited visibility of the actual operational status, which makes it more difficult to analyze and understand what is going on in the network. Services may be negatively affected (for example, degrading or breaking a customer service), and network resources may be misallocated.

有効になっている設定が適用された設定と異なる場合、多くの問題が生じる可能性があります。実際の運用状況が見えにくくなるため、ネットワークを適切に運用することが難しくなり、ネットワークで何が起きているかを分析して理解することも難しくなります。サービスが悪影響を受けたり（たとえば、顧客サービスの品質が低下したり停止したりする）、ネットワークリソースが誤って割り当てられたりする可能性があります。

Applications can potentially analyze any differences between two datastores by retrieving the contents from both datastores and comparing them. However, in many cases, this will be both costly and extremely wasteful.

アプリケーションは、2つのデータストアの両方から内容を取得して比較することで、それらの間の差異を分析できる可能性があります。しかし、多くの場合、これはコストが高く、きわめて無駄の多い方法になります。

This document introduces a YANG data model that defines RPCs intended to be used in conjunction with NETCONF [RFC6241] or RESTCONF [RFC8040]. These RPCs allow a client to request a server to compare two NMDA datastores and report any differences.

この文書は、NETCONF[RFC6241]またはRESTCONF[RFC8040]と組み合わせて使用することを意図したRPCを定義するYANGデータモデルを導入します。これらのRPCにより、クライアントはサーバーに対して、2つのNMDAデータストアを比較して差異を報告するようリクエストできます。

3. Data Model Overview

3. データモデルの概要

The core of the solution is a new management operation, <compare>, that compares the data tree contents of two datastores. The operation checks whether there are any differences in values or in data nodes that are contained in either datastore and returns any differences as output. The output is returned in the format specified in YANG Patch [RFC8072].

この解決策の中核となるのは、2つのデータストアのデータツリーの内容を比較する新しい管理操作<compare>です。この操作は、いずれかのデータストアに含まれる値やデータノードに差異があるかどうかを確認し、差異があればそれを出力として返します。出力は、YANG Patch[RFC8072]で規定されている形式で返されます。

The YANG data model defines the <compare> operation as a new RPC. The operation takes the following input parameters:

YANGデータモデルは、<compare>操作を新しいRPCとして定義します。この操作は、次の入力パラメーターを受け取ります。

source:
The source identifies the datastore to serve as the reference for the comparison -- for example, <intended>.
target:
The target identifies the datastore to compare against the source -- for example, <operational>.
filter-spec:
This is a choice between different filter constructs to identify the parts of the datastore to be retrieved. It acts as a node selector that specifies which data nodes are within the scope of the comparison and which nodes are outside the scope. This allows a comparison operation to be applied only to a specific part of the datastore that is of interest, such as a particular subtree. Note that the filter does not allow expressions that match against data node values, since this may incur implementation difficulties and is not required for normal use cases.
all:
When set, this parameter indicates that all differences should be included, including differences pertaining to schema nodes that exist in only one of the datastores. When this parameter is not included, a prefiltering step is automatically applied to exclude data from the comparison that does not pertain to both datastores: if the same schema node is not present in both datastores, then all instances of that schema node and all its descendants are excluded from the comparison. This allows client applications to focus on the differences that constitute true mismatches of instance data without needing to specify more complex filter constructs.
report-origin:
When set, this parameter indicates that origin metadata should be included as part of RPC output. When this parameter is omitted, origin metadata in comparisons that involve <operational> is by default omitted. Note that origin metadata only applies to <operational>; it is therefore also omitted in comparisons that do not involve <operational> regardless of whether or not the parameter is set.
source:
source（ソース）は、比較の基準となるデータストアを識別します。たとえば、<intended>です。
target:
target（ターゲット）は、ソースと比較するデータストアを識別します。たとえば、<operational>です。
filter-spec:
これは、取得するデータストアの部分を識別するための、さまざまなフィルター構文からの選択（choice）です。これはノードセレクターとして機能し、どのデータノードが比較の範囲内にあり、どのノードが範囲外にあるかを指定します。これにより、特定のサブツリーなど、関心のあるデータストアの特定の部分にのみ比較操作を適用できます。なお、このフィルターでは、データノードの値に対してマッチする式は使えません。そのような式は実装上の困難を招く可能性があり、通常のユースケースでは必要ないためです。
all:
このパラメーターが設定されている場合、片方のデータストアにのみ存在するスキーマノードに関する差異も含めて、すべての差異を含めるべきであることを示します。このパラメーターが含まれていない場合、両方のデータストアに関係するわけではないデータを比較から除外するための事前フィルタリングの手順が自動的に適用されます。つまり、同じスキーマノードが両方のデータストアに存在しない場合、そのスキーマノードのすべてのインスタンスとそのすべての子孫が比較から除外されます。これにより、クライアントアプリケーションは、より複雑なフィルター構文を指定しなくても、インスタンスデータの真の不一致となる差異に集中できます。
report-origin:
このパラメーターが設定されている場合、originメタデータをRPC出力の一部として含めるべきであることを示します。 このパラメーターが省略されている場合、デフォルトでは、 <operational>が関わる比較においてoriginメタデータは省略されます。 なお、originメタデータは<operational>にのみ適用されます。したがって、<operational>が関わらない比較では、このパラメーターが設定されているかどうかにかかわらず、originメタデータは省略されます。

The operation provides the following output parameter:

この操作は、次の出力パラメーターを提供します。

differences:
This parameter contains the list of differences. Those differences are encoded per the YANG Patch data model defined in [RFC8072]. When a datastore node in the source of the comparison is not present in the target of the comparison, this can be indicated either as a "delete" or as a "remove" in the patch as there is no differentiation between those operations for the purposes of the comparison. The YANG Patch data model is augmented to indicate the value of source datastore nodes in addition to the patch itself that would need to be applied to the source to produce the target. When the target datastore is <operational> and the input parameter "report-origin" is set, origin metadata is included as part of the patch. Including origin metadata can help explain the cause of a difference in some cases -- for example, when a data node is part of <intended> but the origin of the same data node in <operational> is reported as "system".
differences:
このパラメーターには、差異のリストが含まれます。これらの差異は、[RFC8072]で定義されているYANG Patchデータモデルに従ってエンコードされます。比較のソースにあるデータストアノードが比較のターゲットに存在しない場合、これはパッチの中で"delete"または"remove"のいずれかとして示すことができます。比較という目的においては、これらの操作の間に違いはないからです。 YANG Patchデータモデルは、ソースからターゲットを作り出すためにソースに適用する必要があるパッチそのものに加えて、ソースデータストアのノードの値も示すように拡張（augment）されます。ターゲットデータストアが<operational>であり、入力パラメーター"report-origin"が設定されている場合、originメタデータがパッチの一部として含まれます。originメタデータを含めることは、場合によっては差異の原因を説明するのに役立ちます。たとえば、あるデータノードが<intended>の一部であるにもかかわらず、<operational>における同じデータノードのoriginが"system"と報告される場合です。

4. YANGデータモデル

This YANG module includes references to [RFC6991], [RFC8342], [RFC8072], and [RFC6241].

このYANGモジュールは、[RFC6991]、[RFC8342]、[RFC8072]、[RFC6241]を参照しています。

  yang-version 1.1;
  namespace "urn:ietf:params:xml:ns:yang:ietf-nmda-compare";
  prefix cmp;

  import ietf-yang-types {

    reference
      "RFC 8072: YANG Patch Media Type";
  }
  import ietf-netconf {
    prefix nc;
    reference
      "RFC 6241: Network Configuration Protocol (NETCONF)";
  }

  organization
    "IETF NETMOD (Network Modeling) Working Group";
  contact
    "WG Web:   <https://datatracker.ietf.org/wg/netmod/>
     WG List:  <mailto:netmod@ietf.org>

     Author: Andy Bierman
             <mailto:andy@yumaworks.com>";
  description
    "The YANG data model defines a new operation, <compare>, that
     can be used to compare NMDA datastores.

     Copyright (c) 2021 IETF Trust and the persons identified as
     authors of the code.  All rights reserved.

     Redistribution and use in source and binary forms, with or
     without modification, is permitted pursuant to, and subject to

     This version of this YANG module is part of RFC 9144; see the
     RFC itself for full legal notices.";

  revision 2021-12-10 {
    description
      "Initial revision.";
    reference
      "RFC 9144: Comparison of Network Management Datastore
       Architecture (NMDA) Datastores";
  }

  /* RPC */

  rpc compare {
    description
      "NMDA datastore compare operation.";
    input {
      leaf source {
        type identityref {
          base ds:datastore;
        }
        mandatory true;
        description
          "The source datastore to be compared.";
      }
      leaf target {
        type identityref {
          base ds:datastore;
        }
        mandatory true;
        description
          "The target datastore to be compared.";
      }
      leaf all {
        type empty;
        description
          "When this leaf is provided, all data nodes are compared,
           whether their schema node pertains to both datastores or
           not.  When this leaf is omitted, a prefiltering step is
           automatically applied that excludes data nodes from the
           comparison that can occur in only one datastore but not
           the other.  Specifically, if one of the datastores
           (source or target) contains only configuration data and
           the other datastore is <operational>, data nodes for
           the config that is false are excluded from the
           comparison.";
      }
      leaf report-origin {
        type empty;
        description
          "When this leaf is provided, origin metadata is
           included as part of RPC output.  When this leaf is
           omitted, origin metadata in comparisons that involve
           <operational> is by default omitted.";
      }
      choice filter-spec {
        description
          "Identifies the portions of the datastores to be
               compared.";
        anydata subtree-filter {
          description
            "This parameter identifies the portions of the
             target datastore to retrieve.";
          reference
            "RFC 6241, Section 6.";
        }
        leaf xpath-filter {
          if-feature "nc:xpath";
          type yang:xpath1.0;
          description
            "This parameter contains an XPath expression
             identifying the portions of the target
             datastore to retrieve.";
          reference
            "RFC 6991: Common YANG Data Types";
        }
      }
    }
    output {
      choice compare-response {
        description
          "Comparison results.";
        leaf no-matches {
          type empty;
          description
            "This leaf indicates that the filter did not match
             anything and nothing was compared.";
        }
        container differences {
          description
            "The list of differences, encoded per RFC 8072 with an
             augmentation to include source values where applicable.
             When a datastore node in the source is not present in
             the target, this can be indicated either as a 'delete'
             or as a 'remove' as there is no difference between
             them for the purposes of the comparison.";
          uses ypatch:yang-patch {
            augment "yang-patch/edit" {
              description
                "Provides the value of the source of the patch,
                 respectively of the source of the comparison, in
                 addition to the target value, where applicable.";
              anydata source-value {
                when "../operation = 'delete'"
                   + "or ../operation = 'merge'"
                   + "or ../operation = 'move'"
                   + "or ../operation = 'replace'"
                   + "or ../operation = 'remove'";
                description
                  "The anydata 'value' is only used for 'delete',
                   'move', 'merge', 'replace', and 'remove'
                   operations.";
              }
              reference
                "RFC 8072: YANG Patch Media Type";
            }
          }
        }
      }
    }
  }
}

     This version of this YANG module is part of RFC 9144; see the
     RFC itself for full legal notices.";

  revision 2021-12-10 {
    description
      "Initial revision.";
    reference
      "RFC 9144: Comparison of Network Management Datastore
       Architecture (NMDA) Datastores";
  }

  /* RPC */

  rpc compare {
    description
      "NMDA datastore compare operation.";
    input {
      leaf source {
        type identityref {
          base ds:datastore;
        }
        mandatory true;
        description
          "The source datastore to be compared.";
      }
      leaf target {
        type identityref {
          base ds:datastore;
        }
        mandatory true;
        description
          "The target datastore to be compared.";
      }
      leaf all {
        type empty;
        description
          "When this leaf is provided, all data nodes are compared,
           whether their schema node pertains to both datastores or
           not.  When this leaf is omitted, a prefiltering step is
           automatically applied that excludes data nodes from the
           comparison that can occur in only one datastore but not
           the other.  Specifically, if one of the datastores
           (source or target) contains only configuration data and
           the other datastore is <operational>, data nodes for
           the config that is false are excluded from the
           comparison.";
      }
      leaf report-origin {
        type empty;
        description
          "When this leaf is provided, origin metadata is
           included as part of RPC output.  When this leaf is
           omitted, origin metadata in comparisons that involve
           <operational> is by default omitted.";
      }
      choice filter-spec {
        description
          "Identifies the portions of the datastores to be
               compared.";
        anydata subtree-filter {
          description
            "This parameter identifies the portions of the
             target datastore to retrieve.";
          reference
            "RFC 6241, Section 6.";
        }
        leaf xpath-filter {
          if-feature "nc:xpath";
          type yang:xpath1.0;
          description
            "This parameter contains an XPath expression
             identifying the portions of the target
             datastore to retrieve.";
          reference
            "RFC 6991: Common YANG Data Types";
        }
      }
    }
    output {
      choice compare-response {
        description
          "Comparison results.";
        leaf no-matches {
          type empty;
          description
            "This leaf indicates that the filter did not match
             anything and nothing was compared.";
        }
        container differences {
          description
            "The list of differences, encoded per RFC 8072 with an
             augmentation to include source values where applicable.
             When a datastore node in the source is not present in
             the target, this can be indicated either as a 'delete'
             or as a 'remove' as there is no difference between
             them for the purposes of the comparison.";
          uses ypatch:yang-patch {
            augment "yang-patch/edit" {
              description
                "Provides the value of the source of the patch,
                 respectively of the source of the comparison, in
                 addition to the target value, where applicable.";
              anydata source-value {
                when "../operation = 'delete'"
                   + "or ../operation = 'merge'"
                   + "or ../operation = 'move'"
                   + "or ../operation = 'replace'"
                   + "or ../operation = 'remove'";
                description
                  "The anydata 'value' is only used for 'delete',
                   'move', 'merge', 'replace', and 'remove'
                   operations.";
              }
              reference
                "RFC 8072: YANG Patch Media Type";
            }
          }
        }
      }
    }
  }
}

The origin of the leaf instances in <operational> is "learned", which may help explain the discrepancies.

<operational>には、<intended>に含まれているリーフ"description"のインスタンスが含まれていません。もう1つのリーフ"enabled"は2つのデータストアで値が異なり、<operational>では"true"、<intended>では"false"になっています。3つ目のリーフ"name"は、どちらでも同じです。<operational>におけるリーフインスタンスのoriginは"learned"であり、これは不一致を説明するのに役立つ可能性があります。

6. Performance Considerations

6. 性能に関する考慮事項

The <compare> operation can be computationally expensive. While responsible client applications are expected to use the operation responsibly and sparingly only when warranted, implementations need to be aware of the fact that excessive invocation of this operation will burden system resources and need to ensure that system performance will not be adversely impacted. One possibility for an implementation to mitigate against this is to limit the number of requests that are served to a client, or to any number of clients, in any one time interval, by rejecting requests made at a higher frequency than the implementation can reasonably sustain.

<compare>操作は、計算コストが高くなる可能性があります。責任あるクライアントアプリケーションは、必要な場合にのみ、この操作を責任をもって控えめに使用することが期待されます。しかし実装は、この操作が過度に呼び出されるとシステムリソースに負担がかかることを認識し、システムの性能に悪影響が及ばないようにする必要があります。実装がこれを緩和するための方法の1つは、実装が無理なく維持できる頻度を超えてなされたリクエストを拒否することで、任意の時間間隔において1つのクライアント、あるいは任意の数のクライアントに対して処理するリクエストの数を制限することです。

While useful, tools such as YANG data models that allow for the monitoring of server resources, system performance, and statistics about RPCs and RPC rates are outside the scope of this document. When defined, any such model should be general in nature and not limited to the RPC operation defined in this document.

サーバーリソース、システム性能、RPCおよびRPCレートに関する統計の監視を可能にするYANGデータモデルなどのツールは有用ですが、この文書の範囲外です。 そのようなモデルを定義する場合は、汎用的なものにすべきであり、この文書で定義されるRPC操作に限定すべきではありません。

8. Security Considerations

8. セキュリティーに関する考慮事項

The YANG module specified in this document defines a schema for data that is designed to be accessed via network management protocols such as NETCONF [RFC6241] or RESTCONF [RFC8040]. The lowest NETCONF layer is the secure transport layer, and the mandatory-to-implement secure transport is Secure Shell (SSH) [RFC6242]. The lowest RESTCONF layer is HTTPS, and the mandatory-to-implement secure transport is TLS [RFC8446].

この文書で規定されるYANGモジュールは、NETCONF[RFC6241]やRESTCONF[RFC8040]などのネットワーク管理プロトコルを介してアクセスされるように設計されたデータのスキーマを定義します。NETCONFの最下位層はセキュアなトランスポート層であり、実装必須のセキュアなトランスポートはSecure Shell（SSH）[RFC6242]です。RESTCONFの最下位層はHTTPSであり、実装必須のセキュアなトランスポートはTLS[RFC8446]です。

The Network Configuration Access Control Model (NACM) [RFC8341] provides the means to restrict access for particular NETCONF or RESTCONF users to a preconfigured subset of all available NETCONF or RESTCONF protocol operations and content.

ネットワーク設定アクセス制御モデル（Network Configuration Access Control Model: NACM）[RFC8341]は、特定のNETCONFユーザーまたはRESTCONFユーザーのアクセスを、利用可能なすべてのNETCONFまたはRESTCONFのプロトコル操作とコンテンツのうち、事前に設定されたサブセットに制限する手段を提供します。

NACM specifies access for the server in its entirety, and the same access rules apply to all datastores. Any subtrees to which a requestor does not have read access are silently skipped and not included in the comparison.

NACMはサーバー全体に対するアクセスを規定し、同じアクセス規則がすべてのデータストアに適用されます。リクエスターが読み取りアクセス権を持たないサブツリーは黙ってスキップされ、比較には含まれません。

The RPC operation defined in this YANG module, <compare>, may be considered sensitive or vulnerable in some network environments. It is thus important to control access to this operation. This is the sensitivity/vulnerability of RPC operation <compare>:

このYANGモジュールで定義されるRPC操作<compare>は、ネットワーク環境によっては機密性が高い、または脆弱であるとみなされる場合があります。したがって、この操作へのアクセスを制御することが重要です。RPC操作<compare>の機密性と脆弱性は次のとおりです。

Comparing datastores for differences requires a certain amount of processing resources at the server. An attacker could attempt to attack a server by making a high volume of comparison requests. Server implementations can guard against such scenarios in several ways. For one, they can implement the NACM in order to require proper authorization for requests to be made. Second, server implementations can limit the number of requests that they serve to a client in any one time interval, rejecting requests made at a higher frequency than the implementation can reasonably sustain.

データストアを比較して差異を調べるには、サーバーで一定量の処理リソースが必要です。攻撃者は、大量の比較リクエストを送ることで、サーバーを攻撃しようとする可能性があります。サーバー実装は、そのようなシナリオに対していくつかの方法で防御できます。1つ目として、リクエストを行うために適切な認可を要求するよう、NACMを実装できます。2つ目として、サーバー実装は、実装が無理なく維持できる頻度を超えてなされたリクエストを拒否することで、任意の時間間隔において1つのクライアントに対して処理するリクエストの数を制限できます。

Appendix A. Possible Future Extensions

Appendix A. 将来の拡張の可能性

It is conceivable to extend the <compare> operation with a number of possible additional features in the future.

将来、<compare>操作を、いくつかの追加機能によって拡張することが考えられます。

Specifically, it is possible to define an extension with an optional feature for dampening. This will allow clients to specify a minimum time period for which a difference must persist for it to be reported. This will enable clients to distinguish between differences that are only fleeting from ones that are not and that may represent a real operational issue and inconsistency within the device.

具体的には、ダンピングのためのオプション機能を持つ拡張を定義することが可能です。これにより、クライアントは、差異が報告されるためにその差異が持続しなければならない最小の期間を指定できるようになります。これによってクライアントは、一時的なものにすぎない差異と、そうではなく、デバイス内の実際の運用上の問題や不整合を表している可能性のある差異とを区別できるようになります。

For this purpose, an additional input parameter can be added to specify the dampening period. Only differences that pertain for at least the dampening time are reported. A value of 0 or omission of the parameter indicates no dampening. Reporting of differences MAY correspondingly be delayed by the dampening period from the time the request is received.

この目的のために、ダンピング期間を指定するための追加の入力パラメーターを追加できます。少なくともダンピング時間のあいだ持続している差異のみが報告されます。 値が0であるか、パラメーターが省略されている場合は、ダンピングを行わないことを示します。 これに応じて、差異の報告を、リクエストを受信した時点からダンピング期間だけ遅らせてもよいです（MAY）。

To implement this feature, a server implementation might run a comparison when the RPC is first invoked and temporarily store the result. Subsequently, it could wait until after the end of the dampening period to check whether the same differences are still observed. The differences that still persist are then returned.

この機能を実装するために、サーバー実装は、RPCが最初に呼び出されたときに比較を実行し、その結果を一時的に保存することが考えられます。その後、ダンピング期間が終了するまで待ってから、同じ差異がまだ観測されるかどうかを確認できます。その時点でまだ持続している差異が返されます。
