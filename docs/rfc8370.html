RFC 8370

Techniques to Improve the Scalability of RSVP-TE Deployments

RFC 8370

RSVP-TEの展開のスケーラビリティーを向上させる技法

Abstract

概要

Networks that utilize RSVP-TE LSPs are encountering implementations that have a limited ability to support the growth in the number of LSPs deployed.

RSVP-TE LSPを利用するネットワークでは、展開されるLSPの数の増加に対応する能力が限られた実装に直面しています。

This document defines two techniques, Refresh-Interval Independent RSVP (RI-RSVP) and Per-Peer Flow Control, that reduce the number of processing cycles required to maintain RSVP-TE LSP state in Label Switching Routers (LSRs) and hence allow implementations to support larger scale deployments.

この文書では、リフレッシュ間隔非依存RSVP（Refresh-Interval Independent RSVP、RI-RSVP）とピアごとのフロー制御（Per-Peer Flow Control）という2つの技法を定義します。 これらの技法は、ラベルスイッチングルーター（LSR）でRSVP-TE LSPの状態を維持するために必要な処理サイクル数を削減し、それによって実装がより大規模な展開をサポートできるようにします。

1. Introduction

1. はじめに

Networks that utilize RSVP-TE [RFC3209] LSPs are encountering implementations that have a limited ability to support the growth in the number of LSPs deployed.

RSVP-TE[RFC3209]のLSPを利用するネットワークでは、展開されるLSPの数の増加に対応する能力が限られた実装に直面しています。

The set of RSVP Refresh Overhead Reduction procedures [RFC2961] serves as a powerful toolkit for RSVP-TE implementations to help cover a majority of the concerns about soft-state scaling. However, even with these tools in the toolkit, analysis of existing implementations [RFC5439] indicates that the processing required beyond a certain scale may still cause significant disruption to a Label Switching Router (LSR).

一連のRSVPリフレッシュオーバーヘッド削減手順[RFC2961]は、ソフトステートのスケーリングに関する懸念の大部分に対処するのに役立つ、RSVP-TE実装向けの強力なツールキットとして機能します。 しかし、ツールキットにこれらのツールがあっても、既存の実装の分析[RFC5439]によれば、ある規模を超えると、必要な処理がラベルスイッチングルーター（LSR）に依然として重大な混乱を引き起こす可能性があります。

This document builds on existing scaling work and analysis and defines protocol extensions to help RSVP-TE deployments push the envelope further on scaling by increasing the threshold above which an LSR struggles to achieve sufficient processing to maintain LSP state.

この文書は、既存のスケーリングに関する作業と分析を基にしており、LSPの状態を維持するのに十分な処理を行うことにLSRが苦労し始めるしきい値を引き上げることで、RSVP-TEの展開がスケーリングの限界をさらに押し広げるのに役立つプロトコル拡張を定義します。

This document defines two techniques, Refresh-Interval Independent RSVP (RI-RSVP) and Per-Peer Flow Control, that cut down the number of processing cycles required to maintain LSP state. RI-RSVP helps completely eliminate RSVP's reliance on refreshes and refresh timeouts, while Per-Peer Flow Control enables a busy RSVP speaker to apply back pressure to its peer(s). This document defines a unique RSVP Capability [RFC5063] for each technique (support for the CAPABILITY object is a prerequisite for implementing these techniques). Note that the Per-Peer Flow-Control technique requires the RI-RSVP technique as a prerequisite. In order to reap maximum scaling benefits, it is strongly recommended that implementations support both techniques and have them enabled by default. Both techniques are fully backward compatible and can be deployed incrementally.

この文書では、LSPの状態を維持するために必要な処理サイクル数を削減する、リフレッシュ間隔非依存RSVP（RI-RSVP）とピアごとのフロー制御という2つの技法を定義します。 RI-RSVPは、RSVPがリフレッシュとリフレッシュタイムアウトに依存することを完全に排除するのに役立ち、ピアごとのフロー制御は、ビジー状態のRSVPスピーカーがそのピアに背圧（back pressure）をかけることを可能にします。 この文書では、技法ごとに固有のRSVP能力（RSVP Capability）[RFC5063]を定義します（CAPABILITYオブジェクトのサポートは、これらの技法を実装するための前提条件です）。 ピアごとのフロー制御の技法は、前提条件としてRI-RSVPの技法を必要とすることに注意してください。 スケーリングの利点を最大限に得るために、実装は両方の技法をサポートし、デフォルトで有効にすることが強く推奨されます。 どちらの技法も完全に後方互換であり、段階的に展開できます。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

2. Required Support for RFC 2961

2. RFC 2961の必須サポート

The techniques defined in Sections 3 and 4 are based on proposals made in [RFC2961]. Implementations of these techniques need to support the RSVP messages and procedures defined in [RFC2961] with some minor modifications and alterations to recommended time intervals and iteration counts (see Appendix A for the set of recommended defaults).

セクション3と4で定義する技法は、[RFC2961]でなされた提案に基づいています。 これらの技法の実装は、[RFC2961]で定義されたRSVPメッセージと手順を、推奨される時間間隔と反復回数にいくつかの小さな修正と変更を加えたうえでサポートする必要があります（推奨されるデフォルト値の一覧については付録Aを参照してください）。

2.1. Required Functionality from RFC 2961

2.1. RFC 2961の必須機能

An implementation that supports the techniques discussed in Sections 3 and 4 must support the functionality described in [RFC2961] as follows:

セクション3と4で説明する技法をサポートする実装は、[RFC2961]で説明されている機能を次のとおりサポートする必要があります。

  • It MUST indicate support for RSVP Refresh Overhead Reduction extensions (as specified in Section 2 of [RFC2961]).
  • It MUST support receipt of any RSVP Refresh Overhead Reduction message as defined in [RFC2961].
  • It MUST initiate all RSVP Refresh Overhead Reduction mechanisms as defined in [RFC2961] (including the SRefresh message) with the default behavior being to initiate the mechanisms; however, a configuration override should be offered.
  • It MUST support reliable delivery of Path/Resv and the corresponding Tear/Err messages (as specified in Section 4 of [RFC2961]).
  • It MUST support retransmission of all unacknowledged RSVP-TE messages using exponential backoff (as specified in Section 6 of [RFC2961]).
  • （[RFC2961]のセクション2で規定されているように）RSVPリフレッシュオーバーヘッド削減拡張のサポートを示さなければなりません（MUST）。
  • [RFC2961]で定義されているあらゆるRSVPリフレッシュオーバーヘッド削減メッセージの受信をサポートしなければなりません（MUST）。
  • [RFC2961]で定義されているすべてのRSVPリフレッシュオーバーヘッド削減メカニズム（SRefreshメッセージを含む）を開始しなければなりません（MUST）。 デフォルトの振る舞いはメカニズムを開始することですが、設定による上書きを提供すべきです。
  • （[RFC2961]のセクション4で規定されているように）Path/Resvと、それに対応するTear/Errメッセージの信頼性のある配送をサポートしなければなりません（MUST）。
  • （[RFC2961]のセクション6で規定されているように）指数バックオフを用いた、確認応答されていないすべてのRSVP-TEメッセージの再送をサポートしなければなりません（MUST）。

2.2. Making Acknowledgements Mandatory

2.2. 確認応答の必須化

The reliable message delivery mechanism specified in [RFC2961] states that "Nodes receiving a non-out of order [sic] message containing a MESSAGE_ID object with the ACK_Desired flag set, SHOULD respond with a MESSAGE_ID_ACK object."

[RFC2961]で規定されている信頼性のあるメッセージ配送メカニズムには、「ACK_Desiredフラグが設定されたMESSAGE_IDオブジェクトを含む、順序外れでない[sic]メッセージを受信したノードは、MESSAGE_ID_ACKオブジェクトで応答すべきです（SHOULD）」と記載されています。

In an implementation that supports the techniques discussed in Sections 3 and 4, nodes receiving a non-out-of-order message containing a MESSAGE_ID object with the ACK_Desired flag set MUST respond with a MESSAGE_ID_ACK object. This MESSAGE_ID_ACK object can be packed with other MESSAGE_ID_ACK or MESSAGE_ID_NACK objects and sent in an Ack message (or piggybacked in any other RSVP message).

セクション3と4で説明する技法をサポートする実装では、ACK_Desiredフラグが設定されたMESSAGE_IDオブジェクトを含む順序外れでないメッセージを受信したノードは、MESSAGE_ID_ACKオブジェクトで応答しなければなりません（MUST）。 このMESSAGE_ID_ACKオブジェクトは、ほかのMESSAGE_ID_ACKオブジェクトやMESSAGE_ID_NACKオブジェクトとまとめて、Ackメッセージで送信する（またはほかの任意のRSVPメッセージに相乗りさせる）ことができます。

This improvement to the predictability of the system in terms of reliable message delivery is key for being able to take any action based on a non-receipt of an ACK.

信頼性のあるメッセージ配送の観点からシステムの予測可能性をこのように向上させることは、ACKを受信しなかったことに基づいて何らかのアクションを取れるようにするための鍵となります。

3. Refresh-Interval Independent RSVP (RI-RSVP)

3. リフレッシュ間隔非依存RSVP（RI-RSVP）

The RSVP protocol relies on periodic refreshes for state synchronization between RSVP neighbors and recovery from lost RSVP messages. It relies on a refresh timeout for stale-state cleanup. The primary motivation behind introducing the notion of Refresh-Interval Independent RSVP (RI-RSVP) is to completely eliminate RSVP's reliance on refreshes and refresh timeouts. This is done by simply increasing the refresh interval to a fairly large value. [RFC2961] and [RFC5439] talk about increasing the value of the refresh interval to provide linear improvement of transmission overhead, but they also point out the degree of functionality that is lost by doing so. This section revisits this notion, but also sets out additional requirements to make sure that there is no loss of functionality incurred by increasing the value of the refresh interval.

RSVPプロトコルは、RSVPネイバー間の状態の同期と、失われたRSVPメッセージからの回復のために、定期的なリフレッシュに依存しています。 また、古い状態の消去のためにリフレッシュタイムアウトに依存しています。 リフレッシュ間隔非依存RSVP（RI-RSVP）という概念を導入する主な動機は、RSVPがリフレッシュとリフレッシュタイムアウトに依存することを完全に排除することです。 これは、単にリフレッシュ間隔をかなり大きな値に増やすことで実現されます。 [RFC2961]と[RFC5439]は、送信オーバーヘッドを線形に改善するためにリフレッシュ間隔の値を増やすことについて述べていますが、そうすることで失われる機能の程度についても指摘しています。 このセクションでは、この考え方を再検討するとともに、リフレッシュ間隔の値を増やすことによって機能が失われないようにするための追加の要件を示します。

An implementation that supports RI-RSVP:

RI-RSVPをサポートする実装は、次のとおりです。

  • MUST support all of the requirements specified in Section 2.
  • MUST make the default value of the configurable refresh interval (R) be a large value (tens of minutes). A default value of 20 minutes is RECOMMENDED by this document.
  • MUST use a separate shorter refresh interval for refreshing state associated with unacknowledged Path/Resv (uR) messages. A default value of 30 seconds is RECOMMENDED by this document.
  • MUST implement coupling the state of individual LSPs with the state of the corresponding RSVP-TE signaling adjacency. When an RSVP-TE speaker detects RSVP-TE signaling adjacency failure, the speaker MUST act as if all the Path and Resv states learned via the failed signaling adjacency have timed out.
  • MUST make use of the Hello session based on the Node-ID ([RFC3209] [RFC4558]) for detection of RSVP-TE signaling adjacency failures. A default value of 9 seconds is RECOMMENDED by this document for the configurable node hello interval (as opposed to the default value of 5 milliseconds proposed in Section 5.3 of [RFC3209]).
  • MUST indicate support for RI-RSVP via the CAPABILITY object [RFC5063] in Hello messages.
  • セクション2で規定されているすべての要件をサポートしなければなりません（MUST）。
  • 設定可能なリフレッシュ間隔（R）のデフォルト値を大きな値（数十分）にしなければなりません（MUST）。 この文書では、デフォルト値を20分とすることが推奨されます（RECOMMENDED）。
  • 確認応答されていないPath/Resv（uR）メッセージに関連付けられた状態をリフレッシュするために、別のより短いリフレッシュ間隔を使用しなければなりません（MUST）。 この文書では、デフォルト値を30秒とすることが推奨されます（RECOMMENDED）。
  • 個々のLSPの状態を、対応するRSVP-TEシグナリング隣接関係の状態と連動させることを実装しなければなりません（MUST）。 RSVP-TEスピーカーがRSVP-TEシグナリング隣接関係の障害を検出した場合、そのスピーカーは、障害の発生したシグナリング隣接関係を介して学習したすべてのPath状態とResv状態がタイムアウトしたかのように振る舞わなければなりません（MUST）。
  • RSVP-TEシグナリング隣接関係の障害を検出するために、Node-IDに基づくHelloセッション（[RFC3209] [RFC4558]）を利用しなければなりません（MUST）。 この文書では、設定可能なノードのHello間隔のデフォルト値を9秒とすることが推奨されます（RECOMMENDED）（[RFC3209]のセクション5.3で提案されているデフォルト値の5ミリ秒とは異なります）。
  • HelloメッセージのCAPABILITYオブジェクト[RFC5063]を介して、RI-RSVPのサポートを示さなければなりません（MUST）。

3.1. Capability Advertisement

3.1. 能力の広告

An implementation supporting the RI-RSVP technique MUST set a new flag, RI-RSVP Capable, in the CAPABILITY object signaled in Hello messages. The following bit indicates that the sender supports RI-RSVP:

RI-RSVPの技法をサポートする実装は、HelloメッセージでシグナリングされるCAPABILITYオブジェクトに、新しいフラグRI-RSVP Capableを設定しなければなりません（MUST）。 次のビットは、送信者がRI-RSVPをサポートしていることを示します。

Bit Number 28 (0x0008) - RI-RSVP Capable (I-bit)

ビット番号28（0x0008） - RI-RSVP Capable（Iビット）

Any node that sets the new I-bit in its CAPABILITY object MUST also set the Refresh-Reduction-Capable bit [RFC2961] in the common header of all RSVP-TE messages. If a peer sets the I-bit in the CAPABILITY object but does not set the Refresh-Reduction-Capable bit, then the RI-RSVP functionality MUST NOT be activated for that peer.

CAPABILITYオブジェクトに新しいIビットを設定するノードは、すべてのRSVP-TEメッセージの共通ヘッダーにRefresh-Reduction-Capableビット[RFC2961]も設定しなければなりません（MUST）。 ピアがCAPABILITYオブジェクトにIビットを設定しているにもかかわらず、Refresh-Reduction-Capableビットを設定していない場合、そのピアに対してRI-RSVPの機能を有効にしてはなりません（MUST NOT）。

3.2. Compatibility

3.2. 互換性

The RI-RSVP functionality MUST NOT be activated with a peer that does not indicate support for this functionality. Inactivation of the RI-RSVP functionality MUST result in the use of the traditional smaller refresh interval [RFC2205].

この機能のサポートを示していないピアに対して、RI-RSVPの機能を有効にしてはなりません（MUST NOT）。 RI-RSVPの機能を無効にした場合は、従来のより短いリフレッシュ間隔[RFC2205]を使用しなければなりません（MUST）。

4. Per-Peer Flow Control

4. ピアごとのフロー制御

The functionality discussed in this section provides an RSVP speaker with the ability to apply back pressure to its peer(s) to reduce/eliminate a significant portion of the RSVP-TE control message load.

このセクションで説明する機能は、RSVPスピーカーに対して、そのピアに背圧をかけてRSVP-TE制御メッセージの負荷のかなりの部分を削減または排除する能力を提供します。

An implementation that supports Per-Peer Flow Control:

ピアごとのフロー制御をサポートする実装は、次のとおりです。

  • MUST support all of the requirements specified in Section 2.
  • MUST support RI-RSVP (Section 3).
  • MUST treat lack of ACKs from a peer as an indication of a peer's RSVP-TE control-plane congestion. If congestion is detected, the local system MUST throttle RSVP-TE messages to the affected peer. This MUST be done on a per-peer basis. (Per-peer throttling MAY be implemented by a traffic-shaping mechanism that proportionally reduces the RSVP-signaling packet rate as the number of outstanding ACKs increases. When the number of outstanding ACKs decreases, the send rate would be adjusted up again.)
  • SHOULD use a Retry Limit (Rl) value of 7 (Section 6.2 of [RFC2961] suggests using 3).
  • SHOULD prioritize Hello messages and messages carrying Acknowledgements over other RSVP messages.
  • SHOULD prioritize Tear/Error over trigger Path/Resv (messages that bring up new LSP state) sent to a peer when the local system detects RSVP-TE control-plane congestion in the peer.
  • MUST indicate support for this technique via the CAPABILITY object [RFC5063] in Hello messages.
  • セクション2で規定されているすべての要件をサポートしなければなりません（MUST）。
  • RI-RSVP（セクション3）をサポートしなければなりません（MUST）。
  • ピアからのACKがないことを、ピアのRSVP-TEコントロールプレーンの輻輳の兆候として扱わなければなりません（MUST）。 輻輳が検出された場合、ローカルシステムは影響を受けるピアへのRSVP-TEメッセージを抑制しなければなりません（MUST）。 これはピアごとに行わなければなりません（MUST）。 （ピアごとの抑制は、未処理のACKの数が増えるにつれてRSVPシグナリングのパケットレートを比例的に下げるトラフィックシェーピングメカニズムによって実装してもよいです（MAY）。 未処理のACKの数が減ると、送信レートは再び引き上げられることになります。）
  • 再試行回数の上限（Retry Limit、Rl）の値として7を使用すべきです（SHOULD）（[RFC2961]のセクション6.2では3を使用することを提案しています）。
  • Helloメッセージと確認応答を運ぶメッセージを、ほかのRSVPメッセージよりも優先すべきです（SHOULD）。
  • ローカルシステムがピアにおけるRSVP-TEコントロールプレーンの輻輳を検出した場合、そのピアに送信するTear/Errorを、トリガーPath/Resv（新しいLSPの状態を立ち上げるメッセージ）よりも優先すべきです（SHOULD）。
  • HelloメッセージのCAPABILITYオブジェクト[RFC5063]を介して、この技法のサポートを示さなければなりません（MUST）。

4.1. Capability Advertisement

4.1. 能力の広告

An implementation supporting the Per-Peer Flow-Control technique MUST set a new flag, Per-Peer Flow-Control Capable, in the CAPABILITY object signaled in Hello messages. The following bit indicates that the sender supports Per-Peer Flow Control:

ピアごとのフロー制御の技法をサポートする実装は、HelloメッセージでシグナリングされるCAPABILITYオブジェクトに、新しいフラグPer-Peer Flow-Control Capableを設定しなければなりません（MUST）。 次のビットは、送信者がピアごとのフロー制御をサポートしていることを示します。

Bit Number 27 (0x0010) - Per-Peer Flow-Control Capable (F-bit)

ビット番号27（0x0010） - Per-Peer Flow-Control Capable（Fビット）

Any node that sets the new F-bit in its CAPABILITY object MUST also set the Refresh-Reduction-Capable bit in the common header of all RSVP-TE messages. If a peer sets the F-bit in the CAPABILITY object but does not set the Refresh-Reduction-Capable bit, then the Per-Peer Flow-Control functionality MUST NOT be activated for that peer.

CAPABILITYオブジェクトに新しいFビットを設定するノードは、すべてのRSVP-TEメッセージの共通ヘッダーにRefresh-Reduction-Capableビットも設定しなければなりません（MUST）。 ピアがCAPABILITYオブジェクトにFビットを設定しているにもかかわらず、Refresh-Reduction-Capableビットを設定していない場合、そのピアに対してピアごとのフロー制御の機能を有効にしてはなりません（MUST NOT）。

4.2. Compatibility

4.2. 互換性

The Per-Peer Flow-Control functionality MUST NOT be activated with a peer that does not indicate support for this functionality. If a peer hasn't indicated that it is capable of participating in Per-Peer Flow Control, then it SHOULD NOT be assumed that the peer would always acknowledge a non-out-of-order message containing a MESSAGE_ID object with the ACK_Desired flag set.

この機能のサポートを示していないピアに対して、ピアごとのフロー制御の機能を有効にしてはなりません（MUST NOT）。 ピアがピアごとのフロー制御に参加できることを示していない場合、ACK_Desiredフラグが設定されたMESSAGE_IDオブジェクトを含む順序外れでないメッセージに対して、そのピアが常に確認応答を返すと想定すべきではありません（SHOULD NOT）。

Appendix A. Recommended Defaults

付録A. 推奨されるデフォルト値

  1. Refresh Interval (R) - 20 minutes (Section 3): Given that an implementation supporting RI-RSVP doesn't rely on refreshes for state sync between peers, the function of the RSVP refresh interval is analogous to that of IGP refresh interval (the default of which is typically in the order of tens of minutes). Choosing a default of 20 minutes allows the refresh timer to be randomly set to a value in the range [10 minutes (0.5R), 30 minutes (1.5R)].

  2. Node Hello Interval - 9 seconds (Section 3):

    [RFC3209] defines the hello timeout as 3.5 times the hello interval. Choosing 9 seconds for the node hello interval gives a hello timeout of 3.5 * 9 = 31.5 seconds. This puts the hello timeout value in the vicinity of the IGP hello timeout value.

  3. Retry-Limit (Rl) - 7 (Section 4): Choosing 7 as the retry-limit results in an overall rapid retransmit phase of 31.5 seconds. This matches up with the hello timeout of 31.5 seconds.

  4. Refresh Interval for refreshing state associated with unacknowledged Path/Resv messages (uR) - 30 seconds (Section 3): The recommended refresh interval (R) value of 20 minutes (for an implementation supporting RI-RSVP) cannot be used for refreshing state associated with unacknowledged Path/Resv messages. This document recommends the use of the traditional default refresh interval value of 30 seconds for uR.

  1. リフレッシュ間隔（R） - 20分（セクション3）： RI-RSVPをサポートする実装はピア間の状態同期をリフレッシュに依存しないため、RSVPのリフレッシュ間隔の役割は、IGPのリフレッシュ間隔（そのデフォルト値は通常、数十分程度です）の役割と類似しています。 デフォルト値として20分を選ぶと、リフレッシュタイマーを[10分（0.5R）、30分（1.5R）]の範囲内の値にランダムに設定できます。

  2. ノードのHello間隔 - 9秒（セクション3）：

    [RFC3209]は、HelloタイムアウトをHello間隔の3.5倍と定義しています。 ノードのHello間隔として9秒を選ぶと、Helloタイムアウトは3.5 * 9 = 31.5秒になります。 これにより、HelloタイムアウトはIGPのHelloタイムアウトの値に近い値になります。

  3. 再試行回数の上限（Rl） - 7（セクション4）： 再試行回数の上限として7を選ぶと、迅速な再送フェーズ全体が31.5秒になります。 これは31.5秒のHelloタイムアウトと一致します。

  4. 確認応答されていないPath/Resvメッセージに関連付けられた状態をリフレッシュするためのリフレッシュ間隔（uR） - 30秒（セクション3）： （RI-RSVPをサポートする実装向けに）推奨されるリフレッシュ間隔（R）の値である20分は、確認応答されていないPath/Resvメッセージに関連付けられた状態のリフレッシュには使用できません。 この文書では、uRには従来のデフォルトのリフレッシュ間隔の値である30秒を使用することを推奨します。
