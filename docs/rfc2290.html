RFC 2290

Mobile-IPv4 Configuration Option for PPP IPCP

RFC 2290

PPP IPCPのためのMobile-IPv4構成オプション

Abstract

概要

Mobile IP [RFC2002] defines media-independent procedures by which a Mobile Node can maintain existing transport and application-layer connections despite changing its point-of-attachment to the Internet and without changing its IP address. PPP [RFC1661] provides a standard method for transporting multi-protocol packets over point-to-point links. As currently specified, Mobile IP Foreign Agents which support Mobile Node connections via PPP can do so only by first assigning unique addresses to those Mobile Nodes, defeating one of the primary advantages of Foreign Agents. This documents corrects this problem by defining the Mobile-IPv4 Configuration Option to the Internet Protocol Control Protocol (IPCP) [RFC1332]. Using this option, two peers can communicate their support for Mobile IP during the IPCP phase of PPP. Familiarity with Mobile IP [RFC2002], IPCP [RFC1332], and PPP [RFC1661] is assumed.

モバイルIP [RFC2002] は、モバイルノードがインターネットへの接続点を変更しても、IPアドレスを変更することなく、既存のトランスポート層およびアプリケーション層のコネクションを維持できるようにするための、メディアに依存しない手順を定義しています。PPP [RFC1661] は、ポイントツーポイントリンク上でマルチプロトコルのパケットを転送するための標準的な方法を提供します。現在の仕様では、PPP経由のモバイルノードの接続をサポートするモバイルIPのフォーリンエージェントは、まずそれらのモバイルノードに一意なアドレスを割り当てることによってしかそれを実現できず、フォーリンエージェントの主要な利点の1つを損なっています。この文書は、インターネットプロトコル制御プロトコル（Internet Protocol Control Protocol: IPCP）[RFC1332] に対するMobile-IPv4構成オプションを定義することで、この問題を解決します。このオプションを使用すると、2つのピアはPPPのIPCPフェーズ中に、モバイルIPのサポートについて互いに伝えることができます。この文書は、モバイルIP [RFC2002]、IPCP [RFC1332]、およびPPP [RFC1661] についての知識を前提としています。

1. Introduction

1. はじめに

Mobile IP [RFC2002] defines protocols and procedures by which packets can be routed to a mobile node, regardless of its current point-of-attachment to the Internet, and without changing its IP address. Mobile IP is designed to run over any type of media and any type of data link-layer. However, the interaction between Mobile IP and PPP is currently underspecified and generally results in an inappropriate application of Mobile IP when mobile nodes connect to the Internet via PPP.

モバイルIP [RFC2002] は、モバイルノードの現在のインターネットへの接続点にかかわらず、またそのIPアドレスを変更することなく、パケットをモバイルノードへルーティングできるようにするためのプロトコルと手順を定義しています。モバイルIPは、あらゆる種類のメディアとあらゆる種類のデータリンク層の上で動作するように設計されています。しかし、モバイルIPとPPPとの相互作用は現在十分に規定されておらず、モバイルノードがPPP経由でインターネットに接続する場合、一般にモバイルIPの不適切な適用を招いています。

This document defines proper interaction between a mobile node [RFC2002] and a peer through which the mobile node connects to the Internet using PPP. This requires the definition of a new option for IPCP [RFC1332], named the "Mobile-IPv4" Configuration Option, which is defined in this document. The mobile node and the peer use this option to negotiate the appropriate use of Mobile IP over the PPP link.

この文書は、モバイルノード [RFC2002] と、そのモバイルノードがPPPを使用してインターネットに接続する際に経由するピアとの間の、適切な相互作用を定義します。そのためには、IPCP [RFC1332] の新しいオプションを定義する必要があります。このオプションは「Mobile-IPv4」構成オプションと呼ばれ、この文書で定義されます。モバイルノードとピアは、このオプションを使用して、PPPリンク上でのモバイルIPの適切な使用方法をネゴシエーションします。

The Mobile-IPv4 option defined in this document is intended to work in conjunction with the existing IP-Address option [RFC1332].

この文書で定義するMobile-IPv4オプションは、既存のIP-Addressオプション [RFC1332] と組み合わせて動作することを意図しています。

1.2. Terminology

1.2. 用語

This document uses the following terms as defined in [RFC2002]:

この文書では、[RFC2002] で定義されている次の用語を使用します。

Mobile Node
A host or router that changes its point-of-attachment from one link to another. A mobile node may change its location without changing its IP address; it may continue to communicate with other Internet nodes at any location using its (permanent) home, IP address, assuming link-layer connectivity is available at its current location.
Home Agent
A router with at least one interface on a mobile node's home link. A home agent intercepts packets destined to a mobile node's home address and tunnels them to the mobile node's care-of address when the mobile node is connected to a foreign link. A mobile node informs its home agent of its current care-of address through an authenticated registration protocol defined by Mobile IP.
Foreign Agent
A router with at least one interface on a mobile node's (current) foreign link. When a mobile node uses a foreign agent's care-of address, the foreign agent detunnels and delivers packets to the mobile node that were tunneled by the mobile node's home agent. A foreign agent might also serve as a default router for packets sent by a registered mobile node.
Peer
The PPP peer of a mobile node. The mobile node's peer might support home agent functionality, foreign agent functionality, both, or neither.
モバイルノード（Mobile Node）
あるリンクから別のリンクへと接続点を変更するホストまたはルーター。モバイルノードは、IPアドレスを変更することなく位置を変更できます。現在の位置でリンク層の接続性が利用可能であれば、モバイルノードはどの位置においても、その（恒久的な）ホームIPアドレスを使用して、他のインターネットノードと通信し続けることができます。
ホームエージェント（Home Agent）
モバイルノードのホームリンク上に少なくとも1つのインターフェイスを持つルーター。ホームエージェントは、モバイルノードがフォーリンリンクに接続しているとき、そのモバイルノードのホームアドレス宛てのパケットを横取りし、モバイルノードの気付アドレス（care-of address）へトンネリングします。モバイルノードは、モバイルIPで定義されている認証付きの登録プロトコルを通じて、現在の気付アドレスをホームエージェントに通知します。
フォーリンエージェント（Foreign Agent）
モバイルノードの（現在の）フォーリンリンク上に少なくとも1つのインターフェイスを持つルーター。モバイルノードがフォーリンエージェントの気付アドレスを使用する場合、フォーリンエージェントは、モバイルノードのホームエージェントによってトンネリングされたパケットのトンネルを解除し、モバイルノードへ配送します。フォーリンエージェントは、登録済みのモバイルノードが送信するパケットのデフォルトルーターとしても機能する場合があります。
ピア（Peer）
モバイルノードのPPPピア。モバイルノードのピアは、ホームエージェントの機能、フォーリンエージェントの機能、その両方をサポートしている場合もあれば、どちらもサポートしていない場合もあります。

1.3. Problem Statement

1.3. 問題の記述

In Mobile IP, packets sent to a mobile node's home address are routed first to the mobile node's home agent, a router on the mobile node's home link which intercepts packets sent to the home address. The home agent then tunnels such packets to the mobile node's care-of address, where the packets are extracted from the tunnel and delivered to the mobile node. There are two types of care-of addresses:

モバイルIPでは、モバイルノードのホームアドレスに送信されたパケットは、まずモバイルノードのホームエージェントにルーティングされます。ホームエージェントは、モバイルノードのホームリンク上にあり、ホームアドレスに送信されたパケットを横取りするルーターです。次にホームエージェントは、そのようなパケットをモバイルノードの気付アドレスへトンネリングし、そこでパケットはトンネルから取り出されてモバイルノードに配送されます。気付アドレスには2つの種類があります。

Co-located Care-of Address
An address temporarily assigned to a mobile node itself. In this case, the mobile node is the exit-point of the tunnel and decapsulates packets encapsulated for delivery by its home agent. A Co-located Care-of Address may be used by exactly one mobile node at any point in time.
Foreign Agent Care-of Address
An address of a foreign agent that has at least one interface on a mobile node's visited, foreign link. In this case, the foreign agent decapsulates packets that have been tunneled by the home agent and delivers them to the mobile node over the visited link. A Foreign Agent Care-of Address may be used simultaneously by many mobile nodes at any point in time.
共存気付アドレス（Co-located Care-of Address）
モバイルノード自身に一時的に割り当てられるアドレス。この場合、モバイルノードがトンネルの出口となり、ホームエージェントが配送のためにカプセル化したパケットのカプセル化を解除します。共存気付アドレスは、どの時点においても、ちょうど1つのモバイルノードだけが使用できます。
フォーリンエージェント気付アドレス（Foreign Agent Care-of Address）
モバイルノードの訪問先であるフォーリンリンク上に少なくとも1つのインターフェイスを持つフォーリンエージェントのアドレス。この場合、フォーリンエージェントが、ホームエージェントによってトンネリングされたパケットのカプセル化を解除し、訪問先のリンクを通じてモバイルノードへ配送します。フォーリンエージェント気付アドレスは、どの時点においても、多数のモバイルノードが同時に使用できます。

In Appendix B, Mobile IP [RFC2002] currently specifies only the following with respect to PPP:

モバイルIP [RFC2002] は現在、その付録Bで、PPPに関して次のことだけを規定しています。

"The Point-to-Point-Protocol (PPP) [RFC 1661] and its Internet Protocol Control Protocol (IPCP) [RFC 1332], negotiates [sic] the use of IP addresses.

"The mobile node SHOULD first attempt to specify its home address, so that if the mobile node is attaching to its home [link], the unrouted link will function correctly. When the home address is not accepted by the peer, but a transient IP address is dynamically assigned to the mobile node, and the mobile node is capable of supporting a co-located care-of address, the mobile node MAY register that address as a co-located care-of address. When the peer specifies its own IP address, that address MUST NOT be assumed to be a foreign agent care-of address or the IP address of a home agent."

「Point-to-Point-Protocol（PPP）[RFC 1661]とそのインターネットプロトコル制御プロトコル（IPCP）[RFC 1332]は、IPアドレスの使用をネゴシエーションする［原文ママ］。

「モバイルノードがホーム［リンク］に接続している場合にルーティングされないリンクが正しく機能するように、モバイルノードはまず自身のホームアドレスを指定しようとすべきです（SHOULD）。ホームアドレスがピアに受け入れられず、一時的なIPアドレスがモバイルノードに動的に割り当てられ、かつモバイルノードが共存気付アドレスをサポートできる場合、モバイルノードはそのアドレスを共存気付アドレスとして登録してもよいです（MAY）。ピアが自身のIPアドレスを指定した場合、そのアドレスがフォーリンエージェント気付アドレスやホームエージェントのIPアドレスであると想定してはなりません（MUST NOT）。」

Inspection of this text reveals that there is currently no way for the mobile node to use a foreign agent care-of address, without first being assigned a unique IP address, even if the peer also supports foreign agent functionality. The reason for this can be seen by walking through the IPCP negotiation:

この文章を調べると、ピアがフォーリンエージェントの機能もサポートしている場合であっても、現在は、モバイルノードがまず一意なIPアドレスを割り当てられることなしにフォーリンエージェント気付アドレスを使用する方法がないことがわかります。その理由は、IPCPのネゴシエーションを順に追うとわかります。

  1. A mobile node connects to a peer via PPP and proposes its home address in an IPCP Configure-Request containing the IP-Address option. In this scenario, we assume that the mobile node is connecting to some foreign link.
  2. The peer has no way of knowing whether this Configure-Request was received from: (a) a mobile node proposing its home address; or (b) a conventional node proposing some topologically non-routable address. In this case, the peer must (conservatively) send a Configure-Nak of the IP-Address option supplying a topologically appropriate address for use by the node at the other end of the PPP link.
  3. The mobile node, in turn, has no way of knowing whether this Configure-Nak was received because the peer is a foreign agent being conservative, or because the peer does not implement Mobile IP at all. Therefore, the mobile node must (conservatively) assume that the peer does not implement Mobile IP and continue the negotiation of an IP address in IPCP, after which point the mobile node can use the assigned address as a co-located care-of address.
  1. モバイルノードは、PPP経由でピアに接続し、IP-Addressオプションを含むIPCPのConfigure-Requestで自身のホームアドレスを提案します。このシナリオでは、モバイルノードは何らかのフォーリンリンクに接続しているものとします。
  2. ピアには、このConfigure-Requestを、(a) 自身のホームアドレスを提案しているモバイルノードから受信したのか、(b) トポロジー的にルーティング不可能なアドレスを提案している従来のノードから受信したのかを知る方法がありません。この場合、ピアは（保守的に）IP-AddressオプションのConfigure-Nakを送信し、PPPリンクの反対側のノードが使用するためのトポロジー的に適切なアドレスを提供しなければなりません。
  3. 一方のモバイルノードにも、このConfigure-Nakを受信したのが、ピアが保守的に振る舞っているフォーリンエージェントだからなのか、それともピアがモバイルIPをまったく実装していないからなのかを知る方法がありません。したがって、モバイルノードは（保守的に）ピアがモバイルIPを実装していないと想定し、IPCPでのIPアドレスのネゴシエーションを続けなければなりません。その後、モバイルノードは割り当てられたアドレスを共存気付アドレスとして使用できます。

Here we observe that, even if the mobile node's peer is a foreign agent and sends an Agent Advertisement to the mobile node after IPCP reaches the Opened state, the mobile node will still have negotiated a routable address in step 3, which it is likely already using as a co-located care-of address. This defeats the purpose of foreign agent care-of addresses, which are designed to be shared by multiple mobile nodes and to eliminate the need to assign a unique address to each mobile node.

ここで、モバイルノードのピアがフォーリンエージェントであり、IPCPがOpened状態に達した後にエージェント広告（Agent Advertisement）をモバイルノードに送信したとしても、モバイルノードはステップ3ですでにルーティング可能なアドレスをネゴシエーションしてしまっており、おそらくそれをすでに共存気付アドレスとして使用していることがわかります。これでは、複数のモバイルノードで共有され、モバイルノードごとに一意なアドレスを割り当てる必要をなくすように設計されているフォーリンエージェント気付アドレスの目的が損なわれます。

1.4. Requirements

1.4. 要件

The purpose of this document is to specify the behavior of both ends of the PPP link when one or more of the PPP peers supports Mobile IP. Specifically, the design of the option and protocol defined in this document is based upon the following requirements:

この文書の目的は、PPPピアの一方または両方がモバイルIPをサポートしている場合の、PPPリンクの両端の振る舞いを規定することです。具体的には、この文書で定義するオプションとプロトコルの設計は、次の要件に基づいています。

  1. The option and protocol described in this document must be backwards compatible with conventional nodes and their potential peers which do not implement this option nor any Mobile IP functionality.
  2. The option and protocol described in this document must accommodate a variety of scenarios, minimally those provided in the examples of Section 2.6.
  3. The option and protocol described in this document must not duplicate any functionality already defined in other IPCP options; specifically, the IP-Address option.
  4. A unique address must not be assigned to a mobile node unless absolutely necessary. Specifically, no such address is assigned to a mobile node that connects via PPP to its home link or a mobile node that connects via PPP to a foreign agent (and uses that foreign agent's care-of address).
  1. この文書で説明するオプションとプロトコルは、このオプションもモバイルIPの機能もまったく実装していない従来のノードおよびその潜在的なピアと後方互換でなければなりません。
  2. この文書で説明するオプションとプロトコルは、さまざまなシナリオに対応しなければなりません。少なくとも、セクション2.6の例で示すシナリオに対応する必要があります。
  3. この文書で説明するオプションとプロトコルは、他のIPCPオプション、具体的にはIP-Addressオプションですでに定義されている機能を重複して定義してはなりません。
  4. 絶対に必要な場合を除き、モバイルノードに一意なアドレスを割り当ててはなりません。具体的には、PPP経由で自身のホームリンクに接続するモバイルノードや、PPP経由でフォーリンエージェントに接続する（そしてそのフォーリンエージェントの気付アドレスを使用する）モバイルノードには、そのようなアドレスを割り当てません。

2.2. Overview

2.2. 概要

The Mobile-IPv4 Configuration Option is designed to be used in conjunction with the IP-Address Configuration Option. For the convenience of implementors, the detailed description in section 2.5 includes all possible combinations of these two options that might be sent by a PPP peer during IPCP. Along with each possibility is a description of how the receiver should interpret the contents as well as a suggested course of action.

Mobile-IPv4構成オプションは、IP-Address構成オプションと組み合わせて使用するように設計されています。実装者の便宜のため、セクション2.5の詳細な説明には、IPCPの間にPPPピアが送信する可能性のある、これら2つのオプションのすべての組み合わせを含めています。それぞれの組み合わせについて、受信者がその内容をどのように解釈すべきかの説明と、推奨される対応方法を示しています。

2.3. High-Level Requirements for Non-Mobile-Nodes

2.3. モバイルノード以外に対する高レベルの要件

A node that is not performing mobile node functionality (such as non-Mobile-IP-aware nodes as well as nodes performing only home agent functionality, foreign agent functionality, or both) MUST NOT include a Mobile-IPv4 Configuration Option within any Configure-Request message. As per [RFC1332], such a node SHOULD send a Configure-Request containing an IP-Address Configuration Option in which the IP-Address field is set to a non-zero IP address that the node has assigned to one of its interfaces. If an explicit IP address has been assigned to the node's PPP interface then this address SHOULD be sent in preference to any of the node's other addresses.

モバイルノードの機能を実行していないノード（モバイルIPを認識しないノードや、ホームエージェントの機能、フォーリンエージェントの機能、またはその両方だけを実行するノードなど）は、どのConfigure-RequestメッセージにもMobile-IPv4構成オプションを含めてはなりません（MUST NOT）。[RFC1332] に従い、そのようなノードは、IP-Address構成オプションを含むConfigure-Requestを送信すべきです（SHOULD）。このとき、IP-Addressフィールドには、そのノードが自身のインターフェイスの1つに割り当てている0以外のIPアドレスを設定します。ノードのPPPインターフェイスに明示的なIPアドレスが割り当てられている場合は、ノードの他のどのアドレスよりも優先してこのアドレスを送信すべきです（SHOULD）。

A node MUST NOT send a Configure-Nak containing a Mobile-IPv4 Configuration Option. Doing so is currently "undefined" and might cause interoperability problems when a useful meaning for Configure-Nak is ultimately defined for the Mobile-IPv4 Configuration Option. A node that sends a Configure-Ack containing a Mobile-IPv4 Configuration Option SHOULD send an Agent Advertisement [RFC2002] immediately upon IPCP for that link entering the Opened state.

ノードは、Mobile-IPv4構成オプションを含むConfigure-Nakを送信してはなりません（MUST NOT）。そうすることは現在「未定義」であり、最終的にMobile-IPv4構成オプションに対するConfigure-Nakの有用な意味が定義されたときに、相互運用性の問題を引き起こす可能性があります。Mobile-IPv4構成オプションを含むConfigure-Ackを送信したノードは、そのリンクのIPCPがOpened状態に入った直後にエージェント広告 [RFC2002] を送信すべきです（SHOULD）。

2.4. High-Level Requirements for Mobile Nodes

2.4. モバイルノードに対する高レベルの要件

A mobile node SHOULD begin its IPCP negotiation by sending the Configure-Request described in either item #1 or item #4 in Section 2.5. The mobile node MAY begin its negotiation with one of the other numbered items in Section 2.5 under extenuating circumstances.

モバイルノードは、セクション2.5の項目#1または項目#4のいずれかで説明するConfigure-Requestを送信することで、IPCPのネゴシエーションを開始すべきです（SHOULD）。やむを得ない事情がある場合、モバイルノードはセクション2.5の番号付き項目のうち他のものでネゴシエーションを開始してもよいです（MAY）。

A mobile node that receives a Configure-Ack containing a Mobile-IPv4 Configuration Option MUST receive an Agent Advertisement, possibly in response to an Agent Solicitation, before sending a Registration Request [RFC2002] if that mobile node is connecting to a foreign link. This is because the peer might be a foreign agent that enforces a policy which requires a mobile node to register with that foreign agent even if the mobile node is using a co-located care-of address. A mobile node need not wait for such an advertisement if it connects to its home link. See item 7a in section 2.5 for one way in which a mobile node can determine if it has connected to its home link. Another way is by receiving an explicit notification of this fact from its peer, such as receipt of the messages in items 1b, 2c, and 3a in section 2.5.

Mobile-IPv4構成オプションを含むConfigure-Ackを受信したモバイルノードは、フォーリンリンクに接続している場合、登録要求（Registration Request）[RFC2002] を送信する前に、エージェント広告を受信しなければなりません（MUST）。このエージェント広告は、エージェント要請（Agent Solicitation）に対する応答として受信する場合もあります。これは、ピアが、モバイルノードが共存気付アドレスを使用している場合であってもそのフォーリンエージェントを通じて登録することを要求するポリシーを適用するフォーリンエージェントである可能性があるためです。モバイルノードがホームリンクに接続する場合は、そのような広告を待つ必要はありません。モバイルノードがホームリンクに接続したかどうかを判断する方法の1つについては、セクション2.5の項目7aを参照してください。別の方法として、セクション2.5の項目1b、2c、3aのメッセージを受信するなど、ピアからこの事実について明示的な通知を受け取る方法もあります。

A mobile node that receives a Configure-Reject containing a Mobile-IPv4 Configuration Option SHOULD fall back to IPCP negotiation using the IP-Address option [RFC1332]. A mobile node SHOULD begin this negotiation with Request(IP=home) or Request(IP=0), depending on whether or not the mobile node is connecting to its home link, respectively. A mobile node MAY make this determination by inspection of an IP-Address option contained within a Configure-Request sent by its peer. If the prefix of the peer's stated IP-address is equal to the prefix of the mobile node's home address, then the mobile node MAY conclude that it is connecting to its home link. Otherwise, if the mobile node is connecting to a foreign link, then the mobile node SHOULD send Request(IP=0) since its peer might have no means for assigning addresses other than IPCP. This specification therefore updates this behavior as described in [RFC2002], the latter of which recommends that a mobile node begin IP-Address negotiation with Request(IP=Home) under all circumstances.

Mobile-IPv4構成オプションを含むConfigure-Rejectを受信したモバイルノードは、IP-Addressオプション [RFC1332] を使用したIPCPのネゴシエーションにフォールバックすべきです（SHOULD）。モバイルノードは、自身のホームリンクに接続しているかどうかに応じて、それぞれRequest(IP=home)またはRequest(IP=0)でこのネゴシエーションを開始すべきです（SHOULD）。モバイルノードは、ピアが送信したConfigure-Requestに含まれるIP-Addressオプションを調べることで、この判断をしてもよいです（MAY）。ピアが示したIPアドレスのプレフィックスがモバイルノードのホームアドレスのプレフィックスと等しい場合、モバイルノードは自身のホームリンクに接続していると結論してもよいです（MAY）。そうではなく、モバイルノードがフォーリンリンクに接続している場合は、ピアがIPCP以外にアドレスを割り当てる手段を持たない可能性があるため、モバイルノードはRequest(IP=0)を送信すべきです（SHOULD）。したがって、この仕様は、[RFC2002] で説明されている振る舞いを更新します。[RFC2002] では、モバイルノードはあらゆる状況においてRequest(IP=Home)でIP-Addressのネゴシエーションを開始することを推奨しています。

A peer that is performing neither home agent nor foreign agent functionality SHOULD send a Reject in response to any Request received from its peer that contains a Mobile-IPv4 Configuration Option.

ホームエージェントの機能もフォーリンエージェントの機能も実行していないピアは、Mobile-IPv4構成オプションを含むRequestをピアから受信した場合、それに対する応答としてRejectを送信すべきです（SHOULD）。

2.5. Detailed Description

2.5. 詳細な説明

The numbered items below show all possible combinations of Mobile-IPv4 and IP-Address Configuration Options that a mobile node (or a conventional node) might send to its peer. Mobile nodes SHOULD begin their IPCP negotiation with item #1 or item #4 depending on whether they prefer a co-located or a foreign agent care-of address respectively. The lettered items list the possible legal responses that a peer might send to the mobile node (or conventional node) in response to the numbered Request.

以下の番号付き項目は、モバイルノード（または従来のノード）がピアに送信する可能性のある、Mobile-IPv4構成オプションとIP-Address構成オプションのすべての組み合わせを示しています。モバイルノードは、共存気付アドレスとフォーリンエージェント気付アドレスのどちらを好むかに応じて、それぞれ項目#1または項目#4でIPCPのネゴシエーションを開始すべきです（SHOULD）。英字付きの項目は、番号付きのRequestに対する応答としてピアがモバイルノード（または従来のノード）に送信する可能性のある、正当な応答を列挙しています。

In each case, an interpretation is defined and a suggested course of action is provided. Finally, it is believed that the presentation below has the advantages of conciseness and precision in comparison to an equivalent presentation in "prose form."

それぞれの場合について、解釈を定義し、推奨される対応方法を示します。なお、以下の表現は、同等の内容を「散文形式」で表現するのに比べて、簡潔さと正確さの点で利点があると考えています。

  1. Request(IP=0,MIPv4=home) means "I prefer a co-located care-of address to a foreign agent care-of address." Peer MUST respond with one of the following:

    a.
    Nak(IP=coa) means "use coa as your co-located care-of address". Goto 2.
    b.
    Nak(IP=home) means "you're at home and don't need a care-of address". Goto 3.
    c.
    Reject(IP=0) means "I cannot assign a co-located care-of address but you're welcome to use me as a foreign agent". Goto 4.
    d.
    Reject(MIPv4=home) means "I do not implement the Mobile-IPv4 option". If the peer also sent Request(IP=address) and the prefix of the peer's assigned address is equal to that of the mobile node's home address, then goto 6 with a.b.c.d=home; otherwise, goto 5.
    e.
    Reject(IP=0,MIPv4=home) means "use the default". Goto 7.

    => Ack(IP=0, ...), Nak(MIPv4=any, ...) MUST NOT be sent.

  2. Request(IP=coa,MIPv4=home) means "I want to use coa as my co-located care-of address." Peer MUST respond with one of the following:

    a.
    Ack(IP=coa,MIPv4=home) means "ok, use coa as your co-located care-of address; be sure to wait for an advertisement." Opened.
    b.
    Nak(IP=alternate-coa) means "no, use alternate-coa as your co-located care-of address". Goto 2.
    c.
    Nak(IP=home) means "you're at home and don't need a co-located care-of address". Goto 3.
    d.
    Reject(IP=coa) means "coa is not a useful value for a co-located care-of address on this link and I cannot assign a useful one (or I will not negotiate the IP-Address option) -- you may use me as a foreign agent". Goto 4.
    e.
    Reject(MIPv4=home) means "I do not implement the Mobile-IPv4 option". If the peer also sent Request(IP=address) and the prefix of the peer's address is equal to that of the mobile node's home address, then goto 6 with a.b.c.d=home; otherwise, goto 5.
    f.
    Reject(IP=coa,MIPv4=home) means "use the default". Goto 7.

    => Nak(MIPv4=any, ...) MUST NOT be sent.

  3. Request(IP=home,MIPv4=home) means "I think I'm at home but if I'm wrong then I prefer a co-located care-of address to a foreign agent care-of address." Peer MUST respond with one of the following:

    a.
    Ack(IP=home,MIPv4=home) means "yes, you're at home". Opened.
    b.
    Nak(IP=coa) means "you're not at home, use coa as your co-located care-of address". Goto 2.
    c.
    Reject(IP=home) means "you're not at home and I cannot assign a co-located care-of address (or I will not negotiate the IP-Address option) -- you may use me as a foreign agent". Goto 4.
    d.
    Reject(MIPv4=home) means "I do not implement the Mobile-IPv4 option". If the peer also sent Request(IP=address) and the prefix of the peer's address is equal to that of the mobile node's home address, then goto 6 with a.b.c.d=home; otherwise, goto 5.
    e.
    Reject(IP=home,MIPv4=home) means "use the default". Goto 7.

    => Nak(MIPv4=any, ...) MUST NOT be sent.

  4. Request(MIPv4=home) means "I want to run Mobile IP over this link and I don't want a co-located care-of address." Peer MUST respond with one of the following:

    a.
    Ack(MIPv4=home) means "ok, wait for an advertisement to figure out where you are." Opened.
    b.
    Reject(MIPv4=home) means "I do not implement the Mobile-IPv4 option". If the peer also sent Request(IP=address) and the prefix of the peer's address is equal to that of the mobile node's home address, then goto 6 with a.b.c.d=home; otherwise, goto 5.

    => Nak(MIPv4=any, ...) MUST NOT be sent.

  5. Request(IP=0) means "Please assign an address/co-located-care-of-address". Peer MUST respond with one of the following:

    a.
    Nak(IP=a.b.c.d) means "use a.b.c.d as your address/co-located-care-of-address". Goto 6.
    b.
    Reject(IP=0) means "I cannot assign an address (for the Mobile Node to use as a co-located-care-of-address), or I do not implement the IP-Address option". Goto 7.

    => Ack(IP=0) MUST NOT be sent and historically means "I don't know your address either". Opened. An implementation MUST NOT use 0 as its IP address upon receiving Ack(IP=0) but MAY use some other, non-zero, interface address for packets sent on its PPP interface.

  6. Request(IP=a.b.c.d) means "I want to use a.b.c.d as my address/home-address/co-located-care-of-address". Peer MUST respond with one of the following:

    a.
    Ack(IP=a.b.c.d) means "ok, a.b.c.d is your address/home-address/co-located-care-of-address". Opened.
    b.
    Nak(IP=w.x.y.z) means "no, use w.x.y.z as your address/home-address/co-located-care-of-address". Goto 6.
    c.
    Reject(IP=a.b.c.d) means "a.b.c.d is a bad address to use, but I cannot give you a good one" or "I do not implement the IP-Address option". Goto 7.

  7. Request() means "I want to use the default". Peer MUST respond with one of the following:

    a.

    Ack() means "ok, use the default". Opened.

    In this case the mobile node will use the "default" values of the IP-Address option (no address configured by IPCP) and the Mobile-IPv4 option (the mobile node's IP home address). The mobile node SHOULD send Agent Solicitations to see if there are any agents present on the current link. (Note that the current "link" might also include a shared medium if the mobile node's PPP peer is a bridge.) If an agent is present and the mobile node receives an Agent Advertisement, then the mobile node employs its move-detection algorithm(s) and registers accordingly.

    In any case, if the mobile node's peer supplied an IP-Address option containing a non-zero value within an IPCP Configure-Request, the mobile node MAY use this address to determine whether or not it is connected to its home link. This can be accomplished by comparing the stated IP address with the mobile node's home address under the prefix-length associated with the home link. If the mobile node is connected to its home link then it SHOULD de-register with its home agent.

    Otherwise, the mobile node MAY attempt to obtain a topologically routable address through any of its supported means (e.g., DHCP, manual configuration, etc.) for use as a co-located care-of address. If the mobile node is successful in obtaining such an address then it SHOULD register this address with its home agent.

    => Nak(IP=0) MUST NOT be sent. Goto 6.

    a.
    Ack(IP=a.b.c.d)は「了解した。a.b.c.dがあなたのアドレス／ホームアドレス／共存気付アドレスである」を意味します。Opened状態になります。
    b.
    Nak(IP=w.x.y.z)は「いいえ、w.x.y.zをアドレス／ホームアドレス／共存気付アドレスとして使用せよ」を意味します。6へ進みます。
    c.
    Reject(IP=a.b.c.d)は「a.b.c.dは使用するには不適切なアドレスだが、適切なアドレスを与えることはできない」または「IP-Addressオプションを実装していない」を意味します。7へ進みます。

  7. Request()は「デフォルトを使用したい」ことを意味します。ピアは次のいずれかで応答しなければなりません（MUST）。

    a.

    Ack()は「了解した。デフォルトを使用せよ」を意味します。Opened状態になります。

    この場合、モバイルノードは、IP-Addressオプションの「デフォルト」値（IPCPで構成されたアドレスなし）と、Mobile-IPv4オプションの「デフォルト」値（モバイルノードのIPホームアドレス）を使用します。モバイルノードは、現在のリンク上にエージェントが存在するかどうかを確認するために、エージェント要請を送信すべきです（SHOULD）（なお、モバイルノードのPPPピアがブリッジである場合、現在の「リンク」には共有媒体も含まれる場合があります）。エージェントが存在し、モバイルノードがエージェント広告を受信した場合、モバイルノードは自身の移動検出アルゴリズムを用いて、それに応じて登録します。

    いずれの場合も、モバイルノードのピアが、IPCPのConfigure-Request内で0以外の値を含むIP-Addressオプションを提供した場合、モバイルノードはこのアドレスを使用して、自身がホームリンクに接続しているかどうかを判断してもよいです（MAY）。これは、示されたIPアドレスとモバイルノードのホームアドレスとを、ホームリンクに関連付けられたプレフィックス長で比較することで実現できます。モバイルノードがホームリンクに接続している場合は、ホームエージェントへの登録を解除すべきです（SHOULD）。

    そうでない場合、モバイルノードは、共存気付アドレスとして使用するために、自身がサポートする任意の手段（たとえば、DHCP、手動設定など）を通じて、トポロジー的にルーティング可能なアドレスの取得を試みてもよいです（MAY）。モバイルノードがそのようなアドレスの取得に成功した場合は、このアドレスをホームエージェントに登録すべきです（SHOULD）。

    => Nak(IP=0)を送信してはなりません（MUST NOT）。6へ進みます。

    => Nak()を送信してはなりません（MUST NOT）。

    => Reject()を送信してはなりません（MUST NOT）。

3. Additional Requirements

3. 追加の要件

3.1. Other IPCP Options

3.1. その他のIPCPオプション

A mobile node MUST NOT include the deprecated IP-Addresses option in any Configure-Request that contains a Mobile-IPv4 option, an IP-Address option, or both.

モバイルノードは、Mobile-IPv4オプション、IP-Addressオプション、またはその両方を含むConfigure-Requestに、非推奨のIP-Addressesオプションを含めてはなりません（MUST NOT）。

Conversely, the mobile node MAY include an IP-Compression-Protocol option and any other options that do not involve the negotiation of IP addresses.

一方、モバイルノードは、IP-Compression-Protocolオプションや、IPアドレスのネゴシエーションに関係しないその他のオプションを含めてもよいです（MAY）。

If a mobile node and a foreign agent or a home agent agree in IPCP to use Van Jacobson Header Compression [RFC1144], then the mobile node MUST NOT set the 'V' bit in its ensuing Mobile IP Registration Request [RFC2002]. If the PPP peer entities are utilizing VJ header compression there is no gain for the mobile ip entities to do so, and requesting this option is likely to cause confusion.

モバイルノードとフォーリンエージェントまたはホームエージェントが、IPCPでVan Jacobsonヘッダー圧縮 [RFC1144] を使用することに合意した場合、モバイルノードは、その後のモバイルIPの登録要求 [RFC2002] で「V」ビットを設定してはなりません（MUST NOT）。PPPのピアエンティティーがVJヘッダー圧縮を利用している場合、モバイルIPのエンティティーがそれを行っても得るものはなく、このオプションを要求すると混乱を招く可能性が高くなります。

3.2. Move Detection

3.2. 移動検出

Mobile nodes that connect via PPP MUST correctly implement PPP's IPCP, since movement by the mobile node will likely change its PPP peer. Specifically, mobile nodes MUST be prepared to renegotiate IPCP at any time, including, the renegotiation of the IP-Address Configuration Option and the Mobile-IPv4 Configuration Option described in this document. As per [RFC1661], a mobile node in the Opened state MUST renegotiate IPCP upon receiving an IPCP Configure-Request from its peer.

モバイルノードが移動するとPPPピアが変わる可能性が高いため、PPP経由で接続するモバイルノードは、PPPのIPCPを正しく実装しなければなりません（MUST）。具体的には、モバイルノードは、IP-Address構成オプションやこの文書で説明するMobile-IPv4構成オプションの再ネゴシエーションを含め、いつでもIPCPを再ネゴシエーションできるように準備しなければなりません（MUST）。[RFC1661] に従い、Opened状態のモバイルノードは、ピアからIPCPのConfigure-Requestを受信したときに、IPCPを再ネゴシエーションしなければなりません（MUST）。

Also note that certain wireless links can employ handoff and proxying mechanisms that would not necessarily require bringing down a PPP link but would indeed require a mobile node to register with a new foreign agent. Therefore, mobile nodes which connect to an agent via PPP MUST employ their move detection algorithms (see section 2.4.2 in [RFC2002]) and register whenever they detect a change in connectivity.

また、特定の無線リンクでは、PPPリンクを切断する必要は必ずしもないものの、モバイルノードが新しいフォーリンエージェントに登録する必要は確かに生じるような、ハンドオフやプロキシーの仕組みが用いられる場合があることにも注意してください。したがって、PPP経由でエージェントに接続するモバイルノードは、自身の移動検出アルゴリズム（[RFC2002] のセクション2.4.2を参照）を用い、接続性の変化を検出したときには常に登録しなければなりません（MUST）。

Specifically, a mobile node that fails to receive an Agent Advertisement within the Lifetime advertised by its current foreign agent, MUST assume that it has lost contact with that foreign agent (see Section 2.4.2.1, [RFC2002]). If, in the mean time, the mobile node has received Agent Advertisements from another foreign agent, the mobile node SHOULD immediately register with that foreign agent upon timing out with its current foreign agent.

具体的には、現在のフォーリンエージェントが広告したLifetime内にエージェント広告を受信できなかったモバイルノードは、そのフォーリンエージェントとの接続を失ったと想定しなければなりません（MUST）（[RFC2002] のセクション2.4.2.1を参照）。その間にモバイルノードが別のフォーリンエージェントからエージェント広告を受信していた場合、モバイルノードは、現在のフォーリンエージェントとの間でタイムアウトした時点で、ただちにそのフォーリンエージェントに登録すべきです（SHOULD）。

Likewise, a mobile node that implements move detection based upon the Prefix-Length Extension MUST compare the prefix of any advertising agents with that of its current foreign agent (see Section 2.4.2.2, [RFC2002]). If such a mobile node receives an Agent Advertisement from a foreign agent specifying a different prefix than that of its current foreign agent, then the mobile node that employs this method of move detection MUST register with that new foreign agent.

同様に、Prefix-Length拡張に基づく移動検出を実装しているモバイルノードは、広告しているエージェントのプレフィックスと現在のフォーリンエージェントのプレフィックスとを比較しなければなりません（MUST）（[RFC2002] のセクション2.4.2.2を参照）。そのようなモバイルノードが、現在のフォーリンエージェントとは異なるプレフィックスを示すフォーリンエージェントからエージェント広告を受信した場合、この移動検出方法を用いるモバイルノードは、その新しいフォーリンエージェントに登録しなければなりません（MUST）。

A mobile node MAY treat PPP link-establishment as a sufficient reason to proceed with a new Mobile IP registration. Section 2 defines the circumstances under which mobile nodes MUST wait for an Agent Advertisement before registering. Accordingly, foreign agents and home agents SHOULD send an Agent Advertisement over a PPP link immediately after IPCP for that link enters the Opened state.

モバイルノードは、PPPリンクの確立を、新たなモバイルIPの登録を進める十分な理由として扱ってもよいです（MAY）。セクション2では、モバイルノードが登録の前にエージェント広告を待機しなければならない（MUST）状況を定義しています。それに応じて、フォーリンエージェントとホームエージェントは、PPPリンクのIPCPがOpened状態に入った直後に、そのリンク上でエージェント広告を送信すべきです（SHOULD）。

4. Security Considerations

4. セキュリティーに関する考慮事項

This document introduces no known security threats over and above those facing any node on the Internet that either connects via PPP or implements Mobile IP or both. Specifically, service providers should use cryptographically strong authentication (e.g., CHAP [RFC1994]) to prevent theft-of-service. Additionally, users requiring confidentiality should use PPP link encryption [RFC1968], IP-layer encryption [RFC1827], or application-layer encryption, depending upon their individual requirements. Finally, Mobile IP authentication [RFC2002] protects against trivial denial-of-service attacks that could otherwise be waged against a mobile node and its home agent.

この文書は、PPP経由で接続するか、モバイルIPを実装するか、またはその両方を行うインターネット上のあらゆるノードが直面する脅威を超える、既知のセキュリティー上の脅威をもたらしません。具体的には、サービスの不正利用を防ぐために、サービスプロバイダーは暗号学的に強力な認証（たとえば、CHAP [RFC1994]）を使用すべきです。さらに、機密性を必要とするユーザーは、個々の要件に応じて、PPPリンクの暗号化 [RFC1968]、IP層の暗号化 [RFC1827]、またはアプリケーション層の暗号化を使用すべきです。最後に、モバイルIPの認証 [RFC2002] は、これがなければモバイルノードとそのホームエージェントに対して仕掛けられうる、単純なサービス拒否攻撃から保護します。
