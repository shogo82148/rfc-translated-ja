RFC 10066

Path Computation Element Communication Protocol (PCEP) Extensions for Signaling Multipath Information

RFC 10066

マルチパス情報をシグナリングするための経路計算要素通信プロトコル（PCEP）拡張

Abstract

概要

This document defines Path Computation Element Communication Protocol (PCEP) extensions to signal multipath information, associating multiple forwarding paths with a single PCEP Label Switched Path (LSP) to allow load balancing and redundancy across diverse paths. The extensions are generic and applicable to both stateless and stateful PCEP and are designed to be reusable for future path types. Their primary application is Segment Routing Policy (SR Policy), where a Candidate Path can contain multiple segment lists: current PCEP extensions for SR Policy only allow signaling of a single segment list per Candidate Path. These extensions enable multipath capabilities such as weighted or equal-cost load balancing across paths.

この文書は、マルチパス情報をシグナリングするための経路計算要素通信プロトコル（Path Computation Element Communication Protocol: PCEP）の拡張を定義します。 この拡張は、複数の転送パスを単一のPCEPラベルスイッチパス（Label Switched Path: LSP）に関連付けることで、 多様なパスにわたる負荷分散と冗長性を可能にします。 この拡張は汎用的なもので、ステートレスPCEPとステートフルPCEPの両方に適用でき、将来のパスタイプでも再利用できるよう設計されています。 主な用途はセグメントルーティングポリシー（SR Policy）であり、SRポリシーでは1つの候補パス（Candidate Path）に複数のセグメントリストを含めることができます。 現在のSRポリシー向けPCEP拡張では、候補パスごとに1つのセグメントリストしかシグナリングできません。 この拡張により、パス間の重み付き負荷分散や等コスト負荷分散といったマルチパスの機能が可能になります。

1. Introduction

1. はじめに

Segment Routing Policy (SR Policy) for Traffic Engineering [RFC9256] details the concepts of Segment Routing Policy and approaches to steering traffic into an SR Policy. In particular, it describes the SR Candidate Path as a collection of one or more segment lists. The current PCEP specifications only allow for signaling of one segment list per Candidate Path. The PCEP extension to support Segment Routing Policy Candidate Paths [RFC9862] specifically kept the signaling of multiple segment lists outside its scope.

トラフィックエンジニアリングのためのセグメントルーティングポリシー（SR Policy） [RFC9256]は、 セグメントルーティングポリシーの概念と、SRポリシーにトラフィックを誘導する方法について詳しく説明しています。 特に、SR候補パス（SR Candidate Path）を1つ以上のセグメントリストの集まりとして説明しています。 現在のPCEP仕様では、候補パスごとに1つのセグメントリストしかシグナリングできません。 セグメントルーティングポリシーの候補パスをサポートするPCEP拡張 [RFC9862]は、 複数のセグメントリストのシグナリングを明示的にその範囲外としていました。

This document defines the required extensions that allow the signaling of multipath information via PCEP. Although these extensions are motivated by the SR Policy use case, they are also applicable to other technologies. For SR Policy, support for [RFC9862] is a prerequisite for using the multipath extensions defined in this document with SR Policy Candidate Paths.

この文書は、PCEPを介してマルチパス情報をシグナリングするために必要な拡張を定義します。 これらの拡張はSRポリシーのユースケースを動機としていますが、ほかの技術にも適用できます。 SRポリシーでは、この文書で定義するマルチパス拡張をSRポリシーの候補パスで使用するための前提条件として、 [RFC9862]のサポートが必要です。

1.2. Terminology

1.2. 用語

The following terms are used in this document:

この文書では次の用語を使用します。

ECMP:
Equal-Cost Multipath, equally distributing traffic among multiple paths/links, where each path/link gets the same share of traffic as others.
W-ECMP:
Weighted Equal-Cost Multipath, unequally distributing traffic among multiple paths/links, where some paths/links get more traffic than others.
PLSP:
PCE Label Switched Path, a path or set of paths computed or controlled by the PCE. In the context of SR Policy, a PLSP corresponds to a Candidate Path.
Segment List:
An ordered list of segments that defines a forwarding path in Segment Routing, as defined in [RFC9256]. In PCEP for SR Policy, each segment list is encoded as an ERO or RRO.
ERO:
Explicit Route Object, defined in [RFC5440], encodes an explicit path. In the context of SR Policy, an ERO encodes a segment list.
RRO:
Record Route Object, defined in [RFC5440], encodes the actual signaled path. In the context of SR Policy, an RRO reports a segment list.
Path:
In the context of this document, a path refers to a single forwarding path encoded in an ERO or RRO. For SR Policy, a path corresponds to a segment list. The mechanisms defined in this document use the generic term "path" to allow applicability beyond SR Policy.
LSP:
Label Switched Path. The base PCEP specification [RFC4655] originally defined the use of the PCE architecture for MPLS and GMPLS networks with LSPs instantiated using the RSVP-TE signaling protocol [RFC3209]. Over time, support for additional path setup types such as SRv6 has been introduced [RFC9603]. The term "LSP" is used extensively in PCEP specifications and, while the multipath extensions defined in this document are applicable beyond SR Policy, in the context of PCEP for SR Policy [RFC9862], an LSP object represents an SR Policy Candidate Path, which may be an SRv6 path (still represented using the LSP object as specified in [RFC8231]). A single LSP may contain multiple paths (segment lists).
SR Policy:
A Segment Routing Policy as defined in [RFC9256], identified by the tuple (headend, color, endpoint).
ECMP:
等コストマルチパス（Equal-Cost Multipath）。複数のパスやリンクの間でトラフィックを均等に分散することで、各パスやリンクはほかと同じ割合のトラフィックを受け持ちます。
W-ECMP:
重み付き等コストマルチパス（Weighted Equal-Cost Multipath）。複数のパスやリンクの間でトラフィックを不均等に分散することで、一部のパスやリンクはほかよりも多くのトラフィックを受け持ちます。
PLSP:
PCEラベルスイッチパス（PCE Label Switched Path）。PCEによって計算または制御されるパス、またはパスの集合です。SRポリシーの文脈では、PLSPは候補パスに対応します。
セグメントリスト（Segment List）:
[RFC9256]で定義されている、セグメントルーティングにおける転送パスを定義するセグメントの順序付きリストです。SRポリシー向けのPCEPでは、各セグメントリストはEROまたはRROとしてエンコードされます。
ERO:
明示的経路オブジェクト（Explicit Route Object）。[RFC5440]で定義されており、明示的なパスをエンコードします。SRポリシーの文脈では、EROはセグメントリストをエンコードします。
RRO:
経路記録オブジェクト（Record Route Object）。[RFC5440]で定義されており、実際にシグナリングされたパスをエンコードします。SRポリシーの文脈では、RROはセグメントリストを報告します。
パス（Path）:
この文書の文脈では、パスはEROまたはRROにエンコードされた単一の転送パスを指します。SRポリシーでは、パスはセグメントリストに対応します。この文書で定義するメカニズムは、SRポリシー以外にも適用できるよう、「パス」という汎用的な用語を使用します。
LSP:
ラベルスイッチパス（Label Switched Path）。基本のPCEP仕様[RFC4655]は、もともとRSVP-TEシグナリングプロトコル[RFC3209]を使用してLSPを確立するMPLSおよびGMPLSネットワーク向けに、PCEアーキテクチャーの使用を定義していました。その後、SRv6などの追加のパスセットアップタイプのサポートが導入されました[RFC9603]。「LSP」という用語はPCEP仕様で広く使われています。この文書で定義するマルチパス拡張はSRポリシー以外にも適用できますが、SRポリシー向けのPCEP[RFC9862]の文脈では、LSPオブジェクトはSRポリシーの候補パスを表します。この候補パスはSRv6パスであってもかまいません（その場合も[RFC8231]で規定されているLSPオブジェクトを使って表現されます）。単一のLSPは複数のパス（セグメントリスト）を含むことができます。
SRポリシー（SR Policy）:
[RFC9256]で定義されているセグメントルーティングポリシーで、タプル（ヘッドエンド、カラー、エンドポイント）によって識別されます。

2. Motivation

2. 動機

This extension is motivated by the use cases described below.

この拡張は、以下で説明するユースケースを動機としています。

2.1. Signaling Multiple Segment Lists of an SR Candidate Path

2.1. SR候補パスの複数のセグメントリストのシグナリング

The Candidate Path of an SR Policy is the unit of signaling in PCEP [RFC9862]. A single Candidate Path can consist of multiple segment lists. Each segment list is represented by an ERO. In existing PCEP specifications, a PCEP LSP object is associated with exactly one ERO. This restriction prevents the encoding of multiple segment lists (i.e., multiple EROs) within the single LSP.

SRポリシーの候補パスは、PCEPにおけるシグナリングの単位です [RFC9862]。単一の候補パスは複数のセグメントリストから構成できます。 各セグメントリストはEROで表現されます。 既存のPCEP仕様では、PCEPのLSPオブジェクトはちょうど1つのEROに関連付けられます。 この制約により、単一のLSP内に複数のセグメントリスト（つまり複数のERO）をエンコードできません。

2.2. Splitting of Requested Bandwidth

2.2. 要求帯域幅の分割

For example, a Path Computation Client (PCC) may request a path whose bandwidth demand cannot be accommodated on any single link along an available path in the network. The PCE can return multiple paths that together can carry the requested bandwidth. The PCC can then equally or unequally split the incoming traffic among these paths.

たとえば、経路計算クライアント（Path Computation Client: PCC）が、 ネットワーク内の利用可能なパス上のどの単一リンクにも収まらない帯域幅需要を持つパスを要求することがあります。 PCEは、合わせて要求された帯域幅を運べる複数のパスを返すことができます。 そしてPCCは、到着するトラフィックをこれらのパスの間で均等または不均等に分割できます。

2.3. Reverse Path Information

2.3. 逆方向パス情報

PCEP extensions for Associated Bidirectional LSPs [RFC9059] defines a mechanism in PCEP to associate two opposite-direction SR Policy Candidate Paths. However, within each Candidate Path there can be multiple segment lists, and [RFC9059] does not define a mechanism to specify mapping between segment lists of the forward and reverse Candidate Paths.

関連付けられた双方向LSPのためのPCEP拡張 [RFC9059]は、 逆方向の2つのSRポリシー候補パスを関連付けるPCEPのメカニズムを定義しています。 しかし、各候補パスの中には複数のセグメントリストが存在しうるにもかかわらず、 [RFC9059]は 順方向と逆方向の候補パスのセグメントリスト間の対応を指定するメカニズムを定義していません。

Certain applications, such as Circuit Style SR Policy [CS-SR-POLICY], require the knowledge of reverse paths per segment list, not just per Candidate Path. For example, when the headend knows the reverse segment list for each forward segment list, then Performance Measurement (PM) / Bidirectional Forwarding Detection (BFD) can run a separate session on every segment list, by imposing a double stack (forward stack followed by a reverse stack) onto the packet. If the reverse segment list is co-routed with the forward segment list, then the PM/BFD session would traverse the same links in the forward and reverse directions, thus allowing detection of link/node failures in both directions.

サーキットスタイルSRポリシー [CS-SR-POLICY]などの一部のアプリケーションでは、 候補パス単位だけでなく、セグメントリスト単位で逆方向パスを知る必要があります。 たとえば、ヘッドエンドが各順方向セグメントリストに対する逆方向セグメントリストを知っていれば、 パケットに二重のスタック（順方向スタックに続けて逆方向スタック）を付与することで、 パフォーマンス測定（Performance Measurement: PM）や双方向転送検出（Bidirectional Forwarding Detection: BFD）は すべてのセグメントリストで個別のセッションを実行できます。 逆方向セグメントリストが順方向セグメントリストと同一経路（co-routed）であれば、 PM/BFDセッションは順方向と逆方向で同じリンクを通過するため、 両方向のリンクやノードの障害を検出できます。

3. Protocol Extensions

3. プロトコル拡張

3.1. PATH-ATTRIB Object

3.1. PATH-ATTRIBオブジェクト

This document defines the PATH-ATTRIB object that is used to carry per-path information and to act as a separator between EROs/RROs in the <intended-path>/<actual-path> Routing Backus-Naur Form (RBNF) [RFC5511] element. The PATH-ATTRIB object always precedes the ERO or RRO that it applies to. If multiple EROs or RROs are present, then each ERO or RRO MUST be preceded by a PATH-ATTRIB object that describes it.

この文書はPATH-ATTRIBオブジェクトを定義します。 このオブジェクトはパスごとの情報を運び、 ルーティングバッカス・ナウア記法（Routing Backus-Naur Form: RBNF）[RFC5511]の <intended-path>/<actual-path>要素において、ERO/RRO間の区切りとして機能します。 PATH-ATTRIBオブジェクトは、常にそれが適用されるEROまたはRROの前に置かれます。 複数のEROまたはRROが存在する場合、各EROまたはRROの前には、 それを記述するPATH-ATTRIBオブジェクトが置かれなければなりません（MUST）。

The PATH-ATTRIB Object-Class value is 45.

PATH-ATTRIBのObject-Class値は45です。

The PATH-ATTRIB Object-Type value is 1.

PATH-ATTRIBのObject-Type値は1です。

The format of the PATH-ATTRIB object is shown in Figure 1.

PATH-ATTRIBオブジェクトの形式をFigure 1に示します。

Flags (32 bits):


O (Operational - 3 bits):
Operational state of the path, same values as the identically named field in the LSP object [RFC8231]. The relationship between the per-path Operational state and the LSP-level Operational state in the LSP object is outside the scope of this document; for SR Policy, the Candidate Path validity criterion is defined in Section 2.8 of [RFC9256].
R (Reverse - 1 bit):
Indicates the path flows in the reverse direction, i.e., it originates on the LSP destination and terminates on the LSP source (usually the PCC headend itself). Paths with this flag set are not installed in the forwarding plane for load-balancing purposes, but MAY be used by the PCC for operations such as Performance Measurement (PM) or Bidirectional Forwarding Detection (BFD).
Unassigned bits
MUST be set to 0 on transmission and MUST be ignored on receipt.
Path ID (32 bits):
4-octet identifier that identifies a path (encoded in the ERO/RRO) within the set of multiple paths under the PCEP LSP. See Section 4.2 for details.
Optional TLVs:
Variable length field that can contain zero or more Type-Length-Value (TLV) elements that carry additional per-path information. The specific TLVs that can be included are defined in subsequent sections of this document.
Flags（32ビット）:


O（Operational - 3ビット）:
パスの運用状態（Operational state）です。 値はLSPオブジェクト[RFC8231]の同名のフィールドと同じです。 パスごとの運用状態と、LSPオブジェクト内のLSPレベルの運用状態との関係は、この文書の範囲外です。 SRポリシーについては、候補パスの有効性の基準が [RFC9256]のSection 2.8で定義されています。
R（Reverse - 1ビット）:

3.3. MULTIPATH-WEIGHT TLV

3.3. MULTIPATH-WEIGHT TLV

A new MULTIPATH-WEIGHT TLV is optional in the PATH-ATTRIB object.

新しいMULTIPATH-WEIGHT TLVは、PATH-ATTRIBオブジェクト内でオプションです。

Type (16 bits):
61 for "MULTIPATH-WEIGHT" TLV.
Length (16 bits):
MUST be set to 4.
Weight (32 bits):
unsigned integer weight of the path described by the enclosing PATH-ATTRIB object, if W-ECMP is desired. The fraction of flows that a specific ERO/RRO carries is derived from the ratio of its weight to the sum of the weights of all paths in the multipath (including that path): see Section 4.3 for details. For SR Policy, if the Weight value is 0, the corresponding segment list is declared invalid per Section 5.1 of [RFC9256] and carries no traffic. If all paths within an LSP have Weight 0, the sum of weights is zero, making the candidate path invalid per Section 2.11 of [RFC9256]. Signaling a zero-weight path alongside paths with non-zero weights can be used to drain traffic from a path while retaining its forwarding instructions.
Type（16ビット）:
「MULTIPATH-WEIGHT」TLVでは61です。
Length（16ビット）:
4に設定しなければなりません（MUST）。
Weight（32ビット）:
W-ECMPが望まれる場合の、 それを囲むPATH-ATTRIBオブジェクトが記述するパスの重みを表す符号なし整数です。 特定のERO/RROが運ぶフローの割合は、その重みと、マルチパス内のすべてのパス（そのパスを含む）の重みの合計との比から求められます。 詳細はSection 4.3を参照してください。 SRポリシーでは、Weight値が0の場合、対応するセグメントリストは [RFC9256]のSection 5.1に従って無効と宣言され、トラフィックを運びません。 LSP内のすべてのパスのWeightが0の場合、重みの合計は0になり、 [RFC9256]のSection 2.11に従って候補パスは無効になります。 重みが0でないパスと一緒に重みが0のパスをシグナリングすることで、 パスの転送命令を保持したまま、そのパスからトラフィックを排出（drain）できます。

When the MULTIPATH-WEIGHT TLV is absent from the PATH-ATTRIB object, or the PATH-ATTRIB object is absent from the <intended-path>/<actual-path>, then the Weight of the corresponding path is assumed to be 1.

A new MULTIPATH-OPPDIR-PATH TLV is optional in the PATH-ATTRIB object. Multiple instances of the TLV are allowed in the same PATH-ATTRIB object. See Section 4.4 for operational details.

Type (16 bits):
63 for "MULTIPATH-OPPDIR-PATH" TLV
Length (16 bits):
MUST be set to 8.
Reserved:
This field MUST be set to zero on transmission and MUST be ignored on receipt.
Flags (16 bits):


N (Node co-routed):
If set, indicates this path is node co-routed with its opposite-direction path specified in this TLV. Two opposite-direction paths are node co-routed if they traverse the same nodes, but MAY traverse different links. If not set, the paths are not guaranteed to be node co-routed (they may or may not traverse the same set of nodes).

If set, indicates this path is link co-routed with its opposite-direction path, specified in this TLV. Two opposite-direction paths are link co-routed if they traverse the same links (but in opposite directions). Link co-routing implies node co-routing; therefore, it is not necessary to set the N-flag when the L-flag is set.
The terms "link" and "node" used by the N-flag and L-flag
refer to the links and nodes as represented in the topology that the PCE uses for path computation. The exact nature of a link is determined by the PCE's topology view and is out of scope of this document. The same notion of "link" and "node" MUST be used consistently for both the forward and the opposite-direction path when evaluating co-routing; a path and its opposite-direction path are represented in the same topology view.

Type（16ビット）:
「MULTIPATH-OPPDIR-PATH」TLVでは63です。
Length（16ビット）:
8に設定しなければなりません（MUST）。
Reserved:

Flags（16ビット）:

3.5. Composite Candidate Path

3.5. 複合候補パス

SR Policy Architecture [RFC9256] defines the concept of a composite candidate path. A regular SR Policy candidate path outputs traffic to a set of segment lists, while an SR Policy composite candidate path outputs traffic recursively to a set of SR Policies on the same headend. In PCEP, the composite candidate path still consists of PATH-ATTRIB objects, but ERO is replaced by color of the recursively used SR Policy.

SRポリシーアーキテクチャー[RFC9256]は、 複合候補パス（composite candidate path）の概念を定義しています。 通常のSRポリシー候補パスはトラフィックをセグメントリストの集合に出力するのに対し、 SRポリシーの複合候補パスは、同じヘッドエンド上のSRポリシーの集合に再帰的にトラフィックを出力します。 PCEPでは、複合候補パスも引き続きPATH-ATTRIBオブジェクトから構成されますが、 EROは再帰的に使用されるSRポリシーのカラーに置き換えられます。

To signal the composite candidate path, this document makes use of the COLOR TLV, defined in [RFC9863]. For a composite candidate path, the COLOR TLV is included in the PATH-ATTRIB object, thus allowing each composite candidate path to do ECMP/W-ECMP among SR Policies identified by its constituent colors. To achieve W-ECMP, the MULTIPATH-WEIGHT TLV (Section 3.3) is included alongside the COLOR TLV in each PATH-ATTRIB object. Each PATH-ATTRIB object identifies one constituent color of the composite candidate path. If multiple COLOR TLVs are contained in the PATH-ATTRIB object, the first one is processed and the others MUST be ignored.

複合候補パスをシグナリングするために、この文書は [RFC9863]で定義されているCOLOR TLVを利用します。 複合候補パスでは、COLOR TLVをPATH-ATTRIBオブジェクトに含めることで、 各複合候補パスが、その構成要素のカラーで識別されるSRポリシー間でECMP/W-ECMPを行えるようになります。 W-ECMPを実現するには、各PATH-ATTRIBオブジェクトに、COLOR TLVとともにMULTIPATH-WEIGHT TLV （Section 3.3）を含めます。 各PATH-ATTRIBオブジェクトは、複合候補パスの構成要素のカラーを1つ識別します。 PATH-ATTRIBオブジェクトに複数のCOLOR TLVが含まれている場合、 最初のものが処理され、ほかのものは無視しなければなりません（MUST）。

An ERO MUST be included as per the existing RBNF; this ERO MUST contain no subobjects. This empty ERO serves as a placeholder to maintain compatibility with existing implementations based on the RBNF defined in [RFC8231]. If the headend receives a non-empty ERO for a composite candidate path, it MUST send a PCErr message with Error-Type = 19 ("Invalid Operation") and Error-Value = 21 ("Non-empty path").

既存のRBNFに従ってEROを含めなければなりません（MUST）。 このEROはサブオブジェクトを含まないようにしなければなりません（MUST）。 この空のEROは、[RFC8231]で定義されているRBNFに基づく既存の実装との互換性を保つためのプレースホルダーとして機能します。 ヘッドエンドは、複合候補パスに対して空でないEROを受信した場合、 Error-Type = 19（"Invalid Operation"）、Error-Value = 21（"Non-empty path"）の PCErrメッセージを送信しなければなりません（MUST）。

See Appendix A.2 for an example of the encoding.

エンコードの例についてはAppendix A.2を参照してください。

3.5.1. Per-Flow Candidate Path

3.5.1. フロー単位候補パス

Per-Flow Candidate Path builds on the concept of the composite candidate path. Each Path in a Per-Flow Candidate Path is assigned a 3-bit forwarding class value, which allows Quality-of-Service (QoS) classified traffic to be steered depending on the forwarding class.

フロー単位候補パス（Per-Flow Candidate Path）は、複合候補パスの概念の上に構築されます。 フロー単位候補パス内の各パスには3ビットの転送クラス値が割り当てられ、 これにより、サービス品質（Quality-of-Service: QoS）で分類されたトラフィックを転送クラスに応じて誘導できます。

A new MULTIPATH-FORWARD-CLASS TLV is optional in the PATH-ATTRIB object.

新しいMULTIPATH-FORWARD-CLASS TLVは、PATH-ATTRIBオブジェクト内でオプションです。

Type (16 bits):
76 for "MULTIPATH-FORWARD-CLASS" TLV.
Length (16 bits):
MUST be set to 4.
Flags (32 bits):


T (1 bit):
MPLS Traffic Class (TC) type. This is the most significant bit of the Flags field. When set, indicates that the FC value is derived from the MPLS TC bits as described in Section 8.6 of [RFC9256]. When not set, the interpretation of the FC value is reserved for future use; a future specification MAY define a wider, right-aligned classifier value occupying additional low-order bits of the Flags field (e.g., for a non-MPLS data plane).
FC (3 bits):
Forwarding class value. When the T-flag is set, this carries the MPLS TC-based forwarding class value as defined in Section 8.6 of [RFC9256]. This value is given by the QoS classifier to traffic entering the given Candidate Path. Different classes of traffic that enter the given Candidate Path can be differentially steered into different colors. The FC field allows up to 8 different forwarding classes (values 0-7). The semantics of specific FC values are significant at the headend node (PCC) that implements the SR Policy and are determined by that node's local QoS policy or configuration. Coordination of FC value meanings between PCEP peers (e.g., through out-of-band configuration management or operational procedures) is outside the scope of this document.
Unassigned bits
MUST be set to 0 on transmission and MUST be ignored on receipt.
Type（16ビット）:
「MULTIPATH-FORWARD-CLASS」TLVでは76です。
Length（16ビット）:
4に設定しなければなりません（MUST）。
Flags（32ビット）:


T（1ビット）:
MPLSトラフィッククラス（Traffic Class: TC）タイプです。これはFlagsフィールドの最上位ビットです。 設定されている場合、FC値が [RFC9256]のSection 8.6で説明されているとおりMPLSのTCビットから導出されることを示します。 設定されていない場合、FC値の解釈は将来の使用のために予約されています。 将来の仕様では、Flagsフィールドの追加の下位ビットを占める、より幅の広い右寄せの分類子の値を定義してもよいです（MAY） （たとえば、MPLS以外のデータプレーン向け）。

転送クラス値です。T-flagが設定されている場合、 これは[RFC9256]のSection 8.6で定義されているMPLS TCに基づく転送クラス値を運びます。 この値は、対象の候補パスに入るトラフィックに対してQoS分類子が付与するものです。 対象の候補パスに入る異なるクラスのトラフィックは、それぞれ異なるカラーに区別して誘導できます。 FCフィールドでは、最大8つの異なる転送クラス（値0〜7）を表せます。 特定のFC値のセマンティクスは、SRポリシーを実装するヘッドエンドノード（PCC）において意味を持ち、 そのノードのローカルなQoSポリシーまたは設定によって決まります。 PCEPピア間でのFC値の意味の調整（たとえば、帯域外の設定管理や運用手順による調整）は、 この文書の範囲外です。
未割り当てのビット
送信時には0に設定しなければならず（MUST）、受信時には無視しなければなりません（MUST）。

4.1. Capability Negotiation

4.1.1. Multipath Capability TLV

A peer that supports Per-Flow Candidate Path MUST set both the C-flag and F-flag. Note that the F-flag is defined independently of the C-flag to allow for future use cases that may use the MULTIPATH-FORWARD-CLASS TLV for purposes other than Per-Flow Candidate Path; in such cases, the F-flag MAY be set without the C-flag.

ケイパビリティーのネゴシエーションにおいて、F-flagとC-flagは独立に設定できることに注意してください。 フロー単位候補パス（Section 3.5.1）は複合候補パスの上に構築されますが、 F-flagはMULTIPATH-FORWARD-CLASS TLVがサポートされているかどうかを反映し、 C-flagは複合候補パスのシグナリングがサポートされているかどうかを反映します。 フロー単位候補パスをサポートするピアは、C-flagとF-flagの両方を設定しなければなりません（MUST）。 F-flagがC-flagとは独立に定義されているのは、 フロー単位候補パス以外の目的でMULTIPATH-FORWARD-CLASS TLVを使用する将来のユースケースを可能にするためです。 そのような場合、C-flagなしでF-flagを設定してもよいです（MAY）。

When a PCE computes an LSP path, it MUST NOT return more forward multipaths than the minimum of the effective "Number of Multipaths" values of both the PCE and PCC. The effective value for a given LSP is determined by the per-LSP MULTIPATH-CAP TLV in the LSP object if present; otherwise, it defaults to the value from the MULTIPATH-CAP TLV in the OPEN object. This ensures the PCE does not exceed either its own computation capability or the PCC's installation capability. If this TLV is absent from both OPEN and LSP objects, the PCEP speaker does not support multipath and the behavior is consistent with existing PCEP specifications, where a single path is associated with each LSP.

PCEは、LSPのパスを計算する際、 PCEとPCCの両方の実効的な「Number of Multipaths」値の最小値を超える数の順方向マルチパスを返してはなりません（MUST NOT）。 あるLSPの実効値は、LSPオブジェクト内のLSPごとのMULTIPATH-CAP TLVが存在すればそれによって決まり、 存在しなければOPENオブジェクト内のMULTIPATH-CAP TLVの値がデフォルトとなります。 これにより、PCEが自身の計算能力とPCCのインストール能力のいずれも超えないことが保証されます。 このTLVがOPENオブジェクトとLSPオブジェクトのどちらにも存在しない場合、 そのPCEPスピーカーはマルチパスをサポートしておらず、 その動作は各LSPに単一のパスが関連付けられる既存のPCEP仕様と一致します。

If a PCC receives more paths than it advertised support for, it MUST send a PCErr message with Error-Type = 19 ("Invalid Operation") and Error-Value = 36 ("Unsupported multipath capability"). When a PCE receives a PCRpt message containing more paths than its own computation capability, it MUST NOT treat this as an error condition; PCRpt conveys PCC-reported Operational state and is not subject to the PCE's computation limits.

PCCは、サポートを広告した数より多くのパスを受信した場合、 Error-Type = 19（"Invalid Operation"）、Error-Value = 36（"Unsupported multipath capability"）の PCErrメッセージを送信しなければなりません（MUST）。 PCEは、自身の計算能力より多くのパスを含むPCRptメッセージを受信した場合、 これをエラー状態として扱ってはなりません（MUST NOT）。 PCRptはPCCが報告する運用状態を伝えるものであり、PCEの計算上の制限の対象ではないためです。

The PCC MAY also include the MULTIPATH-CAP TLV in the LSP object for each individual LSP, to specify per-LSP values. The PCC MUST NOT include this TLV in the LSP object if the TLV was not present in the OPEN objects of both PCEP peers. TLV values in the LSP object override the session default values in the OPEN object. If a PCEP speaker receives a PATH-ATTRIB object but the multipath capability was not successfully negotiated during session establishment, it MUST treat this as an error. The PCEP speaker MUST send a PCErr message with Error-Type = 10 ("Reception of an invalid object") and Error-Value = 45 ("Unexpected PATH-ATTRIB object").

PCCは、LSPごとの値を指定するために、個々のLSPについてLSPオブジェクトにMULTIPATH-CAP TLVを含めてもよいです（MAY）。 両方のPCEPピアのOPENオブジェクトにこのTLVが存在しなかった場合、 PCCはLSPオブジェクトにこのTLVを含めてはなりません（MUST NOT）。 LSPオブジェクト内のTLVの値は、OPENオブジェクト内のセッションのデフォルト値を上書きします。 PCEPスピーカーは、セッション確立時にマルチパスケイパビリティーのネゴシエーションが成功していないにもかかわらず PATH-ATTRIBオブジェクトを受信した場合、これをエラーとして扱わなければなりません（MUST）。 そのPCEPスピーカーは、Error-Type = 10（"Reception of an invalid object"）、Error-Value = 45（"Unexpected PATH-ATTRIB object"）のPCErrメッセージを送信しなければなりません（MUST）。

For example, the PCC includes this TLV in the OPEN object at session establishment, setting "Number of Multipaths" to 4 and "O-flag" to 0. The PCC also includes this TLV in the LSP object for a particular LSP, setting "Number of Multipaths" to 16 and "O-flag" to 1. This indicates that the PCC only wants to receive the reverse path information for that particular LSP and that this LSP can have up to 16 multipaths, while other LSPs can only have up to 4 multipaths.

たとえば、PCCはセッション確立時にOPENオブジェクトにこのTLVを含め、 「Number of Multipaths」を4に、「O-flag」を0に設定します。 PCCはまた、特定のLSPについてLSPオブジェクトにこのTLVを含め、 「Number of Multipaths」を16に、「O-flag」を1に設定します。 これは、PCCがその特定のLSPについてのみ逆方向パス情報を受け取りたいこと、 およびこのLSPは最大16のマルチパスを持てる一方で、ほかのLSPは最大4つのマルチパスしか持てないことを示します。

Additionally, if a PCEP speaker receives a TLV within the PATH-ATTRIB object (such as MULTIPATH-WEIGHT, MULTIPATH-OPPDIR-PATH, or MULTIPATH-FORWARD-CLASS) but the corresponding capability flag was not set in the negotiated MULTIPATH-CAP TLV, it MUST treat this as an error. The PCEP speaker MUST send a PCErr message with Error-Type = 19 ("Invalid Operation") and Error-Value = 36 ("Unsupported multipath capability").

さらに、PCEPスピーカーは、PATH-ATTRIBオブジェクト内のTLV （MULTIPATH-WEIGHT、MULTIPATH-OPPDIR-PATH、MULTIPATH-FORWARD-CLASSなど）を受信したにもかかわらず、 ネゴシエーションされたMULTIPATH-CAP TLVで対応するケイパビリティーフラグが設定されていなかった場合、 これをエラーとして扱わなければなりません（MUST）。 そのPCEPスピーカーは、Error-Type = 19 （"Invalid Operation"）、Error-Value = 36（"Unsupported multipath capability"）のPCErrメッセージを送信しなければなりません（MUST）。

4.2. Path ID

4.2. Path ID

The Path ID uniquely identifies a Path within the context of an LSP. A single Path ID space is shared among all paths within the LSP, including forward paths and reverse paths (R-flag=1). Path IDs MUST be unique across forward and reverse paths within the same LSP. The meaning of "Path" depends on the type of LSP:

Path IDは、LSPのコンテキスト内でパスを一意に識別します。 順方向パスと逆方向パス（R-flag=1）を含め、LSP内のすべてのパスで単一のPath ID空間を共有します。 Path IDは、同じLSP内の順方向パスと逆方向パスにわたって一意でなければなりません（MUST）。 「パス」の意味はLSPの種類によって異なります。

  • For a regular SR Policy Candidate Path, the Paths within that LSP are the segment lists.

  • For a composite candidate path (Section 3.5), the Paths within that LSP are the constituent SR Policies, each of which is identified by its color (carried in the COLOR TLV within the corresponding PATH-ATTRIB object).

  • 通常のSRポリシー候補パスでは、そのLSP内のパスはセグメントリストです。

  • 複合候補パス（Section 3.5）では、そのLSP内のパスは構成要素のSRポリシーであり、 それぞれ（対応するPATH-ATTRIBオブジェクト内のCOLOR TLVで運ばれる）カラーによって識別されます。

Value 0 indicates an unallocated Path ID. The value of 0 MAY be used when this Path is not referenced and the allocation of a Path ID is not necessary.

値0は、未割り当てのPath IDを示します。 このパスが参照されず、Path IDの割り当てが不要な場合は、値0を使用してもよいです（MAY）。

Path IDs are allocated by the PCEP peer that owns the LSP. If the LSP is delegated to the PCE, then the PCE allocates the Path IDs and sends them in the PCRep/PCUpd/PCInitiate messages. If the LSP is locally computed on the PCC, then the PCC allocates the Path IDs and sends them in the PCReq/PCRpt messages. When LSP delegation changes (e.g., the PCC revokes delegation from the PCE), the new path owner SHOULD retain the existing Path IDs to simplify path correlation in the event of redelegation. If the new owner cannot retain them, it MAY allocate new Path IDs.

Path IDは、LSPを所有するPCEPピアによって割り当てられます。 LSPがPCEに委任されている場合、PCEがPath IDを割り当て、 PCRep/PCUpd/PCInitiateメッセージで送信します。 LSPがPCC上でローカルに計算される場合、PCCがPath IDを割り当て、 PCReq/PCRptメッセージで送信します。 LSPの委任が変わった場合（たとえば、PCCがPCEからの委任を取り消した場合）、 再委任の際のパスの対応付けを簡単にするため、新しいパスの所有者は既存のPath IDを保持すべきです（SHOULD）。 新しい所有者がそれらを保持できない場合は、新しいPath IDを割り当ててもよいです（MAY）。

If a PCEP speaker detects that there are two Paths with the same non-zero Path ID, then the PCEP speaker MUST send a PCErr message with Error-Type = 10 ("Reception of an invalid object") and Error-Value = 38 ("Conflicting Path ID"). Multiple paths MAY have Path ID set to 0, as this value indicates those paths are not referenced and do not require unique identification.

PCEPスピーカーは、0以外の同じPath IDを持つ2つのパスがあることを検出した場合、 Error-Type = 10（"Reception of an invalid object"）、 Error-Value = 38（"Conflicting Path ID"）のPCErrメッセージを送信しなければなりません（MUST）。 複数のパスがPath IDを0に設定してもよいです（MAY）。 この値は、それらのパスが参照されず、一意な識別を必要としないことを示すためです。

4.3. Signaling Multiple Paths for Load Balancing

4.3. 負荷分散のための複数パスのシグナリング

The PATH-ATTRIB object can be used to signal multiple paths and indicate equal or unequal load balancing among the set of multipaths. In this case, the PATH-ATTRIB is populated for each ERO as follows:

PATH-ATTRIBオブジェクトは、複数のパスをシグナリングし、 マルチパスの集合の間での均等または不均等な負荷分散を示すために使用できます。 この場合、PATH-ATTRIBは各EROについて次のように設定されます。

  1. The PCE MAY assign a unique Path ID to each ERO path and populate it inside the PATH-ATTRIB object. The Path ID is unique within the context of a PLSP (when non-zero).

  2. The PCE MAY include the MULTIPATH-WEIGHT TLV inside the PATH-ATTRIB object, populating a weight value to reflect the relative share of traffic to be carried by the path. If the MULTIPATH-WEIGHT is not carried inside a PATH-ATTRIB object, the PCC MUST assume the default weight of 1 when computing the traffic share.

  3. The PCC derives the fraction of flows carried by a specific primary path from the ratio of its weight to the sum of the weights of all paths in the multipath. For SR Policy, the use of weights for load balancing between segment lists of a Candidate Path is described in Section 2.11 of [RFC9256].

  1. PCEは、各EROパスに一意なPath IDを割り当て、 それをPATH-ATTRIBオブジェクト内に設定してもよいです（MAY）。 Path IDは、（0以外の場合）PLSPのコンテキスト内で一意です。

  2. PCEは、PATH-ATTRIBオブジェクト内にMULTIPATH-WEIGHT TLVを含め、 そのパスが運ぶトラフィックの相対的な割合を反映する重みの値を設定してもよいです（MAY）。 PATH-ATTRIBオブジェクト内でMULTIPATH-WEIGHTが運ばれない場合、 PCCはトラフィックの割合を計算する際にデフォルトの重み1を仮定しなければなりません（MUST）。

  3. PCCは、特定のプライマリーパスが運ぶフローの割合を、 その重みと、マルチパス内のすべてのパスの重みの合計との比から求めます。 SRポリシーについては、候補パスのセグメントリスト間の負荷分散における重みの使用が [RFC9256]のSection 2.11で説明されています。

4.4. Signaling Opposite-Direction Path Information

4.4. 逆方向パス情報のシグナリング

The PATH-ATTRIB object can be used to signal opposite-direction path associations within a PCEP LSP. This capability is used to establish bidirectional path relationships where forward and reverse paths can be explicitly mapped to each other. In this case, the PATH-ATTRIB is populated for each ERO as follows:

PATH-ATTRIBオブジェクトは、PCEPのLSP内で逆方向パスの関連付けをシグナリングするために使用できます。 この機能は、順方向パスと逆方向パスを互いに明示的に対応付けられる双方向のパス関係を確立するために使われます。 この場合、PATH-ATTRIBは各EROについて次のように設定されます。

  1. The PCEP peer (PCC or PCE) allocates a unique Path ID to each path and populates it inside the PATH-ATTRIB object. The Path ID is unique within the context of a PLSP (PCE Label Switched Path).

  2. For paths that have opposite-direction counterparts, the MULTIPATH-OPPDIR-PATH TLV is added to the PATH-ATTRIB object. The Opposite-Direction Path ID field is set to reference the Path ID of the corresponding opposite-direction path.

  3. Multiple instances of the MULTIPATH-OPPDIR-PATH TLV MAY be present in the same PATH-ATTRIB object to support many-to-many mappings between forward and reverse paths. This allows a single forward path to map to multiple reverse paths and vice versa. A many-to-many mapping can occur when a segment list contains Node Segment(s) that traverse parallel links at a midpoint. The reverse of this segment list may require multiple reverse segment lists to cover all the parallel links at the midpoint.

  4. The N-flag and L-flag in the MULTIPATH-OPPDIR-PATH TLV MAY be set to indicate node co-routing or link co-routing respectively. These flags inform the receiver about the relationship between the forward and reverse paths.

    The N-flag and L-flag describe the relationship between the signaled paths as known to the PCEP speaker at the time the message is sent. They do not guarantee that transient local protection, local repair, or local policy actions in the network will preserve node or link co-routing for all forwarded traffic.

  5. For paths that have no opposite-direction counterpart, the MULTIPATH-OPPDIR-PATH TLV is omitted from the PATH-ATTRIB object.

  1. PCEPピア（PCCまたはPCE）は、各パスに一意なPath IDを割り当て、 それをPATH-ATTRIBオブジェクト内に設定します。 Path IDは、PLSP（PCEラベルスイッチパス）のコンテキスト内で一意です。

  2. 逆方向の対となるパスを持つパスについては、 PATH-ATTRIBオブジェクトにMULTIPATH-OPPDIR-PATH TLVを追加します。 Opposite-Direction Path IDフィールドには、対応する逆方向パスのPath IDを参照するよう設定します。

  3. 順方向パスと逆方向パスの間の多対多の対応付けをサポートするために、 同じPATH-ATTRIBオブジェクト内にMULTIPATH-OPPDIR-PATH TLVの複数のインスタンスが存在してもよいです（MAY）。 これにより、単一の順方向パスを複数の逆方向パスに対応付けることができ、その逆も可能です。 多対多の対応付けは、セグメントリストが中間点で並列リンクを通過するノードセグメントを含む場合に発生することがあります。 このセグメントリストの逆方向では、中間点のすべての並列リンクをカバーするために、 複数の逆方向セグメントリストが必要になることがあります。

  4. MULTIPATH-OPPDIR-PATH TLVのN-flagとL-flagは、 それぞれノード同一経路またはリンク同一経路を示すために設定してもよいです（MAY）。 これらのフラグは、順方向パスと逆方向パスの関係を受信者に知らせます。

    N-flagとL-flagは、メッセージ送信時点でPCEPスピーカーが把握している、シグナリングされたパス間の関係を記述します。 これらは、ネットワーク内の一時的なローカル保護、ローカル修復、ローカルポリシーの動作が、 転送されるすべてのトラフィックについてノードやリンクの同一経路性を維持することを保証するものではありません。

  5. 逆方向の対となるパスを持たないパスについては、 PATH-ATTRIBオブジェクトからMULTIPATH-OPPDIR-PATH TLVを省略します。

Forward paths (R-flag=0) and reverse paths (R-flag=1) are included in the same PCEP LSP, allowing bidirectional relationships to be established in a single message exchange. The opposite-direction path associations MUST be symmetric within the same LSP: for each (A -> B) reference expressed via a MULTIPATH-OPPDIR-PATH TLV instance in path A's PATH-ATTRIB object, the corresponding (B -> A) reference MUST also be present as a MULTIPATH-OPPDIR-PATH TLV instance in path B's PATH-ATTRIB object. Multiple MULTIPATH-OPPDIR-PATH TLV instances per PATH-ATTRIB object are permitted, supporting many-to-many mappings. Additionally, the R-flags of opposite-direction paths MUST have opposite values (one set to 0, the other to 1).

順方向パス（R-flag=0）と逆方向パス（R-flag=1）は同じPCEPのLSPに含まれるため、 単一のメッセージ交換で双方向の関係を確立できます。 逆方向パスの関連付けは、同じLSP内で対称でなければなりません（MUST）。 つまり、パスAのPATH-ATTRIBオブジェクト内のMULTIPATH-OPPDIR-PATH TLVインスタンスで表現された 各（A -> B）の参照について、対応する（B -> A）の参照も、 パスBのPATH-ATTRIBオブジェクト内のMULTIPATH-OPPDIR-PATH TLVインスタンスとして存在しなければなりません（MUST）。 PATH-ATTRIBオブジェクトごとに複数のMULTIPATH-OPPDIR-PATH TLVインスタンスが許可されており、 多対多の対応付けをサポートします。 さらに、逆方向の関係にあるパスのR-flagは、互いに反対の値（一方が0、もう一方が1）でなければなりません（MUST）。

If a PCEP speaker receives an opposite-direction path mapping that is asymmetric or where the R-flags are inconsistent, it MUST send a PCErr message with Error-Type = 19 ("Invalid Operation") and Error-Value = 37 ("Invalid opposite-direction path mapping").

PCEPスピーカーは、非対称である、またはR-flagが矛盾している逆方向パスの対応付けを受信した場合、 Error-Type = 19（"Invalid Operation"）、Error-Value = 37 （"Invalid opposite-direction path mapping"）のPCErrメッセージを送信しなければなりません（MUST）。

See Appendix A.3 for an example of usage.

使用例についてはAppendix A.3を参照してください。

5. PCEP Message Extensions

5. PCEPメッセージの拡張

The RBNF of PCRpt and PCUpd messages, as defined in [RFC8231], uses a combination of <intended-path> and/or <actual-path>. PCReq and PCRep messages, as defined in [RFC5440] and extended by [RFC8231], directly include ERO and RRO within their respective message structures rather than encapsulating them within <intended-path> or <actual-path> constructs.

[RFC8231]で定義されているPCRptメッセージとPCUpdメッセージのRBNFは、 <intended-path>と<actual-path>の一方または両方の組み合わせを使用します。 [RFC5440]で定義され、[RFC8231]で拡張されたPCReqメッセージとPCRepメッセージは、 EROとRROを<intended-path>や<actual-path>の構成要素に包むのではなく、 それぞれのメッセージ構造の中に直接含めます。

As specified in Section 6.1 of [RFC8231], within the context of messages that use these constructs, <intended-path> is represented by the ERO and <actual-path> is represented by the RRO:

[RFC8231]のSection 6.1で規定されているとおり、 これらの構成要素を使用するメッセージのコンテキストでは、 <intended-path>はEROで表され、<actual-path>はRROで表されます。

   <intended-path> ::= <ERO>

   <actual-path> ::= <RRO>
   <intended-path> ::= <ERO>

   <actual-path> ::= <RRO>

This document extends [RFC8231] by allowing multiple EROs/RROs to be present in the <intended-path>/<actual-path>:

この文書は、<intended-path>/<actual-path>に複数のERO/RROが存在できるようにすることで、 [RFC8231]を拡張します。

   <intended-path> ::= <ERO> |
                       <PATH-ATTRIB><ERO>[<intended-path-multipath>]

   <intended-path-multipath> ::= <PATH-ATTRIB><ERO>
                                 [<intended-path-multipath>]

   <actual-path> ::= <RRO> |
                     <PATH-ATTRIB><RRO>[<actual-path-multipath>]

   <actual-path-multipath> ::= <PATH-ATTRIB><RRO>
                               [<actual-path-multipath>]
   <intended-path> ::= <ERO> |
                       <PATH-ATTRIB><ERO>[<intended-path-multipath>]

   <intended-path-multipath> ::= <PATH-ATTRIB><ERO>
                                 [<intended-path-multipath>]

   <actual-path> ::= <RRO> |
                     <PATH-ATTRIB><RRO>[<actual-path-multipath>]

   <actual-path-multipath> ::= <PATH-ATTRIB><RRO>
                               [<actual-path-multipath>]

Similarly, this document extends [RFC8281] by allowing multiple paths in the PCInitiate message by allowing multiple EROs with their associated path attributes. The PCE-initiated LSP instantiation format is updated to:

同様に、この文書は、関連するパス属性を伴う複数のEROを許可することで PCInitiateメッセージで複数のパスを扱えるようにし、 [RFC8281]を拡張します。 PCE起動のLSPインスタンス化の形式は次のように更新されます。

   <PCE-initiated-lsp-instantiation> ::= <SRP>
                                          <LSP>
                                          [<END-POINTS>]
                                          <intended-path>
                                          [<attribute-list>]
   <PCE-initiated-lsp-instantiation> ::= <SRP>
                                          <LSP>
                                          [<END-POINTS>]
                                          <intended-path>
                                          [<attribute-list>]

where <intended-path> follows the recursive definition above, allowing multiple paths to be signaled in a single PCInitiate message. When multiple paths are present, each ERO MUST be preceded by a PATH-ATTRIB object that describes it. A single path MAY be sent as a bare ERO without PATH-ATTRIB for backward compatibility.

ここで、<intended-path>は上記の再帰的な定義に従い、 単一のPCInitiateメッセージで複数のパスをシグナリングできるようにします。 複数のパスが存在する場合、各EROの前には、それを記述するPATH-ATTRIBオブジェクトが置かれなければなりません（MUST）。 後方互換性のために、単一のパスはPATH-ATTRIBを伴わない裸のEROとして送信してもよいです（MAY）。

This document also extends the PCRep and PCReq messages, defined in [RFC5440], to carry multipath information. Because these messages include the ERO and RRO directly rather than within the <intended-path>/<actual-path> constructs, the extension allows a PATH-ATTRIB object to precede each ERO or RRO that it describes.

この文書はまた、[RFC5440]で定義されているPCRepメッセージとPCReqメッセージを拡張し、 マルチパス情報を運べるようにします。 これらのメッセージは、EROとRROを<intended-path>/<actual-path>の構成要素の中ではなく直接含むため、 この拡張では、記述対象の各EROまたはRROの前にPATH-ATTRIBオブジェクトを置けるようにします。

In the PCRep message, the <path> element is updated to allow a PATH-ATTRIB object to precede the ERO, with multiple <path> elements in the existing <path-list> used to signal multiple paths:

PCRepメッセージでは、<path>要素を更新してEROの前にPATH-ATTRIBオブジェクトを置けるようにし、 既存の<path-list>内の複数の<path>要素を使って複数のパスをシグナリングします。

   <path> ::= <ERO><attribute-list> |
              <PATH-ATTRIB><ERO><attribute-list>
   <path> ::= <ERO><attribute-list> |
              <PATH-ATTRIB><ERO><attribute-list>

When multiple paths are returned for load balancing, each <path> in the <path-list> MUST include a PATH-ATTRIB object preceding its ERO. A single <path> MAY be sent as a bare ERO without PATH-ATTRIB for backward compatibility.

負荷分散のために複数のパスが返される場合、 <path-list>内の各<path>は、そのEROの前にPATH-ATTRIBオブジェクトを含めなければなりません（MUST）。 後方互換性のために、単一の<path>はPATH-ATTRIBを伴わない裸のEROとして送信してもよいです（MAY）。

In the PCReq message, the existing path reported for reoptimization is updated to allow multiple RROs, each preceded by a PATH-ATTRIB object:

PCReqメッセージでは、再最適化のために報告される既存のパスを更新し、 それぞれの前にPATH-ATTRIBオブジェクトが置かれた複数のRROを許可します。

   <request> ::= <RP>
                 <END-POINTS>
                 [<LSP>]
                 [<LSPA>]
                 [<BANDWIDTH>]
                 [<metric-list>]
                 [<reported-path>]
                 [<IRO>]
                 [<LOAD-BALANCING>]

   <reported-path> ::= <RRO>[<BANDWIDTH>] |
                       <PATH-ATTRIB><RRO>[<BANDWIDTH>]
                       [<reported-path-multipath>]

   <reported-path-multipath> ::= <PATH-ATTRIB><RRO>[<BANDWIDTH>]
                                 [<reported-path-multipath>]
   <request> ::= <RP>
                 <END-POINTS>
                 [<LSP>]
                 [<LSPA>]
                 [<BANDWIDTH>]
                 [<metric-list>]
                 [<reported-path>]
                 [<IRO>]
                 [<LOAD-BALANCING>]

   <reported-path> ::= <RRO>[<BANDWIDTH>] |
                       <PATH-ATTRIB><RRO>[<BANDWIDTH>]
                       [<reported-path-multipath>]

   <reported-path-multipath> ::= <PATH-ATTRIB><RRO>[<BANDWIDTH>]
                                 [<reported-path-multipath>]

When multiple existing paths are reported, each RRO MUST be preceded by a PATH-ATTRIB object. A single reported path MAY be sent as a bare RRO without PATH-ATTRIB for backward compatibility.

複数の既存パスが報告される場合、各RROの前にはPATH-ATTRIBオブジェクトが置かれなければなりません（MUST）。 後方互換性のために、単一の報告パスはPATH-ATTRIBを伴わない裸のRROとして送信してもよいです（MAY）。

The LOAD-BALANCING object [RFC5440] and the multipath extensions defined in this document are two different mechanisms for requesting multiple paths and MUST NOT be combined. The LOAD-BALANCING object requests a set of independent TE LSPs, each with its own bandwidth, whereas these extensions return multiple paths within a single LSP. Accordingly, a PCReq message MUST NOT contain both a LOAD-BALANCING object and a MULTIPATH-CAP TLV (in the LSP object) for the same request. A PCEP speaker that receives such a request MUST send a PCErr message with Error-Type = 19 ("Invalid Operation") and Error-Value = 38 ("LOAD-BALANCING and MULTIPATH-CAP TLV in the same request").

LOAD-BALANCINGオブジェクト[RFC5440]と、 この文書で定義するマルチパス拡張は、複数のパスを要求するための2つの異なるメカニズムであり、 組み合わせてはなりません（MUST NOT）。 LOAD-BALANCINGオブジェクトはそれぞれが独自の帯域幅を持つ独立したTE LSPの集合を要求するのに対し、 これらの拡張は単一のLSP内の複数のパスを返します。 したがって、PCReqメッセージは、同じ要求に対してLOAD-BALANCINGオブジェクトと （LSPオブジェクト内の）MULTIPATH-CAP TLVの両方を含んではなりません（MUST NOT）。 そのような要求を受信したPCEPスピーカーは、Error-Type = 19（"Invalid Operation"）、 Error-Value = 38（"LOAD-BALANCING and MULTIPATH-CAP TLV in the same request"）のPCErrメッセージを送信しなければなりません（MUST）。

The capability negotiation and error handling defined in Section 4 apply equally to the PCReq and PCRep messages. In particular, a PCEP speaker that receives a PATH-ATTRIB object, or a TLV within it, in a PCReq or PCRep message without having negotiated the corresponding capability in the MULTIPATH-CAP TLV MUST treat it as an error as specified in Section 4.

Section 4で定義されているケイパビリティーのネゴシエーションとエラー処理は、 PCReqメッセージとPCRepメッセージにも同様に適用されます。 特に、MULTIPATH-CAP TLVで対応するケイパビリティーをネゴシエーションしていないのに、 PCReqまたはPCRepメッセージでPATH-ATTRIBオブジェクトまたはその中のTLVを受信したPCEPスピーカーは、 Section 4で規定されているとおり、それをエラーとして扱わなければなりません（MUST）。

The RBNF extensions defined in this section are additive and apply only to sessions where the capabilities from the MULTIPATH-CAP TLV have been successfully negotiated (Section 4). Legacy PCEP peers that do not advertise the MULTIPATH-CAP TLV will not receive PATH-ATTRIB objects introduced by the updated RBNF.

このセクションで定義するRBNFの拡張は追加的なものであり、 MULTIPATH-CAP TLVによるケイパビリティーのネゴシエーションが成功したセッション （Section 4）にのみ適用されます。 MULTIPATH-CAP TLVを広告しない従来のPCEPピアが、 更新されたRBNFで導入されたPATH-ATTRIBオブジェクトを受信することはありません。

7. Security Considerations

7. セキュリティーに関する考慮事項

The security considerations described in [RFC5440], [RFC8231], [RFC8281], [RFC8664], [RFC9256], [RFC9862], and [RFC9863] are applicable to this specification.

[RFC5440]、[RFC8231]、 [RFC8281]、[RFC8664]、[RFC9256]、 [RFC9862]、 [RFC9863]で説明されているセキュリティーに関する考慮事項は、この仕様にも適用されます。

As per [RFC8231], it is RECOMMENDED that these PCEP extensions only be activated on authenticated and encrypted sessions across PCEs and PCCs belonging to the same administrative authority, using Transport Layer Security (TLS) [RFC8253] [RFC9916] as per the recommendations and best current practices in [RFC9325].

[RFC8231]に従い、これらのPCEP拡張は、 同じ管理主体に属するPCEとPCCの間で、[RFC9325]の推奨事項とベストカレントプラクティスに従って トランスポート層セキュリティー（TLS）[RFC8253] [RFC9916]を使用した、 認証および暗号化されたセッション上でのみ有効にすることが推奨されます（RECOMMENDED）。

The multipath extensions defined in this document allow a PCE to signal multiple paths per LSP, which increases the per-LSP state maintained by the PCC. A misbehaving or compromised PCE could exploit this to amplify state at the PCC by maximizing multipath fan out. The "Number of Multipaths" field in the MULTIPATH-CAP TLV provides an upper bound on the number of paths a PCC will accept per LSP, and operators SHOULD configure a non-zero value to limit exposure. The existing PCEP authentication and encryption recommendations (TLS per [RFC8253]) mitigate the risk of unauthorized PCE access.

この文書で定義するマルチパス拡張により、PCEはLSPごとに複数のパスをシグナリングできるため、 PCCが維持するLSPごとの状態が増加します。 誤動作している、または侵害されたPCEは、これを悪用してマルチパスのファンアウトを最大化し、 PCCにおける状態を増幅させる可能性があります。 MULTIPATH-CAP TLVの「Number of Multipaths」フィールドは、PCCがLSPごとに受け入れるパスの数の上限を提供します。 運用者は、影響を制限するために0以外の値を設定すべきです（SHOULD）。 既存のPCEPの認証と暗号化に関する推奨事項（[RFC8253]によるTLS）は、 PCEへの不正アクセスのリスクを軽減します。

8.6. Impact on Network Operations

8.6. ネットワーク運用への影響

The mechanisms in this document allow for more complex LSP structures with multiple paths. Network operators should be aware of the potential increase in PCEP message sizes and the additional state that must be maintained by PCEP speakers. The "Number of Multipaths" field in the MULTIPATH-CAP TLV can be used to control the scale of multipath computations and state.

この文書のメカニズムにより、複数のパスを持つ、より複雑なLSP構造が可能になります。 ネットワーク運用者は、PCEPメッセージのサイズが増加する可能性と、 PCEPスピーカーが維持しなければならない追加の状態に注意すべきです。 MULTIPATH-CAP TLVの「Number of Multipaths」フィールドを使用して、 マルチパスの計算と状態の規模を制御できます。

Paths within a single LSP may have significantly different properties, such as MTU, latency, and available bandwidth. When flow-based load balancing is used across such paths, individual flows are hashed to a single path, so per-path MTU or latency divergence is a per-flow concern rather than a per-packet one. However, operators should be aware that advertising weighted load balancing across paths with very different latencies can degrade application performance. Similarly, if paths have different MTUs, the effective MTU for flows on each path will differ; operators should ensure that PMTUD or consistent MTU configuration is in place. For bidirectional applications relying on Performance Measurement (PM) or BFD, note that forward and reverse paths may have asymmetric properties, and implementations should account for this.

単一のLSP内のパスは、MTU、遅延、利用可能な帯域幅などの特性が大きく異なる場合があります。 そのようなパスにわたってフローベースの負荷分散を使用する場合、個々のフローはハッシュによって単一のパスに割り当てられるため、 パスごとのMTUや遅延の違いはパケット単位ではなくフロー単位の問題になります。 しかし、運用者は、遅延が大きく異なるパスにわたって重み付き負荷分散を広告すると、 アプリケーションのパフォーマンスが低下する可能性があることに注意すべきです。 同様に、パスごとにMTUが異なる場合、各パス上のフローの実効MTUも異なります。 運用者は、PMTUDまたは一貫したMTU設定が整っていることを確認すべきです。 パフォーマンス測定（PM）やBFDに依存する双方向アプリケーションについては、 順方向パスと逆方向パスが非対称な特性を持つ可能性があることに注意してください。 実装はこれを考慮すべきです。

PCE implementations should minimize unnecessary churn in multipath state. With multiple paths per LSP, frequent recomputation or weight changes cause flow redistribution across segment lists, which may perturb congestion control state and trigger PMTUD rediscovery on a broader scale than with single-path LSPs.

PCEの実装は、マルチパスの状態の不要な変動（churn）を最小限に抑えるべきです。 LSPごとに複数のパスがある場合、頻繁な再計算や重みの変更はセグメントリスト間でのフローの再分配を引き起こし、 単一パスのLSPの場合よりも広い範囲で、輻輳制御の状態をかく乱したり、PMTUDの再探索を引き起こしたりする可能性があります。

For composite candidate paths, recursive policy resolution is therefore bounded, as Section 2.2 of [RFC9256] prohibits constituent SR Policies of a composite candidate path from themselves using composite candidate paths.

[RFC9256]のSection 2.2は、 複合候補パスの構成要素であるSRポリシー自身が複合候補パスを使用することを禁止しているため、 複合候補パスにおける再帰的なポリシー解決は有限に抑えられます。

Appendix A. Examples

Appendix A. 例

A.1. SR Policy Candidate Path with Multiple Segment Lists

A.1. 複数のセグメントリストを持つSRポリシー候補パス

Consider the following sample SR Policy.

次のSRポリシーの例を考えます。

SR policy POL1 <headend, color, endpoint>
    Candidate Path CP1 <protocol-origin = 20, originator-asn = 100,
                        originator-address = 192.0.2.1,
                        discriminator = 1>
        Preference 200
        Weight W1, SID-List1 <SID11...SID1i>
        Weight W2, SID-List2 <SID21...SID2j>
    Candidate Path CP2 <protocol-origin = 20, originator-asn = 100,
                        originator-address = 198.51.100.1,
                        discriminator = 2>
        Preference 100
        Weight W3, SID-List3 <SID31...SID3i>
        Weight W4, SID-List4 <SID41...SID4j>
SR policy POL1 <headend, color, endpoint>
    Candidate Path CP1 <protocol-origin = 20, originator-asn = 100,
                        originator-address = 192.0.2.1,
                        discriminator = 1>
        Preference 200
        Weight W1, SID-List1 <SID11...SID1i>
        Weight W2, SID-List2 <SID21...SID2j>
    Candidate Path CP2 <protocol-origin = 20, originator-asn = 100,
                        originator-address = 198.51.100.1,
                        discriminator = 2>
        Preference 100
        Weight W3, SID-List3 <SID31...SID3i>
        Weight W4, SID-List4 <SID41...SID4j>

As specified in [RFC9862], CP1 and CP2 are signaled as separate state-report elements and each has a unique PLSP-ID, assigned by the PCC. For this example, PLSP-ID 100 is assigned to CP1 and PLSP-ID 200 to CP2.

[RFC9862]で規定されているとおり、CP1とCP2は 別々のstate-report要素としてシグナリングされ、それぞれがPCCによって割り当てられた一意なPLSP-IDを持ちます。 この例では、CP1にPLSP-ID 100が、CP2にPLSP-ID 200が割り当てられています。

The state-report (as defined in [RFC8231]) for CP1 can be encoded as:

CP1の（[RFC8231]で定義されている）state-reportは、次のようにエンコードできます。

<state-report> =
    <LSP PLSP-ID=100>
    <ASSOCIATION>
    <PATH-ATTRIB Path ID=1 <WEIGHT-TLV Weight=W1>>
    <ERO SID-List1>
    <PATH-ATTRIB Path ID=2 <WEIGHT-TLV Weight=W2>>
    <ERO SID-List2>
<state-report> =
    <LSP PLSP-ID=100>
    <ASSOCIATION>
    <PATH-ATTRIB Path ID=1 <WEIGHT-TLV Weight=W1>>
    <ERO SID-List1>
    <PATH-ATTRIB Path ID=2 <WEIGHT-TLV Weight=W2>>
    <ERO SID-List2>

The state-report for CP2 can be encoded as:

CP2のstate-reportは、次のようにエンコードできます。

<state-report> =
    <LSP PLSP-ID=200>
    <ASSOCIATION>
    <PATH-ATTRIB Path ID=1 <WEIGHT-TLV Weight=W3>>
    <ERO SID-List3>
    <PATH-ATTRIB Path ID=2 <WEIGHT-TLV Weight=W4>>
    <ERO SID-List4>
<state-report> =
    <LSP PLSP-ID=200>
    <ASSOCIATION>
    <PATH-ATTRIB Path ID=1 <WEIGHT-TLV Weight=W3>>
    <ERO SID-List3>
    <PATH-ATTRIB Path ID=2 <WEIGHT-TLV Weight=W4>>
    <ERO SID-List4>

The above sample state-report elements only specify the minimum mandatory objects; of course, other objects like SRP, LSPA, METRIC, etc., are allowed to be inserted.

上記のstate-report要素の例は、必須の最小限のオブジェクトのみを指定しています。 もちろん、SRP、LSPA、METRICなどのほかのオブジェクトを挿入することも許可されています。

Note that the syntax

次の構文

<PATH-ATTRIB Path ID=1 <WEIGHT-TLV Weight=W1>>
<PATH-ATTRIB Path ID=1 <WEIGHT-TLV Weight=W1>>

means that this is a PATH-ATTRIB object with the Path ID field set to 1 and with a MULTIPATH-WEIGHT TLV carrying the weight of "W1".

は、Path IDフィールドが1に設定され、 重み「W1」を運ぶMULTIPATH-WEIGHT TLVを持つPATH-ATTRIBオブジェクトであることを意味することに注意してください。

A.2. Composite Candidate Path

A.2. 複合候補パス

Consider the following composite candidate path.

次の複合候補パスを考えます。

SR policy POL100 <headend = H1, color = 100, endpoint = E1>
    Candidate Path CP1 <protocol-origin = 20, originator-asn = 100,
                        originator-address = 192.0.2.1,
                        discriminator = 1>

        Weight W1, SR policy <color = 1>
        Weight W2, SR policy <color = 2>
SR policy POL100 <headend = H1, color = 100, endpoint = E1>

                        originator-address = 192.0.2.1,
                        discriminator = 1>
        Preference 200
        Weight W1, SR policy <color = 1>
        Weight W2, SR policy <color = 2>

これはPCEPでは次のようにシグナリングされます。

    <LSP PLSP-ID=100>

            <WEIGHT-TLV Weight=W1>
            <COLOR-TLV Color=1>>
        <ERO (empty)>
        <PATH-ATTRIB Path ID=2
            <WEIGHT-TLV Weight=W2>
            <COLOR-TLV Color=2>>
        <ERO (empty)>
    <LSP PLSP-ID=100>
        <ASSOCIATION>
        <PATH-ATTRIB Path ID=1
            <WEIGHT-TLV Weight=W1>
            <COLOR-TLV Color=1>>
        <ERO (empty)>
        <PATH-ATTRIB Path ID=2
            <WEIGHT-TLV Weight=W2>
            <COLOR-TLV Color=2>>
        <ERO (empty)>
