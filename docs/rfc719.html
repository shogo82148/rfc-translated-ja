RFC 719

Discussion on RCTE

RFC 719

RCTEに関する議論

Abstract

概要

The following is the significant portion of a dialog on RCTE that has followed the publication of RFC 718.

以下は、RFC 718の発行後に続いた、RCTEに関するやり取りの重要な部分です。

15-Jul-76 Nancy Mimno (BBN-NET)

1976年7月15日Nancy Mimno（BBN-NET）

Jon,
I've read RFC718 and have got some comments, in particular with respect to the "third problem" or clearing the input buffer part.

Jonへ
RFC718を読み、いくつかコメントがあります。特に「3番目の問題」、つまり入力バッファーのクリアの部分についてです。

1) I believe the stated implementation is backwards: in the normal case of the RCTE mode negotiation, the server sends "WILL RCTE" and the user sends ,"DO RCTE"; the reverse case is thus the server sending "DO RCTE" and the user "WILL RCTE" Also, it is probably wise to say explicitly that the server's sending "DO RCTE" requires the user process to respond "WILL (or WON'T) RCTE" and that this response is the synchronizing mark.

1) 記述されている実装は逆になっていると思います。RCTEモードのネゴシエーションの通常の場合は、サーバーが「WILL RCTE」を送り、ユーザーが「DO RCTE」を送ります。したがって、逆の場合はサーバーが「DO RCTE」を送り、ユーザーが「WILL RCTE」を送ることになります。また、サーバーが「DO RCTE」を送った場合、ユーザープロセスは「WILL（またはWON'T）RCTE」と応答する必要があり、この応答が同期マークになる、と明示しておくのが賢明でしょう。

2) The problem is a real one and I think the RCTE protocol would be better with a "clear input, reset counters" function. The question is Ill now to do it. In talking with Rav yesterday, I learned that he had this in mind as a general function, not restricted to RCTE; in fact, TENEX sends the "reverse RCTE" option for "clear your input buffer" whether or not the connection is in RCTE mode. In this case, the statement about "cannot be confused with the normal use of the RCTE option" will not always be true. I think we both agreed that the current solution should just be an interim one.

2) この問題は現実のものであり、RCTEプロトコルには「入力をクリアし、カウンターをリセットする」機能があったほうがよいと思います。問題はそれをどのように行うかです。昨日Rayと話したところ、彼はこれをRCTEに限らない一般的な機能として考えていたことがわかりました。実際、TENEXは、コネクションがRCTEモードであるかどうかにかかわらず、「入力バッファーをクリアせよ」の意味で「逆RCTE」オプションを送ります。この場合、「RCTEオプションの通常の使い方と混同されることはない」という記述は、常に正しいとは限りません。現在の解決策は暫定的なものにすぎないということで、私たちは2人とも合意したと思います。

3) I suggest a different way of performing this function, using the synch-datamark sequence. First, the RCTE option would have to explicitly require that this function reset the counters and cause a "clear your input buffer (of data)", all synchronized with the datamark of course. This is pretty much what it is now except for the reset counters; receiving Synch-data mark when in RCTE probably needed defining anyhow. Because RCTE won't work unless both sides agree, the "clear input and reset counters" meaning for synch-data mark would have to be a mandatory part of the RCTE option. Second, since the Synch-data mark is a "one-way" function, there needs to be a way for one side of the connection to tell the other side to "send me a Synch-data mark". The New Telnet protocol spec implied that Abort Output could be used for that purpose; if hot, then perhaps a new function could be defined. Again, the RCTE option should make some explicit statement requiring (or very strongLy recommending) this interpretation of AO. For non-RCTE mode, it's a nice idea but probably not required. Ray has tentatively agreed- thinks it could work on Tenex (server side). I would like your comments and Doug Dodds' (Tenex user RCTE). I don't know of any other existing RCTE implementations that would have to change. I also don't know what it takes to extend official protocols these days, but maybe it's easier to do that than define a new option (ie reverse RCTE).

3) この機能を実行する別の方法として、synch-datamarkシーケンスを使うことを提案します。まず、RCTEオプションは、この機能がカウンターをリセットし、「（データの）入力バッファーのクリア」を引き起こすことを明示的に要求する必要があります。もちろん、これらはすべてデータマークと同期して行います。これは、カウンターのリセットを除けば現在とほぼ同じです。RCTEモードでSynch-data markを受信した場合の動作は、いずれにせよ定義する必要があったでしょう。RCTEは双方が合意しなければ機能しないので、Synch-data markの「入力をクリアし、カウンターをリセットする」という意味は、RCTEオプションの必須の部分にする必要があります。次に、Synch-data markは「一方向」の機能なので、コネクションの一方が他方に「Synch-data markを送れ」と伝える方法が必要です。New Telnetプロトコルの仕様は、その目的にAbort Outputを使えることを示唆していました。そうでなければ、おそらく新しい機能を定義できるでしょう。繰り返しになりますが、RCTEオプションは、AOのこの解釈を要求する（または非常に強く推奨する）ことを明示的に記述すべきです。RCTEモードでない場合には、よい考えではありますが、おそらく必須ではないでしょう。Rayは暫定的に同意しており、Tenex（サーバー側）でうまく動くだろうと考えています。あなたと、Doug Dodds（TenexのユーザーRCTE）のコメントをいただきたいと思います。変更が必要になる既存のRCTE実装は、ほかには知りません。また、最近では公式のプロトコルを拡張するのに何が必要なのかも知りませんが、新しいオプション（つまり逆RCTE）を定義するよりも、そのほうが簡単かもしれません。

Regards,
Nancy

よろしくお願いします。
Nancy

15-Jul-76 Doug Dodds (BBN-RCC)

1976年7月15日Doug Dodds（BBN-RCC）

Nancy,

Nancyへ

Your suggestion for the RCTE-clear function being performed by the Au command (when RCTE is on) is a good one. I see no problem with it from the side of the Tenex User Telnet (NTELNET). At present NTELNET is ignoring AO (and some other commands) entirely; this is a good opportunity to implement it in general.

RCTEクリア機能を（RCTEが有効なときに）AOコマンドで実行するというあなたの提案はよいものです。TenexのUser Telnet（NTELNET）の側からは、何の問題もないと思います。現在、NTELNETはAO（およびほかのいくつかのコマンド）を完全に無視しています。これは、それを全般的に実装するよい機会です。

Doug

Doug

21-Jul-76 Jon Postel (SRI-ARC)

1976年7月21日Jon Postel（SRI-ARC）

I met with Ray Tomlinson for a few minutes to discuss the RCTE-clear function and other RCTE features. We agreed that Nancy's suggestion for using the AO command for the clear function made sense. We also determined that the RCTE document should say something about the state some other options should be in when using RCTE. For example we believe that GO-AHEAD must be suppressed while RCTE is in use, that when one quits RCTE the ECHO mode must be restored to what it was at the time of entering RCTE,, and that BINARY and RCTE do not make sense as a combination because every byte would have to be assumed to be a break character. We also determined that it is unworkable to use RCTE and no break characters since there is no way to get out of that state.

Ray Tomlinsonと数分間会い、RCTEクリア機能とRCTEのほかの機能について議論しました。クリア機能にAOコマンドを使うというNancyの提案は理にかなっているということで合意しました。また、RCTEを使用しているときにほかのいくつかのオプションがどのような状態であるべきかについて、RCTEの文書で何か述べるべきだということになりました。たとえば、RCTEの使用中はGO-AHEADを抑制しなければならないこと、RCTEを終了するときにはECHOモードをRCTEに入ったときの状態に戻さなければならないこと、そして、すべてのバイトをブレーク文字とみなさなければならなくなるため、BINARYとRCTEの組み合わせは意味をなさないこと、と私たちは考えています。また、RCTEをブレーク文字なしで使うことは、その状態から抜け出す方法がないため、実行不可能だということになりました。

22-Jul-76 Jon Postel (SRI-ARC)

1976年7月22日Jon Postel（SRI-ARC）

As a result of the above discussion I will prepare a revised RCTE specification document. A draft will be distributed to interested parties for comments and the final document will be published as an RFC.

上記の議論の結果として、改訂版のRCTE仕様の文書を作成します。草稿を関係者に配布してコメントを募り、最終的な文書をRFCとして発行します。
