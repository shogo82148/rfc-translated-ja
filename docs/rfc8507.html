2. Introduction

2. はじめに

SIP is a new version of IP. Its salient differences from IP version 4 [RFC791], subsequently referred to as "IPv4", are:

SIPはIPの新しいバージョンです。 IPバージョン4[RFC791]（以下「IPv4」と呼びます）との顕著な違いは次のとおりです。

  • expansion of addresses to 64 bits,
  • simplification of the IP header by eliminating some inessential fields, and
  • relaxation of length restrictions on optional data, such as source-routing information.
  • アドレスを64ビットに拡張すること
  • 必須ではないいくつかのフィールドを取り除くことによって、IPヘッダーを簡素化すること
  • ソースルーティング情報などのオプションデータの長さに関する制限を緩和すること

SIP retains the IP model of globally-unique addresses, hierarchically-structured for efficient routing. Increasing the address size from 32 to 64 bits allows more levels of hierarchy to be encoded in the addresses, enough to enable efficient routing in an internet with tens of thousands of addressable devices in every office, every residence, and every vehicle in the world. Keeping the addresses fixed-length and relatively compact facilitates high-performance router and host implementation, and keeps the bandwidth overhead of the SIP headers almost as low as IPv4.

SIPは、効率的なルーティングのために階層的に構造化された、グローバルに一意なアドレスというIPのモデルを維持します。 アドレスのサイズを32ビットから64ビットに増やすことで、より多くの階層のレベルをアドレスにエンコードできるようになります。これは、世界中のすべてのオフィス、すべての住居、すべての車両に、アドレスを持つ機器が何万台もあるようなインターネットにおいても、効率的なルーティングを可能にするのに十分なものです。 アドレスを固定長かつ比較的コンパクトに保つことで、ルーターやホストを高性能に実装しやすくなり、SIPヘッダーによる帯域幅のオーバーヘッドをIPv4とほぼ同じくらい低く保てます。

The elimination of inessential fields also contributes to high-performance implementation, and to the likelihood of correct implementation. A change in the way that optional data, such as source-routing information, is encoded allows for more efficient forwarding and less stringent limits on the length of such data.

必須ではないフィールドを取り除くことは、高性能な実装にも、正しい実装の可能性を高めることにも貢献します。 ソースルーティング情報などのオプションデータのエンコード方法を変更することで、より効率的な転送が可能になり、そのようなデータの長さに関する制限も緩やかになります。

Despite these changes, SIP remains very similar to IPv4. This similarity makes it easy to understand SIP (for those who already understand IPv4), makes it possible to reuse much of the code and data structures from IPv4 in an implementation of SIP (including almost all of ICMP and IGMP), and makes it straightforward to translate between SIP packets and IPv4 packets for transition purposes [IPAE].

これらの変更にもかかわらず、SIPはIPv4と非常によく似ています。 この類似性により、（すでにIPv4を理解している人にとっては）SIPを理解しやすくなり、SIPの実装でIPv4のコードやデータ構造の多く（ICMPとIGMPのほぼすべてを含む）を再利用できるようになり、移行を目的としてSIPパケットとIPv4パケットの間で変換を行うことも簡単になります[IPAE]。

The subsequent sections of this document specify SIP and its associated protocols without much explanation of why the design choices were made the way they were. Appendix A presents the rationale for those aspects of SIP that differ from IPv4.

この文書の以降のセクションでは、設計上の選択がなぜそのようになされたのかをあまり説明せずに、SIPとその関連プロトコルを規定します。 付録Aでは、SIPのうちIPv4と異なる側面について、その根拠を示します。

3. Terminology

3. 用語

system
a device that implements SIP.
router
a system that forwards SIP packets.
host
any system that is not a router.
link
a communication facility or medium over which systems can communicate at the link layer, i.e., the layer immediately below SIP.
interface
a system's attachment point to a link.
address
a SIP-layer identifier for an interface or a group of interfaces.
subnet
in the SIP unicast addressing hierarchy, a lowest-level (finest-grain) cluster of addresses, sharing a common address prefix (i.e., high-order address bits). Typically, all interfaces attached to the same link have addresses in the same subnet; however, in some cases, a single link may support more than one subnet, or a single subnet may span more than one link.
link MTU
the maximum transmission unit, i.e., maximum packet size in octets, that can be conveyed in one piece over a link (where a packet is a SIP header plus payload).
path MTU
the minimum link MTU of all the links in a path between a source system and a destination system.
packetization layer
any protocol layer above SIP that is responsible for packetizing data to fit within outgoing SIP packets. Typically, transport-layer protocols, such as TCP, are packetization protocols, but there may also be higher-layer packetization protocols, such as protocols implemented on top of UDP.
システム（system）
SIPを実装する機器。
ルーター（router）
SIPパケットを転送するシステム。
ホスト（host）
ルーターではない任意のシステム。
リンク（link）
システムがリンク層、すなわちSIPのすぐ下の層で通信するために使う通信設備または媒体。
インターフェイス（interface）
システムがリンクに接続する点。
アドレス（address）
インターフェイスまたはインターフェイスのグループを表す、SIP層の識別子。
サブネット（subnet）
SIPのユニキャストアドレス階層において、共通のアドレスプレフィックス（すなわち、アドレスの上位ビット）を共有する、最下位レベル（最も細かい粒度）のアドレスのまとまり。 通常、同じリンクに接続されたすべてのインターフェイスは、同じサブネットのアドレスを持ちます。 ただし、1つのリンクが複数のサブネットをサポートしたり、1つのサブネットが複数のリンクにまたがったりする場合もあります。

5. Addresses

5. アドレス

5.1. Text Representation of Addresses

5.1. アドレスのテキスト表現

SIP addresses are 64 bits (8 octets) long. The text representation of a SIP addresses is 16 hexadecimal digits, with a colon between the 4th and 5th digits, and optional colons between any subsequent pair of digits. Leading zeros must not be dropped. Examples:

SIPアドレスの長さは64ビット（8オクテット）です。 SIPアドレスのテキスト表現は16桁の16進数で、4桁目と5桁目の間にコロンを置き、それ以降の任意の2桁の間にもコロンを置くことができます。 先頭のゼロを省略してはいけません。 例:

       0123:4567:89AB:CDEF

       0123:456789ABCDEF

       0123:456789AB:CDE:F

       0123:4567:89AB:CDEF

       0123:456789ABCDEF

       0123:456789AB:CDE:F

Programs that read the text representation of SIP addresses must be insensitive to the presence or absence of optional colons. Programs that write the text representation of a SIP address should use the first format above (i.e., colons after the 4th, 8th, and 12th digits), in the absence of any knowledge of the structure or preferred format of the address, such as knowledge of the format in which it was originally read.

SIPアドレスのテキスト表現を読み取るプログラムは、オプションのコロンの有無に左右されないようにしなければなりません。 SIPアドレスのテキスト表現を書き出すプログラムは、アドレスの構造や望ましい形式についての知識（たとえば、そのアドレスが最初に読み取られたときの形式についての知識）がない場合には、上記の最初の形式（すなわち、4桁目、8桁目、12桁目の後にコロンを置く形式）を使うべきです。

The presence of at least one colon in the text representation allows SIP addresses to be easily distinguished from both domain names and the text representation of IPv4 addresses.

テキスト表現に少なくとも1つのコロンがあることで、SIPアドレスをドメイン名ともIPv4アドレスのテキスト表現とも容易に区別できます。

5.2. Unicast Addresses

5.2. ユニキャストアドレス

A SIP unicast address is a globally-unique identifier for a single interface, i.e., no two interfaces in a SIP internet may have the same unicast address. A single interface may, however, have more than one unicast address.

SIPユニキャストアドレスは、単一のインターフェイスを表すグローバルに一意な識別子です。すなわち、SIPインターネットにおいて、2つのインターフェイスが同じユニキャストアドレスを持つことはできません。 ただし、1つのインターフェイスが複数のユニキャストアドレスを持つことはできます。

A system considers its own unicast address(es) to have the following structure, where different addresses may have different values for n:

システムは、自身のユニキャストアドレスが次の構造を持つものとみなします。ここで、アドレスごとにnの値が異なってもかまいません。

 |                         n bits                     |  64-n bits |
 +----------------------------------------------------+------------+
 |                     subnet prefix                  |interface ID|
 +----------------------------------------------------+------------+

 |                         n bits                     |  64-n bits |
 +----------------------------------------------------+------------+
 |                     subnet prefix                  |interface ID|
 +----------------------------------------------------+------------+

To know the length of the subnet prefix, the system is required to associate with each of its addresses a 'subnet mask' of the following form:

サブネットプレフィックスの長さを知るために、システムは自身の各アドレスに、次の形式の「サブネットマスク」を関連付けることが求められます。

 |                         n bits                     |  64-n bits |
 +----------------------------------------------------+------------+
 |1111111111111111111111111111111111111111111111111111|000000000000|
 +----------------------------------------------------+------------+

 |                         n bits                     |  64-n bits |
 +----------------------------------------------------+------------+
 |1111111111111111111111111111111111111111111111111111|000000000000|
 +----------------------------------------------------+------------+

A system may have a subnet mask of all-ones, which means that the system belongs to a subnet containing exactly one system -- itself.

システムはすべてのビットが1のサブネットマスクを持つこともできます。これは、そのシステムが、ちょうど1つのシステム、つまりそのシステム自身だけを含むサブネットに属することを意味します。

A system acquires its subnet mask(s) at the same time, and by the same mechanism, as it acquires its address(es), for example, by manual configuration or by a dynamic configuration protocol such as BOOTP [RFC951].

システムは、自身のアドレスを取得するのと同じときに同じ仕組みによって、自身のサブネットマスクを取得します。たとえば、手動設定や、BOOTP[RFC951]などの動的設定プロトコルによって取得します。

Hosts are ignorant of any further structure in a unicast address.

ホストは、ユニキャストアドレスにそれ以上の構造があることを知りません。

ルーターは、手動設定やルーティングプロトコルの動作によって、階層的なアドレス計画におけるより上位のレベルのまとまりを識別する追加のマスクを取得することがあります。 たとえば、単一のサイト内のルーターは通常、次のような「サイトマスク」を持つでしょう。

 |                  m bits                 |       64-m bits       |
 +-----------------------------------------+-----------------------+
 |11111111111111111111111111111111111111111|00000000000000000000000|
 +-----------------------------------------+-----------------------+

 |                  m bits                 |       64-m bits       |
 +-----------------------------------------+-----------------------+
 |11111111111111111111111111111111111111111|00000000000000000000000|
 +-----------------------------------------+-----------------------+

by which they could deduce the following structure in the site's addresses:

ルーターはこのマスクによって、サイトのアドレスが次の構造を持つことを推測できます。

 |                  m bits                 |  p bits  | 64-m-p bits|
 +-----------------------------------------+----------+------------+
 |                site prefix              |subnet  ID|interface ID|
 +-----------------------------------------+----------+------------+

 |                  m bits                 |  p bits  | 64-m-p bits|
 +-----------------------------------------+----------+------------+
 |                site prefix              |subnet  ID|interface ID|
 +-----------------------------------------+----------+------------+

All knowledge by SIP systems of the structure of unicast addresses is based on possession of such masks -- there is no "wired-in" knowledge of unicast address formats.

6. Packet Size Issues

6. パケットサイズの問題

SIP requires that every link in the internet have an MTU of 576 octets or greater. On any link that cannot convey a 576-octet packet in one piece, link-specific fragmentation and reassembly must be provided at a layer below SIP.

SIPでは、インターネット内のすべてのリンクが576オクテット以上のMTUを持つことが求められます。 576オクテットのパケットを1つのまとまりとして運ぶことができないリンクでは、リンク固有の断片化と再構築を、SIPより下の層で提供しなければなりません。

(Note: this minimum link MTU is NOT the same as the one in IPv4. In IPv4, the minimum link MTU is 68 octets [ [RFC791], page 25 ]; 576 octets is the minimum reassembly buffer size required in an IPv4 system, which has nothing to do with link MTUs.)

（注: この最小リンクMTUは、IPv4のものとは同じではありません。 IPv4では、最小リンクMTUは68オクテットです[ [RFC791]の25ページ ]。 576オクテットはIPv4システムで要求される最小の再構築バッファーサイズで、リンクMTUとは何の関係もありません。）

From each link to which a system is directly attached, the system must be able to accept packets as large as that link's MTU. Links that have a configurable MTU, such as PPP links [RFC1661], should be configured with an MTU of 600 octets or greater.

システムは、自身が直接接続されている各リンクから、そのリンクのMTUと同じ大きさまでのパケットを受け入れられなければなりません。 PPPリンク[RFC1661]のようにMTUを設定できるリンクは、600オクテット以上のMTUで設定すべきです。

SIP systems are expected to implement Path MTU Discovery [RFC1191], in order to discover and take advantage of paths with MTU greater than 576 octets. However, a minimal SIP implementation (e.g., in a boot ROM) may simply restrict itself to sending packets no larger than 576 octets, and omit implementation of Path MTU Discovery.

SIPシステムは、576オクテットより大きいMTUを持つ経路を発見して活用するために、パスMTU探索[RFC1191]を実装することが期待されます。 ただし、最小限のSIP実装（たとえば、ブートROM内のもの）では、単に576オクテット以下のパケットだけを送信するように自らを制限し、パスMTU探索の実装を省略してもかまいません。

Path MTU Discovery requires support both in the SIP layer and in the packetization layers. A system that supports Path MTU Discovery at the SIP layer may serve packetization layers that are unable to adapt to changes of the path MTU. Such packetization layers must limit themselves to sending packets no longer than 576 octets, even when sending to destinations that belong to the same subnet.

パスMTU探索には、SIP層とパケット化層の両方でのサポートが必要です。 SIP層でパスMTU探索をサポートするシステムが、パスMTUの変化に適応できないパケット化層にサービスを提供する場合があります。 そのようなパケット化層は、同じサブネットに属する宛先に送信する場合であっても、576オクテット以下のパケットだけを送信するように自らを制限しなければなりません。

(Note: Unlike IPv4, it is unnecessary in SIP to set a "Don't Fragment" flag in the packet header in order to perform Path MTU Discovery; that is an implicit attribute of every SIP packet. Also, those parts of the RFC-1191 procedures that involve use of a table of MTU "plateaus" do not apply to SIP, because the SIP version of the "Datagram Too Big" message always identifies the exact MTU to be used.)

（注: IPv4とは異なり、SIPではパスMTU探索を行うためにパケットヘッダーに「Don't Fragment」フラグを設定する必要はありません。それはすべてのSIPパケットが暗黙的に持つ属性です。 また、RFC 1191の手順のうちMTUの「プラトー」の表を使う部分は、SIPには適用されません。SIP版の「Datagram Too Big」メッセージは、使うべき正確なMTUを常に示すからです。）

The Fragmentation header is NOT intended to support general, SIP-layer fragmentation. In particular, SIP routers shall not fragment a SIP packet that is too big for the MTU of its next hop, except in the special cases described below; in the normal case, such a packet results in an ICMP Packet Too Big message being sent back to its source, for use by the source system's Path MTU Discovery algorithm.

断片化ヘッダーは、SIP層での汎用的な断片化をサポートすることを意図したものでは「ありません」。 特に、SIPルーターは、以下で説明する特別な場合を除いて、ネクストホップのMTUに対して大きすぎるSIPパケットを断片化しません。通常の場合、そのようなパケットに対しては、送信元システムのパスMTU探索アルゴリズムで使うために、ICMP Packet Too Bigメッセージがその送信元に送り返されます。

The special cases for which the Fragmentation header is intended are the following:

断片化ヘッダーが意図している特別な場合とは、次のものです。

  • A SIP packet that is "tunneled", either by encapsulation within another SIP packet or by insertion of a Source Routing header en-route, may, after the addition of the extra header fields, exceed the MTU of the tunnel's path; if the original packet is 576 octets or less in length, the tunnel entry system cannot respond to the source with a Packet Too Big message, and therefore must insert a Fragmentation header and fragment the packet to fit within the tunnel's MTU.
  • An IPv4 fragment that is translated into a SIP packet, or an unfragmented IPv4 packet that is translated into too long a SIP packet to fit in the remaining path MTU, must include the SIP Fragmentation header, so that it may be properly reassembled at the destination SIP system.
  • 別のSIPパケット内へのカプセル化、または途中でのソースルーティングヘッダーの挿入によって「トンネリング」されたSIPパケットは、追加のヘッダーフィールドが付加された後で、トンネルの経路のMTUを超えることがあります。元のパケットの長さが576オクテット以下である場合、トンネルの入口のシステムは送信元にPacket Too Bigメッセージで応答できないため、断片化ヘッダーを挿入して、トンネルのMTUに収まるようにパケットを断片化しなければなりません。
  • SIPパケットに変換されたIPv4フラグメント、または残りのパスMTUに収まらないほど長いSIPパケットに変換された断片化されていないIPv4パケットは、宛先のSIPシステムで適切に再構築できるように、SIPの断片化ヘッダーを含まなければなりません。

Every SIP system must support SIP fragmentation and reassembly, since any system may be configured to serve as a tunnel entry or exit point, and any SIP system may be destination of IPv4 fragments. All SIP systems must be capable of reassembling, from fragments, a SIP packet of up to 1024 octets in length, including the SIP header; a system may be capable of assembling packets longer than 1024 octets.

どのシステムもトンネルの入口または出口として機能するように設定される可能性があり、どのSIPシステムもIPv4フラグメントの宛先になる可能性があるため、すべてのSIPシステムはSIPの断片化と再構築をサポートしなければなりません。 すべてのSIPシステムは、SIPヘッダーを含めて最大1024オクテットの長さのSIPパケットを、フラグメントから再構築できなければなりません。システムは1024オクテットより長いパケットを再構築できてもかまいません。

Routers do not examine or process Fragmentation headers of packets that they forward; only at the destination system is the Fragmentation header acted upon (i.e., reassembly performed), as a result of dispatching on the Payload Type of the preceding header.

ルーターは、自身が転送するパケットの断片化ヘッダーを検査も処理もしません。断片化ヘッダーに基づく処理（すなわち再構築）が行われるのは宛先のシステムだけで、それは直前のヘッダーのPayload Typeに基づいてディスパッチした結果として行われます。

Fragmentation and reassembly employ the same algorithm as IPv4, with the following exceptions:

断片化と再構築には、次の例外を除いて、IPv4と同じアルゴリズムを使います。

  • All headers up to and including the Fragmentation header are repeated in each fragment; no headers or data following the Fragmentation header are repeated in each fragment.
  • the Identification field is increased to 32 bits, to decrease the risk of wraparound of that field within the maximum packet lifetime over very high-throughput paths.
  • 断片化ヘッダーまでの（断片化ヘッダーを含む）すべてのヘッダーが、各フラグメントで繰り返されます。断片化ヘッダーに続くヘッダーやデータは、各フラグメントで繰り返されません。
  • 非常に高スループットの経路において、最大パケット寿命の間にIdentificationフィールドがラップアラウンドするリスクを減らすために、このフィールドは32ビットに拡大されています。

The similarity of the algorithm and the field layout to that of IPv4 enables existing IPv4 fragmentation and reassembly code and data structures to be re-used with little modification.

アルゴリズムとフィールドの配置がIPv4と似ているため、既存のIPv4の断片化と再構築のコードやデータ構造を、ほとんど修正せずに再利用できます。

9. 他のプロトコルへの変更

IPv4をSIPにアップグレードするには、関連する制御プロトコルであるICMPとIGMP、上位のトランスポート層、そしておそらく下位のリンク層にも変更が必要になります。 このセクションでは、それらの変更を示します。

9.3. Changes to Transport Protocols

9.3. トランスポートプロトコルへの変更

The service interface to SIP has some differences from IPv4's service interface. Existing transport protocols that use IPv4 must be changed to operate over SIP's service interface. The differences from IPv4 are:

SIPに対するサービスインターフェイスには、IPv4のサービスインターフェイスとのいくつかの違いがあります。 IPv4を使う既存のトランスポートプロトコルは、SIPのサービスインターフェイス上で動作するように変更しなければなりません。 IPv4との違いは次のとおりです。

  • Any addresses passed across the interface are 64 bits long, rather than 32 bits.
  • The following IPv4 variables are not passed across the interface: Precedence, Type-of-Service, Identifier, Don't Fragment Flag
  • SIP options have a different format than IPv4 options. (For SIP, "options" are all headers between, and not including, the SIP header and the transport header. The only IPv4 option currently specified for SIP is Loose Source Routing.
  • ICMP error messages for SIP that are passed up to the transport layer carry the first 256 octets of the invoking SIP packet.
  • インターフェイスを越えて渡されるアドレスは、32ビットではなく64ビットの長さです。
  • 次のIPv4の変数は、インターフェイスを越えて渡されません: Precedence、Type-of-Service、Identifier、Don't Fragment Flag
  • SIPのオプションは、IPv4のオプションとは異なる形式を持ちます。（SIPでは、「オプション」とは、SIPヘッダーとトランスポートヘッダーの間にある（それらを含まない）すべてのヘッダーのことです。 SIP向けに現在規定されている唯一のIPv4オプションは、ルーズソースルーティングです。
  • トランスポート層に渡されるSIPのICMPエラーメッセージは、それを引き起こしたSIPパケットの最初の256オクテットを運びます。

Transport protocols that use IPv4 addresses for their own purposes, such as identifying connection state or inclusion in a pseudo-header checksum, must be changed to use 64-bit SIP addresses for those purposes instead.

接続状態の識別や疑似ヘッダーチェックサムへの算入など、IPv4アドレスを独自の目的で使うトランスポートプロトコルは、代わりに64ビットのSIPアドレスをそれらの目的で使うように変更しなければなりません。

For SIP, the pseudo-header checksums of TCP, UDP, ICMP, and IGMP include the SIP Source Address, Destination Address, Payload Length, and Payload Type, with the following caveats:

SIPでは、TCP、UDP、ICMP、IGMPの疑似ヘッダーチェックサムは、次の注意事項のもとで、SIPのSource Address、Destination Address、Payload Length、Payload Typeを含みます。

  • If the packet contains a Source Routing header, the destination address used in the pseudo-header checksum is that of the final destination.
  • The Payload Length used in the pseudo-header checksum is the length of the transport-layer packet, including the transport header.
  • The Payload Type used in the pseudo-header checksum is the Payload Type from the header immediately preceding the transport header.
  • When added to the pseudo-header checksum, the Payload Type is treated as the left octet of a 16-bit word, with zeros in the the right octet, when viewed in IP standard octet order.
  • If either of the two addresses used in the pseudo-header checksum has its high-order bit set to 1, only the low-order 32-bits of that address shall be used in the sum. The high-order bit is used to indicate that the addressed system is an IPv4 system, and that the low-order 32-bits of the address contain that system's IPv4 address [IPAE].
  • パケットがソースルーティングヘッダーを含む場合、疑似ヘッダーチェックサムで使う宛先アドレスは、最終的な宛先のものです。
  • 疑似ヘッダーチェックサムで使うPayload Lengthは、トランスポートヘッダーを含むトランスポート層のパケットの長さです。
  • 疑似ヘッダーチェックサムで使うPayload Typeは、トランスポートヘッダーの直前のヘッダーにあるPayload Typeです。
  • 疑似ヘッダーチェックサムに加算する際、Payload Typeは、IP標準のオクテット順で見て、16ビットワードの左側のオクテットとして扱われ、右側のオクテットはゼロになります。
  • 疑似ヘッダーチェックサムで使う2つのアドレスのいずれかの最上位ビットが1に設定されている場合、そのアドレスの下位32ビットだけを合計に使います。 最上位ビットは、アドレスで指定されたシステムがIPv4システムであり、アドレスの下位32ビットにそのシステムのIPv4アドレスが含まれていることを示すために使われます[IPAE]。

The semantics of SIP service differ from IPv4 service in three ways that may affect some transport protocols:

SIPのサービスの意味は、IPv4のサービスとは3つの点で異なり、それが一部のトランスポートプロトコルに影響を与える可能性があります。

  1. SIP does not enforce maximum packet lifetime. Any transport protocol that relies on IPv4 to limit packet lifetime must take this change into account, for example, by providing its own mechanisms for detecting and discarding obsolete packets.
  2. SIP does not checksum its own header fields. Any transport protocol that relies on IPv4 to assure the integrity of the source and destinations addresses, packet length, and transport protocol identifier must take this change into account. In particular, when used with SIP, the UDP checksum is mandatory, and ICMP and IGMP are changed to use a pseudo-header checksum.
  3. SIP does not (except in special cases) fragment packets that exceed the MTU of their delivery paths. Therefore, a transport protocol must not send packets longer than 576 octets unless it implements Path MTU Discovery [RFC1191] and is capable of adapting its transmitted packet size in response to changes of the path MTU.
  1. SIPは最大パケット寿命を強制しません。 パケットの寿命を制限するためにIPv4に依存しているトランスポートプロトコルは、たとえば古くなったパケットを検出して破棄するための独自の仕組みを提供することによって、この変更を考慮しなければなりません。
  2. SIPは自身のヘッダーフィールドのチェックサムを計算しません。 送信元アドレスと宛先アドレス、パケット長、トランスポートプロトコル識別子の完全性を保証するためにIPv4に依存しているトランスポートプロトコルは、この変更を考慮しなければなりません。 特に、SIPで使う場合、UDPのチェックサムは必須で、ICMPとIGMPは疑似ヘッダーチェックサムを使うように変更されます。
  3. SIPは、（特別な場合を除いて）配送経路のMTUを超えるパケットを断片化しません。 したがって、トランスポートプロトコルは、パスMTU探索[RFC1191]を実装していて、パスMTUの変化に応じて送信するパケットのサイズを適応させることができる場合を除いて、576オクテットより長いパケットを送信してはいけません。

9.4. Changes to Link-Layer Protocols

9.4. リンク層プロトコルへの変更

Link-layer media that have an MTU less than 576 must be enhanced with a link-specific fragmentation and reassembly mechanism, to support SIP.

MTUが576未満のリンク層媒体は、SIPをサポートするために、リンク固有の断片化と再構築の仕組みで拡張しなければなりません。

For links on which ARP is used by IPv4, the identical ARP protocol is used for SIP. The low-order 32-bits of SIP addresses are used wherever IPv4 addresses would appear; since ARP is used only among systems on the same subnet, the high-order 32-bits of the SIP addresses may be inferred from the subnet prefix (assuming the subnet prefix is at least 32 bits long). [This is subject to change -- see Appendix B.]

IPv4でARPが使われるリンクでは、SIPにもまったく同じARPプロトコルを使います。 IPv4アドレスが現れる場所ではどこでも、SIPアドレスの下位32ビットを使います。ARPは同じサブネット上のシステム間でのみ使われるため、SIPアドレスの上位32ビットはサブネットプレフィックスから推測できます（サブネットプレフィックスが少なくとも32ビットの長さであると仮定します）。 [これは変更される可能性があります。付録Bを参照してください。]

Appendix B. Future Directions

Appendix B. 今後の方向性

SIP as specified above is a fully functional replacement for IPv4, with a number of improvements, particularly in the areas of scalability of routing and addressing, and performance. Some additional improvements are still under consideration:

上記で規定したSIPは、特にルーティングとアドレス指定のスケーラビリティーと性能の分野で多くの改善を備えた、IPv4の完全に機能する代替です。 いくつかの追加の改善がまだ検討中です。

  • ARP may be modified to carry full 64-bit addresses, and to use link-layer multicast addresses, rather than broadcast addresses.
  • The 28-bit Reserved field in the SIP header may be defined as a "Flow ID", or partitioned into a Type of Service field and a Flow ID field, for classifying packets deserving of special handling, e.g., non-default quality of service or real-time service. On the other hand, the transport-layer port fields may be adequate for performing any such classification. (One possibility would be simply to remove the port fields from TCP & UDP and append them to the SIP header, as in XNS.)
  • A new ICMP "destination has moved" message may defined, for re-routing to mobile hosts or subnets, and to domains that have changed their address prefixes.
  • An explicit Trace Route message or option may be defined; the current IPv4 traceroute scheme will work fine with SIP, but it does not work for multicast, for which it has become very apparent that management and debugging tools are needed.
  • A new Host-to-Router protocol may be specified, encompassing the requirements of router discovery, black-hole detection, auto- configuration of subnet prefixes, "beaconing" for mobile hosts, and, possibly, address resolution. The OSI End System To Intermediate System Protocol may serve as a good model for such a protocol.
  • The requirement that SIP addresses be strictly bound to interfaces may be relaxed, so that, for example, a system might have fewer addresses than interfaces. There is some experience with this approach in the current Internet, with the use of "unnumbered links" in routing protocols such as OSPF.
  • Authentication and integrity-assurance mechanisms for all clients of SIP, including ICMP and IGMP, may be specified, possibly based on the Secure Data Network System (SNDS) SP-3 or SP-4 protocol.
  • ARPは、64ビットのアドレス全体を運び、ブロードキャストアドレスではなくリンク層のマルチキャストアドレスを使うように変更される可能性があります。
  • SIPヘッダーの28ビットのReservedフィールドは、デフォルト以外のサービス品質やリアルタイムサービスなど、特別な扱いに値するパケットを分類するための「Flow ID」として定義されるか、Type of ServiceフィールドとFlow IDフィールドに分割される可能性があります。 一方で、そのような分類を行うには、トランスポート層のポートフィールドで十分かもしれません。 （1つの可能性は、XNSのように、単純にTCPとUDPからポートフィールドを取り除いてSIPヘッダーに付加することです。）
  • 移動するホストやサブネット、およびアドレスプレフィックスを変更したドメインへの再ルーティングのために、新しいICMPの「destination has moved」メッセージが定義される可能性があります。
  • 明示的なTrace Routeメッセージまたはオプションが定義される可能性があります。現在のIPv4のtracerouteの方式はSIPでも問題なく機能しますが、マルチキャストでは機能しません。マルチキャストについては、管理ツールとデバッグツールが必要であることが非常に明らかになっています。
  • ルーター探索、ブラックホール検出、サブネットプレフィックスの自動設定、移動ホストのための「ビーコン」、そしておそらくアドレス解決の要件を包含する、新しいホストとルーター間のプロトコルが規定される可能性があります。 OSIのEnd System To Intermediate System Protocolは、そのようなプロトコルのよいモデルになるかもしれません。
  • SIPアドレスをインターフェイスに厳密に結び付けるという要件が緩和され、たとえば、システムがインターフェイスよりも少ない数のアドレスを持てるようになる可能性があります。 現在のインターネットでは、OSPFなどのルーティングプロトコルにおける「番号なしリンク」の使用によって、このアプローチについての経験がいくらかあります。
  • ICMPとIGMPを含むSIPのすべてのクライアントのための認証と完全性保証の仕組みが、おそらくSecure Data Network System（SNDS）のSP-3またはSP-4プロトコルに基づいて規定される可能性があります。
