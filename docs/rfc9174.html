Delay-Tolerant Networking TCP Convergence-Layer Protocol Version 4

RFC 9174

遅延耐性ネットワーキングTCPコンバージェンス層プロトコルバージョン4

Abstract

概要

This document describes a TCP convergence layer (TCPCL) for Delay-Tolerant Networking (DTN). This version of the TCPCL protocol resolves implementation issues in the earlier TCPCL version 3 as defined in RFC 7242 and provides updates to the Bundle Protocol (BP) contents, encodings, and convergence-layer requirements in BP version 7 (BPv7). Specifically, TCPCLv4 uses BPv7 bundles encoded by the Concise Binary Object Representation (CBOR) as its service data unit being transported and provides a reliable transport of such bundles. This TCPCL version also includes security and extensibility mechanisms.

この文書は、遅延耐性ネットワーキング（DTN）のためのTCPコンバージェンス層（TCPCL）について説明します。このバージョンのTCPCLプロトコルは、RFC 7242で定義された以前のTCPCLバージョン3における実装上の問題を解決し、バンドルプロトコル（BP）バージョン7（BPv7）におけるBPの内容、エンコーディング、コンバージェンス層の要件の更新に対応します。具体的には、TCPCLv4は、Concise Binary Object Representation（CBOR）でエンコードされたBPv7バンドルを、転送されるサービスデータ単位として使用し、そのようなバンドルの信頼性のある転送を提供します。 このTCPCLバージョンには、セキュリティーと拡張性のメカニズムも含まれています。

1. Introduction

1. はじめに

This document describes the TCP convergence-layer protocol for Delay-Tolerant Networking (DTN). DTN is an end-to-end architecture providing communications in and/or through highly stressed environments, including those with intermittent connectivity, long and/or variable delays, and high bit error rates. More detailed descriptions of the rationale and capabilities of these networks can be found in "Delay-Tolerant Networking Architecture" [RFC4838].

この文書は、遅延耐性ネットワーキング（DTN）のためのTCPコンバージェンス層プロトコルについて説明します。 DTNは、断続的な接続性、長い遅延や変動する遅延、高いビット誤り率などを伴う、非常に厳しい環境の中で、またはそのような環境を通じて通信を提供するエンドツーエンドのアーキテクチャーです。 これらのネットワークの論拠と能力についてのより詳細な説明は、「Delay-Tolerant Networking Architecture」[RFC4838]にあります。

An important goal of the DTN architecture is to accommodate a wide range of networking technologies and environments. The protocol used for DTN communications is the Bundle Protocol version 7 (BPv7) [RFC9171], an application-layer protocol that is used to construct a store-and-forward overlay network. BPv7 requires the services of a "convergence-layer adapter" (CLA) to send and receive bundles using the service of some "native" link, network, or Internet protocol. This document describes one such convergence-layer adapter that uses the well-known Transmission Control Protocol (TCP). This convergence layer is referred to as TCP Convergence Layer version 4 (TCPCLv4). For the remainder of this document,

DTNアーキテクチャーの重要な目標は、幅広いネットワーキング技術と環境に対応することです。 DTN通信に使用されるプロトコルはバンドルプロトコルバージョン7（BPv7）[RFC9171]であり、これはストアアンドフォワード型のオーバーレイネットワークを構築するために使用されるアプリケーション層プロトコルです。 BPv7は、何らかの「ネイティブ」なリンク、ネットワーク、またはインターネットプロトコルのサービスを使用してバンドルを送受信するために、「コンバージェンス層アダプター」（CLA）のサービスを必要とします。 この文書では、よく知られた伝送制御プロトコル（TCP）を使用する、そのようなコンバージェンス層アダプターの1つについて説明します。 このコンバージェンス層は、TCPコンバージェンス層バージョン4（TCPCLv4）と呼ばれます。 この文書の残りの部分では、

  • the abbreviation "BP" without the version suffix refers to BPv7.
  • the abbreviation "TCPCL" without the version suffix refers to TCPCLv4.
  • バージョンの接尾辞のない略語「BP」はBPv7を指します。
  • バージョンの接尾辞のない略語「TCPCL」はTCPCLv4を指します。

The locations of the TCPCL and the Bundle Protocol in the Internet model protocol stack (described in [RFC1122]) are shown in Figure 1. In particular, when BP is using TCP as its bearer with the TCPCL as its convergence layer, both BP and the TCPCL reside at the application layer of the Internet model.

（[RFC1122]で説明されている）インターネットモデルのプロトコルスタックにおけるTCPCLとバンドルプロトコルの位置をFigure 1に示します。 特に、BPがTCPCLをコンバージェンス層としてTCPを伝送手段に使用する場合、BPとTCPCLはどちらもインターネットモデルのアプリケーション層に位置します。

1.1. Scope

1.1. 範囲

This document describes the format of the protocol data units passed between entities participating in TCPCL communications. This document does not address:

この文書では、TCPCL通信に参加するエンティティー間で受け渡されるプロトコルデータ単位の形式について説明します。 この文書は次の事項を扱いません。

  • The format of protocol data units of the Bundle Protocol, as those are defined elsewhere in [RFC9171]. This includes the concept of bundle fragmentation or bundle encapsulation. The TCPCL transfers bundles as opaque data blocks.
  • Mechanisms for locating or identifying other bundle entities (peers) within a network or across an internet. The mapping of a node ID to a potential convergence layer (CL) protocol and network address is left to implementation and configuration of the BP Agent (BPA) and its various potential routing strategies, as is the mapping of a DNS name and/or address to a choice of an end-entity certificate to authenticate a node to its peers.
  • Logic for routing bundles along a path toward a bundle's endpoint. This CL protocol is involved only in transporting bundles between adjacent entities in a routing sequence.
  • Policies or mechanisms for issuing Public Key Infrastructure Using X.509 (PKIX) certificates; provisioning, deploying, or accessing certificates and private keys; deploying or accessing certificate revocation lists (CRLs); or configuring security parameters on an individual entity or across a network.
  • Uses of TLS that are not based on PKIX certificate authentication (see Section 7.12.2) or in which authentication of both entities is not possible (see Section 7.12.1).
  • バンドルプロトコルのプロトコルデータ単位の形式。これらは[RFC9171]の別の箇所で定義されています。 これには、バンドルの断片化やバンドルのカプセル化の概念が含まれます。 TCPCLはバンドルを不透明なデータブロックとして転送します。
  • ネットワーク内またはインターネットを越えて、他のバンドルエンティティー（ピア）の場所を特定したり識別したりするためのメカニズム。 ノードIDから潜在的なコンバージェンス層（CL）プロトコルとネットワークアドレスへのマッピングは、バンドルプロトコルエージェント（BPA）の実装と設定、およびBPAのさまざまな潜在的なルーティング戦略に委ねられます。DNS名やアドレスから、ノードをそのピアに対して認証するためのエンドエンティティー証明書の選択へのマッピングも同様です。
  • バンドルのエンドポイントに向かう経路に沿ってバンドルをルーティングするためのロジック。 このCLプロトコルは、ルーティング系列において隣接するエンティティー間でバンドルを運ぶことにのみ関与します。
  • X.509を使用した公開鍵基盤（PKIX）の証明書を発行するためのポリシーやメカニズム、証明書と秘密鍵のプロビジョニング、展開、アクセス、証明書失効リスト（CRL）の展開やアクセス、個々のエンティティーやネットワーク全体でのセキュリティーパラメーターの設定。
  • PKIX証明書による認証に基づかないTLSの使用（Section 7.12.2を参照）や、両方のエンティティーの認証が不可能なTLSの使用（Section 7.12.1を参照）。

Any TCPCL implementation requires a BPA to perform those above-listed functions in order to perform end-to-end bundle delivery.

いずれのTCPCL実装も、エンドツーエンドのバンドル配送を行うために、上記の機能を実行するBPAを必要とします。

2.1. Definitions Specific to the TCPCL Protocol

2.1. TCPCLプロトコルに固有の定義

This section contains definitions specific to the TCPCL protocol.

このセクションには、TCPCLプロトコルに固有の定義が含まれています。

Network Byte Order:
Here, "network byte order" means most significant byte first, a.k.a. big endian. All of the integer encodings in this protocol SHALL be transmitted in network byte order.
TCPCL Entity:

This is the notional TCPCL application that initiates TCPCL sessions. This design, implementation, configuration, and specific behavior of such an entity is outside of the scope of this document. However, the concept of an entity has utility within the scope of this document as the container and initiator of TCPCL sessions. The relationship between a TCPCL entity and TCPCL sessions is defined as follows:

  • A TCPCL entity MAY actively initiate any number of TCPCL sessions and should do so whenever the entity is the initial transmitter of information to another entity in the network.
  • A TCPCL entity MAY support zero or more passive listening elements that listen for connection requests from other TCPCL entities operating on other entities in the network.
  • A TCPCL entity MAY passively initiate any number of TCPCL sessions from requests received by its passive listening element(s) if the entity uses such elements.

These relationships are illustrated in Figure 2. For most TCPCL behavior within a session, the two entities are symmetric and there is no protocol distinction between them. Some specific behavior, particularly during session establishment, distinguishes between the active entity and the passive entity. For the remainder of this document, the term "entity" without the prefix "TCPCL" refers to a TCPCL entity.

TCP Connection:
The term "connection" in this specification exclusively refers to a TCP connection and any and all behaviors, sessions, and other states associated with that TCP connection.
TCPCL Session:
A TCPCL session (as opposed to a TCP connection) is a TCPCL communication relationship between two TCPCL entities. A TCPCL session operates within a single underlying TCP connection, and the lifetime of a TCPCL session is bound to the lifetime of that TCP connection. A TCPCL session is terminated when the TCP connection ends, due to either (1) one or both entities actively closing the TCP connection or (2) network errors causing a failure of the TCP connection. Within a single TCPCL session, there are two possible transfer streams: one in each direction, with one stream from each entity being the outbound stream and the other being the inbound stream (see Figure 3). From the perspective of a TCPCL session, the two transfer streams do not logically interact with each other. The streams do operate over the same TCP connection and between the same BPAs, so there are logical relationships at those layers (message and bundle interleaving, respectively). For the remainder of this document, the term "session" without the prefix "TCPCL" refers to a TCPCL session.
Session Parameters:
These are a set of values used to affect the operation of the TCPCL for a given session. The manner in which these parameters are conveyed to the bundle entity and thereby to the TCPCL is implementation dependent. However, the mechanism by which two entities exchange and negotiate the values to be used for a given session is described in Section 4.3.
Transfer Stream:
A transfer stream is a unidirectional user-data path within a TCPCL session. Transfers sent over a transfer stream are serialized, meaning that one transfer must complete its transmission prior to another transfer being started over the same transfer stream. At the stream layer, there is no logical relationship between transfers in that stream; it's only within the BPA that transfers are fully decoded as bundles. Each unidirectional stream has a single sender entity and a single receiver entity.
Transfer:
This refers to the procedures and mechanisms for conveyance of an individual bundle from one node to another. Each transfer within the TCPCL is identified by a Transfer ID number, which is guaranteed to be unique only to a single direction within a single session.
Transfer Segment:
A transfer segment is a subset of a transfer of user data being communicated over a transfer stream.
Idle Session:
A TCPCL session is idle while there is no transmission in progress in either direction. While idle, the only messages being transmitted or received are KEEPALIVE messages.
Live Session:
A TCPCL session is live while there is a transmission in progress in either direction.
Reason Codes:
The TCPCL uses numeric codes to encode specific reasons for individual failure/error message types.
ネットワークバイトオーダー：
ここで「ネットワークバイトオーダー」とは、最上位バイトが先頭に来ること、いわゆるビッグエンディアンを意味します。 このプロトコルにおけるすべての整数のエンコーディングは、ネットワークバイトオーダーで送信することになります（SHALL）。
TCPCLエンティティー：

これは、TCPCLセッションを開始する概念上のTCPCLアプリケーションです。 そのようなエンティティーの設計、実装、設定、および具体的な振る舞いは、この文書の範囲外です。 しかし、エンティティーの概念は、TCPCLセッションのコンテナーおよび開始者として、この文書の範囲内で有用です。 TCPCLエンティティーとTCPCLセッションの関係は次のように定義されます。

  • TCPCLエンティティーは、任意の数のTCPCLセッションを能動的に開始してもよいです（MAY）。また、エンティティーがネットワーク内の別のエンティティーへの情報の最初の送信者である場合は常に、そうすべきです。
  • TCPCLエンティティーは、ネットワーク内の他のエンティティー上で動作する他のTCPCLエンティティーからのコネクション要求を待ち受ける受動的なリスニング要素を、0個以上サポートしてもよいです（MAY）。
  • TCPCLエンティティーは、受動的なリスニング要素を使用する場合、その受動的なリスニング要素が受信した要求から、任意の数のTCPCLセッションを受動的に開始してもよいです（MAY）。

これらの関係をFigure 2に示します。 セッション内のTCPCLの振る舞いのほとんどにおいて、2つのエンティティーは対称であり、両者の間にプロトコル上の区別はありません。 一部の特定の振る舞い、特にセッション確立時の振る舞いでは、能動的エンティティーと受動的エンティティーが区別されます。 この文書の残りの部分では、接頭辞「TCPCL」のない用語「エンティティー」はTCPCLエンティティーを指します。

TCPコネクション：
この仕様における用語「コネクション」は、もっぱらTCPコネクションと、そのTCPコネクションに関連付けられたあらゆる振る舞い、セッション、その他の状態を指します。
TCPCLセッション：
TCPCLセッションは（TCPコネクションとは異なり）、2つのTCPCLエンティティー間のTCPCL通信関係です。 TCPCLセッションは単一の下位TCPコネクション内で動作し、TCPCLセッションの有効期間はそのTCPコネクションの有効期間に結び付けられます。 TCPCLセッションは、(1)一方または両方のエンティティーがTCPコネクションを能動的に閉じるか、(2)ネットワークエラーによってTCPコネクションが失敗するかのいずれかによってTCPコネクションが終了したときに終了します。 単一のTCPCLセッション内には、2つの転送ストリームがあり得ます。各方向に1つずつで、各エンティティーから見て一方のストリームが送信ストリーム、もう一方が受信ストリームになります（Figure 3を参照）。 TCPCLセッションの観点からは、2つの転送ストリームは論理的に相互作用しません。 ただし、これらのストリームは同じTCPコネクション上で、同じBPA間で動作するため、それらの層では論理的な関係（それぞれメッセージとバンドルのインターリーブ）があります。 この文書の残りの部分では、接頭辞「TCPCL」のない用語「セッション」はTCPCLセッションを指します。
セッションパラメーター：
これは、特定のセッションにおけるTCPCLの動作に影響を与えるために使用される値の集合です。 これらのパラメーターがバンドルエンティティーに、ひいてはTCPCLに伝えられる方法は、実装依存です。 ただし、特定のセッションで使用する値を2つのエンティティーが交換してネゴシエートするメカニズムは、Section 4.3で説明します。
転送ストリーム：
転送ストリームは、TCPCLセッション内の単方向のユーザーデータの経路です。 転送ストリーム上で送信される転送は直列化されます。つまり、同じ転送ストリーム上で別の転送を開始する前に、1つの転送の送信が完了していなければなりません。 ストリーム層では、そのストリーム内の転送間に論理的な関係はありません。転送がバンドルとして完全にデコードされるのはBPA内だけです。 各単方向ストリームには、単一の送信者エンティティーと単一の受信者エンティティーがあります。
転送：
これは、個々のバンドルをあるノードから別のノードへ運ぶための手順とメカニズムを指します。 TCPCL内の各転送は転送ID番号によって識別されます。この番号は、単一のセッション内の単一の方向においてのみ一意であることが保証されます。
転送セグメント：
転送セグメントは、転送ストリーム上で伝達されるユーザーデータの転送の一部分です。
アイドルセッション：
TCPCLセッションは、どちらの方向にも進行中の送信がない間、アイドル状態です。 アイドル状態の間、送受信されるメッセージはKEEPALIVEメッセージだけです。
ライブセッション：
TCPCLセッションは、いずれかの方向に進行中の送信がある間、ライブ状態です。
理由コード：
TCPCLは、個々の失敗・エラーメッセージタイプについて具体的な理由をエンコードするために、数値コードを使用します。

3. General Protocol Description

3. プロトコルの一般的な説明

The service of this protocol is the transmission of DTN bundles via TCP. This document specifies the encapsulation of bundles, procedures for TCP setup and teardown, and a set of messages and entity requirements. The general operation of the protocol is as follows.

このプロトコルのサービスは、TCPを介したDTNバンドルの送信です。 この文書では、バンドルのカプセル化、TCPの確立と切断の手順、およびメッセージとエンティティーの要件の集合を規定します。 プロトコルの一般的な動作は次のとおりです。

3.1. Convergence-Layer Services

3.1. コンバージェンス層のサービス

This version of the TCPCL protocol provides the following services to support the overlaying BPA. In all cases, this is not an API definition but a logical description of how the CL can interact with the BPA. Each of these interactions can be associated with any number of additional metadata items as necessary to support the operation of the CL or BPA.

このバージョンのTCPCLプロトコルは、上位にあるBPAをサポートするために次のサービスを提供します。 いずれの場合も、これはAPIの定義ではなく、CLがBPAとどのようにやり取りできるかについての論理的な説明です。 これらのやり取りのそれぞれには、CLやBPAの動作をサポートするために必要に応じて、任意の数の追加のメタデータ項目を関連付けることができます。

Attempt Session:
The TCPCL allows a BPA to preemptively attempt to establish a TCPCL session with a peer entity. Each session attempt can send a different set of session negotiation parameters as directed by the BPA.
Terminate Session:
The TCPCL allows a BPA to preemptively terminate an established TCPCL session with a peer entity. The terminate request is done on a per-session basis.
Session State Changed:

The TCPCL entity indicates to the BPA when the session state changes. The top-level session states indicated are as follows:

Connecting:
A TCP connection is being established. This state only applies to the active entity.
Contact Negotiating:
A TCP connection has been made (as either the active or passive entity), and contact negotiation has begun.
Session Negotiating:
Contact negotiation has been completed (including possible TLS use), and session negotiation has begun.
Established:
The session has been fully established and is ready for its first transfer. When the session is established, the peer node ID (along with an indication of whether or not it was authenticated) and the negotiated session parameters (see Section 4.7) are also communicated to the BPA.
Ending:
The entity sent a SESS_TERM message and is in the Ending state.
Terminated:
The session has finished normal termination sequencing.
Failed:
The session ended without normal termination sequencing.
Session Idle Changed:
The TCPCL entity indicates to the BPA when the Live/Idle substate of the session changes. This occurs only when the top-level session state is "Established". The session transitions from Idle to Live at the start of a transfer in either transfer stream; the session transitions from Live to Idle at the end of a transfer when the other transfer stream does not have an ongoing transfer. Because the TCPCL transmits serially over a TCP connection, it suffers from "head-of-queue blocking", so a transfer in either direction can block an immediate start of a new transfer in the session.
Begin Transmission:
The principal purpose of the TCPCL is to allow a BPA to transmit bundle data over an established TCPCL session. Transmission requests are done on a per-session basis, and the CL does not necessarily perform any per-session or inter-session queueing. Any queueing of transmissions is the obligation of the BPA.
Transmission Success:
The TCPCL entity indicates to the BPA when a bundle has been fully transferred to a peer entity.
Transmission Intermediate Progress:
The TCPCL entity indicates to the BPA the intermediate progress of a transfer to a peer entity. This intermediate progress is at the granularity of each transferred segment.
Transmission Failure:
The TCPCL entity indicates to the BPA certain reasons for bundle transmission failure, notably when the peer entity rejects the bundle or when a TCPCL session ends before transfer success. The TCPCL itself does not have a notion of transfer timeout.
Reception Initialized:
The TCPCL entity indicates this status to the receiving BPA just before any transmission data is sent. This corresponds to reception of the XFER_SEGMENT message with the START flag set to 1.
Interrupt Reception:
The TCPCL entity allows a BPA to interrupt an individual transfer before it has fully completed (successfully or not). Interruption can occur any time after the reception is initialized.
Reception Success:
The TCPCL entity indicates to the BPA when a bundle has been fully transferred from a peer entity.
Reception Intermediate Progress:
The TCPCL entity indicates to the BPA the intermediate progress of a transfer from the peer entity. This intermediate progress is at the granularity of each transferred segment. An indication of intermediate reception gives a BPA the chance to inspect bundle header contents before the entire bundle is available and thus supports the "Interrupt Reception" capability.
Reception Failure:
The TCPCL entity indicates to the BPA certain reasons for reception failure, notably when the local entity rejects an attempted transfer for some local policy reason or when a TCPCL session ends before transfer success. The TCPCL itself does not have a notion of transfer timeout.
セッションの試行（Attempt Session）：
TCPCLは、BPAがピアエンティティーとのTCPCLセッションの確立を先回りして試行することを可能にします。 セッションの試行ごとに、BPAの指示に従って、異なるセッションネゴシエーションパラメーターの集合を送信できます。
セッションの終了（Terminate Session）：
TCPCLは、BPAがピアエンティティーとの確立済みのTCPCLセッションを先回りして終了することを可能にします。 終了要求はセッション単位で行われます。
セッション状態の変化（Session State Changed）：

TCPCLエンティティーは、セッション状態が変化したときにBPAに通知します。 通知される最上位のセッション状態は次のとおりです。

Connecting：
TCPコネクションを確立しています。この状態は能動的エンティティーにのみ適用されます。
Contact Negotiating：
（能動的エンティティーまたは受動的エンティティーのいずれかとして）TCPコネクションが確立され、コンタクトネゴシエーションが開始されています。
Session Negotiating：
（TLSの使用の可能性も含めて）コンタクトネゴシエーションが完了し、セッションネゴシエーションが開始されています。
Established：
セッションが完全に確立され、最初の転送の準備ができています。 セッションが確立されると、ピアのノードID（認証されたかどうかの表示とともに）と、ネゴシエートされたセッションパラメーター（Section 4.7を参照）もBPAに伝えられます。
Ending：
エンティティーがSESS_TERMメッセージを送信し、Ending状態にあります。
Terminated：
セッションが通常の終了シーケンスを完了しました。
Failed：
セッションが通常の終了シーケンスを経ずに終了しました。
セッションのアイドル状態の変化（Session Idle Changed）：
TCPCLエンティティーは、セッションのLive/Idleのサブ状態が変化したときにBPAに通知します。 これは、最上位のセッション状態が「Established」である場合にのみ発生します。 セッションは、いずれかの転送ストリームで転送が始まるとIdleからLiveに遷移し、もう一方の転送ストリームに進行中の転送がない状態で転送が終わるとLiveからIdleに遷移します。 TCPCLはTCPコネクション上で直列に送信するため、「キューの先頭のブロッキング（head-of-queue blocking）」の影響を受けます。そのため、いずれかの方向の転送が、セッション内での新しい転送の即時開始を妨げる場合があります。
送信の開始（Begin Transmission）：
TCPCLの主な目的は、BPAが確立済みのTCPCLセッション上でバンドルデータを送信できるようにすることです。 送信要求はセッション単位で行われ、CLはセッションごとのキューイングやセッション間のキューイングを必ずしも行いません。 送信のキューイングはすべてBPAの責務です。
送信の成功（Transmission Success）：
TCPCLエンティティーは、バンドルがピアエンティティーに完全に転送されたときにBPAに通知します。
送信の途中経過（Transmission Intermediate Progress）：
TCPCLエンティティーは、ピアエンティティーへの転送の途中経過をBPAに通知します。 この途中経過は、転送された各セグメントの粒度で通知されます。
送信の失敗（Transmission Failure）：
TCPCLエンティティーは、バンドルの送信が失敗した特定の理由をBPAに通知します。特に、ピアエンティティーがバンドルを拒否した場合や、転送が成功する前にTCPCLセッションが終了した場合です。 TCPCL自体には転送のタイムアウトの概念はありません。
受信の初期化（Reception Initialized）：
TCPCLエンティティーは、送信データが送られる直前に、受信側のBPAにこの状態を通知します。 これは、STARTフラグが1に設定されたXFER_SEGMENTメッセージの受信に対応します。
受信の中断（Interrupt Reception）：
TCPCLエンティティーは、個々の転送が（成功したかどうかにかかわらず）完全に完了する前に、BPAがその転送を中断することを可能にします。 中断は、受信が初期化された後であればいつでも発生し得ます。
受信の成功（Reception Success）：
TCPCLエンティティーは、バンドルがピアエンティティーから完全に転送されたときにBPAに通知します。
受信の途中経過（Reception Intermediate Progress）：
TCPCLエンティティーは、ピアエンティティーからの転送の途中経過をBPAに通知します。 この途中経過は、転送された各セグメントの粒度で通知されます。 受信の途中経過の通知により、BPAはバンドル全体が利用可能になる前にバンドルヘッダーの内容を調べる機会を得られます。したがって、これは「受信の中断」の能力をサポートします。
受信の失敗（Reception Failure）：
TCPCLエンティティーは、受信が失敗した特定の理由をBPAに通知します。特に、ローカルエンティティーが何らかのローカルポリシー上の理由で転送の試みを拒否した場合や、転送が成功する前にTCPCLセッションが終了した場合です。 TCPCL自体には転送のタイムアウトの概念はありません。

3.2. TCPCL Session Overview

3.2. TCPCLセッションの概要

First, one entity establishes a TCPCL session to the other by initiating a TCP connection in accordance with [RFC0793]. After setup of the TCP connection is complete, an initial Contact Header is exchanged in both directions to establish a shared TCPCL version and negotiate the use of TLS security (as described in Section 4). Once contact negotiation is complete, TCPCL messaging is available and the session negotiation is used to set parameters of the TCPCL session. One of these parameters is a node ID; each TCPCL entity is acting on behalf of a BPA having a node ID. This is used to assist in routing and forwarding messages by the BPA and is part of the authentication capability provided by TLS.

まず、一方のエンティティーが[RFC0793]に従ってTCPコネクションを開始することにより、もう一方のエンティティーへのTCPCLセッションを確立します。 TCPコネクションの確立が完了した後、共通のTCPCLバージョンを確立し、TLSセキュリティーの使用をネゴシエートするために、最初のコンタクトヘッダーが両方向で交換されます（Section 4で説明します）。 コンタクトネゴシエーションが完了すると、TCPCLのメッセージングが利用可能になり、セッションネゴシエーションを使用してTCPCLセッションのパラメーターを設定します。 これらのパラメーターの1つはノードIDです。各TCPCLエンティティーは、ノードIDを持つBPAに代わって動作します。 これは、BPAによるメッセージのルーティングと転送を支援するために使用され、TLSが提供する認証能力の一部でもあります。

Once negotiated, the parameters of a TCPCL session cannot change; if there is a desire by either peer to transfer data under different parameters, then a new session must be established. This makes CL logic simpler but relies on the assumption that establishing a TCP connection is lightweight enough that TCP connection overhead is negligible compared to TCPCL data sizes.

一度ネゴシエートされると、TCPCLセッションのパラメーターは変更できません。どちらかのピアが異なるパラメーターでデータを転送したい場合は、新しいセッションを確立しなければなりません。 これによりCLのロジックは単純になりますが、TCPコネクションの確立が十分に軽量であり、TCPコネクションのオーバーヘッドがTCPCLのデータサイズに比べて無視できるという前提に依存しています。

Once the TCPCL session is established and configured in this way, bundles can be transferred in either direction. Each transfer is performed by segmenting the transfer data into one or more XFER_SEGMENT messages. Multiple bundles can be transmitted consecutively in a single direction on a single TCPCL connection. Segments from different bundles are never interleaved. Bundle interleaving can be accomplished by fragmentation at the BP layer or by establishing multiple TCPCL sessions between the same peers. There is no fundamental limit on the number of TCPCL sessions that a single entity can establish, beyond the limit imposed by the number of available (ephemeral) TCP ports of the active entity.

このようにしてTCPCLセッションが確立されて設定されると、バンドルをどちらの方向にも転送できます。 各転送は、転送データを1つ以上のXFER_SEGMENTメッセージに分割することによって行われます。 単一のTCPCLコネクション上で、単一の方向に複数のバンドルを連続して送信できます。 異なるバンドルのセグメントがインターリーブされることはありません。 バンドルのインターリーブは、BP層での断片化によって、または同じピア間に複数のTCPCLセッションを確立することによって実現できます。 単一のエンティティーが確立できるTCPCLセッションの数には、能動的エンティティーの利用可能な（エフェメラル）TCPポートの数によって課される制限以外に、基本的な制限はありません。

One feature of this protocol is that the receiving entity can send acknowledgment (XFER_ACK) messages as bundle data segments arrive. The rationale behind these acknowledgments is to enable the transmitting entity to determine how much of the bundle has been received, so that if the session is interrupted, it can perform reactive fragmentation to avoid resending the already-transmitted part of the bundle. In addition, there is no explicit flow control on the TCPCL.

このプロトコルの特徴の1つは、受信側エンティティーが、バンドルデータのセグメントが到着するたびに確認応答（XFER_ACK）メッセージを送信できることです。 これらの確認応答の論拠は、バンドルのどれだけが受信されたかを送信側エンティティーが判断できるようにすることです。そうすることで、セッションが中断された場合に、送信側エンティティーはリアクティブな断片化を行い、バンドルのすでに送信された部分を再送しないようにできます。 さらに、TCPCLには明示的なフロー制御はありません。

A TCPCL receiver can interrupt the transmission of a bundle at any point in time by replying with a XFER_REFUSE message, which causes the sender to stop transmission of the associated bundle (if it hasn't already finished transmission).

TCPCLの受信者は、XFER_REFUSEメッセージを返すことにより、いつでもバンドルの送信を中断できます。これにより、送信者は（まだ送信を終えていなければ）関連するバンドルの送信を停止します。

Note: This enables a cross-layer optimization in that it allows a receiver that detects that it has already received a certain bundle to interrupt transmission as early as possible and thus save transmission capacity for other bundles.

注：これによりクロスレイヤーの最適化が可能になります。つまり、特定のバンドルをすでに受信していることを検出した受信者が、できるだけ早く送信を中断できるようになり、その結果、他のバンドルのために送信容量を節約できます。

For sessions that are idle, a KEEPALIVE message is sent at a negotiated interval. This is used to convey entity liveness information during otherwise messageless time intervals.

アイドル状態のセッションでは、ネゴシエートされた間隔でKEEPALIVEメッセージが送信されます。 これは、メッセージがなければ何も送られない時間間隔の間に、エンティティーの生存情報を伝えるために使用されます。

A SESS_TERM message is used to initiate the ending of a TCPCL session (see Section 6.1). During termination sequencing, in-progress transfers can be completed but no new transfers can be initiated. A SESS_TERM message can also be used to refuse a session setup by a peer (see Section 4.3). Regardless of the reason, session termination is initiated by one of the entities and the other entity responds to it, as illustrated by Figures 13 and 14 in the next subsection. Even when there are no transfers queued or in progress, the session termination procedure allows each entity to distinguish between a clean end to a session and the TCP connection being closed because of some underlying network issue.

SESS_TERMメッセージは、TCPCLセッションの終了を開始するために使用されます（Section 6.1を参照）。 終了シーケンスの間、進行中の転送は完了できますが、新しい転送は開始できません。 SESS_TERMメッセージは、ピアによるセッションの確立を拒否するためにも使用できます（Section 4.3を参照）。 理由にかかわらず、次のサブセクションの図13と図14に示すように、セッションの終了は一方のエンティティーによって開始され、もう一方のエンティティーがそれに応答します。 キューに入っている転送や進行中の転送がない場合でも、セッション終了手順により、各エンティティーは、セッションが正常に終了したのか、何らかの下位のネットワークの問題によってTCPコネクションが閉じられたのかを区別できます。

Once a session is established, the TCPCL is a symmetric protocol between the peers. Both sides can start sending data segments in a session, and one side's bundle transfer does not have to complete before the other side can start sending data segments on its own. Hence, the protocol allows for a bidirectional mode of communication. Note that in the case of concurrent bidirectional transmission, acknowledgment segments MAY be interleaved with data segments.

セッションが確立されると、TCPCLはピア間で対称なプロトコルになります。 セッション内では両側がデータセグメントの送信を開始でき、一方の側のバンドル転送が完了しなくても、もう一方の側は自らデータセグメントの送信を開始できます。 したがって、このプロトコルは双方向の通信モードを可能にします。 並行して双方向の送信を行う場合、確認応答セグメントはデータセグメントとインターリーブしてもよいです（MAY）。

3.4. PKIX Environments and CA Policy

3.4. PKIX環境とCAのポリシー

This specification defines requirements regarding how to use PKIX certificates issued by a Certificate Authority (CA) but does not define any mechanisms for how those certificates come to be. The requirements regarding TCPCL certificate use are broad, to support two quite different PKIX environments:

この仕様は、認証局（CA）が発行したPKIX証明書の使用方法に関する要件を定義しますが、それらの証明書がどのように作られるかについてのメカニズムは定義しません。 TCPCLの証明書の使用に関する要件は、まったく異なる2つのPKIX環境をサポートするために、幅広いものになっています。

DTN-Aware CAs:
In the ideal case, the CA or CAs issuing certificates for TCPCL entities are aware of the end use of the certificate, have a mechanism for verifying ownership of a node ID, and are issuing certificates directly for that node ID. In this environment, the ability to authenticate a peer entity node ID directly avoids the need to authenticate a network name or address and then implicitly trust the node ID of the peer. The TCPCL authenticates the node ID whenever possible; this is preferred over lower-level PKIX identities.
DTN-Ignorant CAs:
It is expected that Internet-scale "public" CAs will continue to focus on DNS names as the preferred PKIX identifier. There are large infrastructures already in place for managing network-level authentication and protocols to manage identity verification in those environments [RFC8555]. The TCPCL allows for this type of environment by authenticating a lower-level identifier for a peer and requiring the entity to trust that the node ID given by the peer (during session initialization) is valid. This situation is not ideal, as it allows the vulnerabilities described in Section 7.9, but it still provides some amount of mutual authentication to take place for a TCPCL session.
DTNを認識するCA：
理想的な場合、TCPCLエンティティー向けの証明書を発行する1つ以上のCAは、証明書の最終的な用途を認識しており、ノードIDの所有権を検証するメカニズムを持ち、そのノードIDに対して直接証明書を発行します。 この環境では、ピアエンティティーのノードIDを直接認証できるため、ネットワーク名やアドレスを認証したうえでピアのノードIDを暗黙的に信頼する必要がなくなります。 TCPCLは可能な限りノードIDを認証します。こちらのほうが、より下位のPKIXアイデンティティーよりも好ましいとされます。
DTNを認識しないCA：
インターネット規模の「公開」CAは、引き続き、好ましいPKIX識別子としてDNS名に重点を置くと予想されます。 ネットワークレベルの認証を管理するための大規模なインフラストラクチャーと、そのような環境でアイデンティティーの検証を管理するためのプロトコル[RFC8555]が、すでに整備されています。 TCPCLは、ピアのより下位の識別子を認証し、（セッション初期化の間に）ピアが提示したノードIDが有効であるとエンティティーが信頼することを求めることにより、この種の環境に対応します。 この状況はSection 7.9で説明する脆弱性を許すため理想的ではありませんが、それでもTCPCLセッションに対してある程度の相互認証を行えるようにします。

Even within a single TCPCL session, each entity may operate within different PKI environments and with different identifier limitations. The requirements related to identifiers in a PKIX certificate are provided in Section 4.4.1.

単一のTCPCLセッション内でも、各エンティティーは異なるPKI環境の中で、異なる識別子の制限のもとで動作する可能性があります。 PKIX証明書における識別子に関連する要件は、Section 4.4.1で示します。

It is important for interoperability that a TCPCL entity have its own security policy tailored to accommodate the peers with which it is expected to operate. Some security policy recommendations are given in Section 4.4.5, but these are meant as a starting point for tailoring. A strict TLS security policy is appropriate for a private network with a single shared CA. Operation on the Internet (such as inter-site BP gateways) could trade more lax TCPCL security with the use of encrypted bundle encapsulation [DTN-BIBECT] to ensure strong bundle security.

相互運用性のためには、TCPCLエンティティーが、一緒に動作することが想定されるピアに対応するように調整された独自のセキュリティーポリシーを持つことが重要です。 いくつかのセキュリティーポリシーの推奨事項をSection 4.4.5で示しますが、これらは調整のための出発点として意図されたものです。 単一の共有CAを持つプライベートネットワークには、厳格なTLSセキュリティーポリシーが適切です。 インターネット上での運用（サイト間のBPゲートウェイなど）では、より緩いTCPCLセキュリティーと引き換えに、暗号化されたバンドルのカプセル化[DTN-BIBECT]を使用して強固なバンドルセキュリティーを確保することも考えられます。

By using the Server Name Indication (SNI) DNS name (see Section 4.4.3), a single passive entity can act as a convergence layer for multiple BPAs with distinct node IDs. When this "virtual host" behavior is used, the DNS name is used as the indication of which BP node the active entity is attempting to communicate with. A virtual host CL entity can be authenticated by a certificate containing all of the DNS names and/or node IDs being hosted or by several certificates each authenticating a single DNS name and/or node ID, using the SNI value from the peer to select which certificate to use. The logic for mapping an SNI DNS name to an end-entity certificate is an implementation matter and can involve correlating a DNS name with a node ID or other certificate attributes.

Server Name Indication（SNI）のDNS名（Section 4.4.3を参照）を使用することにより、単一の受動的エンティティーが、異なるノードIDを持つ複数のBPAのためのコンバージェンス層として動作できます。 この「仮想ホスト」の振る舞いを使用する場合、DNS名は、能動的エンティティーがどのBPノードと通信しようとしているかを示すものとして使用されます。 仮想ホストのCLエンティティーは、ホストしているすべてのDNS名やノードIDを含む1つの証明書によって認証することも、それぞれが単一のDNS名やノードIDを認証する複数の証明書によって認証することもできます。後者の場合は、ピアからのSNIの値を使用して、どの証明書を使用するかを選択します。 SNIのDNS名をエンドエンティティー証明書にマッピングするロジックは実装上の問題であり、DNS名をノードIDやその他の証明書の属性と関連付けることを含む場合があります。

3.5. Session-Keeping Policies

3.5. セッション維持のポリシー

This specification defines requirements regarding how to initiate, sustain, and terminate a TCPCL session but does not impose any requirements on how sessions need to be managed by a BPA. It is a network administration matter to determine an appropriate session-keeping policy, but guidance given here can be used to steer policy toward performance goals.

この仕様は、TCPCLセッションの開始、維持、終了の方法に関する要件を定義しますが、BPAがセッションをどのように管理する必要があるかについての要件は課しません。 適切なセッション維持のポリシーを決定することはネットワーク管理上の問題ですが、ここで示すガイダンスは、ポリシーを性能目標に向けて方向付けるために使用できます。

Persistent Session:
This policy preemptively establishes a single session to known entities in the network and keeps the session active using KEEPALIVEs. Benefits of this policy include reducing the total amount of TCP data that needs to be exchanged for a set of transfers (assuming that the KEEPALIVE size is significantly smaller than the transfer size) and allowing the session state to indicate peer connectivity. Drawbacks include wasted network resources when a session is mostly idle or when network connectivity is inconsistent (which requires that failed sessions be reestablished), and potential queueing issues when multiple transfers are requested simultaneously. This policy assumes that there is agreement between pairs of entities as to which of the peers will initiate sessions; if there is no such agreement, there is potential for duplicate sessions to be established between peers.
Ephemeral Sessions:
This policy only establishes a session when an outgoing transfer needs to be sent. Benefits of this policy include not wasting network resources on sessions that are idle for long periods of time and avoiding potential queueing issues as can be seen when using a single persistent session. Drawbacks include the TCP and TLS overhead of establishing a new session for each transfer. This policy assumes that each entity can function in a passive role to listen for session requests from any peer that needs to send a transfer; when that is not the case, the polling behavior discussed below needs to happen. This policy can be augmented to keep the session established as long as any transfers are queued.
Active-Only Polling Sessions:
When naming and/or addressing of one entity is variable (i.e., a dynamically assigned IP address or domain name) or when firewall or routing rules prevent incoming TCP connections, that entity can only function in the active role. In these cases, sessions also need to be established when an incoming transfer is expected from a peer or based on a periodic schedule. This polling behavior causes inefficiencies compared to as-needed ephemeral sessions.
永続的なセッション：
このポリシーは、ネットワーク内の既知のエンティティーへの単一のセッションを先回りして確立し、KEEPALIVEを使用してそのセッションをアクティブに保ちます。 このポリシーの利点としては、（KEEPALIVEのサイズが転送のサイズよりも大幅に小さいと仮定すると）一連の転送のために交換する必要があるTCPデータの総量を減らせることや、セッションの状態によってピアの接続性を示せることが挙げられます。 欠点としては、セッションがほとんどアイドル状態である場合や、ネットワークの接続性が不安定な場合（失敗したセッションを再確立する必要があります）にネットワークリソースが無駄になることや、複数の転送が同時に要求された場合にキューイングの問題が生じる可能性があることが挙げられます。 このポリシーは、どちらのピアがセッションを開始するかについてエンティティーのペアの間で合意があることを前提としています。そのような合意がない場合、ピア間で重複したセッションが確立される可能性があります。
エフェメラルセッション：
このポリシーは、送信する転送が必要になったときにのみセッションを確立します。 このポリシーの利点としては、長期間アイドル状態のセッションにネットワークリソースを浪費しないことや、単一の永続的なセッションを使用する場合に見られるようなキューイングの問題を避けられることが挙げられます。欠点としては、転送ごとに新しいセッションを確立するためのTCPとTLSのオーバーヘッドが挙げられます。 このポリシーは、各エンティティーが、転送を送信する必要がある任意のピアからのセッション要求を待ち受ける受動的な役割で機能できることを前提としています。そうでない場合は、以下で説明するポーリングの振る舞いが必要になります。 このポリシーは、転送がキューに入っている限りセッションを確立したままにするように拡張できます。
能動側のみのポーリングセッション：
あるエンティティーの名前付けやアドレス付けが可変である場合（つまり、動的に割り当てられるIPアドレスやドメイン名の場合）や、ファイアウォールやルーティングの規則によって着信TCPコネクションが妨げられる場合、そのエンティティーは能動的な役割でしか機能できません。 このような場合、ピアからの着信転送が予想されるときにも、または定期的なスケジュールに基づいて、セッションを確立する必要があります。 このポーリングの振る舞いは、必要に応じたエフェメラルセッションと比べて非効率を生じます。

Many other policies can be established in a TCPCL network between the two extremes of single persistent sessions and only ephemeral sessions. Different policies can be applied to each peer entity and to each bundle as it needs to be transferred (e.g., for quality of service). Additionally, future session extension types can apply further nuance to session policies and policy negotiation.

TCPCLネットワークでは、単一の永続的なセッションと、エフェメラルセッションのみという2つの極端な例の間に、他にも多くのポリシーを確立できます。 ピアエンティティーごとに、また転送する必要があるバンドルごとに（たとえばサービス品質のために）、異なるポリシーを適用できます。 さらに、将来のセッション拡張タイプによって、セッションのポリシーやポリシーのネゴシエーションにさらなる細かな違いを加えることができます。

3.6. Transfer Segmentation Policies

3.6. 転送の分割のポリシー

Each TCPCL session allows a negotiated transfer segmentation policy to be applied in each transfer direction. A receiving entity can set the Segment Maximum Receive Unit (MRU) in its SESS_INIT message to determine the largest acceptable segment size, and a transmitting entity can segment a transfer into any sizes smaller than the receiver's Segment MRU. It is a network administration matter to determine an appropriate segmentation policy for entities using the TCPCL protocol, but guidance given here can be used to steer policy toward performance goals. Administrators are also advised to consider the Segment MRU in relation to chunking/packetization performed by TLS, TCP, and any intermediate network-layer nodes.

各TCPCLセッションでは、ネゴシエートされた転送の分割のポリシーを転送の方向ごとに適用できます。 受信側エンティティーは、SESS_INITメッセージでセグメント最大受信単位（Segment Maximum Receive Unit; MRU）を設定して受け入れ可能な最大のセグメントサイズを決定でき、送信側エンティティーは、受信者のセグメントMRUよりも小さい任意のサイズに転送を分割できます。 TCPCLプロトコルを使用するエンティティーのための適切な分割のポリシーを決定することはネットワーク管理上の問題ですが、ここで示すガイダンスは、ポリシーを性能目標に向けて方向付けるために使用できます。 管理者は、TLS、TCP、および中間のネットワーク層ノードが行うチャンク化・パケット化との関係でセグメントMRUを検討することも勧められます。

Minimum Overhead:
For a simple network expected to exchange relatively small bundles, the Segment MRU can be set to be identical to the Transfer MRU, which indicates that all transfers can be sent with a single data segment (i.e., no actual segmentation). If the network is closed and all transmitters are known to follow a single-segment transfer policy, then receivers can avoid the necessity of segment reassembly. Because this CL operates over a TCP stream, which suffers from a form of head-of-queue blocking between messages, while one entity is transmitting a single XFER_SEGMENT message it is not able to transmit any XFER_ACK or XFER_REFUSE messages for any associated received transfers.
Predictable Message Sizing:
In situations where the maximum message size is desired to be well controlled, the Segment MRU can be set to the largest acceptable size (the message size less the XFER_SEGMENT header size) and transmitters can always segment a transfer into maximum-size chunks no larger than the Segment MRU. This guarantees that any single XFER_SEGMENT will not monopolize the TCP stream for too long, which would prevent outgoing XFER_ACK and XFER_REFUSE messages associated with received transfers.
Dynamic Segmentation:
Even after negotiation of a Segment MRU for each receiving entity, the actual transfer segmentation only needs to guarantee that any individual segment is no larger than that MRU. In a situation where TCP throughput is dynamic, the transfer segmentation size can also be dynamic in order to control message transmission duration.
最小オーバーヘッド：
比較的小さなバンドルを交換することが想定される単純なネットワークでは、セグメントMRUを転送MRUと同じに設定できます。これは、すべての転送を単一のデータセグメントで送信できる（つまり、実際には分割しない）ことを示します。 ネットワークが閉じており、すべての送信者が単一セグメントの転送ポリシーに従うことがわかっている場合、受信者はセグメントの再構築の必要性を避けられます。 このCLはTCPストリーム上で動作し、メッセージ間で一種のキューの先頭のブロッキングの影響を受けるため、一方のエンティティーが単一のXFER_SEGMENTメッセージを送信している間は、関連する受信した転送のためのXFER_ACKメッセージやXFER_REFUSEメッセージを送信できません。
予測可能なメッセージサイズ：
最大メッセージサイズを適切に制御したい状況では、セグメントMRUを受け入れ可能な最大サイズ（メッセージサイズからXFER_SEGMENTのヘッダーサイズを引いたもの）に設定でき、送信者は常に、セグメントMRUを超えない最大サイズのチャンクに転送を分割できます。 これにより、単一のXFER_SEGMENTがTCPストリームを長時間独占することがないことが保証されます。独占が起きると、受信した転送に関連する送信側のXFER_ACKメッセージやXFER_REFUSEメッセージが妨げられてしまいます。
動的な分割：
受信側エンティティーごとにセグメントMRUをネゴシエートした後であっても、実際の転送の分割で保証する必要があるのは、個々のセグメントがそのMRUより大きくないことだけです。 TCPのスループットが動的に変化する状況では、メッセージの送信時間を制御するために、転送の分割サイズも動的に変更できます。

Many other policies can be established in a TCPCL network between the two extremes of minimum overhead (large MRU, single segment) and predictable message sizing (small MRU, highly segmented). Different policies can be applied to each transfer stream to and from any particular entity. Additionally, future session extension and transfer extension types can apply further nuance to transfer policies and policy negotiation.

TCPCLネットワークでは、最小オーバーヘッド（大きなMRU、単一セグメント）と予測可能なメッセージサイズ（小さなMRU、細かく分割）という2つの極端な例の間に、他にも多くのポリシーを確立できます。 特定のエンティティーとの間の転送ストリームごとに、異なるポリシーを適用できます。 さらに、将来のセッション拡張タイプや転送拡張タイプによって、転送のポリシーやポリシーのネゴシエーションにさらなる細かな違いを加えることができます。

4. Session Establishment

4. セッションの確立

For bundle transmissions to occur using the TCPCL, a TCPCL session MUST first be established between communicating entities. It is up to the implementation to decide how and when session setup is triggered. For example, some sessions can be opened proactively and maintained for as long as is possible given the network conditions, while other sessions will be opened only when there is a bundle that is queued for transmission and the routing algorithm selects a certain next-hop node.

TCPCLを使用してバンドルの送信を行うには、まず通信するエンティティー間でTCPCLセッションを確立しなければなりません（MUST）。 セッションの確立をいつどのように開始するかは、実装の判断に委ねられます。 たとえば、一部のセッションは先回りして開かれ、ネットワークの状態が許す限り維持される一方で、他のセッションは、送信のためにキューに入っているバンドルがあり、ルーティングアルゴリズムが特定のネクストホップのノードを選択した場合にのみ開かれる、ということが考えられます。

4.1. TCP Connection

4.1. TCPコネクション

To establish a TCPCL session, an entity MUST first establish a TCP connection with the intended peer entity, typically by using the services provided by the operating system. Destination port number 4556 has been assigned by IANA as the registered port number for the TCPCL; see Section 8.1. Other destination port numbers MAY be used per local configuration. Determining a peer's destination port number (if different from the registered TCPCL port number) is left up to the implementation. Any source port number MAY be used for TCPCL sessions. Typically, an operating system assigned number in the TCP Ephemeral range (49152-65535) is used.

TCPCLセッションを確立するには、エンティティーはまず、通常はオペレーティングシステムが提供するサービスを使用して、目的のピアエンティティーとのTCPコネクションを確立しなければなりません（MUST）。 宛先ポート番号4556は、TCPCLの登録ポート番号としてIANAによって割り当てられています。Section 8.1を参照してください。 ローカルの設定に従って、他の宛先ポート番号を使用してもよいです（MAY）。 ピアの宛先ポート番号（登録されたTCPCLのポート番号と異なる場合）の決定は、実装に委ねられます。 TCPCLセッションには、任意の送信元ポート番号を使用してもよいです（MAY）。 通常は、TCPのエフェメラル範囲（49152〜65535）にある、オペレーティングシステムが割り当てた番号が使用されます。

If the entity is unable to establish a TCP connection for any reason, then it is an implementation matter to determine how to handle the connection failure. An entity MAY decide to reattempt to establish the connection. If it does so, it MUST NOT overwhelm its target with repeated connection attempts. Therefore, the entity MUST NOT retry the connection setup earlier than some delay time from the last attempt, and it SHOULD use a (binary) exponential backoff mechanism to increase this delay in the case of repeated failures. The upper limit on a reattempt backoff is implementation defined but SHOULD be no longer than one minute (60 seconds) before signaling to the BPA that a connection cannot be made.

エンティティーが何らかの理由でTCPコネクションを確立できない場合、そのコネクションの失敗をどのように処理するかを決めることは実装上の問題です。 エンティティーは、コネクションの確立を再試行することを決定してもよいです（MAY）。 その場合、エンティティーは、繰り返しのコネクションの試みによって相手を圧倒してはなりません（MUST NOT）。 したがって、エンティティーは、最後の試行から一定の遅延時間が経過する前にコネクションの確立を再試行してはなりません（MUST NOT）。また、失敗が繰り返される場合には、この遅延を増やすために（2進）指数バックオフのメカニズムを使用すべきです（SHOULD）。 再試行のバックオフの上限は実装で定義されますが、コネクションを確立できないことをBPAに通知するまでの時間は、1分（60秒）以下にすべきです（SHOULD）。

Once a TCP connection is established, the active entity SHALL immediately transmit its Contact Header. The passive entity SHALL wait for the active entity's Contact Header. Upon reception of a Contact Header, the passive entity SHALL transmit its Contact Header. If either entity does not receive a Contact Header after some implementation-defined time duration after the TCP connection is established, the waiting entity SHALL close the TCP connection. Entities SHOULD choose a Contact Header reception timeout interval no longer than one minute (60 seconds). The ordering of the Contact Header exchange allows the passive entity to avoid allocating resources to a potential TCPCL session until after a valid Contact Header has been received from the active entity. This ordering also allows the passive peer to adapt to alternate TCPCL protocol versions.

TCPコネクションが確立されると、能動的エンティティーは直ちに自身のコンタクトヘッダーを送信することになります（SHALL）。 受動的エンティティーは、能動的エンティティーのコンタクトヘッダーを待機することになります（SHALL）。 コンタクトヘッダーを受信すると、受動的エンティティーは自身のコンタクトヘッダーを送信することになります（SHALL）。 TCPコネクションが確立されてから実装で定義された時間が経過してもどちらかのエンティティーがコンタクトヘッダーを受信しない場合、待機しているエンティティーはTCPコネクションをクローズすることになります（SHALL）。 エンティティーは、1分（60秒）を超えないコンタクトヘッダー受信タイムアウト間隔を選択すべきです（SHOULD）。 コンタクトヘッダーの交換の順序により、受動的エンティティーは、能動的エンティティーから有効なコンタクトヘッダーを受信するまで、潜在的なTCPCLセッションにリソースを割り当てずに済みます。 この順序により、受動的ピアが別のTCPCLプロトコルバージョンに適応することも可能になります。

The format of the Contact Header is described in Section 4.2. Because the TCPCL protocol version in use is part of the initial Contact Header, entities using TCPCL version 4 can coexist on a network with entities using earlier TCPCL versions (with some negotiation needed for interoperation, as described in Section 4.3).

コンタクトヘッダーの形式はSection 4.2で説明します。 使用中のTCPCLプロトコルバージョンは最初のコンタクトヘッダーの一部であるため、TCPCLバージョン4を使用するエンティティーは、以前のTCPCLバージョンを使用するエンティティーとネットワーク上で共存できます（Section 4.3で説明するように、相互運用のためには何らかのネゴシエーションが必要です）。

Within this specification, when an entity is said to "close" a TCP connection the entity SHALL use the TCP FIN mechanism and not the RST mechanism. However, either mechanism, when received, will cause a TCP connection to become closed.

この仕様において、エンティティーがTCPコネクションを「閉じる」と言う場合、エンティティーはRSTメカニズムではなくTCPのFINメカニズムを使用することになります（SHALL）。 ただし、どちらのメカニズムを受信した場合も、TCPコネクションは閉じられます。

4.2. コンタクトヘッダー

This section describes the format of the Contact Header and the meaning of its fields.

このセクションでは、コンタクトヘッダーの形式とそのフィールドの意味について説明します。

Upon receipt of the Contact Header, both entities perform the validation and negotiation procedures defined in Section 4.3. After receiving the Contact Header from the other entity, either entity MAY refuse the session by sending a SESS_TERM message with an appropriate reason code.

コンタクトヘッダーを受信すると、両方のエンティティーはSection 4.3で定義されている検証とネゴシエーションの手順を実行します。 もう一方のエンティティーからコンタクトヘッダーを受信した後、どちらのエンティティーも、適切な理由コードを持つSESS_TERMメッセージを送信することによってセッションを拒否してもよいです（MAY）。

4.3. Contact Validation and Negotiation

4.3. コンタクトの検証とネゴシエーション

Upon reception of the Contact Header, each entity follows the following procedures to ensure the validity of the TCPCL session and to negotiate values for the session parameters.

コンタクトヘッダーを受信すると、各エンティティーは、TCPCLセッションの有効性を確認し、セッションパラメーターの値をネゴシエートするために、次の手順に従います。

If the "magic string" is not present or is not valid, the connection MUST be terminated. The intent of the magic string is to provide some protection against an inadvertent TCP connection by a different protocol than the one described in this document. To prevent a flood of repeated connections from a misconfigured application, a passive entity MAY deny new TCP connections from a specific peer address for a period of time after one or more connections fail to provide a decodable Contact Header.

「マジック文字列」が存在しないか有効でない場合、コネクションを終了しなければなりません（MUST）。 マジック文字列の目的は、この文書で説明するプロトコルとは異なるプロトコルによる不注意なTCPコネクションに対して、ある程度の保護を提供することです。 設定を誤ったアプリケーションからの繰り返しのコネクションの殺到を防ぐために、受動的エンティティーは、1つ以上のコネクションがデコード可能なコンタクトヘッダーを提供できなかった後の一定期間、特定のピアアドレスからの新しいTCPコネクションを拒否してもよいです（MAY）。

The first negotiation attempts to determine which TCPCL protocol version to use. The active entity always sends its Contact Header first and waits for a response from the passive entity. During contact initiation, the active TCPCL entity SHALL send the highest TCPCL protocol version on a first session attempt for a TCPCL peer. If the active entity receives a Contact Header with a lower protocol version than the one sent earlier on the TCP connection, the TCP connection SHALL be closed. If the active entity receives a SESS_TERM message with a reason code of "Version mismatch", that entity MAY attempt further TCPCL sessions with the peer using earlier protocol version numbers in decreasing order. Managing multi-TCPCL-session state such as this is an implementation matter.

最初のネゴシエーションでは、どのTCPCLプロトコルバージョンを使用するかを決定しようとします。 能動的エンティティーは常に最初に自身のコンタクトヘッダーを送信し、受動的エンティティーからのレスポンスを待ちます。 コンタクトの開始の間、能動的TCPCLエンティティーは、TCPCLピアに対する最初のセッションの試行で、最も高いTCPCLプロトコルバージョンを送信することになります（SHALL）。 能動的エンティティーが、そのTCPコネクション上で先に送信したものよりも低いプロトコルバージョンを持つコンタクトヘッダーを受信した場合、そのTCPコネクションをクローズすることになります（SHALL）。 能動的エンティティーが理由コード「Version mismatch」を持つSESS_TERMメッセージを受信した場合、そのエンティティーは、より以前のプロトコルバージョン番号を降順に使用して、ピアとのさらなるTCPCLセッションを試行してもよいです（MAY）。 このような複数のTCPCLセッションにまたがる状態の管理は、実装上の問題です。

If the passive entity receives a Contact Header containing a version that is not a version of the TCPCL protocol that the entity implements, then the entity SHALL send its Contact Header and immediately terminate the session with a reason code of "Version mismatch". If the passive entity receives a Contact Header with a version that is lower than the latest version of the protocol that the entity implements, the entity MAY either terminate the session (with a reason code of "Version mismatch") or adapt its operation to conform to the older version of the protocol. The decision of version fallback is an implementation matter.

受動的エンティティーが、そのエンティティーが実装しているTCPCLプロトコルのバージョンではないバージョンを含むコンタクトヘッダーを受信した場合、そのエンティティーは自身のコンタクトヘッダーを送信し、理由コード「Version mismatch」で直ちにセッションを終了することになります（SHALL）。 受動的エンティティーが、そのエンティティーが実装しているプロトコルの最新バージョンよりも低いバージョンを持つコンタクトヘッダーを受信した場合、エンティティーは（理由コード「Version mismatch」で）セッションを終了するか、古いバージョンのプロトコルに準拠するように動作を合わせるかのいずれかをしてもよいです（MAY）。 バージョンのフォールバックの判断は実装上の問題です。

The negotiated contact parameters defined by this specification are described in the following paragraphs.

この仕様で定義される、ネゴシエートされるコンタクトパラメーターについて、以下の段落で説明します。

TCPCL Version:
Both Contact Headers of a successful contact negotiation have identical TCPCL version numbers as described above. Only upon response of a Contact Header from the passive entity is the TCPCL protocol version established and session negotiation begun.
Enable TLS:

Negotiation of the Enable TLS parameter is performed by taking the logical AND of the two Contact Headers' CAN_TLS flags. A local security policy is then applied to determine whether the negotiated value of Enable TLS is acceptable. A reasonable security policy would require or disallow the use of TLS, depending upon the desired network flows. The RECOMMENDED policy is to require TLS for all sessions, even if security policy does not allow or require authentication. Because this state is negotiated over an unsecured medium, there is a risk of TLS Stripping as described in Section 7.4.

If the Enable TLS state is unacceptable, the entity SHALL terminate the session with a reason code of "Contact Failure". Note that this "Contact Failure" reason is different than a failure of a TLS handshake or TLS authentication after an agreed-upon and acceptable Enable TLS state. If the negotiated Enable TLS value is "true" and acceptable, then the TLS negotiation feature described in Section 4.4 begins immediately following the Contact Header exchange.

TCPCLバージョン：
コンタクトネゴシエーションが成功した場合、上で説明したように、両方のコンタクトヘッダーは同一のTCPCLバージョン番号を持ちます。 TCPCLプロトコルバージョンが確立され、セッションネゴシエーションが開始されるのは、受動的エンティティーからのコンタクトヘッダーのレスポンスがあったときだけです。
TLSの有効化（Enable TLS）：

Enable TLSパラメーターのネゴシエーションは、2つのコンタクトヘッダーのCAN_TLSフラグの論理積を取ることによって行われます。 次に、ローカルのセキュリティーポリシーを適用して、ネゴシエートされたEnable TLSの値が受け入れ可能かどうかを判断します。 妥当なセキュリティーポリシーでは、望ましいネットワークフローに応じて、TLSの使用を要求するか禁止するでしょう。 セキュリティーポリシーが認証を許可または要求しない場合であっても、すべてのセッションでTLSを要求するポリシーが推奨されます（RECOMMENDED）。 この状態は保護されていない媒体上でネゴシエートされるため、Section 7.4で説明するTLSストリッピングのリスクがあります。

Enable TLSの状態が受け入れられない場合、エンティティーは理由コード「Contact Failure」でセッションを終了することになります（SHALL）。 この「Contact Failure」という理由は、合意済みで受け入れ可能なEnable TLSの状態の後に発生するTLSハンドシェイクやTLS認証の失敗とは異なることに注意してください。 ネゴシエートされたEnable TLSの値が「true」であり、受け入れ可能である場合、Section 4.4で説明するTLSネゴシエーション機能が、コンタクトヘッダーの交換の直後に開始されます。

4.4. Session Security

4.4. セッションのセキュリティー

This version of the TCPCL protocol supports establishing a TLS session within an existing TCP connection. When TLS is used within the TCPCL, it affects the entire session. Once TLS is established, there is no mechanism available to downgrade the TCPCL session to non-TLS operation.

このバージョンのTCPCLプロトコルは、既存のTCPコネクション内でTLSセッションを確立することをサポートします。 TCPCL内でTLSを使用する場合、TLSはセッション全体に影響します。 TLSが確立されると、TCPCLセッションをTLSを使わない動作にダウングレードするメカニズムはありません。

Once established, the lifetime of a TLS connection SHALL be bound to the lifetime of the underlying TCP connection. Immediately prior to actively ending a TLS connection after TCPCL session termination, the peer that sent the original (non-reply) SESS_TERM message SHOULD follow the closure alert procedure provided in [RFC8446] to cleanly terminate the TLS connection. Because each TCPCL message is either fixed length or self-indicates its length, the lack of a TLS closure alert will not cause data truncation or corruption.

一度確立されると、TLSコネクションの有効期間は、下位のTCPコネクションの有効期間に連動することになります（SHALL）。 TCPCLセッションの終了後にTLSコネクションを能動的に終了する直前に、元の（返信ではない）SESS_TERMメッセージを送信したピアは、TLSコネクションをきれいに終了するために、[RFC8446]で示されているクロージャーアラートの手順に従うべきです（SHOULD）。 各TCPCLメッセージは固定長であるか、自身の長さを示すため、TLSのクロージャーアラートがなくてもデータの切り詰めや破損は生じません。

Subsequent TCPCL session attempts to the same passive entity MAY attempt to use the TLS session resumption feature. There is no guarantee that the passive entity will accept the request to resume a TLS session, and the active entity cannot assume any resumption outcome.

同じ受動的エンティティーへのその後のTCPCLセッションの試行では、TLSセッション再開機能の使用を試行してもよいです（MAY）。 受動的エンティティーがTLSセッションの再開要求を受け入れる保証はなく、能動的エンティティーはどのような再開の結果も想定できません。

4.4.1. Entity Identification

4.4.1. エンティティーの識別

The TCPCL uses TLS for certificate exchange in both directions to identify each entity and to allow each entity to authenticate its peer. Each certificate can potentially identify multiple entities, and there is no problem using such a certificate as long as the identifiers are sufficient to meet authentication policy (as described in later sections) for the entity that presents it.

TCPCLは、各エンティティーを識別し、各エンティティーがそのピアを認証できるようにするために、両方向の証明書の交換にTLSを使用します。 各証明書は複数のエンティティーを識別する可能性があり、その証明書を提示するエンティティーについて、識別子が（後のセクションで説明する）認証ポリシーを満たすのに十分である限り、そのような証明書を使用しても問題はありません。

Network Address:
If no stable DNS name is available but a stable network address is available and CA policy allows a certificate to contain an IPADDR-ID (as defined below), then one or more network addresses can be identified in the certificate.
ノードID：
理想的な証明書のアイデンティティーは、以下で定義するNODE-IDを使用した、エンティティーのノードIDです。 ノードIDが識別される場合、それより下位の識別が存在する必要はありません（ただし、存在してもかまいません。その場合は、それも検証されます）。
DNS名：
CAのポリシーにより、証明書に任意のNODE-IDを含めることは禁止されているものの、DNS-IDの識別は許可されている場合、1つ以上の安定したDNS名を証明書で識別できます。 ワイルドカードのDNS-IDの使用は、照合の規則が複雑であることと、ワイルドカード照合の実装サポートに依存することから、推奨されません（[RFC6125]のSection 6.4.3を参照）。
ネットワークアドレス：
安定したDNS名は利用できないものの、安定したネットワークアドレスが利用可能であり、CAのポリシーが証明書に（以下で定義する）IPADDR-IDを含めることを許可している場合、1つ以上のネットワークアドレスを証明書で識別できます。

This specification defines a NODE-ID of a certificate as being the subjectAltName entry of type otherName with a name form of BundleEID (see Section 4.4.2.1) and a value limited to a node ID. An entity SHALL ignore any entry of type otherName with a name form of BundleEID and a value that is some URI other than a node ID. The NODE-ID is similar to the URI-ID as defined in [RFC6125] but is restricted to a node ID rather than a URI with a qualified-name authority part. Unless specified otherwise by the definition of the URI scheme being authenticated, URI matching of a NODE-ID SHALL use the URI comparison logic provided in [RFC3986] and scheme-based normalization of those schemes specified in [RFC9171]. A URI scheme can refine this "exact match" logic with rules regarding how node IDs within that scheme are to be compared with the certificate-authenticated NODE-ID.

この仕様では、証明書のNODE-IDを、名前形式がBundleEID（Section 4.4.2.1を参照）であり、値がノードIDに限定された、otherName型のsubjectAltNameエントリーとして定義します。 エンティティーは、名前形式がBundleEIDであり、値がノードID以外の何らかのURIであるotherName型のエントリーを無視することになります（SHALL）。 NODE-IDは[RFC6125]で定義されているURI-IDに似ていますが、修飾名のオーソリティー部を持つURIではなく、ノードIDに制限されています。 認証されるURIスキームの定義で別段の規定がない限り、NODE-IDのURI照合では、[RFC3986]で示されているURI比較のロジックと、[RFC9171]で規定されているスキームのスキームベースの正規化を使用することになります（SHALL）。 URIスキームは、そのスキーム内のノードIDを証明書で認証されたNODE-IDとどのように比較するかに関する規則によって、この「完全一致」のロジックを改良できます。

This specification reuses the DNS-ID definition in Section 1.8 of [RFC6125], which is the subjectAltName entry of type dNSName whose value is encoded according to [RFC5280].

この仕様は、[RFC6125]のSection 1.8のDNS-IDの定義を再利用します。これは、値が[RFC5280]に従ってエンコードされた、dNSName型のsubjectAltNameエントリーです。

This specification defines an IPADDR-ID of a certificate as being the subjectAltName entry of type iPAddress whose value is encoded according to [RFC5280].

この仕様では、証明書のIPADDR-IDを、値が[RFC5280]に従ってエンコードされた、iPAddress型のsubjectAltNameエントリーとして定義します。

4.4.2. Certificate Profile for the TCPCL

4.4.2. TCPCLのための証明書プロファイル

All end-entity certificates used by a TCPCL entity SHALL conform to [RFC5280], or any updates or successors to that profile. When an end-entity certificate is supplied, the full certification chain SHOULD be included unless security policy indicates that is unnecessary. An entity SHOULD omit the root CA certificate (the last item of the chain) when sending a certification chain, as the recipient already has the root CA to anchor its validation.

TCPCLエンティティーが使用するすべてのエンドエンティティー証明書は、[RFC5280]、またはそのプロファイルの更新版や後継版に準拠することになります（SHALL）。 エンドエンティティー証明書を提供する場合、セキュリティーポリシーが不要であると示さない限り、完全な証明書チェーンを含めるべきです（SHOULD）。 受信者は自身の検証のアンカーとなるルートCAをすでに持っているため、エンティティーは証明書チェーンを送信する際に、ルートCA証明書（チェーンの最後の項目）を省略すべきです（SHOULD）。

The TCPCL requires version 3 certificates due to the extensions used by this profile. TCPCL entities SHALL reject as invalid version 1 and version 2 end-entity certificates.

このプロファイルで使用する拡張のために、TCPCLではバージョン3の証明書が必要です。 TCPCLエンティティーは、バージョン1とバージョン2のエンドエンティティー証明書を無効として拒否することになります（SHALL）。

TCPCL entities SHALL accept certificates that contain an empty Subject field or contain a Subject without a Common Name. Identity information in end-entity certificates is contained entirely in the subjectAltName extension as defined in Section 4.4.1 and discussed in the paragraphs below.

TCPCLエンティティーは、空のSubjectフィールドを含む証明書や、Common NameのないSubjectを含む証明書を受理することになります（SHALL）。 エンドエンティティー証明書のアイデンティティー情報は、Section 4.4.1で定義し、以下の段落で説明するように、すべてsubjectAltName拡張に含まれます。

All end-entity and CA certificates used for the TCPCL SHOULD contain both a subject key identifier and an authority key identifier extension in accordance with [RFC5280]. TCPCL entities SHOULD NOT rely on either a subject key identifier or an authority key identifier being present in any received certificate. Including key identifiers simplifies the work of an entity that needs to assemble a certification chain.

TCPCLに使用されるすべてのエンドエンティティー証明書とCA証明書には、[RFC5280]に従って、サブジェクト鍵識別子と認証局鍵識別子の拡張の両方を含めるべきです（SHOULD）。 TCPCLエンティティーは、受信した証明書にサブジェクト鍵識別子や認証局鍵識別子が存在することに依存すべきではありません（SHOULD NOT）。 鍵識別子を含めることにより、証明書チェーンを組み立てる必要があるエンティティーの作業が簡単になります。

Unless prohibited by CA policy, a TCPCL end-entity certificate SHALL contain a NODE-ID that authenticates the node ID of the peer. When assigned one or more stable DNS names, a TCPCL end-entity certificate SHOULD contain a DNS-ID that authenticates those (fully qualified) names. When assigned one or more stable network addresses, a TCPCL end-entity certificate MAY contain an IPADDR-ID that authenticates those addresses.

CAのポリシーで禁止されていない限り、TCPCLのエンドエンティティー証明書には、ピアのノードIDを認証するNODE-IDが含まれるようにすることになります（SHALL）。 1つ以上の安定したDNS名が割り当てられている場合、TCPCLのエンドエンティティー証明書には、それらの（完全修飾）名を認証するDNS-IDを含めるべきです（SHOULD）。 1つ以上の安定したネットワークアドレスが割り当てられている場合、TCPCLのエンドエンティティー証明書には、それらのアドレスを認証するIPADDR-IDを含めてもよいです（MAY）。

When allowed by CA policy, a Bundle Protocol Security (BPSec; see [RFC9172]) end-entity certificate SHOULD contain a PKIX Extended Key Usage (EKU) extension in accordance with Section 4.2.1.12 of [RFC5280]. When the PKIX EKU extension is present, it SHOULD contain the key purpose id-kp-bundleSecurity (see Section 4.4.2.1). Although not specifically required by the TCPCL, some networks or TLS implementations assume that id-kp-clientAuth and id-kp-serverAuth need to be used for the client side and the server side of TLS authentication, respectively. For interoperability, a TCPCL end-entity certificate MAY contain an EKU with both id-kp-clientAuth and id-kp-serverAuth values.

CAのポリシーで許可されている場合、バンドルプロトコルセキュリティー（BPSec。[RFC9172]を参照）のエンドエンティティー証明書には、[RFC5280]のSection 4.2.1.12に従って、PKIXの拡張鍵用途（Extended Key Usage; EKU）拡張を含めるべきです（SHOULD）。 PKIXのEKU拡張が存在する場合、それには鍵用途id-kp-bundleSecurity（Section 4.4.2.1を参照）を含めるべきです（SHOULD）。 TCPCLが特に要求するわけではありませんが、一部のネットワークやTLS実装では、TLS認証のクライアント側とサーバー側にそれぞれid-kp-clientAuthとid-kp-serverAuthを使用する必要があると想定しています。 相互運用性のために、TCPCLのエンドエンティティー証明書には、id-kp-clientAuthとid-kp-serverAuthの両方の値を持つEKUを含めてもよいです（MAY）。

When allowed by CA policy, a TCPCL end-entity certificate SHOULD contain a PKIX key usage extension in accordance with Section 4.2.1.3 of [RFC5280]. The PKIX key usage bit that is consistent with TCPCL security using TLS 1.3 is digitalSignature. The specific algorithms used during the TLS handshake will determine which of those key uses are exercised. Earlier versions of TLS can mandate the use of the keyEncipherment bit or the keyAgreement bit.

CAのポリシーで許可されている場合、TCPCLのエンドエンティティー証明書には、[RFC5280]のSection 4.2.1.3に従って、PKIXの鍵用途拡張を含めるべきです（SHOULD）。 TLS 1.3を使用したTCPCLのセキュリティーと整合するPKIXの鍵用途ビットはdigitalSignatureです。 TLSハンドシェイクの間に使用される具体的なアルゴリズムによって、それらの鍵用途のどれが行使されるかが決まります。 以前のバージョンのTLSでは、keyEnciphermentビットまたはkeyAgreementビットの使用が義務付けられる場合があります。

When allowed by CA policy, a TCPCL end-entity certificate SHOULD contain an Online Certificate Status Protocol (OCSP) URI within an authority information access extension in accordance with Section 4.2.2.1 of [RFC5280].

CAのポリシーで許可されている場合、TCPCLのエンドエンティティー証明書には、[RFC5280]のSection 4.2.2.1に従って、Authority Information Access拡張内にOnline Certificate Status Protocol（OCSP）のURIを含めるべきです（SHOULD）。

4.4.2.1. PKIX OID Allocations
4.4.2.1. PKIX OIDの割り当て

This document defines a PKIX Other Name Form identifier, id-on-bundleEID, in Appendix B; this identifier can be used as the type-id in a subjectAltName entry of type otherName. The BundleEID value associated with the otherName type-id id-on-bundleEID SHALL be a URI, encoded as an IA5String, with a scheme that is present in the IANA "Bundle Protocol URI Scheme Types" registry [IANA-BUNDLE]. Although this Other Name Form allows any endpoint ID to be present, the NODE-ID defined in Section 4.4.1 limits its use to contain only a node ID.

この文書では、Appendix BでPKIXのOther Name Form識別子id-on-bundleEIDを定義します。この識別子は、otherName型のsubjectAltNameエントリーにおけるtype-idとして使用できます。 otherNameのtype-id id-on-bundleEIDに関連付けられたBundleEIDの値は、IA5StringとしてエンコードされたURIとし、そのスキームはIANAの「Bundle Protocol URI Scheme Types」レジストリー[IANA-BUNDLE]に存在するものとすることになります（SHALL）。 このOther Name Formでは任意のエンドポイントIDが存在できますが、Section 4.4.1で定義したNODE-IDでは、その使用をノードIDのみを含むものに制限しています。

This document defines a PKIX EKU key purpose, id-kp-bundleSecurity, in Appendix B; this purpose can be used to restrict a certificate's use. The id-kp-bundleSecurity purpose can be combined with other purposes in the same certificate.

この文書では、Appendix BでPKIXのEKUの鍵用途id-kp-bundleSecurityを定義します。この用途は、証明書の使用を制限するために使用できます。 id-kp-bundleSecurityの用途は、同じ証明書内で他の用途と組み合わせることができます。

4.4.3. TLS Handshake

4.4.3. TLSハンドシェイク

The use of TLS is negotiated via the Contact Header, as described in Section 4.3. After negotiating an Enable TLS parameter of "true", and before any other TCPCL messages are sent within the session, the session entities SHALL begin a TLS handshake in accordance with [RFC8446]. By convention, this protocol uses the entity that initiated the underlying TCP connection (the active peer) as the "client" role of the TLS handshake request.

TLSの使用は、Section 4.3で説明したように、コンタクトヘッダーを介してネゴシエートされます。 Enable TLSパラメーターを「true」とネゴシエートした後、セッション内で他のTCPCLメッセージが送信される前に、セッションのエンティティーは[RFC8446]に従ってTLSハンドシェイクを開始することになります（SHALL）。 慣例により、このプロトコルでは、下位のTCPコネクションを開始したエンティティー（能動的ピア）を、TLSハンドシェイク要求の「クライアント」の役割として使用します。

The TLS handshake, if it occurs, is considered to be part of the contact negotiation before the TCPCL session itself is established. Specifics regarding exposure of sensitive data are discussed in Section 7.

TLSハンドシェイクが行われる場合、それはTCPCLセッション自体が確立される前の、コンタクトネゴシエーションの一部とみなされます。 機密データの露出に関する詳細については、Section 7で説明します。

The parameters within each TLS negotiation are implementation dependent but any TCPCL entity SHALL follow all recommended practices specified in BCP 195 [RFC7525], or any updates or successors that become part of BCP 195. Within each TLS handshake, the following requirements apply (using the rough order in which they occur):

各TLSネゴシエーション内のパラメーターは実装依存ですが、いずれのTCPCLエンティティーも、BCP 195[RFC7525]、またはBCP 195の一部となる更新版や後継版で規定されている推奨プラクティスにすべて準拠することになります（SHALL）。 各TLSハンドシェイク内では、次の要件が（おおむね発生する順に）適用されます。

ClientHello:

When a resolved DNS name was used to establish the TCP connection, the TLS ClientHello SHOULD include a "server_name" extension in accordance with [RFC6066]. When present, the server_name extension SHALL contain a "HostName" value taken from the DNS name (of the passive entity) that was resolved.

Note: The "HostName" in the server_name extension is the network name for the passive entity, not the node ID of that entity.

Server Certificate:
The passive entity SHALL supply a certificate within the TLS handshake to allow authentication of its side of the session. The supplied end-entity certificate SHALL conform to the profile described in Section 4.4.2. The passive entity MAY use the SNI DNS name to choose an appropriate server-side certificate that authenticates that DNS name.
Certificate Request:
During the TLS handshake, the passive entity SHALL request a client-side certificate.
Client Certificate:
The active entity SHALL supply a certificate chain within the TLS handshake to allow authentication of its side of the session. The supplied end-entity certificate SHALL conform to the profile described in Section 4.4.2.
ClientHello：

TCPコネクションを確立するために名前解決したDNS名を使用した場合、TLS ClientHelloには、[RFC6066]に従って「server_name」拡張を含めるべきです（SHOULD）。 server_name拡張が存在する場合、それには、名前解決した（受動的エンティティーの）DNS名から取得した「HostName」の値が含まれるようにすることになります（SHALL）。

注：server_name拡張内の「HostName」は、受動的エンティティーのネットワーク名であり、そのエンティティーのノードIDではありません。

サーバー証明書（Server Certificate）：
受動的エンティティーは、セッションの自身の側の認証を可能にするために、TLSハンドシェイク内で証明書を提供することになります（SHALL）。 提供するエンドエンティティー証明書は、Section 4.4.2で説明するプロファイルに準拠することになります（SHALL）。 受動的エンティティーは、SNIのDNS名を使用して、そのDNS名を認証する適切なサーバー側の証明書を選択してもよいです（MAY）。
証明書要求（Certificate Request）：
TLSハンドシェイクの間、受動的エンティティーはクライアント側の証明書を要求することになります（SHALL）。
クライアント証明書（Client Certificate）：
能動的エンティティーは、セッションの自身の側の認証を可能にするために、TLSハンドシェイク内で証明書チェーンを提供することになります（SHALL）。 提供するエンドエンティティー証明書は、Section 4.4.2で説明するプロファイルに準拠することになります（SHALL）。

If a TLS handshake cannot negotiate a TLS connection, both entities of the TCPCL session SHALL close the TCP connection. At this point, the TCPCL session has not yet been established, so there is no TCPCL session to terminate.

TLSハンドシェイクでTLSコネクションをネゴシエートできない場合、TCPCLセッションの両方のエンティティーはTCPコネクションをクローズすることになります（SHALL）。 この時点では、TCPCLセッションはまだ確立されていないため、終了すべきTCPCLセッションはありません。

After a TLS connection is successfully established, the active entity SHALL send a SESS_INIT message to begin session negotiation. This session negotiation and all subsequent messaging are secured.

TLSコネクションが正常に確立された後、能動的エンティティーは、セッションネゴシエーションを開始するためにSESS_INITメッセージを送信することになります（SHALL）。 このセッションネゴシエーションとそれ以降のすべてのメッセージングは保護されます。

4.4.4. TLS Authentication

4.4.4. TLS認証

Using PKIX certificates exchanged during the TLS handshake, each of the entities can authenticate a peer node ID directly or authenticate the peer DNS name or network address. The logic for handling certificates and certificate data is separated into the following phases:

TLSハンドシェイクの間に交換されたPKIX証明書を使用して、各エンティティーは、ピアのノードIDを直接認証するか、ピアのDNS名やネットワークアドレスを認証できます。 証明書と証明書データを処理するロジックは、次の段階に分けられます。

  1. Validating the certification path from the end-entity certificate up to a trusted root CA.
  2. Validating the EKU and other properties of the end-entity certificate.
  3. Authenticating identities from a valid end-entity certificate.
  4. Applying security policy to the result of each identity type authentication.
  1. エンドエンティティー証明書から信頼できるルートCAまでの証明書パスを検証する。
  2. エンドエンティティー証明書のEKUとその他の性質を検証する。
  3. 有効なエンドエンティティー証明書からアイデンティティーを認証する。
  4. 各アイデンティティータイプの認証の結果にセキュリティーポリシーを適用する。

The result of validating a peer identity (see Section 4.4.1) against one or more types of certificate claims is one of the following:

1つ以上のタイプの証明書のクレームに対してピアのアイデンティティー（Section 4.4.1を参照）を検証した結果は、次のいずれかです。

Absent:
Indicating that no such claims are present in the certificate and the identity cannot be authenticated.
Success:
Indicating that one or more such claims are present and at least one matches the peer identity value.
Failure:
Indicating that one or more such claims are present and none match the peer identity.
不在（Absent）：
そのようなクレームが証明書に存在せず、アイデンティティーを認証できないことを示します。
成功（Success）：
そのようなクレームが1つ以上存在し、少なくとも1つがピアのアイデンティティーの値と一致することを示します。
失敗（Failure）：
そのようなクレームが1つ以上存在し、どれもピアのアイデンティティーと一致しないことを示します。
4.4.4.1. Certificate Path and Purpose Validation
4.4.4.1. 証明書パスと用途の検証

For any peer end-entity certificate received during the TLS handshake, the entity SHALL perform the certification path validation described in [RFC5280] up to one of the entity's trusted CA certificates. If enabled by local policy, the entity SHALL perform an OCSP check of each certificate providing OCSP authority information in accordance with [RFC6960]. If certificate validation fails or if security policy disallows a certificate for any reason, the entity SHALL fail the TLS handshake with a "bad_certificate" alert. Leaving out part of the certification chain can cause the entity to fail to validate a certificate if the certificates that were left out are unknown to the entity (see Section 7.6).

TLSハンドシェイクの間に受信したピアのエンドエンティティー証明書について、エンティティーは、[RFC5280]で説明されている証明書パスの検証を、エンティティーの信頼できるCA証明書のいずれかまで実行することになります（SHALL）。 ローカルポリシーで有効になっている場合、エンティティーは、[RFC6960]に従って、OCSPの認証局情報を提供する各証明書のOCSPチェックを実行することになります（SHALL）。 証明書の検証が失敗した場合や、セキュリティーポリシーが何らかの理由で証明書を許可しない場合、エンティティーは「bad_certificate」アラートでTLSハンドシェイクを失敗することになります（SHALL）。 証明書チェーンの一部を省略すると、省略された証明書をエンティティーが知らない場合に、エンティティーが証明書の検証に失敗する可能性があります（Section 7.6を参照）。

For the end-entity peer certificate received during the TLS handshake, the entity SHALL apply security policy to the key usage extension (if present) and EKU extension (if present) in accordance with Sections 4.2.1.12 and 4.2.1.3 of [RFC5280], respectively, and with the profile discussed in Section 4.4.2 of this document.

TLSハンドシェイクの間に受信したピアのエンドエンティティー証明書について、エンティティーは、鍵用途拡張（存在する場合）とEKU拡張（存在する場合）に対して、それぞれ[RFC5280]のセクション4.2.1.12とセクション4.2.1.3に従い、かつこの文書のSection 4.4.2で説明したプロファイルに従って、セキュリティーポリシーを適用することになります（SHALL）。

4.4.4.2. Network-Level Authentication
4.4.4.2. ネットワークレベルの認証

Either during or immediately after the TLS handshake, each entity, if required by security policy, SHALL validate the following certificate identifiers together in accordance with Section 6 of [RFC6125]:

TLSハンドシェイクの間、またはその直後に、セキュリティーポリシーで要求されている場合、各エンティティーは、[RFC6125]のSection 6に従って、次の証明書識別子をまとめて検証することになります（SHALL）。

  • If the active entity resolved a DNS name (of the passive entity) in order to initiate the TCP connection, that DNS name SHALL be used as a DNS-ID reference identifier.
  • The IP address of the other side of the TCP connection SHALL be used as an IPADDR-ID reference identifier.
  • 能動的エンティティーが、TCPコネクションを開始するために（受動的エンティティーの）DNS名を名前解決した場合、そのDNS名をDNS-IDの参照識別子として使用することになります（SHALL）。
  • TCPコネクションの相手側のIPアドレスを、IPADDR-IDの参照識別子として使用することになります（SHALL）。

If the network-level identifier's authentication result is Failure or if the result is Absent and security policy requires an authenticated network-level identifier, the entity SHALL terminate the session (with a reason code of "Contact Failure").

ネットワークレベルの識別子の認証結果がFailureである場合、または結果がAbsentであり、セキュリティーポリシーが認証済みのネットワークレベルの識別子を要求している場合、エンティティーは（理由コード「Contact Failure」で）セッションを終了することになります（SHALL）。

4.4.4.3. Node ID Authentication
4.4.4.3. ノードIDの認証

Immediately before session parameter negotiation, each entity, if required by security policy, SHALL validate the certificate NODE-ID in accordance with Section 6 of [RFC6125] using the node ID of the peer's SESS_INIT message as the NODE-ID reference identifier. If the NODE-ID validation result is Failure or if the result is Absent and security policy requires an authenticated node ID, the entity SHALL terminate the session (with a reason code of "Contact Failure").

4.4.5. Policy Recommendations

A RECOMMENDED security policy encompasses the following:

  • enabling the use of OCSP checking during the TLS handshake.
  • instructing that, if an EKU extension is present, the extension needs to contain id-kp-bundleSecurity (Section 4.4.2.1) to be usable with TCPCL security.
  • requiring a validated node ID (Section 4.4.4.3) and ignoring any network-level identifier (Section 4.4.4.2).
  • TLSハンドシェイクの間のOCSPチェックの使用を有効にする。

  • 検証済みのノードID（Section 4.4.4.3）を要求し、ネットワークレベルの識別子（Section 4.4.4.2）はすべて無視する。

This policy relies on and informs the certificate requirements provided in Section 4.4.3. This policy assumes that a DTN-aware CA (see Section 3.4) will only issue a certificate for a node ID when it has verified that the private key holder actually controls the bundle node; this is needed to avoid the threat identified in Section 7.9. This policy requires that a certificate contain a NODE-ID and allows the certificate to also contain network-level identifiers. A tailored policy on a more controlled network could relax the requirement on node ID validation and allow just network-level identifiers to authenticate a peer.

このポリシーは、Section 4.4.3で示した証明書の要件に依存し、またその要件の根拠となります。 このポリシーは、DTNを認識するCA（Section 3.4を参照）が、秘密鍵の保有者が実際にそのバンドルノードを制御していることを検証した場合にのみ、ノードIDに対する証明書を発行することを前提としています。これは、Section 7.9で特定した脅威を避けるために必要です。 このポリシーでは、証明書にNODE-IDが含まれていることを要求し、証明書にネットワークレベルの識別子も含めることを許可します。 より管理されたネットワーク上で調整されたポリシーでは、ノードIDの検証の要件を緩和し、ネットワークレベルの識別子だけでピアを認証できるようにすることも考えられます。

4.7. Session Parameter Negotiation

4.7. セッションパラメーターのネゴシエーション

An entity calculates the parameters for a TCPCL session by negotiating the values from its own preferences (conveyed by the SESS_INIT it sent to the peer) with the preferences of the peer entity (expressed in the SESS_INIT that it received from the peer). The negotiated parameters defined by this specification are described in the following paragraphs.

エンティティーは、（ピアに送信したSESS_INITで伝えた）自身の希望値と、（ピアから受信したSESS_INITで表された）ピアエンティティーの希望値から値をネゴシエートすることにより、TCPCLセッションのパラメーターを計算します。 この仕様で定義される、ネゴシエートされるパラメーターについて、以下の段落で説明します。

Transfer MTU and Segment MTU:
The Maximum Transmission Unit (MTU) for whole transfers and individual segments is identical to the Transfer MRU and Segment MRU, respectively, of the received SESS_INIT message. A transmitting peer can send individual segments with any size smaller than the Segment MTU, depending on local policy, dynamic network conditions, etc. Determining the size of each transmitted segment is an implementation matter. If either the Transfer MRU or Segment MRU is unacceptable, the entity SHALL terminate the session with a reason code of "Contact Failure".
Session Keepalive:

Negotiation of the Session Keepalive parameter is performed by taking the minimum of the two Keepalive Interval values from the two SESS_INIT messages. The Session Keepalive Interval is a parameter for the behavior described in Section 5.1.1. If the Session Keepalive Interval is unacceptable, the entity SHALL terminate the session with a reason code of "Contact Failure".

Note: A negotiated Session Keepalive of zero indicates that KEEPALIVEs are disabled.

転送MTUとセグメントMTU：
転送全体と個々のセグメントの最大転送単位（MTU）は、受信したSESS_INITメッセージの転送MRUとセグメントMRUにそれぞれ等しくなります。 送信側のピアは、ローカルポリシーや動的なネットワークの状態などに応じて、セグメントMTUより小さい任意のサイズで個々のセグメントを送信できます。 送信する各セグメントのサイズの決定は実装上の問題です。 転送MRUとセグメントMRUのいずれかが受け入れられない場合、エンティティーは理由コード「Contact Failure」でセッションを終了することになります（SHALL）。
Session Keepalive：

Session Keepaliveパラメーターのネゴシエーションは、2つのSESS_INITメッセージにある2つのKeepalive Intervalの値の最小値を取ることによって行われます。 Session Keepalive Intervalは、Section 5.1.1で説明する振る舞いのためのパラメーターです。 Session Keepalive Intervalが受け入れられない場合、エンティティーは理由コード「Contact Failure」でセッションを終了することになります（SHALL）。

注：ネゴシエートされたSession Keepaliveが0の場合は、KEEPALIVEが無効であることを示します。

Once this process of parameter negotiation is completed, this protocol defines no additional mechanism to change the parameters of an established session; to effect such a change, the TCPCL session MUST be terminated and a new session established.

このパラメーターのネゴシエーションの処理が完了すると、このプロトコルでは、確立済みのセッションのパラメーターを変更するための追加のメカニズムは定義されていません。そのような変更を行うには、TCPCLセッションを終了し、新しいセッションを確立しなければなりません（MUST）。

5. Established Session Operation

5. 確立済みのセッションの動作

This section describes the protocol operation for the duration of an established session, including the mechanism for transmitting bundles over the session.

このセクションでは、セッション上でバンドルを送信するメカニズムを含め、確立済みのセッションの期間中のプロトコルの動作について説明します。

5.1. Upkeep and Status Messages

5.1. 維持とステータスのメッセージ

5.1.1. Session Upkeep (KEEPALIVE)

5.1.1. セッションの維持（KEEPALIVE）

The protocol includes a provision for transmission of KEEPALIVE messages over the TCPCL session to help determine if the underlying TCP connection has been disrupted.

このプロトコルには、下位のTCPコネクションが途絶したかどうかを判断するのに役立てるため、TCPCLセッション上でKEEPALIVEメッセージを送信する規定が含まれています。

As described in Section 4.7, a negotiated parameter of each session is the Session Keepalive Interval. If the negotiated Session Keepalive is zero (i.e., one or both SESS_INIT messages contain a zero Keepalive Interval), then the keepalive feature is disabled. There is no logical minimum value for the Keepalive Interval (within the minimum imposed by the positive-value encoding), but when used for many sessions on an open, shared network, a short interval could lead to excessive traffic. For shared network use, entities SHOULD choose a Keepalive Interval no shorter than 30 seconds. There is no logical maximum value for the Keepalive Interval (within the maximum imposed by the fixed-size encoding), but an idle TCP connection is liable for closure by the host operating system if the keepalive time is longer than tens of minutes. Entities SHOULD choose a Keepalive Interval no longer than 10 minutes (600 seconds).

Section 4.7で説明したように、各セッションのネゴシエートされるパラメーターの1つはSession Keepalive Intervalです。 ネゴシエートされたSession Keepaliveが0の場合（つまり、一方または両方のSESS_INITメッセージのKeepalive Intervalが0の場合）、キープアライブ機能は無効になります。 Keepalive Intervalには（正の値のエンコーディングによって課される最小値の範囲内で）論理的な最小値はありませんが、オープンな共有ネットワーク上の多数のセッションで使用すると、短い間隔は過剰なトラフィックにつながる可能性があります。 共有ネットワークで使用する場合、エンティティーは30秒以上のKeepalive Intervalを選択すべきです（SHOULD）。 Keepalive Intervalには（固定サイズのエンコーディングによって課される最大値の範囲内で）論理的な最大値はありませんが、キープアライブの時間が数十分より長い場合、アイドル状態のTCPコネクションはホストのオペレーティングシステムによってクローズされるおそれがあります。 エンティティーは10分（600秒）以下のKeepalive Intervalを選択すべきです（SHOULD）。

The chosen Keepalive Interval SHOULD NOT be too short, as TCP retransmissions may occur in the case of packet loss. Those will have to be triggered by a timeout (TCP retransmission timeout (RTO)), which is dependent on the measured RTT for the TCP connection so that KEEPALIVE messages can experience noticeable latency.

パケット損失の場合にTCPの再送が発生する可能性があるため、選択するKeepalive Intervalを短くしすぎるべきではありません（SHOULD NOT）。 それらの再送はタイムアウト（TCPの再送タイムアウト（RTO））によって引き起こされる必要があり、このタイムアウトはTCPコネクションの測定されたRTTに依存するため、KEEPALIVEメッセージに顕著な遅延が生じる可能性があります。

The format of a KEEPALIVE message is a one-octet Message Type code of KEEPALIVE (as described in Table 2) with no additional data. Both sides SHALL send a KEEPALIVE message whenever the negotiated interval has elapsed with no transmission of any message (KEEPALIVE or other).

KEEPALIVEメッセージの形式は、（Table 2で説明する）KEEPALIVEの1オクテットのMessage Typeコードであり、追加のデータはありません。 両側は、（KEEPALIVEやその他の）メッセージを一切送信しないままネゴシエートされた間隔が経過するたびに、KEEPALIVEメッセージを送信することになります（SHALL）。

If no message (KEEPALIVE or other) has been received in a session after some implementation-defined time duration, then the entity SHALL terminate the session by transmitting a SESS_TERM message (as described in Section 6.1) with a reason code of "Idle timeout". If configurable, the idle timeout duration SHOULD be no shorter than twice the Keepalive Interval. If not configurable, the idle timeout duration SHOULD be exactly twice the Keepalive Interval.

5.2. Bundle Transfer

5.2. バンドルの転送

All of the messages discussed in this section are directly associated with transferring a bundle between TCPCL entities.

このセクションで説明するメッセージはすべて、TCPCLエンティティー間のバンドルの転送に直接関連しています。

A single TCPCL transfer results in the exchange of a bundle (handled by the convergence layer as opaque data) between two entities. In the TCPCL, a transfer is accomplished by dividing a single bundle up into "segments" based on the receiving-side Segment MRU, which is defined in Section 4.6. The choice of the length to use for segments is an implementation matter, but each segment MUST NOT be larger than the receiving entity's Segment MRU. The first segment for a bundle is indicated by the START flag, and the last segment is indicated by the END flag.

単一のTCPCL転送の結果、2つのエンティティー間で（コンバージェンス層によって不透明なデータとして扱われる）バンドルが交換されます。 TCPCLでは、Section 4.6で定義する受信側のセグメントMRUに基づいて、単一のバンドルを「セグメント」に分割することで転送を行います。 セグメントに使用する長さの選択は実装上の問題ですが、各セグメントは受信側エンティティーのセグメントMRUより大きくしてはなりません（MUST NOT）。 バンドルの最初のセグメントはSTARTフラグによって示され、最後のセグメントはENDフラグによって示されます。

A single transfer (and, by extension, a single segment) SHALL NOT contain data of more than a single bundle. This requirement is imposed on the agent using the TCPCL, rather than on the TCPCL itself.

単一の転送（ひいては単一のセグメント）に複数のバンドルのデータを格納することはありません（SHALL NOT）。 この要件は、TCPCL自体ではなく、TCPCLを使用するエージェントに課されます。

If multiple bundles are transmitted on a single TCPCL connection, they MUST be transmitted consecutively, without the interleaving of segments from multiple bundles.

単一のTCPCLコネクション上で複数のバンドルを送信する場合、複数のバンドルのセグメントをインターリーブせずに、連続して送信しなければなりません（MUST）。

5.2.1. Bundle Transfer ID

5.2.1. バンドル転送ID

Each of the bundle transfer messages contains a Transfer ID, which is used to correlate messages (from both sides of a transfer) for each bundle. A Transfer ID does not attempt to address uniqueness of the bundle data itself and is not related to such concepts as bundle fragmentation. Each invocation of the TCPCL by the BPA, requesting transmission of a bundle (fragmentary or otherwise), results in the initiation of a single TCPCL transfer. Each transfer entails the sending of a sequence of some number of XFER_SEGMENT and XFER_ACK messages; all are correlated by the same Transfer ID. The sending entity originates a Transfer ID, and the receiving entity uses that same Transfer ID in acknowledgments.

各バンドル転送メッセージには、各バンドルについて（転送の両側からの）メッセージを関連付けるために使用されるTransfer IDが含まれています。 Transfer IDは、バンドルデータ自体の一意性を扱おうとするものではなく、バンドルの断片化といった概念とは関係ありません。 BPAが（フラグメントであるかどうかにかかわらず）バンドルの送信を要求してTCPCLを呼び出すたびに、単一のTCPCL転送が開始されます。 各転送では、いくつかのXFER_SEGMENTメッセージとXFER_ACKメッセージの系列が送信され、それらはすべて同じTransfer IDによって関連付けられます。 送信側エンティティーがTransfer IDを発信し、受信側エンティティーは確認応答でその同じTransfer IDを使用します。

Transfer IDs from each entity SHALL be unique within a single TCPCL session. Upon exhaustion of the entire 64-bit Transfer ID space, the sending entity SHALL terminate the session with a SESS_TERM reason code of "Resource Exhaustion". For bidirectional bundle transfers, a TCPCL entity SHOULD NOT rely on any relationship between Transfer IDs originating from each side of the TCPCL session.

各エンティティーからのTransfer IDは、単一のTCPCLセッション内で一意にすることになります（SHALL）。 64ビットのTransfer ID空間全体を使い果たした場合、送信側エンティティーはSESS_TERMの理由コード「Resource Exhaustion」でセッションを終了することになります（SHALL）。 双方向のバンドル転送の場合、TCPCLエンティティーは、TCPCLセッションのそれぞれの側から発信されたTransfer ID間の関係に依存すべきではありません（SHOULD NOT）。

Although there is not a strict requirement for initial Transfer ID values or the ordering of Transfer IDs (see Section 7.13), in the absence of any other mechanism for generating Transfer IDs, an entity SHALL use the following algorithm: the initial Transfer ID from each entity is zero, and subsequent Transfer ID values are incremented from the prior Transfer ID value by one.

5.2.3. Data Acknowledgments (XFER_ACK)

5.2.3. データの確認応答（XFER_ACK）

Although the TCP transport provides reliable transfer of data between transport peers, the typical BSD sockets interface provides no means to inform a sending application of when the receiving application has processed some amount of transmitted data. 5.2.4. Transfer Refusal (XFER_REFUSE)

5.2.4. 転送の拒否（XFER_REFUSE）

The TCPCL supports a mechanism by which a receiving entity can indicate to the sender that it does not want to receive the corresponding bundle. To do so, upon receiving a XFER_SEGMENT message, the entity MAY transmit a XFER_REFUSE message. As data segments and acknowledgments can cross on the wire, the bundle that is being refused SHALL be identified by the Transfer ID of the refusal.

TCPCLは、受信側エンティティーが、対応するバンドルを受信したくないことを送信者に示せるメカニズムをサポートします。 そのために、XFER_SEGMENTメッセージを受信したとき、エンティティーはXFER_REFUSEメッセージを送信してもよいです（MAY）。 データセグメントと確認応答は通信路上ですれ違う可能性があるため、拒否されるバンドルは、拒否のTransfer IDによって識別することになります（SHALL）。

There is no required relationship between the Transfer MRU of a TCPCL entity (which is supposed to represent a firm limitation of what the entity will accept) and the sending of a XFER_REFUSE message. A XFER_REFUSE can be used in cases where the agent's bundle storage is temporarily depleted or somehow constrained. A XFER_REFUSE can also be used after the bundle header or any bundle data is inspected by an agent and determined to be unacceptable.

TCPCLエンティティーの転送MRU（エンティティーが受け入れるものについての確固たる制限を表すことになっています）と、XFER_REFUSEメッセージの送信との間に、必須の関係はありません。 XFER_REFUSEは、エージェントのバンドルストレージが一時的に枯渇している場合や、何らかの制約を受けている場合に使用できます。 XFER_REFUSEは、エージェントがバンドルヘッダーやバンドルデータを調べて、受け入れられないと判断した後にも使用できます。

A transfer receiver MAY send a XFER_REFUSE message as soon as it receives any XFER_SEGMENT message. The transfer sender MUST be prepared for this and MUST associate the refusal with the correct bundle via the Transfer ID fields.

6. Session Termination

6. セッションの終了

This section describes the procedures for terminating a TCPCL session. The purpose of terminating a session is to allow transfers to complete before the TCP connection is closed but not allow any new transfers to start. A session state change is necessary for this to happen, because transfers can be in progress in either direction (transfer stream) within a session. Waiting for a transfer to complete in one direction does not control or influence the possibility of a transfer in the other direction. Either peer of a session can terminate an established session at any time.

このセクションでは、TCPCLセッションを終了するための手順について説明します。 セッションを終了する目的は、TCPコネクションを閉じる前に転送を完了させつつ、新しい転送は開始させないことです。 セッション内ではどちらの方向（転送ストリーム）でも転送が進行中である可能性があるため、これを実現するにはセッション状態の変化が必要です。 一方の方向で転送の完了を待っても、もう一方の方向での転送の可能性を制御したり、それに影響を与えたりすることはありません。 セッションのどちらのピアも、確立済みのセッションをいつでも終了できます。

6.1. Session Termination Message (SESS_TERM)

6.1. セッション終了メッセージ（SESS_TERM）

To cleanly terminate a session, a SESS_TERM message SHALL be transmitted by either entity at any point following complete transmission of any other message. When sent to initiate a termination, the REPLY flag of a SESS_TERM message SHALL be 0. Upon receiving a SESS_TERM message after not sending a SESS_TERM message in the same session, an entity SHALL send an acknowledging SESS_TERM message. When sent to acknowledge a termination, a SESS_TERM message SHALL have identical data content from the message being acknowledged except for the REPLY flag, which is set to 1 to indicate acknowledgment.

セッションをきれいに終了するには、他のメッセージの送信が完了した後の任意の時点で、どちらかのエンティティーがSESS_TERMメッセージを送信することになります（SHALL）。 終了を開始するために送信する場合、SESS_TERMメッセージのREPLYフラグは0とすることになります（SHALL）。 同じセッションでSESS_TERMメッセージを送信していない状態でSESS_TERMメッセージを受信した場合、エンティティーは確認応答のSESS_TERMメッセージを送信することになります（SHALL）。 終了を確認応答するために送信する場合、SESS_TERMメッセージは、確認応答を示すために1に設定するREPLYフラグを除いて、確認応答するメッセージと同一のデータ内容を持つようにすることになります（SHALL）。

Once a SESS_TERM message is sent, the state of that TCPCL session changes to Ending. While the session is in the Ending state,

SESS_TERMメッセージが送信されると、そのTCPCLセッションの状態はEndingに変化します。 セッションがEnding状態にある間は、

  • an entity MAY finish an in-progress transfer in either direction.
  • an entity SHALL NOT begin any new outgoing transfer for the remainder of the session.
  • an entity SHALL NOT accept any new incoming transfer for the remainder of the session.
  • エンティティーは、どちらの方向の進行中の転送も完了してもよいです（MAY）。
  • エンティティーは、セッションの残りの期間、新しい送信方向の転送を開始することはありません（SHALL NOT）。
  • エンティティーは、セッションの残りの期間、新しい受信方向の転送を受理することはありません（SHALL NOT）。

If a new incoming transfer is attempted while in the Ending state, the receiving entity SHALL send a XFER_REFUSE with a reason code of "Session Terminating".

Ending状態の間に新しい受信方向の転送が試みられた場合、受信側エンティティーは理由コード「Session Terminating」を持つXFER_REFUSEを送信することになります（SHALL）。

There are circumstances where an entity has an urgent need to close a TCP connection associated with a TCPCL session, without waiting for transfers to complete but also in a way that doesn't force timeouts to occur -- for example, due to impending shutdown of the underlying data-link layer. Instead of following a clean termination sequence, after transmitting a SESS_TERM message, an entity MAY perform an unclean termination by immediately closing the associated TCP connection. When performing an unclean termination, an entity SHOULD acknowledge all received XFER_SEGMENTs with a XFER_ACK before closing the TCP connection. Not acknowledging received segments can result in unnecessary bundle or bundle fragment retransmissions. Any delay between a request to close the TCP connection and the actual closing of the connection (a "half-closed" state) MAY be ignored by the TCPCL entity. If the underlying TCP connection is closed during a transmission (in either transfer stream), the transfer SHALL be indicated to the BPA as failed (see the transmission failure and reception failure indications defined in Section 3.1).

エンティティーが、転送の完了を待たずに、しかしタイムアウトを強制的に発生させない方法で、TCPCLセッションに関連付けられたTCPコネクションを緊急に閉じる必要がある状況があります。たとえば、下位のデータリンク層のシャットダウンが差し迫っている場合です。 きれいな終了シーケンスに従う代わりに、SESS_TERMメッセージを送信した後、エンティティーは関連するTCPコネクションを直ちに閉じることで、きれいでない終了を実行してもよいです（MAY）。 きれいでない終了を実行する場合、エンティティーは、TCPコネクションを閉じる前に、受信したすべてのXFER_SEGMENTをXFER_ACKで確認応答すべきです（SHOULD）。 受信したセグメントを確認応答しないと、バンドルやバンドルのフラグメントの不要な再送が発生する可能性があります。 TCPコネクションを閉じる要求と実際にコネクションが閉じられるまでの間の遅延（「ハーフクローズ」状態）は、TCPCLエンティティーが無視してもよいです（MAY）。 （どちらかの転送ストリームで）送信中に下位のTCPコネクションが閉じられた場合、その転送は失敗としてBPAに通知することになります（SHALL）（Section 3.1で定義した送信の失敗と受信の失敗の通知を参照）。

The TCPCL itself does not have any required behavior related to responding to a SESS_TERM based on its reason code; the termination is passed up as an indication to the BPA that the session state has changed. If a termination has a reason code that is not decodable to the BPA, the agent SHOULD treat the termination as having a reason code of "Unknown".

TCPCL自体には、理由コードに基づいてSESS_TERMに応答することに関する必須の振る舞いはありません。終了は、セッション状態が変化したことを示すものとしてBPAに渡されます。 終了が、BPAがデコードできない理由コードを持つ場合、エージェントは、その終了を理由コード「Unknown」を持つものとして扱うべきです（SHOULD）。

If a session is to be terminated before the sending of a protocol message has completed, then the entity MUST NOT transmit the SESS_TERM message but still SHALL close the TCP connection. Each TCPCL message is contiguous in the octet stream and has no ability to be cut short and/or preempted by another message. This is particularly important when large segment sizes are being transmitted; either the entire XFER_SEGMENT is sent before a SESS_TERM message or the connection is simply terminated mid-XFER_SEGMENT.

プロトコルメッセージの送信が完了する前にセッションを終了する場合、エンティティーはSESS_TERMメッセージを送信してはなりません（MUST NOT）。ただし、その場合もTCPコネクションはクローズすることになります（SHALL）。 各TCPCLメッセージはオクテットストリーム内で連続しており、途中で切り詰めたり、別のメッセージによって割り込まれたりすることはできません。 これは、大きなセグメントサイズで送信している場合に特に重要です。SESS_TERMメッセージの前にXFER_SEGMENT全体を送信するか、XFER_SEGMENTの途中で単にコネクションを終了するかのいずれかになります。

6.2. Idle Session Termination

6.2. アイドルセッションの終了

The protocol includes a provision for clean termination of idle sessions. Determining the length of time to wait before terminating idle sessions, if they are to be terminated at all, is an implementation and configuration matter.

このプロトコルには、アイドル状態のセッションをきれいに終了するための規定が含まれています。 アイドル状態のセッションを終了する前に待つ時間の長さの決定（そもそも終了するかどうかも含めて）は、実装と設定の問題です。

If there is a configured time to terminate idle sessions and if no TCPCL messages (other than KEEPALIVE messages) have been received for at least that amount of time, then either entity MAY terminate the session by transmitting a SESS_TERM message with a reason code of "Idle timeout" (as described in Table 9).

アイドル状態のセッションを終了する時間が設定されており、少なくともその時間の間に（KEEPALIVEメッセージ以外の）TCPCLメッセージを受信しなかった場合、どちらのエンティティーも、（Table 9で説明する）理由コード「Idle timeout」を持つSESS_TERMメッセージを送信することによって、セッションを終了してもよいです（MAY）。

7. Security Considerations

7. セキュリティーに関する考慮事項

This section separates security considerations into threat categories based on guidance provided in BCP 72 [RFC3552].

このセクションでは、BCP 72[RFC3552]で示されているガイダンスに基づいて、セキュリティーに関する考慮事項を脅威のカテゴリーに分けて説明します。

7.1. Threat: Passive Leak of Node Data

7.1. 脅威：ノードデータの受動的な漏洩

When used without TLS security, the TCPCL exposes the node ID and other configuration data to passive eavesdroppers. This occurs even when no transfers occur within a TCPCL session. This can be avoided by always using TLS, even if authentication is not available (see Section 7.12).

TLSセキュリティーなしで使用する場合、TCPCLは、ノードIDやその他の設定データを受動的な盗聴者に露出します。 これは、TCPCLセッション内で転送が行われない場合でも発生します。 これは、認証が利用できない場合でも、常にTLSを使用することで避けられます（Section 7.12を参照）。

7.2. Threat: Passive Leak of Bundle Data

7.2. 脅威：バンドルデータの受動的な漏洩

The TCPCL can be used to provide point-to-point transport security, but it does not provide security of data at rest and does not guarantee end-to-end bundle security. The bundle security mechanisms defined in [RFC9172] are to be used instead.

TCPCLはポイントツーポイントのトランスポートセキュリティーを提供するために使用できますが、保存されたデータのセキュリティーは提供せず、エンドツーエンドのバンドルセキュリティーも保証しません。 代わりに、[RFC9172]で定義されているバンドルセキュリティーのメカニズムを使用します。

When used without TLS security, the TCPCL exposes all bundle data to passive eavesdroppers. This can be avoided by always using TLS, even if authentication is not available (see Section 7.12).

TLSセキュリティーなしで使用する場合、TCPCLは、すべてのバンドルデータを受動的な盗聴者に露出します。 これは、認証が利用できない場合でも、常にTLSを使用することで避けられます（Section 7.12を参照）。

7.3. Threat: TCPCL Version Downgrade

7.3. 脅威：TCPCLバージョンのダウングレード

When a TCPCL entity supports multiple versions of the protocol, it is possible for a malicious or misconfigured peer to use an older version of the TCPCL protocol that does not support transport security. An on-path attacker can also manipulate a Contact Header to present a lower protocol version than desired.

TCPCLエンティティーがプロトコルの複数のバージョンをサポートしている場合、悪意のあるピアや設定を誤ったピアが、トランスポートセキュリティーをサポートしない古いバージョンのTCPCLプロトコルを使用する可能性があります。 経路上の攻撃者が、コンタクトヘッダーを操作して、望ましいものよりも低いプロトコルバージョンを提示させることもできます。

It is up to security policies within each TCPCL entity to ensure that the negotiated TCPCL version meets transport security requirements.

ネゴシエートされたTCPCLバージョンがトランスポートセキュリティーの要件を満たすことを保証するのは、各TCPCLエンティティー内のセキュリティーポリシーの役割です。

7.4. Threat: Transport Security Stripping

7.4. 脅威：トランスポートセキュリティーのストリッピング

When security policy allows non-TLS sessions, the TCPCL does not protect against active network attackers. It is possible for an on-path attacker to set the CAN_TLS flag to 0 on either side of the Contact Header exchange, which will cause the negotiation discussed in Section 4.3 to disable TLS. This leads to the "SSL Stripping" attack described in [RFC7457].

セキュリティーポリシーがTLSを使わないセッションを許可している場合、TCPCLは能動的なネットワーク攻撃者から保護されません。 経路上の攻撃者は、コンタクトヘッダーの交換のどちらの側でもCAN_TLSフラグを0に設定でき、これによりSection 4.3で説明したネゴシエーションでTLSが無効になります。 これにより、[RFC7457]で説明されている「SSLストリッピング」攻撃が生じます。

The purpose of the CAN_TLS flag is to allow the use of the TCPCL on entities that simply do not have a TLS implementation available. When TLS is available on an entity, it is strongly encouraged that the security policy disallow non-TLS sessions. This requires that the TLS handshake occur, regardless of the policy-driven parameters of the handshake and policy-driven handling of the handshake outcome.

CAN_TLSフラグの目的は、そもそもTLS実装を利用できないエンティティーでTCPCLを使用できるようにすることです。 エンティティーでTLSが利用可能な場合は、セキュリティーポリシーでTLSを使わないセッションを禁止することが強く推奨されます。 これにより、ハンドシェイクのポリシー駆動のパラメーターや、ハンドシェイクの結果のポリシー駆動の処理にかかわらず、TLSハンドシェイクが行われることが求められます。

One mechanism to mitigate the possibility of TLS Stripping is the use of DNS-based Authentication of Named Entities (DANE) [RFC6698] toward the passive peer. This mechanism relies on DNS and is unidirectional, so it doesn't help with applying policy toward the active peer, but it can be useful in an environment using opportunistic security. The configuration and use of DANE are outside of the scope of this document.

TLSストリッピングの可能性を緩和するメカニズムの1つは、受動的ピアに向けたDNSベースの名前付きエンティティーの認証（DANE）[RFC6698]の使用です。 このメカニズムはDNSに依存し、単方向であるため、能動的ピアに向けたポリシーの適用には役立ちませんが、日和見的セキュリティーを使用する環境では有用な場合があります。 DANEの設定と使用は、この文書の範囲外です。

The negotiated use of TLS is identical in behavior to the use of STARTTLS as described in [RFC2595], [RFC4511], and others.

ネゴシエートによるTLSの使用は、振る舞いの点で、[RFC2595]や[RFC4511]などで説明されているSTARTTLSの使用と同じです。

7.5. Threat: Weak TLS Configurations

7.5. 脅威：脆弱なTLS設定

Even when using TLS to secure the TCPCL session, the actual cipher suite negotiated between the TLS peers can be insecure. Recommendations for using cipher suites are included in BCP 195 [RFC7525]. It is up to security policies within each TCPCL entity to ensure that the negotiated TLS cipher suite meets transport security requirements.

TCPCLセッションを保護するためにTLSを使用する場合でも、TLSピア間で実際にネゴシエートされた暗号スイートが安全でない可能性があります。 暗号スイートの使用に関する推奨事項は、BCP 195[RFC7525]に含まれています。 ネゴシエートされたTLSの暗号スイートがトランスポートセキュリティーの要件を満たすことを保証するのは、各TCPCLエンティティー内のセキュリティーポリシーの役割です。

7.6. Threat: Untrusted End-Entity Certificate

7.6. 脅威：信頼できないエンドエンティティー証明書

The authentication method discussed in Section 4.4.4 uses end-entity certificates chained to a trusted root CA. During a TLS handshake, either entity can send a certificate set that does not contain the full chain, possibly excluding intermediate or root CAs. In an environment where peers are known to already contain needed root and intermediate CAs, there is no need to include those CAs, but this carries the risk of an entity not actually having one of the needed CAs.

Section 4.4.4で説明した認証方法では、信頼できるルートCAにチェーンされたエンドエンティティー証明書を使用します。 TLSハンドシェイクの間、どちらのエンティティーも、完全なチェーンを含まない証明書の集合を送信する可能性があり、中間CAやルートCAが除外されている可能性があります。 ピアが必要なルートCAと中間CAをすでに持っていることがわかっている環境では、それらのCAを含める必要はありませんが、エンティティーが実際には必要なCAのいずれかを持っていないというリスクを伴います。

7.7. Threat: Certificate Validation Vulnerabilities

7.7. 脅威：証明書の検証の脆弱性

Even when TLS itself is operating properly, an attacker can attempt to exploit vulnerabilities within certificate check algorithms or configuration to establish a secure TCPCL session using an invalid certificate. A BPA treats the peer node ID within a TCPCL session as authoritative, and exploitation via an invalid certificate could lead to bundle data leaking and/or denial of service to the node ID being impersonated.

TLS自体が適切に動作している場合でも、攻撃者は、証明書チェックのアルゴリズムや設定内の脆弱性を悪用して、無効な証明書を使用して安全なTCPCLセッションを確立しようとする可能性があります。 BPAはTCPCLセッション内のピアのノードIDを権威あるものとして扱うため、無効な証明書を介した悪用は、バンドルデータの漏洩や、なりすまされたノードIDに対するサービス拒否につながる可能性があります。

There are many reasons, as described in [RFC5280] and [RFC6125], why a certificate can fail to validate, including using the certificate outside of its valid time interval, using purposes for which it was not authorized, or using it after it has been revoked by its CA. Validating a certificate is a complex task and can require network connectivity outside of the primary TCPCL network path(s) if a mechanism such as OCSP [RFC6960] is used by the CA. The configuration and use of particular certificate validation methods are outside of the scope of this document.

[RFC5280]と[RFC6125]で説明されているように、証明書の検証が失敗する理由は数多くあります。たとえば、有効な期間外での証明書の使用、認可されていない用途での使用、CAによって失効された後の使用などです。 証明書の検証は複雑な作業であり、CAがOCSP [RFC6960]などのメカニズムを使用している場合は、主要なTCPCLのネットワーク経路以外のネットワーク接続が必要になる場合があります。 特定の証明書検証方法の設定と使用は、この文書の範囲外です。

7.8. Threat: Symmetric Key Limits

7.8. 脅威：対称鍵の制限

Even with a secure block cipher and securely established session keys, there are limits to the amount of plaintext that can be safely encrypted with a given set of keys, as described in [AEAD-LIMITS]. When permitted by the negotiated TLS version (see [RFC8446]), it is advisable to take advantage of session key updates to avoid those limits.

安全なブロック暗号と安全に確立されたセッション鍵を使用していても、[AEAD-LIMITS]で説明されているように、特定の鍵の集合で安全に暗号化できる平文の量には制限があります。 ネゴシエートされたTLSバージョンで許可されている場合（[RFC8446]を参照）、それらの制限を避けるためにセッション鍵の更新を活用することが推奨されます。

7.9. Threat: BP Node Impersonation

7.9. 脅威：BPノードのなりすまし

The certificates exchanged by TLS enable authentication of the peer DNS name and node ID, but it is possible that either a peer does not provide a valid certificate or the certificate does not validate either the DNS-ID/IPADDR-ID or NODE-ID of the peer (see Section 3.4). Having a CA-validated certificate does not alone guarantee the identity of the network host or BP node from which the certificate is provided; additional validation procedures as provided in Section 4.4.4 bind the DNS-ID/IPADDR-ID or NODE-ID based on the contents of the certificate.

TLSによって交換される証明書により、ピアのDNS名とノードIDの認証が可能になりますが、ピアが有効な証明書を提供しない場合や、証明書がピアのDNS-ID/IPADDR-IDとNODE-IDのいずれも検証しない場合があり得ます（Section 3.4を参照）。 CAが検証した証明書を持っているだけでは、その証明書を提供したネットワークホストやBPノードのアイデンティティーは保証されません。Section 4.4.4で示した追加の検証手順によって、証明書の内容に基づいてDNS-ID/IPADDR-IDやNODE-IDを結び付けます。

The DNS-ID/IPADDR-ID validation is a weaker form of authentication, because even if a peer is operating on an authenticated network DNS name or IP address it can provide an invalid node ID and cause bundles to be "leaked" to an invalid node. Especially in DTN environments, network names and addresses of nodes can be time-variable, so binding a certificate to a node ID results in a more stable identity.

DNS-ID/IPADDR-IDの検証はより弱い形式の認証です。なぜなら、ピアが認証されたネットワークのDNS名やIPアドレスで動作していても、無効なノードIDを提示して、バンドルを無効なノードに「漏洩」させる可能性があるからです。 特にDTN環境では、ノードのネットワーク名やアドレスは時間とともに変化する可能性があるため、証明書をノードIDに結び付けることで、より安定したアイデンティティーが得られます。

NODE-ID validation ensures that the peer to which a bundle is transferred is in fact the node that the BPA expects it to be. In circumstances where certificates can only be issued to DNS names, node ID validation is not possible, but it could be reasonable to assume that a trusted host is not going to present an invalid node ID. Determining when a DNS-ID/IPADDR-ID authentication can be trusted to validate a node ID is also a policy matter outside of the scope of this document.

NODE-IDの検証により、バンドルの転送先のピアが、実際にBPAが期待するノードであることが保証されます。 証明書をDNS名に対してしか発行できない状況では、ノードIDの検証は不可能ですが、信頼できるホストが無効なノードIDを提示することはないと想定するのは妥当な場合があります。 DNS-ID/IPADDR-IDの認証がノードIDの検証として信頼できるのはどのような場合かを判断することも、この文書の範囲外のポリシーの問題です。

One mitigation regarding arbitrary entities with valid PKIX certificates impersonating arbitrary node IDs is the use of the PKIX EKU key purpose id-kp-bundleSecurity (Section 4.4.2.1). When this EKU is present in the certificate, it represents a stronger assertion that the private key holder should in fact be trusted to operate as a bundle node.

有効なPKIX証明書を持つ任意のエンティティーが任意のノードIDになりすますことに対する緩和策の1つは、PKIXのEKUの鍵用途id-kp-bundleSecurity（Section 4.4.2.1）の使用です。 このEKUが証明書に存在する場合、それは、秘密鍵の保有者がバンドルノードとして動作することを実際に信頼されるべきであるという、より強いアサーションを表します。

7.10. Threat: Denial of Service

7.10. 脅威：サービス拒否

The behaviors described in this section all amount to a potential denial of service to a TCPCL entity. The denial of service could be limited to an individual TCPCL session, could affect other well-behaved sessions on an entity, or could affect all sessions on a host.

このセクションで説明する振る舞いはすべて、TCPCLエンティティーに対する潜在的なサービス拒否に相当します。 サービス拒否は、個々のTCPCLセッションに限定される場合もあれば、エンティティー上の他の正常に振る舞うセッションに影響する場合や、ホスト上のすべてのセッションに影響する場合もあります。

A malicious entity can trigger timeouts by continually establishing TCPCL sessions and delaying the sending of protocol-required data. The victim entity can block TCP connections from network peers that are thought to behave incorrectly within the TCPCL.

悪意のあるエンティティーは、TCPCLセッションを継続的に確立し、プロトコルで必要なデータの送信を遅らせることで、タイムアウトを引き起こすことができます。 被害を受けるエンティティーは、TCPCL内で不正に振る舞うと考えられるネットワークピアからのTCPコネクションをブロックできます。

An entity can send a large amount of data over a TCPCL session, requiring the receiving entity to handle the data. The victim entity can attempt to stop the flood of data by sending a XFER_REFUSE message or can forcibly terminate the session.

エンティティーは、TCPCLセッション上で大量のデータを送信して、受信側エンティティーにそのデータの処理を強いることができます。 被害を受けるエンティティーは、XFER_REFUSEメッセージを送信してデータの殺到を止めようとするか、セッションを強制的に終了できます。

A "data dribble" attack is also possible, in which an entity presents a very small Segment MRU that causes transfers to be split among a large number of very small segments and causes the resultant segmentation overhead to overwhelm the actual bundle data segments. Similarly, an entity can present a very small Transfer MRU that will cause resources to be wasted on establishment and upkeep of a TCPCL session over which a bundle could never be transferred. The victim entity can terminate the session during parameter negotiation (Section 4.7) if the MRUs are unacceptable.

「データドリブル（data dribble）」攻撃も可能です。この攻撃では、エンティティーが非常に小さなセグメントMRUを提示することで、転送を多数の非常に小さなセグメントに分割させ、その結果生じる分割のオーバーヘッドによって実際のバンドルデータのセグメントを圧倒させます。 同様に、エンティティーは非常に小さな転送MRUを提示することで、決してバンドルを転送できないTCPCLセッションの確立と維持にリソースを浪費させることができます。 被害を受けるエンティティーは、MRUが受け入れられない場合、パラメーターのネゴシエーション（Section 4.7）の間にセッションを終了できます。

An abusive entity could cause the keepalive mechanism to waste throughput within a network link that would otherwise be usable for bundle transmissions. Due to the quantization of the Keepalive Interval parameter, the smallest Session Keepalive is one second, which should be long enough to not flood the link. The victim entity can terminate the session during parameter negotiation (Section 4.7) if the Keepalive Interval is unacceptable.

悪用するエンティティーは、キープアライブのメカニズムによって、本来ならバンドルの送信に使用できるネットワークリンク内のスループットを浪費させる可能性があります。 Keepalive Intervalパラメーターの量子化により、最小のSession Keepaliveは1秒であり、これはリンクを殺到させないのに十分な長さであるはずです。 被害を受けるエンティティーは、Keepalive Intervalが受け入れられない場合、パラメーターのネゴシエーション（Section 4.7）の間にセッションを終了できます。

Finally, an attacker or a misconfigured entity can cause issues at the TCP connection that will cause unnecessary TCP retransmissions or connection resets, effectively denying the use of the overlying TCPCL session.

最後に、攻撃者や設定を誤ったエンティティーは、TCPコネクションで問題を引き起こし、不要なTCPの再送やコネクションのリセットを発生させることで、上位のTCPCLセッションの使用を事実上妨げることができます。

7.11. Mandatory-to-Implement TLS

7.11. 実装必須のTLS

Following IETF best current practice, TLS is mandatory to implement for all TCPCL implementations but TLS is optional to use for a given TCPCL session. The policy recommendations in Sections 4.2 and 4.3 both enable TLS and require TLS, but entities are permitted to disable and not require TLS based on local configuration. The configuration to enable or require TLS for an entity or a session is outside of the scope of this document. The configuration to disable TLS is different from the threat of TLS Stripping as described in Section 7.4.

IETFのベストカレントプラクティスに従い、TLSはすべてのTCPCL実装で実装必須ですが、特定のTCPCLセッションでTLSを使用するかどうかは任意です。 セクション4.2とセクション4.3のポリシーの推奨事項はいずれもTLSを有効にし、TLSを要求するものですが、エンティティーはローカルの設定に基づいてTLSを無効にし、要求しないことが許可されています。 エンティティーやセッションでTLSを有効にする、または要求するための設定は、この文書の範囲外です。 TLSを無効にする設定は、Section 7.4で説明したTLSストリッピングの脅威とは異なります。

7.12. Alternate Uses of TLS

7.12. TLSの別の使用方法

This specification makes use of PKIX certificate validation and authentication within TLS. There are alternate uses of TLS that are not necessarily incompatible with the security goals of this specification but that are outside of the scope of this document. The following subsections give examples of alternate TLS uses.

この仕様では、TLS内でPKIX証明書の検証と認証を利用します。 この仕様のセキュリティー目標と両立し得るものの、この文書の範囲外である、TLSの別の使用方法もあります。 以下のサブセクションでは、TLSの別の使用方法の例を示します。

7.12.1. TLS without Authentication

7.12.1. 認証なしのTLS

In environments where PKI is available but there are restrictions on the issuance of certificates (including the contents of certificates), it may be possible to make use of TLS in a way that authenticates only the passive entity of a TCPCL session or that does not authenticate either entity. Using TLS in a way that does not successfully authenticate some claim of both peer entities of a TCPCL session is outside of the scope of this document but does have properties similar to the opportunistic security model [RFC7435].

PKIは利用可能であるものの、証明書の発行（証明書の内容を含む）に制限がある環境では、TCPCLセッションの受動的エンティティーのみを認証する方法や、どちらのエンティティーも認証しない方法でTLSを利用できる場合があります。 TCPCLセッションの両方のピアエンティティーの何らかのクレームの認証に成功しない方法でTLSを使用することは、この文書の範囲外ですが、日和見的セキュリティーモデル[RFC7435]と似た性質を持ちます。

7.12.2. Non-certificate TLS Use

7.12.2. 証明書を使用しないTLSの使用

In environments where PKI is unavailable, alternate uses of TLS that do not require certificates such as pre-shared key (PSK) authentication [RFC5489] and the use of raw public keys [RFC7250] are available and can be used to ensure confidentiality within the TCPCL. Using non-PKI node authentication methods is outside of the scope of this document.

PKIが利用できない環境では、事前共有鍵（PSK）認証[RFC5489]や生の公開鍵の使用[RFC7250]など、証明書を必要としないTLSの別の使用方法が利用可能であり、TCPCL内での機密性を確保するために使用できます。 PKIによらないノード認証方法の使用は、この文書の範囲外です。

7.13. Predictability of Transfer IDs

7.13. Transfer IDの予測可能性

The only requirement on Transfer IDs is that they be unique within each session from the sending peer only. The trivial algorithm of the first transfer starting at zero and later transfers incrementing by one causes absolutely predictable Transfer IDs. Even when a TCPCL session is not TLS secured and there is an on-path attacker causing denial of service with XFER_REFUSE messages, it is not possible to preemptively refuse a transfer, so there is no benefit in having unpredictable Transfer IDs within a session.

Transfer IDに関する唯一の要件は、各セッション内で送信側のピアからのものに限って一意であることです。 最初の転送を0から始め、後の転送で1ずつ増やすという自明なアルゴリズムでは、Transfer IDは完全に予測可能になります。 TCPCLセッションがTLSで保護されておらず、XFER_REFUSEメッセージによってサービス拒否を引き起こしている経路上の攻撃者がいる場合でも、転送を先回りして拒否することはできないため、セッション内でTransfer IDを予測不可能にすることに利点はありません。

Appendix A. Significant Changes from RFC 7242

Appendix A. RFC 7242からの主な変更点

The areas in which changes from [RFC7242] have been made to existing headers and messages are as follows:

既存のヘッダーとメッセージに対して[RFC7242]から変更が加えられた領域は次のとおりです。

  • Split Contact Header into pre-TLS protocol negotiation and SESS_INIT parameter negotiation. The Contact Header is now fixed length.
  • Changed Contact Header content to limit number of negotiated options.
  • Added session option to negotiate maximum segment size (per each direction).
  • Renamed "endpoint ID" to "node ID" to conform with BPv7 terminology.
  • Added session extension capability.
  • Added transfer extension capability. Moved transfer total length into an extension item.
  • Defined new IANA registries for message / type / reason codes to allow renaming some codes for clarity.
  • Pointed out that segments of all new IANA registries are reserved for private/experimental use.
  • Expanded Message Header to octet-aligned fields instead of bit-packing.
  • Added a bundle transfer identification number to all bundle-related messages (XFER_SEGMENT, XFER_ACK, XFER_REFUSE).
  • Added flags in XFER_ACK to mirror flags from XFER_SEGMENT.
  • Removed all uses of Self-Delimiting Numeric Value (SDNV) fields and replaced with fixed-bit-length (network byte order) fields.
  • Renamed SHUTDOWN to SESS_TERM to deconflict term "shutdown" related to TCP connections.
  • Removed the notion of a reconnection delay parameter.
  • コンタクトヘッダーを、TLS前のプロトコルネゴシエーションとSESS_INITのパラメーターネゴシエーションに分割しました。コンタクトヘッダーは固定長になりました。
  • ネゴシエートされるオプションの数を制限するために、コンタクトヘッダーの内容を変更しました。
  • （方向ごとの）最大セグメントサイズをネゴシエートするためのセッションオプションを追加しました。
  • BPv7の用語に合わせるため、「エンドポイントID」を「ノードID」に名称変更しました。
  • セッション拡張の能力を追加しました。
  • 転送拡張の能力を追加しました。転送の総長を拡張項目に移しました。
  • 明確さのために一部のコードの名称を変更できるよう、メッセージ・タイプ・理由コードのための新しいIANAレジストリーを定義しました。
  • すべての新しいIANAレジストリーの一部の範囲がプライベート・実験的な使用のために予約されていることを明記しました。
  • メッセージヘッダーを、ビットパッキングではなくオクテット境界にそろえたフィールドに拡張しました。
  • バンドルに関連するすべてのメッセージ（XFER_SEGMENT、XFER_ACK、XFER_REFUSE）に、バンドル転送の識別番号を追加しました。
  • XFER_SEGMENTのフラグを反映するフラグをXFER_ACKに追加しました。
  • 自己区切り数値（Self-Delimiting Numeric Value; SDNV）フィールドの使用をすべて削除し、固定ビット長（ネットワークバイトオーダー）のフィールドに置き換えました。
  • TCPコネクションに関連する用語「shutdown」との衝突を避けるため、SHUTDOWNをSESS_TERMに名称変更しました。
  • 再接続遅延パラメーターの概念を削除しました。

The areas in which extensions from [RFC7242] have been made as new messages and codes are as follows:

新しいメッセージとコードとして[RFC7242]から拡張が行われた領域は次のとおりです。

  • Added MSG_REJECT message to indicate that an unknown or unhandled message was received.
  • Added TLS connection security mechanism.
  • Added "Not Acceptable", "Extension Failure", and "Session Terminating" XFER_REFUSE reason codes.
  • Added "Contact Failure" (contact negotiation failure) and "Resource Exhaustion" SESS_TERM reason codes.
  • 未知のメッセージや処理されないメッセージを受信したことを示すためのMSG_REJECTメッセージを追加しました。
  • TLSによるコネクションのセキュリティーメカニズムを追加しました。
  • XFER_REFUSEの理由コード「Not Acceptable」、「Extension Failure」、「Session Terminating」を追加しました。
  • SESS_TERMの理由コード「Contact Failure」（コンタクトネゴシエーションの失敗）と「Resource Exhaustion」を追加しました。

Appendix B. ASN.1 Module

Appendix B. ASN.1モジュール

The following ASN.1 module formally specifies the BundleEID structure, its Other Name Form, and the bundleSecurity EKU, using ASN.1 syntax per [X.680]. This specification uses the ASN.1 definitions from [RFC5912] with the 2002 ASN.1 notation used in that document.

次のASN.1モジュールは、[X.680]に従ったASN.1構文を使用して、BundleEID構造、そのOther Name Form、およびbundleSecurity EKUを形式的に規定します。 この仕様では、[RFC5912]のASN.1定義を、その文書で使用されている2002年版のASN.1表記とともに使用します。 

DTN-TCPCLv4-2021
  { iso(1) identified-organization(3) dod(6)
    internet(1) security(5) mechanisms(5) pkix(7) id-mod(0)
    id-mod-dtn-tcpclv4-2021(103) }

DEFINITIONS IMPLICIT TAGS ::=
BEGIN

IMPORTS
  OTHER-NAME
  FROM PKIX1Implicit-2009 -- [RFC5912]
    { iso(1) identified-organization(3) dod(6) internet(1)
      security(5) mechanisms(5) pkix(7) id-mod(0)
      id-mod-pkix1-implicit-02(59) }

  id-pkix
  FROM PKIX1Explicit-2009 -- [RFC5912]
    { iso(1) identified-organization(3) dod(6) internet(1)
      security(5) mechanisms(5) pkix(7) id-mod(0)
      id-mod-pkix1-explicit-02(51) } ;

id-kp OBJECT IDENTIFIER ::= { id-pkix 3 }

id-on OBJECT IDENTIFIER ::= { id-pkix 8 }

DTNOtherNames OTHER-NAME ::= { on-bundleEID, ... }

-- The otherName definition for BundleEID
on-bundleEID OTHER-NAME ::= {
    BundleEID IDENTIFIED BY { id-on-bundleEID }
}

id-on-bundleEID OBJECT IDENTIFIER ::= { id-on 11 }

-- Same encoding as GeneralName of uniformResourceIdentifier
BundleEID ::= IA5String

-- The Extended Key Usage key for bundle security
id-kp-bundleSecurity OBJECT IDENTIFIER ::= { id-kp 35 }

END
