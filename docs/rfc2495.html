RFC 2495

Definitions of Managed Objects for the DS1, E1, DS2 and E2 Interface Types

RFC 2495

DS1、E1、DS2、およびE2のインターフェイスタイプのための管理オブジェクトの定義

Abstract

概要

This memo defines a portion of the Management Information Base (MIB) for use with network management protocols in the Internet community. In particular, it describes objects used for managing DS1, E1, DS2 and E2 interfaces. This document is a companion document with Definitions of Managed Objects for the DS0 (RFC 2494 [30]), DS3/E3 (RFC 2496 [28]), and the work in progress, SONET/SDH Interface Types.

このメモは、インターネットコミュニティーのネットワーク管理プロトコルで使用するための管理情報ベース（MIB）の一部を定義します。特に、DS1、E1、DS2、およびE2のインターフェイスを管理するために使用されるオブジェクトを記述します。この文書は、DS0（RFC 2494[30]）、DS3/E3（RFC 2496[28]）、および作業中のSONET/SDHのインターフェイスタイプのための管理オブジェクトの定義と対になる文書です。

This memo specifies a MIB module in a manner that is both compliant to the SNMPv2 SMI, and semantically identical to the peer SNMPv1 definitions.

このメモは、SNMPv2 SMIに準拠し、かつ対応するSNMPv1の定義と意味的に同一である形でMIBモジュールを規定します。

1. The SNMP Management Framework

1. SNMP管理フレームワーク

The SNMP Management Framework presently consists of five major components:

SNMP管理の枠組みは、現在、5つの主要な構成要素からなります。

  • An overall architecture, described in RFC 2271 [1].
  • Mechanisms for describing and naming objects and events for the purpose of management. The first version of this Structure of Management Information (SMI) is called SMIv1 and described in STD 16, RFC 1155 [2], STD 16, RFC 1212 [3] and RFC 1215 [4]. The second version, called SMIv2, is described in RFC 1902 [5], RFC 1903 [6] and RFC 1904 [7].
  • Message protocols for transferring management information. The first version of the SNMP message protocol is called SNMPv1 and described in STD 15, RFC 1157 [8]. A second version of the SNMP message protocol, which is not an Internet standards track protocol, is called SNMPv2c and described in RFC 1901 [9] and RFC 1906 [10]. The third version of the message protocol is called SNMPv3 and described in RFC 1906 [10], RFC 2272 [11] and RFC 2274 [12].
  • Protocol operations for accessing management information. The first set of protocol operations and associated PDU formats is described in STD 15, RFC 1157 [8]. A second set of protocol operations and associated PDU formats is described in RFC 1905 [13].
  • A set of fundamental applications described in RFC 2273 [14] and the view-based access control mechanism described in RFC 2275 [15]. Managed objects are accessed via a virtual information store, termed the Management Information Base or MIB. Objects in the MIB are defined using the mechanisms defined in the SMI.
  • RFC 2271 [1]で説明されている全体的なアーキテクチャー。
  • 管理の目的でオブジェクトとイベントを記述し命名するための仕組み。この管理情報の構造（SMI）の最初のバージョンはSMIv1と呼ばれ、STD 16、RFC 1155 [2]、STD 16、RFC 1212 [3]、およびRFC 1215 [4]で説明されています。2番目のバージョンはSMIv2と呼ばれ、RFC 1902 [5]、RFC 1903 [6]、およびRFC 1904 [7]で説明されています。
  • 管理情報を転送するためのメッセージプロトコル。SNMPメッセージプロトコルの最初のバージョンはSNMPv1と呼ばれ、STD 15、RFC 1157 [8]で説明されています。SNMPメッセージプロトコルの2番目のバージョンは、インターネット標準化過程のプロトコルではありませんが、SNMPv2cと呼ばれ、RFC 1901 [9]とRFC 1906 [10]で説明されています。メッセージプロトコルの3番目のバージョンはSNMPv3と呼ばれ、RFC 1906 [10]、RFC 2272 [11]、およびRFC 2274 [12]で説明されています。
  • 管理情報にアクセスするためのプロトコル操作。最初のプロトコル操作の集まりとそれに関連するPDUの形式は、STD 15、RFC 1157 [8]で説明されています。2番目のプロトコル操作の集まりとそれに関連するPDUの形式は、RFC 1905 [13]で説明されています。
  • RFC 2273[14]で説明されている基本的なアプリケーションの集まりと、RFC 2275[15]で説明されているビューベースのアクセス制御の仕組み。管理対象のオブジェクトには、管理情報ベース（MIB）と呼ばれる仮想的な情報ストアを介してアクセスします。MIBの中のオブジェクトは、SMIで定義されている仕組みを使用して定義されます。

This memo specifies a MIB module that is compliant to the SMIv2. A MIB conforming to the SMIv1 can be produced through the appropriate translations. The resulting translated MIB must be semantically equivalent, except where objects or events are omitted because no translation is possible (use of Counter64). Some machine readable information in SMIv2 will be converted into textual descriptions in SMIv1 during the translation process. However, this loss of machine readable information is not considered to change the semantics of the MIB.

このメモは、SMIv2に準拠するMIBモジュールを規定します。SMIv1に準拠するMIBは、適切な変換によって作成できます。変換の結果得られるMIBは、変換が不可能なため（Counter64の使用）オブジェクトやイベントが省略される場合を除いて、意味的に等価である必要があります。SMIv2の機械可読な情報の一部は、変換の過程でSMIv1のテキストによる記述に変換されます。しかし、この機械可読な情報の喪失は、MIBの意味を変えるものとはみなされません。

2. Overview

2. 概要

These objects are used when the particular media being used to realize an interface is a DS1/E1/DS2/E2 interface. At present, this applies to these values of the ifType variable in the Internet- standard MIB:

これらのオブジェクトは、インターフェイスを実現するために使用されている特定のメディアがDS1/E1/DS2/E2インターフェイスである場合に使用されます。現在、これはインターネット標準のMIBのifType変数の次の値に適用されます。

ds1 (18)

ds1 (18)

The definitions contained herein are based on the AT&T T-1 Superframe (a.k.a., D4) and Extended Superframe (ESF) formats [17], [18], the latter of which conforms to ANSI specifications [19], and the CCITT Recommendations [20], [21], referred to as E1 for the rest of this memo.

ここに含まれる定義は、AT&TのT-1スーパーフレーム（別名D4）と拡張スーパーフレーム（ESF）の形式[17]、[18]（後者はANSIの仕様[19]に準拠しています）、およびCCITTの勧告[20]、[21]に基づいています。CCITTの勧告については、このメモの残りの部分ではE1と呼びます。

The various DS1 and E1 line disciplines are similar enough that separate MIBs are unwarranted, although there are some differences. For example, Loss of Frame is defined more rigorously in the ESF specification than in the D4 specification, but it is defined in both. Therefore, interface types e1(19) and g703at2mb(67) have been obsoleted.

さまざまなDS1とE1の回線の規律は、いくつかの違いはあるものの、別々のMIBを正当化しないほど似ています。たとえば、フレーム損失は、D4の仕様よりもESFの仕様でより厳密に定義されていますが、両方で定義されています。そのため、インターフェイスタイプe1(19)とg703at2mb(67)は廃止されました。

Where it is necessary to distinguish between the flavors of E1 with and without CRC, E1-CRC denotes the "with CRC" form (G.704 Table 4b) and E1-noCRC denotes the "without CRC" form (G.704 Table 4a).

CRCありとCRCなしのE1の種類を区別する必要がある場合、E1-CRCは「CRCあり」の形式（G.704の表4b）を、E1-noCRCは「CRCなし」の形式（G.704の表4a）を表します。

2.2.1. Usage of ifStackTable for Routers and DSUs

2.2.1. ルーターとDSUでのifStackTableの使用法

The object dsx1IfIndex has been deprecated. This object previously allowed a very special proxy situation to exist for Routers and CSUs. This section now describes how to use ifStackTable to represent this relationship.

オブジェクトdsx1IfIndexは非推奨になりました。このオブジェクトは以前、ルーターとCSUについて非常に特殊なプロキシーの状況が存在することを可能にしていました。この節では、ifStackTableを使用してこの関係を表す方法を説明します。

The paragraphs discussing dsx1IfIndex and dsx1LineIndex have been preserved in Appendix A for informational purposes.

dsx1IfIndexとdsx1LineIndexについて議論する段落は、情報提供の目的で付録Aに残しています。

The ifStackTable is used in the proxy case to represent the association between pairs of interfaces, e.g. this T1 is attached to that T1. This use is consistent with the use of the ifStackTable to show the association between various sub-layers of an interface. In both cases entire PDUs are exchanged between the interface pairs - in the case of a T1, entire T1 frames are exchanged; in the case of PPP and HDLC, entire HDLC frames are exchanged. This usage is not meant to suggest the use of the ifStackTable to represent Time Division Multiplexing (TDM) connections in general.

ifStackTableは、プロキシーの場合に、インターフェイスの組の間の関連付け（例：このT1はあのT1に接続されている）を表すために使用されます。この使用は、インターフェイスのさまざまな副層の間の関連付けを示すためのifStackTableの使用と一貫しています。どちらの場合も、PDU全体がインターフェイスの組の間で交換されます。T1の場合はT1フレーム全体が交換され、PPPとHDLCの場合はHDLCフレーム全体が交換されます。この使用法は、一般に時分割多重（TDM）の接続を表すためにifStackTableを使用することを示唆するものではありません。

2.3. Objectives of this MIB Module

2.3. このMIBモジュールの目的

There are numerous things that could be included in a MIB for DS1 signals: the management of multiplexors, CSUs, DSUs, and the like. The intent of this document is to facilitate the common management of all devices with DS1, E1, DS2, or E3 interfaces. As such, a design decision was made up front to very closely align the MIB with the set of objects that can generally be read from these types devices that are currently deployed.

DS1信号のためのMIBには、マルチプレクサー、CSU、DSUなどの管理といった、数多くのものを含めることができます。この文書の意図は、DS1、E1、DS2、またはE3のインターフェイスを持つすべての機器の共通の管理を容易にすることです。そのため、現在展開されているこれらの種類の機器から一般に読み取ることができるオブジェクトの集合にMIBを非常に密接に合わせるという設計上の決定が、最初に行われました。

J2 interfaces are not supported by this MIB.

2.4. DS1 Terminology

2.4. DS1の用語

The terminology used in this document to describe error conditions on a DS1 interface as monitored by a DS1 device are based on the late but not final draft of what became the ANSI T1.231 standard [11]. If the definition in this document does not match the definition in the ANSI T1.231 document, the implementer should follow the definition described in this document.

DS1機器によって監視されるDS1インターフェイス上のエラーの状態を記述するためにこの文書で使用される用語は、ANSI T1.231標準[11]となったものの、最終ではない後期のドラフトに基づいています。この文書の定義がANSI T1.231文書の定義と一致しない場合、実装者はこの文書で説明する定義に従うべきです。

2.4.1. Error Events

2.4.1. エラーイベント

Bipolar Violation (BPV) Error Event
A BPV error event for an AMI-coded signal is the occurrence of a pulse of the same polarity as the previous pulse. (See T1.231 Section 6.1.1.1.1) A BPV error event for a B8ZS- or HDB3- coded signal is the occurrence of a pulse of the same polarity as the previous pulse without being a part of the zero substitution code.
Excessive Zeroes (EXZ) Error Event
An Excessive Zeroes error event for an AMI-coded signal is the occurrence of more than fifteen contiguous zeroes. (See T1.231 Section 6.1.1.1.2) For a B8ZS coded signal, the defect occurs when more than seven contiguous zeroes are detected.
Line Coding Violation (LCV) Error Event
A Line Coding Violation (LCV) is the occurrence of either a Bipolar Violation (BPV) or Excessive Zeroes (EXZ) Error Event. (Also known as CV-L; See T1.231 Section 6.5.1.1)
Path Coding Violation (PCV) Error Event
A Path Coding Violation error event is a frame synchronization bit error in the D4 and E1-noCRC formats, or a CRC or frame synch. bit error in the ESF and E1-CRC formats. (Also known as CV-P; See T1.231 Section 6.5.2.1)
Controlled Slip (CS) Error Event
A Controlled Slip is the replication or deletion of the payload bits of a DS1 frame. (See T1.231 Section 6.1.1.2.3) A Controlled Slip may be performed when there is a difference between the timing of a synchronous receiving terminal and the received signal. A Controlled Slip does not cause an Out of Frame defect.
バイポーラ違反（BPV）エラーイベント
AMI符号化された信号に対するBPVエラーイベントとは、直前のパルスと同じ極性のパルスが発生することです（T1.231のセクション6.1.1.1.1を参照）。B8ZSまたはHDB3で符号化された信号に対するBPVエラーイベントとは、ゼロ置換符号の一部ではない、直前のパルスと同じ極性のパルスが発生することです。
過剰ゼロ（EXZ）エラーイベント
AMI符号化された信号に対する過剰ゼロエラーイベントとは、16個以上の連続したゼロが発生することです（T1.231のセクション6.1.1.1.2を参照）。B8ZS符号化された信号の場合、この欠陥は8個以上の連続したゼロが検出されたときに発生します。
回線符号違反（LCV）エラーイベント
回線符号違反（LCV）とは、バイポーラ違反（BPV）エラーイベントまたは過剰ゼロ（EXZ）エラーイベントのいずれかが発生することです（CV-Lとしても知られています。T1.231のセクション6.5.1.1を参照）。
パス符号違反（PCV）エラーイベント
パス符号違反エラーイベントとは、D4とE1-noCRCの形式ではフレーム同期ビットのエラーであり、ESFとE1-CRCの形式ではCRCまたはフレーム同期ビットのエラーです（CV-Pとしても知られています。T1.231のセクション6.5.2.1を参照）。
制御スリップ（CS）エラーイベント
制御スリップとは、DS1フレームのペイロードのビットが複製または削除されることです（T1.231のセクション6.1.1.2.3を参照）。制御スリップは、同期受信端末のタイミングと受信信号との間に差がある場合に行われることがあります。制御スリップはフレーム外れの欠陥を引き起こしません。

2.4.2. Performance Defects

2.4.2. 性能の欠陥

Out Of Frame (OOF) Defect

An OOF defect is the occurrence of a particular density of Framing Error events. (See T1.231 Section 6.1.2.2.1)

For DS1 links, an Out of Frame defect is declared when the receiver detects two or more framing errors within a 3 msec period for ESF signals and 0.75 msec for D4 signals, or two or more errors out of five or fewer consecutive framing-bits.

For E1 links, an Out Of Frame defect is declared when three consecutive frame alignment signals have been received with an error (see G.706 Section 4.1 [26]).

For DS2 links, an Out of Frame defect is declared when 7 or more consecutive errored framing patterns (4 multiframe) are received. The LOF is cleared when 3 or more consecutive correct framing patterns are received.

Once an Out Of Frame Defect is declared, the framer starts searching for a correct framing pattern. The Out of Frame defect ends when the signal is in frame.

In-frame occurs when there are fewer than two frame bit errors within 3 msec period for ESF signals and 0.75 msec for D4 signals.

For E1 links, in-frame occurs when a) in frame N the frame alignment signal is correct and b) in frame N+1 the frame alignment signal is absent (i.e., bit 2 in TS0 is a one) and c) in frame N+2 the frame alignment signal is present and correct. (See G.704 Section 4.1)

Alarm Indication Signal (AIS) Defect

For D4 and ESF links, the 'all ones' condition is detected at a DS1 line interface upon observing an unframed signal with a one's density of at least 99.9% present for a time equal to or greater than T, where 3 ms <= T <= 75 ms. The AIS is terminated upon observing a signal not meeting the one's density or the unframed signal criteria for a period equal to or greater than than T. (See G.775, Section 5.4)

For E1 links, the 'all-ones' condition is detected at the line interface as a string of 512 bits containing fewer than three zero bits (see O.162 [23] Section 3.3.2).

For DS2 links, the DS2 AIS shall be sent from the NT1 to the user to indicate a loss of the 6,312 kbps frame capability on the network side. The DS2 AIS is defined as a bit array of 6,312 kbps in which all binary bits are set to '1'.

The DS2 AIS detection and removal shall be implemented according to ITU-T Draft Recommendation G.775 [31] Section 5.5:

  • a DS2 AIS defect is detected when the incoming signal has two (2) or less ZEROs in a sequence of 3156 bits (0.5 ms).
  • a DS2 AIS defect is cleared when the incoming signal has three (3) or more ZEROs in a sequence of 3156 bits (0.5 ms).
フレーム外れ（OOF）の欠陥

OOFの欠陥とは、フレーミングエラーイベントが特定の密度で発生することです（T1.231のセクション6.1.2.2.1を参照）。

DS1リンクでは、受信者が、ESF信号では3ミリ秒、D4信号では0.75ミリ秒の期間内に2つ以上のフレーミングエラーを検出した場合、または5つ以下の連続したフレーミングビットのうち2つ以上のエラーを検出した場合に、フレーム外れの欠陥が宣言されます。

E1リンクでは、3つの連続したフレーム同期信号がエラーとともに受信された場合に、フレーム外れの欠陥が宣言されます（G.706のセクション4.1[26]を参照）。

DS2リンクでは、7つ以上の連続したエラーのあるフレーミングパターン（4マルチフレーム）を受信した場合に、フレーム外れの欠陥が宣言されます。LOFは、3つ以上の連続した正しいフレーミングパターンを受信したときに解除されます。

フレーム外れの欠陥が宣言されると、フレーマーは正しいフレーミングパターンの探索を開始します。フレーム外れの欠陥は、信号がフレーム内になったときに終わります。

フレーム内とは、ESF信号では3ミリ秒、D4信号では0.75ミリ秒の期間内のフレームビットのエラーが2つ未満である状態です。

E1リンクでは、a) フレームNでフレーム同期信号が正しく、b) フレームN+1でフレーム同期信号が存在せず（すなわち、TS0のビット2が1）、c) フレームN+2でフレーム同期信号が存在して正しい場合に、フレーム内になります（G.704のセクション4.1を参照）。

警報表示信号（AIS）の欠陥

D4とESFのリンクでは、少なくとも99.9%の1の密度を持つフレーム化されていない信号がT（3ミリ秒 <= T <= 75ミリ秒）以上の時間存在することを観測したときに、DS1回線インターフェイスで「すべて1」の状態が検出されます。AISは、1の密度またはフレーム化されていない信号の基準を満たさない信号をT以上の期間観測したときに終了します（G.775のセクション5.4を参照）。

E1リンクでは、「すべて1」の状態は、回線インターフェイスで、ゼロのビットを3つ未満しか含まない512ビットの列として検出されます（O.162[23]のセクション3.3.2を参照）。

DS2リンクでは、ネットワーク側での6,312 kbpsのフレームの能力の喪失を示すために、DS2 AISがNT1からユーザーに送信されるものとします。DS2 AISは、すべての2進ビットが「1」に設定された6,312 kbpsのビット配列として定義されます。

DS2 AISの検出と解除は、ITU-Tのドラフト勧告G.775[31]のセクション5.5に従って実装されるものとします。

  • DS2 AISの欠陥は、入力信号の3156ビット（0.5ミリ秒）の列の中のゼロが2つ以下の場合に検出されます。
  • DS2 AISの欠陥は、入力信号の3156ビット（0.5ミリ秒）の列の中のゼロが3つ以上の場合に解除されます。

2.4.3. Performance Parameters

2.4.3. 性能パラメーター

All performance parameters are accumulated in fifteen minute intervals and up to 96 intervals (24 hours worth) are kept by an agent. Fewer than 96 intervals of data whelfill be available if the agent has been restarted within the last 24 hours. In addition, there is a rolling 24-hour total of each performance parameter. Performance parameters continue to be collected when the interface is down.

すべての性能パラメーターは15分間隔で累積され、エージェントは最大96区間（24時間分）を保持します。エージェントが過去24時間以内に再起動された場合、利用できるデータの区間は96未満になります。さらに、各性能パラメーターについて、24時間の移動合計があります。性能パラメーターは、インターフェイスがダウンしているときも収集され続けます。

There is no requirement for an agent to ensure fixed relationship between the start of a fifteen minute interval and any wall clock; however some agents may align the fifteen minute intervals with quarter hours.

エージェントが15分の区間の開始と実時間の時計との間の固定的な関係を保証する必要はありません。ただし、一部のエージェントは15分の区間を15分単位の時刻に合わせることがあります。

Performance parameters are of types PerfCurrentCount, PerfIntervalCount and PerfTotalCount. These textual conventions are all Gauge32, and they are used because it is possible for these objects to decrease. Objects may decrease when Unavailable Seconds occurs across a fifteen minutes interval boundary. See Unavailable Seconds discussion later in this section.

Line Errored Seconds (LES)
A Line Errored Second is a second in which one or more Line Code Violation error events were detected. (Also known as ES-L; See T1.231 Section 6.5.1.2)
Controlled Slip Seconds (CSS)
A Controlled Slip Second is a one-second interval containing one or more controlled slips. (See T1.231 Section 6.5.2.8) This is not incremented during an Unavailable Second.
Errored Seconds (ES)

For ESF and E1-CRC links an Errored Second is a second with one or more Path Code Violation OR one or more Out of Frame defects OR one or more Controlled Slip events OR a detected AIS defect. (See T1.231 Section 6.5.2.2 and G.826 [32] Section B.1)

For D4 and E1-noCRC links, the presence of Bipolar Violations also triggers an Errored Second.

This is not incremented during an Unavailable Second.

Bursty Errored Seconds (BES)

A Bursty Errored Second (also known as Errored Second type B in T1.231 Section 6.5.2.4) is a second with fewer than 320 and more than 1 Path Coding Violation error events, no Severely Errored Frame defects and no detected incoming AIS defects. Controlled slips are not included in this parameter.

This is not incremented during an Unavailable Second. It applies to ESF signals only.

Severely Errored Seconds (SES)

A Severely Errored Second for ESF signals is a second with 320 or more Path Code Violation Error Events OR one or more Out of Frame defects OR a detected AIS defect. (See T1.231 Section 6.5.2.5)

For E1-CRC signals, a Severely Errored Second is a second with 832 or more Path Code Violation error events OR one or more Out of Frame defects.

For E1-noCRC signals, a Severely Errored Second is a 2048 LCVs or more.

For D4 signals, a Severely Errored Second is a count of one- second intervals with Framing Error events, or an OOF defect, or 1544 LCVs or more.

Controlled slips are not included in this parameter.

This is not incremented during an Unavailable Second.

Severely Errored Framing Second (SEFS)
An Severely Errored Framing Second is a second with one or more Out of Frame defects OR a detected AIS defect. (Also known as SAS-P (SEF/AIS second); See T1.231 Section 6.5.2.6)
Degraded Minutes

A Degraded Minute is one in which the estimated error rate exceeds 1E-6 but does not exceed 1E-3 (see G.821 [24]).

Degraded Minutes are determined by collecting all of the Available Seconds, removing any Severely Errored Seconds grouping the result in 60-second long groups and counting a 60- second long group (a.k.a., minute) as degraded if the cumulative errors during the seconds present in the group exceed 1E-6. Available seconds are merely those seconds which are not Unavailable as described below.

Unavailable Seconds (UAS)

Unavailable Seconds (UAS) are calculated by counting the number of seconds that the interface is unavailable. The DS1 interface is said to be unavailable from the onset of 10 contiguous SESs, or the onset of the condition leading to a failure (see Failure States). If the condition leading to the failure was immediately preceded by one or more contiguous SESs, then the DS1 interface unavailability starts from the onset of these SESs. Once unavailable, and if no failure is present, the DS1 interface becomes available at the onset of 10 contiguous seconds with no SESs. Once unavailable, and if a failure is present, the DS1 interface becomes available at the onset of 10 contiguous seconds with no SESs, if the failure clearing time is less than or equal to 10 seconds. If the failure clearing time is more than 10 seconds, the DS1 interface becomes available at the onset of 10 contiguous seconds with no SESs, or the onset period leading to the successful clearing condition, whichever occurs later. With respect to the DS1 error counts, all counters are incremented while the DS1 interface is deemed available. While the interface is deemed unavailable, the only count that is incremented is UASs.

Note that this definition implies that the agent cannot determine until after a ten second interval has passed whether a given one-second interval belongs to available or unavailable time. If the agent chooses to update the various performance statistics in real time then it must be prepared to retroactively reduce the ES, BES, SES, and SEFS counts by 10 and increase the UAS count by 10 when it determines that available time has been entered. It must also be prepared to adjust the PCV count and the DM count as necessary since these parameters are not accumulated during unavailable time. It must be similarly prepared to retroactively decrease the UAS count by 10 and increase the ES, BES, and DM counts as necessary upon entering available time. A special case exists when the 10 second period leading to available or unavailable time crosses a 900 second statistics window boundary, as the foregoing description implies that the ES, BES, SES, SEFS, DM, and UAS counts the PREVIOUS interval must be adjusted. In this case successive GETs of the affected dsx1IntervalSESs and dsx1IntervalUASs objects will return differing values if the first GET occurs during the first few seconds of the window.

The agent may instead choose to delay updates to the various statistics by 10 seconds in order to avoid retroactive adjustments to the counters. A way to do this is sketched in Appendix B.

In any case, a linkDown trap shall be sent only after the agent has determined for certain that the unavailable state has been entered, but the time on the trap will be that of the first UAS (i.e., 10 seconds earlier). A linkUp trap shall be handled similarly.

According to ANSI T1.231 unavailable time begins at the _onset_ of 10 contiguous severely errored seconds -- that is, unavailable time starts with the _first_ of the 10 contiguous SESs. Also, while an interface is deemed unavailable all counters for that interface are frozen except for the UAS count. It follows that an implementation which strictly complies with this standard must _not_ increment any counters other than the UAS count -- even temporarily -- as a result of anything that happens during those 10 seconds. Since changes in the signal state lag the data to which they apply by 10 seconds, an ANSI- compliant implementation must pass the the one-second statistics through a 10-second delay line prior to updating any counters. That can be done by performing the following steps at the end of each one second interval.

利用不能秒（UAS）

利用不能秒（UAS）は、インターフェイスが利用不能である秒数を数えることで計算されます。DS1インターフェイスは、10個の連続したSESの開始時点、または障害につながる状態の開始時点（障害状態を参照）から、利用不能であるといいます。障害につながる状態の直前に1つ以上の連続したSESがあった場合、DS1インターフェイスの利用不能はそれらのSESの開始時点から始まります。利用不能になったあと、障害が存在しない場合、DS1インターフェイスは、SESのない10個の連続した秒の開始時点で利用可能になります。利用不能になったあと、障害が存在する場合、障害の解除時間が10秒以下であれば、DS1インターフェイスは、SESのない10個の連続した秒の開始時点で利用可能になります。障害の解除時間が10秒を超える場合、DS1インターフェイスは、SESのない10個の連続した秒の開始時点か、解除が成功する状態につながる期間の開始時点のいずれか遅いほうで利用可能になります。DS1のエラーのカウントに関しては、DS1インターフェイスが利用可能とみなされている間、すべてのカウンターが増加します。インターフェイスが利用不能とみなされている間、増加する唯一のカウントはUASです。

この定義は、10秒の区間が経過したあとでなければ、エージェントがある1秒の区間が利用可能時間に属するのか利用不能時間に属するのかを判断できないことを意味することに注意してください。エージェントがさまざまな性能の統計をリアルタイムで更新することを選択する場合、利用可能時間に入ったと判断したときに、ES、BES、SES、およびSEFSのカウントを遡って10減らし、UASのカウントを10増やす準備をしなければなりません。これらのパラメーターは利用不能時間の間は累積されないため、PCVのカウントとDMのカウントを必要に応じて調整する準備もしなければなりません。同様に、利用可能時間に入るときには、UASのカウントを遡って10減らし、ES、BES、およびDMのカウントを必要に応じて増やす準備をしなければなりません。利用可能時間または利用不能時間につながる10秒の期間が900秒の統計のウィンドウの境界をまたぐ場合には特別なケースが存在します。前述の説明は、「前の」区間のES、BES、SES、SEFS、DM、およびUASのカウントを調整しなければならないことを意味するからです。この場合、最初のGETがウィンドウの最初の数秒の間に行われると、影響を受けるdsx1IntervalSESsとdsx1IntervalUASsのオブジェクトを連続してGETすると異なる値が返されます。

代わりに、エージェントは、カウンターを遡って調整することを避けるために、さまざまな統計の更新を10秒遅らせることを選択できます。これを行う方法の概略を付録Bで示します。

いずれの場合も、linkDownのトラップは、エージェントが利用不能状態に入ったことを確実に判断したあとでのみ送信されるものとしますが、トラップの時刻は最初のUASの時刻（すなわち10秒前）になります。linkUpのトラップも同様に扱われるものとします。

ANSI T1.231によると、利用不能時間は10個の連続した重大エラー秒の「開始時点」から始まります。すなわち、利用不能時間は10個の連続したSESの「最初」のものから始まります。また、インターフェイスが利用不能とみなされている間、そのインターフェイスのすべてのカウンターは、UASのカウントを除いて凍結されます。したがって、この標準に厳密に準拠する実装は、その10秒の間に起こったことの結果として、UASのカウント以外のカウンターを（一時的にであっても）増加させては「なりません」。信号の状態の変化は、それが適用されるデータから10秒遅れるため、ANSIに準拠する実装は、カウンターを更新する前に1秒ごとの統計を10秒の遅延線に通さなければなりません。これは、各1秒の区間の終わりに次の手順を実行することで行えます。

  1. Read near/far end CV counter and alarm status flags from the hardware.
  2. Accumulate the CV counts for the preceding second and compare them to the ES and SES threshold for the layer in question. Update the signal state and shift the one-second CV counts and ES/SES flags into the 10-element delay line. Note that far-end one-second statistics are to be flagged as "absent" during any second in which there is an incoming defect at the layer in question or at any lower layer.
  3. Update the current interval statistics using the signal state from the _previous_ update cycle and the one-second CV counts and ES/SES flags shifted out of the 10-element delay line.
  1. 近端/遠端のCVカウンターと警報の状態のフラグをハードウェアから読み取ります。
  2. 直前の秒のCVのカウントを累積し、対象の層のESとSESのしきい値と比較します。信号の状態を更新し、1秒ごとのCVのカウントとES/SESのフラグを10要素の遅延線にシフトします。遠端の1秒ごとの統計は、対象の層またはそれより下位の層で入力の欠陥がある秒の間は、「不在」としてフラグを立てることに注意してください。
  3. 「前の」更新サイクルの信号の状態と、10要素の遅延線からシフトアウトされた1秒ごとのCVのカウントとES/SESのフラグを使用して、現在の区間の統計を更新します。

This approach is further described in Appendix B.

この方法については、付録Bでさらに説明します。

2.4.4. Failure States

2.4.4. 障害状態

The following failure states are received, or detected failures, that are reported in the dsx1LineStatus object. When a DS1 interface would, if ever, produce the conditions leading to the failure state is described in the appropriate specification.

以下の障害状態は、受信された障害、または検出された障害であり、dsx1LineStatusオブジェクトで報告されます。DS1インターフェイスが（もしそうなるとすれば）いつ障害状態につながる状態を生じるかは、適切な仕様で説明されています。

Far End Alarm Failure

The Far End Alarm failure is also known as "Yellow Alarm" in the DS1 case, "Distant Alarm" in the E1 case, and "Remote Alarm" in the DS2 case.

For D4 links, the Far End Alarm failure is declared when bit 6 of all channels has been zero for at least 335 ms and is cleared when bit 6 of at least one channel is non-zero for a period T, where T is usually less than one second and always less than 5 seconds. The Far End Alarm failure is not declared for D4 links when a Loss of Signal is detected.

For ESF links, the Far End Alarm failure is declared if the Yellow Alarm signal pattern occurs in at least seven out of ten contiguous 16-bit pattern intervals and is cleared if the Yellow Alarm signal pattern does not occur in ten contiguous 16-bit signal pattern intervals.

For E1 links, the Far End Alarm failure is declared when bit 3 of time-slot zero is received set to one on two consecutive occasions. The Far End Alarm failure is cleared when bit 3 of time-slot zero is received set to zero.

For DS2 links, if a loss of frame alignment (LOF or LOS) and/or DS2 AIS condition, is detected, the RAI signal shall be generated and transmitted to the remote side.

The Remote Alarm Indication(RAI) signal is defined on m-bits as a repetition of the 16bit sequence consisting of eight binary '1s' and eight binary '0s' in m-bits(1111111100000000). When the RAI signal is not sent (in normal operation),the HDLC flag pattern (01111110) in the m-bit is sent.

The RAI failure is detected when 16 or more consecutive RAI- patterns (1111111100000000) are received. The RAI failure is cleared when 4 or more consecutive incorrect-RAI-patterns are received.

Alarm Indication Signal (AIS) Failure

The Alarm Indication Signal failure is declared when an AIS defect is detected at the input and the AIS defect still exists after the Loss Of Frame failure (which is caused by the unframed nature of the 'all-ones' signal) is declared. The AIS failure is cleared when the Loss Of Frame failure is cleared. (See T1.231 Section 6.2.1.2.1)

An AIS defect at a 6312 kbit/s (G.704) interface is detected when the incoming signal has two {2} or less ZEROs in a sequence of 3156 bits (0.5ms).

The AIS signal defect is cleared when the incoming signal has three {3} or more ZEROs in a sequence of 3156 bits (0.5ms).

Loss Of Frame Failure

For DS1 links, the Loss Of Frame failure is declared when an OOF or LOS defect has persisted for T seconds, where 2 <= T <= 10. The Loss Of Frame failure is cleared when there have been no OOF or LOS defects during a period T where 0 <= T <= 20. Many systems will perform "hit integration" within the period T before declaring or clearing the failure e.g., see TR 62411 [25].

For E1 links, the Loss Of Frame Failure is declared when an OOF defect is detected.

Loss Of Signal Failure

For DS1, the Loss Of Signal failure is declared upon observing 175 +/- 75 contiguous pulse positions with no pulses of either positive or negative polarity. The LOS failure is cleared upon observing an average pulse density of at least 12.5% over a period of 175 +/- 75 contiguous pulse positions starting with the receipt of a pulse.

For E1 links, the Loss Of Signal failure is declared when greater than 10 consecutive zeroes are detected (see O.162 Section 3.4`<.4).

A LOS defect at 6312kbit/s interfaces is detected when the incoming signal has "no transitions", i.e. when the signal level is less than or equal to a signal level of 35dB below nominal, for N consecutive pulse intervals, where 10 <=N<=255.

The LOS defect is cleared when the incoming signal has "transitions", i.e. when the signal level is greater than or equal to a signal level of 9dB below nominal, for N consecutive pulse intervals, where 10<=N<=255.

A signal with "transitions" corresponds to a G.703 compliant signal.

Loopback Pseudo-Failure
The Loopback Pseudo-Failure is declared when the near end equipment has placed a loopback (of any kind) on the DS1. This allows a management entity to determine from one object whether the DS1 can be considered to be in service or not (from the point of view of the near end equipment).
TS16 Alarm Indication Signal Failure
For E1 links, the TS16 Alarm Indication Signal failure is declared when time-slot 16 is received as all ones for all frames of two consecutive multiframes (see G.732 Section 4.2.6). This condition is never declared for DS1.
Loss Of MultiFrame Failure
The Loss Of MultiFrame failure is declared when two consecutive multiframe alignment signals (bits 4 through 7 of TS16 of frame 0) have been received with an error. The Loss Of Multiframe failure is cleared when the first correct multiframe alignment signal is received. The Loss Of Multiframe failure can only be declared for E1 links operating with G.732 [27] framing (sometimes called "Channel Associated Signalling" mode).
Far End Loss Of Multiframe Failure
The Far End Loss Of Multiframe failure is declared when bit 2 of TS16 of frame 0 is received set to one on two consecutive occasions. The Far End Loss Of Multiframe failure is cleared when bit 2 of TS16 of frame 0 is received set to zero. The Far End Loss Of Multiframe failure can only be declared for E1 links operating in "Channel Associated Signalling" mode. (See G.732)
DS2 Payload AIS Failure
The DS2 Payload AIS is detected when the incoming signal of the 6,312 kbps frame payload [TS1-TS96] has 2 or less 0's in a sequence of 3072 bits (0.5ms). The DS2 Payload AIS is cleared when the incoming signal of the 6,312 kbps frame payload [TS1- TS96] has 3 or more 0's in a sequence of 3072 bits (0.5 ms).
DS2 Performance Threshold

DS2 Performance Threshold Failure monitors equipment performance and is based on the CRC (Cyclic Redundancy Check) Procedure defined in G.704.

The DS2 Performance Threshold Failure is detected when the bit error ratio exceeds 10^-4 (Performance Threshold), and the DS2 Performance Threshold Failure shall be cleared when the bit error ratio decreased to less than 10^-6."

遠端警報の障害

遠端警報の障害は、DS1の場合は「イエローアラーム」、E1の場合は「遠隔警報（Distant Alarm）」、DS2の場合は「リモート警報（Remote Alarm）」としても知られています。

D4リンクでは、遠端警報の障害は、すべてのチャネルのビット6が少なくとも335ミリ秒の間0であった場合に宣言され、少なくとも1つのチャネルのビット6が期間Tの間0以外であった場合に解除されます。ここで、Tは通常1秒未満であり、常に5秒未満です。D4リンクでは、信号損失が検出された場合、遠端警報の障害は宣言されません。

ESFリンクでは、遠端警報の障害は、10個の連続した16ビットのパターンの区間のうち少なくとも7つでイエローアラームの信号パターンが発生した場合に宣言され、10個の連続した16ビットの信号パターンの区間でイエローアラームの信号パターンが発生しない場合に解除されます。

E1リンクでは、遠端警報の障害は、タイムスロット0のビット3が2回連続して1に設定されて受信された場合に宣言されます。遠端警報の障害は、タイムスロット0のビット3が0に設定されて受信された場合に解除されます。

DS2リンクでは、フレーム同期の損失（LOFまたはLOS）やDS2 AISの状態が検出された場合、RAI信号が生成され、リモート側に送信されるものとします。

リモート警報表示（RAI）信号は、mビット上で、8つの2進の「1」と8つの2進の「0」からなる16ビットの列の繰り返し（mビット(1111111100000000)）として定義されます。RAI信号が送信されない場合（通常の動作時）は、mビットでHDLCのフラグパターン（01111110）が送信されます。

RAIの障害は、16個以上の連続したRAIのパターン（1111111100000000）を受信した場合に検出されます。RAIの障害は、4個以上の連続した正しくないRAIのパターンを受信した場合に解除されます。

警報表示信号（AIS）の障害

警報表示信号の障害は、入力でAISの欠陥が検出され、（「すべて1」の信号のフレーム化されていない性質によって引き起こされる）フレーム損失の障害が宣言されたあとも、AISの欠陥が依然として存在する場合に宣言されます。AISの障害は、フレーム損失の障害が解除されたときに解除されます（T1.231のセクション6.2.1.2.1を参照）。

6312 kbit/s（G.704）のインターフェイスでのAISの欠陥は、入力信号の3156ビット（0.5ミリ秒）の列の中のゼロが2つ以下の場合に検出されます。

AIS信号の欠陥は、入力信号の3156ビット（0.5ミリ秒）の列の中のゼロが3つ以上の場合に解除されます。

フレーム損失の障害

DS1リンクでは、フレーム損失の障害は、OOFまたはLOSの欠陥がT秒（2 <= T <= 10）の間持続した場合に宣言されます。フレーム損失の障害は、期間T（0 <= T <= 20）の間OOFまたはLOSの欠陥がなかった場合に解除されます。多くのシステムは、障害を宣言または解除する前に、期間T内で「ヒット積分」を行います（例：TR 62411[25]を参照）。

E1リンクでは、フレーム損失の障害は、OOFの欠陥が検出された場合に宣言されます。

信号損失の障害

DS1では、信号損失の障害は、正と負のいずれの極性のパルスもない175 +/- 75個の連続したパルス位置を観測したときに宣言されます。LOSの障害は、パルスの受信から始まる175 +/- 75個の連続したパルス位置の期間にわたって、少なくとも12.5%の平均パルス密度を観測したときに解除されます。

E1リンクでは、信号損失の障害は、10個より多くの連続したゼロが検出された場合に宣言されます（O.162のセクション3.4`<.4を参照）。

6312kbit/sのインターフェイスでのLOSの欠陥は、入力信号に「遷移がない」場合、すなわち信号レベルが、N個（10 <=N<=255）の連続したパルスの区間の間、公称値より35dB低い信号レベル以下である場合に検出されます。

LOSの欠陥は、入力信号に「遷移がある」場合、すなわち信号レベルが、N個（10<=N<=255）の連続したパルスの区間の間、公称値より9dB低い信号レベル以上である場合に解除されます。

「遷移がある」信号は、G.703に準拠した信号に相当します。

ループバックの疑似障害
ループバックの疑似障害は、近端の機器がDS1上に（任意の種類の）ループバックを設定した場合に宣言されます。これにより、管理エンティティーは、1つのオブジェクトから、DS1が（近端の機器の観点から）サービス中であるとみなせるかどうかを判断できます。
TS16の警報表示信号の障害
E1リンクでは、TS16の警報表示信号の障害は、2つの連続したマルチフレームのすべてのフレームでタイムスロット16がすべて1として受信された場合に宣言されます（G.732のセクション4.2.6を参照）。この状態がDS1で宣言されることはありません。
マルチフレーム損失の障害
マルチフレーム損失の障害は、2つの連続したマルチフレーム同期信号（フレーム0のTS16のビット4から7）がエラーとともに受信された場合に宣言されます。マルチフレーム損失の障害は、最初の正しいマルチフレーム同期信号を受信したときに解除されます。マルチフレーム損失の障害は、G.732[27]のフレーミング（「チャネル関連シグナリング」モードと呼ばれることもあります）で動作しているE1リンクでのみ宣言できます。
遠端のマルチフレーム損失の障害
遠端のマルチフレーム損失の障害は、フレーム0のTS16のビット2が2回連続して1に設定されて受信された場合に宣言されます。遠端のマルチフレーム損失の障害は、フレーム0のTS16のビット2が0に設定されて受信された場合に解除されます。遠端のマルチフレーム損失の障害は、「チャネル関連シグナリング」モードで動作しているE1リンクでのみ宣言できます（G.732を参照）。
DS2ペイロードAISの障害
DS2ペイロードAISは、6,312 kbpsのフレームのペイロード[TS1-TS96]の入力信号が3072ビット（0.5ミリ秒）の列の中に2つ以下の0を持つ場合に検出されます。DS2ペイロードAISは、6,312 kbpsのフレームのペイロード[TS1- TS96]の入力信号が3072ビット（0.5ミリ秒）の列の中に3つ以上の0を持つ場合に解除されます。
DS2性能しきい値

DS2性能しきい値の障害は、機器の性能を監視するものであり、G.704で定義されているCRC（巡回冗長検査）の手順に基づいています。

DS2性能しきい値の障害は、ビット誤り率が10^-4（性能しきい値）を超えた場合に検出され、DS2性能しきい値の障害は、ビット誤り率が10^-6未満に減少した場合に解除されるものとします。"

2.4.5. Other Terms

2.4.5. その他の用語

Circuit Identifier
This is a character string specified by the circuit vendor, and is useful when communicating with the vendor during the troubleshooting process.
Proxy
In this document, the word proxy is meant to indicate an application which receives SNMP messages and replies to them on behalf of the devices which implement the actual DS3/E3 interfaces. The proxy may have already collected the information about the DS3/E3 interfaces into its local database and may not necessarily forward the requests to the actual DS3/E3 interface. It is expected in such an application that there are periods of time where the proxy is not communicating with the DS3/E3 interfaces. In these instances the proxy will not necessarily have up-to-date configuration information and will most likely have missed the collection of some statistics data. Missed statistics data collection will result in invalid data in the interval table.
回線識別子
これは、回線のベンダーが指定する文字列であり、トラブルシューティングの過程でベンダーと連絡を取る際に役立ちます。
プロキシー
この文書では、プロキシーという語は、SNMPメッセージを受信し、実際のDS3/E3インターフェイスを実装する機器に代わってそれに応答するアプリケーションを示すことを意図しています。プロキシーは、DS3/E3インターフェイスについての情報をすでにローカルのデータベースに収集している場合があり、要求を実際のDS3/E3インターフェイスに必ずしも転送しない場合があります。このようなアプリケーションでは、プロキシーがDS3/E3インターフェイスと通信していない期間があることが予想されます。そのような場合、プロキシーは必ずしも最新の構成情報を持っておらず、一部の統計データの収集を逃している可能性が高いです。統計データの収集を逃すと、区間テーブルのデータが無効になります。

     dsx1FracTable OBJECT-TYPE
          SYNTAX  SEQUENCE OF Dsx1FracEntry
          MAX-ACCESS  not-accessible
          STATUS  deprecated
          DESCRIPTION
                 "This table is deprecated in favour of using
                 ifStackTable.

                 The table was mandatory for systems dividing a DS1
                 into channels containing different data streams
                 that are of local interest.  Systems which are
                 indifferent to data content, such as CSUs, need
                 not implement it.

                 The DS1 fractional table identifies which DS1
                 channels associated with a CSU are being used to
                 support a logical interface, i.e., an entry in the
                 interfaces table from the Internet-standard MIB.

                 For example, consider an application managing a
                 North American ISDN Primary Rate link whose
                 division is a 384 kbit/s H1 _B_ Channel for Video,
                 a second H1 for data to a primary routing peer,

                 some subset of the H0 channels are used for voice
                 and the remainder are available for dynamic data
                 calls.

                 the DS1 interface. Six DS1 channels (for the sake
                 of the example, channels 1..6) are used for Video,
                 six more (7..11 and 13) are used for data, and the
                 remaining 12 are are in channels 12 and 14..24.

                 Let us further imagine that ifIndex 2 is of type
                 DS1 and refers to the DS1 interface, and that the
                 interfaces layered onto it are numbered 3..16.

                 We might describe the allocation of channels, in
                 the dsx1FracTable, as follows:

4. 付録A：dsx1IfIndexとdsx1LineIndexの使用

This Appendix exists to document the previous use if dsx1IfIndex and dsx1LineIndex and to clarify the relationship of dsx1LineIndex as defined in rfc1406 with the dsx1LineIndex as defined in this document.

この付録は、dsx1IfIndexとdsx1LineIndexの以前の使用を文書化し、rfc1406で定義されたdsx1LineIndexとこの文書で定義されたdsx1LineIndexとの関係を明確にするために存在します。

The following shows the old and new definitions and the relationship:

以下に、古い定義と新しい定義、およびその関係を示します。

[New Definition]: "This object should be made equal to ifIndex. The next paragraph describes its previous usage. Making the object equal to ifIndex allows proper use of ifStackTable and ds0/ds0bundle mibs.

[新しい定義]：「このオブジェクトはifIndexと等しくすべきです。次の段落ではその以前の使用法を説明します。オブジェクトをifIndexと等しくすることで、ifStackTableとds0/ds0bundleのMIBを適切に使用できます。

5. Appendix B - The delay approach to Unavialable Seconds.

5. 付録B：利用不能秒に対する遅延の方法

This procedure is illustrated below for a DS1 ESF interface. Similar rules would apply for other DS1, DS2, and E1 interface variants. The procedure guarantees that the statistical counters are correctly updated at all times, although they lag real time by 10 seconds. At the end of each 15 minutes interval the current interval counts are transferred to the most recent interval entry and each interval is shifted up by one position, with the oldest being discarded if necessary in order to make room. The current interval counts then start over from zero. Note, however, that the signal state calculation does not start afresh at each interval boundary; rather, signal state information is retained across interval boundaries.

以下では、この手順をDS1 ESFインターフェイスについて図示します。他のDS1、DS2、およびE1のインターフェイスの種類にも同様の規則が適用されます。この手順は、統計のカウンターが実時間より10秒遅れるものの、常に正しく更新されることを保証します。各15分の区間の終わりに、現在の区間のカウントは最新の区間のエントリーに転送され、各区間は1つずつ上にシフトされ、必要に応じて場所を空けるために最も古いものが破棄されます。その後、現在の区間のカウントは0からやり直します。ただし、信号の状態の計算は各区間の境界で新たに始まるわけではないことに注意してください。むしろ、信号の状態の情報は区間の境界をまたいで保持されます。

9. Security Considerations

9. セキュリティーに関する考慮事項

SNMPv1 by itself is such an insecure environment. Even if the network itself is secure (for example by using IPSec), even then, there is no control as to who on the secure network is allowed to access and GET (read) the objects in this MIB.

SNMPv1自体は、そのような安全でない環境です。ネットワーク自体が安全であっても（たとえば、IPSecを使用することによって）、その場合でも、安全なネットワーク上の誰がこのMIBのオブジェクトにアクセスしてGET（読み取り）できるかについての制御はありません。

It is recommended that the implementors consider the security features as provided by the SNMPv3 framework. Specifically, the use of the User-based Security Model RFC 2274 [12] and the View-based Access Control Model RFC 2275 [15] is recommended.

実装者は、SNMPv3フレームワークが提供するセキュリティーの機能を検討することが推奨されます。具体的には、ユーザーベースセキュリティーモデルRFC 2274[12]とビューベースアクセス制御モデルRFC 2275[15]の使用が推奨されます。

It is then a customer/user responsibility to ensure that the SNMP entity giving access to an instance of this MIB, is properly configured to give access to those objects only to those principals (users) that have legitimate rights to access them.

その場合、このMIBのインスタンスへのアクセスを提供するSNMPエンティティーが、それらのオブジェクトへのアクセスを正当な権利を持つプリンシパル（ユーザー）だけに与えるように適切に構成されていることを保証するのは、顧客/ユーザーの責任です。

Setting any of the following objects to an inappropriate value can cause loss of traffic. The definition of inappropriate varies for each object. In the case of dsx1LineType, for example, both ends of a ds1/e1 must have the same value in order for traffic to flow. In the case of dsx1SendCode and dsx1LoopbackConfig, for another example, traffic may stop transmitting when particular loopbacks are applied.

以下のオブジェクトのいずれかを不適切な値に設定すると、トラフィックが失われる可能性があります。不適切の定義はオブジェクトごとに異なります。たとえば、dsx1LineTypeの場合、トラフィックが流れるためには、ds1/e1の両端が同じ値を持たなければなりません。別の例として、dsx1SendCodeとdsx1LoopbackConfigの場合、特定のループバックが適用されるとトラフィックの送信が停止することがあります。

以下のオブジェクトを設定することはいたずらですが、トラフィックには害を与えません。
