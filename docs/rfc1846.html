RFC 1846

SMTP 521 Reply Code

RFC 1846

SMTP 521応答コード

Abstract

概要

This memo defines a new Simple Mail Transfer Protocol (SMTP) [1] reply code, 521, which one may use to indicate that an Internet host does not accept incoming mail.

このメモは、インターネットホストが受信メールを受け付けないことを示すために使用できる、新しいSimple Mail Transfer Protocol（SMTP）[1]の応答コード521を定義します。

Status of This Memo

このメモのステータス

This memo defines an Experimental Protocol for the Internet community. This memo does not specify an Internet standard of any kind. Discussion and suggestions for improvement are requested. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーのための実験的なプロトコルを定義します。これは、いかなる種類のインターネット標準も規定するものではありません。改善のための議論と提案を求めます。このメモの配布は無制限です。

1. Motivations

1. 動機

Hosts on the Internet have shifted from large, general-purpose hosts to smaller, more specialized hosts. There is an increasing number of hosts which are dedicated to specific tasks, such as serving NTP or DNS. These dedicated hosts frequently do not provide mail service.

インターネット上のホストは、大規模な汎用ホストから、より小規模で特化したホストへと移り変わってきました。NTPやDNSの提供といった特定の作業に専念するホストが増えています。こうした専用ホストは、多くの場合メールサービスを提供しません。

Usually, these mailless hosts do not run an SMTP server. Unfortunately, users will occasionally misaddress mail to these hosts. Regular SMTP clients attempting to deliver this misaddressed mail must treat the lack of an SMTP server on the host as a temporary error. They must queue the mail for later delivery, should an SMTP server be started at a later time.

通常、こうしたメールを扱わないホストではSMTPサーバーを動かしていません。あいにく、ユーザーはときおり、こうしたホストを宛先にして誤ってメールを送ってしまいます。この宛先を誤ったメールを配送しようとする通常のSMTPクライアントは、ホストにSMTPサーバーがないことを一時的なエラーとして扱わなければなりません。後でSMTPサーバーが起動した場合に備えて、メールを後で配送するためにキューに入れておかなければなりません。

This causes the mail to remain queued for days, until it is returned with what is usually a confusing error message.

このため、メールは何日もキューに残り続け、最終的にたいていは分かりにくいエラーメッセージとともに返送されます。

2. Two complementary solutions

2. 2つの相補的な解決策

Two complementary solutions MAY be implemented to deal with this issue. The first one is to use MX relays to bounce misaddressed mails. The second one is to implement a minimal smtp server on the mailless host to bounce all mails.

この問題に対処するために、2つの相補的な解決策を実装してもよいです（MAY）。1つ目は、MXリレーを使って宛先を誤ったメールをバウンスする方法です。2つ目は、メールを扱わないホスト上に、すべてのメールをバウンスする最小限のSMTPサーバーを実装する方法です。

The choice between the two solutions is site dependent.

2つの解決策のどちらを選ぶかはサイトによります。

3. The MX relays solution

3. MXリレーによる解決策

MX relays may be used to indicate SMTP clients that an Internet host does not accept mail.

MXリレーを使って、インターネットホストがメールを受け付けないことをSMTPクライアントに示すことができます。

During the SMTP dialog, these MX relays MAY bounce any message destinated to this particular host with an SMTP 521 reply code.

SMTPの対話の中で、これらのMXリレーは、その特定のホスト宛てのメッセージをSMTPの521応答コードでバウンスしてもよいです（MAY）。

SMTP dialog example:

SMTPの対話の例：

---> 220 relay.imag.fr ready
<--- HELO client.inria.fr
---> 250 relay.imag.fr Hello client.inria.fr
<--- MAIL FROM: <user1@client.inria.fr>
---> 250 <user1@client.inria.fr>... Sender Ok
<--- RCPT TO: <user2@nomail.imag.fr>
---> 521 nomail.imag.fr does not accept mail
<--- QUIT
---> 221 relay.imag.fr closing connection

---> 220 relay.imag.fr ready
<--- HELO client.inria.fr
---> 250 relay.imag.fr Hello client.inria.fr
<--- MAIL FROM: <user1@client.inria.fr>
---> 250 <user1@client.inria.fr>... Sender Ok
<--- RCPT TO: <user2@nomail.imag.fr>
---> 521 nomail.imag.fr does not accept mail
<--- QUIT
---> 221 relay.imag.fr closing connection

If an MX relay of precedence n for a mailless host bounces mails on its behalf, then any other MX relay of precedence lower than n for this mailless host SHOULD do the same.

メールを扱わないホストに対する優先度nのMXリレーが、そのホストに代わってメールをバウンスする場合、そのメールを扱わないホストに対する優先度がnより低い他のMXリレーも同じようにするべきです（SHOULD）。

4. The SMTP server solution

4. SMTPサーバーによる解決策

4.1. 521 greeting

4.1. 521グリーティング

A host may indicate that it does not accept mail by sending an initial 521 "Host does not accept mail" reply to an incoming SMTP connection. The official name of the server host or its IP address MUST be sent as the first word following the reply code.

ホストは、SMTPの接続を受けたときに最初に521「Host does not accept mail」応答を送ることで、メールを受け付けないことを示せます。サーバーホストの正式名またはIPアドレスを、応答コードに続く最初の語として送らなければなりません（MUST）。

For example: 521 canon.inria.fr does not accept mail

例: 521 canon.inria.fr does not accept mail

4.2. SMTP dialog

4.2. SMTPの対話

After issuing the initial 521 reply, the server host MUST do one of the following two options:

最初の521応答を送った後、サーバーホストは次の2つの選択肢のいずれかを実行しなければなりません（MUST）。

  1. Close the SMTP connection.
  2. Read commands, issuing 521 replies to all commands except QUIT. If the SMTP client does not issue the QUIT command after a reasonable time, the SMTP server MUST time out and close the connection. A suggested time-out value is 5 minutes.
  1. SMTPの接続を閉じる。
  2. コマンドを読み取り、QUIT以外のすべてのコマンドに521応答を返す。妥当な時間が経過してもSMTPクライアントがQUITコマンドを送らない場合、SMTPサーバーはタイムアウトして接続を閉じなければなりません（MUST）。タイムアウト値としては5分を提案します。

DISCUSSION:

議論：

When an SMTP server closes the connection immediatly after issuing the initial 521 reply, some existing SMTP clients treat the condition as a transient error and requeue the mail for later delivery. If the SMTP server leaves the connection open, those clients immediately send the QUIT command and return the mail.

SMTPサーバーが最初の521応答を送った直後に接続を閉じると、既存のSMTPクライアントの中には、この状況を一時的なエラーとして扱い、メールを後で配送するために再びキューに入れるものがあります。SMTPサーバーが接続を開いたままにしておけば、そうしたクライアントはすぐにQUITコマンドを送ってメールを返送します。

4.3. MX

4.3. MX

A host which sends a 521 greeting message MUST NOT be listed as an MX record for any domain.

521のグリーティングメッセージを送るホストは、どのドメインに対してもMXレコードに載せてはなりません（MUST NOT）。

4.4. Postmaster

4.4. Postmaster

An SMTP server which sends a 521 greeting message IS NOT subject to the postmaster requirement of STD 3, RFC 1123 ([2]).

521のグリーティングメッセージを送るSMTPサーバーは、STD 3、RFC 1123（[2]）のpostmasterに関する要件の対象外です（IS NOT）。

DISCUSSION:

議論：

Postmaster exists so you can report mail errors. A host that doesn't support mail doesn't need a Postmaster.

Postmasterは、メールのエラーを報告できるようにするために存在します。メールをサポートしないホストにPostmasterは必要ありません。

5. SMTP client behavior

5. SMTPクライアントの動作

If an SMTP client encounters a host in an MX record that issues a 521 greeting message, it must do one of the following two options:

SMTPクライアントは、MXレコードに載っているホストが521のグリーティングメッセージを送ってきた場合、次の2つの選択肢のいずれかを実行しなければなりません。

  1. Attempt to deliver it to a different MX host for that domain.
  2. Return the mail with an appropriate non-delivery report.
  1. そのドメインの別のMXホストへの配送を試みる。
  2. 適切な配送不能通知を付けてメールを返送する。

If an SMTP client encounters a 521 reply code in any other part of the SMTP dialog, it MUST return the mail with an appropriate non-delivery report.

SMTPの対話のそれ以外の部分で521応答コードを受け取った場合、SMTPクライアントは適切な配送不能通知を付けてメールを返送しなければなりません（MUST）。

6. Security Considerations

6. セキュリティーに関する考慮事項

Not running any SMTP server, or running an SMTP server which simply emits fixed strings in response to incoming connection should provide significantly fewer opportunities for security problems than running a complete SMTP implementation.

SMTPサーバーをまったく動かさない、あるいは接続を受けたときに固定の文字列を返すだけのSMTPサーバーを動かすことは、完全なSMTP実装を動かす場合に比べて、セキュリティー上の問題が生じる機会を大幅に減らすはずです。
