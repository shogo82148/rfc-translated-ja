RFC 9894

Dynamic Link Exchange Protocol (DLEP) Diffserv Aware Credit Window Extension

RFC 9894

動的リンク交換プロトコル（DLEP）のDiffserv対応クレジットウィンドウ拡張

Abstract

概要

This document defines an extension to the Dynamic Link Exchange Protocol (DLEP) that enables a Diffserv aware credit window scheme for destination-specific and shared flow control.

この文書は、動的リンク交換プロトコル（Dynamic Link Exchange Protocol; DLEP）の拡張を定義します。 この拡張により、宛先ごとのフロー制御と共有フロー制御のための、Diffservを考慮したクレジットウィンドウ方式が可能になります。

1. Introduction

1. はじめに

The Dynamic Link Exchange Protocol (DLEP) is defined in [RFC8175]. The protocol provides the exchange of link-related control information between DLEP peers. DLEP peers consist of a modem and a router. DLEP defines a base set of mechanisms as well as support for possible extensions. This document defines one such extension.

動的リンク交換プロトコル（DLEP）は[RFC8175]で定義されています。 このプロトコルは、DLEPピア間でリンク関連の制御情報を交換する手段を提供します。 DLEPピアはモデムとルーターで構成されます。 DLEPは、基本的なメカニズムの集合と、拡張を可能にする仕組みを定義しています。 この文書は、そのような拡張の1つを定義します。

The DLEP specification does not include any flow control capability. Various flow control techniques are theoretically possible with DLEP. This document defines a DLEP extension that provides a Diffserv-based flow control mechanism for traffic sent from a router to a modem. Flow control is provided using one or more logical "credit windows", each of which will typically be supported by an associated virtual or physical queue. A router will use traffic flow classification information provided by the modem to identify which traffic is associated with each credit window. Credit windows may be shared or dedicated on a per-flow basis. See [RFC9895] for an Ethernet-based version of credit window flow control. As specified in Section 2.3.1 of [RFC9892], when both Diffserv and Ethernet traffic classification are specified for a flow, the Ethernet information takes precedence.

DLEPの仕様には、フロー制御の機能は含まれていません。 DLEPでは、理論上さまざまなフロー制御の手法が可能です。 この文書は、ルーターからモデムへ送信されるトラフィックに対して、Diffservに基づくフロー制御メカニズムを提供するDLEP拡張を定義します。 フロー制御は、1つ以上の論理的な「クレジットウィンドウ（credit window）」を使って提供されます。 各クレジットウィンドウは通常、それに関連付けられた仮想キューまたは物理キューによってサポートされます。 ルーターは、モデムから提供されるトラフィックフロー分類情報を使って、どのトラフィックがどのクレジットウィンドウに関連付けられているかを識別します。 クレジットウィンドウは、フローごとに共有することも、専用にすることもできます。 イーサネットに基づくバージョンのクレジットウィンドウフロー制御については、[RFC9895]を参照してください。 [RFC9892]のSection 2.3.1で規定されているとおり、 あるフローに対してDiffservとイーサネットの両方のトラフィック分類が指定されている場合は、イーサネットの情報が優先されます。

This document uses the traffic classification and credit window flow control mechanisms defined in [RFC9892] and [RFC9893] to provide credit-window-based flow control based on DLEP destinations and Differentiated Services Code Points (DSCPs) [RFC2475]. The defined mechanism allows for credit windows to be shared across traffic sent to multiple DLEP destinations and DSCPs, or used exclusively for traffic sent to a particular destination and/or DSCP. The extension also supports the "wildcard" matching of any DSCP.

この文書は、[RFC9892]と[RFC9893]で定義されたトラフィック分類とクレジットウィンドウフロー制御のメカニズムを使って、 DLEPの宛先と差別化サービスコードポイント（Differentiated Services Code Point; DSCP）[RFC2475]に基づく、クレジットウィンドウベースのフロー制御を提供します。 ここで定義するメカニズムにより、クレジットウィンドウを、複数のDLEP宛先やDSCPに送信されるトラフィックの間で共有することも、 特定の宛先とDSCPの一方または両方に送信されるトラフィック専用に使うこともできます。 この拡張は、任意のDSCPに一致する「ワイルドカード」マッチングもサポートします。

The extension defined in this document is referred to as the "Diffserv Aware Credit Window" or, more simply, the "DA Credit" extension. The reader should be familiar with both the traffic classification and credit window flow control mechanisms defined in [RFC9892] and [RFC9893].

この文書で定義する拡張を「Diffserv対応クレジットウィンドウ（Diffserv Aware Credit Window）」拡張、 あるいはより簡潔に「DAクレジット（DA Credit）」拡張と呼びます。 読者は、[RFC9892]と[RFC9893]で定義されているトラフィック分類とクレジットウィンドウフロー制御の両方のメカニズムを理解しておく必要があります。

This document defines a new DLEP Extension Type value that is used to indicate support for the extension. See Section 2.

この文書は、この拡張のサポートを示すために使われる、新しいDLEP拡張タイプ（Extension Type）の値を定義します。 Section 2を参照してください。

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

2. Extension Usage and Identification

2. 拡張の使用と識別

The extension defined in this document is built on the mechanisms and processing defined in [RFC9892] and [RFC9893]. To indicate that the Diffserv Aware Credit Window Extension is to be used, an implementation MUST include the Diffserv Aware Credit Window Extension Type value in the Extensions Supported Data Item (see Section 13.6 of [RFC8175]). The Extensions Supported Data Item is sent and processed according to [RFC8175]. Any implementation that indicates the use of the Diffserv Aware Credit Window Extension MUST support all message types, Data Items, the Diffserv Traffic Classification Sub-Data Item, and all related processing defined in [RFC9892] and [RFC9893].

この文書で定義する拡張は、[RFC9892]と[RFC9893]で定義されたメカニズムと処理の上に構築されています。 Diffserv対応クレジットウィンドウ拡張を使用することを示すために、 実装は拡張サポートデータ項目（Extensions Supported Data Item）にDiffserv対応クレジットウィンドウ拡張タイプの値を含めなければなりません（MUST） （[RFC8175]のSection 13.6を参照）。 拡張サポートデータ項目は、[RFC8175]に従って送信および処理されます。 Diffserv対応クレジットウィンドウ拡張の使用を示す実装は、 [RFC9892]と[RFC9893]で定義されているすべてのメッセージタイプ、データ項目、Diffservトラフィック分類サブデータ項目（Diffserv Traffic Classification Sub-Data Item）、 および関連するすべての処理をサポートしなければなりません（MUST）。

The Diffserv Aware Credit Window Extension Type value is 6. See Section 5.

Diffserv対応クレジットウィンドウ拡張タイプの値は6です。 Section 5を参照してください。

3. Management Considerations

3. 管理に関する考慮事項

This section provides several network management guidelines for implementations supporting the Diffserv Aware Credit Window Extension.

このセクションでは、Diffserv対応クレジットウィンドウ拡張をサポートする実装向けに、いくつかのネットワーク管理のガイドラインを示します。

If this extension is supported, that support MUST be declared using the Extensions Supported Data Item (see Section 13.6 of [RFC8175]). Diffserv Aware Credit Window Extension Data Items MUST NOT be emitted by a DLEP participant unless such support was specified in the initialization message received from its peer. The use of the extension defined in this document SHOULD be configurable on both modems and routers. That configuration can be implemented using a proprietary Command-Line Interface or by implementing a YANG module. The definition of the YANG module is out of scope for this document.

この拡張をサポートする場合、そのサポートを拡張サポートデータ項目を使って宣言しなければなりません（MUST） （[RFC8175]のSection 13.6を参照）。 DLEP参加者は、ピアから受信した初期化メッセージでそのサポートが示されていない限り、 Diffserv対応クレジットウィンドウ拡張のデータ項目を送出してはなりません（MUST NOT）。 この文書で定義する拡張の使用は、モデムとルーターの両方で設定可能であるべきです（SHOULD）。 その設定は、独自のコマンドラインインターフェイスを使って実装することも、YANGモジュールを実装することによって実現することもできます。 YANGモジュールの定義は、この文書の範囲外です。

Modems SHOULD support the configuration of mapping a DSCP to a credit window (queue).

モデムは、DSCPをクレジットウィンドウ（キュー）へマッピングする設定をサポートすべきです（SHOULD）。

Modems MAY support the configuration of the number of credit windows (queues) to advertise to a router.

モデムは、ルーターに通知するクレジットウィンドウ（キュー）の数の設定をサポートしてもよいです（MAY）。

Routers may have limits on the number of queues that they can support and limits on supported credit window combinations. Per-destination queues might not be supported at all. When credit window information provided by a modem exceeds the capabilities of a router, the router SHOULD use a subset of the provided credit windows. Alternatively, a router MAY reset the session and indicate that the extension is not supported. In either case, any mismatch in capabilities SHOULD be reported to the user via normal network management mechanisms, such as user interface messages or error logging.

ルーターには、サポートできるキューの数や、サポートするクレジットウィンドウの組み合わせに制限がある場合があります。 宛先ごとのキューがまったくサポートされていない場合もあります。 モデムから提供されたクレジットウィンドウ情報がルーターの能力を超える場合、 ルーターは提供されたクレジットウィンドウのサブセットを使用すべきです（SHOULD）。 あるいは、ルーターはセッションをリセットし、この拡張がサポートされていないことを示してもよいです（MAY）。 いずれの場合も、能力の不一致は、ユーザーインターフェイスのメッセージやエラーログなど、通常のネットワーク管理メカニズムを通じてユーザーに報告すべきです（SHOULD）。

In all cases, if credit windows are in use, traffic for which credits are not available MUST NOT be sent to the modem by the router.

いかなる場合でも、クレジットウィンドウが使用されているときは、 ルーターはクレジットが利用できないトラフィックをモデムへ送信してはなりません（MUST NOT）。

4. Security Considerations

4. セキュリティーに関する考慮事項

This document defines a DLEP extension that uses DLEP mechanisms and the credit window flow control mechanisms defined in [RFC9892] and [RFC9893]. See also the Security Considerations sections of those documents.

この文書は、DLEPのメカニズムと、[RFC9892]と[RFC9893]で定義されたクレジットウィンドウフロー制御のメカニズムを使用するDLEP拡張を定義します。 それらの文書のセキュリティーに関する考慮事項のセクションも参照してください。

The defined extension is exposed to vulnerabilities similar to existing DLEP messages and discussed in the Security Considerations section of [RFC8175], such as an injected message resizing a credit window to a value that results in a denial of service. The security mechanisms documented in [RFC8175] can be applied equally to the mechanism defined in this document.

ここで定義する拡張は、既存のDLEPメッセージと同様の脆弱性にさらされます。 これは[RFC8175]のセキュリティーに関する考慮事項のセクションで議論されているもので、 たとえば、注入されたメッセージによってクレジットウィンドウのサイズがサービス拒否を引き起こす値に変更される、といったものです。 [RFC8175]に記載されているセキュリティーメカニズムは、この文書で定義するメカニズムにも同様に適用できます。

Wildcards for matching Priority Code Point (PCP) and VLAN Identifier (VID) fields (see [RFC9895]) are provided. Note that wildcards may be convenient for matching a number of packet flows but could inadvertently match unexpected flows or new flows that appear after the wildcard matching has been set up. It is therefore RECOMMENDED that wildcards not be used unless needed.

優先度コードポイント（Priority Code Point; PCP）とVLAN識別子（VLAN Identifier; VID）のフィールドに一致させるためのワイルドカードが提供されています （[RFC9895]を参照）。 ワイルドカードは多数のパケットフローに一致させるのに便利ですが、 意図せず予期しないフローや、ワイルドカードマッチングを設定した後に現れる新しいフローに一致してしまう可能性があることに注意してください。 したがって、必要な場合を除き、ワイルドカードを使用しないことが推奨されます（RECOMMENDED）。
