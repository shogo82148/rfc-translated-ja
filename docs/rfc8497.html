RFC 8497

Marking SIP Messages to Be Logged

RFC 8497

ログに記録するSIPメッセージのマーキング

Abstract

概要

SIP networks use signaling monitoring tools to diagnose user-reported problems and to perform regression testing if network or user agent (UA) software is upgraded. As networks grow and become interconnected, including connection via transit networks, it becomes impractical to predict the path that SIP signaling will take between user agents and therefore impractical to monitor SIP signaling end to end.

SIPネットワークでは、ユーザーから報告された問題を診断したり、ネットワークやユーザーエージェント（UA）のソフトウェアをアップグレードした場合に回帰テストを実施したりするために、シグナリング監視ツールを使用します。ネットワークが成長し、トランジットネットワーク経由の接続も含めて相互に接続されるようになると、SIPシグナリングがユーザーエージェント間でたどる経路を予測することは現実的ではなくなり、したがってSIPシグナリングをエンドツーエンドで監視することも現実的ではなくなります。

This document describes an indicator for the SIP protocol that can be used to mark signaling as being of interest to logging. Such marking will typically be applied as part of network testing controlled by the network operator and is not used in normal user agent signaling. Operators of all networks on the signaling path can agree to carry such marking end to end, including the originating and terminating SIP user agents, even if a session originates and terminates in different networks.

この文書は、シグナリングをロギングの対象としてマーキングするために使用できる、SIPプロトコル用のインジケーターについて説明します。このようなマーキングは、通常、ネットワーク事業者が制御するネットワークテストの一環として適用されるものであり、通常のユーザーエージェントのシグナリングでは使用されません。シグナリング経路上のすべてのネットワークの事業者は、セッションが異なるネットワークで開始および終了する場合であっても、発信側と着信側のSIPユーザーエージェントを含めて、このようなマーキングをエンドツーエンドで運ぶことに合意できます。

1. Introduction

1. はじめに

When users experience problems with setting up sessions using SIP, enterprise or service provider network operators often have to identify the root cause by examining the SIP signaling. Also, when network or user agent (UA) software or hardware is upgraded, regression testing is needed. Such diagnostics apply to a small proportion of network traffic and can apply end to end, even if signaling crosses several networks possibly belonging to several different network operators. It may not be possible to predict the path through those networks in advance, therefore, a mechanism is needed to mark a session as being of interest so that SIP entities along the signaling path can provide diagnostic logging. [RFC8123] illustrates this motivating scenario. This document describes a solution that meets the requirements for such "log me" marking of SIP signaling also defined in [RFC8123].

ユーザーがSIPを使用したセッションの確立で問題に遭遇した場合、企業やサービスプロバイダーのネットワーク事業者は、多くの場合、SIPシグナリングを調べて根本原因を特定しなければなりません。また、ネットワークやユーザーエージェント（UA）のソフトウェアやハードウェアをアップグレードした場合には、回帰テストが必要です。このような診断はネットワークトラフィックのごく一部に適用されるものであり、シグナリングが複数の異なるネットワーク事業者に属する可能性のある複数のネットワークを横断する場合であっても、エンドツーエンドで適用できます。それらのネットワークを通る経路を事前に予測できない場合があるため、シグナリング経路上のSIPエンティティーが診断用のロギングを提供できるように、セッションを関心の対象としてマーキングするメカニズムが必要です。[RFC8123]は、この動機となるシナリオを説明しています。この文書は、同じく[RFC8123]で定義されている、SIPシグナリングに対するそのような"log me"マーキングの要件を満たす解決策について説明します。

This document also defines a new header field parameter, "logme", for the Session-ID header field [RFC7989]. Implementations of this document MUST implement [RFC7989].

この文書は、Session-IDヘッダーフィールド[RFC7989]に対する新しいヘッダーフィールドパラメーター"logme"も定義します。この文書の実装は、[RFC7989]を実装しなければなりません（MUST）。

3. "Log Me" Marking Protocol Aspects

3. "Log Me"マーキングのプロトコル面

3.1. Session-ID "logme" Parameter

3.1. Session-IDの"logme"パラメーター

Logging for diagnostic purposes is most effective when it is applied end to end in a communication session. This ability requires a "log me" marker to be passed through SIP intermediaries. The Session-ID header field defined in [RFC7989] was chosen to carry the "log me" marker as a "logme" parameter since the session identifier is typically passed through SIP Back-to-Back User Agents (B2BUAs) (described in [RFC7092]) or other intermediaries, as per the Session-ID requirement REQ3 in [RFC7206]. The "logme" parameter shown in Figure 1 does not introduce any device-specific or user-specific information and MUST be passed unchanged with the Session-ID header field. There is an exception, however, for the cases specified in Section 3.4.2 where the "log me" marker may be removed at a network boundary.

診断目的のロギングは、通信セッションにおいてエンドツーエンドで適用されたときに最も効果的です。これを可能にするには、"log me"マーカーがSIP仲介者を通過して渡される必要があります。[RFC7206]のSession-IDの要件REQ3にあるとおり、セッション識別子は通常、（[RFC7092]で説明されている）SIPバックツーバックユーザーエージェント（B2BUA）やその他の仲介者を通過して渡されるため、[RFC7989]で定義されたSession-IDヘッダーフィールドが、"log me"マーカーを"logme"パラメーターとして運ぶものとして選ばれました。図1に示す"logme"パラメーターは、デバイス固有の情報やユーザー固有の情報を一切持ち込まず、Session-IDヘッダーフィールドとともに変更されずに渡されなければなりません（MUST）。ただし、例外として、セクション3.4.2で規定するケースでは、"log me"マーカーがネットワーク境界で削除される場合があります。

3.2. Starting and Stopping Logging

3.2. ロギングの開始と停止

If a dialog is to be "log me" marked, then marking MUST start with the SIP request that initiates that dialog (dialog-initiating requests are described in Section 12.1 of [RFC3261]). For the most effective testing and troubleshooting, marking continues for the lifetime of the dialog, applies to each request and response in the dialog, and applies uninterrupted end to end (including user devices). The "log me" marking mechanism described in this document allows for parts of the signaling path to not be marked, e.g, because an endpoint does not support the "log me" marking mechanism (see Section 4.5.2) or because an endpoint or intermediary deliberately removes the "log me" marker (see Section 4.5.2.4). Also, marking errors can terminate marking before the dialog ends (see Section 5.3).

ダイアログを"log me"マーキングする場合、マーキングはそのダイアログを開始するSIPリクエストから始めなければなりません（MUST）（ダイアログを開始するリクエストについては[RFC3261]のセクション12.1で説明されています）。最も効果的なテストとトラブルシューティングのために、マーキングはダイアログの存続期間中継続し、ダイアログ内の各リクエストと各レスポンスに適用され、（ユーザーデバイスを含めて）エンドツーエンドで途切れることなく適用されます。この文書で説明する"log me"マーキングメカニズムでは、たとえばエンドポイントが"log me"マーキングメカニズムに対応していない（セクション4.5.2を参照）ため、あるいはエンドポイントや仲介者が意図的に"log me"マーカーを削除する（セクション4.5.2.4を参照）ために、シグナリング経路の一部がマーキングされないことを許容します。また、マーキングのエラーによって、ダイアログが終了する前にマーキングが終了することもあります（セクション5.3を参照）。

A UA or intermediary adds a "log me" marker in an unmarked request or response in two cases: first, because it is configured to add the marking to a dialog-creating request, or second, because it has received a dialog-creating request that is being "log me" marked causing it to maintain state to ensure that all requests and responses in the dialog are similarly "log me" marked. Once the "log me" marking is started for a dialog, all subsequent requests and responses in this dialog are "log me" marked. Marking is stopped when this dialog and its related dialogs end. It is considered an error (see Section 5.1.2) if "log me" marking is started in a mid-dialog request or response.

UAや仲介者がマーキングされていないリクエストやレスポンスに"log me"マーカーを追加するケースは2つあります。1つ目は、ダイアログを作成するリクエストにマーキングを追加するように設定されている場合です。2つ目は、"log me"マーキングされたダイアログを作成するリクエストを受信したことで、ダイアログ内のすべてのリクエストとレスポンスが同様に"log me"マーキングされるように状態を維持する場合です。あるダイアログで"log me"マーキングが開始されると、そのダイアログ内の後続のすべてのリクエストとレスポンスは"log me"マーキングされます。マーキングは、このダイアログとその関連するダイアログが終了したときに停止します。ダイアログの途中のリクエストやレスポンスで"log me"マーキングが開始された場合は、エラーとみなされます（セクション5.1.2を参照）。

For the first case, "log me" marking trigger condition configurations that define whether a UA or intermediary can initiate "log me" marking for a given dialog are out of scope of this document. As an example of trigger condition configurations, the UA or intermediary could be configured to add a "log me" marker for all dialogs initiated during a specific time period (e.g., 9:00 am - 10:00 am every day) or for specific dialogs that have a particular "User-Agent" header field value. They could also be configured to add a "log me" marker for a specific set of called party numbers for which users are experiencing call setup failures.

1つ目のケースについて、UAや仲介者が特定のダイアログに対して"log me"マーキングを開始できるかどうかを定義する"log me"マーキングのトリガー条件の設定は、この文書の範囲外です。トリガー条件の設定の例として、UAや仲介者は、特定の期間（たとえば毎日午前9時から午前10時まで）に開始されたすべてのダイアログや、特定の"User-Agent"ヘッダーフィールド値を持つ特定のダイアログに"log me"マーカーを追加するように設定できます。また、ユーザーが呼の確立に失敗している特定の被呼者番号の集合に対して"log me"マーカーを追加するように設定することもできます。

For the second case of a UA or intermediary detecting that a dialog-initiating request is being "log me" marked, the scope of such marking extends to the lifetime of the dialog. In addition, as discussed in Section 3.7, "log me" marked dialogs that create related dialogs (e.g., REFER) may transfer the marking to the related dialogs. In such cases, the entire "session", identified by the Session-ID header field, is "log me" marked.

UAや仲介者が、ダイアログを開始するリクエストが"log me"マーキングされていることを検出する2つ目のケースでは、そのマーキングの範囲はダイアログの存続期間にわたります。さらに、セクション3.7で説明するように、関連するダイアログ（たとえばREFER）を作成する"log me"マーキングされたダイアログは、そのマーキングを関連するダイアログに引き継ぐ場合があります。そのような場合には、Session-IDヘッダーフィールドによって識別される"session"全体が"log me"マーキングされます。

3.3. Identifying Test Cases

3.3. テストケースの識別

The local Universally Unique Identifier (UUID) portion of the Session-ID header field value [RFC7989] in the initial SIP request of a dialog is used as a random test case identifier (described in REQ 5 in [RFC8123]). This provides the ability to collate all logged SIP requests and responses to the initial SIP request in a dialog or standalone transaction.

ダイアログの最初のSIPリクエストに含まれるSession-IDヘッダーフィールド値[RFC7989]のローカルなUniversally Unique Identifier（UUID）部分は、（[RFC8123]のREQ 5で説明されている）ランダムなテストケース識別子として使用されます。これにより、ログに記録されたすべてのSIPリクエストとレスポンスを、ダイアログまたは単独のトランザクションにおける最初のSIPリクエストと照合できるようになります。

3.4. Passing the Marker

3.4. マーカーの受け渡し

3.4.1. To/From a User Device

3.4.1. ユーザーデバイスとの間

When a user device inserts the "log me" marker, the marker MUST be passed unchanged in the Session-ID header field across an edge proxy or a B2BUA adjacent to the user device.

ユーザーデバイスが"log me"マーカーを挿入した場合、そのマーカーは、ユーザーデバイスに隣接するエッジプロキシーやB2BUAをまたいで、Session-IDヘッダーフィールド内で変更されずに渡されなければなりません（MUST）。

3.4.2. To/From an External Network

3.4.2. 外部ネットワークとの間

An external network is a peer network connected at a network boundary as defined in [RFC8123].

外部ネットワークとは、[RFC8123]で定義されているネットワーク境界で接続されたピアネットワークです。

External networks may be connected directly or via a peering network, and such networks often have specific connection agreements. Whether "log me" marking is removed depends on the policy applied at the network-to-network interface. Troubleshooting and testing will be easier if peer networks endeavor to make agreements to pass "log me" marking unchanged. However, since a "log me" marker may cause a SIP entity to log the SIP header and body of a request or response, the "log me" marker MUST be removed at a network boundary if no agreement exists between peer networks.

外部ネットワークは、直接接続される場合もあれば、ピアリングネットワーク経由で接続される場合もあり、そのようなネットワークには多くの場合、固有の接続協定があります。"log me"マーキングが削除されるかどうかは、ネットワーク間インターフェイスで適用されるポリシーによって決まります。ピアネットワークが"log me"マーキングを変更せずに渡す協定を結ぶよう努めれば、トラブルシューティングとテストは容易になります。ただし、"log me"マーカーによってSIPエンティティーがリクエストやレスポンスのSIPヘッダーとボディーをログに記録する可能性があるため、ピアネットワーク間に協定が存在しない場合、"log me"マーカーはネットワーク境界で削除されなければなりません（MUST）。

3.4.3. Across a Non-supporting SIP Intermediary

3.4.3. 非対応のSIP仲介者をまたぐ場合

"Log me" marking is most effective if passed end to end. However, intermediaries that do not comply with this document might pass the "log me" marker unchanged or even drop it entirely.

"Log me"マーキングは、エンドツーエンドで渡される場合に最も効果的です。しかし、この文書に準拠していない仲介者は、"log me"マーカーを変更せずに渡すかもしれませんし、完全に削除してしまうかもしれません。

3.5. Logging Multiple Simultaneous Dialogs

3.5. 複数の同時ダイアログのロギング

Multiple SIP dialogs can be simultaneously logged by an originating UA, terminating UA, and SIP entities on the signaling path. These dialogs are differentiated by their test case identifier (the local UUID portion of the Session-ID header field value at the originating device).

複数のSIPダイアログを、発信側UA、着信側UA、およびシグナリング経路上のSIPエンティティーが同時にログに記録できます。これらのダイアログは、テストケース識別子（発信側デバイスにおけるSession-IDヘッダーフィールド値のローカルUUID部分）によって区別されます。

3.6. Format of Logged Signaling

3.6. ログに記録するシグナリングの形式

The entire SIP message (SIP request line, response line, header fields, and message body) SHOULD be logged since troubleshooting might be difficult if information is missing. Logging SHOULD use common standard formats such as SIP Common Log Format (CLF) defined in [RFC6873] and Libpcap as defined in "vnd.tcpdump.pcap" in the Media Types registry [MEDIA-TYPES]. If SIP CLF is used, the entire message is logged using Vendor-ID = 00000000 and Tag = 02 in the <OptionalFields> portion of the SIP CLF record (see Section 4.4 of [RFC6873]). Header fields SHOULD be logged in the form in which they appear in the message; they SHOULD NOT be converted between long and compact forms described in Section 7.3.3 of [RFC3261].

情報が欠けているとトラブルシューティングが困難になる可能性があるため、SIPメッセージ全体（SIPリクエスト行、レスポンス行、ヘッダーフィールド、およびメッセージボディー）をログに記録すべきです（SHOULD）。ロギングでは、[RFC6873]で定義されたSIP Common Log Format（CLF）や、Media Typesレジストリー[MEDIA-TYPES]の"vnd.tcpdump.pcap"で定義されたLibpcapなど、一般的な標準形式を使用すべきです（SHOULD）。SIP CLFを使用する場合、メッセージ全体は、SIP CLFレコードの<OptionalFields>部分においてVendor-ID = 00000000およびTag = 02を使用してログに記録されます（[RFC6873]のセクション4.4を参照）。ヘッダーフィールドはメッセージに現れたときの形式でログに記録すべきです（SHOULD）。つまり、[RFC3261]のセクション7.3.3で説明されている長い形式とコンパクトな形式の間で変換すべきではありません（SHOULD NOT）。

3.7. Marking Related Dialogs

3.7. 関連するダイアログのマーキング

"Log me" marking is done per dialog; typically, it begins at dialog creation and ends when the dialog ends. However, dialogs related to a "log me" marked dialog MAY also be "log me" marked for call control features such as call forward, transfer, park, and join. As described in Section 6 of [RFC7989], related dialogs can occur when an endpoint receives a 3xx message, a REFER that directs the endpoint to a different peer, an INVITE request with Replaces that also potentially results in communicating with a new peer, or an INVITE with a Join header field as described in [RFC3911]. An example is the call transfer feature described in Section 6.1 of [RFC5589]. The logged signaling for related dialogs can be correlated using Session-ID header field values as described in Section 10.9 of [RFC7989].

"Log me"マーキングはダイアログ単位で行われます。通常、マーキングはダイアログの作成時に始まり、ダイアログの終了時に終わります。ただし、着信転送（call forward）、転送（transfer）、パーク（park）、参加（join）などの呼制御機能のために、"log me"マーキングされたダイアログに関連するダイアログも"log me"マーキングしてもよいです（MAY）。[RFC7989]のセクション6で説明されているように、関連するダイアログは、エンドポイントが3xxメッセージを受信した場合、エンドポイントを別のピアに誘導するREFERを受信した場合、同じく新しいピアとの通信につながる可能性があるReplacesを含むINVITEリクエストを受信した場合、または[RFC3911]で説明されているJoinヘッダーフィールドを含むINVITEを受信した場合に発生することがあります。その一例が、[RFC5589]のセクション6.1で説明されている呼転送機能です。関連するダイアログについてログに記録されたシグナリングは、[RFC7989]のセクション10.9で説明されているように、Session-IDヘッダーフィールド値を使用して相互に関連付けることができます。

SIP仲介者は、フォークされたリクエストに"log me"マーカーをコピーする必要があります。SIPリクエストのフォーキングについては、[RFC3261]のセクション4と16.6で説明されています。

4. SIP Entity Behavior

4. SIPエンティティーの動作

4.1. Scope of Marking

4.1. マーキングの範囲

"Log me" marking is intended to be limited, in time period and number of dialogs marked, to the minimum needed to troubleshoot a particular problem or perform a particular test.

"Log me"マーキングは、期間とマーキングされるダイアログの数の両方において、特定の問題のトラブルシューティングや特定のテストの実施に必要な最小限に限定することを意図しています。

  • SIP entities MUST be configured to "log me" mark only dialogs needed for the current testing purpose, e.g., troubleshooting or regression testing. The mechanisms in this section ensure that "log me" marking begins at dialog creation and, other than cases of marking related dialogs or premature ending, ends when the dialog being "log me" marked ends.
  • If a dialog is to be marked, the only way to initiate "log me" marking is at the dialog-creating request (e.g., SIP INVITE) sent by an originating endpoint or an intermediary that marks on behalf of the originating endpoint. Marking that appears mid-dialog is an error as described in Section 5.1.2. The final terminating endpoint, or intermediary that marks on behalf of the terminating endpoint, cannot initiate marking, but it takes action as defined in Sections 4.2 and 4.3 if it receives an incoming "log me" marker.
  • SIPエンティティーは、トラブルシューティングや回帰テストなど、現在のテスト目的に必要なダイアログのみを"log me"マーキングするように設定されなければなりません（MUST）。このセクションのメカニズムにより、"log me"マーキングはダイアログの作成時に始まり、関連するダイアログのマーキングや早期終了の場合を除いて、"log me"マーキングされているダイアログが終了したときに終わることが保証されます。
  • ダイアログをマーキングする場合、"log me"マーキングを開始する唯一の方法は、発信側エンドポイント、または発信側エンドポイントの代わりにマーキングする仲介者が送信する、ダイアログを作成するリクエスト（たとえばSIP INVITE）で開始することです。セクション5.1.2で説明するように、ダイアログの途中で現れるマーキングはエラーです。最終的な着信側エンドポイント、または着信側エンドポイントの代わりにマーキングする仲介者は、マーキングを開始できませんが、"log me"マーカーを受信した場合には、セクション4.2と4.3で定義されているとおりに動作します。

Note that the error cases described in Section 5.1 cause SIP entities to stop "log me" marking, and the requirements in Section 7 also place requirements on SIP entities, including allowing SIP entities to not log signaling based on local policies (see Section 8.6).

セクション5.1で説明するエラーケースではSIPエンティティーが"log me"マーキングを停止することになり、またセクション7の要件もSIPエンティティーに要件を課しており、その中にはSIPエンティティーがローカルポリシーに基づいてシグナリングをログに記録しないことを許容することも含まれる点に注意してください（セクション8.6を参照）。

4.2. Endpoints

4.2. エンドポイント

A common scenario is to have both originating and terminating endpoints support "log me" marking with the originating endpoint configured to initiate "log me" marking. In this simplest use case, the originating UA inserts a "log me" marker in the dialog-creating SIP request and all subsequent SIP requests within that dialog. The "log me" marker is passed through the SIP intermediaries and arrives at the terminating UA, which echoes the "log me" marker in the corresponding responses. If the terminating UA sends an in-dialog request on a dialog that is being "log me" marked, it inserts a "log me" marker and the originating UA echoes the "log me" marker in responses. The terminating UA logs the "log me" marked SIP requests and responses if it is allowed as per policy defined in the terminating network. This basic use case suggests the following rules for originating and terminating UAs.

一般的なシナリオは、発信側エンドポイントと着信側エンドポイントの両方が"log me"マーキングに対応しており、発信側エンドポイントが"log me"マーキングを開始するように設定されているものです。この最も単純なユースケースでは、発信側UAは、ダイアログを作成するSIPリクエストと、そのダイアログ内の後続のすべてのSIPリクエストに"log me"マーカーを挿入します。"log me"マーカーはSIP仲介者を通過して着信側UAに到着し、着信側UAは対応するレスポンスで"log me"マーカーをエコーします。着信側UAが"log me"マーキングされているダイアログでダイアログ内リクエストを送信する場合、着信側UAは"log me"マーカーを挿入し、発信側UAはレスポンスで"log me"マーカーをエコーします。着信側UAは、着信側ネットワークで定義されたポリシーに従って許可されている場合、"log me"マーキングされたSIPリクエストとレスポンスをログに記録します。この基本的なユースケースから、発信側UAと着信側UAに対して次の規則が導かれます。

For originating UAs:

発信側UAについて：

  • The originating UA configured for "log me" marking MUST insert a "log me" marker into the dialog-creating SIP request and subsequent in-dialog SIP requests.
  • The originating UA itself logs marked requests and responses.
  • The originating UA echoes, in responses, the "log me" marker received in in-dialog requests from the terminating side.
  • The originating UA logs the SIP responses that it sends in response to received "log me" marked in-dialog requests.
  • The originating UA MAY also apply these rules to any subsequent related SIP dialogs as described in Section 3.7.
  • "log me"マーキング用に設定された発信側UAは、ダイアログを作成するSIPリクエストと、後続のダイアログ内SIPリクエストに"log me"マーカーを挿入しなければなりません（MUST）。
  • 発信側UA自身が、マーキングされたリクエストとレスポンスをログに記録します。
  • 発信側UAは、着信側から受信したダイアログ内リクエストに含まれる"log me"マーカーをレスポンスでエコーします。
  • 発信側UAは、受信した"log me"マーキングされたダイアログ内リクエストに応答して送信するSIPレスポンスをログに記録します。
  • 発信側UAは、セクション3.7で説明するように、後続の関連するSIPダイアログにもこれらの規則を適用してもよいです（MAY）。

For terminating UAs:

着信側UAについて：

  • The terminating UA detects that a dialog is of interest to logging by the existence of a "log me" marker in an incoming dialog-creating SIP request.
  • The terminating UA itself logs marked requests and corresponding marked responses if allowed as per policy.
  • The terminating UA MUST echo a "log me" marker in responses to a SIP request that included a "log me" marker.
  • If the terminating UA has detected that a dialog is being "log me" marked, it MUST insert a "log me" marker in any in-dialog SIP requests that it sends.
  • The terminating UA itself logs any in-dialog SIP requests that it sends if allowed as per policy.
  • The terminating UA MAY also apply these rules to any subsequent related SIP dialogs as described in Section 3.7.
  • 着信側UAは、受信したダイアログを作成するSIPリクエストに"log me"マーカーが存在することによって、ダイアログがロギングの対象であることを検出します。
  • 着信側UA自身が、ポリシーに従って許可されている場合、マーキングされたリクエストと対応するマーキングされたレスポンスをログに記録します。
  • 着信側UAは、"log me"マーカーを含んでいたSIPリクエストに対するレスポンスで"log me"マーカーをエコーしなければなりません（MUST）。
  • 着信側UAは、ダイアログが"log me"マーキングされていることを検出した場合、自身が送信するすべてのダイアログ内SIPリクエストに"log me"マーカーを挿入しなければなりません（MUST）。
  • 着信側UA自身が、ポリシーに従って許可されている場合、自身が送信するダイアログ内SIPリクエストをログに記録します。
  • 着信側UAは、セクション3.7で説明するように、後続の関連するSIPダイアログにもこれらの規則を適用してもよいです（MAY）。

4.3. SIP Intermediaries Acting on Behalf of Endpoints

4.3. エンドポイントの代わりに動作するSIP仲介者

A network operator may know that some of the UAs connected to the network do not support "log me" marking. Subject to the authorizations in Section 7.1, a SIP intermediary close to the UA (e.g., edge proxy, B2BUA) on the originating and/or terminating sides inserts the "log me" marker instead in order to test sessions involving such UAs.

ネットワーク事業者は、ネットワークに接続されたUAの一部が"log me"マーキングに対応していないことを把握している場合があります。セクション7.1の認可を前提として、そのようなUAが関与するセッションをテストするために、発信側と着信側の一方または両方でUAに近いSIP仲介者（たとえばエッジプロキシー、B2BUA）が代わりに"log me"マーカーを挿入します。

The originating and terminating SIP intermediaries are not identified by protocol means but are designated and explicitly configured by the network administrator to "log me" mark on behalf of endpoints. The intermediaries that are known to be closest to the terminals can be configured to "log me" mark on behalf of terminals that do not support "log me" marking. The originating SIP intermediary is the first one to be traversed by a SIP request sent by the originating endpoint. Similarly, the terminating SIP intermediary is the last intermediary traversed before the terminating endpoint is reached.

発信側と着信側のSIP仲介者はプロトコル上の手段によって識別されるのではなく、エンドポイントの代わりに"log me"マーキングするようにネットワーク管理者が指定し、明示的に設定します。端末に最も近いことがわかっている仲介者を、"log me"マーキングに対応していない端末の代わりに"log me"マーキングするように設定できます。発信側SIP仲介者とは、発信側エンドポイントが送信したSIPリクエストが最初に通過するSIP仲介者です。同様に、着信側SIP仲介者とは、着信側エンドポイントに到達する前に最後に通過する仲介者です。

The SIP intermediary at the originating side is configured to insert the "log me" marker on behalf of the originating endpoint. If the terminating UA does not echo the "log me" marker in responses to a marked request, then the SIP intermediary closest to the terminating UA, if configured to mark on behalf of the terminating UA, inserts a "log me" marker in responses to the request. Likewise, if the terminating UA sends an in-dialog request, the SIP intermediary at the terminating side inserts a "log me" marker and the SIP intermediary at the originating side echoes the "log me" marker in responses to that request. Originating and terminating intermediaries that are configured for "log me" marking on behalf of the endpoint must also mark dialog-creating requests that contain Target-Dialog [RFC4538], Join [RFC3911], and Replaces [RFC3891] header fields and corresponding responses. The SIP intermediaries at the originating and terminating sides log the "log me" marked SIP requests and responses if it is allowed as per policy defined in the originating and terminating networks. This scenario suggests the following rules when a SIP intermediary is configured to initiate or handle "log me" marking on behalf of a UA.

発信側のSIP仲介者は、発信側エンドポイントの代わりに"log me"マーカーを挿入するように設定されます。着信側UAがマーキングされたリクエストに対するレスポンスで"log me"マーカーをエコーしない場合、着信側UAに最も近いSIP仲介者は、着信側UAの代わりにマーキングするように設定されていれば、そのリクエストに対するレスポンスに"log me"マーカーを挿入します。同様に、着信側UAがダイアログ内リクエストを送信する場合、着信側のSIP仲介者が"log me"マーカーを挿入し、発信側のSIP仲介者はそのリクエストに対するレスポンスで"log me"マーカーをエコーします。エンドポイントの代わりに"log me"マーキングするように設定された発信側と着信側の仲介者は、Target-Dialog [RFC4538]、Join [RFC3911]、Replaces [RFC3891]の各ヘッダーフィールドを含むダイアログを作成するリクエストと、それに対応するレスポンスもマーキングする必要があります。発信側と着信側のSIP仲介者は、発信側と着信側のネットワークで定義されたポリシーに従って許可されている場合、"log me"マーキングされたSIPリクエストとレスポンスをログに記録します。このシナリオから、SIP仲介者がUAの代わりに"log me"マーキングを開始または処理するように設定されている場合について、次の規則が導かれます。

For the originating SIP intermediary:

発信側SIP仲介者について：

  • The originating SIP intermediary configured for "log me" marking MUST insert a "log me" marker into the dialog-creating SIP request and subsequent in-dialog SIP requests.
  • The originating SIP intermediary itself logs marked requests and responses.
  • The originating SIP intermediary detects the "log me" marker received in in-dialog requests and echoes the "log me" marker in the corresponding SIP responses.
  • The originating SIP intermediary logs the SIP responses that it sends in response to "log me" marked in-dialog requests.
  • The originating SIP intermediary MAY also apply these rules to any subsequent related SIP dialogs as described in Section 3.7.
  • "log me"マーキング用に設定された発信側SIP仲介者は、ダイアログを作成するSIPリクエストと、後続のダイアログ内SIPリクエストに"log me"マーカーを挿入しなければなりません（MUST）。
  • 発信側SIP仲介者自身が、マーキングされたリクエストとレスポンスをログに記録します。
  • 発信側SIP仲介者は、ダイアログ内リクエストで受信した"log me"マーカーを検出し、対応するSIPレスポンスで"log me"マーカーをエコーします。
  • 発信側SIP仲介者は、"log me"マーキングされたダイアログ内リクエストに応答して送信するSIPレスポンスをログに記録します。
  • 発信側SIP仲介者は、セクション3.7で説明するように、後続の関連するSIPダイアログにもこれらの規則を適用してもよいです（MAY）。

For the terminating SIP intermediary:

着信側SIP仲介者について：

  • The terminating SIP intermediary detects that a dialog is of interest to logging by the existence of a "log me" marker in an incoming dialog-creating SIP request.
  • The terminating SIP intermediary itself logs marked requests and corresponding responses if allowed as per policy.
  • The terminating SIP intermediary MUST echo a "log me" marker in responses to a SIP request that included a "log me" marker.
  • If the terminating SIP intermediary has detected that a dialog is being "log me" marked, it MUST insert a "log me" marker in any in-dialog SIP requests from the terminating UA.
  • The terminating SIP intermediary itself logs any in-dialog SIP requests that it sends if allowed as per policy.
  • The terminating SIP intermediary MAY also apply these rules to any subsequent related SIP dialogs as described in Section 3.7.
  • 着信側SIP仲介者は、受信したダイアログを作成するSIPリクエストに"log me"マーカーが存在することによって、ダイアログがロギングの対象であることを検出します。
  • 着信側SIP仲介者自身が、ポリシーに従って許可されている場合、マーキングされたリクエストと対応するレスポンスをログに記録します。
  • 着信側SIP仲介者は、"log me"マーカーを含んでいたSIPリクエストに対するレスポンスで"log me"マーカーをエコーしなければなりません（MUST）。
  • 着信側SIP仲介者は、ダイアログが"log me"マーキングされていることを検出した場合、着信側UAからのすべてのダイアログ内SIPリクエストに"log me"マーカーを挿入しなければなりません（MUST）。
  • 着信側SIP仲介者自身が、ポリシーに従って許可されている場合、自身が送信するダイアログ内SIPリクエストをログに記録します。
  • 着信側SIP仲介者は、セクション3.7で説明するように、後続の関連するSIPダイアログにもこれらの規則を適用してもよいです（MAY）。

4.4. B2BUAs

4.4. B2BUA

B2BUA "log me" behavior is specified based on its different signaling plane roles described in [RFC7092].

B2BUAの"log me"動作は、[RFC7092]で説明されているシグナリングプレーンにおけるさまざまな役割に基づいて規定されます。

A Proxy-B2BUA SHOULD copy "log me" marking in requests and responses from its terminating side to the originating side without needing explicit configuration to do so.

Proxy-B2BUAは、明示的な設定を必要とせずに、リクエストとレスポンスにおける"log me"マーキングを着信側から発信側へコピーすべきです（SHOULD）。

A dialog on one "side" of the B2BUA may or may not be coupled to a related dialog on the other "side" for "log me" purposes. To allow end-to-end troubleshooting of user problems and regression testing, a signaling-only and SDP-modifying signaling-only B2BUA [RFC7092] SHOULD couple related dialogs for "log me" marking purposes and pass on the received "log me" parameter from the originating side to the terminating side and vice versa. For example, a SIP B2BUA handling an end-to-end session between an external caller and an agent in a contact center environment can couple the dialog between itself and an agent with the dialog between itself and the external caller. It can pass on the "log me" marking from the originating side to the terminating side to enable end-to-end logging of specific sessions of interest.

B2BUAの一方の"side"のダイアログは、"log me"の目的で、もう一方の"side"の関連するダイアログと結び付けられる場合もあれば、結び付けられない場合もあります。ユーザーの問題のエンドツーエンドでのトラブルシューティングと回帰テストを可能にするために、シグナリング専用B2BUAおよびSDPを変更するシグナリング専用B2BUA [RFC7092]は、"log me"マーキングの目的で関連するダイアログを結び付け、受信した"log me"パラメーターを発信側から着信側へ、またその逆方向へ渡すべきです（SHOULD）。たとえば、コンタクトセンター環境において外部の発信者とエージェントとの間のエンドツーエンドセッションを処理するSIP B2BUAは、自身とエージェントとの間のダイアログを、自身と外部の発信者との間のダイアログと結び付けることができます。これにより、関心のある特定のセッションのエンドツーエンドのロギングを可能にするために、"log me"マーキングを発信側から着信側へ渡すことができます。

For dialogs that are being "log me" marked, all B2BUAs MUST "log me" mark in-dialog SIP requests that they generate on their own, without needing explicit configuration to do so. This rule applies to both the originating and terminating sides of a B2BUA.

"log me"マーキングされているダイアログについて、すべてのB2BUAは、明示的な設定を必要とせずに、自身が独自に生成するダイアログ内SIPリクエストを"log me"マーキングしなければなりません（MUST）。この規則は、B2BUAの発信側と着信側の両方に適用されます。

4.5. "Log Me" Marker Processing by SIP Intermediaries

4.5. SIP仲介者による"Log Me"マーカーの処理

4.5.1. Stateless Processing

4.5.1. ステートレス処理

Typically, "log me" marking will be done by an originating UA and echoed by a terminating UA. SIP intermediaries on the signaling path between these UAs that do not perform the tasks described in Sections 4.3 or 4.4 MUST simply log any request or response that contains a "log me" marker in a stateless manner, if it is allowed per local policy.

通常、"log me"マーキングは発信側UAによって行われ、着信側UAによってエコーされます。これらのUA間のシグナリング経路上にあり、セクション4.3または4.4で説明するタスクを実行しないSIP仲介者は、ローカルポリシーに従って許可されている場合、"log me"マーカーを含むリクエストやレスポンスをステートレスな方法で単にログに記録しなければなりません（MUST）。

4.5.2. Stateful Processing

4.5.2. ステートフル処理

The originating and terminating SIP intermediaries that "log me" mark on behalf of endpoints and SIP intermediaries that remove "log me" marking at the network boundary must maintain state to enable "log me" marking. Applicable scenarios are as follows:

エンドポイントの代わりに"log me"マーキングする発信側と着信側のSIP仲介者、およびネットワーク境界で"log me"マーキングを削除するSIP仲介者は、"log me"マーキングを可能にするために状態を維持する必要があります。該当するシナリオは次のとおりです。

  • The originating UA does not support "log me" marking. This scenario was described in Section 4.3 and requires support by the originating SIP intermediary. "Log me" marker processing is illustrated in Section 4.5.2.1.
  • The terminating UA does not support "log me" marking. This scenario was described in Section 4.3 and requires support by the terminating SIP intermediary. "Log me" marker processing is illustrated in Section 4.5.2.2.
  • The originating network ensures that it does not pass marking outside its boundaries in order to not impact any external networks. The originating network removes "log me" marking from SIP requests and responses before forwarding them from its network boundary to external networks, but it adds marking back to any incoming SIP requests and responses belonging to any "log me" marked dialog. This scenario requires support by the SIP intermediary at the originating network boundary. "Log me" marker processing is illustrated in Section 4.5.2.3.
  • The terminating network ensures that it does not allow "log me" marking from external networks to pass through its boundary to its internal entities. The terminating network removes "log me" marking from SIP requests and responses before forwarding them internally, but it adds marking back to any outgoing SIP requests and responses belonging to any "log me" marked dialog. This scenario requires support by the SIP intermediary at the terminating network boundary. "Log me" marker processing is illustrated in Section 4.5.2.4.
  • The terminating network does not support "log me" marking and does not echo marking that it receives. The originating network adds marking back to any incoming SIP requests and responses belonging to the "log me" marked dialog. This scenario requires support by the SIP intermediary at the originating network boundary and "log me" marker processing is illustrated in Section 4.5.2.5.
  • 発信側UAが"log me"マーキングに対応していない場合。このシナリオはセクション4.3で説明したものであり、発信側SIP仲介者による対応を必要とします。"Log me"マーカーの処理はセクション4.5.2.1で示します。
  • 着信側UAが"log me"マーキングに対応していない場合。このシナリオはセクション4.3で説明したものであり、着信側SIP仲介者による対応を必要とします。"Log me"マーカーの処理はセクション4.5.2.2で示します。
  • 発信側ネットワークが、外部ネットワークに影響を与えないように、マーキングを自身の境界の外に渡さないようにする場合。発信側ネットワークは、SIPリクエストとレスポンスを自身のネットワーク境界から外部ネットワークへ転送する前に"log me"マーキングを削除しますが、"log me"マーキングされたダイアログに属する受信SIPリクエストとレスポンスにはマーキングを付け直します。このシナリオは、発信側ネットワーク境界にあるSIP仲介者による対応を必要とします。"Log me"マーカーの処理はセクション4.5.2.3で示します。

5. Errors

5. エラー

5.1. Error Cases

5.1. エラーケース

The following error cases are possible for "log me" marking:

"log me"マーキングでは、次のエラーケースが起こり得ます。

  1. A "log me" marker is unexpectedly missing from a dialog that is being logged.
  2. A "log me" marker unexpectedly appears in a dialog that is not being logged.
  3. A "log me" marker unexpectedly disappears and then reappears in a dialog being logged. This is treated in the same way as case 1.
  4. A "log me" marker is unexpectedly missing from a retransmission in a dialog being logged. This is treated in the same way as case 1.
  1. ログに記録されているダイアログから、"log me"マーカーが予期せず欠落します。
  2. ログに記録されていないダイアログに、"log me"マーカーが予期せず現れます。
  3. ログに記録されているダイアログで、"log me"マーカーが予期せず消え、その後再び現れます。これはケース1と同じように扱われます。
  4. ログに記録されているダイアログで、再送から"log me"マーカーが予期せず欠落します。これはケース1と同じように扱われます。

These cases apply to any request or response sent by any entity and in any direction in a dialog being "log me" marked. Detection of these error cases is described in this section.

これらのケースは、"log me"マーキングされているダイアログにおいて、任意のエンティティーが任意の方向に送信する任意のリクエストまたはレスポンスに適用されます。これらのエラーケースの検出について、このセクションで説明します。

5.1.1. Missing "Log Me" Marker Error Case

5.1.1. "Log Me"マーカーが欠落するエラーケース

Since "log me" marking is per-dialog, if a dialog is being marked and marking is missing from a request or response then this is an error.

"Log me"マーキングはダイアログ単位であるため、ダイアログがマーキングされているのにリクエストやレスポンスからマーキングが欠落している場合、それはエラーです。

However, detecting such errors is not as simple as checking for missing markers because of cases such as non-supporting terminals where it is normal that marking is not done.

しかし、非対応の端末のようにマーキングが行われないことが正常であるケースがあるため、このようなエラーを検出することは、マーカーの欠落を確認するほど単純ではありません。

Detecting errors must be evaluated separately for each neighbor. It is an error if a particular neighbor has previously sent "log me" in the dialog and then stops, independently of what has been happening with other neighbors.

エラーの検出は、隣接するノードごとに個別に評価しなければなりません。ある隣接ノードが以前にそのダイアログで"log me"を送信しており、その後送信をやめた場合、ほかの隣接ノードで何が起きているかとは無関係に、それはエラーです。

UAs and intermediaries that are stateless with respect to "log me" marking are not able detect such errors. User agents and intermediaries that are stateful with respect to "log me" marking are able to detect that a marker is missing from a dialog that has previously been "log me" marked. Error cases are illustrated in this section, and non-error cases in Section 5.2.1.

"log me"マーキングに関してステートレスなUAや仲介者は、このようなエラーを検出できません。"log me"マーキングに関してステートフルなユーザーエージェントや仲介者は、以前に"log me"マーキングされていたダイアログからマーカーが欠落していることを検出できます。エラーケースはこのセクションで示し、エラーではないケースはセクション5.2.1で示します。

5.2.3. Combining Dialogs Non-error Case

5.2.3. ダイアログを結合するエラーではないケース

When troubleshooting call flows that involve the SIP Join header field specified in [RFC3911], the ideal scenario is to have "log me" marking enabled on all UAs and intermediaries participating in the end-to-end session. If the ideal scenario is not feasible, the following rules apply:

[RFC3911]で規定されているSIP Joinヘッダーフィールドが関与する呼フローをトラブルシューティングする場合、理想的なシナリオは、エンドツーエンドセッションに参加するすべてのUAと仲介者で"log me"マーキングを有効にすることです。理想的なシナリオが実現できない場合は、次の規則が適用されます。

  • If an endpoint or an intermediary that is "log me" aware and is already "log me" marking a dialog receives a SIP INVITE with a Join header field and without a "log me" marker, it MUST NOT "log me" mark responses and requests exchanged within the new dialog established as a result of processing the SIP INVITE.
  • If an endpoint or an intermediary that is "log me" aware and is not "log me" marking a dialog receives a SIP INVITE with a Join header field and with a "log me" marker, it MUST "log me" mark responses and requests exchanged within the new dialog established as a result of processing the SIP INVITE as per Section 4 of this document.
  • "log me"に対応しており、すでにあるダイアログを"log me"マーキングしているエンドポイントまたは仲介者が、Joinヘッダーフィールドを含み"log me"マーカーを含まないSIP INVITEを受信した場合、そのSIP INVITEを処理した結果として確立される新しいダイアログ内で交換されるレスポンスとリクエストを"log me"マーキングしてはなりません（MUST NOT）。
  • "log me"に対応しており、あるダイアログを"log me"マーキングしていないエンドポイントまたは仲介者が、Joinヘッダーフィールドと"log me"マーカーを含むSIP INVITEを受信した場合、この文書のセクション4に従って、そのSIP INVITEを処理した結果として確立される新しいダイアログ内で交換されるレスポンスとリクエストを"log me"マーキングしなければなりません（MUST）。

5.3. Error Handling

5.3. エラー処理

The two error types that SIP entities must handle are defined in Section 5.1: a missing marker error and an error of "log me" marking that begins mid-dialog. Section 5.2 gives exceptions that have marking that begins mid-dialog or a missing marker but are not errors.

SIPエンティティーが処理しなければならない2種類のエラーは、セクション5.1で定義されています。マーカーの欠落エラーと、ダイアログの途中で始まる"log me"マーキングのエラーです。セクション5.2では、ダイアログの途中で始まるマーキングやマーカーの欠落があってもエラーではない例外を示しています。

If a missing marker error is detected by a UA, SIP intermediary, or B2BUA, it SHOULD consider this to be an error condition in the "log me" functionality. It MUST NOT mark subsequent requests and responses, and it MUST stop logging messages in the same dialog. Any previously logged messages SHOULD be retained, for the time period defined in Section 8.5, and not deleted.

UA、SIP仲介者、またはB2BUAがマーカーの欠落エラーを検出した場合、これを"log me"機能のエラー状態とみなすべきです（SHOULD）。後続のリクエストとレスポンスをマーキングしてはなりません（MUST NOT）。また、同じダイアログ内のメッセージのロギングを停止しなければなりません（MUST）。それまでにログに記録したメッセージは、削除せずに、セクション8.5で定義する期間保持すべきです（SHOULD）。

If a "log me" marking that begins mid-dialog error is detected by a UA, SIP intermediary, or B2BUA, it SHOULD consider this to be an error condition in the "log me" functionality. It MUST NOT forward the "log me" marker, and it MUST NOT log the message. It MUST NOT mark subsequent requests and responses, and it MUST NOT log subsequent messages in the same dialog.

UA、SIP仲介者、またはB2BUAが、ダイアログの途中で始まる"log me"マーキングのエラーを検出した場合、これを"log me"機能のエラー状態とみなすべきです（SHOULD）。"log me"マーカーを転送してはなりません（MUST NOT）。また、そのメッセージをログに記録してはなりません（MUST NOT）。後続のリクエストとレスポンスをマーキングしてはなりません（MUST NOT）。また、同じダイアログ内の後続のメッセージをログに記録してはなりません（MUST NOT）。

"Log me" marking errors can be detected and handled only by supporting UAs or B2BUAs. A SIP proxy as defined in [RFC3261] cannot detect or handle marking errors and will simply forward any "log me" marker it receives.

"Log me"マーキングのエラーは、対応しているUAまたはB2BUAによってのみ検出および処理できます。[RFC3261]で定義されているSIPプロキシーは、マーキングのエラーを検出したり処理したりできず、受信した"log me"マーカーを単に転送します。

7. Security Considerations

7. セキュリティーに関する考慮事項

7.1. "Log Me" Authorization

7.1. "Log Me"の認可

"Log me" marking MUST be disabled by default both at the endpoints and intermediaries and MUST be enabled only by authorized users. For example, an end user or network administrator must give permission for a terminal that supports "log me" marking in order to initiate marking. Similarly, a network administrator must enable a configuration at the SIP intermediary to perform "log me" marking on behalf of a terminal that does not support "log me" marking. The permission MUST be limited to only specific calls of interest that are originated in a given time duration.

"Log me"マーキングは、エンドポイントと仲介者の両方でデフォルトで無効にされなければなりません（MUST）。また、認可されたユーザーによってのみ有効にされなければなりません（MUST）。たとえば、"log me"マーキングに対応した端末がマーキングを開始するには、エンドユーザーまたはネットワーク管理者が許可を与えなければなりません。同様に、"log me"マーキングに対応していない端末の代わりに"log me"マーキングを実行するには、ネットワーク管理者がSIP仲介者で設定を有効にしなければなりません。この許可は、所定の期間内に発信された関心のある特定の呼のみに限定されなければなりません（MUST）。

Activating a debug mode affects the operation of a terminal; therefore, the debugging configuration MUST be supplied by an authorized party to an authorized terminal through a secure communication channel.

デバッグモードを有効にすることは端末の動作に影響を与えます。したがって、デバッグ設定は、認可された当事者から認可された端末へ、安全な通信チャネルを通じて提供されなければなりません（MUST）。

7.2. "Log Me" Marker Removal

7.2. "Log Me"マーカーの削除

The "log me" marker is not sensitive information, though it will sometimes be inserted because a particular device is experiencing problems.

"log me"マーカーは機密情報ではありませんが、特定のデバイスで問題が発生しているために挿入される場合があります。

The presence of a "log me" marker will cause some SIP entities to log signaling messages. Therefore, this marker MUST be removed at the earliest opportunity if it has been incorrectly inserted, such as appearing mid-dialog in a dialog that was not being logged or outside the configured start and stop of logging.

"log me"マーカーが存在すると、一部のSIPエンティティーはシグナリングメッセージをログに記録します。したがって、このマーカーが誤って挿入された場合、たとえばログに記録されていないダイアログの途中で現れた場合や、設定されたロギングの開始と停止の範囲外で現れた場合には、できるだけ早い機会に削除されなければなりません（MUST）。

If SIP requests and responses are exchanged with an external network with which there is no agreement to pass "log me" marking, then the "log me" marking is removed as mandated in Section 3.4.2. This behavior applies to incoming and outgoing requests and responses.

"log me"マーキングを渡す協定のない外部ネットワークとSIPリクエストとレスポンスを交換する場合、セクション3.4.2で義務付けているように、"log me"マーキングは削除されます。この動作は、受信と送信の両方のリクエストとレスポンスに適用されます。

7.3. Denial-of-Service Attacks

7.3. サービス拒否攻撃

Maliciously configuring a large number of terminals to simultaneously mark dialogs with a "log me" marker will cause high processor load on SIP entities that are logging signaling. Since "log me" marking is for the small number of dialogs subject to troubleshooting or regression testing, the number of dialogs that can be simultaneously logged can be statically limited without adversely affecting the usefulness of "log me" marking. Also, the SIP intermediary closest to the terminal and SIP intermediary at network edge (e.g., Session Border Controllers) can be configured to screen-out "log me" markers when troubleshooting or regression testing is not in progress.

多数の端末を同時にダイアログを"log me"マーカーでマーキングするように悪意を持って設定すると、シグナリングをログに記録しているSIPエンティティーで高いプロセッサー負荷が発生します。"Log me"マーキングはトラブルシューティングや回帰テストの対象となる少数のダイアログのためのものなので、"log me"マーキングの有用性を損なうことなく、同時にログに記録できるダイアログの数を静的に制限できます。また、端末に最も近いSIP仲介者と、ネットワークエッジにあるSIP仲介者（たとえばセッションボーダーコントローラー）は、トラブルシューティングや回帰テストが進行中でないときに"log me"マーカーを除去するように設定できます。

7.4. Data Protection

7.4. データ保護

A SIP entity that has logged information MUST protect the logs. Storage of the log files are subject to the security considerations specified in [RFC6872].

情報をログに記録したSIPエンティティーは、そのログを保護しなければなりません（MUST）。ログファイルの保存には、[RFC6872]で規定されているセキュリティーに関する考慮事項が適用されます。

8. Privacy Considerations

8. プライバシーに関する考慮事項

Logging includes all SIP header fields. The SIP privacy mechanisms defined in [RFC3323] can be used to ensure that logs do not divulge personal identity information in the core SIP header fields specified in [RFC3261].

ロギングにはすべてのSIPヘッダーフィールドが含まれます。[RFC3323]で定義されているSIPプライバシーメカニズムを使用すると、[RFC3261]で規定されているコアSIPヘッダーフィールドにおいて、ログが個人の身元情報を漏らさないようにすることができます。

Privacy mechanisms might also need to be applied to header fields defined by SIP extensions and for managing the confidentiality of the Request-URI and SIP header fields and bodies.

SIP拡張によって定義されたヘッダーフィールドに対しても、またRequest-URIやSIPヘッダーフィールドおよびボディーの機密性を管理するためにも、プライバシーメカニズムを適用する必要があるかもしれません。

8.1. Personal Identifiers

8.1. 個人識別子

"Log me" marking is defined for the SIP protocol, and SIP has header fields such as From, Contact, and P-Asserted-Identity that can carry personal identifiers. Different protocol interactions can be correlated using the Session-ID and Call-ID header fields, but such correlation is limited to a single end-to-end session.

"Log me"マーキングはSIPプロトコル用に定義されており、SIPには、From、Contact、P-Asserted-Identityなど、個人識別子を運ぶことができるヘッダーフィールドがあります。異なるプロトコルのやり取りをSession-IDヘッダーフィールドとCall-IDヘッダーフィールドを使用して相互に関連付けることができますが、そのような関連付けは単一のエンドツーエンドセッションに限定されます。

In order to protect user privacy during logging, privacy settings can be enabled or requested by the terminal used by the end user. [RFC3323] suggests two mechanisms:

ロギング中にユーザーのプライバシーを保護するために、エンドユーザーが使用する端末がプライバシー設定を有効にしたり要求したりできます。[RFC3323]は2つのメカニズムを提案しています。

  • By using the value "anonymous" in the From header field
  • By requesting header-level and session-level privacy from SIP intermediaries using the Privacy header
  • Fromヘッダーフィールドで値"anonymous"を使用する方法
  • Privacyヘッダーを使用して、SIP仲介者にヘッダーレベルおよびセッションレベルのプライバシーを要求する方法

Endpoints that support Globally Routable User Agent URIs (GRUUs) can use a temporary GRUU (see Section 3.1.2 of [RFC5627]) assigned by the Registrar in order to protect user privacy as discussed in Section 10.3 of [RFC5627].

Globally Routable User Agent URI（GRUU）に対応したエンドポイントは、[RFC5627]のセクション10.3で論じられているように、ユーザーのプライバシーを保護するために、レジストラーによって割り当てられた一時GRUU（[RFC5627]のセクション3.1.2を参照）を使用できます。

Intermediaries that perform "log me" marking on behalf of the endpoints (see Section 4.3) may also be configured to apply privacy (as defined in Section 3.3 of [RFC3323]) on messages that belong to a dialog that is "log me" marked.

エンドポイントの代わりに"log me"マーキングを実行する仲介者（セクション4.3を参照）も、"log me"マーキングされたダイアログに属するメッセージに（[RFC3323]のセクション3.3で定義されている）プライバシーを適用するように設定できます。

Complete anonymization (e.g., the Request-URI and the "username" field in the "o=" parameter of an SDP body) may not be possible in all circumstances; therefore, administrators of the originating and terminating networks should consider how privacy will be ensured when providing consent for "log me" marking.

完全な匿名化（たとえばRequest-URIや、SDPボディーの"o="パラメーターにある"username"フィールドの匿名化）は、あらゆる状況で可能であるとは限りません。したがって、発信側と着信側のネットワークの管理者は、"log me"マーキングへの同意を与える際に、どのようにプライバシーを確保するかを考慮すべきです。

"Log me" marking is typically used for troubleshooting and regression testing; in some cases, a service-provider-owned device with a dummy account can be used instead of a customer device. In such cases, no personal identifiers are included in the logged signaling messages.

"Log me"マーキングは通常、トラブルシューティングや回帰テストに使用されます。場合によっては、顧客のデバイスの代わりに、ダミーアカウントを持つサービスプロバイダー所有のデバイスを使用できます。そのような場合、ログに記録されるシグナリングメッセージには個人識別子は含まれません。

8.2. Data Stored at SIP Intermediaries

8.2. SIP仲介者に保存されるデータ

SIP endpoints and intermediaries that honor the "log me" request store all the SIP messages that are exchanged within a given dialog. SIP messages can contain the personal identifiers listed in Section 8.1 and additionally a user identity, calling party number, IP address, hostname, and other user-related or device-related items. The SIP message bodies describe the kind of session being set up by the identified end user and device.

"log me"要求に従うSIPエンドポイントと仲介者は、特定のダイアログ内で交換されるすべてのSIPメッセージを保存します。SIPメッセージには、セクション8.1に挙げた個人識別子に加えて、ユーザーの身元、発呼者番号、IPアドレス、ホスト名、その他のユーザー関連またはデバイス関連の項目が含まれる可能性があります。SIPメッセージボディーは、識別されたエンドユーザーとデバイスによって確立されるセッションの種類を記述しています。

"Log me" marking does not introduce any additional user or device data to SIP but might indicate that a specific user is experiencing a problem.

"Log me"マーキングはSIPに追加のユーザーデータやデバイスデータを持ち込むことはありませんが、特定のユーザーが問題に遭遇していることを示す可能性があります。

If the SIP SDP parameters [SDP-PARAMETERS] contain sensitive security information (e.g., encryption keys) such as "crypto" [RFC4568], 3GPP-Integrity-Key, or 3GPP-SRTP-Config [RFC6064] attributes, then the attribute value MUST be masked with a dummy value prior to storing the message in a log file. For example, the attribute value can be replaced with a string of special characters like "X", "*", and "#" as shown in the example below.

SIPのSDPパラメーター[SDP-PARAMETERS]に、"crypto" [RFC4568]、3GPP-Integrity-Key、3GPP-SRTP-Config [RFC6064]などの属性のような、機密性の高いセキュリティー情報（たとえば暗号鍵）が含まれている場合、そのメッセージをログファイルに保存する前に、属性値をダミー値でマスクしなければなりません（MUST）。たとえば、以下の例に示すように、属性値を"X"、"*"、"#"のような特殊文字の文字列に置き換えることができます。

8.3. Data Visible at Network Elements

8.3. ネットワーク要素から見えるデータ

SIP messages that are logged due to "log me" requests are stored only by the SIP initiators, intermediaries, and recipients. Enablers as defined in Section 3.1 of [RFC6973], such as firewalls and DNS servers, do not log messages due to the "log me" marking.

"log me"要求によってログに記録されたSIPメッセージは、SIPの開始者、仲介者、および受信者によってのみ保存されます。ファイアウォールやDNSサーバーなど、[RFC6973]のセクション3.1で定義されているイネーブラーは、"log me"マーキングを理由としてメッセージをログに記録することはありません。

8.4. Preventing Fingerprinting

8.4. フィンガープリンティングの防止

"Log me" functionality is typically used to troubleshoot a given problem and, hence, can be used as a method to identify users and devices that are experiencing issues. The best way to prevent fingerprinting of users is to enable or request SIP privacy for the logged dialog.

"Log me"機能は通常、特定の問題のトラブルシューティングに使用されるため、問題に遭遇しているユーザーやデバイスを識別する方法として使用される可能性があります。ユーザーのフィンガープリンティングを防ぐ最善の方法は、ログに記録されるダイアログに対してSIPプライバシーを有効にするか要求することです。

8.5. Retaining Logs

8.5. ログの保持

The lifetime of "log me" marking is equivalent to the lifetime of the dialog that initiated the "log me" request. When "log me" is extended to related dialogs, the lifetime is extended until there is no remaining related dialog for the end-to-end session.

"log me"マーキングの存続期間は、"log me"要求を開始したダイアログの存続期間と同じです。"Log me"が関連するダイアログに拡張される場合、存続期間は、エンドツーエンドセッションの関連するダイアログが残っていない状態になるまで延長されます。

"Log me" automatically expires at the end of the dialog, and there is no explicit mechanism to turn off logging within a dialog.

"Log me"はダイアログの終了時に自動的に失効し、ダイアログ内でロギングを無効にする明示的なメカニズムはありません。

The scope of "log me" marking is limited, i.e., a user or the network administrator has to enable it on a per-session basis or for a specific time period. This minimizes the risk of exposing user data for an indefinite time.

"log me"マーキングの範囲は限定されています。つまり、ユーザーまたはネットワーク管理者は、セッション単位で、または特定の期間について、それを有効にしなければなりません。これにより、ユーザーデータが無期限に露出するリスクが最小限に抑えられます。

The retention time period for logged messages SHOULD be the minimum needed for each particular troubleshooting or testing case. The retention period is configured based on the data-retention policies of service providers and enterprises.

ログに記録されたメッセージの保持期間は、個々のトラブルシューティングやテストのケースに必要な最小限にすべきです（SHOULD）。保持期間は、サービスプロバイダーや企業のデータ保持ポリシーに基づいて設定されます。

8.6. User Control of Logging

8.6. ユーザーによるロギングの制御

Consent to turn on "log me" marking for a given session MUST be provided by the end user or by the network administrator. It is handled outside of the protocol through user interface or application programming interfaces at the endpoint, call control elements, and network management systems.

特定のセッションに対して"log me"マーキングを有効にすることへの同意は、エンドユーザーまたはネットワーク管理者によって与えられなければなりません（MUST）。これは、エンドポイント、呼制御要素、ネットワーク管理システムにおけるユーザーインターフェイスやアプリケーションプログラミングインターフェイスを通じて、プロトコルの外部で扱われます。

Originating and terminating endpoints that are "log me" aware and have a user interface MUST indicate (using text, icon, etc.) to the user that a session is being logged.

"log me"に対応し、ユーザーインターフェイスを持つ発信側と着信側のエンドポイントは、セッションがログに記録されていることを（テキストやアイコンなどを使用して）ユーザーに示さなければなりません（MUST）。

SIP entities across the communication path MAY be configured to pass through the "log me" marking but not honor the request, i.e., not log the data based on local policies.

通信経路上のSIPエンティティーは、"log me"マーキングを通過させるものの要求には従わない、つまりローカルポリシーに基づいてデータをログに記録しないように設定してもよいです（MAY）。

8.7. Recommended Defaults

8.7. 推奨されるデフォルト

The recommended defaults for "log me" marking are:

"log me"マーキングの推奨されるデフォルトは次のとおりです。

  • Turn on SIP privacy as described in Section 8 or use a device that is service provider owned with a dummy user identity for test calls.
  • Use the local UUID portion of the Session-ID header field value at the originating device as the test case identifier as described in Section 3.3.
  • セクション8で説明するようにSIPプライバシーを有効にするか、テスト呼のためにダミーのユーザーIDを持つサービスプロバイダー所有のデバイスを使用します。
  • セクション3.3で説明するように、発信側デバイスにおけるSession-IDヘッダーフィールド値のローカルUUID部分をテストケース識別子として使用します。
