RFC 8123

Requirements for Marking SIP Messages to be Logged

RFC 8123

ログに記録するSIPメッセージをマーキングするための要件

Abstract

概要

SIP networks use signaling monitoring tools to debug customer-reported problems and for regression testing if network or client software is upgraded. As networks grow and become interconnected, including connection via transit networks, it becomes impractical to predict the path that SIP signaling will take between clients and, therefore, impractical to monitor SIP signaling end-to-end.

SIPネットワークでは、顧客から報告された問題のデバッグや、ネットワークまたはクライアントのソフトウェアをアップグレードする場合の回帰テストのために、シグナリング監視ツールを使用します。ネットワークが成長し、トランジットネットワークを経由した接続を含めて相互に接続されるようになるにつれ、クライアント間でSIPシグナリングがたどる経路を予測することは現実的ではなくなり、したがってSIPシグナリングをエンドツーエンドで監視することも現実的ではなくなります。

This document describes the requirements for adding an indicator to the SIP Protocol Data Unit (PDU) or a SIP message that marks the PDU as a candidate for logging. Such a marking will typically be applied as part of network testing controlled by the network operator and not used in regular client signaling. However, such a marking can be carried end-to-end, including the SIP terminals, even if a session originates and terminates in different networks.

この文書では、SIPプロトコルデータユニット（PDU）またはSIPメッセージに、そのPDUがログ記録の候補であることを示すインジケーターを追加するための要件を説明します。このようなマーキングは、通常はネットワーク事業者が制御するネットワークテストの一部として適用され、通常のクライアントのシグナリングでは使用されません。しかし、このようなマーキングは、セッションの発信と着信が異なるネットワークで行われる場合でも、SIP端末を含めてエンドツーエンドで運ぶことができます。

1. Introduction

1. はじめに

Service providers, enterprises, and others who operate networks that use SIP (see [RFC3261]) need the ability to debug problems reported by end users and also to run regression tests if SIP client software/hardware is upgraded. Such debugging and testing might be confined to a single service provider or network, or they may occur between the administrative domains of different network operators, including domains in different countries that are interconnected through networks belonging to one or more third parties.

SIP（[RFC3261]を参照）を使用するネットワークを運用するサービスプロバイダー、企業などは、エンドユーザーから報告された問題をデバッグできる必要があり、またSIPクライアントのソフトウェアやハードウェアをアップグレードする場合には回帰テストを実行できる必要があります。このようなデバッグやテストは、単一のサービスプロバイダーやネットワークの中に限定される場合もあれば、異なるネットワーク事業者の管理ドメインの間で行われる場合もあります。後者には、1つ以上の第三者が所有するネットワークを通じて相互接続された、異なる国のドメインも含まれます。

A mechanism is needed to mark particular SIP sessions, i.e., those related to debugging or regression testing, as candidates for logging; this marking must be carried within the candidate SIP messages as they are routed across networks (and geographies) to enable logging at each SIP entity without having to know in advance the list of SIP entities through which the SIP signaling messages will traverse. Such marking must take into account that SIP messages might traverse different network operators, different countries, regions with different privacy requirements, and different trust domains. This document describes the requirements for such a "log me" marker for SIP signaling.

特定のSIPセッション、つまりデバッグや回帰テストに関連するセッションを、ログ記録の候補としてマーキングするメカニズムが必要です。このマーキングは、候補となるSIPメッセージがネットワーク（および地域）をまたいでルーティングされる間、そのメッセージの中で運ばれなければなりません。これにより、SIPシグナリングメッセージが通過するSIPエンティティーの一覧を事前に知らなくても、各SIPエンティティーでログ記録を行えるようになります。このようなマーキングでは、SIPメッセージが、異なるネットワーク事業者、異なる国、異なるプライバシー要件を持つ地域、異なる信頼ドメインを通過する可能性があることを考慮しなければなりません。この文書では、SIPシグナリングのためのこのような「log me」マーカーの要件を説明します。

2. Conventions Used in This Document

2. この文書で使用する表記規則

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119], except that rather than describing interoperability requirements, they are used to describe requirements to be satisfied by the "log me" marker solution.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 [RFC2119]に記載されているとおりに解釈されるものとします。ただし、これらのキーワードは相互運用性の要件を記述するのではなく、「log me」マーカーのソリューションが満たすべき要件を記述するために使用します。

3. Terminology

3. 用語

3.1. Network Boundary

3.1. ネットワーク境界

A network boundary is the part of a signaling path where messages pass between entities that are under different administrative control. Figure 2 in [RFC5853] shows a network boundary between the originating gateway GW-A1 in operator A's network and the Session Border Controller (SBC) in operator B's network. A network boundary is significant in this document because manipulation of signaling at the boundary could prevent end-to-end testing or troubleshooting.

ネットワーク境界とは、異なる管理主体の制御下にあるエンティティーの間でメッセージが受け渡される、シグナリング経路上の部分です。[RFC5853]の図2は、事業者Aのネットワーク内の発信側ゲートウェイGW-A1と、事業者Bのネットワーク内のセッションボーダーコントローラー（SBC）との間のネットワーク境界を示しています。境界でシグナリングが操作されるとエンドツーエンドのテストやトラブルシューティングができなくなる可能性があるため、この文書ではネットワーク境界が重要です。

Topology hiding and protocol repair (see [RFC5853]) are two common functions that manipulate signaling at the network boundary. These functions are performed by SIP device types (see [RFC7092]) such as a Session Border Controller and Interconnection Border Control Function (IBCF).

トポロジー隠蔽とプロトコル修復（[RFC5853]を参照）は、ネットワーク境界でシグナリングを操作する2つの一般的な機能です。これらの機能は、セッションボーダーコントローラーや相互接続ボーダー制御機能（Interconnection Border Control Function、IBCF）などのSIPデバイスタイプ（[RFC7092]を参照）によって実行されます。

3.2. Trust Domain

3.2. 信頼ドメイン

In this document, a trust domain is the set of entities that have been identified by prior agreement as the participating elements in logging, typically for the purpose of debugging or regression testing. A trust domain contains all SIP entities under configuration control of the network operator who is performing regression testing plus all SIP entities that are under configuration control of peer network operators who have agreed to participate in that regression testing. The purpose of trust domain requirements is to prevent network operators from inadvertently triggering logging in networks that are not part of any testing or troubleshooting.

この文書では、信頼ドメインとは、通常はデバッグや回帰テストを目的として、ログ記録に参加する要素であると事前の合意によって特定されたエンティティーの集合です。信頼ドメインには、回帰テストを実行しているネットワーク事業者の設定管理下にあるすべてのSIPエンティティーと、その回帰テストへの参加に合意したピアのネットワーク事業者の設定管理下にあるすべてのSIPエンティティーが含まれます。信頼ドメインの要件の目的は、ネットワーク事業者が、どのテストやトラブルシューティングにも含まれないネットワークで誤ってログ記録を引き起こすことを防ぐことです。

3.3. Intermediary

3.3. 仲介者

The term "intermediary" is defined in Section 2 of [RFC7989]; it refers to any entity along the call signaling path.

用語「仲介者（intermediary）」は[RFC7989]のセクション2で定義されており、呼のシグナリング経路上にある任意のエンティティーを指します。

4. Motivating Scenario

4. 動機となるシナリオ

4.1. Introduction

4.1. はじめに

Signaling for SIP session setup can cross several networks; these networks may not have common ownership and may also be in different countries. If a single operator wishes to perform regression testing or fault debugging end-to-end, the separate ownership of networks that carry the signaling and the explosion in the number of possible signaling paths through SIP entities from the originating to the terminating user make it impractical to preconfigure logging end-to-end SIP signaling of a session of interest.

SIPのセッション確立のためのシグナリングは、複数のネットワークを横断することがあります。これらのネットワークは共通の所有者を持たないことがあり、また異なる国にあることもあります。単一の事業者が回帰テストや障害のデバッグをエンドツーエンドで実行したい場合、シグナリングを運ぶネットワークの所有者が別々であることと、発信側ユーザーから着信側ユーザーまでSIPエンティティーを通るシグナリング経路の候補の数が爆発的に増えることにより、関心のあるセッションのエンドツーエンドのSIPシグナリングのログ記録を事前に設定することは現実的ではありません。

4.3. Example Debugging Procedure

4.3. デバッグ手順の例

One possible set of steps is outlined below to illustrate the debugging procedure.

デバッグ手順を説明するために、考えられる手順の一例を以下に概説します。

  • The user's terminal is placed in debug mode. The terminal logs its own signaling and inserts a "log me" marker into SIP requests for session setup.
  • All SIP entities that the signaling traverses, from the first proxy the terminal connects to at the edge of the network to the destination client terminal, detect that the "log me" marker is present and then log SIP requests and responses that contain the marker if configured to do so.
  • Subsequent responses and requests in the same dialog are also marked with a "log me" marker. For some scenarios, such as call transfer, related dialogs may also be marked with "log me" marker.
  • Logging stops, either because the dialog has ended or because a "stop event", typically expiry of a certain amount of time, occurred.
  • Logs are retrieved, for example, by logging on to the SIP entity or entities that contain the logs.
  • ユーザーの端末をデバッグモードにします。端末は自身のシグナリングをログに記録し、セッション確立のためのSIPリクエストに「log me」マーカーを挿入します。
  • 端末がネットワークのエッジで接続する最初のプロキシーから宛先のクライアント端末まで、シグナリングが通過するすべてのSIPエンティティーは、「log me」マーカーが存在することを検出し、そうするように設定されていれば、そのマーカーを含むSIPリクエストとレスポンスをログに記録します。
  • 同じダイアログ内の後続のレスポンスとリクエストにも「log me」マーカーでマーキングします。呼転送などの一部のシナリオでは、関連するダイアログにも「log me」マーカーでマーキングすることがあります。
  • ダイアログが終了したか、「停止イベント（stop event）」（通常は一定時間の経過）が発生したかのいずれかにより、ログ記録が停止します。
  • ログを取得します。たとえば、ログを保持しているSIPエンティティーにログオンして取得します。

5. "Log Me" Marking Requirements

5. 「Log Me」マーキングの要件

5.1. Message Logs

5.1. メッセージのログ

REQ1
If a SIP message is logged, then the entire SIP message (SIP headers and message body) MUST be logged using a standard logging format such as SIP Common Log Format (CLF) defined in [RFC6873].
REQ2
Header fields SHOULD be logged in the form in which they appear in the message; they SHOULD NOT be converted between long and compact forms as described in [RFC3261], Section 7.3.3.
REQ1
SIPメッセージをログに記録する場合、SIPメッセージ全体（SIPヘッダーとメッセージ本文）を、[RFC6873]で定義されているSIP共通ログフォーマット（Common Log Format、CLF）などの標準的なログフォーマットを使用してログに記録しなければなりません（MUST）。
REQ2
ヘッダーフィールドは、メッセージに現れる形式のままログに記録すべきです（SHOULD）。[RFC3261], セクション7.3.3で説明されている長い形式とコンパクト形式との間で変換すべきではありません（SHOULD NOT）。

When and how signaling logs are retrieved is out of scope of this document. Logs might be retrieved by logging on to the SIP entity that contains the logs, by sending logs to a central server that is coordinating debugging, by storing them on removable media for later manual collection, or by some other method. All log retrieval mechanisms MUST adhere to the authorization and privacy protection policies set forth by the network administrator.

シグナリングのログをいつどのように取得するかは、この文書の範囲外です。ログは、ログを保持しているSIPエンティティーにログオンする、デバッグを調整している中央のサーバーにログを送信する、後で手作業で回収するためにリムーバブルメディアに保存する、またはその他の方法で取得されることがあります。すべてのログ取得メカニズムは、ネットワーク管理者が定めた認可とプライバシー保護のポリシーに従わなければなりません（MUST）。

5.2. "Log Me" Marking

5.2. 「Log Me」マーキング

REQ3:
It MUST be possible to mark a SIP request or response to be considered for logging by inserting a "log me" marker. This is known as "log me" marking.
REQ4:
It MUST be possible for a "log me" marker to cross network boundaries.
REQ5:
A "log me" marker MAY include an identifier that indicates the test case that caused it to be inserted, known as a "test case identifier". The test case identifier does not have any impact on session setup; it is used to collate all logged SIP requests and responses to the initial SIP request in a dialog or standalone transaction. The local Universally Unique Identifier (UUID) portion of the Session-ID described in [RFC7206] and [RFC7989] could be used as a random test case identifier.
REQ3:
SIPリクエストまたはレスポンスに「log me」マーカーを挿入することで、そのリクエストまたはレスポンスをログ記録の検討対象としてマーキングできなければなりません（MUST）。これを「log me」マーキングと呼びます。
REQ4:
「log me」マーカーがネットワーク境界を越えられなければなりません（MUST）。
REQ5:
「log me」マーカーには、そのマーカーを挿入する原因となったテストケースを示す識別子を含めてもよいです（MAY）。この識別子を「テストケース識別子」と呼びます。テストケース識別子はセッション確立には何の影響も与えません。テストケース識別子は、ログに記録されたすべてのSIPリクエストとレスポンスを、ダイアログまたは単独のトランザクションにおける最初のSIPリクエストと照合するために使用します。[RFC7206]と[RFC7989]で説明されているSession-IDのローカルの汎用一意識別子（UUID）部分を、ランダムなテストケース識別子として使用できます。

5.3. Processing the "Log Me" Marker

5.3. 「Log Me」マーカーの処理

REQ6:
A "log me" marker is most effective if all networks on the signaling path agree to pass it end-to-end. However, source networks should behave responsibly and not leave it to a downstream network to detect and remove a marker that it is not expecting.
REQ7:
The presence of a "log me" marker indicates that a request or response is part of debugging or regression testing.
REQ8:
It MUST be possible to insert a "log me" marker in SIP responses that correspond to SIP requests with a "log me" marker in order to ensure that the complete SIP transaction is logged. This requirement applies to endpoints, SIP/Public Switched Telephone Network (PSTN) gateways, and back-to-back user agents (B2BUAs).
REQ9:
The "log me" marker mechanism SHOULD allow a SIP intermediary to request logging SIP requests and responses on behalf of the originating endpoint. The typical use case for this requirement is for compatibility with User Agents (UAs) that have not implemented "log me" marking, i.e., when a UA has not marked a request or when responses received on a dialog of interest for logging do not contain an echoed "log me" marker. Another use case is when the session origination UA that inserted the "log me" marker is no longer participating in the session (e.g., call transfer scenarios) and the intermediary adds a "log me" marker in related sessions to enable end-to-end signaling analysis.
REQ10:
The mechanism MUST allow stateless processing of SIP requests that contain a "log me" marker by SIP intermediaries. This requirement enables the SIP intermediaries to base the decision to log a SIP request or response solely on the presence of the "log me" marker.
REQ11:
The scope of a SIP message logging request includes all requests and responses within a given dialog. The scope can be extended to related dialogs that correspond to an end-to-end session for scenarios discussed in REQ9. The "log me" request MUST be indicated at the beginning of the dialog of interest and SHOULD continue to the dialog end without any stop and restart during the duration of the dialog.
REQ12:
The presence of a "log me" marker might cause some SIP entities to log signaling. Therefore, this marker MUST be removed at the earliest opportunity if it has been incorrectly inserted (e.g., mid-dialog or outside the configured start and stop of "log me" marking).
REQ6:
「log me」マーカーは、シグナリング経路上のすべてのネットワークがそれをエンドツーエンドで受け渡すことに合意している場合に最も効果的です。しかし、送信元のネットワークは責任ある振る舞いをすべきであり、下流のネットワークに、そのネットワークが想定していないマーカーの検出と削除を任せるべきではありません。
REQ7:
「log me」マーカーの存在は、リクエストまたはレスポンスがデバッグまたは回帰テストの一部であることを示します。
REQ8:
完全なSIPトランザクションが確実にログに記録されるように、「log me」マーカーを持つSIPリクエストに対応するSIPレスポンスに、「log me」マーカーを挿入できなければなりません（MUST）。この要件は、エンドポイント、SIP/公衆交換電話網（PSTN）ゲートウェイ、バックツーバックユーザーエージェント（B2BUA）に適用されます。
REQ9:
「log me」マーカーのメカニズムは、SIPの仲介者が発信元のエンドポイントに代わってSIPリクエストとレスポンスのログ記録を要求できるようにすべきです（SHOULD）。この要件の典型的なユースケースは、「log me」マーキングを実装していないユーザーエージェント（UA）との互換性のため、つまりUAがリクエストをマーキングしていない場合や、ログ記録の対象となるダイアログで受信したレスポンスに「log me」マーカーがエコーされていない場合です。別のユースケースは、「log me」マーカーを挿入したセッション発信元のUAがもはやセッションに参加しておらず（たとえば呼転送のシナリオ）、エンドツーエンドのシグナリングの分析を可能にするために仲介者が関連するセッションに「log me」マーカーを追加する場合です。
REQ10:
このメカニズムは、「log me」マーカーを含むSIPリクエストをSIPの仲介者がステートレスに処理できるようにしなければなりません（MUST）。この要件により、SIPの仲介者は、SIPリクエストまたはレスポンスをログに記録するかどうかを「log me」マーカーの存在だけに基づいて決定できるようになります。
REQ11:
SIPメッセージのログ記録の要求の範囲には、あるダイアログ内のすべてのリクエストとレスポンスが含まれます。REQ9で説明したシナリオでは、この範囲を、エンドツーエンドのセッションに対応する関連するダイアログに拡張できます。「log me」の要求は、対象となるダイアログの開始時に示さなければなりません（MUST）。また、ダイアログの期間中に停止と再開をすることなくダイアログの終了まで継続すべきです（SHOULD）。
REQ12:
「log me」マーカーが存在すると、一部のSIPエンティティーがシグナリングをログに記録する可能性があります。したがって、このマーカーが誤って挿入された場合（たとえばダイアログの途中や、設定された「log me」マーキングの開始から停止までの範囲外で挿入された場合）、このマーカーはできるだけ早い機会に削除しなければなりません（MUST）。

The definition of types of events that cause logging to stop and the configuration of SIP entities to detect such "stop events" is outside the scope of this document.

ログ記録を停止させるイベントの種類の定義と、そのような「停止イベント」を検出するためのSIPエンティティーの設定は、この文書の範囲外です。

6. Security Considerations

6. セキュリティーに関する考慮事項

In order to prevent any security implications of a "log me" marker, the marker itself MUST NOT contain any sensitive information, detecting its presence or absence MUST NOT reveal sensitive information, and maliciously adding a "log me" marker MUST NOT adversely affect a network. This section analyzes how to meet these requirements.

「log me」マーカーによるセキュリティー上の影響を防ぐために、マーカー自体に機密情報を含めてはなりません（MUST NOT）。また、マーカーの有無を検出することで機密情報が明らかになってはなりません（MUST NOT）。さらに、悪意を持って「log me」マーカーを追加することでネットワークに悪影響が及んではなりません（MUST NOT）。このセクションでは、これらの要件を満たす方法を分析します。

6.1. Trust Domain

6.1. 信頼ドメイン

Since a "log me" marker may cause a SIP entity to log the SIP header and body of a request or response, the "log me" marker MUST be removed at a trust domain boundary. If a prior agreement to log sessions exists with the next hop network, then the "log me" marker SHOULD NOT be removed.

「log me」マーカーによってSIPエンティティーがリクエストまたはレスポンスのSIPヘッダーと本文をログに記録する可能性があるため、「log me」マーカーは信頼ドメインの境界で削除しなければなりません（MUST）。ネクストホップのネットワークとの間にセッションをログに記録するという事前の合意が存在する場合、「log me」マーカーを削除すべきではありません（SHOULD NOT）。

6.2. Security Threats

6.2. セキュリティー上の脅威

6.2.1. "Log Me" Marking

6.2.1. 「Log Me」マーキング

The "log me" marker MUST NOT convey any sensitive information, although the "log me" marker will sometimes be inserted because a particular device is experiencing problems. The "log me" marker MUST NOT reveal any information related to any SIP user or device.

「log me」マーカーは、特定のデバイスで問題が発生しているために挿入されることもありますが、機密情報を伝えてはなりません（MUST NOT）。「log me」マーカーは、SIPのユーザーやデバイスに関連するいかなる情報も明らかにしてはなりません（MUST NOT）。

The insertion of the "log me" marker at the endpoint MUST be approved by the end user or by the network administrator. Similarly, network administrator authorization is required for a SIP intermediary to insert a "log me" marker on behalf of a UA that does not support "log me" marking.

エンドポイントでの「log me」マーカーの挿入は、エンドユーザーまたはネットワーク管理者によって承認されなければなりません（MUST）。同様に、SIPの仲介者が「log me」マーキングをサポートしていないUAに代わって「log me」マーカーを挿入するには、ネットワーク管理者の認可が必要です。

Activating a debug mode affects the operation of a terminal; therefore, the debugging configuration MUST be supplied by an authorized party to an authorized terminal through a secure communication channel.

デバッグモードを有効にすると端末の動作に影響するため、デバッグの設定は、認可された当事者が、安全な通信チャネルを通じて、認可された端末に提供しなければなりません（MUST）。

6.2.2. Logged Information

6.2.2. ログに記録される情報

Logged signaling is privacy-sensitive data; therefore, signaling logs MUST NOT be readable by an unauthorized third party.

ログに記録されたシグナリングはプライバシー上機微なデータです。したがって、シグナリングのログは、認可されていない第三者が読めるようになっていてはなりません（MUST NOT）。
