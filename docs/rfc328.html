RFC 328

Suggested Telnet Protocol Changes

RFC 328

Telnetプロトコルの変更の提案

Abstract

概要

I hereby propose the following changes to the Telnet protocol. If no substantial negative response is received by 15 May 72 it will be assumed that these changes are desired and should be incorporated in any "Official Telnet Protocol".

私はここに、Telnetプロトコルに対する次の変更を提案します。72年5月15日までに実質的な反対意見が寄せられなければ、これらの変更は望まれているものとみなし、あらゆる「公式Telnetプロトコル」に取り入れるべきものとします。

First I suggest that we drop the idea of a "minimum" implementation and require a standard implementation which includes all aspects of the protocol.

第一に、「最小」実装という考え方をやめ、プロトコルのすべての側面を含む標準実装を必須とすることを提案します。

Second I suggest that we eliminate the DATA TYPE signals.

第二に、DATA TYPE信号を廃止することを提案します。

Third I suggest that we do away with HIDE YOUR INPUT signal.

第三に、HIDE YOUR INPUT信号をなくすことを提案します。

Arguments:

論拠：

Standard Implementation:
The idea of an accepted implementation which does not include whole protocol is an admission that the parts of the protocol left out are either not useful or not expected to be used, and that other mechanisms will be constructed to provide those functions. Thus there should be no minimum implementation, but only the standard implementation which includes the whole protocol.
Data Types:
The DATA TYPE signals are supposed to allow the communicating processes to switch from ASCII to some other code set. However, the other code sets suggested do not allow for the Telnet signals, and thus once the switch is made the Telnet protocol is no longer applicable. There is no way to specify how to get back to ASCII or Telnet thus the conversation is "out of control".
Hide Your Input:
The HIDE YOUR INPUT signal is supposed to tell the user Telnet process to do whatever it can to hide the user's subsequent input. One problem with this is determining how much input is to be hidden. It is very difficult to find a method of hiding input which works for all combinations of systems and terminals, but the HIDE YOUR INPUT signal dosen't help in any real way.
標準実装：
プロトコル全体を含まない実装を認めるという考え方は、省かれたプロトコルの部分が役に立たないか、使われる見込みがないこと、そしてそれらの機能を提供するためにほかの仕組みが作られることを認めるに等しいものです。したがって、最小実装は設けず、プロトコル全体を含む標準実装だけにすべきです。
データ型：
DATA TYPE信号は、通信するプロセスがASCIIからほかのコードセットに切り替えられるようにするためのものです。しかし、提案されているほかのコードセットにはTelnet信号の余地がないため、いったん切り替えるとTelnetプロトコルはもう適用できなくなります。ASCIIやTelnetに戻る方法を指定する手段がないので、会話は「制御不能」になってしまいます。
入力の隠蔽：
HIDE YOUR INPUT信号は、ユーザーTelnetプロセスに対し、ユーザーのその後の入力を隠すためにできることを何でもするよう伝えるためのものです。これに関する問題の1つは、どれだけの入力を隠すべきかを判断することです。システムと端末のあらゆる組み合わせで機能する入力の隠し方を見つけるのは非常に難しく、HIDE YOUR INPUT信号は実際にはまったく役に立ちません。
