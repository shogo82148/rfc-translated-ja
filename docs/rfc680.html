RFC 680

Message Transmission Protocol

RFC 680

メッセージ伝送プロトコル

Abstract

概要

This document defines a number of message fields beyond those discussed in RFC 561. The overall message format is compatible with RFC 561; it makes extensive use of the miscellaneous fileds defined within RFC 561. The purpose of this document is to establish ARPANET standards with regard to the syntax and semantics for these additional fields. It is fully expected that all fields discussed herein will not be automatically processed by all Message Servers; however, the standard is necessary so that sites which wish to make use of these fields have a standard to work with.

この文書では、RFC 561で説明されているもの以外の、いくつかのメッセージフィールドを定義します。全体的なメッセージ形式はRFC 561と互換性があり、RFC 561で定義されているその他のフィールドを広く活用しています。この文書の目的は、これらの追加フィールドの構文とセマンティクスに関するARPANETの標準を確立することです。ここで説明するすべてのフィールドが、すべてのメッセージサーバーによって自動的に処理されるわけではないことは十分に予想されます。しかし、これらのフィールドを利用したいサイトが拠り所にできる標準を用意するために、この標準が必要です。

This document attempts to tread the narrow line between features for human processing and features for machine processing. The general feeling is that the fields listed are useful to people even if automatic processing is not supplied. In most cases, machine-readable notations have been enclosed in angle brackets (<>) to allow easy non-ambiguous ways for automatic processes to know whether and where to look in any field. The entire specifications has been made excessively general to allow for experimentation. Future documents based on experience will try to be more specific. This is simply the next step following <RFC 561>.

この文書は、人間による処理のための機能と機械による処理のための機能の間の、狭い境界線をたどろうとするものです。概して、ここに挙げたフィールドは、自動処理が提供されていなくても人間にとって有用であると考えられます。ほとんどの場合、機械可読な表記は山括弧（<>）で囲まれています。これにより、自動処理を行うプロセスは、あるフィールドの中を見るべきかどうか、どこを見るべきかを、簡単かつ曖昧さなく知ることができます。仕様全体は、実験ができるように過度に汎用的なものにしてあります。経験に基づく今後の文書では、より具体的にしていく予定です。これは単に、<RFC 561>に続く次の一歩にすぎません。

This document is contained in two sections. Section I contains the relevant parts of RFC 561 which define the basic message syntax. Section II lists the new (and existing) header fields together with their proposed uses.

この文書は2つのセクションで構成されています。セクションIには、基本的なメッセージ構文を定義しているRFC 561の関連部分を収めています。セクションIIでは、新しい（および既存の）ヘッダーフィールドを、提案する用途とともに列挙します。

SECTION I: BASIC MESSAGE SYNTAX

セクションI：基本的なメッセージ構文 

<message>            ::=     <header><crlf><body>
<header>             ::=     <required header><optional header>
<required header>    ::=     <date item><sender item>
<date item>          ::=     DATE:<sp><date><sp>AT<sp>
                             <time>-<zone><crlf>
<date>               ::=     <vdate>  !  <tdate>
<vdate>              ::=     <dayofmonth><SP><vmonth><SP><vyear>
<tdate>              ::=     <tmonth>/<dayofmonth>/<tyear>
<dayofmonth>         ::=     one or two decimal digits
<vmonth>             ::=     JAN ! FEB ! MAR ! APR ! MAY ! JUN !
                             JUL ! AUG ! SEP ! OCT ! NOV !  DEC
<tmonth>             ::=     one or two decimal digits
<vyear>              ::=     four decimal digits
<tyear>              ::=     two decimal digits
<zone>               ::=     EST ! EDT ! CST ! CDT ! MST ! MDT !
                             PST ! PDT ! GMT ! GDT
<time>               ::=     four decimal digits
<sender item         :=      SENDER: <sp><user><sp>AT<sp><host>
                             <crlf>
<optional header>    ::=     <subjects><optional items>
<subjects>           ::=     !<subject item> !
                             <subject item><subjects>
<subject item>       ::=     SUBJECT:<sp><line><crlf>
<optional items>     ::=     <optional item> ! <optional item>
                             <optional items>
<optional item>      ::=     <messid> ! <addressee item> !
                             <other item>
<addressee item>     ::=     <addressee keyword>:<sp><addressee
                             list><crlf>
<addressee keywork>  ::=     TO:! CC:! BCC:!
<messid>             ::=     Message-ID:<sp>[<Net
                             Address>}]<line>
                             <crlf>
<other item>         ::=     <other keyword>:<sp><line><crlf>
<other keyword>      ::=     FROM ! IN-REPLY-TO! REFERENCES!
                             KEYWORD ! PRECEDENCE !
                             MESSAGE-CLASS!
                             SPECIAL-HANDLING! AUTHENTICATION!
                             ACCESSION-KEY
<address list>       ::=     <addressee> ! <addressee><addressee
                             list>
<addressee>          ::=     <mailbox> ! <mailbox group>
<mailbox>            ::=     <user><host spec><attention spec>
<host spec>          ::=     !@<host>
<attention spec>     ::=     (ATTN:<sp><user list>)
<user list>          ::=     <user> ! <user><user list>
<mailbox group>      ::=     <group name>:(<group numbers>)
<group numbers>      ::=     ! (<mailbox list>)
<mailbox list>       ::=     <mailbox> ! <mailbox>,<mailboxlist>

Notes:

注：

  1. A message may have at most one MESSAGE-ID item.
  2. All items with the same keyword must be grasped together.
  1. 1つのメッセージが持てるMESSAGE-ID項目は、最大で1つです。
  2. 同じキーワードを持つ項目は、すべてまとめて扱わなければなりません。

Please note the following:

次の点に注意してください。

  1. The case (upper or lower) of keywords -- specifically, 'FROM', 'DATE', 'SUBJECT', 'AT', <host>, <zone>, <vmonth> and <keyword> -- is insignificant. Although 'FROM', for example, appears in upper-case in the formal syntax above, in the header of an actual message it may appear as 'FROM', 'from', or 'From', etc.
  2. No attempt has been made to legislate the format of <user> except to exclude spaces from it.
  3. The time has no internal punctuation.
  1. キーワード（具体的には、'FROM'、'DATE'、'SUBJECT'、'AT'、<host>、<zone>、<vmonth>、<keyword>）の大文字・小文字の区別は重要ではありません。たとえば、上の形式的な構文では'FROM'は大文字で書かれていますが、実際のメッセージのヘッダーでは'FROM'、'from'、'From'などと書いてもかまいません。
  2. <user>の形式については、空白を含まないこと以外は何も規定していません。
  3. 時刻には内部に区切り記号を含めません。

SECTION II: MESSAGE HEADER FIELDS

セクションII：メッセージヘッダーフィールド

A. ORIGINATOR SPECIFICATION FIELDS

A. 発信者を指定するフィールド

FROM
This field contains the identity of the person who wished this message to be sent. This is expected to be the originator field which is specified by the user in the case that the message is being entered by one person for another. The message-creation process should default this field to be the user entering the message. [The usage for FROM and SENDER differs from that of RFC 561.]
SENDER
This field contains the identity of the person who sends the message. This field is expected to be set by the message-creation process automatically. It is possible that some sites will not include this field in external communications.
AUTHENTICATION

This field contains a description of which originator fields have been authenticated, and by which operating systems. This field should be created by message transmission and/or reception processes (FTP/Operating System level).

It is expected that current system will be able to authenticate only the SENDER field; however, later systems might have mechanisms to verify that the FROM actually authorized the SENDER to act on his/her behalf. It is expected that, when the FROM is authenticated, the SENDER will no longer be necessary for external distribution.

FROM
このフィールドには、このメッセージの送信を望んだ人物の識別情報が入ります。これは、ある人が別の人の代わりにメッセージを入力する場合に、ユーザーが指定する発信者フィールドとなることが想定されています。メッセージ作成プロセスは、このフィールドのデフォルト値を、メッセージを入力しているユーザーにすべきです。[FROMとSENDERの使い方は、RFC 561のものとは異なります。]
SENDER
このフィールドには、メッセージを送信する人物の識別情報が入ります。このフィールドは、メッセージ作成プロセスによって自動的に設定されることが想定されています。サイトによっては、外部との通信にこのフィールドを含めない可能性があります。
AUTHENTICATION

このフィールドには、どの発信者フィールドがどのオペレーティングシステムによって認証されたかの説明が入ります。このフィールドは、メッセージの送信プロセスと受信プロセスの一方または両方（FTP／オペレーティングシステムのレベル）が作成すべきです。

現在のシステムで認証できるのはSENDERフィールドだけと考えられますが、将来のシステムには、FROMがSENDERに自分の代理として行動することを実際に許可したかを検証するメカニズムが備わるかもしれません。FROMが認証されるようになれば、外部への配布にSENDERはもはや必要なくなると考えられます。

B. REFERENCE SPECIFICATION FIELDS

B. 参照を指定するフィールド

MESSAGE-ID

This field contains a unique identifier to refer to this message. The format for a message identifier is:

[Net Address]Text String CRLF
Examples:
           [ISIB]7-DEC-74.14:23:45
           [ARC]QLOURNAL 39274a3

The uniqueness of the message identifier is guaranteed by each net-address message processor making the text which follows unique for that net-address. This, specifically says net-address and not site name. This would allow BBN (for instance) to allocate unique identifiers over all four machines, which may be addressed as BBN within the message system, thus producing a more integrated service for their users.

The text following the net-address is not defined here, as the problems associated with this specification are too great at this time. However, the net-address should allow automatic processes to determine if they can deal intelligently with the following text. Several types of automatic processing by the local message reader are thus possible: 1) if the site uses a filing mechanism known to the reader, the reader can retrieve the message 2) if the site supports remote message access (protocol not currently defined), the message id can be passed to the remote site and the message has been filed in the Datacomputer (using the entire message id [including net-address] as the handle), the reader can retrieve it from the Datacomputer.

IN-REPLY-TO
The contents of this field identify previous correspondence which this message answers. If message identifiers are used in this field, they should be enclosed in angle brackets (<>).
REFERENCES
The contents of this field identify other correspondence which this message references. If message identifiers are used, they should be enclosed in angle brackets (<>).
KEYWORDS
This field contains keywords or phrases from the message, separated by commas.
MESSAGE-ID

このフィールドには、このメッセージを参照するための一意な識別子が入ります。メッセージ識別子の形式は次のとおりです。

[Net Address]Text String CRLF
Examples:
           [ISIB]7-DEC-74.14:23:45
           [ARC]QLOURNAL 39274a3

メッセージ識別子の一意性は、ネットアドレスごとのメッセージプロセッサーが、続くテキストをそのネットアドレス内で一意にすることによって保証されます。ここでは、サイト名ではなく、あくまでネットアドレスと言っていることに注意してください。これにより、たとえばBBNは、メッセージシステム内でBBNとしてアドレス指定される可能性のある4台のマシン全体にわたって一意な識別子を割り当てることができ、ユーザーにより統合されたサービスを提供できます。

ネットアドレスに続くテキストは、この仕様に伴う問題が現時点ではあまりにも大きいため、ここでは定義しません。しかし、ネットアドレスによって、自動処理を行うプロセスは、続くテキストを賢く扱えるかどうかを判断できるはずです。したがって、ローカルのメッセージリーダーでは、いくつかの種類の自動処理が可能になります。1）サイトがリーダーの知っているファイリングメカニズムを使用している場合、リーダーはメッセージを取得できます。2）サイトがリモートメッセージアクセス（プロトコルは現在定義されていません）をサポートしている場合、メッセージIDをリモートサイトに渡すことができます。また、メッセージが（ネットアドレスを含むメッセージID全体をハンドルとして使用して）Datacomputerに保存されている場合、リーダーはDatacomputerからメッセージを取得できます。

IN-REPLY-TO
このフィールドの内容は、このメッセージが返答している過去のやりとりを識別します。このフィールドでメッセージ識別子を使用する場合は、山括弧（<>）で囲むべきです。
REFERENCES
このフィールドの内容は、このメッセージが参照している他のやりとりを識別します。メッセージ識別子を使用する場合は、山括弧（<>）で囲むべきです。
KEYWORDS
このフィールドには、メッセージ中のキーワードや語句をコンマで区切って入れます。

C. RECEIVER SPECIFICATION FIELDS

C. 受信者を指定するフィールド

TO
This field contains the identity of the primary receivers of the message.
CC
This field contains the identity of the secondary receivers of the message.
BCC
This field contains the identity of the tertiary receivers of the message. This field should not be made available to the primary and secondary receivers, but it may be recorded to provide information for access control.
TO
このフィールドには、メッセージの一次受信者の識別情報が入ります。
CC
このフィールドには、メッセージの二次受信者の識別情報が入ります。
BCC
このフィールドには、メッセージの三次受信者の識別情報が入ります。このフィールドは一次受信者と二次受信者が見られるようにすべきではありませんが、アクセス制御のための情報を提供するために記録しておいてもかまいません。

D. MESSAGE-TYPE SPECIFICATION FIELDS

D. メッセージの種類を指定するフィールド

PRECEDENCE
This field describes the importance and urgency of the message. Machine-readable notations will be enclosed in angle brackets (<>). <PRIORITY> means that the message should be delivered as soons as possible. <ROUTINE> means that Priority processing is not necessary. Plain text may also be included in this field.
MESSAGE-CLASS

This field describes the "legal" status of the message. Examples: Official, Unofficial, Record, Off the Record, Junk Mail. No automatic processing of this field is immediately expected. Certain message creation processes might, for example, always insert:

MESSAGE CLASS: Unofficial ARPANET Message
SPECIAL-HANDLING
This field contains any special instructions with regard to the handling of the message at the receiver's end. Machine-readable notations will be enclosed in angle brackets (<>). <PRIVATE> means that the message reception process should not aid the user in circulating copies to others. Plain text may also be included in this field.
PRECEDENCE
このフィールドは、メッセージの重要度と緊急度を表します。機械可読な表記は山括弧（<>）で囲みます。<PRIORITY>は、メッセージをできるだけ早く配送すべきであることを意味します。<ROUTINE>は、優先処理が必要ないことを意味します。このフィールドには平文を含めることもできます。
MESSAGE-CLASS

このフィールドは、メッセージの「法的な」位置付けを表します。例：Official（公式）、Unofficial（非公式）、Record（記録用）、Off the Record（オフレコ）、Junk Mail（ジャンクメール）。このフィールドがすぐに自動処理されることは想定していません。たとえば、メッセージ作成プロセスによっては、常に次のように挿入するかもしれません。

MESSAGE CLASS: Unofficial ARPANET Message
SPECIAL-HANDLING
このフィールドには、受信者側でのメッセージの取り扱いに関する特別な指示が入ります。機械可読な表記は山括弧（<>）で囲みます。<PRIVATE>は、メッセージ受信プロセスが、ユーザーによる他者へのコピーの回覧を手助けすべきではないことを意味します。このフィールドには平文を含めることもできます。
