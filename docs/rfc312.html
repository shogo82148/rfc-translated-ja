RFC 312

Proposed Change in IMP-to-Host Protocol

RFC 312

IMP-to-Hostプロトコルの変更の提案

Abstract

概要

We are currently considering a redefinition of the IMP-to-Host error message types (type 1 and type 8) and the creation of additional IMP-to-Host error message types. We believe that these changes will assist the Hosts in determining appropriate recovery action, without causing any serious reprogramming problems. Our current plans are to install these changes within a few months; therefore we should be informed of any strong negative reactions relatively quickly.

現在、私たちは、IMP-to-Hostのエラーメッセージタイプ（タイプ1とタイプ8）の再定義と、IMP-to-Hostのエラーメッセージタイプの追加を検討しています。これらの変更は、深刻なプログラムの書き直しの問題を引き起こすことなく、ホストが適切な回復動作を決定するのに役立つと考えています。現在の計画では、これらの変更を数か月以内に導入する予定です。したがって、強い反対意見があれば、比較的早く知らせてもらう必要があります。

The proposed changes fall into two general classes as described below:

提案する変更は、以下で説明するように、大きく2つの種類に分かれます：

A) General Error Message
Under certain circumstances, particularly when the Host has been unresponsive to queued input for a "long time" the IMP drops its ready line for a short period, causing the "error flip-flops" to be set (see RFC #270, NIC 7818). Under these conditions the IMP sends a few NOP's to the Host and then resumes normal operation. We propose to send the Host a new message (message type 13) in addition to the NOPs; this message will tell the Host that the IMP's Ready Line was dropped, that the IMP's error flop was set, and that the IMP will respond to the next completion of a Host-to-IMP message with a type 1 or type 8 message (because of the setting of the IMP's error flop.
B) Error Messages which are Responses to Specific Host-to-IMP Transmissions:
  1. IMP-to-Host message type 1 will be redefined to mean: "IMP's Error flip-flop was set on a message which the IMP cannot identify."
  2. IMP-to-Host message type 8 will be redefined to mean: "IMP's Error flip-flop was set during receipt of the message identified by the 'source' and 'link number' bits of this error message."
  3. IMP-to-Host message type 10 will be defined to mean: "A Host-to-IMP message was too short (and cannot be identified)."
  4. IMP-to-Host message type 11 will be defined to mean: "A Host-to-IMP message was too long; the message is identified by the 'source' and 'link number' bits of this error message."
  5. IMP-to-Host message type 12 will be defined to mean: "A Host-to-IMP message with an illegal message type code was received; the message is identified by the 'source' and 'link number' bits of this error message. (Note that the erroneous type code is not included in the error message.)"
A）一般エラーメッセージ
特定の状況下で、特にキューに入れられた入力にホストが「長時間」応答しない場合、IMPはレディー線（ready line）を短時間落とし、その結果「エラーフリップフロップ」がセットされます（RFC #270、NIC 7818を参照）。この状況では、IMPはホストにいくつかのNOPを送信し、その後通常の動作を再開します。私たちは、NOPに加えて、新しいメッセージ（メッセージタイプ13）をホストに送信することを提案します。このメッセージは、IMPのレディー線が落とされたこと、IMPのエラーフロップがセットされたこと、そして（IMPのエラーフロップがセットされたために）IMPが次にHost-to-IMPメッセージの完了に対してタイプ1またはタイプ8のメッセージで応答することをホストに伝えます。
B）特定のHost-to-IMP送信への応答であるエラーメッセージ：
  1. IMP-to-Hostメッセージタイプ1を、次の意味に再定義します：「IMPが識別できないメッセージに対して、IMPのエラーフリップフロップがセットされた。」
  2. IMP-to-Hostメッセージタイプ8を、次の意味に再定義します：「このエラーメッセージの『source』ビットと『link number』ビットで識別されるメッセージの受信中に、IMPのエラーフリップフロップがセットされた。」
  3. IMP-to-Hostメッセージタイプ10を、次の意味に定義します：「Host-to-IMPメッセージが短すぎた（そして識別できない）。」
  4. IMP-to-Hostメッセージタイプ11を、次の意味に定義します：「Host-to-IMPメッセージが長すぎた。そのメッセージは、このエラーメッセージの『source』ビットと『link number』ビットで識別される。」
  5. IMP-to-Hostメッセージタイプ12を、次の意味に定義します：「不正なメッセージタイプコードを持つHost-to-IMPメッセージを受信した。そのメッセージは、このエラーメッセージの『source』ビットと『link number』ビットで識別される。（誤ったタイプコードはエラーメッセージに含まれないことに注意すること。）」
