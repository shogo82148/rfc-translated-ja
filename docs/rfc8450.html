RTP Payload Format for VC-2 High Quality (HQ) Profile

RFC 8450

VC-2 High Quality（HQ）プロファイルのためのRTPペイロード形式

Abstract

概要

This memo describes an RTP payload format for the High Quality (HQ) profile of Society of Motion Picture and Television Engineers Standard ST 2042-1, known as VC-2. This document describes the transport of HQ Profile VC-2 in RTP packets and has applications for low-complexity, high-bandwidth streaming of both lossless and lossy compressed video.

このメモは、VC-2として知られる米国映画テレビ技術者協会（Society of Motion Picture and Television Engineers）の規格ST 2042-1のHigh Quality（HQ）プロファイルのためのRTPペイロード形式を説明します。この文書は、HQプロファイルのVC-2をRTPパケットで転送する方法を説明するもので、可逆圧縮と非可逆圧縮の両方のビデオを、低い複雑さかつ高帯域幅でストリーミングする用途に適用できます。

The HQ profile of VC-2 is intended for low-latency video compression (with latency potentially on the order of lines of video) at high data rates (with compression ratios on the order of 2:1 or 4:1).

VC-2のHQプロファイルは、高データレート（圧縮率は2:1から4:1程度）での低遅延（遅延はビデオの数ライン程度になる可能性があります）のビデオ圧縮を目的としています。

1. Introduction

1. はじめに

This memo specifies an RTP payload format for the video coding standard Society of Motion Picture and Television Engineers ST 2042-1:2017 [VC2], also known as VC-2

このメモは、VC-2としても知られる米国映画テレビ技術者協会（Society of Motion Picture and Television Engineers）のビデオ符号化規格ST 2042-1:2017 [VC2]のためのRTPペイロード形式を規定します。

The VC-2 codec is a wavelet-based codec intended primarily for professional video use with high bit-rates and only low levels of compression. It has been designed to have a low level of complexity and potentially a very low latency through both encoder and decoder: with some choices of parameters, this latency may be as low as a few lines of video.

VC-2コーデックはウェーブレットベースのコーデックで、主に高ビットレートかつ低い圧縮レベルでのプロフェッショナル向けビデオ用途を意図しています。複雑さが低く、エンコーダーとデコーダーの両方を通じて非常に低い遅延を実現できる可能性があるように設計されています。パラメーターの選び方によっては、この遅延をビデオの数ライン分にまで抑えられる場合があります。

The low level of complexity in the VC-2 codec allows for this low-latency operation but also means that it lacks many of the more powerful compression techniques used in other codecs. As such, it is suitable for low compression ratios that produce coded data rates around half to a quarter of that of uncompressed video, at a similar visual quality.

VC-2コーデックの複雑さが低いことで、このような低遅延での動作が可能になりますが、その反面、他のコーデックで使用されている、より強力な圧縮技術の多くを欠いていることにもなります。そのため、VC-2は、同程度の視覚品質で、非圧縮ビデオの2分の1から4分の1程度の符号化データレートとなるような、低い圧縮率に適しています。

The primary use for VC-2 is likely to be in professional video production environments.

VC-2の主な用途は、プロフェッショナル向けのビデオ制作環境になると考えられます。

3. Media Format Description

3. メディア形式の説明

The VC-2 specification defines a VC-2 Stream as being composed of one or more Sequences. Each Sequence is independently decodable, containing all of the needed parameters and metadata for configuring the decoder.

VC-2仕様は、VC-2ストリーム（Stream）を、1つ以上のシーケンス（Sequence）で構成されるものとして定義しています。各シーケンスは独立して復号可能で、デコーダーを設定するために必要なすべてのパラメーターとメタデータを含んでいます。

Each Sequence consists of a series of 13-octet Parse Info Headers and variable-length Data Units. The Sequence begins and ends with a Parse Info Header, and each Data Unit is preceded by a Parse Info Header. Data Units come in a variety of types, and the type of a Data Unit is signaled in the preceding Parse Info Header. The most important types are the Sequence Header, which contains configuration data needed by the decoder, and several types of Coded Picture, which contain the coded data for the pictures themselves. Each picture represents a frame in a progressively scanned video Sequence or a field in an interlaced video Sequence.

各シーケンスは、13オクテットのパース情報ヘッダー（Parse Info Header）と可変長のデータユニット（Data Unit）の並びで構成されます。シーケンスはパース情報ヘッダーで始まり、パース情報ヘッダーで終わります。また、各データユニットの前にはパース情報ヘッダーが置かれます。データユニットにはさまざまな種類があり、データユニットの種類はその前にあるパース情報ヘッダーで通知されます。最も重要な種類は、デコーダーが必要とする設定データを含むシーケンスヘッダー（Sequence Header）と、ピクチャー自体の符号化データを含む数種類の符号化ピクチャー（Coded Picture）です。各ピクチャーは、プログレッシブ走査のビデオシーケンスではフレームを、インターレースのビデオシーケンスではフィールドを表します。

The first Data Unit in a Sequence as produced by an encoder is always a Sequence Header; however, Sequences can be joined in the middle, so it should not be assumed that the first Data Unit received will always be a Sequence Header.

エンコーダーが生成するシーケンスの最初のデータユニットは、常にシーケンスヘッダーです。しかし、シーケンスには途中から参加できるため、受信した最初のデータユニットが常にシーケンスヘッダーであると想定すべきではありません。

The High Quality (HQ) profile for VC-2 restricts the types of Parse Info Headers that may appear in the Sequence (and hence also the types of Data Unit) to only:

VC-2のHigh Quality（HQ）プロファイルでは、シーケンス内に出現できるパース情報ヘッダーの種類（したがってデータユニットの種類も）を、次のものだけに制限しています。

  • Sequence Headers (which are always followed by a Data Unit),
  • High Quality Pictures (which are always followed by a Data Unit),
  • High Quality Fragments (which are always followed by a Data Unit),
  • Auxiliary Data (which are always followed by a Data Unit),
  • Padding Data (which are always followed by a Data Unit), and
  • End of Sequence (which are never followed by a Data Unit).
  • シーケンスヘッダー（常に後ろにデータユニットが続きます）
  • High Quality Picture（常に後ろにデータユニットが続きます）
  • High Quality Fragment（常に後ろにデータユニットが続きます）
  • 補助データ（Auxiliary Data）（常に後ろにデータユニットが続きます）
  • パディングデータ（Padding Data）（常に後ろにデータユニットが続きます）
  • シーケンス終了（End of Sequence）（後ろにデータユニットが続くことはありません）

At the time of writing, there is no definition for the use of Auxiliary Data in VC-2, and Padding Data is required to be ignored by all receivers.

執筆時点では、VC-2における補助データの使用方法は定義されておらず、パディングデータはすべての受信者が無視することになっています。

Each High Quality Picture Data Unit contains a set of parameters for the picture followed by a series of Coded Slices, each representing a rectangular region of the transformed picture. Slices within a picture may vary in coded length, but all represent the same shape and size of rectangle in the picture.

各High Quality Pictureデータユニットは、そのピクチャーのパラメーターのセットと、それに続く一連の符号化スライス（Coded Slice）を含みます。各符号化スライスは、変換されたピクチャーの矩形領域を表します。ピクチャー内のスライスは符号化後の長さが異なる場合がありますが、いずれもピクチャー内の同じ形状と大きさの矩形を表します。

Each High Quality Fragment Data Unit contains either a set of parameters for a picture or a series of Coded Slices. Fragments carry the same data as pictures, but broken up into smaller units to facilitate transmission via packet-based protocols such as RTP.

各High Quality Fragmentデータユニットは、ピクチャーのパラメーターのセットか、一連の符号化スライスのいずれかを含みます。フラグメントはピクチャーと同じデータを運びますが、RTPのようなパケットベースのプロトコルでの送信を容易にするために、より小さな単位に分割されています。

This payload format only makes use of Fragments, not pictures.

このペイロード形式では、ピクチャーではなくフラグメントだけを使用します。

4. Payload Format

4. ペイロード形式

In this specification, each RTP packet is used to carry data corresponding to a single Parse Info Header and its following Data Unit (if it has one). A single packet MAY NOT contain data from more than one Parse Info Header or Data Unit. A single Parse Info Header and Data Unit pair MUST NOT be split across more than one packet. The sole exception to this rule is that an Auxiliary Data Unit MAY be split between multiple packets, using the B and E flags to indicate start and end.

この仕様では、各RTPパケットは、1つのパース情報ヘッダーと、それに続くデータユニット（ある場合）に対応するデータを運ぶために使用します。単一のパケットに、複数のパース情報ヘッダーやデータユニットのデータを含めることはできません（MAY NOT）。1組のパース情報ヘッダーとデータユニットを、複数のパケットに分割してはなりません（MUST NOT）。この規則の唯一の例外として、補助データユニットは、開始と終了を示すBフラグとEフラグを使用して、複数のパケットに分割してもよいです（MAY）。

This specification only covers the transport of Sequence Headers (together with their accompanying Data Unit), High Quality Fragments (together with their accompanying Data Unit), Auxiliary Data (together with their accompanying Data Unit), and (optionally) End Sequence Headers and Padding Data (for which no Data Unit it carried).

この仕様が扱うのは、シーケンスヘッダー（付随するデータユニットを含む）、High Quality Fragment（付随するデータユニットを含む）、補助データ（付随するデータユニットを含む）、および（任意で）シーケンス終了ヘッダーとパディングデータ（データユニットは運ばれません）の転送だけです。

High Quality Pictures can be transported by converting them into an equivalent set of High Quality Fragments. The size of Fragments should be chosen so as to fit within the MTU of the network in use.

High Quality Pictureは、等価なHigh Quality Fragmentのセットに変換することで転送できます。フラグメントのサイズは、使用するネットワークのMTUに収まるように選ぶべきです。

For this reason, this document defines six types of RTP packets in a VC-2 media stream:

このため、この文書では、VC-2メディアストリームにおける6種類のRTPパケットを定義します。

  • a VC-2 Sequence Header (Figure 1) (see Section 11 of the VC-2 specification [VC2]),
  • a Picture Fragment containing the VC-2 Transform Parameters for a Picture (Figure 2) (see Section 14 of the VC-2 specification [VC2]),
  • a Picture Fragment containing VC-2 Coded Slices (Figure 3) for a picture (see Section 14 of the VC-2 specification [VC2]),
  • the end of a VC-2 Sequence (Figure 4) (see Section 10.5.2 of the VC-2 specification [VC2]),
  • the contents of an Auxiliary Data Unit (Figure 5) (see Section 10.4.4 of the VC-2 specification [VC2]), and
  • an indication of the presence of a padding Data Unit (Figure 6) (see Section 10.4.5 of the VC-2 specification [VC2]).
  • VC-2シーケンスヘッダー（図1）（VC-2仕様[VC2]のセクション11を参照）
  • ピクチャーのVC-2変換パラメーター（Transform Parameters）を含むピクチャーフラグメント（図2）（VC-2仕様[VC2]のセクション14を参照）
  • ピクチャーのVC-2符号化スライスを含むピクチャーフラグメント（図3）（VC-2仕様[VC2]のセクション14を参照）
  • VC-2シーケンスの終了（図4）（VC-2仕様[VC2]のセクション10.5.2を参照）
  • 補助データユニットの内容（図5）（VC-2仕様[VC2]のセクション10.4.4を参照）
  • パディングデータユニットが存在することの通知（図6）（VC-2仕様[VC2]のセクション10.4.5を参照）

These six packet types can be distinguished by the fact that they use different codes in the Parse Code ("PC") field, except for the two types of Picture Fragment that use the same value in PC but have different values in the "No. of Slices" field.

これら6種類のパケットは、パースコード（Parse Code、「PC」）フィールドに異なるコードを使用することで区別できます。ただし、2種類のピクチャーフラグメントはPCに同じ値を使用し、「No. of Slices」フィールドの値が異なります。

The options for PC codes are explained in more detail in Section 4.3.

PCコードの選択肢については、セクション4.3で詳しく説明します。

All fields in the headers longer than a single bit are interpreted as unsigned integers in network byte order.

ヘッダー内の1ビットより長いフィールドは、すべてネットワークバイトオーダーの符号なし整数として解釈されます。

4.1. RTP Header Usage

4.1. RTPヘッダーの使用法

The fields of the RTP header have the following additional notes on their usage:

RTPヘッダーのフィールドの使用法について、次の補足事項があります。

Marker Bit (M):
1 bit. The marker bit MUST be set on any packet that contains the final slice in a coded picture and MUST NOT be set otherwise.
Payload Type (PT):
7 bits. A dynamically allocated payload type field that designates the payload as VC-2-coded video.
Sequence Number:
16 bits. Because the data rate of VC-2-coded Streams can often be very high, in the order of gigabits rather than megabits per second, the standard 16-bit RTP sequence number can cycle very quickly. For this reason, the sequence number is extended to 32 bits, and this field MUST hold the low-order 16 bits of this value.
Timestamp:

32 bits. If the packet contains Transform Parameters or Coded Slice data for a coded picture, then the timestamp corresponds to the sampling instant of the coded picture. A 90kHz clock SHOULD be used. A single RTP packet MUST NOT contain coded data for more than one coded picture, so there is no ambiguity here.

A Sequence Header packet SHOULD have the same timestamp as the picture that will follow it in the Stream. An End of Sequence packet SHOULD have the same timestamp as the previous picture that appeared in the Stream.

Marker Bit (M):
1ビット。符号化ピクチャーの最後のスライスを含むパケットには、マーカービットを設定しなければなりません（MUST）。それ以外の場合は設定してはなりません（MUST NOT）。
Payload Type (PT):
7ビット。ペイロードがVC-2で符号化されたビデオであることを示す、動的に割り当てられるペイロードタイプフィールドです。
Sequence Number:
16ビット。VC-2で符号化されたストリームのデータレートは、毎秒メガビットではなくギガビットのオーダーと非常に高くなることが多いため、標準の16ビットのRTPシーケンス番号は非常に短い時間で一周してしまう可能性があります。このため、シーケンス番号は32ビットに拡張され、このフィールドにはその値の下位16ビットを格納しなければなりません（MUST）。
Timestamp:

32ビット。パケットが符号化ピクチャーの変換パラメーターまたは符号化スライスのデータを含む場合、タイムスタンプはその符号化ピクチャーのサンプリング時刻に対応します。90kHzのクロックを使用すべきです（SHOULD）。単一のRTPパケットに複数の符号化ピクチャーの符号化データを含めてはなりません（MUST NOT）。そのため、ここであいまいさが生じることはありません。

シーケンスヘッダーパケットは、ストリーム内でその後に続くピクチャーと同じタイムスタンプを持つべきです（SHOULD）。シーケンス終了パケットは、ストリーム内でその前に出現したピクチャーと同じタイムスタンプを持つべきです（SHOULD）。

The remaining RTP header fields are used as specified in RTP [RFC3550].

残りのRTPヘッダーフィールドは、RTP [RFC3550]で規定されているとおりに使用します。

4.2. Payload Header

4.2. ペイロードヘッダー

The fields of the extended headers are defined as follows:

拡張ヘッダーのフィールドは、次のように定義します。

Extended Sequence Number:
16 bits. MUST contain the high-order 16 bits of the 32-bit packet sequence number. This is needed since the high data rates of VC-2 Sequences mean that it is highly likely that the 16-bit sequence number will roll over too frequently to be of use for Stream synchronization.
B:
1 bit. MUST be set to 1 if the packet contains the first byte of an Auxiliary Data Unit and otherwise MUST be 0. If the recommendations in Section 4.4 ("Stream Constraints") are followed, then every Auxiliary Data Unit will be small enough to fit in a single packet, and so this bit (where present) will always be 1.
E:
1 bit. MUST be set to 1 if the packet contains the final byte of an Auxiliary Data Unit and otherwise MUST be 0. If the recommendations in Section 4.4 ("Stream Constraints") are followed, then every Auxiliary Data Unit will be small enough to fit in a single packet, and so this bit (where present) will always be 1.
I:
1 bit. MUST be set to 1 if the packet contains coded picture parameters or slice data from a field in an interlaced frame. MUST be set to 0 if the packet contains data from any part of a progressive frame.
F:
1 bit. MUST be set to 1 if the packet contains coded picture parameters or slice data from the second field of an interlaced frame. MUST be set to 0 if the packet contains data from the first field of an interlaced frame or any part of a progressive frame.
Parse Code (PC):
8 bits. Contains a Parse Code that MUST be the value indicated for the type of data in the packet.
Data Length:
32 bits. For an auxiliary Data Unit, this contains the number of bytes of data contained in the payload section of this packet. If the recommendations in Section 4.4 ("Stream Constraints") are followed, then no Auxiliary Data Unit will be large enough to cause a packet to exceed the MTU of the network.
Picture Number:

32 bits. MUST contain the Picture Number for the coded picture this packet contains data for, as described in Section 12.1 of the VC-2 specification [VC2].

The sender MUST send at least one transform-parameters packet for each coded picture and MAY include more than one as long as they contain identical data. The sender MUST NOT send a packet from a new picture until all the coded data from the current picture has been sent.

If the receiver receives Coded Slices packets for a picture but does not receive a Transform Parameters packet for that picture, then this is an indication of either packet loss, joining a Stream mid-picture, or a non-compliant transmitter. In this case, the receiver MAY assume that the parameters are unchanged since the last picture, or it MAY discard the picture. Choosing between these two options is left up to the implementation as it will be dependent on intended use. The former may result in malformed pictures, while the latter will result in dropped frames.

パケット内の「PC」フィールドは、パケットの内容の種類を識別するパースコードを運ぶために使用します。このコードは、VC-2仕様で定義されている、VC-2ストリーム内の各データユニットを識別するために使用されるパースコードの値と一致し、各パケットはデータユニット全体を含みます。

4.4. Stream Constraints

4.4. ストリームの制約

A Sequence needs to conform to certain constraints in order to be transmissible with this specification.

この仕様で送信できるようにするためには、シーケンスは特定の制約に従う必要があります。

  • The Sequence MUST NOT contain Parse Info Headers with a Parse Code other than 0x00 (Sequence Header), 0x10 (End of Sequence), 0x20 (Auxiliary Data), 0x30 (Padding Data), or 0xEC (High Quality Picture Fragment). Some other Streams MAY be convertible to meet this restriction (see below).
  • Every High Quality Picture Fragment MUST be no longer than 65535 bytes. This can usually be ensured by splitting large Fragments into several smaller Fragments, except in the case where an individual slice is too large, in which case see the notes below on conversion.
  • Informative note: this requirement ensures that every High Quality Picture Fragment will always contain no more than 65535 slices.
  • Every High Quality Picture Fragment SHOULD be small enough that the RTP packet carrying it will fit within the network MTU size. This can usually be ensured by splitting large Fragments into several smaller Fragments, except in the case where an individual slice is too large, in which case see the notes below on conversion.
  • Every High Quality Picture Fragment MUST be encoded using values for Slice Prefix Bytes and Slice Size Scaler no greater than 65535.
  • シーケンスは、0x00（シーケンスヘッダー）、0x10（シーケンス終了）、0x20（補助データ）、0x30（パディングデータ）、0xEC（High Quality Picture Fragment）以外のパースコードを持つパース情報ヘッダーを含んではなりません（MUST NOT）。その他のストリームの中には、この制限を満たすように変換できるものがある場合があります（MAY）（後述）。
  • すべてのHigh Quality Picture Fragmentは、65535バイト以下でなければなりません（MUST）。これは通常、大きなフラグメントを複数の小さなフラグメントに分割することで確保できます。ただし、個々のスライスが大きすぎる場合は例外です。その場合は、後述の変換に関する注記を参照してください。
  • 参考情報としての注記：この要件により、すべてのHigh Quality Picture Fragmentに含まれるスライスは常に65535個以下になります。
  • すべてのHigh Quality Picture Fragmentは、それを運ぶRTPパケットがネットワークのMTUサイズに収まるほど小さいべきです（SHOULD）。これは通常、大きなフラグメントを複数の小さなフラグメントに分割することで確保できます。ただし、個々のスライスが大きすぎる場合は例外です。その場合は、後述の変換に関する注記を参照してください。
  • すべてのHigh Quality Picture Fragmentは、Slice Prefix BytesとSlice Size Scalerに65535以下の値を使用して符号化しなければなりません（MUST）。

If a Sequence intended for transmission does not conform to these restrictions, then it MAY be possible to simply convert it into a form that does by splitting pictures and/or large Fragments into suitably sized Fragments. This can be done provided that the following (weaker) constraints are met:

送信しようとするシーケンスがこれらの制限に従っていない場合でも、ピクチャーや大きなフラグメントを適切なサイズのフラグメントに分割することで、制限に従う形式に簡単に変換できる場合があります（MAY）。これは、次の（より弱い）制約が満たされていれば可能です。

  • The Sequence does not contain Parse Info Headers with a Parse Code other than 0x00 (Sequence Header), 0x10 (End of Sequence), 0x20 (Auxiliary Data), 0x30 (Padding Data), 0xE8 (High Quality Picture), or 0xEC (High Quality Picture Fragment).
  • None of the High Quality Pictures or High Quality Picture Fragments contain slices that are individually longer than 65535 bytes. Note: When this is the case, the values of Slice Prefix Bytes and Slice Size Scaler will necessarily also be smaller than 65535.
  • None of the High Quality Pictures or High Quality Picture Fragments contain slices that are individually so large that an RTP packet carrying a Fragment containing that single slice will fit within the network MTU size.
  • シーケンスが、0x00（シーケンスヘッダー）、0x10（シーケンス終了）、0x20（補助データ）、0x30（パディングデータ）、0xE8（High Quality Picture）、0xEC（High Quality Picture Fragment）以外のパースコードを持つパース情報ヘッダーを含んでいないこと。
  • どのHigh Quality PictureやHigh Quality Picture Fragmentも、個々の長さが65535バイトを超えるスライスを含んでいないこと。注：この場合、Slice Prefix BytesとSlice Size Scalerの値も必然的に65535より小さくなります。
  • どのHigh Quality PictureやHigh Quality Picture Fragmentも、その単一のスライスを含むフラグメントを運ぶRTPパケットがネットワークのMTUサイズに収まるほど大きなスライスを含んでいないこと。

It is not possible to send a Stream that does not meet the above requirements via this mechanism unless the Stream is re-encoded by a VC-2 Encoder so as to meet them.

上記の要件を満たさないストリームは、それを満たすようにVC-2エンコーダーで再符号化しない限り、この仕組みで送信することはできません。

In addition, every Auxiliary Data Unit SHOULD be small enough that a single RTP packet carrying it will fit within the network MTU size. Since there is currently no specification for the format of Auxiliary Data in VC-2, the mechanism for ensuring this with an encoder implementation that includes Auxiliary Data Units will be dependent upon the implementation's use for them.

さらに、すべての補助データユニットは、それを運ぶ単一のRTPパケットがネットワークのMTUサイズに収まるほど小さいべきです（SHOULD）。現在VC-2には補助データの形式に関する仕様がないため、補助データユニットを含むエンコーダー実装でこれを確保する仕組みは、その実装における補助データの用途に依存することになります。

When encoding VC-2 video intended to be transported via RTP, a VC-2 profile and level that ensures these requirements are met SHOULD be used.

RTPで転送することを意図したVC-2ビデオを符号化する場合は、これらの要件が満たされることを保証するVC-2のプロファイルとレベルを使用すべきです（SHOULD）。

4.5. Payload Data

4.5. ペイロードデータ

For the Sequence Header packet type (PC = 0x00), the payload data MUST be the coded Sequence Header exactly as it appears in the VC-2 Sequence.

シーケンスヘッダーのパケットタイプ（PC = 0x00）では、ペイロードデータは、VC-2シーケンスに出現するとおりの符号化されたシーケンスヘッダーそのものでなければなりません（MUST）。

For the Transform Parameters packet type (PC = 0xEC and No. of Slices = 0), the payload data MUST be the variable-length coded Transform Parameters. This MUST NOT include the Fragment header (since all data in the picture header is already included in the packet header).

変換パラメーターのパケットタイプ（PC = 0xECかつNo. of Slices = 0）では、ペイロードデータは、可変長符号化された変換パラメーターでなければなりません（MUST）。これにはフラグメントヘッダーを含めてはなりません（MUST NOT）（ピクチャーヘッダー内のすべてのデータは、すでにパケットヘッダーに含まれているためです）。

For the Auxiliary Data packet type (PC = 0x20), the payload data MUST be a portion of the auxiliary data bytes contained in the Auxiliary Data Unit being transmitted. The B flag MUST be set on the packet that contains the first byte, the E flag MUST be set on the packet that contains the last byte, the bytes MUST be included in order, and the packets MUST have contiguous sequence numbers.

補助データのパケットタイプ（PC = 0x20）では、ペイロードデータは、送信される補助データユニットに含まれる補助データのバイトの一部でなければなりません（MUST）。最初のバイトを含むパケットにはBフラグを設定しなければなりません（MUST）。最後のバイトを含むパケットにはEフラグを設定しなければなりません（MUST）。バイトは順番どおりに含めなければなりません（MUST）。また、パケットは連続したシーケンス番号を持たなければなりません（MUST）。

For the Picture Fragment packet type (PC = 0xEC and No. of Slices > 0), the payload data MUST be a specified number of Coded Slices in the same order that they appear in the VC-2 Stream. Which slices appear in the packet is identified using the Slice Offset X and Slice Offset Y fields in the payload header.

ピクチャーフラグメントのパケットタイプ（PC = 0xECかつNo. of Slices > 0）では、ペイロードデータは、VC-2ストリームに出現するのと同じ順序で並んだ、指定された数の符号化スライスでなければなりません（MUST）。どのスライスがパケットに含まれるかは、ペイロードヘッダーのSlice Offset XフィールドとSlice Offset Yフィールドを使用して識別します。

For the End of Sequence packet type (PC = 0x10), there is no payload data.

シーケンス終了のパケットタイプ（PC = 0x10）には、ペイロードデータはありません。

4.5.1. Reassembling the Data

4.5.1. データの再構築

To reassemble the data in the RTP packets into a valid VC-2 Sequence:

RTPパケット内のデータを有効なVC-2シーケンスに再構築するには、次のようにします。

  • The receiver SHOULD take the data from each packet with a Parse Code of 0x00 and prepend a valid VC-2 Parse Info Header (Figure 8) with the same Parse Code (0x00). The resulting Sequence Header Parse Info Header and Data Unit MUST be included in the output stream before any coded pictures that followed the packet being processed in the RTP stream, unless an identical Sequence Header has already been included, and they MAY be repeated (with appropriate modifications to the next and previous header offsets) at any point that results in a valid VC-2 Stream.
  • The receiver SHOULD take the data from each packet with a Parse Code of 0xEC and No. of Slices set to 0 (which together indicate that this packet contains the Transform Parameters for a coded picture) and prepend with the same Parse Code a valid VC-2 Parse Info Header (Figure 8) followed by the picture number, Fragment data length, and slice count (0).
  • The receiver SHOULD take the data from each packet with a Parse Code of 0xEC and No. of Slices not set to 0 (which together indicate that this packet contains Coded Slices) and prepend with the same Parse Code a valid VC-2 Parse Info Header (Figure 8) followed by the picture number, Fragment data length, slice count, x offset and y offset taken from the packet header.
  • A receiver MAY combine all Fragment Data Units (with Parse Code 0xEC) and the same picture number into a single picture Data Unit with Parse Code 0xE8. If the Stream is required to comply with major versions 1 or 2 of the VC-2 specification, then this MUST be done.
  • The receiver SHOULD take the data from each packet with a Parse Code of 0x20 and the B bit set and prepend a valid VC-2 Parse Info Header (Figure 8) with the Parse Code 0x20, and then take each subsequent packet with Parse Code 0x20 without the B bit set and append its payload to the growing Data Unit. When all packets for a particular Data Unit have been received, it SHOULD be included in the output stream. The final packet for a Data Unit will have the E bit set.
  • Once a Data Unit has been assembled, whether a Sequence Header, Coded Picture Fragment, Coded Picture, or Auxiliary Data Unit, the next parse offset and previous parse offset values in its Parse Info Header SHOULD be filled with the offset between the start of the header and the start of the next or previous header.
  • An End of Sequence Parse Info Header MAY be inserted when a packet with Parse Code set to 0x10 is encountered, or at any other time that is allowed in a valid VC-2 Stream. After an End of Sequence Parse Info Header is included in the output stream, either the Stream must end, or it MUST be followed by a Sequence Header indicating the start of a new Sequence. The next parse offset of the End of Sequence header MUST be set to 0, and the previous parse offset SHOULD be filled with the offset from the start of the previous Parse Info Header in the Stream.
  • A Padding Data Parse Info Header MAY be inserted when a packet with Parse Code set to 0x30 and the B bit set is encountered, or at any other time that is allowed in a valid VC-2 Stream. The length of the accompanying Data Unit MAY have any value, and its contents MUST be set to a series of zero bytes. The next parse offset and previous parse offset values in its Parse Info Header SHOULD be filled with the offset between the start of the header and the start of the next or previous header.
  • 受信者は、パースコードが0x00の各パケットからデータを取り出し、その前に同じパースコード（0x00）を持つ有効なVC-2パース情報ヘッダー（図8）を付加すべきです（SHOULD）。その結果得られるシーケンスヘッダーのパース情報ヘッダーとデータユニットは、同一のシーケンスヘッダーがすでに含まれている場合を除き、RTPストリーム内で処理中のパケットの後に続いていた符号化ピクチャーよりも前に、出力ストリームに含めなければなりません（MUST）。また、これらは、有効なVC-2ストリームとなる任意の位置で（次および前のヘッダーオフセットを適切に修正した上で）繰り返してもよいです（MAY）。
  • 受信者は、パースコードが0xECでNo. of Slicesが0に設定された（この2つの組み合わせは、このパケットが符号化ピクチャーの変換パラメーターを含むことを示します）各パケットからデータを取り出し、その前に、同じパースコードを持つ有効なVC-2パース情報ヘッダー（図8）と、それに続くピクチャー番号、フラグメントのデータ長、スライス数（0）を付加すべきです（SHOULD）。
  • 受信者は、パースコードが0xECでNo. of Slicesが0以外に設定された（この2つの組み合わせは、このパケットが符号化スライスを含むことを示します）各パケットからデータを取り出し、その前に、同じパースコードを持つ有効なVC-2パース情報ヘッダー（図8）と、それに続く、パケットヘッダーから取得したピクチャー番号、フラグメントのデータ長、スライス数、xオフセット、yオフセットを付加すべきです（SHOULD）。
  • 受信者は、（パースコード0xECを持ち）同じピクチャー番号を持つすべてのフラグメントデータユニットを、パースコード0xE8を持つ単一のピクチャーデータユニットに結合してもよいです（MAY）。ストリームがVC-2仕様のメジャーバージョン1または2に準拠する必要がある場合は、これを行わなければなりません（MUST）。
  • 受信者は、パースコードが0x20でBビットが設定された各パケットからデータを取り出し、その前にパースコード0x20を持つ有効なVC-2パース情報ヘッダー（図8）を付加し、その後、パースコードが0x20でBビットが設定されていない後続の各パケットを取り出して、そのペイロードを構築中のデータユニットに追加すべきです（SHOULD）。特定のデータユニットのすべてのパケットを受信したら、そのデータユニットを出力ストリームに含めるべきです（SHOULD）。データユニットの最後のパケットには、Eビットが設定されています。
  • データユニットが組み立てられたら、それがシーケンスヘッダー、符号化ピクチャーフラグメント、符号化ピクチャー、補助データユニットのいずれであっても、そのパース情報ヘッダー内の次のパースオフセットと前のパースオフセットの値には、そのヘッダーの先頭から次または前のヘッダーの先頭までのオフセットを設定すべきです（SHOULD）。
  • パースコードが0x10に設定されたパケットに遭遇したとき、または有効なVC-2ストリームで許可されているその他の任意の時点で、シーケンス終了のパース情報ヘッダーを挿入してもよいです（MAY）。シーケンス終了のパース情報ヘッダーを出力ストリームに含めた後は、ストリームを終了するか、新しいシーケンスの開始を示すシーケンスヘッダーを続けなければなりません（MUST）。シーケンス終了ヘッダーの次のパースオフセットは0に設定しなければなりません（MUST）。前のパースオフセットには、ストリーム内の前のパース情報ヘッダーの先頭からのオフセットを設定すべきです（SHOULD）。
  • パースコードが0x30に設定されBビットが設定されたパケットに遭遇したとき、または有効なVC-2ストリームで許可されているその他の任意の時点で、パディングデータのパース情報ヘッダーを挿入してもよいです（MAY）。付随するデータユニットの長さは任意の値でよいです（MAY）。その内容はゼロバイトの並びに設定しなければなりません（MUST）。そのパース情報ヘッダー内の次のパースオフセットと前のパースオフセットの値には、そのヘッダーの先頭から次または前のヘッダーの先頭までのオフセットを設定すべきです（SHOULD）。

5. Forward Error Correction (FEC) Considerations

5. 前方誤り訂正（FEC）に関する考慮事項

VC-2 provides no underlying protection against data loss, so it may be useful to employ Forward Error Correction to the Stream. A mechanism for doing this to a generic RTP stream is specified in RFC 5109 [RFC5109]. If making use of this mechanism to provide multilevel protection, then the packets SHOULD be assigned to layers based upon their packet type, with the packet types being, in order of importance:

VC-2はデータ損失に対する基本的な保護を何も提供しないため、ストリームに前方誤り訂正（Forward Error Correction）を適用すると役立つ場合があります。一般的なRTPストリームにこれを適用する仕組みは、RFC 5109 [RFC5109]で規定されています。この仕組みを利用して多段階の保護を提供する場合、パケットはそのパケットタイプに基づいてレイヤーに割り当てるべきです（SHOULD）。パケットタイプを重要度の高い順に並べると、次のようになります。

  1. Sequence Headers
  2. Fragments containing Transform Parameters
  3. Fragments containing Coded Slices
  4. Auxiliary Data and end of Sequence
  5. Padding
  1. シーケンスヘッダー
  2. 変換パラメーターを含むフラグメント
  3. 符号化スライスを含むフラグメント
  4. 補助データとシーケンス終了
  5. パディング

It is RECOMMENDED that if multilevel protection is to be used, then one layer will protect all Sequence Header packets, and a second will protect Sequence Headers and all Fragments. If desired, a third layer MAY protect Auxiliary Data and End of Sequence packets. Padding data SHOULD NOT be protected by FEC.

多段階の保護を使用する場合は、1つ目のレイヤーですべてのシーケンスヘッダーパケットを保護し、2つ目のレイヤーでシーケンスヘッダーとすべてのフラグメントを保護することが推奨されます（RECOMMENDED）。必要に応じて、3つ目のレイヤーで補助データとシーケンス終了のパケットを保護してもよいです（MAY）。パディングデータはFECで保護すべきではありません（SHOULD NOT）。

6. Congestion Control Considerations

6. 輻輳制御に関する考慮事項

Congestion control for RTP SHALL be used in accordance with RFC 3550 [RFC3550] and any applicable RTP profile -- e.g., RFC 3551 [RFC3551]. An additional requirement if best-effort service is being used is: users of this payload format MUST monitor packet loss to ensure that the packet loss rate is within acceptable parameters. Circuit Breakers [RFC8083] are an update to RTP [RFC3550] that defines criteria for when one is required to stop sending RTP Packet Streams, and applications implementing this standard MUST comply with it. RFC 8085 [RFC8085] provides additional information on the best practices for applying congestion control to UDP streams.

RTPの輻輳制御は、RFC 3550 [RFC3550]、および適用可能なRTPプロファイル（たとえばRFC 3551 [RFC3551]）に従って使用するものとすることになります（SHALL）。ベストエフォートのサービスを使用する場合の追加の要件として、このペイロード形式の利用者は、パケット損失率が許容可能な範囲内にあることを確かめるために、パケット損失を監視しなければなりません（MUST）。サーキットブレーカー（Circuit Breakers）[RFC8083]はRTP [RFC3550]の更新であり、RTPパケットストリームの送信を停止しなければならない場合の基準を定義しています。この標準を実装するアプリケーションは、それに準拠しなければなりません（MUST）。RFC 8085 [RFC8085]は、UDPストリームに輻輳制御を適用するためのベストプラクティスに関する追加情報を提供しています。

In particular, it should be noted that the expected data rate for RTP sessions that use this profile is likely to be in the range of gigabits per second. If used on a closed network that has been correctly provisioned for the expected data rates, this might not pose a problem, but there is always the risk of data getting out onto the open internet.

特に、このプロファイルを使用するRTPセッションで想定されるデータレートは、毎秒ギガビットの範囲になる可能性が高いことに注意すべきです。想定されるデータレートに合わせて正しく設計・準備された閉じたネットワークで使用する場合は問題にならないかもしれませんが、データが開かれたインターネットに流出するリスクは常に存在します。

7.2. Mapping to the Session Description Protocol (SDP)

7.2. セッション記述プロトコル（SDP）へのマッピング

The mapping of the above-defined payload format media type and its parameters SHALL be done according to Section 3 of RFC 4855 [RFC4855].

上記で定義したペイロード形式のメディアタイプとそのパラメーターのマッピングは、RFC 4855 [RFC4855]のセクション3に従って行うものとすることになります（SHALL）。

  • The type name ("video") goes in SDP "m=" as the media name.
  • The subtype name ("vc2") goes in SDP "a=rtpmap" as the encoding name, followed by a slash ("/") and the rate parameter.
  • The required parameter profile and the optional parameters version and level, when present, are included in the "a=fmtp" attribute line of SDP as a semicolon-separated list of parameter=value pairs.
  • タイプ名（"video"）は、メディア名としてSDPの"m="に入ります。
  • サブタイプ名（"vc2"）は、エンコーディング名としてSDPの"a=rtpmap"に入り、その後にスラッシュ（"/"）とrateパラメーターが続きます。
  • 必須パラメーターであるprofileと、省略可能なパラメーターであるversionとlevelは、存在する場合、parameter=valueの組をセミコロンで区切ったリストとして、SDPの"a=fmtp"属性行に含めます。

Version and level SHALL be specified in decimal when present.

versionとlevelは、存在する場合、10進数で指定するものとすることになります（SHALL）。

For example, a sample SDP mapping for VC-2 could be as follows:

たとえば、VC-2のSDPマッピングの例は次のようになります。

          m=video 30000 RTP/AVP 112
          a=rtpmap:112 vc2/90000
          a=fmtp:112 profile=HQ;version=3;level=0

          m=video 30000 RTP/AVP 112
          a=rtpmap:112 vc2/90000
          a=fmtp:112 profile=HQ;version=3;level=0

In this example, a dynamic payload type 112 is used for vc-2 data. The 90 kHz RTP timestamp rate is specified in the "a=rtpmap" line after the subtype. In the "a=fmtp:" line, profile HQ, version 3, and level 0 (unknown or non-standard level) are specified.

この例では、VC-2データに動的ペイロードタイプ112を使用しています。90kHzのRTPタイムスタンプレートは、"a=rtpmap"行のサブタイプの後で指定しています。"a=fmtp:"行では、profile HQ、version 3、level 0（不明または非標準のレベル）を指定しています。

9. Security Considerations

9. セキュリティーに関する考慮事項

RTP packets using the payload format defined in this specification are subject to the security considerations discussed in the RTP specification [RFC3550] and any applicable RTP profile such as RTP/AVP [RFC3551], RTP/AVPF [RFC4585], RTP/SAVP [RFC3711], or RTP/SAVPF [RFC5124]. However, as "Securing the RTP Framework: Why RTP Does Not Mandate a Single Media Security Solution" [RFC7202] discusses, it is not an RTP payload format's responsibility to discuss or mandate what solutions are used to meet the basic security goals like confidentiality, integrity, and source authenticity for RTP in general. This responsibility lies with anyone using RTP in an application. They can find guidance on available security mechanisms and important considerations in "Options for Securing RTP Sessions" [RFC7201]. Applications SHOULD use one or more appropriate strong security mechanisms. The rest of this section discusses the security-impacting properties of the payload format itself.

この仕様で定義するペイロード形式を使用するRTPパケットは、RTP仕様[RFC3550]、およびRTP/AVP [RFC3551]、RTP/AVPF [RFC4585]、RTP/SAVP [RFC3711]、RTP/SAVPF [RFC5124]などの適用可能なRTPプロファイルで議論されているセキュリティーに関する考慮事項の対象となります。しかし、"Securing the RTP Framework: Why RTP Does Not Mandate a Single Media Security Solution" [RFC7202]で議論されているように、RTP全般について、機密性、完全性、送信元の真正性といった基本的なセキュリティー目標を満たすためにどのような解決策を使用するかを議論したり義務付けたりするのは、RTPペイロード形式の責任ではありません。この責任は、アプリケーションでRTPを使用するすべての者にあります。利用可能なセキュリティーメカニズムと重要な考慮事項に関するガイダンスは、"Options for Securing RTP Sessions" [RFC7201]にあります。アプリケーションは、1つ以上の適切な強いセキュリティーメカニズムを使用すべきです（SHOULD）。このセクションの残りの部分では、ペイロード形式自体のセキュリティーに影響する特性について説明します。

This RTP payload format and its media decoder do not exhibit any significant non-uniformity in the receiver-side computational complexity for packet processing and thus are unlikely to pose a denial-of-service threat due to the receipt of pathological data. Nor does the RTP payload format contain any active content.

このRTPペイロード形式とそのメディアデコーダーは、パケット処理における受信側の計算の複雑さに大きな不均一性を示さないため、異常なデータの受信によってサービス拒否の脅威をもたらす可能性は低いと考えられます。また、このRTPペイロード形式はアクティブコンテンツを一切含みません。

To avoid buffer overruns when processing these packets, the receiver MUST consider both the reported Fragment length and the actual received size of a packet containing slice data.

これらのパケットを処理する際のバッファーオーバーランを避けるために、受信者は、スライスデータを含むパケットについて、通知されたフラグメント長と実際に受信したサイズの両方を考慮しなければなりません（MUST）。

In some cases, the transmitter may need to decode variable-length coded headers in order to extract some data from the VC-2 bitstream before assembling packets. This process is potentially subject to buffer overruns if not implemented carefully.

場合によっては、送信者がパケットを組み立てる前にVC-2ビットストリームからデータを取り出すために、可変長符号化されたヘッダーを復号する必要があるかもしれません。この処理は、注意深く実装しないとバッファーオーバーランの影響を受ける可能性があります。
