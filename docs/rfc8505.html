RFC 8505

Registration Extensions for IPv6 over Low-Power Wireless Personal Area Network (6LoWPAN) Neighbor Discovery

RFC 8505

低電力無線パーソナルエリアネットワーク上のIPv6（6LoWPAN）の近隣探索のための登録の拡張

Abstract

概要

This specification updates RFC 6775 -- the Low-Power Wireless Personal Area Network (6LoWPAN) Neighbor Discovery specification -- to clarify the role of the protocol as a registration technique and simplify the registration operation in 6LoWPAN routers, as well as to provide enhancements to the registration capabilities and mobility detection for different network topologies, including the Routing Registrars performing routing for host routes and/or proxy Neighbor Discovery in a low-power network.

この仕様は、低電力無線パーソナルエリアネットワーク上のIPv6（6LoWPAN）の近隣探索の仕様であるRFC 6775を更新します。その目的は、登録手法としてのプロトコルの役割を明確にし、6LoWPANルーターにおける登録操作を単純化すること、およびさまざまなネットワークトポロジー（低電力ネットワークにおいてホストルートのルーティングやプロキシー近隣探索、またはその両方を実行するルーティングレジストラーを含む）に対して、登録の機能と移動検出を強化することです。

1. Introduction

1. はじめに

IPv6 Low-Power and Lossy Networks (LLNs) support star and mesh topologies. For such networks, "Neighbor Discovery Optimization for IPv6 over Low-Power Wireless Personal Area Networks (6LoWPANs)" [RFC6775] (also referred to as "6LoWPAN Neighbor Discovery (ND)") defines a registration mechanism and a central IPv6 ND Registrar to ensure unique addresses. The 6LoWPAN ND mechanism reduces the dependency of the IPv6 ND protocol [RFC4861] [RFC4862] on network-layer multicast and link-layer broadcast operations.

IPv6の低電力・高損失ネットワーク（Low-Power and Lossy Network、LLN）は、スター型とメッシュ型のトポロジーをサポートします。そのようなネットワークのために、「Neighbor Discovery Optimization for IPv6 over Low-Power Wireless Personal Area Networks (6LoWPANs)」[RFC6775]（「6LoWPAN近隣探索（ND）」とも呼ばれます）は、アドレスの一意性を保証するための登録メカニズムと中央のIPv6 NDレジストラーを定義しています。6LoWPAN NDのメカニズムは、IPv6 NDプロトコル[RFC4861] [RFC4862]がネットワーク層のマルチキャストとリンク層のブロードキャストの操作に依存する度合いを減らします。

This specification updates 6LoWPAN ND [RFC6775] to simplify and generalize registration in 6LoWPAN Routers (6LRs). In particular, this specification modifies and extends the behavior and protocol elements of 6LoWPAN ND to enable the following actions:

この仕様は、6LoWPANルーター（6LR）での登録を単純化・一般化するために、6LoWPAN ND [RFC6775]を更新します。特に、この仕様は、次の動作を可能にするために、6LoWPAN NDの振る舞いとプロトコル要素を変更・拡張します。

  • Determining the most recent location in the case of node mobility
  • Simplifying the registration flow for Link-Local Addresses
  • Support for a routing-unaware leaf node in a route-over network
  • Proxy registration in a route-over network
  • Enabling verification for the registration, using the Registration Ownership Verifier (ROVR) (Section 5.3)
  • Registration to an IPv6 ND proxy (e.g., a Routing Registrar)
  • Better support for privacy and temporary addresses
  • ノードが移動する場合に、最新の位置を判断すること
  • リンクローカルアドレスの登録フローを単純化すること
  • ルートオーバーネットワークにおいて、ルーティングを認識しないリーフノードをサポートすること
  • ルートオーバーネットワークにおけるプロキシー登録
  • 登録所有権検証子（Registration Ownership Verifier、ROVR）（Section 5.3）を使用して、登録の検証を可能にすること
  • IPv6 NDプロキシー（たとえば、ルーティングレジストラー）への登録
  • プライバシーアドレスと一時アドレスのより良いサポート

These features satisfy the requirements listed in Appendix B.

これらの機能は、Appendix Bに列挙されている要件を満たします。

3. Applicability of Address Registration Options

3. アドレス登録オプションの適用範囲

The ARO as described in [RFC6775] facilitates DAD for hosts and populates NCEs [RFC4861] in the routers. This reduces the reliance on multicast operations, which are often as intrusive as broadcast, in IPv6 ND operations (see [Multicast-over-IEEE802-Wireless]).

[RFC6775]で説明されているAROは、ホストのDADを容易にし、ルーター内のNCE [RFC4861]を設定します。これにより、IPv6 NDの操作において、しばしばブロードキャストと同程度に負担の大きいマルチキャスト操作への依存が減ります（[Multicast-over-IEEE802-Wireless]を参照）。

This document specifies new status codes for registrations rejected by a 6LR or 6LBR for reasons other than address duplication. Examples include:

この文書は、6LRまたは6LBRがアドレスの重複以外の理由で拒否した登録のための新しいステータスコードを規定します。例としては次のものがあります。

  • the router running out of space.
  • a registration bearing a stale sequence number. This could happen if the host moves after the registration was placed.
  • a host misbehaving and attempting to register an invalid address, such as the unspecified address as defined in [RFC4291].
  • a host using an address that is not topologically correct on that link.
  • ルーターの空き容量が不足した場合。
  • 古いシーケンス番号を持つ登録の場合。これは、登録が行われた後にホストが移動した場合に起こる可能性があります。
  • ホストが誤動作して、[RFC4291]で定義されている未指定アドレスのような無効なアドレスを登録しようとした場合。
  • ホストが、そのリンク上でトポロジー的に正しくないアドレスを使用している場合。

In such cases, the host will receive an error that will help diagnose the issue; the host may retry -- possibly with a different address or possibly registering to a different router -- depending on the returned error. The ability to return errors to address registrations is not intended to be used to restrict the ability of hosts to form and use multiple addresses. Each host may form and register a number of addresses for enhanced privacy, using mechanisms such as those described in [RFC4941] ("Privacy Extensions for Stateless Address Autoconfiguration in IPv6"), e.g., Stateless Address Autoconfiguration (SLAAC), and SHOULD conform to [RFC7934] ("Host Address Availability Recommendations").

そのような場合、ホストは問題の診断に役立つエラーを受け取ります。ホストは、返されたエラーに応じて、（場合によっては別のアドレスで、または別のルーターに登録して）再試行することがあります。アドレス登録に対してエラーを返す能力は、ホストが複数のアドレスを形成して使用する能力を制限するために使用することを意図したものではありません。各ホストは、プライバシーを強化するために、[RFC4941]（「Privacy Extensions for Stateless Address Autoconfiguration in IPv6」）で説明されているようなメカニズム、たとえばステートレスアドレス自動設定（Stateless Address Autoconfiguration、SLAAC）を使用して、多数のアドレスを形成して登録してもかまいません。また、[RFC7934]（「Host Address Availability Recommendations」）に準拠すべきです（SHOULD）。

As indicated in IPv6 ND [RFC4861], a router needs enough storage to hold NCEs for all directly connected addresses to which it is currently forwarding packets (unused entries may be flushed). In contrast, a router serving the address-registration mechanism needs enough storage to hold NCEs for all the addresses that may be registered to it, regardless of whether or not they are actively communicating. The number of registrations supported by a 6LR or 6LBR MUST be clearly documented by the vendor, and the dynamic use of associated resources SHOULD be made available to the network operator, e.g., to a management console. Network administrators need to ensure that 6LRs/6LBRs in their network support the number and types of devices that can register to them, based on the number of IPv6 Addresses that those devices require, as well as their address renewal rate and behavior.

IPv6 ND [RFC4861]に示されているように、ルーターには、現在パケットを転送している直接接続されたすべてのアドレスについてNCEを保持するのに十分な記憶領域が必要です（使用されていないエントリーはフラッシュされることがあります）。これに対して、アドレス登録メカニズムを提供するルーターには、実際に通信しているかどうかにかかわらず、自身に登録される可能性のあるすべてのアドレスについてNCEを保持するのに十分な記憶領域が必要です。6LRまたは6LBRがサポートする登録数は、ベンダーによって明確に文書化されなければなりません（MUST）。また、関連するリソースの動的な使用状況は、ネットワーク運用者が（たとえば管理コンソールで）利用できるようにするべきです（SHOULD）。ネットワーク管理者は、自身のネットワーク内の6LR/6LBRが、それらに登録できるデバイスの数と種類をサポートできることを、それらのデバイスが必要とするIPv6アドレスの数や、アドレス更新の頻度と振る舞いに基づいて確認する必要があります。

The EARO (see Section 4.1) updates the ARO used within NS and NA messages between a 6LN and a 6LR. 5.1. Extending the Address Registration Option

5.1. アドレス登録オプションの拡張

The EARO updates the ARO and is backward compatible with the ARO if and only if the Length value of the option is set to 2. The format of the EARO is presented in Section 4.1. More details on backward compatibility can be found in Section 6.

EAROはAROを更新するものであり、オプションのLength値が2に設定されている場合に限り、AROと後方互換性があります。EAROのフォーマットはSection 4.1で示しています。後方互換性の詳細はSection 6にあります。

The NS message and the ARO are modified as follows:

NSメッセージとAROは、次のように変更されます。

  • The Target Address field in the NS containing the EARO is now the field that indicates the address that is being registered, as opposed to the Source Address field in the NS as specified in [RFC6775] (see Section 5.5). This change enables a 6LBR to send a proxy registration for a 6LN's address to a Routing Registrar and in most cases also avoids the use of an address as the Source Address before it is registered.
  • The EUI-64 field in the ARO is renamed "Registration Ownership Verifier (ROVR)" and is not required to be derived from a MAC address (see Section 5.3).
  • The option's Length value MAY be different than 2 and take a value between 3 and 5, in which case the EARO is not backward compatible with an ARO. The increase in size corresponds to a larger ROVR field, so the size of the ROVR is inferred from the option's Length value.
  • A new Opaque field is introduced to carry opaque information in cases where the registration is relayed to another process, e.g., to be advertised by a routing protocol. A new "I" field provides a type for the opaque information and indicates the other process to which the 6LN passes the opaque value. A value of 0 for the "I" field indicates topological information to be passed to a routing process if the registration is redistributed. In that case, a value of 0 for the Opaque field (1) is backward compatible with the reserved fields that are overloaded and (2) indicates that the default topology is to be used.
  • This document specifies a new flag in the EARO: the R flag. If the R flag is set, the Registering Node requests that the 6LR ensure reachability for the Registered Address, e.g., by means of routing or proxy ND. Conversely, when it is not set, the R flag indicates that the Registering Node is a router and that it will advertise reachability to the Registered Address via a routing protocol (such as RPL [RFC6550]).
  • A node that supports this specification MUST provide a TID field in the EARO and set the T flag to indicate the presence of the TID (see Section 5.2).
  • Finally, this specification introduces new status codes to help diagnose the cause of a registration failure (see Table 1).
  • EAROを含むNSのターゲットアドレスフィールドが、[RFC6775]で規定されているNSの送信元アドレスフィールドに代わって、登録されるアドレスを示すフィールドになります（Section 5.5を参照）。この変更により、6LBRは6LNのアドレスの代理登録をルーティングレジストラーに送信できるようになり、またほとんどの場合、登録される前のアドレスを送信元アドレスとして使用することも避けられます。
  • AROのEUI-64フィールドは「登録所有権検証子（Registration Ownership Verifier、ROVR）」と改名され、MACアドレスから導出する必要はなくなります（Section 5.3を参照）。
  • オプションのLength値は、2とは異なる3から5までの値をとってもよいです（MAY）。その場合、EAROはAROと後方互換性がありません。サイズの増加はより大きなROVRフィールドに対応しているため、ROVRのサイズはオプションのLength値から推測されます。
  • 登録が別のプロセスに中継される場合（たとえば、ルーティングプロトコルによって広告される場合）に不透明な情報を運ぶために、新しいOpaqueフィールドが導入されます。新しい「I」フィールドは、不透明な情報の種類を提供し、6LNが不透明な値を渡す先の別のプロセスを示します。「I」フィールドの値0は、登録が再配布される場合にルーティングプロセスに渡されるトポロジー情報を示します。その場合、Opaqueフィールドの値0は、(1) 多重利用される予約フィールドと後方互換性があり、(2) デフォルトのトポロジーを使用することを示します。
  • この文書は、EAROの新しいフラグとしてRフラグを規定します。Rフラグが設定されている場合、登録者ノードは、たとえばルーティングやプロキシーNDによって、登録アドレスへの到達可能性を確保するよう6LRに要求します。逆に、設定されていない場合、Rフラグは、登録者ノードがルーターであり、ルーティングプロトコル（RPL [RFC6550]など）を介して登録アドレスへの到達可能性を広告することを示します。
  • この仕様をサポートするノードは、EAROにTIDフィールドを提供し、TIDの存在を示すためにTフラグを設定しなければなりません（MUST）（Section 5.2を参照）。
  • 最後に、この仕様は、登録失敗の原因の診断に役立つ新しいステータスコードを導入します（Table 1を参照）。

When registering, a 6LN that acts only as a host MUST set the R flag to indicate that it is not a router and that it will not handle its own reachability. A 6LR that manages its reachability SHOULD NOT set the R flag; if it does, routes towards this router may be installed on its behalf and may interfere with those it advertises.

登録の際、ホストとしてのみ動作する6LNは、自身がルーターではなく、自身の到達可能性を扱わないことを示すために、Rフラグを設定しなければなりません（MUST）。自身の到達可能性を管理する6LRは、Rフラグを設定すべきではありません（SHOULD NOT）。設定した場合、このルーターに向かう経路がこのルーターに代わってインストールされ、このルーターが広告する経路と干渉する可能性があります。

5.2. Transaction ID

5.2. トランザクションID

The TID is a sequence number that is incremented by the 6LN with each re-registration to a 6LR. The TID is used to determine the recency of the registration request. The network uses the most recent TID to determine the most recent known location(s) of a moving 6LN. When a Registered Node is registered with multiple 6LRs in parallel, the same TID MUST be used. This enables the 6LBRs and/or Routing Registrars to determine whether the registrations are identical and to distinguish that situation from a movement (for example, see Section 5.7 and Appendix A).

TIDは、6LRへの再登録ごとに6LNによってインクリメントされるシーケンス番号です。TIDは、登録要求の新しさを判断するために使用されます。ネットワークは、移動する6LNの既知の最新の位置（複数の場合もあります）を判断するために、最新のTIDを使用します。登録ノードが複数の6LRに並行して登録される場合、同じTIDを使用しなければなりません（MUST）。これにより、6LBRやルーティングレジストラーは、それらの登録が同一のものかどうかを判断し、その状況を移動と区別できます（たとえば、Section 5.7とAppendix Aを参照）。

5.2.1. Comparing TID Values

5.2.1. TIDの値の比較

The operation of the TID is fully compatible with that of the RPL Path Sequence counter as described in Section 7.2 of [RFC6550] ("RPL: IPv6 Routing Protocol for Low-Power and Lossy Networks").

TIDの動作は、[RFC6550]のSection 7.2（「RPL: IPv6 Routing Protocol for Low-Power and Lossy Networks」）で説明されているRPLのパスシーケンス（Path Sequence）カウンターの動作と完全に互換性があります。

A TID is deemed to be more recent than another when its value is greater as determined by the operations detailed in this section.

このセクションで詳述する操作によって判断した値が大きい場合に、そのTIDは別のTIDよりも新しいとみなされます。

The TID range is subdivided in a "lollipop" fashion [Perlman83], where the values from 128 and greater are used as a linear sequence to indicate a restart and bootstrap the counter, and the values less than or equal to 127 are used as a circular sequence number space of size 128 as mentioned in [RFC1982]. Consideration is given to the mode of operation when transitioning from the linear region to the circular region. Finally, when operating in the circular region, if sequence numbers are determined to be too far apart, then they are not comparable, as detailed below.

TIDの範囲は「ロリポップ」方式[Perlman83]で分割されます。128以上の値は、再起動を示してカウンターをブートストラップするための線形のシーケンスとして使用され、127以下の値は、[RFC1982]で述べられているような、サイズ128の循環シーケンス番号空間として使用されます。線形領域から循環領域に遷移する際の動作モードについても考慮されています。最後に、循環領域で動作している場合、シーケンス番号が離れすぎていると判断されたときは、以下で詳述するように、それらは比較できません。

A window of comparison, SEQUENCE_WINDOW = 16, is configured based on a value of 2^N, where N is defined to be 4 in this specification.

比較のウィンドウSEQUENCE_WINDOW = 16は、2^Nの値に基づいて設定されます。ここで、Nはこの仕様では4と定義されます。

For a given sequence counter,

あるシーケンスカウンターについて、

  1. Prior to use, the sequence counter SHOULD be initialized to an implementation-defined value of 128 or greater. A recommended value is 240 (256 - SEQUENCE_WINDOW).
  2. When a sequence counter increment would cause the sequence counter to increment beyond its maximum value, the sequence counter MUST wrap back to 0. When incrementing a sequence counter greater than or equal to 128, the maximum value is 255. When incrementing a sequence counter less than 128, the maximum value is 127.

  3. When comparing two sequence counters, the following rules MUST be applied:

    1. When a first sequence counter A is in the interval [128-255] and a second sequence counter B is in the interval [0-127]:

      1. If (256 + B - A) is less than or equal to SEQUENCE_WINDOW, then B is greater than A, A is less than B, and the two are not equal.
      2. If (256 + B - A) is greater than SEQUENCE_WINDOW, then A is greater than B, B is less than A, and the two are not equal.

      For example, if A is 240 and B is 5, then (256 + 5 - 240) is 21. 21 is greater than SEQUENCE_WINDOW (16); thus, 240 is greater than 5. As another example, if A is 250 and B is 5, then (256 + 5 - 250) is 11. 11 is less than SEQUENCE_WINDOW (16); thus, 250 is less than 5.

    2. In the case where both sequence counters to be compared are less than or equal to 127, and in the case where both sequence counters to be compared are greater than or equal to 128:

      1. If the absolute magnitude of difference between the two sequence counters is less than or equal to SEQUENCE_WINDOW, then a comparison as described in [RFC1982] is used to determine the relationships "greater than", "less than", and "equal".
      2. If the absolute magnitude of difference of the two sequence counters is greater than SEQUENCE_WINDOW, then a desynchronization has occurred and the two sequence numbers are not comparable.
  4. If two sequence numbers are determined to be not comparable, i.e., the results of the comparison are not defined, then a node should give precedence to the sequence number that was most recently incremented. Failing this, the node should select the sequence number in order to minimize the resulting changes to its own state.
  1. 使用前に、シーケンスカウンターは、実装で定義された128以上の値に初期化すべきです（SHOULD）。推奨値は240（256 - SEQUENCE_WINDOW）です。
  2. シーケンスカウンターをインクリメントするとその最大値を超えてしまう場合、シーケンスカウンターは0に戻らなければなりません（MUST）。128以上のシーケンスカウンターをインクリメントする場合、最大値は255です。128未満のシーケンスカウンターをインクリメントする場合、最大値は127です。

  3. 2つのシーケンスカウンターを比較する場合、次の規則を適用しなければなりません（MUST）。

    1. 1つ目のシーケンスカウンターAが区間[128-255]にあり、2つ目のシーケンスカウンターBが区間[0-127]にある場合:

      1. (256 + B - A)がSEQUENCE_WINDOW以下の場合、BはAより大きく、AはBより小さく、両者は等しくありません。
      2. (256 + B - A)がSEQUENCE_WINDOWより大きい場合、AはBより大きく、BはAより小さく、両者は等しくありません。

      たとえば、Aが240でBが5の場合、(256 + 5 - 240)は21です。21はSEQUENCE_WINDOW（16）より大きいので、240は5より大きくなります。別の例として、Aが250でBが5の場合、(256 + 5 - 250)は11です。11はSEQUENCE_WINDOW（16）より小さいので、250は5より小さくなります。

    2. 比較する両方のシーケンスカウンターが127以下の場合、および比較する両方のシーケンスカウンターが128以上の場合:

      1. 2つのシーケンスカウンターの差の絶対値がSEQUENCE_WINDOW以下の場合、「より大きい」、「より小さい」、「等しい」の関係を判断するために、[RFC1982]で説明されている比較が使用されます。
      2. 2つのシーケンスカウンターの差の絶対値がSEQUENCE_WINDOWより大きい場合、非同期化が発生しており、2つのシーケンス番号は比較できません。
  4. 2つのシーケンス番号が比較できないと判断された場合、つまり比較の結果が定義されない場合、ノードは、最も最近インクリメントされたシーケンス番号を優先すべきです。それができない場合、ノードは、自身の状態に生じる変化が最小になるようにシーケンス番号を選択すべきです。

5.3. Registration Ownership Verifier (ROVR)

5.3. 登録所有権検証子（ROVR）

The ROVR field replaces the EUI-64 field of the ARO defined in [RFC6775]. It is associated in the 6LR and the 6LBR with the registration state. The ROVR can be a unique ID of the Registering Node, such as the EUI-64 address of an interface. This can also be a token obtained with cryptographic methods that can be used in additional protocol exchanges to associate a cryptographic identity (key) with this registration to ensure that only the owner can modify it later, if the proof of ownership of the ROVR can be obtained. The scope of a ROVR is the registration of a particular IPv6 Address, and it MUST NOT be used to correlate registrations of different addresses.

ROVRフィールドは、[RFC6775]で定義されているAROのEUI-64フィールドを置き換えます。ROVRは、6LRと6LBRにおいて登録状態に関連付けられます。ROVRは、インターフェイスのEUI-64アドレスなどの、登録者ノードの一意なIDにできます。また、ROVRの所有権の証明が得られるのであれば、暗号学的な方法で得られたトークンにすることもできます。このトークンは、後で所有者だけが登録を変更できるようにするため、暗号学的なアイデンティティー（鍵）をこの登録に関連付ける追加のプロトコル交換で使用できます。ROVRのスコープは特定のIPv6アドレスの登録であり、異なるアドレスの登録を相関付けるために使用してはなりません（MUST NOT）。

The ROVR can be of different types; the type is signaled in the message that carries the new type. For instance, the type can be a cryptographic string and can be used to prove the ownership of the registration as specified in [AP-ND] ("Address Protected Neighbor Discovery for Low-power and Lossy Networks"). In order to support the flows related to the proof of ownership, this specification introduces new status codes "Validation Requested" and "Validation Failed" in the EARO.

ROVRにはさまざまな種類があり、その種類は新しい種類を運ぶメッセージの中で通知されます。たとえば、その種類は暗号学的な文字列であってもよく、[AP-ND]（「Address Protected Neighbor Discovery for Low-power and Lossy Networks」）で規定されているように、登録の所有権を証明するために使用できます。所有権の証明に関連するフローをサポートするために、この仕様はEAROに新しいステータスコード「Validation Requested」と「Validation Failed」を導入します。

Note regarding ROVR collisions: Different techniques for forming the ROVR will operate in different namespaces. [RFC6775] specifies the use of EUI-64 addresses. [AP-ND] specifies the generation of cryptographic tokens. While collisions are not expected in the EUI-64 namespace only, they may happen if [AP-ND] is implemented by at least one of the nodes. An implementation that understands the namespace MUST consider that ROVRs from different namespaces are different even if they have the same value. An RFC 6775-only 6LBR or 6LR will confuse the namespaces; this slightly increases the risk of a ROVR collision. A ROVR collision has no effect if the two Registering Nodes register different addresses, since the ROVR is only significant within the context of one registration. A ROVR is not expected to be unique to one registration, as this specification allows a node to use the same ROVR to register multiple IPv6 Addresses. This is why the ROVR MUST NOT be used as a key to identify the Registering Node or as an index to the registration. It is only used as a match to ensure that the node that updates a registration for an IPv6 Address is the node that made the original registration for that IPv6 Address. Also, when the ROVR is not an EUI-64 address, then it MUST NOT be used as the Interface Identifier of the Registered Address. This way, a registration that uses that ROVR will not collide with that of an IPv6 Address derived from EUI-64 and using the EUI-64 as the ROVR per [RFC6775].

ROVRの衝突に関する注記：ROVRを形成するための異なる手法は、異なる名前空間で動作します。[RFC6775]はEUI-64アドレスの使用を規定しています。[AP-ND]は暗号学的なトークンの生成を規定しています。EUI-64の名前空間だけであれば衝突は想定されませんが、少なくとも1つのノードが[AP-ND]を実装している場合には衝突が起こる可能性があります。名前空間を理解する実装は、異なる名前空間からのROVRは、同じ値を持っていても異なるものとみなさなければなりません（MUST）。RFC 6775のみの6LBRまたは6LRは名前空間を混同するため、ROVRの衝突のリスクがわずかに高まります。ROVRは1つの登録の文脈の中でのみ意味を持つため、2つの登録者ノードが異なるアドレスを登録する場合、ROVRの衝突は影響しません。この仕様では、ノードが同じROVRを使用して複数のIPv6アドレスを登録することを許可しているため、ROVRが1つの登録に固有であることは想定されていません。そのため、ROVRを、登録者ノードを識別するためのキーや登録へのインデックスとして使用してはなりません（MUST NOT）。ROVRは、あるIPv6アドレスの登録を更新するノードが、そのIPv6アドレスの元の登録を行ったノードと同じであることを確認するための照合にのみ使用されます。また、ROVRがEUI-64アドレスでない場合、それを登録アドレスのインターフェイス識別子として使用してはなりません（MUST NOT）。こうすることで、そのROVRを使用する登録が、EUI-64から導出され、かつ[RFC6775]に従ってEUI-64をROVRとして使用するIPv6アドレスの登録と衝突することはありません。

The Registering Node SHOULD store the ROVR, or enough information to regenerate it, in persistent memory. If this is not done and an event such as a reboot causes a loss of state, re-registering the same address could be impossible until (1) the 6LRs and the 6LBR time out the previous registration or (2) a management action clears the relevant state in the network.

登録者ノードは、ROVR、またはそれを再生成するのに十分な情報を、永続的なメモリーに保存すべきです（SHOULD）。これが行われず、再起動などのイベントによって状態が失われた場合、(1) 6LRと6LBRで以前の登録がタイムアウトするか、(2) 管理操作によってネットワーク内の関連する状態がクリアされるまで、同じアドレスを再登録できなくなる可能性があります。

5.4. Extended Duplicate Address Messages

5.4. 拡張重複アドレスメッセージ

In order to map the new EARO content in the EDA messages, a new TID field is added to the EDAR and EDAC messages as a replacement for the Reserved field, and a non-null value of the ICMP Code indicates support for this specification. The format of the EDAR and EDAC messages is presented in Section 4.2.

EDAメッセージに新しいEAROの内容を対応させるために、EDARメッセージとEDACメッセージには予約フィールドの代わりに新しいTIDフィールドが追加され、ICMPコードがゼロでない値の場合はこの仕様をサポートしていることを示します。EDARメッセージとEDACメッセージのフォーマットはSection 4.2で示しています。

As with the EARO, the EDA messages are backward compatible with the RFC 6775-only versions, as long as the ROVR field is 64 bits long. Remarks concerning backward compatibility for the protocol between the 6LN and the 6LR apply similarly between a 6LR and a 6LBR.

EAROと同様に、EDAメッセージは、ROVRフィールドの長さが64ビットである限り、RFC 6775のみのバージョンと後方互換性があります。6LNと6LRの間のプロトコルの後方互換性に関する注意事項は、6LRと6LBRの間にも同様に適用されます。

5.5. Registering the Target Address

5.5. ターゲットアドレスの登録

An NS message with an EARO is a registration if and only if it also carries an SLLA Option ("SLLAO") [RFC6775] ("SLLA" stands for "Source Link-Layer Address"). The EARO can also be used in NS and NA messages between Routing Registrars to determine the distributed registration state; in that case, it does not carry the SLLA Option and is not confused with a registration.

EAROを含むNSメッセージは、SLLAオプション（「SLLAO」）[RFC6775]も運ぶ場合に限り、登録となります（「SLLA」は「Source Link-Layer Address（送信元リンク層アドレス）」の略です）。EAROは、分散された登録状態を判断するために、ルーティングレジストラー間のNSメッセージとNAメッセージでも使用できます。その場合、EAROはSLLAオプションを運ばず、登録と混同されることはありません。

The Registering Node is the node that performs the registration to the Routing Registrar. As also described in [RFC6775], it may be the Registered Node as well, in which case it registers one of its own addresses and indicates its own MAC address as the SLLA in the NS(EARO).

登録者ノードは、ルーティングレジストラーへの登録を実行するノードです。[RFC6775]でも説明されているように、登録者ノードは登録ノード自身である場合もあります。その場合、登録者ノードは自身のアドレスの1つを登録し、NS(EARO)のSLLAとして自身のMACアドレスを示します。

This specification adds the capability to proxy the registration operation on behalf of a Registered Node that is reachable over an LLN mesh. In that case, if the Registered Node is reachable from the Routing Registrar via a mesh-under configuration, the Registering Node indicates the MAC address of the Registered Node as the SLLA in the NS(EARO). If the Registered Node is reachable over a route-over configuration from the Registering Node, the SLLA in the NS(ARO) is that of the Registering Node. This enables the Registering Node to attract the packets from the Routing Registrar and route them over the LLN to the Registered Node.

この仕様は、LLNメッシュを介して到達可能な登録ノードに代わって、登録操作を代理する能力を追加します。その場合、登録ノードがメッシュアンダー構成を介してルーティングレジストラーから到達可能であれば、登録者ノードは、NS(EARO)のSLLAとして登録ノードのMACアドレスを示します。登録ノードが登録者ノードからルートオーバー構成を介して到達可能な場合、NS(ARO)のSLLAは登録者ノードのものになります。これにより、登録者ノードは、ルーティングレジストラーからのパケットを引き寄せ、それらをLLN経由で登録ノードにルーティングできます。

In order to enable the latter operation, this specification changes the behavior of the 6LN and the 6LR so that the Registered Address is found in the Target Address field of the NS and NA messages as opposed to the Source Address field. With this convention, a TLLA Option (Target Link-Layer Address Option, or "TLLAO") indicates the link-layer address of the 6LN that owns the address.

後者の動作を可能にするために、この仕様は、登録アドレスがNSメッセージとNAメッセージの送信元アドレスフィールドではなくターゲットアドレスフィールドに含まれるように、6LNと6LRの振る舞いを変更します。この規約により、TLLAオプション（ターゲットリンク層アドレスオプション（Target Link-Layer Address Option）、「TLLAO」）は、そのアドレスを所有する6LNのリンク層アドレスを示します。

A Registering Node (e.g., a 6LBR also acting as a RPL root) that advertises reachability for the 6LN MUST place its own link-layer address in the SLLA Option of the registration NS(EARO) message. This maintains compatibility with RFC 6775-only 6LoWPAN ND.

6LNの到達可能性を広告する登録者ノード（たとえば、RPLルートとしても動作する6LBR）は、登録のNS(EARO)メッセージのSLLAオプションに自身のリンク層アドレスを格納しなければなりません（MUST）。これにより、RFC 6775のみの6LoWPAN NDとの互換性が維持されます。

5.6. Link-Local Addresses and Registration

5.6. リンクローカルアドレスと登録

LLN nodes are often not wired and may move. There is no guarantee that a Link-Local Address will remain unique among a huge and potentially variable set of neighboring nodes.

LLNのノードは多くの場合有線ではなく、移動することもあります。リンクローカルアドレスが、膨大で変動する可能性のある近隣ノードの集合の中で一意であり続ける保証はありません。

Compared to [RFC6775], this specification only requires that a Link-Local Address be unique from the perspective of the two nodes that use it to communicate (e.g., the 6LN and the 6LR in an NS/NA exchange). This simplifies the DAD process in a route-over topology for Link-Local Addresses by avoiding an exchange of EDA messages between the 6LR and a 6LBR for those addresses.

[RFC6775]と比べて、この仕様では、リンクローカルアドレスが、それを使用して通信する2つのノード（たとえば、NS/NA交換における6LNと6LR）の観点から一意であることだけを要求します。これにより、それらのアドレスについて6LRと6LBRの間でEDAメッセージを交換することを避けられるため、ルートオーバートポロジーにおけるリンクローカルアドレスのDADプロセスが単純になります。

An exchange between two nodes using Link-Local Addresses implies that they are reachable over one hop. A node MUST register a Link-Local Address to a 6LR in order to obtain further reachability by way of that 6LR and, in particular, to use the Link-Local Address as the Source Address to register other addresses, e.g., global addresses.

リンクローカルアドレスを使用した2つのノード間の交換は、それらが1ホップで到達可能であることを意味します。ノードは、その6LRを経由してさらに到達可能性を得るために、特に、そのリンクローカルアドレスを送信元アドレスとして使用して他のアドレス（たとえばグローバルアドレス）を登録するために、リンクローカルアドレスを6LRに登録しなければなりません（MUST）。

If there is no collision with a previously registered address, then the Link-Local Address is unique from the standpoint of this 6LR and the registration is not a duplicate. Two different 6LRs might claim the same Link-Local Address but different link-layer addresses. In that case, a 6LN MUST only interact with at most one of the 6LRs.

以前に登録されたアドレスとの衝突がなければ、そのリンクローカルアドレスはこの6LRの観点から一意であり、その登録は重複ではありません。2つの異なる6LRが、同じリンクローカルアドレスを異なるリンク層アドレスで主張する可能性があります。その場合、6LNは、それらの6LRのうち多くとも1つとだけやり取りしなければなりません（MUST）。

The exchange of EDAR and EDAC messages between the 6LR and a 6LBR, which ensures that an address is unique across the domain covered by the 6LBR, does not need to take place for Link-Local Addresses.

アドレスが6LBRのカバーするドメイン全体で一意であることを保証する、6LRと6LBRの間のEDARメッセージとEDACメッセージの交換は、リンクローカルアドレスについては行う必要がありません。

When sending an NS(EARO) to a 6LR, a 6LN MUST use a Link-Local Address as the Source Address of the registration, whatever the type of IPv6 Address that is being registered. That Link-Local Address MUST be either an address that is already registered to the 6LR or the address that is being registered.

6LRにNS(EARO)を送信する場合、6LNは、登録されるIPv6アドレスの種類にかかわらず、登録の送信元アドレスとしてリンクローカルアドレスを使用しなければなりません（MUST）。そのリンクローカルアドレスは、すでに6LRに登録されているアドレスか、登録されようとしているアドレスのいずれかでなければなりません（MUST）。

When a 6LN starts up, it typically multicasts an RS and receives one or more unicast RA messages from 6LRs. If the 6LR can process EARO messages, then it places a 6CIO in its RA message with the E flag set as required in Section 6.1.

6LNは、起動時に通常、RSをマルチキャストし、6LRから1つ以上のユニキャストのRAメッセージを受信します。6LRがEAROメッセージを処理できる場合、Section 6.1で要求されているように、6LRはEフラグを設定した6CIOをRAメッセージに格納します。

When a Registering Node does not have an already-registered address, it MUST register a Link-Local Address, using it as both the Source Address and the Target Address of an NS(EARO) message. In that case, it is RECOMMENDED to use an address for which DAD is not required (see [RFC6775]), e.g., derived from a globally unique EUI-64 address; using the SLLA Option in the NS is consistent with existing ND specifications such as [RFC4429] ("Optimistic Duplicate Address Detection (DAD) for IPv6"). The 6LN MAY then use that address to register one or more other addresses.

登録者ノードは、すでに登録されたアドレスを持っていない場合、リンクローカルアドレスを、NS(EARO)メッセージの送信元アドレスとターゲットアドレスの両方として使用して登録しなければなりません（MUST）。その場合、DADが不要なアドレス（[RFC6775]を参照）、たとえばグローバルに一意なEUI-64アドレスから導出されたアドレスを使用することが推奨されます（RECOMMENDED）。NSでSLLAオプションを使用することは、[RFC4429]（「Optimistic Duplicate Address Detection (DAD) for IPv6」）などの既存のND仕様と整合しています。その後、6LNは、そのアドレスを使用して1つ以上の他のアドレスを登録してもよいです（MAY）。

A 6LR that supports this specification replies with an NA(EARO), setting the appropriate status. Since there is no exchange of EDAR or EDAC messages for Link-Local Addresses, the 6LR may answer immediately to the registration of a Link-Local Address, based solely on its existing state and the SLLA Option that is placed in the NS(EARO) message as required in [RFC6775].

この仕様をサポートする6LRは、適切なステータスを設定したNA(EARO)で応答します。リンクローカルアドレスについてはEDARメッセージやEDACメッセージの交換がないため、6LRは、自身の既存の状態と、[RFC6775]で要求されているようにNS(EARO)メッセージに格納されたSLLAオプションだけに基づいて、リンクローカルアドレスの登録に直ちに応答できます。

A node registers its IPv6 Global Unicast Addresses (GUAs) to a 6LR in order to establish global reachability for these addresses via that 6LR. When registering with an updated 6LR, a Registering Node does not use a GUA as the Source Address, in contrast to a node that complies with [RFC6775]. For non-Link-Local Addresses, the exchange of EDAR and EDAC messages MUST conform to [RFC6775], but the extended formats described in this specification for the DAR and the DAC are used to relay the extended information in the case of an EARO.

ノードは、6LRを経由してIPv6グローバルユニキャストアドレス（Global Unicast Address、GUA）へのグローバルな到達可能性を確立するために、それらのアドレスをその6LRに登録します。[RFC6775]に準拠するノードとは対照的に、更新済みの6LRに登録する場合、登録者ノードはGUAを送信元アドレスとして使用しません。リンクローカルアドレス以外のアドレスについては、EDARメッセージとEDACメッセージの交換は[RFC6775]に準拠しなければなりません（MUST）。ただし、EAROの場合には、拡張された情報を中継するために、この仕様で説明するDARとDACの拡張フォーマットが使用されます。

5.7. Maintaining the Registration States

5.7. 登録状態の維持

This section discusses protocol actions that involve the Registering Node, the 6LR, and the 6LBR. It must be noted that the portion that deals with a 6LBR only applies to those addresses that are registered to it; as discussed in Section 5.6, this is not the case for Link-Local Addresses. The registration state includes all data that is stored in the router relative to that registration, in particular, but not limited to, an NCE. 6LBRs and Routing Registrars may store additional registration information and use synchronization protocols that are out of scope for this document.

このセクションでは、登録者ノード、6LR、および6LBRが関与するプロトコルの動作について説明します。6LBRを扱う部分は、6LBRに登録されるアドレスにのみ適用されることに注意する必要があります。Section 5.6で説明したように、リンクローカルアドレスはこれに該当しません。登録状態には、その登録に関してルーターに保存されるすべてのデータが含まれます。特にNCEが含まれますが、それに限定されません。6LBRとルーティングレジストラーは、追加の登録情報を保存し、この文書の範囲外の同期プロトコルを使用する場合があります。

A 6LR cannot accept a new registration when its registration storage space is exhausted. In that situation, the EARO is returned in an NA message with a status code of "Neighbor Cache Full" (Status 2; see [RFC6775] and Table 1), and the Registering Node may attempt to register to another 6LR.

6LRは、登録の記憶領域を使い果たした場合、新しい登録を受け付けることができません。その場合、EAROは、ステータスコード「Neighbor Cache Full」（ステータス2。[RFC6775]とTable 1を参照）とともにNAメッセージで返され、登録者ノードは別の6LRへの登録を試みる場合があります。

If the registry in the 6LBR is full, then the 6LBR cannot decide whether a registration for a new address is a duplicate. In that case, the 6LBR replies to an EDAR message with an EDAC message that carries a new status code indicating "6LBR Registry Saturated" (Table 1). Note: This code is used by 6LBRs instead of "Neighbor Cache Full" when responding to a Duplicate Address message exchange and is passed on to the Registering Node by the 6LR. There is no point in the node retrying this registration via another 6LR, since the problem is network-wide. The node may abandon that address, de-register other addresses first to make room, or keep the address "tentative" [RFC4861] and retry later.

6LBRのレジストリーが満杯の場合、6LBRは新しいアドレスの登録が重複かどうかを判断できません。その場合、6LBRは、「6LBR Registry Saturated」を示す新しいステータスコード（Table 1）を運ぶEDACメッセージでEDARメッセージに応答します。注：このコードは、重複アドレスメッセージの交換に応答する際に、「Neighbor Cache Full」の代わりに6LBRによって使用され、6LRによって登録者ノードに渡されます。問題はネットワーク全体にわたるものであるため、ノードが別の6LRを経由してこの登録を再試行しても意味はありません。ノードは、そのアドレスを放棄するか、空きを作るためにまず他のアドレスの登録を解除するか、またはそのアドレスを「仮（tentative）」[RFC4861]のままにして後で再試行することがあります。

A node renews an existing registration by sending a new NS(EARO) message for the Registered Address, and the 6LR MUST report the new registration to the 6LBR.

ノードは、登録アドレスについて新しいNS(EARO)メッセージを送信することで既存の登録を更新します。6LRは、新しい登録を6LBRに報告しなければなりません（MUST）。

A node that ceases to use an address SHOULD attempt to de-register that address from all the 6LRs to which it has registered the address. This is achieved using an NS(EARO) message with a Registration Lifetime of 0. If this is not done, the associated state will remain in the network until the current Registration Lifetime expires; this may lead to a situation where the 6LR resources become saturated, even if they were correctly planned to start with. The 6LR may then take defensive measures that may prevent this node or some other nodes from owning as many addresses as they request (see Section 7).

アドレスの使用をやめるノードは、そのアドレスを登録したすべての6LRから、そのアドレスの登録解除を試みるべきです（SHOULD）。これは、登録有効期間を0にしたNS(EARO)メッセージを使用して行います。これが行われない場合、関連する状態は、現在の登録有効期間が満了するまでネットワーク内に残ります。これにより、たとえ当初は正しく計画されていたとしても、6LRのリソースが飽和する状況につながる可能性があります。その場合、6LRは、このノードや他のいくつかのノードが要求するだけの数のアドレスを所有することを妨げる防御的な措置をとる可能性があります（Section 7を参照）。

A node that moves away from a particular 6LR SHOULD attempt to de-register all of its addresses registered to that 6LR and register to a new 6LR with an incremented TID. When/if the node appears elsewhere, an asynchronous NA(EARO) or EDAC message with a status code of "Moved" SHOULD be used to clean up the state in the previous location. The "Moved" status can be used by a Routing Registrar in an NA(EARO) message to indicate that the ownership of the proxy state was transferred to another Routing Registrar due to movement of the device. If the receiver of the message has registration state corresponding to the related address, it SHOULD propagate the status down the forwarding path to the Registered Node (e.g., reversing an existing RPL [RFC6550] path as prescribed in [Efficient-NPDAO]). Whether it could do so or not, the receiver MUST clean up said state.

特定の6LRから離れるノードは、その6LRに登録された自身のすべてのアドレスの登録解除を試み、インクリメントしたTIDで新しい6LRに登録すべきです（SHOULD）。そのノードが別の場所に現れた場合（または現れたときに）、以前の位置の状態をクリーンアップするために、ステータスコード「Moved」を持つ非同期のNA(EARO)メッセージまたはEDACメッセージを使用すべきです（SHOULD）。「Moved」ステータスは、デバイスの移動によってプロキシー状態の所有権が別のルーティングレジストラーに移されたことを示すために、ルーティングレジストラーがNA(EARO)メッセージで使用できます。メッセージの受信者は、関連するアドレスに対応する登録状態を持っている場合、そのステータスを転送経路に沿って登録ノードまで伝播すべきです（SHOULD）（たとえば、[Efficient-NPDAO]で規定されているように、既存のRPL [RFC6550]パスを逆にたどります）。伝播できたかどうかにかかわらず、受信者はその状態をクリーンアップしなければなりません（MUST）。

Upon receiving an NS(EARO) message with a Registration Lifetime of 0 and determining that this EARO is the most recent for a given NCE (see Section 5.2), a 6LR cleans up its NCE. If the address was registered to the 6LBR, then the 6LR MUST report to the 6LBR, through a Duplicate Address exchange with the 6LBR, indicating the null Registration Lifetime and the latest TID that this 6LR is aware of.

登録有効期間が0のNS(EARO)メッセージを受信し、このEAROが所定のNCEについて最新のものであると判断した場合（Section 5.2を参照）、6LRは自身のNCEをクリーンアップします。そのアドレスが6LBRに登録されていた場合、6LRは、6LBRとの重複アドレス交換を通じて、ゼロの登録有効期間と、この6LRが認識している最新のTIDを示して、6LBRに報告しなければなりません（MUST）。

Upon receiving the EDAR message, the 6LBR determines if this is the most recent TID it has received for that particular registry entry. If so, then the EDAR is answered with an EDAC message bearing a status code of 0 ("Success") [RFC6775], and the entry is scheduled to be removed. Otherwise, a status code of "Moved" is returned instead, and the existing entry is maintained.

EDARメッセージを受信すると、6LBRは、これがその特定のレジストリーエントリーについて受信した最新のTIDかどうかを判断します。そうであれば、EDARには、ステータスコード0（「Success」）[RFC6775]を持つEDACメッセージで応答し、そのエントリーは削除が予定されます。そうでなければ、代わりにステータスコード「Moved」が返され、既存のエントリーは維持されます。

When an address is scheduled to be removed, the 6LBR SHOULD keep its NCE in a DELAY state [RFC4861] for a configurable period of time, so as to prevent a scenario where (1) a mobile node that de-registered from one 6LR did not yet register to a new one or (2) the new registration did not yet reach the 6LBR due to propagation delays in the network. Once the DELAY time has passed, the 6LBR silently removes its entry.

アドレスの削除が予定された場合、6LBRは、(1) ある6LRから登録解除したモバイルノードがまだ新しい6LRに登録していない、または (2) ネットワーク内の伝播遅延のために新しい登録がまだ6LBRに届いていない、というシナリオを防ぐために、設定可能な期間、そのNCEをDELAY状態[RFC4861]に保持すべきです（SHOULD）。DELAY時間が経過すると、6LBRはそのエントリーを暗黙のうちに削除します。

6. Backward Compatibility

6. 後方互換性

This specification changes the behavior of the peers in a registration flow. To enable backward compatibility, a 6LN that registers to a 6LR that is not known to support this specification MUST behave in a manner that is backward compatible with [RFC6775]. Conversely, if the 6LR is found to support this specification, then the 6LN MUST conform to this specification when communicating with that 6LR.

この仕様は、登録フローにおけるピアの振る舞いを変更します。後方互換性を可能にするために、この仕様をサポートしていることがわかっていない6LRに登録する6LNは、[RFC6775]と後方互換性のある方法で振る舞わなければなりません（MUST）。逆に、6LRがこの仕様をサポートしていることがわかった場合、6LNは、その6LRと通信する際にこの仕様に準拠しなければなりません（MUST）。

A 6LN that supports this specification MUST always use an EARO as a replacement for an ARO in its registration to a router. This behavior is backward compatible, since the T flag and TID field occupy fields that are reserved in [RFC6775] and are thus ignored by an RFC 6775-only router. A router that supports this specification MUST answer an NS(ARO) and an NS(EARO) with an NA(EARO). A router that does not support this specification will consider the ROVR as an EUI-64 address and treat it the same; this scenario has no consequence if the Registered Addresses are different.

この仕様をサポートする6LNは、ルーターへの登録において、常にAROの代わりにEAROを使用しなければなりません（MUST）。TフラグとTIDフィールドは[RFC6775]で予約されているフィールドを占めており、そのためRFC 6775のみのルーターでは無視されるので、この振る舞いには後方互換性があります。この仕様をサポートするルーターは、NS(ARO)とNS(EARO)にNA(EARO)で応答しなければなりません（MUST）。この仕様をサポートしないルーターは、ROVRをEUI-64アドレスとみなし、同じように扱います。このシナリオは、登録アドレスが異なる場合には何の影響もありません。

6.1. Signaling EARO Support

6.1. EAROのサポートの通知

[RFC7400] specifies the 6CIO, which indicates a node's capabilities to the node's peers. The 6CIO MUST be present in both RS and RA messages, unless the 6CIO information was already shared in recent exchanges or pre-configured in all nodes in a network. In any case, a 6CIO MUST be placed in an RA message that is sent in response to an RS with a 6CIO.

[RFC7400]は、ノードの能力をそのノードのピアに示す6CIOを規定しています。6CIOの情報が最近の交換ですでに共有されているか、ネットワーク内のすべてのノードに事前設定されている場合を除き、6CIOはRSメッセージとRAメッセージの両方に存在しなければなりません（MUST）。いずれの場合でも、6CIOを含むRSへの応答として送信されるRAメッセージには、6CIOを格納しなければなりません（MUST）。

Section 4.3 defines a new flag for the 6CIO to signal EARO support by the issuer of the message. New flags are also added to the 6CIO to signal the sender's capability to act as a 6LR, 6LBR, and Routing Registrar (see Section 4.3).

Section 4.3では、メッセージの発行者によるEAROのサポートを通知するための6CIOの新しいフラグを定義しています。また、送信者が6LR、6LBR、およびルーティングレジストラーとして動作する能力を通知するための新しいフラグも6CIOに追加されます（Section 4.3を参照）。

Section 4.3 also defines a new flag that indicates the support of EDAR and EDAC messages by the 6LBR. This flag is valid in RA messages but not in RS messages. More information on the 6LBR is found in a separate Authoritative Border Router Option (ABRO). The ABRO is placed in RA messages as prescribed by [RFC6775]; in particular, it MUST be placed in an RA message that is sent in response to an RS with a 6CIO indicating the capability to act as a 6LR, since the RA propagates information between routers.

Section 4.3では、6LBRがEDARメッセージとEDACメッセージをサポートしていることを示す新しいフラグも定義しています。このフラグはRAメッセージでは有効ですが、RSメッセージでは有効ではありません。6LBRに関するより多くの情報は、別の権威境界ルーターオプション（Authoritative Border Router Option、ABRO）にあります。ABROは、[RFC6775]で規定されているとおりにRAメッセージに格納されます。特に、RAはルーター間で情報を伝播するため、6LRとして動作する能力を示す6CIOを含むRSへの応答として送信されるRAメッセージには、ABROを格納しなければなりません（MUST）。

6.2. RFC 6775-Only 6LN

6.2. RFC 6775のみの6LN

An RFC 6775-only 6LN will use the Registered Address as the Source Address of the NS message and will not use an EARO. An updated 6LR MUST accept that registration if it is valid per [RFC6775], and it MUST manage the binding cache accordingly. The updated 6LR MUST then use the RFC 6775-only DAR and DAC messages as specified in [RFC6775] to indicate to the 6LBR that the TID is not present in the messages.

RFC 6775のみの6LNは、登録アドレスをNSメッセージの送信元アドレスとして使用し、EAROを使用しません。更新済みの6LRは、その登録が[RFC6775]に従って有効であれば、それを受け付けなければなりません（MUST）。また、それに応じてバインディングキャッシュを管理しなければなりません（MUST）。その後、更新済みの6LRは、メッセージにTIDが存在しないことを6LBRに示すために、[RFC6775]で規定されているRFC 6775のみのDARメッセージとDACメッセージを使用しなければなりません（MUST）。

The main difference from [RFC6775] is that the exchange of DAR and DAC messages for the purpose of DAD is avoided for Link-Local Addresses. In any case, the 6LR MUST use an EARO in the reply and can use any of the status codes defined in this specification.

[RFC6775]との主な違いは、リンクローカルアドレスについてはDADのためのDARメッセージとDACメッセージの交換を行わないことです。いずれの場合でも、6LRは応答でEAROを使用しなければなりません（MUST）。また、この仕様で定義されているいずれのステータスコードも使用できます。

6.3. RFC 6775-Only 6LR

6.3. RFC 6775のみの6LR

An updated 6LN discovers the capabilities of the 6LR in the 6CIO in RA messages from that 6LR; if the 6CIO was not present in the RA, then the 6LR is assumed to be RFC 6775-only.

更新済みの6LNは、6LRからのRAメッセージの6CIOで、その6LRの能力を発見します。RAに6CIOが存在しなかった場合、その6LRはRFC 6775のみであるとみなされます。

An updated 6LN MUST use an EARO in the request, regardless of the type of 6LR -- RFC 6775-only or updated; this implies that the T flag is set. It MUST use a ROVR of 64 bits if the 6LR is RFC 6775-only.

更新済みの6LNは、6LRの種類（RFC 6775のみか更新済みか）にかかわらず、要求でEAROを使用しなければなりません（MUST）。これは、Tフラグが設定されることを意味します。6LRがRFC 6775のみである場合、6LNは64ビットのROVRを使用しなければなりません（MUST）。

If an updated 6LN moves from an updated 6LR to an RFC 6775-only 6LR, the RFC 6775-only 6LR will send an RFC 6775-only DAR message, which cannot be compared with an updated one for recency. Allowing RFC 6775-only DAR messages to update a state established by the updated protocol in the 6LBR would be an attack vector; therefore, this cannot be the default behavior. But if RFC 6775-only and updated 6LRs coexist temporarily in a network, then it makes sense for an administrator to install a policy that allows this behavior, using some method that is out of scope for this document.

更新済みの6LNが、更新済みの6LRからRFC 6775のみの6LRに移動した場合、RFC 6775のみの6LRはRFC 6775のみのDARメッセージを送信しますが、これは新しさについて更新済みのDARメッセージと比較できません。RFC 6775のみのDARメッセージが、6LBRにおいて更新済みのプロトコルによって確立された状態を更新することを許すと、攻撃ベクトルになります。したがって、これをデフォルトの振る舞いにすることはできません。ただし、RFC 6775のみの6LRと更新済みの6LRがネットワーク内に一時的に共存する場合、管理者が、この文書の範囲外の何らかの方法を使用して、この振る舞いを許可するポリシーをインストールすることは理にかなっています。

6.4. RFC 6775-Only 6LBR

6.4. RFC 6775のみの6LBR

With this specification, the Duplicate Address messages are extended to transport the EARO information. As with the NS/NA exchange, an updated 6LBR MUST always use the EDAR and EDAC messages.

この仕様により、重複アドレスメッセージはEAROの情報を転送するように拡張されます。NS/NA交換と同様に、更新済みの6LBRは常にEDARメッセージとEDACメッセージを使用しなければなりません（MUST）。

Note that an RFC 6775-only 6LBR will accept and process an EDAR message as if it were an RFC 6775-only DAR, as long as the ROVR is 64 bits long. An updated 6LR discovers the capabilities of the 6LBR in the 6CIO in RA messages from the 6LR; if the 6CIO was not present in any RA, then the 6LBR is assumed to be RFC 6775-only.

RFC 6775のみの6LBRは、ROVRの長さが64ビットである限り、EDARメッセージをRFC 6775のみのDARであるかのように受け付けて処理することに注意してください。更新済みの6LRは、6LRからのRAメッセージの6CIOで6LBRの能力を発見します。どのRAにも6CIOが存在しなかった場合、その6LBRはRFC 6775のみであるとみなされます。

If the 6LBR is RFC 6775-only, the 6LR MUST use only the 64 leftmost bits of the ROVR and place the result in the EDAR message to maintain compatibility. This way, the support of DAD is preserved.

6LBRがRFC 6775のみである場合、6LRは、互換性を維持するために、ROVRの左端の64ビットだけを使用し、その結果をEDARメッセージに格納しなければなりません（MUST）。こうすることで、DADのサポートが維持されます。

7. Security Considerations

7. セキュリティーに関する考慮事項

This specification extends [RFC6775], and the Security Considerations section of that document also applies to this document. In particular, the link layer SHOULD be sufficiently protected to prevent rogue access.

この仕様は[RFC6775]を拡張するものであり、その文書のセキュリティーに関する考慮事項のセクションはこの文書にも適用されます。特に、リンク層は、不正なアクセスを防ぐために十分に保護されるべきです（SHOULD）。

[RFC6775] does not protect the content of its messages and expects lower-layer encryption to defeat potential attacks. This specification requires the LLN MAC layer to provide secure unicast to/from a Routing Registrar and secure broadcast or multicast from the Routing Registrar in a way that prevents tampering with or replaying the ND messages.

[RFC6775]は自身のメッセージの内容を保護せず、潜在的な攻撃を阻止するために下位層の暗号化を想定しています。この仕様は、NDメッセージの改ざんやリプレイを防ぐ方法で、LLNのMAC層が、ルーティングレジストラーとの間のセキュアなユニキャストと、ルーティングレジストラーからのセキュアなブロードキャストまたはマルチキャストを提供することを要求します。

This specification recommends using privacy techniques (see Section 8) and protecting against address theft via methods that are outside the scope of this document. As an example, [AP-ND] guarantees the ownership of the Registered Address using a cryptographic ROVR.

この仕様は、プライバシー技術を使用すること（Section 8を参照）と、この文書の範囲外の方法でアドレスの盗用から保護することを推奨します。たとえば、[AP-ND]は、暗号学的なROVRを使用して登録アドレスの所有権を保証します。

The registration mechanism may be used by a rogue node to attack the 6LR or 6LBR with a denial-of-service attack against the registry. It may also happen that the registry of a 6LR or 6LBR is saturated and cannot take any more registrations; this scenario effectively denies the requesting node the capability to use a new address. In order to alleviate those concerns, (1) Section 5.2 provides a sequence counter that keeps incrementing to detect and clean up stale registration information and that contributes to defeat replay attacks and (2) Section 5.7 provides a number of recommendations that ensure that a stale registration is removed as soon as possible from the 6LR and 6LBR.

登録メカニズムは、不正なノードが、レジストリーに対するサービス拒否攻撃によって6LRや6LBRを攻撃するために使用される可能性があります。また、6LRや6LBRのレジストリーが飽和して、それ以上の登録を受け付けられなくなることもあります。このシナリオは、事実上、要求元のノードが新しいアドレスを使用する能力を拒否することになります。これらの懸念を軽減するために、(1) Section 5.2は、古い登録情報を検出してクリーンアップするためにインクリメントされ続け、リプレイ攻撃の阻止にも寄与するシーケンスカウンターを提供し、(2) Section 5.7は、古い登録ができるだけ早く6LRと6LBRから削除されることを保証するいくつかの推奨事項を提供します。

In particular, this specification recommends that:

特に、この仕様は次のことを推奨します。

  • A node that ceases to use an address SHOULD attempt to de-register that address from all the 6LRs to which it is registered.
  • The registration lifetimes SHOULD be individually configurable for each address or group of addresses. A node SHOULD be configured for each address (or address category) with a Registration Lifetime that reflects the expectation of how long it will use the address with the 6LR to which the address is registered. In particular, use cases that involve mobility or rapid address changes SHOULD use lifetimes that are the same order of magnitude as the duration of the expectation of presence but that are still longer.
  • The router (6LR or 6LBR) SHOULD be configurable so as to limit the number of addresses that can be registered by a single node, but as a protective measure only. In any case, a router MUST be able to keep a minimum number of addresses per node. That minimum depends on the type of device and ranges between 3 for a very constrained LLN and 10 for a larger device. A node may be identified by its MAC address, as long as it is not obfuscated by privacy measures. A stronger identification (e.g., by security credentials) is RECOMMENDED. When the maximum is reached, the router SHOULD use a Least Recently Used (LRU) algorithm to clean up the addresses, keeping at least one Link-Local Address. The router SHOULD attempt to keep one or more stable addresses if stability can be determined, e.g., because they are used over a much longer time span than other (privacy, shorter-lived) addresses.
  • In order to avoid denial of registration due to a lack of resources, administrators should take great care to deploy adequate numbers of 6LRs to cover the needs of the nodes in their range, so as to avoid a situation of starving nodes. It is expected that the 6LBR that serves an LLN is a more capable node than the average 6LR, but in a network condition where it may become saturated, a particular LLN should distribute the 6LBR functionality -- for instance, by leveraging a high-speed Backbone Link and Routing Registrars to aggregate multiple LLNs into a larger subnet.
  • アドレスの使用をやめるノードは、そのアドレスが登録されているすべての6LRから、そのアドレスの登録解除を試みるべきです（SHOULD）。
  • 登録有効期間は、アドレスまたはアドレスのグループごとに個別に設定可能であるべきです（SHOULD）。ノードには、アドレス（またはアドレスのカテゴリー）ごとに、アドレスが登録されている6LRでそのアドレスをどのくらいの期間使用するかの見込みを反映した登録有効期間を設定すべきです（SHOULD）。特に、移動や頻繁なアドレス変更を伴うユースケースでは、存在が見込まれる期間と同じ桁でありながら、それよりも長い有効期間を使用すべきです（SHOULD）。
  • ルーター（6LRまたは6LBR）は、単一のノードが登録できるアドレスの数を制限するように設定可能であるべきです（SHOULD）。ただし、これは保護手段としてのみ行います。いずれの場合でも、ルーターは、ノードあたり最小限の数のアドレスを保持できなければなりません（MUST）。その最小数はデバイスの種類によって異なり、非常に制約の厳しいLLNでは3、より大きなデバイスでは10の範囲です。ノードは、プライバシー対策によって難読化されていない限り、そのMACアドレスによって識別できます。より強力な識別（たとえばセキュリティークレデンシャルによる識別）が推奨されます（RECOMMENDED）。最大数に達した場合、ルーターは、少なくとも1つのリンクローカルアドレスを保持しつつ、LRU（Least Recently Used）アルゴリズムを使用してアドレスをクリーンアップすべきです（SHOULD）。安定性を判断できる場合（たとえば、他の（プライバシー用の、より短命な）アドレスよりもはるかに長い期間にわたって使用されているなど）、ルーターは1つ以上の安定したアドレスを保持するよう試みるべきです（SHOULD）。
  • リソース不足による登録の拒否を避けるために、管理者は、ノードが枯渇する状況を避けるように、範囲内のノードのニーズをカバーするのに十分な数の6LRを展開するよう細心の注意を払うべきです。LLNにサービスを提供する6LBRは平均的な6LRよりも能力の高いノードであることが想定されますが、6LBRが飽和する可能性のあるネットワーク状況では、特定のLLNは6LBRの機能を分散すべきです。たとえば、高速なバックボーンリンクとルーティングレジストラーを活用して、複数のLLNをより大きなサブネットに集約します。

The LLN nodes depend on a 6LBR and may use the services of a Routing Registrar for their operation. A trust model MUST be put in place to ensure that only authorized devices are acting in these roles, so as to avoid threats such as black-holing or bombing attack whereby an impersonated 6LBR would destroy state in the network by using the "Removed" status code. At a minimum, this trust model could be based on Layer 2 access control or could provide role validation as well (see Req-5.1 in Appendix B.5).

LLNのノードは、その動作のために6LBRに依存し、ルーティングレジストラーのサービスを使用する場合があります。偽装された6LBRが「Removed」ステータスコードを使用してネットワーク内の状態を破壊するブラックホール攻撃や爆撃攻撃などの脅威を避けるために、許可されたデバイスだけがこれらの役割で動作することを保証する信頼モデルを導入しなければなりません（MUST）。この信頼モデルは、最低限、レイヤー2のアクセス制御に基づくことができ、役割の検証も提供できます（Appendix B.5のReq-5.1を参照）。

8. Privacy Considerations

8. プライバシーに関する考慮事項

As indicated in Section 3, this protocol does not limit the number of IPv6 Addresses that each device can form. However, to mitigate denial-of-service attacks, it can be useful as a protective measure to have a limit that is high enough not to interfere with the normal behavior of devices in the network. A host should be able to form and register any address that is topologically correct in the subnet(s) advertised by the 6LR/6LBR.

Section 3で示したように、このプロトコルは、各デバイスが形成できるIPv6アドレスの数を制限しません。ただし、サービス拒否攻撃を緩和するために、ネットワーク内のデバイスの通常の振る舞いに干渉しない程度に十分高い上限を設けることは、保護手段として有用な場合があります。ホストは、6LR/6LBRが広告するサブネットにおいてトポロジー的に正しい任意のアドレスを形成して登録できるべきです。

This specification does not mandate any particular way for forming IPv6 Addresses, but it discourages using EUI-64 for forming the Interface Identifier in the Link-Local Address because this method prevents the usage of Secure Neighbor Discovery (SEND) [RFC3971], Cryptographically Generated Addresses (CGAs) [RFC3972], and other address privacy techniques.

この仕様は、IPv6アドレスを形成する特定の方法を義務付けませんが、リンクローカルアドレスのインターフェイス識別子を形成するためにEUI-64を使用することは推奨しません。この方法では、セキュア近隣探索（Secure Neighbor Discovery、SEND）[RFC3971]、暗号学的に生成されたアドレス（Cryptographically Generated Address、CGA）[RFC3972]、その他のアドレスのプライバシー技術が使用できなくなるためです。

[RFC8065] ("Privacy Considerations for IPv6 Adaptation-Layer Mechanisms") explains why privacy is important and how to form privacy-aware addresses. All implementations and deployments must consider the option of privacy addresses in their own environments.

[RFC8065]（「Privacy Considerations for IPv6 Adaptation-Layer Mechanisms」）は、プライバシーが重要である理由と、プライバシーに配慮したアドレスを形成する方法を説明しています。すべての実装と展開は、それぞれの環境においてプライバシーアドレスという選択肢を考慮する必要があります。

The IPv6 Address of the 6LN in the IPv6 header can be compressed statelessly when the Interface Identifier in the IPv6 Address can be derived from the lower-layer address. When it is not critical to benefit from that compression, e.g., the address can be compressed statefully, or it is rarely used and/or it is used only over one hop, privacy concerns should be considered. In particular, new implementations should follow [RFC8064] ("Recommendation on Stable IPv6 Interface Identifiers"). [RFC8064] recommends the mechanism specified in [RFC7217] ("A Method for Generating Semantically Opaque Interface Identifiers with IPv6 Stateless Address Autoconfiguration (SLAAC)") for generating Interface Identifiers to be used in SLAAC.

IPv6ヘッダー内の6LNのIPv6アドレスは、IPv6アドレスのインターフェイス識別子を下位層アドレスから導出できる場合、ステートレスに圧縮できます。その圧縮の恩恵を受けることが重要でない場合、たとえば、アドレスをステートフルに圧縮できる場合や、アドレスがまれにしか使用されない場合、1ホップでしか使用されない場合には、プライバシーの懸念を考慮すべきです。特に、新しい実装は[RFC8064]（「Recommendation on Stable IPv6 Interface Identifiers」）に従うべきです。[RFC8064]は、SLAACで使用するインターフェイス識別子を生成するために、[RFC7217]（「A Method for Generating Semantically Opaque Interface Identifiers with IPv6 Stateless Address Autoconfiguration (SLAAC)」）で規定されているメカニズムを推奨しています。

Appendix A. Applicability and Fulfilled Requirements (Not Normative)

Appendix A. 適用範囲と満たされる要件（規範的ではない）

This specification extends 6LoWPAN ND to provide a sequence number to the registration and fulfills the requirements expressed in Appendix B.1 by enabling the mobility of devices from one LLN to the next. A full specification for enabling mobility based on the use of the EARO and the registration procedures defined in this document can be found in subsequent work [IPv6-Backbone-Router] ("IPv6 Backbone Router"). The 6BBR is an example of a Routing Registrar that acts as an IPv6 ND proxy over a Backbone Link that federates multiple LLNs as well as the Backbone Link itself into a single IPv6 subnet. The expected registration flow in that case is illustrated in Figure 6, noting that any combination of 6LR, 6LBR, and 6BBR may be collocated.

この仕様は、登録にシーケンス番号を提供するように6LoWPAN NDを拡張し、あるLLNから次のLLNへのデバイスの移動を可能にすることで、Appendix B.1で表明された要件を満たします。EAROとこの文書で定義する登録手順の使用に基づいて移動を可能にするための完全な仕様は、後続の作業[IPv6-Backbone-Router]（「IPv6 Backbone Router」）にあります。6BBRは、複数のLLNとバックボーンリンク自体を単一のIPv6サブネットに連携させるバックボーンリンク上で、IPv6 NDプロキシーとして動作するルーティングレジストラーの例です。その場合に想定される登録フローをFigure 6に示します。なお、6LR、6LBR、6BBRは、どのような組み合わせでも同じ場所に配置できることに注意してください。

[Arch-for-6TiSCH] ("An Architecture for IPv6 over the TSCH mode of IEEE 802.15.4") describes how a 6LoWPAN ND host using the Time-Slotted Channel Hopping (TSCH) mode of IEEE Std. 802.15.4 [IEEE-802-15-4] can connect to the Internet via a RPL mesh network. Doing so requires additions to the 6LoWPAN ND protocol to support mobility and reachability in a secure and manageable network environment. This document specifies those new operations and fulfills the requirements listed in Appendix B.2.

[Arch-for-6TiSCH]（「An Architecture for IPv6 over the TSCH mode of IEEE 802.15.4」）は、IEEE Std. 802.15.4 [IEEE-802-15-4]のタイムスロットチャネルホッピング（Time-Slotted Channel Hopping、TSCH）モードを使用する6LoWPAN NDホストが、RPLメッシュネットワークを介してインターネットに接続する方法を説明しています。そのためには、安全で管理可能なネットワーク環境で移動性と到達可能性をサポートするための6LoWPAN NDプロトコルへの追加が必要です。この文書は、それらの新しい操作を規定し、Appendix B.2に列挙されている要件を満たします。

The term "LLN" is used loosely in this document and is intended to cover multiple types of WLANs and WPANs, including Low-Power IEEE Std. 802.11 networking, Bluetooth low energy, IEEE Std. 802.11ah, and IEEE Std. 802.15.4 wireless meshes, so as to address the requirements discussed in Appendix B.3.

「LLN」という用語は、この文書では緩やかに使用されており、Appendix B.3で議論されている要件に対処するために、低電力のIEEE Std. 802.11ネットワーク、Bluetooth Low Energy、IEEE Std. 802.11ah、IEEE Std. 802.15.4の無線メッシュなど、複数の種類のWLANとWPANをカバーすることを意図しています。

This specification can be used by any wireless node to register its IPv6 Addresses with a Routing Registrar and to obtain routing services such as proxy ND operations over a Backbone Link. This satisfies the requirements expressed in Appendix B.4.

この仕様は、任意の無線ノードが自身のIPv6アドレスをルーティングレジストラーに登録し、バックボーンリンク上でのプロキシーNDの操作などのルーティングサービスを得るために使用できます。これにより、Appendix B.4で表明された要件が満たされます。

This specification is extended by [AP-ND] to provide a solution to some of the security-related requirements expressed in Appendix B.5.

この仕様は、Appendix B.5で表明されたセキュリティー関連の要件の一部に対する解決策を提供するために、[AP-ND]によって拡張されます。

[ND-Optimizations] ("IPv6 Neighbor Discovery Optimizations for Wired and Wireless Networks") suggests that 6LoWPAN ND [RFC6775] can be extended to other types of links (beyond IEEE Std. 802.15.4) for which it was defined. The registration technique is beneficial when the link-layer technique used to carry IPv6 multicast packets is not sufficiently efficient in terms of delivery ratio or energy consumption in the end devices -- in particular, to enable energy-constrained sleeping nodes. The value of such an extension is especially apparent in the case of mobile wireless nodes, to reduce the multicast operations that are related to IPv6 ND [RFC4861] [RFC4862] and affect the operation of the wireless medium [Multicast-over-IEEE802-Wireless]. This fulfills the scalability requirements listed in Appendix B.6.

[ND-Optimizations]（「IPv6 Neighbor Discovery Optimizations for Wired and Wireless Networks」）は、6LoWPAN ND [RFC6775]を、それが定義された対象（IEEE Std. 802.15.4）以外の種類のリンクに拡張できることを示唆しています。登録の手法は、IPv6マルチキャストパケットを運ぶために使用されるリンク層の手法が、エンドデバイスにおける配送率やエネルギー消費の点で十分に効率的でない場合に有益です。特に、エネルギーに制約のあるスリープするノードを可能にするのに有益です。このような拡張の価値は、モバイル無線ノードの場合に特に明らかであり、IPv6 ND [RFC4861] [RFC4862]に関連し、無線媒体の動作に影響を与えるマルチキャスト操作[Multicast-over-IEEE802-Wireless]を削減できます。これにより、Appendix B.6に列挙されているスケーラビリティーの要件が満たされます。

Appendix B. Requirements (Not Normative)

Appendix B. 要件（規範的ではない）

This appendix lists requirements that were discussed by the 6lo Working Group for an update to 6LoWPAN ND. How those requirements are matched with existing specifications at the time of this writing is shown in Appendix B.8.

この付録では、6LoWPAN NDの更新のために6lo作業部会で議論された要件を列挙します。執筆時点で、それらの要件が既存の仕様とどのように対応しているかをAppendix B.8に示します。

B.1. Requirements Related to Mobility

B.1. 移動性に関する要件

Due to the unstable nature of LLN links, even in an LLN of immobile nodes, a 6LN may change its point of attachment from, say, 6LR-a to 6LR-b but may not be able to notify 6LR-a. Consequently, 6LR-a may still attract traffic that it cannot deliver any more. When links to a 6LR change state, there is thus a need to identify stale states in a 6LR and restore reachability in a timely fashion, e.g., by using some type of signaling upon detection of the movement or using a keep-alive mechanism with a period that is consistent with the needs of the application.

LLNのリンクは不安定であるため、移動しないノードで構成されるLLNであっても、6LNは、接続点をたとえば6LR-aから6LR-bに変更したにもかかわらず、6LR-aに通知できないことがあります。その結果、6LR-aは、もはや配送できないトラフィックを引き寄せ続ける可能性があります。したがって、6LRへのリンクの状態が変化した場合には、たとえば移動を検出した際に何らかのシグナリングを使用したり、アプリケーションのニーズに合った周期のキープアライブメカニズムを使用したりして、6LR内の古い状態を識別し、到達可能性を適時に回復する必要があります。

Req-1.1:
Upon a change of point of attachment, connectivity via a new 6LR MUST be restored in a timely fashion without the need to de-register from the previous 6LR.
Req-1.2:
For that purpose, the protocol MUST enable differentiating between multiple registrations from one 6LN and registrations from different 6LNs claiming the same address.
Req-1.3:
Stale states MUST be cleaned up in 6LRs.
Req-1.4:
A 6LN SHOULD also be able to register its address concurrently to multiple 6LRs.
Req-1.1:
接続点の変更時には、以前の6LRから登録解除する必要なく、新しい6LRを経由する接続性を適時に回復しなければなりません（MUST）。
Req-1.2:
そのために、プロトコルは、1つの6LNからの複数の登録と、同じアドレスを主張する異なる6LNからの登録とを区別できるようにしなければなりません（MUST）。
Req-1.3:
6LR内の古い状態はクリーンアップしなければなりません（MUST）。
Req-1.4:
6LNは、自身のアドレスを複数の6LRに同時に登録することもできるべきです（SHOULD）。

B.2. Requirements Related to Routing Protocols

B.2. ルーティングプロトコルに関する要件

The point of attachment of a 6LN may be a 6LR in an LLN mesh. IPv6 routing in an LLN can be based on RPL, which is the routing protocol that was defined by the IETF for this particular purpose. Other routing protocols are also considered by Standards Development Organizations (SDOs) on the basis of the expected network characteristics. It is required that a 6LN attached via ND to a 6LR indicate whether or not it (1) participates in the selected routing protocol to obtain reachability via the 6LR or (2) expects the 6LR to manage its reachability.

6LNの接続点は、LLNメッシュ内の6LRである場合があります。LLNにおけるIPv6ルーティングは、IETFがこの特定の目的のために定義したルーティングプロトコルであるRPLに基づくことができます。他のルーティングプロトコルも、想定されるネットワーク特性に基づいて、標準化団体（Standards Development Organization、SDO）によって検討されています。NDを介して6LRに接続された6LNは、(1) 6LRを経由する到達可能性を得るために選択されたルーティングプロトコルに参加するのか、それとも (2) 6LRが自身の到達可能性を管理することを期待するのかを示すことが要求されます。

The specified updates enable other specifications to define new services such as Source Address Validation Improvement (SAVI) (via [AP-ND]), participation as an unaware leaf to a routing protocol (such as the protocol described in [RFC6550] (RPL)) (via [Routing-for-RPL-Leaves]), and registration to Backbone Routers performing proxy ND in an LLN (via [IPv6-Backbone-Router]).

規定された更新により、他の仕様は、送信元アドレス検証の改善（Source Address Validation Improvement、SAVI）（[AP-ND]による）、ルーティングプロトコル（[RFC6550]で説明されているプロトコル（RPL）など）への非認識リーフとしての参加（[Routing-for-RPL-Leaves]による）、LLNでプロキシーNDを実行するバックボーンルーターへの登録（[IPv6-Backbone-Router]による）などの新しいサービスを定義できるようになります。

Beyond the 6LBR unicast address registered by ND, other addresses, including multicast addresses, are needed as well. For example, a routing protocol often uses a multicast address to register changes to established paths. ND needs to register such a multicast address to enable routing concurrently with discovery.

NDによって登録される6LBRのユニキャストアドレス以外にも、マルチキャストアドレスを含む他のアドレスも必要です。たとえば、ルーティングプロトコルは、確立された経路への変更を登録するためにマルチキャストアドレスをよく使用します。発見と同時にルーティングを可能にするために、NDはそのようなマルチキャストアドレスを登録する必要があります。

Multicast is needed for groups. Groups may be formed by device type (e.g., routers, street lamps), location (geography, RPL subtree), or both.

マルチキャストはグループのために必要です。グループは、デバイスの種類（たとえば、ルーター、街灯）、位置（地理、RPLのサブツリー）、またはその両方によって形成される場合があります。

The Bit Index Explicit Replication (BIER) architecture [RFC8279] proposes an optimized technique to enable multicast in an LLN with a very limited requirement for routing state in the nodes.

ビットインデックス明示的複製（Bit Index Explicit Replication、BIER）アーキテクチャー[RFC8279]は、ノードにおけるルーティング状態の要件を非常に限られたものにしつつ、LLNでマルチキャストを可能にする最適化された手法を提案しています。

Related requirements are as follows:

関連する要件は次のとおりです。

Req-2.1:
The ND registration method SHOULD be extended so that the 6LR is instructed whether to advertise the address of a 6LN over the selected routing protocol and obtain reachability to that address using the selected routing protocol.
Req-2.2:
Considering RPL, the ARO that is used in the ND registration SHOULD be extended to carry enough information to generate a DAO message as specified in Section 6.4 of [RFC6550] -- in particular, the capability to compute a Path Sequence and, as an option, a RPLInstanceID.
Req-2.3:
Multicast operations SHOULD be supported and optimized -- for instance, using BIER or the Multicast Protocol for Low-Power and Lossy Networks (MPL). Whether ND is appropriate for the registration to the Routing Registrar is to be defined, considering the additional burden of supporting Multicast Listener Discovery Version 2 (MLDv2) for IPv6 [RFC3810].
Req-2.1:
NDの登録方法は、6LNのアドレスを選択されたルーティングプロトコルで広告し、選択されたルーティングプロトコルを使用してそのアドレスへの到達可能性を得るかどうかを6LRに指示できるように拡張されるべきです（SHOULD）。
Req-2.2:
RPLを考慮すると、NDの登録で使用されるAROは、[RFC6550]のSection 6.4で規定されているDAOメッセージを生成するのに十分な情報、特に、パスシーケンス（Path Sequence）と、オプションとしてRPLInstanceIDを計算する能力を運ぶように拡張されるべきです（SHOULD）。
Req-2.3:
マルチキャスト操作は、たとえばBIERや低電力・高損失ネットワークのためのマルチキャストプロトコル（Multicast Protocol for Low-Power and Lossy Networks、MPL）を使用して、サポートされ最適化されるべきです（SHOULD）。IPv6のためのマルチキャストリスナー探索バージョン2（Multicast Listener Discovery Version 2、MLDv2）[RFC3810]をサポートする追加の負担を考慮して、ルーティングレジストラーへの登録にNDが適切かどうかは今後定義されます。

B.3. Requirements Related to Various Low-Power Link Types

B.3. さまざまな低電力リンクの種類に関する要件

6LoWPAN ND [RFC6775] was defined with a focus on IEEE Std.802.15.4 and, in particular, the capability to derive a unique identifier from a globally unique EUI-64 address. At this point, the 6lo Working Group is extending the 6LoWPAN Header Compression (HC) technique [RFC6282] to other link types, including ITU-T G.9959 [RFC7428], Master-Slave/Token-Passing [RFC8163], Digital Enhanced Cordless Telecommunications (DECT) Ultra Low Energy [RFC8105], Near Field Communication [IPv6-over-NFC], and IEEE Std. 802.11ah [IPv6-over-802.11ah], as well as Bluetooth low energy [RFC7668] and Power Line Communication (PLC) Networks [IPv6-over-PLC].

6LoWPAN ND [RFC6775]は、IEEE Std.802.15.4、特にグローバルに一意なEUI-64アドレスから一意な識別子を導出する能力に焦点を当てて定義されました。現時点で、6lo作業部会は、6LoWPANヘッダー圧縮（Header Compression、HC）の手法[RFC6282]を、ITU-T G.9959 [RFC7428]、Master-Slave/Token-Passing [RFC8163]、DECT（Digital Enhanced Cordless Telecommunications）Ultra Low Energy [RFC8105]、近距離無線通信（Near Field Communication）[IPv6-over-NFC]、IEEE Std. 802.11ah [IPv6-over-802.11ah]、さらにBluetooth Low Energy [RFC7668]や電力線通信（Power Line Communication、PLC）ネットワーク[IPv6-over-PLC]などの他の種類のリンクに拡張しています。

Related requirements are as follows:

関連する要件は次のとおりです。

Req-3.1:
The support of the registration mechanism SHOULD be extended to more LLN links than IEEE Std.802.15.4, matching at least the LLN links for which an "IPv6 over foo" specification exists, as well as low-power Wi-Fi.
Req-3.2:
As part of this extension, a mechanism to compute a unique identifier should be provided, with the capability to form a Link-Local Address that SHOULD be unique at least within the LLN connected to a 6LBR discovered by ND in each node within the LLN.
Req-3.3:
The ARO used in the ND registration SHOULD be extended to carry the relevant forms of the unique identifier.
Req-3.4:
ND should specify the formation of a site-local address that follows the security recommendations in [RFC7217].
Req-3.1:
登録メカニズムのサポートは、少なくとも「IPv6 over foo」仕様が存在するLLNリンクと低電力Wi-Fiに対応するように、IEEE Std.802.15.4よりも多くのLLNリンクに拡張されるべきです（SHOULD）。
Req-3.2:
この拡張の一部として、一意な識別子を計算するメカニズムが提供されるべきです。このメカニズムは、リンクローカルアドレスを形成する能力を備えたものとします。そのリンクローカルアドレスは、少なくとも、LLN内の各ノードでNDによって発見された6LBRに接続されたLLNの中では一意であるべきです（SHOULD）。
Req-3.3:
NDの登録で使用されるAROは、一意な識別子の関連する形式を運ぶように拡張されるべきです（SHOULD）。
Req-3.4:
NDは、[RFC7217]のセキュリティーの推奨事項に従ったサイトローカルアドレスの形成を規定すべきです。

B.4. Requirements Related to Proxy Operations

B.4. プロキシーの操作に関する要件

Duty-cycled devices may not be awake to answer a lookup from a node that uses IPv6 ND and may need a proxy. Additionally, the duty-cycled device may rely on the 6LBR to perform registration to the Routing Registrar.

デューティーサイクルで動作するデバイスは、IPv6 NDを使用するノードからの検索に応答するために起きていないことがあり、プロキシーが必要になる場合があります。さらに、デューティーサイクルで動作するデバイスは、ルーティングレジストラーへの登録を6LBRに頼ることがあります。

The ND registration method SHOULD defend the addresses of duty-cycled devices that are sleeping most of the time and incapable of defending their own addresses.

NDの登録方法は、ほとんどの時間スリープしていて自身のアドレスを防御できない、デューティーサイクルで動作するデバイスのアドレスを防御すべきです（SHOULD）。

Related requirements are as follows:

関連する要件は次のとおりです。

Req-4.1:
The registration mechanism SHOULD enable a third party to proxy-register an address on behalf of a 6LN that may be sleeping or located deeper in an LLN mesh.
Req-4.2:
The registration mechanism SHOULD be applicable to a duty-cycled device regardless of the link type and SHOULD enable a Routing Registrar to operate as a proxy to defend the Registered Addresses on its behalf.
Req-4.3:
The registration mechanism SHOULD enable long sleep durations, on the order of multiple days to a month.
Req-4.1:
登録メカニズムは、スリープしているか、LLNメッシュのより深い位置にある可能性のある6LNに代わって、第三者がアドレスを代理登録できるようにするべきです（SHOULD）。
Req-4.2:
登録メカニズムは、リンクの種類にかかわらず、デューティーサイクルで動作するデバイスに適用可能であるべきです（SHOULD）。また、ルーティングレジストラーがプロキシーとして動作し、そのデバイスに代わって登録アドレスを防御できるようにするべきです（SHOULD）。
Req-4.3:
登録メカニズムは、数日から1か月程度の長いスリープ期間を可能にするべきです（SHOULD）。

B.5. Requirements Related to Security

B.5. セキュリティーに関する要件

In order to guarantee the operations of the 6LoWPAN ND flows, spoofing the roles of the 6LR, 6LBR, and Routing Registrar should be avoided. Once a node successfully registers an address, 6LoWPAN ND should provide energy-efficient means for the 6LBR to protect that ownership even when the node that registered the address is sleeping.

6LoWPAN NDのフローの動作を保証するために、6LR、6LBR、およびルーティングレジストラーの役割のなりすましは避けるべきです。ノードがアドレスの登録に成功したら、6LoWPAN NDは、アドレスを登録したノードがスリープしている場合でも、6LBRがその所有権を保護するためのエネルギー効率の良い手段を提供すべきです。

In particular, the 6LR and the 6LBR should then be able to verify whether a subsequent registration for a given address comes from the original node.

特に、6LRと6LBRは、あるアドレスに対する後続の登録が元のノードからのものかどうかを検証できるべきです。

In an LLN, it makes sense to base security on Layer 2 security. During bootstrap of the LLN, nodes join the network after authorization by a Joining Assistant (JA) or a Commissioning Tool (CT). After joining, nodes communicate with each other via secured links. The keys for Layer 2 security are distributed by the JA/CT.

LLNでは、セキュリティーをレイヤー2のセキュリティーに基づかせることは理にかなっています。LLNのブートストラップ中、ノードは、参加支援者（Joining Assistant、JA）またはコミッショニングツール（Commissioning Tool、CT）による認可の後にネットワークに参加します。参加後、ノードは保護されたリンクを介して互いに通信します。レイヤー2のセキュリティーのための鍵は、JA/CTによって配布されます。

The JA/CT can be part of the LLN or be outside the LLN. In both cases, the ability to route packets between the JA/CT and the joining node is needed.

JA/CTは、LLNの一部である場合もあれば、LLNの外部にある場合もあります。どちらの場合も、JA/CTと参加するノードの間でパケットをルーティングする能力が必要です。

Related requirements are as follows:

関連する要件は次のとおりです。

Req-5.1:
6LoWPAN ND security mechanisms SHOULD provide a mechanism for the 6LR, 6LBR, and Routing Registrar to authenticate and authorize one another for their respective roles, as well as with the 6LN for the role of 6LR.
Req-5.2:
6LoWPAN ND security mechanisms SHOULD provide a mechanism for the 6LR and the 6LBR to validate new registrations of authorized nodes. Joining of unauthorized nodes MUST be prevented.
Req-5.3:
The use of 6LoWPAN ND security mechanisms SHOULD NOT result in large packet sizes. In particular, the NS, NA, DAR, and DAC messages for a re-registration flow SHOULD NOT exceed 80 octets so as to fit in a secured IEEE Std.802.15.4 [IEEE-802-15-4] frame.
Req-5.4:
Recurrent 6LoWPAN ND security operations MUST NOT be computationally intensive on the 6LN's CPU. When calculation of a key hash is employed, a mechanism lighter than SHA-1 SHOULD be used.
Req-5.5:
The number of keys that the 6LN needs to manipulate SHOULD be minimized.
Req-5.6:
6LoWPAN ND security mechanisms SHOULD enable (1) the variation of CCM ("Counter with CBC-MAC") [RFC3610] called "CCM*" for use at both Layer 2 and Layer 3 and (2) the reuse of a security code that has to be present on the device for upper-layer security (e.g., TLS). Algorithm agility and support for large keys (e.g., 256-bit key sizes) are also desirable.
Req-5.7:
Public key and signature sizes SHOULD be minimized while maintaining adequate confidentiality and data origin authentication for multiple types of applications with various degrees of criticality.
Req-5.8:
Routing of packets should continue when links pass from the unsecured state to the secured state.
Req-5.9:
6LoWPAN ND security mechanisms SHOULD provide a mechanism for the 6LR and the 6LBR to validate whether a new registration for a given address corresponds to the same 6LN that registered it initially and, if not, determine the rightful owner and deny or clean up the registration if it is a duplicate.
Req-5.1:
6LoWPAN NDのセキュリティーメカニズムは、6LR、6LBR、およびルーティングレジストラーが、それぞれの役割について互いを認証・認可するためのメカニズムと、6LRの役割について6LNとの間で認証・認可するためのメカニズムを提供するべきです（SHOULD）。
Req-5.2:
6LoWPAN NDのセキュリティーメカニズムは、6LRと6LBRが、許可されたノードの新しい登録を検証するためのメカニズムを提供するべきです（SHOULD）。許可されていないノードの参加は防止しなければなりません（MUST）。
Req-5.3:
6LoWPAN NDのセキュリティーメカニズムの使用によって、パケットサイズが大きくなるべきではありません（SHOULD NOT）。特に、再登録フローのためのNS、NA、DAR、およびDACメッセージは、保護されたIEEE Std.802.15.4 [IEEE-802-15-4]フレームに収まるように、80オクテットを超えるべきではありません（SHOULD NOT）。
Req-5.4:
6LoWPAN NDの繰り返し行われるセキュリティー操作は、6LNのCPUにとって計算負荷が高いものであってはなりません（MUST NOT）。鍵ハッシュの計算を用いる場合、SHA-1より軽量なメカニズムを使用すべきです（SHOULD）。
Req-5.5:
6LNが操作する必要のある鍵の数は、最小限にするべきです（SHOULD）。
Req-5.6:
6LoWPAN NDのセキュリティーメカニズムは、(1) レイヤー2とレイヤー3の両方で使用するための、「CCM*」と呼ばれるCCM（「Counter with CBC-MAC」）[RFC3610]の変種と、(2) 上位層のセキュリティー（たとえばTLS）のためにデバイス上に存在する必要のあるセキュリティーコードの再利用を可能にするべきです（SHOULD）。アルゴリズムの俊敏性と大きな鍵（たとえば256ビットの鍵サイズ）のサポートも望まれます。
Req-5.7:
公開鍵と署名のサイズは、重要度の異なる複数の種類のアプリケーションに対して適切な機密性とデータ発信元認証を維持しつつ、最小限にするべきです（SHOULD）。
Req-5.8:
リンクが保護されていない状態から保護された状態に移行する際にも、パケットのルーティングは継続されるべきです。
Req-5.9:
6LoWPAN NDのセキュリティーメカニズムは、あるアドレスに対する新しい登録が、最初にそのアドレスを登録したのと同じ6LNに対応するかどうかを6LRと6LBRが検証し、そうでない場合には正当な所有者を判断して、重複している登録を拒否またはクリーンアップするためのメカニズムを提供するべきです（SHOULD）。

B.6. Requirements Related to Scalability

B.6. スケーラビリティーに関する要件

Use cases from Automatic Meter Reading (AMR) (collection-tree operations) and Advanced Metering Infrastructure (AMI) (bidirectional communication to the meters) indicate the need for a large number of LLN nodes pertaining to a single RPL DODAG (e.g., 5000) and connected to the 6LBR over a large number of LLN hops (e.g., 15).

自動検針（Automatic Meter Reading、AMR）（コレクションツリーの操作）と高度計量インフラストラクチャー（Advanced Metering Infrastructure、AMI）（メーターとの双方向通信）のユースケースは、単一のRPL DODAGに属し（たとえば5000）、多数のLLNホップ（たとえば15）を介して6LBRに接続される多数のLLNノードが必要であることを示しています。

Related requirements are as follows:

関連する要件は次のとおりです。

Req-6.1:
The registration mechanism SHOULD enable a single 6LBR to register multiple thousands of devices.
Req-6.2:
The timing of the registration operation should allow for long latency, such as that found in LLNs with ten or more hops.
Req-6.1:
登録メカニズムは、単一の6LBRが数千のデバイスを登録できるようにするべきです（SHOULD）。
Req-6.2:
登録操作のタイミングは、10ホップ以上のLLNに見られるような長い遅延を許容すべきです。

B.7. Requirements Related to Operations and Management

B.7. 運用と管理に関する要件

Guideline 3.8 in Section 3 of [RFC1958] ("Architectural Principles of the Internet") recommends the following: "Avoid options and parameters whenever possible. Any options and parameters should be configured or negotiated dynamically rather than manually." This is especially true in LLNs where the number of devices may be large and manual configuration is infeasible. Capabilities for dynamic configuration of LLN devices can also be constrained by network and power limitations.

[RFC1958]のSection 3（「Architectural Principles of the Internet」）のガイドライン3.8は、次のことを推奨しています。「Avoid options and parameters whenever possible. Any options and parameters should be configured or negotiated dynamically rather than manually.（オプションやパラメーターは可能な限り避けてください。オプションやパラメーターは、手動ではなく動的に設定またはネゴシエートすべきです。）」これは、デバイスの数が多く、手動設定が不可能なLLNでは特に当てはまります。LLNデバイスの動的な設定の能力も、ネットワークと電力の制限によって制約される可能性があります。

A network administrator should be able to validate that the network is operating within capacity and that, in particular, a 6LBR does not get overloaded with an excessive amount of registrations, so the administrator can take actions such as adding a Backbone Link with additional 6LBRs and Routing Registrars to the network.

ネットワーク管理者は、ネットワークが容量の範囲内で動作していること、特に、6LBRが過剰な量の登録によって過負荷になっていないことを検証できるべきです。それにより、管理者は、追加の6LBRとルーティングレジストラーを備えたバックボーンリンクをネットワークに追加するなどの措置をとることができます。

Related requirements are as follows:

関連する要件は次のとおりです。

Req-7.1:
A management model SHOULD be provided that enables access to the 6LBR, monitors its usage vs. capacity, and sends alerts in the case of congestion. It is recommended that the 6LBR be reachable over a non-LLN link.
Req-7.2:
A management model SHOULD be provided that enables access to the 6LR and its capacity to host additional NCEs. This management model SHOULD avoid polling individual 6LRs in a way that could disrupt the operation of the LLN.
Req-7.3:
Information on successful and failed registrations SHOULD be provided, including information such as the ROVR of the 6LN, the Registered Address, the address of the 6LR, and the duration of the registration flow.
Req-7.4:
In the case of a failed registration, information on the failure, including the identification of the node that rejected the registration and the status in the EARO, SHOULD be provided.
Req-7.1:
6LBRへのアクセスを可能にし、容量に対する使用状況を監視し、輻輳の場合に警告を送信する管理モデルが提供されるべきです（SHOULD）。6LBRは、LLN以外のリンクを介して到達可能であることが推奨されます。
Req-7.2:
6LRと、追加のNCEを収容するその容量へのアクセスを可能にする管理モデルが提供されるべきです（SHOULD）。この管理モデルは、LLNの動作を妨げる可能性のある方法で個々の6LRをポーリングすることを避けるべきです（SHOULD）。
Req-7.3:
成功した登録と失敗した登録に関する情報が提供されるべきです（SHOULD）。これには、6LNのROVR、登録アドレス、6LRのアドレス、登録フローの所要時間などの情報が含まれます。
Req-7.4:
登録が失敗した場合、登録を拒否したノードの識別情報やEARO内のステータスを含む、失敗に関する情報が提供されるべきです（SHOULD）。
