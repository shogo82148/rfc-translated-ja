RFC 2111

Content-ID and Message-ID Uniform Resource Locators

RFC 2111

Content-IDとMessage-IDのURL（Uniform Resource Locator）

Abstract

概要

The Uniform Resource Locator (URL) schemes, "cid:" and "mid:" allow references to messages and the body parts of messages. For example, within a single multipart message, one HTML body part might include embedded references to other parts of the same message.

URL（Uniform Resource Locator）のスキームである「cid:」と「mid:」を使うと、メッセージやメッセージのボディーパートを参照できます。たとえば、1つのマルチパートメッセージの中で、あるHTMLボディーパートが、同じメッセージの他のパートへの参照を埋め込むことがあります。

このメモのステータス

1. Introduction

1. はじめに

The use of [MIME] within email to convey Web pages and their associated images requires a URL scheme to permit the HTML to refer to the images or other data included in the message. The Content-ID Uniform Resource Locator, "cid:", serves that purpose.

電子メールでWebページとそれに関連する画像を運ぶために[MIME]を使う場合、HTMLからメッセージに含まれる画像やその他のデータを参照できるようにするためのURLスキームが必要です。Content-ID URL（Uniform Resource Locator）である「cid:」は、その目的のためのものです。

Similarly Net News readers use Message-IDs to link related messages together. The Message-ID URL provides a scheme, "mid:", to refer to such messages as a "resource".

同様に、ネットニュースのリーダーは、関連するメッセージを結び付けるためにMessage-IDを使います。Message-ID URLは、そのようなメッセージを「リソース」として参照するためのスキーム「mid:」を提供します。

The "mid" (Message-ID) and "cid" (Content-ID) URL schemes provide identifiers for messages and their body parts. The "mid" scheme uses (a part of) the message-id of an email message to refer to a specific message. The "cid" scheme refers to a specific body part of a message; its use is generally limited to references to other body parts in the same message as the referring body part. The "mid" scheme may also refer to a specific body part within a designated message, by including the content-ID's address.

「mid」（Message-ID）と「cid」（Content-ID）のURLスキームは、メッセージとそのボディーパートの識別子を提供します。「mid」スキームは、電子メールメッセージのmessage-id（の一部）を使って特定のメッセージを参照します。「cid」スキームは、メッセージの特定のボディーパートを参照します。その用途は一般に、参照元のボディーパートと同じメッセージ内にある他のボディーパートへの参照に限られます。「mid」スキームは、content-IDのアドレスを含めることで、指定したメッセージ内の特定のボディーパートを参照することもできます。

A note on terminology. The terms "body part" and "MIME entity" are used interchangeably. They refer to the headers and body of a MIME message, either the message itself or one of the body parts contained in a Multipart message.

用語についての注記です。「ボディーパート（body part）」と「MIMEエンティティー（MIME entity）」という用語は、同じ意味で使います。これらは、MIMEメッセージのヘッダーとボディーを指します。メッセージそのものの場合も、マルチパートメッセージに含まれるボディーパートの1つの場合もあります。

2. The MID and CID URL Schemes

2. MIDとCIDのURLスキーム

RFC1738 [URL] reserves the "mid" and "cid" schemes for Message-ID and Content-ID respectively. This memorandum defines the syntax for those URLs. Because they use the same syntactic elements they are presented together.

RFC1738 [URL]は、「mid」と「cid」のスキームを、それぞれMessage-IDとContent-ID用に予約しています。このメモは、これらのURLの構文を定義します。両者は同じ構文要素を使うので、まとめて示します。

The URLs take the form

URLは次の形式をとります。

     content-id    = url-addr-spec

     message-id    = url-addr-spec

     url-addr-spec = addr-spec  ; URL encoding of RFC 822 addr-spec

     cid-url       = "cid" ":" content-id

     mid-url       = "mid" ":" message-id [ "/" content-id ]

     content-id    = url-addr-spec

     message-id    = url-addr-spec

     url-addr-spec = addr-spec  ; URL encoding of RFC 822 addr-spec

     cid-url       = "cid" ":" content-id

     mid-url       = "mid" ":" message-id [ "/" content-id ]

Note: in Internet mail messages, the addr-spec in a Content-ID [MIME] or Message-ID [822] header are enclosed in angle brackets (<>). Since addr-spec in a Message-ID or Content-ID might contain characters not allowed within a URL; any such character (including "/", which is reserved within the "mid" scheme) must be hex-encoded using the %hh escape mechanism in [URL].

注記: インターネットのメールメッセージでは、Content-ID [MIME]ヘッダーやMessage-ID [822]ヘッダーのaddr-specは山括弧（<>）で囲まれます。Message-IDやContent-IDのaddr-specには、URL内で許されない文字が含まれる可能性があるため、そのような文字（「mid」スキーム内で予約されている「/」を含む）は、[URL]の%hhエスケープ機構を使って16進エンコードしなければなりません。

A "mid" URL with only a "message-id" refers to an entire message. With the appended "content-id", it refers to a body part within a message, as does a "cid" URL. The Content-ID of a MIME body part is required to be globally unique. However, in many systems that store messages, body parts are not indexed independently their context (message). The "mid" URL long form was designed to supply the context needed to support interoperability with such systems.

「message-id」だけを含む「mid」URLは、メッセージ全体を参照します。「content-id」を付加すると、「cid」URLと同様に、メッセージ内のボディーパートを参照します。MIMEボディーパートのContent-IDは、グローバルに一意であることが求められています。しかし、メッセージを保存する多くのシステムでは、ボディーパートはそのコンテキスト（メッセージ）とは独立にインデックス付けされていません。「mid」URLの長い形式は、そのようなシステムとの相互運用性をサポートするのに必要なコンテキストを提供するために設計されました。

A implementation conforming to this specification is required to support the "mid" URL long form (message-id/content-id). Conforming implementations can choose to, but are not required to, take advantage of the content-id's uniqueness and interpret a "cid" URL to refer to any body part within the message store.

この仕様に準拠する実装は、「mid」URLの長い形式（message-id/content-id）をサポートすることが求められます。準拠する実装は、content-idの一意性を利用して、「cid」URLをメッセージストア内の任意のボディーパートを参照するものとして解釈することもできますが、それは必須ではありません。

In limited circumstances (e.g., within multipart/alternate), a single message may contain several body parts that have the same Content-ID. That occurs, for example, when identical data can be accessed through different methods [MIME, sect. 7.2.3]. In those cases, conforming implementations are required to use the rules of the containing MIME entity (e.g., multi-part/alternate) to select the body part to which the Content-ID refers.

限られた状況（たとえばmultipart/alternateの中）では、1つのメッセージに同じContent-IDを持つボディーパートが複数含まれることがあります。これはたとえば、同一のデータに異なる方法でアクセスできる場合に起こります[MIME, sect. 7.2.3]。そのような場合、準拠する実装は、Content-IDが参照するボディーパートを選ぶために、それを含むMIMEエンティティー（たとえばmulti-part/alternate）の規則を使うことが求められます。

A "cid" URL is converted to the corresponding Content-ID message header [MIME] by removing the "cid:" prefix, converting %hh hex-escaped characters to their ASCII equivalents and enclosing the remaining parts with an angle bracket pair, "<" and ">". For example, "mid:foo4%25foo1@bar.net" corresponds to

「cid」URLは、「cid:」接頭辞を取り除き、%hhで16進エスケープされた文字を対応するASCII文字に変換し、残りの部分を山括弧の組「<」と「>」で囲むことで、対応するContent-IDメッセージヘッダー[MIME]に変換されます。たとえば、「mid:foo4%25foo1@bar.net」は次のものに対応します。

     Message-ID: <foo4%foo1@bar.net>

     Message-ID: <foo4%foo1@bar.net>

A "mid" URL is converted to a Message-ID or Message-ID/Content-ID pair in a similar fashion.

「mid」URLも、同様の方法でMessage-ID、またはMessage-IDとContent-IDの組に変換されます。

Both message-id and content-id are required to be globally unique. That is, no two different messages will ever have the same Message-ID addr-spec; no different body parts will ever have the same Content-ID addr-spec. A common technique used by many message systems is to use a time and date stamp along with the local host's domain name, e.g., 950124.162336@XIson.com.

message-idとcontent-idはどちらも、グローバルに一意であることが求められています。つまり、異なる2つのメッセージが同じMessage-IDのaddr-specを持つことはなく、異なるボディーパートが同じContent-IDのaddr-specを持つことはありません。多くのメッセージシステムで使われている一般的な手法は、日付と時刻のスタンプをローカルホストのドメイン名と組み合わせて使うことです（例: 950124.162336@XIson.com）。

Some Examples

いくつかの例

The following message contains an HTML body part that refers to an image contained in another body part. Both body parts are contained in a Multipart/Related MIME entity. The HTML IMG tag contains a cidurl which points to the image.

次のメッセージには、別のボディーパートに含まれる画像を参照するHTMLボディーパートが含まれています。どちらのボディーパートも、Multipart/Related MIMEエンティティーに含まれています。HTMLのIMGタグには、画像を指すcidurlが含まれています。

     From: foo1@bar.net
     To: foo2@bar.net
     Subject: A simple example
     Mime-Version: 1.0
     Content-Type: multipart/related; boundary="boundary-example-1";
                   type=Text/HTML

     --boundary-example 1
     Content-Type: Text/HTML; charset=US-ASCII

     ... text of the HTML document, which might contain a hyperlink
     to the other body part, for example through a statement such as:
     <IMG SRC="cid:foo4*foo1@bar.net" ALT="IETF logo">

     --boundary-example-1
     Content-ID: foo4*foo1@bar.net
     Content-Type: IMAGE/GIF
     Content-Transfer-Encoding: BASE64

     R0lGODlhGAGgAPEAAP/////ZRaCgoAAAACH+PUNvcHlyaWdodCAoQykgMTk5
     NSBJRVRGLiBVbmF1dGhvcml6ZWQgZHVwbGljYXRpb24gcHJvaGliaXRlZC4A
     etc...

     --boundary-example-1--

     From: foo1@bar.net
     To: foo2@bar.net
     Subject: A simple example
     Mime-Version: 1.0
     Content-Type: multipart/related; boundary="boundary-example-1";
                   type=Text/HTML

     --boundary-example 1
     Content-Type: Text/HTML; charset=US-ASCII

     ... text of the HTML document, which might contain a hyperlink
     to the other body part, for example through a statement such as:
     <IMG SRC="cid:foo4*foo1@bar.net" ALT="IETF logo">

     --boundary-example-1
     Content-ID: foo4*foo1@bar.net

次のメッセージは、（受信者のメッセージストアにまだ残っていることを期待して）別のメッセージを指しています。

     From: bar@none.com
     To: phooey@all.com
     Subject: Here's how to do it
     Content-type: text/html; charset=usascii

3. Security Considerations

3. セキュリティーに関する考慮事項

The URLs defined here provide an addressing or referencing mechanism. The values of these URLs disclose no more about the originators environment than the corresponding Message-ID and Content-ID values. Where concern exists about such disclosures the originator of a message using mid and cid URLs must take precautions to insure that confidential information is not disclosed. Those precautions should already be in place to handle existing mail use of the Message-ID and Content-ID.

ここで定義するURLは、アドレス指定または参照の機構を提供します。これらのURLの値が発信者の環境について明らかにする情報は、対応するMessage-IDやContent-IDの値が明らかにするもの以上ではありません。そのような情報の開示が懸念される場合、midやcidのURLを使うメッセージの発信者は、機密情報が開示されないように予防措置をとらなければなりません。そのような予防措置は、Message-IDとContent-IDを使う既存のメールの利用に対処するために、すでに講じられているはずです。
