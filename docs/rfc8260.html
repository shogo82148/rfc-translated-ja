RFC 8260

Stream Schedulers and User Message Interleaving for the Stream Control Transmission Protocol

RFC 8260

ストリーム制御伝送プロトコルのストリームスケジューラーとユーザーメッセージのインターリーブ

Abstract

概要

The Stream Control Transmission Protocol (SCTP) is a message-oriented transport protocol supporting arbitrarily large user messages. This document adds a new chunk to SCTP for carrying payload data. This allows a sender to interleave different user messages that would otherwise result in head-of-line blocking at the sender. The interleaving of user messages is required for WebRTC data channels.

ストリーム制御伝送プロトコル（Stream Control Transmission Protocol、SCTP）は、任意の大きさのユーザーメッセージをサポートするメッセージ指向のトランスポートプロトコルです。この文書は、ペイロードデータを運ぶための新しいチャンクをSCTPに追加します。これにより、送信者は、そうしなければ送信者側でヘッドオブラインブロッキングを引き起こすことになる異なるユーザーメッセージを、インターリーブできるようになります。ユーザーメッセージのインターリーブは、WebRTCデータチャネルで必要とされています。

Whenever an SCTP sender is allowed to send user data, it may choose from multiple outgoing SCTP streams. Multiple ways for performing this selection, called stream schedulers, are defined in this document. A stream scheduler can choose to either implement, or not implement, user message interleaving.

SCTPの送信者がユーザーデータの送信を許可されているときはいつでも、送信者は複数の送信側SCTPストリームから選択できます。この文書では、ストリームスケジューラーと呼ばれる、この選択を行うための複数の方法を定義します。ストリームスケジューラーは、ユーザーメッセージのインターリーブを実装するかしないかを選択できます。

1. Introduction

1. はじめに

1.1. Overview

1.1. 概要

When SCTP [RFC4960] was initially designed, it was mainly envisioned for the transport of small signaling messages. Late in the design stage, it was decided to add support for fragmentation and reassembly of larger messages with the thought that someday signaling messages in the style of Session Initiation Protocol (SIP) [RFC3261] may also need to use SCTP, and a message that is a single Maximum Transmission Unit (MTU) would be too small. Unfortunately this design decision, though valid at the time, did not account for other applications that might send large messages over SCTP. The sending of such large messages over SCTP, as specified in [RFC4960], can result in a form of sender-side head-of-line blocking (e.g., when the transmission of a message is blocked from transmission because the sender has started the transmission of another, possibly large, message). This head-of-line blocking is caused by the use of the Transmission Sequence Number (TSN) for three different purposes:

SCTP[RFC4960]が最初に設計されたとき、SCTPは主に小さなシグナリングメッセージの転送を想定していました。設計段階の終盤になって、いつかSIP（Session Initiation Protocol）[RFC3261]のようなシグナリングメッセージもSCTPを使用する必要が生じ、単一の最大伝送単位（Maximum Transmission Unit、MTU）に収まるメッセージでは小さすぎるようになるかもしれないとの考えから、より大きなメッセージの断片化と再組み立てのサポートを追加することが決定されました。残念ながら、この設計上の決定は、当時は妥当なものでしたが、SCTP上で大きなメッセージを送信する可能性のある他のアプリケーションを考慮していませんでした。[RFC4960]で規定されているように、SCTP上でそのような大きなメッセージを送信すると、ある種の送信者側のヘッドオブラインブロッキング（head-of-line blocking）が発生する可能性があります（たとえば、送信者が別の（大きい可能性のある）メッセージの送信を開始したために、あるメッセージの送信が妨げられる場合）。このヘッドオブラインブロッキングは、伝送シーケンス番号（Transmission Sequence Number、TSN）を3つの異なる目的に使用していることが原因です。

  1. As an identifier for DATA chunks to provide a reliable transfer.
  2. As an identifier for the sequence of fragments to allow reassembly.
  3. As a sequence number allowing up to 2**16 - 1 Stream Sequence Numbers (SSNs) outstanding.
  1. 信頼性のある転送を提供するための、DATAチャンクの識別子として。
  2. 再組み立てを可能にするための、フラグメントの並びの識別子として。
  3. 最大2**16 - 1個の未処理（outstanding）のストリームシーケンス番号（Stream Sequence Number、SSN）を可能にするシーケンス番号として。

The protocol requires all fragments of a user message to have consecutive TSNs. This document allows an SCTP sender to interleave different user messages.

このプロトコルでは、ユーザーメッセージのすべてのフラグメントが連続したTSNを持つ必要があります。この文書は、SCTPの送信者が異なるユーザーメッセージをインターリーブできるようにします。

This document also defines several stream schedulers for general SCTP associations allowing different relative stream treatments. The stream schedulers may behave differently depending on whether or not user message interleaving has been negotiated for the association.

この文書では、一般的なSCTPアソシエーションのために、ストリームごとに異なる相対的な扱いを可能にするいくつかのストリームスケジューラーも定義します。ストリームスケジューラーは、そのアソシエーションでユーザーメッセージのインターリーブがネゴシエートされたかどうかに応じて、異なる動作をする場合があります。

Figure 1 illustrates the behavior of a round-robin stream scheduler using DATA chunks when three streams with the Stream Identifiers (SIDs) 0, 1, and 2 are used. Each queue for SID 0 and SID 2 contains a single user message requiring three chunks. The queue for SID 1 contains three user messages each requiring a single chunk. It is shown how these user messages are encapsulated in chunks using TSN 0 to TSN 8. Please note that the use of such a scheduler implies late TSN assignment, but it can be used with an implementation that is compliant with [RFC4960] and that does not support user message interleaving. Late TSN assignment means that the sender generates chunks from user messages and assigns the TSN as late as possible in the process of sending the user messages.

図1は、ストリーム識別子（Stream Identifier、SID）0、1、2の3つのストリームが使用される場合に、DATAチャンクを使用するラウンドロビンのストリームスケジューラーの動作を示しています。SID 0とSID 2のキューには、それぞれ3つのチャンクを必要とする1つのユーザーメッセージが含まれています。SID 1のキューには、それぞれ1つのチャンクを必要とする3つのユーザーメッセージが含まれています。この図は、これらのユーザーメッセージがTSN 0からTSN 8を使用してどのようにチャンクにカプセル化されるかを示しています。このようなスケジューラーを使用することは遅延TSN割り当て（late TSN assignment）を意味しますが、[RFC4960]に準拠し、ユーザーメッセージのインターリーブをサポートしない実装でも使用できることに注意してください。遅延TSN割り当てとは、送信者がユーザーメッセージからチャンクを生成し、ユーザーメッセージを送信する処理の中でできるだけ遅くTSNを割り当てることを意味します。

This document describes a new chunk carrying payload data called I-DATA. This chunk incorporates the properties of the current SCTP DATA chunk, all the flags and fields except the Stream Sequence Number (SSN), and also adds two new fields in its chunk header -- the Fragment Sequence Number (FSN) and the Message Identifier (MID). The FSN is only used for reassembling all fragments that have the same MID and the same ordering property. The TSN is only used for the reliable transfer in combination with Selective Acknowledgment (SACK) chunks.

この文書では、I-DATAと呼ばれる、ペイロードデータを運ぶ新しいチャンクについて説明します。このチャンクは、現在のSCTP DATAチャンクの性質と、ストリームシーケンス番号（SSN）を除くすべてのフラグとフィールドを取り入れ、さらにチャンクヘッダーに2つの新しいフィールド、フラグメントシーケンス番号（Fragment Sequence Number、FSN）とメッセージ識別子（Message Identifier、MID）を追加します。FSNは、同じMIDと同じ順序付けの性質を持つすべてのフラグメントを再組み立てするためだけに使用されます。TSNは、選択的確認応答（Selective Acknowledgment、SACK）チャンクと組み合わせた信頼性のある転送のためだけに使用されます。

In addition, the MID is also used for ensuring ordered delivery instead of using the stream sequence number (the I-DATA chunk omits an SSN).

さらに、MIDは、ストリームシーケンス番号を使用する代わりに、順序どおりの配送を保証するためにも使用されます（I-DATAチャンクはSSNを持ちません）。

Figure 2 illustrates the behavior of an interleaving round-robin stream scheduler using I-DATA chunks.

図2は、I-DATAチャンクを使用する、インターリーブを行うラウンドロビンのストリームスケジューラーの動作を示しています。

The support of the I-DATA chunk is negotiated during the association setup using the Supported Extensions Parameter, as defined in [RFC5061]. If I-DATA support has been negotiated for an association, I-DATA chunks are used for all user messages. DATA chunks are not permitted when I-DATA support has been negotiated. It should be noted that an SCTP implementation supporting I-DATA chunks needs to allow the coexistence of associations using DATA chunks and associations using I-DATA chunks.

I-DATAチャンクのサポートは、[RFC5061]で定義されているSupported Extensions Parameterを使用して、アソシエーションのセットアップ中にネゴシエートされます。アソシエーションでI-DATAのサポートがネゴシエートされた場合、すべてのユーザーメッセージにI-DATAチャンクが使用されます。I-DATAのサポートがネゴシエートされた場合、DATAチャンクは許可されません。I-DATAチャンクをサポートするSCTP実装は、DATAチャンクを使用するアソシエーションとI-DATAチャンクを使用するアソシエーションの共存を可能にする必要があることに注意してください。

In Section 2, this document specifies the user message interleaving by defining the I-DATA chunk, the procedures to use it, and its interactions with other SCTP extensions. Section 3 defines multiple stream schedulers, and Section 4 describes an extension to the socket API for using the mechanism specified in this document.

この文書では、セクション2で、I-DATAチャンク、その使用手順、および他のSCTP拡張との相互作用を定義することによって、ユーザーメッセージのインターリーブを規定します。セクション3では複数のストリームスケジューラーを定義し、セクション4では、この文書で規定するメカニズムを使用するためのソケットAPIの拡張について説明します。

2. User Message Interleaving

2. ユーザーメッセージのインターリーブ

The protocol mechanisms described in this document allow the interleaving of user messages sent on different streams. They do not support the interleaving of multiple messages (ordered or unordered) sent on the same stream.

この文書で説明するプロトコルメカニズムは、異なるストリームで送信されるユーザーメッセージのインターリーブを可能にします。同じストリームで送信される複数のメッセージ（順序付きまたは順序なし）のインターリーブはサポートしません。

The interleaving of user messages is required for WebRTC data channels, as specified in [DATA-CHAN].

[DATA-CHAN]で規定されているように、ユーザーメッセージのインターリーブはWebRTCデータチャネルで必要とされています。

An SCTP implementation supporting user message interleaving is REQUIRED to support the coexistence of associations using DATA chunks and associations using I-DATA chunks. If an SCTP implementation supports user message interleaving and the Partial Reliability extension described in [RFC3758] or the Stream Reconfiguration Extension described in [RFC6525], it is REQUIRED to implement the corresponding changes specified in Section 2.3.

ユーザーメッセージのインターリーブをサポートするSCTP実装は、DATAチャンクを使用するアソシエーションとI-DATAチャンクを使用するアソシエーションの共存をサポートすることが要求されています（REQUIRED）。SCTP実装が、ユーザーメッセージのインターリーブと、[RFC3758]で説明されている部分信頼性（Partial Reliability）拡張または[RFC6525]で説明されているストリーム再構成（Stream Reconfiguration）拡張をサポートする場合、セクション2.3で規定されている対応する変更を実装することが要求されています（REQUIRED）。

2.1. The I-DATA Chunk Supporting User Message Interleaving

2.1. ユーザーメッセージのインターリーブをサポートするI-DATAチャンク

The following Figure 3 shows the new I-DATA chunk allowing user message interleaving.

次の図3は、ユーザーメッセージのインターリーブを可能にする新しいI-DATAチャンクを示しています。

The only differences between the I-DATA chunk in Figure 3 and the DATA chunk defined in [RFC4960] and [RFC7053] are the addition of the new Message Identifier (MID) and the new Fragment Sequence Number (FSN) and the removal of the Stream Sequence Number (SSN). The Payload Protocol Identifier (PPID), which is already defined for DATA chunks in [RFC4960], and the new FSN are stored at the same location of the packet using the B bit to determine which value is stored at the location. The length of the I-DATA chunk header is 20 bytes, which is 4 bytes more than the length of the DATA chunk header defined in [RFC4960] and [RFC7053].

図3のI-DATAチャンクと、[RFC4960]と[RFC7053]で定義されているDATAチャンクとの違いは、新しいメッセージ識別子（MID）と新しいフラグメントシーケンス番号（FSN）が追加され、ストリームシーケンス番号（SSN）が削除されたことだけです。[RFC4960]でDATAチャンクに対してすでに定義されているペイロードプロトコル識別子（Payload Protocol Identifier、PPID）と新しいFSNは、パケットの同じ位置に格納され、その位置にどちらの値が格納されているかを判断するためにBビットを使用します。I-DATAチャンクヘッダーの長さは20バイトで、[RFC4960]と[RFC7053]で定義されているDATAチャンクヘッダーの長さより4バイト長くなっています。

The old fields are:

既存のフィールドは次のとおりです。

Res: 4 bits
These bits are reserved. They MUST be set to 0 by the sender and MUST be ignored by the receiver.
I bit: 1 bit
The (I)mmediate Bit, if set, indicates that the receiver SHOULD NOT delay the sending of the corresponding SACK chunk. Same as the I bit for DATA chunks, as specified in [RFC7053].
U bit: 1 bit
The (U)nordered bit, if set, indicates the user message is unordered. Same as the U bit for DATA chunks, as specified in [RFC4960].
B bit: 1 bit
The (B)eginning fragment bit, if set, indicates the first fragment of a user message. Same as the B bit for DATA chunks, as specified in [RFC4960].
E bit: 1 bit
The (E)nding fragment bit, if set, indicates the last fragment of a user message. Same as the E bit for DATA chunks, as specified in [RFC4960].
Length: 16 bits (unsigned integer)
This field indicates the length in bytes of the DATA chunk from the beginning of the Type field to the end of the User Data field, excluding any padding. Similar to the Length for DATA chunks, as specified in [RFC4960].
TSN: 32 bits (unsigned integer)
This value represents the TSN for this I-DATA chunk. Same as the TSN for DATA chunks, as specified in [RFC4960].
Stream Identifier: 16 bits (unsigned integer)
Identifies the stream to which the user data belongs. Same as the Stream Identifier for DATA chunks, as specified in [RFC4960].
Res: 4ビット
これらのビットは予約済みです。送信者はこれらのビットを0に設定しなければなりません（MUST）。受信者はこれらのビットを無視しなければなりません（MUST）。
I bit: 1ビット
(I)mmediateビットが設定されている場合、受信者は対応するSACKチャンクの送信を遅延させるべきではありません（SHOULD NOT）。[RFC7053]で規定されているDATAチャンクのIビットと同じです。
U bit: 1ビット
(U)norderedビットが設定されている場合、そのユーザーメッセージが順序なしであることを示します。[RFC4960]で規定されているDATAチャンクのUビットと同じです。
B bit: 1ビット
(B)eginning fragmentビットが設定されている場合、ユーザーメッセージの最初のフラグメントであることを示します。[RFC4960]で規定されているDATAチャンクのBビットと同じです。
E bit: 1ビット
(E)nding fragmentビットが設定されている場合、ユーザーメッセージの最後のフラグメントであることを示します。[RFC4960]で規定されているDATAチャンクのEビットと同じです。
Length: 16ビット（符号なし整数）
このフィールドは、Typeフィールドの先頭からUser Dataフィールドの末尾までの、パディングを除いたDATAチャンクの長さをバイト単位で示します。[RFC4960]で規定されているDATAチャンクのLengthと同様です。
TSN: 32ビット（符号なし整数）
この値は、このI-DATAチャンクのTSNを表します。[RFC4960]で規定されているDATAチャンクのTSNと同じです。
Stream Identifier: 16ビット（符号なし整数）
ユーザーデータが属するストリームを識別します。[RFC4960]で規定されているDATAチャンクのStream Identifierと同じです。

The new fields are:

新しいフィールドは次のとおりです。

Reserved: 16 bits (unsigned integer)
This field is reserved. It MUST be set to 0 by the sender and MUST be ignored by the receiver.
Message Identifier (MID): 32 bits (unsigned integer)
The MID is the same for all fragments of a user message; it is used to determine which fragments (enumerated by the FSN) belong to the same user message. For ordered user messages, the MID is also used by the SCTP receiver to deliver the user messages in the correct order to the upper layer (similar to the SSN of the DATA chunk defined in [RFC4960]). The sender uses two counters for each outgoing stream: one for ordered messages and one for unordered messages. All of these counters are independent and initially 0. They are incremented by 1 for each user message. Please note that the serial number arithmetic defined in [RFC1982] using SERIAL_BITS = 32 applies. Therefore, the sender MUST NOT have more than 2**31 - 1 ordered messages for each outgoing stream in flight and MUST NOT have more than 2**31 - 1 unordered messages for each outgoing stream in flight. A message is considered in flight if at least one of its I-DATA chunks is not acknowledged in a way that cannot be reneged (i.e., not acknowledged by the cumulative TSN Ack). Please note that the MID is in "network byte order", a.k.a. Big Endian.
Payload Protocol Identifier (PPID) / Fragment Sequence Number (FSN): 32 bits (unsigned integer)
If the B bit is set, this field contains the PPID of the user message. Note that in this case, this field is not touched by an SCTP implementation; therefore, its byte order is not necessarily in network byte order. The upper layer is responsible for any byte order conversions to this field, similar to the PPID of DATA chunks. In this case, the FSN is implicitly considered to be 0. If the B bit is not set, this field contains the FSN. The FSN is used to enumerate all fragments of a single user message, starting from 0 and incremented by 1. The last fragment of a message MUST have the E bit set. Note that the FSN MAY wrap completely multiple times, thus allowing arbitrarily large user messages. For the FSN, the serial number arithmetic defined in [RFC1982] applies with SERIAL_BITS = 32. Therefore, a sender MUST NOT have more than 2**31 - 1 fragments of a single user message in flight. A fragment is considered in flight if it is not acknowledged in a way that cannot be reneged. Please note that the FSN is in "network byte order", a.k.a. Big Endian.
Reserved: 16ビット（符号なし整数）
このフィールドは予約済みです。送信者はこのフィールドを0に設定しなければなりません（MUST）。受信者はこのフィールドを無視しなければなりません（MUST）。
Message Identifier (MID): 32ビット（符号なし整数）
MIDは、ユーザーメッセージのすべてのフラグメントで同じであり、（FSNによって番号付けされた）どのフラグメントが同じユーザーメッセージに属するかを判断するために使用されます。順序付きのユーザーメッセージの場合、MIDは、SCTPの受信者がユーザーメッセージを正しい順序で上位層に配送するためにも使用されます（[RFC4960]で定義されているDATAチャンクのSSNと同様です）。送信者は、送信ストリームごとに2つのカウンター、つまり順序付きメッセージ用のカウンターと順序なしメッセージ用のカウンターを使用します。これらのカウンターはすべて互いに独立しており、初期値は0です。カウンターはユーザーメッセージごとに1ずつ増加します。SERIAL_BITS = 32として[RFC1982]で定義されているシリアル番号演算が適用されることに注意してください。したがって、送信者は、各送信ストリームについて2**31 - 1個を超える順序付きメッセージを送信中（in flight）の状態にしてはなりません（MUST NOT）。また、各送信ストリームについて2**31 - 1個を超える順序なしメッセージを送信中の状態にしてはなりません（MUST NOT）。メッセージは、そのI-DATAチャンクのうち少なくとも1つが、取り消し（renege）できない方法で確認応答されていない（つまり、累積TSN確認応答（cumulative TSN Ack）によって確認応答されていない）場合に、送信中であるとみなされます。MIDは「ネットワークバイトオーダー」、別名ビッグエンディアンであることに注意してください。
Payload Protocol Identifier (PPID) / Fragment Sequence Number (FSN): 32ビット（符号なし整数）
Bビットが設定されている場合、このフィールドにはユーザーメッセージのPPIDが含まれます。この場合、このフィールドはSCTP実装によって変更されないため、そのバイトオーダーは必ずしもネットワークバイトオーダーではないことに注意してください。DATAチャンクのPPIDと同様に、このフィールドのバイトオーダー変換は上位層の責任です。この場合、FSNは暗黙的に0であるとみなされます。Bビットが設定されていない場合、このフィールドにはFSNが含まれます。FSNは、単一のユーザーメッセージのすべてのフラグメントに、0から始めて1ずつ増やしながら番号を付けるために使用されます。メッセージの最後のフラグメントでは、Eビットを設定しなければなりません（MUST）。FSNは完全に何度でもラップアラウンドしてもよいです（MAY）。これにより、任意の大きさのユーザーメッセージが可能になることに注意してください。FSNについては、SERIAL_BITS = 32として[RFC1982]で定義されているシリアル番号演算が適用されます。したがって、送信者は、単一のユーザーメッセージについて2**31 - 1個を超えるフラグメントを送信中の状態にしてはなりません（MUST NOT）。フラグメントは、取り消しできない方法で確認応答されていない場合に、送信中であるとみなされます。FSNは「ネットワークバイトオーダー」、別名ビッグエンディアンであることに注意してください。

2.2. Procedures

2.2. 手順

This subsection describes how the support of the I-DATA chunk is negotiated and how the I-DATA chunk is used by the sender and receiver.

このサブセクションでは、I-DATAチャンクのサポートをどのようにネゴシエートするか、および送信者と受信者がI-DATAチャンクをどのように使用するかについて説明します。

The handling of the I bit for the I-DATA chunk corresponds to the handling of the I bit for the DATA chunk described in [RFC7053].

I-DATAチャンクのIビットの扱いは、[RFC7053]で説明されているDATAチャンクのIビットの扱いに対応します。

2.2.1. Negotiation

2.2.1. ネゴシエーション

An SCTP endpoint indicates user message interleaving support by listing the I-DATA chunk within the Supported Extensions Parameter, as defined in [RFC5061]. User message interleaving has been negotiated for an association if both endpoints have indicated I-DATA support.

SCTPエンドポイントは、[RFC5061]で定義されているSupported Extensions ParameterにI-DATAチャンクを列挙することによって、ユーザーメッセージのインターリーブのサポートを示します。両方のエンドポイントがI-DATAのサポートを示した場合、そのアソシエーションでユーザーメッセージのインターリーブがネゴシエートされたことになります。

If user message interleaving support has been negotiated for an association, I-DATA chunks MUST be used for all user messages and DATA chunks MUST NOT be used. If user message interleaving support has not been negotiated for an association, DATA chunks MUST be used for all user messages and I-DATA chunks MUST NOT be used.

アソシエーションでユーザーメッセージのインターリーブのサポートがネゴシエートされた場合、すべてのユーザーメッセージにI-DATAチャンクを使用しなければなりません（MUST）。DATAチャンクを使用してはなりません（MUST NOT）。アソシエーションでユーザーメッセージのインターリーブのサポートがネゴシエートされなかった場合、すべてのユーザーメッセージにDATAチャンクを使用しなければなりません（MUST）。I-DATAチャンクを使用してはなりません（MUST NOT）。

An endpoint implementing the socket API specified in [RFC6458] MUST NOT indicate user message interleaving support unless the user has requested its use (e.g., via the socket API; see Section 4.3). This constraint is made since the usage of this chunk requires that the application is capable of handling interleaved messages upon reception within an association. This is not the default choice within the socket API (see the SCTP_FRAGMENT_INTERLEAVE socket option in Section 8.1.20 of [RFC6458]); thus, the user MUST indicate to the SCTP implementation its support for receiving completely interleaved messages.

[RFC6458]で規定されているソケットAPIを実装するエンドポイントは、ユーザーが（たとえば、ソケットAPIを介して。セクション4.3を参照）その使用を要求しない限り、ユーザーメッセージのインターリーブのサポートを示してはなりません（MUST NOT）。この制約は、このチャンクを使用するには、アプリケーションがアソシエーション内でインターリーブされたメッセージを受信時に処理できる必要があるために設けられています。これはソケットAPIにおけるデフォルトの選択ではありません（[RFC6458]のセクション8.1.20のSCTP_FRAGMENT_INTERLEAVEソケットオプションを参照）。そのため、ユーザーは、完全にインターリーブされたメッセージの受信をサポートしていることをSCTP実装に示さなければなりません（MUST）。

Note that stacks that do not implement [RFC6458] may use other methods to indicate interleaved message support and thus indicate the support of user message interleaving. The crucial point is that the SCTP stack MUST know that the application can handle interleaved messages before indicating the I-DATA support.

[RFC6458]を実装していないスタックは、インターリーブされたメッセージのサポートを示し、それによってユーザーメッセージのインターリーブのサポートを示すために、他の方法を使用する場合があることに注意してください。重要な点は、SCTPスタックが、I-DATAのサポートを示す前に、アプリケーションがインターリーブされたメッセージを処理できることを知っていなければなりません（MUST）ということです。

2.2.2. Sender-Side Considerations

2.2.2. 送信者側の考慮事項

The sender-side usage of the I-DATA chunk is quite simple. Instead of using the TSN for fragmentation purposes, the sender uses the new FSN field to indicate which fragment number is being sent. The first fragment MUST have the B bit set. The last fragment MUST have the E bit set. All other fragments MUST NOT have the B or E bit set. All other properties of the existing SCTP DATA chunk also apply to the I-DATA chunk, i.e., congestion control as well as receiver window conditions MUST be observed, as defined in [RFC4960].

送信者側でのI-DATAチャンクの使用方法は非常に単純です。送信者は、断片化の目的でTSNを使用する代わりに、新しいFSNフィールドを使用して、送信しているフラグメントの番号を示します。最初のフラグメントでは、Bビットを設定しなければなりません（MUST）。最後のフラグメントでは、Eビットを設定しなければなりません（MUST）。それ以外のすべてのフラグメントでは、BビットもEビットも設定してはなりません（MUST NOT）。既存のSCTP DATAチャンクのその他すべての性質もI-DATAチャンクに適用されます。つまり、[RFC4960]で定義されているように、輻輳制御と受信者ウィンドウの条件を守らなければなりません（MUST）。

Note that the usage of this chunk implies the late assignment of the actual TSN to any chunk being sent. Each I-DATA chunk uses a single TSN. This way messages from other streams may be interleaved with the fragmented message. Please note that this is the only form of interleaving support. For example, it is not possible to interleave multiple ordered or unordered user messages from the same stream.

このチャンクを使用することは、送信されるすべてのチャンクに対して実際のTSNを遅れて割り当てることを意味することに注意してください。各I-DATAチャンクは1つのTSNを使用します。このようにして、他のストリームのメッセージを、断片化されたメッセージとインターリーブできます。これが唯一のインターリーブのサポート形態であることに注意してください。たとえば、同じストリームの複数の順序付きまたは順序なしのユーザーメッセージをインターリーブすることはできません。

The sender MUST NOT process (move user data into I-DATA chunks and assign a TSN to it) more than one user message in any given stream at any time. At any time, a sender MAY process multiple user messages, each of them on different streams.

送信者は、どの時点でも、ある1つのストリームにおいて2つ以上のユーザーメッセージを処理（ユーザーデータをI-DATAチャンクに移し、それにTSNを割り当てること）してはなりません（MUST NOT）。送信者は、どの時点でも、それぞれ異なるストリーム上にある複数のユーザーメッセージを処理してもよいです（MAY）。

The sender MUST assign TSNs to I-DATA chunks in a way that the receiver can make progress. One way to achieve this is to assign a higher TSN to the later fragments of a user message and send out the I-DATA chunks such that the TSNs are in sequence.

送信者は、受信者が処理を進められるような方法で、I-DATAチャンクにTSNを割り当てなければなりません（MUST）。これを実現する1つの方法は、ユーザーメッセージの後のフラグメントほど大きなTSNを割り当て、TSNが順番になるようにI-DATAチャンクを送り出すことです。

2.2.3. Receiver-Side Considerations

2.2.3. 受信者側の考慮事項

Upon reception of an SCTP packet containing an I-DATA chunk whose user message needs to be reassembled, the receiver MUST first use the SID to identify the stream, consider the U bit to determine if it is part of an ordered or unordered message, find the user message identified by the MID, and use the FSN for reassembly of the message and not the TSN. The receiver MUST NOT make any assumption about the TSN assignments of the sender. Note that a non-fragmented message is indicated by the fact that both the E and B bits are set. A message (either ordered or unordered) whose E and B bits are not both set may be identified as being fragmented.

再組み立てが必要なユーザーメッセージのI-DATAチャンクを含むSCTPパケットを受信したとき、受信者はまず、SIDを使用してストリームを識別し、Uビットを考慮してそれが順序付きメッセージと順序なしメッセージのどちらの一部であるかを判断し、MIDで識別されるユーザーメッセージを見つけ、TSNではなくFSNを使用してメッセージを再組み立てしなければなりません（MUST）。受信者は、送信者のTSNの割り当てについて何も仮定してはなりません（MUST NOT）。断片化されていないメッセージは、EビットとBビットの両方が設定されていることによって示されることに注意してください。EビットとBビットの両方が設定されてはいない（順序付きまたは順序なしの）メッセージは、断片化されているものと識別できます。

If I-DATA support has been negotiated for an association, the reception of a DATA chunk is a violation of the above rules and therefore the receiver of the DATA chunk MUST abort the association by sending an ABORT chunk. The ABORT chunk MAY include the 'Protocol Violation' error cause. The same applies if I-DATA support has not been negotiated for an association and an I-DATA chunk is received.

アソシエーションでI-DATAのサポートがネゴシエートされている場合、DATAチャンクの受信は上記の規則に違反しているため、DATAチャンクの受信者はABORTチャンクを送信してアソシエーションを中断しなければなりません（MUST）。ABORTチャンクには、「Protocol Violation」エラー原因を含めてもよいです（MAY）。アソシエーションでI-DATAのサポートがネゴシエートされておらず、I-DATAチャンクを受信した場合にも同じことが当てはまります。

2.3. Interaction with Other SCTP Extensions

2.3. 他のSCTP拡張との相互作用

The usage of the I-DATA chunk might interfere with other SCTP extensions. Future SCTP extensions MUST describe if and how they interfere with the usage of I-DATA chunks. For the SCTP extensions already defined when this document was published, the details are given in the following subsections.

I-DATAチャンクの使用は、他のSCTP拡張に干渉する可能性があります。将来のSCTP拡張は、I-DATAチャンクの使用に干渉するかどうか、およびどのように干渉するかを記述しなければなりません（MUST）。この文書の発行時点ですでに定義されているSCTP拡張については、以降のサブセクションで詳細を示します。

2.3.1. SCTP Partial Reliability Extension

2.3.1. SCTP部分信頼性拡張

When the SCTP extension defined in [RFC3758] is used in combination with the user message interleaving extension, the new I-FORWARD-TSN chunk MUST be used instead of the FORWARD-TSN chunk. The difference between the FORWARD-TSN and the I-FORWARD-TSN chunk is that the 16-bit Stream Sequence Number (SSN) has been replaced by the 32-bit Message Identifier (MID), and the largest skipped MID can also be provided for unordered messages. Therefore, the principle applied to ordered messages when using FORWARD-TSN chunks is applied to ordered and unordered messages when using I-FORWARD-TSN chunks.

[RFC3758]で定義されているSCTP拡張をユーザーメッセージのインターリーブ拡張と組み合わせて使用する場合、FORWARD-TSNチャンクの代わりに新しいI-FORWARD-TSNチャンクを使用しなければなりません（MUST）。FORWARD-TSNチャンクとI-FORWARD-TSNチャンクの違いは、16ビットのストリームシーケンス番号（SSN）が32ビットのメッセージ識別子（MID）に置き換えられ、順序なしメッセージについてもスキップされた最大のMIDを提供できることです。したがって、FORWARD-TSNチャンクを使用する場合に順序付きメッセージに適用される原則が、I-FORWARD-TSNチャンクを使用する場合には順序付きメッセージと順序なしメッセージに適用されます。

The old fields are:

既存のフィールドは次のとおりです。

Flags: 8 bits (unsigned integer)
These bits are reserved. They MUST be set to 0 by the sender and MUST be ignored by the receiver. Same as the Flags for FORWARD TSN chunks, as specified in [RFC3758].
Length: 16 bits (unsigned integer)
This field holds the length of the chunk. Similar to the Length for FORWARD TSN chunks, as specified in [RFC3758].
New Cumulative TSN: 32 bits (unsigned integer)
This indicates the New Cumulative TSN to the data receiver. Same as the New Cumulative TSN for FORWARD TSN chunks, as specified in [RFC3758].
Flags: 8ビット（符号なし整数）
これらのビットは予約済みです。送信者はこれらのビットを0に設定しなければなりません（MUST）。受信者はこれらのビットを無視しなければなりません（MUST）。[RFC3758]で規定されているFORWARD TSNチャンクのFlagsと同じです。
Length: 16ビット（符号なし整数）
このフィールドはチャンクの長さを保持します。[RFC3758]で規定されているFORWARD TSNチャンクのLengthと同様です。
New Cumulative TSN: 32ビット（符号なし整数）
これは、データ受信者に新しい累積TSN（New Cumulative TSN）を示します。[RFC3758]で規定されているFORWARD TSNチャンクのNew Cumulative TSNと同じです。

The new fields are:

新しいフィールドは次のとおりです。

Stream Identifier (SID): 16 bits (unsigned integer)
This field holds the stream number this entry refers to.
Reserved: 15 bits
This field is reserved. It MUST be set to 0 by the sender and MUST be ignored by the receiver.
U bit: 1 bit
The U bit specifies if the Message Identifier of this entry refers to unordered messages (U bit is set) or ordered messages (U bit is not set).
Message Identifier (MID): 32 bits (unsigned integer)
This field holds the largest Message Identifier for ordered or unordered messages indicated by the U bit that was skipped for the stream specified by the Stream Identifier. For ordered messages, this is similar to the FORWARD-TSN chunk, just replacing the 16-bit SSN by the 32-bit MID.
Stream Identifier (SID): 16ビット（符号なし整数）
このフィールドは、このエントリーが参照するストリーム番号を保持します。
Reserved: 15ビット
このフィールドは予約済みです。送信者はこのフィールドを0に設定しなければなりません（MUST）。受信者はこのフィールドを無視しなければなりません（MUST）。
U bit: 1ビット
Uビットは、このエントリーのMessage Identifierが、順序なしメッセージ（Uビットが設定されている）と順序付きメッセージ（Uビットが設定されていない）のどちらを参照するかを指定します。
Message Identifier (MID): 32ビット（符号なし整数）
このフィールドは、Stream Identifierで指定されたストリームについてスキップされた、Uビットで示される順序付きまたは順序なしメッセージの最大のMessage Identifierを保持します。順序付きメッセージの場合、これはFORWARD-TSNチャンクと同様であり、16ビットのSSNを32ビットのMIDに置き換えただけです。

Support for the I-FORWARD-TSN chunk is negotiated during the SCTP association setup via the Supported Extensions Parameter, as defined in [RFC5061]. The partial reliability extension is negotiated and can be used in combination with user message interleaving only if both endpoints indicated their support of user message interleaving and the I-FORWARD-TSN chunk.

I-FORWARD-TSNチャンクのサポートは、[RFC5061]で定義されているSupported Extensions Parameterを介して、SCTPアソシエーションのセットアップ中にネゴシエートされます。部分信頼性拡張がネゴシエートされ、ユーザーメッセージのインターリーブと組み合わせて使用できるのは、両方のエンドポイントがユーザーメッセージのインターリーブとI-FORWARD-TSNチャンクのサポートを示した場合だけです。

The FORWARD-TSN chunk MUST be used in combination with the DATA chunk and MUST NOT be used in combination with the I-DATA chunk. The I-FORWARD-TSN chunk MUST be used in combination with the I-DATA chunk and MUST NOT be used in combination with the DATA chunk.

FORWARD-TSNチャンクは、DATAチャンクと組み合わせて使用しなければなりません（MUST）。I-DATAチャンクと組み合わせて使用してはなりません（MUST NOT）。I-FORWARD-TSNチャンクは、I-DATAチャンクと組み合わせて使用しなければなりません（MUST）。DATAチャンクと組み合わせて使用してはなりません（MUST NOT）。

If I-FORWARD-TSN support has been negotiated for an association, the reception of a FORWARD-TSN chunk is a violation of the above rules and therefore the receiver of the FORWARD-TSN chunk MUST abort the association by sending an ABORT chunk. The ABORT chunk MAY include the 'Protocol Violation' error cause. The same applies if I-FORWARD-TSN support has not been negotiated for an association and a FORWARD-TSN chunk is received.

アソシエーションでI-FORWARD-TSNのサポートがネゴシエートされている場合、FORWARD-TSNチャンクの受信は上記の規則に違反しているため、FORWARD-TSNチャンクの受信者はABORTチャンクを送信してアソシエーションを中断しなければなりません（MUST）。ABORTチャンクには、「Protocol Violation」エラー原因を含めてもよいです（MAY）。アソシエーションでI-FORWARD-TSNのサポートがネゴシエートされておらず、FORWARD-TSNチャンクを受信した場合にも同じことが当てはまります。

2.3.2. SCTP Stream Reconfiguration Extension

2.3.2. SCTPストリーム再構成拡張

When an association resets the SSN using the SCTP extension defined in [RFC6525], the two counters (one for the ordered messages, one for the unordered messages) used for the MIDs MUST be reset to 0.

アソシエーションが[RFC6525]で定義されているSCTP拡張を使用してSSNをリセットする場合、MIDに使用される2つのカウンター（順序付きメッセージ用と順序なしメッセージ用）を0にリセットしなければなりません（MUST）。

Since most schedulers, especially all schedulers supporting user message interleaving, require late TSN assignment, it should be noted that the implementation of [RFC6525] needs to handle this.

ほとんどのスケジューラー、特にユーザーメッセージのインターリーブをサポートするすべてのスケジューラーは遅延TSN割り当てを必要とするため、[RFC6525]の実装はこれに対処する必要があることに注意してください。

3. Stream Schedulers

3. ストリームスケジューラー

This section defines several stream schedulers. The stream schedulers may behave differently depending on whether or not user message interleaving has been negotiated for the association. An implementation MAY implement any subset of them. If the implementation is used for WebRTC data channels, as specified in [DATA-CHAN], it MUST implement the Weighted Fair Queueing Scheduler defined in Section 3.6.

このセクションでは、いくつかのストリームスケジューラーを定義します。ストリームスケジューラーは、そのアソシエーションでユーザーメッセージのインターリーブがネゴシエートされたかどうかに応じて、異なる動作をする場合があります。実装は、これらのスケジューラーの任意のサブセットを実装してもよいです（MAY）。[DATA-CHAN]で規定されているWebRTCデータチャネルにその実装が使用される場合、その実装はセクション3.6で定義されている重み付け公平キューイングスケジューラー（Weighted Fair Queueing Scheduler）を実装しなければなりません（MUST）。

The selection of the stream scheduler is done at the sender side. There is no mechanism provided for signaling the stream scheduler being used to the receiver side or even for letting the receiver side influence the selection of the stream scheduler used at the sender side.

ストリームスケジューラーの選択は送信者側で行われます。使用しているストリームスケジューラーを受信者側に通知するためのメカニズムや、送信者側で使用するストリームスケジューラーの選択に受信者側が影響を与えるためのメカニズムは提供されていません。

3.1. First-Come, First-Served Scheduler (SCTP_SS_FCFS)

3.1. 先着順スケジューラー（SCTP_SS_FCFS）

The simple first-come, first-served scheduler of user messages is used. It just passes through the messages in the order in which they have been delivered by the application. No modification of the order is done at all. The usage of user message interleaving does not affect the sending of the chunks, except that I-DATA chunks are used instead of DATA chunks.

ユーザーメッセージの単純な先着順（first-come, first-served）スケジューラーが使用されます。このスケジューラーは、アプリケーションから渡された順序でメッセージをそのまま通過させるだけです。順序の変更はまったく行われません。ユーザーメッセージのインターリーブを使用しても、DATAチャンクの代わりにI-DATAチャンクが使用されることを除いて、チャンクの送信には影響しません。

3.2. Round-Robin Scheduler (SCTP_SS_RR)

3.2. ラウンドロビンスケジューラー（SCTP_SS_RR）

When not interleaving user messages, this scheduler provides a fair scheduling based on the number of user messages by cycling around non-empty stream queues. When interleaving user messages, this scheduler provides a fair scheduling based on the number of I-DATA chunks by cycling around non-empty stream queues.

ユーザーメッセージをインターリーブしない場合、このスケジューラーは、空でないストリームキューを巡回することによって、ユーザーメッセージの数に基づく公平なスケジューリングを提供します。ユーザーメッセージをインターリーブする場合、このスケジューラーは、空でないストリームキューを巡回することによって、I-DATAチャンクの数に基づく公平なスケジューリングを提供します。

3.3. Round-Robin Scheduler per Packet (SCTP_SS_RR_PKT)

3.3. パケット単位のラウンドロビンスケジューラー（SCTP_SS_RR_PKT）

This is a round-robin scheduler, which only switches streams when starting to fill a new packet. It bundles only DATA or I-DATA chunks referring to the same stream in a packet. This scheduler minimizes head-of-line blocking when a packet is lost because only a single stream is affected.

これはラウンドロビンスケジューラーであり、新しいパケットを埋め始めるときにだけストリームを切り替えます。このスケジューラーは、同じストリームを参照するDATAチャンクまたはI-DATAチャンクだけを1つのパケットにバンドルします。パケットが失われた場合に影響を受けるのは単一のストリームだけであるため、このスケジューラーはヘッドオブラインブロッキングを最小限に抑えます。

3.4. Priority-Based Scheduler (SCTP_SS_PRIO)

3.4. 優先度ベースのスケジューラー（SCTP_SS_PRIO）

Scheduling of user messages with strict priorities is used. The priority is configurable per outgoing SCTP stream. Streams having a higher priority will be scheduled first and when multiple streams have the same priority, the scheduling between them is implementation dependent. When the scheduler interleaves user messages, the sending of large, lower-priority user messages will not delay the sending of higher-priority user messages.

厳密な優先度によるユーザーメッセージのスケジューリングが使用されます。優先度は、送信SCTPストリームごとに設定できます。より高い優先度を持つストリームが先にスケジュールされ、複数のストリームが同じ優先度を持つ場合、それらの間のスケジューリングは実装依存です。スケジューラーがユーザーメッセージをインターリーブする場合、優先度の低い大きなユーザーメッセージの送信が、優先度の高いユーザーメッセージの送信を遅延させることはありません。

3.5. Fair Capacity Scheduler (SCTP_SS_FC)

3.5. 公平容量スケジューラー（SCTP_SS_FC）

A fair capacity distribution between the streams is used. This scheduler considers the lengths of the messages of each stream and schedules them in a specific way to maintain an equal capacity for all streams. The details are implementation dependent. interleaving user messages allows for a better realization of the fair capacity usage.

ストリーム間での公平な容量の配分が使用されます。このスケジューラーは、各ストリームのメッセージの長さを考慮し、すべてのストリームで等しい容量を維持するように特定の方法でメッセージをスケジュールします。詳細は実装依存です。ユーザーメッセージをインターリーブすることで、公平な容量の利用をよりよく実現できます。

3.6. Weighted Fair Queueing Scheduler (SCTP_SS_WFQ)

3.6. 重み付け公平キューイングスケジューラー（SCTP_SS_WFQ）

A Weighted Fair Queueing scheduler between the streams is used. The weight is configurable per outgoing SCTP stream. This scheduler considers the lengths of the messages of each stream and schedules them in a specific way to use the capacity according to the given weights. If the weight of stream S1 is n times the weight of stream S2, the scheduler should assign to stream S1 n times the capacity it assigns to stream S2. The details are implementation dependent. Interleaving user messages allows for a better realization of the capacity usage according to the given weights.

ストリーム間で重み付け公平キューイング（Weighted Fair Queueing）スケジューラーが使用されます。重みは、送信SCTPストリームごとに設定できます。このスケジューラーは、各ストリームのメッセージの長さを考慮し、与えられた重みに従って容量を使用するように特定の方法でメッセージをスケジュールします。ストリームS1の重みがストリームS2の重みのn倍である場合、スケジューラーは、ストリームS2に割り当てる容量のn倍の容量をストリームS1に割り当てるべきです。詳細は実装依存です。ユーザーメッセージをインターリーブすることで、与えられた重みに従った容量の利用をよりよく実現できます。

This scheduler, in combination with user message interleaving, is used for WebRTC data channels, as specified in [DATA-CHAN].

[DATA-CHAN]で規定されているように、このスケジューラーは、ユーザーメッセージのインターリーブと組み合わせて、WebRTCデータチャネルで使用されます。

6. Security Considerations

6. セキュリティーに関する考慮事項

This document does not add any additional security considerations in addition to the ones given in [RFC4960] and [RFC6458].

この文書は、[RFC4960]と[RFC6458]で示されているものに加えて、セキュリティーに関する考慮事項を追加するものではありません。

It should be noted that the application has to consent that it is willing to do the more complex reassembly support required for user message interleaving. When doing so, an application has to provide a reassembly buffer for each incoming stream. It has to protect itself against these buffers taking too many resources. If user message interleaving is not used, only a single reassembly buffer needs to be provided for each association. But the application has to protect itself for excessive resource usages there too.

アプリケーションは、ユーザーメッセージのインターリーブに必要な、より複雑な再組み立てのサポートを行うことに同意する必要があることに注意してください。その場合、アプリケーションは、受信ストリームごとに再組み立てバッファーを用意する必要があります。アプリケーションは、これらのバッファーが過剰なリソースを消費しないように自らを保護する必要があります。ユーザーメッセージのインターリーブを使用しない場合、アソシエーションごとに再組み立てバッファーを1つだけ用意すれば十分です。しかし、その場合でも、アプリケーションは過剰なリソース使用から自らを保護する必要があります。
