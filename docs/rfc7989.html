RFC 7989

End-to-End Session Identification in IP-Based Multimedia Communication Networks

RFC 7989

IPベースのマルチメディア通信ネットワークにおけるエンドツーエンドのセッション識別

Abstract

概要

This document describes an end-to-end session identifier for use in IP-based multimedia communication systems that enables endpoints, intermediary devices, and management systems to identify a session end-to-end, associate multiple endpoints with a given multipoint conference, track communication sessions when they are redirected, and associate one or more media flows with a given communication session. While the identifier is intended to work across multiple protocols, this document describes its usage in the Session Initiation Protocol (SIP).

この文書は、IPベースのマルチメディア通信システムで使用するエンドツーエンドのセッション識別子について記述します。 この識別子により、エンドポイント、仲介装置、管理システムは、セッションをエンドツーエンドで識別し、複数のエンドポイントを特定の多地点会議に関連付け、リダイレクトされた通信セッションを追跡し、1つ以上のメディアフローを特定の通信セッションに関連付けることができます。 この識別子は複数のプロトコルにまたがって機能することを意図していますが、この文書ではセッション開始プロトコル（SIP）での使用方法を記述します。

This document also describes a backwards-compatibility mechanism for an existing session identifier implementation (RFC 7329) that is sufficiently different from the procedures defined in this document.

この文書では、この文書で定義する手順とは大きく異なる既存のセッション識別子の実装（RFC 7329）に対する後方互換性のメカニズムについても記述します。

This document obsoletes RFC 7329.

この文書はRFC 7329を廃止します。

1. Introduction

1. はじめに

IP-based multimedia communication systems, such as Session Initiation Protocol (SIP) [RFC3261] and [H.323], have the concept of a "call identifier" that is globally unique. The identifier is intended to represent an end-to-end communication session from the originating device to the terminating device. Such an identifier is useful for troubleshooting, session tracking, and so forth.

セッション開始プロトコル（SIP）[RFC3261]や[H.323]などのIPベースのマルチメディア通信システムには、グローバルに一意な「呼識別子（call identifier）」という概念があります。 この識別子は、発信側の装置から着信側の装置までのエンドツーエンドの通信セッションを表すことを意図しています。 このような識別子は、トラブルシューティングやセッションの追跡などに役立ちます。

For several reasons, however, the current call identifiers defined in SIP and H.323 are not suitable for end-to-end session identification. A fundamental issue in protocol interworking is the fact that the syntax for the call identifier in SIP and H.323 is different. Thus, if both protocols are used in a call, it is impossible to exchange the call identifier end-to-end.

しかし、いくつかの理由から、SIPとH.323で定義されている現在の呼識別子は、エンドツーエンドのセッション識別には適していません。 プロトコルの相互接続における根本的な問題は、SIPとH.323で呼識別子の構文が異なることです。 したがって、1つの通話で両方のプロトコルが使われる場合、呼識別子をエンドツーエンドで交換することはできません。

Another reason why the current call identifiers are not suitable to identify a session end-to-end is that, in real-world deployments, devices such as session border controllers [RFC7092] often change the session signaling, including the value of the call identifier, as it passes through the device. While this is deliberate and useful, it makes it very difficult to track a session end-to-end.

現在の呼識別子がセッションをエンドツーエンドで識別するのに適していないもう1つの理由は、実際の展開では、セッションボーダーコントローラー[RFC7092]などの装置が、セッションのシグナリングが装置を通過する際に、呼識別子の値を含めてそれを変更することがよくあるからです。 これは意図的で有用なことですが、セッションをエンドツーエンドで追跡することを非常に困難にします。

This document defines a new identifier, referred to as the "session identifier", that is intended to overcome the issues that exist with the currently defined call identifiers used in SIP and other IP-based communication systems. The identifier defined here has been adopted by the ITU ([H.460.27]) for use in H.323-based systems, allowing for the ability to trace a session end-to-end for sessions traversing both SIP and H.323-based systems. This document defines its use in SIP.

この文書では、SIPやその他のIPベースの通信システムで使われている、現在定義されている呼識別子に存在する問題を克服することを意図した、「セッション識別子（session identifier）」と呼ばれる新しい識別子を定義します。 ここで定義する識別子は、H.323ベースのシステムで使用するためにITU（[H.460.27]）によって採用されており、SIPとH.323ベースのシステムの両方を通過するセッションについて、セッションをエンドツーエンドで追跡できるようになっています。 この文書では、SIPにおけるその使用方法を定義します。

The procedures specified in this document attempt to comply with the requirements specified in [RFC7206]. The procedures also specify capabilities not mentioned in [RFC7206], shown in the call flows in Section 10. Additionally, this specification attempts to account for a previous, pre-standard version of a SIP session identifier header [RFC7329], specifying a backwards-compatibility approach in Section 11.

この文書で規定する手順は、[RFC7206]で規定された要件に準拠することを目指しています。 また、この手順では、[RFC7206]で言及されていない機能も規定しており、それらはセクション10のコールフローで示します。 さらに、この仕様では、SIPセッション識別子ヘッダーの以前の標準化前のバージョン[RFC7329]を考慮し、セクション11で後方互換性のためのアプローチを規定しています。

The term "session identifier" refers to the value of the identifier, whereas "Session-ID" refers to the header field used to convey the identifier. The session identifier is a set of two Universally Unique Identifiers (UUIDs) and each element of that set is simply referred to herein as a "UUID".

「セッション識別子（session identifier）」という用語は識別子の値を指し、「Session-ID」はその識別子を伝えるために使われるヘッダーフィールドを指します。 セッション識別子は2つのUUID（Universally Unique Identifier）の組であり、この組の各要素をこの文書では単に「UUID」と呼びます。

Throughout this document, the term "endpoint" refers to a SIP User Agent (UA) that either initiates or terminates a SIP session, such as a user's mobile phone or a conference server, but excludes entities such as Back-to-Back User Agents (B2BUAs) that are generally located along the call-signaling path between endpoints. The term "intermediary" refers to any entity along the call-signaling path between the aforementioned endpoints, including B2BUAs and SIP proxies. In certain scenarios, intermediaries are allowed to originate and terminate SIP messages without an endpoint being part of the session or transaction. An intermediary may be performing interworking between different protocols (e.g., SIP and H.323) that support the session identifier defined in this document.

この文書全体を通じて、「エンドポイント（endpoint）」という用語は、ユーザーの携帯電話や会議サーバーのように、SIPセッションを開始または終端するSIPユーザーエージェント（UA）を指します。 ただし、一般にエンドポイント間の呼シグナリング経路上に位置するバックツーバックユーザーエージェント（B2BUA）などのエンティティーは除きます。 「仲介者（intermediary）」という用語は、前述のエンドポイント間の呼シグナリング経路上にある、B2BUAやSIPプロキシーを含むあらゆるエンティティーを指します。 特定のシナリオでは、仲介者は、エンドポイントがセッションやトランザクションに加わっていなくても、SIPメッセージを発信および終端することが許されています。 仲介者は、この文書で定義するセッション識別子をサポートする異なるプロトコル（たとえば、SIPとH.323）の間で相互接続を行っている場合があります。

エンドツーエンドのセッション識別子の要件とユースケース、ならびに「セッション識別子（session identifier）」、「通信セッション（communication session）」、「エンドツーエンド（end-to-end）」の定義は、[RFC7206]にあります。 この文書全体を通じて、「セッション」という用語は、[RFC7206]で定義されている「通信セッション」を指します。

As mentioned in Section 6.1 of [RFC7206], the ITU-T undertook a parallel effort to define compatible procedures for an H.323 session identifier. They are documented in [H.460.27].

[RFC7206]のセクション6.1で述べられているように、ITU-Tは、H.323のセッション識別子について互換性のある手順を定義する取り組みを並行して行いました。 それらは[H.460.27]に文書化されています。

4. Constructing and Conveying the Session Identifier

4. セッション識別子の構築と伝達

4.1. Constructing the Session Identifier

4.1. セッション識別子の構築

The session identifier comprises two UUIDs [RFC4122], with each UUID representing one of the endpoints participating in the session.

セッション識別子は2つのUUID[RFC4122]で構成され、各UUIDはセッションに参加しているエンドポイントの1つを表します。

The version number in the UUID indicates the manner in which the UUID is generated, such as using random values or using the Media Access Control (MAC) address of the endpoint. To satisfy the requirement that no user or device information be conveyed, endpoints MUST generate version 4 (random) or version 5 (SHA-1) UUIDs to address privacy concerns related to the use of MAC addresses in UUIDs.

UUIDのバージョン番号は、ランダムな値を使用する、エンドポイントのMAC（Media Access Control）アドレスを使用するなど、UUIDの生成方法を示します。 ユーザーや装置の情報を伝えないという要件を満たすため、UUIDにMACアドレスを使用することに関するプライバシーの懸念に対処するために、エンドポイントはバージョン4（ランダム）またはバージョン5（SHA-1）のUUIDを生成しなければなりません（MUST）。

When generating a version 5 UUID, endpoints or intermediaries MUST utilize the procedures defined in Section 4.3 of [RFC4122] and employ the following "namespace ID":

バージョン5のUUIDを生成する場合、エンドポイントまたは仲介者は、[RFC4122]のセクション4.3で定義されている手順を利用し、次の「名前空間ID（namespace ID）」を使用しなければなりません（MUST）。

uuid_t NameSpace_SessionID = {
    /* a58587da-c93d-11e2-ae90-f4ea67801e29 */
    0xa58587da,
    0xc93d,
    0x11e2,
    0xae, 0x90, 0xf4, 0xea, 0x67, 0x80, 0x1e, 0x29
};

uuid_t NameSpace_SessionID = {
    /* a58587da-c93d-11e2-ae90-f4ea67801e29 */
    0xa58587da,
    0xc93d,
    0x11e2,
    0xae, 0x90, 0xf4, 0xea, 0x67, 0x80, 0x1e, 0x29
};

Further, the "name" to utilize for version 5 UUIDs is the concatenation of the Call-ID header-value and the "tag" parameter that appears on the "From" or "To" line associated with the device for which the UUID is created. Once an endpoint generates a UUID for a session, the UUID never changes, even if values originally used as input into its construction change over time.

さらに、バージョン5のUUIDに使用する「名前（name）」は、Call-IDのヘッダー値と、UUIDを作成する対象の装置に関連付けられた「From」行または「To」行に現れる「tag」パラメーターとを連結したものです。 エンドポイントがセッションのUUIDを一度生成したら、その構築の入力として最初に使用した値が時間とともに変化したとしても、そのUUIDが変わることはありません。

Stateless intermediaries that insert a Session-ID header field into a SIP message on behalf of an endpoint MUST utilize version 5 UUIDs to ensure that UUIDs for the communication session are consistently generated. If a stateless intermediary does not know the tag value for the endpoint (e.g., a new INVITE request without a To: tag value or an older SIP implementation [RFC2543] that did not include a "tag" parameter), the intermediary MUST NOT attempt to generate a UUID for that endpoint. Note that, if an intermediary is stateless and the endpoint on one end of the call is replaced with another endpoint due to some service interaction, the values used to create the UUID should change and, if so, the intermediary will compute a different UUID.

エンドポイントに代わってSIPメッセージにSession-IDヘッダーフィールドを挿入するステートレスな仲介者は、通信セッションのUUIDが一貫して生成されるように、バージョン5のUUIDを利用しなければなりません（MUST）。 ステートレスな仲介者がエンドポイントのtag値を知らない場合（たとえば、To:のtag値のない新しいINVITEリクエストや、「tag」パラメーターを含めない古いSIP実装[RFC2543]の場合）、仲介者はそのエンドポイントのUUIDを生成しようとしてはなりません（MUST NOT）。 仲介者がステートレスであり、何らかのサービスインタラクションによって通話の一方の端のエンドポイントが別のエンドポイントに置き換えられた場合、UUIDの作成に使われる値は変わるはずであり、その場合、仲介者は異なるUUIDを計算することに注意してください。

4.2. Conveying the Session Identifier

4.2. セッション識別子の伝達

The SIP User Agent (UA) initiating a new session by transmitting a SIP request ("Alice"), i.e., a User Agent Client (UAC), MUST create a new, previously unused UUID and transmit that to the ultimate destination UA ("Bob"). Likewise, the destination UA ("Bob"), i.e., a User Agent Server (UAS), MUST create a new, previously unused UUID and transmit that to the first UA ("Alice"). These two distinct UUIDs form what is referred to as the "session identifier" and is represented in this document in set notation of the form {A,B}, where "A" is UUID value created by UA "Alice" and "B" is the UUID value created by UA "Bob". The session identifier {A,B} is equal to the session identifier {B,A}. Section 6 describes how the UUIDs selected by the source and destination UAs persist for the duration of the session.

SIPリクエストを送信して新しいセッションを開始するSIPユーザーエージェント（UA）（「Alice」）、つまりユーザーエージェントクライアント（UAC）は、これまで使用されていない新しいUUIDを作成し、それを最終的な宛先のUA（「Bob」）に送信しなければなりません（MUST）。 同様に、宛先のUA（「Bob」）、つまりユーザーエージェントサーバー（UAS）は、これまで使用されていない新しいUUIDを作成し、それを最初のUA（「Alice」）に送信しなければなりません（MUST）。 これら2つの異なるUUIDが「セッション識別子」と呼ばれるものを形成し、この文書では{A,B}という形式の集合表記で表します。 ここで、「A」はUA「Alice」が作成したUUID値、「B」はUA「Bob」が作成したUUID値です。 セッション識別子{A,B}はセッション識別子{B,A}と等しくなります。 送信元と宛先のUAが選択したUUIDがセッションの期間中どのように維持されるかは、セクション6で説明します。

In the case where only one UUID is known, such as when a UA first initiates a potentially dialog-initiating SIP request, the session identifier would be {A,N}, where "A" represents the UUID value transmitted by the UA "Alice", and "N" is what is referred to as the "nil UUID" [RFC4122] (see Section 5 of this document).

UAがダイアログを開始する可能性のあるSIPリクエストを最初に開始するときのように、1つのUUIDしかわかっていない場合、セッション識別子は{A,N}となります。 ここで、「A」はUA「Alice」が送信したUUID値を表し、「N」は「nil UUID」[RFC4122]と呼ばれるものです（この文書のセクション5を参照してください）。

Since SIP sessions are subject to any number of service interactions, SIP INVITE requests might be forked as sessions are established, and since conferences might be established or expanded with endpoints calling in or the conference focus calling out, the construction of the session identifier as a set of UUIDs is important.

SIPセッションは任意の数のサービスインタラクションの対象となり、セッションの確立時にSIP INVITEリクエストがフォークされる可能性があり、またエンドポイントがコールインしたり会議フォーカスがコールアウトしたりすることで会議が確立または拡張される可能性があるため、セッション識別子をUUIDの組として構築することが重要です。

To understand this better, consider that an endpoint participating in a communication session might be replaced with another, such as the case where two "legs" of a call are joined together by a Private Branch Exchange (PBX). Suppose "Alice" and "Bob" both call UA "C" ("Carol"). There would be two distinctly identifiable session identifiers, namely {A,C} and {B,C}. Then, suppose that "Carol" uses a local PBX function to join the call between herself and "Alice" with the call between herself and "Bob", resulting in a single remaining call between "Alice" and "Bob". This merged call can be identified using two UUID values assigned by each entity in the communication session, namely {A,B} in this example.

これをよりよく理解するために、通信セッションに参加しているエンドポイントが別のエンドポイントに置き換えられる場合を考えてみてください。 たとえば、構内交換機（PBX）によって通話の2つの「レッグ」が結合される場合です。 「Alice」と「Bob」がともにUA「C」（「Carol」）に電話をかけたとします。 この場合、明確に識別可能な2つのセッション識別子、すなわち{A,C}と{B,C}が存在します。 次に、「Carol」がローカルのPBX機能を使って、自分と「Alice」の間の通話を自分と「Bob」の間の通話と結合し、その結果「Alice」と「Bob」の間の1つの通話だけが残ったとします。 この結合された通話は、通信セッションの各エンティティーが割り当てた2つのUUID値、すなわちこの例では{A,B}を使用して識別できます。

In the case of forking, "Alice" might send an INVITE request that gets forked to several different endpoints. A means of identifying each of these separate communication sessions is needed; since each of the destination UAs will create its own UUID, each communication session would be uniquely identified by the values {A, B1}, {A, B2}, {A, B3}, and so on, where each of the Bn values refers to the UUID created by the different UAs to which the SIP session is forked.

フォークの場合、「Alice」は、いくつかの異なるエンドポイントにフォークされるINVITEリクエストを送信することがあります。 これらの個別の通信セッションのそれぞれを識別する手段が必要です。 宛先のUAはそれぞれ独自のUUIDを作成するため、各通信セッションは{A, B1}、{A, B2}、{A, B3}などの値によって一意に識別されます。 ここで、各Bnの値は、SIPセッションのフォーク先である異なるUAが作成したUUIDを指します。

For conferencing scenarios, it is also useful to have a two-part session identifier where the conference focus specifies the same UUID for each conference participant. This allows for correlation among the participants in a single conference. For example, in a conference with three participants, the session identifiers might be {A,M}, {B,M}, and {C,M}, where "M" is assigned by the conference focus. Only a conference focus will purposely utilize the same UUID for more than one SIP session and, even then, such reuse MUST be restricted to the participants in the same conference.

会議のシナリオでも、会議フォーカスが会議の各参加者に同じUUIDを指定する2つの部分からなるセッション識別子があると便利です。 これにより、1つの会議の参加者間で相関をとることができます。 たとえば、3人の参加者がいる会議では、セッション識別子は{A,M}、{B,M}、{C,M}となり、「M」は会議フォーカスによって割り当てられます。 意図的に同じUUIDを複数のSIPセッションに利用するのは会議フォーカスだけであり、その場合でも、そのような再利用は同じ会議の参加者に限定しなければなりません（MUST）。

How a device acting on session identifiers processes or utilizes the session identifier is outside the scope of this document. However, devices storing a session identifier in a log file SHOULD follow the security considerations outlined in [RFC6872]. Note that the primary intent of a session identifier is for troubleshooting; therefore, it should be included in logs at rest that will be used for troubleshooting purposes.

セッション識別子を扱う装置がセッション識別子をどのように処理または利用するかは、この文書の範囲外です。 ただし、セッション識別子をログファイルに保存する装置は、[RFC6872]に概説されているセキュリティーに関する考慮事項に従うべきです（SHOULD）。 セッション識別子の主な目的はトラブルシューティングであることに注意してください。 したがって、トラブルシューティングの目的で使用される保存済みのログには、セッション識別子を含めるべきです。

5. The Session-ID Header Field

5. Session-IDヘッダーフィールド

This document replaces the definition of the "Session-ID" token that was added to the definition of the element "message-header" in the SIP message grammar by [RFC7329]. The Session-ID header is a single-instance header.

この文書は、[RFC7329]によってSIPメッセージ文法の要素「message-header」の定義に追加された「Session-ID」トークンの定義を置き換えます。 Session-IDヘッダーは、単一インスタンスのヘッダーです。

Each endpoint participating in a communication session has a distinct, preferably locally generated UUID associated with it. The endpoint's UUID value remains unchanged throughout the duration of the communication session. Multipoint conferences can bridge sessions from multiple endpoints and impose unique requirements defined in Section 9. An intermediary MAY generate a UUID on behalf of an endpoint that did not include a UUID of its own.

通信セッションに参加している各エンドポイントには、それぞれ異なる、できればローカルで生成されたUUIDが関連付けられています。 エンドポイントのUUID値は、通信セッションの期間中変わりません。 多地点会議は複数のエンドポイントからのセッションをブリッジすることができ、セクション9で定義する独自の要件を課します。 仲介者は、自身のUUIDを含めなかったエンドポイントに代わってUUIDを生成してもよいです（MAY）。

The UUID values for each endpoint are inserted into the Session-ID header field of all transmitted SIP messages. The Session-ID header field has the following ABNF [RFC5234] syntax:

各エンドポイントのUUID値は、送信されるすべてのSIPメッセージのSession-IDヘッダーフィールドに挿入されます。 Session-IDヘッダーフィールドは、次のABNF[RFC5234]構文を持ちます。

session-id          = "Session-ID" HCOLON session-id-value

session-id-value    = local-uuid *(SEMI sess-id-param)

local-uuid          = sess-uuid / nil

remote-uuid         = sess-uuid / nil

sess-uuid           = 32(DIGIT / %x61-66)  ;32 chars of [0-9a-f]

sess-id-param       = remote-param / generic-param

remote-param        = "remote" EQUAL remote-uuid

nil                 = 32("0")

session-id          = "Session-ID" HCOLON session-id-value

session-id-value    = local-uuid *(SEMI sess-id-param)

local-uuid          = sess-uuid / nil

remote-uuid         = sess-uuid / nil

sess-uuid           = 32(DIGIT / %x61-66)  ;32 chars of [0-9a-f]

sess-id-param       = remote-param / generic-param

remote-param        = "remote" EQUAL remote-uuid

nil                 = 32("0")

The productions "SEMI", "EQUAL", and "generic-param" are defined in [RFC3261]. The production DIGIT is defined in [RFC5234].

生成規則「SEMI」、「EQUAL」、「generic-param」は[RFC3261]で定義されています。 生成規則DIGITは[RFC5234]で定義されています。

The Session-ID header field MUST NOT have more than one "remote" parameter. In the case where an entity compliant with this specification is interworking with an entity that implemented a session identifier as defined in [RFC7329], the "remote" parameter may be absent; otherwise, the "remote" parameter MUST be present. The details under which those conditions apply are described in Section 11. Except for backwards compatibility with [RFC7329], the "remote" parameter MUST be present.

Session-IDヘッダーフィールドは、複数の「remote」パラメーターを持ってはなりません（MUST NOT）。 この仕様に準拠したエンティティーが、[RFC7329]で定義されたセッション識別子を実装したエンティティーと相互接続している場合は、「remote」パラメーターが存在しないことがあります。 それ以外の場合、「remote」パラメーターは存在しなければなりません（MUST）。 これらの条件が適用される詳細は、セクション11で説明します。 [RFC7329]との後方互換性の場合を除き、「remote」パラメーターは存在しなければなりません（MUST）。

A special nil UUID value composed of 32 zeros is required in certain situations. A nil UUID is expected as the "remote-uuid" of every initial standard SIP request since the initiating endpoint would not initially know the UUID value of the remote endpoint. This nil value will get replaced by the ultimate destination UAS when that UAS generates a response message. One caveat is explained in Section 11 for a possible backwards-compatibility case. A nil UUID value is also returned by some intermediary devices that send provisional or other responses as the "local-uuid" component of the Session-ID header field value, as described in Section 7.

特定の状況では、32個のゼロからなる特別なnil UUID値が必要です。 開始側のエンドポイントは最初はリモートエンドポイントのUUID値を知らないため、すべての標準的な最初のSIPリクエストの「remote-uuid」にはnil UUIDが入ることが想定されます。 このnil値は、最終的な宛先のUASがレスポンスメッセージを生成するときに、そのUASによって置き換えられます。 後方互換性に関して起こり得るケースについての1つの注意点を、セクション11で説明します。 また、セクション7で説明するように、暫定レスポンスやその他のレスポンスを送信する一部の仲介装置も、Session-IDヘッダーフィールド値の「local-uuid」コンポーネントとしてnil UUID値を返します。

The "local-uuid" in the Session-ID header field represents the UUID value of the endpoint transmitting a message and the "remote-uuid" in the Session-ID header field represents the UUID of the endpoint's peer. For example, a Session-ID header field might appear like this:

Session-IDヘッダーフィールドの「local-uuid」はメッセージを送信するエンドポイントのUUID値を表し、Session-IDヘッダーフィールドの「remote-uuid」はそのエンドポイントのピアのUUIDを表します。 たとえば、Session-IDヘッダーフィールドは次のようになります。

Session-ID: ab30317f1a784dc48ff824d0d3715d86;
            remote=47755a9de7794ba387653f2099600ef2

Session-ID: ab30317f1a784dc48ff824d0d3715d86;
            remote=47755a9de7794ba387653f2099600ef2

While this is the general form of the Session-ID header field, exceptions to syntax and procedures are detailed in subsequent sections.

これがSession-IDヘッダーフィールドの一般的な形式ですが、構文と手順の例外については後続のセクションで詳しく説明します。

The UUID values are presented as strings of lowercase hexadecimal characters, with the most significant octet of the UUID appearing first.

UUID値は小文字の16進文字の文字列として表され、UUIDの最上位オクテットが最初に現れます。

6. Endpoint Behavior

6. エンドポイントの振る舞い

To comply with this specification, endpoints (non-intermediaries) MUST include a Session-ID header field value in all SIP messages transmitted as a part of a communication session. The locally generated UUID of the transmitter of the message MUST appear in the "local-uuid" portion of the Session-ID header field value. The UUID of the peer device, if known, MUST appear as the "remote" parameter following the transmitter's UUID. The nil UUID value MUST be used if the peer device's UUID is not known.

この仕様に準拠するために、エンドポイント（仲介者ではないもの）は、通信セッションの一部として送信するすべてのSIPメッセージにSession-IDヘッダーフィールド値を含めなければなりません（MUST）。 メッセージの送信者がローカルで生成したUUIDは、Session-IDヘッダーフィールド値の「local-uuid」部分に現れなければなりません（MUST）。 ピア装置のUUIDがわかっている場合、それは送信者のUUIDに続く「remote」パラメーターとして現れなければなりません（MUST）。 ピア装置のUUIDがわからない場合は、nil UUID値を使用しなければなりません（MUST）。

Once an endpoint allocates a UUID value for a communication session, the endpoint originating the request MUST NOT change that UUID value for the duration of the session, including when:

エンドポイントが通信セッションにUUID値を割り当てたら、リクエストを発信するエンドポイントは、次の場合も含め、セッションの期間中そのUUID値を変更してはなりません（MUST NOT）。

  • communication attempts are retried due to receipt of 4xx messages or request timeouts;
  • the session is redirected in response to a 3xx message;
  • a session is transferred via a REFER message [RFC3515]; or
  • a SIP dialog is replaced via an INVITE request with Replaces [RFC3891].
  • 4xxメッセージの受信やリクエストのタイムアウトにより、通信の試行が再試行される場合
  • 3xxメッセージに応じてセッションがリダイレクトされる場合
  • REFERメッセージ[RFC3515]によってセッションが転送される場合
  • Replaces[RFC3891]付きのINVITEリクエストによってSIPダイアログが置き換えられる場合

An endpoint that receives a Session-ID header field MUST take note of any non-nil "local-uuid" value that it receives and assume that is the UUID of the peer endpoint within that communication session. Endpoints MUST include this received UUID value as the "remote" parameter when transmitting subsequent messages, making sure not to change this UUID value in the process of moving the value internally from the "local-uuid" field to the "remote-uuid" field.

Session-IDヘッダーフィールドを受信したエンドポイントは、受信したnilでない「local-uuid」値に留意し、それがその通信セッション内のピアエンドポイントのUUIDであるとみなさなければなりません（MUST）。 エンドポイントは、後続のメッセージを送信するとき、この受信したUUID値を「remote」パラメーターとして含めなければなりません（MUST）。 その際、値を内部的に「local-uuid」フィールドから「remote-uuid」フィールドに移す過程でこのUUID値を変更しないようにします。

If an endpoint receives a 3xx message, a REFER that directs the endpoint to a different peer, or an INVITE request with Replaces that also potentially results in communicating with a new peer, the endpoint MUST complete any message exchanges with its current peer using the existing session identifier, but it MUST NOT use the current peer's UUID value when sending the first message to what it believes may be a new peer endpoint (even if the exchange results in communicating with the same physical or logical entity). The endpoint MUST retain its own UUID value, however, as described above.

エンドポイントが3xxメッセージ、エンドポイントを別のピアに向けるREFER、または新しいピアとの通信につながる可能性のあるReplaces付きのINVITEリクエストを受信した場合、エンドポイントは既存のセッション識別子を使用して現在のピアとのメッセージ交換を完了しなければなりません（MUST）。 ただし、新しいピアエンドポイントかもしれないと考える相手に最初のメッセージを送信するときは、（その交換の結果として同じ物理的または論理的なエンティティーと通信することになったとしても）現在のピアのUUID値を使用してはなりません（MUST NOT）。 とはいえ、上記のとおり、エンドポイントは自身のUUID値を保持しなければなりません（MUST）。

It should be noted that messages received by an endpoint might contain a "local-uuid" value that does not match what the endpoint expected its peer's UUID to be. It is also possible for an endpoint to receive a "remote-uuid" value that does not match its generated UUID for the session. Either might happen as a result of service interactions by intermediaries and MUST NOT affect how the endpoint processes the session; however, the endpoint may log this event for troubleshooting purposes.

エンドポイントが受信したメッセージには、エンドポイントがピアのUUIDとして想定していたものと一致しない「local-uuid」値が含まれている可能性があることに注意すべきです。 また、エンドポイントが、そのセッションについて自身が生成したUUIDと一致しない「remote-uuid」値を受信する可能性もあります。 いずれも仲介者によるサービスインタラクションの結果として起こる可能性があり、エンドポイントがセッションを処理する方法に影響を与えてはなりません（MUST NOT）。 ただし、エンドポイントは、トラブルシューティングの目的でこのイベントをログに記録してもかまいません。

An endpoint MUST assume that the UUID value of the peer endpoint may change at any time due to service interactions. Section 8 discusses how endpoints must handle remote UUID changes.

エンドポイントは、サービスインタラクションによってピアエンドポイントのUUID値がいつでも変わり得るとみなさなければなりません（MUST）。 エンドポイントがリモートUUIDの変更をどのように扱わなければならないかについては、セクション8で説明します。

It is also important to note that if an intermediary in the network forks a session, the endpoint initiating a session may receive multiple responses back from different endpoints, each of which contains a different UUID ("local-uuid") value. Endpoints MUST ensure that the correct UUID value is returned in the "remote" parameter when interacting with each endpoint. The one exception is when the endpoint sends a CANCEL request, in which case the Session-ID header field value MUST be identical to the Session-ID header field value sent in the original request.

また、ネットワーク内の仲介者がセッションをフォークした場合、セッションを開始したエンドポイントは、異なるエンドポイントから複数のレスポンスを受け取ることがあり、それぞれに異なるUUID（「local-uuid」）値が含まれていることにも注意することが重要です。 エンドポイントは、各エンドポイントとやり取りするときに、正しいUUID値が「remote」パラメーターで返されるようにしなければなりません（MUST）。 唯一の例外は、エンドポイントがCANCELリクエストを送信する場合です。 この場合、Session-IDヘッダーフィールド値は、元のリクエストで送信したSession-IDヘッダーフィールド値と同一でなければなりません（MUST）。

If an endpoint receives a message that does not contain a Session-ID header field, that message must have no effect on what the endpoint believes is the UUID value of the remote endpoint. That is, the endpoint MUST NOT change the internally maintained "remote-uuid" value for the peer.

エンドポイントがSession-IDヘッダーフィールドを含まないメッセージを受信した場合、そのメッセージは、エンドポイントがリモートエンドポイントのUUID値だと考えているものに影響を与えてはなりません。 つまり、エンドポイントは、内部で保持しているピアの「remote-uuid」値を変更してはなりません（MUST NOT）。

If an endpoint receives a SIP response with a non-nil "local-uuid" that is not 32 octets long, this response comes from a misbehaving implementation, and its Session-ID header field MUST be discarded. That said, the response might still be valid according to the rules within SIP [RFC3261], and it SHOULD be checked further.

エンドポイントが、長さが32オクテットではないnilでない「local-uuid」を含むSIPレスポンスを受信した場合、このレスポンスは誤動作している実装から来たものであり、そのSession-IDヘッダーフィールドは破棄しなければなりません（MUST）。 とはいえ、そのレスポンスはSIP[RFC3261]の規則に従えば有効である可能性があり、さらに検査すべきです（SHOULD）。

A Multipoint Control Unit (MCU) is a special type of conferencing endpoint and is discussed in Section 9.

多地点制御装置（MCU）は特別な種類の会議エンドポイントであり、セクション9で説明します。

7. Processing by Intermediaries

7. 仲介者による処理

The following applies only to an intermediary that wishes to comply with this specification and does not impose a conformance requirement on intermediaries that elect not to provide any special treatment for the Session-ID header field. Intermediaries that do not comply with this specification might pass the header unchanged or drop it entirely.

以下は、この仕様に準拠したい仲介者にのみ適用されるものであり、Session-IDヘッダーフィールドを特別に扱わないことを選択した仲介者に適合要件を課すものではありません。 この仕様に準拠しない仲介者は、ヘッダーを変更せずに通過させるか、完全に削除する可能性があります。

The Call-ID often reveals personal, device, domain, or other sensitive information associated with a user, which is one reason why intermediaries, such as session border controllers, sometimes alter the Call-ID. In order to ensure the integrity of the end-to-end session identifier, it is constructed in a way that does not reveal such information, removing the need for intermediaries to alter it.

Call-IDは、ユーザーに関連する個人、装置、ドメイン、その他の機微な情報を明らかにすることが多く、これがセッションボーダーコントローラーなどの仲介者がCall-IDを変更することがある理由の1つです。 エンドツーエンドのセッション識別子の完全性を確保するために、セッション識別子はそのような情報を明らかにしない方法で構築されており、仲介者がそれを変更する必要をなくしています。

When an intermediary receives messages from one endpoint in a communication session that causes the transmission of one or more messages toward the second endpoint in a communication session, the intermediary MUST include the Session-ID header field in the transmitted messages with the same UUID values found in the received message, except as outlined in this section and in Section 8.

仲介者が通信セッションの一方のエンドポイントからメッセージを受信し、それによって通信セッションのもう一方のエンドポイントに向けて1つ以上のメッセージを送信することになる場合、仲介者は、このセクションとセクション8で概説する場合を除き、受信したメッセージにあるのと同じUUID値を持つSession-IDヘッダーフィールドを、送信するメッセージに含めなければなりません（MUST）。

If the intermediary aggregates several responses from different endpoints, as described in Section 16.7 of [RFC3261], the intermediary MUST set the local-uuid field to the nil UUID value when forwarding the aggregated response to the endpoint since the true UUID value of the peer is undetermined at that point. Note that an intermediary that does not implement this specification might forward a non-nil value, resulting in the originating endpoint receiving different UUID values in the responses. It is possible for this to result in the endpoint temporarily using the wrong remote UUID. Subsequent messages in the dialog should resolve the temporary mismatch as long as the endpoint follows the rules outlined in Section 8 dealing with the handling of remote UUID changes.

[RFC3261]のセクション16.7で説明されているように、仲介者が異なるエンドポイントからの複数のレスポンスを集約する場合、その時点ではピアの本当のUUID値が確定していないため、仲介者は集約したレスポンスをエンドポイントに転送するときにlocal-uuidフィールドをnil UUID値に設定しなければなりません（MUST）。 この仕様を実装していない仲介者はnilでない値を転送する可能性があり、その結果、発信元のエンドポイントがレスポンスで異なるUUID値を受信することに注意してください。 その結果、エンドポイントが一時的に誤ったリモートUUIDを使用する可能性があります。 エンドポイントがリモートUUIDの変更の扱いに関するセクション8で概説されている規則に従っている限り、ダイアログ内の後続のメッセージによって一時的な不一致は解消されるはずです。

Intermediary devices that transfer a call, such as by joining together two different "call legs", MUST properly construct a Session-ID header field that contains the UUID values associated with the endpoints involved in the joined session and correct placement of those values. As described in Section 6, the endpoint receiving a message transmitted by the intermediary will assume that the first UUID value belongs to its peer endpoint.

2つの異なる「コールレッグ」を結合するなどして通話を転送する仲介装置は、結合されたセッションに関与するエンドポイントに関連付けられたUUID値を含み、それらの値を正しく配置したSession-IDヘッダーフィールドを適切に構築しなければなりません（MUST）。 セクション6で説明したように、仲介者が送信したメッセージを受信したエンドポイントは、最初のUUID値がピアエンドポイントのものであるとみなします。

If an intermediary receives a SIP message without a Session-ID header field or valid header field value from an endpoint for which the intermediary is not storing a "remote-uuid" value, the intermediary MAY assign a "local-uuid" value to represent that endpoint and, having done so, MUST insert that assigned value into all signaling messages on behalf of the endpoint for that dialog. In effect, the intermediary becomes dialog-stateful, and it MUST follow the endpoint procedures in Section 6 with respect to Session-ID header field value treatment with itself acting as the endpoint (for the purposes of the Session-ID header field) for which it inserted a component into the Session-ID header field value. If the intermediary is aware of the UUID value that identifies the endpoint to which a message is directed, it MUST insert that UUID value into the Session-ID header field value as the "remote-uuid" value. If the intermediary is unaware of the UUID value that identifies the receiving endpoint, it MUST use the nil UUID value as the "remote-uuid" value.

仲介者が「remote-uuid」値を保存していないエンドポイントから、Session-IDヘッダーフィールドまたは有効なヘッダーフィールド値のないSIPメッセージを受信した場合、仲介者はそのエンドポイントを表す「local-uuid」値を割り当ててもよいです（MAY）。 そうした場合は、そのダイアログについて、エンドポイントに代わってすべてのシグナリングメッセージにその割り当てた値を挿入しなければなりません（MUST）。 実質的に、仲介者はダイアログステートフルになり、Session-IDヘッダーフィールド値の扱いに関してセクション6のエンドポイントの手順に従わなければなりません（MUST）。 その際、仲介者自身が、Session-IDヘッダーフィールド値にコンポーネントを挿入した対象のエンドポイントとして（Session-IDヘッダーフィールドの目的上）振る舞います。 仲介者が、メッセージの宛先であるエンドポイントを識別するUUID値を知っている場合、そのUUID値を「remote-uuid」値としてSession-IDヘッダーフィールド値に挿入しなければなりません（MUST）。 仲介者が受信側のエンドポイントを識別するUUID値を知らない場合、「remote-uuid」値としてnil UUID値を使用しなければなりません（MUST）。

If an intermediary receives a SIP message without a Session-ID header field or a valid Session-ID header field value from an endpoint for which the intermediary has previously received a Session-ID and is storing a "remote-uuid" value for that endpoint, the lack of a Session-ID must have no effect on what the intermediary believes is the UUID value of the endpoint. That is, the intermediary MUST NOT change the internally maintained "remote-uuid" value for the peer.

仲介者が以前にSession-IDを受信し、「remote-uuid」値を保存しているエンドポイントから、Session-IDヘッダーフィールドまたは有効なSession-IDヘッダーフィールド値のないSIPメッセージを受信した場合、Session-IDがないことは、仲介者がそのエンドポイントのUUID値だと考えているものに影響を与えてはなりません。 つまり、仲介者は、内部で保持しているピアの「remote-uuid」値を変更してはなりません（MUST NOT）。

When an intermediary originates a response, such as a provisional response or a response to a CANCEL request, the "remote-uuid" field will contain the UUID value of the receiving endpoint. When the UUID of the peer endpoint is known, the intermediary MUST insert the UUID of the peer endpoint in the "local-uuid" field of the header value. Otherwise, the intermediary MAY set the "local-uuid" field of the header value to the "nil" UUID value.

仲介者が暫定レスポンスやCANCELリクエストに対するレスポンスなどのレスポンスを発信する場合、「remote-uuid」フィールドには受信側のエンドポイントのUUID値が入ります。 ピアエンドポイントのUUIDがわかっている場合、仲介者はヘッダー値の「local-uuid」フィールドにピアエンドポイントのUUIDを挿入しなければなりません（MUST）。 そうでない場合、仲介者はヘッダー値の「local-uuid」フィールドを「nil」UUID値に設定してもよいです（MAY）。

When an intermediary originates a request message without first having received a SIP message that triggered the transmission of the message (e.g., sending a BYE message to terminate a call for policy reasons), the intermediary MUST, if it has knowledge of the UUID values for the two communicating endpoints, insert a Session-ID header field with the "remote-uuid" field of the header value set to the UUID value of the receiving endpoint and the "local-uuid" field of the header value set to the UUID value of the other endpoint. When the intermediary does not have knowledge of the UUID value of an endpoint in the communication session, the intermediary SHOULD set the unknown UUID value(s) to the "nil" UUID value. (If both are unknown, the Session-ID header value SHOULD NOT be included at all, since it would have no practical value.)

仲介者が、送信のきっかけとなるSIPメッセージを先に受信することなくリクエストメッセージを発信する場合（たとえば、ポリシー上の理由で通話を終了するためにBYEメッセージを送信する場合）、通信している2つのエンドポイントのUUID値を知っていれば、仲介者は、ヘッダー値の「remote-uuid」フィールドを受信側のエンドポイントのUUID値に設定し、ヘッダー値の「local-uuid」フィールドをもう一方のエンドポイントのUUID値に設定したSession-IDヘッダーフィールドを挿入しなければなりません（MUST）。 仲介者が通信セッション内のエンドポイントのUUID値を知らない場合、仲介者は不明なUUID値を「nil」UUID値に設定すべきです（SHOULD）。 （両方とも不明な場合は、実用的な価値がないため、Session-IDヘッダー値をまったく含めるべきではありません（SHOULD NOT）。）

With respect to the previous two paragraphs, note that if an intermediary transmits a "nil" UUID value, the receiving endpoint might use that value in subsequent messages it sends. This effectively violates the requirement of maintaining an end-to-end session identifier value for the communication session if a UUID for the peer endpoint had been previously conveyed. Therefore, an intermediary MUST only send the "nil" UUID when the intermediary has not communicated with the peer endpoint to learn its UUID. This means that intermediaries SHOULD maintain state related to the UUID values for both ends of a communication session if it intends to originate messages (versus merely conveying messages). An intermediary that does not maintain this state and that originates a message as described in the previous two paragraphs MUST NOT insert a Session-ID header field in order to avoid unintended, incorrect reassignment of a UUID value.

前の2つの段落に関して、仲介者が「nil」UUID値を送信すると、受信側のエンドポイントは自身が送信する後続のメッセージでその値を使用する可能性があることに注意してください。 ピアエンドポイントのUUIDが以前に伝えられていた場合、これは実質的に、通信セッションについてエンドツーエンドのセッション識別子の値を維持するという要件に違反します。 したがって、仲介者は、ピアエンドポイントと通信してそのUUIDを知る前の場合にのみ、「nil」UUIDを送信しなければなりません（MUST）。 これは、（単にメッセージを中継するのではなく）メッセージを発信するつもりであれば、仲介者は通信セッションの両端のUUID値に関する状態を保持すべきです（SHOULD）ということを意味します。 この状態を保持せず、前の2つの段落で説明したようにメッセージを発信する仲介者は、意図しない誤ったUUID値の再割り当てを避けるために、Session-IDヘッダーフィールドを挿入してはなりません（MUST NOT）。

The Session-ID header field value included in a CANCEL request MUST be identical to the Session-ID header field value included in the corresponding request being cancelled.

CANCELリクエストに含まれるSession-IDヘッダーフィールド値は、キャンセルされる対応するリクエストに含まれるSession-IDヘッダーフィールド値と同一でなければなりません（MUST）。

If a SIP intermediary initiates a dialog between two endpoints in a third-party call control (3PCC [RFC3725]) scenario, the initial INVITE request will have a non-nil, locally fabricated "local-uuid" value; call this temporary UUID "X". The request will still have a nil "remote-uuid" value; call this value "N". The SIP server MUST be transaction-stateful. The UUID pair in the INVITE request will be {X,N}. A 1xx or 2xx response will have a UUID pair {A,X}. This transaction-stateful, dialog-initiating SIP server MUST replace its own UUID, i.e.,"X", with a nil UUID (i.e., {A,N}) in the INVITE request sent towards the other UAS as expected (see Section 10.7 for an example).

第三者呼制御（3PCC [RFC3725]）のシナリオでSIP仲介者が2つのエンドポイント間のダイアログを開始する場合、最初のINVITEリクエストには、ローカルで作成されたnilでない「local-uuid」値が含まれます。 この一時的なUUIDを「X」と呼びます。 このリクエストの「remote-uuid」値はnilのままであり、この値を「N」と呼びます。 SIPサーバーはトランザクションステートフルでなければなりません（MUST）。 INVITEリクエスト内のUUIDの組は{X,N}になります。 1xxまたは2xxレスポンスのUUIDの組は{A,X}になります。 このトランザクションステートフルでダイアログを開始するSIPサーバーは、想定どおり、もう一方のUASに向けて送信するINVITEリクエストにおいて、自身のUUID、つまり「X」をnil UUIDに置き換え（つまり{A,N}にし）なければなりません（MUST）（例についてはセクション10.7を参照してください）。

Intermediaries that manipulate messages containing a Session-ID header field SHOULD be aware of what UUID values it last sent towards an endpoint and, following any kind of service interaction initiated or affected by the intermediary, what UUID values the receiving endpoint should have knowledge of to ensure that both endpoints in the session have the correct and same UUID values. If an intermediary can determine that an endpoint might not have received a current, correct Session-ID field, the intermediary SHOULD attempt to provide the correct Session-ID header field to the endpoint such as by sending a re-INVITE request. Failure to take such measures may make troubleshooting more difficult because of the mismatched identifiers; therefore, it is strongly advised that intermediaries attempt to provide the correct session identifier if able to do so.

Session-IDヘッダーフィールドを含むメッセージを操作する仲介者は、セッションの両方のエンドポイントが正しく同じUUID値を持つようにするために、エンドポイントに向けて最後に送信したUUID値を把握し、また仲介者が開始したり影響を与えたりしたあらゆる種類のサービスインタラクションの後で、受信側のエンドポイントがどのUUID値を知っているべきかを把握しているべきです（SHOULD）。 エンドポイントが現在の正しいSession-IDフィールドを受信していない可能性があると判断できる場合、仲介者は、re-INVITEリクエストを送信するなどして、正しいSession-IDヘッダーフィールドをエンドポイントに提供するよう試みるべきです（SHOULD）。 このような措置をとらないと、識別子の不一致によってトラブルシューティングがより困難になる可能性があります。 したがって、仲介者は、可能であれば正しいセッション識別子を提供するよう試みることが強く勧められます。

If an intermediary receives a SIP response with a non-nil "local-uuid" that is not 32 octets long, this response comes from a misbehaving implementation, and its Session-ID header field MUST be discarded. That said, the response might still be valid according to the rules within SIP [RFC3261], and it SHOULD be checked further.

仲介者が、長さが32オクテットではないnilでない「local-uuid」を含むSIPレスポンスを受信した場合、このレスポンスは誤動作している実装から来たものであり、そのSession-IDヘッダーフィールドは破棄しなければなりません（MUST）。 とはいえ、そのレスポンスはSIP[RFC3261]の規則に従えば有効である可能性があり、さらに検査すべきです（SHOULD）。

An intermediary MUST assume that the UUID value of session peers may change at any time due to service interactions and MAY itself change UUID values for sessions under its control to ensure that end-to-end session identifiers are consistent for all participants in a session. Section 8 discusses how intermediaries must handle remote UUID changes if they maintain state of the session identifier.

仲介者は、サービスインタラクションによってセッションのピアのUUID値がいつでも変わり得るとみなさなければなりません（MUST）。 また、セッションのすべての参加者にとってエンドツーエンドのセッション識別子が一貫するように、自身の制御下にあるセッションのUUID値を自ら変更してもよいです（MAY）。 セッション識別子の状態を保持している仲介者がリモートUUIDの変更をどのように扱わなければならないかについては、セクション8で説明します。

An intermediary may perform protocol interworking between different IP-based communications systems, e.g., interworking between H.323 and SIP. If the intermediary supports the session identifier for both protocols for which it is interworking, it SHOULD pass the identifier between the two call legs to maintain an end-to-end identifier, regardless of protocol.

仲介者は、異なるIPベースの通信システム間でプロトコルの相互接続、たとえばH.323とSIPの間の相互接続を行う場合があります。 仲介者が、相互接続している両方のプロトコルでセッション識別子をサポートしている場合、プロトコルにかかわらずエンドツーエンドの識別子を維持するために、2つのコールレッグの間で識別子を受け渡すべきです（SHOULD）。

8. Handling of Remote UUID Changes

8. リモートUUIDの変更の扱い

It is desirable to have all endpoints and intermediaries involved in a session agree upon the current session identifier when these changes occur. Due to race conditions or certain interworking scenarios, it is not always possible to guarantee session identifier consistency; however, in an attempt to ensure the highest likelihood of consistency, all endpoints and intermediaries involved in a session MUST accept a peer's new UUID under the following conditions:

このような変更が発生したとき、セッションに関与するすべてのエンドポイントと仲介者が現在のセッション識別子について合意していることが望まれます。 競合状態や特定の相互接続のシナリオのため、セッション識別子の一貫性を常に保証できるわけではありません。 しかし、一貫性が得られる可能性をできるだけ高めるために、セッションに関与するすべてのエンドポイントと仲介者は、次の条件の下でピアの新しいUUIDを受け入れなければなりません（MUST）。

  • When an endpoint or intermediary receives a mid-dialog request containing a new UUID from a peer, all responses to that request MUST contain the new UUID value as the "remote" parameter unless a subsequent successful transaction (for example, an UPDATE) contains a different UUID, in which case, the newest UUID MUST be used.
  • If an endpoint or intermediary sends a successful (2xx) or redirection (3xx) response to the request containing the new UUID value, the endpoint or intermediary MUST accept the peer's UUID and include this new UUID as the "remote" parameter for any subsequent messages unless the UUID from a subsequent transaction has already been accepted. The one exception is a CANCEL request, as outlined below.
  • If the endpoint or intermediary sends a failure (4xx, 5xx, or 6xx) response, it MUST NOT accept the new UUID value and any subsequent messages MUST contain the previously stored UUID value in the "remote" parameter for any subsequent message. Note that the failure response itself will contain the new UUID value from the request in the "remote" parameter.
  • When an endpoint or intermediary receives an ACK for a successful (2xx) or redirection (3xx) response with a new UUID value, it MUST accept the peer's new UUID value and include this new UUID as the "remote" parameter for any subsequent messages. If the ACK is for a failure (4xx, 5xx, or 6xx) response, the new value MUST NOT be used.
  • As stated in Sections 6 and 7, the Session-ID header field value included in a CANCEL request MUST be identical to the Session-ID header field value included in the corresponding INVITE request. Upon receiving a CANCEL request, an endpoint or intermediary would normally send a 487 Request Terminated response (see Section 15.1.2 of [RFC3261]) which, by the rules outlined above, would result in the endpoint or intermediary not storing any UUID value contained in the CANCEL request. Section 3.8 of [RFC6141] specifies conditions where a CANCEL request can result in a 2xx response. Because a CANCEL request is not passed end-to-end and will always contain the UUID from the original INVITE request, retaining a new UUID value received in a CANCEL request may result in inconsistency with the Session-ID value stored on the endpoints and intermediaries involved in the session. To avoid this situation, an endpoint or intermediary MUST NOT accept the new UUID value received in a CANCEL request and any subsequent messages MUST contain the previously stored UUID value in the "remote" parameter". Note that the response to the CANCEL request will contain the UUID value from the CANCEL request in the "remote" parameter.
  • When an endpoint or intermediary receives a response containing a new UUID from a peer, the endpoint or intermediary MUST accept the new UUID as the peer's UUID and include this new UUID as the "remote" parameter for any subsequent messages.
  • エンドポイントまたは仲介者が、新しいUUIDを含むダイアログ内リクエストをピアから受信した場合、そのリクエストに対するすべてのレスポンスは、新しいUUID値を「remote」パラメーターとして含めなければなりません（MUST）。 ただし、後続の成功したトランザクション（たとえば、UPDATE）に異なるUUIDが含まれている場合は除きます。 その場合は、最新のUUIDを使用しなければなりません（MUST）。
  • エンドポイントまたは仲介者が、新しいUUID値を含むリクエストに対して成功（2xx）またはリダイレクト（3xx）のレスポンスを送信した場合、エンドポイントまたは仲介者はピアのUUIDを受け入れ、後続のトランザクションのUUIDをすでに受け入れているのでない限り、後続のすべてのメッセージでこの新しいUUIDを「remote」パラメーターとして含めなければなりません（MUST）。 唯一の例外は、後述するCANCELリクエストです。
  • エンドポイントまたは仲介者が失敗（4xx、5xx、または6xx）のレスポンスを送信した場合、新しいUUID値を受け入れてはなりません（MUST NOT）。 また、後続のメッセージは、後続のあらゆるメッセージについて、以前に保存したUUID値を「remote」パラメーターに含めなければなりません（MUST）。 失敗のレスポンス自体には、リクエストからの新しいUUID値が「remote」パラメーターに含まれることに注意してください。
  • エンドポイントまたは仲介者が、新しいUUID値を含む成功（2xx）またはリダイレクト（3xx）のレスポンスに対するACKを受信した場合、ピアの新しいUUID値を受け入れ、後続のすべてのメッセージでこの新しいUUIDを「remote」パラメーターとして含めなければなりません（MUST）。 ACKが失敗（4xx、5xx、または6xx）のレスポンスに対するものである場合、新しい値を使用してはなりません（MUST NOT）。
  • セクション6と7で述べたように、CANCELリクエストに含まれるSession-IDヘッダーフィールド値は、対応するINVITEリクエストに含まれるSession-IDヘッダーフィールド値と同一でなければなりません（MUST）。 CANCELリクエストを受信すると、エンドポイントまたは仲介者は通常、487 Request Terminatedレスポンスを送信します（[RFC3261]のセクション15.1.2を参照してください）。 上で概説した規則により、その結果、エンドポイントまたは仲介者はCANCELリクエストに含まれるUUID値を保存しないことになります。 [RFC6141]のセクション3.8は、CANCELリクエストが2xxレスポンスになり得る条件を規定しています。 CANCELリクエストはエンドツーエンドで受け渡されず、常に元のINVITEリクエストのUUIDを含むため、CANCELリクエストで受信した新しいUUID値を保持すると、セッションに関与するエンドポイントや仲介者に保存されているSession-ID値との不整合が生じる可能性があります。 この状況を避けるために、エンドポイントまたは仲介者は、CANCELリクエストで受信した新しいUUID値を受け入れてはなりません（MUST NOT）。 また、後続のメッセージは、以前に保存したUUID値を「remote」パラメーターに含めなければなりません（MUST）。 CANCELリクエストに対するレスポンスには、CANCELリクエストからのUUID値が「remote」パラメーターに含まれることに注意してください。
  • エンドポイントまたは仲介者が、新しいUUIDを含むレスポンスをピアから受信した場合、エンドポイントまたは仲介者は、新しいUUIDをピアのUUIDとして受け入れ、後続のすべてのメッセージでこの新しいUUIDを「remote」パラメーターとして含めなければなりません（MUST）。

When an intermediary accepts a new UUID from a peer, the intermediary SHOULD attempt to provide the correct Session-ID header field to other endpoints involved in the session, for example, by sending a re-INVITE request. If an intermediary receives a message with a "remote" parameter in the session identifier that does not match the updated UUID, the intermediary MUST update the "remote" parameter with the latest stored UUID.

仲介者がピアから新しいUUIDを受け入れた場合、仲介者は、たとえばre-INVITEリクエストを送信するなどして、セッションに関与する他のエンドポイントに正しいSession-IDヘッダーフィールドを提供するよう試みるべきです（SHOULD）。 仲介者が、セッション識別子の「remote」パラメーターが更新されたUUIDと一致しないメッセージを受信した場合、仲介者は「remote」パラメーターを保存されている最新のUUIDで更新しなければなりません（MUST）。

If an intermediary is performing interworking between two different protocols that both support the session identifier defined in this document (e.g., SIP to H.323), UUID changes SHOULD be communicated between protocols to maintain the end-to-end session identifier.

この文書で定義するセッション識別子を両方ともサポートする2つの異なるプロトコル間（たとえば、SIPとH.323の間）で仲介者が相互接続を行っている場合、エンドツーエンドのセッション識別子を維持するために、UUIDの変更をプロトコル間で伝えるべきです（SHOULD）。

9. Associating Endpoints in a Multipoint Conference

9. 多地点会議におけるエンドポイントの関連付け

Multipoint Control Units (MCUs) group two or more sessions into a single multipoint conference and have a conference focus responsible for maintaining the dialogs connected to it [RFC4353]. MCUs, including cascaded MCUs, MUST utilize the same UUID value ("local-uuid" portion of the Session-ID header field value) with all participants in the conference. In so doing, each individual session in the conference will have a unique session identifier (since each endpoint will create a unique UUID of its own), but will also have one UUID in common with all other participants in the conference.

多地点制御装置（MCU）は、2つ以上のセッションを1つの多地点会議にまとめ、それに接続されたダイアログを維持する責任を持つ会議フォーカスを持ちます[RFC4353]。 カスケード接続されたMCUを含め、MCUは会議のすべての参加者に対して同じUUID値（Session-IDヘッダーフィールド値の「local-uuid」部分）を利用しなければなりません（MUST）。 そうすることで、会議内の個々のセッションは（各エンドポイントが独自の一意なUUIDを作成するため）一意なセッション識別子を持ちますが、会議の他のすべての参加者と共通する1つのUUIDも持つことになります。

When creating a cascaded conference, an MCU MUST convey the UUID value to be utilized for a conference via the "local-uuid" portion of the Session-ID header field value in an INVITE request to a second MCU when using SIP to establish the cascaded conference. A conference bridge, or MCU, needs a way to identify itself when contacting another MCU. [RFC4579] defines the "isfocus" Contact header field value parameter just for this purpose. The initial MCU MUST include the UUID of that particular conference in the "local-uuid" of an INVITE request to the other MCU(s) participating in that conference. Also included in this INVITE request is an "isfocus" Contact header field value parameter identifying that this INVITE request is coming from an MCU, and that this UUID is to be given out in all responses from endpoints into those MCUs participating in this same conference. This ensures that a single UUID is common across all participating MCUs of the same conference, but that it is unique between different conferences.

カスケード会議を作成する場合、SIPを使用してカスケード会議を確立するときには、MCUは2番目のMCUへのINVITEリクエストにおいて、Session-IDヘッダーフィールド値の「local-uuid」部分を介して、会議に利用するUUID値を伝えなければなりません（MUST）。 会議ブリッジ、つまりMCUは、別のMCUに接続するときに自身を識別する方法を必要とします。 [RFC4579]は、まさにこの目的のために「isfocus」というContactヘッダーフィールド値パラメーターを定義しています。 最初のMCUは、その会議に参加している他のMCUへのINVITEリクエストの「local-uuid」に、その特定の会議のUUIDを含めなければなりません（MUST）。 このINVITEリクエストには、このINVITEリクエストがMCUから来たものであること、そしてこのUUIDが、この同じ会議に参加しているMCUに入ってくるエンドポイントからのすべてのレスポンスで配布されるものであることを示す「isfocus」Contactヘッダーフィールド値パラメーターも含まれます。 これにより、1つのUUIDが同じ会議に参加するすべてのMCUで共通となり、かつ異なる会議の間では一意となることが保証されます。

In the case where two existing conferences are joined, there should be a session between the two MCUs where the session identifier is comprised of the UUID values of the two conferences. This session identifier can be used to correlate the sessions between participants in the joined conference. This specification does not impose any additional requirements when two existing conferences are joined.

既存の2つの会議が結合される場合、2つのMCUの間に、2つの会議のUUID値からなるセッション識別子を持つセッションが存在するはずです。 このセッション識別子を使って、結合された会議の参加者間のセッションを相関させることができます。 この仕様は、既存の2つの会議が結合される場合について追加の要件を課しません。

Intermediary devices or network-diagnostic equipment might assume that when they see two or more sessions with different session identifiers but with one UUID in common, the sessions are part of the same conference. However, the assumption that two sessions having one common UUID being part of the same conference is not always correct. In a SIP-forking scenario, for example, there might also exist what appears to be multiple sessions with a shared UUID value; this is intended. The desire is to allow for the association of related sessions, regardless of whether a session is forked or part of a conference.

仲介装置やネットワーク診断機器は、セッション識別子は異なるが1つのUUIDを共通に持つ2つ以上のセッションを見たとき、それらのセッションが同じ会議の一部であると想定するかもしれません。 しかし、1つの共通のUUIDを持つ2つのセッションが同じ会議の一部であるという想定は、常に正しいとは限りません。 たとえば、SIPのフォークのシナリオでも、UUID値を共有する複数のセッションのように見えるものが存在することがあり、これは意図されたものです。 目的は、セッションがフォークされたものか会議の一部であるかにかかわらず、関連するセッションを関連付けられるようにすることです。

  • UA-Aliceは、Session-IDヘッダーフィールド値の「local-uuid」部分を設定します。

10.2. Basic Call Transfer Using REFER

10.2. REFERを使用した基本的な通話転送

From the example built within Section 10.1, we proceed to this 'Basic Call Transfer using REFER' example. Note that this is a mid-dialog REFER in contrast with the out-of-dialog REFER in Section 10.9.

セクション10.1で構築した例から、この「REFERを使用した基本的な通話転送（Basic Call Transfer using REFER）」の例に進みます。 これは、セクション10.9のダイアログ外のREFERとは対照的に、ダイアログ内のREFERであることに注意してください。

General operation of this example:

この例の一般的な動作は次のとおりです。

Starting from the existing Alice/Bob call described in Figure 1 of this document, which established an existing Session-ID header field value:

この文書の図1で説明した、既存のSession-IDヘッダーフィールド値を確立した既存のAlice/Bob間の通話から始めます。

  • UA-Bob requests Alice to call Carol, using a REFER transaction, as described in [RFC3515]. UA-Alice is initially put on hold, then told in the REFER who to contact with a new INVITE, in this case UA-Carol. This Alice-to-Carol dialog will have a new Call-ID; therefore, it requires a new Session-ID header field value. The wrinkle here is we can, and will, use Alice's UUID from her existing dialog with Bob in the new INVITE request to Carol.
  • UA-Alice retains her UUID from the Alice-to-Bob call {A} when requesting a call with UA-Carol. This is placed in the "local-uuid" portion of the Session-ID header field value, at the same time inserting a nil "remote-uuid" value (because Carol's UA has not yet received the UUID value). This same UUID traverses the B2BUA unchanged.
  • UA-Carol receives the INVITE request with a session identifier UUID {A,N}, replaces the "A" UUID value into the "remote-uuid" portion of the Session-ID header field value and creates its own UUID {C}, and places this value in the "local-uuid" portion of the Session-ID header field value, thereby removing the "N" (nil) value altogether. This combination forms a full session identifier {C,A} in the 200 OK to the INVITE. This Session-ID header field traverses the B2BUA unchanged towards UA-Alice.
  • UA-Alice receives the 200 OK with the session identifier {C,A} and responds to UA-Carol with an ACK (just as in Figure 1, this switches the places of the two UUID fields), and generates a NOTIFY request to Bob with a session identifier {A,B} indicating that the call transfer was successful.
  • It does not matter which UA terminates the Alice-to-Bob call; Figure 2 shows UA-Bob terminating the call.
  • UA-Bobは、[RFC3515]で説明されているREFERトランザクションを使用して、AliceにCarolに電話をかけるよう要求します。 UA-Aliceはまず保留にされ、次にREFERで、新しいINVITEで誰に接続するか、この場合はUA-Carolであることを伝えられます。 このAliceからCarolへのダイアログは新しいCall-IDを持つため、新しいSession-IDヘッダーフィールド値が必要です。 ここで工夫する点は、Carolへの新しいINVITEリクエストで、AliceとBobの既存のダイアログからのAliceのUUIDを使用できる、そして実際に使用するということです。
  • UA-Aliceは、UA-Carolとの通話を要求するとき、AliceからBobへの通話のUUID{A}を保持します。 これをSession-IDヘッダーフィールド値の「local-uuid」部分に置き、同時に（CarolのUAがまだUUID値を受信していないため）nilの「remote-uuid」値を挿入します。 この同じUUIDが変更されずにB2BUAを通過します。
  • UA-Carolは、セッション識別子UUID{A,N}を含むINVITEリクエストを受信し、「A」のUUID値をSession-IDヘッダーフィールド値の「remote-uuid」部分に移し、自身のUUID{C}を作成して、この値をSession-IDヘッダーフィールド値の「local-uuid」部分に置きます。 これにより、「N」（nil）値は完全に取り除かれます。 この組み合わせにより、INVITEに対する200 OKにおいて完全なセッション識別子{C,A}が形成されます。 このSession-IDヘッダーフィールドは変更されずにB2BUAを通過し、UA-Aliceに向かいます。
  • UA-Aliceは、セッション識別子{C,A}を含む200 OKを受信し、UA-CarolにACKで応答します（図1と同様に、これにより2つのUUIDフィールドの位置が入れ替わります）。 そして、通話転送が成功したことを示すセッション識別子{A,B}を含むNOTIFYリクエストをBobに対して生成します。
  • AliceからBobへの通話をどちらのUAが終了するかは問題ではありません。 図2では、UA-Bobが通話を終了しています。

10.3. Basic Call Transfer Using Re-INVITE

10.3. re-INVITEを使用した基本的な通話転送

From the example built within Section 10.1, we proceed to this 'Basic Call Transfer using re-INVITE' example.

セクション10.1で構築した例から、この「re-INVITEを使用した基本的な通話転送（Basic Call Transfer using re-INVITE）」の例に進みます。

Alice is talking to Bob. Bob pushes a button on his phone to transfer Alice to Carol via the B2BUA (using re-INVITE).

AliceはBobと話しています。 Bobは電話のボタンを押して、（re-INVITEを使用して）B2BUAを介してAliceをCarolに転送します。

General operation of this example:

この例の一般的な動作は次のとおりです。

  • We assume the call between Alice and Bob from Section 10.1 is operational with session identifier {A,B}.
  • Bob uses non-standard signaling to the B2BUA to initiate a call transfer from Alice to Carol. This could also be initiated via a REFER message from Bob, but the signaling that follows might still be similar to the above flow. In either case, Alice is completely unaware of the call transfer until a future point in time when Alice receives a message from Carol.
  • The B2BUA sends a re-INVITE request with the session identifier {"local-uuid" = "A", "remote-uuid" = "B"} to renegotiate the session with Bob.
  • The B2BUA sends a new INVITE request with Alice's UUID {"local-uuid" = "A"} to Carol.
  • Carol receives the INVITE request and accepts the request and adds her UUID {C} to the session identifier for this session {"local-uuid" = "C", "remote-uuid" = "A"}.
  • The B2BUA then terminates the call to Bob with a BYE using the session identifier {"local-uuid" = "A", "remote-uuid" = "B"}.
  • The B2BUA sends a re-INVITE request to Alice to update Alice's view of the session identifier.
  • When Alice later attempts to modify the session with a re-INVITE, Alice will send "remote-uuid" = "C" toward Carol because it had previously received the updated UUID in the re-INVITE request from the B2BUA. The B2BUA maintains the session identifier {"local-uuid" = "A", "remote-uuid" = "C"}. Carol replies with the "local-uuid" = "C", "remote-uuid" = "A" to reflect what was received in the INVITE request (which Carol already knew from previous exchanges with the B2BUA). Alice then includes "remote-uuid" = "C" in the subsequent ACK message.
  • セクション10.1のAliceとBobの間の通話が、セッション識別子{A,B}で動作していると仮定します。
  • Bobは、B2BUAに対する非標準のシグナリングを使って、AliceからCarolへの通話転送を開始します。 これはBobからのREFERメッセージによって開始することもできますが、その後に続くシグナリングは上記のフローと同様になるでしょう。 いずれの場合も、AliceはCarolからのメッセージを受信する将来の時点まで、通話転送にまったく気づきません。
  • B2BUAは、Bobとのセッションを再ネゴシエートするために、セッション識別子{「local-uuid」=「A」, 「remote-uuid」=「B」}を含むre-INVITEリクエストを送信します。
  • B2BUAは、AliceのUUID{「local-uuid」=「A」}を含む新しいINVITEリクエストをCarolに送信します。
  • CarolはINVITEリクエストを受信して受け入れ、このセッションのセッション識別子に自身のUUID{C}を追加して{「local-uuid」=「C」, 「remote-uuid」=「A」}とします。
  • 次に、B2BUAは、セッション識別子{「local-uuid」=「A」, 「remote-uuid」=「B」}を使用したBYEでBobへの通話を終了します。
  • B2BUAは、Aliceが認識しているセッション識別子を更新するために、Aliceにre-INVITEリクエストを送信します。
  • 後でAliceがre-INVITEでセッションを変更しようとするとき、AliceはB2BUAからのre-INVITEリクエストで更新されたUUIDを以前に受信しているため、Carolに向けて「remote-uuid」=「C」を送信します。 B2BUAはセッション識別子{「local-uuid」=「A」, 「remote-uuid」=「C」}を維持します。 Carolは、INVITEリクエストで受信したもの（CarolはB2BUAとの以前のやり取りからすでに知っていたもの）を反映して、「local-uuid」=「C」、「remote-uuid」=「A」で応答します。 その後、Aliceは後続のACKメッセージに「remote-uuid」=「C」を含めます。

10.4. Single Focus Conferencing

10.4. 単一フォーカスの会議

Multiple users call into a conference server (for example, an MCU) to attend one of many conferences hosted on or managed by that server. Each user has to identify which conference they want to join, but this information is not necessarily in the SIP messaging. It might be done by having a dedicated address for the conference or via an Interactive Voice Response (IVR), as assumed in this example and depicted with the use of M1, M2, and M3. Each user in this example goes through a two-step process of signaling to gain entry onto their conference call, which the conference focus identifies as "M".

複数のユーザーが、会議サーバー（たとえば、MCU）にコールインして、そのサーバーでホストまたは管理されている多数の会議の1つに出席します。 各ユーザーは参加したい会議を特定する必要がありますが、この情報は必ずしもSIPメッセージングに含まれているとは限りません。 それは、会議専用のアドレスを持つことによって行われる場合もあれば、この例で想定し、M1、M2、M3を使って示しているように、自動音声応答（IVR）を介して行われる場合もあります。 この例の各ユーザーは、会議通話に入るためにシグナリングの2段階のプロセスを経ます。 会議フォーカスはその会議通話を「M」として識別します。

General operation of this example:

この例の一般的な動作は次のとおりです。

Alice calls into a conference server to attend a certain conference. This is a two-step operation since Alice cannot include the conference ID at this time and/or any passcode in the INVITE request. The first step is Alice's UA calling another UA to participate in a session. This will appear to be similar as the call flow in Figure 1 (in Section 10.1). What is unique about this call is the second step: the conference server sends a re-INVITE request with its second UUID, but maintaining the UUID Alice sent in the first INVITE. This subsequent UUID from the conference server will be the same for each UA that calls into this conference server participating in this same conference bridge/call, which is generated once Alice typically authenticates and identifies which bridge she wants to participate on.

Aliceは、ある会議に出席するために会議サーバーにコールインします。 Aliceはこの時点ではINVITEリクエストに会議IDやパスコードを含めることができないため、これは2段階の操作になります。 最初のステップは、AliceのUAがセッションに参加するために別のUAに電話をかけることです。 これは（セクション10.1の）図1のコールフローと同様に見えます。 この通話に特有なのは2番目のステップです。 会議サーバーは、Aliceが最初のINVITEで送信したUUIDを維持したまま、2番目のUUIDを含むre-INVITEリクエストを送信します。 会議サーバーからのこの後続のUUIDは、この同じ会議ブリッジ／通話に参加するためにこの会議サーバーにコールインする各UAに対して同じものになります。 このUUIDは、通常、Aliceが認証を受け、参加したいブリッジを特定した時点で生成されます。

  • Alice sends an INVITE request to the conference server with her UUID {A} and a "remote-uuid" = "N".
  • The conference server responds with a 200 OK response, which replaces the "N" UUID with a temporary UUID ("M1") as the "local-uuid" and a "remote-uuid" = "A".
  • Aliceは、自身のUUID{A}と「remote-uuid」=「N」を含むINVITEリクエストを会議サーバーに送信します。
  • 会議サーバーは200 OKレスポンスで応答します。 このレスポンスでは、「N」のUUIDが「local-uuid」としての一時的なUUID（「M1」）に置き換えられ、「remote-uuid」=「A」となります。

NOTE: this 'temporary' UUID is a real UUID; it is only temporary to the conference server because it knows that it is going to generate another UUID to replace the one just sent in the 200 OK response.

注：この「一時的な」UUIDは本物のUUIDです。 これが会議サーバーにとって一時的にすぎないのは、200 OKレスポンスで送信したばかりのUUIDを置き換える別のUUIDを生成することになるとわかっているからです。

  • Once Alice, the user, gains access to the IVR for this conference server, she enters a specific conference ID and whatever passcode (if needed) to enter a specific conference call.
  • Once the conference server is satisfied Alice has identified which conference she wants to attend (including any passcode verification), the conference server re-INVITEs Alice to the specific conference and includes the Session-ID header field value component "local-uuid" = "M'" (and "remote-uuid" = "A") for that conference. All valid participants in the same conference will receive this same UUID for identification purposes and to better enable monitoring and tracking functions.
  • Bob goes through this two-step process of an INVITE transaction, followed by a re-INVITE transaction to get this same UUID ("M'") for the conference.
  • In this example, Carol (and each additional user) goes through the same procedures as Alice and Bob to get on this same conference.
  • ユーザーであるAliceは、この会議サーバーのIVRにアクセスすると、特定の会議通話に入るために、特定の会議IDと（必要であれば）パスコードを入力します。
  • Aliceが出席したい会議を特定したこと（パスコードの検証を含む）を会議サーバーが確認すると、会議サーバーはAliceを特定の会議にre-INVITEし、その会議のSession-IDヘッダーフィールド値のコンポーネント「local-uuid」=「M'」（および「remote-uuid」=「A」）を含めます。 同じ会議の有効な参加者はすべて、識別のため、および監視と追跡の機能をよりよく実現するために、この同じUUIDを受け取ります。
  • Bobも、会議用のこの同じUUID（「M'」）を得るために、INVITEトランザクションに続いてre-INVITEトランザクションを行うというこの2段階のプロセスを経ます。
  • この例では、Carol（および追加の各ユーザー）も、この同じ会議に参加するためにAliceやBobと同じ手順を経ます。

10.5. Single Focus Conferencing Using a Web-Based Conference Service

10.5. Webベースの会議サービスを使用した単一フォーカスの会議

Alice, Bob, and Carol call into the same web-based conference. Note that this is one of many ways of implementing this functionality, and it should not be construed as the preferred way of establishing a web-based conference.

Alice、Bob、Carolは、同じWebベースの会議にコールインします。 これはこの機能を実装する多くの方法の1つであり、Webベースの会議を確立するための推奨される方法と解釈すべきではないことに注意してください。

General operation of this example:

この例の一般的な動作は次のとおりです。

  • Alice communicates with the web server that she wants to join a certain meeting by using a meeting number and including UA-Alice's contact information (phone number, URI, and/or IP address, etc.) for each device she wants for this conference call. For example, the audio and video (A/V) play-out devices could be separate units.
  • The Conference Focus server sends the INVITE request (Session-ID header field value components "local-uuid" = "M" and a remote UUID of "N", where "M" equals the "local-uuid" for each participant on this conference bridge) to UA-Alice to start a session with that server for this A/V conference call.
  • Upon receiving the INVITE request from the conference focus server, Alice responds with a 200 OK. Her UA moves the "local-uuid" unchanged into the "remote-uuid" field, generates her own UUID, and places that into the "local-uuid" field to complete the Session-ID construction.
  • Bob and Carol perform same function to join this same A/V conference call as Alice.
  • Aliceは、会議番号を使い、この会議通話に使いたい各装置についてUA-Aliceの連絡先情報（電話番号、URI、IPアドレスなど）を含めて、ある会議に参加したいことをWebサーバーに伝えます。 たとえば、音声とビデオ（A/V）の再生装置は別々のユニットである場合があります。
  • 会議フォーカスサーバーは、このA/V会議通話のためにそのサーバーとのセッションを開始するために、INVITEリクエスト（Session-IDヘッダーフィールド値のコンポーネントは「local-uuid」=「M」とリモートUUID「N」で、「M」はこの会議ブリッジの各参加者の「local-uuid」と等しい）をUA-Aliceに送信します。
  • 会議フォーカスサーバーからINVITEリクエストを受信すると、Aliceは200 OKで応答します。 AliceのUAは、「local-uuid」を変更せずに「remote-uuid」フィールドに移し、自身のUUIDを生成して「local-uuid」フィールドに置き、Session-IDの構築を完了します。
  • BobとCarolも、Aliceと同様に、この同じA/V会議通話に参加するために同じ動作を行います。

10.6. Cascading Conference Bridges

10.6. 会議ブリッジのカスケード接続

10.6.1. Establishing a Cascaded Conference

10.6.1. カスケード会議の確立

Expanding conferencing capabilities requires cascading conference bridges. A conference bridge, or MCU, needs a way to identify itself when contacting another MCU. [RFC4579] defines the "isfocus" Contact header field value parameter just for this purpose.

会議機能を拡張するには、会議ブリッジをカスケード接続する必要があります。 会議ブリッジ、つまりMCUは、別のMCUに接続するときに自身を識別する方法を必要とします。 [RFC4579]は、まさにこの目的のために「isfocus」というContactヘッダーフィールド値パラメーターを定義しています。

Regardless of which MCU (1 or 2) a UA contacts for this conference, once the above exchange has been received and acknowledged, the UA will get the same {M',N} UUID pair from the MCU for the complete session identifier.

UAがこの会議のためにどちらのMCU（1または2）に接続するかにかかわらず、上記のやり取りが受信され確認応答されると、UAは完全なセッション識別子のためにMCUから同じ{M',N}のUUIDの組を得ます。

A more complex form would be a series of MCUs all being informed of the same UUID to use for a specific conference. This series of MCUs can be informed in one of two ways:

より複雑な形態としては、一連のMCUすべてに、特定の会議で使用する同じUUIDを知らせるものがあります。 この一連のMCUには、次の2つの方法のいずれかで知らせることができます。

  • All by one MCU (that initially generates the UUID for the conference).
  • The MCU that generates the UUID informs one or several MCUs of this common UUID, and then they inform downstream MCUs of this common UUID that each will be using for this one conference.
  • すべてを1つのMCU（最初に会議のUUIDを生成するMCU）が知らせる。
  • UUIDを生成するMCUが1つまたは複数のMCUにこの共通のUUIDを知らせ、次にそれらのMCUが、この1つの会議でそれぞれが使用するこの共通のUUIDを下流のMCUに知らせる。

General operation of this example:

この例の一般的な動作は次のとおりです。

  • The MCU generating the session identifier UUID communicates this in a separate INVITE, having a Contact header with the "isfocus" Contact header field value parameter. This will identify the MCU as what [RFC4579] calls a "conference-aware" SIP entity.
  • An MCU that receives this {M',N} UUID pair in an inter-MCU transaction can communicate the M' UUID in a manner in which it was received to construct a hierarchical cascade (though this time this second MCU would be the UAC MCU).
  • Once the conference is terminated, the cascaded MCUs will receive a BYE message to terminate the cascade.
  • セッション識別子UUIDを生成するMCUは、「isfocus」Contactヘッダーフィールド値パラメーターを持つContactヘッダーを含む別のINVITEで、これを伝えます。 これにより、そのMCUは、[RFC4579]で「会議対応（conference-aware）」SIPエンティティーと呼ばれるものとして識別されます。
  • MCU間のトランザクションでこの{M',N}のUUIDの組を受信したMCUは、受信したのと同じ方法でM'のUUIDを伝えて、階層的なカスケードを構築することができます（ただし、このときはこの2番目のMCUがUAC側のMCUになります）。
  • 会議が終了すると、カスケード接続されたMCUは、カスケードを終了するためのBYEメッセージを受信します。

10.6.2. Calling Into Cascaded Conference Bridges

10.6.2. カスケード接続された会議ブリッジへのコールイン

Here is an example of how a UA, Robert for example, calls into a cascaded conference focus. Because MCU-1 has already contacted MCU-3 (the MCU where Robert is going to join the conference), MCU-3 already has the Session-ID (M') for this particular conference call.

以下は、UA（たとえばRobert）が、カスケード接続された会議フォーカスにどのようにコールインするかの例です。 MCU-1はすでにMCU-3（Robertが会議に参加しようとしているMCU）に接続しているため、MCU-3はこの特定の会議通話のSession-ID（M'）をすでに持っています。

General operation of this example:

この例の一般的な動作は次のとおりです。

  • The UA, Robert in this case, INVITEs the MCU to join a particular conference call. Robert's UA does not know anything about whether this is the main MCU of the conference call or a cascaded MCU. Robert likely does not know MCUs can be cascaded, he just wants to join a particular call. As is the case with any standard implementation, he includes a nil "remote-uuid".
  • The cascaded MCU, upon receiving this INVITE request from Robert, replaces the nil UUID with the UUID value communicated from MCU-1 for this conference call as the "local-uuid" in the SIP response, thus moving Robert's UUID "R" to the "remote-uuid" value.
  • The ACK has the Session-ID {R,M'}, completing the three-way handshake for this call establishment. Robert has now joined the conference call originated from MCU-1.
  • Once the conference is terminated, the cascaded MCUs will receive a BYE message to terminate the cascade.
  • UA（この場合はRobert）は、特定の会議通話に参加するためにMCUをINVITEします。 RobertのUAは、これが会議通話のメインのMCUなのか、カスケード接続されたMCUなのかについて何も知りません。 Robertはおそらく、MCUがカスケード接続できることを知らず、単に特定の通話に参加したいだけです。 標準的な実装と同様に、Robertはnilの「remote-uuid」を含めます。
  • カスケード接続されたMCUは、RobertからこのINVITEリクエストを受信すると、SIPレスポンスにおいて、nil UUIDを、MCU-1からこの会議通話用に伝えられたUUID値で「local-uuid」として置き換え、RobertのUUID「R」を「remote-uuid」値に移します。
  • ACKはSession-ID{R,M'}を持ち、この通話確立のための3ウェイハンドシェイクを完了します。 これでRobertは、MCU-1から発信された会議通話に参加しました。
  • 会議が終了すると、カスケード接続されたMCUは、カスケードを終了するためのBYEメッセージを受信します。

10.7. Basic 3PCC for Two UAs

10.7. 2つのUAに対する基本的な3PCC

An external entity sets up calls to both Alice and Bob for them to talk to each other.

外部のエンティティーが、AliceとBobが互いに話せるように、両者への通話を設定します。

General operation of this example:

この例の一般的な動作は次のとおりです。

  • Some out-of-band procedure directs a B2BUA (or other SIP server) to have Alice and Bob talk to each other. In this case, the SIP server has to be transaction stateful, if not dialog stateful.
  • The SIP server INVITEs Alice to a session and uses a temporary UUID {X} and a nil UUID pairing.
  • Alice receives and accepts this call setup and replaces the nil UUID with her UUID {A} in the session identifier, now {A,X}.
  • The transaction-stateful SIP server receives Alice's UUID {A} in the local UUID portion and keeps it there; and it discards its own UUID {X}, replacing this with a nil UUID value in the INVITE request to Bob as if this came from Alice originally.
  • Bob receives and accepts this INVITE request and adds his own UUID {B} to the session identifier, now {B,A}, for the response.
  • The session is established.
  • 何らかの帯域外の手順により、B2BUA（またはその他のSIPサーバー）に対して、AliceとBobが互いに話せるようにするよう指示します。 この場合、SIPサーバーは、ダイアログステートフルでないとしても、トランザクションステートフルである必要があります。
  • SIPサーバーはAliceをセッションにINVITEし、一時的なUUID{X}とnil UUIDの組を使用します。
  • Aliceはこの通話の設定を受信して受け入れ、セッション識別子のnil UUIDを自身のUUID{A}に置き換えて{A,X}とします。
  • トランザクションステートフルなSIPサーバーは、ローカルUUID部分にあるAliceのUUID{A}を受信してそのまま残し、自身のUUID{X}を破棄して、あたかも元々Aliceから来たかのように、BobへのINVITEリクエストではそれをnil UUID値に置き換えます。
  • BobはこのINVITEリクエストを受信して受け入れ、レスポンスのためにセッション識別子に自身のUUID{B}を追加して{B,A}とします。
  • セッションが確立されます。

10.8. Handling in 100 Trying SIP Response and CANCEL Request

10.8. 100 Trying SIPレスポンスとCANCELリクエストにおける扱い

The following two subsections show examples of the session identifier for a 100 Trying response and a CANCEL request in a single call flow.

以下の2つのサブセクションでは、1つのコールフローにおける100 TryingレスポンスとCANCELリクエストのセッション識別子の例を示します。

10.8.1. Handling in a 100 Trying SIP Response

10.8.1. 100 Trying SIPレスポンスにおける扱い

The following 100 Trying response is taken from [RFC5359], Section 2.9 ("Call Forwarding - No Answer").

Below is the explanatory text from RFC 5359, Section 2.9, detailing what the desired behavior is in the above call flow (i.e., what the call flow is attempting to achieve).

以下は、上記のコールフローで望まれる振る舞い（つまり、コールフローが実現しようとしていること）を詳しく述べた、RFC 5359のセクション2.9の説明文です。

Bob wants calls to B1 forwarded to B2 if B1 is not answered (information is known to the SIP server). Alice calls B1, and no one answers. The SIP server then places the call to B2.

Bobは、B1が応答しない場合にB1への通話をB2に転送したいと考えています（この情報はSIPサーバーが知っています）。 AliceがB1に電話をかけますが、誰も応答しません。 そこでSIPサーバーはB2に通話を発信します。

General operation of this example:

この例の一般的な動作は次のとおりです。

  • Alice generates an INVITE request because she wants to invite Bob to join her session. She creates a UUID as described in Section 10.1, and she places that value in the "local-uuid" field of the Session-ID header field value. Alice also generates a "remote-uuid" of nil and sends this along with the "local-uuid".
  • The SIP server (imagine this is a B2BUA), upon receiving Alice's INVITE request, generates the optional provisional response 100 Trying. Since the SIP server has no knowledge of Bob's UUID for his part of the session identifier value, it cannot include his "local-uuid". Rather, any 100 Trying response includes Alice's UUID in the "remote-uuid" portion of the Session-ID header-value with a nil "local-uuid" value in the response. This is consistent with what Alice's UA expects to receive in any SIP response containing this UUID.
  • Aliceは、Bobを自分のセッションに招待したいので、INVITEリクエストを生成します。 Aliceはセクション10.1で説明したようにUUIDを作成し、その値をSession-IDヘッダーフィールド値の「local-uuid」フィールドに置きます。 また、Aliceはnilの「remote-uuid」を生成し、これを「local-uuid」とともに送信します。
  • SIPサーバー（これはB2BUAだと考えてください）は、AliceのINVITEリクエストを受信すると、任意の暫定レスポンスである100 Tryingを生成します。 SIPサーバーは、セッション識別子の値のうちBobの部分であるBobのUUIDを知らないため、Bobの「local-uuid」を含めることはできません。 代わりに、100 Tryingレスポンスはすべて、Session-IDヘッダー値の「remote-uuid」部分にAliceのUUIDを含め、レスポンスの「local-uuid」値はnilになります。 これは、このUUIDを含むSIPレスポンスでAliceのUAが受信を想定しているものと一致します。

11. Compatibility with a Previous Implementation

11. 以前の実装との互換性

There is a much earlier document that specifies the use of a Session-ID header field (namely, [RFC7329]) that we will herewith attempt to achieve backwards compatibility. Neither Session-ID header field has any versioning information, so merely adding that this document describes "version 2" is insufficient. This section contains the set of rules for compatibility between the two specifications. Although the previous version was never standardized, it has been heavily implemented and adopted by other standards development organizations. For the purposes of this discussion, we will label the pre-standard specification of the Session-ID as the "old" version and this specification as the "new" version of the Session-ID.

Session-IDヘッダーフィールドの使用を規定した、ずっと以前の文書（すなわち[RFC7329]）があり、ここではそれとの後方互換性の実現を試みます。 どちらのSession-IDヘッダーフィールドにもバージョン情報がないため、この文書が「バージョン2」を記述していると付け加えるだけでは不十分です。 このセクションには、2つの仕様間の互換性のための一連の規則が含まれています。 以前のバージョンは標準化されませんでしたが、広く実装されており、他の標準化団体でも採用されています。 この議論の目的上、Session-IDの標準化前の仕様を「旧」バージョン、この仕様をSession-IDの「新」バージョンと呼びます。

The previous (i.e., "old") version only has a single UUID value as a Session-ID header field value, but has a generic-parameter value that can be of use.

以前の（つまり「旧」）バージョンは、Session-IDヘッダーフィールド値として1つのUUID値しか持ちませんが、利用可能なgeneric-parameter値を持っています。

In order to have an "old" version talk to an "old" version implementation, nothing needs to be done as far as the IETF is concerned.

「旧」バージョンが「旧」バージョンの実装と通信するためには、IETFに関する限り、何もする必要はありません。

In order to have a "new" version talk to a "new" version implementation, both implementations need to follow this document (to the letter) and everything should be just fine.

「新」バージョンが「新」バージョンの実装と通信するためには、両方の実装がこの文書に（文字どおり）従う必要があり、そうすればすべてうまくいくはずです。

For this "new" implementation to work with the "old" implementation and an "old" implementation to work with "new" implementations, there needs to be a set of rules that all "new" implementations MUST follow if the "new" implementation will be communicating with devices that have implemented the "old" implementation.

この「新」実装が「旧」実装と連携し、「旧」実装が「新」実装と連携するためには、「新」実装が「旧」実装を実装した装置と通信する場合に、すべての「新」実装が従わなければなりません（MUST）一連の規則が必要です。

  • Since no option tags or feature tags are to be used for distinguishing versions, the presence and order of any "remote-uuid" value within the Session-ID header field value is to be used to distinguish implementation versions.
  • If a SIP request has a "remote-uuid" value, this comes from a standard implementation, and not a pre-standard one.
  • If a SIP request has no "remote-uuid" value, this comes from a pre-standard implementation, and not a standard one. In this case, one UUID is used to identify this dialog, even if the responder is a standard implementor of this specification.
  • If a SIP response has a non-nil "local-uuid" that is 32 octets long and differs from the endpoint's own UUID value, this response comes from a standard implementation.
  • If a SIP response arrives that has the same value of Session-ID UUIDs in the same order as was sent, this comes from a pre-standard implementation and MUST NOT be discarded even though the "remote-uuid" may be nil. In this case, any new transaction within this dialog MUST preserve the order of the two UUIDs within all Session-ID header fields, including the ACK, until this dialog is terminated.
  • If a SIP response only contains the "local-uuid" that was sent originally, this comes from a pre-standard implementation and MUST NOT be discarded for removing the nil "remote-uuid". In this case, all future transactions within this dialog MUST contain only the UUID received in the first SIP response. Any new transaction starting a new dialog from the standard Session-ID implementation MUST include a "local-uuid" and a nil "remote-uuid", even if that new dialog is between the same two UAs.
  • Standard implementations should not expect pre-standard implementations to be consistent in their implementation, even within the same dialog. For example, perhaps the first, third, and tenth responses contain a "remote-uuid", but all the others do not. This behavior MUST be allowed by implementations of this specification.
  • The foregoing does not apply to other, presently unknown parameters that might be defined in the future. They are ignored for the purposes of interoperability with previous implementations.
  • バージョンの区別にはオプションタグや機能タグを使用しないため、Session-IDヘッダーフィールド値内の「remote-uuid」値の有無と順序を使用して、実装のバージョンを区別します。
  • SIPリクエストに「remote-uuid」値がある場合、これは標準化前の実装ではなく標準の実装から来たものです。
  • SIPリクエストに「remote-uuid」値がない場合、これは標準の実装ではなく標準化前の実装から来たものです。 この場合、応答側がこの仕様の標準の実装者であっても、このダイアログの識別には1つのUUIDが使用されます。
  • SIPレスポンスが、長さが32オクテットで、エンドポイント自身のUUID値とは異なるnilでない「local-uuid」を持つ場合、このレスポンスは標準の実装から来たものです。
  • 送信したときと同じ順序で同じSession-IDのUUIDの値を持つSIPレスポンスが届いた場合、これは標準化前の実装から来たものであり、「remote-uuid」がnilである可能性があっても破棄してはなりません（MUST NOT）。 この場合、このダイアログ内の新しいトランザクションはすべて、このダイアログが終了するまで、ACKを含むすべてのSession-IDヘッダーフィールド内の2つのUUIDの順序を維持しなければなりません（MUST）。
  • SIPレスポンスに元々送信した「local-uuid」だけが含まれている場合、これは標準化前の実装から来たものであり、nilの「remote-uuid」を取り除いたことを理由に破棄してはなりません（MUST NOT）。 この場合、このダイアログ内の今後のすべてのトランザクションは、最初のSIPレスポンスで受信したUUIDだけを含めなければなりません（MUST）。 標準のSession-ID実装から新しいダイアログを開始する新しいトランザクションは、その新しいダイアログが同じ2つのUAの間のものであっても、「local-uuid」とnilの「remote-uuid」を含めなければなりません（MUST）。
  • 標準の実装は、標準化前の実装が、同じダイアログ内であっても、その実装において一貫していることを期待すべきではありません。 たとえば、1番目、3番目、10番目のレスポンスには「remote-uuid」が含まれているが、それ以外のレスポンスには含まれていないということもあり得ます。 この仕様の実装は、この振る舞いを許容しなければなりません（MUST）。
  • 前述の内容は、将来定義される可能性のある、現在は未知の他のパラメーターには適用されません。 それらは、以前の実装との相互運用性の目的では無視されます。

12. Security and Privacy Considerations

12. セキュリティーとプライバシーに関する考慮事項

The session identifier MUST be constructed in such a way that does not convey any user or device information as outlined in Section 4.1. This ensures that the data contained in the session identifier itself does not convey user or device information; however, the session identifier may reveal relationships between endpoints that might not be revealed by messages without a session identifier.

セクション4.1で概説したように、セッション識別子は、ユーザーや装置の情報を一切伝えない方法で構築しなければなりません（MUST）。 これにより、セッション識別子自体に含まれるデータがユーザーや装置の情報を伝えないことが保証されます。 ただし、セッション識別子は、セッション識別子のないメッセージでは明らかにならないかもしれないエンドポイント間の関係を明らかにする可能性があります。

Section 4.2 requires that a UA always generate a new, previously unused UUID when transmitting a request to initiate a new session. This ensures that two unrelated sessions originating from the same UA will never have the same UUID value, thereby removing the ability for an attacker to use the session identifier to identify the two unrelated sessions as being associated with the same user.

セクション4.2では、新しいセッションを開始するリクエストを送信するとき、UAは常にこれまで使用されていない新しいUUIDを生成することを要求しています。 これにより、同じUAから発信された無関係な2つのセッションが同じUUID値を持つことはなくなり、攻撃者がセッション識別子を使って無関係な2つのセッションを同じユーザーに関連するものとして識別することができなくなります。

Because of the inherent property that session identifiers are conveyed end-to-end and remain unchanged by a UA for the duration of a session, the session identifier could be misused to discover relationships between two or more parties when multiple parties are involved in the same session such as the case of a redirect, transfer, or conference. For example, suppose that Alice calls Bob and Bob, via his PBX (acting as a B2BUA), forwards or transfers the call to Carol. Without use of the session identifier, an unauthorized third party that is observing the communications between Alice and Bob might not know that Alice is actually communicating with Carol. If Alice, Bob, and Carol include the session identifier as a part of the signaling messages, it is possible for the third party to observe that the UA associated with Bob changed to some other UA. If the third party also has access to signaling messages between Bob and Carol, the third party can then discover that Alice is communicating with Carol. This would be true even if all other information relating to the session is changed by the PBX, including both signaling information and media address information. That said, the session identifier would not reveal the identity of Alice, Bob, or Carol. It would only reveal the fact that those endpoints were associated with the same session.

セッション識別子はエンドツーエンドで伝えられ、セッションの期間中UAによって変更されないという本質的な性質があるため、リダイレクト、転送、会議の場合のように複数の当事者が同じセッションに関与するとき、セッション識別子が悪用されて2つ以上の当事者間の関係が発見される可能性があります。 たとえば、AliceがBobに電話をかけ、Bobが（B2BUAとして動作する）自身のPBXを介してその通話をCarolに転送する場合を考えてみてください。 セッション識別子を使用しなければ、AliceとBobの間の通信を観察している権限のない第三者は、Aliceが実際にはCarolと通信していることを知らないかもしれません。 Alice、Bob、Carolがシグナリングメッセージの一部としてセッション識別子を含めている場合、第三者は、Bobに関連付けられたUAが別のUAに変わったことを観察できる可能性があります。 第三者がBobとCarolの間のシグナリングメッセージにもアクセスできる場合、第三者はAliceがCarolと通信していることを発見できます。 これは、シグナリング情報とメディアアドレス情報の両方を含め、セッションに関する他のすべての情報がPBXによって変更されたとしても当てはまります。 とはいえ、セッション識別子は、Alice、Bob、Carolの身元を明らかにするわけではありません。 明らかにするのは、それらのエンドポイントが同じセッションに関連付けられていたという事実だけです。

This document allows for additional parameters (generic-param) to be included in the Session-ID header. This is done to allow for future extensions while preserving backward compatibility with this document. To protect privacy, the data for any generic-param included in the Session-ID header value MUST NOT include any user or device information. Additionally, any information conveyed through an additional parameter MUST NOT persist beyond the current session, and therefore MUST NOT be reused between unrelated sessions. Additional parameters MAY be used by future extensions of this document to correlate related communication sessions that cannot already be correlated by the procedures described in this document as long as the requirements regarding privacy and persistence defined above are followed.

この文書では、Session-IDヘッダーに追加のパラメーター（generic-param）を含めることを許可しています。 これは、この文書との後方互換性を保ちながら将来の拡張を可能にするためです。 プライバシーを保護するために、Session-IDヘッダー値に含まれるgeneric-paramのデータには、ユーザーや装置の情報を一切含めてはなりません（MUST NOT）。 さらに、追加のパラメーターを通じて伝えられる情報は、現在のセッションを超えて持続してはなりません（MUST NOT）。 したがって、無関係なセッション間で再利用してはなりません（MUST NOT）。 上で定義したプライバシーと持続性に関する要件に従う限り、この文書で説明する手順ではまだ相関させることができない関連する通信セッションを相関させるために、この文書の将来の拡張で追加のパラメーターを使用してもよいです（MAY）。

An intermediary implementing a privacy service that provides user privacy as per Section 5.3 of [RFC3323] MAY choose to consider the Session-ID header as being a nonessential informational header with the understanding that doing so will impair the ability to use the session identifier for troubleshooting purposes.

[RFC3323]のセクション5.3に従ってユーザーのプライバシーを提供するプライバシーサービスを実装している仲介者は、そうすることでトラブルシューティングの目的でセッション識別子を使用する能力が損なわれることを理解したうえで、Session-IDヘッダーを必須ではない情報提供用のヘッダーとみなすことを選択してもよいです（MAY）。
