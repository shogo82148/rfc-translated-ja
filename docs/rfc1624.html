RFC 1624

Computation of the Internet Checksum via Incremental Update

RFC 1624

差分更新によるインターネットチェックサムの計算

Abstract

概要

This memo describes an updated technique for incremental computation of the standard Internet checksum. It updates the method described in RFC 1141.

このメモは、標準のインターネットチェックサムを差分計算するための改訂された手法を記述します。このメモは、RFC 1141で記述された方法を更新します。

Status of This Memo

このメモのステータス

This memo provides information for the Internet community. This memo does not specify an Internet standard of any kind. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーに情報を提供するものです。いかなる種類のインターネット標準も規定するものではありません。このメモの配布は無制限です。

1. Introduction

1. はじめに

Incremental checksum update is useful in speeding up several types of operations routinely performed on IP packets, such as TTL update, IP fragmentation, and source route update.

チェックサムの差分更新は、TTLの更新、IPのフラグメンテーション、ソースルートの更新など、IPパケットに対して日常的に行われるいくつかの種類の操作を高速化するのに役立ちます。

RFC 1071, on pages 4 and 5, describes a procedure to incrementally update the standard Internet checksum. The relevant discussion, though comprehensive, was not complete. Therefore, RFC 1141 was published to replace this description on Incremental Update. In particular, RFC 1141 provides a more detailed exposure to the procedure described in RFC 1071. However, it computes a result for certain cases that differs from the one obtained from scratch (one's complement of one's complement sum of the original fields).

RFC 1071は、4ページと5ページで、標準のインターネットチェックサムを差分更新する手順を記述しています。この議論は包括的ではあるものの、完全ではありませんでした。そのため、差分更新に関するこの記述を置き換えるためにRFC 1141が発行されました。特に、RFC 1141はRFC 1071で記述された手順をより詳細に説明しています。しかし、RFC 1141は、ある特定の場合に、最初から計算して得られる結果（元のフィールドの1の補数和の1の補数）とは異なる結果を算出します。

For the sake of completeness, this memo briefly highlights key points from RFCs 1071 and 1141. Based on these discussions, an updated procedure to incrementally compute the standard Internet checksum is developed and presented.

完全を期すために、このメモではRFC 1071とRFC 1141の要点を簡単に取り上げます。これらの議論に基づいて、標準のインターネットチェックサムを差分計算するための改訂された手順を導き、提示します。

2. Notation and Equations

2. 表記と式

Given the following notation:

次の表記を用います。

       HC  - old checksum in header
       C   - one's complement sum of old header
       HC' - new checksum in header
       C'  - one's complement sum of new header
       m   - old value of a 16-bit field
       m'  - new value of a 16-bit field

       HC  - old checksum in header
       C   - one's complement sum of old header
       HC' - new checksum in header
       C'  - one's complement sum of new header
       m   - old value of a 16-bit field
       m'  - new value of a 16-bit field

RFC 1071 states that C' is:

RFC 1071では、C'は次のようになるとしています。

       C' = C + (-m) + m'    --    [Eqn. 1]
          = C + (m' - m)

       C' = C + (-m) + m'    --    [Eqn. 1]
          = C + (m' - m)

As RFC 1141 points out, the equation above is not useful for direct use in incremental updates since C and C' do not refer to the actual checksum stored in the header. In addition, it is pointed out that RFC 1071 did not specify that all arithmetic must be performed using one's complement arithmetic.

RFC 1141が指摘しているように、CとC'はヘッダーに格納された実際のチェックサムを指すものではないため、上の式を差分更新にそのまま使うことはできません。さらに、すべての演算を1の補数演算で行わなければならないことをRFC 1071が規定していなかったことも指摘されています。

Finally, complementing the above equation to get the actual checksum, RFC 1141 presents the following:

最後に、実際のチェックサムを得るために上の式の補数を取って、RFC 1141は次の式を示しています。

       HC' = ~(C + (-m) + m')
           = HC + (m - m')
           = HC + m + ~m'    --    [Eqn. 2]

       HC' = ~(C + (-m) + m')
           = HC + (m - m')
           = HC + m + ~m'    --    [Eqn. 2]

3. Discussion

3. 議論

Although this equation appears to work, there are boundary conditions under which it produces a result which differs from the one obtained by checksum computation from scratch. This is due to the way zero is handled in one's complement arithmetic.

この式はうまく機能するように見えますが、最初からチェックサムを計算して得られる結果とは異なる結果を生じる境界条件があります。これは、1の補数演算におけるゼロの扱い方に起因します。

In one's complement, there are two representations of zero: the all zero and the all one bit values, often referred to as +0 and -0. One's complement addition of non-zero inputs can produce -0 as a result, but never +0. Since there is guaranteed to be at least one non-zero field in the IP header, and the checksum field in the protocol header is the complement of the sum, the checksum field can never contain ~(+0), which is -0 (0xFFFF). It can, however, contain ~(-0), which is +0 (0x0000).

1の補数では、ゼロに2つの表現があります。すべてのビットが0の値とすべてのビットが1の値で、それぞれ+0、-0と呼ばれることがよくあります。ゼロでない入力どうしの1の補数加算は、結果として-0を生じることはあっても、+0を生じることはありません。IPヘッダーにはゼロでないフィールドが少なくとも1つあることが保証されており、プロトコルヘッダーのチェックサムフィールドは和の補数であるため、チェックサムフィールドが~(+0)、すなわち-0（0xFFFF）を含むことはありえません。しかし、~(-0)、すなわち+0（0x0000）を含むことはありえます。

RFC 1141 yields an updated header checksum of -0 when it should be +0. This is because it assumed that one's complement has a distributive property, which does not hold when the result is 0 (see derivation of [Eqn. 2]).

RFC 1141は、更新後のヘッダーチェックサムが+0となるべきときに-0を算出します。これは、1の補数が分配法則を満たすと仮定しているためですが、この性質は結果が0のときには成り立ちません（[Eqn. 2]の導出を参照）。

The problem is avoided by not assuming this property. The correct equation is given below:

この問題は、この性質を仮定しないことで回避できます。正しい式を次に示します。

       HC' = ~(C + (-m) + m')    --    [Eqn. 3]
           = ~(~HC + ~m + m')

       HC' = ~(C + (-m) + m')    --    [Eqn. 3]
           = ~(~HC + ~m + m')

4. Examples

4. 例

Consider an IP packet header in which a 16-bit field m = 0x5555 changes to m' = 0x3285. Also, the one's complement sum of all other header octets is 0xCD7A.

16ビットのフィールドがm = 0x5555からm' = 0x3285に変わるIPパケットヘッダーを考えます。また、ヘッダーのその他すべてのオクテットの1の補数和は0xCD7Aであるとします。

Then the header checksum would be:

このとき、ヘッダーチェックサムは次のようになります。

       HC = ~(0xCD7A + 0x5555)
          = ~0x22D0
          =  0xDD2F

       HC = ~(0xCD7A + 0x5555)
          = ~0x22D0
          =  0xDD2F

The new checksum via recomputation is:

再計算による新しいチェックサムは次のとおりです。

       HC' = ~(0xCD7A + 0x3285)
           = ~0xFFFF
           =  0x0000

       HC' = ~(0xCD7A + 0x3285)
           = ~0xFFFF
           =  0x0000

Using [Eqn. 2], as specified in RFC 1141, the new checksum is computed as:

RFC 1141で規定されているとおりに[Eqn. 2]を使うと、新しいチェックサムは次のように計算されます。

       HC' = HC + m + ~m'
           =  0xDD2F + 0x5555 + ~0x3285
           =  0xFFFF

       HC' = HC + m + ~m'
           =  0xDD2F + 0x5555 + ~0x3285
           =  0xFFFF

which does not match that computed from scratch, and moreover can never obtain for an IP header.

これは最初から計算した値と一致せず、しかもIPヘッダーでは決して得られるはずのない値です。

Applying [Eqn. 3] to the example above, we get the correct result:

上の例に[Eqn. 3]を適用すると、正しい結果が得られます。

       HC' = ~(C + (-m) + m')
           = ~(0x22D0 + ~0x5555 + 0x3285)
           = ~0xFFFF
           =  0x0000

       HC' = ~(C + (-m) + m')
           = ~(0x22D0 + ~0x5555 + 0x3285)
           = ~0xFFFF
           =  0x0000

5. Checksum verification by end systems

5. エンドシステムによるチェックサムの検証

If an end system verifies the checksum by including the checksum field itself in the one's complement sum and then comparing the result against -0, as recommended by RFC 1071, it does not matter if an intermediate system generated a -0 instead of +0 due to the RFC 1141 property described here. In the example above:

RFC 1071で推奨されているように、エンドシステムがチェックサムフィールド自体を1の補数和に含めてから、その結果を-0と比較することでチェックサムを検証するのであれば、ここで説明したRFC 1141の性質のために中間システムが+0の代わりに-0を生成したとしても問題はありません。上の例では次のようになります。

       0xCD7A + 0x3285 + 0xFFFF = 0xFFFF
       0xCD7A + 0x3285 + 0x0000 = 0xFFFF

       0xCD7A + 0x3285 + 0xFFFF = 0xFFFF
       0xCD7A + 0x3285 + 0x0000 = 0xFFFF

However, implementations exist which verify the checksum by computing it and comparing against the header checksum field.

しかし、チェックサムを計算し、それをヘッダーのチェックサムフィールドと比較することで検証する実装も存在します。

It is recommended that intermediate systems compute incremental checksum using the method described in this document, and end systems verify checksum as per the method described in RFC 1071.

中間システムはこの文書で説明した方法を使ってチェックサムを差分計算し、エンドシステムはRFC 1071で説明されている方法に従ってチェックサムを検証することを推奨します。

The method in [Eqn. 3] is slightly more expensive than the one in RFC 1141. If this is a concern, the two additional instructions can be eliminated by subtracting complements with borrow [see Sec. 7]. This would result in the following equation:

[Eqn. 3]の方法は、RFC 1141の方法よりもわずかにコストがかかります。これが問題となる場合は、ボロー付きで補数を減算することで、追加の2命令を取り除くことができます[セクション7を参照]。その結果、次の式になります。

       HC' = HC - ~m - m'    --    [Eqn. 4]

       HC' = HC - ~m - m'    --    [Eqn. 4]

In the example shown above,

上に示した例では、次のようになります。

       HC' = HC - ~m - m'
           =  0xDD2F - ~0x5555 - 0x3285
           =  0x0000

       HC' = HC - ~m - m'
           =  0xDD2F - ~0x5555 - 0x3285
           =  0x0000

6. Historical Note

6. 歴史的な注記

A historical aside: the fact that standard one's complement arithmetic produces negative zero results is one of its main drawbacks; it makes for difficulty in interpretation. In the CDC 6000 series computers [4], this problem was avoided by using subtraction as the primitive in one's complement arithmetic (i.e., addition is subtraction of the complement).

歴史的な余談です。標準的な1の補数演算が負のゼロという結果を生じることは、その主な欠点の1つであり、解釈を難しくします。CDC 6000シリーズのコンピューター[4]では、1の補数演算の基本演算として減算を用いること（つまり、加算は補数の減算として行うこと）で、この問題を回避していました。
