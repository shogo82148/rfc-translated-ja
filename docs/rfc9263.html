RFC 9263

Network Service Header (NSH) Metadata Type 2 Variable-Length Context Headers

RFC 9263

ネットワークサービスヘッダー（NSH）メタデータタイプ2の可変長コンテキストヘッダー

Abstract

概要

Service Function Chaining (SFC) uses the Network Service Header (NSH) (RFC 8300) to steer and provide context metadata (MD) with each packet. Such metadata can be of various types, including MD Type 2, consisting of Variable-Length Context Headers. This document specifies several such Context Headers that can be used within a Service Function Path (SFP).

サービス機能チェイニング（Service Function Chaining、SFC）は、ネットワークサービスヘッダー（Network Service Header、NSH）（RFC 8300）を使用して、各パケットを誘導し、各パケットにコンテキストメタデータ（MD）を付与します。このようなメタデータにはさまざまなタイプがあり、その中には可変長コンテキストヘッダーで構成されるMDタイプ2があります。この文書は、サービス機能パス（Service Function Path、SFP）内で使用できる、このようなコンテキストヘッダーをいくつか規定します。

1. Introduction

1. はじめに

The Network Service Header (NSH) [RFC8300] is the Service Function Chaining (SFC) encapsulation that supports the SFC architecture [RFC7665]. As such, the NSH provides the following key elements:

ネットワークサービスヘッダー（NSH）[RFC8300]は、SFCアーキテクチャー[RFC7665]をサポートするサービス機能チェイニング（SFC）のカプセル化です。そのため、NSHは次の主要な要素を提供します。

  1. Service Function Path (SFP) identification
  2. indication of location within an SFP
  3. optional, per-packet metadata (fixed-length or variable-length)
  1. サービス機能パス（SFP）の識別
  2. SFP内の位置の表示
  3. オプションの、パケットごとのメタデータ（固定長または可変長）

[RFC8300] further defines two metadata formats (MD Types): 1 and 2. MD Type 1 defines the fixed-length, 16-octet metadata, whereas MD Type 2 defines a variable-length context format for metadata. This document defines several common metadata Context Headers for use within NSH MD Type 2. These supplement the Subscriber Identifier and Performance Policy MD Type 2 metadata Context Headers specified in [RFC8979].

[RFC8300]はさらに、2つのメタデータ形式（MDタイプ）、1と2を定義しています。MDタイプ1は固定長の16オクテットのメタデータを定義し、MDタイプ2はメタデータのための可変長のコンテキスト形式を定義します。この文書は、NSH MDタイプ2で使用するための、いくつかの共通のメタデータのコンテキストヘッダーを定義します。 これらは、[RFC8979]で規定されている加入者識別子（Subscriber Identifier）と性能ポリシー（Performance Policy）のMDタイプ2メタデータのコンテキストヘッダーを補完するものです。

This document does not address metadata usage, updating/chaining of metadata, or other SFP functions. Those topics are described in [RFC8300].

この文書は、メタデータの使用法、メタデータの更新・連鎖、その他のSFPの機能は扱いません。これらのトピックは[RFC8300]で説明されています。

3. NSH MD Type 2 Format

3. NSH MDタイプ2の形式

An NSH is composed of a 4-octet Base Header, a 4-octet Service Path Header, and optional Context Headers. The Base Header identifies the MD Type in use:

NSHは、4オクテットのベースヘッダー（Base Header）、4オクテットのサービスパスヘッダー（Service Path Header）、およびオプションのコンテキストヘッダーで構成されます。ベースヘッダーは、使用中のMDタイプを識別します。

Please refer to the NSH [RFC8300] for a detailed header description.

ヘッダーの詳細な説明については、NSH[RFC8300]を参照してください。

When the Base Header specifies MD Type = 0x2, zero or more Variable-Length Context Headers MAY be added, immediately following the Service Path Header. Figure 2 below depicts the format of the Context Header as defined in Section 2.5.1 of [RFC8300].

ベースヘッダーがMD Type = 0x2を指定している場合、サービスパスヘッダーの直後に、0個以上の可変長コンテキストヘッダーを追加してもよいです（MAY）。以下のFigure 2は、[RFC8300]のSection 2.5.1で定義されているコンテキストヘッダーの形式を示しています。

4. NSH MD Type 2 Context Headers

4. NSH MDタイプ2のコンテキストヘッダー

[RFC8300] specifies Metadata Class 0x0000 as IETF Base NSH MD Class. In this document, metadata types are defined for the IETF Base NSH MD Class. The Context Headers specified in the subsections below are as follows:

[RFC8300]は、メタデータクラス0x0000をIETF Base NSH MD Classとして規定しています。この文書では、IETF Base NSH MD Classのメタデータタイプを定義します。以下のサブセクションで規定するコンテキストヘッダーは次のとおりです。

  1. Forwarding Context
  2. Tenant ID
  3. Ingress Network Node Information
  4. Ingress Node Source Interface
  5. Flow ID
  6. Source and/or Destination Groups
  7. Policy ID
  1. 転送コンテキスト（Forwarding Context）
  2. テナントID（Tenant ID）
  3. 入口ネットワークノード情報（Ingress Network Node Information）
  4. 入口ノード送信元インターフェイス（Ingress Node Source Interface）
  5. フローID（Flow ID）
  6. 送信元グループと宛先グループ（Source and/or Destination Groups）
  7. ポリシーID（Policy ID）

4.1. Forwarding Context

4.1. 転送コンテキスト

This metadata context carries a network forwarding context, used for segregation and forwarding scope. Forwarding context can take several forms depending on the network environment, for example, Virtual eXtensible Local Area Network (VXLAN) / Generic Protocol Extension for VXLAN (VXLAN-GPE) Virtual Network Identifier (VNID), VPN Routing and Forwarding (VRF) identification, or VLAN.

このメタデータコンテキストは、分離と転送範囲のために使用される、ネットワークの転送コンテキストを運びます。 転送コンテキストは、ネットワーク環境に応じていくつかの形式をとることができます。たとえば、Virtual eXtensible Local Area Network（VXLAN）/ Generic Protocol Extension for VXLAN（VXLAN-GPE）の仮想ネットワーク識別子（Virtual Network Identifier、VNID）、VPNルーティングおよび転送（VPN Routing and Forwarding、VRF）の識別子、またはVLANです。

The fields are described as follows:

各フィールドは次のとおりです。

Context Type (CT):

This 4-bit field that defines the interpretation of the Forwarding Context field. Please see the IANA considerations in Section 6.2. This document defines these CT values:

0x0:
12-bit VLAN identifier [IEEE.802.1Q_2018]. See Figure 3.
0x1:
24-bit double tagging identifiers. A service VLAN tag followed by a customer VLAN tag [IEEE.802.1Q_2018]. The two VLAN IDs are concatenated and appear in the same order that they appeared in the payload. See Figure 4.
0x2:
20-bit MPLS VPN label [RFC3032] [RFC4364]. See Figure 5.
0x3:
24-bit virtual network identifier (VNI) [RFC8926]. See Figure 6.
0x4:
32-bit Session ID [RFC3931]. This is called Key in GRE [RFC2890]. See Figure 7.
Reserved (Resv):
These bits in the context fields MUST be sent as zero and ignored on receipt.
Context Type (CT):

Forwarding Contextフィールドの解釈を定義する4ビットのフィールドです。Section 6.2のIANAに関する考慮事項を参照してください。この文書は次のCT値を定義します。

0x0:
12ビットのVLAN識別子[IEEE.802.1Q_2018]。Figure 3を参照してください。
0x1:
24ビットの二重タギング識別子。サービスVLANタグの後に顧客VLANタグが続きます[IEEE.802.1Q_2018]。2つのVLAN IDは連結され、ペイロード内に現れたのと同じ順序で現れます。Figure 4を参照してください。
0x2:
20ビットのMPLS VPNラベル[RFC3032] [RFC4364]。Figure 5を参照してください。
0x3:
24ビットの仮想ネットワーク識別子（VNI）[RFC8926]。Figure 6を参照してください。
0x4:
32ビットのセッションID[RFC3931]。これはGRE[RFC2890]ではKeyと呼ばれます。Figure 7を参照してください。
Reserved (Resv):
コンテキストフィールド内のこれらのビットは、0として送信しなければなりません（MUST）。受信時には無視します。

4.2. Tenant ID

4.2. テナントID

Tenant identification is often used for segregation within a multi-tenant environment. Orchestration system-generated Tenant IDs are an example of such data. This Context Header carries the value of the Tenant ID. Virtual Tenant Network (VTN) [OpenDaylight-VTN] is an application that provides multi-tenant virtual networks on a Software-Defined Networking (SDN) controller.

テナントの識別は、マルチテナント環境内での分離によく使用されます。オーケストレーションシステムが生成するテナントIDは、そのようなデータの一例です。このコンテキストヘッダーは、テナントIDの値を運びます。Virtual Tenant Network（VTN）[OpenDaylight-VTN]は、Software-Defined Networking（SDN）コントローラー上でマルチテナントの仮想ネットワークを提供するアプリケーションです。

The fields are described as follows:

各フィールドは次のとおりです。

Length:
Indicates the length of the Tenant ID in octets (see Section 2.5.1 of [RFC8300]).
Tenant ID:
Represents an opaque value pointing to orchestration system-generated Tenant ID. The structure and semantics of this field are specific to the operator's deployment across its operational domain and are specified and assigned by an orchestration function. The specifics of that orchestration-based assignment are outside the scope of this document.
Length:
テナントIDの長さをオクテット単位で示します（[RFC8300]のSection 2.5.1を参照してください）。
Tenant ID:
オーケストレーションシステムが生成したテナントIDを指す不透明な値を表します。このフィールドの構造とセマンティクスは、運用者の運用ドメイン全体にわたる展開に固有のものであり、オーケストレーション機能によって規定され、割り当てられます。オーケストレーションに基づく割り当ての詳細は、この文書の範囲外です。

4.3. Ingress Network Node Information

4.3. 入口ネットワークノード情報

This Context Header carries a Node ID of the network node at which the packet entered the SFC-enabled domain. This node will necessarily be a classifier [RFC7665]. In cases where the Service Path Identifier (SPI) identifies the ingress node, this Context Header is superfluous.

このコンテキストヘッダーは、パケットがSFC対応ドメインに入ったネットワークノードのノードIDを運びます。このノードは必ず分類器[RFC7665]になります。サービスパス識別子（Service Path Identifier、SPI）が入口ノードを識別する場合、このコンテキストヘッダーは不要です。

The fields are described as follows:

各フィールドは次のとおりです。

Length:
Indicates the length of the Node ID in octets (see Section 2.5.1 of [RFC8300]).
Node ID:
Represents an opaque value of the ingress network Node ID. The structure and semantics of this field are deployment specific. For example, Node ID may be a 4-octet IPv4 address Node ID, a 16-octet IPv6 address Node ID, a 6-octet MAC address, an 8-octet MAC address (64-bit Extended Unique Identifier (EUI-64)), etc.
Length:
ノードIDの長さをオクテット単位で示します（[RFC8300]のSection 2.5.1を参照してください）。
Node ID:
入口ネットワークのノードIDの不透明な値を表します。このフィールドの構造とセマンティクスは展開に固有です。たとえば、ノードIDは、4オクテットのIPv4アドレスのノードID、16オクテットのIPv6アドレスのノードID、6オクテットのMACアドレス、8オクテットのMACアドレス（64ビット拡張一意識別子（64-bit Extended Unique Identifier、EUI-64））などです。

4.4. Ingress Network Source Interface

4.4. 入口ネットワーク送信元インターフェイス

This context identifies the ingress interface of the ingress network node. The l2vlan (135), l3ipvlan (136), ipForward (142), and mpls (166) in [IANAifType] are examples of source interfaces.

このコンテキストは、入口ネットワークノードの入口インターフェイスを識別します。[IANAifType]のl2vlan（135）、l3ipvlan（136）、ipForward（142）、mpls（166）は、送信元インターフェイスの例です。

The fields are described as follows:

各フィールドは次のとおりです。

Length:
Indicates the length of the Source Interface in octets (see Section 2.5.1 of [RFC8300]).
Source Interface:
Represents an opaque value of the identifier of the ingress interface of the ingress network node.
Length:
送信元インターフェイスの長さをオクテット単位で示します（[RFC8300]のSection 2.5.1を参照してください）。
Source Interface:
入口ネットワークノードの入口インターフェイスの識別子の不透明な値を表します。

4.5. Flow ID

4.5. フローID

Flow ID provides a field in NSH MD Type 2 to label packets belonging to the same flow. For example, [RFC8200] defines IPv6 Flow Label as Flow ID. Another example of Flow ID is how [RFC6790] defines an entropy label that is generated based on flow information in the MPLS network. Absence of this field or a value of zero denotes that packets have not been labeled with a Flow ID.

フローIDは、同じフローに属するパケットにラベルを付けるためのフィールドをNSH MDタイプ2に提供します。たとえば、[RFC8200]はIPv6フローラベルをフローIDとして定義しています。フローIDの別の例として、[RFC6790]は、MPLSネットワークにおいてフロー情報に基づいて生成されるエントロピーラベルを定義しています。このフィールドがないか、値が0の場合は、パケットにフローIDのラベルが付けられていないことを示します。

The fields are described as follows:

各フィールドは次のとおりです。

Length:
Indicates the length of the Flow ID in octets (see Section 2.5.1 of [RFC8300]). For example, the IPv6 Flow Label in [RFC8200] is 20 bits long. An entropy label in the MPLS network in [RFC6790] is also 20 bits long.
Context Type (CT):

This 4-bit field that defines the interpretation of the Flow ID field. Please see the IANA considerations in Section 6.3. This document defines these CT values:

0x0:
20-bit IPv6 Flow Label in [RFC8200]. See Figure 11.
0x1:
20-bit entropy label in the MPLS network in [RFC6790]. See Figure 12.
Reserved:
These bits in the context fields MUST be sent as zero and ignored on receipt.
Length:
フローIDの長さをオクテット単位で示します（[RFC8300]のSection 2.5.1を参照してください）。たとえば、[RFC8200]のIPv6フローラベルは20ビット長です。[RFC6790]のMPLSネットワークにおけるエントロピーラベルも20ビット長です。
Context Type (CT):

Flow IDフィールドの解釈を定義する4ビットのフィールドです。Section 6.3のIANAに関する考慮事項を参照してください。この文書は次のCT値を定義します。

0x0:
[RFC8200]の20ビットのIPv6フローラベル。Figure 11を参照してください。
0x1:
[RFC6790]のMPLSネットワークにおける20ビットのエントロピーラベル。Figure 12を参照してください。
Reserved:
コンテキストフィールド内のこれらのビットは、0として送信しなければなりません（MUST）。受信時には無視します。

4.6. Source and/or Destination Groups

4.6. 送信元グループと宛先グループ

Intent-based systems can use this data to express the logical grouping of source and/or destination objects. [OpenStack] and [OpenDaylight] provide examples of such a system. Each is expressed as a 32-bit opaque object.

インテントベースのシステムは、このデータを使用して、送信元オブジェクトや宛先オブジェクトの論理的なグループ化を表現できます。 [OpenStack]と[OpenDaylight]は、そのようなシステムの例を示しています。それぞれは32ビットの不透明なオブジェクトとして表現されます。

If there is no group information specified for the Source Group or Destination Group field, the field MUST be sent as zero and ignored on receipt.

Source GroupフィールドまたはDestination Groupフィールドに指定するグループ情報がない場合、そのフィールドは0として送信しなければなりません（MUST）。受信時には無視します。

4.7. Policy ID

4.7. ポリシーID

Traffic handling policies are often referred to by a system-generated identifier, which is then used by the devices to look up the policy's content locally. For example, this identifier could be an index to an array, a lookup key, or a database ID. The identifier allows enforcement agents or services to look up the content of their part of the policy.

トラフィック処理のポリシーは、システムが生成した識別子によって参照されることがよくあります。この識別子は、デバイスがポリシーの内容をローカルで検索するために使用されます。たとえば、この識別子は、配列へのインデックス、検索キー、またはデータベースのIDなどです。この識別子により、ポリシーを適用するエージェントやサービスは、ポリシーのうち自身が担当する部分の内容を検索できます。

The fields are described as follows:

各フィールドは次のとおりです。

Length:
Indicates the length of the Policy ID in octets (see Section 2.5.1 of [RFC8300]).
Policy ID:
Represents an opaque value of the Policy ID.
Length:
ポリシーIDの長さをオクテット単位で示します（[RFC8300]のSection 2.5.1を参照してください）。
Policy ID:
ポリシーIDの不透明な値を表します。

This Policy ID is a general Policy ID, essentially a key to allow Service Functions (SFs) to know which policies to apply to packets. Those policies generally will not have much to do with performance but rather with what specific treatment to apply. It may, for example, select a URL filter data set for a URL filter or select a video transcoding policy in a transcoding SF. The Performance Policy ID in [RFC8979] is described there as having very specific use and, for example, says that fully controlled SFPs would not use it. The Policy ID in this document is for cases not covered by [RFC8979].

このポリシーIDは汎用的なポリシーIDであり、本質的には、サービス機能（Service Function、SF）がパケットにどのポリシーを適用するかを知るためのキーです。これらのポリシーは一般に、性能とはあまり関係がなく、むしろどのような特定の処理を適用するかに関係します。たとえば、URLフィルターのためのURLフィルターデータセットを選択したり、トランスコーディングSFにおいてビデオのトランスコーディングポリシーを選択したりできます。[RFC8979]の性能ポリシーID（Performance Policy ID）は、そこではきわめて限定的な用途を持つものとして説明されており、たとえば、完全に制御されたSFPではそれを使用しないとされています。この文書のポリシーIDは、[RFC8979]でカバーされない場合のためのものです。

5. Security Considerations

5. セキュリティーに関する考慮事項

A misbehaving node from within the SFC-enabled domain may alter the content of the Context Headers, which may lead to service disruption. Such an attack is not unique to the Context Headers defined in this document. Measures discussed in Section 8 of [RFC8300] describes the general security considerations for protecting the NSH. [RFC9145] specifies methods of protecting the integrity of the NSH metadata. If the NSH includes the Message Authentication Code (MAC) and Encrypted Metadata Context Header [RFC9145], the authentication of the packet MUST be verified before using any data. If the verification fails, the receiver MUST stop processing the Variable-Length Context Headers and notify an operator.

SFC対応ドメイン内の不正な動作をするノードが、コンテキストヘッダーの内容を改変する可能性があり、それによってサービスが中断される可能性があります。このような攻撃は、この文書で定義するコンテキストヘッダーに特有のものではありません。[RFC8300]のSection 8で議論されている対策は、NSHを保護するための一般的なセキュリティーに関する考慮事項を説明しています。[RFC9145]は、NSHメタデータの完全性を保護する方法を規定しています。NSHにメッセージ認証コード（MAC）と暗号化メタデータのコンテキストヘッダー[RFC9145]が含まれている場合、データを使用する前にパケットの認証を検証しなければなりません（MUST）。検証に失敗した場合、受信者は可変長コンテキストヘッダーの処理を停止し、運用者に通知しなければなりません（MUST）。

The security and privacy considerations for the 7 types of Context Headers specified above are discussed below. Since NSH-ignorant SFs will never see the NSH, then even if they are malign, they cannot compromise security or privacy based on the NSH or any of these Context Headers; however, they could cause compromise based on the rest of the packet. To the extent that any of these headers are included when they would be unneeded or have no effect, they provide a covert channel for the entity adding the Context Header to communicate a limited amount of arbitrary information to downstream entities within the SFC-enabled domain.

上で規定した7種類のコンテキストヘッダーについてのセキュリティーとプライバシーに関する考慮事項を以下で議論します。NSHを認識しないSFがNSHを目にすることはないため、たとえそれらが悪意のあるものであっても、NSHやこれらのコンテキストヘッダーに基づいてセキュリティーやプライバシーを侵害することはできません。ただし、パケットの残りの部分に基づいて侵害を引き起こす可能性はあります。これらのヘッダーのいずれかが、不要な場合や効果がない場合に含まれていると、その限りにおいて、それらのヘッダーは、コンテキストヘッダーを追加するエンティティーがSFC対応ドメイン内の下流のエンティティーに限られた量の任意の情報を伝えるための隠れチャネルとなります。

5.1. Forwarding Context

5.1. 転送コンテキスト

All of the Forwarding Context variants specified in this document (those with CT values between 0 and 4) merely repeat a field that is available in the packet encapsulated by the NSH. These variants repeat that field in the NSH for convenience. Thus, there are no special security or privacy considerations in these cases. Any future new values of CT for the Forwarding Context must specify the security and privacy considerations for those extensions.

この文書で規定する転送コンテキストの変種（CT値が0から4のもの）はすべて、NSHによってカプセル化されたパケット内で利用可能なフィールドを繰り返しているだけです。これらの変種は、利便性のためにそのフィールドをNSH内で繰り返します。したがって、これらの場合には特別なセキュリティーやプライバシーに関する考慮事項はありません。転送コンテキストに対する将来の新しいCT値は、それらの拡張についてのセキュリティーとプライバシーに関する考慮事項を規定しなければなりません。

5.2. Tenant ID

5.2. テナントID

The Tenant ID indicates the tenant to which traffic belongs and might be used to tie together and correlate packets for a tenant that some monitoring function could not otherwise group, especially if other possible identifiers were being randomized. As such, it may reduce security by facilitating traffic analysis but only within the SFC-enabled domain where this Context Header is present in packets.

テナントIDはトラフィックが属するテナントを示し、何らかの監視機能がほかの方法ではグループ化できないテナントのパケットを結びつけて相関させるために使用される可能性があります。ほかに識別子となりうるものがランダム化されている場合は特にそうです。そのため、テナントIDはトラフィック分析を容易にすることでセキュリティーを低下させる可能性がありますが、それはこのコンテキストヘッダーがパケットに存在するSFC対応ドメイン内に限られます。

5.3. Ingress Network Node Information

5.3. 入口ネットワークノード情報

The SFC-enabled domain manager normally operates the initial ingress/classifier node and is thus potentially aware of the information provided by this Context Header. Furthermore, in many cases, the SPI that will be present in the NSH identifies or closely constrains the ingress node. Also, in most cases, it is anticipated that many entities will be sending packets into an SFC-enabled domain through the same ingress node. Thus, under most circumstances, this Context Header is expected to weaken security and privacy to only a minor extent and only within the SFC-enabled domain.

SFC対応ドメインの管理者は通常、最初の入口ノード／分類器ノードを運用しているため、このコンテキストヘッダーが提供する情報を知りうる立場にあります。さらに、多くの場合、NSHに存在するSPIは入口ノードを識別するか、入口ノードを厳しく絞り込みます。また、ほとんどの場合、多くのエンティティーが同じ入口ノードを通じてSFC対応ドメインにパケットを送信することが予想されます。したがって、ほとんどの状況において、このコンテキストヘッダーがセキュリティーとプライバシーを弱める程度はわずかであり、その影響もSFC対応ドメイン内に限られると予想されます。

5.4. Ingress Node Source Interface

5.4. 入口ノード送信元インターフェイス

This Context Header is likely to be meaningless unless the Ingress Network Node Information Context Header is also present. When that node information header is present, this source interface header provides a more fine-grained view of the source by identifying not just the initial ingress/classifier node but also the port of that node on which the data arrived. Thus, it is more likely to identify a specific source entity or at least to more tightly constrain the set of possible source entities than just the node information header. As a result, inclusion of this Context Header with the node information Context Header is potentially a greater threat to security and privacy than the node information header alone, but this threat is still constrained to the SFC-enabled domain.

このコンテキストヘッダーは、入口ネットワークノード情報のコンテキストヘッダーも存在しない限り、意味をなさない可能性が高いです。そのノード情報ヘッダーが存在する場合、この送信元インターフェイスヘッダーは、最初の入口ノード／分類器ノードだけでなく、データが到着したそのノードのポートも識別することで、送信元についてよりきめ細かい情報を提供します。したがって、ノード情報ヘッダーだけの場合よりも、特定の送信元エンティティーを識別する可能性、または少なくとも送信元エンティティーの候補の集合をより厳しく絞り込む可能性が高くなります。その結果、このコンテキストヘッダーをノード情報のコンテキストヘッダーとともに含めることは、ノード情報ヘッダーだけの場合よりもセキュリティーとプライバシーに対する大きな脅威となる可能性がありますが、この脅威もやはりSFC対応ドメイン内に限られます。

5.5. Flow ID

5.5. フローID

The variations of this Context Header specified in this document simply repeat fields already available in the packet and thus have no special security or privacy considerations. Any future new values of CT for the Flow ID must specify the security and privacy considerations for those extensions.

この文書で規定するこのコンテキストヘッダーの変種は、パケット内ですでに利用可能なフィールドを単に繰り返すだけであるため、特別なセキュリティーやプライバシーに関する考慮事項はありません。フローIDに対する将来の新しいCT値は、それらの拡張についてのセキュリティーとプライバシーに関する考慮事項を規定しなければなりません。

5.6. Source and/or Destination Groups

5.6. 送信元グループと宛先グループ

This Context Header provides additional information that might help identify the source and/or destination of packets. Depending on the granularity of the groups, it could either (1) distinguish packets as part of flows from and/or to objects where those flows could not otherwise be easily distinguished but appear to be part of one or fewer flows or (2) group packet flows that are from and/or to an object where those flows could not otherwise be easily grouped for analysis or another purpose. Thus, the presence of this Context Header with non-zero source and/or destination groups can, within the SFC-enabled domain, erode security and privacy to an extent that depends on the details of the grouping.

このコンテキストヘッダーは、パケットの送信元や宛先の識別に役立つ可能性のある追加情報を提供します。グループの粒度によっては、(1) オブジェクトから、またはオブジェクトへのフローの一部としてパケットを区別できる可能性があります。ここで、それらのフローはほかの方法では容易に区別できず、1つ以下のフローの一部であるように見えるものです。あるいは、(2) あるオブジェクトから、またはあるオブジェクトへのパケットフローをグループ化できる可能性があります。ここで、それらのフローは、分析やほかの目的のためにほかの方法では容易にグループ化できないものです。 したがって、0以外の送信元グループや宛先グループを持つこのコンテキストヘッダーが存在すると、SFC対応ドメイン内において、グループ化の詳細に応じた程度でセキュリティーとプライバシーが損なわれる可能性があります。

5.7. Policy ID

5.7. ポリシーID

This Context Header carries an identifier that nodes in the SFC-enabled domain can use to look up policy to potentially influence their actions with regard to the packet carrying this header. If there are no such decisions regarding their actions, then the header should not be included. If there are such decisions, the information on which they are to be based needs to be included somewhere in the packet. There is no reason for inclusion in this Context Header to have any security or privacy considerations that would not apply to any other plaintext way of including such information. It may provide additional information to help identify a flow of data for analysis.

このコンテキストヘッダーは、SFC対応ドメイン内のノードがポリシーを検索するために使用できる識別子を運びます。そのポリシーは、このヘッダーを運ぶパケットに関するノードの動作に影響を与える可能性があります。ノードの動作に関してそのような判断がない場合は、このヘッダーを含めるべきではありません。そのような判断がある場合は、判断の基となる情報をパケット内のどこかに含める必要があります。このコンテキストヘッダーに含めることで、そのような情報を平文で含めるほかの方法には当てはまらないセキュリティーやプライバシーに関する考慮事項が生じる理由はありません。このコンテキストヘッダーは、分析のためにデータのフローを識別するのに役立つ追加情報を提供する可能性があります。
