RFC 658

Telnet output linefeed disposition

RFC 658

Telnetの出力ラインフィード処理

1. Command name and code

1. コマンド名とコード

NAOLFD 16
(Negotiate About Output Linefeed Disposition)

NAOLFD 16
（Negotiate About Output Linefeed Disposition、出力ラインフィード処理に関するネゴシエーション）

2. Command meanings

2. コマンドの意味

In the following, we are discussing a simplex connection, as described in the NAOL and NAOP Telnet Options.

以下では、NAOLおよびNAOPのTelnetオプションで説明されているような単方向（simplex）のコネクションについて述べます。

IAC DO NAOLFD
The data sender requests or agrees to negotiate about output linefeed disposition with the data receiver. In the case where agreement has been reached and in the absence of further subnegotiations, the data receiver is assumed to be handling output linefeed considerations.
IAC DON'T NAOLFD
The data sender refuses to negotiate about output linefeed disposition with the data receiver, or demands a return to the unnegotiated default mode.
IAC WILL NAOLFD
The data receiver requests or agrees to negotiate about output linefeed disposition with the sender. In the case where agreement has been reached and in the absence of further subnegotiations, the data receiver alone is assumed to be handling output linefeed considerations.
IAC WON'T NAOLFD
The data receiver refuses to negotiate about output linefeed disposition, or demands a return to the unnegotiated default mode.
IAC SB NAOLFD DS <8-bit value> IAC SE
The data sender specifies, with the 8-bit value, which party should handle output linefeeds and what their disposition should be. The code for DS is 1.
IAC SB NAOLFD DR <8-bit value> IAC SE
The data receiver specifies, with the 8-bit value, which party should handle output linefeeds and what their disposition should be. The code for DR is 0.
IAC DO NAOLFD
データ送信側が、データ受信側と出力ラインフィード（linefeed）の処理についてネゴシエーションすることを要求するか、またはそれに同意します。合意に達し、それ以上のサブネゴシエーションがない場合は、データ受信側が出力ラインフィードに関する事柄を処理するものとみなします。
IAC DON'T NAOLFD
データ送信側が、データ受信側と出力ラインフィードの処理についてネゴシエーションすることを拒否するか、またはネゴシエーションしていないデフォルトのモードに戻ることを要求します。
IAC WILL NAOLFD
データ受信側が、送信側と出力ラインフィードの処理についてネゴシエーションすることを要求するか、またはそれに同意します。合意に達し、それ以上のサブネゴシエーションがない場合は、データ受信側だけが出力ラインフィードに関する事柄を処理するものとみなします。
IAC WON'T NAOLFD
データ受信側が、出力ラインフィードの処理についてネゴシエーションすることを拒否するか、またはネゴシエーションしていないデフォルトのモードに戻ることを要求します。
IAC SB NAOLFD DS <8-bit value> IAC SE
データ送信側が、8ビット値によって、どちらの側が出力ラインフィードを処理すべきか、およびその処理方法をどうすべきかを指定します。DSのコードは1です。
IAC SB NAOLFD DR <8-bit value> IAC SE
データ受信側が、8ビット値によって、どちらの側が出力ラインフィードを処理すべきか、およびその処理方法をどうすべきかを指定します。DRのコードは0です。

3. Default

3. デフォルト

DON'T NAOLFD/WON'T NAOLFD.
In the default absence of negotiations concerning which party, data under or data receiver, is handling output linefeed considerations, neither party is required nor prohibited from handling linefeeds; but it is appropriate if at least the data receiver handles them, albeit primitively.
DON'T NAOLFD/WON'T NAOLFD.
データ送信側（原文では「data under」）とデータ受信側のどちらが出力ラインフィードに関する事柄を処理するかについてのネゴシエーションがないデフォルトの状態では、どちらの側もラインフィードを処理することを要求されず、どちらの側もそれを処理することを禁止されません。ただし、少なくともデータ受信側が、原始的な方法であってもラインフィードを処理するのが適切です。

4. Motivation for the Option

4. このオプションの動機

Please refer to section 4 of the NAOL and of the NAOLFD Telnet option descriptions.

NAOLおよびNAOLFDのTelnetオプションの説明のセクション4を参照してください。

5. Description of the Option

5. このオプションの説明

The data sender and the data receiver use the 8-bit value along with DS and DR SB commands as follows:

データ送信側とデータ受信側は、DSおよびDRのSBコマンドとともに、8ビット値を次のように使用します。

Table 1
8-bit value Meaning
0 Command sender suggests that he alone will handle linefeeds, for the connection.
1 to 250 Command sender suggests that the other party alone should handle linefeeds, but suggests that a delay of the indicated value be used. The value is the number of character-times to wait or number of NULs to insert in the data stream before sending the next data character. (See qualifications, below.)
251 Not allowed, in order to be compatible with related Telnet options.
252 Command sender suggests that the other party alone handle linefeeds, but suggests that they be discarded.
253 Command sender suggests that the other party alone should handle linefeeds, but suggests that linefeeds be simulated.
254 Command sender suggests that the other party alone should handle output linefeeds but suggests waiting for a character to be transmitted (on the other simplex connection) before sending more data. (See qualifications, below.) Note that, due to the assynchrony of the two simplex connections, phase problems can occur with this option.
255 Command sender suggests that the other party alone should handle output linefeeds and suggests nothing about how it should be done.

1～250 コマンド送信者は、相手側だけがラインフィードを処理すべきであると提案しますが、示した値の遅延を使用することも提案します。この値は、次のデータ文字を送信する前に待つ文字時間の数、またはデータストリームに挿入するNULの数です。（後述の条件を参照してください。）

255 コマンド送信者は、相手側だけが出力ラインフィードを処理すべきであると提案し、それをどのように行うべきかについては何も提案しません。

The guiding rules are that:

指針となる規則は次のとおりです。

  1. if neither data receiver nor data sender wants to handle output linefeeds, the data receiver must do it, and
  2. if both data receiver and data sender want to handle output linefeed disposition, the data sender gets to do it.
  1. データ受信側もデータ送信側も出力ラインフィードを処理することを望まない場合は、データ受信側がそれを行わなければなりません。
  2. データ受信側とデータ送信側の両方が出力ラインフィードの処理を望む場合は、データ送信側がそれを行います。

The reasoning for the former rule is that if neither wants to do it, then the default in the NAOLFD option dominates. If both want to do it, the sender, who is presumed to have special knowledge about the data, should be allowed to do it, taking into account any suggestions the receiver may make. Simulation is defined as the replacement of the linefeed character by new-line (see following) and enough blanks to move the print head (or line pointer) to the same lateral position it occupied just prior to receiving the linefeed. To avoid infinite recursion, such simulation is allowed only for linefeed characters that are not immediately preceded by carriage-returns (that is, part of a Telnet new-line combination). It is assumed that linefeed simulation will be necessary for printers that do not have a separate linefeed (like the IBM 2741); in this case, end-of-line character padding can be specified through NAOCRD. Any padding (0 < <8-bit-value> < 251) of linefeed characters is to be done for ALL linefeed characters.

前者の規則の根拠は、どちらもそれを行いたくない場合は、NAOLFDオプションのデフォルトが優先されるということです。両方がそれを行いたい場合は、データについて特別な知識を持っていると想定される送信側が、受信側が行う提案を考慮に入れたうえで、それを行えるようにすべきです。シミュレーションとは、ラインフィード文字を、改行（new-line、後述）と、印字ヘッド（または行ポインター）をラインフィードを受信する直前にあった横方向の位置まで移動させるのに十分な数の空白とに置き換えることと定義します。無限の再帰を避けるため、このようなシミュレーションは、直前にキャリッジリターンがない（つまり、Telnetの改行の組み合わせの一部ではない）ラインフィード文字に対してのみ許可されます。ラインフィードのシミュレーションは、独立したラインフィードを持たないプリンター（IBM 2741など）で必要になると想定されます。この場合、行末文字のパディングはNAOCRDで指定できます。ラインフィード文字のパディング（0 < <8-bit-value> < 251）は、すべての（ALL）ラインフィード文字に対して行うものとします。

NOTE: Delays, controlled by the data sender, must consist of NUL characters inserted immediately after the character. This is necessary due to the assynchrony of network transmissions. Additionally, due to the presence of the Telnet end-of-line convention, it may be necessary to add carriage-return padding or delay after the associated linefeed (see NAOCRD Telnet option). As with all option negotiations, neither party should suggest a state already in effect except to refuse to negotiate; changes should be acknowledged; and once refused, an option should not be resuggested until "something changes" (e.g., another process starts). At any time, either party can disable further negotiation by giving the appropriate WON'T NAOLFD or DON'T NAOLFD command.

注：データ送信側が制御する遅延は、その文字の直後に挿入したNUL文字で構成しなければなりません。これは、ネットワーク伝送が非同期であるために必要です。さらに、Telnetの行末の規約があるため、対応するラインフィードの後にキャリッジリターンのパディングや遅延を追加する必要がある場合があります（NAOCRDのTelnetオプションを参照してください）。すべてのオプションのネゴシエーションと同様に、どちらの側も、ネゴシエーションを拒否する場合を除いて、すでに有効になっている状態を提案すべきではありません。変更には確認応答をすべきです。また、いったん拒否されたオプションは、「何かが変わる」（たとえば、別のプロセスが開始する）まで再提案すべきではありません。どちらの側も、適切なWON'T NAOLFDまたはDON'T NAOLFDコマンドを送ることで、いつでもそれ以降のネゴシエーションを無効にできます。
