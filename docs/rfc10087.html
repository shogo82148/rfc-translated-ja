RFC 10087

Extensible Provisioning Protocol (EPP) Transport over QUIC

RFC 10087

QUIC上の拡張可能プロビジョニングプロトコル（EPP）トランスポート

Abstract

概要

This document specifies how an Extensible Provisioning Protocol (EPP) session is mapped onto a QUIC connection. EPP over QUIC (EoQ) leverages features of the QUIC protocol.

この文書は、拡張可能プロビジョニングプロトコル（Extensible Provisioning Protocol、EPP）のセッションをQUICコネクションにどのようにマッピングするかを規定します。 EPP over QUIC（EoQ）は、QUICプロトコルの機能を活用します。

1. Introduction

1. はじめに

This document specifies how the Extensible Provisioning Protocol (EPP) [RFC5730] is mapped onto QUIC transport [RFC9000]. QUIC is a protocol that is based on UDP and incorporates encryption support using TLS [RFC9001]. Though based on UDP, QUIC provides connection semantics like other stateful protocols. This document discusses how EPP implementations can work with this and other features of QUIC while preserving the core EPP semantics.

この文書は、拡張可能プロビジョニングプロトコル（EPP）[RFC5730]をQUICトランスポート[RFC9000]にどのようにマッピングするかを規定します。 QUICは、UDPに基づき、TLS[RFC9001]を使った暗号化のサポートを組み込んだプロトコルです。 QUICはUDPに基づいていますが、ほかのステートフルなプロトコルと同様にコネクションのセマンティクスを提供します。 この文書では、EPPの中核となるセマンティクスを維持しながら、EPPの実装がこの機能やQUICのほかの機能をどのように扱えるかについて説明します。

EPP sessions use a single QUIC stream for all command and response exchanges throughout the session lifecycle. Unlike stateless transaction protocols that permit per-command independent streams, EPP is a stateful protocol with inherent sequential command dependencies defined in [RFC5730]. Maintaining a single stream preserves ordered transaction processing, consistent session state, and full compatibility with existing EPP operational and implementation models.

EPPセッションは、セッションのライフサイクル全体を通して、すべてのコマンドとレスポンスのやりとりに単一のQUICストリームを使用します。 コマンドごとに独立したストリームを許容するステートレスなトランザクションプロトコルとは異なり、EPPは[RFC5730]で定義されているとおり、コマンド間に本質的な順序依存関係を持つステートフルなプロトコルです。 単一のストリームを維持することで、トランザクションの順序どおりの処理、一貫したセッション状態、既存のEPPの運用モデルおよび実装モデルとの完全な互換性が保たれます。

EPP [RFC5730] was designed for pluggability of transports that must follow Section 2.1 of [RFC5730]. EoQ defines a fully pluggable QUIC transport for EPP as an alternative to other EPP transports, such as EPP over TCP (EoT) [RFC5734]. The server can choose to offer EoQ in addition to EoT or as a replacement for EoT, based on the security and performance considerations of QUIC and the preferred deployment architecture of the server and clients.

EPP[RFC5730]は、[RFC5730]のセクション2.1に従わなければならないトランスポートを差し替え可能（pluggable）にするよう設計されています。 EoQは、EPP over TCP（EoT）[RFC5734]などのほかのEPPトランスポートの代替として、EPPのための完全に差し替え可能なQUICトランスポートを定義します。 サーバーは、QUICのセキュリティーと性能に関する考慮事項、およびサーバーとクライアントが望むデプロイメントアーキテクチャーに基づいて、EoTに加えてEoQを提供するか、EoTの代わりにEoQを提供するかを選択できます。

EPP is primarily deployed for communication between domain registries and registrars, which commonly run many concurrent EPP sessions. Conventional EPP over TCP (EoT) requires a dedicated TCP connection for every single EPP session, resulting in connection overhead and resource consumption. EoQ addresses this issue by leveraging QUIC stream multiplexing: multiple independent EPP sessions can run over one single persistent QUIC connection.

EPPは主にドメインレジストリーとレジストラー間の通信に導入されており、これらは一般に多数のEPPセッションを並行して実行しています。 従来のEPP over TCP（EoT）では、EPPセッションごとに専用のTCPコネクションが必要となり、コネクションのオーバーヘッドとリソースの消費が生じます。 EoQは、QUICのストリーム多重化を活用することでこの問題に対処します。 つまり、複数の独立したEPPセッションを、永続的な1つのQUICコネクション上で実行できます。

2. Terminology

2. 用語

This document makes use of the following terms:

この文書では、次の用語を使用します。

EoQ:

The acronym used for the EPP-over-QUIC transport that defines the use of QUIC as an EPP transport following the considerations in Section 2.1 of [RFC5730].

EoQ connection:

Is a client-initiated bidirectional QUIC stream established on a QUIC connection using the "EoQ" Application-Layer Protocol Negotiation (ALPN) [RFC7301] value. The EoQ connection maps to the client-server connection defined in Section 2.1 of [RFC5730], where the server returns an EPP <greeting>. A single QUIC connection supports many EoQ connections.

EoQ session:

Is an authenticated EoQ connection, which occurs after a successful EPP <login>.

EoQ Connection Start Packet:

Used by clients to complete the creation of an EoQ connection by signaling the server to create the QUIC stream and return the EPP <greeting> needed for an EPP connection. Section 6 formally defines the EoQ Connection Start Packet.

EoQ:

EPP-over-QUICトランスポートを表す略語です。 このトランスポートは、[RFC5730]のセクション2.1の考慮事項に従って、EPPトランスポートとしてのQUICの使用法を定義します。

EoQ connection:

「EoQ」というアプリケーション層プロトコルネゴシエーション（ALPN）[RFC7301]の値を使用するQUICコネクション上に確立された、クライアントが開始する双方向QUICストリームです。 EoQコネクションは、[RFC5730]のセクション2.1で定義されているクライアントとサーバー間のコネクションに対応し、そこでサーバーはEPPの<greeting>を返します。 1つのQUICコネクションは多数のEoQコネクションをサポートします。

EoQ session:

認証済みのEoQコネクションです。EPPの<login>が成功した後に生じます。

EoQ Connection Start Packet:

クライアントがEoQコネクションの作成を完了するために使用するものです。 QUICストリームを作成し、EPPコネクションに必要なEPPの<greeting>を返すようサーバーに合図します。 セクション6で、EoQ Connection Start Packetを正式に定義します。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

3. Session Management

3. セッション管理

Mapping EPP session management facilities onto the QUIC service is accomplished with a combination of a QUIC connection with the "EoQ" ALPN [RFC7301] value and client-initiated, bidirectional QUIC streams. QUIC supports four stream types (Section 2.1 of [RFC9000]), but EoQ only supports the client-initiated, bidirectional stream type.

EPPのセッション管理機能のQUICサービスへのマッピングは、「EoQ」というALPN[RFC7301]の値を使ったQUICコネクションと、クライアントが開始する双方向QUICストリームの組み合わせによって実現します。 QUICは4種類のストリームをサポートしています（[RFC9000]のセクション2.1）が、EoQはクライアントが開始する双方向ストリームの種類のみをサポートします。

As shown in Figure 1, an EPP session first requires creation of a QUIC connection between two peers, one that initiates the connection request and one that responds to the connection request. The initiating peer is called the "client", and the responding peer is called the "server". By default, an EPP server MUST listen for QUIC connection requests on the well-known UDP port number updated by IANA (see Section 9.2), unless there is a mutual agreement to use another port number.

図1に示すように、EPPセッションではまず、2つのピア間にQUICコネクションを作成する必要があります。 一方はコネクションリクエストを開始するピアであり、もう一方はコネクションリクエストに応答するピアです。 開始する側のピアを「クライアント」、応答する側のピアを「サーバー」と呼びます。 別のポート番号を使用することについて相互の合意がない限り、デフォルトでは、EPPサーバーはIANAによって更新されたウェルノウンUDPポート番号（セクション9.2を参照）でQUICのコネクションリクエストを待ち受けなければなりません（MUST）。

A successfully established QUIC connection is secured by the TLS support that QUIC provides using the "EoQ" ALPN value.

正常に確立されたQUICコネクションは、「EoQ」というALPNの値を使用して、QUICが提供するTLSのサポートによって保護されます。

Once the QUIC connection is established, the EPP client MUST then create a bidirectional QUIC stream by sending the Section 6. [RFC9000] states that "streams can be created by sending data". If the EPP server accepts the QUIC stream, it reads the Section 6 and returns an EPP <greeting> to the client on the same QUIC stream. After reading the EPP <greeting> message, and absent processing errors, the EPP client sends EPP commands and receives EPP responses on the same stream. A QUIC stream corresponds to an EPP connection, which is referred to as an EoQ connection. An authenticated QUIC stream, via a successful EPP <login>, corresponds to an EPP session, which is referred to as an EoQ session.

QUICコネクションが確立されたら、次にEPPクライアントはSection 6を送信して、双方向QUICストリームを作成しなければなりません（MUST）。 [RFC9000]には「streams can be created by sending data（ストリームはデータを送信することで作成できる）」と記載されています。 EPPサーバーがQUICストリームを受け入れる場合、サーバーはSection 6を読み取り、同じQUICストリーム上でクライアントにEPPの<greeting>を返します。 EPPの<greeting>メッセージを読み取った後、処理エラーがなければ、EPPクライアントは同じストリーム上でEPPコマンドを送信し、EPPレスポンスを受信します。 1つのQUICストリームは1つのEPPコネクションに対応し、これをEoQコネクションと呼びます。 EPPの<login>の成功によって認証されたQUICストリームは1つのEPPセッションに対応し、これをEoQセッションと呼びます。

An EPP session is normally ended by the client issuing an EPP <logout> command. A server receiving an EPP <logout> command MUST end the EPP session and close the QUIC stream. A client MAY end an EoQ session by closing the QUIC stream and the server MUST end the EoQ session by closing the QUIC stream.

EPPセッションは通常、クライアントがEPPの<logout>コマンドを発行することで終了します。 EPPの<logout>コマンドを受信したサーバーは、EPPセッションを終了し、QUICストリームをクローズしなければなりません（MUST）。 クライアントはQUICストリームをクローズすることでEoQセッションを終了してもよいです（MAY）。その場合、サーバーはQUICストリームをクローズすることでEoQセッションを終了しなければなりません（MUST）。

EoQ connections are established as described in the QUIC transport specification [RFC9000]. During connection establishment, EoQ support is indicated using the "EoQ" ALPN value in the cryptographic handshake.

EoQコネクションは、QUICトランスポートの仕様[RFC9000]に記載されているとおりに確立されます。 コネクションの確立中、EoQのサポートは、暗号ハンドシェイクで「EoQ」というALPNの値を使用することで示されます。

A single QUIC connection may allow multiple QUIC streams. This means that a single QUIC connection may support multiple EoQ sessions. A server MAY limit the life span of an established EoQ session. EoQ sessions that are inactive for more than a server-defined period MAY be ended by the server closing the QUIC stream. A server MAY close EoQ sessions that have been open and active for longer than a server-defined limit. The max_idle_timeout transport parameter defined in Section 18.2 of [RFC9000] MUST NOT be set to a non-zero value by the client or server. Once the last QUIC stream for a QUIC connection is closed, the server MAY either immediately end the QUIC connection or retain the open connection in accordance with local configuration and operational policy.

1つのQUICコネクションでは、複数のQUICストリームを使える場合があります。 これは、1つのQUICコネクションが複数のEoQセッションをサポートできる場合があることを意味します。 サーバーは、確立されたEoQセッションの存続期間を制限してもよいです（MAY）。 サーバーが定義した期間を超えて非アクティブなEoQセッションは、サーバーがQUICストリームをクローズすることで終了してもよいです（MAY）。 サーバーは、サーバーが定義した上限よりも長くオープンかつアクティブな状態が続いているEoQセッションをクローズしてもよいです（MAY）。 クライアントもサーバーも、[RFC9000]のセクション18.2で定義されているmax_idle_timeoutトランスポートパラメーターを0以外の値に設定してはなりません（MUST NOT）。 QUICコネクションの最後のQUICストリームがクローズされたら、サーバーは、ローカルの設定と運用ポリシーに従って、QUICコネクションをただちに終了するか、オープンなコネクションを維持するかのいずれかを行ってもよいです（MAY）。

4. Message Exchange

4. メッセージ交換

EPP messages are passed on an EoQ connection, which is a client-initiated, bidirectional QUIC stream, defined in Section 3. Except for the EPP server <greeting>, EPP messages are initiated by the EPP client in the form of EPP commands. An EPP server MUST return an EPP response to an EPP command on the same QUIC stream that carried the command. If the QUIC stream is closed after a server receives and successfully processes a command but before the response can be returned to the client, the server MAY attempt to undo the effects of the command to ensure a consistent state between the client and the server. EPP commands are idempotent, so processing a command more than once produces the same net effect on the repository as successfully processing the command once.

EPPメッセージは、セクション3で定義した、クライアントが開始する双方向QUICストリームであるEoQコネクション上で受け渡されます。 EPPサーバーの<greeting>を除き、EPPメッセージはEPPコマンドの形でEPPクライアントが開始します。 EPPサーバーは、EPPコマンドに対するEPPレスポンスを、そのコマンドを運んだのと同じQUICストリーム上で返さなければなりません（MUST）。 サーバーがコマンドを受信して正常に処理した後、クライアントにレスポンスを返す前にQUICストリームがクローズされた場合、サーバーは、クライアントとサーバー間の状態の一貫性を確保するために、そのコマンドの効果を取り消そうとしてもよいです（MAY）。 EPPコマンドは冪等であるため、コマンドを複数回処理しても、リポジトリーに対しては、そのコマンドを1回正常に処理した場合と同じ最終的な効果が生じます。

An EPP client streams EPP commands to an EPP server on an established QUIC stream. A client MAY establish multiple QUIC streams to support multiple EoQ sessions with each EoQ session mapped to a single QUIC stream. A server SHOULD limit a client to a maximum number of QUIC streams per QUIC connection based on server capabilities and operational load. Absent such a limit, a server may be subject to overload and resource exhaustion. Section 4.6 of [RFC9000] discusses this situation.

EPPクライアントは、確立されたQUICストリーム上でEPPサーバーにEPPコマンドを順次送信します。 クライアントは、各EoQセッションを1つのQUICストリームにマッピングして、複数のEoQセッションをサポートするために複数のQUICストリームを確立してもよいです（MAY）。 サーバーは、サーバーの能力と運用上の負荷に基づいて、QUICコネクションあたりのQUICストリームの最大数でクライアントを制限すべきです（SHOULD）。 そのような制限がない場合、サーバーは過負荷やリソースの枯渇にさらされる可能性があります。 [RFC9000]のセクション4.6では、この状況について説明しています。

EPP describes client-server interaction as a command-response exchange where the client sends one command to the server and the server returns one response to the client.

EPPでは、クライアントとサーバー間のやりとりを、クライアントがサーバーに1つのコマンドを送信し、サーバーがクライアントに1つのレスポンスを返すコマンドとレスポンスの交換として記述しています。

Each EPP data unit MUST contain a single EPP message. Commands MUST be processed independently.

各EPPデータユニットは、単一のEPPメッセージを含まなければなりません（MUST）。 コマンドは独立して処理されなければなりません（MUST）。

A server SHOULD impose a limit on the amount of time required for a client to issue a well-formed EPP command to reduce the risk associated with a resource exhaustion attack. For example, the time limit is 10 minutes for the server idle timeout and 8 minutes for client keep-alive. Absent local policy, a server MUST end an EoQ session and close the QUIC stream if a well-formed command is not received within the time limit.

リソース枯渇攻撃に関連するリスクを低減するために、サーバーは、クライアントが整形式のEPPコマンドを発行するまでに要する時間に上限を課すべきです（SHOULD）。 たとえば、時間の上限をサーバーのアイドルタイムアウトについては10分、クライアントのキープアライブについては8分とします。 ローカルポリシーがない場合、時間の上限内に整形式のコマンドを受信しなかったときは、サーバーはEoQセッションを終了し、QUICストリームをクローズしなければなりません（MUST）。

A general state machine for an EPP server is described in Section 2 of [RFC5730]. A general client-server message exchange using QUIC transport is illustrated in Figure 1. It shows an example of successful exchange over a single QUIC stream of a QUIC connection. Many QUIC streams may be opened and closed during the life of a QUIC connection.

EPPサーバーの一般的な状態機械は、[RFC5730]のセクション2に記載されています。 QUICトランスポートを使用したクライアントとサーバー間の一般的なメッセージ交換を図1に示します。 この図は、QUICコネクションの単一のQUICストリーム上で交換が成功する例を示しています。 QUICコネクションの存続期間中に、多数のQUICストリームがオープンされ、クローズされる場合があります。

The EPP server MUST follow the "EPP Server State Machine" procedure (see Figure 1 in [RFC5730]).

5. Data Unit Format

5. データユニットの形式

The EPP data unit contains two fields: a 32-bit header that describes the total length of the data unit, and the EPP XML instance. The length of the EPP XML instance is determined by subtracting four octets from the total length of the data unit. A receiver must successfully read that many octets to retrieve the complete EPP XML instance before processing the EPP message. The EPP data unit format is depicted in Figure 2 (one tick mark represents one bit position).

EPPデータユニットは、データユニットの全長を表す32ビットのヘッダーと、EPP XMLインスタンスの2つのフィールドを含みます。 EPP XMLインスタンスの長さは、データユニットの全長から4オクテットを引くことで求められます。 受信者は、EPPメッセージを処理する前に、その数のオクテットを正常に読み取って、完全なEPP XMLインスタンスを取得しなければなりません。 EPPデータユニットの形式を図2に示します（目盛り1つが1ビットの位置を表します）。

The fields shown in Figure 2 are defined as follows:

The fields shown in 図2に示したフィールドは、次のように定義されます。

Total Length (32 bits):

The total length of the EPP data unit measured in octets in network (big endian) byte order. The octets contained in this field MUST be included in the total length calculation. The 32-bit total length matches the total length used in EoT, defined in [RFC5734], to support transport pluggability.

EPP XML Instance (variable length):
The EPP XML instance carried in the data unit.
Total Length（32ビット）:

オクテット単位で測ったEPPデータユニットの全長で、ネットワーク（ビッグエンディアン）バイトオーダーで表します。 このフィールドに含まれるオクテットも、全長の計算に含めなければなりません（MUST）。 トランスポートの差し替え可能性をサポートするため、32ビットの全長は、[RFC5734]で定義されているEoTで使用される全長と一致させています。

EPP XML Instance（可変長）:
データユニットで運ばれるEPP XMLインスタンスです。

6. EoQ Connection Start Packet

6. EoQ Connection Start Packet

The EoQ Connection Start Packet is written by the client after creating a QUIC stream to signal to the server to initialize the QUIC stream. Absent processing errors or local policy, the server accepts the QUIC stream, reads the EoQ Connection Start Packet, and returns the EPP <greeting> to the client on same QUIC stream.

EoQ Connection Start Packetは、QUICストリームの初期化をサーバーに合図するために、クライアントがQUICストリームを作成した後に書き込みます。 処理エラーやローカルポリシーによる妨げがなければ、サーバーはQUICストリームを受け入れ、EoQ Connection Start Packetを読み取り、同じQUICストリーム上でクライアントにEPPの<greeting>を返します。

The EoQ Connection Start Packet follows the Section 5 with two fields: a 32-bit header that describes the total length of the data unit, and the constant value of "EoQ Connection Start" instead of an "EPP XML Instance". The length of a valid data unit MUST be 24 octets, which includes 4 octets for the Total Length and 20 octets for the "EoQ Connection Start" constant value.

EoQ Connection Start PacketはSection 5に従い、データユニットの全長を表す32ビットのヘッダーと、「EPP XML Instance」の代わりとなる「EoQ Connection Start」という定数値の2つのフィールドを持ちます。 有効なデータユニットの長さは24オクテットでなければなりません（MUST）。 これには、Total Lengthの4オクテットと、「EoQ Connection Start」という定数値の20オクテットが含まれます。

If the EoQ Connection Start Packet received by the server is not valid (e.g., when the total length is not exactly 24 octets), the server MUST close that QUIC stream. The server MAY return an error indication prior to closing the stream.

サーバーが受信したEoQ Connection Start Packetが有効でない場合（たとえば、全長がちょうど24オクテットでない場合）、サーバーはそのQUICストリームをクローズしなければなりません（MUST）。 サーバーは、ストリームをクローズする前にエラーを示すものを返してもよいです（MAY）。

7. Transport Considerations

7. トランスポートに関する考慮事項

Section 2.1 of [RFC5730] describes considerations to be addressed by protocol transport mappings. This document addresses each of those considerations using a combination of features of the QUIC protocol and features of this document as discussed below:

[RFC5730]のセクション2.1では、プロトコルのトランスポートマッピングで対処すべき考慮事項を説明しています。 この文書では、以下で説明するように、QUICプロトコルの機能とこの文書の機能を組み合わせて、それらの考慮事項のそれぞれに対処します。

Command Order:
QUIC guarantees ordered processing of data within each stream. Section 2 of [RFC9000] describes streams in detail.
Session Mapping:
EPP session management utilizes QUIC streams and is described in Section 3.
Stateful Nature:
QUIC supports stateful communications between endpoints via Connection IDs and long-lived streams within each connection. QUIC streams on top of QUIC connections, defined in Sections 2 and 5 of [RFC9000], are used to create stateful communications between the client and server.
Frame Data Units:
EoQ uses the packet framing defined in Section 5.
Congestion Avoidance:
QUIC provides various mechanisms to help achieve congestion avoidance. [RFC9002] describes these mechanisms in detail.
Reliability:
QUIC uses message acknowledgement, packet retransmission, and other features to ensure reliability. Section 13 of [RFC9000] describes these features in detail.
Pipelining:

Pipelining is allowed in EoQ. QUIC streams support sending multiple frames without waiting for responses from the other peer. This does not change the basic single command, single response operating mode of the core EPP.

Commands MUST be processed independently and in the same order as sent from the client.

Batch-oriented processing (combining multiple EPP commands in a single data unit) is not permitted. Each EPP data unit must contain a single EPP message.

An EPP x5zz "Connection Management" error response, defined in Section 3 of [RFC5730], of a well-formed EPP client packet results in the server closing the EoQ connection after returning the error response. A malformed EPP client packet results in the server closing the EoQ connection without providing an error response. All subsequent EPP commands sent on the EoQ connection will not be processed.

コマンドの順序（Command Order）:
QUICは、各ストリーム内のデータが順序どおりに処理されることを保証します。 ストリームについては[RFC9000]のセクション2で詳しく説明しています。
セッションのマッピング（Session Mapping）:
EPPのセッション管理はQUICストリームを利用しており、セクション3で説明しています。
ステートフル性（Stateful Nature）:
QUICは、コネクションIDと、各コネクション内の長期間存続するストリームによって、エンドポイント間のステートフルな通信をサポートします。 [RFC9000]のセクション2と5で定義されている、QUICコネクション上のQUICストリームを使用して、クライアントとサーバー間のステートフルな通信を作り出します。
データユニットのフレーム化（Frame Data Units）:
EoQは、セクション5で定義したパケットのフレーム化を使用します。
輻輳回避（Congestion Avoidance）:
QUICは、輻輳回避を実現するためのさまざまなメカニズムを提供しています。 これらのメカニズムについては[RFC9002]で詳しく説明しています。
信頼性（Reliability）:
QUICは、信頼性を確保するために、メッセージの確認応答、パケットの再送、その他の機能を使用します。 これらの機能については[RFC9000]のセクション13で詳しく説明しています。
パイプライン化（Pipelining）:

EoQではパイプライン化が許されています。 QUICストリームは、相手のピアからのレスポンスを待たずに複数のフレームを送信することをサポートしています。 これは、中核となるEPPの、1つのコマンドに1つのレスポンスという基本的な動作モードを変えるものではありません。

コマンドは、独立して、かつクライアントから送信されたのと同じ順序で処理されなければなりません（MUST）。

バッチ指向の処理（複数のEPPコマンドを1つのデータユニットにまとめること）は許されていません。 各EPPデータユニットは、単一のEPPメッセージを含まなければなりません。

整形式のEPPクライアントパケットに対して、[RFC5730]のセクション3で定義されているEPPのx5zz「Connection Management」エラーレスポンスが生じた場合、サーバーはそのエラーレスポンスを返した後にEoQコネクションをクローズします。 不正な形式のEPPクライアントパケットの場合、サーバーはエラーレスポンスを返さずにEoQコネクションをクローズします。 そのEoQコネクション上で送信された後続のEPPコマンドはすべて処理されません。

8. Operational Considerations

8. 運用上の考慮事項

Some of the concerns examined within this section are also addressed in [RFC9308]. Authors of this specification encourage implementers to understand [RFC9308].

このセクションで検討する懸念事項の一部は、[RFC9308]でも扱われています。 この仕様の著者は、実装者が[RFC9308]を理解することを推奨します。

8.1. Clients Fall Back with Management of Multiple Transport

8.1. 複数のトランスポートの管理によるクライアントのフォールバック

If the establishment of an EoQ connection fails, clients MAY attempt to fall back to EPP over TCP as specified in [RFC5734], depending on local deployment and security policy. It is up to clients to determine the mix of transports that best meets their business needs.

EoQコネクションの確立に失敗した場合、クライアントは、ローカルのデプロイメントとセキュリティーのポリシーに応じて、[RFC5734]で規定されているEPP over TCPへのフォールバックを試みてもよいです（MAY）。 自身のビジネス上のニーズに最も合うトランスポートの組み合わせを決めるのはクライアントです。

8.2. Port Number Reuse

8.2. ポート番号の再利用

Although [RFC5734] does only a request for TCP, the companion UDP port number was also allocated. That practice was prior to [RFC6335] when TCP and UDP port numbers were simultaneously assigned when either was requested. Section 9.2 updates EPP UDP/700 allocation to be used exclusively for EoQ. This update does not introduce any operational issues given that there are no known implementations of EPP over UDP.

[RFC5734]はTCPについてのみリクエストしましたが、対となるUDPポート番号も割り当てられました。 この慣行は、TCPとUDPのいずれかがリクエストされたときに両方のポート番号を同時に割り当てていた、[RFC6335]より前のものです。 セクション9.2では、EPPのUDP/700の割り当てを、EoQ専用に使用するよう更新します。 EPP over UDPの既知の実装は存在しないため、この更新によって運用上の問題が生じることはありません。

8.3. QUIC Support Announcement and Discovery

8.3. QUICサポートの告知と発見

There is no dedicated in-band mechanism defined in this specification for a server to explicitly announce EoQ support to clients. Operators MAY use out-of-band configuration or provisioning channels to advertise server EoQ support to clients in advance.

この仕様では、サーバーがクライアントにEoQのサポートを明示的に告知するための専用のインバンドのメカニズムを定義していません。 運用者は、サーバーのEoQサポートをクライアントに事前に通知するために、帯域外の設定チャネルやプロビジョニングチャネルを使用してもよいです（MAY）。

8.4. Configuration Parameters

8.4. 設定パラメーター

Implementations MAY configure operational parameters to control EoQ session behavior. These parameters can include idle session timeout, maximum QUIC streams per connection, command processing timeout, and maximum session timeout. Servers and clients SHOULD configure limits to avoid session disruption and resource exhaustion.

実装は、EoQセッションの振る舞いを制御するための運用パラメーターを設定してもよいです（MAY）。 これらのパラメーターには、アイドルセッションのタイムアウト、コネクションあたりのQUICストリームの最大数、コマンド処理のタイムアウト、最大セッションタイムアウトなどがあります。 サーバーとクライアントは、セッションの中断やリソースの枯渇を避けるために制限を設定すべきです（SHOULD）。

Implementation Note: There is no in-band protocol mechanism to align limits. Operators typically distribute standard settings via SDKs. Client timeout and stream limits shall be set lower than server values for graceful connection handling. Timeout rules are consistent across EoT and EoQ; per-connection stream limits are newly introduced in EoQ.

実装上の注意: 制限をそろえるためのインバンドのプロトコルメカニズムはありません。 運用者は通常、SDKを通じて標準的な設定を配布します。 コネクションを適切に扱うために、クライアントのタイムアウトとストリームの制限は、サーバーの値よりも小さく設定することになっています。 タイムアウトの規則はEoTとEoQで共通ですが、コネクションごとのストリームの制限はEoQで新たに導入されたものです。

8.5. Diagnostic and Troubleshooting

8.5. 診断とトラブルシューティング

Operators SHOULD log the EoQ connection establishment status, stream lifecycle events, and command transaction results for diagnostic purposes. QUIC transport errors and EPP protocol failures ought to be distinguishable to facilitate efficient troubleshooting. Implementations MAY provide granular error reporting to help identify session termination, connection timeout, and stream closure root causes. Operators MUST redact sensitive data in the logs, such as user credentials and authorization information values.

運用者は、診断のために、EoQコネクションの確立状況、ストリームのライフサイクルイベント、コマンドのトランザクション結果をログに記録すべきです（SHOULD）。 効率的なトラブルシューティングを容易にするために、QUICトランスポートのエラーとEPPプロトコルの失敗は区別できるようにすべきです。 実装は、セッションの終了、コネクションのタイムアウト、ストリームのクローズの根本原因の特定に役立つ、きめ細かなエラー報告を提供してもよいです（MAY）。 運用者は、ユーザーのクレデンシャルや認可情報の値など、ログ内の機密データを編集して隠さなければなりません（MUST）。

8.6. Address Validation

8.6. アドレスの検証

EoQ implementations MUST follow the address validation requirements defined in Section 8 of [RFC9000] to mitigate potential amplification attacks and validate client address reachability.

EoQの実装は、潜在的な増幅攻撃を緩和し、クライアントのアドレスへの到達可能性を検証するために、[RFC9000]のセクション8で定義されているアドレス検証の要件に従わなければなりません（MUST）。

8.7. Authentication Considerations

8.7. 認証に関する考慮事項

EoQ relies on the TLS authentication mechanisms defined in [RFC9001] for peer authentication and credential validation. Implementations MUST follow the same authentication practices specified for EPP over TLS in [RFC5734]. Server and client authentication procedures remain unchanged from existing EPP deployment models when running over QUIC transport.

EoQは、ピアの認証とクレデンシャルの検証について、[RFC9001]で定義されているTLSの認証メカニズムに依存します。 実装は、[RFC5734]でEPP over TLSについて規定されているのと同じ認証の慣行に従わなければなりません（MUST）。 QUICトランスポート上で動作する場合も、サーバーとクライアントの認証手順は既存のEPPのデプロイメントモデルから変わりません。

8.8. 0-RTT and Session Resumption

8.8. 0-RTTとセッションの再開

Using 0-RTT for EoQ allows clients to establish connections and initiate EPP transactions without round-trip delay, enabling servers to use shorter idle timers and reduce connection overhead. Session resumption and 0-RTT introduce privacy and replay risks.

EoQで0-RTTを使用すると、クライアントはラウンドトリップの遅延なしにコネクションを確立してEPPトランザクションを開始できるため、サーバーはより短いアイドルタイマーを使用し、コネクションのオーバーヘッドを削減できます。 セッションの再開と0-RTTは、プライバシーとリプレイのリスクをもたらします。

EPP commands fall into three categories: session management, queries, and transform commands. EPP query commands perform read-only object information retrieval operations. Only read-only EPP query commands MAY be carried in 0-RTT STREAM frames; all other EPP commands MUST NOT use 0-RTT. Clients SHOULD use resumption tickets only once specified in [RFC9846]. Servers SHOULD issue session-resumption tickets with a sufficiently long lifetime (e.g., 6 hours). Servers SHOULD implement the anti-replay mechanisms specified in Section 8 of [RFC9846].

EPPコマンドは、セッション管理、クエリー、変換（transform）コマンドの3つのカテゴリーに分類されます。 EPPのクエリーコマンドは、オブジェクトの情報を読み取り専用で取得する操作を行います。 読み取り専用のEPPクエリーコマンドに限り、0-RTTのSTREAMフレームで運んでもよいです（MAY）。ほかのすべてのEPPコマンドは0-RTTを使用してはなりません（MUST NOT）。 クライアントは、[RFC9846]で規定されているとおり、再開チケットを1回だけ使用すべきです（SHOULD）。 サーバーは、十分に長い有効期間（たとえば6時間）を持つセッション再開チケットを発行すべきです（SHOULD）。 サーバーは、[RFC9846]のセクション8で規定されているリプレイ防止メカニズムを実装すべきです（SHOULD）。

EoQ implementations SHOULD follow the guidance in [RFC9846] and [RFC9001] to balance performance and risk mitigation. Failure to do so increases privacy exposure and replay attack risks.

EoQの実装は、性能とリスク緩和のバランスをとるために、[RFC9846]と[RFC9001]のガイダンスに従うべきです（SHOULD）。 そうしない場合、プライバシーの露出とリプレイ攻撃のリスクが高まります。

8.9. MTU and Fragmentation

8.9. MTUとフラグメンテーション

EoQ implementations MUST follow Section 14 of [RFC9000].

EoQの実装は、[RFC9000]のセクション14に従わなければなりません（MUST）。

10. Security Considerations

10. セキュリティーに関する考慮事項

EPP over QUIC provides similar security foundations as EPP over TCP with TLS, though the security properties of QUIC specified in Section 21.1 of [RFC9000] differ from those of TLS/TCP in that QUIC is an encrypted transport protocol. Some related security issues are discussed in [RFC5734] and [RFC9000]. Sections 8.7 and 8.8 of this document also discuss related security issues.

EPP over QUICは、TLSを使用したEPP over TCPと同様のセキュリティーの基盤を提供します。 ただし、QUICは暗号化されたトランスポートプロトコルであるという点で、[RFC9000]のセクション21.1で規定されているQUICのセキュリティー特性は、TLS/TCPのセキュリティー特性とは異なります。 関連するセキュリティー上の問題の一部は、[RFC5734]と[RFC9000]で説明されています。 この文書のセクション8.7と8.8でも、関連するセキュリティー上の問題について説明しています。

EoQ servers run the risk of a resource exhaustion attack by allowing the creation of unlimited QUIC streams per QUIC connection. As indicated in Section 8.4, servers should limit a client to a maximum number of QUIC streams per QUIC connection based on server capabilities and operational load. Absent such a limit, the server may be subject to overload that would exhaust its resources.

EoQサーバーは、QUICコネクションあたりのQUICストリームを無制限に作成できるようにすると、リソース枯渇攻撃を受けるリスクがあります。 セクション8.4で示したように、サーバーは、サーバーの能力と運用上の負荷に基づいて、QUICコネクションあたりのQUICストリームの最大数でクライアントを制限すべきです。 そのような制限がない場合、サーバーはリソースを枯渇させるような過負荷にさらされる可能性があります。

The 32-bit total length field defined in Section 5 allows a declared payload size up to approximately 4 gigabytes. Implementations MUST validate the advertised total length against a locally configured maximum frame size limit before allocating memory or attempting to read the full frame. Without this check, an attacker could send a crafted frame with an excessively large length value to exhaust receiver memory and trigger a denial-of-service condition.

セクション5で定義した32ビットの全長フィールドでは、宣言するペイロードのサイズとして最大約4ギガバイトまで指定できます。 実装は、メモリーを割り当てたりフレーム全体を読み取ろうとしたりする前に、通知された全長を、ローカルに設定されたフレームサイズの上限と照らし合わせて検証しなければなりません（MUST）。 この検査を行わない場合、攻撃者は、過度に大きな長さの値を持つ細工したフレームを送信して受信者のメモリーを枯渇させ、サービス拒否状態を引き起こすおそれがあります。
