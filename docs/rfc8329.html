RFC 8329

Framework for Interface to Network Security Functions

RFC 8329

ネットワークセキュリティー機能へのインターフェイスのためのフレームワーク

Abstract

概要

This document describes the framework for Interface to Network Security Functions (I2NSF) and defines a reference model (including major functional components) for I2NSF. Network Security Functions (NSFs) are packet-processing engines that inspect and optionally modify packets traversing networks, either directly or in the context of sessions to which the packet is associated.

この文書は、ネットワークセキュリティー機能へのインターフェイス（Interface to Network Security Functions: I2NSF）のフレームワークを説明し、I2NSFの参照モデル（主要な機能コンポーネントを含む）を定義します。 ネットワークセキュリティー機能（NSF）は、ネットワークを通過するパケットを、直接、またはパケットが関連付けられているセッションのコンテキストにおいて検査し、場合によってはそれを変更するパケット処理エンジンです。

1. Introduction

1. はじめに

This document describes the framework for Interface to Network Security Functions (I2NSF) and defines a reference model (including major functional components) for I2NSF. This includes an analysis of the threats implied by the deployment of Network Security Functions (NSFs) that are externally provided. It also describes how I2NSF facilitates implementing security functions in a technology- and vendor-independent manner in Software-Defined Networking (SDN) and Network Function Virtualization (NFV) environments, while avoiding potential constraints that could limit the capabilities of NSFs.

この文書は、ネットワークセキュリティー機能へのインターフェイス（Interface to Network Security Functions: I2NSF）のフレームワークを説明し、I2NSFの参照モデル（主要な機能コンポーネントを含む）を定義します。 これには、外部から提供されるネットワークセキュリティー機能（NSF）の展開がもたらす脅威の分析が含まれます。 また、NSFの能力を制限しかねない潜在的な制約を避けつつ、ソフトウェア定義ネットワーキング（SDN）やネットワーク機能仮想化（NFV）の環境において、I2NSFが技術やベンダーに依存しない方法でのセキュリティー機能の実装をどのように容易にするかも説明します。

I2NSF use cases [RFC8192] call for standard interfaces for users of an I2NSF system (e.g., applications, overlay or cloud network management system, or enterprise network administrator or management system) to inform the I2NSF system which I2NSF functions should be applied to which traffic (or traffic patterns). The I2NSF system realizes this as a set of security rules for monitoring and controlling the behavior of different traffic. It also provides standard interfaces for users to monitor flow-based security functions hosted and managed by different administrative domains.

I2NSFのユースケース[RFC8192]では、I2NSFシステムのユーザー（たとえば、アプリケーション、オーバーレイネットワークやクラウドネットワークの管理システム、企業のネットワーク管理者や管理システム）が、どのI2NSF機能をどのトラフィック（またはトラフィックパターン）に適用すべきかをI2NSFシステムに伝えるための標準インターフェイスが求められています。 I2NSFシステムは、これをさまざまなトラフィックの振る舞いを監視および制御するためのセキュリティー規則の集合として実現します。 また、異なる管理ドメインによってホストおよび管理されているフローベースのセキュリティー機能をユーザーが監視するための標準インターフェイスも提供します。

[RFC8192] also describes the motivation and the problem space for an Interface to Network Security Functions system.

[RFC8192]では、ネットワークセキュリティー機能へのインターフェイスのシステムの動機と問題領域についても説明しています。

3. I2NSF Reference Model

3. I2NSFの参照モデル

Figure 1 shows a reference model (including major functional components and interfaces) for an I2NSF system. This figure is drawn from the point of view of the Network Operator Management System; hence, this view does not assume any particular management architecture for either the NSFs or how the NSFs are managed (on the developer's side). In particular, the Network Operator Management System does not participate in NSF data-plane activities.

図1は、I2NSFシステムの参照モデル（主要な機能コンポーネントとインターフェイスを含む）を示しています。 この図はネットワーク運用者管理システム（Network Operator Management System）の視点から描かれています。 したがって、この視点では、NSFの管理アーキテクチャーや、（開発者側で）NSFがどのように管理されるかについて、特定のものを前提としていません。 特に、ネットワーク運用者管理システムは、NSFのデータプレーンの活動には関与しません。

When defining I2NSF Interfaces, this framework adheres to the following principles:

I2NSFインターフェイスを定義するにあたり、このフレームワークは次の原則に従います。

  • It is agnostic of network topology and NSF location in the network
  • It is agnostic of provider of the NSF (i.e., independent of the way that the provider makes an NSF available, as well as how the provider allows the NSF to be managed)
  • It is agnostic of any vendor-specific operational, administrative, and management implementation; hosting environment; and form factor (physical or virtual)
  • It is agnostic to NSF control-plane implementation (e.g., signaling capabilities)
  • It is agnostic to NSF data-plane implementation (e.g., encapsulation capabilities)
  • ネットワークトポロジーや、ネットワーク内でのNSFの位置に依存しません。
  • NSFのプロバイダーに依存しません（すなわち、プロバイダーがNSFを利用可能にする方法や、プロバイダーがNSFをどのように管理させるかに依存しません）。
  • ベンダー固有の運用・管理・マネジメントの実装、ホスティング環境、およびフォームファクター（物理または仮想）に依存しません。
  • NSFのコントロールプレーンの実装（たとえば、シグナリングの能力）に依存しません。
  • NSFのデータプレーンの実装（たとえば、カプセル化の能力）に依存しません。

In general, all I2NSF Interfaces should require at least mutual authentication and authorization for their use. Other security and privacy considerations are specified in Section 11.

一般に、すべてのI2NSFインターフェイスは、その使用にあたって少なくとも相互認証と認可を要求すべきです。 その他のセキュリティーとプライバシーに関する考慮事項は、セクション11で規定しています。

3.1. I2NSF Consumer-Facing Interface

3.1. I2NSFコンシューマー向けインターフェイス

The I2NSF Consumer-Facing Interface is used to enable different users of a given I2NSF system to define, manage, and monitor security policies for specific flows within an administrative domain. The location and implementation of I2NSF policies are irrelevant to the consumer of I2NSF policies.

I2NSFコンシューマー向けインターフェイス（I2NSF Consumer-Facing Interface）は、あるI2NSFシステムのさまざまなユーザーが、管理ドメイン内の特定のフローに対するセキュリティーポリシーを定義、管理、監視できるようにするために使用されます。 I2NSFポリシーの位置や実装は、I2NSFポリシーのコンシューマーには関係ありません。

Some examples of I2NSF Consumers include:

I2NSFコンシューマーの例には次のものがあります。

  • A video-conference network manager that needs to dynamically inform the underlay network to allow, rate-limit, or deny flows (some of which are encrypted) based on specific fields in the packets for a certain time span.
  • Enterprise network administrators and management systems that need to request their provider network to enforce specific I2NSF policies for particular flows.
  • An IoT management system sending requests to the underlay network to block flows that match a set of specific conditions.
  • 一定の時間帯において、パケット内の特定のフィールドに基づいてフロー（その一部は暗号化されています）を許可、レート制限、または拒否するよう、アンダーレイネットワークに動的に伝える必要があるビデオ会議のネットワーク管理者。
  • 特定のフローに対して特定のI2NSFポリシーを適用するよう、プロバイダーのネットワークに要求する必要がある企業のネットワーク管理者や管理システム。
  • 特定の条件の集合に一致するフローをブロックするよう、アンダーレイネットワークにリクエストを送るIoT管理システム。

3.2. I2NSF NSF-Facing Interface

3.2. I2NSF NSF向けインターフェイス

The I2NSF NSF-Facing Interface (NSF-Facing Interface for short) is used to specify and monitor flow-based security policies enforced by one or more NSFs. Note that the I2NSF Management System does not need to use all features of a given NSF, nor does it need to use all available NSFs. Hence, this abstraction enables NSF features to be treated as building blocks by an NSF system; thus, developers are free to use the security functions defined by NSFs independent of vendor and technology.

I2NSF NSF向けインターフェイス（I2NSF NSF-Facing Interface、略してNSF向けインターフェイス）は、1つ以上のNSFによって適用されるフローベースのセキュリティーポリシーを指定および監視するために使用されます。 I2NSF管理システムは、あるNSFのすべての機能を使用する必要はなく、利用可能なすべてのNSFを使用する必要もないことに注意してください。 したがって、この抽象化により、NSFの機能をNSFシステムの構成要素として扱えるようになります。 そのため、開発者は、ベンダーや技術に依存せずに、NSFによって定義されたセキュリティー機能を自由に使用できます。

Flow-based NSFs [RFC8192] inspect packets in the order that they are received. Note that all Interface Groups require the NSF to be registered using the Registration Interface. The interface to flow-based NSFs can be categorized as follows:

フローベースNSF[RFC8192]は、パケットを受信した順に検査します。 すべてのインターフェイスグループは、登録インターフェイスを使用してNSFが登録されていることを要求することに注意してください。 フローベースNSFへのインターフェイスは、次のように分類できます。

  1. NSF Operational and Administrative Interface: an Interface Group used by the I2NSF Management System to program the operational state of the NSF; this also includes administrative control functions. I2NSF Policy Rules represent one way to change this Interface Group in a consistent manner. Since applications and I2NSF Components need to dynamically control the behavior of traffic that they send and receive, much of the I2NSF effort is focused on this Interface Group.
  2. Monitoring Interface: an Interface Group used by the I2NSF Management System to obtain monitoring information from one or more selected NSFs. Each interface in this Interface Group could be a query- or a report-based interface. The difference is that a query-based interface is used by the I2NSF Management System to obtain information, whereas a report-based interface is used by the NSF to provide information. The functionality of this Interface Group may also be defined by other protocols, such as SYSLOG and DOTS. The I2NSF Management System may take one or more actions based on the receipt of information; this should be specified by an I2NSF Policy Rule. This Interface Group does NOT change the operational state of the NSF.
  1. NSF運用・管理インターフェイス（NSF Operational and Administrative Interface）：I2NSF管理システムがNSFの運用状態をプログラムするために使用するインターフェイスグループです。 これには管理上の制御機能も含まれます。 I2NSFポリシー規則は、このインターフェイスグループを一貫した方法で変更するための1つの方法です。 アプリケーションやI2NSFコンポーネントは、それらが送受信するトラフィックの振る舞いを動的に制御する必要があるため、I2NSFの取り組みの多くはこのインターフェイスグループに焦点を当てています。
  2. 監視インターフェイス（Monitoring Interface）：I2NSF管理システムが、選択された1つ以上のNSFから監視情報を取得するために使用するインターフェイスグループです。 このインターフェイスグループの各インターフェイスは、クエリーベースのインターフェイスまたは報告ベースのインターフェイスのいずれかです。 両者の違いは、クエリーベースのインターフェイスはI2NSF管理システムが情報を取得するために使用するのに対し、報告ベースのインターフェイスはNSFが情報を提供するために使用することです。 このインターフェイスグループの機能は、SYSLOGやDOTSなどの他のプロトコルによって定義されることもあります。 I2NSF管理システムは、情報の受信に基づいて1つ以上のアクションを実行することがあります。 これはI2NSFポリシー規則によって指定されるべきです。 このインターフェイスグループは、NSFの運用状態を変更しません（does NOT change）。

This document uses the flow-based paradigm to develop the NSF-Facing Interface. A common trait of flow-based NSFs is in the processing of packets based on the content (e.g., header/payload) and/or context (e.g., session state and authentication state) of the received packets. This feature is one of the requirements for defining the behavior of I2NSF.

この文書では、NSF向けインターフェイスを策定するためにフローベースのパラダイムを使用します。 フローベースNSFに共通する特徴は、受信したパケットのコンテンツ（たとえば、ヘッダーやペイロード）やコンテキスト（たとえば、セッションの状態や認証の状態）に基づいてパケットを処理することです。 この特徴は、I2NSFの振る舞いを定義するための要件の1つです。

3.3. I2NSF Registration Interface

3.3. I2NSF登録インターフェイス

NSFs provided by different vendors may have different capabilities. In order to automate the process of utilizing multiple types of security functions provided by different vendors, it is necessary to have a dedicated interface for vendors to define the capabilities of (i.e., register) their NSFs. This interface is called the I2NSF Registration Interface.

異なるベンダーが提供するNSFは、異なる能力を持つことがあります。 異なるベンダーが提供する複数の種類のセキュリティー機能を利用するプロセスを自動化するには、ベンダーが自社のNSFの能力を定義する（すなわち、登録する）ための専用のインターフェイスが必要です。 このインターフェイスをI2NSF登録インターフェイス（I2NSF Registration Interface）と呼びます。

An NSF's capabilities can be either pre-configured or retrieved dynamically through the I2NSF Registration Interface. If a new function that is exposed to the consumer is added to an NSF, then the capabilities of that new function should be registered in the I2NSF Registry via the I2NSF Registration Interface, so that interested management and control entities may be made aware of them.

NSFの能力は、事前に設定することも、I2NSF登録インターフェイスを通じて動的に取得することもできます。 コンシューマーに公開される新しい機能がNSFに追加された場合、関心を持つ管理エンティティーや制御エンティティーがその能力を把握できるように、その新しい機能の能力をI2NSF登録インターフェイス経由でI2NSFレジストリーに登録すべきです。

4. Threats Associated with Externally Provided NSFs

4. 外部から提供されるNSFに関連する脅威

While associated with a much higher flexibility, and in many cases a necessary approach given the deployment conditions, the usage of externally provided NSFs implies several additional concerns in security. The most relevant threats associated with a security platform of this nature are:

外部から提供されるNSFの使用は、はるかに高い柔軟性を伴い、また展開の条件によっては多くの場合に必要なアプローチですが、セキュリティー上の追加の懸念をいくつかもたらします。 この種のセキュリティープラットフォームに関連する最も重要な脅威は次のとおりです。

  • An unknown/unauthorized user can try to impersonate another user that can legitimately access external NSF services. This attack may lead to accessing the I2NSF Policy Rules and applications of the attacked user and/or generating network traffic outside the security functions with a falsified identity.
  • An authorized user may misuse assigned privileges to alter the network traffic processing of other users in the NSF underlay or platform.
  • A user may try to install malformed elements (e.g., I2NSF Policy Rules or configuration files) to directly take control of an NSF or the whole provider platform. For example, a user may exploit a vulnerability on one of the functions or may try to intercept or modify the traffic of other users in the same provider platform.
  • A malicious provider can modify the software (e.g., the operating system or the specific NSF implementation) to alter the behavior of one or more NSFs. This event has a high impact on all users accessing NSFs, since the provider has the highest level of privileges controlling the operation of the software.
  • A user that has physical access to the provider platform can modify the behavior of the hardware/software components or the components themselves. For example, the user can access a serial console (most devices offer this interface for maintenance reasons) to access the NSF software with the same level of privilege of the provider.
  • 未知のユーザーや認可されていないユーザーが、外部のNSFサービスに正当にアクセスできる別のユーザーになりすまそうとする可能性があります。 この攻撃により、攻撃を受けたユーザーのI2NSFポリシー規則やアプリケーションにアクセスされたり、偽装された身元を使ってセキュリティー機能の外側でネットワークトラフィックを生成されたりする可能性があります。
  • 認可されたユーザーが、割り当てられた権限を悪用して、NSFのアンダーレイやプラットフォームにおける他のユーザーのネットワークトラフィックの処理を改変する可能性があります。
  • ユーザーが、NSFやプロバイダーのプラットフォーム全体を直接制御するために、不正な形式の要素（たとえば、I2NSFポリシー規則や設定ファイル）をインストールしようとする可能性があります。 たとえば、ユーザーがいずれかの機能の脆弱性を悪用したり、同じプロバイダーのプラットフォーム上の他のユーザーのトラフィックを傍受または改変しようとしたりする可能性があります。
  • 悪意のあるプロバイダーが、1つ以上のNSFの振る舞いを改変するために、ソフトウェア（たとえば、オペレーティングシステムや特定のNSFの実装）を改変する可能性があります。 プロバイダーはソフトウェアの動作を制御する最高レベルの権限を持っているため、この事態はNSFにアクセスするすべてのユーザーに大きな影響を与えます。
  • プロバイダーのプラットフォームに物理的にアクセスできるユーザーが、ハードウェアやソフトウェアのコンポーネントの振る舞い、またはコンポーネントそのものを改変する可能性があります。 たとえば、そのユーザーは、シリアルコンソール（ほとんどのデバイスは保守のためにこのインターフェイスを提供しています）にアクセスして、プロバイダーと同じレベルの権限でNSFのソフトウェアにアクセスできます。

The use of authentication, authorization, accounting, and audit mechanisms is recommended for all users and applications to access the I2NSF environment. This can be further enhanced by requiring attestation to be used to detect changes to the I2NSF environment by authorized parties. The characteristics of these procedures will define the level of assurance of the I2NSF environment.

すべてのユーザーとアプリケーションがI2NSF環境にアクセスする際には、認証、認可、アカウンティング、および監査のメカニズムを使用することが推奨されます。 これは、認可された当事者によるI2NSF環境への変更を検出するためにアテステーションの使用を要求することで、さらに強化できます。 これらの手順の特性によって、I2NSF環境の保証レベルが定まります。

5. Avoiding NSF Ossification

5. NSFの硬直化の回避

A basic tenet in the introduction of I2NSF standards is that the standards should not make it easier for attackers to compromise the network. Therefore, in constructing standards for I2NSF Interfaces as well as I2NSF Policy Rules, it is equally important to allow support for specific functions, as this enables the introduction of NSFs that evolve to meet new threats. Proposed standards for I2NSF Interfaces to communicate with NSFs, as well as I2NSF Policy Rules to control NSF functionality, should not:

I2NSF標準の導入における基本的な信条は、標準によって攻撃者がネットワークを侵害しやすくなってはならないということです。 したがって、I2NSFインターフェイスやI2NSFポリシー規則の標準を策定するにあたっては、特定の機能のサポートを可能にすることも同様に重要です。 これにより、新たな脅威に対応するために進化するNSFを導入できるようになるからです。 NSFと通信するためのI2NSFインターフェイスや、NSFの機能を制御するためのI2NSFポリシー規則として提案される標準は、次のようなものであるべきではありません。

  • Narrowly define NSF categories, or their roles, when implemented within a network. Security is a constantly evolving discipline. The I2NSF framework relies on an object-oriented information model, which provides an extensible definition of NSF information elements and categories; it is recommended that implementations follow this model.
  • Attempt to impose functional requirements or constraints, either directly or indirectly, upon NSF developers. Implementations should be free to realize and apply NSFs in a way that best suits the needs of the applications and environment using them.
  • Be a limited lowest common denominator approach, where interfaces can only support a limited set of standardized functions, without allowing for developer-specific functions. NSFs, interfaces, and the data communicated should be extensible, so that they can evolve to protect against new threats.
  • Be seen as endorsing a best common practice for the implementation of NSFs; rather, this document describes the conceptual structure and reference model of I2NSF. The purpose of this reference model is to define a common set of concepts in order to facilitate the flexible implementation of an I2NSF system.
  • ネットワーク内に実装されるNSFのカテゴリーやそのロールを狭く定義するもの。 セキュリティーは絶えず進化している分野です。 I2NSFフレームワークは、NSFの情報要素とカテゴリーの拡張可能な定義を提供するオブジェクト指向の情報モデルに依拠しています。 実装はこのモデルに従うことが推奨されます。
  • NSFの開発者に対して、直接的または間接的に、機能要件や制約を課そうとするもの。 実装は、NSFを使用するアプリケーションや環境のニーズに最も適した方法で、NSFを自由に実現し、適用できるべきです。
  • インターフェイスが標準化された限られた機能の集合しかサポートできず、開発者固有の機能を許容しない、限定的な最小公分母のアプローチであるもの。 NSF、インターフェイス、および通信されるデータは、新たな脅威から保護するために進化できるよう、拡張可能であるべきです。
  • NSFの実装のための共通のベストプラクティスを推奨していると見なされるもの。 むしろ、この文書はI2NSFの概念的な構造と参照モデルを説明するものです。 この参照モデルの目的は、I2NSFシステムの柔軟な実装を容易にするために、共通の概念の集合を定義することです。

To prevent constraints on NSF developers' creativity and innovation, this document recommends flow-based NSF interfaces to be designed from the paradigm of processing packets in the network. Flow-based NSFs are ultimately packet-processing engines that inspect packets traversing networks, either directly or in the context of sessions in which the packet is associated. The goal is to create a workable interface to NSFs that aids in their integration within legacy, SDN, and/or NFV environments, while avoiding potential constraints that could limit their functional capabilities.

NSFの開発者の創造性や革新を制約しないように、この文書では、フローベースのNSFインターフェイスを、ネットワーク内でパケットを処理するというパラダイムに基づいて設計することを推奨します。 フローベースNSFは、つまるところ、ネットワークを通過するパケットを、直接、またはパケットが関連付けられているセッションのコンテキストにおいて検査するパケット処理エンジンです。 その目標は、NSFの機能上の能力を制限しかねない潜在的な制約を避けつつ、レガシー、SDN、NFVの各環境へのNSFの統合を支援する、実用的なNSFへのインターフェイスを作ることです。

6. The Network Connecting I2NSF Components

6. I2NSFコンポーネントを接続するネットワーク

6.1. Network Connecting I2NSF Users and the I2NSF Controller

6.1. I2NSFユーザーとI2NSFコントローラーを接続するネットワーク

As a general principle, in the I2NSF environment, users directly interact with the I2NSF Controller. Given the role of the I2NSF Controller, a mutual authentication of users and the I2NSF Controller is required. I2NSF does not mandate a specific authentication scheme; it is up to the users to choose available authentication schemes based on their needs.

一般的な原則として、I2NSF環境では、ユーザーはI2NSFコントローラーと直接やり取りします。 I2NSFコントローラーの役割を考えると、ユーザーとI2NSFコントローラーの相互認証が必要です。 I2NSFは特定の認証方式を義務付けません。 利用可能な認証方式をニーズに基づいて選択するのはユーザーに任されています。

Upon successful authentication, a trusted connection between the user and the I2NSF Controller (or an endpoint designated by it) will be established. This means that a direct, physical point-to-point connection, with physical access restricted according to access control, must be used. All traffic to and from the NSF environment will flow through this connection. The connection is intended not only to be secure but trusted in the sense that it should be bound to the mutual authentication between the user and the I2NSF Controller, as described in [I2NSF-ATTESTATION]. The only possible exception is when the required level of assurance is lower (see Section 4.1 of [I2NSF-ATTESTATION]), in which case the user must be made aware of this circumstance.

認証に成功すると、ユーザーとI2NSFコントローラー（またはI2NSFコントローラーが指定したエンドポイント）の間に信頼できるコネクションが確立されます。 これは、アクセス制御に従って物理的なアクセスが制限された、直接の物理的なポイントツーポイント接続を使用しなければならないことを意味します。 NSF環境との間のすべてのトラフィックは、このコネクションを通って流れます。 このコネクションは、安全であるだけでなく、[I2NSF-ATTESTATION]で説明されているように、ユーザーとI2NSFコントローラーの間の相互認証に結び付けられるべきであるという意味で、信頼できるものであることを意図しています。 唯一ありうる例外は、要求される保証レベルがより低い場合（[I2NSF-ATTESTATION]のセクション4.1を参照）であり、その場合はユーザーにこの状況を認識させなければなりません。

6.2. Network Connecting the I2NSF Controller and NSFs

6.2. I2NSFコントローラーとNSFを接続するネットワーク

Most likely, the NSFs are not directly attached to the I2NSF Controller; for example, NSFs can be distributed across the network. The network that connects the I2NSF Controller with the NSFs can be the same network that carries the data traffic, or it can be a dedicated network for management purposes only. In either case, packet loss could happen due to failure, congestion, or other reasons.

NSFは、I2NSFコントローラーに直接接続されていない可能性が高いです。 たとえば、NSFはネットワーク全体に分散していることがあります。 I2NSFコントローラーとNSFを接続するネットワークは、データトラフィックを運ぶネットワークと同じこともあれば、管理目的だけの専用ネットワークのこともあります。 いずれの場合も、障害、輻輳、その他の理由によってパケット損失が発生する可能性があります。

Therefore, the transport mechanism used to carry management data and information must be secure. It does not have to be a reliable transport; rather, a transport-independent reliable messaging mechanism is required, where communication can be performed reliably (e.g., by establishing end-to-end communication sessions and by introducing explicit acknowledgement of messages into the communication flow). Latency requirements for control message delivery must also be evaluated. Note that monitoring does not require reliable transport.

したがって、管理データや管理情報を運ぶために使用するトランスポートメカニズムは安全でなければなりません。 それは信頼性のあるトランスポートである必要はありません。 むしろ、通信を信頼性のある形で行える（たとえば、エンドツーエンドの通信セッションを確立したり、メッセージの明示的な確認応答を通信フローに導入したりすることによって）、トランスポートに依存しない信頼性のあるメッセージングメカニズムが必要です。 制御メッセージの配送に関する遅延の要件も評価しなければなりません。 監視には信頼性のあるトランスポートは必要ないことに注意してください。

The network connection between the I2NSF Controller and NSFs can rely on either:

I2NSFコントローラーとNSFの間のネットワーク接続は、次のいずれかに依拠できます。

  • Open environments, where one or more NSFs can be hosted in one or more external administrative domains that are reached via secure external network connections. This requires more restrictive security control to be placed over the I2NSF Interface. The information over the I2NSF Interfaces shall be exchanged by using the trusted connection described in Section 6.1, or
  • Closed environments, where there is only one administrative domain. Such environments provide a more **isolated** environment but still communicate over the same set of I2NSF Interfaces present in open environments (see above). Hence, the security control and access requirements for closed environments are the same as those for open environments.
  • オープン環境。 この環境では、1つ以上のNSFを、安全な外部ネットワーク接続を介して到達する1つ以上の外部の管理ドメインでホストできます。 これには、I2NSFインターフェイスに対して、より厳格なセキュリティー制御を課すことが必要です。 I2NSFインターフェイス上の情報は、セクション6.1で説明した信頼できるコネクションを使用して交換されることになります。または、
  • クローズド環境。 この環境では、管理ドメインは1つだけです。 このような環境は、より**隔離された**環境を提供しますが、それでもオープン環境に存在するのと同じI2NSFインターフェイスの集合を介して通信します（上記を参照）。 したがって、クローズド環境のセキュリティー制御とアクセスの要件は、オープン環境のものと同じです。

The network connection between the I2NSF Controller and NSFs will use the trusted connection mechanisms described in Section 6.1. Following these mechanisms, the connections need to rely on the use of properly verified peer identities (e.g., through an Authentication, Authorization, and Accounting (AAA) framework). The implementations of identity management functions, as well as the AAA framework, are out of scope for I2NSF.

I2NSFコントローラーとNSFの間のネットワーク接続は、セクション6.1で説明した信頼できるコネクションのメカニズムを使用します。 これらのメカニズムに従い、コネクションは、適切に検証されたピアの身元を使用すること（たとえば、認証・認可・アカウンティング（AAA）フレームワークを通じて）に依拠する必要があります。 身元管理機能の実装やAAAフレームワークは、I2NSFの範囲外です。

6.3. Interface to vNSFs

6.3. vNSFへのインターフェイス

There are some unique characteristics in interfacing to virtual NSFs (vNSFs):

仮想NSF（vNSF）とのインターフェイスには、いくつかの固有の特性があります。

  • There could be multiple instantiations of one single NSF that has been distributed across a network. When different instantiations are visible to the I2NSF Controller, different policies may be applied to different instantiations of an individual NSF (e.g., to reflect the different roles that each vNSF is designated for). Therefore, it is recommended that Roles, in addition to the use of robust identities, be used to distinguish between different instantiations of the same vNSF. Note that this also applies to physical NSFs.
  • When multiple instantiations of one single NSF appear as one single entity to the I2NSF Controller, the I2NSF Controller may need to get assistance from other entities in the I2NSF Management System and/or delegate the provisioning of the multiple instantiations of the (single) NSF to other entities in the I2NSF Management System. This is shown in Figure 2 below.
  • Policies enforced by one vNSF instance may need to be retrieved and moved to another vNSF of the same type when user flows are moved from one vNSF to another.
  • Multiple vNSFs may share the same physical platform.
  • There may be scenarios where multiple vNSFs collectively perform the security policies needed.
  • ネットワーク全体に分散された1つのNSFに、複数のインスタンスが存在することがあります。 異なるインスタンスがI2NSFコントローラーから見える場合、個々のNSFの異なるインスタンスに異なるポリシーが適用されることがあります（たとえば、各vNSFが割り当てられた異なるロールを反映するため）。 したがって、同じvNSFの異なるインスタンスを区別するために、堅牢な身元の使用に加えて、ロールを使用することが推奨されます。 これは物理的なNSFにも当てはまることに注意してください。
  • 1つのNSFの複数のインスタンスが、I2NSFコントローラーから1つのエンティティーとして見える場合、I2NSFコントローラーは、I2NSF管理システム内の他のエンティティーの支援を得たり、（単一の）NSFの複数のインスタンスのプロビジョニングをI2NSF管理システム内の他のエンティティーに委任したりする必要があるかもしれません。 これを下の図2に示します。
  • ユーザーのフローがあるvNSFから別のvNSFに移される場合、あるvNSFインスタンスによって適用されているポリシーを取得し、同じ種類の別のvNSFに移す必要があるかもしれません。
  • 複数のvNSFが同じ物理プラットフォームを共有することがあります。
  • 複数のvNSFが協調して、必要なセキュリティーポリシーを実行するシナリオもありえます。

6.4. Consistency

6.4. 一貫性

There are three basic models of consistency:

一貫性には3つの基本的なモデルがあります。

  • centralized, which uses a single manager to impose behavior
  • decentralized, in which managers make decisions without being aware of each other (i.e., managers do not exchange information)
  • distributed, in which managers make explicit use of information exchange to arrive at a decision
  • 集中型（centralized）：単一のマネージャーを使用して振る舞いを課します。
  • 非集中型（decentralized）：マネージャーが互いを認識せずに意思決定を行います（すなわち、マネージャー同士は情報を交換しません）。
  • 分散型（distributed）：マネージャーが情報交換を明示的に利用して意思決定に至ります。

This document does NOT make a recommendation on which of the above three models to use. I2NSF Policy Rules, coupled with an appropriate management strategy, is applicable to the design and integration of any of the above three consistency models.

この文書では、上記の3つのモデルのどれを使用すべきかについての推奨は行いません（does NOT make a recommendation）。 I2NSFポリシー規則は、適切な管理戦略と組み合わせることで、上記の3つの一貫性モデルのいずれの設計と統合にも適用できます。

7. I2NSF Flow Security Policy Structure

7. I2NSFのフローセキュリティーポリシーの構造

Even though security functions come in a variety of form factors and have different features, provisioning to flow-based NSFs can be standardized by using policy rules.

セキュリティー機能にはさまざまなフォームファクターがあり、それぞれ異なる機能を持っていますが、フローベースNSFへのプロビジョニングは、ポリシー規則を使用することで標準化できます。

In this version of I2NSF, policy rules are limited to imperative paradigms. I2NSF is using an Event-Condition-Action (ECA) policy, where:

このバージョンのI2NSFでは、ポリシー規則は命令型のパラダイムに限定されています。 I2NSFは、イベント・条件・アクション（Event-Condition-Action: ECA）ポリシーを使用しています。 ここで、

  • An Event clause is used to trigger the evaluation of the Condition clause of the I2NSF Policy Rule.
  • A Condition clause is used to determine whether or not the set of Actions in the I2NSF Policy Rule can be executed or not.
  • An Action clause defines the type of operations that may be performed on this packet or flow.
  • イベント（Event）節は、I2NSFポリシー規則の条件節の評価を起動するために使用されます。
  • 条件（Condition）節は、I2NSFポリシー規則のアクションの集合を実行できるかどうかを判断するために使用されます。
  • アクション（Action）節は、このパケットまたはフローに対して実行されうる操作の種類を定義します。

Each of the above three clauses are defined to be Boolean clauses. This means that each is a logical statement that evaluates to either TRUE or FALSE.

上記の3つの節は、それぞれブール節として定義されています。 これは、それぞれがTRUEまたはFALSEのいずれかに評価される論理文であることを意味します。

The above concepts are described in detail in [I2NSF-CAPABILITIES].

上記の概念は、[I2NSF-CAPABILITIES]で詳しく説明されています。

7.1. Customer-Facing Flow Security Policy Structure

7.1. 顧客向けのフローセキュリティーポリシーの構造

This layer is for the user's network management system to express and monitor the needed flow security policies for their specific flows.

この層は、ユーザーのネットワーク管理システムが、自身の特定のフローに必要なフローセキュリティーポリシーを表現および監視するためのものです。

Some customers may not have the requisite security skills to express security requirements or policies that are precise enough to implement in an NSF. These customers may instead express expectations (e.g., goals or intent) of the functionality desired by their security policies. Customers may also express guidelines, such as which types of destinations are (or are not) allowed for certain users. As a result, there could be different levels of content and abstractions used in Service Layer policies. Here are some examples of more abstract security policies that can be developed based on the I2NSF-defined Customer-Facing Interface:

顧客によっては、NSFに実装できるほど正確なセキュリティー要件やポリシーを表現するのに必要なセキュリティーのスキルを持っていないことがあります。 そのような顧客は、代わりに、セキュリティーポリシーに望む機能についての期待（たとえば、目標や意図）を表現することがあります。 顧客は、特定のユーザーに対してどの種類の宛先が許可される（または許可されない）かといったガイドラインを表現することもあります。 その結果、サービス層のポリシーで使用されるコンテンツや抽象化のレベルはさまざまになりえます。 I2NSFが定義する顧客向けインターフェイス（Customer-Facing Interface）に基づいて策定できる、より抽象的なセキュリティーポリシーの例を次に示します。

  • Enable Internet access for authenticated users
  • Any operation on a HighValueAsset must use the corporate network
  • The use of FTP from any user except the CxOGroup must be audited

One flow policy over the Customer-Facing Interface may need multiple NSFs at various locations to achieve the desired enforcement. Some flow security policies from users may not be granted because of resource constraints. [I2NSF-DEMO] describes an implementation of translating a set of 1) user policies to flow policies and 2) flow policies to individual NSFs.

顧客向けインターフェイス上の1つのフローポリシーは、望ましい適用を実現するために、さまざまな場所にある複数のNSFを必要とすることがあります。 ユーザーからのフローセキュリティーポリシーの中には、リソースの制約のために受け入れられないものもありえます。 [I2NSF-DEMO]は、1）ユーザーポリシーからフローポリシーへの変換と、2）フローポリシーから個々のNSFへの変換の実装について説明しています。

I2NSF will first focus on user policies that can be modeled as closely as possible to the flow security policies used by individual NSFs. An I2NSF user flow policy should be similar in structure to the structure of an I2NSF Policy Rule, but with more of a user-oriented expression for the packet content, the context, and other parts of an ECA policy rule. This enables the user to construct an I2NSF Policy Rule without having to know the exact syntax of the desired content (e.g., actual tags or addresses) to match in the packets. For example, when used in the context of policy rules over the Client-Facing Interface:

I2NSFはまず、個々のNSFが使用するフローセキュリティーポリシーにできるだけ近くモデル化できるユーザーポリシーに焦点を当てます。 I2NSFのユーザーフローポリシーは、構造の面でI2NSFポリシー規則の構造に似ているべきですが、パケットのコンテンツ、コンテキスト、およびECAポリシー規則の他の部分については、よりユーザー指向の表現を用いるべきです。 これにより、ユーザーは、パケット内で一致させたいコンテンツ（たとえば、実際のタグやアドレス）の正確な構文を知らなくても、I2NSFポリシー規則を構築できます。 たとえば、クライアント向けインターフェイス（Client-Facing Interface）上のポリシー規則のコンテキストで使用する場合、次のようになります。

  • An Event can be "the client has passed the AAA process"
  • A Condition can be matching the user identifier or from specific ingress or egress points
  • An Action can be establishing an IPsec tunnel
  • イベントは「クライアントがAAAプロセスを通過した」とすることができます。
  • 条件は、ユーザー識別子との一致や、特定の入口点または出口点からであることとすることができます。
  • アクションは、IPsecトンネルの確立とすることができます。

7.2. NSF-Facing Flow Security Policy Structure

7.2. NSF向けのフローセキュリティーポリシーの構造

The NSF-Facing Interface is to pass explicit rules to individual NSFs to treat packets, as well as methods to monitor the execution status of those functions.

NSF向けインターフェイスは、パケットを扱うための明示的な規則と、それらの機能の実行状態を監視するための方法を、個々のNSFに渡すためのものです。

Here are some examples of Events over the NSF-Facing Interface:

NSF向けインターフェイス上のイベントの例を次に示します。

  • time == 08:00
  • notification that a NSF state changes from standby to active
  • user logon or logoff
  • time == 08:00
  • NSFの状態がスタンバイからアクティブに変わったことの通知
  • ユーザーのログオンまたはログオフ

Here are some examples of Conditions over the NSF-Facing Interface:

NSF向けインターフェイス上の条件の例を次に示します。

  • Packet content values that look for one or more packet headers, data from the packet payload, bits in the packet, or data that are derived from the packet.
  • Context values that are based on measured and/or inferred knowledge, which can be used to define the state and environment in which a managed entity exists or has existed. In addition to state data, this includes data from sessions, direction of the traffic, time, and geo-location information. State refers to the behavior of a managed entity at a particular point in time. Hence, it may refer to situations in which multiple pieces of information that are not available at the same time must be analyzed. For example, tracking established TCP connections (connections that have gone through the initial three-way handshake).
  • 1つ以上のパケットヘッダー、パケットのペイロードのデータ、パケット内のビット、またはパケットから導出されたデータを調べるパケットコンテンツの値。
  • 測定された知識や推論された知識に基づくコンテキストの値。 これは、管理対象のエンティティーが存在する、または存在していた状態と環境を定義するために使用できます。 状態データに加えて、これにはセッションからのデータ、トラフィックの方向、時刻、地理的位置の情報が含まれます。 状態とは、ある特定の時点における管理対象のエンティティーの振る舞いを指します。 したがって、同時には得られない複数の情報を分析しなければならない状況を指すこともあります。 たとえば、確立済みのTCPコネクション（最初のスリーウェイハンドシェイクを終えたコネクション）を追跡することです。

Actions to individual flow-based NSFs include:

個々のフローベースNSFに対するアクションには、次のものがあります。

  • Actions performed on ingress packets, such as pass, drop, rate limiting, and mirroring.
  • Actions performed on egress packets, such as invoke signaling, tunnel encapsulation, packet forwarding, and/or transformation.
  • Applying a specific functional profile or signature -- e.g., an IPS Profile, a signature file, an anti-virus file, or a URL filtering file. Many flow-based NSFs utilize profile and/or signature files to achieve more effective threat detection and prevention. It is not uncommon for an NSF to apply different profiles and/or signatures for different flows. Some profiles/signatures do not require any knowledge of past or future activities, while others are stateful and may need to maintain state for a specific length of time.
  • 入力パケットに対して実行されるアクション。 たとえば、通過、破棄、レート制限、ミラーリングなどです。
  • 出力パケットに対して実行されるアクション。 たとえば、シグナリングの起動、トンネルのカプセル化、パケットの転送、変換などです。
  • 特定の機能プロファイルやシグネチャーの適用。 たとえば、IPSプロファイル、シグネチャーファイル、アンチウイルスファイル、URLフィルタリングファイルなどです。 多くのフローベースNSFは、より効果的な脅威の検出と防止を実現するために、プロファイルファイルやシグネチャーファイルを利用します。 NSFがフローごとに異なるプロファイルやシグネチャーを適用することは珍しくありません。 プロファイルやシグネチャーの中には、過去や将来の活動についての知識をまったく必要としないものもあれば、ステートフルで、特定の期間にわたって状態を維持する必要があるものもあります。

The functional profile or signature file is one of the key properties that determine the effectiveness of the NSF and is mostly NSF specific today. The rulesets and software interfaces of I2NSF aim to specify the format to pass profile and signature files while supporting specific functionalities of each.

機能プロファイルやシグネチャーファイルは、NSFの有効性を決定する重要な特性の1つであり、現在ではそのほとんどがNSF固有のものです。 I2NSFの規則セットとソフトウェアインターフェイスは、それぞれの特定の機能をサポートしつつ、プロファイルファイルやシグネチャーファイルを渡すための形式を規定することを目指しています。

Policy consistency among multiple security function instances is very critical because security policies are no longer maintained by one central security device; instead, they are enforced by multiple security functions instantiated at various locations.

セキュリティーポリシーはもはや1つの中央のセキュリティーデバイスによって維持されるのではなく、さまざまな場所でインスタンス化された複数のセキュリティー機能によって適用されるため、複数のセキュリティー機能インスタンスの間でのポリシーの一貫性は非常に重要です。

7.3. Differences from ACL Data Models

7.3. ACLデータモデルとの違い

Policy rules are very different from Access Control Lists (ACLs). An ACL is NOT a policy. Rather, policies are used to manage the construction and life cycle of an ACL.

ポリシー規則は、アクセス制御リスト（ACL）とは大きく異なります。 ACLはポリシーではありません（is NOT a policy）。 むしろ、ポリシーはACLの構築とライフサイクルを管理するために使用されます。

[ACL-YANG] has defined rules for ACLs supported by most routers/switches that forward packets based on their L2, L3, or sometimes L4 headers. The actions for ACLs include Pass, Drop, or Redirect.

[ACL-YANG]は、L2、L3、または場合によってはL4のヘッダーに基づいてパケットを転送する、ほとんどのルーターやスイッチがサポートするACLのための規則を定義しています。 ACLのアクションには、Pass、Drop、Redirectがあります。

The functional profiles (or signatures) for NSFs are not present in [ACL-YANG] because the functional profiles are unique to specific NSFs. For example, most IPS/IDS implementations have their proprietary functions/profiles. One of the goals of I2NSF is to define a common envelope format for exchanging or sharing profiles among different organizations to achieve more effective protection against threats.

機能プロファイルは特定のNSFに固有のものであるため、NSFの機能プロファイル（またはシグネチャー）は[ACL-YANG]には存在しません。 たとえば、ほとんどのIPSやIDSの実装は、独自の機能やプロファイルを持っています。 I2NSFの目標の1つは、脅威に対するより効果的な保護を実現するために、異なる組織の間でプロファイルを交換または共有するための共通のエンベロープ形式を定義することです。

The "packet content matching" of the I2NSF policies should not only include the matching criteria specified by [ACL-YANG] but also the L4-L7 fields depending on the NSFs selected.

I2NSFポリシーの「パケットコンテンツのマッチング」には、[ACL-YANG]で規定されているマッチング基準だけでなく、選択されたNSFに応じてL4～L7のフィールドも含めるべきです。

Some flow-based NSFs need matching criteria that include the context associated with the packets. This may also include metadata.

フローベースNSFの中には、パケットに関連付けられたコンテキストを含むマッチング基準を必要とするものがあります。 これにはメタデータも含まれることがあります。

The I2NSF "actions" should extend the actions specified by [ACL-YANG] to include applying statistics functions, threat profiles, or signature files that clients provide.

I2NSFの「アクション」は、[ACL-YANG]で規定されているアクションを拡張して、クライアントが提供する統計機能、脅威プロファイル、またはシグネチャーファイルの適用を含めるべきです。

8. Capability Negotiation

8. 能力のネゴシエーション

It is very possible that the underlay network (or provider network) does not have the capability or resources to enforce the flow security policies requested by the overlay network (or enterprise network). Therefore, it is required that the I2NSF system support dynamic discovery capabilities, as well as a query mechanism, so that the I2NSF system can expose appropriate security services using I2NSF capabilities. This may also be used to support negotiation between a user and the I2NSF system. Such dynamic negotiation facilitates the delivery of the required security service(s). The outcome of the negotiation would feed the I2NSF Management System, which would then dynamically allocate appropriate NSFs (along with any resources needed by the allocated NSFs) and configure the set of security services that meet the requirements of the user.

アンダーレイネットワーク（またはプロバイダーネットワーク）が、オーバーレイネットワーク（または企業ネットワーク）から要求されたフローセキュリティーポリシーを適用するための能力やリソースを持っていないことは十分にありえます。 したがって、I2NSFシステムがI2NSFの能力を使用して適切なセキュリティーサービスを公開できるように、I2NSFシステムは動的な発見の能力とクエリーのメカニズムをサポートする必要があります。 これは、ユーザーとI2NSFシステムの間のネゴシエーションをサポートするためにも使用できます。 このような動的なネゴシエーションは、必要なセキュリティーサービスの提供を容易にします。 ネゴシエーションの結果はI2NSF管理システムに供給され、I2NSF管理システムは適切なNSF（および割り当てられたNSFが必要とするリソース）を動的に割り当て、ユーザーの要件を満たすセキュリティーサービスの集合を設定することになります。

When an NSF cannot perform the desired provisioning (e.g., due to resource constraints), it must inform the I2NSF Management System. The protocol needed for this security function/capability negotiation may be somewhat correlated to the dynamic service parameter negotiation procedure described in [RFC7297]. The Connectivity Provisioning Profile (CPP) template, even though currently covering only connectivity requirements, includes security clauses such as isolation requirements and non-via nodes. Hence, it could be extended as a basis for the negotiation procedure. Likewise, the companion Connectivity Provisioning Negotiation Protocol (CPNP) could be a candidate for the negotiation procedure.

NSFが望ましいプロビジョニングを実行できない場合（たとえば、リソースの制約のため）、NSFはI2NSF管理システムにそれを通知しなければなりません。 このセキュリティー機能や能力のネゴシエーションに必要なプロトコルは、[RFC7297]で説明されている動的なサービスパラメーターのネゴシエーション手順と、ある程度関連している可能性があります。 コネクティビティープロビジョニングプロファイル（Connectivity Provisioning Profile: CPP）のテンプレートは、現在のところ接続性の要件だけを対象としていますが、分離の要件や経由しないノード（non-via nodes）などのセキュリティーに関する条項を含んでいます。 したがって、ネゴシエーション手順の基礎として拡張できる可能性があります。 同様に、対となるコネクティビティープロビジョニングネゴシエーションプロトコル（Connectivity Provisioning Negotiation Protocol: CPNP）も、ネゴシエーション手順の候補となりえます。

"Security-as-a-Service" would be a typical example of the kind of (CPP-based) negotiation procedures that could take place between a corporate customer and a service provider. However, more security-specific parameters have to be considered.

「Security-as-a-Service」は、企業の顧客とサービスプロバイダーの間で行われうる（CPPベースの）ネゴシエーション手順の典型的な例でしょう。 ただし、よりセキュリティーに特化したパラメーターを考慮する必要があります。

[I2NSF-CAPABILITIES] describes the concepts of capabilities in detail.

[I2NSF-CAPABILITIES]では、能力の概念を詳しく説明しています。

9.1. Flow-Based NSF Capability Characterization

9.1. フローベースNSFの能力の特徴付け

There are many types of flow-based NSFs. Firewall, IPS, and IDS are the commonly deployed flow-based NSFs. However, the differences among them are definitely blurring, due to more powerful technology, integration of platforms, and new threats. Basic types of flow-based NSFs include:

フローベースNSFには多くの種類があります。 ファイアウォール、IPS、IDSは、一般的に展開されているフローベースNSFです。 しかし、より強力な技術、プラットフォームの統合、新たな脅威により、それらの違いは確実に曖昧になってきています。 フローベースNSFの基本的な種類には、次のものがあります。

  • Firewall -- A device or a function that analyzes packet headers and enforces policy based on protocol type, source address, destination address, source port, destination port, and/or other attributes of the packet header. Packets that do not match policy are rejected. Note that additional functions, such as logging and notification of a system administrator, could optionally be enforced as well.
  • IDS (Intrusion Detection System) -- A device or function that analyzes packets, both header and payload, looking for known events. When a known event is detected, a log message is generated detailing the event. Note that additional functions, such as notification of a system administrator, could optionally be enforced as well.
  • IPS (Intrusion Prevention System) -- A device or function that analyzes packets, both header and payload, looking for known events. When a known event is detected, the packet is rejected. Note that additional functions, such as logging and notification of a system administrator, could optionally be enforced as well.
  • ファイアウォール：パケットヘッダーを分析し、プロトコルの種類、送信元アドレス、宛先アドレス、送信元ポート、宛先ポート、その他のパケットヘッダーの属性に基づいてポリシーを適用するデバイスまたは機能です。 ポリシーに一致しないパケットは拒否されます。 ログ記録やシステム管理者への通知などの追加の機能も、任意で実行される場合があることに注意してください。
  • IDS（侵入検知システム）：既知のイベントを探して、パケットのヘッダーとペイロードの両方を分析するデバイスまたは機能です。 既知のイベントが検出されると、そのイベントの詳細を記したログメッセージが生成されます。 システム管理者への通知などの追加の機能も、任意で実行される場合があることに注意してください。
  • IPS（侵入防御システム）：既知のイベントを探して、パケットのヘッダーとペイロードの両方を分析するデバイスまたは機能です。 既知のイベントが検出されると、そのパケットは拒否されます。 ログ記録やシステム管理者への通知などの追加の機能も、任意で実行される場合があることに注意してください。

Flow-based NSFs differ in the depth of packet header or payload they can inspect, the various session/context states they can maintain, and the specific profiles and the actions they can apply. An example of a session is as follows: allowing outbound connection requests and only allowing return traffic from the external network.

フローベースNSFは、検査できるパケットヘッダーやペイロードの深さ、維持できるさまざまなセッションやコンテキストの状態、適用できる特定のプロファイルやアクションの点で異なります。 セッションの例は次のとおりです。 外向きのコネクションリクエストを許可し、外部ネットワークからは戻りのトラフィックだけを許可するというものです。

11. Security Considerations

11. セキュリティーに関する考慮事項

The configuration, control, and monitoring of NSFs provide access to and information about security functions that are critical for delivering network security and for protecting end-to-end traffic. Therefore, it is important that the messages that are exchanged within this architecture utilize a trustworthy, robust, and fully secure communication channel. The mechanisms adopted within the solution space must include proper secure communication channels that are carefully specified for carrying the controlling and monitoring information between the NSFs and their management entity or entities. The threats associated with remotely managed NSFs are discussed in Section 4, and solutions must address those concerns.

NSFの設定、制御、および監視は、ネットワークセキュリティーの提供とエンドツーエンドのトラフィックの保護にとって極めて重要なセキュリティー機能へのアクセスと、その機能に関する情報を提供します。 したがって、このアーキテクチャー内で交換されるメッセージには、信頼でき、堅牢で、完全に安全な通信チャネルを利用することが重要です。 ソリューション空間で採用されるメカニズムには、NSFとその管理エンティティー（単数または複数）の間で制御情報と監視情報を運ぶために慎重に規定された、適切で安全な通信チャネルを含めなければなりません。 リモートで管理されるNSFに関連する脅威についてはセクション4で議論しており、ソリューションはそれらの懸念に対処しなければなりません。

This framework is intended for enterprise users, with or without cloud service offerings. Privacy of users must be provided by using existing standard mechanisms, such as encryption; anonymization of data should also be done if possible (depending on the transport used). Such mechanisms require confidentiality and integrity.

このフレームワークは、クラウドサービスの提供の有無にかかわらず、企業のユーザーを対象としています。 ユーザーのプライバシーは、暗号化などの既存の標準的なメカニズムを使用して提供しなければなりません。 可能であれば（使用するトランスポートによりますが）、データの匿名化も行うべきです。 このようなメカニズムには、機密性と完全性が必要です。
