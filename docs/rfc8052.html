RFC 8052

Group Domain of Interpretation (GDOI) Protocol Support for IEC 62351 Security Services

RFC 8052

IEC 62351セキュリティーサービスのためのGroup Domain of Interpretation（GDOI）プロトコルのサポート

Abstract

概要

The IEC 61850 power utility automation family of standards describes methods using Ethernet and IP for distributing control and data frames within and between substations. The IEC 61850-90-5 and IEC 62351-9 standards specify the use of the Group Domain of Interpretation (GDOI) protocol (RFC 6407) to distribute security transforms for some IEC 61850 security protocols. This memo defines GDOI payloads to support those security protocols.

IEC 61850の電力ユーティリティー自動化の標準規格群は、変電所内および変電所間で制御フレームとデータフレームを配布するためにEthernetとIPを使用する方法を記述しています。IEC 61850-90-5とIEC 62351-9の標準規格は、一部のIEC 61850のセキュリティープロトコルのためのセキュリティートランスフォームを配布するのに、Group Domain of Interpretation（GDOI）プロトコル（RFC 6407）を使用することを規定しています。このメモは、それらのセキュリティープロトコルをサポートするためのGDOIペイロードを定義します。

1. Introduction

1. はじめに

Power substations use Generic Object Oriented Substation Events (GOOSE) protocol [IEC-61850-8-1] to distribute control information to groups of devices using a multicast strategy. Sources within the power substations also distribute IEC 61850-9-2 sampled values data streams [IEC-61850-9-2]. The IEC 62351-9 standard [IEC-62351-9] describes key management methods for the security methods protecting these IEC 61850 messages, including methods of device authentication and authorization, and methods of policy and keying material agreement for IEC 61850 message encryption and data integrity protection. These key management methods include the use of GDOI [RFC6407] to distribute the security policy and session keying material used to protect IEC 61850 messages when the messages are sent to a group of devices.

変電所では、マルチキャスト方式を用いてデバイスのグループに制御情報を配布するために、Generic Object Oriented Substation Events（GOOSE）プロトコル[IEC-61850-8-1]を使用します。変電所内の送信元は、IEC 61850-9-2のサンプル値のデータストリーム[IEC-61850-9-2]も配布します。IEC 62351-9標準規格[IEC-62351-9]は、これらのIEC 61850メッセージを保護するセキュリティー方式のための鍵管理の方法を記述しています。これには、デバイスの認証と認可の方法や、IEC 61850メッセージの暗号化とデータ完全性保護のためのポリシーと鍵素材の合意の方法が含まれます。これらの鍵管理の方法には、IEC 61850メッセージがデバイスのグループに送信される場合に、そのメッセージの保護に使用されるセキュリティーポリシーとセッションの鍵素材を配布するための、GDOI[RFC6407]の使用が含まれます。

The protection of the messages is defined in IEC 62351-6 [IEC-62351-6], IEC 61850-8-1 [IEC-61850-8-1], and IEC 61850-9-2 [IEC-61850-9-2]. Protected IEC 61850 messages typically include the output of a Message Authentication Code (MAC) and may also be encrypted using a symmetric cipher such as the Advanced Encryption Standard (AES).

メッセージの保護は、IEC 62351-6[IEC-62351-6]、IEC 61850-8-1[IEC-61850-8-1]、IEC 61850-9-2[IEC-61850-9-2]で定義されています。保護されたIEC 61850メッセージには通常、メッセージ認証コード（MAC）の出力が含まれ、さらにAdvanced Encryption Standard（AES）などの対称暗号を用いて暗号化されることもあります。

Section 5.5.2 of RFC 6407 specifies that the following information needs to be provided in order to fully define a new security protocol:

RFC 6407のセクション5.5.2は、新しいセキュリティープロトコルを完全に定義するために、次の情報を提供する必要があると規定しています。

  • The Protocol-ID for the particular security protocol
  • The SPI Size
  • The method of SPI generation
  • The transforms, attributes, and keys needed by the security protocol
  • その特定のセキュリティープロトコルのProtocol-ID
  • SPIのサイズ
  • SPIの生成方法
  • そのセキュリティープロトコルが必要とするトランスフォーム、属性、鍵

This document defines GDOI payloads to distribute policy and keying material to protect IEC 61850 messages and defines the necessary information to ensure interoperability between IEC 61850 implementations.

この文書は、IEC 61850メッセージを保護するためのポリシーと鍵素材を配布するGDOIペイロードを定義し、IEC 61850の実装間の相互運用性を確保するために必要な情報を定義します。

This memo extends RFC 6407 in order to define extensions needed by IEC 62351-9. With the current IANA registry rules set up by RFC 6407, this requires "Standards Action" [RFC5226] by the IETF; this document satisfies that requirement. As the relevant IEC specifications are not available to the IETF community, it is not possible for this RFC to fully describe the security considerations that apply. Therefore, implementers need to depend on the security analysis within the IEC specifications. As two different Standards Development Organizations are involved here, and since group key management is inherently complex, it is possible that some security issues have not been identified, so additional analysis of the security of the combined set of specifications may be advisable.

このメモは、IEC 62351-9が必要とする拡張を定義するためにRFC 6407を拡張します。RFC 6407によって設定された現在のIANAレジストリーの規則では、これにはIETFによる「Standards Action」[RFC5226]が必要であり、この文書はその要件を満たします。関連するIECの仕様はIETFコミュニティーが入手できないため、このRFCで、適用されるセキュリティー上の考慮事項を完全に記述することはできません。したがって、実装者はIECの仕様の中のセキュリティー分析に頼る必要があります。ここでは2つの異なる標準化団体が関わっており、またグループ鍵管理は本質的に複雑であるため、一部のセキュリティー上の問題が特定されていない可能性があります。そのため、組み合わされた仕様群のセキュリティーについて追加の分析を行うことが望ましいかもしれません。

2. IEC 61850 Protocol Information

2. IEC 61850プロトコル情報

The following subsections describe the GDOI payload extensions that are needed in order to distribute security policy and keying material for the IEC 62351 Security Services. The Identification (ID) Payload is used to describe an IEC 62351 GDOI group. The Security Association (SA) Traffic Encryption Key (TEK) payload is used to describe the policy defined by a Group Controller/Key Server (GCKS) for a particular IEC 62351 traffic selector. No changes are required to the Key Download (KD) Payload, but a mapping of IEC 62351 keys to the KD payload key types is included.

以降のサブセクションでは、IEC 62351セキュリティーサービスのためのセキュリティーポリシーと鍵素材を配布するのに必要なGDOIペイロードの拡張について説明します。識別（Identification、ID）ペイロードは、IEC 62351のGDOIグループを記述するのに使用されます。セキュリティーアソシエーション（SA）トラフィック暗号化鍵（TEK）ペイロードは、特定のIEC 62351のトラフィックセレクターについて、グループコントローラー／鍵サーバー（Group Controller/Key Server、GCKS）が定義したポリシーを記述するのに使用されます。鍵ダウンロード（Key Download、KD）ペイロードには変更は必要ありませんが、IEC 62351の鍵とKDペイロードの鍵タイプとの対応付けを示します。

All multi-octet fields are in network byte order.

複数オクテットのフィールドはすべてネットワークバイトオーダーです。

2.1. ID Payload

2.1. IDペイロード

The ID payload in a GDOI GROUPKEY-PULL exchange allows the Group Member (GM) to declare the group it would like to join. A group is defined by an ID payload as defined in GDOI [RFC6407] and reproduced in Figure 1.

GDOIのGROUPKEY-PULL交換におけるIDペイロードによって、グループメンバー（GM）は参加したいグループを宣言できます。グループは、GDOI[RFC6407]で定義され、図1に再掲するIDペイロードによって定義されます。

An ID Type name of ID_OID (value 13) is defined in this memo to specify an Object Identifier (OID) [ITU-T-X.683] encoded using Distinguished Encoding Rules (DER) [ITU-T-X.690]. Associated with the OID may be an OID-Specific Payload DER encoded as further defining the group. Several OIDs are specified in [IEC-62351-9] for use with IEC 61850. Each OID represents a GOOSE or Sampled Value protocol, and in some cases IEC 61850 also specifies a particular multicast destination address to be described in the OID-Specific Payload field. The format of the ID_OID Identification Data is specified as shown in Figure 2.

このメモでは、識別符号化規則（Distinguished Encoding Rules、DER）[ITU-T-X.690]を用いてエンコードされたオブジェクト識別子（Object Identifier、OID）[ITU-T-X.683]を指定するために、ID_OID（値13）というID Type名を定義します。OIDには、グループをさらに定義するものとして、DERでエンコードされたOID-Specific Payloadが関連付けられることがあります。[IEC-62351-9]には、IEC 61850で使用するためのOIDがいくつか規定されています。各OIDはGOOSEプロトコルまたはSampled Valueプロトコルを表し、場合によっては、IEC 61850はOID-Specific Payloadフィールドに記述する特定のマルチキャスト宛先アドレスも規定します。ID_OIDのIdentification Dataの形式は、図2に示すとおりに規定されます。

The ID_OID Identification Data fields are defined as follows:

ID_OIDのIdentification Dataのフィールドは、次のように定義されます。

  • OID Length (1 octet) -- Length of the OID field.
  • OID (variable) -- An ASN.1 ObjectIdentifier encoded using DER [ITU-T-X.690].
  • OID-Specific Payload Length (2 octets) -- Length of the OID-Specific payload. Set to zero if the OID does not require an OID-Specific payload.
  • OID-Specific Payload (variable) -- OID-specific selector encoded in DER. If OID-Specific Payload Length is set to zero, this field does not appear in the ID payload.
  • OID Length（1オクテット） -- OIDフィールドの長さ。
  • OID（可変長） -- DER[ITU-T-X.690]を用いてエンコードされたASN.1のObjectIdentifier。
  • OID-Specific Payload Length（2オクテット） -- OID-Specificペイロードの長さ。OIDがOID-Specificペイロードを必要としない場合は0に設定されます。
  • OID-Specific Payload（可変長） -- DERでエンコードされた、OID固有のセレクター。OID-Specific Payload Lengthが0に設定されている場合、このフィールドはIDペイロードに現れません。

2.2. SA TEK Payload

2.2. SA TEKペイロード

The SA TEK payload contains security attributes for a single set of policy associated with a group TEK. The type of policy to be used with the TEK is described by a Protocol-ID field included in the SA TEK. As shown in Figure 3 reproduced from RFC 6407, each Protocol-ID describes a particular TEK Protocol-Specific Payload definition.

SA TEKペイロードには、グループのTEKに関連付けられた1組のポリシーのためのセキュリティー属性が含まれます。TEKとともに使用されるポリシーの種類は、SA TEKに含まれるProtocol-IDフィールドによって記述されます。RFC 6407から再掲した図3に示すように、各Protocol-IDは特定のTEK Protocol-Specific Payloadの定義を表します。

The Protocol-ID name of GDOI_PROTO_IEC_61850 (value 3) is defined in this memo for the purposes of distributing IEC 61850 policy. A GDOI_PROTO_IEC_61850 SA TEK includes an OID and (optionally) an OID-Specific payload that together define the selectors for the network traffic. The selector fields are followed by security policy fields indicating how the specified traffic is to be protected. The GDOI_PROTO_IEC_61850 TEK Protocol-Specific Payload is defined as shown in Figure 4.

このメモでは、IEC 61850のポリシーを配布する目的で、GDOI_PROTO_IEC_61850（値3）というProtocol-ID名を定義します。GDOI_PROTO_IEC_61850のSA TEKには、OIDと（省略可能な）OID-Specificペイロードが含まれ、これらが合わさってネットワークトラフィックのセレクターを定義します。セレクターのフィールドの後には、指定されたトラフィックをどのように保護するかを示すセキュリティーポリシーのフィールドが続きます。GDOI_PROTO_IEC_61850のTEK Protocol-Specific Payloadは、図4に示すとおりに定義されます。

The GDOI_PROTO_IEC_61850 SA TEK payload fields are defined as follows:

GDOI_PROTO_IEC_61850のSA TEKペイロードのフィールドは、次のように定義されます。

  • OID Length (1 octet) -- Length of the OID field.
  • OID (variable) -- An ASN.1 ObjectIdentifier encoded using DER. OIDs defined in IEC 61850 declare the type of IEC 61850 message to be protected, as defined by [IEC-62351-9].
  • OID-Specific Payload Length (2 octets) -- Length of the OID-Specific payload. This field is set to zero if the policy does not include an OID-Specific payload.
  • OID-Specific Payload (variable) -- The traffic selector (e.g., multicast address) specific to the OID encoded using DER. Some OID policy settings do not require the use of an OID-Specific payload, in which case this field is not included in the TEK and the OID-Specific Payload Length is set to zero.
  • SPI (4 octets) -- Identifier for the Current Key. This field represents an SPI.
  • Auth Alg (2 octets) -- Authentication Algorithm ID. Valid values are defined in Section 2.2.2.
  • Enc Alg (2 octets) -- Confidentiality Algorithm ID. Valid values are defined in Section 2.2.3.
  • Remaining Lifetime value (4 octets) -- The number of seconds remaining before this TEK expires. A value of zero (0) shall indicate that the TEK does not have an expire time.
  • SA Data Attributes (variable length) -- Contains zero or more attributes associated with this SA. Section 2.2.4 defines attributes.
  • OID Length（1オクテット） -- OIDフィールドの長さ。
  • OID（可変長） -- DERを用いてエンコードされたASN.1のObjectIdentifier。IEC 61850で定義されたOIDは、[IEC-62351-9]で定義されているように、保護されるIEC 61850メッセージの種類を宣言します。
  • OID-Specific Payload Length（2オクテット） -- OID-Specificペイロードの長さ。ポリシーにOID-Specificペイロードが含まれない場合、このフィールドは0に設定されます。
  • OID-Specific Payload（可変長） -- DERを用いてエンコードされた、OIDに固有のトラフィックセレクター（たとえば、マルチキャストアドレス）。OIDのポリシー設定によってはOID-Specificペイロードの使用を必要としないものがあり、その場合、このフィールドはTEKに含まれず、OID-Specific Payload Lengthは0に設定されます。
  • SPI（4オクテット） -- 現在の鍵（Current Key）の識別子。このフィールドはSPIを表します。
  • Auth Alg（2オクテット） -- 認証アルゴリズムのID。有効な値はセクション2.2.2で定義されています。
  • Enc Alg（2オクテット） -- 機密性アルゴリズムのID。有効な値はセクション2.2.3で定義されています。
  • Remaining Lifetime value（4オクテット） -- このTEKが期限切れになるまでの残りの秒数。値0（ゼロ）は、そのTEKに有効期限がないことを示すものとします。
  • SA Data Attributes（可変長） -- このSAに関連付けられた0個以上の属性を含みます。属性はセクション2.2.4で定義します。

2.2.1. Selectors

2.2.1. セレクター

The OID and (optionally) an OID-Specific payload together define the selectors for the network traffic. While they may match the OID and OID-Specific payload that the GM had previously requested in the ID payload, there is no guarantee that this will be the case. Including selectors in the SA TEK is important for at least the following reasons:

OIDと（省略可能な）OID-Specificペイロードが合わさって、ネットワークトラフィックのセレクターを定義します。これらは、GMが以前にIDペイロードで要求したOIDとOID-Specificペイロードと一致することもありますが、そうなるという保証はありません。SA TEKにセレクターを含めることは、少なくとも次の理由で重要です。

  • The Key Server (KS) policy may direct the KS to return multiple TEKs, each representing different traffic selectors, and it is important that every GM receiving the set of TEKs explicitly identify the traffic selectors associated with the TEK.
  • The KS policy may include the use of a GDOI GROUPKEY-PUSH message, which distributes new or replacement TEKs to group members. Since the GROUPKEY-PUSH message does not contain an ID payload, the TEK definition must include the traffic selectors.
  • 鍵サーバー（Key Server、KS）のポリシーにより、KSがそれぞれ異なるトラフィックセレクターを表す複数のTEKを返すよう指示される場合があります。その場合、TEKの集合を受信するすべてのGMが、TEKに関連付けられたトラフィックセレクターを明示的に識別することが重要です。
  • KSのポリシーには、新しいTEKや置き換えのTEKをグループメンバーに配布するGDOIのGROUPKEY-PUSHメッセージの使用が含まれる場合があります。GROUPKEY-PUSHメッセージにはIDペイロードが含まれないため、TEKの定義にはトラフィックセレクターが含まれていなければなりません。

2.2.4.1. SA Time Activation Delay (SA_ATD)
2.2.4.1. SA有効化遅延時間（SA Time Activation Delay、SA_ATD）

A GCKS will sometimes distribute an SA TEK in advance of when it is expected to be used. This is communicated to group members using the SA Activation Time Delay (SA_ATD) attribute. When a GM receives an SA_TEK with this attribute, it waits for the number of seconds contained within the attribute before installing it for either transmitting or receiving.

If both attributes are included in a GROUPKEY-PUSH payload, the value contained in SA_ATD will be used.

このActivation Time Delay属性はこのSAにのみ適用され、GROUPKEY-PULL交換とGROUPKEY-PUSH交換のどちらで使用してもよいです（MAY）。RFC 6407では、Group Associated Policy（GAP）ペイロードのためのACTIVATION_TIME_DELAY属性も記述されています。この属性はすべてのセキュリティーアソシエーションに適用され、GROUPKEY-PUSHメッセージでの使用に限定されています。GROUPKEY-PUSHペイロードに両方の属性が含まれている場合は、SA_ATDに含まれる値が使用されます。

2.2.4.2. Key Delivery Assurance (SA_KDA)

Group policy can include notifying a multicast source ("Publisher") of an indication of whether multicast receivers ("Subscribers") have previously received the SA TEK. This notification allows a Publisher to set a policy as to whether to activate the new SA TEK or not based on the percentage of Subscribers that are able to receive packets protected by the SA TEK. The attribute value is a number between 0 and 100 (inclusive).

グループポリシーには、マルチキャスト受信者（「サブスクライバー（Subscriber）」）がSA TEKを受信済みかどうかの通知を、マルチキャスト送信元（「パブリッシャー（Publisher）」）に送ることを含められます。この通知によって、パブリッシャーは、SA TEKで保護されたパケットを受信できるサブスクライバーの割合に基づいて、新しいSA TEKを有効化するかどうかについてのポリシーを設定できます。属性値は0以上100以下の数値です。

2.2.5. SPI Discussion

2.2.5. SPIに関する議論

As noted in Section 1, RFC 6407 requires that characteristics of an SPI must be defined. An SPI in a GDOI_PROTO_IEC_61850 SA TEK is represented as a Key Identifier (KeyID). The SPI size is 4 octets. The SPI is unilaterally chosen by the GCKS using any method chosen by the implementation. However, an implementation needs to take care not to duplicate an SPI value that is currently in use for a particular group.

セクション1で述べたように、RFC 6407は、SPIの特性を定義しなければならないことを要求しています。GDOI_PROTO_IEC_61850のSA TEKにおけるSPIは、鍵識別子（Key Identifier、KeyID）として表されます。SPIのサイズは4オクテットです。SPIは、実装が選んだ任意の方法を用いて、GCKSが一方的に選択します。ただし、実装は、特定のグループで現在使用中のSPI値と重複しないように注意する必要があります。

3. Security Considerations

3. セキュリティーに関する考慮事項

GDOI is a Security Association (SA) management protocol for groups of senders and receivers. This protocol performs authentication of communicating protocol participants (Group Member, Group Controller/Key Server). GDOI provides confidentiality of key management messages, and it provides source authentication of those messages. GDOI includes defenses against man-in-middle, connection-hijacking, replay, reflection, and denial-of-service (DOS) attacks on unsecured networks. GDOI assumes that the network is not secure and may be under the complete control of an attacker. The Security Considerations described in RFC 6407 are relevant to the distribution of GOOSE and sampled values policy as defined in this memo.

GDOIは、送信者と受信者のグループのためのセキュリティーアソシエーション（SA）管理プロトコルです。このプロトコルは、通信するプロトコル参加者（グループメンバー、グループコントローラー／鍵サーバー）の認証を行います。GDOIは、鍵管理メッセージの機密性を提供し、それらのメッセージの発信元認証を提供します。GDOIには、保護されていないネットワーク上での中間者攻撃、コネクションハイジャック攻撃、リプレイ攻撃、リフレクション攻撃、サービス拒否（DOS）攻撃に対する防御が含まれています。GDOIは、ネットワークが安全ではなく、攻撃者の完全な制御下にある可能性があることを前提としています。RFC 6407に記述されているセキュリティーに関する考慮事項は、このメモで定義するGOOSEとサンプル値のポリシーの配布に関係します。

Message Authentication is an optional property for IEC 62351 Security Services; however, when encryption is used, authentication MUST also be provided by using an authenticated encryption algorithm such as AES-GCM-128 or by using a specific authentication algorithm such as HMAC-SHA-256. Setting the authentication algorithm to NONE but setting the confidentiality algorithm to an algorithm that does not include authentication (i.e., is marked with an N in the "Authenticated Encryption" column of the "IEC 62351-9 Confidentiality Values" registry) is not safe and MUST NOT be done.

メッセージ認証は、IEC 62351セキュリティーサービスにとって省略可能な特性です。ただし、暗号化を使用する場合は、AES-GCM-128などの認証付き暗号アルゴリズムを使用するか、HMAC-SHA-256などの特定の認証アルゴリズムを使用することによって、認証も提供しなければなりません（MUST）。認証アルゴリズムをNONEに設定し、かつ機密性アルゴリズムを認証を含まないアルゴリズム（すなわち、「IEC 62351-9 Confidentiality Values」レジストリーの「Authenticated Encryption」列にNが記されているもの）に設定することは安全ではなく、行ってはなりません（MUST NOT）。

When Message Authentication is used, a common practice is to truncate the output of a MAC and include some of the bits in the integrity protection field of the data security transform. Current guidance in [RFC2104] is to truncate no less than half of the length of the hash output. The authentication algorithm HMAC-SHA256-128 defined in this memo truncates the output to exactly half of the output, which follows this guidance.

メッセージ認証を使用する場合、MACの出力を切り詰め、そのビットの一部をデータセキュリティートランスフォームの完全性保護フィールドに含めるのが一般的な慣行です。[RFC2104]の現在のガイダンスでは、ハッシュ出力の長さの半分以上を残して切り詰めることになっています。このメモで定義する認証アルゴリズムHMAC-SHA256-128は、出力をちょうど半分に切り詰めるので、このガイダンスに従っています。

Confidentiality is an optional security property for IEC 62351 Security Services. Confidentiality Algorithm IDs SHOULD be included in the IEC 61850 SA TEK payload if the IEC 61850 messages are expected to traverse public network links and are not protected by another level of encryption (e.g., an encrypted Virtual Private Network). Current cryptographic advice indicates that the use of AES-CBC-128 for confidentiality is sufficient for the foreseeable future [SP.800-131A], but some security policies may require the use of AES-CBC-256.

機密性は、IEC 62351セキュリティーサービスにとって省略可能なセキュリティー特性です。IEC 61850メッセージが公衆ネットワークのリンクを通過すると予想され、かつ別のレベルの暗号化（たとえば、暗号化された仮想プライベートネットワーク）で保護されていない場合は、IEC 61850のSA TEKペイロードに機密性アルゴリズムのIDを含めるべきです（SHOULD）。現在の暗号に関する助言では、機密性のためにAES-CBC-128を使用すれば当面の間は十分であるとされています[SP.800-131A]が、セキュリティーポリシーによってはAES-CBC-256の使用を要求する場合があります。

IEC 62351 Security Services describe a variety of policy choices for protecting network traffic, including the option of specifying no protection at all. This is enabled with the use of NONE as an authentication algorithm and/or confidentiality algorithm. The following guidance is given regarding the use of NONE.

IEC 62351セキュリティーサービスは、ネットワークトラフィックを保護するためのさまざまなポリシーの選択肢を記述しており、その中には保護をまったく指定しないという選択肢も含まれています。これは、認証アルゴリズムと機密性アルゴリズムのどちらか一方または両方としてNONEを使用することで可能になります。NONEの使用に関して、次のガイダンスを示します。

  • Setting both the authentication algorithm and confidentiality algorithm to NONE is possible but NOT RECOMMENDED. Setting such a policy is sometimes necessary during a migration period, when traffic is being protected incrementally and some traffic has not yet been scheduled for protection. Alternatively, site security policy for some packet flows requires inspection of packet data on the private network followed by network-layer encryption before delivery to a public network.
  • Setting the confidentiality algorithm to NONE but setting the authentication algorithm to a MAC can be an acceptable policy in the following conditions: the disclosed information in the data packets is comprised of raw data values and the disclosure of the data files is believed to be of no more value to an observer than traffic analysis on the frequency and size of packets protected for confidentiality. Alternatively, site security policy for some packet flows requires inspection of packet data on the private network followed by network-layer encryption before delivery to a public network.
  • Setting the authentication algorithm to NONE but setting the confidentiality algorithm to an algorithm that does not include authentication is not safe and MUST NOT be done.
  • 認証アルゴリズムと機密性アルゴリズムの両方をNONEに設定することは可能ですが、推奨されません（NOT RECOMMENDED）。このようなポリシーの設定は、トラフィックが段階的に保護されつつあり、一部のトラフィックがまだ保護の予定に組み込まれていない移行期間中に必要になることがあります。あるいは、一部のパケットフローに対するサイトのセキュリティーポリシーが、プライベートネットワーク上でパケットデータを検査し、その後、公衆ネットワークに配信する前にネットワーク層で暗号化することを要求する場合もあります。
  • 機密性アルゴリズムをNONEに設定し、かつ認証アルゴリズムをMACに設定することは、次の条件では許容できるポリシーとなりえます。それは、データパケット内で開示される情報が生のデータ値で構成されており、そのデータファイルの開示が、観測者にとって、機密性のために保護されたパケットの頻度とサイズに基づくトラフィック分析以上の価値を持たないと考えられる場合です。あるいは、一部のパケットフローに対するサイトのセキュリティーポリシーが、プライベートネットワーク上でパケットデータを検査し、その後、公衆ネットワークに配信する前にネットワーク層で暗号化することを要求する場合もあります。
  • 認証アルゴリズムをNONEに設定し、かつ機密性アルゴリズムを認証を含まないアルゴリズムに設定することは安全ではなく、行ってはなりません（MUST NOT）。

Appendix A. Example ID, SA TEK, and KD Payloads for IEC 61850

付録A. IEC 61850のためのID、SA TEK、KDペイロードの例

An Intelligent Electronic Device (IED) begins a GROUPKEY-PULL exchange and requests keys and security policy for 61850_UDP_ADDR_GOOSE (OID = 1.2.840.10070.61850.8.1.2 as defined in [IEC-61850-9-2]) and IP multicast address 233.252.0.1 encoded as specified in [IEC-61850-9-2].

インテリジェント電子装置（Intelligent Electronic Device、IED）は、GROUPKEY-PULL交換を開始し、61850_UDP_ADDR_GOOSE（[IEC-61850-9-2]で定義されているOID = 1.2.840.10070.61850.8.1.2）と、[IEC-61850-9-2]の規定どおりにエンコードされたIPマルチキャストアドレス233.252.0.1のための鍵とセキュリティーポリシーを要求します。

OID and OID-Specific Payload protocol fields are variable-length fields. To improve readability, their representations in Figures 7 and 8 are "compressed", as indicated by a trailing "~" for these fields. Implementations should be aware that because these fields are variably sized, some payload fields may not be conveniently aligned on an even octet.

OIDとOID-Specific Payloadのプロトコルフィールドは可変長のフィールドです。読みやすくするため、図7と図8では、これらのフィールドの表現は「圧縮」されており、そのことをフィールドの末尾の「~」で示しています。これらのフィールドは可変サイズであるため、一部のペイロードフィールドは都合よく偶数オクテットの境界にそろわない場合があることに、実装は注意すべきです。

Note: The actual DER for the OID-Specific Payload field is defined in [IEC-62351-6].

注: OID-Specific PayloadフィールドのDERの実際の内容は、[IEC-62351-6]で定義されています。

The Key Server responds with the following SA TEK payload including two GDOI_PROTO_IEC_61850 Protocol-Specific TEK payloads in the second GROUPKEY-PULL message. The first one is to be activated immediately and has a lifetime of 3600 seconds (0x0E10) remaining. The second has a lifetime of 12 hours (0xA8C0) and should be activated in 3300 seconds (0x0CE4), which gives a 5-minute (300-second) overlap of the two SAs.

鍵サーバーは、2番目のGROUPKEY-PULLメッセージで、2つのGDOI_PROTO_IEC_61850 Protocol-Specific TEKペイロードを含む次のSA TEKペイロードで応答します。1つ目はただちに有効化されるもので、残りの有効期間は3600秒（0x0E10）です。2つ目は有効期間が12時間（0xA8C0）で、3300秒（0x0CE4）後に有効化されるべきものです。これにより、2つのSAは5分間（300秒間）重複します。

The IED acknowledges that it is capable and willing to use this policy in the third GROUPKEY-PULL message. In response, the KS sends a KD payload to the requesting IED. This concludes the GROUPKEY-PULL exchange.

IEDは、3番目のGROUPKEY-PULLメッセージで、このポリシーを使用する能力と意思があることを確認応答します。これに応じて、KSは要求元のIEDにKDペイロードを送信します。これでGROUPKEY-PULL交換は終了します。

Appendix B. Implementation Considerations

付録B. 実装上の考慮事項

Several topics have been suggested as useful for implementers.

実装者にとって有用なものとして、いくつかの話題が提案されています。

B.1. DER Length Fields

B.1. DERの長さフィールド

The ID and SA TEK payloads defined in this memo include explicit lengths for fields formatted as DER. This includes the OID Length and OID-Specific Payload Length fields shown in Figures 2 and 4. Strictly speaking, these lengths are redundant since the length of the DER value is also encoded within the DER fields. It would be possible to determine the lengths of the fields from those encoded values. However, many implementations will find the explicit length fields convenient when constructing and sanity checking the GDOI messages including these payloads. Implementations will thus be spared from manipulating the DER itself when performing activities that do not otherwise require parsing in order to obtain values therein.

このメモで定義するIDペイロードとSA TEKペイロードには、DERとして形式化されたフィールドの明示的な長さが含まれます。これには、図2と図4に示すOID LengthフィールドとOID-Specific Payload Lengthフィールドが含まれます。厳密に言えば、DERの値の長さはDERのフィールド内にもエンコードされているので、これらの長さは冗長です。フィールドの長さを、それらのエンコードされた値から判断することも可能でしょう。しかし、多くの実装では、これらのペイロードを含むGDOIメッセージを構築したり妥当性チェックしたりする際に、明示的な長さフィールドが便利だと感じるでしょう。そのため、実装は、ほかの点では中の値を得るための解析を必要としない処理を行う際に、DERそのものを操作せずに済みます。

B.2. Groups with Multiple Senders

B.2. 複数の送信者を持つグループ

GCKS policy may specify more than one protected type of IEC 61850 message within a GDOI group. This is represented within a GDOI SA Payload by the presence of an SA TEK payload for each multicast group that is protected as part of group policy. The OID contained in each of the SA TEK payloads may be identical, but the value of each OID-Specific Payload would be unique. Typically, the OID-Specific payload defines a destination address, and there is typically a single sender to that destination address.

GCKSのポリシーは、1つのGDOIグループ内で、保護されるIEC 61850メッセージの種類を複数指定することがあります。これは、GDOIのSAペイロード内で、グループポリシーの一部として保護されるマルチキャストグループごとにSA TEKペイロードが存在することによって表されます。各SA TEKペイロードに含まれるOIDは同一であってもかまいませんが、各OID-Specific Payloadの値は一意になります。通常、OID-Specificペイロードは宛先アドレスを定義し、その宛先アドレスへの送信者は通常1つだけです。

Appendix C. Data Attribute Format

付録C. データ属性の形式

Data attributes attached to an SA TEK following the data attribute format are described in this section. Data attributes can be in Type/Value (TV) format (useful when a value is defined to be less than two octets in size) or in Type/Length/Value (TLV) form.

このセクションでは、SA TEKに付加される、データ属性の形式に従ったデータ属性について説明します。データ属性は、Type/Value（TV）形式（値のサイズが2オクテット未満と定義される場合に便利です）またはType/Length/Value（TLV）形式のいずれかです。

The Data Attributes fields are defined as follows:

データ属性のフィールドは、次のように定義されます。

  • Attribute Type (2 octets) -- Unique identifier for each type of attribute. These attributes are defined as part of the DOI-specific information. The most significant bit, or Attribute Format (AF), indicates whether the data attributes follow the Type/Length/Value (TLV) format or a shortened Type/Value (TV) format. If the AF bit is a zero (0), then the data attributes are of the Type/Length/Value (TLV) form. If the AF bit is a one (1), then the data attributes are of the Type/Value form.
  • Attribute Length (2 octets) -- Length in octets of the Attribute Value. When the AF bit is a one (1), the Attribute Value is only 2 octets, and the Attribute Length field is not present.
  • Attribute Value (variable length) -- Value of the attribute associated with the DOI-specific Attribute Type. If the AF bit is a zero (0), this field has a variable length defined by the Attribute Length field. If the AF bit is a one (1), the Attribute Value has a length of 2 octets.
  • Attribute Type（2オクテット） -- 属性の種類ごとの一意な識別子。これらの属性は、DOI固有の情報の一部として定義されます。最上位ビット、すなわち属性形式（Attribute Format、AF）は、データ属性がType/Length/Value（TLV）形式と短縮されたType/Value（TV）形式のどちらに従うかを示します。AFビットが0（ゼロ）の場合、データ属性はType/Length/Value（TLV）形式です。AFビットが1の場合、データ属性はType/Value形式です。
  • Attribute Length（2オクテット） -- Attribute Valueのオクテット単位の長さ。AFビットが1の場合、Attribute Valueは2オクテットだけであり、Attribute Lengthフィールドは存在しません。
  • Attribute Value（可変長） -- DOI固有のAttribute Typeに関連付けられた属性の値。AFビットが0（ゼロ）の場合、このフィールドはAttribute Lengthフィールドで定義される可変長を持ちます。AFビットが1の場合、Attribute Valueの長さは2オクテットです。
