RFC 903

A Reverse Address Resolution Protocol

RFC 903

逆アドレス解決プロトコル

Status of This Memo

このメモのステータス

This RFC suggests a method for workstations to dynamically find their protocol address (e.g., their Internet Address), when they know only their hardware address (e.g., their attached physical network address).

このRFCは、ワークステーションがハードウェアアドレス（たとえば、接続している物理ネットワークのアドレス）しか知らないときに、自分のプロトコルアドレス（たとえば、インターネットアドレス）を動的に見つける方法を提案します。

This RFC specifies a proposed protocol for the ARPA Internet community, and requests discussion and suggestions for improvements.

このRFCは、ARPAインターネットコミュニティーのためのプロトコルを提案し、改善のための議論と提案を求めるものです。

I. Introduction

I. はじめに

Network hosts such as diskless workstations frequently do not know their protocol addresses when booted; they often know only their hardware interface addresses. To communicate using higher-level protocols like IP, they must discover their protocol address from some external source. Our problem is that there is no standard mechanism for doing so.

ディスクレスワークステーションのようなネットワークホストは、起動時に自分のプロトコルアドレスを知らないことがよくあります。知っているのはハードウェアインターフェイスのアドレスだけということが多いのです。IPのような上位層のプロトコルを使って通信するには、何らかの外部の情報源から自分のプロトコルアドレスを見つけ出さなければなりません。問題は、そのための標準的な仕組みがないことです。

Plummer's "Address Resolution Protocol" (ARP) [1] is designed to solve a complementary problem, resolving a host's hardware address given its protocol address. This RFC proposes a "Reverse Address Resolution Protocol" (RARP). As with ARP, we assume a broadcast medium, such as Ethernet.

Plummerの「アドレス解決プロトコル（Address Resolution Protocol、ARP）」[1]は、これと相補的な問題、つまりホストのプロトコルアドレスからそのハードウェアアドレスを解決する問題を解くために設計されています。このRFCは「逆アドレス解決プロトコル（Reverse Address Resolution Protocol、RARP）」を提案します。ARPと同じく、イーサネットのようなブロードキャスト媒体を前提とします。

II. Design Considerations

II. 設計上の考慮事項

The following considerations guided our design of the RARP protocol.

RARPプロトコルの設計にあたっては、次の考慮事項を指針としました。

  1. ARP and RARP are different operations. ARP assumes that every host knows the mapping between its own hardware address and protocol address(es). Information gathered about other hosts is accumulated in a small cache. All hosts are equal in status; there is no distinction between clients and servers.

    On the other hand, RARP requires one or more server hosts to maintain a database of mappings from hardware address to protocol address and respond to requests from client hosts.

  2. As mentioned, RARP requires that server hosts maintain large databases. It is undesirable and in some cases impossible to maintain such a database in the kernel of a host's operating system. Thus, most implementations will require some form of interaction with a program outside the kernel.
  3. Ease of implementation and minimal impact on existing host software are important. It would be a mistake to design a protocol that required modifications to every host's software, whether or not it intended to participate.
  4. It is desirable to allow for the possibility of sharing code with existing software, to minimize overhead and development costs.

  1. ARPとRARPは異なる操作です。ARPは、すべてのホストが自分自身のハードウェアアドレスとプロトコルアドレス（複数の場合もあります）の対応付けを知っていることを前提とします。他のホストについて集めた情報は、小さなキャッシュに蓄積します。すべてのホストは対等であり、クライアントとサーバーの区別はありません。

    一方、RARPでは、1台以上のサーバーホストが、ハードウェアアドレスからプロトコルアドレスへの対応付けのデータベースを保持し、クライアントホストからの要求に応答する必要があります。

  2. 前述のとおり、RARPではサーバーホストが大きなデータベースを保持する必要があります。そのようなデータベースをホストのオペレーティングシステムのカーネル内に保持することは望ましくなく、場合によっては不可能です。したがって、ほとんどの実装では、カーネル外のプログラムと何らかの形でやり取りする必要があるでしょう。
  3. 実装の容易さと、既存のホストソフトウェアへの影響を最小限にすることが重要です。参加するつもりがあるかどうかにかかわらず、すべてのホストのソフトウェアに変更を要求するようなプロトコルを設計するのは誤りでしょう。
  4. オーバーヘッドと開発コストを最小限にするために、既存のソフトウェアとコードを共有できる可能性を残しておくことが望ましいです。

III. The Proposed Protocol

III. 提案するプロトコル

We propose that RARP be specified as a separate protocol at the data-link level. For example, if the medium used is Ethernet, then RARP packets will have an Ethertype (still to be assigned) different from that of ARP. This recognizes that ARP and RARP are two fundamentally different operations, not supported equally by all hosts. The impact on existing systems is minimized; existing ARP servers will not be confused by RARP packets. It makes RARP a general facility that can be used for mapping hardware addresses to any higher level protocol address.

RARPは、データリンクレベルの独立したプロトコルとして規定することを提案します。たとえば、使用する媒体がイーサネットであれば、RARPパケットはARPとは異なるEthertype（まだ割り当てられていません）を持つことになります。これは、ARPとRARPが根本的に異なる2つの操作であり、すべてのホストが等しくサポートするわけではないことを踏まえたものです。既存のシステムへの影響は最小限に抑えられます。既存のARPサーバーがRARPパケットによって混乱することはありません。また、これによってRARPは、ハードウェアアドレスを任意の上位層プロトコルのアドレスに対応付けるために使える汎用的な機能になります。

This approach provides the simplest implementation for RARP client hosts, but also provides the most difficulties for RARP server hosts. However, these difficulties should not be insurmountable, as is shown in Appendix A, where we sketch two possible implementations for 4.2BSD Unix.

この方式は、RARPクライアントホストにとっては最も単純な実装になりますが、RARPサーバーホストにとっては最も困難が多いものになります。しかし、4.2BSD Unix向けに考えられる2つの実装の概略を示した付録Aからわかるように、これらの困難は克服できるはずです。

RARPは、ARPと同じパケット形式を使います。すなわち、次のとおりです。

ar$hrd, ar$pro, ar$hln and ar$pln are the same as in regular ARP (see [1]).

ar$hrd、ar$pro、ar$hln、ar$plnは、通常のARPと同じです（[1]を参照してください）。

Suppose, for example, that 'hardware' addresses are 48-bit Ethernet addresses, and 'protocol' addresses are 32-bit Internet Addresses. That is, we wish to determine Internet Addresses corresponding to known Ethernet addresses. Then, in each RARP packet, ar$hrd = 1 (Ethernet), ar$pro = 2048 decimal (the Ethertype of IP packets), ar$hln = 6, and ar$pln = 4.

たとえば、「ハードウェア」アドレスが48ビットのイーサネットアドレスで、「プロトコル」アドレスが32ビットのインターネットアドレスだとします。つまり、既知のイーサネットアドレスに対応するインターネットアドレスを求めたいとします。この場合、各RARPパケットでは、ar$hrd = 1（イーサネット）、ar$pro = 10進数で2048（IPパケットのEthertype）、ar$hln = 6、ar$pln = 4となります。

There are two opcodes: 3 ('request reverse') and 4 ('reply reverse'). An opcode of 1 or 2 has the same meaning as in [1]; packets with such opcodes may be passed on to regular ARP code. A packet with any other opcode is undefined. As in ARP, there are no "not found" or "error" packets, since many RARP servers are free to respond to a request. The sender of a RARP request packet should timeout if it does not receive a reply for this request within a reasonable amount of time.

オペコードは3（'request reverse'、逆要求）と4（'reply reverse'、逆応答）の2つです。オペコード1または2は[1]と同じ意味を持ち、そのようなオペコードを持つパケットは通常のARPのコードに渡してもかまいません。それ以外のオペコードを持つパケットは未定義です。ARPと同様に、「見つからない」パケットや「エラー」パケットはありません。多くのRARPサーバーが自由に要求に応答できるからです。RARP要求パケットの送信者は、妥当な時間内にその要求に対する応答を受信しなければ、タイムアウトすべきです。

The ar$sha, ar$spa, $ar$tha, and ar$tpa fields of the RARP packet are interpreted as follows:

RARPパケットのar$sha、ar$spa、$ar$tha、ar$tpaの各フィールドは、次のように解釈します。

When the opcode is 3 ('request reverse'):

オペコードが3（'request reverse'）の場合：

  • ar$sha is the hardware address of the sender of the packet.

  • ar$spa is undefined.

  • ar$tha is the 'target' hardware address.

    • In the case where the sender wishes to determine his own protocol address, this, like ar$sha, will be the hardware address of the sender.

  • ar$tpa is undefined.

  • ar$shaは、パケットの送信者のハードウェアアドレスです。

  • ar$spaは未定義です。

  • ar$thaは、「ターゲット」のハードウェアアドレスです。

    • 送信者が自分自身のプロトコルアドレスを求めたい場合、これはar$shaと同じく、送信者のハードウェアアドレスになります。

  • ar$tpaは未定義です。

When the opcode is 4 ('reply reverse'):

オペコードが4（'reply reverse'）の場合：

  • ar$sha is the hardware address of the responder (the sender of the reply packet).

  • ar$spa is the protocol address of the responder (see the note below).

  • ar$tha is the hardware address of the target, and should be the same as that which was given in the request.

  • ar$tpa is the protocol address of the target, that is, the desired address.

  • ar$shaは、応答者（応答パケットの送信者）のハードウェアアドレスです。

  • ar$spaは、応答者のプロトコルアドレスです（下記の注を参照してください）。

  • ar$thaは、ターゲットのハードウェアアドレスであり、要求で与えられたものと同じであるべきです。

  • ar$tpaは、ターゲットのプロトコルアドレス、つまり求めているアドレスです。

Note that the requirement that ar$spa in opcode 4 packets be filled in with the responder's protocol is purely for convenience. For instance, if a system were to use both ARP and RARP, then the inclusion of the valid protocol-hardware address pair (ar$spa, ar$sha) may eliminate the need for a subsequent ARP request.

オペコード4のパケットのar$spaに応答者のプロトコル（アドレス）を入れるという要件は、純粋に利便性のためのものであることに注意してください。たとえば、あるシステムがARPとRARPの両方を使う場合、有効なプロトコルアドレスとハードウェアアドレスの組（ar$spa、ar$sha）が含まれていれば、その後のARP要求が不要になるかもしれません。

Appendix A. Two Example Implementations for 4.2BSD Unix

付録A. 4.2BSD Unix向けの2つの実装例

The following implementation sketches outline two different approaches to implementing a RARP server under 4.2BSD.

次の実装の概略は、4.2BSDでRARPサーバーを実装するための2つの異なる方式を示すものです。

  1. Provide access to data-link level packets outside the kernel. The RARP server is implemented completely outside the kernel and interacts with the kernel only to receive and send RARP packets. The kernel has to be modified to provide the appropriate access for these packets; currently the 4.2 kernel allows access only to IP packets. One existing mechanism that provides this capability is the CMU "packet-filter" pseudo driver. This has been used successfully at CMU and Stanford to implement similar sorts of "user-level" network servers.

  2. Maintain a cache of database entries inside the kernel. The full RARP server database is maintained outside the kernel by a user process. The RARP server itself is implemented directly in the kernel and employs a small cache of database entries for its responses. This cache could be the same as is used for forward ARP.

    The cache gets filled from the actual RARP database by means of two new ioctls. (These are like SIOCIFADDR, in that they are not really associated with a specific socket.) One means: "sleep until there is a translation to be done, then pass the request out to the user process"; the other means: "enter this translation into the kernel table". Thus, when the kernel can't find an entry in the cache, it puts the request on a (global) queue and then does a wakeup(). The implementation of the first ioctl is to sleep() and then pull the first item off of this queue and return it to the user process. Since the kernel can't wait around at interrupt level until the user process replies, it can either give up (and assume that the requesting host will retransmit the request packet after a second) or if the second ioctl passes a copy of the request back into the kernel, formulate and send a response at that time.

  1. データリンクレベルのパケットへのアクセスをカーネル外に提供する。RARPサーバーは完全にカーネルの外で実装し、カーネルとのやり取りはRARPパケットの受信と送信のためだけに行います。これらのパケットへの適切なアクセスを提供するために、カーネルを変更する必要があります。現在の4.2カーネルでは、IPパケットへのアクセスしか許していません。この機能を提供する既存の仕組みの1つに、CMUの「パケットフィルター」疑似ドライバーがあります。これは、CMUとスタンフォードで、同じような「ユーザーレベル」のネットワークサーバーの実装に使われて成功を収めています。

  2. カーネル内にデータベースのエントリーのキャッシュを保持する。RARPサーバーの完全なデータベースは、ユーザープロセスがカーネルの外で保持します。RARPサーバー自体はカーネル内に直接実装し、応答には小さなデータベースエントリーのキャッシュを使います。このキャッシュは、順方向のARPで使うものと同じでもかまいません。

    キャッシュは、2つの新しいioctlによって実際のRARPデータベースから埋められます（これらはSIOCIFADDRと同様に、特定のソケットには実際には関連付けられていません）。1つは「変換すべきものが現れるまでスリープし、その要求をユーザープロセスに渡す」ことを意味し、もう1つは「この変換をカーネルの表に登録する」ことを意味します。したがって、カーネルはキャッシュ内にエントリーを見つけられなかったとき、要求を（グローバルな）キューに入れてwakeup()を行います。1つ目のioctlの実装は、sleep()してから、このキューの先頭の項目を取り出してユーザープロセスに返すというものです。カーネルは、ユーザープロセスが応答するまで割り込みレベルで待ち続けることはできないので、あきらめる（そして、要求元のホストが1秒後に要求パケットを再送すると想定する）か、2つ目のioctlが要求のコピーをカーネルに戻してきた場合に、その時点で応答を組み立てて送信するかのどちらかを行えます。
