RFC 615

Proposed Network Standard Data Pathname Syntax

RFC 615

ネットワーク標準データパス名の構文の提案

Abstract

概要

There seems to be an increasing call for a Network Standard Data Pathname (NSDP); that is, a standardized means of referring to a specific location for/of a collection of bits somewhere on the Network.

ネットワーク標準データパス名（Network Standard Data Pathname、NSDP）、つまりネットワーク上のどこかにあるビットの集まりのための（あるいはその）特定の場所を参照する標準化された手段を求める声が高まっているようです。

The reasons for a standard or virtual anything have been discussed, at length, elsewhere and will not be elaborated upon here. Rather than attack the entire issue of virtual pathnames, I wish only to propose a standardized SYNTAX for specifying pathnames. Such a standard will be useful for 1) users who are unfamiliar with a site or who use several different sites and do not want to have to remember each site's idiosynchracies, 2) programs accessing data at several other sites, and 3) documentation:

何かを標準化したり仮想化したりする理由は、ほかの場所で詳しく論じられているので、ここでは詳述しません。仮想パス名の問題全体に取り組むのではなく、パス名を指定するための標準化された構文（SYNTAX）だけを提案したいと思います。このような標準は、1) あるサイトに不慣れなユーザーや、複数の異なるサイトを使っていて各サイトの癖を覚えておきたくないユーザー、2) ほかの複数のサイトにあるデータにアクセスするプログラム、3) 文書化、に役立つでしょう。

The syntax allows the user to specify the necessary network, host, peripheral device, directory, file, type, and site-specific fields. Adding other fields, as needed, is expected to be quite simple.

この構文では、ユーザーは必要なネットワーク、ホスト、周辺装置、ディレクトリー、ファイル、タイプ、サイト固有のフィールドを指定できます。必要に応じてほかのフィールドを追加するのも、きわめて簡単だと考えています。

First the BNF:

まずBNFを示します。

   <NSDP> ::= % <bulk> <cr><lf>

   <bulk> ::= <field> / <field> <bulk>

   <field> ::= <key> <L-delim> <name> <R-delim>

   <key> ::= NETWORK / HOST / PERIPHERAL/ DIRECTORY /
             FILE / TYPE / SITEPARM / N / H / P / D / F /
             T / S

   <NSDP> ::= % <bulk> <cr><lf>

   <bulk> ::= <field> / <field> <bulk>

   <field> ::= <key> <L-delim> <name> <R-delim>

   <key> ::= NETWORK / HOST / PERIPHERAL/ DIRECTORY /
             FILE / TYPE / SITEPARM / N / H / P / D / F /
             T / S
<L-delim> ::=
any printable character that is not in the succeeding <name> field and that is acceptable to the object site: For visual aesthetics and to facilitate human parsing, anytime <L-delim> is a left-bracket character (<, [, (, _), <R-delim> must be the complementary right-bracket character (>, ], ), |).
<name> ::=
any sequence of characters acceptable to the object site. This is the actual data field with the file, directory, device (or whatever) name.
<R-delim> ::=
Either 1) the same character as <L-delim> or 2) if the <L-delim> character is a left-bracket character (<, [, (, _) then its complementary right-bracket (>, ], ), |).
<cr> ::=
carriage-return
<lf> ::=
line-feed
<L-delim> ::=
後続の<name>フィールドに含まれず、対象サイトが受け付ける任意の印字可能文字。見た目の美しさと人間が解析しやすいように、<L-delim>が左括弧文字（<、[、(、_）の場合は、<R-delim>はそれと対になる右括弧文字（>、]、)、|）でなければなりません。
<name> ::=
対象サイトが受け付ける任意の文字列。これは、ファイル、ディレクトリー、装置（など）の名前を含む実際のデータフィールドです。
<R-delim> ::=
1) <L-delim>と同じ文字、または2) <L-delim>の文字が左括弧文字（<、[、(、_）の場合は、それと対になる右括弧（>、]、)、|）のいずれかです。
<cr> ::=
復帰（carriage-return）
<lf> ::=
改行（line-feed）

And some elaboration:

いくつか補足します。

The syntax allows <name> fields to be an arbitrary number of rs long. Case is irrelevant to the syntax, though some sites will care about case in <name> fields:

この構文では、<name>フィールドの長さは任意です。構文上は大文字と小文字を区別しませんが、<name>フィールドの大文字と小文字を区別するサイトもあるでしょう。

<Key> indicates what part of the pathname the next <name> is going to refer to: The single-character keys are abbreviations for the respective full-word keys:

<Key>は、次の<name>がパス名のどの部分を参照するかを示します。1文字のキーは、それぞれ対応する完全な語のキーの略記です。

<Fields> ARE order dependent, but defaulted ones may be omitted. The order is as indicated for <key>s: That is, Network, Host, ..: Siteparm:

<Fields>の順序には意味がありますが、デフォルト値を使うフィールドは省略できます。順序は<key>に示したとおり、つまりNetwork、Host、……、Siteparmの順です。

Fields may be repeated, as appropriate for the object site; that is, multiple Directory fields, etc:

対象サイトに応じて、フィールドを繰り返してもかまいません。つまり、Directoryフィールドを複数並べるなどです。

The validity of any combination of <field>s is entirely site-dependent: For example, if a site will accept it, an NSDP with a Host field, and nothing more, is permissible:

<field>のどの組み合わせが有効かは、完全にサイトに依存します。たとえば、サイトが受け付けるのであれば、Hostフィールドだけを持つNSDPも許されます。

<delim> is used to delimit the beginning and end of the <name> field:

<delim>は、<name>フィールドの始まりと終わりを区切るのに使います。

Explanation of <key>s:

<key>の説明：

NETWORK or N:
Currently, only ARPA is defined.
HOST or H:
Reference to host, by official name or nickname or number: The default radix is ten; a numeric string ending with "H" indicates hexadecimal, "O"(oh) indicates octal, and (gratuitously) "D" indicates decimal:
PERIPHERAL or P:
Peripheral device being referred to:
DIRECTORY or D:
Name of a directory which contains a pointer to the entity (directory or filename) specified in the following <field>:
FILE or F:
Basic name of the file or data set:
TYPE or T:
Optional modifier to filename: (Tenex calls it the extension.)
SITEPARM or S:
A parameter, such as an access specification or version number, peculiar to the object site. The content of the <name> field must serve to identify what Siteparm is involved. Each site will be responsible for defining the syntax of Siteparm <name>s it will accept.
NETWORKまたはN：
現在のところ、ARPAだけが定義されています。
HOSTまたはH：
正式名、ニックネーム、または番号によるホストの参照です。デフォルトの基数は10です。数字列の末尾が「H」なら16進数、「O」（オー）なら8進数、そして（念のため）「D」なら10進数を示します。
PERIPHERALまたはP：
参照する周辺装置です。
DIRECTORYまたはD：
後続の<field>で指定する実体（ディレクトリーまたはファイル名）へのポインターを含むディレクトリーの名前です。
FILEまたはF：
ファイルまたはデータセットの基本名です。
TYPEまたはT：
ファイル名に付ける省略可能な修飾子です（Tenexでは拡張子と呼んでいます）。
SITEPARMまたはS：
アクセス指定やバージョン番号など、対象サイトに固有のパラメーターです。<name>フィールドの内容によって、どのSiteparmであるかを識別できなければなりません。各サイトは、自身が受け付けるSiteparmの<name>の構文を定める責任を負います。

Some reserved PERIPHERAL <name>s:

予約済みのPERIPHERALの<name>の例：

DISK or DSK:
Immediately accessible, direct-access storage.
ONLINE or ONL:
Whatever immediately-accessible (measured in fractions of a second) storage the user accesses by default; usually disk:
TAPE or TAP:
Industry-compatible magnetic tape:
TAPE7 or TP7:
7-Track industry compatible tape:
TAPE9 or TP9:
9-Track industry compatible tape:
DECTAPE or DEC:
DEC Tape.
OFFLINE or OFF:
Any tertiary storage; usually tape, though "devices" like the Datacomputer are permissible: The user should expect to wait minutes or hours before being able to access OFFLINE files:
PRINTER or PTR:
Any available line-printer:
DOCPRINTER or DOC:
Upper-lower case line printer, preferably with 8 1/2" X 11" unlined paper.
PAPER or PAP:
Paper tape.
PUNCH or PUN:
Standard 8O-column card punch.
READER or RDR:
Standard 80-column card reader:
OPERATOR or OPR:
System Operator's console.
CONSULTANT or CON:
On-line consultant.
DISKまたはDSK：
すぐにアクセスできる直接アクセス記憶装置です。
ONLINEまたはONL：
ユーザーがデフォルトでアクセスする、すぐに（1秒未満で）アクセスできる任意の記憶装置です。通常はディスクです。
TAPEまたはTAP：
業界互換の磁気テープです。
TAPE7またはTP7：
7トラックの業界互換テープです。
TAPE9またはTP9：
9トラックの業界互換テープです。
DECTAPEまたはDEC：
DECテープです。
OFFLINEまたはOFF：
任意の3次記憶装置です。通常はテープですが、Datacomputerのような「装置」でもかまいません。ユーザーは、OFFLINEのファイルにアクセスできるようになるまで数分から数時間待つことを覚悟すべきです。
PRINTERまたはPTR：
利用可能な任意のラインプリンターです。
DOCPRINTERまたはDOC：
大文字と小文字を印字できるラインプリンターです。8 1/2" X 11"の罫線のない用紙を使えるものが望ましいです。
PAPERまたはPAP：
紙テープです。
PUNCHまたはPUN：
標準的な80桁のカードパンチ（8O-column card punch）です。
READERまたはRDR：
標準的な80桁のカードリーダーです。
OPERATORまたはOPR：
システムオペレーターのコンソールです。
CONSULTANTまたはCON：
オンラインのコンサルタントです。

Defaults:

デフォルト：

Defaults will generally be context dependent. Consequently, the following defaults are offered only as guidelines:

デフォルトは一般に文脈に依存します。そのため、以下のデフォルトは指針として示すにすぎません。

Network:
ARPA
Host:
The host interpreting the NVP
Peripheral:
ONLINE (DISK)
Directory:
The user's current "working" directory, usually set by the logon process:
Filename:
None.
Type:
None.
Siteparm:
None.
Network：
ARPA
Host：
NVPを解釈するホスト
Peripheral：
ONLINE（DISK）
Directory：
ユーザーの現在の「作業」ディレクトリー。通常はログオン処理で設定されます。
Filename：
なし。
Type：
なし。
Siteparm：
なし。

General Comments

全般的なコメント

The only field that must be considered in relation to any host's current syntax is the escape-to-NVP field (The per-cent sign as the first character of a pathname specification): It is not currently known to conflict with any host's syntax:

各ホストの現在の構文との関係を考慮しなければならない唯一のフィールドは、NVPへのエスケープのフィールド（パス名指定の先頭文字としてのパーセント記号）です。現在のところ、これがどのホストの構文とも衝突するという話は知られていません。

Exclamation mark (!) is the only other character that seems permissible (on the assumption that the character should be a graphic): Its use would cause minor problems at Multics; but more importantly as a graphic, it is too similar to the numeral "1":

ほかに使えそうな文字は感嘆符（!）だけです（その文字は図形文字であるべきだという前提に立った場合）。感嘆符を使うとMulticsで多少の問題が生じます。しかしもっと重要なのは、図形文字として数字の「1」に似すぎていることです。

The syntax is intended to be adequate for all hosts, so any given portion of it may be inappropriate for any given host.

この構文はすべてのホストに十分対応できることを意図しているので、どの部分であれ、特定のホストには適さないことがあります。

A site is expected to permit specifications in a given field iff that site already has a way of accepting the same information:

サイトは、同じ情報を受け付ける方法をすでに持っている場合に限り（iff）、そのフィールドでの指定を許すことが期待されます。

I believe that any modifications to the syntax will be graceful additions, rather than wholesale redesign, and thus can be deferred for a while. Currently, any undefined attributes must be specified in a Siteparm field:

構文の変更は、全面的な再設計ではなく、穏当な追加になると考えているので、しばらく先送りできます。現在のところ、定義されていない属性はSiteparmフィールドで指定しなければなりません。

Perhaps Version, Access protection and Accounting, as well as other types of information, should be made standard <key>s, rather than buried as Siteparms. I expect that the next version of the NSDP Syntax specification will include them as <key>s, but I would like to wait for some comments from the community.

Version、Access protection、Accountingなどの種類の情報は、Siteparmに埋もれさせるのではなく、標準の<key>にすべきかもしれません。NSDP構文仕様の次の版ではこれらを<key>として含めるつもりですが、コミュニティーからのコメントを待ちたいと思います。

The syntax does not currently allow addressing any collection of bits smaller than a file: This can be remedied by adding PAGE, BYTE and other <key>s; but, again, I would like to solicit some comments first:

現在の構文では、ファイルより小さいビットの集まりを指定できません。これはPAGE、BYTEなどの<key>を追加すれば解決できますが、ここでもまずコメントを募りたいと思います。

Disclaimer

但し書き

A pathname specified in the proposed syntax is fairly easy to type but is quite ugly to read: So, at the expense of design cleanliness, the <L-delim>/<R-delim> syntax was modified in an attempt to remedy the problem somewhat: As you will see below, it is only partially successful.

提案した構文で指定したパス名は、入力するのはかなり簡単ですが、読むのは非常に見苦しいものです。そこで、設計の簡潔さを犠牲にして、この問題を多少なりとも改善しようと<L-delim>/<R-delim>の構文を変更しました。以下で見るように、これは部分的にしか成功していません。

The first draft of this document had a syntax that was a mix of Tenex and Multics conventions: That is,

この文書の最初の草稿では、TenexとMulticsの慣習を混ぜた構文を使っていました。つまり、次のとおりです。

       (Network)[Host]Peripheral:Directory>Filename:Type;Siteparm

       (Network)[Host]Peripheral:Directory>Filename:Type;Siteparm

Though visually more attractive and generally quicker to type, it lacks extensibility. For example, adding Version number or Access protection as standard fields would be difficult:

こちらのほうが見た目は魅力的で、一般に入力も速いのですが、拡張性に欠けます。たとえば、Version番号やAccess protectionを標準のフィールドとして追加するのは困難でしょう。

It is suggested that human interfaces be built to translate to/from NSDP syntax and the user's standard environment.

NSDP構文とユーザーの標準的な環境とを相互に変換する、人間向けのインターフェイスを作ることを提案します。

Some sample pathnames:

パス名の例をいくつか示します。

%H[ISI]D<DCROCKER>F(MESSAGE)T/TXT/S(P77O4O4)<cr><lf> refers to my protected message file at ISI (<DCROCKER>MESSAGE:TXT;P77O4O4).

%H[ISI]D<DCROCKER>F(MESSAGE)T/TXT/S(P77O4O4)<cr><lf>は、ISIにある私の保護されたメッセージファイル（<DCROCKER>MESSAGE:TXT;P77O4O4）を参照します。

%H/OFFICE-l/D>JOURNAL>F<l8659>T.NLS.<cr><lf> refers to NIC Journal document #18659 (Tenex file <JOURNAL>l8659:NLS):

%H/OFFICE-l/D>JOURNAL>F<l8659>T.NLS.<cr><lf>は、NIC Journalの文書#18659（Tenexのファイル<JOURNAL>l8659:NLS）を参照します。

%H/65/D.ARP061.D.LAD:F.DOCUMENT.<cr><lf> refers to a file ARPO6l:LAD.DOCUMENT at UCLA-CCN. Note the use of multiple Directory fields.

%H/65/D.ARP061.D.LAD:F.DOCUMENT.<cr><lf>は、UCLA-CCNにあるファイルARPO6l:LAD.DOCUMENTを参照します。Directoryフィールドを複数使っていることに注意してください。

%H[540]D//D>udd>D>Comp=net>D>Map>F(Mail)<cr><lf> refers to file CompNet>Map>Mail at Mit-Multics. Note that the initial NSPD Directory <name> field is empty. This conforms to Multics' method of starting at the top of its directory structure:

%H[540]D//D>udd>D>Comp=net>D>Map>F(Mail)<cr><lf>は、Mit-MulticsにあるファイルCompNet>Map>Mailを参照します。NSPDの最初のDirectoryの<name>フィールドが空であることに注意してください。これは、ディレクトリー構造の最上位から始めるMulticsの方式に合わせたものです。
