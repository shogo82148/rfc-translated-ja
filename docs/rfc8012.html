RFC 8012

Label Switched Path (LSP) and Pseudowire (PW) Ping/Trace over MPLS Networks Using Entropy Labels (ELs)

RFC 8012

エントロピーラベル（EL）を使用するMPLSネットワーク上でのラベルスイッチパス（LSP）および疑似回線（PW）のPing/Trace

Abstract

概要

Multiprotocol Label Switching (MPLS) Label Switched Path (LSP) ping and traceroute are methods used to test Equal-Cost Multipath (ECMP) paths. Ping is known as a connectivity-verification method and traceroute is known as a fault-isolation method, as described in RFC 4379. When an LSP is signaled using the Entropy Label (EL) described in RFC 6790, the ability for LSP ping and traceroute operations to discover and exercise ECMP paths is lost for scenarios where Label Switching Routers (LSRs) apply different load-balancing techniques. One such scenario is when some LSRs apply EL-based load balancing while other LSRs apply load balancing that is not EL based (e.g., IP). Another scenario is when an EL-based LSP is stitched with another LSP that can be EL based or not EL based.

マルチプロトコルラベルスイッチング（MPLS）のラベルスイッチパス（LSP）のpingとtracerouteは、等コストマルチパス（ECMP）のパスをテストするために使用される手法です。RFC 4379で説明されているように、pingは接続性検証の手法として、tracerouteは障害切り分けの手法として知られています。RFC 6790で説明されているエントロピーラベル（EL）を使用してLSPがシグナリングされる場合、ラベルスイッチングルーター（LSR）が異なる負荷分散の手法を適用するシナリオでは、LSP pingとtracerouteの操作がECMPのパスを発見してそこにパケットを通す能力が失われます。そのようなシナリオの1つは、一部のLSRがELに基づく負荷分散を適用し、ほかのLSRがELに基づかない負荷分散（たとえばIP）を適用する場合です。もう1つのシナリオは、ELに基づくLSPが、ELに基づくこともELに基づかないこともある別のLSPとスティッチされる場合です。

This document extends the MPLS LSP ping and traceroute multipath mechanisms in RFC 6424 to allow the ability of exercising LSPs that make use of the EL. This document updates RFC 6790.

この文書は、RFC 6424のMPLS LSP pingとtracerouteのマルチパスのメカニズムを拡張し、ELを利用するLSPにパケットを通せるようにします。この文書はRFC 6790を更新します。

1. Introduction

1. はじめに

[RFC4379] describes LSP traceroute as an operation where the initiating LSR sends a series of MPLS echo requests towards the same destination. The first packet in the series has the TTL set to 1. When the echo reply is received from the LSR one hop away, the second echo request in the series is sent with the TTL set to 2. For each additional echo request, the TTL is incremented by one until a response is received from the intended destination. The initiating LSR discovers and exercises ECMP by obtaining Multipath Information from each transit LSR and using a specific destination IP address or specific entropy label.

[RFC4379]は、LSP tracerouteを、イニシエーターLSRが同じ宛先に向けて一連のMPLSエコーリクエストを送信する操作として説明しています。一連のパケットの最初のパケットでは、TTLが1に設定されます。1ホップ先のLSRからエコーリプライを受信すると、一連のエコーリクエストの2番目のものがTTLを2に設定して送信されます。意図した宛先からレスポンスを受信するまで、エコーリクエストを追加するごとにTTLを1ずつ増やします。イニシエーターLSRは、各トランジットLSRからMultipath Informationを取得し、特定の宛先IPアドレスまたは特定のエントロピーラベルを使用することで、ECMPを発見し、そこにパケットを通します。

From here on, the notation {x, y, z} refers to Multipath Information Types x, y, or z. Multipath Information Types are defined in Section 3.3 of [RFC4379] .

以降、{x, y, z}という表記は、Multipath Information Typeのx、y、またはzを指します。Multipath Information Typeは、[RFC4379]のセクション3.3で定義されています。

The LSR initiating LSP ping sends an MPLS echo request with the Multipath Information. This Multipath Information is described in the echo request's DDMAP TLV and may contain a set of IP addresses or a set of labels. Multipath Information Types {2, 4, 8} carry a set of IP addresses, and the Multipath Information Type {9} carries a set of labels. The responder LSR (the receiver of the MPLS echo request) will determine the subset of initiator-specified Multipath Information, which load balances to each downstream (outgoing) interface. The responder LSR sends an MPLS echo reply with the resulting Multipath Information per downstream (outgoing interface) back to the initiating LSR. The initiating LSR is then able to use a specific IP destination address or a specific label to exercise a specific ECMP path on the responder LSR.

LSP pingを開始するLSRは、Multipath Informationを含むMPLSエコーリクエストを送信します。このMultipath InformationはエコーリクエストのDDMAP TLVに記述され、IPアドレスの集合またはラベルの集合を含むことがあります。Multipath Information Type {2, 4, 8}はIPアドレスの集合を運び、Multipath Information Type {9}はラベルの集合を運びます。レスポンダーLSR（MPLSエコーリクエストの受信者）は、イニシエーターが指定したMultipath Informationのうち、各下流（送信）インターフェイスへ負荷分散されるサブセットを決定します。レスポンダーLSRは、下流（送信インターフェイス）ごとに得られたMultipath Informationを含むMPLSエコーリプライをイニシエーターLSRに送り返します。これにより、イニシエーターLSRは、特定のIP宛先アドレスまたは特定のラベルを使用して、レスポンダーLSR上の特定のECMPパスにパケットを通すことができます。

The current behavior is problematic in the following scenarios:

現在の動作は、次のシナリオで問題があります。

  • The initiating LSR sends the IP Multipath Information, but the responder LSR load balances on labels.
  • The initiating LSR sends the Label Multipath Information, but the responder LSR load balances on IP addresses.

  • The initiating LSR sends the existing Multipath Information to an LSR that pushes ELI/EL in the label stack, but the initiating LSR can only continue to discover and exercise specific paths of the ECMP if the LSR that pushes ELI/EL responds with both IP addresses and the associated EL corresponding to each IP address. This is because:

    • An ELI/EL-pushing LSR that is a stitching point will load balance based on the IP address.
    • Downstream LSR(s) of an ELI/EL-pushing LSR may load balance based on ELs.

  • The initiating LSR sends existing Multipath Information to an ELI/EL-pushing LSR, but the initiating LSR can only continue to discover and exercise specific paths of ECMP if the ELI/EL-pushing LSR responds with both labels and the associated EL corresponding to the label. This is because:

    • An ELI/EL-pushing LSR that is a stitching point will load balance based on the EL from the previous LSP and push a new EL.
    • Downstream LSR(s) of ELI/EL-pushing LSR may load balance based on new ELs.
  • イニシエーターLSRはIPのMultipath Informationを送信しますが、レスポンダーLSRはラベルに基づいて負荷分散します。
  • イニシエーターLSRはLabelのMultipath Informationを送信しますが、レスポンダーLSRはIPアドレスに基づいて負荷分散します。

  • イニシエーターLSRは、ラベルスタックにELI/ELをプッシュするLSRに既存のMultipath Informationを送信しますが、イニシエーターLSRがECMPの特定のパスを発見し、そこにパケットを通し続けられるのは、ELI/ELをプッシュするLSRがIPアドレスと各IPアドレスに対応する関連ELの両方を返す場合だけです。これは次の理由によります。

    • スティッチングポイントであるELI/ELをプッシュするLSRは、IPアドレスに基づいて負荷分散します。
    • ELI/ELをプッシュするLSRの下流のLSRは、ELに基づいて負荷分散することがあります。

  • イニシエーターLSRは、ELI/ELをプッシュするLSRに既存のMultipath Informationを送信しますが、イニシエーターLSRがECMPの特定のパスを発見し、そこにパケットを通し続けられるのは、ELI/ELをプッシュするLSRがラベルとそのラベルに対応する関連ELの両方を返す場合だけです。これは次の理由によります。

    • スティッチングポイントであるELI/ELをプッシュするLSRは、前のLSPのELに基づいて負荷分散し、新しいELをプッシュします。
    • ELI/ELをプッシュするLSRの下流のLSRは、新しいELに基づいて負荷分散することがあります。

The above scenarios demonstrate that the existing Multipath Information is insufficient when LSP traceroute is used on an LSP with entropy labels [RFC6790]. This document defines a new Multipath Information Type to be used in the DDMAP of MPLS echo request/reply packets for [RFC6790] LSPs.

上記のシナリオは、エントロピーラベル[RFC6790]を使用するLSP上でLSP tracerouteを使用する場合、既存のMultipath Informationでは不十分であることを示しています。この文書は、[RFC6790]のLSPに対するMPLSエコーリクエスト／リプライパケットのDDMAPで使用する、新しいMultipath Information Typeを定義します。

The responder LSR can reply with empty Multipath Information if no IP address set or if no label set is received with the Multipath Information. An empty return is also possible if an initiating LSR sends Multipath Information of one type, IP Address or Label, but the responder LSR load balances on the other type. To disambiguate between the two results, this document introduces new flags in the DDMAP TLV to allow the responder LSR to describe the load-balancing technique being used.

Multipath InformationとともにIPアドレスの集合もラベルの集合も受信しなかった場合、レスポンダーLSRは空のMultipath Informationを返すことができます。イニシエーターLSRがIPアドレスまたはラベルの一方の種類のMultipath Informationを送信したが、レスポンダーLSRがもう一方の種類に基づいて負荷分散する場合にも、空の結果が返ることがあります。この2つの結果を区別するために、この文書はDDMAP TLVに新しいフラグを導入し、レスポンダーLSRが使用している負荷分散の手法を記述できるようにします。

To use this enhanced method end-to-end, all LSRs along the LSP need to be able to understand the new flags and the new Multipath Information Type. Mechanisms to verify this condition are outside of the scope of this document. The rest of the requirements are detailed in the initiating LSR and responder LSR procedures. Two additional DS Flags are defined for the DDMAP TLV in Section 6. These two flags are used by the responder LSR to describe its load-balancing behavior on a received MPLS echo request.

この拡張された手法をエンドツーエンドで使用するには、LSPに沿ったすべてのLSRが新しいフラグと新しいMultipath Information Typeを理解できる必要があります。この条件を確認するメカニズムは、この文書の範囲外です。残りの要件は、イニシエーターLSRとレスポンダーLSRの手順で詳しく説明します。セクション6で、DDMAP TLVに対して2つのDS Flagsを追加で定義します。この2つのフラグは、受信したMPLSエコーリクエストに対する負荷分散の動作を記述するために、レスポンダーLSRが使用します。

Note that the terms "IP-Based Load Balancer" and "Label-Based Load Balancer" are in context of how a received MPLS echo request is handled by the responder LSR.

「IP-Based Load Balancer」と「Label-Based Load Balancer」という用語は、受信したMPLSエコーリクエストをレスポンダーLSRがどのように扱うかという文脈におけるものであることに注意してください。

1.1. Terminology

1.1. 用語

The following abbreviations and terms are used in this document:

この文書では、次の略語と用語を使用します。

  • MPLS: Multiprotocol Label Switching.
  • LSP: Label Switched Path.
  • Stitched LSP: Stitched Label Switched Paths combine several LSPs such that a single end-to-end LSP is realized. [RFC6424] describes LSP ping for Stitched LSPs.
  • LSR: Label Switching Router.
  • FEC: Forwarding Equivalence Class.
  • ECMP: Equal-Cost Multipath.
  • EL: Entropy Label.
  • ELI: Entropy Label Indicator.
  • GAL: Generic Associated Channel Label.
  • MS-PW: Multi-Segment Pseudowire.
  • Initiating LSR: An LSR that sends an MPLS echo request.
  • Responder LSR: An LSR that receives an MPLS echo request and sends an MPLS echo reply.
  • IP-Based Load Balancer: An LSR that load balances on fields from an IP header (and possibly fields from upper layers) and does not consider an entropy label from an MPLS label stack (i.e., flow label [RFC6391] or entropy label [RFC6790]) for load-balancing purposes.
  • Label-Based Load Balancer: An LSR that load balances on an entropy label from an MPLS label stack (i.e., flow label or entropy label) and does not consider fields from an IP header (and possibly fields from upper layers) for load-balancing purposes.
  • Label and IP-Based Load Balancer: An LSR that load balances on both entropy labels from an MPLS label stack and fields from an IP header (and possibly fields from upper layers).
  • MPLS: マルチプロトコルラベルスイッチング（Multiprotocol Label Switching）。
  • LSP: ラベルスイッチパス（Label Switched Path）。
  • スティッチングLSP（Stitched LSP）: スティッチングされたラベルスイッチパスは、複数のLSPを結合して、単一のエンドツーエンドのLSPを実現するものです。[RFC6424]は、スティッチングLSPに対するLSP pingを説明しています。
  • LSR: ラベルスイッチングルーター（Label Switching Router）。
  • FEC: 転送等価クラス（Forwarding Equivalence Class）。
  • ECMP: 等コストマルチパス（Equal-Cost Multipath）。
  • EL: エントロピーラベル（Entropy Label）。
  • ELI: エントロピーラベルインジケーター（Entropy Label Indicator）。
  • GAL: 汎用関連チャネルラベル（Generic Associated Channel Label）。
  • MS-PW: マルチセグメント疑似回線（Multi-Segment Pseudowire）。
  • イニシエーターLSR（Initiating LSR）: MPLSエコーリクエストを送信するLSR。
  • レスポンダーLSR（Responder LSR）: MPLSエコーリクエストを受信し、MPLSエコーリプライを送信するLSR。
  • IPベースのロードバランサー（IP-Based Load Balancer）: IPヘッダーのフィールド（および場合によっては上位レイヤーのフィールド）に基づいて負荷分散し、負荷分散の目的でMPLSラベルスタックのエントロピーラベル（すなわち、フローラベル[RFC6391]またはエントロピーラベル[RFC6790]）を考慮しないLSR。
  • ラベルベースのロードバランサー（Label-Based Load Balancer）: MPLSラベルスタックのエントロピーラベル（すなわち、フローラベルまたはエントロピーラベル）に基づいて負荷分散し、負荷分散の目的でIPヘッダーのフィールド（および場合によっては上位レイヤーのフィールド）を考慮しないLSR。
  • ラベルおよびIPベースのロードバランサー（Label and IP-Based Load Balancer）: MPLSラベルスタックのエントロピーラベルと、IPヘッダーのフィールド（および場合によっては上位レイヤーのフィールド）の両方に基づいて負荷分散するLSR。

1.2. Background

1.2. 背景

MPLS implementations employ a wide variety of load-balancing techniques in terms of fields used for hash "keys". The mechanisms in [RFC4379] and updated by [RFC6424] are designed to provide multipath support for a subset of techniques. The intent of this document is to provide multipath support for the supported techniques that are compromised by the use of ELs [RFC6790]. Section 9 describes supported and unsupported cases, and it may be useful for the reader to first review this section.

MPLSの実装は、ハッシュの「キー」として使用するフィールドに関して、多種多様な負荷分散の手法を採用しています。[RFC4379]のメカニズムと[RFC6424]による更新は、手法のサブセットに対してマルチパスのサポートを提供するように設計されています。この文書の意図は、サポートされている手法のうち、EL[RFC6790]の使用によって損なわれるものに対して、マルチパスのサポートを提供することです。セクション9は、サポートされるケースとサポートされないケースを説明しており、読者はまずそのセクションを確認すると役に立つかもしれません。

The Downstream Detailed Mapping (DDMAP) TLV [RFC6424] provides Multipath Information, which can be used by an LSP ping initiator to trace and validate ECMP paths between an ingress and egress. The Multipath Information encodings defined by [RFC6424] are sufficient when all the LSRs along the path(s), between ingress and egress, consider the same set of "keys" as input for load-balancing algorithms, e.g., either all IP based or all label based.

Downstream Detailed Mapping（DDMAP）TLV [RFC6424]はMultipath Informationを提供し、LSP pingのイニシエーターはこれを使用して、イングレスとイグレスの間のECMPパスをトレースし、検証できます。[RFC6424]で定義されたMultipath Informationのエンコーディングは、イングレスとイグレスの間のパスに沿ったすべてのLSRが、負荷分散のアルゴリズムへの入力として同じ「キー」の集合を考慮する場合（たとえば、すべてIPに基づく、またはすべてラベルに基づく場合）には十分です。

With the introduction of [RFC6790], some LSRs may perform load balancing based on labels while others may be IP based. This results in an LSP ping initiator that is unable to trace and validate all the ECMP paths in the following scenarios:

[RFC6790]の導入により、一部のLSRはラベルに基づいて負荷分散を行い、ほかのLSRはIPに基づいて負荷分散を行うことがあります。その結果、次のシナリオでは、LSP pingのイニシエーターはすべてのECMPパスをトレースして検証することができなくなります。

  • One or more transit LSRs along an LSP with ELI/EL in the label stack do not perform ECMP load balancing based on EL (hashes based on "keys" including the IP destination address). This scenario is not only possible but quite common due to transit LSRs not implementing [RFC6790] or transit LSRs implementing [RFC6790] but not implementing the suggested transit LSR behavior in Section 4.3 of [RFC6790].
  • Two or more LSPs stitched together with at least one of these LSPs pushing ELI/EL into the label stack.
  • ラベルスタックにELI/ELを持つLSPに沿った1つ以上のトランジットLSRが、ELに基づくECMPの負荷分散を行わない（IP宛先アドレスを含む「キー」に基づいてハッシュする）場合。このシナリオは、起こり得るだけでなく、ごく一般的です。というのも、[RFC6790]を実装していないトランジットLSRや、[RFC6790]を実装していても[RFC6790]のセクション4.3で提案されているトランジットLSRの動作を実装していないトランジットLSRがあるためです。
  • 2つ以上のLSPがスティッチされており、そのうち少なくとも1つのLSPがラベルスタックにELI/ELをプッシュしている場合。

These scenarios can be quite common because deployments of [RFC6790] typically have a mixture of nodes that support ELI/EL and nodes that do not. There will also typically be a mixture of areas that support ELI/EL and areas that do not.

[RFC6790]の展開では一般に、ELI/ELをサポートするノードとサポートしないノードが混在するため、これらのシナリオはごく一般的なものになり得ます。また、一般に、ELI/ELをサポートするエリアとサポートしないエリアも混在します。

As pointed out in [RFC6790], the procedures of [RFC4379] (and consequently of [RFC6424]) with respect to Multipath Information Type {9} are incomplete. However, [RFC6790] does not actually update [RFC4379]. Further, the specific EL location is not clearly defined, particularly in the case of Flow-Aware Pseudowires [RFC6391]. This document defines a new FEC Stack sub-TLV for the entropy label. Section 2 of this document updates the procedures for the Multipath Information Type {9} that are described in [RFC4379] and that are applicable to [RFC6424]. The rest of this document describes extensions required to restore ECMP discovery and tracing capabilities for the scenarios described.

[RFC6790]で指摘されているように、Multipath Information Type {9}に関する[RFC4379]の手順（したがって[RFC6424]の手順）は不完全です。しかし、[RFC6790]は実際には[RFC4379]を更新していません。さらに、特にフロー認識型の疑似回線（Flow-Aware Pseudowire）[RFC6391]の場合に、ELの具体的な位置が明確に定義されていません。この文書は、エントロピーラベルのための新しいFECスタックのサブTLVを定義します。この文書のセクション2は、[RFC4379]で説明され、[RFC6424]に適用されるMultipath Information Type {9}の手順を更新します。この文書の残りの部分では、説明したシナリオでECMPの発見とトレースの能力を回復するために必要な拡張を説明します。

[RFC4379], [RFC6424], and this document will support IP-based load balancers and label-based load balancers that limit their hash to the first (top-most) or only entropy label in the label stack. Other use cases (refer to Section 9) are out of scope.

[RFC4379]、[RFC6424]、およびこの文書は、IPベースのロードバランサーと、ハッシュの対象をラベルスタック内の最初の（最も上の）エントロピーラベルまたは唯一のエントロピーラベルに限定するラベルベースのロードバランサーをサポートします。その他のユースケース（セクション9を参照）は範囲外です。

2. Multipath Type {9}

2. マルチパスタイプ{9}

[RFC4379] defined Multipath Type {9} for the tracing of LSPs where label-based load balancing is used. However, as pointed out in [RFC6790], the procedures for using this type are incomplete as the specific location of the label was not defined. It was assumed that the presence of Multipath Type {9} implied that the value of the bottom-of-stack label should be varied by the values indicated by the multipath to determine the respective outgoing interfaces.

[RFC4379]は、ラベルベースの負荷分散が使用されているLSPのトレースのためにMultipath Type {9}を定義しました。しかし、[RFC6790]で指摘されているように、ラベルの具体的な位置が定義されていなかったため、このタイプを使用する手順は不完全です。Multipath Type {9}の存在は、それぞれの送信インターフェイスを決定するために、スタックの最下部のラベルの値をマルチパスが示す値で変化させるべきであることを意味すると想定されていました。

Section 4 defines a new FEC-Stack sub-TLV to indicate an entropy label. These labels MAY appear anywhere in a label stack.

セクション4は、エントロピーラベルを示すための新しいFECスタックのサブTLVを定義します。これらのラベルは、ラベルスタック内のどこに現れてもよいです（MAY）。

Multipath Type {9} applies to the first label in the label stack that corresponds to an EL-FEC. If no such label is found, it applies to the label at the bottom of the label stack.

Multipath Type {9}は、ラベルスタック内でEL-FECに対応する最初のラベルに適用されます。そのようなラベルが見つからない場合は、ラベルスタックの最下部のラベルに適用されます。

3. Pseudowire Tracing

3. 疑似回線のトレース

This section defines procedures for tracing Pseudowires. These procedures pertain to the use of Multipath Information Type {9} as well as Type {10}. In all cases below, when a control word is in use, the N flag in the DDMAP MUST be set. Note that when a control word is not in use, the returned DDMAPs may not be accurate.

このセクションでは、疑似回線をトレースするための手順を定義します。これらの手順は、Multipath Information Type {9}とType {10}の使用に関係します。以下のすべての場合において、コントロールワードが使用されているときは、DDMAPのNフラグを設定しなければなりません（MUST）。コントロールワードが使用されていないときは、返されるDDMAPが正確でない可能性があることに注意してください。

In order to trace a Pseudowire that is not flow aware, the initiator includes an EL-FEC instead of the appropriate PW FEC at the bottom of the FEC Stack. Tracing in this way will cause compliant routers to return the proper outgoing interface. Note that this procedure only traces to the end of the MPLS LSP that is under test and will not verify the PW FEC. To actually verify the PW FEC or in the case of a MS-PW, to determine the next Pseudowire label value, the initiator MUST repeat that step of the trace (i.e., repeating the TTL value used) but with the FEC Stack modified to contain the appropriate PW FEC. Note that these procedures are applicable to scenarios where an initiator is able to vary the bottom label (i.e., Pseudowire label). Possible scenarios are tracing multiple Pseudowires that are not flow aware on the same endpoints or tracing a Pseudowire that is not flow-aware provisioned with multiple Pseudowire labels.

フロー認識型ではない疑似回線をトレースするために、イニシエーターは、FECスタックの最下部に、適切なPW FECの代わりにEL-FECを含めます。この方法でトレースすると、準拠ルーターは適切な送信インターフェイスを返します。この手順は、テスト対象のMPLS LSPの終端までしかトレースせず、PW FECを検証しないことに注意してください。実際にPW FECを検証するため、またはMS-PWの場合に次の疑似回線ラベルの値を決定するために、イニシエーターは、適切なPW FECを含むようにFECスタックを変更したうえで、トレースのその段階を繰り返さなければなりません（MUST）（すなわち、使用したTTLの値を繰り返します）。これらの手順は、イニシエーターが最下部のラベル（すなわち、疑似回線ラベル）を変化させることができるシナリオに適用可能であることに注意してください。考えられるシナリオは、同じエンドポイント上にあるフロー認識型ではない複数の疑似回線をトレースする場合や、複数の疑似回線ラベルでプロビジョニングされたフロー認識型ではない疑似回線をトレースする場合です。

In order to trace a flow-aware Pseudowire [RFC6391], the initiator includes an EL FEC at the bottom of the FEC Stack and pushes the appropriate PW FEC onto the FEC Stack.

フロー認識型の疑似回線[RFC6391]をトレースするために、イニシエーターは、FECスタックの最下部にEL FECを含め、適切なPW FECをFECスタックにプッシュします。

In order to trace through routers that are not compliant, the initiator forms an MPLS echo request message and includes a DDMAP with the Multipath Type {9}. For a Pseudowire that is not flow aware, it includes the appropriate PW FEC in the FEC Stack. For a flow- aware Pseudowire, the initiator includes a Nil FEC at the bottom of the FEC Stack and pushes the appropriate PW FEC onto the FEC Stack.

準拠していないルーターを通してトレースするために、イニシエーターは、MPLSエコーリクエストメッセージを作成し、Multipath Type {9}のDDMAPを含めます。フロー認識型ではない疑似回線の場合、イニシエーターは、適切なPW FECをFECスタックに含めます。フロー認識型の疑似回線の場合、イニシエーターは、FECスタックの最下部にNil FECを含め、適切なPW FECをFECスタックにプッシュします。

4. Entropy Label FEC

4. エントロピーラベルFEC

The ELI is a reserved label that has no associated explicit FEC, and has the label value 7 assigned from the reserved range. Use the Nil FEC as the Target FEC Stack sub-TLV to account for ELI in a Target FEC Stack TLV.

ELIは、関連する明示的なFECを持たない予約済みラベルであり、予約済みの範囲から割り当てられたラベル値7を持ちます。Target FEC Stack TLV内のELIを表すには、Target FEC StackのサブTLVとしてNil FECを使用します。

The EL is a special-purpose label with the label value being discretionary (i.e., the label value is not from the reserved range). For LSP verification mechanics to perform its purpose, it is necessary for a Target FEC Stack sub-TLV to clearly describe the EL, particularly in the scenario where the label stack does not carry ELI (e.g., flow-aware Pseudowire [RFC6391]). Therefore, this document defines an EL FEC sub-TLV (33, see Section 11.1) that allows a Target FEC Stack sub-TLV to be added to the Target FEC Stack to account for EL.

ELは、ラベル値が任意に選ばれる（すなわち、ラベル値が予約済みの範囲のものではない）特殊用途のラベルです。LSPの検証のメカニズムがその目的を果たすためには、特にラベルスタックがELIを運ばないシナリオ（たとえば、フロー認識型の疑似回線[RFC6391]）において、Target FEC StackのサブTLVがELを明確に記述する必要があります。そのため、この文書は、ELを表すためにTarget FEC StackにTarget FEC StackのサブTLVを追加できるようにする、EL FECのサブTLV（33、セクション11.1を参照）を定義します。

The Length is 4. Labels are 20-bit values treated as numbers.

Lengthは4です。ラベルは、数値として扱われる20ビットの値です。

"Label" is the actual label value inserted in the label stack; the "MBZ" field MUST be zero when sent and ignored on receipt.

「Label」は、ラベルスタックに挿入される実際のラベル値です。「MBZ」フィールドは、送信時にはゼロにし、受信時には無視しなければなりません（MUST）。

7. Initiating LSR Procedures

7. イニシエーターLSRの手順

The following procedure is described in terms of an EL_LSP boolean maintained by the initiating LSR. This value controls the Multipath Information Type to be used in the transmitted echo request packets. When the initiating LSR is transmitting an echo request packet with DDMAP with a non-zero Multipath Information Type, then the EL_LSP boolean MUST be consulted to determine the Multipath Information Type to use.

以下の手順は、イニシエーターLSRが保持するEL_LSPというブール値を用いて説明します。この値は、送信するエコーリクエストパケットで使用するMultipath Information Typeを制御します。イニシエーターLSRが、ゼロ以外のMultipath Information TypeのDDMAPを含むエコーリクエストパケットを送信する場合、使用するMultipath Information Typeを決定するためにEL_LSPのブール値を参照しなければなりません（MUST）。

In addition to the procedures described in [RFC4379], as updated by Section 2 and [RFC6424], the initiating LSR MUST operate with the following procedures:

セクション2と[RFC6424]によって更新された[RFC4379]で説明されている手順に加えて、イニシエーターLSRは次の手順で動作しなければなりません（MUST）。

  • When the initiating LSR pushes ELI/EL, initialize EL_LSP=True. Else, set EL_LSP=False.

  • When the initiating LSR is transmitting a non-zero Multipath Information Type:

    • If (EL_LSP), the initiating LSR MUST use the Multipath Information Type {10} unless the responder LSR cannot handle Type {10}. When the initiating LSR is transmitting the Multipath Information Type {10}, both "IP Multipath Information" and "Label Multipath Information" MUST be included, and "Associated Label Multipath Information" MUST be omitted (NULL).
    • Else, the initiating LSR MAY use the Multipath Information Type {2, 4, 8, 9, 10}. When the initiating LSR is transmitting the Multipath Information Type {10} in this case, "IP Multipath Information" MUST be included, and "Label Multipath Information" and "Associated Label Multipath Information" MUST be omitted (NULL).
  • When the initiating LSR receives an echo reply with {L=0, E=1} in the DS Flags with valid contents, set EL_LSP=True.

  • イニシエーターLSRがゼロ以外のMultipath Information Typeを送信する場合:

    • （EL_LSP）の場合、レスポンダーLSRがType {10}を扱えない場合を除き、イニシエーターLSRはMultipath Information Type {10}を使用しなければなりません（MUST）。イニシエーターLSRがMultipath Information Type {10}を送信する場合、「IP Multipath Information」と「Label Multipath Information」の両方を含めなければなりません（MUST）。また、「Associated Label Multipath Information」は省略（NULL）しなければなりません（MUST）。
    • そうでない場合、イニシエーターLSRはMultipath Information Type {2, 4, 8, 9, 10}を使用してもよいです（MAY）。この場合にイニシエーターLSRがMultipath Information Type {10}を送信するときは、「IP Multipath Information」を含めなければなりません（MUST）。また、「Label Multipath Information」と「Associated Label Multipath Information」は省略（NULL）しなければなりません（MUST）。
  • イニシエーターLSRが、有効な内容を持ち、DS Flagsが{L=0, E=1}であるエコーリプライを受信した場合は、EL_LSP=Trueに設定します。

In the following conditions, the initiating LSR may have lost the ability to exercise specific ECMP paths. The initiating LSR MAY continue with "best effort" in the following cases:

次の状況では、イニシエーターLSRは特定のECMPパスにパケットを通す能力を失っている可能性があります。次の場合、イニシエーターLSRは「ベストエフォート」で続行してもよいです（MAY）。

  • IP Multipath Information Types {2, 4, 8} sent, and received echo reply with {L=1, E=0} in DS Flags.
  • Multipath Information Type {10} sent, and received echo reply with Multipath Information Type other than {10}.
  • 受信したエコーリプライが空のMultipath Informationを含む場合。
  • 受信したエコーリプライが{L=0, E=<any>}のDS Flagsを含むが、IP Multipath Informationを含まない場合。
  • 受信したエコーリプライが{L=1, E=<any>}のDS Flagsを含むが、Label Multipath Informationを含まない場合。
  • 受信したエコーリプライが{L=<any>, E=1}のDS Flagsを含むが、Associated Label Multipath Informationを含まない場合。
  • IP Multipath Information Type {2, 4, 8}を送信し、DS Flagsが{L=1, E=0}のエコーリプライを受信した場合。
  • Multipath Information Type {10}を送信し、{10}以外のMultipath Information Typeを含むエコーリプライを受信した場合。

8. Responder LSR Procedures

8. レスポンダーLSRの手順

Common Procedures:

共通の手順:

  • The responder LSR receiving an MPLS echo request packet MUST first determine whether or not the initiating LSR supports this LSP ping and traceroute extension for entropy labels. If either of the following conditions are met, the responder LSR SHOULD determine that the initiating LSR supports this LSP ping and traceroute extension for entropy labels.

    1. Received MPLS echo request contains the Multipath Information Type {10}.
    2. Received MPLS echo request contains a Target FEC Stack TLV that includes the entropy label FEC.

    If the initiating LSR is determined not to support this LSP ping and traceroute extension for entropy labels, then the responder LSR MUST NOT follow further procedures described in this section. Specifically, MPLS echo reply packets:

    • MUST have the following DS Flags cleared (i.e., not set): "ELI/EL push indicator" and "Label-based load balance indicator".
    • MUST NOT use the Multipath Information Type {10}.

  • The responder LSR receiving an MPLS echo request packet with the Multipath Information Type {10} MUST validate the following contents. Any deviation MUST result in the responder LSR considering the packet to be malformed and returning code 1 ("Malformed echo request received") in the MPLS echo reply packet.

    • IP Multipath Information MUST be included.
    • Label Multipath Information MAY be included.
    • Associated Label Multipath Information MUST be omitted (NULL).

  • MPLSエコーリクエストパケットを受信したレスポンダーLSRは、まず、イニシエーターLSRがエントロピーラベルのためのこのLSP pingとtracerouteの拡張をサポートしているかどうかを判断しなければなりません（MUST）。次の条件のいずれかが満たされる場合、レスポンダーLSRは、イニシエーターLSRがエントロピーラベルのためのこのLSP pingとtracerouteの拡張をサポートしていると判断すべきです（SHOULD）。

    1. 受信したMPLSエコーリクエストが、Multipath Information Type {10}を含む場合。
    2. 受信したMPLSエコーリクエストが、エントロピーラベルFECを含むTarget FEC Stack TLVを含む場合。

    イニシエーターLSRがエントロピーラベルのためのこのLSP pingとtracerouteの拡張をサポートしていないと判断された場合、レスポンダーLSRは、このセクションで説明するそれ以降の手順に従ってはなりません（MUST NOT）。具体的には、MPLSエコーリプライパケットは次のようにします。

    • 次のDS Flags、すなわち「ELI/EL push indicator」と「Label-based load balance indicator」をクリア（つまり、設定しない）しなければなりません（MUST）。
    • Multipath Information Type {10}を使用してはなりません（MUST NOT）。

  • Multipath Information Type {10}を含むMPLSエコーリクエストパケットを受信したレスポンダーLSRは、次の内容を検証しなければなりません（MUST）。いずれかに違反している場合、レスポンダーLSRは、そのパケットを不正な形式とみなし、MPLSエコーリプライパケットでコード1（"Malformed echo request received"）を返す必要があります（MUST）。

    • IP Multipath Informationを含めなければなりません（MUST）。
    • Label Multipath Informationを含めてもよいです（MAY）。
    • Associated Label Multipath Informationは省略（NULL）しなければなりません（MUST）。

The following subsections describe expected responder LSR procedures when the echo reply is to include DDMAP TLVs, based on the local load balance technique being employed. In case the responder LSR performs deviating load balance techniques on a per-downstream basis, appropriate procedures matched to each downstream load balance technique MUST be followed.

以下のサブセクションでは、エコーリプライにDDMAP TLVを含める場合に期待されるレスポンダーLSRの手順を、使用しているローカルの負荷分散の手法ごとに説明します。レスポンダーLSRが下流ごとに異なる負荷分散の手法を実行する場合、各下流の負荷分散の手法に合った適切な手順に従わなければなりません（MUST）。

8.1. IP-Based Load Balancer That Does Not Push ELI/EL

8.1. ELI/ELをプッシュしないIPベースのロードバランサー

8.5. Flow-Aware MS-PW Stitching LSR

A stitching LSR that cross-connects flow-aware Pseudowires behaves in one of two ways:

9. Supported and Unsupported Cases

9. サポートされるケースとサポートされないケース

The MPLS architecture does not define strict rules on how implementations are to identify hash "keys" for load-balancing purposes. As a result, implementations may be of the following load balancer types:

MPLSアーキテクチャーは、負荷分散の目的でハッシュの「キー」を実装がどのように識別するかについて、厳密な規則を定義していません。その結果、実装は次のロードバランサーの種類のいずれかになり得ます。

  1. IP-based load balancer.
  2. Label-based load balancer.
  3. Label- and IP-based load balancer.
  1. IPベースのロードバランサー。
  2. ラベルベースのロードバランサー。
  3. ラベルおよびIPベースのロードバランサー。

For cases (2) and (3), an implementation can include different sets of labels from the label stack for load-balancing purpose. Thus, the following sub-cases are possible:

ケース（2）と（3）では、実装は負荷分散の目的で、ラベルスタックからさまざまなラベルの集合を含めることができます。したがって、次のサブケースが考えられます。

  1. Entire label stack.
  2. Top N labels from label stack where the number of labels in label stack is > N.
  3. Bottom N labels from label stack where the number of labels in label stack is > N.
  1. ラベルスタック全体。
  2. ラベルスタック内のラベルの数がNを超える場合の、ラベルスタックの上位N個のラベル。
  3. ラベルスタック内のラベルの数がNを超える場合の、ラベルスタックの下位N個のラベル。

In a scenario where there is one flow label or entropy label present in the label stack, the following further cases are possible for (2b), (2c), (3b), and (3c):

ラベルスタック内にフローラベルまたはエントロピーラベルが1つ存在するシナリオでは、（2b）、（2c）、（3b）、（3c）について、さらに次のケースが考えられます。

  1. N labels from label stack include flow label or entropy label.
  2. N labels from label stack do not include flow label or entropy label.
  1. ラベルスタックのN個のラベルが、フローラベルまたはエントロピーラベルを含む場合。
  2. ラベルスタックのN個のラベルが、フローラベルまたはエントロピーラベルを含まない場合。

Also, in a scenario where there are multiple entropy labels present in the label stack, it is possible for implementations to employ deviating techniques:

また、ラベルスタック内に複数のエントロピーラベルが存在するシナリオでは、実装が異なる手法を採用する可能性があります。

  • Search for entropy stops at the first entropy label.
  • Search for entropy includes any entropy label found plus continues to search for entropy in the label stack.
  • エントロピーの探索は、最初のエントロピーラベルで停止します。
  • エントロピーの探索は、見つかったエントロピーラベルを含めたうえで、ラベルスタック内でエントロピーの探索を続けます。

Furthermore, handling of reserved (i.e., special) labels varies among implementations:

さらに、予約済み（すなわち、特殊な）ラベルの扱いは実装によって異なります。

  • Reserved labels are used in the hash as any other label would be (not a recommended practice).
  • Reserved labels are skipped over and, for implementations limited to N labels, the reserved labels do not count towards the limit of N.
  • Reserved labels are skipped over and, for implementations limited to N labels, the reserved labels count towards the limit of N.
  • 予約済みラベルを、ほかのラベルと同じようにハッシュで使用します（推奨される慣行ではありません）。
  • 予約済みラベルを読み飛ばし、N個のラベルに制限される実装では、予約済みラベルをNの上限に数えません。
  • 予約済みラベルを読み飛ばし、N個のラベルに制限される実装では、予約済みラベルをNの上限に数えます。

It is important to point this out since the presence of GAL will affect those implementations that include reserved labels for load-balancing purposes.

GALの存在は、負荷分散の目的で予約済みラベルを含める実装に影響を与えるので、この点を指摘しておくことは重要です。

As can be seen from the above, there are many types of potential load-balancing implementations. Attempting to get any Operations, Administration, and Maintenance (OAM) tools to support ECMP discovery and traversal over all types would require fairly complex procedures. Complexities in OAM tools have minimal benefit if the majority of implementations are expected to employ only a small subset of the cases described above.

上記からわかるように、負荷分散の実装には多くの種類が考えられます。運用・管理・保守（OAM）ツールに、すべての種類にわたってECMPの発見と走査をサポートさせようとすると、かなり複雑な手順が必要になります。実装の大多数が上記のケースのごく一部しか採用しないと予想される場合、OAMツールを複雑にしても得られる利点はわずかです。

  • Section 4.3 of [RFC6790] states that in implementations, for load-balancing purposes, parsing beyond the label stack after finding an entropy label has "limited incremental value". Therefore, it is expected that most implementations will be of types "IP-based load balancer" or "Label-based load balancer".
  • Section 2.4.5.1 of [RFC7325] recommends that searching for entropy labels in the label stack should terminate upon finding the first entropy label. Therefore, it is expected that implementations will only include the first (top-most) entropy label when there are multiple entropy labels in the label stack.
  • It is expected that, in most cases, the number of labels in the label stack will not exceed the number of labels (N) that implementations can include for load-balancing purposes.
  • It is expected that labels in the label stack, besides the flow label and entropy label, are constant for the lifetime of a single LSP multipath traceroute operation. Therefore, deviating load-balancing implementations with respect to reserved labels should not affect this tool.
  • [RFC6790]のセクション4.3は、実装において、負荷分散の目的でエントロピーラベルを見つけた後にラベルスタックの先まで解析することは「付加的な価値が限られている（limited incremental value）」と述べています。したがって、ほとんどの実装は「IPベースのロードバランサー」または「ラベルベースのロードバランサー」の種類になると予想されます。
  • [RFC7325]のセクション2.4.5.1は、ラベルスタック内のエントロピーラベルの探索は最初のエントロピーラベルを見つけた時点で終了すべきであると推奨しています。したがって、ラベルスタック内に複数のエントロピーラベルがある場合、実装は最初の（最も上の）エントロピーラベルだけを含めると予想されます。
  • ほとんどの場合、ラベルスタック内のラベルの数は、実装が負荷分散の目的で含めることができるラベルの数（N）を超えないと予想されます。
  • ラベルスタック内のフローラベルとエントロピーラベル以外のラベルは、単一のLSPマルチパスtraceroute操作の期間中は一定であると予想されます。したがって、予約済みラベルに関して負荷分散の実装が異なっていても、このツールには影響しないはずです。

Thus, [RFC4379], [RFC6424], and this document support cases (1) and (2a1), where only the first (top-most) entropy label is included when there are multiple entropy labels in the label stack.

以上から、[RFC4379]、[RFC6424]、およびこの文書は、ケース（1）と（2a1）をサポートします。ここで、ラベルスタック内に複数のエントロピーラベルがある場合は、最初の（最も上の）エントロピーラベルだけが含まれます。

10. Security Considerations

10. セキュリティーに関する考慮事項

While [RFC4379] and [RFC6424] already allow for the discovery and exercise of ECMP paths, this document extends the LSP ping and traceroute mechanisms to more precisely discover and exercise ECMP paths when an LSP uses ELI/EL in the label stack. Sourcing or inspecting LSP ping packets can be used for network reconnaissance.

[RFC4379]と[RFC6424]はすでにECMPパスの発見とそこへのパケットの送出を可能にしていますが、この文書は、LSPがラベルスタックでELI/ELを使用する場合に、ECMPパスをより正確に発見してそこにパケットを通せるよう、LSP pingとtracerouteのメカニズムを拡張します。LSP pingパケットを送出または検査することは、ネットワークの偵察に使用される可能性があります。

The extended capability defined in this document requires minor additional processing for the responder and initiator nodes. The responder node that pushes ELI/EL will need to compute and return multipath data including associated EL. The initiator node will need to store and handle both IP Multipath and Label Multipath Information, and include destination IP addresses and/or ELs in MPLS echo request packets as well as in the Multipath Information sent to downstream nodes. The security considerations of [RFC4379] already cover Denial-of-Service attacks by regulating LSP ping traffic going to the control plane.

この文書で定義する拡張された能力は、レスポンダーノードとイニシエーターノードにわずかな追加処理を必要とします。ELI/ELをプッシュするレスポンダーノードは、関連ELを含むマルチパスのデータを計算して返す必要があります。イニシエーターノードは、IP Multipath InformationとLabel Multipath Informationの両方を保存して扱い、MPLSエコーリクエストパケットと、下流ノードに送信するMultipath Informationに、宛先IPアドレスとELの一方または両方を含める必要があります。[RFC4379]のセキュリティーに関する考慮事項は、コントロールプレーンに向かうLSP pingのトラフィックを規制することにより、サービス拒否攻撃にすでに対処しています。

Finally, the security measures described in [RFC4379], [RFC6424], and [RFC6790] are applicable. [RFC6424] provides guidelines if a network operator wants to prevent tracing or does not want to expose details of the tunnel and [RFC6790] provides guidance on the use of the EL.

最後に、[RFC4379]、[RFC6424]、および[RFC6790]で説明されているセキュリティー対策が適用されます。[RFC6424]は、ネットワーク運用者がトレースを防止したい場合やトンネルの詳細を公開したくない場合のガイドラインを提供し、[RFC6790]はELの使用に関するガイダンスを提供しています。
