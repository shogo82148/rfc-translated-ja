RFC 513

Comments on the new Telnet specifications

RFC 513

新しいTelnet仕様に対するコメント

Abstract

概要

I would like to make the following comments on the proposed new TELNET Protocol Specification (NIC # 15372) and TELNET Option Specification (NIC 15373). In general I feel the new TELNET protocol is far superior to the previous version. There are, however, a few items of substance which I feel should be changed, as well as some recommended editorial changes.

提案されている新しいTELNETプロトコル仕様（NIC # 15372）とTELNETオプション仕様（NIC 15373）について、以下のコメントを述べたいと思います。全体として、新しいTELNETプロトコルは以前のバージョンよりはるかに優れていると感じています。しかし、変更すべきだと思う実質的な項目がいくつかあり、また編集上の変更もいくつか推奨します。

I feel the most significant error concerns the "Note on 'Sub-negotiations'" section of the Option Specification (page 2). The problem stems from the statements "Each party is presumed to be able to parse the parameter(s)" and "Finally, if parameters in an option 'subnegotiation' include a byte with a value of 255, it is not necessary to double this byte in accordance with the general TELNET IAC." These two statements make the completely unwarranted but all too prevalent assumption that there is only one "Telnet Interpreter" and that all TELNET functions are carried out by it. In particular, problems arise when a TELNET "synch" is received, and the receiving NCP is required to scan the input looking for "interesting" things. If the subnegotiation was in fact being carried out by a user process (and not the "TELNET interpreter") then that user process is probably the only one that knows how to interpret the SB parameters; the NCP itself would have no way of parsing them. As a solution to this problem I propose that all subnegotiation parameters be delimited at the end (perhaps with the same TELNET command SB) and that they be required to obey all TELNET rules, including doubling of IAC's. It may be argued that the user process interpreting the SB itself should do the scanning for "interesting" things, but I do not feel that this burden should be place on all user processes.

最も重大な誤りは、オプション仕様（2ページ）の「Note on 'Sub-negotiations'」の節に関するものだと思います。問題の原因は、「各当事者はパラメーターを解析できるものと想定する（Each party is presumed to be able to parse the parameter(s)）」と「最後に、オプションの『サブネゴシエーション』のパラメーターに値255のバイトが含まれていても、TELNETの一般的なIACに従ってこのバイトを二重にする必要はない（Finally, if parameters in an option 'subnegotiation' include a byte with a value of 255, it is not necessary to double this byte in accordance with the general TELNET IAC.）」という記述にあります。この2つの記述は、「Telnetインタープリター」は1つしかなく、TELNETのすべての機能がそれによって実行されるという、まったく根拠がないにもかかわらずあまりにも広まっている前提に立っています。特に、TELNETの「synch」を受信し、受信側のNCPが「興味深い（interesting）」ものを探して入力を走査しなければならない場合に問題が生じます。実際にサブネゴシエーションを（「TELNETインタープリター」ではなく）ユーザープロセスが行っていた場合、SBパラメーターの解釈方法を知っているのはおそらくそのユーザープロセスだけであり、NCP自身にはそれらを解析する手段がありません。この問題の解決策として、サブネゴシエーションのパラメーターはすべて（おそらく同じTELNETコマンドSBで）末尾を区切り、IACの二重化を含むTELNETのすべての規則に従うよう義務付けることを提案します。SBを解釈するユーザープロセス自身が「興味深い」ものの走査を行うべきだという意見もあるかもしれませんが、この負担をすべてのユーザープロセスに課すべきではないと思います。

The solution to the above problem is in fact fairly simple to define and implement. The general problem, however, is one of not taking proper cognizance of what I called "user processes" (processes which are not network standards, but which are simply programs attempting to do work using the network). I feel we must be more careful to shape all future network standards with these very real user processes in mind if in fact the network will ever be as useful as is possible.

上記の問題の解決策は、実際には定義も実装もかなり簡単です。しかし、より一般的な問題は、私が「ユーザープロセス」（ネットワークの標準ではなく、ネットワークを使って仕事をしようとする単なるプログラムであるプロセス）と呼んだものを適切に考慮していないことです。ネットワークが本当に可能な限り役に立つものになるためには、今後のネットワーク標準はすべて、こうした現実に存在するユーザープロセスを念頭に置いて、より注意深く形作っていかなければならないと思います。

The second item I object to is the incredibly loose definition of "interesting" things (an aside: words which are so imprecise as to require quotation marks should never appear in protocol specifications). The specifications do define some of these "interesting" things (eg, most TELNET commands) but they then include "and perhaps other characters or character strings as well". To eliminate the difficulty of implementing an undefined set of "interesting" things, I would propose that the set of "interesting" things, contain only the DM command itself. The TELNET "synch" would thus be defined as "discard all input up to and including the next DM command." This change should cause no problems with user-generated "interesting" things if they are sent after the "synch" (as specified in the proposed new File Transfer Protocol Specifications). System-generated signals (such as option requests) could be discarded, however, so some additional discussion is in order. If the recommendation that requests not be sent except when something changes is followed, the spontaneous generation of "interesting" things by TELNET itself (whatever that implies) would seem to be rare, especially at the same time that users are generating "synch's". A more positive solution could be had by defining a "synch response" (SR) TELNET command. The SR command would be sent when the INS and DM had both been processed (ie, when the "synch" had been completely received). If a process should ever receive an SR when it has an option request outstanding, the request has been discarded and must be repeated. User processes which carry on option negotiations would be the generators of any "synch's" so they can handle discarded option requests as desired. Note that this assumes that the TELNET process itself will never generate a spontaneous "synch"; comments are solicited on this. Another possible solution would be to define a "TIMING-MARK" TELNET command (see "TELNET Timing Mark Option", NIC # 16238), which would be sent immediately following the DM of a "synch". The response to the TIMING-MARK (also to be defined) would mean the same as the proposed SR command.

私が異議を唱える2つ目の項目は、「興味深い」ものの定義が信じられないほど曖昧なことです（余談ですが、引用符を必要とするほど不正確な語は、プロトコル仕様に決して現れるべきではありません）。仕様は、これらの「興味深い」もののいくつか（たとえば、ほとんどのTELNETコマンド）を定義してはいますが、さらに「そしておそらく他の文字や文字列も（and perhaps other characters or character strings as well）」と付け加えています。未定義の「興味深い」ものの集合を実装するという困難をなくすために、「興味深い」ものの集合にはDMコマンドそのものだけを含めることを提案します。そうすると、TELNETの「synch」は「次のDMコマンドまで（それを含む）のすべての入力を破棄する」と定義されることになります。この変更は、ユーザーが生成する「興味深い」ものが（提案されている新しいファイル転送プロトコル仕様で規定されているように）「synch」の後に送信されるのであれば、何の問題も引き起こさないはずです。しかし、システムが生成するシグナル（オプション要求など）は破棄される可能性があるので、さらに議論が必要です。何かが変化したとき以外は要求を送信しないという推奨事項に従うのであれば、TELNET自身が（それが何を意味するにせよ）「興味深い」ものを自発的に生成することはまれであり、特にユーザーが「synch」を生成しているのと同時に生成することはまれだと思われます。より積極的な解決策としては、「synch応答（synch response）」（SR）というTELNETコマンドを定義することが考えられます。SRコマンドは、INSとDMの両方が処理されたとき（つまり、「synch」を完全に受信したとき）に送信します。オプション要求に対する応答を待っている間にプロセスがSRを受信した場合、その要求は破棄されているので、要求を繰り返さなければなりません。オプションのネゴシエーションを行うユーザープロセスが「synch」を生成する側になるので、破棄されたオプション要求を望むように処理できます。これは、TELNETプロセス自身が自発的に「synch」を生成することはないという前提に立っていることに注意してください。この点についてコメントを求めます。もう1つの解決策として考えられるのは、「TIMING-MARK」というTELNETコマンド（「TELNET Timing Mark Option」、NIC # 16238を参照）を定義し、「synch」のDMの直後に送信することです。（これも定義が必要な）TIMING-MARKに対する応答は、提案したSRコマンドと同じ意味になります。

The final non-editorial comment concerns the need for some means of specifying horizontal tab positions and use. This is quite a nuisance when dealing with systems which normally handle tabs for local terminals. Perhaps this issue can be best handled with an appropriate option; comments are solicited.

編集上のものではない最後のコメントは、水平タブの位置と使い方を指定する何らかの手段が必要だということです。これは、通常はローカル端末のタブを処理するシステムを扱う際に、とても厄介な問題です。おそらくこの問題は、適切なオプションで扱うのが最善でしょう。コメントを求めます。

The only editorial comments are on the TELNET Protocol document, which I reference below by page number.

編集上のコメントは、TELNETプロトコルの文書に対するものだけです。以下では、ページ番号でその文書を参照します。

On page 8 the parenthetical comment "(i.e., when a process at one end of a TELNET connection is 'blocked on input')" should either be removed or rewritten to avoid the (to me) incomprehensible phrase "blocked on input." If additional discussion is felt to be necessary, I would propose "i.e., when a process at one end of a TELNET connection cannot proceed without additional input)." If examples are felt necessary, I would propose "(e.g., in the state characterized by the Multics term 'blocked on input')." The parallel could also be drawn between the GA and the concept of a "read command" being issued to request more input.

8ページの括弧書きのコメント「（つまり、TELNETコネクションの一端にあるプロセスが『入力待ちでブロックしている（blocked on input）』とき）」は、（私にとっては）理解できない「blocked on input」という語句を避けるために、削除するか書き直すべきです。追加の説明が必要だと思われるのであれば、「つまり、TELNETコネクションの一端にあるプロセスが追加の入力なしには先に進めないとき）」を提案します。例が必要だと思われるのであれば、「（たとえば、Multicsの用語『blocked on input』で特徴付けられる状態）」を提案します。また、GAと、さらなる入力を要求するために発行される「readコマンド」という概念との類似を示すこともできるでしょう。

On page 10 I feel that there needs to be some more discussion of the Abort Output (AO) command, particularly the statement that it "allows a process... to run to completion... but without sending the output to the user's terminal." The problem is that nothing is said about when output is to resume (presumably at the next system prompt character). I realized that the AO is meant only to invoke this function on systems which already provide it, but it would seem to be more useful if more fully specified.

10ページでは、Abort Output（AO）コマンドについて、特にそれが「プロセスが……完了まで実行することを……ただし、出力をユーザーの端末に送らずに……可能にする（allows a process... to run to completion... but without sending the output to the user's terminal.）」という記述について、もう少し説明が必要だと思います。問題は、出力がいつ再開されるのか（おそらく次のシステムのプロンプト文字のとき）について何も述べられていないことです。AOは、この機能をすでに提供しているシステムでその機能を呼び出すためだけのものだとは理解していますが、より完全に規定されていれば、より役に立つと思われます。

On page 11 I do not understand what the example "(e.g., an over-strike)" is trying to say. Speaking of an overstrike on output would imply to me that both characters are to be printed in the same print position, reducing the EC to a backspace. Some more discussion should also be added as to what EC (and EL) mean on output (if anything).

11ページの例「（たとえば、重ね打ち（over-strike））」が何を言おうとしているのか理解できません。出力時の重ね打ちというと、私には両方の文字を同じ印字位置に印字することを意味するように思われ、ECはバックスペースにすぎなくなってしまいます。また、EC（とEL）が出力時に（何かを意味するとすれば）何を意味するのかについて、もう少し説明を加えるべきです。

On page 11 I would like to see the word "promptly" (which is in quotation marks) either eliminated or defined, as per my earlier aside comment. The phrase "if necessary" in the last line also seems unnecessary.

11ページでは、先ほどの余談で述べたとおり、（引用符で囲まれている）「promptly」という語を削除するか定義してほしいと思います。また、最終行の「if necessary」という語句も不要だと思われます。

On page 12 my proposed redefinition of "interesting" signals would remove the middle paragraph entirely and would modify the third paragraph substantially. The line "discard all characters which would have had an effect on the NVT printer" should be changed, however, as it seems BELL's should also be discarded.

12ページについては、私が提案した「興味深い」シグナルの再定義によって、中間の段落がまるごと不要になり、3番目の段落が大幅に変わることになります。ただし、BELLも破棄すべきだと思われるので、「NVTプリンターに影響を与えたであろうすべての文字を破棄する（discard all characters which would have had an effect on the NVT printer）」という行は変更すべきです。

On page 14 I see no reason why the sequence "CR NUL" is required to generate a "CR" only, and also object to "and the CR character must be avoided in other contexts." Either some supporting discussion should be added or this restriction should be removed.

14ページについて、「CR NUL」という並びで「CR」だけを生成することが要求される理由がわかりません。また、「そしてCR文字は他の文脈では避けなければならない（and the CR character must be avoided in other contexts.）」にも異議を唱えます。裏付けとなる説明を加えるか、この制限を削除すべきです。
