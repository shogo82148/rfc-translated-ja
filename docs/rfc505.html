RFC 505

Two Solutions to a File Transfer Access Problem

RFC 505

ファイル転送のアクセス問題に対する2つの解決策

Abstract

概要

In RFC #87, Bob Bressler raises the issue of how one can use the File Transfer Protocol to send a file to a user on another system without knowing that user's password. In RFC 501, Kan Pogran points out certain objections to Bressler's solution of having a "daemon" process do the job -- in particular, the fact that it would require an interpretive access control mechanism in the daemon different from most system's normal access control mechanisms. Because Ken felt that it would be too much of a digression in RFC 501 for him to cover the following points fully, I decided it might be of interest to deal with them separately: There are at least two solutions to the problem Bob raised in RFC 487 -- in regard to "my" sending "him" a file without knowing his password -- which don't give rise to the problems noted in RFC 501. One hinges on adding a convention to the FTP, the other on adding a command.

RFC #87で、Bob Bresslerは、別のシステム上のユーザーのパスワードを知らずに、ファイル転送プロトコル（File Transfer Protocol）を使ってそのユーザーにファイルを送るにはどうすればよいかという問題を提起しています。RFC 501で、Kan Pogranは、「デーモン」プロセスにその作業をさせるというBresslerの解決策に対するいくつかの反論を指摘しています。特に、その解決策では、ほとんどのシステムの通常のアクセス制御メカニズムとは異なる、解釈型のアクセス制御メカニズムをデーモンに持たせる必要があるという点です。Kenは、以下の点を十分に扱うのはRFC 501では脱線が大きすぎると感じていたので、私はそれらを別個に扱うと興味深いかもしれないと考えました。BobがRFC 487で提起した問題、つまり「私」が「彼」のパスワードを知らずに「彼」にファイルを送るという問題には、RFC 501で指摘された問題を生じさせない解決策が少なくとも2つあります。1つはFTPに慣例を追加することに、もう1つはコマンドを追加することにかかっています。

The first solution is very straightforward. Instead of having me push the file, he could pull it. That is, he uses his own "principal identifies" (thus solving access permission problems at his end) and his own User FTP to extract the file with the aid of my Server FTP. All this requires is that 1) I give appropriate access permission on my end, and 2) he have the ability to use my Server FTP. The second condition is met by either a) his having an account on my system, or b) my system's having a known account for "free" Server FTP use. (*)

1つ目の解決策は非常に単純です。私がファイルをプッシュするのではなく、彼がそれをプルすればよいのです。つまり、彼は自分自身の「principal identifies」（これにより彼の側でのアクセス許可の問題は解決します）と自分自身のUser FTPを使って、私のServer FTPの助けを借りてファイルを取り出します。これに必要なのは、1)私が私の側で適切なアクセス許可を与えること、2)彼が私のServer FTPを使えること、だけです。2つ目の条件は、a)彼が私のシステムにアカウントを持っているか、b)私のシステムが「無料」のServer FTP利用のための既知のアカウントを持っているか、のどちらかによって満たされます。(*)

So standing the model on its head solves the functional problem, although he has to pay for the User FTP. But, then, it's he who wants the file, so why shouldn't he? On the other hand, "he" might not be logged in right now and I might be -- and by the time he can get logged in my system might be scheduled to be down. Fortunately, there's also a moderately straightforward solution to the problem as originally posed. This goes back to the mechanism used to prevent capricious and/or malicious card input on Multics: Instead of placing input (card deck or transferred file) directly into the alleged recipient's directory, place it in a "pool" directory and merely inform the recipient of its arrival. If he really wanted it, he then copies it into his own directory. That way, unauthorized people can't freeload on somebody else's directory (and the pool is, of course, periodically purged), nor can they clobber others' already-existing files.

このように、モデルを逆さまにすることで機能上の問題は解決しますが、彼はUser FTPの費用を払わなければなりません。しかし、ファイルを欲しがっているのは彼なのですから、そうして何が悪いでしょうか。一方で、「彼」は今ログインしていないが私はログインしている、ということもあり得ますし、彼がログインできるころには私のシステムが停止する予定になっているかもしれません。幸いなことに、もともと提起された問題に対しても、そこそこ単純な解決策があります。これは、Multicsで気まぐれな、あるいは悪意のあるカード入力を防ぐために使われているメカニズムにさかのぼります。入力（カードデッキや転送されたファイル）を受信者とされる者のディレクトリーに直接置くのではなく、「プール」ディレクトリーに置き、受信者にはその到着を知らせるだけにします。受信者が本当にそれを欲しければ、自分のディレクトリーにコピーします。こうすれば、権限のない人が他人のディレクトリーにただ乗りすることも（もちろん、プールは定期的に一掃されます）、他人の既存のファイルを壊すこともできません。

This second solution has the virtue of requiring fewer steps than the first, and would work even when the first wouldn't; so even though it would require another FTP command, I propose the addition of a new FTP "POOL" command, which does what the last paragraph described. Depending on the various Servers' protection mechanisms, the pooled files could be made readable only by the declared recipients. This would, for example, offer an easy way to get some privacy for "mail" (which otherwise is likely to be readable by anybody who can write it), although other solutions to that particular problem of course exist. At any rate, the POOL command's syntax would be POOL id name where id is a valid user identifier on the Server, and name is the desired name to be placed on the about-to-be-transferred file in the Server's pool directory. (*) (Servers must, of course, do whatever pre- or post-fixing to name is necessary to make it unique within the pool.) The transfer then takes place in the same manner as with STOR, and on successful completion the Server sends a message to id that he should pick up name (suitably) modified to look like a local pathname) if he wants it. The message should also identify the putative sender (even though it might have come in from a free account). The id should, naturally, be validated before starting the transfer.

この2つ目の解決策には、1つ目よりも手順が少なくて済み、1つ目がうまくいかない場合でも機能するという長所があります。そのため、FTPコマンドをもう1つ必要とはしますが、前の段落で説明したことを行う新しいFTPの"POOL"コマンドの追加を提案します。各Serverの保護メカニズムによっては、プールされたファイルを、宣言された受信者だけが読めるようにすることもできます。これにより、たとえば「メール」（そうしなければ、それを書き込める人なら誰でも読める可能性が高い）にある程度のプライバシーを持たせる簡単な方法が得られますが、もちろんその特定の問題に対する解決策は他にもあります。いずれにせよ、POOLコマンドの構文はPOOL id nameとなります。ここで、idはServer上の有効なユーザー識別子であり、nameは、これから転送されるファイルにServerのプールディレクトリー内で付けたい名前です。(*)（もちろん、Serverは、nameをプール内で一意にするために必要な接頭辞や接尾辞の付加を行わなければなりません。）その後、転送はSTORと同じ方法で行われ、正常に完了すると、Serverはidに対して、欲しければname（ローカルのパス名に見えるよう（適切に）変更されたもの）を取りに来るようにというメッセージを送ります。このメッセージは、推定される送信者も識別すべきです（たとえそれが無料アカウントから来たものであってもです）。当然ながら、idは転送を開始する前に検証されるべきです。

The question has been raised locally as to why we don't simply take a pooled view of STOR on Multics and forget about pushing for a new command. To do so would have two drawbacks, I feel: first, I think we'd be remiss in our duty as NWG participants if we failed to attempt to offer solutions to protocol problems to the Network community as a whole. Second, on a less pious but more practical note, if we don't know the id we have to infer it from the pathname, which rules out abbreviations and forces senders to have to know too much about our internal structure. (The alternative of requiring an additional argument to the STOR is subject to the same objection. It is also subject to the objection that protocols really shouldn't be unilaterally extended. Of course, we could go to "site-specific parameters", but that's complicating life so much that the alternative of no unsolicited files seems preferable.) Therefore, I think that POOL would be worthwhile unless no other Servers have enough access control for it to be necessary anywhere but on Multics. At the very least, having the protocol specify an "access id" optional argument to STOR seems desirable.

Multicsでは単にSTORをプール方式として扱い、新しいコマンドを推し進めるのはやめればよいのではないか、という疑問がローカルで提起されています。私の考えでは、そうすることには2つの欠点があります。第一に、ネットワークコミュニティー全体に対してプロトコルの問題の解決策を提示しようとしなければ、NWGの参加者としての義務を怠ることになると思います。第二に、それほど殊勝ではないがより実際的な話として、idがわからなければパス名からそれを推測しなければならず、そうすると省略形が使えなくなり、送信者が私たちの内部構造について知らなければならないことが多くなりすぎます。（STORに追加の引数を要求するという代替案も、同じ反論を受けます。また、プロトコルは本来一方的に拡張されるべきではないという反論も受けます。もちろん、「サイト固有のパラメーター」に頼ることもできますが、それでは物事が複雑になりすぎるので、求められていないファイルは受け付けないという代替案のほうが望ましいように思えます。）したがって、他のServerがどれも、Multics以外の場所でPOOLが必要になるほどのアクセス制御を持っていないのでない限り、POOLは価値があると考えます。少なくとも、プロトコルでSTORに対する任意の引数として「access id」を規定することは望ましいと思われます。

Input as to whether any of the other Servers has file access control abilities similar to those of Multics would be useful in clarifying whether this whole area is one which needs specific treatment at the Protocol level, or merely needs internally acceptable handling at our end. In the meantime, if you're trying to send an unsolicited file to us for free, you can use the NETML mechanism with no directory qualification on the target pathname in the STOR, then MAIL the file name to the intended recipient, who will copy the file into his own directory (from, in our syntax, >udd>Cnet>anonymous). That's all pretty complicated, but it sure does go to show that higher-level protocols need to know an awful lot about the various operating systems. At any rate, comment on either Bressler's Problem, POOL, STOR, or other people's access control mechanisms would all be appreciated.

他のServerのいずれかがMulticsと同様のファイルアクセス制御能力を持っているかどうかについての意見をいただければ、この領域全体がプロトコルのレベルで特別な扱いを必要とするものなのか、それとも私たちの側で内部的に受け入れ可能な処理をすればよいだけなのかを明らかにするのに役立ちます。それまでの間、私たちに求められていないファイルを無料で送ろうとする場合は、NETMLメカニズムを使い、STORの対象パス名にディレクトリーの修飾を付けずに送り、その後ファイル名を意図した受信者にMAILしてください。受信者はそのファイルを（私たちの構文では>udd>Cnet>anonymousから）自分のディレクトリーにコピーします。これはかなり複雑ですが、上位レベルのプロトコルがさまざまなオペレーティングシステムについて非常に多くのことを知る必要があることを確かに示しています。いずれにせよ、Bresslerの問題、POOL、STOR、あるいは他の人々のアクセス制御メカニズムのいずれについてでも、コメントをいただければありがたいです。

文末脚注

[1] (*) For b),I suggest that the USER NETML / PASS NETML discipline of RFC 491 be extended. [1] (*) b)については、RFC 491のUSER NETML / PASS NETMLの規律を拡張することを提案します。つまり、自分のFTP Serverの無料利用を認めるHostは、このFTPコマンドの組を無料サービス開始の合図として受け付けるべきです。これがダミーユーザーのログインにつながるのか、デーモンプロセスへの引き渡しにつながるのかは、もちろんローカルの実装上の好みの問題です。

[2] (*) Note that this definition relieves the user of having to know the Server's pathname for the pool directory.
