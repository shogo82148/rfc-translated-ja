RFC 7813

IS-IS Path Control and Reservation

RFC 7813

IS-ISのパス制御と予約

Abstract

概要

IEEE 802.1Qca Path Control and Reservation (PCR) specifies explicit path control via IS-IS in Layer 2 networks in order to move beyond the shortest path capabilities provided by IEEE 802.1aq Shortest Path Bridging (SPB). IS-IS PCR provides capabilities for the establishment and control of explicit forwarding trees in a Layer 2 network domain. This document specifies the sub-TLVs for IS-IS PCR.

IEEE 802.1Qcaのパス制御と予約（Path Control and Reservation: PCR）は、IEEE 802.1aqの最短パスブリッジング（Shortest Path Bridging: SPB）が提供する最短パスの機能を超えるために、レイヤー2ネットワークにおいてIS-ISによる明示的なパス制御を規定します。 IS-IS PCRは、レイヤー2ネットワークドメインにおいて明示的な転送ツリーを確立し制御するための機能を提供します。 この文書は、IS-IS PCRのためのサブTLVを規定します。

1. Introduction

1. はじめに

IEEE 802.1Qca Path Control and Reservation (PCR) [IEEE8021Qca] specifies extensions to IS-IS for the control of Explicit Trees (ETs). The PCR extensions are compatible with the Shortest Path Bridging (SPB) extensions to IS-IS specified by [RFC6329] and [IEEE8021aq] (already rolled into [IEEE8021Q]). Furthermore, IS-IS with PCR extensions relies on the SPB architecture and terminology, and some of the IS-IS SPB sub-TLVs are also leveraged. IS-IS PCR builds upon IS-IS and uses IS-IS in a similar way to SPB. IS-IS PCR only addresses point-to-point physical links, although IS-IS also supports shared media LANs.

IEEE 802.1Qcaのパス制御と予約（Path Control and Reservation: PCR）[IEEE8021Qca]は、明示的ツリー（Explicit Tree: ET）を制御するためのIS-ISの拡張を規定しています。 PCRの拡張は、[RFC6329]と[IEEE8021aq]（すでに[IEEE8021Q]に統合済み）で規定された、IS-ISの最短パスブリッジング（Shortest Path Bridging: SPB）拡張と互換性があります。 さらに、PCR拡張を備えたIS-ISは、SPBのアーキテクチャーと用語に依拠しており、IS-IS SPBのサブTLVのいくつかも活用しています。 IS-IS PCRはIS-ISを基盤としており、SPBと同様の方法でIS-ISを使用します。 IS-ISは共有メディアLANもサポートしていますが、IS-IS PCRはポイントツーポイントの物理リンクのみを対象とします。

This document specifies five IS-IS sub-TLVs for the control of explicit trees by IS-IS PCR in a Layer 2 network as specified by IEEE Std 802.1Qca. In addition to the sub-TLVs specified here, IS-IS PCR relies on the following IS-IS SPB sub-TLVs specified by [RFC6329]:

この文書は、IEEE Std 802.1Qcaで規定されているとおりに、レイヤー2ネットワークにおいてIS-IS PCRによって明示的ツリーを制御するための5つのIS-ISサブTLVを規定します。 ここで規定するサブTLVに加えて、IS-IS PCRは、[RFC6329]で規定された次のIS-IS SPBサブTLVに依拠します。

  • SPB Link Metric sub-TLV
  • SPB Base VLAN-Identifiers sub-TLV
  • SPB Instance sub-TLV
  • SPBV MAC address sub-TLV
  • SPBM Service Identifier and Unicast Address sub-TLV
  • SPB Link MetricサブTLV
  • SPB Base VLAN-IdentifiersサブTLV
  • SPB InstanceサブTLV
  • SPBV MAC addressサブTLV
  • SPBM Service Identifier and Unicast AddressサブTLV

These sub-TLVs are used to provide the link metric and the associations among bridges, Media Access Control (MAC) addresses, VLAN IDs (VIDs), and I-SIDs within an IS-IS domain. The use of these SPB sub-TLVs for PCR is specified by IEEE Std 802.1Qca. Note that IS-IS PCR does not require the implementation of the full IS-IS SPB protocol but only the support of these SPB sub-TLVs. A bridge can support both IS-IS SPB and IS-IS PCR at the same time; however, when it supports both, they are implemented by the same IS-IS entity on a per-instance basis.

これらのサブTLVは、IS-ISドメイン内でのリンクメトリックと、ブリッジ、メディアアクセス制御（MAC）アドレス、VLAN ID（VID）、I-SIDの間の関連付けを提供するために使用されます。 PCRにおけるこれらのSPBサブTLVの使用は、IEEE Std 802.1Qcaで規定されています。 IS-IS PCRは、IS-IS SPBプロトコル全体の実装を必要とせず、これらのSPBサブTLVのサポートのみを必要とすることに注意してください。 ブリッジはIS-IS SPBとIS-IS PCRの両方を同時にサポートできます。 ただし、両方をサポートする場合、それらはインスタンスごとに同一のIS-ISエンティティーによって実装されます。

The sub-TLVs specified in this document can also be applied for Fast Reroute using Maximally Redundant Trees (MRT-FRR) [RFC7812] in a Layer 2 network. Maximally Redundant Trees (MRTs) are computed as specified in [RFC7811]. If MRT computation is split such that the Generalized Almost Directed Acyclic Graph (GADAG) is computed centrally, then these sub-TLVs can be used to distribute the GADAG, which is identical for each network node throughout a network domain.

この文書で規定するサブTLVは、レイヤー2ネットワークにおける最大冗長ツリーを用いた高速リルート（Fast Reroute using Maximally Redundant Trees: MRT-FRR）[RFC7812]にも適用できます。 最大冗長ツリー（MRT）は、[RFC7811]で規定されているとおりに計算されます。 一般化ほぼ有向非巡回グラフ（Generalized Almost Directed Acyclic Graph: GADAG）を集中的に計算するようにMRTの計算を分割する場合、これらのサブTLVを使用してGADAGを配布できます。 GADAGは、ネットワークドメイン全体を通じて各ネットワークノードで同一です。

PCR uses IS-IS, the SPB sub-TLVs listed above, and the new sub-TLVs defined in this document. IS-IS PCR has no impact on IETF protocols.

PCRは、IS-IS、上に挙げたSPBサブTLV、およびこの文書で定義する新しいサブTLVを使用します。 IS-IS PCRはIETFのプロトコルに影響を与えません。

4. Explicit Trees

4. 明示的ツリー

Explicit trees may be determined in some fashion. For example, an explicit tree may be determined by a Path Computation Element (PCE) [RFC4655]. A PCE is an entity that is capable of computing a topology for forwarding based on a network topology, its corresponding attributes, and potential constraints. If a PCE is used, it MUST explicitly specify an explicit tree as described in Section 6.1. Either a single PCE or multiple PCEs determine explicit trees for a domain. Even if there are multiple PCEs in a domain, each explicit tree MUST only be determined by one PCE, which is referred to as the owner PCE of the tree. PCEs and IS-IS PCR can be used in combination with IS-IS SPB shortest path routing. The remainder of this section, and subsequent sections, are written assuming PCE use.

明示的ツリーは、何らかの方法で決定されます。 たとえば、明示的ツリーはパス計算エレメント（PCE）[RFC4655]によって決定される場合があります。 PCEは、ネットワークトポロジー、それに対応する属性、および想定される制約に基づいて、転送のためのトポロジーを計算できるエンティティーです。 PCEを使用する場合、PCEはセクション6.1で説明するように明示的ツリーを明示的に指定しなければなりません（MUST）。 単一のPCEまたは複数のPCEが、ドメインの明示的ツリーを決定します。 ドメイン内に複数のPCEがある場合でも、各明示的ツリーは1つのPCEのみによって決定されなければなりません（MUST）。 このPCEを、そのツリーの所有者PCEと呼びます。 PCEとIS-IS PCRは、IS-IS SPBの最短パスルーティングと組み合わせて使用できます。 このセクションの残りの部分と後続のセクションは、PCEを使用することを前提に記述しています。

The PCE interacts with the active topology control protocol, i.e., with IS-IS. The collaboration with IS-IS can be provided by a Path Control Agent (PCA) on behalf of a PCE. Either the PCE or the corresponding PCA is part of the IS-IS domain. If the PCE is not part of the IS-IS domain, then the PCE MUST be associated with a PCA that is part of the IS-IS domain. The PCE or its PCA MUST establish IS-IS adjacency in order to receive all the LSPs transmitted by the bridges in the domain. The PCE, either on its own or via its PCA, can control the establishment of explicit trees in that domain by injecting an LSP conveying an explicit tree and thus instruct IS-IS to set up the explicit tree determined by the PCE. If instructed to do so by a PCE, IS-IS MAY also record and communicate bandwidth assignments, which MUST NOT be applied if reservation protocol (e.g., Multiple Stream Registration Protocol (MSRP)) is used in the domain. Both MSRP and IS-IS MUST NOT be used to make bandwidth assignments in the same domain.

PCEは、アクティブトポロジー制御プロトコル、すなわちIS-ISと相互作用します。 IS-ISとの連携は、PCEに代わってパス制御エージェント（PCA）が提供できます。 PCEまたは対応するPCAのいずれかがIS-ISドメインの一部となります。 PCEがIS-ISドメインの一部でない場合、PCEはIS-ISドメインの一部であるPCAと関連付けられなければなりません（MUST）。 PCEまたはそのPCAは、ドメイン内のブリッジが送信するすべてのLSPを受信するために、IS-ISの隣接関係を確立しなければなりません（MUST）。 PCEは、単独で、またはPCAを介して、明示的ツリーを伝えるLSPを注入し、それによってPCEが決定した明示的ツリーを設定するようIS-ISに指示することで、そのドメインにおける明示的ツリーの確立を制御できます。 PCEから指示された場合、IS-ISは帯域幅割り当てを記録し伝達してもよいです（MAY）。 ただし、ドメイン内で予約プロトコル（たとえば、マルチプルストリーム登録プロトコル（MSRP））が使用されている場合、この帯域幅割り当てを適用してはなりません（MUST NOT）。 同じドメイン内で、MSRPとIS-ISの両方を帯域幅割り当てに使用してはなりません（MUST NOT）。

The operation details of the PCE are not specified by this document or by IEEE Std 802.1Qca. If the PCE is part of the IS-IS domain, then the PCE uses IS-IS PDUs to communicate with the IS-IS domain and the PCE has a live IS-IS LSDB (i.e., the PCE implements the PCA functions too). A PCE can instead communicate with the IS-IS domain via a PCA, e.g., to retrieve the LSDB or instruct the creation of an explicit tree. However, the means of communication between the PCE and the PCA is not specified by this document or by IEEE Std 802.1Qca.

PCEの動作の詳細は、この文書でもIEEE Std 802.1Qcaでも規定していません。 PCEがIS-ISドメインの一部である場合、PCEはIS-IS PDUを使用してIS-ISドメインと通信し、PCEは稼働中のIS-IS LSDBを持ちます（すなわち、PCEはPCAの機能も実装します）。 代わりに、PCEはPCAを介してIS-ISドメインと通信することもできます。 たとえば、LSDBを取得したり、明示的ツリーの作成を指示したりするためです。 ただし、PCEとPCAの間の通信手段は、この文書でもIEEE Std 802.1Qcaでも規定していません。

An Explicit Tree (ET) is an undirected loop-free topology, whose use is under the control of the owner PCE by means of associating VIDs and MAC addresses with it. An ET MUST NOT contain cycles. As it is undirected, an ET contains no assumptions about the direction of any flows that use it; it can be used in either direction as specified by the VIDs and MAC addresses associated with it. It is the responsibility of the PCE to ensure reverse-path congruency and multicast-unicast congruency if that is required.

明示的ツリー（ET）は無向でループのないトポロジーであり、その使用は、VIDとMACアドレスをそれに関連付けることによって所有者PCEの制御下に置かれます。 ETは閉路を含んではなりません（MUST NOT）。 ETは無向であるため、それを使用するフローの方向について何も前提を置きません。 ETは、それに関連付けられたVIDとMACアドレスで指定されるとおりに、どちらの方向にも使用できます。 逆方向パスの一致性（reverse-path congruency）とマルチキャストとユニキャストの一致性が必要な場合、それを保証するのはPCEの責任です。

An explicit tree is either strict or loose. A strict explicit tree specifies all bridges and paths it comprises. A loose tree only specifies the bridges as a list of hops that have a special role in the tree, e.g., an Edge Bridge, and no path or path segment is specified between the bridges, which are therefore loose hops even if Edge Bridges are adjacent neighbors. The special role of a hop can be: Edge Bridge, root, leaf, a bridge to be avoided, or a transit hop in case of a tree with a single leaf. The path for a loose hop is determined by the Bridge Local Computation Engine (BLCE) of the bridges. The shortest path is used for a loose hop unless specified otherwise by the descriptor (Section 6.1) of the tree or by the corresponding ECT Algorithm (Section 5).

明示的ツリーは、厳密か緩いかのいずれかです。 厳密な明示的ツリーは、それを構成するすべてのブリッジとパスを指定します。 緩いツリーは、ツリー内で特別な役割（たとえば、エッジブリッジ）を持つブリッジをホップのリストとして指定するのみで、ブリッジ間のパスやパスセグメントは指定しません。 そのため、エッジブリッジ同士が隣接する近隣であっても、それらは緩いホップとなります。 ホップの特別な役割には、エッジブリッジ、ルート、リーフ、回避すべきブリッジ、またはリーフが1つだけのツリーの場合の中継ホップがあります。 緩いホップのパスは、ブリッジのブリッジローカル計算エンジン（BLCE）によって決定されます。 ツリーの記述子（セクション6.1）または対応するECTアルゴリズム（セクション5）によって別に指定されていない限り、緩いホップには最短パスが使用されます。

A loose explicit tree is constrained if the tree descriptor includes one or more constraints, e.g., the administrative group that the links of the tree have to belong to. The BLCE of the bridges then applies the Constrained Shortest Path First (CSPF) algorithm, which is Shortest Path First (SPF) on the topology that only contains the links meeting the constraint(s).

ツリーの記述子が1つ以上の制約（たとえば、ツリーのリンクが属さなければならない管理グループ）を含む場合、その緩い明示的ツリーは制約付きです。 その場合、ブリッジのBLCEは制約付き最短パス優先（CSPF）アルゴリズムを適用します。 これは、制約を満たすリンクのみを含むトポロジー上での最短パス優先（SPF）です。

An explicit tree is specified by a Topology sub-TLV (Section 6.1). The Topology sub-TLV associates one or more VIDs with an explicit tree. The Topology sub-TLV includes two or more Hop sub-TLVs (Section 6.2), and a hop is specified by an IS-IS System ID. A Hop sub-TLV MAY include a delay constraint for a loose hop. A Topology sub-TLV MAY also include further sub-TLVs to constrain loose hops. The bridges involved in an explicit tree store the corresponding Topology sub-TLVs in their Explicit Tree Database (ETDB).

明示的ツリーは、TopologyサブTLV（セクション6.1）によって指定されます。 TopologyサブTLVは、1つ以上のVIDを明示的ツリーに関連付けます。 TopologyサブTLVは2つ以上のHopサブTLV（セクション6.2）を含み、ホップはIS-ISのシステムIDによって指定されます。 HopサブTLVは、緩いホップに対する遅延制約を含めてもよいです（MAY）。 TopologyサブTLVは、緩いホップを制約するために、さらに別のサブTLVを含めてもよいです（MAY）。 明示的ツリーに関与するブリッジは、対応するTopologyサブTLVを自身の明示的ツリーデータベース（ETDB）に格納します。

Explicit trees are propagated and set up by IS-IS PCR in a domain. The PCE or its PCA assembles the Topology sub-TLVs (Section 6.1), and adds it into an LSP, which is flooded throughout the domain. The Topology sub-TLV is flooded by the same techniques used for the SPB LSPs. The bridges then MUST process the Topology sub-TLV upon reception. If the Topology sub-TLV specifies one or more loose trees, then the path for the loose hops is determined by the BLCE of the bridges. The bridges then install the appropriate FDB entries for frame forwarding along the tree described by the Topology sub-TLV or the trees computed based on the Topology sub-TLV. Dynamic Filtering Entries are maintained by IS-IS for the [VID, MAC address] two-tuples associated with an ET.

明示的ツリーは、ドメイン内でIS-IS PCRによって伝搬され、設定されます。 PCEまたはそのPCAはTopologyサブTLV（セクション6.1）を組み立て、それをLSPに追加します。 このLSPはドメイン全体にフラッディングされます。 TopologyサブTLVは、SPBのLSPに使用されるのと同じ技法でフラッディングされます。 その後、ブリッジは受信時にTopologyサブTLVを処理しなければなりません（MUST）。 TopologyサブTLVが1つ以上の緩いツリーを指定している場合、緩いホップのパスはブリッジのBLCEによって決定されます。 その後、ブリッジは、TopologyサブTLVが記述するツリー、またはTopologyサブTLVに基づいて計算されたツリーに沿ってフレームを転送するための適切なFDBエントリーをインストールします。 ETに関連付けられた[VID, MACアドレス]の2つ組に対する動的フィルタリングエントリー（Dynamic Filtering Entry）は、IS-ISによって維持されます。

Due to the LSP aging of IS-IS, the Topology sub-TLVs (Section 6.1) have to be refreshed similar to other IS-IS TLVs in order to keep the integrity of the LSDB. The corresponding Dynamic Filtering Entries are also refreshed in the FDB when a Topology sub-TLV is refreshed. Refreshing Topology sub-TLVs is the task of the entity being part of the IS-IS domain, i.e., either the PCE or the PCA.

IS-ISのLSPのエージングのため、LSDBの完全性を保つために、TopologyサブTLV（セクション6.1）は他のIS-IS TLVと同様にリフレッシュされる必要があります。 TopologyサブTLVがリフレッシュされると、対応する動的フィルタリングエントリーもFDB内でリフレッシュされます。 TopologyサブTLVのリフレッシュは、IS-ISドメインの一部であるエンティティー、すなわちPCEまたはPCAのいずれかのタスクです。

The owner PCE can withdraw an explicit tree by sending an updated LSP that does not include the Topology sub-TLV (Section 6.1). If a Topology sub-TLV is removed from an LSP (or has been changed) so that (previous) Topology sub-TLV is no longer present (or has been changed) in the LSDB, then that (previous) Topology sub-TLV is implicitly withdrawn. IS-IS PCR then removes (or updates) the explicit tree.

所有者PCEは、TopologyサブTLV（セクション6.1）を含まない更新されたLSPを送信することで、明示的ツリーを撤回できます。 TopologyサブTLVがLSPから削除され（または変更され）、その結果（以前の）TopologyサブTLVがLSDBにもはや存在しない（または変更された）場合、その（以前の）TopologyサブTLVは暗黙的に撤回されます。 その後、IS-IS PCRは明示的ツリーを削除（または更新）します。

There is no precedence order between explicit trees. Precedence order among bandwidth assignments recorded by IS-IS PCR is specified in Section 6.4.

明示的ツリーの間に優先順位はありません。 IS-IS PCRによって記録される帯域幅割り当ての間の優先順位は、セクション6.4で規定しています。

If it is not possible to install an explicit tree, e.g., constraint(s) cannot be met or the Topology sub-TLV is ill-formed, then no tree is installed, but a management report is generated.

明示的ツリーをインストールできない場合（たとえば、制約を満たせない場合や、TopologyサブTLVの形式が不正な場合）、ツリーはインストールされず、管理レポートが生成されます。

5. Explicit ECT Algorithms

5. 明示的ECTアルゴリズム

The exact IS-IS control mode of operation MUST be selected for a VLAN by associating its Base VID with the appropriate ECT Algorithm in the SPB Base VLAN-Identifiers sub-TLV [RFC6329], in addition to allocating the Base VID to IS-IS control. There are five distinct ECT Algorithms for the five explicit path control modes. The operation details of the explicit ECT Algorithms and their configuration is specified by IEEE Std 802.1Qca; a high-level overview is given here. An ECT Algorithm value consists of the IEEE 802.1 OUI (Organizationally Unique Identifier) value 00-80-C2 concatenated with an index [RFC6329].

VLANのBase VIDをIS-ISの制御に割り当てることに加えて、SPB Base VLAN-IdentifiersサブTLV[RFC6329]においてそのBase VIDを適切なECTアルゴリズムに関連付けることで、VLANに対するIS-IS制御の正確な動作モードを選択しなければなりません（MUST）。 5つの明示的パス制御モードに対して、5つの異なるECTアルゴリズムがあります。 明示的ECTアルゴリズムの動作の詳細とその設定はIEEE Std 802.1Qcaで規定されており、ここでは高レベルの概要を示します。 ECTアルゴリズムの値は、IEEE 802.1のOUI（Organizationally Unique Identifier）の値00-80-C2にインデックスを連結したもので構成されます[RFC6329]。

The Strict Tree (ST) ECT Algorithm MUST be used for a strict explicit tree. A strict ET is static, as no other entity can update it but the owner PCE. In case of a topology change, it is the task of the owner PCE to detect the topology change, e.g., based on the changes in the LSDB and to update the strict trees if needed. That is, the owner PCE computes the new tree, assembles its descriptor (Section 6.1), and then instructs IS-IS PCR to install it. The value for the ST ECT Algorithm is 00-80-C2-17.

厳密な明示的ツリーには、厳密ツリー（Strict Tree: ST）ECTアルゴリズムを使用しなければなりません（MUST）。 厳密なETは、所有者PCE以外のエンティティーが更新できないため、静的です。 トポロジー変更が発生した場合、たとえばLSDBの変化に基づいてトポロジー変更を検出し、必要に応じて厳密なツリーを更新するのは、所有者PCEのタスクです。 すなわち、所有者PCEは新しいツリーを計算し、その記述子（セクション6.1）を組み立て、それからIS-IS PCRにそれをインストールするよう指示します。 ST ECTアルゴリズムの値は00-80-C2-17です。

The Loose Tree (LT) ECT Algorithm MAY also be supported. It is used for a single loose explicit tree. The path for loose hops is determined by the BLCE of the bridges; therefore, the Topology sub-TLV (Section 6.1) specifying the tree MUST indicate which hop is the root of the tree. The loose hops are maintained by IS-IS, i.e., restored upon a topology change if a loop-free path is available. If the tree computed by the BLCE visits the same bridge twice (implying that a loop or hairpin has been created), then that loop or hairpin MUST be pruned from the tree even if it contains a hop specified by the Topology sub-TLV. It is a constraint if a bridge is not to be included, which can be specified by the Exclude flag of a Hop sub-TLV (Section 6.2) conveyed by the Topology sub-TLV specifying the tree. The range of values for the LT ECT Algorithms is 00-80-C2-21...00-80-C2-30.

緩いツリー（Loose Tree: LT）ECTアルゴリズムもサポートしてもよいです（MAY）。 これは単一の緩い明示的ツリーに使用されます。 緩いホップのパスはブリッジのBLCEによって決定されます。 そのため、ツリーを指定するTopologyサブTLV（セクション6.1）は、どのホップがツリーのルートであるかを示さなければなりません（MUST）。 緩いホップはIS-ISによって維持されます。 すなわち、ループのないパスが利用可能であれば、トポロジー変更時に復旧されます。 BLCEが計算したツリーが同じブリッジを2回訪れる場合（ループまたはヘアピンが作成されたことを意味します）、そのループまたはヘアピンは、TopologyサブTLVで指定されたホップを含んでいても、ツリーから刈り込まなければなりません（MUST）。 ブリッジを含めないことは制約であり、ツリーを指定するTopologyサブTLVが伝えるHopサブTLV（セクション6.2）のExcludeフラグによって指定できます。 LT ECTアルゴリズムの値の範囲は00-80-C2-21...00-80-C2-30です。

The Loose Tree Set (LTS) ECT Algorithm MAY also be supported. It is used if connectivity among the Edge Bridges specified by the Topology sub-TLV (Section 6.1) is to be provided by a set of loose trees such that one tree is rooted at each Edge Bridge. The BLCE of the bridges compute the loose trees, which are maintained by IS-IS, i.e., restored upon a topology change. One constraint can be to avoid some bridges in these trees, which can be specified by the Exclude flag (item c.6. in Section 6.2). Further constraints can be specified by the Topology sub-TLV. The range of values for the LT ECT Algorithms is 00-80-C2-31...00-80-C2-40.

緩いツリー集合（Loose Tree Set: LTS）ECTアルゴリズムもサポートしてもよいです（MAY）。 これは、TopologyサブTLV（セクション6.1）で指定されたエッジブリッジ間の接続性を、各エッジブリッジをルートとするツリーが1つずつあるような緩いツリーの集合によって提供する場合に使用されます。 ブリッジのBLCEが緩いツリーを計算し、それらのツリーはIS-ISによって維持されます。 すなわち、トポロジー変更時に復旧されます。 制約の1つとして、これらのツリーで一部のブリッジを回避することがあり、これはExcludeフラグ（セクション6.2の項目c.6.）によって指定できます。 さらに別の制約をTopologyサブTLVによって指定できます。 LT ECTアルゴリズムの値の範囲は00-80-C2-31...00-80-C2-40です。

The LT and LTS ECT Algorithms use the shortest paths after pruning the topology according to the constraint(s), if any. The shortest path tie-breaking specified by Section 12 of [RFC6329] is applied (see also subclauses 28.5 - 28.8 of [IEEE8021aq]), that's why range of values are associated with the LT and LTS ECT Algorithms. In case of the LT ECT Algorithm, the indexes are 0x21...0x30, and ECT-MASK{index-0x20} is applied to retrieve the ECT-MASK of Section 12 of [RFC6329]. In case of the LTS ECT Algorithm, the indexes are 0x31...0x40, and ECT-MASK{index-0x30} is applied to retrieve the ECT-MASK for shortest path tie-breaking.

LTおよびLTS ECTアルゴリズムは、制約があればそれに従ってトポロジーを刈り込んだ後の最短パスを使用します。 [RFC6329]のセクション12で規定された最短パスのタイブレークが適用されます（[IEEE8021aq]のサブクローズ28.5～28.8も参照してください）。 これが、LTおよびLTS ECTアルゴリズムに値の範囲が関連付けられている理由です。 LT ECTアルゴリズムの場合、インデックスは0x21...0x30であり、[RFC6329]のセクション12のECT-MASKを得るためにECT-MASK{index-0x20}が適用されます。 LTS ECTアルゴリズムの場合、インデックスは0x31...0x40であり、最短パスのタイブレークのためのECT-MASKを得るためにECT-MASK{index-0x30}が適用されます。

The MRT ECT Algorithm MAY also be supported. It is used for the establishment and maintenance of MRTs in a distributed fashion. The MRT Lowpoint algorithm specified by [RFC7811] MUST be used for the computation of MRTs. The MRT Lowpoint algorithm first computes the GADAG and then produces two MRTs for each MRT Root: MRT-Blue and MRT-Red. If the level of redundancy provided by each bridge being an MRT Root is not required, then the MRT Roots can be specified by a Topology sub-TLV (Section 6.1). Both the GADAG and the MRT computation steps are performed distributed, i.e., by each bridge. The value for the MRT ECT Algorithm is 00-80-C2-18.

MRT ECTアルゴリズムもサポートしてもよいです（MAY）。 これは、MRTを分散的に確立し維持するために使用されます。 MRTの計算には、[RFC7811]で規定されたMRT Lowpointアルゴリズムを使用しなければなりません（MUST）。 MRT Lowpointアルゴリズムは、まずGADAGを計算し、次に各MRTルートに対して2つのMRT（MRT-BlueとMRT-Red）を生成します。 各ブリッジがMRTルートとなることで提供される冗長性のレベルが必要でない場合、MRTルートをTopologyサブTLV（セクション6.1）で指定できます。 GADAGとMRTの計算ステップは、どちらも分散的に、すなわち各ブリッジによって実行されます。 MRT ECTアルゴリズムの値は00-80-C2-18です。

The MRT GADAG (MRTG) ECT Algorithm MAY also be supported. It splits the computation into two. As the GADAG is identical for each MRT within a domain, it is computed by a single entity, which is the GADAG Computer. The GADAG is then described in a Topology sub-TLV (Section 6.1), which is flooded in the domain. The bridges then compute the MRTs for the MRT Roots based on the GADAG received. Section 7 provides more details on the description of the GADAG. The value for the MRTG ECT Algorithm is 00-80-C2-19.

MRT GADAG（MRTG）ECTアルゴリズムもサポートしてもよいです（MAY）。 これは計算を2つに分割します。 GADAGはドメイン内の各MRTで同一であるため、単一のエンティティーによって計算されます。 このエンティティーをGADAG計算機（GADAG Computer）と呼びます。 その後、GADAGはTopologyサブTLV（セクション6.1）で記述され、ドメイン内にフラッディングされます。 その後、ブリッジは受信したGADAGに基づいて、MRTルートに対するMRTを計算します。 セクション7で、GADAGの記述についてさらに詳しく説明します。 MRTG ECTアルゴリズムの値は00-80-C2-19です。

MRTs are loose trees as bridges are involved in their computation and restoration. Thus, both the MRT and the MRTG ECT Algorithms provide a set of loose trees: two MRTs for each MRT Root.

MRTは、ブリッジがその計算と復旧に関与するため、緩いツリーです。 したがって、MRTとMRTGのECTアルゴリズムはどちらも、緩いツリーの集合（各MRTルートに対して2つのMRT）を提供します。

The SPB Link Metric sub-TLV [RFC6329] specifies the metric of each link for IS-IS PCR if the LT, the LTS, the MRT, or the MRTG ECT Algorithm is used. If the SPB Link Metric values advertised by different ends of an adjacency are different, then the maximum value MUST be used.

LT、LTS、MRT、またはMRTGのECTアルゴリズムを使用する場合、SPB Link MetricサブTLV[RFC6329]が、IS-IS PCRにおける各リンクのメトリックを指定します。 隣接関係の異なる端で広告されたSPB Link Metricの値が異なる場合、最大値を使用しなければなりません（MUST）。

6. IS-IS PCR Sub-TLVs

6. IS-IS PCRのサブTLV

The following sub-TLVs are specified for IS-IS PCR. The Topology sub-TLV MUST be carried in an MT-Capability TLV, the rest of the sub-TLVs are conveyed by the Topology sub-TLV.

IS-IS PCRのために、次のサブTLVを規定します。 TopologyサブTLVはMT-Capability TLVで運ばなければなりません（MUST）。 残りのサブTLVはTopologyサブTLVによって伝えられます。

6.1. Topology Sub-TLV

6.1. TopologyサブTLV

An explicit tree MUST be described by the variable-length Topology sub-TLV. A Generalized Almost Directed Acyclic Graph (GADAG) MAY be described by a Topology sub-TLV as explained in Section 7 in detail. The Topology sub-TLV MUST be carried in an MT-Capability TLV (type 144) [RFC6329] in a Link State PDU. A Topology sub-TLV specifying an explicit tree conveys one or more Base VIDs, two or more Hop sub-TLVs (Section 6.2). A Topology sub-TLV describing a loose tree MAY also convey further sub-TLVs to specify constraints. Figure 1 shows the format of the Topology sub-TLV.

明示的ツリーは、可変長のTopologyサブTLVによって記述されなければなりません（MUST）。 セクション7で詳しく説明するように、一般化ほぼ有向非巡回グラフ（GADAG）をTopologyサブTLVによって記述してもよいです（MAY）。 TopologyサブTLVは、リンクステートPDU内のMT-Capability TLV（タイプ144）[RFC6329]で運ばなければなりません（MUST）。 明示的ツリーを指定するTopologyサブTLVは、1つ以上のBase VIDと、2つ以上のHopサブTLV（セクション6.2）を伝えます。 緩いツリーを記述するTopologyサブTLVは、制約を指定するために、さらに別のサブTLVを伝えてもよいです（MAY）。 図1に、TopologyサブTLVのフォーマットを示します。

The parameters of explicit trees are encoded by the Topology sub-TLV as follows:

明示的ツリーのパラメーターは、TopologyサブTLVによって次のようにエンコードされます。

  1. Type (8 bits): The type of the sub-TLV, its value is 21.
  2. Length (8 bits): The total number of bytes contained in the Value field.
  3. Number of Base VIDs (8 bits): The number of Base VIDs carried in the Topology sub-TLV. Its minimum value is 1 if the Topology sub-TLV specifies one or more explicit trees. Its value can be 0 if the Topology sub-TLV specifies a GADAG.
  4. Reserved (Res) (4 bits): The reserved bits MUST be set to 0 on transmission and the value MUST be ignored on reception.
  5. Base VID (12 bits): The Base VID parameter provides the Base VID of the VLAN that is associated with the explicit tree. Multiple Base VIDs can be associated with the same explicit tree. In addition to the Base VID, some of the explicit ECT Algorithms (Section 5) require further VIDs that are associated with the VLAN via the SPB Instance sub-TLV [RFC6329]. A Topology sub-TLV specifying a GADAG can have zero Base VID parameters. In this case, the given GADAG MUST be applied for each VLAN associated with the MRTG ECT Algorithm (Section 5).
  6. sub-TLVs: The rest conveys further sub-TLVs that specify the hops of the topology and can also specify constraints as described in the following.
  1. Type（8ビット）: サブTLVのタイプで、その値は21です。
  2. Length（8ビット）: Valueフィールドに含まれるバイトの総数です。
  3. Number of Base VIDs（8ビット）: TopologyサブTLVで運ばれるBase VIDの数です。 TopologyサブTLVが1つ以上の明示的ツリーを指定する場合、その最小値は1です。 TopologyサブTLVがGADAGを指定する場合、その値は0になることがあります。
  4. Reserved（Res）（4ビット）: 予約済みビットは、送信時に0に設定しなければなりません（MUST）。 受信時にはその値を無視しなければなりません（MUST）。
  5. Base VID（12ビット）: Base VIDパラメーターは、明示的ツリーに関連付けられたVLANのBase VIDを提供します。 複数のBase VIDを同じ明示的ツリーに関連付けることができます。 Base VIDに加えて、一部の明示的ECTアルゴリズム（セクション5）は、SPB InstanceサブTLV[RFC6329]を介してVLANに関連付けられた追加のVIDを必要とします。 GADAGを指定するTopologyサブTLVは、Base VIDパラメーターを0個持つことができます。 この場合、与えられたGADAGは、MRTG ECTアルゴリズム（セクション5）に関連付けられた各VLANに適用しなければなりません（MUST）。
  6. sub-TLVs: 残りの部分は、トポロジーのホップを指定し、以下で説明するように制約も指定できる、さらに別のサブTLVを伝えます。

A topology is specified by a list of Hop sub-TLVs (Section 6.2), and a hop is specified by an IS-IS System ID. An ill-formed Topology sub-TLV (e.g., specifying an invalid or inconsistent tree) is ignored; no tree is installed, but a management report is generated.

トポロジーはHopサブTLV（セクション6.2）のリストによって指定され、ホップはIS-ISのシステムIDによって指定されます。 形式が不正なTopologyサブTLV（たとえば、無効または矛盾したツリーを指定しているもの）は無視されます。 ツリーはインストールされず、管理レポートが生成されます。

The Topology sub-TLV specifies a strict tree by decomposing the tree to branches. Each branch is a point-to-point path specified by an ordered list of hops where the end of each branch is a leaf. Each element of a branch is the direct link between adjacent neighbor bridges whose Hop sub-TLV is next to each other in the Topology sub-TLV. The first hop of the Topology sub-TLV is the root; hence, the first branch originates from the root. The rest of the branches fork from another branch. The first hop of a branch is a bridge that is already part of a former branch, and the last hop is a leaf bridge. Therefore, the hop after a leaf hop is the beginning of a new branch, if any. A hop of a branch is created if and only if the bridge specified for that hop is directly connected to the preceding bridge of the same branch. The first branch MUST begin with the root; after that, the order of the branches does not matter within the Topology sub-TLV. Figure 2 shows an example strict tree and its description.

TopologyサブTLVは、ツリーを枝（branch）に分解することで厳密なツリーを指定します。 各枝は、ホップの順序付きリストによって指定されるポイントツーポイントのパスであり、各枝の終端はリーフです。 枝の各要素は、TopologyサブTLV内でHopサブTLVが互いに隣り合っている、隣接する近隣ブリッジ間の直接リンクです。 TopologyサブTLVの最初のホップはルートです。 したがって、最初の枝はルートから始まります。 残りの枝は、別の枝から分岐します。 枝の最初のホップは、すでに前の枝の一部となっているブリッジであり、最後のホップはリーフブリッジです。 したがって、リーフホップの後のホップがあれば、それは新しい枝の始まりです。 枝のホップは、そのホップに指定されたブリッジが同じ枝の先行するブリッジに直接接続されている場合に限り、作成されます。 最初の枝はルートから始まらなければなりません（MUST）。 それ以降、TopologyサブTLV内での枝の順序は問題になりません。 図2に、厳密なツリーとその記述の例を示します。

The Topology sub-TLV of a loose tree does not provide any path or path segment other than the hops that are to participate. The root MUST be the first hop. The leaves of a single loose tree MUST also be specified. Hop sub-TLVs can be included in a Topology sub-TLV to specify bridges that have to be avoided. If the Topology sub-TLV only specifies a single leaf, then one or more transit hops can be specified by the Topology sub-TLV to direct the path along a sequence of bridges, specified by the order of hops. If bridges whose respective Hop sub-TLVs are adjacent to each other in the Topology sub-TLV are not topology neighbors, then it is a loose hop. If a Topology sub-TLV conveys one or more loose hops, then that sub-TLV defines a loose explicit tree and each hop is considered to be a loose hop. The path of a loose hop MUST be pruned from the tree if the path would create a loop or hairpin.

緩いツリーのTopologyサブTLVは、参加すべきホップ以外のパスやパスセグメントを一切提供しません。 ルートは最初のホップでなければなりません（MUST）。 単一の緩いツリーのリーフも指定しなければなりません（MUST）。 回避しなければならないブリッジを指定するために、HopサブTLVをTopologyサブTLVに含めることができます。 TopologyサブTLVがリーフを1つだけ指定する場合、ホップの順序で指定されるブリッジの並びに沿ってパスを誘導するために、1つ以上の中継ホップをTopologyサブTLVで指定できます。 TopologyサブTLV内でそれぞれのHopサブTLVが互いに隣接しているブリッジ同士が、トポロジー上の近隣ではない場合、それは緩いホップです。 TopologyサブTLVが1つ以上の緩いホップを伝える場合、そのサブTLVは緩い明示的ツリーを定義し、各ホップは緩いホップとみなされます。 緩いホップのパスがループまたはヘアピンを作り出す場合、そのパスはツリーから刈り込まなければなりません（MUST）。

If the Base VIDs of the Topology sub-TLV are associated with the LTS ECT Algorithm or the MRT ECT Algorithm, then the Hop sub-TLVs conveyed by the Topology sub-TLV belong to Edge Bridges or bridges to be excluded. The BLCEs compute the loose trees, e.g., MRTs, such that they span the Edge Bridges and are rooted at an Edge Bridge.

TopologyサブTLVのBase VIDがLTS ECTアルゴリズムまたはMRT ECTアルゴリズムに関連付けられている場合、TopologyサブTLVが伝えるHopサブTLVは、エッジブリッジまたは除外すべきブリッジに属します。 BLCEは、エッジブリッジにまたがり、エッジブリッジをルートとするように、緩いツリー（たとえば、MRT）を計算します。

The Topology sub-TLV specifies a GADAG if the Base VIDs conveyed by the Topology sub-TLV are associated with the MRTG ECT Algorithm. Section 7 provides the details on the description of a GADAG by a Topology sub-TLV.

TopologyサブTLVが伝えるBase VIDがMRTG ECTアルゴリズムに関連付けられている場合、TopologyサブTLVはGADAGを指定します。 セクション7で、TopologyサブTLVによるGADAGの記述の詳細を説明します。

Each Edge Bridge of an explicit tree MUST always be specified in the Topology sub-TLV by the inclusion of the Hop sub-TLVs corresponding to the Edge Bridges. The Edge Bridges of a tree are identified by setting the Edge Bridge flag (item c.3. in Section 6.2) in the appropriate Hop sub-TLVs.

明示的ツリーの各エッジブリッジは、エッジブリッジに対応するHopサブTLVを含めることによって、常にTopologyサブTLV内で指定されなければなりません（MUST）。 ツリーのエッジブリッジは、該当するHopサブTLVでEdge Bridgeフラグ（セクション6.2の項目c.3.）を設定することによって識別されます。

If the explicit tree is loose, then the Topology sub-TLV MAY convey further sub-TLVs to specify constraints, e.g., an Administrative Group sub-TLV [RFC5305] or a Bandwidth Constraint (Section 6.3). If it is not possible to meet the constraint(s) specified by the Topology sub-TLV, then no tree is installed but a management report is generated.

明示的ツリーが緩い場合、TopologyサブTLVは、制約を指定するために、さらに別のサブTLV（たとえば、Administrative GroupサブTLV[RFC5305]やBandwidth Constraint（セクション6.3））を伝えてもよいです（MAY）。 TopologyサブTLVで指定された制約を満たすことができない場合、ツリーはインストールされず、管理レポートが生成されます。

IS-IS PCR MAY be used for recording bandwidth assignment. In that case, the Topology sub-TLV conveys Bandwidth Assignment sub-TLV (Section 6.4), and it MAY also convey Timestamp sub-TLV (Section 6.5). If assignment of the bandwidth indicated by the Bandwidth Assignment sub-TLV of the Topology sub-TLV would result in overbooking any link of the explicit tree, then bandwidth assignment MUST NOT be performed and a management report is generated. If the Topology sub-TLV specifies a new valid explicit tree, then the tree is installed without bandwidth assignment.

IS-IS PCRを帯域幅割り当ての記録に使用してもよいです（MAY）。 その場合、TopologyサブTLVはBandwidth AssignmentサブTLV（セクション6.4）を伝え、TimestampサブTLV（セクション6.5）も伝えてもよいです（MAY）。 TopologyサブTLVのBandwidth AssignmentサブTLVが示す帯域幅を割り当てると明示的ツリーのいずれかのリンクがオーバーブッキングになる場合、帯域幅割り当てを実行してはなりません（MUST NOT）。 この場合、管理レポートが生成されます。 TopologyサブTLVが新しい有効な明示的ツリーを指定している場合、そのツリーは帯域幅割り当てなしでインストールされます。

6.2. Hop Sub-TLV

6.2. HopサブTLV

The Hop sub-TLV MUST be used to specify a hop of a topology. Each Hop sub-TLV conveys an IS-IS System ID, which specifies a hop. A Hop sub-TLV is conveyed by a Topology sub-TLV (Section 6.1). A strict explicit tree is decomposed to branches where each branch is a point-to-point path specified by an ordered list of Hop sub-TLVs as specified in Section 6.1. A hop of a branch is created if and only if the bridge specified for that hop is directly connected to the preceding bridge in the path. That is, a point-to-point LAN is identified by the two bridges it interconnects; and the LAN is part of the strict tree if and only if the Hop sub-TLVs of the two bridges are next to each other in the Topology sub-TLV. A Hop sub-TLV can convey a Circuit ID in order to distinguish multiple links between adjacent neighbor bridges. A Hop sub-TLV also specifies the role of a bridge, e.g., if it is the root or an Edge Bridge. The Topology sub-TLV of a loose tree only comprises the Hop sub-TLV of the bridges that have a special role in the tree. The Hop sub-TLV MAY also specify a delay budget for a loose hop.

トポロジーのホップを指定するには、HopサブTLVを使用しなければなりません（MUST）。 各HopサブTLVは、ホップを指定するIS-ISのシステムIDを伝えます。 HopサブTLVは、TopologyサブTLV（セクション6.1）によって伝えられます。 セクション6.1で規定するように、厳密な明示的ツリーは枝に分解され、各枝はHopサブTLVの順序付きリストによって指定されるポイントツーポイントのパスです。 枝のホップは、そのホップに指定されたブリッジがパス上の先行するブリッジに直接接続されている場合に限り、作成されます。 すなわち、ポイントツーポイントLANは、それが相互接続する2つのブリッジによって識別されます。 そして、そのLANは、2つのブリッジのHopサブTLVがTopologyサブTLV内で互いに隣り合っている場合に限り、厳密なツリーの一部となります。 HopサブTLVは、隣接する近隣ブリッジ間の複数のリンクを区別するために、サーキットIDを伝えることができます。 HopサブTLVは、ブリッジの役割（たとえば、ルートであるかエッジブリッジであるか）も指定します。 緩いツリーのTopologyサブTLVは、ツリー内で特別な役割を持つブリッジのHopサブTLVのみで構成されます。 HopサブTLVは、緩いホップに対する遅延の予算（delay budget）を指定してもよいです（MAY）。

By default, the Edge Bridges both transmit and receive with respect to each VID associated with an explicit tree, except for an LTS (Section 5) associated with a learning VLAN, which uses a unidirectional VID per bridge. The Hop sub-TLV allows different configuration by means of the Transmit (T) and Receive (R) flags conveyed in the sub-TLV. The VID and its T/R flags are only present in the Hop sub-TLV if the behavior of the Edge Bridges differs from the default.

デフォルトでは、エッジブリッジは、明示的ツリーに関連付けられた各VIDについて、送信と受信の両方を行います。 ただし、学習VLANに関連付けられたLTS（セクション5）は例外で、これはブリッジごとに単方向のVIDを使用します。 HopサブTLVは、サブTLVで伝えられる送信（Transmit: T）フラグと受信（Receive: R）フラグによって、異なる設定を可能にします。 VIDとそのT/Rフラグは、エッジブリッジの振る舞いがデフォルトと異なる場合にのみ、HopサブTLVに存在します。

Figure 3 shows the format of the variable length Hop sub-TLV, which MUST be conveyed by a Topology sub-TLV (Section 6.1).

図3に、可変長のHopサブTLVのフォーマットを示します。 HopサブTLVは、TopologyサブTLV（セクション6.1）によって伝えられなければなりません（MUST）。

The parameters of a hop are encoded as follows:

ホップのパラメーターは次のようにエンコードされます。

  1. Type (8 bits): The type of the sub-TLV, its value is 22.
  2. Length (8 bits): The total number of bytes contained in the Value field.

  3. Hop Flags (8 bits): The Hop sub-TLV conveys six one-bit flags. The Circuit and the VID flags influence the length of the Hop sub-TLV. Two bits are reserved for future use, transmitted as 0 and ignored on receipt.

    1. Circuit (C) flag (1 bit): The Circuit flag is a one-bit flag to indicate whether or not the Extended Local Circuit ID parameter is present. If the flag is set, then an Extended Local Circuit ID is also included in the Hop sub-TLV.
    2. VID (V) flag (1 bit): The VID flag is a one-bit flag to indicate whether or not one or more VIDs are conveyed by the Hop sub-TLV. If the flag is set, then the Number of VIDs parameter is present and indicates how many VIDs are conveyed by the Hop sub-TLV. If the VID flag is reset, then neither the Number of VIDs parameter nor VIDs are present in the Hop sub-TLV.
    3. Edge Bridge (B) flag (1 bit): The Edge Bridge flag is a one-bit flag to indicate whether or not the given System is an Edge Bridge, i.e., transmitter and/or receiver. If the System is an Edge Bridge, then the Edge Bridge flag MUST be set. The Edge Bridge flag indicates that FDB entries have to be installed for the given hop as specified by the SPBV MAC address sub-TLV or SPBM Service Identifier and Unicast Address sub-TLV of the hop.

    4. Root (R) flag (1 bit): The Root flag is a one-bit flag to indicate whether or not the given System is a root of the explicit tree specified by the Topology sub-TLV. If the System is a root of a tree, then the Root flag MUST be set. If the Topology sub-TLV specifies a single tree, i.e., the Base VIDs conveyed by the Topology sub-TLV are associated with either the ST ECT Algorithm or the LT ECT Algorithm (Section 5), then the Root flag is only set for one of the Systems conveyed by the Topology sub-TLV. Furthermore, the first Hop sub-TLV of the Topology sub-TLV conveys the System that is the root of the tree.

      If the Topology sub-TLV specifies a Loose Tree Set, i.e., the Base VIDs conveyed by the Topology sub-TLV are associated with the LTS ECT Algorithm (Section 5), then the Root flag is set for each Edge Bridge as each of them roots a tree.

      If the Topology sub-TLV is used for MRT operations, i.e., the Base VIDs conveyed by the Topology sub-TLV are associated with either the MRT ECT Algorithm or the MRTG ECT algorithm (Section 5), then the Root flag is set for each MRT Root. If no MRT Root is specified by a Topology sub-TLV specifying a GADAG, then each SPT Root is an MRT Root as well.

      If the Base VIDs conveyed by the Topology sub-TLV are associated with the MRTG ECT algorithm (Section 5), then the Topology sub-TLV specifies a GADAG and the very first Hop sub-TLV specifies the GADAG Root. There is no flag for indicating the GADAG Root.

    5. Leaf (L) flag (1 bit): The Leaf flag is a one-bit flag to indicate whether or not the given System is a leaf of the explicit tree specified by the Topology sub-TLV. If the System is a leaf, then the Leaf flag MUST be set. The Leaf flag is only used to mark a leaf of a tree if the Topology sub-TLV specifies a single tree. The Leaf flag MUST be used to indicate the end of a topology block if the Topology sub-TLV specifies a GADAG, see Section 7.
    6. Exclude (E) flag (1 bit): The Exclude flag is a one-bit flag to indicate if the given System MUST be excluded from the topology. The Exclude flag and the Root flag cannot be set for a given hop at the same time.
    7. Reserved (Res) (2 bits): The reserved bits MUST be set to 0 on transmission, and the value MUST be ignored on reception.
  4. System ID (48 bits): The six-byte IS-IS System Identifier of the bridge to which the Hop sub-TLV refers.
  5. Extended Local Circuit ID (32 bits): The Extended Local Circuit ID [RFC5303] parameter is not necessarily present in the Hop sub-TLV. Its presence is indicated by the Circuit flag. Parallel links corresponding to different IS-IS adjacencies between a pair of neighbor bridges can be distinguished by means of the Extended Local Circuit ID. The Extended Local Circuit ID is conveyed by the Hop sub-TLV specifying the bridge nearer to the root of the tree, and identifies a circuit that attaches the given bridge to its neighbor cited by the next Hop sub-TLV of the Topology sub-TLV. The Extended Local Circuit ID can only be used in strict trees.
  6. Number of VIDs (8 bits): The Number of VIDs parameter is not present if the Hop sub-TLV does not convey VIDs, which is indicated by the VID flag.

  7. VID and its T/R flags (14 bits): The VID and its T/R flags are only present in the Hop sub-TLV if the given bridge is an Edge Bridge and it behaves differently from the default with respect to that particular VID.

    1. T flag (1 bit): This is the Transmit allowed flag for the VID following the flag.
    2. R flag (1 bit): This is the Receive allowed flag for the VID following the flag.
    3. Reserved (Res) (2 bits): The reserved bits MUST be set to 0 on transmission, and the value MUST be ignored on reception.
    4. VID (12 bits): A VID.
  8. Delay Constraint (48 bits): A Hop sub-TLV MAY specify a delay constraint. The Length of the Hop sub-TLV indicates whether or not a delay constraint is present because the Length of a Hop sub-TLV conveying a delay constraint is six bytes greater than it would be without the delay constraint. The last six bytes then specify a delay constraint if they convey a Unidirectional Link Delay sub-TLV [RFC7810]. The delay constraint MAY be used in a Topology sub-TLV that specifies a single loose tree, i.e., the Base VIDs are associated with the LT ECT Algorithm (Section 5). If the delay constraint is applied, then the loose hop MUST fit in the delay budget specified by the Delay parameter of the Unidirectional Link Delay sub-TLV conveyed by the Hop sub-TLV. If the Topology sub-TLV specifies a single leaf, then the path between the preceding Hop sub-TLV and the current Hop sub-TLV MUST meet the delay budget. If the Topology sub-TLV specifies multiple leaves, then the path between the root and the current Hop sub-TLV MUST to meet the delay budget. If the tree is used as a reverse congruent tree, then the delay constraint applies in both directions. If the tree is used as a directed tree, then the delay constraint applies in the direction of the tree. If it is not possible to meet the delay constraint specified by the Topology sub-TLV, then no tree is installed but a management report is generated.
  1. Type（8ビット）: サブTLVのタイプで、その値は22です。
  2. Length（8ビット）: Valueフィールドに含まれるバイトの総数です。

  3. Hop Flags（8ビット）: HopサブTLVは6つの1ビットフラグを伝えます。 CircuitフラグとVIDフラグは、HopサブTLVの長さに影響します。 2ビットは将来の使用のために予約されており、0として送信され、受信時には無視されます。

    1. Circuit（C）フラグ（1ビット）: Circuitフラグは、Extended Local Circuit IDパラメーターが存在するかどうかを示す1ビットのフラグです。 このフラグが設定されている場合、Extended Local Circuit IDもHopサブTLVに含まれます。
    2. VID（V）フラグ（1ビット）: VIDフラグは、1つ以上のVIDがHopサブTLVによって伝えられるかどうかを示す1ビットのフラグです。 このフラグが設定されている場合、Number of VIDsパラメーターが存在し、HopサブTLVによって伝えられるVIDの数を示します。 VIDフラグがリセットされている場合、Number of VIDsパラメーターもVIDもHopサブTLVに存在しません。
    3. Edge Bridge（B）フラグ（1ビット）: Edge Bridgeフラグは、与えられたシステムがエッジブリッジ、すなわち送信者または受信者（あるいはその両方）であるかどうかを示す1ビットのフラグです。 システムがエッジブリッジである場合、Edge Bridgeフラグを設定しなければなりません（MUST）。 Edge Bridgeフラグは、そのホップのSPBV MAC addressサブTLVまたはSPBM Service Identifier and Unicast AddressサブTLVで指定されるとおりに、与えられたホップに対してFDBエントリーをインストールする必要があることを示します。

    4. Root（R）フラグ（1ビット）: Rootフラグは、与えられたシステムが、TopologyサブTLVで指定された明示的ツリーのルートであるかどうかを示す1ビットのフラグです。 システムがツリーのルートである場合、Rootフラグを設定しなければなりません（MUST）。 TopologyサブTLVが単一のツリーを指定する場合、すなわちTopologyサブTLVが伝えるBase VIDがST ECTアルゴリズムまたはLT ECTアルゴリズム（セクション5）のいずれかに関連付けられている場合、Rootフラグは、TopologyサブTLVが伝えるシステムのうちの1つに対してのみ設定されます。 さらに、TopologyサブTLVの最初のHopサブTLVは、ツリーのルートであるシステムを伝えます。

      TopologyサブTLVが緩いツリー集合を指定する場合、すなわちTopologyサブTLVが伝えるBase VIDがLTS ECTアルゴリズム（セクション5）に関連付けられている場合、各エッジブリッジがそれぞれツリーのルートとなるため、Rootフラグは各エッジブリッジに対して設定されます。

      TopologyサブTLVがMRTの操作に使用される場合、すなわちTopologyサブTLVが伝えるBase VIDがMRT ECTアルゴリズムまたはMRTG ECTアルゴリズム（セクション5）のいずれかに関連付けられている場合、Rootフラグは各MRTルートに対して設定されます。 GADAGを指定するTopologyサブTLVでMRTルートが指定されていない場合、各SPTルートがMRTルートでもあります。

      TopologyサブTLVが伝えるBase VIDがMRTG ECTアルゴリズム（セクション5）に関連付けられている場合、TopologyサブTLVはGADAGを指定し、一番最初のHopサブTLVがGADAGルートを指定します。 GADAGルートを示すためのフラグはありません。

    5. Leaf（L）フラグ（1ビット）: Leafフラグは、与えられたシステムが、TopologyサブTLVで指定された明示的ツリーのリーフであるかどうかを示す1ビットのフラグです。 システムがリーフである場合、Leafフラグを設定しなければなりません（MUST）。 Leafフラグは、TopologyサブTLVが単一のツリーを指定する場合にのみ、ツリーのリーフを示すために使用されます。 TopologyサブTLVがGADAGを指定する場合、Leafフラグはトポロジーブロックの終わりを示すために使用しなければなりません（MUST）。 セクション7を参照してください。
    6. Exclude（E）フラグ（1ビット）: Excludeフラグは、与えられたシステムをトポロジーから除外しなければならない（MUST）かどうかを示す1ビットのフラグです。 与えられたホップに対して、ExcludeフラグとRootフラグを同時に設定することはできません。
    7. Reserved（Res）（2ビット）: 予約済みビットは、送信時に0に設定しなければなりません（MUST）。 受信時にはその値を無視しなければなりません（MUST）。
  4. System ID（48ビット）: HopサブTLVが参照するブリッジの6バイトのIS-ISシステム識別子です。
  5. Extended Local Circuit ID（32ビット）: Extended Local Circuit ID[RFC5303]パラメーターは、HopサブTLVに必ずしも存在するとは限りません。 その存在はCircuitフラグによって示されます。 近隣ブリッジのペアの間の異なるIS-IS隣接関係に対応する並列リンクは、Extended Local Circuit IDによって区別できます。 Extended Local Circuit IDは、ツリーのルートにより近いブリッジを指定するHopサブTLVによって伝えられ、与えられたブリッジを、TopologyサブTLVの次のHopサブTLVで挙げられている近隣に接続するサーキットを識別します。 Extended Local Circuit IDは、厳密なツリーでのみ使用できます。
  6. Number of VIDs（8ビット）: HopサブTLVがVIDを伝えない場合、Number of VIDsパラメーターは存在しません。 これはVIDフラグによって示されます。

  7. VIDとそのT/Rフラグ（14ビット）: VIDとそのT/Rフラグは、与えられたブリッジがエッジブリッジであり、かつその特定のVIDに関してデフォルトとは異なる振る舞いをする場合にのみ、HopサブTLVに存在します。

    1. Tフラグ（1ビット）: フラグに続くVIDに対する送信許可フラグです。
    2. Rフラグ（1ビット）: フラグに続くVIDに対する受信許可フラグです。
    3. Reserved（Res）（2ビット）: 予約済みビットは、送信時に0に設定しなければなりません（MUST）。 受信時にはその値を無視しなければなりません（MUST）。
    4. VID（12ビット）: VIDです。
  8. Delay Constraint（48ビット）: HopサブTLVは遅延制約を指定してもよいです（MAY）。 遅延制約を伝えるHopサブTLVのLengthは、遅延制約がない場合よりも6バイト大きくなるため、HopサブTLVのLengthによって遅延制約が存在するかどうかがわかります。 その場合、最後の6バイトがUnidirectional Link DelayサブTLV[RFC7810]を伝えていれば、それが遅延制約を指定します。 遅延制約は、単一の緩いツリーを指定する（すなわち、Base VIDがLT ECTアルゴリズム（セクション5）に関連付けられている）TopologyサブTLVで使用してもよいです（MAY）。 遅延制約を適用する場合、緩いホップは、HopサブTLVが伝えるUnidirectional Link DelayサブTLVのDelayパラメーターで指定された遅延の予算内に収まらなければなりません（MUST）。 TopologyサブTLVがリーフを1つだけ指定する場合、先行するHopサブTLVと現在のHopサブTLVの間のパスが遅延の予算を満たさなければなりません（MUST）。 TopologyサブTLVが複数のリーフを指定する場合、ルートと現在のHopサブTLVの間のパスが遅延の予算を満たさなければなりません（MUST）。 ツリーが逆方向に一致するツリー（reverse congruent tree）として使用される場合、遅延制約は両方向に適用されます。 ツリーが有向ツリーとして使用される場合、遅延制約はツリーの方向に適用されます。 TopologyサブTLVで指定された遅延制約を満たすことができない場合、ツリーはインストールされず、管理レポートが生成されます。

6.3. Bandwidth Constraint Sub-TLV

6.3. Bandwidth ConstraintサブTLV

The Bandwidth Constraint sub-TLV MAY be included in a Topology sub-TLV (Section 6.1) in order to specify how much available bandwidth is to be provided by the constrained tree. Each loose hop MUST meet the bandwidth constraint. The bandwidth value of the constraint is a total value or it only refers to a single PCP as specified by the sub-TLV. Figure 4 shows the format of the Bandwidth Constraint sub-TLV.

制約付きツリーがどれだけの利用可能な帯域幅を提供すべきかを指定するために、Bandwidth ConstraintサブTLVをTopologyサブTLV（セクション6.1）に含めてもよいです（MAY）。 各緩いホップは帯域幅制約を満たさなければなりません（MUST）。 制約の帯域幅の値は、サブTLVで指定されるとおりに、合計値であるか、単一のPCPのみを対象とするかのいずれかです。 図4に、Bandwidth ConstraintサブTLVのフォーマットを示します。

The parameters of the bandwidth constraint are encoded as follows:

帯域幅制約のパラメーターは次のようにエンコードされます。

  1. Type (8 bits): The type of the sub-TLV, its value is 23.
  2. Length (8 bits): The total number of bytes contained in the Value field. The value of the Length field is 5 bytes.
  3. PCP (4 bits): The Priority Code Point (PCP) parameter identifies the traffic class the Available Bandwidth parameter refers to, if any.
  4. DEI (D) (1 bit): This is the Drop Eligible Indicator (DEI) parameter. If the DEI parameter is clear, then the bandwidth constraint refers to committed information rate. If the DEI parameter is set, then the bandwidth constraint refers to the peak information rate.
  5. PCP (P) flag (1 bit): If this flag is set, then the PCP parameter is taken into account.
  6. Reserved (Res) (3 bits): The reserved bits MUST be set to 0 on transmission, and the value MUST be ignored on reception.
  7. Available Bandwidth (32 bits): The Available Bandwidth is specific to the traffic class identified by the PCP parameter if the PCP flag is set; otherwise, it is total bandwidth. In line with the bandwidth parameters specified in [RFC5305], the Available Bandwidth is encoded as a 32-bit IEEE floating-point number [IEEE754], and the units are bytes (not bits!) per second. When the Unreserved Bandwidth sub-TLV (sub-TLV type 11 specified by [RFC5305]) is used in a Layer 2 bridge network, the priority value encoded in the Unreserved Bandwidth sub-TLV provides the PCP, i.e., identifies a traffic class (not a setup priority level). Thus, the Available Bandwidth of a traffic class is easily comparable with the Unreserved Bandwidth stored in the TED for the given traffic class. The bandwidth constraint applies for both directions in case of symmetric explicit trees. Nevertheless, a VID associated with an explicit tree can be made unidirectional by means of the T/R flags belonging to the VID in the Hop sub-TLV (item g. in Section 6.2) of the Edge Bridges. If all the VIDs of the Topology sub-TLV (Section 6.1) are unidirectional and all belong to the traffic class identified by the PCP parameter of the Bandwidth Constraint sub-TLV, then it is enough to meet the bandwidth constraint in the direction applied for those VIDs.
  1. Type（8ビット）: サブTLVのタイプで、その値は23です。
  2. Length（8ビット）: Valueフィールドに含まれるバイトの総数です。 Lengthフィールドの値は5バイトです。
  3. PCP（4ビット）: 優先度コードポイント（PCP）パラメーターは、Available Bandwidthパラメーターが対象とするトラフィッククラスがあれば、それを識別します。
  4. DEI（D）（1ビット）: 廃棄適格表示（DEI）パラメーターです。 DEIパラメーターがクリアされている場合、帯域幅制約は認定情報レート（committed information rate）を対象とします。 DEIパラメーターが設定されている場合、帯域幅制約は最大情報レート（peak information rate）を対象とします。
  5. PCP（P）フラグ（1ビット）: このフラグが設定されている場合、PCPパラメーターが考慮されます。
  6. Reserved（Res）（3ビット）: 予約済みビットは、送信時に0に設定しなければなりません（MUST）。 受信時にはその値を無視しなければなりません（MUST）。
  7. Available Bandwidth（32ビット）: PCPフラグが設定されている場合、Available BandwidthはPCPパラメーターで識別されるトラフィッククラスに固有のものです。 そうでない場合、合計の帯域幅です。 [RFC5305]で規定された帯域幅パラメーターに合わせて、Available Bandwidthは32ビットのIEEE浮動小数点数[IEEE754]としてエンコードされ、単位は1秒あたりのバイト数（ビット数ではありません！）です。 Unreserved BandwidthサブTLV（[RFC5305]で規定されたサブTLVタイプ11）をレイヤー2ブリッジネットワークで使用する場合、Unreserved BandwidthサブTLVにエンコードされた優先度の値はPCPを提供します。 すなわち、（セットアップ優先度レベルではなく）トラフィッククラスを識別します。 したがって、トラフィッククラスのAvailable Bandwidthは、そのトラフィッククラスについてTEDに格納されたUnreserved Bandwidthと容易に比較できます。 対称な明示的ツリーの場合、帯域幅制約は両方向に適用されます。 とはいえ、明示的ツリーに関連付けられたVIDは、エッジブリッジのHopサブTLV（セクション6.2の項目g.）でそのVIDに付随するT/Rフラグによって、単方向にできます。 TopologyサブTLV（セクション6.1）のすべてのVIDが単方向であり、かつすべてがBandwidth ConstraintサブTLVのPCPパラメーターで識別されるトラフィッククラスに属する場合、それらのVIDに適用される方向で帯域幅制約を満たせば十分です。

6.4. Bandwidth Assignment Sub-TLV

6.4. Bandwidth AssignmentサブTLV

IS-IS PCR MAY be used for recording bandwidth assignment for explicitly placed data traffic in a domain if MSRP is not used within the domain. If MSRP is used in a domain, then only MSRP performs reservations and IS-IS does not. Both MSRP and IS-IS MUST NOT be used to make bandwidth assignments in the same domain.

ドメイン内でMSRPが使用されていない場合、IS-IS PCRを、ドメイン内に明示的に配置されたデータトラフィックに対する帯域幅割り当ての記録に使用してもよいです（MAY）。 ドメイン内でMSRPが使用されている場合、予約を行うのはMSRPのみであり、IS-ISは行いません。 同じドメイン内で、MSRPとIS-ISの両方を帯域幅割り当てに使用してはなりません（MUST NOT）。

The Bandwidth Assignment sub-TLV can be used to define the amount of bandwidth whose assignment is to be recorded by IS-IS PCR at each hop of the explicit tree described by the corresponding Topology sub-TLV (Section 6.1). The Bandwidth Assignment sub-TLV is used by IS-IS PCR for the recording of bandwidth assignment for a traffic class identified by the PCP parameter of a VLAN tag. If precedence order has to be determined among bandwidth assignments in a domain with multiple PCEs, then IS-IS PCR does it as described below. If the bandwidth assignment specified by the Topology sub-TLV is not possible, e.g., due to overbooking, then bandwidth recording MUST NOT be performed and a management report is generated. If the Topology sub-TLV specifies a new valid explicit tree, then the tree is installed without bandwidth assignment. The Bandwidth Assignment sub-TLV is conveyed by a Topology sub-TLV (Section 6.1). Figure 5 shows the format of the Bandwidth Assignment sub-TLV.

Bandwidth AssignmentサブTLVは、対応するTopologyサブTLV（セクション6.1）によって記述された明示的ツリーの各ホップで、IS-IS PCRが割り当てを記録すべき帯域幅の量を定義するために使用できます。 Bandwidth AssignmentサブTLVは、VLANタグのPCPパラメーターで識別されるトラフィッククラスに対する帯域幅割り当てを記録するために、IS-IS PCRによって使用されます。 複数のPCEを持つドメインで帯域幅割り当ての間の優先順位を決定する必要がある場合、IS-IS PCRは以下で説明するようにそれを行います。 TopologyサブTLVで指定された帯域幅割り当てが（たとえば、オーバーブッキングのために）不可能な場合、帯域幅の記録を実行してはなりません（MUST NOT）。 この場合、管理レポートが生成されます。 TopologyサブTLVが新しい有効な明示的ツリーを指定している場合、そのツリーは帯域幅割り当てなしでインストールされます。 Bandwidth AssignmentサブTLVは、TopologyサブTLV（セクション6.1）によって伝えられます。 図5に、Bandwidth AssignmentサブTLVのフォーマットを示します。

The parameters of the bandwidth assignment are encoded as follows:

帯域幅割り当てのパラメーターは次のようにエンコードされます。

  1. Type (8 bits): The type of the sub-TLV, its value is 24.
  2. Length (8 bits): The total number of bytes contained in the Value field. The value of the Length field is 5 bytes.
  3. PCP (3 bits): The PCP parameter identifies the traffic class for which the bandwidth is to be assigned.
  4. DEI (D) (1 bit): This is the Drop Eligible Indicator (DEI) parameter. If the DEI parameter is clear, then the bandwidth assignment is performed for providing the committed information rate. If the DEI parameter is set, then the bandwidth assignment is performed for providing the peak information rate.
  5. Importance (Imp) (3 bits): This is the Importance parameter for determining precedence order among bandwidth assignments within a PCP as described below. A lower numerical value indicates more important bandwidth assignment within a PCP. The default value of the Importance parameter is 7.
  6. Reserved (R) (1 bit): The reserved bit MUST be set to 0 on transmission, and the value MUST be ignored on reception.
  7. Bandwidth (32 bits): This is the amount of bandwidth to be assigned for the traffic class identified by the PCP parameter. In line with the bandwidth values specified in [RFC5305], the Bandwidth parameter is encoded as a 32-bit IEEE floating-point number [IEEE754], and the units are bytes (not bits!) per second. The bandwidth assignment applies for both directions in case of symmetric explicit trees.
  1. Type（8ビット）: サブTLVのタイプで、その値は24です。
  2. Length（8ビット）: Valueフィールドに含まれるバイトの総数です。 Lengthフィールドの値は5バイトです。
  3. PCP（3ビット）: PCPパラメーターは、帯域幅を割り当てる対象のトラフィッククラスを識別します。
  4. DEI（D）（1ビット）: 廃棄適格表示（DEI）パラメーターです。 DEIパラメーターがクリアされている場合、帯域幅割り当ては認定情報レートを提供するために実行されます。 DEIパラメーターが設定されている場合、帯域幅割り当ては最大情報レートを提供するために実行されます。
  5. Importance（Imp）（3ビット）: 以下で説明するように、PCP内での帯域幅割り当ての間の優先順位を決定するためのImportanceパラメーターです。 数値が小さいほど、PCP内でより重要な帯域幅割り当てであることを示します。 Importanceパラメーターのデフォルト値は7です。
  6. Reserved（R）（1ビット）: 予約済みビットは、送信時に0に設定しなければなりません（MUST）。 受信時にはその値を無視しなければなりません（MUST）。
  7. Bandwidth（32ビット）: PCPパラメーターで識別されるトラフィッククラスに割り当てる帯域幅の量です。 [RFC5305]で規定された帯域幅の値に合わせて、Bandwidthパラメーターは32ビットのIEEE浮動小数点数[IEEE754]としてエンコードされ、単位は1秒あたりのバイト数（ビット数ではありません！）です。 対称な明示的ツリーの場合、帯域幅割り当ては両方向に適用されます。

The PCEs are collectively responsible for making a consistent set of bandwidth assignments when IS-IS PCR is used for recording bandwidth allocations. If, despite that, precedence ordering is required among bandwidth assignments, then ordering based on the following parameters MUST be applied:

IS-IS PCRを帯域幅の割り当ての記録に使用する場合、PCEは全体として、一貫した帯域幅割り当ての集合を作成する責任を負います。 それにもかかわらず帯域幅割り当ての間に優先順位付けが必要な場合、次のパラメーターに基づく順序付けを適用しなければなりません（MUST）。

  1. PCP parameter of Bandwidth Assignment sub-TLV,
  2. Importance parameter of Bandwidth Assignment sub-TLV,
  3. Timestamp sub-TLV (if present in the Topology sub-TLV).
  1. Bandwidth AssignmentサブTLVのPCPパラメーター
  2. Bandwidth AssignmentサブTLVのImportanceパラメーター
  3. TimestampサブTLV（TopologyサブTLVに存在する場合）

A bandwidth assignment takes precedence if it has a higher PCP, or a higher Importance within a PCP, or an earlier timestamp in case of equal Importance within a PCP. A bandwidth assignment associated with a timestamp takes precedence over a bandwidth assignment without a timestamp when PCP and Importance of different bandwidth assignments are both equal. If resolution is not possible based on the above parameters or they are not available, e.g., each bandwidth assignment lacks a timestamp or the precedence order has to be determined for the use of a VID, then the item is granted to the PCE whose LSP has the numerically lowest LSP ID.

帯域幅割り当ては、PCPがより高い場合、PCP内でImportanceがより高い場合、またはPCP内でImportanceが等しいときにタイムスタンプがより早い場合に、優先されます。 異なる帯域幅割り当てのPCPとImportanceがどちらも等しい場合、タイムスタンプに関連付けられた帯域幅割り当ては、タイムスタンプのない帯域幅割り当てよりも優先されます。 上記のパラメーターに基づいて解決できない場合、またはそれらが利用できない場合（たとえば、どの帯域幅割り当てもタイムスタンプを持たない場合や、VIDの使用について優先順位を決定する必要がある場合）、その項目は、数値的に最も小さいLSP IDのLSPを持つPCEに与えられます。

6.5. Timestamp Sub-TLV

6.5. TimestampサブTLV

The Timestamp sub-TLV MAY be included in a Topology sub-TLV (Section 6.1) in order to provide precedence order among equally important bandwidth assignments within a PCP as described in Section 6.4. Figure 6 shows the format of the Timestamp sub-TLV.

セクション6.4で説明するように、PCP内で同じ重要度の帯域幅割り当ての間に優先順位を与えるために、TimestampサブTLVをTopologyサブTLV（セクション6.1）に含めてもよいです（MAY）。 図6に、TimestampサブTLVのフォーマットを示します。

The timestamp represents a positive time with respect to the Precision Time Protocol (PTP) epoch, and it is encoded as follows:

タイムスタンプは、高精度時刻プロトコル（PTP）のエポックを基準とした正の時刻を表し、次のようにエンコードされます。

  1. Type (8 bits): The type of the sub-TLV; its value is 25.
  2. Length (8 bits): The total number of bytes contained in the Value field. The value of the Length field is 4 bytes.
  3. Time (32 bits): This is the time in units of seconds with respect to the PTP epoch.
  1. Type（8ビット）: サブTLVのタイプで、その値は25です。
  2. Length（8ビット）: Valueフィールドに含まれるバイトの総数です。 Lengthフィールドの値は4バイトです。
  3. Time（32ビット）: PTPのエポックを基準とした、秒単位の時刻です。

The Timestamp sub-TLV carries the seconds portion of PTP as specified by [IEEE1588]. The epoch is 1970-01-01 00:00:00 TAI (i.e., the PTP time does not include leap seconds).

TimestampサブTLVは、[IEEE1588]で規定されたPTPの秒の部分を運びます。 エポックは1970-01-01 00:00:00 TAIです（すなわち、PTPの時刻はうるう秒を含みません）。

7. MRT-FRR Application

7. MRT-FRRの適用

The application of MRT by [IEEE8021Qca] is discussed in detail in [MRT-IEEE8021qca]. This section describes some special considerations for the use of the MRT Lowpoint algorithm [RFC7811], which are applicable both to the MRT ECT Algorithm and the MRTG ECT Algorithm. This section also explains details related to the MRTG ECT Algorithm and the application of the Topology sub-TLV in particular.

[IEEE8021Qca]によるMRTの適用については、[MRT-IEEE8021qca]で詳しく議論されています。 このセクションでは、MRT Lowpointアルゴリズム[RFC7811]を使用する際のいくつかの特別な考慮事項を説明します。 これらは、MRT ECTアルゴリズムとMRTG ECTアルゴリズムの両方に適用されます。 このセクションでは、MRTG ECTアルゴリズムに関する詳細、特にTopologyサブTLVの適用についても説明します。

IS-IS PCR does not use the MRT Profile specified in [RFC7812]. IS-IS PCR only relies on the algorithm specification in [RFC7811]. Both the MRT ECT Algorithm and the MRTG ECT Algorithm use the MRT Lowpoint algorithm specified in [RFC7811].

IS-IS PCRは、[RFC7812]で規定されたMRTプロファイルを使用しません。 IS-IS PCRは、[RFC7811]のアルゴリズム仕様のみに依拠します。 MRT ECTアルゴリズムとMRTG ECTアルゴリズムはどちらも、[RFC7811]で規定されたMRT Lowpointアルゴリズムを使用します。

The SPB Link Metric sub-TLV [RFC6329] specifies the metric of each link for IS-IS PCR including the MRT algorithms. If the SPB Link Metric values advertised by different ends of an adjacency are different, then the maximum value MUST be used. If equal cost (sub-)paths are found during the MRT computation, then the default tie-breaking specified by Section 11 of [RFC6329] MUST be used, which is based on the lower BridgeID. (The BridgeID is an 8-byte quantity whose upper 2 bytes are the node's BridgePriority and lower 6 bytes are the node's System ID.) Note that if MRTs are used for source-specific multicast (see [IEEE8021Qca] for details), then the bridges have to compute the MRTs of the other bridges in addition to their own in order to be able to install the appropriated FDB entries. (This is similar to the need for all pairs shortest path computation instead of Dijkstra for source-specific shortest path multicast trees.)

SPB Link MetricサブTLV[RFC6329]は、MRTアルゴリズムを含むIS-IS PCRにおける各リンクのメトリックを指定します。 隣接関係の異なる端で広告されたSPB Link Metricの値が異なる場合、最大値を使用しなければなりません（MUST）。 MRTの計算中に等コストの（サブ）パスが見つかった場合、[RFC6329]のセクション11で規定されたデフォルトのタイブレークを使用しなければなりません（MUST）。 これは、より小さいBridgeIDに基づきます。 （BridgeIDは8バイトの量で、上位2バイトはノードのBridgePriority、下位6バイトはノードのシステムIDです。） MRTを送信元固有マルチキャスト（source-specific multicast）に使用する場合（詳細は[IEEE8021Qca]を参照してください）、適切なFDBエントリーをインストールできるようにするために、ブリッジは自身のMRTに加えて他のブリッジのMRTも計算する必要があることに注意してください。 （これは、送信元固有の最短パスマルチキャストツリーのために、ダイクストラ法の代わりに全点対間の最短パス計算が必要になるのと同様です。）

The GADAG is identical for all the MRTs within a network domain, as a consequence of the use of the MRT Lowpoint algorithm [RFC7811]. Therefore, it is beneficial to compute the GADAG by a single entity, which is referred to as the GADAG Computer and is either a PCE or the GADAG Root. If the MRTG ECT Algorithm is applied, then the GADAG MUST be computed only by the GADAG Computer, which then MUST flood the descriptor Topology sub-TLV of the GADAG. The bridges then compute the MRTs based on the received GADAG.

MRT Lowpointアルゴリズム[RFC7811]を使用する結果として、GADAGはネットワークドメイン内のすべてのMRTで同一です。 したがって、GADAGを単一のエンティティーで計算することには利点があります。 このエンティティーをGADAG計算機（GADAG Computer）と呼び、PCEかGADAGルートのいずれかです。 MRTG ECTアルゴリズムを適用する場合、GADAGはGADAG計算機のみによって計算されなければなりません（MUST）。 その後、GADAG計算機はGADAGの記述子であるTopologyサブTLVをフラッディングしなければなりません（MUST）。 その後、ブリッジは受信したGADAGに基づいてMRTを計算します。

The GADAG computation requires the selection of the GADAG Root. The bridge with the best BridgeID MUST be selected as the GADAG Root, where the numerically lower value indicates the better identifier. The Bridge Priority component of the BridgeID allows the configuration of the GADAG Root by management action. The Bridge Priority is conveyed by the SPB Instance sub-TLV [RFC6329].

GADAGの計算には、GADAGルートの選択が必要です。 最良のBridgeIDを持つブリッジをGADAGルートとして選択しなければなりません（MUST）。 ここで、数値的により小さい値がより良い識別子を示します。 BridgeIDのBridge Priority成分により、管理操作によってGADAGルートを設定できます。 Bridge Priorityは、SPB InstanceサブTLV[RFC6329]によって伝えられます。

The GADAG Computer MUST perform the GADAG computation as specified by the MRT Lowpoint algorithm [RFC7811]. The GADAG Computer then MUST encode the GADAG in a Topology sub-TLV (Section 6.1), which is then flooded throughout the domain. A GADAG is encoded in a Topology sub-TLV by means of directed ear decomposition as follows. A directed ear is a directed point-to-point path whose end points can coincide but no other element of the path is repeated in the ear. Each ear is specified by an ordered list of hops such that the order of hops is according to the direction of the arcs in the GADAG. There are no leaves in a GADAG; hence, the Leaf flag (item c.5. in Section 6.2) is used to mark the end of a topology block. (A GADAG with multiple blocks is illustrated in Figure 8.) The sequence of ears in the Topology sub-TLV is such that the end points of an ear belong to preceding ears. The GADAG Root is not marked by any flag, but the GADAG Root is the first hop in the Topology sub-TLV; correspondingly, the first ear starts and ends with the GADAG Root. MRT Roots MUST be marked by the Root flag (item c.4. in Section 6.2) and all other Edge Bridges are leaves of the given MRTs. If no MRT Root is specified, then each SPT Root is also an MRT Root.

GADAG計算機は、MRT Lowpointアルゴリズム[RFC7811]で規定されているとおりにGADAGの計算を実行しなければなりません（MUST）。 その後、GADAG計算機はGADAGをTopologyサブTLV（セクション6.1）にエンコードしなければなりません（MUST）。 このTopologyサブTLVはドメイン全体にフラッディングされます。 GADAGは、次のように有向耳分解（directed ear decomposition）によってTopologyサブTLVにエンコードされます。 有向耳（directed ear）とは、端点が一致してもよいが、パスの他の要素は耳の中で繰り返されない、有向のポイントツーポイントのパスです。 各耳は、ホップの順序がGADAGの弧の方向に従うようなホップの順序付きリストによって指定されます。 GADAGにはリーフがありません。 そのため、Leafフラグ（セクション6.2の項目c.5.）は、トポロジーブロックの終わりを示すために使用されます。 （複数のブロックを持つGADAGを図8に示します。） TopologyサブTLV内の耳の並びは、ある耳の端点がそれより前の耳に属するようになっています。 GADAGルートはどのフラグでも示されませんが、GADAGルートはTopologyサブTLVの最初のホップです。 それに対応して、最初の耳はGADAGルートで始まり、GADAGルートで終わります。 MRTルートはRootフラグ（セクション6.2の項目c.4.）で示されなければなりません（MUST）。 その他のすべてのエッジブリッジは、与えられたMRTのリーフです。 MRTルートが指定されていない場合、各SPTルートがMRTルートでもあります。

Figure 7 shows an example GADAG. The figure also illustrates the description of the GADAG; it shows the System ID parameter of the Hop sub-TLV (Section 6.2) and the order of hops in the Topology sub-TLV (Section 6.1).

図7に、GADAGの例を示します。 この図はGADAGの記述も示しています。 すなわち、HopサブTLV（セクション6.2）のSystem IDパラメーターと、TopologyサブTLV（セクション6.1）内のホップの順序を示しています。

A topology can comprise multiple blocks, like the one illustrated in Figure 8(a). This example topology comprises four blocks as each cut-link is a block. A-B-C-D-E-F is a block, D-G is another block, G-H, and H-J-K are further blocks. A GADAG for this topology is shown in Figure 8(b). Note that two arcs with opposite directions represent a cut-link in a GADAG; see, for example, the cut-link between D and G. The encoding starts with the block (ADAG) involving the GADAG Root as illustrated in Figure 8. The first hop in the Topology sub-TLV is the GADAG Root (node A in this example). The ADAG of the first block is then described using the ear decomposition, as described above. In this example, the first block has been completely traversed at the second occurrence of node A in the GADAG descriptor. The end of a block is indicated by setting the Leaf flag for the last hop of the block, e.g., for the second occurrence of node A in the example GADAG descriptor. The next node that appears in the GADAG descriptor (D in this case) is the localroot for the nodes in the next block. Continuing this process, the Leaf flag is set for the third occurrence of D, the third occurrence of G, and the third occurrence of H, each indicating the end of a block. The first hop of the first block is the GADAG Root, the fist hop in the rest of the blocks is the localroot. The position of the set Leaf flags helps to determine the localroot, which is the next hop. In the example GADAG descriptor, one can determine that A is the localroot for B, C, D, E, F (and A is the GADAG Root). D is the localroot for G. G is the localroot for H. And H is the localroot for J and K. The GADAG Root is assigned a localroot of None.

トポロジーは、図8(a)に示すもののように、複数のブロックで構成されることがあります。 この例のトポロジーは、各カットリンクが1つのブロックとなるため、4つのブロックで構成されます。 A-B-C-D-E-Fが1つのブロックであり、D-Gが別のブロックであり、G-HとH-J-Kがさらに別のブロックです。 このトポロジーに対するGADAGを図8(b)に示します。 GADAGでは、反対方向の2つの弧がカットリンクを表すことに注意してください。 たとえば、DとGの間のカットリンクを参照してください。 図8に示すように、エンコードはGADAGルートを含むブロック（ADAG）から始まります。 TopologyサブTLVの最初のホップはGADAGルート（この例ではノードA）です。 次に、上で説明したように、耳分解を使用して最初のブロックのADAGを記述します。 この例では、GADAG記述子においてノードAが2回目に出現した時点で、最初のブロックが完全にたどられています。 ブロックの終わりは、ブロックの最後のホップ（たとえば、この例のGADAG記述子におけるノードAの2回目の出現）に対してLeafフラグを設定することで示されます。 GADAG記述子に次に出現するノード（この場合はD）は、次のブロック内のノードのlocalrootです。 この処理を続けると、Dの3回目の出現、Gの3回目の出現、Hの3回目の出現に対してLeafフラグが設定され、それぞれがブロックの終わりを示します。 最初のブロックの最初のホップはGADAGルートであり、残りのブロックの最初のホップはlocalrootです。 設定されたLeafフラグの位置は、次のホップであるlocalrootを判断するのに役立ちます。 この例のGADAG記述子からは、AがB、C、D、E、Fのlocalrootであること（そしてAがGADAGルートであること）がわかります。 DはGのlocalrootです。 GはHのlocalrootです。 そして、HはJとKのlocalrootです。 GADAGルートには、localrootとしてNoneが割り当てられます。

Block IDs are reconstructed while parsing a Topology sub-TLV specifying a GADAG. The current Block ID starts at 0 and is assigned to the GADAG Root. A node appearing in the GADAG descriptor without a previously assigned Block ID value is assigned the current Block ID. And the current Block ID is incremented by 1 after processing the localroot of a block. Note that the localroot of a block will keep the Block ID of the first block in which it is assigned a Block ID. In the example in Figure 8, A has Block ID=0. B, C, D, E, and F have Block ID=1. G has Block ID=2. H has Block ID=3. J and K have Block ID=4.

ブロックIDは、GADAGを指定するTopologyサブTLVを解析する間に再構築されます。 現在のブロックIDは0から始まり、GADAGルートに割り当てられます。 以前にブロックIDの値が割り当てられていない状態でGADAG記述子に出現したノードには、現在のブロックIDが割り当てられます。 そして、ブロックのlocalrootを処理した後、現在のブロックIDは1だけ増やされます。 ブロックのlocalrootは、最初にブロックIDが割り当てられたブロックのブロックIDを保持することに注意してください。 図8の例では、AのブロックIDは0です。 B、C、D、E、FのブロックIDは1です。 GのブロックIDは2です。 HのブロックIDは3です。 JとKのブロックIDは4です。

8. Summary

8. まとめ

This document specifies IS-IS sub-TLVs for the control of explicit trees in Layer 2 networks. These sub-TLVs can be also used for the distribution of a centrally computed GADAG or MRTs if MFT-FRR is used.

この文書は、レイヤー2ネットワークにおいて明示的ツリーを制御するためのIS-ISサブTLVを規定します。 MFT-FRRを使用する場合、これらのサブTLVは、集中的に計算されたGADAGまたはMRTの配布にも使用できます。

10. Security Considerations

10. セキュリティーに関する考慮事項

This document adds no additional security risks to IS-IS, nor does it provide any additional security for IS-IS when used in a configured environment or a single-operator domain such as a data center. IS-IS PCR is not for zero-configuration environments.

この文書は、設定済みの環境、またはデータセンターのような単一オペレーターのドメインで使用される場合に、IS-ISに新たなセキュリティーリスクを追加することはなく、IS-ISに新たなセキュリティーを提供することもありません。 IS-IS PCRは、ゼロコンフィギュレーション環境向けではありません。

Any mechanism that chooses forwarding paths, and allocates resources to those paths, is potentially vulnerable to attack. The security considerations section of [RFC4655] describes the risks associated with the use of PCE for this purpose and should be referred to. Use of any other means to determine paths should only be used after considering similar concerns.

転送パスを選択し、それらのパスに資源を割り当てる仕組みはいずれも、攻撃に対して脆弱である可能性があります。 [RFC4655]のセキュリティーに関する考慮事項のセクションは、この目的でPCEを使用することに伴うリスクを説明しており、参照すべきです。 パスを決定するためのその他の手段は、同様の懸念を考慮した後でのみ使用すべきです。

Because the mechanism assumed for distributing tree information relies on IS-IS routing, IS-IS routing security considerations (Section 6, [RFC1195]) and mechanisms (e.g., [RFC5310]) used to authenticate peer advertisements apply.

ツリー情報を配布するために想定している仕組みはIS-ISルーティングに依拠しているため、IS-ISルーティングのセキュリティーに関する考慮事項（セクション6、[RFC1195]）と、ピアの広告を認証するために使用される仕組み（たとえば、[RFC5310]）が適用されます。
