RFC 65

Comments on Host-Host Protocol Document No. 1 (S. Crocker - 8/3/70)

RFC 65

ホスト間プロトコル文書第1号へのコメント（S. Crocker - 8/3/70）

Abstract

概要

Page 3. Eliminate marking. Instead, make all regular messages into two message: The first containing just the leader and indicating that the data follows in the second (next) message. Do this both from the source Host to its IMP and from the destination IMP to its Host. Thus, no more hunting for the beginning of the data is necessary. Once this adjustment is made, an additional simplification is available. If the maximum message length is a common multiple of the word sizes of all the computers in the network (perhaps 2880*2 bits), successive messages of long files can be dropped in place without shifting.

3ページ。マーキング（marking）を廃止します。その代わりに、すべての通常のメッセージを2つのメッセージにします。1つ目はリーダー（leader）だけを含み、データが2つ目（次）のメッセージに続くことを示します。これを、送信元のHostからそのIMPへの方向と、宛先のIMPからそのHostへの方向の両方で行います。そうすれば、データの先頭を探し回る必要はもうなくなります。この調整を行えば、さらなる簡素化が可能になります。最大メッセージ長がネットワーク内のすべてのコンピューターのワードサイズの公倍数（おそらく2880*2ビット）であれば、長いファイルの連続するメッセージを、シフトせずにそのまま所定の位置に置くことができます。

Page 4. Control messages should be sent to and from the control socket -- not over the control link. The concept of the control link causes a great big, unnecessary special case.

4ページ。制御メッセージは、制御リンクを通じてではなく、制御ソケットとの間で送受信すべきです。制御リンクという概念は、非常に大きな不要な特殊ケースを生み出します。

Page 5. Assigning sockets permanently to certain network resources should be encouraged and a directory of the socket/resource associations should be available somewhere in the network, perhaps in physical book form at each site.

5ページ。特定のネットワーク資源にソケットを恒久的に割り当てることを奨励すべきであり、ソケットと資源の対応関係のディレクトリーをネットワーク内のどこかで、おそらくは各サイトに物理的な本の形で、利用できるようにすべきです。

Page 6. Links have no Host-Host purpose other than identifying a connection so that socket numbers don't have to be included in all messages and to simplify table look-ups in the NCPs. However, since there are possibly 512 links* with the same number, links don't aid table look-ups very much. Also finding the next available link to a particular destination is very ugly . Therefore, I suggest limiting the number of links to a total of n (where n = 32, 64, or 256 or some other good number) for all destinations. In other words, a particular link is only in use to one destination at a time(actually from one destination at a time since the receiver picks the link to be used for a connection). This change makes picking the next available link very simple and,I feel,is a worthwhile change if only for this reason. The question of simplifying table look-ups is a little more complex. It is easy to use the link directly as an index into tables in the receive portion of the NCP since the receiver picks the link. But a hash table or linear search or something is still necessary in the send portion of the NCP. This too can be fixed with the following changes. Add to STR a pseudo link chosen by the sender. This link is sent in all non-control messages in the 8 bits to the right of the link in the leader. The IMP must preserve these bits and return them with RFNMs and the receiver must use the pseudo link instead of the link in RET and INR. The extra memory necessary to store the pseudo link in the NCP receive tables (which are indexed by link) and the link in the NCP send tables (which are indexed by pseudo link) is certainly less than the overhead necessary to maintain associative tables.

6ページ。リンクには、すべてのメッセージにソケット番号を含めなくて済むようにコネクションを識別することと、NCPでのテーブル検索を簡単にすること以外に、ホスト間（Host-Host）での目的はありません。しかし、同じ番号のリンクが512個*ある可能性があるので、リンクはテーブル検索にはあまり役立ちません。また、特定の宛先に対して次に使用可能なリンクを見つけるのは非常に煩雑です。そこで、リンクの数を、すべての宛先を合わせてn個（n = 32、64、256、またはその他の適当な数）に制限することを提案します。言い換えれば、特定のリンクは一度に1つの宛先に対してだけ使用されます（コネクションに使用するリンクは受信側が選ぶので、実際には一度に1つの宛先からだけ使用されます）。この変更によって、次に使用可能なリンクを選ぶのが非常に簡単になり、この理由だけでも価値のある変更だと私は考えます。テーブル検索の簡素化の問題は、もう少し複雑です。受信側がリンクを選ぶので、NCPの受信部分ではリンクをテーブルのインデックスとして直接使うのは簡単です。しかし、NCPの送信部分では、依然としてハッシュテーブルや線形探索などが必要です。これも次の変更で解決できます。送信側が選ぶ疑似リンク（pseudo link）をSTRに追加します。このリンクは、制御以外のすべてのメッセージで、リーダー内のリンクの右側の8ビットに入れて送られます。IMPはこれらのビットを保持して、RFNMとともに返さなければならず、受信側はRETとINRでリンクの代わりに疑似リンクを使わなければなりません。NCPの受信テーブル（リンクでインデックス付けされます）に疑似リンクを、NCPの送信テーブル（疑似リンクでインデックス付けされます）にリンクを格納するのに必要な追加のメモリーは、連想テーブルを維持するのに必要なオーバーヘッドより確実に小さくなります。

*A destination number is 9 bits.

*宛先番号は9ビットです。

Page 8. The allocate mechanism seems very inconvenient for the receive portion of the NCP to use. The receiver wants the allocation to be used up in units of the receiver's buffer size not in units of sender messages which may be variable length. Otherwise the receiver has a memory compaction problem.

8ページ。割り当て（allocate）の仕組みは、NCPの受信部分にとって非常に使いにくいように思えます。受信側は、割り当てが、可変長かもしれない送信側のメッセージ単位ではなく、受信側のバッファーサイズ単位で使い切られることを望みます。そうでなければ、受信側にメモリーの断片化を解消する（compaction）問題が生じます。

Page 9. The new irregular message to make the "cease" mechanism work are unnecessary, I think. The sender can keep track (probably with a one bit counter) of ALLs and GVBs and ignore GVB 0s for which resume ALLs have already arrived. This the receiver need not know whether the cease has been sent or not.

9ページ。「cease」の仕組みを機能させるための新しい不規則メッセージは、不要だと思います。送信側は、ALLとGVBを（おそらく1ビットのカウンターで）追跡し、再開のALLがすでに到着しているGVB 0を無視できます。こうすれば、受信側はceaseが送られたかどうかを知る必要がありません。

Page 15. If I implemented an NCP, all ERRs would be treated like NOP. As an error control mechanism ERR is complicated and insufficient. Who wants to debug a complicated mechanism which only catches bugs due to the primary mechanism being undebugged. The one error control mechanism I would provide is a receive process to send process acknowledgment on every message. If this is not received for too long, the send process can send the message again if it has been saving it. This acknowledgment catches errors causing message loss at the process/NCP, NCP/NCP, Host/IMP, IMP/IMP, etc. levels. Currently the Host/IMP interface is particularly lacking in useful error controls. I wouldn't worry about kinds of errors check-sums are designed to pick up. If dropped and picked up bits ever become a problem either add hardware to more interfaces or let the receive process not send the process to process acknowledgment if a software checksum does not check.

15ページ。私がNCPを実装するなら、ERRはすべてNOPのように扱うでしょう。エラー制御の仕組みとして、ERRは複雑で不十分です。主たる仕組みのデバッグが済んでいないことによるバグしか捕まえられない複雑な仕組みを、誰がデバッグしたいでしょうか。私が用意するエラー制御の仕組みは、すべてのメッセージについての受信プロセスから送信プロセスへの確認応答の1つだけです。これを長時間受け取らなければ、送信プロセスは、メッセージを保存していればそれを再送できます。この確認応答は、プロセス/NCP、NCP/NCP、Host/IMP、IMP/IMPなどのレベルでメッセージの損失を引き起こすエラーを捕まえます。現在、Host/IMPインターフェイスには、特に有用なエラー制御が欠けています。チェックサムが検出するように設計されている種類のエラーについては、私は心配しないでしょう。ビットの欠落や混入が問題になるようなら、より多くのインターフェイスにハードウェアを追加するか、ソフトウェアのチェックサムが合わない場合に受信プロセスがプロセス間の確認応答を送らないようにすればよいのです。

The page 3 and page 6 comments involve a change to the IMP program. I feel a tiny bit guilty suggesting changes I don't have to implement any more. However, I trust Crowther and Cosell will, as always, resist bad changes while making sensible ones. The page 9 comment is aimed at avoiding a change in the IMP program.

3ページと6ページについてのコメントは、IMPプログラムの変更を伴います。もう自分で実装しなくてよい変更を提案するのは、ほんの少し気がとがめます。しかし、CrowtherとCosellは、いつものように、理にかなった変更は行いながら、悪い変更には抵抗してくれると信じています。9ページについてのコメントは、IMPプログラムの変更を避けることを目的としています。
