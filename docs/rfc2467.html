1. Introduction

1. はじめに

This document specifies the frame format for transmission of IPv6 packets and the method of forming IPv6 link-local addresses and statelessly autoconfigured addresses on FDDI networks. It also specifies the content of the Source/Target Link-layer Address option used in Router Solicitation, Router Advertisement, Neighbor Solicitation, Neighbor Advertisement and Redirect messages when those messages are transmitted on an FDDI network.

この文書は、FDDIネットワーク上でIPv6パケットを伝送するためのフレーム形式と、IPv6のリンクローカルアドレスおよびステートレスに自動設定されるアドレスを形成する方法を規定します。また、ルーター要請、ルーター広告、近隣要請、近隣広告、およびリダイレクトのメッセージがFDDIネットワーク上で送信される場合に、それらのメッセージで使用される送信元/ターゲットリンク層アドレスオプションの内容も規定します。

This document replaces RFC 2019, "Transmission of IPv6 Packets Over FDDI", which will become historic.

この文書は、RFC 2019「Transmission of IPv6 Packets Over FDDI」を置き換えます。RFC 2019は歴史的（historic）な文書になります。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119].

この文書におけるキーワード「MUST」、「MUST NOT」、「REQUIRED」、「SHALL」、「SHALL NOT」、「SHOULD」、「SHOULD NOT」、「RECOMMENDED」、「MAY」、および「OPTIONAL」は、[RFC 2119]で説明されているように解釈されます。

2. Maximum Transmission Unit

2. 最大転送単位

FDDI permits a frame length of 4500 octets (9000 symbols), including at least 22 octets (44 symbols) of Data Link encapsulation when long-format addresses are used. Subtracting 8 octets of LLC/SNAP header, this would, in principle, allow the IPv6 [IPV6] packet in the Information field to be up to 4470 octets. However, it is desirable to allow for the variable sizes and possible future extensions of the MAC header and frame status fields. The default MTU size for IPv6 packets on an FDDI network is therefore 4352 octets. This size may be reduced by a Router Advertisement [DISC] containing an MTU option which specifies a smaller MTU, or by manual configuration of each node. If a Router Advertisement received on an FDDI interface has an MTU option specifying an MTU larger than 4352, or larger than a manually configured value, that MTU option may be logged to system management but must be otherwise ignored.

FDDIでは、長形式のアドレスを使用する場合に少なくとも22オクテット（44シンボル）のデータリンクのカプセル化を含めて、4500オクテット（9000シンボル）のフレーム長が許可されます。LLC/SNAPヘッダーの8オクテットを差し引くと、原理的には、Informationフィールド内のIPv6[IPV6]パケットを最大4470オクテットにすることができます。しかし、MACヘッダーとフレームステータスのフィールドの可変サイズや将来の拡張の可能性を考慮しておくことが望ましいです。そのため、FDDIネットワーク上のIPv6パケットのデフォルトのMTUサイズは4352オクテットです。このサイズは、より小さいMTUを指定するMTUオプションを含むルーター広告[DISC]によって、または各ノードの手動の設定によって縮小される場合があります。FDDIのインターフェイスで受信したルーター広告に、4352より大きい、または手動で設定された値より大きいMTUを指定するMTUオプションがある場合、そのMTUオプションはシステム管理に記録してもかまいませんが、それ以外の点では無視する必要があります。

For purposes of this document, information received from DHCP is considered "manually configured" and the term FDDI includes CDDI.

この文書の目的では、DHCPから受信した情報は「手動で設定された」ものとみなされ、FDDIという用語にはCDDIが含まれます。

3. Frame Format

3. フレーム形式

FDDI provides both synchronous and asynchronous transmission, with the latter class further subdivided by the use of restricted and unrestricted tokens. Only asynchronous transmission with unrestricted tokens is required for FDDI interoperability. Accordingly, IPv6 packets shall be sent in asynchronous frames using unrestricted tokens. The robustness principle dictates that nodes should be able to receive synchronous frames and asynchronous frames sent using restricted tokens.

FDDIは同期と非同期の両方の伝送を提供し、後者のクラスは、制限付きトークンと制限なしトークンの使用によってさらに細分されます。FDDIの相互運用性のために必要なのは、制限なしトークンによる非同期伝送だけです。したがって、IPv6パケットは、制限なしトークンを使用する非同期フレームで送信されることになります。堅牢性の原則により、ノードは、同期フレームと、制限付きトークンを使用して送信された非同期フレームを受信できるべきです。

IPv6 packets are transmitted in LLC/SNAP frames, using long-format (48 bit) addresses. The data field contains the IPv6 header and payload and is followed by the FDDI Frame Check Sequence, Ending Delimiter, and Frame Status symbols.

IPv6パケットは、長形式（48ビット）のアドレスを使用して、LLC/SNAPフレームで伝送されます。データフィールドにはIPv6ヘッダーとペイロードが含まれ、その後にFDDIのフレームチェックシーケンス、終了デリミター、およびフレームステータスのシンボルが続きます。

FDDI Header Fields:

FDDIヘッダーのフィールド：

FC
The Frame Code must be in the range 50 to 57 hexadecimal, inclusive, with the three low order bits indicating the frame priority.
DSAP, SSAP
Both the DSAP and SSAP fields shall contain the value AA hexadecimal, indicating SNAP encapsulation.
CTL
The Control field shall be set to 03 hexadecimal, indicating Unnumbered Information.
OUI
The Organizationally Unique Identifier shall be set to 000000 hexadecimal.
Ethertype
The Ethernet protocol type ("ethertype") shall be set to the value 86DD hexadecimal.
FC
フレームコードは、16進数で50から57まで（両端を含む）の範囲になければならず、下位3ビットはフレームの優先度を示します。
DSAP, SSAP
DSAPフィールドとSSAPフィールドの両方に、SNAPカプセル化を示す16進数の値AAが含まれることになります。
CTL
制御フィールドは、番号なし情報（Unnumbered Information）を示す16進数の03に設定されることになります。
OUI
組織固有識別子（OUI）は、16進数の000000に設定されることになります。
Ethertype
イーサネットのプロトコルタイプ（「ethertype」）は、16進数の値86DDに設定されることになります。

4. Interaction with Bridges

4. ブリッジとの相互作用

802.1d MAC bridges which connect different media, for example Ethernet and FDDI, have become very widespread. Some of them do IPv4 packet fragmentation and/or support IPv4 Path MTU discovery [RFC 1981], many others do not, or do so incorrectly. Use of IPv6 in a bridged mixed-media environment must not depend on support from MAC bridges, unless those bridges are known to correctly implement IPv6 Path MTU Discovery [RFC 1981], [ICMPV6].

たとえばイーサネットとFDDIのような異なる媒体を接続する802.1dのMACブリッジは、非常に広く普及しています。その一部はIPv4パケットの断片化を行ったり、IPv4のパスMTU探索[RFC 1981]をサポートしたりしますが、多くはそれを行わないか、正しく行いません。混在した媒体がブリッジで接続された環境でのIPv6の使用は、MACブリッジがIPv6のパスMTU探索[RFC 1981]、[ICMPV6]を正しく実装していることがわかっていない限り、MACブリッジによるサポートに依存してはいけません。

For correct operation when mixed media are bridged together by bridges which do not support IPv6 Path MTU Discovery, the smallest MTU of all the media must be advertised by routers in an MTU option. If there are no routers present, this MTU must be manually configured in each node which is connected to a medium with a default MTU larger than the smallest MTU.

IPv6のパスMTU探索をサポートしないブリッジによって混在した媒体がブリッジされている場合に正しく動作するためには、すべての媒体の最小のMTUを、ルーターがMTUオプションで広告する必要があります。ルーターが存在しない場合は、デフォルトのMTUが最小のMTUより大きい媒体に接続されている各ノードで、このMTUを手動で設定する必要があります。

The OUI of the FDDI MAC address (the first three octets) becomes the company_id of the EUI-64 (the first three octets). The fourth and fifth octets of the EUI are set to the fixed value FFFE hexadecimal. The last three octets of the FDDI MAC address become the last three octets of the EUI-64.

FDDIのMACアドレスのOUI（最初の3オクテット）は、EUI-64のcompany_id（最初の3オクテット）になります。EUIの4番目と5番目のオクテットは、16進数の固定値FFFEに設定されます。FDDIのMACアドレスの最後の3オクテットは、EUI-64の最後の3オクテットになります。

The Interface Identifier is then formed from the EUI-64 by complementing the "Universal/Local" (U/L) bit, which is the next-to- lowest order bit of the first octet of the EUI-64. For further discussion on this point, see [ETHER] and [AARCH].

次に、EUI-64の最初のオクテットの下位から2番目のビットである「Universal/Local」（U/L）ビットを反転することで、EUI-64からインターフェイス識別子が形成されます。この点についてのさらなる議論は、[ETHER]と[AARCH]を参照してください。

A different MAC address set manually or by software should not be used to derive the Interface Identifier. If such a MAC address must be used, its global uniqueness property should be reflected in the value of the U/L bit.

手動またはソフトウェアによって設定された別のMACアドレスを、インターフェイス識別子の導出に使用すべきではありません。そのようなMACアドレスを使用しなければならない場合は、そのグローバルな一意性の性質をU/Lビットの値に反映すべきです。

An IPv6 address prefix used for stateless autoconfiguration [ACONF] of an FDDI interface must have a length of 64 bits.

FDDIのインターフェイスのステートレスな自動設定[ACONF]に使用されるIPv6アドレスのプレフィックスは、64ビットの長さを持つ必要があります。

6. Link-Local Addresses

6. リンクローカルアドレス

The IPv6 link-local address [AARCH] for an FDDI interface is formed by appending the Interface Identifier, as defined above, to the prefix FE80::/64.

8. Address Mapping -- Multicast

8. アドレスのマッピング -- マルチキャスト

An IPv6 packet with a multicast destination address DST, consisting of the sixteen octets DST[1] through DST[16], is transmitted to the FDDI multicast address whose first two octets are the value 3333 hexadecimal and whose last four octets are the last four octets of DST.

DST[1]からDST[16]までの16オクテットからなるマルチキャストの宛先アドレスDSTを持つIPv6パケットは、最初の2オクテットが16進数の値3333で、最後の4オクテットがDSTの最後の4オクテットであるFDDIのマルチキャストアドレスに送信されます。

9. Differences From RFC 2019

9. RFC 2019との違い

The following are the functional differences between this specification and RFC 2019.

この仕様とRFC 2019との機能上の違いは次のとおりです。

"FDDI adjacency detection" has been removed, due to recent work in IEEE 802.1p.

IEEE 802.1pにおける最近の作業により、「FDDI隣接検出（FDDI adjacency detection）」は削除されました。

The Address Token, which was a node's 48-bit MAC address, is replaced with the Interface Identifier, which is 64 bits in length and based on the EUI-64 format [EUI64]. An IEEE-defined mapping exists from 48-bit MAC addresses to EUI-64 form.

ノードの48ビットのMACアドレスであったアドレストークン（Address Token）は、長さが64ビットでEUI-64形式[EUI64]に基づくインターフェイス識別子に置き換えられました。48ビットのMACアドレスからEUI-64形式へのIEEEが定義したマッピングが存在します。

A prefix used for stateless autoconfiguration must now be 64 bits long rather than 80. The link-local prefix is also shortened to 64 bits.

ステートレスな自動設定に使用されるプレフィックスは、80ビットではなく64ビットの長さでなければならなくなりました。リンクローカルプレフィックスも64ビットに短縮されました。

10. Security Considerations

10. セキュリティーに関する考慮事項

The method of derivation of Interface Identifiers from MAC addresses is intended to preserve global uniqueness when possible. However, there is no protection from duplication through accident or forgery.

MACアドレスからインターフェイス識別子を導出する方法は、可能な場合にはグローバルな一意性を保つことを意図しています。しかし、偶然や偽造による重複からの保護はありません。
