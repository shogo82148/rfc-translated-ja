User-based Security Model (USM) for version 3 of the Simple Network Management Protocol (SNMPv3)

RFC 2274

簡易ネットワーク管理プロトコルバージョン3（SNMPv3）のためのユーザーベースセキュリティーモデル（USM）

Abstract

概要

This document describes the User-based Security Model (USM) for SNMP version 3 for use in the SNMP architecture [RFC2271]. It defines the Elements of Procedure for providing SNMP message level security. This document also includes a MIB for remotely monitoring/managing the configuration parameters for this Security Model.

この文書では、SNMPアーキテクチャー [RFC2271] で使用するための、SNMPバージョン3のユーザーベースセキュリティーモデル（USM）について説明します。この文書は、SNMPのメッセージレベルのセキュリティーを提供するための手順要素を定義します。また、この文書には、このセキュリティーモデルの設定パラメーターをリモートで監視・管理するためのMIBも含まれています。

1. Introduction

1. はじめに

The Architecture for describing Internet Management Frameworks [RFC2271] describes that an SNMP engine is composed of:

インターネット管理フレームワークを記述するためのアーキテクチャー [RFC2271] では、SNMPエンジンが次のもので構成されると述べています。

  1. a Dispatcher
  2. a Message Processing Subsystem,
  3. a Security Subsystem, and
  4. an Access Control Subsystem.
  1. ディスパッチャー
  2. メッセージ処理サブシステム
  3. セキュリティーサブシステム
  4. アクセス制御サブシステム

Applications make use of the services of these subsystems.

アプリケーションは、これらのサブシステムのサービスを利用します。

It is important to understand the SNMP architecture and the terminology of the architecture to understand where the Security Model described in this document fits into the architecture and interacts with other subsystems within the architecture. The reader is expected to have read and understood the description of the SNMP architecture, as defined in [RFC2271].

この文書で説明するセキュリティーモデルがアーキテクチャーのどこに位置し、アーキテクチャー内の他のサブシステムとどのように相互作用するかを理解するには、SNMPアーキテクチャーとその用語を理解することが重要です。読者は、[RFC2271] で定義されているSNMPアーキテクチャーの説明を読み、理解していることが期待されます。

This memo [RFC2274] describes the User-based Security Model as it is used within the SNMP Architecture. The main idea is that we use the traditional concept of a user (identified by a userName) with which to associate security information.

このメモ[RFC2274]では、SNMPアーキテクチャー内で使用されるユーザーベースセキュリティーモデルについて説明します。主なアイデアは、従来の（userNameによって識別される）ユーザーという概念を使用し、それにセキュリティー情報を関連付けることです。

This memo describes the use of HMAC-MD5-96 and HMAC-SHA-96 as the authentication protocols and the use of CBC-DES as the privacy protocol. The User-based Security Model however allows for other such protocols to be used instead of or concurrent with these protocols. Therefore, the description of HMAC-MD5-96, HMAC-SHA-96 and CBC-DES are in separate sections to reflect their self-contained nature and to indicate that they can be replaced or supplemented in the future.

このメモでは、認証プロトコルとしてHMAC-MD5-96とHMAC-SHA-96を使用し、プライバシープロトコルとしてCBC-DESを使用することについて説明します。ただし、ユーザーベースセキュリティーモデルでは、これらのプロトコルの代わりに、またはこれらのプロトコルと同時に、他のそのようなプロトコルを使用することもできます。そのため、HMAC-MD5-96、HMAC-SHA-96、CBC-DESの説明は、それらが自己完結的な性質を持つことを反映し、将来置き換えたり補完したりできることを示すために、別々のセクションにしています。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119].

この文書におけるキーワード「MUST」、「MUST NOT」、「REQUIRED」、「SHALL」、「SHALL NOT」、「SHOULD」、「SHOULD NOT」、「RECOMMENDED」、「MAY」、「OPTIONAL」は、[RFC2119] で説明されているように解釈されます。

1.1. Threats

1.1. 脅威

Several of the classical threats to network protocols are applicable to the network management problem and therefore would be applicable to any SNMP Security Model. Other threats are not applicable to the network management problem. This section discusses principal threats, secondary threats, and threats which are of lesser importance.

ネットワークプロトコルに対する古典的な脅威のいくつかはネットワーク管理の問題にも当てはまり、したがってあらゆるSNMPセキュリティーモデルにも当てはまります。その他の脅威はネットワーク管理の問題には当てはまりません。このセクションでは、主要な脅威、二次的な脅威、およびそれほど重要でない脅威について説明します。

The principal threats against which this SNMP Security Model should provide protection are:

このSNMPセキュリティーモデルが保護を提供すべき主要な脅威は、次のとおりです。

Modification of Information
The modification threat is the danger that some unauthorized entity may alter in-transit SNMP messages generated on behalf of an authorized user in such a way as to effect unauthorized management operations, including falsifying the value of an object.
Masquerade
The masquerade threat is the danger that management operations not authorized for some user may be attempted by assuming the identity of another user that has the appropriate authorizations.
情報の改変（Modification of Information）
改変の脅威とは、権限のないエンティティーが、権限のあるユーザーに代わって生成された転送中のSNMPメッセージを改変し、オブジェクトの値の改ざんを含む、権限のない管理操作を引き起こす危険です。
なりすまし（Masquerade）
なりすましの脅威とは、あるユーザーに許可されていない管理操作が、適切な権限を持つ別のユーザーの身元を装うことによって試みられる危険です。

Two secondary threats are also identified. The Security Model defined in this memo provides limited protection against:

2つの二次的な脅威も識別されています。このメモで定義するセキュリティーモデルは、次のものに対して限定的な保護を提供します。

Disclosure
The disclosure threat is the danger of eavesdropping on the exchanges between managed agents and a management station. Protecting against this threat may be required as a matter of local policy.
Message Stream Modification
The SNMP protocol is typically based upon a connection-less transport service which may operate over any sub-network service. The re-ordering, delay or replay of messages can and does occur through the natural operation of many such sub-network services. The message stream modification threat is the danger that messages may be maliciously re-ordered, delayed or replayed to an extent which is greater than can occur through the natural operation of a sub-network service, in order to effect unauthorized management operations.
漏洩（Disclosure）
漏洩の脅威とは、管理対象エージェントと管理ステーションの間のやり取りが盗聴される危険です。この脅威に対する保護は、ローカルポリシーの問題として必要になる場合があります。
メッセージストリームの改変（Message Stream Modification）
SNMPプロトコルは通常、あらゆるサブネットワークサービス上で動作しうるコネクションレスのトランスポートサービスに基づいています。メッセージの順序の入れ替え、遅延、リプレイは、多くのそのようなサブネットワークサービスの自然な動作によって起こりうるし、実際に起こります。メッセージストリームの改変の脅威とは、権限のない管理操作を引き起こすために、サブネットワークサービスの自然な動作によって起こりうる以上の程度で、メッセージが悪意を持って順序を入れ替えられたり、遅延させられたり、リプレイされたりする危険です。

There are at least two threats that an SNMP Security Model need not protect against. The security protocols defined in this memo do not provide protection against:

SNMPセキュリティーモデルが保護する必要のない脅威が、少なくとも2つあります。このメモで定義するセキュリティープロトコルは、次のものに対する保護を提供しません。

Denial of Service
This SNMP Security Model does not attempt to address the broad range of attacks by which service on behalf of authorized users is denied. Indeed, such denial-of-service attacks are in many cases indistinguishable from the type of network failures with which any viable network management protocol must cope as a matter of course.
Traffic Analysis
This SNMP Security Model does not attempt to address traffic analysis attacks. Indeed, many traffic patterns are predictable - devices may be managed on a regular basis by a relatively small number of management applications - and therefore there is no significant advantage afforded by protecting against traffic analysis.
サービス拒否（Denial of Service）
このSNMPセキュリティーモデルは、権限のあるユーザーに代わるサービスが拒否される広範な攻撃に対処しようとはしません。実際、このようなサービス拒否攻撃は、多くの場合、実用的なネットワーク管理プロトコルであれば当然対処しなければならない種類のネットワーク障害と区別できません。
トラフィック分析（Traffic Analysis）
このSNMPセキュリティーモデルは、トラフィック分析攻撃に対処しようとはしません。実際、多くのトラフィックパターンは予測可能であり（デバイスは比較的少数の管理アプリケーションによって定期的に管理される場合があります）、したがってトラフィック分析から保護することで得られる大きな利点はありません。

1.2. Goals and Constraints

1.2. 目標と制約

Based on the foregoing account of threats in the SNMP network management environment, the goals of this SNMP Security Model are as follows.

SNMPネットワーク管理環境における脅威についての前述の説明に基づき、このSNMPセキュリティーモデルの目標は次のとおりです。

  1. Provide for verification that each received SNMP message has not been modified during its transmission through the network.
  2. Provide for verification of the identity of the user on whose behalf a received SNMP message claims to have been generated.
  3. Provide for detection of received SNMP messages, which request or contain management information, whose time of generation was not recent.
  4. Provide, when necessary, that the contents of each received SNMP message are protected from disclosure.
  1. 受信した各SNMPメッセージが、ネットワークを通じた伝送中に改変されていないことを検証できるようにする。
  2. 受信したSNMPメッセージが、そのユーザーに代わって生成されたと主張しているユーザーの身元を検証できるようにする。
  3. 管理情報を要求する、または管理情報を含む受信SNMPメッセージのうち、生成時刻が最近ではないものを検出できるようにする。
  4. 必要な場合に、受信した各SNMPメッセージの内容が漏洩から保護されるようにする。

In addition to the principal goal of supporting secure network management, the design of this SNMP Security Model is also influenced by the following constraints:

安全なネットワーク管理をサポートするという主要な目標に加えて、このSNMPセキュリティーモデルの設計は、次の制約からも影響を受けています。

  1. When the requirements of effective management in times of network stress are inconsistent with those of security, the design should prefer the former.
  2. Neither the security protocol nor its underlying security mechanisms should depend upon the ready availability of other network services (e.g., Network Time Protocol (NTP) or key management protocols).
  3. A security mechanism should entail no changes to the basic SNMP network management philosophy.
  1. ネットワークに負荷がかかっているときの効果的な管理の要件がセキュリティーの要件と相容れない場合、設計は前者を優先すべきである。
  2. セキュリティープロトコルも、その基盤となるセキュリティーの仕組みも、他のネットワークサービス（たとえば、ネットワークタイムプロトコル（NTP）や鍵管理プロトコル）がすぐに利用できることに依存すべきではない。
  3. セキュリティーの仕組みは、SNMPネットワーク管理の基本的な考え方に変更を伴うべきではない。

1.3. Security Services

1.3. セキュリティーサービス

The security services necessary to support the goals of this SNMP Security Model are as follows:

このSNMPセキュリティーモデルの目標をサポートするために必要なセキュリティーサービスは次のとおりです。

Data Integrity
is the provision of the property that data has not been altered or destroyed in an unauthorized manner, nor have data sequences been altered to an extent greater than can occur non-maliciously.
Data Origin Authentication
is the provision of the property that the claimed identity of the user on whose behalf received data was originated is corroborated.
Data Confidentiality
is the provision of the property that information is not made available or disclosed to unauthorized individuals, entities, or processes.
Message timeliness and limited replay protection
is the provision of the property that a message whose generation time is outside of a specified time window is not accepted. Note that message reordering is not dealt with and can occur in normal conditions too.
データの完全性（Data Integrity）
データが権限のない方法で改変または破壊されておらず、データの並びが悪意なく起こりうる以上の程度で改変されていないという性質を提供することです。
データ発信元の認証（Data Origin Authentication）
受信したデータがそのユーザーに代わって発信されたと主張されているユーザーの身元が裏付けられるという性質を提供することです。
データの機密性（Data Confidentiality）
情報が、権限のない個人、エンティティー、プロセスに利用可能にされたり開示されたりしないという性質を提供することです。
メッセージの適時性と限定的なリプレイ保護（Message timeliness and limited replay protection）
生成時刻が指定された時間枠の外にあるメッセージは受け入れられないという性質を提供することです。メッセージの順序の入れ替えには対処しておらず、通常の状況でも起こりうることに注意してください。

For the protocols specified in this memo, it is not possible to assure the specific originator of a received SNMP message; rather, it is the user on whose behalf the message was originated that is authenticated.

このメモで規定するプロトコルでは、受信したSNMPメッセージの具体的な発信者を保証することはできません。認証されるのは、そのユーザーに代わってメッセージが発信されたユーザーです。

For these protocols, it not possible to obtain data integrity without data origin authentication, nor is it possible to obtain data origin authentication without data integrity. Further, there is no provision for data confidentiality without both data integrity and data origin authentication.

これらのプロトコルでは、データ発信元の認証なしにデータの完全性を得ることはできず、データの完全性なしにデータ発信元の認証を得ることもできません。さらに、データの完全性とデータ発信元の認証の両方がなければ、データの機密性は提供されません。

The security protocols used in this memo are considered acceptably secure at the time of writing. However, the procedures allow for new authentication and privacy methods to be specified at a future time if the need arises.

このメモで使用するセキュリティープロトコルは、執筆時点では十分に安全であると考えられています。ただし、手順は、必要が生じた場合に、将来新しい認証やプライバシーの方法を規定できるようにしています。

1.4. Module Organization

1.4. モジュールの構成

The security protocols defined in this memo are split in three different modules and each has its specific responsibilities such that together they realize the goals and security services described above:

このメモで定義するセキュリティープロトコルは3つの異なるモジュールに分かれており、それぞれが固有の責任を持ち、全体として上記の目標とセキュリティーサービスを実現します。

  • The authentication module MUST provide for:

    • Data Integrity,
    • Data Origin Authentication

  • The timeliness module MUST provide for:

    • Protection against message delay or replay (to an extent greater than can occur through normal operation)

    The privacy module MUST provide for

    • Protection against disclosure of the message payload.

  • 認証モジュールは、次のものを提供しなければなりません（MUST）。

    • データの完全性
    • データ発信元の認証

  • 適時性モジュールは、次のものを提供しなければなりません（MUST）。

    • （通常の動作によって起こりうる以上の程度の）メッセージの遅延やリプレイに対する保護

    プライバシーモジュールは、次のものを提供しなければなりません（MUST）。

    • メッセージのペイロードの漏洩に対する保護

The timeliness module is fixed for the User-based Security Model while there is provision for multiple authentication and/or privacy modules, each of which implements a specific authentication or privacy protocol respectively.

適時性モジュールはユーザーベースセキュリティーモデルに固定されていますが、認証モジュールとプライバシーモジュールは複数用意することができ、それぞれが特定の認証プロトコルまたはプライバシープロトコルを実装します。

1.4.1. Timeliness Module

1.4.1. 適時性モジュール

Section 3 (Elements of Procedure) uses the timeliness values in an SNMP message to do timeliness checking. The timeliness check is only performed if authentication is applied to the message. Since the complete message is checked for integrity, we can assume that the timeliness values in a message that passes the authentication module are trustworthy.

セクション3（手順要素）では、SNMPメッセージ内の適時性の値を使用して適時性の確認を行います。適時性の確認は、メッセージに認証が適用されている場合にのみ行われます。メッセージ全体の完全性が確認されるため、認証モジュールを通過したメッセージ内の適時性の値は信頼できると想定できます。

1.4.2. Authentication Protocol

1.4.2. 認証プロトコル

Section 6 describes the HMAC-MD5-96 authentication protocol which is the first authentication protocol that MUST be supported with the User-based Security Model. Section 7 describes the HMAC-SHA-96 authentication protocol which is another authentication protocol that SHOULD be supported with the User-based Security Model. In the future additional or replacement authentication protocols may be defined as new needs arise.

セクション6では、ユーザーベースセキュリティーモデルでサポートしなければならない（MUST）最初の認証プロトコルであるHMAC-MD5-96認証プロトコルについて説明します。セクション7では、もう1つの認証プロトコルであるHMAC-SHA-96認証プロトコルについて説明します。この認証プロトコルも、ユーザーベースセキュリティーモデルでサポートすべきです（SHOULD）。将来、新たな必要が生じれば、追加の認証プロトコルや代替の認証プロトコルが定義されるかもしれません。

The User-based Security Model prescribes that, if authentication is used, then the complete message is checked for integrity in the authentication module.

ユーザーベースセキュリティーモデルでは、認証が使用される場合、認証モジュールでメッセージ全体の完全性が確認されると規定しています。

For a message to be authenticated, it needs to pass authentication check by the authentication module and the timeliness check which is a fixed part of this User-based Security model.

メッセージが認証されるためには、認証モジュールによる認証の確認と、このユーザーベースセキュリティーモデルに固定的に含まれる適時性の確認に合格する必要があります。

1.4.3. Privacy Protocol

1.4.3. プライバシープロトコル

Section 8 describes the CBC-DES Symmetric Encryption Protocol which is the first privacy protocol to be used with the User-based Security Model. In the future additional or replacement privacy protocols may be defined as new needs arise.

セクション8では、ユーザーベースセキュリティーモデルで使用される最初のプライバシープロトコルであるCBC-DES対称暗号化プロトコルについて説明します。将来、新たな必要が生じれば、追加のプライバシープロトコルや代替のプライバシープロトコルが定義されるかもしれません。

The User-based Security Model prescribes that the scopedPDU is protected from disclosure when a message is sent with privacy.

ユーザーベースセキュリティーモデルでは、メッセージがプライバシー付きで送信される場合、scopedPDUは漏洩から保護されると規定しています。

The User-based Security Model also prescribes that a message needs to be authenticated if privacy is in use.

ユーザーベースセキュリティーモデルではまた、プライバシーが使用されている場合はメッセージが認証される必要があると規定しています。

1.5. Protection against Message Replay, Delay and Redirection

1.5. メッセージのリプレイ、遅延、リダイレクトに対する保護

1.5.1. Authoritative SNMP engine

1.5.1. 権威SNMPエンジン

In order to protect against message replay, delay and redirection, one of the SNMP engines involved in each communication is designated to be the authoritative SNMP engine. When an SNMP message contains a payload which expects a response (for example a Get, GetNext, GetBulk, Set or Inform PDU), then the receiver of such messages is authoritative. When an SNMP message contains a payload which does not expect a response (for example an SNMPv2-Trap, Response or Report PDU), then the sender of such a message is authoritative.

メッセージのリプレイ、遅延、リダイレクトから保護するために、各通信に関与するSNMPエンジンのうちの1つが権威SNMPエンジンとして指定されます。SNMPメッセージに応答を期待するペイロード（たとえば、Get、GetNext、GetBulk、Set、またはInformのPDU）が含まれている場合、そのようなメッセージの受信者が権威を持ちます。SNMPメッセージに応答を期待しないペイロード（たとえば、SNMPv2-Trap、Response、またはReportのPDU）が含まれている場合、そのようなメッセージの送信者が権威を持ちます。

1.5.2. Mechanisms

1.5.2. 仕組み

The following mechanisms are used:

次の仕組みが使用されます。

  1. To protect against the threat of message delay or replay (to an extent greater than can occur through normal operation), a set of timeliness indicators (for the authoritative SNMP engine) are included in each message generated. An SNMP engine evaluates the timeliness indicators to determine if a received message is recent. An SNMP engine may evaluate the timeliness indicators to ensure that a received message is at least as recent as the last message it received from the same source. A non-authoritative SNMP engine uses received authentic messages to advance its notion of the timeliness indicators at the remote authoritative source.

    An SNMP engine MUST also use a mechanism to match incoming Responses to outstanding Requests and it MUST drop any Responses that do not match an outstanding request. For example, a msgID can be inserted in every message to cater for this functionality.

    These mechanisms provide for the detection of authenticated messages whose time of generation was not recent.

    This protection against the threat of message delay or replay does not imply nor provide any protection against unauthorized deletion or suppression of messages. Also, an SNMP engine may not be able to detect message reordering if all the messages involved are sent within the Time Window interval. Other mechanisms defined independently of the security protocol can also be used to detect the re-ordering replay, deletion, or suppression of messages containing Set operations (e.g., the MIB variable snmpSetSerialNo [RFC1907]).

  2. Verification that a message sent to/from one authoritative SNMP engine cannot be replayed to/as-if-from another authoritative SNMP engine.

    Included in each message is an identifier unique to the authoritative SNMP engine associated with the sender or intended recipient of the message.

    A Report, Response or Trap message sent by an authoritative SNMP engine to one non-authoritative SNMP engine can potentially be replayed to another non-authoritative SNMP engine. The latter non-authoritative SNMP engine might (if it knows about the same userName with the same secrets at the authoritative SNMP engine) as a result update its notion of timeliness indicators of the authoritative SNMP engine, but that is not considered a threat. In this case, A Report or Response message will be discarded by the Message Processing Model, because there should not be an outstanding Request message. A Trap will possibly be accepted. Again, that is not considered a threat, because the communication was authenticated and timely. It is as if the authoritative SNMP engine was configured to start sending Traps to the second SNMP engine, which theoretically can happen without the knowledge of the second SNMP engine anyway. Anyway, the second SNMP engine may not expect to receive this Trap, but is allowed to see the management information contained in it.

  3. Detection of messages which were not recently generated.

    A set of time indicators are included in the message, indicating the time of generation. Messages without recent time indicators are not considered authentic. In addition, an SNMP engine MUST drop any Responses that do not match an outstanding request. This however is the responsibility of the Message Processing Model.

  1. （通常の動作によって起こりうる以上の程度の）メッセージの遅延やリプレイの脅威から保護するために、生成される各メッセージに（権威SNMPエンジンについての）一連の適時性の指標が含まれます。SNMPエンジンは、適時性の指標を評価して、受信したメッセージが最近のものであるかどうかを判断します。SNMPエンジンは、適時性の指標を評価して、受信したメッセージが、同じ送信元から最後に受信したメッセージと少なくとも同じくらい新しいことを確認できます。非権威SNMPエンジンは、受信した真正なメッセージを使用して、リモートの権威ある送信元における適時性の指標についての認識を進めます。

    SNMPエンジンはまた、受信した応答を未処理の要求と照合する仕組みを使用しなければなりません（MUST）。また、未処理の要求と一致しない応答はすべて破棄しなければなりません（MUST）。たとえば、この機能に対応するために、すべてのメッセージにmsgIDを挿入できます。

    これらの仕組みにより、生成時刻が最近ではない認証済みメッセージを検出できます。

    メッセージの遅延やリプレイの脅威に対するこの保護は、メッセージの権限のない削除や抑止に対する保護を意味するものでも、提供するものでもありません。また、関係するすべてのメッセージが時間枠の間隔内に送信された場合、SNMPエンジンはメッセージの順序の入れ替えを検出できないかもしれません。セキュリティープロトコルとは独立に定義された他の仕組みを使用して、Set操作を含むメッセージの順序の入れ替え、リプレイ、削除、抑止を検出することもできます（たとえば、MIB変数snmpSetSerialNo [RFC1907]）。

  2. ある権威SNMPエンジンとの間で送受信されたメッセージを、別の権威SNMPエンジンへ、または別の権威SNMPエンジンからのものとしてリプレイできないことの検証。

    各メッセージには、メッセージの送信者または意図された受信者に関連付けられた権威SNMPエンジンに固有の識別子が含まれます。

    権威SNMPエンジンがある非権威SNMPエンジンに送信したReport、Response、またはTrapのメッセージは、別の非権威SNMPエンジンにリプレイされる可能性があります。後者の非権威SNMPエンジンは、（権威SNMPエンジンにおける同じ秘密情報を持つ同じuserNameを知っている場合）その結果として権威SNMPエンジンの適時性の指標についての認識を更新するかもしれませんが、それは脅威とはみなされません。この場合、未処理の要求メッセージは存在しないはずなので、ReportやResponseのメッセージはメッセージ処理モデルによって破棄されます。Trapは受け入れられる可能性があります。ここでも、通信は認証されており適時であるため、それは脅威とはみなされません。これは、権威SNMPエンジンが2番目のSNMPエンジンにTrapの送信を開始するように設定されたかのようなものであり、理論的には、いずれにせよ2番目のSNMPエンジンが知らないうちに起こりうることです。いずれにせよ、2番目のSNMPエンジンはこのTrapを受信することを期待していないかもしれませんが、その中に含まれる管理情報を見ることは許可されています。

  3. 最近生成されたものではないメッセージの検出。

    メッセージには生成時刻を示す一連の時刻指標が含まれます。最近の時刻指標を持たないメッセージは真正とはみなされません。さらに、SNMPエンジンは、未処理の要求と一致しない応答をすべて破棄しなければなりません（MUST）。ただし、これはメッセージ処理モデルの責任です。

This memo allows the same user to be defined on multiple SNMP engines. Each SNMP engine maintains a value, snmpEngineID, which uniquely identifies the SNMP engine. This value is included in each message sent to/from the SNMP engine that is authoritative (see section 1.5.1). On receipt of a message, an authoritative SNMP engine checks the value to ensure that it is the intended recipient, and a non-authoritative SNMP engine uses the value to ensure that the message is processed using the correct state information.

このメモでは、同じユーザーを複数のSNMPエンジンで定義することを認めています。各SNMPエンジンは、そのSNMPエンジンを一意に識別するsnmpEngineIDという値を保持しています。この値は、権威を持つSNMPエンジンとの間で送受信される各メッセージに含まれます（セクション1.5.1を参照）。メッセージを受信すると、権威SNMPエンジンはその値を確認して自身が意図された受信者であることを確認し、非権威SNMPエンジンはその値を使用して、メッセージが正しい状態情報を使用して処理されるようにします。

Each SNMP engine maintains two values, snmpEngineBoots and snmpEngineTime, which taken together provide an indication of time at that SNMP engine. Both of these values are included in an authenticated message sent to/received from that SNMP engine. On receipt, the values are checked to ensure that the indicated timeliness value is within a Time Window of the current time. The Time Window represents an administrative upper bound on acceptable delivery delay for protocol messages.

各SNMPエンジンは、snmpEngineBootsとsnmpEngineTimeという2つの値を保持しており、これらを合わせるとそのSNMPエンジンにおける時刻を示します。これらの値はどちらも、そのSNMPエンジンとの間で送受信される認証済みメッセージに含まれます。受信時に、これらの値を確認して、示された適時性の値が現在時刻の時間枠内にあることを確認します。時間枠は、プロトコルメッセージの許容できる配送遅延の管理上の上限を表します。

For an SNMP engine to generate a message which an authoritative SNMP engine will accept as authentic, and to verify that a message received from that authoritative SNMP engine is authentic, such an SNMP engine must first achieve timeliness synchronization with the authoritative SNMP engine. See section 2.3.

SNMPエンジンが、権威SNMPエンジンが真正として受け入れるメッセージを生成し、またその権威SNMPエンジンから受信したメッセージが真正であることを検証するためには、そのSNMPエンジンはまず権威SNMPエンジンとの適時性の同期を達成しなければなりません。セクション2.3を参照してください。

2. Elements of the Model

2. モデルの要素

This section contains definitions required to realize the security model defined by this memo.

このセクションには、このメモで定義するセキュリティーモデルを実現するために必要な定義が含まれています。

2.1. User-based Security Model Users

2.1. ユーザーベースセキュリティーモデルのユーザー

Management operations using this Security Model make use of a defined set of user identities. For any user on whose behalf management operations are authorized at a particular SNMP engine, that SNMP engine must have knowledge of that user. An SNMP engine that wishes to communicate with another SNMP engine must also have knowledge of a user known to that engine, including knowledge of the applicable attributes of that user.

このセキュリティーモデルを使用する管理操作は、定義されたユーザーアイデンティティーの集合を利用します。特定のSNMPエンジンで、あるユーザーに代わって管理操作が許可されている場合、そのSNMPエンジンはそのユーザーについて知っていなければなりません。別のSNMPエンジンと通信したいSNMPエンジンも、そのエンジンが知っているユーザーについて、そのユーザーの該当する属性を含めて知っていなければなりません。

A user and its attributes are defined as follows:

ユーザーとその属性は、次のように定義されます。

userName
A string representing the name of the user.
securityName
A human-readable string representing the user in a format that is Security Model independent.
authProtocol
An indication of whether messages sent on behalf of this user can be authenticated, and if so, the type of authentication protocol which is used. Two such protocols are defined in this memo: - the HMAC-MD5-96 authentication protocol. - the HMAC-SHA-96 authentication protocol.
authKey
If messages sent on behalf of this user can be authenticated, the (private) authentication key for use with the authentication protocol. Note that a user's authentication key will normally be different at different authoritative SNMP engines. The authKey is not accessible via SNMP. The length requirements of the authKey are defined by the authProtocol in use.
authKeyChange and authOwnKeyChange
The only way to remotely update the authentication key. Does that in a secure manner, so that the update can be completed without the need to employ privacy protection.
privProtocol
An indication of whether messages sent on behalf of this user can be protected from disclosure, and if so, the type of privacy protocol which is used. One such protocol is defined in this memo: the CBC-DES Symmetric Encryption Protocol.
privKey
If messages sent on behalf of this user can be en/decrypted, the (private) privacy key for use with the privacy protocol. Note that a user's privacy key will normally be different at different authoritative SNMP engines. The privKey is not accessible via SNMP. The length requirements of the privKey are defined by the privProtocol in use.
privKeyChange and privOwnKeyChange
The only way to remotely update the encryption key. Does that in a secure manner, so that the update can be completed without the need to employ privacy protection.
userName
ユーザーの名前を表す文字列。
securityName
セキュリティーモデルに依存しない形式でユーザーを表す、人間が読める文字列。
authProtocol
このユーザーに代わって送信されるメッセージを認証できるかどうか、また認証できる場合は使用される認証プロトコルの種類を示すもの。このメモでは、そのようなプロトコルが2つ定義されています。HMAC-MD5-96認証プロトコルとHMAC-SHA-96認証プロトコルです。
authKey
このユーザーに代わって送信されるメッセージを認証できる場合に、認証プロトコルで使用する（秘密の）認証鍵。ユーザーの認証鍵は通常、権威SNMPエンジンごとに異なることに注意してください。authKeyはSNMPを介してアクセスすることはできません。authKeyの長さの要件は、使用されているauthProtocolによって定義されます。
authKeyChange and authOwnKeyChange
認証鍵をリモートで更新する唯一の方法。プライバシー保護を用いずに更新を完了できるように、安全な方法で更新を行います。
privProtocol
このユーザーに代わって送信されるメッセージを漏洩から保護できるかどうか、また保護できる場合は使用されるプライバシープロトコルの種類を示すもの。このメモでは、そのようなプロトコルが1つ定義されています。CBC-DES対称暗号化プロトコルです。
privKey
このユーザーに代わって送信されるメッセージを暗号化・復号できる場合に、プライバシープロトコルで使用する（秘密の）プライバシー鍵。ユーザーのプライバシー鍵は通常、権威SNMPエンジンごとに異なることに注意してください。privKeyはSNMPを介してアクセスすることはできません。privKeyの長さの要件は、使用されているprivProtocolによって定義されます。
privKeyChange and privOwnKeyChange
暗号鍵をリモートで更新する唯一の方法。プライバシー保護を用いずに更新を完了できるように、安全な方法で更新を行います。

2.2. Replay Protection

2.2. リプレイ保護

Each SNMP engine maintains three objects:

各SNMPエンジンは、3つのオブジェクトを保持しています。

  • snmpEngineID, which (at least within an administrative domain) uniquely and unambiguously identifies an SNMP engine.
  • snmpEngineBoots, which is a count of the number of times the SNMP engine has re-booted/re-initialized since snmpEngineID was last configured; and,
  • snmpEngineTime, which is the number of seconds since the snmpEngineBoots counter was last incremented.
  • snmpEngineID。（少なくとも管理ドメイン内で）SNMPエンジンを一意かつ曖昧さなく識別します。
  • snmpEngineBoots。snmpEngineIDが最後に設定されてから、SNMPエンジンが再起動・再初期化された回数です。
  • snmpEngineTime。snmpEngineBootsカウンターが最後にインクリメントされてからの秒数です。

Each SNMP engine is always authoritative with respect to these objects in its own SNMP entity. It is the responsibility of a non-authoritative SNMP engine to synchronize with the authoritative SNMP engine, as appropriate.

各SNMPエンジンは、自身のSNMPエンティティーにおけるこれらのオブジェクトに関しては常に権威を持ちます。必要に応じて権威SNMPエンジンと同期するのは、非権威SNMPエンジンの責任です。

An authoritative SNMP engine is required to maintain the values of its snmpEngineID and snmpEngineBoots in non-volatile storage.

権威SNMPエンジンは、snmpEngineIDとsnmpEngineBootsの値を不揮発性ストレージに保持する必要があります。

2.2.1. msgAuthoritativeEngineID

2.2.1. msgAuthoritativeEngineID

The msgAuthoritativeEngineID value contained in an authenticated message is used to defeat attacks in which messages from one SNMP engine to another SNMP engine are replayed to a different SNMP engine. It represents the snmpEngineID at the authoritative SNMP engine involved in the exchange of the message.

認証済みメッセージに含まれるmsgAuthoritativeEngineIDの値は、あるSNMPエンジンから別のSNMPエンジンへのメッセージが、さらに別のSNMPエンジンにリプレイされる攻撃を阻止するために使用されます。これは、メッセージのやり取りに関与する権威SNMPエンジンにおけるsnmpEngineIDを表します。

When an authoritative SNMP engine is first installed, it sets its local value of snmpEngineID according to a enterprise-specific algorithm (see the definition of the Textual Convention for SnmpEngineID in the SNMP Architecture document [RFC2271]).

権威SNMPエンジンは、最初にインストールされたときに、企業固有のアルゴリズムに従ってsnmpEngineIDのローカルの値を設定します（SNMPアーキテクチャーの文書 [RFC2271] におけるSnmpEngineIDのテキスト規約の定義を参照してください）。

2.2.2. msgAuthoritativeEngineBoots and msgAuthoritativeEngineTime

2.2.2. msgAuthoritativeEngineBoots and msgAuthoritativeEngineTime

The msgAuthoritativeEngineBoots and msgAuthoritativeEngineTime values contained in an authenticated message are used to defeat attacks in which messages are replayed when they are no longer valid. They represent the snmpEngineBoots and snmpEngineTime values at the authoritative SNMP engine involved in the exchange of the message.

認証済みメッセージに含まれるmsgAuthoritativeEngineBootsとmsgAuthoritativeEngineTimeの値は、もはや有効ではなくなったメッセージがリプレイされる攻撃を阻止するために使用されます。これらは、メッセージのやり取りに関与する権威SNMPエンジンにおけるsnmpEngineBootsとsnmpEngineTimeの値を表します。

Through use of snmpEngineBoots and snmpEngineTime, there is no requirement for an SNMP engine to have a non-volatile clock which ticks (i.e., increases with the passage of time) even when the SNMP engine is powered off. Rather, each time an SNMP engine re-boots, it retrieves, increments, and then stores snmpEngineBoots in non-volatile storage, and resets snmpEngineTime to zero.

snmpEngineBootsとsnmpEngineTimeを使用することで、SNMPエンジンが、電源が切れているときでも時を刻む（つまり、時間の経過とともに増加する）不揮発性の時計を持つ必要はなくなります。その代わり、SNMPエンジンは再起動するたびに、snmpEngineBootsを不揮発性ストレージから取得してインクリメントしてから保存し、snmpEngineTimeを0にリセットします。

When an SNMP engine is first installed, it sets its local values of snmpEngineBoots and snmpEngineTime to zero. If snmpEngineTime ever reaches its maximum value (2147483647), then snmpEngineBoots is incremented as if the SNMP engine has re-booted and snmpEngineTime is reset to zero and starts incrementing again.

SNMPエンジンは、最初にインストールされたときに、snmpEngineBootsとsnmpEngineTimeのローカルの値を0に設定します。snmpEngineTimeが最大値（2147483647）に達した場合、SNMPエンジンが再起動したかのようにsnmpEngineBootsがインクリメントされ、snmpEngineTimeは0にリセットされて再びインクリメントを開始します。

Each time an authoritative SNMP engine re-boots, any SNMP engines holding that authoritative SNMP engine's values of snmpEngineBoots and snmpEngineTime need to re-synchronize prior to sending correctly authenticated messages to that authoritative SNMP engine (see Section 2.3 for (re-)synchronization procedures). Note, however, that the procedures do provide for a notification to be accepted as authentic by a receiving SNMP engine, when sent by an authoritative SNMP engine which has re-booted since the receiving SNMP engine last (re-)synchronized.

権威SNMPエンジンが再起動するたびに、その権威SNMPエンジンのsnmpEngineBootsとsnmpEngineTimeの値を保持しているSNMPエンジンはすべて、その権威SNMPエンジンに正しく認証されたメッセージを送信する前に再同期する必要があります（再同期の手順についてはセクション2.3を参照してください）。ただし、受信側SNMPエンジンが最後に（再）同期してから再起動した権威SNMPエンジンから送信された通知を、受信側SNMPエンジンが真正として受け入れられるように、手順が配慮されていることに注意してください。

If an authoritative SNMP engine is ever unable to determine its latest snmpEngineBoots value, then it must set its snmpEngineBoots value to 2147483647.

権威SNMPエンジンが最新のsnmpEngineBootsの値を判断できない場合、snmpEngineBootsの値を2147483647に設定しなければなりません。

Whenever the local value of snmpEngineBoots has the value 2147483647 it latches at that value and an authenticated message always causes an notInTimeWindow authentication failure.

snmpEngineBootsのローカルの値が2147483647になると、その値に固定され、認証済みメッセージは常にnotInTimeWindowの認証失敗を引き起こします。

In order to reset an SNMP engine whose snmpEngineBoots value has reached the value 2147483647, manual intervention is required. The engine must be physically visited and re-configured, either with a new snmpEngineID value, or with new secret values for the authentication and privacy protocols of all users known to that SNMP engine. Note that even if an SNMP engine re-boots once a second that it would still take approximately 68 years before the max value of 2147483647 would be reached.

snmpEngineBootsの値が2147483647に達したSNMPエンジンをリセットするには、手動での介入が必要です。そのエンジンのもとに物理的に赴き、新しいsnmpEngineIDの値か、そのSNMPエンジンが知っているすべてのユーザーの認証プロトコルとプライバシープロトコルの新しい秘密の値で再設定しなければなりません。SNMPエンジンが1秒に1回再起動したとしても、最大値2147483647に達するまでには約68年かかることに注意してください。

2.2.3. Time Window

2.2.3. 時間枠

The Time Window is a value that specifies the window of time in which a message generated on behalf of any user is valid. This memo specifies that the same value of the Time Window, 150 seconds, is used for all users.

時間枠は、任意のユーザーに代わって生成されたメッセージが有効である期間を指定する値です。このメモでは、すべてのユーザーに同じ時間枠の値150秒を使用することを規定しています。

2.3. Time Synchronization

2.3. 時刻の同期

Time synchronization, required by a non-authoritative SNMP engine in order to proceed with authentic communications, has occurred when the non-authoritative SNMP engine has obtained a local notion of the authoritative SNMP engine's values of snmpEngineBoots and snmpEngineTime from the authoritative SNMP engine. These values must be (and remain) within the authoritative SNMP engine's Time Window. So the local notion of the authoritative SNMP engine's values must be kept loosely synchronized with the values stored at the authoritative SNMP engine. In addition to keeping a local copy of snmpEngineBoots and snmpEngineTime from the authoritative SNMP engine, a non-authoritative SNMP engine must also keep one local variable, latestReceivedEngineTime. This value records the highest value of snmpEngineTime that was received by the non-authoritative SNMP engine from the authoritative SNMP engine and is used to eliminate the possibility of replaying messages that would prevent the non-authoritative SNMP engine's notion of the snmpEngineTime from advancing.

非権威SNMPエンジンが真正な通信を進めるために必要な時刻の同期は、非権威SNMPエンジンが、権威SNMPエンジンのsnmpEngineBootsとsnmpEngineTimeの値についてのローカルな認識を権威SNMPエンジンから得たときに達成されます。これらの値は、権威SNMPエンジンの時間枠内になければならず（またそうあり続けなければならず）、そのため権威SNMPエンジンの値についてのローカルな認識は、権威SNMPエンジンに保存されている値と緩やかに同期を保たなければなりません。権威SNMPエンジンのsnmpEngineBootsとsnmpEngineTimeのローカルなコピーを保持することに加えて、非権威SNMPエンジンは、latestReceivedEngineTimeというローカル変数も1つ保持しなければなりません。この値は、非権威SNMPエンジンが権威SNMPエンジンから受信したsnmpEngineTimeの最大値を記録し、非権威SNMPエンジンのsnmpEngineTimeについての認識が進むのを妨げるメッセージのリプレイの可能性を排除するために使用されます。

A non-authoritative SNMP engine must keep local notions of these values for each authoritative SNMP engine with which it wishes to communicate. Since each authoritative SNMP engine is uniquely and unambiguously identified by its value of snmpEngineID, the non-authoritative SNMP engine may use this value as a key in order to cache its local notions of these values.

非権威SNMPエンジンは、通信したい各権威SNMPエンジンについて、これらの値のローカルな認識を保持しなければなりません。各権威SNMPエンジンは、そのsnmpEngineIDの値によって一意かつ曖昧さなく識別されるため、非権威SNMPエンジンは、これらの値のローカルな認識をキャッシュするための鍵としてこの値を使用できます。

Time synchronization occurs as part of the procedures of receiving an SNMP message (Section 3.2, step 7b). As such, no explicit time synchronization procedure is required by a non-authoritative SNMP engine. Note, that whenever the local value of snmpEngineID is changed (e.g., through discovery) or when secure communications are first established with an authoritative SNMP engine, the local values of snmpEngineBoots and latestReceivedEngineTime should be set to zero. This will cause the time synchronization to occur when the next authentic message is received.

時刻の同期は、SNMPメッセージを受信する手順の一部として行われます（セクション3.2、ステップ7b）。そのため、非権威SNMPエンジンが明示的な時刻同期の手順を必要とすることはありません。ただし、snmpEngineIDのローカルの値が（たとえばディスカバリーによって）変更された場合や、権威SNMPエンジンとの安全な通信が最初に確立された場合は、snmpEngineBootsとlatestReceivedEngineTimeのローカルの値を0に設定すべきであることに注意してください。これにより、次に真正なメッセージを受信したときに時刻の同期が行われます。

The fields of this sequence are:

  • The msgAuthoritativeEngineBoots specifies the snmpEngineBoots value at the authoritative SNMP engine involved in the exchange of the message.
  • The msgAuthoritativeEngineTime specifies the snmpEngineTime value at the authoritative SNMP engine involved in the exchange of the message.

  • The msgAuthenticationParameters are defined by the authentication protocol in use for the message, as defined by the usmUserAuthProtocol column in the user's entry in the usmUserTable.

snmpEngineIDとともに、メッセージの保護に使用するusmUserTableの行を識別します。securityNameは、セキュリティーモデルに依存しない形式を持ちます。応答の場合、このパラメーターは無視され、キャッシュの値が使用されます。
securityLevel
セキュリティーのレベル。ユーザーベースセキュリティーモジュールは、これをもとに、メッセージを漏洩から保護する必要があるかどうか、またメッセージを認証する必要があるかどうかを判断します。応答の場合、このパラメーターは無視され、キャッシュの値が使用されます。
securityEngineID
要求メッセージの送信先となる権威SNMPエンジンのsnmpEngineID。応答の場合、これは処理しているSNMPエンジンのsnmpEngineIDであることが暗黙に想定されるため、指定されていても無視されます。
scopedPDU
メッセージのペイロード。ユーザーベースセキュリティーモデルにとって、このデータは不透明です。
securityStateReference
送信する応答メッセージを保護する際に使用するcachedSecurityDataへのハンドル・参照。これは、この応答メッセージが応答する受信した要求メッセージを処理したときに、ユーザーベースセキュリティーモジュールが生成したものとまったく同じハンドル・参照です。

回線上に送信する準備ができた、完全にエンコードされ保護されたメッセージ。
wholeMsgLength
エンコードされ保護されたメッセージ（wholeMsg）の長さ。

Upon completion of the process, the User-based Security module returns statusInformation. If the process was successful, the completed message with privacy and authentication applied if such was requested by the specified securityLevel is returned. If the process was not successful, then an errorIndication is returned.

処理が完了すると、ユーザーベースセキュリティーモジュールはstatusInformationを返します。処理が成功した場合は、指定されたsecurityLevelによって要求されていればプライバシーと認証が適用された、完成したメッセージが返されます。処理が成功しなかった場合は、errorIndicationが返されます。

2.6. Key Localization Algorithm.

2.6. 鍵のローカライズのアルゴリズム

A localized key is a secret key shared between a user U and one authoritative SNMP engine E. Even though a user may have only one password and therefore one key for the whole network, the actual secrets shared between the user and each authoritative SNMP engine will be different. This is achieved by key localization [Localized-Key].

ローカライズされた鍵とは、ユーザーUと1つの権威SNMPエンジンEとの間で共有される秘密鍵です。ユーザーがネットワーク全体に対して1つのパスワード、したがって1つの鍵しか持っていなくても、ユーザーと各権威SNMPエンジンとの間で共有される実際の秘密情報は異なります。これは、鍵のローカライズ [Localized-Key] によって実現されます。

First, if a user uses a password, then the user's password is converted into a key Ku using one of the two algorithms described in Appendices A.2.1 and A.2.2.

まず、ユーザーがパスワードを使用する場合、ユーザーのパスワードは、付録A.2.1とA.2.2で説明されている2つのアルゴリズムのいずれかを使用して鍵Kuに変換されます。

To convert key Ku into a localized key Kul of user U at the authoritative SNMP engine E, one appends the snmpEngineID of the authoritative SNMP engine to the key Ku and then appends the key Ku to the result, thus enveloping the snmpEngineID within the two copies of user's key Ku. Then one runs a secure hash function (which one depends on the authentication protocol defined for this user U at authoritative SNMP engine E; this document defines two authentication protocols with their associated algorithms based on MD5 and SHA). The output of the hash-function is the localized key Kul for user U at the authoritative SNMP engine E.

鍵Kuを権威SNMPエンジンEにおけるユーザーUのローカライズされた鍵Kulに変換するには、鍵Kuに権威SNMPエンジンのsnmpEngineIDを付加し、さらにその結果に鍵Kuを付加して、snmpEngineIDをユーザーの鍵Kuの2つのコピーで挟み込みます。次に、安全なハッシュ関数を実行します（どのハッシュ関数を使うかは、権威SNMPエンジンEでこのユーザーUに対して定義されている認証プロトコルによって決まります。この文書では、MD5とSHAに基づくアルゴリズムを伴う2つの認証プロトコルを定義しています）。ハッシュ関数の出力が、権威SNMPエンジンEにおけるユーザーUのローカライズされた鍵Kulです。

3. Elements of Procedure

3. 手順要素

This section describes the security related procedures followed by an SNMP engine when processing SNMP messages according to the User-based Security Model.

このセクションでは、ユーザーベースセキュリティーモデルに従ってSNMPメッセージを処理する際に、SNMPエンジンが従うセキュリティー関連の手順について説明します。

3.1. Generating an Outgoing SNMP Message

3.1. 送信SNMPメッセージの生成

This section describes the procedure followed by an SNMP engine whenever it generates a message containing a management operation (like a request, a response, a notification, or a report) on behalf of a user, with a particular securityLevel.

このセクションでは、SNMPエンジンが、特定のsecurityLevelで、あるユーザーに代わって管理操作（要求、応答、通知、レポートなど）を含むメッセージを生成するたびに従う手順について説明します。

    1. If any securityStateReference is passed (Response message), then information concerning the user is extracted from the cachedSecurityData. The securityEngineID and the securityLevel are extracted from the cachedSecurityData. The cachedSecurityData can now be discarded.

      Otherwise,

    2. based on the securityName, information concerning the user at the destination snmpEngineID, specified by the securityEngineID, is extracted from the Local Configuration Datastore (LCD, usmUserTable). If information about the user is absent from the LCD, then an error indication (unknownSecurityName) is returned to the calling module.
  2. If the securityLevel specifies that the message is to be protected from disclosure, but the user does not support both an authentication and a privacy protocol then the message cannot be sent. An error indication (unsupportedSecurityLevel) is returned to the calling module.
  3. If the securityLevel specifies that the message is to be authenticated, but the user does not support an authentication protocol, then the message cannot be sent. An error indication (unsupportedSecurityLevel) is returned to the calling module.

    1. If the securityLevel specifies that the message is to be protected from disclosure, then the octet sequence representing the serialized scopedPDU is encrypted according to the user's privacy protocol. To do so a call is made to the privacy module that implements the user's privacy protocol according to the abstract primitive:

      statusInformation =       -- success or failure
  encryptData(
  IN    encryptKey        -- user's localized privKey
  IN    dataToEncrypt     -- serialized scopedPDU
  OUT   encryptedData     -- serialized encryptedPDU
  OUT   privParameters    -- serialized privacy parameters
        )
      statusInformation
      indicates if the encryption process was successful or not.
      encryptKey
      the user's localized private privKey is the secret key that can be used by the encryption algorithm.
      dataToEncrypt
      the serialized scopedPDU is the data that to be encrypted.
      encryptedData
      the encryptedPDU represents the encrypted scopedPDU, encoded as an OCTET STRING.
      privParameters
      the privacy parameters, encoded as an OCTET STRING.

      If the privacy module returns failure, then the message cannot be sent and an error indication (encryptionError) is returned to the calling module.

      If the privacy module returns success, then the returned privParameters are put into the msgPrivacyParameters field of the securityParameters and the encryptedPDU serves as the payload of the message being prepared.

      Otherwise,

    2. If the securityLevel specifies that the message is not to be protected from disclosure, then the NULL string is encoded as an OCTET STRING and put into the msgPrivacyParameters field of the securityParameters and the plaintext scopedPDU serves as the payload of the message being prepared.
  5. The snmpEngineID is encoded as an OCTET STRING into the msgAuthoritativeEngineID field of the securityParameters. Note that an empty (zero length) snmpEngineID is OK for a Request message, because that will cause the remote (authoritative) SNMP engine to return a Report PDU with the proper snmpEngineID included in the msgAuthoritativeEngineID in the securityParameters of that returned Report PDU.

    1. If the securityLevel specifies that the message is to be authenticated, then the current values of snmpEngineBoots and snmpEngineTime corresponding to the snmpEngineID from the LCD are used.

      Otherwise,

    2. If this is a Response message, then the current value of snmpEngineBoots and snmpEngineTime corresponding to the local snmpEngineID from the LCD are used.

      Otherwise,

    3. If this is a Request message, then a zero value is used for both snmpEngineBoots and snmpEngineTime. This zero value gets used if snmpEngineID is empty.

    The values are encoded as INTEGER respectively into the msgAuthoritativeEngineBoots and msgAuthoritativeEngineTime fields of the securityParameters.

  7. The userName is encoded as an OCTET STRING into the msgUserName field of the securityParameters.

    1. If the securityLevel specifies that the message is to be authenticated, the message is authenticated according to the user's authentication protocol. To do so a call is made to the authentication module that implements the user's authentication protocol according to the abstract service primitive:

      statusInformation =
  authenticateOutgoingMsg(
  IN  authKey               -- the user's localized authKey
  IN  wholeMsg              -- unauthenticated message
  OUT authenticatedWholeMsg -- authenticated complete message
      )
      statusInformation
      indicates if authentication was successful or not.
      authKey
      the user's localized private authKey is the secret key that can be used by the authentication algorithm.
      wholeMsg
      the complete serialized message to be authenticated.
      authenticatedWholeMsg
      the same as the input given to the authenticateOutgoingMsg service, but with msgAuthenticationParameters properly filled in.

      If the authentication module returns failure, then the message cannot be sent and an error indication (authenticationFailure) is returned to the calling module.

      If the authentication module returns success, then the msgAuthenticationParameters field is put into the securityParameters and the authenticatedWholeMsg represents the serialization of the authenticated message being prepared.

      Otherwise,

    2. If the securityLevel specifies that the message is not to be authenticated then the NULL string is encoded as an OCTET STRING into the msgAuthenticationParameters field of the securityParameters. The wholeMsg is now serialized and then represents the unauthenticated message being prepared.
  9. The completed message with its length is returned to the calling module with the statusInformation set to success.

    1. securityStateReferenceが渡された場合（応答メッセージ）、ユーザーに関する情報はcachedSecurityDataから抽出されます。securityEngineIDとsecurityLevelはcachedSecurityDataから抽出されます。この時点でcachedSecurityDataは破棄できます。

      そうでない場合は次のようにします。

    2. securityNameに基づいて、securityEngineIDで指定された宛先のsnmpEngineIDにおけるユーザーに関する情報が、ローカル設定データストア（LCD、usmUserTable）から抽出されます。ユーザーに関する情報がLCDにない場合は、エラー通知（unknownSecurityName）が呼び出し元のモジュールに返されます。
  2. securityLevelがメッセージを漏洩から保護することを指定しているが、ユーザーが認証プロトコルとプライバシープロトコルの両方をサポートしていない場合、メッセージは送信できません。エラー通知（unsupportedSecurityLevel）が呼び出し元のモジュールに返されます。
  3. securityLevelがメッセージを認証することを指定しているが、ユーザーが認証プロトコルをサポートしていない場合、メッセージは送信できません。エラー通知（unsupportedSecurityLevel）が呼び出し元のモジュールに返されます。

    1. securityLevelがメッセージを漏洩から保護することを指定している場合、シリアル化されたscopedPDUを表すオクテット列が、ユーザーのプライバシープロトコルに従って暗号化されます。そのために、ユーザーのプライバシープロトコルを実装するプライバシーモジュールが、次の抽象プリミティブに従って呼び出されます。

      statusInformation =       -- success or failure
  encryptData(
  IN    encryptKey        -- user's localized privKey
  IN    dataToEncrypt     -- serialized scopedPDU
  OUT   encryptedData     -- serialized encryptedPDU
  OUT   privParameters    -- serialized privacy parameters
        )
      statusInformation
      暗号化処理が成功したかどうかを示します。
      encryptKey
      ユーザーのローカライズされた秘密のprivKeyであり、暗号化アルゴリズムで使用できる秘密鍵です。
      dataToEncrypt
      シリアル化されたscopedPDUであり、暗号化するデータです。
      encryptedData
      encryptedPDUであり、OCTET STRINGとしてエンコードされた、暗号化されたscopedPDUを表します。
      privParameters
      OCTET STRINGとしてエンコードされたプライバシーパラメーターです。

      プライバシーモジュールが失敗を返した場合、メッセージは送信できず、エラー通知（encryptionError）が呼び出し元のモジュールに返されます。

      プライバシーモジュールが成功を返した場合、返されたprivParametersはsecurityParametersのmsgPrivacyParametersフィールドに格納され、encryptedPDUが準備中のメッセージのペイロードになります。

      そうでない場合は次のようにします。

    2. securityLevelがメッセージを漏洩から保護しないことを指定している場合、NULL文字列がOCTET STRINGとしてエンコードされてsecurityParametersのmsgPrivacyParametersフィールドに格納され、平文のscopedPDUが準備中のメッセージのペイロードになります。
  5. snmpEngineIDは、OCTET STRINGとしてエンコードされ、securityParametersのmsgAuthoritativeEngineIDフィールドに格納されます。要求メッセージでは空の（長さ0の）snmpEngineIDでもかまわないことに注意してください。その場合、リモートの（権威）SNMPエンジンは、返すReport PDUのsecurityParameters内のmsgAuthoritativeEngineIDに適切なsnmpEngineIDを含めて、Report PDUを返すからです。

    1. securityLevelがメッセージを認証することを指定している場合、LCDのsnmpEngineIDに対応するsnmpEngineBootsとsnmpEngineTimeの現在の値が使用されます。

      そうでない場合は次のようにします。

    2. これが応答メッセージの場合、LCDのローカルのsnmpEngineIDに対応するsnmpEngineBootsとsnmpEngineTimeの現在の値が使用されます。

      そうでない場合は次のようにします。

    3. これが要求メッセージの場合、snmpEngineBootsとsnmpEngineTimeの両方に0の値が使用されます。この0の値は、snmpEngineIDが空の場合に使用されます。

    これらの値は、それぞれINTEGERとしてエンコードされ、securityParametersのmsgAuthoritativeEngineBootsフィールドとmsgAuthoritativeEngineTimeフィールドに格納されます。

  7. userNameは、OCTET STRINGとしてエンコードされ、securityParametersのmsgUserNameフィールドに格納されます。

    1. securityLevelがメッセージを認証することを指定している場合、メッセージはユーザーの認証プロトコルに従って認証されます。そのために、ユーザーの認証プロトコルを実装する認証モジュールが、次の抽象サービスプリミティブに従って呼び出されます。

      statusInformation =
  authenticateOutgoingMsg(
  IN  authKey               -- the user's localized authKey
  IN  wholeMsg              -- unauthenticated message
  OUT authenticatedWholeMsg -- authenticated complete message
      )
      statusInformation
      認証が成功したかどうかを示します。
      authKey
      ユーザーのローカライズされた秘密のauthKeyであり、認証アルゴリズムで使用できる秘密鍵です。
      wholeMsg
      認証するシリアル化された完全なメッセージです。
      authenticatedWholeMsg
      authenticateOutgoingMsgサービスへの入力と同じものですが、msgAuthenticationParametersが適切に埋められています。

      認証モジュールが失敗を返した場合、メッセージは送信できず、エラー通知（authenticationFailure）が呼び出し元のモジュールに返されます。

      認証モジュールが成功を返した場合、msgAuthenticationParametersフィールドはsecurityParametersに格納され、authenticatedWholeMsgは準備中の認証済みメッセージのシリアル化を表します。

      そうでない場合は次のようにします。

    2. securityLevelがメッセージを認証しないことを指定している場合、NULL文字列がOCTET STRINGとしてエンコードされ、securityParametersのmsgAuthenticationParametersフィールドに格納されます。この時点でwholeMsgがシリアル化され、準備中の認証されていないメッセージを表します。
  9. 完成したメッセージがその長さとともに、statusInformationを成功に設定して、呼び出し元のモジュールに返されます。

3.2. Processing an Incoming SNMP Message

3.2. 受信SNMPメッセージの処理

This section describes the procedure followed by an SNMP engine whenever it receives a message containing a management operation on behalf of a user, with a particular securityLevel.

このセクションでは、SNMPエンジンが、特定のsecurityLevelで、あるユーザーに代わって管理操作を含むメッセージを受信するたびに従う手順について説明します。

To simplify the elements of procedure, the release of state information is not always explicitly specified. As a general rule, if state information is available when a message gets discarded, the state information should also be released. Also, when an error indication with an OID and value for an incremented counter is returned, then the available information (like securityStateReference) must be passed back to the caller so it can generate a Report PDU.

手順要素を単純化するため、状態情報の解放は常に明示的に規定されているわけではありません。一般的な規則として、メッセージが破棄される時点で状態情報が利用可能であれば、その状態情報も解放すべきです。また、インクリメントされたカウンターのOIDと値を伴うエラー通知が返される場合、呼び出し元がReport PDUを生成できるように、利用可能な情報（securityStateReferenceなど）を呼び出し元に返さなければなりません。

  1. If the received securityParameters is not the serialization (according to the conventions of [RFC1906]) of an OCTET STRING formatted according to the UsmSecurityParameters defined in section 2.4, then the snmpInASNParseErrs counter [RFC1907] is incremented, and an error indication (parseError) is returned to the calling module.     If the authentication module returns success, then the message is authentic and can be trusted so processing continues.

      • the local value of snmpEngineBoots is 2147483647;
      • the value of the msgAuthoritativeEngineBoots field differs from the local value of snmpEngineBoots; or,
      • the value of the msgAuthoritativeEngineTime field differs from the local notion of snmpEngineTime by more than +/- 150 seconds.

      If the message is considered to be outside of the Time Window then the usmStatsNotInTimeWindows counter is incremented and an error indication (notInTimeWindow) together with the OID and value of the incremented counter is returned to the calling module.

    2. If the extracted value of msgAuthoritativeEngineID is not the same as the value snmpEngineID of the processing SNMP engine (meaning this is not the authoritative SNMP engine), then:

      1. if at least one of the following conditions is true:

        • the extracted value of the msgAuthoritativeEngineBoots field is greater than the local notion of the value of snmpEngineBoots; or,
        • the extracted value of the msgAuthoritativeEngineBoots field is equal to the local notion of the value of snmpEngineBoots, the extracted value of msgAuthoritativeEngineTime field is greater than the value of latestReceivedEngineTime,

        • the local notion of the value of snmpEngineBoots to the value of the msgAuthoritativeEngineBoots field,
        • the local notion of the value of snmpEngineTime to the value of the msgAuthoritativeEngineTime field, and
        • the latestReceivedEngineTime to the value of the value of the msgAuthoritativeEngineTime field.

        • the local notion of the value of snmpEngineBoots is 2147483647;

        Note that this means that a too old (possibly replayed) message has been detected and is deemed unauthentic.

        Note that this procedure allows for the value of msgAuthoritativeEngineBoots in the message to be greater than the local notion of the value of snmpEngineBoots to allow for received messages to be accepted as authentic when received from an authoritative SNMP engine that has re-booted since the receiving SNMP engine last (re-)synchronized.

4. Discovery

4. ディスカバリー

The User-based Security Model requires that a discovery process obtains sufficient information about other SNMP engines in order to communicate with them. Discovery requires an non-authoritative SNMP engine to learn the authoritative SNMP engine's snmpEngineID value before communication may proceed. This may be accomplished by generating a Request message with a securityLevel of noAuthNoPriv, a msgUserName of "initial", a msgAuthoritativeEngineID value of zero length, and the varBindList left empty. The response to this message will be a Report message containing the snmpEngineID of the authoritative SNMP engine as the value of the msgAuthoritativeEngineID field within the msgSecurityParameters field. It contains a Report PDU with the usmStatsUnknownEngineIDs counter in the varBindList.

ユーザーベースセキュリティーモデルでは、他のSNMPエンジンと通信するために、ディスカバリーのプロセスによってそれらのSNMPエンジンに関する十分な情報を得る必要があります。ディスカバリーでは、通信を進める前に、非権威SNMPエンジンが権威SNMPエンジンのsnmpEngineIDの値を知る必要があります。これは、securityLevelがnoAuthNoPriv、msgUserNameが"initial"、msgAuthoritativeEngineIDの値が長さ0で、varBindListを空にした要求メッセージを生成することで実現できます。このメッセージに対する応答は、msgSecurityParametersフィールド内のmsgAuthoritativeEngineIDフィールドの値として権威SNMPエンジンのsnmpEngineIDを含むReportメッセージになります。このメッセージには、varBindListにusmStatsUnknownEngineIDsカウンターを含むReport PDUが含まれます。

If authenticated communication is required, then the discovery process should also establish time synchronization with the authoritative SNMP engine. This may be accomplished by sending an authenticated Request message with the value of msgAuthoritativeEngineID set to the newly learned snmpEngineID and with the values of msgAuthoritativeEngineBoots and msgAuthoritativeEngineTime set to zero. The response to this authenticated message will be a Report message containing the up to date values of the authoritative SNMP engine's snmpEngineBoots and snmpEngineTime as the value of the msgAuthoritativeEngineBoots and msgAuthoritativeEngineTime fields respectively. It also contains the usmStatsNotInTimeWindows counter in the varBindList of the Report PDU. The time synchronization then happens automatically as part of the procedures in section 3.2 step 7b. See also section 2.3.

認証された通信が必要な場合、ディスカバリーのプロセスでは、権威SNMPエンジンとの時刻の同期も確立すべきです。これは、msgAuthoritativeEngineIDの値を新たに知ったsnmpEngineIDに設定し、msgAuthoritativeEngineBootsとmsgAuthoritativeEngineTimeの値を0に設定した、認証済みの要求メッセージを送信することで実現できます。この認証済みメッセージに対する応答は、権威SNMPエンジンのsnmpEngineBootsとsnmpEngineTimeの最新の値を、それぞれmsgAuthoritativeEngineBootsフィールドとmsgAuthoritativeEngineTimeフィールドの値として含むReportメッセージになります。このメッセージには、Report PDUのvarBindListにusmStatsNotInTimeWindowsカウンターも含まれます。その後、時刻の同期は、セクション3.2のステップ7bの手順の一部として自動的に行われます。セクション2.3も参照してください。

          are given by the corresponding value of the protocol P;
          if P requires K to be a fixed length, the length of both the
          random and delta components is that fixed length; if P
          allows the length of K to be variable up to a particular
          maximum length, the length of the random component is that
          maximum length and the length of the delta component is any
          length less than or equal to that maximum length.
          For example, usmHMACMD5AuthProtocol requires K to be a fixed
          length of 16 octets and L - of 16 octets.
          usmHMACSHAAuthProtocol requires K to be a fixed length of
          20 octets and L - of 20 octets. Other protocols may define
          other sizes, as deemed appropriate.

          When a requestor wants to change the old key K to a new
          key keyNew on a remote entity, the 'random' component is
          obtained from either a true random generator, or from a
          pseudorandom generator, and the 'delta' component is
          computed as follows:

           - a temporary variable is initialized to the existing value
             of K;
           - if the length of the keyNew is greater than L octets,
             then:
              - the random component is appended to the value of the
                temporary variable, and the result is input to the
                the hash algorithm H to produce a digest value, and
                the temporary variable is set to this digest value;
              - the value of the temporary variable is XOR-ed with
                the first (next) L-octets (16 octets in case of MD5)
                of the keyNew to produce the first (next) L-octets
                (16 octets in case of MD5) of the 'delta' component.
              - the above two steps are repeated until the unused
                portion of the delta component is L octets or less,
           - the random component is appended to the value of the
             temporary variable, and the result is input to the
             hash algorithm H to produce a digest value;
           - this digest value, truncated if necessary to be the same
             length as the unused portion of the keyNew, is XOR-ed
             with the unused portion of the keyNew to produce the
             (final portion of the) 'delta' component.

           For example, using MD5 as the hash algorithm H:

              iterations = (lenOfDelta - 1)/16; /* integer division */
              temp = keyOld;
              for (i = 0; i < iterations; i++) {
                  temp = MD5 (temp || random);
                  delta[i*16 .. (i*16)+15] =
                         temp XOR keyNew[i*16 .. (i*16)+15];
              }
              temp = MD5 (temp || random);
              delta[i*16 .. lenOfDelta-1] =
                     temp XOR keyNew[i*16 .. lenOfDelta-1];

          The 'random' and 'delta' components are then concatenated as
          described above, and the resulting octet string is sent to
          the receipient as the new value of an instance of this
          object.

          At the receiver side, when an instance of this object is set
          to a new value, then a new value of K is computed as follows:

           - a temporary variable is initialized to the existing value
             of K;
           - if the length of the delta component is greater than L
             octets, then:
              - the random component is appended to the value of the
                temporary variable, and the result is input to the
                the hash algorithm H to produce a digest value, and
                the temporary variable is set to this digest value;
              - the value of the temporary variable is XOR-ed with
                the first (next) L-octets (16 octets in case of MD5)
                of the delta component to produce the first (next)
                L-octets (16 octets in case of MD5) of the new value
                of K.
              - the above two steps are repeated until the unused
                portion of the delta component is L octets or less,
           - the random component is appended to the value of the
             temporary variable, and the result is input to the
             hash algorithm H to produce a digest value;
           - this digest value, truncated if necessary to be the same
             length as the unused portion of the delta component, is
             XOR-ed with the unused portion of the delta component to
             produce the (final portion of the) new value of K.

           For example, using MD5 as the hash algorithm H:

              iterations = (lenOfDelta - 1)/16; /* integer division */
              temp = keyOld;
              for (i = 0; i < iterations; i++) {
                  temp = MD5 (temp || random);
                  keyNew[i*16 .. (i*16)+15] =
                         temp XOR delta[i*16 .. (i*16)+15];
              }
              temp = MD5 (temp || random);
              keyNew[i*16 .. lenOfDelta-1] =
                     temp XOR delta[i*16 .. lenOfDelta-1];

          The value of an object with this syntax, whenever it is
          retrieved by the management protocol, is always the zero
          length string.
         "
    SYNTAX       OCTET STRING

KeyChange ::=     TEXTUAL-CONVENTION

   STATUS         current
   DESCRIPTION
         "Every definition of an object with this syntax must identify
          a protocol P, a secret key K, and a hash algorithm H
          that produces output of L octets.

          The object's value is a manager-generated, partially-random
          value which, when modified, causes the value of the secret
          key K, to be modified via a one-way function.

          The value of an instance of this object is the concatenation
          of two components: first a 'random' component and then a
          'delta' component.

          The lengths of the random and delta components
          are given by the corresponding value of the protocol P;
          if P requires K to be a fixed length, the length of both the
          random and delta components is that fixed length; if P
          allows the length of K to be variable up to a particular
          maximum length, the length of the random component is that
          maximum length and the length of the delta component is any
          length less than or equal to that maximum length.
          For example, usmHMACMD5AuthProtocol requires K to be a fixed
          length of 16 octets and L - of 16 octets.
          usmHMACSHAAuthProtocol requires K to be a fixed length of
          20 octets and L - of 20 octets. Other protocols may define
          other sizes, as deemed appropriate.

          When a requestor wants to change the old key K to a new
          key keyNew on a remote entity, the 'random' component is
          obtained from either a true random generator, or from a
          pseudorandom generator, and the 'delta' component is
          computed as follows:

           - a temporary variable is initialized to the existing value
             of K;
           - if the length of the keyNew is greater than L octets,
             then:
              - the random component is appended to the value of the
                temporary variable, and the result is input to the
                the hash algorithm H to produce a digest value, and
                the temporary variable is set to this digest value;
              - the value of the temporary variable is XOR-ed with
                the first (next) L-octets (16 octets in case of MD5)
                of the keyNew to produce the first (next) L-octets
                (16 octets in case of MD5) of the 'delta' component.
              - the above two steps are repeated until the unused
                portion of the delta component is L octets or less,
           - the random component is appended to the value of the
             temporary variable, and the result is input to the
             hash algorithm H to produce a digest value;
           - this digest value, truncated if necessary to be the same
             length as the unused portion of the keyNew, is XOR-ed
             with the unused portion of the keyNew to produce the
             (final portion of the) 'delta' component.

           For example, using MD5 as the hash algorithm H:

              iterations = (lenOfDelta - 1)/16; /* 整数除算 */
              temp = keyOld;
              for (i = 0; i < iterations; i++) {
                  temp = MD5 (temp || random);
                  delta[i*16 .. (i*16)+15] =
                         temp XOR keyNew[i*16 .. (i*16)+15];
              }
              temp = MD5 (temp || random);
              delta[i*16 .. lenOfDelta-1] =
                     temp XOR keyNew[i*16 .. lenOfDelta-1];

          The 'random' and 'delta' components are then concatenated as
          described above, and the resulting octet string is sent to
          the receipient as the new value of an instance of this
          object.

          At the receiver side, when an instance of this object is set
          to a new value, then a new value of K is computed as follows:

           - a temporary variable is initialized to the existing value
             of K;
           - if the length of the delta component is greater than L
             octets, then:
              - the random component is appended to the value of the
                temporary variable, and the result is input to the
                the hash algorithm H to produce a digest value, and
                the temporary variable is set to this digest value;
              - the value of the temporary variable is XOR-ed with
                the first (next) L-octets (16 octets in case of MD5)
                of the delta component to produce the first (next)
                L-octets (16 octets in case of MD5) of the new value
                of K.
              - the above two steps are repeated until the unused
                portion of the delta component is L octets or less,
           - the random component is appended to the value of the
             temporary variable, and the result is input to the
             hash algorithm H to produce a digest value;
           - this digest value, truncated if necessary to be the same
             length as the unused portion of the delta component, is
             XOR-ed with the unused portion of the delta component to
             produce the (final portion of the) new value of K.

           For example, using MD5 as the hash algorithm H:

              iterations = (lenOfDelta - 1)/16; /* 整数除算 */
              temp = keyOld;
              for (i = 0; i < iterations; i++) {
                  temp = MD5 (temp || random);
                  keyNew[i*16 .. (i*16)+15] =
                         temp XOR delta[i*16 .. (i*16)+15];
              }
              temp = MD5 (temp || random);
              keyNew[i*16 .. lenOfDelta-1] =
                     temp XOR delta[i*16 .. lenOfDelta-1];

          The value of an object with this syntax, whenever it is
          retrieved by the management protocol, is always the zero
          length string.
         "
    SYNTAX       OCTET STRING

6. HMAC-MD5-96 Authentication Protocol

6. HMAC-MD5-96認証プロトコル

This section describes the HMAC-MD5-96 authentication protocol. This authentication protocol is the first defined for the User-based Security Model. It uses MD5 hash-function which is described in [MD5], in HMAC mode described in [RFC2104], truncating the output to 96 bits.

このセクションでは、HMAC-MD5-96認証プロトコルについて説明します。この認証プロトコルは、ユーザーベースセキュリティーモデルのために最初に定義されたものです。これは、[MD5]で説明されているMD5ハッシュ関数を、[RFC2104] で説明されているHMACモードで使用し、出力を96ビットに切り詰めます。

This protocol is identified by usmHMACMD5AuthProtocol.

このプロトコルは、usmHMACMD5AuthProtocolによって識別されます。

Over time, other authentication protocols may be defined either as a replacement of this protocol or in addition to this protocol.

時間の経過とともに、このプロトコルの代替として、またはこのプロトコルに加えて、他の認証プロトコルが定義されるかもしれません。

6.1. Mechanisms

6.1. 仕組み

  • In support of data integrity, a message digest algorithm is required. A digest is calculated over an appropriate portion of an SNMP message and included as part of the message sent to the recipient.
  • In support of data origin authentication and data integrity, a secret value is prepended to SNMP message prior to computing the digest; the calculated digest is partially inserted into the SNMP message prior to transmission, and the prepended value is not transmitted. The secret value is shared by all SNMP engines authorized to originate messages on behalf of the appropriate user.
  • データの完全性をサポートするために、メッセージダイジェストアルゴリズムが必要です。ダイジェストはSNMPメッセージの適切な部分に対して計算され、受信者に送信されるメッセージの一部として含まれます。
  • データ発信元の認証とデータの完全性をサポートするために、ダイジェストを計算する前に秘密の値がSNMPメッセージの前に付加されます。計算されたダイジェストは送信前にSNMPメッセージに部分的に挿入され、前に付加された値は送信されません。秘密の値は、適切なユーザーに代わってメッセージを発信することを許可されたすべてのSNMPエンジンによって共有されます。

6.1.1. Digest Authentication Mechanism

6.1.1. ダイジェスト認証の仕組み

The Digest Authentication Mechanism defined in this memo provides for:

このメモで定義するダイジェスト認証の仕組みは、次のものを提供します。

  • verification of the integrity of a received message, i.e., the message received is the message sent.

    The integrity of the message is protected by computing a digest over an appropriate portion of the message. The digest is computed by the originator of the message, transmitted with the message, and verified by the recipient of the message.

  • verification of the user on whose behalf the message was generated.

    A secret value known only to SNMP engines authorized to generate messages on behalf of a user is used in HMAC mode (see [RFC2104]). It also recommends the hash-function output used as Message Authentication Code, to be truncated.

  • 受信したメッセージの完全性の検証。すなわち、受信したメッセージが送信されたメッセージであることの検証。

    メッセージの完全性は、メッセージの適切な部分に対してダイジェストを計算することで保護されます。ダイジェストは、メッセージの発信者によって計算され、メッセージとともに送信され、メッセージの受信者によって検証されます。

  • そのユーザーに代わってメッセージが生成されたユーザーの検証。

    ユーザーに代わってメッセージを生成することを許可されたSNMPエンジンだけが知っている秘密の値が、HMACモード（[RFC2104] を参照）で使用されます。HMACモードでは、メッセージ認証コードとして使用するハッシュ関数の出力を切り詰めることも推奨しています。

This protocol uses the MD5 [MD5] message digest algorithm. A 128-bit MD5 digest is calculated in a special (HMAC) way over the designated portion of an SNMP message and the first 96 bits of this digest is included as part of the message sent to the recipient. The size of the digest carried in a message is 12 octets. The size of the private authentication key (the secret) is 16 octets. For the details see section 6.3.

このプロトコルは、MD5 [MD5]メッセージダイジェストアルゴリズムを使用します。128ビットのMD5ダイジェストが、SNMPメッセージの指定された部分に対して特別な（HMACの）方法で計算され、このダイジェストの最初の96ビットが、受信者に送信されるメッセージの一部として含まれます。メッセージで運ばれるダイジェストのサイズは12オクテットです。秘密の認証鍵（秘密情報）のサイズは16オクテットです。詳細についてはセクション6.3を参照してください。

6.2. Elements of the Digest Authentication Protocol

6.2. ダイジェスト認証プロトコルの要素

This section contains definitions required to realize the authentication module defined in this section of this memo.

このセクションには、このメモのこのセクションで定義する認証モジュールを実現するために必要な定義が含まれています。

6.2.1. Users

6.2.1. ユーザー

Authentication using this authentication protocol makes use of a defined set of userNames. For any user on whose behalf a message must be authenticated at a particular SNMP engine, that SNMP engine must have knowledge of that user. An SNMP engine that wishes to communicate with another SNMP engine must also have knowledge of a user known to that engine, including knowledge of the applicable attributes of that user.

この認証プロトコルを使用する認証は、定義されたuserNameの集合を利用します。特定のSNMPエンジンで、あるユーザーに代わってメッセージを認証しなければならない場合、そのSNMPエンジンはそのユーザーについて知っていなければなりません。別のSNMPエンジンと通信したいSNMPエンジンも、そのエンジンが知っているユーザーについて、そのユーザーの該当する属性を含めて知っていなければなりません。

A user and its attributes are defined as follows:

ユーザーとその属性は、次のように定義されます。

<userName>
A string representing the name of the user.
<authKey>
A user's secret key to be used when calculating a digest. It MUST be 16 octets long for MD5.
<userName>
ユーザーの名前を表す文字列。
<authKey>
ダイジェストを計算する際に使用する、ユーザーの秘密鍵。MD5の場合、16オクテットの長さでなければなりません（MUST）。

6.2.2. msgAuthoritativeEngineID

6.2.2. msgAuthoritativeEngineID

The msgAuthoritativeEngineID value contained in an authenticated message specifies the authoritative SNMP engine for that particular message (see the definition of SnmpEngineID in the SNMP Architecture document [RFC2271]).

認証済みメッセージに含まれるmsgAuthoritativeEngineIDの値は、その特定のメッセージに対する権威SNMPエンジンを指定します（SNMPアーキテクチャーの文書 [RFC2271] におけるSnmpEngineIDの定義を参照してください）。

The user's (private) authentication key is normally different at each authoritative SNMP engine and so the snmpEngineID is used to select the proper key for the authentication process.

ユーザーの（秘密の）認証鍵は通常、権威SNMPエンジンごとに異なるため、認証処理に適切な鍵を選択するためにsnmpEngineIDが使用されます。

6.2.3. SNMP Messages Using this Authentication Protocol

6.2.3. この認証プロトコルを使用するSNMPメッセージ

Messages using this authentication protocol carry a msgAuthenticationParameters field as part of the msgSecurityParameters. For this protocol, the msgAuthenticationParameters field is the serialized OCTET STRING representing the first 12 octets of the HMAC-MD5-96 output done over the wholeMsg.

この認証プロトコルを使用するメッセージは、msgSecurityParametersの一部としてmsgAuthenticationParametersフィールドを運びます。このプロトコルでは、msgAuthenticationParametersフィールドは、wholeMsgに対して行ったHMAC-MD5-96の出力の最初の12オクテットを表す、シリアル化されたOCTET STRINGです。

The digest is calculated over the wholeMsg so if a message is authenticated, that also means that all the fields in the message are intact and have not been tampered with.

ダイジェストはwholeMsgに対して計算されるため、メッセージが認証されたということは、メッセージ内のすべてのフィールドが完全であり、改ざんされていないことも意味します。

6.2.4. Services provided by the HMAC-MD5-96 Authentication Module

6.2.4. HMAC-MD5-96認証モジュールが提供するサービス

This section describes the inputs and outputs that the HMAC-MD5-96 Authentication module expects and produces when the User-based Security module calls the HMAC-MD5-96 Authentication module for services.

このセクションでは、ユーザーベースセキュリティーモジュールがサービスのためにHMAC-MD5-96認証モジュールを呼び出す際に、HMAC-MD5-96認証モジュールが期待する入力と生成する出力について説明します。

6.2.4.1. Services for Generating an Outgoing SNMP Message
6.2.4.1. 送信SNMPメッセージを生成するためのサービス

The HMAC-MD5-96 authentication protocol assumes that the selection of the authKey is done by the caller and that the caller passes the secret key to be used.

HMAC-MD5-96認証プロトコルは、authKeyの選択は呼び出し元によって行われ、呼び出し元が使用する秘密鍵を渡すことを想定しています。

Upon completion the authentication module returns statusInformation and, if the message digest was correctly calculated, the wholeMsg with the digest inserted at the proper place. The abstract service primitive is:

完了すると、認証モジュールはstatusInformationを返し、メッセージダイジェストが正しく計算された場合は、適切な位置にダイジェストを挿入したwholeMsgを返します。抽象サービスプリミティブは次のとおりです。

   statusInformation =              -- success or failure
     authenticateOutgoingMsg(
     IN   authKey                   -- secret key for authentication
     IN   wholeMsg                  -- unauthenticated complete message
     OUT  authenticatedWholeMsg     -- complete authenticated message
          )

   statusInformation =              -- success or failure
     authenticateOutgoingMsg(
     IN   authKey                   -- secret key for authentication
     IN   wholeMsg                  -- unauthenticated complete message
     OUT  authenticatedWholeMsg     -- complete authenticated message
          )

The abstract data elements are:

抽象データ要素は次のとおりです。

An indication of whether the authentication process was successful. If not it is an indication of the problem.
authKey
The secret key to be used by the authentication algorithm. The length of this key MUST be 16 octets.
wholeMsg
The message to be authenticated.
authenticatedWholeMsg
The authenticated message (including inserted digest) on output.
statusInformation
認証処理が成功したかどうかを示すもの。成功しなかった場合は、問題を示すものです。
authKey

6.3. Elements of Procedure

6.3. 手順要素

This section describes the procedures for the HMAC-MD5-96 authentication protocol.

6.3.1. Processing an Outgoing Message

6.3.1. 送信メッセージの処理

This section describes the procedure followed by an SNMP engine whenever it must authenticate an outgoing message using the usmHMACMD5AuthProtocol.

このセクションでは、SNMPエンジンがusmHMACMD5AuthProtocolを使用して送信メッセージを認証しなければならないときに従う手順について説明します。

  1. The msgAuthenticationParameters field is set to the serialization, according to the rules in [RFC1906], of an OCTET STRING containing 12 zero octets.

  2. From the secret authKey, two keys K1 and K2 are derived:

    1. extend the authKey to 64 octets by appending 48 zero octets; save it as extendedAuthKey
    2. obtain IPAD by replicating the octet 0x36 64 times;
    3. obtain K1 by XORing extendedAuthKey with IPAD;
    4. obtain OPAD by replicating the octet 0x5C 64 times;
    5. obtain K2 by XORing extendedAuthKey with OPAD.
  1. msgAuthenticationParametersフィールドは、12個のゼロのオクテットを含むOCTET STRINGの、[RFC1906] の規則に従ったシリアル化に設定されます。

  2. 秘密のauthKeyから、2つの鍵K1とK2が導出されます。

    1. 48個のゼロのオクテットを付加してauthKeyを64オクテットに拡張し、extendedAuthKeyとして保存する。
    2. オクテット0x36を64回繰り返してIPADを得る。
    3. extendedAuthKeyとIPADのXORをとってK1を得る。
    4. オクテット0x5Cを64回繰り返してOPADを得る。
    5. extendedAuthKeyとOPADのXORをとってK2を得る。
  1. Prepend K1 to the wholeMsg and calculate MD5 digest over it according to [MD5].
  2. Prepend K2 to the result of the step 4 and calculate MD5 digest over it according to [MD5]. Take the first 12 octets of the final digest - this is Message Authentication Code (MAC).
  3. Replace the msgAuthenticationParameters field with MAC obtained in the step 5.
  4. The authenticatedWholeMsg is then returned to the caller together with statusInformation indicating success.
  1. wholeMsgの前にK1を付加し、それに対して[MD5]に従ってMD5ダイジェストを計算します。
  2. ステップ4の結果の前にK2を付加し、それに対して[MD5]に従ってMD5ダイジェストを計算します。最終的なダイジェストの最初の12オクテットをとります。これがメッセージ認証コード（MAC）です。
  3. msgAuthenticationParametersフィールドを、ステップ5で得られたMACで置き換えます。
  4. その後、成功を示すstatusInformationとともに、authenticatedWholeMsgが呼び出し元に返されます。

6.3.2. Processing an Incoming Message

6.3.2. 受信メッセージの処理

This section describes the procedure followed by an SNMP engine whenever it must authenticate an incoming message using the usmHMACMD5AuthProtocol.

このセクションでは、SNMPエンジンがusmHMACMD5AuthProtocolを使用して受信メッセージを認証しなければならないときに従う手順について説明します。

  1. If the digest received in the msgAuthenticationParameters field is not 12 octets long, then an failure and an errorIndication (authenticationError) is returned to the calling module.
  2. The MAC received in the msgAuthenticationParameters field is saved.
  3. The digest in the msgAuthenticationParameters field is replaced by the 12 zero octets.

  4. From the secret authKey, two keys K1 and K2 are derived:

    1. extend the authKey to 64 octets by appending 48 zero octets; save it as extendedAuthKey
    2. obtain IPAD by replicating the octet 0x36 64 times;
    3. obtain K1 by XORing extendedAuthKey with IPAD;
    4. obtain OPAD by replicating the octet 0x5C 64 times;
    5. obtain K2 by XORing extendedAuthKey with OPAD.

  5. The MAC is calculated over the wholeMsg:

    1. prepend K1 to the wholeMsg and calculate the MD5 digest over it;
    2. prepend K2 to the result of step 5.a and calculate the MD5 digest over it;
    3. first 12 octets of the result of step 5.b is the MAC.

    The msgAuthenticationParameters field is replaced with the MAC value that was saved in step 2.

  6. Then the newly calculated MAC is compared with the MAC saved in step 2. If they do not match, then an failure and an errorIndication (authenticationFailure) is returned to the calling module.
  7. The authenticatedWholeMsg and statusInformation indicating success are then returned to the caller.
  1. msgAuthenticationParametersフィールドで受信したダイジェストが12オクテットの長さでない場合、失敗とerrorIndication（authenticationError）が呼び出し元のモジュールに返されます。
  2. msgAuthenticationParametersフィールドで受信したMACが保存されます。
  3. msgAuthenticationParametersフィールドのダイジェストが、12個のゼロのオクテットで置き換えられます。

  4. 秘密のauthKeyから、2つの鍵K1とK2が導出されます。

    1. 48個のゼロのオクテットを付加してauthKeyを64オクテットに拡張し、extendedAuthKeyとして保存する。
    2. オクテット0x36を64回繰り返してIPADを得る。
    3. extendedAuthKeyとIPADのXORをとってK1を得る。
    4. オクテット0x5Cを64回繰り返してOPADを得る。
    5. extendedAuthKeyとOPADのXORをとってK2を得る。

  5. wholeMsgに対してMACが計算されます。

    1. wholeMsgの前にK1を付加し、それに対してMD5ダイジェストを計算する。
    2. ステップ5.aの結果の前にK2を付加し、それに対してMD5ダイジェストを計算する。
    3. ステップ5.bの結果の最初の12オクテットがMACである。

    msgAuthenticationParametersフィールドは、ステップ2で保存されたMACの値で置き換えられます。

  6. 次に、新たに計算されたMACが、ステップ2で保存されたMACと比較されます。一致しない場合、失敗とerrorIndication（authenticationFailure）が呼び出し元のモジュールに返されます。
  7. その後、authenticatedWholeMsgと、成功を示すstatusInformationが呼び出し元に返されます。

7. HMAC-SHA-96 Authentication Protocol

7. HMAC-SHA-96認証プロトコル

This section describes the HMAC-SHA-96 authentication protocol. This protocol uses the SHA hash-function which is described in [SHA-NIST], in HMAC mode described in [RFC2104], truncating the output to 96 bits.

このセクションでは、HMAC-SHA-96認証プロトコルについて説明します。このプロトコルは、[SHA-NIST] で説明されているSHAハッシュ関数を、[RFC2104] で説明されているHMACモードで使用し、出力を96ビットに切り詰めます。

This protocol is identified by usmHMACSHAAuthProtocol.

このプロトコルは、usmHMACSHAAuthProtocolによって識別されます。

Over time, other authentication protocols may be defined either as a replacement of this protocol or in addition to this protocol.

時間の経過とともに、このプロトコルの代替として、またはこのプロトコルに加えて、他の認証プロトコルが定義されるかもしれません。

7.1. Mechanisms

7.1. 仕組み

  • In support of data integrity, a message digest algorithm is required. A digest is calculated over an appropriate portion of an SNMP message and included as part of the message sent to the recipient.
  • In support of data origin authentication and data integrity, a secret value is prepended to the SNMP message prior to computing the digest; the calculated digest is then partially inserted into the message prior to transmission. The prepended secret is not transmitted. The secret value is shared by all SNMP engines authorized to originate messages on behalf of the appropriate user.
  • データの完全性をサポートするために、メッセージダイジェストアルゴリズムが必要です。ダイジェストはSNMPメッセージの適切な部分に対して計算され、受信者に送信されるメッセージの一部として含まれます。
  • データ発信元の認証とデータの完全性をサポートするために、ダイジェストを計算する前に秘密の値がSNMPメッセージの前に付加されます。計算されたダイジェストは、送信前にメッセージに部分的に挿入されます。前に付加された秘密情報は送信されません。秘密の値は、適切なユーザーに代わってメッセージを発信することを許可されたすべてのSNMPエンジンによって共有されます。

7.1.1. Digest Authentication Mechanism

7.1.1. ダイジェスト認証の仕組み

The Digest Authentication Mechanism defined in this memo provides for:

このメモで定義するダイジェスト認証の仕組みは、次のものを提供します。

  • verification of the integrity of a received message, i.e., the the message received is the message sent.

    The integrity of the message is protected by computing a digest over an appropriate portion of the message. The digest is computed by the originator of the message, transmitted with the message, and verified by the recipient of the message.

  • verification of the user on whose behalf the message was generated.

    A secret value known only to SNMP engines authorized to generate messages on behalf of a user is used in HMAC mode (see [RFC2104]). It also recommends the hash-function output used as Message Authentication Code, to be truncated.

  • 受信したメッセージの完全性の検証。すなわち、受信したメッセージが送信されたメッセージであることの検証。

    メッセージの完全性は、メッセージの適切な部分に対してダイジェストを計算することで保護されます。ダイジェストは、メッセージの発信者によって計算され、メッセージとともに送信され、メッセージの受信者によって検証されます。

  • そのユーザーに代わってメッセージが生成されたユーザーの検証。

    ユーザーに代わってメッセージを生成することを許可されたSNMPエンジンだけが知っている秘密の値が、HMACモード（[RFC2104] を参照）で使用されます。HMACモードでは、メッセージ認証コードとして使用するハッシュ関数の出力を切り詰めることも推奨しています。

This mechanism uses the SHA [SHA-NIST] message digest algorithm. A 160-bit SHA digest is calculated in a special (HMAC) way over the designated portion of an SNMP message and the first 96 bits of this digest is included as part of the message sent to the recipient. The size of the digest carried in a message is 12 octets. The size of the private authentication key (the secret) is 20 octets. For the details see section 7.3.

この仕組みは、SHA [SHA-NIST] メッセージダイジェストアルゴリズムを使用します。160ビットのSHAダイジェストが、SNMPメッセージの指定された部分に対して特別な（HMACの）方法で計算され、このダイジェストの最初の96ビットが、受信者に送信されるメッセージの一部として含まれます。メッセージで運ばれるダイジェストのサイズは12オクテットです。秘密の認証鍵（秘密情報）のサイズは20オクテットです。詳細についてはセクション7.3を参照してください。

    2. オクテット0x36を64回繰り返してIPADを得る。
    3. extendedAuthKeyとIPADのXORをとってK1を得る。
    4. オクテット0x5Cを64回繰り返してOPADを得る。
    5. extendedAuthKeyとOPADのXORをとってK2を得る。
  3. wholeMsgの前にK1を付加し、それに対して [SHA-NIST] に従ってSHAダイジェストを計算します。
  4. ステップ4の結果の前にK2を付加し、それに対して [SHA-NIST] に従ってSHAダイジェストを計算します。最終的なダイジェストの最初の12オクテットをとります。これがメッセージ認証コード（MAC）です。
  5. msgAuthenticationParametersフィールドを、ステップ5で得られたMACで置き換えます。
  6. その後、成功を示すstatusInformationとともに、authenticatedWholeMsgが呼び出し元に返されます。

7.3.2. Processing an Incoming Message

7.3.2. 受信メッセージの処理

This section describes the procedure followed by an SNMP engine whenever it must authenticate an incoming message using the usmHMACSHAAuthProtocol.

このセクションでは、SNMPエンジンがusmHMACSHAAuthProtocolを使用して受信メッセージを認証しなければならないときに従う手順について説明します。

  1. If the digest received in the msgAuthenticationParameters field is not 12 octets long, then an failure and an errorIndication (authenticationError) is returned to the calling module.
  2. The MAC received in the msgAuthenticationParameters field is saved.
  3. The digest in the msgAuthenticationParameters field is replaced by the 12 zero octets.

  4. From the secret authKey, two keys K1 and K2 are derived:

    1. extend the authKey to 64 octets by appending 44 zero octets; save it as extendedAuthKey
    2. obtain IPAD by replicating the octet 0x36 64 times;
    3. obtain K1 by XORing extendedAuthKey with IPAD;
    4. obtain OPAD by replicating the octet 0x5C 64 times;
    5. obtain K2 by XORing extendedAuthKey with OPAD.

  5. The MAC is calculated over the wholeMsg:

    1. prepend K1 to the wholeMsg and calculate the SHA digest over it;
    2. prepend K2 to the result of step 5.a and calculate the SHA digest over it;
    3. first 12 octets of the result of step 5.b is the MAC.

    The msgAuthenticationParameters field is replaced with the MAC value that was saved in step 2.

  6. The the newly calculated MAC is compared with the MAC saved in step 2. If they do not match, then a failure and an errorIndication (authenticationFailure) are returned to the calling module.
  7. The authenticatedWholeMsg and statusInformation indicating success are then returned to the caller.
  1. msgAuthenticationParametersフィールドで受信したダイジェストが12オクテットの長さでない場合、失敗とerrorIndication（authenticationError）が呼び出し元のモジュールに返されます。
  2. msgAuthenticationParametersフィールドで受信したMACが保存されます。
  3. msgAuthenticationParametersフィールドのダイジェストが、12個のゼロのオクテットで置き換えられます。

  4. 秘密のauthKeyから、2つの鍵K1とK2が導出されます。

    1. 44個のゼロのオクテットを付加してauthKeyを64オクテットに拡張し、extendedAuthKeyとして保存する。
    2. オクテット0x36を64回繰り返してIPADを得る。
    3. extendedAuthKeyとIPADのXORをとってK1を得る。
    4. オクテット0x5Cを64回繰り返してOPADを得る。
    5. extendedAuthKeyとOPADのXORをとってK2を得る。

  5. wholeMsgに対してMACが計算されます。

    1. wholeMsgの前にK1を付加し、それに対してSHAダイジェストを計算する。
    2. ステップ5.aの結果の前にK2を付加し、それに対してSHAダイジェストを計算する。
    3. ステップ5.bの結果の最初の12オクテットがMACである。

    msgAuthenticationParametersフィールドは、ステップ2で保存されたMACの値で置き換えられます。

  6. 新たに計算されたMACが、ステップ2で保存されたMACと比較されます。一致しない場合、失敗とerrorIndication（authenticationFailure）が呼び出し元のモジュールに返されます。
  7. その後、authenticatedWholeMsgと、成功を示すstatusInformationが呼び出し元に返されます。

8. CBC-DES Symmetric Encryption Protocol

8. CBC-DES対称暗号化プロトコル

This section describes the CBC-DES Symmetric Encryption Protocol. This protocol is the first privacy protocol defined for the User-based Security Model.

このセクションでは、CBC-DES対称暗号化プロトコルについて説明します。このプロトコルは、ユーザーベースセキュリティーモデルのために最初に定義されたプライバシープロトコルです。

This protocol is identified by usmDESPrivProtocol.

このプロトコルは、usmDESPrivProtocolによって識別されます。

Over time, other privacy protocols may be defined either as a replacement of this protocol or in addition to this protocol.

時間の経過とともに、このプロトコルの代替として、またはこのプロトコルに加えて、他のプライバシープロトコルが定義されるかもしれません。

8.1. Mechanisms

8.1. 仕組み

  • In support of data confidentiality, an encryption algorithm is required. An appropriate portion of the message is encrypted prior to being transmitted. The User-based Security Model specifies that the scopedPDU is the portion of the message that needs to be encrypted.
  • A secret value in combination with a timeliness value is used to create the en/decryption key and the initialization vector. The secret value is shared by all SNMP engines authorized to originate messages on behalf of the appropriate user.
  • データの機密性をサポートするために、暗号化アルゴリズムが必要です。メッセージの適切な部分が、送信前に暗号化されます。ユーザーベースセキュリティーモデルでは、暗号化する必要があるメッセージの部分はscopedPDUであると規定しています。
  • 秘密の値と適時性の値を組み合わせて、暗号化・復号の鍵と初期化ベクターを作成します。秘密の値は、適切なユーザーに代わってメッセージを発信することを許可されたすべてのSNMPエンジンによって共有されます。

8.1.1. Symmetric Encryption Protocol

8.1.1. 対称暗号化プロトコル

The Symmetric Encryption Protocol defined in this memo provides support for data confidentiality. The designated portion of an SNMP message is encrypted and included as part of the message sent to the recipient.

このメモで定義する対称暗号化プロトコルは、データの機密性のサポートを提供します。SNMPメッセージの指定された部分が暗号化され、受信者に送信されるメッセージの一部として含まれます。

Two organizations have published specifications defining the DES: the National Institute of Standards and Technology (NIST) [DES-NIST] and the American National Standards Institute [DES-ANSI]. There is a companion Modes of Operation specification for each definition ([DESO-NIST] and [DESO-ANSI], respectively).

2つの組織がDESを定義する仕様を公開しています。米国国立標準技術研究所（NIST） [DES-NIST] と米国国家規格協会 [DES-ANSI] です。それぞれの定義には、対応する運用モードの仕様があります（それぞれ [DESO-NIST] と [DESO-ANSI]）。

The NIST has published three additional documents that implementors may find useful.

NISTは、実装者にとって有用と思われる追加の文書を3つ公開しています。

  • There is a document with guidelines for implementing and using the DES, including functional specifications for the DES and its modes of operation [DESG-NIST].
  • There is a specification of a validation test suite for the DES [DEST-NIST]. The suite is designed to test all aspects of the DES and is useful for pinpointing specific problems.
  • There is a specification of a maintenance test for the DES [DESM-NIST]. The test utilizes a minimal amount of data and processing to test all components of the DES. It provides a simple yes-or-no indication of correct operation and is useful to run as part of an initialization step, e.g., when a computer re-boots.
  • DESとその運用モードの機能仕様を含む、DESの実装と使用のためのガイドラインを記した文書 [DESG-NIST]。
  • DESの検証テストスイートの仕様 [DEST-NIST]。このスイートは、DESのあらゆる側面をテストするように設計されており、具体的な問題を特定するのに役立ちます。
  • DESの保守テストの仕様 [DESM-NIST]。このテストは、最小限のデータと処理を使用してDESのすべての構成要素をテストします。正しく動作しているかどうかを単純なyes/noで示し、たとえばコンピューターの再起動時など、初期化ステップの一部として実行するのに役立ちます。
8.1.1.1. DES key and Initialization Vector.
8.1.1.1. DES鍵と初期化ベクター

The first 8 octets of the 16-octet secret (private privacy key) are used as a DES key. Since DES uses only 56 bits, the Least Significant Bit in each octet is disregarded.

16オクテットの秘密情報（秘密のプライバシー鍵）の最初の8オクテットが、DES鍵として使用されます。DESは56ビットしか使用しないため、各オクテットの最下位ビットは無視されます。

The Initialization Vector for encryption is obtained using the following procedure.

暗号化のための初期化ベクターは、次の手順で得られます。

The last 8 octets of the 16-octet secret (private privacy key) are used as pre-IV.

16オクテットの秘密情報（秘密のプライバシー鍵）の最後の8オクテットが、プレIVとして使用されます。

In order to ensure that the IV for two different packets encrypted by the same key, are not the same (i.e., the IV does not repeat) we need to "salt" the pre-IV with something unique per packet. An 8-octet string is used as the "salt". The concatenation of the generating SNMP engine's 32-bit snmpEngineBoots and a local 32-bit integer, that the encryption engine maintains, is input to the "salt". The 32-bit integer is initialized to an arbitrary value at boot time.

同じ鍵で暗号化された2つの異なるパケットのIVが同じにならない（つまり、IVが繰り返されない）ようにするために、パケットごとに一意な何かでプレIVに「ソルト」を加える必要があります。「ソルト」として8オクテットの文字列が使用されます。生成するSNMPエンジンの32ビットのsnmpEngineBootsと、暗号化エンジンが保持するローカルの32ビット整数とを連結したものが、「ソルト」への入力になります。32ビット整数は、起動時に任意の値に初期化されます。

The 32-bit snmpEngineBoots is converted to the first 4 octets (Most Significant Byte first) of our "salt". The 32-bit integer is then converted to the last 4 octet (Most Significant Byte first) of our "salt". The resulting "salt" is then XOR-ed with the pre-IV. The 8-octet "salt" is then put into the privParameters field encoded as an OCTET STRING. The "salt" integer is then modified. We recommend that it be incremented by one and wrap when it reaches the maximum value.

32ビットのsnmpEngineBootsは、「ソルト」の最初の4オクテット（最上位バイトが先）に変換されます。次に、32ビット整数が「ソルト」の最後の4オクテット（最上位バイトが先）に変換されます。得られた「ソルト」は、プレIVとXORされます。次に、8オクテットの「ソルト」が、OCTET STRINGとしてエンコードされてprivParametersフィールドに格納されます。その後、「ソルト」の整数が変更されます。1ずつインクリメントし、最大値に達したら折り返すことを推奨します。

How exactly the value of the "salt" (and thus of the IV) varies, is an implementation issue, as long as the measures are taken to avoid producing a duplicate IV.

重複したIVの生成を避ける手段がとられている限り、「ソルト」の値（したがってIVの値）が正確にどのように変化するかは実装上の問題です。

The "salt" must be placed in the privParameters field to enable the receiving entity to compute the correct IV and to decrypt the message.

受信側エンティティーが正しいIVを計算してメッセージを復号できるように、「ソルト」はprivParametersフィールドに格納しなければなりません。

8.1.1.2. Data Encryption.
8.1.1.2. データの暗号化

The data to be encrypted is treated as sequence of octets. Its length should be an integral multiple of 8 - and if it is not, the data is padded at the end as necessary. The actual pad value is irrelevant.

暗号化するデータは、オクテットの並びとして扱われます。その長さは8の整数倍であるべきであり、そうでない場合は、必要に応じてデータの末尾にパディングが付加されます。実際のパディングの値は重要ではありません。

The data is encrypted in Cipher Block Chaining mode.

データは暗号ブロック連鎖（Cipher Block Chaining）モードで暗号化されます。

The plaintext is divided into 64-bit blocks.

平文は64ビットのブロックに分割されます。

The plaintext for each block is XOR-ed with the ciphertext of the previous block, the result is encrypted and the output of the encryption is the ciphertext for the block. This procedure is repeated until there are no more plaintext blocks.

各ブロックの平文は、前のブロックの暗号文とXORされ、その結果が暗号化され、暗号化の出力がそのブロックの暗号文になります。この手順は、平文のブロックがなくなるまで繰り返されます。

For the very first block, the Initialization Vector is used instead of the ciphertext of the previous block.

最初のブロックでは、前のブロックの暗号文の代わりに初期化ベクターが使用されます。

8.1.1.3. Data Decryption
8.1.1.3. データの復号

Before decryption, the encrypted data length is verified. If the length of the OCTET STRING to be decrypted is not an integral multiple of 8 octets, the decryption process is halted and an appropriate exception noted. When decrypting, the padding is ignored.

復号の前に、暗号化されたデータの長さが検証されます。復号するOCTET STRINGの長さが8オクテットの整数倍でない場合、復号処理は中止され、適切な例外が記録されます。復号の際、パディングは無視されます。

The first ciphertext block is decrypted, the decryption output is XOR-ed with the Initialization Vector, and the result is the first plaintext block.

最初の暗号文ブロックが復号され、復号の出力が初期化ベクターとXORされ、その結果が最初の平文ブロックになります。

For each subsequent block, the ciphertext block is decrypted, the decryption output is XOR-ed with the previous ciphertext block and the result is the plaintext block.

後続の各ブロックについては、暗号文ブロックが復号され、復号の出力が前の暗号文ブロックとXORされ、その結果が平文ブロックになります。

8.2. Elements of the DES Privacy Protocol

8.2. DESプライバシープロトコルの要素

This section contains definitions required to realize the privacy module defined by this memo.

このセクションには、このメモで定義するプライバシーモジュールを実現するために必要な定義が含まれています。

8.2.1. Users

8.2.1. ユーザー

Data en/decryption using this Symmetric Encryption Protocol makes use of a defined set of userNames. For any user on whose behalf a message must be en/decrypted at a particular SNMP engine, that SNMP engine must have knowledge of that user. An SNMP engine that wishes to communicate with another SNMP engine must also have knowledge of a user known to that SNMP engine, including knowledge of the applicable attributes of that user.

この対称暗号化プロトコルを使用するデータの暗号化・復号は、定義されたuserNameの集合を利用します。特定のSNMPエンジンで、あるユーザーに代わってメッセージを暗号化・復号しなければならない場合、そのSNMPエンジンはそのユーザーについて知っていなければなりません。別のSNMPエンジンと通信したいSNMPエンジンも、そのSNMPエンジンが知っているユーザーについて、そのユーザーの該当する属性を含めて知っていなければなりません。

A user and its attributes are defined as follows:

ユーザーとその属性は、次のように定義されます。

<userName>
An octet string representing the name of the user.
<privKey>
A user's secret key to be used as input for the DES key and IV. The length of this key MUST be 16 octets.
<userName>
ユーザーの名前を表すオクテット文字列。
<privKey>
DES鍵とIVの入力として使用する、ユーザーの秘密鍵。この鍵の長さは16オクテットでなければなりません（MUST）。

8.2.2. msgAuthoritativeEngineID

8.2.2. msgAuthoritativeEngineID

The msgAuthoritativeEngineID value contained in an authenticated message specifies the authoritative SNMP engine for that particular message (see the definition of SnmpEngineID in the SNMP Architecture document [RFC2271]).

認証済みメッセージに含まれるmsgAuthoritativeEngineIDの値は、その特定のメッセージに対する権威SNMPエンジンを指定します（SNMPアーキテクチャーの文書 [RFC2271] におけるSnmpEngineIDの定義を参照してください）。

The user's (private) privacy key is normally different at each authoritative SNMP engine and so the snmpEngineID is used to select the proper key for the en/decryption process.

ユーザーの（秘密の）プライバシー鍵は通常、権威SNMPエンジンごとに異なるため、暗号化・復号の処理に適切な鍵を選択するためにsnmpEngineIDが使用されます。

8.2.3. SNMP Messages Using this Privacy Protocol

8.2.3. このプライバシープロトコルを使用するSNMPメッセージ

Messages using this privacy protocol carry a msgPrivacyParameters field as part of the msgSecurityParameters. For this protocol, the msgPrivacyParameters field is the serialized OCTET STRING representing the "salt" that was used to create the IV.

このプライバシープロトコルを使用するメッセージは、msgSecurityParametersの一部としてmsgPrivacyParametersフィールドを運びます。このプロトコルでは、msgPrivacyParametersフィールドは、IVの作成に使用された「ソルト」を表すシリアル化されたOCTET STRINGです。

8.2.4. DESプライバシーモジュールが提供するサービス

このセクションでは、ユーザーベースセキュリティーモジュールがサービスのためにDESプライバシーモジュールを呼び出す際に、DESプライバシーモジュールが期待する入力と生成する出力について説明します。

8.2.4.1. 送信データを暗号化するためのサービス

8.3. Elements of Procedure.

8.3. 手順要素

This section describes the procedures for the DES privacy protocol.

このセクションでは、DESプライバシープロトコルの手順について説明します。

8.3.1. Processing an Outgoing Message

8.3.1. 送信メッセージの処理

This section describes the procedure followed by an SNMP engine whenever it must encrypt part of an outgoing message using the usmDESPrivProtocol.

このセクションでは、SNMPエンジンがusmDESPrivProtocolを使用して送信メッセージの一部を暗号化しなければならないときに従う手順について説明します。

  1. The secret cryptKey is used to construct the DES encryption key, the "salt" and the DES pre-IV (as described in section 8.1.1.1).
  2. The privParameters field is set to the serialization according to the rules in [RFC1906] of an OCTET STRING representing the the "salt" string.
  3. The scopedPDU is encrypted (as described in section 8.1.1.2) and the encrypted data is serialized according to the rules in [RFC1906] as an OCTET STRING.
  4. The serialized OCTET STRING representing the encrypted scopedPDU together with the privParameters and statusInformation indicating success is returned to the calling module.
  1. 秘密のcryptKeyを使用して、DES暗号鍵、「ソルト」、DESのプレIVを構築します（セクション8.1.1.1で説明されているとおりです）。
  2. privParametersフィールドは、「ソルト」の文字列を表すOCTET STRINGの、[RFC1906] の規則に従ったシリアル化に設定されます。
  3. scopedPDUが（セクション8.1.1.2で説明されているとおりに）暗号化され、暗号化されたデータが、[RFC1906] の規則に従ってOCTET STRINGとしてシリアル化されます。
  4. 暗号化されたscopedPDUを表すシリアル化されたOCTET STRINGが、privParametersと、成功を示すstatusInformationとともに、呼び出し元のモジュールに返されます。

8.3.2. Processing an Incoming Message

8.3.2. 受信メッセージの処理

This section describes the procedure followed by an SNMP engine whenever it must decrypt part of an incoming message using the usmDESPrivProtocol.

このセクションでは、SNMPエンジンがusmDESPrivProtocolを使用して受信メッセージの一部を復号しなければならないときに従う手順について説明します。

  1. If the privParameters field is not an 8-octet OCTET STRING, then an error indication (decryptionError) is returned to the calling module.
  2. The "salt" is extracted from the privParameters field.
  3. The secret cryptKey and the "salt" are then used to construct the DES decryption key and pre-IV (as described in section 8.1.1.1).
  4. The encryptedPDU is then decrypted (as described in section 8.1.1.3).
  5. If the encryptedPDU cannot be decrypted, then an error indication (decryptionError) is returned to the calling module.
  6. The decrypted scopedPDU and statusInformation indicating success are returned to the calling module.
  1. privParametersフィールドが8オクテットのOCTET STRINGでない場合、エラー通知（decryptionError）が呼び出し元のモジュールに返されます。
  2. privParametersフィールドから「ソルト」が抽出されます。
  3. 次に、秘密のcryptKeyと「ソルト」を使用して、DES復号鍵とプレIVを構築します（セクション8.1.1.1で説明されているとおりです）。
  4. 次に、encryptedPDUが（セクション8.1.1.3で説明されているとおりに）復号されます。
  5. encryptedPDUを復号できない場合、エラー通知（decryptionError）が呼び出し元のモジュールに返されます。
  6. 復号されたscopedPDUと、成功を示すstatusInformationが、呼び出し元のモジュールに返されます。

11. Security Considerations

11. セキュリティーに関する考慮事項

11.1. Recommended Practices

11.1. 推奨される実践

This section describes practices that contribute to the secure, effective operation of the mechanisms defined in this memo.

このセクションでは、このメモで定義する仕組みの安全で効果的な運用に役立つ実践について説明します。

  • An SNMP engine must discard SNMP Response messages that do not correspond to any currently outstanding Request message. It is the responsibility of the Message Processing module to take care of this. For example it can use a msgID for that.

    An SNMP Command Generator Application must discard any Response PDU for which there is no currently outstanding Request PDU; for example for SNMPv2 [RFC1905] PDUs, the request-id component in the PDU can be used to correlate Responses to outstanding Requests.

    Although it would be typical for an SNMP engine and an SNMP Command Generator Application to do this as a matter of course, when using these security protocols it is significant due to the possibility of message duplication (malicious or otherwise).

  • If an SNMP engine uses a msgID for correlating Response messages to outstanding Request messages, then it MUST use different msgIDs in all such Request messages that it sends out during a Time Window (150 seconds) period.

    A Command Generator or Notification Originator Application MUST use different request-ids in all Request PDUs that it sends out during a TimeWindow (150 seconds) period.

    This must be done to protect against the possibility of message duplication (malicious or otherwise).

    For example, starting operations with a msgID and/or request-id value of zero is not a good idea. Initializing them with an unpredictable number (so they do not start out the same after each reboot) and then incrementing by one would be acceptable.

  • An SNMP engine should perform time synchronization using authenticated messages in order to protect against the possibility of message duplication (malicious or otherwise).

  • When sending state altering messages to a managed authoritative SNMP engine, a Command Generator Application should delay sending successive messages to that managed SNMP engine until a positive acknowledgement is received for the previous message or until the previous message expires.

    No message ordering is imposed by the SNMP. Messages may be received in any order relative to their time of generation and each will be processed in the ordered received. Note that when an authenticated message is sent to a managed SNMP engine, it will be valid for a period of time of approximately 150 seconds under normal circumstances, and is subject to replay during this period. Indeed, an SNMP engine and SNMP Command Generator Applications must cope with the loss and re-ordering of messages resulting from anomalies in the network as a matter of course.

    However, a managed object, snmpSetSerialNo [RFC1907], is specifically defined for use with SNMP Set operations in order to provide a mechanism to ensure that the processing of SNMP messages occurs in a specific order.

  • The frequency with which the secrets of a User-based Security Model user should be changed is indirectly related to the frequency of their use.

    Protecting the secrets from disclosure is critical to the overall security of the protocols. Frequent use of a secret provides a continued source of data that may be useful to a cryptanalyst in exploiting known or perceived weaknesses in an algorithm. Frequent changes to the secret avoid this vulnerability.

    Changing a secret after each use is generally regarded as the most secure practice, but a significant amount of overhead may be associated with that approach.

    Note, too, in a local environment the threat of disclosure may be less significant, and as such the changing of secrets may be less frequent. However, when public data networks are used as the communication paths, more caution is prudent.

  • SNMPエンジンは、現在未処理のどの要求メッセージにも対応しないSNMP応答メッセージを破棄しなければなりません。これを処理するのはメッセージ処理モジュールの責任です。たとえば、そのためにmsgIDを使用できます。

    SNMPコマンドジェネレーターアプリケーションは、現在未処理の要求PDUが存在しない応答PDUをすべて破棄しなければなりません。たとえば、SNMPv2 [RFC1905] のPDUでは、PDU内のrequest-id構成要素を使用して、応答を未処理の要求と関連付けることができます。

    SNMPエンジンとSNMPコマンドジェネレーターアプリケーションがこれを当然のこととして行うのは一般的ですが、これらのセキュリティープロトコルを使用する場合は、（悪意によるものであれ、そうでないものであれ）メッセージの重複の可能性があるため、これは重要です。

  • SNMPエンジンが応答メッセージを未処理の要求メッセージと関連付けるためにmsgIDを使用する場合、時間枠（150秒）の期間中に送信するそのようなすべての要求メッセージで、異なるmsgIDを使用しなければなりません（MUST）。

    コマンドジェネレーターアプリケーションまたは通知発信者アプリケーションは、時間枠（150秒）の期間中に送信するすべての要求PDUで、異なるrequest-idを使用しなければなりません（MUST）。

    これは、（悪意によるものであれ、そうでないものであれ）メッセージの重複の可能性から保護するために行わなければなりません。

    たとえば、msgIDやrequest-idの値を0から始めて操作を開始するのはよい考えではありません。それらを予測不可能な数値で初期化し（再起動のたびに同じ値から始まらないようにするため）、その後1ずつインクリメントするのは許容できるでしょう。

  • SNMPエンジンは、（悪意によるものであれ、そうでないものであれ）メッセージの重複の可能性から保護するために、認証済みメッセージを使用して時刻の同期を行うべきです。

  • 管理対象の権威SNMPエンジンに状態を変更するメッセージを送信する場合、コマンドジェネレーターアプリケーションは、前のメッセージに対する肯定的な確認応答を受信するか、前のメッセージが期限切れになるまで、その管理対象SNMPエンジンへの後続のメッセージの送信を遅らせるべきです。

    SNMPはメッセージの順序付けを課していません。メッセージは、生成時刻に対して任意の順序で受信される可能性があり、それぞれ受信された順序で処理されます。認証済みメッセージが管理対象SNMPエンジンに送信されると、通常の状況では約150秒の期間有効であり、この期間中はリプレイされる可能性があることに注意してください。実際、SNMPエンジンとSNMPコマンドジェネレーターアプリケーションは、ネットワークの異常に起因するメッセージの損失や順序の入れ替えに当然対処しなければなりません。

    ただし、管理オブジェクトsnmpSetSerialNo [RFC1907] は、SNMPメッセージの処理が特定の順序で行われることを保証する仕組みを提供するために、SNMPのSet操作で使用するために特に定義されています。

  • ユーザーベースセキュリティーモデルのユーザーの秘密情報を変更すべき頻度は、その使用の頻度に間接的に関係しています。

    秘密情報を漏洩から保護することは、プロトコル全体のセキュリティーにとって極めて重要です。秘密情報を頻繁に使用すると、アルゴリズムの既知の弱点や認識されている弱点を突くうえで暗号解読者に役立つ可能性のあるデータを継続的に提供することになります。秘密情報を頻繁に変更することで、この脆弱性を回避できます。

    使用するたびに秘密情報を変更することは一般に最も安全な実践とみなされていますが、そのアプローチには大きなオーバーヘッドが伴う可能性があります。

    また、ローカルな環境では漏洩の脅威はそれほど重大ではない場合があり、そのため秘密情報の変更の頻度は低くてもよいかもしれないことにも注意してください。ただし、公衆データネットワークを通信経路として使用する場合は、より慎重になるのが賢明です。

11.2. Defining Users

11.2. ユーザーの定義

The mechanisms defined in this document employ the notion of users on whose behalf messages are sent. How "users" are defined is subject to the security policy of the network administration. For example, users could be individuals (e.g., "joe" or "jane"), or a particular role (e.g., "operator" or "administrator"), or a combination (e.g., "joe-operator", "jane-operator" or "joe-admin"). Furthermore, a user may be a logical entity, such as an SNMP Application or a set of SNMP Applications, acting on behalf of an individual or role, or set of individuals, or set of roles, including combinations.

この文書で定義する仕組みは、そのユーザーに代わってメッセージが送信されるユーザーという概念を採用しています。「ユーザー」をどのように定義するかは、ネットワーク管理のセキュリティーポリシーに従います。たとえば、ユーザーは、個人（たとえば"joe"や"jane"）、特定の役割（たとえば"operator"や"administrator"）、またはそれらの組み合わせ（たとえば"joe-operator"、"jane-operator"、"joe-admin"）でありえます。さらに、ユーザーは、個人や役割、個人の集合や役割の集合（それらの組み合わせを含む）に代わって動作する、SNMPアプリケーションやSNMPアプリケーションの集合などの論理的なエンティティーである場合もあります。

Appendix A describes an algorithm for mapping a user "password" to a 16 octet value for use as either a user's authentication key or privacy key (or both). Note however, that using the same password (and therefore the same key) for both authentication and privacy is very poor security practice and should be strongly discouraged. Passwords are often generated, remembered, and input by a human. Human-generated passwords may be less than the 16 octets required by the authentication and privacy protocols, and brute force attacks can be quite easy on a relatively short ASCII character set. Therefore, the algorithm is Appendix A performs a transformation on the password. If the Appendix A algorithm is used, SNMP implementations (and SNMP configuration applications) must ensure that passwords are at least 8 characters in length.

付録Aでは、ユーザーの「パスワード」を、ユーザーの認証鍵またはプライバシー鍵（あるいはその両方）として使用する16オクテットの値に対応付けるアルゴリズムについて説明しています。ただし、認証とプライバシーの両方に同じパスワード（したがって同じ鍵）を使用することは非常に悪いセキュリティーの実践であり、強く避けるべきであることに注意してください。パスワードは多くの場合、人間によって生成され、記憶され、入力されます。人間が生成したパスワードは、認証プロトコルとプライバシープロトコルが必要とする16オクテットに満たない場合があり、比較的短いASCII文字セットでは総当たり攻撃が非常に容易になりえます。そのため、付録Aのアルゴリズムはパスワードに変換を施します。付録Aのアルゴリズムを使用する場合、SNMPの実装（およびSNMPの設定アプリケーション）は、パスワードが少なくとも8文字の長さであることを保証しなければなりません。

Because the Appendix A algorithm uses such passwords (nearly) directly, it is very important that they not be easily guessed. It is suggested that they be composed of mixed-case alphanumeric and punctuation characters that don't form words or phrases that might be found in a dictionary. Longer passwords improve the security of the system. Users may wish to input multiword phrases to make their password string longer while ensuring that it is memorable.

付録Aのアルゴリズムはそのようなパスワードを（ほぼ）直接使用するため、パスワードが容易に推測されないことが非常に重要です。パスワードは、辞書に載っているような単語や語句にならない、大文字小文字を混在させた英数字と句読文字で構成することが推奨されます。パスワードが長いほど、システムのセキュリティーは向上します。ユーザーは、パスワードを覚えやすく保ちつつパスワード文字列を長くするために、複数の単語からなるフレーズを入力したいと考えるかもしれません。

Since it is infeasible for human users to maintain different passwords for every SNMP engine, but security requirements strongly discourage having the same key for more than one SNMP engine, the User-based Security Model employs a compromise proposed in [Localized-Key]. It derives the user keys for the SNMP engines from user's password in such a way that it is practically impossible to either determine the user's password, or user's key for another SNMP engine from any combination of user's keys on SNMP engines.

人間のユーザーがSNMPエンジンごとに異なるパスワードを維持するのは現実的ではありませんが、セキュリティー要件の観点からは、複数のSNMPエンジンで同じ鍵を持つことは強く避けるべきです。そのため、ユーザーベースセキュリティーモデルは、[Localized-Key] で提案された妥協案を採用しています。これは、SNMPエンジンにおけるユーザーの鍵をどのように組み合わせても、ユーザーのパスワードや別のSNMPエンジンにおけるユーザーの鍵を割り出すことが事実上不可能になるような方法で、ユーザーのパスワードからSNMPエンジンのユーザーの鍵を導出します。

Note however, that if user's password is disclosed, then key localization will not help and network security may be compromised in this case. Therefore a user's password or non-localized key MUST NOT be stored on a managed device/node. Instead the localized key SHALL be stored (if at all) , so that, in case a device does get compromised, no other managed or managing devices get compromised.

ただし、ユーザーのパスワードが漏洩した場合、鍵のローカライズは役に立たず、この場合はネットワークのセキュリティーが損なわれる可能性があることに注意してください。そのため、ユーザーのパスワードやローカライズされていない鍵を管理対象のデバイス・ノードに保存してはなりません（MUST NOT）。その代わりに、デバイスが侵害された場合でも他の管理対象デバイスや管理側デバイスが侵害されないように、（保存するのであれば）ローカライズされた鍵を保存することになります（SHALL）。

11.3. Conformance

11.3. 適合性

To be termed a "Secure SNMP implementation" based on the User-based Security Model, an SNMP implementation MUST:

ユーザーベースセキュリティーモデルに基づく「安全なSNMP実装」と呼ばれるためには、SNMP実装は次のことをしなければなりません（MUST）。

  • implement one or more Authentication Protocol(s). The HMAC-MD5-96 and HMAC-SHA-96 Authentication Protocols defined in this memo are examples of such protocols.
  • to the maximum extent possible, prohibit access to the secret(s) of each user about which it maintains information in a Local Configuration Datastore (LCD) under all circumstances except as required to generate and/or validate SNMP messages with respect to that user.
  • implement the key-localization mechanism.
  • implement the SNMP-USER-BASED-SM-MIB.
  • 1つ以上の認証プロトコルを実装する。このメモで定義するHMAC-MD5-96認証プロトコルとHMAC-SHA-96認証プロトコルは、そのようなプロトコルの例です。
  • ローカル設定データストア（LCD）に情報を保持している各ユーザーの秘密情報へのアクセスを、そのユーザーに関するSNMPメッセージの生成や検証に必要な場合を除き、あらゆる状況において可能な限り禁止する。
  • 鍵のローカライズの仕組みを実装する。
  • SNMP-USER-BASED-SM-MIBを実装する。

In addition, an authoritative SNMP engine SHOULD provide initial configuration in accordance with Appendix A.1.

さらに、権威SNMPエンジンは、付録A.1に従った初期設定を提供すべきです（SHOULD）。

Implementation of a Privacy Protocol (the DES Symmetric Encryption Protocol defined in this memo is one such protocol) is optional.

プライバシープロトコル（このメモで定義するDES対称暗号化プロトコルはそのようなプロトコルの1つです）の実装は任意です。

A.2.1. Password to Key Sample Code for MD5

A.2.1. MD5のためのパスワードから鍵へのサンプルコード 

void password_to_key_md5(

   u_char *password,    /* IN */
   u_int   passwordlen, /* IN */
   u_char *engineID,    /* IN  - pointer to snmpEngineID  */
   u_int   engineLength /* IN  - length of snmpEngineID */
   u_char *key)         /* OUT - pointer to caller 16-octet buffer */

{

   MD5_CTX     MD;
   u_char     *cp, password_buf[64];
   u_long      password_index = 0;
   u_long      count = 0, i;

   MD5Init (&MD);   /* initialize MD5 */
   /**********************************************/
   /* Use while loop until we've done 1 Megabyte */
   /**********************************************/
   while (count < 1048576) {
      cp = password_buf;
      for (i = 0; i < 64; i++) {
          /*************************************************/
          /* Take the next octet of the password, wrapping */
          /* to the beginning of the password as necessary.*/
          /*************************************************/
          *cp++ = password[password_index++ % passwordlen];
      }
      MD5Update (&MD, password_buf, 64);
      count += 64;
   }
   MD5Final (key, &MD);          /* tell MD5 we're done */

   /*****************************************************/
   /* Now localize the key with the engineID and pass   */
   /* through MD5 to produce final key                  */
   /* May want to ensure that engineLength <= 32,       */
   /* otherwise need to use a buffer larger than 64     */
   /*****************************************************/
   memcpy(password_buf, key, 16);
   memcpy(password_buf+16, engineID, engineLength);
   memcpy(password_buf+engineLength, key, 16);

   MD5Init(&MD);
   MD5Update(&MD, password_buf, 32+engineLength);
   MD5Final(key, &MD);

   return;

}
