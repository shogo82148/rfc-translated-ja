RFC 10050

Protocol-Specific Profiles for JSContact

RFC 10050

JSContactのためのプロトコル固有のプロファイル

Abstract

概要

This document defines the "JSContact Profiles" registry, an IANA registry for named subsets of JSContact elements. The document aims to facilitate using JSContact in the context of contact data exchange protocols or other use cases in which supporting all JSContact semantics might be inappropriate.

この文書は、JSContactの要素の名前付きサブセットのためのIANAレジストリーである「JSContact Profiles」レジストリーを定義します。この文書は、連絡先データ交換プロトコルや、JSContactのすべてのセマンティクスをサポートすることが不適切な場合があるその他のユースケースの文脈において、JSContactの使用を容易にすることを目的としています。

1. Introduction

1. はじめに

The JSContact [RFC9553] contact card data model and format are designed for use in address book applications and directory services. Intended as an alternative to the prevalent vCard [RFC6350] data format, JSContact covers vCard core semantics and extensions, and it provides a rich model for personal names, postal addresses, and localization. All JSContact elements are relevant for some contact card use cases, and similar to vCard, implementations are expected to support these elements when exchanging contact card information using protocols such as CardDAV [RFC6352] and the JSON Meta Application Protocol (JMAP) for Contacts [RFC9610].

JSContact[RFC9553]の連絡先カードのデータモデルと形式は、アドレス帳アプリケーションとディレクトリーサービスで使用するために設計されています。広く普及しているvCard[RFC6350]データ形式の代替として意図されたJSContactは、vCardの中核的なセマンティクスと拡張をカバーし、個人名、郵便住所、およびローカライゼーションのための豊富なモデルを提供します。JSContactのすべての要素は何らかの連絡先カードのユースケースに関係しており、vCardと同様に、実装は、CardDAV[RFC6352]やJSON Meta Application Protocol（JMAP）for Contacts[RFC9610]などのプロトコルを使用して連絡先カードの情報を交換する際に、これらの要素をサポートすることが期待されます。

In contrast, other protocols and document specifications might require exchanging some contact card information, but not all of what JSContact provides. Section 1.7.4 of [RFC9553] outlines how JSContact implementations may ignore unknown JSContact elements, but this only applies to future extensions of [RFC9553]; they are still expected to implement all elements of the core specification. Also, the extensibility of JSContact and the requirement to preserve arbitrary contact elements might not be adequate for some protocols.

対照的に、他のプロトコルや文書仕様では、連絡先カードの情報の一部の交換を必要とするものの、JSContactが提供するもののすべてを必要としない場合があります。[RFC9553]のSection 1.7.4は、JSContactの実装が未知のJSContactの要素をどのように無視してよいかを概説していますが、これは[RFC9553]の将来の拡張にのみ適用され、実装は依然として中核仕様のすべての要素を実装することが期待されます。また、JSContactの拡張性と任意の連絡先の要素を保持するという要件は、一部のプロトコルにとって適切でない場合があります。

To make use of JSContact under these circumstances, this document defines a new IANA registry for JSContact that allows registration of named subsets of JSContact elements. These subsets are referred to as "JSContact profiles" and are meant to bring the following benefits:

このような状況でJSContactを利用するために、この文書は、JSContactの要素の名前付きサブセットの登録を可能にする、JSContactの新しいIANAレジストリーを定義します。これらのサブセットは「JSContactプロファイル」と呼ばれ、次の利点をもたらすことを目的としています：

  • Protocol designers might be encouraged to use JSContact rather than coming up with their own contacts format. This facilitates cross-protocol data exchange and migration.
  • Different protocols use the same IANA registry to express which JSContact elements they support. This facilitates understanding their commonalities and reusing existing profiles.
  • A central registry provides implementors of JSContact libraries with a consistent format documenting which profile supports what elements rather than having to look up that information from possibly distinctly organized Internet-Drafts.
  • プロトコルの設計者が、独自の連絡先の形式を考案するのではなく、JSContactを使用するよう促される可能性があります。これにより、プロトコル間のデータ交換と移行が容易になります。
  • 異なるプロトコルが、どのJSContactの要素をサポートしているかを表すために同じIANAレジストリーを使用します。これにより、それらの共通点の理解と既存のプロファイルの再利用が容易になります。
  • 中央のレジストリーにより、JSContactライブラリーの実装者は、どのプロファイルがどの要素をサポートしているかを記述した一貫した形式を得られ、異なる構成をとっている可能性のあるInternet-Draftからその情報を調べる必要がなくなります。

This document is organized as follows. Section 3 defines JSContact profiles; Section 4 discusses the new "JSContact Profiles" registry created by IANA; and Appendix A illustrates JSContact profiles using an example.

この文書の構成は次のとおりです。Section 3ではJSContactプロファイルを定義し、Section 4ではIANAによって作成された新しい「JSContact Profiles」レジストリーについて議論し、Appendix Aでは例を使用してJSContactプロファイルを説明します。

2. Notational Conventions

2. 表記上の規則

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

The ABNF definitions in this document use the notations of [RFC5234]. ABNF rules not defined in this document are defined in [RFC5234] (such as the ABNF for DIGIT).

この文書のABNFの定義は、[RFC5234]の表記法を使用します。この文書で定義されていないABNFの規則（DIGITのABNFなど）は、[RFC5234]で定義されています。

3. JSContact Profiles

3. JSContactプロファイル

A JSContact profile is a named and versioned set of JSContact elements, such as properties, types, and values. The JSContact elements MUST be registered in the IANA "JSContact" registry group [IANA.jscontact]. A profile MAY define additional restrictions for these elements as outlined in Section 3.3, but a profile MUST NOT loosen restrictions. This document creates an IANA registry for JSContact profiles (see Section 4).

JSContactプロファイルは、プロパティー、型、値などのJSContactの要素の、名前とバージョンが付けられた集合です。JSContactの要素は、IANAの「JSContact」レジストリーグループ[IANA.jscontact]に登録されていなければなりません（MUST）。プロファイルは、Section 3.3で概説するように、これらの要素に追加の制限を定義してもよいです（MAY）が、プロファイルは制限を緩めてはなりません（MUST NOT）。この文書は、JSContactプロファイルのためのIANAレジストリーを作成します（Section 4を参照）。

A JSContact object complies with a profile if all its properties are in the set of properties defined by that profile and the property values comply with the profile restrictions for that property. A JSContact object MAY comply with multiple profiles. Accordingly, this document does not specify any means for JSContact data to communicate which profiles it complies with, e.g., it does not define a "profile" property for the Card object.

JSContactオブジェクトは、そのすべてのプロパティーがそのプロファイルで定義されたプロパティーの集合に含まれ、かつプロパティーの値がそのプロパティーに対するプロファイルの制限に準拠している場合に、そのプロファイルに準拠します。JSContactオブジェクトは複数のプロファイルに準拠してもよいです（MAY）。したがって、この文書は、JSContactデータがどのプロファイルに準拠しているかを伝えるための手段を規定しません。たとえば、Cardオブジェクトに「profile」プロパティーは定義しません。

All properties and values of a JSContact object that complies with a profile MUST also be valid (Section 1.7 of [RFC9553]). Handling JSContact data that is valid but that does not comply with the expected profile is protocol-specific. This document deliberately does not define such non-compliant data as invalid. Profile designers decide on their own strategies for handling non-compliant data, one of which may be to reject it as invalid. JSContact data that complies with a profile may still not be valid in the context of that protocol; the protocol specification MAY define additional restrictions that a profile cannot express.

プロファイルに準拠するJSContactオブジェクトのすべてのプロパティーと値は、有効でなければなりません（MUST）（[RFC9553]のSection 1.7）。有効ではあるものの期待されるプロファイルに準拠しないJSContactデータの取り扱いは、プロトコル固有です。この文書は、そのような非準拠のデータを意図的に無効とは定義しません。プロファイルの設計者は、非準拠のデータを扱うための独自の戦略を決定します。その1つは、それを無効として拒否することかもしれません。プロファイルに準拠するJSContactデータであっても、そのプロトコルの文脈では有効でない場合があります。プロトコルの仕様では、プロファイルでは表現できない追加の制限を定義してもよいです（MAY）。

Section 3.1 defines how to name a JSContact profile; Section 3.2 defines how to version it; Section 3.3 defines how to specify the properties supported by that profile; and Section 3.4 describes how to determine the supported properties.

Section 3.1ではJSContactプロファイルの名前の付け方を、Section 3.2ではバージョンの付け方を、Section 3.3ではそのプロファイルでサポートされるプロパティーの指定方法を定義し、Section 3.4ではサポートされるプロパティーの決定方法を説明します。

3.1. Profile Name

3.1. プロファイル名

A JSContact profile has a unique name. The name MUST only contain ASCII lowercase alphabetic and numeric characters, optionally separated by hyphens. It MUST start with an alphabetic character, and it MUST be of at least 1 character and at most 255 characters in size. Formally, it MUST be a valid "profile-name" defined in Figure 1.

JSContactプロファイルは一意な名前を持ちます。名前は、ASCIIの小文字の英字と数字のみを含み、任意でハイフンで区切られていなければなりません（MUST）。名前は英字で始まらなければなりません（MUST）。また、名前のサイズは1文字以上255文字以下でなければなりません（MUST）。形式的には、Figure 1で定義されている有効な「profile-name」でなければなりません（MUST）。

3.2. Profile Version

3.2. プロファイルのバージョン

A JSContact profile has a current version, and each profile is versioned independently. The version MUST be a positive integer, and it MUST increase whenever the profile properties (see Section 3.3) change. The initial version value is 1.

JSContactプロファイルは現在のバージョンを持ち、各プロファイルは独立してバージョン付けされます。バージョンは正の整数でなければなりません（MUST）。また、プロファイルのプロパティー（Section 3.3を参照）が変更されるたびに増加しなければなりません（MUST）。バージョンの初期値は1です。

3.3. Profile Properties

3.3. プロファイルのプロパティー

A profile defines a list of property entries that together determine the set of properties supported by that profile, as described in Section 3.4. The list MUST NOT be empty.

プロファイルは、Section 3.4で説明するように、そのプロファイルでサポートされるプロパティーの集合を一緒に決定するプロパティーエントリーのリストを定義します。このリストは空であってはなりません（MUST NOT）。

Each property entry consists of the following elements:

各プロパティーエントリーは、次の要素で構成されます：

Property Name:
This is the name of the JSContact property that this entry refers to. This MUST be a property name registered in the "JSContact Properties" registry. A property name MAY occur multiple times in the property entry list if the profile-specific restrictions for that property cannot be expressed with a single entry, but such multiple entries MUST NOT result in conflicting restrictions for the same property. This field MUST NOT be empty.
Property Context:
This is a comma-separated list of JSContact object types that support this property in this profile. Each of these types MUST also be listed in the Property Contexts for this property in the "JSContact Properties" registry, but a profile MAY only support the property in a subset of these contexts. This field MUST NOT be empty.
Restricted Attributes:
This restricts the attributes of the property. This specification only defines how to restrict the attributes such that a property becomes mandatory in the listed Property Contexts, despite the property originally being defined to be optional in the same contexts. The verbatim value "mandatory" (without quotes) indicates that it is mandatory in this profile; the absence of any value indicates that this profile does not restrict the property attributes of the original definition.
Restricted Property Type:

This restricts the property value type in the listed Property Contexts. It allows a profile to restrict the allowed types to the original type definition such that future changes to JSContact do not extend the allowed types of the property for this profile, and it allows a profile to restrict the allowed types to a subset of the original type definition. The absence of any value indicates that this profile does not restrict the property value type of the original definition or any future extensions of the value type.

If set, the restricted value type MUST exactly match the original definition at the time when the profile is defined, or the original value type MUST contain some type signature in the form "A|B" and the restricted value type MUST resemble the original except that some of the original "A|B" forms now only allow a subset of the original choices. Restricted property types MUST NOT redefine the "defaultType" attribute (Section 1.3.3 of [RFC9553]); the rules about when to set the "@type" property (Section 1.3.4 of [RFC9553]) of the original type definition still apply.

As an example of restricting the type definition to prevent future type extensions in the profile, one might restrict the type definition of the "addresses" property of the Card object to "Id[Address]", which matches the original definition as of this writing.

As an example of restricting the type to a subset of the original value, one might want to restrict the "date" property of the Anniversary object to only allow partial dates as values. To do so, the original value type "PartialDate|Timestamp" can be restricted to "PartialDate". Note that the original value type need not be exactly in form "A|B". For example, the type signature "Id[A|B|C]" could be restricted to any of "Id[A|B]", "Id[A|C]", "Id[B|C]", "Id[A]", "Id[B]", "Id[C]", and the type signature "(A|B)[]" could be restricted to one of "A[]" or "B[]".

Restricted Enum Values:
This restricts the enumerated values defined for this property to a subset of those values. The values MUST be listed in the "JSContact Enum Values" registry for this property and context. Allowed values are separated by a comma; the absence of any value indicates that all enumerated values are allowed. A profile MAY exclude the default enumerated value of a property, in which case all instances of the object MUST have this property set to one of the allowed values.
Restricted PatchObject:
This restricts the PatchObject value of this property such that each JSON Pointer key in the PatchObject MUST consist of exactly one JSON Pointer reference token (Section 3 of [RFC6901]). For example, with this restriction, the "localizations" property of the Card object can only patch properties of the Card object by replacing their values entirely. The verbatim value "yes" (without quotes) indicates that this profile restricts PatchObject keys to a single token; the absence of any value indicates that it does not restrict them. This MUST NOT be set to "yes" if the property value type is not a PatchObject.
プロパティー名：
これは、このエントリーが参照するJSContactプロパティーの名前です。これは、「JSContact Properties」レジストリーに登録されたプロパティー名でなければなりません（MUST）。そのプロパティーに対するプロファイル固有の制限を単一のエントリーで表現できない場合、プロパティー名はプロパティーエントリーのリストに複数回現れてもよいです（MAY）が、そのような複数のエントリーが同じプロパティーに対して矛盾する制限をもたらしてはなりません（MUST NOT）。このフィールドは空であってはなりません（MUST NOT）。
プロパティーのコンテキスト：
これは、このプロファイルでこのプロパティーをサポートするJSContactオブジェクトの型のカンマ区切りのリストです。これらの各型は、「JSContact Properties」レジストリーにおけるこのプロパティーのProperty Contextsにも列挙されていなければなりません（MUST）が、プロファイルは、これらのコンテキストのサブセットでのみそのプロパティーをサポートしてもよいです（MAY）。このフィールドは空であってはなりません（MUST NOT）。
制限された属性：
これは、プロパティーの属性を制限します。この仕様では、プロパティーが元々同じコンテキストで任意であると定義されているにもかかわらず、列挙されたProperty Contextsでそのプロパティーが必須となるように属性を制限する方法のみを定義します。そのままの値「mandatory」（引用符なし）は、このプロファイルでそれが必須であることを示します。値がない場合は、このプロファイルが元の定義のプロパティーの属性を制限しないことを示します。
制限されたプロパティーの型：

これは、列挙されたProperty Contextsにおけるプロパティーの値の型を制限します。これにより、プロファイルは、JSContactの将来の変更によってこのプロファイルにおけるプロパティーの許可される型が拡張されないように、許可される型を元の型定義に制限できます。また、プロファイルは、許可される型を元の型定義のサブセットに制限できます。値がない場合は、このプロファイルが元の定義のプロパティーの値の型や、その値の型の将来の拡張を制限しないことを示します。

設定されている場合、制限された値の型は、プロファイルが定義された時点の元の定義と正確に一致しなければなりません（MUST）。そうでない場合は、元の値の型が「A|B」の形式の何らかの型シグネチャーを含んでいる必要があります（MUST）。また、制限された値の型は、元の「A|B」の形式の一部が元の選択肢のサブセットのみを許可するようになっている点を除いて、元のものと同様でなければなりません（MUST）。制限されたプロパティーの型は、「defaultType」属性（[RFC9553]のSection 1.3.3）を再定義してはなりません（MUST NOT）。元の型定義の「@type」プロパティー（[RFC9553]のSection 1.3.4）をいつ設定するかについての規則は引き続き適用されます。

プロファイルにおける将来の型拡張を防ぐために型定義を制限する例として、Cardオブジェクトの「addresses」プロパティーの型定義を「Id[Address]」に制限することが考えられます。これは、執筆時点での元の定義と一致します。

型を元の値のサブセットに制限する例として、Anniversaryオブジェクトの「date」プロパティーを、値として部分的な日付のみを許可するように制限したい場合があります。そのためには、元の値の型「PartialDate|Timestamp」を「PartialDate」に制限できます。元の値の型は正確に「A|B」の形式である必要はないことに注意してください。たとえば、型シグネチャー「Id[A|B|C]」は「Id[A|B]」、「Id[A|C]」、「Id[B|C]」、「Id[A]」、「Id[B]」、「Id[C]」のいずれかに制限でき、型シグネチャー「(A|B)[]」は「A[]」または「B[]」のいずれかに制限できます。

制限された列挙値：
これは、このプロパティーに対して定義された列挙値を、それらの値のサブセットに制限します。値は、このプロパティーとコンテキストについて「JSContact Enum Values」レジストリーに列挙されていなければなりません（MUST）。許可される値はカンマで区切られます。値がない場合は、すべての列挙値が許可されることを示します。プロファイルは、プロパティーのデフォルトの列挙値を除外してもよいです（MAY）。その場合、そのオブジェクトのすべてのインスタンスは、このプロパティーを許可された値のいずれかに設定していなければなりません（MUST）。
制限されたPatchObject：
これは、このプロパティーのPatchObjectの値を制限します。この制限の下では、PatchObject内の各JSON Pointerのキーはちょうど1つのJSON Pointer参照トークン（[RFC6901]のSection 3）で構成されなければなりません（MUST）。たとえば、この制限により、Cardオブジェクトの「localizations」プロパティーは、値を完全に置き換えることによってのみCardオブジェクトのプロパティーにパッチを適用できます。そのままの値「yes」（引用符なし）は、このプロファイルがPatchObjectのキーを単一のトークンに制限することを示します。値がない場合は、それらを制限しないことを示します。プロパティーの値の型がPatchObjectでない場合、これを「yes」に設定してはなりません（MUST NOT）。

All profiles MUST support "@type" and "version"; therefore, profiles MUST NOT include entries for these properties.

すべてのプロファイルは「@type」と「version」をサポートしなければなりません（MUST）。したがって、プロファイルはこれらのプロパティーのエントリーを含めてはなりません（MUST NOT）。

3.4. Supported Properties

3.4. サポートされるプロパティー

The supported properties of a JSContact profile are determined by the profile's property entries and the contents of the IANA "JSContact Properties" registry, which are referred to here as "IANA-registered properties" for short. The "version" property of the Card object and the "@type" property of any object type are always supported.

JSContactプロファイルのサポートされるプロパティーは、プロファイルのプロパティーエントリーと、IANAの「JSContact Properties」レジストリーの内容によって決定されます。後者を、ここでは短く「IANA登録プロパティー」と呼びます。Cardオブジェクトの「version」プロパティーと、任意のオブジェクト型の「@type」プロパティーは、常にサポートされます。

A Card object complies with the profile if all its properties are part of the supported properties and all property values are valid according to the restrictions defined in the applicable property entries. A PatchObject MUST NOT patch properties that are not supported in that profile.

Cardオブジェクトは、そのすべてのプロパティーがサポートされるプロパティーの一部であり、かつすべてのプロパティーの値が該当するプロパティーエントリーで定義された制限に従って有効である場合に、そのプロファイルに準拠します。PatchObjectは、そのプロファイルでサポートされていないプロパティーにパッチを適用してはなりません（MUST NOT）。

The following describes the steps to determine the supported properties:

サポートされるプロパティーを決定する手順を次に示します：

  1. Initialize the set with all properties of the Card object for which a property entry contains "Card" in the Property Context of the profile. If no such entry exists, then initialize the set with all IANA-registered properties of the Card object.
  2. For every property in the set having either an object type as the value type or a list, map, or union of object types, add all properties for which a property entry contains those object types in the Property Context of the profile. If no such property entry exists, then add all IANA-registered properties for the object types.
  3. Repeat the previous step until all object types that are value types of properties in the set have been considered.
  1. プロファイルのProperty Contextに「Card」を含むプロパティーエントリーがあるCardオブジェクトのすべてのプロパティーで、集合を初期化します。そのようなエントリーが存在しない場合は、CardオブジェクトのすべてのIANA登録プロパティーで集合を初期化します。
  2. 値の型としてオブジェクト型、またはオブジェクト型のリスト、マップ、もしくはユニオンを持つ集合内のすべてのプロパティーについて、プロファイルのProperty Contextにそれらのオブジェクト型を含むプロパティーエントリーがあるすべてのプロパティーを追加します。そのようなプロパティーエントリーが存在しない場合は、そのオブジェクト型のすべてのIANA登録プロパティーを追加します。
  3. 集合内のプロパティーの値の型であるすべてのオブジェクト型が検討されるまで、前のステップを繰り返します。

Appendix A.4 describes how to determine the supported properties of the example profile in Appendix A.

Appendix A.4では、Appendix Aの例のプロファイルのサポートされるプロパティーを決定する方法を説明します。

4. IANA Considerations

4. IANAに関する考慮事項

IANA has created the "JSContact Profiles" registry within the "JSContact" registry group. The purpose of this new registry is to register profiles for JSContact data. The registry policy to add an entry to this registry is "Specification Required" [RFC8126]; this applies to defining a new profile name or version. The registry policy to update an existing profile is "Expert Review"; this applies to updating the references of an entry. The change controller is the IETF.

IANAは、「JSContact」レジストリーグループ内に「JSContact Profiles」レジストリーを作成しました。この新しいレジストリーの目的は、JSContactデータのプロファイルを登録することです。このレジストリーにエントリーを追加するためのレジストリーポリシーは「Specification Required」[RFC8126]です。これは、新しいプロファイル名またはバージョンを定義する場合に適用されます。既存のプロファイルを更新するためのレジストリーポリシーは「Expert Review」です。これは、エントリーの参照を更新する場合に適用されます。変更管理者はIETFです。

An entry in this registry consists of the following, all of which MUST be set:

このレジストリーのエントリーは次のもので構成され、そのすべてが設定されていなければなりません（MUST）：

Name:
This is the name of the profile. This field is immutable after creation. The name MUST be unique among all registered profiles and MUST comply with the definitions in Section 3.1.
Version:
This is the version number of the profile. This field is immutable after creation. It MUST comply with the definitions in Section 3.2.
Reference:
This refers to the specification of the protocol or use case for which this profile applies. The reference MUST include the section number or section name that defines or updates the property entries for this profile, as defined in Section 3.3.
名前：
これはプロファイルの名前です。このフィールドは作成後に変更できません。名前は、登録されたすべてのプロファイルの中で一意でなければなりません（MUST）。また、Section 3.1の定義に準拠しなければなりません（MUST）。
バージョン：
これはプロファイルのバージョン番号です。このフィールドは作成後に変更できません。Section 3.2の定義に準拠しなければなりません（MUST）。
参照：
これは、このプロファイルが適用されるプロトコルまたはユースケースの仕様を参照します。参照には、Section 3.3で定義されているように、このプロファイルのプロパティーエントリーを定義または更新するセクション番号またはセクション名を含めなければなりません（MUST）。

Designated experts assert that all proposed assignments are valid according to the definitions in this document. For example, they check that:

指定専門家は、提案されたすべての割り当てがこの文書の定義に従って有効であることを確認します。たとえば、次のことを確認します：

  • the profile name is unique,
  • the entries in the profile entries are syntactically valid,
  • only known property names are referred to,
  • type restrictions do not incorrectly alter the type of a property, and
  • the version number increases.
  • プロファイル名が一意であること
  • プロファイルのエントリーが構文的に有効であること
  • 既知のプロパティー名のみが参照されていること
  • 型の制限がプロパティーの型を誤って変更していないこと
  • バージョン番号が増加していること

On the other hand, designated experts do not decide the contents of the profile as long as the assignments are valid.

一方、割り当てが有効である限り、指定専門家がプロファイルの内容を決定することはありません。

The decision whether to register a new profile name or register a new version for an existing profile depends on the scope of the proposed profile. A new profile name is recommended if the profile is introduced in the context of an application or protocol for which no JSContact profile is already registered or if the proposed profile properties or restrictions substantially differ from existing profiles for that context. A new version is recommended if the profile context does not change and multiple implementations of the current profile will also support the new version. The profile version of the new entry for an already-registered profile by that name has to be higher than the last registered version for that profile. Existing registry entries are preserved.

新しいプロファイル名を登録するか、既存のプロファイルの新しいバージョンを登録するかの判断は、提案されたプロファイルの範囲に依存します。JSContactプロファイルがまだ登録されていないアプリケーションやプロトコルの文脈でプロファイルが導入される場合、または提案されたプロファイルのプロパティーや制限がその文脈の既存のプロファイルと大幅に異なる場合は、新しいプロファイル名が推奨されます。プロファイルの文脈が変わらず、現在のプロファイルの複数の実装が新しいバージョンもサポートする場合は、新しいバージョンが推奨されます。その名前ですでに登録されているプロファイルの新しいエントリーのプロファイルバージョンは、そのプロファイルの最後に登録されたバージョンより大きくなければなりません。既存のレジストリーのエントリーは保持されます。

This document does not define any initial contents for the "JSContact Profiles" registry.

この文書は、「JSContact Profiles」レジストリーの初期内容を定義しません。

Note that:

次の点に注意してください：

  • The Address, Card, Name, and NameComponent object values only contain properties for which a property entry exists in the profile.
  • The EmailAddress object contains the "address" property. This is allowed because the profile contains a property entry for the "emails" property of the Card object, but it does not define entries for the EmailAddress object properties. Consequently, all properties of the EmailAddress object can be set.
  • The "full" property of the Address object is set. It is the only property allowed to be set in that profile for Address, and the "full" property is mandatory for this profile.
  • The "kind" property of the NameComponent object is set to "surname" and "given". Since the profile does not restrict the enumerated values of this property, all valid NameComponent "kind" property values are supported.
  • The "kind" property of the Card object is not set. The profile restricts the enumerated values of this property to "individual" and "org". Since "individual" is the default value for this property, there is no need to set it.
  • The "date" property of the Anniversary object is restricted to be of type PartialDate in this profile. Because PartialDate is the default type for this property, there is no need to the set the "@type" property of the PartialDate object.
  • Address、Card、Name、およびNameComponentのオブジェクトの値には、プロファイル内にプロパティーエントリーが存在するプロパティーのみが含まれています。

  • Addressオブジェクトの「full」プロパティーが設定されています。これは、そのプロファイルでAddressについて設定が許可されている唯一のプロパティーであり、「full」プロパティーはこのプロファイルでは必須です。
  • NameComponentオブジェクトの「kind」プロパティーは「surname」と「given」に設定されています。プロファイルはこのプロパティーの列挙値を制限していないため、NameComponentの「kind」プロパティーのすべての有効な値がサポートされます。
  • Cardオブジェクトの「kind」プロパティーは設定されていません。プロファイルは、このプロパティーの列挙値を「individual」と「org」に制限しています。「individual」はこのプロパティーのデフォルト値であるため、設定する必要はありません。
  • Anniversaryオブジェクトの「date」プロパティーは、このプロファイルではPartialDate型に制限されています。PartialDateはこのプロパティーのデフォルトの型であるため、PartialDateオブジェクトの「@type」プロパティーを設定する必要はありません。

A.4. Supported Properties Example

A.4. サポートされるプロパティーの例

The following illustrates how to determine the supported properties of the example profile in this appendix, according to the steps defined in Section 3.4:

以下では、Section 3.4で定義されている手順に従って、この付録の例のプロファイルのサポートされるプロパティーを決定する方法を説明します：

  1. We initialize the set of supported properties with all profile properties for which the Property Context includes the Card object. The set now includes the following properties:

    • Card.addresses
    • Card.anniversaries
    • Card.emails
    • Card.kind
    • Card.localizations
    • Card.name
  2. Next, we determine which of the properties in the current set have an object type as the value type. These are the Card.addresses, Card.anniversaries, Card.emails, and Card.name properties, so we need to inspect the object types Address, Anniversary, EmailAddress, and Name. The "addresses" entry restricts the value type of that property to "Id[Address]", which matches its original definition, but any future type extension would still require us only to inspect the Address type.

  3. For the Address object type, the profile has an entry for the "full" property, which contains the Address object in the Property Context, so we add that and only that to the set of supported properties. It now contains:

    • Address.full
    • Card.addresses
    • Card.emails
    • Card.kind
    • Card.localizations
    • Card.name

    The value type of the Address.full property is not an object type, so we need not consider a new object type to inspect. The remaining object types to inspect are the Anniversary, EmailAddress, and Name objects.

  4. For the Anniversary object type, the profile explicitly lists the "kind" and "date" properties, so we add them to the set of supported properties. It now contains:

    • Address.full
    • Anniversary.date
    • Anniversary.kind
    • Card.addresses
    • Card.emails
    • Card.kind
    • Card.localizations
    • Card.name

    The newly added Anniversary.date property has object value type PartialDate, so we add that to the list of object types to inspect. The entry restricts the type of that property to only be of that type, so we do not add the object value type Timestamp. The remaining object types to inspect are the EmailAddress, Name, and PartialDate objects.

  5. For the PartialDate object type, the profile does not contain any entry where the Property Context contains the PartialDate object. Instead, we add properties from the "JSContact Properties" registry where the Property Context includes the PartialDate object. The set of supported properties now contains:

    • Address.full
    • Anniversary.date
    • Anniversary.kind
    • Card.addresses
    • Card.emails
    • Card.kind
    • Card.localizations
    • Card.name
    • PartialDate.calendarScale
    • PartialDate.day
    • PartialDate.month
    • PartialDate.year

    None of the newly added properties have object value types. The remaining object types to inspect are the EmailAddress and Name objects.

  6. For the EmailAddress object type, the profile does not contain any entry where the Property Context contains the EmailAddress object. Instead, we add properties from the "JSContact Properties" registry where the Property Context includes the EmailAddress object. The set of supported properties now contains:

    • Address.full
    • Anniversary.date
    • Anniversary.kind
    • Card.addresses
    • Card.emails
    • Card.kind
    • Card.localizations
    • Card.name
    • EmailAddress.address
    • EmailAddress.contexts
    • EmailAddress.label
    • EmailAddress.pref
    • PartialDate.calendarScale
    • PartialDate.day
    • PartialDate.month
    • PartialDate.year

    None of the newly added properties have object value types. The remaining object type to inspect is the Name object.

  7. For the Name object type, the profile explicitly lists the "components" and "full" properties, so we add them to the set of supported properties. It now contains:

    • Address.full
    • Anniversary.date
    • Anniversary.kind
    • Card.addresses
    • Card.emails
    • Card.kind
    • Card.localizations
    • Card.name
    • EmailAddress.address
    • EmailAddress.contexts

    • EmailAddress.pref

    • PartialDate.day
    • PartialDate.month
    • PartialDate.year

    The newly added Name.components property has object value type NameComponent, so we add that to the list of object types to inspect.

  8. For the NameComponent object type, the profile does not explicitly list any property. Instead, we add properties of the "JSContact Properties" registry where the Property Context includes the NameComponent object. The set of supported properties now contains:

    • Address.full
    • Anniversary.date
    • Anniversary.kind
    • Card.addresses
    • Card.emails
    • Card.kind
    • Card.localizations
    • Card.name
    • EmailAddress.address
    • EmailAddress.contexts
    • EmailAddress.label
    • EmailAddress.pref
    • NameComponent.kind
    • NameComponent.phonetic
    • NameComponent.value
    • PartialDate.calendarScale
    • PartialDate.day
    • PartialDate.month
    • PartialDate.year

    None of the newly added properties have object value types, and there are no remaining object types to inspect. This determines the set of supported properties by that profile, in addition to the "Card.version" and "@type" property that are always supported.

  1. Property ContextにCardオブジェクトを含むすべてのプロファイルのプロパティーで、サポートされるプロパティーの集合を初期化します。集合には次のプロパティーが含まれるようになります：

    • Card.addresses

    • Card.kind
    • Card.localizations
    • Card.name
  2. 次に、現在の集合内のどのプロパティーが値の型としてオブジェクト型を持つかを判断します。それらはCard.addresses、Card.anniversaries、Card.emails、およびCard.nameのプロパティーであるため、オブジェクト型Address、Anniversary、EmailAddress、およびNameを調べる必要があります。「addresses」エントリーは、そのプロパティーの値の型を元の定義と一致する「Id[Address]」に制限していますが、将来型が拡張されたとしても、Address型のみを調べればよいことに変わりはありません。

    • Card.localizations
    • Card.name

  4. Anniversaryオブジェクト型について、プロファイルは「kind」プロパティーと「date」プロパティーを明示的に列挙しているため、それらをサポートされるプロパティーの集合に追加します。集合には次のものが含まれるようになります：

    • PartialDate.year

  6. EmailAddressオブジェクト型について、プロファイルには、Property ContextにEmailAddressオブジェクトを含むエントリーがありません。代わりに、Property ContextにEmailAddressオブジェクトを含む「JSContact Properties」レジストリーのプロパティーを追加します。サポートされるプロパティーの集合には次のものが含まれるようになります：

    • PartialDate.year

  7. Nameオブジェクト型について、プロファイルは「components」プロパティーと「full」プロパティーを明示的に列挙しているため、それらをサポートされるプロパティーの集合に追加します。集合には次のものが含まれるようになります：
