NETCONF Call Home and RESTCONF Call Home

RFC 8071

NETCONFコールホームとRESTCONFコールホーム

Abstract

概要

This RFC presents NETCONF Call Home and RESTCONF Call Home, which enable a NETCONF or RESTCONF server to initiate a secure connection to a NETCONF or RESTCONF client, respectively.

このRFCは、NETCONFコールホーム（NETCONF Call Home）とRESTCONFコールホーム（RESTCONF Call Home）を示します。これらはそれぞれ、NETCONFサーバーまたはRESTCONFサーバーが、NETCONFクライアントまたはRESTCONFクライアントへのセキュアなコネクションを開始することを可能にします。

1. Introduction

1. はじめに

This RFC presents NETCONF Call Home and RESTCONF Call Home, which enable a NETCONF or RESTCONF server to initiate a secure connection to a NETCONF or RESTCONF client, respectively.

このRFCは、NETCONFコールホーム（NETCONF Call Home）とRESTCONFコールホーム（RESTCONF Call Home）を示します。これらはそれぞれ、NETCONFサーバーまたはRESTCONFサーバーが、NETCONFクライアントまたはRESTCONFクライアントへのセキュアなコネクションを開始することを可能にします。

NETCONF Call Home supports both of the secure transports used by the Network Configuration Protocol (NETCONF) [RFC6241], Secure Shell (SSH), and Transport Layer Security (TLS). The NETCONF protocol's binding to SSH is defined in [RFC6242]. The NETCONF protocol's binding to TLS is defined in [RFC7589].

NETCONFコールホームは、ネットワーク設定プロトコル（Network Configuration Protocol、NETCONF）[RFC6241]が使用する2つのセキュアなトランスポート、すなわちセキュアシェル（Secure Shell、SSH）とトランスポート層セキュリティー（Transport Layer Security、TLS）の両方をサポートします。NETCONFプロトコルのSSHへのバインディングは[RFC6242]で定義されています。NETCONFプロトコルのTLSへのバインディングは[RFC7589]で定義されています。

RESTCONF Call Home only supports TLS, the same as the RESTCONF protocol [RFC8040]. The RESTCONF protocol's binding to TLS is defined in [RFC8040].

RESTCONFコールホームは、RESTCONFプロトコル[RFC8040]と同じく、TLSだけをサポートします。RESTCONFプロトコルのTLSへのバインディングは[RFC8040]で定義されています。

The SSH protocol is defined in [RFC4253]. The TLS protocol is defined in [RFC5246]. Both the SSH and TLS protocols are layered on top of the TCP protocol, which is defined in [RFC793].

SSHプロトコルは[RFC4253]で定義されています。TLSプロトコルは[RFC5246]で定義されています。SSHプロトコルとTLSプロトコルはどちらも、[RFC793]で定義されているTCPプロトコルの上に階層化されています。

Both NETCONF Call Home and RESTCONF Call Home preserve all but one of the client/server roles in their respective protocol stacks, as compared to client-initiated NETCONF and RESTCONF connections. The one and only role reversal that occurs is at the TCP layer; that is, which peer is the TCP client and which is the TCP server.

NETCONFコールホームとRESTCONFコールホームはどちらも、クライアントが開始するNETCONFおよびRESTCONFのコネクションと比べて、それぞれのプロトコルスタックにおけるクライアントとサーバーの役割を、1つを除いてすべて維持します。唯一の役割の逆転はTCP層で起こります。つまり、どちらのピアがTCPクライアントで、どちらがTCPサーバーかという点です。

For example, a network element is traditionally the TCP server. However, when calling home, the network element initially assumes the role of the TCP client. The network element's secure transport-layer roles (SSH server, TLS server) and its application-layer roles (NETCONF server, RESTCONF server) all remain the same.

たとえば、ネットワーク要素は伝統的にTCPサーバーです。しかし、コールホームする場合には、ネットワーク要素は最初にTCPクライアントの役割を担います。ネットワーク要素のセキュアなトランスポート層の役割（SSHサーバー、TLSサーバー）とアプリケーション層の役割（NETCONFサーバー、RESTCONFサーバー）は、すべて同じままです。

Having consistency in both the secure transport-layer (SSH, TLS) and application-layer (NETCONF, RESTCONF) roles conveniently enables deployed network management infrastructure to support call home also. For instance, existing certificate chains and user authentication mechanisms are unaffected by call home.

セキュアなトランスポート層（SSH、TLS）とアプリケーション層（NETCONF、RESTCONF）の両方の役割に一貫性があることにより、配備済みのネットワーク管理インフラストラクチャーが、コールホームも都合よくサポートできるようになります。たとえば、既存の証明書チェーンやユーザー認証メカニズムは、コールホームの影響を受けません。

1.1. Motivation

1.1. 動機

Call home is generally useful for both the initial deployment and ongoing management of networking elements. Here are some scenarios enabled by call home:

コールホームは一般に、ネットワーク要素の初期配備と継続的な管理の両方に役立ちます。コールホームによって可能になるシナリオをいくつか示します。

  • The network element may proactively "call home" after being powered on for the first time in order to register itself with its management system.
  • The network element may access the network in a way that dynamically assigns it an IP address, but does not register its assigned IP address to a mapping service (e.g., dynamic DNS).
  • The network element may be deployed behind a firewall that implements Network Address Translation (NAT) for all internal network IP addresses.
  • The network element may be deployed behind a firewall that does not allow any management access to the internal network.
  • The network element may be configured in "stealth mode", and thus does not have any open ports for the management system to connect to.
  • The operator may prefer to have network elements initiate management connections, believing it is easier to secure one open port in the data center than to have an open port on each network element in the network.
  • ネットワーク要素は、初めて電源が投入された後に、自身を管理システムに登録するために、積極的に「コールホーム」することがあります。
  • ネットワーク要素は、IPアドレスを動的に割り当てる方法でネットワークにアクセスするものの、割り当てられたIPアドレスをマッピングサービス（たとえば、ダイナミックDNS）に登録しないことがあります。
  • ネットワーク要素は、すべての内部ネットワークのIPアドレスに対してネットワークアドレス変換（NAT）を実装するファイアウォールの背後に配備されることがあります。
  • ネットワーク要素は、内部ネットワークへの管理アクセスを一切許可しないファイアウォールの背後に配備されることがあります。
  • ネットワーク要素は「ステルスモード」で設定されることがあり、その場合、管理システムが接続するための開いたポートを持ちません。
  • オペレーターは、ネットワーク内の各ネットワーク要素にポートを開いておくよりも、データセンターで1つの開いたポートを保護するほうが容易だと考え、ネットワーク要素に管理コネクションを開始させることを好むかもしれません。

1.3. Applicability Statement

1.3. 適用性に関する声明

The techniques described in this document are suitable for network management scenarios such as the ones described in Section 1.1. However, these techniques are only defined for NETCONF Call Home and RESTCONF Call Home, as described in this document.

この文書で説明する技術は、セクション1.1で説明したようなネットワーク管理のシナリオに適しています。ただし、これらの技術は、この文書で説明するとおり、NETCONFコールホームとRESTCONFコールホームに対してだけ定義されています。

The reason for this restriction is that different protocols have different security assumptions. The NETCONF and RESTCONF protocols require clients and servers to verify the identity of the other party. This requirement is specified for the NETCONF protocol in Section 2.2 of [RFC6241], and is specified for the RESTCONF protocol in Sections 2.4 and 2.5 of [RFC8040].

この制限の理由は、プロトコルによってセキュリティー上の前提が異なるためです。NETCONFプロトコルとRESTCONFプロトコルは、クライアントとサーバーに相手側の身元を検証することを要求しています。この要件は、NETCONFプロトコルについては[RFC6241]のセクション2.2で規定されており、RESTCONFプロトコルについては[RFC8040]のセクション2.4と2.5で規定されています。

This contrasts with the base SSH and TLS protocols, which do not require programmatic verification of the other party (Section 9.3.4 of [RFC4251], Section 4 of [RFC4252], and Section 7.3 of [RFC5246]). In such circumstances, allowing the SSH/TLS server to contact the SSH/TLS client would open new vulnerabilities. Any use of call home with SSH/TLS for purposes other than NETCONF or RESTCONF will need a thorough contextual risk assessment. A risk assessment for this RFC is in the Security Considerations section (Section 5).

これは、通信相手をプログラムで検証することを要求しない基本のSSHプロトコルおよびTLSプロトコルとは対照的です（[RFC4251]のセクション9.3.4、[RFC4252]のセクション4、[RFC5246]のセクション7.3）。そのような状況では、SSH/TLSサーバーがSSH/TLSクライアントに接続することを許すと、新たな脆弱性が生じることになります。NETCONFまたはRESTCONF以外の目的でSSH/TLSとともにコールホームを使用する場合には、その文脈に即した徹底的なリスク評価が必要になります。このRFCのリスク評価は、「セキュリティーに関する考慮事項」のセクション（セクション5）にあります。

1.4. Relation to RFC 4253

1.4. RFC 4253との関係

This document uses the SSH Transport Layer Protocol [RFC4253] with the exception that the statement "The client initiates the connection" made in Section 4 of RFC 4253 does not apply. Assuming the reference to the client means "SSH client" and the reference to the connection means "TCP connection", this statement doesn't hold true in call home, where the network element is the SSH server and yet still initiates the TCP connection. Security implications related to this change are discussed in Section 5.

この文書はSSHトランスポート層プロトコル[RFC4253]を使用しますが、RFC 4253のセクション4でなされている「クライアントがコネクションを開始する（The client initiates the connection）」という記述は適用されません。クライアントへの言及が「SSHクライアント」を意味し、コネクションへの言及が「TCPコネクション」を意味すると仮定すると、この記述は、ネットワーク要素がSSHサーバーでありながらTCPコネクションを開始するコールホームでは成り立ちません。この変更に関連するセキュリティー上の影響は、セクション5で議論します。

1.5. The NETCONF/RESTCONF Convention

1.5. NETCONF/RESTCONFの表記規則

Throughout the remainder of this document, the term "NETCONF/RESTCONF" is used as an abbreviation in place of the text "the NETCONF or the RESTCONF". The NETCONF/RESTCONF abbreviation is not intended to require or to imply that a client or server must implement both the NETCONF standard and the RESTCONF standard.

この文書の残りの部分を通じて、「NETCONF/RESTCONF」という用語は、「NETCONFまたはRESTCONF」というテキストの代わりの略記として使用します。NETCONF/RESTCONFという略記は、クライアントまたはサーバーがNETCONF標準とRESTCONF標準の両方を実装しなければならないことを要求したり暗示したりすることを意図していません。

2. Solution Overview

2. 解決策の概要

The diagram below illustrates call home from a protocol-layering perspective:

次の図は、プロトコルの階層化の観点からコールホームを示しています。

This diagram makes the following points:

この図は、次の点を示しています。

  1. The NETCONF/RESTCONF server begins by initiating a TCP connection to the NETCONF/RESTCONF client.
  2. Using this TCP connection, the NETCONF/RESTCONF client initiates an SSH/TLS session to the NETCONF/RESTCONF server.
  3. Using this SSH/TLS session, the NETCONF/RESTCONF client initiates a NETCONF/RESTCONF session to the NETCONF/RESTCONF server.
  1. NETCONF/RESTCONFサーバーは、まず、NETCONF/RESTCONFクライアントへのTCPコネクションを開始します。
  2. このTCPコネクションを使用して、NETCONF/RESTCONFクライアントは、NETCONF/RESTCONFサーバーへのSSH/TLSセッションを開始します。
  3. このSSH/TLSセッションを使用して、NETCONF/RESTCONFクライアントは、NETCONF/RESTCONFサーバーへのNETCONF/RESTCONFセッションを開始します。

3. The NETCONF or RESTCONF Client

3. NETCONFクライアントまたはRESTCONFクライアント

The term "client" is defined in [RFC6241], Section 1.1. In the context of network management, the NETCONF/RESTCONF client might be a network management system.

「クライアント」という用語は、[RFC6241], セクション1.1で定義されています。ネットワーク管理の文脈では、NETCONF/RESTCONFクライアントはネットワーク管理システムであるかもしれません。

3.1. Client Protocol Operation

3.1. クライアントのプロトコル動作

C1
The NETCONF/RESTCONF client listens for TCP connection requests from NETCONF/RESTCONF servers. The client MUST support accepting TCP connections on the IANA-assigned ports defined in Section 6, but MAY be configured to listen to a different port.
C2
The NETCONF/RESTCONF client accepts an incoming TCP connection request and a TCP connection is established.
C3
Using this TCP connection, the NETCONF/RESTCONF client starts either the SSH client [RFC4253] or the TLS client [RFC5246] protocol. For example, assuming the use of the IANA-assigned ports, the SSH client protocol is started when the connection is accepted on port 4334 and the TLS client protocol is started when the connection is accepted on either port 4335 or port 4336.
C4
When using TLS, the NETCONF/RESTCONF client MUST advertise "peer_allowed_to_send", as defined by [RFC6520]. This is required so that NETCONF/RESTCONF servers can depend on it being there for call home connections, when keep-alives are needed the most.
C5
As part of establishing an SSH or TLS connection, the NETCONF/RESTCONF client MUST validate the server's presented host key or certificate. This validation MAY be accomplished by certificate path validation or by comparing the host key or certificate to a previously trusted or "pinned" value. If a certificate is presented and it contains revocation-checking information, the NETCONF/RESTCONF client SHOULD check the revocation status of the certificate. If it is determined that a certificate has been revoked, the client MUST immediately close the connection.
C6
If certificate path validation is used, the NETCONF/RESTCONF client MUST ensure that the presented certificate has a valid chain of trust to a preconfigured issuer certificate, and that the presented certificate encodes an "identifier" [RFC6125] that the client was aware of before the connection attempt. How identifiers are encoded in certificates MAY be determined by a policy associated with the certificate's issuer. For instance, a given issuer may be known to only sign IDevID certificates [Std-802.1AR-2009] having a unique identifier (e.g., a serial number) in the X.509 certificate's "CommonName" field.
C7
After the server's host key or certificate is validated, the SSH or TLS protocol proceeds as normal to establish an SSH or TLS connection. When performing client authentication with the NETCONF/RESTCONF server, the NETCONF/RESTCONF client MUST only use credentials that it had previously associated for the NETCONF/RESTCONF server's presented host key or server certificate.
C8
Once the SSH or TLS connection is established, the NETCONF/RESTCONF client starts either the NETCONF client [RFC6241] or RESTCONF client [RFC8040] protocol. Assuming the use of the IANA-assigned ports, the NETCONF client protocol is started when the connection is accepted on either port 4334 or port 4335 and the RESTCONF client protocol is started when the connection is accepted on port 4336.
C1
NETCONF/RESTCONFクライアントは、NETCONF/RESTCONFサーバーからのTCPコネクション要求を待ち受けます。クライアントは、セクション6で定義するIANAが割り当てたポートでTCPコネクションを受け付けることをサポートしなければなりません（MUST）が、別のポートで待ち受けるように設定されてもよいです（MAY）。
C2
NETCONF/RESTCONFクライアントは、着信したTCPコネクション要求を受け付け、TCPコネクションが確立されます。
C3
このTCPコネクションを使用して、NETCONF/RESTCONFクライアントは、SSHクライアント[RFC4253]またはTLSクライアント[RFC5246]のプロトコルを開始します。たとえば、IANAが割り当てたポートを使用すると仮定すると、コネクションがポート4334で受け付けられた場合にはSSHクライアントプロトコルが開始され、コネクションがポート4335またはポート4336で受け付けられた場合にはTLSクライアントプロトコルが開始されます。
C4
TLSを使用する場合、NETCONF/RESTCONFクライアントは、[RFC6520]で定義されている「peer_allowed_to_send」を通知しなければなりません（MUST）。これは、キープアライブが最も必要とされるコールホームのコネクションにおいて、NETCONF/RESTCONFサーバーがそれが存在することを当てにできるようにするために必要です。
C5
SSHまたはTLSのコネクションの確立の一環として、NETCONF/RESTCONFクライアントは、サーバーが提示したホスト鍵または証明書を検証しなければなりません（MUST）。この検証は、証明書パス検証によって、またはホスト鍵や証明書を以前に信頼した値や「ピン留め」された値と比較することによって行ってもよいです（MAY）。証明書が提示され、それが失効確認のための情報を含む場合、NETCONF/RESTCONFクライアントは、その証明書の失効状態を確認すべきです（SHOULD）。証明書が失効していると判断された場合、クライアントはただちにコネクションを閉じなければなりません（MUST）。
C6
証明書パス検証を使用する場合、NETCONF/RESTCONFクライアントは、提示された証明書が事前に設定された発行者証明書への有効な信頼の連鎖を持つこと、および提示された証明書が、コネクションの試行の前にクライアントが知っていた「識別子（identifier）」[RFC6125]をエンコードしていることを確認しなければなりません（MUST）。証明書に識別子をどのようにエンコードするかは、証明書の発行者に関連付けられたポリシーによって決定されてもよいです（MAY）。たとえば、ある発行者は、X.509証明書の「CommonName」フィールドに一意の識別子（たとえば、シリアル番号）を持つIDevID証明書[Std-802.1AR-2009]だけに署名することがわかっている場合があります。
C7
サーバーのホスト鍵または証明書が検証された後、SSHまたはTLSのプロトコルは通常どおりに進み、SSHまたはTLSのコネクションを確立します。NETCONF/RESTCONFサーバーとのクライアント認証を行う際、NETCONF/RESTCONFクライアントは、NETCONF/RESTCONFサーバーが提示したホスト鍵またはサーバー証明書に対して以前に関連付けておいたクレデンシャルだけを使用しなければなりません（MUST）。
C8
SSHまたはTLSのコネクションが確立されると、NETCONF/RESTCONFクライアントは、NETCONFクライアント[RFC6241]またはRESTCONFクライアント[RFC8040]のプロトコルを開始します。IANAが割り当てたポートを使用すると仮定すると、コネクションがポート4334またはポート4335で受け付けられた場合にはNETCONFクライアントプロトコルが開始され、コネクションがポート4336で受け付けられた場合にはRESTCONFクライアントプロトコルが開始されます。

3.2. Client Configuration Data Model

3.2. クライアントの設定データモデル

How a NETCONF or RESTCONF client is configured is outside the scope of this document. For instance, such a configuration might be used to enable listening for call home connections, configuring trusted certificate issuers, or configuring identifiers for expected connections. That said, YANG [RFC7950] data modules for configuring NETCONF and RESTCONF clients, including call home, are provided in [NETCONF-MODELS] and [RESTCONF-MODELS].

NETCONFクライアントまたはRESTCONFクライアントをどのように設定するかは、この文書の範囲外です。たとえば、そのような設定は、コールホームのコネクションの待ち受けを有効にすること、信頼する証明書発行者を設定すること、または予期するコネクションの識別子を設定することに使用されるかもしれません。とはいえ、コールホームを含め、NETCONFクライアントとRESTCONFクライアントを設定するためのYANG [RFC7950]データモジュールが、[NETCONF-MODELS]と[RESTCONF-MODELS]で提供されています。

4. The NETCONF or RESTCONF Server

4. NETCONFサーバーまたはRESTCONFサーバー

The term "server" is defined in [RFC6241], Section 1.1. In the context of network management, the NETCONF/RESTCONF server might be a network element or a device.

「サーバー」という用語は、[RFC6241], セクション1.1で定義されています。ネットワーク管理の文脈では、NETCONF/RESTCONFサーバーはネットワーク要素やデバイスであるかもしれません。

4.1. Server Protocol Operation

4.1. サーバーのプロトコル動作

S1
The NETCONF/RESTCONF server initiates a TCP connection request to the NETCONF/RESTCONF client. The source port may be per local policy or randomly assigned by the operating system. The server MUST support connecting to one of the IANA-assigned ports defined in Section 6, but MAY be configured to connect to a different port. Using the IANA-assigned ports, the server connects to port 4334 for NETCONF over SSH, port 4335 for NETCONF over TLS, and port 4336 for RESTCONF over TLS.
S2
The TCP connection request is accepted and a TCP connection is established.
S3
Using this TCP connection, the NETCONF/RESTCONF server starts either the SSH server [RFC4253] or the TLS server [RFC5246] protocol, depending on how it is configured. For example, assuming the use of the IANA-assigned ports, the SSH server protocol is used after connecting to the remote port 4334 and the TLS server protocol is used after connecting to either remote port 4335 or remote port 4336.
S4
As part of establishing the SSH or TLS connection, the NETCONF/RESTCONF server will send its host key or certificate to the client. If a certificate is sent, the server MUST also send all intermediate certificates leading up to a well-known and trusted issuer. How to send a list of certificates is defined for SSH in [RFC6187], Section 2.1, and for TLS in [RFC5246], Section 7.4.2.
S5
Establishing an SSH or TLS session requires server authentication of client credentials in all cases except with RESTCONF, where some client authentication schemes occur after the secure transport connection (TLS) has been established. If transport-level (SSH or TLS) client authentication is required, and the client is unable to successfully authenticate itself to the server in an amount of time defined by local policy, the server MUST close the connection.
S6
Once the SSH or TLS connection is established, the NETCONF/RESTCONF server starts either the NETCONF server [RFC6241] or RESTCONF server [RFC8040] protocol, depending on how it is configured. Assuming the use of the IANA-assigned ports, the NETCONF server protocol is used after connecting to remote port 4334 or remote port 4335, and the RESTCONF server protocol is used after connecting to remote port 4336.
S7
If a persistent connection is desired, the NETCONF/RESTCONF server, as the connection initiator, SHOULD actively test the aliveness of the connection using a keep-alive mechanism. For TLS-based connections, the NETCONF/RESTCONF server SHOULD send HeartbeatRequest messages, as defined by [RFC6520]. For SSH-based connections, per Section 4 of [RFC4254], the server SHOULD send an SSH_MSG_GLOBAL_REQUEST message with a purposely nonexistent "request name" value (e.g., keepalive@ietf.org) and the "want reply" value set to '1'.
S1
NETCONF/RESTCONFサーバーは、NETCONF/RESTCONFクライアントへのTCPコネクション要求を開始します。送信元ポートは、ローカルポリシーに従ったものでも、オペレーティングシステムによってランダムに割り当てられたものでもかまいません。サーバーは、セクション6で定義するIANAが割り当てたポートのいずれかへの接続をサポートしなければなりません（MUST）が、別のポートに接続するように設定されてもよいです（MAY）。IANAが割り当てたポートを使用する場合、サーバーは、NETCONF over SSHではポート4334に、NETCONF over TLSではポート4335に、RESTCONF over TLSではポート4336に接続します。
S2
TCPコネクション要求が受け付けられ、TCPコネクションが確立されます。
S3
このTCPコネクションを使用して、NETCONF/RESTCONFサーバーは、どのように設定されているかに応じて、SSHサーバー[RFC4253]またはTLSサーバー[RFC5246]のプロトコルを開始します。たとえば、IANAが割り当てたポートを使用すると仮定すると、リモートポート4334に接続した後にはSSHサーバープロトコルが使用され、リモートポート4335またはリモートポート4336に接続した後にはTLSサーバープロトコルが使用されます。
S4
SSHまたはTLSのコネクションの確立の一環として、NETCONF/RESTCONFサーバーは、自身のホスト鍵または証明書をクライアントに送信します。証明書を送信する場合、サーバーは、よく知られた信頼できる発行者に至るまでのすべての中間証明書も送信しなければなりません（MUST）。証明書のリストを送信する方法は、SSHについては[RFC6187], セクション2.1で、TLSについては[RFC5246], セクション7.4.2で定義されています。
S5
SSHまたはTLSのセッションの確立には、RESTCONFの場合を除くすべての場合で、サーバーによるクライアントのクレデンシャルの認証が必要です。RESTCONFでは、一部のクライアント認証スキームが、セキュアなトランスポートのコネクション（TLS）が確立された後に行われます。トランスポートレベル（SSHまたはTLS）のクライアント認証が必要であり、かつ、クライアントがローカルポリシーで定められた時間内にサーバーに対して自身を認証することに成功できない場合、サーバーはコネクションを閉じなければなりません（MUST）。
S6
SSHまたはTLSのコネクションが確立されると、NETCONF/RESTCONFサーバーは、どのように設定されているかに応じて、NETCONFサーバー[RFC6241]またはRESTCONFサーバー[RFC8040]のプロトコルを開始します。IANAが割り当てたポートを使用すると仮定すると、リモートポート4334またはリモートポート4335に接続した後にはNETCONFサーバープロトコルが使用され、リモートポート4336に接続した後にはRESTCONFサーバープロトコルが使用されます。
S7
持続的なコネクションが望まれる場合、NETCONF/RESTCONFサーバーは、コネクションの開始者として、キープアライブメカニズムを使用してコネクションが生きているかどうかを能動的にテストすべきです（SHOULD）。TLSベースのコネクションでは、NETCONF/RESTCONFサーバーは、[RFC6520]で定義されているHeartbeatRequestメッセージを送信すべきです（SHOULD）。SSHベースのコネクションでは、[RFC4254]のセクション4に従い、サーバーは、意図的に存在しない「request name」の値（たとえば、keepalive@ietf.org）を持ち、「want reply」の値を'1'に設定したSSH_MSG_GLOBAL_REQUESTメッセージを送信すべきです（SHOULD）。

4.2. Server Configuration Data Model

4.2. サーバーの設定データモデル

How a NETCONF or RESTCONF server is configured is outside the scope of this document. This includes configuration that might be used to specify hostnames, IP addresses, ports, algorithms, or other relevant parameters. That said, YANG [RFC7950] data modules for configuring NETCONF and RESTCONF servers, including call home, are provided in [NETCONF-MODELS] and [RESTCONF-MODELS].

NETCONFサーバーまたはRESTCONFサーバーをどのように設定するかは、この文書の範囲外です。これには、ホスト名、IPアドレス、ポート、アルゴリズム、またはその他の関連するパラメーターを指定するために使用されるかもしれない設定が含まれます。とはいえ、コールホームを含め、NETCONFサーバーとRESTCONFサーバーを設定するためのYANG [RFC7950]データモジュールが、[NETCONF-MODELS]と[RESTCONF-MODELS]で提供されています。

5. Security Considerations

5. セキュリティーに関する考慮事項

The security considerations described in [RFC6242] and [RFC7589], and by extension [RFC4253], [RFC5246], and [RFC8040] apply here as well.

[RFC6242]と[RFC7589]、およびそれらを通じて[RFC4253]、[RFC5246]、[RFC8040]で説明されているセキュリティーに関する考慮事項が、ここでも適用されます。

This RFC deviates from standard SSH and TLS usage by having the SSH/TLS server initiate the underlying TCP connection. This reversal is incongruous with [RFC4253], which says "the client initiates the connection" and also [RFC6125], which says "the client MUST construct a list of acceptable reference identifiers, and MUST do so independently of the identifiers presented by the service."

このRFCは、SSH/TLSサーバーに基盤となるTCPコネクションを開始させることで、標準的なSSHとTLSの使い方から逸脱しています。この逆転は、「クライアントがコネクションを開始する」と述べている[RFC4253]とも、「クライアントは、受け入れ可能な参照識別子のリストを構築しなければなりません（MUST）。また、サービスが提示する識別子とは独立にそれを行わなければなりません（MUST）」と述べている[RFC6125]とも整合しません。

Risks associated with these variances are centered around server authentication and the inability for clients to compare an independently constructed reference identifier to one presented by the server. To mitigate against these risks, this RFC requires that the NETCONF/RESTCONF client validate the server's SSH host key or certificate, by certificate path validation to a preconfigured issuer certificate, or by comparing the host key or certificate to a previously trusted or "pinned" value. Furthermore, when a certificate is used, this RFC requires that the client be able to match an identifier encoded in the presented certificate with an identifier the client was preconfigured to expect (e.g., a serial number).

これらの相違に関連するリスクは、サーバー認証と、独立して構築した参照識別子をサーバーが提示したものとクライアントが比較できないことを中心としています。これらのリスクを緩和するために、このRFCは、NETCONF/RESTCONFクライアントが、事前に設定された発行者証明書への証明書パス検証によって、またはホスト鍵や証明書を以前に信頼した値や「ピン留め」された値と比較することによって、サーバーのSSHホスト鍵または証明書を検証することを要求しています。さらに、証明書を使用する場合、このRFCは、提示された証明書にエンコードされた識別子を、クライアントが予期するように事前に設定された識別子（たとえば、シリアル番号）と照合できることをクライアントに要求しています。

For cases when the NETCONF/RESTCONF server presents an X.509 certificate, NETCONF/RESTCONF clients should ensure that the preconfigured issuer certificate used for certificate path validation is unique to the manufacturer of the server. That is, the certificate should not belong to a third-party certificate authority that might issue certificates for more than one manufacturer. This is especially important when a client authentication mechanism passing a shared secret (e.g., a password) to the server is used. Not doing so could otherwise lead to a case where the client sends the shared secret to another server that happens to have the same identity (e.g., a serial number) as the server the client was configured to expect.

NETCONF/RESTCONFサーバーがX.509証明書を提示する場合、NETCONF/RESTCONFクライアントは、証明書パス検証に使用する事前に設定された発行者証明書が、そのサーバーの製造業者に固有のものであることを確認すべきです。つまり、その証明書は、複数の製造業者に対して証明書を発行するかもしれない第三者の認証局に属するべきではありません。これは、共有秘密（たとえば、パスワード）をサーバーに渡すクライアント認証メカニズムを使用する場合に特に重要です。そうしなければ、クライアントが予期するように設定されたサーバーと同じ識別情報（たとえば、シリアル番号）をたまたま持つ別のサーバーに、クライアントが共有秘密を送信してしまう事態につながる可能性があります。

Considerations not associated with server authentication follow next.

サーバー認証に関連しない考慮事項を次に示します。

Internet-facing hosts running NETCONF Call Home or RESTCONF Call Home will be fingerprinted via scanning tools such as "zmap" [zmap]. Both SSH and TLS provide many ways in which a host can be fingerprinted. SSH and TLS servers are fairly mature and able to withstand attacks, but SSH and TLS clients may not be as robust. Implementers and deployments need to ensure that software update mechanisms are provided so that vulnerabilities can be fixed in a timely fashion.

NETCONFコールホームまたはRESTCONFコールホームを実行している、インターネットに面したホストは、「zmap」[zmap]のようなスキャンツールによってフィンガープリントを取られるでしょう。SSHとTLSはどちらも、ホストのフィンガープリントを取ることができる多くの方法を提供しています。SSHサーバーとTLSサーバーはかなり成熟しており攻撃に耐えることができますが、SSHクライアントとTLSクライアントはそれほど堅牢ではないかもしれません。実装者と配備者は、脆弱性を時宜を得て修正できるように、ソフトウェア更新メカニズムが提供されることを確実にする必要があります。

An attacker could launch a denial-of-service (DoS) attack on the NETCONF/RESTCONF client by having it perform computationally expensive operations, before deducing that the attacker doesn't possess a valid key. For instance, in TLS 1.3 [TLS1.3], the ClientHello message contains a Key Share value based on an expensive asymmetric key operation. Common precautions mitigating DoS attacks are recommended, such as temporarily blacklisting the source address after a set number of unsuccessful login attempts.

攻撃者は、攻撃者が有効な鍵を所有していないとNETCONF/RESTCONFクライアントが推論する前に、計算コストの高い操作をクライアントに実行させることで、クライアントに対してサービス拒否（DoS）攻撃を仕掛けることができます。たとえば、TLS 1.3 [TLS1.3]では、ClientHelloメッセージに、コストの高い非対称鍵操作に基づくKey Shareの値が含まれます。一定回数のログイン試行の失敗の後に送信元アドレスを一時的にブラックリストに載せるなど、DoS攻撃を緩和する一般的な予防措置が推奨されます。

When using call home with the RESTCONF protocol, special care is required when using some HTTP authentication schemes, especially the Basic [RFC7617] and Digest [RFC7616] schemes, which convey a shared secret (e.g., a password). Implementers and deployments should be sure to review the Security Considerations section in the RFC for any HTTP client authentication scheme used.

RESTCONFプロトコルでコールホームを使用する場合、一部のHTTP認証スキーム、特に共有秘密（たとえば、パスワード）を伝達するBasic [RFC7617]スキームとDigest [RFC7616]スキームを使用するときには、特別な注意が必要です。実装者と配備者は、使用するあらゆるHTTPクライアント認証スキームについて、そのRFCの「セキュリティーに関する考慮事項」のセクションを必ず確認すべきです。
