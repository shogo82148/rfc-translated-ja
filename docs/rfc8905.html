RFC 8905

The 'payto' URI Scheme for Payments

RFC 8905

支払いのための'payto' URIスキーム

Abstract

概要

This document defines the 'payto' Uniform Resource Identifier (URI) scheme for designating targets for payments.

この文書は、支払いの宛先を指定するための'payto' Uniform Resource Identifier（URI）スキームを定義します。

A unified URI scheme for all payment target types allows applications to offer user interactions with URIs that represent payment targets, simplifying the introduction of new payment systems and applications.

すべての支払い宛先タイプに共通の統一されたURIスキームがあれば、アプリケーションは支払い宛先を表すURIを使ったユーザーとのやり取りを提供できるようになり、新しい支払いシステムやアプリケーションの導入が容易になります。

1. Introduction

1. はじめに

This document defines the 'payto' Uniform Resource Identifier (URI) [RFC3986] scheme for designating transfer form data for payments.

この文書は、支払いのための振込フォームデータを指定する'payto' Uniform Resource Identifier（URI）[RFC3986]スキームを定義します。

1.1. Objective

1.1. 目的

A 'payto' URI always identifies the target of a payment. A 'payto' URI consists of a payment target type, a target identifier, and optional parameters such as an amount or a payment reference.

'payto' URIは、常に支払いの宛先を識別します。 'payto' URIは、支払い宛先タイプ、宛先識別子、および金額や支払い参照番号などの任意のパラメーターで構成されます。

The interpretation of the target identifier is defined by the payment target type and typically represents either a bank account or an (unsettled) transaction.

宛先識別子の解釈は支払い宛先タイプによって定義され、通常は銀行口座か（未決済の）取引のいずれかを表します。

A unified URI scheme for all payment target types allows applications to offer user interactions with URIs that represent payment targets, simplifying the introduction of new payment systems and applications.

すべての支払い宛先タイプに共通の統一されたURIスキームがあれば、アプリケーションは支払い宛先を表すURIを使ったユーザーとのやり取りを提供できるようになり、新しい支払いシステムやアプリケーションの導入が容易になります。

1.2. Requirements Language

1.2. 要件言語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

2. Syntax of a 'payto' URI

2. 'payto' URIの構文

This document uses the Augmented Backus-Naur Form (ABNF) of [RFC5234].

この文書では、[RFC5234]の拡張バッカス・ナウア記法（ABNF）を使用します。

  payto-URI = "payto://" authority path-abempty [ "?" opts ]
  opts = opt *( "&" opt )
  opt-name = generic-opt / authority-specific-opt
  opt-value = *pchar
  opt = opt-name "=" opt-value
  generic-opt = "amount" / "receiver-name" / "sender-name" /
                "message" / "instruction"
  authority-specific-opt = ALPHA *( ALPHA / DIGIT / "-" / "." )
  authority = ALPHA *( ALPHA / DIGIT / "-" / "." )

  payto-URI = "payto://" authority path-abempty [ "?" opts ]
  opts = opt *( "&" opt )
  opt-name = generic-opt / authority-specific-opt
  opt-value = *pchar
  opt = opt-name "=" opt-value
  generic-opt = "amount" / "receiver-name" / "sender-name" /
                "message" / "instruction"
  authority-specific-opt = ALPHA *( ALPHA / DIGIT / "-" / "." )
  authority = ALPHA *( ALPHA / DIGIT / "-" / "." )

'path-abempty' is defined in Section 3.3 of [RFC3986]. 'pchar' is defined in Appendix A of [RFC3986].

'path-abempty'は[RFC3986]のSection 3.3で定義されています。 'pchar'は[RFC3986]のAppendix Aで定義されています。

3. Semantics

3. セマンティクス

The authority component of a payment URI identifies the payment target type. The payment target types are defined in the "Payto Payment Target Types" registry (see Section 10). The path component of the URI identifies the target for a payment as interpreted by the respective payment target type. The query component of the URI can provide additional parameters for a payment. Every payment target type SHOULD accept the options defined in generic-opt. The default operation of applications that invoke a URI with the 'payto' scheme MUST be to launch an application (if available) associated with the payment target type that can initiate a payment. If multiple handlers are registered for the same payment target type, the user SHOULD be able to choose which application to launch. This allows users with multiple bank accounts (each accessed via the respective bank's banking application) to choose which account to pay with. An application SHOULD allow dereferencing a 'payto' URI even if the payment target type of that URI is not registered in the "Payto Payment Target Types" registry. Details of the payment MUST be taken from the path and options given in the URI. The user SHOULD be allowed to modify these details before confirming a payment.

支払いURIのオーソリティーコンポーネントは、支払い宛先タイプを識別します。 支払い宛先タイプは、「Payto Payment Target Types」レジストリー（Section 10を参照）で定義されます。 URIのパスコンポーネントは、それぞれの支払い宛先タイプによって解釈される支払いの宛先を識別します。 URIのクエリーコンポーネントは、支払いのための追加のパラメーターを提供できます。 すべての支払い宛先タイプは、generic-optで定義されたオプションを受け入れるべきです（SHOULD）。 'payto'スキームのURIを呼び出すアプリケーションのデフォルトの動作は、支払いを開始できる、支払い宛先タイプに関連付けられたアプリケーションを（利用可能であれば）起動することでなければなりません（MUST）。 同じ支払い宛先タイプに対して複数のハンドラーが登録されている場合、ユーザーはどのアプリケーションを起動するかを選択できるべきです（SHOULD）。 これにより、複数の銀行口座を持つユーザー（それぞれの口座には各銀行のバンキングアプリケーションを介してアクセスする）が、どの口座で支払うかを選択できます。 アプリケーションは、'payto' URIの支払い宛先タイプが「Payto Payment Target Types」レジストリーに登録されていない場合でも、そのURIの参照解決を許可するべきです（SHOULD）。 支払いの詳細は、URIで与えられたパスとオプションから取得しなければなりません（MUST）。 ユーザーは、支払いを確定する前にこれらの詳細を変更できるべきです（SHOULD）。

4. Examples

4. 例

Valid Example:

有効な例：

payto://iban/DE75512108001245126199?amount=EUR:200.0&message=hello

payto://iban/DE75512108001245126199?amount=EUR:200.0&message=hello

Invalid Example (authority missing):

無効な例（オーソリティーがない）：

payto:iban/12345

payto:iban/12345

5. Generic Options

5. 汎用オプション

Applications MUST accept URIs with options in any order. The "amount" option MUST NOT occur more than once. Other options MAY be allowed multiple times, with further restrictions depending on the payment target type. The following options SHOULD be understood by every payment target type.

アプリケーションは、オプションが任意の順序で並んだURIを受け入れなければなりません（MUST）。 "amount"オプションは、2回以上出現してはなりません（MUST NOT）。 その他のオプションは、支払い宛先タイプに応じたさらなる制限のもとで、複数回の出現を許可してもよいです（MAY）。 以下のオプションは、すべての支払い宛先タイプで理解されるべきです（SHOULD）。

amount:

The amount to transfer. The format MUST be:

  amount = currency ":" unit [ "." fraction ]
  currency = 1*ALPHA
  unit = 1*(DIGIT / ",")
  fraction = 1*(DIGIT / ",")

If a 3-letter 'currency' is used, it MUST be an [ISO4217] alphabetic code. A payment target type MAY define semantics beyond ISO 4217 for currency codes that are not 3 characters. The 'unit' value MUST be smaller than 2^53. If present, the 'fraction' MUST consist of no more than 8 decimal digits. The use of commas is optional for readability, and they MUST be ignored.

receiver-name:
Name of the entity that receives the payment (creditor). The value of this option MAY be subject to lossy conversion, modification, and truncation (for example, due to line wrapping or character set conversion).
sender-name:
Name of the entity that makes the payment (debtor). The value of this option MAY be subject to lossy conversion, modification, and truncation (for example, due to line wrapping or character set conversion).
message:
A short message to identify the purpose of the payment. The value of this option MAY be subject to lossy conversion, modification, and truncation (for example, due to line wrapping or character set conversion).
instruction:
A short message giving payment reconciliation instructions to the recipient. An instruction that follows the character set and length limitation defined by the respective payment target type SHOULD NOT be subject to lossy conversion.
amount:

振り込む金額です。 形式は次のとおりでなければなりません（MUST）：

  amount = currency ":" unit [ "." fraction ]
  currency = 1*ALPHA
  unit = 1*(DIGIT / ",")
  fraction = 1*(DIGIT / ",")

3文字の'currency'を使用する場合、それは[ISO4217]のアルファベットコードでなければなりません（MUST）。 支払い宛先タイプは、3文字ではない通貨コードについて、ISO 4217を超えるセマンティクスを定義してもよいです（MAY）。 'unit'の値は2^53より小さくなければなりません（MUST）。 'fraction'が存在する場合、それは8桁以下の10進数字で構成されなければなりません（MUST）。 カンマは読みやすさのために任意で使用できますが、カンマは無視しなければなりません（MUST）。

receiver-name:
支払いを受け取るエンティティー（債権者）の名前です。 このオプションの値は、（たとえば、行の折り返しや文字セットの変換によって）情報が失われる変換、変更、切り詰めの対象となる場合があります（MAY）。
sender-name:
支払いを行うエンティティー（債務者）の名前です。 このオプションの値は、（たとえば、行の折り返しや文字セットの変換によって）情報が失われる変換、変更、切り詰めの対象となる場合があります（MAY）。
message:
支払いの目的を識別するための短いメッセージです。 このオプションの値は、（たとえば、行の折り返しや文字セットの変換によって）情報が失われる変換、変更、切り詰めの対象となる場合があります（MAY）。
instruction:
受取人に支払いの消し込み（reconciliation）の指示を与える短いメッセージです。 それぞれの支払い宛先タイプで定義された文字セットと長さの制限に従う指示は、情報が失われる変換の対象となるべきではありません（SHOULD NOT）。

6. Internationalization and Character Encoding

6. 国際化と文字エンコーディング

Various payment systems use restricted character sets. An application that processes 'payto' URIs MUST convert characters that are not allowed by the respective payment systems into allowable characters using either an encoding or a replacement table. This conversion process MAY be lossy, except for the instruction field. If the value of the instruction field would be subject to lossy conversion, modification, or truncation, the application SHOULD refuse further processing of the payment until a different value for the instruction is provided.

さまざまな支払いシステムでは、制限された文字セットが使われています。 'payto' URIを処理するアプリケーションは、それぞれの支払いシステムで許可されていない文字を、エンコーディングか置換テーブルのいずれかを使って許可された文字に変換しなければなりません（MUST）。 この変換処理は、instructionフィールドを除いて、情報が失われるものでもよいです（MAY）。 instructionフィールドの値が、情報が失われる変換、変更、切り詰めの対象となる場合、アプリケーションは、instructionに別の値が与えられるまで、その支払いのそれ以上の処理を拒否すべきです（SHOULD）。

To avoid special encoding rules for the payment target identifier, the userinfo component [RFC3986] is disallowed in 'payto' URIs. Instead, the payment target identifier is given as an option, where encoding rules are uniform for all options.

支払い宛先識別子のための特別なエンコーディング規則を避けるため、'payto' URIではuserinfoコンポーネント[RFC3986]は許可されません。 代わりに、支払い宛先識別子はオプションとして与えられ、そのエンコーディング規則はすべてのオプションで共通です。

Defining a generic way of tagging the language of option fields containing natural language text (such as "receiver-name", "sender-name", and "message) is out of the scope of this document, as internationalization must accommodate the restrictions and requirements of the underlying banking system of the payment target type. The internationalization concerns SHOULD be individually defined by each payment target type.

自然言語のテキストを含むオプションフィールド（"receiver-name"、"sender-name"、"message"など）の言語をタグ付けする汎用的な方法を定義することは、この文書の範囲外です。 国際化は、支払い宛先タイプの基盤となる銀行システムの制限と要件に対応しなければならないためです。 国際化に関する事項は、支払い宛先タイプごとに個別に定義されるべきです（SHOULD）。

7. Tracking Payment Target Types

7. 支払い宛先タイプの追跡

A registry of "Payto Payment Target Types" is described in Section 10. The registration policy for this registry is "First Come First Served", as described in [RFC8126]. When requesting new entries, careful consideration of the following criteria is strongly advised:

「Payto Payment Target Types」のレジストリーについては、Section 10で説明します。 このレジストリーの登録ポリシーは、[RFC8126]で説明されている「First Come First Served」です。 新しいエントリーをリクエストする際には、次の基準を慎重に検討することを強く勧めます：

  1. The description clearly defines the syntax and semantics of the payment target and optional parameters if applicable.
  2. Relevant references are provided if they are available.
  3. The chosen name is appropriate for the payment target type, does not conflict with well-known payment systems, and avoids potential to confuse users.
  4. The payment system underlying the payment target type is not fundamentally incompatible with the general options (such as positive decimal amounts) in this specification.
  5. The payment target type is not a vendor-specific version of a payment target type that could be described more generally by a vendor-neutral payment target type.
  6. The specification of the new payment target type remains within the scope of payment transfer form data. In particular, specifying complete invoices is not in scope. Neither are processing instructions to the payment processor or bank beyond a simple payment.
  7. The payment target and the options do not contain the payment sender's account details.
  1. 説明が、支払い宛先と、該当する場合は任意のパラメーターの構文とセマンティクスを明確に定義していること。
  2. 関連する参考文献が利用可能であれば、それが提供されていること。
  3. 選択された名前が支払い宛先タイプにふさわしく、よく知られた支払いシステムと衝突せず、ユーザーを混乱させるおそれを避けていること。
  4. 支払い宛先タイプの基盤となる支払いシステムが、この仕様の一般的なオプション（正の10進数の金額など）と根本的に非互換ではないこと。
  5. 支払い宛先タイプが、ベンダー中立の支払い宛先タイプによってより汎用的に記述できるような支払い宛先タイプの、ベンダー固有の版ではないこと。
  6. 新しい支払い宛先タイプの仕様が、支払いの振込フォームデータの範囲内にとどまっていること。 特に、完全な請求書を指定することは範囲外です。 単純な支払いを超えた、決済代行業者や銀行への処理指示も同様に範囲外です。
  7. 支払い宛先とオプションに、支払いの送金者の口座の詳細が含まれていないこと。

Documents that support requests for new registry entries should provide the following information for each entry:

新しいレジストリーエントリーのリクエストを裏付ける文書は、エントリーごとに次の情報を提供するべきです：

Name:
The name of the payment target type (case-insensitive ASCII string, restricted to alphanumeric characters, dots, and dashes).
Description:
A description of the payment target type, including the semantics of the path in the URI if applicable.
Example:
At least one example URI to illustrate the payment target type.
Contact:
The contact information of a person to contact for further information.
References:
Optionally, references describing the payment target type (such as an RFC) and target-specific options or references describing the payment system underlying the payment target type.
名前：
支払い宛先タイプの名前（大文字と小文字を区別しないASCII文字列で、英数字、ドット、ダッシュに制限されます）。
説明：
支払い宛先タイプの説明です。該当する場合は、URIのパスのセマンティクスを含みます。
例：
支払い宛先タイプを説明する、少なくとも1つのURIの例です。
連絡先：
さらなる情報について問い合わせる人の連絡先情報です。
参考文献：
任意で、支払い宛先タイプと宛先固有のオプションを記述した参考文献（RFCなど）、または支払い宛先タイプの基盤となる支払いシステムを記述した参考文献です。

この文書は、次のとおり7つのエントリーをレジストリーに登録します（Section 10も参照してください）。

7.3. International Bank Account Number

7.3. 国際銀行口座番号

Name:
iban
Description:
International Bank Account Number (IBAN). Generally, the IBAN allows to unambiguously derive the associated Business Identifier Code (BIC) using a lookup in the respective proprietary translation table. However, some legacy applications process payments to the same IBAN differently based on the specified BIC. Thus, the path can consist of either a single component (the IBAN) or two components (BIC followed by IBAN). The "message" option of the 'payto' URI corresponds to the "unstructured remittance information" of Single Euro Payments Area (SEPA) credit transfers and is thus limited to 140 characters with character set limitations that differ according to the countries of the banks and payment processors involved in the payment. The "instruction" option of the 'payto' URI corresponds to the "end-to-end identifier" of SEPA credit transfers and is thus limited to, at most, 35 characters, which can be alphanumeric or from the allowed set of special characters, i.e., "+?/-:().,'". Language tagging and internationalization of options are not supported.
Examples:
payto://iban/DE75512108001245126199
payto://iban/SOGEDEFFXXX/DE75512108001245126199

8. Security Considerations

8. セキュリティーに関する考慮事項

Interactive applications handling the 'payto' URI scheme MUST NOT initiate any financial transactions without prior review and confirmation from the user and MUST take measures to prevent clickjacking [HMW12].

'payto' URIスキームを扱う対話型アプリケーションは、ユーザーによる事前の確認と承認なしに金融取引を開始してはなりません（MUST NOT）。 また、クリックジャッキング[HMW12]を防ぐ対策を講じなければなりません（MUST）。

Unless a 'payto' URI is received over a trusted, authenticated channel, a user might not be able to identify the target of a payment. In particular, due to homographs [unicode-tr36], a payment target type SHOULD NOT use human-readable names in combination with unicode in the target account specification, as it could give the user the illusion of being able to identify the target account from the URI.

'payto' URIが信頼できる認証されたチャネルを介して受信されたのでない限り、ユーザーは支払いの宛先を識別できない可能性があります。 特に、ホモグラフ[unicode-tr36]があるため、支払い宛先タイプは、宛先口座の指定において、人間が読める名前をUnicodeと組み合わせて使用すべきではありません（SHOULD NOT）。 そのような名前は、ユーザーにURIから宛先口座を識別できるという錯覚を与える可能性があるためです。

The authentication/authorization mechanisms and transport security services used to process a payment encoded in a 'payto' URI are handled by the application and are not in scope of this document.

'payto' URIにエンコードされた支払いを処理するために使用される認証・認可のメカニズムやトランスポートセキュリティーのサービスは、アプリケーションによって扱われるものであり、この文書の範囲外です。

To avoid unnecessary data collection, payment target types SHOULD NOT include personally identifying information about the sender of a payment that is not essential for an application to conduct a payment.

不必要なデータ収集を避けるため、支払い宛先タイプは、アプリケーションが支払いを行うために必須ではない、支払いの送金者に関する個人を特定できる情報を含めるべきではありません（SHOULD NOT）。
