RFC 10057

A YANG Data Model for Traffic Engineering Tunnels, Label Switched Paths, and Interfaces

RFC 10057

トラフィックエンジニアリングトンネル、ラベルスイッチパス、インターフェイスのためのYANGデータモデル

Abstract

概要

This document defines a YANG data model for the provisioning and management of Traffic Engineering (TE) tunnels, Label Switched Paths (LSPs), and interfaces. The model covers data pertinent to TE tunnels, TE LSPs, and TE interfaces that are independent of any technology or data plane encapsulation. The model is divided into two YANG modules that address both device-specific and device-independent data, supporting configuration, operational state, Remote Procedure Calls (RPCs), and event notifications.

この文書は、トラフィックエンジニアリング（TE）トンネル、ラベルスイッチパス（LSP）、インターフェイスのプロビジョニングと管理のためのYANGデータモデルを定義します。 このモデルは、特定の技術やデータプレーンのカプセル化に依存しない、TEトンネル、TE LSP、TEインターフェイスに関連するデータを対象とします。 このモデルは、デバイス固有のデータとデバイスに依存しないデータの両方を扱う2つのYANGモジュールに分割されており、設定、運用状態、リモートプロシージャーコール（RPC）、イベント通知をサポートします。

1. Introduction

1. はじめに

This document defines a YANG data model intended for the provisioning and management of point-to-point Traffic Engineering (TE) tunnels, Label Switched Paths (LSPs), and interfaces. The modeling of point-to-multipoint TE Tunnels [RFC4875] and Segment Routing (SR) Policies [RFC9256] falls outside the scope of this document.

この文書は、ポイントツーポイントのトラフィックエンジニアリング（TE）トンネル、ラベルスイッチパス（LSP）、インターフェイスのプロビジョニングと管理を目的としたYANGデータモデルを定義します。 ポイントツーマルチポイントのTEトンネル[RFC4875]とセグメントルーティング（SR）ポリシー[RFC9256]のモデル化は、この文書の範囲外です。

The data model described herein is divided into two YANG modules. The "ietf-te" module contains generic, device-independent data, and the "ietf-te-device" module addresses device-specific data.

ここで説明するデータモデルは、2つのYANGモジュールに分割されます。 「ietf-te」モジュールは汎用的でデバイスに依存しないデータを含み、「ietf-te-device」モジュールはデバイス固有のデータを扱います。

This document outlines the high-level relationships between the YANG modules it defines and other external protocol YANG modules. The TE data model intentionally excludes data specific to any signaling protocol, such as RSVP-TE [RFC3209] [RFC3473] or SR [RFC8402] [RFC9256] with the expectation that such technology models will be defined in separate documents and will augment the TE model as needed.

この文書は、この文書で定義するYANGモジュールと、外部の他のプロトコルのYANGモジュールとの高レベルの関係の概要を示します。 TEデータモデルは、RSVP-TE[RFC3209] [RFC3473]やSR[RFC8402] [RFC9256]などのシグナリングプロトコルに固有のデータを意図的に除外しています。 そのような技術のモデルは別の文書で定義され、必要に応じてTEモデルを拡張（augment）することが想定されています。

3. Design Considerations

3. 設計上の考慮事項

This document describes a YANG data model for TE tunnels, TE LSPs, and TE interfaces that are independent of any data plane technology. One of the design objectives is to allow specific data plane technology models to reuse the TE data model and possibly augment it with technology-specific data.

この文書は、データプレーン技術に依存しないTEトンネル、TE LSP、TEインターフェイスのためのYANGデータモデルを説明します。 設計目標のひとつは、特定のデータプレーン技術のモデルがTEデータモデルを再利用し、場合によっては技術固有のデータで拡張できるようにすることです。

The elements of the TE data model, including TE Tunnels, LSPs, and interfaces, have leafs that identify the technology layer where they reside. For example, the LSP encoding type can identify the technology associated with a TE Tunnel or LSP.

TEトンネル、LSP、インターフェイスを含むTEデータモデルの要素は、それらが存在する技術層を識別するリーフを持ちます。 たとえば、LSPのエンコーディング種別によって、TEトンネルやLSPに関連付けられた技術を識別できます。

Also, the TE data model does not cover signaling protocol data. The signaling protocols used to instantiate TE LSPs are outside the scope of this document and are expected to be covered by augmentations defined in other documents.

また、TEデータモデルはシグナリングプロトコルのデータを対象としません。 TE LSPのインスタンス化に使用するシグナリングプロトコルはこの文書の範囲外であり、他の文書で定義される拡張で扱われることが想定されています。

The following other design considerations are taken into account with respect to data organization:

データの構成に関しては、次のその他の設計上の考慮事項を考慮しています：

  • The device-independent TE data is defined in the "ietf-te" module and can be used to manage data off a device, such as a TE controller. When the model is used to manage a specific device, the model contains the TE Tunnels originating from the specific device. When the model is used to manage a TE controller, the 'tunnel' list contains all TE Tunnels and TE tunnel segments originating from devices that the TE controller manages.

  • The device-specific TE data is defined in the "ietf-te-device" module.

  • The TE interfaces in the "ietf-te-device" module are modeled as references to existing interfaces defined in the 'ietf-interfaces' YANG module [RFC8343]. This approach ensures consistency by leveraging standardized interface definitions, allowing TE-specific parameters to be associated with interfaces already defined elsewhere, rather than redefining interface structures within the TE module.

  • Minimal elements in the model are designated as "mandatory" to allow freedom to vendors to adapt the data model to their specific product implementation.

  • Suitable defaults are specified for all configurable elements.

  • Where TE functions or features might be optional within the deployed TE network, the model declares them as optional.

  • Some groupings defined in this document include 'default' statements, which can be problematic for use cases involving templates or profiling. This design does not conform to the guidelines specified in Section 4.13 of [RFC9907]. However, this deviation is intentional as these groupings are specifically tailored for use within the YANG modules defined in this document as well as in [PATH-COMP]. The customization ensures appropriate behavior and consistency across these related modules.

  • デバイスに依存しないTEデータは「ietf-te」モジュールで定義され、TEコントローラーなどのデバイス外でデータを管理するために使用できます。 このモデルを特定のデバイスの管理に使用する場合、モデルにはその特定のデバイスを起点とするTEトンネルが含まれます。 このモデルをTEコントローラーの管理に使用する場合、「tunnel」リストには、TEコントローラーが管理するデバイスを起点とするすべてのTEトンネルとTEトンネルセグメントが含まれます。

  • デバイス固有のTEデータは「ietf-te-device」モジュールで定義されます。

  • 「ietf-te-device」モジュールのTEインターフェイスは、「ietf-interfaces」YANGモジュール[RFC8343]で定義された既存のインターフェイスへの参照としてモデル化されます。 このアプローチでは、標準化されたインターフェイスの定義を活用することで一貫性を確保します。 TEモジュール内でインターフェイスの構造を再定義するのではなく、別の場所ですでに定義されたインターフェイスにTE固有のパラメーターを関連付けることができます。

  • ベンダーが自社製品の実装に合わせてデータモデルを自由に適合させられるように、モデル内で「mandatory」に指定する要素は最小限にしています。

  • 設定可能なすべての要素に適切なデフォルトを指定しています。

  • 展開されたTEネットワーク内でTEの機能が任意である可能性がある場合、モデルではそれらを任意として宣言しています。

  • この文書で定義するグルーピングの一部には「default」文が含まれており、テンプレートやプロファイリングを伴うユースケースでは問題になる可能性があります。 この設計は、[RFC9907]のセクション4.13で規定されたガイドラインに準拠していません。 ただし、これらのグルーピングはこの文書および[PATH-COMP]で定義するYANGモジュール内で使用するために特別に調整されたものであるため、この逸脱は意図的なものです。 このカスタマイズにより、これらの関連するモジュール間で適切な振る舞いと一貫性が確保されます。

5. TE YANG Module

5. TE YANGモジュール

5.1. Relationship Between TE Tunnel, LSP, and Path

5.1. TEトンネル、LSP、パスの関係

The TE model is built around several core constructs: TE tunnel, TE path, and LSP. These concepts are central to the model's structure and functionality.

TEモデルは、TEトンネル、TEパス、LSPといういくつかの中核的な構成概念を中心に構築されています。 これらの概念は、モデルの構造と機能の中心となるものです。

TE Tunnel:
In this context, a TE tunnel represents a logical construct that defines an engineered connectivity service between two endpoints in the network, typically an ingress (source) and an egress (destination). A tunnel is characterized by its attributes (such as name, encoding, and constraints) and serves as the container for the forwarding resources used to realize the desired connectivity.
TE Path:
A path refers to a specific sequence of nodes and links through the network that traffic will follow to traverse the TE tunnel from source to destination. A TE tunnel may have one or more associated TE paths, such as a primary TE path (the preferred path) and secondary TE paths (used for protection or restoration). Each path specifies the constraints, preferences, and optimization criteria that guide its computation and selection.
LSP:
An LSP is an actual, instantiated connection in the data plane that follows a computed TE path through the network. It is the result of signaling protocols (such as RSVP-TE or Segment Routing) setting up forwarding state along the TE path, enabling the tunnel to carry traffic.
TEトンネル（TE Tunnel）：
この文脈において、TEトンネルは、ネットワーク内の2つのエンドポイント（通常は入口（送信元）と出口（宛先））の間のエンジニアリングされた接続サービスを定義する論理的な構成概念を表します。 トンネルは、その属性（名前、エンコーディング、制約など）によって特徴付けられ、目的の接続を実現するために使用される転送リソースのコンテナーとして機能します。
TEパス（TE Path）：
パスとは、トラフィックが送信元から宛先までTEトンネルを通過するためにたどる、ネットワーク内のノードとリンクの特定の並びを指します。 TEトンネルは、プライマリーTEパス（優先されるパス）やセカンダリーTEパス（保護や復旧に使用される）など、1つ以上のTEパスを関連付けることができます。 各パスは、その計算と選択の指針となる制約、優先設定、最適化基準を指定します。
LSP：
LSPは、ネットワーク内の計算されたTEパスに従う、データプレーン内の実際にインスタンス化された接続です。 LSPは、シグナリングプロトコル（RSVP-TEやセグメントルーティングなど）がTEパスに沿って転送状態を設定した結果であり、これによってトンネルがトラフィックを運べるようになります。

The relationship among these concepts is as follows:

これらの概念の関係は次のとおりです：

A TE tunnel is the high-level logical object that defines the desired connectivity and its properties. Each TE tunnel can have one or more TE paths, which define candidate or active routes through the network that may be used to realize the tunnel's connectivity, subject to certain constraints and preferences. For each TE path selected for use, one or more LSPs are instantiated in the network to realize the forwarding state necessary to carry traffic along the specified TE path.

TEトンネルは、目的の接続とその特性を定義する高レベルの論理オブジェクトです。 各TEトンネルは1つ以上のTEパスを持つことができます。 TEパスは、特定の制約と優先設定のもとで、トンネルの接続を実現するために使用される可能性のある、ネットワーク内の候補ルートまたはアクティブなルートを定義します。 使用するために選択された各TEパスについて、指定されたTEパスに沿ってトラフィックを運ぶのに必要な転送状態を実現するために、1つ以上のLSPがネットワーク内でインスタンス化されます。

In summary, a TE tunnel defines the service, a TE path defines how to achieve the service, and an LSP is the instantiated mechanism that actually provides the service in the forwarding plane.

まとめると、TEトンネルはサービスを定義し、TEパスはそのサービスを実現する方法を定義し、LSPは転送プレーンで実際にサービスを提供するインスタンス化されたメカニズムです。

5.2.1. TE Globals

5.2.1. TEのグローバル設定

The 'globals' container covers properties that control a TE feature's behavior system-wide and its respective state as shown in Figure 3 and described in the text that follows.

named-srlgs:
A YANG container for the list of named SRLGs that may be applied to TE links.
named-path-constraints:

A YANG container for a list of named path constraints. Each named path constraint is composed of a set of constraints that can be applied during path computation. A named path constraint can be applied to multiple TE Tunnels. Path constraints may also be specified directly under the TE Tunnel. The path constraints specified under the TE Tunnel take precedence over the path constraints derived from the referenced named path constraint. A named path constraint entry can be formed of the path constraints shown in Figure 4:

name:
A YANG leaf that holds the named path constraint entry. This is unique in the list and used as a key.
te-bandwidth:
A YANG container that holds the technology-agnostic TE bandwidth constraint.
link-protection:
A YANG leaf that holds the link protection type constraint required for the links to be included in the computed path.
setup/hold priority:
YANG leafs that hold the LSP setup and hold admission priority as defined in [RFC3209].
signaling-type:
A YANG leaf that holds the LSP setup type, such as RSVP-TE or SR.
path-metric-bounds:
A YANG container that holds the set of metric bounds applicable on the computed TE tunnel path.
path-affinities-values:
A YANG container that holds the set of affinity values and mask to be used during path computation.
path-affinity-names:
A YANG container that holds the set of named affinity constraints and corresponding inclusion or exclusion instructions for each to be used during path computation.
path-srlgs-lists:
A YANG container that holds the set of SRLG values and corresponding inclusion or exclusion instructions to be used during path computation.
path-srlgs-names:
A YANG container that holds the set of named SRLG constraints and corresponding inclusion or exclusion instructions for each to be used during path computation.
disjointness:
The level of resource disjointness constraint that the secondary path of a TE tunnel has to adhere to.
explicit-route-objects:

A YANG container that holds path constraints in the form of route entries present in the following two lists:

'route-object-exclude-always':
A list of route entries that are always excluded from the path computation. The exclusion of a route entry in this list during path computation is not order sensitive. The route entries in this list have a 'strict' hop-type as described in [RFC4874], Section 3.1.
'route-object-include-exclude':

A list of route entries to include or exclude for the path computation. For route entries in this list that are to be excluded, the hop-type is only allowed to be 'strict' as described in [RFC4874], Section 3.1.

The constraint type (include or exclude) is specified with each route entry. The path computation considers route entry constraints in the order they appear in this list. Once a route entry constraint is consumed from this list, it is not considered any further in the computation of the TE path.

The 'route-object-include-exclude' is used to configure constraints on which route objects (e.g., nodes, links) are included or excluded in the path computation.

The interpretation of an empty 'route-object-include-exclude' list depends on the TE Tunnel (end-to-end or Tunnel Segment) and on the specific path according to the following rules:

  1. An empty 'route-object-include-exclude' list for the primary path of an end-to-end TE Tunnel indicates that there are no route objects to be included or excluded in the path computation.

  2. An empty 'route-object-include-exclude' list for the primary path of a TE Tunnel Segment indicates that no primary LSP is required for that TE Tunnel Segment.

  3. An empty 'route-object-include-exclude' list for a reverse path means it always follows the forward path (i.e., the TE Tunnel is co-routed). When the 'route-object-include-exclude' list is not empty, the reverse path is routed independently of the forward path.

  4. An empty 'route-object-include-exclude' list for the secondary (forward) path of a TE Tunnel segment indicates that the secondary path has the same endpoints as the primary path.

path-in-segment:
A YANG container that contains a list of label restrictions that have to be taken into consideration when stitching to another tunnel segment such as at a domain boundary. The TE tunnel segment in this case is being stitched to the upstream TE tunnel segment.
path-out-segment:
A YANG container that contains a list of label restrictions that have to be taken into consideration when stitching to another tunnel segment such as at a domain boundary. The TE tunnel segment in this case is being stitched to the downstream TE tunnel segment.
named-admin-groups:
TEリンクに適用できる、名前付きの（拡張）管理グループのリストのためのYANGコンテナーです。
named-srlgs:
TEリンクに適用できる、名前付きのSRLGのリストのためのYANGコンテナーです。
named-path-constraints:

名前付きのパス制約のリストのためのYANGコンテナーです。 各名前付きパス制約は、パス計算の際に適用できる制約の集合で構成されます。 名前付きパス制約は、複数のTEトンネルに適用できます。 パス制約は、TEトンネルの下に直接指定することもできます。 TEトンネルの下に指定されたパス制約は、参照された名前付きパス制約から導出されたパス制約よりも優先されます。 名前付きパス制約のエントリーは、図4に示すパス制約で構成できます：

name:
名前付きパス制約のエントリーを保持するYANGリーフです。 これはリスト内で一意であり、キーとして使用されます。
te-bandwidth:
技術に依存しないTE帯域幅の制約を保持するYANGコンテナーです。
link-protection:
計算されたパスに含めるリンクに要求される、リンク保護種別の制約を保持するYANGリーフです。
setup/hold priority:
[RFC3209]で定義された、LSPのセットアップ優先度と保持優先度を保持するYANGリーフです。
signaling-type:
RSVP-TEやSRなどのLSPのセットアップ種別を保持するYANGリーフです。
path-metric-bounds:
計算されたTEトンネルのパスに適用できるメトリックの上限の集合を保持するYANGコンテナーです。
path-affinities-values:
パス計算の際に使用するアフィニティーの値とマスクの集合を保持するYANGコンテナーです。
path-affinity-names:
名前付きのアフィニティー制約の集合と、パス計算の際に使用する、それぞれに対応する包含または除外の指示を保持するYANGコンテナーです。
path-srlgs-lists:
SRLG値の集合と、パス計算の際に使用する、対応する包含または除外の指示を保持するYANGコンテナーです。
path-srlgs-names:
名前付きのSRLG制約の集合と、パス計算の際に使用する、それぞれに対応する包含または除外の指示を保持するYANGコンテナーです。
disjointness:
TEトンネルのセカンダリーパスが従わなければならない、リソースの分離（disjointness）制約のレベルです。
explicit-route-objects:

次の2つのリストに存在するルートエントリーの形で、パス制約を保持するYANGコンテナーです：

'route-object-exclude-always':
パス計算から常に除外されるルートエントリーのリストです。 パス計算の際に、このリスト内のルートエントリーを除外する処理は順序に依存しません。 このリスト内のルートエントリーは、[RFC4874], セクション3.1で説明されている「strict」のホップ種別を持ちます。
'route-object-include-exclude':

パス計算のために包含または除外するルートエントリーのリストです。 このリスト内の除外対象のルートエントリーについては、[RFC4874], セクション3.1で説明されているように、ホップ種別として「strict」のみが許可されます。

制約の種別（包含または除外）は、各ルートエントリーとともに指定されます。 パス計算では、ルートエントリーの制約をこのリストに現れる順序で考慮します。 ルートエントリーの制約がこのリストから消費されると、その制約はTEパスの計算でそれ以上考慮されません。

「route-object-include-exclude」は、パス計算においてどのルートオブジェクト（たとえばノードやリンク）を包含または除外するかについての制約を設定するために使用します。

空の「route-object-include-exclude」リストの解釈は、次の規則に従い、TEトンネル（エンドツーエンドかトンネルセグメントか）と特定のパスに依存します：

  1. エンドツーエンドのTEトンネルのプライマリーパスに対する空の「route-object-include-exclude」リストは、パス計算で包含または除外するルートオブジェクトがないことを示します。

  2. TEトンネルセグメントのプライマリーパスに対する空の「route-object-include-exclude」リストは、そのTEトンネルセグメントにはプライマリーLSPが不要であることを示します。

  3. 逆方向パスに対する空の「route-object-include-exclude」リストは、逆方向パスが常に順方向パスに従う（つまり、TEトンネルが同一経路（co-routed）である）ことを意味します。 「route-object-include-exclude」リストが空でない場合、逆方向パスは順方向パスとは独立に経路選択されます。

  4. TEトンネルセグメントのセカンダリー（順方向）パスに対する空の「route-object-include-exclude」リストは、セカンダリーパスがプライマリーパスと同じエンドポイントを持つことを示します。

path-in-segment:
ドメイン境界などで別のトンネルセグメントに接合（stitch）する際に考慮しなければならない、ラベル制限のリストを含むYANGコンテナーです。 この場合、TEトンネルセグメントは上流のTEトンネルセグメントに接合されます。
path-out-segment:
ドメイン境界などで別のトンネルセグメントに接合する際に考慮しなければならない、ラベル制限のリストを含むYANGコンテナーです。 この場合、TEトンネルセグメントは下流のTEトンネルセグメントに接合されます。

5.2.2. TE Tunnels

The 'tunnels' container holds the list of TE Tunnels that are provisioned on ingress router devices in the network as shown in Figure 5.

The TE Tunnel model allows the configuration and management of the following TE tunnel objects:

TEトンネルモデルでは、次のTEトンネルオブジェクトの設定と管理ができます：

TE Tunnel:
A YANG container of one or more TE LSPs established between the source and destination TE Tunnel termination points.
TE Path:
An engineered path that, once instantiated in the forwarding plane, can be used to forward traffic from the source to the destination TE Tunnel termination points.
TE LSP:
A TE LSP is a connection-oriented service established over a TE path and that allows the delivery of traffic between the TE Tunnel source and destination termination points.
TE Tunnel Segment:
A segment of a TE Tunnel that is stitched with other segments in order to provision an end-to-end tunnel.
TEトンネル（TE Tunnel）：
送信元と宛先のTEトンネル終端点の間に確立された、1つ以上のTE LSPのYANGコンテナーです。

転送プレーンでインスタンス化されると、送信元から宛先のTEトンネル終端点へトラフィックを転送するために使用できる、エンジニアリングされたパスです。
TE LSP：
TE LSPは、TEパス上に確立されるコネクション指向のサービスであり、TEトンネルの送信元と宛先の終端点の間でトラフィックを配送できるようにするものです。

A YANG leaf that holds the name of a TE Tunnel. The name of the TE Tunnel uniquely identifies the tunnel within the TE tunnel list. A YANG leaf that holds an identifier of the tunnel. This identifier is unique among tunnels originated from the same ingress device.

A YANG leaf that holds the color associated with the TE tunnel. The color is used to map or steer services that carry matching colors onto the TE tunnel as described in [RFC9012].
admin-state:
A YANG leaf that holds the tunnel administrative state.
operational-state:
A YANG leaf that holds the tunnel operational state.

トンネルの再最適化の間隔を設定するYANGリーフです。

TEトンネルと他のTEトンネルとの関連付け（association）の集合を保持するYANGコンテナーです。 TEトンネルのレベルの関連付けは、TEトンネルのすべてのパスに適用されます。 TEトンネルの関連付けは、TEトンネルのパスの下に直接設定された関連付けによって上書きできます。

TEトンネルの復旧に関する特性を保持するYANGコンテナーです。

[RFC8345]で定義された、TEトンネルのパスが計算されるネットワークトポロジーを識別するために任意で使用できるYANGリーフです。

TEトンネルの階層に関連する特性を保持するYANGコンテナーです。 TE LSPは、MPLSまたは汎用MPLS（GMPLS）ネットワークで、他の（クライアント）ネットワークのトラフィックを運ぶTEリンクとして使用するためにセットアップできます[RFC6107]。 この場合、このモデルは、基盤となるTEトンネルが関連付けられているクライアント層の特定のリンクを識別するために、TEトンネルの階層リンクのエンドポイントパラメーターを導入します。 hierarchyコンテナーには次のものが含まれます：

dependency-tunnels:
直下の下位層でプロビジョニングされた、またはプロビジョニングされる予定のTEトンネルの階層的な集合であり、現在のTEトンネルはマルチレイヤーのパス計算においてこれに依存します。 依存TEトンネルは、少なくとも1つのクライアント層のTEトンネルをサポートするためにパス計算によって選択された場合にプロビジョニングされます。 依存TEトンネルがプロビジョニングされると、クライアント層のネットワークトポロジーでTEリンクが運用可能になり、クライアント層でTEトンネルをプロビジョニングできるようになります。

このTEトンネルによってサポートされる（クライアント層の）階層リンクの識別情報を保持するYANGコンテナーです。 階層リンクのエンドポイントは、TEトンネルの送信元ノードと宛先ノードのエンドポイントによって定義されます。 階層リンクは、送信元と宛先のリンク終端点の識別子によって識別できます。

primary-reverse-path:

5.2.3. TE LSPs

5.2.3. TE LSP

The 'lsps' container includes the set of TE LSPs that have been instantiated. A TE LSP is identified by a 3-tuple ('tunnel-name', 'lsp-id', 'node').

「lsps」コンテナーには、インスタンス化されたTE LSPの集合が含まれます。 TE LSPは、3つ組（「tunnel-name」、「lsp-id」、「node」）によって識別されます。

When the model is used to manage a specific device, the 'lsps' list contains all TE LSPs that traverse the device (including ingressing, transiting, and egressing the device).

このモデルを特定のデバイスの管理に使用する場合、「lsps」リストには、そのデバイスを通過する（デバイスへの入口、中継、デバイスからの出口を含む）すべてのTE LSPが含まれます。

When the model is used to manage a TE controller, the 'lsps' list contains the TE LSPs on devices managed by the controller that act as ingress, and may optionally include TE LSPs on devices managed by the controller that act as a transit or egress role.

このモデルをTEコントローラーの管理に使用する場合、「lsps」リストには、コントローラーが管理するデバイスのうち入口として動作するデバイス上のTE LSPが含まれます。 また、任意で、コントローラーが管理するデバイスのうち中継または出口の役割として動作するデバイス上のTE LSPを含めることもできます。

6. TE Device YANG Module

6. TEデバイスYANGモジュール

The TE device YANG module "ietf-te-device" models data that is specific to managing a TE device. This module augments the TE YANG module.

TEデバイスYANGモジュール「ietf-te-device」は、TEデバイスの管理に固有のデータをモデル化します。 このモジュールはTE YANGモジュールを拡張します。

6.1. Module Structure

6.1. モジュールの構造

The "ietf-te-device" module defines the configuration and operational state data that is specific to the device, including those related to the TE subsystem, tunnels, LSPs, and interfaces.

「ietf-te-device」モジュールは、TEサブシステム、トンネル、LSP、インターフェイスに関連するものを含む、デバイス固有の設定データと運用状態データを定義します。

6.1.1. TE Device Globals, Tunnels, and LSPs

6.1.1. TEデバイスのグローバル設定、トンネル、LSP

The "ietf-te-device" module augments the TE YANG module "ietf-te" at the 'globals', 'tunnels', and 'lsps' levels to include the device-specific configurations and operational state.

「ietf-te-device」モジュールは、デバイス固有の設定と運用状態を含めるために、TE YANGモジュール「ietf-te」を「globals」、「tunnels」、「lsps」のレベルで拡張します。

Figure 7 shows the "ietf-te-device" subtree generated with depth=4 that describes those augmentations.

図7に、これらの拡張を表す、深さ4（depth=4）で生成した「ietf-te-device」のサブツリーを示します。

The following is the description of the augmented data at each level.

以下は、各レベルで拡張されるデータの説明です。

Global Timers (Augmenting /te:te/te:globals):

These are device-specific global configuration parameters related to LSP timers, applied system-wide.

lsp-install-interval:
An optional leaf that specifies the delay time, in seconds, before a newly provisioned LSP is installed into the forwarding plane to carry traffic.
lsp-cleanup-interval:
An optional leaf that specifies the delay time, in seconds, before an LSP is completely removed from the system after it is no longer in use.
lsp-invalidation-interval:
An optional leaf that specifies the delay time, in seconds, during which a TE LSP's path is considered invalid before any corrective action is taken.
Tunnel Device-Dependent Attributes (Augmenting /te:te/te:tunnels/te:tunnel):

These are device-specific configuration parameters that apply to individual TE Tunnels:

path-invalidation-action:
An optional identityref that specifies the action to be taken when a TE Tunnel's path is deemed invalid (e.g., tear down, recompute).
lsp-install-interval:
An optional leaf that specifies the delay time, in seconds, for this specific TE Tunnel before its LSPs are installed into the forwarding plane. This value can override the global lsp-install-interval.
lsp-cleanup-interval:
An optional leaf that specifies the delay time, in seconds, for this specific TE Tunnel before its LSPs are cleaned up. This value can override the global lsp-cleanup-interval.
lsp-invalidation-interval:
An optional leaf that specifies the delay time, in seconds, for this specific TE Tunnel during which its path is considered invalid before action is taken. This value can override the global lsp-invalidation-interval.
LSP Device-Dependent State (Augmenting /te:te/te:lsps/te:lsp):

These are read-only operational state parameters providing device-specific details for individual LSPs:

lsp-timers:
A container that holds various timer-related operational state for an LSP, applicable primarily to ingress LSPs.
uptime:
An optional leaf that indicates the total time, in seconds, that the LSP has been operational.
time-to-install:
An optional leaf that indicates the remaining time, in seconds, for a new LSP to be fully instantiated and ready to carry traffic.
time-to-destroy:
An optional leaf that indicates the remaining time, in seconds, before an existing LSP is torn down.
downstream-info:
A container that holds information about the downstream neighbor and label for the LSP, applicable when the LSP is not at its egress.
upstream-info:
A container that holds information about the upstream neighbor and label for the LSP, applicable when the LSP is not at its ingress.
グローバルタイマー（/te:te/te:globalsを拡張）：

これらは、システム全体に適用される、LSPのタイマーに関連するデバイス固有のグローバル設定パラメーターです。

lsp-install-interval:
新しくプロビジョニングされたLSPが、トラフィックを運ぶために転送プレーンにインストールされるまでの遅延時間を秒単位で指定する、任意のリーフです。
lsp-cleanup-interval:
LSPが使用されなくなってから、システムから完全に削除されるまでの遅延時間を秒単位で指定する、任意のリーフです。
lsp-invalidation-interval:
是正措置が取られる前に、TE LSPのパスが無効とみなされる遅延時間を秒単位で指定する、任意のリーフです。
トンネルのデバイス依存属性（/te:te/te:tunnels/te:tunnelを拡張）：

これらは、個々のTEトンネルに適用されるデバイス固有の設定パラメーターです：

lsp-install-interval:
この特定のTEトンネルについて、LSPが転送プレーンにインストールされるまでの遅延時間を秒単位で指定する、任意のリーフです。 この値は、グローバルなlsp-install-intervalを上書きできます。
lsp-cleanup-interval:
この特定のTEトンネルについて、LSPがクリーンアップされるまでの遅延時間を秒単位で指定する、任意のリーフです。 この値は、グローバルなlsp-cleanup-intervalを上書きできます。
lsp-invalidation-interval:
この特定のTEトンネルについて、アクションが実行される前にパスが無効とみなされる遅延時間を秒単位で指定する、任意のリーフです。 この値は、グローバルなlsp-invalidation-intervalを上書きできます。
LSPのデバイス依存状態（/te:te/te:lsps/te:lspを拡張）：

lsp-timers:
LSPのタイマーに関連するさまざまな運用状態を保持するコンテナーであり、主に入口LSPに適用されます。
uptime:
LSPが運用可能であった合計時間を秒単位で示す、任意のリーフです。
time-to-install:
新しいLSPが完全にインスタンス化されてトラフィックを運べるようになるまでの残り時間を秒単位で示す、任意のリーフです。
time-to-destroy:
既存のLSPが切断されるまでの残り時間を秒単位で示す、任意のリーフです。
downstream-info:
LSPの下流の隣接ノードとラベルに関する情報を保持するコンテナーであり、LSPが出口にない場合に適用されます。
upstream-info:
LSPの上流の隣接ノードとラベルに関する情報を保持するコンテナーであり、LSPが入口にない場合に適用されます。

down-thresholds:

up-down-thresholds:

te-metric:

admin-group-type:

value-admin-groups:

named-admin-groups:

srlg-type:

named-srlgs:

down-thresholds:

9. Security Considerations

9. セキュリティーに関する考慮事項

The "ietf-te" and "ietf-te-device" YANG modules define a data model that is designed to be accessed via YANG-based management protocols, such as the Network Configuration Protocol (NETCONF) [RFC6241] and RESTCONF [RFC8040]. These YANG-based management protocols (1) have to use a secure transport layer (e.g., Secure Shell (SSH) [RFC6242], TLS [RFC9846], and QUIC [RFC9000]) and (2) have to use mutual authentication.

「ietf-te」YANGモジュールと「ietf-te-device」YANGモジュールは、ネットワーク設定プロトコル（NETCONF）[RFC6241]やRESTCONF[RFC8040]などのYANGベースの管理プロトコルを介してアクセスされるように設計されたデータモデルを定義します。 これらのYANGベースの管理プロトコルは、（1）安全なトランスポート層（たとえば、セキュアシェル（SSH）[RFC6242]、TLS[RFC9846]、QUIC[RFC9000]）を使用する必要があり、（2）相互認証を使用する必要があります。

The Network Configuration Access Control Model (NACM) [RFC8341] provides the means to restrict access for particular NETCONF or RESTCONF users to a preconfigured subset of all available NETCONF or RESTCONF protocol operations and content.

Network Configuration Access Control Model（NACM）[RFC8341]は、特定のNETCONFまたはRESTCONFのユーザーのアクセスを、利用可能なすべてのNETCONFまたはRESTCONFのプロトコル操作とコンテンツのうち、事前に設定されたサブセットに制限する手段を提供します。

There are a number of data nodes defined in these YANG modules that are writable/creatable/deletable (i.e., "config true", which is the default). All writable data nodes are likely to be sensitive or vulnerable in some network environments. Write operations (e.g., edit-config) and delete operations to these data nodes without proper protection or authentication can have a negative effect on network operations. The following subtrees and data nodes have particular sensitivities/vulnerabilities:

これらのYANGモジュールには、書き込み/作成/削除が可能な（つまり、デフォルトである「config true」の）データノードがいくつか定義されています。 書き込み可能なデータノードはすべて、一部のネットワーク環境では機密性が高い、または脆弱である可能性があります。 適切な保護や認証なしにこれらのデータノードに対して書き込み操作（たとえばedit-config）や削除操作を行うと、ネットワークの運用に悪影響を与える可能性があります。 次のサブツリーとデータノードには、特有の機密性や脆弱性があります：

"/te/globals":
This module specifies the global TE configurations on a device. Unauthorized access to this container could cause the device to ignore packets it should receive and process.
"/te/tunnels":
This list specifies the configuration and state of TE Tunnels present on the device or controller. Unauthorized access to this list could cause the device to ignore packets it should receive and process. An attacker may also use state to derive information about the network topology and subsequently orchestrate further attacks.
"/te/interfaces":
This list specifies the configuration and state TE interfaces on a device. Unauthorized access to this list could cause the device to ignore packets it should receive and process.
"/te/globals":
このモジュールは、デバイス上のグローバルなTE設定を指定します。 このコンテナーへの不正なアクセスにより、デバイスが受信して処理すべきパケットを無視する可能性があります。
"/te/tunnels":
このリストは、デバイスまたはコントローラー上に存在するTEトンネルの設定と状態を指定します。 このリストへの不正なアクセスにより、デバイスが受信して処理すべきパケットを無視する可能性があります。 また、攻撃者は状態を使用してネットワークトポロジーに関する情報を導き出し、その後さらなる攻撃を仕掛ける可能性があります。
"/te/interfaces":
このリストは、デバイス上のTEインターフェイスの設定と状態を指定します。 このリストへの不正なアクセスにより、デバイスが受信して処理すべきパケットを無視する可能性があります。

Some of the readable data nodes in these YANG modules may be considered sensitive or vulnerable in some network environments. It is thus important to control read access (e.g., via get, get-config, or notification) to these data nodes. Specifically, the following subtrees and data nodes have particular sensitivities/vulnerabilities:

これらのYANGモジュール内の読み取り可能なデータノードの一部は、一部のネットワーク環境では機密性が高い、または脆弱であるとみなされる場合があります。 したがって、これらのデータノードへの読み取りアクセス（たとえばget、get-config、notificationによるもの）を制御することが重要です。 具体的には、次のサブツリーとデータノードには、特有の機密性や脆弱性があります：

"/te/lsps":
This list contains information state about established LSPs in the network. An attacker can use this information to derive information about the network topology and subsequently orchestrate further attacks.
"/te/lsps":
このリストには、ネットワーク内で確立されたLSPに関する状態情報が含まれます。 攻撃者はこの情報を使用してネットワークトポロジーに関する情報を導き出し、その後さらなる攻撃を仕掛ける可能性があります。

Some of the RPC or action operations in these YANG modules may be considered sensitive or vulnerable in some network environments. It is thus important to control access to these operations. Specifically, the following operations have particular sensitivities/ vulnerabilities:

これらのYANGモジュール内のRPCまたはアクション操作の一部は、一部のネットワーク環境では機密性が高い、または脆弱であるとみなされる場合があります。 したがって、これらの操作へのアクセスを制御することが重要です。 具体的には、次の操作には特有の機密性や脆弱性があります：

"/te/tunnels-actions":
Using this RPC, an attacker can modify existing paths that may be carrying live traffic, and hence result in interruption to services carried over the network.
"/te/tunnels-path-compute":
Using this RPC, an attacker can retrieve sensitive information about the network provider which can be used to orchestrate further attacks.
"/te/tunnels-actions":
このRPCを使用すると、攻撃者は実トラフィックを運んでいる可能性のある既存のパスを変更でき、その結果、ネットワーク上で運ばれるサービスが中断される可能性があります。
"/te/tunnels-path-compute":
このRPCを使用すると、攻撃者はネットワークプロバイダーに関する機密情報を取得でき、それがさらなる攻撃を仕掛けるために使用される可能性があります。

The "ietf-te" YANG module defines a set of identities, types, and groupings. These nodes are intended to be reused by other YANG modules. The module by itself does not expose any data nodes that are writable, data nodes that contain read-only state, or RPCs. As such, there are no additional security issues related to the "ietf-te" YANG module that need to be considered.

「ietf-te」YANGモジュールは、アイデンティティー、型、グルーピングの集合を定義します。 これらのノードは、他のYANGモジュールで再利用されることを意図しています。 このモジュール自体は、書き込み可能なデータノード、読み取り専用の状態を含むデータノード、RPCのいずれも公開しません。 そのため、「ietf-te」YANGモジュールに関連して考慮する必要がある追加のセキュリティー上の問題はありません。

Modules that use the groupings that are defined in this document should identify the corresponding security considerations. For example, reusing some of these groupings will expose privacy-related information (e.g., 'node-example').

この文書で定義するグルーピングを使用するモジュールは、対応するセキュリティーに関する考慮事項を明らかにすべきです。 たとえば、これらのグルーピングの一部を再利用すると、プライバシーに関連する情報（たとえば「node-example」）が公開されることになります。
