RFC 2603

ILMI-Based Server Discovery for NHRP

RFC 2603

NHRPのためのILMIベースのサーバー発見

Abstract

概要

This memo defines how ILMI-based Server Discovery, which provides a method for ATM-attached hosts and routers to dynamically determine the ATM addresses of servers, shall be used to locate NHRP servers.

このメモは、ATMに接続されたホストとルーターがサーバーのATMアドレスを動的に決定する方法を提供するILMIベースのサーバー発見（Server Discovery）を、NHRPサーバーの位置を特定するためにどのように使うものとするかを定義します。

1. Introduction

1. はじめに

Presently, configuring a host or router to use NHRP [1] is cumbersome and error-prone since it requires at least one ATM address to be statically configured on each host or router in the network. Further, it is impossible to implement a diskless host to use NHRP since local configuration is required. ILMI-based Server Discovery, hereafter referred to as "server discovery," provides a solution to these problems.

現在、NHRP[1]を使うようにホストやルーターを設定するのは、ネットワーク内の各ホストやルーターに少なくとも1つのATMアドレスを静的に設定する必要があるため、煩雑で誤りが起きやすくなっています。さらに、ローカルな設定が必要なので、NHRPを使うディスクレスホストを実装することは不可能です。ILMIベースのサーバー発見（以下「サーバー発見」と呼びます）は、これらの問題に対する解決策を提供します。

A brief overview of the Integrated Local Management Interface (ILMI) and the Service Registry MIB, as defined by the ATM Forum, are provided in this memo. The reader should consult [2] for a complete description of ILMI and this MIB, but the information contained here is sufficient for an understanding of its use to support NHRP server discovery.

このメモでは、ATMフォーラムが定義する統合ローカル管理インターフェイス（Integrated Local Management Interface; ILMI）とサービスレジストリーMIB（Service Registry MIB）の概要を簡単に説明します。ILMIとこのMIBの完全な説明については[2]を参照してください。ただし、NHRPサーバー発見を支援するためのその使い方を理解するには、ここに含まれる情報で十分です。

2. Integrated Local Management Interface

2. 統合ローカル管理インターフェイス

The Integrated Local Management Interface (ILMI) [2] provides a mechanism for ATM-attached devices, such as hosts, routers, and ATM switches, to transfer management information. It is based on the Simple Network Management Protocol (SNMP), Version 1, and supports get, get-next, set and trap operations.

統合ローカル管理インターフェイス（ILMI）[2]は、ホスト、ルーター、ATMスイッチなどのATMに接続された機器が管理情報を転送するための仕組みを提供します。ILMIは簡易ネットワーク管理プロトコル（Simple Network Management Protocol; SNMP）のバージョン1に基づいており、get、get-next、set、trapの各操作をサポートします。

The ILMI specification designates the switch side of the ATM link as the 'network side' and the host/router side of the ATM link as the ' user side.' The Service Registry MIB, which is outlined in Section 3, is implmented on the network side and is queried from the user side.

ILMI仕様では、ATMリンクのスイッチ側を「ネットワーク側（network side）」、ATMリンクのホスト/ルーター側を「ユーザー側（user side）」と呼びます。セクション3で概要を説明するサービスレジストリーMIBは、ネットワーク側に実装され、ユーザー側から問い合わせを受けます。

3. ILMI 4.0 Service Registry MIB

3. ILMI 4.0サービスレジストリーMIB

Server discovery utilizes the Service Registry MIB defined by the ATM Forum in ILMI Specification Version 4.0 [2]. To support the existing framework for IP over ATM, ATM switches must support the Service Registry MIB.

サーバー発見は、ATMフォーラムがILMI仕様バージョン4.0[2]で定義したサービスレジストリーMIBを利用します。IP over ATMの既存の枠組みをサポートするために、ATMスイッチはサービスレジストリーMIBをサポートしなければなりません。

A row in the service registry table [2] is defined as:

サービスレジストリーテーブル[2]の行は、次のように定義されています。

   AtmfSrvcRegEntry ::= SEQUENCE {
       atmfSrvcRegPort          INTEGER,
       atmfSrvcRegServiceID     OBJECT IDENTIFIER,
       atmfSrvcRegATMAddress    AtmAddress,
       atmfSrvcRegAddressIndex  INTEGER,
       atmfSrvcRegParm1         OCTET STRING
   }

   AtmfSrvcRegEntry ::= SEQUENCE {
       atmfSrvcRegPort          INTEGER,
       atmfSrvcRegServiceID     OBJECT IDENTIFIER,
       atmfSrvcRegATMAddress    AtmAddress,
       atmfSrvcRegAddressIndex  INTEGER,
       atmfSrvcRegParm1         OCTET STRING
   }

The definition of each field in this structure is:

この構造の各フィールドの定義は次のとおりです。

atmfSrvcRegPort
The ATM port number for which this entry contains management information. The value of zero may be used to indicate the ATM interface over which a management request was received.
atmfSrvcRegServiceID
This is the service identifier that uniquely identifies the type of service at the address provided in the table. (See Section 3.2 for NHRP OID.)
atmfSrvcRegATMAddress
This is the full address of the service. The ATM client will use this address to establish a connection with the service.
atmfSrvcRegAddressIndex
An arbitrary integer to differentiate multiple rows containing different ATM addresses for the same service on the same port.
atmfSrvcRegParm1
An octet string whose size and meaning is determined by the value of atmfSrvcRegServiceID.
atmfSrvcRegPort
このエントリーが管理情報を保持するATMポートの番号です。値0は、管理リクエストを受信したATMインターフェイスを示すために使える場合があります。
atmfSrvcRegServiceID
テーブルで提供されるアドレスにあるサービスの種類を一意に識別するサービス識別子です。（NHRPのOIDについてはセクション3.2を参照してください。）
atmfSrvcRegATMAddress
サービスの完全なアドレスです。ATMクライアントは、このアドレスを使ってサービスとの接続を確立します。
atmfSrvcRegAddressIndex
同じポート上の同じサービスについて、異なるATMアドレスを含む複数の行を区別するための任意の整数です。
atmfSrvcRegParm1
オクテット文字列で、そのサイズと意味はatmfSrvcRegServiceIDの値によって決まります。

The service registry table is indexed by atmfSrvcRegPort, atmfSrvcRegServiceID and atmfSrvcRegAddressIndex.

サービスレジストリーテーブルは、atmfSrvcRegPort、atmfSrvcRegServiceID、atmfSrvcRegAddressIndexによってインデックス付けされます。

3.1. Service Parameter String

3.1. サービスパラメーター文字列

A generic parameter string is defined in the service registry table, thus allowing protocol-specific parameters to be specified. To be consistent with [1], the parameter string for NHRP shall be:

サービスレジストリーテーブルには汎用のパラメーター文字列が定義されており、これによってプロトコル固有のパラメーターを指定できます。[1]との一貫性を保つため、NHRPのパラメーター文字列は次のとおりとします。

    ar$pro.type   16   bits     Protocol type
    ar$pro.snap   40   bits     Optional extension to protocol type
    ar$plen        8   bits     Length of protocol address
    ar$addr       plen octets   Network address
    ar$mask       plen octets   Network mask

    ar$pro.type   16   bits     Protocol type
    ar$pro.snap   40   bits     Optional extension to protocol type
    ar$plen        8   bits     Length of protocol address
    ar$addr       plen octets   Network address
    ar$mask       plen octets   Network mask

Where

ここで、

ar$pro.type
See [1]. (IPv4 is 0x0800, IPv6 is 0x86DD)
ar$pro.snap
See [1]. (IPv4 and IPv6 are 0)
ar$plen
Length of the protocol address. (IPv4 is 4, IPv6 is 16)
ar$addr
Network address represented in network byte order
ar$mask
Network mask represented in network byte order
ar$pro.type
[1]を参照してください。（IPv4は0x0800、IPv6は0x86DDです）
ar$pro.snap
[1]を参照してください。（IPv4とIPv6は0です）
ar$plen
プロトコルアドレスの長さです。（IPv4は4、IPv6は16です）
ar$addr
ネットワークバイトオーダーで表現されたネットワークアドレスです。
ar$mask
ネットワークバイトオーダーで表現されたネットワークマスクです。

3.2. Service Object Identifier

3.2. サービスオブジェクト識別子

This OID, assigned in the ATM Forum Service Registry MIB, names ATMARP within the context of server discovery.

ATMフォーラムのサービスレジストリーMIBで割り当てられたこのOIDは、サーバー発見の文脈においてATMARPを指す名前です。

  atmfSrvcRegNHRP OBJECT IDENTIFIER ::= { 1.3.6.1.4.1.353.1.5.5 }

  atmfSrvcRegNHRP OBJECT IDENTIFIER ::= { 1.3.6.1.4.1.353.1.5.5 }

It does not name any managed objects, rather is used to locate appropriate rows in the service registery table.

このOIDは管理対象オブジェクトを指すものではなく、サービスレジストリーテーブルの適切な行の位置を特定するために使います。

4. Next Hop Client Behavior

4. ネクストホップクライアントの振る舞い

An Next Hop Client NHC) will access the service registry table via ILMI using the SNMP GetNext operator to "sweep" (SNMP parlance for a linear search) beginning with {Port = 0, ServiceID = <see Section 3.2>, Index = 0} while holding the port number and the serviceID constant. (Port number 0 is used within ILMI to indicate "this port.")

ネクストホップクライアント（NHC）は、ILMIを介してSNMPのGetNext操作を使い、ポート番号とserviceIDを固定したまま{Port = 0, ServiceID = <セクション3.2を参照>, Index = 0}から始めて「スイープ」（線形探索を指すSNMPの用語）することで、サービスレジストリーテーブルにアクセスします。（ポート番号0は、ILMIでは「このポート」を示すために使われます。）

An NHC with no local configuration, such as a diskless workstation, must use the row with the lowest index value if multiple Next Hop Server (NHS), possibly for multiple networks, are listed.

ディスクレスワークステーションのようにローカルな設定を持たないNHCは、複数のネクストホップサーバー（NHS）（複数のネットワーク用である可能性もあります）が列挙されている場合、インデックス値が最も小さい行を使わなければなりません。

NHC that have local IP configuration must use a row that has the appropriate IP address. For example, consider the case where an IP router has 3 logical interfaces defined on a single physical interface with IP addresses 1.0.0.1/8, 128.10.0.1/16 and 171.69.150.226/24. The router will sweep the service registry table looking for rows that have atmfSrvcRegParm1 values as shown below:

ローカルなIP設定を持つNHCは、適切なIPアドレスを持つ行を使わなければなりません。たとえば、IPルーターが1つの物理インターフェイス上に、IPアドレスが1.0.0.1/8、128.10.0.1/16、171.69.150.226/24である3つの論理インターフェイスを定義している場合を考えます。このルーターは、次に示すatmfSrvcRegParm1の値を持つ行を探して、サービスレジストリーテーブルをスイープします。

  Net number/mask  atmfSrvcRegParm1
  ---------------- --------------------------------------------------
  1.0.0.0/8        08 00 00 00 00 00 00  04  01 00 00 00  ff 00 00 00
  128.10.0.0/16    08 00 00 00 00 00 00  04  80 0a 00 00  ff ff 00 00
  171.69.150.0/24  08 00 00 00 00 00 00  04  ab 45 96 00  ff ff ff 00

  Net number/mask  atmfSrvcRegParm1
  ---------------- --------------------------------------------------
  1.0.0.0/8        08 00 00 00 00 00 00  04  01 00 00 00  ff 00 00 00
  128.10.0.0/16    08 00 00 00 00 00 00  04  80 0a 00 00  ff ff 00 00
  171.69.150.0/24  08 00 00 00 00 00 00  04  ab 45 96 00  ff ff ff 00

When the correct atmfSrvcRegParm1 values are located, the router may then establish an SVC to the selected NHS and perform the appropriate protocol operations.

正しいatmfSrvcRegParm1の値が見つかったら、ルーターは選択したNHSへのSVCを確立し、適切なプロトコル操作を実行できます。

Redundant NHS are supported with multiple rows in the service registry table. This list of NHS is ordered with the primary NHS having the lowest index value. The NHC must attempt to utilize the primary NHS before utilizing a secondary NHS. Administrators must ensure that the listed NHS are synchronized.

冗長なNHSは、サービスレジストリーテーブル内の複数の行によってサポートされます。このNHSのリストは、プライマリーNHSのインデックス値が最も小さくなるように順序付けられます。NHCは、セカンダリーNHSを利用する前に、プライマリーNHSの利用を試みなければなりません。管理者は、列挙されたNHSが同期されていることを保証しなければなりません。

5. NHRP Server (NHS) Behavior

5. NHRPサーバー（NHS）の振る舞い

A Next Hop Server (NHS) shall be locally configured. The NHS may retrieve the NHRP service registry data to validate the results. If an incorrect row is retrieved the error may be flagged in a locally significant way.

ネクストホップサーバー（NHS）は、ローカルに設定されるものとします。NHSは、結果を検証するためにNHRPのサービスレジストリーデータを取得してもかまいません。誤った行が取得された場合、そのエラーはローカルで意味のある方法で通知してもかまいません。

6. Relationship with PNNI Augmented Routing

6. PNNI拡張ルーティングとの関係

An augmented version PNNI ("PNNI Augmented Routing," or PAR) [3] has been developed by the ATM Forum. PAR can distribute data such as NHS addresses. Further, the ATM Forum is developing a proxy mechanism for PAR (Proxy PAR) that would allow a UNI-attached host or router to access PAR data without a full PAR implementation.

PNNIの拡張版（「PNNI Augmented Routing」、すなわちPAR）[3]が、ATMフォーラムによって開発されています。PARは、NHSのアドレスなどのデータを配布できます。さらにATMフォーラムは、UNIで接続されたホストやルーターが完全なPARの実装なしにPARのデータにアクセスできるようにする、PARのためのプロキシーの仕組み（Proxy PAR）を開発しています。

These mechanisms offer a promising way to manage the service registry tables maintained on each switch in an ATM network, yet would not require changes to the mechanism defined in this memo. Hosts and routers can continue to utilize ILMI-based or Proxy PAR-based server discovery and network administrators could manage the service registry data with local configuration or via PAR and Proxy PAR.

これらの仕組みは、ATMネットワーク内の各スイッチで維持されるサービスレジストリーテーブルを管理する有望な方法を提供しますが、このメモで定義する仕組みの変更は必要としません。ホストとルーターは引き続きILMIベースまたはProxy PARベースのサーバー発見を利用でき、ネットワーク管理者はサービスレジストリーデータを、ローカルな設定によって、またはPARとProxy PARを介して管理できます。

7. Security Considerations

7. セキュリティーに関する考慮事項

The server discovery mechanism is built on the ILMI managment framework and the security embodied in that framework. Access, to user- or network-side information is controlled by MIB design rather than protocol security mechanisms.

サーバー発見の仕組みは、ILMIの管理フレームワークと、そのフレームワークに組み込まれたセキュリティーの上に構築されています。ユーザー側またはネットワーク側の情報へのアクセスは、プロトコルのセキュリティー機構ではなく、MIBの設計によって制御されます。

The service registery MIB, the table containing information for server discovery, is defined in [2] with read-only access. This means that any user-side device may query the service registry, but may not modify the service registry via ILMI. Instead, the sevice registry table must be modified via local configuration on the ATM switch.

サーバー発見のための情報を含むテーブルであるサービスレジストリーMIBは、[2]で読み取り専用アクセスとして定義されています。これは、ユーザー側のどの機器もサービスレジストリーに問い合わせることはできますが、ILMIを介してサービスレジストリーを変更することはできないということです。代わりに、サービスレジストリーテーブルは、ATMスイッチ上のローカルな設定によって変更しなければなりません。
