RFC 129

Request for comments on socket name structure

RFC 129

ソケット名の構造に関するコメントの依頼

INTRODUCTION

はじめに

This RFC is in answer to a request (made at the February NWG Meeting at the University of Illinois) that we comment on several suggested socket name structures. We apologize for the delay in getting out these comments and we hope that you will respond more quickly with your reactions.

このRFCは、提案されたいくつかのソケット名の構造についてコメントしてほしいという（イリノイ大学で開かれた2月のNWG会議での）依頼に答えるものです。これらのコメントを出すのが遅くなったことをお詫びします。みなさんには、より早く反応を返していただけることを願っています。

Please direct your replies via the standard RFC mechanism.

返信は、標準のRFCの仕組みを通じて送ってください。

Two structures are presented in this RFC as shown below.

このRFCでは、次に示す2つの構造を取り上げます。

                        31                 1
          +-------------------------------+-+
     1.   |         Arbitrary             | | <-- gender
          +-------------------------------+-+

                        24             7   1
          +------------------------+------+-+
     2.   |        User ID         | tag  | | <-- gender
          +------------------------+------+-+

                        31                 1
          +-------------------------------+-+
     1.   |         Arbitrary             | | <-- gender
          +-------------------------------+-+

                        24             7   1
          +------------------------+------+-+
     2.   |        User ID         | tag  | | <-- gender
          +------------------------+------+-+

Three variations are given for the way in which socket names are assigned, as examples of use of the first structure.

1つ目の構造の使用例として、ソケット名の割り当て方の3つのバリエーションを示します。

  1. Users pick the arbitrary number arbitrarily and associate it with a process.
  2. A logger chooses the arbitrary number dynamically and associates it with a process via a directory.
  3. The arbitrary number is assigned outside of a logger but may be issued by a logger to the remote party.
  1. ユーザーが任意の番号を任意に選び、それをプロセスに関連付けます。
  2. ロガーが任意の番号を動的に選び、ディレクトリーを介してそれをプロセスに関連付けます。
  3. 任意の番号はロガーの外部で割り当てられますが、ロガーがそれをリモートの相手に発行することもできます。

The second format shown above associates sockets specifically with users as opposed to processes.

上に示した2つ目のフォーマットは、ソケットをプロセスではなく、特にユーザーに関連付けます。

The following discussion covers three different schemes of socket identifier assignment using a simple example. User A at Host A has agreed (by letter, telephone, etc.) with User B at Host B for their respective processes to establish a connection through the Network at a particular time. User B is to be waiting for the connection attempt initiated by User A. The issues to be faced are those of addressing (how is User A to know to which socket to connect?), and of security (how are both users to be confident that they are talking each other, and not some interloper?).

以下の議論では、簡単な例を使って、ソケット識別子の割り当ての3つの異なる方式を取り上げます。ホストAのユーザーAは、ホストBのユーザーBと、それぞれのプロセスが特定の時刻にネットワークを通じてコネクションを確立することについて（手紙や電話などで）合意しています。ユーザーBは、ユーザーAが開始するコネクションの試みを待つことになっています。直面する課題は、アドレス指定（ユーザーAは、どのソケットに接続すればよいかをどうやって知るのか？）と、セキュリティー（両方のユーザーは、どうすれば何者かの割り込みではなく互いに話していると確信できるのか？）です。

A fourth scheme follows which addresses another concept of Network use--that connections are made between processes and that processes not users should be identified via Socket names.

続いて、ネットワークの使用についての別の考え方、つまり、コネクションはプロセス間で確立されるものであり、ソケット名で識別すべきなのはユーザーではなくプロセスである、という考え方を扱う4つ目の方式を示します。

FREELY SELECTED RANDOM SOCKET IDENTIFIERS (Scheme 1)

自由に選択するランダムなソケット識別子（方式1）

Under this scheme a user is able to use any 32-bit socket identifier he chooses. Two restrictions apply: the least significant bit denotes the socket's gender (0-read, 1-write), and no more than one socket bearing a given identifier can be active at a host at a time.

この方式では、ユーザーは自分が選んだ任意の32ビットのソケット識別子を使用できます。制約が2つあります。最下位ビットはソケットの性別（gender）を表すこと（0は読み込み、1は書き込み）と、あるホストで同時に有効にできる、ある識別子を持つソケットは1つだけであることです。

The two users select suitably random identifiers ("a" and "b"). User A will attempt to activate his socket with identifier "a" an connect it to socket "b" at Host B. There is the possibility that somebody other than User B has activated socket "b" at Host B so that User A will address the wrong party. However, the possibility that some other user has accidentally picked this particular identifier is reasonably small, since there are about a billion different identifiers. When the connection request from A gets to User B, he examines the identifier of the calling socket. If for some reasom it is not "a" or not from Host A, he rejects the request, because it is likely to be from some outside party. If the calling socket is named, "a" and from Host A, User B can be reasonably sure that it is from User A. It is very unlikely that some other party will accidentally address socket "b" from a socket named "a".

2人のユーザーは、適度にランダムな識別子（"a"と"b"）を選びます。ユーザーAは、識別子"a"を持つ自分のソケットを有効にし、それをホストBのソケット"b"に接続しようとします。ユーザーB以外の誰かがホストBでソケット"b"を有効にしていて、ユーザーAが誤った相手にアドレスを指定してしまう可能性があります。しかし、識別子はおよそ10億種類あるので、他のユーザーが偶然この特定の識別子を選んでいる可能性はかなり小さいです。Aからのコネクション要求がユーザーBに届くと、ユーザーBは呼び出し元のソケットの識別子を調べます。何らかの理由でそれが"a"でないか、ホストAからのものでない場合、ユーザーBはその要求を拒否します。外部の相手からのものである可能性が高いからです。呼び出し元のソケットの名前が"a"で、ホストAからのものであれば、ユーザーBはそれがユーザーAからのものであるとかなり確信できます。他の相手が偶然、"a"という名前のソケットからソケット"b"にアドレスを指定する可能性は非常に低いです。

The advantages of this scheme are: simplicity and reasonable security in a non-malicious environment. The disadvantages are that there are possibilities from annoyingly unavoidable conflicts with other users and that each pair of users must conduct a prior confidential private communication (as opposed to a broadcast announcement in more secure schemes).

この方式の利点は、単純であることと、悪意のない環境では妥当なセキュリティーがあることです。欠点は、他のユーザーとの、困ったことに避けられない衝突が起こる可能性があることと、（より安全な方式でのブロードキャストによる告知とは対照的に）ユーザーの各ペアが事前に秘密の私的な連絡を取らなければならないことです。

HOST-SELECTED IDENTIFIERS PLUS DIRECTORY (Scheme 2)

ホストが選択する識別子とディレクトリー（方式2）

This system uses the same socket identifier structure as presented above, except that the Host picks the identifier at the time the socket is assigned, and the user has no no prior knowledge or control of the assignment. By itself, this system would be totally unusable, because there would be no way for User A to address User B. However, it allows certain service functions (such as the Network logger) to have specifically assigned sockets.

この方式は、上で示したのと同じソケット識別子の構造を使用しますが、ソケットが割り当てられる時点でホストが識別子を選び、ユーザーはその割り当てを事前に知ることも制御することもできない点が異なります。この方式は、それ単独では、ユーザーAがユーザーBにアドレスを指定する方法がないので、まったく使い物になりません。しかし、特定のサービス機能（ネットワークのロガーなど）に、特別に割り当てられたソケットを持たせることができます。

One of these is a Network Directory service. This serves to relate a socket identifier at a particular host to the name of the user operating it. This might either be a single distributed service, or there might be a separate service at each host.

そのようなサービス機能の1つが、ネットワークディレクトリーサービスです。このサービスは、特定のホストのソケット識別子を、それを操作しているユーザーの名前に関連付ける役割を果たします。これは、単一の分散サービスの場合もあれば、各ホストに個別のサービスがある場合もあります。

Under this scheme, each user, A and B, first activates his socket (or somehow gets his host to assign and tell him of a socket identifier). Then he gets the Directory module at his host to associate his name with the identifier of the socket just activated. Following this, User A in some manner gets the Directory Service at Host B to tell him the socket identifier assigned to User B. Then User A dispatches a connection request for this socket.

この方式では、ユーザーAとユーザーBのそれぞれが、まず自分のソケットを有効にします（または、何らかの方法で自分のホストにソケット識別子を割り当てさせて、それを教えてもらいます）。次に、自分のホストのディレクトリーモジュールに、自分の名前と、有効にしたばかりのソケットの識別子とを関連付けさせます。その後、ユーザーAは何らかの方法でホストBのディレクトリーサービスに、ユーザーBに割り当てられたソケット識別子を教えてもらいます。そして、ユーザーAはこのソケットに対するコネクション要求を送ります。

When User B gets the request, he similarly calls on the Directory service at Host A to find out the name of the user who is operating the socket User B was called by. If the name is that of User A, User B can safely accept the request. Otherwise, he rejects.

ユーザーBは、要求を受け取ると、同様にホストAのディレクトリーサービスを呼び出して、ユーザーBを呼び出したソケットを操作しているユーザーの名前を調べます。その名前がユーザーAのものであれば、ユーザーBは安心して要求を受け入れられます。そうでなければ、拒否します。

This scheme is rather cumbersome, but some directory services must exist for Host-selected socket identifiers to work. On advantage of the Directory Service is thst it allows symbolic addressing. A sizeable disadvantage in view of its complexity is that it does not provide absolute security. (For exemple, after User A gets the identifier of the socket he is to address, User B could deactivate it, and somebody else could come along and get the same-named socket.)

この方式はかなり煩雑ですが、ホストが選択するソケット識別子が機能するためには、何らかのディレクトリーサービスが存在しなければなりません。ディレクトリーサービスの利点の1つは、シンボリックなアドレス指定ができることです。その複雑さを考えると大きな欠点は、絶対的なセキュリティーを提供しないことです。（たとえば、ユーザーAがアドレスを指定すべきソケットの識別子を入手した後に、ユーザーBがそのソケットを無効にし、別の誰かがやって来て同じ名前のソケットを入手する可能性があります。）

ADMINISTRATIVELY ASSIGNED USER IDENTIFIERS (Scheme 3)

管理上割り当てられるユーザー識別子（方式3）

This is the system that is put forth on page 5 of Protocol Document 1(8/3/70). Under it a user is permanently assigned a user identifier by his home host. There is a user identifier subfield within the socket identifier, and a user is permitted by an NCP to operate only those sockets bearing his uder identifier. This gives the user a selection of 256 sockets operable by him.

これは、Protocol Document 1（8/3/70）の5ページで提案されている方式です。この方式では、ユーザーは、自分のホームホストからユーザー識別子を永続的に割り当てられます。ソケット識別子の中にユーザー識別子のサブフィールドがあり、ユーザーは、NCPによって、自分のユーザー識別子を持つソケットだけを操作することを許可されます。これにより、ユーザーは自分が操作できる256個のソケットから選択できます。

In arranging for the connection the two Users A and B tell each other their user identifiers (alternatively a user ID could be read from a directory), and User B specifies which of his sockets ("b") that he will "listen" on. At connection time, User A selects one of his sockets and requests connection for it to socket "b" specified by User B. By protocol only User B can operate socket "b", so User A can be certain of reaching the right party.

コネクションを手配する際、2人のユーザーAとBは、互いに自分のユーザー識別子を伝え合い（あるいは、ユーザーIDをディレクトリーから読み取ることもできます）、ユーザーBは自分のソケットのうちどれ（"b"）で「待ち受ける（listen）」かを指定します。接続時に、ユーザーAは自分のソケットの1つを選び、それをユーザーBが指定したソケット"b"に接続するよう要求します。プロトコルにより、ソケット"b"を操作できるのはユーザーBだけなので、ユーザーAは正しい相手に到達できると確信できます。

When User B receives the connection request, he examines the user identifier subfield of the calling socket identifier. If it is the user identifier of User A, User B accepts the connection request, confident that it is actually User A at the other end. Otherwise B rejects the request.

ユーザーBは、コネクション要求を受け取ると、呼び出し元のソケット識別子のユーザー識別子サブフィールドを調べます。それがユーザーAのユーザー識別子であれば、ユーザーBは、相手側にいるのが実際にユーザーAであると確信して、コネクション要求を受け入れます。そうでなければ、Bは要求を拒否します。

The advantages of this scheme are that if both hosts involved in a connection enforce the user ID assignment, the misconnection aspect of security is solved and there can be no socket naming conflict between users. Also, arrangements can be made openly and publicly between many potential communicators. A disadvantage to this scheme is that some systems may be incapable of insuring user ID integrity.

この方式の利点は、コネクションに関わる両方のホストがユーザーIDの割り当てを強制すれば、セキュリティーのうち誤接続の側面が解決され、ユーザー間でソケット名の衝突が起こりえないことです。また、多数の潜在的な通信相手の間で、手配を公然と公開で行うことができます。この方式の欠点は、ユーザーIDの完全性を保証できないシステムがあるかもしれないことです。

A VIEW OF SOCKET NAME MEANING (Scheme 4)

ソケット名の意味についての1つの見方（方式4）

Another view of Network use is that programs will connect to programs, via NCPs. Some of these programs may be multi-access subsystems that are really agents for local consoles (and TELNETs). Consoles will generally communicate through some such software agent rather than directly to an NCP.

ネットワークの使用についてのもう1つの見方は、プログラムがNCPを介してプログラムに接続する、というものです。これらのプログラムの中には、実際にはローカルのコンソール（とTELNET）のエージェントであるマルチアクセスのサブシステムもあるかもしれません。コンソールは一般に、NCPと直接ではなく、そのようなソフトウェアエージェントを通じて通信します。

Programs, then, must have a fixed, unique identifier, known to its remote users and perhaps to its local logger. The identifier is constant; it does not change from day to day. If such a program is to allow multiple concurrent connections (for many or a single user) then it must have a range of variable identifiers as well. It makes sense to group these sockets in a contiguous range. The variable identifiers are transient and are dynamically associated with Network logical connections.

そうすると、プログラムは、そのリモートのユーザーと、おそらくはそのローカルのロガーに知られている、固定された一意の識別子を持たなければなりません。この識別子は一定で、日によって変わることはありません。そのようなプログラムが（多数のユーザー、または1人のユーザーのために）複数の同時コネクションを許可するのであれば、可変の識別子の範囲も持たなければなりません。これらのソケットを連続した範囲にまとめるのは理にかなっています。可変の識別子は一時的なもので、ネットワークの論理コネクションに動的に関連付けられます。

      +---------------------   ---------------------+
      |                                           |
      | Fixed, unique       /  /  Variable          |
      | Identifier         /  /  Identifier         |
      |                                           |
      +---------------------   ---------------------+

      _________  _________/   _________  _________/
                /                       /
       Identifies the           Identifies a particular
       program uniquely         connection of the program

      +---------------------   ---------------------+
      |                                           |
      | Fixed, unique       /  /  Variable          |
      | Identifier         /  /  Identifier         |
      |                                           |
      +---------------------   ---------------------+

      _________  _________/   _________  _________/
                /                       /
       Identifies the           Identifies a particular
       program uniquely         connection of the program

The above premise is that the program (or agent) is doing the communicating with an NCP and thus needs to be identified for message traffic routing from an NCP. In the past it has been said that users can be mobile, i.e., log on from different sites, and thus it is the user that needs identification. In many typical on-line systems the user first requests a service and then identifies himself to the service for purposes of accounting, etc. User IDs can be transmitted after requesting a service and can thus be elevated above the meaning of socket names.

上記の前提は、NCPと通信しているのはプログラム（またはエージェント）であり、そのためNCPからのメッセージトラフィックをルーティングするために、プログラムを識別する必要がある、というものです。これまでは、ユーザーは移動できる（つまり、異なるサイトからログオンできる）ので、識別が必要なのはユーザーである、と言われてきました。多くの典型的なオンラインシステムでは、ユーザーはまずサービスを要求し、その後、課金などの目的でサービスに対して自分の身元を明らかにします。ユーザーIDはサービスを要求した後に送信できるので、ソケット名の意味からは切り離して上位で扱うことができます。

A program might typically associate the terminals, for which it is an agent, with the variable part of the identifier, i.e., the particular connection(s). For example, the Network Services Program (NSP) at Rand now uses the following format for socket names. The first 24 bits are administratively assigned and would be known to a logger. The multiplex code is normally chosen randomly. Predefined, fixed multiplex codes are possible also.

プログラムは通常、自分がエージェントとなっている端末を、識別子の可変部分、つまり特定のコネクションに関連付けるでしょう。たとえば、RandのNetwork Services Program（NSP）は現在、ソケット名に次のフォーマットを使用しています。最初の24ビットは管理上割り当てられ、ロガーに知られています。多重化コード（multiplex code）は通常ランダムに選ばれます。事前に定義された固定の多重化コードも使用できます。

                24                   7     1
       +------------------------+---------+-+
       | Program Number         |Multiplex| | <-- Gender
       |                        |  Code   | |
       +------------------------+---------+-+

                24                   7     1
       +------------------------+---------+-+
       | Program Number         |Multiplex| | <-- Gender
       |                        |  Code   | |
       +------------------------+---------+-+

The Socket name structure #1 (page 1) thus accomodates the above example as well as other exploratory socket name structures and various "standards" superimposed on the arbitrary field.

したがって、ソケット名の構造#1（1ページ）は、上の例だけでなく、他の試験的なソケット名の構造や、任意のフィールドの上に重ねられたさまざまな「標準」にも対応できます。
