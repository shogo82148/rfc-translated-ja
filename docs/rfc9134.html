RFC 9134

RTP Payload Format for ISO/IEC 21122 (JPEG XS)

RFC 9134

ISO/IEC 21122（JPEG XS）のためのRTPペイロード形式

Abstract

概要

This document specifies a Real-Time Transport Protocol (RTP) payload format to be used for transporting video encoded with JPEG XS (ISO/IEC 21122). JPEG XS is a low-latency, lightweight image coding system. Compared to an uncompressed video use case, it allows higher resolutions and video frame rates while offering visually lossless quality, reduced power consumption, and encoding-decoding latency confined to a fraction of a video frame.

この文書は、JPEG XS（ISO/IEC 21122）でエンコードされたビデオを転送するために使用するReal-Time Transport Protocol（RTP）ペイロード形式を規定します。 JPEG XSは、低遅延で軽量な画像符号化システムです。 非圧縮ビデオのユースケースと比べて、より高い解像度とビデオフレームレートを可能にしつつ、視覚的にロスレスな品質、消費電力の削減、そしてビデオフレームの何分の1かに収まるエンコード・デコードの遅延を提供します。

1. Introduction

1. はじめに

This document specifies a payload format for packetization of video signals encoded with JPEG XS [ISO21122-1] into the Real-time Transport Protocol (RTP) [RFC3550].

この文書は、JPEG XS[ISO21122-1]でエンコードされたビデオ信号をReal-time Transport Protocol（RTP）[RFC3550]にパケット化するためのペイロード形式を規定します。

The JPEG XS coding system offers compression and recompression of image sequences with very moderate computational resources while remaining robust under multiple compression and decompression cycles as well as mixing of content sources, e.g., embedding of subtitles, overlays, or logos. Typical target compression ratios ensuring visually lossless quality are in the range of 2:1 to 10:1 depending on the nature of the source material. The latency that is introduced by the encoding-decoding process can be confined to a fraction of a video frame, typically between a small number of lines down to below a single line.

JPEG XS符号化システムは、ごく控えめな計算リソースで画像シーケンスの圧縮と再圧縮を提供し、しかも複数回の圧縮・伸張サイクルや、コンテンツソースの混合（たとえば字幕、オーバーレイ、ロゴの埋め込み）に対しても堅牢性を保ちます。 視覚的にロスレスな品質を保証する典型的な目標圧縮率は、ソース素材の性質に応じて2:1から10:1の範囲です。 エンコード・デコード処理によって生じる遅延は、ビデオフレームの何分の1かに収めることができ、典型的には少数のライン分から1ライン未満までの間です。

2. 表記規則、定義、略語

Application Data Unit (ADU):
The unit of source data provided as payload to the transport layer. In this RTP payload definition, it corresponds to a single JPEG XS video frame.
Color Specification (CS) box:
An ISO color specification box defined in [ISO21122-3] (JPEG XS Part 3) that includes color-related metadata required to correctly display JPEG XS video frames, such as color primaries, transfer characteristics, and matrix coefficients.
End of Codestream (EOC) marker:
A marker that consists of the two bytes 0xff11 indicating the end of a JPEG XS codestream.
JPEG XS codestream:
A sequence of bytes representing a compressed image formatted according to [ISO21122-1] (JPEG XS Part 1).
JPEG XS codestream header:
A sequence of bytes, starting with an SOC marker, at the beginning of each JPEG XS codestream encoded in multiple markers and marker segments that does not carry entropy coded data, but metadata such as the video frame dimension and component precision.
JPEG XS frame:
In the case of progressive video, a single JPEG XS picture segment. In the case of interlaced video, the concatenation of two JPEG XS picture segments.
JPEG XS header segment:
The concatenation of a video support box [ISO21122-3], a color specification box [ISO21122-3], and a JPEG XS codestream header.
JPEG XS picture segment:
The concatenation of a video support box [ISO21122-3], a color specification box [ISO21122-3], and a JPEG XS codestream.
JPEG XS stream:
A sequence of JPEG XS frames.
Marker:
A two-byte functional sequence that is part of a JPEG XS codestream starting with a 0xff byte and a subsequent byte defining its function.
Marker segment:
A marker along with a 16-bit marker size and payload data following the size.
Packetization unit:
A portion of an ADU whose boundaries coincide with boundaries of RTP packet payloads (excluding payload header), i.e., the first (or respectively, last) byte of a packetization unit is the first (or respectively, last) byte of an RTP packet payload (excluding its payload header).
SLH (SLice Header) marker:
A marker that represents a slice header, as defined in [ISO21122-1].
Slice:
The smallest independently decodable unit of a JPEG XS codestream, bearing in mind that it decodes to wavelet coefficients, which still require inverse wavelet filtering to give an image.
Start of a Codestream (SOC) marker:
A marker that consists of the two bytes 0xff10 indicating the start of a JPEG XS codestream. The SOC marker is considered an integral part of the JPEG XS codestream header.
Video Support (VS) box:
An ISO video support box, as defined in [ISO21122-3], that includes metadata required to play back a JPEG XS stream; such metadata could include its maximum bit rate, its subsampling structure, its buffer model, and its frame rate.
アプリケーションデータユニット（ADU）：
トランスポート層にペイロードとして提供されるソースデータの単位です。 このRTPペイロードの定義では、1つのJPEG XSビデオフレームに対応します。
カラー仕様（CS）ボックス：
[ISO21122-3]（JPEG XS Part 3）で定義されているISOのカラー仕様ボックスで、色の原色、伝達特性、マトリックス係数など、JPEG XSビデオフレームを正しく表示するために必要な色関連のメタデータを含みます。
コードストリーム終端（EOC）マーカー：
JPEG XSコードストリームの終わりを示す、2バイト0xff11からなるマーカーです。
JPEG XSコードストリーム：
[ISO21122-1]（JPEG XS Part 1）に従って形式化された、圧縮画像を表すバイト列です。
JPEG XSコードストリームヘッダー：
各JPEG XSコードストリームの先頭にある、SOCマーカーで始まるバイト列で、複数のマーカーとマーカーセグメントでエンコードされます。 エントロピー符号化されたデータではなく、ビデオフレームの寸法やコンポーネントの精度などのメタデータを運びます。
JPEG XSフレーム：
プログレッシブビデオの場合は、1つのJPEG XSピクチャーセグメントです。 インターレースビデオの場合は、2つのJPEG XSピクチャーセグメントを連結したものです。
JPEG XSヘッダーセグメント：
ビデオサポートボックス[ISO21122-3]、カラー仕様ボックス[ISO21122-3]、およびJPEG XSコードストリームヘッダーを連結したものです。
JPEG XSピクチャーセグメント：
ビデオサポートボックス[ISO21122-3]、カラー仕様ボックス[ISO21122-3]、およびJPEG XSコードストリームを連結したものです。
JPEG XSストリーム：
JPEG XSフレームの並びです。
マーカー：
JPEG XSコードストリームの一部である2バイトの機能シーケンスで、0xffバイトと、その機能を定義する後続のバイトで始まります。
マーカーセグメント：
マーカーに、16ビットのマーカーサイズと、そのサイズに続くペイロードデータを加えたものです。
パケット化ユニット：
ADUの一部分で、その境界が（ペイロードヘッダーを除く）RTPパケットペイロードの境界と一致するものです。 つまり、パケット化ユニットの最初（または最後）のバイトは、RTPパケットペイロード（ペイロードヘッダーを除く）の最初（または最後）のバイトです。
SLH（SLice Header）マーカー：
[ISO21122-1]で定義されている、スライスヘッダーを表すマーカーです。
スライス：
JPEG XSコードストリームの、独立してデコード可能な最小の単位です。 ただし、デコード結果はウェーブレット係数であり、画像を得るにはさらに逆ウェーブレットフィルタリングが必要であることに留意してください。
コードストリーム開始（SOC）マーカー：
JPEG XSコードストリームの開始を示す、2バイト0xff10からなるマーカーです。 SOCマーカーは、JPEG XSコードストリームヘッダーの不可欠な一部とみなされます。
ビデオサポート（VS）ボックス：
[ISO21122-3]で定義されているISOのビデオサポートボックスで、JPEG XSストリームを再生するために必要なメタデータを含みます。 このようなメタデータには、最大ビットレート、サブサンプリング構造、バッファーモデル、フレームレートなどが含まれます。

3. Media Format Description

3. メディア形式の説明

This section explains the terminology and concepts used in this memo specific to JPEG XS as specified in [ISO21122-1], [ISO21122-2], and [ISO21122-3].

このセクションでは、[ISO21122-1]、[ISO21122-2]、[ISO21122-3]で規定されているJPEG XSに固有の、このメモで使用する用語と概念を説明します。

3.1. Image Data Structures

3.1. 画像データの構造

JPEG XS is a low-latency, lightweight image coding system for coding continuous-tone grayscale or continuous-tone color digital images.

JPEG XSは、連続階調のグレースケールまたは連続階調のカラーのデジタル画像を符号化するための、低遅延で軽量な画像符号化システムです。

This coding system provides an efficient representation of image signals through the mathematical tool of wavelet analysis. The wavelet filter process separates each component into multiple bands, where each band consists of multiple coefficients describing the image signal of a given component within a frequency domain specific to the wavelet filter type, i.e., the particular filter corresponding to the band.

この符号化システムは、ウェーブレット解析という数学的手法によって画像信号の効率的な表現を提供します。 ウェーブレットフィルター処理は、各コンポーネントを複数のバンドに分離します。 各バンドは、ウェーブレットフィルターの種類（つまり、そのバンドに対応する特定のフィルター）に固有の周波数領域において、特定のコンポーネントの画像信号を記述する複数の係数で構成されます。

Wavelet coefficients are grouped into precincts, where each precinct includes all coefficients over all bands that contribute to a spatial region of the image.

ウェーブレット係数はプリシンクト（precinct）にグループ化されます。 各プリシンクトには、画像の空間領域に寄与する、すべてのバンドにわたるすべての係数が含まれます。

One or multiple precincts are furthermore combined into slices consisting of an integer number of precincts. Precincts do not cross slice boundaries, and wavelet coefficients in precincts that are part of different slices can be decoded independently of each other. However, note that the wavelet transformation runs across slice boundaries. A slice always extends over the full width of the image but may only cover parts of its height.

さらに、1つまたは複数のプリシンクトは、整数個のプリシンクトからなるスライスにまとめられます。 プリシンクトはスライスの境界をまたがず、異なるスライスに属するプリシンクト内のウェーブレット係数は、互いに独立してデコードできます。 ただし、ウェーブレット変換はスライスの境界をまたいで実行されることに注意してください。 スライスは常に画像の幅全体に広がりますが、高さについては一部しかカバーしない場合があります。

3.2. Codestream

3.2. コードストリーム

A JPEG XS codestream is formed by (in the given order):

JPEG XSコードストリームは、次のもので（この順序で）構成されます。

  • a JPEG XS codestream header, which starts with a Start of Codestream (SOC) marker,
  • one or more slices,
  • an EOC marker to signal the end of the codestream.
  • コードストリーム開始（SOC）マーカーで始まるJPEG XSコードストリームヘッダー
  • 1つ以上のスライス
  • コードストリームの終わりを示すEOCマーカー

The JPEG XS codestream format, including the definition of all markers, is further defined in [ISO21122-1]. It represents sample values of a single image, without any interpretation relative to a color space.

すべてのマーカーの定義を含むJPEG XSコードストリームの形式は、[ISO21122-1]でさらに詳しく定義されています。 コードストリームは単一の画像のサンプル値を表し、色空間に関する解釈は一切含みません。

3.3. Video Support Box and Color Specification Box

3.3. ビデオサポートボックスとカラー仕様ボックス

While the information defined in the codestream is sufficient to reconstruct the sample values of one image, the interpretation of the samples remains undefined by the codestream itself. This interpretation is given by the video support box and the color specification box, which contain significant information to correctly play the JPEG XS stream. The layout and syntax of these boxes, together with their content, are defined in [ISO21122-3].

コードストリームで定義される情報は1つの画像のサンプル値を再構成するのに十分ですが、サンプルの解釈はコードストリーム自体では未定義のままです。 この解釈は、ビデオサポートボックスとカラー仕様ボックスによって与えられます。 これらのボックスには、JPEG XSストリームを正しく再生するための重要な情報が含まれています。 これらのボックスのレイアウトと構文は、その内容とともに[ISO21122-3]で定義されています。

The video support box provides information on the maximum bit rate, the frame rate, the interlaced mode (progressive or interlaced), the subsampling image format, the informative timecode of the current JPEG XS frame, the profile, the level/sublevel used, and optionally the buffer model and the mastering display metadata.

ビデオサポートボックスは、最大ビットレート、フレームレート、インターレースモード（プログレッシブまたはインターレース）、サブサンプリング画像形式、現在のJPEG XSフレームの参考情報としてのタイムコード、プロファイル、使用されるレベル/サブレベル、および任意でバッファーモデルとマスタリングディスプレイメタデータに関する情報を提供します。

Note that the profile and level/sublevel, specified respectively by the Ppih and Plev fields [ISO21122-2], specify limits on the capabilities needed to decode the codestream and handle the output. Profiles represent a limit on the required algorithmic features and parameter ranges used in the codestream. The combination of level and sublevel defines a lower bound on the required throughput for a decoder in the image (or decoded) domain and the codestream (or coded) domain, respectively. The actual defined profiles and levels/sublevels, along with the associated values for the Ppih and Plev fields, are defined in [ISO21122-2].

なお、それぞれPpihフィールドとPlevフィールド[ISO21122-2]で指定されるプロファイルとレベル/サブレベルは、コードストリームをデコードして出力を扱うために必要な能力の上限を規定することに注意してください。 プロファイルは、コードストリームで使用される、必要なアルゴリズム上の機能とパラメーター範囲の上限を表します。 レベルとサブレベルの組み合わせは、それぞれ画像（またはデコード済み）領域とコードストリーム（または符号化済み）領域における、デコーダーに必要なスループットの下限を定義します。 実際に定義されているプロファイルとレベル/サブレベルは、PpihフィールドとPlevフィールドの対応する値とともに、[ISO21122-2]で定義されています。

The color specification box indicates the color primaries, transfer characteristics, matrix coefficients, and video full range flag needed to specify the color space of the video stream.

カラー仕様ボックスは、ビデオストリームの色空間を指定するために必要な、色の原色、伝達特性、マトリックス係数、およびビデオフルレンジフラグを示します。

3.4. JPEG XS Frame

3.4. JPEG XSフレーム

The concatenation of a video support box, a color specification box, and a JPEG XS codestream forms a JPEG XS picture segment.

ビデオサポートボックス、カラー仕様ボックス、およびJPEG XSコードストリームを連結したものが、JPEG XSピクチャーセグメントを形成します。

In the case of a progressive video stream, each JPEG XS frame consists of one single JPEG XS picture segment.

プログレッシブのビデオストリームの場合、各JPEG XSフレームは1つのJPEG XSピクチャーセグメントで構成されます。

In the case of an interlaced video stream, each JPEG XS frame is made of two concatenated JPEG XS picture segments. The codestream of each picture segment corresponds exclusively to one of the two fields of the interlaced frame. Both picture segments SHALL contain identical boxes (i.e., the byte sequence that contains the concatenation of the video support box and the color specification box is exactly the same in both picture segments of the frame).

インターレースのビデオストリームの場合、各JPEG XSフレームは、連結された2つのJPEG XSピクチャーセグメントで構成されます。 各ピクチャーセグメントのコードストリームは、インターレースフレームの2つのフィールドのうち一方だけに対応します。 両方のピクチャーセグメントは、同一のボックスを含むものとすることになります（SHALL）（つまり、ビデオサポートボックスとカラー仕様ボックスを連結したバイト列は、フレームの両方のピクチャーセグメントでまったく同じです）。

Note that the interlaced mode, as signaled by the frat field [ISO21122-3] in the video support box, indicates either progressive interlaced top-field-first or interlaced bottom-field-first mode. Thus, in the case of interlaced content, its value SHALL also be identical in both picture segments.

ビデオサポートボックスのfratフィールド[ISO21122-3]で通知されるインターレースモードは、プログレッシブ、インターレースのトップフィールドファースト、インターレースのボトムフィールドファーストのいずれかのモードを示すことに注意してください。 したがって、インターレースのコンテンツの場合、その値も両方のピクチャーセグメントで同一であるものとすることになります（SHALL）。

4. RTP Payload Format

4. RTPペイロード形式

This section specifies the payload format for JPEG XS streams over the Real-time Transport Protocol (RTP) [RFC3550].

このセクションでは、Real-time Transport Protocol（RTP）[RFC3550]上でJPEG XSストリームを運ぶためのペイロード形式を規定します。

In order to be transported over RTP, each JPEG XS stream is transported in a distinct RTP stream, identified by a distinct synchronization source (SSRC) [RFC3550].

RTPで転送するために、各JPEG XSストリームは、個別の同期送信元（SSRC）[RFC3550]で識別される個別のRTPストリームで転送されます。

A JPEG XS stream is divided into Application Data Units (ADUs), each ADU corresponding to a single JPEG XS frame.

JPEG XSストリームはアプリケーションデータユニット（ADU）に分割され、各ADUは1つのJPEG XSフレームに対応します。

4.1. RTP Packetization

4.1. RTPパケット化

An ADU is made of several packetization units. If a packetization unit is bigger than the maximum size of an RTP packet payload, the unit is split into multiple RTP packet payloads, as illustrated in Figure 1. As seen there, each packet SHALL contain (part of) one, and only one, packetization unit. A packetization unit may extend over multiple packets. The payload of every packet SHALL have the same size (based, e.g., on the Maximum Transfer Unit of the network) with the possible exception of the last packet of a packetization unit. The boundaries of a packetization unit SHALL coincide with the boundaries of the payload of a packet (excluding the payload header), i.e., the first (or, respectively, last) byte of the packetization unit SHALL be the first (or, respectively, last) byte of the payload (excluding its header).

ADUは、いくつかのパケット化ユニットで構成されます。 パケット化ユニットがRTPパケットペイロードの最大サイズよりも大きい場合、Figure 1に示すように、そのユニットは複数のRTPパケットペイロードに分割されます。 図に示すように、各パケットは、ただ1つのパケット化ユニット（の一部）を含むものとすることになります（SHALL）。 パケット化ユニットは、複数のパケットにまたがってもかまいません。 パケット化ユニットの最後のパケットを除き、すべてのパケットのペイロードは（たとえばネットワークの最大転送単位（Maximum Transfer Unit）に基づく）同じサイズであるものとすることになります（SHALL）。 パケット化ユニットの境界は、（ペイロードヘッダーを除く）パケットのペイロードの境界と一致するものとすることになります（SHALL）。 つまり、パケット化ユニットの最初（または最後）のバイトは、（ヘッダーを除く）ペイロードの最初（または最後）のバイトであるものとすることになります（SHALL）。

There are two different packetization modes defined for this RTP payload format.

このRTPペイロード形式には、2つの異なるパケット化モードが定義されています。

Codestream packetization mode:
In this mode, the packetization unit SHALL be the entire JPEG XS picture segment (i.e., codestream preceded by boxes). This means that a progressive frame will have a single packetization unit, while an interlaced frame will have two. The progressive case is illustrated in Figure 2.
Slice packetization mode:
In this mode, the packetization unit SHALL be the slice, i.e., there SHALL be data from no more than one slice per RTP packet. The first packetization unit SHALL be made of the JPEG XS header segment (i.e., the concatenation of the VS box, the CS box, and the JPEG XS codestream header). This first unit is then followed by successive units, each containing one and only one slice. The packetization unit containing the last slice of a JPEG XS codestream SHALL also contain the EOC marker immediately following this last slice. This is illustrated in Figure 3. In the case of an interlaced frame, the JPEG XS header segment of the second field SHALL be in its own packetization unit.
コードストリームパケット化モード：
このモードでは、パケット化ユニットはJPEG XSピクチャーセグメント全体（つまり、ボックスが前に付いたコードストリーム）であるものとすることになります（SHALL）。 これは、プログレッシブフレームではパケット化ユニットが1つになり、インターレースフレームでは2つになることを意味します。 プログレッシブの場合をFigure 2に示します。
スライスパケット化モード：
このモードでは、パケット化ユニットはスライスであるものとすることになります（SHALL）。 つまり、1つのRTPパケットに含まれるデータは、最大でも1つのスライスからのものであるものとすることになります（SHALL）。 最初のパケット化ユニットは、JPEG XSヘッダーセグメント（つまり、VSボックス、CSボックス、JPEG XSコードストリームヘッダーを連結したもの）で構成されるものとすることになります（SHALL）。 この最初のユニットの後に、それぞれただ1つのスライスを含む後続のユニットが続きます。 JPEG XSコードストリームの最後のスライスを含むパケット化ユニットは、この最後のスライスの直後に続くEOCマーカーも含むものとすることになります（SHALL）。 これをFigure 3に示します。 インターレースフレームの場合、2番目のフィールドのJPEG XSヘッダーセグメントは、それ自体で独立したパケット化ユニットに入るものとすることになります（SHALL）。

In a constant bitrate (CBR) scenario of JPEG XS, the codestream packetization mode guarantees that a JPEG XS RTP stream will produce both a constant number of bytes per video frame and a constant number of RTP packets per video frame. However, to provide similar guarantees with JPEG XS in a variable bitrate (VBR) mode or when using the slice packetization mode (for either CBR or VBR), additional mechanisms are needed. This can involve a constraint at the rate allocation stage in the JPEG XS encoder to impose a CBR at the slice level, the usage of padding data, or the insertion of empty RTP packets (i.e., an RTP packet whose payload data is empty). But, management of the amount of produced packets per video frame is application dependent and not a strict requirement of this RTP payload specification.

JPEG XSの固定ビットレート（CBR）のシナリオでは、コードストリームパケット化モードにより、JPEG XSのRTPストリームがビデオフレームあたり一定のバイト数と、ビデオフレームあたり一定数のRTPパケットの両方を生成することが保証されます。 しかし、可変ビットレート（VBR）モードのJPEG XSや、（CBRとVBRのいずれでも）スライスパケット化モードを使用する場合に同様の保証を提供するには、追加のメカニズムが必要です。 これには、スライスレベルでCBRを課すためのJPEG XSエンコーダーのレート割り当て段階での制約、パディングデータの使用、または空のRTPパケット（つまり、ペイロードデータが空のRTPパケット）の挿入が含まれる場合があります。 ただし、ビデオフレームあたりに生成されるパケット数の管理はアプリケーションに依存するものであり、このRTPペイロード仕様の厳密な要件ではありません。

4.2. RTP Header Usage

4.2. RTPヘッダーの使用方法

The format of the RTP header is specified in [RFC3550] and reprinted in Figure 4 for convenience. This RTP payload format uses the fields of the header in a manner consistent with that specification.

RTPヘッダーの形式は[RFC3550]で規定されており、便宜上Figure 4に再掲します。 このRTPペイロード形式は、その仕様と矛盾しない方法でヘッダーのフィールドを使用します。

The RTP payload (and the settings for some RTP header bits) for packetization units are specified in Section 4.3.

パケット化ユニットのためのRTPペイロード（および一部のRTPヘッダービットの設定）は、Section 4.3で規定します。

The version (V), padding (P), extension (X), CSRC count (CC), sequence number, synchronization source (SSRC), and contributing source (CSRC) fields follow their respective definitions in [RFC3550].

バージョン（V）、パディング（P）、拡張（X）、CSRCカウント（CC）、シーケンス番号、同期送信元（SSRC）、および寄与送信元（CSRC）の各フィールドは、[RFC3550]でのそれぞれの定義に従います。

The remaining RTP header information to be set according to this RTP payload format is set as follows:

このRTPペイロード形式に従って設定する残りのRTPヘッダー情報は、次のように設定します。

Marker (M) [1 bit]:

If progressive scan video is being transmitted, the marker bit denotes the end of a video frame. If interlaced video is being transmitted, it denotes the end of the field. The marker bit SHALL be set to 1 for the last packet of the video frame/field. It SHALL be set to 0 for all other packets.

Payload Type (PT) [7 bits]:

The payload type is a dynamically allocated payload type field that designates the payload as JPEG XS video.

Timestamp [32 bits]:

The RTP timestamp is set to the sampling timestamp of the content. A 90 kHz clock rate SHALL be used.

As specified in [RFC3550] and [RFC4175], the RTP timestamp designates the sampling instant of the first octet of the video frame to which the RTP packet belongs. Packets SHALL NOT include data from multiple video frames, and all packets belonging to the same video frame SHALL have the same timestamp. Several successive RTP packets will consequently have equal timestamps if they belong to the same video frame (that is until the marker bit is set to 1, marking the last packet of the video frame), and the timestamp is only increased when a new video frame begins.

If the sampling instant does not correspond to an integer value of the clock, the value SHALL be truncated to the next lowest integer, with no ambiguity.

マーカー（M）［1ビット］：

プログレッシブスキャンのビデオを送信している場合、マーカービットはビデオフレームの終わりを示します。 インターレースのビデオを送信している場合は、フィールドの終わりを示します。 マーカービットは、ビデオフレーム/フィールドの最後のパケットでは1に設定するものとすることになります（SHALL）。 それ以外のすべてのパケットでは0に設定するものとすることになります（SHALL）。

ペイロードタイプ（PT）［7ビット］：

ペイロードタイプは、ペイロードがJPEG XSビデオであることを示す、動的に割り当てられるペイロードタイプフィールドです。

タイムスタンプ［32ビット］：

RTPタイムスタンプは、コンテンツのサンプリングタイムスタンプに設定されます。 90 kHzのクロックレートを使用するものとすることになります（SHALL）。

[RFC3550]と[RFC4175]で規定されているように、RTPタイムスタンプは、そのRTPパケットが属するビデオフレームの最初のオクテットのサンプリング時刻を示します。 パケットに複数のビデオフレームのデータを包含することはありません（SHALL NOT）。 また、同じビデオフレームに属するすべてのパケットは、同じタイムスタンプを持つものとすることになります（SHALL）。 その結果、いくつかの連続するRTPパケットが同じビデオフレームに属する場合（つまり、ビデオフレームの最後のパケットを示すマーカービットが1に設定されるまで）、それらのタイムスタンプは等しくなり、タイムスタンプは新しいビデオフレームが始まったときにのみ増加します。

サンプリング時刻がクロックの整数値に対応しない場合、その値は曖昧さなく、すぐ下の整数に切り捨てるものとすることになります（SHALL）。

4.3. Payload Header Usage

4.3. ペイロードヘッダーの使用方法

The first four bytes of the payload of an RTP packet in this RTP payload format are referred to as the "payload header". Figure 5 illustrates the structure of this payload header.

このRTPペイロード形式におけるRTPパケットのペイロードの最初の4バイトを「ペイロードヘッダー」と呼びます。 Figure 5に、このペイロードヘッダーの構造を示します。

The payload header consists of the following fields:

ペイロードヘッダーは、次のフィールドで構成されます。

Transmission mode (T) [1 bit]:

The T bit is set to indicate that packets are sent sequentially by the transmitter. This information allows a receiver to dimension its input buffer(s) accordingly. If T=0, nothing can be assumed about the transmission order and packets may be sent out of order by the transmitter. If T=1, packets SHALL be sent sequentially by the transmitter. The T-bit value SHALL be identical for all packets of the RTP stream.

pacKetization mode (K) [1 bit]:

The K bit is set to indicate which packetization mode is used. K=0 indicates codestream packetization mode, while K=1 indicates slice packetization mode. In the case that the Transmission mode (T) is set to 0 (out of order), the slice packetization mode SHALL be used and K SHALL be set to 1. This is required because only the slice packetization mode supports out-of-order packet transmission. The K-bit value SHALL be identical for all packets of the RTP stream.

Last (L) [1 bit]:

The L bit is set to indicate the last packet of a packetization unit. As the end of the video frame also ends the packet containing the last unit of the video frame, the L bit is set whenever the M bit is set. In the codestream packetization mode, the L bit and M bit get an equivalent meaning, so they SHALL have identical values in each packet.

Interlaced information (I) [2 bits]:

These two I bits are used to indicate how the JPEG XS frame is scanned (progressive or interlaced). In case of an interlaced frame, they also indicate which JPEG XS picture segment the payload is part of (first or second).

00:
The payload is progressively scanned.
01:
This value is reserved for future use.
10:
The payload is part of the first JPEG XS picture segment of an interlaced video frame. The height specified in the included JPEG XS codestream header is half of the height of the entire displayed image.
11:
The payload is part of the second JPEG XS picture segment of an interlaced video frame. The height specified in the included JPEG XS codestream header is half of the height of the entire displayed image.
F counter [5 bits]:

The Frame (F) counter identifies the video frame number modulo 32 to which a packet belongs. Frame numbers are incremented by 1 for each video frame transmitted. The frame number, in addition to the timestamp, may help the decoder manage its input buffer and bring packets back into their natural order.

Slice and Extended Packet (SEP) counter [11 bits]:

The SEP counter is used differently depending on the packetization mode.

  • In the case of codestream packetization mode (K=0), this counter resets whenever the Packet counter resets (see Section 4.4) and increments by 1 whenever the Packet counter overruns.
  • In the case of slice packetization mode (K=1), this counter identifies the slice modulo 2047 to which the packet contributes. If the data belongs to the JPEG XS header segment, this field SHALL have its maximal value, namely 2047 = 0x07ff. Otherwise, it is the slice index modulo 2047. Slice indices are counted from 0 (corresponding to the top of the video frame).
P counter [11 bits]:

The Packet (P) counter identifies the packet number modulo 2048 within the current packetization unit. It is set to 0 at the start of the packetization unit and incremented by 1 for every subsequent packet (if any) belonging to the same unit. Practically, if codestream packetization mode is enabled, this field counts the packets within a JPEG XS picture segment and is extended by the SEP counter when it overruns. If slice packetization mode is enabled, this field counts the packets within a slice or within the JPEG XS header segment.

送信モード（Transmission mode、T）［1ビット］：

Tビットは、送信者がパケットを順番に送信することを示すために設定されます。 この情報により、受信者は入力バッファーのサイズを適切に決めることができます。 T=0の場合、送信順序については何も前提にできず、送信者はパケットを順不同で送信する場合があります。 T=1の場合、送信者はパケットを順番に送信するものとすることになります（SHALL）。 Tビットの値は、RTPストリームのすべてのパケットで同一であるものとすることになります（SHALL）。

パケット化モード（pacKetization mode、K）［1ビット］：

Kビットは、どのパケット化モードを使用しているかを示すために設定されます。 K=0はコードストリームパケット化モードを示し、K=1はスライスパケット化モードを示します。 送信モード（T）が0（順不同）に設定されている場合、スライスパケット化モードを使用するものとすることになります（SHALL）。 そして、Kは1に設定するものとすることになります（SHALL）。 これが必要なのは、順不同のパケット送信をサポートするのはスライスパケット化モードだけだからです。 Kビットの値は、RTPストリームのすべてのパケットで同一であるものとすることになります（SHALL）。

最終（Last、L）［1ビット］：

Lビットは、パケット化ユニットの最後のパケットを示すために設定されます。 ビデオフレームの終わりは、そのビデオフレームの最後のユニットを含むパケットの終わりでもあるため、Mビットが設定されるときは常にLビットも設定されます。 コードストリームパケット化モードでは、LビットとMビットは同等の意味を持つため、各パケットで同一の値を持つものとすることになります（SHALL）。

インターレース情報（Interlaced information、I）［2ビット］：

これら2つのIビットは、JPEG XSフレームがどのように走査されるか（プログレッシブまたはインターレース）を示すために使用されます。 インターレースフレームの場合は、ペイロードがどちらのJPEG XSピクチャーセグメント（1番目または2番目）の一部であるかも示します。

00:
ペイロードはプログレッシブに走査されています。
01:
この値は将来の使用のために予約されています。
10:
ペイロードは、インターレースビデオフレームの1番目のJPEG XSピクチャーセグメントの一部です。 含まれているJPEG XSコードストリームヘッダーで指定されている高さは、表示される画像全体の高さの半分です。
11:
ペイロードは、インターレースビデオフレームの2番目のJPEG XSピクチャーセグメントの一部です。 含まれているJPEG XSコードストリームヘッダーで指定されている高さは、表示される画像全体の高さの半分です。
Fカウンター［5ビット］：

フレーム（F）カウンターは、パケットが属するビデオフレームの番号を32を法として識別します。 フレーム番号は、送信されるビデオフレームごとに1ずつ増加します。 フレーム番号は、タイムスタンプに加えて、デコーダーが入力バッファーを管理し、パケットを本来の順序に戻すのに役立つ場合があります。

スライスおよび拡張パケット（Slice and Extended Packet、SEP）カウンター［11ビット］：

SEPカウンターは、パケット化モードに応じて異なる使い方をします。

  • コードストリームパケット化モード（K=0）の場合、このカウンターはパケットカウンターがリセットされるたびにリセットされ（Section 4.4を参照）、パケットカウンターがオーバーランするたびに1ずつ増加します。
  • スライスパケット化モード（K=1）の場合、このカウンターは、パケットが寄与するスライスを2047を法として識別します。 データがJPEG XSヘッダーセグメントに属する場合、このフィールドはその最大値、つまり2047 = 0x07ffを持つものとすることになります（SHALL）。 それ以外の場合は、2047を法としたスライスインデックスです。 スライスインデックスは0（ビデオフレームの最上部に対応）から数えます。
Pカウンター［11ビット］：

パケット（P）カウンターは、現在のパケット化ユニット内のパケット番号を2048を法として識別します。 パケット化ユニットの開始時に0に設定され、同じユニットに属する後続のパケット（もしあれば）ごとに1ずつ増加します。 実際には、コードストリームパケット化モードが有効な場合、このフィールドはJPEG XSピクチャーセグメント内のパケットを数え、オーバーランしたときにはSEPカウンターによって拡張されます。 スライスパケット化モードが有効な場合、このフィールドはスライス内またはJPEG XSヘッダーセグメント内のパケットを数えます。

4.4. Payload Data

4.4. ペイロードデータ

The payload data of a JPEG XS RTP stream consists of a concatenation of multiple JPEG XS frames. Within the RTP stream, all of the video support boxes and all of the color specification boxes SHALL retain their respective layouts for each JPEG XS frame. Thus, each video support box in the RTP stream SHALL define the same sub boxes. The effective values in the boxes are allowed to change under the condition that their relative byte offsets SHALL NOT change.

JPEG XSのRTPストリームのペイロードデータは、複数のJPEG XSフレームを連結したもので構成されます。 RTPストリーム内では、すべてのビデオサポートボックスとすべてのカラー仕様ボックスは、各JPEG XSフレームでそれぞれのレイアウトを保持するものとすることになります（SHALL）。 したがって、RTPストリーム内の各ビデオサポートボックスは、同じサブボックスを定義するものとすることになります（SHALL）。 ボックス内の実際の値は変化してもかまいませんが、その相対的なバイトオフセットは変化することはありません（SHALL NOT）という条件が付きます。

Each JPEG XS frame is the concatenation of one or more packetization unit(s), as explained in Section 4.1. The Frame counter value is not indicated because the value is constant for all packetization units of a given video frame.

各JPEG XSフレームは、Section 4.1で説明したように、1つ以上のパケット化ユニットを連結したものです。 Figure 6はコードストリームパケット化モードにおけるプログレッシブビデオフレームのこのレイアウトを示し、Figure 7はコードストリームパケット化モードにおけるインターレースビデオフレームのこのレイアウトを示し、Figure 8はスライスパケット化モードにおけるプログレッシブビデオフレームのこのレイアウトを示し、Figure 9はスライスパケット化モードにおけるインターレースビデオフレームのこのレイアウトを示します。 フレームカウンターの値は、特定のビデオフレームのすべてのパケット化ユニットで一定であるため、図には示していません。

5. Traffic Shaping and Delivery Timing

5. トラフィックシェーピングと配送タイミング

In order to facilitate proper synchronization between senders and receivers, it is RECOMMENDED to implement traffic shaping and delivery timing in accordance with the Network Compatibility Model compliance definitions specified in [SMPTE2110-21]. In such a case, the session description SHALL signal the compliance with the media type parameter TP. The actual applied traffic shaping and timing delivery mechanism is outside the scope of this memo and does not influence the payload packetization.

6. Congestion Control Considerations

6. 輻輳制御に関する考慮事項

Congestion control for RTP SHALL be used in accordance with [RFC3550] and with any applicable RTP profile, e.g., RTP/AVP [RFC3551] or RTP/AVPF [RFC4585].

RTPの輻輳制御は、[RFC3550]、および適用可能なRTPプロファイル（たとえばRTP/AVP[RFC3551]やRTP/AVPF[RFC4585]）に従って使用するものとすることになります（SHALL）。

While JPEG XS is mainly designed to be used in controlled network environments, it can also be employed in best-effort network environments, like the Internet. However, in this case, the users of this payload format SHALL monitor packet loss to ensure that the packet loss rate is within acceptable parameters. This can be achieved, for example, by means of RTP Control Protocol (RTCP) Feedback for Congestion Control [RFC8888].

JPEG XSは主に管理されたネットワーク環境で使用するように設計されていますが、インターネットのようなベストエフォートのネットワーク環境でも使用できます。 ただし、その場合、このペイロード形式の利用者は、パケット損失率が許容可能な範囲内にあることを確かめるために、パケット損失を監視するものとすることになります（SHALL）。 これは、たとえば輻輳制御のためのRTP Control Protocol（RTCP）フィードバック[RFC8888]によって実現できます。

In addition, [RFC8083] is an update to [RFC3550] that defines criteria for when one is required to stop sending RTP Packet Streams and for when applications implementing this standard SHALL comply with it.

さらに、[RFC8083]は[RFC3550]の更新であり、RTPパケットストリームの送信を停止しなければならない場合の基準を定義しています。 この標準を実装するアプリケーションは、それに準拠するものとすることになります（SHALL）。

[RFC8085] provides additional information on the best practices for applying congestion control to UDP streams.

[RFC8085]は、UDPストリームに輻輳制御を適用するためのベストプラクティスに関する追加情報を提供しています。

メディアタイプ（"video"）は、メディア名としてSDPの"m="に入ります。
メディアサブタイプ（"jxsv"）は、エンコーディング名としてSDPの"a=rtpmap"に入り、その後にスラッシュ（"/"）と、RTPタイムスタンプのクロックレートに対応する必須パラメーター"rate"が続きます（この文書で定義するペイロード形式では、この値は90000であるものとすることになります（SHALL））。
必須パラメーター"packetmode"と、Section 7.1で説明している追加の任意パラメーターは、メディアタイプの文字列からセミコロンで区切られたparameter=valueのペアのリストとして直接コピーすることで、SDPのメディア形式記述である"a=fmtp"属性（Format Parameters）に入ります。

All parameters of the media format SHALL correspond to the parameters of the payload. In case of discrepancies between payload parameter values and SDP fields, the values from the payload data SHALL prevail.

メディア形式のすべてのパラメーターは、ペイロードのパラメーターに対応するものとすることになります（SHALL）。 ペイロードのパラメーター値とSDPのフィールドの間に食い違いがある場合は、ペイロードデータの値を優先するものとすることになります（SHALL）。

The receiver SHALL ignore any parameter that is not defined in Section 7.1.

受信者は、Section 7.1で定義されていないパラメーターをすべて無視するものとすることになります（SHALL）。

An example SDP mapping for JPEG XS video is as follows:

JPEG XSビデオのSDPへの対応付けの例を次に示します。 

   m=video 30000 RTP/AVP 112
   a=rtpmap:112 jxsv/90000
   a=fmtp:112 packetmode=0;sampling=YCbCr-4:2:2;
              width=1920;height=1080;depth=10;
              colorimetry=BT709;TCS=SDR;RANGE=FULL;TP=2110TPNL

   m=video 30000 RTP/AVP 112
   a=rtpmap:112 jxsv/90000
   a=fmtp:112 packetmode=0;sampling=YCbCr-4:2:2;
              width=1920;height=1080;depth=10;
              colorimetry=BT709;TCS=SDR;RANGE=FULL;TP=2110TPNL

In this example, a JPEG XS RTP stream is to be sent to UDP destination port 30000, with an RTP dynamic payload type of 112 and a media clock rate of 90000 Hz. Note that the "a=fmtp:" line has been wrapped to fit this page and will be a single long line in the SDP file. This example includes the TP parameter (as specified in Section 5).

この例では、JPEG XSのRTPストリームが、RTPの動的ペイロードタイプ112、メディアクロックレート90000 HzでUDPの宛先ポート30000に送信されます。 "a=fmtp:"の行はこのページに収まるように折り返されていますが、SDPファイルでは1行の長い行になることに注意してください。 この例には、（Section 5で規定されている）TPパラメーターが含まれています。

8.2. Usage with SDP Offer/Answer Model

8.2. SDPオファー/アンサーモデルでの使用

When JPEG XS is offered over RTP using SDP in an offer/answer model [RFC3264] for negotiation for unicast usage, the following limitations and rules apply:

ユニキャストでの使用のためのネゴシエーションにおいて、オファー/アンサーモデルのSDP[RFC3264]を使用してRTP上のJPEG XSをオファーする場合、次の制限と規則が適用されます。

The "a=fmtp" attribute SHALL be present specifying the required parameter "packetmode" and MAY specify any of the optional parameters, as described in Section 7.1.
All parameters in the "a=fmtp" attribute indicate sending capabilities (i.e., properties of the payload).
An answerer of the SDP is required to support all parameters and values of the parameters provided by the offerer; otherwise, the answerer SHALL reject the session. It falls on the offerer to use values that are expected to be supported by the answerer. If the answerer accepts the session, it SHALL reply with the exact same parameter values in the "a=fmtp" attribute as they were initially offered.
The same RTP payload type number used in the offer SHOULD be used in the answer, as specified in [RFC3264].
"a=fmtp"属性は、必須パラメーター"packetmode"を指定して存在するものとすることになります（SHALL）。 また、Section 7.1で説明している任意パラメーターのいずれかを指定してもよいです（MAY）。
"a=fmtp"属性のすべてのパラメーターは、送信能力（つまり、ペイロードの特性）を示します。
SDPのアンサー側は、オファー側が提供したすべてのパラメーターとパラメーターの値をサポートする必要があります。 そうでない場合、アンサー側はセッションを拒否するものとすることになります（SHALL）。 アンサー側がサポートすると見込まれる値を使用するのは、オファー側の責任です。 アンサー側がセッションを受け入れる場合、最初にオファーされたものとまったく同じパラメーター値を"a=fmtp"属性に入れて応答するものとすることになります（SHALL）。
[RFC3264]で規定されているように、オファーで使用したのと同じRTPペイロードタイプ番号をアンサーでも使用すべきです（SHOULD）。

10. Security Considerations

10. セキュリティーに関する考慮事項

RTP packets using the payload format defined in this memo are subject to the security considerations discussed in [RFC3550] and in any applicable RTP profile such as RTP/AVP [RFC3551], RTP/AVPF [RFC4585], RTP/SAVP [RFC3711], or RTP/SAVPF [RFC5124]. This implies that confidentiality of the media streams is achieved by encryption.

このメモで定義するペイロード形式を使用するRTPパケットは、[RFC3550]、およびRTP/AVP[RFC3551]、RTP/AVPF[RFC4585]、RTP/SAVP[RFC3711]、RTP/SAVPF[RFC5124]などの適用可能なRTPプロファイルで議論されているセキュリティーに関する考慮事項の対象となります。 これは、メディアストリームの機密性が暗号化によって実現されることを意味します。

However, as "Securing the RTP Framework: Why RTP Does Not Mandate a Single Media Security Solution" [RFC7202] discusses, it is not an RTP payload format's responsibility to discuss or mandate what solutions are used to meet the basic security goals like confidentiality, integrity, and source authenticity for RTP in general. This responsibility lies on anyone using RTP in an application. They can find guidance on available security mechanisms and important considerations in "Options for Securing RTP Sessions" [RFC7201]. Applications SHOULD use one or more appropriate strong security mechanisms.

しかし、"Securing the RTP Framework: Why RTP Does Not Mandate a Single Media Security Solution"[RFC7202]で議論されているように、RTP全般について、機密性、完全性、送信元の真正性といった基本的なセキュリティー目標を満たすためにどのような解決策を使用するかを議論したり義務付けたりするのは、RTPペイロード形式の責任ではありません。 この責任は、アプリケーションでRTPを使用するすべての者にあります。 利用可能なセキュリティーメカニズムと重要な考慮事項に関するガイダンスは、"Options for Securing RTP Sessions"[RFC7201]にあります。 アプリケーションは、1つ以上の適切な強力なセキュリティーメカニズムを使用すべきです（SHOULD）。

Implementations of this RTP payload format need to take appropriate security considerations into account. It is important for the decoder to be robust against malicious or malformed payloads and ensure that they do not cause the decoder to overrun its allocated memory or otherwise misbehave. An overrun in allocated memory could lead to arbitrary code execution by an attacker. The same applies to the encoder, even though problems in encoders are typically rarer.

このRTPペイロード形式の実装では、適切なセキュリティー上の考慮事項を考慮に入れる必要があります。 デコーダーは、悪意のあるペイロードや不正な形式のペイロードに対して堅牢であり、それらによってデコーダーが割り当てられたメモリーをオーバーランしたり、その他の誤動作をしたりしないようにすることが重要です。 割り当てられたメモリーのオーバーランは、攻撃者による任意のコード実行につながる可能性があります。 エンコーダーの問題は一般にまれですが、同じことがエンコーダーにも当てはまります。

This payload format and the JPEG XS encoding do not exhibit any substantial non-uniformity, either in output or in complexity to perform the decoding operation; thus, they are unlikely to pose a denial-of-service threat due to the receipt of pathological datagrams.

このペイロード形式とJPEG XSのエンコーディングは、出力においても、デコード操作を実行するための複雑さにおいても、実質的な不均一性を示しません。 したがって、異常なデータグラムの受信によってサービス拒否の脅威をもたらす可能性は低いです。

This payload format and the JPEG XS encoding do not contain code that is executable.

このペイロード形式とJPEG XSのエンコーディングには、実行可能なコードは含まれていません。

It is important to note that high-definition (HD) or ultra-high-definition (UHD) video that is encoded with JPEG XS can have significant bandwidth requirements (typically more than 1 Gbps for UHD video, especially if using high framerate). This is sufficient to cause potential for denial of service if transmitted onto most currently available Internet paths.

JPEG XSでエンコードされた高精細（HD）または超高精細（UHD）のビデオは、かなりの帯域幅を必要とする場合があることに注意することが重要です（典型的には、UHDビデオでは、特に高フレームレートを使用する場合、1 Gbpsを超える）。 これは、現在利用可能なほとんどのインターネットのパス上で送信された場合に、サービス拒否を引き起こす可能性があるのに十分な量です。

Accordingly, if best-effort service is being used, users of this payload format SHALL monitor packet loss to ensure that the packet loss rate is within acceptable parameters. Packet loss is considered acceptable if a TCP flow across the same network path, and experiencing the same network conditions, would achieve an average throughput, measured on a reasonable timescale, that is not less than the RTP flow is achieving. This condition can be satisfied by implementing congestion control mechanisms to adapt the transmission rate (or the number of layers subscribed for a layered multicast session) or by arranging for a receiver to leave the session if the loss rate is unacceptably high.

したがって、ベストエフォートのサービスを使用している場合、このペイロード形式の利用者は、パケット損失率が許容可能な範囲内にあることを確かめるために、パケット損失を監視するものとすることになります（SHALL）。 パケット損失は、同じネットワークパスを通過し、同じネットワーク状況を経験するTCPフローが、妥当な時間尺度で測定して、RTPフローが達成しているよりも小さくない平均スループットを達成する場合に、許容可能とみなされます。 この条件は、送信レート（または階層化マルチキャストセッションで購読する層の数）を調整する輻輳制御メカニズムを実装するか、損失率が許容できないほど高い場合に受信者がセッションから離脱するように手配することで満たすことができます。

This payload format may also be used in networks that provide quality-of-service guarantees. If enhanced service is being used, receivers SHOULD monitor packet loss to ensure that the service that was requested is actually being delivered. If it is not, then they SHOULD assume that they are receiving best-effort service and behave accordingly.

このペイロード形式は、サービス品質の保証を提供するネットワークで使用される場合もあります。 強化されたサービスを使用している場合、受信者は、要求したサービスが実際に提供されていることを確かめるためにパケット損失を監視すべきです（SHOULD）。 提供されていない場合、受信者はベストエフォートのサービスを受けていると想定し、それに応じて振る舞うべきです（SHOULD）。
