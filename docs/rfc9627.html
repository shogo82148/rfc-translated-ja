The Layer Refresh Request (LRR) RTCP Feedback Message

RFC 9627

Layer Refresh Request（LRR）RTCPフィードバックメッセージ

Abstract

概要

This memo describes the RTCP Payload-Specific Feedback Message Layer Refresh Request (LRR), which can be used to request a state refresh of one or more substreams of a layered media stream. This document also defines its use with several RTP payloads for scalable media formats.

このメモでは、階層化されたメディアストリームの1つ以上のサブストリームの状態のリフレッシュを要求するために使用できる、 RTCPのペイロード固有フィードバックメッセージであるLayer Refresh Request（LRR）について説明します。 この文書では、スケーラブルなメディア形式のためのいくつかのRTPペイロードでの使用方法も定義します。

1. Introduction

1. はじめに

This memo describes an [RFC3550] [RFC4585] "Layer Refresh Request" (LRR), which is designed to allow a receiver of a layered media stream to request that one or more of its substreams be refreshed. The stream can then be decoded by an endpoint that previously was not receiving those layers, without requiring that the entire stream be refreshed (as it would be if the receiver sent a [RFC5104]; see also [RFC8082]).

このメモでは、[RFC3550]の[RFC4585]である「Layer Refresh Request」（LRR）について説明します。 LRRは、階層化されたメディアストリームの受信者が、そのサブストリームの1つ以上をリフレッシュするよう要求できるように設計されています。 これにより、ストリーム全体をリフレッシュする必要なしに（受信者が[RFC5104]を送信した場合にはストリーム全体がリフレッシュされます。[RFC8082]も参照してください）、それまでそれらのレイヤーを受信していなかったエンドポイントがストリームをデコードできるようになります。

The feedback message is applicable to both temporally and spatially scaled streams and to both single-stream and multi-stream scalability modes.

このフィードバックメッセージは、時間方向と空間方向のどちらにスケーリングされたストリームにも適用でき、 シングルストリームとマルチストリームのどちらのスケーラビリティーモードにも適用できます。

2. Conventions and Terminology

2. 表記規則と用語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

2.1. Terminology

2.1. 用語

A "layer refresh point" is a point in a scalable stream after which a decoder, which previously had been able to decode only some (possibly none) of the available layers of stream, is able to decode a greater number of the layers.

「レイヤーリフレッシュポイント（layer refresh point）」とは、スケーラブルなストリーム内のある地点で、 それまでストリームの利用可能なレイヤーの一部しか（場合によってはまったく）デコードできなかったデコーダーが、 その地点以降はより多くのレイヤーをデコードできるようになるものです。

For spatial (or quality) layers, in normal encoding, a subpicture can depend both on earlier pictures of that spatial layer and also on lower-layer pictures of the current picture. However, a layer refresh typically requires that a spatial-layer picture be encoded in a way that references only the lower-layer subpictures of the current picture, not any earlier pictures of that spatial layer. Additionally, the encoder must promise that no earlier pictures of that spatial layer will be used as reference in the future.

空間（または品質）レイヤーでは、通常のエンコーディングにおいて、 サブピクチャーは、その空間レイヤーの以前のピクチャーと、現在のピクチャーの下位レイヤーのピクチャーの両方に依存できます。 しかし、レイヤーリフレッシュでは通常、空間レイヤーのピクチャーを、その空間レイヤーの以前のピクチャーをいっさい参照せず、 現在のピクチャーの下位レイヤーのサブピクチャーだけを参照する方法でエンコードする必要があります。 さらに、エンコーダーは、その空間レイヤーの以前のピクチャーを今後参照として使用しないことを約束する必要があります。

However, even in a layer refresh, layers other than the ones being refreshed may still maintain dependency on earlier content of the stream. This is the difference between a layer refresh and a [RFC5104]. This minimizes the coding overhead of refresh to only those parts of the stream that actually need to be refreshed at any given time.

ただし、レイヤーリフレッシュにおいても、リフレッシュ対象以外のレイヤーは、 ストリームの以前のコンテンツへの依存関係を維持していてもかまいません。 これがレイヤーリフレッシュと[RFC5104]の違いです。 これにより、リフレッシュの符号化オーバーヘッドを、その時点で実際にリフレッシュする必要があるストリームの部分だけに最小化できます。

拡張レイヤーの空間レイヤーリフレッシュを以下に示します。 「<--」は符号化の依存関係を示します。

In Figure 1, frame 3 is a layer refresh point for spatial layer S1; a decoder that had previously only been decoding spatial layer S0 would be able to decode layer S1 starting at frame 3.

Figure 1では、 フレーム3が空間レイヤーS1のレイヤーリフレッシュポイントです。 それまで空間レイヤーS0だけをデコードしていたデコーダーは、フレーム3からレイヤーS1をデコードできるようになります。

The spatial-layer refresh of a base layer is shown below. The "<--" indicates a coding dependency.

ベースレイヤーの空間レイヤーリフレッシュを以下に示します。 「<--」は符号化の依存関係を示します。

In Figure 2, frame 3 is a layer refresh point for spatial layer S0; a decoder that had previously not been decoding the stream at all could decode layer S0 starting at frame 3.

Figure 2では、 フレーム3が空間レイヤーS0のレイヤーリフレッシュポイントです。 それまでストリームをまったくデコードしていなかったデコーダーは、フレーム3からレイヤーS0をデコードできます。

For temporal layers, while normal encoding allows frames to depend on earlier frames of the same temporal layer, layer refresh requires that the layer be "temporally nested", i.e., use as reference only earlier frames of a lower temporal layer, not any earlier frames of this temporal layer and promise that no future frames of this temporal layer will reference frames of this temporal layer before the refresh point. In many cases, the temporal structure of the stream will mean that all frames are temporally nested; in this case, decoders will have no need to send LRR messages for the stream.

時間レイヤーでは、通常のエンコーディングでは同じ時間レイヤーの以前のフレームにフレームが依存することを許しますが、 レイヤーリフレッシュでは、そのレイヤーが「時間的に入れ子（temporally nested）」であることが必要です。 つまり、この時間レイヤーの以前のフレームはいっさい参照せず、下位の時間レイヤーの以前のフレームだけを参照として使用し、 さらに、この時間レイヤーの今後のフレームが、リフレッシュポイントより前のこの時間レイヤーのフレームを参照しないことを約束する必要があります。 多くの場合、ストリームの時間構造上、すべてのフレームが時間的に入れ子になります。 この場合、デコーダーがそのストリームに対してLRRメッセージを送信する必要はありません。

時間レイヤーのリフレッシュを以下に示します。 「<--」は符号化の依存関係を示します。

In Figure 3, frame 6 is a layer refresh point for temporal layer T1; a decoder that had previously only been decoding temporal layer T0 would be able to decode layer T1 starting at frame 6.

Figure 3では、フレーム6が時間レイヤーT1のレイヤーリフレッシュポイントです。 それまで時間レイヤーT0だけをデコードしていたデコーダーは、フレーム6からレイヤーT1をデコードできるようになります。

本質的に時間的に入れ子になっているストリームを以下に示します。 「<--」は符号化の依存関係を示します。

Figure 4では、ストリームは通常の構造において時間的に入れ子になっています。 レイヤーT0を受信しているデコーダーは、任意の地点でレイヤーT1のデコードを開始できます。

A "layer index" is a numeric label for a specific spatial and temporal layer of a scalable stream. It consists of both a "temporal-layer ID" identifying the temporal layer and a "layer ID" identifying the spatial or quality layer. The details of how layers of a scalable stream are labeled are codec specific. Details for several codecs are defined in Section 4.

「レイヤーインデックス（layer index）」とは、スケーラブルなストリームの特定の空間レイヤーおよび時間レイヤーを表す数値のラベルです。 レイヤーインデックスは、時間レイヤーを識別する「時間レイヤーID（temporal-layer ID）」と、 空間レイヤーまたは品質レイヤーを識別する「レイヤーID（layer ID）」の両方から構成されます。 スケーラブルなストリームのレイヤーにどのようにラベルを付けるかの詳細はコーデックに固有です。 いくつかのコーデックについての詳細はSection 4で定義します。

3. Layer Refresh Request

3. Layer Refresh Request

A layer refresh frame can be requested by sending a Layer Refresh Request (LRR), which is an [RFC3550] [RFC4585] asking the encoder to encode a frame that makes it possible to upgrade to a higher layer. The LRR contains one or two tuples, indicating the temporal and spatial layer the decoder wants to upgrade to and (optionally) the currently highest temporal and spatial layer the decoder can decode.

レイヤーリフレッシュフレームは、Layer Refresh Request（LRR）を送信することで要求できます。 LRRは、より上位のレイヤーへのアップグレードを可能にするフレームをエンコードするようエンコーダーに求める[RFC3550]の[RFC4585]です。 LRRには1つまたは2つのタプルが含まれ、デコーダーがアップグレードしたい時間レイヤーと空間レイヤー、 および（任意で）デコーダーが現在デコードできる最上位の時間レイヤーと空間レイヤーを示します。

The specific format of the tuples, and the mechanism by which a receiver recognizes a refresh frame, is codec dependent. Usage for several codecs is discussed in Section 4.

タプルの具体的な形式と、受信者がリフレッシュフレームを認識する仕組みは、コーデックに依存します。 いくつかのコーデックでの使用方法はSection 4で説明します。

The design of LRR follows the FIR model (Section 3.5.1 of [RFC5104]) for its retransmission, reliability, and use in multipoint conferences.

LRRの設計は、再送、信頼性、多地点会議での使用について、FIRのモデル（[RFC5104]のSection 3.5.1）に従います。

The LRR message is identified by RTCP packet type value PT=PSFB and FMT=10. The Feedback Control Information (FCI) field MUST contain one or more LRR entries. Each entry applies to a different media sender, identified by its Synchronization Source (SSRC).

LRRメッセージは、RTCPパケットタイプの値PT=PSFBおよびFMT=10で識別されます。 フィードバック制御情報（Feedback Control Information：FCI）フィールドには、1つ以上のLRRエントリーが含まれなければなりません（MUST）。 各エントリーは、同期ソース（Synchronization Source：SSRC）で識別される、それぞれ異なるメディア送信者に適用されます。

3.1. Message Format

3.1. メッセージ形式

The FCI for the Layer Refresh Request consists of one or more FCI entries, the content of which is depicted in Figure 5. The length of the LRR feedback message MUST be set to 2+3*N 32-bit words, where N is the number of FCI entries.

Layer Refresh RequestのFCIは1つ以上のFCIエントリーで構成され、 その内容をFigure 5に示します。 LRRフィードバックメッセージの長さは、2+3*N個の32ビットワードに設定しなければなりません（MUST）。 ここで、NはFCIエントリーの数です。

Synchronization Source (SSRC) (32 bits):
The SSRC value of the media sender that is requested to send a layer refresh point.
Seq nr. (8 bits):
The command sequence number. The sequence number space is unique for each pairing of the SSRC of command source and the SSRC of the command target. The sequence number SHALL be increased by 1 for each new command (modulo 256, so the value after 255 is 0). A repetition SHALL NOT increase the sequence number. The initial value is arbitrary.
C (1 bit):
A flag bit indicating whether the Current Temporal-layer ID (CTID) and Current Layer ID (CLID) fields are present in the FCI. If this bit is 0, the sender of the LRR message is requesting refresh of all layers up to and including the target layer.
Payload Type (7 bits):
The RTP payload type for which the LRR is being requested. This gives the context in which the target layer index is to be interpreted.
Reserved (RES) (three separate fields of 16 bits / 5 bits / 5 bits):
All bits SHALL be set to zero by the sender and SHALL be ignored on reception.
Target Temporal-layer ID (TTID) (3 bits):
The temporal-layer ID of the target layer for which the receiver wishes a refresh point.
Target Layer ID (TLID) (8 bits):
The layer ID of the target spatial or quality layer for which the receiver wishes a refresh point. Its format is dependent on the payload type field.
Current Temporal-layer ID (CTID) (3 bits):
If C is 1, the ID of the current temporal layer being decoded by the receiver. This message is not requesting refresh of layers at or below this layer. If C is 0, this field SHALL be set to zero by the sender and SHALL be ignored on reception.
Current Layer ID (CLID) (8 bits):
If C is 1, the layer ID of the current spatial or quality layer being decoded by the receiver. This message is not requesting refresh of layers at or below this layer. If C is 0, this field SHALL be set to zero by the sender and SHALL be ignored on reception.
Synchronization Source（SSRC）（32ビット）：
レイヤーリフレッシュポイントの送信を要求されるメディア送信者のSSRC値です。
Seq nr.（8ビット）：
コマンドのシーケンス番号です。 シーケンス番号空間は、コマンド送信元のSSRCとコマンド対象のSSRCの組ごとに一意です。 シーケンス番号は、新しいコマンドごとに1ずつ増加することになります（SHALL）（256を法とするので、255の次の値は0です）。 繰り返しによってシーケンス番号が増加することはありません（SHALL NOT）。 初期値は任意です。
C（1ビット）：
Current Temporal-layer ID（CTID）フィールドとCurrent Layer ID（CLID）フィールドがFCIに存在するかどうかを示すフラグビットです。 このビットが0の場合、LRRメッセージの送信者は、ターゲットレイヤーまでの（ターゲットレイヤーを含む）すべてのレイヤーのリフレッシュを要求しています。
Payload Type（7ビット）：
LRRを要求する対象のRTPペイロードタイプです。 これは、ターゲットレイヤーインデックスを解釈する際のコンテキストを与えます。
Reserved（RES）（16ビット / 5ビット / 5ビットの3つの独立したフィールド）：
送信者はすべてのビットをゼロに設定することになります（SHALL）。 また、受信時には無視することになります（SHALL）。
Target Temporal-layer ID（TTID）（3ビット）：
受信者がリフレッシュポイントを望むターゲットレイヤーの時間レイヤーIDです。
Target Layer ID（TLID）（8ビット）：
受信者がリフレッシュポイントを望む、ターゲットの空間レイヤーまたは品質レイヤーのレイヤーIDです。 その形式はペイロードタイプフィールドに依存します。
Current Temporal-layer ID（CTID）（3ビット）：
Cが1の場合、受信者が現在デコードしている時間レイヤーのIDです。 このメッセージは、このレイヤー以下のレイヤーのリフレッシュは要求していません。 Cが0の場合、送信者はこのフィールドをゼロに設定することになります（SHALL）。 また、受信時には無視することになります（SHALL）。
Current Layer ID（CLID）（8ビット）：
Cが1の場合、受信者が現在デコードしている空間レイヤーまたは品質レイヤーのレイヤーIDです。 このメッセージは、このレイヤー以下のレイヤーのリフレッシュは要求していません。 Cが0の場合、送信者はこのフィールドをゼロに設定することになります（SHALL）。 また、受信時には無視することになります（SHALL）。

When C is 1, TTID MUST NOT be less than CTID, and TLID MUST NOT be less than CLID; at least one of either TTID or TLID MUST be greater than CTID or CLID, respectively. That is to say, the target layer index <TTID, TLID> MUST be a layer upgrade from the current layer index <CTID, CLID>. A sender MAY request an upgrade in both temporal and spatial or quality layers simultaneously.

Cが1の場合、TTIDはCTID未満であってはなりません（MUST NOT）。 また、TLIDはCLID未満であってはなりません（MUST NOT）。 TTIDとTLIDの少なくとも一方は、それぞれCTIDまたはCLIDより大きくなければなりません（MUST）。 つまり、ターゲットレイヤーインデックス<TTID, TLID>は、現在のレイヤーインデックス<CTID, CLID>からのレイヤーのアップグレードでなければなりません（MUST）。 送信者は、時間レイヤーと、空間レイヤーまたは品質レイヤーの両方のアップグレードを同時に要求してもよいです（MAY）。

A receiver receiving an LRR feedback packet that does not satisfy the requirements of the previous paragraph, i.e., one where the C bit is present but the TTID is less than the CTID or the TLID is less than the CLID, MUST discard the request.

前の段落の要件を満たさないLRRフィードバックパケット、 すなわち、Cビットが存在するにもかかわらずTTIDがCTID未満であるか、TLIDがCLID未満であるパケットを受信した受信者は、 その要求を破棄しなければなりません（MUST）。

Note: The syntax of the TTID, TLID, CTID, and CLID fields match, by design, the TID and LID fields in [RFC9626].

注：TTID、TLID、CTID、CLIDの各フィールドの構文は、意図的に[RFC9626]のTIDフィールドおよびLIDフィールドと一致させています。

3.2. Semantics

3.2. セマンティクス

Within the common packet header for feedback messages (as defined in Section 6.1 of [RFC4585]), the "SSRC of packet sender" field indicates the source of the request, and the "SSRC of media source" is not used and SHALL be set to zero. The SSRCs of the media senders to which the LRR command applies are in the corresponding FCI entries. An LRR message MAY contain requests to multiple media senders, using one FCI entry per target media sender.

（[RFC4585]のSection 6.1で定義されている）フィードバックメッセージの共通パケットヘッダー内では、 「SSRC of packet sender」フィールドが要求の送信元を示し、 「SSRC of media source」は使用されず、ゼロに設定することになります（SHALL）。 LRRコマンドを適用するメディア送信者のSSRCは、対応するFCIエントリーに含まれます。 LRRメッセージには、対象のメディア送信者ごとに1つのFCIエントリーを使用して、複数のメディア送信者への要求を含めてもよいです（MAY）。

Upon reception of an LRR, the encoder MUST send a decoder refresh point (see Section 2.1) as soon as possible.

LRRを受信したエンコーダーは、デコーダーリフレッシュポイント（Section 2.1を参照）をできるだけ早く送信しなければなりません（MUST）。

The sender MUST respect bandwidth limits provided by the application of congestion control, as described in Section 5 of [RFC5104]. As layer refresh points will often be larger than non-refreshing frames, this may restrict a sender's ability to send a layer refresh point quickly.

[RFC5104]のSection 5で説明されているように、送信者は、輻輳制御の適用によって与えられる帯域幅の制限を尊重しなければなりません（MUST）。 レイヤーリフレッシュポイントは、リフレッシュを行わないフレームよりも大きくなることが多いため、 これにより、送信者がレイヤーリフレッシュポイントをすばやく送信する能力が制限される可能性があります。

An LRR MUST NOT be sent as a reaction to picture losses due to packet loss or corruption; it is RECOMMENDED to use [RFC4585] instead. An LRR SHOULD be used only in situations where there is an explicit change in a decoder's behavior: for example, when a receiver will start decoding a layer that it previously had been discarding.

パケットの損失や破損によるピクチャーの損失への対応として、LRRを送信してはなりません（MUST NOT）。 その代わりに[RFC4585]を使用することが推奨されます（RECOMMENDED）。 LRRは、デコーダーの振る舞いに明示的な変化がある状況、 たとえば、受信者がそれまで破棄していたレイヤーのデコードを開始する場合にのみ使用されるべきです（SHOULD）。

4. Usage with Specific Codecs

4. 特定のコーデックでの使用

In order for an LRR to be used with a scalable codec, the format of the temporal and layer ID fields (for both the target and current layer indices) needs to be specified for that codec's RTP packetization. New RTP packetization specifications for scalable codecs SHOULD define how this is done. (The [RFC9628], for instance, has done so.) If the payload also specifies how it is used with the Video Frame Marking RTP Header Extension described in [RFC9626], the syntax MUST be defined in the same manner as the TID and LID fields in that header.

LRRをスケーラブルなコーデックで使用するには、 （ターゲットと現在の両方のレイヤーインデックスについて）時間IDフィールドとレイヤーIDフィールドの形式を、そのコーデックのRTPパケット化について規定する必要があります。 スケーラブルなコーデックのための新しいRTPパケット化仕様では、これをどのように行うかを定義すべきです（SHOULD）。 （たとえば、[RFC9628]ではそのように定義しています。） ペイロードが、[RFC9626]で説明されているVideo Frame Marking RTPヘッダー拡張との使用方法も規定している場合、 その構文は、そのヘッダーのTIDフィールドおよびLIDフィールドと同じ方法で定義しなければなりません（MUST）。

4.1. H.264 SVC

4.1. H.264 SVC

[RFC6190] defines temporal, dependency (spatial), and quality scalability modes.

[RFC6190]は、時間、依存関係（空間）、品質のスケーラビリティーモードを定義しています。

Figure 6 shows the format of the layer index fields for H.264 SVC streams. The "R" and "RES" fields MUST be set to zero on transmission and ignored on reception. See Section 1.1.3 of [RFC6190] for details on the dependency_id (DID), quality_id (QID), and temporal_id (TID) fields.

Figure 6に、H.264 SVCストリームのレイヤーインデックスフィールドの形式を示します。 「R」フィールドと「RES」フィールドは、送信時にゼロに設定し、受信時には無視しなければなりません（MUST）。 dependency_id（DID）、quality_id（QID）、temporal_id（TID）の各フィールドの詳細については、[RFC6190]のSection 1.1.3を参照してください。

A dependency or quality layer refresh of a given layer in H.264 SVC can be identified by the I bit (idr_flag) in the extended Network Abstraction Layer (NAL) unit header, present in NAL unit types 14 (prefix NAL unit) and 20 (coded scalable slice). Layer refresh of the base layer can also be identified by its NAL unit type of its coded slices, which is "5" rather than "1". A dependency or quality layer refresh is complete once this bit has been seen on all the appropriate layers (in decoding order) above the current layer index (if any, or beginning from the base layer if not) through the target layer index.

H.264 SVCにおける特定のレイヤーの依存関係レイヤーまたは品質レイヤーのリフレッシュは、 拡張ネットワーク抽象化レイヤー（Network Abstraction Layer：NAL）ユニットヘッダーのIビット（idr_flag）によって識別できます。 このヘッダーは、NALユニットタイプ14（プレフィックスNALユニット）と20（符号化スケーラブルスライス）に存在します。 ベースレイヤーのレイヤーリフレッシュは、その符号化スライスのNALユニットタイプが「1」ではなく「5」であることによっても識別できます。 依存関係レイヤーまたは品質レイヤーのリフレッシュは、現在のレイヤーインデックスより上の（現在のレイヤーインデックスがない場合はベースレイヤーから始まる）、 ターゲットレイヤーインデックスまでのすべての該当するレイヤーで（デコード順に）このビットが確認された時点で完了します。

Note that as the I bit in a Payload Content Scalability Information (PACSI) header is set if the corresponding bit is set in any of the aggregated NAL units it describes; thus, it is not sufficient to identify layer refresh when NAL units of multiple dependency or quality layers are aggregated.

Payload Content Scalability Information（PACSI）ヘッダーのIビットは、 それが記述する集約されたNALユニットのいずれかで対応するビットが設定されていれば設定されることに注意してください。 したがって、複数の依存関係レイヤーまたは品質レイヤーのNALユニットが集約されている場合、このビットだけではレイヤーリフレッシュを識別するのに十分ではありません。

In H.264 SVC, temporal layer refresh information can be determined from various Supplemental Encoding Information (SEI) messages in the bitstream.

H.264 SVCでは、時間レイヤーのリフレッシュ情報は、 ビットストリーム内のさまざまなSupplemental Encoding Information（SEI）メッセージから判断できます。

Whether an H.264 SVC stream is scalably nested can be determined from the Scalability Information SEI message's temporal_id_nesting flag. If this flag is set in a stream's currently applicable Scalability Information SEI, receivers SHOULD NOT send temporal LRR messages for that stream, as every frame is implicitly a temporal layer refresh point. (The Scalability Information SEI message may also be available in the signaling negotiation of H.264 SVC as the sprop-scalability-info parameter.)

H.264 SVCストリームがスケーラブルに入れ子になっているかどうかは、 Scalability Information SEIメッセージのtemporal_id_nestingフラグから判断できます。 ストリームに現在適用されているScalability Information SEIでこのフラグが設定されている場合、 すべてのフレームが暗黙的に時間レイヤーリフレッシュポイントとなるので、 受信者はそのストリームに対して時間レイヤーのLRRメッセージを送信すべきではありません（SHOULD NOT）。 （Scalability Information SEIメッセージは、H.264 SVCのシグナリングネゴシエーションにおいて、sprop-scalability-infoパラメーターとして利用できる場合もあります。）

If a stream's temporal_id_nesting flag is not set, the Temporal Level Switching Point SEI message identifies temporal layer switching points. A temporal layer refresh is satisfied when this SEI message is present in a frame with the target layer index, if the message's delta_frame_num refers to a frame with the requested current layer index. (Alternately, temporal layer refresh can also be satisfied by a complete state refresh, such as an Instantaneous Decoding Refresh (IDR).) Senders that support receiving an LRR for streams that are not temporally nested MUST insert Temporal Level Switching Point SEI messages as appropriate.

ストリームのtemporal_id_nestingフラグが設定されていない場合、 Temporal Level Switching Point SEIメッセージが時間レイヤーの切り替えポイントを識別します。 時間レイヤーのリフレッシュは、ターゲットレイヤーインデックスを持つフレームにこのSEIメッセージが存在し、 かつメッセージのdelta_frame_numが、要求された現在のレイヤーインデックスを持つフレームを参照している場合に満たされます。 （あるいは、Instantaneous Decoding Refresh（IDR）のような完全な状態リフレッシュによっても、時間レイヤーのリフレッシュを満たすことができます。） 時間的に入れ子になっていないストリームに対するLRRの受信をサポートする送信者は、 必要に応じてTemporal Level Switching Point SEIメッセージを挿入しなければなりません（MUST）。

4.2. VP8

4.2. VP8

The [RFC7741] defines temporal scalability modes. It does not support spatial scalability.

[RFC7741]は、時間スケーラビリティーモードを定義しています。 空間スケーラビリティーはサポートしていません。

Figure 7 shows the format of the layer index field for VP8 streams. The "RES" fields MUST be set to zero on transmission and be ignored on reception. See Section 4.2 of [RFC7741] for details on the TID field.

Figure 7に、VP8ストリームのレイヤーインデックスフィールドの形式を示します。 「RES」フィールドは、送信時にゼロに設定し、受信時には無視しなければなりません（MUST）。 TIDフィールドの詳細については、[RFC7741]のSection 4.2を参照してください。

A VP8 layer refresh point can be identified by the presence of the Y bit (see [RFC7741]) in the VP8 payload header. When this bit is set, this and all subsequent frames depend only on the current base temporal layer. On receipt of an LRR for a VP8 stream, a sender that supports LRRs MUST encode the stream so it can set the Y bit in a packet whose temporal layer is at or below the target layer index.

VP8のレイヤーリフレッシュポイントは、VP8ペイロードヘッダー内のYビット（[RFC7741]を参照）の存在によって識別できます。 このビットが設定されている場合、このフレームと後続のすべてのフレームは、現在のベース時間レイヤーにのみ依存します。 VP8ストリームに対するLRRを受信した場合、LRRをサポートする送信者は、 時間レイヤーがターゲットレイヤーインデックス以下であるパケットでYビットを設定できるように、ストリームをエンコードしなければなりません（MUST）。

Note that in VP8, not every layer switch point can be identified by the Y bit since the Y bit implies layer switch of all layers, not just the layer in which it is sent. Thus, the use of an LRR with VP8 can result in some inefficiency in transmission. However, this is not expected to be a major issue for temporal structures in normal use.

VP8では、Yビットは送信されたレイヤーだけでなくすべてのレイヤーのレイヤー切り替えを意味するため、 すべてのレイヤー切り替えポイントをYビットで識別できるわけではないことに注意してください。 したがって、VP8でLRRを使用すると、送信がある程度非効率になる可能性があります。 しかし、通常使用される時間構造では、これが大きな問題になることはないと予想されます。

4.3. H.265

4.3. H.265

The initial version of the [RFC7798] defines temporal scalability, with protocol elements reserved for spatial or other scalability modes (which are expected to be defined in a future version of the specification).

[RFC7798]の初版は、時間スケーラビリティーを定義しており、 空間スケーラビリティーやその他のスケーラビリティーモード（仕様の将来のバージョンで定義されると予想されます）のためにプロトコル要素を予約しています。

Figure 8 shows the format of the layer index field for H.265 streams. The "RES" fields MUST be set to zero on transmission and ignored on reception. See Section 1.1.4 of [RFC7798] for details on the layer ID and TID fields.

Figure 8に、H.265ストリームのレイヤーインデックスフィールドの形式を示します。 「RES」フィールドは、送信時にゼロに設定し、受信時には無視しなければなりません（MUST）。 layer IDフィールドとTIDフィールドの詳細については、[RFC7798]のSection 1.1.4を参照してください。

H.265 streams signal whether they are temporally nested by using the vps_temporal_id_nesting_flag in the Video Parameter Set (VPS) and the sps_temporal_id_nesting_flag in the Sequence Parameter Set (SPS). If this flag is set in a stream's currently applicable VPS or SPS, receivers SHOULD NOT send temporal LRR messages for that stream, as every frame is implicitly a temporal layer refresh point.

H.265ストリームは、ビデオパラメーターセット（Video Parameter Set：VPS）のvps_temporal_id_nesting_flagと、 シーケンスパラメーターセット（Sequence Parameter Set：SPS）のsps_temporal_id_nesting_flagを使用して、時間的に入れ子になっているかどうかを通知します。 ストリームに現在適用されているVPSまたはSPSでこのフラグが設定されている場合、 すべてのフレームが暗黙的に時間レイヤーリフレッシュポイントとなるので、 受信者はそのストリームに対して時間レイヤーのLRRメッセージを送信すべきではありません（SHOULD NOT）。

If a stream's sps_temporal_id_nesting_flag is not set, the NAL unit types 2 to 5 inclusively identify temporal layer switching points. A layer refresh to any higher target temporal layer is satisfied when a NAL unit type of 4 or 5 with TID equal to 1 more than current TID is seen. Alternatively, layer refresh to a target temporal layer can be incrementally satisfied with a NAL unit type of 2 or 3. In this case, given current TID = TO and target TID = TN, layer refresh to TN is satisfied when a NAL unit type of 2 or 3 is seen for TID = T1, then TID = T2, all the way up to TID = TN (note that TN and TO refer to nonce variables in this instance). During this incremental process, layer refresh to TN can be completely satisfied as soon as a NAL unit type of 2 or 3 is seen.

ストリームのsps_temporal_id_nesting_flagが設定されていない場合、 NALユニットタイプ2から5（両端を含む）が時間レイヤーの切り替えポイントを識別します。 任意の上位のターゲット時間レイヤーへのレイヤーリフレッシュは、 現在のTIDより1大きいTIDを持つNALユニットタイプ4または5が確認された時点で満たされます。 あるいは、ターゲット時間レイヤーへのレイヤーリフレッシュは、NALユニットタイプ2または3によって段階的に満たすこともできます。 この場合、現在のTID = TO、ターゲットのTID = TNとすると、 TID = T1、次にTID = T2、と順にTID = TNまで、NALユニットタイプ2または3が確認された時点で、TNへのレイヤーリフレッシュが満たされます （ここでのTNとTOは一時的な変数であることに注意してください）。 この段階的なプロセスの途中でも、NALユニットタイプ2または3が確認され次第、TNへのレイヤーリフレッシュが完全に満たされる場合があります。

Of course, temporal layer refresh can also be satisfied whenever any Intra-Random Access Point (IRAP) NAL unit type (with values 16-23, inclusively) is seen. An IRAP picture is similar to an IDR picture in H.264 (NAL unit type of 5 in H.264) where decoding of the picture can start without any older pictures.

もちろん、時間レイヤーのリフレッシュは、 任意のIntra-Random Access Point（IRAP）NALユニットタイプ（値16〜23、両端を含む）が確認されたときにも満たされます。 IRAPピクチャーは、H.264のIDRピクチャー（H.264ではNALユニットタイプ5）に似ており、 それより古いピクチャーなしでそのピクチャーのデコードを開始できます。

In the (future) H.265 payloads that support spatial scalability, a spatial-layer refresh of a specific layer can be identified by NAL units with the requested layer ID and NAL unit types between 16 and 21, inclusive. A dependency or quality layer refresh is complete once NAL units of this type have been seen on all the appropriate layers (in decoding order) above the current layer index (if any, or beginning from the base layer if not) through the target layer index.

空間スケーラビリティーをサポートする（将来の）H.265ペイロードでは、 特定のレイヤーの空間レイヤーリフレッシュは、要求されたレイヤーIDを持ち、NALユニットタイプが16から21（両端を含む）のNALユニットによって識別できます。 依存関係レイヤーまたは品質レイヤーのリフレッシュは、現在のレイヤーインデックスより上の（現在のレイヤーインデックスがない場合はベースレイヤーから始まる）、 ターゲットレイヤーインデックスまでのすべての該当するレイヤーで（デコード順に）このタイプのNALユニットが確認された時点で完了します。

5. Usage with Different Scalability Transmission Mechanisms

5. さまざまなスケーラビリティー伝送メカニズムでの使用

Several different mechanisms are defined for how scalable streams can be transmitted in RTP. Section 3.7 of [RFC7656] defines three mechanisms: Single RTP stream on a Single media Transport (SRST), Multiple RTP streams on a Single media Transport (MRST), and Multiple RTP streams on Multiple media Transports (MRMT).

RTPでスケーラブルなストリームをどのように伝送できるかについて、いくつかの異なるメカニズムが定義されています。 [RFC7656]のSection 3.7は、 3つのメカニズムを定義しています。 単一メディアトランスポート上の単一RTPストリーム（Single RTP stream on a Single media Transport：SRST）、 単一メディアトランスポート上の複数RTPストリーム（Multiple RTP streams on a Single media Transport：MRST）、 複数メディアトランスポート上の複数RTPストリーム（Multiple RTP streams on Multiple media Transports：MRMT）です。

The LRR message is applicable to all these mechanisms. For MRST and MRMT mechanisms, the "media source" field of the LRR FCI is set to the SSRC of the RTP stream containing the layer indicated by the Current Layer Index (if "C" is 1) or the stream containing the base encoded stream (if "C" is 0). For MRMT, the LRR message is sent on the RTP session on which this stream is sent. On receipt, the sender MUST refresh all the layers requested in the stream, simultaneously in decode order.

LRRメッセージは、これらすべてのメカニズムに適用できます。 MRSTとMRMTのメカニズムでは、LRR FCIの「media source」フィールドには、 Current Layer Indexが示すレイヤーを含むRTPストリーム（「C」が1の場合）、 またはベースのエンコードされたストリームを含むストリーム（「C」が0の場合）のSSRCを設定します。 MRMTでは、LRRメッセージは、このストリームが送信されるRTPセッション上で送信されます。 受信時に、送信者は、ストリーム内で要求されたすべてのレイヤーを、デコード順で同時にリフレッシュしなければなりません（MUST）。

6. SDP Definitions

6. SDPの定義

Section 7 of [RFC5104] defines Session Description Protocol (SDP) procedures for indicating and negotiating support for Codec Control Messages (CCM) in SDP. This document extends this with a new codec control command, "lrr", which indicates support of the LRR.

[RFC5104]のSection 7は、 SDPでコーデック制御メッセージ（Codec Control Messages：CCM）のサポートを示し、ネゴシエーションするためのセッション記述プロトコル（Session Description Protocol：SDP）の手順を定義しています。 この文書は、これを新しいコーデック制御コマンド「lrr」で拡張します。 このコマンドはLRRのサポートを示します。

Figure 9 gives a formal [RFC5234] showing this grammar extension, extending the grammar defined in [RFC5104].

Figure 9は、 [RFC5104]で定義されている文法を拡張する、 この文法拡張を示す形式的な[RFC5234]を示します。

The Offer-Answer considerations defined in Section 7.2 of [RFC5104] apply.

[RFC5104]のSection 7.2で定義されているオファー・アンサーに関する考慮事項が適用されます。

7. Security Considerations

7. セキュリティーに関する考慮事項

All the security considerations of [RFC5104] apply to LRR feedback packets as well. Additionally, media senders receiving LRR feedback packets MUST validate that the payload types and layer indices they are receiving are valid for the stream they are currently sending, and discard the requests if not.

[RFC5104]のセキュリティーに関する考慮事項はすべて、LRRフィードバックパケットにも適用されます。 さらに、LRRフィードバックパケットを受信するメディア送信者は、 受信したペイロードタイプとレイヤーインデックスが、現在送信しているストリームに対して有効であることを検証し、 有効でなければ要求を破棄しなければなりません（MUST）。
