IPv6 Options for In Situ Operations, Administration, and Maintenance (IOAM)

RFC 9486

In Situ Operations, Administration, and Maintenance（IOAM）のためのIPv6オプション

Abstract

概要

In situ Operations, Administration, and Maintenance (IOAM) records operational and telemetry information in the packet while the packet traverses a path between two points in the network. This document outlines how IOAM Data-Fields are encapsulated in IPv6.

In situ Operations, Administration, and Maintenance（IOAM）は、パケットがネットワーク内の2点間のパスを通過する間に、運用情報とテレメトリー情報をパケット内に記録します。 この文書は、IOAMデータフィールド（IOAM Data-Fields）をIPv6でカプセル化する方法の概要を示します。

1. Introduction

1. はじめに

In situ Operations, Administration, and Maintenance (IOAM) records operational and telemetry information in the packet while the packet traverses a path between two points in the network. IOAM concepts and associated nomenclature as well as IOAM Data-Fields are defined in [RFC9197]. This document outlines how IOAM Data-Fields are encapsulated in IPv6 [RFC8200] and discusses deployment requirements for networks that use IPv6-encapsulated IOAM Data-Fields.

In situ Operations, Administration, and Maintenance（IOAM）は、パケットがネットワーク内の2点間のパスを通過する間に、運用情報とテレメトリー情報をパケット内に記録します。 IOAMの概念と関連する用語、およびIOAMデータフィールドは、[RFC9197]で定義されています。 この文書は、IOAMデータフィールドをIPv6 [RFC8200]でカプセル化する方法の概要を示し、IPv6でカプセル化されたIOAMデータフィールドを使用するネットワークの展開要件について説明します。

The terms "encapsulation" and "decapsulation" are used in this document in the same way as in [RFC9197]: An IOAM encapsulating node incorporates one or more IOAM Option-Types into packets that IOAM is enabled for.

この文書では、「カプセル化（encapsulation）」と「カプセル化解除（decapsulation）」という用語を、[RFC9197]と同じ意味で使用します。 すなわち、IOAMカプセル化ノードは、IOAMが有効になっているパケットに1つ以上のIOAMオプションタイプ（IOAM Option-Types）を組み込みます。

3. In situ OAM Metadata Transport in IPv6

3. IPv6におけるIn situ OAMメタデータの転送

IOAM in IPv6 is used to enhance diagnostics of IPv6 networks. It complements other mechanisms designed to enhance diagnostics of IPv6 networks, such as the "IPv6 Performance and Diagnostic Metrics (PDM) Destination Option" described in [RFC8250].

IPv6におけるIOAMは、IPv6ネットワークの診断を強化するために使用されます。 IPv6におけるIOAMは、[RFC8250]で説明されている「IPv6 Performance and Diagnostic Metrics (PDM) Destination Option」など、IPv6ネットワークの診断を強化するために設計された他のメカニズムを補完します。

At the time this document was written, several implementations of IOAM for IPv6 exist, e.g., IOAM for IPv6 in the Linux Kernel (supported from Kernel version 5.15 onward, IPv6 IOAM in Linux Kernel) and IOAM for IPv6 in Vector Packet Processing (VPP).

この文書の執筆時点で、IPv6向けのIOAMの実装がいくつか存在します。 たとえば、LinuxカーネルにおけるIPv6向けのIOAM（カーネルバージョン5.15以降でサポート、 LinuxカーネルにおけるIPv6 IOAM）や、 Vector Packet Processing（VPP）におけるIPv6向けのIOAMがあります。

IOAM Data-Fields can be encapsulated with two types of extension headers in IPv6 packets -- either the hop-by-hop options header or the destination options header. Multiple options with the same option type MAY appear in the same hop-by-hop options or destination options header with distinct content.

IOAMデータフィールドは、IPv6パケット内の2種類の拡張ヘッダー、すなわちホップバイホップオプションヘッダーまたは宛先オプションヘッダーのいずれかでカプセル化できます。 同じオプションタイプを持つ複数のオプションが、異なる内容で、同じホップバイホップオプションヘッダーまたは宛先オプションヘッダーに現れてもよいです（MAY）。

An IPv6 packet carrying IOAM data in an extension header can have other extension headers, compliant with [RFC8200].

拡張ヘッダー内でIOAMデータを運ぶIPv6パケットは、[RFC8200]に準拠した他の拡張ヘッダーを持つことができます。

All the IOAM IPv6 options defined here have alignment requirements. Specifically, they all require alignment on multiples of 4 bytes. This ensures that fields specified in [RFC9197] are aligned at a multiple-of-4 offset from the start of the hop-by-hop and destination options header.

ここで定義するすべてのIOAM IPv6オプションには、アラインメント要件があります。 具体的には、いずれも4バイトの倍数でのアラインメントを必要とします。 これにより、[RFC9197]で規定されているフィールドが、ホップバイホップオプションヘッダーおよび宛先オプションヘッダーの先頭から4の倍数のオフセットにアラインされることが保証されます。

IPv6 options can have a maximum length of 255 octets. Consequently, the total length of IOAM Option-Types including all data fields is also limited to 255 octets when encapsulated into IPv6.

IPv6オプションの最大長は255オクテットです。 したがって、IPv6にカプセル化される場合、すべてのデータフィールドを含むIOAMオプションタイプの全長も255オクテットに制限されます。

4. IOAM Deployment in IPv6 Networks

4. IPv6ネットワークにおけるIOAMの展開

4.1. Considerations for IOAM Deployment and Implementation in IPv6 Networks

4.1. IPv6ネットワークにおけるIOAMの展開と実装に関する考慮事項

IOAM deployments in IPv6 networks MUST take the following considerations and requirements into account.

IPv6ネットワークにおけるIOAMの展開では、次の考慮事項と要件を考慮しなければなりません（MUST）。

  1. IOAM MUST be deployed in an IOAM-Domain. An IOAM-Domain is a set of nodes that use IOAM. An IOAM-Domain is bounded by its perimeter or edge. The set of nodes forming an IOAM-Domain may be connected to the same physical infrastructure (e.g., a service provider's network). They may also be remotely connected to each other (e.g., an enterprise VPN or an overlay). It is expected that all nodes in an IOAM-Domain are managed by the same administrative entity. Please refer to [RFC9197] for more details on IOAM-Domains.
  2. Implementations of IOAM MUST ensure that the addition of IOAM Data-Fields does not alter the way routers forward packets or the forwarding decisions they make. Packets with added IOAM information must follow the same path within the domain as an identical packet without IOAM information would, even in the presence of Equal-Cost Multipath (ECMP). This behavior is important for deployments where IOAM Data-Fields are only added "on-demand". Implementations of IOAM MUST ensure that ECMP behavior for packets with and without IOAM Data-Fields is the same. In order for IOAM to work in IPv6 networks, IOAM MUST be explicitly enabled per interface on every node within the IOAM-Domain. Unless a particular interface is explicitly enabled (i.e., explicitly configured) for IOAM, a router MUST ignore IOAM Options.
  3. In order to maintain the integrity of packets in an IOAM-Domain, the Maximum Transmission Unit (MTU) of transit routers and switches must be configured to a value that does not lead to an "ICMP Packet Too Big" error message being sent to the originator and the packet being dropped. The PMTU tolerance range must be identified, and IOAM encapsulation operations or data field insertion must not exceed this range. Control of the MTU is critical to the proper operation of IOAM. The PMTU tolerance must be identified through configuration, and IOAM operations must not exceed the packet size beyond PMTU.
  4. [RFC8200] precludes insertion of IOAM data directly into the original IPv6 header of in-flight packets. IOAM deployments that do not encapsulate/decapsulate IOAM on the host but desire to encapsulate/decapsulate IOAM on transit nodes MUST add an additional IPv6 header to the original packet. IOAM data is added to this additional IPv6 header.
  1. IOAMは、IOAMドメイン（IOAM-Domain）内で展開しなければなりません（MUST）。 IOAMドメインは、IOAMを使用するノードの集合です。 IOAMドメインは、その周辺部（perimeter）またはエッジによって境界が定められます。 IOAMドメインを形成するノードの集合は、同じ物理インフラストラクチャー（たとえば、サービスプロバイダーのネットワーク）に接続されている場合があります。 また、互いにリモートで接続されている場合もあります（たとえば、企業のVPNやオーバーレイ）。 IOAMドメイン内のすべてのノードは、同じ管理エンティティーによって管理されることが想定されています。 IOAMドメインの詳細については、[RFC9197]を参照してください。
  2. IOAMの実装は、IOAMデータフィールドの追加によって、ルーターがパケットを転送する方法や、ルーターが行う転送の決定が変わらないことを保証しなければなりません（MUST）。 IOAM情報が追加されたパケットは、等コストマルチパス（Equal-Cost Multipath、ECMP）が存在する場合であっても、IOAM情報を持たない同一のパケットがたどるのと同じパスをドメイン内でたどらなければなりません。 この振る舞いは、IOAMデータフィールドが「オンデマンド」でのみ追加される展開にとって重要です。 IOAMの実装は、IOAMデータフィールドを持つパケットと持たないパケットとで、ECMPの振る舞いが同じであることを保証しなければなりません（MUST）。 IPv6ネットワークでIOAMを機能させるためには、IOAMドメイン内のすべてのノードで、インターフェイスごとにIOAMを明示的に有効にしなければなりません（MUST）。 特定のインターフェイスでIOAMが明示的に有効化（つまり、明示的に設定）されていない限り、ルーターはIOAMオプションを無視しなければなりません（MUST）。
  3. IOAMドメイン内のパケットの完全性を維持するために、中継ルーターおよびスイッチの最大転送単位（Maximum Transmission Unit、MTU）は、送信元への「ICMP Packet Too Big」エラーメッセージの送信とパケットの破棄を引き起こさない値に設定されなければなりません。 PMTUの許容範囲を特定し、IOAMのカプセル化操作やデータフィールドの挿入がこの範囲を超えないようにしなければなりません。 MTUの制御は、IOAMが適切に動作するために極めて重要です。 PMTUの許容範囲は設定によって特定されなければならず、IOAMの操作によってパケットサイズがPMTUを超えてはなりません。
  4. [RFC8200]は、転送中のパケットの元のIPv6ヘッダーにIOAMデータを直接挿入することを禁じています。 ホストではIOAMのカプセル化／カプセル化解除を行わず、中継ノードでIOAMのカプセル化／カプセル化解除を行いたいIOAMの展開では、元のパケットに追加のIPv6ヘッダーを付加しなければなりません（MUST）。 IOAMデータは、この追加のIPv6ヘッダーに追加されます。

4.2. IOAM-Domains Bounded by Hosts

4.2. ホストを境界とするIOAMドメイン

For deployments where the IOAM-Domain is bounded by hosts, hosts will perform the operation of IOAM Data-Field encapsulation and decapsulation, i.e., hosts will place the IOAM Data-Fields directly in the IPv6 header or remove the IOAM Data-Fields directly from the IPv6 header. IOAM data is carried in IPv6 packets as hop-by-hop or destination options as specified in this document.

IOAMドメインの境界がホストである展開では、ホストがIOAMデータフィールドのカプセル化とカプセル化解除の操作を行います。 つまり、ホストはIOAMデータフィールドをIPv6ヘッダーに直接配置したり、IPv6ヘッダーから直接削除したりします。 IOAMデータは、この文書で規定するとおり、ホップバイホップオプションまたは宛先オプションとしてIPv6パケットで運ばれます。

4.3. IOAM-Domains Bounded by Network Devices

4.3. ネットワーク機器を境界とするIOAMドメイン

For deployments where the IOAM-Domain is bounded by network devices, network devices such as routers form the edge of an IOAM-Domain. Network devices will perform the operation of IOAM Data-Field encapsulation and decapsulation. Network devices will encapsulate IOAM Data-Fields in an additional, outer, IPv6 header that carries the IOAM Data-Fields.

IOAMドメインの境界がネットワーク機器である展開では、ルーターなどのネットワーク機器がIOAMドメインのエッジを形成します。 ネットワーク機器が、IOAMデータフィールドのカプセル化とカプセル化解除の操作を行います。 ネットワーク機器は、IOAMデータフィールドを運ぶ追加の外側のIPv6ヘッダーに、IOAMデータフィールドをカプセル化します。

5. Security Considerations

5. セキュリティーに関する考慮事項

This document describes the encapsulation of IOAM Data-Fields in IPv6. For general IOAM security considerations, see [RFC9197]. Security considerations of the specific IOAM Data-Fields for each case (i.e., Trace, POT, and E2E) are also described and defined in [RFC9197].

この文書は、IPv6におけるIOAMデータフィールドのカプセル化について説明します。 IOAMのセキュリティーに関する一般的な考慮事項については、[RFC9197]を参照してください。 それぞれの場合（つまり、トレース、POT、E2E）における特定のIOAMデータフィールドのセキュリティーに関する考慮事項も、[RFC9197]で説明および定義されています。

As this document describes new options for IPv6, the security considerations of [RFC8200] and [RFC8250] apply.

この文書はIPv6の新しいオプションについて説明するので、[RFC8200]と[RFC8250]のセキュリティーに関する考慮事項が適用されます。

From a network-protection perspective, there is an assumed trust model such that any node that adds IOAM to a packet, removes IOAM from a packet, or modifies IOAM Data-Fields of a packet is assumed to be allowed to do so. By default, packets that include IPv6 extension headers with IOAM information MUST NOT be leaked through the boundaries of the IOAM-Domain.

ネットワーク保護の観点からは、パケットにIOAMを追加するノード、パケットからIOAMを削除するノード、またはパケットのIOAMデータフィールドを変更するノードは、いずれもそうすることが許可されているとみなすという信頼モデルが前提とされています。 デフォルトでは、IOAM情報を含むIPv6拡張ヘッダーを持つパケットを、IOAMドメインの境界を越えて漏洩させてはなりません（MUST NOT）。

IOAM-Domain boundary routers MUST filter any incoming traffic from outside the IOAM-Domain that contains IPv6 extension headers with IOAM information. IOAM-Domain boundary routers MUST also filter any outgoing traffic leaving the IOAM-Domain that contains IPv6 extension headers with IOAM information.

IOAMドメインの境界ルーターは、IOAMドメインの外部から入ってくるトラフィックのうち、IOAM情報を含むIPv6拡張ヘッダーを持つものをすべてフィルターしなければなりません（MUST）。 また、IOAMドメインの境界ルーターは、IOAMドメインから出ていくトラフィックのうち、IOAM情報を含むIPv6拡張ヘッダーを持つものもすべてフィルターしなければなりません（MUST）。

In the general case, an IOAM node only adds, removes, or modifies an IPv6 extension header with IOAM information, if the directive to do so comes from a trusted source and the directive is validated.

一般的な場合、IOAMノードがIOAM情報を含むIPv6拡張ヘッダーを追加、削除、または変更するのは、そうする指示が信頼できる送信元から来ており、かつその指示が検証された場合だけです。

Problems may occur if the above behaviors are not implemented or if the assumed trust model is violated (e.g., through a security breach). In addition to the security considerations discussed in [RFC9197], the security considerations associated with IPv6 extension headers listed in [RFC9098] apply.

上記の振る舞いが実装されていない場合や、前提とされている信頼モデルが（たとえば、セキュリティー侵害によって）破られた場合には、問題が発生する可能性があります。 [RFC9197]で議論されているセキュリティーに関する考慮事項に加えて、[RFC9098]に列挙されているIPv6拡張ヘッダーに関連するセキュリティーに関する考慮事項が適用されます。

5.1. Applicability of Authentication Header (AH)

5.1. 認証ヘッダー（AH）の適用可能性

The network devices in an IOAM-Domain are trusted to add, update, and remove IOAM options according to the constraints specified in [RFC8200]. IOAM-Domain does not rely on the AH as defined in [RFC4302] to secure IOAM options. The use of IOAM options with AH and its processing are not defined in this document. Future documents may define the use of IOAM with AH and its processing.

IOAMドメイン内のネットワーク機器は、[RFC8200]で規定されている制約に従って、IOAMオプションを追加、更新、削除することを信頼されています。 IOAMドメインは、IOAMオプションを保護するために、[RFC4302]で定義されているAHに依存しません。 AHとともにIOAMオプションを使用することとその処理は、この文書では定義しません。 AHとともにIOAMを使用することとその処理は、将来の文書で定義される可能性があります。
