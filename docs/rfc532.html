RFC 532

UCSD-CC Server-FTP Facility

RFC 532

UCSD-CCのServer-FTP機能

1.0. Introduction

1.0. はじめに

The UCSD Computer Center is a service site that must support itself by charging for the usage of its facilities. Because of this, the prospective user of our Server-FTP must supply a valid usercode (USER) and password (PASS) before any further FTP commands are accepted.

UCSD計算機センター（UCSD Computer Center）は、施設の利用に料金を課すことで自らを支えなければならないサービスサイトです。そのため、私たちのServer-FTPを利用しようとするユーザーは、それ以降のFTPコマンドが受け付けられる前に、有効なユーザーコード（USER）とパスワード（PASS）を提示しなければなりません。

Through FTP, you are allowed to access or store files on our disk or on any of our 7 or 9-track tape drives. Each individual file transfer is handled by a separate process on the B6700 and the user is charged for the processor, I/O, core, and (if any) tape charges incurred by this process (note that these charges are quite minimal). Each of these transfer processes is given a separate "job" number and is therefore billed separately for each transfer by our accounting system.

FTPを通じて、私たちのディスク、または7トラックや9トラックのどのテープドライブにあるファイルにもアクセスしたり、ファイルを格納したりできます。個々のファイル転送はB6700上の別々のプロセスで処理され、ユーザーには、そのプロセスで発生したプロセッサー、I/O、コア、および（もしあれば）テープの料金が課金されます（これらの料金はごくわずかであることに注意してください）。これらの転送プロセスにはそれぞれ別々の「ジョブ」番号が与えられるので、私たちの課金システムによって転送ごとに別々に請求されます。

Please note that we have implemented FTP as defined in RFC# 354 (July 8, 1972) except as noted.

私たちは、注記した点を除き、RFC# 354（1972年7月8日）で定義されているとおりにFTPを実装していることに注意してください。

2.0. FTP Commands

2.0. FTPコマンド

(1) USER
As mentioned, you must supply a legal, known, UCSD--CC user-code. Following which, the "230" message will be given, asking for the corresponding password.
(2) PASS
After the 'USER' command is accepted, you must then enter the PASS command giving the corresponding password. If the usercode and password are of correct form, if they match, if there is money in your account, if your account is active, and if you are authorized for "Q1" service, then you will be properly logged-on and the "230" response will be returned.
(3) BYTE
We allow only the (default) byte-size of "8" - all others will be rejected.
(4) MODE
We only allow the (default) mode of "S" (Stream) - all others will be rejected
(5) TYPE
We allow "A" (ASCII) and "I" (Image) types - all others will be rejected. As in standard-FTP, "A" is default.
(6) STRU
We allow both "F" (file) and "R" (Record) structuring. Record-structuring is meaningful only in ASCII/Stream, where CRLF is used as End-of-Line. When using Record-structuring in a STOR to us, if an incoming record is longer than the "MAXRECSIZE" of the designated B6700 file, then we close the data connection, issue a reject message, and abort the local (B6700) transfer process. If a record of incoming data is shorter than the specified MAXRECSIZE of the file, then the record is filled-out with blanks in type-ASCII or with nulls (0) in type-Image. With Image, of course, this applies only to the last record of the B6700 file. As in standard-FTP, "F" is default.
(7) ALLO

We have taken the liberty with the FTP-protocol of using the "ALLO" command to enable the user to designate the B6700 "file-attributes" of his UCSD file. The FTP-standard form of ALLO is ignored (i.e. "ALLO n", where 'n' is some integer), although a "200" response will be returned in this case. Our "special" form is where the ALLO verb is immediately followed by a "#", which is in turn followed by a parenthesized list of standard B6700 file attributes as used on B6700 "label-equate" cards. Following is an example of this usage;

      ALLO #(KIND=TAPE9,MAXRECSIZE=10,MYUSE=OUT,TITLE=XYZ)

If this form of the ALLO command is not given prior to a STOR, then the file will have the name given prior in the STOR command and will have the same characteristics as a standard "CANDE" type-DATA disk file (i.e. where (MAXRECSIZE=14, BLOCKSIZE=420, AREAS=15, AREASIZE=450)). If no special ALLO is given preceding a RETR, then the file attributes are those of the file itself as it exists on the disk and are not altered. In cases where the special ALLO is given prior to a transfer, the name of the file is determined by the TITLE attribute and the name given as the pathname of the STOR or RETR command is ignored. If no TITLE is specified in an ALLO, then the internal filename of "LOCALFILE" is used. With the "file-attribute-list" form of the ALLO command, the user has much of the same liberty to govern file characteristics as he does in using a "label-equate" card with a normal B6700 job. For information concerning the available file attributes and their possible values, please contact the UCSD-CC consultant. Additionally, you must remember that when doing a STOR to a tape at UCSD, you must specify MYUSE=OUT in the file-attribute list of the ALLO command. Also, when transferring to or from tapes at UCSD, you must make prior arrangements with our operators (over TELNET) to locate and mount the tape. We will soon implement a means whereby you may communicate with the operators directly through FTP.

(8) XLINE
This special command sets Record-structuring in our Server-FTP without the foreign user having to use a STRU R command (which may be rejected by his own host system). This is specifically useful when transferring text files between UCSD and TENEX's (which do not implement Record-structuring) - i.e., if we are sending, we will append CRLF's to the end of each line of text (we do not store these in the file) and will store a line upon receiving data when a CRLF is seen, stripping the CRLF. Entering "XLINE OFF" will restore File-structuring on our end.
(9) RETR , STOR
As specified in standard-FTP except as modified by the "special" ALLO command (see part (7)).
(10) APPE
Not implemented at this time, but will be in near future.
(11) DELE , RNTO , RNFR

Not implemented. It is suggested that to perform these functions, the user log to our TELNET server ("CANDE"), invoke the "LIBMAINT" program (simply type LIBMAINT), and say;

      REMOVE file-name
          or
      CHANGE file-name-1 TO file-name-2

Say BYE in order to exit LIBMAINT.

(12) ABOR, BYE
As specified in standard-FTP; except that, until further notice, a BYE given while a transfer is in progress will not be queued for action following the transfer.
(1) USER
前述のとおり、正当で既知のUCSD--CCユーザーコードを提示しなければなりません。その後、「230」メッセージが返され、対応するパスワードを求められます。
(2) PASS
「USER」コマンドが受け付けられたら、次にPASSコマンドを入力して、対応するパスワードを提示しなければなりません。ユーザーコードとパスワードが正しい形式であり、それらが一致し、アカウントに残高があり、アカウントが有効であり、「Q1」サービスの利用が認可されていれば、正しくログオンされ、「230」応答が返されます。
(3) BYTE
（デフォルトの）バイトサイズ「8」だけを許可します。それ以外はすべて拒否されます。
(4) MODE
（デフォルトの）モード「S」（Stream）だけを許可します。それ以外はすべて拒否されます
(5) TYPE
「A」（ASCII）と「I」（Image）のタイプを許可します。それ以外はすべて拒否されます。標準のFTPと同じく、デフォルトは「A」です。
(6) STRU
「F」（file）と「R」（Record）の両方の構造化を許可します。レコード構造化（Record-structuring）が意味を持つのはASCII/Streamの場合だけで、その場合はCRLFが行末として使われます。私たちに対するSTORでレコード構造化を使う場合、受信したレコードが指定されたB6700ファイルの「MAXRECSIZE」よりも長ければ、データ接続を閉じ、拒否メッセージを発行し、ローカル（B6700）の転送プロセスを中止します。受信データのレコードがファイルに指定されたMAXRECSIZEよりも短ければ、そのレコードは、ASCIIタイプでは空白で、Imageタイプではヌル（0）で埋められます。もちろん、Imageの場合、これが当てはまるのはB6700ファイルの最後のレコードだけです。標準のFTPと同じく、デフォルトは「F」です。
(7) ALLO

私たちはFTPプロトコルを自由に解釈して、ユーザーがUCSDのファイルのB6700「ファイル属性」を指定できるように「ALLO」コマンドを使うことにしました。FTP標準の形式のALLO（つまり「ALLO n」。'n'は何らかの整数）は無視されますが、この場合も「200」応答が返されます。私たちの「特別な」形式では、ALLO動詞の直後に「#」が続き、さらにその後に、B6700の「label-equate」カードで使われる標準のB6700ファイル属性を括弧で囲んだリストが続きます。この使い方の例を次に示します。

      ALLO #(KIND=TAPE9,MAXRECSIZE=10,MYUSE=OUT,TITLE=XYZ)

STORの前にこの形式のALLOコマンドが与えられなかった場合、ファイルは先にSTORコマンドで与えられた名前を持ち、標準的な「CANDE」のtype-DATAディスクファイルと同じ特性（つまり(MAXRECSIZE=14, BLOCKSIZE=420, AREAS=15, AREASIZE=450)）を持ちます。RETRの前に特別なALLOが与えられなかった場合、ファイル属性はディスク上に存在するファイル自身のものとなり、変更されません。転送の前に特別なALLOが与えられた場合、ファイルの名前はTITLE属性によって決まり、STORまたはRETRコマンドのパス名として与えられた名前は無視されます。ALLOでTITLEが指定されていなければ、内部ファイル名「LOCALFILE」が使われます。ALLOコマンドの「ファイル属性リスト」形式を使うと、ユーザーは、通常のB6700ジョブで「label-equate」カードを使う場合とほぼ同じように、ファイルの特性を自由に決められます。利用できるファイル属性とその取りうる値については、UCSD-CCのコンサルタントに問い合わせてください。また、UCSDのテープにSTORを行う場合は、ALLOコマンドのファイル属性リストにMYUSE=OUTを指定しなければならないことを覚えておいてください。さらに、UCSDのテープとの間で転送を行う場合は、テープを探してマウントしてもらえるように、事前に（TELNETを通じて）私たちのオペレーターと打ち合わせておかなければなりません。近いうちに、FTPを通じて直接オペレーターと連絡を取れる手段を実装する予定です。

(8) XLINE
この特別なコマンドは、外部のユーザーがSTRU Rコマンド（そのユーザー自身のホストシステムによって拒否されるかもしれません）を使わなくても、私たちのServer-FTPでレコード構造化を設定します。これは、UCSDと（レコード構造化を実装していない）TENEXとの間でテキストファイルを転送する場合に特に役立ちます。つまり、私たちが送信する場合はテキストの各行の末尾にCRLFを付加し（ファイルにはCRLFを格納していません）、データを受信する場合はCRLFを見つけた時点でCRLFを取り除いて1行を格納します。「XLINE OFF」を入力すると、私たちの側のファイル構造化が元に戻ります。
(9) RETR , STOR
「特別な」ALLOコマンド（パート(7)を参照）によって変更される点を除き、標準のFTPで規定されているとおりです。
(10) APPE
現時点では実装されていませんが、近いうちに実装する予定です。
(11) DELE , RNTO , RNFR

実装されていません。これらの機能を実行するには、ユーザーが私たちのTELNETサーバー（「CANDE」）にログインし、「LIBMAINT」プログラムを起動して（単にLIBMAINTと入力します）、次のように入力することをお勧めします。

      REMOVE file-name
          or
      CHANGE file-name-1 TO file-name-2

LIBMAINTを終了するには、BYEと入力します。

(12) ABOR, BYE
標準のFTPで規定されているとおりです。ただし、追って通知するまでは、転送の進行中に与えられたBYEは、転送後に処理されるようキューに入れられることはありません。

Any commands not mentioned above are not yet implemented.

上で言及していないコマンドは、まだ実装されていません。
