The BagIt File Packaging Format (V1.0)

RFC 8493

BagItファイルパッケージング形式（V1.0）

Abstract

概要

This document describes BagIt, a set of hierarchical file layout conventions for storage and transfer of arbitrary digital content. A "bag" has just enough structure to enclose descriptive metadata "tags" and a file "payload" but does not require knowledge of the payload's internal semantics. This BagIt format is suitable for reliable storage and transfer.

この文書では、任意のデジタルコンテンツを保管および転送するための、階層的なファイル配置の規約の集合であるBagItについて説明します。 「バッグ」は、記述的なメタデータである「タグ」とファイルの「ペイロード」を包むのに十分なだけの構造を持ちますが、ペイロード内部のセマンティクスについての知識は必要としません。 このBagIt形式は、信頼性の高い保管と転送に適しています。

1. Introduction

1. はじめに

1.1. Purpose

1.1. 目的

BagIt is a set of hierarchical file layout conventions designed to support storage and transfer of arbitrary digital content. A "bag" consists of a directory containing the payload files and other accompanying metadata files known as "tag" files. The "tags" are metadata files intended to facilitate and document the storage and transfer of the bag. Processing a bag does not require any understanding of the payload file contents, and the payload files can be accessed without processing the BagIt metadata.

BagItは、任意のデジタルコンテンツの保管と転送をサポートするために設計された、階層的なファイル配置の規約の集合です。 「バッグ」は、ペイロードファイルと、それに付随する「タグ」ファイルと呼ばれるその他のメタデータファイルを含むディレクトリーで構成されます。 「タグ」は、バッグの保管と転送を容易にし、それを記録することを目的としたメタデータファイルです。 バッグを処理するのにペイロードファイルの内容を理解する必要はなく、ペイロードファイルにはBagItのメタデータを処理せずにアクセスできます。

The name, BagIt, is inspired by the "enclose and deposit" method [ENCDEP], sometimes referred to as "bag it and tag it". BagIt differs from serialized archival formats such as MIME, TAR, or ZIP in two general areas:

BagItという名前は、「bag it and tag it（バッグに入れてタグを付ける）」とも呼ばれる「enclose and deposit（包んで預ける）」方式[ENCDEP]に由来しています。 BagItは、MIME、TAR、ZIPなどのシリアル化されたアーカイブ形式とは、大きく2つの点で異なります。

  1. Strong integrity assurances. The format supports cryptographic-quality hash algorithms (see Section 2.4) and allows for in-place upgrades to add additional manifests using stronger algorithms without breaking backwards compatibility. This provides high levels of confidence against data corruption, but it is not designed to be secure against active attacks.
  2. Direct file access. Because BagIt specifies an actual filesystem hierarchy rather than a serialized representation of one, files can be accessed using standard operating system utilities, implementations do not need to process a potentially large archival file to extract a subset of data, and the format imposes no size limits for either individual files or a bag.
  1. 強力な完全性の保証。 この形式は暗号学的な品質のハッシュアルゴリズムをサポートしており（セクション2.4を参照）、後方互換性を損なうことなく、より強力なアルゴリズムを使用したマニフェストを追加するインプレースアップグレードが可能です。 これにより、データの破損に対して高いレベルの信頼性が得られますが、能動的な攻撃に対して安全であるようには設計されていません。
  2. ファイルへの直接アクセス。 BagItはファイルシステム階層をシリアル化した表現ではなく、実際のファイルシステム階層を規定しているので、標準的なオペレーティングシステムのユーティリティーを使用してファイルにアクセスでき、実装はデータの一部を取り出すために巨大になりうるアーカイブファイルを処理する必要がありません。 また、この形式は個々のファイルにもバッグにもサイズの制限を課しません。

BagIt is widely used for preserving digital assets originating from different domains. Organizations involved in digital preservation with BagIt include the Library of Congress, Dryad Data Repository, NSF DataONE, and the Rockefeller Archive Center. Software implementations are available for many languages, including Python, Ruby, Java, Perl, and PHP. It is also used in the libraries of many universities, such as Cornell, Purdue, Stanford, Ghent University, New York University, and the University of California.

BagItは、さまざまな分野に由来するデジタル資産の保存に広く使用されています。 BagItを用いたデジタル保存に関わっている組織には、米国議会図書館（Library of Congress）、Dryad Data Repository、NSF DataONE、Rockefeller Archive Centerなどがあります。 ソフトウェア実装は、Python、Ruby、Java、Perl、PHPを含む多くの言語で利用できます。 また、Cornell、Purdue、Stanford、Ghent University、New York University、University of Californiaなど、多くの大学の図書館でも使用されています。

1.3. Terminology

1.3. 用語

The following terms have precise definitions as used in this document:

この文書で使用する以下の用語は、厳密な定義を持ちます。

bag:
A set of opaque files contained within the structure defined by this document.
bag declaration:
The file required to be in all bags conforming to this document. Contains values necessary to process the rest of a bag. See Section 2.1.1.
bag checksum algorithm:
The name of a cryptographic checksum algorithm that has been normalized for use in a manifest or tag manifest file name (e.g., "sha512") as described in Section 2.4.
manifest:
A tag file that maps filepaths to checksums. A manifest can be a payload manifest (see Section 2.1.3) or a tag manifest (see Section 2.2.1).
payload:
The data encapsulated by the bag as a set of named files, which may be organized in subdirectories. The contents of the payload files are opaque to this document, and, with respect to BagIt processing, are always considered as sequences of uninterpreted octets. See Section 2.1.2.
tag directory:
A directory that contains one or more tag files.
tag file:
A file that contains metadata about the bag or its payload. This document defines the standard BagIt tag files: the bag declaration in "bagit.txt" (see Section 2.1.1), payload manifests (see Section 2.1.3), tag manifests (see Section 2.2.1), bag metadata in "bag-info.txt" (see Section 2.2.2), and remote payload in "fetch.txt" (see Section 2.2.3). This document also allows other arbitrary tag files as described in Section 2.2.4.
complete:
A bag that contains every element required by this document, every payload file listed in a manifest, and any optional files that are listed in a tag manifest. See Section 3.
valid:
A complete bag where every checksum in every manifest has been successfully verified against the corresponding file.
バッグ（bag）：
この文書で定義する構造の中に含まれる、不透明なファイルの集合。
バッグ宣言（bag declaration）：
この文書に準拠するすべてのバッグに存在することが求められるファイル。 バッグの残りの部分を処理するのに必要な値を含みます。 セクション2.1.1を参照してください。
バッグチェックサムアルゴリズム（bag checksum algorithm）：
セクション2.4で説明するように、マニフェストまたはタグマニフェストのファイル名で使用するために正規化された、暗号学的チェックサムアルゴリズムの名前（例：「sha512」）。
マニフェスト（manifest）：
ファイルパスをチェックサムに対応付けるタグファイル。 マニフェストは、ペイロードマニフェスト（セクション2.1.3を参照）またはタグマニフェスト（セクション2.2.1を参照）のいずれかです。
ペイロード（payload）：
名前付きファイルの集合としてバッグにカプセル化されたデータ。サブディレクトリーに整理されている場合があります。 ペイロードファイルの内容はこの文書にとって不透明であり、BagItの処理においては、常に解釈されないオクテットの並びとして扱われます。 セクション2.1.2を参照してください。
タグディレクトリー（tag directory）：
1つ以上のタグファイルを含むディレクトリー。
タグファイル（tag file）：
バッグまたはそのペイロードに関するメタデータを含むファイル。 この文書は、標準のBagItタグファイルとして、「bagit.txt」のバッグ宣言（セクション2.1.1を参照）、ペイロードマニフェスト（セクション2.1.3を参照）、タグマニフェスト（セクション2.2.1を参照）、「bag-info.txt」のバッグメタデータ（セクション2.2.2を参照）、「fetch.txt」のリモートペイロード（セクション2.2.3を参照）を定義します。 また、この文書は、セクション2.2.4で説明するように、その他の任意のタグファイルも許可します。
完全（complete）：
この文書が要求するすべての要素、マニフェストに列挙されたすべてのペイロードファイル、およびタグマニフェストに列挙された任意のファイルをすべて含むバッグ。 セクション3を参照してください。
有効（valid）：
すべてのマニフェストのすべてのチェックサムが、対応するファイルに対して検証に成功している完全なバッグ。

2. Structure

2. 構造

A bag MUST consist of a base directory containing the following:

バッグは、以下を含むベースディレクトリーで構成されなければなりません（MUST）。

  1. a set of required and optional tag files (see Section 2.2);
  2. a subdirectory named "data", called the payload directory (see Section 2.1.2); and
  3. a set of optional tag directories.
  1. 必須のタグファイルと任意のタグファイルの集合（セクション2.2を参照）
  2. ペイロードディレクトリーと呼ばれる「data」という名前のサブディレクトリー（セクション2.1.2を参照）
  3. 任意のタグディレクトリーの集合

The tag files in the base directory consist of one or more files named "manifest-_algorithm_.txt" (see Sections 2.1.3 and 2.4), a file named "bagit.txt" (see Section 2.1.1), and zero or more additional tag files (see Section 2.2). The tag files and directories are in arbitrary file hierarchies and MAY have any name that is not reserved for a file or directory in this document.

ベースディレクトリー内のタグファイルは、「manifest-_algorithm_.txt」という名前の1つ以上のファイル（セクション2.1.3と2.4を参照）、「bagit.txt」という名前のファイル（セクション2.1.1を参照）、および0個以上の追加のタグファイル（セクション2.2を参照）で構成されます。 タグファイルとタグディレクトリーは任意のファイル階層に置かれ、この文書でファイルまたはディレクトリーのために予約されていない任意の名前を持ってもよいです（MAY）。

2.1. Required Elements

2.1. 必須要素

2.1.1. Bag Declaration: bagit.txt

2.1.1. バッグ宣言：bagit.txt

The "bagit.txt" tag file MUST consist of exactly two lines in this order:

「bagit.txt」タグファイルは、ちょうど2行からなり、次の順序で並んでいなければなりません（MUST）。

BagIt-Version: M.N
Tag-File-Character-Encoding: ENCODING

BagIt-Version: M.N
Tag-File-Character-Encoding: ENCODING

_M.N_ identifies the BagIt major (M) and minor (N) version numbers. _ENCODING_ identifies the character set encoding used by the remaining tag files. _ENCODING_ SHOULD be "UTF-8", but for backwards compatibility it MAY be any other encoding registered in [cs-registry]. The bag declaration itself MUST be encoded in UTF-8 and MUST NOT contain a Byte Order Mark (BOM) [RFC3629].

_M.N_は、BagItのメジャーバージョン番号（M）とマイナーバージョン番号（N）を示します。 _ENCODING_は、残りのタグファイルで使用される文字セットのエンコーディングを示します。 _ENCODING_は「UTF-8」であるべきです（SHOULD）が、後方互換性のために、[cs-registry]に登録されている他の任意のエンコーディングであってもよいです（MAY）。 バッグ宣言自体はUTF-8でエンコードされなければなりません（MUST）。また、バイトオーダーマーク（BOM）[RFC3629]を含んではなりません（MUST NOT）。

The number for this version of BagIt is "1.0".

このバージョンのBagItの番号は「1.0」です。

2.1.2. Payload Directory: data/

2.1.2. ペイロードディレクトリー：data/

The base directory MUST contain a subdirectory named "data".

ベースディレクトリーは、「data」という名前のサブディレクトリーを含まなければなりません（MUST）。

The payload directory contains the arbitrary digital content within the bag. The files under the payload directory are called payload files, or the payload. Each payload file is treated as an opaque octet stream when verifying file correctness. Payload files MAY be organized in arbitrary subdirectory structures within the payload directory; however, for the purpose of this document, such subdirectory structures and filenames have no given meaning.

ペイロードディレクトリーは、バッグ内の任意のデジタルコンテンツを含みます。 ペイロードディレクトリーの下にあるファイルは、ペイロードファイル、またはペイロードと呼ばれます。 ファイルの正しさを検証する際、各ペイロードファイルは不透明なオクテットストリームとして扱われます。 ペイロードファイルは、ペイロードディレクトリー内で任意のサブディレクトリー構造に整理されてもよいです（MAY）。 ただし、この文書の目的においては、そのようなサブディレクトリー構造やファイル名に特定の意味はありません。

2.1.3. Payload Manifest: manifest-algorithm.txt

2.1.3. ペイロードマニフェスト：manifest-algorithm.txt

A payload manifest file provides a complete listing of each payload file name along with a corresponding checksum to permit data integrity checking. A bag can have more than one payload manifest, with each using a different checksum algorithm. Manifest entries MUST satisfy the following constraints:

ペイロードマニフェストファイルは、データの完全性を検査できるように、各ペイロードファイルの名前とそれに対応するチェックサムの完全な一覧を提供します。 バッグは複数のペイロードマニフェストを持つことができ、それぞれが異なるチェックサムアルゴリズムを使用します。 マニフェストのエントリーは、以下の制約を満たさなければなりません（MUST）。

  • Every bag MUST contain at least one payload manifest file and MAY contain more than one.
  • Every payload manifest MUST list every payload file name exactly once.
  • A payload manifest file MUST have a name of the form "manifest-_algorithm_.txt", where _algorithm_ is a string specifying the checksum algorithm used by that manifest as described in Section 2.4.
  • すべてのバッグは、少なくとも1つのペイロードマニフェストファイルを含まなければなりません（MUST）。また、複数のペイロードマニフェストファイルを含んでもよいです（MAY）。
  • すべてのペイロードマニフェストは、すべてのペイロードファイルの名前をちょうど1回ずつ列挙しなければなりません（MUST）。
  • ペイロードマニフェストファイルは、「manifest-_algorithm_.txt」という形式の名前を持たなければなりません（MUST）。ここで、_algorithm_は、セクション2.4で説明するように、そのマニフェストで使用されるチェックサムアルゴリズムを指定する文字列です。

Example payload manifest filenames:

ペイロードマニフェストのファイル名の例：

manifest-sha256.txt
manifest-sha512.txt

manifest-sha256.txt
manifest-sha512.txt

Each line of a payload manifest file MUST be of the form

ペイロードマニフェストファイルの各行は、次の形式でなければなりません（MUST）。

checksum filepath

checksum filepath

where _filepath_ is the pathname of a file relative to the base directory, and _checksum_ is a hex-encoded checksum calculated by applying _algorithm_ over the file.

ここで、_filepath_はベースディレクトリーからの相対的なファイルのパス名であり、_checksum_はそのファイルに_algorithm_を適用して計算した、16進数でエンコードされたチェックサムです。

  • The hex-encoded checksum MAY use uppercase and/or lowercase letters.
  • The slash character ('/') MUST be used as a path separator in _filepath_.
  • One or more linear whitespace characters (spaces or tabs) MUST separate _checksum_ from _filepath_.
  • There is no limitation on the length of a pathname.
  • The payload manifest MUST NOT reference files outside the payload directory.
  • If a _filepath_ includes a Line Feed (LF), a Carriage Return (CR), a Carriage-Return Line Feed (CRLF), or a percent sign (%), those characters (and only those) MUST be percent-encoded following [RFC3986].
  • 16進数でエンコードされたチェックサムには、大文字と小文字のどちらか、または両方を使用してもよいです（MAY）。
  • _filepath_では、パスの区切り文字としてスラッシュ文字（'/'）を使用しなければなりません（MUST）。
  • _checksum_と_filepath_は、1つ以上の線形空白文字（スペースまたはタブ）で区切らなければなりません（MUST）。
  • パス名の長さに制限はありません。
  • ペイロードマニフェストは、ペイロードディレクトリーの外にあるファイルを参照してはなりません（MUST NOT）。
  • _filepath_がラインフィード（LF）、キャリッジリターン（CR）、キャリッジリターンとラインフィード（CRLF）、またはパーセント記号（%）を含む場合、それらの文字（およびそれらの文字だけ）を[RFC3986]に従ってパーセントエンコードしなければなりません（MUST）。

A manifest MUST NOT reference directories. Bag creators who wish to create an otherwise empty directory have typically done so by creating an empty placeholder file with a name such as ".keep".

マニフェストは、ディレクトリーを参照してはなりません（MUST NOT）。 それ以外は空のディレクトリーを作成したいバッグ作成者は、一般に「.keep」のような名前の空のプレースホルダーファイルを作成することで、これを実現してきました。

2.2.1. Tag Manifest: tagmanifest-algorithm.txt

タグマニフェストファイルは、「tagmanifest-_algorithm_.txt」という形式の名前を持たなければなりません（MUST）。ここで、_algorithm_は、セクション2.4で説明する形式に従う文字列で、そのマニフェストで使用されるバッグチェックサムアルゴリズムを指定します。

2.2.3. Fetch File: fetch.txt

2.2.3. フェッチファイル：fetch.txt

For reasons of efficiency, a bag MAY be sent with a list of files to be fetched and added to the payload before it can meaningfully be checked for completeness. The fetch file allows a bag to be transmitted with "holes" in it, which can be practical for several reasons. For example, it obviates the need for the sender to stage a large serialized copy of the content while the bag is transferred to the receiver. Also, this method allows a sender to construct a bag from components that are either a subset of logically related components (e.g., the localized logical object could be much larger than what is intended for export) or assembled from logically distributed sources (e.g., the object components for export are not stored locally under one filesystem tree). An OPTIONAL tag file, called the fetch file, contains such a list.

効率上の理由から、バッグは、完全性を意味のある形で検査できるようになる前に取得してペイロードに追加すべきファイルの一覧とともに送信されてもよいです（MAY）。 フェッチファイルを使用すると、「穴」の開いたバッグを送信できます。これはいくつかの理由で実用的な場合があります。 たとえば、バッグを受信者に転送する間、送信者がコンテンツの大きなシリアル化されたコピーを用意しておく必要がなくなります。 また、この方法を使用すると、送信者は、論理的に関連するコンポーネントの一部分であるコンポーネント（たとえば、ローカルにある論理的なオブジェクトが、エクスポートしようとするものよりはるかに大きい場合）や、論理的に分散したソースから集めたコンポーネント（たとえば、エクスポートするオブジェクトのコンポーネントが、ローカルの1つのファイルシステムツリーの下に保管されていない場合）からバッグを構築できます。 フェッチファイルと呼ばれる選択可能な（OPTIONAL）タグファイルに、そのような一覧を記載します。

The fetch file MUST be named "fetch.txt". Every file listed in the fetch file MUST be listed in every payload manifest. A fetch file MUST NOT list any tag files.

フェッチファイルの名前は「fetch.txt」でなければなりません（MUST）。 フェッチファイルに列挙されたすべてのファイルは、すべてのペイロードマニフェストに列挙されなければなりません（MUST）。 フェッチファイルは、タグファイルを列挙してはなりません（MUST NOT）。

Each line of a fetch file MUST be of the form

フェッチファイルの各行は、次の形式でなければなりません（MUST）。

url length filepath

url length filepath

where _url_ identifies the file to be fetched and MUST be an absolute URI as defined in [RFC3986], _length_ is the number of octets in the file (or "-", to leave it unspecified), and _filepath_ identifies the corresponding payload file, relative to the base directory.

ここで、_url_は取得するファイルを識別するもので、[RFC3986]で定義される絶対URIでなければなりません（MUST）。_length_はファイルのオクテット数（または、指定しない場合は「-」）であり、_filepath_はベースディレクトリーからの相対パスで、対応するペイロードファイルを識別します。

The slash character ('/') MUST be used as a path separator in _filepath_. One or more linear whitespace characters (spaces or tabs) MUST separate these three values, and any such characters in the _url_ MUST be percent-encoded [RFC3986]. If _filename_ includes an LF, a CR, a CRLF, or a percent sign (%), those characters (and only those) MUST be percent-encoded as described in [RFC3986]. There is no limitation on the length of any of the fields in the fetch file.

_filepath_では、パスの区切り文字としてスラッシュ文字（'/'）を使用しなければなりません（MUST）。 これら3つの値は、1つ以上の線形空白文字（スペースまたはタブ）で区切らなければなりません（MUST）。また、_url_に含まれるそのような文字は、パーセントエンコード[RFC3986]されなければなりません（MUST）。 _filename_がLF、CR、CRLF、またはパーセント記号（%）を含む場合、それらの文字（およびそれらの文字だけ）を[RFC3986]で説明されているようにパーセントエンコードしなければなりません（MUST）。 フェッチファイル内のどのフィールドの長さにも制限はありません。

2.2.4. その他のタグファイル

A bag MAY contain other tag files that are not defined by this document. Implementations MUST perform standard checksum validation on any tag file that is listed in a tag manifest but MUST otherwise ignore their contents.

Text tag files except for the bag declaration file MAY include a Byte Order Mark (BOM) only if the specified encoding requires it for proper decoding. In accordance with [RFC3629], when "bagit.txt" specifies UTF-8, the tag files MUST NOT begin with a BOM. See Section 2.1.1.

バッグ宣言ファイルを除くすべてのテキストタグファイルでは、テキストは「bagit.txt」バッグ宣言ファイルで指定された文字エンコーディングを使用しなければなりません（MUST）。 バッグ宣言ファイルを除くテキストタグファイルは、指定されたエンコーディングが正しくデコードするためにバイトオーダーマーク（BOM）を必要とする場合に限り、BOMを含んでもよいです（MAY）。 [RFC3629]に従い、「bagit.txt」がUTF-8を指定している場合、タグファイルはBOMで始まってはなりません（MUST NOT）。 セクション2.1.1を参照してください。

2.4. Bag Checksum Algorithms

2.4. バッグチェックサムアルゴリズム

The payload manifest and tag manifest permit validating the integrity of the payload and tag files in a bag produced by the checksum algorithms. Checksum values MUST be encoded so as to conform to the manifest format specified in Section 2.1.3. However, the internal details of a checksum are outside the scope of this document.

ペイロードマニフェストとタグマニフェストにより、チェックサムアルゴリズムが生成した値を用いて、バッグ内のペイロードファイルとタグファイルの完全性を検証できます。 チェックサムの値は、セクション2.1.3で規定するマニフェスト形式に適合するようにエンコードされなければなりません（MUST）。 ただし、チェックサムの内部の詳細は、この文書の範囲外です。

To avoid future ambiguity, the checksum algorithm SHOULD be registered in IANA's "Named Information Hash Algorithm Registry" [ni-registry] according to [RFC6920] but MAY, for backwards compatibility, also be MD5 [RFC1321] or SHA-1 [RFC3174].

将来の曖昧さを避けるために、チェックサムアルゴリズムは、[RFC6920]に従ってIANAの「Named Information Hash Algorithm Registry」[ni-registry]に登録されているべきです（SHOULD）。 ただし、後方互換性のために、MD5 [RFC1321]またはSHA-1 [RFC3174]であってもよいです（MAY）。

The name of the checksum algorithm MUST be normalized for use in the manifest's filename by lowercasing the common name of the algorithm and removing all non-alphanumeric characters. Following is a partial list that maps common algorithm names to normalized names:

チェックサムアルゴリズムの名前は、アルゴリズムの一般的な名前を小文字にし、英数字以外の文字をすべて取り除くことで、マニフェストのファイル名で使用するために正規化されなければなりません（MUST）。 以下は、一般的なアルゴリズム名を正規化された名前に対応付けた一覧の一部です。

  • MD5: md5
  • SHA-1: sha1
  • sha-256: sha256
  • sha-512: sha512
  • MD5: md5
  • SHA-1: sha1
  • sha-256: sha256
  • sha-512: sha512

Starting with BagIt 1.0, bag creation and validation tools MUST support the SHA-256 and SHA-512 algorithms [RFC6234] and SHOULD enable SHA-512 by default when creating new bags. For backwards compatibility, implementers SHOULD support MD5 [RFC1321] and SHA-1 [RFC3174]. Implementers are encouraged to simplify the process of adding additional manifests using new algorithms to streamline the process of in-place upgrades.

BagIt 1.0以降、バッグの作成ツールと検証ツールは、SHA-256アルゴリズムとSHA-512アルゴリズム[RFC6234]をサポートしなければなりません（MUST）。また、新しいバッグを作成する際には、デフォルトでSHA-512を有効にすべきです（SHOULD）。 後方互換性のために、実装者はMD5 [RFC1321]とSHA-1 [RFC3174]をサポートすべきです（SHOULD）。 実装者は、インプレースアップグレードの処理を効率化するために、新しいアルゴリズムを使用したマニフェストを追加する処理を簡単にすることが奨励されます。

3. Complete and Valid Bags

3. 完全なバッグと有効なバッグ

A _complete_ bag MUST meet the following requirements:

_complete_（完全）なバッグは、以下の要件を満たさなければなりません（MUST）。

  1. Every required element MUST be present (see Section 2.1).
  2. Every file listed in every tag manifest MUST be present.
  3. Every file listed in every payload manifest MUST be present.
  4. For BagIt 1.0, every payload file MUST be listed in every payload manifest. Note that older versions of BagIt allowed payload files to be listed in just one of the manifests.
  5. Every element present MUST conform to BagIt 1.0.
  1. すべての必須要素が存在しなければなりません（MUST）（セクション2.1を参照）。
  2. すべてのタグマニフェストに列挙されたすべてのファイルが存在しなければなりません（MUST）。
  3. すべてのペイロードマニフェストに列挙されたすべてのファイルが存在しなければなりません（MUST）。
  4. BagIt 1.0では、すべてのペイロードファイルが、すべてのペイロードマニフェストに列挙されなければなりません（MUST）。 古いバージョンのBagItでは、ペイロードファイルをいずれか1つのマニフェストだけに列挙することが許されていたことに注意してください。
  5. 存在するすべての要素は、BagIt 1.0に準拠しなければなりません（MUST）。

A _valid_ bag MUST meet the following requirements:

_valid_（有効）なバッグは、以下の要件を満たさなければなりません（MUST）。

  1. The bag MUST be _complete_.
  2. Every checksum in every payload manifest and tag manifest has been successfully verified against the contents of the corresponding file.
  1. バッグは_complete_（完全）でなければなりません（MUST）。
  2. すべてのペイロードマニフェストとタグマニフェストのすべてのチェックサムが、対応するファイルの内容に対する検証に成功していること。

5. Security Considerations

5. セキュリティーに関する考慮事項

5.1. Special Directory Characters

5.1. 特殊なディレクトリー文字

The paths specified in the payload manifests, tag manifests, and fetch files do not prohibit special directory characters that have special meaning on some operating systems. Implementers MUST ensure that files outside the bag directory structure are not accessed when reading or writing files based on paths specified in a bag.

ペイロードマニフェスト、タグマニフェスト、フェッチファイルで指定されるパスは、一部のオペレーティングシステムで特別な意味を持つ特殊なディレクトリー文字を禁止していません。 実装者は、バッグ内で指定されたパスに基づいてファイルを読み書きする際に、バッグのディレクトリー構造の外にあるファイルにアクセスしないことを保証しなければなりません（MUST）。

All implementations SHOULD have a test suite to guard against special directory characters.

すべての実装は、特殊なディレクトリー文字から保護するためのテストスイートを持つべきです（SHOULD）。

For example, a maliciously crafted "tagmanifest-sha512.txt" file might contain entries that begin with a path character such as "/", "..", or a "~username" home directory reference in an attempt to cause a naive implementation to leak or overwrite targeted files on a POSIX operating system.

たとえば、悪意を持って作成された「tagmanifest-sha512.txt」ファイルは、素朴な実装にPOSIXオペレーティングシステム上の標的のファイルを漏えいさせたり上書きさせたりしようとして、「/」、「..」、または「~username」のようなホームディレクトリーの参照といったパス文字で始まるエントリーを含むかもしれません。

Windows implementations SHOULD test their implementations to ensure that safety checks prevent use of drive letters and the less commonly used namespace sequences (e.g., "\\?\C:\...") described in [MSFNAM].

Windowsの実装は、安全性チェックにより、ドライブ文字や、[MSFNAM]で説明されているあまり一般的に使用されない名前空間のシーケンス（例：「\\?\C:\...」）の使用が防止されることを確認するために、自身の実装をテストすべきです（SHOULD）。

To assist implementers, the Library of Congress conformance suite [LC-CONFORMANCE-SUITE] has some tests for invalid bags that are expected to fail on POSIX or Windows clients.

実装者を支援するために、米国議会図書館の適合性テストスイート[LC-CONFORMANCE-SUITE]には、POSIXクライアントまたはWindowsクライアントで失敗することが期待される無効なバッグのテストがいくつか含まれています。

5.2. Control of URLs in fetch.txt

5.2. fetch.txt内のURLの制御

Implementers of tools that complete bags by retrieving URLs listed in a fetch file need to be aware that some of those URLs might point to hosts, intentionally or unintentionally, that are not under control of the bag's sender. Moreover, older checksum algorithms, even if reasonable for detecting corruption during transit, may not offer strong cryptographic protection against intentional spoofing.

フェッチファイルに列挙されたURLを取得してバッグを完全にするツールの実装者は、それらのURLの一部が、意図的または意図せずに、バッグの送信者の管理下にないホストを指している可能性があることに注意する必要があります。 さらに、古いチェックサムアルゴリズムは、転送中の破損を検出するには妥当であっても、意図的ななりすましに対する強力な暗号学的保護を提供しない場合があります。

5.3. File Sizes in fetch.txt

5.3. fetch.txt内のファイルサイズ

The size of files, as optionally reported in the fetch file, cannot be guaranteed to match the actual file size to be downloaded. Implementers SHOULD take steps to monitor and abort transfer when the received file size exceeds the file size reported in the fetch file. Implementers SHOULD NOT use the file size in the fetch file for critical resource allocation, such as buffer sizing or storage requisitioning.

フェッチファイルで任意に報告されるファイルのサイズが、ダウンロードされる実際のファイルサイズと一致することは保証できません。 実装者は、受信したファイルサイズがフェッチファイルで報告されたファイルサイズを超えた場合に、それを監視して転送を中止する手段を講じるべきです（SHOULD）。 実装者は、バッファーのサイズ決定やストレージの確保などの重要なリソース割り当てに、フェッチファイル内のファイルサイズを使用すべきではありません（SHOULD NOT）。

5.4. Attacks on Payload File Content

5.4. ペイロードファイルの内容に対する攻撃

The integrity assurance provided by manifests is designed to provide high levels of confidence against data corruption but is not designed to be secure against active attacks. Organizations that need to secure bags against such threats SHOULD agree on additional measures, such as digital signatures, that are out of scope for this specification.

マニフェストが提供する完全性の保証は、データの破損に対して高いレベルの信頼性を提供するように設計されていますが、能動的な攻撃に対して安全であるようには設計されていません。 そのような脅威からバッグを保護する必要がある組織は、この仕様の範囲外であるデジタル署名などの追加の対策について合意すべきです（SHOULD）。

6.1.1. Filename Normalization

6.1.1. ファイル名の正規化

This section provides background information on various challenges caused by differences in how operating systems, filesystems, and common tools handle filenames. This section is followed by a list of recommendations for implementers in Section 6.1.1.3.

このセクションでは、オペレーティングシステム、ファイルシステム、一般的なツールがファイル名を扱う方法の違いによって生じるさまざまな課題について、背景情報を提供します。 このセクションの後のセクション6.1.1.3に、実装者向けの推奨事項の一覧があります。

6.1.1.1. Case Sensitivity
6.1.1.1. 大文字と小文字の区別

There are three challenges for interoperability related to filename case:

ファイル名の大文字と小文字に関連して、相互運用性には3つの課題があります。

  • Filesystems such as File Allocation Table (FAT) or Extended File Allocation Table (EXFAT) always convert filenames to uppercase: "example.txt" will be stored as "EXAMPLE.TXT".
  • Many Unix filesystems save filenames exactly as provided, which allows multiple files that differ only in case: "example.txt" and "Example.txt" are separate files.
  • New Technology File System (NTFS) and Apple's Hierarchical File System (HFS) Plus usually preserve case when storing files but are case insensitive when retrieving them. A file saved as "Example.txt" will be retrieved by that name but will also be retrieved as "EXAMPLE.TXT", "example.txt", etc.
  • File Allocation Table（FAT）やExtended File Allocation Table（EXFAT）などのファイルシステムは、ファイル名を常に大文字に変換します。 「example.txt」は「EXAMPLE.TXT」として保存されます。
  • 多くのUnixファイルシステムは、ファイル名を与えられたとおりに保存するので、大文字と小文字だけが異なる複数のファイルが存在できます。 「example.txt」と「Example.txt」は別々のファイルです。
  • New Technology File System（NTFS）とAppleのHierarchical File System（HFS）Plusは、通常、ファイルを保存する際には大文字と小文字を保持しますが、ファイルを取り出す際には大文字と小文字を区別しません。 「Example.txt」として保存されたファイルは、その名前で取り出せるだけでなく、「EXAMPLE.TXT」や「example.txt」などとしても取り出せます。
6.1.1.2. Unicode Normalization
6.1.1.2. Unicode正規化

  • Windows treats filenames as opaque character sequences (see [MSFNAM]) and will store and return the encoded bytes exactly as provided.
  • Linux and other common Unix systems are generally similar to Windows in storing and returning opaque byte streams, but this behavior is technically dependent on the filesystem.
  • Utilities used for file management, transfer, and archiving may ignore this issue, apply an arbitrary normalization form, or allow the user to control how normalization is applied.
  • AppleのHFS Plusファイルシステムは、ファイル名を常に、Unicode 2.0仕様に基づく完全に分解された形式に正規化します（[TN1150]を参照）。
  • Windowsは、ファイル名を不透明な文字の並びとして扱い（[MSFNAM]を参照）、エンコードされたバイトを与えられたとおりに保存して返します。
  • Linuxやその他の一般的なUnixシステムは、不透明なバイトストリームを保存して返すという点で、一般にWindowsと似ていますが、この振る舞いは厳密にはファイルシステムに依存します。

This situation is very confusing for users because the filenames are visually indistinguishable, and the "missing" file is obviously present in the payload directory.

実際には、これは、マニフェストが書かれた後のある時点でファイル名の正規化が変更されたために、マニフェストに格納されたエンコード済みのファイル名が、単純なファイルの存在チェックに失敗する可能性があることを意味します。 ファイル名は見た目では区別できず、「見つからない」ファイルはペイロードディレクトリーに明らかに存在しているので、この状況はユーザーにとって非常に紛らわしいものです。

6.1.1.3. Recommendations
6.1.1.3. 推奨事項
  • Implementations SHOULD discourage the creation of bags containing files that differ only in case.
  • Implementations SHOULD prevent the creation of bags containing files that differ only in normalization form.
  • BagIt implementations SHOULD tolerate differences in normalization form by comparing both the list of filesystem and manifest names after applying the same normalization form to both.
  • Implementations SHOULD issue a warning when multiple manifests are present that differ only in case or normalization form.
  • 実装は、大文字と小文字だけが異なるファイルを含むバッグの作成を思いとどまらせるべきです（SHOULD）。
  • 実装は、正規化形式だけが異なるファイルを含むバッグの作成を防止すべきです（SHOULD）。
  • BagItの実装は、ファイルシステム上の名前の一覧とマニフェスト内の名前の一覧の両方に同じ正規化形式を適用してから比較することで、正規化形式の違いを許容すべきです（SHOULD）。
  • 実装は、大文字と小文字または正規化形式だけが異なる複数のマニフェストが存在する場合に、警告を出すべきです（SHOULD）。

6.1.2. Windows and Unix File Naming

6.1.2. WindowsとUnixのファイル命名

As specified above, only the Unix-based path separator ('/') may be used inside filenames listed in BagIt manifest and fetch.txt files. When bags are exchanged between Windows and Unix platforms, the path separator SHOULD be translated as needed. Receivers of bags on physical media SHOULD be prepared for filesystems created under either Windows or Unix. Besides the fundamental difference between path separators ('\' and '/'), generally, Windows filesystems have more limitations than Unix filesystems.

上で規定したように、BagItのマニフェストとfetch.txtファイルに列挙されるファイル名の中では、Unixベースのパス区切り文字（'/'）だけを使用できます。 WindowsとUnixのプラットフォーム間でバッグを交換する場合、パスの区切り文字は必要に応じて変換されるべきです（SHOULD）。 物理媒体でバッグを受け取る受信者は、WindowsとUnixのどちらで作成されたファイルシステムにも対応できるように準備しておくべきです（SHOULD）。 パス区切り文字（'\'と'/'）の根本的な違いに加えて、一般にWindowsのファイルシステムにはUnixのファイルシステムよりも多くの制限があります。

Windows path names have a maximum of 255 characters, and none of these characters may be used in a path component:

Windowsのパス名は最大255文字であり、以下の文字はいずれもパスの構成要素に使用できません。

    < > : " / | ? *

    < > : " / | ? *

    CON, PRN, AUX, NUL
    COM1, COM2, COM3, COM4, COM5, COM6, COM7, COM8, COM9
    LPT1, LPT2, LPT3, LPT4, LPT5, LPT6, LPT7, LPT8, LPT9

    CON, PRN, AUX, NUL
    COM1, COM2, COM3, COM4, COM5, COM6, COM7, COM8, COM9

6.1.3. Legacy Checksum Tools

6.1.3. レガシーなチェックサムツール

Some bags have been manually assembled using checksum utilities such as those contained in the GNU Coreutils package (md5sum, sha1sum, etc.), collectively referred to here as "md5sum". Implementers who desire wide support of legacy content should be aware of some known quirks of these tools.

一部のバッグは、GNU Coreutilsパッケージに含まれるもの（md5sum、sha1sumなど）のようなチェックサムユーティリティーを使用して、手作業で組み立てられてきました。ここでは、これらをまとめて「md5sum」と呼びます。 レガシーなコンテンツを幅広くサポートしたい実装者は、これらのツールのいくつかの既知の癖に注意する必要があります。

md5sum can be run in "text mode", which causes it to normalize line endings on some operating systems. On Unix-like systems, both modes will usually produce the same results; on systems like Windows, they can produce different results based on the file contents. The md5sum output format has two characters between the checksum and the filepath: the first is always a space, and the second is an asterisk ("*") for binary mode and a space for text mode.

md5sumは「テキストモード」で実行でき、その場合、一部のオペレーティングシステムでは行末が正規化されます。 Unix系のシステムでは、通常、どちらのモードでも同じ結果になりますが、Windowsのようなシステムでは、ファイルの内容によって異なる結果になる可能性があります。 md5sumの出力形式では、チェックサムとファイルパスの間に2つの文字があります。1つ目は常にスペースで、2つ目はバイナリーモードではアスタリスク（「*」）、テキストモードではスペースです。

A final note about md5sum-generated manifests is that, for a _filepath_ containing a backslash ('\'), the manifest line will have a backslash inserted in front of the _checksum_ and, under Windows, the backslashes inside _filepath_ can be doubled.

md5sumが生成したマニフェストについての最後の注意として、バックスラッシュ（'\'）を含む_filepath_に対しては、マニフェストの行の_checksum_の前にバックスラッシュが挿入され、さらにWindowsでは_filepath_内のバックスラッシュが二重になる場合があります。

Implementers MAY wish to accept this format by ignoring a leading asterisk or handling differences in line termination gracefully but, if so, implementations MUST warn the user that the bag in question will fail strict validation. In such cases, it is RECOMMENDED that tools provide an easy option to update the bag with valid manifests.

実装者は、先頭のアスタリスクを無視したり、行の終端の違いを適切に扱ったりすることで、この形式を受け入れることを望んでもよいです（MAY）が、その場合、実装は、問題のバッグが厳密な検証には失敗することをユーザーに警告しなければなりません（MUST）。 そのような場合、ツールは、有効なマニフェストでバッグを更新する簡単なオプションを提供することが推奨されます（RECOMMENDED）。
