RFC 146

Views on Issues Relevant to Data Sharing on Computer Networks

RFC 146

コンピューターネットワーク上のデータ共有に関連する問題についての見解

Introduction

はじめに

The formation of a committee to address the problems of achieving data sharing on the ARPA Network, as suggested by Arie Shoshani (RFC #140) is desirable at this point of network development. We concur with Shoshani's ideas (presented in an introductory paper to the network data sharing meeting, scheduled for Tuesday, May 18) and believe that purpose of the committee should be -

Arie Shoshaniが提案したように（RFC #140）、ARPAネットワーク上でデータ共有を実現するための問題に取り組む委員会を結成することは、ネットワーク開発のこの時点において望ましいことです。私たちはShoshaniの考え（5月18日火曜日に予定されているネットワークデータ共有会議に向けた導入論文で提示されたもの）に同意し、委員会の目的は次のとおりであるべきだと考えます。

  1. to classify the issues involved and to propose various approaches;
  2. to integrate the hitherto independent network activities that address problems in the area of data sharing, and;
  3. to set up and coordinate appropriate experiments to test the services developed and to evaluate alternative approaches.
  1. 関係する論点を分類し、さまざまなアプローチを提案すること。
  2. データ共有の分野の問題に取り組む、これまで独立していたネットワーク上の活動を統合すること。
  3. 開発されたサービスをテストし、代替となるアプローチを評価するための適切な実験を準備し、調整すること。

This position paper is intended to augment Shoshani's as a basis for discussion at the data sharing meeting. No attempt is made to discuss specific means of implementation since many approaches to data handling problems are possible and have been proposed. Rather, our viewpoint on what the committee's role should be in giving some cohesion to various existing implementations is presented.

この意見書は、データ共有会議での議論の土台として、Shoshaniの論文を補うことを意図しています。データ処理の問題には多くのアプローチが可能であり、実際に提案されてもいるため、具体的な実装手段について論じることはしません。むしろ、既存のさまざまな実装にまとまりを与えるうえで委員会が果たすべき役割について、私たちの見解を示します。

Our Views

私たちの見解

One approach to achieving data sharing on the ARPA Network can be thought of as having three stages, which roughly correspond to the modes of use or operation. Within each stage are various levels of development required to get to the next stage. This development is not necessarily sequential. A description of the three stages follows.

ARPAネットワーク上でデータ共有を実現するための1つのアプローチは、3つの段階を持つものと考えることができ、それらは使用または運用の形態におおむね対応します。各段階の中には、次の段階に進むために必要なさまざまなレベルの開発があります。この開発は必ずしも順番に進むわけではありません。3つの段階の説明を以下に示します。

Stage 1:
Data handling services are provided at various Hosts. The user talks directly to the serving Host (via TELNET or by addressing a known socket) to explicitly access the service. This mode of operation corresponds to Bhushan's category of "direct" usage (RFC #114). The data services provided by the serving Host range from simple ones, such as White's file transfer system (RFC #122) to sophisticated systems such as the CCA's data machine (NIC 5791 and 6706).
Stage 2:
The user has access to an intermediate process or data control facility* that routes his requests for a particular data service to the serving system. The user must explicitly identify the data services to the used. This mode of operation corresponds to Bhushan's category of "indirect" access. The data control facility provides the necessary control commands, data transformations, and accessing methods. A single request would include the use of several interacting services. For example, Heafner's Data Reconfiguration Service (RFC #l38) could be used in conjunction with the use of CCA's data machine.
Stage 3:
The user treats the network as a single resource and is unconcerned with the location of the services, data files, etc. All references are by name. In this mode of operation, the data control facility can function as a referral center for data service requests by using the most appropriate data service available and by automatically combining the use of several services that may be needed to satisfy a request. For example, data could be retrieved from several files, each managed by a different data management system. The data control facility must be cognizant of the location of data files, their structure, data management system capabilities, etc.
段階1:
データ処理サービスがさまざまなホストで提供されます。ユーザーは、サービスに明示的にアクセスするために、サービスを提供するホストと（TELNETを介して、または既知のソケットを指定して）直接やり取りします。この運用形態は、Bhushanの「直接（direct）」利用の分類（RFC #114）に対応します。サービスを提供するホストが提供するデータサービスは、Whiteのファイル転送システム（RFC #122）のような単純なものから、CCAのデータマシン（NIC 5791および6706）のような高度なシステムまでさまざまです。
段階2:
ユーザーは、特定のデータサービスに対する要求を、サービスを提供するシステムへ振り分ける中間プロセスまたはデータ制御機能（data control facility）*にアクセスできます。ユーザーは、使用するデータサービスを明示的に指定しなければなりません。この運用形態は、Bhushanの「間接（indirect）」アクセスの分類に対応します。データ制御機能は、必要な制御コマンド、データ変換、アクセス方法を提供します。1つの要求が、相互に作用するいくつかのサービスの使用を含むこともあるでしょう。たとえば、HeafnerのData Reconfiguration Service（RFC #l38）を、CCAのデータマシンの使用と組み合わせて使うことができます。
段階3:
ユーザーはネットワークを単一の資源として扱い、サービスやデータファイルなどの場所を気にしません。すべての参照は名前によって行います。この運用形態では、データ制御機能は、利用可能な最も適切なデータサービスを使い、要求を満たすために必要となりうる複数のサービスの使用を自動的に組み合わせることで、データサービス要求の仲介センターとして機能できます。たとえば、それぞれ異なるデータ管理システムによって管理されている複数のファイルからデータを取得できます。データ制御機能は、データファイルの場所、その構造、データ管理システムの機能などを把握していなければなりません。

*The data control facility is not necessarily located at his local Host. Such a facility may exist on from one to all Host (i.e., ranging from centralized to completely distributed).

*データ制御機能は、必ずしもユーザーのローカルホストに置かれるとは限りません。そのような機能は、1つのホストからすべてのホストにまで存在しうるものです（つまり、集中型から完全な分散型までの幅があります）。

Some approaches to the design of the data control facility have been suggested by Shoshani, notably the integrated data management system (IDMS) and the unified data management system (UDMS). The notion of the network machine (RFC #51) is closest to the capabilities one would see in Stage 3.

データ制御機能の設計に対するいくつかのアプローチがShoshaniによって提案されており、特に統合データ管理システム（integrated data management system: IDMS）と統一データ管理システム（unified data management system: UDMS）があります。ネットワークマシン（RFC #51）の概念は、段階3で見られるであろう機能に最も近いものです。

Relevant Areas of Development

関連する開発分野

The data control facility can range anywhere from a simple interface to an intelligent front-end processor to a network-wide referral system. In any case, a common means is desirable for handling applications such as file transfer, on-line update and retrieval of data, information gathering and reporting, and program access to data. To attain this end, a few of the areas in which developments will be required include:

データ制御機能は、単純なインターフェイスから、インテリジェントなフロントエンドプロセッサー、さらにはネットワーク全体にわたる仲介システムまで、どのようなものでもありえます。いずれの場合でも、ファイル転送、データのオンライン更新と検索、情報の収集と報告、プログラムからのデータアクセスなどのアプリケーションを扱うための共通の手段が望まれます。この目的を達成するために開発が必要となる分野には、次のようなものがあります。

  1. a data description language, permitting the user to define the physical structure of files, to define logical files, and to categorize data fields for name referencing. The language should be designed to facilitate the resolution of physical discrepancies in data and file structures. The user should be able to superimpose logical restructuring of data without any change in the physical structure.
  2. a control or access language that can be mapped into various data management languages. Considered here is Shoshani's suggested two-level approach with perhaps a meta-language implementation to facilitate conversions among already existing languages.
  3. methods for managing and merging distributed data, search mechanisms for file directories, error recovery techniques, etc.
  1. データ記述言語。ユーザーがファイルの物理的な構造を定義し、論理的なファイルを定義し、名前で参照するためにデータフィールドを分類できるようにするものです。この言語は、データやファイルの構造における物理的な不一致を解消しやすいように設計すべきです。ユーザーは、物理的な構造を一切変更せずに、データの論理的な再構成を重ねて適用できるようにすべきです。
  2. さまざまなデータ管理言語に対応づけることのできる制御言語またはアクセス言語。ここでは、既存の言語間の変換を容易にするために、場合によってはメタ言語による実装を伴う、Shoshaniが提案した2レベルのアプローチを考えています。
  3. 分散したデータを管理し統合するための方法、ファイルディレクトリーの探索の仕組み、エラー回復の技術など。

Independent ARPA Network activities that in effect constitute Stage 1 have touched on these areas and should be incorporated into the overall data sharing scheme such that all of the isolated pieces are compatible. For example,

実質的に段階1を構成している独立したARPAネットワークの活動は、これらの分野に触れており、孤立した個々の部分がすべて互換性を持つように、データ共有の全体的な枠組みに組み込むべきです。たとえば、次のとおりです。

  1. the data reconfiguration service (RFC #138) would be invoked by the data control facility whenever data transformations are required.
  2. the file transfer protocol (RFC #114, #122) should be consistent with other data handling services.
  3. CCA's data machine should be a subset or part of any data control facility. The network data language and set of data management services that they plan to implement can perhaps be adopted network-wide.
  4. the network machine concept (RFC #51) for defining the program and data environments should be resurrected. The data control facility should be a subset of a network machine architecture.
  1. データ再構成サービス（data reconfiguration service、RFC #138）は、データ変換が必要になるたびに、データ制御機能によって呼び出されるでしょう。
  2. ファイル転送プロトコル（RFC #114、#122）は、他のデータ処理サービスと整合しているべきです。
  3. CCAのデータマシンは、あらゆるデータ制御機能のサブセットまたは一部であるべきです。CCAが実装を計画しているネットワークデータ言語とデータ管理サービス群は、ネットワーク全体で採用できるかもしれません。
  4. プログラムとデータの環境を定義するためのネットワークマシンの概念（RFC #51）を復活させるべきです。データ制御機能は、ネットワークマシンのアーキテクチャーのサブセットであるべきです。

Some other relevant topics include NIL (RFC #51), DEL (RFC 5), the notion Of MYLOCAL n, YOUR LOCAL n, and STANDARD n (RFC #42), user level protocol objectives as described in RFC #76 and #91.

その他の関連する話題には、NIL（RFC #51）、DEL（RFC 5）、MYLOCAL n、YOUR LOCAL n、STANDARD nの概念（RFC #42）、RFC #76と#91で説明されているユーザーレベルプロトコルの目標などがあります。

Experimentation and Testing

実験とテスト

As data services are developed on the network, a coordinated effort is desirable

ネットワーク上でデータサービスが開発されるにつれて、次のことのために協調した取り組みが望まれます。

  1. to exercise individual implementations to see if they work, both alone and in conjunction with other data services, and
  2. to evaluate alternative approaches.
  1. 個々の実装を動かしてみて、単独でも他のデータサービスと組み合わせても動作するかを確かめること。
  2. 代替となるアプローチを評価すること。

Some examples of experimentation to test data services follow:

データサービスをテストするための実験の例をいくつか以下に示します。

  1. File Transfer Protocol

    The file transfer protocol should be used to manipulate data files controlled by various systems.

  2. Data Transfer to Data Computer

    The ability to transfer existing data bases and their structures onto the data computer should be demonstrated.

  3. Data Restructuring

    The ability to define logical restructuring of data for users needs which would be accessible by name should be demonstrated. The original physical structure would be maintained.

  4. Data Transformation

    The ability to access various data management systems on the network without the user being concerned with the data transformation involved should be demonstrated. Necessary calls to forms available on the Data Reconfiguration Service should be handled automatically and should be transparent to the user.

  5. Data Consistency

    Problems of maintaining consistency when duplicate copies of a data file exist and updates to the file are made should be investigated. Automatic use of file transfer protocol and DRS to generate new duplicate copies should be included.

  6. Data Privacy

    Access controls for privacy Of data files in the network environment should be designed and evaluated. This includes controls on parts of distributed files.

  1. ファイル転送プロトコル

    ファイル転送プロトコルを使って、さまざまなシステムが管理するデータファイルを操作すべきです。

  2. データコンピューターへのデータ転送

    既存のデータベースとその構造をデータコンピューターへ転送できることを実証すべきです。

  3. データの再構成

    ユーザーの必要に応じて、名前でアクセスできるデータの論理的な再構成を定義できることを実証すべきです。元の物理的な構造は維持されます。

  4. データ変換

    ユーザーが関係するデータ変換を気にすることなく、ネットワーク上のさまざまなデータ管理システムにアクセスできることを実証すべきです。Data Reconfiguration Serviceで利用可能なフォームの必要な呼び出しは、自動的に処理され、ユーザーからは透過的であるべきです。

  5. データの一貫性

    データファイルの複製が存在し、そのファイルが更新される場合に一貫性を保つ問題を調査すべきです。新しい複製を生成するために、ファイル転送プロトコルとDRSを自動的に使用することも含めるべきです。

  6. データのプライバシー

    ネットワーク環境におけるデータファイルのプライバシーのためのアクセス制御を設計し、評価すべきです。これには、分散したファイルの一部に対する制御も含まれます。

Our recommendation is that the committee on data sharing be responsible for coordinating development in these areas, for attempting to maintain consistency among data services, and for testing services in a series of experiments as they are implemented.

私たちの推奨は、データ共有に関する委員会が、これらの分野の開発を調整し、データサービス間の一貫性を保つよう努め、サービスが実装されるにつれて一連の実験でテストすることに責任を持つことです。
