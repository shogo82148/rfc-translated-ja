RFC 2147

TCP and UDP over IPv6 Jumbograms

RFC 2147

IPv6ジャンボグラム上のTCPとUDP

Status of This Memo

このメモのステータス

This document specifies an Internet standards track protocol for the Internet community, and requests discussion and suggestions for improvements. Please refer to the current edition of the "Internet Official Protocol Standards" (STD 1) for the standardization state and status of this protocol. Distribution of this memo is unlimited.

この文書は、インターネットコミュニティーのためのインターネット標準化過程（Internet Standards Track）のプロトコルを規定し、改善のための議論と提案を求めるものです。このプロトコルの標準化の状態とステータスについては、「Internet Official Protocol Standards」（STD 1）の最新版を参照してください。このメモの配布は無制限です。

1. Overview

1. 概要

IPv6 supports datagrams larger than 65535 bytes long, often referred to as jumbograms, through use of the Jumbo Payload hop-by-hop option [Deering95]. The UDP protocol has a 16-bit length field that keeps it from being able to make use of jumbograms, and though TCP does not have a length field, both the MSS option and the Urgent field are constrained by 16-bits. This document describes some simple changes that can be made to allow TCP and UDP to make use of IPv6 jumbograms.

IPv6は、ジャンボペイロード（Jumbo Payload）ホップバイホップオプション[Deering95]を使用することで、65535バイトを超える長さのデータグラムをサポートします。このようなデータグラムはジャンボグラム（jumbogram）と呼ばれることがよくあります。UDPプロトコルには16ビットの長さフィールドがあるため、ジャンボグラムを利用できません。また、TCPには長さフィールドはありませんが、MSSオプションと緊急（Urgent）フィールドはいずれも16ビットに制約されています。この文書では、TCPとUDPがIPv6ジャンボグラムを利用できるようにするためのいくつかの簡単な変更について説明します。

2. UDP Jumbograms

2. UDPジャンボグラム

To allow UDP to make use of jumbograms, either the UDP length field needs to be extended, or it needs to be ignored. Since the size of the field can't be changed, a length of zero is used to indicate that it is to be ignored, and the length in the "pseudo-header" is to be used to determine the true length of the UDP header plus data. This works because UDP length field includes the UDP header, so the minimum valid value for this field is 8.

UDPがジャンボグラムを利用できるようにするには、UDPの長さフィールドを拡張するか、無視するかのどちらかが必要です。フィールドのサイズは変更できないため、長さフィールドを無視することを示すために長さ0を使用し、UDPヘッダーとデータを合わせた本当の長さを判断するには「疑似ヘッダー（pseudo-header）」の長さを使用します。UDPの長さフィールドにはUDPヘッダーが含まれるため、このフィールドの有効な最小値は8であり、それゆえこの方法はうまく機能します。

When sending a UDP packet, if and only if the length of the UDP header plus data is greater than 65,535, set the length field in the UDP header to zero.

UDPパケットを送信するとき、UDPヘッダーとデータを合わせた長さが65,535を超える場合に限り、UDPヘッダーの長さフィールドを0に設定します。

Note 1: The length used in the "pseudo-header" for computing the UDP checksum is always the true length of the UDP header plus data, NOT zero [RFC-1883, Section 8.1].

注1：UDPチェックサムの計算のために「疑似ヘッダー」で使用される長さは、常にUDPヘッダーとデータを合わせた本当の長さであり、0ではありません（NOT）[RFC-1883, Section 8.1]。

Note 2: An IPv6 packet that carries a UDP packet of length greater than 65,535 will necessarily carry a Jumbo Payload option in a Hop-by-Hop Options header [RFC1883, Section 4.3]). The length field in the Jumbo Payload option contains the length of the IP packet excluding the IPv6 header, that is, it contains the length of all extension headers present plus the UDP header plus the UDP data. The length field in the IPv6 header contains zero to indicate the presence of the Jumbo Payload option.

注2：長さが65,535を超えるUDPパケットを運ぶIPv6パケットは、必ずホップバイホップオプションヘッダーの中にジャンボペイロードオプションを含みます[RFC1883, Section 4.3])。ジャンボペイロードオプションの長さフィールドには、IPv6ヘッダーを除いたIPパケットの長さ、つまり、存在するすべての拡張ヘッダーの長さにUDPヘッダーとUDPデータを加えた長さが含まれます。IPv6ヘッダーの長さフィールドには、ジャンボペイロードオプションが存在することを示すために0が含まれます。

If a UDP packet is received with a length field of zero, the length of the UDP packet is computed from the length field in the Jumbo Payload option minus the length of all extension headers present between the IPv6 header and the UDP header.

長さフィールドが0のUDPパケットを受信した場合、UDPパケットの長さは、ジャンボペイロードオプションの長さフィールドから、IPv6ヘッダーとUDPヘッダーの間に存在するすべての拡張ヘッダーの長さを引いて計算します。

3. TCP Jumbograms

3. TCPジャンボグラム

Because there is no length field in the TCP header, there is nothing limiting the length of an individual TCP packet. However, the MSS value that is negotiated at the beginning of the connection limits the largest TCP packet that can be sent, and the Urgent Pointer cannot reference data beyond 65535 bytes.

TCPヘッダーには長さフィールドがないため、個々のTCPパケットの長さを制限するものはありません。しかし、コネクションの開始時にネゴシエーションされるMSSの値によって、送信できる最大のTCPパケットが制限されます。また、緊急ポインター（Urgent Pointer）は65535バイトより先のデータを参照できません。

3.1. TCP MSS

3.1. TCP MSS

When determining what MSS value to send, if the MTU of the directly attached interface is greater than 65535, then set the MSS value to 65535.

送信するMSSの値を決めるとき、直接接続されたインターフェイスのMTUが65535を超える場合は、MSSの値を65535に設定します。

When an MSS value of 65535 is received, it is to be treated as infinity. MTU discovery code, starting with the MTU of the outgoing interface, will be used to determine the actual MSS.

65535というMSSの値を受信した場合は、それを無限大として扱います。実際のMSSは、送信インターフェイスのMTUを出発点として、MTU探索のコードによって決定されます。

3.2. TCP Urgent Pointer

3.2. TCPの緊急ポインター

The Urgent Pointer problem could be fixed by adding a TCP Urgent Pointer Option. However, since it is unlikely that applications using jumbograms will also use Urgent Pointers, a less intrusive change similar to the MSS change will suffice.

緊急ポインターの問題は、TCP緊急ポインターオプションを追加することで解決できるかもしれません。しかし、ジャンボグラムを使用するアプリケーションが緊急ポインターも使用する可能性は低いため、MSSの変更と同様の、より影響の小さい変更で十分です。

When a TCP packet is to be sent with an Urgent Pointer (i.e., the URG bit set), first calculate the offset from the Sequence Number to the Urgent Pointer. If the offset is less than 65535, fill in the Urgent field and continue with the normal TCP processing. If the offset is greater than 65535, and the offset is greater than or equal to the length of the TCP data, fill in the Urgent Pointer with 65535 and continue with the normal TCP processing. Otherwise, the TCP packet must be split into two pieces. The first piece contains data up to, but not including the data pointed to by the Urgent Pointer, and the Urgent field is set to 65535 to indicate that the Urgent Pointer is beyond the end of this packet. The second piece can then be sent with the Urgent field set normally.

緊急ポインターを持つ（つまり、URGビットがセットされた）TCPパケットを送信する場合は、まずシーケンス番号から緊急ポインターまでのオフセットを計算します。オフセットが65535未満の場合は、緊急フィールドに値を入れ、通常のTCP処理を続けます。オフセットが65535を超え、かつオフセットがTCPデータの長さ以上の場合は、緊急ポインターに65535を入れ、通常のTCP処理を続けます。それ以外の場合は、TCPパケットを2つに分割しなければなりません。1つ目には、緊急ポインターが指すデータの手前まで（そのデータは含みません）のデータを入れ、緊急ポインターがこのパケットの終わりより先にあることを示すために緊急フィールドを65535に設定します。その後、2つ目は緊急フィールドを通常どおりに設定して送信できます。

Note: The first piece does not have to include all of the data up to the Urgent Pointer. It can be shorter, just as long as it ends within 65534 bytes of the Urgent Pointer, so that the offset to the Urgent Pointer in the second piece will be less than 65535 bytes.

注：1つ目に緊急ポインターまでのデータをすべて含める必要はありません。2つ目における緊急ポインターまでのオフセットが65535バイト未満になるように、緊急ポインターから65534バイト以内で終わってさえいれば、より短くてもかまいません。

For TCP input processing, when a TCP packet is received with the URG bit set and an Urgent field of 65535, the Urgent Pointer is calculated using an offset equal to the length of the TCP data, rather than the offset in the Urgent field.

TCPの入力処理では、URGビットがセットされ、緊急フィールドが65535であるTCPパケットを受信した場合、緊急ポインターは、緊急フィールドのオフセットではなく、TCPデータの長さに等しいオフセットを使って計算します。

It should also be noted that though the TCP window is only 16-bits, larger windows can be used through use of the TCP Window Scale option [Jacobson92].

また、TCPウィンドウは16ビットしかありませんが、TCPウィンドウスケールオプション[Jacobson92]を使用することで、より大きなウィンドウを使用できることにも注意してください。

4. Security Considerations

4. セキュリティーに関する考慮事項

There are no known security issues involved in these changes.

これらの変更に関連する既知のセキュリティーの問題はありません。
