The scrypt Password-Based Key Derivation Function

RFC 7914

scryptパスワードベース鍵導出関数

Abstract

概要

This document specifies the password-based key derivation function scrypt. The function derives one or more secret keys from a secret string. It is based on memory-hard functions, which offer added protection against attacks using custom hardware. The document also provides an ASN.1 schema.

この文書は、パスワードベースの鍵導出関数scryptを規定します。この関数は、秘密の文字列から1つ以上の秘密鍵を導出します。この関数はメモリーハード関数に基づいており、専用ハードウェアを用いた攻撃に対する保護を強化します。この文書では、ASN.1スキーマも提供します。

1. Introduction

1. はじめに

Password-based key derivation functions are used in cryptography and security protocols for deriving one or more secret keys from a secret value. Over the years, several password-based key derivation functions have been used, including the original DES-based UNIX Crypt-function, FreeBSD MD5 crypt, Public-Key Cryptography Standards#5 (PKCS#5) PBKDF2 [RFC2898] (typically used with SHA-1), GNU SHA-256/512 crypt [SHA2CRYPT], Windows NT LAN Manager (NTLM) [NTLM] hash, and the Blowfish-based bcrypt [BCRYPT]. These algorithms are all based on a cryptographic primitive combined with salting and/or iteration. The iteration count is used to slow down the computation, and the salt is used to make pre-computation costlier.

パスワードベースの鍵導出関数は、暗号やセキュリティープロトコルにおいて、秘密の値から1つ以上の秘密鍵を導出するために使われます。これまでに、オリジナルのDESベースのUNIX Crypt関数、FreeBSD MD5 crypt、Public-Key Cryptography Standards#5（PKCS#5）のPBKDF2 [RFC2898]（通常はSHA-1とともに使われます）、GNU SHA-256/512 crypt [SHA2CRYPT]、Windows NT LAN Manager（NTLM）ハッシュ[NTLM]、Blowfishベースのbcrypt [BCRYPT]など、いくつかのパスワードベースの鍵導出関数が使われてきました。これらのアルゴリズムはすべて、暗号プリミティブにソルト付けと反復の一方または両方を組み合わせたものに基づいています。反復回数は計算を遅くするために使われ、ソルトは事前計算のコストを高くするために使われます。

All password-based key derivation functions mentioned above share the same weakness against powerful attackers. Provided that the number of iterations used is increased as computer systems get faster, this allows legitimate users to spend a constant amount of time on key derivation without losing ground to attackers' ever-increasing computing power -- as long as attackers are limited to the same software implementations as legitimate users. While parallelized hardware implementations may not change the number of operations performed compared to software implementations, this does not prevent them from dramatically changing the asymptotic cost, since in many contexts -- including the embarrassingly parallel task of performing a brute-force search for a passphrase -- dollar-seconds are the most appropriate units for measuring the cost of a computation. As semiconductor technology develops, circuits do not merely become faster; they also become smaller, allowing for a larger amount of parallelism at the same cost.

上に挙げたパスワードベースの鍵導出関数はすべて、強力な攻撃者に対して同じ弱点を抱えています。コンピューターシステムが高速になるのに合わせて使用する反復回数を増やせば、正当なユーザーは鍵導出に一定の時間をかけるだけで、増え続ける攻撃者の計算能力に後れを取らずに済みます。ただしそれは、攻撃者が正当なユーザーと同じソフトウェア実装に制限されている限りの話です。並列化されたハードウェア実装は、ソフトウェア実装と比べて実行する演算の数を変えないかもしれませんが、だからといって漸近的なコストを劇的に変えられないわけではありません。というのも、多くの状況（パスフレーズの総当たり探索という、自明に並列化可能な（embarrassingly parallel）タスクを含む）では、計算のコストを測る単位としてはドル秒が最も適切だからです。半導体技術が発展するにつれて、回路は単に高速になるだけでなく小型にもなり、同じコストでより大きな並列性を実現できるようになります。

Consequently, with existing key derivation algorithms, even when the iteration count is increased so that the time taken to verify a password remains constant, the cost of finding a password by using a brute-force attack implemented in hardware drops each year.

その結果、既存の鍵導出アルゴリズムでは、パスワードの検証にかかる時間が一定に保たれるように反復回数を増やしたとしても、ハードウェアで実装された総当たり攻撃によってパスワードを見つけるコストは毎年下がっていきます。

The scrypt function aims to reduce the advantage that attackers can gain by using custom-designed parallel circuits for breaking password-based key derivation functions.

scrypt関数は、パスワードベースの鍵導出関数を破るために専用設計の並列回路を用いることで攻撃者が得られる優位性を小さくすることを目的としています。

This document does not introduce scrypt for the first time. The original scrypt paper [SCRYPT] was published as a peer-reviewed scientific paper and contains further background and discussions.

この文書でscryptが初めて紹介されるわけではありません。scryptのオリジナルの論文[SCRYPT]は、査読付きの学術論文として公開されており、さらなる背景や議論が含まれています。

The purpose of this document is to serve as a stable reference for documents making use of scrypt. The rest of this document is divided into sections that each describe parameter choices and algorithm steps needed for the final "scrypt" algorithm.

この文書の目的は、scryptを利用する文書のための安定した参照先となることです。この文書の残りの部分はいくつかのセクションに分かれており、各セクションでは、最終的な「scrypt」アルゴリズムに必要なパラメーターの選択とアルゴリズムの手順を説明します。

2. scrypt Parameters

2. scryptのパラメーター

The scrypt function takes several parameters. The passphrase P is typically a human-chosen password. The salt is normally uniquely and randomly generated [RFC4086]. The parameter r ("blockSize") specifies the block size. The CPU/Memory cost parameter N ("costParameter") must be larger than 1, a power of 2, and less than 2^(128 * r / 8). The parallelization parameter p ("parallelizationParameter") is a positive integer less than or equal to ((2^32-1) * 32) / (128 * r). The intended output length dkLen is the length in octets of the key to be derived ("keyLength"); it is a positive integer less than or equal to (2^32 - 1) * 32.

scrypt関数はいくつかのパラメーターを取ります。パスフレーズPは、通常は人間が選んだパスワードです。ソルトは通常、一意かつランダムに生成されます[RFC4086]。パラメーターr（"blockSize"）はブロックサイズを指定します。CPU/メモリーコストパラメーターN（"costParameter"）は、1より大きく、2のべき乗で、2^(128 * r / 8)未満でなければなりません。並列化パラメーターp（"parallelizationParameter"）は、((2^32-1) * 32) / (128 * r)以下の正の整数です。意図する出力長dkLenは、導出する鍵のオクテット単位の長さ（"keyLength"）であり、(2^32 - 1) * 32以下の正の整数です。

Users of scrypt can tune the parameters N, r, and p according to the amount of memory and computing power available, the latency-bandwidth product of the memory subsystem, and the amount of parallelism desired. At the current time, r=8 and p=1 appears to yield good results, but as memory latency and CPU parallelism increase, it is likely that the optimum values for both r and p will increase. Note also that since the computations of SMix are independent, a large value of p can be used to increase the computational cost of scrypt without increasing the memory usage; so we can expect scrypt to remain useful even if the growth rates of CPU power and memory capacity diverge.

scryptの利用者は、利用可能なメモリー量と計算能力、メモリーサブシステムのレイテンシーと帯域幅の積、および望ましい並列性の程度に応じて、パラメーターN、r、pを調整できます。現時点では、r=8かつp=1で良好な結果が得られるようですが、メモリーレイテンシーとCPUの並列性が向上するにつれて、rとpの最適値はどちらも大きくなる可能性が高いです。また、SMixの計算は互いに独立しているため、大きなpの値を使うことで、メモリー使用量を増やさずにscryptの計算コストを増やせることにも注意してください。したがって、CPU能力とメモリー容量の成長率が乖離したとしても、scryptは引き続き有用であると期待できます。

3. The Salsa20/8 Core Function

3. Salsa20/8 Core関数

Salsa20/8 Core is a round-reduced variant of the Salsa20 Core. It is a hash function from 64-octet strings to 64-octet strings. Note that Salsa20/8 Core is not a cryptographic hash function since it is not collision resistant. See Section 8 of [SALSA20SPEC] for its specification and [SALSA20CORE] for more information. The algorithm description, in C language, is included below as a stable reference, without endianness conversion and alignment.

Salsa20/8 Coreは、Salsa20 Coreのラウンド数を減らした変種です。これは、64オクテットの文字列から64オクテットの文字列へのハッシュ関数です。Salsa20/8 Coreは衝突耐性がないため、暗号学的ハッシュ関数ではないことに注意してください。その仕様については[SALSA20SPEC]のセクション8を、詳しい情報については[SALSA20CORE]を参照してください。安定した参照先として、エンディアン変換とアラインメントを省いたC言語によるアルゴリズムの記述を以下に示します。

void salsa20_word_specification(uint32 out[16],uint32 in[16])
{

  for (i = 0;i < 16;++i) x[i] = in[i];
  for (i = 8;i > 0;i -= 2) {

    x[ 1] ^= R(x[13]+x[ 9],13);  x[ 5] ^= R(x[ 1]+x[13],18);
    x[14] ^= R(x[10]+x[ 6], 7);  x[ 2] ^= R(x[14]+x[10], 9);

    x[ 3] ^= R(x[15]+x[11], 7);  x[ 7] ^= R(x[ 3]+x[15], 9);
    x[11] ^= R(x[ 7]+x[ 3],13);  x[15] ^= R(x[11]+x[ 7],18);
    x[ 1] ^= R(x[ 0]+x[ 3], 7);  x[ 2] ^= R(x[ 1]+x[ 0], 9);
    x[ 3] ^= R(x[ 2]+x[ 1],13);  x[ 0] ^= R(x[ 3]+x[ 2],18);

4. The scryptBlockMix Algorithm

4. scryptBlockMixアルゴリズム

The scryptBlockMix algorithm is the same as the BlockMix algorithm described in [SCRYPT] but with Salsa20/8 Core used as the hash function H. Below, Salsa(T) corresponds to the Salsa20/8 Core function applied to the octet vector T.

scryptBlockMixアルゴリズムは、[SCRYPT]で説明されているBlockMixアルゴリズムと同じですが、ハッシュ関数HとしてSalsa20/8 Coreを使います。以下では、Salsa(T)は、オクテットベクトルTにSalsa20/8 Core関数を適用したものに相当します。

Parameters:
r
Block size parameter.
Input:
B[0] || B[1] || ... || B[2 * r - 1]
Input octet string (of size 128 * r octets), treated as 2 * r 64-octet blocks, where each element in B is a 64-octet block.
Output:
B'[0] || B'[1] || ... || B'[2 * r - 1]
Output octet string.
パラメーター：
r
ブロックサイズパラメーター。
入力：
B[0] || B[1] || ... || B[2 * r - 1]
入力オクテット文字列（サイズは128 * rオクテット）。2 * r個の64オクテットブロックとして扱い、Bの各要素は64オクテットのブロックです。
出力：
B'[0] || B'[1] || ... || B'[2 * r - 1]

Steps:

手順：

  2. for i = 0 to 2 * r - 1 do
  T = X xor B[i]
  X = Salsa (T)
  Y[i] = X
end for

  3. B' = (Y[0], Y[2], ..., Y[2 * r - 2],
      Y[1], Y[3], ..., Y[2 * r - 1])

5. The scryptROMix Algorithm

  X = scryptBlockMix (T)
end for

  4. B' = X

14. セキュリティーに関する考慮事項

This document specifies a cryptographic algorithm, and there is always a risk that someone will find a weakness in it. By following the cryptographic research area, you may learn of publications relevant to scrypt.

この文書は暗号アルゴリズムを規定しており、誰かがその弱点を見つけるリスクは常に存在します。暗号の研究分野の動向を追うことで、scryptに関連する出版物を知ることができるでしょう。

ROMix has been proven sequential memory-hard under the random oracle model for the hash function. The security of scrypt relies on the assumption that BlockMix with Salsa20/8 Core does not exhibit any "shortcuts" that would allow it to be iterated more easily than a random oracle. For other claims about the security properties, see [SCRYPT].

ROMixは、ハッシュ関数についてのランダムオラクルモデルのもとで、逐次メモリーハード（sequential memory-hard）であることが証明されています。scryptの安全性は、Salsa20/8 Coreを用いたBlockMixが、ランダムオラクルよりも容易に反復できるような「近道」を一切持たないという前提に依存しています。安全性に関するその他の主張については、[SCRYPT]を参照してください。

Passwords and other sensitive data, such as intermediate values, may continue to be stored in memory, core dumps, swap areas, etc., for a long time after the implementation has processed them. This makes attacks on the implementation easier. Thus, implementation should consider storing sensitive data in protected memory areas. How to achieve this is system dependent.

パスワードや、中間値などのその他の機密データは、実装がそれらを処理した後も長い間、メモリー、コアダンプ、スワップ領域などに保存され続ける可能性があります。これにより、実装に対する攻撃が容易になります。したがって、実装は、機密データを保護されたメモリー領域に保存することを検討すべきです。これを実現する方法はシステムに依存します。

By nature and depending on parameters, running the scrypt algorithm may require large amounts of memory. Systems should protect against a denial-of-service attack resulting from attackers presenting unreasonably large parameters.

その性質上、パラメーターによっては、scryptアルゴリズムの実行に大量のメモリーが必要になる場合があります。システムは、攻撃者が不当に大きなパラメーターを提示することによるサービス拒否攻撃から保護すべきです。

Poor parameter choices can be harmful for security; for example, if you tune the parameters so that memory use is reduced to small amounts that will affect the properties of the algorithm.

パラメーターの選択を誤ると、セキュリティーを損なう可能性があります。たとえば、メモリー使用量が少量にまで削減されるようにパラメーターを調整すると、アルゴリズムの特性に影響が生じます。
