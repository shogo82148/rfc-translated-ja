RFC 7931

NFSv4.0 Migration: Specification Update

RFC 7931

NFSv4.0の移行：仕様の更新

Abstract

概要

The migration feature of NFSv4 allows the transfer of responsibility for a single file system from one server to another without disruption to clients. Recent implementation experience has shown problems in the existing specification for this feature in NFSv4.0. This document identifies the problem areas and provides revised specification text that updates the NFSv4.0 specification in RFC 7530.

NFSv4の移行（migration）機能を使用すると、クライアントの動作を中断させることなく、単一のファイルシステムに対する責任をあるサーバーから別のサーバーへ移すことができます。最近の実装経験により、NFSv4.0におけるこの機能の既存の仕様に問題があることがわかりました。この文書は、問題のある領域を特定し、RFC 7530のNFSv4.0仕様を更新する改訂された仕様のテキストを提供します。

1. Introduction

1. はじめに

This Standards Track document corrects the existing definitive specification of the NFSv4.0 protocol described in [RFC7530]. Given this fact, one should take the current document into account when learning about NFSv4.0, particularly if one is concerned with issues that relate to:

この標準化過程の文書は、[RFC7530]に記述されているNFSv4.0プロトコルの既存の決定版の仕様を訂正するものです。このため、NFSv4.0について学ぶときには、この文書を考慮に入れるべきです。特に、次に関連する問題に関心がある場合はそうです：

  • File system migration, particularly when it involves transparent state migration.
  • The construction and interpretation of the nfs_client_id4 structure and particularly the requirements on the id string within it, referred to below as a "client ID string".
  • ファイルシステムの移行。特に、透過的な状態移行を伴う場合。
  • nfs_client_id4構造体の構築と解釈。特に、その中のid文字列（以下では「クライアントID文字列」と呼びます）に関する要件。

3. Definitions

3. 定義

3.1. Terminology

3.1. 用語

The following definitions are included to provide an appropriate context for the reader. This section is derived from Section 1.5 of [RFC7530] but has been adapted to the needs of this document.

読者に適切な文脈を提供するために、次の定義を含めています。このセクションは[RFC7530]のセクション1.5から派生したものですが、この文書の必要に合わせて調整されています。

Boot Instance Id:
A boot instance id is an identifier, such as a boot time, allowing two different instances of the same client to be reliably distinguished. A boot instance id is opaque to the server and is often used as the verifier field in the nfs_client_id4 structure, which identifies the client to the server.
Client:

A client is an entity that accesses the NFS server's resources. The client may be an application that contains the logic to access the NFS server directly. The client may also be the traditional operating system client that provides remote file system services for a set of applications.

With reference to byte-range locking, the client is also the entity that maintains a set of locks on behalf of one or more applications. This client is responsible for crash or failure recovery for those locks it manages.

Note that multiple clients may share the same transport and connection, and multiple clients may exist on the same network node.

Client ID:
A client ID is a 64-bit quantity (in the form of a clientid4) used as a unique, shorthand reference to a particular client instance, identified by a client-supplied verifier (in the form of a boot instance id) and client ID string. The server is responsible for supplying the client ID.
File System:
A file system is the collection of objects on a server that share the same fsid attribute (see Section 5.8.1.9 of [RFC7530]).
Grace Period:
A grace period is an interval of time during which the server will only grant locking requests to reclaim existing locks but not those that create new locks. This gives clients an opportunity to re-establish locking state in response to a potentially disruptive event. The grace period may be general to help deal with server reboot, or it may be specific to a file system to deal with file system migration when transparent state migration is not provided.
Lease:

A lease is an interval of time defined by the server for which the client is irrevocably granted a lock. At the end of a lease period, the lock may be revoked if the lease has not been extended. The lock must be revoked if a conflicting lock has been granted after the lease interval.

All leases granted by a server have the same fixed duration. Note that the fixed interval duration was chosen to alleviate the expense a server would have in maintaining state about variable-length leases across server failures.

Lock:
The term "lock" is used to refer to record (byte-range) locks as well as share reservations unless specifically stated otherwise.
Lock-Owner:
Each byte-range lock is associated with a specific lock-owner and an open-owner. The lock-owner consists of a client ID and an opaque owner string. The client presents this to the server to establish the ownership of the byte-range lock as needed.
Open-Owner:
Each open file is associated with a specific open-owner, which consists of a client ID and an opaque owner string. The client presents this to the server to establish the ownership of the open as needed.
Server:
A server is an entity responsible for coordinating client access to a set of file systems.
Stateid:
A stateid is a 128-bit quantity returned by a server that uniquely identifies the open and locking states provided by the server for a specific open-owner or lock-owner/open-owner pair for a specific file and type of lock.
Trunking:
A situation in which multiple physical addresses are connected to the same logical server.
Verifier:
A verifier is a quantity, in the form of a verifier4, that allows one party to an interaction to be aware of a reinitialization or other significant change to the state of the other party. In [RFC7530], this term most often designates the verifier field of an nfs_client_id4, in which a boot instance id is placed to allow the server to determine when there has been a client reboot, making it necessary to eliminate locking state associated with the previous instance of the same client.
ブートインスタンスID（Boot Instance Id）：
ブートインスタンスIDは、ブート時刻などの識別子であり、同じクライアントの2つの異なるインスタンスを確実に区別できるようにするものです。ブートインスタンスIDはサーバーにとって不透明であり、多くの場合、サーバーに対してクライアントを識別するnfs_client_id4構造体のverifierフィールドとして使用されます。
クライアント（Client）：

クライアントは、NFSサーバーのリソースにアクセスするエンティティーです。クライアントは、NFSサーバーに直接アクセスするロジックを含むアプリケーションである場合があります。また、一連のアプリケーションに対してリモートファイルシステムのサービスを提供する、従来のオペレーティングシステムのクライアントである場合もあります。

バイト範囲ロックに関しては、クライアントは、1つ以上のアプリケーションに代わってロックの集合を維持するエンティティーでもあります。このクライアントは、自身が管理するロックについて、クラッシュや障害からの回復に責任を持ちます。

複数のクライアントが同じトランスポートとコネクションを共有する場合があり、また、複数のクライアントが同じネットワークノード上に存在する場合があることに注意してください。

クライアントID（Client ID）：
クライアントIDは、（clientid4の形式の）64ビットの量であり、クライアントが提供するベリファイアー（ブートインスタンスIDの形式）とクライアントID文字列によって識別される特定のクライアントインスタンスへの、一意な短縮形の参照として使用されます。クライアントIDの提供はサーバーが担います。
ファイルシステム（File System）：
ファイルシステムは、同じfsid属性（[RFC7530]のセクション5.8.1.9を参照）を共有する、サーバー上のオブジェクトの集まりです。
猶予期間（Grace Period）：
猶予期間は、サーバーが既存のロックを再取得するためのロックリクエストだけを許可し、新しいロックを作成するロックリクエストは許可しない期間です。これにより、クライアントは、混乱を引き起こす可能性のある事象に対応してロック状態を再確立する機会を得られます。猶予期間は、サーバーの再起動に対処するための全般的なものである場合もあれば、透過的な状態移行が提供されない場合にファイルシステムの移行に対処するための、特定のファイルシステムに固有のものである場合もあります。
リース（Lease）：

リースは、サーバーによって定義される期間であり、その期間についてクライアントはロックを取り消し不能な形で許可されます。リース期間の終了時に、リースが延長されていない場合、ロックは取り消される可能性があります。リース期間の後に競合するロックが許可された場合、ロックは取り消されなければなりません。

サーバーが許可するすべてのリースは、同じ固定の期間を持ちます。固定の期間が選ばれたのは、サーバーの障害をまたいで可変長のリースに関する状態を維持するためにサーバーが負うことになる負担を軽減するためであることに注意してください。

ロック（Lock）：
「ロック」という用語は、特に明記しない限り、レコード（バイト範囲）ロックと共有予約の両方を指すために使用されます。
Lock-Owner：
各バイト範囲ロックは、特定のlock-ownerとopen-ownerに関連付けられます。lock-ownerは、クライアントIDと不透明なオーナー文字列から構成されます。クライアントは、必要に応じてバイト範囲ロックの所有権を確立するために、これをサーバーに提示します。
Open-Owner：
オープンされた各ファイルは、特定のopen-ownerに関連付けられます。open-ownerは、クライアントIDと不透明なオーナー文字列から構成されます。クライアントは、必要に応じてオープンの所有権を確立するために、これをサーバーに提示します。
サーバー（Server）：
サーバーは、一連のファイルシステムへのクライアントのアクセスを調整する責任を持つエンティティーです。
Stateid：
stateidは、サーバーによって返される128ビットの量であり、特定のファイルとロックの種類について、特定のopen-ownerまたはlock-owner/open-ownerの組に対してサーバーが提供するオープンとロックの状態を一意に識別します。
トランキング（Trunking）：
複数の物理アドレスが同じ論理サーバーに接続されている状況です。
ベリファイアー（Verifier）：
ベリファイアーは、verifier4の形式の量であり、やり取りの一方の当事者が、もう一方の当事者の状態の再初期化やその他の重要な変化に気付けるようにするものです。[RFC7530]では、この用語は多くの場合、nfs_client_id4のverifierフィールドを指します。このフィールドにはブートインスタンスIDが入れられ、サーバーはこれによってクライアントの再起動があったかどうかを判断できます。クライアントの再起動があった場合は、同じクライアントの以前のインスタンスに関連付けられたロック状態を削除する必要があります。

4. Background

4. 背景

Implementation experience with transparent state migration has exposed a number of problems with the then existing specifications of this feature in [RFC7530] and predecessors. The symptoms were:

透過的な状態移行の実装経験により、[RFC7530]とそれ以前の文書に含まれていた、この機能に関する当時の既存の仕様の問題がいくつか明らかになりました。その症状は次のとおりです：

  • After migration of a file system, a reboot of the associated client was not appropriately dealt with, in that the state associated with the rebooting client was not promptly freed.
  • Situations can arise whereby a given server has multiple leases with the same nfs_client_id4 (consisting of id and verifier fields), when the protocol clearly assumes there can be only one.
  • Excessive client implementation complexity since clients have to deal with situations in which a single client can wind up with its locking state with a given server divided among multiple leases each with its own clientid4.
  • ファイルシステムの移行後、関連するクライアントの再起動が適切に処理されませんでした。つまり、再起動したクライアントに関連付けられた状態がすぐには解放されませんでした。
  • プロトコルは明らかにリースが1つしか存在しないことを前提としているにもかかわらず、あるサーバーが同じnfs_client_id4（idフィールドとverifierフィールドから構成されます）を持つ複数のリースを持つ状況が生じることがあります。
  • クライアントの実装が過度に複雑になります。これは、単一のクライアントの、あるサーバーとのロック状態が、それぞれ独自のclientid4を持つ複数のリースに分割されてしまう状況に、クライアントが対処しなければならないからです。

An analysis of these symptoms leads to the conclusion that existing specifications have erred. They assume that locking state, including both state ids and clientid4s, should be transferred as part of transparent state migration. The troubling symptoms arise from the failure to describe how migrating state is to be integrated with existing client definition structures on the destination server.

これらの症状を分析した結果、既存の仕様が誤っていたという結論に至りました。既存の仕様は、stateidとclientid4の両方を含むロック状態が、透過的な状態移行の一部として転送されるべきであると想定しています。厄介な症状が生じるのは、移行される状態を移行先サーバー上の既存のクライアント定義の構造とどのように統合するかが記述されていないためです。

The need for the server to appropriately merge stateids associated with a common client boot instance encounters a difficult problem. The issue is that the common client practice with regard to the presentation of unique strings specifying client identity makes it essentially impossible for the client to determine whether or not two stateids, originally generated on different servers, are referable to the same client. This practice is allowed and endorsed by the existing NFSv4.0 specification [RFC7530].

共通のクライアントのブートインスタンスに関連付けられたstateidをサーバーが適切にマージする必要性は、難しい問題に直面します。問題は、クライアントのアイデンティティーを指定する一意な文字列の提示に関する一般的なクライアントの慣行により、元々異なるサーバー上で生成された2つのstateidが同じクライアントに帰属するかどうかを、クライアントが判断することが本質的に不可能になっていることです。この慣行は、既存のNFSv4.0仕様[RFC7530]によって許可され、支持されています。

However, upon the prototyping of clients implementing an alternative approach, it has been found that there exist servers that do not work well with these new clients. It appears that current circumstances, in which a particular client implementation pattern had been adopted universally, have resulted in some servers not being able to interoperate against alternate client implementation patterns. As a result, we have a situation that requires careful attention to untangling compatibility issues.

しかし、別の方式を実装したクライアントのプロトタイプを作成したところ、これらの新しいクライアントとうまく動作しないサーバーが存在することがわかりました。特定のクライアントの実装パターンが普遍的に採用されてきたという現在の状況により、一部のサーバーは別のクライアントの実装パターンと相互運用できなくなっているようです。その結果、互換性の問題を解きほぐすために注意深い配慮を要する状況になっています。

This document updates the existing NFSv4.0 specification [RFC7530] as follows:

この文書は、既存のNFSv4.0仕様[RFC7530]を次のように更新します：

  • NFSv4.0がクライアントID文字列の構築について複数の方式をサポートしていることを明確にします。これには、以前に既存のNFSV4.0仕様で支持されていた方式と、現在広く展開されている方式が含まれます。
  • 複数のサーバーに提示されるクライアントID文字列を、クライアントがどのように効果的に使用できるかを説明します。

5.2. Client Identity Data Items

5.2. クライアントアイデンティティーのデータ項目

The NFSv4 protocol contains a number of protocol entities to identify clients and client-based entities for locking-related purposes:

NFSv4プロトコルには、ロックに関連する目的のために、クライアントとクライアントに基づくエンティティーを識別するプロトコルエンティティーがいくつか含まれています：

  • The nfs_client_id4 structure, which uniquely identifies a specific client boot instance. That identification is presented to the server by doing a SETCLIENTID operation. The SETCLIENTID operation is described in Section 8.4, which modifies a description in Section 16.33 of [RFC7530].
  • The clientid4, which is returned by the server upon completion of a successful SETCLIENTID operation. This id is used by the client to identify itself when doing subsequent locking-related operations. A clientid4 is associated with a particular lease whereby a client instance holds state on a server instance and may become invalid due to client reboot, server reboot, or other circumstances.
  • Opaque arrays, which are used together with the clientid4 to designate within-client entities (e.g., processes) as the owners of opens (open-owners) and owners of byte-range locks (lock-owners).
  • nfs_client_id4構造体。これは、特定のクライアントのブートインスタンスを一意に識別します。この識別は、SETCLIENTID操作を行うことによってサーバーに提示されます。SETCLIENTID操作はセクション8.4で説明されており、これは[RFC7530]のセクション16.33の説明を修正するものです。
  • clientid4。これは、SETCLIENTID操作が正常に完了したときにサーバーによって返されます。このidは、クライアントが後続のロック関連の操作を行う際に自身を識別するために使用されます。clientid4は、クライアントインスタンスがサーバーインスタンス上で状態を保持するための特定のリースに関連付けられ、クライアントの再起動、サーバーの再起動、またはその他の状況によって無効になる場合があります。
  • 不透明な配列。これは、clientid4と一緒に使用され、クライアント内のエンティティー（たとえば、プロセス）を、オープンのオーナー（open-owner）やバイト範囲ロックのオーナー（lock-owner）として指定します。

5.2.1. Client Identity Structure

5.2.1. クライアントアイデンティティーの構造体

The basis of the client identification infrastructure is encapsulated in the following data structure, which also appears in Section 9.1.1 of [RFC7530]:

クライアント識別の基盤の基本は、次のデータ構造体にカプセル化されています。これは[RFC7530]のセクション9.1.1にも記載されています：

struct nfs_client_id4 {
        verifier4       verifier;
        opaque          id<NFS4_OPAQUE_LIMIT>;
};

struct nfs_client_id4 {
        verifier4       verifier;
        opaque          id<NFS4_OPAQUE_LIMIT>;
};

The nfs_client_id4 structure uniquely defines a particular client boot instance as follows:

nfs_client_id4構造体は、特定のクライアントのブートインスタンスを次のように一意に定義します：

  • The id field is a variable-length string that uniquely identifies a specific client. Although it is described here as a string and is often referred to as a "client string", it should be understood that the protocol defines this as opaque data. In particular, those receiving such an id should not assume that it will be in the UTF-8 encoding. Servers MUST NOT reject an nfs_client_id4 simply because the id string does not follow the rules of UTF-8 encoding.

    The encoding and decoding processes for this field (e.g., use of network byte order) need to result in the same internal representation whatever the endianness of the originating and receiving machines.

  • The verifier field contains a client boot instance identifier that is used by the server to detect client reboots. Only if the boot instance is different from that which the server has previously recorded in connection with the client (as identified by the id field) does the server cancel the client's leased state. This cancellation occurs once it receives confirmation of the new nfs_clientd4 via SETCLIENTID_CONFIRM. The SETCLIENTID_CONFIRM operation is described in Section 16.34 of [RFC7530].

    In order to prevent the possibility of malicious destruction of the locking state associated with a client, the server MUST NOT cancel a client's leased state if the principal that established the state for a given id string is not the same as the principal issuing the SETCLIENTID.

  • idフィールドは、特定のクライアントを一意に識別する可変長の文字列です。ここでは文字列として説明し、しばしば「クライアント文字列」と呼ばれますが、プロトコルはこれを不透明なデータとして定義していることを理解すべきです。特に、そのようなidを受け取る側は、それがUTF-8エンコーディングであると想定すべきではありません。サーバーは、id文字列がUTF-8エンコーディングの規則に従っていないという理由だけでnfs_client_id4を拒否してはなりません（MUST NOT）。

    このフィールドのエンコードとデコードの処理（たとえば、ネットワークバイトオーダーの使用）は、送信元と受信側のマシンのエンディアンにかかわらず、同じ内部表現にならなければなりません。

  • verifierフィールドには、サーバーがクライアントの再起動を検出するために使用する、クライアントのブートインスタンス識別子が含まれます。サーバーは、ブートインスタンスが（idフィールドによって識別される）そのクライアントに関して以前に記録したものと異なる場合にのみ、クライアントのリースされた状態を取り消します。この取り消しは、SETCLIENTID_CONFIRMによって新しいnfs_clientd4の確認を受け取った時点で行われます。SETCLIENTID_CONFIRM操作は[RFC7530]のセクション16.34で説明されています。

    クライアントに関連付けられたロック状態が悪意を持って破壊される可能性を防ぐために、特定のid文字列について状態を確立したプリンシパルが、SETCLIENTIDを発行したプリンシパルと同じでない場合、サーバーはクライアントのリースされた状態を取り消してはなりません（MUST NOT）。

There are several considerations for how the client generates the id string:

クライアントがid文字列をどのように生成するかについては、いくつかの考慮事項があります：

  • The string should be unique so that multiple clients do not present the same string. The consequences of two clients presenting the same string range from one client getting an error to one client having its leased state abruptly and unexpectedly canceled.
  • The string should be selected so that subsequent incarnations (e.g., reboots) of the same client cause the client to present the same string. The implementer is cautioned against an approach that requires the string to be recorded in a local file because this precludes the use of the implementation in an environment where there is no local disk and all file access is from an NFSv4 server.

  • The string MAY be different for each server network address that the client accesses rather than common to all server network addresses.

    The considerations that might influence a client to use different strings for different network server addresses are explained in Section 5.4.

  • The algorithm for generating the string should not assume that the clients' network addresses will remain the same for any set period of time. Even while the client is still running in its current incarnation, changes might occur between client incarnations.

    Changes to the client ID string due to network address changes would result in successive SETCLIENTID operations for the same client appearing as from different clients, interfering with the use of the nfs_client_id4 verifier field to cancel state associated with previous boot instances of the same client.

    The difficulty is more severe if the client address is the only client-based information in the client ID string. In such a case, there is a real risk that after the client gives up the network address, another client, using the same algorithm, would generate a conflicting id string. This would be likely to cause an inappropriate loss of locking state. See Section 5.9 for detailed guidance regarding client ID string construction.

  • 複数のクライアントが同じ文字列を提示しないように、文字列は一意であるべきです。2つのクライアントが同じ文字列を提示した場合の結果は、一方のクライアントがエラーを受け取ることから、一方のクライアントのリースされた状態が突然予期せず取り消されることまで、さまざまです。
  • 文字列は、同じクライアントの後続のインカーネーション（たとえば、再起動）でもクライアントが同じ文字列を提示するように選択されるべきです。実装者は、文字列をローカルファイルに記録する必要がある方式に注意してください。そのような方式では、ローカルディスクがなく、すべてのファイルアクセスがNFSv4サーバーから行われる環境で実装を使用できなくなるからです。

  • 文字列は、すべてのサーバーのネットワークアドレスで共通にするのではなく、クライアントがアクセスするサーバーのネットワークアドレスごとに異なってもよいです（MAY）。

    クライアントがネットワークサーバーアドレスごとに異なる文字列を使用するかどうかに影響を与える可能性のある考慮事項は、セクション5.4で説明します。

  • 文字列を生成するアルゴリズムは、クライアントのネットワークアドレスが一定の期間同じままであると想定すべきではありません。クライアントが現在のインカーネーションで実行中であっても変更は起こりえますし、クライアントのインカーネーションの間でも変更は起こりえます。

    ネットワークアドレスの変更によってクライアントID文字列が変わると、同じクライアントからの連続したSETCLIENTID操作が異なるクライアントからのものに見えてしまいます。その結果、同じクライアントの以前のブートインスタンスに関連付けられた状態を取り消すためにnfs_client_id4のverifierフィールドを使用することが妨げられます。

    クライアントアドレスがクライアントID文字列内の唯一のクライアントに基づく情報である場合、問題はより深刻になります。そのような場合、クライアントがネットワークアドレスを手放した後に、同じアルゴリズムを使用する別のクライアントが、競合するid文字列を生成してしまうという現実的なリスクがあります。これにより、ロック状態が不適切に失われる可能性が高くなります。クライアントID文字列の構築に関する詳細なガイダンスについては、セクション5.9を参照してください。

5.2.2. Client Identity Shorthand

5.2.2. クライアントアイデンティティーの短縮形

Once a SETCLIENTID and SETCLIENTID_CONFIRM sequence has successfully completed, the client uses the shorthand client identifier, of type clientid4, instead of the longer and less compact nfs_client_id4 structure. This shorthand client identifier (a client ID) is assigned by the server and should be chosen so that it will not conflict with a client ID previously assigned by the same server and, to the degree practicable, by other servers as well. This applies across server restarts or reboots.

SETCLIENTIDとSETCLIENTID_CONFIRMの一連の操作が正常に完了すると、クライアントは、より長くてコンパクトでないnfs_client_id4構造体の代わりに、clientid4型の短縮形のクライアント識別子を使用します。この短縮形のクライアント識別子（クライアントID）はサーバーによって割り当てられ、同じサーバーが以前に割り当てたクライアントIDや、実用的な範囲で他のサーバーが割り当てたクライアントIDとも競合しないように選ばれるべきです。これは、サーバーの再起動やリブートをまたいでも当てはまります。

Establishment of the client ID by a new incarnation of the client also has the effect of immediately breaking any leased state that a previous incarnation of the client might have had on the server, as opposed to forcing the new client incarnation to wait for the leases to expire. Breaking the lease state amounts to the server removing all locks, share reservations, and delegation states not requested using the CLAIM_DELEGATE_PREV claim type associated with a client having the same identity. For a discussion of delegation state recovery, see Section 10.2.1 of [RFC7530].

クライアントの新しいインカーネーションによるクライアントIDの確立には、クライアントの以前のインカーネーションがサーバー上に持っていた可能性のあるリースされた状態を、新しいクライアントのインカーネーションにリースの期限切れを待たせるのではなく、直ちに破棄するという効果もあります。リースの状態を破棄するということは、同じアイデンティティーを持つクライアントに関連付けられた、すべてのロック、共有予約、およびCLAIM_DELEGATE_PREVのクレームタイプを使用して要求されたものではない委任の状態を、サーバーが削除することに相当します。委任の状態の回復に関する説明については、[RFC7530]のセクション10.2.1を参照してください。

Note that the SETCLIENTID and SETCLIENTID_CONFIRM operations have a secondary purpose of establishing the information the server needs to make callbacks to the client for the purpose of supporting delegations. The client is able to change this information via SETCLIENTID and SETCLIENTID_CONFIRM within the same incarnation of the client without causing removal of the client's leased state.

SETCLIENTID操作とSETCLIENTID_CONFIRM操作には、委任をサポートする目的でサーバーがクライアントへのコールバックを行うために必要な情報を確立するという、副次的な目的があることに注意してください。クライアントは、クライアントの同じインカーネーション内で、クライアントのリースされた状態を削除させることなく、SETCLIENTIDとSETCLIENTID_CONFIRMによってこの情報を変更できます。

Distinct servers MAY assign clientid4s independently, and they will generally do so. Therefore, a client has to be prepared to deal with multiple instances of the same clientid4 value received on distinct IP addresses, denoting separate entities. When trunking of server IP addresses is not a consideration, a client should keep track of <IP-address, clientid4> pairs, so that each pair is distinct. For a discussion of how to address the issue in the face of possible trunking of server IP addresses, see Section 5.4.

異なるサーバーは、clientid4を独立して割り当ててもよいです（MAY）。また、一般にそうするでしょう。したがって、クライアントは、異なるIPアドレスで受け取った同じclientid4の値の複数のインスタンスが、別個のエンティティーを表している場合に対処できるように準備しておく必要があります。サーバーIPアドレスのトランキングを考慮する必要がない場合、クライアントは<IP-address, clientid4>の組を追跡し、それぞれの組が区別されるようにすべきです。サーバーIPアドレスのトランキングの可能性がある場合にこの問題にどのように対処するかについては、セクション5.4を参照してください。

Owners of opens and owners of byte-range locks are separate entities and remain separate even if the same opaque arrays are used to designate owners of each. The protocol distinguishes between open-owners (represented by open_owner4 structures) and lock-owners (represented by lock_owner4 structures).

オープンのオーナーとバイト範囲ロックのオーナーは別個のエンティティーであり、それぞれのオーナーを指定するために同じ不透明な配列が使用される場合でも別個のままです。このプロトコルは、open-owner（open_owner4構造体で表されます）とlock-owner（lock_owner4構造体で表されます）を区別します。

Both sorts of owners consist of a clientid4 and an opaque owner string. For each client, there is a set of distinct owner values used with that client which constitutes the set of known owners of that type, for the given client.

どちらの種類のオーナーも、clientid4と不透明なオーナー文字列から構成されます。各クライアントについて、そのクライアントで使用される異なるオーナーの値の集合が、そのクライアントにとってのその種類の既知のオーナーの集合を構成します。

Each open is associated with a specific open-owner while each byte-range lock is associated with a lock-owner and an open-owner, the latter being the open-owner associated with the open file under which the LOCK operation was done.

各オープンは特定のopen-ownerに関連付けられます。一方、各バイト範囲ロックはlock-ownerとopen-ownerに関連付けられ、後者は、LOCK操作がその下で行われたオープンされたファイルに関連付けられたopen-ownerです。

When a clientid4 is presented to a server and that clientid4 is not valid, the server will reject the request with an error that depends on the reason for clientid4 invalidity. The error NFS4ERR_ADMIN_REVOKED is returned when the invalidation is the result of administrative action. When the clientid4 is unrecognizable, the error NFS4ERR_STALE_CLIENTID or NFS4ERR_EXPIRED may be returned. An unrecognizable clientid4 can occur for a number of reasons:

clientid4がサーバーに提示され、そのclientid4が有効でない場合、サーバーは、clientid4が無効である理由に応じたエラーでリクエストを拒否します。無効化が管理上の措置の結果である場合は、エラーNFS4ERR_ADMIN_REVOKEDが返されます。clientid4が認識できない場合は、エラーNFS4ERR_STALE_CLIENTIDまたはNFS4ERR_EXPIREDが返される場合があります。認識できないclientid4は、さまざまな理由で発生する可能性があります：

  • A server reboot causing loss of the server's knowledge of the client. (Always returns NFS4ERR_STALE_CLIENTID.)
  • Client error sending an incorrect clientid4 or a valid clientid4 to the wrong server. (May return either error.)
  • Loss of lease state due to lease expiration. (Always returns NFS4ERR_EXPIRED.)
  • Client or server error causing the server to believe that the client has rebooted (i.e., receiving a SETCLIENTID with an nfs_client_id4 that has a matching id string and a non-matching boot instance id as the verifier). (May return either error.)
  • Migration of all state under the associated lease causes its non-existence to be recognized on the source server. (Always returns NFS4ERR_STALE_CLIENTID.)
  • Merger of state under the associated lease with another lease under a different client ID causes the clientid4 serving as the source of the merge to cease being recognized on its server. (Always returns NFS4ERR_STALE_CLIENTID.)
  • サーバーの再起動によって、サーバーがクライアントに関する知識を失った場合。（常にNFS4ERR_STALE_CLIENTIDを返します。）
  • クライアントのエラーによって、誤ったclientid4を送信したか、有効なclientid4を誤ったサーバーに送信した場合。（どちらのエラーを返す場合もあります。）
  • リースの期限切れによってリースの状態が失われた場合。（常にNFS4ERR_EXPIREDを返します。）
  • クライアントまたはサーバーのエラーによって、クライアントが再起動したとサーバーが判断した場合（つまり、id文字列が一致し、verifierとしてのブートインスタンスIDが一致しないnfs_client_id4を持つSETCLIENTIDを受け取った場合）。（どちらのエラーを返す場合もあります。）
  • 関連するリースの下にあるすべての状態の移行によって、移行元サーバー上でそのリースが存在しないと認識される場合。（常にNFS4ERR_STALE_CLIENTIDを返します。）
  • 関連するリースの下にある状態が、異なるクライアントIDの下にある別のリースとマージされることによって、マージ元となったclientid4がそのサーバー上で認識されなくなる場合。（常にNFS4ERR_STALE_CLIENTIDを返します。）

In the event of a server reboot, loss of lease state due to lease expiration, or administrative revocation of a clientid4, the client must obtain a new clientid4 by use of the SETCLIENTID operation and then proceed to any other necessary recovery for the server reboot case (see Section 9.6.2 in [RFC7530]). In cases of server or client error resulting in a clientid4 becoming unusable, use of SETCLIENTID to establish a new lease is desirable as well.

サーバーの再起動、リースの期限切れによるリースの状態の喪失、またはclientid4の管理上の取り消しが発生した場合、クライアントは、SETCLIENTID操作を使用して新しいclientid4を取得し、その後、サーバーの再起動の場合に必要なその他の回復処理に進まなければなりません（[RFC7530]のセクション9.6.2を参照）。サーバーまたはクライアントのエラーによってclientid4が使用できなくなった場合も、SETCLIENTIDを使用して新しいリースを確立することが望ましいです。

In cases in which loss of server knowledge of a clientid4 is the result of migration, different recovery procedures are required. See Section 6.1.1 for details. Note that in cases in which there is any uncertainty about which sort of handling is applicable, the distinguishing characteristic is that in reboot-like cases, the clientid4 and all associated stateids cease to exist while in migration-related cases, the clientid4 ceases to exist while the stateids are still valid.

clientid4に関するサーバーの知識の喪失が移行の結果である場合は、異なる回復手順が必要です。詳細についてはセクション6.1.1を参照してください。どちらの種類の処理が適用されるかが少しでも不確かな場合、区別する特徴は次のとおりであることに注意してください。再起動に類する場合は、clientid4と関連するすべてのstateidが存在しなくなります。一方、移行に関連する場合は、clientid4は存在しなくなりますが、stateidは引き続き有効です。

The client must also employ the SETCLIENTID operation when it receives an NFS4ERR_STALE_STATEID error using a stateid derived from its current clientid4, since this indicates a situation, such as a server reboot that has invalidated the existing clientid4 and associated stateids (see Section 9.1.5 in [RFC7530] for details).

クライアントは、現在のclientid4から導出されたstateidを使用してNFS4ERR_STALE_STATEIDエラーを受け取った場合にも、SETCLIENTID操作を使用しなければなりません。これは、サーバーの再起動のように、既存のclientid4と関連するstateidを無効にした状況を示しているからです（詳細については[RFC7530]のセクション9.1.5を参照）。

See the detailed descriptions of SETCLIENTID (in Section 8.4) and SETCLIENTID_CONFIRM (in Section 16.34 of [RFC7530]) for a complete specification of these operations.

これらの操作の完全な仕様については、SETCLIENTID（セクション8.4）とSETCLIENTID_CONFIRM（[RFC7530]のセクション16.34）の詳細な説明を参照してください。

5.3. Server Release of Client ID

5.3. サーバーによるクライアントIDの解放

If the server determines that the client holds no associated state for its clientid4, the server may choose to release that clientid4. The server may make this choice for an inactive client so that resources are not consumed by those intermittently active clients. If the client contacts the server after this release, the server must ensure the client receives the appropriate error so that it will use the SETCLIENTID/SETCLIENTID_CONFIRM sequence to establish a new identity. It should be clear that the server must be very hesitant to release a client ID since the resulting work on the client to recover from such an event will be the same burden as if the server had failed and restarted. Typically, a server would not release a client ID unless there had been no activity from that client for many minutes.

クライアントがそのclientid4に関連付けられた状態を何も保持していないとサーバーが判断した場合、サーバーはそのclientid4を解放することを選択できます。サーバーは、断続的にしかアクティブにならないクライアントによってリソースが消費されないように、非アクティブなクライアントに対してこの選択を行えます。この解放の後にクライアントがサーバーに接触した場合、サーバーは、クライアントがSETCLIENTID/SETCLIENTID_CONFIRMの一連の操作を使用して新しいアイデンティティーを確立するように、クライアントが適切なエラーを受け取ることを保証しなければなりません。そのような事象から回復するためにクライアントで生じる作業は、サーバーが故障して再起動した場合と同じ負担になるため、サーバーはクライアントIDの解放に非常に慎重でなければならないことは明らかです。通常、サーバーは、そのクライアントからの活動が何分もない場合でなければクライアントIDを解放しません。

Note that if the id string in a SETCLIENTID request is properly constructed, and if the client takes care to use the same principal for each successive use of SETCLIENTID, then, barring an active denial-of-service attack, NFS4ERR_CLID_INUSE should never be returned.

SETCLIENTIDリクエスト内のid文字列が適切に構築されており、クライアントがSETCLIENTIDを使用するたびに同じプリンシパルを使用するよう注意していれば、アクティブなサービス拒否攻撃がない限り、NFS4ERR_CLID_INUSEが返されることは決してないはずであることに注意してください。

However, client bugs, server bugs, or perhaps a deliberate change of the principal owner of the id string (such as may occur in the case in which a client changes security flavors, and under the new flavor, there is no mapping to the previous owner) will in rare cases result in NFS4ERR_CLID_INUSE.

しかし、クライアントのバグ、サーバーのバグ、あるいはid文字列のプリンシパルであるオーナーの意図的な変更（たとえば、クライアントがセキュリティーフレーバーを変更し、新しいフレーバーでは以前のオーナーへの対応付けがない場合など）によって、まれにNFS4ERR_CLID_INUSEとなることがあります。

In situations in which there is an apparent change of principal, when the server gets a SETCLIENTID specifying a client ID string for which the server has a clientid4 that currently has no state, or for which it has state, but where the lease has expired, the server MUST allow the SETCLIENTID rather than returning NFS4ERR_CLID_INUSE. The server MUST then confirm the new client ID if followed by the appropriate SETCLIENTID_CONFIRM.

プリンシパルが明らかに変更されている状況で、現在状態を持たないclientid4、または状態を持っているがリースの期限が切れているclientid4をサーバーが持っているクライアントID文字列を指定したSETCLIENTIDをサーバーが受け取った場合、サーバーはNFS4ERR_CLID_INUSEを返すのではなく、そのSETCLIENTIDを許可しなければなりません（MUST）。その後、適切なSETCLIENTID_CONFIRMが続いた場合、サーバーは新しいクライアントIDを確認しなければなりません（MUST）。

5.4. Client ID String Approaches

5.4. クライアントID文字列の方式

One particular aspect of the construction of the nfs_client_id4 string has proved recurrently troublesome. The client has a choice of:

nfs_client_id4の文字列の構築には、繰り返し問題となってきた特定の側面が1つあります。クライアントは次のどちらかを選択できます：

  • Presenting the same id string to multiple server addresses. This is referred to as the "uniform client ID string approach" and is discussed in Section 5.6.
  • Presenting different id strings to multiple server addresses. This is referred to as the "non-uniform client ID string approach" and is discussed in Section 5.5.
  • 複数のサーバーアドレスに同じid文字列を提示する。これは「統一クライアントID文字列方式（uniform client ID string approach）」と呼ばれ、セクション5.6で説明します。
  • 複数のサーバーアドレスに異なるid文字列を提示する。これは「非統一クライアントID文字列方式（non-uniform client ID string approach）」と呼ばれ、セクション5.5で説明します。

Note that implementation considerations, including compatibility with existing servers, may make it desirable for a client to use both approaches, based on configuration information, such as mount options. This issue will be discussed in Section 5.7.

既存のサーバーとの互換性を含む実装上の考慮事項により、クライアントがマウントオプションなどの設定情報に基づいて両方の方式を使用することが望ましい場合があることに注意してください。この問題についてはセクション5.7で説明します。

Construction of the client ID string has arisen as a difficult issue because of the way in which the NFS protocols have evolved. It is useful to consider two points in that evolution.

NFSプロトコルが進化してきた経緯のために、クライアントID文字列の構築は難しい問題となっています。その進化における2つの時点を考えると役に立ちます。

  • NFSv3 as a stateless protocol had no need to identify the state shared by a particular client-server pair (see [RFC1813]). Thus, there was no need to consider the question of whether a set of requests come from the same client or whether two server IP addresses are connected to the same server. As the environment was one in which the user supplied the target server IP address as part of incorporating the remote file system in the client's file namespace, there was no occasion to take note of server trunking. Within a stateless protocol, the situation was symmetrical. The client has no server identity information, and the server has no client identity information.
  • NFSv4.1 is a stateful protocol with full support for client and server identity determination (see [RFC5661]). This enables the server to be aware when two requests come from the same client (they are on sessions sharing a clientid4) and the client to be aware when two server IP addresses are connected to the same server. Section 2.10.5.1 of [RFC5661] explains how the client is able to assure itself that the connections are to the same logical server.
  • ステートレスなプロトコルであるNFSv3では、特定のクライアントとサーバーの組が共有する状態を識別する必要がありませんでした（[RFC1813]を参照）。したがって、一連のリクエストが同じクライアントから来ているかどうかや、2つのサーバーIPアドレスが同じサーバーに接続されているかどうかという問題を考慮する必要はありませんでした。リモートファイルシステムをクライアントのファイル名前空間に組み込む際に、ユーザーがターゲットサーバーのIPアドレスを指定するという環境だったので、サーバーのトランキングに注意を払う機会はありませんでした。ステートレスなプロトコルの中では、状況は対称的でした。クライアントはサーバーのアイデンティティー情報を持たず、サーバーはクライアントのアイデンティティー情報を持ちません。
  • NFSv4.1は、クライアントとサーバーのアイデンティティーの判定を完全にサポートするステートフルなプロトコルです（[RFC5661]を参照）。これにより、サーバーは2つのリクエストが同じクライアントから来ている（clientid4を共有するセッション上にある）ことを認識でき、クライアントは2つのサーバーIPアドレスが同じサーバーに接続されていることを認識できます。[RFC5661]のセクション2.10.5.1は、コネクションが同じ論理サーバーへのものであることをクライアントがどのように確かめられるかを説明しています。

NFSv4.0 is unfortunately halfway between these two. It introduced new requirements such as the need to identify specific clients and client instances without addressing server identity issues. The two client ID string approaches have arisen in attempts to deal with the changing requirements of the protocol as implementation has proceeded, and features that were not very substantial in early implementations of NFSv4.0 became more substantial as implementation proceeded.

残念ながら、NFSv4.0はこれら2つの中間にあります。NFSv4.0は、サーバーのアイデンティティーの問題に対処しないまま、特定のクライアントとクライアントインスタンスを識別する必要性などの新しい要件を導入しました。2つのクライアントID文字列方式は、実装が進むにつれて変化するプロトコルの要件に対処しようとする試みの中で生まれたものであり、NFSv4.0の初期の実装ではそれほど重要ではなかった機能が、実装が進むにつれてより重要になりました。

  • In the absence of any implementation of features related to fs_locations (replication, referral, and migration), the situation is very similar to that of NFSv3 (see Section 8.1 and the subsections within Section 8.4 of [RFC7530] for discussion of these features). In this case, locking state has been added, but there is no need for concern about the provision of accurate client and server identity determination. This is the situation that gave rise to the non-uniform client ID string approach.
  • In the presence of replication and referrals, the client may have occasion to take advantage of knowledge of server trunking information. Even more important, transparent state migration, by transferring state among servers, causes difficulties for the non-uniform client ID string approach, in that the two different client ID strings sent to different IP addresses may wind up being processed by the same logical server, adding confusion.
  • A further consideration is that client implementations typically provide NFSv4.1 by augmenting their existing NFSv4.0 implementation, not by providing two separate implementations. Thus, the more NFSv4.0 and NFSv4.1 can work alike, the less complex the clients are. This is a key reason why those implementing NFSv4.0 clients might prefer using the uniform client string model, even if they have chosen not to provide fs_locations-related features in their NFSv4.0 client.
  • fs_locationsに関連する機能（複製、リファラル、移行）の実装がまったくない場合、状況はNFSv3の場合とよく似ています（これらの機能の説明については、[RFC7530]のセクション8.1とセクション8.4内のサブセクションを参照）。この場合、ロック状態は追加されていますが、クライアントとサーバーのアイデンティティーの正確な判定の提供について心配する必要はありません。これが、非統一クライアントID文字列方式を生み出した状況です。
  • 複製とリファラルがある場合、クライアントはサーバーのトランキング情報の知識を活用する機会があるかもしれません。さらに重要なことに、透過的な状態移行は、サーバー間で状態を転送することによって、非統一クライアントID文字列方式に困難をもたらします。異なるIPアドレスに送信された2つの異なるクライアントID文字列が、最終的に同じ論理サーバーで処理されることになり、混乱を招く可能性があるからです。
  • さらに考慮すべき点として、クライアントの実装は通常、2つの別個の実装を提供するのではなく、既存のNFSv4.0の実装を拡張することによってNFSv4.1を提供します。したがって、NFSv4.0とNFSv4.1が同じように動作できるほど、クライアントは複雑でなくなります。これは、NFSv4.0クライアントを実装する人々が、NFSv4.0クライアントでfs_locations関連の機能を提供しないことを選択した場合でも、統一クライアント文字列モデルを使用することを好む可能性がある主な理由です。

Both approaches have to deal with the asymmetry in client and server identity information between client and server. Each seeks to make the client's and the server's views match. In the process, each encounters some combination of inelegant protocol features and/or implementation difficulties. The choice of which to use is up to the client implementer, and the sections below try to give some useful guidance.

どちらの方式も、クライアントとサーバーの間での、クライアントとサーバーのアイデンティティー情報の非対称性に対処しなければなりません。どちらの方式も、クライアントの見え方とサーバーの見え方を一致させようとします。その過程で、どちらの方式も、洗練されていないプロトコルの機能や実装上の困難の何らかの組み合わせに直面します。どちらを使用するかの選択はクライアントの実装者に委ねられており、以降のセクションでは役に立つガイダンスを示すようにしています。

5.5. Non-uniform Client ID String Approach

5.5. 非統一クライアントID文字列方式

The non-uniform client ID string approach is an attempt to handle these matters in NFSv4.0 client implementations in as NFSv3-like a way as possible.

非統一クライアントID文字列方式は、NFSv4.0クライアントの実装において、これらの問題をできるだけNFSv3に近い方法で扱おうとする試みです。

For a client using the non-uniform approach, all internal recording of clientid4 values is to include, whether explicitly or implicitly, the server IP address so that one always has an <IP-address, clientid4> pair. Two such pairs from different servers are always distinct even when the clientid4 values are the same, as they may occasionally be. In this approach, such equality is always treated as simple happenstance.

非統一方式を使用するクライアントでは、clientid4の値の内部的な記録はすべて、明示的か暗黙的かにかかわらず、サーバーIPアドレスを含むものとし、常に<IP-address, clientid4>の組を持つようにします。異なるサーバーからの2つのそのような組は、clientid4の値が同じであっても（時にはそうなる場合があります）、常に区別されます。この方式では、そのような一致は常に単なる偶然として扱われます。

Making the client ID string different on different server IP addresses results in a situation in which a server has no way of tying together information from the same client, when the client accesses multiple server IP addresses. As a result, it will treat a single client as multiple clients with separate leases for each server network address. Since there is no way in the protocol for the client to determine if two network addresses are connected to the same server, the resulting lack of knowledge is symmetrical and can result in simpler client implementations in which there is a single clientid4/lease per server network address.

サーバーIPアドレスごとにクライアントID文字列を異なるものにすると、クライアントが複数のサーバーIPアドレスにアクセスしたときに、サーバーには同じクライアントからの情報を結び付ける方法がないという状況になります。その結果、サーバーは単一のクライアントを、サーバーのネットワークアドレスごとに別個のリースを持つ複数のクライアントとして扱います。2つのネットワークアドレスが同じサーバーに接続されているかどうかをクライアントが判断する方法はプロトコルにないため、結果として生じる知識の欠如は対称的であり、サーバーのネットワークアドレスごとに単一のclientid4/リースを持つ、より単純なクライアントの実装につながる可能性があります。

Support for migration, particularly with transparent state migration, is more complex in the case of non-uniform client ID strings. For example, migration of a lease can result in multiple leases for the same client accessing the same server addresses, vitiating many of the advantages of this approach. Therefore, client implementations that support migration with transparent state migration are likely to experience difficulties using the non-uniform client ID string approach and should not do so, except where it is necessary for compatibility with existing server implementations (for details of arranging use of multiple client ID string approaches, see Section 5.7).

移行のサポート、特に透過的な状態移行を伴う移行のサポートは、非統一クライアントID文字列の場合はより複雑になります。たとえば、リースの移行により、同じサーバーアドレスにアクセスする同じクライアントについて複数のリースが生じることがあり、この方式の利点の多くが損なわれます。したがって、透過的な状態移行を伴う移行をサポートするクライアントの実装は、非統一クライアントID文字列方式を使用すると困難に直面する可能性が高いため、既存のサーバーの実装との互換性のために必要な場合を除いて、この方式を使用すべきではありません（複数のクライアントID文字列方式の使用の準備に関する詳細については、セクション5.7を参照してください）。

5.6. Uniform Client ID String Approach

5.6. 統一クライアントID文字列方式

When the client ID string is kept uniform, the server has the basis to have a single clientid4/lease for each distinct client. The problem that has to be addressed is the lack of explicit server identity information, which was made available in NFSv4.1.

クライアントID文字列を統一しておくと、サーバーは異なるクライアントごとに単一のclientid4/リースを持つための根拠を得ます。対処しなければならない問題は、明示的なサーバーのアイデンティティー情報がないことです。この情報はNFSv4.1で利用可能になりました。

When the same client ID string is given to multiple IP addresses, the client can determine whether two IP addresses correspond to a single server, based on the server's behavior. This is the inverse of the strategy adopted for the non-uniform approach in which different server IP addresses are told about different clients, simply to prevent a server from manifesting behavior that is inconsistent with there being a single server for each IP address, in line with the traditions of NFS. So, to compare:

複数のIPアドレスに同じクライアントID文字列が与えられた場合、クライアントは、サーバーの振る舞いに基づいて、2つのIPアドレスが単一のサーバーに対応するかどうかを判断できます。これは、非統一方式で採用されている戦略の逆です。非統一方式では、NFSの伝統に沿って、IPアドレスごとに単一のサーバーが存在することと矛盾する振る舞いをサーバーが示すことを防ぐためだけに、異なるサーバーIPアドレスに異なるクライアントについて伝えます。比較すると、次のようになります：

  • In the non-uniform approach, servers are told about different clients because, if the server were to use accurate client identity information, two IP addresses on the same server would behave as if they were talking to the same client, which might prove disconcerting to a client not expecting such behavior.

  • In the uniform approach, the servers are told about there being a single client, which is, after all, the truth. Then, when the server uses this information, two IP addresses on the same server will behave as if they are talking to the same client, and this difference in behavior allows the client to infer the server IP address trunking configuration, even though NFSv4.0 does not explicitly provide this information.

    The approach given in the section below shows one example of how this might be done.

  • 非統一方式では、サーバーに異なるクライアントについて伝えます。その理由は、サーバーが正確なクライアントのアイデンティティー情報を使用すると、同じサーバー上の2つのIPアドレスが同じクライアントと通信しているかのように振る舞い、そのような振る舞いを予期していないクライアントを混乱させる可能性があるからです。

  • 統一方式では、サーバーに単一のクライアントが存在することを伝えます。結局のところ、それが真実です。そして、サーバーがこの情報を使用すると、同じサーバー上の2つのIPアドレスは同じクライアントと通信しているかのように振る舞います。この振る舞いの違いにより、NFSv4.0がこの情報を明示的に提供していなくても、クライアントはサーバーIPアドレスのトランキング構成を推測できます。

The uniform client ID string approach makes it necessary to exercise more care in the definition of the boot instance id sent as the verifier field in an nfs_client_id4:

統一クライアントID文字列方式では、nfs_client_id4のverifierフィールドとして送信されるブートインスタンスIDの定義に、より注意を払う必要があります：

  • In [RFC7530], the client is told to change the verifier field value when reboot occurs, but there is no explicit statement as to the converse, so that any requirement to keep the verifier field constant unless rebooting is only present by implication.
  • Many existing clients change the boot instance id every time they destroy and recreate the data structure that tracks an <IP-address, clientid4> pair. This might happen if the last mount of a particular server is removed, and then a fresh mount is created. Also, note that this might result in each <IP-address, clientid4> pair having its own boot instance id that is independent of the others.

  • Within the uniform client ID string approach, an nfs_client_id4 designates a globally known client instance, so that the verifier field should change if and only if a new client instance is created, typically as a result of a reboot.

    Clients using the uniform client ID string approach are therefore well advised to use a verifier established only once for each reboot, typically at reboot time.

  • [RFC7530]では、クライアントは再起動が発生したときにverifierフィールドの値を変更するよう指示されていますが、その逆については明示的な記述がありません。そのため、再起動しない限りverifierフィールドを一定に保つという要件は、暗に示されているにすぎません。
  • 既存のクライアントの多くは、<IP-address, clientid4>の組を追跡するデータ構造を破棄して再作成するたびに、ブートインスタンスIDを変更します。これは、特定のサーバーの最後のマウントが削除され、その後新たにマウントが作成された場合に起こる可能性があります。また、その結果、<IP-address, clientid4>の組ごとに、他とは独立した独自のブートインスタンスIDを持つことになる可能性があることにも注意してください。

  • 統一クライアントID文字列方式では、nfs_client_id4はグローバルに知られたクライアントインスタンスを指定します。そのため、verifierフィールドは、通常は再起動の結果として、新しいクライアントインスタンスが作成された場合にのみ、そしてその場合には必ず変更されるべきです。

    したがって、統一クライアントID文字列方式を使用するクライアントは、再起動ごとに一度だけ、通常は再起動時に確立されるベリファイアーを使用するのが賢明です。

The following are advantages for the implementation of using the uniform client ID string approach:

統一クライアントID文字列方式を使用することによる実装上の利点は次のとおりです：

  • Clients can take advantage of server trunking (and clustering with single-server-equivalent semantics) to increase bandwidth or reliability.
  • There are advantages in state management so that, for example, one never has a delegation under one clientid4 revoked because of a reference to the same file from the same client under a different clientid4.
  • The uniform client ID string approach allows the server to do any necessary automatic lease merger in connection with transparent state migration, without requiring any client involvement. This consideration is of sufficient weight to cause us to recommend use of the uniform client ID string approach for clients supporting transparent state migration.
  • クライアントは、帯域幅や信頼性を向上させるために、サーバーのトランキング（および単一サーバーと同等のセマンティクスを持つクラスタリング）を活用できます。
  • 状態管理において利点があります。たとえば、ある1つのclientid4の下にある委任が、同じクライアントから別のclientid4の下で同じファイルが参照されたことによって取り消されることは決してありません。
  • 統一クライアントID文字列方式により、サーバーは、クライアントの関与を必要とせずに、透過的な状態移行に関連して必要となる自動的なリースのマージを行えます。この考慮事項は十分に重要であるため、透過的な状態移行をサポートするクライアントには統一クライアントID文字列方式の使用を推奨します。

The following implementation considerations might cause issues for client implementations.

次の実装上の考慮事項は、クライアントの実装に問題を引き起こす可能性があります。

  • This approach is considerably different from the non-uniform approach, which most client implementations have been following. Until substantial implementation experience is obtained with this approach, reluctance to embrace something so new is to be expected.
  • Mapping between server network addresses and leases is more complicated in that it is no longer a one-to-one mapping.
  • この方式は、ほとんどのクライアントの実装が従ってきた非統一方式とはかなり異なります。この方式について十分な実装経験が得られるまでは、これほど新しいものを受け入れることにためらいがあるのは当然でしょう。
  • サーバーのネットワークアドレスとリースの間の対応付けは、もはや1対1の対応付けではないという点で、より複雑になります。

Another set of relevant considerations relate to privacy concerns, which users of the client might have in that use of the uniform client ID string approach would enable multiple servers acting in concert to determine when multiple requests received at different times derive from the same NFSv4.0 client. For example, this might enable determination that multiple distinct user identities in fact are likely to correspond to requests made by the same person, even when those requests are directed to different servers.

関連するもう1つの考慮事項は、クライアントのユーザーが抱く可能性のあるプライバシーの懸念に関するものです。統一クライアントID文字列方式を使用すると、複数のサーバーが協調して、異なる時点で受け取った複数のリクエストが同じNFSv4.0クライアントから来ていることを判断できるようになるからです。たとえば、これにより、異なるサーバーに向けられたリクエストであっても、複数の異なるユーザーアイデンティティーが実際には同じ人物によるリクエストに対応している可能性が高いと判断できるようになるかもしれません。

How to balance these considerations depends on implementation goals.

これらの考慮事項のバランスをどのように取るかは、実装の目標によって異なります。

5.7. Mixing Client ID String Approaches

5.7. クライアントID文字列方式の混在

As noted above, a client that needs to use the uniform client ID string approach (e.g., to support migration) may also need to support existing servers with implementations that do not work properly in this case.

前述のように、（たとえば、移行をサポートするために）統一クライアントID文字列方式を使用する必要があるクライアントは、この場合に正しく動作しない実装を持つ既存のサーバーもサポートする必要があるかもしれません。

Some examples of such server issues include:

そのようなサーバーの問題の例として、次のものがあります：

  • Some existing NFSv4.0 server implementations of IP address failover depend on clients' use of a non-uniform client ID string approach. In particular, when a server supports both its own IP address and one failed over from a partner server, it may have separate sets of state applicable to the two IP addresses, owned by different servers but residing on a single one.

    In this situation, some servers have relied on clients' use of the non-uniform client ID string approach, as suggested but not mandated by [RFC7530], to keep these sets of state separate, and they will have problems handling clients using the uniform client ID string approach, in that such clients will see changes in trunking relationships whenever server failover and giveback occur.

  • Some existing servers incorrectly return NFS4ERR_CLID_INUSE simply because there already exists a clientid4 for the same client, established using a different IP address. This causes difficulty for a multihomed client using the uniform client ID string approach.

    Although this behavior is not correct, such servers still exist, and this specification should give clients guidance about dealing with the situation, as well as making the correct behavior clear.

  • 既存のNFSv4.0サーバーにおけるIPアドレスのフェイルオーバーの実装には、クライアントが非統一クライアントID文字列方式を使用することに依存しているものがあります。特に、サーバーが自身のIPアドレスと、パートナーサーバーからフェイルオーバーされたIPアドレスの両方をサポートしている場合、サーバーは2つのIPアドレスに適用される別々の状態の集合を持つことがあります。それらは異なるサーバーが所有していますが、単一のサーバー上に存在しています。

    この状況では、一部のサーバーは、これらの状態の集合を別々に保つために、[RFC7530]で提案されているものの義務付けられてはいない、クライアントによる非統一クライアントID文字列方式の使用に依存してきました。そのようなサーバーは、統一クライアントID文字列方式を使用するクライアントの処理に問題を抱えることになります。そのようなクライアントは、サーバーのフェイルオーバーとギブバックが発生するたびに、トランキング関係の変化を目にすることになるからです。

  • 既存のサーバーの中には、異なるIPアドレスを使用して確立された同じクライアントのclientid4がすでに存在するというだけの理由で、誤ってNFS4ERR_CLID_INUSEを返すものがあります。これは、統一クライアントID文字列方式を使用するマルチホームのクライアントにとって困難を引き起こします。

    この振る舞いは正しくありませんが、そのようなサーバーはいまだに存在しています。この仕様は、正しい振る舞いを明確にするとともに、この状況への対処についてクライアントにガイダンスを与えるべきです。

In order to support use of these sorts of servers, the client can use different client ID string approaches for different mounts, in order to assure that:

この種のサーバーの使用をサポートするために、クライアントはマウントごとに異なるクライアントID文字列方式を使用して、次のことを保証できます：

  • The uniform client ID string approach is used when accessing servers that may return NFS4ERR_MOVED and when the client wishes to enable transparent state migration.
  • The non-uniform client ID string approach is used when accessing servers whose implementations make them incompatible with the uniform client ID string approach.
  • NFS4ERR_MOVEDを返す可能性のあるサーバーにアクセスする場合で、かつクライアントが透過的な状態移行を有効にしたい場合には、統一クライアントID文字列方式を使用する。
  • 実装が統一クライアントID文字列方式と互換性のないサーバーにアクセスする場合には、非統一クライアントID文字列方式を使用する。

Since the client cannot easily determine which of the above are true, implementations are likely to rely on user-specified mount options to select the appropriate approach to use, in cases in which a client supports simultaneous use of multiple approaches. Choice of a default to use in such cases is up to the client implementation.

クライアントは上記のどれが当てはまるかを簡単には判断できないため、クライアントが複数の方式の同時使用をサポートする場合、実装は、使用する適切な方式を選択するためにユーザーが指定したマウントオプションに頼ることになるでしょう。そのような場合に使用するデフォルトの選択は、クライアントの実装に委ねられます。

In the case in which the same server has multiple mounts, and both approaches are specified for the same server, the client could have multiple clientid4s corresponding to the same server, one for each approach, and would then have to keep these separate.

同じサーバーに複数のマウントがあり、同じサーバーに対して両方の方式が指定されている場合、クライアントは同じサーバーに対応する複数のclientid4を方式ごとに1つずつ持つことがあり、その場合はそれらを別々に保たなければなりません。

5.8. Trunking Determination when Using Uniform Client ID Strings

5.8. 統一クライアントID文字列を使用する場合のトランキング判定

This section provides an example of how trunking determination could be done by a client following the uniform client ID string approach (whether this is used for all mounts or not). Clients need not follow this procedure, but implementers should make sure that the issues dealt with by this procedure are all properly addressed.

このセクションでは、統一クライアントID文字列方式に従うクライアントが（それをすべてのマウントに使用するかどうかにかかわらず）トランキング判定をどのように行えるかの例を示します。クライアントはこの手順に従う必要はありませんが、実装者は、この手順で扱う問題がすべて適切に対処されていることを確認すべきです。

It is best to clarify here the various possible purposes of trunking determination and the corresponding requirements as to server behavior. The following points should be noted:

ここで、トランキング判定の考えられるさまざまな目的と、それに対応するサーバーの振る舞いに関する要件を明確にしておくのが最善です。次の点に注意すべきです：

  • The primary purpose of the trunking determination algorithm is to make sure that, if the server treats client requests on two IP addresses as part of the same client, the client will not be surprised and encounter disconcerting server behavior, as mentioned in Section 5.6. Such behavior could occur if the client were unaware that all of its client requests for the two IP addresses were being handled as part of a single client talking to a single server.
  • A second purpose is to be able to use knowledge of trunking relationships for better performance, etc.
  • If a server were to give out distinct clientid4s in response to receiving the same nfs_client_id4 on different network addresses, and acted as if these were separate clients, the primary purpose of trunking determination would be met, as long as the server did not treat them as part of the same client. In this case, the server would be acting, with regard to that client, as if it were two distinct servers. This would interfere with the secondary purpose of trunking determination, but there is nothing the client can do about that.

  • Suppose a server were to give such a client two different clientid4s but act as if they were one. That is the only way that the server could behave in a way that would defeat the primary purpose of the trunking determination algorithm.

    Servers MUST NOT behave that way.

  • トランキング判定アルゴリズムの主な目的は、サーバーが2つのIPアドレス上のクライアントリクエストを同じクライアントの一部として扱う場合に、セクション5.6で述べたように、クライアントが驚いたり混乱させるようなサーバーの振る舞いに遭遇したりしないようにすることです。そのような振る舞いは、2つのIPアドレスに対するクライアントのリクエストがすべて、単一のサーバーと通信する単一のクライアントの一部として処理されていることにクライアントが気付いていない場合に起こる可能性があります。
  • 2つ目の目的は、性能の向上などのために、トランキング関係の知識を使用できるようにすることです。
  • サーバーが、異なるネットワークアドレスで同じnfs_client_id4を受け取ったことに応じて別個のclientid4を発行し、それらが別々のクライアントであるかのように振る舞った場合でも、サーバーがそれらを同じクライアントの一部として扱わない限り、トランキング判定の主な目的は達成されます。この場合、サーバーは、そのクライアントに関して、あたかも2つの別個のサーバーであるかのように振る舞うことになります。これはトランキング判定の2つ目の目的を妨げますが、クライアントにはそれについてできることは何もありません。

  • サーバーが、そのようなクライアントに2つの異なるclientid4を与えながら、それらが1つであるかのように振る舞ったとします。サーバーがトランキング判定アルゴリズムの主な目的を損なうような振る舞いをする方法は、これしかありません。

    サーバーはそのように振る舞ってはなりません（MUST NOT）。

For a client using the uniform approach, clientid4 values are treated as important information in determining server trunking patterns.

統一方式を使用するクライアントにとって、clientid4の値は、サーバーのトランキングパターンを判定する上で重要な情報として扱われます。

For two different IP addresses to return the same clientid4 value is a necessary, though not a sufficient condition for them to be considered as connected to the same server. As a result, when two different IP addresses return the same clientid4, the client needs to determine, using the procedure given below or otherwise, whether the IP addresses are connected to the same server. For such clients, all internal recording of clientid4 values needs to include, whether explicitly or implicitly, identification of the server from which the clientid4 was received so that one always has a (server, clientid4) pair. Two such pairs from different servers are always considered distinct even when the clientid4 values are the same, as they may occasionally be.

2つの異なるIPアドレスが同じclientid4の値を返すことは、それらが同じサーバーに接続されているとみなされるための必要条件ですが、十分条件ではありません。そのため、2つの異なるIPアドレスが同じclientid4を返した場合、クライアントは、以下に示す手順またはその他の方法を使用して、それらのIPアドレスが同じサーバーに接続されているかどうかを判断する必要があります。そのようなクライアントでは、clientid4の値の内部的な記録はすべて、明示的か暗黙的かにかかわらず、clientid4を受け取ったサーバーの識別を含む必要があり、常に（サーバー, clientid4）の組を持つようにします。異なるサーバーからの2つのそのような組は、clientid4の値が同じであっても（時にはそうなる場合があります）、常に別個のものとみなされます。

In order to make this approach work, the client must have certain information accessible for each nfs_client_id4 used by the uniform approach (only one in general). The client needs to maintain a list of all server IP addresses, together with the associated clientid4 values, SETCLIENTID principals, and authentication flavors. As a part of the associated data structures, there should be the ability to mark a server IP structure as having the same server as another and to mark an IP address as currently unresolved. One way to do this is to allow each such entry to point to another with the pointer value being one of:

この方式を機能させるためには、クライアントは、統一方式で使用される各nfs_client_id4（一般には1つだけ）について、特定の情報にアクセスできなければなりません。クライアントは、すべてのサーバーIPアドレスのリストを、関連するclientid4の値、SETCLIENTIDのプリンシパル、および認証フレーバーとともに維持する必要があります。関連するデータ構造の一部として、サーバーIPの構造が別のものと同じサーバーを持つことを示す印を付けたり、IPアドレスが現在未解決であることを示す印を付けたりする機能があるべきです。これを行う1つの方法は、そのような各エントリーが別のエントリーを指すことができるようにし、そのポインターの値を次のいずれかにすることです：

  • A pointer to another entry for an IP address associated with the same server, where that IP address is the first one referenced to access that server.
  • A pointer to the current entry if there is no earlier IP address associated with the same server, i.e., where the current IP address is the first one referenced to access that server. The text below refers to such an IP address as the lead IP address for a given server.
  • The value NULL if the address's server identity is currently unresolved.
  • 同じサーバーに関連付けられたIPアドレスの別のエントリーへのポインター。そのIPアドレスは、そのサーバーにアクセスするために最初に参照されたものです。
  • 同じサーバーに関連付けられたそれ以前のIPアドレスがない場合、つまり現在のIPアドレスがそのサーバーにアクセスするために最初に参照されたものである場合は、現在のエントリーへのポインター。以下のテキストでは、そのようなIPアドレスを、そのサーバーのリードIPアドレスと呼びます。
  • アドレスのサーバーアイデンティティーが現在未解決である場合は、値NULL。

In order to keep the above information current, in the interests of the most effective trunking determination, RENEWs should be periodically done on each server. However, even if this is not done, the primary purpose of the trunking determination algorithm, to prevent confusion due to trunking hidden from the client, will be achieved.

上記の情報を最新に保つために、最も効果的なトランキング判定のためには、各サーバーで定期的にRENEWを行うべきです。ただし、これが行われない場合でも、トランキング判定アルゴリズムの主な目的、つまりクライアントから隠されたトランキングによる混乱を防ぐという目的は達成されます。

Given this apparatus, when a SETCLIENTID is done and a clientid4 returned, the data structure can be searched for a matching clientid4 and if such is found, further processing can be done to determine whether the clientid4 match is accidental, or the result of trunking.

この仕組みがあれば、SETCLIENTIDが行われてclientid4が返されたときに、データ構造から一致するclientid4を検索でき、見つかった場合には、clientid4の一致が偶然なのか、トランキングの結果なのかを判断するためのさらなる処理を行えます。

In this algorithm, when SETCLIENTID is done initially, it will use the common nfs_client_id4 and specify the current target IP address as callback.cb_location within the callback parameters. We call the clientid4 and SETCLIENTID verifier returned by this operation XC and XV, respectively.

このアルゴリズムでは、最初にSETCLIENTIDを行うときに、共通のnfs_client_id4を使用し、コールバックパラメーター内のcallback.cb_locationとして現在のターゲットIPアドレスを指定します。この操作によって返されるclientid4とSETCLIENTIDのベリファイアーを、それぞれXCとXVと呼びます。

This choice of callback parameters is provisional and reflects the client's preferences in the event that the IP address is not trunked with other IP addresses. The algorithm is constructed so that only the appropriate callback parameters, reflecting observed trunking patterns, are actually confirmed.

このコールバックパラメーターの選択は暫定的なものであり、IPアドレスが他のIPアドレスとトランキングされていない場合のクライアントの希望を反映しています。このアルゴリズムは、観測されたトランキングパターンを反映した適切なコールバックパラメーターだけが実際に確認されるように構成されています。

Note that when the client has done previous SETCLIENTIDs to any IP addresses, with more than one principal or authentication flavor, one has the possibility of receiving NFS4ERR_CLID_INUSE, since it is not yet known which of the connections with existing IP addresses might be trunked with the current one. In the event that the SETCLIENTID fails with NFS4ERR_CLID_INUSE, one must try all other combinations of principals and authentication flavors currently in use, and eventually one will be correct and not return NFS4ERR_CLID_INUSE.

クライアントが以前に任意のIPアドレスに対して複数のプリンシパルまたは認証フレーバーでSETCLIENTIDを行っている場合、NFS4ERR_CLID_INUSEを受け取る可能性があることに注意してください。既存のIPアドレスとのコネクションのうち、どれが現在のものとトランキングされているかがまだわからないからです。SETCLIENTIDがNFS4ERR_CLID_INUSEで失敗した場合は、現在使用中のプリンシパルと認証フレーバーの他のすべての組み合わせを試さなければなりません。最終的にはどれかが正しく、NFS4ERR_CLID_INUSEを返さないはずです。

Note that at this point, no SETCLIENTID_CONFIRM has yet been done. This is because the SETCLIENTID just done has either established a new clientid4 on a previously unknown server or changed the callback parameters on a clientid4 associated with some already known server. Given it is undesirable to confirm something that should not happen, what is to be done next depends on information about existing clientid4s.

この時点では、まだSETCLIENTID_CONFIRMが行われていないことに注意してください。これは、直前に行われたSETCLIENTIDが、以前は未知だったサーバー上に新しいclientid4を確立したか、すでに既知のサーバーに関連付けられたclientid4のコールバックパラメーターを変更したかのどちらかだからです。起こるべきでないことを確認するのは望ましくないため、次に何を行うかは既存のclientid4に関する情報によって決まります。

  • If no matching clientid4 is found, the IP address X and clientid4 XC are added to the list and considered as having no existing known IP addresses trunked with it. The IP address is marked as a lead IP address for a new server. A SETCLIENTID_CONFIRM is done using XC and XV.
  • If a matching clientid4 is found that is marked unresolved, processing on the new IP address is suspended. In order to simplify processing, there can only be one unresolved IP address for any given clientid4.
  • If one or more matching clientid4s are found, none of which are marked unresolved, the new IP address X is entered and marked unresolved. A SETCLIENTID_CONFIRM is done to X using XC and XV.
  • 一致するclientid4が見つからない場合、IPアドレスXとclientid4のXCはリストに追加され、それとトランキングされている既知のIPアドレスは存在しないとみなされます。そのIPアドレスには、新しいサーバーのリードIPアドレスであることを示す印が付けられます。XCとXVを使用してSETCLIENTID_CONFIRMが行われます。
  • 未解決の印が付けられた一致するclientid4が見つかった場合、新しいIPアドレスに対する処理は一時停止されます。処理を単純にするために、任意のclientid4について、未解決のIPアドレスは1つしか存在できません。
  • 一致するclientid4が1つ以上見つかり、そのいずれにも未解決の印が付けられていない場合、新しいIPアドレスXが登録され、未解決の印が付けられます。XCとXVを使用して、XにSETCLIENTID_CONFIRMが行われます。

When, as a result of encountering the last of the three cases shown above, an unresolved IP address exists, further processing is required. After applying the steps below to each of the lead IP addresses with a matching clientid4, the address will have been resolved: It may have been determined to be part of an already known server as a new IP address to be added to an existing set of IP addresses for that server. Otherwise, it will be recognized as a new server. At the point at which this determination is made, the unresolved indication is cleared and any suspended SETCLIENTID processing is restarted.

上に示した3つのケースのうち最後のケースに遭遇した結果として未解決のIPアドレスが存在する場合は、さらなる処理が必要です。一致するclientid4を持つ各リードIPアドレスに以下の手順を適用した後、そのアドレスは解決されています。つまり、既知のサーバーの一部であり、そのサーバーの既存のIPアドレスの集合に追加される新しいIPアドレスであると判断されているかもしれません。そうでなければ、新しいサーバーとして認識されます。この判断が行われた時点で、未解決の表示は解除され、一時停止されていたSETCLIENTIDの処理は再開されます。

For each lead IP address IPn with a clientid4 matching XC, the following steps are done. Because the Remote Procedure Call (RPC) to do a SETCLIENTID could take considerable time, it is desirable for the client to perform these operations in parallel. Note that because the clientid4 is a 64-bit value, the number of such IP addresses that would need to be tested is expected to be quite small, even when the client is interacting with many NFSv4.0 servers. Thus, while parallel processing is desirable, it is not necessary.

XCと一致するclientid4を持つ各リードIPアドレスIPnについて、次の手順が行われます。SETCLIENTIDを行うためのリモートプロシージャーコール（RPC）にはかなりの時間がかかる可能性があるため、クライアントはこれらの操作を並行して実行するのが望ましいです。clientid4は64ビットの値であるため、クライアントが多数のNFSv4.0サーバーとやり取りしている場合でも、テストする必要があるそのようなIPアドレスの数はかなり少ないと予想されることに注意してください。したがって、並行処理は望ましいものの、必須ではありません。

  • If the principal for IPn does not match that for X, the IP address is skipped, since it is impossible for IPn and X to be trunked in these circumstances. If the principal does match but the authentication flavor does not, the authentication flavor already used should be used for address X as well. This will avoid any possibility that NFS4ERR_CLID_INUSE will be returned for the SETCLIENTID and SETCLIENTID_CONFIRM to be done below, as long as the server(s) at IP addresses IPn and X is correctly implemented.

  • A SETCLIENTID is done to update the callback parameters to reflect the possibility that X will be marked as associated with the server whose lead IP address is IPn. The specific callback parameters chosen, in terms of cb_client4 and callback_ident, are up to the client and should reflect its preferences as to callback handling for the common clientid4, in the event that X and IPn are trunked together. When a SETCLIENTID is done on IP address IPn, a setclientid_confirm value (in the form of a verifier4) is returned, which will be referred to as SCn.

    Note that the NFSv4.0 specification requires the server to make sure that such verifiers are very unlikely to be regenerated. Given that it is already highly unlikely that the clientid4 XC is duplicated by distinct servers, the probability that SCn is duplicated as well has to be considered vanishingly small. Note also that the callback update procedure can be repeated multiple times to reduce the probability of further spurious matches.

  • The setclientid_confirm value SCn is saved for later use in confirming the SETCLIENTID done to IPn.
  • IPnのプリンシパルがXのプリンシパルと一致しない場合、そのIPアドレスはスキップされます。このような状況では、IPnとXがトランキングされていることはありえないからです。プリンシパルは一致するが認証フレーバーが一致しない場合は、すでに使用されている認証フレーバーをアドレスXにも使用すべきです。これにより、IPアドレスIPnとXのサーバーが正しく実装されている限り、以下で行うSETCLIENTIDとSETCLIENTID_CONFIRMに対してNFS4ERR_CLID_INUSEが返される可能性はなくなります。

  • リードIPアドレスがIPnであるサーバーにXが関連付けられているという印が付けられる可能性を反映するように、コールバックパラメーターを更新するためのSETCLIENTIDが行われます。cb_client4とcallback_identに関して具体的にどのコールバックパラメーターを選ぶかはクライアントに委ねられており、XとIPnがトランキングされている場合の、共通のclientid4に対するコールバック処理についてのクライアントの希望を反映すべきです。IPアドレスIPnに対してSETCLIENTIDが行われると、（verifier4の形式の）setclientid_confirmの値が返されます。これをSCnと呼びます。

    NFSv4.0の仕様は、そのようなベリファイアーが再生成される可能性が非常に低くなるようにすることをサーバーに要求していることに注意してください。clientid4のXCが異なるサーバーによって重複する可能性がすでに非常に低いことを考えると、SCnも重複する確率は無視できるほど小さいとみなすべきです。また、さらなる偽の一致の確率を減らすために、コールバックの更新手順を複数回繰り返すことができることにも注意してください。

  • setclientid_confirmの値SCnは、IPnに対して行われたSETCLIENTIDの確認に後で使用するために保存されます。

Once the SCn values are gathered up by the procedure above, they are each tested by being used as the verifier for a SETCLIENTID_CONFIRM operation directed to the original IP address X, whose trunking relationships are to be determined. These RPC operations may be done in parallel.

上記の手順によってSCnの値が集められたら、それぞれを、トランキング関係を判定する対象である元のIPアドレスXに向けたSETCLIENTID_CONFIRM操作のベリファイアーとして使用することによってテストします。これらのRPC操作は並行して行ってもかまいません。

There are a number of things that should be noted at this point.

この時点で注意すべき点がいくつかあります。

  • The SETCLIENTID operations done on the various IPn addresses in the procedure above will never be confirmed by SETCLIENTID_CONFIRM operations directed to the various IPn addresses. If these callback updates are to be confirmed, they will be confirmed by SETCLIENTID_CONFIRM operations directed at the original IP address X, which can only happen if SCn was generated by an IPn that was trunked with X, allowing the SETCLIENTID to be successfully confirmed and allowing us to infer the existence of that trunking relationship.
  • The number of successful SETCLIENTID_CONFIRM operations done should never be more than one. If both SCn and SCm are accepted by X, then it indicates that both IPn and IPm are trunked with X, but that is only possible if IPn and IPm are trunked together. Since these two addresses were earlier recognized as not trunked together, this should be impossible, if the servers in question are implemented correctly.
  • 上記の手順でさまざまなIPnアドレスに対して行われたSETCLIENTID操作が、さまざまなIPnアドレスに向けたSETCLIENTID_CONFIRM操作によって確認されることは決してありません。これらのコールバックの更新が確認されるとすれば、元のIPアドレスXに向けたSETCLIENTID_CONFIRM操作によって確認されます。これが起こりうるのは、SCnがXとトランキングされているIPnによって生成された場合だけです。その場合、SETCLIENTIDが正常に確認され、そのトランキング関係の存在を推測できます。
  • 成功するSETCLIENTID_CONFIRM操作の数は、決して1を超えないはずです。SCnとSCmの両方がXによって受け入れられた場合、それはIPnとIPmの両方がXとトランキングされていることを示しますが、それはIPnとIPmが互いにトランキングされている場合にのみ可能です。これら2つのアドレスは、以前に互いにトランキングされていないと認識されているため、該当するサーバーが正しく実装されていれば、これは起こりえないはずです。

Further processing depends on the success or failure of the various SETCLIENTD_CONFIRM operations done in the step above.

さらなる処理は、上記の手順で行われたさまざまなSETCLIENTD_CONFIRM操作の成否によって決まります。

  • If the setclientid_confirm value generated by a particular IPn is accepted on X, then X and IPn are recognized as connected to the same server, and the entry for X is marked as associated with IPn.
  • If none of the confirm operations are accepted, then X is recognized as a distinct server. Its callback parameters will remain as the ones established by the original SETCLIENTID.
  • 特定のIPnによって生成されたsetclientid_confirmの値がXで受け入れられた場合、XとIPnは同じサーバーに接続されていると認識され、Xのエントリーには、IPnに関連付けられているという印が付けられます。
  • 確認操作がどれも受け入れられなかった場合、Xは別個のサーバーとして認識されます。そのコールバックパラメーターは、元のSETCLIENTIDによって確立されたもののままです。

In either of the cases, the entry is considered resolved and processing can be restarted for IP addresses whose clientid4 matched XC but whose resolution had been deferred.

どちらの場合も、エントリーは解決されたとみなされ、clientid4がXCと一致したものの解決が延期されていたIPアドレスについて、処理を再開できます。

The procedure described above must be performed so as to exclude the possibility that multiple SETCLIENTIDs done to different server IP addresses and returning the same clientid4 might "race" in such a fashion that there is no explicit determination of whether they correspond to the same server. The following possibilities for serialization are all valid, and implementers may choose among them based on a tradeoff between performance and complexity. They are listed in order of increasing parallelism:

上記の手順は、異なるサーバーIPアドレスに対して行われ、同じclientid4を返す複数のSETCLIENTIDが、それらが同じサーバーに対応するかどうかが明示的に判定されないような形で「競合」する可能性を排除するように実行されなければなりません。次に挙げるシリアル化の方法はどれも有効であり、実装者は性能と複雑さのトレードオフに基づいてその中から選択できます。これらは並列性の低い順に並べています：

  • An NFSv4.0 client might serialize all instances of SETCLIENTID/SETCLIENTID_CONFIRM processing, either directly or by serializing mount operations involving use of NFSv4.0. While doing so will prevent the races mentioned above, this degree of serialization can cause performance issues when there is a high volume of mount operations.
  • One might instead serialize the period of processing that begins when the clientid4 received from the server is processed and ends when all trunking determination for that server is completed. This prevents the races mentioned above, without adding to delay except when trunking determination is common.
  • One might avoid much of the serialization implied above, by allowing trunking determination for distinct clientid4 values to happen in parallel, with serialization of trunking determination happening independently for each distinct clientid4 value.
  • NFSv4.0クライアントは、直接、またはNFSv4.0の使用を伴うマウント操作をシリアル化することによって、SETCLIENTID/SETCLIENTID_CONFIRMの処理のすべてのインスタンスをシリアル化できます。そうすることで前述の競合は防げますが、この程度のシリアル化は、マウント操作が大量にある場合に性能の問題を引き起こす可能性があります。
  • 代わりに、サーバーから受け取ったclientid4が処理されるときに始まり、そのサーバーのトランキング判定がすべて完了したときに終わる処理の期間をシリアル化することもできます。これにより、トランキング判定が頻繁に行われる場合を除いて遅延を増やすことなく、前述の競合を防げます。
  • 異なるclientid4の値に対するトランキング判定を並行して行えるようにし、トランキング判定のシリアル化を異なるclientid4の値ごとに独立して行うことで、上で述べたシリアル化の多くを避けることもできます。

The procedure above has made no explicit mention of the possibility that server reboot can occur at any time. To address this possibility, the client should make sure the following steps are taken:

上記の手順では、サーバーの再起動がいつでも起こりうる可能性について明示的には触れていません。この可能性に対処するために、クライアントは次の手順が確実に行われるようにすべきです：

  • When a SETCLIENTID_CONFIRM is rejected by a given IPn, the client should be aware of the possibility that the rejection is due to XC (rather than XV) being invalid. This situation can be addressed by doing a RENEW specifying XC directed to the IP address X. If that operation succeeds, then the rejection is to be acted on normally since either XV is invalid on IPn or XC has become invalid on IPn while it is valid on X, showing that IPn and X are not trunked. If, on the other hand, XC is not valid on X, then the trunking detection process should be restarted once a new client ID is established on X.
  • In the event of a reboot detected on any server-lead IP, the set of IP addresses associated with the server should not change, and state should be re-established for the lease as a whole, using all available connected server IP addresses. It is prudent to verify connectivity by doing a RENEW using the new clientid4 on each such server address before using it, however.
  • SETCLIENTID_CONFIRMが特定のIPnによって拒否された場合、クライアントは、その拒否が（XVではなく）XCが無効であることによる可能性があることを認識しておくべきです。この状況には、IPアドレスXに向けてXCを指定したRENEWを行うことで対処できます。その操作が成功した場合、XVがIPn上で無効であるか、XCがX上では有効なのにIPn上では無効になったかのどちらかであり、IPnとXがトランキングされていないことを示しているため、拒否は通常どおりに扱われます。一方、XCがX上で有効でない場合は、X上で新しいクライアントIDが確立された後に、トランキング検出の処理を再開すべきです。
  • いずれかのサーバーのリードIPで再起動が検出された場合、そのサーバーに関連付けられたIPアドレスの集合は変更すべきではなく、利用可能なすべての接続済みのサーバーIPアドレスを使用して、リース全体の状態を再確立すべきです。ただし、そのような各サーバーアドレスを使用する前に、新しいclientid4を使用したRENEWを行って接続性を確認するのが賢明です。

Another situation not discussed explicitly above is the possibility that a SETCLIENTID done to one of the IPn addresses might take so long that it is necessary to time out the operation, to prevent unacceptably delaying the MOUNT operation. One simple possibility is to simply fail the MOUNT at this point. Because the average number of IP addresses that might have to be tested is quite small, this will not greatly increase the probability of MOUNT failure. Other possible approaches are:

上記で明示的に説明していないもう1つの状況は、IPnアドレスの1つに対して行われたSETCLIENTIDに非常に長い時間がかかり、MOUNT操作が許容できないほど遅延することを防ぐために、操作をタイムアウトさせる必要がある可能性です。単純な方法の1つは、この時点で単にMOUNTを失敗させることです。テストする必要がある可能性のあるIPアドレスの平均的な数はかなり少ないため、これによってMOUNTの失敗の確率が大きく増えることはありません。考えられる他の方式は次のとおりです：

  • If the IPn has sufficient state in existence, the existing stateids and sequence values might be validated by being used on IP address X. In the event of success, X and IPn should be considered trunked together.

    What constitutes "sufficient" state in this context is an implementation decision that is affected by the implementer's willingness to fail the MOUNT in an uncertain case and the strength of the state verification procedure implemented.

  • If IPn has no locking state in existence, X could be recorded as a lead IP address on a provisional basis, subject to trunking being tested again, once IPn starts becoming responsive. To avoid confusion between IPn and X, and the need to merge distinct state corpora for X and IPn at a later point, this retest of trunking should occur after RENEWs on IPn are responded to and before establishing any new state for either IPn as a separate server or for IPn considered as a server address trunked with X.

  • The client locking-related code could be made more tolerant of what would otherwise be considered anomalous results due to an unrecognized trunking relationship. The client could use the appearance of behavior explainable by a previously unknown trunking relationship as the cue to consider the addresses as trunked.

    This choice has a lot of complexity associated with it, and it is likely that few implementations will use it. When the set of locking state on IPn is small (e.g., a single stateid) but not empty, most client implementations are likely to either fail the MOUNT or implement a more stringent verification procedure using the existing stateid on IPn as a basis to generate further state as raw material for the trunking verification process.

  • IPnに十分な状態が存在する場合、既存のstateidとシーケンス値をIPアドレスX上で使用することによって検証できるかもしれません。成功した場合、XとIPnは互いにトランキングされているとみなすべきです。

    この文脈で何が「十分な」状態であるかは実装上の判断であり、不確かな場合にMOUNTを失敗させることを実装者がどれだけ許容するかと、実装された状態の検証手順の強さに左右されます。

  • IPnにロック状態が存在しない場合、Xを暫定的にリードIPアドレスとして記録し、IPnが応答し始めた時点でトランキングを再度テストすることもできます。IPnとXの間の混乱や、後の時点でXとIPnの別個の状態の集まりをマージする必要性を避けるために、このトランキングの再テストは、IPnでのRENEWに応答があった後、かつ、IPnを別個のサーバーとして、またはIPnをXとトランキングされたサーバーアドレスとして、新しい状態を確立する前に行うべきです。

  • クライアントのロック関連のコードを、認識されていないトランキング関係のために本来なら異常とみなされる結果に対して、より寛容にすることもできます。クライアントは、以前は未知だったトランキング関係によって説明できる振る舞いが現れたことを、それらのアドレスがトランキングされているとみなす手がかりとして使用できます。

    この選択肢には多くの複雑さが伴うため、それを使用する実装は少ないでしょう。IPn上のロック状態の集合が小さい（たとえば、単一のstateid）が空ではない場合、ほとんどのクライアントの実装は、MOUNTを失敗させるか、IPn上の既存のstateidを基にしてトランキング検証処理の素材となるさらなる状態を生成する、より厳格な検証手順を実装するかのどちらかになるでしょう。

5.9. Client ID String Construction Details

5.9. クライアントID文字列の構築の詳細

This section gives more detailed guidance on client ID string construction. The guidance in this section will cover cases in which either the uniform or the non-uniform approach to the client ID string is used.

このセクションでは、クライアントID文字列の構築について、より詳細なガイダンスを示します。このセクションのガイダンスは、クライアントID文字列に統一方式と非統一方式のどちらを使用する場合も対象とします。

Note that among the items suggested for inclusion, there are many that may conceivably change. In order for the client ID string to remain valid in such circumstances, the client SHOULD either:

含めることが提案されている項目の中には、変化する可能性が考えられるものが多くあることに注意してください。そのような状況でもクライアントID文字列が有効であり続けるためには、クライアントは次のどちらかを行うべきです（SHOULD）：

  • Use a saved copy of such value rather than the changeable value itself, or
  • Save the constructed client ID string rather than constructing it anew at SETCLIENTID time, based on unchangeable parameters and saved copies of changeable data items.
  • 変更可能な値そのものではなく、そのような値の保存されたコピーを使用する。または、
  • SETCLIENTIDの時点で、変更できないパラメーターと変更可能なデータ項目の保存されたコピーに基づいて新たにクライアントID文字列を構築するのではなく、構築済みのクライアントID文字列を保存しておく。

A file is not always a valid choice to store such information, given the existence of diskless clients. In such situations, whatever facilities exist for a client to store configuration information such as boot arguments should be used.

ディスクレスのクライアントが存在することを考えると、そのような情報を格納するためにファイルを使用することが常に有効な選択肢であるとは限りません。そのような状況では、ブート引数などの設定情報を格納するためにクライアントが持っている何らかの機能を使用すべきです。

Given the considerations listed in Section 5.2.1, an id string would be one that includes as its basis:

セクション5.2.1に挙げた考慮事項を踏まえると、id文字列は、その基礎として次のものを含むものになるでしょう：

  • An identifier uniquely associated with the node on which the client is running.
  • For a user-level NFSv4.0 client, it should contain additional information to distinguish the client from a kernel-based client and from other user-level clients running on the same node, such as a universally unique identifier (UUID).
  • Where the non-uniform approach is to be used, the IP address of the server.

  • Additional information that tends to be unique, such as one or more of:

    • The timestamp of when the NFSv4 software was first installed on the client (though this is subject to the previously mentioned caution about using information that is stored in a file, because the file might only be accessible over NFSv4).
    • A true random number, generally established once and saved.
  • クライアントが実行されているノードに一意に関連付けられた識別子。
  • ユーザーレベルのNFSv4.0クライアントの場合は、カーネルベースのクライアントや、同じノード上で実行されている他のユーザーレベルのクライアントとそのクライアントを区別するための追加の情報（汎用一意識別子（UUID）など）を含むべきです。
  • 非統一方式を使用する場合は、サーバーのIPアドレス。

  • 一意になりやすい追加の情報。たとえば、次のうちの1つ以上：

    • NFSv4ソフトウェアがクライアントに最初にインストールされたときのタイムスタンプ（ただし、ファイルにはNFSv4経由でしかアクセスできない可能性があるため、これには、ファイルに格納された情報の使用に関する前述の注意が当てはまります）。
    • 真の乱数。一般には、一度だけ確立して保存しておきます。

With regard to the identifier associated with the node on which the client is running, the following possibilities are likely candidates.

クライアントが実行されているノードに関連付けられた識別子については、次のものが有力な候補です。

  • The client machine's serial number.
  • The client's IP address. Note that this SHOULD be treated as a changeable value.
  • A Media Access Control (MAC) address. Note that this also should be considered a changeable value because of the possibility of configuration changes.
  • クライアントマシンのシリアル番号。
  • クライアントのIPアドレス。これは変更可能な値として扱うべきです（SHOULD）。
  • メディアアクセス制御（MAC）アドレス。設定が変更される可能性があるため、これも変更可能な値とみなすべきです。

Privacy concerns may be an issue if some of the items above (e.g., machine serial number and MAC address) are used. When it is necessary to use such items to ensure uniqueness, application of a one-way hash function is desirable. When the non-uniform approach is used, that hash function should be applied to all of the components chosen as a unit rather than to particular individual elements.

上記の項目の一部（たとえば、マシンのシリアル番号やMACアドレス）を使用する場合、プライバシーの懸念が問題になることがあります。一意性を確保するためにそのような項目を使用する必要がある場合は、一方向ハッシュ関数を適用することが望ましいです。非統一方式を使用する場合、そのハッシュ関数は、特定の個々の要素に適用するのではなく、選択したすべての構成要素をひとまとめにしたものに適用すべきです。

6.1. Lock State and File System Transitions

6.1. ロック状態とファイルシステムの遷移

File systems may transition to a different server in several circumstances:

ファイルシステムは、いくつかの状況で別のサーバーに遷移することがあります：

  • Responsibility for handling a given file system is transferred to a new server via migration.
  • A client may choose to use an alternate server (e.g., in response to server unresponsiveness) in the context of file system replication.
  • 特定のファイルシステムを扱う責任が、移行によって新しいサーバーに移される場合。
  • ファイルシステムの複製の文脈で、クライアントが（たとえば、サーバーが応答しないことに対応して）代わりのサーバーを使用することを選択する場合。

In such cases, the appropriate handling of state shared between the client and server (i.e., locks, leases, stateids, and client IDs) is as described below. The handling differs between migration and replication.

このような場合、クライアントとサーバーの間で共有される状態（つまり、ロック、リース、stateid、クライアントID）の適切な処理は、以下で説明するとおりです。処理は移行と複製とで異なります。

If a server replica or a server immigrating a file system agrees to, or is expected to, accept opaque values from the client that originated from another server, then it is a wise implementation practice for the servers to encode the "opaque" values in network byte order (i.e., in a big-endian format). When doing so, servers acting as replicas or immigrating file systems will be able to parse values like stateids, directory cookies, filehandles, etc., even if their native byte order is different from that of other servers cooperating in the replication and migration of the file system.

サーバーのレプリカ、またはファイルシステムを移入するサーバーが、別のサーバーから発生した不透明な値をクライアントから受け入れることに同意している場合、または受け入れることが期待されている場合、サーバーが「不透明な」値をネットワークバイトオーダーで（つまり、ビッグエンディアン形式で）エンコードすることは賢明な実装の慣行です。そうすることで、レプリカとして動作するサーバーやファイルシステムを移入するサーバーは、自身のネイティブなバイトオーダーがファイルシステムの複製と移行に協力する他のサーバーのものと異なる場合でも、stateid、ディレクトリーのクッキー、ファイルハンドルなどの値を解析できるようになります。

6.1.1. Migration and State

6.1.1. 移行と状態

In the case of migration, the servers involved in the migration of a file system should transfer all server state associated with the migrating file system from source to the destination server. If state is transferred, this MUST be done in a way that is transparent to the client. This state transfer will ease the client's transition when a file system migration occurs. If the servers are successful in transferring all state, the client will continue to use stateids assigned by the original server. Therefore, the new server must recognize these stateids as valid and treat them as representing the same locks as they did on the source server.

移行の場合、ファイルシステムの移行に関わるサーバーは、移行されるファイルシステムに関連付けられたすべてのサーバーの状態を、移行元サーバーから移行先サーバーへ転送すべきです。状態が転送される場合、それはクライアントに対して透過的な方法で行われなければなりません（MUST）。この状態の転送により、ファイルシステムの移行が発生したときのクライアントの遷移が容易になります。サーバーがすべての状態の転送に成功した場合、クライアントは元のサーバーによって割り当てられたstateidを引き続き使用します。したがって、新しいサーバーは、これらのstateidを有効なものとして認識し、移行元サーバー上と同じロックを表すものとして扱わなければなりません。

In this context, the phrase "the same locks" means that:

この文脈において、「同じロック」という語句は次のことを意味します：

  • They are associated with the same file.
  • They represent the same types of locks, whether opens, delegations, advisory byte-range locks, or mandatory byte-range locks.
  • They have the same lock particulars, including such things as access modes, deny modes, and byte ranges.
  • They are associated with the same owner string(s).
  • 同じファイルに関連付けられている。
  • オープン、委任、助言的なバイト範囲ロック、強制的なバイト範囲ロックのいずれであれ、同じ種類のロックを表している。
  • アクセスモード、拒否モード、バイト範囲などを含めて、ロックの詳細が同じである。
  • 同じオーナー文字列に関連付けられている。

If transferring stateids from server to server would result in a conflict for an existing stateid for the destination server with the existing client, transparent state migration MUST NOT happen for that client. Servers participating in using transparent state migration should coordinate their stateid assignment policies to make this situation unlikely or impossible. The means by which this might be done, like all of the inter-server interactions for migration, are not specified by the NFS version 4.0 protocol (neither in [RFC7530] nor this update).

サーバーからサーバーへのstateidの転送によって、既存のクライアントについて移行先サーバーの既存のstateidとの競合が生じる場合、そのクライアントについて透過的な状態移行が行われてはなりません（MUST NOT）。透過的な状態移行の使用に参加するサーバーは、この状況が起こりにくい、または起こりえないように、stateidの割り当てポリシーを調整すべきです。これを行う手段は、移行に関するサーバー間のすべてのやり取りと同様に、NFSバージョン4.0プロトコルでは（[RFC7530]でもこの更新でも）規定されていません。

A client may determine the disposition of migrated state by using a stateid associated with the migrated state on the new server.

クライアントは、新しいサーバー上で移行された状態に関連付けられたstateidを使用することによって、移行された状態がどう扱われたかを判断できます。

  • If the stateid is not valid and an error NFS4ERR_BAD_STATEID is received, either transparent state migration has not occurred or the state was purged due to a mismatch in the verifier (i.e., the boot instance id).
  • If the stateid is valid, transparent state migration has occurred.
  • stateidが有効でなく、エラーNFS4ERR_BAD_STATEIDを受け取った場合、透過的な状態移行が行われなかったか、ベリファイアー（つまり、ブートインスタンスID）の不一致のために状態が削除されたかのどちらかです。
  • stateidが有効な場合、透過的な状態移行が行われています。

Since responsibility for an entire file system is transferred with a migration event, there is no possibility that conflicts will arise on the destination server as a result of the transfer of locks.

移行の事象ではファイルシステム全体に対する責任が移されるため、ロックの転送の結果として移行先サーバー上で競合が発生する可能性はありません。

The servers may choose not to transfer the state information upon migration. However, this choice is discouraged, except where specific issues such as stateid conflicts make it necessary. When a server implements migration and it does not transfer state information, it MUST provide a file-system-specific grace period, to allow clients to reclaim locks associated with files in the migrated file system. If it did not do so, clients would have to re-obtain locks, with no assurance that a conflicting lock was not granted after the file system was migrated and before the lock was re-obtained.

サーバーは、移行時に状態情報を転送しないことを選択できます。ただし、stateidの競合などの特定の問題によって必要となる場合を除いて、この選択は推奨されません。サーバーが移行を実装していて、状態情報を転送しない場合、クライアントが移行されたファイルシステム内のファイルに関連付けられたロックを再取得できるように、サーバーはファイルシステム固有の猶予期間を提供しなければなりません（MUST）。そうしなければ、クライアントはロックを取得し直さなければならず、ファイルシステムが移行された後、ロックを取得し直す前に、競合するロックが許可されていないという保証がなくなります。

In the case of migration without state transfer, when the client presents state information from the original server (e.g., in a RENEW operation or a READ operation of zero length), the client must be prepared to receive either NFS4ERR_STALE_CLIENTID or NFS4ERR_BAD_STATEID from the new server. The client should then recover its state information as it normally would in response to a server failure. The new server must take care to allow for the recovery of state information as it would in the event of server restart.

状態の転送を伴わない移行の場合、クライアントが元のサーバーからの状態情報を（たとえば、RENEW操作や長さ0のREAD操作で）提示すると、クライアントは新しいサーバーからNFS4ERR_STALE_CLIENTIDまたはNFS4ERR_BAD_STATEIDのいずれかを受け取ることに備えておかなければなりません。その後、クライアントは、サーバーの障害に対応する場合と同じように状態情報を回復すべきです。新しいサーバーは、サーバーの再起動の場合と同じように、状態情報の回復を許可するよう注意しなければなりません。

In those situations in which state has not been transferred, as shown by a return of NFS4ERR_BAD_STATEID, the client may attempt to reclaim locks in order to take advantage of cases in which the destination server has set up a file-system-specific grace period in support of the migration.

NFS4ERR_BAD_STATEIDが返されたことによって示されるように、状態が転送されていない状況では、移行先サーバーが移行をサポートするためにファイルシステム固有の猶予期間を設定している場合を活用するために、クライアントはロックの再取得を試みることができます。

6.1.1.1. Migration and Client IDs
6.1.1.1. 移行とクライアントID

The handling of clientid4 values is similar to that for stateids. However, there are some differences that derive from the fact that a clientid4 is an object that spans multiple file systems while a stateid is inherently limited to a single file system.

clientid4の値の扱いは、stateidの扱いと似ています。ただし、clientid4は複数のファイルシステムにまたがるオブジェクトであるのに対し、stateidは本質的に単一のファイルシステムに限定されるという事実に由来する違いがいくつかあります。

The clientid4 and nfs_client_id4 information (id string and boot instance id) will be transferred with the rest of the state information, and the destination server should use that information to determine appropriate clientid4 handling. Although the destination server may make state stored under an existing lease available under the clientid4 used on the source server, the client should not assume that this is always so. In particular,

clientid4とnfs_client_id4の情報（id文字列とブートインスタンスID）は、残りの状態情報とともに転送され、移行先サーバーはその情報を使用して適切なclientid4の扱いを決定すべきです。移行先サーバーは、既存のリースの下に格納されている状態を、移行元サーバーで使用されていたclientid4の下で利用可能にすることもありますが、クライアントは常にそうであると想定すべきではありません。特に、次のとおりです。

  • If there is an existing lease with an nfs_client_id4 that matches a migrated lease (same id string and verifier), the server SHOULD merge the two, making the union of the sets of stateids available under the clientid4 for the existing lease. As part of the lease merger, the expiration time of the lease will reflect renewal done within either of the ancestor leases (and so will reflect the latest of the renewals).
  • If there is an existing lease with an nfs_client_id4 that partially matches a migrated lease (same id string and a different (boot) verifier), the server MUST eliminate one of the two, possibly invalidating one of the ancestor clientid4s. Since boot instance ids are not ordered, the later lease renewal time will prevail.
  • If the destination server already has the transferred clientid4 in use for another purpose, it is free to substitute a different clientid4 and associate that with the transferred nfs_client_id4.
  • 移行されたリースと一致する（id文字列とverifierが同じ）nfs_client_id4を持つ既存のリースがある場合、サーバーはその2つをマージし、stateidの集合の和集合を既存のリースのclientid4の下で利用可能にするべきです（SHOULD）。リースのマージの一環として、リースの有効期限は、元となったどちらのリースで行われた更新も反映します（したがって、最も遅い更新を反映します）。
  • 移行されたリースと部分的に一致する（id文字列が同じで、（ブート）verifierが異なる）nfs_client_id4を持つ既存のリースがある場合、サーバーはその2つのうち一方を削除しなければなりません（MUST）。これにより、元となったclientid4の一方が無効になる可能性があります。ブートインスタンスIDには順序がないため、リースの更新時刻が遅い方が優先されます。
  • 移行先サーバーが、転送されたclientid4をすでに別の目的で使用している場合、移行先サーバーは自由に別のclientid4で置き換え、それを転送されたnfs_client_id4に関連付けることができます。

When leases are not merged, the transfer of state should result in creation of a confirmed client record with empty callback information but matching the {v, x, c} with v and x derived from the transferred client information and c chosen by the destination server. For a description of this notation, see Section 8.4.5

リースがマージされない場合、状態の転送の結果として、コールバック情報が空で、{v, x, c}が一致する確認済みのクライアントレコードが作成されるべきです。ここで、vとxは転送されたクライアント情報から導出され、cは移行先サーバーによって選ばれます。この表記の説明については、セクション8.4.5を参照してください

In such cases, the client SHOULD re-establish new callback information with the new server as soon as possible, according to sequences described in sections "Operation 35: SETCLIENTID -- Negotiate Client ID" and "Operation 36: SETCLIENTID_CONFIRM -- Confirm Client ID". This ensures that server operations are not delayed due to an inability to recall delegations and prevents the unwanted revocation of existing delegations. The client can determine the new clientid4 (the value c) from the response to SETCLIENTID.

そのような場合、クライアントは、「Operation 35: SETCLIENTID -- Negotiate Client ID」と「Operation 36: SETCLIENTID_CONFIRM -- Confirm Client ID」のセクションで説明されている手順に従って、できるだけ早く新しいサーバーとの間で新しいコールバック情報を再確立するべきです（SHOULD）。これにより、委任をリコールできないことによってサーバーの操作が遅延することがなくなり、既存の委任が望まない形で取り消されることが防がれます。クライアントは、SETCLIENTIDへのレスポンスから新しいclientid4（値c）を判断できます。

The client can use its own information about leases with the destination server to see if lease merger should have happened. When there is any ambiguity, the client MAY use the above procedure to set the proper callback information and find out, as part of the process, the correct value of its clientid4 with respect to the server in question.

クライアントは、移行先サーバーとのリースに関する自身の情報を使用して、リースのマージが行われたはずかどうかを確認できます。少しでも曖昧さがある場合、クライアントは、上記の手順を使用して適切なコールバック情報を設定し、その過程の一環として、該当するサーバーに関する自身のclientid4の正しい値を調べてもよいです（MAY）。

6.1.1.2. Migration and State Owner Information
6.1.1.2. 移行と状態オーナー情報

In addition to stateids, the locks they represent, and client identity information, servers also need to transfer information related to the current status of open-owners and lock-owners.

サーバーは、stateid、それが表すロック、クライアントのアイデンティティー情報に加えて、open-ownerとlock-ownerの現在の状態に関する情報も転送する必要があります。

This information includes:

この情報には次のものが含まれます：

  • The sequence number of the last operation associated with the particular owner.
  • Sufficient information regarding the results of the last operation to allow reissued operations to be correctly responded to.
  • 特定のオーナーに関連付けられた最後の操作のシーケンス番号。
  • 再発行された操作に正しく応答できるようにするための、最後の操作の結果に関する十分な情報。

When individual open-owners and lock-owners have only been used in connection with a particular file system, the server SHOULD transfer this information together with the lock state. The owner ceases to exist on the source server and is reconstituted on the destination server. This will happen in the case of clients that have been written to isolate each owner to a specific file system, but it may happen for other clients as well.

個々のopen-ownerとlock-ownerが特定のファイルシステムに関してのみ使用されてきた場合、サーバーはこの情報をロック状態とともに転送するべきです（SHOULD）。そのオーナーは移行元サーバー上では存在しなくなり、移行先サーバー上で再構成されます。これは、各オーナーを特定のファイルシステムに分離するように書かれたクライアントの場合に起こりますが、他のクライアントでも起こる可能性があります。

Note that when servers take this approach for all owners whose state is limited to the particular file system being migrated, doing so will not cause difficulties for clients not adhering to an approach in which owners are isolated to particular file systems. As long as the client recognizes the loss of transferred state, the protocol allows the owner in question to disappear, and the client may have to deal with an owner confirmation request that would not have occurred in the absence of the migration.

状態が移行される特定のファイルシステムに限定されているすべてのオーナーについてサーバーがこの方式を採用しても、オーナーを特定のファイルシステムに分離する方式に従っていないクライアントにとって困難が生じることはないことに注意してください。クライアントが転送された状態の喪失を認識している限り、プロトコルは該当するオーナーが消えることを許容しており、クライアントは、移行がなければ発生しなかったはずのオーナーの確認リクエストに対処しなければならない場合があります。

When migration occurs and the source server discovers an owner whose state includes the migrated file system but other file systems as well, it cannot transfer the associated owner state. Instead, the existing owner state stays in place, but propagation of owner state is done as specified below:

移行が発生し、移行元サーバーが、移行されたファイルシステムだけでなく他のファイルシステムも含む状態を持つオーナーを発見した場合、移行元サーバーは関連するオーナーの状態を転送できません。代わりに、既存のオーナーの状態はそのまま残りますが、オーナーの状態の伝播は次のように行われます：

  • When the current seqid for an owner represents an operation associated with the file system being migrated, owner status SHOULD be propagated to the destination file system.
  • When the current seqid for an owner does not represent an operation associated with the file system being migrated, owner status MAY be propagated to the destination file system.
  • When the owner in question has never been used for an operation involving the migrated file system, the owner information SHOULD NOT be propagated to the destination file system.
  • オーナーの現在のseqidが、移行されるファイルシステムに関連付けられた操作を表している場合、オーナーの状態は移行先のファイルシステムに伝播されるべきです（SHOULD）。
  • オーナーの現在のseqidが、移行されるファイルシステムに関連付けられた操作を表していない場合、オーナーの状態は移行先のファイルシステムに伝播されてもよいです（MAY）。
  • 該当するオーナーが、移行されたファイルシステムに関わる操作に一度も使用されていない場合、オーナー情報は移行先のファイルシステムに伝播されるべきではありません（SHOULD NOT）。

Note that a server may obey all of the conditions above without the overhead of keeping track of a set of file systems that any particular owner has been associated with. Consider a situation in which the source server has decided to keep lock-related state associated with a file system fixed, preparatory to propagating it to the destination file system. If a client is free to create new locks associated with existing owners on other file systems, the owner information may be propagated to the destination file system, even though, at the time the file system migration is recognized by the client to have occurred, the last operation associated with the owner may not be associated with the migrating file system.

サーバーは、特定のオーナーが関連付けられてきたファイルシステムの集合を追跡するオーバーヘッドなしに、上記の条件をすべて守ることができることに注意してください。移行元サーバーが、移行先のファイルシステムへの伝播の準備として、あるファイルシステムに関連付けられたロック関連の状態を固定することにした状況を考えてみましょう。クライアントが他のファイルシステム上で既存のオーナーに関連付けられた新しいロックを自由に作成できる場合、ファイルシステムの移行が発生したとクライアントが認識した時点で、そのオーナーに関連付けられた最後の操作が移行されるファイルシステムに関連付けられていなくても、オーナー情報が移行先のファイルシステムに伝播されることがあります。

When a source server propagates owner-related state associated with owners that span multiple file systems, it will propagate the owner sequence value to the destination server, while retaining it on the source server, as long as there exists state associated with the owner. When owner information is propagated in this way, source and destination servers start with the same owner sequence value that is then updated independently, as the client makes owner-related requests to the servers. Note that each server will have some period in which the associated sequence value for an owner is identical to the one transferred as part of migration. At those times, when a server receives a request with a matching owner sequence value, it MUST NOT respond with the associated stored response if the associated file system is not, when the reissued request is received, part of the set of file systems handled by that server.

移行元サーバーが、複数のファイルシステムにまたがるオーナーに関連付けられたオーナー関連の状態を伝播する場合、そのオーナーに関連付けられた状態が存在する限り、移行元サーバーはオーナーのシーケンス値を移行元サーバー上に保持したまま、移行先サーバーに伝播します。オーナー情報がこのように伝播される場合、移行元サーバーと移行先サーバーは同じオーナーのシーケンス値から始まり、その後、クライアントがサーバーにオーナー関連のリクエストを行うにつれて、それぞれ独立して更新されます。各サーバーには、オーナーの関連するシーケンス値が、移行の一部として転送されたものと同一である期間があることに注意してください。そのような時に、サーバーが一致するオーナーのシーケンス値を持つリクエストを受け取った場合、再発行されたリクエストを受け取った時点で関連するファイルシステムがそのサーバーが扱うファイルシステムの集合に含まれていなければ、サーバーは関連する格納済みのレスポンスで応答してはなりません（MUST NOT）。

One sort of case may require more complex handling. When multiple file systems are migrated, in sequence, to a specific destination server, an owner may be migrated to a destination server, on which it was already present, leading to the issue of how the resident owner information and that being newly migrated are to be reconciled.

ある種のケースでは、より複雑な処理が必要になる場合があります。複数のファイルシステムが順番に特定の移行先サーバーへ移行される場合、オーナーが、すでにそのオーナーが存在している移行先サーバーへ移行されることがあり、既存のオーナー情報と新たに移行されるオーナー情報をどのように調整するかという問題が生じます。

If file system migration encounters a situation where owner information needs to be merged, it MAY decline to transfer such state, even if it chooses to handle other cases in which locks for a given owner are spread among multiple file systems.

ファイルシステムの移行において、オーナー情報をマージする必要がある状況に遭遇した場合、特定のオーナーのロックが複数のファイルシステムに分散している他のケースを扱うことを選択していても、そのような状態の転送を断ってもよいです（MAY）。

As a way of understanding the situations that need to be addressed when owner information needs to be merged, consider the following scenario:

オーナー情報をマージする必要がある場合に対処しなければならない状況を理解する方法として、次のシナリオを考えてみましょう：

  • There is client C and two servers, X and Y. There are two clientid4s designating C, which are referred to as CX and CY.
  • Initially, server X supports file systems F1, F2, F3, and F4. These will be migrated, one at a time, to server Y.
  • While these migrations are proceeding, the client makes locking requests for file systems F1 through F4 on behalf of owner O (either a lock-owner or an open-owner), with each request going to X or Y depending on where the relevant file system is being supported at the time the request is made.
  • Once the first migration event occurs, client C will maintain two instances for owner O, one for each server.
  • It is always possible that C may make a request of server X relating to owner O, and before receiving a response, it finds the target file system has moved to Y and needs to reissue the request to server Y.
  • At the same time, C may make a request of server Y relating to owner O, and this too may encounter a lost-response situation.
  • クライアントCと、2つのサーバーXとYがあります。Cを指定する2つのclientid4があり、それらをCXとCYと呼びます。
  • 最初は、サーバーXがファイルシステムF1、F2、F3、F4をサポートしています。これらは1つずつサーバーYへ移行されます。
  • これらの移行が進行している間、クライアントはオーナーO（lock-ownerまたはopen-owner）に代わってファイルシステムF1からF4に対するロックリクエストを行います。各リクエストは、リクエストが行われた時点で該当するファイルシステムがどちらでサポートされているかに応じて、XまたはYに送られます。
  • 最初の移行の事象が発生すると、クライアントCはオーナーOについて、サーバーごとに1つずつ、2つのインスタンスを維持します。
  • CがオーナーOに関するリクエストをサーバーXに対して行い、レスポンスを受け取る前に、ターゲットのファイルシステムがYに移動したことがわかり、リクエストをサーバーYに再発行する必要が生じる可能性は常にあります。
  • 同時に、CはオーナーOに関するリクエストをサーバーYに対して行う場合があり、これもレスポンスが失われる状況に遭遇する可能性があります。

As a result of such merger situations, the server will need to provide support for dealing with retransmission of owner-sequenced requests that diverge from the typical model in which there is support for retransmission of replies only for a request whose sequence value exactly matches the last one sent. In some situations, there may be two requests, each of which had the last sequence when it was issued. As a result of migration and owner merger, one of those will no longer be the last by sequence.

このようなマージの状況の結果として、サーバーは、オーナーによってシーケンス番号が付けられたリクエストの再送に対処するためのサポートを提供する必要があります。これは、シーケンス値が最後に送信されたものと正確に一致するリクエストに対してのみ応答の再送をサポートするという典型的なモデルとは異なります。状況によっては、2つのリクエストがあり、どちらも発行された時点では最後のシーケンスを持っていたということがありえます。移行とオーナーのマージの結果、そのうちの一方はもはやシーケンスの上で最後のものではなくなります。

When servers do support such merger of owner information on the destination server, the following rules are to be adhered to:

サーバーが移行先サーバー上でのそのようなオーナー情報のマージをサポートする場合は、次の規則に従うものとします：

  • When an owner sequence value is propagated to a destination server where it already exists, the resulting sequence value is to be the greater of the one present on the destination server and the one being propagated as part of migration.
  • In the event that an owner sequence value on a server represents a request applying to a file system currently present on the server, it is not to be rendered invalid simply because that sequence value is changed as a result of owner information propagation as part of file system migration. Instead, it is retained until it can be deduced that the client in question has received the reply.
  • オーナーのシーケンス値が、そのオーナーがすでに存在する移行先サーバーに伝播される場合、結果のシーケンス値は、移行先サーバー上に存在するものと、移行の一部として伝播されるもののうち、大きい方とします。
  • サーバー上のオーナーのシーケンス値が、そのサーバー上に現在存在するファイルシステムに適用されるリクエストを表している場合、ファイルシステムの移行の一部としてのオーナー情報の伝播の結果としてそのシーケンス値が変更されたというだけの理由で、それを無効にしてはいけません。代わりに、該当するクライアントが応答を受け取ったと推測できるまで、それを保持します。

As a result of the operation of these rules, there are three ways in which there can be more reply data than what is typically present, i.e., data for a single request per owner whose sequence is the last one received, where the next sequence to be used is one beyond that.

これらの規則を運用した結果、通常存在するもの、つまり、シーケンスが最後に受け取ったものであり、次に使用されるシーケンスがその1つ先であるような、オーナーごとに単一のリクエストのデータよりも多くの応答データが存在しうる場合が3つあります。

  • When the owner sequence value for a migrating file system is greater than the corresponding value on the destination server, the last request for the owner in effect at the destination server needs to be retained, even though it is no longer one less than the next sequence to be received.
  • When the owner sequence value for a migrating file system is less than the corresponding value on the destination server, the sequence number for last request for the owner in effect on the migrating file system needs to be retained, even though it is no longer than one less the next sequence to be received.
  • When the owner sequence value for a migrating file system is equal to the corresponding value on the destination server, one has two different "last" requests that both must be retained. The next sequence value to be used is one beyond the sequence value shared by these two requests.
  • 移行されるファイルシステムのオーナーのシーケンス値が、移行先サーバー上の対応する値よりも大きい場合、移行先サーバーで有効なそのオーナーの最後のリクエストは、もはや次に受け取るシーケンスより1つ小さいものではなくなっていても、保持される必要があります。
  • 移行されるファイルシステムのオーナーのシーケンス値が、移行先サーバー上の対応する値よりも小さい場合、移行されるファイルシステム上で有効なそのオーナーの最後のリクエストのシーケンス番号は、もはや次に受け取るシーケンスより1つ小さいものではなくなっていても、保持される必要があります。
  • 移行されるファイルシステムのオーナーのシーケンス値が、移行先サーバー上の対応する値と等しい場合、2つの異なる「最後の」リクエストが存在し、その両方を保持しなければなりません。次に使用されるシーケンス値は、これら2つのリクエストが共有するシーケンス値の1つ先です。

Here are some guidelines as to when servers can drop such additional reply data, which is created as part of owner information migration.

オーナー情報の移行の一部として作成された、そのような追加の応答データを、サーバーがいつ破棄できるかについてのガイドラインを次に示します。

  • The server SHOULD NOT drop this information simply because it receives a new sequence value for the owner in question, since that request may have been issued before the client was aware of the migration event.
  • The server SHOULD drop this information if it receives a new sequence value for the owner in question, and the request relates to the same file system.
  • The server SHOULD drop the part of this information that relates to non-migrated file systems if it receives a new sequence value for the owner in question, and the request relates to a non-migrated file system.
  • The server MAY drop this information when it receives a new sequence value for the owner in question for a considerable period of time (more than one or two lease periods) after the migration occurs.
  • サーバーは、該当するオーナーについて新しいシーケンス値を受け取ったというだけの理由で、この情報を破棄すべきではありません（SHOULD NOT）。そのリクエストは、クライアントが移行の事象に気付く前に発行された可能性があるからです。
  • サーバーは、該当するオーナーについて新しいシーケンス値を受け取り、そのリクエストが同じファイルシステムに関するものである場合、この情報を破棄するべきです（SHOULD）。
  • サーバーは、該当するオーナーについて新しいシーケンス値を受け取り、そのリクエストが移行されていないファイルシステムに関するものである場合、この情報のうち移行されていないファイルシステムに関する部分を破棄するべきです（SHOULD）。
  • サーバーは、移行が発生してからかなりの期間（1つまたは2つのリース期間より長い期間）後に、該当するオーナーについて新しいシーケンス値を受け取った場合、この情報を破棄してもよいです（MAY）。

6.1.2. Replication and State

6.1.2. 複製と状態

Since client switch-over in the case of replication is not under server control, the handling of state is different. In this case, leases, stateids, and client IDs do not have validity across a transition from one server to another. The client must re-establish its locks on the new server. This can be compared to the re-establishment of locks by means of reclaim-type requests after a server reboot. The difference is that the server has no provision to distinguish requests reclaiming locks from those obtaining new locks or to defer the latter. Thus, a client re-establishing a lock on the new server (by means of a LOCK or OPEN request) may have the requests denied due to a conflicting lock. Since replication is intended for read-only use of file systems, such denial of locks should not pose large difficulties in practice. When an attempt to re-establish a lock on a new server is denied, the client should treat the situation as if its original lock had been revoked.

複製の場合のクライアントの切り替えはサーバーの制御下にないため、状態の扱いは異なります。この場合、リース、stateid、クライアントIDは、あるサーバーから別のサーバーへの遷移をまたいで有効性を持ちません。クライアントは、新しいサーバー上でロックを再確立しなければなりません。これは、サーバーの再起動後に再取得型のリクエストによってロックを再確立することに似ています。違いは、サーバーには、ロックを再取得するリクエストと新しいロックを取得するリクエストを区別したり、後者を延期したりする仕組みがないことです。したがって、（LOCKリクエストまたはOPENリクエストによって）新しいサーバー上でロックを再確立しようとするクライアントは、競合するロックのためにリクエストが拒否される可能性があります。複製はファイルシステムの読み取り専用の使用を意図しているため、そのようなロックの拒否が実際に大きな困難をもたらすことはないはずです。新しいサーバー上でロックを再確立する試みが拒否された場合、クライアントは、元のロックが取り消されたかのようにその状況を扱うべきです。

6.1.3. Notification of Migrated Lease

6.1.3. 移行されたリースの通知

A file system can be migrated to another server while a client that has state related to that file system is not actively submitting requests to it. In this case, the migration is reported to the client during lease renewal. Lease renewal can occur either explicitly via a RENEW operation or implicitly when the client performs a lease-renewing operation on another file system on that server.

ファイルシステムは、そのファイルシステムに関連する状態を持つクライアントがそのファイルシステムに積極的にリクエストを送信していない間に、別のサーバーへ移行されることがあります。この場合、移行はリースの更新中にクライアントに報告されます。リースの更新は、RENEW操作によって明示的に行われるか、クライアントがそのサーバー上の別のファイルシステムに対してリースを更新する操作を行ったときに暗黙的に行われます。

In order for the client to schedule renewal of leases that may have been relocated to the new server, the client must find out about lease relocation before those leases expire. Similarly, when migration occurs but there has not been transparent state migration, the client needs to find out about the change soon enough to be able to reclaim the lock within the destination server's grace period. To accomplish this, all operations that implicitly renew leases for a client (such as OPEN, CLOSE, READ, WRITE, RENEW, LOCK, and others) will return the error NFS4ERR_LEASE_MOVED if responsibility for any of the leases to be renewed has been transferred to a new server. Note that when the transfer of responsibility leaves remaining state for that lease on the source server, the lease is renewed just as it would have been in the NFS4ERR_OK case, despite returning the error. The transfer of responsibility happens when the server receives a GETATTR(fs_locations) from the client for each file system for which a lease has been moved to a new server. Normally, it does this after receiving an NFS4ERR_MOVED for an access to the file system, but the server is not required to verify that this happens in order to terminate the return of NFS4ERR_LEASE_MOVED. By convention, the compounds containing GETATTR(fs_locations) SHOULD include an appended RENEW operation to permit the server to identify the client getting the information.

新しいサーバーに再配置された可能性のあるリースの更新をクライアントが計画できるように、クライアントは、それらのリースの期限が切れる前にリースの再配置について知らなければなりません。同様に、移行が発生したものの透過的な状態移行が行われていない場合、クライアントは、移行先サーバーの猶予期間内にロックを再取得できるように、十分早く変更について知る必要があります。これを実現するために、クライアントのリースを暗黙的に更新するすべての操作（OPEN、CLOSE、READ、WRITE、RENEW、LOCKなど）は、更新対象のリースのいずれかに対する責任が新しいサーバーに移されている場合、エラーNFS4ERR_LEASE_MOVEDを返します。責任の移転によってそのリースの状態が移行元サーバー上に残っている場合、エラーを返すにもかかわらず、リースはNFS4ERR_OKの場合とまったく同じように更新されることに注意してください。責任の移転は、リースが新しいサーバーに移動された各ファイルシステムについて、サーバーがクライアントからGETATTR(fs_locations)を受け取ったときに行われます。通常、クライアントはファイルシステムへのアクセスに対してNFS4ERR_MOVEDを受け取った後にこれを行いますが、サーバーは、NFS4ERR_LEASE_MOVEDを返すのをやめるために、これが行われたことを検証する必要はありません。慣例として、GETATTR(fs_locations)を含むCOMPOUNDには、情報を取得しているクライアントをサーバーが識別できるように、RENEW操作を追加して含めるべきです（SHOULD）。

Note that the NFS4ERR_LEASE_MOVED error is required only when responsibility for at least one stateid has been affected. In the case of a null lease, where the only associated state is a clientid4, an NFS4ERR_LEASE_MOVED error SHOULD NOT be generated.

NFS4ERR_LEASE_MOVEDエラーが必要となるのは、少なくとも1つのstateidに対する責任が影響を受けた場合だけであることに注意してください。関連する状態がclientid4だけであるヌルリースの場合、NFS4ERR_LEASE_MOVEDエラーを生成すべきではありません（SHOULD NOT）。

Upon receiving the NFS4ERR_LEASE_MOVED error, a client that supports file system migration MUST perform the necessary GETATTR operation for each of the file systems containing state that have been migrated, so it gives the server evidence that it is aware of the migration of the file system. Once the client has done this for all migrated file systems on which the client holds state, the server MUST resume normal handling of stateful requests from that client.

NFS4ERR_LEASE_MOVEDエラーを受け取ったとき、ファイルシステムの移行をサポートするクライアントは、移行された、状態を含む各ファイルシステムについて必要なGETATTR操作を行い、ファイルシステムの移行を認識していることの証拠をサーバーに示さなければなりません（MUST）。クライアントが状態を保持している移行されたすべてのファイルシステムについてクライアントがこれを行ったら、サーバーはそのクライアントからのステートフルなリクエストの通常の処理を再開しなければなりません（MUST）。

One way in which clients can do this efficiently in the presence of large numbers of file systems is described below. This approach divides the process into two phases: one devoted to finding the migrated file systems, and the second devoted to doing the necessary GETATTRs.

多数のファイルシステムが存在する場合にクライアントがこれを効率的に行える1つの方法を以下で説明します。この方式は、処理を2つのフェーズに分けます。1つ目は移行されたファイルシステムを見つけることに充てられ、2つ目は必要なGETATTRを行うことに充てられます。

The client can find the migrated file systems by building and issuing one or more COMPOUND requests, each consisting of a set of PUTFH/GETFH pairs, each pair using a filehandle in one of the file systems in question. All such COMPOUND requests can be done in parallel. The successful completion of such a request indicates that none of the file systems interrogated have been migrated while termination with NFS4ERR_MOVED indicates that the file system getting the error has migrated while those interrogated before it in the same COMPOUND have not. Those whose interrogation follows the error remain in an uncertain state and can be interrogated by restarting the requests from after the point at which NFS4ERR_MOVED was returned or by issuing a new set of COMPOUND requests for the file systems that remain in an uncertain state.

クライアントは、1つ以上のCOMPOUNDリクエストを構築して発行することによって、移行されたファイルシステムを見つけられます。各リクエストはPUTFH/GETFHの組の集合から構成され、各組は該当するファイルシステムのいずれかのファイルハンドルを使用します。そのようなCOMPOUNDリクエストはすべて並行して行えます。そのようなリクエストが正常に完了した場合は、問い合わせたファイルシステムがどれも移行されていないことを示します。一方、NFS4ERR_MOVEDで終了した場合は、エラーを受け取ったファイルシステムは移行されており、同じCOMPOUND内でそれより前に問い合わせたファイルシステムは移行されていないことを示します。エラーの後に問い合わせる予定だったファイルシステムは不確かな状態のままであり、NFS4ERR_MOVEDが返された時点の後からリクエストを再開するか、不確かな状態のままのファイルシステムについて新しいCOMPOUNDリクエストの集合を発行することによって、問い合わせることができます。

Once the migrated file systems have been found, all that is needed is for the client to give evidence to the server that it is aware of the migrated status of file systems found by this process, by interrogating the fs_locations attribute for a filehandle within each of the migrated file systems. The client can do this by building and issuing one or more COMPOUND requests, each of which consists of a set of PUTFH operations, each followed by a GETATTR of the fs_locations attribute. A RENEW is necessary to enable the operations to be associated with the lease returning NFS4ERR_LEASE_MOVED. Once the client has done this for all migrated file systems on which the client holds state, the server will resume normal handling of stateful requests from that client.

移行されたファイルシステムが見つかったら、あとはクライアントが、移行された各ファイルシステム内のファイルハンドルについてfs_locations属性を問い合わせることによって、この処理で見つかったファイルシステムが移行された状態であることを認識していることの証拠をサーバーに示すだけです。クライアントは、1つ以上のCOMPOUNDリクエストを構築して発行することでこれを行えます。各リクエストはPUTFH操作の集合から構成され、それぞれの後にfs_locations属性のGETATTRが続きます。これらの操作を、NFS4ERR_LEASE_MOVEDを返しているリースに関連付けられるようにするには、RENEWが必要です。クライアントが状態を保持している移行されたすべてのファイルシステムについてクライアントがこれを行ったら、サーバーはそのクライアントからのステートフルなリクエストの通常の処理を再開します。

In order to support legacy clients that do not handle the NFS4ERR_LEASE_MOVED error correctly, the server SHOULD time out after a wait of at least two lease periods, at which time it will resume normal handling of stateful requests from all clients. If a client attempts to access the migrated files, the server MUST reply with NFS4ERR_MOVED. In this situation, it is likely that the client would find its lease expired, although a server may use "courtesy" locks (as described in Section 9.6.3.1 of [RFC7530]) to mitigate the issue.

NFS4ERR_LEASE_MOVEDエラーを正しく処理しないレガシーなクライアントをサポートするために、サーバーは少なくとも2つのリース期間待機した後にタイムアウトすべきです（SHOULD）。その時点で、サーバーはすべてのクライアントからのステートフルなリクエストの通常の処理を再開します。クライアントが移行されたファイルにアクセスしようとした場合、サーバーはNFS4ERR_MOVEDで応答しなければなりません（MUST）。この状況では、クライアントは自身のリースの期限が切れていることに気付く可能性が高いですが、サーバーはこの問題を緩和するために（[RFC7530]のセクション9.6.3.1で説明されている）「courtesy」ロックを使用できます。

When the client receives an NFS4ERR_MOVED error, the client can follow the normal process to obtain the destination server information (through the fs_locations attribute) and perform renewal of those leases on the new server. If the server has not had state transferred to it transparently, the client will receive either NFS4ERR_STALE_CLIENTID or NFS4ERR_STALE_STATEID from the new server, as described above. The client can then recover state information as it does in the event of server failure.

クライアントがNFS4ERR_MOVEDエラーを受け取った場合、クライアントは通常の処理に従って（fs_locations属性によって）移行先サーバーの情報を取得し、新しいサーバー上でそれらのリースの更新を行えます。サーバーに状態が透過的に転送されていない場合、前述のように、クライアントは新しいサーバーからNFS4ERR_STALE_CLIENTIDまたはNFS4ERR_STALE_STATEIDのいずれかを受け取ります。その後、クライアントはサーバーの障害の場合と同じように状態情報を回復できます。

Aside from recovering from a migration, there are other reasons a client may wish to retrieve fs_locations information from a server. When a server becomes unresponsive, for example, a client may use cached fs_locations data to discover an alternate server hosting the same file system data. A client may periodically request fs_locations data from a server in order to keep its cache of fs_locations data fresh.

移行からの回復以外にも、クライアントがサーバーからfs_locationsの情報を取得したい理由はあります。たとえば、サーバーが応答しなくなった場合、クライアントはキャッシュされたfs_locationsのデータを使用して、同じファイルシステムのデータをホストしている代わりのサーバーを見つけることができます。クライアントは、fs_locationsのデータのキャッシュを新鮮に保つために、サーバーに定期的にfs_locationsのデータを要求することがあります。

Since a GETATTR(fs_locations) operation would be used for refreshing cached fs_locations data, a server could mistake such a request as indicating recognition of an NFS4ERR_LEASE_MOVED condition. Therefore, a compound that is not intended to signal that a client has recognized a migrated lease SHOULD be prefixed with a guard operation that fails with NFS4ERR_MOVED if the filehandle being queried is no longer present on the server. The guard can be as simple as a GETFH operation.

GETATTR(fs_locations)操作はキャッシュされたfs_locationsのデータの更新に使用されるため、サーバーはそのようなリクエストを、NFS4ERR_LEASE_MOVEDの状態を認識したことを示すものと誤解する可能性があります。したがって、移行されたリースをクライアントが認識したことを伝えることを意図していないCOMPOUNDの先頭には、問い合わせ対象のファイルハンドルがサーバー上にもはや存在しない場合にNFS4ERR_MOVEDで失敗するガード操作を置くべきです（SHOULD）。ガードは、GETFH操作のような単純なもので構いません。

Though unlikely, it is possible that the target of such a compound could be migrated in the time after the guard operation is executed on the server but before the GETATTR(fs_locations) operation is encountered. When a client issues a GETATTR(fs_locations) operation as part of a compound not intended to signal recognition of a migrated lease, it SHOULD be prepared to process fs_locations data in the reply that shows the current location of the file system is gone.

可能性は低いものの、そのようなCOMPOUNDのターゲットが、ガード操作がサーバー上で実行された後、GETATTR(fs_locations)操作に到達する前の時間に移行される可能性があります。移行されたリースの認識を伝えることを意図していないCOMPOUNDの一部としてGETATTR(fs_locations)操作を発行する場合、クライアントは、ファイルシステムの現在の場所がなくなったことを示すfs_locationsのデータが応答に含まれていても処理できるように準備しておくべきです（SHOULD）。

6.1.4. Migration and the lease_time Attribute

6.1.4. 移行とlease_time属性

In order that the client may appropriately manage its leases in the case of migration, the destination server must establish proper values for the lease_time attribute.

移行の場合にクライアントがリースを適切に管理できるように、移行先サーバーはlease_time属性に適切な値を設定しなければなりません。

When state is transferred transparently, that state should include the correct value of the lease_time attribute. The lease_time attribute on the destination server must never be less than that on the source since this would result in premature expiration of leases granted by the source server. Upon migration in which state is transferred transparently, the client is under no obligation to refetch the lease_time attribute and may continue to use the value previously fetched (on the source server).

状態が透過的に転送される場合、その状態にはlease_time属性の正しい値が含まれるべきです。移行先サーバー上のlease_time属性は、移行元のものより決して小さくてはいけません。そうなると、移行元サーバーが許可したリースが早期に期限切れになってしまうからです。状態が透過的に転送される移行の際、クライアントにはlease_time属性を再取得する義務はなく、以前に（移行元サーバー上で）取得した値を引き続き使用できます。

In the case in which lease merger occurs as part of state transfer, the lease_time attribute of the destination lease remains in effect. The client can simply renew that lease with its existing lease_time attribute. State in the source lease is renewed at the time of transfer so that it cannot expire, as long as the destination lease is appropriately renewed.

状態の転送の一部としてリースのマージが行われる場合、移行先のリースのlease_time属性が引き続き有効です。クライアントは、既存のlease_time属性でそのリースを更新するだけで済みます。移行元のリースにある状態は、移行先のリースが適切に更新されている限り期限切れにならないように、転送時に更新されます。

If state has not been transferred transparently (i.e., the client needs to reclaim or re-obtain its locks), the client should fetch the value of lease_time on the new (i.e., destination) server, and use it for subsequent locking requests. However, the server must respect a grace period at least as long as the lease_time on the source server, in order to ensure that clients have ample time to reclaim their locks before potentially conflicting non-reclaimed locks are granted. The means by which the new server obtains the value of lease_time on the old server is left to the server implementations. It is not specified by the NFS version 4.0 protocol.

状態が透過的に転送されていない場合（つまり、クライアントがロックを再取得するか取得し直す必要がある場合）、クライアントは新しい（つまり、移行先の）サーバー上のlease_timeの値を取得し、それを後続のロックリクエストに使用すべきです。ただし、競合する可能性のある再取得でないロックが許可される前に、クライアントがロックを再取得するための十分な時間を確保するために、サーバーは少なくとも移行元サーバー上のlease_timeと同じ長さの猶予期間を守らなければなりません。新しいサーバーが古いサーバー上のlease_timeの値を取得する手段は、サーバーの実装に委ねられます。それはNFSバージョン4.0プロトコルでは規定されていません。

7. Server Implementation Considerations

7. サーバーの実装に関する考慮事項

This section provides suggestions to help server implementers deal with issues involved in the transparent transfer of file-system-related data between servers. Servers are not obliged to follow these suggestions but should be sure that their approach to the issues handle all the potential problems addressed below.

このセクションでは、サーバー間でのファイルシステム関連のデータの透過的な転送に伴う問題にサーバーの実装者が対処するのに役立つ提案を示します。サーバーはこれらの提案に従う義務はありませんが、問題に対する自身の方式が、以下で取り上げる潜在的な問題のすべてに対処していることを確認すべきです。

7.1. Relation of Locking State Transfer to Other Aspects of File System Motion

7.1. ロック状態の転送とファイルシステムの移動の他の側面との関係

In many cases, state transfer will be part of a larger function wherein the contents of a file system are transferred from server to server. Although specifics will vary with the implementation, the relation between the transfer of persistent file data and metadata and the transfer of state will typically be described by one of the cases below.

多くの場合、状態の転送は、ファイルシステムの内容をサーバーからサーバーへ転送する、より大きな機能の一部になります。詳細は実装によって異なりますが、永続的なファイルのデータとメタデータの転送と、状態の転送との関係は、通常、次のいずれかのケースで説明されます。

  • In some implementations, access to the on-disk contents of a file system can be transferred from server to server by making the storage devices on which the file system resides physically accessible from multiple servers, and transferring the right and responsibility for handling that file system from server to server.

    In such implementations, the transfer of locking state happens on its own, as described in Section 7.2. The transfer of physical access to the file system happens after the locking state is transferred and before any subsequent access to the file system. In cases where such transfer is not instantaneous, there will be a period in which all operations on the file system are held off, either by having the operations themselves return NFS4ERR_DELAY or, where this is not allowed, by using the techniques described below in Section 7.2.

  • In other implementations, file system data and metadata must be copied from the server where they have existed to the destination server. Because of the typical amounts of data involved, it is generally not practical to hold off access to the file system while this transfer is going on. Normal access to the file system, including modifying operations, will generally happen while the transfer is going on.

    Eventually, the file system copying process will complete. At this point, there will be two valid copies of the file system, one on each of the source and destination servers. Servers may maintain that state of affairs by making sure that each modification to file system data is done on both the source and destination servers.

    Although the transfer of locking state can begin before the above state of affairs is reached, servers will often wait until it is arrived at to begin transfer of locking state. Once the transfer of locking state is completed, as described in the section below, clients may be notified of the migration event and access the destination file system on the destination server.

  • Another case in which file system data and metadata must be copied from server to server involves a variant of the pattern above. In cases in which a single file system moves between or among a small set of servers, it will transition to a server on which a previous instantiation of that same file system existed before. In such cases, it is often more efficient to update the previous file system instance to reflect changes made while the active file system was residing elsewhere rather than copying the file system data anew.

    In such cases, the copying of file system data and metadata is replaced by a process that validates each visible file system object, copying new objects and updating those that have changed since the file system was last present on the destination server. Although this process is generally shorter than a complete copy, it is generally long enough that it is not practical to hold off access to the file system while this update is going on.

    Eventually, the file system updating process will complete. At this point, there will be two valid copies of the file system, one on each of the source and destination servers. Servers may maintain that state of affairs just as is done in the previous case. Similarly, the transfer of locking state, once it is complete, allows the clients to be notified of the migration event and access the destination file system on the destination server.

  • 一部の実装では、ファイルシステムが存在するストレージデバイスを複数のサーバーから物理的にアクセス可能にし、そのファイルシステムを扱う権利と責任をサーバーからサーバーへ移すことによって、ファイルシステムのディスク上の内容へのアクセスをサーバーからサーバーへ移すことができます。

    そのような実装では、セクション7.2で説明するように、ロック状態の転送は単独で行われます。ファイルシステムへの物理的なアクセスの移転は、ロック状態が転送された後、かつファイルシステムへの後続のアクセスの前に行われます。そのような移転が瞬時に行われない場合、ファイルシステムに対するすべての操作が保留される期間が生じます。これは、操作自体にNFS4ERR_DELAYを返させるか、それが許されない場合は、以下のセクション7.2で説明する手法を使用することによって行われます。

  • 他の実装では、ファイルシステムのデータとメタデータを、それらが存在していたサーバーから移行先サーバーへコピーしなければなりません。通常は関わるデータの量が多いため、この転送が行われている間ファイルシステムへのアクセスを保留することは、一般に現実的ではありません。転送が行われている間も、変更を伴う操作を含め、ファイルシステムへの通常のアクセスは一般に行われます。

    最終的に、ファイルシステムのコピー処理は完了します。この時点で、移行元サーバーと移行先サーバーのそれぞれに1つずつ、ファイルシステムの有効なコピーが2つ存在することになります。サーバーは、ファイルシステムのデータへの各変更が移行元サーバーと移行先サーバーの両方で行われるようにすることによって、その状態を維持できます。

    ロック状態の転送は上記の状態に達する前に開始できますが、サーバーは多くの場合、その状態に達するまで待ってからロック状態の転送を開始します。以下のセクションで説明するように、ロック状態の転送が完了すると、クライアントは移行の事象を通知され、移行先サーバー上の移行先のファイルシステムにアクセスできます。

  • ファイルシステムのデータとメタデータをサーバーからサーバーへコピーしなければならないもう1つのケースは、上記のパターンの変形です。単一のファイルシステムが少数のサーバーの間を移動する場合、そのファイルシステムは、同じファイルシステムの以前のインスタンスが存在していたサーバーへ遷移することになります。そのような場合、ファイルシステムのデータを新たにコピーするよりも、アクティブなファイルシステムが他の場所にあった間に行われた変更を反映するように以前のファイルシステムのインスタンスを更新する方が、多くの場合効率的です。

    そのような場合、ファイルシステムのデータとメタデータのコピーは、目に見える各ファイルシステムオブジェクトを検証し、新しいオブジェクトをコピーし、ファイルシステムが最後に移行先サーバー上に存在していた時点以降に変更されたオブジェクトを更新する処理に置き換えられます。この処理は一般に完全なコピーよりも短くて済みますが、それでも一般に十分長いため、この更新が行われている間ファイルシステムへのアクセスを保留することは現実的ではありません。

    最終的に、ファイルシステムの更新処理は完了します。この時点で、移行元サーバーと移行先サーバーのそれぞれに1つずつ、ファイルシステムの有効なコピーが2つ存在することになります。サーバーは、前のケースとまったく同じようにその状態を維持できます。同様に、ロック状態の転送が完了すると、クライアントは移行の事象を通知され、移行先サーバー上の移行先のファイルシステムにアクセスできるようになります。

7.2. Preventing Locking State Modification during Transfer

7.2. 転送中のロック状態の変更の防止

When transferring locking state from the source to a destination server, there will be occasions when the source server will need to prevent operations that modify the state being transferred. For example, if the locking state at time T is sent to the destination server, any state change that occurs on the source server after that time but before the file system transfer is made effective will mean that the state on the destination server will differ from that on the source server, which matches what the client would expect to see.

移行元サーバーから移行先サーバーへロック状態を転送する際、移行元サーバーが、転送中の状態を変更する操作を防ぐ必要がある場合があります。たとえば、時刻Tのロック状態が移行先サーバーに送られた場合、その時刻より後、ファイルシステムの移転が有効になる前に移行元サーバー上で発生した状態の変化は、移行先サーバー上の状態が、クライアントが見ることを期待している状態と一致する移行元サーバー上の状態と異なることを意味します。

In general, a server can prevent some set of server-maintained data from changing by returning NFS4ERR_DELAY on operations that attempt to change that data. In the case of locking state for NFSv4.0, there are two specific issues that might interfere:

一般に、サーバーは、サーバーが維持するデータの集合が変更されるのを、そのデータを変更しようとする操作に対してNFS4ERR_DELAYを返すことによって防ぐことができます。NFSv4.0のロック状態の場合、妨げとなりうる具体的な問題が2つあります：

  • Returning NFS4ERR_DELAY will not prevent state from changing in that owner-based sequence values will still change, even though NFS4ERR_DELAY is returned. For example, OPEN and LOCK will change state (in the form of owner seqid values) even when they return NFS4ERR_DELAY.
  • Some operations that modify locking state are not allowed to return NFS4ERR_DELAY (i.e., OPEN_CONFIRM, RELEASE_LOCKOWNER, and RENEW).
  • NFS4ERR_DELAYを返しても、オーナーに基づくシーケンス値はNFS4ERR_DELAYが返されても変化するという点で、状態の変化を防ぐことはできません。たとえば、OPENとLOCKは、NFS4ERR_DELAYを返す場合でも（オーナーのseqidの値という形で）状態を変更します。
  • ロック状態を変更する一部の操作（つまり、OPEN_CONFIRM、RELEASE_LOCKOWNER、RENEW）は、NFS4ERR_DELAYを返すことが許されていません。

Note that the first problem and most instances of the second can be addressed by returning NFS4ERR_DELAY on the operations that establish a filehandle within the target as one of the filehandles associated with the request, i.e., as either the current or saved filehandle. This would require returning NFS4ERR_DELAY under the following circumstances:

1つ目の問題と2つ目の問題のほとんどの場合は、ターゲット内のファイルハンドルを、リクエストに関連付けられたファイルハンドルの1つとして、つまり現在のファイルハンドルまたは保存されたファイルハンドルとして確立する操作に対してNFS4ERR_DELAYを返すことで対処できることに注意してください。そのためには、次の状況でNFS4ERR_DELAYを返す必要があります：

  • On a PUTFH that specifies a filehandle within the target file system.
  • On a LOOKUP or LOOKUPP that crosses into the target file system.
  • ターゲットのファイルシステム内のファイルハンドルを指定するPUTFHに対して。
  • ターゲットのファイルシステムへと境界を越えるLOOKUPまたはLOOKUPPに対して。

As a result of doing this, OPEN_CONFIRM is dealt with, leaving only RELEASE_LOCKOWNER and RENEW still to be dealt with.

こうすることで、OPEN_CONFIRMには対処でき、対処すべきものとして残るのはRELEASE_LOCKOWNERとRENEWだけになります。

Note that if the server establishes and maintains a situation in which no request has, as either the current or saved filehandle, a filehandle within the target file system, no special handling of SAVEFH or RESTOREFH is required. Thus, the fact that these operations cannot return NFS4ERR_DELAY is not a problem since neither will establish a filehandle in the target file system as the current filehandle.

ターゲットのファイルシステム内のファイルハンドルを現在のファイルハンドルとしても保存されたファイルハンドルとしても持つリクエストが存在しない状況をサーバーが確立して維持する場合、SAVEFHやRESTOREFHの特別な処理は必要ないことに注意してください。したがって、これらの操作がNFS4ERR_DELAYを返せないという事実は問題になりません。どちらの操作も、ターゲットのファイルシステム内のファイルハンドルを現在のファイルハンドルとして確立することはないからです。

If the server is to establish the situation described above, it may have to take special note of long-running requests that started before state migration. Part of any solution to this issue will involve distinguishing two separate points in time at which handling for the target file system will change. Let us distinguish:

サーバーが上記の状況を確立する場合、状態の移行の前に開始された長時間実行されるリクエストに特に注意を払う必要があるかもしれません。この問題に対するどのような解決策にも、ターゲットのファイルシステムの処理が変わる2つの別々の時点を区別することが含まれるでしょう。次のように区別します：

  • A time T after which the previously mentioned operations will return NFS4ERR_DELAY.
  • A later time T' at which the server can consider file system locking state fixed, making it possible for it to be sent to the destination server.
  • それ以降、前述の操作がNFS4ERR_DELAYを返すようになる時刻T。
  • サーバーがファイルシステムのロック状態を固定されたものとみなすことができ、それを移行先サーバーに送れるようになる、それより後の時刻T'。

For a server to decide on T', it must ensure that requests started before T cannot change target file system locking state, given that all those started after T are dealt with by returning NFS4ERR_DELAY upon setting filehandles within the target file system. Among the ways of doing this are:

サーバーがT'を決定するためには、Tより後に開始されたリクエストはすべて、ターゲットのファイルシステム内のファイルハンドルを設定する際にNFS4ERR_DELAYを返すことで対処されることを前提として、Tより前に開始されたリクエストがターゲットのファイルシステムのロック状態を変更できないことを保証しなければなりません。これを行う方法には次のものがあります：

  • Keeping track of the earliest request started that is still in execution (for example, by keeping a list of active requests ordered by request start time). Requests that started before and are still in progress at time T may potentially affect the locking state; once the starting time of the earliest-started active request is later than T, the starting time of the first such request can be chosen as T' by the server since any request in progress after T' started after time T. Accordingly, it would not have been allowed to change locking state for the migrating file system and would have returned NFS4ERR_DELAY had it tried to make a change.
  • Keeping track of the count of requests started before time T that have a filehandle within the target file system as either the current or saved filehandle. The server can then define T' to be the first time after T at which the count is zero.
  • まだ実行中のリクエストのうち最も早く開始されたものを追跡する（たとえば、リクエストの開始時刻順に並べたアクティブなリクエストのリストを保持することによって）。時刻Tより前に開始され、時刻Tにまだ進行中のリクエストは、ロック状態に影響を与える可能性があります。最も早く開始されたアクティブなリクエストの開始時刻がTより後になったら、サーバーはそのような最初のリクエストの開始時刻をT'として選ぶことができます。T'の後に進行中のリクエストはどれも時刻Tの後に開始されたものだからです。したがって、そのリクエストは移行されるファイルシステムのロック状態を変更することを許されず、変更しようとしていればNFS4ERR_DELAYを返していたはずです。
  • 時刻Tより前に開始され、ターゲットのファイルシステム内のファイルハンドルを現在のファイルハンドルまたは保存されたファイルハンドルとして持つリクエストの数を追跡する。その後、サーバーは、T'を、Tより後でその数が0になった最初の時刻と定義できます。

The set of operations that change locking state include two that cannot be dealt with by the above approach, because they are not specific to a particular file system and do not use a current filehandle as an implicit parameter.

ロック状態を変更する操作の集合には、上記の方式では対処できないものが2つ含まれています。それらは特定のファイルシステムに固有のものではなく、暗黙のパラメーターとして現在のファイルハンドルを使用しないからです。

  • RENEW can be dealt with by applying the renewal to state for non-transitioning file systems. The effect of renewal for the transitioning file system can be ignored, as long as the servers make sure that the lease on the destination server has an expiration time that is no earlier than the latest renewal done on the source server. This can be easily accomplished by making the lease expiration on the destination server equal to the time in which the state transfer was completed plus the lease period.

  • RELEASE_LOCKOWNER can be handled by propagating the fact of the lock-owner deletion (e.g., by using an RPC) to the destination server. Such a propagation RPC can be done as part of the operation, or the existence of the deletion can be recorded locally and propagation of owner deletions to the destination server done as a batch later. In either case, the actual deletions on the destination server have to be delayed until all of the other state information has been transferred.

    Alternatively, RELEASE_LOCKOWNER can be dealt with by returning NFS4ERR_DELAY. In order to avoid compatibility issues for clients not prepared to accept NFS4ERR_DELAY in response to RELEASE_LOCKOWNER, care must be exercised. (See Section 8.3 for details.)

  • RENEWには、遷移中でないファイルシステムの状態に更新を適用することで対処できます。遷移中のファイルシステムに対する更新の効果は、移行先サーバー上のリースの有効期限が移行元サーバー上で行われた最新の更新よりも早くならないようにサーバーが保証する限り、無視できます。これは、移行先サーバー上のリースの有効期限を、状態の転送が完了した時刻にリース期間を加えたものに等しくすることで簡単に実現できます。

  • RELEASE_LOCKOWNERは、lock-ownerが削除されたという事実を（たとえば、RPCを使用して）移行先サーバーに伝播することによって処理できます。そのような伝播のRPCは操作の一部として行うこともできますし、削除があったことをローカルに記録しておき、オーナーの削除の移行先サーバーへの伝播を後でまとめて行うこともできます。いずれの場合も、移行先サーバー上での実際の削除は、他のすべての状態情報が転送されるまで遅延させなければなりません。

    あるいは、RELEASE_LOCKOWNERにはNFS4ERR_DELAYを返すことで対処することもできます。RELEASE_LOCKOWNERに対するレスポンスとしてNFS4ERR_DELAYを受け入れる準備ができていないクライアントとの互換性の問題を避けるために、注意しなければなりません。（詳細についてはセクション8.3を参照してください。）

The approach outlined above, wherein NFS4ERR_DELAY is returned based primarily on the use of current and saved filehandles in the file system, prevents all reference to the transitioning file system rather than limiting the delayed operations to those that change locking state on the transitioning file system. Because of this, servers may choose to limit the time during which this broad approach is used by adopting a layered approach to the issue.

上で概説した方式では、主にファイルシステム内の現在のファイルハンドルと保存されたファイルハンドルの使用に基づいてNFS4ERR_DELAYを返すため、遅延させる操作を遷移中のファイルシステムのロック状態を変更するものに限定するのではなく、遷移中のファイルシステムへのすべての参照を妨げます。このため、サーバーは、この問題に対して段階的な方式を採用することによって、この広範な方式を使用する時間を制限することを選択できます。

  • During the preparatory phase, operations that change, create, or destroy locks or modify the valid set of stateids will return NFS4ERR_DELAY. During this phase, owner-associated seqids may change, and the identity of the file system associated with the last request for a given owner may change as well. Also, RELEASE_LOCKOWNER operations may be processed without returning NFS4ERR_DELAY as long as the fact of the lock-owner deletion is recorded locally for later transmission.
  • During the restrictive phase, operations that change locking state for the file system in transition are prevented by returning NFS4ERR_DELAY on any attempt to make a filehandle within that file system either the current or saved filehandle for a request. RELEASE_LOCKOWNER operations may return NFS4ERR_DELAY, but if they are processed, the lock-owner deletion needs to be communicated immediately to the destination server.
  • 準備フェーズの間は、ロックを変更、作成、破棄する操作や、stateidの有効な集合を変更する操作はNFS4ERR_DELAYを返します。このフェーズの間、オーナーに関連付けられたseqidは変化する場合があり、特定のオーナーの最後のリクエストに関連付けられたファイルシステムのアイデンティティーも変化する場合があります。また、lock-ownerが削除されたという事実が後で送信するためにローカルに記録される限り、RELEASE_LOCKOWNER操作はNFS4ERR_DELAYを返さずに処理できます。
  • 制限フェーズの間は、遷移中のファイルシステムのロック状態を変更する操作は、そのファイルシステム内のファイルハンドルをリクエストの現在のファイルハンドルまたは保存されたファイルハンドルにしようとするあらゆる試みに対してNFS4ERR_DELAYを返すことによって防がれます。RELEASE_LOCKOWNER操作はNFS4ERR_DELAYを返すことができますが、処理される場合は、lock-ownerの削除を直ちに移行先サーバーに伝える必要があります。

A possible sequence would be the following.

考えられる手順は次のようになるでしょう。

  • The server enters the preparatory phase for the transitioning file system.
  • At this point, locking state, including stateids, locks, and owner strings, is transferred to the destination server. The seqids associated with owners are either not transferred or transferred on a provisional basis, subject to later change.
  • After the above has been transferred, the server may enter the restrictive phase for the file system.

  • At this point, the updated seqid values may be sent to the destination server.

    Reporting regarding pending owner deletions (as a result of RELEASE_LOCKOWNER operations) can be communicated at the same time.

  • Once it is known that all of this information has been transferred to the destination server, and there are no pending RELEASE_LOCKOWNER notifications outstanding, the source server may treat the file system transition as having occurred and return NFS4ERR_MOVED when an attempt is made to access it.
  • サーバーは、遷移中のファイルシステムについて準備フェーズに入ります。
  • この時点で、stateid、ロック、オーナー文字列を含むロック状態が移行先サーバーに転送されます。オーナーに関連付けられたseqidは、転送されないか、後で変更されることを前提として暫定的に転送されます。
  • 上記が転送された後、サーバーはそのファイルシステムについて制限フェーズに入ることができます。

  • この時点で、更新されたseqidの値を移行先サーバーに送ることができます。

    （RELEASE_LOCKOWNER操作の結果としての）保留中のオーナーの削除に関する報告も、同時に伝えることができます。

  • これらの情報がすべて移行先サーバーに転送され、未処理の保留中のRELEASE_LOCKOWNERの通知がないことがわかったら、移行元サーバーは、ファイルシステムの遷移が行われたものとして扱い、そのファイルシステムへのアクセスが試みられた場合にNFS4ERR_MOVEDを返すことができます。

8.2. NFS4ERR_CLID_INUSE Definition

8.2. NFS4ERR_CLID_INUSEの定義

The definition of this error is now as follows:

このエラーの定義は、次のようになります：

The SETCLIENTID operation has found that the id string within the specified nfs_client_id4 was previously presented with a different principal and that client instance currently holds an active lease. A server MAY return this error if the same principal is used, but a change in authentication flavor gives good reason to reject the new SETCLIENTID operation as not bona fide.

SETCLIENTID操作は、指定されたnfs_client_id4内のid文字列が以前に異なるプリンシパルで提示されており、そのクライアントインスタンスが現在アクティブなリースを保持していることを発見しました。同じプリンシパルが使用されていても、認証フレーバーの変更が新しいSETCLIENTID操作を正当でないものとして拒否する十分な理由になる場合、サーバーはこのエラーを返してもよいです（MAY）。

8.3. NFS4ERR_DELAY Return from RELEASE_LOCKOWNER

8.3. RELEASE_LOCKOWNERからのNFS4ERR_DELAYの返却

The existing error tables should be considered modified to allow NFS4ERR_DELAY to be returned by RELEASE_LOCKOWNER. However, the scope of this addition is limited and is not to be considered as making this error return generally acceptable.

既存のエラー表は、RELEASE_LOCKOWNERがNFS4ERR_DELAYを返すことを許可するように修正されたものとみなすべきです。ただし、この追加の範囲は限定されており、このエラーを返すことが一般的に許容されるようになったものとみなしてはいけません。

It needs to be made clear that servers may not return this error to clients not prepared to support file system migration. Such clients may be following the error specifications in [RFC7530] and so might not expect NFS4ERR_DELAY to be returned on RELEASE_LOCKOWNER.

ファイルシステムの移行をサポートする準備ができていないクライアントに対しては、サーバーがこのエラーを返せないことを明確にしておく必要があります。そのようなクライアントは[RFC7530]のエラー仕様に従っている可能性があり、そのため、RELEASE_LOCKOWNERに対してNFS4ERR_DELAYが返されることを予期していないかもしれません。

The following constraint applies to this additional error return, as if it were a note appearing together with the newly allowed error code:

この追加のエラーの返却には、新たに許可されたエラーコードとともに記載される注記であるかのように、次の制約が適用されます：

In order to make server state fixed for a file system being migrated, a server MAY return NFS4ERR_DELAY in response to a RELEASE_LOCKOWNER that will affect locking state being propagated to a destination server. The source server MUST NOT do so unless it is likely that it will later return NFS4ERR_MOVED for the file system in question.

In the context of lock-owner release, the set of file systems, such that server state being made fixed can result in NFS4ERR_DELAY, must include the file system on which the operation associated with the current lock-owner seqid was performed.

In addition, this set may include other file systems on which an operation associated with an earlier seqid for the current lock-owner seqid was performed, since servers will have to deal with the issue of an owner being used in succession for multiple file systems.

Thus, if a client is prepared to receive NFS4ERR_MOVED after creating state associated with a given file system, it also needs to be prepared to receive NFS4ERR_DELAY in response to RELEASE_LOCKOWNER, if it has used that owner in connection with a file on that file system.

移行されるファイルシステムについてサーバーの状態を固定するために、サーバーは、移行先サーバーに伝播されるロック状態に影響を与えるRELEASE_LOCKOWNERに対するレスポンスとしてNFS4ERR_DELAYを返してもよいです（MAY）。移行元サーバーは、該当するファイルシステムについて後でNFS4ERR_MOVEDを返す可能性が高い場合を除いて、そうしてはなりません（MUST NOT）。

lock-ownerの解放の文脈において、サーバーの状態が固定されることによってNFS4ERR_DELAYとなりうるファイルシステムの集合には、現在のlock-ownerのseqidに関連付けられた操作が実行されたファイルシステムが含まれなければなりません。

さらに、サーバーは、オーナーが複数のファイルシステムに対して連続して使用されるという問題に対処しなければならないため、この集合には、現在のlock-ownerのseqidに対するそれ以前のseqidに関連付けられた操作が実行された他のファイルシステムが含まれる場合があります。

したがって、特定のファイルシステムに関連付けられた状態を作成した後にNFS4ERR_MOVEDを受け取る準備ができているクライアントは、そのファイルシステム上のファイルに関してそのオーナーを使用したことがある場合、RELEASE_LOCKOWNERに対するレスポンスとしてNFS4ERR_DELAYを受け取る準備もしておく必要があります。

8.4.4. DESCRIPTION

8.4.4. 説明

The client uses the SETCLIENTID operation to notify the server of its intention to use a particular client identifier, callback, and callback_ident for subsequent requests that entail creating lock, share reservation, and delegation state on the server. Upon successful completion, the server will return a shorthand client ID that, if confirmed via a separate step, will be used in subsequent file locking and file open requests. Confirmation of the client ID must be done via the SETCLIENTID_CONFIRM operation to return the client ID and setclientid_confirm values, as verifiers, to the server. The reason why two verifiers are necessary is that it is possible to use SETCLIENTID and SETCLIENTID_CONFIRM to modify the callback and callback_ident information but not the shorthand client ID. In that event, the setclientid_confirm value is effectively the only verifier.

クライアントは、SETCLIENTID操作を使用して、サーバー上にロック、共有予約、委任の状態を作成することを伴う後続のリクエストで、特定のクライアント識別子、callback、callback_identを使用するという意図をサーバーに通知します。正常に完了すると、サーバーは短縮形のクライアントIDを返します。このクライアントIDは、別の手順で確認されれば、後続のファイルロックとファイルオープンのリクエストで使用されます。クライアントIDの確認は、クライアントIDとsetclientid_confirmの値をベリファイアーとしてサーバーに返すSETCLIENTID_CONFIRM操作によって行わなければなりません。2つのベリファイアーが必要な理由は、SETCLIENTIDとSETCLIENTID_CONFIRMを使用して、短縮形のクライアントIDは変更せずに、callbackとcallback_identの情報を変更できるからです。その場合、setclientid_confirmの値が事実上唯一のベリファイアーになります。

The callback information provided in this operation will be used if the client is provided an open delegation at a future point. Therefore, the client must correctly reflect the program and port numbers for the callback program at the time SETCLIENTID is used.

この操作で提供されるコールバック情報は、将来の時点でクライアントにオープン委任が提供された場合に使用されます。したがって、クライアントは、SETCLIENTIDを使用する時点で、コールバックプログラムのプログラム番号とポート番号を正しく反映しなければなりません。

The callback_ident value is used by the server on the callback. The client can leverage the callback_ident to eliminate the need for more than one callback RPC program number, while still being able to determine which server is initiating the callback.

callback_identの値は、サーバーがコールバックで使用します。クライアントは、callback_identを活用することで、どのサーバーがコールバックを開始しているかを判断できるようにしながら、複数のコールバックRPCプログラム番号を必要としないようにできます。

8.4.5.1. IMPLEMENTATION (Preparatory Phase)
8.4.5.1. 実装（準備フェーズ）

Since SETCLIENTID is a non-idempotent operation, our treatment assumes use of a duplicate request cache (DRC). For a discussion of the DRC, see Section 9.1.7 of [RFC7530].

SETCLIENTIDは非冪等な操作であるため、ここでの扱いでは重複リクエストキャッシュ（DRC）の使用を前提とします。DRCの説明については、[RFC7530]のセクション9.1.7を参照してください。

When the server gets a SETCLIENTID { v, x, k } request, it first does a number of preliminary checks as listed below before proceeding to the main part of SETCLIENTID processing.

サーバーは、SETCLIENTID { v, x, k }リクエストを受け取ると、SETCLIENTIDの処理の主要部分に進む前に、まず次に挙げるいくつかの予備的なチェックを行います。

  • It first looks up the request in the DRC. If there is a hit, it returns the result cached in the DRC. The server does NOT remove client state (locks, shares, delegations) nor does it modify any recorded callback and callback_ident information for client { x }. The server now proceeds to the main part of SETCLIENTID.

  • Otherwise (i.e., in the case of any DRC miss), the server takes the client ID string x and searches for confirmed client records for x that the server may have recorded from previous SETCLIENTID calls. If there are no such records, or if all such records have a recorded principal that matches that of the current request's principal, then the preparatory phase proceeds as follows.

    • If there is a confirmed client record with a matching client ID string and a non-matching principal, the server checks the current state of the associated lease. If there is no associated state for the lease, or the lease has expired, the server proceeds to the main part of SETCLIENTID.
    • Otherwise, the server is being asked to do a SETCLIENTID for a client by a non-matching principal while there is active state. In this case, the server rejects the SETCLIENTID request returning an NFS4ERR_CLID_INUSE error, since use of a single client with multiple principals is not allowed. Note that even though the previously used clientaddr4 is returned with this error, the use of the same id string with multiple clientaddr4s is not prohibited, while its use with multiple principals is prohibited.
  • まず、DRC内でリクエストを検索します。ヒットした場合は、DRCにキャッシュされている結果を返します。サーバーは、クライアントの状態（ロック、共有、委任）を削除せず（NOT）、クライアント{ x }について記録されたcallbackとcallback_identの情報も変更しません。ここでサーバーはSETCLIENTIDの主要部分に進みます。

  • そうでない場合（つまり、DRCでミスした場合）、サーバーはクライアントID文字列xを取り、以前のSETCLIENTIDの呼び出しからサーバーが記録している可能性のある、xの確認済みのクライアントレコードを探索します。そのようなレコードがない場合、またはそのようなレコードのすべてが、現在のリクエストのプリンシパルと一致するプリンシパルを記録している場合、準備フェーズは次のように進みます。

    • クライアントID文字列が一致し、プリンシパルが一致しない確認済みのクライアントレコードがある場合、サーバーは関連するリースの現在の状態をチェックします。そのリースに関連する状態がない場合、またはリースの期限が切れている場合、サーバーはSETCLIENTIDの主要部分に進みます。
    • そうでない場合、サーバーは、アクティブな状態が存在する間に、一致しないプリンシパルによってクライアントのSETCLIENTIDを行うよう求められていることになります。この場合、単一のクライアントを複数のプリンシパルで使用することは許されないため、サーバーはNFS4ERR_CLID_INUSEエラーを返してSETCLIENTIDリクエストを拒否します。このエラーとともに以前に使用されたclientaddr4が返されますが、同じid文字列を複数のclientaddr4で使用することは禁止されておらず、複数のプリンシパルで使用することが禁止されていることに注意してください。
8.4.5.2. IMPLEMENTATION (Main Phase)
8.4.5.2. 実装（主要フェーズ）

If the SETCLIENTID has not been dealt with by DRC processing, and has not been rejected with an NFS4ERR_CLID_INUSE error, then the main part of SETCLIENTID processing proceeds, as described below.

SETCLIENTIDがDRCの処理によって扱われず、NFS4ERR_CLID_INUSEエラーで拒否されてもいない場合、以下で説明するように、SETCLIENTIDの処理の主要部分に進みます。

  • The server checks if it has recorded a confirmed record for { v, x, c, l, s }, where l may or may not equal k. If so, and since the id verifier v of the request matches that which is confirmed and recorded, the server treats this as a probable callback information update and records an unconfirmed { v, x, c, k, t } and leaves the confirmed { v, x, c, l, s } in place, such that t != s. It does not matter if k equals l or not. Any pre-existing unconfirmed { v, x, c, *, * } is removed.

    The server returns { c, t }. It is indeed returning the old clientid4 value c, because the client apparently only wants to update callback value k to value l. It's possible this request is one from the Byzantine router that has stale callback information, but this is not a problem. The callback information update is only confirmed if followed up by a SETCLIENTID_CONFIRM { c, t }.

    The server awaits confirmation of k via SETCLIENTID_CONFIRM { c, t }.

    The server does NOT remove client (lock/share/delegation) state for x.

  • The server has previously recorded a confirmed { u, x, c, l, s } record such that v != u, l may or may not equal k, and has not recorded any unconfirmed { *, x, *, *, * } record for x. The server records an unconfirmed { v, x, d, k, t } (d != c, t != s).

    The server returns { d, t }.

    The server awaits confirmation of { d, k } via SETCLIENTID_CONFIRM { d, t }.

    The server does NOT remove client (lock/share/delegation) state for x.

  • The server has previously recorded a confirmed { u, x, c, l, s } record such that v != u, l may or may not equal k, and recorded an unconfirmed { w, x, d, m, t } record such that c != d, t != s, m may or may not equal k, m may or may not equal l, and k may or may not equal l. Whether w == v or w != v makes no difference. The server simply removes the unconfirmed { w, x, d, m, t } record and replaces it with an unconfirmed { v, x, e, k, r } record, such that e != d, e != c, r != t, r != s.

    The server returns { e, r }.

    The server awaits confirmation of { e, k } via SETCLIENTID_CONFIRM { e, r }.

    The server does NOT remove client (lock/share/delegation) state for x.

  • The server has no confirmed { *, x, *, *, * } for x. It may or may not have recorded an unconfirmed { u, x, c, l, s }, where l may or may not equal k, and u may or may not equal v. Any unconfirmed record { u, x, c, l, * }, regardless whether u == v or l == k, is replaced with an unconfirmed record { v, x, d, k, t } where d != c, t != s.

    The server returns { d, t }.

    The server awaits confirmation of { d, k } via SETCLIENTID_CONFIRM { d, t }. The server does NOT remove client (lock/share/delegation) state for x.

  • サーバーは、{ v, x, c, l, s }の確認済みのレコードを記録しているかどうかをチェックします。ここで、lはkと等しい場合も等しくない場合もあります。そうであれば、リクエストのidベリファイアーvは確認済みで記録されているものと一致するため、サーバーはこれをコールバック情報の更新の可能性が高いものとして扱い、未確認の{ v, x, c, k, t }を記録し、確認済みの{ v, x, c, l, s }をそのまま残します。ここで、t != sです。kがlと等しいかどうかは関係ありません。既存の未確認の{ v, x, c, *, * }はすべて削除されます。

    サーバーは{ c, t }を返します。クライアントは明らかにコールバックの値kを値lに更新したいだけなので、実際に古いclientid4の値cを返しています。このリクエストが、古いコールバック情報を持つビザンチンルーターからのものである可能性もありますが、これは問題ではありません。コールバック情報の更新は、SETCLIENTID_CONFIRM { c, t }が続いた場合にのみ確認されます。

    サーバーは、SETCLIENTID_CONFIRM { c, t }によるkの確認を待ちます。

    サーバーは、xのクライアント（ロック／共有／委任）の状態を削除しません（NOT）。

  • サーバーは、v != uであり、lがkと等しい場合も等しくない場合もある確認済みの{ u, x, c, l, s }レコードを以前に記録しており、xについて未確認の{ *, x, *, *, * }レコードを何も記録していません。サーバーは未確認の{ v, x, d, k, t }（d != c、t != s）を記録します。

    サーバーは{ d, t }を返します。

    サーバーは、SETCLIENTID_CONFIRM { d, t }による{ d, k }の確認を待ちます。

    サーバーは、xのクライアント（ロック／共有／委任）の状態を削除しません（NOT）。

  • サーバーは、v != uであり、lがkと等しい場合も等しくない場合もある確認済みの{ u, x, c, l, s }レコードを以前に記録しており、さらに、c != d、t != sであり、mがkと等しい場合も等しくない場合もあり、mがlと等しい場合も等しくない場合もあり、kがlと等しい場合も等しくない場合もある未確認の{ w, x, d, m, t }レコードを記録しています。w == vであるかw != vであるかは違いを生じません。サーバーは単に未確認の{ w, x, d, m, t }レコードを削除し、e != d、e != c、r != t、r != sである未確認の{ v, x, e, k, r }レコードで置き換えます。

    サーバーは{ e, r }を返します。

    サーバーは、SETCLIENTID_CONFIRM { e, r }による{ e, k }の確認を待ちます。

    サーバーは、xのクライアント（ロック／共有／委任）の状態を削除しません（NOT）。

  • サーバーは、xについて確認済みの{ *, x, *, *, * }を持っていません。サーバーは、未確認の{ u, x, c, l, s }を記録している場合も記録していない場合もあります。ここで、lはkと等しい場合も等しくない場合もあり、uはvと等しい場合も等しくない場合もあります。未確認のレコード{ u, x, c, l, * }は、u == vであるかl == kであるかにかかわらず、d != c、t != sである未確認のレコード{ v, x, d, k, t }で置き換えられます。

    サーバーは{ d, t }を返します。

    サーバーは、SETCLIENTID_CONFIRM { d, t }による{ d, k }の確認を待ちます。サーバーは、xのクライアント（ロック／共有／委任）の状態を削除しません（NOT）。

The server generates the clientid and setclientid_confirm values and must take care to ensure that these values are extremely unlikely to ever be regenerated.

サーバーはclientidとsetclientid_confirmの値を生成し、これらの値が再生成される可能性が極めて低くなるように注意しなければなりません。

8.5. Security Considerations for Inter-server Information Transfer

8.5. サーバー間の情報転送についてのセキュリティーに関する考慮事項

Although the means by which the source and destination server communicate is not specified by NFSv4.0, the following security-related considerations for inter-server communication should be noted.

移行元サーバーと移行先サーバーが通信する手段はNFSv4.0では規定されていませんが、サーバー間の通信に関するセキュリティー関連の次の考慮事項に注意すべきです。

  • Communication between source and destination servers needs to be carried out in a secure manner, with protection against deliberate modification of data in transit provided by using either a private network or a security mechanism that ensures integrity. In many cases, privacy will also be required, requiring a strengthened security mechanism if a private network is not used.
  • Effective implementation of the file system migration function requires that a trust relationship exist between source and destination servers. The details of that trust relationship depend on the specifics of the inter-server transfer protocol, which is outside the scope of this specification.
  • The source server may communicate to the destination server security-related information in order to allow it to more rigorously validate clients' identity. For example, the destination server might reject a SETCLIENTID done with a different principal or with a different IP address than was done previously by the client on the source server. However, the destination server MUST NOT use this information to allow any operation to be performed by the client that would not be allowed otherwise.
  • 移行元サーバーと移行先サーバーの間の通信は、プライベートネットワークまたは完全性を保証するセキュリティーメカニズムを使用することによって、転送中のデータの意図的な改変から保護された、安全な方法で行う必要があります。多くの場合、プライバシーも必要となり、プライベートネットワークを使用しない場合は、強化されたセキュリティーメカニズムが必要になります。
  • ファイルシステムの移行機能を効果的に実装するには、移行元サーバーと移行先サーバーの間に信頼関係が存在する必要があります。その信頼関係の詳細は、サーバー間の転送プロトコルの詳細に依存しますが、それはこの仕様の範囲外です。
  • 移行元サーバーは、移行先サーバーがクライアントのアイデンティティーをより厳密に検証できるように、セキュリティー関連の情報を移行先サーバーに伝えることがあります。たとえば、移行先サーバーは、クライアントが以前に移行元サーバー上で行ったものとは異なるプリンシパルで、または異なるIPアドレスから行われたSETCLIENTIDを拒否するかもしれません。ただし、移行先サーバーは、この情報を使用して、本来なら許可されないような操作をクライアントが実行することを許可してはなりません（MUST NOT）。

8.6. Security Considerations Revision

8.6. セキュリティーに関する考慮事項の改訂

The penultimate paragraph of Section 19 of [RFC7530] should be revised to read as follows:

[RFC7530]のセクション19の最後から2番目の段落は、次のように改訂すべきです：

Because the operations SETCLIENTID/SETCLIENTID_CONFIRM are responsible for the release of client state, it is imperative that the principal used for these operations be checked against and match the previous use of these operations. In addition, use of integrity protection is desirable on the SETCLIENTID operation, to prevent an attack whereby a change in the boot instance id (verifier) forces an undesired loss of client state. See Section 5 for further discussion.

SETCLIENTID/SETCLIENTID_CONFIRM操作はクライアントの状態の解放に責任を持つため、これらの操作に使用されるプリンシパルを、これらの操作の以前の使用と照合し、一致させることが不可欠です。さらに、ブートインスタンスID（verifier）の変更によって望まないクライアントの状態の喪失が強制される攻撃を防ぐために、SETCLIENTID操作では完全性保護を使用することが望ましいです。さらなる議論についてはセクション5を参照してください。

9. セキュリティーに関する考慮事項

[RFC7530]のセキュリティーに関する考慮事項は、この文書のセクション8.6で規定する最後から2番目の段落の修正と、セクション8.5の内容の追加を除いて、引き続き適切です。
