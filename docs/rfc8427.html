RFC 8427

Representing DNS Messages in JSON

RFC 8427

DNSメッセージのJSONによる表現

Abstract

概要

Some applications use DNS messages, or parts of DNS messages, as data. For example, a system that captures DNS queries and responses might want to be able to easily search them without having to decode the messages each time. Another example is a system that puts together DNS queries and responses from message parts. This document describes a general format for DNS message data in JSON. Specific profiles of the format in this document can be described in other documents for specific applications and usage scenarios.

一部のアプリケーションは、DNSメッセージやDNSメッセージの一部をデータとして使用します。たとえば、DNSのクエリーとレスポンスを収集するシステムは、メッセージを毎回デコードしなくても、それらを簡単に検索できるようにしたいと考えるかもしれません。別の例としては、メッセージの部品からDNSのクエリーとレスポンスを組み立てるシステムがあります。この文書は、DNSメッセージのデータをJSONで表現するための汎用的な形式を記述します。この文書の形式の特定のプロファイルは、特定のアプリケーションや利用シナリオ向けに、別の文書で記述できます。

1. Introduction

1. はじめに

The DNS message format is defined in [RFC1035]. DNS queries and DNS responses have exactly the same structure. Many of the field names and data type names given in [RFC1035] are commonly used in discussions of DNS. For example, it is common to hear things like "the query had a QNAME of 'example.com'" or "the RDATA has a simple structure".

DNSメッセージの形式は[RFC1035]で定義されています。DNSクエリーとDNSレスポンスはまったく同じ構造を持ちます。[RFC1035]で示されているフィールド名やデータ型名の多くは、DNSに関する議論でよく使われます。たとえば、「the query had a QNAME of 'example.com'（そのクエリーのQNAMEは「example.com」だった）」や「the RDATA has a simple structure（そのRDATAは単純な構造をしている）」といった表現をよく耳にします。

There are hundreds of data-interchange formats for serializing structured data. Currently, JSON [RFC8259] is quite popular for many types of data, particularly data that has named subfields and optional parts.

構造化データをシリアル化するためのデータ交換形式は何百もあります。現在、JSON [RFC8259]は多くの種類のデータ、特に名前付きのサブフィールドや省略可能な部分を持つデータで非常に広く使われています。

This document uses JSON to describe DNS messages. It also defines how to describe a paired DNS query and response and how to stream DNS objects.

この文書は、JSONを使用してDNSメッセージを記述します。また、DNSクエリーとレスポンスの組を記述する方法と、DNSオブジェクトをストリーミングする方法も定義します。

1.1. Design of the Format

1.1. 形式の設計

There are many ways to design a data format. This document uses a specific design methodology based on the DNS format.

データ形式を設計する方法はたくさんあります。この文書は、DNSの形式に基づいた特定の設計方針を採用しています。

  • The format is based on JSON objects in order to allow a writer to include or exclude parts of the format at will. No object members are ever required.
  • This format is purposely overly general. A protocol or application that uses this format is expected to use only a subset of the items defined here; it is expected to define its own profile from this format.
  • The format allows transformation through JSON that would permit re-creation of the wire content of the message.
  • All members whose values are always 16 bits or shorter are represented by JSON numbers with no minus sign, no fractional part (except in fields that are specifically noted below), and no exponent part. One-bit values are represented as JSON numbers whose values are either 0 or 1. See Section 6 of [RFC8259] for more detail on JSON numbers.
  • The JSON representation of the objects described in this document is limited to the UTF-8 codepoints from U+0000 to U+007F. This is done to prevent an attempt to use a different encoding such as UTF-8 for octets in names or data.
  • Items that have string values can have "HEX" appended to their names to indicate a non-ASCII encoding of the value. Names that end in "HEX" have values stored in base16 encoding (hex with uppercase letters) defined in [RFC4648]. This is particularly useful for RDATA that is binary.
  • All field names in this format are used as in [RFC1035], including their capitalization. Names not defined in [RFC1035] generally use "camel case".
  • The same data may be represented in multiple object members multiple times. For example, there is a member for the octets of the DNS message header, and there are members for each named part of the header. A message object can thus inadvertently have inconsistent data, such as a header member whose value does not match the value of the first bits in the entire message member.
  • It is acceptable that there are multiple ways to represent the same data. This is done so that application designers can choose what fields are best for them and even so that they are able to allow multiple representations. That is, there is no "better" way to represent DNS data, so this design doesn't prefer specific representations.

  • The design explicitly allows for the description of malformed DNS messages. This is important for systems that are logging messages seen on the wire, particularly messages that might be used as part of an attack. A few examples of malformed DNS messages include:

    • a resource record (RR) that has an RDLENGTH of 4 but an RDATA whose length is longer than 4 (if it is the last RR in a message)
    • a DNS message whose QDCOUNT is 0
    • a DNS message whose ANCOUNT is large but there are insufficient bytes after the header
    • a DNS message whose length is less than 12 octets, meaning it doesn't even have a full header
  • An object in this format can have zero or more of the members defined here; that is, no members are required by the format itself. Instead, profiles that use this format might have requirements for mandatory members, optional members, and prohibited members from the format. Also, this format does not prohibit members that are not defined in this format; profiles of the format are free to add new members in the profile.
  • This document defines DNS messages, not the zone files described in [RFC1035]. A different specification could be written to extend it to represent zone files. Note that DNS zone files allow escaping of octet values using "\DDD" notation, but this specification does not allow that; when encoding from a zone file to this JSON format, you need to do a conversion for many types of values.
  • 書き手が形式の一部を自由に含めたり除外したりできるように、この形式はJSONオブジェクトに基づいています。オブジェクトのメンバーが必須となることはありません。
  • この形式は、意図的に過度に汎用的にしています。この形式を使用するプロトコルやアプリケーションは、ここで定義する項目のサブセットだけを使用することが想定されています。つまり、この形式から独自のプロファイルを定義することが想定されています。
  • この形式では、JSONを介した変換によって、メッセージのワイヤー上の内容を再現できます。
  • 値が常に16ビット以下であるメンバーはすべて、マイナス記号、小数部（以下で特に明記するフィールドを除く）、指数部のいずれも持たないJSONの数値で表現します。1ビットの値は、値が0または1のJSONの数値で表現します。JSONの数値の詳細については、[RFC8259]のセクション6を参照してください。
  • この文書で説明するオブジェクトのJSON表現は、U+0000からU+007FまでのUTF-8コードポイントに限定されます。これは、名前やデータのオクテットにUTF-8などの別のエンコーディングを使用しようとするのを防ぐためです。
  • 文字列値を持つ項目は、名前に「HEX」を付加して、値が非ASCIIのエンコーディングであることを示せます。名前が「HEX」で終わる項目の値は、[RFC4648]で定義されているbase16エンコーディング（大文字を使った16進数）で格納されます。これは、バイナリーであるRDATAに特に有用です。
  • この形式のフィールド名はすべて、大文字小文字の区別も含めて[RFC1035]のとおりに使用します。[RFC1035]で定義されていない名前には、一般に「キャメルケース」を使用します。
  • 同じデータが、複数のオブジェクトメンバーで複数回表現されることがあります。たとえば、DNSメッセージヘッダーのオクテットを表すメンバーがあり、さらにヘッダーの名前付きの各部分を表すメンバーもあります。そのため、メッセージオブジェクトは、メッセージ全体を表すメンバーの先頭ビットの値と一致しない値を持つヘッダーメンバーのように、意図せず矛盾したデータを持つことがあります。
  • 同じデータを表現する方法が複数あることは許容されます。これは、アプリケーション設計者が自分にとって最適なフィールドを選べるようにするためであり、さらには複数の表現を許容できるようにするためです。つまり、DNSデータを表現する「より良い」方法というものはないので、この設計では特定の表現を優先しません。

  • この設計では、不正な形式のDNSメッセージを記述することを明示的に許容しています。これは、ワイヤー上で観測されたメッセージ、特に攻撃の一部として使われる可能性のあるメッセージをログに記録するシステムにとって重要です。不正な形式のDNSメッセージの例をいくつか挙げます。

    • RDLENGTHが4であるのに、RDATAの長さが4より長いリソースレコード（RR）（それがメッセージの最後のRRである場合）
    • QDCOUNTが0のDNSメッセージ
    • ANCOUNTが大きいのに、ヘッダーの後に十分なバイトがないDNSメッセージ
    • 長さが12オクテット未満、つまり完全なヘッダーすら持たないDNSメッセージ
  • この形式のオブジェクトは、ここで定義するメンバーを0個以上持つことができます。つまり、形式自体が必須とするメンバーはありません。その代わりに、この形式を使用するプロファイルは、この形式のメンバーのうち、必須のメンバー、省略可能なメンバー、禁止するメンバーについての要件を持つことがあります。また、この形式は、この形式で定義されていないメンバーを禁止しません。この形式のプロファイルは、プロファイル内で新しいメンバーを自由に追加できます。
  • この文書はDNSメッセージを定義するものであり、[RFC1035]で説明されているゾーンファイルを定義するものではありません。ゾーンファイルを表現できるように拡張する別の仕様を書くことは可能です。DNSゾーンファイルでは「\DDD」表記を使ってオクテット値をエスケープできますが、この仕様ではそれを許可しないことに注意してください。ゾーンファイルからこのJSON形式にエンコードする際には、多くの種類の値について変換を行う必要があります。

1.2. Terminology

1.2. 用語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

2. JSON Format for DNS Messages

2. DNSメッセージのJSON形式

The following gives all of the members defined for a DNS message. It is organized approximately by levels of the DNS message.

以下に、DNSメッセージについて定義されるすべてのメンバーを示します。おおむねDNSメッセージの階層ごとに整理しています。

2.1. Message Object Members

2.1. メッセージオブジェクトのメンバー

  • ID - Integer whose value is 0 to 65535
  • QR - Boolean
  • Opcode - Integer whose value is 0 to 15
  • AA - Boolean
  • TC - Boolean
  • RD - Boolean
  • RA - Boolean
  • AD - Boolean
  • CD - Boolean
  • RCODE - Integer whose value is 0 to 15
  • QDCOUNT - Integer whose value is 0 to 65535
  • ANCOUNT - Integer whose value is 0 to 65535
  • NSCOUNT - Integer whose value is 0 to 65535
  • ARCOUNT - Integer whose value is 0 to 65535
  • QNAME - String of the name of the first Question section of the message; see Section 2.6 for a description of the contents
  • compressedQNAME - Object that describes the name with two optional values: "isCompressed" (with a value of 0 for no and 1 for yes) and "length" (with an integer giving the length in the message)
  • QTYPE - Integer whose value is 0 to 65535, of the QTYPE of the first Question section of the message
  • QTYPEname - String whose value is from the IANA "Resource Record (RR) TYPEs" registry or has the format in [RFC3597]; this is case sensitive, so "AAAA", not "aaaa"
  • QCLASS - Integer whose value is 0 to 65535, of the QCLASS of the first Question section of the message
  • QCLASSname - String whose value is "IN", "CH", or "HS" or that has the format in [RFC3597]
  • questionRRs - Array of zero or more resource records or rrSet objects in the Question section
  • answerRRs - Array of zero or more resource records or rrSet objects in the Answer section
  • authorityRRs - Array of zero or more resource records or rrSet objects in the Authority section
  • additionalRRs - Array of zero or more resource records or rrSet objects in the Additional section
  • ID - 値が0から65535の整数
  • QR - ブール値
  • Opcode - 値が0から15の整数
  • AA - ブール値
  • TC - ブール値
  • RD - ブール値
  • RA - ブール値
  • AD - ブール値
  • CD - ブール値
  • RCODE - 値が0から15の整数
  • QDCOUNT - 値が0から65535の整数
  • ANCOUNT - 値が0から65535の整数
  • NSCOUNT - 値が0から65535の整数
  • ARCOUNT - 値が0から65535の整数
  • QNAME - メッセージの最初のQuestionセクションの名前を表す文字列。内容の説明はセクション2.6を参照してください。
  • compressedQNAME - 名前を記述するオブジェクトで、省略可能な2つの値「isCompressed」（いいえなら0、はいなら1）と「length」（メッセージ内での長さを示す整数）を持ちます。
  • QTYPE - メッセージの最初のQuestionセクションのQTYPEを表す、値が0から65535の整数
  • QTYPEname - 値がIANAの「Resource Record (RR) TYPEs」レジストリーに由来するか、[RFC3597]の形式を持つ文字列。大文字と小文字を区別するので、「aaaa」ではなく「AAAA」とします。
  • QCLASS - メッセージの最初のQuestionセクションのQCLASSを表す、値が0から65535の整数
  • QCLASSname - 値が「IN」、「CH」、「HS」のいずれかであるか、[RFC3597]の形式を持つ文字列
  • questionRRs - Questionセクションにある0個以上のリソースレコードまたはrrSetオブジェクトの配列
  • answerRRs - Answerセクションにある0個以上のリソースレコードまたはrrSetオブジェクトの配列
  • authorityRRs - Authorityセクションにある0個以上のリソースレコードまたはrrSetオブジェクトの配列
  • additionalRRs - Additionalセクションにある0個以上のリソースレコードまたはrrSetオブジェクトの配列

2.2. Resource Record Object Members

2.2. リソースレコードオブジェクトのメンバー

A resource record is represented as an object with the following members.

リソースレコードは、次のメンバーを持つオブジェクトとして表現します。

  • NAME - String of the NAME field of the resource record; see Section 2.6 for a description of the contents
  • compressedNAME - Object that describes the name with two optional values: "isCompressed" (with a value of 0 for no and 1 for yes) and "length" (with an integer giving the length in the message)
  • TYPE - Integer whose value is 0 to 65535
  • TYPEname - String whose value is from the IANA "Resource Record (RR) TYPEs" registry or has the format in [RFC3597]; this is case sensitive, so "AAAA", not "aaaa"
  • CLASS - Integer whose value is 0 to 65535
  • CLASSname - String whose value is "IN", "CH", or "HS" or has the format in [RFC3597]
  • TTL - Integer whose value is -2147483648 to 2147483647 (it will only be 0 to 2147483647 in normal circumstances)
  • RDLENGTH - Integer whose value is 0 to 65535. Applications using this format are unlikely to use this value directly, and instead calculate the value from the RDATA.
  • RDATAHEX - Hex-encoded string (base16 encoding, described in [RFC4648]) of the octets of the RDATA field of the resource record. The data in some common RDATA fields are also described in their own members; see Section 2.3
  • rrSet - List of objects that have RDLENGTH and RDATA members
  • NAME - リソースレコードのNAMEフィールドを表す文字列。内容の説明はセクション2.6を参照してください。
  • compressedNAME - 名前を記述するオブジェクトで、省略可能な2つの値「isCompressed」（いいえなら0、はいなら1）と「length」（メッセージ内での長さを示す整数）を持ちます。
  • TYPE - 値が0から65535の整数
  • TYPEname - 値がIANAの「Resource Record (RR) TYPEs」レジストリーに由来するか、[RFC3597]の形式を持つ文字列。大文字と小文字を区別するので、「aaaa」ではなく「AAAA」とします。
  • CLASS - 値が0から65535の整数
  • CLASSname - 値が「IN」、「CH」、「HS」のいずれかであるか、[RFC3597]の形式を持つ文字列
  • TTL - 値が-2147483648から2147483647の整数（通常の状況では0から2147483647にしかなりません）
  • RDLENGTH - 値が0から65535の整数。この形式を使用するアプリケーションがこの値を直接使用することはまれで、代わりにRDATAから値を計算します。
  • RDATAHEX - リソースレコードのRDATAフィールドのオクテットを16進エンコードした文字列（[RFC4648]で説明されているbase16エンコーディング）。一般的なRDATAフィールドのいくつかについては、そのデータがそれぞれ専用のメンバーでも記述されます。セクション2.3を参照してください。
  • rrSet - RDLENGTHメンバーとRDATAメンバーを持つオブジェクトのリスト

A Question section can be expressed as a resource record. When doing so, the TTL, RDLENGTH, and RDATA members make no sense.

Questionセクションはリソースレコードとして表現できます。その場合、TTL、RDLENGTH、RDATAの各メンバーは意味を持ちません。

2.3. Specific RDATA Field Members

2.3. 特定のRDATAフィールドのメンバー

The following are common RDATA types and how to specify them as JSON members. The name of the member contains the name of the RDATA type. The data type for each of these members is a string. Each name is prefaced with "rdata" to prevent a name collision with fields that might later be defined that have the same name as the raw type name.

以下は、一般的なRDATAの型と、それらをJSONのメンバーとして指定する方法です。メンバーの名前にはRDATAの型の名前が含まれます。これらの各メンバーのデータ型は文字列です。将来、生の型名と同じ名前を持つフィールドが定義された場合の名前の衝突を防ぐために、各名前には「rdata」が前置されます。

  • rdataA - IPv4 address, such as "192.168.33.44"
  • rdataAAAA - IPv6 address, such as "fe80::a65e:60ff:fed6:8aaf", as defined in [RFC5952]
  • rdataCNAME - A domain name
  • rdataDNAME - A domain name
  • rdataNS - A domain name
  • rdataPTR - A domain name
  • rdataTXT - A text value
  • rdataA - 「192.168.33.44」のようなIPv4アドレス
  • rdataAAAA - [RFC5952]で定義されている、「fe80::a65e:60ff:fed6:8aaf」のようなIPv6アドレス
  • rdataCNAME - ドメイン名
  • rdataDNAME - ドメイン名
  • rdataNS - ドメイン名
  • rdataPTR - ドメイン名
  • rdataTXT - テキスト値

In addition, each of the following members has a value that is a space-separated string that matches the display format definition in the RFC that defines that RDATA type. It is not expected that every receiving application will know how to parse these values.

さらに、次の各メンバーは、そのRDATAの型を定義するRFCにある表示形式の定義に合致する、空白区切りの文字列を値として持ちます。受信するすべてのアプリケーションが、これらの値の解析方法を知っていることは想定されていません。

rdataCDNSKEY, rdataCDS, rdataCSYNC, rdataDNSKEY, rdataHIP, rdataIPSECKEY, rdataKEY, rdataMX, rdataNSEC, rdataNSEC3, rdataNSEC3PARAM, rdataOPENPGPKEY, rdataRRSIG, rdataSMIMEA, rdataSPF, rdataSRV, rdataSSHFP, rdataTLSA

rdataCDNSKEY, rdataCDS, rdataCSYNC, rdataDNSKEY, rdataHIP, rdataIPSECKEY, rdataKEY, rdataMX, rdataNSEC, rdataNSEC3, rdataNSEC3PARAM, rdataOPENPGPKEY, rdataRRSIG, rdataSMIMEA, rdataSPF, rdataSRV, rdataSSHFP, rdataTLSA

2.4. The Message and Its Parts as Octets

2.4. オクテットとしてのメッセージとその部分

The following can be members of a message object. These members are all encoded in base16 encoding, described in [RFC4648]. All these items are strings.

以下は、メッセージオブジェクトのメンバーになりえます。これらのメンバーはすべて、[RFC4648]で説明されているbase16エンコーディングでエンコードされます。これらの項目はすべて文字列です。

  • messageOctetsHEX - The octets of the message
  • headerOctetsHEX - The first 12 octets of the message (or fewer, if the message is truncated)
  • questionOctetsHEX - The octets of the Question section
  • answerOctetsHEX - The octets of the Answer section
  • authorityOctetsHEX - The octets of the Authority section
  • additionalOctetsHEX - The octets of the Additional section
  • messageOctetsHEX - メッセージのオクテット
  • headerOctetsHEX - メッセージの先頭12オクテット（メッセージが切り詰められている場合はそれより少ないこともあります）
  • questionOctetsHEX - Questionセクションのオクテット
  • answerOctetsHEX - Answerセクションのオクテット
  • authorityOctetsHEX - Authorityセクションのオクテット
  • additionalOctetsHEX - Additionalセクションのオクテット

The following can be a member of a resource record object.

以下は、リソースレコードオブジェクトのメンバーになりえます。

  • rrOctetsHEX - The octets of a particular resource record
  • rrOctetsHEX - 特定のリソースレコードのオクテット

The items in this section are useful in applications to canonically reproduce what appeared on the wire. For example, an application that is converting wire-format requests and responses might do decompression of names, but the system reading the converted data may want to be sure the decompression was done correctly. Such a system would need to see the part of the message where the decompressed labels resided, such as in one of the items in this section.

このセクションの項目は、ワイヤー上に現れたものをアプリケーションで正規に再現するのに役立ちます。たとえば、ワイヤー形式のリクエストとレスポンスを変換するアプリケーションは名前の展開（圧縮の解除）を行うことがありますが、変換されたデータを読み取るシステムは、展開が正しく行われたことを確認したい場合があります。そのようなシステムは、展開されたラベルがあったメッセージの部分を、このセクションの項目のいずれかなどで確認する必要があります。

2.5. Additional Message Object Members

2.5. メッセージオブジェクトの追加のメンバー

The following are members that might appear in a message object:

以下は、メッセージオブジェクトに現れる可能性のあるメンバーです。

  • dateString - The date that the message was sent or received, given as a string in the standard format described in [RFC3339] and refined by Section 3.3 of [RFC4287].
  • dateSeconds - The date that the message was sent or received, given as a JSON number that is the number of seconds since 1970-01-01T00:00Z in UTC time; this number can be fractional. This number must have no minus sign, can have an optional fractional part, and can have no exponent part.
  • comment - An unstructured comment as a string.
  • dateString - メッセージが送信または受信された日時。[RFC3339]で説明され、[RFC4287]のセクション3.3で詳細化された標準形式の文字列で表します。
  • dateSeconds - メッセージが送信または受信された日時。UTCで1970-01-01T00:00Zからの秒数を表すJSONの数値で表します。この数値は小数でもかまいません。この数値はマイナス記号を持たず、省略可能な小数部を持つことができ、指数部を持つことはできません。
  • comment - 文字列で表した、構造を持たないコメント

2.6. Name Fields

2.6. 名前フィールド

Names are represented by JSON strings. The rules for how names are encoded are described in Section 1.1. (To recap: it is limited to the UTF-8 codepoints from U+0000 to U+007F.) The contents of these fields are always uncompressed; that is, after [RFC1035], name compression has been removed.

名前はJSONの文字列で表現します。名前をエンコードする方法の規則はセクション1.1で説明しています（要約すると、U+0000からU+007FまでのUTF-8コードポイントに限定されます）。これらのフィールドの内容は常に圧縮されていません。つまり、[RFC1035]の名前圧縮は解除されています。

There are two encodings for names:

名前のエンコーディングには次の2つがあります。

  • If the member name does not end in "HEX", the value is a domain name encoded as DNS labels consisting of UTF-8 codepoints from U+0000 to U+007F. Within a label, codepoints above U+007F and the codepoint U+002E (ASCII period) MUST be expressed using JSON's escaping rules within this set of codepoints. Separation between labels is indicated with a period (codepoint U+002E). Internationalized Domain Name (IDN) labels are always expressed in their A-label form, as described in [RFC5890].
  • If the member name ends in "HEX", the value is the wire format for an entire domain name stored in base16 encoding, which is described in [RFC4648].
  • メンバー名が「HEX」で終わらない場合、値は、U+0000からU+007FまでのUTF-8コードポイントからなるDNSラベルとしてエンコードされたドメイン名です。ラベル内では、U+007Fより大きいコードポイントとコードポイントU+002E（ASCIIのピリオド）は、このコードポイントの範囲内でJSONのエスケープ規則を使って表現しなければなりません（MUST）。ラベル間の区切りはピリオド（コードポイントU+002E）で示します。国際化ドメイン名（IDN）のラベルは、[RFC5890]で説明されているように、常にAラベル形式で表現します。
  • メンバー名が「HEX」で終わる場合、値は、ドメイン名全体のワイヤー形式を[RFC4648]で説明されているbase16エンコーディングで格納したものです。

3. JSON Format for a Paired DNS Query and Response

3. DNSクエリーとレスポンスの組のJSON形式

A paired DNS query and response is represented as an object. Two optional members of this object are named "queryMessage" and "responseMessage", and each has a value that is a message object. This design was chosen (as compared to the more obvious array of two values) so that a paired DNS query and response could be differentiated from a stream of DNS messages whose length happens to be two.

DNSクエリーとレスポンスの組は、オブジェクトとして表現します。このオブジェクトの省略可能な2つのメンバーは「queryMessage」と「responseMessage」という名前で、それぞれの値はメッセージオブジェクトです。（より自然に思える2つの値の配列と比べて）この設計が選ばれたのは、DNSクエリーとレスポンスの組を、たまたま長さが2であるDNSメッセージのストリームと区別できるようにするためです。

4. Streaming DNS Objects

4. DNSオブジェクトのストリーミング

Streaming of DNS objects is performed using JSON text sequences [RFC7464].

DNSオブジェクトのストリーミングは、JSONテキストシーケンス[RFC7464]を使用して行います。

6. Local Format Policy

6. ローカルな形式のポリシー

Systems using the format in this document will likely have policy about what must be in the objects. Those policies are outside the scope of this document.

この文書の形式を使用するシステムは、オブジェクトに何を含めなければならないかについてのポリシーを持つことになるでしょう。そうしたポリシーはこの文書の範囲外です。

For example, passive DNS systems such as those described in [PASSIVE-DNS] cover just DNS responses. Such a system might have a policy that makes QNAME, QTYPE, and answerRRs mandatory. That document also describes two mandatory times that are not in this format, so the policy would possibly also define those members and make them mandatory. The policy could also define additional members that might appear in a record.

たとえば、[PASSIVE-DNS]で説明されているようなパッシブDNSシステムは、DNSレスポンスだけを対象とします。そのようなシステムは、QNAME、QTYPE、answerRRsを必須とするポリシーを持つかもしれません。その文書では、この形式にはない2つの必須の時刻も記述しているので、ポリシーでそれらのメンバーも定義して必須とすることもありえます。ポリシーでは、レコードに現れうる追加のメンバーを定義することもできます。

As another example, a program that uses this format for configuring what a test client sends on the wire might have a policy of "each record object can have as few members as it wants; all unstated members are filled in from previous records".

別の例として、テストクライアントがワイヤー上に送信する内容を設定するためにこの形式を使用するプログラムは、「各レコードオブジェクトは必要なだけ少ないメンバーを持つことができ、記述されていないメンバーはすべて前のレコードから補完される」というポリシーを持つかもしれません。

8. Security Considerations

8. セキュリティーに関する考慮事項

As described in Section 1.1, a message object can have inconsistent data, such as a message with an ANCOUNT of 1 but that has either an empty answerRRs array or an answerRRs array that has two or more RRs. Other examples of inconsistent data would be resource records whose RDLENGTH does not match the length of the decoded value in the RDATAHEX member, a record whose various header fields do not match the value in headerOctetsHEX, and so on. A reader of this format must never assume that all of the data in an object are all consistent with each other.

セクション1.1で説明したように、メッセージオブジェクトは矛盾したデータを持つことがあります。たとえば、ANCOUNTが1であるのに、answerRRs配列が空であったり、answerRRs配列に2つ以上のRRがあったりするメッセージです。矛盾したデータのほかの例としては、RDLENGTHがRDATAHEXメンバーのデコードした値の長さと一致しないリソースレコードや、さまざまなヘッダーフィールドがheaderOctetsHEXの値と一致しないレコードなどがあります。この形式の読み手は、オブジェクト内のデータがすべて互いに整合していると決して仮定してはいけません。

This document describes a format, not a profile of that format. Lack of profile can lead to security issues. For example, if a system has a filter for JSON representations of DNS packets, that filter needs to have the same semantics for the output JSON as the consumer has. Unless the profile is quite tight, this can lead to the producer being able to create fields with different contents (using the HEX and regular formats), fields with malformed lengths, and so on.

この文書は形式を記述するものであり、その形式のプロファイルを記述するものではありません。プロファイルがないことはセキュリティー上の問題につながる可能性があります。たとえば、システムがDNSパケットのJSON表現に対するフィルターを持っている場合、そのフィルターは出力されるJSONについて、消費者と同じセマンティクスを持つ必要があります。プロファイルが十分に厳密でない限り、生成者が（HEX形式と通常の形式を使って）異なる内容を持つフィールドや、不正な長さを持つフィールドなどを作成できてしまう可能性があります。

Numbers in JSON do not have any bounds checking. Thus, integer values in a record might have invalid values, such as an ID field whose value is greater than or equal to 2^16, a QR field that has a value of 2, and so on.

JSONの数値には境界チェックがまったくありません。そのため、レコード内の整数値は、値が2^16以上のIDフィールドや、値が2のQRフィールドなどのように、無効な値を持つ可能性があります。

9. Privacy Considerations

9. プライバシーに関する考慮事項

The values that can be contained in this format may contain privacy-sensitive information. For example, a profile of this format that is used for logging queries sent to recursive resolvers might have source IP addresses that could identify the location of the person who sent the DNS query.

この形式に含めることのできる値には、プライバシー上の機微な情報が含まれる可能性があります。たとえば、再帰リゾルバーに送信されたクエリーをログに記録するために使われるこの形式のプロファイルでは、DNSクエリーを送信した人の所在地を特定しうる送信元IPアドレスが含まれる可能性があります。
