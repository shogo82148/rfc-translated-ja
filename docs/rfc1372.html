RFC 1372

Telnet Remote Flow Control Option

RFC 1372

Telnetのリモートフロー制御オプション

Status of This Memo

このメモのステータス

This RFC specifies an IAB standards track protocol for the Internet community, and requests discussion and suggestions for improvements. Please refer to the current edition of the "IAB Official Protocol Standards" for the standardization state and status of this protocol. Distribution of this memo is unlimited.

このRFCは、インターネットコミュニティーのためのIAB標準化過程のプロトコルを規定し、改善のための議論と提案を求めるものです。このプロトコルの標準化の状態とステータスについては、「IAB Official Protocol Standards」の最新版を参照してください。このメモの配布は無制限です。

Introduction

はじめに

This document specifies an extended version of the Telnet Remote Flow Control Option, RFC 1080, with the addition of the RESTART-ANY and RESTART-XON suboptions.

この文書は、Telnetのリモートフロー制御オプション（RFC 1080）にRESTART-ANYとRESTART-XONのサブオプションを追加した拡張版を規定します。

1. Command Names and Codes

1. コマンド名とコード 

TOGGLE-FLOW-CONTROL   33
    OFF                    0
    ON                     1
    RESTART-ANY            2
    RESTART-XON            3

TOGGLE-FLOW-CONTROL   33
    OFF                    0
    ON                     1
    RESTART-ANY            2
    RESTART-XON            3

2. Command Meanings

2. コマンドの意味

IAC WILL TOGGLE-FLOW-CONTROL
Sender is willing to enable and disable flow control upon command.
IAC WONT TOGGLE-FLOW-CONTROL
Sender refuses to enable and disable flow control. Nothing is implied about whether sender does or does not use flow control. It is simply unwilling to enable and disable it using this protocol.
IAC DO TOGGLE-FLOW-CONTROL
Sender is willing to send commands to enable and disable flow control.
IAC DONT TOGGLE-FLOW-CONTROL
Sender refuses to send command to enable and disable flow control.
IAC SB TOGGLE-FLOW-CONTROL OFF IAC SE
Sender requests receiver to disable flow control.
IAC SB TOGGLE-FLOW-CONTROL ON IAC SE
Sender requests receiver to enable flow control.
IAC SB TOGGLE-FLOW-CONTROL RESTART-ANY IAC SE
Sender requests that when flow control is enabled, the receiver allow any character (except another XOFF) to restart output.
IAC SB TOGGLE-FLOW-CONTROL RESTART-XON IAC SE
Sender requests that when flow control is enabled, the receiver allows only the XON character to restart output.
IAC WILL TOGGLE-FLOW-CONTROL
送信者は、コマンドに応じてフロー制御を有効化・無効化する意思があります。
IAC WONT TOGGLE-FLOW-CONTROL
送信者は、フロー制御の有効化・無効化を拒否します。送信者がフロー制御を使用するかどうかについては何も示しません。単に、このプロトコルを使ってフロー制御を有効化・無効化する意思がないということです。
IAC DO TOGGLE-FLOW-CONTROL
送信者は、フロー制御を有効化・無効化するコマンドを送信する意思があります。
IAC DONT TOGGLE-FLOW-CONTROL
送信者は、フロー制御を有効化・無効化するコマンドの送信を拒否します。
IAC SB TOGGLE-FLOW-CONTROL OFF IAC SE
送信者は、受信者にフロー制御を無効にするよう要求します。
IAC SB TOGGLE-FLOW-CONTROL ON IAC SE
送信者は、受信者にフロー制御を有効にするよう要求します。
IAC SB TOGGLE-FLOW-CONTROL RESTART-ANY IAC SE
送信者は、フロー制御が有効なときに、受信者が任意の文字（ただし、別のXOFFを除く）で出力を再開できるようにすることを要求します。
IAC SB TOGGLE-FLOW-CONTROL RESTART-XON IAC SE
送信者は、フロー制御が有効なときに、受信者がXON文字でのみ出力を再開できるようにすることを要求します。

3. Default Specification

3. デフォルトの指定

The default specification for this option is

このオプションのデフォルトの指定は次のとおりです。

   WONT TOGGLE-FLOW-CONTROL DONT TOGGLE-FLOW-CONTROL

   WONT TOGGLE-FLOW-CONTROL DONT TOGGLE-FLOW-CONTROL

meaning flow control information will not be exchanged in either direction.

これは、フロー制御の情報がどちらの方向にも交換されないことを意味します。

4. Motivation

4. 動機

This memo describes a method of remotely toggling flow control between a user telnet process and the attached terminal. Only flow control of data being transmitted from the telnet process to the terminal is considered. Many systems will also allow flow control of data from the terminal to the telnet process, however there is seldom need to change this behavior repeatedly during the session.

このメモは、ユーザーtelnetプロセスと、それに接続された端末との間のフロー制御を、リモートから切り替える方法を説明します。対象とするのは、telnetプロセスから端末へ送信されるデータのフロー制御だけです。多くのシステムでは、端末からtelnetプロセスへのデータのフロー制御もできますが、この動作をセッション中に何度も変更する必要はめったにありません。

There are two common ways of doing flow control: hardware and software. Hardware flow control uses signals on wires dedicated for this purpose. Software flow control uses one or two specific characters sent along the same path as normal input data. Most commonly, XOFF (control-S) and XON (control-Q) are used to stop and start output, respectively. The option described herein is useful primarily where software flow control is being used. (Since hardware flow control does not preempt any characters, there is normally no need to disable it.) It should also be noted that flow control can either be generated automatically by the terminal when its buffers are close to overflowing, or manually by the user, when he/she cannot read the information as fast as it is being displayed, and unread information will start scrolling off the screen.

フロー制御の一般的な方法には、ハードウェアとソフトウェアの2つがあります。ハードウェアフロー制御は、この目的専用の線の信号を使用します。ソフトウェアフロー制御は、通常の入力データと同じ経路で送られる1つまたは2つの特定の文字を使用します。最も一般的には、出力の停止と開始にそれぞれXOFF（control-S）とXON（control-Q）が使われます。ここで説明するオプションは、主にソフトウェアフロー制御を使用している場合に役立ちます。（ハードウェアフロー制御はどの文字も横取りしないので、通常はそれを無効にする必要はありません。）また、フロー制御は、バッファーがあふれそうになったときに端末によって自動的に生成されることもあれば、表示される速さに情報の読み取りが追いつかず、未読の情報が画面外にスクロールし始めたときにユーザーによって手動で生成されることもある点にも注意してください。

The primary difficulty with software flow control is that it preempts one or two characters. Host software often requires the user to be able to input every possible ASCII character. (Certain editors are notorious for having XOFF and XON as commonly-used commands.) For this reason, operating systems often allow programs to disable flow control. While it is disabled, the characters that normally signal flow control may be read as normal input. In a telnet environment, flow control is normally done by the user telnet process, not by the host computer. In addition, many operating systems, when flow control is enabled, the user may specify whether the XOFF character is the only character that is allowed to re-enable the output of data, or whether any typed character should re-enable the flow of data. Thus this RFC defines a way to propagate flow control status from the host computer to the user telnet process.

ソフトウェアフロー制御の主な難点は、1つまたは2つの文字を横取りしてしまうことです。ホストのソフトウェアでは、ユーザーがあらゆるASCII文字を入力できる必要があることがよくあります。（ある種のエディターは、XOFFとXONをよく使うコマンドにしていることで悪名高いです。）このため、オペレーティングシステムでは、プログラムがフロー制御を無効にできることがよくあります。フロー制御が無効になっている間、通常はフロー制御の合図となる文字を通常の入力として読み取れます。telnet環境では、フロー制御は通常、ホストコンピューターではなくユーザーtelnetプロセスが行います。さらに、多くのオペレーティングシステムでは、フロー制御が有効なとき、データの出力を再開できる文字をXOFF文字だけにするか、入力された任意の文字でデータの流れを再開するかをユーザーが指定できます。そこで、このRFCは、フロー制御の状態をホストコンピューターからユーザーtelnetプロセスに伝える方法を定義します。

5. Description of the Option

5. このオプションの説明

Use of the option requires two phases. In the first phase, the telnet processes agree that one of them will TOGGLE-FLOW-CONTROL. WILL and DO are used only in this first phase. In general there will be only one exchange of WILL and DO for a session. Subnegotiations must not be issued until DO and WILL have been exchanged. It is permissible for either side to turn off the option by sending a WONT or DONT. Should this happen, no more subnegotiations may be sent, unless the option is re-enabled by another exchange of DO and WILL.

このオプションの使用には2つのフェーズが必要です。第1のフェーズでは、telnetプロセスどうしが、どちらか一方がTOGGLE-FLOW-CONTROLを行うことに合意します。WILLとDOは、この第1のフェーズでのみ使用します。一般に、WILLとDOの交換は1つのセッションにつき1回だけです。DOとWILLが交換されるまでは、サブネゴシエーションを発行してはなりません。どちらの側も、WONTまたはDONTを送信してこのオプションをオフにしてかまいません。そうなった場合、DOとWILLを再び交換してオプションが再度有効にならない限り、それ以上サブネゴシエーションを送信することはできません。

Once the hosts have exchanged a WILL and a DO, the sender of the DO TOGGLE-FLOW-CONTROL is free to send subnegotiations to enable and disable flow control in the other process, and to send subnegotiations for recommendations on when to restart output. Normally, the sender of the DO will be a host, and the other end will be a user telnet process, which is connected to a terminal. Thus the protocol is normally asymmetric, however it may be used in both directions without confusion should need for this arise.

ホストどうしがWILLとDOを交換したら、DO TOGGLE-FLOW-CONTROLの送信者は、相手のプロセスのフロー制御を有効化・無効化するサブネゴシエーションや、出力をいつ再開するかを推奨するサブネゴシエーションを自由に送信できます。通常、DOの送信者はホストであり、相手側は端末に接続されたユーザーtelnetプロセスです。したがって、このプロトコルは通常は非対称ですが、必要が生じた場合には、混乱なく双方向で使用できます。

As soon as the DO and WILL have been exchanged, the sender of the WILL must enable flow control. This allows flow control to begin in a known state. The decision of whether to restart output only when the XON character is received, or when any character received, starts in a system dependent state. (This is to make it consistent with older implementations of the TOGGLE-FLOW-CONTROL option that do not understand the RESTART-ANY and RESTART-XON suboptions.) The sender of the DO should send either a RESTART-ANY or RESTART-XON suboption to put the restart characteristics to a know state. Some clients might not be able to support both of the RESTART-ANY and RESTART-XON modes due to system limitations, and would then choose to ignore these commands. There is no way for the server to be notified of this condition, but a client should make every attempt to honor the state requested by the RESTART-ANY and RESTART-XON modes. Should the option be disabled by exchange of DONT and WONT, flow control may revert to an implementation-defined default state. It is not safe to assume that flow control will remain in the state requested by the most recent subnegotiation.

DOとWILLが交換されたらすぐに、WILLの送信者はフロー制御を有効にしなければなりません。これにより、フロー制御を既知の状態から開始できます。XON文字を受信したときだけ出力を再開するのか、任意の文字を受信したときに出力を再開するのかは、システムに依存した状態から始まります。（これは、RESTART-ANYとRESTART-XONのサブオプションを理解しない、TOGGLE-FLOW-CONTROLオプションの古い実装との整合性を保つためです。）DOの送信者は、再開の特性を既知の状態にするために、RESTART-ANYまたはRESTART-XONのいずれかのサブオプションを送信すべきです。クライアントによっては、システムの制約により、RESTART-ANYとRESTART-XONの両方のモードをサポートできず、これらのコマンドを無視することを選ぶ場合もあります。サーバーがこの状況を通知される方法はありませんが、クライアントは、RESTART-ANYとRESTART-XONのモードによって要求された状態に従うよう、あらゆる努力をすべきです。DONTとWONTの交換によってこのオプションが無効になった場合、フロー制御は実装で定義されたデフォルトの状態に戻ることがあります。フロー制御が直近のサブネゴシエーションで要求された状態のままであると仮定するのは安全ではありません。

In most implementations of software flow control, when enabled, the XOFF and XON characters are never propagated to the server; they are typically eaten by the terminal driver between the telnet client and the attached terminal. In most implementations that support the RESTART-ANY functionality, the typed character that re-enables the output is not eaten by the terminal driver, unless it is the XON character.

ソフトウェアフロー制御のほとんどの実装では、有効なとき、XOFF文字とXON文字がサーバーに伝わることはありません。これらは通常、telnetクライアントと接続された端末との間にある端末ドライバーによって消費されます。RESTART-ANYの機能をサポートするほとんどの実装では、出力を再開させる入力文字は、それがXON文字でない限り、端末ドライバーによって消費されません。

Currently, only four command codes are defined for the subnegotiations: flow control off (code 0), flow control on (code 1), restart output on any character (code 2) and restart output only on XON (code 3). None of these codes requires any additional data, however it is possible that additional commands may be added. Thus subnegotiations having command codes other than those defined in this document should be silently ignored.

現在、サブネゴシエーションに定義されているコマンドコードは、フロー制御オフ（コード0）、フロー制御オン（コード1）、任意の文字で出力を再開（コード2）、XONでのみ出力を再開（コード3）の4つだけです。どのコードも追加のデータを必要としませんが、今後コマンドが追加される可能性があります。そのため、この文書で定義されたもの以外のコマンドコードを持つサブネゴシエーションは、黙って無視すべきです。

This option does not deal with the issue of allowing the DO side of the connection to inform the WILL side which characters should be used for XON and XOFF. That functionality is already supplied by the LINEMODE [1] option.

このオプションは、コネクションのDO側がWILL側に対して、XONとXOFFにどの文字を使用すべきかを知らせることを可能にするという問題は扱いません。その機能は、すでにLINEMODE [1]オプションによって提供されています。

6. Example

6. 例

Here is an example of the use of this option:

このオプションの使用例を次に示します。

    Client                           Server
                                     IAC DO TOGGLE-FLOW-CONTROL
    IAC WILL TOGGLE-FLOW-CONTROL
    [ The server is now free to send commands to change flow control.
      Note that the client must now have enabled flow control, but
      that whether it is restart on XON only or on any character is
      client specific.  ]
                                     IAC SB TOGGLE-FLOW-CONTROL
                                     RESTART-ANY IAC SE

    [ The client should now switch to allowing output to restart when
      the user types any character, if the client is able to support
      that functionality.  ]
                                     IAC SB TOGGLE-FLOW-CONTROL OFF
                                     IAC SE
                                     IAC SB TOGGLE-FLOW-CONTROL ON
                                     IAC SE

    Client                           Server
                                     IAC DO TOGGLE-FLOW-CONTROL
    IAC WILL TOGGLE-FLOW-CONTROL
    [ The server is now free to send commands to change flow control.
      Note that the client must now have enabled flow control, but
      that whether it is restart on XON only or on any character is
      client specific.  ]
                                     IAC SB TOGGLE-FLOW-CONTROL
                                     RESTART-ANY IAC SE

    [ The client should now switch to allowing output to restart when
      the user types any character, if the client is able to support
      that functionality.  ]
                                     IAC SB TOGGLE-FLOW-CONTROL OFF
                                     IAC SE
                                     IAC SB TOGGLE-FLOW-CONTROL ON
                                     IAC SE
