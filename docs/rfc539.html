RFC 539

Thoughts on the Mail Protocol Proposed in RFC 524

RFC 539

RFC 524で提案されたメールプロトコルについての考え

Abstract

概要

Generally, we feel that the protocol is extremely rich. We also feel that there are some minor and some major problems.

全体として、このプロトコルは非常に機能が豊富だと私たちは感じています。また、いくつかの小さな問題と、いくつかの大きな問題があるとも感じています。

The minor points first:

まず小さな点から述べます。

  1. <CA> and <CA2> are not explained until the formal syntax. It would be more convenient, if they were explained sooner.
  2. The Proposed <CA2> is a bad thing, since it is the Telnet Go-Ahead, which should not be used by higher level protocols.
  3. The default SIGNATURE should be the sign-on or ident of the author(s).

  4. The Disposition INTERRUPT would be more useful if it had author/clerk-assigned "levels". Currently mail would be either urgent or not. With levels (say 1 to 10), the sender could rate the degree of urgency.

    There would be no precise defined meaning to any of these levels, merely the opportunity for a subjective evaluation by the sender. The receiver (process or person) may do whatever they wish with the information.

    A user could thereby direct a receiving process to notify him immediately of Priority 5 or higher Short mail or any Priority 10 mail immediately, but defer notification of any other mail. (Length is discussed later in this note.)

  5. Also, we would like the word, "INTERRUPT", to be changed to URGENT or PRIORITY
  6. In keeping with offering the sender the opportunity to 'rate' his mail, we would like to allow him the chance to warn the receiver of the size of the mail. This could be a byte count and/or an imprecise SHORT/MEDIUM/LONG. Again, the receiver may use this information as he/it sees fit.

  7. The ID command seems confusing.

    If I am a clerk and sending to someone on another host, that host may ask me to 'prove' my identity by using an ID. How can the Sigma-7 at UCLA-NMC know WHITE's id? He does not have one on the Sigma, but certainly should be able to send mail to us there.

  8. How do ACK's, Progress Reports, or Replies work when there is no Reference Serial number?
  9. Please include the distinction between Static and Dynamic attributes as part of the formal syntax.
  10. Though hosts must be allowed to require a login, before they will accept mail, would like the Protocol document to reflect a negative attitude towards such a requirement.
  11. In describing defaults, relatively cryptic phrases such as "Author to the Clerk" are sometimes used. Please be a bit more clear.

  12. The sender is required to send Static, Dynamic, and then Optional parameters.

    This requires receiving hosts to buffer the contents before passing them on to the appropriate recipient. (In fact, before finding out whether it can/will accept the mail.)

    The order should be: Dynamic, Optional, Static.

    By requiring the sending host to transmit the dynamic and optional attributes first, the receiving host can also reroute mail based upon its Priority and Length.

  1. <CA>と<CA2>は、形式的な構文のところまで説明されていません。もっと早い段階で説明されていれば便利でしょう。
  2. 提案されている<CA2>はよくありません。これはTelnetのGo-Aheadであり、上位レベルのプロトコルで使うべきものではないからです。
  3. SIGNATUREのデフォルトは、作成者のサインオンまたはidentにすべきです。

  4. Disposition INTERRUPTは、作成者や事務担当者（clerk）が割り当てる「レベル」があれば、もっと便利になるでしょう。現状では、メールは緊急か緊急でないかのどちらかしかありません。レベル（たとえば1から10）があれば、送信者は緊急度を評価できます。

    これらのレベルのいずれにも厳密に定義された意味はなく、単に送信者が主観的に評価する機会を与えるだけです。受信者（プロセスまたは人）は、その情報を好きなように扱ってかまいません。

    これにより、ユーザーは受信プロセスに対して、優先度5以上の短い（Short）メールや優先度10のメールはすぐに通知し、それ以外のメールの通知は後回しにするよう指示できます（長さについては、このメモの後半で説明します）。

  5. また、「INTERRUPT」という語を、URGENTまたはPRIORITYに変更してほしいと考えています。
  6. 送信者が自分のメールを「評価」できるようにすることにあわせて、メールの大きさを受信者に予告する機会も送信者に与えたいと考えています。これは、バイト数や、大まかなSHORT/MEDIUM/LONGなどで表せます。ここでも、受信者はこの情報を適切だと思うように使ってかまいません。

  7. IDコマンドはわかりにくいように思われます。

    私が事務担当者で、別のホストにいる誰かに送信する場合、そのホストはIDを使って私の身元を「証明」するよう求めてくるかもしれません。UCLA-NMCのSigma-7が、どうやってWHITEのidを知ることができるでしょうか？　彼はSigmaにidを持っていませんが、そこにいる私たちにメールを送れるべきなのは確かです。

  8. 参照シリアル番号（Reference Serial number）がない場合、ACK、進捗報告（Progress Report）、返信（Reply）はどのように機能するのでしょうか？
  9. 静的（Static）属性と動的（Dynamic）属性の区別を、形式的な構文の一部に含めてください。
  10. ホストがメールを受け付ける前にログインを要求できるようにしなければならないとしても、プロトコル文書にはそのような要件に否定的な姿勢を反映してほしいと考えています。
  11. デフォルトの説明で、「Author to the Clerk」のような比較的わかりにくい言い回しが使われていることがあります。もう少しわかりやすくしてください。

  12. 送信者は、静的（Static）パラメーター、動的（Dynamic）パラメーター、オプション（Optional）パラメーターの順に送信することを求められています。

    このため、受信側のホストは、内容を適切な受信者に渡す前に（実際には、そのメールを受け付けられるか、受け付けるかどうかを判断する前に）、内容をバッファリングする必要があります。

    順序は、動的、オプション、静的とすべきです。

    送信側のホストに動的属性とオプション属性を先に送信させることで、受信側のホストは優先度（Priority）と長さ（Length）に基づいてメールの経路を変更することもできます。

Now for the hairier problems:

次に、もっと厄介な問題です。

  1. We would like to make a strong statement in favor of the unified-access (one selector process with one listening socket) approach. However, since it does not exist, yet:

    The Mail Protocol should NOT be a subsystem of FTP. The Mail Protocol USES the File Transfer Protocol, the same as RJE uses FTP. We therefore suggest the use of the RJE model.

    This unfortunately opens up the issue of logging in, to send mail. The advantage of having FTP have a MAIL command is that it defines a class of data transfer which many hosts will allow for free, while maintaining control over other, 'normal' file transfer.

    The solution should be the same as that currently used by RJE.

  2. The FORWARD function allows a site to receive and hold mail during and/or, until a transfer request is received from the 'recipient' at another host.

    This action takes place AFTER receipt of the mail, so we would like to suggest a command for "Rerouting" mail just PRIOR to its receipt.

    This allows a receiving host to refuse a given piece of mail, but suggest an alternate receiver. This would be useful if the recipient were using another host for a while, or if the recipient didn't want to rack up storage charges at the first site.

    Three variation can occur, one of which will require a special MP reply code:

    Automatic forwarding:

    Accept the mail and then automatically transfer it to the user's alternate mailbox.

    This could be classed as a user "feature" and would not be part of the protocol. However, it would be quite useful.

    Automatic forwarding with copy held:
    The same as the first case, but the transferring server keeps a copy of the mail.
    Rerouting without accepting:

    The mail is never accepted from the sender. The sender is, however, informed of an alternate mailbox.

    The Rerouting information would be in reply to a RECIPIENT command.

    476 <recipient> IS AT <pathname>

  1. 私たちは、統合アクセス（unified-access）方式（1つの待ち受けソケットを持つ1つのセレクタープロセス）を強く支持したいと考えています。しかし、それはまだ存在しないので、次のように考えます。

    メールプロトコルは、FTPのサブシステムにすべきではありません。RJEがFTPを使うのと同じように、メールプロトコルはファイル転送プロトコルを「使う」ものです。したがって、RJEのモデルを使うことを提案します。

    残念ながら、これによって、メールを送信するためのログインの問題が持ち上がります。FTPにMAILコマンドを持たせる利点は、他の「通常の」ファイル転送の制御を維持しつつ、多くのホストが無料で許可するデータ転送のクラスを定義できることです。

    解決策は、現在RJEで使われているものと同じにすべきです。

  2. FORWARD機能により、サイトは、別のホストにいる「受信者」から転送要求を受け取るまで、またはその間、メールを受信して保持できます。

    この動作はメールを受信した「後」に行われるので、メールを受信する直「前」にメールの「経路を変更（Rerouting）」するコマンドを提案したいと考えています。

    これにより、受信側のホストは、あるメールを拒否しつつ、代わりの受信者を提示できます。これは、受信者がしばらく別のホストを使っている場合や、受信者が最初のサイトで保存料金をかさませたくない場合に便利です。

    3つの変形が考えられ、そのうちの1つには特別なMP応答コードが必要になります。

    自動転送：

    メールを受け付け、その後ユーザーの代わりのメールボックスに自動的に転送します。

    これはユーザー向けの「機能」に分類でき、プロトコルの一部にはならないでしょう。しかし、非常に便利です。

    コピーを保持する自動転送：
    1つ目の場合と同じですが、転送するサーバーがメールのコピーを保持します。
    受け付けずに経路を変更：

    メールは送信者から一切受け付けられません。ただし、送信者には代わりのメールボックスが通知されます。

    経路変更の情報は、RECIPIENTコマンドへの応答として返されます。

    476 <recipient> IS AT <pathname>
