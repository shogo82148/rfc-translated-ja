RFC 9236

Architectural Considerations of Information-Centric Networking (ICN) Using a Name Resolution Service

RFC 9236

名前解決サービスを使用する情報指向ネットワーキング（ICN）のアーキテクチャーに関する考慮事項

Abstract

概要

This document describes architectural considerations and implications related to the use of a Name Resolution Service (NRS) in Information-Centric Networking (ICN). It explains how the ICN architecture can change when an NRS is utilized and how its use influences the ICN routing system. This document is a product of the Information-Centric Networking Research Group (ICNRG).

この文書は、情報指向ネットワーキング（Information-Centric Networking、ICN）における名前解決サービス（Name Resolution Service、NRS）の使用に関連する、アーキテクチャー上の考慮事項と影響について説明します。 NRSを利用するとICNアーキテクチャーがどのように変化するか、またその使用がICNのルーティングシステムにどのように影響するかを説明します。 この文書は、情報指向ネットワーキング研究グループ（Information-Centric Networking Research Group、ICNRG）の成果物です。

1. Introduction

1. はじめに

Information-Centric Networking (ICN) is an approach to evolving the Internet infrastructure to provide direct access to Named Data Objects (NDOs) by names. In two common ICN architectures, Named Data Networking (NDN) [NDN] and Content-Centric Networking (CCNx) [CCNx], the name of an NDO is used directly to route a request to retrieve the data object. Such direct name-based routing has inherent challenges in enabling a globally scalable routing system, accommodating producer mobility, and supporting off-path caching. These specific issues are discussed in detail in Section 3. In order to address these challenges, a Name Resolution Service (NRS) has been utilized in the literature as well as the proposals of several ICN projects [Afanasyev] [Zhang2] [Ravindran] [SAIL] [MF] [Bayhan].

情報指向ネットワーキング（Information-Centric Networking、ICN）は、名前付きデータオブジェクト（Named Data Object、NDO）に名前で直接アクセスできるようにするために、インターネットインフラストラクチャーを進化させるアプローチです。 一般的な2つのICNアーキテクチャーである名前付きデータネットワーキング（Named Data Networking、NDN）[NDN]とコンテンツ指向ネットワーキング（Content-Centric Networking、CCNx）[CCNx]では、データオブジェクトを取得するリクエストのルーティングに、NDOの名前が直接使用されます。 このような名前に基づく直接的なルーティングには、グローバルにスケーラブルなルーティングシステムの実現、プロデューサーのモビリティーへの対応、経路外キャッシングのサポートにおいて、本質的な課題があります。 これらの具体的な問題については、Section 3で詳しく議論します。 これらの課題に対処するために、名前解決サービス（Name Resolution Service、NRS）が、文献や、いくつかのICNプロジェクトの提案で利用されてきました[Afanasyev] [Zhang2] [Ravindran] [SAIL] [MF] [Bayhan]。

This document describes the potential changes in the ICN architecture caused by the introduction of an NRS and the corresponding implication to the ICN routing system. It also describes ICN architectural considerations for the integration of an NRS. The scope of this document includes considerations from the perspective of an ICN architecture and routing system when using an NRS in ICN. A description of the NRS itself is provided in the companion NRS design considerations document [RFC9138], which provides the NRS approaches, functions, and design considerations.

この文書では、NRSの導入によって生じうるICNアーキテクチャーの変化と、それに対応するICNのルーティングシステムへの影響について説明します。 また、NRSを統合する際のICNアーキテクチャー上の考慮事項についても説明します。 この文書の範囲には、ICNでNRSを使用する際の、ICNアーキテクチャーとルーティングシステムの観点からの考慮事項が含まれます。 NRS自体の説明は、姉妹文書であるNRSの設計上の考慮事項に関する文書[RFC9138]で提供されており、その文書ではNRSのアプローチ、機能、設計上の考慮事項が示されています。

This document represents the consensus of the Information-Centric Networking Research Group (ICNRG). It has been reviewed extensively by the Research Group (RG) members who are actively involved in the research and development of the technology covered by this document. It is not an IETF product and is not a standard.

この文書は、情報指向ネットワーキング研究グループ（Information-Centric Networking Research Group、ICNRG）のコンセンサスを代表するものです。 この文書は、この文書で扱う技術の研究開発に積極的に関わっている研究グループ（Research Group、RG）のメンバーによって、広範にレビューされています。 この文書はIETFの成果物ではなく、標準でもありません。

2. Terminology

2. 用語

Name Resolution Service (NRS):
An NRS in ICN is defined as a service that provides the function of translating a content name or a data object name into some other information such as a routable prefix, a locator, an off-path-cache pointer, or an alias name that is more amenable than the input name to forwarding the object request toward the target destination storing the NDO [RFC9138]. An NRS is most likely implemented through the use of a distributed mapping database system. The Domain Name System (DNS) may be used as an NRS. However, in this case, the requirements of frequent updates of NRS records due to the creations of a lot of new NDOs and changes in their locations in the network need to be considered.
NRS server:
An NRS comprises the distributed NRS servers storing the mapping records in their databases. NRS servers store and maintain the mapping records that keep the mappings of content or object name to some other information that is used for forwarding the content request or the content itself.
NRS resolver:
The client-side function of an NRS is called an NRS resolver. The NRS resolver is responsible for initiating name resolution request queries that ultimately lead to a name resolution of the target data objects. NRS resolvers can be located in the consumer (or client) nodes and/or ICN routers. An NRS resolver may also cache the mapping records obtained through the name resolution for later usage.
Name registration:
In order to populate the NRS, the content names and their mapping records must be registered in the NRS system by a publisher who has access rights to at least one authoritative NRS server or by a producer who generates named data objects. The records contain the mapping of an object name to some information such as other alias names, routable prefixes, and locators, which are used for forwarding the content request. Thus, a publisher or producer of content creates an NRS registration request and sends it to an NRS server. On registration, the NRS server stores (or updates) the name mapping record in the database and sends an acknowledgement back to the producer or publisher that made the registration request.
Name resolution:
Name resolution is the main function of the NRS system. It is performed by an NRS resolver, which can be deployed on a consumer node or an ICN router. Resolvers are responsible for either returning a cached mapping record (whose lifetime has not expired) or alternatively sending a name resolution request toward an NRS server. The NRS server searches for the content name in its mapping record database and, if found, retrieves the mapping record and returns it in a name resolution response message to the NRS resolver.
NRS node:
NRS servers are also referred to as NRS nodes that maintain the name records. The terms are used interchangeably.
NRS client:
A node that uses the NRS is called an NRS client. Any node that initiates a name registration, resolution, or update procedure is an NRS client; that is, NRS resolvers, ICN client nodes, ICN routers, or producers can be NRS clients.
名前解決サービス（Name Resolution Service、NRS）：
ICNにおけるNRSは、コンテンツ名やデータオブジェクト名を、ルーティング可能なプレフィックス、ロケーター、経路外キャッシュへのポインター、エイリアス名など、オブジェクトのリクエストをNDOを格納している目的の宛先に向けて転送するのに入力された名前よりも適した、何らかの別の情報に変換する機能を提供するサービスとして定義されます[RFC9138]。 NRSは、分散マッピングデータベースシステムを使用して実装される可能性が最も高いです。 ドメインネームシステム（DNS）をNRSとして使用することもできます。 ただし、その場合は、多数の新しいNDOの作成やネットワーク内でのその位置の変化によって、NRSレコードを頻繁に更新するという要件を考慮する必要があります。
NRSサーバー：
NRSは、マッピングレコードをデータベースに格納する分散したNRSサーバーで構成されます。 NRSサーバーは、コンテンツ名またはオブジェクト名から、コンテンツのリクエストやコンテンツ自体の転送に使用される何らかの別の情報へのマッピングを保持するマッピングレコードを、格納し維持します。
NRSリゾルバー：
NRSのクライアント側の機能を、NRSリゾルバーと呼びます。 NRSリゾルバーは、最終的に目的のデータオブジェクトの名前解決につながる、名前解決リクエストのクエリーを開始する役割を担います。 NRSリゾルバーは、コンシューマー（またはクライアント）ノードとICNルーターの一方または両方に配置できます。 NRSリゾルバーは、名前解決によって得られたマッピングレコードを、後で使用するためにキャッシュすることもできます。
名前登録：
NRSにデータを投入するには、少なくとも1つの権威NRSサーバーへのアクセス権を持つパブリッシャー、または名前付きデータオブジェクトを生成するプロデューサーが、コンテンツ名とそのマッピングレコードをNRSシステムに登録する必要があります。 レコードには、オブジェクト名から、他のエイリアス名、ルーティング可能なプレフィックス、ロケーターなど、コンテンツのリクエストの転送に使用される何らかの情報へのマッピングが含まれます。 したがって、コンテンツのパブリッシャーまたはプロデューサーは、NRS登録リクエストを作成し、それをNRSサーバーに送信します。 登録時に、NRSサーバーは名前マッピングレコードをデータベースに格納（または更新）し、登録リクエストを行ったプロデューサーまたはパブリッシャーに確認応答を返します。
名前解決：
名前解決は、NRSシステムの主要な機能です。 名前解決はNRSリゾルバーによって実行され、NRSリゾルバーはコンシューマーノードまたはICNルーターに展開できます。 リゾルバーは、（有効期間が切れていない）キャッシュ済みのマッピングレコードを返すか、または代わりにNRSサーバーに向けて名前解決リクエストを送信する役割を担います。 NRSサーバーは、マッピングレコードのデータベースでコンテンツ名を検索し、見つかった場合はマッピングレコードを取得して、名前解決レスポンスメッセージに含めてNRSリゾルバーに返します。
NRSノード：
NRSサーバーは、名前レコードを維持するNRSノードとも呼ばれます。 これらの用語は同じ意味で使用されます。
NRSクライアント：
NRSを使用するノードを、NRSクライアントと呼びます。 名前の登録、解決、または更新の手続きを開始するノードはすべてNRSクライアントです。 つまり、NRSリゾルバー、ICNクライアントノード、ICNルーター、またはプロデューサーがNRSクライアントになりえます。

3. Background

3. 背景

A pure name-based routing approach in ICN has inherent challenges in enabling a globally scalable routing system, accommodating producer mobility, and supporting off-path caching. In order to address these challenges, an NRS has been utilized in proposals and literature of several ICN projects as follows:

ICNにおける純粋な名前ベースのルーティングのアプローチには、グローバルにスケーラブルなルーティングシステムの実現、プロデューサーのモビリティーへの対応、経路外キャッシングのサポートにおいて、本質的な課題があります。 これらの課題に対処するために、次のように、いくつかのICNプロジェクトの提案や文献でNRSが利用されてきました。

Routing scalability:
In ICN, application names identifying content are intended to be used directly for packet delivery, so ICN routers run a name-based routing protocol to build name-based routing and forwarding tables. Similar to the scalability challenge of IP routing, if non-aggregatable name prefixes are injected into the Default Route Free Zone (DFZ) of ICN routers, they would be driving the uncontrolled growth of the DFZ routing table size. Thus, providing the level of indirection enabled by an NRS in ICN can be an approach to keeping the routing table size under control. The NRS system resolves name prefixes that do not exist in the DFZ forwarding table into globally routable prefixes such as the one proposed in NDN [Afanasyev]. Another approach dealing with routing scalability is the Multi-level Distributed Hash Table (MDHT) used in NetInf [Dannewitz]. It provides name-based anycast routing that can support a non-hierarchical namespace and can be adopted on a global scale [Dannewitz2].
Producer mobility:
In ICN, if a producer moves into a different name domain that uses a different name prefix, the request for a content produced by the moving producer with the origin content name must be forwarded to the moving producer's new location. Especially in a hierarchical naming scheme, producer mobility support is much harder than in a flat naming scheme since the routing tables in a broader area need to be updated to track the producer movement. Therefore, various ICN architectures such as NetInf [Dannewitz] and MobilityFirst [MF] have adopted NRS systems to tackle the issues of producers whose location changes.
Off-path caching:
In-network caching is a common feature of an ICN architecture. Caching approaches can be categorized into on-path caching and off-path caching, according to the location of caches in relation to the forwarding path from the original content store to a consumer. Off-path caching, sometimes also referred to as content replication or content storing, aims to replicate a Named Data Object in various locations within a network in order to increase the availability of content, reduce access latency, or both. These caching locations may not be lying along the content forwarding path. Thus, finding off-path cached content requires more complex forwarding procedures if a pure name-based routing is employed. In order to support access to off-path caches, the locations of replicas are usually advertised into a name-based routing system or into an NRS as described in [Bayhan].
ルーティングのスケーラビリティー：
ICNでは、コンテンツを識別するアプリケーション名をパケットの配送に直接使用することを意図しているため、ICNルーターは名前ベースのルーティングプロトコルを実行して、名前ベースのルーティングテーブルと転送テーブルを構築します。 IPルーティングのスケーラビリティーの課題と同様に、集約できない名前プレフィックスがICNルーターのデフォルトルートフリーゾーン（Default Route Free Zone、DFZ）に注入されると、DFZのルーティングテーブルのサイズが際限なく増大する原因になります。 したがって、ICNにおいてNRSによって実現される間接参照のレベルを提供することは、ルーティングテーブルのサイズを抑制するためのアプローチになりえます。 NRSシステムは、NDNで提案されているもの[Afanasyev]のように、DFZの転送テーブルに存在しない名前プレフィックスを、グローバルにルーティング可能なプレフィックスに解決します。 ルーティングのスケーラビリティーに対処するもう1つのアプローチは、NetInf [Dannewitz]で使用されているマルチレベル分散ハッシュテーブル（Multi-level Distributed Hash Table、MDHT）です。 MDHTは、階層的でない名前空間をサポートでき、グローバルな規模で採用できる、名前ベースのエニーキャストルーティングを提供します[Dannewitz2]。
プロデューサーのモビリティー：
ICNでは、プロデューサーが異なる名前プレフィックスを使用する別の名前ドメインに移動した場合、移動するプロデューサーが生成したコンテンツに対する元のコンテンツ名でのリクエストを、移動したプロデューサーの新しい位置に転送する必要があります。 特に階層的な命名方式では、プロデューサーの移動を追跡するためにより広い範囲のルーティングテーブルを更新する必要があるので、プロデューサーのモビリティーのサポートはフラットな命名方式よりもはるかに困難です。 そのため、NetInf [Dannewitz]やMobilityFirst [MF]などのさまざまなICNアーキテクチャーは、位置が変化するプロデューサーの問題に取り組むために、NRSシステムを採用しています。
経路外キャッシング：
ネットワーク内キャッシュは、ICNアーキテクチャーに共通の機能です。 キャッシングのアプローチは、元のコンテンツストアからコンシューマーへの転送経路に対するキャッシュの位置に応じて、経路上キャッシングと経路外キャッシングに分類できます。 経路外キャッシングは、コンテンツレプリケーションやコンテンツストアリングとも呼ばれ、コンテンツの可用性を高めたり、アクセスの遅延を減らしたり、あるいはその両方を実現したりするために、名前付きデータオブジェクトをネットワーク内のさまざまな場所に複製することを目的とします。 これらのキャッシュの場所は、コンテンツの転送経路上にあるとは限りません。 したがって、純粋な名前ベースのルーティングを採用している場合、経路外にキャッシュされたコンテンツを見つけるには、より複雑な転送手続きが必要になります。 経路外キャッシュへのアクセスをサポートするために、通常、レプリカの位置は、名前ベースのルーティングシステムに広告されるか、または[Bayhan]で説明されているようにNRSに広告されます。

This document discusses architectural considerations and implications of ICN when an NRS is utilized to solve such challenges facing a name-based routing in ICN.

この文書では、ICNにおける名前ベースのルーティングが直面するこのような課題を解決するためにNRSを利用する場合の、ICNのアーキテクチャー上の考慮事項と影響について議論します。

4. Implications of an NRS in ICN

4. ICNにおけるNRSの影響

An NRS is not a mandatory part of an ICN architecture, as the majority of ICN architectures uses name-based routing that avoids the need for a name resolution procedure. Therefore, the utilization of an NRS in an ICN architecture changes some architectural aspects at least with respect to forwarding procedures, latency, and security, as discussed below:

ICNアーキテクチャーの大部分は、名前解決の手続きを必要としない名前ベースのルーティングを使用しているため、NRSはICNアーキテクチャーの必須の部分ではありません。 そのため、ICNアーキテクチャーでNRSを利用すると、以下で議論するように、少なくとも転送手続き、遅延、セキュリティーに関して、アーキテクチャーのいくつかの側面が変化します。

Forwarding procedure:
When an NRS is included in an ICN architecture, the name resolution procedure has to be included in the ICN overall routing and forwarding architectural procedures. To integrate an NRS into an ICN architecture, there are certain things that have to be decided and specified such as where, when, and how the name resolution task is performed.
Latency:
When an NRS is included in an ICN architecture, additional latency introduced by the name resolution process is incurred by the routing and forwarding system. Although the latency due to the name resolution is added, the total latency of individual requests being served could be lower if the nearest copies or off-path caches can be located by the NRS lookup procedure. Additionally, there might be a favorable trade-off between the name resolution latency and inter-domain traffic reduction by finding the nearest off-path cached copy of the content. Finding the nearest cache holding the content might significantly reduce the content discovery as well as delivery latency.
Security:
When any new component such as an NRS is introduced in the ICN architecture, the attack surface may increase. Protection of the NRS system itself against attacks such as Distributed Denial of Service (DDoS) and spoofing or alteration of name mapping records and related signaling messages may be challenging.
転送手続き：
ICNアーキテクチャーにNRSを含める場合、名前解決の手続きを、ICN全体のルーティングと転送のアーキテクチャー上の手続きに含める必要があります。 NRSをICNアーキテクチャーに統合するには、名前解決のタスクをどこで、いつ、どのように実行するかなど、決定して規定しなければならない事項があります。
遅延：
ICNアーキテクチャーにNRSを含める場合、ルーティングおよび転送システムには、名前解決の処理によって追加の遅延が生じます。 名前解決による遅延は加わりますが、NRSの検索手続きによって最も近いコピーや経路外キャッシュを見つけることができれば、処理される個々のリクエストの全体の遅延は小さくなる可能性があります。 さらに、コンテンツの最も近い経路外キャッシュのコピーを見つけることで、名前解決の遅延とドメイン間トラフィックの削減との間に、好ましいトレードオフが生じる可能性があります。 コンテンツを保持している最も近いキャッシュを見つけることで、コンテンツの発見と配送の遅延を大幅に削減できる可能性があります。
セキュリティー：
NRSのような新しいコンポーネントがICNアーキテクチャーに導入されると、攻撃対象領域が増加する可能性があります。 分散型サービス拒否（Distributed Denial of Service、DDoS）や、名前マッピングレコードおよび関連するシグナリングメッセージの偽装や改ざんなどの攻撃から、NRSシステム自体を保護することは困難な場合があります。

5. ICN Architectural Considerations for NRS

5. NRSのためのICNアーキテクチャー上の考慮事項

This section discusses the various items that can be considered from the perspective of ICN architecture when employing an NRS system. These items are related to the registration, resolution, and update of name mapping records, protocols and messages, and integration with the routing system.

このセクションでは、NRSシステムを採用する際に、ICNアーキテクチャーの観点から考慮できるさまざまな項目について議論します。 これらの項目は、名前マッピングレコードの登録、解決、更新、プロトコルとメッセージ、およびルーティングシステムとの統合に関連します。

5.1. Name Mapping Records Registration, Resolution, and Update

5.1. 名前マッピングレコードの登録、解決、更新

When an NRS is integrated in ICN architecture, the functions related to the registration, resolution, and update of name mapping records have to be considered. The NRS nodes maintain the name mapping records and may exist as an overlay network over the ICN routers, that is, they communicate to each other through ICN routers. Figure 1 shows the NRS nodes and NRS clients connected through an underlying network. The NRS nodes should be deployed in such a manner that an NRS node is always available at a short distance from an NRS client so that communication latency for the name registration and resolution requested by the NRS client remains very low. The name registration, name resolution, and name record update procedures are briefly discussed below.

NRSをICNアーキテクチャーに統合する場合、名前マッピングレコードの登録、解決、更新に関連する機能を考慮する必要があります。 NRSノードは名前マッピングレコードを維持し、ICNルーター上のオーバーレイネットワークとして存在する場合があります。 つまり、NRSノードはICNルーターを介して互いに通信します。 Figure 1は、下位のネットワークを介して接続されたNRSノードとNRSクライアントを示しています。 NRSノードは、NRSクライアントが要求する名前登録と名前解決の通信遅延が非常に小さく保たれるように、NRSクライアントから短い距離に常にNRSノードが利用可能であるような方法で展開されるべきです。 名前登録、名前解決、名前レコードの更新の手続きについて、以下で簡単に議論します。

Name registration:
Name registration is performed by the producer (as an NRS client) when it creates a new content. When a producer creates content and assigns a name from its name prefix space to the content, the producer performs the name registration in an NRS node. Name registration may be performed by an ICN router when the ICN architecture supports off-path caching or cooperative caching since involving an NRS may be a good idea for off-path caching. The ICN routers with forwarder caches do not require name registration for their cached content because they lie on the path toward an upstream content store or producer. They will be hit when a future request is forwarded to the content producer by an ICN router lying downstream toward the ICN client node. However, ICN routers performing off-path caching of content must invoke the name registration procedure so that other ICN routers can depend on name resolutions to know about the off-path cache locations. If a content gets cached in many off-path ICN routers, all of them may register the same content names in the same NRS node, resulting in multiple registration actions. In this case, the NRS node adds the new location of the content to the name record together with the previous locations. In this way, each of the name records stored in the NRS node may contain multiple locations of the content. Assigning validity time or a lifetime of each mapping record may be considered especially for the off-path caching content and managing mobility.
Name resolution:
Name resolution is performed by an NRS client to obtain the name record from an NRS node by sending a name resolution request message and getting a response containing the record. In the name-based ICN routing context, the name resolution is needed by any ICN router whose forwarding information base (FIB) does not contain the requested name prefix. Name resolution may also be performed by the consumer (especially in the case where the consumer is multihomed) to forward the content request in a better direction so that it obtains the content from the nearest cache. If the consumer is single homed, it may not bother to perform name resolution, instead depending on either straightforward name-based routing or name resolution by an upstream ICN router. In this case, the consumer creates the content request packet containing the content name and forwards to the nearest ICN router. The ICN router checks its FIB table to see where to forward the content request. If the ICN router fails to identify whether the requested content is reachable, it performs name resolution to obtain the name mapping record and adds this information to its FIB. The ICN router may also perform name resolution even before the arrival of a content request to use the name mapping record to configure its FIB.
Name record update:
Name record update is carried out when a content name mapping record changes, e.g., the content is not available in one or more of the previous locations. The name record update includes the substitution and deletion of the name mapping records. The name record update may take place explicitly by the exchange of name record update messages or implicitly when a timeout occurs and a name record is deemed to be invalid. The implicit update is possible when each record is accompanied by a lifetime value. The lifetime can be renewed only by the authoritative producer or node. The cached mapping records get erased after the lifetime expires unless a lifetime extension indication is obtained from the authoritative producer.
名前登録：
名前登録は、プロデューサーが新しいコンテンツを作成するときに、（NRSクライアントとして）プロデューサーによって実行されます。 プロデューサーがコンテンツを作成し、自身の名前プレフィックス空間からその名前をコンテンツに割り当てると、プロデューサーはNRSノードで名前登録を実行します。 ICNアーキテクチャーが経路外キャッシングや協調キャッシングをサポートしている場合は、ICNルーターが名前登録を実行することもあります。 経路外キャッシングでは、NRSを関与させるのがよい考えである場合があるためです。 フォワーダーキャッシュを持つICNルーターは、上流のコンテンツストアやプロデューサーに向かう経路上に位置しているので、キャッシュしたコンテンツの名前登録を必要としません。 ICNクライアントノードに向かう下流に位置するICNルーターによって、将来のリクエストがコンテンツのプロデューサーに転送されるときに、これらのキャッシュがヒットします。 しかし、コンテンツの経路外キャッシングを実行するICNルーターは、他のICNルーターが名前解決を利用して経路外キャッシュの位置を知ることができるように、名前登録の手続きを呼び出す必要があります。 コンテンツが多くの経路外のICNルーターにキャッシュされると、それらのすべてが同じNRSノードに同じコンテンツ名を登録し、複数の登録動作が発生する可能性があります。 この場合、NRSノードは、コンテンツの新しい位置を以前の位置とともに名前レコードに追加します。 このようにして、NRSノードに格納される各名前レコードには、コンテンツの複数の位置が含まれる場合があります。 特に経路外キャッシングのコンテンツやモビリティーの管理のために、各マッピングレコードに有効時間や有効期間を割り当てることを検討できます。
名前解決：
名前解決は、NRSクライアントが名前解決リクエストメッセージを送信し、レコードを含むレスポンスを受け取ることで、NRSノードから名前レコードを取得するために実行されます。 名前ベースのICNルーティングの文脈では、転送情報ベース（forwarding information base、FIB）に要求された名前プレフィックスが含まれていないICNルーターは、名前解決を必要とします。 名前解決は、コンシューマーが最も近いキャッシュからコンテンツを取得できるように、コンテンツのリクエストをより適切な方向に転送するために、（特にコンシューマーがマルチホームの場合に）コンシューマーによって実行されることもあります。 コンシューマーがシングルホームの場合、コンシューマーはわざわざ名前解決を実行せず、代わりに単純な名前ベースのルーティングか、上流のICNルーターによる名前解決のどちらかに依存する場合があります。 この場合、コンシューマーはコンテンツ名を含むコンテンツリクエストパケットを作成し、最も近いICNルーターに転送します。 ICNルーターは、自身のFIBテーブルを確認して、コンテンツのリクエストをどこに転送するかを調べます。 要求されたコンテンツが到達可能かどうかを特定できなかった場合、ICNルーターは名前解決を実行して名前マッピングレコードを取得し、この情報を自身のFIBに追加します。 ICNルーターは、名前マッピングレコードを使用してFIBを設定するために、コンテンツのリクエストが到着する前に名前解決を実行することもあります。
名前レコードの更新：
名前レコードの更新は、たとえば以前の位置の1つ以上でコンテンツが利用できなくなったなど、コンテンツ名のマッピングレコードが変化したときに実行されます。 名前レコードの更新には、名前マッピングレコードの置き換えと削除が含まれます。 名前レコードの更新は、名前レコード更新メッセージの交換によって明示的に行われる場合と、タイムアウトが発生して名前レコードが無効とみなされたときに暗黙的に行われる場合があります。 暗黙的な更新は、各レコードに有効期間の値が付随している場合に可能です。 有効期間を更新できるのは、権威のあるプロデューサーまたはノードだけです。 キャッシュされたマッピングレコードは、権威のあるプロデューサーから有効期間の延長の指示が得られない限り、有効期間が切れた後に消去されます。

5.2. Protocols and Semantics

5.2. プロトコルとセマンティクス

In order to develop an NRS system within a local ICN network domain or global ICN network domain, new protocols and semantics must be designed and implemented to manage and resolve names among different namespaces.

ローカルなICNネットワークドメインまたはグローバルなICNネットワークドメイン内でNRSシステムを開発するには、異なる名前空間の間で名前を管理し解決するための新しいプロトコルとセマンティクスを設計し、実装する必要があります。

One way of implementing an NRS for CCNx is by extending the basic TLV format and semantics [RFC8569] [RFC8609]. For instance, name resolution and response messages can be implemented by defining new type fields in the Interest and Content Object messages [CCNxNRS]. By leveraging the existing CCNx Interest and Content Object packets for name resolution and registration, the NRS system can be deployed with a few ICN protocol changes. However, because of confining the changes to the basic ICN protocol and semantics, the NRS system may not be able to exploit more flexible and scalable designs.

CCNx向けにNRSを実装する方法の1つは、基本的なTLV形式とセマンティクス[RFC8569] [RFC8609]を拡張することです。 たとえば、名前解決メッセージとレスポンスメッセージは、InterestメッセージとContent Objectメッセージに新しいタイプフィールドを定義することで実装できます[CCNxNRS]。 名前解決と登録に既存のCCNxのInterestパケットとContent Objectパケットを活用することで、わずかなICNプロトコルの変更でNRSシステムを展開できます。 しかし、変更を基本的なICNプロトコルとセマンティクスの範囲に限定するため、NRSシステムは、より柔軟でスケーラブルな設計を活用できない可能性があります。

On the other hand, an NRS system can be designed independently with its own protocol and semantics like the NRS system described in [Hong]. For instance, the NRS protocol and messages can be implemented by using a RESTful API, and the NRS can be operated as an application protocol independent of the rest of the ICN protocol.

一方、[Hong]で説明されているNRSシステムのように、独自のプロトコルとセマンティクスを持つNRSシステムを独立して設計することもできます。 たとえば、NRSのプロトコルとメッセージをRESTful APIを使用して実装し、NRSをICNプロトコルの他の部分から独立したアプリケーションプロトコルとして運用できます。

5.3. Routing System

5.3. ルーティングシステム

An NRS reduces the routing complexity of ICN architecture compared to pure name-based routing. It does so by permitting the routing system to update the routing table on demand with the help of name records obtained from NRS. The routing system therefore needs to make name resolution requests and process the information returned, such as a prefix, a locator, an off-path-cache pointer, or an alias name, obtained from the name resolution.

NRSは、純粋な名前ベースのルーティングと比べて、ICNアーキテクチャーのルーティングの複雑さを軽減します。 これは、NRSから得られた名前レコードを利用して、ルーティングシステムがオンデマンドでルーティングテーブルを更新できるようにすることで実現されます。 したがって、ルーティングシステムは、名前解決リクエストを行い、名前解決から得られたプレフィックス、ロケーター、経路外キャッシュへのポインター、エイリアス名などの返された情報を処理する必要があります。

No matter what kind of information is obtained from the name resolution, as long as it is in the form of a name, the content request message in the routing system may be reformatted with the obtained information. In this case, the content name requested originally by a consumer needs to be involved in the reformatted content request to check the integrity of the binding between the name and the requested content. In other words, the information obtained from the name resolution is used to forward the content request, and the original content name requested by a consumer is used to identify the content. Alternatively, the resolved information may be used to build the routing table.

名前解決からどのような種類の情報が得られたとしても、それが名前の形式である限り、ルーティングシステム内のコンテンツリクエストメッセージは、得られた情報を使って再フォーマットされる場合があります。 この場合、名前と要求されたコンテンツとの間の結び付きの完全性を検査するために、コンシューマーが最初に要求したコンテンツ名を、再フォーマットされたコンテンツリクエストに含める必要があります。 言い換えると、名前解決から得られた情報はコンテンツのリクエストの転送に使用され、コンシューマーが要求した元のコンテンツ名はコンテンツの識別に使用されます。 あるいは、解決された情報をルーティングテーブルの構築に使用することもできます。

The information obtained from name resolution may not be in the form of a name. For example, it may identify tunnel endpoints by IP address and instead be used to construct an IP protocol tunnel through which to forward the content request.

名前解決から得られた情報は、名前の形式でない場合もあります。 たとえば、その情報がトンネルのエンドポイントをIPアドレスで識別し、代わりに、コンテンツのリクエストを転送するためのIPプロトコルのトンネルの構築に使用される場合があります。

6. Conclusion

6. 結論

A Name Resolution Service (NRS) is not a mandatory part in an ICN architecture, as the majority of ICN architectures use name-based routing that does not employ a name resolution procedure. However, such name-based routing in ICN has inherent challenges in enabling a globally scalable routing system, accommodating producer mobility, and supporting off-path caching. In order to address these challenges, an NRS system has been introduced in several ICN projects. Therefore, this document describes how the ICN architecture changes when an NRS is utilized and how this affects the ICN routing system.

ICNアーキテクチャーの大部分は、名前解決の手続きを用いない名前ベースのルーティングを使用しているため、名前解決サービス（NRS）はICNアーキテクチャーの必須の部分ではありません。 しかし、ICNにおけるこのような名前ベースのルーティングには、グローバルにスケーラブルなルーティングシステムの実現、プロデューサーのモビリティーへの対応、経路外キャッシングのサポートにおいて、本質的な課題があります。 これらの課題に対処するために、いくつかのICNプロジェクトでNRSシステムが導入されてきました。 そのため、この文書では、NRSを利用するとICNアーキテクチャーがどのように変化するか、またそれがICNのルーティングシステムにどのように影響するかを説明しています。

The document defines a few terminologies related to an NRS and explains some inherent challenges of pure name-based routing in ICN such as routing scalability, producer mobility, and off-path caching. This document describes how the ICN architecture would change with respect to procedures, latency, and security when an NRS is utilized. According to the ICN architectural changes, this document describes ICN architectural considerations for NRS such as the functions related to the registration, resolution and update of name mapping records, protocols and semantics to implement an NRS system, and the routing system involving the name resolution.

この文書では、NRSに関連するいくつかの用語を定義し、ルーティングのスケーラビリティー、プロデューサーのモビリティー、経路外キャッシングなど、ICNにおける純粋な名前ベースのルーティングの本質的な課題をいくつか説明しています。 この文書では、NRSを利用する場合に、手続き、遅延、セキュリティーに関してICNアーキテクチャーがどのように変化するかを説明しています。 こうしたICNアーキテクチャーの変化に応じて、この文書では、名前マッピングレコードの登録、解決、更新に関連する機能、NRSシステムを実装するためのプロトコルとセマンティクス、名前解決を伴うルーティングシステムなど、NRSのためのICNアーキテクチャー上の考慮事項を説明しています。

8. Security Considerations

8. セキュリティーに関する考慮事項

When any new component such as an NRS is introduced in the ICN architecture, the attack surface increases. The related security vulnerability issues are discussed below:

NRSのような新しいコンポーネントがICNアーキテクチャーに導入されると、攻撃対象領域が増加します。 関連するセキュリティー脆弱性の問題について、以下で議論します。

Namespace security:
In order to deploy an NRS system in ICN architecture, ICN namespaces, which may be assigned by authoritative entities, must be securely mapped to the content publishers and securely managed by them. According to the ICN research challenges [RFC7927], a new namespace can also provide an integrity verification function to authenticate its publisher. The issues of namespace authentication and the mapping among different namespaces require further investigation.
NRS system security:
An NRS requires the deployment of new entities (e.g., NRS servers) to build distributed and scalable NRS systems. Thus, the entities, e.g., an NRS server maintaining a mapping database, could be the focus of attacks by receiving malicious requests from innumerable adversaries comprising of Denial-of-Service or Distributed-Denial-of-Service attacks. In addition, NRS clients in general must trust the NRS nodes in other network domains to some degree, and communication among them must also be protected securely to prevent malicious entities from participating in this communication. The history of name resolution data requires to be stored and analyzed as in passive DNS to uncover potential security incidents or discover malicious infrastructures.
NRS protocol and message security:
In an NRS system, the protocols to generate, transmit, and receive NRS messages related to the name registration, resolution, and record update should be protected by proper security mechanisms. Proper security measures must be provided so that only legitimate nodes can initiate and read NRS messages. These messages must be secured by integrity protection and authentication mechanisms so that unauthorized parties cannot manipulate them when being forwarded through the network. Security measures to encrypt these messages should also be developed to thwart all threats to both security and privacy. Numerous problems similar to the security issues of an IP network and DNS can affect the overall ICN architecture. The DNS QNAME minimization type of approach would be suitable for preserving privacy in the name resolution process. Therefore, security mechanisms such as accessibility, authentication, etc., for the NRS system [RFC9138] should be considered to protect not only the NRS system but also the ICN architecture overall.
名前空間のセキュリティー：
ICNアーキテクチャーにNRSシステムを展開するには、権威のあるエンティティーによって割り当てられる場合があるICNの名前空間を、コンテンツのパブリッシャーに安全にマッピングし、パブリッシャーによって安全に管理する必要があります。 ICNの研究課題[RFC7927]によれば、新しい名前空間は、そのパブリッシャーを認証するための完全性検証の機能を提供することもできます。 名前空間の認証や、異なる名前空間の間のマッピングの問題については、さらなる調査が必要です。
NRSシステムのセキュリティー：
NRSでは、分散したスケーラブルなNRSシステムを構築するために、新しいエンティティー（たとえば、NRSサーバー）を展開する必要があります。 したがって、マッピングデータベースを維持するNRSサーバーなどのエンティティーは、無数の攻撃者からの悪意のあるリクエストを受信することで、サービス拒否攻撃や分散型サービス拒否攻撃の標的になる可能性があります。 さらに、NRSクライアントは一般に、他のネットワークドメインのNRSノードをある程度信頼する必要があり、悪意のあるエンティティーがこの通信に参加するのを防ぐために、それらの間の通信も安全に保護する必要があります。 潜在的なセキュリティーインシデントを明らかにしたり、悪意のあるインフラストラクチャーを発見したりするために、パッシブDNSのように、名前解決データの履歴を保存し、分析する必要があります。
NRSのプロトコルとメッセージのセキュリティー：
NRSシステムでは、名前登録、名前解決、レコードの更新に関連するNRSメッセージを生成、送信、受信するプロトコルを、適切なセキュリティーメカニズムによって保護すべきです。 正当なノードだけがNRSメッセージを開始し、読み取ることができるように、適切なセキュリティー対策を提供する必要があります。 これらのメッセージは、ネットワークを介して転送される際に権限のない者が操作できないように、完全性保護と認証のメカニズムによって保護する必要があります。 セキュリティーとプライバシーの両方に対するあらゆる脅威を阻止するために、これらのメッセージを暗号化するセキュリティー対策も開発すべきです。 IPネットワークやDNSのセキュリティー問題に類似した多数の問題が、ICNアーキテクチャー全体に影響を及ぼす可能性があります。 DNSのQNAME最小化のようなアプローチは、名前解決の処理においてプライバシーを保護するのに適しているでしょう。 したがって、NRSシステムだけでなくICNアーキテクチャー全体を保護するために、NRSシステムのためのアクセス可能性や認証などのセキュリティーメカニズム[RFC9138]を考慮すべきです。
