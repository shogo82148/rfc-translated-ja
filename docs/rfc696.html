RFC 696

Comments on IMP/HOST and HOST/IMP Protocol Changes

RFC 696

IMP/HostおよびHost/IMPプロトコルの変更に関するコメント

Abstract

概要

With reference to RFC's 687, 690, and 692 (NIC's 32564, 32699, and 32734, respectively) by D.C. Walden, J. Postel, and S. Wolfe (respectively), I would like to offer some observations relative to current international standards recommendations from working group 6.1 of the International Federation of Information Processing. In a meeting held last May at the NCC, this working group voted to present a recommendation to CCITT (International Consultative Committee on Telephony and Telegraphy of the International Telegraphics Union) for a standard packet (or DATAGRAM) header.

D.C. Walden、J. Postel、S. Wolfeによる（それぞれ）RFC 687、690、692（それぞれNIC 32564、32699、32734）に関連して、国際情報処理連合（International Federation of Information Processing）のワーキンググループ6.1による現在の国際標準の勧告に関していくつか所見を述べたいと思います。このワーキンググループは、去る5月にNCCで開催された会議で、標準のパケット（またはデータグラム（DATAGRAM））ヘッダーについての勧告をCCITT（国際電気通信連合（International Telegraphics Union）の国際電信電話諮問委員会（International Consultative Committee on Telephony and Telegraphy））に提出することを議決しました。

The proposed packet header format is meant to interface hosts to packet networks. It is not a header for Host-to-Host protocol, nor is it an IMP-to-IMP header. The bulk of the header is taken up with addressing space(96 bits!) since this will be compatible with the current maximum address space of the telephone system (14 digits).

提案されたパケットヘッダーのフォーマットは、ホストをパケットネットワークに接続するためのものです。Host-to-Hostプロトコルのためのヘッダーでも、IMP-to-IMPのヘッダーでもありません。ヘッダーの大部分はアドレス空間（96ビット！）が占めています。これは、電話システムの現在の最大アドレス空間（14桁）と互換性を持たせるためです。

LOCAL NETWORK FIELD - 4 bits
This field allows local networks to operate easily on multiple formats, since the 4 bits can be used in any fashion desired by the local network.
DATAGRAM FORMAT - 4 bits
This field could be used by ARPANET to contain "1001" binary, so as to maintain backward compatibility with the existing message leader format.
PACKET TYPE CODE - 8 bits
This could be used for the HOST/IMP and IMP/HOST code.
FACILITIES - 16 bits
These bits have not yet been specifically allocated. Some will no doubt be for international services (e.g., tracing at gateways between networks, accounting, class of service). It was the feeling of WG 6.1 members that some of these bits (e.g., 8) might be allocated to the originating network (or destination network) for its own use.
TEXT LENGTH - 16 bits
These bits count the number of octets in the text of the packet, not including octets in the header (which is fixed in length for any particular format).
DESTINATION ADDRESS - 48 bits [1]
These bits could be allocated in the following way: Destination Network Identifier - 8 bits; Destination Host Identifier - 8 bits; Destination IMP identifier - 16 bits; Reserved- 16 bits.
SOURCE ADDRESS - 48 bits
These bits would be used in a fashion similar to the destination address bits.
LOCAL NETWORK FIELD - 4ビット
この4ビットはローカルネットワークが望む任意の方法で使用できるため、このフィールドにより、ローカルネットワークは複数のフォーマットで容易に運用できます。
DATAGRAM FORMAT - 4ビット
既存のメッセージリーダーのフォーマットとの後方互換性を保つため、ARPANETはこのフィールドに2進数の「1001」を入れることができます。
PACKET TYPE CODE - 8ビット
これは、HOST/IMPおよびIMP/HOSTのコードに使用できます。
FACILITIES - 16ビット
これらのビットは、まだ具体的には割り当てられていません。そのうちのいくつかは、間違いなく国際的なサービス（たとえば、ネットワーク間のゲートウェイでの追跡、課金、サービスクラス）のためのものになるでしょう。WG 6.1のメンバーの感触としては、これらのビットのうちのいくつか（たとえば8ビット）を、送信元ネットワーク（または宛先ネットワーク）が独自に使用するために割り当ててもよいのではないか、というものでした。
TEXT LENGTH - 16ビット
これらのビットは、ヘッダー（特定のフォーマットについては長さが固定されています）のオクテットを含まない、パケットのテキストのオクテット数を数えます。
DESTINATION ADDRESS - 48ビット[1]
これらのビットは、次のように割り当てることができます。宛先ネットワーク識別子 - 8ビット、宛先ホスト識別子 - 8ビット、宛先IMP識別子 - 16ビット、予約 - 16ビット。
SOURCE ADDRESS - 48ビット
これらのビットは、宛先アドレスのビットと同様の方法で使用します。

The resulting packet is 144 bits long and adding the present 40-bit Host-to-Host header results in a total of 184 bits, which is not very pleasant. A temporary fix (until we can introduce a new NCP design) might be to squeeze out the reserved 16-bit fields in the source and destination address fields, giving 32 bits to carry the byte size and byte count information for the present Host/Host protocol. Alternatively, the length field of the packet header and one of the facilities flags (or a whole field) could be used to indicate byte size and byte count. Either idea would require some fairly substantial modification of existing NCP programs, so is probably not very palatable.

結果として得られるパケットの長さは144ビットであり、現在の40ビットのHost-to-Hostヘッダーを加えると合計184ビットになりますが、これはあまり好ましくありません。（新しいNCPの設計を導入できるまでの）一時的な修正として、送信元アドレスと宛先アドレスのフィールドにある予約済みの16ビットのフィールドを詰めて取り除き、現在のHost/Hostプロトコルのバイトサイズとバイト数の情報を運ぶための32ビットを確保することが考えられます。あるいは、パケットヘッダーの長さフィールドと、ファシリティーフラグのうちの1つ（またはフィールド全体）を使って、バイトサイズとバイト数を示すこともできます。どちらの案も、既存のNCPプログラムにかなり大幅な変更が必要になるため、おそらくあまり受け入れられないでしょう。

Another alternative would be to add a dummy byte after the 144th bit of header, followed by 40 bits of NCP header, giving a total length of message leader and NCP header of 192 bits, a number divisible by 12, 16, 24, 32, 48.

別の案としては、ヘッダーの144ビット目の後にダミーのバイトを追加し、その後に40ビットのNCPヘッダーを続けることが考えられます。そうすると、メッセージリーダーとNCPヘッダーの全長は192ビットになり、この数は12、16、24、32、48で割り切れます。

With respect to the proposed text length field, although bit lengths are the most flexible, it seems reasonable to admit that nearly all data transmission is done in 8-bit quantities, and therefore that bit lengths are, in fact, an unnecessary luxury. This is a weak argument when 36-bit and 32-bit machines must interface.

提案されたテキスト長フィールドに関しては、ビット長が最も柔軟ではあるものの、ほぼすべてのデータ伝送が8ビット単位で行われており、したがってビット長は実際には不必要なぜいたくであると認めるのが妥当だと思われます。ただし、36ビットのマシンと32ビットのマシンが相互に接続しなければならない場合には、これは弱い論拠です。
