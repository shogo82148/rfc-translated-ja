RFC 1648

Postmaster Convention for X.400 Operations

RFC 1648

X.400運用のためのpostmasterの慣習

Abstract

概要

Both STD 11, RFC 822 [1] and STD 3, RFC 1123 [2] (Host Requirements) require that the email address "postmaster" be supported at all hosts. This paper extends this concept to X.400 mail domains which have registered RFC 1327 mapping rules, and which therefore appear to have normal RFC822-style addresses.

STD 11、RFC 822 [1]とSTD 3、RFC 1123 [2]（ホスト要件）はいずれも、すべてのホストで電子メールアドレス「postmaster」をサポートすることを要求しています。この文書では、この考え方を、RFC 1327のマッピング規則を登録しており、そのため通常のRFC 822形式のアドレスを持つように見えるX.400メールドメインにまで拡張します。

Status of This Memo

このメモのステータス

This document specifies an Internet standards track protocol for the Internet community, and requests discussion and suggestions for improvements. Please refer to the current edition of the "Internet Official Protocol Standards" (STD 1) for the standardization state and status of this protocol. Distribution of this memo is unlimited.

この文書は、インターネットコミュニティーのためのインターネット標準化過程（Internet Standards Track）のプロトコルを規定し、改善のための議論と提案を求めるものです。このプロトコルの標準化の状態とステータスについては、「Internet Official Protocol Standards」（STD 1）の最新版を参照してください。このメモの配布は無制限です。

1. Postmaster Convention in RFC822

1. RFC 822におけるpostmasterの慣習

Operating a reliable, large-scale electronic mail (email) network requires cooperation between many mail managers and system administrators. As noted in RFC 822 [1], often mail or system managers need to be able to contact a responsible person at a remote host without knowing any specific user name or address at that host. For that reason, both RFC 822 and the Internet Host Requirements [2] require that the address "postmaster" be supported at every Internet host.

信頼性の高い大規模な電子メール（email）ネットワークを運用するには、多くのメール管理者とシステム管理者の協力が必要です。RFC 822 [1]で述べられているように、メール管理者やシステム管理者は、リモートホストの特定のユーザー名やアドレスを知らなくても、そのホストの責任者に連絡できる必要がしばしばあります。そのため、RFC 822とインターネットのホスト要件[2]はいずれも、すべてのインターネットホストでアドレス「postmaster」をサポートすることを要求しています。

2. Postmaster Convention and X.400

2. postmasterの慣習とX.400

However, RFC 822 is not the only email protocol being used in the Internet. Some Internet sites are also running the X.400 (1984) [3] and X.400 (1988) [4] email protocols. RFC 1327 specifies how to map between X.400 and RFC 822 addresses [5]. When mapping rules are used, addresses map cleanly between X.400 and RFC 822. In fact, it is impossible to determine by inspecting the address whether the recipient is an RFC 822 mail user or an X.400 mail user.

しかし、インターネットで使われている電子メールプロトコルはRFC 822だけではありません。インターネットのサイトの中には、X.400（1984）[3]やX.400（1988）[4]の電子メールプロトコルも運用しているところがあります。RFC 1327は、X.400とRFC 822のアドレスの間のマッピング方法を規定しています[5]。マッピング規則を使うと、アドレスはX.400とRFC 822の間できれいにマッピングされます。実際、アドレスを見ただけでは、受信者がRFC 822メールのユーザーなのかX.400メールのユーザーなのかを判別することはできません。

A paper by Rob Hagens and Alf Hansen describes an X.400 community known as the "Global Open MHS Community" (GO-MHS) [6]. Many mail domains in the GO-MHS Community have registered RFC 1327 mapping rules. Therefore, users in those domains have RFC 822-style email addresses, and these email domains are a logical extension of the RFC 822 Internet. It is impossible to tell by inspecting a user's address whether the user receives RFC 822 mail or X.400 mail.

Rob HagensとAlf Hansenの文書は、「Global Open MHS Community」（GO-MHS）[6]と呼ばれるX.400コミュニティーについて説明しています。GO-MHSコミュニティーの多くのメールドメインは、RFC 1327のマッピング規則を登録しています。そのため、それらのドメインのユーザーはRFC 822形式の電子メールアドレスを持っており、これらの電子メールドメインはRFC 822インターネットの論理的な拡張となっています。ユーザーのアドレスを見ただけでは、そのユーザーがRFC 822メールを受け取るのかX.400メールを受け取るのかはわかりません。

Since these addresses appear to be standard RFC 822 addresses, mail managers, mailing list managers, host administrators, and users expect to be able to simply send mail to "postmaster@domain" and having the message be delivered to a responsible party. When an RFC 1327 mapping rule exists, the X.400 address element corresponding to the left-hand-side "postmaster" is "Surname=Postmaster" (both 1984 and 1988). However, neither the X.400 protocols, North America X.400 Implementor's Agreements [7], nor the other regional X.400 implementor's agreements require that "Surname=Postmaster" and "CommonName=Postmaster" be supported. (Supporting these addresses is recommended in X.400 (1988)).

これらのアドレスは標準的なRFC 822アドレスに見えるため、メール管理者、メーリングリスト管理者、ホスト管理者、ユーザーは、単に「postmaster@domain」にメールを送れば、そのメッセージが責任者に届けられるものと期待します。RFC 1327のマッピング規則が存在する場合、左辺の「postmaster」に対応するX.400のアドレス要素は「Surname=Postmaster」です（1984年版と1988年版の両方）。しかし、X.400プロトコルも、北米のX.400実装者合意（Implementor's Agreements）[7]も、ほかの地域のX.400実装者合意も、「Surname=Postmaster」と「CommonName=Postmaster」のサポートを要求していません（これらのアドレスのサポートは、X.400（1988）では推奨されています）。

For mapped X.400 domains which do not support the postmaster address(es), this means that an address such as "user@some.place.zz" might be valid, yet mail to the corresponding address "postmaster@some.place.zz" fails. This is frustrating for remote administrators and users, and can prevent operational problems from being communicated and resolved. In this case, the desired seamless integration of the Internet RFC 822 mail world and the mapped X.400 domain has not been achieved.

これは、postmasterアドレスをサポートしていないマッピングされたX.400ドメインでは、「user@some.place.zz」のようなアドレスは有効であっても、対応するアドレス「postmaster@some.place.zz」へのメールは失敗するかもしれないということを意味します。これはリモートの管理者やユーザーにとって不満の種であり、運用上の問題が伝えられて解決されることを妨げるおそれがあります。この場合、インターネットのRFC 822メールの世界とマッピングされたX.400ドメインとの、望まれているシームレスな統合は達成されていません。

The X.400 mail managers participating in the Cosine MHS Project discussed this problem in a meeting in June 1992 [8]. The discussion recognized the need for supporting the postmaster address at any level of the address hierarchy where these are user addresses. However, the group only required supporting the postmaster address down to certain levels of the O/R Address tree. This approach solved part of the problem, but not all of it. A more complete solution is required.

Cosine MHSプロジェクトに参加しているX.400メール管理者は、1992年6月の会合でこの問題を議論しました[8]。この議論では、ユーザーアドレスが存在するアドレス階層のどのレベルでもpostmasterアドレスをサポートする必要があることが認識されました。しかし、このグループが要求したのは、O/Rアドレスツリーの特定のレベルまでpostmasterアドレスをサポートすることだけでした。このアプローチで問題の一部は解決しましたが、すべてではありませんでした。より完全な解決策が必要です。

3. Proposed Solution

3. 提案する解決策

To fully achieve the desired seamless integration of email domains for which RFC 1327 mapping rules have been defined, the following convention must be followed,

RFC 1327のマッピング規則が定義されている電子メールドメインの、望まれているシームレスな統合を完全に達成するには、次の慣習に従わなければなりません。

If there are any valid addresses of the form "user@domain", then the address "postmaster@domain" must also be valid.

「user@domain」という形式の有効なアドレスが1つでもあれば、アドレス「postmaster@domain」も有効でなければなりません。

To express this in terms of X.400: For every X.400 domain for which an RFC 1327 mapping rule exists, if any address of the form

これをX.400の用語で表すと次のようになります。RFC 1327のマッピング規則が存在するすべてのX.400ドメインについて、次の形式のアドレス

   Surname=User; <Other X.400 Address Elements>

   Surname=User; <Other X.400 Address Elements>

is a valid address, then the address

のいずれかが有効なアドレスであれば、次のアドレス

   Surname=Postmaster; <Same X.400 Address Elements>

   Surname=Postmaster; <Same X.400 Address Elements>

must also be a valid address. If the X.400 system is running X.400(1988), then the address

も有効なアドレスでなければなりません。X.400システムがX.400（1988）を運用している場合は、次のアドレス

   CommonName=Postmaster; <Same X.400 Address Elements>

   CommonName=Postmaster; <Same X.400 Address Elements>

must also be supported. (Note that CommonName=Postmaster will not be generated by RFC 1327 mappings, but it is recommended in the 1988 X.400 standard).

もサポートしなければなりません（CommonName=PostmasterはRFC 1327のマッピングでは生成されませんが、1988年版のX.400標準では推奨されていることに注意してください）。

To remain consistent with RFC 822, "Mail sent to that address is to be routed to a person responsible for the site's mail system or to a person with responsibility for general site operation." [9].

RFC 822との一貫性を保つため、「そのアドレスに送られたメールは、サイトのメールシステムの責任者か、サイトの運用全般の責任者に配送される」ものとします[9]。

3.1. Software Limitations

3.1. ソフトウェアの制限

If software is unable to support this requirement, it should be upgraded. X.400 software developers are strongly encouraged and requested to support forwarding mail to a centralized postmaster mailbox in products.

ソフトウェアがこの要件をサポートできない場合は、アップグレードすべきです。X.400ソフトウェアの開発者には、製品において、集中管理されたpostmasterメールボックスへのメール転送をサポートすることを強く推奨し、要請します。

It may be possible to support forwarding postmaster mail to a central mailbox in software packages which do not explicitly support it by applying work-around solutions. For example, some packages support creating a mailing list for "postmaster" which has one entry that points to the desired centralized postmaster mailbox. Alternatively, it may be possible to support a postmaster address using the X.400 Autoforwarding feature. The software package may also support rewriting the address in some other way.

集中管理されたメールボックスへのpostmasterメールの転送を明示的にサポートしていないソフトウェアパッケージでも、回避策を適用すればサポートできる場合があります。たとえば、パッケージによっては、目的の集中管理されたpostmasterメールボックスを指すエントリーを1つだけ持つ「postmaster」用のメーリングリストを作成できます。あるいは、X.400の自動転送（Autoforwarding）機能を使ってpostmasterアドレスをサポートできる場合もあります。ソフトウェアパッケージが、ほかの方法でアドレスの書き換えをサポートしている場合もあります。
