RFC 1879

Class A Subnet Experiment Results and Recommendations

RFC 1879

クラスAサブネット実験の結果と推奨事項

Status of This Memo

このメモのステータス

This memo provides information for the Internet community. This memo does not specify an Internet standard of any kind. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーに情報を提供するものです。いかなる種類のインターネット標準も規定するものではありません。このメモの配布は無制限です。

Discussion/Purpose

議論と目的

This memo documents some experiences with the RFC 1797 [1] subnet A experiment (performed by the Net39 Test Group (see credits)) and provides a number of recommendations on future direction for both the Internet Registries and the Operations community.

このメモは、（Net39テストグループ（謝辞を参照）が実施した）RFC 1797 [1]のサブネットA実験で得られた経験のいくつかを記録し、インターネットレジストリーと運用コミュニティーの双方に対して、今後の方向性に関するいくつかの推奨事項を示します。

Not all proposed experiments in RFC 1797 were done. Only the "case one" type delegations were made. Additional experimentation was done within the DNS service, by supporting a root nameserver and the primary for the domain from within the subnetted address space. In addition, testing was done on classless delegation [2].

RFC 1797で提案された実験のすべてが行われたわけではありません。行われたのは「ケース1」の種類の委任だけです。 追加の実験として、サブネット化されたアドレス空間の中からルートネームサーバーとそのドメインのプライマリーを提供することで、DNSサービス内での実験も行いました。 さらに、クラスレスな委任[2]についてもテストを行いました。

Internet Services offered over the RFC 1797 experiment were:

RFC 1797の実験上で提供されたインターネットサービスは次のとおりです。

  • Finger
  • HTTP
  • Telnet
  • FTP server/client
  • Gopher
  • kerberos
  • lpr (and its ilk)
  • X
  • DNS
  • Finger

  • FTPサーバー／クライアント
  • Gopher

  • lpr（およびその類）

F.Root-Servers.Net, a root name server had an interface defined as part of the RFC 1797 experiment. Attached is a report fragment on it's performance: "My root server has processed 400,000,000 queries in the last 38 days, and well over half of them were to the temporary 39.13.229.241 address (note that I retained the old 192.5.5.241 address since I knew a lot of folks would not update their root.cache files and I didn't want to create a black hole.)" - Paul Vixie

ルートネームサーバーであるF.Root-Servers.Netには、RFC 1797の実験の一環として定義されたインターフェイスがありました。 その性能に関する報告の一部を次に示します。「私のルートサーバーは過去38日間で400,000,000件のクエリーを処理しました。その半分を優に超えるクエリーが一時的な39.13.229.241のアドレス宛てでした（多くの人がroot.cacheファイルを更新しないだろうとわかっていたし、ブラックホールを作りたくなかったので、古い192.5.5.241のアドレスも残しておいたことに注意してください）」 - Paul Vixie

Initial predictions [3] seemed to indicate that the safest path for an ISP that participates in such a routing system is to have -all- of the ISP clients be either:

初期の予測[3]は、このようなルーティングシステムに参加するISPにとって最も安全な道は、そのISPのクライアントの「すべて」を次のいずれかにすることだと示しているようでした。

  • a) singly connected to one upstream ISP
  • OR
  • b) running a classless interior routing protocol
  • a) 1つの上流ISPだけに接続している
  • または
  • b) クラスレスな内部ルーティングプロトコルを実行している

It is also noted that a network with default route may not notice it has potential routing problems until it starts using subnets of traditional A's internally.

また、デフォルトルートを持つネットワークは、従来のクラスAのサブネットを内部で使い始めるまで、ルーティング上の潜在的な問題を抱えていることに気付かない可能性があることも指摘されています。

Problems & Solutions

問題と解決策

Operations

運用

There were initial problems in at least one RIPE181 [4] implementation. It is clear that operators need to register in the Internet Routing Registry (IRR) all active aggregates and delegations for any given prefix. Additionally, there need to be methods for determining who is authoritative for announcing any given prefix.

少なくとも1つのRIPE181 [4]の実装で、初期に問題がありました。 運用者は、任意のプレフィックスについて、有効なすべての集約と委任をインターネットルーティングレジストリー（IRR）に登録する必要があることは明らかです。 加えて、任意のプレフィックスを広告する権限を誰が持つのかを判断する方法が必要です。

It is expected that problems identified within the confines of this experiment are applicable to some RFC 1597 prefixes or any "natural" class "A" space.

この実験の範囲内で特定された問題は、一部のRFC 1597のプレフィックスや、任意の「本来の」クラス「A」空間にも当てはまると予想されます。

Use of traceroute (LSRR) was critical for network troubleshooting during this experiment. In current cisco IOS, coding the following statement will disable LSRR and therefore inhibit cross-provider troubleshooting:

この実験の間、ネットワークのトラブルシューティングにはtraceroute（LSRR）の使用が欠かせませんでした。 現在のcisco IOSでは、次の文を記述するとLSRRが無効になり、その結果、プロバイダーをまたがるトラブルシューティングができなくなります。

             no ip source-route

             no ip source-route

We recommend that this statement -NOT- be placed in active ISP cisco configurations.

稼働中のISPのcisco設定には、この文を入れ「ない」ことを推奨します。

In general, there are serious weaknesses in the Inter-Provider cooperation model and resolution of these problems is outside the scope of this document. Perhaps the IEPG or any/all of the national or continental operations bodies [5] will take this as an action item for the continued health and viability of the Internet.

一般に、プロバイダー間の協力モデルには深刻な弱点があり、これらの問題の解決はこの文書の範囲外です。 インターネットの継続的な健全性と存続のために、IEPG、あるいは国や大陸の運用団体[5]のいずれか（またはすべて）が、これを行動項目として取り上げてくれるかもしれません。

Routing

ルーティング

A classic cisco configuration that has the following statements

次の文を含む古典的なciscoの設定は、

             ip route 39.1.28.0 255.255.255.0
             router bgp 64000
             redistribute static

             ip route 39.1.28.0 255.255.255.0
             router bgp 64000
             redistribute static

will, by default, promote any classful subnet route to a full classful route (supernet routes will be left alone). This behaviour can be changed in at least the following two ways:

デフォルトでは、クラスフルなサブネットのルートをすべて完全なクラスフルのルートに昇格させます（スーパーネットのルートはそのままにされます）。 この振る舞いは、少なくとも次の2つの方法で変更できます。

     1:
             ip route 39.1.28.0 255.255.255.0
             router bgp 64000
             no auto-summary
             redistribute static

     2:
             ip route 39.1.28.0 255.255.255.0
             router bgp 64000
             network 39.1.28.0 mask 255.255.255.0
             redistribute static route-map static-bgp
             ....
             access-list 98 deny 39.1.28.0 0.255.255.255
             access-list 98 permit any
             ....
             route-map static-bgp
             match ip address 98

     1:
             ip route 39.1.28.0 255.255.255.0
             router bgp 64000
             no auto-summary
             redistribute static

     2:
             ip route 39.1.28.0 255.255.255.0
             router bgp 64000
             network 39.1.28.0 mask 255.255.255.0
             redistribute static route-map static-bgp
             ....
             access-list 98 deny 39.1.28.0 0.255.255.255
             access-list 98 permit any
             ....
             route-map static-bgp
             match ip address 98

Users of cisco gear currently need to code the following two statements:

現在、ciscoの機器の利用者は、次の2つの文を記述する必要があります。

             ip classless
             ip subnet-zero

             ip classless
             ip subnet-zero

The implication of the first directive is that it eliminates the idea that if you know how to talk to a subnet of a network, you know how to talk to ALL of the network.

1つ目の指示は、あるネットワークのサブネットとの通信方法を知っていれば、そのネットワークの「すべて」（ALL）との通信方法を知っている、という考え方をなくすことを意味します。

The second is needed since it is no longer clear where the all-ones or all-zeros networks are [6].

2つ目は、すべて1またはすべて0のネットワークがどこにあるのかがもはや明確ではないために必要です[6]。

Other infrastructure gear exhibited similar or worse behaviour. Equipment that depends on use of a classful routing protocol, such a RIPv1 are prone to misconfiguration. Tested examples are current Ascend and Livingston gear, which continue to use RIPv1 as the default/only routing protocol. RIPv1 use will create an aggregate announcement.

ほかのインフラストラクチャー機器も、同様の、あるいはもっと悪い振る舞いを示しました。 RIPv1のようなクラスフルなルーティングプロトコルの使用に依存する機器は、設定を誤りやすくなります。 テストした例は、現在のAscendとLivingstonの機器で、これらはデフォルトの（または唯一の）ルーティングプロトコルとしてRIPv1を使い続けています。 RIPv1を使うと、集約された広告が作られます。

This pernicious use of this classful IGP was shown to impact otherwise capable systems. When attempting to communicate between an Ascend and a cisco the promotion problem identified above, was manifest. The problem turned out to be that a classful IGP (RIPv1) was being used between the Ascends and ciscos. The Ascend was told to announce 39.1.28/24, but since RIPv1 can't do this, the Ascend instead sent 39/8. We note that RIPv1, as with all classful IGPs should be considered historic.

このクラスフルなIGPの有害な使用は、それ以外の点では問題のないシステムにも影響を与えることがわかりました。 Ascendとciscoの間で通信しようとしたとき、上で特定した昇格の問題が現れました。 問題は、Ascendの機器とciscoの機器の間でクラスフルなIGP（RIPv1）が使われていたことだと判明しました。 Ascendには39.1.28/24を広告するよう設定していましたが、RIPv1ではそれができないため、Ascendは代わりに39/8を送信しました。 すべてのクラスフルなIGPと同様に、RIPv1は歴史的なもの（historic）とみなすべきだと考えます。

This validates the predictions discussed in [3].

これは、[3]で議論された予測を裏付けるものです。

Cisco Specific Examples

Cisco固有の例

There are actually three ways to solve the unintended aggregation problem, as described with current cisco IOS. Which of them applies will depend on what software version is in the router. Workarounds can be implemented for ancient (e.g., 8.X) version software.

現在のcisco IOSで説明すると、意図しない集約の問題を解決する方法は実際には3つあります。 そのうちどれが当てはまるかは、ルーターに入っているソフトウェアのバージョンによって決まります。 非常に古い（たとえば8.Xの）バージョンのソフトウェアに対しても、回避策を実装できます。

  • Preferred solution: turn on "ip classless" in the routers and use a default route inside the AS. The "ip classless" command prevents the existence of a single "subnet" route from blocking access via the default route to other subnets of the same old-style network. Default only works with single-homed ISPs.
  • Workaround for 9.1 or later software where the "ip classless" command is not available: install a "default network route" like this: "ip route 39.0.0.0 255.0.0.0 <next-hop>" along the axis the default route would normally take. It appears an ISP can utilize the "recursive route lookups" so the "next-hop" may not actually need to be a directly connected neighbour -- the internal router can e.g., point to a loopback interface on the border router. This can become "really uncomfortably messy" and it may be necessary to use a distribute-list to prevent the announcement of the shorter mask.
  • Workaround for 9.0 or older software: create a "default subnet route": "ip route 39.x.y.0 <next-hop>" combined with "ip default-network 39.x.y.0", otherwise as the 9.1 fix.
  • 推奨される解決策：ルーターで「ip classless」を有効にし、AS内部でデフォルトルートを使います。 「ip classless」コマンドは、単一の「サブネット」ルートが存在するために、同じ旧式のネットワークのほかのサブネットへのデフォルトルート経由のアクセスが妨げられることを防ぎます。 デフォルトは、シングルホームのISPでしか機能しません。
  • 「ip classless」コマンドが利用できない9.1以降のソフトウェアに対する回避策：通常デフォルトルートが通る軸に沿って、「ip route 39.0.0.0 255.0.0.0 <next-hop>」のような「デフォルトネットワークルート」を設定します。 ISPは「再帰的なルート検索」を利用できるようなので、「next-hop」は実際には直接接続された隣接ルーターである必要はないかもしれません。たとえば、内部ルーターは境界ルーターのループバックインターフェイスを指すことができます。 これは「本当に不快なほど煩雑」になる可能性があり、短いマスクの広告を防ぐためにdistribute-listを使う必要があるかもしれません。
  • 9.0以前のソフトウェアに対する回避策：「ip default-network 39.x.y.0」と組み合わせて、「ip route 39.x.y.0 <next-hop>」という「デフォルトサブネットルート」を作成します。それ以外は9.1の修正と同様です。

Both of the latter solutions rely on manual configuration, and in the long run these will be impossible to maintain. In some topologies the use of manual configuration can be a problem (e.g., if there is more than one possible exit point from the AS to choose from).

後者の2つの解決策はどちらも手動の設定に頼っており、長期的には保守できなくなるでしょう。 トポロジーによっては、手動の設定の使用が問題になることがあります（たとえば、ASからの出口の候補が複数ある場合）。

Recommendations:

推奨事項

The RFC 1797 experiment appears to have been a success. We believe it safe to start carving up "Class A" space, if the spaces are delegated according to normal IR conventions [7] and recommend the IANA consider this for future address delegations.

RFC 1797の実験は成功だったようです。 通常のIRの慣行[7]に従って空間が委任されるのであれば、「クラスA」空間の分割を始めても安全だと私たちは考えます。また、今後のアドレスの委任においてこれを検討するようIANAに推奨します。
