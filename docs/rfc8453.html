RFC 8453

Framework for Abstraction and Control of TE Networks (ACTN)

RFC 8453

TEネットワークの抽象化と制御（ACTN）のためのフレームワーク

Abstract

概要

Traffic Engineered (TE) networks have a variety of mechanisms to facilitate the separation of the data plane and control plane. They also have a range of management and provisioning protocols to configure and activate network resources. These mechanisms represent key technologies for enabling flexible and dynamic networking. The term "Traffic Engineered network" refers to a network that uses any connection-oriented technology under the control of a distributed or centralized control plane to support dynamic provisioning of end-to-end connectivity.

トラフィックエンジニアリングされた（Traffic Engineered、TE）ネットワークには、データプレーンとコントロールプレーンの分離を容易にするさまざまなメカニズムがあります。また、ネットワークリソースを設定して有効化するための管理プロトコルやプロビジョニングプロトコルも各種あります。これらのメカニズムは、柔軟で動的なネットワーキングを可能にするための重要な技術です。「トラフィックエンジニアリングされたネットワーク」という用語は、エンドツーエンドの接続性の動的なプロビジョニングをサポートするために、分散型または集中型のコントロールプレーンの制御下で、何らかのコネクション指向の技術を使用するネットワークを指します。

Abstraction of network resources is a technique that can be applied to a single network domain or across multiple domains to create a single virtualized network that is under the control of a network operator or the customer of the operator that actually owns the network resources.

ネットワークリソースの抽象化は、単一のネットワークドメインに、または複数のドメインにまたがって適用できる手法であり、ネットワーク運用者、またはネットワークリソースを実際に所有する運用者の顧客の制御下にある単一の仮想化されたネットワークを作成します。

This document provides a framework for Abstraction and Control of TE Networks (ACTN) to support virtual network services and connectivity services.

この文書は、仮想ネットワークサービスと接続性サービスをサポートするための、TEネットワークの抽象化と制御（Abstraction and Control of TE Networks、ACTN）のフレームワークを提供します。

1. Introduction

1. はじめに

The term "Traffic Engineered network" refers to a network that uses any connection-oriented technology under the control of a distributed or centralized control plane to support dynamic provisioning of end-to-end connectivity. TE networks have a variety of mechanisms to facilitate the separation of data planes and control planes including distributed signaling for path setup and protection, centralized path computation for planning and traffic engineering, and a range of management and provisioning protocols to configure and activate network resources. These mechanisms represent key technologies for enabling flexible and dynamic networking. Some examples of networks that are in scope of this definition are optical, MPLS Transport Profile (MPLS-TP) [RFC5654], and MPLS-TE networks [RFC2702].

「トラフィックエンジニアリングされたネットワーク」という用語は、エンドツーエンドの接続性の動的なプロビジョニングをサポートするために、分散型または集中型のコントロールプレーンの制御下で、何らかのコネクション指向の技術を使用するネットワークを指します。TEネットワークには、データプレーンとコントロールプレーンの分離を容易にするさまざまなメカニズムがあります。たとえば、パスの設定と保護のための分散シグナリング、計画とトラフィックエンジニアリングのための集中型の経路計算、ネットワークリソースを設定して有効化するための各種の管理プロトコルやプロビジョニングプロトコルなどです。これらのメカニズムは、柔軟で動的なネットワーキングを可能にするための重要な技術です。この定義の範囲に含まれるネットワークの例としては、光ネットワーク、MPLS Transport Profile（MPLS-TP）ネットワーク[RFC5654]、MPLS-TEネットワーク[RFC2702]があります。

One of the main drivers for Software-Defined Networking (SDN) [RFC7149] is a decoupling of the network control plane from the data plane. This separation has been achieved for TE networks with the development of MPLS/GMPLS [RFC3945] and the Path Computation Element (PCE) [RFC4655]. One of the advantages of SDN is its logically centralized control regime that allows a global view of the underlying networks. Centralized control in SDN helps improve network resource utilization compared with distributed network control. For TE-based networks, a PCE may serve as a logically centralized path computation function.

ソフトウェア定義ネットワーキング（Software-Defined Networking、SDN）[RFC7149]の主な推進要因の1つは、ネットワークのコントロールプレーンをデータプレーンから切り離すことです。TEネットワークでは、MPLS/GMPLS[RFC3945]と経路計算要素（Path Computation Element、PCE）[RFC4655]の開発によって、この分離が実現されてきました。SDNの利点の1つは、論理的に集中化された制御体制により、基盤となるネットワークを全体的に見渡せることです。SDNにおける集中制御は、分散型のネットワーク制御と比べて、ネットワークリソースの利用効率の向上に役立ちます。TEベースのネットワークでは、PCEが論理的に集中化された経路計算機能の役割を果たすことができます。

This document describes a set of management and control functions used to operate one or more TE networks to construct virtual networks that can be presented to customers and that are built from abstractions of the underlying TE networks. For example, a link in the customer's network is constructed from a path or collection of paths in the underlying networks. We call this set of functions "Abstraction and Control of TE Networks" or "ACTN".

この文書は、1つ以上のTEネットワークを運用して、顧客に提示できる仮想ネットワーク、すなわち基盤となるTEネットワークの抽象化から構築される仮想ネットワークを構成するために使用する、一連の管理機能と制御機能について説明します。たとえば、顧客のネットワーク内のリンクは、基盤となるネットワーク内のパスまたはパスの集合から構成されます。この一連の機能を「TEネットワークの抽象化と制御（Abstraction and Control of TE Networks）」または「ACTN」と呼びます。

2. Overview

2. 概要

Three key aspects that need to be solved by SDN are:

SDNによって解決する必要がある3つの重要な側面は次のとおりです。

  • Separation of service requests from service delivery so that the configuration and operation of a network is transparent from the point of view of the customer but it remains responsive to the customer's services and business needs.
  • Network abstraction: As described in [RFC7926], abstraction is the process of applying policy to a set of information about a TE network to produce selective information that represents the potential ability to connect across the network. The process of abstraction presents the connectivity graph in a way that is independent of the underlying network technologies, capabilities, and topology so that the graph can be used to plan and deliver network services in a uniform way
  • Coordination of resources across multiple independent networks and multiple technology layers to provide end-to-end services regardless of whether or not the networks use SDN.
  • サービス要求をサービス提供から分離し、ネットワークの設定と運用が顧客の視点からは透過的でありながら、顧客のサービスやビジネス上のニーズには引き続き応えられるようにすること。
  • ネットワークの抽象化：[RFC7926]で説明されているように、抽象化とは、TEネットワークに関する一連の情報にポリシーを適用して、ネットワークをまたいで接続できる潜在的な能力を表す選択的な情報を生成するプロセスです。抽象化のプロセスは、基盤となるネットワークの技術、能力、トポロジーに依存しない形で接続性のグラフを提示し、そのグラフを使用して統一的な方法でネットワークサービスを計画して提供できるようにします
  • 複数の独立したネットワークと複数の技術層にまたがってリソースを協調させ、それらのネットワークがSDNを使用しているかどうかにかかわらず、エンドツーエンドのサービスを提供すること。

As networks evolve, the need to provide support for distinct services, separated service orchestration, and resource abstraction have emerged as key requirements for operators. In order to support multiple customers each with its own view of and control of the server network, a network operator needs to partition (or "slice") or manage sharing of the network resources. Network slices can be assigned to each customer for guaranteed usage, which is a step further than shared use of common network resources.

ネットワークの進化に伴い、個別のサービスのサポート、分離されたサービスオーケストレーション、リソースの抽象化を提供する必要性が、運用者にとっての重要な要件として浮上してきました。それぞれがサーバーネットワークに対する独自のビューと制御を持つ複数の顧客をサポートするために、ネットワーク運用者はネットワークリソースを分割（つまり「スライス」）するか、ネットワークリソースの共有を管理する必要があります。ネットワークスライスは、使用を保証するために各顧客に割り当てることができ、これは共通のネットワークリソースを共有して使用することより一歩進んだものです。

Furthermore, each network represented to a customer can be built from virtualization of the underlying networks so that, for example, a link in the customer's network is constructed from a path or collection of paths in the underlying network.

さらに、顧客に提示される各ネットワークは、基盤となるネットワークを仮想化して構築できます。たとえば、顧客のネットワーク内のリンクは、基盤となるネットワーク内のパスまたはパスの集合から構成されます。

ACTN can facilitate virtual network operation via the creation of a single virtualized network or a seamless service. This supports operators in viewing and controlling different domains (at any dimension: applied technology, administrative zones, or vendor-specific technology islands) and presenting virtualized networks to their customers.

ACTNは、単一の仮想化されたネットワークまたはシームレスなサービスを作成することで、仮想ネットワークの運用を容易にできます。これにより、運用者は、異なるドメイン（適用される技術、管理区域、ベンダー固有の技術の孤島など、あらゆる次元でのドメイン）を参照して制御し、仮想化されたネットワークを顧客に提示できるようになります。

The ACTN framework described in this document facilitates:

この文書で説明するACTNフレームワークは、次のことを容易にします。

  • Abstraction of the underlying network resources to higher-layer applications and customers [RFC7926].
  • Virtualization of particular underlying resources, whose selection criterion is the allocation of those resources to a particular customer, application, or service [ONF-ARCH].
  • TE Network slicing of infrastructure to meet specific customers' service requirements.
  • Creation of an abstract environment allowing operators to view and control multi-domain networks as a single abstract network.
  • The presentation to customers of networks as a virtual network via open and programmable interfaces.
  • 上位層のアプリケーションや顧客に対する、基盤となるネットワークリソースの抽象化[RFC7926]。
  • 基盤となる特定のリソースの仮想化。そのリソースの選択基準は、特定の顧客、アプリケーション、またはサービスへのリソースの割り当てです[ONF-ARCH]。
  • 特定の顧客のサービス要件を満たすための、インフラストラクチャーのTEネットワークスライシング。
  • 運用者がマルチドメインネットワークを単一の抽象ネットワークとして参照して制御できるようにする、抽象的な環境の作成。
  • オープンでプログラム可能なインターフェイスを介した、仮想ネットワークとしての顧客へのネットワークの提示。

2.1. Terminology

2.1. 用語

The following terms are used in this document. Some of them are newly defined, some others reference existing definitions:

この文書では次の用語を使用します。新しく定義するものもあれば、既存の定義を参照するものもあります。

Domain:
A domain as defined by [RFC4655] is "any collection of network elements within a common sphere of address management or path computation responsibility". Specifically, within this document we mean a part of an operator's network that is under common management (i.e., under shared operational management using the same instances of a tool and the same policies). Network elements will often be grouped into domains based on technology types, vendor profiles, and geographic proximity.
Abstraction:
This process is defined in [RFC7926].
TE Network Slicing:
In the context of ACTN, a TE network slice is a collection of resources that is used to establish a logically dedicated virtual network over one or more TE networks. TE network slicing allows a network operator to provide dedicated virtual networks for applications/customers over a common network infrastructure. The logically dedicated resources are a part of the larger common network infrastructures that are shared among various TE network slice instances, which are the end-to-end realization of TE network slicing, consisting of the combination of physically or logically dedicated resources.
Node:
A node is a vertex on the graph representation of a TE topology. In a physical network topology, a node corresponds to a physical network element (NE) such as a router. In an abstract network topology, a node (sometimes called an "abstract node") is a representation as a single vertex of one or more physical NEs and their connecting physical connections. The concept of a node represents the ability to connect from any access to the node (a link end) to any other access to that node, although "limited cross-connect capabilities" may also be defined to restrict this functionality. Network abstraction may be applied recursively, so a node in one topology may be created by applying abstraction to the nodes in the underlying topology.
Link:
A link is an edge on the graph representation of a TE topology. Two nodes connected by a link are said to be "adjacent" in the TE topology. In a physical network topology, a link corresponds to a physical connection. In an abstract network topology, a link (sometimes called an "abstract link") is a representation of the potential to connect a pair of points with certain TE parameters (see [RFC7926] for details). Network abstraction may be applied recursively, so a link in one topology may be created by applying abstraction to the links in the underlying topology.
Abstract Topology:
The topology of abstract nodes and abstract links presented through the process of abstraction by a lower-layer network for use by a higher-layer network.
Virtual Network (VN):

A VN is a network provided by a service provider to a customer for the customer to use in any way it wants as though it was a physical network. There are two views of a VN as follows:

  • The VN can be abstracted as a set of edge-to-edge links (a Type 1 VN). Each link is referred as a "VN member" and is formed as an end-to-end tunnel across the underlying networks. Such tunnels may be constructed by recursive slicing or abstraction of paths in the underlying networks and can encompass edge points of the customer's network, access links, intra-domain paths, and inter-domain links.
  • The VN can also be abstracted as a topology of virtual nodes and virtual links (a Type 2 VN). The operator needs to map the VN to actual resource assignment, which is known as "virtual network embedding". The nodes in this case include physical endpoints, border nodes, and internal nodes as well as abstracted nodes. Similarly, the links include physical access links, inter-domain links, and intra-domain links as well as abstract links.

Clearly, a Type 1 VN is a special case of a Type 2 VN.

Access link:
A link between a customer node and an operator node.
Inter-domain link:
A link between domains under distinct management administration.
Access Point (AP):
An AP is a logical identifier shared between the customer and the operator used to identify an access link. The AP is used by the customer when requesting a Virtual Network Service (VNS). Note that the term "TE Link Termination Point" defined in [TE-TOPO] describes the endpoints of links, while an AP is a common identifier for the link itself.
VN Access Point (VNAP):
A VNAP is the binding between an AP and a given VN.
Server Network:
As defined in [RFC7926], a server network is a network that provides connectivity for another network (the Client Network) in a client-server relationship.
ドメイン（Domain）：
[RFC4655]で定義されているドメインとは、「アドレス管理または経路計算の責任の共通範囲内にあるネットワーク要素の任意の集合」です。具体的には、この文書では、共通の管理下（つまり、同じツールのインスタンスと同じポリシーを使用する共有の運用管理下）にある運用者のネットワークの一部を意味します。ネットワーク要素は、技術の種類、ベンダーのプロファイル、地理的な近さに基づいてドメインにグループ化されることがよくあります。
抽象化（Abstraction）：
このプロセスは[RFC7926]で定義されています。
TEネットワークスライシング（TE Network Slicing）：
ACTNの文脈では、TEネットワークスライスとは、1つ以上のTEネットワーク上に論理的に専用の仮想ネットワークを確立するために使用されるリソースの集合です。TEネットワークスライシングにより、ネットワーク運用者は、共通のネットワークインフラストラクチャー上でアプリケーションや顧客に専用の仮想ネットワークを提供できます。論理的に専用のリソースは、さまざまなTEネットワークスライスインスタンスの間で共有される、より大きな共通のネットワークインフラストラクチャーの一部です。TEネットワークスライスインスタンスは、TEネットワークスライシングをエンドツーエンドで実現したものであり、物理的または論理的に専用のリソースの組み合わせで構成されます。
ノード（Node）：
ノードとは、TEトポロジーをグラフで表現したときの頂点です。物理ネットワークトポロジーでは、ノードはルーターなどの物理的なネットワーク要素（network element、NE）に対応します。抽象ネットワークトポロジーでは、ノード（「抽象ノード」と呼ばれることもあります）は、1つ以上の物理的なNEとそれらを接続する物理的な接続を、単一の頂点として表現したものです。ノードの概念は、ノードへの任意のアクセス（リンクの端）から、そのノードへの他の任意のアクセスへ接続できる能力を表しますが、この機能を制限するために「限定的なクロスコネクト能力」を定義することもできます。ネットワークの抽象化は再帰的に適用できるため、あるトポロジー内のノードは、基盤となるトポロジー内のノードに抽象化を適用して作成できます。
リンク（Link）：
リンクとは、TEトポロジーをグラフで表現したときの辺です。リンクで接続された2つのノードは、TEトポロジーにおいて「隣接している」といいます。物理ネットワークトポロジーでは、リンクは物理的な接続に対応します。抽象ネットワークトポロジーでは、リンク（「抽象リンク」と呼ばれることもあります）は、特定のTEパラメーターで2点間を接続できる可能性を表現したものです（詳細は[RFC7926]を参照）。ネットワークの抽象化は再帰的に適用できるため、あるトポロジー内のリンクは、基盤となるトポロジー内のリンクに抽象化を適用して作成できます。
抽象トポロジー（Abstract Topology）：
上位層のネットワークが使用するために、下位層のネットワークによる抽象化のプロセスを通じて提示される、抽象ノードと抽象リンクのトポロジー。
仮想ネットワーク（Virtual Network、VN）：

VNとは、サービスプロバイダーが顧客に提供するネットワークであり、顧客はそれを物理ネットワークであるかのように任意の方法で使用できます。VNには、次のような2つの見方があります。

  • VNは、エッジツーエッジのリンクの集合として抽象化できます（タイプ1 VN）。各リンクは「VNメンバー」と呼ばれ、基盤となるネットワークをまたぐエンドツーエンドのトンネルとして形成されます。このようなトンネルは、基盤となるネットワーク内のパスを再帰的にスライスまたは抽象化して構築でき、顧客のネットワークのエッジポイント、アクセスリンク、ドメイン内パス、ドメイン間リンクを含むことができます。
  • VNは、仮想ノードと仮想リンクのトポロジーとして抽象化することもできます（タイプ2 VN）。運用者はVNを実際のリソース割り当てにマッピングする必要があり、これは「仮想ネットワーク埋め込み」として知られています。この場合のノードには、物理的なエンドポイント、境界ノード、内部ノードのほか、抽象化されたノードも含まれます。同様に、リンクには、物理的なアクセスリンク、ドメイン間リンク、ドメイン内リンクのほか、抽象リンクも含まれます。

明らかに、タイプ1 VNはタイプ2 VNの特殊な場合です。

アクセスリンク（Access link）：
顧客のノードと運用者のノードの間のリンク。
ドメイン間リンク（Inter-domain link）：
別々の管理主体の下にあるドメイン間のリンク。
アクセスポイント（Access Point、AP）：
APとは、アクセスリンクを識別するために使用される、顧客と運用者の間で共有される論理的な識別子です。APは、顧客が仮想ネットワークサービス（Virtual Network Service、VNS）を要求するときに使用されます。[TE-TOPO]で定義されている「TEリンク終端点（TE Link Termination Point）」という用語はリンクのエンドポイントを表すのに対し、APはリンク自体の共通の識別子であることに注意してください。
VNアクセスポイント（VN Access Point、VNAP）：
VNAPとは、APと特定のVNとの間のバインディングです。
サーバーネットワーク（Server Network）：
[RFC7926]で定義されているように、サーバーネットワークとは、クライアントサーバー関係において、別のネットワーク（クライアントネットワーク）に接続性を提供するネットワークです。

2.2. VNS Model of ACTN

2.2. ACTNのVNSモデル

A Virtual Network Service (VNS) is the service agreement between a customer and operator to provide a VN. When a VN is a simple connectivity between two points, the difference between VNS and connectivity service becomes blurred. There are three types of VNSs defined in this document.

仮想ネットワークサービス（Virtual Network Service、VNS）とは、VNを提供するための顧客と運用者の間のサービス契約です。VNが2点間の単純な接続性である場合、VNSと接続性サービスの違いはあいまいになります。この文書では、3種類のVNSを定義します。

  • Type 1 VNS refers to a VNS in which the customer is allowed to create and operate a Type 1 VN.
  • Type 2a and 2b VNS refer to VNSs in which the customer is allowed to create and operates a Type 2 VN. With a Type 2a VNS, the VN is statically created at service configuration time, and the customer is not allowed to change the topology (e.g., by adding or deleting abstract nodes and links). A Type 2b VNS is the same as a Type 2a VNS except that the customer is allowed to make dynamic changes to the initial topology created at service configuration time.
  • タイプ1 VNSとは、顧客がタイプ1 VNを作成して運用することを許可されたVNSを指します。
  • タイプ2a VNSとタイプ2b VNSとは、顧客がタイプ2 VNを作成して運用することを許可されたVNSを指します。タイプ2a VNSでは、VNはサービスの設定時に静的に作成され、顧客はトポロジーを変更すること（たとえば、抽象ノードや抽象リンクを追加または削除すること）を許可されません。タイプ2b VNSは、サービスの設定時に作成された初期トポロジーに対して顧客が動的な変更を加えることを許可されている点を除いて、タイプ2a VNSと同じです。

VN Operations are functions that a customer can exercise on a VN depending on the agreement between the customer and the operator.

VN操作とは、顧客と運用者の間の合意に応じて、顧客がVNに対して実行できる機能です。

  • VN Creation allows a customer to request the instantiation of a VN. This could be through offline preconfiguration or through dynamic requests specifying attributes to a Service Level Agreement (SLA) to satisfy the customer's objectives.
  • Dynamic Operations allow a customer to modify or delete the VN. The customer can further act upon the virtual network to create/modify/delete virtual links and nodes. These changes will result in subsequent tunnel management in the operator's networks.
  • VN作成により、顧客はVNのインスタンス化を要求できます。これは、オフラインでの事前設定によって行うことも、顧客の目的を満たすためにサービスレベル合意（Service Level Agreement、SLA）に対する属性を指定する動的な要求によって行うこともできます。
  • 動的操作により、顧客はVNを変更または削除できます。顧客はさらに、仮想ネットワークに対して操作を行い、仮想リンクや仮想ノードを作成、変更、削除できます。これらの変更は、その後の運用者のネットワークにおけるトンネル管理につながります。

There are three key entities in the ACTN VNS model:

ACTNのVNSモデルには、次の3つの重要なエンティティーがあります。

  • Customers
  • Service Providers
  • Network Operators
  • 顧客
  • サービスプロバイダー
  • ネットワーク運用者

These entities are related in a three tier model as shown in Figure 1.

これらのエンティティーは、図1に示すように3層モデルで関係しています。

The commercial roles of these entities are described in the following sections.

これらのエンティティーの商業上の役割については、以降のセクションで説明します。

2.2.1. Customers

2.2.1. 顧客

Basic customers include fixed residential users, mobile users, and small enterprises. Each requires a small amount of resources and is characterized by steady requests (relatively time invariant). Basic customers do not modify their services themselves: if a service change is needed, it is performed by the provider as a proxy.

基本顧客には、固定回線の住宅ユーザー、モバイルユーザー、小規模企業が含まれます。各基本顧客が必要とするリソースは少量であり、安定した（時間的に比較的変化しない）要求が特徴です。基本顧客は自らサービスを変更しません。サービスの変更が必要な場合は、プロバイダーが代理として実行します。

Advanced customers include enterprises and governments. Such customers ask for both point-to point and multipoint connectivity with high resource demands varying significantly in time. This is one of the reasons why a bundled service offering is not enough, and it is desirable to provide each advanced customer with a customized VNS. Advanced customers may also have the ability to modify their service parameters within the scope of their virtualized environments. The primary focus of ACTN is Advanced Customers.

高度な顧客には、企業や政府が含まれます。このような顧客は、時間とともに大きく変動する高いリソース需要を伴う、ポイントツーポイントとマルチポイントの両方の接続性を求めます。これは、バンドルされたサービスの提供では不十分であり、各高度な顧客にカスタマイズされたVNSを提供することが望ましい理由の1つです。高度な顧客は、仮想化された環境の範囲内でサービスパラメーターを変更する能力を持つこともあります。ACTNが主に対象とするのは高度な顧客です。

As customers are geographically spread over multiple network operator domains, they have to interface to multiple operators and may have to support multiple virtual network services with different underlying objectives set by the network operators. To enable these customers to support flexible and dynamic applications, they need to control their allocated virtual network resources in a dynamic fashion; that means that they need a view of the topology that spans all of the network operators. Customers of a given service provider can, in turn, offer a service to other customers in a recursive way.

顧客は地理的に複数のネットワーク運用者のドメインにまたがって分布しているため、複数の運用者とやり取りする必要があり、ネットワーク運用者が設定した異なる基本目的を持つ複数の仮想ネットワークサービスをサポートしなければならない場合があります。このような顧客が柔軟で動的なアプリケーションをサポートできるようにするためには、顧客は割り当てられた仮想ネットワークリソースを動的に制御する必要があります。つまり、すべてのネットワーク運用者にまたがるトポロジーのビューが必要です。特定のサービスプロバイダーの顧客は、今度は再帰的に、他の顧客にサービスを提供することができます。

2.2.2. Service Providers

2.2.2. サービスプロバイダー

In the scope of ACTN, service providers deliver VNSs to their customers. Service providers may or may not own physical network resources (i.e., may or may not be network operators as described in Section 2.2.3). When a service provider is the same as the network operator, the case is similar to existing VPN models applied to a single operator (although it may be hard to use this approach when the customer spans multiple independent network operator domains).

ACTNの範囲では、サービスプロバイダーはVNSを顧客に提供します。サービスプロバイダーは、物理的なネットワークリソースを所有している場合もあれば、所有していない場合もあります（つまり、セクション2.2.3で説明するネットワーク運用者である場合もあれば、そうでない場合もあります）。サービスプロバイダーがネットワーク運用者と同じである場合、その状況は、単一の運用者に適用される既存のVPNモデルに似ています（ただし、顧客が複数の独立したネットワーク運用者のドメインにまたがる場合には、このアプローチを使用するのは難しいことがあります）。

When network operators supply only infrastructure, while distinct service providers interface with the customers, the service providers are themselves customers of the network infrastructure operators. One service provider may need to keep multiple independent network operators because its end users span geographically across multiple network operator domains. In some cases, a service provider is also a network operator when it owns network infrastructure on which service is provided.

ネットワーク運用者はインフラストラクチャーのみを提供し、別個のサービスプロバイダーが顧客とやり取りする場合、サービスプロバイダー自身がネットワークインフラストラクチャー運用者の顧客になります。あるサービスプロバイダーは、そのエンドユーザーが地理的に複数のネットワーク運用者のドメインにまたがっているため、複数の独立したネットワーク運用者を抱える必要がある場合があります。場合によっては、サービスプロバイダーは、サービスを提供するためのネットワークインフラストラクチャーを所有しているときに、ネットワーク運用者でもあります。

2.2.3. Network Operators

2.2.3. ネットワーク運用者

Network operators are the infrastructure operators that provision the network resources and provide network resources to their customers. The layered model described in this architecture separates the concerns of network operators and customers, with service providers acting as aggregators of customer requests.

ネットワーク運用者とは、ネットワークリソースをプロビジョニングし、ネットワークリソースを顧客に提供するインフラストラクチャー運用者です。このアーキテクチャーで説明する階層化モデルは、ネットワーク運用者と顧客の関心事を分離し、サービスプロバイダーが顧客の要求の集約者として振る舞います。

3. ACTN Base Architecture

3. ACTNの基本アーキテクチャー

This section provides a high-level model of ACTN, showing the interfaces and the flow of control between components.

このセクションでは、ACTNの高レベルのモデルを示し、コンポーネント間のインターフェイスと制御の流れを示します。

The ACTN architecture is based on a three-tier reference model and allows for hierarchy and recursion. The main functionalities within an ACTN system are:

ACTNアーキテクチャーは3層の参照モデルに基づいており、階層と再帰を可能にします。ACTNシステム内の主な機能は次のとおりです。

  • Multi-domain coordination: This function oversees the specific aspects of different domains and builds a single abstracted end-to-end network topology in order to coordinate end-to-end path computation and path/service provisioning. Domain sequence path calculation/determination is also a part of this function.
  • Abstraction: This function provides an abstracted view of the underlying network resources for use by the customer -- a customer may be the client or a higher-level controller entity. This function includes network path computation based on customer-service-connectivity request constraints, path computation based on the global network-wide abstracted topology, and the creation of an abstracted view of network resources allocated to each customer. These operations depend on customer-specific network objective functions and customer traffic profiles.
  • Customer mapping/translation: This function is to map customer requests/commands into network provisioning requests that can be sent from the Multi-Domain Service Coordinator (MDSC) to the Provisioning Network Controller (PNC) according to business policies provisioned statically or dynamically at the Operations Support System (OSS) / Network Management System (NMS). Specifically, it provides mapping and translation of a customer's service request into a set of parameters that are specific to a network type and technology such that network configuration process is made possible.
  • Virtual service coordination: This function translates information that is customer service related into virtual network service operations in order to seamlessly operate virtual networks while meeting a customer's service requirements. In the context of ACTN, service/virtual service coordination includes a number of service orchestration functions such as multi-destination load-balancing and guarantees of service quality. It also includes notifications for service fault and performance degradation and so forth.
  • マルチドメイン協調：この機能は、異なるドメインの固有の側面を監督し、エンドツーエンドの経路計算とパス／サービスのプロビジョニングを協調させるために、単一の抽象化されたエンドツーエンドのネットワークトポロジーを構築します。ドメインシーケンスのパスの計算／決定も、この機能の一部です。
  • 抽象化：この機能は、顧客が使用するための、基盤となるネットワークリソースの抽象化されたビューを提供します。顧客は、クライアントであることも、上位レベルのコントローラーエンティティーであることもあります。この機能には、顧客のサービス接続性の要求の制約に基づくネットワークの経路計算、ネットワーク全体のグローバルな抽象化されたトポロジーに基づく経路計算、各顧客に割り当てられたネットワークリソースの抽象化されたビューの作成が含まれます。これらの操作は、顧客固有のネットワークの目的関数と顧客のトラフィックプロファイルに依存します。
  • 顧客マッピング／変換：この機能は、運用支援システム（Operations Support System、OSS）／ネットワーク管理システム（Network Management System、NMS）で静的または動的にプロビジョニングされたビジネスポリシーに従って、顧客の要求／コマンドを、マルチドメインサービスコーディネーター（Multi-Domain Service Coordinator、MDSC）からプロビジョニングネットワークコントローラー（Provisioning Network Controller、PNC）に送信できるネットワークプロビジョニング要求にマッピングするものです。具体的には、ネットワーク設定のプロセスを可能にするために、顧客のサービス要求を、ネットワークの種類と技術に固有の一連のパラメーターにマッピングして変換します。
  • 仮想サービス協調：この機能は、顧客の要件を満たしながら仮想ネットワークをシームレスに運用するために、顧客のサービスに関連する情報を仮想ネットワークサービスの操作に変換します。ACTNの文脈では、サービス／仮想サービス協調には、マルチデスティネーションの負荷分散やサービス品質の保証など、多数のサービスオーケストレーション機能が含まれます。また、サービスの障害や性能の劣化などの通知も含まれます。

ACTNの基本アーキテクチャーは、3種類のコントローラーと、それらのコントローラー間の対応するインターフェイスを定義します。図2には、次の種類のコントローラーが示されています。

3.1. Customer Network Controller

3.1. 顧客ネットワークコントローラー

A Customer Network Controller (CNC) is responsible for communicating a customer's VNS requirements to the network operator over the CNC-MDSC Interface (CMI). It has knowledge of the endpoints associated with the VNS (expressed as APs), the service policy, and other QoS information related to the service.

顧客ネットワークコントローラー（Customer Network Controller、CNC）は、CNC-MDSCインターフェイス（CNC-MDSC Interface、CMI）を介して、顧客のVNS要件をネットワーク運用者に伝える役割を担います。CNCは、VNSに関連付けられたエンドポイント（APとして表現されます）、サービスポリシー、そのサービスに関連するその他のQoS情報を把握しています。

As the CNC directly interfaces with the applications, it understands multiple application requirements and their service needs. The capability of a CNC beyond its CMI role is outside the scope of ACTN and may be implemented in different ways. For example, the CNC may, in fact, be a controller or part of a controller in the customer's domain, or the CNC functionality could also be implemented as part of a service provider's portal.

CNCはアプリケーションと直接やり取りするため、複数のアプリケーションの要件とそのサービスのニーズを理解しています。CMIの役割を超えるCNCの能力はACTNの範囲外であり、さまざまな方法で実装される可能性があります。たとえば、CNCは実際には顧客のドメインにあるコントローラーまたはコントローラーの一部であることもあれば、CNCの機能がサービスプロバイダーのポータルの一部として実装されることもあります。

3.2. Multi-Domain Service Coordinator

3.2. マルチドメインサービスコーディネーター

A Multi-Domain Service Coordinator (MDSC) is a functional block that implements all of the ACTN functions listed in Section 3 and described further in Section 4.2. Two functions of the MDSC, namely, multi-domain coordination and virtualization/abstraction are referred to as network-related functions; whereas the other two functions, namely, customer mapping/translation and virtual service coordination, are referred to as service-related functions. The MDSC sits at the center of the ACTN model between the CNC that issues connectivity requests and the Provisioning Network Controllers (PNCs) that manage the network resources. The key point of the MDSC (and of the whole ACTN framework) is detaching the network and service control from underlying technology to help the customer express the network as desired by business needs. The MDSC envelopes the instantiation of the right technology and network control to meet business criteria. In essence, it controls and manages the primitives to achieve functionalities as desired by the CNC.

マルチドメインサービスコーディネーター（Multi-Domain Service Coordinator、MDSC）は、セクション3に列挙し、セクション4.2でさらに説明するACTNの機能をすべて実装する機能ブロックです。MDSCの機能のうち2つ、すなわちマルチドメイン協調と仮想化／抽象化はネットワーク関連機能と呼ばれ、他の2つの機能、すなわち顧客マッピング／変換と仮想サービス協調はサービス関連機能と呼ばれます。MDSCは、接続性の要求を発行するCNCと、ネットワークリソースを管理するプロビジョニングネットワークコントローラー（Provisioning Network Controller、PNC）との間で、ACTNモデルの中心に位置します。MDSC（およびACTNフレームワーク全体）の要点は、ネットワークとサービスの制御を基盤となる技術から切り離し、顧客がビジネス上のニーズに応じて望むとおりにネットワークを表現できるよう支援することです。MDSCは、ビジネス上の基準を満たすために、適切な技術とネットワーク制御のインスタンス化を包み込みます。本質的に、MDSCは、CNCが望む機能を実現するためのプリミティブを制御し、管理します。

In order to allow for multi-domain coordination, a 1:N relationship must be allowed between MDSCs and PNCs.

マルチドメイン協調を可能にするために、MDSCとPNCの間には1:Nの関係が許されなければなりません。

In addition to that, it could also be possible to have an M:1 relationship between MDSCs and PNCs to allow for network-resource partitioning/sharing among different customers that are not necessarily connected to the same MDSC (e.g., different service providers) but that are all using the resources of a common network infrastructure operator.

それに加えて、MDSCとPNCの間にM:1の関係を持たせることも可能です。これにより、必ずしも同じMDSCに接続されているわけではない（たとえば、異なるサービスプロバイダーである）が、すべてが共通のネットワークインフラストラクチャー運用者のリソースを使用している異なる顧客の間で、ネットワークリソースを分割／共有できるようになります。

3.3. Provisioning Network Controller

3.3. プロビジョニングネットワークコントローラー

The Provisioning Network Controller (PNC) oversees configuring the network elements, monitoring the topology (physical or virtual) of the network, and collecting information about the topology (either raw or abstracted).

プロビジョニングネットワークコントローラー（Provisioning Network Controller、PNC）は、ネットワーク要素の設定、ネットワークの（物理的または仮想的な）トポロジーの監視、トポロジーに関する（生の、または抽象化された）情報の収集を監督します。

The PNC functions can be implemented as part of an SDN domain controller, a Network Management System (NMS), an Element Management System (EMS), an active PCE-based controller [RFC8283], or any other means to dynamically control a set of nodes that implements a northbound interface from the standpoint of the nodes (which is out of the scope of this document). A PNC domain includes all the resources under the control of a single PNC. It can be composed of different routing domains and administrative domains, and the resources may come from different layers. The interconnection between PNC domains is illustrated in Figure 3.

PNCの機能は、SDNドメインコントローラー、ネットワーク管理システム（Network Management System、NMS）、要素管理システム（Element Management System、EMS）、アクティブなPCEベースのコントローラー[RFC8283]の一部として実装することも、ノードの観点からノースバウンドインターフェイスを実装する一連のノードを動的に制御する他の任意の手段（これはこの文書の範囲外です）の一部として実装することもできます。PNCドメインには、単一のPNCの制御下にあるすべてのリソースが含まれます。PNCドメインは、異なるルーティングドメインや管理ドメインで構成されることがあり、リソースは異なる層から提供されることがあります。PNCドメイン間の相互接続を図3に示します。

3.4. ACTN Interfaces

3.4. ACTNのインターフェイス

Direct customer control of transport network elements and virtualized services is not a viable proposition for network operators due to security and policy concerns. Therefore, the network has to provide open, programmable interfaces, through which customer applications can create, replace, and modify virtual network resources and services in an interactive, flexible, and dynamic fashion.

セキュリティーとポリシー上の懸念から、トランスポートネットワーク要素や仮想化されたサービスを顧客が直接制御することは、ネットワーク運用者にとって実行可能な提案ではありません。したがって、ネットワークは、顧客のアプリケーションが対話的、柔軟、かつ動的な方法で仮想ネットワークリソースとサービスを作成、置換、変更できる、オープンでプログラム可能なインターフェイスを提供する必要があります。

Three interfaces exist in the ACTN architecture as shown in Figure 2.

図2に示すように、ACTNアーキテクチャーには3つのインターフェイスが存在します。

  • CMI: The CNC-MDSC Interface (CMI) is an interface between a CNC and an MDSC. The CMI is a business boundary between customer and network operator. It is used to request a VNS for an application. All service-related information is conveyed over this interface (such as the VNS type, topology, bandwidth, and service constraints). Most of the information over this interface is agnostic of the technology used by network operators, but there are some cases (e.g., access link configuration) where it is necessary to specify technology-specific details.
  • MPI: The MDSC-PNC Interface (MPI) is an interface between an MDSC and a PNC. It communicates requests for new connectivity or for bandwidth changes in the physical network. In multi-domain environments, the MDSC needs to communicate with multiple PNCs, each responsible for control of a domain. The MPI presents an abstracted topology to the MDSC hiding technology-specific aspects of the network and hiding topology according to policy.
  • SBI: The Southbound Interface (SBI) is out of scope of ACTN. Many different SBIs have been defined for different environments, technologies, standards organizations, and vendors. It is shown in Figure 3 for reference reason only.
  • CMI：CNC-MDSCインターフェイス（CNC-MDSC Interface、CMI）は、CNCとMDSCの間のインターフェイスです。CMIは、顧客とネットワーク運用者の間のビジネス上の境界です。CMIは、アプリケーションのためにVNSを要求するために使用されます。サービスに関連するすべての情報（VNSの種類、トポロジー、帯域幅、サービスの制約など）が、このインターフェイスを介して伝達されます。このインターフェイスを介した情報のほとんどは、ネットワーク運用者が使用する技術に依存しませんが、技術固有の詳細を指定する必要がある場合（たとえば、アクセスリンクの設定）もあります。
  • MPI：MDSC-PNCインターフェイス（MDSC-PNC Interface、MPI）は、MDSCとPNCの間のインターフェイスです。MPIは、物理ネットワークにおける新しい接続性や帯域幅の変更の要求を伝達します。マルチドメイン環境では、MDSCは複数のPNCと通信する必要があり、それぞれのPNCが1つのドメインの制御を担います。MPIは、ネットワークの技術固有の側面を隠し、ポリシーに従ってトポロジーを隠した、抽象化されたトポロジーをMDSCに提示します。
  • SBI：サウスバウンドインターフェイス（Southbound Interface、SBI）はACTNの範囲外です。さまざまな環境、技術、標準化団体、ベンダーに向けて、多くの異なるSBIが定義されています。SBIは参照のためだけに図3に示しています。

4. Advanced ACTN Architectures

4. ACTNの高度なアーキテクチャー

This section describes advanced configurations of the ACTN architecture.

このセクションでは、ACTNアーキテクチャーの高度な構成について説明します。

4.1. MDSC Hierarchy

4.1. MDSCの階層

A hierarchy of MDSCs can be foreseen for many reasons, among which are scalability, administrative choices, or putting together different layers and technologies in the network. In the case where there is a hierarchy of MDSCs, we introduce the terms "higher-level MDSC" (MDSC-H) and "lower-level MDSC" (MDSC-L). The interface between them is a recursion of the MPI. An implementation of an MDSC-H makes provisioning requests as normal using the MPI, but an MDSC-L must be able to receive requests as normal at the CMI and also at the MPI. The hierarchy of MDSCs can be seen in Figure 4.

MDSCの階層は、スケーラビリティー、管理上の選択、ネットワーク内の異なる層や技術の統合など、多くの理由から想定できます。MDSCの階層がある場合のために、「上位MDSC（higher-level MDSC）」（MDSC-H）と「下位MDSC（lower-level MDSC）」（MDSC-L）という用語を導入します。両者の間のインターフェイスは、MPIの再帰です。MDSC-Hの実装は、MPIを使用して通常どおりにプロビジョニング要求を行いますが、MDSC-Lは、CMIでもMPIでも通常どおりに要求を受信できなければなりません。MDSCの階層を図4に示します。

Another implementation choice could foresee the usage of an MDSC-L for all the PNCs related to a given technology (e.g., Internet Protocol (IP) / Multiprotocol Label Switching (MPLS)) and a different MDSC-L for the PNCs related to another technology (e.g., Optical Transport Network (OTN) / Wavelength Division Multiplexing (WDM)) and an MDSC-H to coordinate them.

別の実装の選択肢として、ある技術（たとえば、インターネットプロトコル（Internet Protocol、IP）／マルチプロトコルラベルスイッチング（Multiprotocol Label Switching、MPLS））に関連するすべてのPNCに1つのMDSC-Lを使用し、別の技術（たとえば、光トランスポートネットワーク（Optical Transport Network、OTN）／波長分割多重（Wavelength Division Multiplexing、WDM））に関連するPNCには別のMDSC-Lを使用し、それらを協調させるためにMDSC-Hを使用することも想定できます。

The hierarchy of MDSC can be recursive, where an MDSC-H is, in turn, an MDSC-L to a higher-level MDSC-H.

MDSCの階層は再帰的にすることができ、その場合、MDSC-Hは、さらに上位のMDSC-Hに対してはMDSC-Lになります。

4.2. Functional Split of MDSC Functions in Orchestrators

4.2. オーケストレーターにおけるMDSC機能の機能分割

An implementation choice could separate the MDSC functions into two groups: one group for service-related functions and the other for network-related functions. This enables the implementation of a service orchestrator that provides the service-related functions of the MDSC and a network orchestrator that provides the network-related functions of the MDSC. This split is consistent with the YANG service model architecture described in [RFC8309]. Figure 5 depicts this and shows how the ACTN interfaces may map to YANG data models.

実装の選択肢として、MDSCの機能を2つのグループ、すなわちサービス関連機能のグループとネットワーク関連機能のグループに分けることができます。これにより、MDSCのサービス関連機能を提供するサービスオーケストレーターと、MDSCのネットワーク関連機能を提供するネットワークオーケストレーターを実装できるようになります。この分割は、[RFC8309]で説明されているYANGサービスモデルのアーキテクチャーと一致しています。図5はこれを図示し、ACTNのインターフェイスがYANGデータモデルにどのようにマッピングされうるかを示しています。

5. Topology Abstraction Methods

5. トポロジーの抽象化の方法

Topology abstraction is described in [RFC7926]. This section discusses topology abstraction factors, types, and their context in the ACTN architecture.

トポロジーの抽象化については[RFC7926]で説明されています。このセクションでは、トポロジーの抽象化の要因、種類、およびACTNアーキテクチャーにおけるそれらの位置付けについて説明します。

Abstraction in ACTN is performed by the PNC when presenting available topology to the MDSC, or by an MDSC-L when presenting topology to an MDSC-H. This function is different from the creation of a VN (and particularly a Type 2 VN) that is not abstraction but construction of virtual resources.

ACTNにおける抽象化は、PNCが利用可能なトポロジーをMDSCに提示するとき、またはMDSC-LがトポロジーをMDSC-Hに提示するときに実行されます。この機能は、VN（特にタイプ2 VN）の作成とは異なります。VNの作成は抽象化ではなく、仮想リソースの構築です。

5.1. Abstraction Factors

5.1. 抽象化の要因

As discussed in [RFC7926], abstraction is tied with the policy of the networks. For instance, per an operational policy, the PNC would not provide any technology-specific details (e.g., optical parameters for Wavelength Switched Optical Network (WSON) in the abstract topology it provides to the MDSC. Similarly, the policy of the networks may determine the abstraction type as described in Section 5.2.

[RFC7926]で議論されているように、抽象化はネットワークのポリシーと結び付いています。たとえば、運用ポリシーによっては、PNCは、MDSCに提供する抽象トポロジーにおいて、技術固有の詳細（たとえば、波長スイッチ光ネットワーク（Wavelength Switched Optical Network、WSON）の光パラメーター）を一切提供しないことがあります。同様に、セクション5.2で説明するように、ネットワークのポリシーによって抽象化の種類が決まることがあります。

There are many factors that may impact the choice of abstraction:

抽象化の選択に影響を与えうる要因は数多くあります。

  • Abstraction depends on the nature of the underlying domain networks. For instance, packet networks may be abstracted with fine granularity while abstraction of optical networks depends on the switching units (such as wavelengths) and the end-to-end continuity and cross-connect limitations within the network.
  • Abstraction also depends on the capability of the PNCs. As abstraction requires hiding details of the underlying network resources, the PNC's capability to run algorithms impacts the feasibility of abstraction. Some PNCs may not have the ability to abstract native topology while other PNCs may have the ability to use sophisticated algorithms.
  • Abstraction is a tool that can improve scalability. Where the native network resource information is of a large size, there is a specific scaling benefit to abstraction.
  • The proper abstraction level may depend on the frequency of topology updates and vice versa.
  • The nature of the MDSC's support for technology-specific parameters impacts the degree/level of abstraction. If the MDSC is not capable of handling such parameters, then a higher level of abstraction is needed.
  • In some cases, the PNC is required to hide key internal topological data from the MDSC. Such confidentiality can be achieved through abstraction.
  • 抽象化は、基盤となるドメインネットワークの性質に依存します。たとえば、パケットネットワークは細かい粒度で抽象化できますが、光ネットワークの抽象化は、スイッチング単位（波長など）や、ネットワーク内のエンドツーエンドの連続性とクロスコネクトの制限に依存します。
  • 抽象化は、PNCの能力にも依存します。抽象化には基盤となるネットワークリソースの詳細を隠すことが必要なため、アルゴリズムを実行するPNCの能力が抽象化の実現可能性に影響します。PNCによっては、ネイティブトポロジーを抽象化する能力を持たないこともあれば、高度なアルゴリズムを使用する能力を持つこともあります。
  • 抽象化は、スケーラビリティーを向上させることのできるツールです。ネイティブなネットワークリソースの情報のサイズが大きい場合、抽象化には特有のスケーリング上の利点があります。
  • 適切な抽象化のレベルは、トポロジーの更新頻度に依存することがあり、その逆もあります。
  • 技術固有のパラメーターに対するMDSCのサポートの性質は、抽象化の程度／レベルに影響します。MDSCがそのようなパラメーターを扱えない場合は、より高いレベルの抽象化が必要です。
  • 場合によっては、PNCは、重要な内部のトポロジーデータをMDSCから隠す必要があります。このような機密性は、抽象化によって実現できます。

5.2. Abstraction Types

5.2. 抽象化の種類

This section defines the following three types of topology abstraction:

このセクションでは、次の3種類のトポロジーの抽象化を定義します。

  • Native/White Topology (Section 5.2.1)
  • Black Topology (Section 5.2.2)
  • Grey Topology (Section 5.2.3)
  • ネイティブ／ホワイトトポロジー（セクション5.2.1）
  • ブラックトポロジー（セクション5.2.2）
  • グレートポロジー（セクション5.2.3）

5.2.1. Native/White Topology

5.2.1. ネイティブ／ホワイトトポロジー

This is a case where the PNC provides the actual network topology to the MDSC without any hiding or filtering of information, i.e., no abstraction is performed. In this case, the MDSC has the full knowledge of the underlying network topology and can operate on it directly.

これは、PNCが情報を一切隠したりフィルタリングしたりせずに、実際のネットワークトポロジーをMDSCに提供する場合です。つまり、抽象化は実行されません。この場合、MDSCは基盤となるネットワークトポロジーを完全に把握しており、それに対して直接操作できます。

5.2.2. Black Topology

5.2.2. ブラックトポロジー

A black topology replaces a full network with a minimal representation of the edge-to-edge topology without disclosing any node internal connectivity information. The entire domain network may be abstracted as a single abstract node with the network's access/egress links appearing as the ports to the abstract node and the implication that any port can be "cross-connected" to any other. Figure 6 depicts a native topology with the corresponding black topology with one virtual node and inter-domain links. In this case, the MDSC has to make a provisioning request to the PNCs to establish the port-to-port connection. If there is a large number of interconnected domains, this abstraction method may impose a heavy coordination load at the MDSC level in order to find an optimal end-to-end path since the abstraction hides so much information that it is not possible to determine whether an end-to-end path is feasible without asking each PNC to set up each path fragment. For this reason, the MPI might need to be enhanced to allow the PNCs to be queried for the practicality and characteristics of paths across the abstract node.

ブラックトポロジーは、ノード内部の接続性の情報を一切開示せずに、ネットワーク全体をエッジツーエッジのトポロジーの最小限の表現に置き換えます。ドメインネットワーク全体を単一の抽象ノードとして抽象化し、ネットワークのアクセス／出口リンクを抽象ノードのポートとして見せ、任意のポートを他の任意のポートに「クロスコネクト」できることを暗に示すことができます。図6は、ネイティブトポロジーと、それに対応する、1つの仮想ノードとドメイン間リンクを持つブラックトポロジーを示しています。この場合、MDSCは、ポート間の接続を確立するためにPNCにプロビジョニング要求を行う必要があります。相互接続されたドメインの数が多い場合、この抽象化の方法では、最適なエンドツーエンドのパスを見つけるために、MDSCのレベルで重い協調の負荷がかかる可能性があります。抽象化によって非常に多くの情報が隠されるため、各PNCに各パスの断片を設定するよう依頼しなければ、エンドツーエンドのパスが実現可能かどうかを判断できないからです。このため、抽象ノードをまたぐパスの実用性と特性をPNCに問い合わせることができるように、MPIを拡張する必要があるかもしれません。

5.2.3. Grey Topology

5.2.3. グレートポロジー

A grey topology represents a compromise between black and white topologies from a granularity point of view. In this case, the PNC exposes an abstract topology containing all PNC domain border nodes and an abstraction of the connectivity between those border nodes. This abstraction may contain either physical or abstract nodes/links.

グレートポロジーは、粒度の観点から、ブラックトポロジーとホワイトトポロジーの妥協点を表します。この場合、PNCは、すべてのPNCドメインの境界ノードと、それらの境界ノード間の接続性の抽象化を含む抽象トポロジーを公開します。この抽象化には、物理的なノード／リンクと抽象的なノード／リンクのどちらを含めることもできます。

Two types of grey topology are identified:

グレートポロジーには、次の2つの種類があります。

  • In a type A grey topology, border nodes are connected by a full mesh of TE links (see Figure 7).
  • In a type B grey topology, border nodes are connected over a more-detailed network comprising internal abstract nodes and abstracted links. This mode of abstraction supplies the MDSC with more information about the internals of the PNC domain and allows it to make more informed choices about how to route connectivity over the underlying network.
  • タイプAのグレートポロジーでは、境界ノードはTEリンクのフルメッシュで接続されます（図7を参照）。
  • タイプBのグレートポロジーでは、境界ノードは、内部の抽象ノードと抽象化されたリンクで構成される、より詳細なネットワークを介して接続されます。このモードの抽象化は、PNCドメインの内部に関するより多くの情報をMDSCに提供し、基盤となるネットワーク上で接続性をどのようにルーティングするかについて、MDSCがより多くの情報に基づいて選択できるようにします。

5.3. Methods of Building Grey Topologies

5.3. グレートポロジーの構築方法

This section discusses two different methods of building a grey topology:

このセクションでは、グレートポロジーを構築する2つの異なる方法について説明します。

  • Automatic generation of abstract topology by configuration (Section 5.3.1)
  • On-demand generation of supplementary topology via path computation request/reply (Section 5.3.2)
  • 設定による抽象トポロジーの自動生成（セクション5.3.1）
  • 経路計算の要求／応答による補足トポロジーのオンデマンド生成（セクション5.3.2）

5.3.1. Automatic Generation of Abstract Topology by Configuration

5.3.1. 設定による抽象トポロジーの自動生成

Automatic generation is based on the abstraction/summarization of the whole domain by the PNC and its advertisement on the MPI. The level of abstraction can be decided based on PNC configuration parameters (e.g., "provide the potential connectivity between any PE and any ASBR in an MPLS-TE network").

自動生成は、PNCによるドメイン全体の抽象化／要約と、MPI上でのその広告に基づいています。抽象化のレベルは、PNCの設定パラメーター（たとえば、「MPLS-TEネットワークにおいて、任意のPEと任意のASBRの間の潜在的な接続性を提供する」）に基づいて決定できます。

Note that the configuration parameters for this abstract topology can include available bandwidth, latency, or any combination of defined parameters. How to generate such information is beyond the scope of this document.

この抽象トポロジーの設定パラメーターには、利用可能な帯域幅、遅延、または定義されたパラメーターの任意の組み合わせを含めることができることに注意してください。そのような情報をどのように生成するかは、この文書の範囲外です。

This abstract topology may need to be periodically or incrementally updated when there is a change in the underlying network or the use of the network resources that make connectivity more or less available.

この抽象トポロジーは、基盤となるネットワーク、または接続性の利用可能性を増減させるネットワークリソースの使用状況に変化があったときに、定期的または増分的に更新する必要がある場合があります。

5.3.2. On-Demand Generation of Supplementary Topology via Path Compute Request/Reply

5.3.2. 経路計算の要求／応答による補足トポロジーのオンデマンド生成

While abstract topology is generated and updated automatically by configuration as explained in Section 5.3.1, additional supplementary topology may be obtained by the MDSC via a path compute request/reply mechanism.

セクション5.3.1で説明したように抽象トポロジーは設定によって自動的に生成され更新されますが、MDSCは、経路計算の要求／応答のメカニズムを介して、追加の補足トポロジーを取得することもできます。

The abstract topology advertisements from PNCs give the MDSC the border node/link information for each domain. Under this scenario, when the MDSC needs to create a new VN, the MDSC can issue path computation requests to PNCs with constraints matching the VN request as described in [ACTN-YANG]. An example is provided in Figure 8, where the MDSC is creating a P2P VN between AP1 and AP2. The MDSC could use two different inter-domain links to get from domain X to domain Y, but in order to choose the best end-to-end path, it needs to know what domain X and Y can offer in terms of connectivity and constraints between the PE nodes and the border nodes.

PNCからの抽象トポロジーの広告により、MDSCは各ドメインの境界ノード／リンクの情報を得ます。このシナリオでは、MDSCが新しいVNを作成する必要があるとき、MDSCは、[ACTN-YANG]で説明されているように、VNの要求に一致する制約を付けた経路計算要求をPNCに発行できます。図8に例を示します。ここでは、MDSCがAP1とAP2の間にP2P VNを作成しようとしています。MDSCは、ドメインXからドメインYに到達するために2つの異なるドメイン間リンクを使用できますが、最適なエンドツーエンドのパスを選択するためには、PEノードと境界ノードの間の接続性と制約の観点から、ドメインXとドメインYが何を提供できるかを知る必要があります。

The MDSC issues a path computation request to PNC.X asking for potential connectivity between PE1 and border node BrdrX.1 and between PE1 and BrdrX.2 with related objective functions and TE metric constraints. A similar request for connectivity from the border nodes in domain Y to PE2 will be issued to PNC.Y. The MDSC merges the results to compute the optimal end-to-end path including the inter-domain links. The MDSC can use the result of this computation to request the PNCs to provision the underlying networks, and the MDSC can then use the end-to-end path as a virtual link in the VN it delivers to the customer.

MDSCは、PE1と境界ノードBrdrX.1の間、およびPE1とBrdrX.2の間の潜在的な接続性を、関連する目的関数とTEメトリックの制約とともに問い合わせる経路計算要求をPNC.Xに発行します。ドメインYの境界ノードからPE2への接続性についても、同様の要求がPNC.Yに発行されます。MDSCは結果をマージして、ドメイン間リンクを含む最適なエンドツーエンドのパスを計算します。MDSCは、この計算結果を使用して、基盤となるネットワークのプロビジョニングをPNCに要求できます。そしてMDSCは、そのエンドツーエンドのパスを、顧客に提供するVN内の仮想リンクとして使用できます。

7. Advanced ACTN Application: Multi-Destination Service

7. ACTNの高度な応用：マルチデスティネーションサービス

A more-advanced application of ACTN is the case of data center (DC) selection, where the customer requires the DC selection to be based on the network status; this is referred to as "Multi-Destination Service" in [ACTN-REQ]. In terms of ACTN, a CNC could request a VNS between a set of source APs and destination APs and leave it up to the network (MDSC) to decide which source and destination APs to be used to set up the VNS. The candidate list of source and destination APs is decided by a CNC (or an entity outside of ACTN) based on certain factors that are outside the scope of ACTN.

ACTNのより高度な応用は、データセンター（data center、DC）の選択の場合です。ここでは、顧客は、DCの選択がネットワークの状態に基づいて行われることを要求します。これは[ACTN-REQ]では「マルチデスティネーションサービス（Multi-Destination Service）」と呼ばれています。ACTNの観点では、CNCは、送信元APの集合と宛先APの集合の間のVNSを要求し、VNSの設定にどの送信元APと宛先APを使用するかの決定をネットワーク（MDSC）に任せることができます。送信元APと宛先APの候補リストは、ACTNの範囲外である特定の要因に基づいて、CNC（またはACTN外部のエンティティー）が決定します。

Based on the AP selection as determined and returned by the network (MDSC), the CNC (or an entity outside of ACTN) should further take care of any subsequent actions such as orchestration or service setup requirements. These further actions are outside the scope of ACTN.

ネットワーク（MDSC）によって決定され返されたAPの選択に基づいて、CNC（またはACTN外部のエンティティー）は、オーケストレーションやサービス設定の要件など、その後のあらゆるアクションをさらに処理すべきです。これらのさらなるアクションは、ACTNの範囲外です。

Consider a case as shown in Figure 18, where three DCs are available, but the customer requires the DC selection to be based on the network status and the connectivity service setup between the AP1 (CE1) and one of the destination APs (AP2 (DC-A), AP3 (DC-B), and AP4 (DC-C)). The MDSC (in coordination with PNCs) would select the best destination AP based on the constraints, optimization criteria, policies, etc., and set up the connectivity service (virtual network).

図18に示すような場合を考えてみましょう。ここでは、3つのDCが利用可能ですが、顧客は、DCの選択がネットワークの状態に基づいて行われ、AP1（CE1）と宛先APの1つ（AP2（DC-A）、AP3（DC-B）、AP4（DC-C））の間に接続性サービスが設定されることを要求しています。MDSCは（PNCと協調して）、制約、最適化の基準、ポリシーなどに基づいて最適な宛先APを選択し、接続性サービス（仮想ネットワーク）を設定します。

7.1. Preplanned Endpoint Migration

7.1. 事前計画されたエンドポイントの移行

Furthermore, in the case of DC selection, a customer could request a backup DC to be selected, such that in case of failure, another DC site could provide hot stand-by protection. As shown in Figure 19, DC-C is selected as a backup for DC-A. Thus, the VN should be set up by the MDSC to include primary connectivity between AP1 (CE1) and AP2 (DC-A) as well as protection connectivity between AP1 (CE1) and AP4 (DC-C).

さらに、DCの選択の場合、顧客は、障害が発生した場合に別のDCサイトがホットスタンバイの保護を提供できるように、バックアップのDCを選択するよう要求できます。図19に示すように、DC-CがDC-Aのバックアップとして選択されています。したがって、MDSCは、AP1（CE1）とAP2（DC-A）の間の主接続性と、AP1（CE1）とAP4（DC-C）の間の保護接続性を含むようにVNを設定すべきです。

7.2. On-the-Fly Endpoint Migration

7.2. オンザフライのエンドポイントの移行

Compared to preplanned endpoint migration, on-the-fly endpoint selection is dynamic in that the migration is not preplanned but decided based on network condition. Under this scenario, the MDSC would monitor the network (based on the VN SLA) and notify the CNC in the case where some other destination AP would be a better choice based on the network parameters. The CNC should instruct the MDSC when it is suitable to update the VN with the new AP if it is required.

事前計画されたエンドポイントの移行と比べて、オンザフライのエンドポイントの選択は、移行が事前に計画されるのではなく、ネットワークの状況に基づいて決定されるという点で動的です。このシナリオでは、MDSCは（VNのSLAに基づいて）ネットワークを監視し、ネットワークのパラメーターに基づいて他の宛先APの方がよりよい選択になる場合に、CNCに通知します。CNCは、必要であれば、新しいAPでVNを更新するのに適したタイミングをMDSCに指示すべきです。

8. Manageability Considerations

8. 管理性に関する考慮事項

The objective of ACTN is to manage traffic engineered resources and provide a set of mechanisms to allow customers to request virtual connectivity across server-network resources. ACTN supports multiple customers, each with its own view of and control of a virtual network built on the server network; the network operator will need to partition (or "slice") their network resources, and manage the resources accordingly.

ACTNの目的は、トラフィックエンジニアリングされたリソースを管理し、顧客がサーバーネットワークのリソースをまたぐ仮想的な接続性を要求できるようにするための一連のメカニズムを提供することです。ACTNは、それぞれがサーバーネットワーク上に構築された仮想ネットワークに対する独自のビューと制御を持つ、複数の顧客をサポートします。ネットワーク運用者は、自身のネットワークリソースを分割（つまり「スライス」）し、それに応じてリソースを管理する必要があります。

The ACTN platform will, itself, need to support the request, response, and reservations of client- and network-layer connectivity. It will also need to provide performance monitoring and control of TE resources. The management requirements may be categorized as follows:

ACTNプラットフォーム自体は、クライアント層とネットワーク層の接続性の要求、応答、予約をサポートする必要があります。また、TEリソースの性能の監視と制御を提供する必要もあります。管理の要件は、次のように分類できます。

  • Management of external ACTN protocols
  • Management of internal ACTN interfaces/protocols
  • Management and monitoring of ACTN components
  • Configuration of policy to be applied across the ACTN system
  • 外部のACTNプロトコルの管理
  • 内部のACTNインターフェイス／プロトコルの管理
  • ACTNコンポーネントの管理と監視
  • ACTNシステム全体に適用されるポリシーの設定

The ACTN framework and interfaces are defined to enable traffic engineering for virtual network services and connectivity services. Network operators may have other Operations, Administration, and Maintenance (OAM) tasks for service fulfillment, optimization, and assurance beyond traffic engineering. The realization of OAM beyond abstraction and control of TE networks is not discussed in this document.

ACTNのフレームワークとインターフェイスは、仮想ネットワークサービスと接続性サービスのトラフィックエンジニアリングを可能にするために定義されています。ネットワーク運用者には、トラフィックエンジニアリングを超えて、サービスの履行、最適化、保証のための他の運用・管理・保守（Operations, Administration, and Maintenance、OAM）のタスクがあるかもしれません。TEネットワークの抽象化と制御を超えたOAMの実現については、この文書では議論しません。

8.1. Policy

8.1. ポリシー

Policy is an important aspect of ACTN control and management. Policies are used via the components and interfaces, during deployment of the service, to ensure that the service is compliant with agreed-upon policy factors and variations (often described in SLAs); these include, but are not limited to connectivity, bandwidth, geographical transit, technology selection, security, resilience, and economic cost.

ポリシーは、ACTNの制御と管理の重要な側面です。ポリシーは、サービスの展開中に、コンポーネントとインターフェイスを介して使用され、サービスが合意されたポリシーの要因とバリエーション（多くの場合SLAに記述されます）に準拠していることを保証します。これには、接続性、帯域幅、地理的な経由地、技術の選択、セキュリティー、回復力、経済的なコストなどが含まれますが、これらに限定されません。

Depending on the deployment of the ACTN architecture, some policies may have local or global significance. That is, certain policies may be ACTN component specific in scope, while others may have broader scope and interact with multiple ACTN components. Two examples are provided below:

ACTNアーキテクチャーの展開によっては、ローカルな意味を持つポリシーもあれば、グローバルな意味を持つポリシーもあります。つまり、特定のポリシーは範囲がACTNコンポーネント固有である一方、他のポリシーはより広い範囲を持ち、複数のACTNコンポーネントと相互作用することがあります。2つの例を以下に示します。

  • A local policy might limit the number, type, size, and scheduling of virtual network services a customer may request via its CNC. This type of policy would be implemented locally on the MDSC.
  • A global policy might constrain certain customer types (or specific customer applications) only to use certain MDSCs and be restricted to physical network types managed by the PNCs. A global policy agent would govern these types of policies.
  • ローカルポリシーは、顧客がCNCを介して要求できる仮想ネットワークサービスの数、種類、規模、スケジューリングを制限することがあります。この種のポリシーは、MDSC上でローカルに実装されます。
  • グローバルポリシーは、特定の種類の顧客（または特定の顧客アプリケーション）に対して、特定のMDSCのみを使用するように制約し、PNCが管理する物理ネットワークの種類に制限することがあります。グローバルポリシーエージェントが、この種のポリシーを管轄します。

The objective of this section is to discuss the applicability of ACTN policy: requirements, components, interfaces, and examples. This section provides an analysis and does not mandate a specific method for enforcing policy, or the type of policy agent that would be responsible for propagating policies across the ACTN components. It does highlight examples of how policy may be applied in the context of ACTN, but it is expected further discussion in an applicability or solution-specific document, will be required.

このセクションの目的は、ACTNのポリシーの適用可能性、すなわち要件、コンポーネント、インターフェイス、例について議論することです。このセクションは分析を提供するものであり、ポリシーを施行するための特定の方法や、ACTNコンポーネント全体にポリシーを伝播する役割を担うポリシーエージェントの種類を義務付けるものではありません。ACTNの文脈でポリシーをどのように適用できるかの例は示しますが、適用可能性に関する文書やソリューション固有の文書でさらなる議論が必要になると予想されます。

8.2. Policy Applied to the Customer Network Controller

8.2. 顧客ネットワークコントローラーに適用されるポリシー

A virtual network service for a customer application will be requested by the CNC. The request will reflect the application requirements and specific service needs, including bandwidth, traffic type and survivability. Furthermore, application access and type of virtual network service requested by the CNC, will be need adhere to specific access control policies.

顧客のアプリケーションのための仮想ネットワークサービスは、CNCによって要求されます。その要求には、帯域幅、トラフィックの種類、生存性など、アプリケーションの要件と特定のサービスのニーズが反映されます。さらに、アプリケーションのアクセスと、CNCが要求する仮想ネットワークサービスの種類は、特定のアクセス制御ポリシーに従う必要があります。

8.3. Policy Applied to the Multi-Domain Service Coordinator

8.3. マルチドメインサービスコーディネーターに適用されるポリシー

A key objective of the MDSC is to support the customer's expression of the application connectivity request via its CNC as a set of desired business needs; therefore, policy will play an important role.

MDSCの重要な目的は、顧客がCNCを介してアプリケーションの接続性の要求を一連の望ましいビジネス上のニーズとして表現することをサポートすることです。したがって、ポリシーは重要な役割を果たします。

Once authorized, the virtual network service will be instantiated via the CNC-MDSC Interface (CMI); it will reflect the customer application and connectivity requirements and specific service-transport needs. The CNC and the MDSC components will have agreed-upon connectivity endpoints; use of these endpoints should be defined as a policy expression when setting up or augmenting virtual network services. Ensuring that permissible endpoints are defined for CNCs and applications will require the MDSC to maintain a registry of permissible connection points for CNCs and application types.

認可されると、仮想ネットワークサービスはCNC-MDSCインターフェイス（CMI）を介してインスタンス化されます。このサービスには、顧客のアプリケーションと接続性の要件、および特定のサービストランスポートのニーズが反映されます。CNCコンポーネントとMDSCコンポーネントは、接続性のエンドポイントについて合意しておきます。仮想ネットワークサービスを設定または拡張するときには、これらのエンドポイントの使用をポリシー表現として定義すべきです。CNCとアプリケーションに対して許可されたエンドポイントが定義されていることを保証するためには、MDSCが、CNCとアプリケーションの種類ごとに許可された接続ポイントのレジストリーを維持する必要があります。

Conflicts may occur when virtual network service optimization criteria are in competition. For example, to meet objectives for service reachability, a request may require an interconnection point between multiple physical networks; however, this might break a confidentially policy requirement of a specific type of end-to-end service. Thus, an MDSC may have to balance a number of the constraints on a service request and between different requested services. It may also have to balance requested services with operational norms for the underlying physical networks. This balancing may be resolved using configured policy and using hard and soft policy constraints.

仮想ネットワークサービスの最適化の基準が競合する場合には、衝突が発生する可能性があります。たとえば、サービスの到達可能性に関する目的を満たすために、ある要求が複数の物理ネットワーク間の相互接続ポイントを必要とする場合がありますが、これは特定の種類のエンドツーエンドサービスの機密性ポリシーの要件に違反する可能性があります。そのため、MDSCは、サービス要求に対する多数の制約の間や、異なる要求サービスの間でバランスをとる必要がある場合があります。また、要求されたサービスと、基盤となる物理ネットワークの運用上の規範との間でバランスをとる必要がある場合もあります。このバランス調整は、設定されたポリシーを使用し、ハードなポリシー制約とソフトなポリシー制約を使用して解決できます。

8.4. Policy Applied to the Provisioning Network Controller

8.4. プロビジョニングネットワークコントローラーに適用されるポリシー

The PNC is responsible for configuring the network elements, monitoring physical network resources, and exposing connectivity (direct or abstracted) to the MDSC. Therefore, it is expected that policy will dictate what connectivity information will be exchanged on the MPI.

PNCは、ネットワーク要素の設定、物理的なネットワークリソースの監視、および（直接の、または抽象化された）接続性のMDSCへの公開を担います。したがって、MPI上でどのような接続性の情報を交換するかは、ポリシーによって規定されると予想されます。

Policy interactions may arise when a PNC determines that it cannot compute a requested path from the MDSC, or notices that (per a locally configured policy) the network is low on resources (for example, the capacity on key links became exhausted). In either case, the PNC will be required to notify the MDSC, which may (again per policy) act to construct a virtual network service across another physical network topology.

ポリシーとの相互作用は、MDSCから要求されたパスをPNCが計算できないと判断したとき、または（ローカルに設定されたポリシーに従って）ネットワークのリソースが不足していること（たとえば、重要なリンクの容量が枯渇したこと）にPNCが気付いたときに発生する可能性があります。いずれの場合も、PNCはMDSCに通知する必要があり、MDSCは（これもポリシーに従って）別の物理ネットワークトポロジーにまたがる仮想ネットワークサービスを構築するように動作することがあります。

Furthermore, additional forms of policy-based resource management will be required to provide VNS performance, security, and resilience guarantees. This will likely be implemented via a local policy agent and additional protocol methods.

さらに、VNSの性能、セキュリティー、回復力の保証を提供するためには、追加の形式のポリシーベースのリソース管理が必要になります。これはおそらく、ローカルなポリシーエージェントと追加のプロトコルの手法によって実装されます。

9. Security Considerations

9. セキュリティーに関する考慮事項

The ACTN framework described in this document defines key components and interfaces for managed TE networks. Securing the request and control of resources, confidentiality of the information, and availability of function should all be critical security considerations when deploying and operating ACTN platforms.

この文書で説明するACTNフレームワークは、管理されたTEネットワークのための主要なコンポーネントとインターフェイスを定義しています。ACTNプラットフォームを展開して運用する際には、リソースの要求と制御の保護、情報の機密性、機能の可用性のすべてが、重要なセキュリティー上の考慮事項となるはずです。

Several distributed ACTN functional components are required, and implementations should consider encrypting data that flows between components, especially when they are implemented at remote nodes, regardless of whether these data flows are on external or internal network interfaces.

分散したACTNの機能コンポーネントがいくつか必要になります。実装は、コンポーネント間を流れるデータを暗号化することを検討すべきです。特に、コンポーネントがリモートのノードに実装されている場合は、データフローが外部のネットワークインターフェイス上にあるか内部のネットワークインターフェイス上にあるかにかかわらず、暗号化を検討すべきです。

The ACTN security discussion is further split into two specific categories described in the following subsections:

ACTNのセキュリティーに関する議論は、以下のサブセクションで説明する2つの具体的なカテゴリーにさらに分かれます。

  • Interface between the Customer Network Controller and Multi-Domain Service Coordinator (MDSC), CNC-MDSC Interface (CMI)
  • Interface between the Multi-Domain Service Coordinator and Provisioning Network Controller (PNC), MDSC-PNC Interface (MPI)
  • 顧客ネットワークコントローラーとマルチドメインサービスコーディネーター（MDSC）の間のインターフェイス、すなわちCNC-MDSCインターフェイス（CMI）
  • マルチドメインサービスコーディネーターとプロビジョニングネットワークコントローラー（PNC）の間のインターフェイス、すなわちMDSC-PNCインターフェイス（MPI）

From a security and reliability perspective, ACTN may encounter many risks such as malicious attack and rogue elements attempting to connect to various ACTN components. Furthermore, some ACTN components represent a single point of failure and threat vector and must also manage policy conflicts and eavesdropping of communication between different ACTN components.

セキュリティーと信頼性の観点からは、ACTNは、悪意のある攻撃や、さまざまなACTNコンポーネントへの接続を試みる不正な要素など、多くのリスクに直面する可能性があります。さらに、一部のACTNコンポーネントは単一障害点や脅威ベクトルとなり、ポリシーの衝突や、異なるACTNコンポーネント間の通信の盗聴にも対処しなければなりません。

The conclusion is that all protocols used to realize the ACTN framework should have rich security features, and customer, application and network data should be stored in encrypted data stores. Additional security risks may still exist. Therefore, discussion and applicability of specific security functions and protocols will be better described in documents that are use case and environment specific.

結論として、ACTNフレームワークを実現するために使用されるすべてのプロトコルは豊富なセキュリティー機能を備えるべきであり、顧客、アプリケーション、ネットワークのデータは暗号化されたデータストアに保存されるべきです。それでも、追加のセキュリティーリスクが存在する可能性があります。したがって、特定のセキュリティー機能やプロトコルの議論と適用可能性は、ユースケースや環境に固有の文書でよりよく説明されるでしょう。

9.1. CNC-MDSC Interface (CMI)

9.1. CNC-MDSCインターフェイス（CMI）

Data stored by the MDSC will reveal details of the virtual network services and which CNC and customer/application is consuming the resource. Therefore, the data stored must be considered a candidate for encryption.

MDSCが保存するデータからは、仮想ネットワークサービスの詳細や、どのCNCと顧客／アプリケーションがリソースを消費しているかが明らかになります。したがって、保存されるデータは暗号化の対象候補と考えなければなりません。

CNC Access rights to an MDSC must be managed. The MDSC must allocate resources properly, and methods to prevent policy conflicts, resource waste, and denial-of-service attacks on the MDSC by rogue CNCs should also be considered.

MDSCに対するCNCのアクセス権は管理されなければなりません。MDSCはリソースを適切に割り当てなければならず、ポリシーの衝突、リソースの浪費、不正なCNCによるMDSCへのサービス拒否攻撃を防ぐ方法も検討すべきです。

The CMI will likely be an external protocol interface. Suitable authentication and authorization of each CNC connecting to the MDSC will be required; especially, as these are likely to be implemented by different organizations and on separate functional nodes. Use of the AAA-based mechanisms would also provide role-based authorization methods so that only authorized CNC's may access the different functions of the MDSC.

CMIは、おそらく外部のプロトコルインターフェイスになります。MDSCに接続する各CNCの適切な認証と認可が必要になります。特に、これらは異なる組織によって、別々の機能ノード上に実装される可能性が高いためです。AAAベースのメカニズムを使用すれば、認可されたCNCのみがMDSCのさまざまな機能にアクセスできるように、ロールベースの認可方法も提供されるでしょう。

9.2. MDSC-PNC Interface (MPI)

9.2. MDSC-PNCインターフェイス（MPI）

Where the MDSC must interact with multiple (distributed) PNCs, a PKI-based mechanism is suggested, such as building a TLS or HTTPS connection between the MDSC and PNCs, to ensure trust between the physical network layer control components and the MDSC. Trust anchors for the PKI can be configured to use a smaller (and potentially non-intersecting) set of trusted Certificate Authorities (CAs) than in the Web PKI.

MDSCが複数の（分散した）PNCとやり取りしなければならない場合、物理ネットワーク層の制御コンポーネントとMDSCの間の信頼を確保するために、MDSCとPNCの間にTLSまたはHTTPSの接続を構築するなど、PKIベースのメカニズムが推奨されます。PKIのトラストアンカーは、Web PKIよりも小さな（そして交わらない可能性もある）信頼された認証局（Certificate Authority、CA）の集合を使用するように設定できます。

Which MDSC the PNC exports topology information to, and the level of detail (full or abstracted), should also be authenticated, and specific access restrictions and topology views should be configurable and/or policy based.

PNCがどのMDSCにトポロジー情報をエクスポートするか、および詳細のレベル（完全か抽象化されたものか）も認証されるべきであり、特定のアクセス制限とトポロジーのビューは設定可能、またはポリシーベース、あるいはその両方であるべきです。
