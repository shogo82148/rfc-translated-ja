RFC 1151

Version 2 of the Reliable Data Protocol (RDP)

RFC 1151

Reliable Data Protocol（RDP）のバージョン2

Status of This Memo

このメモのステータス

This RFC suggests several updates to the specification of the Reliable Data Protocol (RDP) in RFC-908 based on experience with the protocol. This revised version of the protocol is experimental.

このRFCは、プロトコルの経験に基づいて、RFC-908のReliable Data Protocol（RDP）の仕様に対するいくつかの更新を提案します。このプロトコルの改訂版は実験的なものです。

Distribution of this memo is unlimited.

このメモの配布は無制限です。

Introduction

はじめに

Experiments in 1986 and 1987 turned up some ambiguities and problems with the RDP specification. At the time, it was hoped that the authors might find the time to revise the entire RDP specification to fix these problems, however given the limited demand for RDP implementations, the authors were never able to justify the time involved in revising the spec. This document lists the changes that we believe are appropriate to make to RDP version 1.

1986年と1987年の実験で、RDPの仕様にいくつかの曖昧さと問題が見つかりました。当時は、著者らがこれらの問題を修正するためにRDPの仕様全体を改訂する時間を見つけられることが期待されていました。しかし、RDPの実装に対する需要が限られていたため、著者らは仕様の改訂にかかる時間を正当化できませんでした。この文書では、RDPバージョン1に加えるのが適切だと私たちが考える変更点を列挙します。

Readers are expected to be familiar with RFC-908.

読者はRFC-908をよく知っていることを前提とします。

Changes To The Protocol Header

プロトコルヘッダーの変更

There are three changes to the protocol header: the checksum algorithm has been changed, the port size increased, and the version number incremented. The new header format is shown in Figure 1.

プロトコルヘッダーには3つの変更があります。チェックサムのアルゴリズムの変更、ポートのサイズの拡大、バージョン番号の増加です。新しいヘッダーの形式を図1に示します。

The major discovery during the testing of the protocol is that cost of computing the the RDP checksum proved surprisingly variable; its performance was more heavily affected by the host's data representation than anticipated. Optimized checksum implementations on two comparable hardware bases gave performance that differed by a factor of five. Since the speed of the checksum is a key factor in the performance of the protocol itself, this variation caused a noticeable difference in throughput.

プロトコルのテスト中の主な発見は、RDPのチェックサムの計算コストが驚くほどばらつくことでした。その性能は、予想以上にホストのデータ表現に大きく左右されました。同等の2つのハードウェア基盤上で最適化したチェックサムの実装は、5倍も異なる性能を示しました。チェックサムの速度はプロトコル自体の性能の重要な要因であるため、このばらつきはスループットに目に見える差をもたらしました。

The wide variation in performance on comparable machines was felt to be undesirable, so the checksum has been changed. RDP now uses the 16-bit TCP checksum, which is specified on page 16 of RFC-793.

同等のマシン上で性能が大きくばらつくのは望ましくないと考えられたため、チェックサムを変更しました。RDPは現在、RFC-793の16ページで規定されている16ビットのTCPチェックサムを使います。

The 8-bit port size is probably too small to support a large range of applications. Accordingly, the port size is now 16-bits. Port numbers less than 1024 are reserved for well-defined applications. Allocable ports begin at port number 1024.

8ビットのポートのサイズは、幅広いアプリケーションをサポートするにはおそらく小さすぎます。そのため、ポートのサイズを16ビットにしました。1024未満のポート番号は、明確に定義されたアプリケーションのために予約されています。割り当て可能なポートは、ポート番号1024から始まります。

Finally, because the checksum and port size have been changed, the version number has been increased to 2.

最後に、チェックサムとポートのサイズを変更したため、バージョン番号を2に上げました。

Minor Errors and Ambiguities

軽微な誤りと曖昧さ

Some ambiguities and minor errors have been found in RFC-908. They are corrected in this section.

RFC-908には、いくつかの曖昧さと軽微な誤りが見つかっています。このセクションでそれらを訂正します。

The value of the state variable, SND.UNA is treated inconsistently in the pseudo-code on pages 21-29. On page 12, SND.UNA is defined as "the sequence number of the oldest unacknowledged segment", and on page 21 it is appropriately set to the initial sequence number when the connection is opened. But on page 28, when an acknowledgement is received, SND.UNA is set to SEG.ACK, the sequence number being acknowledged, instead of SEG.ACK+1. A similar inconsistency occurs on page 26. The proper fix is to always set SND.UNA to SEG.ACK+1.

21〜29ページの疑似コードでは、状態変数SND.UNAの値が一貫しない扱いを受けています。12ページでは、SND.UNAは「確認応答されていない最も古いセグメントのシーケンス番号」と定義されており、21ページではコネクションを開くときに初期シーケンス番号が適切に設定されています。しかし28ページでは、確認応答を受信したときに、SND.UNAにSEG.ACK+1ではなく、確認応答されたシーケンス番号であるSEG.ACKが設定されています。同様の不整合が26ページにもあります。正しい修正は、SND.UNAに常にSEG.ACK+1を設定することです。

The pseudo-code on page 25 for the SYN-SENT state is incorrect. The first few lines cause all packets with the ACK bit set to be discarded, but later lines test the ACK bit. The test for the ACK bit should be placed after all the other tests. Also note that if the ACK bit is set, a RST segment is sent to reset the remote peer, but the local peer is left half-open. There is a similar problem in the SYN-RCVD state. The local peer should deallocate the connection record and close.

25ページのSYN-SENT状態の疑似コードは誤っています。最初の数行によってACKビットが設定されたパケットはすべて破棄されますが、後の行ではACKビットを検査しています。ACKビットの検査は、ほかのすべての検査の後に置くべきです。また、ACKビットが設定されている場合、リモートのピアをリセットするためにRSTセグメントが送信されますが、ローカルのピアは半開きのまま残されることにも注意してください。SYN-RCVD状態にも同様の問題があります。ローカルのピアは、コネクションレコードを解放してクローズすべきです。

On page 24, the pseudo-code indicates that if non-data packets are received in the CLOSED state, a RST segment with SEG.ACK set to RCV.CUR should be sent. RCV.CUR is not defined in the CLOSED state. SEG.ACK should be set to SEG.SEG.

24ページの疑似コードは、CLOSED状態でデータ以外のパケットを受信した場合、SEG.ACKにRCV.CURを設定したRSTセグメントを送信すべきであることを示しています。RCV.CURはCLOSED状態では定義されていません。SEG.ACKにはSEG.SEGを設定すべきです。

There is some inconsistency about how to handle a RST packet in the CLOSE-WAIT state. On page 24, the pseudo-code shows that a RST should cause the connection state to become CLOSED. Text on page 13 and the state diagram on page 10 suggest the connection state should stay in CLOSE-WAIT. The implementation should stay in CLOSE-WAIT.

CLOSE-WAIT状態でのRSTパケットの扱い方には、いくつかの不整合があります。24ページの疑似コードは、RSTによってコネクションの状態がCLOSEDになるべきであることを示しています。13ページの本文と10ページの状態遷移図は、コネクションの状態がCLOSE-WAITのままであるべきことを示唆しています。実装はCLOSE-WAITのままにすべきです。

On page 29, the pseudo-code for the OPEN state suggests that if a data packet is received in sequence, the acknowledgement packet should not contain EACKs. This is misleading. Implementations may include EACKs in the acknowledgement.

29ページのOPEN状態の疑似コードは、データパケットを順序どおりに受信した場合、確認応答パケットにEACKを含めるべきではないことを示唆しています。これは誤解を招きます。実装は確認応答にEACKを含めてもかまいません。

On page 18, it is possible to interpret the right edge as being either inside or outside the window. This results in a one segment difference in the window size. The proper interpretation is that the right edge is outside the window. In other words, the right edge is the first sequence number that cannot be sent or received and the total window size is 2*X, where X is the maximum number of outstanding segments.

18ページでは、右端をウィンドウの内側とも外側とも解釈できます。これにより、ウィンドウのサイズに1セグメントの差が生じます。正しい解釈は、右端はウィンドウの外側にあるというものです。言い換えれば、右端は送信も受信もできない最初のシーケンス番号であり、ウィンドウ全体のサイズは2*Xです。ここで、Xは未処理のセグメントの最大数です。

One final problem is that RDP's flow control scheme does not allow the receiver to close the sender's window. As a result, if the receiver acknowledges segments when they are received the sender can easily send more data than the receiver is prepared to buffer. A solution to this problem (suggested by members of the End-2-End Research Group) is to only acknowledge a segment after it has been delivered to the application. This scheme, however, has not be tested.

最後の問題は、RDPのフロー制御の方式では、受信者が送信者のウィンドウを閉じられないことです。その結果、受信者がセグメントを受信した時点で確認応答すると、送信者は受信者がバッファリングできる量を超えるデータを容易に送信できてしまいます。この問題の解決策の1つは（End-2-End Research Groupのメンバーが提案したもので）、セグメントがアプリケーションに配送された後でのみそのセグメントを確認応答することです。ただし、この方式はテストされていません。
