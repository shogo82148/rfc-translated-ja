Definitions of Managed Objects for Mapping of Address and Port with Encapsulation (MAP-E)

Abstract

概要

This memo defines a portion of the Management Information Base (MIB) for Mapping of Address and Port with Encapsulation (MAP-E) for use with network management protocols.

このメモでは、ネットワーク管理プロトコルで使用するための、カプセル化によるアドレスとポートのマッピング（Mapping of Address and Port with Encapsulation、MAP-E）の管理情報ベース（Management Information Base、MIB）の一部を定義します。

1. Introduction

1. はじめに

Mapping of Address and Port with Encapsulation (MAP-E) [RFC7597] is a stateless, automatic tunneling mechanism for providing an IPv4 connectivity service to end users over a service provider's IPv6 network.

カプセル化によるアドレスとポートのマッピング（Mapping of Address and Port with Encapsulation、MAP-E）[RFC7597]は、サービスプロバイダーのIPv6ネットワーク上でエンドユーザーにIPv4の接続サービスを提供するための、ステートレスな自動トンネリングメカニズムです。

This document defines a portion of the Management Information Base (MIB) for use with monitoring MAP-E devices.

この文書では、MAP-Eデバイスの監視に使用するための管理情報ベース（MIB）の一部を定義します。

2. The Internet-Standard Management Framework

2. インターネット標準管理フレームワーク

For a detailed overview of the documents that describe the current Internet-Standard Management Framework, please refer to section 7 of RFC 3410 [RFC3410].

現在のインターネット標準管理フレームワーク（Internet-Standard Management Framework）を記述している文書の詳細な概要については、RFC 3410 [RFC3410]のセクション7を参照してください。

Managed objects are accessed via a virtual information store, termed the Management Information Base or MIB. MIB objects are generally accessed through the Simple Network Management Protocol (SNMP). Objects in the MIB are defined using the mechanisms defined in the Structure of Management Information (SMI). This memo specifies a MIB module that is compliant to the SMIv2, which is described in STD 58, RFC 2578 [RFC2578], STD 58, RFC 2579 [RFC2579] and STD 58, RFC 2580 [RFC2580].

管理オブジェクトには、管理情報ベース（Management Information Base、MIB）と呼ばれる仮想的な情報ストアを介してアクセスします。MIBオブジェクトには、一般にSimple Network Management Protocol（SNMP）を通じてアクセスします。MIB内のオブジェクトは、管理情報構造（Structure of Management Information、SMI）で定義されたメカニズムを使って定義されます。このメモでは、STD 58、RFC 2578 [RFC2578]、STD 58、RFC 2579 [RFC2579]、およびSTD 58、RFC 2580 [RFC2580]で記述されているSMIv2に準拠したMIBモジュールを規定します。

4. Structure of the MIB Module

4. MIBモジュールの構造

The IF-MIB [RFC2863] defines generic managed objects for managing interfaces. Each logical interface (physical or virtual) has an ifEntry. Tunnels are handled by creating a logical interface (ifEntry) for each tunnel. Each MAP-E tunnel endpoint also acts as a virtual interface that has a corresponding entry in the IF-MIB. Those corresponding entries are indexed by ifIndex. The MAP-E MIB is configurable on a per-interface basis, so it depends on several parts (ifEntry) of the IF-MIB [RFC2863].

IF-MIB [RFC2863]は、インターフェイスを管理するための汎用的な管理オブジェクトを定義しています。各論理インターフェイス（物理または仮想）はifEntryを持ちます。トンネルは、トンネルごとに論理インターフェイス（ifEntry）を作成することで扱われます。各MAP-Eトンネルエンドポイントも、IF-MIB内に対応するエントリーを持つ仮想インターフェイスとして機能します。これらの対応するエントリーは、ifIndexによってインデックス付けされます。MAP-E MIBはインターフェイスごとに設定可能であるため、IF-MIB [RFC2863]のいくつかの部分（ifEntry）に依存します。

4.1. The mapMIBObjects

4.1. mapMIBObjects

4.1.1. The mapRule Subtree

4.1.1. mapRuleサブツリー

The mapRule subtree describes managed objects used for managing the multiple mapping rules in MAP-E.

mapRuleサブツリーは、MAP-Eにおける複数のマッピング規則を管理するために使用する管理オブジェクトを記述します。

According to [RFC7597], the mapping rules are divided into two categories: Basic Mapping Rule (BMR) and Forwarding Mapping Rule (FMR). According to Section 4.1 of [RFC7598], an F-flag specifies whether the rule is to be used for forwarding (FMR). If set, this rule is used as an FMR; if not set, this rule is BMR only and MUST NOT be used for forwarding. A BMR can also be used as an FMR for forwarding if the F-flag is set. So, the RuleType definition in the MAP-E MIB (see Section 5) defines bmrAndfmr to specify this scenario.

[RFC7597]によると、マッピング規則は基本マッピング規則（Basic Mapping Rule、BMR）と転送マッピング規則（Forwarding Mapping Rule、FMR）の2つのカテゴリーに分けられます。[RFC7598]のセクション4.1によると、Fフラグは、その規則を転送（FMR）に使用するかどうかを指定します。Fフラグがセットされている場合、その規則はFMRとして使用されます。セットされていない場合、その規則はBMR専用であり、転送に使用してはなりません（MUST NOT）。Fフラグがセットされていれば、BMRを転送用のFMRとしても使用できます。そのため、MAP-E MIBのRuleTypeの定義（セクション5を参照）では、この状況を指定するためにbmrAndfmrを定義しています。

4.1.2. The mapSecurityCheck Subtree

4.1.2. mapSecurityCheckサブツリー

The mapSecurityCheck subtree provides statistics for the number of invalid packets that have been identified. [RFC7597] defines two kinds of invalid packets:

mapSecurityCheckサブツリーは、検出された無効なパケットの数の統計情報を提供します。[RFC7597]では、2種類の無効なパケットを定義しています。

  • The Border Relay (BR) will validate the received packet's source IPv6 address against the configured MAP domain rule and the destination IPv6 address against the configured BR IPv6 address.
  • The MAP node (Customer Edge (CE) and BR) will check that the received packet's source IPv4 address and port are in the range derived from the matching MAP rule.
  • ボーダーリレー（Border Relay、BR）は、受信したパケットの送信元IPv6アドレスを設定済みのMAPドメインの規則と照合し、宛先IPv6アドレスを設定済みのBRのIPv6アドレスと照合して検証します。
  • MAPノード（顧客エッジ（Customer Edge、CE）およびBR）は、受信したパケットの送信元IPv4アドレスとポートが、一致するMAP規則から導出された範囲内にあることを確認します。

4.2. The mapMIBConformance Subtree

4.2. mapMIBConformanceサブツリー

The mapMIBConformance subtree provides conformance information of MIB objects.

mapMIBConformanceサブツリーは、MIBオブジェクトの適合性情報を提供します。

7. Security Considerations

7. セキュリティーに関する考慮事項

There are no management objects defined in this MIB module that have a MAX-ACCESS clause of read-write and/or read-create. So, if this MIB module is implemented correctly, then there is no risk that an intruder can alter or create any management objects of this MIB module via direct SNMP SET operations.

このMIBモジュールには、MAX-ACCESS句がread-writeまたはread-create（あるいはその両方）である管理オブジェクトは定義されていません。したがって、このMIBモジュールが正しく実装されていれば、侵入者が直接のSNMP SET操作によってこのMIBモジュールの管理オブジェクトを変更したり作成したりする危険はありません。

Some of the objects in this MIB module may be considered sensitive or vulnerable in some network environments. This includes INDEX objects with a MAX-ACCESS of not-accessible, and any indices from other modules exposed via AUGMENTS. It is thus important to control even GET and/or NOTIFY access to these objects and possibly to even encrypt the values of these objects when sending them over the network via SNMP. These are the tables and objects and their sensitivity/vulnerability:

このMIBモジュールのオブジェクトの一部は、ネットワーク環境によっては機密である、または脆弱であるとみなされる場合があります。これには、MAX-ACCESSがnot-accessibleであるINDEXオブジェクトや、AUGMENTSを介して公開される他のモジュールのインデックスが含まれます。したがって、これらのオブジェクトへのGETアクセスやNOTIFYアクセス（あるいはその両方）さえも制御し、場合によってはSNMPを介してネットワーク上で送信する際にこれらのオブジェクトの値を暗号化することさえ重要です。以下に、これらのテーブルとオブジェクト、およびその機密性・脆弱性を示します。

  • mapRuleIPv6Prefix
  • mapRuleIPv6PrefixLen
  • mapRuleIPv4Prefix
  • mapRuleIPv4PrefixLen
  • mapRuleBRIPv6Address
  • mapRulePSID
  • mapRulePSIDLen
  • mapRuleOffset
  • mapRuleEALen
  • mapRuleType
  • mapRuleIPv6Prefix
  • mapRuleIPv6PrefixLen
  • mapRuleIPv4Prefix
  • mapRuleIPv4PrefixLen
  • mapRuleBRIPv6Address
  • mapRulePSID
  • mapRulePSIDLen
  • mapRuleOffset
  • mapRuleEALen
  • mapRuleType

Some of the MIB model's objects are vulnerable because the information that they hold may be used for targeting an attack against a MAP node (CE or BR). For example, an intruder could use the information to help deduce the customer IPv4 and IPv6 topologies and address-sharing ratios in use by the ISP.

このMIBモデルのオブジェクトの一部は、保持している情報がMAPノード（CEまたはBR）を標的とした攻撃に使用されるおそれがあるため、脆弱です。たとえば、侵入者はこの情報を使って、ISPが使用している顧客のIPv4およびIPv6のトポロジーやアドレス共有率を推測する手がかりにできます。

SNMP versions prior to SNMPv3 did not include adequate security. Even if the network itself is secure (for example by using IPsec), there is no control as to who on the secure network is allowed to access and GET/SET (read/change/create/delete) the objects in this MIB module.

SNMPv3より前のバージョンのSNMPには、十分なセキュリティーが含まれていませんでした。ネットワーク自体が安全であっても（たとえばIPsecを使用している場合）、安全なネットワーク上の誰がこのMIBモジュールのオブジェクトにアクセスしてGET/SET（読み取り・変更・作成・削除）できるかについては制御がありません。

Implementations SHOULD provide the security features described by the SNMPv3 framework (see [RFC3410]), and implementations claiming compliance to the SNMPv3 standard MUST include full support for authentication and privacy via the User-based Security Model (USM) [RFC3414] with the AES cipher algorithm [RFC3826]. Implementations MAY also provide support for the Transport Security Model (TSM) [RFC5591] in combination with a secure transport such as SSH [RFC5592] or TLS/DTLS [RFC6353].

実装は、SNMPv3フレームワークで説明されているセキュリティー機能を提供すべきです（SHOULD）（[RFC3410]を参照）。また、SNMPv3標準への準拠を主張する実装は、AES暗号アルゴリズム[RFC3826]を用いたユーザーベースセキュリティーモデル（USM）[RFC3414]による認証とプライバシーを完全にサポートしなければなりません（MUST）。実装は、SSH [RFC5592]やTLS/DTLS [RFC6353]などの安全なトランスポートと組み合わせて、トランスポートセキュリティーモデル（TSM）[RFC5591]のサポートも提供してもよいです（MAY）。

Further, deployment of SNMP versions prior to SNMPv3 is NOT RECOMMENDED. Instead, it is RECOMMENDED to deploy SNMPv3 and to enable cryptographic security. It is then a customer/operator responsibility to ensure that the SNMP entity giving access to an instance of this MIB module is properly configured to give access to the objects only to those principals (users) that have legitimate rights to indeed GET or SET (change/create/delete) them.

さらに、SNMPv3より前のバージョンのSNMPを展開することは推奨されません（NOT RECOMMENDED）。代わりに、SNMPv3を展開し、暗号によるセキュリティーを有効にすることが推奨されます（RECOMMENDED）。そのうえで、このMIBモジュールのインスタンスへのアクセスを提供するSNMPエンティティーが、オブジェクトを実際にGETまたはSET（変更・作成・削除）する正当な権利を持つプリンシパル（ユーザー）にのみオブジェクトへのアクセスを与えるよう適切に設定されていることを保証するのは、顧客・運用者の責任です。
