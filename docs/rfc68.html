RFC 68

Comments on memory allocation control commands CEASE, ALL, GVB, RET) and RFNM

RFC 68

メモリー割り当て制御コマンド（CEASE、ALL、GVB、RET）とRFNMについてのコメント

Abstract

概要

The protocol provides a scheme for buffer allocation. This scheme is rather complicated because it necessitates two parallel mechanisms. It is not obvious that both are necessary. In fact it is suggested that this scheme could be probably replaced by a slightly different conception of the Request for Next Message (RFNM). Now the RFNM is sent back from the receiving imp after the message has been reconstituted and the first packet transmitted to the host. Nothing insures that the whole message has been accepted and correctly received by the host; also the design of the host imp interface permits the host to stop accepting data from the imp during any length of time; as the link has been already unblocked by sending back the RFNM another message may be transmitted by the sending foreign host which will congest the imp's memory. On the other hand it is probable that usually the host is able to accept data from the imp at a higher rate than it is transmitted on the network, e.g. 200k bits/sec; thus the time to transmit a full message from the imp to the host would be approximately 1/20th of a second which is 10 times less than the average delay of transmission of a message over the network. This indicates that to send a RFNM after the reception of a full message by the host would not increase significantly the response time on the network.

プロトコルはバッファー割り当ての方式を提供しています。この方式は、2つの並行するメカニズムを必要とするため、かなり複雑です。両方が必要かどうかは明らかではありません。実際のところ、この方式はおそらく、次メッセージ要求（Request for Next Message、RFNM）の考え方を少し変えたもので置き換えられると考えられます。現在、RFNMは、メッセージが再構成されて最初のパケットがホストに送信された後に、受信側のIMPから返送されます。メッセージ全体がホストに受け入れられ、正しく受信されたことを保証するものは何もありません。また、ホストとIMPのインターフェイスの設計上、ホストはIMPからのデータの受け入れを任意の時間停止できます。RFNMを返送したことでリンクのブロックはすでに解除されているため、送信側の外部ホストが別のメッセージを送信するかもしれず、それがIMPのメモリーを混雑させることになります。一方で、通常、ホストはネットワーク上で送信されるよりも高い速度、たとえば200kビット/秒でIMPからデータを受け入れられると考えられます。そのため、IMPからホストへメッセージ全体を送信する時間はおよそ1/20秒となり、これはネットワーク上でのメッセージの平均伝送遅延の10分の1です。このことから、ホストがメッセージ全体を受信した後にRFNMを送信しても、ネットワークの応答時間はそれほど増えないことがわかります。

In this case there is no reason why the RFNM could not be initiated by the receiving host as an acknowledgment of the correct reception of the message (ACK), and take the form of either a host imp or a control command message. This RFNM could have the two forms

この場合、受信側のホストが、メッセージを正しく受信したことの確認応答（ACK）としてRFNMを発行し、それをホストとIMP間のメッセージか制御コマンドのメッセージのどちらかの形にできない理由はありません。このRFNMは、次の2つの形をとることができます。

         ACK  (CONTINUE)
or       ACK  (CEASE)

         ACK  (CONTINUE)
or       ACK  (CEASE)

This would permit to add to the message some error detection redundancy, such as check sum bits as proposed in [DELO 69]. In the present design nothing insures that one or several bits of the text has not been altered, e.g., by an interference or a deficiency of one of the host imp interfaces. This could have important consequences, e.g. if the text is used to update a centralized data base. Also, if the user has a way of detecting the error, but none of correcting it, it has no way of asking for the retransmission of the message, which has probably been discarded at the sending end upon reception of the RFNM. In fact it seems not up to the user to have to detect errors in its text but rather up to the NCP: the user process must as much as possible act as if it was talking to some other local process. So a third kind of RFNM sent by the NCP could be:

こうすれば、[DELO 69]で提案されているチェックサムビットのような、誤り検出のための冗長性をメッセージに追加できるようになります。現在の設計では、たとえば干渉やホストとIMPのインターフェイスのどれかの不具合によって、テキストの1ビットまたは数ビットが変化していないことを保証するものは何もありません。これは、たとえばテキストが集中型のデータベースの更新に使われる場合には、重大な結果をもたらす可能性があります。また、ユーザーが誤りを検出する手段を持っていても、それを訂正する手段を持っていなければ、メッセージの再送を求める手段はありません。そのメッセージは、RFNMを受け取った時点でおそらく送信側で破棄されているからです。実際、テキストの誤りを検出しなければならないのはユーザーではなく、NCPであるように思われます。ユーザープロセスは、できる限り、ほかのローカルのプロセスと会話しているかのように振る舞えなければなりません。そこで、NCPが送信する第3の種類のRFNMとして、次のものが考えられます。

            NAK(REPEAT)

            NAK(REPEAT)

Repetition would also be initiated in case of no reply.

応答がない場合にも再送が開始されます。

Thus we see that it seems worthwhile to make these slight modifications which would permit to use between the sending host and the receiving host a very simple point-to-point transmission procedure which would insure control of the data transmitted from end-to-end.

このように、こうしたわずかな変更を加えることには価値があると思われます。この変更により、送信側のホストと受信側のホストの間で非常に単純なポイントツーポイントの伝送手順を使えるようになり、送信するデータの制御をエンドツーエンドで保証できるようになります。

It could also replace the memory allocation mechanism: ACK (CONTINUE) would only be sent if space was available for a new message on this connection and/or ACK (CEASE) would be sent if no more space was available; it corresponds to the WABT of classic transmission procedures [USAS69]; transmission could be resumed by an ACK (CONTINUE) or a RESUME from the receiving end. The user process is not mixed at all with this memory allocation which is a function of the system (or NCP): it only sees a varying global transmission speed of its data on a connection. The imp programs take care of the routing of the data according to the distributed nature of the network, and neither the user nor the system (or NCP) is concerned with it. Other improvements to the protocol may be found after experiencing it.

これはメモリー割り当てのメカニズムを置き換えることもできます。ACK (CONTINUE) は、このコネクションで新しいメッセージのための領域が利用可能な場合にのみ送信し、ACK (CEASE) は、それ以上の領域が利用できない場合に送信するようにします。これは、古典的な伝送手順[USAS69]のWABTに相当します。伝送は、受信側からのACK (CONTINUE) またはRESUMEによって再開できます。ユーザープロセスは、システム（またはNCP）の機能であるこのメモリー割り当てにはまったく関わりません。ユーザープロセスに見えるのは、コネクション上でのデータの全体的な伝送速度が変化することだけです。IMPのプログラムがネットワークの分散的な性質に応じてデータのルーティングを行うので、ユーザーもシステム（またはNCP）もそれに関与しません。プロトコルのその他の改良点は、実際に使ってみた後で見つかるかもしれません。

Finally note that this solution does not immobilize the imp memory any longer than the actual solution, because it is not the imp which has to repeat a message, but the sending host.

最後に、この解決策では、現在の解決策よりも長くIMPのメモリーを占有することはないことに注意してください。メッセージを再送しなければならないのはIMPではなく、送信側のホストだからです。
