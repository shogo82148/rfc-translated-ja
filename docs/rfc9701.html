JSON Web Token (JWT) Response for OAuth Token Introspection

RFC 9701

OAuthトークンイントロスペクションのためのJSON Web Token（JWT）レスポンス

Abstract

概要

This specification proposes an additional response secured by JSON Web Token (JWT) for OAuth 2.0 Token Introspection.

この仕様は、OAuth 2.0トークンイントロスペクションのために、JSON Web Token（JWT）で保護された追加のレスポンスを提案します。

1. Introduction

1. はじめに

[RFC7662] specifies a method for a protected resource to query an OAuth 2.0 authorization server to determine the state of an access token and obtain data associated with the access token. This enables deployments to implement opaque access tokens in an interoperable way.

[RFC7662]は、保護されたリソースがOAuth 2.0認可サーバーに問い合わせて、アクセストークンの状態を判断し、そのアクセストークンに関連付けられたデータを取得する方法を規定しています。 これにより、デプロイメントは不透明なアクセストークンを相互運用可能な方法で実装できます。

The introspection response, as specified in [RFC7662], is a plain JSON object. However, there are use cases where the resource server requires stronger assurance that the authorization server issued the token introspection response for an access token, including cases where the authorization server assumes liability for the content of the token introspection response. An example is a resource server using verified personal data to create certificates, which in turn are used to create qualified electronic signatures.

[RFC7662]で規定されているイントロスペクションレスポンスは、単純なJSONオブジェクトです。 しかし、アクセストークンに対するトークンイントロスペクションレスポンスを認可サーバーが発行したことについて、リソースサーバーがより強い保証を必要とするユースケースがあります。 これには、認可サーバーがトークンイントロスペクションレスポンスの内容に対して責任を負う場合も含まれます。 その例として、検証済みの個人データを使用して証明書を作成し、その証明書を使って適格電子署名（qualified electronic signature）を作成するリソースサーバーがあります。

In such use cases, it may be useful or even required to return a signed [RFC7519] as the introspection response. This specification extends the token introspection endpoint with the capability to return responses as JWTs.

このようなユースケースでは、イントロスペクションレスポンスとして署名付きの[RFC7519]を返すことが有用な場合や、必須な場合さえあります。 この仕様は、レスポンスをJWTとして返す機能によってトークンイントロスペクションエンドポイントを拡張します。

3. Resource Server Management

3. リソースサーバーの管理

The authorization server (AS) and the resource server (RS) maintain a strong, two-way trust relationship. The resource server relies on the authorization server to obtain authorization, user, and other data as input to its access control decisions and service delivery. The authorization server relies on the resource server to handle the provided data appropriately.

認可サーバー（authorization server、AS）とリソースサーバー（resource server、RS）は、強固な双方向の信頼関係を維持します。 リソースサーバーは、アクセス制御の判断とサービス提供の入力として、認可データ、ユーザーデータ、その他のデータを取得するために認可サーバーに依存します。 認可サーバーは、提供したデータをリソースサーバーが適切に取り扱うことに依存します。

In the context of this specification, the token introspection endpoint is used to convey such security data and potentially also privacy-sensitive data related to an access token.

この仕様の文脈では、トークンイントロスペクションエンドポイントは、そのようなセキュリティーデータを伝達するために使用され、場合によってはアクセストークンに関連するプライバシー上センシティブなデータも伝達します。

In order to process the introspection requests in a secure and privacy-preserving manner, the authorization server MUST be able to identify, authenticate, and authorize resource servers.

イントロスペクションリクエストを安全かつプライバシーを保護する方法で処理するために、認可サーバーはリソースサーバーを識別、認証、認可できなければなりません（MUST）。

The AS MAY additionally encrypt the token introspection response JWTs. If encryption is used, the AS is provisioned with encryption keys and algorithms for the RS.

ASは、さらにトークンイントロスペクションレスポンスのJWTを暗号化してもよいです（MAY）。 暗号化を使用する場合、ASにはそのRS用の暗号化鍵とアルゴリズムが設定されます。

The AS MUST be able to determine whether an RS is the audience for a particular access token and what data it is entitled to receive; otherwise, the RS is not authorized to obtain data for the access token. The AS has the discretion of how to fulfill this requirement. The AS could, for example, maintain a mapping between scope values and RSs.

ASは、RSが特定のアクセストークンのオーディエンスであるかどうかと、そのRSがどのデータを受け取る権利を持つかを判断できなければなりません（MUST）。 そうでなければ、RSはそのアクセストークンのデータを取得することを認可されません。 この要件をどのように満たすかはASの裁量に委ねられます。 たとえば、ASはスコープ値とRSの対応付けを維持することが考えられます。

The requirements given above imply that the AS maintains credentials and other configuration data for each RS.

上記の要件は、ASがRSごとにクレデンシャルとその他の設定データを維持することを意味します。

One way is by utilizing dynamic client registration [RFC7591] and treating every RS as an OAuth client. In this case, the AS is assumed to at least maintain a "client_id" and a "token_endpoint_auth_method" with complementary authentication method metadata, such as "jwks" or "client_secret". In cases where the AS needs to acquire consent to transmit data to an RS, the following client metadata fields are recommended: "client_name", "client_uri", "contacts", "tos_uri", and "policy_uri".

その方法の1つは、動的クライアント登録[RFC7591]を利用し、すべてのRSをOAuthクライアントとして扱うことです。 この場合、ASは少なくとも「client_id」と「token_endpoint_auth_method」を、「jwks」や「client_secret」などの補完的な認証方式のメタデータとともに維持していることが想定されます。 RSにデータを送信するためにASが同意を取得する必要がある場合には、次のクライアントメタデータフィールドが推奨されます：「client_name」、「client_uri」、「contacts」、「tos_uri」、「policy_uri」。

The AS MUST restrict the use of client credentials by an RS to the calls it requires, e.g., the AS MAY restrict such a client to call the token introspection endpoint only. How the AS implements this restriction is beyond the scope of this specification.

ASは、RSによるクライアントクレデンシャルの使用を、そのRSが必要とする呼び出しに制限しなければなりません（MUST）。 たとえば、ASはそのようなクライアントがトークンイントロスペクションエンドポイントだけを呼び出せるように制限してもよいです（MAY）。 ASがこの制限をどのように実装するかは、この仕様の範囲外です。

This specification further introduces client metadata to manage the configuration options required to sign and encrypt token introspection response JWTs.

この仕様はさらに、トークンイントロスペクションレスポンスのJWTの署名と暗号化に必要な設定オプションを管理するためのクライアントメタデータを導入します。

4. Requesting a JWT Response

4. JWTレスポンスのリクエスト

An RS requests a JWT introspection response by sending an introspection request with an Accept HTTP header field set to "application/token-introspection+jwt".

RSは、Accept HTTPヘッダーフィールドを「application/token-introspection+jwt」に設定したイントロスペクションリクエストを送信することで、JWTイントロスペクションレスポンスをリクエストします。

The AS MUST authenticate the caller at the token introspection endpoint. Authentication can utilize client authentication methods or a separate access token that is issued to the RS and identifies the RS as the subject.

ASは、トークンイントロスペクションエンドポイントで呼び出し元を認証しなければなりません（MUST）。 認証には、クライアント認証方式を利用することも、RSに対して発行され、RSをサブジェクトとして識別する別のアクセストークンを利用することもできます。

The following is a non-normative example request, with the RS authenticating with a private key JWT:

以下は、RSが秘密鍵JWTで認証するリクエストの非規範的な例です：

POST /introspect HTTP/1.1
Host: as.example.com
Accept: application/token-introspection+jwt
Content-Type: application/x-www-form-urlencoded

token=2YotnFZFEjr1zCsicMWpAA&
client_assertion_type=
 urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer&
 client_assertion=PHNhbWxwOl[...omitted for brevity...]ZT

POST /introspect HTTP/1.1
Host: as.example.com
Accept: application/token-introspection+jwt
Content-Type: application/x-www-form-urlencoded

token=2YotnFZFEjr1zCsicMWpAA&
client_assertion_type=
 urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer&
 client_assertion=PHNhbWxwOl[...omitted for brevity...]ZT

5. JWT Response

5. JWTレスポンス

The introspection endpoint responds with a JWT, setting the Content-Type HTTP header field to "application/token-introspection+jwt" and the JWT typ ("type") header parameter to "token-introspection+jwt".

イントロスペクションエンドポイントは、Content-Type HTTPヘッダーフィールドを「application/token-introspection+jwt」に、JWTのtyp（「type」）ヘッダーパラメーターを「token-introspection+jwt」に設定して、JWTでレスポンスします。

The JWT MUST include the following top-level claims:

JWTは、次のトップレベルのクレームを含めなければなりません（MUST）：

iss
MUST be set to the issuer URL of the authorization server.
aud
MUST identify the resource server receiving the token introspection response.
iat
MUST be set to the time when the introspection response was created by the authorization server
token_introspection

A JSON object containing the members of the token introspection response, as specified in [RFC7662], Section 2.2. The separation of the introspection response members into a dedicated JSON object containing a JWT claim is intended to prevent conflict and confusion with top-level JWT claims that may bear the same name.

If the access token is invalid, expired, revoked, or not intended for the calling resource server (audience), the authorization server MUST set the value of the active member in the token_introspection claim to false and MUST NOT include other members. Otherwise, the active member is set to true.

The AS SHOULD narrow down the scope value to the scopes relevant to the particular RS.

As specified in Section 2.2 of [RFC7662], implementations MAY extend the token introspection response with service-specific claims. In the context of this specification, such claims will be added as top-level members of the token_introspection claim.

Token introspection response parameter names intended to be used across domains MUST be registered in the [IANA.OAuth.Token.Introspection] defined by [RFC7662].

When the AS acts as a provider of resource owner identity claims to the RS, the AS determines, based on its RS-specific policy, what identity claims to return in the token introspection response. The AS MUST ensure the release of any privacy-sensitive data is legally based (see Section 9).

Further content of the introspection response is determined by the RS-specific policy at the AS.

iss
認可サーバーの発行者URLに設定されなければなりません（MUST）。
aud
トークンイントロスペクションレスポンスを受信するリソースサーバーを識別しなければなりません（MUST）。
iat
認可サーバーがイントロスペクションレスポンスを作成した時刻に設定されなければなりません（MUST）。
token_introspection

[RFC7662], Section 2.2で規定されているトークンイントロスペクションレスポンスのメンバーを含むJSONオブジェクトです。 イントロスペクションレスポンスのメンバーを、JWTクレームを持つ専用のJSONオブジェクトに分離するのは、同じ名前を持つ可能性のあるトップレベルのJWTクレームとの衝突や混同を防ぐためです。

アクセストークンが無効である、期限切れである、取り消されている、または呼び出し元のリソースサーバー（オーディエンス）向けではない場合、認可サーバーはtoken_introspectionクレーム内のactiveメンバーの値をfalseに設定しなければなりません（MUST）。 また、その他のメンバーを含めてはなりません（MUST NOT）。 それ以外の場合、activeメンバーはtrueに設定されます。

ASは、scopeの値を、特定のRSに関連するスコープに絞り込むべきです（SHOULD）。

[RFC7662]のSection 2.2で規定されているように、実装はサービス固有のクレームによってトークンイントロスペクションレスポンスを拡張してもよいです（MAY）。 この仕様の文脈では、そのようなクレームはtoken_introspectionクレームのトップレベルのメンバーとして追加されます。

ドメインをまたいで使用することを意図したトークンイントロスペクションレスポンスのパラメーター名は、[RFC7662]で定義された[IANA.OAuth.Token.Introspection]に登録されなければなりません（MUST）。

ASがリソースオーナーの識別情報クレーム（identity claim）の提供者としてRSに対して振る舞う場合、ASは、RS固有のポリシーに基づいて、トークンイントロスペクションレスポンスでどの識別情報クレームを返すかを決定します。 ASは、プライバシー上センシティブなデータの開示が法的根拠に基づくことを保証しなければなりません（MUST）（Section 9を参照）。

イントロスペクションレスポンスのその他の内容は、AS上のRS固有のポリシーによって決定されます。

The JWT MAY include other claims, including those from the "JSON Web Token Claims" registry established by [RFC7519]. The JWT SHOULD NOT include the sub and exp claims, as an additional measure to prevent misuse of the JWT as an access token (see Section 8.1).

JWTは、[RFC7519]によって設立された「JSON Web Token Claims」レジストリーに含まれるクレームなど、他のクレームを含めてもよいです（MAY）。 JWTがアクセストークンとして悪用されるのを防ぐ追加の対策として、JWTはsubクレームとexpクレームを含めるべきではありません（SHOULD NOT）（Section 8.1を参照）。

Note: Although the JWT format is widely used as an access token format, the JWT returned in the introspection response is not an alternative representation of the introspected access token and is not intended to be used as an access token.

注：JWT形式はアクセストークンの形式として広く使用されていますが、イントロスペクションレスポンスで返されるJWTは、イントロスペクションの対象となったアクセストークンの代替表現ではなく、アクセストークンとして使用されることを意図したものではありません。

This specification registers the "application/token-introspection+jwt" media type, which is used as the value of the typ ("type") header parameter of the JWT to indicate that the payload is a token introspection response.

この仕様は「application/token-introspection+jwt」メディアタイプを登録します。 このメディアタイプは、ペイロードがトークンイントロスペクションレスポンスであることを示すために、JWTのtyp（「type」）ヘッダーパラメーターの値として使用されます。

The JWT is cryptographically secured as specified in [RFC7519].

JWTは、[RFC7519]で規定されているとおりに暗号学的に保護されます。

Depending on the specific resource server policy, the JWT is either signed or signed and encrypted. If the JWT is signed and encrypted, it MUST be a Nested JWT, as defined in [RFC7519].

個々のリソースサーバーのポリシーに応じて、JWTは署名されるか、署名されたうえで暗号化されます。 JWTが署名されたうえで暗号化される場合、それは[RFC7519]で定義されているNested JWTでなければなりません（MUST）。

Note: An AS compliant with this specification MUST refuse to serve introspection requests that don't authenticate the caller and return an HTTP status code 400. This is done to ensure token data is released to legitimate recipients only and prevent downgrading to [RFC7662] behavior (see Section 8.2).

注：この仕様に準拠するASは、呼び出し元を認証しないイントロスペクションリクエストへの対応を拒否し、HTTPステータスコード400を返さなければなりません（MUST）。 これは、トークンデータが正当な受信者にのみ開示されることを保証し、[RFC7662]の動作へのダウングレードを防ぐためです（Section 8.2を参照）。

6. Client Metadata

6. クライアントメタデータ

The authorization server determines the algorithm to secure the JWT for a particular introspection response. This decision can be based on registered metadata parameters for the resource server, supplied via dynamic client registration [RFC7591] with the resource server acting as a client, as specified below.

認可サーバーは、特定のイントロスペクションレスポンスについて、JWTを保護するためのアルゴリズムを決定します。 この決定は、以下で規定するように、リソースサーバーがクライアントとして振る舞い、動的クライアント登録[RFC7591]によって提供された、そのリソースサーバー用に登録済みのメタデータパラメーターに基づいて行うことができます。

The parameter names follow the pattern established by [OpenID.Registration] for configuring signing and encryption algorithms for JWT responses at the UserInfo endpoint.

パラメーター名は、UserInfoエンドポイントでのJWTレスポンスの署名と暗号化のアルゴリズムを設定するために[OpenID.Registration]で確立されたパターンに従います。

The following client metadata parameters are introduced by this specification:

この仕様では、次のクライアントメタデータパラメーターを導入します：

introspection_signed_response_alg
OPTIONAL. [RFC7515] algorithm (alg value), as defined in [RFC7518], for signing introspection responses. If this is specified, the response will be signed using JWS and the configured algorithm. The default, if omitted, is RS256.
introspection_encrypted_response_alg
OPTIONAL. [RFC7516] algorithm (alg value), as defined in [RFC7518], for content key encryption. If this is specified, the response will be encrypted using JWE and the configured content encryption algorithm (introspection_encrypted_response_enc). The default, if omitted, is that no encryption is performed. If both signing and encryption are requested, the response will be signed then encrypted, with the result being a Nested JWT, as defined in [RFC7519].
introspection_encrypted_response_enc
OPTIONAL. [RFC7516] algorithm (enc value), as defined in [RFC7518], for content encryption of introspection responses. The default, if omitted, is A128CBC-HS256. Note: This parameter MUST NOT be specified without setting introspection_encrypted_response_alg.
introspection_signed_response_alg
選択できます（OPTIONAL）。 イントロスペクションレスポンスに署名するための、[RFC7518]で定義されている[RFC7515]のアルゴリズム（algの値）です。 これが指定された場合、レスポンスはJWSと設定されたアルゴリズムを使用して署名されます。 省略された場合のデフォルトはRS256です。
introspection_encrypted_response_alg
選択できます（OPTIONAL）。 コンテンツ鍵の暗号化のための、[RFC7518]で定義されている[RFC7516]のアルゴリズム（algの値）です。 これが指定された場合、レスポンスはJWEと設定されたコンテンツ暗号化アルゴリズム（introspection_encrypted_response_enc）を使用して暗号化されます。 省略された場合のデフォルトでは、暗号化は行われません。 署名と暗号化の両方がリクエストされた場合、レスポンスは署名されてから暗号化され、その結果は[RFC7519]で定義されているNested JWTになります。
introspection_encrypted_response_enc
選択できます（OPTIONAL）。 イントロスペクションレスポンスのコンテンツ暗号化のための、[RFC7518]で定義されている[RFC7516]のアルゴリズム（encの値）です。 省略された場合のデフォルトはA128CBC-HS256です。 注：このパラメーターは、introspection_encrypted_response_algを設定せずに指定してはなりません（MUST NOT）。

Resource servers may register their public encryption keys using the jwks_uri or jwks metadata parameters.

リソースサーバーは、jwks_uriまたはjwksメタデータパラメーターを使用して、暗号化用の公開鍵を登録できます。

7. Authorization Server Metadata

7. 認可サーバーのメタデータ

Authorization servers SHOULD publish the supported algorithms for signing and encrypting the JWT of an introspection response by utilizing [RFC8414] parameters. Resource servers use this data to parametrize their client registration requests.

認可サーバーは、[RFC8414]のパラメーターを利用して、イントロスペクションレスポンスのJWTの署名と暗号化でサポートするアルゴリズムを公開すべきです（SHOULD）。 リソースサーバーは、このデータを使用してクライアント登録リクエストのパラメーターを決定します。

The following parameters are introduced by this specification:

この仕様では、次のパラメーターを導入します：

introspection_signing_alg_values_supported
OPTIONAL. JSON array containing a list of the [RFC7515] signing algorithms (alg values), as defined in [RFC7518], supported by the introspection endpoint to sign the response.
introspection_encryption_alg_values_supported
OPTIONAL. JSON array containing a list of the [RFC7516] encryption algorithms (alg values), as defined in [RFC7518], supported by the introspection endpoint to encrypt the content encryption key for introspection responses (content key encryption).
introspection_encryption_enc_values_supported
OPTIONAL. JSON array containing a list of the [RFC7516] encryption algorithms (enc values), as defined in [RFC7518], supported by the introspection endpoint to encrypt the response (content encryption).
introspection_signing_alg_values_supported
選択できます（OPTIONAL）。 レスポンスに署名するためにイントロスペクションエンドポイントがサポートする、[RFC7518]で定義されている[RFC7515]署名アルゴリズム（algの値）のリストを含むJSON配列です。
introspection_encryption_alg_values_supported
選択できます（OPTIONAL）。 イントロスペクションレスポンスのコンテンツ暗号化鍵を暗号化する（コンテンツ鍵の暗号化）ためにイントロスペクションエンドポイントがサポートする、[RFC7518]で定義されている[RFC7516]暗号化アルゴリズム（algの値）のリストを含むJSON配列です。
introspection_encryption_enc_values_supported
選択できます（OPTIONAL）。 レスポンスを暗号化する（コンテンツ暗号化）ためにイントロスペクションエンドポイントがサポートする、[RFC7518]で定義されている[RFC7516]暗号化アルゴリズム（encの値）のリストを含むJSON配列です。

8. Security Considerations

8. セキュリティーに関する考慮事項

8.1. Cross-JWT Confusion

8.1. JWT間の混同

The iss and potentially the aud claim of a token introspection JWT can resemble those of a JWT-encoded access token. An attacker could try to exploit this and pass a JWT token introspection response as an access token to the resource server. The typ ("type") JWT header "token-introspection+jwt" and the encapsulation of the token introspection members, such as sub and scope in the token_introspection claim, are intended to prevent such substitution attacks. Resource servers MUST therefore check the typ JWT header value of received JWT-encoded access tokens and ensure all minimally required claims for a valid access token are present.

トークンイントロスペクションJWTのissクレームと、場合によってはaudクレームは、JWTでエンコードされたアクセストークンのものと似ていることがあります。 攻撃者はこれを悪用して、JWTのトークンイントロスペクションレスポンスをアクセストークンとしてリソースサーバーに渡そうとする可能性があります。 typ（「type」）JWTヘッダーの「token-introspection+jwt」と、subやscopeなどのトークンイントロスペクションのメンバーをtoken_introspectionクレーム内にカプセル化することは、このような置換攻撃を防ぐことを意図しています。 したがって、リソースサーバーは、受信したJWTエンコードのアクセストークンのtyp JWTヘッダーの値をチェックし、有効なアクセストークンに最低限必要なクレームがすべて存在することを確認しなければなりません（MUST）。

Resource servers MUST additionally apply the countermeasures against access token replay, as described in [RFC9700].

リソースサーバーはさらに、[RFC9700]で説明されているアクセストークンのリプレイへの対策を適用しなければなりません（MUST）。

JWT confusion and other attacks involving JWTs are discussed in [RFC8725].

JWTの混同や、JWTに関するその他の攻撃については、[RFC8725]で議論されています。

8.2. Token Data Leakage

8.2. トークンデータの漏洩

The authorization server MUST use Transport Layer Security (TLS) 1.2 (or higher), per BCP 195 [RFC9325], in order to prevent token data leakage.

認可サーバーは、トークンデータの漏洩を防ぐために、BCP 195 [RFC9325]に従って、Transport Layer Security（TLS）1.2（またはそれ以上）を使用しなければなりません（MUST）。

Section 2.1 of [RFC7662] permits requests to the introspection endpoint to be authorized with an access token that doesn't identify the caller. To prevent introspection of tokens by parties that are not the intended consumer, the authorization server MUST require all requests to the token introspection endpoint to be authenticated.

[RFC7662]のSection 2.1は、呼び出し元を識別しないアクセストークンによってイントロスペクションエンドポイントへのリクエストを認可することを許可しています。 意図された利用者ではない当事者によるトークンのイントロスペクションを防ぐために、認可サーバーは、トークンイントロスペクションエンドポイントへのすべてのリクエストに認証を要求しなければなりません（MUST）。

9. Privacy Considerations

9. プライバシーに関する考慮事項

The token introspection response can be used to transfer personal identifiable information (PII) from the AS to the RS. The AS MUST conform to legal and jurisdictional constraints for the data transfer before any data is released to a particular RS. The details and determining of these constraints vary by jurisdiction and are outside the scope of this document.

トークンイントロスペクションレスポンスは、個人を特定できる情報（personal identifiable information、PII）をASからRSに転送するために使用できます。 ASは、特定のRSに何らかのデータを開示する前に、データ転送に関する法的および管轄上の制約に従わなければなりません（MUST）。 これらの制約の詳細とその判断は管轄によって異なり、この文書の範囲外です。

A commonly found way to establish the legal basis for releasing PII is by explicit user consent gathered from the resource owner by the AS during the authorization flow.

PIIを開示するための法的根拠を確立する一般的な方法は、認可フローの間にASがリソースオーナーから明示的なユーザーの同意を得ることです。

It is also possible that the legal basis is established out of band, for example, in an explicit contract or by the client gathering the resource owner's consent.

たとえば明示的な契約によって、あるいはクライアントがリソースオーナーの同意を得ることによって、法的根拠が帯域外で確立されることもあり得ます。

If the AS and the RS belong to the same legal entity (1st party scenario), there is potentially no need for an explicit user consent, but the terms of service and policy of the respective service provider MUST be enforced at all times.

ASとRSが同じ法人に属する場合（ファーストパーティーのシナリオ）、明示的なユーザーの同意は必要ない可能性がありますが、それぞれのサービス提供者の利用規約とポリシーは常に適用されなければなりません（MUST）。

In any case, the AS MUST ensure that the scope of the legal basis is enforced throughout the whole process. The AS MUST retain the scope of the legal basis with the access token, e.g., in the scope value, it MUST authenticate the RS, and the AS MUST determine the data an RS is allowed to receive based on the RS's identity and suitable token data, e.g., the scope value.

いずれの場合も、ASは、法的根拠の範囲がプロセス全体を通じて適用されることを保証しなければなりません（MUST）。 ASは、法的根拠の範囲をアクセストークンとともに（たとえばスコープ値として）保持しなければなりません（MUST）。 また、ASはRSを認証しなければなりません（MUST）。 さらに、ASは、RSが受け取ることを許可されるデータを、RSの識別情報と適切なトークンデータ（たとえばスコープ値）に基づいて決定しなければなりません（MUST）。

Implementers should be aware that a token introspection request lets the AS know when the client (and potentially the user) is accessing the RS, which is also an indication of when the user is using the client. If this implication is not acceptable, implementers MUST use other means to relay access token data, for example, by directly transferring the data needed by the RS within the access token.

実装者は、トークンイントロスペクションリクエストによって、クライアント（および場合によってはユーザー）がいつRSにアクセスしているかをASが知ることになり、それはユーザーがいつクライアントを使用しているかの手がかりにもなることに注意してください。 この影響が受け入れられない場合、実装者は、たとえばRSが必要とするデータをアクセストークン内で直接転送するなど、アクセストークンのデータを中継するための他の手段を使用しなければなりません（MUST）。
