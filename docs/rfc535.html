RFC 535

Comments on File Access Protocol

RFC 535

ファイルアクセスプロトコルに関するコメント

Abstract

概要

A file access protocol (FAP) of the sort proposed by John Day in RFC 520 is a good idea. The following comments suggest improvements (mostly additions) to the protocol described in RFC 520.

RFC 520でJohn Dayが提案したような種類のファイルアクセスプロトコル（FAP）は良いアイデアです。以下のコメントは、RFC 520で記述されたプロトコルに対する改善（主に追加）を提案するものです。

  1. (Philosophical comment) The intent of both FTP and FAP is to make it possible for a user to remotely access files. In effect, FTP provides means for a user to have (parts of) file activity of the sort typically initiated at the command language level "slaved" across the network to the site where the file resides. In a similar way the intent of FAP is to provide a mechanism which allows activity of the sort typically initiated by programs at the operating system or monitor level to be "slaved" across the network to the site where the file resides. The OPEN, CLOS, SETP, etc. commands of FAP can be viewed as attempts to define "generic" file system monitor calls. The suggestions made below are further attempts to make features typically available to local users also available to remote users via FAP.

  2. The OPEN command should allow for a third OPEN mode called A for append. In terms of its action with respect to a file and file pointer, the command

       OPEN A FOO

    would be equivalent to the sequence:

       OPEN W FOO
   SETP E

    The difference would be with respect to access control. Many systems allow a user to control separately write and append access to a file (e.g., on TENEX a user usually sets the protection on his MESSAGE.TXT file such that anyone can append to it but only he can write it). For such systems the append OPEN would succeed in many cases in which the write OPEN would fail. The principle here is that FAP (to as large as degree as is practical) should allow remote users to access files in the same way as local users may.

  3. The protocol as proposed allows for the creation of non-sequential files but provides no convenient way for remotely accessing them after they are created. For example if sent to a TENEX server, the sequence:

            OPEN W FOO     //byte size assumed = 36
        SETP B
        WRITE 512
        SETP 1024
        WRITE 512
        CLOS

    would create a file FOO with two pages (on TENEX a page = 512 36 bit words). The two pages would be page #0 and page #2; because page #1 does not exist the file is said to have a "hole" in it. Access to FOO via FAP would be difficult unless the remote user knew its (page) structure prior to access. To support remote access to files such as FOO, FAP should have means for a user to determine a file's structure. Consider a value-returning command that returns the value the file pointer should be set to in order to point to the first byte of the next used page (block or record) beyond the current position of the file pointer. With such a command, call it FNUB (Find Next Used Block), the following sequence could be used to retrieve a holey file such as FOO:

            OPEN R FILE
        SETP B
a:      FNUB               //let x=the value returned
        if x=null
           then CLOS
           else ( SETP x
                  READ 512   //page size=512
                  goto a )

    This presumes that the remote user knows the block (page) size so that he can properly access the file. One can imagine files having blocks of variable size; perhaps FNUB should return two values: the file pointer position of the next block and the size of that block in bytes.

  4. FAP should provide means for a remote user to acquire certain status and "descriptor" information about a given file. The following is a (non-exhaustive) list of information which would be useful to a user remotely accessing TENEX files:

    • user's access to file; can he read, write, execute or append the file?
    • size information; byte size used in last write access (OPEN W) of the file; file size in bytes (of that size).
    • file access dates; date of create, last read, last write.
    • on TENEX a user can specify different access control for different pages within the same file; a remote user should be able to acquire such access control information about files (and be able to specify such access control when he creates them).

  5. There are many applications in which a remote user would like to access several files simultaneously in much the same way as a local user can. FAP as proposed can not support such multiple file access (of course, the user always has the option of going through an ICP to establish another connection with the server). FAP can be extended in a simple way to support multiple file access by including the notion of a "file handle" which is used to specify which file a given FAP command refers to. When the user does:

            OPEN R FOO

    the server's response would include a handle for FOO which the user would use in subsequent references to FOO. The handle returned would be a string of the server's choice; it might be the file's name (FOO), a small integer, etc. Use of a (server chosen) file handle rather than the complete file name enables the server to respond to FAP commands without incurring the overhead of re-parsing the file name for each command. To illustrate, consider the following sequence which opens a file for reading and one for writing, reads 3 bytes from the first file as data, computes using the data and writes a 2 byte result to the second file:

            OPEN R FOO   //server returns FH as handle
        OPEN W MOO   //server returns MH as handle
        READ 3 FH    //user reads data
        //User does some computation on the 3 bytes
        WRIT 2  MH   //user writes the result
        CLOS MH
        CLOS FH

    Reasonable defaults could be provided with handles: e.g., a FAP command without a handle refers to the same file as the previous command; etc. (The association of a handle with a file is probably better achieved via a separate FAP command rather than as a side effect of the OPEN command; e.g.,

            HNDL FOO   )
  6. It is important to take local transformations into account (page 3 of RFC 520). However, it is equally important to allow a remote user to suppress local transformations, if he wishes, so that he can access the file as it is stored. This would enable a program that manipulates a file to work equally well whether the file is local (and accessed "directly" via system calls) or remote (and accessed "indirectly" via system calls that are "trapped" and transformed into FAP commands which are sent to the remote site).
  1. （思想的なコメント）FTPとFAPのどちらも、ユーザーがリモートからファイルにアクセスできるようにすることを意図しています。実質的に、FTPは、通常コマンド言語のレベルで開始されるような種類のファイル操作（の一部）を、ネットワーク越しにファイルが存在するサイトへ「従属」させる手段をユーザーに提供します。同様に、FAPは、通常オペレーティングシステムやモニターのレベルでプログラムによって開始されるような種類の操作を、ネットワーク越しにファイルが存在するサイトへ「従属」させるしくみを提供することを意図しています。FAPのOPEN、CLOS、SETPなどのコマンドは、「汎用的な」ファイルシステムのモニターコールを定義する試みとみなせます。以下の提案は、通常ローカルユーザーが利用できる機能を、FAPを介してリモートユーザーも利用できるようにするためのさらなる試みです。

  2. OPENコマンドでは、追記（append）を表すAという3つ目のOPENモードを使えるようにすべきです。ファイルとファイルポインターに対する動作の点では、次のコマンド

       OPEN A FOO

    は、次の一連のコマンドと等価になります。

       OPEN W FOO
   SETP E

    違いはアクセス制御に関するものです。多くのシステムでは、ユーザーはファイルへの書き込みアクセスと追記アクセスを別々に制御できます（たとえば、TENEXでは、ユーザーは通常、自分のMESSAGE.TXTファイルの保護を、誰でも追記できるが書き込めるのは本人だけになるように設定します）。そのようなシステムでは、書き込みのOPENが失敗するような多くの場合でも、追記のOPENは成功します。ここでの原則は、FAPは（実用的な範囲でできる限り）ローカルユーザーと同じ方法でリモートユーザーがファイルにアクセスできるようにすべきだということです。

  3. 提案されたプロトコルでは非順次ファイルを作成できますが、作成後にそれらにリモートからアクセスする便利な方法がありません。たとえば、TENEXサーバーに次の一連のコマンドを送ると、

            OPEN W FOO     //byte size assumed = 36
        SETP B
        WRITE 512
        SETP 1024
        WRITE 512
        CLOS

    2つのページ（TENEXでは1ページ＝36ビットワード512個）を持つファイルFOOが作成されます。2つのページはページ#0とページ#2になります。ページ#1が存在しないので、このファイルには「穴」があると言います。リモートユーザーがアクセスする前にFOOの（ページ）構造を知っていなければ、FAPを介してFOOにアクセスするのは困難です。FOOのようなファイルへのリモートアクセスをサポートするために、FAPには、ユーザーがファイルの構造を調べる手段があるべきです。ファイルポインターの現在の位置より先にある、次の使用中のページ（ブロックまたはレコード）の先頭バイトを指すために、ファイルポインターに設定すべき値を返す、値を返すコマンドを考えてみてください。そのようなコマンドをFNUB（Find Next Used Block）と呼ぶことにすると、FOOのような穴のあるファイルを取得するのに、次の一連のコマンドを使えます。

            OPEN R FILE
        SETP B
a:      FNUB               //let x=the value returned
        if x=null
           then CLOS
           else ( SETP x
                  READ 512   //page size=512
                  goto a )

    これは、リモートユーザーがファイルに適切にアクセスできるよう、ブロック（ページ）のサイズを知っていることを前提としています。可変サイズのブロックを持つファイルも考えられます。おそらくFNUBは、次のブロックのファイルポインター位置と、そのブロックのバイト単位のサイズという、2つの値を返すべきでしょう。

  4. FAPは、リモートユーザーが特定のファイルに関するある種のステータス情報や「記述子」情報を取得する手段を提供すべきです。以下は、TENEXのファイルにリモートからアクセスするユーザーにとって有用な情報の（網羅的ではない）一覧です。

    • ファイルに対するユーザーのアクセス権。ユーザーはそのファイルを読み込み、書き込み、実行、追記できるか？
    • サイズ情報。ファイルへの最後の書き込みアクセス（OPEN W）で使われたバイトサイズ。（そのサイズの）バイト単位でのファイルサイズ。
    • ファイルアクセスの日付。作成日、最終読み込み日、最終書き込み日。
    • TENEXでは、ユーザーは同じファイル内のページごとに異なるアクセス制御を指定できます。リモートユーザーは、ファイルに関するそのようなアクセス制御情報を取得できる（そして、ファイルを作成するときにそのようなアクセス制御を指定できる）べきです。

  5. ローカルユーザーと同じように、リモートユーザーが複数のファイルに同時にアクセスしたいアプリケーションは数多くあります。提案されたFAPは、そのような複数ファイルへのアクセスをサポートできません（もちろん、ユーザーはいつでもICPを実行してサーバーとの別の接続を確立できます）。あるFAPコマンドがどのファイルを対象とするかを指定するのに使う「ファイルハンドル」という概念を取り入れることで、FAPを簡単に拡張して複数ファイルへのアクセスをサポートできます。ユーザーが次のコマンドを実行すると、

            OPEN R FOO

    サーバーの応答にはFOOのハンドルが含まれ、ユーザーはその後FOOを参照するときにそのハンドルを使います。返されるハンドルはサーバーが選んだ文字列です。ファイルの名前（FOO）や小さな整数などが考えられます。完全なファイル名の代わりに（サーバーが選んだ）ファイルハンドルを使うことで、サーバーはコマンドごとにファイル名を解析し直すオーバーヘッドを負うことなく、FAPコマンドに応答できます。例として、読み込み用に1つ、書き込み用に1つのファイルを開き、1つ目のファイルからデータとして3バイトを読み込み、そのデータを使って計算し、2バイトの結果を2つ目のファイルに書き込む、次の一連のコマンドを考えてみてください。

            OPEN R FOO   //server returns FH as handle
        OPEN W MOO   //server returns MH as handle
        READ 3 FH    //user reads data
        //User does some computation on the 3 bytes
        WRIT 2  MH   //user writes the result
        CLOS MH
        CLOS FH

    ハンドルには妥当なデフォルトを設けることもできます。たとえば、ハンドルのないFAPコマンドは直前のコマンドと同じファイルを対象とする、などです。（ハンドルとファイルの関連付けは、OPENコマンドの副作用として行うよりも、たとえば次のような別のFAPコマンドで行うほうがおそらく良いでしょう。

            HNDL FOO   )
  6. ローカルな変換を考慮に入れることは重要です（RFC 520の3ページ）。しかし、リモートユーザーが望むなら、ローカルな変換を抑止して、格納されているとおりにファイルにアクセスできるようにすることも同じくらい重要です。これにより、ファイルを操作するプログラムは、ファイルがローカルにある（そしてシステムコールを介して「直接」アクセスされる）場合でも、リモートにある（そして「トラップ」されてFAPコマンドに変換され、リモートサイトに送られるシステムコールを介して「間接的に」アクセスされる）場合でも、同じようにうまく動作できるようになります。
