RFC 410

Removal of the 30-Second Delay When Hosts Come Up

RFC 410

ホストの起動時の30秒の遅延の廃止

Abstract

概要

The IMP currently delays accepting input from a Host for 30 seconds after the Host has come up. This delay serves to allow the fact that the Host is up to propagate through the network. The fundamental problem is that a Host must not be permitted to communicate with a second Host until the second Host (actually its IMP) has been made aware that the first Host is up. Otherwise, one Host may come up and send a "hello" message to another Host, whose reply is discarded by the IMP because it is for a dead destination.

現在、IMPは、ホストが起動してから30秒間、そのホストからの入力の受け付けを遅らせています。この遅延は、ホストが起動したという事実をネットワーク全体に伝播させるためのものです。根本的な問題は、2番目のホスト（実際にはそのIMP）が1番目のホストの起動を知るまでは、1番目のホストに2番目のホストとの通信を許してはならないということです。そうしないと、あるホストが起動して別のホストに「hello」メッセージを送ったときに、その返答が停止中の宛先に向けたものだとしてIMPに破棄されてしまうおそれがあります。

All this reasoning is based on a dead destination detection mechanism at the source IMP. The 30-second delay is based on the worst-case propagation delay for routing information in the network, so that every potential source IMP can update its host up/down table. There are several drawbacks to this scheme:

この理屈はすべて、送信元IMPで宛先の停止を検出するしくみに基づいています。30秒の遅延は、ネットワークにおけるルーティング情報の最悪の場合の伝播遅延に基づいており、送信元になりうるすべてのIMPがホストの稼働/停止の表を更新できるようにしています。この方式にはいくつかの欠点があります。

  1. Hosts should not have to wait the worst-case time of 30 seconds to send to Hosts at their IMP or nearby in the network.
  2. The operation of half-duplex interfaces is made even more complicated because of the startup delay.
  3. The timeout period of 30 seconds is really a function of network topology and we would like to be able to change it when necessary as the network expands.
  1. ホストは、自身のIMPやネットワーク上の近くにあるホストに送信するために、最悪の場合の時間である30秒も待たなくてよいはずです。
  2. 起動時の遅延のせいで、半二重インターフェイスの運用がさらに複雑になります。
  3. 30秒というタイムアウト時間は、実際にはネットワークトポロジーによって決まるものであり、ネットワークの拡大に合わせて必要に応じて変更できるようにしたいと考えています。

We propose to eliminate the 30-second delay altogether. The IMP subnetwork will detect messages for a dead Host at the destination IMP instead of at the source IMP. There is no delay involved for an IMP to sense when its own Hosts come up, so that it can always make the correct decision about whether to give a message to one of its Hosts or to return a destination dead message to the source Host. Under this new scheme, whenever the IMP's ready line is up it is ready to accept input from its Hosts without delay. Several comments on this change should be noted:

私たちは、30秒の遅延を完全になくすことを提案します。IMPサブネットワークは、停止中のホストへのメッセージを、送信元IMPではなく宛先IMPで検出するようにします。IMPが自身のホストの起動を検知するのに遅延はないので、メッセージを自身のホストに渡すか、送信元ホストに宛先停止（destination dead）メッセージを返すかを、常に正しく判断できます。この新しい方式では、IMPのレディー線が上がっていれば、IMPはいつでも遅延なしに自身のホストからの入力を受け付けられます。この変更について、いくつか注意すべき点があります。

  1. No change to Host software should be necessitated by this change. The Host may attempt to send a message to the IMP as soon as it brings its ready line up, or it may delay for a long time. In either case, the IMP will take the message. As before, as soon as the Host has brought up its ready line, it must accept messages from the IMP.
  2. The Hosts may wish to remove any delays _they_ have programmed into their startup routines, since such delays are no longer necessary.
  3. Destination dead messages will be returned as before with two differences. There will be more delay between the receipt of the message at the IMP and the return of the dead destination message because it must travel through the network. For the same reason, if many messages are sent to dead Hosts, the dead destination messages may come back out of order.
  1. この変更によって、ホストのソフトウェアを変更する必要はないはずです。ホストは、レディー線を上げたらすぐにIMPにメッセージを送ろうとしてもかまいませんし、長い時間待ってもかまいません。どちらの場合でも、IMPはメッセージを受け取ります。これまでと同様に、ホストはレディー線を上げたらすぐに、IMPからのメッセージを受け付けなければなりません。
  2. このような遅延はもう必要ないので、ホストは、_自身の_起動ルーチンに組み込んだ遅延を取り除きたいと思うかもしれません。
  3. 宛先停止メッセージはこれまでどおり返されますが、2つの違いがあります。宛先停止メッセージはネットワークを通って戻ってくる必要があるので、IMPがメッセージを受信してから宛先停止メッセージが返されるまでの遅延が大きくなります。同じ理由で、停止中のホストに多数のメッセージを送ると、宛先停止メッセージの戻ってくる順序が入れ替わることがあります。

The Host personnel responsible for the IMP software at each site should check that this proposed change will not adversely affect them. If no adverse comments are received, this change will go into effect on Tuesday morning, December 12 at the regular IMP software release time.

各サイトでIMPのソフトウェアを担当するホスト側の担当者は、この変更案が悪影響を及ぼさないかどうかを確認してください。否定的な意見が寄せられなければ、この変更は12月12日（火）の朝、通常のIMPソフトウェアのリリース時刻に実施します。
