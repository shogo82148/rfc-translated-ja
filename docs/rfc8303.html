RFC 8303

On the Usage of Transport Features Provided by IETF Transport Protocols

RFC 8303

IETFトランスポートプロトコルが提供するトランスポート機能の使用について

Abstract

概要

This document describes how the transport protocols Transmission Control Protocol (TCP), MultiPath TCP (MPTCP), Stream Control Transmission Protocol (SCTP), User Datagram Protocol (UDP), and Lightweight User Datagram Protocol (UDP-Lite) expose services to applications and how an application can configure and use the features that make up these services. It also discusses the service provided by the Low Extra Delay Background Transport (LEDBAT) congestion control mechanism. The description results in a set of transport abstractions that can be exported in a transport services (TAPS) API.

この文書は、トランスポートプロトコルであるトランスミッション制御プロトコル（TCP）、マルチパスTCP（MPTCP）、ストリーム制御伝送プロトコル（SCTP）、ユーザーデータグラムプロトコル（UDP）、軽量ユーザーデータグラムプロトコル（UDP-Lite）が、アプリケーションにどのようにサービスを公開しているか、そしてアプリケーションがそれらのサービスを構成する機能をどのように設定して使用できるかを説明します。 また、低遅延バックグラウンドトランスポート（LEDBAT）輻輳制御メカニズムが提供するサービスについても論じます。 この説明の結果として、トランスポートサービス（TAPS）APIで公開できるトランスポート抽象化のセットが得られます。

1. Introduction

1. はじめに

This specification describes how transport protocols offer transport services, such that applications using them are no longer directly tied to a specific protocol. Breaking this strict connection can reduce the effort for an application programmer, yet attain greater transport flexibility by pushing complexity into an underlying transport services (TAPS) system.

この仕様は、トランスポートプロトコルがどのようにトランスポートサービスを提供するかを説明し、それによって、それらを使用するアプリケーションが特定のプロトコルに直接結び付けられなくなるようにします。 この強い結び付きを断ち切ることで、アプリケーションプログラマーの労力を減らしつつ、複雑さを下位のトランスポートサービス（TAPS）システムに押し込むことで、トランスポートの柔軟性を高めることができます。

This design process has started with a survey of the services provided by IETF transport protocols and congestion control mechanisms [RFC8095]. The present document and [RFC8304] complement this survey with an in-depth look at the defined interactions between applications and the following unicast transport protocols: Transmission Control Protocol (TCP), MultiPath TCP (MPTCP), Stream Control Transmission Protocol (SCTP), User Datagram Protocol (UDP), and Lightweight User Datagram Protocol (UDP-Lite). We also define a primitive to enable/disable and configure the Low Extra Delay Background Transport (LEDBAT) unicast congestion control mechanism. For UDP and UDP-Lite, the first step of the protocol analysis -- a discussion of relevant RFC text -- is documented in [RFC8304].

この設計プロセスは、IETFのトランスポートプロトコルと輻輳制御メカニズムが提供するサービスの調査[RFC8095]から始まりました。 この文書と[RFC8304]は、アプリケーションと次のユニキャストトランスポートプロトコルとの間で定義されているやり取りを詳しく調べることで、この調査を補完します：トランスミッション制御プロトコル（TCP）、マルチパスTCP（MPTCP）、ストリーム制御伝送プロトコル（SCTP）、ユーザーデータグラムプロトコル（UDP）、軽量ユーザーデータグラムプロトコル（UDP-Lite）。 また、低遅延バックグラウンドトランスポート（LEDBAT）ユニキャスト輻輳制御メカニズムを有効化／無効化し、設定するためのプリミティブも定義します。 UDPとUDP-Liteについては、プロトコル分析の最初のステップ、すなわち関連するRFCのテキストの議論は、[RFC8304]に記載されています。

This snapshot in time of the IETF transport protocols is published as an RFC to document the analysis by the authors and the TAPS Working Group; this generates a set of transport abstractions that can be exported in a TAPS API. It provides the basis for the minimal set of transport services that end systems supporting TAPS should implement [TAPS-MINSET].

IETFのトランスポートプロトコルのある時点でのこのスナップショットは、著者らとTAPSワーキンググループによる分析を文書化するためにRFCとして公開されます。 これにより、TAPS APIで公開できるトランスポート抽象化のセットが得られます。 この文書は、TAPSをサポートするエンドシステムが実装すべきトランスポートサービスの最小セット[TAPS-MINSET]の基礎となります。

The list of primitives, events, and transport features in this document is strictly based on the parts of protocol specifications that describe what the protocol provides to an application using it and how the application interacts with it. Transport protocols provide communication between processes that operate on network endpoints, which means that they allow for multiplexing of communication between the same IP addresses, and this multiplexing is achieved using port numbers. Port multiplexing is therefore assumed to be always provided and not discussed in this document.

この文書におけるプリミティブ、イベント、トランスポート機能の一覧は、プロトコル仕様のうち、プロトコルがそれを使用するアプリケーションに何を提供するか、およびアプリケーションがプロトコルとどのようにやり取りするかを説明している部分に厳密に基づいています。 トランスポートプロトコルは、ネットワークのエンドポイント上で動作するプロセス間の通信を提供します。 つまり、同じIPアドレス間の通信の多重化を可能にし、この多重化はポート番号を使って実現されます。 したがって、ポート多重化は常に提供されるものとみなし、この文書では論じません。

Parts of a protocol that are explicitly stated as optional to implement are not covered. Interactions between the application and a transport protocol that are not directly related to the operation of the protocol are also not covered. For example, there are various ways for an application to use socket options to indicate its interest in receiving certain notifications [RFC6458]. However, for the purpose of identifying primitives, events, and transport features, the ability to enable or disable the reception of notifications is irrelevant. Similarly, "one-to-many style sockets" [RFC6458] just affect the application programming style, not how the underlying protocol operates, and they are therefore not discussed here. The same is true for the ability to obtain the unchanged value of a parameter that an application has previously set (e.g., via "get" in get/set operations [RFC6458]).

実装が任意であると明示されているプロトコルの部分は扱いません。 アプリケーションとトランスポートプロトコルとの間のやり取りのうち、プロトコルの動作に直接関係しないものも扱いません。 たとえば、アプリケーションがソケットオプションを使って特定の通知の受信に関心があることを示す方法はさまざまあります[RFC6458]。 しかし、プリミティブ、イベント、トランスポート機能を特定するという目的においては、通知の受信を有効化または無効化する能力は無関係です。 同様に、「1対多スタイルのソケット」[RFC6458]は、アプリケーションのプログラミングスタイルに影響するだけで、下位のプロトコルの動作には影響しないため、ここでは論じません。 アプリケーションが以前に設定したパラメーターの変更されていない値を取得する能力（たとえば、get/set操作[RFC6458]の「get」によるもの）についても同様です。

The document presents a three-pass process to arrive at a list of transport features. In the first pass (pass 1), the relevant RFC text is discussed per protocol. In the second pass (pass 2), this discussion is used to derive a list of primitives and events that are uniformly categorized across protocols. Here, an attempt is made to present or -- where text describing primitives or events does not yet exist -- construct primitives or events in a slightly generalized form to highlight similarities. This is, for example, achieved by renaming primitives or events of protocols or by avoiding a strict 1:1 mapping between the primitives or events in the protocol specification and primitives or events in the list. Finally, the third pass (pass 3) presents transport features based on pass 2, identifying which protocols implement them.

この文書では、トランスポート機能の一覧に到達するための3パスのプロセスを示します。 最初のパス（パス1）では、関連するRFCのテキストをプロトコルごとに論じます。 2番目のパス（パス2）では、この議論を使用して、プロトコル間で統一的に分類されたプリミティブとイベントの一覧を導き出します。 ここでは、類似点を強調するために、プリミティブやイベントを少し一般化した形で提示する、あるいは（プリミティブやイベントを説明するテキストがまだ存在しない場合には）構築することを試みます。 これは、たとえば、プロトコルのプリミティブやイベントの名前を変更したり、プロトコル仕様のプリミティブやイベントと一覧のプリミティブやイベントとの厳密な1対1の対応付けを避けたりすることで実現しています。 最後に、3番目のパス（パス3）では、パス2に基づいてトランスポート機能を提示し、どのプロトコルがそれらを実装しているかを特定します。

In the list resulting from the second pass, some transport features are missing because they are implicit in some protocols, and they only become explicit when we consider the superset of all transport features offered by all protocols. For example, TCP always carries out congestion control; we have to consider it together with a protocol like UDP (which does not have congestion control) before we can consider congestion control as a transport feature. The complete list of transport features across all protocols is therefore only available after pass 3.

2番目のパスの結果として得られる一覧では、一部のトランスポート機能が欠けています。 それらは一部のプロトコルでは暗黙的なものであり、すべてのプロトコルが提供するすべてのトランスポート機能の上位集合を考えたときに初めて明示的になるからです。 たとえば、TCPは常に輻輳制御を行います。 輻輳制御をトランスポート機能として考えることができるのは、TCPをUDPのような（輻輳制御を持たない）プロトコルと一緒に考えたときです。 したがって、すべてのプロトコルにわたるトランスポート機能の完全な一覧は、パス3の後で初めて得られます。

Some protocols are connection oriented. Connection-oriented protocols often use an initial call to a specific primitive to open a connection before communication can progress and require communication to be explicitly terminated by issuing another call to a primitive (usually called 'Close'). A "connection" is the common state that some transport primitives refer to, e.g., to adjust general configuration settings. Connection establishment, maintenance, and termination are therefore used to categorize transport primitives of connection-oriented transport protocols in pass 2 and pass 3. For this purpose, UDP is assumed to be used with "connected" sockets, i.e., sockets that are bound to a specific pair of addresses and ports [RFC8304].

一部のプロトコルはコネクション指向です。 コネクション指向プロトコルは、多くの場合、通信を進める前に特定のプリミティブを最初に呼び出してコネクションをオープンし、別のプリミティブ（通常は「Close」と呼ばれます）を呼び出して通信を明示的に終了することを必要とします。 「コネクション」とは、一部のトランスポートプリミティブが、たとえば全般的な設定を調整するために参照する共通の状態です。 したがって、パス2とパス3では、コネクションの確立、維持、終了を使用して、コネクション指向トランスポートプロトコルのトランスポートプリミティブを分類します。 この目的のために、UDPは「接続済み（connected）」ソケット、すなわちアドレスとポートの特定のペアにバインドされたソケットとともに使用されるものと想定します[RFC8304]。

2. Terminology

2. 用語

Transport Feature:
a specific end-to-end feature that the transport layer provides to an application. Examples include confidentiality, reliable delivery, ordered delivery, message-versus-stream orientation, etc.
Transport Service:
a set of transport features, without an association to any given framing protocol, which provides a complete service to an application.
Transport Protocol:
an implementation that provides one or more transport services using a specific framing and header format on the wire.
Transport Protocol Component:
an implementation of a transport feature within a protocol.
Transport Service Instance:
an arrangement of transport protocols with a selected set of features and configuration parameters that implement a single transport service, e.g., a protocol stack (RTP over UDP).
Application:
an entity that uses the transport layer for end-to-end delivery of data across the network (this may also be an upper-layer protocol or tunnel encapsulation).
Endpoint:
an entity that communicates with one or more other endpoints using a transport protocol.
Connection:
shared state of two or more endpoints that persists across messages that are transmitted between these endpoints.
Primitive:
a function call that is used to locally communicate between an application and a transport endpoint. A primitive is related to one or more transport features.
Event:
a primitive that is invoked by a transport endpoint.
Parameter:
a value passed between an application and a transport protocol by a primitive.
Socket:
the combination of a destination IP address and a destination port number.
Transport Address:
the combination of an IP address, transport protocol, and the port number used by the transport protocol.
トランスポート機能（Transport Feature）：
トランスポート層がアプリケーションに提供する、特定のエンドツーエンドの機能。 例としては、機密性、信頼性のある配送、順序どおりの配送、メッセージ指向かストリーム指向か、などがあります。
トランスポートサービス（Transport Service）：
特定のフレーミングプロトコルとの関連付けを持たない、アプリケーションに完全なサービスを提供するトランスポート機能のセット。
トランスポートプロトコル（Transport Protocol）：
回線上で特定のフレーミングとヘッダー形式を使用して、1つ以上のトランスポートサービスを提供する実装。
トランスポートプロトコルコンポーネント（Transport Protocol Component）：
プロトコル内でのトランスポート機能の実装。
トランスポートサービスインスタンス（Transport Service Instance）：
単一のトランスポートサービスを実装する、選択された機能と設定パラメーターのセットを伴うトランスポートプロトコルの配置。 たとえば、プロトコルスタック（UDP上のRTP）。
アプリケーション（Application）：
ネットワークを介したデータのエンドツーエンドの配送のためにトランスポート層を使用するエンティティー（これは上位層プロトコルやトンネルのカプセル化である場合もあります）。
エンドポイント（Endpoint）：
トランスポートプロトコルを使用して1つ以上の他のエンドポイントと通信するエンティティー。
コネクション（Connection）：
2つ以上のエンドポイント間で送信されるメッセージをまたいで持続する、それらのエンドポイントの共有状態。
プリミティブ（Primitive）：
アプリケーションとトランスポートエンドポイントとの間でローカルに通信するために使用される関数呼び出し。 プリミティブは1つ以上のトランスポート機能に関連します。
イベント（Event）：
トランスポートエンドポイントによって呼び出されるプリミティブ。
パラメーター（Parameter）：
プリミティブによってアプリケーションとトランスポートプロトコルとの間で受け渡される値。
ソケット（Socket）：
宛先IPアドレスと宛先ポート番号の組み合わせ。
トランスポートアドレス（Transport Address）：
IPアドレス、トランスポートプロトコル、およびトランスポートプロトコルが使用するポート番号の組み合わせ。

3. Pass 1

3. パス1

This first iteration summarizes the relevant text parts of the RFCs describing the protocols, focusing on what each transport protocol provides to the application and how it is used (abstract API descriptions, where they are available). When presenting primitives, events, and parameters, the use of lower- and upper-case characters is made uniform for the sake of readability.

この最初の反復では、プロトコルを説明しているRFCの関連するテキスト部分を要約します。 その際、各トランスポートプロトコルがアプリケーションに何を提供し、それがどのように使用されるか（抽象APIの説明がある場合はその説明）に焦点を当てます。 プリミティブ、イベント、パラメーターを提示する際には、読みやすさのために小文字と大文字の使い方を統一しています。

3.1. Primitives Provided by TCP

3.1. TCPが提供するプリミティブ

The initial TCP specification [RFC0793] states:

最初のTCP仕様[RFC0793]は次のように述べています：

The Transmission Control Protocol (TCP) is intended for use as a highly reliable host-to-host protocol between hosts in packet-switched computer communication networks, and in interconnected systems of such networks.

トランスミッション制御プロトコル（TCP）は、パケット交換型のコンピューター通信ネットワーク、およびそのようなネットワークを相互接続したシステムにおいて、ホスト間で使用する信頼性の高いホスト間プロトコルとして意図されています。

Section 3.8 of [RFC0793] further specifies the interaction with the application by listing several transport primitives. It is also assumed that an Operating System provides a means for TCP to asynchronously signal the application; the primitives representing such signals are called 'events' in this section. This section describes the relevant primitives.

[RFC0793]のセクション3.8は、いくつかのトランスポートプリミティブを列挙することで、アプリケーションとのやり取りをさらに規定しています。 また、オペレーティングシステムが、TCPがアプリケーションに非同期にシグナルを送る手段を提供することも想定しています。 このセクションでは、そのようなシグナルを表すプリミティブを「イベント」と呼びます。 このセクションでは、関連するプリミティブを説明します。

Open:

This is either active or passive, to initiate a connection or listen for incoming connections. All other primitives are associated with a specific connection, which is assumed to first have been opened. An active open call contains a socket. A passive open call with a socket waits for a particular connection; alternatively, a passive open call can leave the socket unspecified to accept any incoming connection. A fully specified passive call can later be made active by calling 'Send'. Optionally, a timeout can be specified, after which TCP will abort the connection if data has not been successfully delivered to the destination (else a default timeout value is used). A procedure for aborting the connection is used to avoid excessive retransmissions, and an application is able to control the threshold used to determine the condition for aborting; this threshold may be measured in time units or as a count of retransmission [RFC1122]. This indicates that the timeout could also be specified as a count of retransmission.

Also optional, for multihomed hosts, the local IP address can be provided [RFC1122]. If it is not provided, a default choice will be made in case of active open calls. A passive open call will await incoming connection requests to all local addresses and then maintain usage of the local IP address where the incoming connection request has arrived. Finally, the 'options' parameter allows the application to specify IP options such as Source Route, Record Route, or Timestamp [RFC1122]. It is not stated on which segments of a connection these options should be applied, but probably on all segments, as this is also stated in a specification given for the usage of the Source Route IP option (Section 4.2.3.8 of [RFC1122]). Source Route is the only non-optional IP option in this parameter, allowing an application to specify a source route when it actively opens a TCP connection.

Master Key Tuples (MKTs) for authentication can optionally be configured when calling 'Open' (Section 7.1 of [RFC5925]). When authentication is in use, complete TCP segments are authenticated, including the TCP IPv4 pseudoheader, TCP header, and TCP data.

TCP Fast Open (TFO) [RFC7413] allows applications to immediately hand over a message from the active open to the passive open side of a TCP connection together with the first message establishment packet (the SYN). This can be useful for applications that are sensitive to TCP's connection setup delay. [RFC7413] states that "TCP implementations MUST NOT use TFO by default, but only use TFO if requested explicitly by the application on a per-service-port basis." The size of the message sent with TFO cannot be more than TCP's maximum segment size (minus options used in the SYN). For the active open side, it is recommended to change or replace the connect() call in order to support a user data buffer argument [RFC7413]. For the passive open side, the application needs to enable the reception of Fast Open requests, e.g., via a new TCP_FASTOPEN setsockopt() socket option before listen(). The receiving application must be prepared to accept duplicates of the TFO message, as the first data written to a socket can be delivered more than once to the application on the remote host.

Send:
This is the primitive that an application uses to give the local TCP transport endpoint a number of bytes that TCP should reliably send to the other side of the connection. The 'urgent' flag, if set, states that the data handed over by this send call is urgent and this urgency should be indicated to the receiving process in case the receiving application has not yet consumed all non-urgent data preceding it. An optional timeout parameter can be provided that updates the connection's timeout (see 'Open'). Additionally, optional parameters allow the ability to indicate the preferred outgoing MKT (current_key) and/or the preferred incoming MKT (rnext_key) of a connection (Section 7.1 of [RFC5925]).
Receive:
This primitive allocates a receiving buffer for a provided number of bytes. It returns the number of received bytes provided in the buffer when these bytes have been received and written into the buffer by TCP. The application is informed of urgent data via an 'urgent' flag: if it is on, there is urgent data; if it is off, there is no urgent data or this call to 'Receive' has returned all the urgent data. The application is also informed about the current_key and rnext_key information carried in a recently received segment via an optional parameter (Section 7.1 of [RFC5925]).
Close:
This primitive closes one side of a connection. It is semantically equivalent to "I have no more data to send" but does not mean "I will not receive any more", as the other side may still have data to send. This call reliably delivers any data that has already been given to TCP (and if that fails, 'Close' becomes 'abort').
Abort:
This primitive causes all pending 'Send' and 'Receive' calls to be aborted. A TCP "RESET" message is sent to the TCP endpoint on the other side of the connection [RFC0793].
Close Event:
TCP uses this primitive to inform an application that the application on the other side has called the 'Close' primitive, so the local application can also issue a 'Close' and terminate the connection gracefully. See [RFC0793], Section 3.5.
Abort Event:
When TCP aborts a connection upon receiving a "RESET" from the peer, it "advises the user and goes to the CLOSED state." See [RFC0793], Section 3.4.
User Timeout Event:
This event is executed when the user timeout (Section 3.9 of [RFC0793]) expires (see the definition of 'Open' in this section). All queues are flushed, and the application is informed that the connection had to be aborted due to user timeout.
Error_Report event:
This event informs the application of "soft errors" that can be safely ignored [RFC5461], including the arrival of an ICMP error message or excessive retransmissions (reaching a threshold below the threshold where the connection is aborted). See Section 4.2.4.1 of [RFC1122].
Type-of-Service:
Section 4.2.4.2 of the requirements for Internet hosts [RFC1122] states that "The application layer MUST be able to specify the Type-of-Service (TOS) for segments that are sent on a connection." The application should be able to change the TOS during the connection lifetime, and the TOS value should be passed to the IP layer unchanged. Since then, the TOS field has been redefined. The Differentiated Services (Diffserv) model [RFC2475] [RFC3260] replaces this field in the IP header, assigning the six most significant bits to carry the Differentiated Services Code Point (DSCP) field [RFC2474].
Nagle:
The Nagle algorithm delays sending data for some time to increase the likelihood of sending a full-sized segment (Section 4.2.3.4 of [RFC1122]). An application can disable the Nagle algorithm for an individual connection.
User Timeout Option:
The User Timeout Option (UTO) [RFC5482] allows one end of a TCP connection to advertise its current user timeout value so that the other end of the TCP connection can adapt its own user timeout accordingly. In addition to the configurable value of the user timeout (see 'Send'), there are three per-connection state variables that an application can adjust to control the operation of the UTO: 'adv_uto' is the value of the UTO advertised to the remote TCP peer (default: system-wide default user timeout); 'enabled' (default false) is a boolean-type flag that controls whether the UTO option is enabled for a connection. This applies to both sending and receiving. 'changeable' is a boolean-type flag (default true) that controls whether the user timeout may be changed based on a UTO option received from the other end of the connection. 'changeable' becomes false when an application explicitly sets the user timeout (see 'Send').
Set/Get Authentication Parameters:
The preferred outgoing MKT (current_key) and/or the preferred incoming MKT (rnext_key) of a connection can be configured. Information about current_key and rnext_key carried in a recently received segment can be retrieved (Section 7.1 of [RFC5925]).
Open:

これは、コネクションを開始するか、着信コネクションをリッスンするための、アクティブまたはパッシブのいずれかです。 他のすべてのプリミティブは特定のコネクションに関連付けられており、そのコネクションは最初にオープンされているものと想定しています。 アクティブオープンの呼び出しにはソケットが含まれます。 ソケットを伴うパッシブオープンの呼び出しは、特定のコネクションを待ちます。 あるいは、パッシブオープンの呼び出しはソケットを指定しないままにして、任意の着信コネクションを受け入れることもできます。 完全に指定されたパッシブ呼び出しは、後で「Send」を呼び出すことでアクティブにすることができます。 任意で、タイムアウトを指定できます。 データが宛先に正常に配送されなかった場合、TCPはこのタイムアウトの後にコネクションを中断します（指定しない場合はデフォルトのタイムアウト値が使われます）。 コネクションを中断する手続きは過剰な再送を避けるために使用され、アプリケーションは中断の条件を判定するためのしきい値を制御できます。 このしきい値は、時間の単位で、または再送の回数として測定される場合があります[RFC1122]。 これは、タイムアウトを再送の回数として指定することもできることを示しています。

同じく任意で、マルチホームのホストでは、ローカルIPアドレスを提供できます[RFC1122]。 提供されない場合、アクティブオープンの呼び出しではデフォルトの選択が行われます。 パッシブオープンの呼び出しは、すべてのローカルアドレスへの着信コネクション要求を待ち、その後、着信コネクション要求が到着したローカルIPアドレスを使い続けます。 最後に、「options」パラメーターによって、アプリケーションはSource Route、Record Route、TimestampなどのIPオプションを指定できます[RFC1122]。 これらのオプションをコネクションのどのセグメントに適用すべきかは述べられていませんが、おそらくすべてのセグメントです。 Source Route IPオプションの使用に関する仕様（[RFC1122]のセクション4.2.3.8）でもそのように述べられているからです。 Source Routeは、このパラメーターで任意ではない唯一のIPオプションであり、アプリケーションがTCPコネクションをアクティブにオープンする際に送信元経路を指定できるようにします。

認証のためのマスター鍵タプル（MKT）は、「Open」を呼び出す際に任意で設定できます（[RFC5925]のセクション7.1）。 認証を使用している場合、TCP IPv4疑似ヘッダー、TCPヘッダー、TCPデータを含むTCPセグメント全体が認証されます。

TCP Fast Open（TFO）[RFC7413]により、アプリケーションは、最初のメッセージ確立パケット（SYN）とともに、TCPコネクションのアクティブオープン側からパッシブオープン側へメッセージを即座に引き渡すことができます。 これは、TCPのコネクション確立の遅延の影響を受けやすいアプリケーションに役立ちます。 [RFC7413]は、「TCP実装はデフォルトでTFOを使用してはなりません（MUST NOT）。サービスポートごとにアプリケーションによって明示的に要求された場合にのみTFOを使用します。」と述べています。 TFOで送信されるメッセージのサイズは、TCPの最大セグメントサイズ（からSYNで使用されるオプションを引いたもの）を超えることはできません。 アクティブオープン側では、ユーザーデータバッファー引数をサポートするために、connect()呼び出しを変更または置き換えることが推奨されています[RFC7413]。 パッシブオープン側では、アプリケーションは、たとえばlisten()の前に新しいTCP_FASTOPEN setsockopt()ソケットオプションを使って、Fast Openリクエストの受信を有効にする必要があります。 ソケットに書き込まれた最初のデータはリモートホスト上のアプリケーションに複数回配送される可能性があるため、受信側のアプリケーションはTFOメッセージの重複を受け入れる準備ができていなければなりません。

Send:
これは、TCPがコネクションの相手側に信頼性をもって送信すべきバイト列をローカルのTCPトランスポートエンドポイントに渡すために、アプリケーションが使用するプリミティブです。 「urgent」フラグが設定されている場合、この送信呼び出しで引き渡されたデータが緊急であることを示します。 受信側のアプリケーションがその前にある緊急でないデータをまだすべて消費していない場合には、この緊急性を受信側のプロセスに示すべきです。 コネクションのタイムアウトを更新する任意のタイムアウトパラメーターを提供できます（「Open」を参照）。 さらに、任意のパラメーターにより、コネクションの優先する送信用MKT（current_key）と優先する受信用MKT（rnext_key）の一方または両方を示すことができます（[RFC5925]のセクション7.1）。
Receive:
このプリミティブは、指定されたバイト数の受信バッファーを割り当てます。 TCPによってバイトが受信されバッファーに書き込まれると、バッファーに提供された受信バイト数を返します。 アプリケーションには「urgent」フラグによって緊急データが通知されます。 フラグがオンの場合は緊急データがあり、オフの場合は緊急データがないか、この「Receive」の呼び出しがすべての緊急データを返したことを意味します。 アプリケーションには、最近受信したセグメントで運ばれたcurrent_keyとrnext_keyの情報も、任意のパラメーターを介して通知されます（[RFC5925]のセクション7.1）。
Close:
このプリミティブは、コネクションの片側をクローズします。 これは意味的には「これ以上送信するデータはない」と同等ですが、「これ以上受信しない」という意味ではありません。 相手側にはまだ送信するデータがある可能性があるからです。 この呼び出しは、すでにTCPに渡されたデータを信頼性をもって配送します（それが失敗した場合、「Close」は「abort」になります）。
Abort:
このプリミティブは、保留中のすべての「Send」と「Receive」の呼び出しを中断させます。 コネクションの相手側のTCPエンドポイントにTCPの「RESET」メッセージが送信されます[RFC0793]。
Close Event:
TCPはこのプリミティブを使用して、相手側のアプリケーションが「Close」プリミティブを呼び出したことをアプリケーションに通知します。 これにより、ローカルのアプリケーションも「Close」を発行して、コネクションを正常に終了することができます。 [RFC0793], セクション3.5を参照してください。
Abort Event:
ピアから「RESET」を受信してTCPがコネクションを中断する場合、TCPは「ユーザーに通知してCLOSED状態に移行します」。 [RFC0793], セクション3.4を参照してください。
User Timeout Event:
このイベントは、ユーザータイムアウト（[RFC0793]のセクション3.9）が期限切れになったときに実行されます（このセクションの「Open」の定義を参照してください）。 すべてのキューがフラッシュされ、ユーザータイムアウトのためにコネクションを中断しなければならなかったことがアプリケーションに通知されます。
Error_Report event:
このイベントは、安全に無視できる「ソフトエラー」[RFC5461]をアプリケーションに通知します。 これには、ICMPエラーメッセージの到着や、（コネクションが中断されるしきい値よりも低いしきい値に達する）過剰な再送が含まれます。 [RFC1122]のセクション4.2.4.1を参照してください。
Type-of-Service:
インターネットホストの要件[RFC1122]のセクション4.2.4.2は、「アプリケーション層は、コネクション上で送信されるセグメントのサービスタイプ（TOS）を指定できなければなりません（MUST）。」と述べています。 アプリケーションはコネクションの有効期間中にTOSを変更できるべきであり、TOS値は変更されずにIP層に渡されるべきです。 その後、TOSフィールドは再定義されました。 差別化サービス（Diffserv）モデル[RFC2475] [RFC3260]は、IPヘッダーのこのフィールドを置き換え、最上位の6ビットを差別化サービスコードポイント（DSCP）フィールド[RFC2474]を運ぶために割り当てています。
Nagle:
Nagleアルゴリズムは、フルサイズのセグメントを送信する可能性を高めるために、データの送信をしばらく遅らせます（[RFC1122]のセクション4.2.3.4）。 アプリケーションは、個々のコネクションに対してNagleアルゴリズムを無効にできます。
User Timeout Option:
ユーザータイムアウトオプション（UTO）[RFC5482]により、TCPコネクションの一方の端は現在のユーザータイムアウト値を広告でき、TCPコネクションのもう一方の端はそれに応じて自身のユーザータイムアウトを調整できます。 設定可能なユーザータイムアウトの値（「Send」を参照）に加えて、アプリケーションがUTOの動作を制御するために調整できる、コネクションごとの状態変数が3つあります。 「adv_uto」は、リモートのTCPピアに広告されるUTOの値です（デフォルト：システム全体のデフォルトのユーザータイムアウト）。 「enabled」（デフォルトはfalse）は、コネクションに対してUTOオプションを有効にするかどうかを制御する真偽値型のフラグです。 これは送信と受信の両方に適用されます。 「changeable」は、コネクションのもう一方の端から受信したUTOオプションに基づいてユーザータイムアウトを変更してよいかどうかを制御する真偽値型のフラグ（デフォルトはtrue）です。 アプリケーションがユーザータイムアウトを明示的に設定すると（「Send」を参照）、「changeable」はfalseになります。
Set/Get Authentication Parameters:
コネクションの優先する送信用MKT（current_key）と優先する受信用MKT（rnext_key）の一方または両方を設定できます。 最近受信したセグメントで運ばれたcurrent_keyとrnext_keyに関する情報を取得できます（[RFC5925]のセクション7.1）。

3.1.1. Excluded Primitives or Parameters

3.1.1. 除外したプリミティブやパラメーター

The 'Open' primitive can be handed optional precedence or security/compartment information [RFC0793], but this was not included here because it is mostly irrelevant today [RFC7414].

「Open」プリミティブには、任意の優先順位（precedence）やセキュリティー／コンパートメントの情報を渡すことができます[RFC0793]。 しかし、今日ではほとんど意味がないため[RFC7414]、ここには含めていません。

The 'Status' primitive was not included because the initial TCP specification describes this primitive as "implementation dependent" and states that it "could be excluded without adverse effect" [RFC0793]. Moreover, while a data block containing specific information is described, it is also stated that not all of this information may always be available. While [RFC5925] states that 'Status' "SHOULD be augmented to allow the MKTs of a current or pending connection to be read (for confirmation)", the same information is also available via 'Receive', which, following [RFC5925], "MUST be augmented" with that functionality. The 'Send' primitive includes an optional 'push' flag which, if set, requires data to be promptly transmitted to the receiver without delay [RFC0793]; the 'Receive' primitive described in can (under some conditions) yield the status of the 'push' flag. Because "push" functionality is optional to implement for both the 'Send' and 'Receive' primitives [RFC1122], this functionality is not included here. The requirements for Internet hosts [RFC1122] also introduce keep-alives to TCP, but these are optional to implement and hence not considered here. The same document also describes that "some TCP implementations have included a FLUSH call", indicating that this call is also optional to implement; therefore, it is not considered here.

「Status」プリミティブは含めていません。 最初のTCP仕様がこのプリミティブを「実装依存」と説明し、「悪影響なく除外できる」と述べているからです[RFC0793]。 さらに、特定の情報を含むデータブロックが説明されているものの、この情報のすべてが常に利用できるとは限らないとも述べられています。 [RFC5925]は、「Status」は「現在または保留中のコネクションのMKTを（確認のために）読み取れるように拡張されるべきです（SHOULD）」と述べていますが、同じ情報は「Receive」を介しても利用できます。 [RFC5925]によれば、「Receive」はその機能で「拡張されなければなりません（MUST）」。 「Send」プリミティブには任意の「push」フラグが含まれており、これが設定されている場合、データを遅延なく速やかに受信者に送信することが要求されます[RFC0793]。 説明されている「Receive」プリミティブは、（ある条件の下で）「push」フラグの状態を返すことができます。 「push」機能は「Send」と「Receive」の両方のプリミティブで実装が任意であるため[RFC1122]、この機能はここには含めていません。 インターネットホストの要件[RFC1122]はTCPにキープアライブも導入していますが、これは実装が任意であるため、ここでは考慮しません。 同じ文書には、「一部のTCP実装にはFLUSH呼び出しが含まれている」とも記述されており、この呼び出しも実装が任意であることを示しているため、ここでは考慮しません。

3.2. Primitives Provided by MPTCP

3.2. MPTCPが提供するプリミティブ

MPTCP is an extension to TCP that allows the use of multiple paths for a single data stream. It achieves this by creating different so-called TCP subflows for each of the interfaces and scheduling the traffic across these TCP subflows. The service provided by MPTCP is described as follows in [RFC6182]:

MPTCPは、単一のデータストリームに対して複数のパスを使用できるようにするTCPの拡張です。 これは、インターフェイスごとにいわゆるTCPサブフローを別々に作成し、これらのTCPサブフローにトラフィックをスケジューリングすることで実現されます。 MPTCPが提供するサービスは、[RFC6182]で次のように説明されています：

Multipath TCP MUST follow the same service model as TCP [RFC0793]: in-order, reliable, and byte-oriented delivery. Furthermore, a Multipath TCP connection SHOULD provide the application with no worse throughput or resilience than it would expect from running a single TCP connection over any one of its available paths.

マルチパスTCPは、TCP[RFC0793]と同じサービスモデル、すなわち順序どおりで信頼性のあるバイト指向の配送に従わなければなりません（MUST）。 さらに、マルチパスTCPコネクションは、利用可能なパスのいずれか1つで単一のTCPコネクションを実行した場合に期待されるよりも悪くないスループットや回復力をアプリケーションに提供すべきです（SHOULD）。

Further, there are some constraints on the API exposed by MPTCP, as stated in [RFC6182]:

さらに、[RFC6182]で述べられているように、MPTCPが公開するAPIにはいくつかの制約があります：

A multipath-capable equivalent of TCP MUST retain some level of backward compatibility with existing TCP APIs, so that existing applications can use the newer transport merely by upgrading the operating systems of the end hosts.

マルチパスに対応したTCPの同等物は、既存のアプリケーションがエンドホストのオペレーティングシステムをアップグレードするだけで新しいトランスポートを使用できるように、既存のTCP APIとのある程度の後方互換性を維持しなければなりません（MUST）。

As such, the primitives provided by MPTCP are equivalent to the ones provided by TCP. Nevertheless, the MPTCP RFCs [RFC6824] and [RFC6897] clarify some parts of TCP's primitives with respect to MPTCP and add some extensions for better control on MPTCP's subflows. Hereafter is a list of the clarifications and extensions the above-cited RFCs provide to TCP's primitives.

そのため、MPTCPが提供するプリミティブはTCPが提供するものと同等です。 とはいえ、MPTCPのRFC[RFC6824] [RFC6897]は、MPTCPに関するTCPのプリミティブのいくつかの部分を明確にし、MPTCPのサブフローをよりよく制御するためのいくつかの拡張を追加しています。 以下は、上で引用したRFCがTCPのプリミティブに対して提供する明確化と拡張の一覧です。

Open:
"An application should be able to request to turn on or turn off the usage of MPTCP" [RFC6897]. This functionality can be provided through a socket option called 'tcp_multipath_enable'. Further, MPTCP must be disabled in case the application is binding to a specific address [RFC6897].
Send/Receive:

The sending and receiving of data does not require any changes to the application when MPTCP is being used [RFC6824]. The MPTCP-layer will take one input data stream from an application, and split it into one or more subflows, with sufficient control information to allow it to be reassembled and delivered reliably and in order to the recipient application.

The use of the Urgent Pointer is special in MPTCP [RFC6824], which states: "a TCP subflow MUST NOT use the Urgent Pointer to interrupt an existing mapping."

Address and Subflow Management:
MPTCP uses different addresses and allows a host to announce these addresses as part of the protocol. The MPTCP API Considerations RFC [RFC6897] says "An application should be able to restrict MPTCP to binding to a given set of addresses" and thus allows applications to limit the set of addresses that are being used by MPTCP. Further, "An application should be able to obtain information on the pairs of addresses used by the MPTCP subflows."
Open:
「アプリケーションは、MPTCPの使用をオンまたはオフにするよう要求できるべきです」[RFC6897]。 この機能は、「tcp_multipath_enable」というソケットオプションを通じて提供できます。 さらに、アプリケーションが特定のアドレスにバインドしている場合、MPTCPは無効にしなければなりません[RFC6897]。
Send/Receive:

MPTCPを使用している場合でも、データの送信と受信にアプリケーションの変更は必要ありません[RFC6824]。 MPTCP層は、アプリケーションから1つの入力データストリームを受け取り、それを1つ以上のサブフローに分割します。 その際、データを再組み立てして受信側のアプリケーションに信頼性をもって順序どおりに配送できるようにするための十分な制御情報を付加します。

MPTCPでは、緊急ポインター（Urgent Pointer）の使用は特殊です[RFC6824]。 RFC 6824は、「TCPサブフローは、既存のマッピングを中断するために緊急ポインターを使用してはなりません（MUST NOT）。」と述べています。

Address and Subflow Management:
MPTCPは異なるアドレスを使用し、ホストがプロトコルの一部としてこれらのアドレスを通知できるようにします。 MPTCPのAPIに関する考慮事項のRFC[RFC6897]は、「アプリケーションは、MPTCPが特定のアドレスのセットにバインドするように制限できるべきです」と述べており、これによりアプリケーションはMPTCPが使用するアドレスのセットを制限できます。 さらに、「アプリケーションは、MPTCPサブフローが使用するアドレスのペアに関する情報を取得できるべきです。」とも述べています。

3.3. Primitives Provided by SCTP

3.3. SCTPが提供するプリミティブ

TCP has a number of limitations that SCTP removes (Section 1.1 of [RFC4960]). The following three removed limitations directly translate into transport features that are visible to an application using SCTP: 1) it allows for preservation of message delimiters; 2) it does not provide in-order or reliable delivery unless the application wants that; 3) multihoming is supported. In SCTP, connections are called "associations" and they can be between not only two (as in TCP) but multiple addresses at each endpoint.

TCPにはSCTPが取り除いたいくつかの制限があります（[RFC4960]のセクション1.1）。 取り除かれた制限のうち次の3つは、SCTPを使用するアプリケーションから見えるトランスポート機能に直接つながります：1）メッセージの区切りを保持できる、2）アプリケーションが望まない限り順序どおりの配送や信頼性のある配送を提供しない、3）マルチホーミングがサポートされている。 SCTPでは、コネクションは「アソシエーション」と呼ばれ、（TCPのように）2つのアドレス間だけでなく、各エンドポイントの複数のアドレス間で構成できます。

Section 10 of the SCTP base protocol specification [RFC4960] specifies the interaction with the application (which SCTP calls the "Upper-Layer Protocol (ULP)"). It is assumed that the Operating System provides a means for SCTP to asynchronously signal the application; the primitives representing such signals are called 'events' in this section. Here, we describe the relevant primitives. In addition to the abstract API described in Section 10 of [RFC4960], an extension to the sockets API is described in [RFC6458]. This covers the functionality of the base protocol [RFC4960] and some of its extensions [RFC3758] [RFC4895] [RFC5061]. For other protocol extensions [RFC6525] [RFC6951] [RFC7053] [RFC7496] [RFC7829] [RFC8260], the corresponding extensions of the sockets API are specified in these protocol specifications. The functionality exposed to the ULP through all these APIs is considered here.

SCTPの基本プロトコル仕様[RFC4960]のセクション10は、アプリケーション（SCTPはこれを「上位層プロトコル（ULP）」と呼びます）とのやり取りを規定しています。 オペレーティングシステムが、SCTPがアプリケーションに非同期にシグナルを送る手段を提供することを想定しています。 このセクションでは、そのようなシグナルを表すプリミティブを「イベント」と呼びます。 ここでは、関連するプリミティブを説明します。 [RFC4960]のセクション10で説明されている抽象APIに加えて、ソケットAPIの拡張が[RFC6458]で説明されています。 これは、基本プロトコル[RFC4960]とその拡張のいくつか[RFC3758] [RFC4895] [RFC5061]の機能を扱っています。 その他のプロトコル拡張[RFC6525] [RFC6951] [RFC7053] [RFC7496] [RFC7829] [RFC8260]については、対応するソケットAPIの拡張がそれぞれのプロトコル仕様で規定されています。 ここでは、これらすべてのAPIを通じてULPに公開される機能を考慮します。

The abstract API contains a 'SetProtocolParameters' primitive that allows elements of a parameter list [RFC4960] to be adjusted; it is stated that SCTP implementations "may allow ULP to customize some of these protocol parameters", indicating that none of the elements of this parameter list are mandatory to make ULP configurable. Thus, we only consider the parameters in the abstract API that are also covered in one of the other RFCs listed above, which leads us to exclude the parameters 'RTO.Alpha', 'RTO.Beta', and 'HB.Max.Burst'. For clarity, we also replace 'SetProtocolParameters' itself with primitives that adjust parameters or groups of parameters that fit together.

抽象APIには、パラメーターリスト[RFC4960]の要素を調整できるようにする「SetProtocolParameters」プリミティブが含まれています。 SCTP実装は「ULPがこれらのプロトコルパラメーターの一部をカスタマイズできるようにしてもよい」と述べられており、このパラメーターリストのどの要素もULPが設定可能にすることが必須ではないことを示しています。 したがって、抽象APIのパラメーターのうち、上に挙げた他のRFCのいずれかでも扱われているものだけを考慮します。 その結果、パラメーター「RTO.Alpha」「RTO.Beta」「HB.Max.Burst」は除外します。 わかりやすくするために、「SetProtocolParameters」自体も、パラメーターまたはまとまりのあるパラメーターのグループを調整するプリミティブに置き換えます。

Initialize:
Initialize creates a local SCTP instance that it binds to a set of local addresses (and, if provided, a local port number) [RFC4960]. Initialize needs to be called only once per set of local addresses. A number of per-association initialization parameters can be used when an association is created, but before it is connected (via the primitive 'Associate' below): the maximum number of inbound streams the application is prepared to support, the maximum number of attempts to be made when sending the INIT (the first message of association establishment), and the maximum retransmission timeout (RTO) value to use when attempting an INIT [RFC6458]. At this point, before connecting, an application can also enable UDP encapsulation by configuring the remote UDP encapsulation port number [RFC6951].
Associate:
This creates an association (the SCTP equivalent of a connection) that connects the local SCTP instance and a remote SCTP instance. To identify the remote endpoint, it can be given one or multiple (using "connectx") sockets (Section 9.9 of [RFC6458]). Most primitives are associated with a specific association, which is assumed to first have been created. Associate can return a list of destination transport addresses so that multiple paths can later be used. One of the returned sockets will be selected by the local endpoint as the default primary path for sending SCTP packets to this peer, but this choice can be changed by the application using the list of destination addresses. Associate is also given the number of outgoing streams to request and optionally returns the number of negotiated outgoing streams. An optional parameter of 32 bits, the adaptation layer indication, can be provided [RFC5061]. If authenticated chunks are used, the chunk types required to be sent authenticated by the peer can be provided [RFC4895]. An 'SCTP_Cant_Str_Assoc' notification is used to inform the application of a failure to create an association [RFC6458]. An application could use sendto() or sendmsg() to implicitly set up an association, thereby handing over a message that SCTP might send during the association setup phase [RFC6458]. Note that this mechanism is different from TCP's TFO mechanism: the message would arrive only once, after at least one RTT, as it is sent together with the third message exchanged during association setup, the COOKIE-ECHO chunk).
Send:
This sends a message of a certain length in bytes over an association. A number can be provided to later refer to the correct message when reporting an error, and a stream id is provided to specify the stream to be used inside an association (we consider this as a mandatory parameter here for simplicity: if not provided, the stream id defaults to 0). A condition to abandon the message can be specified (for example limiting the number of retransmissions or the lifetime of the user message). This allows control of the partial reliability extension [RFC3758] [RFC7496]. An optional maximum lifetime can specify the time after which the message should be discarded rather than sent. A choice (advisory, i.e., not guaranteed) of the preferred path can be made by providing a socket, and the message can be delivered out-of-order if the 'unordered' flag is set. An advisory flag indicates that the peer should not delay the acknowledgement of the user message provided [RFC7053]. Another advisory flag indicates whether the application prefers to avoid bundling user data with other outbound DATA chunks (i.e., in the same packet). A payload protocol-id can be provided to pass a value that indicates the type of payload protocol data to the peer. If authenticated chunks are used, the key identifier for authenticating DATA chunks can be provided [RFC4895].
Receive:
Messages are received from an association, and optionally a stream within the association, with their size returned. The application is notified of the availability of data via a 'Data Arrive' notification. If the sender has included a payload protocol-id, this value is also returned. If the received message is only a partial delivery of a whole message, a 'partial' flag will indicate so, in which case the stream id and a stream sequence number are provided to the application.
Shutdown:
This primitive gracefully closes an association, reliably delivering any data that has already been handed over to SCTP. A parameter lets the application control whether further receive or send operations or both are disabled when the call is issued. A return code informs about success or failure of this procedure.
Abort:
This ungracefully closes an association, by discarding any locally queued data and informing the peer that the association was aborted. Optionally, an abort reason to be passed to the peer may be provided by the application. A return code informs about success or failure of this procedure.
Change Heartbeat / Request Heartbeat:
This allows the application to enable/disable heartbeats and optionally specify a heartbeat frequency as well as requesting a single heartbeat to be carried out upon a function call, with a notification about success or failure of transmitting the HEARTBEAT chunk to the destination.
Configure Max. Retransmissions of an Association:
The parameter 'Association.Max.Retrans' [RFC4960] (called "sasoc_maxrxt" in the SCTP sockets API extensions [RFC6458]) allows the configuration of the number of unsuccessful retransmissions after which an entire association is considered as failed; this should invoke a 'Communication Lost' notification.
Set Primary:
This allows the ability to set a new primary default path for an association by providing a socket. Optionally, a default source address to be used in IP datagrams can be provided.
Change Local Address / Set Peer Primary:
This allows an endpoint to add/remove local addresses to/from an association. In addition, the peer can be given a hint for which address to use as the primary address [RFC5061].
Configure Path Switchover:
The abstract API contains a primitive called 'Set Failure Threshold' [RFC4960]. This configures the parameter 'Path.Max.Retrans', which determines after how many retransmissions a particular transport address is considered as unreachable. If there are more transport addresses available in an association, reaching this limit will invoke a path switchover. An extension called "SCTP-PF" adds a concept of "Potentially Failed (PF)" paths to this method [RFC7829]. When a path is in PF state, SCTP will not entirely give up sending on that path, but it will preferably send data on other active paths if such paths are available. Entering the PF state is done upon exceeding a configured maximum number of retransmissions. Thus, for all paths where this mechanism is used, there are two configurable error thresholds: one to decide that a path is in PF state, and one to decide that the transport address is unreachable.
Set/Get Authentication Parameters:
This allows an endpoint to add/remove key material to/from an association. In addition, the chunk types being authenticated can be queried [RFC4895].
Add/Reset Streams, Reset Association:
This allows an endpoint to add streams to an existing association or to reset them individually. Additionally, the association can be reset [RFC6525].
Status:
The 'Status' primitive returns a data block with information about a specified association, containing: an association connection state; a destination transport address list; destination transport address reachability states; current local and peer receiver window sizes; current local congestion window sizes; number of unacknowledged DATA chunks; number of DATA chunks pending receipt; a primary path; the most recent Smoothed Round-Trip Time (SRTT) on a primary path; RTO on a primary path; SRTT and RTO on other destination addresses [RFC4960]; and an MTU per path [RFC6458].
Enable/Disable Interleaving:
This allows the negotiation of user message interleaving support for future associations to be enabled or disabled. For existing associations, it is possible to query whether user message interleaving support was negotiated or not on a particular association [RFC8260].
Set Stream Scheduler:
This allows the ability to select a stream scheduler per association, with a choice of: First-Come, First-Served; Round-Robin; Round-Robin per Packet; Priority-Based; Fair Bandwidth; and Weighted Fair Queuing [RFC8260].
Configure Stream Scheduler:
This allows the ability to change a parameter per stream for the schedulers: a priority value for the Priority-Based scheduler and a weight for the Weighted Fair Queuing scheduler.
Enable/Disable NoDelay:
This turns on/off any Nagle-like algorithm for an association [RFC6458].
Configure Send Buffer Size:
This controls the amount of data SCTP may have waiting in internal buffers to be sent or retransmitted [RFC6458].
Configure Receive Buffer Size:
This sets the receive buffer size in octets, thereby controlling the receiver window for an association [RFC6458].
Configure Message Fragmentation:
If a user message causes an SCTP packet to exceed the maximum fragmentation size (which can be provided by the application and is otherwise the Path MTU (PMTU) size), then the message will be fragmented by SCTP. Disabling message fragmentation will produce an error instead of fragmenting the message [RFC6458].
Configure Path MTU Discovery:
Path MTU Discovery (PMTUD) can be enabled or disabled per peer address of an association (Section 8.1.12 of [RFC6458]). When it is enabled, the current Path MTU value can be obtained. When it is disabled, the Path MTU to be used can be controlled by the application.
Configure Delayed SACK Timer:
The time before sending a SACK can be adjusted; delaying SACKs can be disabled; and the number of packets that must be received before a SACK is sent without waiting for the delay timer to expire can be configured [RFC6458].
Set Cookie Life Value:
The cookie life value can be adjusted (Section 8.1.2 of [RFC6458]). 'Valid.Cookie.Life' is also one of the parameters that is potentially adjustable with 'SetProtocolParameters' [RFC4960].
Set Maximum Burst:
The maximum burst of packets that can be emitted by a particular association (default 4, and values above 4 are optional to implement) can be adjusted (Section 8.1.2 of [RFC6458]). 'Max.Burst' is also one of the parameters that is potentially adjustable with 'SetProtocolParameters' [RFC4960].
Configure RTO Calculation:
The abstract API contains the following adjustable parameters: 'RTO.Initial'; 'RTO.Min'; 'RTO.Max'; 'RTO.Alpha'; and 'RTO.Beta'. Only the initial, minimum and maximum RTOs are also described as configurable in the SCTP sockets API extensions [RFC6458].
Set DSCP Value:
The DSCP value can be set per peer address of an association (Section 8.1.12 of [RFC6458]).
Set IPv6 Flow Label:
The flow label field can be set per peer address of an association (Section 8.1.12 of [RFC6458]).
Set Partial Delivery Point:
This allows the ability to specify the size of a message where partial delivery will be invoked. Setting this to a lower value will cause partial deliveries to happen more often [RFC6458].
Communication Up Notification:
When a lost communication to an endpoint is restored or when SCTP becomes ready to send or receive user messages, this notification informs the application process about the affected association, the type of event that has occurred, the complete set of sockets of the peer, the maximum number of allowed streams, and the inbound stream count (the number of streams the peer endpoint has requested). If interleaving is supported by both endpoints, this information is also included in this notification.
Restart Notification:
When SCTP has detected that the peer has restarted, this notification is passed to the upper layer [RFC6458].
Data Arrive Notification:
When a message is ready to be retrieved via the 'Receive' primitive, the application is informed by this notification.
Send Failure Notification / Receive Unsent Message / Receive Unacknowledged Message:
When a message cannot be delivered via an association, the sender can be informed about it and learn whether the message has just not been acknowledged or (e.g., in case of lifetime expiry) if it has not even been sent. This can also inform the sender that a part of the message has been successfully delivered.
Network Status Change Notification:
This informs the application about a socket becoming active/inactive [RFC4960] or "Potentially Failed" [RFC7829].
Communication Lost Notification:
When SCTP loses communication to an endpoint (e.g., via heartbeats or excessive retransmission) or detects an abort, this notification informs the application process of the affected association and the type of event (failure OR termination in response to a shutdown or abort request).
Shutdown Complete Notification:
When SCTP completes the shutdown procedures, this notification is passed to the upper layer, informing it about the affected association.
Authentication Notification:
When SCTP wants to notify the upper layer regarding the key management related to authenticated chunks [RFC4895], this notification is passed to the upper layer.
Adaptation Layer Indication Notification:
When SCTP completes the association setup and the peer provided an adaptation layer indication, this is passed to the upper layer [RFC5061] [RFC6458].
Stream Reset Notification:
When SCTP completes the procedure for resetting streams [RFC6525], this notification is passed to the upper layer, informing it about the result.
Association Reset Notification:
When SCTP completes the association reset procedure [RFC6525], this notification is passed to the upper layer, informing it about the result.
Stream Change Notification:
When SCTP completes the procedure used to increase the number of streams [RFC6525], this notification is passed to the upper layer, informing it about the result.
Sender Dry Notification:
When SCTP has no more user data to send or retransmit on a particular association, this notification is passed to the upper layer [RFC6458].
Partial Delivery Aborted Notification:
When a receiver has begun to receive parts of a user message but the delivery of this message is then aborted, this notification is passed to the upper layer (Section 6.1.7 of [RFC6458]).
Initialize:
Initializeは、ローカルアドレスのセット（および、提供された場合はローカルポート番号）にバインドしたローカルのSCTPインスタンスを作成します[RFC4960]。 Initializeは、ローカルアドレスのセットごとに1回だけ呼び出す必要があります。 アソシエーションごとのいくつかの初期化パラメーターは、アソシエーションが作成された後、（下記のプリミティブ「Associate」によって）接続される前に使用できます。 すなわち、アプリケーションがサポートする準備ができている受信ストリームの最大数、INIT（アソシエーション確立の最初のメッセージ）を送信する際に行う試行の最大回数、INITを試行する際に使用する最大再送タイムアウト（RTO）値です[RFC6458]。 この時点で、接続する前に、アプリケーションはリモートのUDPカプセル化ポート番号を設定することでUDPカプセル化を有効にすることもできます[RFC6951]。
Associate:
これは、ローカルのSCTPインスタンスとリモートのSCTPインスタンスを接続するアソシエーション（SCTPにおけるコネクションの同等物）を作成します。 リモートエンドポイントを識別するために、1つまたは（「connectx」を使用して）複数のソケットを与えることができます（[RFC6458]のセクション9.9）。 ほとんどのプリミティブは特定のアソシエーションに関連付けられており、そのアソシエーションは最初に作成されているものと想定しています。 Associateは、後で複数のパスを使用できるように、宛先トランスポートアドレスのリストを返すことができます。 返されたソケットのうちの1つが、このピアにSCTPパケットを送信するためのデフォルトのプライマリーパスとしてローカルエンドポイントによって選択されますが、この選択は宛先アドレスのリストを使ってアプリケーションが変更できます。 Associateには要求する送信ストリームの数も与えられ、任意でネゴシエートされた送信ストリームの数を返します。 32ビットの任意のパラメーターである適応層表示（adaptation layer indication）を提供できます[RFC5061]。 認証付きチャンクを使用する場合は、ピアが認証して送信することを要求するチャンクタイプを提供できます[RFC4895]。 アソシエーションの作成に失敗したことをアプリケーションに通知するために、「SCTP_Cant_Str_Assoc」通知が使われます[RFC6458]。 アプリケーションは、sendto()やsendmsg()を使って暗黙的にアソシエーションを確立し、それによってSCTPがアソシエーション確立フェーズ中に送信する可能性のあるメッセージを引き渡すこともできます[RFC6458]。 このメカニズムはTCPのTFOメカニズムとは異なることに注意してください。 メッセージはアソシエーション確立中に交換される3番目のメッセージであるCOOKIE-ECHOチャンクとともに送信されるので、少なくとも1 RTT後に、1回だけ到着します）。
Send:
これは、アソシエーション上で特定のバイト長のメッセージを送信します。 エラーを報告する際に後で正しいメッセージを参照するための番号を提供でき、アソシエーション内で使用するストリームを指定するためにストリームIDが提供されます（ここでは簡単のためにこれを必須のパラメーターとみなします。提供されない場合、ストリームIDのデフォルトは0です）。 メッセージを放棄する条件（たとえば、再送回数やユーザーメッセージの有効期間の制限）を指定できます。 これにより、部分信頼性拡張[RFC3758] [RFC7496]を制御できます。 任意の最大有効期間によって、メッセージを送信せずに破棄すべき時間を指定できます。 ソケットを提供することで優先するパスを（助言的に、つまり保証なしで）選択でき、「unordered」フラグが設定されている場合はメッセージを順序どおりでなく配送できます。 助言的なフラグにより、提供されたユーザーメッセージの確認応答をピアが遅延させるべきでないことを示します[RFC7053]。 別の助言的なフラグは、アプリケーションがユーザーデータを他の送信DATAチャンクとバンドルする（つまり、同じパケットに入れる）ことを避けたいかどうかを示します。 ペイロードプロトコルデータの種類を示す値をピアに渡すために、ペイロードプロトコルIDを提供できます。 認証付きチャンクを使用する場合は、DATAチャンクを認証するための鍵識別子を提供できます[RFC4895]。
Receive:
メッセージは、アソシエーション（および任意でアソシエーション内のストリーム）から受信され、そのサイズが返されます。 アプリケーションには、「Data Arrive」通知によってデータが利用可能であることが通知されます。 送信者がペイロードプロトコルIDを含めている場合は、この値も返されます。 受信したメッセージがメッセージ全体の部分的な配送にすぎない場合は、「partial」フラグがそのことを示し、その場合はストリームIDとストリームシーケンス番号がアプリケーションに提供されます。
Shutdown:
このプリミティブは、すでにSCTPに引き渡されたデータを信頼性をもって配送しつつ、アソシエーションを正常にクローズします。 パラメーターにより、呼び出しを発行したときに、以降の受信操作と送信操作のどちらを（あるいは両方を）無効にするかをアプリケーションが制御できます。 戻りコードは、この手続きの成功または失敗を知らせます。
Abort:
これは、ローカルにキューに入れられたデータを破棄し、アソシエーションが中断されたことをピアに通知することで、アソシエーションを正常でない形でクローズします。 任意で、ピアに渡す中断の理由をアプリケーションが提供してもかまいません。 戻りコードは、この手続きの成功または失敗を知らせます。
Change Heartbeat / Request Heartbeat:
これにより、アプリケーションはハートビートを有効化／無効化し、任意でハートビートの頻度を指定できます。 また、関数呼び出し時に単一のハートビートを実行するよう要求することもでき、その場合は宛先へのHEARTBEATチャンクの送信の成功または失敗に関する通知が行われます。
Configure Max. Retransmissions of an Association:
パラメーター「Association.Max.Retrans」[RFC4960]（SCTPソケットAPI拡張[RFC6458]では「sasoc_maxrxt」と呼ばれます）により、アソシエーション全体が失敗したとみなされるまでの、失敗した再送の回数を設定できます。 これは「Communication Lost」通知を発生させるべきです。
Set Primary:
これにより、ソケットを提供することで、アソシエーションの新しいデフォルトのプライマリーパスを設定できます。 任意で、IPデータグラムで使用するデフォルトの送信元アドレスを提供できます。
Change Local Address / Set Peer Primary:
これにより、エンドポイントはアソシエーションにローカルアドレスを追加したり、アソシエーションからローカルアドレスを削除したりできます。 さらに、どのアドレスをプライマリーアドレスとして使用するかのヒントをピアに与えることができます[RFC5061]。
Configure Path Switchover:
抽象APIには「Set Failure Threshold」というプリミティブが含まれています[RFC4960]。 これは、特定のトランスポートアドレスが何回の再送の後に到達不能とみなされるかを決定するパラメーター「Path.Max.Retrans」を設定します。 アソシエーションで利用可能なトランスポートアドレスが他にもある場合、この上限に達するとパスの切り替えが発生します。 「SCTP-PF」という拡張は、この方法に「潜在的に失敗した（Potentially Failed：PF）」パスという概念を追加します[RFC7829]。 パスがPF状態にある場合、SCTPはそのパスでの送信を完全にはあきらめませんが、他にアクティブなパスが利用可能であれば、そちらで優先的にデータを送信します。 PF状態には、設定された最大再送回数を超えたときに入ります。 したがって、このメカニズムを使用するすべてのパスには、設定可能なエラーしきい値が2つあります。 1つはパスがPF状態にあると判断するためのもので、もう1つはトランスポートアドレスが到達不能であると判断するためのものです。
Set/Get Authentication Parameters:
これにより、エンドポイントはアソシエーションに鍵素材を追加したり、アソシエーションから鍵素材を削除したりできます。 さらに、認証されているチャンクタイプを問い合わせることができます[RFC4895]。
Add/Reset Streams, Reset Association:
これにより、エンドポイントは既存のアソシエーションにストリームを追加したり、ストリームを個別にリセットしたりできます。 さらに、アソシエーションをリセットすることもできます[RFC6525]。
Status:
「Status」プリミティブは、指定されたアソシエーションに関する情報を含むデータブロックを返します。 その内容は、アソシエーションのコネクション状態、宛先トランスポートアドレスのリスト、宛先トランスポートアドレスの到達可能性の状態、ローカルとピアの現在の受信ウィンドウサイズ、ローカルの現在の輻輳ウィンドウサイズ、確認応答されていないDATAチャンクの数、受信保留中のDATAチャンクの数、プライマリーパス、プライマリーパスでの最新の平滑化往復時間（SRTT）、プライマリーパスでのRTO、他の宛先アドレスでのSRTTとRTO[RFC4960]、およびパスごとのMTU[RFC6458]です。
Enable/Disable Interleaving:
これにより、今後のアソシエーションに対するユーザーメッセージのインターリーブのサポートのネゴシエーションを有効化または無効化できます。 既存のアソシエーションについては、特定のアソシエーションでユーザーメッセージのインターリーブのサポートがネゴシエートされたかどうかを問い合わせることができます[RFC8260]。
Set Stream Scheduler:
これにより、アソシエーションごとにストリームスケジューラーを選択できます。 選択肢は、First-Come, First-Served、Round-Robin、Round-Robin per Packet、Priority-Based、Fair Bandwidth、Weighted Fair Queuingです[RFC8260]。
Configure Stream Scheduler:
これにより、スケジューラーのストリームごとのパラメーターを変更できます。 Priority-Basedスケジューラーでは優先度の値、Weighted Fair Queuingスケジューラーでは重みです。
Enable/Disable NoDelay:
これは、アソシエーションに対するNagleのようなアルゴリズムをオン／オフにします[RFC6458]。
Configure Send Buffer Size:
これは、送信または再送されるのを内部バッファーで待つことができるデータの量を制御します[RFC6458]。
Configure Receive Buffer Size:
これは、受信バッファーのサイズをオクテット単位で設定し、それによってアソシエーションの受信ウィンドウを制御します[RFC6458]。
Configure Message Fragmentation:
ユーザーメッセージによってSCTPパケットが最大フラグメント化サイズ（アプリケーションが提供でき、そうでない場合はパスMTU（PMTU）のサイズ）を超える場合、メッセージはSCTPによってフラグメント化されます。 メッセージのフラグメント化を無効にすると、メッセージをフラグメント化する代わりにエラーが発生します[RFC6458]。
Configure Path MTU Discovery:
パスMTU探索（PMTUD）は、アソシエーションのピアアドレスごとに有効化または無効化できます（[RFC6458]のセクション8.1.12）。 有効な場合は、現在のパスMTUの値を取得できます。 無効な場合は、使用するパスMTUをアプリケーションが制御できます。
Configure Delayed SACK Timer:
SACKを送信するまでの時間を調整でき、SACKの遅延を無効にでき、遅延タイマーが期限切れになるのを待たずにSACKを送信するまでに受信しなければならないパケットの数を設定できます[RFC6458]。
Set Cookie Life Value:
クッキーの有効期間の値を調整できます（[RFC6458]のセクション8.1.2）。 「Valid.Cookie.Life」も、「SetProtocolParameters」で調整できる可能性のあるパラメーターの1つです[RFC4960]。
Set Maximum Burst:
特定のアソシエーションが送出できるパケットの最大バースト（デフォルトは4で、4を超える値の実装は任意です）を調整できます（[RFC6458]のセクション8.1.2）。 「Max.Burst」も、「SetProtocolParameters」で調整できる可能性のあるパラメーターの1つです[RFC4960]。
Configure RTO Calculation:
抽象APIには、調整可能なパラメーターとして「RTO.Initial」「RTO.Min」「RTO.Max」「RTO.Alpha」「RTO.Beta」が含まれています。 SCTPソケットAPI拡張[RFC6458]でも設定可能と記述されているのは、初期値、最小値、最大値のRTOだけです。
Set DSCP Value:
DSCP値は、アソシエーションのピアアドレスごとに設定できます（[RFC6458]のセクション8.1.12）。
Set IPv6 Flow Label:
フローラベルフィールドは、アソシエーションのピアアドレスごとに設定できます（[RFC6458]のセクション8.1.12）。
Set Partial Delivery Point:
これにより、部分配送が発生するメッセージのサイズを指定できます。 これを小さな値に設定すると、部分配送がより頻繁に発生します[RFC6458]。
Communication Up Notification:
エンドポイントとの失われた通信が回復したとき、またはSCTPがユーザーメッセージを送受信する準備ができたときに、この通知はアプリケーションプロセスに次の情報を知らせます。 すなわち、影響を受けたアソシエーション、発生したイベントの種類、ピアのソケットの完全なセット、許可されたストリームの最大数、および受信ストリームの数（ピアエンドポイントが要求したストリームの数）です。 両方のエンドポイントがインターリーブをサポートしている場合は、その情報もこの通知に含まれます。
Restart Notification:
ピアが再起動したことをSCTPが検出したときに、この通知が上位層に渡されます[RFC6458]。
Data Arrive Notification:
メッセージを「Receive」プリミティブで取得できるようになったときに、この通知によってアプリケーションに知らされます。
Send Failure Notification / Receive Unsent Message / Receive Unacknowledged Message:
メッセージをアソシエーションを介して配送できない場合、送信者はそのことを知らされ、メッセージが単に確認応答されていないだけなのか、それとも（たとえば有効期間の期限切れの場合に）送信すらされていないのかを知ることができます。 これにより、メッセージの一部が正常に配送されたことを送信者に知らせることもできます。
Network Status Change Notification:
これは、ソケットがアクティブ／非アクティブ[RFC4960]、または「潜在的に失敗した（Potentially Failed）」[RFC7829]になったことをアプリケーションに通知します。
Communication Lost Notification:
SCTPが（たとえばハートビートや過剰な再送によって）エンドポイントとの通信を失ったとき、または中断を検出したときに、この通知は、影響を受けたアソシエーションとイベントの種類（失敗、または（OR）シャットダウンや中断の要求に応じた終了）をアプリケーションプロセスに通知します。
Shutdown Complete Notification:
SCTPがシャットダウン手続きを完了すると、この通知が上位層に渡され、影響を受けたアソシエーションについて知らせます。
Authentication Notification:
SCTPが認証付きチャンク[RFC4895]に関連する鍵管理について上位層に通知したいときに、この通知が上位層に渡されます。
Adaptation Layer Indication Notification:
SCTPがアソシエーションの確立を完了し、ピアが適応層表示を提供した場合、これが上位層に渡されます[RFC5061] [RFC6458]。
Stream Reset Notification:
SCTPがストリームをリセットする手続き[RFC6525]を完了すると、この通知が上位層に渡され、その結果を知らせます。
Association Reset Notification:
SCTPがアソシエーションのリセット手続き[RFC6525]を完了すると、この通知が上位層に渡され、その結果を知らせます。
Stream Change Notification:
SCTPがストリームの数を増やすために使われる手続き[RFC6525]を完了すると、この通知が上位層に渡され、その結果を知らせます。
Sender Dry Notification:
SCTPが特定のアソシエーションで送信または再送するユーザーデータをもう持っていないときに、この通知が上位層に渡されます[RFC6458]。
Partial Delivery Aborted Notification:
受信者がユーザーメッセージの一部の受信を開始したものの、そのメッセージの配送がその後中断された場合に、この通知が上位層に渡されます（[RFC6458]のセクション6.1.7）。

3.3.1. Excluded Primitives or Parameters

3.3.1. 除外したプリミティブやパラメーター

The 'Receive' primitive can return certain additional information, but this is optional to implement and therefore not considered. With a 'Communication Lost' notification, some more information may optionally be passed to the application (e.g., identification to retrieve unsent and unacknowledged data). SCTP "can invoke" a 'Communication Error' notification and "may send" a 'Restart' notification, making these two notifications optional to implement. The list provided under 'Status' includes "etc.", indicating that more information could be provided. The primitive 'Get SRTT Report' returns information that is included in the information that 'Status' provides and is therefore not discussed. The 'Destroy SCTP Instance' API function was excluded: it erases the SCTP instance that was created by 'Initialize' but is not a primitive as defined in this document because it does not relate to a transport feature. The 'Shutdown' event informs an application that the peer has sent a SHUTDOWN, and hence no further data should be sent on this socket (Section 6.1 of [RFC6458]). However, if an application would try to send data on the socket, it would get an error message anyway; thus, this event is classified as "just affecting the application programming style, not how the underlying protocol operates" and is not included here.

「Receive」プリミティブは特定の追加情報を返すことができますが、これは実装が任意であるため考慮しません。 「Communication Lost」通知では、任意でさらにいくつかの情報（たとえば、送信されていないデータや確認応答されていないデータを取得するための識別情報）がアプリケーションに渡される場合があります。 SCTPは「Communication Error」通知を「発生させることができ」、「Restart」通知を「送信してもよい」とされており、これら2つの通知は実装が任意となっています。 「Status」の下に示されたリストには「など」が含まれており、さらに多くの情報が提供される可能性があることを示しています。 プリミティブ「Get SRTT Report」は、「Status」が提供する情報に含まれる情報を返すため、論じません。 「Destroy SCTP Instance」API関数は除外しました。 これは「Initialize」によって作成されたSCTPインスタンスを消去しますが、トランスポート機能に関係しないため、この文書で定義するプリミティブではありません。 「Shutdown」イベントは、ピアがSHUTDOWNを送信したため、このソケットでこれ以上データを送信すべきでないことをアプリケーションに通知します（[RFC6458]のセクション6.1）。 しかし、アプリケーションがそのソケットでデータを送信しようとしても、いずれにせよエラーメッセージを受け取ることになります。 したがって、このイベントは「アプリケーションのプログラミングスタイルに影響するだけで、下位のプロトコルの動作には影響しない」ものに分類され、ここには含めていません。

3.4. Primitives Provided by UDP and UDP-Lite

3.4. UDPとUDP-Liteが提供するプリミティブ

The set of pass 1 primitives for UDP and UDP-Lite is documented in [RFC8304].

UDPとUDP-Liteのパス1のプリミティブのセットは、[RFC8304]に記載されています。

3.5. The Service of LEDBAT

3.5. LEDBATのサービス

The service of the LEDBAT congestion control mechanism is described as follows:

LEDBAT輻輳制御メカニズムのサービスは、次のように説明されています：

LEDBAT is designed for use by background bulk-transfer applications to be no more aggressive than standard TCP congestion control (as specified in RFC 5681) and to yield in the presence of competing flows, thus limiting interference with the network performance of competing flows [RFC6817].

LEDBATは、バックグラウンドの一括転送アプリケーションが、（RFC 5681で規定されている）標準のTCP輻輳制御よりも積極的にならず、競合するフローが存在する場合には譲ることで、競合するフローのネットワーク性能への干渉を抑えるように使用することを想定して設計されています[RFC6817]。

LEDBAT does not have any primitives, as LEDBAT is not a transport protocol. According to its specification [RFC6817]:

LEDBATはトランスポートプロトコルではないため、プリミティブを持ちません。 その仕様[RFC6817]によれば：

LEDBAT can be used as part of a transport protocol or as part of an application, as long as the data transmission mechanisms are capable of carrying timestamps and acknowledging data frequently. LEDBAT can be used with TCP, Stream Control Transmission Protocol (SCTP), and Datagram Congestion Control Protocol (DCCP), with appropriate extensions where necessary; and it can be used with proprietary application protocols, such as those built on top of UDP for peer-to-peer (P2P) applications.

LEDBATは、データ送信メカニズムがタイムスタンプを運び、データを頻繁に確認応答できるのであれば、トランスポートプロトコルの一部として、またはアプリケーションの一部として使用できます。 LEDBATは、必要に応じて適切な拡張を加えることで、TCP、ストリーム制御伝送プロトコル（SCTP）、データグラム輻輳制御プロトコル（DCCP）とともに使用できます。 また、ピアツーピア（P2P）アプリケーションのためにUDP上に構築されたものなど、独自のアプリケーションプロトコルとともに使用することもできます。

At the time of writing, the appropriate extensions for TCP, SCTP, or DCCP do not exist.

執筆時点では、TCP、SCTP、DCCPのための適切な拡張は存在しません。

A number of configurable parameters exist in the LEDBAT specification: TARGET, which is the queuing delay target at which LEDBAT tries to operate, must be set to 100 ms or less. 'allowed_increase' (should be 1, must be greater than 0) limits the speed at which LEDBAT increases its rate. 'gain', which according to [RFC6817] "MUST be set to 1 or less" to avoid a faster ramp-up than TCP Reno, determines how quickly the sender responds to changes in queueing delay. Implementations may divide 'gain' into two parameters: one for increase and a possibly larger one for decrease. We call these parameters 'Gain_Inc' and 'Gain_Dec' here. 'Base_History' is the size of the list of measured base delays, and, according to [RFC6817], "SHOULD be 10". This list can be filtered using a 'Filter' function, which is not prescribed [RFC6817], that yields a list of size 'Current_Filter'. The initial and minimum congestion windows, 'Init_CWND' and 'Min_CWND', should both be 2.

LEDBATの仕様には、設定可能なパラメーターがいくつか存在します。 LEDBATが動作しようとするキューイング遅延の目標であるTARGETは、100ms以下に設定しなければなりません。 「allowed_increase」（1であるべきで、0より大きくなければなりません）は、LEDBATがレートを増加させる速度を制限します。 「gain」は、TCP Renoよりも速い立ち上がりを避けるために、[RFC6817]によれば「1以下に設定しなければなりません（MUST）」とされており、キューイング遅延の変化に送信者がどれだけ速く反応するかを決定します。 実装は「gain」を2つのパラメーターに分割してもかまいません。 1つは増加用で、もう1つは（おそらくより大きな）減少用です。 ここでは、これらのパラメーターを「Gain_Inc」と「Gain_Dec」と呼びます。 「Base_History」は測定された基本遅延のリストのサイズであり、[RFC6817]によれば「10であるべきです（SHOULD）」。 このリストは、規定されていない[RFC6817]「Filter」関数を使ってフィルタリングでき、その結果としてサイズ「Current_Filter」のリストが得られます。 初期輻輳ウィンドウと最小輻輳ウィンドウである「Init_CWND」と「Min_CWND」は、どちらも2であるべきです。

Regarding which of these parameters should be under control of an application, the possible range goes from exposing nothing on the one hand to considering everything that is not prescribed with a "MUST" in the specification as a parameter on the other hand. Function implementations are not provided as a parameter to any of the transport protocols discussed here; hence, we do not regard the 'Filter' function as a parameter. However, to avoid unnecessarily limiting future implementations, we consider all other parameters above as tunable parameters that should be exposed.

これらのパラメーターのうちどれをアプリケーションの制御下に置くべきかについては、何も公開しないという一方の極から、仕様で「しなければなりません（MUST）」と規定されていないものをすべてパラメーターとみなすという他方の極まで、さまざまな範囲が考えられます。 ここで論じるトランスポートプロトコルのいずれにおいても、関数の実装はパラメーターとして提供されていません。 したがって、「Filter」関数はパラメーターとはみなしません。 しかし、将来の実装を不必要に制限することを避けるため、上記の他のすべてのパラメーターは、公開すべき調整可能なパラメーターとみなします。

4. Pass 2

4. パス2

This pass categorizes the primitives from pass 1 based on whether they relate to a connection or to data transmission. Primitives are presented following the nomenclature "CATEGORY.[SUBCATEGORY].PRIMITIVENAME.PROTOCOL". The CATEGORY can be CONNECTION or DATA. Within the CONNECTION category, ESTABLISHMENT, AVAILABILITY, MAINTENANCE, and TERMINATION subcategories can be considered. The DATA category does not have any SUBCATEGORY. The PROTOCOL name "UDP(-Lite)" is used when primitives are equivalent for UDP and UDP-Lite; the PROTOCOL name "TCP" refers to both TCP and MPTCP. We present "connection" as a general protocol-independent concept and use it to refer to, e.g., TCP connections (identifiable by a unique pair of IP addresses and TCP port numbers), SCTP associations (identifiable by multiple IP address and port number pairs), as well UDP and UDP-Lite connections (identifiable by a unique socket pair).

このパスでは、パス1のプリミティブを、コネクションに関係するかデータ送信に関係するかに基づいて分類します。 プリミティブは、「CATEGORY.[SUBCATEGORY].PRIMITIVENAME.PROTOCOL」という命名法に従って示します。 CATEGORYはCONNECTIONまたはDATAです。 CONNECTIONカテゴリー内では、ESTABLISHMENT、AVAILABILITY、MAINTENANCE、TERMINATIONのサブカテゴリーが考えられます。 DATAカテゴリーにはSUBCATEGORYはありません。 プリミティブがUDPとUDP-Liteで同等の場合はPROTOCOL名「UDP(-Lite)」を使用し、PROTOCOL名「TCP」はTCPとMPTCPの両方を指します。 「コネクション」はプロトコルに依存しない一般的な概念として示し、たとえば、TCPコネクション（IPアドレスとTCPポート番号の一意のペアで識別可能）、SCTPアソシエーション（複数のIPアドレスとポート番号のペアで識別可能）、およびUDPとUDP-Liteのコネクション（一意のソケットペアで識別可能）を指すために使用します。

Some minor details are omitted for the sake of generalization -- e.g., SCTP's 'Close' [RFC4960] returns success or failure and lets the application control whether further receive or send operations, or both, are disabled [RFC6458]. This is not described in the same way for TCP [RFC0793], but these details play no significant role for the primitives provided by either TCP or SCTP (for the sake of being generic, it could be assumed that both receive and send operations are disabled in both cases).

一般化のために、いくつかの細かい点は省略しています。 たとえば、SCTPの「Close」[RFC4960]は成功または失敗を返し、以降の受信操作と送信操作のどちらを（あるいは両方を）無効にするかをアプリケーションが制御できるようにします[RFC6458]。 TCP[RFC0793]ではこれは同じようには記述されていませんが、これらの詳細はTCPとSCTPのどちらが提供するプリミティブにとっても重要な役割を果たしません（汎用性のために、どちらの場合も受信操作と送信操作の両方が無効になると想定することができます）。

The TCP 'Send' and 'Receive' primitives include usage of an 'urgent' parameter. This parameter controls a mechanism that is required to implement the "synch signal" used by telnet [RFC0854], but [RFC6093] states that "new applications SHOULD NOT employ the TCP urgent mechanism." Because pass 2 is meant as a basis for the creation of future systems, the "urgent" mechanism is excluded. This also concerns the notification 'Urgent Pointer Advance' in the 'Error_Report' (Section 4.2.4.1 of [RFC1122]).

TCPの「Send」と「Receive」のプリミティブには、「urgent」パラメーターの使用が含まれています。 このパラメーターは、telnet[RFC0854]で使用される「同期シグナル（synch signal）」を実装するために必要なメカニズムを制御しますが、[RFC6093]は「新しいアプリケーションはTCPの緊急メカニズムを採用すべきではありません（SHOULD NOT）。」と述べています。 パス2は将来のシステムを作成するための基礎として意図されているため、「緊急」メカニズムは除外します。 これは、「Error_Report」における「Urgent Pointer Advance」通知（[RFC1122]のセクション4.2.4.1）にも関係します。

Since LEDBAT is a congestion control mechanism and not a protocol, it is not currently defined when to enable/disable or configure the mechanism. For instance, it could be a one-time choice upon connection establishment or when listening for incoming connections, in which case it should be categorized under CONNECTION.ESTABLISHMENT or CONNECTION.AVAILABILITY, respectively. To avoid unnecessarily limiting future implementations, it was decided to place it under CONNECTION.MAINTENANCE, with all parameters that are described in the specification [RFC6817] made configurable.

LEDBATはプロトコルではなく輻輳制御メカニズムであるため、このメカニズムをいつ有効化／無効化または設定するかは現在定義されていません。 たとえば、コネクション確立時や着信コネクションをリッスンする際の一度きりの選択とすることも考えられ、その場合はそれぞれCONNECTION.ESTABLISHMENTまたはCONNECTION.AVAILABILITYに分類すべきです。 将来の実装を不必要に制限することを避けるため、仕様[RFC6817]で記述されているすべてのパラメーターを設定可能にしたうえで、CONNECTION.MAINTENANCEに置くことにしました。

4.1. CONNECTION-Related Primitives

ESTABLISHMENT:

ESTABLISHMENT（確立）：

Active creation of a connection from one transport endpoint to one or more transport endpoints. Interfaces to UDP and UDP-Lite allow both connection-oriented and connection-less usage of the API [RFC8085].

1つのトランスポートエンドポイントから1つ以上のトランスポートエンドポイントへのコネクションの能動的な作成。 UDPとUDP-Liteへのインターフェイスでは、APIのコネクション指向の使用とコネクションレスの使用の両方が可能です[RFC8085]。

  • CONNECT.TCP:

    Pass 1 primitive/event: 'Open' (active) or 'Open' (passive) with socket, followed by 'Send'

    Parameters: 1 local IP address (optional); 1 destination transport address (for active open; else the socket and the local IP address of the succeeding incoming connection request will be maintained); timeout (optional); options (optional); MKT configuration (optional); and user message (optional)

    Comments: if the local IP address is not provided, a default choice will automatically be made. The timeout can also be a retransmission count. The options are IP options to be used on all segments of the connection. At least the Source Route option is mandatory for TCP to provide. 'MKT configuration' refers to the ability to configure MKTs for authentication. The user message may be transmitted to the peer application immediately upon reception of the TCP SYN packet. To benefit from the lower latency this provides as part of the experimental TFO mechanism, its length must be at most the TCP's maximum segment size (minus TCP options used in the SYN). The message may also be delivered more than once to the application on the remote host.

RTO for INIT (optional); user message (optional); and remote UDP port number (optional)

The user message may be transmitted to the peer application immediately upon reception of the packet containing the COOKIE-ECHO chunk. To benefit from the lower latency this provides, its length must be limited such that it fits into the packet containing the COOKIE-ECHO chunk. If a remote UDP port number is provided, SCTP packets will be encapsulated in UDP.

MAINTENANCE:

MAINTENANCE（維持）：

Adjustments made to an open connection, or notifications about it. These are out-of-band messages to the protocol that can be issued at any time, at least after a connection has been established and before it has been terminated (with one exception: CHANGE_TIMEOUT.TCP can only be issued for an open connection when DATA.SEND.TCP is called). In some cases, these primitives can also be immediately issued during ESTABLISHMENT or AVAILABILITY, without waiting for the connection to be opened (e.g., CHANGE_TIMEOUT.TCP can be done using TCP's 'Open' primitive). For UDP and UDP-Lite, these functions may establish a setting per connection but may also be changed per datagram message.

オープンしているコネクションに対する調整、またはそれに関する通知。 これらはプロトコルに対する帯域外のメッセージであり、少なくともコネクションが確立された後、終了される前であれば、いつでも発行できます（ただし例外が1つあります：CHANGE_TIMEOUT.TCPは、オープンしているコネクションに対しては、DATA.SEND.TCPが呼び出されたときにしか発行できません）。 場合によっては、これらのプリミティブは、コネクションがオープンされるのを待たずに、ESTABLISHMENTやAVAILABILITYの間にただちに発行することもできます（たとえば、CHANGE_TIMEOUT.TCPはTCPの「Open」プリミティブを使って行うことができます）。 UDPとUDP-Liteでは、これらの関数はコネクションごとの設定を確立する場合がありますが、データグラムメッセージごとに変更することもできます。

    Parameters: timeout value (optional); adv_uto (optional); boolean uto_enabled (optional, default false); and boolean changeable (optional, default true)

    Comments: when sending data, an application can adjust the connection's timeout value (the time after which the connection will be aborted if data could not be delivered). If 'uto_enabled' is true, the 'timeout value' (or, if provided, the value 'adv_uto') will be advertised for the TCP on the other side of the connection to adapt its own user timeout accordingly. 'uto_enabled' controls whether the UTO option is enabled for a connection. This applies to both sending and receiving. 'changeable' controls whether the user timeout may be changed based on a UTO option received from the other end of the connection; it becomes false when the 'timeout value' is used.

4.2. DATA-Transfer-Related Primitives

All primitives in this section refer to an existing connection, i.e., a connection that was either established or made available for receiving data (although this is optional for the primitives of UDP(-Lite)). In addition to the listed parameters, all sending primitives contain a reference to a data block, and all receiving primitives contain a reference to available buffer space for the data. Note that CONNECT.TCP and LISTEN.TCP in the ESTABLISHMENT and AVAILABILITY categories also allow to transfer data (an optional user message) before the connection is fully established.

このセクションのすべてのプリミティブは、既存のコネクション、すなわち確立されたコネクション、またはデータを受信できるようにされたコネクションを参照します（ただし、UDP(-Lite)のプリミティブではこれは任意です）。 列挙したパラメーターに加えて、すべての送信プリミティブはデータブロックへの参照を含み、すべての受信プリミティブはデータのための利用可能なバッファー空間への参照を含みます。 ESTABLISHMENTカテゴリーとAVAILABILITYカテゴリーのCONNECT.TCPとLISTEN.TCPでも、コネクションが完全に確立される前にデータ（任意のユーザーメッセージ）を転送できることに注意してください。

  • SEND.TCP:

    Pass 1 primitive/event: 'Send'

    Parameters: timeout (optional); current_key (optional); and rnext_key (optional)

    Comments: this gives TCP a data block for reliable transmission to the TCP on the other side of the connection. The timeout can be configured with this call (see also CONNECTION.MAINTENANCE.CHANGE_TIMEOUT.TCP). 'current_key' and 'rnext_key' are authentication parameters that can be configured with this call (see also CONNECTION.MAINTENANCE.SET_AUTH.TCP).

  • SEND.SCTP:

    Pass 1 primitive/event: 'Send'

    Parameters: stream number; context (optional); socket (optional); unordered flag (optional); no-bundle flag (optional); payload protocol-id (optional); pr-policy (optional) pr-value (optional); sack-immediately flag (optional); and key-id (optional)

    Comments: this gives SCTP a data block for transmission to the SCTP on the other side of the connection (SCTP association). The 'stream number' denotes the stream to be used. The 'context' number can later be used to refer to the correct message when an error is reported. The 'socket' can be used to state which path should be preferred, if there are multiple paths available (see also CONNECTION.MAINTENANCE.SETPRIMARY.SCTP). The data block can be delivered out of order if the 'unordered' flag is set. The 'no-bundle flag' can be set to indicate a preference to avoid bundling. The 'payload protocol-id' is a number that will, if provided, be handed over to the receiving application. Using pr-policy and pr-value, the level of reliability can be controlled. The 'sack-immediately' flag can be used to indicate that the peer should not delay the sending of a SACK corresponding to the provided user message. If specified, the provided key-id is used for authenticating the user message.

  • SEND.UDP(-Lite):

    Pass 1 primitive/event: 'Send'

    Parameters: IP address and port number of the destination endpoint (optional if connected)

    Comments: this provides a message for unreliable transmission using UDP(-Lite) to the specified transport address. The IP address and port number may be omitted for connected UDP(-Lite) sockets. All CONNECTION.MAINTENANCE.SET_*.UDP(-Lite) primitives apply per message sent.

  • RECEIVE.TCP:

    Pass 1 primitive/event: 'Receive'

    Parameters: current_key (optional) and rnext_key (optional)

    Comments: 'current_key' and 'rnext_key' are authentication parameters that can be read with this call (see also CONNECTION.MAINTENANCE.GET_AUTH.TCP).

  • RECEIVE.SCTP:

    Pass 1 primitive/event: 'Data Arrive' notification, followed by 'Receive'

    Parameters: stream number (optional)

    Returns: stream sequence number (optional) and partial flag (optional)

    Comments: if the 'stream number' is provided, the call to receive only receives data on one particular stream. If a partial message arrives, this is indicated by the 'partial flag', and then the 'stream sequence number' must be provided such that an application can restore the correct order of data blocks that comprise an entire message.

  • RECEIVE.UDP(-Lite):

    Pass 1 primitive/event: 'Receive'

    Parameters: buffer for received datagram

    Comments: all CONNECTION.MAINTENANCE.GET_*.UDP(-Lite) primitives apply per message received.

  • SENDFAILURE-EVENT.SCTP:

    Pass 1 primitive/event: 'Send Failure' notification, optionally followed by 'Receive Unsent Message' or 'Receive Unacknowledged Message'

    Returns: cause code; context; and unsent or unacknowledged message (optional)

    Comments: 'cause code' indicates the reason of the failure, and 'context' is the context number if such a number has been provided in DATA.SEND.SCTP, for later use with 'Receive Unsent Message' or 'Receive Unacknowledged Message', respectively. These primitives can be used to retrieve the unsent or unacknowledged message (or part of the message, in case a part was delivered) if desired.

  • SEND_FAILURE.UDP(-Lite):

    Pass 1 primitive/event: 'Send'

    Comments: this may be used to probe for the effective PMTU when using in combination with the 'MAINTENANCE.SET_DF' primitive.

    Comments: this informs the application that the stack has no more user data to send.

  • PARTIAL_DELIVERY_ABORTED-EVENT.SCTP:

    Pass 1 primitive/event: 'Partial Delivery Aborted' notification

    Comments: this informs the receiver of a partial message that the further delivery of the message has been aborted.

  • SEND.TCP:

    パス1のプリミティブ／イベント：「Send」

5.2. DATA-Transfer-Related Transport Features

5.2. DATA-Transfer関連のトランスポート機能

All transport features in this section refer to an existing connection, i.e., a connection that was either established or made available for receiving data. Note that TCP allows the transfer of data (a single optional user message, possibly arriving multiple times) before the connection is fully established. Reliable data transfer entails delay -- e.g., for the sender to wait until it can transmit data or due to retransmission in case of packet loss.

このセクションのすべてのトランスポート機能は、既存のコネクション、すなわち確立されたコネクション、またはデータを受信できるようにされたコネクションを参照します。 TCPでは、コネクションが完全に確立される前にデータ（任意の単一のユーザーメッセージで、複数回到着する可能性があるもの）を転送できることに注意してください。 信頼性のあるデータ転送には遅延が伴います。 たとえば、送信者がデータを送信できるようになるまで待つための遅延や、パケット損失の場合の再送による遅延です。

7. Security Considerations

7. セキュリティーに関する考慮事項

Authentication, confidentiality protection, and integrity protection are identified as transport features [RFC8095]. These transport features are generally provided by a protocol or layer on top of the transport protocol; none of the transport protocols considered in this document provides these transport features on its own. Therefore, these transport features are not considered in this document, with the exception of native authentication capabilities of TCP and SCTP for which the security considerations in [RFC5925] and [RFC4895] apply.

認証、機密性の保護、完全性の保護は、トランスポート機能として特定されています[RFC8095]。 これらのトランスポート機能は、一般にトランスポートプロトコルの上のプロトコルまたは層によって提供されます。 この文書で考慮したトランスポートプロトコルはいずれも、それ自体ではこれらのトランスポート機能を提供しません。 したがって、この文書ではこれらのトランスポート機能を考慮しません。 ただし、TCPとSCTPに固有の認証能力は例外であり、それらには[RFC5925]と[RFC4895]のセキュリティーに関する考慮事項が適用されます。

Security considerations for the use of UDP and UDP-Lite are provided in the referenced RFCs. Security guidance for application usage is provided in the UDP Guidelines [RFC8085].

UDPとUDP-Liteの使用に関するセキュリティーの考慮事項は、参照しているRFCで提供されています。 アプリケーションでの使用に関するセキュリティーのガイダンスは、UDPガイドライン[RFC8085]で提供されています。

Appendix B. How This Document Was Developed

付録B. この文書の作成方法

This section gives an overview of the method that was used to develop this document. It was given to contributors for guidance, and it can be helpful for future updates or extensions.

このセクションでは、この文書を作成するために使用した方法の概要を示します。 この方法はガイダンスとして貢献者に与えられたものであり、将来の更新や拡張に役立つ可能性があります。

This document is only concerned with transport features that are explicitly exposed to applications via primitives. It also strictly follows RFC text: if a transport feature is truly relevant for an application, the RFCs should say so, and they should describe how to use and configure it. Thus, the approach followed for developing this document was to identify the right RFCs, then analyze and process their text.

この文書は、プリミティブを介してアプリケーションに明示的に公開されるトランスポート機能だけを対象としています。 また、RFCのテキストに厳密に従っています。 トランスポート機能がアプリケーションにとって本当に重要なのであれば、RFCはそのように述べ、それをどのように使用し設定するかを説明しているはずだからです。 したがって、この文書を作成するために採ったアプローチは、適切なRFCを特定し、そのテキストを分析して処理するというものでした。

Primitives that "MAY" be implemented by a transport protocol were excluded. To be included, the minimum requirement level for a primitive to be implemented by a protocol was "SHOULD". Where style requirement levels as described in [RFC2119] are not used, primitives were excluded when they are described in conjunction with statements like, e.g., "some implementations also provide" or "an implementation may also". Excluded primitives or parameters were briefly described in a dedicated subsection.

トランスポートプロトコルが実装「してもよいです（MAY）」とされているプリミティブは除外しました。 含めるためには、プロトコルがプリミティブを実装する要件レベルが最低でも「すべきです（SHOULD）」である必要がありました。 [RFC2119]で説明されているスタイルの要件レベルが使われていない場合は、たとえば「一部の実装は〜も提供する」や「実装は〜してもよい」といった記述とともに説明されているプリミティブを除外しました。 除外したプリミティブやパラメーターは、専用のサブセクションで簡単に説明しました。

Pass 1: This began by identifying text that talks about primitives. An API specification, abstract or not, obviously describes primitives -- but we are not *only* interested in API specifications. The text describing the 'Send' primitive in the API specified in [RFC0793], for instance, does not say that data transfer is reliable. TCP's reliability is clear, however, from this text in Section 1 of [RFC0793]:

パス1：これは、プリミティブについて述べているテキストを特定することから始めました。 抽象的なものであるかどうかにかかわらず、API仕様は明らかにプリミティブを説明していますが、私たちはAPI仕様*だけ*に関心があるわけではありません。 たとえば、[RFC0793]で規定されているAPIの「Send」プリミティブを説明するテキストは、データ転送に信頼性があるとは述べていません。 しかし、TCPの信頼性は、[RFC0793]のセクション1の次のテキストから明らかです：

The Transmission Control Protocol (TCP) is intended for use as a highly reliable host-to-host protocol between hosts in packet-switched computer communication networks, and in interconnected systems of such networks.

トランスミッション制御プロトコル（TCP）は、パケット交換型のコンピューター通信ネットワーク、およびそのようなネットワークを相互接続したシステムにおいて、ホスト間で使用する信頼性の高いホスト間プロトコルとして意図されています。

Some text for the pass 1 subsections was developed by copying and pasting all the relevant text parts from the relevant RFCs then adjusting the terminology to match that in Section 2 and shortening phrasing to match the general style of the document. An effort was made to formulate everything as a primitive description such that the primitive descriptions became as complete as possible (e.g., the 'SEND.TCP' primitive in pass 2 is explicitly described as reliably transferring data); text that is relevant for the primitives presented in this pass but still does not fit directly under any primitive was used in a subsection's introduction.

パス1のサブセクションのテキストの一部は、関連するRFCから関連するテキスト部分をすべてコピー＆ペーストし、その後、用語をセクション2の用語に合わせて調整し、文書全体のスタイルに合わせて言い回しを短くすることで作成しました。 プリミティブの説明ができるだけ完全になるように、すべてをプリミティブの説明として定式化するよう努めました（たとえば、パス2の「SEND.TCP」プリミティブは、データを信頼性をもって転送するものとして明示的に説明されています）。 このパスで提示したプリミティブに関係するものの、どのプリミティブの下にも直接当てはまらないテキストは、サブセクションの導入部で使用しました。

Pass 2: The main goal of this pass is unification of primitives. As input, only text from pass 1 was used (no exterior sources). The list in pass 2 is not arranged by protocol (i.e., "first protocol X, here are all the primitives; then protocol Y, here are all the primitives, ...") but by primitive (i.e., "primitive A, implemented this way in protocol X, this way in protocol Y, ..."). It was a goal to obtain as many similar pass 2 primitives as possible. For instance, this was sometimes achieved by not always maintaining a 1:1 mapping between pass 1 and pass 2 primitives, renaming primitives, etc. For every new primitive, the already-existing primitives were considered to try to make them as coherent as possible.

パス2：このパスの主な目標は、プリミティブの統一です。 入力としては、パス1のテキストだけを使用しました（外部の情報源は使用していません）。 パス2の一覧は、プロトコルごと（つまり、「まずプロトコルXについて、これがすべてのプリミティブ。次にプロトコルYについて、これがすべてのプリミティブ、…」）ではなく、プリミティブごと（つまり、「プリミティブA、プロトコルXではこのように実装され、プロトコルYではこのように実装され、…」）に並べています。 できるだけ多くの類似したパス2のプリミティブを得ることが目標でした。 たとえば、これは、パス1とパス2のプリミティブの間で1対1の対応付けを常には維持しないことや、プリミティブの名前を変更することなどによって実現した場合があります。 新しいプリミティブごとに、既存のプリミティブを考慮して、それらができるだけ一貫したものになるよう試みました。

For each primitive, the following style was used:

各プリミティブについて、次のスタイルを使用しました：

  • PRIMITIVENAME.PROTOCOL:

    Pass 1 primitive/event:

    Parameters:

    Returns:

    Comments:

  • PRIMITIVENAME.PROTOCOL:

    パス1のプリミティブ／イベント：

    パラメーター：

    戻り値：

    コメント：

The entries "Parameters", "Returns", and "Comments" were skipped when a primitive had no parameters, no described return value, or no comments seemed necessary, respectively. Optional parameters are followed by "(optional)". When known, default values were provided.

プリミティブにパラメーターがない場合、記述された戻り値がない場合、またはコメントが必要と思われない場合は、それぞれ「パラメーター」「戻り値」「コメント」の項目を省略しました。 任意のパラメーターの後には「（任意）」を付けています。 わかっている場合はデフォルト値を示しました。

Pass 3: The main point of this pass is to identify transport features that are the result of static properties of protocols, for which all protocols have to be listed together; this is then the final list of all available transport features. This list was primarily based on text from pass 2, with additional input from pass 1 (but no external sources).

パス3：このパスの要点は、プロトコルの静的な性質の結果であるトランスポート機能を特定することです。 そのためにはすべてのプロトコルをまとめて列挙しなければならず、これが利用可能なすべてのトランスポート機能の最終的な一覧となります。 この一覧は主にパス2のテキストに基づいており、パス1からの入力も追加しています（ただし、外部の情報源は使用していません）。
