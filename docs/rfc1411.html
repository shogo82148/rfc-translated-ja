RFC 1411

Telnet Authentication: Kerberos Version 4

RFC 1411

Telnet認証：Kerberosバージョン4

Status of This Memo

このメモのステータス

This memo defines an Experimental Protocol for the Internet community. Discussion and suggestions for improvement are requested. Please refer to the current edition of the "IAB Official Protocol Standards" for the standardization state and status of this protocol. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーのための実験的プロトコル（Experimental Protocol）を定義します。改善のための議論と提案を求めます。このプロトコルの標準化の状態とステータスについては、「IAB Official Protocol Standards」の最新版を参照してください。このメモの配布は無制限です。

サブオプションコマンド

2. Command Meanings

2. コマンドの意味

IAC SB AUTHENTICATION IS <authentication-type-pair> AUTH <kerberos ticket and authenticator> IAC SE
This is used to pass the Kerberos ticket to the remote side of the connection. The first octet of the <authentication-type-pair> value is KERBEROS_V4, to indicate the usage of Kerberos version 4.
IAC SB AUTHENTICATION REPLY <authentication-type-pair> ACCEPT IAC SE
This command indicates that the authentication was successful.
IAC SB AUTHENTICATION REPLY <authentication-type-pair> REJECT <optional reason for rejection> IAC SE
This command indicates that the authentication was not successful, and if there is any more data in the sub-option, it is an ASCII text message of the reason for the rejection.
IAC SB AUTHENTICATION IS <authentication-type-pair> CHALLENGE <encrypted challenge> IAC SE IAC SB AUTHENTICATION REPLY <authentication-type-pair> RESPONSE <encrypted response> IAC SE

These two commands are used to perform mutual authentication. They are only used when the AUTH_HOW_MUTUAL bit is set in the second octet of the authentication-type-pair. After successfully sending an AUTH and receiving an ACCEPT, a CHALLENGE is sent. The challenge is a random 8 byte number with the most significant byte first, and the least significant byte last. When the CHALLENGE command is sent, the "encrypted challenge" is the 8-byte-challenge encrypted in the session key. When the CHALLENGE command is received, the contents are decrypted to get the original 8-byte-challenge, this value is then incremented by one, re-encrypted with the session key, and returned as the "encrypted response" in the RESPONSE command. The receiver of the RESPONSE command decrypts the "encrypted response", and verifies that the resultant value is the original 8-byte-challenge incremented by one.

The "encrypted challenge" value sent/received in the CHALLENGE command is also encrypted with the session key on both sides of the session, to produce a random 8-byte key to be used as the default key for the ENCRYPTION option.

IAC SB AUTHENTICATION IS <authentication-type-pair> AUTH <kerberos ticket and authenticator> IAC SE
これは、Kerberosチケットをコネクションのリモート側に渡すために使います。Kerberosバージョン4を使うことを示すため、<authentication-type-pair>の値の最初のオクテットはKERBEROS_V4です。
IAC SB AUTHENTICATION REPLY <authentication-type-pair> ACCEPT IAC SE
このコマンドは、認証が成功したことを示します。
IAC SB AUTHENTICATION REPLY <authentication-type-pair> REJECT <optional reason for rejection> IAC SE
このコマンドは、認証が成功しなかったことを示します。サブオプションにさらにデータがある場合、それは拒否の理由を示すASCIIテキストのメッセージです。
IAC SB AUTHENTICATION IS <authentication-type-pair> CHALLENGE <encrypted challenge> IAC SE IAC SB AUTHENTICATION REPLY <authentication-type-pair> RESPONSE <encrypted response> IAC SE

これらの2つのコマンドは、相互認証を行うために使います。これらは、authentication-type-pairの2番目のオクテットにAUTH_HOW_MUTUALビットが設定されている場合にだけ使います。AUTHの送信とACCEPTの受信に成功した後、CHALLENGEを送信します。チャレンジは、最上位バイトを先頭に、最下位バイトを末尾に置いた、8バイトのランダムな数値です。CHALLENGEコマンドを送信するとき、「encrypted challenge」は、8バイトのチャレンジをセッション鍵で暗号化したものです。CHALLENGEコマンドを受信すると、その内容を復号して元の8バイトのチャレンジを得て、この値に1を加え、セッション鍵で再び暗号化し、RESPONSEコマンドの「encrypted response」として返します。RESPONSEコマンドの受信者は、「encrypted response」を復号し、得られた値が元の8バイトのチャレンジに1を加えたものであることを検証します。

CHALLENGEコマンドで送受信する「encrypted challenge」の値は、セッションの両側でさらにセッション鍵で暗号化され、ENCRYPTIONオプションのデフォルトの鍵として使うランダムな8バイトの鍵を生成します。

3. Implementation Rules

3. 実装規則

If the second octet of the authentication-type-pair has the AUTH_WHO bit set to AUTH_CLIENT_TO_SERVER, then the client sends the initial AUTH command, and the server responds with either ACCEPT or REJECT. In addition, if the AUTH_HOW bit is set to AUTH_HOW_MUTUAL, and the server responds with ACCEPT, then the client then sends a CHALLENGE, and the server sends a RESPONSE.

authentication-type-pairの2番目のオクテットのAUTH_WHOビットがAUTH_CLIENT_TO_SERVERに設定されている場合、クライアントが最初のAUTHコマンドを送信し、サーバーはACCEPTまたはREJECTのいずれかで応答します。さらに、AUTH_HOWビットがAUTH_HOW_MUTUALに設定されていて、サーバーがACCEPTで応答した場合は、続いてクライアントがCHALLENGEを送信し、サーバーがRESPONSEを送信します。

If the second octet of the authentication-type-pair has the AUTH_WHO bit set to AUTH_SERVER_TO_CLIENT, then the server sends the initial AUTH command, and the client responds with either ACCEPT or REJECT. In addition, if the AUTH_HOW bit is set to AUTH_HOW_MUTUAL, and the client responds with ACCEPT, then the server then sends a CHALLENGE, and the client sends a RESPONSE.

authentication-type-pairの2番目のオクテットのAUTH_WHOビットがAUTH_SERVER_TO_CLIENTに設定されている場合、サーバーが最初のAUTHコマンドを送信し、クライアントはACCEPTまたはREJECTのいずれかで応答します。さらに、AUTH_HOWビットがAUTH_HOW_MUTUALに設定されていて、クライアントがACCEPTで応答した場合は、続いてサーバーがCHALLENGEを送信し、クライアントがRESPONSEを送信します。

The authenticator (Kerberos Principal) used is of the form "rcmd.host@realm".

使用する認証子（Kerberosプリンシパル）は、「rcmd.host@realm」の形式です。

4. Examples

4. 例

User "joe" may wish to log in as user "pete" on machine "foo". If "pete" has set things up on "foo" to allow "joe" access to his account, then the client would send IAC SB AUTHENTICATION NAME "pete" IAC SE IAC SB AUTHENTICATION IS KERBEROS_V4 AUTH <joe's kerberos ticket> IAC SE The server would then authenticate the user as "joe" from the ticket information, and since "pete" is allowing "joe" to use his account, the server would send back ACCEPT. If mutual authentication is being used, the the client would send a CHALLENGE, and verify the RESPONSE that the server sends back.

ユーザー"joe"が、マシン"foo"にユーザー"pete"としてログインしたいとします。"pete"が"foo"上で"joe"に自分のアカウントへのアクセスを許可するよう設定している場合、クライアントはIAC SB AUTHENTICATION NAME "pete" IAC SE IAC SB AUTHENTICATION IS KERBEROS_V4 AUTH <joe's kerberos ticket> IAC SEを送信します。サーバーは次に、チケットの情報からユーザーを"joe"として認証し、"pete"は"joe"に自分のアカウントの使用を許可しているので、ACCEPTを送り返します。相互認証を使用している場合、クライアントはCHALLENGEを送信し、サーバーが送り返すRESPONSEを検証します。

                                        IAC DO AUTHENTICATION
       IAC WILL AUTHENTICATION

       Client                           Server
                                        IAC DO AUTHENTICATION
       IAC WILL AUTHENTICATION

[ The server is now free to request authentication information. ]

[これでサーバーは自由に認証情報を要求できます。]

                                        IAC SB AUTHENTICATION SEND
                                        KERBEROS_V4 CLIENT|MUTUAL
                                        KERBEROS_V4 CLIENT|ONE_WAY IAC
                                        SE

                                        IAC SB AUTHENTICATION SEND
                                        KERBEROS_V4 CLIENT|MUTUAL
                                        KERBEROS_V4 CLIENT|ONE_WAY IAC
                                        SE

[ The server has requested mutual Version 4 Kerberos authentication. If mutual authentication is not supported, then the server is willing to do one-way authentication.

[サーバーは、Kerberosバージョン4による相互認証を要求しました。相互認証がサポートされていない場合、サーバーは一方向の認証を行ってもかまわないと考えています。

The client will now respond with the name of the user that it wants to log in as, and the Kerberos ticket. ]

次にクライアントは、ログインしたいユーザーの名前とKerberosチケットで応答します。]

       IAC SB AUTHENTICATION NAME
       "pete" IAC SE
       IAC SB AUTHENTICATION IS
       KERBEROS_V4 CLIENT|MUTUAL AUTH
       <kerberos ticket information>
       IAC SE

       IAC SB AUTHENTICATION NAME
       "pete" IAC SE
       IAC SB AUTHENTICATION IS
       KERBEROS_V4 CLIENT|MUTUAL AUTH
       <kerberos ticket information>
       IAC SE

[ The server responds with an ACCEPT command to state that the authentication was successful. ]

[サーバーは、認証が成功したことを伝えるためにACCEPTコマンドで応答します。]

                                        IAC SB AUTHENTICATION REPLY
                                        KERBEROS_V4 CLIENT|MUTUAL ACCEPT
                                        IAC SE

                                        IAC SB AUTHENTICATION REPLY
                                        KERBEROS_V4 CLIENT|MUTUAL ACCEPT
                                        IAC SE

[ Next, the client sends across a CHALLENGE to verify that it is really talking to the right server. ]

[次にクライアントは、本当に正しいサーバーと通信していることを検証するために、CHALLENGEを送信します。]

[最後に、サーバーは、本当に正しいサーバーであることを証明するために、RESPONSEを送信します。

Security Considerations

セキュリティーに関する考慮事項

The ability to negotiate a common authentication mechanism between client and server is a feature of the authentication option that should be used with caution. When the negotiation is performed, no authentication has yet occurred. Therefore, each system has no way of knowing whether or not it is talking to the system it intends. An intruder could attempt to negotiate the use of an authentication system which is either weak, or already compromised by the intruder.

クライアントとサーバーの間で共通の認証メカニズムをネゴシエートできることは、認証オプションの機能の1つですが、注意して使うべきものです。ネゴシエーションが行われる時点では、まだ認証は行われていません。そのため、各システムには、意図したシステムと通信しているかどうかを知る手段がありません。侵入者は、弱い認証システムや、すでに侵入者によって破られている認証システムを使うようネゴシエートしようとするかもしれません。
