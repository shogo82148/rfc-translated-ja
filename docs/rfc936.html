RFC 936

Another Internet Subnet Addressing Scheme

RFC 936

もう1つのインターネットサブネットアドレッシング方式

Status of This Memo

このメモのステータス

This RFC suggests a proposed protocol for the ARPA-Internet community, and requests discussion and suggestions for improvements. Distribution of this memo is unlimited.

このRFCは、ARPAインターネットコミュニティーのためのプロトコルを提案し、改善のための議論と提案を求めるものです。このメモの配布は無制限です。

Introduction

はじめに

There have been several proposals for schemes to allow the use of a single Internet network number to refer to a collection of physical networks under common administration which are reachable from the rest of the Internet by a common route. Such schemes allow a simplified view of an otherwise complicated topology from hosts and gateways outside of this collection. They allow the complexity of the number and type of these networks, and routing to them, to be localized. Additions and changes in configuration thus cause no detectable change, and no interruption of service, due to slow propagation of routing and other information outside of the local environment. These schemes also simplify the administration of the network, as changes do not require allocation of new network numbers for each new cable installed. The motivation for explicit or implicit subnets, several of the alternatives, and descriptions of existing implementations of this type have been described in detail [1],[2]. This proposal discusses an alternative scheme, one that has been in use at the University of California, Berkeley since April 1984.

共通の管理下にあり、インターネットの他の部分から共通の経路で到達可能な物理ネットワークの集まりを、単一のインターネットネットワーク番号で参照できるようにする方式について、いくつかの提案がなされてきました。このような方式により、この集まりの外部にあるホストやゲートウェイからは、本来は複雑なトポロジーを単純化して見ることができます。これらのネットワークの数や種類、およびそれらへのルーティングの複雑さを局所化できます。したがって、構成の追加や変更があっても、ローカル環境の外部へのルーティング情報やその他の情報の伝播が遅いことに起因する、検出可能な変化やサービスの中断は生じません。また、これらの方式では、新しいケーブルを敷設するたびに新しいネットワーク番号を割り当てる必要がなくなるので、ネットワークの管理も簡単になります。明示的または暗黙的なサブネットの動機、いくつかの代替案、およびこの種の既存の実装の説明は、[1],[2]で詳しく述べられています。この提案では、1984年4月からカリフォルニア大学バークレー校で使用されている代替方式について議論します。

Subnet Addressing at Berkeley

バークレーにおけるサブネットアドレッシング

As in the proposal by Jeff Mogul in RFC-917, the Berkeley subnet addressing utilizes encoding of the host part of the Internet address. Hosts and gateways on the local network are able to determine the subnet number from each local address, and then route local packets based on the subnet number. Logically, the collection of subnets appears to external sites to be a single, homogenous network. Internally, however, each subnet is distinguished from the others and from other networks, and internal routing decisions are based on the subnet rather than the network number.

RFC-917のJeff Mogulによる提案と同様に、バークレーのサブネットアドレッシングは、インターネットアドレスのホスト部のエンコーディングを利用します。ローカルネットワーク上のホストとゲートウェイは、各ローカルアドレスからサブネット番号を判断し、サブネット番号に基づいてローカルパケットをルーティングできます。論理的には、サブネットの集まりは、外部のサイトからは単一の均質なネットワークに見えます。しかし内部的には、各サブネットは他のサブネットや他のネットワークと区別され、内部のルーティングの決定はネットワーク番号ではなくサブネットに基づいて行われます。

The encoding of subnet addresses is similar to that proposed in RFC-917. In decomposing an Internet address into the network and host parts, the algorithm is modified if the network is "local", that is, if the network is a directly-connected network under local administrative control. (Networks are marked as local or non-local at the time each network interface's address is set at boot time.) For local addresses, the host part is examined for a subnet number. Local addresses may be on the main network, or they may be on a subnet. The high-order bit of the host number is used to distinguish between subnets and the main net. If the high-order bit of the host field is set, then the remainder of the high-order byte of the host part is taken to be the subnet number. If the high-order bit is clear, then the address is interpreted in the normal fashion. For Class A networks, using 8-bit subnet fields, this allows a network with up to 127 subnets, each of 65535 hosts maximum, and a main net with 2^23 hosts. Class B nets may include 127 subnets, each of up to 255 hosts, and 32767 hosts on the main net. Class C networks are not currently included in this scheme. They might be reasonably be added, using four bits of the host part for a subnet desgination and four bits for the host, allowing 8 subnets of 15 hosts and 126 hosts on the main net.

サブネットアドレスのエンコーディングは、RFC-917で提案されているものと似ています。インターネットアドレスをネットワーク部とホスト部に分解する際、ネットワークが「ローカル」である場合、つまりネットワークがローカルの管理下にある直接接続されたネットワークである場合には、アルゴリズムが変更されます。（ネットワークは、ブート時に各ネットワークインターフェイスのアドレスが設定される時点で、ローカルまたは非ローカルとしてマークされます。）ローカルアドレスについては、ホスト部を調べてサブネット番号を探します。ローカルアドレスは、メインネットワーク上にある場合もあれば、サブネット上にある場合もあります。ホスト番号の最上位ビットを使用して、サブネットとメインネットを区別します。ホストフィールドの最上位ビットがセットされている場合、ホスト部の最上位バイトの残りがサブネット番号と見なされます。最上位ビットがクリアされている場合、アドレスは通常の方法で解釈されます。8ビットのサブネットフィールドを使用するクラスAネットワークでは、これにより、それぞれ最大65535ホストのサブネットを最大127個と、2^23ホストのメインネットを持つネットワークが可能になります。クラスBネットは、それぞれ最大255ホストのサブネットを127個と、メインネット上の32767ホストを含むことができます。クラスCネットワークは、現在この方式に含まれていません。ホスト部の4ビットをサブネットの指定に、4ビットをホストに使用して、クラスCネットワークを追加することも十分に考えられます。そうすると、15ホストのサブネットを8個と、メインネット上の126ホストが可能になります。

The current implementation does not use subnet numbers separately from the network field, but instead treats the subnet field as an extension of the network field. Functions that previously returned the network number from an address now return a network or network-subnetwork number. Conveniently, Class A subnets are distinguishable from Class B networks, although each is a 16-bit quantity, and Class B subnets are disjoint with Class C network numbers. The net result is that subnets appear to be separate, independent networks with their own routing entries within the network, but outside of the network, they are invisible. There is no current facility at Berkeley for broadcasting on the logical network; broadcasting may be done on each subnet that uses harware capable of broadcast.

現在の実装では、サブネット番号をネットワークフィールドとは別に使用するのではなく、サブネットフィールドをネットワークフィールドの拡張として扱います。以前はアドレスからネットワーク番号を返していた関数が、現在はネットワーク番号またはネットワーク・サブネットワーク番号を返します。都合のよいことに、クラスAのサブネットとクラスBのネットワークはどちらも16ビットの量ですが区別でき、クラスBのサブネットはクラスCのネットワーク番号と重なりません。結果として、サブネットはネットワーク内部ではそれぞれ独自のルーティングエントリーを持つ別個の独立したネットワークに見えますが、ネットワークの外部からは見えません。バークレーには現在、論理ネットワーク上でブロードキャストする機能はありません。ブロードキャストは、ブロードキャストが可能なハードウェアを使用する各サブネット上で行うことができます。

Discussion

議論

There have been several earlier proposals for methods of allowing several physical networks to share an Internet network designation, and to provide routing within this logical network. RFC-917 proposes a means for encoding the host part of each local address such that the hosts, or the gateways connecting them, are able to determine the physical network for the host. The current proposal is most similar to that scheme; the differences are discussed in detail below.

複数の物理ネットワークが1つのインターネットネットワークの指定を共有し、この論理ネットワーク内でルーティングを提供できるようにする方法について、これまでにいくつかの提案がなされてきました。RFC-917は、ホストまたはそれらを接続するゲートウェイがホストの物理ネットワークを判断できるように、各ローカルアドレスのホスト部をエンコードする手段を提案しています。今回の提案はその方式に最も似ています。相違点は以下で詳しく議論します。

Another proposal (RFC-925) involves the use of intelligent gateways to perform routing for unmodified hosts, using an Address Resolution Protocol (ARP) [2]. This has the advantage of placing all modifications in the gateways, but is likely to require additional routing protocols and caching mechanisms in the gateways in order to avoid excessive broadcasts for address resolution. A modification of this method is to perform encoding of subnets within host addresses by convention to simplify the routing in the gateways, without modifying host software to recognize these subnet addresses. These techniques were not considered for use at Berkeley, because all packet forwarding was being done by multi- homed hosts, all of which ran the same software as the singly-homed hosts (4.2BSD Unix).

別の提案（RFC-925）では、アドレス解決プロトコル（Address Resolution Protocol、ARP）[2]を使用して、変更されていないホストのためにルーティングを行うインテリジェントなゲートウェイを使用します。これには、すべての変更をゲートウェイに集約できるという利点がありますが、アドレス解決のための過剰なブロードキャストを避けるために、ゲートウェイに追加のルーティングプロトコルとキャッシュの仕組みが必要になる可能性が高くなります。この方法の変形として、ホストソフトウェアを変更してサブネットアドレスを認識させることなく、ゲートウェイでのルーティングを簡単にするために、規約によってホストアドレス内にサブネットをエンコードする方法があります。これらの手法は、バークレーでの使用は検討されませんでした。すべてのパケット転送はマルチホームホストによって行われており、そのすべてがシングルホームホストと同じソフトウェア（4.2BSD Unix）を実行していたからです。

The most recent proposal, RFC-932 [3], provides subnetting by encoding the network part of the Internet address rather than the host part. Ordinary hosts need not know of this convention, eliminating the need for modification to host software. Gateways would be able to take advantage of this encoding to compress the routing information for the collection of networks into a single entry. Unfortunately, implementation of that scheme would require a fairly concerted transition by the gateways of the Internet, or the transition period would be likely to overflow the routing tables in the existing gateways. All of the hosts on the larger networks would be forced to change addresses from their current Class A or B addresses to "B 1/2" addresses. There are a limited number (4096) of blocks of Class C addresses available using this encoding. The number of universities and other organizations having already implemented subnets or contemplating their installation argues for a more extensible scheme, as well as one that can be implemented more quickly.

最新の提案であるRFC-932[3]は、インターネットアドレスのホスト部ではなくネットワーク部をエンコードすることでサブネット化を提供します。通常のホストはこの規約を知る必要がないので、ホストソフトウェアを変更する必要がなくなります。ゲートウェイは、このエンコーディングを利用して、ネットワークの集まりに関するルーティング情報を1つのエントリーに圧縮できます。残念ながら、その方式を実装するには、インターネットのゲートウェイによるかなり協調的な移行が必要であり、そうでなければ移行期間中に既存のゲートウェイのルーティングテーブルがあふれる可能性が高くなります。大規模なネットワーク上のすべてのホストは、現在のクラスAまたはBのアドレスから「B 1/2」アドレスへのアドレス変更を強いられます。このエンコーディングを使用して利用できるクラスCアドレスのブロック数は限られています（4096）。すでにサブネットを実装している、あるいは導入を検討している大学やその他の組織の数を考えると、より拡張性があり、かつより迅速に実装できる方式が求められます。

The current proposal is most similar to that of RFC-917; indeed, the two implementations are nearly compatible. There are two differences of significance. First, the use of a bit to distinguish subnetted addresses from non-subnetted addresses allows both smaller subnets and a larger (physical or logical) main network. Half of the host addresses within a Class A or B network are reserved for use in subnets, the other half are available for the primary net. This may useful when using a hardware medium that is capable of supporting large numbers of hosts or for transparent subnetting (e.g. using ARP-based bridges). The corresponding disadvantage is that fewer subnets may be supported. The allocation of bits between the subnet number and the host field could be adjusted, but for Class B networks, neither is excessively large. Given the limited address space of the current Internet addressing, this is a difficult choice.

今回の提案はRFC-917の提案に最も似ています。実際、2つの実装はほぼ互換性があります。重要な相違点が2つあります。第1に、サブネット化されたアドレスとサブネット化されていないアドレスを区別するためにビットを使用することで、より小さなサブネットと、より大きな（物理的または論理的な）メインネットワークの両方が可能になります。クラスAまたはBのネットワーク内のホストアドレスの半分はサブネットでの使用のために予約され、残りの半分はプライマリーネットで利用できます。これは、多数のホストをサポートできるハードウェア媒体を使用する場合や、透過的なサブネット化（たとえば、ARPベースのブリッジを使用する場合）に役立つかもしれません。対応する欠点は、サポートできるサブネットの数が少なくなることです。サブネット番号とホストフィールドの間のビットの割り当ては調整できますが、クラスBネットワークでは、どちらも過剰に大きくはありません。現在のインターネットアドレッシングの限られたアドレス空間を考えると、これは難しい選択です。

The second difference is that the width of the subnet field is fixed in advance. This simplifies the already-too-complicated code to interpret Internet addresses, and avoids the bootstrap problem. If the subnet field width is to be determined dynamically, some fraction of the hosts on a network must be prepared to specify this value, and the situation will be unworkable if one of these hosts does not make the correct choice or none are accessible when other machines come up. Also, the recovery procedure proposed by RFC-917 seems unnecessarily complicated and liable to fail. Dynamic discovery of this value depends on another modification as well, the addition of a new ICMP request. The alternatives are to specify the field size as a standard, or to require each implementation to be configurable in advance (e.g with a system compilation option or the use of a system patch installed when a host is initially installed. The use of a standard field width seems preferable, and an 8-bit field allows the most efficient implementations on most architectures. For Class C nets, a 4-bit field seems the only choice for a standard division.

2つ目の相違点は、サブネットフィールドの幅が事前に固定されていることです。これにより、すでに複雑すぎるインターネットアドレスの解釈コードが単純になり、ブートストラップの問題が回避されます。サブネットフィールドの幅を動的に決定する場合、ネットワーク上のホストの一部がこの値を指定できるように準備しておく必要があり、これらのホストの1つが正しい選択をしなかったり、他のマシンが起動したときにどのホストにもアクセスできなかったりすると、状況は立ち行かなくなります。また、RFC-917で提案されている回復手順は、不必要に複雑で失敗しやすいように思われます。この値の動的な発見は、別の変更、つまり新しいICMP要求の追加にも依存します。代替案は、フィールドサイズを標準として規定するか、各実装を事前に構成可能にすること（たとえば、システムのコンパイルオプションや、ホストの初期インストール時に適用するシステムパッチを使用する）を要求することです。標準のフィールド幅を使用するのが望ましいと思われ、8ビットのフィールドであれば、ほとんどのアーキテクチャーで最も効率的な実装が可能になります。クラスCネットについては、標準の分割として4ビットのフィールドが唯一の選択肢であると思われます。
