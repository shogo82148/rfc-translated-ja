RFC 10005

BGP Link Bandwidth Extended Community

RFC 10005

BGPリンク帯域幅拡張コミュニティー

Abstract

概要

This document defines a BGP extended community, the Link Bandwidth Extended Community, which carries bandwidth information to enable weighted load-balancing in multipath scenarios. It specifies the format and processing rules for this extended community type.

この文書は、マルチパスのシナリオにおいて重み付けされた負荷分散を可能にするために帯域幅の情報を運ぶBGP拡張コミュニティーである、Link Bandwidth拡張コミュニティーを定義します。 この拡張コミュニティーの種類の形式と処理規則を規定します。

1. Introduction

1. はじめに

Load-balancing is a critical aspect of network design, enabling efficient utilization of available bandwidth and improving overall network performance. Traditional equal load-balancing does not account for the varying capacities of different paths. This document suggests that the bandwidth be carried in the network using one of two new extended communities [RFC4360]: the transitive and non-transitive Link Bandwidth Extended Community. The Link Bandwidth Extended Community carries the bandwidth information of a directly connected link or multi-hop/multipath next hop as advertised by a router. This mechanism facilitates maximizing utilization of network resources.

負荷分散はネットワーク設計の重要な側面であり、利用可能な帯域幅の効率的な活用とネットワーク全体のパフォーマンスの向上を可能にします。 従来の均等な負荷分散では、異なる経路のさまざまな容量が考慮されません。 この文書は、2つの新しい拡張コミュニティー[RFC4360]、すなわち推移的なLink Bandwidth拡張コミュニティーと非推移的なLink Bandwidth拡張コミュニティーのいずれかを使用して、ネットワーク内で帯域幅を運ぶことを提案します。 Link Bandwidth拡張コミュニティーは、ルーターによって広告される、直接接続されたリンクまたはマルチホップ/マルチパスのネクストホップの帯域幅の情報を運びます。 このメカニズムにより、ネットワークリソースの利用率の最大化が容易になります。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

2. Link Bandwidth Extended Community

2. Link Bandwidth拡張コミュニティー

The Link Bandwidth Extended Community is defined as a BGP extended community that carries the bandwidth information of a router (represented by BGP next hop) that is connecting to a remote network. This community can be used to inform other routers about the available bandwidth through a given route.

Link Bandwidth拡張コミュニティーは、リモートネットワークに接続している（BGPネクストホップで表される）ルーターの帯域幅の情報を運ぶBGP拡張コミュニティーとして定義されます。 このコミュニティーは、特定の経路を通じて利用可能な帯域幅について他のルーターに知らせるために使用できます。

The Link Bandwidth Extended Community can be either transitive or non-transitive. Therefore, the value of the high-order octet of the extended Type field can be 0x00 or 0x40, respectively. The value of the low-order octet of the extended Type field for this community is 0x04.

Link Bandwidth拡張コミュニティーは、推移的または非推移的のいずれかにできます。 したがって、拡張Typeフィールドの上位オクテットの値は、それぞれ0x00または0x40になりえます。 このコミュニティーの拡張Typeフィールドの下位オクテットの値は0x04です。

The Global Administrator sub-field in the Value field SHOULD be set to the Autonomous System Number (ASN) of the router attaching the Link Bandwidth Extended Community, but it MAY contain any 2-octet value. If the ASN cannot be represented in 2 octets, AS_TRANS [RFC6793] SHOULD be used in the Global Administrator sub-field. The encoding of the full 4-octet ASNs is not supported by the Link Bandwidth Extended Community. Such a capability, should the operational need for it arise, may be provided by a new BGP extension. The value in the Global Administrator sub-field does not affect the use or semantics of the Link Bandwidth Extended Community. This approach maintains consistency with 2-octet community registries and remains operationally familiar.

ValueフィールドのGlobal Administratorサブフィールドは、Link Bandwidth拡張コミュニティーを付加するルーターの自律システム番号（ASN）に設定すべきです（SHOULD）が、任意の2オクテットの値を含めてもよいです（MAY）。 ASNを2オクテットで表現できない場合は、Global AdministratorサブフィールドにAS_TRANS[RFC6793]を使用すべきです（SHOULD）。 完全な4オクテットのASNのエンコーディングは、Link Bandwidth拡張コミュニティーではサポートされていません。 そのような機能は、運用上の必要性が生じた場合には、新しいBGP拡張によって提供される可能性があります。 Global Administratorサブフィールドの値は、Link Bandwidth拡張コミュニティーの使用やセマンティクスには影響しません。 このアプローチは、2オクテットのコミュニティーのレジストリーとの一貫性を維持し、運用上なじみのあるものであり続けます。

The bandwidth value is expressed as 4 octets in the floating point format of [IEEE.754-2019], with units being bytes (not bits!) per second. It is carried in the Local Administrator sub-field of the Value field.

帯域幅の値は、[IEEE.754-2019]の浮動小数点形式で4オクテットとして表され、単位は1秒あたりのバイト（ビットではありません！）です。 これはValueフィールドのLocal Administratorサブフィールドで運ばれます。

Type:
A 1-octet field that MUST be set to 0x00 or 0x40 to indicate transitive/non-transitive.
SubType:
A 1-octet field that MUST be set to 0x04 to indicate "link-bandwidth".
Global Administrator sub-field:
A 2-octet field that represents an operator-assigned 2-octet value. For example, this can be a 16-bit ASN.
Local Administrator sub-field:
Bandwidth value (bytes per second) encoded as 4 octets in the 32-bit floating point format of [IEEE.754-2019].
Type：
推移的/非推移的を示すために、0x00または0x40に設定しなければなりません（MUST）1オクテットのフィールド。
SubType：
「link-bandwidth」を示すために、0x04に設定しなければなりません（MUST）1オクテットのフィールド。
Global Administratorサブフィールド：
運用者が割り当てる2オクテットの値を表す2オクテットのフィールド。 たとえば、16ビットのASNにできます。
Local Administratorサブフィールド：
[IEEE.754-2019]の32ビット浮動小数点形式で4オクテットとしてエンコードされた帯域幅の値（1秒あたりのバイト数）。

3. Protocol Procedures

3. プロトコルの手順

The procedures cover both the transitive and non-transitive variants of the Link Bandwidth Extended Community so that implementations can handle both variants, ensuring that implementations can interoperate correctly across all deployments. Please refer to Section 5 and Appendix A for more details.

この手順は、実装が両方の変種を扱えるように、Link Bandwidth拡張コミュニティーの推移的な変種と非推移的な変種の両方を対象としており、すべての展開において実装が正しく相互運用できることを保証します。 詳しくはSection 5とAppendix Aを参照してください。

3.1. Sender (Originating Link Bandwidth Extended Community)

3.1. 送信者（Link Bandwidth拡張コミュニティーの生成）

A BGP speaker that attaches a Link Bandwidth Extended Community SHOULD be able to advertise either a transitive or a non-transitive Link Bandwidth Extended Community. Implementations SHOULD provide the configuration to set the transitivity type of the Link Bandwidth Extended Community, as well as the Global Administrator and bandwidth values in the Local Administrator sub-field, by using local policy. Different implementations MAY use different default values for the transitivity type of the Link Bandwidth Extended Community. The provided configuration SHOULD allow operators to override the default transitivity value as needed. Likewise, implementations SHOULD expose their default value.

Link Bandwidth拡張コミュニティーを付加するBGPスピーカーは、推移的または非推移的のいずれかのLink Bandwidth拡張コミュニティーを広告できるべきです（SHOULD）。 実装は、ローカルポリシーを使用して、Link Bandwidth拡張コミュニティーの推移性の種類と、Global AdministratorおよびLocal Administratorサブフィールドの帯域幅の値を設定するための設定を提供すべきです（SHOULD）。 異なる実装は、Link Bandwidth拡張コミュニティーの推移性の種類に異なるデフォルト値を使用してもよいです（MAY）。 提供される設定は、運用者が必要に応じてデフォルトの推移性の値を上書きできるようにすべきです（SHOULD）。 同様に、実装は自身のデフォルト値を公開すべきです（SHOULD）。

An implementation MAY advertise bandwidth value as zero. An operator may, for example, set the Link Bandwidth Extended Community to zero to indicate that the path should not attract traffic during maintenance. However, as per Section 3.2, it is up to the local policy of the receiver to decide how a link-bandwidth value of zero is handled.

実装は、帯域幅の値を0として広告してもよいです（MAY）。 たとえば、運用者は、メンテナンス中にその経路がトラフィックを引き寄せるべきではないことを示すために、Link Bandwidth拡張コミュニティーを0に設定することがあります。 ただし、Section 3.2のとおり、0のリンク帯域幅の値をどのように扱うかを決定するのは受信者のローカルポリシーです。

Generally, a single Link Bandwidth Extended Community of the transitivity type desired in a deployment is attached to a route. However, during transition (refer Section 7 for details), a BGP speaker MAY attach one Link Bandwidth Extended Community per transitivity (transitive/non-transitive); the bandwidth value included in both communities SHOULD be the same.

一般に、展開で望まれる推移性の種類の単一のLink Bandwidth拡張コミュニティーが経路に付加されます。 ただし、移行中（詳細はSection 7を参照）は、BGPスピーカーは推移性（推移的/非推移的）ごとに1つのLink Bandwidth拡張コミュニティーを付加してもよいです（MAY）。両方のコミュニティーに含まれる帯域幅の値は同じであるべきです（SHOULD）。

A Link Bandwidth Extended Community MAY be attached or updated for a BGP route upon receipt during Adj-RIB-In processing. The Link Bandwidth Extended Community MAY be attached or updated for a BGP route's Adj-RIB-Out entry while being advertised to a neighboring BGP speaker. (Adj-RIB-In and Adj-RIB-Out are as defined in [RFC4271].)

Link Bandwidth拡張コミュニティーは、Adj-RIB-Inの処理中に、受信時にBGP経路に付加または更新してもよいです（MAY）。 Link Bandwidth拡張コミュニティーは、隣接するBGPスピーカーに広告される際に、BGP経路のAdj-RIB-Outエントリーに付加または更新してもよいです（MAY）。 （Adj-RIB-InとAdj-RIB-Outは[RFC4271]で定義されているとおりです。）

Implementations MAY provide a configuration option to send non-transitive Link Bandwidth Extended Communities on external BGP sessions.

実装は、外部BGPセッションで非推移的なLink Bandwidth拡張コミュニティーを送信するための設定オプションを提供してもよいです（MAY）。

3.2. Receiver (Receiving Link Bandwidth Extended Community)

3.2. 受信者（Link Bandwidth拡張コミュニティーの受信）

A BGP receiver that supports the Link Bandwidth Extended Community MUST support processing of both the transitive and non-transitive types. The receiver MUST NOT flap or treat the route as malformed based on the transitivity of the Link Bandwidth Extended Community and/or BGP session type (internal versus external).

Link Bandwidth拡張コミュニティーをサポートするBGP受信者は、推移的と非推移的の両方の種類の処理をサポートしなければなりません（MUST）。 受信者は、Link Bandwidth拡張コミュニティーの推移性やBGPセッションの種類（内部か外部か）に基づいて、経路をフラップさせたり、不正な形式として扱ったりしてはなりません（MUST NOT）。

Implementations MAY provide configuration to accept non-transitive Link Bandwidth Extended Communities from external BGP sessions.

実装は、外部BGPセッションからの非推移的なLink Bandwidth拡張コミュニティーを受け入れるための設定を提供してもよいです（MAY）。

A BGP update with an attached Link Bandwidth Extended Community with a bandwidth value of zero is valid. When all contributing paths have a non-zero value in the Link Bandwidth Extended Community, the bandwidth values of those paths (or their ratio) can be utilized as weights to enable weighted load-balancing. Details of weighted load-balancing are outside the scope of this document. Refer to [LINK-BW-USE-CASES], which describes some of the weighted load-balancing aspects. However, in the case where the paths have a mix of zero and non-zero values, or all zero values, the behavior is determined by local policy. For example, implementations may exclude the paths with a zero value from weighted load-balancing formation as long as at least one path with a non-zero value exists, or they may fall back to equal load-balancing. The bandwidth value, however, SHOULD NOT be used as an input to the BGP best path selection process.

帯域幅の値が0であるLink Bandwidth拡張コミュニティーが付加されたBGP更新は有効です。 寄与するすべての経路のLink Bandwidth拡張コミュニティーの値が0でない場合、それらの経路の帯域幅の値（またはその比率）を重みとして利用して、重み付けされた負荷分散を可能にできます。 重み付けされた負荷分散の詳細はこの文書の範囲外です。 重み付けされた負荷分散のいくつかの側面を説明している[LINK-BW-USE-CASES]を参照してください。 ただし、経路の値に0と0以外が混在している場合や、すべて0である場合、動作はローカルポリシーによって決定されます。 たとえば、実装は、0以外の値を持つ経路が少なくとも1つ存在する限り、値が0の経路を重み付けされた負荷分散の構成から除外することもあれば、均等な負荷分散にフォールバックすることもあります。 ただし、帯域幅の値は、BGPの最適経路選択プロセスへの入力として使用すべきではありません（SHOULD NOT）。

Between transitive and non-transitive types of Link Bandwidth Extended Communities that have the same bandwidth value, the transitivity does not matter for the purpose of computing weighted load-balancing or programming to the Forwarding Information Base (FIB).

同じ帯域幅の値を持つ推移的なLink Bandwidth拡張コミュニティーと非推移的なLink Bandwidth拡張コミュニティーの間では、重み付けされた負荷分散の計算や転送情報ベース（FIB）へのプログラミングの目的において、推移性は問題になりません。

3.3. Re-Advertisement Procedures

3.3. 再広告の手順

This section describes the procedures to be followed when a BGP speaker receives a route with an attached Link Bandwidth Extended Community and subsequently re-advertises that route.

このセクションでは、BGPスピーカーがLink Bandwidth拡張コミュニティーが付加された経路を受信し、その後その経路を再広告する場合に従うべき手順について説明します。

3.3.1. Re-Advertisement with Next Hop Change

3.3.1. ネクストホップを変更する再広告

When a BGP speaker re-advertises a route received with a Link Bandwidth Extended Community and sets the next hop to itself or to another address, it MAY do any one of the following as its default behavior: remove the Link Bandwidth Extended Community, re-advertise it unchanged, or regenerate it with an updated value. Implementations SHOULD provide a local configuration method to alter their default behavior to the other options with per-session granularity. Likewise, implementations SHOULD expose their default value.

BGPスピーカーが、Link Bandwidth拡張コミュニティー付きで受信した経路を再広告し、ネクストホップを自身または別のアドレスに設定する場合、デフォルトの動作として、Link Bandwidth拡張コミュニティーを削除する、変更せずに再広告する、または更新した値で再生成する、のいずれかを行ってもよいです（MAY）。 実装は、セッション単位の粒度で、デフォルトの動作を他の選択肢に変更するためのローカルな設定方法を提供すべきです（SHOULD）。 同様に、実装は自身のデフォルト値を公開すべきです（SHOULD）。

When regenerating the Link Bandwidth Extended Community, the same procedures as outlined in Section 3.1 apply. Please also refer to Section 3.4 for use in a BGP multipath environment.

Link Bandwidth拡張コミュニティーを再生成する場合は、Section 3.1で概説したものと同じ手順が適用されます。 BGPマルチパス環境での使用についてはSection 3.4も参照してください。

3.3.2. Re-Advertisement with Next Hop Unchanged

3.3.2. ネクストホップを変更しない再広告

A BGP speaker that receives a route with a Link Bandwidth Extended Community and re-advertises or reflects the same without changing its next hop SHOULD NOT change the Link Bandwidth Extended Community in any way.

Link Bandwidth拡張コミュニティー付きの経路を受信し、ネクストホップを変更せずにそれを再広告またはリフレクトするBGPスピーカーは、Link Bandwidth拡張コミュニティーをいかなる方法でも変更すべきではありません（SHOULD NOT）。

3.4. Link Bandwidth Extended Community Arithmetic and BGP Multipath

3.4. Link Bandwidth拡張コミュニティーの演算とBGPマルチパス

In a BGP multipath environment, the bandwidth value that is sent or re-advertised MAY be calculated based on the Link Bandwidth Extended Community associated with each constituent path contributing to multipath in the Local Routing Information Base (Local-RIB). This topic is beyond the scope of this document. Refer to [LINK-BW-USE-CASES], which describes how this could be done in specific scenarios.

BGPマルチパス環境では、送信または再広告される帯域幅の値を、ローカルルーティング情報ベース（Local-RIB）でマルチパスに寄与する各構成経路に関連付けられたLink Bandwidth拡張コミュニティーに基づいて計算してもよいです（MAY）。 このトピックはこの文書の範囲外です。 特定のシナリオでこれをどのように行えるかを説明している[LINK-BW-USE-CASES]を参照してください。

4. Error Handling

4. エラー処理

If a BGP speaker receives a route with more than one Link Bandwidth Extended Community and uses the route to compute weighted load-balancing, it SHOULD use the extended community with the lowest bandwidth value (including zero), ignoring the transitivity. Implementations MAY provide configuration to change the above preference.

BGPスピーカーが複数のLink Bandwidth拡張コミュニティーを持つ経路を受信し、その経路を使用して重み付けされた負荷分散を計算する場合、推移性を無視して、帯域幅の値が最も小さい（0を含む）拡張コミュニティーを使用すべきです（SHOULD）。 実装は、上記の優先順位を変更するための設定を提供してもよいです（MAY）。

A negative value in a Link Bandwidth Extended Community SHOULD NOT be attached or originated by any BGP speaker. If a BGP receiver encounters a Link Bandwidth Extended Community that contains a negative link-bandwidth value, the Link Bandwidth Extended Community SHALL be ignored.

負の値を持つLink Bandwidth拡張コミュニティーは、いかなるBGPスピーカーによっても付加または生成されるべきではありません（SHOULD NOT）。 BGP受信者が負のリンク帯域幅の値を含むLink Bandwidth拡張コミュニティーに遭遇した場合、そのLink Bandwidth拡張コミュニティーは無視することになります（SHALL）。

Link Bandwidth Extended Communities with a zero value MUST NOT be considered malformed.

値が0であるLink Bandwidth拡張コミュニティーを不正な形式とみなしてはなりません（MUST NOT）。

If any of the paths lack a valid Link Bandwidth Extended Community, equal load-balancing SHOULD be used unless overridden by local configuration.

いずれかの経路に有効なLink Bandwidth拡張コミュニティーがない場合、ローカルの設定で上書きされない限り、均等な負荷分散を使用すべきです（SHOULD）。

6. Security Considerations

6. セキュリティーに関する考慮事項

This extension to BGP has similar security implications as BGP extended communities [RFC4360].

このBGPの拡張には、BGP拡張コミュニティー[RFC4360]と同様のセキュリティー上の影響があります。

The Link Bandwidth Extended Community conveys bandwidth and capacity information that may be sensitive. Exporting this community outside of an administrative domain can expose private network resource details. When propagating the routes with a Link Bandwidth Extended Community towards an untrusted network or outside of an administrative domain, it is recommended operators use policy to filter out this community.

Link Bandwidth拡張コミュニティーは、機密性のある可能性がある帯域幅と容量の情報を伝えます。 このコミュニティーを管理ドメインの外にエクスポートすると、プライベートなネットワークリソースの詳細が露出する可能性があります。 Link Bandwidth拡張コミュニティー付きの経路を信頼できないネットワークに向けて、または管理ドメインの外に伝播させる場合、運用者はポリシーを使用してこのコミュニティーをフィルタリングすることが推奨されます。

7. Operational Considerations

7. 運用上の考慮事項

7.1. Inconsistent Deployment

7.1. 一貫性のない展開

Prior deployments of the feature specified in this document have involved implementations that only understood one of the two extended community transitivity types. As a result, such implementations would ignore the other transitivity type that they don't understand. The procedures in this document govern how multiple transitivity types for bandwidth should operate.

この文書で規定する機能のこれまでの展開には、2つの拡張コミュニティーの推移性の種類のうち一方しか理解しない実装が含まれていました。 その結果、そのような実装は、理解しないもう一方の推移性の種類を無視していました。 この文書の手順は、帯域幅に関する複数の推移性の種類がどのように動作すべきかを規定します。

Inconsistent behavior could occur when networks have deployed a mixture of implementations supporting this document's procedures for both transitivity types, or have deployed older implementations that only understand one transitivity type. A prime example is when a route received by a BGP speaker contains both a transitive and a non-transitive Link Bandwidth Extended Community, and that BGP speaker performs an operation that updates only one of the Link Bandwidth Extended Communities, so then the other community may have an inconsistent value. As a result, downstream BGP speakers that may receive such routes may perform inappropriate weighted load-balancing.

ネットワークに、両方の推移性の種類についてこの文書の手順をサポートする実装が混在して展開されている場合や、一方の推移性の種類しか理解しない古い実装が展開されている場合、一貫性のない動作が発生する可能性があります。 その典型的な例は、BGPスピーカーが受信した経路に推移的と非推移的の両方のLink Bandwidth拡張コミュニティーが含まれており、そのBGPスピーカーが一方のLink Bandwidth拡張コミュニティーのみを更新する操作を実行し、その結果もう一方のコミュニティーが一貫性のない値を持つ可能性がある場合です。 その結果、そのような経路を受信する可能性のある下流のBGPスピーカーが、不適切な重み付けされた負荷分散を実行する可能性があります。

To mitigate such issues, when operators are aware that older implementations are present in their networks, they may wish to take actions to address such inconsistencies. One option would be to filter the unsupported transitivity type of the Link Bandwidth Extended Community at advertisement time on the older BGP speaker, if the implementation is capable of such filtering. Alternatively, a receiving BGP speaker, knowing that the sending speaker is incapable of doing such operations, could strip the Link Bandwidth Extended Community type that is unsupported by the sender.

このような問題を緩和するために、運用者は、ネットワーク内に古い実装が存在することを認識している場合、そのような不整合に対処するための措置を講じたいと考えるかもしれません。 1つの選択肢は、実装がそのようなフィルタリングに対応している場合、古いBGPスピーカーにおいて、広告時にLink Bandwidth拡張コミュニティーのサポートされていない推移性の種類をフィルタリングすることです。 あるいは、送信側のスピーカーがそのような操作を行えないことを知っている受信側のBGPスピーカーが、送信者によってサポートされていないLink Bandwidth拡張コミュニティーの種類を取り除くこともできます。

Ideally, this operational consideration is short lived until all the routers in the network have been upgraded to implementations that consistently support the procedures in this document.

理想的には、この運用上の考慮事項は、ネットワーク内のすべてのルーターがこの文書の手順を一貫してサポートする実装にアップグレードされるまでの短期間のものです。

7.2. Bandwidth Value

7.2. 帯域幅の値

How the bandwidth value is computed or determined is out of scope of this document. Refer to [LINK-BW-USE-CASES], which describes how this could be done in specific scenarios. It is recommended that implementations provide mechanisms to limit the churn caused by frequently changing bandwidth values, because rapid fluctuations could impact protocol stability and network operations.

帯域幅の値をどのように計算または決定するかは、この文書の範囲外です。 特定のシナリオでこれをどのように行えるかを説明している[LINK-BW-USE-CASES]を参照してください。 急激な変動はプロトコルの安定性とネットワークの運用に影響を与える可能性があるため、実装は、頻繁に変化する帯域幅の値によって引き起こされる変動を制限するメカニズムを提供することが推奨されます。

Appendix A. Document History

Appendix A. 文書の履歴

The BGP Link Bandwidth Extended Community has evolved over several versions of the IETF draft. In the earlier versions up to draft-ietf-idr-link-bandwidth-08, only the non-transitive version of the Link Bandwidth Extended Community was supported. However, starting from draft-ietf-idr-link-bandwidth-09, both transitive and non-transitive versions of the Link Bandwidth Extended Community are supported.

BGP Link Bandwidth拡張コミュニティーは、IETFドラフトのいくつかのバージョンを経て発展してきました。 draft-ietf-idr-link-bandwidth-08までの初期のバージョンでは、Link Bandwidth拡張コミュニティーの非推移的なバージョンのみがサポートされていました。 しかし、draft-ietf-idr-link-bandwidth-09からは、Link Bandwidth拡張コミュニティーの推移的なバージョンと非推移的なバージョンの両方がサポートされています。

A BGP speaker (sender or receiver) needs to be upgraded to support the procedures defined in this document to provide full interoperability for both transitive and non-transitive versions of the Link Bandwidth Extended Community. In order to simplify implementations, it is not a goal to provide interoperability by upgrading only the Route Reflector (RR).

Link Bandwidth拡張コミュニティーの推移的なバージョンと非推移的なバージョンの両方について完全な相互運用性を提供するには、BGPスピーカー（送信者または受信者）をアップグレードして、この文書で定義されている手順をサポートする必要があります。 実装を簡素化するために、ルートリフレクター（RR）のみをアップグレードすることで相互運用性を提供することは目標としていません。
