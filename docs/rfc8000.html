RFC 8000

Requirements for NFSv4 Multi-Domain Namespace Deployment

RFC 8000

NFSv4マルチドメイン名前空間のデプロイに対する要件

Abstract

概要

This document presents requirements for the deployment of the NFSv4 protocols for the construction of an NFSv4 file namespace in environments with multiple NFSv4 Domains. To participate in an NFSv4 multi-domain file namespace, the server must offer a multi-domain- capable file system and support RPCSEC_GSS for user authentication. In most instances, the server must also support identity-mapping services.

この文書は、複数のNFSv4ドメインが存在する環境でNFSv4ファイル名前空間を構築するための、NFSv4プロトコルのデプロイに対する要件を示します。 NFSv4マルチドメインファイル名前空間に参加するには、サーバーはマルチドメイン対応のファイルシステムを提供し、ユーザー認証のためにRPCSEC_GSSをサポートしなければなりません。 ほとんどの場合、サーバーはアイデンティティーマッピングサービスもサポートしなければなりません。

1. Introduction

1. はじめに

The NFSv4 protocols NFSv4.0 [RFC7530], NFSv4.1 [RFC5661], and NFSv4.2 [RFC7862] introduce the concept of an NFS Domain. An NFSv4 Domain is defined as a set of users and groups using the NFSv4 name@domain user and group identification syntax with the same specified @domain.

NFSv4プロトコルであるNFSv4.0 [RFC7530]、NFSv4.1 [RFC5661]、およびNFSv4.2 [RFC7862]は、NFSドメインの概念を導入しました。 NFSv4ドメインは、NFSv4のname@domain形式のユーザーおよびグループ識別構文で、同じ@domainを指定して使用するユーザーとグループの集合として定義されます。

Previous versions of the NFS protocol, such as NFSv3 [RFC1813], use the UNIX-centric user identification mechanism of numeric user and group ID for the uid3 and gid3 [RFC1813] file attributes and for identity in the authsys_parms AUTH_SYS credential defined in the Open Network Computing (ONC) Remote Procedure Call (RPC) protocol [RFC5531]. Section 6.1 of [RFC2624] notes that the use of UNIX- centric numeric IDs limits the scale of NFS to large local work groups. UNIX-centric numeric IDs are not unique across NFSv3 deployments and so are not designed for Internet scaling achieved by taking into account multiple naming domains and multiple naming mechanisms (see Section 6.2). The NFSv4 Domain's use of the name@domain syntax provides this Internet scaling by allowing servers and clients to translate between the external name@domain string representation to a local or internal numeric (or other identifier) representation, which matches internal implementation needs.

NFSv3 [RFC1813]など、以前のバージョンのNFSプロトコルは、uid3およびgid3 [RFC1813]ファイル属性、およびオープンネットワークコンピューティング（ONC）リモートプロシージャコール（RPC）プロトコル [RFC5531]で定義されるauthsys_parms AUTH_SYSクレデンシャル内のアイデンティティーに、数値のユーザーIDとグループIDというUNIX中心のユーザー識別メカニズムを使用していました。 [RFC2624]のセクション6.1は、UNIX中心の数値IDを使用すると、NFSの規模が大規模なローカルワークグループに制限されると指摘しています。 UNIX中心の数値IDはNFSv3のデプロイ間で一意ではないため、複数のネーミングドメインと複数のネーミングメカニズムを考慮することで実現されるインターネット規模への拡張を想定して設計されていません（セクション6.2を参照）。 NFSv4ドメインでのname@domain構文の使用は、サーバーとクライアントが、外部のname@domain文字列表現と、内部実装のニーズに合ったローカルまたは内部の数値（または他の識別子）表現との間で変換できるようにすることで、このインターネット規模への拡張を実現します。

Multi-domain deployments require support for unique identities across the deployment's name services and security services, as well as the use of multi-domain file systems capable of the on-disk representation of identities belonging to multiple NFSv4 Domains. The name@domain syntax can provide unique identities and thus enables the NFSv4 multi-domain file namespace.

マルチドメインのデプロイには、デプロイ内のネームサービスとセキュリティーサービス全体で一意なアイデンティティーをサポートすることに加え、複数のNFSv4ドメインに属するアイデンティティーをディスク上で表現できるマルチドメインファイルシステムの使用が必要です。 name@domain構文は一意なアイデンティティーを提供できるため、NFSv4マルチドメインファイル名前空間を可能にします。

Unlike previous versions of NFS, the NFSv4 protocols define a referral mechanism (Section 8.4.3 of [RFC7530]) that allows a single server or a set of servers to present a multi-server namespace that encompasses file systems located on multiple servers. This enables the establishment of site-wide, organization-wide, or even a truly global file namespace.

以前のバージョンのNFSとは異なり、NFSv4プロトコルは、単一のサーバーまたはサーバーの集合が、複数のサーバー上にあるファイルシステムを包含するマルチサーバー名前空間を提示できるようにするリファーラルメカニズム（[RFC7530]のセクション8.4.3）を定義しています。 これにより、サイト全体、組織全体、さらには真にグローバルなファイル名前空間を確立できます。

The NFSv4 protocols' name@domain syntax and referral mechanism along with the use of RPCSEC_GSS security mechanisms enables the construction of an NFSv4 multi-domain file namespace.

NFSv4プロトコルのname@domain構文とリファーラルメカニズムに、RPCSEC_GSSセキュリティーメカニズムの使用を組み合わせることで、NFSv4マルチドメインファイル名前空間を構築できます。

This document presents requirements on the deployment of the NFSv4 protocols for the construction of an NFSv4 file namespace in environments with multiple NFSv4 Domains. To participate in an NFSv4 multi-domain file namespace, the server must offer a multi-domain- capable file system and support RPCSEC_GSS [RFC2203] for user authentication. In most instances, the server must also support identity-mapping services.

この文書は、複数のNFSv4ドメインが存在する環境でNFSv4ファイル名前空間を構築するための、NFSv4プロトコルのデプロイに対する要件を示します。 NFSv4マルチドメインファイル名前空間に参加するには、サーバーはマルチドメイン対応のファイルシステムを提供し、ユーザー認証のためにRPCSEC_GSS [RFC2203]をサポートしなければなりません。 ほとんどの場合、サーバーはアイデンティティーマッピングサービスもサポートしなければなりません。

2. Terminology

2. 用語

NFSv4 Domain:
A set of users and groups using the NFSv4 name@domain user and group identification syntax with the same specified @domain.
Stand-alone NFSv4 Domain:
A deployment of the NFSv4 protocols and NFSv4 file namespace in an environment with a single NFSv4 Domain.
Local representation of identity:
A representation of a user or a group of users capable of being stored persistently within a file system. Typically, such representations are identical to the form in which users and groups are represented within internal server APIs. Examples are numeric IDs such as a uidNumber (UID), gidNumber (GID) [RFC2307], or a Windows Security Identifier (SID) [CIFS]. In some cases, the identifier space for user and groups overlap, requiring anyone using such an ID to know a priori whether the identifier is for a user or a group.
Unique identity:
An on-the-wire form of identity that is unique across an NFSv4 multi-domain namespace that can be mapped to a local representation. For example, the NFSv4 name@domain or the Kerberos principal [RFC4120].
Multi-domain:
In this document, the term "multi-domain" always refers to multiple NFSv4 Domains.
Multi-domain-capable file system:
A local file system that uses a local ID form that can represent NFSv4 identities from multiple domains.
Principal:
An RPCSEC_GSS [RFC2203] authentication identity. It is usually, but not always, a user; rarely, if ever, a group; and sometimes a host or server.
Authorization Context:
A collection of information about a principal such as user name, userID, group membership, etc., used in authorization decisions.
Stringified UID or GID:
NFSv4 owner and group strings that consist of decimal numeric values with no leading zeros and that do not contain an '@' sign. See Section 5.9 of [RFC5661].
Name Service:
Facilities that provide the mapping between {NFSv4 Domain, group, or user name} and the appropriate local representation of identity. Also includes facilities providing mapping between a security principal and local representation of identity. Can be applied to unique identities or principals from within local and remote domains. Often provided by a Directory Service such as the Lightweight Directory Access Protocol (LDAP) [RFC4511].
Name Service Switch (nsswitch):
A facility that provides a variety of sources for common configuration databases and name resolution mechanisms.
FedFS:
The Federated File System (FedFS) [RFC5716] describes the requirements and administrative tools to construct a uniform NFSv4 file-server-based namespace that is capable of spanning a whole enterprise and that is easy to manage.
Domain:

This term is used in multiple contexts where it has different meanings. "NFSv4 Domain" and "multi-domain" are defined above.

DNS domain:
A set of computers, services, or any Internet resource identified by a DNS domain name [RFC1034].
Security realm or domain:
A set of configured security providers, users, groups, security roles, and security policies running a single security protocol and administered by a single entity, for example, a Kerberos realm.
FedFS domain:
A file namespace that can cross multiple shares on multiple file servers using file-access protocols such as NFSv4. A FedFS domain is typically a single administrative entity and has a name that is similar to a DNS domain name. Also known as a "Federation".
Administrative domain:
A set of users, groups, computers, and services administered by a single entity. Can include multiple DNS domains, NFSv4 Domains, security domains, and FedFS domains.
NFSv4ドメイン（NFSv4 Domain）:
NFSv4のname@domain形式のユーザーおよびグループ識別構文で、同じ@domainを指定して使用するユーザーとグループの集合です。
スタンドアロンNFSv4ドメイン（Stand-alone NFSv4 Domain）:
単一のNFSv4ドメインを持つ環境における、NFSv4プロトコルとNFSv4ファイル名前空間のデプロイです。
アイデンティティーのローカル表現（Local representation of identity）:
ファイルシステム内に永続的に保存できる、ユーザーまたはユーザーのグループの表現です。 通常、このような表現は、サーバー内部のAPIでユーザーとグループが表現される形式と同一です。 例として、uidNumber（UID）、gidNumber（GID）[RFC2307]などの数値ID、またはWindowsセキュリティー識別子（SID） [CIFS]があります。 場合によっては、ユーザーとグループの識別子空間が重複しており、そのようなIDを使用する者は、その識別子がユーザーのものかグループのものかを事前に知っている必要があります。
一意なアイデンティティー（Unique identity）:
NFSv4マルチドメイン名前空間全体で一意であり、ローカル表現にマッピングできる、ネットワーク上のアイデンティティーの形式です。 例として、NFSv4のname@domain、またはKerberosプリンシパル[RFC4120]があります。
マルチドメイン（Multi-domain）:
この文書では、「マルチドメイン」という用語は常に複数のNFSv4ドメインを指します。
マルチドメイン対応ファイルシステム（Multi-domain-capable file system）:
複数のドメインのNFSv4アイデンティティーを表現できるローカルID形式を使用する、ローカルファイルシステムです。
プリンシパル（Principal）:
RPCSEC_GSS [RFC2203]の認証アイデンティティーです。 通常はユーザーですが、常にそうとは限りません。グループであることはまれで、ホストやサーバーであることもあります。
認可コンテキスト（Authorization Context）:
認可の判断に使用される、ユーザー名、ユーザーID、グループメンバーシップなど、プリンシパルに関する情報の集まりです。
文字列化されたUIDまたはGID（Stringified UID or GID）:
先頭にゼロのない10進数の数値で構成され、「@」記号を含まない、NFSv4のオーナー文字列およびグループ文字列です。 [RFC5661]のセクション5.9を参照してください。
ネームサービス（Name Service）:
{NFSv4ドメイン、グループ名、またはユーザー名}と、適切なアイデンティティーのローカル表現との間のマッピングを提供する機能です。 セキュリティープリンシパルとアイデンティティーのローカル表現との間のマッピングを提供する機能も含みます。 ローカルドメインおよびリモートドメインの一意なアイデンティティーまたはプリンシパルに適用できます。 多くの場合、ライトウェイトディレクトリアクセスプロトコル（LDAP） [RFC4511]などのディレクトリサービスによって提供されます。
ネームサービススイッチ（Name Service Switch、nsswitch）:
共通の設定データベースと名前解決メカニズムに対して、さまざまなソースを提供する機能です。
FedFS:
フェデレーテッドファイルシステム（FedFS）[RFC5716]は、企業全体にわたることができ、管理が容易な、ファイルサーバーベースの統一されたNFSv4名前空間を構築するための要件と管理ツールを記述しています。
ドメイン（Domain）:

この用語は複数の文脈で異なる意味で使用されます。 「NFSv4ドメイン」と「マルチドメイン」は上で定義されています。

DNSドメイン（DNS domain）:
DNSドメイン名[RFC1034]で識別される、コンピューター、サービス、または任意のインターネットリソースの集合です。
セキュリティーレルムまたはセキュリティードメイン（Security realm or domain）:
単一のセキュリティープロトコルを実行し、単一のエンティティーによって管理される、設定済みのセキュリティープロバイダー、ユーザー、グループ、セキュリティーロール、セキュリティーポリシーの集合です。 例として、Kerberosレルムがあります。
FedFSドメイン（FedFS domain）:
NFSv4などのファイルアクセスプロトコルを使用して、複数のファイルサーバー上の複数の共有にまたがることができるファイル名前空間です。 FedFSドメインは通常、単一の管理エンティティーであり、DNSドメイン名に似た名前を持ちます。 「フェデレーション（Federation）」とも呼ばれます。
管理ドメイン（Administrative domain）:
単一のエンティティーによって管理される、ユーザー、グループ、コンピューター、サービスの集合です。 複数のDNSドメイン、NFSv4ドメイン、セキュリティードメイン、FedFSドメインを含むことができます。

3. Federated File System

3. フェデレーテッドファイルシステム

The FedFS is the standardized method of constructing and administrating an enterprise-wide NFSv4 file system and is thus referenced in this document. The requirements for multi-domain deployments described in this document apply to all NFSv4 multi- domain deployments, whether or not they are run as a FedFS.

FedFSは、企業全体のNFSv4ファイルシステムを構築および管理するための標準化された方法であるため、この文書で参照しています。 この文書で説明するマルチドメインのデプロイに対する要件は、FedFSとして運用されているかどうかにかかわらず、すべてのNFSv4マルチドメインのデプロイに適用されます。

Stand-alone NFSv4 Domain deployments can be run in many ways. While a FedFS can be run within all stand-alone NFSv4 Domain configurations, some of these configurations (Section 5) are not compatible with joining a multi-domain FedFS namespace.

スタンドアロンNFSv4ドメインのデプロイは、さまざまな方法で運用できます。 FedFSはすべてのスタンドアロンNFSv4ドメイン構成内で運用できますが、それらの構成の一部（セクション5）は、マルチドメインFedFS名前空間への参加と互換性がありません。

4. Identity Mapping

4. アイデンティティーマッピング

4.1. NFSv4 Server Identity Mapping

4.1. NFSv4サーバーのアイデンティティーマッピング

NFSv4 servers deal with two kinds of identities: authentication identities (referred to here as "principals") and authorization identities ("users" and "groups" of users). NFSv4 supports multiple authentication methods, each authenticating an "initiator principal" (typically representing a user) to an "acceptor principal" (always corresponding to the NFSv4 server). NFSv4 does not prescribe how to represent authorization identities on file systems. All file access decisions constitute "authorization" and are made by NFSv4 servers using authorization context information and file metadata related to authorization, such as a file's access control list (ACL).

NFSv4サーバーは、2種類のアイデンティティーを扱います。 認証アイデンティティー（ここでは「プリンシパル」と呼びます）と、認可アイデンティティー（ユーザーの「ユーザー」と「グループ」）です。 NFSv4は複数の認証方式をサポートしており、それぞれが「イニシエータープリンシパル」（通常はユーザーを表します）を「アクセプタープリンシパル」（常にNFSv4サーバーに対応します）に対して認証します。 NFSv4は、ファイルシステム上で認可アイデンティティーをどのように表現するかを規定していません。 ファイルアクセスの判断はすべて「認可」にあたり、NFSv4サーバーが、認可コンテキスト情報と、ファイルのアクセス制御リスト（ACL）など認可に関連するファイルメタデータを使用して行います。

NFSv4 servers may be required to perform two kinds of mappings depending upon what authentication and authorization information is sent on the wire and what is stored in the exported file system. For example, if an authentication identity such as a Kerberos principal is sent with authorization information such as a "privilege attribute certificate" (PAC) [PAC], then mapping is not required (see Section 8).

NFSv4サーバーは、ネットワーク上でどのような認証情報と認可情報が送信されるか、およびエクスポートされたファイルシステムに何が保存されているかに応じて、2種類のマッピングを実行する必要がある場合があります。 たとえば、Kerberosプリンシパルなどの認証アイデンティティーが、「特権属性証明書（privilege attribute certificate）」（PAC）[PAC]などの認可情報とともに送信される場合、マッピングは必要ありません（セクション8を参照）。

  1. Auth-to-authz: A mapping between the authentication identity and the authorization context information.
  2. Wire-to-disk: A mapping between the on-the-wire authorization identity representation and the on-disk authorization identity representation.
  1. Auth-to-authz: 認証アイデンティティーと認可コンテキスト情報との間のマッピングです。
  2. Wire-to-disk: ネットワーク上の認可アイデンティティー表現とディスク上の認可アイデンティティー表現との間のマッピングです。

A name service such as LDAP often provides these mappings.

LDAPなどのネームサービスが、これらのマッピングを提供することがよくあります。

Many aspects of these mappings are entirely implementation specific, but some require multi-domain-capable name resolution and security services in order to interoperate in a multi-domain environment.

これらのマッピングの多くの側面は完全に実装依存ですが、マルチドメイン環境で相互運用するには、マルチドメイン対応の名前解決サービスとセキュリティーサービスを必要とするものもあります。

NFSv4 servers use these mappings for:

NFSv4サーバーは、次の目的でこれらのマッピングを使用します。

  1. File access: Both the auth-to-authz and the wire-to-disk mappings may be required for file access decisions.
  2. Metadata setting and listing: The auth-to-authz mapping is usually required to service file metadata setting or listing requests such as ACL or UNIX permission setting or listing. This mapping is needed because NFSv4 messages use identity representations of the form name@domain, which normally differs from the server's local representation of identity.
  1. ファイルアクセス: ファイルアクセスの判断には、auth-to-authzマッピングとwire-to-diskマッピングの両方が必要になる場合があります。
  2. メタデータの設定と一覧表示: ACLやUNIXパーミッションの設定や一覧表示など、ファイルメタデータの設定または一覧表示のリクエストを処理するには、通常、auth-to-authzマッピングが必要です。 このマッピングが必要なのは、NFSv4メッセージがname@domain形式のアイデンティティー表現を使用しており、これは通常、サーバーのアイデンティティーのローカル表現とは異なるためです。

4.2. NFSv4 Client Identity Mapping

4.2. NFSv4クライアントのアイデンティティーマッピング

A client setting the owner or group attribute will often need access to identity-mapping services. This is because APIs within the client will specify the identity in a local form (e.g., UNIX using a UID/ GID) so that when stringified id's cannot be used, the ID must be converted to a unique identity form.

オーナー属性またはグループ属性を設定するクライアントは、アイデンティティーマッピングサービスにアクセスする必要があることが多くあります。 これは、クライアント内のAPIがアイデンティティーをローカル形式（たとえば、UNIXではUID/GID）で指定するため、文字列化されたIDを使用できない場合には、そのIDを一意なアイデンティティー形式に変換しなければならないためです。

A client obtaining values for the owner or group attributes will similarly need access to identity-mapping services. This is because the client API will need these attributes in a local form, as above. As a result, name services need to be available to convert the unique identity to a local form.

オーナー属性またはグループ属性の値を取得するクライアントも、同様にアイデンティティーマッピングサービスにアクセスする必要があります。 これは、上記と同様に、クライアントAPIがこれらの属性をローカル形式で必要とするためです。 その結果、一意なアイデンティティーをローカル形式に変換するために、ネームサービスが利用可能である必要があります。

Note that each of these situations arises because client-side APIs require a particular local identity representation. The need for mapping services would not arise if the clients could use the unique representation of identity directly.

これらの状況はいずれも、クライアント側のAPIが特定のアイデンティティーのローカル表現を必要とするために生じることに注意してください。 クライアントが一意なアイデンティティー表現を直接使用できれば、マッピングサービスの必要性は生じません。

5. Stand-Alone NFSv4 Domain Deployment Examples

5. スタンドアロンNFSv4ドメインのデプロイ例

The purpose of this section is to list some typical stand-alone deployment examples to highlight the need for the required restraints to the NFSv4 protocol, name service configuration, and security service choices in an NFSv4 multi-domain environment described in Section 6.

このセクションの目的は、典型的なスタンドアロンのデプロイ例をいくつか挙げ、セクション6で説明するNFSv4マルチドメイン環境における、NFSv4プロトコル、ネームサービスの構成、セキュリティーサービスの選択に対して必要な制約の必要性を明らかにすることです。

Section 7 notes how these stand-alone deployment examples would need to change to participate in an NFSv4 multi-domain deployment.

セクション7では、これらのスタンドアロンのデプロイ例がNFSv4マルチドメインのデプロイに参加するには、どのように変更する必要があるかを示します。

In order to service as many environments as possible, the NFSv4 protocol is designed to allow administrators freedom to configure their NFSv4 Domains as they please. Stand-alone NFSv4 Domains can be run in many ways.

できるだけ多くの環境に対応するため、NFSv4プロトコルは、管理者が自由にNFSv4ドメインを構成できるように設計されています。 スタンドアロンNFSv4ドメインは、さまざまな方法で運用できます。

These examples are for an NFSv4 server exporting a POSIX UID/GID- based file system, a typical deployment. These examples are listed in the order of increasing NFSv4 administrative complexity.

これらの例は、典型的なデプロイである、POSIXのUID/GIDベースのファイルシステムをエクスポートするNFSv4サーバーを対象としています。 これらの例は、NFSv4の管理の複雑さが増す順に並べています。

5.1. AUTH_SYS with Stringified UID/GID

5.1. 文字列化されたUID/GIDを使用するAUTH_SYS

This example is the closest NFSv4 gets to being run as NFSv3 as there is no need for a name service for file metadata listing.

この例は、ファイルメタデータの一覧表示にネームサービスが不要なため、NFSv4がNFSv3として運用される場合に最も近いものです。

File access: The AUTH_SYS RPC credential [RFC5531] provides a UID as the authentication identity, and a list of GIDs as authorization context information. File access decisions require no name service interaction as the on-the-wire and on-disk representation are the same and the auth-to-authz UID and GID authorization context information is provided in the RPC credential.

ファイルアクセス: AUTH_SYS RPCクレデンシャル[RFC5531]は、認証アイデンティティーとしてUIDを、認可コンテキスト情報としてGIDのリストを提供します。 ネットワーク上の表現とディスク上の表現は同じであり、auth-to-authzのUIDおよびGIDの認可コンテキスト情報はRPCクレデンシャルで提供されるため、ファイルアクセスの判断にはネームサービスとのやり取りは必要ありません。

Metadata setting and listing: When the NFSv4 clients and servers implement a stringified UID/GID scheme, where a stringified UID or GID is used for the NFSv4 name@domain on-the-wire identity, then a name service is not required for file metadata listing as the UID, or GID can be constructed from the stringified form on the fly by the server.

メタデータの設定と一覧表示: NFSv4のクライアントとサーバーが、文字列化されたUIDまたはGIDをNFSv4のname@domain形式のネットワーク上のアイデンティティーに使用する、文字列化されたUID/GIDの方式を実装している場合、サーバーは文字列化された形式からその場でUIDまたはGIDを構築できるため、ファイルメタデータの一覧表示にネームサービスは必要ありません。

5.2. AUTH_SYS with Name@domain

5.2. Name@domainを使用するAUTH_SYS

Another possibility is to express identity using the form 'name@domain', rather than using a stringified UID/GID scheme for file metadata setting and listing.

もう1つの可能性は、ファイルメタデータの設定と一覧表示に、文字列化されたUID/GIDの方式を使用する代わりに、「name@domain」形式でアイデンティティーを表現することです。

File access: This is the same as in Section 5.1.

ファイルアクセス: セクション5.1と同じです。

Metadata setting and listing: The NFSv4 server will need to use a name service for the wire-to-disk mappings to map between the on-the- wire name@domain syntax and the on-disk UID/GID representation. Often, the NFSv4 server will use the nsswitch interface for these mappings. A typical use of the nsswitch name service interface uses no domain component, just the UID attribute [RFC2307] (or login name) as the name component. This is not an issue in a stand-alone NFSv4 Domain deployment as the NFSv4 Domain is known to the NFSv4 server and can be combined with the login name to form the name@domain syntax after the return of the name service call.

メタデータの設定と一覧表示: NFSv4サーバーは、ネットワーク上のname@domain構文とディスク上のUID/GID表現との間でマッピングを行うwire-to-diskマッピングのために、ネームサービスを使用する必要があります。 多くの場合、NFSv4サーバーはこれらのマッピングにnsswitchインターフェイスを使用します。 nsswitchネームサービスインターフェイスの典型的な使用では、ドメイン部分を使用せず、名前部分としてUID属性[RFC2307]（またはログイン名）のみを使用します。 スタンドアロンNFSv4ドメインのデプロイでは、NFSv4ドメインがNFSv4サーバーに既知であり、ネームサービス呼び出しの結果が返された後にログイン名と組み合わせてname@domain構文を形成できるため、これは問題になりません。

5.3. RPCSEC_GSS with Name@domain

5.3. Name@domainを使用するRPCSEC_GSS

RPCSEC_GSS uses Generic Security Service Application Program Interface (GSS-API) [RFC2743] security mechanisms to securely authenticate users to servers. The most common mechanism is Kerberos [RFC4121].

RPCSEC_GSSは、ジェネリックセキュリティーサービスアプリケーションプログラムインターフェイス（GSS-API）[RFC2743]のセキュリティーメカニズムを使用して、ユーザーをサーバーに対して安全に認証します。 最も一般的なメカニズムはKerberos [RFC4121]です。

This final example adds the use of RPCSEC_GSS with the Kerberos 5 GSS security mechanism.

この最後の例では、Kerberos 5 GSSセキュリティーメカニズムを使用するRPCSEC_GSSを追加します。

File Access: The forms of GSS principal names are mechanism specific. For Kerberos, these are of the form principal@REALM. Sometimes authorization context information is delivered with authentication, but this cannot be counted on. Authorization context information not delivered with authentication has timely update considerations (i.e., generally it's not possible to get a timely update). File access decisions therefore require a wire-to-disk mapping of the GSS principal to a UID and an auth-to-authz mapping to obtain the list of GIDs as the authorization context.

ファイルアクセス: GSSプリンシパル名の形式はメカニズムに固有です。 Kerberosの場合、これらはprincipal@REALMの形式です。 認可コンテキスト情報が認証とともに配信されることもありますが、これを当てにすることはできません。 認証とともに配信されない認可コンテキスト情報には、タイムリーな更新に関する考慮事項があります（つまり、一般にタイムリーな更新を得ることはできません）。 そのため、ファイルアクセスの判断には、GSSプリンシパルをUIDにマッピングするwire-to-diskマッピングと、認可コンテキストとしてGIDのリストを取得するauth-to-authzマッピングが必要です。

Metadata setting and listing: This is the same as in Section 5.2.

メタデータの設定と一覧表示: セクション5.2と同じです。

6. Multi-Domain Constraints to the NFSv4 Protocol

6. NFSv4プロトコルに対するマルチドメインの制約

Joining NFSv4 Domains under a single file namespace imposes slightly on the NFSv4 administrative freedom. In this section, we describe the required constraints.

NFSv4ドメインを単一のファイル名前空間の下で結合すると、NFSv4の管理上の自由度がわずかに制約されます。 このセクションでは、必要な制約について説明します。

6.1. Name@domain Constraints

6.1. Name@domainの制約

NFSv4 uses a syntax of the form "name@domain" (see Section 5.9 of [RFC7530]) as the on-the-wire representation of the "who" field of an NFSv4 access control entry (ACE) for users and groups. This design provides a level of indirection that allows NFSv4 clients and servers with different internal representations of authorization identity to interoperate even when referring to authorization identities from different NFSv4 Domains.

NFSv4は、ユーザーおよびグループに対するNFSv4アクセス制御エントリー（ACE）の「who」フィールドのネットワーク上の表現として、「name@domain」形式の構文（[RFC7530]のセクション5.9を参照）を使用します。 この設計は、間接参照の層を提供することで、認可アイデンティティーの内部表現が異なるNFSv4クライアントとサーバーが、異なるNFSv4ドメインの認可アイデンティティーを参照する場合でも相互運用できるようにします。

Multi-domain-capable sites need to meet the following requirements in order to ensure that NFSv4 clients and servers can map between name@domain and internal representations reliably. While some of these constraints are basic assumptions in NFSv4.0 [RFC7530] and NFSv4.1 [RFC5661], they need to be clearly stated for the multi- domain case.

マルチドメイン対応のサイトは、NFSv4のクライアントとサーバーがname@domainと内部表現との間で確実にマッピングできるようにするために、次の要件を満たす必要があります。 これらの制約の一部は、NFSv4.0 [RFC7530]およびNFSv4.1 [RFC5661]における基本的な前提ですが、マルチドメインの場合には明確に述べる必要があります。

  • The NFSv4 Domain portion of name@domain MUST be unique within the multi-domain namespace. See [RFC5661], Section 5.9 ("Interpreting owner and owner_group") for a discussion on NFSv4 Domain configuration.
  • The name portion of name@domain MUST be unique within the specified NFSv4 Domain.
  • name@domainのNFSv4ドメイン部分は、マルチドメイン名前空間内で一意でなければなりません（MUST）。 NFSv4ドメインの構成に関する議論については、[RFC5661], セクション5.9（「Interpreting owner and owner_group」）を参照してください。
  • name@domainの名前部分は、指定されたNFSv4ドメイン内で一意でなければなりません（MUST）。

Due to UID and GID collisions, stringified UID/GIDs MUST NOT be used in a multi-domain deployment. This means that multi-domain-capable servers MUST reject requests that use stringified UID/GIDs.

UIDとGIDの衝突のため、マルチドメインのデプロイでは文字列化されたUID/GIDを使用してはなりません（MUST NOT）。 これは、マルチドメイン対応のサーバーは、文字列化されたUID/GIDを使用するリクエストを拒否しなければならない（MUST）ことを意味します。

6.1.1. NFSv4 Domain and DNS Services

6.1.1. NFSv4ドメインとDNSサービス

Here we address the relationship between NFSv4 Domain name and DNS domain name in a multi-domain deployment.

ここでは、マルチドメインのデプロイにおけるNFSv4ドメイン名とDNSドメイン名との関係を取り上げます。

The definition of an NFSv4 Domain name, the @domain portion of the name@domain syntax, needs clarification to work in a multi-domain file system namespace. [RFC5661], Section 5.9 loosely defines the NFSv4 Domain name as a DNS domain name. This loose definition for the NFSv4 Domain name is a good one, as DNS domain names are globally unique. As noted in Section 6.1, any choice of NFSv4 Domain name can work within a stand-alone NFSv4 Domain deployment whereas the NFSv4 Domain name is required to be unique across a multi-domain deployment.

NFSv4ドメイン名、つまりname@domain構文の@domain部分の定義は、マルチドメインファイルシステム名前空間で機能させるために明確化が必要です。 [RFC5661], セクション5.9は、NFSv4ドメイン名をDNSドメイン名として大まかに定義しています。 DNSドメイン名はグローバルに一意であるため、NFSv4ドメイン名のこの大まかな定義は適切です。 セクション6.1で述べたように、スタンドアロンNFSv4ドメインのデプロイ内では、NFSv4ドメイン名にどのような名前を選んでも機能しますが、マルチドメインのデプロイ全体ではNFSv4ドメイン名が一意であることが求められます。

A typical configuration is that there is a single NFSv4 Domain that is served by a single DNS domain. In this case, the NFSv4 Domain name can be the same as the DNS domain name.

典型的な構成では、単一のNFSv4ドメインが単一のDNSドメインによって提供されます。 この場合、NFSv4ドメイン名をDNSドメイン名と同じにできます。

An NFSv4 Domain can span multiple DNS domains. In this case, one of the DNS domain names can be chosen as the NFSv4 Domain name.

NFSv4ドメインは複数のDNSドメインにまたがることができます。 この場合、いずれかのDNSドメイン名をNFSv4ドメイン名として選択できます。

Multiple NFSv4 Domains can also share a DNS domain. In this case, only one of the NFSv4 Domains can use the DNS domain name, the other NFSv4 Domains must choose another unique NFSv4 Domain name.

複数のNFSv4ドメインが1つのDNSドメインを共有することもできます。 この場合、DNSドメイン名を使用できるNFSv4ドメインは1つだけであり、他のNFSv4ドメインは別の一意なNFSv4ドメイン名を選ばなければなりません。

6.1.2. NFSv4 Domain and Name Services

6.1.2. NFSv4ドメインとネームサービス

As noted in Section 6.1, each name@domain is unique across the multi- domain namespace and maps, on each NFSv4 server, to the local representation of identity used by that server. Typically, this representation consists of an indication of the particular domain combined with the UID/GID corresponding to the name component. To support such an arrangement, each NFSv4 Domain needs to have a single name resolution service capable of converting the names defined within the domain to the corresponding local representation.

セクション6.1で述べたように、各name@domainはマルチドメイン名前空間全体で一意であり、各NFSv4サーバーで、そのサーバーが使用するアイデンティティーのローカル表現にマッピングされます。 通常、この表現は、特定のドメインを示すものと、名前部分に対応するUID/GIDを組み合わせたもので構成されます。 このような仕組みをサポートするには、各NFSv4ドメインに、そのドメイン内で定義された名前を対応するローカル表現に変換できる、単一の名前解決サービスが必要です。

6.2. RPC Security Constraints

6.2. RPCセキュリティーの制約

As described in [RFC5661], Section 2.2.1.1 ("RPC Security Flavors"):

[RFC5661], セクション2.2.1.1（「RPC Security Flavors」）では、次のように説明されています。

NFSv4.1 clients and servers MUST implement RPCSEC_GSS. (This requirement to implement is not a requirement to use.) Other flavors, such as AUTH_NONE and AUTH_SYS, MAY be implemented as well.

NFSv4.1のクライアントとサーバーは、RPCSEC_GSSを実装しなければならない（MUST）。 （この実装の要件は、使用の要件ではない。） AUTH_NONEやAUTH_SYSなどの他のフレーバーも実装してもよい（MAY）。

The underlying RPCSEC_GSS GSS-API [RFC2203] security mechanism used in a multi-domain namespace is REQUIRED to employ a method of cross NFSv4 Domain trust so that a principal from a security service in one NFSv4 Domain can be authenticated in another NFSv4 Domain that uses a security service with the same security mechanism. Kerberos is an example of such a security service.

マルチドメイン名前空間で使用される、基盤となるRPCSEC_GSS GSS-API [RFC2203]セキュリティーメカニズムは、あるNFSv4ドメインのセキュリティーサービスのプリンシパルが、同じセキュリティーメカニズムのセキュリティーサービスを使用する別のNFSv4ドメインで認証できるように、NFSv4ドメイン間の信頼の方法を採用することが要求されています（REQUIRED）。 Kerberosは、このようなセキュリティーサービスの一例です。

The AUTH_NONE [RFC5531] security flavor can be useful in a multi- domain deployment to grant universal read-only access to public data without any credentials.

AUTH_NONE [RFC5531]セキュリティーフレーバーは、マルチドメインのデプロイにおいて、クレデンシャルなしで公開データへの普遍的な読み取り専用アクセスを許可するのに役立ちます。

The AUTH_SYS security flavor [RFC5531] uses a host-based authentication model where the weakly authenticated host (the NFSv4 client) asserts the user's authorization identities using small integers, uidNumber, and gidNumber [RFC2307] as user and group identity representations. Because this authorization ID representation has no domain component, AUTH_SYS can only be used in a namespace where all NFSv4 clients and servers share a name service as described in [RFC2307]. A shared name service is required because uidNumbers and gidNumbers are passed in the RPC credential; there is no negotiation of namespace in AUTH_SYS. Collisions can occur if multiple name services are used, so AUTH_SYS MUST NOT be used in a multi-domain file system deployment.

AUTH_SYSセキュリティーフレーバー[RFC5531]は、ホストベースの認証モデルを使用します。 このモデルでは、弱く認証されたホスト（NFSv4クライアント）が、ユーザーおよびグループのアイデンティティー表現として、小さな整数であるuidNumberとgidNumber [RFC2307]を使用して、ユーザーの認可アイデンティティーを主張します。 この認可ID表現にはドメイン部分がないため、AUTH_SYSは、すべてのNFSv4クライアントとサーバーが[RFC2307]で説明されているネームサービスを共有している名前空間でのみ使用できます。 uidNumberとgidNumberはRPCクレデンシャルで渡され、AUTH_SYSには名前空間のネゴシエーションがないため、共有ネームサービスが必要です。 複数のネームサービスが使用されると衝突が発生する可能性があるため、マルチドメインのファイルシステムのデプロイでは、AUTH_SYSを使用してはなりません（MUST NOT）。

6.2.1. NFSv4 Domain and Security Services

6.2.1. NFSv4ドメインとセキュリティーサービス

As noted in Section 6.2 regarding AUTH_NONE, multiple NFSv4 Domain security services are RPCSEC_GSS based with the Kerberos 5 security mechanism being the most commonly (and as of this writing, the only) deployed service.

AUTH_NONEに関してセクション6.2で述べたように、NFSv4ドメインのセキュリティーサービスは、複数ともRPCSEC_GSSに基づいており、Kerberos 5セキュリティーメカニズムが最も一般的に（そして、この文書の執筆時点では唯一）デプロイされているサービスです。

A single Kerberos 5 security service per NFSv4 Domain with the upper case NFSv4 Domain name as the Kerberos 5 REALM name is a common deployment.

NFSv4ドメインごとに単一のKerberos 5セキュリティーサービスを置き、NFSv4ドメイン名の大文字版をKerberos 5のREALM名とするのが、一般的なデプロイです。

Multiple security services per NFSv4 Domain is allowed and brings the need of mapping multiple Kerberos 5 principal@REALMs to the same local ID. Methods of achieving this are beyond the scope of this document.

NFSv4ドメインごとに複数のセキュリティーサービスを置くことは許可されており、複数のKerberos 5のprincipal@REALMを同じローカルIDにマッピングする必要が生じます。 これを実現する方法は、この文書の範囲外です。

7. Stand-Alone Examples in an NFSv4 Multi-Domain Deployment

7. NFSv4マルチドメインのデプロイにおけるスタンドアロンの例

In this section, we revisit the stand-alone NFSv4 Domain deployment examples in Section 5 and note what is prohibiting them from participating in an NFSv4 multi-domain deployment.

このセクションでは、セクション5のスタンドアロンNFSv4ドメインのデプロイ例を再び取り上げ、それらがNFSv4マルチドメインのデプロイに参加できない原因を示します。

Note that because all on-disk identities participating in a stand- alone NFSv4 Domain belong to the same NFSv4 Domain, stand-alone NFSv4 Domain deployments have no requirement for exporting multi-domain- capable file systems. To participate in an NFSv4 multi-domain deployment, all three examples in Section 5 would need to export multi-domain-capable file systems.

スタンドアロンNFSv4ドメインに参加するディスク上のアイデンティティーはすべて同じNFSv4ドメインに属するため、スタンドアロンNFSv4ドメインのデプロイでは、マルチドメイン対応のファイルシステムをエクスポートする必要がないことに注意してください。 NFSv4マルチドメインのデプロイに参加するには、セクション5の3つの例のすべてが、マルチドメイン対応のファイルシステムをエクスポートする必要があります。

Due to the use of AUTH_SYS and stringified UID/GIDs, the first stand- alone deployment example (described in Section 5.1) is not suitable for participation in an NFSv4 multi-domain deployment.

AUTH_SYSと文字列化されたUID/GIDを使用しているため、最初のスタンドアロンのデプロイ例（セクション5.1で説明）は、NFSv4マルチドメインのデプロイへの参加には適していません。

The second example (described in Section 5.2) does use the name@domain syntax, but the use of AUTH_SYS prohibits its participation in an NFSv4 multi-domain deployment.

2番目の例（セクション5.2で説明）はname@domain構文を使用していますが、AUTH_SYSを使用しているため、NFSv4マルチドメインのデプロイへの参加はできません。

The third example (described in Section 5.3) can participate in a multi-domain namespace deployment if:

3番目の例（セクション5.3で説明）は、次の場合にマルチドメイン名前空間のデプロイに参加できます。

  • The NFSv4 Domain name is unique across the namespace.
  • All exported file systems are multi-domain capable.
  • A secure method is used to resolve the remote NFSv4 Domain principal's authorization information from an authoritative source.
  • NFSv4ドメイン名が名前空間全体で一意である。
  • エクスポートされるすべてのファイルシステムがマルチドメイン対応である。
  • リモートNFSv4ドメインのプリンシパルの認可情報を、信頼できる情報源から解決するために、安全な方法が使用される。

8. Resolving Multi-Domain Authorization Information

8. マルチドメインの認可情報の解決

When an RPCSEC_GSS principal is seeking access to files on an NFSv4 server, after authenticating the principal, the server SHOULD obtain in a secure manner the principal's authorization context information from an authoritative source such as the name service in the principal's NFSv4 Domain.

RPCSEC_GSSプリンシパルがNFSv4サーバー上のファイルへのアクセスを求める場合、サーバーはそのプリンシパルを認証した後、プリンシパルのNFSv4ドメインのネームサービスなどの信頼できる情報源から、プリンシパルの認可コンテキスト情報を安全な方法で取得すべきです（SHOULD）。

In the stand-alone NFSv4 Domain case where the principal is seeking access to files on an NFSv4 server in the principal's home NFSv4 Domain, the server administrator has knowledge of the local policies and methods for obtaining the principal's authorization information and the mappings to local representation of identity from an authoritative source. For example, the administrator can configure secure access to the local NFSv4 Domain name service.

プリンシパルが、自身のホームNFSv4ドメイン内のNFSv4サーバー上のファイルへのアクセスを求める、スタンドアロンNFSv4ドメインの場合、サーバー管理者は、信頼できる情報源からプリンシパルの認可情報を取得する方法とローカルポリシー、およびアイデンティティーのローカル表現へのマッピングを把握しています。 たとえば、管理者はローカルNFSv4ドメインのネームサービスへの安全なアクセスを設定できます。

In the multi-domain case where a principal is seeking access to files on an NFSv4 server not in the principal's home NFSv4 Domain, the NFSv4 server may be required to contact the remote name service in the principal's NFSv4 Domain. In this case, there is no assumption of:

プリンシパルが、自身のホームNFSv4ドメインにないNFSv4サーバー上のファイルへのアクセスを求める、マルチドメインの場合、NFSv4サーバーは、プリンシパルのNFSv4ドメインにあるリモートのネームサービスに問い合わせる必要がある場合があります。 この場合、次のことは前提とされません。

  • Remote name service configuration knowledge.
  • The syntax of the remote authorization context information presented to the NFSv4 server by the remote name service for mapping to a local representation.
  • リモートのネームサービスの構成に関する知識。
  • ローカル表現にマッピングするためにリモートのネームサービスからNFSv4サーバーに提示される、リモートの認可コンテキスト情報の構文。

There are several methods the NFSv4 server can use to obtain the NFSv4 Domain authoritative authorization information for a remote principal from an authoritative source. While detailing these methods is beyond the scope of this document, some general methods are listed here.

NFSv4サーバーが、リモートプリンシパルのNFSv4ドメインの信頼できる認可情報を信頼できる情報源から取得するために使用できる方法はいくつかあります。 これらの方法の詳細は、この文書の範囲外ですが、一般的な方法をいくつかここに挙げます。

  1. A mechanism-specific GSS-API authorization payload containing credential authorization data such as a "privilege attribute certificate" (PAC) [PAC] or a "principal authorization data" (PAD) [GEN-PAC]. This is the preferred method as the payload is delivered as part of GSS-API authentication, avoids requiring any knowledge of the remote authoritative service configuration, and has a well-known syntax.
  2. When there is a security agreement between the local and remote NFSv4 Domain name services plus regular update data feeds, the NFSv4 server local NFSv4 Domain name service can be authoritative for principals in the remote NFSv4 Domain. In this case, the NFSv4 server makes a query to its local NFSv4 Domain name service just as it does when servicing a local domain principal. While this requires detailed knowledge of the remote NFSv4 Domain name service for the update data feeds, the authorization context information presented to the NFSv4 server is in the same form as a query for a local principal.
  3. An authenticated direct query from the NFSv4 server to the principal's NFSv4 Domain authoritative name service. This requires the NFSv4 server to have detailed knowledge of the remote NFSv4 Domain's authoritative name service and detailed knowledge of the syntax of the resultant authorization context information.
  1. 「特権属性証明書（privilege attribute certificate）」（PAC）[PAC]や「プリンシパル認可データ（principal authorization data）」（PAD）[GEN-PAC]などのクレデンシャルの認可データを含む、メカニズム固有のGSS-API認可ペイロード。 ペイロードがGSS-API認証の一部として配信され、リモートの信頼できるサービスの構成に関する知識を必要とせず、構文もよく知られているため、これが推奨される方法です。
  2. ローカルとリモートのNFSv4ドメインのネームサービス間にセキュリティー上の合意があり、さらに定期的な更新データフィードがある場合、NFSv4サーバーのローカルNFSv4ドメインのネームサービスが、リモートNFSv4ドメインのプリンシパルに対して信頼できる情報源になることができます。 この場合、NFSv4サーバーは、ローカルドメインのプリンシパルを処理する場合と同様に、ローカルNFSv4ドメインのネームサービスに問い合わせます。 これには、更新データフィードのためにリモートNFSv4ドメインのネームサービスに関する詳細な知識が必要ですが、NFSv4サーバーに提示される認可コンテキスト情報は、ローカルプリンシパルへの問い合わせと同じ形式です。
  3. NFSv4サーバーからプリンシパルのNFSv4ドメインの信頼できるネームサービスへの、認証された直接の問い合わせ。 これには、NFSv4サーバーが、リモートNFSv4ドメインの信頼できるネームサービスに関する詳細な知識と、結果として得られる認可コンテキスト情報の構文に関する詳細な知識を持っている必要があります。

9. Security Considerations

9. セキュリティーに関する考慮事項

This RFC discusses security throughout. All the security considerations of the relevant protocols, such as NFSv4.0 [RFC7530], NFSv4.1 [RFC5661], RPCSEC_GSS [RFC2203], GSS-API [RFC4121], LDAP [RFC4511], Requirements for Federated FS [RFC5716], FedFS Namespace Database Protocol [RFC7532], FedFS Administration Protocol [RFC7533], and FedFS Security Addendum [SEC-ADD] apply.

このRFCでは、全体を通してセキュリティーについて論じています。 NFSv4.0 [RFC7530]、NFSv4.1 [RFC5661]、RPCSEC_GSS [RFC2203]、GSS-API [RFC4121]、LDAP [RFC4511]、フェデレーテッドFSの要件[RFC5716]、FedFS名前空間データベースプロトコル[RFC7532]、FedFS管理プロトコル[RFC7533]、およびFedFSセキュリティー補遺[SEC-ADD]など、関連するプロトコルのセキュリティーに関する考慮事項はすべて適用されます。

Authentication and authorization across administrative domains present security considerations, most of which are treated elsewhere, but we repeat some of them here:

管理ドメインをまたぐ認証と認可にはセキュリティー上の考慮事項があり、その大部分は他の文書で扱われていますが、ここではその一部を繰り返します。

  • latency in propagation of revocation of authentication credentials
  • latency in propagation of revocation of authorizations
  • latency in propagation of granting of authorizations
  • complications in establishing a complete authorization context for users of a foreign domain (only parts may be available to servers)
  • privacy considerations in a federated environment
  • 認証クレデンシャルの失効の伝播における遅延
  • 認可の失効の伝播における遅延
  • 認可の付与の伝播における遅延
  • 外部ドメインのユーザーに対する完全な認可コンテキストを確立する際の複雑さ（サーバーが利用できるのは一部のみの場合があります）
  • フェデレーテッド環境におけるプライバシーに関する考慮事項

Most of these are security considerations of the mechanisms used to authenticate users to servers and servers to users and of the mechanisms used to evaluate a user's authorization context.

これらの大部分は、ユーザーをサーバーに対して、およびサーバーをユーザーに対して認証するために使用されるメカニズムと、ユーザーの認可コンテキストを評価するために使用されるメカニズムの、セキュリティーに関する考慮事項です。

Implementors may be tempted to assume that "realm" (or "issuer") and "NFSv4 Domain" are roughly the same thing, but they are not. Configuration and/or lookup protocols (such as LDAP) and associated schemas are generally required in order to evaluate a user principal's authorization context (see Section 8). In the simplest scheme, a server has access to a database mapping all known principal names to user names whose authorization context can be evaluated using operating system interfaces that deal in user names rather than principal names.

実装者は、「レルム」（または「発行者」）と「NFSv4ドメイン」がほぼ同じものだと考えたくなるかもしれませんが、同じではありません。 ユーザープリンシパルの認可コンテキストを評価するには、一般に、設定プロトコルや検索プロトコル（LDAPなど）と、それに関連するスキーマが必要です（セクション8を参照）。 最も単純な方式では、サーバーは、既知のすべてのプリンシパル名をユーザー名にマッピングするデータベースにアクセスでき、そのユーザー名の認可コンテキストは、プリンシパル名ではなくユーザー名を扱うオペレーティングシステムのインターフェイスを使用して評価できます。

Note that clients may also need to evaluate a server's authorization context when using labeled security [RFC7862] (e.g., is the server authorized to handle content at a given security level for the given client process subject label).

ラベル付きセキュリティー[RFC7862]を使用する場合、クライアントもサーバーの認可コンテキストを評価する必要がある場合があることに注意してください（たとえば、サーバーが、特定のクライアントプロセスのサブジェクトラベルに対して、特定のセキュリティーレベルのコンテンツを扱う権限を持っているかどうか）。

When the server accepts user credentials from more than one realm, it is important to remember that the server must verify that the client it is talking to has a credential for the name the client has presented the server and that the credential's issuer (i.e., its realm) is allowed to issue it. Usually, the service principal realm authorization function is implemented by the security mechanism, but the implementor should check this.

サーバーが複数のレルムからユーザークレデンシャルを受け入れる場合、サーバーは、通信相手のクライアントが、サーバーに提示した名前に対するクレデンシャルを持っていること、およびそのクレデンシャルの発行者（つまり、そのレルム）がそれを発行することを許可されていることを、検証しなければならないことを覚えておくことが重要です。 通常、サービスプリンシパルのレルムの認可機能はセキュリティーメカニズムによって実装されますが、実装者はこれを確認すべきです。
