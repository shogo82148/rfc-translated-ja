RFC 10038

Distributing the Segment Routing over IPv6 (SRv6) Locator Using DHCPv6

RFC 10038

DHCPv6を使用したSegment Routing over IPv6（SRv6）ロケーターの配布

Abstract

概要

In an SRv6 network, each SRv6 Segment Endpoint Node must be assigned an SRv6 Locator, and segment identifiers (SIDs) are generated within the address space of this SRv6 Locator. This document describes a method for assigning SRv6 Locators to SRv6 Segment Endpoint Nodes through the Dynamic Host Configuration Protocol for IPv6 (DHCPv6).

SRv6ネットワークでは、各SRv6セグメントエンドポイントノードにSRv6ロケーターを割り当てる必要があり、セグメント識別子（SID）はこのSRv6ロケーターのアドレス空間内で生成されます。この文書は、Dynamic Host Configuration Protocol for IPv6（DHCPv6）を通じて、SRv6セグメントエンドポイントノードにSRv6ロケーターを割り当てる方法について説明します。

1. Introduction

1. はじめに

The Segment Routing (SR) architecture [RFC8402] specifies how a node can steer a packet using an ordered list of instructions called "segments". These segments are identified using segment identifiers (SIDs).

セグメントルーティング（SR）アーキテクチャー[RFC8402]は、ノードが「セグメント」と呼ばれる命令の順序付きリストを使用してパケットを誘導する方法を規定しています。これらのセグメントは、セグメント識別子（SID）を使用して識別されます。

SR can be instantiated on the IPv6 data plane using either the Segment Routing Header (SRH) defined in [RFC8754] or compressed segment lists defined in [RFC9800]. SR instantiation on the IPv6 data plane is referred to as SRv6.

SRは、[RFC8754]で定義されているセグメントルーティングヘッダー（SRH）または[RFC9800]で定義されている圧縮セグメントリストのいずれかを使用して、IPv6データプレーン上でインスタンス化できます。IPv6データプレーン上でのSRのインスタンス化はSRv6と呼ばれます。

[RFC8986] introduces the SRv6 Network Programming concept and specifies the base set of SRv6 behaviors.

[RFC8986]は、SRv6ネットワークプログラミングの概念を導入し、SRv6の振る舞いの基本セットを規定しています。

In an SRv6 network, each SRv6 Segment Endpoint Node must be assigned an SRv6 Locator, and SIDs are generated within the address space of this SRv6 Locator. This document describes a method for assigning SRv6 Locators to SRv6 Segment Endpoint Nodes through the Dynamic Host Configuration Protocol for IPv6 (DHCPv6).

SRv6ネットワークでは、各SRv6セグメントエンドポイントノードにSRv6ロケーターを割り当てる必要があり、SIDはこのSRv6ロケーターのアドレス空間内で生成されます。この文書は、Dynamic Host Configuration Protocol for IPv6（DHCPv6）を通じて、SRv6セグメントエンドポイントノードにSRv6ロケーターを割り当てる方法について説明します。

3. Motivation

3. 動機

As shown in Figure 1, in the IP backbone network, access network devices are deployed for access users in different regions. This deployment assumes that all of the relevant components in Figure 1 are part of a single trusted SR domain. The Customer Premises Equipment (CPE) must be managed by the operator providing services or by a trusted partner. If the CPE is located within the customer premises, it must ensure that the device itself and its ports are under the same operator's administrative domain; otherwise, security risks may arise.

Figure 1に示すように、IPバックボーンネットワークでは、さまざまな地域のアクセスユーザーのためにアクセスネットワークデバイスが展開されています。この展開では、Figure 1の関連するすべてのコンポーネントが、単一の信頼されたSRドメインの一部であることを前提としています。顧客宅内機器（CPE）は、サービスを提供するオペレーターまたは信頼されたパートナーによって管理されなければなりません。CPEが顧客の宅内に設置されている場合は、デバイス自体とそのポートが同じオペレーターの管理ドメインの下にあることを保証しなければなりません。そうでない場合、セキュリティー上のリスクが生じる可能性があります。

CPEs for access users are connected to the local metropolitan area network (MAN) in various ways. CPEs are responsible for assigning addresses to access users by requesting DHCPv6 Prefix Delegation (PD) from a DHCPv6 server, as specified in Section 6.3 of [RFC9915]. [RFC7084] and [RFC7368] describe such use in detail. The DHCPv6 server is usually enabled on or relayed by the Broadband Remote Access Server (BRAS).

アクセスユーザーのCPEは、さまざまな方法でローカルのメトロポリタンエリアネットワーク（MAN）に接続されます。CPEは、[RFC9915]のSection 6.3で規定されているように、DHCPv6サーバーにDHCPv6プレフィックス委任（PD）をリクエストすることで、アクセスユーザーにアドレスを割り当てる責任を負います。[RFC7084]と[RFC7368]は、このような使用法について詳しく説明しています。DHCPv6サーバーは通常、ブロードバンドリモートアクセスサーバー（BRAS）上で有効化されるか、BRASによって中継されます。

After the DHCPv6 server allocates any delegated prefix, the BRAS will add a network route corresponding to the delegated prefix to a local routing table and distribute the network route to the upstream routers.

DHCPv6サーバーが委任されたプレフィックスを割り当てた後、BRASは、委任されたプレフィックスに対応するネットワークルートをローカルのルーティングテーブルに追加し、そのネットワークルートを上流のルーターに配布します。

In this network, operators hope to achieve interconnection between access users through CPE-to-CPE SRv6 tunnels. Taking the service traffic from Host1 to Host2 as an example, CPE1 is the SRv6 ingress node and CPE2 is the SRv6 egress node. The SRv6 Locator should be configured on the CPEs. Other devices within the operator's network learn the SRv6 Locator routes of the CPEs.

このネットワークにおいて、オペレーターは、CPE間のSRv6トンネルを通じてアクセスユーザー間の相互接続を実現したいと考えています。Host1からHost2へのサービストラフィックを例にとると、CPE1がSRv6の入口ノードであり、CPE2がSRv6の出口ノードです。SRv6ロケーターはCPEに設定されるべきです。オペレーターのネットワーク内の他のデバイスは、CPEのSRv6ロケーターのルートを学習します。

At the same time, SRv6 policies need to be configured on CPEs to steer the service traffic between CPEs to the specified SRv6 forwarding path. The SRv6 policy can be manually configured statically (via command-line interface (CLI), the Network Configuration Protocol (NETCONF), YANG, APIs, etc.).

同時に、CPE間のサービストラフィックを指定されたSRv6転送パスに誘導するために、CPEにSRv6ポリシーを設定する必要があります。SRv6ポリシーは、手動で静的に（コマンドラインインターフェース（CLI）、Network Configuration Protocol（NETCONF）、YANG、APIなどを介して）設定できます。

This document proposes a method for allocating SRv6 Locators to CPE via DHCPv6 and distributing SRv6 Locator routes using the DHCPv6 workflow. This approach simplifies network operation and maintains consistency with existing IPv6 address allocation mechanisms already deployed in such networks.

この文書は、DHCPv6を介してCPEにSRv6ロケーターを割り当て、DHCPv6のワークフローを使用してSRv6ロケーターのルートを配布する方法を提案します。このアプローチにより、ネットワークの運用が簡素化され、そのようなネットワークですでに展開されている既存のIPv6アドレス割り当てメカニズムとの一貫性が保たれます。

4. DHCPv6 Extensions

4. DHCPv6の拡張

4.1. Identity Association for SRv6 Locator Option

4.1. SRv6ロケーターのためのIdentity Associationオプション

The Identity Association for SRv6 Locator (IA_SRV6_LOCATOR) option is used to carry an IA_SRV6_LOCATOR, the parameters associated with the IA_SRV6_LOCATOR, and the SRv6 Locator associated with the IA_SRV6_LOCATOR.

Identity Association for SRv6 Locator（IA_SRV6_LOCATOR）オプションは、IA_SRV6_LOCATOR、IA_SRV6_LOCATORに関連するパラメーター、およびIA_SRV6_LOCATORに関連するSRv6ロケーターを運ぶために使用されます。

The IA_SRV6_LOCATOR option can be carried in DHCPv6 Solicit, Advertise, Request, Reply, Renew, Release, and Rebind messages.

IA_SRV6_LOCATORオプションは、DHCPv6のSolicit、Advertise、Request、Reply、Renew、Release、およびRebindメッセージで運ぶことができます。

The format of the IA_SRV6_LOCATOR option is:
IA_SRV6_LOCATORオプションの形式は次のとおりです：

Where:

ここで：

Option-Code:
OPTION_IA_SRV6_LOCATOR (149), the option code for the Identity Association for SRv6 Locator option.
Option-Len:
12 + the length of the IA_SRV6_LOCATOR-Options field in octets.
IAID:
The unique identifier for this IA_SRV6_LOCATOR. The IAID MUST be unique among the identifiers for all of this client's IA_SRV6_LOCATORs. The number space for IA_SRV6_LOCATOR IAIDs is separate from the number space for other IA option types. A 4-octet field containing an unsigned integer.
T1:
The time interval after which the client should contact the server from which the SRv6 Locators in the IA_SRV6_LOCATOR were obtained to extend the lifetimes of the SRv6 Locators to the IA_SRV6_LOCATOR. T1 is a time duration relative to the message reception time expressed in units of seconds. A 4-octet field containing an unsigned integer.
T2:
The time interval after which the client should contact any available server to extend the lifetimes of the SRv6 Locators assigned to the IA_SRV6_LOCATOR. T2 is a time duration relative to the message reception time expressed in units of seconds. A 4-octet field containing an unsigned integer.
IA_SRV6_LOCATOR-Options:
Options associated with this IA_SRV6_LOCATOR. A variable-length field (12 octets less than the value in the Option-Len field).
Option-Code:

T1:
クライアントが、IA_SRV6_LOCATOR内のSRv6ロケーターの有効期間を延長するために、IA_SRV6_LOCATOR内のSRv6ロケーターを取得したサーバーに連絡すべき時間間隔。T1は、メッセージの受信時刻からの相対的な時間であり、秒単位で表されます。符号なし整数を含む4オクテットのフィールドです。
T2:
クライアントが、IA_SRV6_LOCATORに割り当てられたSRv6ロケーターの有効期間を延長するために、利用可能な任意のサーバーに連絡すべき時間間隔。T2は、メッセージの受信時刻からの相対的な時間であり、秒単位で表されます。符号なし整数を含む4オクテットのフィールドです。
IA_SRV6_LOCATOR-Options:
このIA_SRV6_LOCATORに関連するオプション。可変長のフィールドです（Option-Lenフィールドの値より12オクテット少ない）。

The IA_SRV6_LOCATOR-Options field encapsulates those options that are specific to this IA_SRV6_LOCATOR. For example, all of the IA Locator options (see Section 4.2) carrying the SRv6 Locators associated with this IA_SRV6_LOCATOR are in the IA_SRV6_LOCATOR-Options field.

IA_SRV6_LOCATOR-Optionsフィールドは、このIA_SRV6_LOCATORに固有のオプションをカプセル化します。たとえば、このIA_SRV6_LOCATORに関連するSRv6ロケーターを運ぶすべてのIA Locatorオプション（Section 4.2を参照）は、IA_SRV6_LOCATOR-Optionsフィールドにあります。

An IA_SRV6_LOCATOR option may only appear in the options area of a DHCP message. A DHCP message may contain multiple IA_SRV6_LOCATOR options (though each must have a unique IAID).

IA_SRV6_LOCATORオプションは、DHCPメッセージのオプション領域にのみ現れることができます。DHCPメッセージには、複数のIA_SRV6_LOCATORオプションが含まれる場合があります（ただし、それぞれが一意なIAIDを持たなければなりません）。

The status of any operations involving this IA_SRV6_LOCATOR is indicated in a Status Code option (see Section 21.13 of [RFC9915]) in the IA_SRV6_LOCATOR-Options field.

このIA_SRV6_LOCATORに関係する操作のステータスは、IA_SRV6_LOCATOR-Optionsフィールド内のStatus Codeオプション（[RFC9915]のSection 21.13を参照）で示されます。

Note that an IA_SRV6_LOCATOR has no explicit "lifetime" or "lease length" of its own. When the valid lifetimes of all of the SRv6 Locators in an IA_SRV6_LOCATOR have expired, the IA_SRV6_LOCATOR can be considered as having expired. The T1 and T2 fields are included to give the server explicit control over when a client should contact the server about a specific IA_SRV6_LOCATOR.

IA_SRV6_LOCATORには、それ自体の明示的な「有効期間（lifetime）」や「リース期間（lease length）」がないことに注意してください。IA_SRV6_LOCATOR内のすべてのSRv6ロケーターの有効期間が満了した場合、そのIA_SRV6_LOCATORは満了したとみなすことができます。T1フィールドとT2フィールドは、特定のIA_SRV6_LOCATORについてクライアントがいつサーバーに連絡すべきかをサーバーが明示的に制御できるようにするために含まれています。

In a message sent by a client to a server, the T1 and T2 fields SHOULD be set to 0. The server MUST ignore any values in these fields in messages received from a client.

クライアントからサーバーに送信されるメッセージでは、T1フィールドとT2フィールドは0に設定されるべきです（SHOULD）。サーバーは、クライアントから受信したメッセージ内のこれらのフィールドの値を無視しなければなりません（MUST）。

In a message sent by a server to a client, the client MUST use the values in the T1 and T2 fields for the T1 and T2 timers, unless values in those fields are 0. The values in the T1 and T2 fields are the number of seconds until T1 and T2.

サーバーからクライアントに送信されるメッセージでは、T1フィールドとT2フィールドの値が0でない限り、クライアントはそれらの値をT1タイマーとT2タイマーに使用しなければなりません（MUST）。T1フィールドとT2フィールドの値は、T1とT2までの秒数です。

The server selects the T1 and T2 times to allow the client to extend the lifetimes of any SRv6 Locators in the IA_SRV6_LOCATOR before the lifetimes expire, even if the server is unavailable for some short period of time. Recommended values for T1 and T2 are 0.5 and 0.8 times the shortest preferred lifetime of the SRv6 Locators in the IA_SRV6_LOCATOR that the server is willing to extend, respectively. If the time at which the SRv6 Locators in an IA_SRV6_LOCATOR are to be renewed is to be left to the discretion of the client, the server sets T1 and T2 to 0. The client MUST follow the rules defined in Section 14.2 of [RFC9915].

サーバーは、短期間サーバーが利用できない場合でも、有効期間が満了する前にクライアントがIA_SRV6_LOCATOR内のSRv6ロケーターの有効期間を延長できるように、T1とT2の時間を選択します。T1とT2の推奨値は、それぞれ、サーバーが延長する意思のあるIA_SRV6_LOCATOR内のSRv6ロケーターの最短の推奨有効期間の0.5倍と0.8倍です。IA_SRV6_LOCATOR内のSRv6ロケーターを更新する時刻をクライアントの裁量に任せる場合、サーバーはT1とT2を0に設定します。クライアントは、[RFC9915]のSection 14.2で定義されている規則に従わなければなりません（MUST）。

If a client receives an IA_SRV6_LOCATOR with T1 greater than T2 and both T1 and T2 are greater than 0, the client discards the IA_SRV6_LOCATOR option and processes the remainder of the message as though the server had not included the IA_SRV6_LOCATOR option.

クライアントが、T1がT2より大きく、かつT1とT2の両方が0より大きいIA_SRV6_LOCATORを受信した場合、クライアントはIA_SRV6_LOCATORオプションを破棄し、サーバーがIA_SRV6_LOCATORオプションを含めなかったかのようにメッセージの残りの部分を処理します。

4.2. IA Locator Option

4.2. IA Locatorオプション

SRv6 SID Locator Block (LB) length in bits. A 1-octet unsigned integer.
LN-Len:
SRv6 SID Locator Node (LN) length in bits. A 1-octet unsigned integer.
Fun-Len:
SRv6 SID function (FUNCT) length in bits. A 1-octet unsigned integer.
Arg-Len:
SRv6 SID arguments (ARG) length in bits. A 1-octet unsigned integer.
SRv6-Locator:
0-16 octets. This field encodes the SRv6 Locator. The SRv6 Locator is encoded in the minimal number of octets for the SRv6 SID Locator length that is LB-Len plus LN-Len. Trailing bits MUST be set to zero and ignored when received.
IALocator-Options:
Options associated with this SRv6 Locator. A variable-length field (determined by subtracting the length of SRv6-Locator from Option-Len minus 12). The status code NoSRv6LocatorAvail indicates the server has no locators available to assign to the IA_SRV6_LOCATOR(s).
Option-Code:
OPTION_IALOCATOR（150）。IA Locatorオプションのオプションコード。
Option-Len:
16 + SRv6-Locatorの長さ + IALocator-Optionsフィールドのオクテット単位の長さ。
Preferred-lifetime:
オプション内のSRv6ロケーターの推奨有効期間（秒単位）。0xffffffffの値は「無限」を表します（[RFC9915]のSection 7.7を参照）。符号なし整数を含む4オクテットのフィールドです。
Valid-lifetime:
オプション内のSRv6ロケーターの有効期間（秒単位）。0xffffffffの値は「無限」を表します。符号なし整数を含む4オクテットのフィールドです。
Algorithm:
1オクテットの符号なし整数。SIDの割り当て元となるSRv6ロケーターに関連付けられたアルゴリズム。アルゴリズムの値は「IGP Algorithm Types」レジストリー[RFC8665]で定義されています。[RFC9350]も参照してください。
Reserved:
3オクテットの符号なし整数。0に設定されなければなりません（MUST）。受信時には無視されます。
LB-Len:
SRv6 SIDのロケーターブロック（LB）のビット単位の長さ。1オクテットの符号なし整数です。
LN-Len:
SRv6 SIDのロケーターノード（LN）のビット単位の長さ。1オクテットの符号なし整数です。
Fun-Len:
SRv6 SIDの関数（FUNCT）のビット単位の長さ。1オクテットの符号なし整数です。
Arg-Len:
SRv6 SIDの引数（ARG）のビット単位の長さ。1オクテットの符号なし整数です。
SRv6-Locator:
0～16オクテット。このフィールドはSRv6ロケーターをエンコードします。SRv6ロケーターは、LB-LenとLN-Lenの和であるSRv6 SIDのロケーター長に必要な最小のオクテット数でエンコードされます。末尾のビットは0に設定されなければなりません（MUST）。受信時には無視されます。
IALocator-Options:
このSRv6ロケーターに関連するオプション。可変長のフィールドです（Option-Lenから12を引いた値からSRv6-Locatorの長さを引いて決定されます）。ステータスコードNoSRv6LocatorAvailは、IA_SRV6_LOCATORに割り当てられるロケーターがサーバーにないことを示します。

The SRv6 SID Locator length (LOC-Len) is LB-Len plus LN-Len.

SRv6 SIDのロケーター長（LOC-Len）は、LB-LenとLN-Lenの和です。

The sum of LB-Len, LN-Len, Fun-Len, and Arg-Len MUST NOT exceed 128 bits. The sum of LB-Len and LN-Len MUST NOT be zero. If either of these conditions are violated, the IA_SRV6_LOCATOR option MUST be marked as invalid, and the remainder of the message SHOULD be processed as if the packet did not include this option.

LB-Len、LN-Len、Fun-Len、およびArg-Lenの合計は、128ビットを超えてはなりません（MUST NOT）。LB-LenとLN-Lenの合計は、0であってはなりません（MUST NOT）。これらの条件のいずれかに違反した場合、IA_SRV6_LOCATORオプションは無効としてマークされなければなりません（MUST）。また、メッセージの残りの部分は、パケットにこのオプションが含まれていなかったかのように処理されるべきです（SHOULD）。

The values in the Preferred-lifetime and Valid-lifetime fields are the number of seconds remaining in each lifetime. The value of 0xffffffff for the preferred lifetime or the valid lifetime is taken to mean "infinity" and should be used carefully. The details about the use of lifetime values for assigned SRv6 Locators are the same as the ones specified for PD in Section 18.2.10.1 of [RFC9915].

Preferred-lifetimeフィールドとValid-lifetimeフィールドの値は、それぞれの有効期間の残りの秒数です。推奨有効期間または有効期間の0xffffffffの値は「無限」を意味するものとみなされ、慎重に使用すべきです。割り当てられたSRv6ロケーターに対する有効期間の値の使用に関する詳細は、[RFC9915]のSection 18.2.10.1でPDについて規定されているものと同じです。

An IA Locator option may appear only in an IA_SRV6_LOCATOR option. More than one IA Locator option can appear in a single IA_SRV6_LOCATOR option.

IA Locatorオプションは、IA_SRV6_LOCATORオプション内にのみ現れることができます。単一のIA_SRV6_LOCATORオプションに、複数のIA Locatorオプションが現れることができます。

The status of any operations involving this IA_SRV6_LOCATOR option is indicated in a Status Code option (see Section 21.13 of [RFC9915]) in the IALocator-Options field.

このIA_SRV6_LOCATORオプションに関係する操作のステータスは、IALocator-Optionsフィールド内のStatus Codeオプション（[RFC9915]のSection 21.13を参照）で示されます。

5. Process of Assigning the SRv6 Locator

5. SRv6ロケーターの割り当てプロセス

5.1. Procedure of the SRv6 Locator

5.1. SRv6ロケーターの手順

Consistent with the PD mechanism [RFC9915], the DHCPv6 client obtains an SRv6 Locator via DHCPv6. The key message exchanges involved are Solicit, Request, Advertise, and Reply. Once the DHCPv6 server assigns an SRv6 Locator to the DHCPv6 client, it automatically adds the associated SRv6 Locator routes.

PDメカニズム[RFC9915]と同様に、DHCPv6クライアントはDHCPv6を介してSRv6ロケーターを取得します。関係する主要なメッセージ交換は、Solicit、Request、Advertise、およびReplyです。DHCPv6サーバーは、DHCPv6クライアントにSRv6ロケーターを割り当てると、関連するSRv6ロケーターのルートを自動的に追加します。

Figure 4 illustrates the process of SRv6 Locator allocation through DHCPv6.

Figure 4は、DHCPv6を通じたSRv6ロケーターの割り当てのプロセスを示しています。

As specified in Section 18.2.1 of [RFC9915], the DHCPv6 client sends a Solicit message containing an IA_SRV6_LOCATOR option to request a locator. The client may include its preferred locator value within the IA_SRV6_LOCATOR option.

[RFC9915]のSection 18.2.1で規定されているように、DHCPv6クライアントは、ロケーターをリクエストするためにIA_SRV6_LOCATORオプションを含むSolicitメッセージを送信します。クライアントは、IA_SRV6_LOCATORオプション内に希望するロケーターの値を含めることができます。

The DHCPv6 server processes the Solicit message, assigns a locator to the client, and returns the allocated locator in an Advertise message with the IA_SRV6_LOCATOR option.

DHCPv6サーバーはSolicitメッセージを処理し、クライアントにロケーターを割り当て、割り当てたロケーターをIA_SRV6_LOCATORオプション付きのAdvertiseメッセージで返します。

As specified in Section 18.2.2 of [RFC9915], upon receiving the Advertise message, the client accepts the assigned locator and sends a Request message with the IA_SRV6_LOCATOR option to confirm the requested locator.

[RFC9915]のSection 18.2.2で規定されているように、Advertiseメッセージを受信すると、クライアントは割り当てられたロケーターを受け入れ、リクエストしたロケーターを確認するためにIA_SRV6_LOCATORオプション付きのRequestメッセージを送信します。

The server processes the Request message, confirms the locator assignment, and responds with a Reply message containing the IA_SRV6_LOCATOR option with the allocated locator.

サーバーはRequestメッセージを処理し、ロケーターの割り当てを確定し、割り当てたロケーターを含むIA_SRV6_LOCATORオプション付きのReplyメッセージで応答します。

As described in Section 18.2.4 of [RFC9915], the client periodically sends a Renew message with the IA_SRV6_LOCATOR option to refresh the lease. The server processes the Renew message, updates the lease, and replies with a Reply message containing the IA_SRV6_LOCATOR option.

[RFC9915]のSection 18.2.4で説明されているように、クライアントはリースを更新するために、IA_SRV6_LOCATORオプション付きのRenewメッセージを定期的に送信します。サーバーはRenewメッセージを処理し、リースを更新して、IA_SRV6_LOCATORオプションを含むReplyメッセージで応答します。

As described in Section 18.2.5 of [RFC9915], if the client does not receive a Reply message before the T2 timer expires, it sends a Rebind message with the IA_SRV6_LOCATOR option to attempt lease renewal.

[RFC9915]のSection 18.2.5で説明されているように、T2タイマーが満了する前にクライアントがReplyメッセージを受信しなかった場合、クライアントはリースの更新を試みるために、IA_SRV6_LOCATORオプション付きのRebindメッセージを送信します。

If the server responds with a Reply message, the client retains its allocated locator.

サーバーがReplyメッセージで応答した場合、クライアントは割り当てられたロケーターを保持します。

If no response is received, the client considers the lease expired and restarts the process by sending a new Solicit message.

応答を受信しなかった場合、クライアントはリースが満了したとみなし、新しいSolicitメッセージを送信してプロセスを再開します。

As described in Section 18.2.7 of [RFC9915], if the client is about to go offline, it sends a Release message with the IA_SRV6_LOCATOR option to relinquish the locator.

[RFC9915]のSection 18.2.7で説明されているように、クライアントがオフラインになろうとしている場合、クライアントはロケーターを放棄するためにIA_SRV6_LOCATORオプション付きのReleaseメッセージを送信します。

Upon receiving a valid Release message, and when the SRv6 Locator in the message is valid, the server MUST remove the lease and free the locator, making it available for allocation to other clients. For detailed processing procedures, refer to Section 18.3.7 of [RFC9915].

有効なReleaseメッセージを受信し、かつメッセージ内のSRv6ロケーターが有効である場合、サーバーはリースを削除し、ロケーターを解放して他のクライアントに割り当てられるようにしなければなりません（MUST）。詳細な処理手順については、[RFC9915]のSection 18.3.7を参照してください。

5.2. DHCPv6 Client Behavior

5.2. DHCPv6クライアントの動作

A client uses the Solicit message to discover DHCPv6 servers configured to assign leases or return other configuration parameters on the link to which the client is attached.

クライアントは、クライアントが接続されているリンク上で、リースを割り当てたり他の設定パラメーターを返したりするように設定されたDHCPv6サーバーを発見するために、Solicitメッセージを使用します。

A client uses Request, Renew, Rebind, Release, and Decline messages during the normal lifecycle of SRv6 Locator assignment.

クライアントは、SRv6ロケーターの割り当ての通常のライフサイクルの間に、Request、Renew、Rebind、Release、およびDeclineメッセージを使用します。

In a message sent by a client to a server, the Preferred-lifetime and Valid-lifetime fields SHOULD be set to 0. The server MUST ignore any received values in these lifetime fields.

クライアントからサーバーに送信されるメッセージでは、Preferred-lifetimeフィールドとValid-lifetimeフィールドは0に設定されるべきです（SHOULD）。サーバーは、これらの有効期間のフィールドで受信した値を無視しなければなりません（MUST）。

The client MUST NOT send an IA_SRV6_LOCATOR option with 0 in the LB-Len or LN-Len fields. The client MAY send non-zero values in the LB-Len and LN-Len fields and the unspecified value (::) in the SRv6-Locator field to indicate a preference for the size of the SRv6 Locator to be assigned. The LOC-Len (LB-Len + LN-Len) hint provided by a client is similar to the prefix-length hint in an IA_PD. Clients and servers are expected to follow the guidance provided in [RFC8168].

クライアントは、LB-LenフィールドまたはLN-Lenフィールドが0のIA_SRV6_LOCATORオプションを送信してはなりません（MUST NOT）。クライアントは、割り当てられるSRv6ロケーターのサイズに関する希望を示すために、LB-LenフィールドとLN-Lenフィールドに0以外の値を、SRv6-Locatorフィールドに未指定の値（::）を入れて送信してもよいです（MAY）。クライアントが提供するLOC-Len（LB-Len + LN-Len）のヒントは、IA_PDにおけるプレフィックス長のヒントに似ています。クライアントとサーバーは、[RFC8168]で提供されているガイダンスに従うことが期待されます。

The client MUST discard any SRv6 Locators for which the preferred lifetime is greater than the valid lifetime.

クライアントは、推奨有効期間が有効期間より大きいSRv6ロケーターを破棄しなければなりません（MUST）。

The process of requesting an SRv6 Locator is the same as that of requesting prefixes. When requesting an SRv6 Locator, the DHCPv6 client sends a Request message carrying the IA_SRV6_LOCATOR option to the DHCPv6 server.

SRv6ロケーターをリクエストするプロセスは、プレフィックスをリクエストするプロセスと同じです。SRv6ロケーターをリクエストする際、DHCPv6クライアントは、IA_SRV6_LOCATORオプションを運ぶRequestメッセージをDHCPv6サーバーに送信します。

Upon the receipt of a valid Reply message with the IA_SRV6_LOCATOR option in response to a Solicit with a Rapid Commit option, Request, Renew, or Rebind message, the client MUST process the Reply message according to the requirements of Section 18.2.10 of [RFC9915] and configure the assigned SRv6 Locator in the client device automatically.

Rapid Commitオプション付きのSolicit、Request、Renew、またはRebindメッセージに応答して、IA_SRV6_LOCATORオプション付きの有効なReplyメッセージを受信すると、クライアントは[RFC9915]のSection 18.2.10の要件に従ってReplyメッセージを処理し、割り当てられたSRv6ロケーターをクライアントデバイスに自動的に設定しなければなりません（MUST）。

DHCP allows a client to obtain multiple addresses as specified in Section 6.5 of [RFC9915]. The same principle applies to SRv6 Locator assignment. In scenarios requiring multiple allocations (e.g., when multiple SRv6 Locators are needed for distinct services, such as best-effort and low-latency traffic, each with a different algorithm), the allocation policy between the DHCPv6 client and DHCPv6 server MUST remain consistent. After obtaining the SRv6 Locator assigned by the DHCPv6 server, how to assign local SRv6 SIDs based on this SRv6 Locator, how to use multiple assigned SRv6 Locators, and how to advertise these SRv6 SIDs to the rest of the network are not within the scope of this document. However, and consistent with the guidance in Section 16 of [RFC7227], the client MUST NOT make any assumption about the ordering of locators or infer any service logic from these locators.

DHCPでは、[RFC9915]のSection 6.5で規定されているように、クライアントが複数のアドレスを取得できます。同じ原則がSRv6ロケーターの割り当てにも適用されます。複数の割り当てを必要とするシナリオ（たとえば、ベストエフォートのトラフィックと低遅延のトラフィックなど、それぞれ異なるアルゴリズムを持つ別個のサービスのために複数のSRv6ロケーターが必要な場合）では、DHCPv6クライアントとDHCPv6サーバーの間の割り当てポリシーは一貫していなければなりません（MUST）。DHCPv6サーバーによって割り当てられたSRv6ロケーターを取得した後、このSRv6ロケーターに基づいてローカルのSRv6 SIDをどのように割り当てるか、割り当てられた複数のSRv6ロケーターをどのように使用するか、およびこれらのSRv6 SIDをネットワークの他の部分にどのように広告するかは、この文書の範囲外です。ただし、[RFC7227]のSection 16のガイダンスと整合して、クライアントはロケーターの順序について何らかの仮定をしたり、これらのロケーターから何らかのサービスロジックを推測したりしてはなりません（MUST NOT）。

The client uses the SRv6 Locators and associated information from any IAs that do not contain a Status Code option with the NoSRv6LocatorAvail status code. The client MAY include the IAs for which it received the NoSRv6LocatorAvail status code, with no SRv6 Locators, in subsequent Renew and Rebind messages sent to the server, to retry obtaining the SRv6 Locators for these IAs.

クライアントは、NoSRv6LocatorAvailステータスコードを持つStatus Codeオプションを含まない任意のIAから、SRv6ロケーターと関連情報を使用します。クライアントは、NoSRv6LocatorAvailステータスコードを受信したIAについて、それらのIAのSRv6ロケーターの取得を再試行するために、サーバーに送信する後続のRenewメッセージとRebindメッセージに、SRv6ロケーターなしでそれらのIAを含めてもよいです（MAY）。

To extend the preferred and valid lifetimes for the assigned SRv6 Locators or obtain new assigned SRv6 Locators, the client sends a Renew/Rebind message to the server with the IA_SRV6_LOCATOR option as specified in Sections 18.2.4 and 18.2.5 of [RFC9915].

割り当てられたSRv6ロケーターの推奨有効期間と有効期間を延長するため、または新しく割り当てられるSRv6ロケーターを取得するために、クライアントは、[RFC9915]のセクション18.2.4とセクション18.2.5で規定されているように、IA_SRV6_LOCATORオプション付きのRenew/Rebindメッセージをサーバーに送信します。

If the client no longer uses the SRv6 Locator, the client can actively send a Release message to notify the server to reclaim the SRv6 Locator and delete the corresponding SRv6 Locator. The client MUST include options containing the IAs for the SRv6 Locators it is releasing in the IA_SRV6_LOCATOR-Options field of the IA_SRV6_LOCATOR option.

クライアントがSRv6ロケーターをもう使用しない場合、クライアントは、SRv6ロケーターを回収して対応するSRv6ロケーターを削除するようサーバーに通知するために、Releaseメッセージを能動的に送信できます。クライアントは、解放するSRv6ロケーターのIAを含むオプションを、IA_SRV6_LOCATORオプションのIA_SRV6_LOCATOR-Optionsフィールドに含めなければなりません（MUST）。

A client can explicitly request multiple SRv6 Locator prefixes by sending multiple IA_SRV6_LOCATOR options. A client can send multiple IA_SRV6_LOCATOR options in its initial transmissions. Alternatively, it can send an extra Request message with additional new IA_SRV6_LOCATOR options (or include them in a Renew message).

クライアントは、複数のIA_SRV6_LOCATORオプションを送信することで、複数のSRv6ロケーターのプレフィックスを明示的にリクエストできます。クライアントは、最初の送信で複数のIA_SRV6_LOCATORオプションを送信できます。あるいは、追加の新しいIA_SRV6_LOCATORオプションを含む追加のRequestメッセージを送信する（またはそれらをRenewメッセージに含める）こともできます。

DHCP allows a client to request new SRv6 Locators to be assigned by sending additional new IA_SRV6_LOCATOR options. However, a typical operator usually prefers to assign a single, larger prefix. In most deployments, it is RECOMMENDED that the client request a larger SRv6 Locator in its initial transmissions rather than request additional SRv6 Locators later on.

DHCPでは、クライアントが追加の新しいIA_SRV6_LOCATORオプションを送信することで、新しいSRv6ロケーターの割り当てをリクエストできます。しかし、一般的なオペレーターは通常、単一のより大きなプレフィックスを割り当てることを好みます。ほとんどの展開では、クライアントは、後から追加のSRv6ロケーターをリクエストするのではなく、最初の送信でより大きなSRv6ロケーターをリクエストすることが推奨されます（RECOMMENDED）。

5.3. DHCPv6 Server Behavior

5.3. DHCPv6サーバーの動作

When the server receives a valid Request message or a valid Solicit message with a Rapid Commit option, the server creates the bindings for that client according to the server's policy and configuration information and records the IAs and other information requested by the client.

サーバーは、有効なRequestメッセージ、またはRapid Commitオプション付きの有効なSolicitメッセージを受信すると、サーバーのポリシーと設定情報に従ってそのクライアントのバインディングを作成し、クライアントがリクエストしたIAやその他の情報を記録します。

The DHCPv6 server treats the SRv6 Locator as the prefix of the prefix pool. Upon the receipt of the IA_SRV6_LOCATOR option, the server searches the SRv6 Locator prefix pool and allocates appropriate SRv6 Locators for the client.

DHCPv6サーバーは、SRv6ロケーターをプレフィックスプールのプレフィックスとして扱います。IA_SRV6_LOCATORオプションを受信すると、サーバーはSRv6ロケーターのプレフィックスプールを探索し、クライアントに適切なSRv6ロケーターを割り当てます。

If there is an assignable SRv6 Locator, the server creates the SRv6 Locator binding entry for that client according to the server's policy and configuration information and constructs a Reply message that includes an IA_SRV6_LOCATOR option with the SRv6 Locator information (including LB-Len, LN-Len, Fun-Len, and Arg-Len) assigned to the client.

割り当て可能なSRv6ロケーターがある場合、サーバーは、サーバーのポリシーと設定情報に従ってそのクライアントのSRv6ロケーターのバインディングエントリーを作成し、クライアントに割り当てたSRv6ロケーターの情報（LB-Len、LN-Len、Fun-Len、およびArg-Lenを含む）を持つIA_SRV6_LOCATORオプションを含むReplyメッセージを構築します。

The IA_SRV6_LOCATOR option is filled with the SRv6 Locator information assigned to the client. The IA_SRV6_LOCATOR option populates the LB-Len, LN-Len, Fun-Len, and Arg-Len fields.

IA_SRV6_LOCATORオプションには、クライアントに割り当てられたSRv6ロケーターの情報が格納されます。IA_SRV6_LOCATORオプションは、LB-Len、LN-Len、Fun-Len、およびArg-Lenのフィールドを埋めます。

Upon receiving a Release message from the client or when the SRv6 Locator lease expires, the server reclaims the SRv6 Locator prefix resource and deletes the corresponding binding entry.

クライアントからReleaseメッセージを受信したとき、またはSRv6ロケーターのリースが満了したとき、サーバーはSRv6ロケーターのプレフィックスのリソースを回収し、対応するバインディングエントリーを削除します。

For any IA_SRV6_LOCATOR option in the Request message to which the server cannot assign any SRv6 Locators, the server MUST return the IA_SRV6_LOCATOR option in the Reply message with no SRv6 Locator prefixes in the IA_SRV6_LOCATOR and with a Status Code option containing status code NoSRv6LocatorAvail in the IA_SRV6_LOCATOR.

Requestメッセージ内のIA_SRV6_LOCATORオプションのうち、サーバーがSRv6ロケーターを割り当てることのできないものについて、サーバーは、IA_SRV6_LOCATOR内にSRv6ロケーターのプレフィックスを含まず、かつIA_SRV6_LOCATOR内にステータスコードNoSRv6LocatorAvailを含むStatus Codeオプションを持つIA_SRV6_LOCATORオプションを、Replyメッセージで返さなければなりません（MUST）。

After receiving a DHCP message with multiple IA_SRV6_LOCATOR options at the same time, whether the server can assign multiple SRv6 Locators to the client depends on the server policy, which is out of scope for this document. Note that the configuration behavior of the server and client SHOULD be consistent (e.g., "clients and servers assign a single locator unless explicitly configured").

複数のIA_SRV6_LOCATORオプションを同時に含むDHCPメッセージを受信した後、サーバーがクライアントに複数のSRv6ロケーターを割り当てられるかどうかはサーバーのポリシーに依存し、この文書の範囲外です。サーバーとクライアントの設定上の振る舞いは一貫しているべきです（SHOULD）（たとえば、「明示的に設定されない限り、クライアントとサーバーは単一のロケーターを割り当てる」）ことに注意してください。

5.4. DHCPv6 Relay Agent Behavior

5.4. DHCPv6リレーエージェントの動作

The allocation of SRv6 Locators to clients that reside on a different link from the server requires a DHCPv6 relay agent. A DHCPv6 relay agent forwards messages containing IA_SRV6_LOCATOR options in the same way as it would relay addresses (i.e., per Sections 19.1.1 and 19.1.2 of [RFC9915]).

サーバーとは異なるリンク上にあるクライアントにSRv6ロケーターを割り当てるには、DHCPv6リレーエージェントが必要です。DHCPv6リレーエージェントは、IA_SRV6_LOCATORオプションを含むメッセージを、アドレスを中継する場合と同じ方法で（つまり、[RFC9915]のセクション19.1.1とセクション19.1.2に従って）転送します。

5.5. Advertisement of the SRv6 Locator Route

5.5. SRv6ロケーターのルートの広告

This section describes the processing of SRv6 Locator routes.

このセクションでは、SRv6ロケーターのルートの処理について説明します。

As shown in Figure 5, when a DHCPv6 Relay or DHCPv6 server receives an SRv6 Locator allocation request from a client, it MAY assign an SRv6 Locator to the client and install a corresponding SRv6 Locator route locally. The next hop of this route SHOULD point to the requesting client. Through this route, the DHCPv6 Relay or DHCPv6 server can access the Host under the DHCPv6 client, while the DHCPv6 Relay or DHCPv6 server MAY then advertise this route via traditional routing protocols (e.g., an IGP) to allow other routers to learn it.

Figure 5に示すように、DHCPv6リレーまたはDHCPv6サーバーは、クライアントからSRv6ロケーターの割り当てリクエストを受信すると、クライアントにSRv6ロケーターを割り当て、対応するSRv6ロケーターのルートをローカルにインストールしてもよいです（MAY）。このルートのネクストホップは、リクエストしたクライアントを指すべきです（SHOULD）。このルートを通じて、DHCPv6リレーまたはDHCPv6サーバーはDHCPv6クライアントの配下にあるホストにアクセスでき、その後、DHCPv6リレーまたはDHCPv6サーバーは、他のルーターがこのルートを学習できるように、従来のルーティングプロトコル（たとえばIGP）を介してこのルートを広告してもよいです（MAY）。

SRv6 Locators with an Algorithm value of zero can be advertised as normal IP prefix reachability information. Conversely, SRv6 Locators with a non-zero Algorithm value MUST be advertised using the Locators TLV as defined in [RFC9352] and [RFC9513].

Algorithmの値が0のSRv6ロケーターは、通常のIPプレフィックスの到達可能性情報として広告できます。逆に、Algorithmの値が0以外のSRv6ロケーターは、[RFC9352]と[RFC9513]で定義されているLocators TLVを使用して広告されなければなりません（MUST）。

Upon receiving an SRv6 Locator release request from the client, the DHCPv6 Relay or DHCPv6 server MUST release the allocated SRv6 Locator, remove the local SRv6 Locator route, and withdraw the previously advertised SRv6 Locator route via traditional routing protocols.

クライアントからSRv6ロケーターの解放リクエストを受信すると、DHCPv6リレーまたはDHCPv6サーバーは、割り当てたSRv6ロケーターを解放し、ローカルのSRv6ロケーターのルートを削除し、以前に広告したSRv6ロケーターのルートを従来のルーティングプロトコルを介して取り消さなければなりません（MUST）。

6. Operational Considerations

6. 運用上の考慮事項

This section outlines some operational considerations for assigning SRv6 Locators through DHCPv6.

このセクションでは、DHCPv6を通じてSRv6ロケーターを割り当てる際の運用上の考慮事項をいくつか概説します。

The SRv6 Locator can be used to allocate SIDs with SR Endpoint Behaviors as defined in [RFC8986] and also to allocate SIDs with the NEXT and REPLACE flavors defined in [RFC9800]. Operators can allocate corresponding SIDs based on the LB and LN lengths of the SRv6 Locator, as well as local policies.

SRv6ロケーターは、[RFC8986]で定義されているSRエンドポイントの振る舞いを持つSIDの割り当てに使用でき、また[RFC9800]で定義されているNEXTフレーバーとREPLACEフレーバーを持つSIDの割り当てにも使用できます。オペレーターは、SRv6ロケーターのLBとLNの長さ、およびローカルポリシーに基づいて、対応するSIDを割り当てることができます。

When processing the SRv6 Locator defined in this document, if an error occurs in packet processing, SRv6 Locator allocation fails, or lease aging is handled, the DHCPv6 client and DHCPv6 server SHOULD log or record these SRv6 Locators as required by local policy.

この文書で定義されたSRv6ロケーターを処理する際に、パケット処理でエラーが発生した場合、SRv6ロケーターの割り当てが失敗した場合、またはリースのエージングが処理された場合、DHCPv6クライアントとDHCPv6サーバーは、ローカルポリシーの要求に応じて、これらのSRv6ロケーターをログに記録または記録すべきです（SHOULD）。

Section 4.4 of [RFC8987] provides necessary functional requirements for operating DHCPv6 relays with PD. These requirements also apply to the allocation of SRv6 Locators in DHCPv6 Relay scenarios.

[RFC8987]のSection 4.4は、PDとともにDHCPv6リレーを運用するために必要な機能要件を提供しています。これらの要件は、DHCPv6リレーのシナリオにおけるSRv6ロケーターの割り当てにも適用されます。

Routing Stability is an additional operational consideration. Network operators may advertise an aggregated route rather than individual prefixes in certain deployments to optimize Routing Information Base (RIB) performance. The withdrawal of specific routes triggered by address releases may lead to a reduction in advertised routes. An alternative approach is to implement a policy that governs this behavior. In such cases, delegating routers will discard packets destined for specific prefixes that are not "delegated" on the customer-facing interface.

ルーティングの安定性も運用上の考慮事項の1つです。ネットワークオペレーターは、ルーティング情報ベース（RIB）の性能を最適化するために、特定の展開では個々のプレフィックスではなく集約されたルートを広告する場合があります。アドレスの解放によって引き起こされる特定のルートの取り消しは、広告されるルートの減少につながる可能性があります。代替のアプローチは、この振る舞いを管理するポリシーを実装することです。そのような場合、委任ルーターは、顧客側のインターフェースで「委任」されていない特定のプレフィックス宛てのパケットを破棄します。

8. Security Considerations

8. セキュリティーに関する考慮事項

See Section 22 of [RFC9915] and Section 23 of [RFC7227] for the DHCP security considerations. See [RFC8200] for the IPv6 security considerations.

DHCPのセキュリティーに関する考慮事項については[RFC9915]のSection 22と[RFC7227]のSection 23を、IPv6のセキュリティーに関する考慮事項については[RFC8200]を参照してください。

As discussed in Section 22 of [RFC9915], "DHCP lacks end-to-end encryption between clients and servers; thus, hijacking, tampering, and eavesdropping attacks are all possible as a result."

[RFC9915]のSection 22で議論されているように、「DHCPにはクライアントとサーバーの間のエンドツーエンドの暗号化がないため、その結果として、ハイジャック、改ざん、および盗聴の攻撃がすべて可能です。」

In some network environments, it is possible to secure the communication between clients and servers, as discussed in Section 22 of [RFC9915].

一部のネットワーク環境では、[RFC9915]のSection 22で議論されているように、クライアントとサーバーの間の通信を保護することが可能です。

If not all parties use this mechanism to obtain an SRv6 Locator from the DHCPv6 server, there is the possibility of the same SRv6 Locator being used by more than one device. Note that this issue could exist on these networks even if DHCP were not used to obtain the SRv6 Locator. A potential mitigation is to partition the available address prefixes, ensuring that different allocation mechanisms draw from non-overlapping pools.

すべての当事者がこのメカニズムを使用してDHCPv6サーバーからSRv6ロケーターを取得するわけではない場合、同じSRv6ロケーターが複数のデバイスで使用される可能性があります。この問題は、SRv6ロケーターの取得にDHCPが使用されていない場合でも、これらのネットワークに存在しうることに注意してください。考えられる緩和策は、利用可能なアドレスプレフィックスを分割し、異なる割り当てメカニズムが重複しないプールから割り当てを行うようにすることです。

Server implementations SHOULD consider configuration options to limit the maximum number of SRv6 Locators to allocate (both in a single request and in total) to a client. However, note that this does not prevent a bad client actor from pretending to be many different clients and consuming all available SRv6 Locators.

サーバーの実装は、クライアントに割り当てるSRv6ロケーターの最大数（単一のリクエストと合計の両方）を制限する設定オプションを検討すべきです（SHOULD）。ただし、これは、悪意のあるクライアントが多数の異なるクライアントになりすまして、利用可能なすべてのSRv6ロケーターを消費することを防げないことに注意してください。

The SR domain is a trusted domain, as defined in Sections 2 and 8.2 of [RFC8402]. Having such a well-defined trust boundary is necessary in order to operate SRv6-based services for internal traffic while preventing any external traffic from accessing or exploiting the SRv6-based services. Care and rigor in IPv6 address allocation for use for SRv6 SID allocations and network infrastructure addresses, as distinct from IPv6 addresses allocated for end users and systems (as illustrated in Section 5.1 of [RFC8754]), can provide the clear distinction between internal and external address space that is required to maintain the integrity and security of the SRv6 domain.

SRドメインは、[RFC8402]のセクション2とセクション8.2で定義されているように、信頼されたドメインです。内部トラフィックのためのSRv6ベースのサービスを運用しつつ、外部トラフィックがSRv6ベースのサービスにアクセスしたりそれを悪用したりすることを防ぐためには、このような明確に定義された信頼境界が必要です。エンドユーザーやシステムに割り当てられるIPv6アドレスとは区別して、SRv6 SIDの割り当てやネットワークインフラストラクチャーのアドレスに使用するためのIPv6アドレスの割り当てを慎重かつ厳密に行うこと（[RFC8754]のSection 5.1に示されているとおり）で、SRv6ドメインの完全性とセキュリティーを維持するために必要な、内部と外部のアドレス空間の明確な区別を提供できます。

When assigning SRv6 Locators to SRv6 Segment Endpoint Nodes using DHCPv6 as specified in this document, DHCPv6 clients and DHCPv6 servers MUST operate within a single trusted SR domain. As a border node device, a DHCPv6 client may reside in customer premises, while the DHCPv6 server is located within the provider network. Although they belong to the same trusted SR domain, the DHCPv6 client MUST implement appropriate traffic filtering capabilities on both its internal and external interfaces, as required by Section 5.1 of [RFC8754].

この文書で規定されているようにDHCPv6を使用してSRv6セグメントエンドポイントノードにSRv6ロケーターを割り当てる場合、DHCPv6クライアントとDHCPv6サーバーは、単一の信頼されたSRドメイン内で動作しなければなりません（MUST）。境界ノードデバイスとして、DHCPv6クライアントは顧客の宅内に存在する場合があり、一方DHCPv6サーバーはプロバイダーのネットワーク内に配置されます。両者は同じ信頼されたSRドメインに属しますが、DHCPv6クライアントは、[RFC8754]のSection 5.1で要求されているように、内部と外部の両方のインターフェースで適切なトラフィックフィルタリング機能を実装しなければなりません（MUST）。
