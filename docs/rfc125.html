RFC 125

Response to RFC #86, Proposal for Network Standard Format for a graphics data stream

RFC 125

RFC 86への回答: グラフィックスデータストリームのためのネットワーク標準形式の提案

Abstract

概要

The basic approach of transmitting an intermediate, device independent language which is translated into specific device codes at the receiving host is sound. It appears to be the only approach that will allow thought to be centered on picture descriptions. Ames Research Center has adopted this approach in tying its graphic facilities, of various types, and on various computers together. At present, we are in the design phase and expect our package to be running in about six months. The main objections to the structure as it now exists, is that it takes no cognizance of the many features available on graphics devices. Since these features will always be changing with new devices, a set of option or mode primitives should be defined which are logically separate from the drawing primitives provided in RFC 86. The mode primitives will act upon the drawing primitives to modify their actions. The scope of a mode primitive extends until a new mode primitive resets an option. The use of mode primitives will allow the network standard stream interpreter to treat them as null operations if the features are missing at a particular host, or to perform more detailed interpretation of the following data stream to achieve results. The drawing primitives may also then keep a standard format which need not be changed to incorporate new features.

中間的でデバイスに依存しない言語を送信し、受信側のホストでそれを特定のデバイスコードに変換するという基本的なアプローチは妥当です。これは、画像の記述に考えを集中させられる唯一のアプローチであるように思われます。Ames Research Centerは、さまざまなコンピューター上にあるさまざまな種類のグラフィックス設備を結び付けるのにこのアプローチを採用しました。現在は設計段階にあり、約6か月後にはパッケージが稼働する見込みです。現在の構造に対する主な異論は、グラフィックスデバイスで利用できる多くの機能をまったく考慮していないことです。これらの機能は新しいデバイスが出るたびに変わり続けるので、RFC 86で示された描画プリミティブとは論理的に分離された、オプションまたはモードのプリミティブの集合を定義すべきです。モードプリミティブは描画プリミティブに作用して、その動作を変更します。モードプリミティブの効力は、新しいモードプリミティブがオプションを再設定するまで続きます。モードプリミティブを使うことで、ネットワーク標準ストリームのインタープリターは、特定のホストにその機能がない場合にはそれらを何もしない操作として扱うことも、後続のデータストリームをより詳しく解釈して結果を得ることもできるようになります。そうすれば、描画プリミティブも、新しい機能を取り込むために変更する必要のない標準形式を保てます。

Overall modes which primitives could control would be intensity levels, or color selections for objects, in addition blinking of objects should be provided. For vectors, the additional facility for drawing dashed lines is necessary.

プリミティブで制御できる全体的なモードとしては、オブジェクトの輝度レベルや色の選択があり、さらにオブジェクトの点滅も提供すべきです。ベクトルについては、破線を描く追加の機能が必要です。

Character strings require another set of specification. The convention for the beam is usually that it is in the center of the rectangular area defining a character's boundaries. The beam position is usually undefined at the finish of drawing a character string. A strong exception is taken to the exclusion of form control characters from strings. If included in the character string, they could provide for shifting from upper to lower case, subscripting, superscripting, and underscoring, as well as tab and other "carriage" motion functions. The appropriate characters could be extracted at interpretation time to provide the necessary information to display more complex strings. To allow the facility for generating ALGOL-like delimiters, such as "then", a convention for canonical character string should be adopted. I believe the Multics conventions described in reference 1 will suffice.

文字列には、別の一連の仕様が必要です。ビームについての慣習では、通常、ビームは文字の境界を定める長方形領域の中央にあるものとされます。文字列の描画を終えた時点でのビームの位置は、通常は未定義です。文字列から書式制御文字を除外することには強く異議を唱えます。書式制御文字を文字列に含めれば、大文字と小文字の切り替え、下付き文字、上付き文字、下線のほか、タブやそのほかの「キャリッジ」の移動機能を提供できます。解釈時に適切な文字を抽出して、より複雑な文字列を表示するのに必要な情報を得られます。「then」のようなALGOL風の区切り記号を生成する機能を実現するには、正規の文字列に関する規約を採用すべきです。参考文献1で説明されているMulticsの規約で十分だと考えます。

Additional options for character strings should include a size specification and an orientation selection. As many devices, have hardware character generators that are fixed, some of these options may not be desirable to implement as subroutines.

文字列の追加のオプションとして、サイズの指定と向きの選択を含めるべきです。多くのデバイスは固定のハードウェア文字ジェネレーターを持っているので、これらのオプションのいくつかはサブルーチンとして実装するのが望ましくないかもしれません。

Another area that should be looked at further is the additional symbols available which are not specified in ASCII. Some means of defining them should be provided within the argument string itself, again Multics has allowed the specification of arbitrary characters by entering their octal equivalents. The convention should use a control character code followed by a l6-bit list name which specifies the sub-list defining the character. The other alternative is to allow 8-bit characters and allow the interpreter to choose a sub-list if the character is not realizable with a hardware generator.

さらに検討すべきもう1つの分野は、ASCIIで規定されていない追加の記号です。それらを定義する何らかの手段を引数文字列そのものの中に用意すべきです。ここでもMulticsは、任意の文字をその8進数の値を入力することで指定できるようにしています。この規約では、制御文字のコードの後に、その文字を定義するサブリストを指定するl6ビットのリスト名を続けるべきです。もう1つの方法は、8ビット文字を許可し、その文字がハードウェアのジェネレーターで実現できない場合にはインタープリターがサブリストを選べるようにすることです。

The special form control characters to be used are:

使用する特別な書式制御文字は次のとおりです。

  1. BS - backspace
  2. LF - for new line
  3. SO/Sl - shift case
  4. DC2 - superscript following characters
  5. DC4 - subscript following characters
  6. DC3 - special non-ASCII character follows
  7. Tab - position to next tab. May be predefined or specified.
  1. BS - バックスペース
  2. LF - 改行
  3. SO/Sl - 大文字と小文字の切り替え
  4. DC2 - 後続の文字を上付きにする
  5. DC4 - 後続の文字を下付きにする
  6. DC3 - 特別な非ASCII文字が続く
  7. Tab - 次のタブ位置に移動する。あらかじめ定義しておくことも、指定することもできる。

Another construct should be added to those proposed in RFC 86. This is the display list pointer (NGDLP). It will have as a value the next drawing primitive to be executed. The value is a displacement from the head of a list. With no mode setting primitives, this value is one to one with the drawing primitives transmitted in the NGDS. The NGDLP is needed for consistency for execution of the nested list structure. Whenever an execute list primitive is encountered, the current value of the NGDLP is saved along with the list name and current origin value. When execution of a list is finished, the last values saved are restored.

RFC 86で提案されているものに、もう1つの構成要素を追加すべきです。それはディスプレイリストポインター（NGDLP）です。その値は、次に実行する描画プリミティブです。値はリストの先頭からの変位です。モードを設定するプリミティブがなければ、この値はNGDSで送信される描画プリミティブと1対1に対応します。NGDLPは、入れ子になったリスト構造を一貫して実行するために必要です。リスト実行プリミティブに遭遇するたびに、NGDLPの現在の値を、リスト名と現在の原点の値とともに保存します。リストの実行が終わると、最後に保存した値を復元します。

An include list primitive would allow the treatment of a sub-list to be equivalent to a macro instead of a subroutine. This would be necessary to avoid changes to all sub-pictures on the screen due to the manipulation of a sub-list. The include primitive should have as parameters such specifications as size, intensity, orientation, blinking, etc. After a sub-list has been included in another list, it is no longer distinguished as a separate entity.

リスト取り込み（include list）プリミティブを使えば、サブリストをサブルーチンではなくマクロと同等に扱えるようになります。これは、サブリストの操作によって画面上のすべての部分画像が変わってしまうのを避けるために必要です。取り込みプリミティブには、サイズ、輝度、向き、点滅などの指定をパラメーターとして持たせるべきです。サブリストを別のリストに取り込んだ後は、それはもはや別個の実体としては区別されません。

To cut down on the volume of data being transferred, other commands to be parsed by the stream interpreter should be added. These would allow the manipulation of a list by the receiving host without a retransmission. The types of manipulations would include rescaling the coordinates for shrinking or zooming, translation of the origin, or rotation. Other manipulations to provide for displaying or not displaying a list, or enabling of disabling light pen detections would be desirable.

転送されるデータの量を減らすために、ストリームのインタープリターが解析するほかのコマンドを追加すべきです。それらのコマンドによって、受信側のホストは再送信なしでリストを操作できるようになります。操作の種類としては、縮小や拡大のための座標の再スケーリング、原点の平行移動、回転などがあります。リストを表示するかしないかを指定する操作や、ライトペンによる検出を有効または無効にする操作も望ましいでしょう。

The problem of interaction with the displayed picture has yet to be addressed, so this will be an attempt to elicit some more discussion in this area. The use of a keyboard or function keys poses no problem in that both can be handled as a standard message from the graphics terminal. The use of devices that interact with the picture or the screen such as light pens, mice, joysticks, or tablets presents a different and more complex problem. This problem is the standard one of making an association between the point selected and some meaningful entity such as a list or a primitive. This association should be made at the receiving host since the NGDS has been changed in unknown ways.

表示された画像とのインタラクションの問題はまだ取り上げられていないので、ここではこの分野についてもう少し議論を引き出すことを試みます。キーボードやファンクションキーの使用は、どちらもグラフィックス端末からの標準的なメッセージとして扱えるので、問題にはなりません。ライトペン、マウス、ジョイスティック、タブレットのように、画像や画面とインタラクションするデバイスの使用は、それとは異なる、より複雑な問題を提起します。この問題は、選択された点と、リストやプリミティブのような何らかの意味のある実体とを関連付けるという標準的な問題です。NGDSは未知の方法で変更されているので、この関連付けは受信側のホストで行うべきです。

To allow the transmitting host to identify the object pointed at, the stack of suspended lists and the current value of the NGDLP will qualify the object to any level in a hierarchical structure. In addition, normalized x,y coordinates should be returned, as well as a character displacement if a string was pointed at. This structure will serve a light pen device very well since the light pen mechanism allows the determination of the currently executing primitive. Other devices interact with the picture in an asynchronous fashion and the association of an x,y pair to a structure is a more difficult problem. This may require that the host generating the graphic data stream be responsible for making that association. A further complication arises when it is desired to use a light pen in an area where no beam motion occurs, then some directive to periodically sweep the screen and "find" the pen must be provided. This might be a sub-list which is executed periodically for this function.

送信側のホストが指し示されたオブジェクトを特定できるように、中断されたリストのスタックとNGDLPの現在の値によって、階層構造の任意のレベルまでオブジェクトを限定します。さらに、正規化されたx,y座標と、文字列が指し示された場合には文字の変位も返すべきです。ライトペンの機構では現在実行中のプリミティブを判別できるので、この構造はライトペンデバイスには非常によく適しています。ほかのデバイスは画像と非同期的にインタラクションするので、x,yの組を構造に関連付けるのはより難しい問題です。そのため、グラフィックスデータストリームを生成するホストがその関連付けに責任を負う必要があるかもしれません。ビームの動きがない領域でライトペンを使いたい場合には、さらに複雑になります。その場合は、定期的に画面を走査してペンを「見つける」何らかの指令を用意しなければなりません。これは、この機能のために定期的に実行されるサブリストとして実現できるかもしれません。
