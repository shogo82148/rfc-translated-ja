RFC 7857

Updates to Network Address Translation (NAT) Behavioral Requirements

RFC 7857

ネットワークアドレス変換（NAT）の動作要件の更新

Abstract

概要

This document clarifies and updates several requirements of RFCs 4787, 5382, and 5508 based on operational and development experience. The focus of this document is Network Address Translation from IPv4 to IPv4 (NAT44).

この文書は、運用および開発の経験に基づいて、RFC 4787、5382、5508のいくつかの要件を明確化し、更新します。この文書の焦点は、IPv4からIPv4へのネットワークアドレス変換（NAT44）です。

This document updates RFCs 4787, 5382, and 5508.

この文書は、RFC 4787、5382、5508を更新します。

1. Introduction

1. はじめに

[RFC4787], [RFC5382], and [RFC5508] contributed to enhance Network Address Translation (NAT) interoperability and conformance. Operational experience gained through widespread deployment and evolution of NAT indicates that some areas of the original documents need further clarification or updates. This document provides such clarifications and updates.

[RFC4787]、[RFC5382]、[RFC5508]は、ネットワークアドレス変換（NAT）の相互運用性と適合性の向上に貢献しました。NATの広範な展開と進化を通じて得られた運用経験から、もとの文書のいくつかの領域にはさらなる明確化や更新が必要であることがわかっています。この文書は、そのような明確化と更新を提供します。

1.1. Scope

1.1. 範囲

The goal of this document is to clarify and update the set of requirements listed in [RFC4787], [RFC5382], and [RFC5508]. The document focuses exclusively on NAT44.

この文書の目的は、[RFC4787]、[RFC5382]、[RFC5508]に記載された一連の要件を明確化し、更新することです。この文書はNAT44のみを対象とします。

The scope of this document has been set so that it does not create new requirements beyond those specified in the documents cited above.

この文書の範囲は、上記で引用した文書で規定されているものを超える新しい要件を作らないように設定されています。

Requirements related to Carrier-Grade NAT (CGN) are defined in [RFC6888].

キャリアグレードNAT（CGN）に関する要件は、[RFC6888]で定義されています。

1.2. Terminology

1.2. 用語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119].

この文書におけるキーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、「要求されています（REQUIRED）」、「することになります（SHALL）」、「することはありません（SHALL NOT）」、「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、「推奨されます（RECOMMENDED）」、「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、[RFC2119]で説明されているとおりに解釈されるものとします。

The reader is assumed to be familiar with the terminology defined in [RFC2663], [RFC4787], [RFC5382], and [RFC5508].

読者は、[RFC2663]、[RFC4787]、[RFC5382]、[RFC5508]で定義された用語に精通していることを前提とします。

In this document, the term "NAT" refers to both "Basic NAT" and "Network Address/Port Translator (NAPT)" (see Section 3 of [RFC4787]). As a reminder, Basic NAT and NAPT are two variations of traditional NAT in that translation in Basic NAT is limited to IP addresses alone, whereas translation in NAPT is extended to include IP addresses and transport identifiers (such as a TCP/UDP port or ICMP query ID); refer to Section 2 of [RFC3022].

この文書では、「NAT」という用語は「ベーシックNAT（Basic NAT）」と「ネットワークアドレス/ポート変換器（Network Address/Port Translator、NAPT）」の両方を指します（[RFC4787]のセクション3を参照）。念のため述べておくと、ベーシックNATとNAPTは従来型NATの2つの変種であり、ベーシックNATでの変換はIPアドレスのみに限定されるのに対し、NAPTでの変換はIPアドレスとトランスポート識別子（TCP/UDPポートやICMPクエリーIDなど）を含むように拡張されています。[RFC3022]のセクション2を参照してください。

2. TCP Session Tracking

2. TCPセッションの追跡

[RFC5382] specifies TCP timers associated with various connection states but does not specify the TCP state machine a NAT44 should follow as a basis to apply such timers.

[RFC5382]は、さまざまな接続状態に関連付けられたTCPタイマーを規定していますが、そのようなタイマーを適用する基礎としてNAT44が従うべきTCP状態機械は規定していません。

Update:
The TCP state machine depicted in Figure 1, adapted from [RFC6146], SHOULD be implemented by a NAT for TCP session tracking purposes.
更新:
NATは、TCPセッションを追跡する目的で、[RFC6146]から改変した図1に示すTCP状態機械を実装すべきです（SHOULD）。

2.1. TCP Transitory Connection Idle-Timeout

2.1. TCPの過渡的接続のアイドルタイムアウト

The transitory connection idle-timeout is defined as the minimum time a TCP connection in the partially open or closing phases must remain idle before the NAT considers the associated session a candidate for removal (REQ-5 of [RFC5382]). However, [RFC5382] does not clearly state whether these can be configured separately.

過渡的接続のアイドルタイムアウト（transitory connection idle-timeout）は、半開状態またはクローズ中の段階にあるTCP接続について、NATが関連するセッションを削除の候補とみなすまでにその接続がアイドル状態のままでなければならない最小時間として定義されています（[RFC5382]のREQ-5）。しかし、[RFC5382]は、これらを個別に設定できるかどうかを明確に述べていません。

Clarification:

This document clarifies that a NAT SHOULD provide different configurable parameters for configuring the open and closing idle timeouts.

To accommodate deployments that consider a partially open timeout of 4 minutes as being excessive from a security standpoint, a NAT MAY allow the configured timeout to be less than 4 minutes. However, a minimum default transitory connection idle-timeout of 4 minutes is RECOMMENDED.

明確化:

この文書は、NATがオープン中とクローズ中のアイドルタイムアウトを設定するための、それぞれ異なる設定可能なパラメーターを提供すべきです（SHOULD）ということを明確にします。

半開状態のタイムアウトとして4分はセキュリティーの観点から長すぎると考える展開に対応するため、NATは設定するタイムアウトを4分未満にすることを許可してもよいです（MAY）。ただし、過渡的接続のアイドルタイムアウトのデフォルト値は最小で4分とすることが推奨されます（RECOMMENDED）。

2.2. TCP RST

2.2. TCP RST

[RFC5382] leaves the handling of TCP RST packets unspecified.

[RFC5382]は、TCP RSTパケットの扱いを規定していません。

Update:

This document adopts a similar default behavior as in [RFC6146]. Concretely, when the NAT receives a TCP RST matching an existing mapping, it MUST translate the packet according to the NAT mapping entry. Moreover, the NAT SHOULD wait for 4 minutes before deleting the session and removing any state associated with it if no packets are received during that 4-minute timeout.

Notes:

  • Admittedly, the NAT has to verify whether received TCP RST packets belong to a connection. This verification check is required to avoid off-path attacks.
  • If the NAT immediately removes the NAT mapping upon receipt of a TCP RST message, stale connections may be maintained by endpoints if the first RST message is lost between the NAT and the recipient.
更新:

この文書は、[RFC6146]と同様のデフォルトの動作を採用します。具体的には、既存のマッピングに一致するTCP RSTを受信したとき、NATはNATマッピングエントリーに従ってそのパケットを変換しなければなりません（MUST）。さらに、NATは、その4分間のタイムアウトの間にパケットを受信しなかった場合に、セッションを削除してそれに関連する状態を取り除く前に、4分間待機すべきです（SHOULD）。

注記:

  • 確かに、NATは受信したTCP RSTパケットが接続に属しているかどうかを検証する必要があります。この検証は、オフパス攻撃を回避するために必要です。
  • NATがTCP RSTメッセージの受信時にただちにNATマッピングを削除すると、最初のRSTメッセージがNATと受信者の間で失われた場合に、古くなった接続がエンドポイントによって維持されることがあります。

3. Port Overlapping Behavior

3. ポートオーバーラッピングの動作

REQ-1 from [RFC4787] and REQ-1 from [RFC5382] specify a specific port overlapping behavior; that is, the external IP address and port can be reused for connections originating from the same internal source IP address and port irrespective of the destination. This is known as Endpoint-Independent Mapping (EIM).

[RFC4787]のREQ-1と[RFC5382]のREQ-1は、特定のポートオーバーラッピングの動作を規定しています。すなわち、同じ内部の送信元IPアドレスとポートから発信される接続に対しては、宛先にかかわらず外部IPアドレスとポートを再利用できるというものです。これはエンドポイント非依存マッピング（Endpoint-Independent Mapping、EIM）として知られています。

Update:

This document clarifies that this port overlapping behavior may be extended to connections originating from different internal source IP addresses and ports as long as their destinations are different.

The following mechanism MAY be implemented by a NAT:

If destination addresses and ports are different for outgoing connections started by local clients, a NAT MAY assign the same external port as the source ports for the connections. The port overlapping mechanism manages mappings between external packets and internal packets by looking at and storing their 5-tuple (protocol, source address, source port, destination address, and destination port).

This enables concurrent use of a single NAT external port for multiple transport sessions, which allows a NAT to successfully process packets in a network that has a limited number of IP addresses (e.g., deployment with a high address space multiplicative factor (refer to Appendix B of [RFC6269])).

更新:

この文書は、このポートオーバーラッピングの動作を、宛先が異なる限り、異なる内部の送信元IPアドレスとポートから発信される接続にも拡張してよいことを明確にします。

NATは次のメカニズムを実装してもよいです（MAY）。

ローカルのクライアントが開始した外向きの接続の宛先アドレスとポートが異なる場合、NATはそれらの接続の送信元ポートとして同じ外部ポートを割り当ててもよいです（MAY）。ポートオーバーラッピングのメカニズムは、外部のパケットと内部のパケットの5タプル（プロトコル、送信元アドレス、送信元ポート、宛先アドレス、宛先ポート）を調べて保存することにより、それらの間のマッピングを管理します。

これにより、単一のNAT外部ポートを複数のトランスポートセッションで同時に使用できるようになり、IPアドレスの数が限られたネットワーク（たとえば、アドレス空間の多重化係数が高い展開（[RFC6269]の付録Bを参照））でも、NATがパケットを正常に処理できるようになります。

4. Address Pooling Paired (APP)

4. ペア化アドレスプーリング（APP）

The "IP address pooling" behavior of "Paired" (APP) was recommended in REQ-2 from [RFC4787], but the behavior when an external IPv4 runs out of ports was left undefined.

[RFC4787]のREQ-2では、「IPアドレスプーリング」の動作として「ペア（Paired）」（APP）が推奨されていましたが、外部IPv4のポートが枯渇した場合の動作は未定義のままでした。

Clarification:

This document clarifies that if APP is enabled, new sessions from a host that already has a mapping associated with an external IP that ran out of ports SHOULD be dropped. A configuration parameter MAY be provided to allow a NAT to start using ports from another external IP address when the one that anchored the APP mapping ran out of ports. Tweaking this configuration parameter is a trade-off between service continuity and APP strict enforcement. Note, this behavior is sometimes referred to as "soft-APP".

As a reminder, the recommendation for the particular case of a CGN is that an implementation must use the same external IP address mapping for all sessions associated with the same internal IP address, be they TCP, UDP, ICMP, something else, or a mix of different protocols [RFC6888].

Update:
This behavior SHOULD apply also for TCP.
明確化:

この文書は、APPが有効な場合、ポートが枯渇した外部IPに関連付けられたマッピングをすでに持つホストからの新しいセッションは破棄されるべきです（SHOULD）ということを明確にします。APPマッピングを固定していた外部IPアドレスのポートが枯渇したときに、NATが別の外部IPアドレスのポートを使い始めることを許可する設定パラメーターを提供してもよいです（MAY）。この設定パラメーターの調整は、サービスの継続性とAPPの厳格な適用との間のトレードオフになります。なお、この動作は「ソフトAPP（soft-APP）」と呼ばれることもあります。

念のため述べておくと、CGNという特定のケースに対する推奨は、TCP、UDP、ICMP、その他のプロトコル、あるいは異なるプロトコルの組み合わせのいずれであっても、同じ内部IPアドレスに関連付けられたすべてのセッションに対して、実装は同じ外部IPアドレスのマッピングを使用しなければならないというものです[RFC6888]。

更新:
この動作はTCPにも適用されるべきです（SHOULD）。

5. Endpoint-Independent Mapping (EIM) Protocol Independence

5. エンドポイント非依存マッピング（EIM）のプロトコル非依存性

REQ-1 from [RFC4787] and REQ-1 from [RFC5382] do not specify whether EIM are protocol dependent or protocol independent. For example, if an outbound TCP SYN creates a mapping, it is left undefined whether outbound UDP packets can reuse such mapping.

[RFC4787]のREQ-1と[RFC5382]のREQ-1は、EIMがプロトコル依存なのかプロトコル非依存なのかを規定していません。たとえば、外向きのTCP SYNがマッピングを作成した場合に、外向きのUDPパケットがそのマッピングを再利用できるかどうかは未定義のままです。

Update:

EIM mappings SHOULD be protocol dependent. A configuration parameter MAY be provided to allow protocols that multiplex TCP and UDP over the same source IP address and port number to use a single mapping. The default value of this configuration parameter MUST be protocol-dependent EIM.

This update is consistent with the stateful Network Address and Protocol Translation from IPv6 Clients to IPv4 Servers (NAT64) [RFC6146] that clearly specifies three binding information bases (TCP, UDP, and ICMP).

更新:

EIMマッピングはプロトコル依存であるべきです（SHOULD）。同じ送信元IPアドレスとポート番号の上でTCPとUDPを多重化するプロトコルが単一のマッピングを使用できるようにするための設定パラメーターを提供してもよいです（MAY）。この設定パラメーターのデフォルト値は、プロトコル依存のEIMでなければなりません（MUST）。

この更新は、3つのバインディング情報ベース（TCP、UDP、ICMP）を明確に規定している、ステートフルなIPv6クライアントからIPv4サーバーへのネットワークアドレスおよびプロトコル変換（NAT64）[RFC6146]と整合しています。

6. Endpoint-Independent Filtering (EIF) Protocol Independence

6. エンドポイント非依存フィルタリング（EIF）のプロトコル非依存性

REQ-8 from [RFC4787] and REQ-3 from [RFC5382] do not specify whether mappings with Endpoint-Independent Filtering (EIF) are protocol independent or protocol dependent. For example, if an outbound TCP SYN creates a mapping, it is left undefined whether inbound UDP packets matching that mapping should be accepted or rejected.

[RFC4787]のREQ-8と[RFC5382]のREQ-3は、エンドポイント非依存フィルタリング（Endpoint-Independent Filtering、EIF）を伴うマッピングがプロトコル非依存なのかプロトコル依存なのかを規定していません。たとえば、外向きのTCP SYNがマッピングを作成した場合に、そのマッピングに一致する内向きのUDPパケットを受け入れるべきか拒否すべきかは未定義のままです。

Update:

EIF filtering SHOULD be protocol dependent. A configuration parameter MAY be provided to make it protocol independent. The default value of this configuration parameter MUST be protocol-dependent EIF.

This behavior is aligned with the update in Section 5.

Applications that can be transported over a variety of transport protocols and/or support transport fallback schemes won't experience connectivity failures if the NAT is configured with protocol-independent EIM and protocol-independent EIF.

更新:

EIFのフィルタリングはプロトコル依存であるべきです（SHOULD）。それをプロトコル非依存にするための設定パラメーターを提供してもよいです（MAY）。この設定パラメーターのデフォルト値は、プロトコル依存のEIFでなければなりません（MUST）。

この動作は、セクション5の更新と一致しています。

さまざまなトランスポートプロトコル上で転送できる、またはトランスポートのフォールバック方式をサポートする（あるいはその両方の）アプリケーションは、NATがプロトコル非依存のEIMとプロトコル非依存のEIFで設定されていれば、接続性の障害を経験することはありません。

7. Endpoint-Independent Filtering (EIF) Mapping Refresh

7. エンドポイント非依存フィルタリング（EIF）のマッピングのリフレッシュ

The NAT mapping Refresh direction may have a "NAT Inbound refresh behavior" of "True" according to REQ-6 from [RFC4787], but [RFC4787] does not clarify how this behavior applies to EIF mappings. The issue in question is whether inbound packets that match an EIF mapping but do not create a new session due to a security policy should refresh the mapping timer.

[RFC4787]のREQ-6によると、NATマッピングのリフレッシュ方向は「NATインバウンドリフレッシュ動作（NAT Inbound refresh behavior）」が「True」であってもよいとされていますが、[RFC4787]はこの動作がEIFマッピングにどのように適用されるかを明確にしていません。問題となるのは、EIFマッピングに一致するものの、セキュリティーポリシーのために新しいセッションを作成しない内向きのパケットが、マッピングのタイマーをリフレッシュすべきかどうかです。

Clarification:
This document clarifies that even when a NAT has an inbound refresh behavior set to "TRUE", such packets SHOULD NOT refresh the mapping. Otherwise, a simple attack of a packet every two minutes can keep the mapping indefinitely.
Update:
This behavior SHOULD apply also for TCP.
明確化:
この文書は、NATのインバウンドリフレッシュ動作が「TRUE」に設定されている場合であっても、そのようなパケットはマッピングをリフレッシュすべきではありません（SHOULD NOT）ということを明確にします。そうしないと、2分ごとに1つのパケットを送るという単純な攻撃によって、マッピングを無期限に維持できてしまいます。
更新:
この動作はTCPにも適用されるべきです（SHOULD）。

7.1. Outbound Mapping Refresh and Error Packets

7.1. アウトバウンドのマッピングのリフレッシュとエラーパケット

Update:
In the case of NAT outbound refresh behavior, ICMP Errors or TCP RST outbound packets sent as a response to inbound packets SHOULD NOT refresh the mapping. Other packets that indicate the host is not interested in receiving packets MAY be configurable to also not refresh state, such as a Session Traversal Utilities for NAT (STUN) error response [RFC5389] or IKE INVALID_SYNTAX [RFC7296].
更新:
NATのアウトバウンドリフレッシュ動作の場合、内向きのパケットに対する応答として送信されるICMPエラーまたはTCP RSTの外向きのパケットは、マッピングをリフレッシュすべきではありません（SHOULD NOT）。ホストがパケットの受信に関心がないことを示すその他のパケット、たとえばSession Traversal Utilities for NAT（STUN）のエラー応答[RFC5389]やIKEのINVALID_SYNTAX[RFC7296]についても、状態をリフレッシュしないように設定可能であってもよいです（MAY）。

8. Port Parity

8. ポートパリティー

Update:

A NAT MAY disable port parity preservation for all dynamic mappings. Nevertheless, A NAT SHOULD support means to explicitly request to preserve port parity (e.g., [RFC7753]).

Note: According to [RFC6887], dynamic mappings are said to be dynamic in the sense that they are created on demand, either implicitly or explicitly:

  1. Implicit dynamic mappings refer to mappings that are created as a side effect of traffic such as an outgoing TCP SYN or outgoing UDP packet. Implicit dynamic mappings usually have a finite lifetime, though this lifetime is generally not known to the client using them.
  2. Explicit dynamic mappings refer to mappings that are created as a result, for example, of explicit Port Control Protocol (PCP) MAP and PEER requests. Explicit dynamic mappings have a finite lifetime, and this lifetime is communicated to the client.
更新:

NATは、すべての動的マッピングについて、ポートパリティーの保持を無効にしてもよいです（MAY）。それでも、NATはポートパリティーの保持を明示的に要求する手段（たとえば[RFC7753]）をサポートすべきです（SHOULD）。

注記: [RFC6887]によると、動的マッピングは、暗黙的または明示的にオンデマンドで作成されるという意味で動的であるとされています。

  1. 暗黙的な動的マッピングとは、外向きのTCP SYNや外向きのUDPパケットなどのトラフィックの副作用として作成されるマッピングのことです。暗黙的な動的マッピングは通常は有限の存続期間を持ちますが、一般にこの存続期間はそれを使用するクライアントには知らされません。
  2. 明示的な動的マッピングとは、たとえば明示的なポート制御プロトコル（Port Control Protocol、PCP）のMAPリクエストやPEERリクエストの結果として作成されるマッピングのことです。明示的な動的マッピングは有限の存続期間を持ち、この存続期間はクライアントに通知されます。

9. Port Randomization

9. ポートのランダム化

Update:

A NAT SHOULD follow the recommendations specified in Section 4 of [RFC6056], especially:

A NAPT that does not implement port preservation [RFC4787] [RFC5382] SHOULD obfuscate selection of the ephemeral port of a packet when it is changed during translation of that packet.

A NAPT that does implement port preservation SHOULD obfuscate the ephemeral port of a packet only if the port must be changed as a result of the port being already in use for some other session.

A NAPT that performs parity preservation and that must change the ephemeral port during translation of a packet SHOULD obfuscate the ephemeral ports. The algorithms described in this document could be easily adapted such that the parity is preserved (i.e., force the lowest order bit of the resulting port number to 0 or 1 according to whether even or odd parity is desired).

更新:

NATは、[RFC6056]のセクション4で規定された推奨事項に従うべきです（SHOULD）。特に次の推奨事項です。

ポート保持[RFC4787] [RFC5382]を実装していないNAPTは、パケットの変換中にそのパケットのエフェメラルポートを変更する場合、その選択を難読化すべきです（SHOULD）。

ポート保持を実装しているNAPTは、そのポートがすでにほかのセッションで使用中であるためにポートを変更しなければならない場合にのみ、パケットのエフェメラルポートを難読化すべきです（SHOULD）。

パリティーの保持を行い、かつパケットの変換中にエフェメラルポートを変更しなければならないNAPTは、エフェメラルポートを難読化すべきです（SHOULD）。この文書で説明しているアルゴリズムは、パリティーが保持されるように容易に適合させることができます（すなわち、偶数と奇数のどちらのパリティーが望まれるかに応じて、結果のポート番号の最下位ビットを強制的に0または1にします）。

10. IP Identification (IP ID)

10. IP識別子（IP ID）

Update:
A NAT SHOULD handle the Identification field of translated IPv4 packets as specified in Section 5.3.1 of [RFC6864].
更新:
NATは、変換したIPv4パケットのIdentificationフィールドを[RFC6864]のセクション5.3.1で規定されているとおりに扱うべきです（SHOULD）。

11. ICMP Query Mappings Timeout

11. ICMPクエリーマッピングのタイムアウト

Section 3.1 of [RFC5508] specifies that ICMP Query mappings are to be maintained by a NAT. However, the specification doesn't discuss Query mapping timeout values. Section 3.2 of [RFC5508] only discusses ICMP Query session timeouts.

[RFC5508]のセクション3.1は、ICMPクエリーマッピングをNATが維持することを規定しています。しかし、その仕様はクエリーマッピングのタイムアウト値については論じていません。[RFC5508]のセクション3.2は、ICMPクエリーセッションのタイムアウトについて論じているだけです。

Update:
ICMP Query mappings MAY be deleted once the last session using the mapping is deleted.
更新:
ICMPクエリーマッピングは、そのマッピングを使用する最後のセッションが削除された時点で削除してもよいです（MAY）。

12. Hairpinning Support for ICMP Packets

12. ICMPパケットのヘアピニングのサポート

REQ-7 from [RFC5508] specifies that a NAT enforcing Basic NAT must support traversal of hairpinned ICMP Query sessions.

[RFC5508]のREQ-7は、ベーシックNATを実施するNATが、ヘアピンされたICMPクエリーセッションの通過をサポートしなければならないと規定しています。

Clarification:
This implicitly means that address mappings from external address to internal address (similar to Endpoint-Independent Filters) must be maintained to allow inbound ICMP Query sessions. If an ICMP Query is received on an external address, a NAT can then translate to an internal IP.
明確化:
これは暗黙的に、内向きのICMPクエリーセッションを許可するために、外部アドレスから内部アドレスへのアドレスマッピング（エンドポイント非依存フィルターと同様のもの）を維持しなければならないことを意味します。そうすれば、外部アドレスでICMPクエリーを受信した場合に、NATは内部IPへの変換を行うことができます。

REQ-7 from [RFC5508] specifies that all NATs must support the traversal of hairpinned ICMP Error messages.

[RFC5508]のREQ-7は、すべてのNATが、ヘアピンされたICMPエラーメッセージの通過をサポートしなければならないと規定しています。

Clarification:
This behavior requires a NAT to maintain address mappings from external IP address to internal IP address in addition to the ICMP Query mappings described in Section 3.1 of [RFC5508].
明確化:
この動作のためには、NATは、[RFC5508]のセクション3.1で説明されているICMPクエリーマッピングに加えて、外部IPアドレスから内部IPアドレスへのアドレスマッピングを維持する必要があります。

13. Security Considerations

13. セキュリティーに関する考慮事項

NAT behavioral considerations are discussed in [RFC4787], [RFC5382], and [RFC5508].

NATの動作に関する考慮事項は、[RFC4787]、[RFC5382]、[RFC5508]で論じられています。

Because some of the clarifications and updates (e.g., Section 2) are inspired from NAT64, the security considerations discussed in Section 5 of [RFC6146] apply also for this specification.

明確化と更新のいくつか（たとえばセクション2）はNAT64から着想を得ているため、[RFC6146]のセクション5で論じられているセキュリティーに関する考慮事項はこの仕様にも適用されます。

The update in Section 3 allows for an optimized NAT resource usage. In order to avoid service disruption, the NAT must not invoke this functionality unless the packets are to be sent to distinct destination addresses.

セクション3の更新により、NATのリソース使用を最適化できます。サービスの中断を避けるため、パケットが異なる宛先アドレスに送信される場合を除き、NATはこの機能を発動してはなりません。

Some of the updates (e.g., Sections 7, 9, and 11) allow for increased security compared to [RFC4787], [RFC5382], and [RFC5508]. Particularly,

更新のいくつか（たとえばセクション7、9、11）により、[RFC4787]、[RFC5382]、[RFC5508]と比べてセキュリティーを高めることができます。特に、

  • the updates in Sections 7 and 11 prevent an illegitimate node to maintain mappings activated in the NAT while these mappings should be cleared, and
  • port randomization (Section 9) complicates tracking hosts located behind a NAT.
  • セクション7と11の更新は、本来であれば消去されるべきマッピングを、不正なノードがNAT内で有効なまま維持することを防ぎます。また、
  • ポートのランダム化（セクション9）は、NATの背後にあるホストの追跡を困難にします。

Sections 4 and 12 propose updates that increase the serviceability of a host located behind a NAT. These updates do not introduce any additional security concerns to [RFC4787], [RFC5382], and [RFC5508].

セクション4と12は、NATの背後にあるホストのサービス性を高める更新を提案しています。これらの更新は、[RFC4787]、[RFC5382]、[RFC5508]に対して、セキュリティー上の懸念を新たにもたらすことはありません。

The updates in Sections 5 and 6 allow for a better NAT transparency from an application standpoint. Hosts that require a restricted filtering behavior should enable specific policies (e.g., Access Control List (ACL)) either locally or by soliciting a dedicated security device (e.g., firewall). How a host updates its filtering policies is out of scope of this document.

セクション5と6の更新により、アプリケーションの観点からNATの透過性を高めることができます。制限されたフィルタリング動作を必要とするホストは、ローカルで、または専用のセキュリティー機器（たとえばファイアウォール）に依頼することによって、特定のポリシー（たとえばアクセス制御リスト（Access Control List、ACL））を有効にすべきです。ホストがフィルタリングポリシーをどのように更新するかは、この文書の範囲外です。

The update in Section 8 induces security concerns that are specific to the protocol used to interact with the NAT. For example, if PCP is used to explicitly request parity preservation for a given mapping, the security considerations discussed in [RFC6887] should be taken into account.

セクション8の更新は、NATとのやり取りに使用するプロトコルに固有のセキュリティー上の懸念をもたらします。たとえば、特定のマッピングに対するパリティーの保持を明示的に要求するためにPCPを使用する場合は、[RFC6887]で論じられているセキュリティーに関する考慮事項を考慮に入れるべきです。

The update in Section 10 may have undesired effects on the performance of the NAT in environments in which fragmentation is massively experienced. Such an issue may be used as an attack vector against NATs.

セクション10の更新は、断片化が大量に発生する環境において、NATの性能に望ましくない影響を与える可能性があります。そのような問題は、NATに対する攻撃ベクトルとして使用される可能性があります。
