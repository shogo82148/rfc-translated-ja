RFC 8265

Preparation, Enforcement, and Comparison of Internationalized Strings Representing Usernames and Passwords

RFC 8265

ユーザー名とパスワードを表す国際化文字列の準備、強制、比較

Abstract

概要

This document describes updated methods for handling Unicode strings representing usernames and passwords. The previous approach was known as SASLprep (RFC 4013) and was based on Stringprep (RFC 3454). The methods specified in this document provide a more sustainable approach to the handling of internationalized usernames and passwords. This document obsoletes RFC 7613.

この文書は、ユーザー名とパスワードを表すUnicode文字列を扱うための更新された方法を説明します。以前のアプローチはSASLprep（RFC 4013）として知られており、Stringprep（RFC 3454）に基づいていました。この文書で規定する方法は、国際化されたユーザー名とパスワードの扱いに関して、より持続可能なアプローチを提供します。この文書はRFC 7613を廃止します。

1. Introduction

1. はじめに

Usernames and passwords are widely used for authentication and authorization on the Internet, either directly when provided in plaintext (as in the PLAIN Simple Authentication and Security Layer (SASL) mechanism [RFC4616] and the HTTP Basic scheme [RFC7617]) or indirectly when provided as the input to a cryptographic algorithm such as a hash function (as in the Salted Challenge Response Authentication Mechanism (SCRAM) SASL mechanism [RFC5802] and the HTTP Digest scheme [RFC7616]).

ユーザー名とパスワードは、インターネット上の認証と認可に広く使用されています。その使われ方には、平文で提供される場合の直接的なもの（PLAIN Simple Authentication and Security Layer（SASL）メカニズム[RFC4616]やHTTP Basicスキーム[RFC7617]など）と、ハッシュ関数などの暗号アルゴリズムへの入力として提供される場合の間接的なもの（Salted Challenge Response Authentication Mechanism（SCRAM）SASLメカニズム[RFC5802]やHTTP Digestスキーム[RFC7616]など）があります。

To increase the likelihood that the input and comparison of usernames and passwords will work in ways that make sense for typical users throughout the world, this document defines rules for handling internationalized strings that represent usernames and passwords. Such strings consist of code points from the Unicode coded character set [Unicode], with special attention to code points outside the ASCII range [RFC20]. The rules for handling such strings are specified through profiles of the string classes defined in the preparation, enforcement, and comparison of internationalized strings (PRECIS) framework specification [RFC8264].

ユーザー名とパスワードの入力と比較が、世界中の典型的なユーザーにとって意味のある方法で機能する可能性を高めるために、この文書は、ユーザー名とパスワードを表す国際化文字列を扱うための規則を定義します。そのような文字列は、Unicode符号化文字集合[Unicode]のコードポイントで構成され、ASCII範囲[RFC20]外のコードポイントには特別な注意が払われます。そのような文字列を扱うための規則は、国際化文字列の準備、強制、比較（preparation, enforcement, and comparison of internationalized strings：PRECIS）フレームワーク仕様[RFC8264]で定義されている文字列クラスのプロファイルを通じて規定されます。

Profiles of the PRECIS framework enable software to handle Unicode code points outside the ASCII range in an automated way, so that such code points are treated carefully and consistently in application protocols. In large measure, these profiles are designed to protect application developers from the potentially negative consequences of supporting the full range of Unicode code points. For instance, in almost all application protocols it would be dangerous to treat the Unicode code point "¹" (SUPERSCRIPT ONE, U+00B9) as equivalent to "1" (DIGIT ONE, U+0031), because that would result in false accepts during comparison, authentication, and authorization (e.g., an attacker could easily spoof an account "user1@example.com").

PRECISフレームワークのプロファイルにより、ソフトウェアはASCII範囲外のUnicodeコードポイントを自動化された方法で扱えるようになり、そのようなコードポイントがアプリケーションプロトコルで慎重かつ一貫して扱われるようになります。これらのプロファイルは主に、Unicodeコードポイントの全範囲をサポートすることで生じうる悪影響から、アプリケーション開発者を保護するように設計されています。たとえば、ほとんどすべてのアプリケーションプロトコルにおいて、Unicodeコードポイント「¹」（SUPERSCRIPT ONE、U+00B9）を「1」（DIGIT ONE、U+0031）と等価として扱うことは危険です。そうすると、比較、認証、認可の際に誤受理（false accept）が発生するからです（たとえば、攻撃者はアカウント「user1@example.com」を容易になりすますことができてしまいます）。

Whereas a naive use of Unicode would make such attacks trivially easy, the PRECIS profile defined here for usernames generally protects applications from inadvertently causing such problems. (Similar considerations apply to passwords, although here it is desirable to support a wider range of characters so as to maximize entropy for purposes of authentication.)

Unicodeを素朴に使用すると、そのような攻撃がきわめて容易になってしまうのに対し、ここでユーザー名について定義するPRECISプロファイルは、一般に、アプリケーションがそのような問題をうっかり引き起こすことを防ぎます（パスワードにも同様の考慮事項が当てはまりますが、パスワードの場合は、認証のためにエントロピーを最大化するよう、より広い範囲の文字をサポートすることが望まれます）。

The methods defined here might be applicable wherever usernames or passwords are used. However, the methods are not intended for use in preparing strings that are not usernames (e.g., Lightweight Directory Access Protocol (LDAP) distinguished names), nor in cases where identifiers or secrets are not strings (e.g., keys and certificates) or require specialized handling.

ここで定義する方法は、ユーザー名やパスワードが使用されるあらゆる場面に適用できるかもしれません。ただし、これらの方法は、ユーザー名ではない文字列（たとえば、Lightweight Directory Access Protocol（LDAP）の識別名）の準備に使用することや、識別子や秘密が文字列ではない場合（たとえば、鍵や証明書）、または特殊な扱いを必要とする場合に使用することを意図していません。

Although the historical predecessor of this document was the SASLprep profile of Stringprep [RFC3454]), the approach defined here can be used by technologies other than SASL [RFC4422], such as HTTP authentication as specified in [RFC7617] and [RFC7616].

この文書の歴史的な前身はStringprep[RFC3454]のSASLprepプロファイルでしたが、ここで定義するアプローチは、SASL[RFC4422]以外の技術、たとえば[RFC7617]と[RFC7616]で規定されているHTTP認証でも使用できます。

This document does not modify the handling of internationalized strings in usernames and passwords as prescribed by existing application protocols that use SASLprep. If the community that uses such an application protocol wishes to modernize its handling of internationalized strings to use PRECIS instead of Stringprep, it needs to explicitly update the existing application protocol definition (one example is [RFC7622]). Non-coordinated updates to protocol implementations are discouraged because they can have a negative impact on interoperability and security.

この文書は、SASLprepを使用する既存のアプリケーションプロトコルが規定している、ユーザー名とパスワードにおける国際化文字列の扱いを変更するものではありません。そのようなアプリケーションプロトコルを使用するコミュニティーが、Stringprepの代わりにPRECISを使用するように国際化文字列の扱いを近代化したい場合は、既存のアプリケーションプロトコルの定義を明示的に更新する必要があります（一例は[RFC7622]です）。プロトコル実装を協調せずに更新することは、相互運用性とセキュリティーに悪影響を及ぼすおそれがあるため、推奨されません。

2. Terminology

2. 用語

A "username" or "user identifier" is a string of characters designating an account on a computing device or system, often but not necessarily for use by a person. Although some devices and systems might allow a username to be part or all of a person's name and a person might want their account designator to be part or all of their name, because of the complexities involved, that outcome is not guaranteed for all human names on all computing devices or systems that follow the rules defined in this specification. Protocol designers and application developers who wish to allow a wider range of characters are encouraged to consider a separation between more restrictive account identifiers and more expressive display names or nicknames (see [RFC8266]).

「ユーザー名（username）」または「ユーザー識別子（user identifier）」とは、コンピューティングデバイスやシステム上のアカウントを指定する文字の並びであり、必ずではないものの多くの場合、人が使用するためのものです。デバイスやシステムによってはユーザー名を人名の一部または全部にすることを許可する場合があり、また人は自分のアカウントの指定子を自分の名前の一部または全部にしたいと考えるかもしれませんが、関係する複雑さのため、この仕様で定義する規則に従うすべてのコンピューティングデバイスやシステム上で、すべての人名についてそれが実現できるとは保証されません。より広い範囲の文字を許可したいプロトコル設計者やアプリケーション開発者は、より制限的なアカウント識別子と、より表現力の高い表示名やニックネームとを分離することを検討するよう推奨されます（[RFC8266]を参照）。

A "password" is a string of characters that allows access to a computing device or system, often associated with a particular username. A password is not literally limited to a word, because a password could be a passphrase consisting of more than one word, perhaps separated by spaces, punctuation, or other non-alphanumeric characters.

「パスワード（password）」とは、コンピューティングデバイスやシステムへのアクセスを可能にする文字の並びであり、多くの場合、特定のユーザー名に関連付けられています。パスワードは文字どおり1つの単語に限定されるわけではありません。パスワードは、2つ以上の単語からなり、スペース、句読点、その他の英数字以外の文字で区切られることもあるパスフレーズである可能性があるからです。

Some SASL mechanisms (e.g., CRAM-MD5, DIGEST-MD5, and SCRAM) specify that the authentication identity used in the context of such mechanisms is a "simple username" (see Section 2 of [RFC4422] as well as [RFC4013]). Various application technologies also assume that the identity of a user or account takes the form of a username (e.g., authentication for the Hypertext Transfer Protocol as specified in [RFC7617] and [RFC7616]), whether or not they use SASL. Note well that the exact form of a username in any particular SASL mechanism or application technology is a matter for implementation and deployment; note also that a username does not necessarily map to any particular application identifier.

一部のSASLメカニズム（たとえば、CRAM-MD5、DIGEST-MD5、SCRAM）は、そのようなメカニズムの文脈で使用される認証アイデンティティーが「単純ユーザー名（simple username）」であると規定しています（[RFC4422]のセクション2と[RFC4013]を参照）。さまざまなアプリケーション技術も、SASLを使用するかどうかにかかわらず、ユーザーやアカウントのアイデンティティーがユーザー名の形をとることを前提としています（たとえば、[RFC7617]と[RFC7616]で規定されているHypertext Transfer Protocolの認証）。特定のSASLメカニズムやアプリケーション技術におけるユーザー名の正確な形式は、実装と展開の問題であることに十分注意してください。また、ユーザー名は必ずしも特定のアプリケーション識別子に対応付けられるわけではないことにも注意してください。

Many important terms used in this document are defined in [RFC5890], [RFC6365], [RFC8264], and [Unicode]. The term "non-ASCII space" refers to any Unicode code point having a Unicode general category of "Zs", naturally with the exception of SPACE (U+0020).

この文書で使用する重要な用語の多くは、[RFC5890]、[RFC6365]、[RFC8264]、[Unicode]で定義されています。「非ASCIIの空白（non-ASCII space）」という用語は、Unicode一般カテゴリーが「Zs」である任意のUnicodeコードポイントを指します。ただし当然ながら、SPACE（U+0020）は除きます。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、「要求されています（REQUIRED）」、「することになります（SHALL）」、「することはありません（SHALL NOT）」、「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。ただし、ここに示すようにすべて大文字で表示される場合に限ります。

3. Usernames

3. ユーザー名

3.1. Definition

3.1. 定義

This document specifies that a username is a string of Unicode code points [Unicode] that is structured as an ordered sequence of "userparts" and expressed in a standard Unicode Encoding Form (such as UTF-8 [RFC3629]). A userpart is allowed to contain only code points that are allowed by the PRECIS IdentifierClass defined in Section 4.2 of [RFC8264] and thus consists almost exclusively of letters and digits. A username can consist of a single userpart or a space-separated sequence of userparts.

この文書では、ユーザー名を、「ユーザーパート（userpart）」の順序付き並びとして構成され、標準のUnicodeエンコーディング形式（UTF-8[RFC3629]など）で表現される、Unicodeコードポイント[Unicode]の文字列と規定します。ユーザーパートには、[RFC8264]のセクション4.2で定義されているPRECIS IdentifierClassで許可されたコードポイントだけを含めることができ、そのためユーザーパートはほぼ文字と数字だけで構成されます。ユーザー名は、1つのユーザーパートで構成することも、スペースで区切られたユーザーパートの並びで構成することもできます。

The syntax for a username is defined as follows, using the Augmented Backus-Naur Form (ABNF) [RFC5234].

ユーザー名の構文は、拡張バッカス・ナウア記法（ABNF）[RFC5234]を使用して次のように定義されます。

   username   = userpart *(1*SP userpart)
   userpart   = 1*(idpoint)
                ;
                ; an "idpoint" is a Unicode code point that
                ; can be contained in a string conforming to
                ; the PRECIS IdentifierClass
                ;

   username   = userpart *(1*SP userpart)
   userpart   = 1*(idpoint)
                ;
                ; an "idpoint" is a Unicode code point that
                ; can be contained in a string conforming to
                ; the PRECIS IdentifierClass
                ;

All code points and blocks not explicitly allowed in the PRECIS IdentifierClass are disallowed; this includes private-use code points, surrogate code points, and the other code points and blocks that were defined as "Prohibited Output" in Section 2.3 of [RFC4013] (when corrected per [Err1812]). In addition, common constructions such as "user@example.com" (e.g., the Network Access Identifier from [RFC7542]) are allowed as usernames under this specification, as they were under [RFC4013].

PRECIS IdentifierClassで明示的に許可されていないすべてのコードポイントとブロックは不許可となります。これには、私用コードポイント、サロゲートコードポイント、および[RFC4013]のセクション2.3で「Prohibited Output」と定義されていた（[Err1812]で訂正したもの）その他のコードポイントとブロックが含まれます。加えて、「user@example.com」のような一般的な構成（たとえば、[RFC7542]のNetwork Access Identifier）は、[RFC4013]のもとでそうであったように、この仕様のもとでもユーザー名として許可されます。

Implementation Note: The username construct defined in this document does not necessarily match what all deployed applications might refer to as a "username" or "userid" but instead provides a relatively safe subset of Unicode code points that can be used in existing SASL mechanisms and in application protocols that use SASL, and even in most application protocols that do not currently use SASL.

実装上の注意：この文書で定義するユーザー名の構成は、展開済みのすべてのアプリケーションが「ユーザー名（username）」や「ユーザーID（userid）」と呼ぶものと必ずしも一致するわけではありません。そうではなく、既存のSASLメカニズムや、SASLを使用するアプリケーションプロトコル、さらには現在SASLを使用していないほとんどのアプリケーションプロトコルでも使用できる、Unicodeコードポイントの比較的安全なサブセットを提供するものです。

A username MUST NOT be zero bytes in length. This rule is to be enforced after any normalization and mapping of code points.

ユーザー名の長さは0バイトであってはなりません（MUST NOT）。この規則は、コードポイントの正規化とマッピングをすべて行った後に強制されます。

This specification defines two profiles for usernames: the UsernameCaseMapped profile performs case mapping, and the UsernameCasePreserved performs case preservation (see further discussion under Section 3.2).

この仕様は、ユーザー名について2つのプロファイルを定義します。UsernameCaseMappedプロファイルは大文字小文字マッピングを行い、UsernameCasePreservedは大文字小文字の保持を行います（セクション3.2のさらなる議論を参照）。

In protocols that provide usernames as input to a cryptographic algorithm such as a hash function, the client will need to perform enforcement of the rules for the UsernameCaseMapped or UsernameCasePreserved profile before applying the algorithm.

ハッシュ関数などの暗号アルゴリズムへの入力としてユーザー名を提供するプロトコルでは、クライアントは、アルゴリズムを適用する前に、UsernameCaseMappedプロファイルまたはUsernameCasePreservedプロファイルの規則の強制を行う必要があります。

3.2. Case Mapping vs. Case Preservation

3.2. 大文字小文字マッピングと大文字小文字の保持

In order to accommodate the widest range of username constructs in applications, this document defines two username profiles: UsernameCaseMapped and UsernameCasePreserved. These two profiles differ only in their use (or not) of the Case Mapping Rule and are otherwise identical.

アプリケーションにおけるユーザー名の構成を最も幅広く受け入れるために、この文書は、UsernameCaseMappedとUsernameCasePreservedという2つのユーザー名プロファイルを定義します。これら2つのプロファイルの違いは、大文字小文字マッピング規則を使用するかどうかだけであり、それ以外は同一です。

Case mapping is a matter for the application protocol, protocol implementation, or end deployment. In general, this document suggests that it is preferable to apply the UsernameCaseMapped profile and therefore perform case mapping, because not doing so can lead to false accepts during authentication and authorization (as described in [RFC6943]) and can result in confusion among end users, given the prevalence of case mapping in many existing protocols and applications. However, there can be good reasons to apply the UsernameCasePreserved profile and thus not perform case mapping, such as backward compatibility with deployed infrastructure.

大文字小文字マッピングは、アプリケーションプロトコル、プロトコル実装、または最終的な展開の問題です。一般に、この文書は、UsernameCaseMappedプロファイルを適用して大文字小文字マッピングを行うほうが望ましいと提案します。そうしないと、認証と認可の際に誤受理が発生するおそれがあり（[RFC6943]で説明されているとおり）、また多くの既存のプロトコルやアプリケーションで大文字小文字マッピングが広く行われていることを考えると、エンドユーザーの混乱を招くおそれがあるからです。ただし、展開済みのインフラストラクチャーとの後方互換性など、UsernameCasePreservedプロファイルを適用して大文字小文字マッピングを行わないことにも正当な理由がありえます。

In particular:

具体的には次のとおりです。

  • SASL mechanisms that follow the recommendations in this document MUST specify whether and when case mapping is to be applied to authentication identifiers. Because case mapping results in information loss, in order to retain that information for as long as possible during processing, implementations SHOULD delay any case mapping to the last possible moment, such as when doing a lookup by username, performing username comparisons, or generating a cryptographic salt from a username (if the last possible moment happens on a server, then decisions about case mapping can be a matter of service deployment policy). In keeping with [RFC4422], SASL mechanisms are not to apply this or any other profile to authorization identifiers, only to authentication identifiers.
  • Application protocols that use SASL (such as IMAP [RFC3501] and the Extensible Messaging and Presence Protocol (XMPP) [RFC6120]) and that directly reuse this profile MUST specify whether or not case mapping is to be applied to authorization identifiers. Such "SASL application protocols" SHOULD delay any case mapping of authorization identifiers to the last possible moment, which happens to necessarily be on the server side (this enables decisions about case mapping to be a matter of service deployment policy). In keeping with [RFC4422], SASL application protocols are not to apply this or any other profile to authentication identifiers, only to authorization identifiers.
  • Application protocols that do not use SASL (such as HTTP authentication with the HTTP Basic and Digest schemes as specified in [RFC7617] and [RFC7616]) but that directly reuse this profile MUST specify whether and when case mapping is to be applied to authentication identifiers or authorization identifiers, or both. Such "non-SASL application protocols" SHOULD delay any case mapping to the last possible moment, such as when doing a lookup by username, performing username comparisons, or generating a cryptographic salt from a username (if the last possible moment happens on the server, then decisions about case mapping can be a matter of service deployment policy).
  • この文書の推奨事項に従うSASLメカニズムは、認証識別子に大文字小文字マッピングを適用するかどうか、および適用する場合はいつ適用するかを規定しなければなりません（MUST）。大文字小文字マッピングは情報の損失をもたらすため、処理中にその情報をできるだけ長く保持するために、実装は大文字小文字マッピングを可能な限り最後の時点まで遅らせるべきです（SHOULD）。その時点とは、たとえば、ユーザー名による検索を行うとき、ユーザー名の比較を行うとき、ユーザー名から暗号ソルトを生成するときなどです（可能な限り最後の時点がサーバー上で訪れる場合、大文字小文字マッピングに関する決定はサービスの展開ポリシーの問題とすることができます）。[RFC4422]に従い、SASLメカニズムは、このプロファイルやその他のプロファイルを認可識別子には適用せず、認証識別子にのみ適用します。
  • SASLを使用し（IMAP [RFC3501]やExtensible Messaging and Presence Protocol（XMPP）[RFC6120]など）、かつこのプロファイルを直接再利用するアプリケーションプロトコルは、認可識別子に大文字小文字マッピングを適用するかどうかを規定しなければなりません（MUST）。そのような「SASLアプリケーションプロトコル」は、認可識別子の大文字小文字マッピングを可能な限り最後の時点まで遅らせるべきです（SHOULD）。その時点は必然的にサーバー側となります（これにより、大文字小文字マッピングに関する決定をサービスの展開ポリシーの問題とすることができます）。[RFC4422]に従い、SASLアプリケーションプロトコルは、このプロファイルやその他のプロファイルを認証識別子には適用せず、認可識別子にのみ適用します。
  • SASLを使用しない（[RFC7617]と[RFC7616]で規定されているHTTP BasicスキームとHTTP Digestスキームを用いたHTTP認証など）が、このプロファイルを直接再利用するアプリケーションプロトコルは、認証識別子と認可識別子のどちらか、または両方に大文字小文字マッピングを適用するかどうか、および適用する場合はいつ適用するかを規定しなければなりません（MUST）。そのような「非SASLアプリケーションプロトコル」は、大文字小文字マッピングを可能な限り最後の時点まで遅らせるべきです（SHOULD）。その時点とは、たとえば、ユーザー名による検索を行うとき、ユーザー名の比較を行うとき、ユーザー名から暗号ソルトを生成するときなどです（可能な限り最後の時点がサーバー上で訪れる場合、大文字小文字マッピングに関する決定はサービスの展開ポリシーの問題とすることができます）。

If the specification for a SASL mechanism, SASL application protocol, or non-SASL application protocol uses the UsernameCaseMapped profile, it MUST clearly describe whether case mapping is to be applied at the level of the protocol itself, implementations thereof, or service deployments (each of these approaches can be legitimate, depending on the application in question).

SASLメカニズム、SASLアプリケーションプロトコル、または非SASLアプリケーションプロトコルの仕様がUsernameCaseMappedプロファイルを使用する場合、その仕様は、大文字小文字マッピングをプロトコル自体のレベルで適用するのか、その実装のレベルで適用するのか、サービスの展開のレベルで適用するのかを明確に記述しなければなりません（MUST）（これらのアプローチはいずれも、対象となるアプリケーションによっては正当なものとなりえます）。

3.3. UsernameCaseMapped Profile

3.3. UsernameCaseMappedプロファイル

3.3.1. Rules

3.3.1. 規則

The following rules are defined for use within the UsernameCaseMapped profile of the PRECIS IdentifierClass.

PRECIS IdentifierClassのUsernameCaseMappedプロファイル内で使用するために、次の規則を定義します。

  1. Width Mapping Rule: Map fullwidth and halfwidth code points to their decomposition mappings (see Unicode Standard Annex #11 [UAX11]).
  2. Additional Mapping Rule: There is no additional mapping rule.
  3. Case Mapping Rule: Map uppercase and titlecase code points to their lowercase equivalents, preferably using the Unicode toLowerCase() operation as defined in the Unicode Standard [Unicode]; see further discussion in Section 3.2.
  4. Normalization Rule: Apply Unicode Normalization Form C (NFC) to all strings.
  5. Directionality Rule: Apply the "Bidi Rule" defined in [RFC5893] to strings that contain right-to-left code points (i.e., each of the six conditions of the Bidi Rule must be satisfied); for strings that do not contain right-to-left code points, there is no special processing for directionality.
  1. 幅マッピング規則：全角および半角のコードポイントを、その分解マッピングにマッピングします（Unicode標準付属書#11[UAX11]を参照）。
  2. 追加マッピング規則：追加マッピング規則はありません。
  3. 大文字小文字マッピング規則：大文字とタイトルケースのコードポイントを、対応する小文字にマッピングします。その際には、Unicode標準[Unicode]で定義されているUnicodeのtoLowerCase()操作を使用することが望まれます。セクション3.2のさらなる議論を参照してください。
  4. 正規化規則：すべての文字列にUnicode正規化形式C（NFC）を適用します。
  5. 方向性規則：右から左に書くコードポイントを含む文字列には、[RFC5893]で定義されている「Bidi Rule」を適用します（つまり、Bidi Ruleの6つの条件のそれぞれが満たされなければなりません）。右から左に書くコードポイントを含まない文字列については、方向性に関する特別な処理はありません。

3.3.2. Preparation

3.3.2. 準備

An entity that prepares an input string for subsequent enforcement according to this profile MUST proceed as follows (applying the steps in the order shown).

このプロファイルに従って、後続の強制のために入力文字列を準備するエンティティーは、次のように処理しなければなりません（MUST）（手順は示された順序で適用します）。

  1. Apply the width mapping rule specified in Section 3.3.1. It is necessary to apply the rule at this point because otherwise the PRECIS "HasCompat" category specified in Section 9.17 of [RFC8264] would forbid fullwidth and halfwidth code points.
  2. Ensure that the string consists only of Unicode code points that are explicitly allowed by the PRECIS IdentifierClass defined in Section 4.2 of [RFC8264].
  1. セクション3.3.1で規定されている幅マッピング規則を適用します。この時点でこの規則を適用する必要があるのは、そうしないと、[RFC8264]のセクション9.17で規定されているPRECISの「HasCompat」カテゴリーによって、全角と半角のコードポイントが禁止されてしまうからです。
  2. 文字列が、[RFC8264]のセクション4.2で定義されているPRECIS IdentifierClassで明示的に許可されたUnicodeコードポイントだけで構成されていることを確認します。

  2. Normalization Rule
  3. Directionality Rule
  1. 大文字小文字マッピング規則

  3. 方向性規則

3.5. Application-Layer Constructs

3.5. アプリケーション層の構成要素

Both the UsernameCaseMapped and UsernameCasePreserved profiles enable an application protocol, implementation, or deployment to create application-layer constructs such as a username that is a space-separated set of userparts like "Firstname Middlename Lastname". Such a construct is not a profile of the PRECIS IdentifierClass, because SPACE (U+0020) is not allowed in the IdentifierClass; however, it can be created at the application layer because SPACE (U+0020) can be used as a separator between instances of the PRECIS IdentifierClass (e.g., userparts as defined in this specification).

UsernameCaseMappedプロファイルとUsernameCasePreservedプロファイルはどちらも、アプリケーションプロトコル、実装、または展開が、アプリケーション層の構成要素を作成できるようにします。たとえば、「Firstname Middlename Lastname」のような、ユーザーパートをスペースで区切った集合であるユーザー名です。そのような構成要素は、PRECIS IdentifierClassのプロファイルではありません。IdentifierClassではSPACE（U+0020）が許可されていないからです。しかし、SPACE（U+0020）はPRECIS IdentifierClassのインスタンス（たとえば、この仕様で定義するユーザーパート）の間の区切りとして使用できるため、そのような構成要素はアプリケーション層で作成できます。

例2と例3について：ドイツ語の表記ではエスツェット「ß」（LATIN SMALL LETTER SHARP S、U+00DF）はおおむね2文字の「ss」と交換可能に使用できますが、これらの例のユーザーパートは異なるものです。そのため、（望ましい場合は）一方が登録されているときにもう一方を許可しない登録ポリシーを、サーバーが強制する必要があるでしょう。

Regarding examples 5, 6, and 7: optional case mapping of "Σ" (GREEK CAPITAL LETTER SIGMA, U+03A3) to the lowercase character "σ" (GREEK SMALL LETTER SIGMA, U+03C3) during comparison would result in matching the userparts in examples 5 and 6; however, because the PRECIS mapping rules do not account for the special status of the character "ς" (GREEK SMALL LETTER FINAL SIGMA, U+03C2), the userparts in examples 5 and 7 or examples 6 and 7 would not be matched during comparison.

4. Passwords

4. パスワード

4.1. Definition

4.1. 定義

This document specifies that a password is a string of Unicode code points [Unicode] that is conformant to the OpaqueString profile (specified below) of the PRECIS FreeformClass defined in Section 4.3 of [RFC8264] and expressed in a standard Unicode Encoding Form (such as UTF-8 [RFC3629]).

この文書では、パスワードを、[RFC8264]のセクション4.3で定義されているPRECIS FreeformClassのOpaqueStringプロファイル（後述）に準拠し、標準のUnicodeエンコーディング形式（UTF-8[RFC3629]など）で表現される、Unicodeコードポイント[Unicode]の文字列と規定します。

The syntax for a password is defined as follows, using the Augmented Backus-Naur Form (ABNF) [RFC5234].

パスワードの構文は、拡張バッカス・ナウア記法（ABNF）[RFC5234]を使用して次のように定義されます。

   password   = 1*(freepoint)
                ;
                ; a "freepoint" is a Unicode code point that
                ; can be contained in a string conforming to
                ; the PRECIS FreeformClass
                ;

   password   = 1*(freepoint)
                ;
                ; a "freepoint" is a Unicode code point that
                ; can be contained in a string conforming to
                ; the PRECIS FreeformClass
                ;

All code points and blocks not explicitly allowed in the PRECIS FreeformClass are disallowed; this includes private-use code points, surrogate code points, and the other code points and blocks defined as "Prohibited Output" in Section 2.3 of [RFC4013] (when corrected per [Err1812]).

PRECIS FreeformClassで明示的に許可されていないすべてのコードポイントとブロックは不許可となります。これには、私用コードポイント、サロゲートコードポイント、および[RFC4013]のセクション2.3で「Prohibited Output」と定義されている（[Err1812]で訂正したもの）その他のコードポイントとブロックが含まれます。

A password MUST NOT be zero bytes in length. This rule is to be enforced after any normalization and mapping of code points.

パスワードの長さは0バイトであってはなりません（MUST NOT）。この規則は、コードポイントの正規化とマッピングをすべて行った後に強制されます。

Note: Some existing systems allow an empty string in places where a password would be expected (e.g., command-line tools that might be called from an automated script, or servers that might need to be restarted without human intervention). From the perspective of this document (and RFC 4013 before it), these empty strings are not passwords but are workarounds for the practical difficulty of using passwords in certain scenarios.

注：既存のシステムの中には、パスワードが期待される場所で空文字列を許可するものがあります（たとえば、自動化されたスクリプトから呼び出される可能性のあるコマンドラインツールや、人の介入なしに再起動する必要がある可能性のあるサーバーなど）。この文書（およびそれ以前のRFC 4013）の観点からは、これらの空文字列はパスワードではなく、特定のシナリオでパスワードを使用することの実際上の困難に対する回避策です。

Note: The prohibition of zero-length passwords is not a recommendation regarding password strength (because a password of only one byte is highly insecure) but is meant to prevent applications from mistakenly omitting a password entirely; such an outcome is possible when internationalized strings are accepted, because a non-empty sequence of characters can result in a zero-length password after canonicalization.

注：長さ0のパスワードの禁止は、パスワードの強度に関する推奨ではありません（1バイトだけのパスワードはきわめて安全でないからです）。そうではなく、アプリケーションが誤ってパスワードを完全に省略してしまうことを防ぐためのものです。国際化文字列を受け入れる場合、空でない文字の並びが正準化後に長さ0のパスワードになることがあるため、そのような結果が起こりえます。

In protocols that provide passwords as input to a cryptographic algorithm such as a hash function, the client will need to perform enforcement of the rules for the OpaqueString profile before applying the algorithm, because the password is not available to the server in plaintext form.

ハッシュ関数などの暗号アルゴリズムへの入力としてパスワードを提供するプロトコルでは、サーバーはパスワードを平文の形で利用できないため、クライアントは、アルゴリズムを適用する前にOpaqueStringプロファイルの規則の強制を行う必要があります。

4.2. OpaqueString Profile

4.2. OpaqueStringプロファイル

The definition of the OpaqueString profile is provided in the following sections, including detailed information about preparation, enforcement, and comparison (for details on the distinction between these actions, refer to [RFC8264]).

OpaqueStringプロファイルの定義は、準備、強制、比較に関する詳細な情報を含め、以下のセクションで示します（これらの操作の違いの詳細については、[RFC8264]を参照してください）。

4.2.1. Preparation

4.2.1. 準備

An entity that prepares a string according to this profile MUST ensure that the string consists only of Unicode code points that are explicitly allowed by the FreeformClass string class defined in [RFC8264].

このプロファイルに従って文字列を準備するエンティティーは、その文字列が、[RFC8264]で定義されているFreeformClass文字列クラスで明示的に許可されたUnicodeコードポイントだけで構成されていることを確認しなければなりません（MUST）。

4.2.2. Enforcement

4.2.2. 強制

An entity that performs enforcement according to this profile MUST prepare a string as described in Section 4.2.1 and MUST also apply the rules specified below for the OpaqueString profile (these rules MUST be applied in the order shown):

このプロファイルに従って強制を行うエンティティーは、セクション4.2.1で説明されているように文字列を準備しなければなりません（MUST）。また、以下に規定するOpaqueStringプロファイルの規則を適用しなければなりません（MUST）（これらの規則は示された順序で適用しなければなりません（MUST））。

  1. Width Mapping Rule: Fullwidth and halfwidth code points MUST NOT be mapped to their decomposition mappings (see Unicode Standard Annex #11 [UAX11]).
  2. Additional Mapping Rule: Any instances of non-ASCII space MUST be mapped to SPACE (U+0020); a non-ASCII space is any Unicode code point having a Unicode general category of "Zs", with the exception of SPACE (U+0020). As was the case in RFC 4013, the inclusion of only SPACE (U+0020) prevents confusion with various non-ASCII space code points, many of which are difficult to reproduce across different input methods.
  3. Case Mapping Rule: There is no case mapping rule (because mapping uppercase and titlecase code points to their lowercase equivalents would lead to false accepts and thus to reduced security).
  4. Normalization Rule: Unicode Normalization Form C (NFC) MUST be applied to all strings.
  5. Directionality Rule: There is no directionality rule. The "Bidi Rule" (defined in [RFC5893]) and similar rules are unnecessary and inapplicable to passwords, because they can reduce the repertoire of characters that are allowed in a string and therefore reduce the amount of entropy that is possible in a password. Such rules are intended to minimize the possibility that the same string will be displayed differently on a layout system set for right-to-left display and a layout system set for left-to-right display; however, passwords are typically not displayed at all and are rarely meant to be interoperable across different layout systems in the way that non-secret strings like domain names and usernames are. Furthermore, it is perfectly acceptable for opaque strings other than passwords to be presented differently in different layout systems, as long as the presentation is consistent in any given layout system.
  1. 幅マッピング規則：全角および半角のコードポイントを、その分解マッピングにマッピングしてはなりません（MUST NOT）（Unicode標準付属書#11[UAX11]を参照）。
  2. 追加マッピング規則：非ASCIIの空白はすべてSPACE（U+0020）にマッピングしなければなりません（MUST）。非ASCIIの空白とは、Unicode一般カテゴリーが「Zs」である任意のUnicodeコードポイントです。ただし、SPACE（U+0020）は除きます。RFC 4013の場合と同様に、SPACE（U+0020）だけを含めることで、さまざまな非ASCIIの空白のコードポイントとの混同を防ぎます。それらの多くは、異なる入力方式の間で再現するのが困難です。
  3. 大文字小文字マッピング規則：大文字小文字マッピング規則はありません（大文字とタイトルケースのコードポイントを対応する小文字にマッピングすると、誤受理につながり、その結果セキュリティーが低下するからです）。
  4. 正規化規則：すべての文字列にUnicode正規化形式C（NFC）を適用しなければなりません（MUST）。
  5. 方向性規則：方向性規則はありません。「Bidi Rule」（[RFC5893]で定義）や類似の規則は、パスワードには不要であり、適用できません。そうした規則は、文字列で許可される文字のレパートリーを減らし、したがってパスワードで可能なエントロピーの量を減らす可能性があるからです。そうした規則は、右から左の表示に設定されたレイアウトシステムと、左から右の表示に設定されたレイアウトシステムとで、同じ文字列が異なって表示される可能性を最小限にすることを意図しています。しかし、パスワードは通常まったく表示されず、ドメイン名やユーザー名のような秘密でない文字列のように、異なるレイアウトシステム間で相互運用可能であることが意図されることはまれです。さらに、パスワード以外の不透明な文字列が、異なるレイアウトシステムで異なって表示されることも、任意のレイアウトシステム内で表示が一貫している限り、まったく問題ありません。

The result of the foregoing operations is an output string that conforms to the OpaqueString profile. Until an implementation produces such an output string, it MUST NOT treat the string as conforming (in particular, it MUST NOT assume that an input string is conforming before the enforcement operation has been completed).

前述の操作の結果は、OpaqueStringプロファイルに準拠する出力文字列です。実装は、そのような出力文字列を生成するまで、その文字列を準拠しているものとして扱ってはなりません（MUST NOT）（特に、強制の操作が完了する前に、入力文字列が準拠していると仮定してはなりません（MUST NOT））。

4.2.3. Comparison

4.2.3. 比較

An entity that performs comparison of two strings according to this profile MUST prepare each string as specified in Section 4.2.1 and then MUST enforce the rules specified in Section 4.2.2. The two strings are to be considered equivalent if and only if they are an exact octet-for-octet match (sometimes called "bit-string identity").

このプロファイルに従って2つの文字列の比較を行うエンティティーは、セクション4.2.1で規定されているように各文字列を準備しなければなりません（MUST）。次に、セクション4.2.2で規定されている規則を強制しなければなりません（MUST）。2つの文字列は、オクテット単位で完全に一致する場合（「ビット列の同一性（bit-string identity）」と呼ばれることもあります）に限り、等価であると見なされます。

Until an implementation determines whether two strings are to be considered equivalent, it MUST NOT treat them as equivalent (in particular, it MUST NOT assume that two input strings are equivalent before the comparison operation has been completed).

実装は、2つの文字列を等価と見なすべきかどうかを判断するまで、それらを等価として扱ってはなりません（MUST NOT）（特に、比較の操作が完了する前に、2つの入力文字列が等価であると仮定してはなりません（MUST NOT））。

See Section 8.2 regarding comparison of passwords and passphrases.

パスワードとパスフレーズの比較については、セクション8.2を参照してください。

5. Use in Application Protocols

5. アプリケーションプロトコルでの使用

This specification defines only the PRECIS-based rules for the handling of strings conforming to the UsernameCaseMapped and UsernameCasePreserved profiles of the PRECIS IdentifierClass, and strings conforming to the OpaqueString profile of the PRECIS FreeformClass. It is the responsibility of an application protocol to specify the protocol slots in which such strings can appear, the entities that are expected to enforce the rules governing such strings, and at what points during protocol processing or interface handling the rules need to be enforced. See Section 6 of [RFC8264] for guidelines on using PRECIS profiles in applications.

この仕様は、PRECIS IdentifierClassのUsernameCaseMappedプロファイルとUsernameCasePreservedプロファイルに準拠する文字列、およびPRECIS FreeformClassのOpaqueStringプロファイルに準拠する文字列を扱うための、PRECISに基づく規則だけを定義します。そのような文字列が現れうるプロトコルスロット、そのような文字列を支配する規則を強制することが期待されるエンティティー、およびプロトコル処理やインターフェイスの処理中のどの時点で規則を強制する必要があるかを規定するのは、アプリケーションプロトコルの責任です。アプリケーションでPRECISプロファイルを使用するためのガイドラインについては、[RFC8264]のセクション6を参照してください。

Above and beyond the PRECIS-based rules specified here, application protocols can also define application-specific rules governing such strings (rules regarding minimum or maximum length, further restrictions on allowable code points or character ranges, safeguards to mitigate the effects of visually similar characters, etc.), application-layer constructs (see Section 3.5), and related matters.

ここで規定するPRECISに基づく規則に加えて、アプリケーションプロトコルは、そのような文字列を支配するアプリケーション固有の規則（最小長や最大長に関する規則、許可されるコードポイントや文字範囲に対するさらなる制限、視覚的に類似した文字の影響を緩和するための保護策など）、アプリケーション層の構成要素（セクション3.5を参照）、および関連する事項も定義できます。

Some PRECIS profile definitions encourage entities that enforce the rules to be liberal in what they accept. However, for usernames and passwords such a policy can be problematic, because it can lead to false accepts. An in-depth discussion can be found in [RFC6943].

PRECISプロファイルの定義の中には、規則を強制するエンティティーに対して、受け入れるものについて寛容であることを推奨するものがあります。しかし、ユーザー名とパスワードについては、そのようなポリシーは誤受理につながるおそれがあるため、問題となりえます。詳細な議論は[RFC6943]にあります。

Applying the rules for any given PRECIS profile is not necessarily an idempotent procedure for all code points. Therefore, an implementation SHOULD apply the rules repeatedly until the output string is stable; if the output string does not stabilize after reapplying the rules three (3) additional times after the first application, the implementation SHOULD terminate application of the rules and reject the input string as invalid.

任意のPRECISプロファイルの規則の適用は、すべてのコードポイントについて冪等な手続きであるとは限りません。したがって、実装は、出力文字列が安定するまで規則を繰り返し適用するべきです（SHOULD）。最初の適用の後に規則をさらに3回再適用しても出力文字列が安定しない場合、実装は規則の適用を終了し、入力文字列を無効として拒否するべきです（SHOULD）。

6. Migration

6. 移行

The rules defined in this specification differ slightly from those defined by the SASLprep specification [RFC4013] (but not from [RFC7613]). In order to smooth the process of migrating from SASLprep to the approach defined herein, the following sections describe these differences, along with their implications for migration, in more detail.

この仕様で定義する規則は、SASLprep仕様[RFC4013]で定義されている規則とはわずかに異なります（ただし、[RFC7613]とは異なりません）。SASLprepからここで定義するアプローチへの移行プロセスを円滑にするために、以下のセクションでは、これらの違いと移行への影響を詳しく説明します。

6.1. Usernames

6.1. ユーザー名

Deployments that currently use SASLprep for handling usernames might need to scrub existing data when they migrate to the rules defined in this specification. In particular:

現在ユーザー名の処理にSASLprepを使用している展開では、この仕様で定義する規則に移行する際に、既存のデータを洗浄する必要があるかもしれません。具体的には次のとおりです。

  • SASLprep specified the use of Unicode Normalization Form KC (NFKC), whereas the UsernameCaseMapped and UsernameCasePreserved profiles employ Unicode Normalization Form C (NFC). In practice, this change is unlikely to cause significant problems, because NFKC provides methods for mapping Unicode code points with compatibility equivalents to those equivalents, whereas the PRECIS IdentifierClass entirely disallows Unicode code points with compatibility equivalents (i.e., during comparison, NFKC is more "aggressive" about finding matches than NFC). A few examples might suffice to indicate the nature of the problem:

    1. "ſ" (LATIN SMALL LETTER LONG S, U+017F) is compatibility equivalent to "s" (LATIN SMALL LETTER S, U+0073).
    2. "Ⅳ" (ROMAN NUMERAL FOUR, U+2163) is compatibility equivalent to "I" (LATIN CAPITAL LETTER I, U+0049) and "V" (LATIN CAPITAL LETTER V, U+0056).
    3. "ﬁ" (LATIN SMALL LIGATURE FI, U+FB01) is compatibility equivalent to "f" (LATIN SMALL LETTER F, U+0066) and "i" (LATIN SMALL LETTER I, U+0069).

    Under SASLprep, the use of NFKC also handled the mapping of fullwidth and halfwidth code points to their decomposition mappings.

    For migration purposes, operators might want to search their database of usernames for names containing Unicode code points with compatibility equivalents and, where there is no conflict, map those code points to their equivalents. Naturally, it is possible that during this process the operator will discover conflicting usernames; for instance, "HENRYIV" with the last two code points being LATIN CAPITAL LETTER I (U+0049) and LATIN CAPITAL LETTER V (U+0056) as opposed to "HENRYⅣ" with the last character being "Ⅳ" (ROMAN NUMERAL FOUR, U+2163), which is compatibility equivalent to U+0049 and U+0056). In these cases, the operator will need to determine how to proceed, for instance, by disabling the account whose name contains a Unicode code point with a compatibility equivalent. Such cases are probably rare, but it is important for operators to be aware of them.

  • SASLprep mapped the "characters commonly mapped to nothing" (from Appendix B.1 of [RFC3454]) to nothing, whereas the PRECIS IdentifierClass entirely disallows most of these code points, which correspond to the code points from the PRECIS "M" category defined under Section 9.13 of [RFC8264]. For migration purposes, the operator might want to remove from usernames any code points contained in the PRECIS "M" category (e.g., SOFT HYPHEN (U+00AD)). Because these code points would have been "mapped to nothing" in Stringprep, in practice a user would not notice the difference if, upon migration to PRECIS, the code points are removed.
  • SASLprep allowed uppercase and titlecase code points, whereas the UsernameCaseMapped profile maps uppercase and titlecase code points to their lowercase equivalents (by contrast, the UsernameCasePreserved profile matches SASLprep in this regard). For migration purposes, the operator can use either the UsernameCaseMapped profile (thus losing the case information) or the UsernameCasePreserved profile (thus ignoring case difference when comparing usernames).

  • SASLprepはUnicode正規化形式KC（NFKC）の使用を規定していましたが、UsernameCaseMappedプロファイルとUsernameCasePreservedプロファイルはUnicode正規化形式C（NFC）を採用しています。実際には、この変更が重大な問題を引き起こす可能性は低いでしょう。なぜなら、NFKCは互換等価物を持つUnicodeコードポイントをその等価物にマッピングする方法を提供するのに対し、PRECIS IdentifierClassは互換等価物を持つUnicodeコードポイントを完全に不許可とするからです（つまり、比較の際には、NFKCのほうがNFCよりも一致を見つけることに関して「積極的」です）。問題の性質を示すには、いくつかの例で十分でしょう。

    1. 「ſ」（LATIN SMALL LETTER LONG S、U+017F）は、「s」（LATIN SMALL LETTER S、U+0073）と互換等価です。
    2. 「Ⅳ」（ROMAN NUMERAL FOUR、U+2163）は、「I」（LATIN CAPITAL LETTER I、U+0049）と「V」（LATIN CAPITAL LETTER V、U+0056）と互換等価です。
    3. 「ﬁ」（LATIN SMALL LIGATURE FI、U+FB01）は、「f」（LATIN SMALL LETTER F、U+0066）と「i」（LATIN SMALL LETTER I、U+0069）と互換等価です。

    SASLprepのもとでは、NFKCの使用によって、全角および半角のコードポイントをその分解マッピングにマッピングすることも扱われていました。

    移行のために、運用者は、ユーザー名のデータベースから互換等価物を持つUnicodeコードポイントを含む名前を検索し、競合がない場合には、それらのコードポイントをその等価物にマッピングしたいと考えるかもしれません。当然ながら、この過程で運用者が競合するユーザー名を発見する可能性もあります。たとえば、最後の2つのコードポイントがLATIN CAPITAL LETTER I（U+0049）とLATIN CAPITAL LETTER V（U+0056）である「HENRYIV」と、最後の文字がU+0049とU+0056と互換等価である「Ⅳ」（ROMAN NUMERAL FOUR、U+2163）である「HENRYⅣ」です。このような場合、運用者は、たとえば互換等価物を持つUnicodeコードポイントを名前に含むアカウントを無効にするなど、どのように対処するかを決定する必要があります。このようなケースはおそらくまれですが、運用者がそれを認識しておくことは重要です。

  • SASLprepは、「何もないものにマッピングされることが一般的な文字（characters commonly mapped to nothing）」（[RFC3454]の付録B.1より）を何もないものにマッピングしていましたが、PRECIS IdentifierClassはこれらのコードポイントのほとんどを完全に不許可とします。これらのコードポイントは、[RFC8264]のセクション9.13で定義されているPRECISの「M」カテゴリーのコードポイントに対応します。移行のために、運用者は、PRECISの「M」カテゴリーに含まれるコードポイント（たとえば、SOFT HYPHEN（U+00AD））をユーザー名から削除したいと考えるかもしれません。これらのコードポイントはStringprepでは「何もないものにマッピング」されていたはずなので、PRECISへの移行時にこれらのコードポイントが削除されても、実際にはユーザーがその違いに気付くことはないでしょう。
  • SASLprepは大文字とタイトルケースのコードポイントを許可していましたが、UsernameCaseMappedプロファイルは大文字とタイトルケースのコードポイントを対応する小文字にマッピングします（対照的に、UsernameCasePreservedプロファイルはこの点でSASLprepと一致します）。移行のために、運用者はUsernameCaseMappedプロファイル（したがって大文字小文字の情報は失われます）とUsernameCasePreservedプロファイル（したがってユーザー名の比較時に大文字小文字の違いは無視されます）のどちらを使用してもかまいません。

6.2. Passwords

6.2. パスワード

Depending on local service policy, migration from SASLprep to this specification might not involve any scrubbing of data (because passwords might not be stored in the clear anyway); however, service providers need to be aware of possible issues that might arise during migration. In particular:

ローカルなサービスポリシーによっては、SASLprepからこの仕様への移行にデータの洗浄が一切伴わない場合もあります（そもそもパスワードは平文で保存されていない可能性があるからです）。しかし、サービス提供者は、移行中に発生する可能性のある問題を認識しておく必要があります。具体的には次のとおりです。

  • SASLprep specified the use of Unicode Normalization Form KC (NFKC), whereas the OpaqueString profile employs Unicode Normalization Form C (NFC). Because NFKC is more aggressive about finding matches than NFC, in practice this change is unlikely to cause significant problems and indeed has the security benefit of probably resulting in fewer false accepts when comparing passwords. A few examples might suffice to indicate the nature of the problem:

    1. "ſ" (LATIN SMALL LETTER LONG S, U+017F) is compatibility equivalent to "s" (LATIN SMALL LETTER S, U+0073).
    2. "Ⅳ" (ROMAN NUMERAL FOUR, U+2163) is compatibility equivalent to "I" (LATIN CAPITAL LETTER I, U+0049) and "V" (LATIN CAPITAL LETTER V, U+0056).
    3. "ﬁ" (LATIN SMALL LIGATURE FI, U+FB01) is compatibility equivalent to "f" (LATIN SMALL LETTER F, U+0066) and "i" (LATIN SMALL LETTER I, U+0069).

    Under SASLprep, the use of NFKC also handled the mapping of fullwidth and halfwidth code points to their decomposition mappings. Although it is expected that code points with compatibility equivalents are rare in existing passwords, some passwords that matched when SASLprep was used might no longer work when the rules in this specification are applied.

  • SASLprep mapped the "characters commonly mapped to nothing" (from Appendix B.1 of [RFC3454]) to nothing, whereas the PRECIS FreeformClass entirely disallows such code points, which correspond to the code points from the PRECIS "M" category defined under Section 9.13 of [RFC8264]. In practice, this change will probably have no effect on comparison, but user-oriented software might reject such code points instead of ignoring them during password preparation.

  • SASLprepはUnicode正規化形式KC（NFKC）の使用を規定していましたが、OpaqueStringプロファイルはUnicode正規化形式C（NFC）を採用しています。NFKCはNFCよりも一致を見つけることに関して積極的であるため、実際にはこの変更が重大な問題を引き起こす可能性は低く、むしろパスワードの比較時の誤受理がおそらく少なくなるというセキュリティー上の利点があります。問題の性質を示すには、いくつかの例で十分でしょう。

    1. 「ſ」（LATIN SMALL LETTER LONG S、U+017F）は、「s」（LATIN SMALL LETTER S、U+0073）と互換等価です。
    2. 「Ⅳ」（ROMAN NUMERAL FOUR、U+2163）は、「I」（LATIN CAPITAL LETTER I、U+0049）と「V」（LATIN CAPITAL LETTER V、U+0056）と互換等価です。
    3. 「ﬁ」（LATIN SMALL LIGATURE FI、U+FB01）は、「f」（LATIN SMALL LETTER F、U+0066）と「i」（LATIN SMALL LETTER I、U+0069）と互換等価です。

    SASLprepのもとでは、NFKCの使用によって、全角および半角のコードポイントをその分解マッピングにマッピングすることも扱われていました。既存のパスワードに互換等価物を持つコードポイントが含まれることはまれだと予想されますが、SASLprepを使用していたときに一致していたパスワードの一部が、この仕様の規則を適用すると機能しなくなる可能性があります。

  • SASLprepは、「何もないものにマッピングされることが一般的な文字（characters commonly mapped to nothing）」（[RFC3454]の付録B.1より）を何もないものにマッピングしていましたが、PRECIS FreeformClassはそのようなコードポイントを完全に不許可とします。これらのコードポイントは、[RFC8264]のセクション9.13で定義されているPRECISの「M」カテゴリーのコードポイントに対応します。実際には、この変更はおそらく比較に影響しませんが、ユーザー向けのソフトウェアは、パスワードの準備の際にそのようなコードポイントを無視するのではなく拒否するかもしれません。

8. Security Considerations

8. セキュリティーに関する考慮事項

8.1. Password/Passphrase Strength

8.1. パスワード／パスフレーズの強度

The ability to include a wide range of characters in passwords and passphrases can increase the potential for creating a strong password with high entropy. However, in practice, the ability to include such characters ought to be weighed against the possible need to reproduce them on various devices using various input methods.

パスワードやパスフレーズに幅広い文字を含められることは、エントロピーの高い強力なパスワードを作成できる可能性を高めます。しかし実際には、そのような文字を含められることと、さまざまな入力方式を使用してさまざまなデバイスでそれらを再現する必要が生じる可能性とを比較検討すべきです。

8.2. Password/Passphrase Comparison

8.2. パスワード／パスフレーズの比較

In systems that conform to modern best practices for security, verification of passwords during authentication will not use the comparison defined in Section 4.2.3. Instead, because the system performs cryptographic calculations to verify the password, it will prepare the password as defined in Section 4.2.1 and enforce the rules as defined in Section 4.2.2 before performing the relevant calculations.

セキュリティーに関する現代のベストプラクティスに準拠するシステムでは、認証時のパスワードの検証に、セクション4.2.3で定義する比較を使用しません。代わりに、システムはパスワードを検証するために暗号計算を行うので、関連する計算を行う前に、セクション4.2.1で定義するようにパスワードを準備し、セクション4.2.2で定義するように規則を強制します。

8.3. Identifier Comparison

8.3. 識別子の比較

The process of comparing identifiers (such as SASL simple usernames, authentication identifiers, and authorization identifiers) can lead to either false rejects or false accepts, both of which have security implications. A more detailed discussion can be found in [RFC6943].

識別子（SASLの単純ユーザー名、認証識別子、認可識別子など）を比較する処理は、誤拒否または誤受理のいずれかにつながるおそれがあり、どちらもセキュリティーに影響を及ぼします。より詳細な議論は[RFC6943]にあります。

8.4. Reuse of PRECIS

8.4. PRECISの再利用

The security considerations described in [RFC8264] apply to the IdentifierClass and FreeformClass string classes used in this document for usernames and passwords, respectively.

[RFC8264]で説明されているセキュリティーに関する考慮事項は、この文書でそれぞれユーザー名とパスワードに使用するIdentifierClass文字列クラスとFreeformClass文字列クラスに当てはまります。

8.5. Reuse of Unicode

8.5. Unicodeの再利用

The security considerations described in [UTS39] apply to the use of Unicode code points in usernames and passwords.

[UTS39]で説明されているセキュリティーに関する考慮事項は、ユーザー名とパスワードにおけるUnicodeコードポイントの使用に当てはまります。

Appendix A. Changes from RFC 7613

付録A. RFC 7613からの変更点

The following changes were made from [RFC7613].

[RFC7613]から次の変更を行いました。

  • Corrected the order of operations for the UsernameCaseMapped profile to ensure consistency with [RFC8264].
  • In accordance with working group discussions and updates to [RFC8264], removed the use of the Unicode toCaseFold() operation in favor of the Unicode toLowerCase() operation.
  • Modified the presentation (but not the content) of the rules.
  • Removed UTF-8 as a mandatory encoding, because that is a matter for the application.
  • Clarified several editorial matters.
  • Updated references.
  • [RFC8264]との一貫性を確保するために、UsernameCaseMappedプロファイルの操作の順序を修正しました。
  • ワーキンググループでの議論と[RFC8264]の更新に従い、UnicodeのtoCaseFold()操作の使用をやめ、UnicodeのtoLowerCase()操作を使用するようにしました。
  • 規則の表現を変更しました（内容は変更していません）。
  • UTF-8を必須のエンコーディングから外しました。それはアプリケーションの問題だからです。
  • 編集上のいくつかの事項を明確にしました。
  • 参考文献を更新しました。
