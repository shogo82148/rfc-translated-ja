RFC 9154

Extensible Provisioning Protocol (EPP) Secure Authorization Information for Transfer

RFC 9154

移管のための拡張可能プロビジョニングプロトコル（EPP）のセキュアな認可情報

Abstract

概要

The Extensible Provisioning Protocol (EPP) (RFC 5730) defines the use of authorization information to authorize a transfer of an EPP object, such as a domain name, between clients that are referred to as "registrars". Object-specific, password-based authorization information (see RFCs 5731 and 5733) is commonly used but raises issues related to the security, complexity, storage, and lifetime of authentication information. This document defines an operational practice, using the EPP RFCs, that leverages the use of strong random authorization information values that are short lived, not stored by the client, and stored by the server using a cryptographic hash that provides for secure authorization information that can safely be used for object transfers.

拡張可能プロビジョニングプロトコル（Extensible Provisioning Protocol: EPP）（RFC 5730）は、「レジストラー」と呼ばれるクライアント間でドメイン名などのEPPオブジェクトを移管することを認可するために、認可情報を使用することを定義しています。オブジェクト固有のパスワードベースの認可情報（RFC 5731およびRFC 5733を参照）が一般的に使用されていますが、これには認証情報のセキュリティー、複雑さ、保存、有効期間に関する問題があります。この文書は、EPPのRFCを使用した運用プラクティスを定義します。この運用プラクティスでは、強力なランダムの認可情報の値を活用します。この値は短命で、クライアントには保存されず、サーバーには暗号学的ハッシュを使用して保存されます。これにより、オブジェクトの移管に安全に使用できるセキュアな認可情報が実現されます。

1. Introduction

1. はじめに

The Extensible Provisioning Protocol (EPP) [RFC5730] defines the use of authorization information to authorize a transfer of an EPP object, such as a domain name, between clients that are referred to as "registrars". The authorization information is object specific and has been defined in "Extensible Provisioning Protocol (EPP) Domain Name Mapping" [RFC5731] and "Extensible Provisioning Protocol (EPP) Contact Mapping" [RFC5733] as password-based authorization information. Other authorization mechanisms can be used, but in practice the password-based authorization information has been used at the time of object creation, managed with the object update, and used to authorize an object transfer request. What has not been considered is the security of the authorization information, which includes the complexity of the authorization information, the Time To Live (TTL) of the authorization information, and where and how the authorization information is stored.

拡張可能プロビジョニングプロトコル（Extensible Provisioning Protocol: EPP）[RFC5730]は、「レジストラー」と呼ばれるクライアント間でドメイン名などのEPPオブジェクトを移管することを認可するために、認可情報を使用することを定義しています。 認可情報はオブジェクト固有のものであり、「Extensible Provisioning Protocol (EPP) Domain Name Mapping」[RFC5731]および「Extensible Provisioning Protocol (EPP) Contact Mapping」[RFC5733]において、パスワードベースの認可情報として定義されています。 他の認可メカニズムを使用することもできますが、実際には、パスワードベースの認可情報がオブジェクトの作成時に使用され、オブジェクトの更新によって管理され、オブジェクトの移管リクエストを認可するために使用されてきました。 これまで考慮されてこなかったのは認可情報のセキュリティーであり、これには認可情報の複雑さ、認可情報の生存時間（Time To Live: TTL）、そして認可情報をどこにどのように保存するかが含まれます。

The current/original lifecycle for authorization information involves long-term storage of encrypted (not hashed) passwords, which presents a significant latent risk of password compromise and is not consistent with current best practices. The mechanisms in this document provide a way to avoid long-term password storage entirely and to only require the storage of hashed (not retrievable) passwords instead of encrypted passwords.

認可情報の現在の（そして当初からの）ライフサイクルには、暗号化された（ハッシュ化されていない）パスワードの長期保存が含まれます。 これはパスワードが侵害されるという重大な潜在的リスクをもたらし、現在のベストプラクティスとも一致しません。 この文書のメカニズムは、パスワードの長期保存を完全に回避し、暗号化されたパスワードの代わりにハッシュ化された（復元できない）パスワードの保存だけを要求する方法を提供します。

This document defines an operational practice, using the EPP RFCs, that leverages the use of strong, random authorization information values that are short lived, not stored by the client, and stored by the server using a cryptographic hash to provide secure authorization information used for transfers. This operational practice can be used to support transfers of any EPP object, where the domain name object as defined in [RFC5731] is used in this document for illustration purposes. Elements of the practice may be used to support the secure use of the authorization information for purposes other than transfer, but any other purposes and the applicable elements are out of scope for this document.

この文書は、EPPのRFCを使用した運用プラクティスを定義します。 この運用プラクティスでは、強力でランダムな認可情報の値を活用します。 この値は短命で、クライアントには保存されず、サーバーには暗号学的ハッシュを使用して保存されます。 これにより、移管に使用するセキュアな認可情報を提供します。 この運用プラクティスは任意のEPPオブジェクトの移管をサポートするために使用できますが、この文書では説明のために[RFC5731]で定義されているドメイン名オブジェクトを使用します。 このプラクティスの要素は、移管以外の目的で認可情報をセキュアに使用することをサポートするために使用してもかまいませんが、それ以外の目的と、それに適用可能な要素はこの文書の範囲外です。

The overall goal is to have strong, random authorization information values that are short lived and are either not stored or stored as cryptographic hash values by the non-responsible parties. In a registrant, registrar, and registry model, the registrant registers the object through the registrar to the registry. The registrant is the responsible party, and the registrar and the registry are the non-responsible parties. EPP is a protocol between the registrar and the registry, where the registrar is referred to as the "client" and the registry is referred to as the "server". The following are the elements of the operational practice and how the existing features of the EPP RFCs can be leveraged to satisfy them:

全体的な目標は、強力でランダムな認可情報の値を持つことです。 この値は短命で、責任を持たない当事者によって保存されないか、暗号学的ハッシュ値として保存されます。 登録者、レジストラー、レジストリーのモデルでは、登録者はレジストラーを通じてレジストリーにオブジェクトを登録します。 登録者は責任を持つ当事者であり、レジストラーとレジストリーは責任を持たない当事者です。 EPPはレジストラーとレジストリーの間のプロトコルであり、レジストラーは「クライアント」、レジストリーは「サーバー」と呼ばれます。 以下は、運用プラクティスの要素と、それらを満たすためにEPPのRFCの既存の機能をどのように活用できるかを示します。

Strong Random Authorization Information:
The EPP RFCs define the password-based authorization information value using an XML schema "normalizedString" type, so they don't restrict what can be used in any substantial way. This operational practice defines the recommended mechanism for creating a strong random authorization value that would be generated by the client.
Short-Lived Authorization Information:
The EPP RFCs don't explicitly support short-lived authorization information or a TTL for authorization information, but there are EPP RFC features that can be leveraged to support short-lived authorization information. All of these features are compatible with the EPP RFCs, though not mandatory to implement. As stated in Section 2.6 of [RFC5731], authorization information is assigned when a domain object is created, which results in long-lived authorization information. This specification changes the nature of the authorization information from long lived to short lived. If authorization information is set only when a transfer is in process, the server needs to support an empty authorization information value on create, support setting and unsetting authorization information, and support automatically unsetting the authorization information upon a successful transfer. All of these features can be supported by the EPP RFCs.
Storing Authorization Information Securely:
The EPP RFCs don't specify where and how the authorization information is stored in the client or the server, so there are no restrictions on defining an operational practice for storing the authorization information securely. The operational practice will require the client to not store the authorization information and will require the server to store the authorization information using a cryptographic hash with at least a 256-bit hash function, such as SHA-256 [FIPS-180-4], and with a per-authorization information random salt with at least 128 bits. Returning the authorization information set in an EPP info response will not be supported.
強力でランダムな認可情報：
EPPのRFCは、パスワードベースの認可情報の値をXMLスキーマの「normalizedString」型を使用して定義しているため、使用できるものを実質的に何も制限していません。 この運用プラクティスは、クライアントが生成する強力でランダムな認可情報の値を作成するための推奨メカニズムを定義します。
短命な認可情報：
EPPのRFCは、短命な認可情報や認可情報のTTLを明示的にはサポートしていません。 しかし、短命な認可情報をサポートするために活用できるEPPのRFCの機能があります。 これらの機能はすべてEPPのRFCと互換性がありますが、実装必須ではありません。 [RFC5731]のSection 2.6に記載されているように、認可情報はドメインオブジェクトの作成時に割り当てられるため、認可情報は長命なものになります。 この仕様は、認可情報の性質を長命なものから短命なものへと変更します。 移管が進行中のときにのみ認可情報を設定するのであれば、サーバーは、作成時に空の認可情報の値をサポートし、認可情報の設定と設定解除をサポートし、移管が成功したときに認可情報を自動的に設定解除することをサポートする必要があります。 これらの機能はすべて、EPPのRFCでサポートできます。
認可情報のセキュアな保存：
EPPのRFCは、クライアントやサーバーにおいて認可情報をどこにどのように保存するかを規定していません。 そのため、認可情報をセキュアに保存するための運用プラクティスを定義することに制限はありません。 この運用プラクティスでは、クライアントに認可情報を保存しないことを要求し、サーバーには、SHA-256 [FIPS-180-4]などの少なくとも256ビットのハッシュ関数による暗号学的ハッシュと、認可情報ごとの少なくとも128ビットのランダムなソルトを使用して、認可情報を保存することを要求します。 EPPのinfoレスポンスで、設定された認可情報を返すことはサポートされません。

2. Registrant, Registrar, Registry

2. 登録者、レジストラー、レジストリー

The EPP RFCs refer to "client" and "server", but when it comes to transfers, there are three types of actors that are involved. This document will refer to these actors as "registrant", "registrar", and "registry". [RFC8499] defines these terms formally for the Domain Name System (DNS). The terms are further described below to cover their roles as actors using the authorization information in the transfer process of any object in the registry, such as a domain name or a contact:

EPPのRFCは「クライアント」と「サーバー」に言及していますが、移管に関しては3種類のアクターが関与します。 この文書では、これらのアクターを「登録者（registrant）」、「レジストラー（registrar）」、「レジストリー（registry）」と呼びます。 [RFC8499]は、ドメインネームシステム（DNS）に関してこれらの用語を正式に定義しています。 以下では、ドメイン名や連絡先など、レジストリー内の任意のオブジェクトの移管プロセスにおいて認可情報を使用するアクターとしての役割を説明するために、これらの用語をさらに説明します。

Registrant:
[RFC8499] defines the registrant as "an individual or organization on whose behalf a name in a zone is registered by the registry." The registrant can be the owner of any object in the registry, such as a domain name or a contact. The registrant interfaces with the registrar for provisioning the objects. A transfer is coordinated by the registrant to transfer the sponsorship of the object from one registrar to another. The authorization information is meant to authenticate the registrant as the owner of the object to the non-sponsoring registrar and to authorize the transfer.
Registrar:
[RFC8499] defines the registrar as "a service provider that acts as a go-between for registrants and registries." The registrar interfaces with the registrant for the provisioning of objects, such as domain names and contacts, and with the registries to satisfy the registrant's provisioning requests. A registrar may (1) directly interface with the registrant or (2) indirectly interface with the registrant, typically through one or more resellers. Implementing a transfer using secure authorization information extends through the registrar's reseller channel up to the direct interface with the registrant. The registrar's interface with the registries uses EPP. The registrar's interface with its reseller channel or the registrant is registrar specific. In the EPP RFCs, the registrar is referred to as the "client", since EPP is the protocol used between the registrar and the registry. The sponsoring registrar is the authorized registrar to manage objects on behalf of the registrant. A non-sponsoring registrar is not authorized to manage objects on behalf of the registrant. A transfer of an object's sponsorship is from one registrar, referred to as the "losing registrar", to another registrar, referred to as the "gaining registrar".
Registry:
[RFC8499] defines the registry as "the administrative operation of a zone that allows registration of names within that zone." The registry typically interfaces with the registrars over EPP and generally does not interact directly with the registrant. In the EPP RFCs, the registry is referred to as the "server", since EPP is the protocol used between the registrar and the registry. The registry has a record of the sponsoring registrar for each object and provides the mechanism (over EPP) to coordinate a transfer of an object's sponsorship between registrars.
登録者：
[RFC8499]は、登録者を「その者に代わってレジストリーがゾーン内の名前を登録する個人または組織」と定義しています。 登録者は、ドメイン名や連絡先など、レジストリー内の任意のオブジェクトの所有者になることができます。 登録者は、オブジェクトをプロビジョニングするためにレジストラーとやり取りします。 移管は、オブジェクトのスポンサーシップをあるレジストラーから別のレジストラーへ移すために、登録者によって調整されます。 認可情報は、非スポンサーレジストラーに対して登録者をオブジェクトの所有者として認証し、移管を認可するためのものです。
レジストラー：
[RFC8499]は、レジストラーを「登録者とレジストリーの仲介役として機能するサービスプロバイダー」と定義しています。 レジストラーは、ドメイン名や連絡先などのオブジェクトをプロビジョニングするために登録者とやり取りし、登録者のプロビジョニングリクエストを満たすためにレジストリーとやり取りします。 レジストラーは、（1）登録者と直接やり取りすることも、（2）一般的には1つ以上のリセラーを通じて、登録者と間接的にやり取りすることもあります。 セキュアな認可情報を使用した移管の実装は、レジストラーのリセラーチャネルを経由して、登録者との直接のインターフェイスにまで及びます。 レジストラーとレジストリーの間のインターフェイスにはEPPを使用します。 レジストラーとそのリセラーチャネルまたは登録者との間のインターフェイスは、レジストラー固有のものです。 EPPはレジストラーとレジストリーの間で使用されるプロトコルであるため、EPPのRFCではレジストラーを「クライアント」と呼びます。 スポンサーレジストラー（sponsoring registrar）は、登録者に代わってオブジェクトを管理することを認可されたレジストラーです。 非スポンサーレジストラー（non-sponsoring registrar）は、登録者に代わってオブジェクトを管理することを認可されていません。 オブジェクトのスポンサーシップの移管は、「移管元レジストラー（losing registrar）」と呼ばれるレジストラーから、「移管先レジストラー（gaining registrar）」と呼ばれる別のレジストラーへと行われます。
レジストリー：
[RFC8499]は、レジストリーを「ゾーン内での名前の登録を可能にする、そのゾーンの管理運営」と定義しています。 レジストリーは通常、EPPを介してレジストラーとやり取りし、一般に登録者と直接やり取りすることはありません。 EPPはレジストラーとレジストリーの間で使用されるプロトコルであるため、EPPのRFCではレジストリーを「サーバー」と呼びます。 レジストリーは、各オブジェクトのスポンサーレジストラーの記録を保持し、レジストラー間でのオブジェクトのスポンサーシップの移管を調整するメカニズムを（EPPを介して）提供します。

3. Signaling Client and Server Support

3. クライアントとサーバーのサポートの通知

This document does not define a new protocol; rather, it defines an operational practice using existing EPP features, where the client and the server can signal support for the operational practice using a namespace URI in the login and greeting extension services. The namespace URI "urn:ietf:params:xml:ns:epp:secure-authinfo-transfer-1.0" is used to signal support for the operational practice. The client includes the namespace URI in an <svcExtension> <extURI> element of the <login> command [RFC5730]. The server includes the namespace URI in an <svcExtension> <extURI> element of the greeting [RFC5730].

この文書は新しいプロトコルを定義するものではありません。 むしろ、既存のEPPの機能を使用した運用プラクティスを定義するものであり、クライアントとサーバーは、ログインおよびグリーティングの拡張サービスにおける名前空間URIを使用して、この運用プラクティスのサポートを通知できます。 名前空間URI「urn:ietf:params:xml:ns:epp:secure-authinfo-transfer-1.0」は、この運用プラクティスのサポートを通知するために使用されます。 クライアントは、<login>コマンド[RFC5730]の<svcExtension> <extURI>要素にこの名前空間URIを含めます。 サーバーは、グリーティング[RFC5730]の<svcExtension> <extURI>要素にこの名前空間URIを含めます。

A client that receives the namespace URI in the server's greeting extension services can expect the following supported behavior by the server:

サーバーのグリーティングの拡張サービスでこの名前空間URIを受信したクライアントは、サーバーが次の振る舞いをサポートしていると期待できます。

  1. Support for an empty authorization information value with a <create> command.
  2. Support for unsetting authorization information with an <update> command.
  3. Support for validating authorization information with an <info> command.
  4. Support for not returning an indication of whether the authorization information is set or unset to the non-sponsoring registrar.
  5. Support for returning an empty authorization information value to the sponsoring registrar when the authorization information is set in an info response.
  6. Support for allowing the passing of a matching non-empty authorization information value to authorize a transfer.
  7. Support for automatically unsetting the authorization information upon successful completion of a transfer.
  1. <create>コマンドで空の認可情報の値をサポートすること。
  2. <update>コマンドで認可情報の設定解除をサポートすること。
  3. <info>コマンドで認可情報の検証をサポートすること。
  4. 非スポンサーレジストラーに対して、認可情報が設定されているか設定解除されているかを示す情報を返さないことをサポートすること。
  5. infoレスポンスにおいて、認可情報が設定されている場合に、スポンサーレジストラーに空の認可情報の値を返すことをサポートすること。
  6. 移管を認可するために、一致する空でない認可情報の値を渡すことを許可するのをサポートすること。
  7. 移管が正常に完了したときに、認可情報を自動的に設定解除することをサポートすること。

A server that receives the namespace URI in the client's <login> command extension services can expect the following supported behavior by the client:

クライアントの<login>コマンドの拡張サービスでこの名前空間URIを受信したサーバーは、クライアントが次の振る舞いをサポートしていると期待できます。

  1. Support for the generation of authorization information using a secure random value.
  2. Support for only setting the authorization information when a transfer is in process.
  1. セキュアなランダム値を使用して認可情報を生成することをサポートすること。
  2. 移管が進行中のときにのみ認可情報を設定することをサポートすること。

4. Secure Authorization Information

4. セキュアな認可情報

The EPP RFCs ([RFC5731] and [RFC5733]) use password-based authorization information to support transfer with the <domain:pw> element [RFC5731] and with the <contact:pw> element [RFC5733]. Other EPP objects that support password-based authorization information for transfer can use secure authorization information as defined in this document. For authorization information to be secure, it must be generated using a strong random value and have a short TTL. The security of the authorization information is defined in the following sections.

EPPのRFC（[RFC5731]および[RFC5733]）は、移管をサポートするためにパスワードベースの認可情報を使用しており、それぞれ<domain:pw>要素[RFC5731]と<contact:pw>要素[RFC5733]を使用します。 移管のためのパスワードベースの認可情報をサポートする他のEPPオブジェクトも、この文書で定義するセキュアな認可情報を使用できます。 認可情報をセキュアにするためには、強力なランダム値を使用して生成し、短いTTLを持たせる必要があります。 認可情報のセキュリティーについては、以降のセクションで定義します。

4.1. Secure Random Authorization Information

4.1. セキュアなランダムの認可情報

For authorization information to be secure, it MUST be generated using a secure random value. The authorization information is treated as a password, and the required length L of a password, rounded up to the largest whole number, is based on the size N of the set of characters and the desired entropy H, in the equation L = ROUNDUP(H / log2 N). Given a target entropy, the required length can be calculated after deciding on the set of characters that will be randomized. In accordance with current best practices and noting that the authorization information is a machine-generated value, the implementation SHOULD use at least 128 bits of entropy as the value of H. The lengths below are calculated using that value.

認可情報をセキュアにするためには、セキュアなランダム値を使用して生成しなければなりません（MUST）。 認可情報はパスワードとして扱われます。 パスワードに必要な長さL（最も近い整数に切り上げたもの）は、文字セットのサイズNと望ましいエントロピーHに基づき、式L = ROUNDUP(H / log2 N)で求められます。 目標とするエントロピーが与えられれば、ランダム化する文字セットを決めた後に、必要な長さを計算できます。 現在のベストプラクティスに従い、また認可情報が機械生成された値であることに留意して、実装はHの値として少なくとも128ビットのエントロピーを使用すべきです（SHOULD）。 以下の長さは、その値を使用して計算しています。

Calculation of the required length with 128 bits of entropy and with the set of all printable ASCII characters except space (0x20), which consists of the 94 characters 0x21-0x7E:

128ビットのエントロピーで、空白（0x20）を除くすべての印字可能なASCII文字のセット（0x21〜0x7Eの94文字からなる）を使用した場合の必要な長さの計算：

ROUNDUP(128 / log2 94) =~ ROUNDUP(128 / 6.55) =~ ROUNDUP(19.54) = 20

ROUNDUP(128 / log2 94) =~ ROUNDUP(128 / 6.55) =~ ROUNDUP(19.54) = 20

Calculation of the required length with 128 bits of entropy and with the set of case-insensitive alphanumeric characters, which consists of 36 characters (a-z A-Z 0-9):

128ビットのエントロピーで、大文字と小文字を区別しない英数字のセット（a-z A-Z 0-9の36文字からなる）を使用した場合の必要な長さの計算：

ROUNDUP(128 / log2 36) =~ ROUNDUP(128 / 5.17) =~ ROUNDUP(24.76) = 25

ROUNDUP(128 / log2 36) =~ ROUNDUP(128 / 5.17) =~ ROUNDUP(24.76) = 25

The strength of the random authorization information is dependent on the random number generator. Suitably strong random number generators are available in a wide variety of implementation environments, including the interfaces listed in Sections 7.1.2 and 7.1.3 of [RFC4086]. In environments that do not provide interfaces to strong random number generators, the practices defined in [RFC4086] and Section 4.7.1 of the NIST Federal Information Processing Standards (FIPS) Publication 140-2 [FIPS-140-2] can be followed to produce random values that will be resistant to attack. (Note: FIPS 140-2 has been superseded by FIPS 140-3, but FIPS 140-3 does not contain information regarding random number generators.)

ランダムな認可情報の強度は、乱数生成器に依存します。 十分に強力な乱数生成器は、[RFC4086]のセクション7.1.2および7.1.3に挙げられているインターフェイスなど、さまざまな実装環境で利用できます。 強力な乱数生成器へのインターフェイスを提供しない環境では、[RFC4086]で定義されているプラクティスと、NIST Federal Information Processing Standards (FIPS) Publication 140-2[FIPS-140-2]のセクション4.7.1に従って、攻撃に耐性のあるランダム値を生成できます。 （注：FIPS 140-2はFIPS 140-3に置き換えられていますが、FIPS 140-3には乱数生成器に関する情報は含まれていません。）

4.2. Authorization Information Time To Live (TTL)

4.2. 認可情報の生存時間（TTL）

The authorization information SHOULD only be set when a transfer is in process. This implies that the authorization information has a TTL by which the authorization information is cleared when the TTL expires. The EPP RFCs do not provide definitions for TTL, but since the server supports the setting and unsetting of the authorization information by the sponsoring registrar, the sponsoring registrar can apply a TTL based on client policy. The TTL client policy may be based on proprietary registrar-specific criteria, which provides for a transfer-specific TTL tuned for the particular circumstances of the transaction. The sponsoring registrar will be aware of the TTL, and the sponsoring registrar MUST inform the registrant of the TTL when the authorization information is provided to the registrant.

認可情報は、移管が進行中のときにのみ設定すべきです（SHOULD）。 これは、認可情報がTTLを持ち、TTLが期限切れになると認可情報が消去されることを意味します。 EPPのRFCはTTLの定義を提供していませんが、サーバーはスポンサーレジストラーによる認可情報の設定と設定解除をサポートしているため、スポンサーレジストラーはクライアントのポリシーに基づいてTTLを適用できます。 TTLに関するクライアントのポリシーは、レジストラー固有の独自の基準に基づいてもかまいません。 これにより、トランザクションの特定の状況に合わせて調整された、移管固有のTTLが実現されます。 スポンサーレジストラーはTTLを把握しています。 スポンサーレジストラーは、登録者に認可情報を提供するときに、登録者にTTLを通知しなければなりません（MUST）。

4.3. Authorization Information Storage and Transport

4.3. 認可情報の保存と転送

To protect the disclosure of the authorization information, the following requirements apply:

認可情報の開示から保護するために、次の要件を適用します。

  1. The authorization information MUST be stored by the registry using a strong one-way cryptographic hash with at least a 256-bit hash function, such as SHA-256 [FIPS-180-4], and with a per-authorization information random salt with at least 128 bits.
  2. An empty authorization information value MUST be stored as an undefined value that is referred to as a "NULL" value. The representation of a NULL (undefined) value is dependent on the type of database used.
  3. The authorization information MUST NOT be stored by the losing registrar.
  4. The authorization information MUST only be stored by the gaining registrar as a "transient" value in support of the transfer process.
  5. The plain-text version of the authorization information MUST NOT be written to any logs by a registrar or the registry, nor otherwise recorded where it will persist beyond the transfer process.
  6. All communication that includes the authorization information MUST be over an encrypted channel (for example, see [RFC5734]) for EPP.
  7. The registrar's interface for communicating the authorization information with the registrant MUST be over an authenticated and encrypted channel.
  1. レジストリーは、SHA-256 [FIPS-180-4]などの少なくとも256ビットのハッシュ関数による強力な一方向の暗号学的ハッシュと、認可情報ごとの少なくとも128ビットのランダムなソルトを使用して、認可情報を保存しなければなりません（MUST）。
  2. 空の認可情報の値は、「NULL」値と呼ばれる未定義の値として保存しなければなりません（MUST）。 NULL（未定義）値の表現は、使用するデータベースの種類に依存します。
  3. 移管元レジストラーは、認可情報を保存してはなりません（MUST NOT）。
  4. 移管先レジストラーは、移管プロセスをサポートするための「一時的な」値としてのみ、認可情報を保存しなければなりません（MUST）。
  5. レジストラーまたはレジストリーは、認可情報の平文版をいかなるログにも書き込んではなりません（MUST NOT）。また、移管プロセスを超えて残るような場所に記録してもいけません。
  6. 認可情報を含むすべての通信は、EPPの暗号化されたチャネル（たとえば、[RFC5734]を参照）を介して行わなければなりません（MUST）。
  7. 登録者と認可情報をやり取りするためのレジストラーのインターフェイスは、認証され暗号化されたチャネルを介したものでなければなりません（MUST）。

4.4. Authorization Information Matching

4.4. 認可情報の照合

To support the authorization information TTL, as described in Section 4.2, the authorization information must have either a set or unset state. Authorization information that is unset is stored with a NULL (undefined) value. Based on the requirement to store the authorization information using a strong one-way cryptographic hash, as described in Section 4.3, authorization information that is set is stored with a non-NULL hashed value. The empty authorization information value is used as input in both the Section 5.1 and the Section 5.2 to define the unset state. The matching of the authorization information in the Section 5.3 and the Section 5.4 is based on the following rules:

Section 4.2で説明した認可情報のTTLをサポートするために、認可情報は設定済みまたは未設定のいずれかの状態を持つ必要があります。 未設定の認可情報は、NULL（未定義）値で保存されます。 Section 4.3で説明した、強力な一方向の暗号学的ハッシュを使用して認可情報を保存するという要件に基づき、設定済みの認可情報はNULLでないハッシュ値で保存されます。 空の認可情報の値は、Section 5.1とSection 5.2の両方において、未設定の状態を定義するための入力として使用されます。 Section 5.3とSection 5.4における認可情報の照合は、次の規則に基づきます。

  1. Any input authorization information value MUST NOT match an unset authorization information value. For example, in [RFC5731] the input <domain:pw>2fooBAR</domain:pw> must not match an unset authorization information value that used <domain:null/> or <domain:pw/>.
  2. An empty input authorization information value MUST NOT match any set authorization information value.
  3. A non-empty input authorization information value MUST be hashed and matched against the set authorization information value, which is stored using the same hash algorithm.
  1. いかなる入力の認可情報の値も、未設定の認可情報の値と一致してはなりません（MUST NOT）。 たとえば、[RFC5731]において、入力<domain:pw>2fooBAR</domain:pw>は、<domain:null/>または<domain:pw/>を使用した未設定の認可情報の値と一致してはいけません。
  2. 空の入力の認可情報の値は、いかなる設定済みの認可情報の値とも一致してはなりません（MUST NOT）。
  3. 空でない入力の認可情報の値はハッシュ化され、同じハッシュアルゴリズムを使用して保存されている設定済みの認可情報の値と照合されなければなりません（MUST）。

5. Create, Transfer, and Secure Authorization Information

5. 作成、移管、セキュアな認可情報

To secure the transfer process using secure authorization information as described in Section 4, the client and server need to implement steps where the authorization information is set only when a transfer is actively in process and ensure that the authorization information is stored securely and transported only over secure channels. The steps for management of the authorization information for transfers include the following:

Section 4で説明したセキュアな認可情報を使用して移管プロセスをセキュアにするために、クライアントとサーバーは、移管が実際に進行中のときにのみ認可情報を設定する手順を実装し、認可情報がセキュアに保存され、セキュアなチャネルを介してのみ転送されることを保証する必要があります。 移管のための認可情報の管理手順は次のとおりです。

  1. The registrant requests to register the object with the registrar. The registrar sends the <create> command with an empty authorization information value to the registry, as described in Section 5.1.
  2. The registrant requests from the losing registrar the authorization information to provide to the gaining registrar.
  3. The losing registrar generates a secure random authorization information value and sends it to the registry, as described in Section 5.2, and then provides it to the registrant.
  4. The registrant provides the authorization information value to the gaining registrar.
  5. The gaining registrar optionally verifies the authorization information with the <info> command to the registry, as described in Section 5.3.
  6. The gaining registrar sends the transfer request with the authorization information to the registry, as described in Section 5.4.
  7. If the transfer completes successfully, the registry automatically unsets the authorization information; otherwise, the losing registrar unsets the authorization information when the TTL expires; see Section 5.2.
  1. 登録者は、レジストラーにオブジェクトの登録をリクエストします。 レジストラーは、Section 5.1で説明するように、空の認可情報の値を含む<create>コマンドをレジストリーに送信します。
  2. 登録者は、移管先レジストラーに提供するための認可情報を、移管元レジストラーにリクエストします。
  3. 移管元レジストラーは、セキュアなランダムの認可情報の値を生成し、Section 5.2で説明するようにそれをレジストリーに送信し、その後、登録者に提供します。
  4. 登録者は、認可情報の値を移管先レジストラーに提供します。
  5. 移管先レジストラーは、Section 5.3で説明するように、任意でレジストリーへの<info>コマンドを使用して認可情報を検証します。
  6. 移管先レジストラーは、Section 5.4で説明するように、認可情報を含む移管リクエストをレジストリーに送信します。
  7. 移管が正常に完了した場合、レジストリーは自動的に認可情報を設定解除します。 そうでない場合は、TTLが期限切れになったときに、移管元レジストラーが認可情報を設定解除します。 Section 5.2を参照してください。

The following sections outline the practices of the EPP commands and responses between the registrar and the registry that supports secure authorization information for transfer.

以降のセクションでは、移管のためのセキュアな認可情報をサポートする、レジストラーとレジストリーの間のEPPコマンドとレスポンスのプラクティスについて概説します。

5.1. <Create> Command

5.1. <Create>コマンド

For a <create> command, the registry MUST allow the passing of an empty authorization information value and MAY disallow the passing of a non-empty authorization information value. By having an empty authorization information value on create, the object is initially not involved in the transfer process. Any EPP object extension that supports setting the authorization information with an "eppcom:pwAuthInfoType" element can pass an empty authorization information value. Examples of such extensions are found in [RFC5731] and [RFC5733].

<create>コマンドについて、レジストリーは空の認可情報の値を渡すことを許可しなければなりません（MUST）。 また、空でない認可情報の値を渡すことを禁止してもよいです（MAY）。 作成時に空の認可情報の値を持たせることで、オブジェクトは最初は移管プロセスに関与しない状態になります。 「eppcom:pwAuthInfoType」要素による認可情報の設定をサポートするEPPオブジェクト拡張はいずれも、空の認可情報の値を渡すことができます。 そのような拡張の例は、[RFC5731]と[RFC5733]にあります。

Example of passing an empty authorization information value in a domain name <create> command [RFC5731]:

ドメイン名の<create>コマンド[RFC5731]で空の認可情報の値を渡す例：

C:<?xml version="1.0" encoding="UTF-8" standalone="no"?>
C:<epp xmlns="urn:ietf:params:xml:ns:epp-1.0">
C:  <command>
C:    <create>
C:      <domain:create
C:        xmlns:domain="urn:ietf:params:xml:ns:domain-1.0">
C:        <domain:name>example.com</domain:name>
C:        <domain:authInfo>
C:          <domain:pw/>
C:        </domain:authInfo>
C:      </domain:create>
C:    </create>
C:    <clTRID>ABC-12345</clTRID>
C:  </command>
C:</epp>

C:<?xml version="1.0" encoding="UTF-8" standalone="no"?>
C:<epp xmlns="urn:ietf:params:xml:ns:epp-1.0">
C:  <command>
C:    <create>
C:      <domain:create
C:        xmlns:domain="urn:ietf:params:xml:ns:domain-1.0">
C:        <domain:name>example.com</domain:name>
C:        <domain:authInfo>
C:          <domain:pw/>
C:        </domain:authInfo>
C:      </domain:create>
C:    </create>
C:    <clTRID>ABC-12345</clTRID>
C:  </command>
C:</epp>

Example of passing an empty authorization information value in a contact <create> command [RFC5733]:

連絡先の<create>コマンド[RFC5733]で空の認可情報の値を渡す例：

C:<?xml version="1.0" encoding="UTF-8" standalone="no"?>
C:<epp xmlns="urn:ietf:params:xml:ns:epp-1.0">
C:  <command>
C:    <create>
C:      <contact:create
C:       xmlns:contact="urn:ietf:params:xml:ns:contact-1.0">

5.2. <Update> Command

5.2. <Update>コマンド

For an <update> command, the registry MUST allow the setting and unsetting of the authorization information. The registrar sets the authorization information by first generating a strong, random authorization information value, based on the information provided in Section 4.1, and setting it in the registry in the <update> command. The importance of generating strong authorization information values cannot be overstated: secure transfers are very important to the Internet to mitigate damage in the form of theft, fraud, and other abuse. It is critical that registrars only use strong, randomly generated authorization information values.

<update>コマンドについて、レジストリーは認可情報の設定と設定解除を許可しなければなりません（MUST）。 レジストラーは、まずSection 4.1で提供する情報に基づいて強力でランダムな認可情報の値を生成し、それを<update>コマンドでレジストリーに設定することで、認可情報を設定します。 強力な認可情報の値を生成することの重要性は、いくら強調してもしすぎることはありません。 セキュアな移管は、窃盗、詐欺、その他の濫用といった形の被害を緩和するために、インターネットにとって非常に重要です。 レジストラーが、強力でランダムに生成された認可情報の値だけを使用することが極めて重要です。

Because of this, registries may validate the randomness of the authorization information based on the length and character set required by the registry -- for example, validating that an authorization value contains a combination of uppercase, lowercase, and non-alphanumeric characters in an attempt to assess the strength of the value and returning an EPP error result of 2202 ("Invalid authorization information") [RFC5730] if the check fails.

このため、レジストリーは、レジストリーが要求する長さと文字セットに基づいて、認可情報のランダム性を検証することがあります。 たとえば、値の強度を評価するために、認可情報の値に大文字、小文字、英数字以外の文字の組み合わせが含まれていることを検証し、チェックに失敗した場合はEPPのエラー結果2202（"Invalid authorization information"）[RFC5730]を返すことが考えられます。

Such checks are, by their nature, heuristic and imperfect, and may identify well-chosen authorization information values as being not sufficiently strong. Registrars, therefore, must be prepared for an error response of 2202 and respond by generating a new value and trying again, possibly more than once.

このようなチェックは、その性質上ヒューリスティックで不完全なものであり、適切に選ばれた認可情報の値を十分に強力ではないと判定する可能性があります。 したがって、レジストラーは2202のエラーレスポンスに備える必要があり、その場合は新しい値を生成して、場合によっては複数回、再試行する必要があります。

5.4. <Transfer> Request Command

5.4. <Transfer>リクエストコマンド

The registry compares the hash of the passed authorization information with the hashed authorization information value stored for the object. When the authorization information is not set or the passed authorization information does not match the previously set value, the registry MUST return an EPP error result code of 2202 [RFC5730]. Whether the transfer occurs immediately or is pending is up to server policy. When the transfer occurs immediately, the registry MUST return the EPP success result code of 1000 ("Command completed successfully") [RFC5730], and when the transfer is pending, the registry MUST return the EPP success result code of 1001 ("Command completed successfully; action pending"). Upon successful completion of the transfer, the registry MUST automatically unset the authorization information. If the transfer request is not submitted within the Section 4.2 or the transfer is canceled or rejected, the registrar MUST unset the authorization information, as described in Section 5.2.

移管が正常に完了したとき、レジストリーは自動的に認可情報を設定解除しなければなりません（MUST）。 移管リクエストがSection 4.2内に送信されない場合、または移管がキャンセルもしくは拒否された場合、レジストラーは、Section 5.2で説明したように、認可情報を設定解除しなければなりません（MUST）。

6. Transition Considerations

6. 移行に関する考慮事項

The goal of the transition considerations is to minimize the impact to the registrars in supporting the Secure Authorization Information Model defined in this document by supporting incremental transition steps. The transition steps are dependent on the starting point of the registry. Registries may have different starting points, since some of the elements of the Secure Authorization Information Model may have already been implemented. The considerations assume a starting point, referred to as the "Classic Authorization Information Model", which incorporates the following steps for management of the authorization information for transfers:

移行に関する考慮事項の目標は、段階的な移行手順をサポートすることで、この文書で定義するセキュア認可情報モデル（Secure Authorization Information Model）をサポートする際のレジストラーへの影響を最小限に抑えることです。 移行手順は、レジストリーの出発点に依存します。 セキュア認可情報モデルの要素の一部がすでに実装されている可能性があるため、レジストリーごとに出発点が異なる場合があります。 この考慮事項では、「従来型認可情報モデル（Classic Authorization Information Model）」と呼ばれる出発点を想定しています。 このモデルには、移管のための認可情報の管理について次の手順が含まれます。

  1. The registrant requests to register the object with the registrar. The registrar sends the <create> command, with a non-empty authorization information value, to the registry. The registry stores the authorization information as an encrypted value and requires a non-empty authorization information value for the life of the object. The registrar may store the long-lived authorization information.
  2. At the time of transfer, the registrant requests from the losing registrar the authorization information to provide to the gaining registrar.
  3. The losing registrar retrieves the locally stored authorization information or queries the registry for authorization information using the <info> command, and provides it to the registrant. If the registry is queried, the authorization information is decrypted and the plain-text authorization information is returned in the info response to the registrar.
  4. The registrant provides the authorization information value to the gaining registrar.
  5. The gaining registrar optionally verifies the authorization information with the <info> command to the registry, by passing the authorization information in the <info> command to the registry.
  6. The gaining registrar sends the transfer request with the authorization information to the registry. The registry will decrypt the stored authorization information to compare to the passed authorization information.
  7. If the transfer completes successfully, the authorization information is not touched by the registry and may be updated by the gaining registrar using the <update> command. If the transfer is canceled or rejected, the losing registrar may reset the authorization information using the <update> command.
  1. 登録者は、レジストラーにオブジェクトの登録をリクエストします。 レジストラーは、空でない認可情報の値を含む<create>コマンドをレジストリーに送信します。 レジストリーは、認可情報を暗号化された値として保存し、オブジェクトの存続期間中は空でない認可情報の値を要求します。 レジストラーは、長命な認可情報を保存する場合があります。
  2. 移管時に、登録者は、移管先レジストラーに提供するための認可情報を、移管元レジストラーにリクエストします。
  3. 移管元レジストラーは、ローカルに保存されている認可情報を取得するか、<info>コマンドを使用してレジストリーに認可情報を問い合わせ、それを登録者に提供します。 レジストリーに問い合わせた場合、認可情報は復号され、平文の認可情報がinfoレスポンスでレジストラーに返されます。
  4. 登録者は、認可情報の値を移管先レジストラーに提供します。
  5. 移管先レジストラーは、任意で、レジストリーへの<info>コマンドで認可情報を渡すことにより、<info>コマンドを使用して認可情報を検証します。
  6. 移管先レジストラーは、認可情報を含む移管リクエストをレジストリーに送信します。 レジストリーは、保存されている認可情報を復号し、渡された認可情報と比較します。
  7. 移管が正常に完了した場合、レジストリーは認可情報に手を加えず、移管先レジストラーが<update>コマンドを使用して認可情報を更新する場合があります。 移管がキャンセルまたは拒否された場合、移管元レジストラーは<update>コマンドを使用して認可情報をリセットする場合があります。

The gaps between the Classic Authorization Information Model and the Secure Authorization Information Model include the following:

従来型認可情報モデルとセキュア認可情報モデルの間の差異は次のとおりです。

  1. Registry requirement for a non-empty authorization information value on create and for the life of the object versus the authorization information not being set on create and only being set when a transfer is in process.
  2. Registry not allowing the authorization information to be unset versus providing support for unsetting the authorization information in the <update> command.
  3. Registry storing the authorization information as an encrypted value versus a hashed value.
  4. Registry support for returning the authorization information versus not returning the authorization information in the info response.
  5. Registry not touching the authorization information versus the registry automatically unsetting the authorization information upon a successful transfer.
  6. Registry possibly validating a shorter authorization information value using password complexity rules versus validating the randomness of a longer authorization information value that meets the required bits of entropy.
  1. レジストリーが作成時およびオブジェクトの存続期間中に空でない認可情報の値を要求すること、対、作成時には認可情報を設定せず、移管が進行中のときにのみ設定すること。
  2. レジストリーが認可情報の設定解除を許可しないこと、対、<update>コマンドで認可情報の設定解除をサポートすること。
  3. レジストリーが認可情報を暗号化された値として保存すること、対、ハッシュ値として保存すること。
  4. レジストリーがinfoレスポンスで認可情報を返すことをサポートすること、対、認可情報を返さないこと。
  5. レジストリーが認可情報に手を加えないこと、対、移管の成功時にレジストリーが自動的に認可情報を設定解除すること。
  6. レジストリーがパスワードの複雑さの規則を使用して、より短い認可情報の値を検証する可能性があること、対、必要なエントロピーのビット数を満たす、より長い認可情報の値のランダム性を検証すること。

The transition can be handled in the three phases defined in Sections 6.1, 6.2, and 6.3.

移行は、セクション6.1、6.2、6.3で定義する3つのフェーズで扱うことができます。

6.1. Transition Phase 1 - Features

6.1. 移行フェーズ1 - 機能

The goal of "Transition Phase 1 - Features" is to implement the needed features in EPP so that the registrar can optionally implement the Secure Authorization Information Model. The features to implement are broken out by the commands and responses below:

「移行フェーズ1 - 機能」の目標は、レジストラーが任意でセキュア認可情報モデルを実装できるように、EPPに必要な機能を実装することです。 実装する機能は、以下のようにコマンドとレスポンスごとに分けて示します。

<Create> Command:
Change the <create> command to make the authorization information optional, by allowing both a non-empty value and an empty value. This enables a registrar to optionally create objects without an authorization information value, as described in Section 5.1.
<Update> Command:
Change the <update> command to allow unsetting the authorization information, as described in Section 5.2. This enables the registrar to optionally unset the authorization information when the TTL expires or when the transfer is canceled or rejected.
Transfer Approve Command and Transfer Auto-Approve:
Change the transfer approve command and the transfer auto-approve to automatically unset the authorization information. This sets the default state of the object to not have the authorization information set. The registrar implementing the Secure Authorization Information Model will not set the authorization information for an inbound transfer, and the registrar implementing the Classic Authorization Information Model will set the new authorization information upon a successful transfer.
Info Response:
Change the <info> command to not return the authorization information in the info response, as described in Section 5.3. This sets up the implementation of "Transition Phase 2 - Storage" (Section 6.2), since the dependency on returning the authorization information in the info response will be removed. This feature is the only one that is not an optional change to the registrar, and this change could potentially break the client, so it's recommended that the registry provide notice of the change.
<Info> Command and Transfer Request:
Change the <info> command and the transfer request to ensure that a registrar cannot get an indication that the authorization information is set or not set by returning the EPP error result code of 2202 when comparing a passed authorization to a non-matching set authorization information value or an unset value.
<Create>コマンド：
空でない値と空の値の両方を許可することで、認可情報を任意とするように<create>コマンドを変更します。 これにより、Section 5.1で説明したように、レジストラーは任意で認可情報の値なしにオブジェクトを作成できるようになります。
<Update>コマンド：
Section 5.2で説明したように、認可情報の設定解除を許可するように<update>コマンドを変更します。 これにより、TTLが期限切れになったとき、または移管がキャンセルもしくは拒否されたときに、レジストラーが任意で認可情報を設定解除できるようになります。
移管承認コマンドと移管の自動承認：
移管承認コマンドと移管の自動承認で、認可情報を自動的に設定解除するように変更します。 これにより、オブジェクトのデフォルトの状態は、認可情報が設定されていない状態になります。 セキュア認可情報モデルを実装しているレジストラーは、受け入れた移管について認可情報を設定しません。 一方、従来型認可情報モデルを実装しているレジストラーは、移管の成功時に新しい認可情報を設定します。
Infoレスポンス：
Section 5.3で説明したように、infoレスポンスで認可情報を返さないように<info>コマンドを変更します。 infoレスポンスで認可情報を返すことへの依存がなくなるため、これは「移行フェーズ2 - 保存」（Section 6.2）の実装の準備となります。 この機能は、レジストラーにとって任意の変更ではない唯一のものであり、この変更によってクライアントが動作しなくなる可能性があるため、レジストリーはこの変更について事前に通知することが推奨されます。
<Info>コマンドと移管リクエスト：
渡された認可情報を、一致しない設定済みの認可情報の値または未設定の値と比較した場合に、EPPのエラー結果コード2202を返すようにすることで、認可情報が設定されているかどうかをレジストラーが知ることができないように、<info>コマンドと移管リクエストを変更します。

6.2. Transition Phase 2 - Storage

6.2. 移行フェーズ2 - 保存

The goal of "Transition Phase 2 - Storage" is to transition the registry to use hashed authorization information instead of encrypted authorization information. There is no direct impact on the registrars, since the only visible indication that the authorization information has been hashed is that the set authorization information is not returned in the info response, as addressed in Section 6.1. Transitioning the authorization information storage includes the following three steps:

「移行フェーズ2 - 保存」の目標は、暗号化された認可情報の代わりにハッシュ化された認可情報を使用するように、レジストリーを移行することです。 認可情報がハッシュ化されたことを示す唯一の目に見える兆候は、Section 6.1で対処したように、設定済みの認可情報がinfoレスポンスで返されないことであるため、レジストラーへの直接の影響はありません。 認可情報の保存の移行には、次の3つの手順が含まれます。

Hash New Authorization Information Values:
Change the <create> command and the <update> command to hash rather than encrypt the authorization information.
Support Comparison against Encrypted or Hashed Authorization Information:
Change the <info> command and the <transfer> request command to be able to compare a passed authorization information value with either a hashed or encrypted authorization information value. This requires that the stored values be self-identifying as being in hashed or encrypted form.
Hash Existing Encrypted Authorization Information Values:
Convert the encrypted authorization information values stored in the registry database to hashed values. This update will not be visible to the registrar. The conversion can be done over a period of time, depending on registry policy.
新しい認可情報の値のハッシュ化：
認可情報を暗号化するのではなくハッシュ化するように、<create>コマンドと<update>コマンドを変更します。
暗号化された認可情報またはハッシュ化された認可情報との比較のサポート：
渡された認可情報の値を、ハッシュ化された認可情報の値と暗号化された認可情報の値のどちらとも比較できるように、<info>コマンドと<transfer>リクエストコマンドを変更します。 これには、保存されている値が、ハッシュ化された形式と暗号化された形式のどちらであるかを自己識別できる必要があります。
既存の暗号化された認可情報の値のハッシュ化：
レジストリーのデータベースに保存されている暗号化された認可情報の値を、ハッシュ値に変換します。 この更新はレジストラーからは見えません。 変換は、レジストリーのポリシーに応じて、一定の期間をかけて行うことができます。

6.3. Transition Phase 3 - Enforcement

6.3. 移行フェーズ3 - 強制

The goal of "Transition Phase 3 - Enforcement" is to complete the implementation of the Secure Authorization Information Model, by enforcing the following:

「移行フェーズ3 - 強制」の目標は、次の事項を強制することで、セキュア認可情報モデルの実装を完了することです。

Disallow Authorization Information on <Create> Command:
Change the <create> command to not allow the passing of a non-empty authorization information value. This behavior could potentially break the client, so it's recommended that the registry provide notice of this change.
Validate the Strong Random Authorization Information:
Change the validation of the authorization information in the <update> command to ensure at least 128 bits of entropy.
<Create>コマンドでの認可情報の禁止：
空でない認可情報の値を渡すことを許可しないように、<create>コマンドを変更します。 この振る舞いによってクライアントが動作しなくなる可能性があるため、レジストリーはこの変更について事前に通知することが推奨されます。
強力でランダムな認可情報の検証：
少なくとも128ビットのエントロピーを確保するように、<update>コマンドにおける認可情報の検証を変更します。

8. Security Considerations

8. セキュリティーに関する考慮事項

Section 4.1 defines the use of a secure random value for the generation of authorization information. The client SHOULD choose a length and set of characters that result in at least 128 bits of entropy.

Section 4.1は、認可情報の生成にセキュアなランダム値を使用することを定義しています。 クライアントは、少なくとも128ビットのエントロピーとなる長さと文字セットを選択すべきです（SHOULD）。

Section 4.2 defines the use of an authorization information TTL. The registrar SHOULD only set the authorization information during the transfer process by setting the authorization information at the start of the transfer process and unsetting the authorization information at the end of the transfer process. The TTL value is left up to registrar policy, and the sponsoring registrar MUST inform the registrant of the TTL when providing the authorization information to the registrant.

Section 4.2は、認可情報のTTLの使用を定義しています。 レジストラーは、移管プロセスの開始時に認可情報を設定し、移管プロセスの終了時に認可情報を設定解除することによって、移管プロセスの間だけ認可情報を設定すべきです（SHOULD）。 TTLの値はレジストラーのポリシーに委ねられます。 スポンサーレジストラーは、登録者に認可情報を提供するときに、登録者にTTLを通知しなければなりません（MUST）。

Section 4.3 defines the storage and transport of authorization information. The losing registrar MUST NOT store the authorization information and the gaining registrar MUST only store the authorization information as a "transient" value during the transfer process, where the authorization information MUST NOT be stored after the end of the transfer process. The registry MUST store the authorization information using a one-way cryptographic hash of at least 256 bits and with a per-authorization information random salt with at least 128 bits. All communication that includes the authorization information MUST be over an encrypted channel. The plain-text authorization information MUST NOT be written to any logs by the registrar or the registry.

Section 4.3は、認可情報の保存と転送を定義しています。 移管元レジストラーは、認可情報を保存してはなりません（MUST NOT）。 移管先レジストラーは、移管プロセスの間の「一時的な」値としてのみ認可情報を保存しなければなりません（MUST）。 認可情報は、移管プロセスの終了後に保存してはなりません（MUST NOT）。 レジストリーは、少なくとも256ビットの一方向の暗号学的ハッシュと、認可情報ごとの少なくとも128ビットのランダムなソルトを使用して、認可情報を保存しなければなりません（MUST）。 認可情報を含むすべての通信は、暗号化されたチャネルを介して行わなければなりません（MUST）。 レジストラーまたはレジストリーは、平文の認可情報をいかなるログにも書き込んではなりません（MUST NOT）。

Section 4.4 defines the matching of the authorization information values. The registry stores an unset authorization information value as a NULL (undefined) value to ensure that an empty input authorization information value never matches it. The method used to define a NULL (undefined) value is database specific.

Section 4.4は、認可情報の値の照合を定義しています。 レジストリーは、空の入力の認可情報の値が決して一致しないように、未設定の認可情報の値をNULL（未定義）値として保存します。 NULL（未定義）値を定義するために使用される方法は、データベース固有です。
