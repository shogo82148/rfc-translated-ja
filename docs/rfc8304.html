Transport Features of the User Datagram Protocol (UDP) and Lightweight UDP (UDP-Lite)

RFC 8304

ユーザーデータグラムプロトコル（UDP）と軽量UDP（UDP-Lite）のトランスポート機能

Abstract

概要

This is an informational document that describes the transport protocol interface primitives provided by the User Datagram Protocol (UDP) and the Lightweight User Datagram Protocol (UDP-Lite) transport protocols. It identifies the datagram services exposed to applications and how an application can configure and use the features offered by the Internet datagram transport service. RFC 8303 documents the usage of transport features provided by IETF transport protocols, describing the way UDP, UDP-Lite, and other transport protocols expose their services to applications and how an application can configure and use the features that make up these services. This document provides input to and context for that document, as well as offers a road map to documentation that may help users of the UDP and UDP-Lite protocols.

この文書は、ユーザーデータグラムプロトコル（UDP）と軽量ユーザーデータグラムプロトコル（UDP-Lite）の2つのトランスポートプロトコルが提供する、トランスポートプロトコルインターフェイスのプリミティブを説明する情報提供の文書です。 この文書は、アプリケーションに公開されるデータグラムサービスと、インターネットのデータグラムトランスポートサービスが提供する機能をアプリケーションが設定して使用する方法を明らかにします。 RFC 8303は、IETFのトランスポートプロトコルが提供するトランスポート機能の使い方を文書化しており、UDP、UDP-Lite、その他のトランスポートプロトコルがアプリケーションにサービスを公開する方法と、それらのサービスを構成する機能をアプリケーションが設定して使用する方法を説明しています。 この文書は、その文書への入力と文脈を提供するとともに、UDPおよびUDP-Liteプロトコルの利用者に役立つ可能性のある文書へのロードマップを提供します。

1. Introduction

1. はじめに

This document presents defined interactions between transport protocols and applications in the form of 'primitives' (function calls) for the User Datagram Protocol (UDP) [RFC0768] and the Lightweight User Datagram Protocol (UDP-Lite) [RFC3828]. In this usage, the word application refers to any program built on the datagram interface, including tunnels and other upper-layer protocols that use UDP and UDP-Lite.

この文書は、ユーザーデータグラムプロトコル（UDP）[RFC0768]と軽量ユーザーデータグラムプロトコル（UDP-Lite）[RFC3828]について、トランスポートプロトコルとアプリケーションの間で定義されたやり取りを「プリミティブ」（関数呼び出し）の形で示します。 ここでいうアプリケーションという語は、データグラムインターフェイスの上に構築されたあらゆるプログラムを指し、UDPやUDP-Liteを使用するトンネルやその他の上位層プロトコルも含みます。

UDP is widely implemented and deployed. It is used for a wide range of applications. A special class of applications can derive benefit from having partially damaged payloads delivered, rather than discarded, when using paths that include error-prone links. Applications that can tolerate payload corruption can choose to use UDP-Lite instead of UDP and use the application programming interface (API) to control checksum protection. Conversely, UDP applications could choose to use UDP-Lite, but this is currently less widely deployed, and users could encounter paths that do not support UDP-Lite. These topics are discussed more in Section 3.4 of "UDP Usage Guidelines" [RFC8085].

UDPは広く実装され、展開されています。 UDPは幅広いアプリケーションで使われています。 特別な種類のアプリケーションでは、エラーの起きやすいリンクを含むパスを使用する場合に、部分的に損傷したペイロードを破棄せずに配送してもらうことで利益を得られます。 ペイロードの破損を許容できるアプリケーションは、UDPの代わりにUDP-Liteを使用することを選択し、アプリケーションプログラミングインターフェイス（API）を使用してチェックサムによる保護を制御できます。 逆に、UDPアプリケーションがUDP-Liteの使用を選択することもできますが、UDP-Liteは現在のところ広くは展開されておらず、ユーザーはUDP-Liteをサポートしないパスに遭遇する可能性があります。 これらの話題は、「UDP Usage Guidelines」[RFC8085]のセクション3.4で詳しく議論されています。

The IEEE standard API for TCP/IP applications is the "socket" interface [POSIX]. An application can use the recv() and send() POSIX functions as well as the recvfrom(), sendto(), recvmsg(), and sendmsg() functions. The UDP and UDP-Lite sockets API differs from that for TCP in several key ways. (Examples of usage of this API are provided in [STEVENS].) In UDP and UDP-Lite, each datagram is a self-contained message of a specified length, and options at the transport layer can be used to set properties for all subsequent datagrams sent using a socket or changed for each datagram. For datagrams, this can require the application to use the API to set IP-level information (IP Time To Live (TTL), Differentiated Services Code Point (DSCP), IP fragmentation, etc.) for the datagrams it sends and receives. In contrast, when using TCP and other connection-oriented transports, the IP-level information normally either remains the same for the duration of a connection or is controlled by the transport protocol rather than the application.

TCP/IPアプリケーション向けのIEEE標準APIは「ソケット」インターフェイス[POSIX]です。 アプリケーションは、POSIXのrecv()関数とsend()関数のほか、recvfrom()、sendto()、recvmsg()、sendmsg()関数を使用できます。 UDPとUDP-LiteのソケットAPIは、いくつかの重要な点でTCPのものと異なります。 （このAPIの使用例は[STEVENS]に記載されています。） UDPとUDP-Liteでは、各データグラムは指定された長さの自己完結したメッセージであり、トランスポート層のオプションを使用して、ソケットを使って送信される後続のすべてのデータグラムに対してプロパティーを設定することも、データグラムごとにプロパティーを変更することもできます。 データグラムの場合、アプリケーションは送受信するデータグラムについて、APIを使用してIPレベルの情報（IPのTime To Live（TTL）、Differentiated Services Code Point（DSCP）、IPフラグメンテーションなど）を設定する必要が生じることがあります。 対照的に、TCPやその他のコネクション指向のトランスポートを使用する場合、IPレベルの情報は通常、コネクションの期間中は同じままであるか、アプリケーションではなくトランスポートプロトコルによって制御されます。

Socket options are used in the sockets API to provide additional functions. For example, the IP_RECVTTL socket option is used by some UDP multicast applications to return the IP TTL field from the IP header of a received datagram.

ソケットAPIでは、追加の機能を提供するためにソケットオプションが使われます。 たとえば、IP_RECVTTLソケットオプションは、受信したデータグラムのIPヘッダーにあるIP TTLフィールドを返すために、一部のUDPマルチキャストアプリケーションで使用されています。

Some platforms also offer applications the ability to directly assemble and transmit IP packets through "raw sockets" or similar facilities. The raw sockets API is a second, more cumbersome, method to send UDP datagrams. The use of this API is discussed in the RFC series in the UDP Guidelines [RFC8085].

一部のプラットフォームでは、「rawソケット」やそれに類する機能を通じて、IPパケットを直接組み立てて送信する能力をアプリケーションに提供しています。 rawソケットAPIは、UDPデータグラムを送信するための、より扱いにくい第2の方法です。 このAPIの使用については、RFCシリーズのUDPガイドライン[RFC8085]で議論されています。

The list of transport service features and primitives in this document is strictly based on the parts of protocol specifications in the RFC series that relate to what the transport protocol provides to an application that uses it and how the application interacts with the transport protocol. Primitives can be invoked by an application or a transport protocol; the latter type is called an "event".

この文書におけるトランスポートサービスの機能とプリミティブの一覧は、RFCシリーズのプロトコル仕様のうち、トランスポートプロトコルがそれを使用するアプリケーションに何を提供するか、およびアプリケーションがトランスポートプロトコルとどのようにやり取りするかに関係する部分に厳密に基づいています。 プリミティブは、アプリケーションまたはトランスポートプロトコルによって呼び出されます。 後者の種類は「イベント」と呼ばれます。

The description in Section 3 follows the methodology defined by the IETF TAPS Working Group in [RFC8303]. Specifically, this document provides the first pass of this process, which discusses the relevant RFC text describing primitives for each protocol. [RFC8303] uses this input to document the usage of transport features provided by IETF transport protocols, describing the way UDP, UDP-Lite, and other transport protocols expose their services to applications and how an application can configure and use the features that make up these services.

セクション3の説明は、IETF TAPSワーキンググループが[RFC8303]で定義した方法論に従っています。 具体的には、この文書はこのプロセスの最初のパスを提供するもので、各プロトコルのプリミティブを説明している関連するRFCの記述を議論します。 [RFC8303]はこの入力を使用して、IETFのトランスポートプロトコルが提供するトランスポート機能の使い方を文書化し、UDP、UDP-Lite、その他のトランスポートプロトコルがアプリケーションにサービスを公開する方法と、それらのサービスを構成する機能をアプリケーションが設定して使用する方法を説明しています。

The presented road map to documentation of the transport interface may also help developers working with UDP and UDP-Lite.

ここで示すトランスポートインターフェイスの文書へのロードマップは、UDPやUDP-Liteを扱う開発者にも役立つかもしれません。

この文書は、「On the Usage of Transport Features Provided by IETF Transport Protocols」[RFC8303]で使用される、UDPとUDP-Liteのパス1の分析の詳細を提供します。 この文書は、その文書で定義された共通の用語を使用し、また、RFC 2119[RFC2119]の用語を使用しているRFCを引用します。

3. UDP and UDP-Lite Primitives

3. UDPとUDP-Liteのプリミティブ

UDP [RFC0768] [RFC8200] and UDP-Lite [RFC3828] are IETF Standards Track transport protocols. These protocols provide unidirectional, datagram services, supporting transmit and receive operations that preserve message boundaries.

UDP[RFC0768] [RFC8200]とUDP-Lite[RFC3828]は、IETFの標準化過程のトランスポートプロトコルです。 これらのプロトコルは、メッセージの境界を保持する送信操作と受信操作をサポートする、単方向のデータグラムサービスを提供します。

This section summarizes the relevant text parts of the RFCs describing the UDP and UDP-Lite protocols, focusing on what the transport protocols provide to the application and how the transport is used (based on abstract API descriptions, where they are available). It describes how UDP is used with IPv4 or IPv6 to send unicast or anycast datagrams and is used to send broadcast datagrams for IPv4. A set of network-layer primitives required to use UDP or UDP-Lite with IP multicast (for IPv4 and IPv6) have been specified in the RFC series. Appendix A describes where to find documentation for network-layer primitives required to use UDP or UDP-Lite with IP multicast (for IPv4 and IPv6).

このセクションでは、UDPとUDP-Liteのプロトコルを説明しているRFCの関連する記述を、トランスポートプロトコルがアプリケーションに何を提供するか、そしてトランスポートがどのように使われるか（抽象的なAPIの記述がある場合にはそれに基づきます）に焦点を当てて要約します。 このセクションでは、IPv4またはIPv6でユニキャストやエニーキャストのデータグラムを送信するためにUDPをどのように使用するか、そしてIPv4でブロードキャストのデータグラムを送信するためにUDPをどのように使用するかを説明します。 UDPやUDP-LiteをIPマルチキャストで（IPv4とIPv6で）使用するために必要なネットワーク層のプリミティブの一式が、RFCシリーズで規定されています。 付録Aでは、UDPやUDP-LiteをIPマルチキャストで（IPv4とIPv6で）使用するために必要なネットワーク層のプリミティブについての文書をどこで見つけられるかを説明します。

3.1. Primitives Provided by UDP

3.1. UDPが提供するプリミティブ

"User Datagram Protocol" [RFC0768] states:

「User Datagram Protocol」[RFC0768]には次のように書かれています。

This User Datagram Protocol (UDP) is defined to make available a datagram mode of packet-switched computer communication in the environment of an interconnected set of computer networks...This protocol provides a procedure for application programs to send messages to other programs with a minimum of protocol mechanism.

このユーザーデータグラムプロトコル（UDP）は、相互接続されたコンピューターネットワークの集合という環境において、パケット交換方式のコンピューター通信のデータグラムモードを利用可能にするために定義されています……このプロトコルは、最小限のプロトコルメカニズムで、アプリケーションプログラムが他のプログラムにメッセージを送信するための手順を提供します。

The User Interface section of RFC 768 states that the user interface to an application should allow

RFC 768のUser Interfaceセクションには、アプリケーションへのユーザーインターフェイスが次のことを可能にすべきだと書かれています。

the creation of new receive ports, receive operations on the receive ports that return the data octets and an indication of source port and source address, and an operation that allows a datagram to be sent, specifying the data, source and destination ports and addresses to be sent.

新しい受信ポートの作成、データオクテットと送信元ポートおよび送信元アドレスの表示を返す受信ポート上の受信操作、そしてデータ、送信元と宛先のポートとアドレスを指定してデータグラムを送信できるようにする操作。

UDP has been defined for IPv6 [RFC8200], together with API extensions for "Basic Socket Interface Extensions for IPv6" [RFC3493].

UDPはIPv6向けにも定義されており[RFC8200]、あわせて「Basic Socket Interface Extensions for IPv6」[RFC3493]のAPI拡張も定義されています。

[RFC6935] and [RFC6936] define an update to the UDP transport originally specified in [RFC2460] (note that RFC 2460 has been obsoleted by RFC 8200). This enables use of a zero UDP checksum mode with a tunnel protocol, providing that the method satisfies the requirements in the corresponding applicability statement [RFC6936].

[RFC6935]と[RFC6936]は、もともと[RFC2460]で規定されていたUDPトランスポートに対する更新を定義しています（RFC 2460はRFC 8200によって廃止されていることに注意してください）。 これにより、対応する適用性声明[RFC6936]の要件をその方法が満たしていれば、トンネルプロトコルでUDPチェックサムをゼロにするモードを使用できるようになります。

UDP offers only a basic transport interface. UDP datagrams may be directly sent and received, without exchanging messages between the endpoints to set up a connection (i.e., no handshake is performed by the transport protocol prior to communication). Using the sockets API, applications can receive packets from more than one IP source address on a single UDP socket. Common support allows specification of the local IP address, destination IP address, local port, and destination port values. Any or all of these can be indicated, with defaults supplied by the local system when these are not specified. The local endpoint address is set using the BIND call. At the remote end, the remote endpoint address is set using the CONNECT call. The CLOSE function has local significance only. It does not impact the status of the remote endpoint.

UDPは基本的なトランスポートインターフェイスしか提供しません。 UDPデータグラムは、コネクションを確立するためにエンドポイント間でメッセージを交換することなく、直接送受信できます（つまり、通信の前にトランスポートプロトコルによるハンドシェイクは行われません）。 ソケットAPIを使用すると、アプリケーションは単一のUDPソケットで複数のIP送信元アドレスからパケットを受信できます。 一般的なサポートでは、ローカルIPアドレス、宛先IPアドレス、ローカルポート、宛先ポートの値を指定できます。 これらのいずれか、またはすべてを指定でき、指定されなかった場合はローカルシステムがデフォルト値を提供します。 ローカルエンドポイントのアドレスはBIND呼び出しを使用して設定します。 リモート側では、リモートエンドポイントのアドレスはCONNECT呼び出しを使用して設定します。 CLOSE関数はローカルでのみ意味を持ちます。 CLOSE関数はリモートエンドポイントの状態には影響を与えません。

Neither UDP nor UDP-Lite provide congestion control, retransmission, or mechanisms for application-level packetization that would avoid IP fragmentation and other transport functions. This means that applications using UDP need to provide additional functions on top of the UDP transport API [RFC8085]. Some transport functions require parameters to be passed through the API to control the network layer (IPv4 or IPv6). These additional primitives could be considered a part of the network layer (e.g., control of the setting of the Don't Fragment (DF) flag on a transmitted IPv4 datagram) but are nonetheless essential to allow a user of the UDP API to implement functions that are normally associated with the transport layer (such as probing for the path maximum transmission size). This document includes such primitives.

UDPもUDP-Liteも、輻輳制御、再送、IPフラグメンテーションを回避するアプリケーションレベルのパケット化のメカニズム、その他のトランスポート機能を提供しません。 つまり、UDPを使用するアプリケーションは、UDPトランスポートAPIの上で追加の機能を提供する必要があります[RFC8085]。 一部のトランスポート機能では、ネットワーク層（IPv4またはIPv6）を制御するために、APIを通じてパラメーターを渡す必要があります。 これらの追加のプリミティブはネットワーク層の一部とみなすこともできますが（たとえば、送信するIPv4データグラムのDon't Fragment（DF）フラグの設定の制御）、それでもUDP APIの利用者が、通常トランスポート層に関連付けられる機能（パスの最大伝送サイズの探索など）を実装するためには不可欠です。 この文書にはそのようなプリミティブも含めています。

Guidance on the use of the services provided by UDP is provided in the UDP Guidelines [RFC8085]. This also states that

UDPが提供するサービスの使用に関するガイダンスは、UDPガイドライン[RFC8085]で提供されています。 UDPガイドラインには次のようにも書かれています。

many operating systems also allow a UDP socket to be connected, i.e., to bind a UDP socket to a specific pair of addresses and ports. This is similar to the corresponding TCP sockets API functionality. However, for UDP, this is only a local operation that serves to simplify the local send/receive functions and to filter the traffic for the specified addresses and ports. Binding a UDP socket does not establish a connection -- UDP does not notify the remote end when a local UDP socket is bound. Binding a socket also allows configuring options that affect the UDP or IP layers, for example, use of the UDP checksum or the IP Timestamp option. On some stacks, a bound socket also allows an application to be notified when ICMP error messages are received for its transmissions [RFC1122].

多くのオペレーティングシステムでは、UDPソケットをコネクト状態にすること、つまり、UDPソケットをアドレスとポートの特定のペアにバインドすることもできます。 これは、対応するTCPソケットAPIの機能に似ています。 しかし、UDPの場合、これはローカルな操作にすぎず、ローカルの送受信関数を単純化し、指定されたアドレスとポートでトラフィックをフィルタリングする役割を果たします。 UDPソケットをバインドしてもコネクションは確立されません。 ローカルのUDPソケットがバインドされても、UDPはリモート側に通知しません。 ソケットをバインドすると、UDP層やIP層に影響するオプション、たとえばUDPチェックサムやIP Timestampオプションの使用を設定することもできます。 一部のスタックでは、バインドされたソケットにより、アプリケーションが自身の送信に対するICMPエラーメッセージを受信したときに通知を受けることもできます[RFC1122]。

The POSIX Base Specifications [POSIX] define an API that offers mechanisms for an application to receive asynchronous data events at the socket layer. Calls such as "poll", "select", or "queue" allow an application to be notified when data has arrived at a socket or when a socket has flushed its buffers.

POSIX Base Specifications[POSIX]は、アプリケーションがソケット層で非同期のデータイベントを受け取るためのメカニズムを提供するAPIを定義しています。 「poll」、「select」、「queue」などの呼び出しにより、アプリケーションは、ソケットにデータが到着したときや、ソケットがバッファーをフラッシュしたときに通知を受けることができます。

A callback-driven API to the network interface can be structured on top of these calls. Implicit connection setup allows an application to delegate connection life management to the transport API. The transport API uses protocol primitives to offer the automated service to the application via the sockets API. By combining UDP primitives (CONNECT.UDP and SEND.UDP), a higher-level API could offer a similar service.

これらの呼び出しの上に、ネットワークインターフェイスへのコールバック駆動型のAPIを構築できます。 暗黙的なコネクションの確立により、アプリケーションはコネクションの存続期間の管理をトランスポートAPIに委ねることができます。 トランスポートAPIは、プロトコルのプリミティブを使用して、ソケットAPIを通じてアプリケーションに自動化されたサービスを提供します。 UDPのプリミティブ（CONNECT.UDPとSEND.UDP）を組み合わせることで、より高レベルのAPIで同様のサービスを提供できるでしょう。

The following datagram primitives are specified:

次のデータグラムプリミティブが規定されています。

CONNECT:

The CONNECT primitive allows the association of source and destination port sets to a socket to enable creation of a 'connection' for UDP traffic. This UDP connection allows an application to be notified of errors received from the network stack and provides a shorthand access to the SEND and RECEIVE primitives. Since UDP is itself connectionless, no datagrams are sent because this primitive is executed. A further connect call can be used to change the association.

The roles of a client and a server are often not appropriate for UDP, where connections can be peer-to-peer. The listening functions are performed using one of the forms of the CONNECT primitive:

  1. bind(): A bind operation sets the local port either implicitly, triggered by a "sendto" operation on an unbound unconnected socket using an ephemeral port, or by an explicit "bind" to use a configured or well-known port.
  2. bind(); connect(): A bind operation that is followed by a CONNECT primitive. The bind operation establishes the use of a known local port for datagrams rather than using an ephemeral port. The connect operation specifies a known address port combination to be used by default for future datagrams. This form either is used after receiving a datagram from an endpoint that causes the creation of a connection or can be triggered by a third-party configuration or a protocol trigger (such as reception of a UDP Service Description Protocol (SDP) [RFC4566] record).
SEND:
The SEND primitive hands over a provided number of bytes that UDP should send to the other side of a UDP connection in a UDP datagram. The primitive can be used by an application to directly send datagrams to an endpoint defined by an address/port pair. If a connection has been created, then the address/port pair is inferred from the current connection for the socket. Connecting a socket allows network errors to be returned to the application as a notification on the SEND primitive. Messages passed to the SEND primitive that cannot be sent atomically in an IP packet will not be sent by the network layer, generating an error.
RECEIVE:
The RECEIVE primitive allocates a receiving buffer to accommodate a received datagram. The primitive returns the number of bytes provided from a received UDP datagram. Section 4.1.3.5 of the requirements of Internet hosts [RFC1122] states "When a UDP datagram is received, its specific-destination address MUST be passed up to the application layer."
CHECKSUM_ENABLED:
The optional CHECKSUM_ENABLED primitive controls whether a sender enables the UDP checksum when sending datagrams [RFC0768] [RFC6935] [RFC6936] [RFC8085]. When unset, this overrides the default UDP behavior, disabling the checksum on sending. Section 4.1.3.4 of the requirements for Internet hosts [RFC1122] states that "An application MAY optionally be able to control whether a UDP checksum will be generated, but it MUST default to checksumming on."
REQUIRE_CHECKSUM:
The optional REQUIRE_CHECKSUM primitive determines whether UDP datagrams received with a zero checksum are permitted or discarded; UDP defaults to requiring checksums. Section 4.1.3.4 of the requirements for Internet hosts [RFC1122] states that "An application MAY optionally be able to control whether UDP datagrams without checksums should be discarded or passed to the application." Section 3.1 of the specification for UDP-Lite [RFC3828] requires that the checksum field be non-zero; hence, the UDP-Lite API must discard all datagrams received with a zero checksum.
SET_IP_OPTIONS:
The SET_IP_OPTIONS primitive requests the network layer to send a datagram with the specified IP options. Section 4.1.3.2 of the requirements for Internet hosts [RFC1122] states that an "application MUST be able to specify IP options to be sent in its UDP datagrams, and UDP MUST pass these options to the IP layer."
GET_IP_OPTIONS:
The GET_IP_OPTIONS primitive retrieves the IP options of a datagram received at the network layer. Section 4.1.3.2 of the requirements for Internet hosts [RFC1122] states that a UDP receiver "MUST pass any IP option that it receives from the IP layer transparently to the application layer."
SET_DF:
The SET_DF primitive allows the network layer to fragment packets using the Fragment Offset in IPv4 [RFC6864] and a host to use Fragment Headers in IPv6 [RFC8200]. The SET_DF primitive sets the Don't Fragment (DF) flag in the IPv4 packet header that carries a UDP datagram, which allows routers to fragment IPv4 packets. Although some specific applications rely on fragmentation support, in general, a UDP application should implement a method that avoids IP fragmentation (Section 4 of [RFC8085]). NOTE: In many other IETF transports (e.g., TCP and the Stream Control Transmission Protocol (SCTP)), the transport provides the support needed to use DF. However, when using UDP, the application is responsible for the techniques needed to discover the effective Path MTU (PMTU) allowed on the network path, coordinating with the network layer. Classical Path MTU Discovery (PMTUD) [RFC1191] relies upon the network path returning ICMP Fragmentation Needed or ICMPv6 Packet Too Big messages to the sender. When these ICMP messages are not delivered (or filtered), a sender is unable to learn the actual PMTU, and UDP datagrams larger than the PMTU will be "black holed". To avoid this, an application can instead implement Packetization Layer Path MTU Discovery (PLPMTUD) [RFC4821] that does not rely upon network support for ICMPv6 messages and is therefore considered more robust than standard PMTUD, as recommended in [RFC8085] and [RFC8201].
GET_MMS_S:

The GET_MMS_S primitive retrieves a network-layer value that indicates the maximum message size (MMS) that may be sent at the transport layer using a non-fragmented IP packet from the configured interface. This value is specified in Section 6.1 of [RFC1191] and Section 5.1 of [RFC8201]. It is calculated from Effective MTU for Sending (EMTU_S) and the link MTU for the given source IP address. This takes into account the size of the IP header plus space reserved by the IP layer for additional headers (if any). UDP applications should use this value as part of a method to avoid sending UDP datagrams that would result in IP packets that exceed the effective PMTU allowed across the network path. The effective PMTU (specified in Section 1 of [RFC1191]) is equivalent to the EMTU_S (specified in [RFC1122]). The specification of PLPMTUD [RFC4821] states:

If PLPMTUD updates the MTU for a particular path, all Packetization Layer sessions that share the path representation (as described in Section 5.2) SHOULD be notified to make use of the new MTU and make the required congestion control adjustments.

GET_MMS_R:
The GET_MMS_R primitive retrieves a network-layer value that indicates the MMS that may be received at the transport layer from the configured interface. This value is specified in Section 3.1 of [RFC1191]. It is calculated from Effective MTU for Receiving (EMTU_R) and the link MTU for the given source IP address, and it takes into account the size of the IP header plus space reserved by the IP layer for additional headers (if any).
SET_TTL:
The SET_TTL primitive sets the Hop Limit (TTL field) in the network layer that is used in the IPv4 header of a packet that carries a UDP datagram. This is used to limit the scope of unicast datagrams. Section 3.2.2.4 of the requirements for Internet hosts [RFC1122] states that "An incoming Time Exceeded message MUST be passed to the transport layer."
GET_TTL:
The GET_TTL primitive retrieves the value of the TTL field in an IP packet received at the network layer. An application using the Generalized TTL Security Mechanism (GTSM) [RFC5082] can use this information to trust datagrams with a TTL value within the expected range, as described in Section 3 of RFC 5082.
SET_MIN_TTL:
The SET_MIN_TTL primitive restricts datagrams delivered to the application to those received with an IP TTL value greater than or equal to the passed parameter. This primitive can be used to implement applications such as GTSM [RFC5082] too, as described in Section 3 of RFC 5082, but this RFC does not specify this method.
SET_IPV6_UNICAST_HOPS:
The SET_IPV6_UNICAST_HOPS primitive sets the network-layer Hop Limit field in an IPv6 packet header [RFC8200] carrying a UDP datagram. For IPv6 unicast datagrams, this is functionally equivalent to the SET_TTL IPv4 function.
GET_IPV6_UNICAST_HOPS:
The GET_IPV6_UNICAST_HOPS primitive is a network-layer function that reads the hop count in the IPv6 header [RFC8200] information of a received UDP datagram. This is specified in Section 6.3 of RFC 3542. For IPv6 unicast datagrams, this is functionally equivalent to the GET_TTL IPv4 function.
SET_DSCP:
The SET_DSCP primitive is a network-layer function that sets the DSCP (or the legacy Type of Service (ToS)) value [RFC2474] to be used in the field of an IP header of a packet that carries a UDP datagram. Section 2.4 of the requirements for Internet hosts [RFC1123] states that "Applications MUST select appropriate ToS values when they invoke transport layer services, and these values MUST be configurable." The application should be able to change the ToS during the connection lifetime, and the ToS value should be passed to the IP layer unchanged. Section 4.1.4 of [RFC1122] also states that on reception the "UDP MAY pass the received ToS up to the application layer." The Diffserv model [RFC2475] [RFC3260] replaces this field in the IP header assigning the six most significant bits to carry the DSCP field [RFC2474]. Preserving the intention of the host requirements [RFC1122] to allow the application to specify the "Type of Service" should be interpreted to mean that an API should allow the application to set the DSCP. Section 3.1.8 of the UDP Guidelines [RFC8085] describes the way UDP applications should use this field. Normally, a UDP socket will assign a single DSCP value to all datagrams in a flow, but a sender is allowed to use different DSCP values for datagrams within the same flow in certain cases [RFC8085]. There are guidelines for WebRTC that illustrate this use [RFC7657].
SET_ECN:
The SET_ECN primitive is a network-layer function that sets the Explicit Congestion Notification (ECN) field in the IP header of a UDP datagram. The ECN field defaults to a value of 00. When the use of the ToS field was redefined by Diffserv [RFC3260], 2 bits of the field were assigned to support ECN [RFC3168]. Section 3.1.5 of the UDP Guidelines [RFC8085] describes the way UDP applications should use this field. NOTE: In many other IETF transports (e.g., TCP), the transport provides the support needed to use ECN; when using UDP, the application or higher-layer protocol is itself responsible for the techniques needed to use ECN.
GET_ECN:
The GET_ECN primitive is a network-layer function that returns the value of the ECN field in the IP header of a received UDP datagram. Section 3.1.5 of [RFC8085] states that a UDP receiver "MUST check the ECN field at the receiver for each UDP datagram that it receives on this port", requiring the UDP receiver API to pass the received ECN field up to the application layer to enable appropriate congestion feedback.
ERROR_REPORT:
The ERROR_REPORT event informs an application of "soft errors", including the arrival of an ICMP or ICMPv6 error message. Section 4.1.4 of the requirements for Internet hosts [RFC1122] states that "UDP MUST pass to the application layer all ICMP error messages that it receives from the IP layer." For example, this event is required to implement ICMP-based Path MTU Discovery [RFC1191] [RFC8201]. UDP applications must perform a CONNECT to receive ICMP errors.
CLOSE:
The CLOSE primitive closes a connection. No further datagrams can be sent or received. Since UDP is itself connectionless, no datagrams are sent when this primitive is executed.
CONNECT:

CONNECTプリミティブは、送信元ポートと宛先ポートの組をソケットに関連付けて、UDPトラフィックの「コネクション」を作成できるようにします。 このUDPコネクションにより、アプリケーションはネットワークスタックから受け取ったエラーの通知を受けられるようになり、またSENDプリミティブとRECEIVEプリミティブへの簡易なアクセスが提供されます。 UDP自体はコネクションレスなので、このプリミティブを実行してもデータグラムは送信されません。 関連付けを変更するには、もう一度connect呼び出しを使用できます。

コネクションがピアツーピアになりうるUDPでは、クライアントとサーバーという役割が適切でないことがよくあります。 待ち受けの機能は、CONNECTプリミティブの次のいずれかの形式を使用して実行されます。

  1. bind()：バインド操作は、ローカルポートを設定します。 バインドされておらずコネクトもされていないソケットに対する「sendto」操作をきっかけにエフェメラルポートを使用して暗黙的に設定するか、明示的な「bind」によって設定済みのポートまたはウェルノウンポートを使用するように設定します。
  2. bind(); connect()：バインド操作の後にCONNECTプリミティブが続くものです。 バインド操作は、エフェメラルポートを使用する代わりに、データグラムに既知のローカルポートを使用することを確立します。 コネクト操作は、以降のデータグラムにデフォルトで使用する既知のアドレスとポートの組み合わせを指定します。 この形式は、コネクションの作成のきっかけとなるデータグラムをエンドポイントから受信した後に使用されるか、第三者による設定やプロトコルのトリガー（UDP Service Description Protocol（SDP）[RFC4566]レコードの受信など）によって起動されます。
SEND:
SENDプリミティブは、UDPがUDPコネクションの相手側にUDPデータグラムで送信すべき、指定されたバイト数のデータを引き渡します。 アプリケーションは、このプリミティブを使用して、アドレスとポートのペアで定義されたエンドポイントにデータグラムを直接送信できます。 コネクションが作成されている場合、アドレスとポートのペアはソケットの現在のコネクションから推測されます。 ソケットをコネクトすると、ネットワークエラーをSENDプリミティブに対する通知としてアプリケーションに返すことができます。 SENDプリミティブに渡されたメッセージのうち、1つのIPパケットでアトミックに送信できないものは、ネットワーク層によって送信されず、エラーが発生します。
RECEIVE:
RECEIVEプリミティブは、受信したデータグラムを格納するための受信バッファーを割り当てます。 このプリミティブは、受信したUDPデータグラムから提供されたバイト数を返します。 インターネットホストの要件[RFC1122]のセクション4.1.3.5には、「UDPデータグラムを受信したとき、その特定宛先アドレスはアプリケーション層に渡されなければなりません（MUST）」と書かれています。
CHECKSUM_ENABLED:
任意のCHECKSUM_ENABLEDプリミティブは、送信者がデータグラムを送信するときにUDPチェックサムを有効にするかどうかを制御します[RFC0768] [RFC6935] [RFC6936] [RFC8085]。 これが設定されていない場合、UDPのデフォルトの振る舞いを上書きし、送信時のチェックサムを無効にします。 インターネットホストの要件[RFC1122]のセクション4.1.3.4には、「アプリケーションは、UDPチェックサムを生成するかどうかを任意で制御できてもよいです（MAY）。ただし、デフォルトではチェックサムを有効にしなければなりません（MUST）」と書かれています。
REQUIRE_CHECKSUM:
任意のREQUIRE_CHECKSUMプリミティブは、チェックサムがゼロで受信したUDPデータグラムを許可するか破棄するかを決定します。 UDPのデフォルトでは、チェックサムを要求します。 インターネットホストの要件[RFC1122]のセクション4.1.3.4には、「アプリケーションは、チェックサムのないUDPデータグラムを破棄すべきかアプリケーションに渡すべきかを任意で制御できてもよいです（MAY）」と書かれています。 UDP-Liteの仕様[RFC3828]のセクション3.1では、チェックサムフィールドがゼロでないことを要求しています。 したがって、UDP-Lite APIは、チェックサムがゼロで受信したすべてのデータグラムを破棄する必要があります。
SET_IP_OPTIONS:
SET_IP_OPTIONSプリミティブは、指定したIPオプションを付けてデータグラムを送信するようネットワーク層に要求します。 インターネットホストの要件[RFC1122]のセクション4.1.3.2には、「アプリケーションは、自身のUDPデータグラムで送信するIPオプションを指定できる必要があります（MUST）。また、UDPはこれらのオプションをIP層に渡さなければなりません（MUST）」と書かれています。
GET_IP_OPTIONS:
GET_IP_OPTIONSプリミティブは、ネットワーク層で受信したデータグラムのIPオプションを取得します。 インターネットホストの要件[RFC1122]のセクション4.1.3.2には、UDPの受信者は「IP層から受け取ったすべてのIPオプションを、透過的にアプリケーション層に渡さなければなりません（MUST）」と書かれています。
SET_DF:
SET_DFプリミティブは、ネットワーク層がIPv4のFragment Offset[RFC6864]を使用してパケットをフラグメント化することや、ホストがIPv6のFragmentヘッダー[RFC8200]を使用することを可能にします。 SET_DFプリミティブは、UDPデータグラムを運ぶIPv4パケットヘッダーのDon't Fragment（DF）フラグを設定し、これによってルーターがIPv4パケットをフラグメント化できるようになります。 一部の特定のアプリケーションはフラグメンテーションのサポートに依存していますが、一般に、UDPアプリケーションはIPフラグメンテーションを回避する方法を実装すべきです（[RFC8085]のセクション4）。 注：他の多くのIETFトランスポート（たとえば、TCPやStream Control Transmission Protocol（SCTP））では、DFを使用するために必要なサポートをトランスポートが提供します。 しかし、UDPを使用する場合、ネットワーク層と連携して、ネットワークパス上で許容される実効パスMTU（PMTU）を発見するために必要な技術については、アプリケーションが責任を負います。 従来のパスMTU探索（PMTUD）[RFC1191]は、ネットワークパスがICMP Fragmentation NeededメッセージまたはICMPv6 Packet Too Bigメッセージを送信者に返すことに依存しています。 これらのICMPメッセージが配送されない（またはフィルタリングされる）場合、送信者は実際のPMTUを知ることができず、PMTUより大きいUDPデータグラムは「ブラックホール化」されます。 これを回避するために、アプリケーションは代わりにパケット化層パスMTU探索（PLPMTUD）[RFC4821]を実装できます。 [RFC8085]や[RFC8201]で推奨されているように、PLPMTUDはICMPv6メッセージに対するネットワークのサポートに依存しないので、標準のPMTUDよりも堅牢であるとみなされています。
GET_MMS_S:

GET_MMS_Sプリミティブは、設定されたインターフェイスから、フラグメント化されていないIPパケットを使用してトランスポート層で送信できる最大メッセージサイズ（MMS）を示すネットワーク層の値を取得します。 この値は、[RFC1191]のセクション6.1と[RFC8201]のセクション5.1で規定されています。 この値は、送信の実効MTU（EMTU_S）と、指定された送信元IPアドレスのリンクMTUから計算されます。 これには、IPヘッダーのサイズに加えて、IP層が追加のヘッダー（もしあれば）のために予約した領域が考慮されます。 UDPアプリケーションは、ネットワークパス全体で許容される実効PMTUを超えるIPパケットとなるようなUDPデータグラムの送信を回避する方法の一部として、この値を使用すべきです。 実効PMTU（[RFC1191]のセクション1で規定）は、EMTU_S（[RFC1122]で規定）と同等です。 PLPMTUDの仕様[RFC4821]には、次のように書かれています。

PLPMTUDが特定のパスのMTUを更新した場合、（セクション5.2で説明されているように）そのパスの表現を共有するすべてのパケット化層セッションに通知し、新しいMTUを利用して必要な輻輳制御の調整を行わせるべきです（SHOULD）。

GET_MMS_R:
GET_MMS_Rプリミティブは、設定されたインターフェイスからトランスポート層で受信できるMMSを示すネットワーク層の値を取得します。 この値は[RFC1191]のセクション3.1で規定されています。 この値は、受信の実効MTU（EMTU_R）と、指定された送信元IPアドレスのリンクMTUから計算され、IPヘッダーのサイズに加えて、IP層が追加のヘッダー（もしあれば）のために予約した領域が考慮されます。
SET_TTL:
SET_TTLプリミティブは、UDPデータグラムを運ぶパケットのIPv4ヘッダーで使用される、ネットワーク層のHop Limit（TTLフィールド）を設定します。 これは、ユニキャストデータグラムの範囲を制限するために使用されます。 インターネットホストの要件[RFC1122]のセクション3.2.2.4には、「受信したTime Exceededメッセージは、トランスポート層に渡されなければなりません（MUST）」と書かれています。
GET_TTL:
GET_TTLプリミティブは、ネットワーク層で受信したIPパケットのTTLフィールドの値を取得します。 Generalized TTL Security Mechanism（GTSM）[RFC5082]を使用するアプリケーションは、RFC 5082のセクション3で説明されているように、この情報を使用して、TTL値が期待される範囲内にあるデータグラムを信頼できます。
SET_MIN_TTL:
SET_MIN_TTLプリミティブは、アプリケーションに配送されるデータグラムを、IP TTL値が渡されたパラメーター以上で受信したものに制限します。 このプリミティブは、RFC 5082のセクション3で説明されているように、GTSM[RFC5082]のようなアプリケーションの実装にも使用できますが、このRFCではこの方法を規定していません。
SET_IPV6_UNICAST_HOPS:
SET_IPV6_UNICAST_HOPSプリミティブは、UDPデータグラムを運ぶIPv6パケットヘッダー[RFC8200]の、ネットワーク層のHop Limitフィールドを設定します。 IPv6ユニキャストデータグラムの場合、これは機能的にIPv4のSET_TTL関数と同等です。
GET_IPV6_UNICAST_HOPS:
GET_IPV6_UNICAST_HOPSプリミティブは、受信したUDPデータグラムのIPv6ヘッダー[RFC8200]の情報にあるホップ数を読み取る、ネットワーク層の関数です。 これはRFC 3542のセクション6.3で規定されています。 IPv6ユニキャストデータグラムの場合、これは機能的にIPv4のGET_TTL関数と同等です。
SET_DSCP:
SET_DSCPプリミティブは、UDPデータグラムを運ぶパケットのIPヘッダーのフィールドで使用するDSCP（または従来のType of Service（ToS））の値[RFC2474]を設定する、ネットワーク層の関数です。 インターネットホストの要件[RFC1123]のセクション2.4には、「アプリケーションは、トランスポート層のサービスを呼び出すときに適切なToS値を選択しなければなりません（MUST）。また、これらの値は設定可能でなければなりません（MUST）」と書かれています。 アプリケーションはコネクションの存続期間中にToSを変更できるべきであり、ToS値は変更されずにIP層に渡されるべきです。 [RFC1122]のセクション4.1.4にも、受信時に「UDPは受信したToSをアプリケーション層に渡してもよいです（MAY）」と書かれています。 Diffservモデル[RFC2475] [RFC3260]は、IPヘッダーのこのフィールドを置き換え、上位6ビットをDSCPフィールドの運搬に割り当てています[RFC2474]。 アプリケーションが「Type of Service」を指定できるようにするというホスト要件[RFC1122]の意図を保つには、APIがアプリケーションにDSCPの設定を許可すべきであるという意味に解釈すべきです。 UDPガイドライン[RFC8085]のセクション3.1.8では、UDPアプリケーションがこのフィールドをどのように使用すべきかを説明しています。 通常、UDPソケットはフロー内のすべてのデータグラムに単一のDSCP値を割り当てますが、特定の場合には、送信者が同じフロー内のデータグラムに異なるDSCP値を使用することが許されています[RFC8085]。 この使い方を示すWebRTC向けのガイドラインがあります[RFC7657]。
SET_ECN:
SET_ECNプリミティブは、UDPデータグラムのIPヘッダーにある明示的輻輳通知（ECN）フィールドを設定する、ネットワーク層の関数です。 ECNフィールドのデフォルト値は00です。 ToSフィールドの使い方がDiffserv[RFC3260]によって再定義された際に、このフィールドの2ビットがECNのサポートに割り当てられました[RFC3168]。 UDPガイドライン[RFC8085]のセクション3.1.5では、UDPアプリケーションがこのフィールドをどのように使用すべきかを説明しています。 注：他の多くのIETFトランスポート（たとえば、TCP）では、ECNを使用するために必要なサポートをトランスポートが提供します。 UDPを使用する場合は、ECNを使用するために必要な技術について、アプリケーションまたは上位層プロトコル自身が責任を負います。
GET_ECN:
GET_ECNプリミティブは、受信したUDPデータグラムのIPヘッダーにあるECNフィールドの値を返す、ネットワーク層の関数です。 [RFC8085]のセクション3.1.5には、UDPの受信者は「このポートで受信する各UDPデータグラムについて、受信者でECNフィールドをチェックしなければなりません（MUST）」と書かれています。 そのため、適切な輻輳フィードバックを可能にするには、UDP受信者のAPIが、受信したECNフィールドをアプリケーション層に渡す必要があります。
ERROR_REPORT:
ERROR_REPORTイベントは、ICMPやICMPv6のエラーメッセージの到着を含む「ソフトエラー」をアプリケーションに通知します。 インターネットホストの要件[RFC1122]のセクション4.1.4には、「UDPは、IP層から受け取ったすべてのICMPエラーメッセージをアプリケーション層に渡さなければなりません（MUST）」と書かれています。 たとえば、ICMPベースのパスMTU探索[RFC1191] [RFC8201]を実装するには、このイベントが必要です。 UDPアプリケーションがICMPエラーを受け取るには、CONNECTを実行する必要があります。
CLOSE:
CLOSEプリミティブは、コネクションをクローズします。 それ以降、データグラムを送信することも受信することもできなくなります。 UDP自体はコネクションレスなので、このプリミティブを実行してもデータグラムは送信されません。

3.1.1. Excluded Primitives

3.1.1. 除外したプリミティブ

In the requirements for Internet hosts [RFC1122], Section 3.4 describes GET_MAXSIZES and ADVISE_DELIVPROB, and Section 3.3.4.4 describes GET_SRCADDR. These mechanisms are no longer used. It also specifies use of the Source Quench ICMP message, which has since been deprecated [RFC6633].

インターネットホストの要件では、[RFC1122], セクション3.4でGET_MAXSIZESとADVISE_DELIVPROBを説明し、セクション3.3.4.4でGET_SRCADDRを説明しています。 これらのメカニズムはもう使われていません。 インターネットホストの要件では、ICMPのSource Quenchメッセージの使用も規定していますが、このメッセージはその後非推奨になりました[RFC6633]。

The IPV6_V6ONLY function is a network-layer primitive that applies to all transport services, as defined in Section 5.3 of the basic socket interface for IPv6 [RFC3493]. This restricts the use of information from the name resolver to only allow communication of AF_INET6 sockets to use IPv6 only. This is not considered part of the transport service.

IPV6_V6ONLY関数は、IPv6の基本ソケットインターフェイス[RFC3493]のセクション5.3で定義されているように、すべてのトランスポートサービスに適用されるネットワーク層のプリミティブです。 これは、名前解決器からの情報の使用を制限し、AF_INET6ソケットの通信がIPv6のみを使用するようにします。 これはトランスポートサービスの一部とはみなされません。

3.2. Primitives Provided by UDP-Lite

3.2. UDP-Liteが提供するプリミティブ

UDP-Lite [RFC3828] provides similar services to UDP. It changed the semantics of the UDP "payload length" field to that of a "checksum coverage length" field. UDP-Lite requires the pseudo-header checksum to be computed at the sender and checked at a receiver. Apart from the length and coverage changes, UDP-Lite is semantically identical to UDP.

UDP-Lite[RFC3828]は、UDPと同様のサービスを提供します。 UDP-Liteは、UDPの「ペイロード長（payload length）」フィールドのセマンティクスを、「チェックサムカバレッジ長（checksum coverage length）」フィールドのセマンティクスに変更しました。 UDP-Liteでは、疑似ヘッダーのチェックサムを送信者で計算し、受信者で検査する必要があります。 長さとカバレッジの変更を除けば、UDP-LiteはセマンティクスとしてUDPと同一です。

The sending interface of UDP-Lite differs from that of UDP by the addition of a single (socket) option that communicates the checksum coverage length. This specifies the intended checksum coverage, with the remaining unprotected part of the payload called the "error-insensitive part".

UDP-Liteの送信インターフェイスは、チェックサムカバレッジ長を伝える（ソケット）オプションが1つ追加されている点でUDPのものと異なります。 このオプションは意図するチェックサムカバレッジを指定し、ペイロードのうち保護されない残りの部分は「エラー非感受部分（error-insensitive part）」と呼ばれます。

The receiving interface of UDP-Lite differs from that of UDP by the addition of a single (socket) option that specifies the minimum acceptable checksum coverage. The UDP-Lite Management Information Base (MIB) [RFC5097] further defines the checksum coverage method. Guidance on the use of services provided by UDP-Lite is provided in the UDP Guidelines [RFC8085].

UDP-Liteの受信インターフェイスは、許容できる最小のチェックサムカバレッジを指定する（ソケット）オプションが1つ追加されている点でUDPのものと異なります。 UDP-Liteの管理情報ベース（MIB）[RFC5097]は、チェックサムカバレッジの方法をさらに定義しています。 UDP-Liteが提供するサービスの使用に関するガイダンスは、UDPガイドライン[RFC8085]で提供されています。

UDP-Lite requires use of the UDP or UDP-Lite checksum; hence, it is not permitted to use the DISABLE_CHECKSUM function to disable use of a checksum, nor is it possible to disable receiver checksum processing using the REQUIRE_CHECKSUM function. All other primitives and functions for UDP are permitted.

UDP-Liteでは、UDPまたはUDP-Liteのチェックサムを使用する必要があります。 したがって、DISABLE_CHECKSUM関数を使用してチェックサムの使用を無効にすることは許可されておらず、REQUIRE_CHECKSUM関数を使用して受信者のチェックサム処理を無効にすることもできません。 UDPのその他のすべてのプリミティブと関数は許可されています。

In addition, the following are defined:

加えて、次のものが定義されています。

SET_CHECKSUM_COVERAGE:
The SET_CHECKSUM_COVERAGE primitive sets the coverage area for a sent datagram. UDP-Lite traffic uses this primitive to set the coverage length provided by the UDP checksum. Section 3.3 of the UDP-Lite specification [RFC3828] states that "Applications that wish to define the payload as partially insensitive to bit errors...should do this by an explicit system call on the sender side." The default is to provide the same coverage as for UDP.
SET_MIN_COVERAGE:
The SET_MIN_COVERAGE primitive sets the minimum acceptable coverage protection for received datagrams. UDP-Lite traffic uses this primitive to set the coverage length that is checked on receive. (Section 1.1 of [RFC5097] describes the corresponding MIB entry as udpliteEndpointMinCoverage.) Section 3.3 of the UDP-Lite specification [RFC3828] states that "Applications that wish to receive payloads that were only partially covered by a checksum should inform the receiving system by an explicit system call." The default is to require only minimal coverage of the datagram payload.
SET_CHECKSUM_COVERAGE:
SET_CHECKSUM_COVERAGEプリミティブは、送信するデータグラムのカバレッジ領域を設定します。 UDP-Liteのトラフィックは、このプリミティブを使用して、UDPチェックサムが提供するカバレッジ長を設定します。 UDP-Liteの仕様[RFC3828]のセクション3.3には、「ペイロードを部分的にビットエラーに対して非感受なものとして定義したいアプリケーションは……送信側で明示的なシステムコールによってこれを行うべきです」と書かれています。 デフォルトでは、UDPと同じカバレッジを提供します。
SET_MIN_COVERAGE:
SET_MIN_COVERAGEプリミティブは、受信したデータグラムに対して許容できる最小のカバレッジ保護を設定します。 UDP-Liteのトラフィックは、このプリミティブを使用して、受信時に検査されるカバレッジ長を設定します。 （[RFC5097]のセクション1.1は、対応するMIBエントリーをudpliteEndpointMinCoverageとして説明しています。） UDP-Liteの仕様[RFC3828]のセクション3.3には、「チェックサムで部分的にしかカバーされていないペイロードを受信したいアプリケーションは、明示的なシステムコールによって受信システムに通知すべきです」と書かれています。 デフォルトでは、データグラムのペイロードの最小限のカバレッジのみを要求します。

Appendix A. Multicast Primitives

付録A. マルチキャストのプリミティブ

This appendix describes primitives that are used when UDP and UDP-Lite support IPv4/IPv6 multicast. Multicast services are not considered by the IETF TAPS WG, but the currently specified primitives are included for completeness in this appendix. Guidance on the use of UDP and UDP-Lite for multicast services is provided in the UDP Guidelines [RFC8085].

この付録では、UDPとUDP-LiteがIPv4/IPv6マルチキャストをサポートする場合に使用されるプリミティブを説明します。 マルチキャストサービスはIETF TAPS WGでは検討されていませんが、現在規定されているプリミティブを網羅性のためにこの付録に含めています。 マルチキャストサービスでのUDPとUDP-Liteの使用に関するガイダンスは、UDPガイドライン[RFC8085]で提供されています。

IP multicast may be supported by using the Any Source Multicast (ASM) model or the Source-Specific Multicast (SSM) model. The latter requires use of a Multicast Source Filter (MSF) when specifying an IP multicast group destination address.

IPマルチキャストは、Any Source Multicast（ASM）モデルまたはSource-Specific Multicast（SSM）モデルを使用してサポートされる場合があります。 後者では、IPマルチキャストグループの宛先アドレスを指定する際に、マルチキャスト送信元フィルター（MSF）を使用する必要があります。

Use of multicast requires additional primitives at the transport API that need to be called to coordinate operation of the IPv4 and IPv6 network-layer protocols. For example, to receive datagrams sent to a group, an endpoint must first become a member of a multicast group at the network layer. Local multicast reception is signaled for IPv4 by the Internet Group Management Protocol (IGMP) [RFC3376] [RFC4604]. IPv6 uses the equivalent Multicast Listener Discovery (MLD) protocol [RFC3810] [RFC5790], carried over ICMPv6. A lightweight version of these protocols has also been specified [RFC5790].

マルチキャストを使用するには、IPv4とIPv6のネットワーク層プロトコルの動作を調整するために呼び出す必要がある、トランスポートAPIの追加のプリミティブが必要です。 たとえば、グループに送信されたデータグラムを受信するには、エンドポイントはまずネットワーク層でマルチキャストグループのメンバーになる必要があります。 IPv4では、ローカルでのマルチキャストの受信は、Internet Group Management Protocol（IGMP）[RFC3376] [RFC4604]によって通知されます。 IPv6では、ICMPv6上で運ばれる同等のMulticast Listener Discovery（MLD）プロトコル[RFC3810] [RFC5790]を使用します。 これらのプロトコルの軽量版も規定されています[RFC5790]。

The following are defined:

次のものが定義されています。

JoinHostGroup:
Section 7.1 of "Host Extensions for IP Multicasting" [RFC1112] provides a function that allows receiving traffic from an IP multicast group.
JoinLocalGroup:
Section 7.3 of "Host Extensions for IP Multicasting" [RFC1112] provides a function that allows receiving traffic from a local IP multicast group.
LeaveHostGroup:
Section 7.1 of "Host Extensions for IP Multicasting" [RFC1112] provides a function that allows leaving an IP multicast group.
LeaveLocalGroup:
Section 7.3 of "Host Extensions for IP Multicasting" [RFC1112] provides a function that allows leaving a local IP multicast group.
IPV6_MULTICAST_IF:
Section 5.2 of the basic socket extensions for IPv6 [RFC3493] states that this sets the interface that will be used for outgoing multicast packets.
IP_MULTICAST_TTL:
This sets the time-to-live field t to use for outgoing IPv4 multicast packets. This is used to limit the scope of multicast datagrams. Methods such as "The Generalized TTL Security Mechanism (GTSM)" [RFC5082] set this value to ensure link-local transmission. GTSM also requires the UDP receiver API to pass the received value of this field to the application.
IPV6_MULTICAST_HOPS:
Section 5.2 of the basic socket extensions for IPv6 [RFC3493] states that this sets the hop count to use for outgoing multicast IPv6 packets. (This is equivalent to IP_MULTICAST_TTL used for IPv4 multicast.)
IPV6_MULTICAST_LOOP:
Section 5.2 of the basic socket extensions for IPv6 [RFC3493] states that this sets whether a copy of a datagram is looped back by the IP layer for local delivery when the datagram is sent to a group to which the sending host itself belongs).
IPV6_JOIN_GROUP:
Section 5.2 of the basic socket extensions for IPv6 [RFC3493] provides a function that allows an endpoint to join an IPv6 multicast group.
SIOCGIPMSFILTER:
Section 8.1 of the socket interface for MSF [RFC3678] provides a function that allows reading the multicast source filters.
SIOCSIPMSFILTER:
Section 8.1 of the socket interface for MSF [RFC3678] provides a function that allows setting/modifying the multicast source filters.
IPV6_LEAVE_GROUP:
Section 5.2 of the basic socket extensions for IPv6 [RFC3493] provides a function that allows leaving an IPv6 multicast group.
JoinHostGroup:
「Host Extensions for IP Multicasting」[RFC1112]のセクション7.1は、IPマルチキャストグループからのトラフィックを受信できるようにする関数を提供しています。
JoinLocalGroup:
「Host Extensions for IP Multicasting」[RFC1112]のセクション7.3は、ローカルのIPマルチキャストグループからのトラフィックを受信できるようにする関数を提供しています。
LeaveHostGroup:
「Host Extensions for IP Multicasting」[RFC1112]のセクション7.1は、IPマルチキャストグループから離脱できるようにする関数を提供しています。
LeaveLocalGroup:
「Host Extensions for IP Multicasting」[RFC1112]のセクション7.3は、ローカルのIPマルチキャストグループから離脱できるようにする関数を提供しています。
IPV6_MULTICAST_IF:
IPv6の基本ソケット拡張[RFC3493]のセクション5.2によると、これは送信するマルチキャストパケットに使用するインターフェイスを設定します。
IP_MULTICAST_TTL:
これは、送信するIPv4マルチキャストパケットに使用するTime-to-Liveフィールドを設定します。 これは、マルチキャストデータグラムの範囲を制限するために使用されます。 「The Generalized TTL Security Mechanism (GTSM)」[RFC5082]などの方法では、リンクローカルな送信を保証するためにこの値を設定します。 GTSMでは、UDP受信者のAPIが、受信したこのフィールドの値をアプリケーションに渡すことも必要です。
IPV6_MULTICAST_HOPS:
IPv6の基本ソケット拡張[RFC3493]のセクション5.2によると、これは送信するIPv6マルチキャストパケットに使用するホップ数を設定します。 （これは、IPv4マルチキャストで使用されるIP_MULTICAST_TTLと同等です。）
IPV6_MULTICAST_LOOP:
IPv6の基本ソケット拡張[RFC3493]のセクション5.2によると、これは、送信ホスト自身が属しているグループにデータグラムが送信されたときに、ローカルへの配送のためにデータグラムのコピーをIP層でループバックするかどうかを設定します。
IPV6_JOIN_GROUP:
IPv6の基本ソケット拡張[RFC3493]のセクション5.2は、エンドポイントがIPv6マルチキャストグループに参加できるようにする関数を提供しています。
SIOCGIPMSFILTER:
MSFのためのソケットインターフェイス[RFC3678]のセクション8.1は、マルチキャスト送信元フィルターを読み取れるようにする関数を提供しています。
SIOCSIPMSFILTER:
MSFのためのソケットインターフェイス[RFC3678]のセクション8.1は、マルチキャスト送信元フィルターを設定または変更できるようにする関数を提供しています。
IPV6_LEAVE_GROUP:
IPv6の基本ソケット拡張[RFC3493]のセクション5.2は、IPv6マルチキャストグループから離脱できるようにする関数を提供しています。

The socket interface extensions for MSF [RFC3678] updates the multicast interface to add support for MSF for IPv4 and IPv6 required by IGMPv3. Section 3 defines both basic and advanced APIs, and Section 5 describes protocol-independent versions of these APIs. Four sets of API functionality are therefore defined:

MSFのためのソケットインターフェイス拡張[RFC3678]は、IGMPv3で必要となるIPv4とIPv6のMSFのサポートを追加するために、マルチキャストのインターフェイスを更新しています。 そのセクション3では基本APIと高度なAPIの両方を定義し、セクション5ではこれらのAPIのプロトコル非依存版を説明しています。 したがって、次の4組のAPI機能が定義されています。

  1. IPv4 Basic (Delta-based) API. "Each function call specifies a single source address which should be added to or removed from the existing filter for a given multicast group address on which to listen."
  2. IPv4 Advanced (Full-state) API. "This API allows an application to define a complete source-filter comprised of zero or more source addresses, and replace the previous filter with a new one."
  3. Protocol-Independent Basic MSF (Delta-based) API.
  4. Protocol-Independent Advanced MSF (Full-state) API.
  1. IPv4基本（差分ベース）API。 「各関数呼び出しは、待ち受ける特定のマルチキャストグループアドレスについて、既存のフィルターに追加または既存のフィルターから削除すべき単一の送信元アドレスを指定します。」
  2. IPv4高度（完全状態）API。 「このAPIにより、アプリケーションは、0個以上の送信元アドレスからなる完全な送信元フィルターを定義し、以前のフィルターを新しいもので置き換えることができます。」
  3. プロトコル非依存の基本MSF（差分ベース）API。
  4. プロトコル非依存の高度MSF（完全状態）API。

It specifies the following primitives:

これは次のプリミティブを規定しています。

IP_ADD_MEMBERSHIP:
This is used to join an ASM group.
IP_BLOCK_SOURCE:
This MSF can block data from a given multicast source to a given ASM or SSM group.
IP_UNBLOCK_SOURCE:
This updates an MSF to undo a previous call to IP_UNBLOCK_SOURCE for an ASM or SSM group.
IP_DROP_MEMBERSHIP:
This is used to leave an ASM or SSM group. (In SSM, this drops all sources that have been joined for a particular group and interface. The operations are the same as if the socket had been closed.)
IP_ADD_MEMBERSHIP:
これは、ASMグループに参加するために使用されます。
IP_BLOCK_SOURCE:
このMSFは、特定のマルチキャスト送信元から特定のASMグループまたはSSMグループへのデータをブロックできます。
IP_UNBLOCK_SOURCE:
これは、ASMグループまたはSSMグループについて、以前のIP_UNBLOCK_SOURCEの呼び出しを取り消すようにMSFを更新します。
IP_DROP_MEMBERSHIP:
これは、ASMグループまたはSSMグループから離脱するために使用されます。 （SSMでは、これは特定のグループとインターフェイスについて参加していたすべての送信元を取り除きます。 操作は、ソケットがクローズされた場合と同じです。）

Section 4.1.2 of the socket interface for MSF [RFC3678] updates the interface to add IPv4 MSF support to IGMPv3 using ASM:

MSFのためのソケットインターフェイス[RFC3678]のセクション4.1.2は、ASMを使用するIGMPv3にIPv4のMSFのサポートを追加するために、インターフェイスを更新しています。

IP_ADD_SOURCE_MEMBERSHIP:
This is used to join an SSM group.
IP_DROP_SOURCE_MEMBERSHIP:
This is used to leave an SSM group.
IP_ADD_SOURCE_MEMBERSHIP:
これは、SSMグループに参加するために使用されます。
IP_DROP_SOURCE_MEMBERSHIP:
これは、SSMグループから離脱するために使用されます。

Section 4.2 of the socket interface for MSF [RFC3678] defines the Advanced (Full-state) API:

MSFのためのソケットインターフェイス[RFC3678]のセクション4.2は、高度（完全状態）APIを定義しています。

setipv4sourcefilter:
This is used to join an IPv4 multicast group or to enable multicast from a specified source.
getipv4sourcefilter:
This is used to leave an IPv4 multicast group or to filter multicast from a specified source.
setipv4sourcefilter:
これは、IPv4マルチキャストグループに参加するため、または指定した送信元からのマルチキャストを有効にするために使用されます。
getipv4sourcefilter:
これは、IPv4マルチキャストグループから離脱するため、または指定した送信元からのマルチキャストをフィルタリングするために使用されます。

Section 5.1 of the socket interface for MSF [RFC3678] specifies Protocol-Independent Multicast API functions:

MSFのためのソケットインターフェイス[RFC3678]のセクション5.1は、プロトコル非依存のマルチキャストAPI関数を規定しています。

MCAST_JOIN_GROUP:
This is used to join an ASM group.
MCAST_JOIN_SOURCE_GROUP:
This is used to join an SSM group.
MCAST_BLOCK_SOURCE:
This is used to block a source in an ASM group.
MCAST_UNBLOCK_SOURCE:
This removes a previous MSF set by MCAST_BLOCK_SOURCE.
MCAST_LEAVE_GROUP:
This leaves an ASM or SSM group.
MCAST_LEAVE_SOURCE_GROUP:
This leaves an SSM group.
MCAST_JOIN_GROUP:
これは、ASMグループに参加するために使用されます。
MCAST_JOIN_SOURCE_GROUP:
これは、SSMグループに参加するために使用されます。
MCAST_BLOCK_SOURCE:
これは、ASMグループで送信元をブロックするために使用されます。
MCAST_UNBLOCK_SOURCE:
これは、MCAST_BLOCK_SOURCEによって以前に設定されたMSFを取り除きます。
MCAST_LEAVE_GROUP:
これは、ASMグループまたはSSMグループから離脱します。
MCAST_LEAVE_SOURCE_GROUP:
これは、SSMグループから離脱します。

Section 5.2 of the socket interface for MSF [RFC3678] specifies the Protocol-Independent Advanced MSF (Full-state) API applicable for both IPv4 and IPv6:

MSFのためのソケットインターフェイス[RFC3678]のセクション5.2は、IPv4とIPv6の両方に適用できる、プロトコル非依存の高度MSF（完全状態）APIを規定しています。

setsourcefilter:
This is used to join an IPv4 or IPv6 multicast group or to enable multicast from a specified source.
getsourcefilter:
This is used to leave an IPv4 or IPv6 multicast group or to filter multicast from a specified source.
setsourcefilter:
これは、IPv4またはIPv6のマルチキャストグループに参加するため、または指定した送信元からのマルチキャストを有効にするために使用されます。
getsourcefilter:
これは、IPv4またはIPv6のマルチキャストグループから離脱するため、または指定した送信元からのマルチキャストをフィルタリングするために使用されます。

The Lightweight IGMPv3 (LW_IGMPv3) and MLDv2 protocol [RFC5790] updates this interface (in Section 7.2 of RFC 5790).
