cite-as: A Link Relation to Convey a Preferred URI for Referencing

RFC 8574

cite-as: 参照に推奨されるURIを伝えるためのリンク関係

Abstract

概要

A web resource is routinely referenced by means of the URI with which it is directly accessed. But cases exist where referencing a resource by means of a different URI is preferred. This specification defines a link relation type that can be used to convey such a preference.

Webリソースは通常、そのリソースに直接アクセスする際のURIによって参照されます。 しかし、別のURIによってリソースを参照することが推奨される場合もあります。 この仕様は、そのような推奨を伝えるために使用できるリンク関係タイプを定義します。

1. Introduction

1. はじめに

A web resource is routinely referenced (e.g., linked or bookmarked) by means of the URI with which it is directly accessed. But cases exist where referencing a resource by means of a different URI is preferred, for example, because the latter URI is intended to be more persistent over time. Currently, there is no link relation type to convey such an alternative referencing preference; this specification addresses this deficit by introducing a link relation type intended for that purpose.

Webリソースは通常、そのリソースに直接アクセスする際のURIによって参照（たとえば、リンクやブックマーク）されます。 しかし、たとえば別のURIのほうが長期にわたって永続的であることを意図しているといった理由で、その別のURIによってリソースを参照することが推奨される場合もあります。 現在、このような代替の参照の推奨を伝えるためのリンク関係タイプはありません。 この仕様は、その目的のためのリンク関係タイプを導入することで、この不足に対処します。

2. Terminology

2. 用語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

This specification uses the terms "link context" and "link target" as defined in [RFC8288]. These terms correspond with "Context IRI" and "Target IRI", respectively, as used in [RFC5988]. Although defined as IRIs (Internationalized Resource Identifiers), they are also URIs in common scenarios.

この仕様は、[RFC8288]で定義されている「リンクコンテキスト（link context）」と「リンクターゲット（link target）」という用語を使用します。 これらの用語は、それぞれ[RFC5988]で使用されている「コンテキストIRI（Context IRI）」と「ターゲットIRI（Target IRI）」に対応します。 これらはIRI（国際化リソース識別子）として定義されていますが、一般的なシナリオではURIでもあります。

Additionally, this specification uses the following terms:

さらに、この仕様は次の用語を使用します。

  • "access URI": A URI at which a user agent accesses a web resource.
  • "reference URI": A URI, other than the access URI, that should preferentially be used for referencing.
  • 「アクセスURI（access URI）」: ユーザーエージェントがWebリソースにアクセスするURIです。
  • 「参照URI（reference URI）」: アクセスURI以外のURIで、参照に優先的に使用されるべきURIです。

By interacting with the access URI, the user agent may discover typed links. For such links, the access URI is the link context.

ユーザーエージェントは、アクセスURIとやり取りすることで、型付きリンクを発見する場合があります。 そのようなリンクでは、アクセスURIがリンクコンテキストです。

3. Scenarios

3. シナリオ

3.1. Persistent Identifiers

3.1. 永続識別子

Despite sound advice regarding the design of Cool URIs [CoolURIs], link rot ("HTTP 404 Not Found") is a common phenomena when following links on the Web. Certain communities of practice (see examples below) have introduced solutions to combat this problem. These solutions typically consist of:

Cool URIの設計に関する的確な助言[CoolURIs]があるにもかかわらず、Web上のリンクをたどる際のリンク切れ（「HTTP 404 Not Found」）はよくある現象です。 いくつかの実践コミュニティー（後述の例を参照）は、この問題に対処するための解決策を導入しています。 これらの解決策は、通常次の要素から成ります。

  • Accepting the reality that the web location of a resource -- the access URI -- may change over time.
  • Minting an additional URI for the resource -- the reference URI -- that is specifically intended to remain persistent over time.
  • Redirecting (typically with "HTTP 301 Moved Permanently", "HTTP 302 Found", or "HTTP 303 See Other") from the reference URI to the access URI.
  • Committing, as a community of practice, to adjust that redirection whenever the access URI changes over time.
  • リソースのWeb上の場所（アクセスURI）は、時間とともに変わりうるという現実を受け入れます。
  • 長期にわたって永続することを特に意図した、リソースの追加のURI（参照URI）を発行します。
  • 参照URIからアクセスURIへリダイレクトします（通常は「HTTP 301 Moved Permanently」、「HTTP 302 Found」、または「HTTP 303 See Other」を使用します）。
  • アクセスURIが時間とともに変わるたびにそのリダイレクトを調整することを、実践コミュニティーとして約束します。

This approach is, for example, used by:

このアプローチは、たとえば次のような主体によって使用されています。

  • Scholarly publishers that use DOIs (Digital Object Identifiers) [DOIs] to identify articles and DOI URLs [DOI-URLs] as a means to keep cross-publisher article-to-article links operational, even when the journals in which the articles are published change hands from one publisher to another, for example, as a result of an acquisition.
  • Authors of controlled vocabularies that use PURLs (Persistent Uniform Resource Locators) [PURLs] for vocabulary terms to ensure that the URIs they assign to vocabulary terms remain stable even if management of the vocabulary is transferred to a new custodian.
  • A variety of organizations (including libraries, archives, and museums) that assign ARK (Archival Resource Key) URLs [ARK] to information objects in order to support long-term access.
  • 学術出版社です。 学術出版社は、論文を識別するためにDOI（デジタルオブジェクト識別子）[DOIs]を使用し、DOI URL[DOI-URLs]を使用することで、たとえば買収の結果として論文が掲載されているジャーナルがある出版社から別の出版社へ移った場合でも、出版社をまたいだ論文間のリンクが機能し続けるようにしています。
  • 統制語彙の作成者です。 統制語彙の作成者は、語彙の管理が新しい管理者に移った場合でも語彙の用語に割り当てたURIが安定し続けるように、語彙の用語にPURL（永続的URL）[PURLs]を使用しています。
  • さまざまな組織（図書館、アーカイブ、博物館を含みます）です。 これらの組織は、長期的なアクセスをサポートするために、情報オブジェクトにARK（Archival Resource Key）URL[ARK]を割り当てています。

In order for the investments in infrastructure involved in these approaches to pay off, and hence for links to effectively remain operational as intended, it is crucial that a resource be referenced by means of its reference URI. However, the access URI is where a user agent actually accesses the resource (e.g., it is the URI in the browser's address bar). As such, there is a considerable risk that the access URI instead of the reference URI is used for referencing [PIDs-must-be-used].

これらのアプローチに関わるインフラストラクチャーへの投資が報われるためには、つまりリンクが意図どおりに実際に機能し続けるためには、リソースがその参照URIによって参照されることが不可欠です。 しかし、ユーザーエージェントが実際にリソースにアクセスするのはアクセスURIです（たとえば、ブラウザーのアドレスバーにあるURIです）。 そのため、参照URIの代わりにアクセスURIが参照に使用されてしまう大きなリスクがあります[PIDs-must-be-used]。

The link relation type defined in this document makes it possible for user agents to differentiate the reference URI from the access URI.

この文書で定義するリンク関係タイプにより、ユーザーエージェントは参照URIをアクセスURIと区別できるようになります。

3.2. Version Identifiers

3.2. バージョン識別子

Resource versioning systems often use a naming approach whereby:

リソースのバージョン管理システムは、多くの場合、次のような命名方式を使用します。

  • The most recent version of a resource is always available at the same, generic URI.
  • Each version of the resource -- including the most recent one -- has a distinct version URI.
  • リソースの最新バージョンは、常に同じ汎用URIで利用できます。
  • リソースの各バージョン（最新のものを含みます）は、それぞれ別個のバージョンURIを持ちます。

For example, Wikipedia uses generic URIs of the form <https://en.wikipedia.org/wiki/John_Doe> and version URIs of the form <https://en.wikipedia.org/w/index.php?title=John_Doe&oldid=776253882>.

たとえば、Wikipediaは汎用URIとして <https://en.wikipedia.org/wiki/John_Doe>という形式を使用し、バージョンURIとして <https://en.wikipedia.org/w/index.php?title=John_Doe&oldid=776253882>という形式を使用しています。

While the current version of a resource is accessed at the generic URI, some versioning systems adhere to a policy that favors linking and referencing a specific version URI. To express this using the terminology of Section 2, these policies intend that the generic URI is the access URI and that the version URI is the reference URI. These policies are informed by the understanding that the content at the generic URI is likely to evolve over time and that accurate links or references should lead to the content as it was at the time of referencing. To that end, Wikipedia's "Permanent link" and "Cite this page" functionalities promote the version URI, not the generic URI.

リソースの現在のバージョンには汎用URIでアクセスしますが、一部のバージョン管理システムは、特定のバージョンURIへのリンクと参照を優先するポリシーに従っています。 Section 2の用語を使ってこれを表現すると、これらのポリシーは、汎用URIをアクセスURIとし、バージョンURIを参照URIとすることを意図しています。 これらのポリシーは、汎用URIにあるコンテンツは時間とともに変化する可能性が高く、正確なリンクや参照は参照した時点のコンテンツにたどり着くべきだという理解にもとづいています。 そのため、Wikipediaの「Permanent link（この版への固定リンク）」と「Cite this page（このページを引用）」の機能は、汎用URIではなくバージョンURIを提示します。

The link relation type defined in this document makes it possible for user agents to differentiate the version URI from the generic URI.

この文書で定義するリンク関係タイプにより、ユーザーエージェントはバージョンURIを汎用URIと区別できるようになります。

3.3. Preferred Social Identifier

3.3. 推奨されるソーシャル識別子

A web user commonly has multiple profiles on the Web, for example, one per social network, a personal homepage, a professional homepage, a FOAF (Friend Of A Friend) profile [FOAF], etc. Each of these profiles is accessible at a distinct URI. But the user may have a preference for one of those profiles, for example, because it is most complete, kept up to date, or expected to be long lived. As an example, the first author of this document has, among others, the following profile URIs:

Webユーザーは一般に、Web上に複数のプロフィールを持っています。 たとえば、ソーシャルネットワークごとのプロフィール、個人のホームページ、仕事用のホームページ、FOAF（Friend Of A Friend）プロフィール[FOAF]などです。 これらのプロフィールは、それぞれ別個のURIでアクセスできます。 しかし、ユーザーは、たとえばもっとも充実している、最新の状態に保たれている、あるいは長く存続すると見込まれるといった理由で、それらのプロフィールのうちの1つを好む場合があります。 例として、この文書の筆頭著者は、とりわけ次のプロフィールURIを持っています。

  • <https://hvdsomp.info>
  • <https://twitter.com/hvdsomp>
  • <https://www.linkedin.com/in/herbertvandesompel/>
  • <https://orcid.org/0000-0002-0715-6126>
  • <https://hvdsomp.info>
  • <https://twitter.com/hvdsomp>
  • <https://www.linkedin.com/in/herbertvandesompel/>
  • <https://orcid.org/0000-0002-0715-6126>

Of these, from the perspective of the person described by these profiles, the first URI may be the preferred profile URI for the purpose of referencing because the domain is not under the custodianship of a third party. When an agent accesses another profile URI, such as <https://orcid.org/0000-0002-0715-6126>, this preference for referencing by means of the first URI could be expressed.

これらのうち、プロフィールに記述されている本人の観点からは、ドメインが第三者の管理下にないという理由で、最初のURIが参照のために推奨されるプロフィールURIとなる場合があります。 エージェントが<https://orcid.org/0000-0002-0715-6126>などのほかのプロフィールURIにアクセスしたときに、最初のURIによって参照してほしいというこの推奨を表現できます。

The link relation type defined in this specification makes it possible for user agents to differentiate the preferred profile URI from the accessed profile URI.

この仕様で定義するリンク関係タイプにより、ユーザーエージェントは推奨されるプロフィールURIを、アクセスしたプロフィールURIと区別できるようになります。

3.4. Multi-resource Publications

3.4. 複数のリソースからなる出版物

When publishing on the Web, it is not uncommon to make distinct components of a publication available as different web resources, each with their own URI. For example:

Web上で出版する際に、出版物の個々の構成要素を、それぞれ独自のURIを持つ異なるWebリソースとして公開することは珍しくありません。 たとえば、次のようなものがあります。

  • Contemporary scholarly publications routinely consists of a traditional article as well as additional materials that are considered an integral part of the publication such as supplementary information, high-resolution images, or a video recording of an experiment.
  • Scientific or governmental open data sets frequently consist of multiple files.
  • Online books typically consist of multiple chapters.
  • 現代の学術出版物は、通常、従来の論文に加えて、補足情報、高解像度の画像、実験を記録した動画など、出版物に不可欠な部分とみなされる追加資料から構成されます。
  • 科学や行政のオープンデータセットは、多くの場合、複数のファイルから構成されます。
  • オンラインの書籍は、通常、複数の章から構成されます。

While each of these components is accessible at its distinct URI -- the access URI -- they often also share a URI assigned to the intellectual publication of which they are components -- the reference URI.

これらの構成要素はそれぞれ別個のURI（アクセスURI）でアクセスできますが、多くの場合、それらが構成要素となっている知的出版物に割り当てられたURI（参照URI）も共有しています。

The link relation type defined in this document makes it possible for user agents to differentiate the URI of the intellectual publication from the access URI of a component of the publication.

この文書で定義するリンク関係タイプにより、ユーザーエージェントは知的出版物のURIを、その出版物の構成要素のアクセスURIと区別できるようになります。

4. The "cite-as" Link Relation Type for Expressing a Preferred URI for the Purpose of Referencing

4. 参照のために推奨されるURIを表現するための「cite-as」リンク関係タイプ

A link with the "cite-as" relation type indicates that, for referencing the link context, use of the URI of the link target is preferred over use of the URI of the link context. It allows the resource identified by the access URI (link context) to unambiguously link to its corresponding reference URI (link target), thereby expressing that the link target is preferred over the link context for the purpose of permanent citation.

「cite-as」関係タイプのリンクは、リンクコンテキストを参照する際に、リンクコンテキストのURIを使用するよりもリンクターゲットのURIを使用するほうが推奨されることを示します。 このリンクにより、アクセスURIで識別されるリソース（リンクコンテキスト）は、対応する参照URI（リンクターゲット）にあいまいさなくリンクでき、それによって恒久的な引用のためにはリンクコンテキストよりもリンクターゲットが推奨されることを表現できます。

The link target of a "cite-as" link SHOULD support protocol-based access as a means to ensure that applications that store them can effectively reuse them for access.

「cite-as」リンクのリンクターゲットは、それを保存するアプリケーションがアクセスのために効果的に再利用できるようにする手段として、プロトコルにもとづくアクセスをサポートすべきです（SHOULD）。

The link target of a "cite-as" link SHOULD provide the ability for a user agent to follow its nose back to the context of the link, e.g., by following redirects and/or links. This helps a user agent to establish trust in the target URI.

「cite-as」リンクのリンクターゲットは、たとえばリダイレクトやリンクをたどることによって、ユーザーエージェントがリンクのコンテキストまでたどって戻れるようにするべきです（SHOULD）。 これは、ユーザーエージェントがターゲットURIに対する信頼を確立するのに役立ちます。

Because a link with the "cite-as" relation type expresses a preferred URI for the purpose of referencing, the access URI SHOULD only provide one link with that relation type. If more than one "cite-as" link is provided, the user agent may decide to select one (e.g., an HTTP URI over a mailto URI) based on the purpose that the reference URI will serve.

「cite-as」関係タイプのリンクは参照のために推奨されるURIを表現するものなので、アクセスURIはその関係タイプのリンクを1つだけ提供すべきです（SHOULD）。 複数の「cite-as」リンクが提供されている場合、ユーザーエージェントは、参照URIを使う目的にもとづいて1つを選択する（たとえば、mailto URIよりもHTTP URIを選ぶ）ことを決めてもかまいません。

Providing a link with the "cite-as" relation type does not prevent using the access URI for the purpose of referencing if such specificity is needed for the application at hand. For example, in the case of the scenario in Section 3.4, the access URI is likely required for the purpose of annotating a specific component of an intellectual publication. Yet, the annotation application may also want to appropriately include the reference URI in the annotation.

「cite-as」関係タイプのリンクを提供しても、目下のアプリケーションでそのような特定性が必要な場合に、アクセスURIを参照のために使用することが妨げられるわけではありません。 たとえば、Section 3.4のシナリオの場合、知的出版物の特定の構成要素に注釈を付けるためには、おそらくアクセスURIが必要です。 それでも、注釈アプリケーションは、注釈に参照URIも適切に含めたい場合があります。

Applications can leverage the information provided by a "cite-as" link in a variety of ways, for example:

アプリケーションは、「cite-as」リンクによって提供される情報をさまざまな方法で活用できます。 たとえば、次のようなものがあります。

  • Bookmarking tools and citation managers can take this preference into account when recording a URI.
  • Webometrics applications that trace URIs can trace both the access URI and the reference URI.
  • Discovery tools can support lookup by means of both the access and the reference URI. This includes web archives that typically make archived versions of web resources discoverable by means of the original access URI of the archived resource; they can additionally make these archived resources discoverable by means of the associated reference URI.
  • ブックマークツールや文献管理ツールは、URIを記録する際にこの推奨を考慮できます。
  • URIを追跡するウェブメトリクスのアプリケーションは、アクセスURIと参照URIの両方を追跡できます。
  • 発見ツールは、アクセスURIと参照URIの両方による検索をサポートできます。 これにはWebアーカイブも含まれます。 Webアーカイブは通常、アーカイブされたリソースの元のアクセスURIによって、Webリソースのアーカイブされたバージョンを発見できるようにしていますが、さらに、関連する参照URIによってもこれらのアーカイブされたリソースを発見できるようにすることができます。

5. Distinction with Other Link Relation Types

5. ほかのリンク関係タイプとの違い

Some existing IANA-registered relationships intuitively resemble the relationship that "cite-as" is intended to convey. But a closer inspection of these candidates provided in the blog posts [identifier-blog], [canonical-blog], and [bookmark-blog] shows that they are not appropriate for various reasons and that a new link relation type is required. The remainder of this section provides a summary of the detailed explanations provided in the referenced blog posts.

IANAに登録されている既存の関係のいくつかは、直感的には「cite-as」が伝えようとしている関係に似ています。 しかし、ブログ記事[identifier-blog]、[canonical-blog]、[bookmark-blog]でこれらの候補を詳しく検討した結果、それらはさまざまな理由で適切ではなく、新しいリンク関係タイプが必要であることがわかりました。 このセクションの残りの部分では、参照したブログ記事に記載されている詳細な説明の要約を示します。

It can readily be seen that the following link relation types do not address the requirements described in Section 3:

次のリンク関係タイプがSection 3で説明した要件を満たさないことは、容易にわかります。

  • "alternate" [RFC4287]: The link target provides an alternate version of the content at the link context. These are typically variants according to dimensions that are subject to content negotiation, for example, the same content with varying Content-Type (e.g., application/pdf vs. text/html) and/or Content-Language (e.g., en vs. fr). The representations provided by the context URIs and target URIs in the scenarios in Sections 3.1 through 3.4 are not variants in the sense intended by [RFC4287], and, as such, the use of "alternate" is not appropriate.
  • "duplicate" [RFC6249]: The link target is a resource whose available representations are byte-for-byte identical with the corresponding representations of the link context, for example, an identical file on a mirror site. In none of the scenarios described in Sections 3.1 through 3.4 do the link context and the link target provide identical content. As such, the use of "duplicate" is not appropriate.
  • "related" [RFC4287]: The link target is a resource that is related to the link context. While "related" could be used in all of the scenarios described in Sections 3.1 through 3.4, its semantics are too vague to convey the specific semantics intended by "cite-as".
  • 「alternate」[RFC4287]: リンクターゲットは、リンクコンテキストにあるコンテンツの代替バージョンを提供します。 これらは通常、コンテンツネゴシエーションの対象となる次元にもとづく変種です。 たとえば、Content-Type（たとえば、application/pdfとtext/html）やContent-Language（たとえば、enとfr）が異なる同一のコンテンツです。 セクション3.1から3.4のシナリオにおいてコンテキストURIとターゲットURIが提供する表現は、[RFC4287]が意図する意味での変種ではありません。 そのため、「alternate」を使用することは適切ではありません。
  • 「duplicate」[RFC6249]: リンクターゲットは、利用可能な表現がリンクコンテキストの対応する表現とバイト単位で同一であるリソースです。 たとえば、ミラーサイト上の同一のファイルです。 セクション3.1から3.4で説明したシナリオのいずれにおいても、リンクコンテキストとリンクターゲットは同一のコンテンツを提供しません。 そのため、「duplicate」を使用することは適切ではありません。
  • 「related」[RFC4287]: リンクターゲットは、リンクコンテキストに関連するリソースです。 「related」はセクション3.1から3.4で説明したすべてのシナリオで使用できますが、その意味はあいまいすぎて、「cite-as」が意図する特定の意味を伝えることはできません。

Two existing IANA-registered relationships deserve closer attention and are discussed in the remainder of this section.

IANAに登録されている既存の関係のうち2つは、より詳しく検討する価値があるため、このセクションの残りの部分で説明します。

5.1. The "bookmark" Link Relation Type

5.1. 「bookmark」リンク関係タイプ

"bookmark" [W3C.REC-html52-20171214]: The link target provides a URI for the purpose of bookmarking the link context.

「bookmark」[W3C.REC-html52-20171214]: リンクターゲットは、リンクコンテキストをブックマークするためのURIを提供します。

The intent of "bookmark" is closest to that of "cite-as" in that the link target is intended to be a permalink for the link context, for bookmarking purposes. The link relation type dates back to the earliest days of news syndication, before blogs and news feeds had permalinks to identify individual resources that were aggregated into a single page. As such, its intent is to provide permalinks for different sections of an HTML document. It was originally used with HTML elements such as <div>, <h1>, <h2>, etc.; more recently, HTML5 revised it to be exclusively used with the <article> element. Moreover, it is explicitly excluded from use in the <link> element in HTML <head> and, as a consequence, in the HTTP Link header that is semantically equivalent. For these technical and semantic reasons, the use of "bookmark" to convey the relationship intended by "cite-as" is not appropriate.

「bookmark」の意図は、ブックマークの目的でリンクターゲットをリンクコンテキストのパーマリンクとすることを意図している点で、「cite-as」の意図にもっとも近いものです。 このリンク関係タイプの起源は、ブログやニュースフィードが、1つのページに集約された個々のリソースを識別するためのパーマリンクを持つようになる前の、ニュース配信のごく初期の時代にさかのぼります。 そのため、その意図はHTML文書のさまざまなセクションにパーマリンクを提供することです。 もともとは<div>、<h1>、<h2>などのHTML要素とともに使用されていましたが、より最近では、HTML5で<article>要素だけで使用するように改訂されました。 さらに、HTMLの<head>内の<link>要素での使用は明示的に除外されており、その結果、意味的に等価であるHTTP Linkヘッダーでも使用できません。 これらの技術的および意味的な理由から、「cite-as」が意図する関係を伝えるために「bookmark」を使用することは適切ではありません。

A more detailed justification regarding the inappropriateness of "bookmark", including a thorough overview of its turbulent history, is provided in [bookmark-blog].

「bookmark」が適切でないことについてのより詳細な根拠は、その波乱に満ちた歴史の詳しい概要とともに、[bookmark-blog]に記載されています。

5.2. The "canonical" Link Relation Type

5.2. 「canonical」リンク関係タイプ

"canonical" [RFC6596]: The meaning of "canonical" is commonly misunderstood on the basis of its brief definition as being "the preferred version of a resource." The description in the abstract of [RFC6596] is more helpful and states that "canonical" is intended to link to a resource that is preferred over resources with duplicative content. A more detailed reading of [RFC6596] clarifies that the intended meaning is that "canonical" is preferred for the purpose of content indexing. A typical use case is linking from each page in a multi-page magazine article to a single page version of the article provided for indexing by search engines: the former pages provide content that is duplicative to the superset content that is available at the latter page.

「canonical」[RFC6596]: 「canonical」の意味は、「リソースの推奨されるバージョン（the preferred version of a resource）」という簡潔な定義のせいで、よく誤解されています。 [RFC6596]のアブストラクトにある説明のほうが参考になり、「canonical」は、重複するコンテンツを持つリソースよりも推奨されるリソースへのリンクを意図していると述べています。 [RFC6596]をさらに詳しく読むと、意図されている意味は、コンテンツのインデックス作成の目的で「canonical」が推奨されるということだとわかります。 典型的なユースケースは、複数ページにわたる雑誌記事の各ページから、検索エンジンによるインデックス作成のために提供されるその記事の単一ページ版へリンクすることです。 前者の各ページは、後者のページで利用できるコンテンツ全体と重複するコンテンツを提供しています。

The semantics intended by "canonical" as preferred for the purpose of content indexing differ from the semantics intended by "cite-as" as preferred for the purpose of referencing. A further exploration of the various scenarios shows that the use of "canonical" is not appropriate to convey the semantics intended by "cite-as":

コンテンツのインデックス作成の目的で推奨されるという「canonical」の意図する意味は、参照の目的で推奨されるという「cite-as」の意図する意味とは異なります。 さまざまなシナリオをさらに検討すると、「cite-as」が意図する意味を伝えるために「canonical」を使用することは適切でないことがわかります。

  • Scenario of Section 3.1: The reference URI that is intended to be persistent over time does not serve content that needs to be indexed; it merely redirects to the access URI. Since the meaning intended by "canonical" is that it is preferred for the purpose of content indexing, it is not appropriate to point at the reference URI (persistent identifier) using the "canonical" link relation type. Moreover, Section 6.1 shows that scholarly publishers that assign persistent identifiers already use the "canonical" link relation type for search engine optimization; it also shows how that use contrasts with the intended use of "cite-as".
  • Scenario of Section 3.2: In most common cases, custodians of resource versioning systems want search engines to index the most recent version of a page and hence would use a "canonical" link to point from version URIs of a resource to the associated generic URI. Wikipedia effectively does this. However, for some resource versioning systems, including Wikipedia, version URIs are preferred for the purpose of referencing. As such, a "cite-as" link would point from the generic URI to the most recent version URI (that is, in the opposite direction of the "canonical" link).
  • Scenario of Section 3.3: The content at the link target and the link context are different profiles for a same person. Each profile, not just a preferred one, should be indexed. But a single one could be preferred for referencing.
  • Scenario of Section 3.4: The content at the link target, if any, would typically be a landing page that includes descriptive metadata pertaining to the multi-resource publication and links to its component resources. Each component resource provides content that is different, not duplicative, to the landing page.
  • Section 3.1のシナリオ: 長期にわたって永続することを意図した参照URIは、インデックスを作成する必要のあるコンテンツを提供せず、アクセスURIにリダイレクトするだけです。 「canonical」が意図する意味はコンテンツのインデックス作成の目的で推奨されるということなので、「canonical」リンク関係タイプを使用して参照URI（永続識別子）を指すことは適切ではありません。 さらに、Section 6.1では、永続識別子を割り当てる学術出版社がすでに検索エンジン最適化のために「canonical」リンク関係タイプを使用していることを示し、その使い方が「cite-as」の意図する使い方とどう対照的であるかも示します。
  • Section 3.2のシナリオ: もっとも一般的なケースでは、リソースのバージョン管理システムの管理者は、ページの最新バージョンを検索エンジンにインデックスさせたいと考えます。 そのため、リソースのバージョンURIから関連する汎用URIを指すために「canonical」リンクを使用するでしょう。 Wikipediaは実際にこれを行っています。 しかし、Wikipediaを含む一部のリソースのバージョン管理システムでは、参照の目的ではバージョンURIが推奨されます。 そのため、「cite-as」リンクは、汎用URIから最新のバージョンURIを指すことになります（つまり、「canonical」リンクとは逆方向です）。
  • Section 3.3のシナリオ: リンクターゲットとリンクコンテキストにあるコンテンツは、同じ人物の異なるプロフィールです。 推奨されるものだけでなく、各プロフィールのインデックスが作成されるべきです。 しかし、参照のためには、そのうちの1つだけが推奨される場合があります。
  • Section 3.4のシナリオ: リンクターゲットにあるコンテンツは、存在する場合、通常は、複数のリソースからなる出版物に関する記述メタデータと、その構成要素となるリソースへのリンクを含むランディングページです。 各構成要素のリソースは、ランディングページと重複するのではなく、異なるコンテンツを提供します。

A more detailed justification regarding how the use of "canonical" is inappropriate to address the requirements described in this document, including examples, is provided in [canonical-blog].

この文書で説明した要件に対処するために「canonical」を使用することがなぜ不適切であるかについてのより詳細な根拠は、例を含めて[canonical-blog]に記載されています。

6. Examples

6. 例

Sections 6.1 through 6.4 show examples of the use of links with the "cite-as" relation type. They illustrate how the typed links can be used in a response header and/or response body.

セクション6.1から6.4では、「cite-as」関係タイプのリンクの使用例を示します。 これらの例は、型付きリンクをレスポンスヘッダーやレスポンスボディーでどのように使用できるかを示しています。

6.1. Persistent HTTP URI

6.1. 永続的なHTTP URI

PLOS ONE is one of many scholarly publishers that assigns DOIs to the articles it publishes. For example, <https://doi.org/10.1371/journal.pone.0171057> is the persistent identifier for such an article. Via the DOI resolver, this persistent identifier redirects to <https://journals.plos.org/plosone/doi?id=10.1371/journal.pone.0171057> in the plos.org domain. This URI itself redirects to <https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0171057>, which delivers the actual article in HTML.

PLOS ONEは、出版する論文にDOIを割り当てている多くの学術出版社の1つです。 たとえば、<https://doi.org/10.1371/journal.pone.0171057>は、そのような論文の永続識別子です。 DOIリゾルバーを介して、この永続識別子はplos.orgドメインの<https://journals.plos.org/plosone/doi?id=10.1371/journal.pone.0171057>にリダイレクトします。 このURI自体は<https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0171057>にリダイレクトし、そこで実際の論文がHTMLで配信されます。

The HTML article contains a <link> element with the "canonical" link relation type pointing at itself, <https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0167475>. As per Section 5.2, this indicates that the article content at that URI should be indexed by search engines.

このHTMLの論文には、自身<https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0167475>を指す「canonical」リンク関係タイプの<link>要素が含まれています。 Section 5.2で述べたとおり、これは、そのURIにある論文のコンテンツが検索エンジンによってインデックスされるべきであることを示します。

PLOS ONE can additionally provide a link with the "cite-as" relation type pointing at the persistent identifier to indicate it is the preferred URI for permanent citation of the article. Figure 1 shows the addition of the "cite-as" link in both the HTTP header and the HTML that results from an HTTP GET on the article URI <https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0167475>.

PLOS ONEはさらに、永続識別子を指す「cite-as」関係タイプのリンクを提供して、それが論文を恒久的に引用するために推奨されるURIであることを示すことができます。 Figure 1は、論文のURI <https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0167475>に対するHTTP GETの結果として得られるHTTPヘッダーとHTMLの両方に「cite-as」リンクを追加した様子を示しています。

6.2. Version URIs

6.2. バージョンURI

The preprint server arXiv.org has a versioning approach like the one described in Section 3.2:

プレプリントサーバーのarXiv.orgは、Section 3.2で説明したようなバージョン管理の方式を採用しています。

  • The most recent version of a preprint is always available at the same, generic URI. Consider the preprint with generic URI <https://arxiv.org/abs/1711.03787>.
  • Each version of the preprint -- including the most recent one -- has a distinct version URI. The considered preprint has two versions with respective version URIs: <https://arxiv.org/abs/1711.03787v1> (published 10 November 2017) and <https://arxiv.org/abs/1711.03787v2> (published 24 January 2018).
  • プレプリントの最新バージョンは、常に同じ汎用URIで利用できます。 汎用URIが<https://arxiv.org/abs/1711.03787>であるプレプリントを考えます。
  • プレプリントの各バージョン（最新のものを含みます）は、それぞれ別個のバージョンURIを持ちます。 このプレプリントには2つのバージョンがあり、それぞれのバージョンURIは<https://arxiv.org/abs/1711.03787v1>（2017年11月10日公開）と<https://arxiv.org/abs/1711.03787v2>（2018年1月24日公開）です。

A reader who accessed <https://arxiv.org/abs/1711.03787> between 10 November 2017 and 23 January 2018, obtained the first version of the preprint. Starting 24 January 2018, the second version was served at that URI. In order to support accurate referencing, arXiv.org could implement the "cite-as" link to point from the generic URI to the most recent version URI. In doing so, assuming the existence of reference manager tools that consume "cite-as" links:

2017年11月10日から2018年1月23日までの間に<https://arxiv.org/abs/1711.03787>にアクセスした読者は、プレプリントの最初のバージョンを得ました。 2018年1月24日からは、そのURIで2番目のバージョンが提供されました。 正確な参照をサポートするために、arXiv.orgは、汎用URIから最新のバージョンURIを指す「cite-as」リンクを実装できます。 そうすることで、「cite-as」リンクを利用する文献管理ツールが存在すると仮定すると、次のようになります。

  • The reader who accesses <https://arxiv.org/abs/1711.03787> between 10 November 2017 and 23 January 2018 would reference <https://arxiv.org/abs/1711.03787v1>.
  • The reader who accesses <https://arxiv.org/abs/1711.03787> starting 24 January 2018 would reference <https://arxiv.org/abs/1711.03787v2>.
  • 2017年11月10日から2018年1月23日までの間に<https://arxiv.org/abs/1711.03787>にアクセスした読者は、<https://arxiv.org/abs/1711.03787v1>を参照することになります。
  • 2018年1月24日以降に<https://arxiv.org/abs/1711.03787>にアクセスした読者は、<https://arxiv.org/abs/1711.03787v2>を参照することになります。

Figure 2 shows the header that arXiv.org would have returned in the first case, in response to a HTTP HEAD on the generic URI <https://arxiv.org/abs/1711.03787>.

Figure 2は、最初のケースにおいて、汎用URI <https://arxiv.org/abs/1711.03787>に対するHTTP HEADへのレスポンスとしてarXiv.orgが返したであろうヘッダーを示しています。

6.3. Preferred Profile URI

6.3. 推奨されるプロフィールURI

If the access URI is the home page of John Doe, John can add a link with the "cite-as" relation type to it, in order to convey that he would prefer to be referenced by means of the URI of his FOAF profile. Figure 3 shows the response to an HTTP GET on the URI of John's home page.

アクセスURIがJohn Doeのホームページである場合、Johnは、自分のFOAFプロフィールのURIによって参照されることを望んでいると伝えるために、ホームページに「cite-as」関係タイプのリンクを追加できます。 Figure 3は、JohnのホームページのURIに対するHTTP GETへのレスポンスを示しています。

6.4. Multi-resource Publication

6.4. 複数のリソースからなる出版物の例

The Dryad Digital Repository at datadryad.org specializes in hosting and preserving scientific datasets. Each dataset typically consists of multiple resources. For example, the dataset "Data from: Climate, demography, and lek stability in an Amazonian bird" consists of an Excel spreadsheet, a csv file, and a zip file. Each of these resources have different content and are accessible at their respective URIs. In addition, the dataset has a landing page at <https://datadryad.org/resource/doi:10.5061/dryad.5d23f>.

datadryad.orgのDryad Digital Repositoryは、科学データセットのホスティングと保存を専門としています。 各データセットは、通常、複数のリソースから構成されます。 たとえば、「Data from: Climate, demography, and lek stability in an Amazonian bird」というデータセットは、Excelスプレッドシート、csvファイル、zipファイルから構成されます。 これらの各リソースは異なるコンテンツを持ち、それぞれのURIでアクセスできます。 さらに、このデータセットには<https://datadryad.org/resource/doi:10.5061/dryad.5d23f>にランディングページがあります。

Each of these resources should be permanently cited by means of the persistent identifier that was assigned to the entire dataset as an intellectual publication, i.e., <https://doi.org/10.5061/dryad.5d23f>. To that end, the Dryad Digital Repository can add "cite-as" links pointing from the URIs of each of these resources to <https://doi.org/10.5061/dryad.5d23f>. This is shown in Figure 4 for the csv file that is a component resource of the dataset, through use of the HTTP Link header.

これらの各リソースは、知的出版物としてのデータセット全体に割り当てられた永続識別子、すなわち<https://doi.org/10.5061/dryad.5d23f>によって恒久的に引用されるべきです。 そのために、Dryad Digital Repositoryは、これらの各リソースのURIから<https://doi.org/10.5061/dryad.5d23f>を指す「cite-as」リンクを追加できます。 Figure 4では、データセットの構成要素のリソースであるcsvファイルについて、HTTP Linkヘッダーを使用してこれを示しています。

8. Security Considerations

8. セキュリティーに関する考慮事項

In cases where there is no way for the agent to automatically verify the correctness of the reference URI (cf. Section 4), out-of-band mechanisms might be required to establish trust.

エージェントが参照URIの正しさを自動的に検証する方法がない場合（Section 4を参照）、信頼を確立するために帯域外のメカニズムが必要になる場合があります。

If a trusted site is compromised, the "cite-as" link relation could be used with malicious intent to supply misleading URIs for referencing. Use of these links might direct user agents to an attacker's site, break the referencing record they are intended to support, or corrupt algorithmic interpretation of referencing data.

信頼されたサイトが侵害された場合、「cite-as」リンク関係が悪意を持って使用され、参照のための誤解を招くURIが提供される可能性があります。 そのようなリンクを使用すると、ユーザーエージェントが攻撃者のサイトに誘導されたり、リンクがサポートするはずの参照の記録が壊れたり、参照データのアルゴリズムによる解釈が損なわれたりする可能性があります。
