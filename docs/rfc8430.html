RFC 8430

RIB Information Model

RFC 8430

RIB情報モデル

Abstract

概要

Routing and routing functions in enterprise and carrier networks are typically performed by network devices (routers and switches) using a Routing Information Base (RIB). Protocols and configurations push data into the RIB, and the RIB manager installs state into the hardware for packet forwarding. This document specifies an information model for the RIB to enable defining a standardized data model. The IETF's I2RS WG used this document to design the I2RS RIB data model. This document is being published to record the higher-level information model decisions for RIBs so that other developers of RIBs may benefit from the design concepts.

企業ネットワークやキャリアネットワークにおけるルーティングとルーティング機能は、通常、ネットワーク機器（ルーターやスイッチ）がルーティング情報ベース（Routing Information Base、RIB）を使用して実行します。プロトコルや設定がRIBにデータを投入し、RIBマネージャーがパケット転送のための状態をハードウェアにインストールします。この文書は、標準化されたデータモデルを定義できるようにするために、RIBの情報モデルを規定します。IETFのI2RS WGは、この文書を使用してI2RS RIBデータモデルを設計しました。この文書は、RIBの他の開発者が設計概念の恩恵を受けられるように、RIBに関する上位レベルの情報モデルの決定事項を記録するために公開されます。

1. Introduction

1. はじめに

Routing and routing functions in enterprise and carrier networks are traditionally performed in network devices. Customarily, routers run routing protocols, and the routing protocols (along with static configuration information) populate the Routing Information Base (RIB) of the router. The RIB is managed by the RIB manager, and the RIB manager provides a northbound interface to its clients (i.e., the routing protocols) to insert routes into the RIB. The RIB manager consults the RIB and decides how to program the Forwarding Information Base (FIB) of the hardware by interfacing with the FIB manager. The relationship between these entities is shown in Figure 1.

企業ネットワークやキャリアネットワークにおけるルーティングとルーティング機能は、従来、ネットワーク機器の中で実行されてきました。慣例として、ルーターはルーティングプロトコルを実行し、ルーティングプロトコルが（静的な設定情報とともに）ルーターのルーティング情報ベース（Routing Information Base、RIB）にデータを投入します。RIBはRIBマネージャーによって管理され、RIBマネージャーは、クライアント（つまり、ルーティングプロトコル）がRIBに経路を挿入するためのノースバウンドインターフェイスを提供します。RIBマネージャーはRIBを参照し、FIBマネージャーとやり取りすることによって、ハードウェアの転送情報ベース（Forwarding Information Base、FIB）をどのようにプログラムするかを決定します。これらのエンティティー間の関係を図1に示します。

Routing protocols are inherently distributed in nature, and each router makes an independent decision based on the routing data received from its peers. With the advent of newer deployment paradigms and the need for specialized applications, there is an emerging need to guide the router's routing function [RFC7920]. The traditional network-device RIB population that is protocol based suffices for most use cases where distributed network control is used. However, there are use cases that the network operators currently address by configuring static routes, policies, and RIB import/export rules on the routers. There is also a growing list of use cases in which a network operator might want to program the RIB based on data unrelated to just routing (within that network's domain). Programming the RIB could be based on other information (such as routing data in the adjacent domain or the load on storage and compute) in the given domain. Or, it could simply be a programmatic way of creating on-demand dynamic overlays (e.g., GRE tunnels) between compute hosts (without requiring the hosts to run traditional routing protocols). If there was a standardized, publicly documented programmatic interface to a RIB, it would enable further networking applications that address a variety of use cases [RFC7920].

ルーティングプロトコルは本質的に分散型であり、各ルーターはピアから受信したルーティングデータに基づいて独立して判断を下します。新しい展開パラダイムの登場と特殊なアプリケーションの必要性により、ルーターのルーティング機能を誘導する必要性が生じつつあります[RFC7920]。分散型のネットワーク制御を使用するほとんどのユースケースでは、従来のプロトコルベースによるネットワーク機器のRIBへのデータ投入で十分です。しかし、ネットワーク運用者が現在、ルーター上で静的経路、ポリシー、RIBのインポート／エクスポートルールを設定することで対処しているユースケースもあります。また、ネットワーク運用者が（そのネットワークのドメイン内の）ルーティングだけに関係しないデータに基づいてRIBをプログラムしたいと考えるユースケースも増えています。RIBのプログラミングは、そのドメインにおける他の情報（隣接ドメインのルーティングデータや、ストレージと計算の負荷など）に基づく場合があります。あるいは、単に、（ホストが従来のルーティングプロトコルを実行することを必要とせずに）計算ホスト間にオンデマンドの動的なオーバーレイ（たとえば、GREトンネル）を作成するためのプログラム的な方法である場合もあります。標準化され、公開文書化された、RIBへのプログラム的なインターフェイスがあれば、さまざまなユースケースに対応するさらなるネットワーキングアプリケーションが可能になるでしょう[RFC7920]。

A programmatic interface to the RIB involves two types of operations: reading from the RIB and writing (adding/modifying/deleting) to the RIB.

RIBへのプログラム的なインターフェイスには、RIBからの読み取りとRIBへの書き込み（追加／変更／削除）という2種類の操作があります。

In order to understand what is in a router's RIB, methods like per-protocol SNMP MIBs and screen scraping are used. These methods are not scalable since they are client pull mechanisms and not proactive push (from the router) mechanisms. Screen scraping is error prone (since the output format can change) and is vendor dependent. Building a RIB from per-protocol MIBs is error prone since the MIB data represents protocol data and not the exact information that went into the RIB. Thus, just getting read-only RIB information from a router is a hard task.

ルーターのRIBに何が含まれているかを把握するために、プロトコルごとのSNMP MIBやスクリーンスクレイピングといった方法が使用されています。これらの方法は、（ルーターからの）プロアクティブなプッシュ型のメカニズムではなく、クライアントによるプル型のメカニズムであるため、スケーラブルではありません。スクリーンスクレイピングは（出力形式が変わる可能性があるため）エラーが発生しやすく、ベンダーに依存します。プロトコルごとのMIBからRIBを構築することは、MIBのデータがRIBに入った正確な情報ではなくプロトコルのデータを表すため、エラーが発生しやすくなります。したがって、ルーターから読み取り専用のRIB情報を取得するだけでも難しい作業です。

Adding content to the RIB from a RIB client can be done today using static configuration mechanisms provided by router vendors. However, the mix of what can be modified in the RIB varies from vendor to vendor, and the method of configuring it is also vendor dependent. This makes it hard for a RIB client to program a multi-vendor network in a consistent and vendor-independent way.

現在、RIBクライアントからRIBにコンテンツを追加するには、ルーターベンダーが提供する静的な設定メカニズムを使用できます。しかし、RIBで何を変更できるかはベンダーごとに異なり、その設定方法もベンダーに依存します。このため、RIBクライアントがマルチベンダーのネットワークを一貫した、ベンダーに依存しない方法でプログラムすることは困難です。

The purpose of this document is to specify an information model for the RIB. Using the information model, one can build a detailed data model for the RIB. That data model could then be used by a RIB client to program a network device. One data model that has been based on this document is the I2RS RIB data model [RFC8431].

この文書の目的は、RIBの情報モデルを規定することです。この情報モデルを使用して、RIBの詳細なデータモデルを構築できます。そのデータモデルは、RIBクライアントがネットワーク機器をプログラムするために使用できます。この文書に基づいたデータモデルの1つに、I2RS RIBデータモデル[RFC8431]があります。

The rest of this document is organized as follows. Section 2 goes into the details of what constitutes and can be programmed in a RIB. Guidelines for reading and writing the RIB are provided in Sections 3 and 4, respectively. Section 5 provides a high-level view of the events and notifications going from a network device to a RIB client to update the RIB client on asynchronous events. The RIB grammar is specified in Section 6. Examples of using the RIB grammar are shown in Section 7. Section 8 covers considerations for performing RIB operations at scale.

この文書の残りの部分は次のように構成されています。セクション2では、RIBを構成するものと、RIBでプログラムできるものの詳細について説明します。RIBの読み取りと書き込みに関するガイドラインは、それぞれセクション3と4で示します。セクション5では、非同期イベントについてRIBクライアントに知らせるために、ネットワーク機器からRIBクライアントに送られるイベントと通知の概要を示します。RIB文法はセクション6で規定します。RIB文法の使用例はセクション7で示します。セクション8では、RIB操作を大規模に実行するための考慮事項を扱います。

Please note that for ease of representation in ASCII art, this drawing shows a single routing instance, a single RIB, and a single route. このセクションでは、RIBの詳細について説明します。このセクションでは、後で定義するRIB文法のオブジェクトを参照します（セクション6を参照）。RIBの内容の概要を図2に示します。ASCIIアートで表現しやすくするために、この図では単一のルーティングインスタンス、単一のRIB、単一の経路だけを示していることに注意してください。このセクションのサブセクションでは、RIBに含まれるべき論理的なデータノードについて説明します。セクション3と4では、読み取りと書き込みの操作の概要を説明します。

2.1. RIB Definition

2.1. RIBの定義

A RIB, in the context of the RIB information model, is an entity that contains routes. It is identified by its name and is contained within a routing instance (see Section 2.2). A network device MAY contain routing instances, and each routing instance MAY contain RIBs. The name MUST be unique within a routing instance. All routes in a given RIB MUST be of the same address family (e.g., IPv4). Each RIB MUST belong to a routing instance.

RIB情報モデルの文脈におけるRIBとは、経路を含むエンティティーです。RIBは名前によって識別され、ルーティングインスタンスの中に含まれます（セクション2.2を参照）。ネットワーク機器はルーティングインスタンスを含んでもよいです（MAY）。また、各ルーティングインスタンスはRIBを含んでもよいです（MAY）。名前はルーティングインスタンス内で一意でなければなりません（MUST）。あるRIB内のすべての経路は、同じアドレスファミリー（たとえば、IPv4）でなければなりません（MUST）。各RIBは、いずれかのルーティングインスタンスに属さなければなりません（MUST）。

A routing instance may contain two or more RIBs of the same address family (e.g., IPv6). A typical case where this can be used is for multi-topology routing [RFC4915] [RFC5120].

ルーティングインスタンスは、同じアドレスファミリー（たとえば、IPv6）のRIBを2つ以上含む場合があります。これが使用される典型的なケースは、マルチトポロジールーティング[RFC4915] [RFC5120]です。

Each RIB MAY be associated with an ENABLE_IP_RPF_CHECK attribute that enables Reverse Path Forwarding (RPF) checks on all IP routes in that RIB. The RPF check is used to prevent spoofing and limit malicious traffic. For IP packets, the IP source address is looked up and the RPF interface(s) associated with the route for that IP source address is found. If the incoming IP packet's interface matches one of the RPF interfaces, then the IP packet is forwarded based on its IP destination address; otherwise, the IP packet is discarded.

各RIBには、そのRIB内のすべてのIP経路に対してリバースパス転送（Reverse Path Forwarding、RPF）チェックを有効にするENABLE_IP_RPF_CHECK属性を関連付けてもよいです（MAY）。RPFチェックは、なりすましを防止し、悪意のあるトラフィックを制限するために使用されます。IPパケットの場合、IP送信元アドレスを検索し、そのIP送信元アドレスに対する経路に関連付けられたRPFインターフェイスを見つけます。受信したIPパケットのインターフェイスがRPFインターフェイスのいずれかと一致する場合、IPパケットはそのIP宛先アドレスに基づいて転送されます。そうでない場合、IPパケットは破棄されます。

2.2. Routing Instance

2.2. ルーティングインスタンス

A routing instance, in the context of the RIB information model, is a collection of RIBs, interfaces, and routing parameters. A routing instance creates a logical slice of the router. It allows different logical slices across a set of routers to communicate with each other. Layer 3 VPNs, Layer 2 VPNs (L2VPNs), and Virtual Private LAN Service (VPLS) can be modeled as routing instances. Note that modeling an L2VPN using a routing instance only models the Layer 3 (RIB) aspect and does not model any Layer 2 information (like ARP) that might be associated with the L2VPN.

RIB情報モデルの文脈におけるルーティングインスタンスとは、RIB、インターフェイス、ルーティングパラメーターの集合です。ルーティングインスタンスは、ルーターの論理的なスライスを作成します。これにより、ルーターの集合にまたがる異なる論理スライスが互いに通信できるようになります。レイヤー3 VPN、レイヤー2 VPN（L2VPN）、仮想プライベートLANサービス（Virtual Private LAN Service、VPLS）は、ルーティングインスタンスとしてモデル化できます。ルーティングインスタンスを使用してL2VPNをモデル化する場合、レイヤー3（RIB）の側面だけをモデル化し、L2VPNに関連付けられている可能性のあるレイヤー2の情報（ARPなど）はモデル化しないことに注意してください。

The set of interfaces indicates which interfaces are associated with this routing instance. The RIBs specify how incoming traffic is to be forwarded, and the routing parameters control the information in the RIBs. The intersection set of interfaces of two routing instances MUST be the null set. In other words, an interface MUST NOT be present in two routing instances. Thus, a routing instance describes the routing information and parameters across a set of interfaces.

インターフェイスの集合は、どのインターフェイスがこのルーティングインスタンスに関連付けられているかを示します。RIBは受信トラフィックをどのように転送するかを規定し、ルーティングパラメーターはRIB内の情報を制御します。2つのルーティングインスタンスのインターフェイスの共通集合は、空集合でなければなりません（MUST）。言い換えれば、1つのインターフェイスが2つのルーティングインスタンスに存在してはなりません（MUST NOT）。したがって、ルーティングインスタンスは、インターフェイスの集合にわたるルーティング情報とパラメーターを記述します。

A routing instance MUST contain the following mandatory fields:

ルーティングインスタンスは、次の必須フィールドを含まなければなりません（MUST）。

  • INSTANCE_NAME: A routing instance is identified by its name, INSTANCE_NAME. This MUST be unique across all routing instances in a given network device.
  • rib-list: This is the list of RIBs associated with this routing instance. Each routing instance can have multiple RIBs to represent routes of different types. For example, one would put IPv4 routes in one RIB and MPLS routes in another RIB. The list of RIBs can be an empty list.
  • INSTANCE_NAME：ルーティングインスタンスは、その名前であるINSTANCE_NAMEによって識別されます。これは、あるネットワーク機器内のすべてのルーティングインスタンスにわたって一意でなければなりません（MUST）。
  • rib-list：このルーティングインスタンスに関連付けられたRIBのリストです。各ルーティングインスタンスは、異なる種類の経路を表すために複数のRIBを持つことができます。たとえば、IPv4経路をあるRIBに入れ、MPLS経路を別のRIBに入れることが考えられます。RIBのリストは空のリストでもかまいません。

A routing instance MAY contain the following fields:

ルーティングインスタンスは、次のフィールドを含んでもよいです（MAY）。

  • interface-list: This represents the list of interfaces associated with this routing instance. The interface list helps constrain the boundaries of packet forwarding. Packets coming in on these interfaces are directly associated with the given routing instance. The interface list contains a list of identifiers, with each identifier uniquely identifying an interface.
  • ROUTER_ID: This field identifies the network device in control plane interactions with other network devices. This field is to be used if one wants to virtualize a physical router into multiple virtual routers. Each virtual router MUST have a unique ROUTER_ID. A ROUTER_ID MUST be unique across all network devices in a given domain.
  • interface-list：このルーティングインスタンスに関連付けられたインターフェイスのリストを表します。インターフェイスリストは、パケット転送の境界を制約するのに役立ちます。これらのインターフェイスで受信したパケットは、そのルーティングインスタンスに直接関連付けられます。インターフェイスリストは識別子のリストを含み、各識別子は1つのインターフェイスを一意に識別します。
  • ROUTER_ID：このフィールドは、他のネットワーク機器とのコントロールプレーンのやり取りにおいてネットワーク機器を識別します。このフィールドは、物理ルーターを複数の仮想ルーターに仮想化したい場合に使用します。各仮想ルーターは一意のROUTER_IDを持たなければなりません（MUST）。ROUTER_IDは、あるドメイン内のすべてのネットワーク機器にわたって一意でなければなりません（MUST）。

A routing instance may be created purely for the purposes of packet processing and may not have any interfaces associated with it. For example, an incoming packet in routing instance A might have a nexthop of routing instance B, and after packet processing in B, the nexthop might be routing instance C. Thus, routing instance B is not associated with any interface. And, given that this routing instance does not do any control-plane interaction with other network devices, a ROUTER_ID is also not needed.

ルーティングインスタンスは、純粋にパケット処理の目的で作成される場合があり、関連付けられたインターフェイスを持たないこともあります。たとえば、ルーティングインスタンスAで受信したパケットのネクストホップがルーティングインスタンスBであり、Bでのパケット処理の後、ネクストホップがルーティングインスタンスCであることが考えられます。この場合、ルーティングインスタンスBはどのインターフェイスにも関連付けられていません。また、このルーティングインスタンスは他のネットワーク機器とのコントロールプレーンのやり取りを一切行わないため、ROUTER_IDも必要ありません。

2.3. Route

2.3. 経路

A route is essentially a match condition and an action following the match. The match condition specifies the kind of route (IPv4, MPLS, etc.) and the set of fields to match on. Figure 3 represents the overall contents of a route. Please note that for ease of depiction in ASCII art, only a single instance of the route-attribute, match flags, and nexthop is depicted.

経路とは、本質的には、一致条件と、一致した後のアクションです。一致条件は、経路の種類（IPv4、MPLSなど）と、一致させるフィールドの集合を規定します。図3は経路の全体的な内容を表します。ASCIIアートで描きやすくするために、route-attribute、一致フラグ、ネクストホップをそれぞれ1つだけ描いていることに注意してください。

This document specifies the following match types:

この文書では、次の一致タイプを規定します。

  • IPv4: Match on destination and/or source IP address in the IPv4 header
  • IPv6: Match on destination and/or source IP address in the IPv6 header
  • MPLS: Match on an MPLS label at the top of the MPLS label stack
  • MAC: Match on Media Access Control (MAC) destination addresses in the Ethernet header
  • Interface: Match on the incoming interface of the packet
  • IPv4：IPv4ヘッダー内の宛先IPアドレスと送信元IPアドレスの一方または両方で一致させます
  • IPv6：IPv6ヘッダー内の宛先IPアドレスと送信元IPアドレスの一方または両方で一致させます
  • MPLS：MPLSラベルスタックの最上位にあるMPLSラベルで一致させます
  • MAC：イーサネットヘッダー内のメディアアクセス制御（Media Access Control、MAC）宛先アドレスで一致させます
  • Interface：パケットの受信インターフェイスで一致させます

A route MAY be matched on one or more of these match types by policy as either an "AND" (to restrict the number of routes) or an "OR" (to combine two filters).

経路は、ポリシーによって、これらの一致タイプの1つ以上に対して、「AND」（経路の数を制限する場合）または「OR」（2つのフィルターを組み合わせる場合）のいずれかで一致させてもよいです（MAY）。

Each route MUST have the following mandatory route-attributes associated with it:

各経路には、次の必須のroute-attributeを関連付けなければなりません（MUST）。

  • ROUTE_PREFERENCE: This is a numerical value that allows for comparing routes from different protocols. Static configuration is also considered a protocol for the purpose of this field. It is also known as "administrative distance". The lower the value, the higher the preference. For example, there can be an OSPF route for 192.0.2.1/32 (or IPv6 2001:DB8::1/128) with a preference of 5. If a controller programs a route for 192.0.2.1/32 (or IPv6 2001:DB8::1/128) with a preference of 2, then the controller's route will be preferred by the RIB manager. Preference should be used to dictate behavior. For more examples of preference, see Section 7.1.
  • ROUTE_PREFERENCE：異なるプロトコルからの経路を比較できるようにする数値です。このフィールドの目的においては、静的な設定もプロトコルの1つとみなします。これは「アドミニストレーティブディスタンス（administrative distance）」としても知られています。値が小さいほど、優先度は高くなります。たとえば、192.0.2.1/32（またはIPv6の2001:DB8::1/128）に対する優先度5のOSPF経路があるとします。コントローラーが192.0.2.1/32（またはIPv6の2001:DB8::1/128）に対する経路を優先度2でプログラムした場合、RIBマネージャーはコントローラーの経路を優先します。優先度は動作を決定するために使用すべきです。優先度の他の例については、セクション7.1を参照してください。

Each route can have one or more optional route-attributes associated with it.

各経路には、選択可能なroute-attributeを1つ以上関連付けることができます。

  • route-vendor-attributes: Vendors can specify vendor-specific attributes using this. The details of this attribute are outside the scope of this document.
  • route-vendor-attributes：ベンダーは、これを使用してベンダー固有の属性を指定できます。この属性の詳細は、この文書の範囲外です。

Each route has a nexthop associated with it. Nexthops are described in Section 2.4.

各経路には、ネクストホップが関連付けられています。ネクストホップについてはセクション2.4で説明します。

Additional features to match multicast packets were considered (e.g., TTL of the packet to limit the range of a multicast group), but these were not added to this information model. Future RIB information models should investigate these multicast features.

マルチキャストパケットを一致させるための追加機能（たとえば、マルチキャストグループの範囲を制限するためのパケットのTTL）も検討されましたが、この情報モデルには追加されませんでした。将来のRIB情報モデルでは、これらのマルチキャスト機能を検討すべきです。

2.4. Nexthop

2.4. ネクストホップ

A nexthop represents an object resulting from a route lookup. For example, if a route lookup results in sending the packet out of a given interface, then the nexthop represents that interface.

ネクストホップは、経路検索の結果として得られるオブジェクトを表します。たとえば、経路検索の結果、あるインターフェイスからパケットを送出することになる場合、ネクストホップはそのインターフェイスを表します。

Nexthops can be either fully resolved or unresolved. A resolved nexthop has adequate information to send the outgoing packet to the destination by forwarding it on an interface to a directly connected neighbor. For example, a nexthop to a point-to-point interface or a nexthop to an IP address on an Ethernet interface has the nexthop resolved. An unresolved nexthop is something that requires the RIB manager to determine the final resolved nexthop. For example, a nexthop could be an IP address. The RIB manager would resolve how to reach that IP address; for example, is the IP address reachable by regular IP forwarding, by an MPLS tunnel, or by both? If the RIB manager cannot resolve the nexthop, then the nexthop remains in an unresolved state and is NOT a candidate for installation in the FIB. Future RIB events can cause an unresolved nexthop to get resolved (e.g., an IP address being advertised by an IGP neighbor). Conversely, resolved nexthops can also become unresolved (e.g., in the case of a tunnel going down); hence, they would no longer be candidates to be installed in the FIB.

ネクストホップは、完全に解決済みか未解決のいずれかです。解決済みのネクストホップは、直接接続された隣接ノードへのインターフェイス上で送信パケットを転送することにより、そのパケットを宛先に送るのに十分な情報を持っています。たとえば、ポイントツーポイントインターフェイスへのネクストホップや、イーサネットインターフェイス上のIPアドレスへのネクストホップは、ネクストホップが解決済みです。未解決のネクストホップとは、RIBマネージャーが最終的な解決済みのネクストホップを決定する必要があるものです。たとえば、ネクストホップがIPアドレスである場合があります。RIBマネージャーは、そのIPアドレスへの到達方法を解決します。たとえば、そのIPアドレスに到達できるのは、通常のIP転送によるのか、MPLSトンネルによるのか、あるいはその両方によるのかを解決します。RIBマネージャーがネクストホップを解決できない場合、そのネクストホップは未解決の状態のままとなり、FIBへのインストールの候補にはなりません。将来のRIBイベントによって、未解決のネクストホップが解決される場合があります（たとえば、IPアドレスがIGPの隣接ノードによって広告された場合）。逆に、解決済みのネクストホップが未解決になる場合もあります（たとえば、トンネルがダウンした場合）。その場合、それらはもはやFIBにインストールされる候補ではなくなります。

When at least one of a route's nexthops is resolved, then the route can be used to forward packets. Such a route is considered eligible to be installed in the FIB and is henceforth referred to as a FIB-eligible route. Conversely, when all the nexthops of a route are unresolved, that route can no longer be used to forward packets. Such a route is considered ineligible to be installed in the FIB and is henceforth referred to as a FIB-ineligible route. The RIB information model allows a RIB client to program routes whose nexthops may be unresolved initially. Whenever an unresolved nexthop gets resolved, the RIB manager will send a notification of the same (see Section 5).

経路のネクストホップのうち少なくとも1つが解決済みである場合、その経路はパケットの転送に使用できます。このような経路はFIBへのインストールに適格であるとみなされ、以降、FIB適格経路（FIB-eligible route）と呼びます。逆に、経路のすべてのネクストホップが未解決である場合、その経路はもはやパケットの転送に使用できません。このような経路はFIBへのインストールに不適格であるとみなされ、以降、FIB不適格経路（FIB-ineligible route）と呼びます。RIB情報モデルでは、RIBクライアントは、ネクストホップが最初は未解決である可能性のある経路をプログラムできます。未解決のネクストホップが解決されるたびに、RIBマネージャーはその旨の通知を送信します（セクション5を参照）。

The overall structure and usage of a nexthop is as shown in the figure below. For ease of description using ASCII art, only a single instance of any component of the nexthop is shown in Figure 4.

ネクストホップの全体的な構造と使い方を下の図に示します。ASCIIアートで説明しやすくするために、図4ではネクストホップの各構成要素を1つずつしか示していません。

This document specifies a very generic, extensible, and recursive grammar for nexthops. A nexthop can be a base nexthop or a derived nexthop. Section 2.4.1 details base nexthops, and Section 2.4.2 explains various kinds of derived nexthops. There are certain special nexthops, and those are described in Section 2.4.1.1. Lastly, Section 2.4.3 delves into nexthop indirection and its use. Examples of when and how to use tunnel nexthops and derived nexthops are shown in Section 7.2.

この文書では、ネクストホップのための、非常に汎用的で拡張可能かつ再帰的な文法を規定します。ネクストホップは、基本ネクストホップか派生ネクストホップのいずれかです。セクション2.4.1では基本ネクストホップについて詳しく説明し、セクション2.4.2ではさまざまな種類の派生ネクストホップについて説明します。いくつかの特殊なネクストホップがあり、それらについてはセクション2.4.1.1で説明します。最後に、セクション2.4.3では、ネクストホップの間接参照とその使用法について掘り下げます。トンネルネクストホップと派生ネクストホップをいつ、どのように使用するかの例は、セクション7.2で示します。

2.4.1. Base Nexthops

2.4.1. 基本ネクストホップ

At the lowest level, a nexthop can be one of the following:

最も低いレベルでは、ネクストホップは次のいずれかです。

  • Identifier: This is an identifier returned by the network device representing a nexthop. This can be used as a way of reusing a nexthop when programming derived nexthops.

  • Interface nexthops: These are nexthops that are pointing to an interface. Various attributes associated with these nexthops are:

    • Egress-interface: This represents a physical, logical, or virtual interface on the network device. Address resolution must not be required on this interface. This interface may belong to any routing instance.

    • IP address: A route lookup on this IP address is done to determine the egress-interface. Address resolution may be required depending on the interface.

      • An optional rib-name can also be specified to indicate the RIB in which the IP address is to be looked up. One can use the rib-name field to direct the packet from one domain into another domain. By default the RIB will be the same as the one that route belongs to.

    These attributes can be used in combination as follows:

    • Egress-interface and IP address: This can be used in cases where, e.g., the IP address is a link-local address.
    • Egress-interface and MAC address: The egress-interface must be an Ethernet interface. Address resolution is not required for this nexthop.

  • Tunnel nexthops: These are nexthops that are pointing to a tunnel. The types of tunnel nexthops are:

    • tunnel-encapsulation: This can be an encapsulation representing an IP tunnel, MPLS tunnel, or others as defined in this document. An optional egress-interface can be chained to the tunnel-encapsulation to indicate which interface to send the packet out on. The egress-interface is useful when the network device contains Ethernet interfaces and one needs to perform address resolution for the IP packet.
    • tunnel-decapsulation: This is to specify decapsulating a tunnel header. After decapsulation, further lookup on the packet can be done via chaining it with another nexthop. The packet can also be sent out via an egress-interface directly.
    • logical-tunnel: This can be an MPLS Label Switched Path (LSP) or a GRE tunnel (or others as defined in this document) that is represented by a unique identifier (e.g., name).
  • rib-name: A nexthop pointing to a RIB. This indicates that the route lookup needs to continue in the specified RIB. This is a way to perform chained lookups.
  • 識別子（Identifier）：ネクストホップを表す、ネットワーク機器から返される識別子です。これは、派生ネクストホップをプログラムする際にネクストホップを再利用する方法として使用できます。

  • インターフェイスネクストホップ（Interface nexthops）：インターフェイスを指すネクストホップです。これらのネクストホップに関連付けられるさまざまな属性は次のとおりです。

    • Egress-interface：ネットワーク機器上の物理的、論理的、または仮想的なインターフェイスを表します。このインターフェイスでは、アドレス解決を必要としてはなりません。このインターフェイスは、任意のルーティングインスタンスに属することができます。

    • IPアドレス：egress-interfaceを決定するために、このIPアドレスに対して経路検索が行われます。インターフェイスによっては、アドレス解決が必要になる場合があります。

      • IPアドレスを検索するRIBを示すために、選択可能なrib-nameを指定することもできます。rib-nameフィールドを使用して、パケットをあるドメインから別のドメインに向けることができます。デフォルトでは、RIBはその経路が属するRIBと同じになります。

    これらの属性は、次のように組み合わせて使用できます。

    • Egress-interfaceとIPアドレス：たとえば、IPアドレスがリンクローカルアドレスである場合に使用できます。
    • Egress-interfaceとMACアドレス：egress-interfaceはイーサネットインターフェイスでなければなりません。このネクストホップではアドレス解決は必要ありません。

  • トンネルネクストホップ（Tunnel nexthops）：トンネルを指すネクストホップです。トンネルネクストホップの種類は次のとおりです。

    • tunnel-encapsulation：IPトンネル、MPLSトンネル、またはこの文書で定義するその他のトンネルを表すカプセル化です。パケットをどのインターフェイスから送出するかを示すために、選択可能なegress-interfaceをtunnel-encapsulationにチェーンできます。egress-interfaceは、ネットワーク機器がイーサネットインターフェイスを持ち、IPパケットのアドレス解決を行う必要がある場合に役立ちます。
    • tunnel-decapsulation：トンネルヘッダーのカプセル化解除を指定するためのものです。カプセル化解除の後、別のネクストホップとチェーンすることで、パケットに対してさらに検索を行うことができます。また、パケットをegress-interfaceから直接送出することもできます。
    • logical-tunnel：一意の識別子（たとえば、名前）で表される、MPLSラベルスイッチパス（Label Switched Path、LSP）またはGREトンネル（あるいはこの文書で定義するその他のトンネル）です。
  • rib-name：RIBを指すネクストホップです。これは、指定されたRIBで経路検索を継続する必要があることを示します。これは、チェーンされた検索を行う方法の1つです。

Tunnel nexthops allow a RIB client to program static tunnel headers. There can be cases where the remote tunnel endpoint does not support dynamic signaling (e.g., no LDP support on a host); in those cases, the RIB client might want to program the tunnel header on both ends of the tunnel. The tunnel nexthop is kept generic with specifications provided for some commonly used tunnels. It is expected that the data model will model these tunnel types with complete accuracy.

トンネルネクストホップにより、RIBクライアントは静的なトンネルヘッダーをプログラムできます。リモートのトンネルエンドポイントが動的なシグナリングをサポートしていない場合（たとえば、ホストがLDPをサポートしていない場合）があります。そのような場合、RIBクライアントは、トンネルの両端でトンネルヘッダーをプログラムしたいと考えるかもしれません。トンネルネクストホップは汎用的なものとし、よく使用されるいくつかのトンネルについての仕様を示しています。データモデルは、これらのトンネルタイプを完全に正確にモデル化することが期待されます。

2.4.1.1. Special Nexthops
2.4.1.1. 特殊ネクストホップ

Special nexthops are for performing specific well-defined functions (e.g., DISCARD). The purpose of each of them is explained below:

特殊ネクストホップは、明確に定義された特定の機能（たとえば、DISCARD）を実行するためのものです。それぞれの目的を以下で説明します。

  • DISCARD: This indicates that the network device should drop the packet and increment a drop counter.
  • DISCARD_WITH_ERROR: This indicates that the network device should drop the packet, increment a drop counter, and send back an appropriate error message (like ICMP error).
  • RECEIVE: This indicates that the traffic is destined for the network device, for example, protocol packets or Operations, Administration, and Maintenance (OAM) packets. All locally destined traffic SHOULD be throttled to avoid a denial-of-service attack on the router's control plane. An optional rate limiter can be specified to indicate how to throttle traffic destined for the control plane. The description of the rate limiter is outside the scope of this document.
  • DISCARD：ネットワーク機器がパケットを破棄し、破棄カウンターをインクリメントすべきであることを示します。
  • DISCARD_WITH_ERROR：ネットワーク機器がパケットを破棄し、破棄カウンターをインクリメントし、適切なエラーメッセージ（ICMPエラーなど）を送り返すべきであることを示します。
  • RECEIVE：トラフィックがネットワーク機器宛てであることを示します。たとえば、プロトコルパケットや運用・管理・保守（Operations, Administration, and Maintenance、OAM）パケットです。ルーターのコントロールプレーンに対するサービス拒否攻撃を回避するために、ローカル宛てのすべてのトラフィックは流量を制限すべきです（SHOULD）。コントロールプレーン宛てのトラフィックをどのように制限するかを示すために、選択可能なレートリミッターを指定できます。レートリミッターの説明は、この文書の範囲外です。

2.4.2. Derived Nexthops

2.4.2. 派生ネクストホップ

Derived nexthops can be:

派生ネクストホップには次のものがあります。

  • weighted lists, which are used for load-balancing;
  • preference lists, which are used for protection using primary and backup;
  • replication lists, which are lists of nexthops to which to replicate a packet;
  • nexthop chains, which are for chaining multiple operations or attaching multiple headers; or
  • lists of lists, which are a recursive application of the above.
  • 重み付きリスト。負荷分散に使用されます。
  • 優先度リスト。プライマリーとバックアップを使用した保護に使用されます。
  • 複製リスト。パケットを複製する先のネクストホップのリストです。
  • ネクストホップチェーン。複数の操作をチェーンしたり、複数のヘッダーを付加したりするためのものです。
  • リストのリスト。上記を再帰的に適用したものです。

Nexthop chains (see Section 7.2.5 for usage) are a way to perform multiple operations on a packet by logically combining them. For example, one can chain together "decapsulate MPLS header" and "send it out a specific egress-interface". Chains can be used to specify multiple headers over a packet before a packet is forwarded. One simple example is that of MPLS over GRE, wherein the packet has an inner MPLS header followed by a GRE header followed by an IP header. The outermost IP header is decided by the network device, whereas the MPLS header or GRE header is specified by the controller. Not every network device will be able to support all kinds of nexthop chains and an arbitrary number of headers chained together. The RIB data model SHOULD provide a way to expose a nexthop chaining capability supported by a given network device.

ネクストホップチェーン（使用法についてはセクション7.2.5を参照）は、パケットに対する複数の操作を論理的に組み合わせて実行する方法です。たとえば、「MPLSヘッダーのカプセル化を解除する」と「特定のegress-interfaceから送出する」をチェーンできます。チェーンを使用して、パケットが転送される前に、パケットに付ける複数のヘッダーを指定できます。簡単な例の1つはMPLS over GREです。この場合、パケットは内側のMPLSヘッダー、その後にGREヘッダー、その後にIPヘッダーを持ちます。最も外側のIPヘッダーはネットワーク機器が決定しますが、MPLSヘッダーやGREヘッダーはコントローラーが指定します。すべてのネットワーク機器が、あらゆる種類のネクストホップチェーンと、任意の数のヘッダーのチェーンをサポートできるわけではありません。RIBデータモデルは、あるネットワーク機器がサポートするネクストホップのチェーン能力を公開する方法を提供すべきです（SHOULD）。

It is expected that all network devices will have a limit on how many levels of lookup can be performed, and not all hardware will be able to support all kinds of nexthops. RIB capability negotiation becomes very important for this reason, and a RIB data model MUST specify a way for a RIB client to learn about the network device's capabilities.

すべてのネットワーク機器には実行できる検索の段数に上限があり、すべてのハードウェアがあらゆる種類のネクストホップをサポートできるわけではないと予想されます。この理由からRIBの能力ネゴシエーションは非常に重要になり、RIBデータモデルは、RIBクライアントがネットワーク機器の能力を知る方法を規定しなければなりません（MUST）。

2.4.2.1. Nexthop List Attributes
2.4.2.1. ネクストホップリストの属性

For nexthops that are of the form of a list(s), attributes can be associated with each member of the list to indicate the role of an individual member of the list. Two attributes are specified:

リスト形式のネクストホップでは、リストの個々のメンバーの役割を示すために、リストの各メンバーに属性を関連付けることができます。次の2つの属性を規定します。

  • NEXTHOP_PREFERENCE: This is used for protection schemes. It is an integer value between 1 and 99. A lower value indicates higher preference. To download a primary/standby pair to the FIB, the nexthops that are resolved and have the two highest preferences are selected. Each <NEXTHOP_PREFERENCE> should have a unique value within a <nexthop-protection> (see Section 6).
  • NEXTHOP_LB_WEIGHT: This is used for load-balancing. Each list member MUST be assigned a weight between 1 and 99. The weight determines the proportion of traffic to be sent over a nexthop used for forwarding as a ratio of the weight of this nexthop divided by the weights of all the nexthops of this route that are used for forwarding. To perform equal load-balancing, one MAY specify a weight of "0" for all the member nexthops. The value "0" is reserved for equal load-balancing and, if applied, MUST be applied to all member nexthops. Note that a weight of 0 is special because of historical reasons.
  • NEXTHOP_PREFERENCE：保護方式に使用されます。これは1から99までの整数値です。値が小さいほど優先度が高いことを示します。プライマリー／スタンバイのペアをFIBにダウンロードするために、解決済みで、優先度が最も高い2つのネクストホップが選択されます。各<NEXTHOP_PREFERENCE>は、<nexthop-protection>（セクション6を参照）の中で一意の値を持つべきです。
  • NEXTHOP_LB_WEIGHT：負荷分散に使用されます。リストの各メンバーには、1から99までの重みを割り当てなければなりません（MUST）。重みは、転送に使用されるネクストホップを経由して送信されるトラフィックの割合を、このネクストホップの重みを、この経路の転送に使用されるすべてのネクストホップの重みで割った比率として決定します。均等な負荷分散を行うために、すべてのメンバーのネクストホップに重み「0」を指定してもよいです（MAY）。値「0」は均等な負荷分散のために予約されており、適用する場合は、すべてのメンバーのネクストホップに適用しなければなりません（MUST）。重み0は、歴史的な理由により特別なものであることに注意してください。

2.4.3. Nexthop Indirection

2.4.3. ネクストホップの間接参照

Nexthops can be identified by an identifier to create a level of indirection. The identifier is set by the RIB manager and returned to the RIB client on request.

ネクストホップを識別子で識別して、間接参照のレベルを作ることができます。識別子はRIBマネージャーが設定し、要求に応じてRIBクライアントに返します。

One example of usage of indirection is a nexthop that points to another network device (e.g., a BGP peer). The returned nexthop identifier can then be used for programming routes to point to the this nexthop. Given that the RIB manager has created an indirection using the nexthop identifier, if the transport path to the network device (BGP peer) changes, that change in path will be seamless to the RIB client and all routes that point to that network device will automatically start going over the new transport path. Nexthop indirection using identifiers could be applied to not only unicast nexthops but also nexthops that contain chains and nested nexthops. See Section 2.4.2 for examples.

間接参照の使用例の1つは、別のネットワーク機器（たとえば、BGPピア）を指すネクストホップです。返されたネクストホップ識別子は、このネクストホップを指す経路をプログラムするために使用できます。RIBマネージャーがネクストホップ識別子を使用して間接参照を作成しているため、そのネットワーク機器（BGPピア）へのトランスポートパスが変化しても、そのパスの変化はRIBクライアントからはシームレスであり、そのネットワーク機器を指すすべての経路は自動的に新しいトランスポートパスを通るようになります。識別子を使用したネクストホップの間接参照は、ユニキャストのネクストホップだけでなく、チェーンや入れ子のネクストホップを含むネクストホップにも適用できます。例についてはセクション2.4.2を参照してください。

3. Reading from the RIB

3. RIBからの読み取り

A RIB data model MUST allow a RIB client to read entries for RIBs created by that entity. The network device administrator MAY allow reading of other RIBs by a RIB client through access lists on the network device. The details of access lists are outside the scope of this document.

RIBデータモデルは、RIBクライアントが自身の作成したRIBのエントリーを読み取れるようにしなければなりません（MUST）。ネットワーク機器の管理者は、ネットワーク機器上のアクセスリストを通じて、RIBクライアントが他のRIBを読み取ることを許可してもよいです（MAY）。アクセスリストの詳細は、この文書の範囲外です。

The data model MUST support a full read of the RIB and subsequent incremental reads of changes to the RIB. When sending data to a RIB client, the RIB manager SHOULD try to send all dependencies of an object prior to sending that object.

データモデルは、RIBの完全な読み取りと、それに続くRIBの変更の差分読み取りをサポートしなければなりません（MUST）。RIBクライアントにデータを送信する際、RIBマネージャーは、あるオブジェクトを送信する前に、そのオブジェクトのすべての依存関係を送信するように努めるべきです（SHOULD）。

4. Writing to the RIB

4. RIBへの書き込み

A RIB data model MUST allow a RIB client to write entries for RIBs created by that entity. The network device administrator MAY allow writes to other RIBs by a RIB client through access lists on the network device. The details of access lists are outside the scope of this document.

RIBデータモデルは、RIBクライアントが自身の作成したRIBにエントリーを書き込めるようにしなければなりません（MUST）。ネットワーク機器の管理者は、ネットワーク機器上のアクセスリストを通じて、RIBクライアントが他のRIBに書き込むことを許可してもよいです（MAY）。アクセスリストの詳細は、この文書の範囲外です。

When writing an object to a RIB, the RIB client SHOULD try to write all dependencies of the object prior to sending that object. The data model SHOULD support requesting identifiers for nexthops and collecting the identifiers back in the response.

オブジェクトをRIBに書き込む際、RIBクライアントは、そのオブジェクトを送信する前に、そのオブジェクトのすべての依存関係を書き込むように努めるべきです（SHOULD）。データモデルは、ネクストホップの識別子を要求し、その識別子をレスポンスで受け取ることをサポートすべきです（SHOULD）。

Route programming in the RIB MUST result in a return code that contains the following attributes:

RIBへの経路のプログラミングの結果として、次の属性を含むリターンコードを返さなければなりません（MUST）。

  • Installed: Yes/No (indicates whether the route got installed in the FIB)
  • Active: Yes/No (indicates whether a route is fully resolved and is a candidate for selection)
  • Reason: E.g., "Not authorized"
  • Installed：Yes/No（経路がFIBにインストールされたかどうかを示します）
  • Active：Yes/No（経路が完全に解決済みで、選択の候補であるかどうかを示します）
  • Reason：たとえば、「Not authorized」

The data model MUST specify which objects can be modified. An object that can be modified is one whose contents can be changed without having to change objects that depend on it and without affecting any data forwarding. To change a non-modifiable object, one will need to create a new object and delete the old one. For example, routes that use a nexthop that is identified by a nexthop identifier should be unaffected when the contents of that nexthop changes.

データモデルは、どのオブジェクトを変更できるかを規定しなければなりません（MUST）。変更可能なオブジェクトとは、そのオブジェクトに依存するオブジェクトを変更する必要がなく、データ転送にも影響を与えずに、内容を変更できるオブジェクトです。変更不可能なオブジェクトを変更するには、新しいオブジェクトを作成し、古いオブジェクトを削除する必要があります。たとえば、ネクストホップ識別子で識別されるネクストホップを使用する経路は、そのネクストホップの内容が変わっても影響を受けないはずです。

5. Notifications

5. 通知

Asynchronous notifications are sent by the network device's RIB manager to a RIB client when some event occurs on the network device. A RIB data model MUST support sending asynchronous notifications. A brief list of suggested notifications is as below:

非同期通知は、ネットワーク機器上で何らかのイベントが発生したときに、ネットワーク機器のRIBマネージャーからRIBクライアントに送信されます。RIBデータモデルは、非同期通知の送信をサポートしなければなりません（MUST）。推奨される通知の簡単なリストは次のとおりです。

  • Route change notification (with a return code as specified in Section 4)
  • Nexthop resolution status (resolved/unresolved) notification
  • 経路変更通知（セクション4で規定するリターンコード付き）
  • ネクストホップの解決状態（解決済み／未解決）の通知

6. RIB Grammar

6. RIB文法

This section specifies the RIB information model in Routing Backus-Naur Form (rBNF) [RFC5511]. This grammar is intended to help the reader better understand Section 2 in order to derive a data model.

このセクションでは、RIB情報モデルをルーティングバッカス・ナウア記法（Routing Backus-Naur Form、rBNF）[RFC5511]で規定します。この文法は、読者がデータモデルを導出するためにセクション2をよりよく理解できるようにすることを意図しています。

6.1. Nexthop Grammar Explained

6.1. ネクストホップ文法の説明

A nexthop is used to specify the next network element to forward the traffic to. It is also used to specify how the traffic should be load-balanced, protected using preference, or multicast using replication. This is explicitly specified in the grammar. The nexthop has recursion built in to address complex use cases like the one defined in Section 7.2.6.

ネクストホップは、トラフィックの転送先となる次のネットワーク要素を指定するために使用されます。また、トラフィックをどのように負荷分散するか、優先度を使用してどのように保護するか、複製を使用してどのようにマルチキャストするかを指定するためにも使用されます。これは文法の中で明示的に規定されています。セクション7.2.6で定義するような複雑なユースケースに対応するために、ネクストホップには再帰が組み込まれています。

7. Using the RIB Grammar

7. RIB文法の使用

The RIB grammar is very generic and covers a variety of features. This section provides examples on using objects in the RIB grammar and examples to program certain use cases.

RIB文法は非常に汎用的であり、さまざまな機能を扱います。このセクションでは、RIB文法のオブジェクトの使用例と、特定のユースケースをプログラムする例を示します。

7.1. Using Route Preference

7.1. 経路優先度の使用

Using route preference, a client can preinstall alternate paths in the network. For example, if OSPF has a route preference of 10, then another client can install a route with a route preference of 20 to the same destination. The OSPF route will get precedence and will get installed in the FIB. When the OSPF route is withdrawn, the alternate path will get installed in the FIB.

経路優先度を使用すると、クライアントはネットワーク内に代替パスを事前にインストールできます。たとえば、OSPFの経路優先度が10である場合、別のクライアントは同じ宛先への経路を経路優先度20でインストールできます。OSPFの経路が優先され、FIBにインストールされます。OSPFの経路が取り消されると、代替パスがFIBにインストールされます。

Route preference can also be used to prevent denial-of-service attacks by installing routes with the best preference, which either drops the offending traffic or routes it to some monitoring/analysis station. Since the routes are installed with the best preference, they will supersede any route installed by any other protocol.

経路優先度は、最良の優先度を持つ経路をインストールすることで、サービス拒否攻撃を防ぐためにも使用できます。その経路は、問題のあるトラフィックを破棄するか、何らかの監視／分析ステーションにルーティングします。経路は最良の優先度でインストールされるので、他のどのプロトコルがインストールした経路よりも優先されます。

7.2. Using Different Nexthop Types

7.2. さまざまなネクストホップタイプの使用

The RIB grammar allows one to create a variety of nexthops. This section describes uses for certain types of nexthops.

RIB文法を使用すると、さまざまなネクストホップを作成できます。このセクションでは、特定の種類のネクストホップの使い方を説明します。

7.2.1. Tunnel Nexthops

7.2.1. トンネルネクストホップ

A tunnel nexthop points to a tunnel of some kind. Traffic that goes over the tunnel gets encapsulated with the tunnel-encapsulation. Tunnel nexthops are useful for abstracting out details of the network by having the traffic seamlessly route between network edges. At the end of a tunnel, the tunnel will get decapsulated. Thus, the grammar supports two kinds of operations: one for encapsulation and another for decapsulation.

トンネルネクストホップは、何らかの種類のトンネルを指します。トンネルを通過するトラフィックは、tunnel-encapsulationでカプセル化されます。トンネルネクストホップは、ネットワークのエッジ間でトラフィックをシームレスにルーティングさせることで、ネットワークの詳細を抽象化するのに役立ちます。トンネルの終端では、トンネルのカプセル化が解除されます。したがって、この文法は、カプセル化のための操作とカプセル化解除のための操作の2種類をサポートします。

7.2.2. Replication Lists

7.2.2. 複製リスト

One can create a replication list for replicating traffic to multiple destinations. The destinations, in turn, could be derived nexthops in themselves (at a level supported by the network device); point to multipoint and broadcast are examples that involve replication.

トラフィックを複数の宛先に複製するための複製リストを作成できます。その宛先自体が、（ネットワーク機器がサポートするレベルで）派生ネクストホップであってもかまいません。ポイントツーマルチポイントやブロードキャストは、複製を伴う例です。

A replication list (at the simplest level) can be represented as:

複製リストは、（最も単純なレベルでは）次のように表すことができます。

<nexthop> ::= <NEXTHOP_REPLICATE> <nexthop> [ <nexthop> ... ]

<nexthop> ::= <NEXTHOP_REPLICATE> <nexthop> [ <nexthop> ... ]

The above can be derived from the grammar as follows:

上記は、文法から次のように導出できます。

<nexthop> ::= <nexthop-replicate>
<nexthop> ::= <NEXTHOP_REPLICATE> <nexthop> <nexthop> ...

<nexthop> ::= <nexthop-replicate>
<nexthop> ::= <NEXTHOP_REPLICATE> <nexthop> <nexthop> ...

7.2.3. Weighted Lists

7.2.3. 重み付きリスト

A weighted list is used to load-balance traffic among a set of nexthops. From a modeling perspective, a weighted list is very similar to a replication list, with the difference that each member nexthop MUST have a NEXTHOP_LB_WEIGHT associated with it.

重み付きリストは、ネクストホップの集合の間でトラフィックを負荷分散するために使用されます。モデル化の観点からは、重み付きリストは複製リストと非常によく似ていますが、各メンバーのネクストホップにNEXTHOP_LB_WEIGHTを関連付けなければなりません（MUST）という点が異なります。

A weighted list (at the simplest level) can be represented as:

重み付きリストは、（最も単純なレベルでは）次のように表すことができます。

<nexthop> ::= <NEXTHOP_LOAD_BALANCE> (<nexthop> <NEXTHOP_LB_WEIGHT>)
                   [(<nexthop> <NEXTHOP_LB_WEIGHT>)... ]

<nexthop> ::= <NEXTHOP_LOAD_BALANCE> (<nexthop> <NEXTHOP_LB_WEIGHT>)
                   [(<nexthop> <NEXTHOP_LB_WEIGHT>)... ]

The above can be derived from the grammar as follows:

上記は、文法から次のように導出できます。

<nexthop> ::= <nexthop-lb>
<nexthop> ::= <NEXTHOP_LOAD_BALANCE>
                <NEXTHOP_LB_WEIGHT> <nexthop>
                (<NEXTHOP_LB_WEIGHT> <nexthop>) ...
<nexthop> ::= <NEXTHOP_LOAD_BALANCE> (<NEXTHOP_LB_WEIGHT> <nexthop>)
                (<NEXTHOP_LB_WEIGHT> <nexthop>) ...

<nexthop> ::= <nexthop-lb>
<nexthop> ::= <NEXTHOP_LOAD_BALANCE>
                <NEXTHOP_LB_WEIGHT> <nexthop>
                (<NEXTHOP_LB_WEIGHT> <nexthop>) ...
<nexthop> ::= <NEXTHOP_LOAD_BALANCE> (<NEXTHOP_LB_WEIGHT> <nexthop>)
                (<NEXTHOP_LB_WEIGHT> <nexthop>) ...

7.2.4. Protection

7.2.4. 保護

A primary/backup protection can be represented as:

プライマリー／バックアップによる保護は、次のように表すことができます。

<nexthop> ::= <NEXTHOP_PROTECTION> <1> <interface-primary>
                                   <2> <interface-backup>)

<nexthop> ::= <NEXTHOP_PROTECTION> <1> <interface-primary>
                                   <2> <interface-backup>)

The above can be derived from the grammar as follows:

上記は、文法から次のように導出できます。

<nexthop> ::= <nexthop-protection>
<nexthop> ::= <NEXTHOP_PROTECTION> (<NEXTHOP_PREFERENCE> <nexthop>
                      (<NEXTHOP_PREFERENCE> <nexthop>)...)
<nexthop> ::= <NEXTHOP_PROTECTION> (<NEXTHOP_PREFERENCE> <nexthop>
                      (<NEXTHOP_PREFERENCE> <nexthop>))
<nexthop> ::= <NEXTHOP_PROTECTION> ((<NEXTHOP_PREFERENCE> <nexthop-base>
                      (<NEXTHOP_PREFERENCE> <nexthop-base>))
<nexthop> ::= <NEXTHOP_PROTECTION> (<1> <interface-primary>
                      (<2> <interface-backup>))

<nexthop> ::= <nexthop-protection>
<nexthop> ::= <NEXTHOP_PROTECTION> (<NEXTHOP_PREFERENCE> <nexthop>
                      (<NEXTHOP_PREFERENCE> <nexthop>)...)
<nexthop> ::= <NEXTHOP_PROTECTION> (<NEXTHOP_PREFERENCE> <nexthop>
                      (<NEXTHOP_PREFERENCE> <nexthop>))
<nexthop> ::= <NEXTHOP_PROTECTION> ((<NEXTHOP_PREFERENCE> <nexthop-base>
                      (<NEXTHOP_PREFERENCE> <nexthop-base>))
<nexthop> ::= <NEXTHOP_PROTECTION> (<1> <interface-primary>
                      (<2> <interface-backup>))

Traffic can be load-balanced among multiple primary nexthops and a single backup. In such a case, the nexthop will look like:

トラフィックを、複数のプライマリーネクストホップと単一のバックアップの間で負荷分散することもできます。そのような場合、ネクストホップは次のようになります。

<nexthop> ::= <NEXTHOP_PROTECTION> (<1>
              (<NEXTHOP_LOAD_BALANCE>
               (<NEXTHOP_LB_WEIGHT> <nexthop-base>
               (<NEXTHOP_LB_WEIGHT> <nexthop-base>) ...))
                <2> <nexthop-base>)

<nexthop> ::= <NEXTHOP_PROTECTION> (<1>
              (<NEXTHOP_LOAD_BALANCE>
               (<NEXTHOP_LB_WEIGHT> <nexthop-base>
               (<NEXTHOP_LB_WEIGHT> <nexthop-base>) ...))
                <2> <nexthop-base>)

A backup can also have another backup. In such a case, the list will look like:

バックアップがさらに別のバックアップを持つこともできます。そのような場合、リストは次のようになります。

<nexthop> ::= <NEXTHOP_PROTECTION> (<1> <nexthop>
              <2> <NEXTHOP_PROTECTION>(<1> <nexthop> <2> <nexthop>))

<nexthop> ::= <NEXTHOP_PROTECTION> (<1> <nexthop>
              <2> <NEXTHOP_PROTECTION>(<1> <nexthop> <2> <nexthop>))

7.2.5. Nexthop Chains

7.2.5. ネクストホップチェーン

A nexthop chain is a way to perform multiple operations on a packet by logically combining them. For example, when a VPN packet comes on the WAN interface and has to be forwarded to the correct VPN interface, one needs to pop the VPN label before sending the packet out. Using a nexthop chain, one can chain together "pop MPLS header" and "send it out a specific egress-interface".

ネクストホップチェーンは、パケットに対する複数の操作を論理的に組み合わせて実行する方法です。たとえば、VPNパケットがWANインターフェイスに到着し、正しいVPNインターフェイスに転送しなければならない場合、パケットを送出する前にVPNラベルをポップする必要があります。ネクストホップチェーンを使用すると、「MPLSヘッダーをポップする」と「特定のegress-interfaceから送出する」をチェーンできます。

The above example can be derived from the grammar as follows:

上記の例は、文法から次のように導出できます。

<nexthop-chain> ::= <nexthop> <nexthop>
<nexthop-chain> ::= <nexthop-base> <nexthop-base>
<nexthop-chain> ::= <tunnel-decapsulation> <egress-interface>
<nexthop-chain> ::= (<MPLS> <MPLS_POP>) <interface-outgoing>

<nexthop-chain> ::= <nexthop> <nexthop>
<nexthop-chain> ::= <nexthop-base> <nexthop-base>
<nexthop-chain> ::= <tunnel-decapsulation> <egress-interface>
<nexthop-chain> ::= (<MPLS> <MPLS_POP>) <interface-outgoing>

Elements in a nexthop chain are evaluated left to right.

ネクストホップチェーン内の要素は、左から右に評価されます。

A nexthop chain can also be used to put one or more headers on an outgoing packet. One example is a pseudowire, which is MPLS over some transport (MPLS or GRE, for instance). Another example is Virtual eXtensible Local Area Network (VXLAN) over IP. A nexthop chain thus allows a RIB client to break up the programming of the nexthop into independent pieces (one per encapsulation).

ネクストホップチェーンは、送信パケットに1つ以上のヘッダーを付けるためにも使用できます。例の1つは疑似回線（pseudowire）です。これは、何らかのトランスポート（たとえば、MPLSやGRE）上のMPLSです。別の例は、IP上の仮想拡張可能LAN（Virtual eXtensible Local Area Network、VXLAN）です。このように、ネクストホップチェーンにより、RIBクライアントはネクストホップのプログラミングを（カプセル化ごとに1つの）独立した部分に分割できます。

A simple example of MPLS over GRE can be represented as follows:

MPLS over GREの簡単な例は、次のように表すことができます。

<nexthop-chain> ::= (<MPLS> <mpls-header>) (<GRE> <gre-header>)
                    <interface-outgoing>

<nexthop-chain> ::= (<MPLS> <mpls-header>) (<GRE> <gre-header>)
                    <interface-outgoing>

The above can be derived from the grammar as follows:

上記は、文法から次のように導出できます。

<nexthop-chain> ::= <nexthop> <nexthop> <nexthop>
<nexthop-chain> ::= <nexthop-base> <nexthop-base> <nexthop-base>
<nexthop-chain> ::= <tunnel-encapsulation> <tunnel-encapsulation>
                    <egress-interface>
<nexthop-chain> ::= (<MPLS> <mpls-header>) (<GRE> <gre-header>)
                    <interface-outgoing>

<nexthop-chain> ::= <nexthop> <nexthop> <nexthop>
<nexthop-chain> ::= <nexthop-base> <nexthop-base> <nexthop-base>
<nexthop-chain> ::= <tunnel-encapsulation> <tunnel-encapsulation>
                    <egress-interface>
<nexthop-chain> ::= (<MPLS> <mpls-header>) (<GRE> <gre-header>)
                    <interface-outgoing>

7.2.6. Lists of Lists

7.2.6. リストのリスト

Lists of lists is a derived construct. One example of usage of such a construct is to replicate traffic to multiple destinations with load-balancing. In other words, for each branch of the replication tree, there are multiple interfaces on which traffic needs to be load-balanced. So, the outer list is a replication list for multicast and the inner lists are weighted lists for load-balancing. Let's take an example of a network element that has to replicate traffic to two other network elements. Traffic to the first network element should be load-balanced equally over two interfaces: outgoing-1-1 and outgoing-1-2. Traffic to the second network element should be load-balanced over three interfaces: outgoing-2-1, outgoing-2-2, and outgoing-2-3 (in the ratio 20:20:60).

リストのリストは派生的な構成要素です。このような構成要素の使用例の1つは、負荷分散を行いながらトラフィックを複数の宛先に複製することです。言い換えれば、複製ツリーの各分岐について、トラフィックを負荷分散する必要のある複数のインターフェイスがあります。したがって、外側のリストはマルチキャストのための複製リストであり、内側のリストは負荷分散のための重み付きリストです。他の2つのネットワーク要素にトラフィックを複製しなければならないネットワーク要素を例に考えてみましょう。1つ目のネットワーク要素へのトラフィックは、outgoing-1-1とoutgoing-1-2の2つのインターフェイスで均等に負荷分散する必要があります。2つ目のネットワーク要素へのトラフィックは、outgoing-2-1、outgoing-2-2、outgoing-2-3の3つのインターフェイスで（20:20:60の比率で）負荷分散する必要があります。

7.3. Performing Multicast

7.3. マルチキャストの実行

IP multicast involves matching a packet on (S,G) or (*,G), where both S (Source) and G (Group) are IP prefixes. Following the match, the packet is replicated to one or more recipients. How the recipients subscribe to the multicast group is outside the scope of this document.

IPマルチキャストでは、パケットを(S,G)または(*,G)で一致させます。ここで、S（Source、送信元）とG（Group、グループ）はどちらもIPプレフィックスです。一致した後、パケットは1つ以上の受信者に複製されます。受信者がマルチキャストグループをどのように購読するかは、この文書の範囲外です。

In PIM-based multicast, the packets are IP forwarded on an IP multicast tree. The downstream nodes on each point in the multicast tree are one or more IP addresses. These can be represented as a replication list (see Section 7.2.2).

PIMベースのマルチキャストでは、パケットはIPマルチキャストツリー上でIP転送されます。マルチキャストツリーの各地点の下流ノードは、1つ以上のIPアドレスです。これらは複製リスト（セクション7.2.2を参照）として表すことができます。

In MPLS-based multicast, the packets are forwarded on a Point-to-Multipoint (P2MP) LSP. The nexthop for a P2MP LSP can be represented in the nexthop grammar as a <logical-tunnel> (P2MP LSP identifier) or a replication list (see Section 7.2.2) of <tunnel-encapsulation>, with each tunnel-encapsulation representing a single MPLS downstream nexthop.

MPLSベースのマルチキャストでは、パケットはポイントツーマルチポイント（Point-to-Multipoint、P2MP）LSP上で転送されます。P2MP LSPのネクストホップは、ネクストホップ文法では、<logical-tunnel>（P2MP LSP識別子）として、または<tunnel-encapsulation>の複製リスト（セクション7.2.2を参照）として表すことができます。後者の場合、各tunnel-encapsulationは1つのMPLS下流ネクストホップを表します。

8. RIB Operations at Scale

8. 大規模なRIB操作

This section discusses the scale requirements for a RIB data model. The RIB data model should be able to handle a large scale of operations to enable deployment of RIB applications in large networks.

このセクションでは、RIBデータモデルに対する規模の要件について説明します。大規模なネットワークでRIBアプリケーションを展開できるようにするために、RIBデータモデルは大規模な操作を扱えるべきです。

8.1. RIB Reads

8.1. RIBの読み取り

Bulking (grouping of multiple objects in a single message) MUST be supported when a network device sends RIB data to a RIB client. Similarly, the data model MUST enable a RIB client to request data in bulk from a network device.

ネットワーク機器がRIBクライアントにRIBデータを送信する際には、一括処理（単一のメッセージに複数のオブジェクトをまとめること）をサポートしなければなりません（MUST）。同様に、データモデルは、RIBクライアントがネットワーク機器にデータを一括で要求できるようにしなければなりません（MUST）。

8.2. RIB Writes

8.2. RIBへの書き込み

Bulking (grouping of multiple write operations in a single message) MUST be supported when a RIB client wants to write to the RIB. The response from the network device MUST include a return-code for each write operation in the bulk message.

RIBクライアントがRIBに書き込む際には、一括処理（単一のメッセージに複数の書き込み操作をまとめること）をサポートしなければなりません（MUST）。ネットワーク機器からのレスポンスは、一括メッセージ内の書き込み操作ごとにリターンコードを含まなければなりません（MUST）。

8.3. RIB Events and Notifications

8.3. RIBのイベントと通知

There can be cases where a single network event results in multiple events and/or notifications from the network device to a RIB client. On the other hand, due to timing of multiple things happening at the same time, a network device might have to send multiple events and/or notifications to a RIB client. The network-device-originated event/notification message MUST support the bulking of multiple events and notifications in a single message.

単一のネットワークイベントの結果として、ネットワーク機器からRIBクライアントに複数のイベントや通知が送られる場合があります。一方で、複数の事象が同時に発生するタイミングによって、ネットワーク機器がRIBクライアントに複数のイベントや通知を送信しなければならない場合もあります。ネットワーク機器が発信するイベント／通知メッセージは、単一のメッセージに複数のイベントや通知をまとめる一括処理をサポートしなければなりません（MUST）。

9. Security Considerations

9. セキュリティーに関する考慮事項

The information model specified in this document defines a schema for data models that are designed to be accessed via network management protocols such as NETCONF [RFC6241] or RESTCONF [RFC8040]. The lowest NETCONF layer is the secure transport layer, and the mandatory-to-implement secure transport is Secure Shell (SSH) [RFC6242]. The lowest RESTCONF layer is HTTPS, and the mandatory-to-implement secure transport is TLS [RFC8446].

この文書で規定する情報モデルは、NETCONF [RFC6241]やRESTCONF [RFC8040]などのネットワーク管理プロトコルを介してアクセスされるように設計されたデータモデルのスキーマを定義します。NETCONFの最下位層はセキュアなトランスポート層であり、実装必須のセキュアなトランスポートはセキュアシェル（Secure Shell、SSH）[RFC6242]です。RESTCONFの最下位層はHTTPSであり、実装必須のセキュアなトランスポートはTLS [RFC8446]です。

The NETCONF access control model [RFC8341] provides the means to restrict access for particular NETCONF or RESTCONF users to a preconfigured subset of all available NETCONF or RESTCONF protocol operations and content.

NETCONFアクセス制御モデル[RFC8341]は、特定のNETCONFまたはRESTCONFのユーザーのアクセスを、利用可能なすべてのNETCONFまたはRESTCONFのプロトコル操作とコンテンツのうち、事前に設定されたサブセットに制限する手段を提供します。

The RIB information model specifies read and write operations to network devices. These network devices might be considered sensitive or vulnerable in some network environments. Write operations to these network devices without proper protection can have a negative effect on network operations. Due to this factor, it is recommended that data models also consider the following in their design:

RIB情報モデルは、ネットワーク機器に対する読み取りと書き込みの操作を規定します。これらのネットワーク機器は、ネットワーク環境によっては、機微なもの、または脆弱なものとみなされる場合があります。適切な保護なしにこれらのネットワーク機器に書き込み操作を行うと、ネットワークの運用に悪影響を及ぼす可能性があります。このため、データモデルの設計においても次の点を考慮することを推奨します。

  • Require utilization of the authentication and authorization features of the NETCONF or RESTCONF suite of protocols.
  • Augment the limits on how much data can be written or updated by a remote entity built to include enough protection for a RIB data model.
  • Expose the specific RIB data model implemented via NETCONF/RESTCONF data models.
  • NETCONFまたはRESTCONFのプロトコル群の認証機能と認可機能の利用を必須とすること。
  • RIBデータモデルに対して十分な保護を含むように構築された、リモートのエンティティーが書き込みまたは更新できるデータ量の制限を強化すること。
  • 実装された特定のRIBデータモデルを、NETCONF/RESTCONFのデータモデルを介して公開すること。
