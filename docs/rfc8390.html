RSVP-TE Path Diversity Using Exclude Route

RFC 8390

Exclude Routeを用いたRSVP-TEのパスダイバーシティー

Abstract

概要

RSVP-TE provides support for the communication of exclusion information during Label Switched Path (LSP) setup. A typical LSP diversity use case is for protection, where two LSPs should follow different paths through the network in order to avoid single points of failure, thus greatly improving service availability. This document specifies an approach that can be used for network scenarios where the full path(s) is not necessarily known by use of an abstract identifier for the path. Three types of abstract identifiers are specified: client based, Path Computation Element (PCE) based, and network based. This document specifies two new diversity subobjects for the RSVP eXclude Route Object (XRO) and the Explicit Exclusion Route Subobject (EXRS).

RSVP-TEは、ラベルスイッチパス（LSP）のセットアップ中に除外情報を伝達する機能をサポートしています。 LSPダイバーシティーの典型的なユースケースは保護であり、単一障害点を避けるために2つのLSPがネットワーク内で異なるパスをたどるべきとするもので、これによりサービスの可用性が大きく向上します。 この文書は、パスに抽象的な識別子を用いることで、完全なパスが必ずしもわかっていないネットワークシナリオで使用できるアプローチを規定します。 抽象的な識別子として、クライアントベース、経路計算要素（PCE）ベース、ネットワークベースの3種類を規定します。 この文書は、RSVPの除外経路オブジェクト（eXclude Route Object：XRO）と明示的除外経路サブオブジェクト（Explicit Exclusion Route Subobject：EXRS）向けに、2つの新しいダイバーシティーサブオブジェクトを規定します。

For the protection use case, LSPs are typically created at a slow rate and exist for a long time so that it is reasonable to assume that a given (reference) path currently existing (with a well-known identifier) will continue to exist and can be used as a reference when creating the new diverse path. Re-routing of the existing (reference) LSP, before the new path is established, is not considered.

保護のユースケースでは、LSPは通常ゆっくりとした頻度で作成され、長期間存在します。 そのため、現在存在する（よく知られた識別子を持つ）ある（参照）パスは今後も存在し続け、新しいダイバースなパスを作成する際の参照として使用できると想定するのは妥当です。 新しいパスが確立される前に既存の（参照）LSPが再ルーティングされることは考慮しません。

1. Introduction

1. はじめに

Path diversity for multiple connections is a well-known operational requirement. Diversity constraints ensure that Label Switched Paths (LSPs) can be established without sharing network resources, thus greatly reducing the probability of simultaneous connection failures.

複数のコネクションに対するパスダイバーシティーは、よく知られた運用上の要件です。 ダイバーシティー制約は、ラベルスイッチパス（LSP）がネットワークリソースを共有せずに確立できることを保証し、これにより同時にコネクション障害が発生する確率を大きく下げます。

The source node can compute diverse paths for LSPs when it has full knowledge of the network topology and is permitted to signal an Explicit Route Object (ERO). However, there are scenarios where different nodes perform path computations, and therefore there is a need for relevant diversity constraints to be signaled to those nodes. These include (but are not limited to):

送信元ノードは、ネットワークトポロジーを完全に把握しており、明示的経路オブジェクト（ERO）をシグナリングすることが許可されている場合には、LSPのダイバースなパスを計算できます。 しかし、異なるノードが経路計算を行うシナリオもあり、そのため、それらのノードに関連するダイバーシティー制約をシグナリングする必要があります。 そのようなシナリオには次のものが含まれます（ただし、これらに限定されません）。

  • LSPs with loose hops in the Explicit Route Object, e.g., inter-domain LSPs; and
  • Generalized Multiprotocol Label Switching (GMPLS) User-Network Interface (UNI), where the core node may perform path computation [RFC4208].
  • 明示的経路オブジェクト内に緩いホップを含むLSP（たとえば、ドメイン間LSP）
  • コアノードが経路計算を行う場合がある、汎用マルチプロトコルラベルスイッチング（GMPLS）のユーザー・ネットワーク・インターフェイス（UNI）[RFC4208]

[RFC4874] introduced a means of specifying nodes and resources to be excluded from a route using the eXclude Route Object (XRO) and Explicit Exclusion Route Subobject (EXRS). It facilitates the calculation of diverse paths for LSPs based on known properties of those paths including addresses of links and nodes traversed and Shared Risk Link Groups (SRLGs) of traversed links. Employing these mechanisms requires that the source node that initiates signaling knows the relevant properties of the path(s) from which diversity is desired. However, there are circumstances under which this may not be possible or desirable, including (but not limited to):

[RFC4874]は、除外経路オブジェクト（XRO）と明示的除外経路サブオブジェクト（EXRS）を用いて、経路から除外するノードやリソースを指定する手段を導入しました。 これにより、通過するリンクやノードのアドレス、通過するリンクの共有リスクリンクグループ（SRLG）といった、パスの既知の特性に基づいて、LSPのダイバースなパスを計算しやすくなります。 これらのメカニズムを用いるには、シグナリングを開始する送信元ノードが、ダイバーシティーを求める対象のパスの関連する特性を知っている必要があります。 しかし、それが不可能であったり望ましくなかったりする状況もあり、次のものが含まれます（ただし、これらに限定されません）。

  • Exclusion of a path that does not originate, terminate, or traverse the source node of the diverse LSP, in which case the addresses of links and SRLGs of the path from which diversity is required are unknown to the source node.
  • Exclusion of a path that is known to the source node of the diverse LSP for which the node has incomplete or no path information, e.g., due to operator policy. In this case, the source node is aware of the existence of the reference path, but the information required to construct an XRO object to guarantee diversity from the reference path is not fully known. Inter-domain and GMPLS overlay networks can impose such restrictions.
  • ダイバースLSPの送信元ノードを始点・終点・経由点のいずれともしないパスの除外。 この場合、ダイバーシティーが求められるパスのリンクのアドレスやSRLGは、送信元ノードにはわかりません。
  • ダイバースLSPの送信元ノードが存在を知ってはいるものの、たとえば運用者のポリシーのために、そのノードがパス情報を不完全にしか持っていない、あるいはまったく持っていないパスの除外。 この場合、送信元ノードは参照パスの存在を認識していますが、参照パスからのダイバーシティーを保証するXROオブジェクトを構築するのに必要な情報は完全にはわかっていません。 ドメイン間ネットワークやGMPLSオーバーレイネットワークでは、このような制約が課される場合があります。

This is illustrated in Figure 1, where the overlay reference model from [RFC4208] is shown.

これを図1に示します。図1は[RFC4208]のオーバーレイ参照モデルを示しています。

Figure 1 depicts two types of UNI connectivity: single-homed and dual-homed ENs (which also applies to higher-order multihomed connectivity). Single-homed EN devices are connected to a single CN device via a single UNI link. This single UNI link may constitute a single point of failure. UNI connection between EN1 and CN1 is an example of singled-homed UNI connectivity.

図1は、シングルホームのENとデュアルホームのEN（より多重のマルチホーム接続にも当てはまります）という2種類のUNI接続を示しています。 シングルホームのENデバイスは、単一のUNIリンクを介して単一のCNデバイスに接続されます。 この単一のUNIリンクは単一障害点となる可能性があります。 EN1とCN1の間のUNIコネクションは、シングルホームのUNI接続の例です。

Such a single point of failure can be avoided when the EN device is connected to two different CN devices, as depicted for EN2 in Figure 1. For the dual-homing case, it is possible to establish two different UNI connections from the same source EN device to the same destination EN device. For example, two connections from EN2 to EN3 may use the two UNI links EN2-CN1 and EN2-CN4. To avoid single points of failure within the provider network, it is necessary to also ensure path (LSP) diversity within the core network.

図1のEN2のように、ENデバイスが2つの異なるCNデバイスに接続されている場合、このような単一障害点を避けられます。 デュアルホームの場合、同じ送信元ENデバイスから同じ宛先ENデバイスへ、2つの異なるUNIコネクションを確立できます。 たとえば、EN2からEN3への2つのコネクションは、EN2-CN1とEN2-CN4という2つのUNIリンクを使用できます。 プロバイダーネットワーク内の単一障害点を避けるには、コアネットワーク内でもパス（LSP）のダイバーシティーを保証する必要があります。

In a network providing a set of UNI interfaces between ENs and CNs such as that shown in Figure 1, the CNs typically perform path computation. Information sharing across the UNI boundary is restricted based on the policy rules imposed by the core network. Typically, the core network topology information as well as LSP path information is not exposed to the ENs. In the network shown in Figure 1, consider a use case where an LSP from EN2 to EN4 needs to be SRLG diverse from an LSP from EN1 to EN3. In this case, EN2 may not know SRLG attributes of the EN1-EN3 LSP and hence cannot construct an XRO to exclude these SRLGs. In this example, EN2 cannot use the procedures described in [RFC4874]. Similarly, an LSP from EN2 to EN3 traversing CN1 needs to be diverse from an LSP from EN2 to EN3 going via CN4. Again, in this case, exclusions based on [RFC4874] cannot be used.

図1に示すような、ENとCNの間に一連のUNIインターフェイスを提供するネットワークでは、通常はCNが経路計算を行います。 UNI境界を越えた情報共有は、コアネットワークが課すポリシー規則に基づいて制限されます。 通常、コアネットワークのトポロジー情報やLSPのパス情報はENには公開されません。 図1に示すネットワークにおいて、EN2からEN4へのLSPが、EN1からEN3へのLSPに対してSRLGダイバースである必要があるユースケースを考えます。 この場合、EN2はEN1-EN3 LSPのSRLG属性を知らない可能性があり、そのためこれらのSRLGを除外するXROを構築できません。 この例では、EN2は[RFC4874]で説明されている手順を使用できません。 同様に、CN1を経由するEN2からEN3へのLSPが、CN4を経由するEN2からEN3へのLSPに対してダイバースである必要がある場合も考えます。 この場合も、[RFC4874]に基づく除外は使用できません。

This document addresses these diversity requirements by introducing an approach of excluding the path taken by these particular LSP(s). Each reference LSP or route from which diversity is required is identified by an abstract "identifier". The type of identifier to use is highly dependent on the core network operator's networking deployment scenario; it could be client initiated (provided by the EN), provided by a PCE, or allocated by the (core) network. This document defines three different types of identifiers corresponding to these three cases: a client-initiated identifier, a PCE-allocated identifier, and an identifier allocated by the CN ingress node (UNI-N), i.e., a network-assigned identifier.

この文書は、これらの特定のLSPがたどるパスを除外するアプローチを導入することにより、これらのダイバーシティー要件に対処します。 ダイバーシティーが求められる参照LSPまたは経路は、それぞれ抽象的な「識別子」によって識別されます。 使用する識別子の種類は、コアネットワーク運用者のネットワーク展開シナリオに大きく依存します。 識別子は、クライアントが開始する（ENが提供する）もの、PCEが提供するもの、（コア）ネットワークが割り当てるもののいずれかです。 この文書は、これら3つの場合に対応する3種類の識別子、すなわち、クライアント開始識別子、PCE割り当て識別子、そしてCNの入口ノード（UNI-N）が割り当てる識別子であるネットワーク割り当て識別子を定義します。

1.2. Terms and Abbreviations

1.2. 用語と略語

Diverse LSP:
A diverse Label Switched Path (LSP) is an LSP that has a path that does not have any link or SRLG in common with the path of a given LSP. Diverse LSPs are meaningful in the context of protection or restoration.
ERO:
Explicit Route Object as defined in [RFC3209].
EXRS:
Explicit Exclusion Route Subobject as defined in [RFC4874].
SRLG:
Shared Risk Link Group as defined in [RFC4202].
Reference Path:
The reference path is the path of an existing LSP to which the path of a diverse LSP shall be diverse.
XRO:
eXclude Route Object as defined in [RFC4874].
ダイバースLSP（Diverse LSP）：
ダイバースなラベルスイッチパス（LSP）とは、あるLSPのパスとリンクもSRLGも共有しないパスを持つLSPのことです。 ダイバースLSPは、保護や復旧の文脈で意味を持ちます。
ERO：
[RFC3209]で定義されている明示的経路オブジェクト（Explicit Route Object）です。
EXRS：
[RFC4874]で定義されている明示的除外経路サブオブジェクト（Explicit Exclusion Route Subobject）です。
SRLG：
[RFC4202]で定義されている共有リスクリンクグループ（Shared Risk Link Group）です。
参照パス（Reference Path）：
参照パスとは、ダイバースLSPのパスがそれに対してダイバースであるべき、既存のLSPのパスのことです。
XRO：
[RFC4874]で定義されている除外経路オブジェクト（eXclude Route Object）です。

1.3. Client-Initiated Identifier

1.3. クライアント開始識別子

The following fields MUST be used to represent the client-initiated identifier: IPv4/IPv6 tunnel sender address, IPv4/IPv6 tunnel endpoint address, Tunnel ID, and Extended Tunnel ID. Based on local policy, the client MAY also include the LSP ID to identify a specific LSP within the tunnel. These fields are defined in Sections 4.6.1.1 and 4.6.2.1 of [RFC3209].

クライアント開始識別子を表すには、IPv4/IPv6トンネル送信者アドレス、IPv4/IPv6トンネルエンドポイントアドレス、Tunnel ID、Extended Tunnel IDの各フィールドを使用しなければなりません（MUST）。 ローカルポリシーに基づいて、クライアントは、トンネル内の特定のLSPを識別するためにLSP IDも含めてもよいです（MAY）。 これらのフィールドは[RFC3209]のセクション4.6.1.1と4.6.2.1で定義されています。

The usage of the client-initiated identifier is illustrated by Figure 1. Suppose an LSP from EN2 to EN4 needs to be diverse with respect to an LSP from EN1 to EN3.

クライアント開始識別子の使い方を図1を用いて説明します。 EN2からEN4へのLSPが、EN1からEN3へのLSPに対してダイバースである必要があるとします。

The LSP identifier of the EN1-EN3 LSP is LSP-IDENTIFIER1, where LSP-IDENTIFIER1 is defined by the tuple

EN1-EN3 LSPのLSP識別子はLSP-IDENTIFIER1であり、LSP-IDENTIFIER1は次のタプルで定義されます。

   (tunnel-id = T1,
   LSP ID = L1,
   source address = EN1.RID (Route Identifier),
   destination address = EN3.RID,
   extended tunnel-id = EN1.RID).

   (tunnel-id = T1,
   LSP ID = L1,
   source address = EN1.RID (Route Identifier),
   destination address = EN3.RID,
   extended tunnel-id = EN1.RID).

Similarly, the LSP identifier of the EN2-EN4 LSP is LSP-IDENTIFIER2, where LSP-IDENTIFIER2 is defined by the tuple

同様に、EN2-EN4 LSPのLSP識別子はLSP-IDENTIFIER2であり、LSP-IDENTIFIER2は次のタプルで定義されます。

   (tunnel-id = T2,
   LSP ID = L2,
   source address = EN2.RID,
   destination address = EN4.RID,
   extended tunnel-id = EN2.RID).

   (tunnel-id = T2,
   LSP ID = L2,
   source address = EN2.RID,
   destination address = EN4.RID,
   extended tunnel-id = EN2.RID).

The EN1-EN3 LSP is signaled with an exclusion requirement from LSP-IDENTIFIER2, and the EN2-EN4 LSP is signaled with an exclusion requirement from LSP-IDENTIFIER1. In order to maintain diversity between these two connections within the core network, the core network SHOULD implement crankback signaling extensions as defined in [RFC4920]. Note that crankback signaling is known to lead to slower setup times and suboptimal paths under some circumstances as described by [RFC4920].

EN1-EN3 LSPはLSP-IDENTIFIER2からの除外要件付きでシグナリングされ、EN2-EN4 LSPはLSP-IDENTIFIER1からの除外要件付きでシグナリングされます。 コアネットワーク内でこれら2つのコネクションの間のダイバーシティーを維持するために、コアネットワークは[RFC4920]で定義されているクランクバックシグナリング拡張を実装すべきです（SHOULD）。 [RFC4920]で説明されているように、クランクバックシグナリングは状況によってはセットアップ時間の増加や最適でないパスにつながることが知られている点に注意してください。

1.4. PCE-Allocated Identifier

1.4. PCE割り当て識別子

In scenarios where a PCE is deployed and used to perform path computation, typically the ingress node of the core network (e.g., node CN1 in Figure 1) could consult a PCE to allocate identifiers, which are used to signal path diversity constraints. In other deployment scenarios, a PCE is deployed at a network node(s) or it is part of a Network Management System (NMS). In all these cases, the PCE is consulted and the Path Key, as defined in [RFC5520], can be used in RSVP signaling as the identifier to ensure diversity.

PCEが展開され経路計算に使用されるシナリオでは、通常、コアネットワークの入口ノード（たとえば、図1のノードCN1）がPCEに問い合わせて識別子を割り当ててもらうことができ、その識別子はパスダイバーシティー制約をシグナリングするために使用されます。 他の展開シナリオでは、PCEはネットワークノードに展開されるか、ネットワーク管理システム（NMS）の一部となります。 これらのいずれの場合でも、PCEに問い合わせ、[RFC5520]で定義されているPath Keyを、ダイバーシティーを保証するための識別子としてRSVPシグナリングで使用できます。

An example of specifying LSP diversity using a Path Key is shown in Figure 2, where a simple network with two domains is shown. It is desired to set up a pair of path-disjoint LSPs from the source in Domain 1 to the destination in Domain 2, but the domains keep strict confidentiality about all path and topology information.

Path Keyを用いてLSPダイバーシティーを指定する例を図2に示します。図2は、2つのドメインからなる単純なネットワークを示しています。 ドメイン1の送信元からドメイン2の宛先へ、パスが互いに素な（path-disjoint）LSPのペアをセットアップしたいのですが、各ドメインはすべてのパス情報とトポロジー情報について厳格な機密性を保っています。

The first LSP is signaled by the source with ERO {A, B, loose Dst} and is set up with the path {Src, A, B, U, V, W, Dst}. However, when sending the Record Route Object (RRO) out of Domain 2, node U would normally strip the path and replace it with a loose hop to the destination. With this limited information, the source is unable to include enough detail in the ERO of the second LSP to avoid it taking, for example, the path {Src, C, D, X, V, W, Dst} for path-disjointness.

最初のLSPは、送信元によってERO {A, B, loose Dst}でシグナリングされ、パス{Src, A, B, U, V, W, Dst}でセットアップされます。 しかし、ドメイン2から記録経路オブジェクト（Record Route Object：RRO）を送出する際、ノードUは通常、パスを取り除いて宛先への緩いホップに置き換えます。 この限られた情報では、送信元は、パスを互いに素にするために2番目のLSPがたとえばパス{Src, C, D, X, V, W, Dst}をとるのを避けるのに十分な詳細を、2番目のLSPのEROに含めることができません。

In order to support LSP diversity, node U consults the PCE and replaces the path segment {U, V, W} in the RRO with a Path Key subobject. The PCE function assigns an "identifier" and puts it into the Path Key field of the Path Key subobject. The PCE ID in the message indicates that this replacement operation was performed by node U.

LSPダイバーシティーをサポートするために、ノードUはPCEに問い合わせ、RRO内のパスセグメント{U, V, W}をPath Keyサブオブジェクトに置き換えます。 PCE機能は「識別子」を割り当て、それをPath KeyサブオブジェクトのPath Keyフィールドに入れます。 メッセージ内のPCE IDは、この置き換え操作がノードUによって行われたことを示します。

With this additional information, the source node is able to signal the subsequent LSPs with the ERO set to {C, D, exclude Path Key (signaled in the EXRS RSVP subobject), loose Dst}. When the signaling message reaches node X, it can consult the PCE function associated with node U to expand the Path Key in order to calculate a path that is diverse with respect to the first LSP. Alternatively, the source node could use an ERO of {C, D, loose Dst} and include an XRO containing the Path Key.

この追加情報があれば、送信元ノードは、EROを{C, D, exclude Path Key（EXRS RSVPサブオブジェクトでシグナリングされる）, loose Dst}に設定して後続のLSPをシグナリングできます。 シグナリングメッセージがノードXに到達すると、ノードXは、最初のLSPに対してダイバースなパスを計算するために、ノードUに関連付けられたPCE機能に問い合わせてPath Keyを展開できます。 あるいは、送信元ノードは{C, D, loose Dst}というEROを使用し、Path Keyを含むXROを含めることもできます。

This mechanism can work with all the Path Key resolution mechanisms, as detailed in Section 3.1 of [RFC5553]. A PCE, co-located or not, may be used to resolve the Path Key, but the node (i.e., a Label Switching Router (LSR)) can also use the Path Key information to index a path segment previously supplied to it by the entity that originated the Path Key (for example, the LSR that inserted the Path Key in the RRO or a management system).

このメカニズムは、[RFC5553]のセクション3.1で詳しく説明されているすべてのPath Key解決メカニズムと連携できます。 Path Keyの解決には、同じ場所に配置されているかどうかにかかわらずPCEを使用できますが、ノード（すなわち、ラベルスイッチングルーター（LSR））は、Path Keyを生成したエンティティー（たとえば、RROにPath Keyを挿入したLSRや管理システム）から以前に提供されたパスセグメントを索引付けるためにPath Key情報を使用することもできます。

1.5. Network-Assigned Identifier

1.5. ネットワーク割り当て識別子

There are scenarios in which the network provides diversity-related information for a service that allows the client device to include this information in the signaling message. If the Shared Risk Link Group (SRLG) identifier information is both available and shareable (by policy) with the ENs, the procedure defined in [RFC8001] can be used to collect SRLG identifiers associated with an LSP (LSP1). When a second LSP (LSP2) needs to be diverse with respect to LSP1, the EN constructing the RSVP signaling message for setting up LSP2 can insert the SRLG identifiers associated with LSP1 as diversity constraints into the XRO using the procedure described in [RFC4874]. However, if the core network SRLG identifiers are either not available or not shareable with the ENs based on policies enforced by the core network, existing mechanisms cannot be used.

ネットワークがサービスについてダイバーシティー関連の情報を提供し、クライアントデバイスがこの情報をシグナリングメッセージに含められるようにするシナリオがあります。 共有リスクリンクグループ（SRLG）識別子の情報が利用可能であり、かつ（ポリシー上）ENと共有可能である場合、[RFC8001]で定義されている手順を使用して、あるLSP（LSP1）に関連付けられたSRLG識別子を収集できます。 2番目のLSP（LSP2）がLSP1に対してダイバースである必要がある場合、LSP2をセットアップするためのRSVPシグナリングメッセージを構築するENは、[RFC4874]で説明されている手順を使用して、LSP1に関連付けられたSRLG識別子をダイバーシティー制約としてXROに挿入できます。 しかし、コアネットワークのSRLG識別子が利用できない場合や、コアネットワークが適用するポリシーに基づいてENと共有できない場合には、既存のメカニズムを使用できません。

In this document, a signaling mechanism is defined where information signaled to the CN via the UNI does not require shared knowledge of core network SRLG information. For this purpose, the concept of a Path Affinity Set (PAS) is defined for abstracting SRLG information. The motive behind the introduction of the PAS is to minimize the exchange of diversity information between the core network (CNs) and the client devices (ENs). The PAS contains an abstract SRLG identifier associated with a given path rather than a detailed SRLG list. The PAS is a single identifier that can be used to request diversity and associate diversity. The means by which the processing node determines the path corresponding to the PAS is beyond the scope of this document.

この文書では、UNIを介してCNにシグナリングされる情報が、コアネットワークのSRLG情報の共有知識を必要としないシグナリングメカニズムを定義します。 この目的のために、SRLG情報を抽象化するためのパスアフィニティーセット（Path Affinity Set：PAS）という概念を定義します。 PASを導入する動機は、コアネットワーク（CN）とクライアントデバイス（EN）の間のダイバーシティー情報のやり取りを最小限にすることです。 PASは、詳細なSRLGリストではなく、あるパスに関連付けられた抽象的なSRLG識別子を含みます。 PASは、ダイバーシティーを要求したりダイバーシティーを関連付けたりするために使用できる単一の識別子です。 処理ノードがPASに対応するパスを決定する手段は、この文書の範囲外です。

A CN on the core network boundary interprets the specific PAS identifier (e.g., "123") as meaning to exclude the core network SRLG information (or equivalent) that has been allocated by LSPs associated with this PAS identifier value. For example, if a path exists for the LSP with the PAS identifier "123", the CN would use local knowledge of the core network SRLGs associated with the LSPs tagged with PAS attribute "123" and use those SRLGs as constraints for path computation. If a PAS identifier is used as an exclusion identifier in the connection request, the CN (UNI-N) in the core network is assumed to be able to determine the existing core network SRLG information and calculate a path that meets the determined diversity constraints.

コアネットワークの境界にあるCNは、特定のPAS識別子（たとえば「123」）を、このPAS識別子の値に関連付けられたLSPによって割り当てられたコアネットワークのSRLG情報（またはそれに相当するもの）を除外するという意味に解釈します。 たとえば、PAS識別子「123」を持つLSPのパスが存在する場合、CNは、PAS属性「123」でタグ付けされたLSPに関連付けられたコアネットワークのSRLGについてのローカルな知識を用い、それらのSRLGを経路計算の制約として使用します。 PAS識別子がコネクションリクエスト内で除外識別子として使用される場合、コアネットワーク内のCN（UNI-N）は、既存のコアネットワークのSRLG情報を特定し、特定したダイバーシティー制約を満たすパスを計算できるものと想定します。

When a CN satisfies a connection setup for an SRLG-diverse signaled path, the CN may optionally record the core network SRLG information for that connection in terms of CN-based parameters and associate that with the EN addresses in the Path message. Specifically, for Layer 1 Virtual Private Networks (L1VPNs), Port Information Tables (PITs) [RFC5251] can be leveraged to translate between client (EN) addresses and core network addresses.

CNがSRLGダイバースとしてシグナリングされたパスのコネクションセットアップを満たす場合、CNは任意で、そのコネクションのコアネットワークのSRLG情報をCNベースのパラメーターの形で記録し、それをPathメッセージ内のENのアドレスに関連付けてもかまいません。 具体的には、レイヤー1仮想プライベートネットワーク（L1VPN）の場合、クライアント（EN）のアドレスとコアネットワークのアドレスの間の変換に、ポート情報テーブル（PIT）[RFC5251]を活用できます。

The means to distribute the PAS information within the core network is beyond the scope of this document. For example, the PAS and the associated SRLG information can be distributed within the core network by an Interior Gateway Protocol (IGP) or by other means such as configuration. Regardless of means used to distribute the PAS information, the information is kept inside the core network and is not shared with the overlay network (see Figure 1).

コアネットワーク内でPAS情報を配布する手段は、この文書の範囲外です。 たとえば、PASと関連するSRLG情報は、内部ゲートウェイプロトコル（IGP）や、設定などの他の手段によってコアネットワーク内に配布できます。 PAS情報を配布する手段にかかわらず、その情報はコアネットワーク内にとどめられ、オーバーレイネットワークとは共有されません（図1を参照）。

Diversity Identifier Type（DI Type）は、ダイバーシティーが求められる参照LSPまたは経路を、IPv4/IPv6 Diversityサブオブジェクト内でどのように識別するかを示します。 この文書では、次の3つのDI Type値を定義します。

表1
DI Type値 定義
1 Client-Initiated Identifier
2 PCE-Allocated Identifier
3 Network-Assigned Identifier
属性フラグ（A-Flags）：

属性フラグ（A-Flags）は、IPv4/IPv6 Diversityサブオブジェクトにおいて、シグナリングされるLSPの望ましい属性を伝達するために使用されます。 各フラグは独立して作用します。 フラグはどのように組み合わせてもかまいません。

0x01 = Destination node exception（宛先ノード例外）
シグナリングされるLSPの宛先ノードには除外が適用されないことを示します。
0x02 = Processing node exception（処理ノード例外）
シグナリングされるLSPのEROの展開を行うノードには除外が適用されないことを示します。 入口のUNI-Nノードは、そのようなノードの一例です。
0x04 = Penultimate node exception（最後から2番目のノードの例外）

シグナリングされるLSPの最後から2番目のノードについて、除外フラグに反する場合であっても除外対象のパスと共有してもよいです（MAY）ということを示します。 このフラグは、たとえば、ENがデュアルホームではない場合（すべてのLSPがCN5を通過しなければならない、図1のEN4のような場合）に役立ちます。

「Penultimate node exception」フラグは、通常、宛先ノードがシングルホームである場合（たとえば、図2のEN1やEN4）に設定されます。 そのような場合、LSPダイバーシティーはコアネットワーク内の出口ノードまでしか実現できず、最後から2番目のホップはそれらのLSPで同じでなければなりません。

0x08 = LSP ID to be ignored（LSP IDを無視する）
このフラグは、トンネルレベルの除外を示すために使用されます。 具体的には、このフラグは、ダイバーシティー識別子にLSP IDフィールドが含まれている場合にはそのLSP IDを無視し、ダイバーシティー識別子の残りの部分に一致するあらゆるLSPに除外を適用することを示すために使用されます。
除外フラグ（E-Flags）：

除外フラグは、IPv4/IPv6 Diversityサブオブジェクトで要求する除外の望ましい種類を伝達するために使用されます。 次のフラグを定義します。 これらのフラグはどのように組み合わせてもかまいません。 これらのフラグで指定された除外は、A-Flagsの値によって変更される場合がある点に注意してください。 たとえば、A-Flagsの「Penultimate node exception」フラグが設定されている場合、最後から2番目のノードについてはノード除外フラグは無視されます。

0x01 = SRLG exclusion（SRLG除外）
シグナリングされるLSPのパスが、IPv4/IPv6 Diversity XROサブオブジェクトで指定された除外対象のパスに対してSRLGが互いに素であることを要求することを示します。
0x02 = Node exclusion（ノード除外）
シグナリングされるLSPのパスが、IPv4/IPv6 Diversity XROサブオブジェクトで指定された除外対象のパスに対して「ノードダイバース」であることを要求することを示します。
0x04 = Link exclusion（リンク除外）
シグナリングされるLSPのパスが、IPv4/IPv6 Diversity XROサブオブジェクトで指定されたパスに対して「リンクダイバース」であることを要求することを示します。
0x08 = Reserved（予約済み）
このフラグは予約済みです。 IPv4/IPv6のどちらのDiversity XROサブオブジェクトでも、このフラグは送信時にゼロに設定しなければなりません（MUST）。 また、受信時には無視しなければなりません（MUST）。
Resvd：
このフィールドは予約済みです。 IPv4/IPv6のどちらのDiversity XROサブオブジェクトでも、このフィールドは送信時にゼロに設定しなければなりません（MUST）。 また、受信時には無視しなければなりません（MUST）。
IPv4/IPv6 Diversity Identifier Source Address：

このフィールドは、ダイバーシティー識別子を割り当てるノードのIPv4/IPv6アドレスに設定しなければなりません（MUST）。 Diversity Identifier Typeに応じて、ダイバーシティー識別子の送信元は、クライアントノード、PCEエンティティー、ネットワークノードのいずれかとなります。 具体的には次のとおりです。

  • Diversity Identifier Typeが「Client-Initiated Identifier」に設定されている場合、値は、ダイバーシティーが求められる参照LSPのIPv4/IPv6トンネル送信者アドレスに設定しなければなりません（MUST）。 IPv4/IPv6トンネル送信者アドレスは[RFC3209]で定義されているとおりです。

  • Diversity Identifier Typeが「Network-Assigned Identifier」に設定されている場合、値は、パスアフィニティーセット（PAS）を割り当てるノードのIPv4/IPv6アドレスに設定しなければなりません（MUST）。

2.2. Diversity EXRS Subobject

2.2. Diversity EXRSサブオブジェクト

[RFC4874] defines the EXRS ERO subobject. An EXRS is used to identify abstract nodes or resources that must not or should not be used on the path between two inclusive abstract nodes or resources in the explicit route. An EXRS contains one or more subobjects of its own, called EXRS subobjects [RFC4874].

[RFC4874]は、EXRS EROサブオブジェクトを定義しています。 EXRSは、明示的経路内の2つの包含される抽象ノードまたはリソースの間のパス上で、使用してはならない、または使用すべきでない抽象ノードやリソースを識別するために使用されます。 EXRSは、EXRSサブオブジェクトと呼ばれる独自のサブオブジェクトを1つ以上含みます[RFC4874]。

An EXRS MAY include a Diversity subobject as specified in this document. The same type values 38 and 39 MUST be used.

EXRSは、この文書で規定するDiversityサブオブジェクトを含めてもよいです（MAY）。 その場合、同じタイプ値38と39を使用しなければなりません（MUST）。

2.3. Processing Rules for the Diversity XRO and EXRS Subobjects

2.3. Diversity XROサブオブジェクトとDiversity EXRSサブオブジェクトの処理規則

The procedure defined in [RFC4874] for processing the XRO and EXRS is not changed by this document. The processing rules for the Diversity XRO and EXRS subobjects are similar unless the differences are explicitly described. Similarly, IPv4 and IPv6 Diversity XRO subobjects and IPv4 and IPv6 Diversity EXRS subobjects follow the same processing rules.

[RFC4874]で定義されているXROとEXRSを処理する手順は、この文書によって変更されません。 Diversity XROサブオブジェクトとDiversity EXRSサブオブジェクトの処理規則は、違いを明示的に説明している場合を除いて同様です。 同様に、IPv4とIPv6のDiversity XROサブオブジェクト、およびIPv4とIPv6のDiversity EXRSサブオブジェクトは、同じ処理規則に従います。

If the processing node cannot recognize the Diversity XRO/EXRS subobject, the node is expected to follow the procedure defined in [RFC4874].

処理ノードがDiversity XRO/EXRSサブオブジェクトを認識できない場合、そのノードは[RFC4874]で定義されている手順に従うことが期待されます。

An XRO/EXRS object MAY contain multiple Diversity subobjects of the same DI Type. For example, in order to exclude multiple Path Keys, a node MAY include multiple Diversity XRO subobjects, each with a different Path Key. Similarly, in order to exclude the routes taken by multiple LSPs, a node MAY include multiple Diversity XRO/EXRS subobjects, each with a different LSP identifier. Likewise, to exclude multiple PAS identifiers, a node MAY include multiple Diversity XRO/EXRS subobjects, each with a different PAS identifier. However, all Diversity subobjects in an XRO/EXRS MUST contain the same Diversity Identifier Type. If a Path message contains an XRO/EXRS with multiple Diversity subobjects of different DI Types, the processing node MUST return a PathErr with the error code "Routing Problem" (24) and error sub-code "XRO/EXRS Too Complex" (68/69).

XRO/EXRSオブジェクトは、同じDI Typeの複数のDiversityサブオブジェクトを含めてもよいです（MAY）。 たとえば、複数のPath Keyを除外するために、ノードは、それぞれ異なるPath Keyを持つ複数のDiversity XROサブオブジェクトを含めてもよいです（MAY）。 同様に、複数のLSPがたどる経路を除外するために、ノードは、それぞれ異なるLSP識別子を持つ複数のDiversity XRO/EXRSサブオブジェクトを含めてもよいです（MAY）。 同じように、複数のPAS識別子を除外するために、ノードは、それぞれ異なるPAS識別子を持つ複数のDiversity XRO/EXRSサブオブジェクトを含めてもよいです（MAY）。 ただし、XRO/EXRS内のすべてのDiversityサブオブジェクトは、同じDiversity Identifier Typeを含まなければなりません（MUST）。 Pathメッセージに、異なるDI Typeの複数のDiversityサブオブジェクトを持つXRO/EXRSが含まれている場合、処理ノードは、エラーコード「Routing Problem」（24）とエラーサブコード「XRO/EXRS Too Complex」（68/69）を指定したPathErrを返さなければなりません（MUST）。

If the processing node recognizes the Diversity XRO/EXRS subobject but does not support the DI Type, it MUST return a PathErr with the error code "Routing Problem" (24) and error sub-code "Unsupported Diversity Identifier Type" (36).

処理ノードがDiversity XRO/EXRSサブオブジェクトを認識するものの、そのDI Typeをサポートしていない場合、処理ノードは、エラーコード「Routing Problem」（24）とエラーサブコード「Unsupported Diversity Identifier Type」（36）を指定したPathErrを返さなければなりません（MUST）。

In the case of DI Type "Client-Initiated Identifier", all nodes along the path SHOULD process the diversity information signaled in the XRO/EXRS Diversity subobjects to verify that the signaled diversity constraint is satisfied. If a diversity violation is detected, crankback signaling MAY be initiated.

DI Typeが「Client-Initiated Identifier」の場合、パス上のすべてのノードは、XRO/EXRS Diversityサブオブジェクトでシグナリングされたダイバーシティー情報を処理し、シグナリングされたダイバーシティー制約が満たされていることを検証すべきです（SHOULD）。 ダイバーシティー違反が検出された場合、クランクバックシグナリングを開始してもよいです（MAY）。

In the case of DI Type "PCE-Allocated Identifier" and "Network-Assigned Identifier", the nodes in the domain that perform path computation SHOULD process the diversity information signaled in the XRO/EXRS Diversity subobjects as follows. In the PCE case, the ingress node of a domain sends a path computation request for a path from ingress node to egress node, including diversity constraints to a PCE. Or, in the PAS case, the ingress node is capable of calculating the path for the new LSP from ingress node to the egress node, taking the diversity constraints into account. The calculated path is then carried in the Explicit Route Object (ERO). Hence, the transit nodes in a domain and the domain egress node SHOULD NOT process the signaled diversity information unless path computation is performed.

DI Typeが「PCE-Allocated Identifier」または「Network-Assigned Identifier」の場合、経路計算を行うドメイン内のノードは、XRO/EXRS Diversityサブオブジェクトでシグナリングされたダイバーシティー情報を次のように処理すべきです（SHOULD）。 PCEの場合、ドメインの入口ノードは、入口ノードから出口ノードへのパスについて、ダイバーシティー制約を含む経路計算リクエストをPCEに送信します。 あるいはPASの場合、入口ノードは、ダイバーシティー制約を考慮に入れて、入口ノードから出口ノードまでの新しいLSPのパスを計算できます。 計算されたパスは、明示的経路オブジェクト（ERO）で運ばれます。 したがって、ドメイン内のトランジットノードとドメインの出口ノードは、経路計算を行う場合を除いて、シグナリングされたダイバーシティー情報を処理すべきではありません（SHOULD NOT）。

While processing the EXRS object, if a loose hop expansion results in the creation of another loose hop in the outgoing ERO, the processing node MAY include the EXRS in the newly created loose hop for further processing by downstream nodes.

EXRSオブジェクトの処理中に、緩いホップの展開によって送出するERO内に別の緩いホップが作成される場合、処理ノードは、下流ノードでさらに処理されるように、新しく作成された緩いホップにEXRSを含めてもよいです（MAY）。

The A-Flags affect the processing of the Diversity XRO/EXRS subobject as follows:

A-Flagsは、Diversity XRO/EXRSサブオブジェクトの処理に次のように影響します。

  • When the "Processing node exception" flag is set, the exclusion MUST be ignored for the node processing the XRO or EXRS subobject.
  • When the "Destination node exception" flag is set, the exclusion MUST be ignored for the destination node in processing the XRO subobject. The destination node exception for the EXRS subobject applies to the explicit node identified by the ERO subobject that identifies the next abstract node. When the "Destination node exception" flag is set in the EXRS subobject, exclusion MUST be ignored for said node (i.e., the next abstract node).

  • When the "Penultimate node exception" flag is set in the XRO subobject, the exclusion MUST be ignored for the penultimate node on the path of the LSP being established.

    The penultimate node exception for the EXRS subobject applies to the node before the explicit node identified by the ERO subobject that identifies the next abstract node. When the "Penultimate node exception" flag is set in the EXRS subobject, the exclusion MUST be ignored for said node (i.e., the node before the next abstract node).

  • 「Processing node exception」フラグが設定されている場合、XROまたはEXRSサブオブジェクトを処理するノードについては除外を無視しなければなりません（MUST）。
  • 「Destination node exception」フラグが設定されている場合、XROサブオブジェクトの処理において、宛先ノードについては除外を無視しなければなりません（MUST）。 EXRSサブオブジェクトに対する宛先ノード例外は、次の抽象ノードを識別するEROサブオブジェクトによって識別される明示的ノードに適用されます。 EXRSサブオブジェクトで「Destination node exception」フラグが設定されている場合、当該ノード（すなわち、次の抽象ノード）については除外を無視しなければなりません（MUST）。

  • XROサブオブジェクトで「Penultimate node exception」フラグが設定されている場合、確立されるLSPのパス上の最後から2番目のノードについては除外を無視しなければなりません（MUST）。

    EXRSサブオブジェクトに対する最後から2番目のノードの例外は、次の抽象ノードを識別するEROサブオブジェクトによって識別される明示的ノードの1つ手前のノードに適用されます。 EXRSサブオブジェクトで「Penultimate node exception」フラグが設定されている場合、当該ノード（すなわち、次の抽象ノードの1つ手前のノード）については除外を無視しなければなりません（MUST）。

If the L-flag of the Diversity XRO subobject or Diversity EXRS subobject is not set, the processing node proceeds as follows.

Diversity XROサブオブジェクトまたはDiversity EXRSサブオブジェクトのLフラグが設定されていない場合、処理ノードは次のように処理を進めます。

  • If the Diversity Identifier Type is set to "Client-Initiated Identifier", the processing node MUST ensure that the path calculated/expanded for the signaled LSP is diverse from the route taken by the LSP identified in the Diversity Identifier Value field.
  • If the Diversity Identifier Type is set to "PCE-Allocated Identifier", the processing node MUST ensure that any path calculated for the signaled LSP is diverse from the route identified by the Path Key. The processing node MAY use the PCE identified by the Diversity Identifier Source Address in the subobject for route computation. The processing node MAY use the Path Key resolution mechanisms described in [RFC5553].
  • If the Diversity Identifier Type is set to "Network-Assigned Identifier", the processing node MUST ensure that the path calculated for the signaled LSP is diverse with respect to the values associated with the PAS Identifier and Diversity Identifier Source Address fields.
  • Regardless of whether the path computation is performed locally or at a remote node (e.g., PCE), the processing node MUST ensure that any path calculated for the signaled LSP is diverse from the requested Exclusion Flags.
  • If the excluded path referenced in the XRO subobject is unknown to the processing node, the processing node SHOULD ignore the Diversity XRO subobject and SHOULD proceed with the signaling request. After sending the Resv for the signaled LSP, the processing node MUST return a PathErr with the error code "Notify Error" (25) and error sub-code "Route of XRO LSP identifier unknown" (14) for the signaled LSP.
  • If the processing node fails to find a path that meets the requested constraint, the processing node MUST return a PathErr with the error code "Routing Problem" (24) and error sub-code "Route blocked by Exclude Route" (67).
  • Diversity Identifier Typeが「Client-Initiated Identifier」に設定されている場合、処理ノードは、シグナリングされるLSPについて計算・展開したパスが、Diversity Identifier Valueフィールドで識別されるLSPがたどる経路に対してダイバースであることを保証しなければなりません（MUST）。
  • Diversity Identifier Typeが「PCE-Allocated Identifier」に設定されている場合、処理ノードは、シグナリングされるLSPについて計算するいかなるパスも、Path Keyで識別される経路に対してダイバースであることを保証しなければなりません（MUST）。 処理ノードは、経路計算のために、サブオブジェクト内のDiversity Identifier Source Addressで識別されるPCEを使用してもよいです（MAY）。 処理ノードは、[RFC5553]で説明されているPath Key解決メカニズムを使用してもよいです（MAY）。
  • Diversity Identifier Typeが「Network-Assigned Identifier」に設定されている場合、処理ノードは、シグナリングされるLSPについて計算したパスが、PAS IdentifierフィールドとDiversity Identifier Source Addressフィールドに関連付けられた値に対してダイバースであることを保証しなければなりません（MUST）。
  • 経路計算がローカルで行われるかリモートノード（たとえば、PCE）で行われるかにかかわらず、処理ノードは、シグナリングされるLSPについて計算するいかなるパスも、要求された除外フラグに従ってダイバースであることを保証しなければなりません（MUST）。
  • XROサブオブジェクトで参照されている除外対象のパスが処理ノードにとって未知である場合、処理ノードはDiversity XROサブオブジェクトを無視すべきです（SHOULD）。 そして、シグナリングリクエストの処理を進めるべきです（SHOULD）。 シグナリングされたLSPについてResvを送信した後、処理ノードは、シグナリングされたLSPについて、エラーコード「Notify Error」（25）とエラーサブコード「Route of XRO LSP identifier unknown」（14）を指定したPathErrを返さなければなりません（MUST）。
  • 要求された制約を満たすパスを処理ノードが見つけられない場合、処理ノードは、エラーコード「Routing Problem」（24）とエラーサブコード「Route blocked by Exclude Route」（67）を指定したPathErrを返さなければなりません（MUST）。

If the L-flag of the Diversity XRO subobject or Diversity EXRS subobject is set, the processing node proceeds as follows:

Diversity XROサブオブジェクトまたはDiversity EXRSサブオブジェクトのLフラグが設定されている場合、処理ノードは次のように処理を進めます。

  • If the Diversity Identifier Type is set to "Client-Initiated Identifier", the processing node SHOULD ensure that the path calculated/expended for the signaled LSP is diverse from the route taken by the LSP identified in the Diversity Identifier Value field.
  • If the Diversity Identifier Type is set to "PCE-Allocated Identifier", the processing node SHOULD ensure that the path calculated for the signaled LSP is diverse from the route identified by the Path Key.
  • If the Diversity Identifier Type is set to "Network-Assigned Identifier", the processing node SHOULD ensure that the path calculated for the signaled LSP is diverse with respect to the values associated with the PAS Identifier and Diversity Identifier Source Address fields.
  • If the processing node fails to find a path that meets the requested constraint, it SHOULD proceed with signaling using a suitable path that meets the constraint as far as possible. After sending the Resv for the signaled LSP, it MUST return a PathErr message with error code "Notify Error" (25) and error sub-code "Failed to satisfy Exclude Route" (15) to the source node.
  • Diversity Identifier Typeが「Client-Initiated Identifier」に設定されている場合、処理ノードは、シグナリングされるLSPについて計算・展開したパスが、Diversity Identifier Valueフィールドで識別されるLSPがたどる経路に対してダイバースであることを保証すべきです（SHOULD）。
  • Diversity Identifier Typeが「PCE-Allocated Identifier」に設定されている場合、処理ノードは、シグナリングされるLSPについて計算したパスが、Path Keyで識別される経路に対してダイバースであることを保証すべきです（SHOULD）。
  • Diversity Identifier Typeが「Network-Assigned Identifier」に設定されている場合、処理ノードは、シグナリングされるLSPについて計算したパスが、PAS IdentifierフィールドとDiversity Identifier Source Addressフィールドに関連付けられた値に対してダイバースであることを保証すべきです（SHOULD）。
  • 要求された制約を満たすパスを処理ノードが見つけられない場合、処理ノードは、制約を可能な限り満たす適切なパスを使用してシグナリングを進めるべきです（SHOULD）。 シグナリングされたLSPについてResvを送信した後、処理ノードは、エラーコード「Notify Error」（25）とエラーサブコード「Failed to satisfy Exclude Route」（15）を指定したPathErrメッセージを送信元ノードに返さなければなりません（MUST）。

If, subsequent to the initial signaling of a diverse LSP, an excluded path referenced in the XRO subobject becomes known to the processing node or a change in the excluded path becomes known to the processing node, the processing node MUST re-evaluate the exclusion and diversity constraints requested by the diverse LSP to determine whether they are still satisfied.

ダイバースLSPの最初のシグナリングの後で、XROサブオブジェクトで参照されている除外対象のパスが処理ノードにとって既知になった場合、または除外対象のパスの変更が処理ノードに判明した場合、処理ノードは、ダイバースLSPが要求する除外制約とダイバーシティー制約を再評価して、それらがまだ満たされているかどうかを判断しなければなりません（MUST）。

  • In the case where the L-flag was not set in the initial setup message, the exclusion and diversity constraints were satisfied at the time of the initial setup. If the processing node re-evaluating the exclusion and diversity constraints for a diverse LSP detects that the exclusion and diversity constraints are no longer met, it MUST send a PathErr message for the diverse LSP with the error code "Routing Problem" (24) and error sub-code "Route blocked by Exclude Route" (67). The Path_State_Removed (PSR) flag [RFC3473] MUST NOT be set. A source node receiving a PathErr message with this error code and sub-code combination SHOULD take appropriate actions and move the diverse LSP to a new path that meets the original constraints.
  • In the case where the L-flag was set in the initial setup message, the exclusion and diversity constraints may or may not be satisfied at any given time. If the exclusion constraints for a diverse LSP were satisfied before, and if the processing node re-evaluating the exclusion and diversity constraints for a diverse LSP detects that exclusion and diversity constraints are no longer met, it MUST send a PathErr message for the diverse LSP with the error code "Notify Error" (25) and error sub-code "Failed to satisfy Exclude Route" (15). The PSR flag MUST NOT be set. The source node MAY take no consequent action and keep the LSP along the path that does not meet the original constraints. Similarly, if the exclusion constraints for a diverse LSP were not satisfied before, and if the processing node re-evaluating the exclusion and diversity constraints for a diverse LSP detects that the exclusion constraints are met, it MUST send a PathErr message for the diverse LSP with the error code "Notify Error" (25) and a new error sub-code "Compliant path exists" (16). The PSR flag MUST NOT be set. A source node receiving a PathErr message with this error code and sub-code combination MAY move the diverse LSP to a new path that meets the original constraints.
  • 最初のセットアップメッセージでLフラグが設定されていなかった場合、最初のセットアップの時点では除外制約とダイバーシティー制約は満たされていました。 ダイバースLSPの除外制約とダイバーシティー制約を再評価している処理ノードが、除外制約とダイバーシティー制約がもはや満たされていないことを検出した場合、処理ノードは、そのダイバースLSPについて、エラーコード「Routing Problem」（24）とエラーサブコード「Route blocked by Exclude Route」（67）を指定したPathErrメッセージを送信しなければなりません（MUST）。 Path_State_Removed（PSR）フラグ[RFC3473]を設定してはなりません（MUST NOT）。 このエラーコードとサブコードの組み合わせのPathErrメッセージを受信した送信元ノードは、適切な措置をとり、ダイバースLSPを元の制約を満たす新しいパスに移すべきです（SHOULD）。
  • 最初のセットアップメッセージでLフラグが設定されていた場合、除外制約とダイバーシティー制約は、どの時点においても満たされている場合も満たされていない場合もあります。 ダイバースLSPの除外制約が以前は満たされていて、ダイバースLSPの除外制約とダイバーシティー制約を再評価している処理ノードが、除外制約とダイバーシティー制約がもはや満たされていないことを検出した場合、処理ノードは、そのダイバースLSPについて、エラーコード「Notify Error」（25）とエラーサブコード「Failed to satisfy Exclude Route」（15）を指定したPathErrメッセージを送信しなければなりません（MUST）。 PSRフラグを設定してはなりません（MUST NOT）。 送信元ノードは、それに伴う措置を何もとらずに、元の制約を満たさないパスに沿ってLSPを維持してもよいです（MAY）。 同様に、ダイバースLSPの除外制約が以前は満たされておらず、ダイバースLSPの除外制約とダイバーシティー制約を再評価している処理ノードが、除外制約が満たされていることを検出した場合、処理ノードは、そのダイバースLSPについて、エラーコード「Notify Error」（25）と新しいエラーサブコード「Compliant path exists」（16）を指定したPathErrメッセージを送信しなければなりません（MUST）。 PSRフラグを設定してはなりません（MUST NOT）。 このエラーコードとサブコードの組み合わせのPathErrメッセージを受信した送信元ノードは、ダイバースLSPを元の制約を満たす新しいパスに移してもよいです（MAY）。

3. Security Considerations

3. セキュリティーに関する考慮事項

This document does not introduce any additional security issues in addition to those identified in [RFC5920], [RFC2205], [RFC3209], [RFC3473], [RFC2747], [RFC4874], [RFC5520], and [RFC5553].

この文書は、[RFC5920]、[RFC2205]、[RFC3209]、[RFC3473]、[RFC2747]、[RFC4874]、[RFC5520]、[RFC5553]で特定されているもの以外に、追加のセキュリティー上の問題を持ち込みません。

The diversity mechanisms defined in this document rely on the new diversity subobject that is carried in the XRO or EXRS, respectively. In Section 7 of [RFC4874], it is noted that some administrative boundaries may remove the XRO due to security concerns on explicit route information exchange. However, when the diversity subobjects specified in this document are used, removing at the administrative boundary an XRO containing these diversity subobjects would result in the request for diversity being dropped at the boundary, and path computation would be unlikely to produce the requested diverse path. As such, diversity subobjects MUST be retained in an XRO crossing an administrative boundary, even if other subobjects are removed. This retention would be based on operator policy. The use of diversity subobjects is based on mutual agreement. This avoids the need to share the identity of network resources when supporting diversity.

この文書で定義するダイバーシティーメカニズムは、それぞれXROまたはEXRSで運ばれる新しいダイバーシティーサブオブジェクトに依存しています。 [RFC4874]のセクション7では、明示的経路情報のやり取りに関するセキュリティー上の懸念から、一部の管理境界ではXROを取り除く場合があると述べられています。 しかし、この文書で規定するダイバーシティーサブオブジェクトが使用されている場合、これらのダイバーシティーサブオブジェクトを含むXROを管理境界で取り除くと、ダイバーシティーの要求が境界で失われることになり、経路計算によって要求されたダイバースなパスが得られる可能性は低くなります。 そのため、管理境界を越えるXROでは、他のサブオブジェクトが取り除かれる場合であっても、ダイバーシティーサブオブジェクトは保持しなければなりません（MUST）。 この保持は運用者のポリシーに基づくことになります。 ダイバーシティーサブオブジェクトの使用は、相互の合意に基づきます。 これにより、ダイバーシティーをサポートする際にネットワークリソースの識別情報を共有する必要がなくなります。
