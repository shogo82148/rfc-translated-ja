RFC 7804

Salted Challenge Response HTTP Authentication Mechanism

RFC 7804

ソルト付きチャレンジレスポンスHTTP認証メカニズム

Abstract

概要

This specification describes a family of HTTP authentication mechanisms called the Salted Challenge Response Authentication Mechanism (SCRAM), which provides a more robust authentication mechanism than a plaintext password protected by Transport Layer Security (TLS) and avoids the deployment obstacles presented by earlier TLS-protected challenge response authentication mechanisms.

この仕様は、ソルト付きチャレンジレスポンス認証メカニズム（Salted Challenge Response Authentication Mechanism：SCRAM）と呼ばれるHTTP認証メカニズムのファミリーを記述します。SCRAMは、トランスポート層セキュリティー（TLS）で保護された平文パスワードよりも堅牢な認証メカニズムを提供し、TLSで保護された従来のチャレンジレスポンス認証メカニズムが抱えていた展開上の障害を回避します。

1. Introduction

1. はじめに

The authentication mechanism most widely deployed and used by Internet application protocols is the transmission of clear-text passwords over a channel protected by Transport Layer Security (TLS). There are some significant security concerns with that mechanism, which could be addressed by the use of a challenge response authentication mechanism protected by TLS. Unfortunately, the HTTP Digest challenge response mechanism presently on the Standards Track failed widespread deployment and has had only limited success.

インターネットのアプリケーションプロトコルで最も広く展開され使用されている認証メカニズムは、トランスポート層セキュリティー（TLS）で保護されたチャネル上で平文のパスワードを送信するものです。このメカニズムにはセキュリティー上の重大な懸念がいくつかあり、それらはTLSで保護されたチャレンジレスポンス認証メカニズムを使用することで対処できる可能性があります。残念ながら、現在標準化過程にあるHTTP Digestチャレンジレスポンスメカニズムは広く展開されることがなく、限られた成功しか収めていません。

This specification describes a family of authentication mechanisms called the Salted Challenge Response Authentication Mechanism (SCRAM), which addresses the requirements necessary to deploy a challenge response mechanism more widely than past attempts (see [RFC5802]). In particular, it addresses some of the issues identified with HTTP Digest, as described in [RFC6331], such as the complexity of implementation and protection of the whole authentication exchange in order to protect against certain man-in-the-middle attacks.

この仕様は、ソルト付きチャレンジレスポンス認証メカニズム（Salted Challenge Response Authentication Mechanism：SCRAM）と呼ばれる認証メカニズムのファミリーを記述します。SCRAMは、チャレンジレスポンスメカニズムを過去の試みよりも広く展開するために必要な要件に対処します（[RFC5802]を参照）。特に、[RFC6331]で説明されているHTTP Digestで指摘された問題のいくつか、たとえば実装の複雑さや、ある種の中間者攻撃から守るための認証交換全体の保護に対処します。

HTTP SCRAM is an adaptation of [RFC5802] for use in HTTP. The SCRAM data exchanged is identical to what is defined in [RFC5802]. This document also adds a 1 round-trip reauthentication mode.

HTTP SCRAMは、[RFC5802]をHTTPで使用するために適合させたものです。交換されるSCRAMのデータは、[RFC5802]で定義されているものと同一です。この文書は、1往復での再認証モードも追加します。

HTTP SCRAM provides the following protocol features:

HTTP SCRAMは、次のプロトコル機能を提供します。

  • The authentication information stored in the authentication database is not sufficient by itself (without a dictionary attack) to impersonate the client. The information is salted to make it harder to do a pre-stored dictionary attack if the database is stolen.
  • The server does not gain the ability to impersonate the client to other servers (with an exception for server-authorized proxies), unless it performs a dictionary attack.
  • The mechanism permits the use of a server-authorized proxy without requiring that proxy to have super-user rights with the back-end server.
  • Mutual authentication is supported, but only the client is named (i.e., the server has no name).
  • 認証データベースに格納された認証情報だけでは、（辞書攻撃をしない限り）クライアントになりすますのに十分ではありません。データベースが盗まれた場合に事前計算した辞書による攻撃を難しくするため、この情報にはソルトが付けられています。
  • サーバーは、辞書攻撃を実行しない限り、他のサーバーに対してクライアントになりすます能力を得ることはありません（サーバーが認可したプロキシーは例外です）。
  • このメカニズムでは、サーバーが認可したプロキシーを、そのプロキシーにバックエンドサーバーでのスーパーユーザー権限を要求することなく使用できます。
  • 相互認証をサポートしますが、名前を持つのはクライアントだけです（つまり、サーバーには名前がありません）。

Some clarifications and additional definitions follow:

いくつかの補足説明と追加の定義を以下に示します。

Authentication information:
Information used to verify an identity claimed by a SCRAM client. The authentication information for a SCRAM identity consists of salt, iteration count, the StoredKey, and the ServerKey (as defined in the algorithm overview) for each supported cryptographic hash function.

The database used to look up the authentication information associated with a particular identity. For application protocols, LDAPv3 (see [RFC4510]) is frequently used as the authentication database. For lower-layer protocols such as PPP or 802.11x, the use of RADIUS [RFC2865] is more common.

An encoding mechanism defined in Section 4 of [RFC4648] that converts an octet string input to a textual output string that can be easily displayed to a human. The use of base64 in SCRAM is restricted to the canonical form with no whitespace.
Octet:
An 8-bit byte.
Octet string:
A sequence of 8-bit bytes.
Salt:
A random octet string that is combined with a password before applying a one-way encryption function. This value is used to protect passwords that are stored in an authentication database.

SCRAMクライアントが主張するアイデンティティーを検証するために使用される情報です。SCRAMアイデンティティーの認証情報は、サポートされる暗号学的ハッシュ関数ごとの、ソルト、反復回数、StoredKey、ServerKey（アルゴリズムの概要で定義されているもの）で構成されます。

Base64：
[RFC4648]のセクション4で定義されているエンコーディングメカニズムで、入力のオクテット列を、人間に容易に表示できるテキストの出力文字列に変換します。SCRAMでのbase64の使用は、空白を含まない正規形に限定されます。

2.2. Notation

2.2. 表記法

The pseudocode description of the algorithm uses the following notation:

アルゴリズムの疑似コードによる記述では、次の表記を使用します。

":=":
The variable on the left-hand side represents the octet string resulting from the expression on the right-hand side.
"+":
Octet string concatenation.
"[ ]":
A portion of an expression enclosed in "[" and "]" is optional in the result under some circumstances. See the associated text for a description of those circumstances.
Normalize(str):
Apply the Preparation and Enforcement steps according to the OpaqueString profile (see [RFC7613]) to a UTF-8 [RFC3629] encoded "str". The resulting string is also in UTF-8. Note that implementations MUST either implement OpaqueString profile operations from [RFC7613] or disallow the use of non US-ASCII Unicode codepoints in "str". The latter is a particular case of compliance with [RFC7613].
HMAC(key, str):
Apply the HMAC-keyed hash algorithm (defined in [RFC2104]) using the octet string represented by "key" as the key and the octet string "str" as the input string. The size of the result is the hash result size for the hash function in use. For example, it is 32 octets for SHA-256 and 20 octets for SHA-1 (see [RFC6234]).
H(str):
Apply the cryptographic hash function to the octet string "str", producing an octet string as a result. The size of the result depends on the hash result size for the hash function in use.
XOR:
Apply the exclusive-or operation to combine the octet string on the left of this operator with the octet string on the right of this operator. The length of the output and each of the two inputs will be the same for this use.
Hi(str, salt, i):
U1   := HMAC(str, salt + INT(1))
U2   := HMAC(str, U1)
...
Ui-1 := HMAC(str, Ui-2)
Ui   := HMAC(str, Ui-1)

Hi := U1 XOR U2 XOR ... XOR Ui

where "i" is the iteration count, "+" is the string concatenation operator, and INT(g) is a four-octet encoding of the integer g, most significant octet first.

Hi() is, essentially, PBKDF2 [RFC2898] with HMAC() as the Pseudorandom Function (PRF) and with dkLen == output length of HMAC() == output length of H().

":=":
左辺の変数は、右辺の式の結果として得られるオクテット列を表します。
"+":
オクテット列の連結です。
"[ ]":
「[」と「]」で囲まれた式の部分は、状況によっては結果に含まれない場合があります。その状況の説明は、関連する本文を参照してください。
Normalize(str):
UTF-8 [RFC3629]でエンコードされた「str」に、OpaqueStringプロファイル（[RFC7613]を参照）に従った準備（Preparation）と強制（Enforcement）の手順を適用します。結果の文字列もUTF-8です。実装は、[RFC7613]のOpaqueStringプロファイルの操作を実装するか、「str」にUS-ASCII以外のUnicodeコードポイントを使用することを禁止するかのどちらかをしなければなりません（MUST）。後者は、[RFC7613]に準拠する特殊な場合です。
HMAC(key, str):
「key」で表されるオクテット列を鍵とし、オクテット列「str」を入力文字列として、（[RFC2104]で定義されている）HMAC鍵付きハッシュアルゴリズムを適用します。結果のサイズは、使用するハッシュ関数のハッシュ結果のサイズです。たとえば、SHA-256では32オクテット、SHA-1では20オクテットです（[RFC6234]を参照）。
H(str):
オクテット列「str」に暗号学的ハッシュ関数を適用し、結果としてオクテット列を生成します。結果のサイズは、使用するハッシュ関数のハッシュ結果のサイズによって決まります。
XOR:
排他的論理和演算を適用して、この演算子の左側のオクテット列と右側のオクテット列を組み合わせます。この用途では、出力と2つの入力それぞれの長さは同じになります。
Hi(str, salt, i):
U1   := HMAC(str, salt + INT(1))
U2   := HMAC(str, U1)
...
Ui-1 := HMAC(str, Ui-2)
Ui   := HMAC(str, Ui-1)

Hi := U1 XOR U2 XOR ... XOR Ui

ここで、「i」は反復回数、「+」は文字列連結演算子、INT(g)は整数gを最上位オクテットを先頭にした4オクテットでエンコードしたものです。

Hi()は、本質的には、HMAC()を疑似ランダム関数（PRF）とし、dkLen == HMAC()の出力長 == H()の出力長としたPBKDF2 [RFC2898]です。

3. SCRAM Algorithm Overview

3. SCRAMアルゴリズムの概要

The following is a description of a full HTTP SCRAM authentication exchange. Note that this section omits some details, such as client and server nonces. See Section 5 for more details.

以下は、完全なHTTP SCRAM認証交換の説明です。このセクションでは、クライアントとサーバーのノンスなど、いくつかの詳細を省略していることに注意してください。詳細はセクション5を参照してください。

To begin with, the SCRAM client is in possession of a username and password, both encoded in UTF-8 [RFC3629] (or a ClientKey/ServerKey, or SaltedPassword). It sends the username to the server, which retrieves the corresponding authentication information: a salt, a StoredKey, a ServerKey, and an iteration count ("i"). (Note that a server implementation may choose to use the same iteration count for all accounts.) The server sends the salt and the iteration count to the client, which then computes the following values and sends a ClientProof to the server:

まず、SCRAMクライアントは、どちらもUTF-8 [RFC3629]でエンコードされたユーザー名とパスワード（またはClientKey/ServerKey、あるいはSaltedPassword）を持っています。クライアントはユーザー名をサーバーに送信し、サーバーは対応する認証情報（ソルト、StoredKey、ServerKey、反復回数（「i」））を取得します。（サーバーの実装は、すべてのアカウントで同じ反復回数を使用することを選択してもかまわないことに注意してください。）サーバーはソルトと反復回数をクライアントに送信し、クライアントは次の値を計算してClientProofをサーバーに送信します。

Informative Note: Implementors are encouraged to create test cases that use both usernames and passwords with non-ASCII codepoints. In particular, it is useful to test codepoints whose Unicode Normalization Canonical Composition (NFC) and Unicode Normalization Form Compatibility Composition (NFKC) are different (see [Unicode-UAX15]). Some examples of such codepoints include Vulgar Fraction One Half (U+00BD) and Acute Accent (U+00B4).

参考情報としての注記：実装者には、ASCII以外のコードポイントを含むユーザー名とパスワードの両方を使用するテストケースを作成することが推奨されます。特に、Unicode正規化形式の正準合成（NFC）と互換合成（NFKC）の結果が異なるコードポイントをテストすると有用です（[Unicode-UAX15]を参照）。そのようなコードポイントの例には、Vulgar Fraction One Half（U+00BD）やAcute Accent（U+00B4）があります。

   SaltedPassword  := Hi(Normalize(password), salt, i)
   ClientKey       := HMAC(SaltedPassword, "Client Key")
   StoredKey       := H(ClientKey)
   AuthMessage     := client-first-message-bare + "," +
                      server-first-message + "," +
                      client-final-message-without-proof
   ClientSignature := HMAC(StoredKey, AuthMessage)
   ClientProof     := ClientKey XOR ClientSignature
   ServerKey       := HMAC(SaltedPassword, "Server Key")
   ServerSignature := HMAC(ServerKey, AuthMessage)

   SaltedPassword  := Hi(Normalize(password), salt, i)
   ClientKey       := HMAC(SaltedPassword, "Client Key")
   StoredKey       := H(ClientKey)
   AuthMessage     := client-first-message-bare + "," +
                      server-first-message + "," +
                      client-final-message-without-proof
   ClientSignature := HMAC(StoredKey, AuthMessage)
   ClientProof     := ClientKey XOR ClientSignature
   ServerKey       := HMAC(SaltedPassword, "Server Key")
   ServerSignature := HMAC(ServerKey, AuthMessage)

The server authenticates the client by computing the ClientSignature, exclusive-ORing that with the ClientProof to recover the ClientKey, and verifying the correctness of the ClientKey by applying the hash function and comparing the result to the StoredKey. If the ClientKey is correct, this proves that the client has access to the user's password.

サーバーは、ClientSignatureを計算し、それとClientProofの排他的論理和をとってClientKeyを復元し、ClientKeyにハッシュ関数を適用した結果をStoredKeyと比較してClientKeyが正しいことを検証することで、クライアントを認証します。ClientKeyが正しければ、クライアントがユーザーのパスワードにアクセスできることが証明されます。

Similarly, the client authenticates the server by computing the ServerSignature and comparing it to the value sent by the server. If the two are equal, this proves that the server had access to the user's ServerKey.

同様に、クライアントは、ServerSignatureを計算してサーバーから送信された値と比較することで、サーバーを認証します。両者が等しければ、サーバーがユーザーのServerKeyにアクセスできたことが証明されます。

For initial authentication, the AuthMessage is computed by concatenating decoded "data" attribute values from the authentication exchange. The format of each of these 3 decoded "data" attributes is defined in [RFC5802].

初回の認証では、AuthMessageは、認証交換で得られた「data」属性の値をデコードして連結することで計算されます。デコードされたこれら3つの「data」属性それぞれの形式は、[RFC5802]で定義されています。

4. SCRAM Mechanism Names

4. SCRAMメカニズム名

A SCRAM mechanism name (authentication scheme) is a string "SCRAM-" followed by the uppercased name of the underlying hash function taken from the IANA "Hash Function Textual Names" registry (see <http://www.iana.org/assignments/hash-function-text-names>).

SCRAMメカニズム名（認証スキーム）は、文字列「SCRAM-」の後に、IANAの「Hash Function Textual Names」レジストリー（<http://www.iana.org/assignments/hash-function-text-names>を参照）から取った基盤となるハッシュ関数の名前を大文字にしたものを続けたものです。

For interoperability, all HTTP clients and servers supporting SCRAM MUST implement the SCRAM-SHA-256 authentication mechanism, i.e., an authentication mechanism from the SCRAM family that uses the SHA-256 hash function as defined in [RFC7677].

相互運用性のため、SCRAMをサポートするすべてのHTTPクライアントとサーバーは、SCRAM-SHA-256認証メカニズム、すなわち[RFC7677]で定義されているSHA-256ハッシュ関数を使用するSCRAMファミリーの認証メカニズムを実装しなければなりません（MUST）。

The client then responds with another HTTP request with the Authorization header field, which includes the "sid" attribute received in the previous server response, together with the "data" attribute containing base64-encoded "client-final-message" data. The server verifies the nonce and the proof, and, finally, it responds with a 200 HTTP response with the Authentication-Info header field [RFC7615] containing the "sid" attribute (as received from the client) and the "data" attribute containing the base64-encoded "server-final-message", concluding the authentication exchange.

5.1. One Round-Trip Reauthentication

5.1. 1往復での再認証

If the server supports SCRAM reauthentication, the server sends in its initial HTTP response a WWW-Authenticate header field containing the "realm" attribute (as defined earlier), the "sr" attribute that contains the server part of the "r" attribute (see s-nonce in [RFC5802]), and an optional "ttl" attribute (which contains the "sr" value validity in seconds).

サーバーがSCRAMの再認証をサポートしている場合、サーバーは最初のHTTPレスポンスで、（前述のとおりに定義された）「realm」属性、「r」属性のサーバー部分を含む「sr」属性（[RFC5802]のs-nonceを参照）、省略可能な「ttl」属性（「sr」の値の有効期間を秒単位で含む）を含んだWWW-Authenticateヘッダーフィールドを送信します。

If the client has authenticated to the same realm before (i.e., it remembers "i" and "s" attributes for the user from earlier authentication exchanges with the server), it can respond to that with "client-final-message". When constructing the "client-final-message", the client constructs the c-nonce part of the "r" attribute as on initial authentication and the s-nonce part as follows: s-nonce is a concatenation of nonce-count and the "sr" attribute (in that order). The nonce-count is a positive integer that is equal to the user's "i" attribute on first reauthentication and is incremented by 1 on each successful reauthentication.

クライアントが以前に同じレルムに対して認証したことがある場合（つまり、そのサーバーとの以前の認証交換で得たユーザーの「i」属性と「s」属性を覚えている場合）、クライアントはそれに対して「client-final-message」で応答できます。「client-final-message」を構築する際、クライアントは「r」属性のc-nonce部分を初回の認証と同じように構築し、s-nonce部分を次のように構築します。s-nonceは、nonce-countと「sr」属性を（この順序で）連結したものです。nonce-countは正の整数で、最初の再認証ではユーザーの「i」属性と等しく、再認証が成功するたびに1ずつ増やされます。

The purpose of the nonce-count is to allow the server to detect request replays by maintaining its own copy of this count -- if the same nonce-count value is seen twice, then the request is a replay.

nonce-countの目的は、サーバーがこのカウントの独自のコピーを保持することで、リクエストのリプレイを検出できるようにすることです。同じnonce-countの値が2回現れた場合、そのリクエストはリプレイです。

If the server considers the s-nonce part of the "nonce" attribute (the "r" attribute) to still be valid (i.e., the nonce-count part is as expected (see above) and the "sr" part is still fresh), it will provide access to the requested resource (assuming the client hash verifies correctly, of course). However, if the server considers that the server part of the nonce is stale (for example, if the "sr" value is used after the "ttl" seconds), the server returns "401 Unauthorized" containing the SCRAM mechanism name with the following attributes: a new "sr", "stale=true", and an optional "ttl". The "stale" attribute signals to the client that there is no need to ask the user for the password.

サーバーが「nonce」属性（「r」属性）のs-nonce部分がまだ有効である（つまり、nonce-count部分が（上記のとおり）期待どおりで、「sr」部分がまだ新しい）とみなした場合、サーバーは（もちろん、クライアントのハッシュが正しく検証されることを前提として）要求されたリソースへのアクセスを提供します。しかし、サーバーがノンスのサーバー部分が古くなっている（stale）とみなした場合（たとえば、「sr」の値が「ttl」秒を過ぎてから使用された場合）、サーバーは、SCRAMメカニズム名と、新しい「sr」、「stale=true」、省略可能な「ttl」の各属性を含む「401 Unauthorized」を返します。「stale」属性は、ユーザーにパスワードを尋ねる必要がないことをクライアントに伝えます。

Formally, the "stale" attribute is defined as a flag, indicating that the previous request from the client was rejected because the nonce value was stale. If stale is TRUE (case-insensitive), the client may wish to simply retry the request with a new encrypted response without reprompting the user for a new username and password. The server should only set stale to TRUE if it receives a request for which the nonce is invalid but with a valid digest for that nonce (indicating that the client knows the correct username/password). If stale is FALSE or anything other than TRUE, or the stale directive is not present, the username and/or password are invalid, and new values must be obtained.

形式的には、「stale」属性はフラグとして定義され、ノンスの値が古かったためにクライアントからの前回のリクエストが拒否されたことを示します。staleがTRUE（大文字と小文字を区別しない）の場合、クライアントは、ユーザーに新しいユーザー名とパスワードの入力を再度求めることなく、新しい暗号化されたレスポンスでリクエストを単に再試行したいと考えるかもしれません。サーバーは、ノンスは無効だがそのノンスに対する有効なダイジェストを持つ（つまり、クライアントが正しいユーザー名とパスワードを知っていることを示す）リクエストを受信した場合にのみ、staleをTRUEに設定するべきです。staleがFALSEまたはTRUE以外の値である場合や、stale指示子が存在しない場合は、ユーザー名とパスワードのどちらかまたは両方が無効であり、新しい値を取得しなければなりません。

6. Use of the Authentication-Info Header Field with SCRAM

6. SCRAMでのAuthentication-Infoヘッダーフィールドの使用

When used with SCRAM, the Authentication-Info header field is allowed in the trailer of an HTTP message transferred via chunked transfer-coding.

8. Security Considerations

8. セキュリティーに関する考慮事項

If the authentication exchange is performed without a strong session encryption (such as TLS with data confidentiality), then a passive eavesdropper can gain sufficient information to mount an offline dictionary or brute-force attack that can be used to recover the user's password. The amount of time necessary for this attack depends on the cryptographic hash function selected, the strength of the password, and the iteration count supplied by the server. SCRAM allows the server/server administrator to increase the iteration count over time in order to slow down the above attacks. (Note that a server that is only in possession of StoredKey and ServerKey can't automatically increase the iteration count upon successful authentication. Such an increase would require resetting the user's password.) An external security layer with strong encryption will prevent these attacks.

（データの機密性を備えたTLSのような）強力なセッション暗号化なしで認証交換が実行された場合、受動的な盗聴者は、ユーザーのパスワードを復元するためのオフラインの辞書攻撃や総当たり攻撃を仕掛けるのに十分な情報を得られます。この攻撃に必要な時間は、選択された暗号学的ハッシュ関数、パスワードの強度、サーバーが提供する反復回数によって決まります。SCRAMでは、上記の攻撃を遅らせるために、サーバーやサーバーの管理者が時間の経過とともに反復回数を増やすことができます。（StoredKeyとServerKeyしか保持していないサーバーは、認証の成功時に反復回数を自動的に増やすことはできないことに注意してください。そのように増やすには、ユーザーのパスワードをリセットする必要があります。）強力な暗号化を備えた外部のセキュリティー層を使えば、これらの攻撃を防げます。

If the authentication information is stolen from the authentication database, then an offline dictionary or brute-force attack can be used to recover the user's password. The use of salt mitigates this attack somewhat by requiring a separate attack on each password. Authentication mechanisms that protect against this attack are available (e.g., the Encrypted Key Exchange (EKE) class of mechanisms). RFC 2945 [RFC2945] is an example of such technology.

認証データベースから認証情報が盗まれた場合、オフラインの辞書攻撃や総当たり攻撃を使用してユーザーのパスワードを復元できます。ソルトを使用すると、パスワードごとに個別の攻撃が必要になるため、この攻撃をある程度緩和できます。この攻撃から保護する認証メカニズム（たとえば、Encrypted Key Exchange（EKE）系のメカニズム）も利用できます。RFC 2945 [RFC2945]はそのような技術の一例です。

If an attacker obtains the authentication information from the authentication repository and either eavesdrops on one authentication exchange or impersonates a server, the attacker gains the ability to impersonate that user to all servers providing SCRAM access using the same hash function, password, iteration count, and salt. For this reason, it is important to use randomly generated salt values.

攻撃者が認証リポジトリーから認証情報を入手し、さらに1回の認証交換を盗聴するかサーバーになりすますかした場合、攻撃者は、同じハッシュ関数、パスワード、反復回数、ソルトを使用してSCRAMアクセスを提供するすべてのサーバーに対して、そのユーザーになりすます能力を得ます。このため、ランダムに生成したソルト値を使用することが重要です。

SCRAM does not negotiate which hash function to use. Hash function negotiation is left to the HTTP authentication mechanism negotiation. It is important that clients be able to sort a locally available list of mechanisms by preference so that the client may pick the most preferred of a server's advertised mechanism list. This preference order is not specified here as it is a local matter. The preference order should include objective and subjective notions of mechanism cryptographic strength (e.g., SCRAM with SHA-256 should be preferred over SCRAM with SHA-1).

SCRAMは、どのハッシュ関数を使用するかをネゴシエートしません。ハッシュ関数のネゴシエーションは、HTTP認証メカニズムのネゴシエーションに任されます。クライアントが、サーバーが広告するメカニズムの一覧から最も好ましいものを選べるように、ローカルで利用可能なメカニズムの一覧を優先度順に並べ替えられることが重要です。この優先順位はローカルな事柄であるため、ここでは規定しません。優先順位には、メカニズムの暗号強度についての客観的および主観的な観念を含めるべきです（たとえば、SHA-1を使用するSCRAMよりもSHA-256を使用するSCRAMを優先するべきです）。

This document recommends use of SCRAM with SHA-256 hash. SCRAM-SHA-1 is registered for database compatibility with implementations of RFC 5802 (such as IMAP or XMPP servers) that want to also expose HTTP access to a related service, but it is not recommended for new deployments.

この文書は、SHA-256ハッシュを使用するSCRAMの使用を推奨します。SCRAM-SHA-1は、関連するサービスへのHTTPアクセスも公開したいRFC 5802の実装（IMAPやXMPPのサーバーなど）とのデータベース互換性のために登録されていますが、新規の展開には推奨されません。

A hostile server can perform a computational denial-of-service attack on clients by sending a big iteration count value. In order to defend against that, a client implementation can pick a maximum iteration count that it is willing to use and reject any values that exceed that threshold (in such cases, the client, of course, has to fail the authentication).

悪意のあるサーバーは、大きな反復回数の値を送信することで、クライアントに対する計算量的なサービス拒否攻撃を実行できます。これを防ぐために、クライアントの実装は、使用してもかまわない反復回数の最大値を決めておき、その閾値を超える値を拒否できます（その場合、当然ながら、クライアントは認証を失敗させる必要があります）。

See [RFC4086] for more information about generating randomness.

乱数の生成に関する詳細については、[RFC4086]を参照してください。

10. Design Motivations

10. 設計の動機

The following design goals shaped this document. Note that some of the goals have changed since the initial draft version of the document.

この文書は、次の設計目標に基づいて形作られました。目標のいくつかは、この文書の最初のドラフト版から変更されていることに注意してください。

  • The HTTP authentication mechanism has all modern features: support for internationalized usernames and passwords.
  • The protocol supports mutual authentication.
  • The authentication information stored in the authentication database is not sufficient by itself to impersonate the client.
  • The server does not gain the ability to impersonate the client to other servers (with an exception for server-authorized proxies), unless such other servers allow SCRAM authentication and use the same salt and iteration count for the user.
  • The mechanism is extensible, but (hopefully) not over-engineered in this respect.
  • The mechanism is easier to implement than HTTP Digest in both clients and servers.
  • The protocol supports 1 round-trip reauthentication.
  • HTTP認証メカニズムが、国際化されたユーザー名とパスワードのサポートという、現代的な機能をすべて備えていること。
  • プロトコルが相互認証をサポートすること。
  • 認証データベースに格納された認証情報だけでは、クライアントになりすますのに十分でないこと。
  • サーバーが、他のサーバーに対してクライアントになりすます能力を得ないこと（サーバーが認可したプロキシーは例外です）。ただし、そのような他のサーバーがSCRAM認証を許可し、そのユーザーに同じソルトと反復回数を使用している場合を除きます。
  • メカニズムが拡張可能であり、かつ（願わくば）その点で過剰な設計になっていないこと。
  • メカニズムが、クライアントとサーバーの両方において、HTTP Digestよりも実装しやすいこと。
  • プロトコルが1往復での再認証をサポートすること。
