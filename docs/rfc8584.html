RFC 8584

Framework for Ethernet VPN Designated Forwarder Election Extensibility

RFC 8584

イーサネットVPNの指定フォワーダー選出の拡張性のためのフレームワーク

Abstract

概要

An alternative to the default Designated Forwarder (DF) selection algorithm in Ethernet VPNs (EVPNs) is defined. The DF is the Provider Edge (PE) router responsible for sending Broadcast, Unknown Unicast, and Multicast (BUM) traffic to a multihomed Customer Edge (CE) device on a given VLAN on a particular Ethernet Segment (ES). In addition, the ability to influence the DF election result for a VLAN based on the state of the associated Attachment Circuit (AC) is specified. This document clarifies the DF election Finite State Machine in EVPN services. Therefore, it updates the EVPN specification (RFC 7432).

この文書は、イーサネットVPN（EVPN）におけるデフォルトの指定フォワーダー（Designated Forwarder: DF）選択アルゴリズムに代わるものを定義します。DFとは、特定のイーサネットセグメント（Ethernet Segment: ES）上の所定のVLANにおいて、マルチホームされたカスタマーエッジ（Customer Edge: CE）デバイスへブロードキャスト、未知ユニキャスト、マルチキャスト（BUM）トラフィックを送信する責任を持つプロバイダーエッジ（Provider Edge: PE）ルーターです。さらに、関連するアタッチメントサーキット（Attachment Circuit: AC）の状態に基づいて、VLANのDF選出結果に影響を与える能力を規定します。この文書は、EVPNサービスにおけるDF選出の有限状態機械を明確にします。したがって、この文書はEVPNの仕様（RFC 7432）を更新します。

1. Introduction

1. はじめに

The Designated Forwarder (DF) in Ethernet VPNs (EVPNs) is the Provider Edge (PE) router responsible for sending Broadcast, Unknown Unicast, and Multicast (BUM) traffic to a multihomed Customer Edge (CE) device on a given VLAN on a particular Ethernet Segment (ES). The DF is elected from the set of multihomed PEs attached to a given ES, each of which advertises an ES route for the ES as identified by its Ethernet Segment Identifier (ESI). By default, the EVPN uses a DF election algorithm referred to as "service carving". The DF election algorithm is based on a modulus function (V mod N) that takes the number of PEs in the ES (N) and the VLAN value (V) as input. This document addresses inefficiencies in the default DF election algorithm by defining a new DF election algorithm and an ability to influence the DF election result for a VLAN, depending on the state of the associated Attachment Circuit (AC). In order to avoid any ambiguity with the identifier used in the DF election algorithm, this document uses the term "Ethernet Tag" instead of "VLAN". This document also creates a registry with IANA for future DF election algorithms and capabilities (see Section 7). It also presents a formal definition and clarification of the DF election Finite State Machine (FSM). Therefore, this document updates [RFC7432], and EVPN implementations MUST conform to the prescribed FSM.

イーサネットVPN（EVPN）における指定フォワーダー（Designated Forwarder: DF）とは、特定のイーサネットセグメント（Ethernet Segment: ES）上の所定のVLANにおいて、マルチホームされたカスタマーエッジ（Customer Edge: CE）デバイスへブロードキャスト、未知ユニキャスト、マルチキャスト（BUM）トラフィックを送信する責任を持つプロバイダーエッジ（Provider Edge: PE）ルーターです。DFは、所定のESに接続されたマルチホームのPEの集合の中から選出されます。これらのPEはそれぞれ、イーサネットセグメント識別子（Ethernet Segment Identifier: ESI）で識別されるESについてESルートを広告します。デフォルトでは、EVPNは「サービスカービング（service carving）」と呼ばれるDF選出アルゴリズムを使用します。このDF選出アルゴリズムは、ES内のPEの数（N）とVLANの値（V）を入力とする剰余関数（V mod N）に基づいています。この文書は、新しいDF選出アルゴリズムと、関連するアタッチメントサーキット（Attachment Circuit: AC）の状態に応じてVLANのDF選出結果に影響を与える能力とを定義することにより、デフォルトのDF選出アルゴリズムの非効率性に対処します。DF選出アルゴリズムで使用される識別子との曖昧さを避けるため、この文書では「VLAN」の代わりに「イーサネットタグ（Ethernet Tag）」という用語を使用します。この文書はまた、将来のDF選出アルゴリズムと能力のためのレジストリーをIANAに作成します（Section 7を参照）。さらに、DF選出の有限状態機械（Finite State Machine: FSM）の正式な定義と明確化も示します。したがって、この文書は[RFC7432]を更新し、EVPNの実装は規定されたFSMに準拠しなければなりません（MUST）。

The procedures described in this document apply to DF election in all EVPN solutions, including those described in [RFC7432] and [RFC8214]. Apart from the formal description of the FSM, this document does not intend to update other procedures described in [RFC7432]; it only aims to improve the behavior of the DF election on PEs that are upgraded to follow the procedures described in this document.

この文書で説明する手順は、[RFC7432]や[RFC8214]で説明されているものを含む、すべてのEVPNソリューションにおけるDF選出に適用されます。FSMの正式な記述を除けば、この文書は[RFC7432]で説明されている他の手順を更新することを意図していません。この文書は、この文書で説明する手順に従うようにアップグレードされたPEにおけるDF選出の振る舞いを改善することだけを目的としています。

1.2. Default Designated Forwarder (DF) Election in EVPN Services

1.2. EVPNサービスにおけるデフォルトの指定フォワーダー（DF）選出

[RFC7432] defines the DF as the EVPN PE responsible for:

[RFC7432]は、DFを次のことに責任を持つEVPN PEとして定義しています。

  • Flooding BUM traffic on a given Ethernet Tag on a particular ES to the CE. This is valid for Single-Active and All-Active EVPN multihoming.
  • Sending unicast traffic on a given Ethernet Tag on a particular ES to the CE. This is valid for Single-Active multihoming.
  • 特定のES上の所定のイーサネットタグにおいて、BUMトラフィックをCEへフラッディングすること。これは、Single-ActiveとAll-ActiveのEVPNマルチホーミングの両方に当てはまります。
  • 特定のES上の所定のイーサネットタグにおいて、ユニキャストトラフィックをCEへ送信すること。これは、Single-Activeのマルチホーミングに当てはまります。

Figure 1 illustrates an example that we will use to explain the DF function.

Figure 1は、DFの機能を説明するために使用する例を示しています。

Figure 1 illustrates a case where there are two ESes: ES1 and ES2. PE1 is attached to CE1 via ES1, whereas PE2, PE3, and PE4 are attached to CE2 via ES2, i.e., PE2, PE3, and PE4 form a redundancy group. Since CE2 is multihomed to different PEs on the same ES, it is necessary for PE2, PE3, and PE4 to agree on a DF to satisfy the above-mentioned requirements.

Figure 1は、ES1とES2の2つのESがある場合を示しています。PE1はES1を介してCE1に接続され、PE2、PE3、PE4はES2を介してCE2に接続されています。つまり、PE2、PE3、PE4は冗長グループを形成しています。CE2は同じES上の異なるPEにマルチホームされているため、前述の要件を満たすには、PE2、PE3、PE4がDFについて合意する必要があります。

The effect of forwarding loops in a Layer 2 network is particularly severe because of the broadcast nature of Ethernet traffic and the lack of a TTL. Therefore, it is very important that, in the case of a multihomed CE, only one of the PEs be used to send BUM traffic to it.

イーサネットトラフィックのブロードキャストという性質とTTLがないことにより、レイヤー2ネットワークにおける転送ループの影響は特に深刻です。したがって、マルチホームされたCEの場合、そのCEへBUMトラフィックを送信するのにPEのうちの1つだけを使用することが非常に重要です。

One of the prerequisites for this support is that participating PEs must agree amongst themselves as to who would act as the DF. This needs to be achieved through a distributed algorithm in which each participating PE independently and unambiguously selects one of the participating PEs as the DF, and the result should be consistent and unanimous.

これをサポートするための前提条件の1つは、参加しているPEどうしで、どのPEがDFとして動作するかについて合意しなければならないことです。これは、参加している各PEが独立して曖昧さなく参加PEのうちの1つをDFとして選択し、その結果が一貫していて全員一致となるような分散アルゴリズムによって達成する必要があります。

The default algorithm for DF election defined by [RFC7432] at the granularity of (ESI, EVI) is referred to as "service carving". In this document, service carving and the default DF election algorithm are used interchangeably. With service carving, it is possible to elect multiple DFs per ES (one per EVI) in order to perform load balancing of traffic destined to a given ES. The objective is that the load-balancing procedures should carve up the BD space among the redundant PE nodes evenly, in such a way that every PE is the DF for a distinct set of EVIs.

[RFC7432]で定義されている、(ESI, EVI)の粒度でのDF選出のデフォルトのアルゴリズムは、「サービスカービング」と呼ばれます。この文書では、サービスカービングとデフォルトのDF選出アルゴリズムを同じ意味で使用します。サービスカービングでは、所定のES宛てのトラフィックの負荷分散を行うために、ESごとに複数のDF（EVIごとに1つ）を選出できます。その目的は、負荷分散の手順によってBD空間を冗長なPEノード間で均等に切り分け、すべてのPEがそれぞれ異なるEVIの集合に対するDFとなるようにすることです。

The DF election algorithm (as described in [RFC7432], Section 8.5) is based on a modulus operation. The PEs to which the ES (for which DF election is to be carried out per EVI) is multihomed form an ordered (ordinal) list in ascending order by PE IP address value. For example, there are N PEs: PE0, PE1,... PE(N-1) ranked as per increasing IP addresses in the ordinal list; then, for each VLAN with Ethernet Tag V, configured on ES1, PEx is the DF for VLAN V on ES1 when x equals (V mod N). In the case of a VLAN Bundle, only the lowest VLAN is used. In the case when the planned density is high (meaning there are a significant number of VLANs and the Ethernet Tags are uniformly distributed), the thinking is that the DF election will be spread across the PEs hosting that ES and good load balancing can be achieved.

DF選出アルゴリズム（[RFC7432], Section 8.5で説明されているもの）は、剰余演算に基づいています。ES（EVIごとにDF選出を行う対象のES）がマルチホームされているPEは、PEのIPアドレスの値の昇順で順序付き（序数）リストを形成します。たとえば、N個のPE、すなわちPE0、PE1、...、PE(N-1)が序数リスト内でIPアドレスの昇順に並んでいるとすると、ES1上に設定されたイーサネットタグVを持つ各VLANについて、xが(V mod N)に等しいとき、PExがES1上のVLAN VのDFとなります。VLANバンドルの場合は、最も小さいVLANだけが使用されます。計画上の密度が高い場合（つまり、相当数のVLANがあり、イーサネットタグが一様に分布している場合）、DF選出はそのESをホストするPE全体に分散し、良好な負荷分散が達成できると考えられています。

However, the described default DF election algorithm has some undesirable properties and, in some cases, can be somewhat disruptive and unfair. This document describes some of those issues and defines a mechanism for dealing with them. These mechanisms do involve changes to the default DF election algorithm, but they do not require any changes to the EVPN route exchange, and changes in the EVPN routes will be minimal.

しかし、上述のデフォルトのDF選出アルゴリズムには望ましくない特性がいくつかあり、場合によっては、ある程度の中断を引き起こしたり不公平になったりすることがあります。この文書では、それらの問題のいくつかを説明し、それらに対処するためのメカニズムを定義します。これらのメカニズムはデフォルトのDF選出アルゴリズムの変更を伴いますが、EVPNのルート交換の変更は必要とせず、EVPNルートの変更も最小限にとどまります。

In addition, there is a need to extend the DF election procedures so that new algorithms and capabilities are possible. A single algorithm (the default DF election algorithm) may not meet the requirements in all the use cases.

さらに、新しいアルゴリズムや能力を使用できるように、DF選出手順を拡張する必要があります。単一のアルゴリズム（デフォルトのDF選出アルゴリズム）では、すべてのユースケースの要件を満たせない場合があります。

Note that while [RFC7432] elects a DF per <ES, EVI>, this document elects a DF per <ES, BD>. This means that unlike [RFC7432], where for a VLAN-aware Bundle service EVI there is only one DF for the EVI, this document specifies that there will be multiple DFs, one for each BD configured in that EVI.

[RFC7432]は<ES, EVI>ごとにDFを選出しますが、この文書は<ES, BD>ごとにDFを選出することに注意してください。つまり、VLAN対応バンドルのサービスのEVIについてそのEVIに1つのDFしかない[RFC7432]とは異なり、この文書では、そのEVIに設定されたBDごとに1つずつ、複数のDFが存在することを規定します。

1.3. Problem Statement

1.3. 問題の記述

This section describes some potential issues with the default DF election algorithm.

このセクションでは、デフォルトのDF選出アルゴリズムの潜在的な問題をいくつか説明します。

1.3.1. Unfair Load Balancing and Service Disruption

1.3.1. 不公平な負荷分散とサービスの中断

There are three fundamental problems with the current default DF election algorithm.

現在のデフォルトのDF選出アルゴリズムには、3つの根本的な問題があります。

  1. The algorithm will not perform well when the Ethernet Tag follows a non-uniform distribution -- for instance, when the Ethernet Tags are all even or all odd. In such a case, let us assume that the ES is multihomed to two PEs; one of the PEs will be elected as the DF for all of the VLANs. This is very suboptimal. It defeats the purpose of service carving, as the DFs are not really evenly spread across the PEs hosting the ES. In fact, in this particular case, one of the PEs does not get elected as the DF at all, so it does not participate in DF responsibilities at all. Consider another example where, referring to Figure 1, let's assume that (1) PE2, PE3, and PE4 are listed in ascending order by IP address and (2) each VLAN configured on ES2 is associated with an Ethernet Tag of the form (3x+1), where x is an integer. This will result in PE3 always being selected as the DF.

  2. The Ethernet Tag that identifies the BD can be as large as 2^24; however, it is not guaranteed that the tenant BD on the ES will conform to a uniform distribution. In fact, it is up to the customer what BDs they will configure on the ES. Quoting [Knuth]:

    In general, we want to avoid values of M that divide r^k+a or r^k-a, where k and a are small numbers and r is the radix of the alphabetic character set (usually r=64, 256 or 100), since a remainder modulo such a value of M tends to be largely a simple superposition of key digits. Such considerations suggest that we choose M to be a prime number such that r^k!=a(modulo)M or r^k!=?a(modulo)M for small k & a.

    In our case, N is the number of PEs (Section 8.5 of [RFC7432]). N corresponds to M above. Since N, N-1, or N+1 need not satisfy the primality properties of M, as per the modulo-based DF assignment [RFC7432], whenever a PE goes down or a new PE boots up (attached to the same ES), the modulo scheme will not necessarily map BDs to PEs uniformly.

  3. Disruption is another problem. Consider a case when the same ES is multihomed to a set of PEs. When the ES is DOWN in one of the PEs, say PE1, or PE1 itself reboots, or the BGP process goes down or the connectivity between PE1 and an RR goes down, the effective number of PEs in the system now becomes N-1, and DFs are computed for all the VLANs that are configured on that ES. In general, if the DF for a VLAN V happens not to be PE1, but some other PE, say PE2, it is likely that some other PE (different from PE1 and PE2) will become the new DF. This is not desirable. Similarly, when a new PE hosts the same ES, the mapping again changes because of the modulus operation. This results in needless churn. Again referring to Figure 1, say V1, V2, and V3 are VLANs configured on ES2 with associated Ethernet Tags of values 999, 1000, and 1001, respectively. So, PE1, PE2, and PE3 are the DFs for V1, V2, and V3, respectively. Now when PE3 goes down, PE2 will become the DF for V1 and PE1 will become the DF for V2.
  1. イーサネットタグが一様でない分布に従う場合（たとえば、イーサネットタグがすべて偶数またはすべて奇数である場合）、このアルゴリズムはうまく機能しません。このような場合に、ESが2つのPEにマルチホームされていると仮定すると、一方のPEがすべてのVLANのDFとして選出されてしまいます。これは非常に最適とはいえない状態です。DFがESをホストするPE全体に実際には均等に分散しないため、サービスカービングの目的が損なわれます。実際、この特定の場合では、一方のPEはまったくDFとして選出されないため、DFの責務にまったく関与しません。別の例として、Figure 1を参照し、(1) PE2、PE3、PE4がIPアドレスの昇順に並んでおり、(2) ES2上に設定された各VLANが(3x+1)（xは整数）という形式のイーサネットタグに関連付けられていると仮定します。この場合、常にPE3がDFとして選択されることになります。

  2. BDを識別するイーサネットタグは最大で2^24になることがありますが、ES上のテナントBDが一様分布に従う保証はありません。実際、ES上にどのBDを設定するかは顧客次第です。[Knuth]から引用します。

    一般に、r^k+aまたはr^k-a（kとaは小さな数、rは英字の文字集合の基数（通常はr=64、256、または100））を割り切るようなMの値は避けたいところです。なぜなら、そのようなMの値を法とする剰余は、主にキーの桁の単純な重ね合わせになりがちだからです。このような考察から、小さなkとaについてr^k!=a(modulo)Mまたはr^k!=?a(modulo)Mとなるような素数をMとして選ぶことが示唆されます。

    私たちの場合、NはPEの数です（[RFC7432]のSection 8.5）。Nは上記のMに相当します。剰余に基づくDFの割り当て[RFC7432]に従うと、N、N-1、N+1がMの素数性を満たすとは限らないため、PEがダウンしたり（同じESに接続された）新しいPEが起動したりするたびに、剰余方式はBDをPEに一様に対応付けるとは限りません。

  3. 中断も別の問題です。同じESがPEの集合にマルチホームされている場合を考えます。PEのうちの1つ（たとえばPE1）でESがDOWNになった場合や、PE1自体が再起動した場合、BGPプロセスがダウンした場合、PE1とRRの間の接続がダウンした場合には、システム内の実質的なPEの数はN-1になり、そのES上に設定されたすべてのVLANについてDFが計算されます。一般に、VLAN VのDFがたまたまPE1ではなく他のPE（たとえばPE2）であった場合でも、（PE1ともPE2とも異なる）他のPEが新しいDFになる可能性が高くなります。これは望ましくありません。同様に、新しいPEが同じESをホストする場合も、剰余演算のために対応付けが再び変わります。これにより、不要なチャーン（churn）が発生します。再びFigure 1を参照し、V1、V2、V3がES2上に設定されたVLANで、関連するイーサネットタグの値がそれぞれ999、1000、1001であるとします。すると、PE1、PE2、PE3がそれぞれV1、V2、V3のDFになります。ここでPE3がダウンすると、PE2がV1のDFになり、PE1がV2のDFになります。

One point to note is that the default DF election algorithm assumes that all the PEs who are multihomed to the same ES (and interested in the DF election by exchanging EVPN routes) use an Originating Router's IP address [RFC7432] of the same family. This does not need to be the case, as the EVPN address family can be carried over an IPv4 or IPv6 peering, and the PEs attached to the same ES may use an address of either family.

注意すべき点の1つは、デフォルトのDF選出アルゴリズムが、同じESにマルチホームされている（そしてEVPNルートを交換することでDF選出に関与する）すべてのPEが同じファミリーのOriginating Router's IPアドレス[RFC7432]を使用することを前提としていることです。EVPNアドレスファミリーはIPv4とIPv6のどちらのピアリング上でも運ぶことができ、同じESに接続されたPEはどちらのファミリーのアドレスを使用してもよいため、そうである必要はありません。

Mathematically, a conventional hash function maps a key k to a number i representing one of m hash buckets through a function h(k), i.e., i = h(k). In the EVPN case, h is simply a modulo-m hash function viz. h(V) = V mod N, where N is the number of PEs that are multihomed to the ES in question. It is well known that for good hash distribution using the modulus operation, the modulus N should be a prime number not too close to a power of 2 [CLRS2009]. When the effective number of PEs changes from N to N-1 (or vice versa), all the objects (VLAN V) will be remapped except those for which V mod N and V mod (N-1) refer to the same PE in the previous and subsequent ordinal rankings, respectively. From a forwarding perspective, this is a churn, as it results in reprogramming the PE ports as either blocking or non-blocking at the PEs where the DF state changes.

数学的には、従来のハッシュ関数は、関数h(k)によってキーkをm個のハッシュバケットのうちの1つを表す数iに対応付けます。つまり、i = h(k)です。EVPNの場合、hは単にmを法とするハッシュ関数、すなわちh(V) = V mod Nです。ここで、Nは対象のESにマルチホームされているPEの数です。剰余演算を使用して良好なハッシュ分布を得るには、法Nは2のべき乗に近すぎない素数であるべきことがよく知られています[CLRS2009]。実質的なPEの数がNからN-1に（またはその逆に）変化すると、V mod NとV mod (N-1)がそれぞれ変化前と変化後の序数の順位で同じPEを指すものを除き、すべてのオブジェクト（VLAN V）が再対応付けされます。転送の観点からは、DFの状態が変化するPEにおいてPEのポートをブロッキングまたは非ブロッキングとして再プログラミングすることになるため、これはチャーンです。

This document addresses this problem and furnishes a solution to this undesirable behavior.

この文書は、この問題に対処し、この望ましくない振る舞いに対する解決策を提供します。

1.3.2. Traffic Black-Holing on Individual AC Failures

1.3.2. 個々のACの障害によるトラフィックのブラックホール化

The default DF election algorithm defined by [RFC7432] takes into account only two variables in the modulus function for a given ES: the existence of the PE's IP address in the candidate list and the locally provisioned Ethernet Tags.

[RFC7432]で定義されているデフォルトのDF選出アルゴリズムは、所定のESについて、剰余関数で2つの変数だけを考慮します。それは、候補リスト内にPEのIPアドレスが存在するかどうかと、ローカルにプロビジョニングされたイーサネットタグです。

If the DF for an <ESI, EVI> fails (due to physical link/node failures), an ES route withdrawal will make the NDF PEs re-elect the DF for that <ESI, EVI> and the service will be recovered.

<ESI, EVI>のDFが（物理的なリンクやノードの障害により）故障した場合、ESルートの取り消しによってNDFのPEがその<ESI, EVI>のDFを再選出し、サービスが回復します。

However, the default DF election procedure does not provide protection against "logical" failures or human errors that may occur at the service level on the DF, while the list of active PEs for a given ES does not change. These failures may have an impact not only on the local PE where the issue happens but also on the rest of the PEs of the ES. Some examples of such logical failures are listed below:

しかし、デフォルトのDF選出手順は、所定のESのアクティブなPEのリストが変化しないまま、DF上のサービスレベルで発生する可能性のある「論理的な」障害や人為的なミスに対する保護を提供しません。これらの障害は、問題が発生したローカルのPEだけでなく、ESの残りのPEにも影響を与える可能性があります。このような論理的な障害の例をいくつか次に示します。

  1. A given individual AC defined in an ES is accidentally shut down or is not provisioned yet (hence, the ACS is DOWN), while the ES is operationally active (since the ES route is active).
  2. A given MAC-VRF with a defined ES is either shut down or not provisioned yet, while the ES is operationally active (since the ES route is active). In this case, the ACS of all the ACs defined in that MAC-VRF is considered to be DOWN.
  1. ES内に定義された特定の個々のACが誤ってシャットダウンされているか、まだプロビジョニングされておらず（したがってACSはDOWN）、一方でESは運用上アクティブ（ESルートがアクティブであるため）である場合です。
  2. ESが定義された特定のMAC-VRFがシャットダウンされているか、まだプロビジョニングされておらず、一方でESは運用上アクティブ（ESルートがアクティブであるため）である場合です。この場合、そのMAC-VRF内に定義されたすべてのACのACSはDOWNであるとみなされます。

Neither (a) nor (b) will trigger the DF re-election on the remote multihomed PEs for a given ES, since the ACS is not taken into account in the DF election procedures. While the ACS is used as a DF election tiebreaker and trigger in Virtual Private LAN Service (VPLS) multihoming procedures [VPLS-MH], there is no procedure defined in the EVPN specification [RFC7432] to trigger the DF re-election based on the ACS change on the DF.

ACSはDF選出手順で考慮されないため、(a)と(b)のどちらも、所定のESのリモートのマルチホームのPEでDFの再選出を引き起こしません。仮想プライベートLANサービス（Virtual Private LAN Service: VPLS）のマルチホーミング手順[VPLS-MH]ではACSがDF選出のタイブレーカーおよびトリガーとして使用されていますが、EVPNの仕様[RFC7432]には、DF上のACSの変化に基づいてDFの再選出をトリガーする手順は定義されていません。

Figure 2 shows an example of logical AC failure.

Figure 2は、ACの論理的な障害の例を示しています。

BD-1 is defined in PE1, PE2, PE3, and PE4. CE12 is a multihomed CE connected to ES12 in PE1 and PE2. Similarly, CE23 is multihomed to PE2 and PE3 using ES23. Both CE12 and CE23 are connected to BD-1 through VLAN-based service interfaces: CE12-VID 1 (VID 1 on CE12) is associated with AC1 and AC2 in BD-1, whereas CE23-VID 1 is associated with AC3 and AC4 in BD-1. Assume that, although not represented, there are other ACs defined on these ESes mapped to different BDs.

BD-1は、PE1、PE2、PE3、PE4に定義されています。CE12は、PE1とPE2のES12に接続されたマルチホームのCEです。同様に、CE23はES23を使用してPE2とPE3にマルチホームされています。CE12とCE23はどちらも、VLANベースのサービスインターフェイスを介してBD-1に接続されています。CE12-VID 1（CE12上のVID 1）はBD-1内のAC1とAC2に関連付けられ、CE23-VID 1はBD-1内のAC3とAC4に関連付けられています。図には示していませんが、これらのESには、異なるBDに対応付けられた他のACも定義されていると仮定します。

After executing the default DF election algorithm as described in [RFC7432], PE2 turns out to be the DF for ES12 and ES23 in BD-1. The following issues may arise:

[RFC7432]で説明されているデフォルトのDF選出アルゴリズムを実行した結果、BD-1においてPE2がES12とES23のDFになったとします。この場合、次の問題が発生する可能性があります。

  1. If AC2 is accidentally shut down or is not configured yet, CE12 traffic will be impacted. In the case of All-Active multihoming, the BUM traffic to CE12 will be "black-holed", whereas for Single-Active multihoming, all the traffic to/from CE12 will be discarded. This is because a logical failure in PE2's AC2 may not trigger an ES route withdrawal for ES12 (since there are still other ACs active on ES12); therefore, PE1 will not rerun the DF election procedures.
  2. If the bridge table for BD-1 is administratively shut down or is not configured yet on PE2, CE12 and CE23 will both be impacted: BUM traffic to both CEs will be discarded in the case of All-Active multihoming, and all traffic will be discarded to/from the CEs in the case of Single-Active multihoming. This is because PE1 and PE3 will not rerun the DF election procedures and will keep assuming that PE2 is the DF.
  1. AC2が誤ってシャットダウンされたか、まだ設定されていない場合、CE12のトラフィックが影響を受けます。All-Activeのマルチホーミングの場合、CE12へのBUMトラフィックは「ブラックホール化」されます。一方、Single-Activeのマルチホーミングの場合、CE12との間のすべてのトラフィックが破棄されます。これは、PE2のAC2における論理的な障害が、ES12のESルートの取り消しを引き起こさない場合がある（ES12上ではまだ他のACがアクティブであるため）ためです。したがって、PE1はDF選出手順を再実行しません。
  2. PE2上でBD-1のブリッジテーブルが管理上シャットダウンされたか、まだ設定されていない場合、CE12とCE23の両方が影響を受けます。All-Activeのマルチホーミングの場合は両方のCEへのBUMトラフィックが破棄され、Single-Activeのマルチホーミングの場合はCEとの間のすべてのトラフィックが破棄されます。これは、PE1とPE3がDF選出手順を再実行せず、PE2がDFであるとみなし続けるためです。

Quoting [RFC7432], "When an Ethernet tag is decommissioned on an Ethernet segment, then the PE MUST withdraw the Ethernet A-D per EVI route(s) announced for the <ESI, Ethernet tags> that are impacted by the decommissioning." However, while this A-D per EVI route withdrawal is used at the remote PEs performing aliasing or backup procedures, it is not used to influence the DF election for the affected EVIs.

[RFC7432]から引用すると、「イーサネットセグメント上でイーサネットタグの運用が終了した場合、PEは、その運用終了の影響を受ける<ESI, Ethernet tags>について広告したEVIごとのイーサネットA-Dルートを取り消さなければなりません（MUST）」。しかし、このEVIごとのA-Dルートの取り消しは、エイリアシングやバックアップの手順を実行するリモートのPEでは使用されますが、影響を受けるEVIのDF選出に影響を与えるためには使用されません。

This document adds an optional modification of the DF election procedure so that the ACS may be taken into account as a variable in the DF election; therefore, EVPN can provide protection against logical failures.

この文書は、DF選出においてACSを変数として考慮できるように、DF選出手順の任意の修正を追加します。これにより、EVPNは論理的な障害に対する保護を提供できます。

1.4. The Need for Extending the Default DF Election in EVPN Services

1.4. EVPNサービスにおけるデフォルトのDF選出を拡張する必要性

Section 1.3 describes some of the issues that exist in the default DF election procedures. In order to address those issues, this document introduces a new DF election framework. This framework allows the PEs to agree on a common DF election algorithm, as well as the capabilities to enable during the DF election procedure. Generally, "DF election algorithm" refers to the algorithm by which a number of input parameters are used to determine the DF PE, while "DF election capability" refers to an additional feature that can be used prior to the invocation of the DF election algorithm, such as modifying the inputs (or list of candidate PEs).

Section 1.3では、デフォルトのDF選出手順に存在する問題のいくつかを説明しました。それらの問題に対処するため、この文書は新しいDF選出フレームワークを導入します。このフレームワークにより、PEは共通のDF選出アルゴリズムと、DF選出手順の間に有効にする能力について合意できます。一般に、「DF選出アルゴリズム」は、いくつかの入力パラメーターを使用してDFとなるPEを決定するアルゴリズムを指し、「DF選出能力」は、入力（または候補PEのリスト）の変更など、DF選出アルゴリズムの呼び出しより前に使用できる追加の機能を指します。

Within this framework, this document defines a new DF election algorithm and a new capability that can influence the DF election result:

このフレームワークの中で、この文書は、新しいDF選出アルゴリズムと、DF選出結果に影響を与えることのできる新しい能力を定義します。

  • The new DF election algorithm is referred to as "Highest Random Weight" (HRW). The HRW procedures are described in Section 3.
  • The new DF election capability is referred to as "AC-Influenced DF election" (AC-DF). The AC-DF procedures are described in Section 4.
  • HRW and AC-DF mechanisms are independent of each other. Therefore, a PE may support either HRW or AC-DF independently or may support both of them together. A PE may also support the AC-DF capability along with the default DF election algorithm per [RFC7432].
  • 新しいDF選出アルゴリズムは「Highest Random Weight」（HRW）と呼ばれます。HRWの手順はSection 3で説明します。
  • 新しいDF選出能力は「AC影響型DF選出（AC-Influenced DF election）」（AC-DF）と呼ばれます。AC-DFの手順はSection 4で説明します。
  • HRWとAC-DFのメカニズムは互いに独立しています。したがって、PEはHRWとAC-DFのどちらか一方を単独でサポートすることも、両方を一緒にサポートすることもできます。また、PEは、[RFC7432]によるデフォルトのDF選出アルゴリズムとともにAC-DF能力をサポートすることもできます。

In addition, this document defines a way to indicate the support of HRW and/or AC-DF along with the EVPN ES routes advertised for a given ES. Refer to Section 2.2 for more details.

さらに、この文書は、所定のESについて広告されるEVPNのESルートとともに、HRWとAC-DFの一方または両方のサポートを示す方法を定義します。詳細はSection 2.2を参照してください。

2. Designated Forwarder Election Protocol and BGP Extensions

2. 指定フォワーダー選出プロトコルとBGP拡張

This section describes the BGP extensions required to support the new DF election procedures. In addition, since the EVPN specification [RFC7432] leaves several questions open as to the precise FSM behavior of the DF election, Section 2.1 precisely describes the intended behavior.

このセクションでは、新しいDF選出手順をサポートするのに必要なBGP拡張を説明します。さらに、EVPNの仕様[RFC7432]はDF選出の正確なFSMの振る舞いについていくつかの疑問を未解決のまま残しているため、Section 2.1で意図した振る舞いを正確に説明します。

2.1. The DF Election Finite State Machine (FSM)

2.1. DF選出の有限状態機械（FSM）

Per [RFC7432], the FSM shown in Figure 3 is executed per <ES, VLAN> in the case of VLAN-based service or <ES, [VLANs in VLAN Bundle]> in the case of a VLAN Bundle on each participating PE. Note that the FSM is conceptual. Any design or implementation MUST comply with behavior that is equivalent to the behavior outlined in this FSM.

[RFC7432]によると、Figure 3に示すFSMは、参加している各PE上で、VLANベースのサービスの場合は<ES, VLAN>ごとに、VLANバンドルの場合は<ES, [VLANs in VLAN Bundle]>ごとに実行されます。このFSMは概念的なものであることに注意してください。いかなる設計や実装も、このFSMで概説している振る舞いと等価な振る舞いに準拠しなければなりません（MUST）。

Observe that each EVI is locally configured on each of the multihomed PEs attached to a given ES and that the FSM does not provide any protection against inconsistent configuration between these PEs. That is, for a given EVI, one or more of the PEs are inadvertently configured with a different set of VLANs for a VLAN-aware Bundle service or with different VLANs for a VLAN-based service.

各EVIは、所定のESに接続されたマルチホームの各PE上でローカルに設定されること、そしてFSMはこれらのPE間の設定の不整合に対する保護を一切提供しないことに注意してください。つまり、所定のEVIについて、1つ以上のPEが誤って、VLAN対応バンドルのサービスで異なるVLANの集合を設定されていたり、VLANベースのサービスで異なるVLANを設定されていたりする場合です。

The states and events shown in Figure 3 are defined as follows.

Figure 3に示す状態とイベントは、次のように定義されます。

States:

状態：

  1. INIT: Initial state.
  2. DF_WAIT: State in which the participant waits for enough information to perform the DF election for the EVI/ESI/VLAN combination.
  3. DF_CALC: State in which the new DF is recomputed.
  4. DF_DONE: State in which the corresponding DF for the EVI/ESI/VLAN combination has been elected.
  5. ANY_STATE: Refers to any of the above states.
  1. INIT：初期状態です。
  2. DF_WAIT：参加者が、EVI/ESI/VLANの組み合わせについてDF選出を行うのに十分な情報を待っている状態です。
  3. DF_CALC：新しいDFが再計算される状態です。
  4. DF_DONE：EVI/ESI/VLANの組み合わせに対応するDFが選出された状態です。
  5. ANY_STATE：上記のいずれかの状態を指します。

Events:

イベント：

  1. ES_UP: The ES has been locally configured as "UP".
  2. ES_DOWN: The ES has been locally configured as "DOWN".
  3. VLAN_CHANGE: The VLANs configured in a bundle (that uses the ES) changed. This event is necessary for VLAN Bundles only.
  4. DF_TIMER: DF timer [RFC7432] (referred to as "Wait timer" in this document) has expired.
  5. RCVD_ES: A new or changed ES route is received in an Update message with an MP_REACH_NLRI. Receiving an unchanged Update MUST NOT trigger this event.
  6. LOST_ES: An Update message with an MP_UNREACH_NLRI for a previously received ES route has been received. If such a message is seen for a route that has not been advertised previously, the event MUST NOT be triggered.
  7. CALCULATED: DF has been successfully calculated.
  1. ES_UP：ESがローカルで「UP」に設定されました。
  2. ES_DOWN：ESがローカルで「DOWN」に設定されました。
  3. VLAN_CHANGE：（ESを使用する）バンドルに設定されたVLANが変更されました。このイベントはVLANバンドルの場合にのみ必要です。
  4. DF_TIMER：DFタイマー[RFC7432]（この文書では「Wait timer」と呼びます）が期限切れになりました。
  5. RCVD_ES：新しいESルートまたは変更されたESルートが、MP_REACH_NLRIを含むUpdateメッセージで受信されました。変更のないUpdateを受信したことによって、このイベントをトリガーしてはなりません（MUST NOT）。
  6. LOST_ES：以前に受信したESルートについて、MP_UNREACH_NLRIを含むUpdateメッセージが受信されました。以前に広告されていないルートについてこのようなメッセージが見られた場合、このイベントをトリガーしてはなりません（MUST NOT）。
  7. CALCULATED：DFの計算が正常に完了しました。

Corresponding actions when transitions are performed or states are entered/exited:

遷移が実行されたとき、または状態に入るとき・出るときの対応する動作は次のとおりです。

  1. ANY_STATE on ES_DOWN:

    1. Stop the DF Wait timer.
    2. Assume an NDF for the local PE.
  2. INIT on ES_UP: Transition to DF_WAIT.
  3. INIT on VLAN_CHANGE, RCVD_ES, or LOST_ES: Do nothing.

  4. DF_WAIT on entering the state:

    1. Start the DF Wait timer if not started already or expired.
    2. Assume an NDF for the local PE.
  5. DF_WAIT on VLAN_CHANGE, RCVD_ES, or LOST_ES: Do nothing.
  6. DF_WAIT on DF_TIMER: Transition to DF_CALC.

  7. DF_CALC on entering or re-entering the state:

    1. Rebuild the candidate list, perform a hash, and perform the election.
    2. Afterwards, the FSM generates a CALCULATED event against itself.
  8. DF_CALC on VLAN_CHANGE, RCVD_ES, or LOST_ES: Do as prescribed in Transition 7.
  9. DF_CALC on CALCULATED: Mark the election result for the VLAN or bundle, and transition to DF_DONE.
  10. DF_DONE on exiting the state: If a new DF election is triggered and the current DF is lost, then assume an NDF for the local PE for the VLAN or VLAN Bundle.
  11. DF_DONE on VLAN_CHANGE, RCVD_ES, or LOST_ES: Transition to DF_CALC.

  1. ANY_STATEでES_DOWNのとき：

    1. DF Waitタイマーを停止します。
    2. ローカルのPEをNDFとみなします。
  2. INITでES_UPのとき：DF_WAITに遷移します。
  3. INITでVLAN_CHANGE、RCVD_ES、またはLOST_ESのとき：何もしません。

  4. DF_WAITの状態に入るとき：

    1. DF Waitタイマーがまだ開始されていないか期限切れになっている場合は、開始します。
    2. ローカルのPEをNDFとみなします。
  5. DF_WAITでVLAN_CHANGE、RCVD_ES、またはLOST_ESのとき：何もしません。
  6. DF_WAITでDF_TIMERのとき：DF_CALCに遷移します。

  7. DF_CALCの状態に入るとき、または再び入るとき：

    1. 候補リストを再構築し、ハッシュを実行し、選出を行います。
    2. その後、FSMは自身に対してCALCULATEDイベントを生成します。
  8. DF_CALCでVLAN_CHANGE、RCVD_ES、またはLOST_ESのとき：遷移7で規定されているとおりに処理します。
  9. DF_CALCでCALCULATEDのとき：VLANまたはバンドルについて選出結果を記録し、DF_DONEに遷移します。
  10. DF_DONEの状態から出るとき：新しいDF選出がトリガーされ、現在のDFが失われた場合は、そのVLANまたはVLANバンドルについてローカルのPEをNDFとみなします。
  11. DF_DONEでVLAN_CHANGE、RCVD_ES、またはLOST_ESのとき：DF_CALCに遷移します。

The above events and transitions are defined for the default DF election algorithm. As described in Section 4, the use of the AC-DF capability introduces additional events and transitions.

上記のイベントと遷移は、デフォルトのDF選出アルゴリズムについて定義されたものです。Section 4で説明するように、AC-DF能力を使用すると、追加のイベントと遷移が導入されます。

2.2. The DF Election Extended Community

2.2. DF選出拡張コミュニティー

For the DF election procedures to be consistent and unanimous, it is necessary that all the participating PEs agree on the DF election algorithm and capabilities to be used. For instance, it is not possible for some PEs to continue to use the default DF election algorithm while some PEs use HRW. For brownfield deployments and for interoperability with legacy PEs, it is important that all PEs have the ability to fall back on the default DF election. A PE can indicate its willingness to support HRW and/or AC-DF by signaling a DF Election Extended Community along with the ES route (Route Type 4).

DF選出手順が一貫して全員一致となるためには、参加しているすべてのPEが、使用するDF選出アルゴリズムと能力について合意する必要があります。たとえば、一部のPEがデフォルトのDF選出アルゴリズムを使い続け、一部のPEがHRWを使用するということはできません。ブラウンフィールドでの展開や、レガシーなPEとの相互運用性のためには、すべてのPEがデフォルトのDF選出にフォールバックする能力を持つことが重要です。PEは、ESルート（ルートタイプ4）とともにDF選出拡張コミュニティー（DF Election Extended Community）を通知することにより、HRWとAC-DFの一方または両方をサポートする意思を示すことができます。

The DF Election Extended Community is a new BGP transitive Extended Community attribute [RFC4360] that is defined to identify the DF election procedure to be used for the ES. Figure 4 shows the encoding of the DF Election Extended Community.

DF選出拡張コミュニティーは、ESに使用するDF選出手順を識別するために定義された、新しいBGPの推移的な拡張コミュニティー属性[RFC4360]です。Figure 4に、DF選出拡張コミュニティーのエンコーディングを示します。

Where:

各フィールドは次のとおりです。

  • Type: 0x06, as registered with IANA (Section 7) for EVPN Extended Communities.
  • Sub-Type: 0x06. "DF Election Extended Community", as registered with IANA.
  • RSV/Reserved: Reserved bits for information that is specific to DF Alg.

  • DF Alg (5 bits): Encodes the DF election algorithm values (between 0 and 31) that the advertising PE desires to use for the ES. This document creates an IANA registry called "DF Alg" (Section 7), which contains the following values:

    • Type 0: Default DF election algorithm, or modulus-based algorithm as defined in [RFC7432].
    • Type 1: HRW Algorithm (Section 3).
    • Types 2-30: Unassigned.
    • Type 31: Reserved for Experimental Use.

  • Bitmap (2 octets): Encodes "capabilities" to use with the DF election algorithm in the DF Alg field. This document creates an IANA registry (Section 7) for the Bitmap field, with values 0-15. This registry is called "DF Election Capabilities" and includes the bit values listed below.

    • Bit 0 (corresponds to Bit 24 of the DF Election Extended Community): Unassigned.
    • Bit 1: AC-DF Capability (AC-Influenced DF election; see Section 4). When set to 1, it indicates the desire to use AC-DF with the rest of the PEs in the ES.
    • Bits 2-15: Unassigned.
  • Type：EVPN拡張コミュニティーとしてIANAに登録されている0x06です（Section 7）。
  • Sub-Type：0x06です。IANAに登録されている「DF Election Extended Community」です。
  • RSV/Reserved：DF Algに固有の情報のための予約済みビットです。

  • DF Alg（5ビット）：広告するPEがそのESに使用したいDF選出アルゴリズムの値（0から31の間）をエンコードします。この文書は「DF Alg」と呼ばれるIANAレジストリーを作成します（Section 7）。このレジストリーには次の値が含まれます。

    • タイプ0：デフォルトのDF選出アルゴリズム、すなわち[RFC7432]で定義されている剰余に基づくアルゴリズムです。
    • タイプ1：HRWアルゴリズムです（Section 3）。
    • タイプ2～30：未割り当てです。
    • タイプ31：Experimental Useのために予約されています。

  • Bitmap（2オクテット）：DF AlgフィールドのDF選出アルゴリズムとともに使用する「能力」をエンコードします。この文書は、0～15の値を持つBitmapフィールドのためのIANAレジストリーを作成します（Section 7）。このレジストリーは「DF Election Capabilities」と呼ばれ、以下に示すビット値を含みます。

    • ビット0（DF選出拡張コミュニティーのビット24に相当）：未割り当てです。
    • ビット1：AC-DF能力（AC影響型DF選出。Section 4を参照）です。1に設定されている場合、ES内の残りのPEとともにAC-DFを使用したいという意思を示します。
    • ビット2～15：未割り当てです。

The DF Election Extended Community is used as follows:

DF選出拡張コミュニティーは、次のように使用します。

  • A PE SHOULD attach the DF Election Extended Community to any advertised ES route, and the Extended Community MUST be sent if the ES is locally configured with a DF election algorithm other than the default DF election algorithm or if a capability is required to be used. In the Extended Community, the PE indicates the desired "DF Alg" algorithm and "Bitmap" capabilities to be used for the ES.

    • Only one DF Election Extended Community can be sent along with an ES route. Note that the intent is not for the advertising PE to indicate all the supported DF election algorithms and capabilities but to signal the preferred one.
    • DF Alg values 0 and 1 can both be used with Bit 1 (AC-DF) set to 0 or 1.
    • In general, a specific DF Alg SHOULD determine the use of the reserved bits in the Extended Community, which may be used in a different way for a different DF Alg. In particular, for DF Alg values 0 and 1, the reserved bits are not set by the advertising PE and SHOULD be ignored by the receiving PE.

  • When a PE receives the ES routes from all the other PEs for the ES in question, it checks to see if all the advertisements have the Extended Community with the same DF Alg and Bitmap:

    • If they do, this particular PE MUST follow the procedures for the advertised DF Alg and capabilities. For instance, if all ES routes for a given ES indicate DF Alg HRW and AC-DF set to 1, then the PEs attached to the ES will perform the DF election as per the HRW algorithm and following the AC-DF procedures.
    • Otherwise, if even a single advertisement for Route Type 4 is received without the locally configured DF Alg and capability, the default DF election algorithm MUST be used as prescribed in [RFC7432]. This procedure handles the case where participating PEs in the ES disagree about the DF algorithm and capability to be applied.
    • The absence of the DF Election Extended Community or the presence of multiple DF Election Extended Communities (in the same route) MUST be interpreted by a receiving PE as an indication of the default DF election algorithm on the sending PE -- that is, DF Alg 0 and no DF election capabilities.
  • When all the PEs in an ES advertise DF Type 31, they will rely on the local policy to decide how to proceed with the DF election.
  • For any new capability defined in the future, the applicability/compatibility of this new capability to/with the existing DF Alg values must be assessed on a case-by-case basis.
  • Likewise, for any new DF Alg defined in the future, its applicability/compatibility to/with the existing capabilities must be assessed on a case-by-case basis.

  • PEは、広告するすべてのESルートにDF選出拡張コミュニティーを付加すべきです（SHOULD）。そして、ESがデフォルトのDF選出アルゴリズム以外のDF選出アルゴリズムでローカルに設定されている場合や、能力の使用が求められる場合には、この拡張コミュニティーを送信しなければなりません（MUST）。PEは拡張コミュニティーの中で、そのESに使用したい「DF Alg」アルゴリズムと「Bitmap」能力を示します。

    • ESルートとともに送信できるDF選出拡張コミュニティーは1つだけです。その意図は、広告するPEがサポートするすべてのDF選出アルゴリズムと能力を示すことではなく、望ましいものを通知することであることに注意してください。
    • DF Algの値0と1はどちらも、ビット1（AC-DF）を0または1に設定して使用できます。
    • 一般に、拡張コミュニティー内の予約済みビットの使用法は、特定のDF Algが決定すべきです（SHOULD）。予約済みビットは、DF Algが異なれば異なる方法で使用される場合があります。特に、DF Algの値0と1では、予約済みビットは広告するPEによって設定されず、受信するPEはこれを無視すべきです（SHOULD）。

  • PEは、対象のESについて他のすべてのPEからESルートを受信すると、すべての広告が同じDF AlgとBitmapを持つ拡張コミュニティーを含んでいるかどうかを確認します。

    • 含んでいる場合、そのPEは、広告されたDF Algと能力の手順に従わなければなりません（MUST）。たとえば、所定のESのすべてのESルートがDF AlgとしてHRWを示し、AC-DFが1に設定されている場合、そのESに接続されたPEは、HRWアルゴリズムに従い、かつAC-DFの手順に従ってDF選出を行います。
    • そうでない場合、つまりローカルに設定されたDF Algと能力を含まないルートタイプ4の広告を1つでも受信した場合は、[RFC7432]で規定されているとおりにデフォルトのDF選出アルゴリズムを使用しなければなりません（MUST）。この手順は、ES内の参加しているPEが、適用するDFアルゴリズムと能力について一致しない場合に対処するものです。
    • DF選出拡張コミュニティーがないこと、または（同じルート内に）複数のDF選出拡張コミュニティーが存在することは、受信するPEによって、送信するPE上のデフォルトのDF選出アルゴリズム、すなわちDF Alg 0でDF選出能力なし、を示すものとして解釈されなければなりません（MUST）。
  • ES内のすべてのPEがDFタイプ31を広告した場合、それらのPEは、DF選出をどのように進めるかの決定をローカルポリシーに委ねます。
  • 将来定義される新しい能力については、既存のDF Algの値に対するその新しい能力の適用可能性や互換性を個別に評価しなければなりません。
  • 同様に、将来定義される新しいDF Algについては、既存の能力に対するその適用可能性や互換性を個別に評価しなければなりません。

2.2.1. Backward Compatibility

2.2.1. 後方互換性

Implementations that comply with [RFC7432] only (i.e., implementations that predate this specification) will not advertise the DF Election Extended Community. That means that all other participating PEs in the ES will not receive DF preferences and will revert to the default DF election algorithm without AC-DF.

[RFC7432]のみに準拠した実装（つまり、この仕様より前の実装）は、DF選出拡張コミュニティーを広告しません。そのため、ES内の他のすべての参加PEはDFの設定を受信せず、AC-DFなしのデフォルトのDF選出アルゴリズムに戻ります。

Similarly, an implementation that complies with [RFC7432] only and that receives a DF Election Extended Community will ignore it and will continue to use the default DF election algorithm.

同様に、[RFC7432]のみに準拠し、DF選出拡張コミュニティーを受信した実装は、それを無視し、デフォルトのDF選出アルゴリズムを使い続けます。

3. The Highest Random Weight DF Election Algorithm

3. Highest Random Weight DF選出アルゴリズム

The procedure discussed in this section is applicable to the DF election in EVPN services [RFC7432] and the EVPN Virtual Private Wire Service (VPWS) [RFC8214].

このセクションで説明する手順は、EVPNサービス[RFC7432]およびEVPN仮想プライベートワイヤサービス（Virtual Private Wire Service: VPWS）[RFC8214]におけるDF選出に適用できます。

HRW as defined in [HRW1999] is originally proposed in the context of Internet caching and proxy server load balancing. Given an object name and a set of servers, HRW maps a request to a server using the object-name (object-id) and server-name (server-id) rather than the server states. HRW forms a hash out of the server-id and the object-id and forms an ordered list of the servers for the particular object-id. The server for which the hash value is highest serves as the primary server responsible for that particular object, and the server with the next-highest value in that hash serves as the backup server. HRW always maps a given object name to the same server within a given cluster; consequently, it can be used at client sites to achieve global consensus on object-to-server mappings. When that server goes down, the backup server becomes the responsible designate.

[HRW1999]で定義されているHRWは、もともとインターネットのキャッシュとプロキシーサーバーの負荷分散の文脈で提案されたものです。オブジェクト名とサーバーの集合が与えられると、HRWは、サーバーの状態ではなく、オブジェクト名（object-id）とサーバー名（server-id）を使用してリクエストをサーバーに対応付けます。HRWは、server-idとobject-idからハッシュを作成し、特定のobject-idについてサーバーの順序付きリストを作成します。ハッシュ値が最も高いサーバーがその特定のオブジェクトに責任を持つプライマリーサーバーとなり、そのハッシュで次に高い値を持つサーバーがバックアップサーバーとなります。HRWは、所定のクラスター内で所定のオブジェクト名を常に同じサーバーに対応付けます。その結果、クライアント側でオブジェクトとサーバーの対応付けについて全体的なコンセンサスを得るために使用できます。そのサーバーがダウンすると、バックアップサーバーが責任を持つ担当者になります。

Choosing an appropriate hash function that is statistically oblivious to the key distribution and imparts a good uniform distribution of the hash output is an important aspect of the algorithm. Fortunately, many such hash functions exist. [HRW1999] provides pseudorandom functions based on the Unix utilities rand and srand and easily constructed XOR functions that satisfy the desired hashing properties. HRW already finds use in multicast and ECMP [RFC2991] [RFC2992].

キーの分布に対して統計的に無関係で、ハッシュ出力に良好な一様分布をもたらす適切なハッシュ関数を選択することは、このアルゴリズムの重要な側面です。幸い、そのようなハッシュ関数は数多く存在します。[HRW1999]は、Unixユーティリティーのrandとsrandに基づく疑似ランダム関数と、望ましいハッシュの特性を満たす容易に構築できるXOR関数を提供しています。HRWはすでにマルチキャストやECMP [RFC2991] [RFC2992]で使用されています。

3.1. HRW and Consistent Hashing

3.1. HRWとコンシステントハッシュ法

HRW is not the only algorithm that addresses the object-to-server mapping problem with goals of fair load distribution, redundancy, and fast access. There is another family of algorithms that also addresses this problem; these fall under the umbrella of the Consistent Hashing Algorithms [CHASH]. These will not be considered here.

公平な負荷分散、冗長性、高速なアクセスを目標として、オブジェクトとサーバーの対応付けの問題に取り組むアルゴリズムはHRWだけではありません。この問題に取り組むアルゴリズムのファミリーは他にもあり、それらはコンシステントハッシュアルゴリズム（Consistent Hashing Algorithms）[CHASH]という総称に分類されます。ここではそれらは検討しません。

3.2. HRW Algorithm for EVPN DF Election

3.2. EVPNのDF選出のためのHRWアルゴリズム

This section describes the application of HRW to DF election. Let DF(V) denote the DF and BDF(V) denote the BDF for the Ethernet Tag V; Si is the IP address of PE i; Es is the ESI; and Weight is a function of V, Si, and Es.

このセクションでは、HRWのDF選出への適用を説明します。DF(V)はイーサネットタグVのDFを表し、BDF(V)はイーサネットタグVのBDFを表すものとします。SiはPE iのIPアドレス、EsはESIであり、WeightはV、Si、Esの関数です。

Note that while the DF election algorithm provided in [RFC7432] uses a PE address and VLAN as inputs, this document uses an Ethernet Tag, PE address, and ESI as inputs. This is because if the same set of PEs are multihomed to the same set of ESes, then the DF election algorithm used in [RFC7432] would result in the same PE being elected DF for the same set of BDs on each ES; this could have adverse side effects on both load balancing and redundancy. Including an ESI in the DF election algorithm introduces additional entropy, which significantly reduces the probability of the same PE being elected DF for the same set of BDs on each ES. Therefore, when using the HRW algorithm for EVPN DF election, the ESI value in the Weight function below SHOULD be set to that of the corresponding ES.

[RFC7432]で示されているDF選出アルゴリズムはPEのアドレスとVLANを入力として使用しますが、この文書ではイーサネットタグ、PEのアドレス、ESIを入力として使用することに注意してください。これは、同じPEの集合が同じESの集合にマルチホームされている場合、[RFC7432]で使用されているDF選出アルゴリズムでは、各ES上の同じBDの集合について同じPEがDFとして選出されることになり、負荷分散と冗長性の両方に悪影響を及ぼす可能性があるためです。DF選出アルゴリズムにESIを含めることで追加のエントロピーが導入され、各ES上の同じBDの集合について同じPEがDFとして選出される確率が大幅に低下します。したがって、EVPNのDF選出にHRWアルゴリズムを使用する場合、以下のWeight関数のESIの値は、対応するESのESIに設定すべきです（SHOULD）。

In the case of a VLAN Bundle service, V denotes the lowest VLAN, similar to the "lowest VLAN in bundle" logic of [RFC7432].

VLANバンドルのサービスの場合、[RFC7432]の「バンドル内の最も小さいVLAN（lowest VLAN in bundle）」のロジックと同様に、Vは最も小さいVLANを表します。

  1. DF(V) = Si| Weight(V, Es, Si) >= Weight(V, Es, Sj), for all j. In the case of a tie, choose the PE whose IP address is numerically the least. Note that 0 <= i,j < number of PEs in the redundancy group.
  2. BDF(V) = Sk| Weight(V, Es, Si) >= Weight(V, Es, Sk), and Weight(V, Es, Sk) >= Weight(V, Es, Sj). In the case of a tie, choose the PE whose IP address is numerically the least.
  1. DF(V) = Si| Weight(V, Es, Si) >= Weight(V, Es, Sj), for all j。同点の場合は、IPアドレスが数値的に最も小さいPEを選択します。0 <= i,j < 冗長グループ内のPEの数、であることに注意してください。
  2. BDF(V) = Sk| Weight(V, Es, Si) >= Weight(V, Es, Sk), and Weight(V, Es, Sk) >= Weight(V, Es, Sj)。同点の場合は、IPアドレスが数値的に最も小さいPEを選択します。

Where:

ここで：

  • DF(V) is defined to be the address Si (index i) for which Weight(V, Es, Si) is the highest; 0 <= i < N-1.
  • BDF(V) is defined as that PE with address Sk for which the computed Weight is the next highest after the Weight of the DF. j is the running index from 0 to N-1; i and k are selected values.
  • DF(V)は、Weight(V, Es, Si)が最も高くなるアドレスSi（インデックスi）として定義されます。0 <= i < N-1です。
  • BDF(V)は、計算されたWeightがDFのWeightの次に高くなるアドレスSkを持つPEとして定義されます。jは0からN-1までの走査用インデックスで、iとkは選択された値です。

Since the Weight is a pseudorandom function with the domain as the three-tuple (V, Es, S), it is an efficient and deterministic algorithm that is independent of the Ethernet Tag V sample space distribution. Choosing a good hash function for the pseudorandom function is an important consideration for this algorithm to perform better than the default algorithm. As mentioned previously, such functions are described in [HRW1999]. We take as a candidate hash function the first one out of the two that are listed as preferred in [HRW1999]:

Weightは3つ組(V, Es, S)を定義域とする疑似ランダム関数であるため、これはイーサネットタグVの標本空間の分布に依存しない、効率的で決定論的なアルゴリズムです。このアルゴリズムがデフォルトのアルゴリズムより良好に機能するためには、疑似ランダム関数として優れたハッシュ関数を選択することが重要な考慮事項です。前述のとおり、そのような関数は[HRW1999]で説明されています。私たちは、[HRW1999]で望ましいものとして挙げられている2つのうち最初のものを、候補のハッシュ関数として採用します。

   Wrand(V, Es, Si) = (1103515245((1103515245.Si+12345) XOR
   D(V, Es))+12345)(mod 2^31)

   Wrand(V, Es, Si) = (1103515245((1103515245.Si+12345) XOR
   D(V, Es))+12345)(mod 2^31)

Here, D(V, Es) is the 31-bit digest (CRC-32 and discarding the most significant bit (MSB), as noted in [HRW1999]) of the 14-octet stream (the 4-octet Ethernet Tag V followed by the 10-octet ESI). It is mandated that the 14-octet stream be formed by the concatenation of the Ethernet Tag and the ESI in network byte order. The CRC should proceed as if the stream is in network byte order (big-endian). Si is the address of the ith server. The server's IP address length does not matter, as only the low-order 31 bits are modulo significant.

ここで、D(V, Es)は、14オクテットのストリーム（4オクテットのイーサネットタグVに10オクテットのESIが続くもの）の31ビットのダイジェスト（[HRW1999]に記載されているように、CRC-32を計算して最上位ビット（MSB）を捨てたもの）です。14オクテットのストリームは、ネットワークバイトオーダーのイーサネットタグとESIを連結して作成することが必須とされています。CRCは、ストリームがネットワークバイトオーダー（ビッグエンディアン）であるものとして計算すべきです。Siはi番目のサーバーのアドレスです。剰余に関係するのは下位31ビットだけであるため、サーバーのIPアドレスの長さは問題になりません。

A point to note is that the Weight function takes into consideration the combination of the Ethernet Tag, the ES, and the PE IP address, and the actual length of the server IP address (whether IPv4 or IPv6) is not really relevant. The default algorithm defined in [RFC7432] cannot employ both IPv4 and IPv6 PE addresses, since [RFC7432] does not specify how to decide on the ordering (the ordinal list) when both IPv4 and IPv6 PEs are present.

注意すべき点として、Weight関数はイーサネットタグ、ES、PEのIPアドレスの組み合わせを考慮しており、サーバーのIPアドレスの実際の長さ（IPv4かIPv6か）は実際には関係ありません。[RFC7432]で定義されているデフォルトのアルゴリズムは、IPv4とIPv6の両方のPEアドレスを使用することができません。なぜなら、[RFC7432]は、IPv4とIPv6の両方のPEが存在する場合に順序（序数リスト）をどのように決定するかを規定していないためです。

HRW solves the disadvantages pointed out in Section 1.3.1 of this document and ensures that:

HRWは、この文書のSection 1.3.1で指摘した欠点を解決し、次のことを保証します。

  • With very high probability, the task of DF election for the VLANs configured on an ES is more or less equally distributed among the PEs, even in the case of two PEs (see the first fundamental problem listed in Section 1.3.1).
  • If a PE that is not the DF or the BDF for that VLAN goes down or its connection to the ES goes down, it does not result in a DF or BDF reassignment. This saves computation, especially in the case when the connection flaps.
  • More importantly, it avoids the third fundamental problem listed in Section 1.3.1 (needless disruption) that is inherent in the existing default DF election.
  • In addition to the DF, the algorithm also furnishes the BDF, which would be the DF if the current DF fails.
  • 非常に高い確率で、ES上に設定されたVLANのDF選出のタスクが、PEが2つの場合であっても、PE間でほぼ均等に分散されます（Section 1.3.1に挙げた1つ目の根本的な問題を参照）。
  • そのVLANのDFでもBDFでもないPEがダウンしたり、そのPEとESとの接続がダウンしたりしても、DFやBDFの再割り当ては発生しません。これにより、特に接続がフラップする場合に計算が節約されます。
  • さらに重要なこととして、既存のデフォルトのDF選出に内在する、Section 1.3.1に挙げた3つ目の根本的な問題（不要な中断）を回避します。
  • このアルゴリズムは、DFに加えてBDFも提供します。BDFは、現在のDFが故障した場合にDFとなるものです。

4. The AC-Influenced DF Election Capability

4. AC影響型DF選出能力

The procedure discussed in this section is applicable to the DF election in EVPN services [RFC7432] and EVPN VPWS [RFC8214].

このセクションで説明する手順は、EVPNサービス[RFC7432]およびEVPN VPWS [RFC8214]におけるDF選出に適用できます。

The AC-DF capability is expected to be generally applicable to any future DF algorithm. It modifies the DF election procedures by removing from consideration any candidate PE in the ES that cannot forward traffic on the AC that belongs to the BD. This section is applicable to VLAN-based and VLAN Bundle service interfaces. Section 4.1 describes the procedures for VLAN-aware Bundle service interfaces.

AC-DF能力は、将来のあらゆるDFアルゴリズムに一般的に適用できることが期待されています。この能力は、BDに属するAC上でトラフィックを転送できないES内の候補PEを検討対象から除外することにより、DF選出手順を変更します。このセクションは、VLANベースおよびVLANバンドルのサービスインターフェイスに適用できます。VLAN対応バンドルのサービスインターフェイスの手順はSection 4.1で説明します。

In particular, when used with the default DF algorithm, the AC-DF capability modifies Step 3 in the DF election procedure described in [RFC7432], Section 8.5, as follows:

特に、デフォルトのDFアルゴリズムとともに使用する場合、AC-DF能力は、[RFC7432], Section 8.5で説明されているDF選出手順のステップ3を次のように変更します。

  1. When the timer expires, each PE builds an ordered candidate list of the IP addresses of all the PE nodes attached to the ES (including itself), in increasing numeric value. The candidate list is based on the Originating Router's IP addresses of the ES routes but excludes any PE from whom no Ethernet A-D per ES route has been received or from whom the route has been withdrawn. Afterwards, the DF election algorithm is applied on a per <ES, Ethernet Tag>; however, the IP address for a PE will not be considered to be a candidate for a given <ES, Ethernet Tag> until the corresponding Ethernet A-D per EVI route has been received from that PE. In other words, the ACS on the ES for a given PE must be UP so that the PE is considered to be a candidate for a given BD.

    If the default DF algorithm is used, every PE in the resulting candidate list is then given an ordinal indicating its position in the ordered list, starting with 0 as the ordinal for the PE with the numerically lowest IP address. The ordinals are used to determine which PE node will be the DF for a given Ethernet Tag on the ES, using the following rule:

    Assuming a redundancy group of N PE nodes, for VLAN-based service, the PE with ordinal i is the DF for an <ES, Ethernet Tag V> when (V mod N) = i. In the case of a VLAN (-aware) Bundle service, then the numerically lowest VLAN value in that bundle on that ES MUST be used in the modulo function as the Ethernet Tag.

    It should be noted that using the Originating Router's IP Address field [RFC7432] in the ES route to get the PE IP address needed for the ordered list allows for a CE to be multihomed across different Autonomous Systems (ASes) if such a need ever arises.

  1. タイマーが期限切れになると、各PEは、ESに接続されたすべてのPEノード（自身を含む）のIPアドレスを数値の昇順に並べた、順序付きの候補リストを構築します。候補リストはESルートのOriginating Router's IPアドレスに基づきますが、ESごとのイーサネットA-Dルートを受信していないPEや、そのルートが取り消されたPEは除外します。その後、<ES, Ethernet Tag>ごとにDF選出アルゴリズムが適用されます。ただし、あるPEのIPアドレスは、対応するEVIごとのイーサネットA-DルートをそのPEから受信するまで、所定の<ES, Ethernet Tag>の候補とはみなされません。言い換えると、PEが所定のBDの候補とみなされるためには、そのPEのES上のACSがUPでなければなりません。

    デフォルトのDFアルゴリズムを使用する場合、結果として得られた候補リスト内のすべてのPEには、順序付きリスト内の位置を示す序数が与えられます。序数は、IPアドレスが数値的に最も小さいPEの0から始まります。序数は、次の規則を使用して、ES上の所定のイーサネットタグについてどのPEノードがDFになるかを決定するために使用されます。

    N個のPEノードからなる冗長グループを仮定すると、VLANベースのサービスでは、(V mod N) = iのとき、序数iを持つPEが<ES, Ethernet Tag V>のDFになります。VLAN（対応）バンドルのサービスの場合は、そのES上のそのバンドル内で数値的に最も小さいVLANの値を、イーサネットタグとして剰余関数で使用しなければなりません（MUST）。

    順序付きリストに必要なPEのIPアドレスを得るためにESルートのOriginating Router's IP Addressフィールド[RFC7432]を使用することで、必要が生じた場合には、異なる自律システム（Autonomous System: AS）にまたがってCEをマルチホームできることに注意してください。

The modified Step 3, above, differs from [RFC7432], Section 8.5, Step 3 in two ways:

上記の変更されたステップ3は、[RFC7432], Section 8.5のステップ3とは次の2点で異なります。

  • Any DF Alg can be used -- not only the described modulus-based DF Alg (referred to as the default DF election or "DF Alg 0" in this document).
  • The candidate list is pruned based upon non-receipt of Ethernet A-D routes: a PE's IP address MUST be removed from the ES candidate list if its Ethernet A-D per ES route is withdrawn. A PE's IP address MUST NOT be considered to be a candidate DF for an <ES, Ethernet Tag> if its Ethernet A-D per EVI route for the <ES, Ethernet Tag> is withdrawn.
  • 説明した剰余に基づくDF Alg（この文書ではデフォルトのDF選出、または「DF Alg 0」と呼んでいます）だけでなく、任意のDF Algを使用できます。
  • 候補リストは、イーサネットA-Dルートを受信していないことに基づいて刈り込まれます。ESごとのイーサネットA-Dルートが取り消された場合、そのPEのIPアドレスをESの候補リストから削除しなければなりません（MUST）。ある<ES, Ethernet Tag>のEVIごとのイーサネットA-Dルートが取り消された場合、そのPEのIPアドレスをその<ES, Ethernet Tag>のDF候補とみなしてはなりません（MUST NOT）。

次の例は、Figure 2のネットワークを前提として、デフォルトのDF選出アルゴリズムに適用したAC-DFの振る舞いを示しています。

  1. When PE1 and PE2 discover ES12, they advertise an ES route for ES12 with the associated ES-Import Extended Community and the DF Election Extended Community indicating AC-DF = 1; they start a DF Wait timer (independently). Likewise, PE2 and PE3 advertise an ES route for ES23 with AC-DF = 1 and start a DF Wait timer.
  2. PE1 and PE2 advertise an Ethernet A-D per ES route for ES12. PE2 and PE3 advertise an Ethernet A-D per ES route for ES23.
  3. In addition, PE1, PE2, and PE3 advertise an Ethernet A-D per EVI route for AC1, AC2, AC3, and AC4 as soon as the ACs are enabled. Note that the AC can be associated with a single customer VID (e.g., VLAN-based service interfaces) or a bundle of customer VIDs (e.g., VLAN Bundle service interfaces).
  4. When the timer expires, each PE builds an ordered candidate list of the IP addresses of all the PE nodes attached to the ES (including itself) as explained in the modified Step 3 above. Any PE from which an Ethernet A-D per ES route has not been received is pruned from the list.
  5. When electing the DF for a given BD, a PE will not be considered to be a candidate until an Ethernet A-D per EVI route has been received from that PE. In other words, the ACS on the ES for a given PE must be UP so that the PE is considered to be a candidate for a given BD. For example, PE1 will not consider PE2 as a candidate for DF election for <ES12, VLAN-1> until an Ethernet A-D per EVI route is received from PE2 for <ES12, VLAN-1>.

  3. さらに、PE1、PE2、PE3は、ACが有効になるとすぐに、AC1、AC2、AC3、AC4についてEVIごとのイーサネットA-Dルートを広告します。ACは、単一の顧客VID（たとえば、VLANベースのサービスインターフェイス）に関連付けることも、顧客VIDのバンドル（たとえば、VLANバンドルのサービスインターフェイス）に関連付けることもできることに注意してください。
  4. タイマーが期限切れになると、各PEは、上記の変更されたステップ3で説明したように、ESに接続されたすべてのPEノード（自身を含む）のIPアドレスの順序付き候補リストを構築します。ESごとのイーサネットA-Dルートを受信していないPEは、リストから刈り込まれます。

4.1. AC-Influenced DF Election Capability for VLAN-Aware Bundle Services

4.1. VLAN対応バンドルサービスのためのAC影響型DF選出能力

The procedure described in Section 4 works for VLAN-based and VLAN Bundle service interfaces because, for those service types, a PE advertises only one Ethernet A-D per EVI route per <ES, VLAN> or <ES, VLAN Bundle>. In Section 4, an Ethernet Tag represents a given VLAN or VLAN Bundle for the purpose of DF election. The withdrawal of such a route means that the PE cannot forward traffic on that particular <ES, VLAN> or <ES, VLAN Bundle>; therefore, the PE can be removed from consideration for DF election.

Section 4で説明した手順は、VLANベースおよびVLANバンドルのサービスインターフェイスで機能します。これらのサービスタイプでは、PEは<ES, VLAN>または<ES, VLAN Bundle>ごとにEVIごとのイーサネットA-Dルートを1つだけ広告するためです。Section 4では、イーサネットタグは、DF選出のために所定のVLANまたはVLANバンドルを表します。このようなルートの取り消しは、PEがその特定の<ES, VLAN>または<ES, VLAN Bundle>上でトラフィックを転送できないことを意味します。したがって、そのPEをDF選出の検討対象から除外できます。

According to [RFC7432], in VLAN-aware Bundle services, the PE advertises multiple Ethernet A-D per EVI routes per <ES, VLAN Bundle> (one route per Ethernet Tag), while the DF election is still performed per <ES, VLAN Bundle>. The withdrawal of an individual route only indicates the unavailability of a specific AC and not necessarily all the ACs in the <ES, VLAN Bundle>.

[RFC7432]によると、VLAN対応バンドルのサービスでは、PEは<ES, VLAN Bundle>ごとに複数のEVIごとのイーサネットA-Dルート（イーサネットタグごとに1つのルート）を広告しますが、DF選出は依然として<ES, VLAN Bundle>ごとに行われます。個々のルートの取り消しは、特定のACが利用できないことを示すだけで、必ずしも<ES, VLAN Bundle>内のすべてのACが利用できないことを示すわけではありません。

This document modifies the DF election for VLAN-aware Bundle services in the following ways:

この文書は、VLAN対応バンドルのサービスのDF選出を次のように変更します。

  • After confirming that all the PEs in the ES advertise the AC-DF capability, a PE will perform a DF election per <ES, VLAN>, as opposed to per <ES, VLAN Bundle> as described in [RFC7432]. Now, the withdrawal of an Ethernet A-D per EVI route for a VLAN will indicate that the advertising PE's ACS is DOWN and the rest of the PEs in the ES can remove the PE from consideration for DF election in the <ES, VLAN>.
  • The PEs will now follow the procedures in Section 4.
  • ES内のすべてのPEがAC-DF能力を広告していることを確認した後、PEは、[RFC7432]で説明されている<ES, VLAN Bundle>ごとではなく、<ES, VLAN>ごとにDF選出を行います。これにより、VLANのEVIごとのイーサネットA-Dルートの取り消しは、広告していたPEのACSがDOWNであることを示すようになり、ES内の残りのPEは、その<ES, VLAN>のDF選出の検討対象からそのPEを除外できます。
  • これにより、PEはSection 4の手順に従います。

For example, assuming three bridge tables in PE1 for the same MAC-VRF (each one associated with a different Ethernet Tag, e.g., VLAN-1, VLAN-2, and VLAN-3), PE1 will advertise three Ethernet A-D per EVI routes for ES12. Each of the three routes will indicate the status of each of the three ACs in ES12. PE1 will be considered to be a valid candidate PE for DF election in <ES12, VLAN-1>, <ES12, VLAN-2>, and <ES12, VLAN-3> as long as its three routes are active. For instance, if PE1 withdraws the Ethernet A-D per EVI routes for <ES12, VLAN-1>, the PEs in ES12 will not consider PE1 as a suitable DF candidate for <ES12, VLAN-1>. PE1 will still be considered for <ES12, VLAN-2> and <ES12, VLAN-3>, since its routes are active.

たとえば、同じMAC-VRFについてPE1に3つのブリッジテーブル（それぞれが異なるイーサネットタグ、たとえばVLAN-1、VLAN-2、VLAN-3に関連付けられている）があると仮定すると、PE1はES12について3つのEVIごとのイーサネットA-Dルートを広告します。3つのルートはそれぞれ、ES12内の3つのACそれぞれの状態を示します。PE1は、3つのルートがアクティブである限り、<ES12, VLAN-1>、<ES12, VLAN-2>、<ES12, VLAN-3>のDF選出の有効な候補PEとみなされます。たとえば、PE1が<ES12, VLAN-1>のEVIごとのイーサネットA-Dルートを取り消した場合、ES12内のPEは、PE1を<ES12, VLAN-1>の適切なDF候補とはみなしません。PE1は、<ES12, VLAN-2>と<ES12, VLAN-3>についてはルートがアクティブであるため、引き続き考慮されます。

5. Solution Benefits

5. 解決策の利点

The solution described in this document provides the following benefits:

この文書で説明する解決策には、次の利点があります。

  1. It extends the DF election as defined in [RFC7432] to address the unfair load balancing and potential black-holing issues with the default DF election algorithm. The solution is applicable to the DF election in EVPN services [RFC7432] and EVPN VPWS [RFC8214].
  2. It defines a way to signal the DF election algorithm and capabilities intended by the advertising PE. This is done by defining the DF Election Extended Community, which allows the advertising PE to indicate its support for the capabilities defined in this document as well as any subsequently defined DF election algorithms or capabilities.
  3. It is backwards compatible with the procedures defined in [RFC7432]. If one or more PEs in the ES do not support the new procedures, they will all follow DF election as defined in [RFC7432].
  1. [RFC7432]で定義されているDF選出を拡張し、デフォルトのDF選出アルゴリズムにおける不公平な負荷分散と潜在的なブラックホール化の問題に対処します。この解決策は、EVPNサービス[RFC7432]およびEVPN VPWS [RFC8214]におけるDF選出に適用できます。
  2. 広告するPEが意図するDF選出アルゴリズムと能力を通知する方法を定義します。これは、DF選出拡張コミュニティーを定義することによって行われます。DF選出拡張コミュニティーにより、広告するPEは、この文書で定義する能力や、今後定義されるDF選出アルゴリズムや能力のサポートを示すことができます。
  3. [RFC7432]で定義されている手順と後方互換性があります。ES内の1つ以上のPEが新しい手順をサポートしていない場合、すべてのPEが[RFC7432]で定義されているDF選出に従います。

6. Security Considerations

6. セキュリティーに関する考慮事項

This document addresses some identified issues in the DF election procedures described in [RFC7432] by defining a new DF election framework. In general, this framework allows the PEs that are part of the same ES to exchange additional information and agree on the DF election type and capabilities to be used.

この文書は、新しいDF選出フレームワークを定義することにより、[RFC7432]で説明されているDF選出手順で特定された問題のいくつかに対処します。一般に、このフレームワークにより、同じESに属するPEは追加の情報を交換し、使用するDF選出のタイプと能力について合意できます。

By following the procedures in this document, the operator will minimize such undesirable situations as unfair load balancing, service disruption, and traffic black-holing. Because such situations could be purposely created by a malicious user with access to the configuration of one PE, this document also enhances the security of the network. Note that the network will not benefit from the new procedures if the DF election algorithm is not consistently configured on all the PEs in the ES (if there is no unanimity among all the PEs, the DF election algorithm falls back to the default DF election as provided in [RFC7432]). This behavior could be exploited by an attacker that manages to modify the configuration of one PE in the ES so that the DF election algorithm and capabilities in all the PEs in the ES fall back to the default DF election. If that is the case, the PEs will be exposed to the unfair load balancing, service disruption, and black-holing mentioned earlier.

この文書の手順に従うことで、運用者は、不公平な負荷分散、サービスの中断、トラフィックのブラックホール化といった望ましくない状況を最小限に抑えることができます。このような状況は、1つのPEの設定にアクセスできる悪意のあるユーザーによって意図的に作り出される可能性があるため、この文書はネットワークのセキュリティーも向上させます。DF選出アルゴリズムがES内のすべてのPEで一貫して設定されていない場合、ネットワークは新しい手順の恩恵を受けられないことに注意してください（すべてのPEの間で全員一致とならない場合、DF選出アルゴリズムは[RFC7432]で規定されているデフォルトのDF選出にフォールバックします）。この振る舞いは、ES内の1つのPEの設定を変更することに成功した攻撃者によって悪用される可能性があります。攻撃者はそれによって、ES内のすべてのPEのDF選出アルゴリズムと能力をデフォルトのDF選出にフォールバックさせることができます。その場合、PEは前述の不公平な負荷分散、サービスの中断、ブラックホール化にさらされます。

In addition, the new framework is extensible and allows for new security enhancements in the future. Note that such enhancements are out of scope for this document. Finally, since this document extends the procedures in [RFC7432], the same security considerations as those described in [RFC7432] are valid for this document.

さらに、この新しいフレームワークは拡張可能であり、将来の新しいセキュリティー強化を可能にします。そのような強化はこの文書の範囲外であることに注意してください。最後に、この文書は[RFC7432]の手順を拡張するものであるため、[RFC7432]で説明されているものと同じセキュリティーに関する考慮事項がこの文書にも当てはまります。
