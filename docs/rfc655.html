RFC 655

Telnet output formfeed disposition option

RFC 655

Telnetの出力改ページ処理オプション

1. Command name and code

1. コマンド名とコード

NAOFFD - 13
(Negotiate About Output Formfeed Disposition)

NAOFFD - 13
（Negotiate About Output Formfeed Disposition、出力改ページ処理に関するネゴシエーション）

2. Command meanings

2. コマンドの意味

In the following, we are discussing a simplex connection, as described in the NAOL and NAOP Telnet Options specifications.

以下では、NAOLおよびNAOPのTelnetオプションの仕様で説明されているような単方向（simplex）のコネクションについて述べます。

IAC DO NAOFFD
The data sender requests or agrees to negotiate about output formfeed disposition with the data receiver. In the case where agreement has been reached and in the absence of further subnegotiations, the data receiver is assumed to be handling output formfeeds.
IAC DON'T NAOFFD
The data sender refuses to negotiate about output formfeed disposition with the data receiver, or demands a return to the unnegotiated default mode.
IAC WILL NAOFFD
The data receiver requests or agrees to negotiate about output formfeed disposition with the sender. In the case where agreement has been reached and in the absence of further subnegotiations, the data receiver alone is assumed to be handling output formfeeds.
IAC WON'T NAOFFD
The data receiver refuses to negotiate about output formfeed disposition, or demands a return to the unnegotiated default mode.
IAC SB NAOFFD DS <8-bit value> IAC SE
The data sender specifies, with the 8-bit value, which party should handle formfeeds and what their disposition should be. The code for DS is 1.
IAC SB NAOFFD DR <8-bit value> IAC SE
The data receiver specifies, with the 8-bit value, which party should handle formfeeds and what their disposition should be. The code for DR is 0.
IAC DO NAOFFD
データ送信側が、データ受信側と出力改ページ（formfeed）の処理についてネゴシエーションすることを要求するか、またはそれに同意します。合意に達し、それ以上のサブネゴシエーションがない場合は、データ受信側が出力改ページを処理するものとみなします。
IAC DON'T NAOFFD
データ送信側が、データ受信側と出力改ページの処理についてネゴシエーションすることを拒否するか、またはネゴシエーションしていないデフォルトのモードに戻ることを要求します。
IAC WILL NAOFFD
データ受信側が、送信側と出力改ページの処理についてネゴシエーションすることを要求するか、またはそれに同意します。合意に達し、それ以上のサブネゴシエーションがない場合は、データ受信側だけが出力改ページを処理するものとみなします。
IAC WON'T NAOFFD
データ受信側が、出力改ページの処理についてネゴシエーションすることを拒否するか、またはネゴシエーションしていないデフォルトのモードに戻ることを要求します。
IAC SB NAOFFD DS <8-bit value> IAC SE
データ送信側が、8ビット値によって、どちらの側が改ページを処理すべきか、およびその処理方法をどうすべきかを指定します。DSのコードは1です。
IAC SB NAOFFD DR <8-bit value> IAC SE
データ受信側が、8ビット値によって、どちらの側が改ページを処理すべきか、およびその処理方法をどうすべきかを指定します。DRのコードは0です。

3. Default

3. デフォルト

DON'T NAOFFD/WON'T NAOFFD
In the default absence of negotiations concerning which party, data sender or data receiver, is handling output formfeeds, neither party is required to handle formfeeds and neither party is prohibited from handling them; but it is appropriate if at least the data receiver handles formfeed considerations, albeit primitively.
DON'T NAOFFD/WON'T NAOFFD
データ送信側とデータ受信側のどちらが出力改ページを処理するかについてのネゴシエーションがないデフォルトの状態では、どちらの側も改ページを処理することを要求されず、どちらの側もそれを処理することを禁止されません。ただし、少なくともデータ受信側が、原始的な方法であっても改ページに関する事柄を処理するのが適切です。

4. Motivation for the Option

4. このオプションの動機

Please refer to section 4 of the NAOL and of the NAOFFD Telnet option descriptions.

NAOLおよびNAOFFDのTelnetオプションの説明のセクション4を参照してください。

5. Description of the Option

5. このオプションの説明

The data sender and the data receiver use the 8-bit value along with the DS and DR SB commands as follows:

データ送信側とデータ受信側は、DSおよびDRのSBコマンドとともに、8ビット値を次のように使用します。

Table 1
8-bit value Meaning
0 Command sender suggests that he alone will handle formfeeds, for the connection.
1 to 250 Command sender suggests that the other party alone should handle formfeeds, but suggests that the indicated value be used. The value is the number of character-times to wait or number of NULs to insert in the data stream before sending the next data character.
251 Command sender suggests that the other party alone handle formfeeds, but suggests that each occurrence of the character be replaced by carriage-return/line-feed.
252 Command sender suggests that the other party alone handle formfeeds, but suggests that they be discarded.
253 Command sender suggests that the other party alone should handle formfeeds, but suggests that formfeeds be simulated.
254 Command sender suggests that the other party alone should handle output formfeeds but suggests waiting for a character to be transmitted (on the other simplex connection) before sending more data. Note that, due to the assynchrony of the two simplex connections, phase problems can occur with this option.
255 Command sender suggests that the other party alone should handle output formfeeds and suggests nothing about how it should be done.

8ビット値 意味
0 コマンド送信者は、このコネクションについて自分だけが改ページを処理することを提案します。
1～250 コマンド送信者は、相手側だけが改ページを処理すべきであると提案しますが、示した値を使用することも提案します。この値は、次のデータ文字を送信する前に待つ文字時間の数、またはデータストリームに挿入するNULの数です。
251 コマンド送信者は、相手側だけが改ページを処理することを提案しますが、その文字が現れるたびにキャリッジリターン／ラインフィードに置き換えることも提案します。

254 コマンド送信者は、相手側だけが出力改ページを処理すべきであると提案しますが、さらにデータを送信する前に（もう一方の単方向コネクションで）文字が送信されるのを待つことも提案します。2つの単方向コネクションは非同期であるため、このオプションでは位相の問題が起こりうることに注意してください。
255 コマンド送信者は、相手側だけが出力改ページを処理すべきであると提案し、それをどのように行うべきかについては何も提案しません。

The guiding rules are that:

指針となる規則は次のとおりです。

  1. if neither data receiver nor data sender wants to handle output formfeeds, the data receiver must do it, and
  2. if both data receiver and data sender want to handle output formfeeds, the data sender gets to do it.
  1. データ受信側もデータ送信側も出力改ページを処理することを望まない場合は、データ受信側がそれを行わなければなりません。
  2. データ受信側とデータ送信側の両方が出力改ページを処理することを望む場合は、データ送信側がそれを行います。

The reasoning for the former rule is that if neither wants to do it, then the default in the NAOFFD option dominates. If both want to do it, the sender, who is presumed to have special knowledge about the data, should be allowed to do it, taking into account any suggestions the receiver may make. Simulation is defined as the replacement of the formfeed character by enough line-feeds (only) to advance the paper (or line-pointer) to the top of the next page (or to the top of the terminal screen). Note that delays, controlled by the data sender, must consist of NUL characters inserted immediately after the formfeed character. This is necessary due to the assynchrony of network transmission. As with all option negotiations, neither party should suggest a state already in effect except to refuse to negotiate; changes should be acknowledged; and once refused, an option should not be resuggested until "something changes" (e.g., another process starts). At any time, either party can disable further negotiation by giving the appropriate WON'T NAOFFD or DON'T NAOFFD command.

前者の規則の根拠は、どちらもそれを行いたくない場合は、NAOFFDオプションのデフォルトが優先されるということです。両方がそれを行いたい場合は、データについて特別な知識を持っていると想定される送信側が、受信側が行う提案を考慮に入れたうえで、それを行えるようにすべきです。シミュレーションとは、改ページ文字を、用紙（または行ポインター）を次のページの先頭（または端末画面の先頭）まで進めるのに十分な数のラインフィード（だけ）に置き換えることと定義します。データ送信側が制御する遅延は、改ページ文字の直後に挿入したNUL文字で構成しなければならないことに注意してください。これは、ネットワーク伝送が非同期であるために必要です。すべてのオプションのネゴシエーションと同様に、どちらの側も、ネゴシエーションを拒否する場合を除いて、すでに有効になっている状態を提案すべきではありません。変更には確認応答をすべきです。また、いったん拒否されたオプションは、「何かが変わる」（たとえば、別のプロセスが開始する）まで再提案すべきではありません。どちらの側も、適切なWON'T NAOFFDまたはDON'T NAOFFDコマンドを送ることで、いつでもそれ以降のネゴシエーションを無効にできます。
