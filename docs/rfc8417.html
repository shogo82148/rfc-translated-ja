Security Event Token (SET)

RFC 8417

セキュリティーイベントトークン（SET）

Abstract

概要

This specification defines the Security Event Token (SET) data structure. A SET describes statements of fact from the perspective of an issuer about a subject. These statements of fact represent an event that occurred directly to or about a security subject, for example, a statement about the issuance or revocation of a token on behalf of a subject. This specification is intended to enable representing security- and identity-related events. A SET is a JSON Web Token (JWT), which can be optionally signed and/or encrypted. SETs can be distributed via protocols such as HTTP.

この仕様は、セキュリティーイベントトークン（Security Event Token: SET）のデータ構造を定義します。 SETは、サブジェクトについての事実の言明を、発行者の視点から記述するものです。 これらの事実の言明は、セキュリティーサブジェクトに直接起きた、あるいはセキュリティーサブジェクトに関して起きたイベントを表します。 たとえば、サブジェクトに代わってトークンが発行されたことや失効されたことについての言明です。 この仕様は、セキュリティーやアイデンティティーに関連するイベントを表現できるようにすることを目的としています。 SETはJSON Web Token（JWT）であり、必要に応じて署名や暗号化、またはその両方を施すことができます。 SETはHTTPなどのプロトコルを介して配布できます。

1. Introduction and Overview

1. はじめにと概要

This specification defines an extensible Security Event Token (SET) data structure, which can be exchanged using protocols such as HTTP. The specification builds on the JSON Web Token (JWT) format [RFC7519] in order to provide a self-contained token that can be optionally signed using JSON Web Signature (JWS) [RFC7515] and/or encrypted using JSON Web Encryption (JWE) [RFC7516].

この仕様は、拡張可能なセキュリティーイベントトークン（Security Event Token: SET）のデータ構造を定義します。 SETはHTTPなどのプロトコルを使って交換できます。 この仕様は、JSON Web Token（JWT）形式[RFC7519]を基盤として、JSON Web Signature（JWS）[RFC7515]による署名や、JSON Web Encryption（JWE）[RFC7516]による暗号化、またはその両方を必要に応じて施すことのできる自己完結型のトークンを提供します。

This specification profiles the use of JWT for the purpose of issuing SETs. This specification defines a base format used by profiling specifications to define actual events and their meanings. This specification uses non-normative example events to demonstrate how events can be constructed.

この仕様は、SETを発行する目的でのJWTの使い方をプロファイルします。 この仕様は、プロファイル仕様が実際のイベントとその意味を定義するために使う基本形式を定義します。 この仕様では、イベントをどのように構築できるかを示すために、非規範的なイベントの例を使います。

This specification is scoped to security- and identity-related events. While SETs may be used for other purposes, the specification only considers security and privacy concerns relevant to identity and personal information.

この仕様の対象は、セキュリティーやアイデンティティーに関連するイベントです。 SETはほかの目的に使われることもありますが、この仕様では、アイデンティティーと個人情報に関するセキュリティーとプライバシーの懸念のみを考慮します。

Security events are not commands issued between parties. A SET describes statements of fact from the perspective of an issuer about a subject (e.g., a web resource, token, IP address, the issuer itself). These statements of fact represent a logical event that occurred directly to or about a security subject, for example, a statement about the issuance or revocation of a token on behalf of a subject. A security subject may be permanent (e.g., a user account) or temporary (e.g., an HTTP session) in nature. A state change could describe a direct change of entity state, an implicit change of state, or other higher-level security statements such as:

セキュリティーイベントは、当事者間で発行されるコマンドではありません。 SETは、サブジェクト（たとえば、Webリソース、トークン、IPアドレス、発行者自身）についての事実の言明を、発行者の視点から記述するものです。 これらの事実の言明は、セキュリティーサブジェクトに直接起きた、あるいはセキュリティーサブジェクトに関して起きた論理的なイベントを表します。 たとえば、サブジェクトに代わってトークンが発行されたことや失効されたことについての言明です。 セキュリティーサブジェクトは、本質的に永続的なもの（たとえば、ユーザーアカウント）のこともあれば、一時的なもの（たとえば、HTTPセッション）のこともあります。 状態の変化は、エンティティーの状態の直接的な変化、暗黙的な状態の変化、またはそのほかの、次のようなより高レベルのセキュリティーの言明を記述できます。

  • The creation, modification, removal of a resource.
  • The resetting or suspension of an account.
  • The revocation of a security token prior to its expiry.
  • The logout of a user session.
  • An indication that a user has been given control of an email identifier that was previously controlled by another user.
  • リソースの作成、変更、削除
  • アカウントのリセットや停止
  • 有効期限前のセキュリティートークンの失効
  • ユーザーセッションのログアウト
  • 以前は別のユーザーが管理していた電子メール識別子の管理権限が、あるユーザーに与えられたことの通知

While subject state changes are often triggered by a user agent or security subsystem, the issuance and transmission of an event may occur asynchronously and in a back channel to the action that caused the change that generated the security event. Subsequently, a SET recipient, having received a SET, validates and interprets the received SET and takes its own independent actions, if any. For example, having been informed of a personal identifier being associated with a different security subject (e.g., an email address is being used by someone else), the SET recipient may choose to ensure that the new user is not granted access to resources associated with the previous user. Or, the SET recipient may not have any relationship with the subject, and no action is taken.

サブジェクトの状態の変化はユーザーエージェントやセキュリティーサブシステムによって引き起こされることが多いですが、イベントの発行と送信は、セキュリティーイベントを生じさせた変化を引き起こした操作とは非同期に、バックチャネルで行われることがあります。 その後、SETを受け取ったSET受信者は、受け取ったSETを検証して解釈し、もしあれば独自の判断で何らかの操作を行います。 たとえば、ある個人識別子が別のセキュリティーサブジェクトに関連付けられたこと（たとえば、電子メールアドレスが別の誰かに使われていること）を知らされたSET受信者は、以前のユーザーに関連付けられたリソースへのアクセスが新しいユーザーに許可されないようにすることを選択するかもしれません。 あるいは、SET受信者がそのサブジェクトと何の関係も持っておらず、何の操作も行わないこともあります。

While SET recipients will often take actions upon receiving SETs, security events cannot be assumed to be commands or requests. The intent of this specification is to define a syntax for statements of fact that SET recipients may interpret for their own purposes.

SET受信者はSETを受け取ったときに何らかの操作を行うことが多いですが、セキュリティーイベントがコマンドやリクエストであると想定することはできません。 この仕様の意図は、SET受信者が自らの目的のために解釈できる、事実の言明の構文を定義することです。

1.2. 定義

The following definitions are used with SETs:

SETでは次の定義を使います。

SET Issuer
A service provider that creates SETs to be sent to other service providers known as SET recipients.
SET Recipient
A SET recipient is an entity that receives SETs through some distribution method. A SET recipient is the same entity referred as a "recipient" in [RFC7519] or "receiver" in related specifications.
Subject
A SET describes an event or state change that has occurred to a subject. A subject might, for instance, be a principal (e.g., Section 4.1.2 of [RFC7519]), a web resource, an entity such as an IP address, or the issuer of the SET.
Event Identifier
A member name for an element of the JSON object that is the value of the "events" claim in a SET. This member name MUST be a URI.
Event Payload
A member value for an element of the JSON object that is the value of the "events" claim in a SET. This member value MUST be a JSON object.
Profiling Specification
A specification that profiles the SET data structure to define one or more specific event types and their associated claims and processing rules.
セキュリティーイベントトークン（Security Event Token: SET）
SETは、この仕様に準拠したJWT [RFC7519]です。
SET発行者（SET Issuer）
SET受信者と呼ばれるほかのサービスプロバイダーに送信するSETを作成するサービスプロバイダーです。

SET受信者は、何らかの配布方法を通じてSETを受け取るエンティティーです。 SET受信者は、[RFC7519]で「recipient」と呼ばれているもの、または関連する仕様で「receiver」と呼ばれているものと同じエンティティーです。

2. The Security Event Token (SET)

2. セキュリティーイベントトークン（SET）

A SET is a JWT [RFC7519] data structure that represents one or more related aspects of a security event that occurred to a subject. The JWT Claims Set in a SET has the following structure:

SETは、サブジェクトに起きたセキュリティーイベントの、互いに関連する1つ以上の側面を表すJWT [RFC7519]データ構造です。 SETのJWTクレームセットは次の構造を持ちます。

  • The top-level claims in the JWT Claims Set are called the SET "envelope". Some of these claims are present in every SET; others will be specific to particular SET profiles or profile families. Claims in the envelope SHOULD be registered in the "JSON Web Token Claims" registry [IANA.JWT.Claims] or be Public Claims or Private Claims, as defined in [RFC7519].
  • Envelope claims that are profiled and defined in this specification are used to validate the SET and provide information about the event data included in the SET. The "events" claim contains the event identifiers and event-specific data expressed about the security subject. The envelope MAY include event-specific or profile-specific data. The "events" claim value MUST be a JSON object that contains at least one member.
  • Each member of the "events" JSON object is a name/value pair. The JSON member name is a URI string value, which is the event identifier, and the corresponding value is a JSON object known as the event "payload". The payload JSON object contains claims that pertain to that event identifier and need not be registered as JWT claims. These claims are defined by the profiling specification that defines the event. An event with no payload claims SHALL be represented as the empty JSON object ("{}").

  • When multiple event identifiers are contained in a SET, they represent multiple aspects of the same state transition that occurred to the security subject. They are not intended to be used to aggregate distinct events about the same subject. Beyond this, the interpretation of SETs containing multiple event identifiers is out of scope for this specification; profiling specifications MAY define their own rules regarding their use of SETs containing multiple event identifiers, as described in Section 3. Possible uses of multiple values include, but are not limited to:

    • Values to provide classification information (e.g., threat type or level).
    • Additions to existing event representations.
    • Values used to link potential series of events.
    • Specific-purpose event URIs used between particular SET issuers and SET recipients.
  • JWTクレームセットのトップレベルのクレームは、SETの「エンベロープ（envelope）」と呼ばれます。 これらのクレームの一部はすべてのSETに存在し、そのほかは特定のSETプロファイルやプロファイルファミリーに固有のものになります。 エンベロープ内のクレームは、「JSON Web Token Claims」レジストリー[IANA.JWT.Claims]に登録されているか、[RFC7519]で定義されている公開クレーム（Public Claims）または非公開クレーム（Private Claims）であるべきです（SHOULD）。
  • この仕様でプロファイルおよび定義されるエンベロープのクレームは、SETを検証し、SETに含まれるイベントデータについての情報を提供するために使われます。 「events」クレームには、イベント識別子と、セキュリティーサブジェクトについて表現されたイベント固有のデータが含まれます。 エンベロープには、イベント固有またはプロファイル固有のデータを含めてもよいです（MAY）。 「events」クレームの値は、少なくとも1つのメンバーを含むJSONオブジェクトでなければなりません（MUST）。
  • 「events」JSONオブジェクトの各メンバーは名前と値のペアです。 JSONのメンバー名はイベント識別子であるURI文字列値で、対応する値はイベントの「ペイロード（payload）」と呼ばれるJSONオブジェクトです。 ペイロードのJSONオブジェクトには、そのイベント識別子に関係するクレームが含まれ、これらのクレームはJWTクレームとして登録する必要はありません。 これらのクレームは、そのイベントを定義するプロファイル仕様によって定義されます。 ペイロードのクレームを持たないイベントは、空のJSONオブジェクト（「{}」）として表現することになります（SHALL）。

  • SETに複数のイベント識別子が含まれている場合、それらはセキュリティーサブジェクトに起きた同一の状態遷移の複数の側面を表します。 それらは、同じサブジェクトについての別個のイベントを集約するために使うことを意図したものではありません。 これ以外の、複数のイベント識別子を含むSETの解釈は、この仕様の範囲外です。 セクション3で説明するように、プロファイル仕様は、複数のイベント識別子を含むSETの使い方について独自の規則を定義してもよいです（MAY）。 複数の値の使い方としては、次のようなものが考えられますが、これらに限定されません。

    • 分類情報（たとえば、脅威の種類やレベル）を提供するための値
    • 既存のイベント表現への追加
    • 一連のイベントである可能性のあるものを結び付けるために使う値
    • 特定のSET発行者とSET受信者の間で使う、特定目的のイベントURI

2.1. Illustrative Examples

2.1. 説明のための例

This section illustrates several possible uses of SETs through non-normative examples.

このセクションでは、非規範的な例を通して、SETのいくつかの使い方を説明します。

2.1.1. SCIM Example

2.1.1. SCIMの例

The following example shows the JWT Claims Set for a hypothetical System for Cross-domain Identity Management (SCIM) [RFC7644] password reset SET. Such a SET might be used by a receiver as a trigger to reset active user-agent sessions related to the identified user.

次の例は、仮想的なSystem for Cross-domain Identity Management（SCIM）[RFC7644]のパスワードリセットのSETのJWTクレームセットを示しています。 このようなSETは、受信者が、識別されたユーザーに関連するアクティブなユーザーエージェントのセッションをリセットするきっかけとして使えるでしょう。

The JWT Claims Set usage consists of:

JWTクレームセットは次のように使われています。

  • The "events" claim specifying the hypothetical SCIM URN ("urn:ietf:params:scim:event:passwordReset") for a password reset, and a second value, "https://example.com/scim/event/passwordResetExt", that is used to provide additional event information such as the current count of resets.
  • The "iss" claim, denoting the SET issuer.
  • The "sub" claim, specifying the SCIM resource URI that was affected.
  • The "aud" claim, specifying the intended audiences for the event. (The syntax of the "aud" claim is defined in Section 4.1.3 of [RFC7519].)
  • 「events」クレームは、パスワードリセットを表す仮想的なSCIMのURN（「urn:ietf:params:scim:event:passwordReset」）と、2つ目の値「https://example.com/scim/event/passwordResetExt」を指定しています。 2つ目の値は、現在のリセット回数などの追加のイベント情報を提供するために使われます。
  • 「iss」クレームは、SET発行者を示しています。
  • 「sub」クレームは、影響を受けたSCIMリソースのURIを指定しています。
  • 「aud」クレームは、イベントの意図されたオーディエンスを指定しています。 （「aud」クレームの構文は[RFC7519]のセクション4.1.3で定義されています。）

The SET contains two event payloads:

このSETには2つのイベントペイロードが含まれています。

  • The "id" claim represents SCIM's unique identifier for a subject.
  • The second payload identified by "https://example.com/scim/event/passwordResetExt" and the payload claim "resetAttempts" conveys the current count of reset attempts. In this example, while the count is a simple factual statement for the issuer, the meaning of the value (a count) is up to the receiver. As an example, such a value might be used by the receiver to infer increasing risk.
  • 「id」クレームは、サブジェクトに対するSCIMの一意な識別子を表します。
  • 「https://example.com/scim/event/passwordResetExt」で識別される2つ目のペイロードとペイロードクレーム「resetAttempts」は、現在のリセット試行回数を伝えます。 この例では、回数は発行者にとっては単純な事実の言明ですが、その値（回数）の意味は受信者次第です。 たとえば、受信者はこのような値を使ってリスクの増大を推測するかもしれません。

In this example, the SCIM event indicates that a password has been updated and the current password reset count is 5. Notice that the value for "resetAttempts" is in the event payload of an event used to convey this information.

この例では、SCIMイベントは、パスワードが更新されたことと、現在のパスワードリセット回数が5であることを示しています。 「resetAttempts」の値は、この情報を伝えるために使われるイベントのイベントペイロードの中にあることに注意してください。

2.2. Core SET Claims

2.2. SETの中核となるクレーム

The following claims from [RFC7519] are profiled for use in SETs:

[RFC7519]の次のクレームを、SETで使うためにプロファイルします。

"iss" (Issuer) Claim
As defined by Section 4.1.1 of [RFC7519], this claim contains a string identifying the service provider publishing the SET (the issuer). In some cases, the issuer of the SET will not be the issuer associated with the security subject of the SET. Therefore, implementers cannot assume that the issuers are the same unless the profiling specification specifies that they are for SETs conforming to that profile. This claim is REQUIRED.
"iat" (Issued At) Claim
As defined by Section 4.1.6 of [RFC7519], this claim contains a value representing when the SET was issued. This claim is REQUIRED.
"jti" (JWT ID) Claim
As defined by Section 4.1.7 of [RFC7519], this claim contains a unique identifier for the SET. The identifier MUST be unique within a particular event feed and MAY be used by clients to track whether a particular SET has already been received. This claim is REQUIRED.
"aud" (Audience) Claim
As defined by Section 4.1.3 of [RFC7519], this claim contains one or more audience identifiers for the SET. This claim is RECOMMENDED.
"sub" (Subject) Claim

As defined by Section 4.1.2 of [RFC7519], this claim contains a StringOrURI value representing the principal that is the subject of the SET. This is usually the entity whose "state" was changed. For example:

  • an IP Address was added to a blacklist;
  • a URI representing a user resource that was modified; or,
  • a token identifier (e.g. "jti") for a revoked token.

If used, the profiling specification MUST define the content and format semantics for the value. This claim is OPTIONAL, as the principal for any given profile may already be identified without the inclusion of a subject claim. Note that some SET profiles MAY choose to convey event subject information in the event payload (either using the "sub" member name or another name), particularly if the subject information is relative to issuer information that is also conveyed in the event payload, which may be the case for some identity SET profiles.

"exp" (Expiration Time) Claim
As defined by Section 4.1.4 of [RFC7519], this claim is the time after which the JWT MUST NOT be accepted for processing. In the context of a SET, however, this notion does not typically apply, since a SET represents something that has already occurred and is historical in nature. Therefore, its use is NOT RECOMMENDED. (Also, see Section 4.1 for additional reasons not to use the "exp" claim in some SET use cases.)
「iss」（Issuer）クレーム
[RFC7519]のセクション4.1.1で定義されているとおり、このクレームには、SETを公開するサービスプロバイダー（発行者）を識別する文字列が含まれます。 場合によっては、SETの発行者は、SETのセキュリティーサブジェクトに関連付けられた発行者とは異なります。 したがって、実装者は、プロファイル仕様がそのプロファイルに準拠するSETについて同じであると規定していない限り、これらの発行者が同じであると想定することはできません。 このクレームは要求されています（REQUIRED）。
「iat」（Issued At）クレーム
[RFC7519]のセクション4.1.6で定義されているとおり、このクレームには、SETがいつ発行されたかを表す値が含まれます。 このクレームは要求されています（REQUIRED）。
「jti」（JWT ID）クレーム
[RFC7519]のセクション4.1.7で定義されているとおり、このクレームには、SETの一意な識別子が含まれます。 この識別子は、特定のイベントフィード内で一意でなければなりません（MUST）。 クライアントは、特定のSETをすでに受け取ったかどうかを追跡するためにこの識別子を使ってもよいです（MAY）。 このクレームは要求されています（REQUIRED）。
「aud」（Audience）クレーム
[RFC7519]のセクション4.1.3で定義されているとおり、このクレームには、SETの1つ以上のオーディエンス識別子が含まれます。 このクレームは推奨されます（RECOMMENDED）。
「sub」（Subject）クレーム

[RFC7519]のセクション4.1.2で定義されているとおり、このクレームには、SETのサブジェクトであるプリンシパルを表すStringOrURI値が含まれます。 これは通常、「状態」が変化したエンティティーです。 たとえば、次のようなものです。

  • ブラックリストに追加されたIPアドレス
  • 変更されたユーザーリソースを表すURI
  • 失効したトークンのトークン識別子（たとえば「jti」）

このクレームを使う場合、プロファイル仕様は、その値の内容と形式のセマンティクスを定義しなければなりません（MUST）。 どのプロファイルでも、サブジェクトのクレームを含めなくてもプリンシパルがすでに識別されている場合があるので、このクレームは選択できます（OPTIONAL）。 一部のSETプロファイルは、イベントのサブジェクトの情報を（「sub」メンバー名またはほかの名前を使って）イベントペイロードで伝えることを選択してもよいです（MAY）。 これは特に、サブジェクトの情報が、同じくイベントペイロードで伝えられる発行者の情報に相対的なものである場合で、一部のアイデンティティーのSETプロファイルではそうなることがあります。

「exp」（Expiration Time）クレーム
[RFC7519]のセクション4.1.4で定義されているとおり、このクレームは時刻であり、その時刻以降、JWTを処理のために受け入れてはなりません（MUST NOT）。 しかし、SETはすでに起きたことを表すもので、本質的に過去の記録であるため、SETの文脈では通常この概念は当てはまりません。 したがって、このクレームを使うことは推奨されません（NOT RECOMMENDED）。 （一部のSETのユースケースで「exp」クレームを使うべきではない追加の理由については、セクション4.1も参照してください。）

The following new claims are defined by this specification:

この仕様では、次の新しいクレームを定義します。

"events" (Security Events) Claim

This claim contains a set of event statements that each provide information describing a single logical event that has occurred about a security subject (e.g., a state change to the subject). Multiple event identifiers with the same value MUST NOT be used. The "events" claim MUST NOT be used to express multiple independent logical events.

The value of the "events" claim is a JSON object whose members are name/value pairs whose names are URIs identifying the event statements being expressed. Event identifiers SHOULD be stable values (e.g., a permanent URL for an event specification). For each name present, the corresponding value MUST be a JSON object. The JSON object MAY be an empty object ("{}"), or it MAY be a JSON object containing data described by the profiling specification.

"txn" (Transaction Identifier) Claim
An OPTIONAL string value that represents a unique transaction identifier. In cases in which multiple related JWTs are issued, the transaction identifier claim can be used to correlate these related JWTs. Note that this claim can be used in JWTs that are SETs and also in JWTs using non-SET profiles.
"toe" (Time of Event) Claim
A value that represents the date and time at which the event occurred. This value is a NumericDate (see Section 2 of [RFC7519]). By omitting this claim, the issuer indicates that they are not sharing an event time with the recipient. (Note that in some use cases, the represented time might be approximate; statements about the accuracy of this field MAY be made by profiling specifications.) This claim is OPTIONAL.
「events」（Security Events）クレーム

このクレームには、イベントの言明の集合が含まれます。 各言明は、セキュリティーサブジェクトについて起きた単一の論理的なイベント（たとえば、サブジェクトの状態の変化）を記述する情報を提供します。 同じ値を持つ複数のイベント識別子を使ってはなりません（MUST NOT）。 「events」クレームを、複数の独立した論理的なイベントを表現するために使ってはなりません（MUST NOT）。

「events」クレームの値はJSONオブジェクトで、そのメンバーは、表現されるイベントの言明を識別するURIを名前とする名前と値のペアです。 イベント識別子は、安定した値（たとえば、イベント仕様の恒久的なURL）であるべきです（SHOULD）。 存在する名前それぞれについて、対応する値はJSONオブジェクトでなければなりません（MUST）。 そのJSONオブジェクトは空のオブジェクト（「{}」）でもよいです（MAY）。 また、プロファイル仕様で記述されたデータを含むJSONオブジェクトでもよいです（MAY）。

「txn」（Transaction Identifier）クレーム
一意なトランザクション識別子を表す、選択可能な（OPTIONAL）文字列値です。 関連する複数のJWTが発行される場合に、トランザクション識別子クレームを使って、これらの関連するJWTを相関付けることができます。 このクレームは、SETであるJWTでも、SET以外のプロファイルを使うJWTでも使えることに注意してください。
「toe」（Time of Event）クレーム
イベントが起きた日時を表す値です。 この値はNumericDateです（[RFC7519]のセクション2を参照）。 このクレームを省略することによって、発行者は、受信者とイベントの時刻を共有していないことを示します。 （ユースケースによっては、表される時刻が近似値である場合があることに注意してください。 このフィールドの正確さについての言明を、プロファイル仕様で行ってもよいです（MAY）。） このクレームは選択できます（OPTIONAL）。

2.3. Explicit Typing of SETs

2.3. SETの明示的な型付け

This specification registers the "application/secevent+jwt" media type, which can be used to indicate that the content is a SET. SETs MAY include this media type in the "typ" header parameter of the JWT representing the SET to explicitly declare that the JWT is a SET. This MUST be included if the SET could be used in an application context in which it could be confused with other kinds of JWTs.

この仕様は、コンテンツがSETであることを示すために使える「application/secevent+jwt」メディアタイプを登録します。 SETは、JWTがSETであることを明示的に宣言するために、SETを表すJWTの「typ」ヘッダーパラメーターにこのメディアタイプを含めてもよいです（MAY）。 SETがほかの種類のJWTと混同されうるアプリケーションの文脈で使われる可能性がある場合は、これを含めなければなりません（MUST）。

Per the definition of "typ" in Section 4.1.9 of [RFC7515], it is RECOMMENDED that the "application/" prefix be omitted. Therefore, the "typ" value used SHOULD be "secevent+jwt".

[RFC7515]のセクション4.1.9の「typ」の定義に従い、「application/」プレフィックスを省略することが推奨されます（RECOMMENDED）。 したがって、使用する「typ」の値は「secevent+jwt」であるべきです（SHOULD）。

3. Requirements for SET Profiles

3. SETプロファイルの要件

Profiling specifications of this specification define actual SETs to be used in particular use cases. These profiling specifications define the syntax and semantics of SETs conforming to that SET profile and rules for validating those SETs. Profiling specifications SHOULD define syntax, semantics, subject identification, and validation.

この仕様のプロファイル仕様は、特定のユースケースで使われる実際のSETを定義します。 これらのプロファイル仕様は、そのSETプロファイルに準拠するSETの構文とセマンティクス、およびそれらのSETを検証するための規則を定義します。 プロファイル仕様は、構文、セマンティクス、サブジェクトの識別、検証を定義すべきです（SHOULD）。

Syntax

The syntax of the SETs defined, including:

Top-Level Claims
Claims and values in the JWT Claims Set. Examples are claims defined by the JWT specification [RFC7519], this specification, and by the profiling specification.
Event Payload
The JSON data structure contents and format, containing event-specific information, if any (see Section 1.2).
Semantics
Defining the semantics of the SET contents for SETs utilizing the profile is equally important. Possibly most important is defining the procedures used to validate the SET issuer and to obtain the keys controlled by the issuer that were used for cryptographic operations used in the JWT representing the SET. For instance, some profiles may define an algorithm for retrieving the SET issuer's keys that uses the "iss" claim value as its input. Likewise, if the profile allows (or requires) that the JWT be unsecured, the means by which the integrity of the JWT is ensured MUST be specified.
Subject Identification
Profiling specifications MUST define how the event subject is identified in the SET, as well as how to differentiate between the event subject's issuer and the SET issuer, if applicable. It is NOT RECOMMENDED for profiling specifications to use the "sub" claim in cases in which the subject is not globally unique and has a different issuer from the SET itself.
Validation

Profiling specifications MUST clearly specify the steps that a recipient of a SET utilizing that profile MUST perform to validate that the SET is both syntactically and semantically valid.

Among the syntax and semantics of SETs that a profiling specification may define is whether the value of the "events" claim may contain multiple members, and what processing instructions are employed in the single- and multiple-valued cases for SETs conforming to that profile. Many valid choices are possible. For instance, some profiles might allow multiple event identifiers to be present and specify that any that are not understood by recipients be ignored, thus enabling extensibility. Other profiles might allow multiple event identifiers to be present but require that all be understood if the SET is to be accepted. Some profiles might require that only a single value be present. All such choices are within the scope of profiling specifications to define.

構文（Syntax）

定義されるSETの構文です。次のものを含みます。

トップレベルのクレーム（Top-Level Claims）
JWTクレームセット内のクレームと値です。 例としては、JWT仕様[RFC7519]、この仕様、およびプロファイル仕様で定義されるクレームがあります。
イベントペイロード（Event Payload）
イベント固有の情報があればそれを含む、JSONデータ構造の内容と形式です（セクション1.2を参照）。
セマンティクス（Semantics）
そのプロファイルを利用するSETについて、SETの内容のセマンティクスを定義することも同様に重要です。 おそらく最も重要なのは、SET発行者を検証する手順と、SETを表すJWTで使われる暗号操作に使われた、発行者が管理する鍵を取得する手順を定義することです。 たとえば、一部のプロファイルでは、「iss」クレームの値を入力として使ってSET発行者の鍵を取得するアルゴリズムを定義するかもしれません。 同様に、プロファイルがJWTを未保護にすることを許可する（または要求する）場合は、JWTの完全性を確保する手段を規定しなければなりません（MUST）。
サブジェクトの識別（Subject Identification）
プロファイル仕様は、SETにおいてイベントのサブジェクトをどのように識別するか、および該当する場合はイベントのサブジェクトの発行者とSET発行者をどのように区別するかを定義しなければなりません（MUST）。 サブジェクトがグローバルに一意ではなく、SET自体とは異なる発行者を持つ場合に、プロファイル仕様が「sub」クレームを使うことは推奨されません（NOT RECOMMENDED）。
検証（Validation）

プロファイル仕様は、そのプロファイルを利用するSETが構文的にもセマンティクス的にも有効であることを検証するためにSETの受信者が実行しなければならない（MUST）手順を、明確に規定しなければなりません（MUST）。

プロファイル仕様が定義しうるSETの構文とセマンティクスの中には、「events」クレームの値に複数のメンバーを含められるかどうかや、そのプロファイルに準拠するSETについて、単一の値の場合と複数の値の場合にどのような処理手順を用いるかが含まれます。 有効な選択肢は数多くあります。 たとえば、複数のイベント識別子の存在を許可し、受信者が理解できないものは無視するよう規定することで、拡張性を可能にするプロファイルもあるでしょう。 複数のイベント識別子の存在を許可するものの、SETを受け入れるにはそのすべてを理解することを要求するプロファイルもあるでしょう。 単一の値のみが存在することを要求するプロファイルもあるでしょう。 こうした選択はすべて、プロファイル仕様が定義する範囲内のことです。

4. Preventing Confusion between SETs and Other JWTs

4. SETとほかのJWTとの混同の防止

Because [RFC7519] states that "all claims that are not understood by implementations MUST be ignored", there is a consideration that a SET might be confused with another kind of JWT from the same issuer. Unless this confusion is prevented, this might enable an attacker who possesses a SET to use it in a context in which another kind of JWT is expected, or vice versa. This section presents concrete techniques for preventing confusion between SETs and several other specific kinds of JWTs, as well as generic techniques for preventing possible confusion between SETs and other kinds of JWTs.

[RFC7519]は「実装が理解できないクレームはすべて無視しなければなりません（MUST）」と述べているため、SETが同じ発行者からの別の種類のJWTと混同されるおそれがあるという考慮事項があります。 この混同を防がなければ、SETを所持する攻撃者が、別の種類のJWTが期待される文脈でSETを使ったり、その逆を行ったりできてしまうかもしれません。 このセクションでは、SETとほかのいくつかの特定の種類のJWTとの混同を防ぐ具体的な手法と、SETとほかの種類のJWTとの混同の可能性を防ぐ汎用的な手法を示します。

4.1. Distinguishing SETs from ID Tokens

4.1. SETとIDトークンの区別

A SET might be confused with an ID Token [OpenID.Core] if a SET is mistakenly or maliciously used in a context requiring an ID Token. If a SET could otherwise be interpreted as a valid ID Token (because it includes the required claims for an ID Token and valid issuer and audience claim values for an ID Token), then that SET profile MUST require that the "exp" claim not be present in the SET. Because "exp" is a required claim in ID Tokens, valid ID Token implementations will reject such a SET if presented as if it were an ID Token.

IDトークンを要求する文脈でSETが誤って、または悪意を持って使われた場合、SETがIDトークン[OpenID.Core]と混同されるおそれがあります。 SETがほかの点では有効なIDトークンとして解釈されうる場合（IDトークンに必要なクレームと、IDトークンとして有効な発行者とオーディエンスのクレーム値を含んでいるため）、そのSETプロファイルは、SETに「exp」クレームが存在しないことを要求しなければなりません（MUST）。 「exp」はIDトークンの必須クレームなので、有効なIDトークンの実装は、そのようなSETがIDトークンであるかのように提示された場合に拒否します。

Excluding "exp" from SETs that could otherwise be confused with ID Tokens is actually defense in depth. In any OpenID Connect contexts in which an attacker could attempt to substitute a SET for an ID Token, the SET would actually already be rejected as an ID Token because it would not contain the correct "nonce" claim value for the ID Token to be accepted in contexts for which substitution is possible.

ほかの点ではIDトークンと混同されうるSETから「exp」を除外することは、実際には多層防御です。 攻撃者がIDトークンの代わりにSETを使おうとしうるOpenID Connectのどの文脈においても、SETは、実際にはすでにIDトークンとして拒否されるでしょう。 なぜなら、置き換えが可能な文脈でIDトークンが受け入れられるために必要な、正しい「nonce」クレーム値をSETは含んでいないからです。

Note that the use of explicit typing, as described in Section 2.3, will not achieve disambiguation between ID Tokens and SETs, as the ID Token validation rules do not use the "typ" header parameter value.

セクション2.3で説明した明示的な型付けを使っても、IDトークンとSETの曖昧さは解消されないことに注意してください。 IDトークンの検証規則では「typ」ヘッダーパラメーターの値を使わないためです。

4.2. Distinguishing SETs from Access Tokens

4.2. SETとアクセストークンの区別

OAuth 2.0 [RFC6749] defines access tokens as being opaque. Nonetheless, some implementations implement access tokens as JWTs. Because the structure of these JWTs is implementation specific, ensuring that a SET cannot be confused with such an access token is, therefore, also implementation specific, generally. Nonetheless, it is recommended that SET profiles employ the following strategies to prevent possible substitutions of SETs for access tokens in contexts in which that might be possible:

OAuth 2.0 [RFC6749]では、アクセストークンは不透明なものとして定義されています。 それにもかかわらず、一部の実装はアクセストークンをJWTとして実装しています。 これらのJWTの構造は実装固有であるため、SETがそのようなアクセストークンと混同されないようにすることも、一般的には実装固有になります。 それでも、SETプロファイルは、SETがアクセストークンの代わりに使われうる文脈でそのような置き換えが起きないよう、次の戦略を採用することが推奨されます。

  • Prohibit use of the "exp" claim, as is done to prevent ID Token confusion.
  • Where possible, use a separate "aud" claim value to distinguish between the SET recipient and the protected resource that is the audience of an access token.
  • Modify access token validation systems to check for the presence of the "events" claim as a means to detect security event tokens. This is particularly useful if the same endpoint may receive both types of tokens.
  • Employ explicit typing, as described in Section 2.3, and modify access token validation systems to use the "typ" header parameter value.
  • IDトークンとの混同を防ぐために行うのと同様に、「exp」クレームの使用を禁止する。
  • 可能な場合は、別個の「aud」クレーム値を使い、SET受信者と、アクセストークンのオーディエンスである保護されたリソースとを区別する。
  • セキュリティーイベントトークンを検出する手段として「events」クレームの存在をチェックするよう、アクセストークンの検証システムを変更する。 これは、同じエンドポイントが両方の種類のトークンを受け取る可能性がある場合に特に有用です。
  • セクション2.3で説明した明示的な型付けを採用し、「typ」ヘッダーパラメーターの値を使うようアクセストークンの検証システムを変更する。

4.3. Distinguishing SETs from Other Kinds of JWTs

4.3. SETとほかの種類のJWTの区別

JWTs are now being used in application areas beyond the identity applications in which they first appeared. For instance, the "Session Initiation Protocol (SIP) Via Header Field Parameter to Indicate Received Realm" [RFC8055] and "PASSporT: Personal Assertion Token" [RFC8225] specifications both define JWT profiles that use mostly or completely different sets of claims than are used by ID Tokens. If it would otherwise be possible for an attacker to substitute a SET for one of these (or other) kinds of JWTs, then the SET profile must be defined in such a way that any substituted SET will result in its rejection when validated as the intended kind of JWT.

JWTは現在、最初に登場したアイデンティティーのアプリケーション以外の分野でも使われています。 たとえば、「Session Initiation Protocol (SIP) Via Header Field Parameter to Indicate Received Realm」[RFC8055]と「PASSporT: Personal Assertion Token」[RFC8225]の仕様は、どちらも、IDトークンで使われるものとはほとんど、あるいは完全に異なるクレームの集合を使うJWTプロファイルを定義しています。 攻撃者がこれらの（またはほかの）種類のJWTの代わりにSETを使えてしまう可能性があるなら、置き換えられたSETが、意図された種類のJWTとして検証されたときに拒否されるように、SETプロファイルを定義する必要があります。

The most direct way to prevent confusion is to employ explicit typing, as described in Section 2.3, and modify applicable token validation systems to use the "typ" header parameter value. This approach can be employed for new systems but may not be applicable to existing systems.

混同を防ぐ最も直接的な方法は、セクション2.3で説明した明示的な型付けを採用し、該当するトークンの検証システムが「typ」ヘッダーパラメーターの値を使うよう変更することです。 この方法は新しいシステムでは採用できますが、既存のシステムには適用できない場合があります。

Another way to ensure that a SET is not confused with another kind of JWT is to have the JWT validation logic reject JWTs containing an "events" claim unless the JWT is intended to be a SET. This approach can be employed for new systems but may not be applicable to existing systems. Validating that the JWT has an "events" claim will be effective in preventing attackers from passing other kinds of JWTs off as SETs.

SETが別の種類のJWTと混同されないようにする別の方法は、JWTの検証ロジックで、JWTがSETとして意図されたものでない限り、「events」クレームを含むJWTを拒否することです。 この方法は新しいシステムでは採用できますが、既存のシステムには適用できない場合があります。 JWTが「events」クレームを持つことを検証すれば、攻撃者がほかの種類のJWTをSETとして通用させることを効果的に防げます。

For many use cases, the simplest way to prevent substitution is requiring that the SET not include claims that are required for the kind of JWT that might be the target of an attack. For example, for [RFC8055], the "sip_callid" claim could be omitted and for [RFC8225], the "orig" claim could be omitted.

多くのユースケースでは、置き換えを防ぐ最も簡単な方法は、攻撃の対象となりうる種類のJWTに必須のクレームをSETに含めないよう要求することです。 たとえば、[RFC8055]については「sip_callid」クレームを省略でき、[RFC8225]については「orig」クレームを省略できます。

In many contexts, simple measures such as these will accomplish the task, should confusion otherwise even be possible. Note that this topic is being explored in a more general fashion in "JSON Web Token Best Current Practices" [JWT-BCP]. The proposed best practices in that document may also be applicable for particular SET profiles and use cases.

多くの文脈では、そもそも混同が起こりうるとしても、こうした簡単な対策で十分に目的を達成できます。 このトピックは、「JSON Web Token Best Current Practices」[JWT-BCP]でより一般的な形で検討されていることに注意してください。 その文書で提案されているベストプラクティスは、特定のSETプロファイルやユースケースにも適用できるかもしれません。

5. Security Considerations

5. セキュリティーに関する考慮事項

5.1. Confidentiality and Integrity

5.1. 機密性と完全性

SETs may contain sensitive information. Therefore, methods for distribution of events SHOULD require the use of a transport-layer security mechanism when distributing events. Parties MUST support TLS 1.2 [RFC5246] or a higher version and MAY support additional transport-layer mechanisms meeting its security requirements. When using TLS, the client MUST perform a TLS server certificate check, per [RFC6125]. Implementation security considerations for TLS can be found in "Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)" [RFC7525].

SETには機密情報が含まれている場合があります。 したがって、イベントを配布する方法は、イベントを配布する際にトランスポート層のセキュリティーメカニズムの使用を要求すべきです（SHOULD）。 当事者は、TLS 1.2 [RFC5246]またはそれ以降のバージョンをサポートしなければなりません（MUST）。 また、そのセキュリティー要件を満たす追加のトランスポート層のメカニズムをサポートしてもよいです（MAY）。 TLSを使う場合、クライアントは、[RFC6125]に従ってTLSサーバー証明書のチェックを実行しなければなりません（MUST）。 TLSの実装に関するセキュリティーの考慮事項は、「Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)」[RFC7525]にあります。

Security events distributed through third parties or that carry personally identifiable information MUST be encrypted using JWE [RFC7516] or secured for confidentiality by other means.

第三者を通じて配布されるセキュリティーイベントや、個人を特定できる情報を運ぶセキュリティーイベントは、JWE [RFC7516]を使って暗号化するか、ほかの手段で機密性を確保しなければなりません（MUST）。

Unless integrity of the JWT is ensured by other means, it MUST be signed using JWS [RFC7515] by an issuer that is trusted to do so for the use case so that the SET can be authenticated and validated by the SET recipient.

JWTの完全性がほかの手段で確保されていない限り、SET受信者がSETを認証し検証できるように、JWTは、そのユースケースにおいて署名することを信頼された発行者によって、JWS [RFC7515]を使って署名されなければなりません（MUST）。

5.2. Delivery

5.2. 配信

This specification does not define a delivery mechanism for SETs. In addition to confidentiality and integrity (discussed above), implementers and profiling specifications must consider the consequences of delivery mechanisms that are not secure and/or not assured. For example, while a SET may be end-to-end secured using JWE encrypted SETs, without (mutual) TLS, there is no assurance that the correct endpoint received the SET and that it could be successfully processed.

この仕様では、SETの配信メカニズムを定義しません。 （上述の）機密性と完全性に加えて、実装者とプロファイル仕様は、安全でない配信メカニズムや、配信が保証されない配信メカニズム（またはその両方）がもたらす結果を考慮する必要があります。 たとえば、JWEで暗号化されたSETを使ってSETをエンドツーエンドで保護できたとしても、（相互）TLSがなければ、正しいエンドポイントがSETを受け取ったことや、そのSETが正常に処理できたことは保証されません。

5.3. Sequencing

5.3. 順序付け

This specification defines no means of ordering multiple SETs in a sequence. Depending on the type and nature of the events represented by SETs, order may or may not matter. For example, in provisioning, event order is critical -- an object cannot be modified before it is created. In other SET types, such as a token revocation, the order of SETs for revoked tokens does not matter. If, however, the event conveys a logged in or logged out status for a user subject, then order becomes important.

この仕様では、複数のSETを一連の順序に並べる手段を定義しません。 SETで表されるイベントの種類や性質によって、順序が重要な場合もあれば、そうでない場合もあります。 たとえば、プロビジョニングではイベントの順序が決定的に重要です。オブジェクトは作成される前に変更することはできません。 トークンの失効など、ほかの種類のSETでは、失効したトークンについてのSETの順序は重要ではありません。 しかし、イベントがユーザーサブジェクトのログイン状態やログアウト状態を伝える場合は、順序が重要になります。

Profiling specifications and implementers SHOULD take caution when using timestamps such as "iat" to define order. Distributed systems will have some amount of clock skew. Thus, time by itself will not guarantee order.

プロファイル仕様と実装者は、順序を定義するために「iat」などのタイムスタンプを使う場合には注意を払うべきです（SHOULD）。 分散システムでは、ある程度のクロックスキューがあります。 したがって、時刻だけでは順序は保証されません。

Specifications profiling SET SHOULD define a mechanism for detecting order or sequence of events when the order matters. For example, the "txn" claim could contain an ordered value (e.g., a counter) that the issuer includes, although just as for timestamps, ensuring such ordering can be difficult in distributed systems.

SETをプロファイルする仕様は、順序が重要な場合に、イベントの順序や並びを検出するメカニズムを定義すべきです（SHOULD）。 たとえば、「txn」クレームに、発行者が含める順序付きの値（たとえば、カウンター）を含めることができます。 ただし、タイムスタンプの場合と同様に、分散システムではそのような順序付けを確保することが難しい場合があります。

5.4. Timing Issues

5.4. タイミングの問題

When SETs are delivered asynchronously and/or out-of-band with respect to the original action that incurred the security event, it is important to consider that a SET might be delivered to a SET recipient in advance of or behind the process that caused the event. For example, a user having been required to log out and then log back in again, may cause a "token revoked" SET to be issued, typically causing the receiver to reset all active sessions at the receiver that are related to that user. If a revocation SET arrives at the same time as the user agent re-logs in, timing could cause problems by erroneously treating the new user session as logged out. Profiling specifications SHOULD be careful to consider both SET expression and timing issues. For example, it might be more appropriate to revoke a specific session or ID Token rather than a general logout statement about a "user". Alternatively, profiling specifications could use timestamps that allow new sessions to be started immediately after a stated logout event time.

セキュリティーイベントを引き起こした元の操作に対して、SETが非同期に、または帯域外（あるいはその両方）で配信される場合、SETが、イベントを引き起こした処理よりも先に、または後にSET受信者に配信されうることを考慮することが重要です。 たとえば、ユーザーがいったんログアウトしてから再びログインすることを要求されたことで「token revoked」のSETが発行され、通常は受信者がそのユーザーに関連する受信者側のすべてのアクティブなセッションをリセットすることになる場合があります。 ユーザーエージェントが再ログインするのと同時に失効のSETが到着すると、タイミングによっては、新しいユーザーセッションを誤ってログアウトしたものとして扱ってしまうという問題が起きる可能性があります。 プロファイル仕様は、SETの表現とタイミングの問題の両方を慎重に考慮すべきです（SHOULD）。 たとえば、「ユーザー」についての一般的なログアウトの言明よりも、特定のセッションやIDトークンを失効させるほうが適切な場合があります。 あるいは、プロファイル仕様では、記載されたログアウトイベントの時刻の直後から新しいセッションを開始できるようなタイムスタンプを使うこともできます。

5.5. Preventing Confusion

5.5. 混同の防止

Also, see Section 4 above for both additional security considerations and normative text on preventing SETs from being confused with other kinds of JWTs.

SETがほかの種類のJWTと混同されるのを防ぐことに関する追加のセキュリティーの考慮事項と規範的な記述については、上記のセクション4も参照してください。

6. Privacy Considerations

6. プライバシーに関する考慮事項

If a SET needs to be retained for audit purposes, the signature can be used to provide verification of its authenticity.

監査のためにSETを保持する必要がある場合は、署名を使ってその真正性を検証できます。

SET issuers SHOULD attempt to specialize SETs so that their content is targeted to the specific business and protocol needs of the intended SET recipients.

SET発行者は、SETの内容が、意図されたSET受信者の特定のビジネス上およびプロトコル上の必要性に的を絞ったものになるよう、SETを特化させるよう努めるべきです（SHOULD）。

When sharing personally identifiable information or information that is otherwise considered confidential to affected users, SET issuers and recipients should have the appropriate legal agreements and user consent and/or terms of service in place.

個人を特定できる情報や、影響を受けるユーザーにとってそれ以外の点で機密とみなされる情報を共有する場合、SET発行者と受信者は、適切な法的合意を整えたうえで、ユーザーの同意と利用規約のいずれかまたは両方を用意しておくべきです。

The propagation of subject identifiers can be perceived as personally identifiable information. Where possible, SET issuers and recipients SHOULD devise approaches that prevent propagation -- for example, the passing of a salted hash value that requires the SET recipient to know the subject.

サブジェクト識別子の伝播は、個人を特定できる情報とみなされる場合があります。 可能な場合、SET発行者と受信者は、伝播を防ぐ方法を考案すべきです（SHOULD）。 たとえば、SET受信者がサブジェクトを知っていることを必要とする、ソルト付きハッシュ値を渡す方法です。

In some cases, it may be possible for a SET recipient to correlate different events and thereby gain information about a subject that the SET issuer did not intend to share. For example, a SET recipient might be able to use "iat" values or highly precise "toe" values to determine that two otherwise un-relatable events actually relate to the same real-world event. The union of information from both events could allow a SET recipient to de-anonymize data or recognize that unrelated identifiers relate to the same individual. SET issuers SHOULD take steps to minimize the chance of event correlation, when such correlation would constitute a privacy violation. For instance, they could use approximate values for the "toe" claim or arbitrarily delay SET issuance, where such delay can be tolerated.

場合によっては、SET受信者が異なるイベントを相関付け、それによってSET発行者が共有するつもりのなかったサブジェクトについての情報を得ることができるかもしれません。 たとえば、SET受信者は、「iat」の値や非常に精度の高い「toe」の値を使って、ほかの点では関連付けられない2つのイベントが、実際には現実世界の同じイベントに関連していると判断できるかもしれません。 両方のイベントからの情報を合わせることで、SET受信者がデータの匿名性を解除したり、無関係な識別子が同じ個人に関連していると認識したりできるかもしれません。 そのような相関付けがプライバシーの侵害になる場合、SET発行者は、イベントの相関付けの可能性を最小限に抑える措置を講じるべきです（SHOULD）。 たとえば、「toe」クレームに近似値を使ったり、遅延が許容される場合にはSETの発行を任意に遅らせたりできます。
