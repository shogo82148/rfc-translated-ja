RFC 10051

Task Extensions to iCalendar

RFC 10051

iCalendarのタスク拡張

Abstract

概要

The "VTODO" calendar component in the Internet Calendaring and Scheduling Core Object Specification (iCalendar; RFC 5545) has seen limited adoption and use, mainly for personal reminders and to-do lists.

インターネットのカレンダーとスケジューリングのコアオブジェクト仕様（iCalendar、RFC 5545）の「VTODO」カレンダーコンポーネントは、主に個人的なリマインダーやToDoリストのために使われるにとどまり、採用や利用は限られてきました。

This document updates RFC 5545 and defines extensions to "VTODO" to provide improved status tracking, scheduling, and specification of tasks to allow its use in other contexts, such as process control and project management.

この文書はRFC 5545を更新し、状態の追跡、スケジューリング、タスクの仕様記述を改善するための「VTODO」の拡張を定義します。これにより、プロセス制御やプロジェクト管理など、ほかの文脈でも「VTODO」を使えるようにします。

It also defines how Calendaring Extensions to WebDAV (CalDAV) (RFC 4791) servers can be extended to support certain automated task management behaviors.

また、WebDAVのカレンダー拡張（CalDAV）（RFC 4791）のサーバーを拡張して、特定の自動化されたタスク管理の振る舞いをサポートする方法も定義します。

1. Introduction

1. はじめに

This document specifies extensions to the Internet Calendaring and Scheduling Core Object Specification (iCalendar) [RFC5545] and associated protocols in order to enhance the structured communication and execution of tasks. The enhancements allow for the communication, time planning, and scheduling of tasks by and between automated systems (e.g., taxi dispatch systems, smart power grids [WsCalendar], and business process management systems), as well as for human-centered tasks.

この文書は、タスクの構造化されたやり取りと実行を強化するために、インターネットのカレンダーとスケジューリングのコアオブジェクト仕様（iCalendar）[RFC5545]と関連するプロトコルへの拡張を規定します。この強化により、人間中心のタスクだけでなく、自動化されたシステム（たとえば、タクシー配車システム、スマートグリッド[WsCalendar]、ビジネスプロセス管理システム）による、またはそれらの間でのタスクのやり取り、時間計画、スケジューリングが可能になります。

A "task" is a representation of an item of work assigned to an individual or organization. In the iCalendar Object Model [RFC5545] the representation of tasks is by "VTODO" calendar components. Tasks can be identified in a number of situations, either informally as ad hoc tasks in personal to-do lists or more formally in business processes (ranging from repetitive workflows to adaptive cases and trouble ticketing) and project management (whether for large-scale construction projects or collaborative software development).

「タスク」とは、個人または組織に割り当てられた作業項目の表現です。iCalendarオブジェクトモデル[RFC5545]では、タスクは「VTODO」カレンダーコンポーネントで表現されます。タスクはさまざまな状況で見られます。個人のToDoリストにある場当たり的なタスクのように非公式なものもあれば、ビジネスプロセス（繰り返し行うワークフローから、適応型ケース管理やトラブルチケット管理まで）やプロジェクト管理（大規模な建設プロジェクトであれ、共同でのソフトウェア開発であれ）におけるタスクのように、より公式なものもあります。

The extensions specified in this document enhance and standardize the following:

この文書で規定する拡張は、次の事項を強化し、標準化します。

  • The specification of tasks: How a task type is defined and the relationships between tasks; see Section 4.
  • Task planning and scheduling: Improved specification of deadlines and estimated time for completion; see Section 5.
  • Task assignment and status reporting: The addition of "VSTATUS" (Section 8) allows for more detailed reports; see Section 7.
  • タスクの仕様：タスクの種類の定義方法と、タスク間の関係。Section 4を参照してください。
  • タスクの計画とスケジューリング：期限と完了までの見積もり時間の指定の改善。Section 5を参照してください。
  • タスクの割り当てとステータスの報告：「VSTATUS」（Section 8）の追加により、より詳細な報告が可能になります。Section 7を参照してください。

These extensions are defined within the context of an overall architecture for task calendaring and scheduling, which elaborates that supported by [RFC5545] and related standards.

これらの拡張は、タスクのカレンダー管理とスケジューリングのための全体的なアーキテクチャーの文脈の中で定義されます。このアーキテクチャーは、[RFC5545]と関連する標準がサポートするアーキテクチャーを詳細化したものです。

1.1. Terms and Definitions

1.1. 用語と定義

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

The notation used in this memo to (re-)define iCalendar elements is ABNF [RFC5234], as used by [RFC5545]. Any syntax elements shown below that are not explicitly defined in this specification come from iCalendar [RFC5545].

このメモでiCalendarの要素を定義（または再定義）するために使う表記法は、[RFC5545]で使われているのと同じABNF [RFC5234]です。以下に示す構文要素のうち、この仕様で明示的に定義されていないものは、iCalendar [RFC5545]に由来します。

Calendaring and scheduling roles are referred to in quoted-strings of text with the first character of each word in uppercase. For example, "Organizer" refers to the role of a "Calendar User" (CU) within the scheduling protocol.

カレンダーとスケジューリングにおける役割は、各単語の最初の文字を大文字にした、引用符で囲まれた文字列で表します。たとえば、「Organizer」は、スケジューリングプロトコルにおける「Calendar User」（CU）の役割を指します。

Calendar components defined by [RFC5545] and updating specifications are referred to with capitalized quoted-strings of text, followed by the words "calendar component". For example, "VEVENT" calendar component refers to the event calendar component, "VTODO" calendar component refers to the to-do calendar component, and "VJOURNAL" calendar component refers to the daily journal calendar component.

[RFC5545]とそれを更新する仕様で定義されているカレンダーコンポーネントは、大文字の引用符で囲まれた文字列の後に「カレンダーコンポーネント」という語を続けて表します。たとえば、「VEVENT」カレンダーコンポーネントはイベントのカレンダーコンポーネントを、「VTODO」カレンダーコンポーネントはToDoのカレンダーコンポーネントを、「VJOURNAL」カレンダーコンポーネントは日々のジャーナルのカレンダーコンポーネントを指します。

Scheduling methods are referred to with capitalized quoted-strings of text. For example, "REQUEST" refers to the method for requesting a scheduling calendar component be created or modified, and "REPLY" refers to the method the recipient of a request uses to update their status with the "Organizer" of the calendar component.

スケジューリングのメソッドは、大文字の引用符で囲まれた文字列で表します。たとえば、「REQUEST」はスケジューリングのカレンダーコンポーネントの作成や変更を要求するためのメソッドを指し、「REPLY」はリクエストの受信者がカレンダーコンポーネントの「Organizer」に自身のステータスを更新するために使うメソッドを指します。

Properties defined by [RFC5545] and updating specifications are referred to with capitalized quoted-strings of text, followed by the word "property". For example, the "ATTENDEE" property refers to the iCalendar property used to convey the calendar address of a "Calendar User".

[RFC5545]とそれを更新する仕様で定義されているプロパティーは、大文字の引用符で囲まれた文字列の後に「プロパティー」という語を続けて表します。たとえば、「ATTENDEE」プロパティーは、「Calendar User」のカレンダーアドレスを伝えるために使われるiCalendarのプロパティーを指します。

Property parameters defined by [RFC5545] and updating specifications are referred to with lowercase quoted-strings of text, followed by the word "parameter". For example, the "value" parameter refers to the iCalendar property parameter used to override the default data type for a property value.

[RFC5545]とそれを更新する仕様で定義されているプロパティーパラメーターは、小文字の引用符で囲まれた文字列の後に「パラメーター」という語を続けて表します。たとえば、「value」パラメーターは、プロパティーの値のデフォルトのデータ型を上書きするために使われるiCalendarのプロパティーパラメーターを指します。

Enumerated values defined by this specification are referred to with capitalized text, either alone or followed by the word "value".

この仕様で定義する列挙値は、大文字のテキストで表し、単独で、または「値」という語を続けて使います。

In tables, the quoted-string text is specified without quotes in order to minimize the table length.

表の中では、表の長さを抑えるために、引用符で囲まれた文字列を引用符なしで記載します。

Terms defined and used in this specification include:

この仕様で定義され使われる用語には、次のものがあります。

Assignee:

A calendar user assigned to perform a given task. An assignee is equivalent to an "Attendee" of a task.

BPMS:

Business Process Management Software

CU:

Calendar User. A person or software system that accesses or modifies calendar information.

CUA:

Calendar User Agent. This may be one of the following:

  1. Software with which the CU communicates with a calendar service or local calendar store to access calendar information.
  2. Software that gathers calendar data on the CU's behalf.
Candidate:

A calendar user who might be able to perform a given task, prior to actually being assigned the task, e.g., a dispatcher has a list of taxi drivers (candidates) from which one will be selected to pick up a passenger.

Organizer:

A calendar user who creates a calendar item, requests free/busy information, or publishes free/busy information. It is an "Organizer" who invites "Attendees" [RFC5545].

Observer:

A calendar user interested in a calendar component, e.g., a manager may have interest in all tasks that have not been completed. Often represented as an "Attendee" with the "role" parameter set to NON-PARTICIPANT.

Resource:

A resource in the scheduling context is any shared entity that can be scheduled by a calendar user but does not control its own attendance status. Examples of such resources are locations such as a bookable conference room or equipment such as projectors.

Task:

A representation of an item of work that can be assigned to one or more task actor assignees. In [RFC5545], these are "VTODO" calendar components, which are groupings of component properties and possibly "VALARM" calendar components that represent an action item or assignment.

担当者（Assignee）：

与えられたタスクを実行するよう割り当てられたカレンダーユーザー。担当者は、タスクの「Attendee」と同等です。

BPMS：

ビジネスプロセス管理ソフトウェア（Business Process Management Software）

CU：

カレンダーユーザー（Calendar User）。カレンダー情報にアクセスしたり、カレンダー情報を変更したりする人またはソフトウェアシステム。

CUA：

カレンダーユーザーエージェント（Calendar User Agent）。次のいずれかです。

  1. CUがカレンダー情報にアクセスするために、カレンダーサービスやローカルのカレンダーストアとやり取りする際に使うソフトウェア。
  2. CUに代わってカレンダーデータを収集するソフトウェア。
候補者（Candidate）：

実際にタスクを割り当てられる前の段階で、与えられたタスクを実行できる可能性があるカレンダーユーザー。たとえば、配車係はタクシー運転手（候補者）のリストを持っており、その中から1人が乗客を迎えに行くよう選ばれます。

オーガナイザー（Organizer）：

カレンダーアイテムを作成したり、空き時間情報を要求したり、空き時間情報を公開したりするカレンダーユーザー。「Attendee」を招待するのは「Organizer」です[RFC5545]。

オブザーバー（Observer）：

カレンダーコンポーネントに関心を持つカレンダーユーザー。たとえば、管理者は完了していないすべてのタスクに関心を持つかもしれません。多くの場合、「role」パラメーターをNON-PARTICIPANTに設定した「Attendee」として表されます。

リソース（Resource）：

スケジューリングの文脈におけるリソースとは、カレンダーユーザーがスケジュールできるものの、自身の出席ステータスを制御しない共有のエンティティーです。このようなリソースの例としては、予約可能な会議室のような場所や、プロジェクターのような機器があります。

タスク（Task）：

1人以上のタスクアクターの担当者に割り当てることができる作業項目の表現。[RFC5545]では、タスクは「VTODO」カレンダーコンポーネントです。これは、アクションアイテムや割り当てを表すコンポーネントプロパティーと、場合によっては「VALARM」カレンダーコンポーネントをまとめたものです。

2. Task Architecture

2. タスクアーキテクチャー

A reference architecture for task calendaring and scheduling is defined in order to identify the key logical elements involved in task management and the interfaces between them to enable interoperability. Central to this architecture is the Calendar and Scheduling System. The logical elements identified here establish an appropriate separation of concerns and clarify the responsibilities of different elements. However, the architecture does not prescribe the binding or packaging of elements, i.e., software systems may be developed where some elements are tightly bound and the interfaces between bound elements are not exposed. The task architecture is also described in [TARCH].

タスク管理に関わる主要な論理要素と、相互運用性を実現するためのそれらの間のインターフェースを特定するために、タスクのカレンダー管理とスケジューリングのための参照アーキテクチャーを定義します。このアーキテクチャーの中心となるのは、カレンダー・スケジューリングシステムです。ここで特定する論理要素によって、適切な関心の分離が確立され、さまざまな要素の責任が明確になります。ただし、このアーキテクチャーは要素の結合やパッケージングを規定するものではありません。つまり、一部の要素が密に結合され、結合された要素間のインターフェースが公開されないソフトウェアシステムを開発しても構いません。タスクアーキテクチャーは[TARCH]でも説明されています。

2.1. Task Architecture Elements

2.1. タスクアーキテクチャーの要素

The following logical elements form the task architecture that this specification is based on:

この仕様の基礎となるタスクアーキテクチャーは、次の論理要素で構成されます。

Task Actors:

Various calendar users that may be involved in the monitoring or performing of a task. The set of actors includes Organizers, Observers, Resources, Assignees, and Candidates.

Task Organizer:

The creator of a task who also determines task assignment and scheduling and monitors task progress.

Task Domain Data:

This is any domain-specific data that may be acted on or that provides context for performing a task.

Task-Specific Application:

A task-specific application renders the data concerning the task (including task domain data) for presentation and manipulation by a task actor.

Process Logic:

Determines under what conditions one or more tasks are generated and the actions to take upon task completion or upon the occurrence (or non-occurrence) of some other status event.

Task Trigger:

An event that gives rise to the generation of a task according to Process Logic. Task triggers can come from many sources including, for example, a task being requested through the calendaring system or a status change in the progression of a business process being managed by a business process management or enterprise resource planning (ERP) system.

Task Assignment Rules:

Govern how actors are assigned to a task. A range of different assignment patterns [WfRP] may be considered, including the two general cases:

  1. Delegation to a named actor or group of actors
  2. Advertising to a pool of actors for self-selection

In either case, the assignment may be made based on a variety of criteria including, name, availability, skills, capacity, etc.

Task Generating System:

A system that creates and assigns tasks in response to some initiating event (task trigger). Process Logic defines task creation, while Task Assignment Rules determine task assignment. This system also tracks the status of tasks and will initiate further actions based upon the status. A Task Generating System can take many forms, such as a Business Process Management System, Project Management System, Bug Tracking System, and Building Control System. A Task Generating System may also be a human. In iCalendar terms the Task Generating System is the "Organizer".

Task creation, assignment, and tracking coordinated by a human "Organizer" is a special case of a Task Generating System. In this case, Task Assignment Rules and Process Logic may be either explicit or tacit.

Calendar and Scheduling System:

A software system that stores, publishes, and synchronizes calendar data such as events, tasks, and journal entries for actors. In the context of tasks, this includes schedules (i.e., allocated time and availability to perform tasks) and task lists. A calendar and scheduling system typically consists of server and client software components.

タスクアクター（Task Actors）：

タスクの監視や実行に関わる可能性のあるさまざまなカレンダーユーザー。アクターの集合には、Organizer、Observer、Resource、Assignee、Candidateが含まれます。

タスクオーガナイザー（Task Organizer）：

タスクの作成者であり、タスクの割り当てとスケジューリングを決定し、タスクの進捗を監視する者。

タスクドメインデータ（Task Domain Data）：

タスクの実行において操作の対象となる、またはタスクを実行するための文脈を提供する、ドメイン固有のあらゆるデータです。

タスク固有アプリケーション（Task-Specific Application）：

タスク固有アプリケーションは、タスクに関するデータ（タスクドメインデータを含む）を、タスクアクターが閲覧したり操作したりできるように描画します。

プロセスロジック（Process Logic）：

どのような条件で1つ以上のタスクが生成されるか、そしてタスクの完了時や、ほかの何らかのステータスイベントの発生（または不発生）時にどのようなアクションを取るかを決定します。

タスクトリガー（Task Trigger）：

プロセスロジックにしたがってタスクの生成を引き起こすイベント。タスクトリガーはさまざまなところから発生します。たとえば、カレンダーシステムを通じてタスクが要求されることや、ビジネスプロセス管理システムやエンタープライズリソースプランニング（ERP）システムで管理されているビジネスプロセスの進行においてステータスが変化することなどがあります。

タスク割り当てルール（Task Assignment Rules）：

アクターをタスクにどのように割り当てるかを管理します。さまざまな割り当てパターン[WfRP]が考えられ、次の2つの一般的なケースがあります。

  1. 名前で指定されたアクターまたはアクターのグループへの委任
  2. アクターのプールに公示し、アクター自身に選択させる

いずれの場合も、名前、空き状況、スキル、処理能力など、さまざまな基準に基づいて割り当てを行うことができます。

タスク生成システム（Task Generating System）：

何らかの起点となるイベント（タスクトリガー）に応じてタスクを作成し、割り当てるシステム。 タスクの作成はプロセスロジックが定義し、タスクの割り当てはタスク割り当てルールが決定します。このシステムはタスクのステータスも追跡し、そのステータスに基づいてさらなるアクションを開始します。タスク生成システムは、ビジネスプロセス管理システム、プロジェクト管理システム、バグ追跡システム、ビル制御システムなど、さまざまな形を取ります。タスク生成システムが人間であることもあります。iCalendarの用語では、タスク生成システムは「Organizer」です。

人間の「Organizer」が調整するタスクの作成、割り当て、追跡は、タスク生成システムの特殊なケースです。この場合、タスク割り当てルールとプロセスロジックは、明示的なこともあれば暗黙的なこともあります。

カレンダー・スケジューリングシステム（Calendar and Scheduling System）：

アクターのためのイベント、タスク、ジャーナルエントリーなどのカレンダーデータを保存、公開、同期するソフトウェアシステム。タスクの文脈では、これにはスケジュール（つまり、タスクを実行するために割り当てられた時間と空き状況）とタスクリストが含まれます。カレンダー・スケジューリングシステムは、通常、サーバーとクライアントのソフトウェアコンポーネントで構成されます。

It is not within the scope of this document to specify how Process Logic or Task Assignment Rules are codified. Such logic and rules may be codified in a variety of ways, including conventional programming languages (e.g., C++ and Java) or process modeling languages (e.g., Business Process Model and Notation (BPMN) [BPMN]).

プロセスロジックやタスク割り当てルールをどのように記述するかを規定することは、この文書の範囲外です。このようなロジックやルールは、従来のプログラミング言語（たとえば、C++やJava）やプロセスモデリング言語（たとえば、Business Process Model and Notation（BPMN）[BPMN]）など、さまざまな方法で記述できます。

2.2. Architecture Foundations

2.2. アーキテクチャーの基盤

The key standards that enable interoperability between the logical elements of the architecture are iCalendar [RFC5545] and the associated protocols. Task and task status are represented by the "VTODO" calendar component. Protocols include, in particular, the iCalendar Transport-Independent Interoperability Protocol (iTIP) [RFC5546] for task assignment and scheduling and the Calendaring Extensions to WebDAV (CalDAV) [RFC4791] for client server communication.

アーキテクチャーの論理要素間の相互運用性を実現する主要な標準は、iCalendar [RFC5545]と関連するプロトコルです。タスクとタスクのステータスは「VTODO」カレンダーコンポーネントで表現されます。プロトコルとしては、特に、タスクの割り当てとスケジューリングのためのiCalendarトランスポート非依存相互運用プロトコル（iTIP）[RFC5546]と、クライアントとサーバー間の通信のためのWebDAVのカレンダー拡張（CalDAV）[RFC4791]があります。

Additionally, this specification uses definitions from "Support for iCalendar Relationships" [RFC9253]. The "LINK", "REFID", "RELATED-TO", and "CONCEPT" properties enable context and a rich set of relationships between tasks and other calendar components to be specified.

さらに、この仕様は「Support for iCalendar Relationships」[RFC9253]の定義を使います。「LINK」、「REFID」、「RELATED-TO」、「CONCEPT」の各プロパティーにより、文脈と、タスクとほかのカレンダーコンポーネントとの間の豊富な関係を指定できます。

4. Task Specification

4. タスクの仕様

The specification of tasks must be semantically explicit in order for them to be managed within the context of a business process or project and understood by both humans and IT systems. The "VTODO" calendar component [RFC5545] only provides for simple ad hoc tasks or to-do lists and is therefore extended by this specification as follows:

タスクをビジネスプロセスやプロジェクトの文脈の中で管理し、人間とITシステムの両方が理解できるようにするには、タスクの仕様が意味的に明示的である必要があります。「VTODO」カレンダーコンポーネント[RFC5545]は単純な場当たり的なタスクやToDoリストにしか対応していないため、この仕様で次のように拡張します。

Task Type:

Explicitly what type of task is to be performed is identified.

Task Context and Relationships:

How a specific task relates to other tasks and other objects that need to be understood for the effective execution of a task.

Task-Specific Data:

The form and content of domain data provided as input to a task and/or that may be output from a task.

Organizer and Attendee:

Recognizes that a task "Organizer" or "Attendee" can be an automated system.

タスクの種類：

どのような種類のタスクを実行するのかを明示的に識別します。

タスクの文脈と関係：

特定のタスクが、タスクを効果的に実行するために理解しておく必要があるほかのタスクやほかのオブジェクトと、どのように関係しているか。

タスク固有のデータ：

タスクへの入力として与えられる、またはタスクから出力される可能性のあるドメインデータの形式と内容。

OrganizerとAttendee：

タスクの「Organizer」や「Attendee」が自動化されたシステムである可能性を考慮します。

4.1. Task Type

4.1. タスクの種類

The "CONCEPT" property [RFC9253] is used to identify the type of task, for example:

「CONCEPT」プロパティー[RFC9253]は、タスクの種類を識別するために使います。たとえば、次のようになります。

CONCEPT:http://example.com/task/delivery
CONCEPT:http://example.com/task/delivery

4.2. Task Context and Relationships

4.2. タスクの文脈と関係

The "LINK" property [RFC9253] specifies a link to external information, which may provide context for the task. For example:

「LINK」プロパティー[RFC9253]は、外部の情報へのリンクを指定します。この外部の情報は、タスクの文脈を提供することがあります。たとえば、次のようになります。

LINK;LINKREL=describedby;VALUE=URI:
 mid:752142.141482.307E5@mx123.example.com
LINK;LINKREL=describedby;VALUE=URI:
 mid:752142.141482.307E5@mx123.example.com

The external information may consist of data to be manipulated in performing the task.

外部の情報は、タスクの実行において操作されるデータで構成されることもあります。

The "LINK" property can be used to relate a domain-specific service to the task. For example, it might be a URI pointing to a web page where the status of the task can be directly manipulated.

「LINK」プロパティーは、ドメイン固有のサービスをタスクに関連付けるために使うことができます。たとえば、タスクのステータスを直接操作できるWebページを指すURIにすることが考えられます。

Note: The link relations below are for illustration only.

注：以下のリンク関係は説明のためだけのものです。

LINK;LINKREL="vacation-system";VALUE=URI:
 http://example.com/vacation-approval?id=1234
LINK;LINKREL="vacation-system";VALUE=URI:
 http://example.com/vacation-approval?id=1234

Additionally, it might be used to link data specific to the task, for example, an electronic copy of a signature taken to confirm delivery of a package.

また、タスク固有のデータをリンクするために使うこともできます。たとえば、荷物の配達を確認するために取得した署名の電子的なコピーなどです。

LINK;LINKREL="electronic-signature";VALUE=URI:
 http://example.com/delivery/sig1234.jpg
LINK;LINKREL="electronic-signature";VALUE=URI:
 http://example.com/delivery/sig1234.jpg

The "REFID" property [RFC9253] is used to identify a key used to group tasks by that key.

「REFID」プロパティー[RFC9253]は、タスクをグループ化するためのキーを識別するために使います。

REFID:Manhattan

REFID:1234567890
REFID:Manhattan

REFID:1234567890

Extensions to the "RELATED-TO" property defined in [RFC9253] allow temporal relationships between tasks as found in project management to be specified as well as parent/child relationships and dependencies (DEPENDS-ON). Tasks ("VTODO" calendar components) may also be related to other calendar components, for example, a "VEVENT" calendar component used to block time to perform a task.

[RFC9253]で定義されている「RELATED-TO」プロパティーの拡張により、親子関係や依存関係（DEPENDS-ON）に加えて、プロジェクト管理で見られるようなタスク間の時間的な関係を指定できます。タスク（「VTODO」カレンダーコンポーネント）は、ほかのカレンダーコンポーネントと関係付けることもできます。たとえば、タスクを実行するための時間を確保するために使われる「VEVENT」カレンダーコンポーネントなどです。

5. Task Deadlines, Milestones, and Time Planning

5. タスクの期限、マイルストーン、時間計画

5.1. Deadlines

5.1. 期限

Deadlines for starting and finishing a task are defined by the "DTSTART", "DUE", and "DURATION" properties. The "DTSTART" property represents the earliest start time for beginning work on a task. The "DUE" or "DTSTART" + "DURATION" properties represent the latest finish time for a task. Thus, these properties define a "window" within which a task has to be performed. However, [RFC5545] provides no way to indicate how long the task is expected to take. This document defines a new "ESTIMATED-DURATION" property, in Section 10.1, to allow the estimated time that a task should take to be specified separately from the deadlines for starting and finishing a task. This supports time planning by enabling calendar user agents to display when tasks should occur, which allows calendar users to visualize when tasks should be performed and to allocate time to them accordingly.

タスクの開始と終了の期限は、「DTSTART」、「DUE」、「DURATION」の各プロパティーで定義されます。「DTSTART」プロパティーは、タスクの作業を開始できる最も早い開始時刻を表します。「DUE」プロパティー、または「DTSTART」と「DURATION」プロパティーの組み合わせは、タスクの最も遅い終了時刻を表します。したがって、これらのプロパティーは、タスクを実行しなければならない「時間枠」を定義します。しかし、[RFC5545]には、タスクにどれくらいの時間がかかると見込まれるかを示す方法がありません。この文書は、タスクにかかる見積もり時間を、タスクの開始と終了の期限とは別に指定できるように、新しい「ESTIMATED-DURATION」プロパティーをSection 10.1で定義します。これにより、カレンダーユーザーエージェントはタスクをいつ行うべきかを表示できるようになり、時間計画がサポートされます。カレンダーユーザーは、タスクをいつ実行すべきかを視覚的に把握し、それに応じてタスクに時間を割り当てられるようになります。

5.2. Milestones

5.2. マイルストーン

A task that has intermediary deadlines (i.e., milestones) MUST be expressed by child "VTODO" calendar components (i.e., subtasks associated with each of the milestones) in conjunction with the "RELATED-TO" property to relate the parent and child tasks.

中間的な期限（つまり、マイルストーン）を持つタスクは、子の「VTODO」カレンダーコンポーネント（つまり、各マイルストーンに関連付けられたサブタスク）と、親タスクと子タスクを関係付ける「RELATED-TO」プロパティーを組み合わせて表現しなければなりません（MUST）。

6. Task Scheduling and Assignment

6. タスクのスケジューリングと割り当て

Tasks are assigned to actors using one or more "ATTENDEE" properties [RFC5545] and/or one or more "PARTICIPANT" calendar components [RFC9073], as described in Section 7.4.

タスクは、Section 7.4で説明するように、1つ以上の「ATTENDEE」プロパティー[RFC5545]、および/または1つ以上の「PARTICIPANT」カレンダーコンポーネント[RFC9073]を使ってアクターに割り当てられます。

Communication of task assignment or delegation to one or more actors who are allocated to a task by the "Organizer" is directly supported by iTIP, i.e., all included "ATTENDEE" properties in an iTIP "REQUEST" are expected to perform the task.

「Organizer」によってタスクに割り当てられた1人以上のアクターへのタスクの割り当てや委任の伝達は、iTIPで直接サポートされています。つまり、iTIPの「REQUEST」に含まれるすべての「ATTENDEE」プロパティーは、そのタスクを実行することが期待されます。

The offering or advertising of a task to one or more (potential) actors where only one or a subset of the candidates may accept the task will be addressed by a later specification.

1人以上の（潜在的な）アクターにタスクを提示または公示し、候補者のうち1人または一部だけがタスクを受け入れられるようにすることについては、今後の仕様で扱います。

7. Status Reporting

7. ステータスの報告

7.1. Improved Granularity in Status Reporting Information

7.1. ステータス報告情報の粒度の改善

This document defines a new "VSTATUS" calendar component (see Section 12.1) that can be used to group related information about the status of the task. This might include information on why (the "REASON" property) and when (the "DTSTAMP" property) a status has changed. In addition, new status values are specified to provide for task suspension, failure, and preparation.

この文書は、タスクのステータスに関する関連情報をまとめるために使える、新しい「VSTATUS」カレンダーコンポーネント（Section 12.1を参照）を定義します。これには、ステータスがなぜ（「REASON」プロパティー）、いつ（「DTSTAMP」プロパティー）変化したかに関する情報が含まれることがあります。さらに、タスクの一時停止、失敗、準備に対応するための新しいステータス値を規定します。

BEGIN:VSTATUS
STATUS:FAILED
REASON:https://example.com/reason/delivery-failed
SUBSTATE:ERROR
DTSTAMP:20130212T120000Z
COMMENT:Breakdown
END:VSTATUS
BEGIN:VSTATUS
STATUS:FAILED
REASON:https://example.com/reason/delivery-failed
SUBSTATE:ERROR
DTSTAMP:20130212T120000Z
COMMENT:Breakdown
END:VSTATUS

7.3. Updating the Overall Status

7.3. 全体のステータスの更新

Only the Task Organizer, or the server acting as the Organizer's proxy, may change or add "VSTATUS" calendar components and the "STATUS" property.

「VSTATUS」カレンダーコンポーネントと「STATUS」プロパティーを変更または追加できるのは、タスクオーガナイザー、またはOrganizerのプロキシーとして動作するサーバーだけです。

The overall "VSTATUS" will be changed in response to incoming "Attendee" replies. Each change of the overall "VSTATUS" MUST be accompanied by a change to the STATUS.

全体の「VSTATUS」は、受信した「Attendee」の返信に応じて変更されます。全体の「VSTATUS」を変更するたびに、STATUSも変更しなければなりません（MUST）。

Note there is no defined ordering of properties and components so the DTSTAMP property SHOULD be set for each "VSTATUS" component to preserve ordering.

プロパティーとコンポーネントの順序は定義されていないため、順序を保持するために、各「VSTATUS」コンポーネントにDTSTAMPプロパティーを設定すべきです（SHOULD）。

7.5. Task Alerts and Notifications

7.5. タスクのアラートと通知

Different requirements to alert or notify task actors of pending or actual task status changes are recognized:

保留中または実際のタスクのステータス変化について、タスクアクターにアラートや通知を送ることに関しては、次のようなさまざまな要件があります。

Alarms:

"VALARM" calendar components operate in the calendar user agent space to notify the task actor of a pending task state for a task they are assigned to or are interested in.

Current standards (such as [RFC9074]) indicate that "VALARM" calendar components SHOULD be removed from incoming data, and many systems in fact do so. In a task assignment scenario, it may be appropriate for the "Organizer" to be able to set alarms for the participants. A system implementing these standards may choose to preserve "VALARM" calendar components, but sending a task via some external service may result in their removal. This issue is not addressed by this specification.

Escalations:

An escalation or notification to the "Attendee", "Organizer", or other task actor may be required if a deadline associated with a task is exceeded or for some other reason. Process Logic identifying when and who to propagate escalations is the responsibility of the Task Generating System, e.g., a BPMS.

Notifications:

Task actors (Observers) not directly involved in performing a task but that have a known interest in a given task's status can be identified by the "PARTICIPANT" calendar component [RFC9073] against certain components, e.g., the "VALARM" calendar component, to identify which task events the stakeholder/party is interested in. Notifications on shared calendars will allow task actors to register an interest in changes to tasks within a calendar (see Appendix A).

アラーム：

「VALARM」カレンダーコンポーネントは、カレンダーユーザーエージェントの領域で動作し、タスクアクターが割り当てられている、または関心を持っているタスクの保留中のタスク状態をタスクアクターに通知します。

現在の標準（[RFC9074]など）は、受信したデータから「VALARM」カレンダーコンポーネントを削除すべきです（SHOULD）としており、実際に多くのシステムがそうしています。タスクの割り当てのシナリオでは、「Organizer」が参加者のためにアラームを設定できることが適切な場合があります。これらの標準を実装するシステムは「VALARM」カレンダーコンポーネントを保持することを選択できますが、何らかの外部サービスを介してタスクを送信すると、それらが削除される可能性があります。この問題はこの仕様では扱いません。

エスカレーション：

タスクに関連付けられた期限を超過した場合やその他の理由により、「Attendee」、「Organizer」、またはほかのタスクアクターへのエスカレーションや通知が必要になることがあります。いつ誰にエスカレーションを伝えるかを特定するプロセスロジックは、タスク生成システム（たとえば、BPMS）の責任です。

通知：

タスクの実行に直接関わらないものの、与えられたタスクのステータスに関心があることがわかっているタスクアクター（Observer）は、特定のコンポーネント（たとえば、「VALARM」カレンダーコンポーネント）に対して「PARTICIPANT」カレンダーコンポーネント[RFC9073]で識別でき、これによってその利害関係者がどのタスクイベントに関心を持っているかを識別できます。共有カレンダーでの通知により、タスクアクターはカレンダー内のタスクの変更に対する関心を登録できるようになります（Appendix Aを参照）。

10.4. Task Mode

10.4. タスクモード

Property Name:

TASK-MODE

Purpose:

This property specifies automatic operations that servers acting on behalf of the "Organizer" apply to tasks based on changes in "Attendee" status (PARTSTAT).

Value Type:

TEXT

Property Parameters:

IANA and non-standard property parameters can be specified on this property.

Conformance:

This property can be specified zero times or once in a "VTODO" calendar component.

Format Definition:

This property is defined by the following notation:

task-mode   = "TASK-MODE" taskmodeparam ":"
                 ("AUTOMATIC-COMPLETION"
                 / "AUTOMATIC-FAILURE"
                 / "AUTOMATIC"
                 / "SERVER"
                 / "CLIENT"
                 / iana-token) CRLF

taskmodeparam      = *(";" other-param)
Description:

In a "VTODO" calendar component, this property MAY be used to indicate to servers how they can automatically change the state of the task based on iTIP replies from "Attendees". For example, the server can automatically set the overall task status to "COMPLETED" when every "Attendee" has marked their own status (PARTSTAT) as "COMPLETED", or the server could mark the task as "FAILED" if its DUE date passes before completion. "TASK-MODE" processing is performed on the "Organizer's" copy of the task.

To set the status, add a "VSTATUS" component as specified in Section 12.1.

The property value is an IANA-registered token that defines the mode to be used for the task. The modes are described in the following subsections.

If the "TASK-MODE" property is absent, then the "CLIENT" value is assumed.

AUTOMATIC-COMPLETION Task Mode:

The task mode value "AUTOMATIC-COMPLETION" indicates to the server that it SHOULD change the "VTODO" calendar component's status to "COMPLETED" as soon as all "Attendees" in the task have replied with a "partstat" parameter set to "COMPLETED".

Failing the task MUST be handled by a client.

AUTOMATIC-FAILURE Task Mode:

The task mode value "AUTOMATIC-FAILURE" indicates to the server that it SHOULD change the "VTODO" calendar component's status to "FAILED" if either:

  1. the PARTSTAT of one "ATTENDEE" property is set to "FAILED"; or

  2. the current time is past the effective due date of the component and the task has not yet been completed. The effective due date is either the "DUE" property value or the combination of the "DTSTART" and "DURATION" property values.

    Completing the task MUST be handled by a client.

AUTOMATIC Task Mode:

This mode handles the automatic behavior of both "AUTOMATIC-COMPLETION" and "AUTOMATIC-FAILURE".

CLIENT Task Mode:

The task mode value "CLIENT" is an instruction to the server to honor the status set by the client.

SERVER Task Mode:

The task mode value "SERVER" indicates to the server that it SHOULD change the "VTODO" calendar component's status to an appropriate value, based on implementation-defined "business rules", as "Attendee" responses are processed or as deadlines related to the task pass.

Examples:
TASK-MODE:AUTOMATIC-COMPLETION
TASK-MODE:AUTOMATIC-FAILURE
TASK-MODE:SERVER
プロパティー名：

TASK-MODE

目的：

このプロパティーは、「Organizer」に代わって動作するサーバーが、「Attendee」のステータス（PARTSTAT）の変化に基づいてタスクに適用する自動操作を指定します。

値の型：

TEXT

プロパティーパラメーター：

IANAに登録されたプロパティーパラメーターと非標準のプロパティーパラメーターをこのプロパティーに指定できます。

適合性：

このプロパティーは「VTODO」カレンダーコンポーネントで0回または1回指定できます。

形式の定義：

このプロパティーは次の表記で定義されます。

task-mode   = "TASK-MODE" taskmodeparam ":"
                 ("AUTOMATIC-COMPLETION"
                 / "AUTOMATIC-FAILURE"
                 / "AUTOMATIC"
                 / "SERVER"
                 / "CLIENT"
                 / iana-token) CRLF

taskmodeparam      = *(";" other-param)
説明：

「VTODO」カレンダーコンポーネントでは、このプロパティーを、「Attendee」からのiTIPの返信に基づいてタスクの状態を自動的に変更する方法をサーバーに示すために使用してもよいです（MAY）。たとえば、サーバーは、すべての「Attendee」が自身のステータス（PARTSTAT）を「COMPLETED」にしたときに、タスク全体のステータスを自動的に「COMPLETED」に設定できます。あるいは、完了する前にDUEの日付が過ぎた場合に、タスクを「FAILED」にすることもできます。「TASK-MODE」の処理は、タスクの「Organizer」側のコピーに対して行われます。

ステータスを設定するには、Section 12.1で規定されているように「VSTATUS」コンポーネントを追加します。

プロパティーの値は、タスクに使うモードを定義する、IANAに登録されたトークンです。各モードについては、以下で説明します。

「TASK-MODE」プロパティーが存在しない場合は、値「CLIENT」が仮定されます。

AUTOMATIC-COMPLETIONタスクモード：

タスクモードの値「AUTOMATIC-COMPLETION」は、タスクのすべての「Attendee」が「partstat」パラメーターを「COMPLETED」に設定して返信したらすぐに、「VTODO」カレンダーコンポーネントのステータスを「COMPLETED」に変更すべきです（SHOULD）ということをサーバーに示します。

タスクの失敗は、クライアントが処理しなければなりません（MUST）。

AUTOMATIC-FAILUREタスクモード：

タスクモードの値「AUTOMATIC-FAILURE」は、次のいずれかの場合に、「VTODO」カレンダーコンポーネントのステータスを「FAILED」に変更すべきです（SHOULD）ということをサーバーに示します。

  1. いずれかの「ATTENDEE」プロパティーのPARTSTATが「FAILED」に設定された場合。または、

  2. 現在時刻がコンポーネントの実質的な期日を過ぎていて、タスクがまだ完了していない場合。実質的な期日とは、「DUE」プロパティーの値、または「DTSTART」と「DURATION」の各プロパティーの値の組み合わせのいずれかです。

    タスクの完了は、クライアントが処理しなければなりません（MUST）。

このモードは、「AUTOMATIC-COMPLETION」と「AUTOMATIC-FAILURE」の両方の自動的な振る舞いを扱います。

CLIENTタスクモード：

タスクモードの値「CLIENT」は、クライアントが設定したステータスを尊重するようにというサーバーへの指示です。

SERVERタスクモード：

タスクモードの値「SERVER」は、「Attendee」のレスポンスが処理されたときや、タスクに関連する期限が過ぎたときに、実装で定義された「ビジネスルール」に基づいて、「VTODO」カレンダーコンポーネントのステータスを適切な値に変更すべきです（SHOULD）ということをサーバーに示します。

例：
TASK-MODE:AUTOMATIC-COMPLETION
TASK-MODE:AUTOMATIC-FAILURE
TASK-MODE:SERVER

13. CalDAV Support for Task Mode

13. タスクモードのためのCalDAVサポート

The CalDAV [RFC4791] calendar access protocol allows clients and servers to exchange iCalendar data. With the introduction of the "TASK-MODE" property in this specification, different automated task management behaviors may be delegated to the server by the Task Organizer depending upon the value of "TASK-MODE".

CalDAV [RFC4791]のカレンダーアクセスプロトコルにより、クライアントとサーバーはiCalendarデータを交換できます。この仕様で「TASK-MODE」プロパティーが導入されたことにより、タスクオーガナイザーは、「TASK-MODE」の値に応じて、さまざまな自動化されたタスク管理の振る舞いをサーバーに委任できます。

In order for a CalDAV client to know what task modes are available, a CalDAV server advertises a CALDAV:supported-task-mode-set WebDAV property on calendar home or calendar collections if it supports the use of the "TASK-MODE" property as described in this specification. The server can advertise a specific set of supported task modes by including one or more CALDAV:supported-task-mode XML elements within the CALDAV:supported-task-mode-set XML element.

CalDAVクライアントがどのタスクモードを利用できるかを知ることができるように、CalDAVサーバーは、この仕様で説明する「TASK-MODE」プロパティーの使用をサポートしている場合、カレンダーホームまたはカレンダーコレクションでCALDAV:supported-task-mode-set WebDAVプロパティーを公示します。サーバーは、CALDAV:supported-task-mode-set XML要素の中に1つ以上のCALDAV:supported-task-mode XML要素を含めることで、サポートするタスクモードの特定の集合を公示できます。

If no CALDAV:supported-task-mode XML elements are included in the WebDAV property, then clients MUST assume the server does not support this specification. The client MAY attempt to store iCalendar data containing "TASK-MODE" elements but needs to be prepared for a failure response from the server.

WebDAVプロパティーにCALDAV:supported-task-mode XML要素が含まれていない場合、クライアントはサーバーがこの仕様をサポートしていないと仮定しなければなりません（MUST）。クライアントは「TASK-MODE」要素を含むiCalendarデータの保存を試行してもよいです（MAY）が、サーバーからの失敗レスポンスに備えておく必要があります。

A server supporting this specification MUST return an HTTP 403 response with a DAV:error element containing a CALDAV:supported-task-mode XML element, if a client attempts to store iCalendar data with a "TASK-MODE" element value not supported by the server.

この仕様をサポートするサーバーは、クライアントがサーバーのサポートしていない「TASK-MODE」要素の値を持つiCalendarデータを保存しようとした場合、CALDAV:supported-task-mode XML要素を含むDAV:error要素とともにHTTP 403レスポンスを返さなければなりません（MUST）。

It is possible for a "TASK-MODE" value to be present in calendar data on the server being accessed by a client that does not support the "TASK-MODE" property. It is expected that existing clients, unaware of "TASK-MODE", will fail gracefully by ignoring the calendar property.

「TASK-MODE」プロパティーをサポートしていないクライアントがアクセスしているサーバー上のカレンダーデータに、「TASK-MODE」の値が存在する可能性があります。「TASK-MODE」を知らない既存のクライアントは、そのカレンダープロパティーを無視することで、問題なく処理を継続することが期待されます。
