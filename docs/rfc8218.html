RFC 8218

Multipath Extension for the Optimized Link State Routing Protocol Version 2 (OLSRv2)

RFC 8218

Optimized Link State Routing Protocol Version 2（OLSRv2）のマルチパス拡張

Abstract

概要

This document specifies a multipath extension for the Optimized Link State Routing Protocol version 2 (OLSRv2) to discover multiple disjoint paths for Mobile Ad Hoc Networks (MANETs). Considering the characteristics of MANETs, especially the dynamic network topology, using multiple paths can increase aggregated throughput and improve the reliability by avoiding single route failures. The interoperability with OLSRv2 is retained.

この文書は、モバイルアドホックネットワーク（MANET）において互いに素な複数のパスを発見するための、Optimized Link State Routing Protocol version 2（OLSRv2）のマルチパス拡張を規定します。MANETの特性、特に動的なネットワークトポロジーを考慮すると、複数のパスを使うことで、総スループットを増やし、単一ルートの障害を回避することで信頼性を向上させることができます。OLSRv2との相互運用性は維持されます。

1. Introduction

1. はじめに

The Optimized Link State Routing Protocol version 2 (OLSRv2) [RFC7181] is a proactive link state protocol designed for use in Mobile Ad Hoc Networks (MANETs). It generates routing messages periodically to create and maintain a Routing Set, which contains routing information to all the possible destinations in the routing domain. For each destination, there exists a unique Routing Tuple, which indicates the next hop to reach the destination.

Optimized Link State Routing Protocol version 2（OLSRv2）[RFC7181]は、モバイルアドホックネットワーク（MANET）での使用を目的として設計されたプロアクティブなリンクステートプロトコルです。OLSRv2は、ルーティングメッセージを定期的に生成して、ルーティングドメイン内のすべての到達可能な宛先へのルーティング情報を含むRouting Setを作成し、維持します。各宛先に対して、その宛先に到達するためのネクストホップを示す一意のRouting Tupleが存在します。

This document specifies an extension of the OLSRv2 protocol [RFC7181] to provide multiple disjoint paths when appropriate for a source-destination pair. Because of the characteristics of MANETs [RFC2501], especially the dynamic topology, having multiple paths is helpful for increasing network throughput, improving forwarding reliability, and load-balancing.

この文書は、送信元と宛先のペアに対して、適切な場合に互いに素な複数のパスを提供するためのOLSRv2プロトコル[RFC7181]の拡張を規定します。MANETの特性[RFC2501]、特に動的なトポロジーのために、複数のパスを持つことは、ネットワークのスループットの向上、転送の信頼性の向上、および負荷分散に役立ちます。

Multipath OLSRv2 (MP-OLSRv2), specified in this document, uses the Multipath Dijkstra Algorithm by default to explore multiple disjoint paths from a source router to a destination router based on the topology information obtained through OLSRv2 and to forward the datagrams in a load-balancing manner using source routing. MP-OLSRv2 is designed to be interoperable with OLSRv2.

この文書で規定するマルチパスOLSRv2（MP-OLSRv2）は、デフォルトでMultipath Dijkstra Algorithm（マルチパスダイクストラアルゴリズム）を使い、OLSRv2を通じて得られたトポロジー情報に基づいて送信元ルーターから宛先ルーターへの互いに素な複数のパスを探索し、ソースルーティングを使って負荷分散するようにデータグラムを転送します。MP-OLSRv2は、OLSRv2と相互運用できるように設計されています。

1.1. Motivation and Experiments to Be Conducted

1.1. 動機と実施すべき実験

This document is an experimental extension of OLSRv2 that can increase the data forwarding reliability in dynamic and high-load MANET scenarios by transmitting datagrams over multiple disjoint paths using source routing. This mechanism is used because:

この文書は、ソースルーティングを使って互いに素な複数のパスでデータグラムを送信することにより、動的で高負荷なMANETのシナリオにおけるデータ転送の信頼性を向上させることのできる、OLSRv2の実験的な拡張です。このメカニズムを使う理由は次のとおりです。

  • Disjoint paths can avoid single route failures.
  • Transmitting datagrams through parallel paths can increase aggregated throughput.
  • Some scenarios may require that some routers must (or must not) be used.
  • Having control of the paths at the source benefits the load-balancing and traffic engineering.
  • An application of this extension is in combination with Forward Error Correction (FEC) coding applied across packets (erasure coding) [WPMC11]. Because the packet drops are normally bursty in a path (for example, due to route failure), erasure coding is less effective in single path routing protocols. By providing multiple disjoint paths, the application of erasure coding with multipath protocol is more resilient to routing failures.
  • 互いに素なパスによって、単一ルートの障害を回避できます。
  • 並列のパスを通じてデータグラムを送信することで、総スループットを増やすことができます。
  • シナリオによっては、特定のルーターを使わなければならない（または使ってはならない）ことが求められる場合があります。
  • 送信元でパスを制御できることは、負荷分散とトラフィックエンジニアリングに役立ちます。
  • この拡張の応用の1つは、パケットをまたいで適用される前方誤り訂正（FEC）符号化（消失訂正符号化、erasure coding）[WPMC11]との組み合わせです。パケットの欠落は通常、1つのパス内でバースト的に発生する（たとえば、ルートの障害による）ため、単一パスのルーティングプロトコルでは消失訂正符号化の効果が低くなります。互いに素な複数のパスを提供することで、マルチパスプロトコルと組み合わせた消失訂正符号化の適用は、ルーティングの障害に対してより強くなります。

In existing deployments, while running code and simulations have proven the interest of multipath extension for OLSRv2 in certain networks [GIIS14][WCNC08][ADHOC11], more experiments and experiences are still needed to understand the effects of the protocol specified in this Experimental RFC. The multipath extension for OLSRv2 is expected to be revised and documented as a Standards Track RFC once sufficient operational experience is obtained. Other than general experiences, including the protocol specification and interoperability with base OLSRv2 implementations, experiences in the following aspects are highly appreciated:

既存の展開では、動作するコードとシミュレーションによって、特定のネットワークにおけるOLSRv2のマルチパス拡張の有用性が証明されています[GIIS14][WCNC08][ADHOC11]が、このExperimental RFCで規定するプロトコルの効果を理解するには、さらに多くの実験と経験がまだ必要です。OLSRv2のマルチパス拡張は、十分な運用経験が得られた時点で改訂され、標準化過程のRFCとして文書化されることが期待されています。プロトコル仕様や基本のOLSRv2実装との相互運用性を含む一般的な経験のほかに、次の観点での経験が強く歓迎されます。

  • Optimal values for the number of multiple paths (NUMBER_OF_PATHS, see Section 5) to be used. This depends on the network topology and router density.
  • Optimal values used in the metric functions. Metric functions are applied to increase the metric of used links and nodes so as to obtain disjoint paths. What kind of disjointness is desired (node disjoint or link disjoint) may depend on the Layer 2 protocol used and can be achieved by applying different sets of metric functions.
  • Use of different metric types. This multipath extension can be used with metric types that meet the requirement of OLSRv2, such as [RFC7779]. The metric type used also has an impact on the choice of metric functions as indicated in the previous bullet point.
  • The impact of partial topology information to multipath calculation. OLSRv2 maintains a partial topology information base to reduce protocol overhead. Experience has shown that multiple paths can be obtained even with such partial information; however, depending on the Multipoint Relay (MPR) selection algorithm used, the disjointness of the multiple paths might be impacted depending on the Multipoint Relay (MPR) selection algorithm used.
  • Use of IPv6 loose source routing. In the current specification, only strict source routing is used for IPv6 based on [RFC6554]. In [IPv6-SRH], the use of the loose source routing is also proposed in IPv6. In scenarios where the length of the source routing header is critical, the loose source routing can be considered.
  • Optimal choice of "key" routers for loose source routing. In some cases, loose source routing is used to reduce overhead or for interoperability with OLSRv2 routers. Other than the basic rules defined in the following parts of this document, optimal choices of routers to put in the loose source routing header can be further studied.
  • Different path-selection schedulers. Depending on the application type and transport layer type, either a per-flow scheduler or per-datagram scheduler is applied. By default, the traffic load should be equally distributed in multiple paths. In some scenarios, weighted scheduling can be considered: for example, the paths with lower metrics (i.e., higher quality) can transfer more datagrams or flows compared to paths with higher metrics.
  • The impacts of the delay variation due to multipath routing. [RFC2991] brings out some concerns of multipath routing, especially variable latencies when per-datagram scheduling is applied. Although current experiment results show that multipath routing can reduce the jitter in dynamic scenarios, some transport protocols or applications may be sensitive to the datagram reordering.
  • The disjoint multipath protocol has an interesting application with erasure coding, especially for services like video/audio streaming [WPMC11]. The combination of erasure coding mechanisms and this extension is thus encouraged.
  • Different algorithms to obtain multiple paths, other than the default Multipath Dijkstra Algorithm introduced in Section 8.5.2 of this specification.
  • The use of multitopology information. By using [RFC7722], multiple topologies using different metric types can be obtained. Although there is no work defining how this extension can make use of the multitopology information base yet, experimentation with the use of multiple metrics for building multiple paths is encouraged.
  • 使用する複数パスの数（NUMBER_OF_PATHS、セクション5を参照）の最適値。これはネットワークトポロジーとルーターの密度に依存します。
  • メトリック関数で使う最適値。メトリック関数は、互いに素なパスを得るために、使用済みのリンクとノードのメトリックを増やすのに適用されます。どのような種類の非共有性（ノードが互いに素か、リンクが互いに素か）が望まれるかは使用するレイヤー2プロトコルに依存する場合があり、異なるメトリック関数の組を適用することで実現できます。
  • 異なるメトリックタイプの使用。このマルチパス拡張は、[RFC7779]などの、OLSRv2の要件を満たすメトリックタイプとともに使用できます。前の項目で示したように、使用するメトリックタイプはメトリック関数の選択にも影響します。
  • 部分的なトポロジー情報がマルチパス計算に与える影響。OLSRv2は、プロトコルのオーバーヘッドを削減するために、部分的なトポロジー情報ベースを維持します。そのような部分的な情報でも複数のパスを得られることが経験から示されています。ただし、使用するマルチポイントリレー（MPR）選択アルゴリズムによっては、複数のパスの非共有性が影響を受ける可能性があります。
  • IPv6のルーズソースルーティングの使用。現在の仕様では、IPv6では[RFC6554]に基づいてストリクトソースルーティングだけを使用します。[IPv6-SRH]では、IPv6でのルーズソースルーティングの使用も提案されています。ソースルーティングヘッダーの長さが重要となるシナリオでは、ルーズソースルーティングを検討できます。
  • ルーズソースルーティングのための「キー」ルーターの最適な選択。場合によっては、オーバーヘッドの削減のため、またはOLSRv2ルーターとの相互運用性のために、ルーズソースルーティングが使われます。この文書の以降の部分で定義する基本的な規則のほかに、ルーズソースルーティングヘッダーに入れるルーターの最適な選択について、さらに研究できます。
  • 異なるパス選択スケジューラー。アプリケーションの種類とトランスポート層の種類に応じて、フロー単位のスケジューラーかデータグラム単位のスケジューラーのいずれかを適用します。デフォルトでは、トラフィックの負荷は複数のパスに均等に分散させるべきです。シナリオによっては、重み付きスケジューリングを検討できます。たとえば、メトリックの低い（つまり、品質の高い）パスは、メトリックの高いパスに比べて、より多くのデータグラムやフローを転送できます。
  • マルチパスルーティングによる遅延変動の影響。[RFC2991]は、マルチパスルーティングに関するいくつかの懸念、特にデータグラム単位のスケジューリングを適用した場合の遅延のばらつきを提起しています。現在の実験結果では、マルチパスルーティングによって動的なシナリオでのジッターを削減できることが示されていますが、一部のトランスポートプロトコルやアプリケーションはデータグラムの順序の入れ替わりに敏感な場合があります。
  • 互いに素なパスを使うマルチパスプロトコルには、特にビデオ／オーディオのストリーミングのようなサービスにおいて、消失訂正符号化との興味深い応用があります[WPMC11]。したがって、消失訂正符号化のメカニズムとこの拡張の組み合わせが推奨されます。
  • この仕様のセクション8.5.2で紹介するデフォルトのMultipath Dijkstra Algorithm以外の、複数のパスを得るための異なるアルゴリズム。
  • マルチトポロジー情報の使用。[RFC7722]を使うことで、異なるメトリックタイプを使う複数のトポロジーを得ることができます。この拡張がマルチトポロジー情報ベースをどのように利用できるかを定義する作業はまだありませんが、複数のパスを構築するために複数のメトリックを使用する実験が推奨されます。

3. Applicability Statement

3. 適用性に関する声明

As an extension of OLSRv2, this specification is applicable to MANETs for which OLSRv2 is applicable (see [RFC7181]). It can operate on single or multiple interfaces to discover multiple disjoint paths from a source router to a destination router. MP-OLSRv2 is designed for networks with dynamic topology to avoid single route failure. It can also provide higher aggregated throughput and load-balancing.

OLSRv2の拡張として、この仕様は、OLSRv2が適用可能なMANETに適用できます（[RFC7181]を参照）。この仕様は、単一または複数のインターフェイス上で動作して、送信元ルーターから宛先ルーターへの互いに素な複数のパスを発見できます。MP-OLSRv2は、単一ルートの障害を回避するために、動的なトポロジーを持つネットワーク向けに設計されています。また、より高い総スループットと負荷分散も提供できます。

In a router supporting MP-OLSRv2, MP-OLSRv2 does not necessarily replace OLSRv2 completely. The extension can be applied for certain applications that are suitable for multipath routing (mainly video or audio streams) based on information such as a Diffserv codepoint [RFC2474].

MP-OLSRv2をサポートするルーターにおいて、MP-OLSRv2が必ずしもOLSRv2を完全に置き換えるわけではありません。この拡張は、Diffservコードポイント[RFC2474]などの情報に基づいて、マルチパスルーティングに適した特定のアプリケーション（主にビデオやオーディオのストリーム）に適用できます。

Compared to OLSRv2, this extension does not introduce any new message type. A new Message TLV Type is introduced to identify the routers that support forwarding based on the source routing header. It is interoperable with OLSRv2 implementations that do not have this extension: as the MP-OLSRv2 uses source routing, in IPv4 networks the interoperability is achieved using loose source routing headers; in IPv6 networks, it is achieved by eliminating routers that do not support IPv6 strict source routing.

OLSRv2と比べて、この拡張は新しいメッセージタイプを導入しません。ソースルーティングヘッダーに基づく転送をサポートするルーターを識別するために、新しいMessage TLV Typeを導入します。この拡張は、この拡張を持たないOLSRv2実装と相互運用できます。MP-OLSRv2はソースルーティングを使うので、IPv4ネットワークでは、ルーズソースルーティングヘッダーを使うことで相互運用性を実現します。IPv6ネットワークでは、IPv6のストリクトソースルーティングをサポートしないルーターを除外することで相互運用性を実現します。

MP-OLSRv2 supports two different but interoperable multipath calculation approaches: proactive and reactive. In the proactive calculation, the paths to all the destinations are calculated before they are needed. In the reactive calculation, only the paths to desired destination(s) are calculated on demand. The proactive approach requires more computational resources than the reactive one. The reactive approach requires the IP forwarding plane to trigger the multipath calculation.

MP-OLSRv2は、異なるものの相互運用可能な2つのマルチパス計算の方式として、プロアクティブとリアクティブをサポートします。プロアクティブな計算では、すべての宛先へのパスを、それらが必要になる前に計算します。リアクティブな計算では、目的の宛先へのパスだけをオンデマンドで計算します。プロアクティブな方式は、リアクティブな方式よりも多くの計算資源を必要とします。リアクティブな方式では、IPフォワーディングプレーンがマルチパス計算を起動する必要があります。

MP-OLSRv2 forwards datagrams using the source routing header. As there are multiple paths to each destination, MP-OLSRv2 requires the IP forwarding plane to be able to choose which source route to be put in the source routing header based on the path scheduler defined by MP-OLSRv2. For IPv4 networks, implementation of loose source routing is required following [RFC791]. For IPv6 networks, implementation of strict source routing is required following the source routing header generation and processing defined in [RFC6554].

MP-OLSRv2は、ソースルーティングヘッダーを使ってデータグラムを転送します。各宛先へのパスは複数あるため、MP-OLSRv2では、MP-OLSRv2が定義するパススケジューラーに基づいて、どのソースルートをソースルーティングヘッダーに入れるかをIPフォワーディングプレーンが選択できる必要があります。IPv4ネットワークでは、[RFC791]に従ったルーズソースルーティングの実装が必要です。IPv6ネットワークでは、[RFC6554]で定義されているソースルーティングヘッダーの生成と処理に従った、ストリクトソースルーティングの実装が必要です。

4. Protocol Overview and Functioning

4. プロトコルの概要と機能

This specification uses OLSRv2 [RFC7181] to:

この仕様は、OLSRv2 [RFC7181]を次の目的で使用します。

  • Identify all the reachable routers in the network.
  • Identify a sufficient subset of links in the networks so that routes can be calculated to all reachable destinations.
  • Provide a Routing Set containing the shortest routes from this router to all destinations.
  • ネットワーク内の到達可能なすべてのルーターを識別すること。
  • すべての到達可能な宛先へのルートを計算できるように、ネットワーク内のリンクの十分なサブセットを識別すること。
  • このルーターからすべての宛先への最短ルートを含むRouting Setを提供すること。

In addition, the MP-OLSRv2 Routing Process identifies the routers that support source routing by adding a new Message TLV in HELLO and Topology Control (TC) messages. Based on the above information acquired, every MP-OLSRv2 Routing Process is aware of a reduced topology map of the network and the routers supporting source routing.

さらに、MP-OLSRv2 Routing Processは、HELLOメッセージとトポロジー制御（TC）メッセージに新しいMessage TLVを追加することで、ソースルーティングをサポートするルーターを識別します。取得した上記の情報に基づいて、すべてのMP-OLSRv2 Routing Processは、ネットワークの縮約されたトポロジーマップと、ソースルーティングをサポートするルーターを把握します。

A Multipath Routing Set containing the multipath information is maintained. It may be either proactively calculated or reactively calculated:

マルチパスの情報を含むMultipath Routing Setを維持します。これは、プロアクティブに計算することも、リアクティブに計算することもできます。

  • In the proactive approach, multiple paths to all possible destinations are calculated and updated based on control message exchange. The routes are thus available before they are actually needed.
  • In the reactive approach, a multipath algorithm is invoked on demand, i.e., only when there is a datagram to be sent from the source to the destination and there is no available Routing Tuple in the Multipath Routing Set. This requires the IP forwarding information base to trigger the multipath calculation specified in Section 8.5 when no Multipath Routing Tuple is available. The reactive operation is local to the router and no additional exchange of routing control messages is required. When the paths are being calculated, the datagrams SHOULD be buffered unless the router does not have enough memory.
  • プロアクティブな方式では、制御メッセージの交換に基づいて、すべての到達可能な宛先への複数のパスを計算し、更新します。そのため、ルートは実際に必要になる前に利用可能になります。
  • リアクティブな方式では、マルチパスアルゴリズムをオンデマンドで、つまり送信元から宛先へ送信するデータグラムがあり、かつMultipath Routing Setに利用可能なRouting Tupleがない場合にだけ呼び出します。このため、利用可能なMultipath Routing Tupleがない場合に、IPフォワーディング情報ベースがセクション8.5で規定するマルチパス計算を起動する必要があります。リアクティブな動作はルーター内で完結し、ルーティング制御メッセージの追加の交換は必要ありません。パスを計算している間、ルーターに十分なメモリーがない場合を除いて、データグラムをバッファリングすべきです（SHOULD）。

Routers in the same network may choose either proactive or reactive multipath calculation independently according to their computation resources. The Multipath Dijkstra Algorithm (defined in Section 8.5) is introduced as the default algorithm to generate multiple disjoint paths from a source to a destination, and such information is kept in the Multipath Routing Set.

同じネットワーク内のルーターは、それぞれの計算資源に応じて、プロアクティブなマルチパス計算とリアクティブなマルチパス計算のいずれかを独立に選択してもかまいません。送信元から宛先への互いに素な複数のパスを生成するデフォルトのアルゴリズムとして、Multipath Dijkstra Algorithm（セクション8.5で定義）を導入し、そのような情報をMultipath Routing Setに保持します。

The datagram is forwarded based on source routing. When there is a datagram to be sent to a destination, the source router acquires a path from the Multipath Routing Set. The path information is stored in the datagram header using the source routing header.

データグラムはソースルーティングに基づいて転送されます。宛先へ送信するデータグラムがある場合、送信元ルーターはMultipath Routing Setからパスを取得します。パスの情報は、ソースルーティングヘッダーを使ってデータグラムのヘッダーに格納されます。

5. Parameters and Constants

5. パラメーターと定数

In addition to the parameters and constants defined in [RFC7181], this specification uses the parameters and constants described in this section.

この仕様は、[RFC7181]で定義されているパラメーターと定数に加えて、このセクションで説明するパラメーターと定数を使用します。

5.1. Router Parameters

5.1. ルーターのパラメーター

NUMBER_OF_PATHS:
The number of paths desired by the router.
MAX_SRC_HOPS:
The maximum number of hops allowed to be put in the source routing header. A value set to 0 means there is no limitation on the maximum number of hops. In an IPv6 network, it MUST be set to 0 because [RFC6554] supports only strict source routing. All the intermediate routers MUST be included in the source routing header, which is a various number of hops. In an IPv4 network, it MUST be strictly less than 11 and greater than 0 due to the length limit of the IPv4 header.
CUTOFF_RATIO:
The ratio that defines the maximum metric of a path compared to the shortest path kept in the OLSRv2 Routing Set. For example, the metric to a destination is R_metric based on the Routing Set. Then, the maximum metric allowed for a path is CUTOFF_RATIO * R_metric. CUTOFF_RATIO MUST be greater than or equal to 1. Setting the number low makes it less likely that additional paths will be found -- for example, setting it to 1 will mean only equal length paths are considered.
SR_TC_INTERVAL:
The maximum time between the transmission of two successive TC messages by an MP-OLSRv2 Routing Process.
SR_HOLD_TIME:
The minimum value in the TLV with Type = VALIDITY_TIME included in TC messages generated based on SR_TC_INTERVAL.
NUMBER_OF_PATHS:
ルーターが望むパスの数。
MAX_SRC_HOPS:
ソースルーティングヘッダーに入れることのできるホップの最大数。値を0に設定した場合は、ホップの最大数に制限がないことを意味します。[RFC6554]はストリクトソースルーティングだけをサポートするため、IPv6ネットワークでは、この値を0に設定しなければなりません（MUST）。すべての中間ルーターをソースルーティングヘッダーに含めなければなりません（MUST）が、そのホップ数はさまざまです。IPv4ネットワークでは、IPv4ヘッダーの長さの制限のため、この値は11未満かつ0を超える値でなければなりません（MUST）。
CUTOFF_RATIO:
OLSRv2のRouting Setに保持されている最短パスと比較した、パスのメトリックの最大値を定義する比率。たとえば、Routing Setに基づく宛先へのメトリックがR_metricだとします。このとき、パスに許されるメトリックの最大値はCUTOFF_RATIO * R_metricです。CUTOFF_RATIOは1以上でなければなりません（MUST）。この値を小さく設定すると、追加のパスが見つかる可能性が低くなります。たとえば、1に設定すると、同じ長さのパスだけが考慮されることになります。

MP-OLSRv2 Routing Processによる連続する2つのTCメッセージの送信間隔の最大値。
SR_HOLD_TIME:

6. Packets and Messages

6. パケットとメッセージ

This extension employs the routing control messages HELLO and TC as defined in OLSRv2 [RFC7181] to obtain network topology information. For the datagram to support source routing, a source routing header is added to each datagram routed by this extension. Depending on the IP version used, the source routing header is defined in this section.

この拡張は、ネットワークトポロジーの情報を得るために、OLSRv2 [RFC7181]で定義されているルーティング制御メッセージHELLOとTCを使用します。データグラムがソースルーティングをサポートするために、この拡張によってルーティングされる各データグラムにはソースルーティングヘッダーが追加されます。使用するIPのバージョンに応じたソースルーティングヘッダーを、このセクションで定義します。

6.1. HELLO and TC messages

6.1. HELLOメッセージとTCメッセージ

HELLO and TC messages used by the MP-OLSRv2 Routing Process use the same format as defined in [RFC7181]. In addition, a new Message TLV Type is defined to identify the originator of the HELLO or TC message that supports source-route forwarding. The new Message TLV Type is introduced for enabling MP-OLSRv2 as an extension of OLSRv2: only the routers supporting source-route forwarding can be used in the source routing header of a datagram because adding a router that does not understand the source routing header will cause routing failure.

MP-OLSRv2 Routing Processが使うHELLOメッセージとTCメッセージは、[RFC7181]で定義されているものと同じ形式を使用します。さらに、HELLOメッセージまたはTCメッセージの発信者のうち、ソースルート転送をサポートするものを識別するために、新しいMessage TLV Typeを定義します。新しいMessage TLV Typeは、MP-OLSRv2をOLSRv2の拡張として実現するために導入されます。ソースルーティングヘッダーを理解しないルーターを追加するとルーティングの失敗を引き起こすため、データグラムのソースルーティングヘッダーで使用できるのは、ソースルート転送をサポートするルーターだけです。

6.1.1. SOURCE_ROUTE TLV

6.1.1. SOURCE_ROUTEメッセージTLV

The SOURCE_ROUTE TLV is a Message TLV signaling that the message is generated by a router that supports source-route forwarding. It can be an MP-OLSRv2 Routing Process or an OLSRv2 Routing Process that supports source-route forwarding.

SOURCE_ROUTE TLVは、そのメッセージがソースルート転送をサポートするルーターによって生成されたことを通知するMessage TLVです。そのルーターは、MP-OLSRv2 Routing Processである場合も、ソースルート転送をサポートするOLSRv2 Routing Processである場合もあります。

Every HELLO or TC message generated by a MP-OLSRv2 Routing Process MUST have exactly one SOURCE_ROUTE TLV without value.

MP-OLSRv2 Routing Processが生成するすべてのHELLOメッセージまたはTCメッセージは、値のないSOURCE_ROUTE TLVをちょうど1つ持たなければなりません（MUST）。

Every HELLO or TC message generated by an OLSRv2 Routing Process MUST have exactly one SOURCE_ROUTE TLV, if the OLSRv2 Routing Process supports source-route forwarding, and be willing to join the source route generated by other MP-OLSRv2 Routing Processes. The existence of SOURCE_ROUTE TLV MUST be consistent for a specific OLSRv2 Routing Process, i.e., either it adds SOURCE_ROUTE TLV to all its HELLO/TC messages or it does not add SOURCE_ROUTE TLV to any HELLO/TC messages.

OLSRv2 Routing Processがソースルート転送をサポートし、ほかのMP-OLSRv2 Routing Processが生成するソースルートに参加する意思がある場合、そのOLSRv2 Routing Processが生成するすべてのHELLOメッセージまたはTCメッセージは、SOURCE_ROUTE TLVをちょうど1つ持たなければなりません（MUST）。SOURCE_ROUTE TLVの有無は、特定のOLSRv2 Routing Processについて一貫していなければなりません（MUST）。つまり、そのプロセスは自身のすべてのHELLO／TCメッセージにSOURCE_ROUTE TLVを追加するか、どのHELLO／TCメッセージにもSOURCE_ROUTE TLVを追加しないかのいずれかです。

6.2. Datagram

6.2. データグラム

6.2.1. Source Routing Header in IPv4

6.2.1. IPv4のソースルーティングヘッダー

In IPv4 [RFC791] networks, the MP-OLSRv2 Routing Process employs the loose source routing header, as defined in [RFC791]. It exists as an option header with option class 0 and option number 3.

IPv4 [RFC791]ネットワークでは、MP-OLSRv2 Routing Processは、[RFC791]で定義されているルーズソースルーティングヘッダーを使用します。これは、オプションクラス0、オプション番号3のオプションヘッダーとして存在します。

The source route information is kept in the "route data" field of the loose source routing header.

ソースルートの情報は、ルーズソースルーティングヘッダーの「route data」フィールドに保持されます。

6.2.2. Source Routing Header in IPv6

6.2.2. IPv6のソースルーティングヘッダー

In IPv6 [RFC8200] networks, the MP-OLSRv2 Routing Process employs the source routing header, as defined in Section 3 of [RFC6554], with IPv6 Routing Type 3.

IPv6 [RFC8200]ネットワークでは、MP-OLSRv2 Routing Processは、[RFC6554]のセクション3で定義されているソースルーティングヘッダーを、IPv6 Routing Type 3として使用します。

The source route information is kept in the "Addresses" field of the routing header.

ソースルートの情報は、ルーティングヘッダーの「Addresses」フィールドに保持されます。

7. Information Bases

7. 情報ベース

Each MP-OLSRv2 Routing Process maintains the information bases as defined in [RFC7181]. Additionally, a Multipath Information Base is used for this specification. It includes the protocol sets as defined below.

各MP-OLSRv2 Routing Processは、[RFC7181]で定義されている情報ベースを維持します。さらに、この仕様ではMultipath Information Baseを使用します。これには、以下で定義するプロトコルセットが含まれます。

7.1. SR-OLSRv2 Router Set

7.1. SR-OLSRv2ルーターセット（SR-OLSRv2 Router Set）

The SR-OLSRv2 Router Set records the routers that support source-route forwarding. This includes routers that run the MP-OLSRv2 Routing Process or the OLSRv2 Routing Process with source-route forwarding support. The set consists of SR-OLSRv2 Routing Tuple:

SR-OLSRv2 Router Setは、ソースルート転送をサポートするルーターを記録します。これには、MP-OLSRv2 Routing Processを実行するルーターや、ソースルート転送をサポートするOLSRv2 Routing Processを実行するルーターが含まれます。このセットは、次のSR-OLSRv2 Routing Tupleで構成されます。

(SR_addr, SR_time)

(SR_addr, SR_time)

where:

ここで、

  • SR_addr is the originator address of the router that supports source-route forwarding.
  • SR_time is the time until which the SR-OLSRv2 Routing Tuple is considered valid.
  • SR_addrは、ソースルート転送をサポートするルーターの発信者アドレス（originator address）です。
  • SR_timeは、そのSR-OLSRv2 Routing Tupleが有効とみなされる期限の時刻です。

7.2. Multipath Routing Set

7.2. マルチパスルーティングセット（Multipath Routing Set）

The Multipath Routing Set records the full path information of different paths to the destination. It consists of Multipath Routing Tuple:

Multipath Routing Setは、宛先への異なるパスの完全なパス情報を記録します。このセットは、次のMultipath Routing Tupleで構成されます。

(MR_dest_addr, MR_path_set)

(MR_dest_addr, MR_path_set)

where:

ここで、

  • MR_dest_addr is the network address of the destination; it is either the network address of an interface of a destination router or the network address of an attached network.
  • MP_path_set contains the multiple paths to the destination and it consists of a set of Path Tuples.
  • MR_dest_addrは、宛先のネットワークアドレスです。これは、宛先ルーターのインターフェイスのネットワークアドレスか、接続されたネットワークのネットワークアドレスのいずれかです。
  • MP_path_setは、宛先への複数のパスを含み、Path Tupleの集合で構成されます。

Each Path Tuple is defined as:

各Path Tupleは次のように定義されます。

(PT_metric, PT_address[1], PT_address[2], ..., PT_address[n])

(PT_metric, PT_address[1], PT_address[2], ..., PT_address[n])

where:

ここで、

  • PT_metric is the metric of the path to the destination, measured in LINK_METRIC_TYPE defined in [RFC7181].
  • PT_address[1, ..., n-1] are the addresses of intermediate routers to be visited, numbered from 1 to n-1, where n is the number of routers in the path, i.e., the hop count.
  • PT_metricは、宛先へのパスのメトリックで、[RFC7181]で定義されているLINK_METRIC_TYPEで測定されます。
  • PT_address[1, ..., n-1]は、経由する中間ルーターのアドレスで、1からn-1までの番号が付けられます。ここで、nはパス内のルーターの数、つまりホップ数です。

8. Protocol Details

8. プロトコルの詳細

This protocol is based on OLSRv2 and is extended to discover multiple disjoint paths from a source router to a destination router. It retains the formats of the basic routing control packets and the processing of OLSRv2 to obtain the topology information of the network. The main differences from the OLSRv2 Routing Process are the datagram processing at the source router and datagram forwarding.

このプロトコルはOLSRv2に基づいており、送信元ルーターから宛先ルーターへの互いに素な複数のパスを発見するように拡張されています。このプロトコルは、ネットワークのトポロジー情報を得るために、OLSRv2の基本的なルーティング制御パケットの形式と処理を維持します。OLSRv2 Routing Processとの主な違いは、送信元ルーターでのデータグラムの処理とデータグラムの転送です。

8.1. HELLO and TC Message Generation

8.1. HELLOメッセージとTCメッセージの生成

HELLO messages are generated according to Section 15.1 of [RFC7181], plus a single message TLV with Type := SOURCE_ROUTE included.

HELLOメッセージは、[RFC7181]のセクション15.1に従って生成され、さらにType := SOURCE_ROUTEのメッセージTLVが1つ含まれます。

TC messages are generated according to Section 16.1 of [RFC7181], plus a single message TLV with Type := SOURCE_ROUTE included.

TCメッセージは、[RFC7181]のセクション16.1に従って生成され、さらにType := SOURCE_ROUTEのメッセージTLVが1つ含まれます。

For the routers that do not generate TC messages according to [RFC7181], at least one TC message MUST be generated by an MP-OLSRv2 Routing Process during the SR_TC_INTERVAL (Section 5), which MUST be greater than or equal to TC_INTERVAL. Those TC messages MUST NOT carry any advertised neighbor addresses. This serves for those routers to advertise the SOURCE_ROUTE TLV so that the other routers can be aware of the routers that are source-route enabled so as to be used as destinations of multipath routing. The validity time associated with the VALIDITY_TIME TLV in such TC messages equals SR_HOLD_TIME, which MUST be greater than the SR_TC_INTERVAL. If the TC message carries an optional INTERVAL_TIME TLV, it MUST have a value encoding the SR_TC_INTERVAL.

[RFC7181]に従ってTCメッセージを生成しないルーターについては、MP-OLSRv2 Routing Processは、SR_TC_INTERVAL（セクション5）の間に少なくとも1つのTCメッセージを生成しなければなりません（MUST）。SR_TC_INTERVALは、TC_INTERVAL以上でなければなりません（MUST）。それらのTCメッセージは、広告される近隣アドレスを一切運んではなりません（MUST NOT）。これは、それらのルーターがSOURCE_ROUTE TLVを広告し、ほかのルーターがソースルートに対応したルーターを把握して、マルチパスルーティングの宛先として使えるようにするためのものです。そのようなTCメッセージのVALIDITY_TIME TLVに関連付けられる有効時間はSR_HOLD_TIMEと等しくなります。SR_HOLD_TIMEは、SR_TC_INTERVALより大きくなければなりません（MUST）。TCメッセージが省略可能なINTERVAL_TIME TLVを運ぶ場合、そのTLVはSR_TC_INTERVALを符号化した値を持たなければなりません（MUST）。

8.2. HELLO and TC Message Processing

8.2. HELLOメッセージとTCメッセージの処理

HELLO and TC messages are processed according to Sections 15.3 and 16.3 of [RFC7181].

HELLOメッセージとTCメッセージは、[RFC7181]のセクション15.3と16.3に従って処理されます。

In addition to the reasons specified in [RFC7181] for discarding a HELLO message or a TC message on reception, a HELLO or TC message received MUST be discarded if it has more than one Message TLV with Type = SOURCE_ROUTE.

受信時にHELLOメッセージまたはTCメッセージを破棄する理由として[RFC7181]で規定されているものに加えて、受信したHELLOメッセージまたはTCメッセージがType = SOURCE_ROUTEのMessage TLVを複数持つ場合は、そのメッセージを破棄しなければなりません（MUST）。

For every HELLO or TC message received, if there is a Message TLV with Type := SOURCE_ROUTE, create or update (if the Tuple exists already) the SR-OLSR Routing Tuple with:

受信したすべてのHELLOメッセージまたはTCメッセージについて、Type := SOURCE_ROUTEのMessage TLVがある場合は、次の内容でSR-OLSR Routing Tupleを作成するか、（そのTupleがすでに存在する場合は）更新します。

  • SR_addr := originator address of the HELLO or TC message
  • SR_time := current_time + validity time of the TC or HELLO message defined in [RFC7181].
  • SR_addr := そのHELLOメッセージまたはTCメッセージの発信者アドレス
  • SR_time := current_time + [RFC7181]で定義されているTCメッセージまたはHELLOメッセージの有効時間

8.3. MPR Selection

8.3. MPRの選択

Each MP-OLSRv2 Routing Process selects routing MPRs and flooding MPRs following Section 18 of [RFC7181]. In a mixed network with OLSRv2-only routers, the following considerations apply when calculating MPRs:

各MP-OLSRv2 Routing Processは、[RFC7181]のセクション18に従ってルーティングMPRとフラッディングMPRを選択します。OLSRv2のみのルーターが混在するネットワークでは、MPRを計算する際に次の考慮事項が適用されます。

  • MP-OLSRv2 routers SHOULD be preferred as routing MPRs to increase the possibility of finding disjoint paths using MP-OLSRv2 routers.
  • The number of routing MPRs that run the MP-OLSRv2 Routing Process MUST be equal to or greater than NUMBER_OF_PATHS if there are enough MP-OLSRv2 symmetric neighbors. Otherwise, all the MP-OLSRv2 routers are selected as routing MPRs, except the routers with willingness WILL_NEVER.
  • MP-OLSRv2ルーターを使って互いに素なパスを見つける可能性を高めるために、ルーティングMPRとしてMP-OLSRv2ルーターを優先すべきです（SHOULD）。
  • 十分な数のMP-OLSRv2の対称近隣がある場合、MP-OLSRv2 Routing Processを実行するルーティングMPRの数は、NUMBER_OF_PATHS以上でなければなりません（MUST）。そうでない場合は、willingnessがWILL_NEVERであるルーターを除く、すべてのMP-OLSRv2ルーターをルーティングMPRとして選択します。

8.4. Datagram Processing at the MP-OLSRv2 Originator

8.4. MP-OLSRv2の発信者でのデータグラムの処理

If datagrams without a source routing header need to be forwarded using multiple paths (for example, based on the information of a Diffserv codepoint [RFC2474]), the MP-OLSRv2 Routing Process will try to find the Multipath Routing Tuple where:

ソースルーティングヘッダーのないデータグラムを（たとえば、Diffservコードポイント[RFC2474]の情報に基づいて）複数のパスを使って転送する必要がある場合、MP-OLSRv2 Routing Processは、次の条件を満たすMultipath Routing Tupleを探そうとします。

  • MR_dest_addr = destination of the datagram
  • MR_dest_addr = データグラムの宛先

If no matching Multipath Routing Tuple is found and the Multipath Routing Set is maintained proactively, it indicates that there is no multipath route available to the desired destination. The datagram is forwarded following the OLSRv2 Routing Process.

一致するMultipath Routing Tupleが見つからず、Multipath Routing Setがプロアクティブに維持されている場合、それは目的の宛先への利用可能なマルチパスルートがないことを示します。データグラムは、OLSRv2 Routing Processに従って転送されます。

If no matching Multipath Routing Tuple is found and the Multipath Routing Set is maintained reactively, the multipath algorithm defined in Section 8.5 is invoked to calculate the Multipath Routing Tuple to the destination. If the calculation does not return any Multipath Routing Tuple, the following steps are aborted and the datagram is forwarded following the OLSRv2 Routing Process.

一致するMultipath Routing Tupleが見つからず、Multipath Routing Setがリアクティブに維持されている場合は、セクション8.5で定義されているマルチパスアルゴリズムを呼び出して、宛先へのMultipath Routing Tupleを計算します。計算がMultipath Routing Tupleを1つも返さない場合は、以降の手順を中止し、データグラムをOLSRv2 Routing Processに従って転送します。

If a matching Multipath Routing Tuple is obtained, the Path Tuples of the Multipath Routing Tuple are applied to the datagrams using either per-flow or per-datagram scheduling, depending on the transport layer protocol and the application used. By default, per-flow scheduling is used, especially for the transport protocols that are sensitive to reordering, such as TCP. The path-selection decision is made on the first datagram and all subsequent datagrams of the same flow use the same path. If the path breaks before the flow is closed, another path with the most similar metric is used. Per-datagram scheduling is recommended if the traffic is insensitive to reordering such as unreliable transmission of media traffic or when erasure coding is applied. In such a case, each datagram selects its paths independently.

一致するMultipath Routing Tupleが得られた場合、トランスポート層のプロトコルと使用するアプリケーションに応じて、フロー単位またはデータグラム単位のいずれかのスケジューリングを使って、そのMultipath Routing TupleのPath Tupleをデータグラムに適用します。デフォルトでは、フロー単位のスケジューリングを使用します。これは特に、TCPのような順序の入れ替わりに敏感なトランスポートプロトコルに当てはまります。パス選択の決定は最初のデータグラムで行われ、同じフローの後続のすべてのデータグラムは同じパスを使用します。フローが閉じられる前にパスが切断された場合は、メトリックが最も近い別のパスを使用します。メディアトラフィックの信頼性のない伝送のようにトラフィックが順序の入れ替わりに敏感でない場合や、消失訂正符号化を適用する場合は、データグラム単位のスケジューリングを推奨します。そのような場合、各データグラムはそれぞれ独立にパスを選択します。

By default, the traffic load should be equally distributed in multiple paths. Other path-scheduling mechanisms (e.g., assigning more traffic over better paths) are also possible and will not impact the interoperability of different implementations.

デフォルトでは、トラフィックの負荷は複数のパスに均等に分散させるべきです。ほかのパススケジューリングのメカニズム（たとえば、より良いパスにより多くのトラフィックを割り当てるなど）も可能であり、異なる実装間の相互運用性には影響しません。

The addresses in PT_address[1, ..., n-1] of the chosen Path Tuple are thus added to the datagram header as the source routing header. For IPv6 networks, strict source routing is used; thus, all the intermediate routers in the path are stored in the source routing header following the format defined in Section 3 of [RFC6554] with the Routing Type set to 3.

こうして、選択したPath TupleのPT_address[1, ..., n-1]のアドレスが、ソースルーティングヘッダーとしてデータグラムのヘッダーに追加されます。IPv6ネットワークではストリクトソースルーティングを使用します。したがって、パス内のすべての中間ルーターが、[RFC6554]のセクション3で定義されている形式に従い、Routing Typeを3に設定したソースルーティングヘッダーに格納されます。

For IPv4 networks, loose source routing is used with the following rules:

IPv4ネットワークでは、次の規則に従ってルーズソースルーティングを使用します。

  • Only the addresses that exist in the SR-OLSR Router Set can be added to the source routing header.
  • If the length of the path (n) is greater than MAX_SRC_HOPS (Section 5) or if adding the whole path information exceeds the MTU, only the "key" routers in the path are kept. By default, the key routers are uniformly chosen in the path. If further information, such as the capacity of the routers (e.g., battery life) or the routers' willingness in forwarding data, is available, the routers with higher capacity and willingness are preferred.
  • The routers that are considered not appropriate for forwarding indicated by external policies should be avoided.
  • SR-OLSR Router Setに存在するアドレスだけをソースルーティングヘッダーに追加できます。
  • パスの長さ（n）がMAX_SRC_HOPS（セクション5）を超える場合、またはパス情報全体を追加するとMTUを超える場合は、パス内の「キー」ルーターだけを残します。デフォルトでは、キールーターはパス内から均等に選択します。ルーターの能力（たとえば、バッテリーの残量）や、データ転送に対するルーターの意欲（willingness）などのさらなる情報が利用可能な場合は、能力と意欲のより高いルーターを優先します。
  • 外部のポリシーによって示される、転送に適さないとみなされるルーターは避けるべきです。

It is not recommended to fragment the IP packet if the packet with the source routing header would exceed the minimum MTU along the path. Depending on the size of the routing domain, the MTU should be at least 1280 + 40 (for the outer IP header) + 16 * diameter of the network in number of hops (for the source routing header). If the links in the network have different MTU sizes, by using technologies like Path MTU Discovery, the routers are able to be aware of the MTU along the path. The size of the datagram plus the size of IP headers (including the source routing header) should not exceed the minimum MTU along the path; otherwise, the source routing should not be used.

ソースルーティングヘッダーを付けたパケットがパス上の最小MTUを超える場合に、IPパケットをフラグメント化することは推奨されません。ルーティングドメインの大きさに応じて、MTUは少なくとも1280 + 40（外側のIPヘッダーの分）+ 16 * ホップ数で表したネットワークの直径（ソースルーティングヘッダーの分）であるべきです。ネットワーク内のリンクのMTUサイズが異なる場合、ルーターはPath MTU Discoveryのような技術を使うことで、パス上のMTUを把握できます。データグラムのサイズとIPヘッダー（ソースルーティングヘッダーを含む）のサイズの合計がパス上の最小MTUを超えるべきではありません。超える場合は、ソースルーティングを使うべきではありません。

If the destination of the datagrams is out of the MP-OLSRv2 routing domain, the datagram must be source routed to the gateway between the MP-OLSRv2 routing domain and the rest of the Internet. The gateway MUST remove the source routing header before forwarding the datagram to the rest of the Internet.

データグラムの宛先がMP-OLSRv2ルーティングドメインの外にある場合、データグラムは、MP-OLSRv2ルーティングドメインとインターネットの残りの部分との間のゲートウェイまでソースルーティングされなければなりません。ゲートウェイは、データグラムをインターネットの残りの部分へ転送する前に、ソースルーティングヘッダーを削除しなければなりません（MUST）。

8.5. Multipath Calculation

8.5. マルチパスの計算

8.5.1. Requirements of Multipath Calculation

8.5.1. マルチパス計算の要件

The Multipath Routing Set maintains the information of multiple paths to the destination. The Path Tuples of the Multipath Routing Set (Section 7.2) are generated based on a multipath algorithm.

Multipath Routing Setは、宛先への複数のパスの情報を維持します。Multipath Routing Set（セクション7.2）のPath Tupleは、マルチパスアルゴリズムに基づいて生成されます。

For each path to a destination, the algorithm must provide:

アルゴリズムは、宛先への各パスについて次のものを提供しなければなりません。

  • The metric of the path to the destination,
  • The list of intermediate routers on the path.
  • 宛先へのパスのメトリック
  • パス上の中間ルーターのリスト

For IPv6 networks, as strict source routing is used, only the routers that exist in the SR-OLSRv2 Router Set are considered in the path calculation, i.e., only the source-routing-supported routers can exist in the path.

IPv6ネットワークではストリクトソースルーティングを使うので、パスの計算ではSR-OLSRv2 Router Setに存在するルーターだけを考慮します。つまり、ソースルーティングをサポートするルーターだけがパス内に存在できます。

After the calculation of multiple paths, the metric of paths (denoted c_i for path i) to the destination is compared to the R_metric of the OLSRv2 Routing Tuple ([RFC7181]) to the same destination. If the metric c_i is greater than R_metric * CUTOFF_RATIO (Section 5), the corresponding path i SHOULD NOT be used. If less than two paths are found with metrics less than R_metric * CUTOFF_RATIO, the router SHOULD fall back to OLSRv2 Routing Process without using multipath routing. This can happen if there are too many OLSRv2-only routers in the network, and requiring multipath routing may result in inferior paths.

複数のパスを計算した後、宛先へのパスのメトリック（パスiについてc_iと表記）を、同じ宛先へのOLSRv2のRouting Tuple（[RFC7181]）のR_metricと比較します。メトリックc_iがR_metric * CUTOFF_RATIO（セクション5）を超える場合、対応するパスiを使用すべきではありません（SHOULD NOT）。メトリックがR_metric * CUTOFF_RATIO未満のパスが2つ未満しか見つからない場合、ルーターはマルチパスルーティングを使わずに、OLSRv2 Routing Processにフォールバックすべきです（SHOULD）。これは、ネットワーク内にOLSRv2のみのルーターが多すぎる場合に起こり得ることであり、マルチパスルーティングを要求すると劣ったパスになる可能性があります。

By invoking the multipath algorithm, up to NUMBER_OF_PATHS paths are obtained and added to the Multipath Routing Set by creating a Multipath Routing Tuple with:

マルチパスアルゴリズムを呼び出すことで、最大NUMBER_OF_PATHS個のパスが得られ、次の内容のMultipath Routing Tupleを作成することによってMultipath Routing Setに追加されます。

  • MR_dest_addr := destination of the datagram.
  • An MP_path_set with calculated Path Tuples. Each Path Tuple corresponds to a path obtained in the Multipath Dijkstra Algorithm, with PT_metric := metric of the calculated path and PT_address[1, ..., n-1] := list of intermediate routers.
  • MR_dest_addr := データグラムの宛先。
  • 計算されたPath Tupleを持つMP_path_set。各Path Tupleは、Multipath Dijkstra Algorithmで得られた1つのパスに対応し、PT_metric := 計算されたパスのメトリック、PT_address[1, ..., n-1] := 中間ルーターのリストとします。

8.5.2. Multipath Dijkstra Algorithm

8.5.2. マルチパスダイクストラアルゴリズム（Multipath Dijkstra Algorithm）

This section introduces the Multipath Dijkstra Algorithm as a default algorithm. It tries to obtain disjoint paths when appropriate, but it does not guarantee strict disjoint paths. The use of other algorithms is not prohibited, as long as the requirements described in Section 8.5.1 are met. Using different multipath algorithms will not impact the interoperability.

このセクションでは、デフォルトのアルゴリズムとしてMultipath Dijkstra Algorithmを紹介します。このアルゴリズムは、適切な場合に互いに素なパスを得ようとしますが、厳密に互いに素なパスを保証するものではありません。セクション8.5.1で説明した要件を満たす限り、ほかのアルゴリズムの使用は禁止されません。異なるマルチパスアルゴリズムを使っても、相互運用性には影響しません。

The general principle of the Multipath Dijkstra Algorithm [ADHOC11] is to use the Dijkstra Algorithm for multiple iterations and to look for the shortest path P[i] to the destination d at iteration i. After each iteration, the metric of used links is increased. Compared to the original Dijkstra's algorithm, the main modification consists in adding two incremental functions, named metric functions fp and fe, in order to prevent the next steps resulting in similar paths:

Multipath Dijkstra Algorithm [ADHOC11]の一般的な原理は、ダイクストラアルゴリズムを複数回繰り返して使い、繰り返しiで宛先dへの最短パスP[i]を探すことです。各繰り返しの後、使用したリンクのメトリックを増やします。元のダイクストラアルゴリズムと比べた主な変更点は、次のステップで似たパスが得られるのを防ぐために、メトリック関数と呼ばれる2つの増分関数fpとfeを追加することです。

  • fp(c) is used to increase metrics of arcs belonging to the previous path P[i-1] (with i>1), where c is the value of the previous metric. This encourages future paths to use different arcs but not different vertices.
  • fe(c) is used to increase metrics of the arcs that lead to intermediate vertices of the previous path P[i-1] (with i>1), where c is the value of the previous metric. The "lead to" means that only one vertex of the arc belongs to the previous path P[i-1] while the other vertex does not. The "intermediate" means that the source and destination vertices are not considered.
  • fp(c)は、前のパスP[i-1]（i>1）に属する弧（arc）のメトリックを増やすのに使います。ここで、cは以前のメトリックの値です。これにより、以降のパスが異なる弧を使うよう促されますが、異なる頂点（vertex）を使うようには促されません。
  • fe(c)は、前のパスP[i-1]（i>1）の中間頂点に「つながる」弧のメトリックを増やすのに使います。ここで、cは以前のメトリックの値です。「つながる」とは、その弧の一方の頂点だけが前のパスP[i-1]に属し、もう一方の頂点は属さないことを意味します。「中間」とは、送信元と宛先の頂点は考慮しないことを意味します。

Consider the simple example in Figure 1: a path P[i] S--A--D is obtained at step i. For the next step, the metric of link S--A and A--D are to be increased using fp(c) because they belong to the path P[i]. A--B is to be increased using fe(c) because A is an intermediate vertex of path P[i], and B is not part of P[i]. B--D is unchanged.

図1の単純な例を考えます。ステップiでパスP[i] S--A--Dが得られたとします。次のステップでは、リンクS--AとA--DはパスP[i]に属するので、fp(c)を使ってそれらのメトリックを増やします。AはパスP[i]の中間頂点であり、BはP[i]の一部ではないので、A--Bはfe(c)を使って増やします。B--Dは変更しません。

It is possible to choose a different fp and fe to get link-disjoint paths or node-disjoint paths as desired. A recommendation for configuration of fp and fe is given in Section 9.

目的に応じて、異なるfpとfeを選択して、リンクが互いに素なパスやノードが互いに素なパスを得ることができます。fpとfeの設定に関する推奨事項はセクション9で示します。

To get NUMBER_OF_PATHS different paths, for each path P[i] (i = 1, ..., NUMBER_OF_PATHS):

NUMBER_OF_PATHS個の異なるパスを得るために、各パスP[i]（i = 1, ..., NUMBER_OF_PATHS）について次のことを行います。

  1. Run Dijkstra's algorithm to get the shortest path P[i] for the destination d.
  2. Apply metric function fp to the metric of links (in both directions) in P[i].
  3. Apply metric function fe to the metric of links (in both directions) that lead to routers used in P[i].
  1. ダイクストラアルゴリズムを実行して、宛先dへの最短パスP[i]を得ます。
  2. P[i]内のリンクの（両方向の）メトリックにメトリック関数fpを適用します。
  3. P[i]で使われたルーターにつながるリンクの（両方向の）メトリックにメトリック関数feを適用します。

A simple example of the Multipath Dijkstra Algorithm is illustrated in Appendix A.

Multipath Dijkstra Algorithmの単純な例を付録Aに示します。

8.6. Multipath Routing Set Updates

8.6. Multipath Routing Setの更新

The Multipath Routing Set MUST be updated when the Local Information Base, the Neighborhood Information Base, or the Topology Information Base indicate a change (including a change of any potentially used outgoing neighbor metric values) of the known symmetric links and/or attached networks in the MANET, hence, changing the Topology Graph as described in Section 17.7 of [RFC7181]. How the Multipath Routing Set is updated depends on whether the set is maintained reactively or proactively:

Local Information Base、Neighborhood Information Base、またはTopology Information Baseが、MANET内の既知の対称リンクや接続されたネットワークの変化（使用される可能性のある送信方向の近隣メトリック値の変化を含む）を示し、その結果、[RFC7181]のセクション17.7で説明されているようにTopology Graphが変化した場合は、Multipath Routing Setを更新しなければなりません（MUST）。Multipath Routing Setをどのように更新するかは、そのセットがリアクティブに維持されているかプロアクティブに維持されているかによって異なります。

  • In reactive mode, all the Tuples in the Multipath Routing Set are removed. The new arriving datagrams will be processed as specified in Section 8.4.
  • In proactive mode, the routes to all the destinations are updated according to Section 8.5.
  • リアクティブモードでは、Multipath Routing Set内のすべてのTupleを削除します。新しく到着したデータグラムは、セクション8.4で規定されているように処理されます。
  • プロアクティブモードでは、すべての宛先へのルートをセクション8.5に従って更新します。

8.7. Datagram Forwarding

8.7. データグラムの転送

In IPv4 networks, datagrams are forwarded using loose source routing as specified in Section 3.1 of [RFC791].

IPv4ネットワークでは、データグラムは[RFC791]のセクション3.1で規定されているルーズソースルーティングを使って転送されます。

In IPv6 networks, datagrams are forwarded using strict source routing as specified in Section 4.2 of [RFC6554], except the applied routers are MP-OLSRv2 routers rather than RPL routers. The last hop of the source route MUST remove the source routing header.

IPv6ネットワークでは、データグラムは[RFC6554]のセクション4.2で規定されているストリクトソースルーティングを使って転送されます。ただし、適用されるルーターはRPLルーターではなくMP-OLSRv2ルーターです。ソースルートの最後のホップは、ソースルーティングヘッダーを削除しなければなりません（MUST）。

9. Configuration Parameters

9. 設定パラメーター

This section gives default values and guidelines for setting parameters defined in Section 5. Network administrators may wish to change certain or all the parameters for different network scenarios. As an experimental protocol, the users of this protocol are also encouraged to explore different parameter settings in various network environments and provide feedback.

このセクションでは、セクション5で定義したパラメーターのデフォルト値と設定のガイドラインを示します。ネットワーク管理者は、ネットワークのシナリオに応じて、一部またはすべてのパラメーターを変更したいと考えるかもしれません。実験的なプロトコルとして、このプロトコルの利用者には、さまざまなネットワーク環境で異なるパラメーター設定を探索し、フィードバックを提供することも推奨されます。

  • NUMBER_OF_PATHS := 3. This parameter defines the number of parallel paths used in datagram forwarding. Setting it to 1 makes the specification identical to OLSRv2. Setting it to too large of a value may lead to unnecessary computational overhead and inferior paths.
  • MAX_SRC_HOPS := 10, for IPv4 networks. For IPv6 networks, it MUST be set to 0, i.e., no constraint on the maximum number of hops.
  • CUTOFF_RATIO := 1.5. It MUST be greater than or equal to 1.
  • SR_TC_INTERVAL := 10 x TC_INTERVAL. It MUST be greater than or equal to TC_INTERVAL. It SHOULD be significantly greater than TC_INTERVAL to reduce unnecessary TC message generations.
  • SR_HOLD_TIME := 3 x SR_TC_INTERVAL. It MUST be greater than SR_TC_INTERVAL and SHOULD allow for a small number of lost messages.
  • NUMBER_OF_PATHS := 3。このパラメーターは、データグラムの転送に使う並列のパスの数を定義します。これを1に設定すると、この仕様はOLSRv2と同じになります。大きすぎる値に設定すると、不必要な計算のオーバーヘッドや劣ったパスにつながる可能性があります。
  • IPv4ネットワークではMAX_SRC_HOPS := 10。IPv6ネットワークでは、この値を0、つまりホップの最大数に制約なしに設定しなければなりません（MUST）。
  • CUTOFF_RATIO := 1.5。この値は1以上でなければなりません（MUST）。
  • SR_TC_INTERVAL := 10 x TC_INTERVAL。この値はTC_INTERVAL以上でなければなりません（MUST）。不必要なTCメッセージの生成を減らすために、この値はTC_INTERVALより大幅に大きくするべきです（SHOULD）。
  • SR_HOLD_TIME := 3 x SR_TC_INTERVAL。この値はSR_TC_INTERVALより大きくなければなりません（MUST）。また、少数のメッセージの損失を許容できるようにするべきです（SHOULD）。

If the Multipath Dijkstra Algorithm is applied:

Multipath Dijkstra Algorithmを適用する場合は、次のとおりです。

  • fp(c) := 4*c, where c is the original metric of the link.
  • fe(c) := 2*c, where c is the original metric of the link.
  • fp(c) := 4*c。ここで、cはリンクの元のメトリックです。
  • fe(c) := 2*c。ここで、cはリンクの元のメトリックです。

The setting of metric functions fp and fc defines the preference of obtained multiple disjoint paths. If id is the identity function, i.e., fp(c)=c, three cases are possible:

メトリック関数fpとfcの設定によって、得られる互いに素な複数のパスの優先傾向が決まります。idを恒等関数、つまりfp(c)=cとすると、次の3つの場合が考えられます。

  • if id=fe<fp, only increase the metric of related links;
  • if id<fe=fp, apply equal increase to the metric of related nodes and links;
  • if id<fe<fp, apply greater increase to the metric of related links.
  • id=fe<fpの場合、関連するリンクのメトリックだけを増やします。
  • id<fe=fpの場合、関連するノードとリンクのメトリックを等しく増やします。
  • id<fe<fpの場合、関連するリンクのメトリックをより大きく増やします。

Increasing the metric of related links or nodes means avoiding the use of such links or nodes in the next path to be calculated.

関連するリンクやノードのメトリックを増やすことは、次に計算するパスでそのようなリンクやノードの使用を避けることを意味します。

10. Security Considerations

10. セキュリティーに関する考慮事項

As an extension of [RFC7181], the security considerations and security architecture illustrated in [RFC7181] are applicable to this MP-OLSRv2 specification. The implementations without security mechanisms are vulnerable to threats discussed in [RFC8116].

[RFC7181]の拡張として、[RFC7181]で説明されているセキュリティーに関する考慮事項とセキュリティーアーキテクチャーは、このMP-OLSRv2の仕様にも適用されます。セキュリティーメカニズムを持たない実装は、[RFC8116]で議論されている脅威に対して脆弱です。

In a mixed network with OLSRv2-only routers, a compromised router can add SOURCE_ROUTE TLVs in its TC and HELLO messages, which will make other MP-OLSRv2 Routing Processes believe that it supports source routing. This will increase the possibility of being chosen as MPRs and put into the source routing header. The former will make it possible to manipulate the flooding of TC messages and the latter will make the datagram pass through the compromised router.

OLSRv2のみのルーターが混在するネットワークでは、侵害されたルーターが自身のTCメッセージとHELLOメッセージにSOURCE_ROUTE TLVを追加して、ほかのMP-OLSRv2 Routing Processにそのルーターがソースルーティングをサポートしていると信じ込ませることができます。これにより、そのルーターがMPRとして選ばれる可能性と、ソースルーティングヘッダーに入れられる可能性が高まります。前者によってTCメッセージのフラッディングを操作することが可能になり、後者によってデータグラムが侵害されたルーターを通過するようになります。

As with [RFC7181], a conformant implementation of MP-OLSRv2 MUST, at minimum, implement the security mechanisms specified in [RFC7183] to provide integrity and replay protection of routing control messages.

[RFC7181]と同様に、MP-OLSRv2の準拠実装は、ルーティング制御メッセージの完全性とリプレイ保護を提供するために、少なくとも[RFC7183]で規定されているセキュリティーメカニズムを実装しなければなりません（MUST）。

The MP-OLSRv2 Routing Process MUST drop datagrams entering or exiting an OLSRv2/MP-OLSRv2 routing domain that contain a source routing header. Compared to OLSRv2, the use of the source routing header in this specification introduces vulnerabilities related to source routing attacks, which include bypassing filtering devices, bandwidth exhaustion of certain routers, etc. Those attacks are discussed in Section 5 of [RFC6554] and [RFC5095]. The influence is limited to the OLSRv2/MP-OLSRv2 routing domain because the source routing header is used only in the current routing domain.

MP-OLSRv2 Routing Processは、OLSRv2／MP-OLSRv2ルーティングドメインに入る、またはそこから出るデータグラムのうち、ソースルーティングヘッダーを含むものを破棄しなければなりません（MUST）。OLSRv2と比べて、この仕様でのソースルーティングヘッダーの使用は、フィルタリング装置の迂回や特定のルーターの帯域幅の枯渇などを含む、ソースルーティング攻撃に関連する脆弱性をもたらします。それらの攻撃は、[RFC6554]のセクション5と[RFC5095]で議論されています。ソースルーティングヘッダーは現在のルーティングドメイン内でだけ使われるため、その影響はOLSRv2／MP-OLSRv2ルーティングドメインに限定されます。

If the multiple paths are calculated reactively, the datagrams SHOULD be buffered while the paths are being calculated. Because the path calculation is local and no control message is exchanged, the buffering time should be trivial. However, depending on the CPU power and memory of the router, a maximum buffer size SHOULD be set to avoid occupying too much memory of the router. When the buffer is full, the oldest datagrams are dropped. A possible attack that a malicious application could launch would be one in which it initiates a large amount of datagrams to all the other routers in the network, thus triggering path calculation to all the other routers and during which the datagrams are buffered. This might flush other legitimate datagrams. But the impact of the attack is transient: once the path calculation is finished, the datagrams are forwarded and the buffer goes back to empty.

複数のパスをリアクティブに計算する場合、パスを計算している間はデータグラムをバッファリングすべきです（SHOULD）。パスの計算はルーター内で完結し、制御メッセージは交換されないため、バッファリングの時間はごくわずかなはずです。ただし、ルーターのCPU能力とメモリーに応じて、ルーターのメモリーを占有しすぎないように、バッファーの最大サイズを設定すべきです（SHOULD）。バッファーが満杯になると、最も古いデータグラムが破棄されます。悪意のあるアプリケーションが仕掛ける可能性のある攻撃として、ネットワーク内のほかのすべてのルーターに向けて大量のデータグラムを送り出し、それによってほかのすべてのルーターへのパス計算を起動させ、その間データグラムがバッファリングされるというものが考えられます。これにより、ほかの正当なデータグラムが押し出される可能性があります。しかし、この攻撃の影響は一時的です。パスの計算が終わると、データグラムは転送され、バッファーは空に戻ります。

As mentioned in Section 8.5, the Multipath Dijkstra Algorithm does not guarantee strict disjoint paths in order to avoid choosing inferior paths. For example, given the topology in Figure 4, two paths from node S to D are desired. On the top of the figure, there is a high cost path between S and D.

セクション8.5で述べたように、Multipath Dijkstra Algorithmは、劣ったパスを選択するのを避けるために、厳密に互いに素なパスを保証しません。たとえば、図4のトポロジーが与えられ、ノードSからDへの2つのパスが求められているとします。図の上部には、SとDの間の高コストのパスがあります。

If an algorithm tries to obtain strict disjoint paths, the two paths obtained will be S--B--D and S--(high cost path)--D, which are extremely unbalanced. It is undesirable because it will cause huge delay variance between the paths. By using the Multipath Dijkstra Algorithm, which is based on the punishing scheme, S--B--D and S--B--C--D will be obtained.

アルゴリズムが厳密に互いに素なパスを得ようとすると、得られる2つのパスはS--B--DとS--（高コストのパス）--Dになり、極めて不均衡です。これはパス間の遅延に大きなばらつきを引き起こすため、望ましくありません。ペナルティー方式に基づくMultipath Dijkstra Algorithmを使うと、S--B--DとS--B--C--Dが得られます。
