RFC 8337

Model-Based Metrics for Bulk Transport Capacity

RFC 8337

バルク転送容量のためのモデルベースメトリック

Abstract

概要

This document introduces a new class of Model-Based Metrics designed to assess if a complete Internet path can be expected to meet a predefined Target Transport Performance by applying a suite of IP diagnostic tests to successive subpaths. The subpath-at-a-time tests can be robustly applied to critical infrastructure, such as network interconnections or even individual devices, to accurately detect if any part of the infrastructure will prevent paths traversing it from meeting the Target Transport Performance.

この文書は、連続するサブパスに一連のIP診断テストを適用することで、インターネットの完全なパスがあらかじめ定めた目標トランスポート性能（Target Transport Performance）を満たすと期待できるかどうかを評価するために設計された、新しい種類のモデルベースメトリック（Model-Based Metrics）を導入します。 サブパスごとのテストは、ネットワークの相互接続や個々の機器などの重要なインフラストラクチャーに堅牢に適用でき、インフラストラクチャーのいずれかの部分が、そこを通過するパスの目標トランスポート性能の達成を妨げるかどうかを正確に検出できます。

Model-Based Metrics rely on mathematical models to specify a Targeted IP Diagnostic Suite, a set of IP diagnostic tests designed to assess whether common transport protocols can be expected to meet a predetermined Target Transport Performance over an Internet path.

モデルベースメトリックは、目標指向IP診断スイート（Targeted IP Diagnostic Suite）を規定するために数学モデルに依拠します。 目標指向IP診断スイートとは、一般的なトランスポートプロトコルがインターネットのパス上であらかじめ定めた目標トランスポート性能を満たすと期待できるかどうかを評価するために設計された、一連のIP診断テストです。

For Bulk Transport Capacity, the IP diagnostics are built using test streams and statistical criteria for evaluating the packet transfer that mimic TCP over the complete path. The temporal structure of the test stream (e.g., bursts) mimics TCP or other transport protocols carrying bulk data over a long path. However, they are constructed to be independent of the details of the subpath under test, end systems, or applications. Likewise, the success criteria evaluates the packet transfer statistics of the subpath against criteria determined by protocol performance models applied to the Target Transport Performance of the complete path. The success criteria also does not depend on the details of the subpath, end systems, or applications.

バルク転送容量（Bulk Transport Capacity）については、完全なパス上のTCPを模倣するテストストリームと、パケット転送を評価するための統計的基準を用いてIP診断を構築します。 テストストリームの時間的構造（たとえばバースト）は、長いパス上でバルクデータを運ぶTCPやその他のトランスポートプロトコルを模倣します。 ただし、テストストリームは、テスト対象のサブパス、エンドシステム、アプリケーションの詳細には依存しないように構築されます。 同様に、成功基準は、サブパスのパケット転送統計を、完全なパスの目標トランスポート性能にプロトコル性能モデルを適用して決定した基準と照らし合わせて評価します。 成功基準もまた、サブパス、エンドシステム、アプリケーションの詳細には依存しません。

1. Introduction

1. はじめに

Model-Based Metrics (MBM) rely on peer-reviewed mathematical models to specify a Targeted IP Diagnostic Suite (TIDS), a set of IP diagnostic tests designed to assess whether common transport protocols can be expected to meet a predetermined Target Transport Performance over an Internet path. This document describes the modeling framework to derive the test parameters for assessing an Internet path's ability to support a predetermined Bulk Transport Capacity.

モデルベースメトリック（Model-Based Metrics、MBM）は、目標指向IP診断スイート（Targeted IP Diagnostic Suite、TIDS）を規定するために、査読済みの数学モデルに依拠します。 TIDSとは、一般的なトランスポートプロトコルがインターネットのパス上で、あらかじめ定めた目標トランスポート性能（Target Transport Performance）を満たすと期待できるかどうかを評価するために設計された、一連のIP診断テストです。 この文書では、インターネットのパスが、あらかじめ定めたバルク転送容量（Bulk Transport Capacity）をサポートできるかどうかを評価するためのテストパラメーターを導出する、モデル化のフレームワークについて説明します。

Each test in TIDS measures some aspect of IP packet transfer needed to meet the Target Transport Performance. For Bulk Transport Capacity, the TIDS includes IP diagnostic tests to verify that there is sufficient IP capacity (data rate), sufficient queue space at bottlenecks to absorb and deliver typical transport bursts, low enough background packet loss ratio to not interfere with congestion control, and other properties described below. Unlike typical IP Performance Metrics (IPPM) that yield measures of network properties, Model-Based Metrics nominally yield pass/fail evaluations of the ability of standard transport protocols to meet the specific performance objective over some network path.

TIDSの各テストは、目標トランスポート性能を満たすために必要なIPパケット転送のなんらかの側面を測定します。 バルク転送容量の場合、TIDSには、十分なIP容量（データレート）があること、典型的なトランスポートのバーストを吸収して配送するのに十分なキュー空間がボトルネックにあること、輻輳制御を妨げない程度にバックグラウンドのパケット損失率が低いこと、および後述するその他の性質を検証するIP診断テストが含まれます。 ネットワークの性質の測定値をもたらす典型的なIP性能メトリック（IP Performance Metrics、IPPM）とは異なり、モデルベースメトリックは、標準的なトランスポートプロトコルがあるネットワークパス上で特定の性能目標を満たす能力について、名目上、合格／不合格の評価をもたらします。

In most cases, the IP diagnostic tests can be implemented by combining existing IPPM metrics with additional controls for generating test streams having a specified temporal structure (bursts or standing queues caused by constant bit rate streams, etc.) and statistical criteria for evaluating packet transfer. The temporal structure of the test streams mimics transport protocol behavior over the complete path; the statistical criteria models the transport protocol's response to less-than-ideal IP packet transfer. In control theory terms, the tests are "open loop". Note that running a test requires the coordinated activity of sending and receiving measurement points.

ほとんどの場合、IP診断テストは、既存のIPPMメトリックに、指定した時間的構造（バーストや、固定ビットレートのストリームによって生じる定常キューなど）を持つテストストリームを生成するための追加の制御と、パケット転送を評価するための統計的基準とを組み合わせることで実装できます。 テストストリームの時間的構造は、完全なパス上でのトランスポートプロトコルの振る舞いを模倣します。 統計的基準は、理想的とはいえないIPパケット転送に対するトランスポートプロトコルの反応をモデル化します。 制御理論の用語でいえば、これらのテストは「開ループ（open loop）」です。 テストを実行するには、送信側と受信側の測定点が協調して動作する必要があることに注意してください。

This document addresses Bulk Transport Capacity. It describes an alternative to the approach presented in "A Framework for Defining Empirical Bulk Transfer Capacity Metrics" [RFC3148]. Other Model-Based Metrics may cover other applications and transports, such as Voice over IP (VoIP) over UDP, RTP, and new transport protocols.

この文書はバルク転送容量を扱います。 この文書は、「A Framework for Defining Empirical Bulk Transfer Capacity Metrics」[RFC3148]で示されたアプローチに代わるものを説明します。 ほかのモデルベースメトリックでは、UDP上のVoice over IP（VoIP）、RTP、新しいトランスポートプロトコルなど、ほかのアプリケーションやトランスポートを扱う場合があります。

This document assumes a traditional Reno TCP-style, self-clocked, window-controlled transport protocol that uses packet loss and Explicit Congestion Notification (ECN) Congestion Experienced (CE) marks for congestion feedback. There are currently some experimental protocols and congestion control algorithms that are rate based or otherwise fall outside of these assumptions. In the future, these new protocols and algorithms may call for revised models.

この文書では、輻輳のフィードバックにパケット損失と明示的輻輳通知（Explicit Congestion Notification、ECN）の輻輳経験（Congestion Experienced、CE）マークを用いる、従来のReno TCP形式の、セルフクロック型でウィンドウ制御型のトランスポートプロトコルを想定しています。 現在、レートベースであるなど、これらの前提から外れる実験的なプロトコルや輻輳制御アルゴリズムがいくつか存在します。 将来、これらの新しいプロトコルやアルゴリズムのために、モデルの改訂が必要になるかもしれません。

The MBM approach, i.e., mapping Target Transport Performance to a Targeted IP Diagnostic Suite (TIDS) of IP tests, solves some intrinsic problems with using TCP or other throughput-maximizing protocols for measurement. In particular, all throughput-maximizing protocols (especially TCP congestion control) cause some level of congestion in order to detect when they have reached the available capacity limitation of the network. This self-inflicted congestion obscures the network properties of interest and introduces non-linear dynamic equilibrium behaviors that make any resulting measurements useless as metrics because they have no predictive value for conditions or paths different from that of the measurement itself. In order to prevent these effects, it is necessary to avoid the effects of TCP congestion control in the measurement method. These issues are discussed at length in Section 4. Readers who are unfamiliar with basic properties of TCP and TCP-like congestion control may find it easier to start at Section 4 or 4.1.

MBMのアプローチ、すなわち目標トランスポート性能をIPテストからなる目標指向IP診断スイート（TIDS）に対応付けることは、TCPやその他のスループットを最大化するプロトコルを測定に用いる場合に内在するいくつかの問題を解決します。 特に、スループットを最大化するすべてのプロトコル（とりわけTCPの輻輳制御）は、ネットワークの利用可能な容量の限界に達したことを検出するために、ある程度の輻輳を引き起こします。 この自ら引き起こした輻輳は、関心のあるネットワークの性質を覆い隠し、非線形な動的平衡の振る舞いをもたらします。 その結果、得られた測定値は、測定自体とは異なる条件やパスに対する予測価値を持たないため、メトリックとしては役に立たなくなります。 これらの影響を防ぐには、測定方法においてTCPの輻輳制御の影響を避ける必要があります。 これらの問題はセクション4で詳しく議論します。 TCPやTCPに似た輻輳制御の基本的な性質になじみのない読者は、セクション4または4.1から読み始めると理解しやすいかもしれません。

A Targeted IP Diagnostic Suite does not have such difficulties. IP diagnostics can be constructed such that they make strong statistical statements about path properties that are independent of measurement details, such as vantage and choice of measurement points.

目標指向IP診断スイートには、このような難点はありません。 IP診断は、観測地点（vantage）や測定点の選択などの測定の詳細には依存しない、パスの性質についての強い統計的な言明ができるように構築できます。

2. Overview

2. 概要

This document describes a modeling framework for deriving a Targeted IP Diagnostic Suite from a predetermined Target Transport Performance. It is not a complete specification and relies on other standards documents to define important details such as packet type-P selection, sampling techniques, vantage selection, etc. Fully Specified Targeted IP Diagnostic Suites (FSTIDSs) define all of these details. A Targeted IP Diagnostic Suite (TIDS) refers to the subset of such a specification that is in scope for this document. This terminology is further defined in Section 3.

この文書では、あらかじめ定めた目標トランスポート性能から目標指向IP診断スイートを導出するための、モデル化のフレームワークについて説明します。 この文書は完全な仕様ではなく、パケットのtype-Pの選択、サンプリング手法、観測地点の選択などの重要な詳細の定義は、ほかの標準文書に依拠しています。 完全に規定された目標指向IP診断スイート（Fully Specified Targeted IP Diagnostic Suite、FSTIDS）は、これらの詳細をすべて定義します。 目標指向IP診断スイート（TIDS）は、そのような仕様のうち、この文書の範囲内にある部分を指します。 この用語はセクション3でさらに定義します。

Section 4 describes some key aspects of TCP behavior and what they imply about the requirements for IP packet transfer. Most of the IP diagnostic tests needed to confirm that the path meets these properties can be built on existing IPPM metrics, with the addition of statistical criteria for evaluating packet transfer and, in a few cases, new mechanisms to implement the required temporal structure. (One group of tests, the standing queue tests described in Section 8.2, don't correspond to existing IPPM metrics, but suitable new IPPM metrics can be patterned after the existing definitions.)

セクション4では、TCPの振る舞いのいくつかの重要な側面と、それがIPパケット転送の要件について何を意味するかを説明します。 パスがこれらの性質を満たしていることを確認するために必要なIP診断テストのほとんどは、パケット転送を評価するための統計的基準と、いくつかの場合には必要な時間的構造を実現するための新しいメカニズムとを追加することで、既存のIPPMメトリックの上に構築できます。 （セクション8.2で説明する定常キューテストという一群のテストは、既存のIPPMメトリックに対応しませんが、適切な新しいIPPMメトリックを既存の定義にならって作ることができます。）

Figure 1 shows the MBM modeling and measurement framework. The Target Transport Performance at the top of the figure is determined by the needs of the user or application, which are outside the scope of this document. For Bulk Transport Capacity, the main performance parameter of interest is the Target Data Rate. However, since TCP's ability to compensate for less-than-ideal network conditions is fundamentally affected by the Round-Trip Time (RTT) and the Maximum Transmission Unit (MTU) of the complete path, these parameters must also be specified in advance based on knowledge about the intended application setting. They may reflect a specific application over a real path through the Internet or an idealized application and hypothetical path representing a typical user community. Section 5 describes the common parameters and models derived from the Target Transport Performance.

図1は、MBMのモデル化と測定のフレームワークを示しています。 図の上部にある目標トランスポート性能は、ユーザーやアプリケーションのニーズによって決まりますが、それはこの文書の範囲外です。 バルク転送容量の場合、関心のある主な性能パラメーターは目標データレート（Target Data Rate）です。 しかし、理想的とはいえないネットワーク条件を補うTCPの能力は、完全なパスの往復時間（Round-Trip Time、RTT）と最大転送単位（Maximum Transmission Unit、MTU）によって根本的に影響を受けるため、これらのパラメーターも、想定するアプリケーションの環境についての知識に基づいてあらかじめ指定しなければなりません。 これらのパラメーターは、インターネットを通る実際のパス上の特定のアプリケーションを反映する場合もあれば、典型的なユーザーコミュニティーを代表する理想化されたアプリケーションと仮想的なパスを反映する場合もあります。 セクション5では、目標トランスポート性能から導出される共通のパラメーターとモデルについて説明します。

Mathematical TCP models are used to determine traffic parameters and subsequently to design traffic patterns that mimic TCP (which has burst characteristics at multiple time scales) or other transport protocols delivering bulk data and operating at the Target Data Rate, MTU, and RTT over a full range of conditions. Using the techniques described in Section 6, the traffic patterns are generated based on the three Target parameters of the complete path (Target Data Rate, Target RTT, and Target MTU), independent of the properties of individual subpaths. As much as possible, the test streams are generated deterministically (precomputed) to minimize the extent to which test methodology, measurement points, measurement vantage, or path partitioning affect the details of the measurement traffic.

TCPの数学モデルを用いてトラフィックパラメーターを決定し、続いて、あらゆる条件の下で目標データレート、MTU、RTTで動作しバルクデータを配送するTCP（複数の時間スケールでバースト特性を持つ）やその他のトランスポートプロトコルを模倣するトラフィックパターンを設計します。 セクション6で説明する手法を用いて、トラフィックパターンは、個々のサブパスの性質とは無関係に、完全なパスの3つの目標パラメーター（目標データレート、目標RTT、目標MTU）に基づいて生成されます。 テストの方法論、測定点、測定の観測地点、パスの分割が測定トラフィックの詳細に影響する度合いを最小化するために、テストストリームはできる限り決定論的に生成されます（事前に計算されます）。

Section 7 describes packet transfer statistics and methods to test against the statistical criteria provided by the mathematical models. Since the statistical criteria typically apply to the complete path (a composition of subpaths) [RFC6049], in situ testing requires that the end-to-end statistical criteria be apportioned as separate criteria for each subpath. Subpaths that are expected to be bottlenecks would then be permitted to contribute a larger fraction of the end-to-end packet loss budget. In compensation, subpaths that are not expected to exhibit bottlenecks must be constrained to contribute less packet loss. Thus, the statistical criteria for each subpath in each test of a TIDS is an apportioned share of the end-to-end statistical criteria for the complete path that was determined by the mathematical model.

セクション7では、パケット転送統計と、数学モデルが与える統計的基準に照らしてテストする方法について説明します。 統計的基準は通常、完全なパス（サブパスの合成）[RFC6049]に適用されるため、その場（in situ）でのテストでは、エンドツーエンドの統計的基準をサブパスごとの個別の基準として配分する必要があります。 そうすると、ボトルネックになると予想されるサブパスには、エンドツーエンドのパケット損失の予算のより大きな割合を占めることが許されます。 その埋め合わせとして、ボトルネックにならないと予想されるサブパスは、より少ないパケット損失しか占めないように制約されなければなりません。 したがって、TIDSの各テストにおける各サブパスの統計的基準は、数学モデルによって決定された完全なパスに対するエンドツーエンドの統計的基準を配分した割り当て分です。

Section 8 describes the suite of individual tests needed to verify all of the required IP delivery properties. A subpath passes if and only if all of the individual IP diagnostic tests pass. Any subpath that fails any test indicates that some users are likely to fail to attain their Target Transport Performance under some conditions. In addition to passing or failing, a test can be deemed inconclusive for a number of reasons, including the following: the precomputed traffic pattern was not accurately generated, the measurement results were not statistically significant, the test failed to meet some required test preconditions, etc. If all tests pass but some are inconclusive, then the entire suite is deemed to be inconclusive.

セクション8では、必要なIP配送の性質をすべて検証するために必要な個々のテストの一式について説明します。 サブパスは、個々のIP診断テストがすべて合格した場合に限り合格となります。 いずれかのテストに不合格となったサブパスがあれば、一部のユーザーがある条件の下で目標トランスポート性能を達成できない可能性が高いことを示します。 テストは、合格または不合格のほかに、さまざまな理由で判定不能（inconclusive）とみなされることがあります。 その理由には、事前に計算したトラフィックパターンが正確に生成されなかった、測定結果が統計的に有意でなかった、テストが必要な前提条件の一部を満たさなかった、などがあります。 すべてのテストが合格しても一部が判定不能であれば、スイート全体が判定不能とみなされます。

In Section 9, we present an example TIDS that might be representative of High Definition (HD) video and illustrate how Model-Based Metrics can be used to address difficult measurement situations, such as confirming that inter-carrier exchanges have sufficient performance and capacity to deliver HD video between ISPs.

セクション9では、高精細（High Definition、HD）ビデオを代表するようなTIDSの例を示し、ISP間でHDビデオを配送するのに十分な性能と容量がキャリア間の接続にあることを確認するといった、難しい測定状況にモデルベースメトリックをどのように使えるかを説明します。

Since there is some uncertainty in the modeling process, Section 10 describes a validation procedure to diagnose and minimize false positive and false negative results.

モデル化の過程にはある程度の不確実性があるため、セクション10では、偽陽性と偽陰性の結果を診断して最小化するための検証手順について説明します。

3. Terminology

3. 用語

Terms containing underscores (rather than spaces) appear in equations and typically have algorithmic definitions.

（スペースではなく）アンダースコアを含む用語は数式に現れ、通常はアルゴリズム的な定義を持ちます。

3.1. General Terminology

3.1. 一般的な用語

Target:
A general term for any parameter specified by or derived from the user's application or transport performance requirements.
Target Transport Performance:
Application or transport performance target values for the complete path. For Bulk Transport Capacity defined in this document, the Target Transport Performance includes the Target Data Rate, Target RTT, and Target MTU as described below.
Target Data Rate:
The specified application data rate required for an application's proper operation. Conventional Bulk Transport Capacity (BTC) metrics are focused on the Target Data Rate; however, these metrics have little or no predictive value because they do not consider the effects of the other two parameters of the Target Transport Performance -- the RTT and MTU of the complete paths.
Target RTT (Round-Trip Time):
The specified baseline (minimum) RTT of the longest complete path over which the user expects to be able to meet the target performance. TCP and other transport protocol's ability to compensate for path problems is generally proportional to the number of round trips per second. The Target RTT determines both key parameters of the traffic patterns (e.g., burst sizes) and the thresholds on acceptable IP packet transfer statistics. The Target RTT must be specified considering appropriate packets sizes: MTU-sized packets on the forward path and ACK-sized packets (typically, header_overhead) on the return path. Note that Target RTT is specified and not measured; MBM measurements derived for a given target_RTT will be applicable to any path with a smaller RTT.
Target MTU (Maximum Transmission Unit):
The specified maximum MTU supported by the complete path over which the application expects to meet the target performance. In this document, we assume a 1500-byte MTU unless otherwise specified. If a subpath has a smaller MTU, then it becomes the Target MTU for the complete path, and all model calculations and subpath tests must use the same smaller MTU.
Targeted IP Diagnostic Suite (TIDS):
A set of IP diagnostic tests designed to determine if an otherwise ideal complete path containing the subpath under test can sustain flows at a specific target_data_rate using packets with a size of target_MTU when the RTT of the complete path is target_RTT.
Fully Specified Targeted IP Diagnostic Suite (FSTIDS):
A TIDS together with additional specifications such as measurement packet type ("type-p" [RFC2330]) that are out of scope for this document and need to be drawn from other standards documents.
Bulk Transport Capacity (BTC):
Bulk Transport Capacity metrics evaluate an Internet path's ability to carry bulk data, such as large files, streaming (non-real-time) video, and, under some conditions, web images and other content. Prior efforts to define BTC metrics have been based on [RFC3148], which predates our understanding of TCP and the requirements described in Section 4. In general, "Bulk Transport" indicates that performance is determined by the interplay between the network, cross traffic, and congestion control in the transport protocol. It excludes situations where performance is dominated by the RTT alone (e.g., transactions) or bottlenecks elsewhere, such as in the application itself.
IP diagnostic tests:
Measurements or diagnostics to determine if packet transfer statistics meet some precomputed target.
traffic patterns:
The temporal patterns or burstiness of traffic generated by applications over transport protocols such as TCP. There are several mechanisms that cause bursts at various timescales as described in Section 4.1. Our goal here is to mimic the range of common patterns (burst sizes, rates, etc.), without tying our applicability to specific applications, implementations, or technologies, which are sure to become stale.
Explicit Congestion Notification (ECN):
See [RFC3168].
packet transfer statistics:
Raw, detailed, or summary statistics about packet transfer properties of the IP layer including packet losses, ECN Congestion Experienced (CE) marks, reordering, or any other properties that may be germane to transport performance.
packet loss ratio:
As defined in [RFC7680].
apportioned:
To divide and allocate, for example, budgeting packet loss across multiple subpaths such that the losses will accumulate to less than a specified end-to-end loss ratio. Apportioning metrics is essentially the inverse of the process described in [RFC5835].
open loop:
A control theory term used to describe a class of techniques where systems that naturally exhibit circular dependencies can be analyzed by suppressing some of the dependencies, such that the resulting dependency graph is acyclic.
目標（Target）：
ユーザーのアプリケーションやトランスポートの性能要件によって指定される、またはそこから導出される任意のパラメーターを指す一般的な用語です。
目標トランスポート性能（Target Transport Performance）：
完全なパスに対する、アプリケーションまたはトランスポートの性能の目標値です。 この文書で定義するバルク転送容量の場合、目標トランスポート性能には、後述する目標データレート、目標RTT、目標MTUが含まれます。
目標データレート（Target Data Rate）：
アプリケーションが適切に動作するために必要な、指定されたアプリケーションのデータレートです。 従来のバルク転送容量（BTC）メトリックは目標データレートに焦点を当てています。 しかし、これらのメトリックは、目標トランスポート性能のほかの2つのパラメーター、すなわち完全なパスのRTTとMTUの影響を考慮していないため、予測価値がほとんど、あるいはまったくありません。
目標RTT（往復時間）（Target RTT (Round-Trip Time)）：
ユーザーが目標性能を満たせると期待する、最も長い完全なパスの、指定されたベースライン（最小）のRTTです。 パスの問題を補うTCPやその他のトランスポートプロトコルの能力は、一般に1秒あたりの往復の回数に比例します。 目標RTTは、トラフィックパターンの主要なパラメーター（たとえばバーストのサイズ）と、許容できるIPパケット転送統計のしきい値の両方を決定します。 目標RTTは、適切なパケットサイズ、つまり順方向のパスではMTUサイズのパケット、戻りパスではACKサイズのパケット（通常はheader_overhead）を考慮して指定しなければなりません。 目標RTTは指定されるものであって、測定されるものではないことに注意してください。 ある目標RTT（target_RTT）に対して導出されたMBMの測定は、それより小さいRTTを持つ任意のパスに適用できます。
目標MTU（最大転送単位）（Target MTU (Maximum Transmission Unit)）：
アプリケーションが目標性能を満たすと期待する完全なパスがサポートする、指定された最大のMTUです。 この文書では、特に指定がない限り1500バイトのMTUを想定します。 あるサブパスのMTUがより小さい場合は、それが完全なパスの目標MTUになり、すべてのモデルの計算とサブパスのテストで同じ小さいMTUを使わなければなりません。
目標指向IP診断スイート（Targeted IP Diagnostic Suite、TIDS）：
完全なパスのRTTがtarget_RTTであるとき、テスト対象のサブパスを含む（それ以外は理想的な）完全なパスが、target_MTUのサイズのパケットを用いて特定のtarget_data_rateでフローを維持できるかどうかを判定するために設計された、一連のIP診断テストです。
完全に規定された目標指向IP診断スイート（Fully Specified Targeted IP Diagnostic Suite、FSTIDS）：
TIDSに、測定パケットのタイプ（「type-p」[RFC2330]）などの追加の仕様を加えたものです。 これらの追加の仕様はこの文書の範囲外であり、ほかの標準文書から取り入れる必要があります。
バルク転送容量（Bulk Transport Capacity、BTC）：
バルク転送容量のメトリックは、大きなファイル、ストリーミング（非リアルタイム）ビデオ、および条件によってはウェブの画像やその他のコンテンツなどのバルクデータを運ぶ、インターネットのパスの能力を評価します。 BTCメトリックを定義するこれまでの取り組みは[RFC3148]に基づいていましたが、これは、TCPについての我々の理解と、セクション4で説明する要件よりも前のものです。 一般に、「バルク転送（Bulk Transport）」は、ネットワーク、クロストラフィック、トランスポートプロトコルの輻輳制御の相互作用によって性能が決まることを示します。 性能がRTTだけによって支配される状況（たとえばトランザクション）や、アプリケーション自体など、ほかの場所にあるボトルネックによって支配される状況は除外します。
IP診断テスト（IP diagnostic tests）：
パケット転送統計が事前に計算した目標を満たすかどうかを判定するための測定または診断です。
トラフィックパターン（traffic patterns）：
TCPなどのトランスポートプロトコル上でアプリケーションが生成するトラフィックの、時間的なパターンやバースト性です。 セクション4.1で説明するように、さまざまな時間スケールでバーストを引き起こすメカニズムがいくつかあります。 ここでの目標は、必ず陳腐化する特定のアプリケーション、実装、技術に適用範囲を結びつけることなく、一般的なパターン（バーストのサイズ、レートなど）の範囲を模倣することです。
明示的輻輳通知（Explicit Congestion Notification、ECN）：
[RFC3168]を参照してください。
パケット転送統計（packet transfer statistics）：
パケット損失、ECNの輻輳経験（CE）マーク、順序の入れ替わり、そのほかトランスポートの性能に関係しうる任意の性質など、IP層のパケット転送の性質についての、生の統計、詳細な統計、または要約統計です。
パケット損失率（packet loss ratio）：
[RFC7680]で定義されているとおりです。
配分された（apportioned）：
分割して割り当てることです。 たとえば、損失の累積が指定したエンドツーエンドの損失率を下回るように、複数のサブパスにわたってパケット損失の予算を割り当てることです。 メトリックの配分は、本質的に[RFC5835]で説明されている処理の逆です。
開ループ（open loop）：
本来は循環的な依存関係を示すシステムを、依存関係の一部を抑えて依存関係のグラフが非巡回になるようにすることで解析できるようにする、一群の手法を表すために使われる制御理論の用語です。

3.2. Terminology about Paths

3.2. パスに関する用語

See [RFC2330] and [RFC7398] for existing terms and definitions.

既存の用語と定義については、[RFC2330]と[RFC7398]を参照してください。

data sender:
Host sending data and receiving ACKs.
data receiver:
Host receiving data and sending ACKs.
complete path:
The end-to-end path from the data sender to the data receiver.
subpath:
A portion of the complete path. Note that there is no requirement that subpaths be non-overlapping. A subpath can be as small as a single device, link, or interface.
measurement point:
Measurement points as described in [RFC7398].
test path:
A path between two measurement points that includes a subpath of the complete path under test. If the measurement points are off path, the test path may include "test leads" between the measurement points and the subpath.
dominant bottleneck:
The bottleneck that generally determines most packet transfer statistics for the entire path. It typically determines a flow's self-clock timing, packet loss, and ECN CE marking rate, with other potential bottlenecks having less effect on the packet transfer statistics. See Section 4.1 on TCP properties.
front path:
The subpath from the data sender to the dominant bottleneck.
back path:
The subpath from the dominant bottleneck to the receiver.
return path:
The path taken by the ACKs from the data receiver to the data sender.
cross traffic:
Other, potentially interfering, traffic competing for network resources (such as bandwidth and/or queue capacity).
データ送信者（data sender）：
データを送信し、ACKを受信するホストです。
データ受信者（data receiver）：
データを受信し、ACKを送信するホストです。
完全なパス（complete path）：
データ送信者からデータ受信者までのエンドツーエンドのパスです。
サブパス（subpath）：
完全なパスの一部分です。 サブパスが互いに重ならないという要件はないことに注意してください。 サブパスは、単一の機器、リンク、インターフェイスほどの小さなものでもかまいません。
測定点（measurement point）：
[RFC7398]で説明されている測定点です。
テストパス（test path）：
2つの測定点の間のパスで、テスト対象の完全なパスのサブパスを含むものです。 測定点がパスの外にある場合、テストパスには、測定点とサブパスの間の「テストリード（test leads）」が含まれることがあります。
支配的なボトルネック（dominant bottleneck）：
一般に、パス全体のパケット転送統計の大部分を決定するボトルネックです。 通常、これがフローのセルフクロックのタイミング、パケット損失、ECN CEマークの割合を決定し、ほかの潜在的なボトルネックはパケット転送統計への影響がより小さくなります。 TCPの性質についてはセクション4.1を参照してください。
前方パス（front path）：
データ送信者から支配的なボトルネックまでのサブパスです。
後方パス（back path）：
支配的なボトルネックから受信者までのサブパスです。
戻りパス（return path）：
データ受信者からデータ送信者へACKがたどるパスです。
クロストラフィック（cross traffic）：
ネットワークの資源（帯域幅やキュー容量など）を奪い合う、干渉する可能性のあるほかのトラフィックです。

3.3. Properties

3.3. 性質

The following properties are determined by the complete path and application. These are described in more detail in Section 5.1.

以下の性質は、完全なパスとアプリケーションによって決まります。 これらはセクション5.1でより詳しく説明します。

Application Data Rate:
General term for the data rate as seen by the application above the transport layer in bytes per second. This is the payload data rate and explicitly excludes transport-level and lower-level headers (TCP/IP or other protocols), retransmissions, and other overhead that is not part of the total quantity of data delivered to the application.
IP rate:
The actual number of IP-layer bytes delivered through a subpath, per unit time, including TCP and IP headers, retransmits, and other TCP/IP overhead. This is the same as IP-type-P Link Usage in [RFC5136].
IP capacity:
The maximum number of IP-layer bytes that can be transmitted through a subpath, per unit time, including TCP and IP headers, retransmits, and other TCP/IP overhead. This is the same as IP-type-P Link Capacity in [RFC5136].
bottleneck IP capacity:
The IP capacity of the dominant bottleneck in the forward path. All throughput-maximizing protocols estimate this capacity by observing the IP rate delivered through the bottleneck. Most protocols derive their self-clocks from the timing of this data. See Section 4.1 and Appendix B for more details.
implied bottleneck IP capacity:
The bottleneck IP capacity implied by the ACKs returning from the receiver. It is determined by looking at how much application data the ACK stream at the sender reports as delivered to the data receiver per unit time at various timescales. If the return path is thinning, batching, or otherwise altering the ACK timing, the implied bottleneck IP capacity over short timescales might be substantially larger than the bottleneck IP capacity averaged over a full RTT. Since TCP derives its clock from the data delivered through the bottleneck, the front path must have sufficient buffering to absorb any data bursts at the dimensions (size and IP rate) implied by the ACK stream, which are potentially doubled during slowstart. If the return path is not altering the ACK stream, then the implied bottleneck IP capacity will be the same as the bottleneck IP capacity. See Section 4.1 and Appendix B for more details.
sender interface rate:
The IP rate that corresponds to the IP capacity of the data sender's interface. Due to sender efficiency algorithms, including technologies such as TCP segmentation offload (TSO), nearly all modern servers deliver data in bursts at full interface link rate. Today, 1 or 10 Gb/s are typical.
header_overhead:
The IP and TCP header sizes, which are the portion of each MTU not available for carrying application payload. Without loss of generality, this is assumed to be the size for returning acknowledgments (ACKs). For TCP, the Maximum Segment Size (MSS) is the Target MTU minus the header_overhead.
アプリケーションデータレート（Application Data Rate）：
トランスポート層の上にあるアプリケーションから見た、1秒あたりのバイト数でのデータレートを指す一般的な用語です。 これはペイロードのデータレートであり、トランスポートレベル以下のヘッダー（TCP/IPやその他のプロトコル）、再送、およびアプリケーションに配送されるデータの総量に含まれないその他のオーバーヘッドを明示的に除外します。
IPレート（IP rate）：
TCPとIPのヘッダー、再送、その他のTCP/IPのオーバーヘッドを含め、単位時間あたりにサブパスを通して実際に配送されたIP層のバイト数です。 これは[RFC5136]のIP-type-P Link Usageと同じです。
IP容量（IP capacity）：
TCPとIPのヘッダー、再送、その他のTCP/IPのオーバーヘッドを含め、単位時間あたりにサブパスを通して伝送できるIP層の最大のバイト数です。 これは[RFC5136]のIP-type-P Link Capacityと同じです。
ボトルネックIP容量（bottleneck IP capacity）：
順方向のパスにおける支配的なボトルネックのIP容量です。 スループットを最大化するすべてのプロトコルは、ボトルネックを通して配送されたIPレートを観測することで、この容量を推定します。 ほとんどのプロトコルは、このデータのタイミングから自らのセルフクロックを導出します。 詳しくはセクション4.1と付録Bを参照してください。
暗黙のボトルネックIP容量（implied bottleneck IP capacity）：
受信者から戻ってくるACKが示唆するボトルネックIP容量です。 これは、送信者におけるACKストリームが、さまざまな時間スケールで単位時間あたりにどれだけのアプリケーションデータをデータ受信者に配送されたと報告しているかを調べることで決定されます。 戻りパスがACKを間引いたり、まとめたり、そのほかの方法でACKのタイミングを変えたりしている場合、短い時間スケールでの暗黙のボトルネックIP容量は、RTT全体で平均したボトルネックIP容量よりもかなり大きくなる可能性があります。 TCPはボトルネックを通して配送されたデータからクロックを導出するため、前方パスには、ACKストリームが示唆する規模（サイズとIPレート）のデータバーストを吸収するのに十分なバッファリングがなければなりません。 このバーストは、スロースタートの間には2倍になる可能性があります。 戻りパスがACKストリームを変えていない場合、暗黙のボトルネックIP容量はボトルネックIP容量と同じになります。 詳しくはセクション4.1と付録Bを参照してください。
送信者インターフェイスレート（sender interface rate）：
データ送信者のインターフェイスのIP容量に対応するIPレートです。 TCPセグメンテーションオフロード（TSO）などの技術を含む、送信者の効率化アルゴリズムにより、最近のほぼすべてのサーバーは、インターフェイスのリンクレートいっぱいのバーストでデータを配送します。 現在では、1または10 Gb/sが一般的です。
header_overhead：
IPとTCPのヘッダーのサイズで、各MTUのうちアプリケーションのペイロードを運ぶのに使えない部分です。 一般性を失うことなく、これは戻ってくる確認応答（ACK）のサイズでもあると仮定します。 TCPの場合、最大セグメントサイズ（Maximum Segment Size、MSS）は目標MTUからheader_overheadを引いたものです。

3.4. Basic Parameters

3.4. 基本的なパラメーター

Basic parameters common to models and subpath tests are defined here. Formulas for target_window_size and target_run_length appear in Section 5.2. Note that these are mixed between application transport performance (excludes headers) and IP performance (includes TCP headers and retransmissions as part of the IP payload).

ここでは、モデルとサブパスのテストに共通する基本的なパラメーターを定義します。 target_window_sizeとtarget_run_lengthの式はセクション5.2に示します。 これらには、アプリケーションのトランスポート性能（ヘッダーを除く）とIP性能（IPペイロードの一部としてTCPヘッダーと再送を含む）が混在していることに注意してください。

Network power:
The observed data rate divided by the observed RTT. Network power indicates how effectively a transport protocol is filling a network.
Window [size]:
The total quantity of data carried by packets in-flight plus the data represented by ACKs circulating in the network is referred to as the window. See Section 4.1. Sometimes used with other qualifiers (congestion window (cwnd) or receiver window) to indicate which mechanism is controlling the window.
pipe size:
A general term for the number of packets needed in flight (the window size) to exactly fill a network path or subpath. It corresponds to the window size, which maximizes network power. It is often used with additional qualifiers to specify which path, under what conditions, etc.
target_window_size:
The average number of packets in flight (the window size) needed to meet the Target Data Rate for the specified Target RTT and Target MTU. It implies the scale of the bursts that the network might experience.
run length:
A general term for the observed, measured, or specified number of packets that are (expected to be) delivered between losses or ECN CE marks. Nominally, it is one over the sum of the loss and ECN CE marking probabilities, if they are independently and identically distributed.
target_run_length:
The target_run_length is an estimate of the minimum number of non-congestion marked packets needed between losses or ECN CE marks necessary to attain the target_data_rate over a path with the specified target_RTT and target_MTU, as computed by a mathematical model of TCP congestion control. A reference calculation is shown in Section 5.2 and alternatives in Appendix A.
reference target_run_length:
target_run_length computed precisely by the method in Section 5.2. This is likely to be slightly more conservative than required by modern TCP implementations.
ネットワークパワー（Network power）：
観測されたデータレートを観測されたRTTで割ったものです。 ネットワークパワーは、トランスポートプロトコルがどれだけ効果的にネットワークを満たしているかを示します。
ウィンドウ［サイズ］（Window [size]）：
飛行中（in-flight）のパケットが運ぶデータと、ネットワーク内を循環しているACKが表すデータとの総量を、ウィンドウと呼びます。 セクション4.1を参照してください。 どのメカニズムがウィンドウを制御しているかを示すために、ほかの修飾語（輻輳ウィンドウ（cwnd）や受信者ウィンドウ）とともに使われることもあります。
パイプサイズ（pipe size）：
ネットワークのパスやサブパスをちょうど満たすのに必要な、飛行中のパケットの数（ウィンドウサイズ）を指す一般的な用語です。 これは、ネットワークパワーを最大化するウィンドウサイズに相当します。 どのパスについてか、どのような条件の下でかなどを指定するために、追加の修飾語とともに使われることがよくあります。
target_window_size：
指定された目標RTTと目標MTUにおいて、目標データレートを満たすために必要な、飛行中のパケットの平均数（ウィンドウサイズ）です。 これは、ネットワークが経験するかもしれないバーストの規模を示唆します。
ランレングス（run length）：
損失またはECN CEマークの間に配送される（と期待される）パケットの数で、観測された値、測定された値、または指定された値を指す一般的な用語です。 名目上、損失とECN CEマークが独立同分布であれば、それらの確率の和の逆数になります。
target_run_length：
target_run_lengthは、指定されたtarget_RTTとtarget_MTUを持つパス上でtarget_data_rateを達成するために、損失またはECN CEマークの間に必要な、輻輳マークの付いていないパケットの最小数を、TCPの輻輳制御の数学モデルによって計算した推定値です。 参照となる計算をセクション5.2に、代替案を付録Aに示します。
参照target_run_length（reference target_run_length）：
セクション5.2の方法で厳密に計算したtarget_run_lengthです。 これは、最近のTCP実装が必要とするよりもわずかに保守的になる可能性が高いです。

3.5. Ancillary Parameters

3.5. 補助的なパラメーター

The following ancillary parameters are used for some tests:

以下の補助的なパラメーターは、一部のテストで使われます。

derating:
Under some conditions, the standard models are too conservative. The modeling framework permits some latitude in relaxing or "derating" some test parameters, as described in Section 5.3, in exchange for a more stringent TIDS validation procedures, described in Section 10. Models can be derated by including a multiplicative derating factor to make tests less stringent.
subpath_IP_capacity:
The IP capacity of a specific subpath.
test path:
A subpath of a complete path under test.
test_path_RTT:
The RTT observed between two measurement points using packet sizes that are consistent with the transport protocol. This is generally MTU-sized packets of the forward path and packets with a size of header_overhead on the return path.
test_path_pipe:
The pipe size of a test path. Nominally, it is the test_path_RTT times the test path IP_capacity.
test_window:

The smallest window sufficient to meet or exceed the target_rate when operating with a pure self-clock over a test path. The test_window is typically calculated as follows (but see the discussion in Appendix B about the effects of channel scheduling on RTT):

ceiling(target_data_rate * test_path_RTT / (target_MTU -
header_overhead))

On some test paths, the test_window may need to be adjusted slightly to compensate for the RTT being inflated by the devices that schedule packets.

ディレーティング（derating）：
条件によっては、標準的なモデルは保守的すぎます。 モデル化のフレームワークでは、セクション10で説明する、より厳格なTIDSの検証手順と引き換えに、セクション5.3で説明するように、一部のテストパラメーターを緩和する、つまり「ディレーティング（derating）」する余地を認めています。 乗算的なディレーティング係数を含めることでモデルをディレーティングし、テストをより緩やかにできます。
subpath_IP_capacity：
特定のサブパスのIP容量です。
テストパス（test path）：
テスト対象の完全なパスのサブパスです。
test_path_RTT：
トランスポートプロトコルと整合するパケットサイズを用いて、2つの測定点の間で観測されるRTTです。 これは一般に、順方向のパスではMTUサイズのパケット、戻りパスではheader_overheadのサイズのパケットです。
test_path_pipe：
テストパスのパイプサイズです。 名目上、test_path_RTTにテストパスのIP_capacityを掛けたものです。
test_window：

テストパス上で純粋なセルフクロックで動作するときに、target_rate以上を満たすのに十分な最小のウィンドウです。 test_windowは通常、次のように計算されます（ただし、チャネルのスケジューリングがRTTに与える影響についての付録Bの議論を参照してください）。

ceiling(target_data_rate * test_path_RTT / (target_MTU -
header_overhead))

一部のテストパスでは、パケットをスケジューリングする機器によってRTTが膨らむのを補うために、test_windowをわずかに調整する必要があるかもしれません。

3.6. Temporal Patterns for Test Streams

3.6. テストストリームの時間的パターン

The terminology below is used to define temporal patterns for test streams. These patterns are designed to mimic TCP behavior, as described in Section 4.1.

以下の用語は、テストストリームの時間的パターンを定義するために使われます。 これらのパターンは、セクション4.1で説明するように、TCPの振る舞いを模倣するように設計されています。

packet headway:
Time interval between packets, specified from the start of one to the start of the next. For example, if packets are sent with a 1 ms headway, there will be exactly 1000 packets per second.
burst headway:
Time interval between bursts, specified from the start of the first packet of one burst to the start of the first packet of the next burst. For example, if 4 packet bursts are sent with a 1 ms burst headway, there will be exactly 4000 packets per second.
paced single packets:
Individual packets sent at the specified rate or packet headway.
paced bursts:
Bursts on a timer. Specify any 3 of the following: average data rate, packet size, burst size (number of packets), and burst headway (burst start to start). By default, the bursts are assumed to occur at full sender interface rate, such that the packet headway within each burst is the minimum supported by the sender's interface. Under some conditions, it is useful to explicitly specify the packet headway within each burst.
slowstart rate:
Paced bursts of four packets each at an average data rate equal to twice the implied bottleneck IP capacity (but not more than the sender interface rate). This mimics TCP slowstart. This is a two-level burst pattern described in more detail in Section 6.1. If the implied bottleneck IP capacity is more than half of the sender interface rate, the slowstart rate becomes the sender interface rate.
slowstart burst:
A specified number of packets in a two-level burst pattern that resembles slowstart. This mimics one round of TCP slowstart.
repeated slowstart bursts:
Slowstart bursts repeated once per target_RTT. For TCP, each burst would be twice as large as the prior burst, and the sequence would end at the first ECN CE mark or lost packet. For measurement, all slowstart bursts would be the same size (nominally, target_window_size but other sizes might be specified), and the ECN CE marks and lost packets are counted.
パケット間隔（packet headway）：
パケット間の時間間隔で、あるパケットの開始から次のパケットの開始までで指定します。 たとえば、パケットが1 msの間隔で送信される場合、1秒あたりちょうど1000パケットになります。
バースト間隔（burst headway）：
バースト間の時間間隔で、あるバーストの最初のパケットの開始から次のバーストの最初のパケットの開始までで指定します。 たとえば、4パケットのバーストが1 msのバースト間隔で送信される場合、1秒あたりちょうど4000パケットになります。
ペース配分された単一パケット（paced single packets）：
指定したレートまたはパケット間隔で送信される個々のパケットです。
ペース配分されたバースト（paced bursts）：
タイマーに基づくバーストです。 平均データレート、パケットサイズ、バーストサイズ（パケット数）、バースト間隔（バーストの開始から開始まで）のうち、任意の3つを指定します。 デフォルトでは、バーストは送信者インターフェイスレートいっぱいで発生すると仮定するため、各バースト内のパケット間隔は送信者のインターフェイスがサポートする最小値になります。 条件によっては、各バースト内のパケット間隔を明示的に指定すると便利です。
スロースタートレート（slowstart rate）：
それぞれ4パケットからなるペース配分されたバーストで、平均データレートが暗黙のボトルネックIP容量の2倍（ただし送信者インターフェイスレートを超えない）に等しいものです。 これはTCPのスロースタートを模倣します。 これは2段階のバーストパターンで、セクション6.1でより詳しく説明します。 暗黙のボトルネックIP容量が送信者インターフェイスレートの半分を超える場合、スロースタートレートは送信者インターフェイスレートになります。
スロースタートバースト（slowstart burst）：
スロースタートに似た2段階のバーストパターンで送る、指定した数のパケットです。 これはTCPのスロースタートの1ラウンドを模倣します。
繰り返しスロースタートバースト（repeated slowstart bursts）：
target_RTTごとに1回繰り返されるスロースタートバーストです。 TCPの場合、各バーストは前のバーストの2倍の大きさになり、この系列は最初のECN CEマークまたは損失パケットで終了します。 測定の場合、すべてのスロースタートバーストは同じサイズ（名目上はtarget_window_sizeですが、ほかのサイズを指定してもかまいません）とし、ECN CEマークと損失パケットを数えます。

3.7. Tests

3.7. テスト

The tests described in this document can be grouped according to their applicability.

この文書で説明するテストは、その適用範囲に応じてグループに分けられます。

Capacity tests:
Capacity tests determine if a network subpath has sufficient capacity to deliver the Target Transport Performance. As long as the test stream is within the proper envelope for the Target Transport Performance, the average packet losses or ECN CE marks must be below the statistical criteria computed by the model. As such, capacity tests reflect parameters that can transition from passing to failing as a consequence of cross traffic, additional presented load, or the actions of other network users. By definition, capacity tests also consume significant network resources (data capacity and/or queue buffer space), and the test schedules must be balanced by their cost.
Monitoring tests:
Monitoring tests are designed to capture the most important aspects of a capacity test without presenting excessive ongoing load themselves. As such, they may miss some details of the network's performance but can serve as a useful reduced-cost proxy for a capacity test, for example, to support continuous production network monitoring.
Engineering tests:
Engineering tests evaluate how network algorithms (such as Active Queue Management (AQM) and channel allocation) interact with TCP-style self-clocked protocols and adaptive congestion control based on packet loss and ECN CE marks. These tests are likely to have complicated interactions with cross traffic and, under some conditions, can be inversely sensitive to load. For example, a test to verify that an AQM algorithm causes ECN CE marks or packet drops early enough to limit queue occupancy may experience a false pass result in the presence of cross traffic. It is important that engineering tests be performed under a wide range of conditions, including both in situ and bench testing, and over a wide variety of load conditions. Ongoing monitoring is less likely to be useful for engineering tests, although sparse in situ testing might be appropriate.
容量テスト（Capacity tests）：
容量テストは、ネットワークのサブパスに、目標トランスポート性能を実現するのに十分な容量があるかどうかを判定します。 テストストリームが目標トランスポート性能の適切な範囲内にある限り、パケット損失またはECN CEマークの平均は、モデルによって計算された統計的基準を下回らなければなりません。 そのため、容量テストは、クロストラフィック、追加で加えられた負荷、またはほかのネットワークユーザーの行動の結果として、合格から不合格に変わりうるパラメーターを反映します。 定義上、容量テストはネットワークの資源（データ容量やキューのバッファー空間）も大きく消費するため、テストのスケジュールはそのコストとのバランスを取らなければなりません。
監視テスト（Monitoring tests）：
監視テストは、それ自体が継続的に過大な負荷をかけることなく、容量テストの最も重要な側面をとらえるように設計されています。 そのため、ネットワークの性能の細部を見逃すかもしれませんが、たとえば本番ネットワークの継続的な監視を支えるために、容量テストの有用で低コストな代用として機能できます。
エンジニアリングテスト（Engineering tests）：
エンジニアリングテストは、ネットワークのアルゴリズム（アクティブキュー管理（Active Queue Management、AQM）やチャネル割り当てなど）が、TCP形式のセルフクロック型プロトコルや、パケット損失とECN CEマークに基づく適応的な輻輳制御とどのように相互作用するかを評価します。 これらのテストは、クロストラフィックと複雑に相互作用する可能性が高く、条件によっては負荷に対して逆向きに敏感になることがあります。 たとえば、キューの占有を制限するのに十分早くAQMアルゴリズムがECN CEマークやパケットの破棄を引き起こすことを検証するテストは、クロストラフィックが存在すると、誤った合格の結果になることがあります。 エンジニアリングテストは、その場でのテストとベンチテストの両方を含む幅広い条件の下で、また多様な負荷条件にわたって実施することが重要です。 継続的な監視はエンジニアリングテストにはあまり役立たない可能性が高いですが、まばらなその場でのテストは適切かもしれません。

4. Background

4. 背景

When "Framework for IP Performance Metrics" [RFC2330] was published in 1998, sound Bulk Transport Capacity (BTC) measurement was known to be well beyond our capabilities. Even when "A Framework for Defining Empirical Bulk Transfer Capacity Metrics" [RFC3148] was published, we knew that we didn't really understand the problem. Now, in hindsight, we understand why assessing BTC is such a difficult problem:

1998年に「Framework for IP Performance Metrics」[RFC2330]が公開されたとき、健全なバルク転送容量（BTC）の測定は、我々の能力をはるかに超えたものであることがわかっていました。 「A Framework for Defining Empirical Bulk Transfer Capacity Metrics」[RFC3148]が公開されたときでさえ、我々はこの問題を本当には理解していないことを自覚していました。 今振り返ると、BTCの評価がなぜこれほど難しい問題なのかが理解できます。

  • TCP is a control system with circular dependencies -- everything affects performance, including components that are explicitly not part of the test (for example, the host processing power is not in-scope of path performance tests).
  • Congestion control is a dynamic equilibrium process, similar to processes observed in chemistry and other fields. The network and transport protocols find an operating point that balances opposing forces: the transport protocol pushing harder (raising the data rate and/or window) while the network pushes back (raising packet loss ratio, RTT, and/or ECN CE marks). By design, TCP congestion control keeps raising the data rate until the network gives some indication that its capacity has been exceeded by dropping packets or adding ECN CE marks. If a TCP sender accurately fills a path to its IP capacity (e.g., the bottleneck is 100% utilized), then packet losses and ECN CE marks are mostly determined by the TCP sender and how aggressively it seeks additional capacity; they are not determined by the network itself, because the network must send exactly the signals that TCP needs to set its rate.
  • TCP's ability to compensate for network impairments (such as loss, delay, and delay variation, outside of those caused by TCP itself) is directly proportional to the number of send-ACK round-trip exchanges per second (i.e., inversely proportional to the RTT). As a consequence, an impaired subpath may pass a short RTT local test even though it fails when the subpath is extended by an effectively perfect network to some larger RTT.
  • TCP has an extreme form of the Observer Effect (colloquially known as the "Heisenberg Effect"). Measurement and cross traffic interact in unknown and ill-defined ways. The situation is actually worse than the traditional physics problem where you can at least estimate bounds on the relative momentum of the measurement and measured particles. In general, for network measurement, you cannot determine even the order of magnitude of the effect. It is possible to construct measurement scenarios where the measurement traffic starves real user traffic, yielding an overly inflated measurement. The inverse is also possible: the user traffic can fill the network, such that the measurement traffic detects only minimal available capacity. In general, you cannot determine which scenario might be in effect, so you cannot gauge the relative magnitude of the uncertainty introduced by interactions with other network traffic.
  • As a consequence of the properties listed above, it is difficult, if not impossible, for two independent implementations (hardware or software) of TCP congestion control to produce equivalent performance results [RFC6576] under the same network conditions.
  • TCPは循環的な依存関係を持つ制御システムです。 テストの一部ではないと明示されているコンポーネントを含め、あらゆるものが性能に影響します（たとえば、ホストの処理能力はパスの性能テストの範囲外です）。
  • 輻輳制御は、化学などの分野で観察される過程に似た、動的平衡の過程です。 ネットワークとトランスポートプロトコルは、相反する力のバランスが取れる動作点を見つけます。 つまり、トランスポートプロトコルはより強く押し（データレートやウィンドウを上げ）、ネットワークは押し返します（パケット損失率、RTT、ECN CEマークを上げます）。 設計上、TCPの輻輳制御は、ネットワークがパケットを破棄したりECN CEマークを付けたりして容量を超えたことをなんらかの形で示すまで、データレートを上げ続けます。 TCPの送信者がパスをそのIP容量まで正確に満たす（たとえばボトルネックの使用率が100%になる）場合、パケット損失とECN CEマークは主に、TCPの送信者と、それが追加の容量をどれだけ積極的に求めるかによって決まります。 ネットワークは、TCPがレートを設定するのに必要なシグナルをちょうど送らなければならないので、パケット損失とECN CEマークはネットワーク自体によって決まるわけではありません。
  • （TCP自身が引き起こすもの以外の）損失、遅延、遅延変動などのネットワークの障害を補うTCPの能力は、1秒あたりの送信とACKの往復のやりとりの回数に正比例します（つまり、RTTに反比例します）。 その結果、障害のあるサブパスは、RTTの短いローカルなテストには合格しても、実質的に完全なネットワークによってサブパスをより大きなRTTまで延長すると不合格になることがあります。
  • TCPには、極端な形の観測者効果（Observer Effect）（俗に「ハイゼンベルク効果（Heisenberg Effect）」として知られています）があります。 測定とクロストラフィックは、未知の、明確に定義されていない方法で相互作用します。 この状況は、少なくとも測定する粒子と測定される粒子の相対的な運動量の上限を推定できる、伝統的な物理学の問題よりも実際には悪いものです。 一般に、ネットワークの測定では、影響の大きさの桁さえも決定できません。 測定トラフィックが実際のユーザートラフィックを圧迫して、過度に膨らんだ測定値をもたらす測定シナリオを構成することもできます。 その逆も可能です。 つまり、ユーザートラフィックがネットワークを満たして、測定トラフィックがごくわずかな利用可能な容量しか検出しないこともあります。 一般に、どちらのシナリオが起きているかを判断できないため、ほかのネットワークトラフィックとの相互作用によって生じる不確実性の相対的な大きさを見積もることはできません。
  • 上で挙げた性質の結果として、TCPの輻輳制御の2つの独立した実装（ハードウェアまたはソフトウェア）が、同じネットワーク条件の下で同等の性能結果[RFC6576]を出すことは、不可能ではないにしても困難です。

These properties are a consequence of the dynamic equilibrium behavior intrinsic to how all throughput-maximizing protocols interact with the Internet. These protocols rely on control systems based on estimated network metrics to regulate the quantity of data to send into the network. The packet-sending characteristics in turn alter the network properties estimated by the control system metrics, such that there are circular dependencies between every transmission characteristic and every estimated metric. Since some of these dependencies are nonlinear, the entire system is nonlinear, and any change anywhere causes a difficult-to-predict response in network metrics. As a consequence, Bulk Transport Capacity metrics have not fulfilled the analytic framework envisioned in [RFC2330].

これらの性質は、スループットを最大化するすべてのプロトコルがインターネットとどのように相互作用するかに内在する、動的平衡の振る舞いの結果です。 これらのプロトコルは、ネットワークに送るデータの量を調整するために、推定したネットワークのメトリックに基づく制御システムに依拠しています。 そして、パケット送信の特性が、制御システムのメトリックが推定するネットワークの性質を変えるため、すべての送信特性とすべての推定メトリックの間に循環的な依存関係が生じます。 これらの依存関係の一部は非線形であるため、システム全体が非線形になり、どこかで何かが変わると、ネットワークのメトリックに予測の難しい反応が生じます。 その結果、バルク転送容量のメトリックは、[RFC2330]で構想された分析的なフレームワークを実現できていません。

Model-Based Metrics overcome these problems by making the measurement system open loop: the packet transfer statistics (akin to the network estimators) do not affect the traffic or traffic patterns (bursts), which are computed on the basis of the Target Transport Performance. A path or subpath meeting the Target Transfer Performance requirements would exhibit packet transfer statistics and estimated metrics that would not cause the control system to slow the traffic below the Target Data Rate.

モデルベースメトリックは、測定システムを開ループにすることで、これらの問題を克服します。 つまり、パケット転送統計（ネットワークの推定量に相当します）は、トラフィックやトラフィックパターン（バースト）に影響を与えず、トラフィックパターンは目標トランスポート性能に基づいて計算されます。 目標転送性能（Target Transfer Performance）の要件を満たすパスやサブパスは、制御システムがトラフィックを目標データレートより遅くすることにはならないようなパケット転送統計と推定メトリックを示すはずです。

4.1. TCP Properties

4.1. TCPの性質

TCP and other self-clocked protocols (e.g., the Stream Control Transmission Protocol (SCTP)) carry the vast majority of all Internet data. Their dominant bulk data transport behavior is to have an approximately fixed quantity of data and acknowledgments (ACKs) circulating in the network. The data receiver reports arriving data by returning ACKs to the data sender, and the data sender typically responds by sending approximately the same quantity of data back into the network. The total quantity of data plus the data represented by ACKs circulating in the network is referred to as the "window". The mandatory congestion control algorithms incrementally adjust the window by sending slightly more or less data in response to each ACK. The fundamentally important property of this system is that it is self-clocked: the data transmissions are a reflection of the ACKs that were delivered by the network, and the ACKs are a reflection of the data arriving from the network.

TCPやその他のセルフクロック型プロトコル（たとえばストリーム制御伝送プロトコル（Stream Control Transmission Protocol、SCTP））は、インターネットの全データの大部分を運んでいます。 それらの支配的なバルクデータ転送の振る舞いは、ほぼ一定量のデータと確認応答（ACK）をネットワーク内で循環させることです。 データ受信者は、到着したデータをデータ送信者にACKを返すことで報告し、データ送信者は通常、ほぼ同じ量のデータをネットワークに送り返すことで応じます。 ネットワーク内を循環しているデータと、ACKが表すデータとの総量を「ウィンドウ（window）」と呼びます。 必須の輻輳制御アルゴリズムは、各ACKに応じてわずかに多いまたは少ないデータを送ることで、ウィンドウを少しずつ調整します。 このシステムの根本的に重要な性質は、セルフクロック型であることです。 つまり、データの送信はネットワークによって配送されたACKを反映し、ACKはネットワークから到着したデータを反映しています。

A number of protocol features cause bursts of data, even in idealized networks that can be modeled as simple queuing systems.

プロトコルのいくつかの機能は、単純な待ち行列システムとしてモデル化できる理想化されたネットワークにおいてさえ、データのバーストを引き起こします。

During slowstart, the IP rate is doubled on each RTT by sending twice as much data as was delivered to the receiver during the prior RTT. Each returning ACK causes the sender to transmit twice the data the ACK reported arriving at the receiver. For slowstart to be able to fill the pipe, the network must be able to tolerate slowstart bursts up to the full pipe size inflated by the anticipated window reduction on the first loss or ECN CE mark. For example, with classic Reno congestion control, an optimal slowstart has to end with a burst that is twice the bottleneck rate for one RTT in duration. This burst causes a queue that is equal to the pipe size (i.e., the window is twice the pipe size), so when the window is halved in response to the first packet loss, the new window will be the pipe size.

スロースタートの間は、前のRTTの間に受信者に配送されたデータの2倍のデータを送ることで、IPレートがRTTごとに2倍になります。 戻ってくる各ACKにより、送信者は、そのACKが受信者に到着したと報告したデータの2倍のデータを送信します。 スロースタートがパイプを満たせるようにするには、ネットワークは、最初の損失またはECN CEマークで予想されるウィンドウの縮小分だけ膨らませたパイプサイズいっぱいまでのスロースタートバーストを許容できなければなりません。 たとえば、古典的なRenoの輻輳制御では、最適なスロースタートは、1 RTTの間ボトルネックのレートの2倍となるバーストで終わる必要があります。 このバーストはパイプサイズに等しいキューを生じさせます（つまり、ウィンドウはパイプサイズの2倍になります）。 そのため、最初のパケット損失に応じてウィンドウが半分になると、新しいウィンドウはパイプサイズになります。

Note that if the bottleneck IP rate is less than half of the capacity of the front path (which is almost always the case), the slowstart bursts will not by themselves cause significant queues anywhere else along the front path; they primarily exercise the queue at the dominant bottleneck.

ボトルネックのIPレートが前方パスの容量の半分未満である場合（ほとんど常にそうです）、スロースタートバーストはそれ自体では前方パス上のほかの場所に大きなキューを生じさせないことに注意してください。 スロースタートバーストは主に、支配的なボトルネックのキューに負荷をかけます。

Several common efficiency algorithms also cause bursts. The self-clock is typically applied to groups of packets: the receiver's delayed ACK algorithm generally sends only one ACK per two data segments. Furthermore, modern senders use TCP segmentation offload (TSO) to reduce CPU overhead. The sender's software stack builds super-sized TCP segments that the TSO hardware splits into MTU-sized segments on the wire. The net effect of TSO, delayed ACK, and other efficiency algorithms is to send bursts of segments at full sender interface rate.

いくつかの一般的な効率化アルゴリズムもバーストを引き起こします。 セルフクロックは通常、パケットのグループに適用されます。 受信者の遅延ACKアルゴリズムは、一般に2つのデータセグメントにつき1つのACKしか送りません。 さらに、最近の送信者は、CPUのオーバーヘッドを減らすためにTCPセグメンテーションオフロード（TSO）を用います。 送信者のソフトウェアスタックは特大のTCPセグメントを組み立て、それをTSOハードウェアが回線上でMTUサイズのセグメントに分割します。 TSO、遅延ACK、その他の効率化アルゴリズムの最終的な効果は、送信者インターフェイスレートいっぱいでセグメントのバーストを送ることです。

Note that these efficiency algorithms are almost always in effect, including during slowstart, such that slowstart typically has a two-level burst structure. Section 6.1 describes slowstart in more detail.

これらの効率化アルゴリズムは、スロースタートの間も含めてほとんど常に有効であるため、スロースタートは通常、2段階のバースト構造を持つことに注意してください。 セクション6.1では、スロースタートをより詳しく説明します。

Additional sources of bursts include TCP's initial window [RFC6928], application pauses, channel allocation mechanisms, and network devices that schedule ACKs. Appendix B describes these last two items. If the application pauses (e.g., stops reading or writing data) for some fraction of an RTT, many TCP implementations catch up to their earlier window size by sending a burst of data at the full sender interface rate. To fill a network with a realistic application, the network has to be able to tolerate sender interface rate bursts large enough to restore the prior window following application pauses.

そのほかのバーストの発生源には、TCPの初期ウィンドウ[RFC6928]、アプリケーションの一時停止、チャネル割り当てのメカニズム、ACKをスケジューリングするネットワーク機器があります。 付録Bでは、最後の2項目について説明します。 アプリケーションがRTTの何分の一かの間一時停止する（たとえば読み書きを止める）と、多くのTCP実装は、送信者インターフェイスレートいっぱいでデータのバーストを送ることで、以前のウィンドウサイズに追いつきます。 現実的なアプリケーションでネットワークを満たすには、ネットワークは、アプリケーションの一時停止の後に以前のウィンドウを回復できるだけの大きさの、送信者インターフェイスレートのバーストを許容できなければなりません。

Although the sender interface rate bursts are typically smaller than the last burst of a slowstart, they are at a higher IP rate so they potentially exercise queues at arbitrary points along the front path from the data sender up to and including the queue at the dominant bottleneck. It is known that these bursts can hurt network performance, especially in conjunction with other queue pressure; however, we are not aware of any models for estimating the impact or prescribing limits on the size or frequency of sender rate bursts.

送信者インターフェイスレートのバーストは通常、スロースタートの最後のバーストよりも小さいものの、IPレートはより高いため、データ送信者から支配的なボトルネックのキューまで（それを含む）の前方パス上の任意の地点のキューに負荷をかける可能性があります。 これらのバーストが、特にほかのキューへの圧力と組み合わさると、ネットワークの性能を損なう可能性があることは知られています。 しかし、我々は、その影響を推定したり、送信者レートのバーストのサイズや頻度の上限を規定したりするモデルを知りません。

In conclusion, to verify that a path can meet a Target Transport Performance, it is necessary to independently confirm that the path can tolerate bursts at the scales that can be caused by the above mechanisms. Three cases are believed to be sufficient:

結論として、パスが目標トランスポート性能を満たせることを検証するには、上記のメカニズムが引き起こしうる規模のバーストをパスが許容できることを独立に確認する必要があります。 次の3つの場合で十分であると考えられます。

  • Two-level slowstart bursts sufficient to get connections started properly.
  • Ubiquitous sender interface rate bursts caused by efficiency algorithms. We assume four packet bursts to be the most common case, since it matches the effects of delayed ACK during slowstart. These bursts should be assumed not to significantly affect packet transfer statistics.
  • Infrequent sender interface rate bursts that are the maximum of the full target_window_size and the initial window size (10 segments in [RFC6928]). The target_run_length may be derated for these large fast bursts.
  • コネクションを適切に開始させるのに十分な、2段階のスロースタートバースト。
  • 効率化アルゴリズムによって引き起こされる、どこにでもある送信者インターフェイスレートのバースト。 スロースタート中の遅延ACKの影響と一致するため、4パケットのバーストが最も一般的な場合であると仮定します。 これらのバーストは、パケット転送統計に大きな影響を与えないと仮定すべきです。
  • target_window_size全体と初期ウィンドウサイズ（[RFC6928]では10セグメント）のうち大きいほうのサイズの、まれな送信者インターフェイスレートのバースト。 これらの大きく速いバーストについては、target_run_lengthをディレーティングしてもかまいません。

If a subpath can meet the required packet loss ratio for bursts at all of these scales, then it has sufficient buffering at all potential bottlenecks to tolerate any of the bursts that are likely introduced by TCP or other transport protocols.

サブパスがこれらすべての規模のバーストについて必要なパケット損失率を満たせるなら、そのサブパスには、TCPやその他のトランスポートプロトコルによってもたらされる可能性の高いあらゆるバーストを許容するのに十分なバッファリングが、すべての潜在的なボトルネックにあります。

4.2. Diagnostic Approach

4.2. 診断のアプローチ

A complete path is expected to be able to attain a specified Bulk Transport Capacity if the path's RTT is equal to or smaller than the Target RTT, the path's MTU is equal to or larger than the Target MTU, and all of the following conditions are met:

完全なパスは、パスのRTTが目標RTT以下であり、パスのMTUが目標MTU以上であり、かつ以下の条件をすべて満たす場合に、指定されたバルク転送容量を達成できると期待されます。

  1. The IP capacity is above the Target Data Rate by a sufficient margin to cover all TCP/IP overheads. This can be confirmed by the tests described in Section 8.1 or any number of IP capacity tests adapted to implement MBM.
  2. The observed packet transfer statistics are better than required by a suitable TCP performance model (e.g., fewer packet losses or ECN CE marks). See Section 8.1 or any number of low- or fixed-rate packet loss tests outside of MBM.
  3. There is sufficient buffering at the dominant bottleneck to absorb a slowstart burst large enough to get the flow out of slowstart at a suitable window size. See Section 8.3.
  4. There is sufficient buffering in the front path to absorb and smooth sender interface rate bursts at all scales that are likely to be generated by the application, any channel arbitration in the ACK path, or any other mechanisms. See Section 8.4.
  5. When there is a slowly rising standing queue at the bottleneck, then the onset of packet loss has to be at an appropriate point (in time or in queue depth) and has to be progressive, for example, by use of Active Queue Management [RFC7567]. See Section 8.2.
  6. When there is a standing queue at a bottleneck for a shared media subpath (e.g., a half-duplex link), there must be a suitable bound on the interaction between ACKs and data, for example, due to the channel arbitration mechanism. See Section 8.2.4.
  1. IP容量が、TCP/IPのすべてのオーバーヘッドをまかなうのに十分な余裕をもって目標データレートを上回っていること。 これは、セクション8.1で説明するテスト、またはMBMを実装するように適合させた任意の数のIP容量テストによって確認できます。
  2. 観測されたパケット転送統計が、適切なTCP性能モデルが要求するよりも良いこと（たとえば、パケット損失やECN CEマークがより少ないこと）。 セクション8.1、またはMBM以外の任意の数の低レートや固定レートのパケット損失テストを参照してください。
  3. フローを適切なウィンドウサイズでスロースタートから抜け出させるのに十分な大きさのスロースタートバーストを吸収できるだけのバッファリングが、支配的なボトルネックにあること。 セクション8.3を参照してください。
  4. アプリケーション、ACKパスにおけるチャネル調停、またはその他のメカニズムによって生成される可能性の高いあらゆる規模の送信者インターフェイスレートのバーストを吸収して平滑化するのに十分なバッファリングが、前方パスにあること。 セクション8.4を参照してください。
  5. ボトルネックで定常キューがゆっくり増加しているとき、パケット損失の開始が適切な時点（時間またはキューの深さ）で起こり、かつ漸進的であること。 たとえば、アクティブキュー管理[RFC7567]を用いることによります。 セクション8.2を参照してください。
  6. 共有媒体のサブパス（たとえば半二重リンク）のボトルネックに定常キューがあるとき、たとえばチャネル調停のメカニズムによって、ACKとデータの間の相互作用に適切な上限があること。 セクション8.2.4を参照してください。

Note that conditions 1 through 4 require capacity tests for validation and thus may need to be monitored on an ongoing basis. Conditions 5 and 6 require engineering tests, which are best performed in controlled environments (e.g., bench tests). They won't generally fail due to load but may fail in the field (e.g., due to configuration errors, etc.) and thus should be spot checked.

条件1から4は検証に容量テストを必要とするため、継続的に監視する必要があるかもしれないことに注意してください。 条件5と6はエンジニアリングテストを必要とし、これは管理された環境（たとえばベンチテスト）で実施するのが最善です。 これらは一般に負荷のために不合格になることはありませんが、現場では（たとえば設定の誤りなどのために）不合格になることがあるため、抜き取り検査をすべきです。

A tool that can perform many of the tests is available from [MBMSource].

テストの多くを実施できるツールが[MBMSource]から入手できます。

4.3. New Requirements Relative to RFC 2330

4.3. RFC 2330と比べた新しい要件

Model-Based Metrics are designed to fulfill some additional requirements that were not recognized at the time RFC 2330 [RFC2330] was published. These missing requirements may have significantly contributed to policy difficulties in the IP measurement space. Some additional requirements are:

モデルベースメトリックは、RFC 2330[RFC2330]が公開された時点では認識されていなかった、いくつかの追加の要件を満たすように設計されています。 これらの欠けていた要件は、IP測定の分野における政策上の困難に大きく寄与した可能性があります。 追加の要件には次のようなものがあります。

  • IP metrics must be actionable by the ISP -- they have to be interpreted in terms of behaviors or properties at the IP or lower layers that an ISP can test, repair, and verify.
  • Metrics should be spatially composable, such that measures of concatenated paths should be predictable from subpaths.
  • Metrics must be vantage point invariant over a significant range of measurement point choices, including off-path measurement points. The only requirements for Measurement Point (MP) selection should be that the RTT between the MPs is below some reasonable bound and that the effects of the "test leads" connecting MPs to the subpath under test can be calibrated out of the measurements. The latter might be accomplished if the test leads are effectively ideal or their properties can be deducted from the measurements between the MPs. While many tests require that the test leads have at least as much IP capacity as the subpath under test, some do not, for example, the Background Packet Transfer Statistics Tests described in Section 8.1.3.
  • Metric measurements should be repeatable by multiple parties with no specialized access to MPs or diagnostic infrastructure. It should be possible for different parties to make the same measurement and observe the same results. In particular, it is important that both a consumer (or the consumer's delegate) and ISP be able to perform the same measurement and get the same result. Note that vantage independence is key to meeting this requirement.
  • IPメトリックは、ISPが対処できるものでなければなりません。 つまり、ISPがテスト、修理、検証できる、IP層またはそれより下の層での振る舞いや性質の観点から解釈されなければなりません。
  • メトリックは空間的に合成可能であるべきです。 つまり、連結したパスの測定値はサブパスから予測できるべきです。
  • メトリックは、パスの外にある測定点を含め、測定点の選択のかなり広い範囲にわたって、観測地点に対して不変でなければなりません。 測定点（Measurement Point、MP）の選択についての唯一の要件は、MP間のRTTがなんらかの妥当な上限を下回ることと、MPをテスト対象のサブパスにつなぐ「テストリード」の影響を測定から較正によって取り除けることであるべきです。 後者は、テストリードが実質的に理想的であるか、その性質をMP間の測定から差し引ける場合に達成できるかもしれません。 多くのテストでは、テストリードが少なくともテスト対象のサブパスと同じだけのIP容量を持つ必要がありますが、そうでないテストもあります。 たとえば、セクション8.1.3で説明するバックグラウンドパケット転送統計テストがそうです。
  • メトリックの測定は、MPや診断用インフラストラクチャーへの特別なアクセス権を持たない複数の当事者によって再現可能であるべきです。 異なる当事者が同じ測定を行い、同じ結果を観測できるべきです。 特に、消費者（または消費者の代理人）とISPの両方が同じ測定を実施して同じ結果を得られることが重要です。 観測地点に依存しないことが、この要件を満たす鍵であることに注意してください。

5. Common Models and Parameters

5. 共通のモデルとパラメーター

5.1. Target End-to-End Parameters

5.1. 目標エンドツーエンドパラメーター

The target end-to-end parameters are the Target Data Rate, Target RTT, and Target MTU as defined in Section 3. These parameters are determined by the needs of the application or the ultimate end user and the complete Internet path over which the application is expected to operate. The target parameters are in units that make sense to layers above the TCP layer: payload bytes delivered to the application. They exclude overheads associated with TCP and IP headers, retransmits and other protocols (e.g., DNS). Note that IP-based network services include TCP headers and retransmissions as part of delivered payload; this difference (header_overhead) is recognized in calculations below.

目標エンドツーエンドパラメーターは、セクション3で定義した目標データレート、目標RTT、目標MTUです。 これらのパラメーターは、アプリケーションや最終的なエンドユーザーのニーズと、アプリケーションが動作すると期待されるインターネットの完全なパスによって決まります。 目標パラメーターは、TCP層より上の層にとって意味のある単位、つまりアプリケーションに配送されるペイロードのバイト数で表されます。 目標パラメーターは、TCPとIPのヘッダー、再送、ほかのプロトコル（たとえばDNS）に関連するオーバーヘッドを除外します。 IPベースのネットワークサービスは、配送されるペイロードの一部としてTCPヘッダーと再送を含むことに注意してください。 この差（header_overhead）は、以下の計算で考慮されます。

Other end-to-end parameters defined in Section 3 include the effective bottleneck data rate, the sender interface data rate, and the TCP and IP header sizes.

セクション3で定義したそのほかのエンドツーエンドパラメーターには、実効ボトルネックデータレート、送信者インターフェイスのデータレート、TCPとIPのヘッダーのサイズがあります。

The target_data_rate must be smaller than all subpath IP capacities by enough headroom to carry the transport protocol overhead, explicitly including retransmissions and an allowance for fluctuations in TCP's actual data rate. Specifying a target_data_rate with insufficient headroom is likely to result in brittle measurements that have little predictive value.

target_data_rateは、再送とTCPの実際のデータレートの変動に対する余裕を明示的に含め、トランスポートプロトコルのオーバーヘッドを運ぶのに十分なヘッドルームの分だけ、すべてのサブパスのIP容量より小さくなければなりません。 ヘッドルームが不十分なtarget_data_rateを指定すると、予測価値のほとんどないもろい測定になる可能性が高くなります。

Note that the target parameters can be specified for a hypothetical path (for example, to construct TIDS designed for bench testing in the absence of a real application) or for a live in situ test of production infrastructure.

目標パラメーターは、（たとえば、実際のアプリケーションがない状態でのベンチテスト用に設計されたTIDSを構築するために）仮想的なパスに対して指定することも、本番のインフラストラクチャーをその場でライブテストするために指定することもできることに注意してください。

The number of concurrent connections is explicitly not a parameter in this model. If a subpath requires multiple connections in order to meet the specified performance, that must be stated explicitly, and the procedure described in Section 6.4 applies.

同時コネクション数は、明示的にこのモデルのパラメーターではありません。 指定された性能を満たすためにサブパスが複数のコネクションを必要とする場合は、そのことを明示的に述べなければならず、セクション6.4で説明する手順が適用されます。

5.4. Test Preconditions

5.4. テストの前提条件

Many tests have preconditions that are required to assure their validity. Examples include the presence or non-presence of cross traffic on specific subpaths; negotiating ECN; and a test stream preamble of appropriate length to achieve stable access to network resources in the presence of reactive network elements (as defined in Section 1.1 of [RFC7312]). If preconditions are not properly satisfied for some reason, the tests should be considered to be inconclusive. In general, it is useful to preserve diagnostic information as to why the preconditions were not met and any test data that was collected even if it is not useful for the intended test. Such diagnostic information and partial test data may be useful for improving the test or test procedures themselves.

テストが予定されていたという記録を保存しておくことが重要です。 そうしないと、前提条件を強制するメカニズムがサンプリングのバイアスをもたらす可能性があります。 たとえば、加入者のアクセスリンク上のクロストラフィックを理由にテストを取りやめると、ネットワークの負荷のピーク時のテスト数が減ることで、ネットワークの残りの部分のテストにサンプリングのバイアスが生じるかもしれません。

6. Generating Test Streams

6. テストストリームの生成

Many important properties of Model-Based Metrics, such as vantage independence, are a consequence of using test streams that have temporal structures that mimic TCP or other transport protocols running over a complete path. As described in Section 4.1, self-clocked protocols naturally have burst structures related to the RTT and pipe size of the complete path. These bursts naturally get larger (contain more packets) as either the Target RTT or Target Data Rate get larger or the Target MTU gets smaller. An implication of these relationships is that test streams generated by running self-clocked protocols over short subpaths may not adequately exercise the queuing at any bottleneck to determine if the subpath can support the full Target Transport Performance over the complete path.

観測地点に依存しないことなど、モデルベースメトリックの重要な性質の多くは、完全なパス上で動作するTCPやその他のトランスポートプロトコルを模倣する時間的構造を持つテストストリームを用いることの結果です。 セクション4.1で説明したように、セルフクロック型プロトコルは本来、完全なパスのRTTとパイプサイズに関係したバースト構造を持ちます。 これらのバーストは、目標RTTや目標データレートが大きくなるか、目標MTUが小さくなるにつれて、自然に大きくなります（より多くのパケットを含むようになります）。 これらの関係が意味するのは、短いサブパス上でセルフクロック型プロトコルを実行して生成したテストストリームでは、サブパスが完全なパス上で目標トランスポート性能を完全にサポートできるかどうかを判定するために、どのボトルネックのキューイングにも十分な負荷をかけられない可能性があるということです。

Failing to authentically mimic TCP's temporal structure is part of the reason why simple performance tools such as iPerf, netperf, nc, etc., have the reputation for yielding false pass results over short test paths, even when a subpath has a flaw.

TCPの時間的構造を忠実に模倣できていないことは、iPerf、netperf、ncなどの単純な性能ツールが、サブパスに欠陥がある場合でさえ、短いテストパス上で誤った合格の結果を出すという評判を得ている理由の一部です。

The definitions in Section 3 are sufficient for most test streams. We describe the slowstart and standing queue test streams in more detail.

ほとんどのテストストリームには、セクション3の定義で十分です。 ここでは、スロースタートと定常キューのテストストリームについて、より詳しく説明します。

In conventional measurement practice, stochastic processes are used to eliminate many unintended correlations and sample biases. However, MBM tests are designed to explicitly mimic temporal correlations caused by network or protocol elements themselves. Some portions of these systems, such as traffic arrival (e.g., test scheduling), are naturally stochastic. Other behaviors, such as back-to-back packet transmissions, are dominated by implementation-specific deterministic effects. Although these behaviors always contain non-deterministic elements and might be modeled stochastically, these details typically do not contribute significantly to the overall system behavior. Furthermore, it is known that real protocols are subject to failures caused by network property estimators suffering from bias due to correlation in their own traffic. For example, TCP's RTT estimator used to determine the Retransmit Timeout (RTO), can be fooled by periodic cross traffic or start-stop applications. For these reasons, many details of the test streams are specified deterministically.

従来の測定の実践では、意図しない多くの相関やサンプルのバイアスを取り除くために確率過程が用いられます。 しかし、MBMのテストは、ネットワークやプロトコルの要素自体によって引き起こされる時間的な相関を明示的に模倣するように設計されています。 これらのシステムの一部分、たとえばトラフィックの到着（たとえばテストのスケジューリング）は本来確率的です。 連続したパケットの送信など、そのほかの振る舞いは、実装固有の決定論的な効果に支配されます。 これらの振る舞いは常に非決定論的な要素を含み、確率的にモデル化できるかもしれませんが、これらの詳細は通常、システム全体の振る舞いにはあまり寄与しません。 さらに、実際のプロトコルは、自身のトラフィックの相関によるバイアスを受けたネットワークの性質の推定量が原因で、失敗することが知られています。 たとえば、再送タイムアウト（Retransmit Timeout、RTO）を決定するために用いられるTCPのRTT推定量は、周期的なクロストラフィックや、開始と停止を繰り返すアプリケーションによって欺かれることがあります。 これらの理由から、テストストリームの多くの詳細は決定論的に規定されます。

It may prove useful to introduce fine-grained noise sources into the models used for generating test streams in an update of Model-Based Metrics, but the complexity is not warranted at the time this document was written.

モデルベースメトリックの更新において、テストストリームの生成に用いるモデルに細かい粒度のノイズ源を導入することが有用だとわかるかもしれませんが、この文書の執筆時点では、その複雑さに見合う理由はありません。

6.1. Mimicking Slowstart

6.1. スロースタートの模倣

TCP slowstart has a two-level burst structure as shown in Figure 2. The fine time structure is caused by efficiency algorithms that deliberately batch work (CPU, channel allocation, etc.) to better amortize certain network and host overheads. ACKs passing through the return path typically cause the sender to transmit small bursts of data at the full sender interface rate. For example, TCP Segmentation Offload (TSO) and Delayed Acknowledgment both contribute to this effect. During slowstart, these bursts are at the same headway as the returning ACKs but are typically twice as large (e.g., have twice as much data) as the ACK reported was delivered to the receiver. Due to variations in delayed ACK and algorithms such as Appropriate Byte Counting [RFC3465], different pairs of senders and receivers produce slightly different burst patterns. Without loss of generality, we assume each ACK causes four packet sender interface rate bursts at an average headway equal to the ACK headway; this corresponds to sending at an average rate equal to twice the effective bottleneck IP rate. Each slowstart burst consists of a series of four packet sender interface rate bursts such that the total number of packets is the current window size (as of the last packet in the burst).

図2に示すように、TCPのスロースタートは2段階のバースト構造を持ちます。 細かい時間構造は、ネットワークとホストの特定のオーバーヘッドをよりうまく償却するために、作業（CPU、チャネル割り当てなど）を意図的にまとめる効率化アルゴリズムによって引き起こされます。 戻りパスを通過するACKは、通常、送信者に送信者インターフェイスレートいっぱいでデータの小さなバーストを送信させます。 たとえば、TCPセグメンテーションオフロード（TSO）と遅延確認応答（Delayed Acknowledgment）は、どちらもこの効果に寄与します。 スロースタートの間、これらのバーストは戻ってくるACKと同じ間隔で発生しますが、通常は、ACKが受信者に配送されたと報告したものの2倍の大きさ（たとえば2倍のデータ量）になります。 遅延ACKのばらつきや、適切なバイトカウント[RFC3465]などのアルゴリズムのため、送信者と受信者の組ごとにわずかに異なるバーストパターンが生じます。 一般性を失うことなく、各ACKは、ACKの間隔に等しい平均間隔で4パケットの送信者インターフェイスレートのバーストを引き起こすと仮定します。 これは、実効ボトルネックIPレートの2倍に等しい平均レートで送信することに相当します。 各スロースタートバーストは、4パケットの送信者インターフェイスレートのバーストの系列で構成され、パケットの総数は（バーストの最後のパケットの時点での）現在のウィンドウサイズになります。

The coarse time structure is due to each RTT being a reflection of the prior RTT. For real transport protocols, each slowstart burst is twice as large (twice the window) as the previous burst but is spread out in time by the network bottleneck, such that each successive RTT exhibits the same effective bottleneck IP rate. The slowstart phase ends on the first lost packet or ECN mark, which is intended to happen after successive slowstart bursts merge in time: the next burst starts before the bottleneck queue is fully drained and the prior burst is complete.

粗い時間構造は、各RTTが前のRTTを反映していることによるものです。 実際のトランスポートプロトコルでは、各スロースタートバーストは前のバーストの2倍の大きさ（2倍のウィンドウ）ですが、ネットワークのボトルネックによって時間的に引き伸ばされるため、連続する各RTTは同じ実効ボトルネックIPレートを示します。 スロースタートのフェーズは最初の損失パケットまたはECNマークで終わります。 これは、連続するスロースタートバーストが時間的に融合した後、つまりボトルネックのキューが完全に排出されて前のバーストが完了する前に次のバーストが始まった後に起こるように意図されています。

For the diagnostic tests described below, we preserve the fine time structure but manipulate the coarse structure of the slowstart bursts (burst size and headway) to measure the ability of the dominant bottleneck to absorb and smooth slowstart bursts.

以下で説明する診断テストでは、支配的なボトルネックがスロースタートバーストを吸収して平滑化する能力を測定するために、細かい時間構造は保ちつつ、スロースタートバーストの粗い構造（バーストサイズと間隔）を操作します。

Note that a stream of repeated slowstart bursts has three different average rates, depending on the averaging time interval. At the finest timescale (a few packet times at the sender interface), the peak of the average IP rate is the same as the sender interface rate; at a medium timescale (a few ACK times at the dominant bottleneck), the peak of the average IP rate is twice the implied bottleneck IP capacity; and at timescales longer than the target_RTT and when the burst size is equal to the target_window_size, the average rate is equal to the target_data_rate. This pattern corresponds to repeating the last RTT of TCP slowstart when delayed ACK and sender-side byte counting are present but without the limits specified in Appropriate Byte Counting [RFC3465].

繰り返しスロースタートバーストのストリームは、平均をとる時間間隔によって3つの異なる平均レートを持つことに注意してください。 最も細かい時間スケール（送信者インターフェイスでの数パケット分の時間）では、平均IPレートのピークは送信者インターフェイスレートと同じです。 中程度の時間スケール（支配的なボトルネックでの数ACK分の時間）では、平均IPレートのピークは暗黙のボトルネックIP容量の2倍です。 そして、target_RTTより長い時間スケールで、かつバーストサイズがtarget_window_sizeに等しい場合、平均レートはtarget_data_rateに等しくなります。 このパターンは、遅延ACKと送信者側のバイトカウントがあり、ただし適切なバイトカウント[RFC3465]で規定された制限がない場合に、TCPのスロースタートの最後のRTTを繰り返すことに相当します。

6.2. Constant Window Pseudo CBR

6.2. 固定ウィンドウの疑似CBR

Pseudo constant bit rate (CBR) is implemented by running a standard self-clocked protocol such as TCP with a fixed window size. If that window size is test_window, the data rate will be slightly above the target_rate.

疑似固定ビットレート（constant bit rate、CBR）は、TCPなどの標準的なセルフクロック型プロトコルを固定のウィンドウサイズで動作させることで実装します。 そのウィンドウサイズがtest_windowであれば、データレートはtarget_rateをわずかに上回ります。

Since the test_window is constrained to be an integer number of packets, for small RTTs or low data rates, there may not be sufficiently precise control over the data rate. Rounding the test_window up (as defined above) is likely to result in data rates that are higher than the target rate, but reducing the window by one packet may result in data rates that are too small. Also, cross traffic potentially raises the RTT, implicitly reducing the rate. Cross traffic that raises the RTT nearly always makes the test more strenuous (i.e., more demanding for the network path).

test_windowはパケット数の整数値に制約されるため、RTTが小さい場合やデータレートが低い場合は、データレートを十分に精密に制御できないことがあります。 test_windowを（上で定義したように）切り上げると、目標レートよりも高いデータレートになる可能性が高い一方で、ウィンドウを1パケット減らすとデータレートが小さくなりすぎる可能性があります。 また、クロストラフィックはRTTを増大させる可能性があり、それによって暗黙のうちにレートが下がります。 RTTを増大させるクロストラフィックは、ほとんど常にテストをより厳しく（つまり、ネットワークのパスにとってより要求の厳しいものに）します。

Note that Constant Window Pseudo CBR (and Scanned Window Pseudo CBR in the next section) both rely on a self-clock that is at least partially derived from the properties of the subnet under test. This introduces the possibility that the subnet under test exhibits behaviors such as extreme RTT fluctuations that prevent these algorithms from accurately controlling data rates.

固定ウィンドウの疑似CBR（および次のセクションの走査ウィンドウの疑似CBR）は、どちらも少なくとも部分的にはテスト対象のサブネットの性質から導出されるセルフクロックに依拠していることに注意してください。 このため、テスト対象のサブネットが、これらのアルゴリズムがデータレートを正確に制御するのを妨げるような、RTTの極端な変動などの振る舞いを示す可能性が生じます。

An FSTIDS specifying a Constant Window Pseudo CBR test must explicitly indicate under what conditions errors in the data rate cause tests to be inconclusive. Conventional paced measurement traffic may be more appropriate for these environments.

固定ウィンドウの疑似CBRのテストを規定するFSTIDSは、データレートの誤差がどのような条件でテストを判定不能にするかを明示的に示さなければなりません。 このような環境では、従来のペース配分された測定トラフィックのほうが適切かもしれません。

6.3. Scanned Window Pseudo CBR

6.3. 走査ウィンドウの疑似CBR

Scanned Window Pseudo CBR is similar to the Constant Window Pseudo CBR described above, except the window is scanned across a range of sizes designed to include two key events: the onset of queuing and the onset of packet loss or ECN CE marks. The window is scanned by incrementing it by one packet every 2*target_window_size delivered packets. This mimics the additive increase phase of standard Reno TCP congestion avoidance when delayed ACKs are in effect. Normally, the window increases are separated by intervals slightly longer than twice the target_RTT.

走査ウィンドウの疑似CBRは、上で説明した固定ウィンドウの疑似CBRに似ていますが、キューイングの開始と、パケット損失またはECN CEマークの開始という2つの重要なイベントを含むように設計されたサイズの範囲にわたって、ウィンドウを走査する点が異なります。 ウィンドウは、2*target_window_size個のパケットが配送されるごとに1パケットずつ増やすことで走査します。 これは、遅延ACKが有効なときの標準的なRenoのTCPの輻輳回避における加算的増加フェーズを模倣します。 通常、ウィンドウの増加の間隔は、target_RTTの2倍よりわずかに長くなります。

There are two ways to implement this test: 1) applying a window clamp to standard congestion control in a standard protocol such as TCP and 2) stiffening a non-standard transport protocol. When standard congestion control is in effect, any losses or ECN CE marks cause the transport to revert to a window smaller than the clamp, such that the scanning clamp loses control of the window size. The NPAD (Network Path and Application Diagnostics) pathdiag tool is an example of this class of algorithms [Pathdiag].

このテストを実装するには2つの方法があります。 1) TCPなどの標準プロトコルの標準的な輻輳制御にウィンドウのクランプを適用する方法と、2) 非標準のトランスポートプロトコルを硬直化（stiffening）する方法です。 標準的な輻輳制御が有効な場合、損失やECN CEマークが発生するとトランスポートはクランプより小さいウィンドウに戻るため、走査用のクランプはウィンドウサイズの制御を失います。 NPAD（Network Path and Application Diagnostics）のpathdiagツールは、この種のアルゴリズムの例です[Pathdiag]。

Alternatively, a non-standard congestion control algorithm can respond to losses by transmitting extra data, such that it maintains the specified window size independent of losses or ECN CE marks. Such a stiffened transport explicitly violates mandatory Internet congestion control [RFC5681] and is not suitable for in situ testing. It is only appropriate for engineering testing under laboratory conditions. The Windowed Ping tool implements such a test [WPING]. This tool has been updated (see [mpingSource]).

あるいは、非標準の輻輳制御アルゴリズムが、損失に対して追加のデータを送信することで応じ、損失やECN CEマークとは無関係に指定したウィンドウサイズを維持することもできます。 このような硬直化したトランスポートは、インターネットの必須の輻輳制御[RFC5681]に明らかに違反しており、その場でのテストには適していません。 これは、実験室の条件下でのエンジニアリングテストにのみ適しています。 Windowed Pingツールは、このようなテストを実装しています[WPING]。 このツールは更新されています（[mpingSource]を参照してください）。

The test procedures in Section 8.2 describe how to the partition the scans into regions and how to interpret the results.

セクション8.2のテスト手順では、走査を領域に分割する方法と、結果を解釈する方法について説明します。

6.4. Concurrent or Channelized Testing

6.4. 並行テストまたはチャネル化テスト

The procedures described in this document are only directly applicable to single-stream measurement, e.g., one TCP connection or measurement stream. In an ideal world, we would disallow all performance claims based on multiple concurrent streams, but this is not practical due to at least two issues. First, many very high-rate link technologies are channelized and at last partially pin the flow-to-channel mapping to minimize packet reordering within flows.

この文書で説明する手順は、単一ストリームの測定、たとえば1つのTCPコネクションや測定ストリームにのみ直接適用できます。 理想的な世界であれば、複数の並行ストリームに基づく性能の主張をすべて禁止するところですが、少なくとも2つの問題のため、これは現実的ではありません。 第1に、非常に高レートのリンク技術の多くはチャネル化されており、フロー内でのパケットの順序の入れ替わりを最小化するために、フローとチャネルの対応付けを少なくとも部分的に固定しています。

Second, TCP itself has scaling limits. Although the former problem might be overcome through different design decisions, the latter problem is more deeply rooted.

第2に、TCP自体にスケーリングの限界があります。 前者の問題は異なる設計上の決定によって克服できるかもしれませんが、後者の問題はより根深いものです。

All congestion control algorithms that are philosophically aligned with [RFC5681] (e.g., claim some level of TCP compatibility, friendliness, or fairness) have scaling limits; that is, as a long fat network (LFN) with a fixed RTT and MTU gets faster, these congestion control algorithms get less accurate and, as a consequence, have difficulty filling the network [CCscaling]. These properties are a consequence of the original Reno AIMD congestion control design and the requirement in [RFC5681] that all transport protocols have similar responses to congestion.

[RFC5681]と思想的に一致するすべての輻輳制御アルゴリズム（たとえば、なんらかのレベルのTCP互換性、親和性、公平性を主張するもの）には、スケーリングの限界があります。 つまり、RTTとMTUが固定されたロングファットネットワーク（long fat network、LFN）が高速になるにつれて、これらの輻輳制御アルゴリズムは精度が下がり、その結果、ネットワークを満たすことが難しくなります[CCscaling]。 これらの性質は、元のRenoのAIMD輻輳制御の設計と、すべてのトランスポートプロトコルが輻輳に対して同様の反応を持つという[RFC5681]の要件の結果です。

There are a number of reasons to want to specify performance in terms of multiple concurrent flows; however, this approach is not recommended for data rates below several megabits per second, which can be attained with run lengths under 10000 packets on many paths. Since the required run length is proportional to the square of the data rate, at higher rates, the run lengths can be unreasonably large, and multiple flows might be the only feasible approach.

複数の並行フローの観点から性能を規定したい理由はいくつもあります。 しかし、このアプローチは、多くのパスで10000パケット未満のランレングスで達成できる、数メガビット毎秒未満のデータレートには推奨されません。 必要なランレングスはデータレートの2乗に比例するため、より高いレートではランレングスが不当に大きくなる可能性があり、複数のフローが唯一の実現可能なアプローチになるかもしれません。

If multiple flows are deemed necessary to meet aggregate performance targets, then this must be stated both in the design of the TIDS and in any claims about network performance. The IP diagnostic tests must be performed concurrently with the specified number of connections. For the tests that use bursty test streams, the bursts should be synchronized across streams unless there is a priori knowledge that the applications have some explicit mechanism to stagger their own bursts. In the absence of an explicit mechanism to stagger bursts, many network and application artifacts will sometimes implicitly synchronize bursts. A test that does not control burst synchronization may be prone to false pass results for some applications.

総計の性能目標を満たすために複数のフローが必要だと判断した場合は、そのことをTIDSの設計と、ネットワークの性能についてのあらゆる主張の両方で述べなければなりません。 IP診断テストは、指定した数のコネクションで並行して実施しなければなりません。 バースト性のあるテストストリームを用いるテストでは、アプリケーションが自身のバーストをずらす明示的なメカニズムを持つことが事前にわかっている場合を除き、ストリーム間でバーストを同期させるべきです。 バーストをずらす明示的なメカニズムがない場合、ネットワークやアプリケーションのさまざまな要因によって、バーストが暗黙のうちに同期することがあります。 バーストの同期を制御しないテストは、一部のアプリケーションについて誤った合格の結果を出しやすくなるかもしれません。

7. Interpreting the Results

7. 結果の解釈

7.1. Test Outcomes

7.1. テストの結果

To perform an exhaustive test of a complete network path, each test of the TIDS is applied to each subpath of the complete path. If any subpath fails any test, then a standard transport protocol running over the complete path can also be expected to fail to attain the Target Transport Performance under some conditions.

ネットワークの完全なパスを網羅的にテストするには、TIDSの各テストを完全なパスの各サブパスに適用します。 いずれかのサブパスがいずれかのテストに不合格になった場合、完全なパス上で動作する標準的なトランスポートプロトコルも、ある条件の下で目標トランスポート性能を達成できないと予想できます。

In addition to passing or failing, a test can be deemed to be inconclusive for a number of reasons. Proper instrumentation and treatment of inconclusive outcomes is critical to the accuracy and robustness of Model-Based Metrics. Tests can be inconclusive if the precomputed traffic pattern or data rates were not accurately generated; the measurement results were not statistically significant; the required preconditions for the test were not met; or other causes. See Section 5.4.

テストは、合格または不合格のほかに、さまざまな理由で判定不能とみなされることがあります。 判定不能の結果を適切に計測して扱うことは、モデルベースメトリックの正確性と堅牢性にとって極めて重要です。 事前に計算したトラフィックパターンやデータレートが正確に生成されなかった場合、測定結果が統計的に有意でなかった場合、テストに必要な前提条件が満たされなかった場合、またはその他の原因がある場合に、テストは判定不能になることがあります。 セクション5.4を参照してください。

For example, consider a test that implements Constant Window Pseudo CBR (Section 6.2) by adding rate controls and detailed IP packet transfer instrumentation to TCP (e.g., using the extended performance statistics for TCP as described in [RFC4898]). TCP includes built-in control systems that might interfere with the sending data rate. If such a test meets the required packet transfer statistics (e.g., run length) while failing to attain the specified data rate, it must be treated as an inconclusive result, because we cannot a priori determine if the reduced data rate was caused by a TCP problem or a network problem or if the reduced data rate had a material effect on the observed packet transfer statistics.

たとえば、（たとえば[RFC4898]で説明されているTCPの拡張性能統計を用いて）レート制御と詳細なIPパケット転送の計測をTCPに追加することで、固定ウィンドウの疑似CBR（セクション6.2）を実装するテストを考えてみます。 TCPには、送信データレートに干渉する可能性のある組み込みの制御システムがあります。 そのようなテストが、指定されたデータレートを達成できない一方で、必要なパケット転送統計（たとえばランレングス）を満たした場合、それは判定不能の結果として扱わなければなりません。 なぜなら、低下したデータレートがTCPの問題によるものかネットワークの問題によるものか、あるいは低下したデータレートが観測されたパケット転送統計に実質的な影響を与えたかどうかを、事前に判断できないからです。

Note that for capacity tests, if the observed packet transfer statistics meet the statistical criteria for failing (based on acceptance of hypothesis H1 in Section 7.2), the test can be considered to have failed because it doesn't really matter that the test didn't attain the required data rate.

容量テストの場合、観測されたパケット転送統計が（セクション7.2の仮説H1の受容に基づく）不合格の統計的基準を満たしたなら、テストが必要なデータレートを達成しなかったことは実際には問題にならないため、テストは不合格になったとみなせることに注意してください。

The important new properties of MBM, such as vantage independence, are a direct consequence of opening the control loops in the protocols, such that the test stream does not depend on network conditions or IP packets received. Any mechanism that introduces feedback between the path's measurements and the test stream generation is at risk of introducing nonlinearities that spoil these properties. Any exceptional event that indicates that such feedback has happened should cause the test to be considered inconclusive.

観測地点に依存しないことなど、MBMの重要な新しい性質は、プロトコルの制御ループを開いて、テストストリームがネットワークの状態や受信したIPパケットに依存しないようにしたことの直接の結果です。 パスの測定とテストストリームの生成の間にフィードバックをもたらすメカニズムはいずれも、これらの性質を損なう非線形性をもたらす危険があります。 そのようなフィードバックが起きたことを示す例外的なイベントがあれば、テストは判定不能とみなすべきです。

Inconclusive tests may be caused by situations in which a test outcome is ambiguous because of network limitations or an unknown limitation on the IP diagnostic test itself, which may have been caused by some uncontrolled feedback from the network.

判定不能のテストは、ネットワークの制約や、IP診断テスト自体の未知の制約のためにテストの結果があいまいになる状況によって引き起こされることがあります。 後者は、ネットワークからのなんらかの制御されていないフィードバックによって引き起こされた可能性があります。

Note that procedures that attempt to search the target parameter space to find the limits on a parameter such as target_data_rate are at risk of breaking the location-independent properties of Model-Based Metrics if any part of the boundary between passing, inconclusive, or failing results is sensitive to RTT (which is normally the case). For example, the maximum data rate for a marginal link (e.g., exhibiting excess errors) is likely to be sensitive to the test_path_RTT. The maximum observed data rate over the test path has very little value for predicting the maximum rate over a different path.

合格、判定不能、不合格の結果の間の境界のいずれかの部分がRTTに敏感である場合（通常はそうです）、target_data_rateなどのパラメーターの限界を見つけるために目標パラメーターの空間を探索しようとする手順は、モデルベースメトリックの場所に依存しない性質を壊す危険があることに注意してください。 たとえば、限界ぎりぎりのリンク（たとえば過剰なエラーを示すもの）の最大データレートは、test_path_RTTに敏感である可能性が高いです。 テストパス上で観測された最大データレートは、別のパス上での最大レートを予測するのにほとんど価値がありません。

One of the goals for evolving TIDS designs will be to keep sharpening the distinctions between inconclusive, passing, and failing tests. The criteria for inconclusive, passing, and failing tests must be explicitly stated for every test in the TIDS or FSTIDS.

TIDSの設計を発展させるうえでの目標の1つは、判定不能、合格、不合格のテストの区別をより明確にし続けることです。 判定不能、合格、不合格のテストの基準は、TIDSまたはFSTIDSのすべてのテストについて明示的に述べなければなりません。

One of the goals for evolving the testing process, procedures, tools, and measurement point selection should be to minimize the number of inconclusive tests.

テストのプロセス、手順、ツール、測定点の選択を発展させるうえでの目標の1つは、判定不能のテストの数を最小化することであるべきです。

It may be useful to keep raw packet transfer statistics and ancillary metrics [RFC3148] for deeper study of the behavior of the network path and to measure the tools themselves. Raw packet transfer statistics can help to drive tool evolution. Under some conditions, it might be possible to re-evaluate the raw data for satisfying alternate Target Transport Performance. However, it is important to guard against sampling bias and other implicit feedback that can cause false results and exhibit measurement point vantage sensitivity. Simply applying different delivery criteria based on a different Target Transport Performance is insufficient if the test traffic patterns (bursts, etc.) do not match the alternate Target Transport Performance.

ネットワークのパスの振る舞いをより深く研究したり、ツール自体を測定したりするために、生のパケット転送統計と補助的なメトリック[RFC3148]を保存しておくと便利かもしれません。 生のパケット転送統計は、ツールの発展を促すのに役立ちます。 条件によっては、生のデータを再評価して、別の目標トランスポート性能を満たすかどうかを判断できるかもしれません。 しかし、誤った結果をもたらしたり、測定点の観測地点への依存性を示したりする可能性のある、サンプリングのバイアスやその他の暗黙のフィードバックに注意することが重要です。 テストトラフィックのパターン（バーストなど）が別の目標トランスポート性能と一致しない場合、異なる目標トランスポート性能に基づいて異なる配送基準を単に適用するだけでは不十分です。

7.2. Statistical Criteria for Estimating run_length

7.2. run_lengthを推定するための統計的基準

When evaluating the observed run_length, we need to determine appropriate packet stream sizes and acceptable error levels for efficient measurement. In practice, can we compare the empirically estimated packet loss and ECN CE marking ratios with the targets as the sample size grows? How large a sample is needed to say that the measurements of packet transfer indicate a particular run length is present?

観測されたrun_lengthを評価する際には、効率的な測定のために、適切なパケットストリームのサイズと許容できる誤差の水準を決める必要があります。 実際に、サンプルサイズが大きくなるにつれて、経験的に推定したパケット損失率とECN CEマーク率を目標と比較できるでしょうか。 パケット転送の測定が特定のランレングスが存在することを示していると言うには、どれだけの大きさのサンプルが必要でしょうか。

The generalized measurement can be described as recursive testing: send packets (individually or in patterns) and observe the packet transfer performance (packet loss ratio, other metric, or any marking we define).

一般化した測定は、再帰的なテストとして記述できます。 つまり、パケットを（個別に、またはパターンで）送信し、パケット転送の性能（パケット損失率、ほかのメトリック、または我々が定義する任意のマーキング）を観測します。

7.3. Reordering Tolerance

7.3. 順序の入れ替わりに対する許容度

All tests must be instrumented for packet-level reordering [RFC4737]. However, there is no consensus for how much reordering should be acceptable. Over the last two decades, the general trend has been to make protocols and applications more tolerant to reordering (for example, see [RFC5827]), in response to the gradual increase in reordering in the network. This increase has been due to the deployment of technologies such as multithreaded routing lookups and Equal-Cost Multipath (ECMP) routing. These techniques increase parallelism in the network and are critical to enabling overall Internet growth to exceed Moore's Law.

すべてのテストは、パケットレベルの順序の入れ替わり[RFC4737]を計測できるようにしなければなりません。 しかし、どの程度の順序の入れ替わりを許容すべきかについてのコンセンサスはありません。 過去20年間、ネットワークにおける順序の入れ替わりが徐々に増加したことに対応して、プロトコルやアプリケーションを順序の入れ替わりに対してより寛容にするのが一般的な傾向でした（たとえば[RFC5827]を参照してください）。 この増加は、マルチスレッドのルーティング検索や等コストマルチパス（Equal-Cost Multipath、ECMP）ルーティングなどの技術の展開によるものです。 これらの手法はネットワークの並列性を高め、インターネット全体の成長がムーアの法則を上回るようにするために不可欠です。

With transport retransmission strategies, there are fundamental trade-offs among reordering tolerance, how quickly losses can be repaired, and overhead from spurious retransmissions. In advance of new retransmission strategies, we propose the following strawman: transport protocols should be able to adapt to reordering as long as the reordering extent is not more than the maximum of one quarter window or 1 ms, whichever is larger. (These values come from experience prototyping Early Retransmit [RFC5827] and related algorithms. They agree with the values being proposed for "RACK: a time-based fast loss detection algorithm" [RACK].) Within this limit on reorder extent, there should be no bound on reordering density.

トランスポートの再送戦略には、順序の入れ替わりに対する許容度、損失をどれだけ早く修復できるか、偽の再送によるオーバーヘッドの間に、根本的なトレードオフがあります。 新しい再送戦略に先立って、我々は次のたたき台を提案します。 トランスポートプロトコルは、順序の入れ替わりの程度が4分の1ウィンドウと1 msのいずれか大きいほうを超えない限り、順序の入れ替わりに適応できるべきです。 （これらの値は、早期再送（Early Retransmit）[RFC5827]や関連するアルゴリズムの試作経験から得られたものです。 これらは「RACK: a time-based fast loss detection algorithm」[RACK]で提案されている値と一致します。） 順序の入れ替わりの程度に関するこの制限の範囲内では、順序の入れ替わりの密度に上限を設けるべきではありません。

By implication, recording that is less than these bounds should not be treated as a network impairment. However, [RFC4737] still applies: reordering should be instrumented, and the maximum reordering that can be properly characterized by the test (because of the bound on history buffers) should be recorded with the measurement results.

したがって、これらの上限を下回る順序の入れ替わり（原文では「recording」）は、ネットワークの障害として扱うべきではありません。 しかし、それでも[RFC4737]は適用されます。 つまり、順序の入れ替わりを計測すべきであり、（履歴バッファーの上限のために）テストで適切に特徴付けられる最大の順序の入れ替わりを、測定結果とともに記録すべきです。

Reordering tolerance and diagnostic limitations, such as the size of the history buffer used to diagnose packets that are way out of order, must be specified in an FSTIDS.

順序の入れ替わりに対する許容度と、診断上の制限（大きく順序がずれたパケットを診断するのに使う履歴バッファーのサイズなど）は、FSTIDSで規定しなければなりません。

8.1. Basic Data Rate and Packet Transfer Tests

We propose several versions of the basic data rate and packet transfer statistics test that differ in how the data rate is controlled. The third test, Background Packet Transfer Statistics, is a low-rate test designed for ongoing monitoring for changes in subpath quality.

このテストは、バーストサイズを1（単一パケット）または2（パケットペア）としてセクション6.1で説明した手順を用い、タイマーに頼ってtarget_rateでデータを送信しながら、観測されたランレングスが少なくともtarget_run_lengthであることを確認します。

8.2. Standing Queue Tests

8.2. 定常キューテスト

These engineering tests confirm that the bottleneck is well behaved across the onset of packet loss, which typically follows after the onset of queuing. Well behaved generally means lossless for transient queues, but once the queue has been sustained for a sufficient period of time (or reaches a sufficient queue depth), there should be a small number of losses or ECN CE marks to signal to the transport protocol that it should reduce its window or data rate. Losses that are too early can prevent the transport from averaging at the target_data_rate. Losses that are too late indicate that the queue might not have an appropriate AQM [RFC7567] and, as a consequence, be subject to bufferbloat [wikiBloat]. Queues without AQM have the potential to inflict excess delays on all flows sharing the bottleneck. Excess losses (more than half of the window) at the onset of loss make loss recovery problematic for the transport protocol. Non-linear, erratic, or excessive RTT increases suggest poor interactions between the channel acquisition algorithms and the transport self-clock. All of the tests in this section use the same basic scanning algorithm, described here, but score the link or subpath on the basis of how well it avoids each of these problems.

これらのエンジニアリングテストは、通常キューイングの開始に続いて起こるパケット損失の開始の前後にわたって、ボトルネックが行儀よく振る舞うことを確認します。 行儀がよいとは、一般に、一時的なキューに対しては損失がなく、キューが十分な時間持続した（または十分なキューの深さに達した）時点で、ウィンドウやデータレートを下げるべきことをトランスポートプロトコルに知らせるために少数の損失またはECN CEマークが発生することを意味します。 損失が早すぎると、トランスポートが平均してtarget_data_rateに達するのを妨げる可能性があります。 損失が遅すぎることは、キューに適切なAQM[RFC7567]がなく、その結果バッファーブロート[wikiBloat]の影響を受ける可能性があることを示します。 AQMのないキューは、ボトルネックを共有するすべてのフローに過剰な遅延を与える可能性があります。 損失の開始時の過剰な損失（ウィンドウの半分を超えるもの）は、トランスポートプロトコルの損失回復を困難にします。 非線形で、不規則な、あるいは過剰なRTTの増加は、チャネル獲得のアルゴリズムとトランスポートのセルフクロックの相互作用が良くないことを示唆します。 このセクションのテストはすべて、ここで説明する同じ基本的な走査アルゴリズムを用いますが、リンクやサブパスがこれらの各問題をどれだけうまく回避するかに基づいて評価します。

Some network technologies rely on virtual queues or other techniques to meter traffic without adding any queuing delay, in which case the data rate will vary with the window size all the way up to the onset of load-induced packet loss or ECN CE marks. For these technologies, the discussion of queuing in Section 6.3 does not apply, but it is still necessary to confirm that the onset of losses or ECN CE marks be at an appropriate point and progressive. If the network bottleneck does not introduce significant queuing delay, modify the procedure described in Section 6.3 to start the scan at a window equal to or slightly smaller than the test_window.

一部のネットワーク技術は、キューイング遅延を追加することなくトラフィックを計量するために、仮想キューやその他の手法に依拠しています。 その場合、データレートは、負荷によって引き起こされるパケット損失またはECN CEマークが始まるまで、ずっとウィンドウサイズに応じて変化します。 これらの技術では、セクション6.3のキューイングについての議論は当てはまりませんが、損失やECN CEマークの開始が適切な時点で、かつ漸進的であることは、やはり確認する必要があります。 ネットワークのボトルネックが大きなキューイング遅延をもたらさない場合は、セクション6.3で説明した手順を修正して、test_windowと等しいかわずかに小さいウィンドウで走査を開始してください。

Use the procedure in Section 6.3 to sweep the window across the onset of queuing and the onset of loss. The tests below all assume that the scan emulates standard additive increase and delayed ACK by incrementing the window by one packet for every 2*target_window_size packets delivered. A scan can typically be divided into three regions: below the onset of queuing, a standing queue, and at or beyond the onset of loss.

セクション6.3の手順を用いて、キューイングの開始と損失の開始にわたってウィンドウを掃引します。 以下のテストはすべて、2*target_window_size個のパケットが配送されるごとにウィンドウを1パケットずつ増やすことで、走査が標準的な加算的増加と遅延ACKをエミュレートすると仮定しています。 走査は通常、キューイングの開始より下、定常キュー、損失の開始時点以降という3つの領域に分けられます。

Below the onset of queuing, the RTT is typically fairly constant, and the data rate varies in proportion to the window size. Once the data rate reaches the subpath IP rate, the data rate becomes fairly constant, and the RTT increases in proportion to the increase in window size. The precise transition across the start of queuing can be identified by the maximum network power, defined to be the ratio data rate over the RTT. The network power can be computed at each window size, and the window with the maximum is taken as the start of the queuing region.

キューイングの開始より下では、RTTは通常ほぼ一定で、データレートはウィンドウサイズに比例して変化します。 データレートがサブパスのIPレートに達すると、データレートはほぼ一定になり、RTTはウィンドウサイズの増加に比例して増加します。 キューイングの開始をまたぐ正確な遷移は、データレートとRTTの比として定義される、ネットワークパワーの最大値によって特定できます。 ネットワークパワーは各ウィンドウサイズで計算でき、最大値を持つウィンドウをキューイング領域の開始とします。

If there is random background loss (e.g., bit errors), precise determination of the onset of queue-induced packet loss may require multiple scans. At window sizes large enough to cause loss in queues, all transport protocols are expected to experience periodic losses determined by the interaction between the congestion control and AQM algorithms. For standard congestion control algorithms, the periodic losses are likely to be relatively widely spaced, and the details are typically dominated by the behavior of the transport protocol itself. For the case of stiffened transport protocols (with non-standard, aggressive congestion control algorithms), the details of periodic losses will be dominated by how the window increase function responds to loss.

ランダムなバックグラウンドの損失（たとえばビットエラー）がある場合、キューによって引き起こされるパケット損失の開始を正確に判定するには、複数回の走査が必要になることがあります。 キューで損失を引き起こすのに十分大きなウィンドウサイズでは、すべてのトランスポートプロトコルは、輻輳制御とAQMのアルゴリズムの相互作用によって決まる周期的な損失を経験すると予想されます。 標準的な輻輳制御アルゴリズムの場合、周期的な損失は比較的広い間隔で発生する可能性が高く、その詳細は通常、トランスポートプロトコル自体の振る舞いに支配されます。 （非標準の攻撃的な輻輳制御アルゴリズムを持つ）硬直化したトランスポートプロトコルの場合、周期的な損失の詳細は、ウィンドウの増加関数が損失にどう反応するかに支配されます。

8.2.1. Congestion Avoidance

8.2.1. 輻輳回避

A subpath passes the congestion avoidance standing queue test if more than target_run_length packets are delivered between the onset of queuing (as determined by the window with the maximum network power as described above) and the first loss or ECN CE mark. If this test is implemented using a standard congestion control algorithm with a clamp, it can be performed in situ in the production internet as a capacity test. For an example of such a test, see [Pathdiag].

キューイングの開始（上で説明したように、ネットワークパワーが最大になるウィンドウによって決まります）から最初の損失またはECN CEマークまでの間に、target_run_lengthより多くのパケットが配送された場合、サブパスは輻輳回避の定常キューテストに合格します。 このテストをクランプ付きの標準的な輻輳制御アルゴリズムを用いて実装する場合、本番のインターネットでその場で容量テストとして実施できます。 このようなテストの例については、[Pathdiag]を参照してください。

For technologies that do not have conventional queues, use the test_window in place of the onset of queuing. That is, a subpath passes the congestion avoidance standing queue test if more than target_run_length packets are delivered between the start of the scan at test_window and the first loss or ECN CE mark.

従来のキューを持たない技術の場合は、キューイングの開始の代わりにtest_windowを用います。 つまり、test_windowでの走査の開始から最初の損失またはECN CEマークまでの間に、target_run_lengthより多くのパケットが配送された場合、サブパスは輻輳回避の定常キューテストに合格します。

8.2.2. Bufferbloat

8.2.2. バッファーブロート

This test confirms that there is some mechanism to limit buffer occupancy (e.g., that prevents bufferbloat). Note that this is not strictly a requirement for single-stream bulk transport capacity; however, if there is no mechanism to limit buffer queue occupancy, then a single stream with sufficient data to deliver is likely to cause the problems described in [RFC7567] and [wikiBloat]. This may cause only minor symptoms for the dominant flow but has the potential to make the subpath unusable for other flows and applications.

このテストは、バッファーの占有を制限する（たとえばバッファーブロートを防ぐ）なんらかのメカニズムがあることを確認します。 これは、単一ストリームのバルク転送容量にとって厳密には要件ではないことに注意してください。 しかし、バッファーのキューの占有を制限するメカニズムがない場合、配送すべき十分なデータを持つ単一のストリームが、[RFC7567]と[wikiBloat]で説明されている問題を引き起こす可能性が高くなります。 これは、支配的なフローにとっては軽微な症状しか引き起こさないかもしれませんが、ほかのフローやアプリケーションにとってサブパスを使えなくする可能性があります。

The test will pass if the onset of loss occurs before a standing queue has introduced delay greater than twice the target_RTT or another well-defined and specified limit. Note that there is not yet a model for how much standing queue is acceptable. The factor of two chosen here reflects a rule of thumb. In conjunction with the previous test, this test implies that the first loss should occur at a queuing delay that is between one and two times the target_RTT.

定常キューがtarget_RTTの2倍、またはほかの明確に定義され指定された限度より大きな遅延をもたらす前に損失の開始が起これば、このテストは合格します。 どれだけの定常キューが許容できるかについてのモデルはまだないことに注意してください。 ここで選んだ2倍という係数は、経験則を反映したものです。 前のテストと合わせると、このテストは、最初の損失がtarget_RTTの1倍から2倍の間のキューイング遅延で起こるべきであることを意味します。

Specified RTT limits that are larger than twice the target_RTT must be fully justified in the FSTIDS.

target_RTTの2倍より大きいRTTの限度を指定する場合は、FSTIDSで十分に正当化しなければなりません。

8.2.3. Non-excessive Loss

8.2.3. 過剰でない損失

This test confirms that the onset of loss is not excessive. The test will pass if losses are equal to or less than the increase in the cross traffic plus the test stream window increase since the previous RTT. This could be restated as non-decreasing total throughput of the subpath at the onset of loss. (Note that when there is a transient drop in subpath throughput and there is not already a standing queue, a subpath that passes other queue tests in this document will have sufficient queue space to hold one full RTT worth of data).

このテストは、損失の開始が過剰でないことを確認します。 損失が、前のRTTからのクロストラフィックの増加とテストストリームのウィンドウの増加の合計以下であれば、このテストは合格します。 これは、損失の開始時にサブパスの総スループットが減少しないこと、と言い換えられます。 （一時的にサブパスのスループットが低下し、まだ定常キューがない場合、この文書のほかのキューテストに合格するサブパスには、1 RTT分のデータを保持するのに十分なキュー空間があることに注意してください。）

Note that token bucket policers will not pass this test, which is as intended. TCP often stumbles badly if more than a small fraction of the packets are dropped in one RTT. Many TCP implementations will require a timeout and slowstart to recover their self-clock. Even if they can recover from the massive losses, the sudden change in available capacity at the bottleneck wastes serving and front-path capacity until TCP can adapt to the new rate [Policing].

トークンバケットポリサーはこのテストに合格しないことに注意してください。 これは意図したとおりです。 1 RTTの間にパケットのごく一部を超える量が破棄されると、TCPはしばしばひどくつまずきます。 多くのTCP実装は、セルフクロックを回復するためにタイムアウトとスロースタートを必要とします。 大量の損失から回復できたとしても、ボトルネックで利用可能な容量が突然変化すると、TCPが新しいレートに適応できるまで、配信側と前方パスの容量が無駄になります[Policing]。

8.2.4. Duplex Self-Interference

8.2.4. 二重通信の自己干渉

This engineering test confirms a bound on the interactions between the forward data path and the ACK return path when they share a half-duplex link.

このエンジニアリングテストは、順方向のデータパスとACKの戻りパスが半二重リンクを共有している場合に、それらの間の相互作用に上限があることを確認します。

Some historical half-duplex technologies had the property that each direction held the channel until it completely drained its queue. When a self-clocked transport protocol, such as TCP, has data and ACKs passing in opposite directions through such a link, the behavior often reverts to stop-and-wait. Each additional packet added to the window raises the observed RTT by two packet times, once as the additional packet passes through the data path and once for the additional delay incurred by the ACK waiting on the return path.

歴史的な半二重技術の中には、各方向がキューを完全に排出するまでチャネルを保持するという性質を持つものがありました。 TCPなどのセルフクロック型のトランスポートプロトコルで、データとACKがそのようなリンクを逆方向に通過する場合、振る舞いはしばしばストップアンドウェイトに戻ってしまいます。 ウィンドウにパケットを1つ追加するごとに、観測されるRTTは2パケット分の時間だけ増加します。 1回は追加のパケットがデータパスを通過するときで、もう1回はACKが戻りパスで待たされることで生じる追加の遅延です。

The Duplex Self-Interference Test fails if the RTT rises by more than a fixed bound above the expected queuing time computed from the excess window divided by the subpath IP capacity. This bound must be smaller than target_RTT/2 to avoid reverting to stop-and-wait behavior (e.g., data packets and ACKs both have to be released at least twice per RTT).

二重通信の自己干渉テストは、超過したウィンドウをサブパスのIP容量で割って計算した予想キューイング時間を、RTTが一定の上限より大きく上回った場合に不合格となります。 ストップアンドウェイトの振る舞いに戻るのを避けるために、この上限はtarget_RTT/2より小さくなければなりません（たとえば、データパケットとACKの両方が、RTTあたり少なくとも2回は解放されなければなりません）。

8.3. Slowstart Tests

8.3. スロースタートテスト

These tests mimic slowstart: data is sent at twice the effective bottleneck rate to exercise the queue at the dominant bottleneck.

これらのテストはスロースタートを模倣します。 つまり、支配的なボトルネックのキューに負荷をかけるために、実効ボトルネックレートの2倍でデータを送信します。

8.3.1. Full Window Slowstart Test

8.3.1. フルウィンドウスロースタートテスト

This capacity test confirms that slowstart is not likely to exit prematurely. To perform this test, send slowstart bursts that are target_window_size total packets and accumulate packet transfer statistics as described in Section 7.2 to score the outcome. The test will pass if it is statistically significant that the observed number of good packets delivered between losses or ECN CE marks is larger than the target_run_length. The test will fail if it is statistically significant that the observed interval between losses or ECN CE marks is smaller than the target_run_length.

この容量テストは、スロースタートが早期に終了する可能性が低いことを確認します。 このテストを実施するには、合計target_window_size個のパケットからなるスロースタートバーストを送信し、セクション7.2で説明したようにパケット転送統計を蓄積して結果を評価します。 損失またはECN CEマークの間に配送された正常なパケットの観測数がtarget_run_lengthより大きいことが統計的に有意であれば、このテストは合格します。 損失またはECN CEマークの間の観測された間隔がtarget_run_lengthより小さいことが統計的に有意であれば、このテストは不合格になります。

The test is deemed inconclusive if the elapsed time to send the data burst is not less than half of the time to receive the ACKs. (That is, it is acceptable to send data too fast, but sending it slower than twice the actual bottleneck rate as indicated by the ACKs is deemed inconclusive). The headway for the slowstart bursts should be the target_RTT.

データバーストの送信に要した経過時間が、ACKの受信に要した時間の半分未満でない場合、このテストは判定不能とみなされます。 （つまり、データを速く送りすぎることは許容できますが、ACKが示す実際のボトルネックレートの2倍より遅く送ることは判定不能とみなされます。） スロースタートバーストの間隔はtarget_RTTにすべきです。

Note that these are the same parameters that are used for the Sustained Full-Rate Bursts Test, except the burst rate is at slowstart rate rather than sender interface rate.

これらは、バーストのレートが送信者インターフェイスレートではなくスロースタートレートである点を除き、持続的な最大レートバーストテストで使われるのと同じパラメーターであることに注意してください。

8.3.2. Slowstart AQM Test

8.3.2. スロースタートAQMテスト

To perform this test, do a continuous slowstart (send data continuously at twice the implied IP bottleneck capacity) until the first loss; stop and allow the network to drain and repeat; gather statistics on how many packets were delivered before the loss, the pattern of losses, maximum observed RTT, and window size; and justify the results. There is not currently sufficient theory to justify requiring any particular result; however, design decisions that affect the outcome of this tests also affect how the network balances between long and short flows (the "mice vs. elephants" problem). The queue sojourn time for the first packet delivered after the first loss should be at least one half of the target_RTT.

このテストを実施するには、最初の損失まで連続したスロースタートを行い（暗黙のIPボトルネック容量の2倍で連続的にデータを送信し）、停止してネットワークを排出させてから繰り返し、損失の前に配送されたパケットの数、損失のパターン、観測された最大RTT、ウィンドウサイズについての統計を収集して、その結果を正当化します。 現時点では、特定の結果を要求することを正当化できるだけの理論はありません。 しかし、このテストの結果に影響する設計上の決定は、ネットワークが長いフローと短いフローの間のバランスをどう取るか（「ネズミ対ゾウ（mice vs. elephants）」問題）にも影響します。 最初の損失の後に配送された最初のパケットのキュー滞在時間は、少なくともtarget_RTTの半分であるべきです。

This engineering test should be performed on a quiescent network or testbed, since cross traffic has the potential to change the results in ill-defined ways.

クロストラフィックは明確に定義されていない方法で結果を変える可能性があるため、このエンジニアリングテストは静穏なネットワークまたはテストベッドで実施すべきです。

8.4. Sender Rate Burst Tests

8.4. 送信者レートバーストテスト

These tests determine how well the network can deliver bursts sent at the sender's interface rate. Note that this test most heavily exercises the front path and is likely to include infrastructure that may be out of scope for an access ISP, even though the bursts might be caused by ACK compression, thinning, or channel arbitration in the access ISP. See Appendix B.

これらのテストは、送信者のインターフェイスレートで送信されたバーストを、ネットワークがどれだけうまく配送できるかを判定します。 このテストは前方パスに最も大きな負荷をかけ、バーストがアクセスISPにおけるACKの圧縮、間引き、チャネル調停によって引き起こされる場合であっても、アクセスISPの範囲外であるかもしれないインフラストラクチャーを含む可能性が高いことに注意してください。 付録Bを参照してください。

Also, there are a several details about sender interface rate bursts that are not fully defined here. These details, such as the assumed sender interface rate, should be explicitly stated in an FSTIDS.

また、送信者インターフェイスレートのバーストについては、ここで完全には定義されていない詳細がいくつかあります。 想定する送信者インターフェイスレートなどのこれらの詳細は、FSTIDSで明示的に述べるべきです。

Current standards permit TCP to send full window bursts following an application pause. (Congestion Window Validation [RFC2861] and updates to support Rate-Limited Traffic [RFC7661] are not required). Since full window bursts are consistent with standard behavior, it is desirable that the network be able to deliver such bursts; otherwise, application pauses will cause unwarranted losses. Note that the AIMD sawtooth requires a peak window that is twice target_window_size, so the worst-case burst may be 2*target_window_size.

現在の標準では、TCPはアプリケーションの一時停止の後にウィンドウいっぱいのバーストを送ることが許されています。 （輻輳ウィンドウの検証（Congestion Window Validation）[RFC2861]と、レート制限されたトラフィックをサポートするための更新[RFC7661]は必須ではありません。） ウィンドウいっぱいのバーストは標準的な振る舞いと整合するため、ネットワークがそのようなバーストを配送できることが望ましいです。 そうでなければ、アプリケーションの一時停止によって不当な損失が生じます。 AIMDのノコギリ波はtarget_window_sizeの2倍のピークウィンドウを必要とするため、最悪の場合のバーストは2*target_window_sizeになりうることに注意してください。

It is also understood in the application and serving community that interface rate bursts have a cost to the network that has to be balanced against other costs in the servers themselves. For example, TCP Segmentation Offload (TSO) reduces server CPU in exchange for larger network bursts, which increase the stress on network buffer memory. Some newer TCP implementations can pace traffic at scale [TSO_pacing] [TSO_fq_pacing]. It remains to be determined if and how quickly these changes will be deployed.

アプリケーションや配信のコミュニティーでは、インターフェイスレートのバーストにはネットワークにとってのコストがあり、それをサーバー自体のほかのコストと比較してバランスを取らなければならないことも理解されています。 たとえば、TCPセグメンテーションオフロード（TSO）はサーバーのCPUを削減する代わりに、より大きなネットワークバーストをもたらし、それはネットワークのバッファーメモリーへの負担を増やします。 一部の新しいTCP実装は、大規模にトラフィックをペース配分できます[TSO_pacing] [TSO_fq_pacing]。 これらの変更がどの程度早く展開されるか、そもそも展開されるかどうかは、まだわかっていません。

There is not yet theory to unify these costs or to provide a framework for trying to optimize global efficiency. We do not yet have a model for how many server rate bursts should be tolerated by the network. Some bursts must be tolerated by the network, but it is probably unreasonable to expect the network to be able to efficiently deliver all data as a series of bursts.

これらのコストを統一したり、全体的な効率を最適化しようとするためのフレームワークを提供したりする理論はまだありません。 サーバーレートのバーストをネットワークがどれだけ許容すべきかについてのモデルも、まだありません。 ネットワークはある程度のバーストを許容しなければなりませんが、すべてのデータを一連のバーストとして効率的に配送できることをネットワークに期待するのは、おそらく不合理です。

For this reason, this is the only test for which we encourage derating. A TIDS could include a table containing pairs of derating parameters: burst sizes and how much each burst size is permitted to reduce the run length, relative to the target_run_length.

このため、これは我々がディレーティングを推奨する唯一のテストです。 TIDSには、ディレーティングのパラメーターの組、つまりバーストサイズと、各バーストサイズがtarget_run_lengthに対してランレングスをどれだけ減らすことを許されるかを含む表を含めることができます。

8.5. Combined and Implicit Tests

8.5. 複合テストと暗黙のテスト

Combined tests efficiently confirm multiple network properties in a single test, possibly as a side effect of normal content delivery. They require less measurement traffic than other testing strategies at the cost of conflating diagnostic signatures when they fail. These are by far the most efficient for monitoring networks that are nominally expected to pass all tests.

複合テストは、場合によっては通常のコンテンツ配送の副次的な効果として、単一のテストで複数のネットワークの性質を効率的に確認します。 複合テストは、ほかのテスト戦略より少ない測定トラフィックで済みますが、不合格の場合に診断上の特徴が混同されるという代償があります。 これらは、名目上すべてのテストに合格すると予想されるネットワークを監視するには、群を抜いて最も効率的です。

8.5.1. Sustained Full-Rate Bursts Test

8.5.1. 持続的な最大レートバーストテスト

The Sustained Full-Rate Bursts Test implements a combined worst-case version of all of the capacity tests above. To perform this test, send target_window_size bursts of packets at server interface rate with target_RTT burst headway (burst start to next burst start), and verify that the observed packet transfer statistics meets the target_run_length.

持続的な最大レートバーストテストは、上のすべての容量テストを組み合わせた最悪ケースの版を実装します。 このテストを実施するには、target_RTTのバースト間隔（バーストの開始から次のバーストの開始まで）で、サーバーインターフェイスレートでtarget_window_size個のパケットのバーストを送信し、観測されたパケット転送統計がtarget_run_lengthを満たすことを検証します。

Key observations:

重要な観察事項は次のとおりです。

  • The subpath under test is expected to go idle for some fraction of the time, determined by the difference between the time to drain the queue at the subpath_IP_capacity and the target_RTT. If the queue does not drain completely, it may be an indication that the subpath has insufficient IP capacity or that there is some other problem with the test (e.g., it is inconclusive).
  • The burst sensitivity can be derated by sending smaller bursts more frequently (e.g., by sending target_window_size*derate packet bursts every target_RTT*derate, where "derate" is less than one).
  • When not derated, this test is the most strenuous capacity test.
  • A subpath that passes this test is likely to be able to sustain higher rates (close to subpath_IP_capacity) for paths with RTTs significantly smaller than the target_RTT.
  • This test can be implemented with instrumented TCP [RFC4898], using a specialized measurement application at one end (e.g., [MBMSource]) and a minimal service at the other end (e.g., [RFC863] and [RFC864]).
  • This test is efficient to implement, since it does not require per-packet timers, and can make use of TSO in modern network interfaces.
  • If a subpath is known to pass the standing queue engineering tests (particularly that it has a progressive onset of loss at an appropriate queue depth), then the Sustained Full-Rate Bursts Test is sufficient to assure that the subpath under test will not impair Bulk Transport Capacity at the target performance under all conditions. See Section 8.2 for a discussion of the standing queue tests.
  • テスト対象のサブパスは、subpath_IP_capacityでキューを排出するのにかかる時間とtarget_RTTの差によって決まる時間の割合だけ、アイドル状態になると予想されます。 キューが完全に排出されない場合は、サブパスのIP容量が不十分であるか、テストになんらかのほかの問題がある（たとえば判定不能である）ことを示している可能性があります。
  • バーストの感度は、より小さなバーストをより頻繁に送信することで（たとえば、「derate」を1未満の値として、target_window_size*derateパケットのバーストをtarget_RTT*derateごとに送信することで）ディレーティングできます。
  • ディレーティングしない場合、このテストは最も厳しい容量テストです。
  • このテストに合格するサブパスは、RTTがtarget_RTTよりかなり小さいパスでは、より高いレート（subpath_IP_capacityに近いレート）を維持できる可能性が高いです。
  • このテストは、計測機能付きのTCP[RFC4898]を用い、一方の端で専用の測定アプリケーション（たとえば[MBMSource]）を、もう一方の端で最小限のサービス（たとえば[RFC863]と[RFC864]）を使うことで実装できます。
  • このテストは、パケットごとのタイマーを必要とせず、最近のネットワークインターフェイスのTSOを利用できるため、効率的に実装できます。
  • サブパスが定常キューのエンジニアリングテストに合格する（特に、適切なキューの深さで損失が漸進的に始まる）ことがわかっている場合、持続的な最大レートバーストテストは、テスト対象のサブパスがあらゆる条件の下で目標性能におけるバルク転送容量を損なわないことを保証するのに十分です。 定常キューテストの議論についてはセクション8.2を参照してください。

Note that this test is clearly independent of the subpath RTT or other details of the measurement infrastructure, as long as the measurement infrastructure can accurately and reliably deliver the required bursts to the subpath under test.

測定インフラストラクチャーが必要なバーストをテスト対象のサブパスに正確かつ確実に届けられる限り、このテストがサブパスのRTTや測定インフラストラクチャーのほかの詳細に明らかに依存しないことに注意してください。

8.5.2. Passive Measurements

8.5.2. パッシブ測定

Any non-throughput-maximizing application, such as fixed-rate streaming media, can be used to implement passive or hybrid (defined in [RFC7799]) versions of Model-Based Metrics with some additional instrumentation and possibly a traffic shaper or other controls in the servers. The essential requirement is that the data transmission be constrained such that even with arbitrary application pauses and bursts, the data rate and burst sizes stay within the envelope defined by the individual tests described above.

固定レートのストリーミングメディアなど、スループットを最大化しない任意のアプリケーションは、追加の計測機能と、場合によってはサーバーでのトラフィックシェーパーやその他の制御を加えることで、モデルベースメトリックのパッシブ版またはハイブリッド版（[RFC7799]で定義）を実装するのに使えます。 本質的な要件は、アプリケーションが任意に一時停止したりバーストしたりしても、データレートとバーストサイズが上で説明した個々のテストで定義された範囲内にとどまるように、データの送信が制約されることです。

If the application's serving data rate can be constrained to be less than or equal to the target_data_rate and the serving_RTT (the RTT between the sender and client) is less than the target_RTT, this constraint is most easily implemented by clamping the transport window size to serving_window_clamp (which is set to the test_window and computed for the actual serving path).

アプリケーションの配信データレートをtarget_data_rate以下に制約でき、serving_RTT（送信者とクライアントの間のRTT）がtarget_RTT未満であれば、この制約は、トランスポートのウィンドウサイズをserving_window_clamp（test_windowに設定され、実際の配信パスについて計算されます）にクランプすることで最も簡単に実装できます。

Under the above constraints, the serving_window_clamp will limit both the serving data rate and burst sizes to be no larger than the parameters specified by the procedures in Section 8.1.2, 8.4, or 8.5.1. Since the serving RTT is smaller than the target_RTT, the worst-case bursts that might be generated under these conditions will be smaller than called for by Section 8.4, and the sender rate burst sizes are implicitly derated by the serving_window_clamp divided by the target_window_size at the very least. (Depending on the application behavior, the data might be significantly smoother than specified by any of the burst tests.)

上の制約の下では、serving_window_clampは、配信データレートとバーストサイズの両方を、セクション8.1.2、8.4、または8.5.1の手順で規定されるパラメーターより大きくならないように制限します。 配信RTTはtarget_RTTより小さいため、これらの条件の下で生成されうる最悪ケースのバーストはセクション8.4が要求するものより小さくなり、送信者レートのバーストサイズは、少なくともserving_window_clampをtarget_window_sizeで割った値を係数として掛けた大きさに、暗黙のうちにディレーティングされます。 （アプリケーションの振る舞いによっては、データはどのバーストテストで規定されるものよりもかなり滑らかになるかもしれません。）

In an alternative implementation, the data rate and bursts might be explicitly controlled by a programmable traffic shaper or by pacing at the sender. This would provide better control over transmissions but is more complicated to implement, although the required technology is available [TSO_pacing] [TSO_fq_pacing].

別の実装では、データレートとバーストを、プログラム可能なトラフィックシェーパーや送信者でのペース配分によって明示的に制御するかもしれません。 これは送信をより良く制御できますが、必要な技術は利用可能である[TSO_pacing] [TSO_fq_pacing]ものの、実装はより複雑になります。

Note that these techniques can be applied to any content delivery that can be operated at a constrained data rate to inhibit TCP equilibrium behavior.

これらの手法は、TCPの平衡状態の振る舞いを抑えるために制約されたデータレートで運用できる任意のコンテンツ配送に適用できることに注意してください。

Furthermore, note that Dynamic Adaptive Streaming over HTTP (DASH) is generally in conflict with passive Model-Based Metrics measurement, because it is a rate-maximizing protocol. It can still meet the requirement here if the rate can be capped, for example, by knowing a priori the maximum rate needed to deliver a particular piece of content.

さらに、HTTP上の動的適応型ストリーミング（Dynamic Adaptive Streaming over HTTP、DASH）は、レートを最大化するプロトコルであるため、一般にパッシブなモデルベースメトリックの測定と相いれないことに注意してください。 それでも、たとえば特定のコンテンツを配送するのに必要な最大レートを事前に知ることでレートに上限を設けられるなら、DASHはここでの要件を満たせます。

9. Example

9. 例

In this section, we illustrate a TIDS designed to confirm that an access ISP can reliably deliver HD video from multiple content providers to all of its customers. With modern codecs, minimal HD video (720p) generally fits in 2.5 Mb/s. Due to the ISP's geographical size, network topology, and modem characteristics, the ISP determines that most content is within a 50 ms RTT of its users. (This example RTT is sufficient to cover the propagation delay to continental Europe or to either coast of the United States with low-delay modems; it is sufficient to cover somewhat smaller geographical regions if the modems require additional delay to implement advanced compression and error recovery.)

このセクションでは、アクセスISPが複数のコンテンツプロバイダーからのHDビデオをすべての顧客に確実に配送できることを確認するために設計されたTIDSを示します。 最新のコーデックでは、最低限のHDビデオ（720p）は一般に2.5 Mb/sに収まります。 ISPの地理的な規模、ネットワークトポロジー、モデムの特性から、ISPは、ほとんどのコンテンツがユーザーから50 msのRTT以内にあると判断します。 （この例のRTTは、低遅延のモデムでヨーロッパ大陸や米国のどちらかの海岸までの伝搬遅延をカバーするのに十分です。 モデムが高度な圧縮やエラー回復を実装するために追加の遅延を必要とする場合は、やや狭い地理的地域をカバーするのに十分です。）

Table 1 shows the default TCP model with no derating and, as such, is quite conservative. The simplest TIDS would be to use the Sustained Full-Rate Bursts Test, described in Section 8.5.1. Such a test would send 11 packet bursts every 50 ms and confirm that there was no more than 1 packet loss per 33 bursts (363 total packets in 1.650 seconds).

表1は、ディレーティングのないデフォルトのTCPモデルを示しており、そのため非常に保守的です。 最も単純なTIDSは、セクション8.5.1で説明した持続的な最大レートバーストテストを用いるものでしょう。 そのようなテストでは、50 msごとに11パケットのバーストを送信し、33バーストあたり（1.650秒間に合計363パケット）パケット損失が1回以下であることを確認します。

Since this number represents the entire end-to-end loss budget, independent subpath tests could be implemented by apportioning the packet loss ratio across subpaths. For example, 50% of the losses might be allocated to the access or last mile link to the user, 40% to the network interconnections with other ISPs, and 1% to each internal hop (assuming no more than 10 internal hops). Then, all of the subpaths can be tested independently, and the spatial composition of passing subpaths would be expected to be within the end-to-end loss budget.

この数値はエンドツーエンドの損失の予算全体を表すため、パケット損失率をサブパス間で配分することで、独立したサブパスのテストを実装できます。 たとえば、損失の50%をユーザーへのアクセスリンク（ラストマイルのリンク）に、40%をほかのISPとのネットワーク相互接続に、1%を各内部ホップ（内部ホップが10以下と仮定）に割り当てることができます。 そうすると、すべてのサブパスを独立にテストでき、合格したサブパスを空間的に合成したものは、エンドツーエンドの損失の予算の範囲内に収まると期待できます。

9.1. Observations about Applicability

9.1. 適用可能性についての考察

Guidance on deploying and using MBM belong in a future document. However, the example above illustrates some of the issues that may need to be considered.

MBMの展開と使用に関するガイダンスは、将来の文書で扱うべきものです。 しかし、上の例は、考慮が必要になるかもしれない問題のいくつかを示しています。

Note that another ISP, with different geographical coverage, topology, or modem technology may need to assume a different target_RTT and, as a consequence, a different target_window_size and target_run_length, even for the same target_data rate. One of the implications of this is that infrastructure shared by multiple ISPs, such as Internet Exchange Points (IXPs) and other interconnects may need to be evaluated on the basis of the most stringent target_window_size and target_run_length of any participating ISP. One way to do this might be to choose target parameters for evaluating such shared infrastructure on the basis of a hypothetical reference path that does not necessarily match any actual paths.

地理的なカバー範囲、トポロジー、モデムの技術が異なる別のISPは、同じtarget_data rateであっても、異なるtarget_RTTを想定する必要があり、その結果、異なるtarget_window_sizeとtarget_run_lengthを想定する必要があるかもしれないことに注意してください。 このことが意味することの1つは、インターネットエクスチェンジポイント（Internet Exchange Point、IXP）やその他の相互接続など、複数のISPが共有するインフラストラクチャーは、参加するISPのうち最も厳しいtarget_window_sizeとtarget_run_lengthに基づいて評価する必要があるかもしれないということです。 そのための1つの方法として、そのような共有インフラストラクチャーを評価するための目標パラメーターを、実際のパスとは必ずしも一致しない仮想的な参照パスに基づいて選ぶことが考えられます。

Testing interconnects has generally been problematic: conventional performance tests run between measurement points adjacent to either side of the interconnect are not generally useful. Unconstrained TCP tests, such as iPerf [iPerf], are usually overly aggressive due to the small RTT (often less than 1 ms). With a short RTT, these tools are likely to report inflated data rates because on a short RTT, these tools can tolerate very high packet loss ratios and can push other cross traffic off of the network. As a consequence, these measurements are useless for predicting actual user performance over longer paths and may themselves be quite disruptive. Model-Based Metrics solves this problem. The interconnect can be evaluated with the same TIDS as other subpaths. Continuing our example, if the interconnect is apportioned 40% of the losses, 11 packet bursts sent every 50 ms should have fewer than one loss per 82 bursts (902 packets).

相互接続のテストは、一般に問題がありました。 相互接続のどちらかの側に隣接する測定点の間で実行される従来の性能テストは、一般に役に立ちません。 iPerf[iPerf]などの制約のないTCPテストは、RTTが小さい（多くの場合1 ms未満）ため、通常は攻撃的すぎます。 RTTが短いと、これらのツールは非常に高いパケット損失率を許容でき、ほかのクロストラフィックをネットワークから押し出せるため、膨らんだデータレートを報告する可能性が高くなります。 その結果、これらの測定は、より長いパス上での実際のユーザーの性能を予測するのに役立たず、それ自体がかなりの混乱をもたらすかもしれません。 モデルベースメトリックはこの問題を解決します。 相互接続は、ほかのサブパスと同じTIDSで評価できます。 例を続けると、相互接続に損失の40%が配分される場合、50 msごとに送信される11パケットのバーストでは、損失が82バーストあたり（902パケット）1回未満であるべきです。

10. Validation

10. 検証

Since some aspects of the models are likely to be too conservative, Section 5.2 permits alternate protocol models, and Section 5.3 permits test parameter derating. If either of these techniques is used, we require demonstrations that such a TIDS can robustly detect subpaths that will prevent authentic applications using state-of-the-art protocol implementations from meeting the specified Target Transport Performance. This correctness criteria is potentially difficult to prove, because it implicitly requires validating a TIDS against all possible paths and subpaths. The procedures described here are still experimental.

モデルのいくつかの側面は保守的すぎる可能性が高いため、セクション5.2では代替のプロトコルモデルを認め、セクション5.3ではテストパラメーターのディレーティングを認めています。 これらの手法のいずれかを用いる場合、そのようなTIDSが、最先端のプロトコル実装を用いる本物のアプリケーションが指定された目標トランスポート性能を満たすのを妨げるサブパスを、堅牢に検出できることの実証を要求します。 この正しさの基準は、TIDSをあらゆるパスとサブパスに対して検証することを暗に要求するため、証明するのが困難な可能性があります。 ここで説明する手順はまだ実験的なものです。

We suggest two approaches, both of which should be applied. First, publish a fully open description of the TIDS, including what assumptions were used and how it was derived, such that the research community can evaluate the design decisions, test them, and comment on their applicability. Second, demonstrate that applications do meet the Target Transport Performance when running over a network testbed that has the tightest possible constraints that still allow the tests in the TIDS to pass.

我々は2つのアプローチを提案し、その両方を適用すべきです。 第1に、研究コミュニティーが設計上の決定を評価し、テストし、その適用可能性についてコメントできるように、どのような前提を用いたか、どのように導出したかを含め、TIDSの完全にオープンな記述を公開します。 第2に、TIDSのテストに合格しうる範囲で可能な限り厳しい制約を持つネットワークのテストベッド上で動作させたときに、アプリケーションが目標トランスポート性能を満たすことを実証します。

This procedure resembles an epsilon-delta proof in calculus. Construct a test network such that all of the individual tests of the TIDS pass by only small (infinitesimal) margins, and demonstrate that a variety of authentic applications running over real TCP implementations (or other protocols as appropriate) meets the Target Transport Performance over such a network. The workloads should include multiple types of streaming media and transaction-oriented short flows (e.g., synthetic web traffic).

この手順は、微積分学におけるイプシロン-デルタ論法に似ています。 TIDSの個々のテストのすべてにわずかな（無限小の）余裕でしか合格しないようなテストネットワークを構築し、実際のTCP実装（または必要に応じてほかのプロトコル）上で動作するさまざまな本物のアプリケーションが、そのようなネットワーク上で目標トランスポート性能を満たすことを実証します。 ワークロードには、複数の種類のストリーミングメディアと、トランザクション指向の短いフロー（たとえば合成したウェブトラフィック）を含めるべきです。

For example, for the HD streaming video TIDS described in Section 9, the IP capacity should be exactly the header_overhead above 2.5 Mb/s, the per packet random background loss ratio should be 1/363 (for a run length of 363 packets), the bottleneck queue should be 11 packets, and the front path should have just enough buffering to withstand 11 packet interface rate bursts. We want every one of the TIDS tests to fail if we slightly increase the relevant test parameter, so, for example, sending a 12-packet burst should cause excess (possibly deterministic) packet drops at the dominant queue at the bottleneck. This network has the tightest possible constraints that can be expected to pass the TIDS, yet it should be possible for a real application using a stock TCP implementation in the vendor's default configuration to attain 2.5 Mb/s over a 50 ms path.

たとえば、セクション9で説明したHDストリーミングビデオのTIDSでは、IP容量は2.5 Mb/sをちょうどheader_overheadだけ上回るべきであり、パケットごとのランダムなバックグラウンドの損失率は（363パケットのランレングスに対して）1/363であるべきであり、ボトルネックのキューは11パケットであるべきであり、前方パスには11パケットのインターフェイスレートのバーストに耐えるのにちょうど十分なバッファリングがあるべきです。 関係するテストパラメーターをわずかに増やした場合には、TIDSのテストのすべてが不合格になることを求めます。 たとえば、12パケットのバーストを送ると、ボトルネックの支配的なキューで過剰な（場合によっては決定論的な）パケットの破棄が生じるべきです。 このネットワークは、TIDSに合格すると期待できる範囲で可能な限り厳しい制約を持っていますが、ベンダーのデフォルト設定の標準的なTCP実装を用いる実際のアプリケーションが、50 msのパス上で2.5 Mb/sを達成できるはずです。

The most difficult part of setting up such a testbed is arranging for it to have the tightest possible constraints that still allow it to pass the individual tests. Two approaches are suggested:

このようなテストベッドを構築する際に最も難しいのは、個々のテストに合格しうる範囲で可能な限り厳しい制約を持たせるようにすることです。 2つのアプローチを提案します。

  • constraining (configuring) the network devices not to use all available resources (e.g., by limiting available buffer space or data rate)
  • pre-loading subpaths with cross traffic
  • 利用可能なすべての資源を使わないようにネットワーク機器を制約（設定）する（たとえば、利用可能なバッファー空間やデータレートを制限する）
  • サブパスにクロストラフィックで事前に負荷をかける

Note that it is important that a single tightly constrained environment just barely passes all tests; otherwise, there is a chance that TCP can exploit extra latitude in some parameters (such as data rate) to partially compensate for constraints in other parameters (e.g., queue space). This effect is potentially bidirectional: extra latitude in the queue space tests has the potential to enable TCP to compensate for insufficient data-rate headroom.

単一の厳しく制約された環境が、すべてのテストにかろうじて合格することが重要であることに注意してください。 そうでないと、TCPが一部のパラメーター（データレートなど）の余分な余裕を利用して、ほかのパラメーター（たとえばキュー空間）の制約を部分的に補える可能性があります。 この効果は双方向になる可能性があります。 キュー空間のテストに余分な余裕があると、TCPがデータレートのヘッドルームの不足を補えるようになる可能性があります。

To the extent that a TIDS is used to inform public dialog, it should be fully documented publicly, including the details of the tests, what assumptions were used, and how it was derived. All of the details of the validation experiment should also be published with sufficient detail for the experiments to be replicated by other researchers. All components should be either open source or fully described proprietary implementations that are available to the research community.

TIDSが公の議論に情報を提供するために使われる限りにおいて、TIDSは、テストの詳細、どのような前提を用いたか、どのように導出したかを含め、公に完全に文書化すべきです。 検証実験のすべての詳細も、ほかの研究者が実験を再現できるだけの十分な詳細とともに公開すべきです。 すべてのコンポーネントは、オープンソースであるか、研究コミュニティーが利用可能な完全に記述された独自の実装であるべきです。

11. Security Considerations

11. セキュリティーに関する考慮事項

Measurement is often used to inform business and policy decisions and, as a consequence, is potentially subject to manipulation. Model-Based Metrics are expected to be a huge step forward because equivalent measurements can be performed from multiple vantage points, such that performance claims can be independently validated by multiple parties.

測定は、ビジネスや政策の決定に情報を提供するためによく使われるため、操作の対象となる可能性があります。 モデルベースメトリックは、同等の測定を複数の観測地点から実施でき、性能の主張を複数の当事者が独立に検証できるため、大きな前進になると期待されています。

Much of the acrimony in the Net Neutrality debate is due to the historical lack of any effective vantage-independent tools to characterize network performance. Traditional methods for measuring Bulk Transport Capacity are sensitive to RTT and as a consequence often yield very different results when run local to an ISP or interconnect and when run over a customer's complete path. Neither the ISP nor customer can repeat the other's measurements, leading to high levels of distrust and acrimony. Model-Based Metrics are expected to greatly improve this situation.

ネットワーク中立性の議論における激しい対立の多くは、ネットワークの性能を特徴付けるための、観測地点に依存しない効果的なツールが歴史的に欠けていたことによるものです。 バルク転送容量を測定する従来の方法はRTTに敏感であり、その結果、ISPや相互接続の局所で実行した場合と、顧客の完全なパス上で実行した場合とで、しばしば大きく異なる結果をもたらします。 ISPも顧客も相手の測定を再現できず、高いレベルの不信と対立につながっています。 モデルベースメトリックは、この状況を大きく改善すると期待されています。

Note that in situ measurements sometimes require sending synthetic measurement traffic between arbitrary locations in the network and, as such, are potentially attractive platforms for launching DDoS attacks. All active measurement tools and protocols must be designed to minimize the opportunities for these misuses. See the discussion in Section 7 of [RFC7594].

その場での測定では、ネットワーク内の任意の場所の間で合成の測定トラフィックを送信する必要がある場合があり、そのため、DDoS攻撃を仕掛けるための魅力的なプラットフォームになる可能性があることに注意してください。 すべてのアクティブ測定ツールとプロトコルは、このような悪用の機会を最小化するように設計しなければなりません。 [RFC7594]のセクション7の議論を参照してください。

この文書で説明するテストの一部は、ネットワークに高い負荷をかけ、ほかのトラフィックに悪影響を与える可能性があるため、頻繁なネットワーク監視を意図したものではありません。

Appendix A. Model Derivations

付録A. モデルの導出

The reference target_run_length described in Section 5.2 is based on very conservative assumptions: that all excess data in flight (i.e., the window size) above the target_window_size contributes to a standing queue that raises the RTT and that classic Reno congestion control with delayed ACKs is in effect. In this section we provide two alternative calculations using different assumptions.

セクション5.2で説明した参照target_run_lengthは、非常に保守的な前提に基づいています。 つまり、target_window_sizeを超える飛行中の超過データ（すなわちウィンドウサイズ）はすべて、RTTを増大させる定常キューの一因となり、かつ遅延ACKを伴う古典的なRenoの輻輳制御が有効であるという前提です。 このセクションでは、異なる前提を用いた2つの代替の計算を示します。

It may seem out of place to allow such latitude in a measurement method, but this section provides offsetting requirements.

測定方法にこのような余地を認めるのは場違いに思えるかもしれませんが、このセクションでは、それを相殺する要件を示します。

The estimates provided by these models make the most sense if network performance is viewed logarithmically. In the operational Internet, data rates span more than eight orders of magnitude, RTT spans more than three orders of magnitude, and packet loss ratio spans at least eight orders of magnitude if not more. When viewed logarithmically (as in decibels), these correspond to 80 dB of dynamic range. On an 80 dB scale, a 3 dB error is less than 4% of the scale, even though it represents a factor of 2 in untransformed parameter.

これらのモデルが提供する推定値は、ネットワークの性能を対数的に見る場合に最も意味をなします。 運用中のインターネットでは、データレートは8桁以上、RTTは3桁以上、パケット損失率は少なくとも8桁、あるいはそれ以上にわたります。 （デシベルのように）対数的に見ると、これらは80 dBのダイナミックレンジに相当します。 80 dBのスケールでは、3 dBの誤差は、変換前のパラメーターでは2倍の差を表すにもかかわらず、スケールの4%未満です。

This document gives a lot of latitude for calculating target_run_length; however, people designing a TIDS should consider the effect of their choices on the ongoing tussle about the relevance of "TCP friendliness" as an appropriate model for Internet capacity allocation. Choosing a target_run_length that is substantially smaller than the reference target_run_length specified in Section 5.2 strengthens the argument that it may be appropriate to abandon "TCP friendliness" as the Internet fairness model. This gives developers incentive and permission to develop even more aggressive applications and protocols, for example, by increasing the number of connections that they open concurrently.

この文書は、target_run_lengthの計算に大きな余地を与えています。 しかし、TIDSを設計する人は、インターネットの容量の割り当ての適切なモデルとしての「TCP親和性（TCP friendliness）」の妥当性をめぐって続いている論争に、自らの選択が与える影響を考慮すべきです。 セクション5.2で規定した参照target_run_lengthよりかなり小さいtarget_run_lengthを選ぶと、インターネットの公平性のモデルとしての「TCP親和性」を放棄するのが適切かもしれないという主張を強めることになります。 これは開発者に、たとえば同時に開くコネクションの数を増やすことで、さらに攻撃的なアプリケーションやプロトコルを開発する動機と許可を与えます。

A.1. Queueless Reno

A.1. キューのないReno

In Section 5.2, models were derived based on the assumption that the subpath IP rate matches the target rate plus overhead, such that the excess window needed for the AIMD sawtooth causes a fluctuating queue at the bottleneck.

セクション5.2では、サブパスのIPレートが目標レートとオーバーヘッドの合計に一致し、AIMDのノコギリ波に必要な超過ウィンドウがボトルネックで変動するキューを生じさせるという前提に基づいてモデルを導出しました。

An alternate situation would be a bottleneck where there is no significant queue and losses are caused by some mechanism that does not involve extra delay, for example, by the use of a virtual queue as done in Approximate Fair Dropping [AFD]. A flow controlled by such a bottleneck would have a constant RTT and a data rate that fluctuates in a sawtooth due to AIMD congestion control. Assume the losses are being controlled to make the average data rate meet some goal that is equal to or greater than the target_rate. The necessary run length to meet the target_rate can be computed as follows:

別の状況としては、大きなキューがなく、追加の遅延を伴わないなんらかのメカニズム、たとえば近似公平ドロップ（Approximate Fair Dropping）[AFD]で行われているような仮想キューの使用によって損失が引き起こされるボトルネックが考えられます。 そのようなボトルネックによって制御されるフローは、RTTが一定で、AIMDの輻輳制御のためにデータレートがノコギリ波状に変動します。 平均データレートがtarget_rate以上のなんらかの目標を満たすように損失が制御されていると仮定します。 target_rateを満たすのに必要なランレングスは、次のように計算できます。

For some value of Wmin, the window will sweep from Wmin packets to 2*Wmin packets in 2*Wmin RTT (due to delayed ACK). Unlike the queuing case where Wmin = target_window_size, we want the average of Wmin and 2*Wmin to be the target_window_size, so the average data rate is the target rate. Thus, we want Wmin = (2/3)*target_window_size.

あるWminの値に対して、ウィンドウは（遅延ACKのため）2*Wmin RTTの間にWminパケットから2*Wminパケットまで掃引します。 Wmin = target_window_sizeとなるキューイングの場合とは異なり、ここでは平均データレートが目標レートになるように、Wminと2*Wminの平均をtarget_window_sizeにしたいと考えます。 したがって、Wmin = (2/3)*target_window_sizeとします。

Between losses, each sawtooth delivers (1/2)(Wmin+2*Wmin)(2Wmin) packets in 2*Wmin RTTs.

Appendix B. The Effects of ACK Scheduling

付録B. ACKのスケジューリングの影響

For many network technologies, simple queuing models don't apply: the network schedules, thins, or otherwise alters the timing of ACKs and data, generally to raise the efficiency of the channel allocation algorithms when confronted with relatively widely spaced small ACKs. These efficiency strategies are ubiquitous for half-duplex, wireless, and broadcast media.

多くのネットワーク技術では、単純な待ち行列モデルは当てはまりません。 ネットワークは、比較的広い間隔の小さなACKに直面したときにチャネル割り当てアルゴリズムの効率を上げるために、一般にACKとデータのタイミングをスケジューリングしたり、間引いたり、そのほかの方法で変えたりします。 これらの効率化戦略は、半二重、無線、ブロードキャストの媒体ではどこにでも見られます。

Altering the ACK stream by holding or thinning ACKs typically has two consequences: it raises the implied bottleneck IP capacity, making the fine-grained slowstart bursts either faster or larger, and it raises the effective RTT by the average time that the ACKs and data are delayed. The first effect can be partially mitigated by re-clocking ACKs once they are beyond the bottleneck on the return path to the sender; however, this further raises the effective RTT.

ACKを保持したり間引いたりしてACKストリームを変えると、通常2つの結果が生じます。 暗黙のボトルネックIP容量が上がり、細かい粒度のスロースタートバーストがより速くなるかより大きくなります。 また、ACKとデータが遅延される平均時間だけ実効RTTが増大します。 最初の影響は、ACKがボトルネックを越えた後、送信者への戻りパス上でACKのクロックを付け直すことで部分的に緩和できます。 しかし、これは実効RTTをさらに増大させます。

The most extreme example of this sort of behavior would be a half-duplex channel that is not released as long as the endpoint currently holding the channel has more traffic (data or ACKs) to send. Such environments cause self-clocked protocols under full load to revert to extremely inefficient stop-and-wait behavior. The channel constrains the protocol to send an entire window of data as a single contiguous burst on the forward path, followed by the entire window of ACKs on the return path. (A channel with this behavior would fail the Duplex Self-Interference Test described in Section 8.2.4).

この種の振る舞いの最も極端な例は、現在チャネルを保持しているエンドポイントに送るべきトラフィック（データまたはACK）がある限り解放されない、半二重のチャネルでしょう。 このような環境では、全負荷の下でセルフクロック型プロトコルは、極めて非効率なストップアンドウェイトの振る舞いに戻ってしまいます。 このチャネルは、プロトコルに、データのウィンドウ全体を順方向のパス上で単一の連続したバーストとして送らせ、その後に戻りパス上でACKのウィンドウ全体を送らせるという制約を課します。 （このような振る舞いをするチャネルは、セクション8.2.4で説明した二重通信の自己干渉テストに不合格になります。）

If a particular return path contains a subpath or device that alters the timing of the ACK stream, then the entire front path from the sender up to the bottleneck must be tested at the burst parameters implied by the ACK scheduling algorithm. The most important parameter is the implied bottleneck IP capacity, which is the average rate at which the ACKs advance snd.una. Note that thinning the ACK stream (relying on the cumulative nature of seg.ack to permit discarding some ACKs) causes most TCP implementations to send interface rate bursts to offset the longer times between ACKs in order to maintain the average data rate.

特定の戻りパスにACKストリームのタイミングを変えるサブパスや機器が含まれる場合、送信者からボトルネックまでの前方パス全体を、ACKのスケジューリングアルゴリズムが示唆するバーストのパラメーターでテストしなければなりません。 最も重要なパラメーターは暗黙のボトルネックIP容量で、これはACKがsnd.unaを進める平均レートです。 （seg.ackの累積的な性質に頼って一部のACKを破棄できるようにして）ACKストリームを間引くと、ほとんどのTCP実装は、平均データレートを維持するために、ACKの間隔が長くなった分を埋め合わせるインターフェイスレートのバーストを送信することに注意してください。

Note that due to ubiquitous self-clocking in Internet protocols, ill-conceived channel allocation mechanisms are likely to increases the queuing stress on the front path because they cause larger full sender rate data bursts.

インターネットのプロトコルではセルフクロックがどこにでもあるため、よく考えられていないチャネル割り当てのメカニズムは、送信者レートいっぱいのより大きなデータバーストを引き起こすことで、前方パスのキューイングの負担を増やす可能性が高いことに注意してください。

Holding data or ACKs for channel allocation or other reasons (such as forward error correction) always raises the effective RTT relative to the minimum delay for the path. Therefore, it may be necessary to replace target_RTT in the calculation in Section 5.2 by an effective_RTT, which includes the target_RTT plus a term to account for the extra delays introduced by these mechanisms.

チャネル割り当てやその他の理由（前方誤り訂正など）のためにデータやACKを保持すると、常にパスの最小遅延に比べて実効RTTが増大します。 したがって、セクション5.2の計算のtarget_RTTを、target_RTTにこれらのメカニズムによってもたらされる追加の遅延を考慮する項を加えたeffective_RTTで置き換える必要があるかもしれません。
