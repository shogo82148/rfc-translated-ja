RFC 463

FTP Comments and Response to RFC 430

RFC 463

FTPに関するコメントとRFC 430への回答

Abstract

概要

Most of the comments in RFC 430 by Bob Braden are useful suggestions which should be included in the forthcoming official FTP specification. This RFC represents my response to Braden's comments and other views. These comments should be useful for the FTP meeting on March 16 at BBN (announcement warning AAM NIC #14417). The results of the FTP subgroup meeting held at BBN on January 25 will be published in RFC 4541 (are published?).

Bob BradenによるRFC 430のコメントの大半は有益な提案であり、近く出る公式のFTP仕様に盛り込むべきです。このRFCは、Bradenのコメントやその他の意見に対する私の回答です。これらのコメントは、3月16日にBBNで開かれるFTP会議（AAMによる予告NIC #14417）に役立つはずです。1月25日にBBNで開かれたFTPサブグループ会議の結果は、RFC 4541で公開される予定です（公開済み？）。

SPECIFIC RESPONSES TO RFC 430.

RFC 430への個別の回答

Item A1 - I will let Bob Braden handle the "print file" issues (the "still" should be removed).

項目A1 - 「print file」の問題はBob Bradenに任せます（「still」は削除すべきです）。

Item A2 - I agree that concessions are undesirable and should be removed unless people cannot "live" without them.

項目A2 - 妥協策は望ましくなく、それなしでは皆が「やっていけない」というのでない限り削除すべきだという点に同意します。

Item A3 - I strongly support "bit flag coding" for descriptors. Other definition improvement suggestions are ok too.

項目A3 - 記述子に「ビットフラグ符号化」を使うことを強く支持します。定義を改善するその他の提案にも賛成です。

Item A4 - The diagram was useful. An alternate one is given on page 17 of RFC 454. I prefer the latter.

項目A4 - 図は有用でした。別の図がRFC 454の17ページにあります。私は後者のほうが好みです。

Item A5 - The FTP may not be privileged enough to alter passwords in many Host systems (e.g. Multics). I know that CCN allows changing passwords on-line. We can define a format for changing passwords in the pass command, but I don't think we can require that all servers allow password changing. This is a minor problem that can be easily solved.

項目A5 - 多くのホストシステム（たとえばMultics）では、FTPにはパスワードを変更できるほどの特権がないかもしれません。CCNがオンラインでのパスワード変更を許していることは知っています。PASSコマンドでパスワードを変更するための形式を定義することはできますが、すべてのサーバーにパスワードの変更を許すよう要求することはできないと思います。これは容易に解決できる小さな問題です。

Item A6 - Yes, the comment that TYPE should be before BYTE was for bad implementations. The server should reject data transfer parameters only when the data transfer command is received. The order of the parameter-change commands is not important.

項目A6 - そのとおりで、TYPEをBYTEの前に置くべきだというコメントは、出来の悪い実装を念頭に置いたものでした。サーバーは、データ転送コマンドを受信したときにのみ、データ転送パラメーターを拒否すべきです。パラメーターを変更するコマンドの順序は重要ではありません。

Item A7 - I do agree that NCP's should be fixed. A 255 (socket number) reply should be required at a specific time, and NCP's should be able to provide it (this also permits the proposed GSOC command). Let us find out at next meeting if there is anyone who cannot live with this new requirement.

項目A7 - NCPを修正すべきだという点には大いに同意します。255（ソケット番号）応答を特定の時点で必須とし、NCPがそれを提供できるようにすべきです（これにより、提案されているGSOCコマンドも可能になります）。この新しい要件を受け入れられない人がいるかどうか、次の会議で確かめましょう。

Item A8 - Yes.

項目A8 - そのとおりです。

Item B - There are at least two ways to solve the FTP parameter encoding problem presented by Bob Braden. One is to allow multiple letter in the TYPE command as suggested by Bob and the other is to have a new command such as FORM (which could be P or U). Other solutions are equally acceptable to me.

項目B - Bob Bradenが提示したFTPのパラメーターの符号化の問題を解決するには、少なくとも2つの方法があります。1つは、Bobが提案するようにTYPEコマンドで複数の文字を許す方法で、もう1つは、FORM（PまたはUを取ります）のような新しいコマンドを設ける方法です。私にとっては、ほかの解決策も同じように受け入れられます。

Item C - Our emphasis should be on working protocol as well as elegance. I like the proposed GSOC command over the listen. In fact GSOC can be used for all data connection security checking. The 255 reply should be sent with GSOC only, and the server should use only those sockets for data connection.

項目C - 私たちは、洗練さだけでなく、実際に動作するプロトコルにも重点を置くべきです。私はLISTENよりも、提案されているGSOCコマンドのほうが好みです。実際、GSOCはデータコネクションのあらゆるセキュリティー検査に使えます。255応答はGSOCに対してのみ送るべきであり、サーバーはデータコネクションにそのソケットだけを使うべきです。

Item D - We need more discussion on the issue of site dependent FTP parameters. I will put it on the agenda for the forthcoming FTP meeting.

項目D - サイトに依存するFTPパラメーターの問題については、さらに議論が必要です。次回のFTP会議の議題に加えます。

FURTHER COMMENTS

その他のコメント

1. The command-reply sequence needs to be tightened in both specification and implementations to allow convenient use of FTP by programs or "automatons".

1. プログラム、つまり「オートマトン」がFTPを便利に使えるように、コマンドと応答の手順を仕様と実装の両方で厳密にする必要があります。

2. A 300 reply greeting upon first connecting to the FTP server should be required and not optional. This avoids the programs having to wait an arbitrary time for such a greeting before issuing commands. Commands may only be sent after the 300 reply is received from the server.

2. FTPサーバーに最初に接続したときの300応答による挨拶は、省略可能ではなく必須にすべきです。こうすれば、プログラムがコマンドを発行する前に、その挨拶を待って任意の時間待機する必要がなくなります。コマンドは、サーバーから300応答を受信した後にのみ送ることができます。

3. RFC 454 needs a discussion of transfer between two FTP servers arranged by the user via the LSTN or GSOC commands.

3. RFC 454では、ユーザーがLSTNまたはGSOCコマンドを使って手配する、2つのFTPサーバー間の転送について議論する必要があります。

4. Perhaps we should allow specification of data transfer parameters in a single command line (for reasons of efficiency). A suggested format is to have <SP> separate the parameters bunched together in a single line (requiring only a single reply). Consider the following sequences:

4. （効率上の理由から）データ転送パラメーターを1つのコマンド行で指定できるようにすべきかもしれません。提案する形式は、1行にまとめたパラメーターを<SP>で区切るものです（応答は1つだけで済みます）。次の手順を考えてみてください。

        STRU F TYPE I BYTE 36 MODE S <CR><LF>
        reply - 200 OK

        STRU F TYPE I BYTE 36 MODE S <CR><LF>
        reply - 200 OK

5. Further discussion of MAIL and MAIL.file commands seems necessary. Perhaps we will get some useful input from the MAIL meeting at SRI on February 23, The following issues seem particularly relevant to me:

5. MAILコマンドとMAIL.fileコマンドについては、さらに議論が必要と思われます。2月23日にSRIで開かれるMAIL会議から、有益な意見が得られるかもしれません。私には、特に次の問題が重要と思われます。

  • a) Allowing mail to multiple users. It should be required that FTP servers allow this.
  • b) Using NIC idents. FTP servers should accept some standard form of user name. This could be NIC idents or last name with optional use of initials.
  • c) Uniform conventions for who the mail is from, day, time, etc., and how the mail is delivered to user. The mail usually gets tagged twice or sometimes not tagged at all. Perhaps we need a different mechanism for indicating who the mail is from than provided by the USER command.
  • d) handling bulk or junk mail (particularly the NIC documents that may be sent on-line by the NIC). Perhaps mail.file should put a file in user's directory and notify him of the same. The user does not see all the junk on his console but can print the file on a printer and read that class of mail at his leisure.
  • a) 複数のユーザーへのメールを許すこと。FTPサーバーにはこれを許すよう要求すべきです。
  • b) NIC識別子（NIC idents）を使うこと。FTPサーバーは、何らかの標準形式のユーザー名を受け入れるべきです。これはNIC識別子でもよいですし、姓（イニシャルを付けてもよい）でもかまいません。
  • c) メールの差出人、日付、時刻などや、メールをユーザーに届ける方法について、統一的な規約を設けること。メールには通常、タグが2回付けられるか、場合によってはまったく付けられません。メールの差出人を示すには、USERコマンドが提供するものとは別の仕組みが必要かもしれません。
  • d) 大量のメールや不要なメール（特に、NICがオンラインで送ることがあるNICの文書）を扱うこと。おそらく、mail.fileはユーザーのディレクトリーにファイルを置き、そのことをユーザーに通知すべきです。そうすれば、ユーザーは不要なものをすべてコンソールで見ることなく、ファイルをプリンターで印刷して、その種のメールを都合のよいときに読むことができます。
