RFC 1278

A string encoding of Presentation Address

RFC 1278

プレゼンテーションアドレスの文字列エンコーディング

Abstract

概要

There are a number of environments where a simple string encoding of Presentation Address is desirable. This specification defines such a representation.

プレゼンテーションアドレス（Presentation Address）の単純な文字列エンコーディングが望ましい環境は数多くあります。この仕様は、そのような表現を定義します。

Status of this Memo

このメモのステータス

This memo provides information for the Internet community. It does not specify an Internet standard. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーに情報を提供するものです。インターネット標準を規定するものではありません。このメモの配布は無制限です。

1. Introduction

1. はじめに

OSI Application Entities use presentation addresses to address other Application Entities. The model for this is defined in [ISO87b]. Presentation addresses are stored in the OSI Directory using an ASN.1 representation defined by the OSI Directory [CCI88]. Logically, a presentation address consists of:

OSIのアプリケーションエンティティー（Application Entity）は、ほかのアプリケーションエンティティーを指定するためにプレゼンテーションアドレスを使います。このためのモデルは[ISO87b]で定義されています。プレゼンテーションアドレスは、OSIディレクトリー[CCI88]で定義されたASN.1表現を使って、OSIディレクトリーに格納されます。論理的には、プレゼンテーションアドレスは次のもので構成されます。

  • A presentation selector
  • A session selector
  • A transport selector
  • A set of network addresses
  • プレゼンテーションセレクター
  • セッションセレクター
  • トランスポートセレクター
  • ネットワークアドレスの集合

The selectors are all octet strings, but often have IA5 character representations. The format of network addresses is defined in [ISO87a].

セレクターはすべてオクテット文字列ですが、多くの場合IA5文字による表現を持ちます。ネットワークアドレスの形式は[ISO87a]で定義されています。

There is a need to represent presentation addresses as strings in a number of different contexts. This Internet Draft defines a format for use on the Internet. It is for display to human users, and its use is recommended whenever this needs to be done. Typically, this will be for system managers rather than for end users. It is not intended for internal storage.

さまざまな状況で、プレゼンテーションアドレスを文字列として表す必要があります。このインターネットドラフトは、インターネットで使うための形式を定義します。これは人間のユーザーに表示するためのものであり、そうする必要があるときには常にこの形式を使うことを推奨します。通常、これはエンドユーザーではなくシステム管理者向けになるでしょう。内部での格納を意図したものではありません。

This Internet Draft was originally published as UCL Research Note RN/89/14 [Kil89]. It was agreed as a unified syntax for the THORN and ISODE projects. It is used throughout ISODE.

このインターネットドラフトは、もともとUCLのリサーチノートRN/89/14[Kil89]として公開されたものです。これはTHORNプロジェクトとISODEプロジェクトの統一構文として合意されました。ISODEの全体で使われています。

Christian Huitema of Inria and Marshall Rose of PSI Inc. gave much useful input to this document.

InriaのChristian HuitemaとPSI Inc.のMarshall Roseが、この文書に多くの有益な意見をくれました。

2. Requirements

2. 要件

The main requirements are:

主な要件は次のとおりです。

  • Must be able to specify any legal value.
  • Should be clean in the common case of the presentation address containing network addresses and no selectors.

  • Must deal with selectors in the following encodings:

    • IA5
    • Decimal digits encoded as IA5 (this is the most common syntax in Europe, as it is required by X.400(84) and should receive a straightforward encoding)
    • Numeric encoded as a 16 bit unsigned integer (US GOSIP). This is mapped onto two octets, with the first octet being the high order byte of the integer.
    • General Hexadecimal

  • Should give special encodings for the ad hoc encoding proposed in ``An interim approach to use of Network Addresses'' [HK91].

    • X.25(80) Networks
    • TCP/IP Networks
  • Should be extensible for additional forms.
  • Should provide a reasonably compact representation .
  • 任意の正当な値を指定できなければなりません。
  • プレゼンテーションアドレスがネットワークアドレスを含み、セレクターを含まないというよくある場合に、すっきりとした表現になるべきです。

  • 次のエンコーディングのセレクターを扱えなければなりません。

    • IA5
    • IA5としてエンコードされた10進数字（X.400(84)で要求されているため、これはヨーロッパで最も一般的な構文であり、素直なエンコーディングにすべきです）
    • 16ビット符号なし整数としてエンコードされた数値（US GOSIP）。これは2オクテットに対応付けられ、最初のオクテットが整数の上位バイトになります。
    • 一般の16進数

  • 「An interim approach to use of Network Addresses」[HK91]で提案されている場当たり的なエンコーディングに対して、特別なエンコーディングを与えるべきです。

    • X.25(80)ネットワーク
    • TCP/IPネットワーク
  • 追加の形式に対して拡張可能であるべきです。
  • ほどよくコンパクトな表現を提供すべきです。

Four examples:

4つの例を示します。

"256"/NS+a433bb93c1_NS+aa3106

#63/#41/#12/X121+234219200300

'3a'H/TELEX+00728722+X.25(80)+02+00002340555+CUDF+"892796"

Note that the RFC 1006 encoding permits use of either a DNS Domain Name or an IP address. The former is primarily for ease of entry. If this DNS Domain Name maps onto multiple IP addresses, then multiple network addresses should be generated. The DNS Domain Name form is for convenient input. When mapping from an encoded address to string form, the IP address form should always be used.

RFC 1006のエンコーディングでは、DNSドメイン名とIPアドレスのどちらでも使えることに注意してください。前者は主に入力のしやすさのためのものです。このDNSドメイン名が複数のIPアドレスに対応する場合は、複数のネットワークアドレスを生成すべきです。DNSドメイン名の形式は、入力の便宜のためのものです。エンコードされたアドレスから文字列形式に変換する際には、常にIPアドレスの形式を使うべきです。

4. Encoding

4. エンコーディング

Selectors are represented in a manner which can be easily encoded. In the NS notation, the concrete binary form of network address is given. Otherwise, this string notation provides a mechanism for representing the Abstract Syntax of a Network Address. This must be encoded according to Addendum 2 of ISO 8348 [ISO87a].

セレクターは、容易にエンコードできる方法で表現されます。NS表記では、ネットワークアドレスの具象バイナリー形式が与えられます。それ以外の場合、この文字列表記は、ネットワークアドレスの抽象構文を表現する仕組みを提供します。これは、ISO 8348のAddendum 2[ISO87a]に従ってエンコードしなければなりません。

5. Macros

5. マクロ

There are often common addresses, for which a cleaner representation is desired. This is achieved by use of Macros. If a <network-address> can be parsed as:

よく使われるアドレスがあることが多く、そうしたアドレスにはよりすっきりとした表現が望まれます。これはマクロを使うことで実現します。<network-address>が次のように解析できる場合を考えます。

<otherstring> "=" *( any )

<otherstring> "=" *( any )

Then the leading string is taken as a Macro, which is substituted. This may be applied recursively. When presenting Network Address to humans, the longest available substitution should be used. For example:

このとき、先頭の文字列はマクロとみなされ、置換されます。これは再帰的に適用してもかまいません。ネットワークアドレスを人間に提示する際には、利用できる最も長い置換を使うべきです。たとえば次のとおりです。

Table 1
Macro Value
UK.AC DCC+826+d110000
Leeds UK.AC=120
表1
マクロ 値
UK.AC DCC+826+d110000
Leeds UK.AC=120

Then ``Leeds=22'' would be expanded to ``DCC+826+d11000012022''.

この場合、「Leeds=22」は「DCC+826+d11000012022」に展開されます。
