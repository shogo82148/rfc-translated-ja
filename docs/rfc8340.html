RFC 8340

YANG Tree Diagrams

RFC 8340

YANGツリー図

Abstract

概要

This document captures the current syntax used in YANG module tree diagrams. The purpose of this document is to provide a single location for this definition. This syntax may be updated from time to time based on the evolution of the YANG language.

この文書は、YANGモジュールのツリー図で現在使われている構文をまとめたものです。この文書の目的は、この定義を1か所で提供することです。この構文は、YANG言語の発展に応じて随時更新される場合があります。

1. Introduction

1. はじめに

YANG tree diagrams were first published in RFC 6536. Such diagrams are used to provide a simplified graphical representation of a data model and can be automatically generated via tools such as "pyang" [PYANG]. This document describes the syntax used in YANG tree diagrams. It is expected that this document will be updated or replaced as changes to the YANG language [RFC7950] necessitate.

YANGツリー図は、RFC 6536で初めて公開されました。このような図は、データモデルを簡略化して図示するために使われ、「pyang」[PYANG]などのツールで自動的に生成できます。この文書は、YANGツリー図で使われる構文を説明します。この文書は、YANG言語[RFC7950]の変更によって必要になったときに、更新または置き換えられることが想定されています。

Today's common practice is to include the definition of the syntax used to represent a YANG module in every document that provides a tree diagram. This practice has several disadvantages; therefore, the purpose of this document is to provide a single location for this definition. It is not the intent of this document to restrict future changes, but rather to ensure that such changes are easily identified and suitably agreed upon.

現在の一般的な慣行では、ツリー図を掲載するすべての文書に、YANGモジュールを表現するために使う構文の定義を含めています。この慣行にはいくつかの欠点があります。そのため、この文書の目的は、この定義を1か所で提供することです。この文書は、将来の変更を制限することを意図したものではありません。むしろ、そのような変更を容易に識別でき、適切に合意されるようにすることを意図しています。

An example tree diagram can be found in Section 3 of [RFC8343]; the following is a portion of it:

ツリー図の例は[RFC8343]のセクション3にあります。その一部を次に示します。

  +--rw interfaces
     +--rw interface* [name]
        +--rw name                        string
        +--rw description?                string
        +--rw type                        identityref
        +--rw enabled?                    boolean
        +--rw link-up-down-trap-enable?   enumeration {if-mib}?

  +--rw interfaces
     +--rw interface* [name]
        +--rw name                        string
        +--rw description?                string
        +--rw type                        identityref
        +--rw enabled?                    boolean
        +--rw link-up-down-trap-enable?   enumeration {if-mib}?

2. Tree Diagram Syntax

2. ツリー図の構文

This section describes the meaning of the symbols used in YANG tree diagrams.

このセクションでは、YANGツリー図で使われる記号の意味を説明します。

A full tree diagram of a module represents all elements. It includes the name of the module and sections for top-level module statements (typically containers), augmentations, rpcs, and notifications all identified under a module statement. Module trees may be included in a document as a whole, by one or more sections, or even by subsets of nodes.

モジュールの完全なツリー図は、すべての要素を表します。完全なツリー図には、モジュールの名前と、モジュールのトップレベルのステートメント（通常はコンテナー）、augment、RPC、通知のセクションが含まれ、これらはすべてmoduleステートメントの下で識別されます。モジュールツリーは、全体として文書に含めることも、1つ以上のセクション単位で含めることも、さらにはノードの部分集合単位で含めることもできます。

A module is identified by "module:" followed by the module-name. This is followed by one or more sections, in order:

モジュールは、「module:」の後にモジュール名を続けたもので識別されます。その後に、1つ以上のセクションが次の順序で続きます。

  1. The top-level data nodes defined in the module, offset by two spaces.
  2. Augmentations, offset by two spaces and identified by the keyword "augment" followed by the augment target node and a colon (":") character.
  3. RPCs, offset by two spaces and identified by "rpcs:".
  4. Notifications, offset by two spaces and identified by "notifications:".
  5. Groupings, offset by two spaces and identified by the keyword "grouping" followed by the name of the grouping and a colon (":") character.
  6. yang-data, offset by two spaces and identified by the keyword "yang-data" followed by the name of the yang-data structure and a colon (":") character.
  1. モジュールで定義されたトップレベルのデータノード。2つの空白でオフセットします。
  2. augment。2つの空白でオフセットし、キーワード「augment」の後にaugmentの対象ノードとコロン（「:」）文字を続けたもので識別します。
  3. RPC。2つの空白でオフセットし、「rpcs:」で識別します。
  4. 通知。2つの空白でオフセットし、「notifications:」で識別します。
  5. グルーピング。2つの空白でオフセットし、キーワード「grouping」の後にグルーピングの名前とコロン（「:」）文字を続けたもので識別します。
  6. yang-data。2つの空白でオフセットし、キーワード「yang-data」の後にyang-data構造の名前とコロン（「:」）文字を続けたもので識別します。

The relative organization of each section is provided using a text-based format that is typical of a file system directory tree display command. Each node in the tree is prefaced with "+--". Schema nodes that are children of another node are offset from the parent by three spaces. Sibling schema nodes are listed with the same space offset and, when separated by lines, are linked via a vertical bar ("|") character.

各セクションの相対的な構成は、ファイルシステムのディレクトリーツリーを表示するコマンドに典型的なテキストベースの形式で示します。ツリー内の各ノードの先頭には「+--」を付けます。別のノードの子であるスキーマノードは、親から3つの空白でオフセットします。兄弟のスキーマノードは同じ空白のオフセットで並べ、間に行がある場合は縦棒（「|」）文字でつなぎます。

The full format, including spacing conventions, is:

空白の規則を含めた完全な形式は次のとおりです。

  module: <module-name>
    +--<node>
    |  +--<node>
    |     +--<node>
    +--<node>
       +--<node>
          +--<node>

    augment <target-node>:
      +--<node>
         +--<node>
         +--<node>
            +--<node>
    augment <target-node>:
      +--<node>

    rpcs:
      +--<rpc-node>
      +--<rpc-node>
         +--<node>
         |  +--<node>
         +--<node>

    notifications:
      +--<notification-node>
      +--<notification-node>
         +--<node>
         |  +--<node>
         +--<node>

    grouping <grouping-name>:
      +--<node>
         +--<node>
         |  +--<node>
         +--<node>
    grouping <grouping-name>:
      +--<node>

    yang-data <yang-data-name>:
      +--<node>
         +--<node>
         |  +--<node>
         +--<node>
    yang-data <yang-data-name>:
      +--<node>

  module: <module-name>
    +--<node>
    |  +--<node>
    |     +--<node>
    +--<node>
       +--<node>
          +--<node>

    augment <target-node>:
      +--<node>
         +--<node>
         +--<node>
            +--<node>
    augment <target-node>:
      +--<node>

    rpcs:
      +--<rpc-node>
      +--<rpc-node>
         +--<node>
         |  +--<node>
         +--<node>

    notifications:
      +--<notification-node>
      +--<notification-node>
         +--<node>
         |  +--<node>
         +--<node>

    grouping <grouping-name>:
      +--<node>
         +--<node>
         |  +--<node>
         +--<node>
    grouping <grouping-name>:
      +--<node>

    yang-data <yang-data-name>:
      +--<node>
         +--<node>
         |  +--<node>
         +--<node>
    yang-data <yang-data-name>:
      +--<node>

2.1. Submodules

2.1. サブモジュール

Submodules are represented in the same fashion as modules but are identified by "submodule:" followed by the (sub)module-name. For example:

サブモジュールはモジュールと同じ方法で表しますが、「submodule:」の後に（サブ）モジュール名を続けたもので識別します。たとえば次のとおりです。

  submodule: <module-name>
    +--<node>
    |  +--<node>
    |     +--<node>

  submodule: <module-name>
    +--<node>
    |  +--<node>
    |     +--<node>

2.2. Groupings

2.2. グルーピング

Nodes within a used grouping are normally expanded as if the nodes were defined at the location of the "uses" statement. However, it is also possible to not expand the "uses" statement but to instead print the name of the grouping.

使用されたグルーピング内のノードは、通常、それらのノードが「uses」ステートメントの位置で定義されたかのように展開します。ただし、「uses」ステートメントを展開せずに、代わりにグルーピングの名前を表示することもできます。

For example, the following diagram shows the "tls-transport" grouping from [RFC7407] unexpanded:

たとえば、次の図は[RFC7407]の「tls-transport」グルーピングを展開せずに示したものです。

    +--rw tls
       +---u tls-transport

    +--rw tls
       +---u tls-transport

If the grouping is expanded, it could be printed as:

グルーピングを展開すると、次のように表示できます。

    +--rw tls
       +--rw port?                 inet:port-number
       +--rw client-fingerprint?   x509c2n:tls-fingerprint
       +--rw server-fingerprint?   x509c2n:tls-fingerprint
       +--rw server-identity?      snmp:admin-string

    +--rw tls
       +--rw port?                 inet:port-number
       +--rw client-fingerprint?   x509c2n:tls-fingerprint
       +--rw server-fingerprint?   x509c2n:tls-fingerprint
       +--rw server-identity?      snmp:admin-string

Groupings may optionally be present in the "groupings" section.

グルーピングは、任意で「groupings」セクションに含めることができます。

2.3. yang-data

2.3. yang-data

If the module defines a "yang-data" structure [RFC8040], these structures may optionally be present in the "yang-data" section.

モジュールが「yang-data」構造[RFC8040]を定義している場合、これらの構造は、任意で「yang-data」セクションに含めることができます。

2.4. Collapsed Node Representation

2.4. ノードの折りたたみ表現

At times when the composition of the nodes within a module schema is not important in the context of the presented tree, sibling nodes and their children can be collapsed using the notation "..." in place of the text lines used to represent the summarized nodes. For example:

モジュールスキーマ内のノードの構成が、示しているツリーの文脈で重要ではない場合には、要約されるノードを表すテキスト行の代わりに「...」という表記を使って、兄弟ノードとその子を折りたたむことができます。たとえば次のとおりです。

    +--<node>
    |  ...
    +--<node>
       +--<node>
          +--<node>

    +--<node>
    |  ...
    +--<node>
       +--<node>
          +--<node>

2.5. Comments

2.5. コメント

Single line comments, starting with "//" (possibly indented) and ending at the end of the line, may be used in the tree notation.

ツリーの表記では、「//」で始まり（インデントされていてもかまいません）行末で終わる1行コメントを使用できます。

2.6. Node Representation

2.6. ノードの表現

Each node in a YANG module is printed as:

YANGモジュール内の各ノードは、次のように表示します。

  <status>--<flags> <name><opts> <type> <if-features>

  <status>--<flags> <name><opts> <type> <if-features>

  • <status> is one of:

    +
    for current
    x
    for deprecated
    o
    for obsolete

  • <flags> is one of:

    rw
    for configuration data nodes and choice nodes
    ro
    for non-configuration data nodes and choice nodes, output parameters to rpcs and actions, and notification parameters
    -w
    for input parameters to rpcs and actions
    -u
    for uses of a grouping
    -x
    for rpcs and actions
    -n
    for notifications
    mp
    for nodes containing a "mount-point" extension statement

    Case nodes do not have any <flags>.

  • <name> is the name of the node

    (<name>)
    means that the node is a choice node
    :(<name>)
    means that the node is a case node

    If the node is augmented into the tree from another module, its name is printed as <prefix>:<name>, where <prefix> is the prefix defined in the module where the node is defined.

    If the node is a case node, there is no space before the <name>.

  • <opts> is one of:

    ?
    for an optional leaf, choice, anydata, or anyxml
    !
    for a presence container
    *
    for a leaf-list or list
    [<keys>]
    for a list's keys
    /
    for a top-level data node in a mounted module
    @
    for a top-level data node of a module identified in a mount point parent reference

  • <type> is the name of the type for leafs and leaf-lists

    If the type is a leafref, the type is printed as either (1) "-> TARGET", where TARGET is the leafref path, with prefixes removed if possible or (2) "leafref".

  • <if-features> is the list of features this node depends on, printed within curly brackets and a question mark "{...}?"

  • <status>は次のいずれかです。

    +
    現行（current）を表します
    x
    非推奨（deprecated）を表します
    o
    廃止（obsolete）を表します

  • <flags>は次のいずれかです。

    rw
    設定データノードとchoiceノードを表します
    ro
    非設定データノードとchoiceノード、RPCとアクションの出力パラメーター、通知パラメーターを表します
    -w
    RPCとアクションの入力パラメーターを表します
    -u
    グルーピングの使用（uses）を表します
    -x
    RPCとアクションを表します
    -n
    通知を表します
    mp
    「mount-point」拡張ステートメントを含むノードを表します

    caseノードには<flags>はありません。

  • <name>はノードの名前です。

    (<name>)
    そのノードがchoiceノードであることを意味します
    :(<name>)
    そのノードがcaseノードであることを意味します

    ノードが別のモジュールからツリーにaugmentされている場合、その名前は<prefix>:<name>として表示します。ここで<prefix>は、そのノードが定義されているモジュールで定義されたプレフィックスです。

    ノードがcaseノードの場合、<name>の前に空白は入りません。

  • <opts>は次のいずれかです。

    ?
    任意のleaf、choice、anydata、anyxmlを表します
    !
    presenceコンテナーを表します
    *
    leaf-listまたはlistを表します
    [<keys>]
    listのキーを表します
    /
    マウントされたモジュールのトップレベルのデータノードを表します
    @
    マウントポイントの親参照で識別されるモジュールのトップレベルのデータノードを表します

  • <type>は、leafとleaf-listの型の名前です。

    型がleafrefの場合、型は（1）「-> TARGET」（TARGETはleafrefのパスで、可能であればプレフィックスを取り除いたもの）、または（2）「leafref」のいずれかとして表示します。

  • <if-features>は、このノードが依存する機能（feature）のリストで、波かっこと疑問符「{...}?」で囲んで表示します。

Arbitrary whitespace is allowed between any of the whitespace-separated fields (e.g., <opts> and <type>). Additional whitespace may, for example, be used to "column align" fields (e.g., within a list or container) to improve readability.

空白で区切られたフィールドの間（たとえば<opts>と<type>の間）には、任意の空白を入れることができます。たとえば、読みやすくするために、（リストやコンテナーの中などで）フィールドを「列にそろえる」ために追加の空白を使用できます。

3. Usage Guidelines for RFCs

3. RFCでの使用に関するガイドライン

This section provides general guidelines related to the use of tree diagrams in RFCs.

このセクションでは、RFCでのツリー図の使用に関する一般的なガイドラインを示します。

3.1. Wrapping Long Lines

3.1. 長い行の折り返し

Internet-Drafts and RFCs limit the number of characters that may appear in a line of text to 72 characters. When the tree representation of a node results in a line being longer than this limit, the line should be broken between <opts> and <type> or between <type> and <if-feature>. The new line should be indented so that it starts below <name> with a whitespace offset of at least two characters. For example:

インターネットドラフトとRFCでは、テキストの1行に含められる文字数が72文字に制限されています。ノードのツリー表現によって行がこの制限より長くなる場合は、<opts>と<type>の間、または<type>と<if-feature>の間で行を折り返すべきです。新しい行は、<name>の下から始まり、少なくとも2文字分の空白のオフセットを持つようにインデントすべきです。たとえば次のとおりです。

  notifications:
    +---n yang-library-change
       +--ro module-set-id
               -> /modules-state/module-set-id

  notifications:
    +---n yang-library-change
       +--ro module-set-id
               -> /modules-state/module-set-id

Long paths (e.g., leafref paths or augment targets) can be split and printed on more than one line. For example:

長いパス（たとえばleafrefのパスやaugmentの対象）は、分割して複数の行に表示できます。たとえば次のとおりです。

  augment /nat:nat/nat:instances/nat:instance/nat:mapping-table
            /nat:mapping-entry:

  augment /nat:nat/nat:instances/nat:instance/nat:mapping-table
            /nat:mapping-entry:

The previously mentioned "pyang" command can be helpful in producing such output; for example, the notification diagram above was produced using:

このような出力を作成するには、前述の「pyang」コマンドが役立ちます。たとえば、上の通知の図は次のコマンドで作成しました。

  pyang -f tree --tree-line-length 50 ietf-yang-library.yang

  pyang -f tree --tree-line-length 50 ietf-yang-library.yang

When a tree diagram is included as a figure in an Internet-Draft or RFC, "--tree-line-length 69" works well.

ツリー図をインターネットドラフトやRFCの図として含める場合は、「--tree-line-length 69」がうまく機能します。

3.2. Groupings

3.2. グルーピング

If the YANG module is comprised of groupings only, then the tree diagram should contain the groupings. The "pyang" compiler can be used to produce a tree diagram with groupings using the "-f tree --tree-print-groupings" command-line parameters.

YANGモジュールがグルーピングだけで構成されている場合、ツリー図にはそれらのグルーピングを含めるべきです。「pyang」コンパイラーでは、コマンドラインパラメーター「-f tree --tree-print-groupings」を使って、グルーピングを含むツリー図を作成できます。

3.3. Long Diagrams

3.3. 長い図

Tree diagrams can be split into sections to correspond to document structure. As tree diagrams are intended to provide a simplified view of a module, diagrams longer than a page should generally be avoided. If the complete tree diagram for a module becomes too long, the diagram can be split into several smaller diagrams. For example, it might be possible to have one diagram with the data node and another with all notifications. If the data nodes tree is too long, it is also possible to split the diagram into smaller diagrams for different subtrees. When long diagrams are included in a document, authors should consider whether to include the long diagram in the main body of the document or in an appendix.

ツリー図は、文書の構造に対応させて複数の部分に分割できます。ツリー図はモジュールを簡略化して示すことを目的としているので、一般に1ページより長い図は避けるべきです。モジュールの完全なツリー図が長くなりすぎる場合は、図をいくつかの小さな図に分割できます。たとえば、データノードの図とすべての通知の図を別々にすることが考えられます。データノードのツリーが長すぎる場合は、サブツリーごとに小さな図に分割することもできます。長い図を文書に含める場合、著者は、その長い図を文書の本文に含めるか付録に含めるかを検討すべきです。

An example of such a split can be found in [RFC7407], where Section 2.4 of that document shows the diagram for "engine configuration":

このような分割の例は[RFC7407]にあり、その文書のセクション2.4では「engine configuration」の図を次のように示しています。

    +--rw snmp
       +--rw engine
          // more parameters from the "engine" subtree here

    +--rw snmp
       +--rw engine
          // 「engine」サブツリーのその他のパラメーターがここに入る

Further, Section 2.5 of [RFC7407] shows the diagram for "target configuration":

さらに、[RFC7407]のセクション2.5では「target configuration」の図を次のように示しています。

    +--rw snmp
       +--rw target* [name]
          // more parameters from the "target" subtree here

    +--rw snmp
       +--rw target* [name]
          // 「target」サブツリーのその他のパラメーターがここに入る

The previously mentioned "pyang" command can be helpful in producing such output; for example, the above example was produced using:

このような出力を作成するには、前述の「pyang」コマンドが役立ちます。たとえば、上の例は次のコマンドで作成しました。

  pyang -f tree --tree-path /snmp/target ietf-snmp.yang

  pyang -f tree --tree-path /snmp/target ietf-snmp.yang

4. YANG Schema Mount Tree Diagrams

4. YANGスキーママウントのツリー図

"YANG schema mount" is defined in [SCHEMA-MOUNT] and warrants some specific discussion. Schema mount is a generic mechanism that allows for the mounting of one or more YANG modules at a specified location of another (parent) schema. The specific location is referred to as a "mount point", and any container or list node in a schema may serve as a mount point. Mount points are identified via the inclusion of the "mount-point" extension statement as a substatement under a container or list node. Mount point nodes are thus directly identified in a module schema definition and can be identified in a tree diagram as indicated above using the "mp" flag.

「YANGスキーママウント（YANG schema mount）」は[SCHEMA-MOUNT]で定義されており、いくつか固有の議論が必要です。スキーママウントは、1つ以上のYANGモジュールを別の（親）スキーマの指定した位置にマウントできるようにする汎用的なメカニズムです。この指定した位置は「マウントポイント（mount point）」と呼ばれ、スキーマ内のどのコンテナーノードやリストノードもマウントポイントになることができます。マウントポイントは、コンテナーノードまたはリストノードのサブステートメントとして「mount-point」拡張ステートメントを含めることで識別されます。したがって、マウントポイントノードはモジュールのスキーマ定義の中で直接識別され、ツリー図では前述のとおり「mp」フラグを使って識別できます。

In the following example taken from [YANG-NIs], "vrf-root" is a container that includes the "mount-point" extension statement as part of its definition:

[YANG-NIs]から引用した次の例では、「vrf-root」は、その定義の一部として「mount-point」拡張ステートメントを含むコンテナーです。

  module: ietf-network-instance
    +--rw network-instances
       +--rw network-instance* [name]
          +--rw name           string
          +--rw enabled?       boolean
          +--rw description?   string
          +--rw (ni-type)?
          +--rw (root-type)
             +--:(vrf-root)
             |  +--mp vrf-root

  module: ietf-network-instance
    +--rw network-instances
       +--rw network-instance* [name]
          +--rw name           string
          +--rw enabled?       boolean
          +--rw description?   string
          +--rw (ni-type)?
          +--rw (root-type)
             +--:(vrf-root)
             |  +--mp vrf-root

4.1. Representation of Mounted Schema Trees

4.1. マウントされたスキーマツリーの表現

The actual modules made available under a mount point are controlled by a server and are provided to clients. This information is typically provided via the schema mount module ("ietf-yang-schema-mount") defined in [SCHEMA-MOUNT]. The schema mount module supports the exposure of both mounted schema and "parent-references". Parent references are used for XML Path Language (XPath) evaluation within mounted modules and do not represent client-accessible paths; the referenced information is available to clients via the parent schema. Schema mount also defines an "inline" type of mount point, where mounted modules are exposed via the YANG library module.

マウントポイントの下で実際に利用可能になるモジュールは、サーバーが制御し、クライアントに提供します。この情報は通常、[SCHEMA-MOUNT]で定義されているスキーママウントモジュール（「ietf-yang-schema-mount」）を介して提供されます。スキーママウントモジュールは、マウントされたスキーマと「親参照（parent-references）」の両方の公開をサポートします。親参照は、マウントされたモジュール内でのXMLパス言語（XPath）の評価に使われ、クライアントがアクセスできるパスを表すものではありません。参照される情報は、親スキーマを介してクライアントが利用できます。スキーママウントでは「inline」タイプのマウントポイントも定義されており、この場合、マウントされたモジュールはYANGライブラリーモジュールを介して公開されます。

Although the modules made available under a mount point are not specified in YANG modules that include mount points, the document defining the module will describe the intended use of the module and may identify both modules that will be mounted and parent modules that can be referenced by mounted modules. An example of such a description can be found in [YANG-NIs]. A specific implementation of a module containing mount points will also support a specific list of mounted and referenced modules. In describing both intended use and actual implementations, it is helpful to show how mounted modules would be instantiated and referenced under a mount point using tree diagrams.

マウントポイントの下で利用可能になるモジュールは、マウントポイントを含むYANGモジュールでは規定されませんが、そのモジュールを定義する文書では、モジュールの意図された用途を説明し、マウントされるモジュールと、マウントされたモジュールから参照できる親モジュールの両方を示すことがあります。このような説明の例は[YANG-NIs]にあります。また、マウントポイントを含むモジュールの具体的な実装は、マウントされるモジュールと参照されるモジュールの具体的なリストをサポートします。意図された用途と実際の実装のどちらを説明する場合でも、マウントされたモジュールがマウントポイントの下でどのようにインスタンス化され参照されるのかをツリー図で示すと役立ちます。

In such diagrams, the mount point should be treated much like a container that uses a grouping. The flags should also be set based on the "config" leaf mentioned above, and the mount-related options indicated above should be shown for the top-level nodes in a mounted or referenced module. The following example, taken from [YANG-NIs], represents the prior example with the YANG modules "ietf-routing" [YANG-Routing] and "ietf-ospf" [OSPF-YANG] mounted, nodes from the YANG module "ietf-interfaces" [RFC8343] accessible via a parent-reference, and "config" indicating "true":

このような図では、マウントポイントを、グルーピングを使用するコンテナーとほぼ同じように扱うべきです。また、フラグは前述の「config」リーフに基づいて設定すべきであり、前述のマウントに関するオプションは、マウントされたモジュールまたは参照されるモジュールのトップレベルのノードに示すべきです。[YANG-NIs]から引用した次の例は、前の例に、YANGモジュール「ietf-routing」[YANG-Routing]と「ietf-ospf」[OSPF-YANG]をマウントし、YANGモジュール「ietf-interfaces」[RFC8343]のノードに親参照（parent-reference）でアクセスできるようにし、「config」が「true」を示している状態を表したものです。

  module: ietf-network-instance
    +--rw network-instances
       +--rw network-instance* [name]
          +--rw name           string
          +--rw enabled?       boolean
          +--rw description?   string
          +--rw (ni-type)?
          +--rw (root-type)
             +--:(vrf-root)
                +--mp vrf-root
                   +--ro rt:routing-state/
                   |  +--ro router-id?
                   |  +--ro control-plane-protocols
                   |     +--ro control-plane-protocol* [type name]
                   |        +--ro ospf:ospf
                   |           +--ro instance* [af]
                   |           ...
                   +--rw rt:routing/
                   |  +--rw router-id?
                   |  +--rw control-plane-protocols
                   |     +--rw control-plane-protocol* [type name]
                   |     +--rw ospf:ospf
                   |        +--rw instance* [af]
                   |           ...
                   +--ro if:interfaces@
                   |  ...
                   +--ro if:interfaces-state@
                   |  ...

  module: ietf-network-instance
    +--rw network-instances
       +--rw network-instance* [name]
          +--rw name           string
          +--rw enabled?       boolean
          +--rw description?   string
          +--rw (ni-type)?
          +--rw (root-type)
             +--:(vrf-root)
                +--mp vrf-root
                   +--ro rt:routing-state/
                   |  +--ro router-id?
                   |  +--ro control-plane-protocols
                   |     +--ro control-plane-protocol* [type name]
                   |        +--ro ospf:ospf
                   |           +--ro instance* [af]
                   |           ...
                   +--rw rt:routing/
                   |  +--rw router-id?
                   |  +--rw control-plane-protocols
                   |     +--rw control-plane-protocol* [type name]
                   |     +--rw ospf:ospf
                   |        +--rw instance* [af]
                   |           ...
                   +--ro if:interfaces@
                   |  ...
                   +--ro if:interfaces-state@
                   |  ...

It is worth highlighting that the "ietf-ospf" module augments the "ietf-routing" module, and although it is listed in the schema mount module (or inline YANG library), there is no special mount-related notation in the tree diagram.

注目すべき点として、「ietf-ospf」モジュールは「ietf-routing」モジュールをaugmentしており、スキーママウントモジュール（またはインラインのYANGライブラリー）には列挙されていますが、ツリー図にはマウントに関する特別な表記はありません。

A mount point definition alone is not sufficient to identify whether the mounted modules are used for configuration data or for non-configuration data. This is determined by the "ietf-yang-schema-mount" module's "config" leaf associated with the specific mount point and is indicated on the top-level mounted nodes.

マウントポイントの定義だけでは、マウントされたモジュールが設定データに使われるのか、非設定データに使われるのかを識別するには不十分です。これは、特定のマウントポイントに関連付けられた「ietf-yang-schema-mount」モジュールの「config」リーフによって決まり、マウントされたトップレベルのノードに示されます。

For example, in the above tree, when the "config" leaf for the "ietf-routing" module indicates "false", the nodes in the "rt:routing" subtree would have different flags:

たとえば、上のツリーで「ietf-routing」モジュールの「config」リーフが「false」を示している場合、「rt:routing」サブツリーのノードは次のように異なるフラグを持つことになります。

                   +--ro rt:routing/
                   |  +--ro router-id?
                   |  +--ro control-plane-protocols
                      ...

                   +--ro rt:routing/
                   |  +--ro router-id?
                   |  +--ro control-plane-protocols
                      ...
