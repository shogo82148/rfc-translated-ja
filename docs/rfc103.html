RFC 103

Implementation of Interrupt Keys

RFC 103

割り込みキーの実装

Abstract

概要

The current protocol specifications contain a serious logical error in the implementation of the program interrupt function. This paper discusses the problem and offers a solution that is simple to implement.

現在のプロトコル仕様には、プログラム割り込み機能の実装に深刻な論理的誤りがあります。この文書では、その問題について議論し、実装が簡単な解決策を提示します。

THE PROBLEM

問題

As found on most time-sharing systems the program interrupt key, elsewhere known as the break key, or help request button, has two functions. It suspends temporarily the user process being run, and it switches the keyboard input stream to a dormant supervisory process. Unaccepted input typed prior to the interrupt request remains buffered for the suspended user process. Subsequent typing is sent to a supervisory routine.

ほとんどのタイムシェアリングシステムに見られるように、プログラム割り込みキー（ブレークキーやヘルプ要求ボタンとも呼ばれます）には2つの機能があります。実行中のユーザープロセスを一時的に中断することと、キーボードの入力ストリームを休止中の監視プロセス（supervisory process）に切り替えることです。割り込み要求の前に入力されてまだ受け付けられていない入力は、中断されたユーザープロセスのためにバッファーに残ります。その後の入力は監視ルーチンに送られます。

The current NCP protocol implements only half this function. It pprovides, through use of INS and INR control messages, for the suspension of a remote process, but it offers no mechanism for notifying the remote host at what time the data stream should be switched. INR and INS messages are sent via the control link and because messages on this link travel concurrently with those on the user's keyboard input link, the receiving host can not rely on relative arrival times as a source of synchronizing information. Without such information the remote NCP can not know which input characters are meant for the user process and which are meant for the supervisory routine.

現在のNCPプロトコルは、この機能の半分しか実装していません。NCPプロトコルは、INSとINRの制御メッセージを使ってリモートプロセスを中断する手段を提供していますが、どの時点でデータストリームを切り替えるべきかをリモートホストに通知する仕組みはありません。INRとINSのメッセージは制御リンクを介して送られ、このリンク上のメッセージはユーザーのキーボード入力リンク上のメッセージと並行して伝わるので、受信ホストは相対的な到着時刻を同期情報の源として当てにできません。そのような情報がなければ、リモートのNCPは、どの入力文字がユーザープロセス向けで、どの入力文字が監視ルーチン向けなのかを知ることができません。

A solution found on some systems to this problem is that of mapping the interrupt signal into some code from the character set -- typically an ASCII control-C. Unfortunately, this is not general enough to be used within the ARPA network. Some systems, eg. MULTICS, make use of all available ASCII codes for other purposes, none are available for such an assignment. Even if such an assignment could be made, there is the problem of getting the interrupt character to be recognized by the remote host. Buffers on that user link may be full and the sending host may be unable to transmit the message containing the interrupt code. If the remote user process loops without accepting data, there is the possibility that its input buffers will never become free and that the message will never get through.

この問題に対して一部のシステムで見られる解決策は、割り込み信号を文字セットの何らかのコード（典型的にはASCIIのcontrol-C）に対応付けることです。残念ながら、これはARPAネットワーク内で使えるほど汎用的ではありません。MULTICSなどの一部のシステムは、利用できるすべてのASCIIコードを他の目的に使っており、そのような割り当てに使えるコードはありません。仮にそのような割り当てができたとしても、割り込み文字をリモートホストに認識させるという問題があります。そのユーザーリンクのバッファーがいっぱいになっていて、送信ホストが割り込みコードを含むメッセージを送信できないかもしれません。リモートのユーザープロセスがデータを受け付けずにループしている場合、その入力バッファーがいつまでも空かず、メッセージがいつまでも届かない可能性があります。

A partial answer is that of providing at the serving end a teletype scanner process that is always hungry for input. Because all input messages are immediately consumed, buffers remain available and interrupt codes can get through. Unfortunately, this implies that at times characters must be thrown away. After being scanned there may be no buffer space available for them. While not critical during console interactions -- users can type only when the program demands input -- this defect prevents the scanner from being driven from a text file.

部分的な答えは、常に入力を欲しがっているテレタイプスキャナープロセスをサービス提供側に用意することです。すべての入力メッセージがただちに消費されるので、バッファーは利用可能なままとなり、割り込みコードが届くようになります。残念ながら、これは時には文字を捨てなければならないことを意味します。スキャンしたあと、それらの文字のためのバッファー領域がないかもしれません。コンソールでの対話中には致命的ではありませんが（ユーザーはプログラムが入力を求めたときにしか入力できません）、この欠陥のために、スキャナーをテキストファイルから駆動することができません。

A SOLUTION

解決策

The following defines a solution to this problem for the case of ASCII data streams.

以下では、ASCIIデータストリームの場合について、この問題の解決策を定義します。

  1. Character messages should use eight bit fields for each character code.
  2. For all of the defined ASCII character codes the left most bit in the eight bit field shall be zero.
  3. An interrupt sync character ( arbitrarilly given the code octal 200 ) should be placed in the data stream at the correct point in the typing sequence.
  4. All codes from octal 201 to octal 377 are officially to be ignored by a receiving host. Their use is reserved for additional control information, should it become necessary. Attempts to use them as additional character codes will meet with resistance from PDP-10 systems that internally pack characters into seven bit fields. Note that this objection can not be made against the interrupt sync character because it is filtered out by the system and never appears in a user's input buffer.
  5. Because of the possibility that there may be an insufficient allocation to allow the user message containing the interrupt sync character to be sent, the INR/INS mechanism currently defined must be kept. An INS control message should be sent at the time an interrupt sync character is entered into a text stream. Upon its reception by the foreign host, the attached process should be immediately suspended and the associated input stream should be scanned. If possible, all input up to the interrupt sync character should be buffered for the suspended process. Once the sync character is found, the stream should be switched to the newly activated supervisory process. If it is not possible to buffer all of the user process's input, it can be thrown away, and a error message returned to the user by the supervisory process. In either event it must be guaranteed that outstanding input will be consumed and message buffers will be freed so that pending character messages can be sent.
  6. In the event that an interrupt sync character is received before the matching INS, the user process should be suspended and the NCP should wait for the INS before proceeding.
  7. The function of the NCP is the above discussion can, of course, be delegated a separate modulo, eg. a TELNET process. If this is done, the NCP can be transparent to message content.
  1. 文字メッセージは、各文字コードに8ビットのフィールドを使うべきです。
  2. 定義されているすべてのASCII文字コードについて、8ビットのフィールドの最も左のビットはゼロとします。
  3. 割り込み同期文字（便宜上、8進数で200というコードを与えます）を、入力の並びの正しい位置でデータストリームに置くべきです。
  4. 8進数で201から377までのすべてのコードは、受信ホストが無視するものと公式に定めます。これらのコードは、必要になった場合の追加の制御情報のために予約します。これらを追加の文字コードとして使おうとすると、文字を内部で7ビットのフィールドに詰め込むPDP-10のシステムからの抵抗にあうでしょう。割り込み同期文字はシステムによって取り除かれ、ユーザーの入力バッファーに現れることはないので、割り込み同期文字に対してはこの反論は当たらないことに注意してください。
  5. 割り込み同期文字を含むユーザーメッセージを送れるだけの割り当てがない可能性があるので、現在定義されているINR/INSの仕組みは残さなければなりません。割り込み同期文字がテキストストリームに入れられた時点で、INS制御メッセージを送るべきです。外部ホストがこれを受信したら、接続されているプロセスをただちに中断し、関連する入力ストリームをスキャンすべきです。可能であれば、割り込み同期文字までのすべての入力を、中断されたプロセスのためにバッファーに入れるべきです。同期文字が見つかったら、ストリームを新たに起動された監視プロセスに切り替えるべきです。ユーザープロセスの入力をすべてバッファーに入れることができない場合は、それを捨てて、監視プロセスがユーザーにエラーメッセージを返してもかまいません。いずれの場合も、未処理の入力が消費され、保留中の文字メッセージを送れるようにメッセージバッファーが解放されることを保証しなければなりません。
  6. 対応するINSより前に割り込み同期文字を受信した場合は、ユーザープロセスを中断し、NCPはINSを待ってから処理を進めるべきです。
  7. 上記の議論におけるNCPの機能は、もちろん、TELNETプロセスなどの別のモジュールに委ねることもできます。そうすれば、NCPはメッセージの内容に対して透過的でいられます。

COMMENTARY

論評

The proposed change to the second level protocol described herein is not meant as a general solution, but rather as a specific patch to the current NCP design with the intent of correcting a critical error. Its more obvious deficiencies are...

ここで述べた第2レベルのプロトコルへの変更案は、一般的な解決策を意図したものではなく、致命的な誤りを正すことを目的とした、現在のNCPの設計に対する特定のパッチです。より明らかな欠点は次のとおりです。

  1. It only works with seven bit code character streams. No extensions are allowed for EBCDIC, ASCII-8, or other large character sets. No provision is made for interrupting a process to which there is no character stream, although the author knows of no case in which the concept means more than closing the connection.
  2. It requires the system to scan all data coming over an interruptable connection. Presumably this means that at the time the connection is created, the receiving host must be told that this scan is to be done. Various techniques, both implicit and explicit, could be used.
  3. The technique is not immune to loss character boundaries within a message nor can it tolerate INS control messages that do not have matching sync characters, or vis versa.
  4. It may not possible to get either the INS or the text message containing the interrupt sync character to a remote host. Possible reasons include user console failure, local host failure, network failure, blocked control link, insufficient allocation etc. Under such circumstances the remote process may loop indefinitely.
  1. 7ビットのコードの文字ストリームでしか機能しません。EBCDIC、ASCII-8、その他の大きな文字セットへの拡張は認められません。文字ストリームのないプロセスに割り込むための規定はありません。ただし、筆者の知る限り、その場合に割り込みという概念がコネクションを閉じること以上の意味を持つ例はありません。
  2. 割り込み可能なコネクションを介して届くすべてのデータを、システムがスキャンする必要があります。おそらくこれは、コネクションを作成する時点で、このスキャンを行うことを受信ホストに伝えなければならないことを意味します。暗黙的なものと明示的なものの両方を含め、さまざまな手法が使えるでしょう。
  3. この手法は、メッセージ内の文字境界が失われることに対処できず、対応する同期文字のないINS制御メッセージや、その逆にも耐えられません。
  4. INSと、割り込み同期文字を含むテキストメッセージのどちらも、リモートホストに届けられないかもしれません。考えられる理由としては、ユーザーのコンソールの障害、ローカルホストの障害、ネットワークの障害、制御リンクのブロック、割り当ての不足などがあります。そのような状況では、リモートプロセスはいつまでもループし続けるかもしれません。

The only comprehensive solution known to the interrupt synchronization problem, those that avoid the above difficulties, require more than minor changes to the current NCP protocol. Unless simpler answers are suggested, their implementation must be postponed until the next major design revision.

割り込みの同期の問題に対して知られている包括的な解決策、つまり上記の困難を回避する解決策は、いずれも現在のNCPプロトコルにわずかな変更を加える以上のものを必要とします。より単純な答えが提案されない限り、その実装は次の大きな設計改訂まで延期せざるをえません。
