RFC 1868

ARP Extension - UNARP

RFC 1868

ARPの拡張 - UNARP

Abstract

概要

The Address Resolution Protocol allows an IP node to determine the hardware (datalink) address of a neighboring node on a broadcast network. The protocol depends on timers to age away old ARP entries. This document specifies a trivial modification to the ARP mechanism, not the packet format, which allows a node to announce that it is leaving the network and that all other nodes should modify their ARP tables accordingly.

アドレス解決プロトコル（Address Resolution Protocol）は、IPノードがブロードキャストネットワーク上の隣接ノードのハードウェア（データリンク）アドレスを決定できるようにします。このプロトコルは、古いARPエントリーを期限切れにするのにタイマーに依存しています。この文書は、ARPのメカニズムに対するささいな変更を規定します（パケット形式は変更しません）。この変更により、ノードはネットワークから離脱することと、ほかのすべてのノードがそれに応じてARPテーブルを変更すべきことを告知できます。

Status of This Memo

このメモのステータス

This memo defines an Experimental Protocol for the Internet community. This memo does not specify an Internet standard of any kind. Discussion and suggestions for improvement are requested. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーのための実験的なプロトコルを定義します。いかなる種類のインターネット標準も規定するものではありません。改善のための議論と提案を求めます。このメモの配布は無制限です。

1. Introduction

1. はじめに

The primary purpose of the Address Resolution Protocol, as defined in [1], is to determine a node's hardware address based on its network address (protocol address in ARPspeak). The ARP protocol specifically states that nodes should not periodically advertise their existence for two reasons: first, this would generate a lot of network traffic and table maintenance overhead; second, it is highly unlikely that all nodes will need to communicate to all other nodes. Since a node does not advertise its existence, neither does it advertise its imminent departure. This is not a serious problem since most ARP implementations maintain timers to age away old entries, and departing nodes seldom depart gracefully in any case.

[1]で定義されているアドレス解決プロトコルの主な目的は、ノードのネットワークアドレス（ARPの用語ではプロトコルアドレス）に基づいて、そのノードのハードウェアアドレスを決定することです。ARPプロトコルは、ノードが自身の存在を定期的に広告すべきではないと明確に述べています。その理由は2つあります。1つ目は、そうするとネットワークのトラフィックとテーブルの維持管理のオーバーヘッドが大量に発生すること、2つ目は、すべてのノードがほかのすべてのノードと通信する必要がある可能性は非常に低いことです。ノードは自身の存在を広告しないので、自身の離脱が差し迫っていることも広告しません。ほとんどのARP実装は古いエントリーを期限切れにするためのタイマーを維持しており、いずれにせよ離脱するノードが行儀よく離脱することはめったにないので、これは深刻な問題ではありません。

Over time, an additional use has been found for ARP: Proxy ARP. While there are those who believe Proxy ARP is an evil thing, it does serve a purpose; that is, it allows for communication in ways never considered in the original IP architecture. For example, allows dial-in hosts to connect to a network without consuming a large amount of the IP address space (i.e., all of the hosts contain addresses on the same subnet, even though they are not directly attached to the physical network associated with that subnet address. It is this use of Proxy ARP which produces the problem addressed by this document.

時が経つにつれ、ARPには追加の用途が見いだされました。Proxy ARPです。Proxy ARPを悪いものだと考える人もいますが、Proxy ARPは目的を果たしています。つまり、元のIPアーキテクチャーでは考慮されていなかった方法での通信を可能にします。たとえば、ダイヤルインのホストが、IPアドレス空間を大量に消費することなくネットワークに接続できるようにします（つまり、すべてのホストが、そのサブネットアドレスに関連付けられた物理ネットワークに直接接続されていなくても、同じサブネット上のアドレスを持ちます）。この文書で扱う問題を生み出すのは、このProxy ARPの使い方です。

2. The Problem

2. 問題

Consider the following topology:

次のトポロジーを考えます。

                 +--------+
                 | Host A |
                 +--------+
                     |
   ======================================== LAN
       |                             |
   +--------+                    +--------+
   |  CS1   |   comm. servers    |  CS2   |
   +--------+                    +--------+
     |    |                        |    |
    +-+  +-+                      +-+  +-+
    | |  | |       modems         | |  | |
    +-+  +-+                      +-+  +-+

                 +--------+
                 | Host A |
                 +--------+
                     |
   ======================================== LAN
       |                             |
   +--------+                    +--------+
   |  CS1   |   comm. servers    |  CS2   |
   +--------+                    +--------+
     |    |                        |    |
    +-+  +-+                      +-+  +-+
    | |  | |       modems         | |  | |
    +-+  +-+                      +-+  +-+

Assume that all of the modems are on the same rotary; that is, when a remote host dials in, it may be assigned a modem on either of the communication servers. Further assume that all of the remote hosts' IP addresses have the same subnet address as the servers and Host A, this in order to conserve address space.

すべてのモデムが同じロータリー（rotary）上にあると仮定します。つまり、リモートホストがダイヤルインすると、どちらの通信サーバーのモデムが割り当てられる可能性もあります。さらに、アドレス空間を節約するために、リモートホストのIPアドレスはすべて、サーバーやHost Aと同じサブネットアドレスを持つと仮定します。

To begin, a remote host dials into CS1 and attempts to communicate with Host A. Host A will assume, based on the subnet mask, that the remote host is actually attached to the LAN and will issue an ARP Request to determine its hardware address. Naturally, the remote host will not hear this request. CS1, knowing this, will respond in the remote host's place with its own hardware address. Host A, on receiving the ARP Reply, will then communicate with the remote host, transparently through CS1. So far everything is just fine.

まず、リモートホストがCS1にダイヤルインし、Host Aと通信しようとします。Host Aは、サブネットマスクに基づいて、リモートホストが実際にLANに接続されていると仮定し、そのハードウェアアドレスを決定するためにARP Requestを発行します。当然、リモートホストにはこのリクエストは聞こえません。CS1はこれを知っているので、リモートホストの代わりに自身のハードウェアアドレスで応答します。Host AはARP Replyを受信すると、CS1を透過的に経由してリモートホストと通信するようになります。ここまでは何も問題ありません。

Now, the remote host disconnects and, before Host A can age its ARP cache, reconnects through CS2. Herein lies the problem. Whenever Host A attempts to send a packet to the remote host, it will send it to CS1 because it cannot know that its ARP cache entry is invalid. If, when the remote host disconnects, the server to which it was attached could inform other nodes on the LAN that the protocol address/hardware address mapping was no longer valid, the problem would not occur.

ここで、リモートホストが切断し、Host AがARPキャッシュを期限切れにする前に、CS2を経由して再接続したとします。ここに問題があります。Host Aは、リモートホストにパケットを送ろうとするたびに、パケットをCS1に送ります。Host Aは、自身のARPキャッシュのエントリーが無効であることを知ることができないからです。リモートホストが切断するときに、そのホストが接続していたサーバーが、プロトコルアドレスとハードウェアアドレスの対応付けがもはや有効ではないことをLAN上のほかのノードに通知できれば、この問題は起こりません。

3. 解決策

注：これは16バイトのパケットです（MACヘッダーを含まない）。

On receiving an UNARP, a node deletes the ARP cache entry associated with the IP address.

UNARPを受信したノードは、そのIPアドレスに関連付けられたARPキャッシュのエントリーを削除します。

It is not strictly necessary that a server keep state information about whether or not it has actually sent a Proxy ARP Reply; it would be sufficient if a server always sends an UNARP when a remote host disconnects.

サーバーが実際にProxy ARP Replyを送信したかどうかについての状態情報を保持することは、厳密には必要ありません。リモートホストが切断したときに、サーバーが常にUNARPを送信すれば十分でしょう。

Of course, there is no reason why a host which gracefully detaches from a LAN cannot also send an UNARP for itself. This would be especially useful if, upon re-attaching, it might have a different hardware address.

もちろん、LANから行儀よく離脱するホストが、自分自身のためにUNARPを送信してはいけない理由はありません。これは、再接続したときに異なるハードウェアアドレスを持つ可能性がある場合に特に役立つでしょう。

4. Backwards Compatibility

4. 後方互換性

The modifications to support UNARP are trivial, so there is every expectation that it will be widely supported. Of course, there will be a period of time during which nodes which support UNARP will coexist with nodes which do not support UNARP. To prevent unenlightened nodes from adding spurious ARP cache entries with hardware addresses of zero, UNARP packets specify a hardware address length of zero. This should be rejected by nodes which do not support UNARP. As a consequence of this, the source and target hardware address fields do not exist in UNARP packets (as previously described).

UNARPをサポートするための変更はささいなものなので、広くサポートされることが大いに期待されます。もちろん、UNARPをサポートするノードとサポートしないノードが共存する期間はあるでしょう。UNARPを知らないノードが、ハードウェアアドレスが0の不正なARPキャッシュのエントリーを追加しないように、UNARPパケットではハードウェアアドレスの長さとして0を指定します。これは、UNARPをサポートしないノードによって拒否されるはずです。その結果、（前述のとおり）UNARPパケットには送信元と宛先のハードウェアアドレスのフィールドが存在しません。

It is recommended that implementors include a configuration switch to disable UNARP in the event that some vendor's ARP implementation might take offense at the abbreviated UNARP packet format.

一部のベンダーのARP実装が省略されたUNARPパケット形式を受け付けない場合に備えて、実装者はUNARPを無効にする設定スイッチを用意することを推奨します。
