RFC 8381

Transparent Interconnection of Lots of Links (TRILL): Vendor-Specific RBridge Channel Protocol

RFC 8381

Transparent Interconnection of Lots of Links（TRILL）：ベンダー固有のRBridgeチャネルプロトコル

Abstract

概要

The IETF TRILL (Transparent Interconnection of Lots of Links) protocol is implemented by devices called TRILL switches or RBridges (Routing Bridges). TRILL includes a general mechanism, called an RBridge Channel, for the transmission of typed messages between RBridges in the same campus and between RBridges and end stations on the same link. This document specifies a method to send vendor-specific messages over the RBridge Channel facility.

IETFのTRILL（Transparent Interconnection of Lots of Links）プロトコルは、TRILLスイッチまたはRBridge（ルーティングブリッジ）と呼ばれるデバイスによって実装されます。TRILLには、同じキャンパス内のRBridge間、および同じリンク上のRBridgeとエンドステーションの間で、型付きメッセージを送信するための、RBridgeチャネルと呼ばれる汎用的なメカニズムが含まれています。この文書は、RBridgeチャネル機能を介してベンダー固有のメッセージを送信する方法を規定します。

1. Introduction

1. はじめに

The IETF TRILL (Transparent Interconnection of Lots of Links) protocol [RFC6325] [RFC7780] is implemented by devices called TRILL switches or RBridges (Routing Bridges). It provides efficient least-cost transparent routing in multi-hop networks with arbitrary topologies and link technologies, using link-state routing and a hop count.

IETFのTRILL（Transparent Interconnection of Lots of Links）プロトコル[RFC6325] [RFC7780]は、TRILLスイッチまたはRBridge（ルーティングブリッジ）と呼ばれるデバイスによって実装されます。TRILLは、リンクステートルーティングとホップカウントを使用して、任意のトポロジーとリンク技術を持つマルチホップネットワークにおいて、効率的な最小コストの透過的ルーティングを提供します。

The TRILL protocol includes an RBridge Channel facility [RFC7178] to support typed message transmission between RBridges in the same campus and between RBridges and end stations on the same link. This document specifies a method of sending messages specified by a particular organization, indicated by OUI (Organizationally Unique Identifier) [RFC7042] or CID (Company Identifier) [802], over the RBridge Channel facility. Such organization-specific messages could, for example, be used for vendor-specific diagnostic or control messages.

TRILLプロトコルには、同じキャンパス内のRBridge間、および同じリンク上のRBridgeとエンドステーションの間での型付きメッセージの送信をサポートするための、RBridgeチャネル機能[RFC7178]が含まれています。この文書は、OUI（Organizationally Unique Identifier、組織固有識別子）[RFC7042]またはCID（Company Identifier、企業識別子）[802]によって示される特定の組織が規定したメッセージを、RBridgeチャネル機能を介して送信する方法を規定します。このような組織固有のメッセージは、たとえば、ベンダー固有の診断メッセージや制御メッセージに使用できます。

However, note that a range of RBridge Channel protocol numbers are available based on RFC publication. Those intending to use the RBridge Channel facility are encouraged to document their use in an RFC and to use RBridge Channel protocol numbers based on such RFC publication.

ただし、RFCの発行に基づいて割り当てられるRBridgeチャネルのプロトコル番号の範囲があることに注意してください。RBridgeチャネル機能を使用しようとする者は、その用途をRFCとして文書化し、そのようなRFCの発行に基づくRBridgeチャネルのプロトコル番号を使用することが推奨されます。

2. ベンダーチャネルのパケット形式

The general structure of an RBridge Channel packet on a link between TRILL switches (RBridges) is shown in Figure 1 below. When an RBridge Channel message is sent between an RBridge and an end station on the same link, in either direction, it is called a Native RBridge Channel message and the TRILL Header (including the Inner Ethernet Addresses and Data Label area) is omitted as shown in Figure 2. The type of RBridge Channel packet is given by a Protocol field in the RBridge Channel Header that indicates how to interpret the Channel-Protocol-Specific Payload. See [RFC7178].

TRILLスイッチ（RBridge）間のリンク上のRBridgeチャネルパケットの一般的な構造を、以下の図1に示します。RBridgeチャネルメッセージが、同じリンク上のRBridgeとエンドステーションの間でいずれかの方向に送信される場合、それはネイティブRBridgeチャネルメッセージと呼ばれ、図2に示すように、TRILLヘッダー（内側イーサネットアドレスとデータラベル領域を含む）は省略されます。RBridgeチャネルパケットの種類は、RBridgeチャネルヘッダー内のProtocolフィールドによって与えられ、このフィールドはチャネルプロトコル固有ペイロード（Channel-Protocol-Specific Payload）をどのように解釈するかを示します。[RFC7178]を参照してください。

Figure 3 below expands the RBridge Channel Header and Channel Protocol Specific Payload above for the case of the Vendor-Specific RBridge Channel Tunnel Protocol. 0x8946 is the Ethertype [RFC7042] assigned by the IEEE for the RBridge Channel protocol.

以下の図3は、ベンダー固有RBridgeチャネルトンネルプロトコルの場合について、上記のRBridgeチャネルヘッダーとチャネルプロトコル固有ペイロードを展開したものです。0x8946は、IEEEがRBridgeチャネルプロトコルに割り当てたEthertype[RFC7042]です。

The fields in Figure 3 related to the Vendor RBridge Channel Protocol are as follows:

図3のフィールドのうち、ベンダーRBridgeチャネルプロトコルに関連するものは次のとおりです。

Channel Protocol:
The RBridge Channel Protocol value allocated for the Vendor Channel (see Section 4).
Vendor ID:

This field indicates the vendor specifying the particular use or uses of the Vendor Channel. The vendor to whom the OUI or CID in this field has been allocated is in charge of specifying Vendor Channel messages using their identifier. Depending on the first byte of this field as follows:

OUI:
When the bottom two bits of the first byte of the Vendor ID are zero (that is, the first byte is 0bXXXXXX00), the Vendor ID is an OUI.
CID:
When the bottom two bits of the first byte are a one followed by a zero (that is, the first byte is 0bXXXXXX10), the Vendor ID is a CID.
Other:
Other values of the bottom two bits of the first byte of the Vendor ID are invalid, and a VERR of 2 MUST be returned, subject to possible rate limiting (see Section 3).
VERR:
Vendor Channel Error. See Section 3.
Sub-Protocol:
Actually, the vendor specifying their use of the Vendor Channel can do whatever they want with the bits after the VERR field. But it is strongly RECOMMENDED that they use the sub-protocol / sub-version fields indicated so that multiple and evolving uses can be specified based on a single OUI.
Sub-Version:
See explanation above of the Sub-Protocol field. This field is provided to indicate the version of the particular vendor's Sub-Protocol.
Channel Protocol:
ベンダーチャネルに割り当てられたRBridgeチャネルプロトコルの値（セクション4を参照）。
Vendor ID:

このフィールドは、ベンダーチャネルの特定の用途を規定するベンダーを示します。このフィールドのOUIまたはCIDが割り当てられたベンダーが、その識別子を使用するベンダーチャネルメッセージを規定する責任を負います。このフィールドの最初のバイトに応じて、次のようになります。

OUI:
Vendor IDの最初のバイトの下位2ビットがゼロである場合（つまり、最初のバイトが0bXXXXXX00である場合）、Vendor IDはOUIです。
CID:
最初のバイトの下位2ビットが1に続いて0である場合（つまり、最初のバイトが0bXXXXXX10である場合）、Vendor IDはCIDです。
Other:
Vendor IDの最初のバイトの下位2ビットがそれ以外の値である場合は無効であり、レート制限が行われる可能性はあるものの（セクション3を参照）、VERRを2として返さなければなりません（MUST）。
VERR:
ベンダーチャネルエラー（Vendor Channel Error）。セクション3を参照してください。
Sub-Protocol:
実際のところ、ベンダーチャネルの用途を規定するベンダーは、VERRフィールドより後ろのビットを自由に扱うことができます。しかし、単一のOUIに基づいて複数の用途や進化していく用途を規定できるように、ここで示したサブプロトコル／サブバージョンのフィールドを使用することが強く推奨されます（RECOMMENDED）。
Sub-Version:
上記のSub-Protocolフィールドの説明を参照してください。このフィールドは、特定のベンダーのサブプロトコルのバージョンを示すために用意されています。

3. Vendor Channel Errors

3. ベンダーチャネルのエラー

The VERR field values from 0x0 through 0x0F (inclusive) and the value 0xFF are reserved for specification by the IETF. See Section 4. All other values of VERR are available for whatever use the vendor specifies, except that a Vendor Channel implementation MUST NOT send a Vendor Channel Error in response to a Vendor Channel message with a nonzero VERR.

VERRフィールドの値のうち、0x0から0x0Fまで（両端を含む）と値0xFFは、IETFによる規定のために予約されています。セクション4を参照してください。VERRのそれ以外の値はすべて、ベンダーが規定する任意の用途に使用できます。ただし、ベンダーチャネルの実装は、ゼロ以外のVERRを持つベンダーチャネルメッセージへの応答としてベンダーチャネルエラーを送信してはなりません（MUST NOT）。

The VERR values thus far specified by the IETF are as follows:

これまでにIETFによって規定されたVERRの値は、次のとおりです。

  1. The VERR field is zero in Vendor Channel messages unless the Vendor Channel packet is reporting an error.
  2. The value one indicates that the length of the RBridge-Channel-Specific Data is less than 4 bytes. This means that at least the VERR byte and possibly part or all of the OUI is truncated. If an RBridge that implements the Vendor Channel facility receives such a Vendor Channel message, it MUST expand it to extend through the VERR field, set that field to one, and return the packet as described in Section 3.1.
  3. The OUI/CID field value is unknown. If an RBridge implements the Vendor Channel facility and receives a Vendor Channel packet with a zero VERR field and an OUI/CID field it does not recognize and the SL flag is zero in the RBridge Channel Header, it MUST set the VERR field to the value two and return the packet as described in Section 3.1.

  4. The value 3 indicates that the Sub-Protocol field value is unknown. An RBridge SHOULD set the VERR field to 3 and return the packet as described in Section 3.1 if it implements the Vendor Channel facility and it receives a Vendor Channel packet meeting the following conditions:

    1. a zero VERR field in the RBridge Channel Header,
    2. a zero SL flag in the RBridge Channel Header,
    3. an OUI/CID that it implements, and
    4. a Sub-Protocol field value it does not recognize even though it implements and uses the Sub-Protocol field.

  5. The value 4 indicates that the Sub-Version field value is unknown. An RBridge SHOULD set the VERR field to 4 and return the packet as described in Section 3.1 if it implements the Vendor RBridge Channel facility and it receives a Vendor Channel packet meeting the following conditions:

    1. a zero VERR field in the RBridge Channel Header,
    2. a zero SL flag in the RBridge Channel Header,
    3. an OUI/CID and Sub-Protocol that it implements, and
    4. a Sub-Version field value it does not recognize even though it implements and uses the Sub-Version field.
  1. ベンダーチャネルパケットがエラーを報告している場合を除き、ベンダーチャネルメッセージのVERRフィールドはゼロです。
  2. 値1は、RBridgeチャネル固有データ（RBridge-Channel-Specific Data）の長さが4バイト未満であることを示します。これは、少なくともVERRバイトが切り詰められており、場合によってはOUIの一部または全部も切り詰められていることを意味します。ベンダーチャネル機能を実装しているRBridgeがそのようなベンダーチャネルメッセージを受信した場合、そのメッセージをVERRフィールドまで延長し、そのフィールドを1に設定して、セクション3.1で説明するようにパケットを返さなければなりません（MUST）。
  3. OUI/CIDフィールドの値が未知です。RBridgeがベンダーチャネル機能を実装しており、VERRフィールドがゼロで、認識できないOUI/CIDフィールドを持ち、RBridgeチャネルヘッダーのSLフラグがゼロであるベンダーチャネルパケットを受信した場合、VERRフィールドを値2に設定して、セクション3.1で説明するようにパケットを返さなければなりません（MUST）。

  4. 値3は、Sub-Protocolフィールドの値が未知であることを示します。RBridgeがベンダーチャネル機能を実装しており、次の条件を満たすベンダーチャネルパケットを受信した場合、そのRBridgeはVERRフィールドを3に設定して、セクション3.1で説明するようにパケットを返すべきです（SHOULD）。

    1. RBridgeチャネルヘッダーのVERRフィールドがゼロである
    2. RBridgeチャネルヘッダーのSLフラグがゼロである
    3. そのRBridgeが実装しているOUI/CIDである
    4. そのRBridgeがSub-Protocolフィールドを実装して使用しているにもかかわらず、認識できないSub-Protocolフィールドの値である

  5. 値4は、Sub-Versionフィールドの値が未知であることを示します。RBridgeがベンダーRBridgeチャネル機能を実装しており、次の条件を満たすベンダーチャネルパケットを受信した場合、そのRBridgeはVERRフィールドを4に設定して、セクション3.1で説明するようにパケットを返すべきです（SHOULD）。

    1. RBridgeチャネルヘッダーのVERRフィールドがゼロである
    2. RBridgeチャネルヘッダーのSLフラグがゼロである
    3. そのRBridgeが実装しているOUI/CIDとサブプロトコルである
    4. そのRBridgeがSub-Versionフィールドを実装して使用しているにもかかわらず、認識できないSub-Versionフィールドの値である

Uniform error handling is generally advisable for the sake of maintenance and understandability; however, "SHOULD" is chosen for errors 3 and 4 above because, as long as each message is distinguished by a vendor's OUI/CID, it is up to that vendor to decide between standard and nonstandard error handling.

保守性と理解しやすさのために、一般的には統一的なエラー処理が望ましいです。しかし、上記のエラー3と4については「すべきです（SHOULD）」を選択しています。なぜなら、各メッセージがベンダーのOUI/CIDによって区別される限り、標準的なエラー処理と非標準的なエラー処理のどちらにするかは、そのベンダーが決めることだからです。

3.1. Sending an Error Response

3.1. エラーレスポンスの送信

The IETF-specified Vendor Channel errors are sent in response to a received RBridge Channel packet by setting the VERR field as specified above and modifying the packet as specified below. (The ERR field will be zero because, if it were nonzero, the packet would have been handled at the general RBridge Channel level rather than being passed down to the Vendor Channel level.)

IETFが規定したベンダーチャネルエラーは、受信したRBridgeチャネルパケットに対して、上記のとおりVERRフィールドを設定し、以下のとおりパケットを変更することによって、応答として送信されます。（ERRフィールドはゼロになります。なぜなら、ゼロ以外であれば、そのパケットはベンダーチャネルのレベルに渡されるのではなく、一般的なRBridgeチャネルのレベルで処理されていたはずだからです。）

The RBridge Channel Header is modified by setting the SL flag. (The flags in the Channel Header and the semantics of the SL flag are specified in [RFC7178].)

RBridgeチャネルヘッダーは、SLフラグを設定することによって変更されます。（チャネルヘッダーのフラグとSLフラグのセマンティクスは、[RFC7178]で規定されています。）

  • If an error 1 is being generated because of truncation, the RBridge-Channel-Specific Data area is extended to include the VERR byte.
  • If a Vendor Channel message was sent between RBridges, the TRILL Header is modified by (1) clearing the M bit, (2) setting the egress nickname to the ingress nickname as received, (3) setting the ingress nickname to a nickname held by the TRILL switch sending the error packet, and (4) setting the hop count to the usual value on TRILL Data packets used by the TRILL switch sending the error packet.
  • If a Vendor Channel message was sent between an RBridge and an end station in either direction, the outer MAC addresses are modified by (1) setting the Outer.MacDA to the Outer.MacSA as received and (2) setting the Outer.MacSA to the MAC address of the port of the TRILL switch or end station sending the error packet.
  • The priority of the error response message MAY be reduced from the priority of the Vendor Chanel message causing the error, unless it was already minimum priority, and the Drop Eligibility Indicator bit MAY be set in an error response. (See Section 4.1.1 of [RFC6325].)
  • Vendor Channel error responses MAY be rate-limited.
  • 切り詰めのためにエラー1を生成する場合は、RBridgeチャネル固有データの領域を、VERRバイトを含むように延長します。
  • ベンダーチャネルメッセージがRBridge間で送信された場合は、TRILLヘッダーを次のように変更します。(1) Mビットをクリアする、(2) 出口ニックネームを受信した入口ニックネームに設定する、(3) 入口ニックネームを、エラーパケットを送信するTRILLスイッチが保持するニックネームに設定する、(4) ホップカウントを、エラーパケットを送信するTRILLスイッチがTRILLデータパケットで使用する通常の値に設定する。
  • ベンダーチャネルメッセージがRBridgeとエンドステーションの間でいずれかの方向に送信された場合は、外側のMACアドレスを次のように変更します。(1) Outer.MacDAを受信したOuter.MacSAに設定する、(2) Outer.MacSAを、エラーパケットを送信するTRILLスイッチまたはエンドステーションのポートのMACアドレスに設定する。
  • エラーレスポンスメッセージの優先度は、すでに最低優先度である場合を除き、エラーの原因となったベンダーチャネルメッセージの優先度よりも下げてもよいです（MAY）。また、エラーレスポンスでは、Drop Eligibility Indicatorビットを設定してもよいです（MAY）。（[RFC6325]のセクション4.1.1を参照してください。）
  • ベンダーチャネルのエラーレスポンスにはレート制限をかけてもよいです（MAY）。

It is generally anticipated that the entire packet in which an error was detected would be sent back, modified as above, as the protocol specific payload, so that, for example, error responses could more easily be matched with messages sent; however, except for errors 1 and 2, this is up to the vendor specifying how their Vendor RBridge Channel messages are to be used.

一般的には、エラーが検出されたパケット全体を、上記のとおり変更したうえで、プロトコル固有ペイロードとして送り返すことが想定されています。そうすることで、たとえば、エラーレスポンスを送信したメッセージとより簡単に照合できるようになります。ただし、エラー1と2を除き、これはベンダーRBridgeチャネルメッセージの使用方法を規定するベンダーに委ねられます。

Note that if you receive a Vendor Channel error message with error 1, indicating a truncation error, you cannot trust the apparent "OUI/CID" in that Vendor Channel error message.

切り詰めエラーを示すエラー1のベンダーチャネルエラーメッセージを受信した場合、そのベンダーチャネルエラーメッセージ内の見かけ上の「OUI/CID」は信頼できないことに注意してください。

5. Security Considerations

5. セキュリティーに関する考慮事項

See [RFC6325] for general TRILL Security Considerations.

TRILLのセキュリティーに関する一般的な考慮事項については、[RFC6325]を参照してください。

See [RFC7178] for general RBridge Channel Security Considerations.

RBridgeチャネルのセキュリティーに関する一般的な考慮事項については、[RFC7178]を参照してください。

Neither the Vendor-Specific RBridge Channel Protocol nor the basic RBridge Channel Protocol [RFC7178] provide any security assurances or features. (The basic RBridge Channel Protocol's first use was as an envelope for Bidirectional Forwarding Detection (BFD) messages [RFC7175], which provide their own security.) Any needed security can be provided by fields or processing within the Vendor-Protocol-Specific Data, which is outside the scope of this document. Alternatively or in addition, use of a Vendor Channel MAY be nested inside the RBridge Channel Header Extension Protocol [RFC7978]; this can provide some security services.

ベンダー固有RBridgeチャネルプロトコルも、基本的なRBridgeチャネルプロトコル[RFC7178]も、セキュリティーの保証や機能を何も提供しません。（基本的なRBridgeチャネルプロトコルが最初に使用されたのは、双方向フォワーディング検出（Bidirectional Forwarding Detection: BFD）メッセージ[RFC7175]のエンベロープとしてであり、BFDメッセージは独自のセキュリティーを提供します。）必要なセキュリティーは、ベンダープロトコル固有データ（Vendor-Protocol-Specific Data）内のフィールドや処理によって提供できますが、それはこの文書の範囲外です。その代わりに、またはそれに加えて、ベンダーチャネルの使用をRBridgeチャネルヘッダー拡張プロトコル[RFC7978]の内側に入れ子にしてもよいです（MAY）。これにより、いくつかのセキュリティーサービスを提供できます。
