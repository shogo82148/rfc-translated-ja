RFC 8178

Rules for NFSv4 Extensions and Minor Versions

RFC 8178

NFSv4の拡張とマイナーバージョンに関する規則

Abstract

概要

This document describes the rules relating to the extension of the NFSv4 family of protocols. It covers the creation of minor versions, the addition of optional features to existing minor versions, and the correction of flaws in features already published as Proposed Standards. The rules relating to the construction of minor versions and the interaction of minor version implementations that appear in this document supersede the minor versioning rules in RFC 5661 and other RFCs defining minor versions.

この文書は、NFSv4プロトコルファミリーの拡張に関する規則を記述します。この文書は、マイナーバージョンの作成、既存のマイナーバージョンへの任意の機能の追加、およびすでに提案標準（Proposed Standard）として公開されている機能の欠陥の修正を扱います。この文書に記載されているマイナーバージョンの構築とマイナーバージョン実装間の相互作用に関する規則は、RFC 5661およびマイナーバージョンを定義するその他のRFCにあるマイナーバージョニング規則に優先します。

1. Introduction

1. はじめに

To address the requirement for an NFS protocol that can evolve as the need arises, the Network File System (NFS) version 4 (NFSv4) protocol provides a framework to allow for future changes via the creation of new protocol versions, including minor versions and certain forms of modification of existing minor versions. The extension rules contained in this document allow extensions and other changes to be implemented in a way that maintains compatibility with existing clients and servers.

必要に応じて進化できるNFSプロトコルという要件に対応するため、Network File System（NFS）バージョン4（NFSv4）プロトコルは、マイナーバージョンや既存のマイナーバージョンに対する特定の形式の変更を含む、新しいプロトコルバージョンの作成によって将来の変更を可能にするフレームワークを提供します。この文書に含まれる拡張規則により、既存のクライアントおよびサーバーとの互換性を維持する方法で、拡張やその他の変更を実装できるようになります。

Previously, all protocol changes had been part of new minor versions. The COMPOUND procedure (see Section 14.2 of [RFC7530]) specifies the minor version being used by the client in making requests. The CB_COMPOUND procedure (see Section 15.2 of [RFC7530]) specifies the minor version being used by the server on callback requests.

以前は、プロトコルの変更はすべて新しいマイナーバージョンの一部でした。COMPOUNDプロシージャー（[RFC7530]のセクション14.2を参照）は、クライアントがリクエストを行う際に使用するマイナーバージョンを指定します。CB_COMPOUNDプロシージャー（[RFC7530]のセクション15.2を参照）は、サーバーがコールバックリクエストで使用するマイナーバージョンを指定します。

Creation of a new minor version is no longer the only way in which protocol changes may be made. Optional features may be added as extensions and protocol corrections can be proposed, specified, and implemented within the context of a single minor version. Creation of new minor versions remains available when needed.

新しいマイナーバージョンの作成は、もはやプロトコルを変更できる唯一の方法ではありません。任意の機能を拡張として追加でき、プロトコルの修正を単一のマイナーバージョンの文脈の中で提案、規定、実装できます。必要な場合には、新しいマイナーバージョンを作成することも引き続き可能です。

The goal of allowing extensions within the context of a minor version is to provide more implementation flexibility while preserving interoperability on protocol upgrade. As described in Section 4.4, a client and server may each choose a subset of available extensions. Each party can successfully use a subset of protocol elements that are known to and supported by both the client and server. Support for this common subset is not affected by the fact that extensions outside this common subset may be supported by the server or potentially used by the client.

マイナーバージョンの文脈の中で拡張を許可する目的は、プロトコルのアップグレード時の相互運用性を維持しつつ、実装の柔軟性を高めることです。セクション4.4で説明するように、クライアントとサーバーはそれぞれ、利用可能な拡張のサブセットを選択できます。各当事者は、クライアントとサーバーの両方が知っていて、かつ両方がサポートしているプロトコル要素のサブセットを問題なく使用できます。この共通のサブセットのサポートは、この共通のサブセットの外にある拡張がサーバーによってサポートされていたり、クライアントによって使用される可能性があったりすることの影響を受けません。

2. Terminology

2. 用語

A basic familiarity with NFSv4 terminology is assumed in this document and the reader is pointed to [RFC7530].

この文書は、NFSv4の用語の基本的な知識があることを前提としており、読者には[RFC7530]を参照していただきます。

In this document, the term "version" is not limited to minor versions. When minor versions are meant, the term "minor version" is used explicitly. For more discussion of this and related terms, see Section 2.3.

この文書では、「バージョン（version）」という用語はマイナーバージョンに限定されません。マイナーバージョンを意味する場合は、「マイナーバージョン（minor version）」という用語を明示的に使用します。この用語や関連する用語に関する詳細な議論については、セクション2.3を参照してください。

A "feature package" is a set of features that are defined together, either as part of a minor version or as part of the same protocol extension.

「機能パッケージ（feature package）」とは、マイナーバージョンの一部として、または同じプロトコル拡張の一部として、一緒に定義される機能の集合です。

2.1. Use of Keywords Defined in RFCs 2119 and 8174

2.1. RFC 2119とRFC 8174で定義されたキーワードの使用

The keywords defined by [RFC2119] [RFC8174] have special meanings that this document intends to adhere to. However, due to the nature of this document and some special circumstances, there are some complexities to take note of:

[RFC2119] [RFC8174]で定義されたキーワードには特別な意味があり、この文書はそれに従うことを意図しています。ただし、この文書の性質といくつかの特別な事情により、注意すべき複雑な点がいくつかあります。

  • Where this document does not directly specify implementation requirements, use of these capitalized terms is often not appropriate since the guidance given in this document does not directly affect interoperability.

  • In this document, what authors of RFCs defining features and minor versions need to do is stated without these specialized terms. Although it is necessary to follow this guidance to provide successful NFSv4 protocol extension, that sort of necessity is not of the sort defined as applicable to the use of the keywords defined in [RFC2119] [RFC8174].

    The fact that these capitalized terms are not used should not be interpreted as indicating that this guidance does not need to be followed or is somehow not important.

  • In speaking of the possible statuses of features and feature elements, the terms "OPTIONAL" and "REQUIRED" are used. For further discussion, see Section 2.2.
  • When one of these upper-case keywords defined in [RFC2119] [RFC8174] is used in this document, it is in the context of a rule directed to an implementer of NFSv4 minor versions, the status of a feature or protocol element, or in a quotation, sometimes indirect, from another document.
  • この文書が実装要件を直接規定していない箇所では、これらの大文字の用語を使用することは多くの場合適切ではありません。この文書で示すガイダンスは相互運用性に直接影響しないためです。

  • この文書では、機能やマイナーバージョンを定義するRFCの著者が行う必要があることを、これらの特別な用語を使わずに述べています。NFSv4プロトコルの拡張を成功させるためにはこのガイダンスに従う必要がありますが、その種の必要性は、[RFC2119] [RFC8174]で定義されたキーワードの使用に当てはまるものとして定義されている種類の必要性ではありません。

    これらの大文字の用語が使われていないことを、このガイダンスに従う必要がない、あるいはなんらかの意味で重要でないことを示していると解釈すべきではありません。

  • 機能や機能要素のとりうるステータスについて述べる際には、「選択できます（OPTIONAL）」と「要求されています（REQUIRED）」という用語を使用します。詳しい議論については、セクション2.2を参照してください。
  • [RFC2119] [RFC8174]で定義されたこれらの大文字のキーワードのいずれかがこの文書で使われる場合、それは、NFSv4マイナーバージョンの実装者に向けた規則、機能やプロトコル要素のステータス、あるいは別の文書からの（ときに間接的な）引用という文脈においてです。

2.2. Use of Feature Statuses

2.2. 機能ステータスの使用

There has been some confusion during the history of NFSv4 about the correct use of these terms, and instances in which the keywords defined in [RFC2119] [RFC8174] were used in ways that appear to be at variance with the definitions in that document.

NFSv4の歴史の中では、これらの用語の正しい使い方について混乱があり、[RFC2119] [RFC8174]で定義されたキーワードが、その文書の定義と食い違っているように見える方法で使われた例もありました。

  • In [RFC3530], the lower-case terms "optional", "recommended", and "required" were used as feature statuses, Later, in [RFC5661] and [RFC7530], the corresponding upper-case keywords were used. It is not clear why this change was made.
  • In the case of "RECOMMENDED", its use as a feature status is inconsistent with [RFC2119] [RFC8174] and it will not be used for this purpose in this document.
  • The word "RECOMMENDED" to denote the status of attributes in [RFC7530] and [RFC5661] raises similar issues. This has been recognized in [RFC7530] with regard to NFSV4.0, although the situation with regard to NFSv4.1 remains unresolved.
  • [RFC3530]では、小文字の用語「optional」、「recommended」、「required」が機能ステータスとして使われていました。その後、[RFC5661]と[RFC7530]では、対応する大文字のキーワードが使われました。なぜこの変更が行われたのかは明らかではありません。
  • 「推奨されます（RECOMMENDED）」の場合、それを機能ステータスとして使うことは[RFC2119] [RFC8174]と矛盾するため、この文書ではこの目的には使用しません。
  • [RFC7530]と[RFC5661]で属性のステータスを表すために「推奨されます（RECOMMENDED）」という語を使っていることも、同様の問題を引き起こします。このことはNFSV4.0については[RFC7530]で認識されていますが、NFSv4.1に関する状況は未解決のままです。

In this document, the keywords "OPTIONAL" and "REQUIRED" and the phrase "mandatory to not implement" are used to denote the status of features within a given minor version. In using these terms, RFCs that specify the status of features inform:

この文書では、キーワード「選択できます（OPTIONAL）」と「要求されています（REQUIRED）」、および「実装しないことが必須（mandatory to not implement）」という語句を、特定のマイナーバージョン内での機能のステータスを表すために使用します。これらの用語を使うことで、機能のステータスを規定するRFCは次のことを伝えます。

  • client implementations whether they need to deal with the absence of support for these features.
  • server implementations whether they need to provide support for these features.
  • クライアント実装に対しては、これらの機能がサポートされていない場合に対処する必要があるかどうか。
  • サーバー実装に対しては、これらの機能のサポートを提供する必要があるかどうか。

2.3. NFSv4 Versions

2.3. NFSv4のバージョン

The term "version" denotes any valid protocol variant constructed according to the rules in this document. It includes minor versions, but there are situations that allow multiple variant versions to be associated with and coexist within a single minor version:

「バージョン（version）」という用語は、この文書の規則に従って構築された有効なプロトコルのバリアント（variant）を表します。これにはマイナーバージョンが含まれますが、単一のマイナーバージョンに複数のバリアントのバージョンが関連付けられ、その中で共存できる状況もあります。

  • When there are feature specification documents published as Proposed Standards extending a given minor version, then the protocol defined by the minor version specification document, when combined with any subset (not necessarily a proper subset) of the feature specification documents, is a valid NFSv4 version variant that is part of the minor version in question.
  • When there are protocol corrections published that update a given minor version, each set of published updates, up to the date of publication of the update, is a valid NFSv4 version variant that is part of the minor version in question.
  • 特定のマイナーバージョンを拡張する機能仕様文書が提案標準として公開されている場合、マイナーバージョン仕様文書で定義されたプロトコルに、それらの機能仕様文書の任意のサブセット（真部分集合である必要はありません）を組み合わせたものは、当該マイナーバージョンの一部である有効なNFSv4のバージョンのバリアントです。
  • 特定のマイナーバージョンを更新するプロトコルの修正が公開されている場合、ある更新の公開日までに公開された更新の各集合は、当該マイナーバージョンの一部である有効なNFSv4のバージョンのバリアントです。

Because of the above, there can be multiple version variants that are part of a given minor version. Two of these are worthy of special terms:

以上のことから、特定のマイナーバージョンの一部であるバージョンのバリアントは複数存在し得ます。そのうちの2つは特別な用語に値します。

  • The term "base minor version" denotes the version variant that corresponds to the minor version as originally defined, including all protocol elements specified in the minor version definition document but not incorporating any extensions or protocol corrections published after that original definition.
  • At any given time, the term "current minor version" denotes the minor version variant including all extensions of and corrections to the minor version made by Standards Track documents published up to that time.
  • 「基本マイナーバージョン（base minor version）」という用語は、当初定義されたとおりのマイナーバージョンに対応するバージョンのバリアントを表します。これには、マイナーバージョン定義文書で規定されたすべてのプロトコル要素が含まれますが、その当初の定義の後に公開された拡張やプロトコルの修正は一切取り込まれません。
  • ある時点において、「現在のマイナーバージョン（current minor version）」という用語は、その時点までに公開された標準化過程の文書によって行われた、そのマイナーバージョンのすべての拡張と修正を含むマイナーバージョンのバリアントを表します。

Each client and server that implements a specific minor version will implement some particular variant of that minor version. Each variant is a subset of the current minor version and a superset of the base minor version. When the term "minor version" is used without either of these qualifiers, it should refer to something that is true of all variants within that minor version. For example, in the case of a minor version that has not had a protocol correction, one may refer to the set of REQUIRED features for that minor version since it is the same for all variants within the minor version. See Section 9 for a discussion of correcting an existing minor version.

特定のマイナーバージョンを実装する各クライアントとサーバーは、そのマイナーバージョンのなんらかの特定のバリアントを実装することになります。各バリアントは、現在のマイナーバージョンのサブセットであり、基本マイナーバージョンのスーパーセットです。「マイナーバージョン」という用語がこれらの修飾語のどちらも付けずに使われる場合、それはそのマイナーバージョン内のすべてのバリアントに当てはまるものを指すべきです。たとえば、プロトコルの修正を受けていないマイナーバージョンの場合、そのマイナーバージョンの「要求されています（REQUIRED）」機能の集合について言及できます。それはそのマイナーバージョン内のすべてのバリアントで同じだからです。既存のマイナーバージョンの修正に関する議論については、セクション9を参照してください。

3. Consolidation of Extension Rules

3. 拡張規則の統合

In the past, the only existing extension rules were the minor versioning rules that were being maintained and specified in the Standards Track RFCs, which defined the individual minor versions. In the past, these minor versioning rules were modified on an ad hoc basis for each new minor version.

これまで、存在していた拡張規則は、個々のマイナーバージョンを定義した標準化過程のRFCの中で維持・規定されていたマイナーバージョニング規則だけでした。これまでは、これらのマイナーバージョニング規則は、新しいマイナーバージョンごとに場当たり的に変更されていました。

More recently, minor versioning rules were specified in [RFC5661] while modifications to those rules were allowed in subsequent minor versions.

より最近では、マイナーバージョニング規則は[RFC5661]で規定され、その規則に対する変更は後続のマイナーバージョンで許可されていました。

This document defines a set of extension rules, including rules for minor version construction. These rules apply to all future changes to the NFSv4 protocol. The rules are subject to change but any such change should be part of a Standards Track RFC obsoleting or updating this document.

この文書は、マイナーバージョンの構築に関する規則を含む、一連の拡張規則を定義します。これらの規則は、NFSv4プロトコルに対する将来のすべての変更に適用されます。これらの規則は変更される可能性がありますが、そのような変更は、この文書を廃止または更新する標準化過程のRFCの一部として行われるべきです。

Rather than a single list of extension rules, as was done in the minor versioning rules in [RFC5661], this document defines multiple sets of rules that deal with the various forms of protocol change provided for in the NFSv4 extension framework.

[RFC5661]のマイナーバージョニング規則で行われたような拡張規則の単一のリストではなく、この文書では、NFSv4拡張フレームワークで提供されるさまざまな形式のプロトコル変更を扱う複数の規則の集合を定義します。

  • The kinds of changes in External Data Representation (XDR) definitions that may be made to extend NFSv4 are addressed in the rules in Section 4.2.
  • Minor version construction, including rules applicable to changes that cannot be made in extensions to existing minor versions are addressed in Section 7.1.
  • Minor version interaction rules are discussed in Sections 8.1 and 8.2.
  • NFSv4を拡張するために行ってもよい外部データ表現（External Data Representation、XDR）の定義の変更の種類は、セクション4.2の規則で扱います。
  • 既存のマイナーバージョンに対する拡張では行えない変更に適用される規則を含む、マイナーバージョンの構築については、セクション7.1で扱います。
  • マイナーバージョンの相互作用の規則については、セクション8.1と8.2で議論します。

この文書は、[RFC5661]にあるものを含むマイナーバージョン仕様のRFCに記載されたマイナーバージョニング規則と、[RFC7862]で言及されたそれらの規則の変更にも優先します。その結果、文書間で生じ得る矛盾は次のように対処すべきです。

4. XDR Considerations

4. XDRに関する考慮事項

As an extensible XDR-based protocol, NFSv4 has to ensure inter-version compatibility in situations in which the client and server use different XDR descriptions. For example, the client and server may implement different variants of the same minor version, in that they each might add different sets of extensions to the base minor version.

XDRに基づく拡張可能なプロトコルとして、NFSv4は、クライアントとサーバーが異なるXDR記述を使用する状況でもバージョン間の互換性を確保しなければなりません。たとえば、クライアントとサーバーは、それぞれが基本マイナーバージョンに異なる拡張の集合を追加しているという点で、同じマイナーバージョンの異なるバリアントを実装しているかもしれません。

The XDR extension paradigm, discussed in Section 4.1, assures that these descriptions are compatible, with clients and servers able to determine and use those portions of the protocol that they both share according to the method described in Section 4.4.2.

セクション4.1で議論するXDR拡張のパラダイムは、これらの記述に互換性があることを保証し、クライアントとサーバーは、セクション4.4.2で説明する方法に従って、両者が共有するプロトコルの部分を判断して使用できます。

4.1. XDR Extension

4.1. XDR拡張

When an NFSv4 version change requires a modification to the protocol XDR, this is effected within a framework based on the idea of XDR extension. This is in contrast to transitions between major NFS versions (including that between NFSv3 and NFSv4.0) in which the XDR for one version was replaced by a different XDR for a newer version.

NFSv4のバージョンの変更でプロトコルのXDRの修正が必要な場合、それはXDR拡張という考え方に基づくフレームワークの中で行われます。これは、あるバージョンのXDRがより新しいバージョンの別のXDRに置き換えられた、NFSのメジャーバージョン間の移行（NFSv3とNFSv4.0の間の移行を含む）とは対照的です。

The XDR extension approach allows an XDR description to be extended in a way that retains the structure of all previously valid messages. If a base XDR description is extended to create a second XDR description, the following will be true for the second description to be a valid extension of the first:

XDR拡張のアプローチでは、以前に有効だったすべてのメッセージの構造を保持する方法でXDR記述を拡張できます。基本となるXDR記述を拡張して2つ目のXDR記述を作成する場合、2つ目の記述が1つ目の記述の有効な拡張であるためには、次のことが成り立ちます。

  • The set of valid messages described by the extended definition is a superset of that described by the first.
  • Each message within the set of valid messages described by the base definition is recognized as having exactly the same structure/interpretation using the extended definition.
  • Each message within the set of messages described as valid by the extended definition but not the base definition must be recognized, using the base definition, as part of an unknown extension.
  • 拡張された定義によって記述される有効なメッセージの集合は、1つ目の定義によって記述されるもののスーパーセットです。
  • 基本の定義によって記述される有効なメッセージの集合内の各メッセージは、拡張された定義を使用しても、まったく同じ構造・解釈を持つものとして認識されます。
  • 拡張された定義では有効と記述されるが基本の定義では有効と記述されないメッセージの集合内の各メッセージは、基本の定義を使用すると、未知の拡張の一部として認識されなければなりません。

The use of XDR extension can facilitate compatibility between different versions of the NFSv4 protocol. When XDR extension is used to implement OPTIONAL features, the greatest degree of inter-version compatibility is obtained. In this case, as long as the rules in Section 6 are followed, no change in minor version number is needed and the extension may be effected in the context of a single minor version.

XDR拡張を使用すると、NFSv4プロトコルの異なるバージョン間の互換性を促進できます。XDR拡張を使用して選択可能な（OPTIONAL）機能を実装する場合に、最大限のバージョン間の互換性が得られます。この場合、セクション6の規則に従う限り、マイナーバージョン番号の変更は必要なく、拡張は単一のマイナーバージョンの文脈の中で行えます。

4.2. Rules for XDR Extension within NFSv4

4.2. NFSv4におけるXDR拡張の規則

In the context of NFSv4, given the central role of COMPOUND and CB_COMPOUND, addition of new RPC procedures is not allowed and the enumeration of operations and callback operations have a special role.

NFSv4の文脈では、COMPOUNDとCB_COMPOUNDが中心的な役割を担っていることから、新しいRPCプロシージャーの追加は許可されず、操作とコールバック操作の列挙が特別な役割を持ちます。

The following XDR extensions, by their nature, affect both messages sent by requesters (i.e., requests and callbacks), and responders (i.e., replies and callback replies).

次のXDR拡張は、その性質上、リクエスター（requester）が送信するメッセージ（つまりリクエストとコールバック）と、レスポンダー（responder）が送信するメッセージ（つまりリプライとコールバックリプライ）の両方に影響します。

  • Addition of previously unspecified operation codes, within the framework established by COMPOUND and CB_COMPOUND. These extend the appropriate enumeration and the corresponding switches devoted to requests and responses for the associated direction of operation.
  • Addition of previously unspecified attributes. These add additional numeric constants that define each attribute's bit position within the attribute bitmap, together with XDR typedefs that specify the attributes' format within the nominally opaque arrays specifying sets of attributes.
  • COMPOUNDとCB_COMPOUNDによって確立されたフレームワークの中での、以前は規定されていなかった操作コードの追加。これらは、該当する列挙と、関連する操作方向のリクエストとレスポンスに充てられた対応するswitchを拡張します。
  • 以前は規定されていなかった属性の追加。これらは、属性のビットマップ内での各属性のビット位置を定義する数値定数を追加するとともに、属性の集合を指定する名目上は不透明な配列の中での属性の形式を規定するXDRのtypedefを追加します。

Other sorts of changes will generally affect one of requests, replies, callback, or callback replies. Although all are valid XDR extensions, the messages that are affected may determine whether the extension requires a new minor version (see Section 7) or can be made as an extension within an existing minor version (see Section 6).

その他の種類の変更は、一般にリクエスト、リプライ、コールバック、コールバックリプライのいずれか1つに影響します。それらはすべて有効なXDR拡張ですが、影響を受けるメッセージによって、その拡張に新しいマイナーバージョンが必要か（セクション7を参照）、既存のマイナーバージョン内の拡張として行えるか（セクション6を参照）が決まることがあります。

  • Addition of new, previously unused, values to existing enums.
  • Addition of previously unassigned bit values to a flag word.
  • Addition of new cases to existing switches, provided that the existing switch did not contain a default case.
  • 既存のenumに対する、以前は使われていなかった新しい値の追加。
  • フラグワードに対する、以前は割り当てられていなかったビット値の追加。
  • 既存のswitchに対する新しいケースの追加。ただし、既存のswitchにdefaultケースが含まれていなかった場合に限ります。

None of the following is allowed to happen:

次のことはいずれも許可されません。

  • Any change to the structure of existing requests or replies other than those listed above.
  • Addition of previously unspecified RPC procedures for either the NFSv4 program or the callback program.
  • Deletion of existing RPC procedures, operation codes, enum values, flag bit values, and switch cases. Note that changes may be made to define use of any of these as causing an error, as long as the XDR is unaffected. Similarly, none of these items may be reused for a new purpose.
  • 上記に挙げたもの以外の、既存のリクエストやリプライの構造に対する変更。
  • NFSv4プログラムまたはコールバックプログラムのいずれかに対する、以前は規定されていなかったRPCプロシージャーの追加。
  • 既存のRPCプロシージャー、操作コード、enum値、フラグビット値、switchケースの削除。なお、XDRに影響しない限り、これらのいずれかの使用がエラーを引き起こすと定義する変更は行ってもかまいません。同様に、これらの項目はいずれも新しい目的のために再利用してはいけません。

4.3. Handling of Protocol Elements by Responders

4.3. レスポンダーによるプロトコル要素の扱い

Implementations handle protocol elements received in requests and callbacks in one of three ways. Which of the following ways are valid depends on the status of the protocol element in the variant being implemented:

実装は、リクエストやコールバックで受信したプロトコル要素を、3つの方法のいずれかで扱います。次の方法のうちどれが有効かは、実装されているバリアントにおけるそのプロトコル要素のステータスによって決まります。

  • The protocol element is not a part of definition of the variant in question and so is "unknown". The responder, when it does not report an RPC XDR decode error, reports an error indicative of the element not being defined in the XDR such as NFS4ERR_OP_ILLEGAL, NFS4ERR_BADXDR, or NFS4ERR_INVAL. See Section 4.4.3 for details.
  • The protocol element is a known part of the variant but is not supported by the particular implementation. The responder reports an error indicative of the element being recognized as one which is not supported such as NFS4ERR_NOTSUPP, NFS4ERR_UNION_NOTSUPP, or NFS4ERR_ATTRNOTSUPP.
  • The protocol element is a known part of the variant that is supported by the particular implementation. The responder reports success or an error other than the special ones discussed above.
  • そのプロトコル要素は当該バリアントの定義の一部ではないため、「未知（unknown）」です。レスポンダーは、RPCのXDRデコードエラーを報告しない場合、NFS4ERR_OP_ILLEGAL、NFS4ERR_BADXDR、NFS4ERR_INVALなど、その要素がXDRで定義されていないことを示すエラーを報告します。詳細についてはセクション4.4.3を参照してください。
  • そのプロトコル要素はバリアントの既知の一部ですが、その特定の実装ではサポートされていません。レスポンダーは、NFS4ERR_NOTSUPP、NFS4ERR_UNION_NOTSUPP、NFS4ERR_ATTRNOTSUPPなど、その要素がサポートされていないものとして認識されたことを示すエラーを報告します。
  • そのプロトコル要素はバリアントの既知の一部であり、その特定の実装でサポートされています。レスポンダーは、成功、または上記で議論した特別なエラー以外のエラーを報告します。

Which of these are validly returned by the responder depends on the status of the protocol element in the minor version specified in the COMPOUND or CB_COMPOUND. The possibilities that can exist when dealing with minor versions that have not been subject to corrections are listed below. See Sections 9.1 and 9.3 for a discussion of the effects of protocol correction.

レスポンダーがこれらのうちどれを正当に返せるかは、COMPOUNDまたはCB_COMPOUNDで指定されたマイナーバージョンにおけるそのプロトコル要素のステータスによって決まります。修正を受けていないマイナーバージョンを扱う場合に存在し得る可能性を以下に挙げます。プロトコルの修正の影響に関する議論については、セクション9.1と9.3を参照してください。

  • The protocol element is not known in the minor version. In this case, all implementations of the minor version MUST indicate that the protocol element is not known.
  • The protocol element is part of a feature specified as mandatory to not implement in the minor version. In this case as well, all implementations of the minor version MUST indicate that the protocol element is not known.
  • The protocol element is defined as part of the current variant of the minor version but is not part of the corresponding base variant. In this case, the requester can encounter situations in which the protocol element is either not known to the responder, is known to but not supported by the responder, or is both known to and supported by the responder.
  • The protocol element is defined as an OPTIONAL part of the base minor version. In this case, the requester can expect the protocol element to be known but must deal with cases in which it is supported or is not supported.
  • The protocol element is defined as a REQUIRED part of the base minor version. In this case, the requester can expect the protocol element to be both known and supported by the responder.
  • そのプロトコル要素は、そのマイナーバージョンでは未知です。この場合、そのマイナーバージョンのすべての実装は、そのプロトコル要素が未知であることを示さなければなりません（MUST）。
  • そのプロトコル要素は、そのマイナーバージョンで実装しないことが必須と規定された機能の一部です。この場合も、そのマイナーバージョンのすべての実装は、そのプロトコル要素が未知であることを示さなければなりません（MUST）。
  • そのプロトコル要素は、そのマイナーバージョンの現在のバリアントの一部として定義されていますが、対応する基本バリアントの一部ではありません。この場合、リクエスターは、そのプロトコル要素がレスポンダーにとって未知である状況、レスポンダーにとって既知だがサポートされていない状況、レスポンダーにとって既知でありかつサポートされている状況のいずれにも遭遇し得ます。
  • そのプロトコル要素は、基本マイナーバージョンの選択可能な（OPTIONAL）部分として定義されています。この場合、リクエスターは、そのプロトコル要素が既知であることを期待できますが、それがサポートされている場合とサポートされていない場合に対処しなければなりません。
  • そのプロトコル要素は、基本マイナーバージョンの「要求されています（REQUIRED）」部分として定義されています。この場合、リクエスターは、そのプロトコル要素がレスポンダーにとって既知であり、かつサポートされていることを期待できます。

The listing of possibilities above does not mean that a requester always needs to be prepared for all such possibilities. Often, depending on the scope of the feature of which the protocol element is a part, handling of a previous request using the same or related protocol elements will allow the requester to be sure that certain of these possibilities cannot occur.

上記の可能性の列挙は、リクエスターが常にそれらの可能性すべてに備える必要があるという意味ではありません。多くの場合、そのプロトコル要素が属する機能の範囲によっては、同じプロトコル要素または関連するプロトコル要素を使用した以前のリクエストの処理によって、リクエスターはこれらの可能性のうち特定のものが起こり得ないと確信できます。

Requesters, typically clients, may test for knowledge of, or support for, protocol elements as part of connection establishment. This may allow the requester to be aware of a responder's lack of knowledge of or support for problematic requests before they are actually used to affect user requests.

リクエスター（通常はクライアント）は、接続確立の一環として、プロトコル要素を知っているか、あるいはサポートしているかをテストしてもかまいません。これにより、リクエスターは、問題となるリクエストを実際にユーザーのリクエストに影響する形で使用する前に、レスポンダーがそれを知らないことやサポートしていないことを把握できる場合があります。

4.4. Inter-version Interoperability

4.4. バージョン間の相互運用性

Because of NFSv4's use of XDR extension, any communicating client and server versions have XDR definitions such that each is a valid extension of a third version. Once that version is determined, it may be used by both client and server to communicate. Each party can successfully use a subset of protocol elements that are both known to and supported by both parties.

NFSv4はXDR拡張を使用しているため、通信するクライアントとサーバーのどのバージョンも、それぞれが第3のバージョンの有効な拡張であるようなXDR定義を持ちます。そのバージョンが決まれば、クライアントとサーバーの両方がそれを使用して通信できます。各当事者は、両当事者が知っていて、かつ両当事者がサポートしているプロトコル要素のサブセットを問題なく使用できます。

4.4.1. Requirements for Knowledge of Protocol Elements

4.4.1. プロトコル要素の知識に関する要件

With regard to requirements for knowledge of protocol elements, the following rules apply. These rules are the result of the use of the XDR extension paradigm combined with the way in which extensions are incorporated in existing minor versions (for details, see Section 6).

プロトコル要素の知識に関する要件については、次の規則が適用されます。これらの規則は、XDR拡張のパラダイムの使用と、拡張を既存のマイナーバージョンに組み込む方法（詳細についてはセクション6を参照）とを組み合わせた結果です。

  • Any protocol element defined as part of the base variant of a particular minor version is required to be known by that minor version. This occurs whether the specification happens in the body of the minor definition document or is in a feature definition document that is made part of the minor version by being normatively referenced by the minor version definition document.
  • Any protocol element required to be known in a given minor version is required to be known in subsequent minor versions, unless and until a minor version has made that protocol element as mandatory to not implement.
  • When a protocol element is defined as part of an extension to an extensible minor version, it is not required to be known in that minor version but is required to be known by the next minor version. In the earlier minor version, it might not be defined in the XDR definition document, while in the later version it needs to be defined in the XDR definition document. In either case, if it is defined, it might or might not be supported.
  • When knowledge of protocol elements is optional in a given minor version, the responder's knowledge of such optional elements must obey the rule that if one such element is known, then all the protocol elements defined in the same minor version definition document must be known as well.
  • 特定のマイナーバージョンの基本バリアントの一部として定義されたプロトコル要素は、そのマイナーバージョンによって知られている必要があります。これは、その規定がマイナー定義文書の本文で行われている場合でも、マイナーバージョン定義文書から規範的に参照されることでマイナーバージョンの一部となった機能定義文書の中で行われている場合でも同様です。
  • 特定のマイナーバージョンで知られている必要があるプロトコル要素は、あるマイナーバージョンがそのプロトコル要素を「実装しないことが必須」とするまでは（そうしない限りは）、後続のマイナーバージョンでも知られている必要があります。
  • プロトコル要素が、拡張可能なマイナーバージョンに対する拡張の一部として定義されている場合、そのプロトコル要素はそのマイナーバージョンで知られている必要はありませんが、次のマイナーバージョンでは知られている必要があります。前のマイナーバージョンでは、そのプロトコル要素はXDR定義文書で定義されていないかもしれませんが、後のバージョンではXDR定義文書で定義されている必要があります。いずれの場合も、定義されているなら、サポートされていることもあれば、サポートされていないこともあります。
  • 特定のマイナーバージョンでプロトコル要素の知識が任意である場合、そのような任意の要素に関するレスポンダーの知識は、そのような要素の1つが既知であるなら、同じマイナーバージョン定義文書で定義されたすべてのプロトコル要素も既知でなければならないという規則に従わなければなりません。

For many minor versions, all existing protocol elements are required to be known by both the client and the server, and so requesters do not have to test for the presence or absence of knowledge regarding protocol elements. This is the case if there has been no extension for the minor version in question. Extensions can be added to extensible minor versions as described in Section 6 and can be used to correct protocol flaws as described in Section 9.

多くのマイナーバージョンでは、既存のすべてのプロトコル要素がクライアントとサーバーの両方によって知られている必要があるため、リクエスターは、プロトコル要素に関する知識の有無をテストする必要がありません。当該マイナーバージョンに対する拡張がなかった場合がこれに当たります。拡張は、セクション6で説明するように拡張可能なマイナーバージョンに追加でき、セクション9で説明するようにプロトコルの欠陥を修正するために使用できます。

Requesters can ascertain the knowledge of the responder in two ways:

リクエスターは、2つの方法でレスポンダーの知識を確認できます。

  • By issuing a request using the protocol element and looking at the response. Note that, even if the protocol element used is not supported by the responder, the requester can still determine if the element is known by the responder.
  • By receiving a request from the responder, acting in the role of requester. For example, a client may issue a request enabling the server to infer that it is aware of a corresponding callback.
  • そのプロトコル要素を使用するリクエストを発行し、レスポンスを調べる方法。なお、使用したプロトコル要素がレスポンダーによってサポートされていない場合でも、リクエスターは、その要素がレスポンダーにとって既知であるかどうかを判断できます。
  • リクエスターの役割を果たすレスポンダーからリクエストを受信する方法。たとえば、クライアントは、対応するコールバックをクライアントが認識していることをサーバーが推測できるようなリクエストを発行することがあります。

In making this determination, the requester can rely on two basic facts:

この判断を行う際、リクエスターは2つの基本的な事実に頼れます。

  • If the responder is aware of a single protocol element within a feature package, it must be aware of all protocol elements within that feature package.
  • If a protocol element is one defined by the minor version specified by a request (and not in an extension), or in a previous minor version, the responder must be aware of it.
  • レスポンダーが機能パッケージ内の1つのプロトコル要素を認識しているなら、そのレスポンダーはその機能パッケージ内のすべてのプロトコル要素を認識していなければなりません。
  • プロトコル要素が、リクエストで指定されたマイナーバージョンで（拡張ではなく）定義されたもの、または以前のマイナーバージョンで定義されたものである場合、レスポンダーはそれを認識していなければなりません。

4.4.2. Establishing Interoperability

4.4.2. 相互運用性の確立

When a client and a server interact, they need to able to take advantage of the compatibility provided by NFSv4's use of XDR extension.

クライアントとサーバーがやり取りする際、両者は、NFSv4がXDR拡張を使用していることによって得られる互換性を活用できる必要があります。

In this context, the client and server would arrive at a common variant, which the client uses to send requests that the server would then accept. The server would use that variant to send callbacks that the client would then accept. This state of affairs could arise in a number of ways:

この文脈において、クライアントとサーバーは共通のバリアントに到達します。クライアントはそのバリアントを使用して、サーバーが受け入れるリクエストを送信します。サーバーはそのバリアントを使用して、クライアントが受け入れるコールバックを送信します。このような状態は、いくつかの形で生じ得ます。

  • Client and server have been built using XDR variants that belong to the same minor version.
  • The client's minor version is lower than that of the server. In this case the server, in accord with Section 8.2, accepts the client's minor version, and acts as if it has no knowledge of extensions made in subsequent minor versions. It has knowledge of protocol elements within the current (i.e., effectively final) variant of the lower minor version.
  • The client's minor version is higher than that of the server. In this case the client, in accord with Section 8.2, uses a lower minor version that the server will accept. In this case, the server has no knowledge of extensions made in subsequent minor versions.
  • クライアントとサーバーが、同じマイナーバージョンに属するXDRのバリアントを使用して構築されている場合。
  • クライアントのマイナーバージョンがサーバーのマイナーバージョンより低い場合。この場合、サーバーは、セクション8.2に従ってクライアントのマイナーバージョンを受け入れ、後続のマイナーバージョンで行われた拡張についての知識を持たないかのように動作します。サーバーは、その低いマイナーバージョンの現在の（つまり事実上最終的な）バリアント内のプロトコル要素についての知識を持っています。
  • クライアントのマイナーバージョンがサーバーのマイナーバージョンより高い場合。この場合、クライアントは、セクション8.2に従って、現在のものより低く、かつサーバーが受け入れるマイナーバージョンを使用します。この場合、サーバーは後続のマイナーバージョンで行われた拡張についての知識を持ちません。

There are a number of cases to consider based on the characteristics of the minor version chosen.

選択されたマイナーバージョンの特性に基づいて、考慮すべきケースがいくつかあります。

  • When the minor version consists of only a single variant (no extension or XDR corrections), the client and the server are using the same XDR description and have knowledge of the same protocol elements.
  • When the minor version consists of multiple variants (i.e., there are one or more XDR extensions or XDR corrections), the client and the server are using compatible XDR descriptions. The client is aware of some set of extensions while the server may be aware of a different set. The client can use the approach described in Section 4.4.3 to determine which of the extensions it knows about are also known by the server. Once this is done, the client and server will both be using a common variant. The variants that the client and the server were built with will both either be identical to this variant or a valid extension of it. Similarly, the variants that the client and the server actually use will be a subset of this variant, in that certain OPTIONAL features will not be used.
  • マイナーバージョンが単一のバリアントだけで構成される（拡張やXDRの修正がない）場合、クライアントとサーバーは同じXDR記述を使用しており、同じプロトコル要素についての知識を持っています。
  • マイナーバージョンが複数のバリアントで構成される（つまり、1つ以上のXDR拡張またはXDRの修正がある）場合、クライアントとサーバーは互換性のあるXDR記述を使用しています。クライアントはある拡張の集合を認識している一方で、サーバーは別の集合を認識しているかもしれません。クライアントは、セクション4.4.3で説明するアプローチを使用して、自身が知っている拡張のうちどれがサーバーにも知られているかを判断できます。これが済めば、クライアントとサーバーはどちらも共通のバリアントを使用することになります。クライアントとサーバーが構築に使用したバリアントは、どちらもこのバリアントと同一であるか、その有効な拡張であるかのいずれかです。同様に、クライアントとサーバーが実際に使用するバリアントは、特定の選択可能な（OPTIONAL）機能が使用されないという点で、このバリアントのサブセットになります。

In either case, the client must determine which of the OPTIONAL protocol elements within the common version are supported by the server, just as it does for OPTIONAL features introduced as part of a minor version.

いずれの場合も、クライアントは、マイナーバージョンの一部として導入された選択可能な（OPTIONAL）機能について行うのと同様に、共通のバージョン内の選択可能な（OPTIONAL）プロトコル要素のうちどれがサーバーによってサポートされているかを判断しなければなりません。

It is best if client implementations make the determination as to the support provided by the server before acting on user requests. This includes the determination of the common protocol variant and the level of support for OPTIONAL protocol elements.

クライアント実装は、ユーザーのリクエストに基づいて動作する前に、サーバーが提供するサポートについての判断を行うのが最善です。これには、共通のプロトコルのバリアントの判断と、選択可能な（OPTIONAL）プロトコル要素のサポートの程度の判断が含まれます。

4.4.3. Determining Knowledge of Protocol Elements

4.4.3. プロトコル要素の知識の判断

A requester may test the responder's knowledge of particular protocol elements as defined below, based on the type of protocol element. Note that in the case of attribute or flag bits, use of a request that refers to 2 or more bits of undetermined status ("known" versus "unknown") may return results that are not particularly helpful. In such cases, when the response is NFS4ERR_INVAL, the requester can only conclude that at least one of the bits is unknown.

リクエスターは、プロトコル要素の種類に基づいて、以下に定義するように、特定のプロトコル要素に関するレスポンダーの知識をテストできます。なお、属性ビットやフラグビットの場合、ステータス（「既知」か「未知」か）が未確定である2つ以上のビットを参照するリクエストを使用すると、あまり役に立たない結果が返されることがあります。そのような場合、レスポンスがNFS4ERR_INVALであれば、リクエスターは、それらのビットのうち少なくとも1つが未知であるとしか結論づけられません。

  • When a GETATTR request is made specifying an attribute bit to be tested and that attribute is not a set-only attribute, if the GETATTR returns with the error NFS4ERR_INVAL, then it can be concluded that the responder has no knowledge of the attribute in question. Other responses, including NFS4ERR_ATTRNOTSUPP, indicate that the responder is aware of the attribute in question.
  • When a SETATTR request is made specifying the attribute bit to be tested and that attribute is not a get-only attribute, if the SETATTR returns with the error NFS4ERR_INVAL, then it can be concluded that the responder has no knowledge of the attribute in question. Other responses, including NFS4ERR_ATTRNOTSUPP, indicate that the responder is aware of the attribute in question.
  • When a request is made including an operation with a new flag bit, if the operation returns with the error NFS4ERR_INVAL, then it can generally be concluded that the responder has no knowledge of the flag bit in question, as long as the requester is careful to avoid other error situations in which the operation in question is defined as returning NFS4ERR_INVAL. Other responses indicate that the responder is aware of the flag bit in question.
  • When a request is made including the operation to be tested, if the responder returns an RPC XDR decode error, or a response indicating that the operation in question resulted in NFS4ERR_OP_ILLEGAL or NFS4ERR_BADXDR, then it can be concluded that the responder has no knowledge of the operation in question. Other responses, including NFS4ERR_NOTSUPP, indicate that the responder is aware of the operation in question.
  • When a request is made including the switch arm to be tested, if the responder returns an RPC XDR decode error, or a response indicating that the operation in question resulted in NFS4ERR_BADXDR, then it can be concluded that the responder has no knowledge of the operation in question. Other responses, including NFS4ERR_UNION_NOTSUPP, indicate that the responder is aware of the protocol element in question.
  • テスト対象の属性ビットを指定してGETATTRリクエストを行い、その属性が設定専用の属性ではない場合、GETATTRがエラーNFS4ERR_INVALを返したなら、レスポンダーは当該属性についての知識を持っていないと結論づけられます。NFS4ERR_ATTRNOTSUPPを含むその他のレスポンスは、レスポンダーが当該属性を認識していることを示します。
  • テスト対象の属性ビットを指定してSETATTRリクエストを行い、その属性が取得専用の属性ではない場合、SETATTRがエラーNFS4ERR_INVALを返したなら、レスポンダーは当該属性についての知識を持っていないと結論づけられます。NFS4ERR_ATTRNOTSUPPを含むその他のレスポンスは、レスポンダーが当該属性を認識していることを示します。
  • 新しいフラグビットを持つ操作を含むリクエストを行い、その操作がエラーNFS4ERR_INVALを返した場合、リクエスターが当該操作がNFS4ERR_INVALを返すと定義されているその他のエラー状況を注意深く避けている限り、一般に、レスポンダーは当該フラグビットについての知識を持っていないと結論づけられます。その他のレスポンスは、レスポンダーが当該フラグビットを認識していることを示します。
  • テスト対象の操作を含むリクエストを行い、レスポンダーがRPCのXDRデコードエラーを返すか、当該操作の結果がNFS4ERR_OP_ILLEGALまたはNFS4ERR_BADXDRとなったことを示すレスポンスを返した場合、レスポンダーは当該操作についての知識を持っていないと結論づけられます。NFS4ERR_NOTSUPPを含むその他のレスポンスは、レスポンダーが当該操作を認識していることを示します。
  • テスト対象のswitchのアームを含むリクエストを行い、レスポンダーがRPCのXDRデコードエラーを返すか、当該操作の結果がNFS4ERR_BADXDRとなったことを示すレスポンスを返した場合、レスポンダーは当該操作についての知識を持っていないと結論づけられます。NFS4ERR_UNION_NOTSUPPを含むその他のレスポンスは、レスポンダーが当該プロトコル要素を認識していることを示します。

A determination of the knowledge or lack of knowledge of a particular protocol element is expected to remain valid as long as the clientid associated with the request remains valid.

特定のプロトコル要素についての知識の有無の判断は、そのリクエストに関連付けられたclientidが有効である限り、有効であり続けることが期待されます。

The above assumes, as should be the case, that the server will accept the minor version used by the client. For more detail regarding this issue, see Section 8.2.

上記は、本来そうあるべきように、サーバーがクライアントの使用するマイナーバージョンを受け入れることを前提としています。この問題に関する詳細については、セクション8.2を参照してください。

4.5. XDR Overlay

4.5. XDRオーバーレイ

XDR additions may also be made by defining XDR structures that overlay nominally opaque fields that are defined to allow such incremental extensions.

XDRの追加は、そのような段階的な拡張を可能にするように定義された、名目上は不透明なフィールドに重ねるXDR構造を定義することによっても行えます。

For example, each parallel NFS (pNFS) mapping type provides its own XDR definition for various pNFS-related fields defined in [RFC5661] as opaque arrays.

たとえば、各パラレルNFS（pNFS）のマッピングタイプは、[RFC5661]で不透明な配列として定義されたさまざまなpNFS関連のフィールドについて、独自のXDR定義を提供します。

Because such additions provide new interpretations of existing fields, they may be made outside of the extension framework as long as they obey the rules previously established when the nominally opaque protocol elements were added to the protocol.

このような追加は既存のフィールドに新しい解釈を与えるものであるため、名目上は不透明なプロトコル要素がプロトコルに追加されたときに以前に確立された規則に従う限り、拡張フレームワークの外で行ってもかまいません。

5. Other NFSv4 Protocol Changes

5. NFSv4プロトコルのその他の変更

There are a number of types of protocol changes that are outside the XDR extension framework discussed in Section 4. These changes are also managed within the NFSv4 versioning framework and may be of a number of types, which are discussed in the sections below.

セクション4で議論したXDR拡張フレームワークの外にあるプロトコル変更には、いくつかの種類があります。これらの変更もNFSv4のバージョニングフレームワークの中で管理され、いくつかの種類があり得ます。それらについては以下のセクションで議論します。

Despite the previous emphasis on XDR changes, additions and changes to the NFSv4 protocols have not been limited to those that involve changes (in the form of extensions) to the protocol XDR. Examples of other sorts of changes have been taken from NFSv4.1.

これまでXDRの変更を強調してきましたが、NFSv4プロトコルに対する追加や変更は、プロトコルのXDRに対する（拡張の形での）変更を伴うものに限られてはいませんでした。その他の種類の変更の例は、NFSv4.1から取っています。

All such changes that have been made in the past have been made as part of new minor version. Future change of these sorts may not be done in an extension but can only be made in a new minor version.

過去に行われたそのような変更はすべて、新しいマイナーバージョンの一部として行われてきました。今後のこの種の変更は、拡張では行えず、新しいマイナーバージョンでのみ行えます。

5.1. Field Interpretation and Use

5.1. フィールドの解釈と使用

The XDR description of a protocol does not constitute a complete description of the protocol. Therefore, versioning needs to consider the role of changes in the use of fields, even when there is no change to the underlying XDR.

プロトコルのXDR記述は、そのプロトコルの完全な記述ではありません。そのため、バージョニングでは、基礎となるXDRに変更がない場合でも、フィールドの使用方法の変更が果たす役割を考慮する必要があります。

Although any XDR element is potentially subject to a change in its interpretation and use, the likelihood of such change will vary with the XDR-specified type of the element, as discussed below:

どのXDR要素もその解釈と使用方法が変更される可能性がありますが、以下で議論するように、そのような変更の可能性の高さは、その要素のXDRで規定された型によって異なります。

  • When XDR elements are defined as strings, rules regarding the appropriate string values are specified in protocol specification text with changes in such rules documented in minor version definition documents. Some types of strings within NFS4 are used in server names (in location-related attributes), user and group names, and in the names of file objects within directories. Rules regarding what strings are acceptable appear in [RFC7530] and [RFC5661] with the role of the XDR limited to hints regarding UTF-8 and capitalization issues via XDR typedefs.

  • Fields that are XDR-defined as opaque elements and that are truly opaque, do not raise versioning issues, except as regards inter-version use, which is effectively foreclosed by the rules in Section 8.1.

    Note that sometimes a field will seem to be opaque but not actually be fully opaque when considered carefully. For example, the "other" field of stateids is defined as an opaque array, while the specification text specially defines appropriate treatment when the "other" field within it is either all zeros or all ones. Given this context, creation or deletion of reserved values for "special" stateids will be a protocol change that versioning rules need to deal with.

  • Some nominally opaque elements have external XDR definitions that overlay the nominally opaque arrays. Such cases are discussed in Section 4.5.
  • XDR要素が文字列として定義されている場合、適切な文字列値に関する規則はプロトコル仕様の本文で規定され、そのような規則の変更はマイナーバージョン定義文書に記載されます。NFS4内の文字列のいくつかの種類は、（場所関連の属性内の）サーバー名、ユーザー名とグループ名、およびディレクトリー内のファイルオブジェクトの名前に使用されます。どの文字列が受け入れられるかに関する規則は[RFC7530]と[RFC5661]に記載されており、XDRの役割は、XDRのtypedefによるUTF-8と大文字小文字の問題に関するヒントに限られています。

  • XDRで不透明な要素として定義され、かつ真に不透明であるフィールドは、バージョニングの問題を引き起こしません。ただし、バージョン間での使用については別であり、それはセクション8.1の規則によって事実上排除されています。

    なお、フィールドが不透明であるように見えても、注意深く検討すると実際には完全には不透明ではない場合があります。たとえば、stateidの「other」フィールドは不透明な配列として定義されていますが、仕様の本文では、その中の「other」フィールドがすべて0またはすべて1である場合の適切な扱いを特別に定義しています。この文脈を踏まえると、「特別な」stateidのための予約値の作成や削除は、バージョニング規則が扱う必要のあるプロトコル変更になります。

  • 名目上は不透明な要素の中には、その名目上は不透明な配列に重ねる外部のXDR定義を持つものがあります。そのようなケースについてはセクション4.5で議論しています。

5.2. Behavioral Changes

5.2. 動作の変更

Changes in the behavior of NFSv4 operations are possible, even if there is no change in the underlying XDR or change to field interpretation and use.

基礎となるXDRに変更がなく、フィールドの解釈や使用方法にも変更がない場合でも、NFSv4の操作の動作を変更することは可能です。

One class of behavioral change involves changes in the set of errors to be returned when various failure conditions occur. When the set of valid requests remain the same, and the behavior for each of them remains the same, such changes can be implemented with only limited disruption to existing clients.

動作の変更の1つの種類は、さまざまな障害条件が発生したときに返されるエラーの集合の変更です。有効なリクエストの集合が同じままで、それぞれのリクエストに対する動作も同じままであれば、そのような変更は既存のクライアントへの混乱を限定的なものにとどめて実装できます。

Many more substantial behavioral changes have occurred in connection with the addition of the session concept in NFSv4.1. Even though there was no change to the XDR for existing operations, many existing operations and COMPOUNDs consisting only of them became invalid.

さらに多くの大幅な動作の変更が、NFSv4.1でのセッションの概念の追加に関連して発生しました。既存の操作のXDRには変更がなかったにもかかわらず、多くの既存の操作と、それらのみで構成されるCOMPOUNDが無効になりました。

Also, changes were made regarding the required server behavior as to the interaction of the MODE and Access Control List (ACL) attributes.

また、MODE属性とアクセス制御リスト（Access Control List、ACL）属性の相互作用について、要求されるサーバーの動作に関する変更も行われました。

6. Extending Existing Minor Versions

6. 既存のマイナーバージョンの拡張

Extensions to the most recently published NFSv4 minor version may be made by publishing the extension as a Proposed Standard, unless the minor version in question has been defined as non-extensible. A document need not use the "Updates" header specifying the RFC that defines the minor version, which remains a valid description of the base variant of the minor version in question.

最も新しく公開されたNFSv4マイナーバージョンに対する拡張は、当該マイナーバージョンが拡張不可能と定義されていない限り、その拡張を提案標準として公開することによって行えます。その文書は、マイナーバージョンを定義するRFCを指定する「Updates」ヘッダーを使用する必要はありません。そのRFCは、当該マイナーバージョンの基本バリアントの有効な記述であり続けます。

In addition to following the rules for XDR extensions in Section 4.2, such extensions must also obey the rules listed below in order to allow interoperability to be established, as described in Section 4.4:

セクション4.2のXDR拡張の規則に従うことに加えて、そのような拡張は、セクション4.4で説明するように相互運用性を確立できるようにするため、以下に挙げる規則にも従わなければなりません。

  • Additions to the set of callback requests and extensions to the XDR for existing callback operations can only be made if the server can determine, based on the client's actions, that the client is aware of the changes. This determination, for any particular client (as defined by its clientid), is made before sending those new or extended callbacks.
  • XDR extensions that affect the structures of responses to existing operations can only be made if the server can determine, based on the client's actions, that it is aware of the existence of XDR changes, before sending responses containing those extensions. This determination can be based on the request being responded to, but that is not required. Use of any protocol element defined in the extension can be the basis of the determination, provided that the requirements for determining client awareness are clearly stated.
  • コールバックリクエストの集合への追加と、既存のコールバック操作のXDRに対する拡張は、クライアントがその変更を認識していることを、サーバーがクライアントの行動に基づいて判断できる場合にのみ行えます。この判断は、（そのclientidによって定義される）特定のクライアントごとに、それらの新しいコールバックや拡張されたコールバックを送信する前に行われます。
  • 既存の操作に対するレスポンスの構造に影響するXDR拡張は、それらの拡張を含むレスポンスを送信する前に、クライアントがXDRの変更の存在を認識していることを、サーバーがクライアントの行動に基づいて判断できる場合にのみ行えます。この判断は、応答の対象となっているリクエストに基づいて行えますが、それは必須ではありません。クライアントの認識を判断するための要件が明確に記述されていれば、その拡張で定義された任意のプロトコル要素の使用を判断の根拠にできます。

Corrections to protocol errors (see Section 9) may be accomplished by publishing an extension, including a compatible XDR change that follows the rules above. Such documents will update the defining documents for the minor version to be corrected.

プロトコルの誤り（セクション9を参照）の修正は、上記の規則に従う互換性のあるXDRの変更を含む拡張を公開することによって行えます。そのような文書は、修正対象のマイナーバージョンを定義する文書を更新することになります。

In some cases, extensions will contain elements such as new operations or previously invalid switch cases. Although it is possible to determine whether these OPTIONAL elements are supported using the rules described above, those defining an extension that contains such elements have the choice of defining a new attribute that indicates whether the feature is present and supported. Since it is easy to determine whether a new attribute is supported using the supported_attrs attribute, this can make it simple and convenient for clients to determine whether support is present, particularly when a feature involves support for multiple such elements.

拡張が、新しい操作や以前は無効だったswitchケースといった要素を含む場合があります。上記の規則を使用して、これらの選択可能な（OPTIONAL）要素がサポートされているかどうかを判断することは可能ですが、そのような要素を含む拡張を定義する者は、その機能が存在しサポートされているかどうかを示す新しい属性を定義することも選択できます。新しい属性がサポートされているかどうかはsupported_attrs属性を使用して容易に判断できるため、これにより、特に機能がそのような要素を複数サポートすることを伴う場合に、クライアントはサポートの有無を簡単かつ便利に判断できるようになります。

7. Minor Versions

7. マイナーバージョン

7.1. Creation of New Minor Versions

7.1. 新しいマイナーバージョンの作成

It is important to note that this section, in describing situations that would require new minor versions to be created, does not thereby imply that situations will exist in the future. Judgments regarding desirability of future changes will be made by the working group or its successors and any guidance that can be offered at this point is necessarily quite limited.

このセクションは、新しいマイナーバージョンの作成が必要となるような状況を記述していますが、それによって将来そのような状況が存在することを示唆しているわけではないことに注意することが重要です。将来の変更が望ましいかどうかの判断はワーキンググループまたはその後継者が行うものであり、現時点で提供できるガイダンスは必然的にかなり限られたものになります。

Creation of a new minor version is an option that the working group retains. The listing of situations below that would prompt such actions is not meant to be exhaustive.

新しいマイナーバージョンの作成は、ワーキンググループが保持している選択肢です。以下に挙げる、そのような行動を促す状況の列挙は、網羅的なものを意図していません。

The following sorts of features are not allowed as extensions and would require creation of a new minor version:

次の種類の機能は拡張としては許可されず、新しいマイナーバージョンの作成が必要になります。

  • Features that incorporate any of the non-XDR-based changes discussed in Sections 5.1 and 5.2.
  • Features whose XDR changes do not follow the rules in Section 6.
  • Addition of REQUIRED new features.
  • Changes to the status of existing features including converting features to be mandatory to not implement.
  • セクション5.1と5.2で議論した、XDRに基づかない変更のいずれかを組み込んだ機能。
  • XDRの変更がセクション6の規則に従っていない機能。
  • 「要求されています（REQUIRED）」とされる新しい機能の追加。
  • 既存の機能のステータスの変更。機能を「実装しないことが必須」に変えることも含みます。

8. Minor Version Interaction Rules

8. マイナーバージョンの相互作用の規則

This section addresses issues related to rules #11 and #13 in the minor versioning rules in [RFC5661]. With regard to the supersession of minor versioning rules, the treatment here overrides that in [RFC5661] when either of the potentially interacting minor versions has not yet been published as a Proposed Standard.

このセクションでは、[RFC5661]のマイナーバージョニング規則のうち規則#11と#13に関連する問題を扱います。マイナーバージョニング規則の置き換えに関しては、相互作用する可能性のあるマイナーバージョンのいずれかがまだ提案標準として公開されていない場合、ここでの扱いが[RFC5661]での扱いに優先します。

Note that these rules are the only ones directed to minor version implementers, rather than to those specifying new minor versions.

これらの規則は、新しいマイナーバージョンを規定する者ではなく、マイナーバージョンの実装者に向けた唯一の規則であることに注意してください。

8.1. Minor Version Identifier Transfer Issues

8.1. マイナーバージョン識別子の移行に関する問題

Each relationship between a client instance and a server instance, as represented by a clientid, is to be devoted to a single minor version. If a server detects that a COMPOUND with an inappropriate minor version is being used, it MUST reject the request. In doing so, it may return either NFS4ERR_BAD_CLIENTID or NFS4RR_MINOR_VERS_MISMATCH.

clientidによって表されるクライアントインスタンスとサーバーインスタンスの間の各関係は、単一のマイナーバージョンに充てられます。不適切なマイナーバージョンのCOMPOUNDが使用されていることをサーバーが検出した場合、サーバーはそのリクエストを拒否しなければなりません（MUST）。その際、サーバーはNFS4ERR_BAD_CLIENTIDまたはNFS4RR_MINOR_VERS_MISMATCHのいずれかを返してもかまいません。

As a result of the above, the client has the assurance that the set of REQUIRED and OPTIONAL features will not change within the context of a single clientid. Server implementations MUST ensure that the set of supported features and protocol elements does not change within such a context.

上記の結果として、クライアントは、単一のclientidの文脈の中では、「要求されています（REQUIRED）」機能と選択可能な（OPTIONAL）機能の集合が変わらないことを保証されます。サーバー実装は、そのような文脈の中で、サポートされる機能とプロトコル要素の集合が変わらないことを保証しなければなりません（MUST）。

8.2. Minor Version Compatibility

8.2. マイナーバージョンの互換性

The goal of the NFSv4 extension model is to enable compatibility including compatibility between clients and servers implementing different minor versions.

NFSv4の拡張モデルの目標は、異なるマイナーバージョンを実装するクライアントとサーバーの間の互換性を含め、互換性を実現することです。

Within a set of minor versions that define the same set of features as REQUIRED and mandatory to not implement, it is relatively easy for clients and servers to provide the needed compatibility by adhering to the following practices:

「要求されています（REQUIRED）」機能および実装しないことが必須の機能として同じ機能の集合を定義するマイナーバージョンの集合の中では、クライアントとサーバーは、次のやり方に従うことによって、必要な互換性を比較的容易に提供できます。

  • Servers supporting a given minor version should support earlier minor versions within that set and return appropriate errors for use of protocol elements that were not a valid part of that earlier minor version. For details, see below.
  • Clients should deal with an NFS4ERR_MINOR_VERS_MISMATCH error by searching for a lower minor version number that the server will accept.
  • 特定のマイナーバージョンをサポートするサーバーは、その集合の中のより前のマイナーバージョンをサポートし、そのより前のマイナーバージョンの有効な一部ではなかったプロトコル要素の使用に対しては適切なエラーを返すべきです。詳細については以下を参照してください。
  • クライアントは、NFS4ERR_MINOR_VERS_MISMATCHエラーに対して、より低く、かつサーバーが受け入れるマイナーバージョン番号を探すことで対処すべきです。

Servers supporting a given minor version MUST, in returning errors for operations that were a valid part of the minor version, return the errors allowed for the current operation in the minor version actually being used.

特定のマイナーバージョンをサポートするサーバーは、そのマイナーバージョンの有効な一部であった操作に対してエラーを返す際、実際に使用されているマイナーバージョンにおいてその操作に許可されているエラーを返さなければなりません（MUST）。

With regard to protocol elements not known in a given minor version, the appropriate error codes are given below. Essentially, the server, although it has a more extensive XDR reflective of a newer minor version, must act as a server with a more limited XDR would.

特定のマイナーバージョンで未知のプロトコル要素に関しては、適切なエラーコードを以下に示します。基本的に、サーバーは、より新しいマイナーバージョンを反映したより広範なXDRを持っていても、より限定されたXDRを持つサーバーと同じように動作しなければなりません。

  • When an operation is used that is not known in the specified minor version, NFS4ERR_OP_ILLEGAL (as opposed to NFS4ERR_NOTSUPP) should be returned.
  • When an attribute is used that is not known in the specified minor version, NFS4ERR_INVAL (as opposed to NFS4ERR_ATTRNOTSUPP) should be returned.
  • When a switch case is used that is not known in the specified minor version, NFS4ERR_BADXDR (as opposed to NFS4ERR_UNION_NOTSUPP) should be returned. Even though the message may be XDR-decodable by the server's current XDR, it is not so according to the minor version being used.
  • When a flag bit is used that is not known in the specified minor version, NFS4ERR_INVAL (as opposed to NFS4ERR_NOTSUPP or any other error defined as indicating non-support of a flag bit) should be returned.
  • 指定されたマイナーバージョンでは未知の操作が使用された場合、（NFS4ERR_NOTSUPPではなく）NFS4ERR_OP_ILLEGALを返すべきです。
  • 指定されたマイナーバージョンでは未知の属性が使用された場合、（NFS4ERR_ATTRNOTSUPPではなく）NFS4ERR_INVALを返すべきです。
  • 指定されたマイナーバージョンでは未知のswitchケースが使用された場合、（NFS4ERR_UNION_NOTSUPPではなく）NFS4ERR_BADXDRを返すべきです。そのメッセージはサーバーの現在のXDRではXDRデコード可能かもしれませんが、使用されているマイナーバージョンに従えばそうではありません。
  • 指定されたマイナーバージョンでは未知のフラグビットが使用された場合、（NFS4ERR_NOTSUPPや、フラグビットが非サポートであることを示すと定義されたその他のエラーではなく）NFS4ERR_INVALを返すべきです。

9. Correction of Existing Minor Versions and Features

9. 既存のマイナーバージョンと機能の修正

The possibility always exists that there will be a need to correct an existing feature in some way after the acceptance of that feature, or a minor version containing it, as a Proposed Standard. While the working group can reduce the probability of such situations arising by waiting for running code before considering a feature as done, it cannot reduce the probability to zero. As features are used more extensively and interact with other features, previously unseen flaws may be discovered and will need to be corrected.

ある機能、またはその機能を含むマイナーバージョンが提案標準として受け入れられた後に、既存の機能をなんらかの形で修正する必要が生じる可能性は常に存在します。ワーキンググループは、機能を完成したとみなす前に実働するコードを待つことによって、そのような状況が生じる確率を下げることはできますが、その確率をゼロにすることはできません。機能がより広範に使用され、他の機能と相互作用するようになるにつれて、それまで見えていなかった欠陥が発見されることがあり、それらを修正する必要が生じます。

Such corrections are best done in a document obsoleting or updating the RFC defining the relevant feature or minor version. In making such corrections, the working group will have to carefully consider how to assure interoperability with older clients and servers.

そのような修正は、関連する機能またはマイナーバージョンを定義するRFCを廃止または更新する文書で行うのが最善です。そのような修正を行う際、ワーキンググループは、古いクライアントやサーバーとの相互運用性をどのように保証するかを慎重に検討しなければなりません。

Often, corrections can be done without changing the protocol XDR. In many cases, a change in client and server behavior can be implemented without taking special provision with regard to interoperability with earlier implementations. In those cases, and in cases in which a revision merely clarifies an earlier protocol definition document, a new document can be published that simply updates the earlier protocol definition document.

多くの場合、修正はプロトコルのXDRを変更せずに行えます。多くの場合、クライアントとサーバーの動作の変更は、以前の実装との相互運用性に関する特別な措置を講じることなく実装できます。そのような場合や、改訂が以前のプロトコル定義文書を明確化するだけの場合には、以前のプロトコル定義文書を単に更新する新しい文書を公開できます。

In other cases, it is best if client or server behavior needs to change in a way that raises interoperability concerns. In such cases, incompatible changes in server or client behavior should not be mandated in order to avoid XDR changes.

その他の場合には、相互運用性の懸念を生じるような形でクライアントやサーバーの動作を変更する必要が生じます。そのような場合、XDRの変更を避けるために、サーバーやクライアントの動作の互換性のない変更を義務付けるべきではありません。

9.1. XDR Changes to Implement Protocol Corrections

9.1. プロトコルの修正を実装するためのXDRの変更

When XDR changes are necessary as part of correcting a flaw, these should be done in a manner similar to that used when implementing new minor versions or features within them. In particular:

欠陥の修正の一環としてXDRの変更が必要な場合、その変更は、新しいマイナーバージョンやその中の機能を実装する際に使われる方法と同様の方法で行うべきです。特に、次のとおりです。

  • Existing XDR structures may not be modified or deleted.
  • XDR extensions may be used to correct existing protocol facilities in a manner similar to those used to add additional optional features. Such corrections may be done in a minor version for which optional features may no longer be added, if the working group decides that it is an appropriate way to compatibly effect a correction.
  • When a correction is made to an OPTIONAL feature, the result is similar to a situation in which there are two independent OPTIONAL features. A server may choose to implement either or both. See Section 9.2 for a detailed discussion of interoperability issues.
  • When a correction is made to a REQUIRED feature, the situation becomes one in which the old version of the feature remains REQUIRED while the corrected version, while OPTIONAL, is intended to be adopted to provide correct operation. Although use of the corrected version is ultimately better and may be recommended, it should not be described as "RECOMMENDED" since the choice of versions to support will depend on the needs of clients, which may be slow to adopt the updated version. The nature of such corrections is such that it may result in situations in which different variants of the same minor version may not both support the corrected version. See Section 9.3 for details.
  • In all of the cases above, it is appropriate that the old version of the feature be considered obsolescent, with the expectation that the working group might, in a later minor version, change the status of the uncorrected version. See Section 9.4 for more detail.
  • 既存のXDR構造を変更または削除してはいけません。
  • XDR拡張は、任意の機能を追加するために使われる方法と同様の方法で、既存のプロトコルの機能を修正するために使用できます。ワーキンググループが、それが互換性を保って修正を行うための適切な方法であると判断した場合には、そのような修正は、任意の機能をもはや追加できないマイナーバージョンでも行えます。
  • 選択可能な（OPTIONAL）機能に修正が行われた場合、その結果は、2つの独立した選択可能な（OPTIONAL）機能が存在する状況と似たものになります。サーバーは、そのどちらか、または両方を実装することを選択できます。相互運用性の問題に関する詳細な議論については、セクション9.2を参照してください。
  • 「要求されています（REQUIRED）」機能に修正が行われた場合、その機能の古いバージョンは「要求されています（REQUIRED）」のままである一方、修正されたバージョンは、「選択できます（OPTIONAL）」でありながら、正しい動作を提供するために採用されることを意図したものになります。修正されたバージョンを使用するほうが最終的には優れており、推奨されることもありますが、それを「推奨されます（RECOMMENDED）」と記述すべきではありません。サポートするバージョンの選択はクライアントのニーズに依存し、クライアントは更新されたバージョンの採用に時間がかかることがあるからです。そのような修正の性質上、同じマイナーバージョンの異なるバリアントが両方とも修正されたバージョンをサポートするとは限らない状況が生じることがあります。詳細についてはセクション9.3を参照してください。
  • 上記のいずれの場合も、その機能の古いバージョンは廃止予定とみなすのが適切であり、ワーキンググループが後のマイナーバージョンで未修正のバージョンのステータスを変更するかもしれないことが想定されます。詳細についてはセクション9.4を参照してください。

9.2. XDR Corrections to OPTIONAL Features

9.2. OPTIONAL機能に対するXDRの修正

By defining the corrected and uncorrected version as independent OPTIONAL features, the protocol with the XDR modification can accommodate clients and servers that support either the corrected or the uncorrected version of the protocol, and also clients and servers aware of and capable of supporting both alternatives.

修正されたバージョンと未修正のバージョンを独立した選択可能な（OPTIONAL）機能として定義することにより、XDRの修正を伴うプロトコルは、プロトコルの修正されたバージョンと未修正のバージョンのいずれかをサポートするクライアントとサーバーに加え、両方の選択肢を認識しそれらをサポートできるクライアントとサーバーにも対応できます。

Based on the type of client:

クライアントの種類に基づくと、次のようになります。

  • A client that uses only the earlier version of the feature (i.e., an older unfixed client) can determine whether the server it is connecting to supports the older version of feature. It is capable of interoperating with older servers that support only the unfixed protocol as well as ones that support both versions.
  • A client that supports only the corrected version of the feature (i.e., a new or updated client) can determine whether the server it is connecting to supports the newer version of the feature. It is capable of interoperating with newer servers that support only the updated feature as well as ones that support both versions.
  • A client that supports both the older and newer version of the feature can determine which version of the particular feature is supported by the server it is working with.
  • その機能の以前のバージョンのみを使用するクライアント（つまり、修正されていない古いクライアント）は、接続先のサーバーがその機能の古いバージョンをサポートしているかどうかを判断できます。このクライアントは、修正されていないプロトコルのみをサポートする古いサーバーとも、両方のバージョンをサポートするサーバーとも相互運用できます。
  • その機能の修正されたバージョンのみをサポートするクライアント（つまり、新しいクライアントまたは更新されたクライアント）は、接続先のサーバーがその機能の新しいバージョンをサポートしているかどうかを判断できます。このクライアントは、更新された機能のみをサポートする新しいサーバーとも、両方のバージョンをサポートするサーバーとも相互運用できます。
  • その機能の古いバージョンと新しいバージョンの両方をサポートするクライアントは、やり取りしているサーバーがその特定の機能のどちらのバージョンをサポートしているかを判断できます。

Based on the type of server:

サーバーの種類に基づくと、次のようになります。

  • A server that supports only the earlier version of the feature (i.e., an older unfixed server) can only successfully interoperate with clients implementing the older version. However, clients that do not implement the older version of the feature can easily determine that the feature cannot be used on that server.
  • A server that supports only the newer version of the feature (i.e., a new or updated server) can only successfully interoperate with newer clients. However, older clients can easily determine that the feature cannot be used on that server. In the case of OPTIONAL features, clients can be expected to deal with non-support of that particular feature.
  • A server that supports both the older and newer versions of the feature can interoperate with all client variants.
  • その機能の以前のバージョンのみをサポートするサーバー（つまり、修正されていない古いサーバー）は、古いバージョンを実装しているクライアントとしか問題なく相互運用できません。ただし、その機能の古いバージョンを実装していないクライアントは、そのサーバーではその機能を使用できないことを容易に判断できます。
  • その機能の新しいバージョンのみをサポートするサーバー（つまり、新しいサーバーまたは更新されたサーバー）は、新しいクライアントとしか問題なく相互運用できません。ただし、古いクライアントは、そのサーバーではその機能を使用できないことを容易に判断できます。選択可能な（OPTIONAL）機能の場合、クライアントはその特定の機能が非サポートであることに対処できると期待できます。
  • その機能の古いバージョンと新しいバージョンの両方をサポートするサーバーは、すべてのクライアントのバリアントと相互運用できます。

By using extensions in this manner, the protocol creates a clear path that preserves the functioning of existing clients and servers and allows client and server implementers to adopt the new version of the feature at a reasonable pace.

このように拡張を使用することで、プロトコルは、既存のクライアントとサーバーの機能を維持し、かつクライアントとサーバーの実装者がその機能の新しいバージョンを妥当なペースで採用できるようにする、明確な道筋を作り出します。

9.3. XDR Corrections to REQUIRED Features

9.3. REQUIRED機能に対するXDRの修正

Interoperability issues in this case are similar to those for the OPTIONAL case described above (in Section 9.2). However, because the use of the uncorrected version is REQUIRED, servers have to support this until there is a minor version change. Nevertheless, there is the opportunity for clients and servers to implement the corrected version, while maintaining necessary interoperability with earlier implementations.

この場合の相互運用性の問題は、上記（セクション9.2）で説明した選択可能な（OPTIONAL）機能の場合の問題と似ています。ただし、未修正のバージョンの使用は「要求されています（REQUIRED）」であるため、サーバーはマイナーバージョンの変更があるまでそれをサポートしなければなりません。それでも、クライアントとサーバーには、以前の実装との必要な相互運用性を維持しつつ、修正されたバージョンを実装する機会があります。

The following types of servers can exist:

次の種類のサーバーが存在し得ます。

  • Servers only aware of and supporting the uncorrected version, such as servers developed before the issue requiring correction was known.
  • Servers aware of both versions while only supporting the uncorrected version.
  • Servers aware of and supporting both versions.
  • 未修正のバージョンのみを認識しサポートするサーバー。たとえば、修正を必要とする問題が知られる前に開発されたサーバーです。
  • 両方のバージョンを認識しているが、未修正のバージョンのみをサポートするサーバー。
  • 両方のバージョンを認識しサポートするサーバー。

With the exception of clients that do not use the feature in question, the following sorts of clients may exist:

当該機能を使用しないクライアントを除くと、次の種類のクライアントが存在し得ます。

  • Clients only aware of and prepared to use the uncorrected version, such as those developed before the issue requiring correction was known.

    Clients developed before the correction was defined would be of this type. They would be capable of interoperating with all of the types of servers listed above, but could not use the corrected version.

  • Clients aware of both versions while only prepared to use the uncorrected version.

    Some clients developed or modified after the correction was defined would be of this type, until they were modified to support the corrected version. They would also be capable of interoperating with all of the types of servers listed above, but could not use the corrected version.

  • Clients aware of and prepared to use either version.

    Such clients would be capable of interoperating with all of the types of servers listed above, and could use the corrected version with servers that supported it.

  • Clients aware of both versions while only prepared to use the newer, corrected version.

    Such clients would only be capable of interoperating with servers that supported the corrected version. With other types of servers, they could determine the absence of appropriate support at an early stage and treat the minor version in question as unsupported by the server. Such clients are only likely to be deployed when the majority of servers support the corrected version.

  • 未修正のバージョンのみを認識し、それを使用する準備ができているクライアント。たとえば、修正を必要とする問題が知られる前に開発されたクライアントです。

    修正が定義される前に開発されたクライアントは、この種類になります。これらのクライアントは、上記に挙げたすべての種類のサーバーと相互運用できますが、修正されたバージョンは使用できません。

  • 両方のバージョンを認識しているが、未修正のバージョンを使用する準備しかできていないクライアント。

    修正が定義された後に開発または変更されたクライアントの一部は、修正されたバージョンをサポートするように変更されるまでは、この種類になります。これらのクライアントも、上記に挙げたすべての種類のサーバーと相互運用できますが、修正されたバージョンは使用できません。

  • どちらのバージョンも認識し、使用する準備ができているクライアント。

    そのようなクライアントは、上記に挙げたすべての種類のサーバーと相互運用でき、修正されたバージョンをサポートするサーバーとの間ではそれを使用できます。

  • 両方のバージョンを認識しているが、新しい修正されたバージョンを使用する準備しかできていないクライアント。

    そのようなクライアントは、修正されたバージョンをサポートするサーバーとしか相互運用できません。他の種類のサーバーに対しては、適切なサポートがないことを早い段階で判断し、当該マイナーバージョンがそのサーバーではサポートされていないものとして扱うことができます。そのようなクライアントが展開されるのは、大多数のサーバーが修正されたバージョンをサポートするようになってからである可能性が高いでしょう。

9.4. Addressing XDR Corrections in Later Minor Versions

9.4. 後のマイナーバージョンでのXDRの修正への対処

As described in Sections 9.2 and 9.3, a corrected XDR can be incorporated in an existing minor version and be used, while an existing uncorrected version is still supported. Nevertheless, the uncorrected version will remain part of the protocol until its status is changed in a later minor version.

セクション9.2と9.3で説明したように、修正されたXDRは、既存の未修正のバージョンが引き続きサポートされている間に、既存のマイナーバージョンに組み込んで使用できます。それでも、未修正のバージョンは、後のマイナーバージョンでそのステータスが変更されるまで、プロトコルの一部であり続けます。

One possible change that could be made in a later minor version is to define the uncorrected version as mandatory to not implement. Because of the difficulty of determining that no clients depend on support for the uncorrected version, it is unlikely that this step would be appropriate for a considerable time.

後のマイナーバージョンで行える変更の1つとして、未修正のバージョンを実装しないことが必須と定義することが考えられます。未修正のバージョンのサポートに依存しているクライアントが存在しないと判断するのは難しいため、この手順が適切となるのはかなり先のことになるでしょう。

In the case of a correction to a REQUIRED feature, there are a number of less disruptive changes that could be made earlier:

「要求されています（REQUIRED）」機能に対する修正の場合、より早い時期に行える、混乱の少ない変更がいくつかあります。

  • Changing the uncorrected version from REQUIRED to OPTIONAL while REQUIRING that servers support at least one of the two versions.

    This would allow new server implementations to avoid support for the uncorrected version.

  • Changing the corrected version from OPTIONAL to REQUIRED, making both versions REQUIRED.

    This would allow new clients to depend on support for the corrected version being present.

  • Changing the uncorrected version from REQUIRED to OPTIONAL while changing the corrected version from OPTIONAL to REQUIRED.

    This would complete the shift to the corrected version once clients are prepared to use the corrected version.

  • サーバーが2つのバージョンのうち少なくとも1つをサポートすることを要求（REQUIRING）しつつ、未修正のバージョンを「要求されています（REQUIRED）」から「選択できます（OPTIONAL）」に変更すること。

    これにより、新しいサーバー実装は未修正のバージョンのサポートを避けられるようになります。

  • 修正されたバージョンを「選択できます（OPTIONAL）」から「要求されています（REQUIRED）」に変更し、両方のバージョンを「要求されています（REQUIRED）」にすること。

    これにより、新しいクライアントは修正されたバージョンのサポートが存在することに依存できるようになります。

  • 未修正のバージョンを「要求されています（REQUIRED）」から「選択できます（OPTIONAL）」に変更すると同時に、修正されたバージョンを「選択できます（OPTIONAL）」から「要求されています（REQUIRED）」に変更すること。

    これにより、クライアントが修正されたバージョンを使用する準備ができた時点で、修正されたバージョンへの移行が完了します。

In making such changes, interoperability issues would need to be carefully considered.

そのような変更を行う際には、相互運用性の問題を慎重に検討する必要があります。
