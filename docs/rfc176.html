RFC 176

Comments on Byte Size for Connections

RFC 176

コネクションのバイトサイズに対するコメント

Abstract

概要

There are at least the following three views on the use of byte size for network connections*:

ネットワークコネクションでのバイトサイズの使い方については、少なくとも次の3つの見解があります*。

  1. Byte size should not be used at all.
  2. Byte size is solely for the convenience of NCP's.
  3. Byte size choice is a user-level prerogative.
  1. バイトサイズはまったく使うべきではない。
  2. バイトサイズはもっぱらNCPの都合のためのものである。
  3. バイトサイズの選択はユーザーレベルの特権である。

According to the first view, network connections are bit streams, and messages should contain bit counts (i.e., a byte size of 1). This view existed before the "Glitch Cleaning" of RFC 107, and was discarded in favour of byte stream because of stated reasons of efficiency in storage management and message concatenation.

1つ目の見解によれば、ネットワークコネクションはビットストリームであり、メッセージにはビット数を含めるべきです（つまり、バイトサイズは1です）。この見解はRFC 107の「グリッチ除去（Glitch Cleaning）」以前に存在していましたが、記憶域管理とメッセージ連結の効率という理由が示され、バイトストリームを採用するために捨てられました。

The second view represents a special interpretation of RFC 107. According to this interpretation, byte size is entirely a 2nd level (i.e., NCP) issue. There is no requirement that 3rd level user processes be able to specify byte size. This view is indicated in RFC 151 by Shoshani.

2つ目の見解は、RFC 107の特殊な解釈を表しています。この解釈によれば、バイトサイズは完全に第2レベル（つまりNCP）の問題です。第3レベルのユーザープロセスがバイトサイズを指定できる必要はありません。この見解は、ShoshaniによるRFC 151に示されています。

* Byte size for connection is the byte size selected by sending NCP, as explained in RFC 107 (Output of Host-Host Protocol Glitch Cleaning Committee).

* コネクションのバイトサイズとは、RFC 107（Output of Host-Host Protocol Glitch Cleaning Committee）で説明されているとおり、送信側のNCPが選択したバイトサイズのことです。

According to the third view user processes are always allowed to choose byte size for connection, either explicitly (specify a specific byte size parameter) or implicitly (byte size depends on I/O mode). An NCP is allowed to use a default byte size, if the user does not specify it.

3つ目の見解によれば、ユーザープロセスは常に、明示的に（特定のバイトサイズのパラメーターを指定して）、または暗黙的に（バイトサイズが入出力モードに依存する形で）、コネクションのバイトサイズを選択できます。ユーザーが指定しない場合、NCPはデフォルトのバイトサイズを使ってもかまいません。

The Correct View

正しい見解

The third view should be considered the correct interpretation of RFC 107. In fact, RFC 107 states on page 2, "the choice of the byte size for a connection is a 3rd level protocol issue." To be consistent with TELNET, ICP, and other 3rd level protocols which require that a specific byte size be used for connection, it is imperative that corresponding 3rd level processes be able to specify (and_impose) a particular byte size to the NCP. NCP implementors should take note of it.

3つ目の見解を、RFC 107の正しい解釈とみなすべきです。実際、RFC 107の2ページには「コネクションのバイトサイズの選択は、第3レベルのプロトコルの問題である」と書かれています。コネクションに特定のバイトサイズを使うことを要求するTELNET、ICP、その他の第3レベルのプロトコルとの一貫性を保つためには、対応する第3レベルのプロセスが、特定のバイトサイズをNCPに指定（そして強制）できることが不可欠です。NCPの実装者はこのことに留意すべきです。

On Specifying Fixed Byte Sizes in 3rd Level Protocols

第3レベルのプロトコルで固定のバイトサイズを指定することについて

Holding the view that byte size choice is a 3rd level issue, we are still faced with the following two questions. First, is it appropriate for 3rd level protocols to legislate a specific byte size for all connections using that protocol? Second, if it is appropriate to specify byte size, then what should this choice be?

バイトサイズの選択は第3レベルの問題であるという見解に立っても、なお次の2つの疑問に直面します。1つ目は、第3レベルのプロトコルが、そのプロトコルを使うすべてのコネクションに対して特定のバイトサイズを定めるのは適切なのかという疑問です。2つ目は、バイトサイズを指定するのが適切だとして、どのようなバイトサイズを選ぶべきかという疑問です。

There are two arguments in favour of using specific byte size in 3rd level protocols. First is that a potential mismatch problem exists because RFC 107 does not require that NCPs be capable of handling all byte sizes 1 through 255. Using a fixed byte size of 8-bits or 8-bit multiples resolves the problem as this is acceptable to all hosts (including terminal IMPs).

第3レベルのプロトコルで特定のバイトサイズを使うことを支持する論拠が2つあります。1つ目は、RFC 107はNCPが1から255までのすべてのバイトサイズを扱えることを要求していないため、不一致の問題が起こる可能性があるということです。8ビットまたは8ビットの倍数の固定バイトサイズを使えば、これは（端末IMPを含む）すべてのホストで受け入れられるので、この問題は解決します。

The second argument is one of efficiency. If it is agreed before hand that only a specific byte size would be used, it is possible to make programs more efficient (i.e., reduce program space, and possibly run time). The efficiency argument assumes that the byte size for connection represents the natural byte structure of data being transferred over the connection.

2つ目の論拠は効率です。特定のバイトサイズだけを使うことを事前に合意しておけば、プログラムをより効率的に（つまり、プログラムの領域を小さく、場合によっては実行時間も短く）できます。この効率の論拠は、コネクションのバイトサイズが、そのコネクションで転送されるデータの自然なバイト構造を表していることを前提としています。

For TELNET and ICP, the byte size choice is straight forward as data is naturally in 8-bit multiples (8-bit ASCII characters in TELNET, and 32-bit socket numbers in ICP). But for data transfer protocols, the byte size choice is more complex, as data may be structured in a variety of byte sizes. Specifying a byte size for a data transfer connection reduces efficiency in instances where connection byte size does not correspond to data byte size. Further, filler fields will be required for data blocks which are not a multiple of the fixed byte size. This imposes an additional overhead.

TELNETとICPでは、データは本来8ビットの倍数（TELNETでは8ビットのASCII文字、ICPでは32ビットのソケット番号）なので、バイトサイズの選択は簡単です。しかし、データ転送プロトコルでは、データがさまざまなバイトサイズで構造化されている可能性があるので、バイトサイズの選択はより複雑です。データ転送コネクションのバイトサイズを指定すると、コネクションのバイトサイズがデータのバイトサイズに対応しない場合に効率が低下します。さらに、固定バイトサイズの倍数でないデータブロックには、埋め草のフィールドが必要になります。これは追加のオーバーヘッドとなります。

Even if all hosts were to accept arbitrary byte sizes, and the 3rd level protocol does not legislate a specific byte size, the inefficiency problem will not be solved entirely. Under current specifications "the byte size is fixed for the life of a connection".* This means that byte size cannot be varied during the life of a connection even if structure of data varies. The problem of inefficiency is solved only for instances in which data has a constant byte structure.

たとえすべてのホストが任意のバイトサイズを受け入れ、第3レベルのプロトコルが特定のバイトサイズを定めないとしても、非効率の問題が完全に解決されるわけではありません。現在の仕様では、「バイトサイズはコネクションの存続期間中は固定される」となっています*。つまり、データの構造が変わっても、コネクションの存続期間中にバイトサイズを変えることはできません。非効率の問題が解決するのは、データが一定のバイト構造を持つ場合だけです。

Given the current state of the network, it appears that specifying fixed byte size in 3rd level protocols is a good idea. This eliminates the potential byte size mismatch problem, and improves efficiency at least for TELNET and ICP. In data transfer, the efficiency issue is more complex, as discussed earlier. It is not clear that overall efficiency would be degraded if a fixed byte size was required.

ネットワークの現状を踏まえると、第3レベルのプロトコルで固定のバイトサイズを指定するのはよい考えだと思われます。これにより、バイトサイズの不一致の問題が起こる可能性がなくなり、少なくともTELNETとICPについては効率が向上します。データ転送では、先に述べたように、効率の問題はより複雑です。固定のバイトサイズを必須にした場合に、全体的な効率が低下するかどうかは明らかではありません。

On Reopening the Byte Size Issue

バイトサイズの問題を再検討することについて

The above discussion exposes certain weaknesses in the efficiency arguments for having byte streams on network connections. In moving from bit stream to byte stream, we may have lost generality, and it is not clear how much overall efficiency is gained. Sometimes, the gain in NCP efficiency may be at the expense of user process efficiencies.

以上の議論から、ネットワークコネクションでバイトストリームを使うことを支持する効率の論拠には、いくつかの弱点があることがわかります。ビットストリームからバイトストリームに移行したことで、私たちは汎用性を失ったかもしれず、しかも全体的な効率がどれだけ向上したのかは明らかではありません。NCPの効率の向上が、ユーザープロセスの効率を犠牲にして得られている場合もあるかもしれません。

* RFC 107の2ページ

It is also clear that for efficiency arguments to hold, the byte size choice should not be an NCP prerogative. It is the combined efficiency, rather than NCP efficiency which should be our primary concern. Restricting byte size choice to NCPs has the further disadvantage of potential byte size mismatch not only between communicating NPCs but also at the user-NCP interface. Therefore, allowing a user process to specify byte size is a step in the right direction, given that we have adopted byte streams.

また、効率の論拠が成り立つためには、バイトサイズの選択がNCPの特権であってはならないことも明らかです。私たちが第一に考慮すべきなのは、NCPの効率ではなく、全体を合わせた効率です。バイトサイズの選択をNCPに限定すると、通信するNCPの間だけでなく、ユーザーとNCPのインターフェイスでもバイトサイズの不一致が起こる可能性があるという欠点もあります。したがって、バイトストリームを採用した以上、ユーザープロセスがバイトサイズを指定できるようにすることは正しい方向への一歩です。

It is our opinion that the issue of bit stream and byte stream be set aside until serious consideration can be given to a major Host-Host Protocol overhaul. At a later stage we will have a better idea of the relative efficiency merits.

ビットストリームとバイトストリームの問題は、ホスト間プロトコル（Host-Host Protocol）の大幅な見直しを真剣に検討できるようになるまで保留すべきだというのが私たちの意見です。後の段階になれば、それぞれの効率上の利点について、よりよく把握できているでしょう。
