RFC 180

File System Questionnaire

RFC 180

ファイルシステムに関するアンケート

Abstract

概要

As noted in RFC #164 (page 35), a subcommittee of the NWG, under the chairmanship of Abhay Bhushan, is currently generating proposals for a "data transfer protocol" and a "file transfer protocol".

RFC #164（35ページ）で述べられているように、NWGの小委員会が、Abhay Bhushanを委員長として、現在「データ転送プロトコル（data transfer protocol）」と「ファイル転送プロトコル（file transfer protocol）」の提案を作成しています。

The subcommittee has decided that the file transfer protocol should provide standard methods for requesting the transfer of a file but should not, at this time, attempt to standardize file naming conventions, access control conventions, and the like. Thus a user who is, for example, trying to store a file on a remote Host will be required to use the file naming conventions appropriate to the remote Host.

小委員会は、ファイル転送プロトコルではファイルの転送を要求する標準的な方法を提供すべきですが、現時点ではファイルの命名規則やアクセス制御の規則などを標準化しようとはすべきではないと判断しました。したがって、たとえばリモートのホストにファイルを保存しようとするユーザーは、そのリモートのホストに適したファイル命名規則を使用する必要があります。

Given the above point of view, it becomes imperative for users to have some source of information about Host file conventions. Such information, once compiled, will also serve as input to possible standardization efforts of the file transfer subcommittee. For this reason Abhay has asked me to solicit information on file conventions from the Host organizations. What follows is a description of the kinds of information of interest. I am well aware of the fact that many of you are tired of writing system descriptions; Xerox copies of short sections of your local documentation are fine if the result is complete and comprehensible. (In the case that your Host will never permit network use of your file system, a note to that effect would be sufficient.)

上記の観点からすると、ユーザーがホストのファイル規則についての情報源を持つことが不可欠になります。そのような情報は、まとめられれば、ファイル転送小委員会による今後の標準化の取り組みへの入力にもなります。そのため、Abhayから、ホストの各組織にファイル規則についての情報提供を依頼するよう頼まれました。以下は、関心のある情報の種類の説明です。多くの方がシステムの説明を書くことにうんざりしていることはよく承知しています。結果が完全で理解できるものであれば、ローカルの文書の短い節をゼロックスでコピーしたものでもかまいません。（あなたのホストがネットワークからのファイルシステムの使用を今後も決して許可しない場合は、その旨のメモで十分です。）

Information Requested

求める情報

  1. File naming conventions - We (loosely) define a pathname to be the data string which must be input to the file system by a user (a network user if your system makes a distinction between local and network users) in order to identify a file. We are interested in syntax, semantics, and defaults. Typical components of pathnames are:

    • "device" fields
    • user names
    • version numbers
    • index names
    • punctuation marks

    Common types of defaults are:

    • device is disk
    • version number is largest in system

    For hierarchical file structures, descriptions may be fairly complex, but with lots of defaults; in such cases an illustration of a "normal" pathname might be helpful.

  2. Access control mechanisms - Access control mechanisms range from simply knowledge of a file's pathname to elaborate hierarchies of group-project-task-username membership with passwords and separate controls for reading and writing. There are two aspects of the access control mechanism which are of interest:

    1. A description of what inputs the user should give the file system, both at the time of file creation and at the time of retrieval, in order to define the permitted modes of access and to gain access. What are the syntax and semantics of these inputs?
    2. A description of the ways in which the access control mechanism is designed to help (or hinder) the sharing of files. For example, may two users "simultaniously" update a given file? May the creator of the file define a set of authorized users to the file system (and how)? Is it possible to define different access controls for various subunits of a given file?

  3. Directories - Many systems maintain file directories which are designed to be helpful to the user. A directory might, for example, provide a list of all files created by a particular individual, along with some information regarding file size, file structure, access controls, etc. In general, such systems allow the user to input a pathname and retrieve the directory to which that pathname refers. Aspects of the directory structure of interest are:

    1. What are the syntax and semantics of a directory pathname?
    2. What use is a directory, i.e., what type of information does the directory contain?
    3. What access controls are used for access to the directories? For example, must a user supply a password in order to retrieve a directory, and is this password typically the same as the password he would use to retrieve a file listed in that directory.

  4. Commands and functions of the file system - A general description of what the file system is designed to do would be useful. For example, the system might simply accept an entire file and store it sequentially on a tape; with the only mode of retrieval being to retrieve the entire file. On the other hand, the system might provide the ability to access any "subfield" with a unique pathname. Perhaps there is the ability to restructure a file, change the access control, delete all the fields associated with a directory, etc. We realize that this aspect of the file system begins to overlap the area of "data management", which is the responsibility of another subcommittee; therefore, use your judgement as to what functions are an intrinsic aspect of the file-handling system and which are aspects of "data-management".

  5. Internal representation and I/O modes - The remote user of a file system will normally be interested in internal representation of data only insofar as that representation of data is reflected in the I/O interface between the file system and the network. For example, if all of the file system's I/O is in 8-bit ASCII characters, then the user is unlikely to care if they are stored in ASCII, EBCDIC, or some other form. However, if an alternate transmission mode is available it may be useful; for example, two PDP-10's, both of which store 5 characters and one "filler" bit per word, might find it advantageous to transfer information in this mode rather than converting between internal representation and 8-bit ASCII for each character. Other information on internal representation which would be of interest to the user might include (if applicable):

    • range of numeric data permitted
    • maximum text string lengths
    • whether the user must indicate "record" boundaries on input
    • what "logical structure" information the user may specify for a new file, and what he must specify
    • whether the user must specify the file size before beginning input, and how he does it

  6. Undoubtedly, there will be aspects of each file system which don't fit neatly into the categories above, but which users will find important or essantial in using the system. These should be identified and described if possible.

  1. ファイルの命名規則 - パス名（pathname）とは、（大まかに言えば）ファイルを識別するためにユーザー（あなたのシステムがローカルのユーザーとネットワークのユーザーを区別する場合はネットワークのユーザー）がファイルシステムに入力しなければならないデータ文字列のことです。関心があるのは、構文、意味、デフォルトです。パス名の典型的な構成要素は次のとおりです。

    • 「デバイス（device）」フィールド
    • ユーザー名
    • バージョン番号
    • インデックス名
    • 区切り記号

    よくあるデフォルトの種類は次のとおりです。

    • デバイスはディスクである
    • バージョン番号はシステム内で最大のものである

    階層的なファイル構造の場合、説明はかなり複雑になるかもしれませんが、デフォルトも多くあります。そのような場合は、「通常の」パス名の例を示すと役立つかもしれません。

  2. アクセス制御の仕組み - アクセス制御の仕組みには、単にファイルのパス名を知っていればよいだけのものから、パスワードや読み取りと書き込みの個別の制御を伴う、グループ-プロジェクト-タスク-ユーザー名の所属からなる精巧な階層まで、さまざまなものがあります。アクセス制御の仕組みについて関心があるのは、次の2つの側面です。

    1. 許可するアクセスのモードを定義したり、アクセスを得たりするために、ファイルの作成時と取得時の両方で、ユーザーがファイルシステムにどのような入力を与えるべきかの説明。それらの入力の構文と意味はどのようなものですか？
    2. アクセス制御の仕組みが、ファイルの共有をどのように助ける（または妨げる）ように設計されているかの説明。たとえば、2人のユーザーが特定のファイルを「同時に」更新できますか？ファイルの作成者は、許可するユーザーの集合をファイルシステムに対して定義できますか（またその方法は）？特定のファイルのさまざまな下位単位に対して、異なるアクセス制御を定義できますか？

  3. ディレクトリー - 多くのシステムは、ユーザーの役に立つように設計されたファイルディレクトリーを管理しています。たとえば、ディレクトリーは特定の個人が作成したすべてのファイルの一覧を、ファイルのサイズ、ファイルの構造、アクセス制御などに関する情報とともに提供するかもしれません。一般に、そのようなシステムでは、ユーザーがパス名を入力して、そのパス名が指すディレクトリーを取得できます。ディレクトリー構造について関心がある点は次のとおりです。

    1. ディレクトリーのパス名の構文と意味はどのようなものですか？
    2. ディレクトリーは何に使われますか？つまり、ディレクトリーにはどのような種類の情報が含まれていますか？
    3. ディレクトリーへのアクセスには、どのようなアクセス制御が使われていますか？たとえば、ユーザーはディレクトリーを取得するためにパスワードを提示しなければなりませんか？また、そのパスワードは通常、そのディレクトリーに載っているファイルを取得するために使うパスワードと同じですか？

  4. ファイルシステムのコマンドと機能 - ファイルシステムが何をするように設計されているかの一般的な説明があると役立ちます。たとえば、システムはファイル全体を受け取ってテープに順番に保存するだけで、取得の方法はファイル全体を取得することしかないかもしれません。一方、システムは一意のパス名を持つ任意の「サブフィールド」にアクセスする機能を提供するかもしれません。ファイルの再構成、アクセス制御の変更、ディレクトリーに関連づけられたすべてのフィールドの削除などの機能があるかもしれません。ファイルシステムのこの側面は、別の小委員会の担当である「データ管理（data management）」の領域と重なり始めることは承知しています。したがって、どの機能がファイル処理システムに本質的な側面で、どの機能が「データ管理」の側面であるかは、あなたの判断に任せます。

  5. 内部表現とI/Oモード - ファイルシステムのリモートのユーザーは、通常、データの内部表現には、その表現がファイルシステムとネットワークの間のI/Oインターフェイスに反映される範囲でしか関心を持ちません。たとえば、ファイルシステムのI/Oがすべて8ビットのASCII文字で行われるのであれば、ユーザーはそれらがASCII、EBCDIC、その他の形式のどれで保存されているかを気にすることはまずないでしょう。しかし、別の伝送モードが利用できるなら、それが役立つ場合があります。たとえば、どちらも1ワードあたり5文字と1つの「埋め草（filler）」ビットを保存する2台のPDP-10は、1文字ごとに内部表現と8ビットのASCIIとの間で変換するよりも、このモードで情報を転送するほうが有利だと考えるかもしれません。ユーザーにとって関心がありそうな内部表現に関するその他の情報には、（該当する場合）次のものが考えられます。

    • 許される数値データの範囲
    • テキスト文字列の最大長
    • ユーザーが入力時に「レコード」の境界を示さなければならないかどうか
    • 新しいファイルに対してユーザーがどのような「論理構造」の情報を指定でき、何を指定しなければならないか
    • ユーザーが入力を始める前にファイルサイズを指定しなければならないかどうか、またその指定方法

  6. 各ファイルシステムには、上記の分類にうまく当てはまらないものの、ユーザーがシステムを使ううえで重要または不可欠だと考える側面がきっとあるでしょう。可能であれば、それらを特定して説明してください。
