RFC 4027

Domain Name System Media Types

RFC 4027

ドメインネームシステムのメディアタイプ

Abstract

概要

This document registers the media types application/dns and text/dns in accordance with RFC 2048. The application/dns media type is used to identify data on the detached Domain Name System (DNS) format described in RFC 2540. The text/dns media type is used to identify master files as described in RFC 1035.

この文書は、RFC 2048に従ってメディアタイプapplication/dnsとtext/dnsを登録します。application/dnsメディアタイプは、RFC 2540で説明されている切り離された（detached）ドメインネームシステム（DNS）形式のデータを識別するために使用します。text/dnsメディアタイプは、RFC 1035で説明されているマスターファイルを識別するために使用します。

1. Introduction

1. はじめに

Domain Name System (DNS) [1] information is traditionally stored in text files, so-called master files or zone files. The format is described in section 5 of RFC 1035 [2].

ドメインネームシステム（DNS）[1]の情報は、伝統的にテキストファイル、いわゆるマスターファイルまたはゾーンファイルに格納されています。その形式はRFC 1035[2]のセクション5で説明されています。

DNS data can also be stored in a "detached" format, intended for archiving purposes, described in RFC 2540 [4].

DNSデータは、アーカイブ目的を意図した「切り離された（detached）」形式で格納することもできます。この形式はRFC 2540[4]で説明されています。

This document registers MIME media types for the two data formats, with the registration procedures described in RFC 2048 [3].

この文書は、RFC 2048[3]で説明されている登録手続きに従って、この2つのデータ形式のためのMIMEメディアタイプを登録します。

2. MIME Type Registration of application/dns

2. application/dnsのMIMEタイプ登録

To:
ietf-types@iana.org
Subject:

MIME media type name:
application
MIME subtype name:
dns
Required parameters:
None.
Optional parameters:
None.
Encoding considerations:
The data format is binary, and data must be transfered unmodified. Using encodings intended for textual parts is not recommended.
Security considerations:
This media type identifies content as being detached DNS information, as documented in RFC 2540 [4]. This data may be security relevant as per RFC 2538 [7] or may be secured information as per RFC 2535 [6]. Securing the content further may be done with standard techniques, such as OpenPGP [5] or CMS [9], but this is outside of the scope here. Further security assessments are not available at this point.
Interoperability considerations:
The encoding of detached DNS information is, unlike textual master files, well defined. No further interoperability considerations are known.
Published specification:
The format of data that could be tagged with this media type is documented in RFC 2540 [4].
Applications that use this media type:
DNS-related software, including software storing and using certificates stored in DNS.

3. MIME Type Registration of text/dns

3. text/dnsのMIMEタイプ登録

To:
ietf-types@iana.org
Subject:
Registration of MIME media type text/dns
MIME media type name:
text
MIME subtype name:
dns
Required parameters:
None.
Optional parameters:
None.
Encoding considerations:
The data is textual and should be transfered in a line-oriented mode. Text literals may contain CRLF within the text. Binary transport is possible between systems that use the same end-of-line conventions. Master files are in general ASCII, but non-ASCII octet values may occur and are treated as opaque values by DNS software (compare RFC 1035, section 5). The master file format permits encoding arbitrary octet values by using the "\DDD" encoding. The use of "\DDD" encoding can be more reliable than transporting non-ASCII through MIME transports, if data passes through a gateway that re-encodes the character data.
Security considerations:
This media type identifies content as being DNS information in "master file" format, as documented in RFC 1035 [2]. The DNS data may be security relevant as per to RFC 2538 [7], or may be secured information as per to RFC 2535 [6]. Securing the content further may be done with standard techniques, such as OpenPGP [5] or CMS [9], but this is outside of the scope here. Further security assessments are not available at this point.
Interoperability considerations:
There are interoperability concerns with master files, due to the widespread use of vendor-specific extensions. Non-ASCII comments within master files may have been encoded in locally chosen character sets, which may be difficult to transport interoperably. Non-ASCII data in general can become corrupted by re-encoding gateways. To achieve interoperability, one can use the master file format described in the specification and the "\DDD" encoding for non-ASCII octets. Further interoperability issues with unrecognized RR types exist, which may be handled as discussed in section 5 of RFC 3597 [8].
Published specification:
The format of data that could be tagged with this MIME type is documented in RFC 1035 [2].
Applications that use this media type:
DNS-related software, including software storing and using certificates stored in DNS.
Additional information:
Magic number(s):
None.
File extension(s):
'soa' and 'zone' are known to be used.
Macintosh file type code(s):
Unknown.

LIMITED USE

simon@josefsson.org

エンコーディングに関する考慮事項：
データはテキストであり、行指向のモードで転送すべきです。テキストのリテラルには、テキスト内にCRLFが含まれる場合があります。同じ行末規則を使用するシステム間では、バイナリー転送も可能です。マスターファイルは一般にASCIIですが、非ASCIIのオクテット値が現れることもあり、DNSソフトウェアはそれを不透明な値として扱います（RFC 1035のセクション5と比較してください）。マスターファイル形式では、「\DDD」エンコーディングを使って任意のオクテット値をエンコードできます。文字データを再エンコードするゲートウェイをデータが通過する場合、「\DDD」エンコーディングを使うほうが、非ASCIIをMIMEトランスポートで転送するよりも信頼性が高くなることがあります。
セキュリティーに関する考慮事項：
このメディアタイプは、RFC 1035[2]で文書化されているとおり、コンテンツが「マスターファイル」形式のDNS情報であることを識別します。このDNSデータは、RFC 2538[7]によればセキュリティーに関連する場合があり、RFC 2535[6]によれば保護された情報である場合があります。OpenPGP[5]やCMS[9]などの標準的な手法でコンテンツをさらに保護することもできますが、それはここでの範囲外です。現時点では、これ以上のセキュリティー評価はありません。
相互運用性に関する考慮事項：
ベンダー固有の拡張が広く使われているため、マスターファイルには相互運用性の懸念があります。マスターファイル内の非ASCIIのコメントは、ローカルで選択された文字セットでエンコードされている場合があり、相互運用可能な形で転送するのが難しいことがあります。一般に、非ASCIIのデータは再エンコードを行うゲートウェイによって破損する可能性があります。相互運用性を実現するには、仕様で説明されているマスターファイル形式と、非ASCIIのオクテットに対する「\DDD」エンコーディングを使用できます。認識されないRRタイプについてはさらに相互運用性の問題がありますが、これはRFC 3597[8]のセクション5で議論されているとおりに処理できます。
公開された仕様：
このMIMEタイプでタグ付けされうるデータの形式は、RFC 1035[2]で文書化されています。
このメディアタイプを使用するアプリケーション：
DNSに格納された証明書を格納・使用するソフトウェアを含む、DNS関連のソフトウェア。
追加情報：
マジックナンバー：
なし。
ファイル拡張子：
「soa」と「zone」が使われていることが知られています。
Macintoshファイルタイプコード：
不明。
