RFC 624

Comments on the File Transfer Protocol

RFC 624

ファイル転送プロトコルに関するコメント

Abstract

概要

This document replaces RFC 607, which was inadvertently released while still in rough draft form. It would be appreciated if RFC 607 were disregarded, and this document considered the accurate statement of the authors' opinions.

この文書は、まだ大まかな草稿の段階であったのに誤って公開されてしまったRFC 607を置き換えるものです。RFC 607は無視していただき、この文書を著者らの意見を正確に述べたものとみなしていただけると幸いです。

There are several aspects of the File Transfer Protocol of RFC 542 that constitute serious drawbacks. Some of these are quite basic in nature, and imply substantial design changes; these will be discussed in a later RFC. Others could be remedied with very little effort, and this should be done as soon as possible.

RFC 542のファイル転送プロトコル（File Transfer Protocol）には、重大な欠点となっている点がいくつかあります。そのうちのいくつかは本質的にかなり根本的なもので、大幅な設計変更を必要とします。これらについては、後のRFCで論じます。その他のものはごくわずかな労力で改善でき、できるだけ早く改善すべきです。

Following is a list of those problems that can be easily solved, together with their proposed solutions:

以下は、容易に解決できる問題と、その解決策の提案を一覧にしたものです。

  1. Once a server has been set to the state where he is "passive" with regard to establishment of data connections, there is no convenient way for the user to make him "active" again. The "REIN" command accomplishes this, but affects more than just the desired active/passive state. SOLUTION: define a new command, with a command verb of "ACTV", to mean that the server is to issue a CONNECT rather than a LISTEN on the data socket. If the server is already "active", the command is a no op. "ACTV" is to have the same reply codes as "PASV".
  2. Design of an FTP server or user would be simpler if all command verbs were the same length. While it is certainly possible to handle varying length verbs, fixed length string manipulation is in general easier to write and faster to run than varying length string manipulation, and it would seem that nothing is to be gained in this application by allowing varying length strings. SOLUTION: replace the only three-letter verb, "BYE", with a four-letter one, such as "QUIT", and constrain future command verbs to be four letters long.
  3. The order of the handshaking elements following a file transfer command is left unspecified. After sending a STOR command, for example, a user process has no way of knowing which to wait for first, the "250 FILE TRANSFER STARTED" reply, or establishment of the data connection. SOLUTION: specify that the server is to send a "250" reply before attempting to establish the data connection. If it is desired to check if the user is logged in, if the file exists, or if the user is to be allowed access to the file, these checks must be made before any reply is sent. The text of the "250" reply would perhaps be more appropriate as "250 OPENING DATA CONNECTION", since it comes before actual data transfer begins. If the server wishes to send an error reply in the event that the data connection cannot be opened, it is to be sent in lieu of the "252 TRANSFER COMPLETE" reply.
  4. Some hosts currently send an error reply on receipt of a command that is unimplemented because it is hot needed (e.g., "ACCT" or "ALLO"). Even though the text of the reply indicates that the command has been ignored, it is obviously impossible for a user process to know that there is no real "error". SOLUTION: require that any server that does not support a particular command because it is not needed in that system must return the success reply for that command.
  5. There is no specified maximum length of a TELNET command line, TELNET reply line, user name, password, account, or pathname. It is true that every system implementing an FTP server likely has different maxima for its own parameters, but it is inconvenient, at least in some systems, for the writer of an FTP user (which must converse with many FTP servers) to construct an indefinite length buffer. Similar difficulties confront the writer of a server FTP. SOLUTION: specify a maximum length for TELNET command lines, TELNET replies, user names, passwords, account numbers, and pathnames. This is to be done after conducting a Poll of serving sites concerning their individual maxima. If Network mail is to be included in FTP, the mail text, if sent over the TELNET connection, is to be subject to the same line length maximum.
  6. The notion of allowing continuation lines to start with arbitrary text solves a minor problem for a few server FTP implementors at the expense of creating a major problem for all user FTP implementors. The logic needed to decode a multi-line reply is unnecessarily complex, and made an order of magnitude more so by the fact that multi-line replies arc allowed to be nested. SOLUTION: assign a unique (numeric) reply code, such as "009", to be used on all lines of a multi-line reply after the first. The reply code used for this purpose must begin with "0" (it cannot be three blanks, for example), so that it will appear as extraneous to a user process by virtue of the already existing rules concerning reply code groupings.
  7. If it is the case that the above solution to (6) is not accepted, the fact that the maximum allowed level of nesting is left unspecified creates a hardship for implementors of user FTPs. This hardship is somewhat easily solved on a machine that has hardware stacks, but not so for other machines. SOLUTION: either disallow nested replies (preferred), or specify a maximum level of nesting of multi-line replies.
  8. The prose descriptions of the meanings of the various reply codes are in several cases unclear or ambiguous. For example, the code "020" is explained only as "announcing FTP". It is given as a reply that can be issued when a server cannot accept input immediately after an ICP, but its exact meaning is not obvious. Also. the code "331" is said to mean "ENTER ACCOUNT (if required as part of login sequence)", but is listed as a possible success reply for most of the commands. The explanation indicates that it is only valid in the login sequence, but the command-reply correspondence table implies that it also means, "I can't do that without an account". SOLUTION: an expanded effort should be made by those who originated the reply codes to define them more completely.
  1. いったんサーバーが、データコネクションの確立に関して「パッシブ」な状態に設定されると、ユーザーがサーバーを再び「アクティブ」にする便利な方法がありません。「REIN」コマンドを使えばこれを実現できますが、このコマンドは目的のアクティブ／パッシブの状態以外にも影響を及ぼします。解決策：コマンド動詞が「ACTV」である新しいコマンドを定義し、サーバーがデータソケット上でLISTENではなくCONNECTを発行することを意味するものとします。サーバーがすでに「アクティブ」な場合、このコマンドは何もしません。「ACTV」の応答コードは「PASV」と同じにします。
  2. すべてのコマンド動詞が同じ長さであれば、FTPサーバーやFTPユーザーの設計はより簡単になります。可変長の動詞を扱うことはもちろん可能ですが、一般に、固定長の文字列操作は可変長の文字列操作よりも書くのが簡単で、実行も高速です。また、このアプリケーションでは、可変長の文字列を許しても何も得るものはないように思われます。解決策：唯一の3文字の動詞である「BYE」を「QUIT」などの4文字の動詞に置き換え、今後のコマンド動詞は4文字の長さに制限します。
  3. ファイル転送コマンドに続くハンドシェイク要素の順序が規定されていません。たとえば、STORコマンドを送信した後、ユーザープロセスは、「250 FILE TRANSFER STARTED」応答とデータコネクションの確立のどちらを先に待てばよいかを知る方法がありません。解決策：サーバーは、データコネクションの確立を試みる前に「250」応答を送信するものと規定します。ユーザーがログインしているかどうか、ファイルが存在するかどうか、ユーザーにファイルへのアクセスを許可するかどうかを確認したい場合は、これらの確認を応答を送信する前に行わなければなりません。「250」応答は実際のデータ転送が始まる前に来るので、その本文は「250 OPENING DATA CONNECTION」とするほうがおそらく適切でしょう。データコネクションを開けなかった場合にサーバーがエラー応答を送信したいときは、「252 TRANSFER COMPLETE」応答の代わりにそれを送信するものとします。
  4. 現在、一部のホストは、不要であるために実装していないコマンド（たとえば「ACCT」や「ALLO」）を受信すると、エラー応答を送信します。応答の本文にはコマンドが無視されたことが示されていますが、本当の「エラー」ではないことをユーザープロセスが知ることは明らかに不可能です。解決策：そのシステムでは不要であるために特定のコマンドをサポートしていないサーバーは、そのコマンドに対して成功応答を返さなければならないと要求します。
  5. TELNETのコマンド行、TELNETの応答行、ユーザー名、パスワード、アカウント、パス名の最大長が規定されていません。FTPサーバーを実装する各システムが、それぞれのパラメーターについて異なる最大値を持っているであろうことは確かですが、少なくとも一部のシステムでは、（多くのFTPサーバーとやりとりしなければならない）FTPユーザーの作成者にとって、長さが不定のバッファーを用意するのは不便です。同様の困難は、サーバーFTPの作成者も直面します。解決策：TELNETのコマンド行、TELNETの応答、ユーザー名、パスワード、アカウント番号、パス名の最大長を規定します。これは、サービスを提供しているサイトに対してそれぞれの最大値に関する調査を行ってから決めることにします。ネットワークメールをFTPに含めるのであれば、メールの本文は、TELNETコネクション上で送信する場合、同じ行長の最大値に従うものとします。
  6. 継続行を任意のテキストで始められるようにするという考え方は、一部のサーバーFTPの実装者にとっての小さな問題を解決しますが、その代わりにすべてのユーザーFTPの実装者にとって大きな問題を生み出します。複数行の応答を解読するために必要なロジックは不必要に複雑で、複数行の応答の入れ子が許されているために、その複雑さは桁違いに増しています。解決策：複数行の応答の2行目以降のすべての行で使用する、一意な（数値の）応答コード、たとえば「009」を割り当てます。この目的に使用する応答コードは「0」で始まらなければなりません（たとえば、3つの空白にすることはできません）。そうすることで、応答コードのグループ分けに関する既存の規則により、ユーザープロセスにとっては無関係なものとして見えるようになります。
  7. 上記の(6)の解決策が受け入れられない場合、許される入れ子の最大レベルが規定されていないことが、ユーザーFTPの実装者にとって困難を生み出します。この困難は、ハードウェアスタックを持つマシンではある程度容易に解決できますが、それ以外のマシンではそうはいきません。解決策：入れ子になった応答を禁止する（こちらが望ましい）か、複数行の応答の入れ子の最大レベルを規定します。
  8. さまざまな応答コードの意味についての文章による説明は、いくつかの場合で不明瞭またはあいまいです。たとえば、コード「020」は「announcing FTP」とだけ説明されています。これは、ICPの直後にサーバーが入力を受け付けられないときに発行できる応答として示されていますが、その正確な意味は明らかではありません。また、コード「331」は「ENTER ACCOUNT (if required as part of login sequence)」を意味するとされていますが、ほとんどのコマンドに対して成功応答になりうるものとして記載されています。説明ではログインシーケンスでのみ有効であることが示されていますが、コマンドと応答の対応表からは、「アカウントがなければそれはできません」という意味でもあることが読み取れます。解決策：応答コードを考案した人々が、それらをより完全に定義するために一層の努力をすべきです。

A major complaint about the protocol concerns the fact that the writer of an FTP user process must handle a considerable number of special cases merely to determine Whether or not the last command sent was successful. It is admitted that the protocol is well-defined in all the following areas, but it is important to realize that the characteristic "well-defined" is necessary, but hot sufficient; for many reasons, it is very desirable to employ the simplest mechanism that satisfies all the needs. Following is a list of those drawbacks that unduly complicate the flow chart of an FTP user process:

このプロトコルに対する大きな不満は、FTPユーザープロセスの作成者が、最後に送信したコマンドが成功したかどうかを判断するためだけに、かなりの数の特殊なケースを処理しなければならないという点に関するものです。以下のすべての領域でプロトコルが明確に定義されていることは認めますが、「明確に定義されている」という特性は必要ではあっても十分ではないことを理解しておくことが重要です。多くの理由から、すべての必要を満たす最も単純な仕組みを採用することが非常に望ましいのです。以下は、FTPユーザープロセスのフローチャートを過度に複雑にしている欠点を一覧にしたものです。

  1. Different commands have different success reply codes. A successful "USER" command, for example, returns a "230", whereas a successful "BYTE" command returns a "200". The stated concept that the first digit would carry this information does not apply, as "100" means success for "STAT", and "200" means success for "SOCK". SOLUTION: specify that any command must return a reply code beginning with some unique digit, such as "2", if successful, and anything other than that digit if not successful. For example this includes changing the success reply for STAT, Perhaps to "200".
  2. Some commands have multiple possible success reply codes, e.g., "USER" and "REIN". It is undesirable for ah FTP user to be required to keep a list of reply codes for each command, all of which mean "command accepted, continue". Again, the stated concept concerning the first digit fails, as "230" and "330" are in truth both acknowledgments to a successful "USER" command. SOLUTION: same as for (9) above. The desire to communicate more specific information than simply "yes" or "no", such as the difficulty that some servers do not need all the login parameters, may be solved by having, for example, "230" mean "PASSWORD ACCEPTED, YOU ARE NOW LOGGED IN", and "237" mean "PASSWORD ACCEPTED, ACCOUNT NOW NEEDED". Given the solution to (4) above, a user process becomes much less interested in the difference between "YOU ARE NOW LOGGED IN" and "ACCOUNT NOW NEEDED". The important point is that the idea of "command accepted" is conveyed by the initial "2, and that finer gradations of meaning can be deduced by the user process, if desired.
  3. The meanings of the various connection greeting reply codes are somewhat inconsistent. "300 connection greeting, awaiting input", if intended as a positive acknowledgments to the ICP, should be a 200-series reply, or if intended to be purely informative, a 000-series reply. If the former, then clearly "020 expected delay" is the corresponding negative acknowledgments, and should be a 400-series reply. It is however unlikely that notification of an expected delay would be of importance to a user Process without knowledge of the length of the delay. SOLUTION.: change "300 connection greeting" to a 000-series reply, perhaps "011" (preferred), or change "300 connection greeting" to a 200-series reply, perhaps "211", and "020 expected delay" to a 400-series reply, perhaps "411".
  1. コマンドによって成功応答コードが異なります。たとえば、成功した「USER」コマンドは「230」を返しますが、成功した「BYTE」コマンドは「200」を返します。最初の桁がこの情報を伝えるという、述べられている概念は当てはまりません。「STAT」では「100」が成功を意味し、「SOCK」では「200」が成功を意味するからです。解決策：どのコマンドも、成功した場合は「2」などの特定の一意な数字で始まる応答コードを返し、成功しなかった場合はその数字以外で始まる応答コードを返さなければならないと規定します。たとえば、これにはSTATの成功応答を、おそらく「200」に変更することが含まれます。
  2. 一部のコマンド、たとえば「USER」や「REIN」には、成功応答コードが複数ありえます。FTPユーザーが、すべて「コマンドを受け付けた、続行せよ」を意味する応答コードの一覧をコマンドごとに保持しなければならないのは望ましくありません。ここでも、最初の桁に関する述べられている概念は成り立ちません。「230」と「330」は、実際にはどちらも成功した「USER」コマンドに対する肯定応答だからです。解決策：上記の(9)と同じです。一部のサーバーがログインパラメーターのすべてを必要とするわけではないという問題など、単なる「はい」や「いいえ」よりも具体的な情報を伝えたいという要望は、たとえば「230」は「PASSWORD ACCEPTED, YOU ARE NOW LOGGED IN」を意味し、「237」は「PASSWORD ACCEPTED, ACCOUNT NOW NEEDED」を意味するようにすれば解決できます。上記の(4)の解決策を前提とすれば、ユーザープロセスは「YOU ARE NOW LOGGED IN」と「ACCOUNT NOW NEEDED」の違いにはあまり関心を持たなくなります。重要な点は、「コマンドを受け付けた」という考えが最初の「2」によって伝えられ、必要であれば、より細かい意味の違いをユーザープロセスが推定できるということです。
  3. さまざまな接続時の挨拶の応答コードの意味は、いくぶん一貫性を欠いています。「300 connection greeting, awaiting input」は、ICPに対する肯定応答を意図しているのであれば200番台の応答であるべきで、純粋に情報提供を意図しているのであれば000番台の応答であるべきです。前者であれば、明らかに「020 expected delay」が対応する否定応答であり、400番台の応答であるべきです。しかし、遅延の長さがわからないのに、予想される遅延の通知がユーザープロセスにとって重要になるとは考えにくいです。解決策：「300 connection greeting」を000番台の応答、たとえば「011」に変更する（こちらが望ましい）か、「300 connection greeting」を200番台の応答、たとえば「211」に変更し、「020 expected delay」を400番台の応答、たとえば「411」に変更します。

In addition to the above mentioned weaknesses in the protocol, the following is believed to be a typographical error:

プロトコルの上記の弱点に加えて、次の点は誤植であると考えられます。

  1. Reply code "332 LOGIN PLEASE" is not listed anywhere in the command-reply correspondence table. It Would seem that this would be a more-information-needed (success) reply for all those commands which require the user to be logged in. It should also be stressed that the "332" code is to be used for this purpose, as many servers currently use other codes, such as "451" and "504", to mean "LOGIN PLEASE".
  1. 応答コード「332 LOGIN PLEASE」が、コマンドと応答の対応表のどこにも記載されていません。これは、ユーザーがログインしていることを必要とするすべてのコマンドに対する、追加情報を必要とする（成功）応答であると思われます。また、多くのサーバーが現在「451」や「504」などの他のコードを「LOGIN PLEASE」の意味で使用しているので、この目的には「332」コードを使用することを強調しておくべきです。
