RFC 10080

Updated Use of the Expires Message Header Field

RFC 10080

Expiresメッセージヘッダーフィールドの使用方法の更新

Abstract

概要

This document allows broader use of the "Expires" message header field for mail messages. Message creators can then indicate when a message expires, while recipients can use this information to handle an expired message differently.

この文書は、メールメッセージにおける「Expires」メッセージヘッダーフィールドのより広範な使用を認めます。 これにより、メッセージ作成者はメッセージがいつ期限切れになるかを示すことができ、受信者はこの情報を使用して期限切れのメッセージを異なる方法で扱うことができます。

1. Introduction

1. はじめに

[RFC2156] defined a mapping of header fields between the formats specified in X.400 and [RFC822]. One of the mapped fields is the "Expires" header field, which provides a date and time at which a message is considered to lose its validity.

[RFC2156]は、X.400と[RFC822]で規定された形式の間のヘッダーフィールドのマッピングを定義しました。 マッピングされたフィールドの1つが「Expires」ヘッダーフィールドで、これはメッセージが有効性を失うとみなされる日時を示します。

[RFC4021] registered the field with IANA but stated that it is "not for general use." This document extends the use of the "Expires" header field to Internet email in general, whether the message comes from an X.400 gateway or elsewhere.

[RFC4021]はこのフィールドをIANAに登録しましたが、「一般的な使用のためではない（not for general use）」と述べていました。 この文書は、メッセージがX.400ゲートウェイから来たものかどうかにかかわらず、「Expires」ヘッダーフィールドの使用をインターネットの電子メール全般に拡張します。

Netnews articles [RFC5536] have an "Expires" header with a similar, slightly more strict, syntax and similar meaning.

ネットニュースの記事[RFC5536]には、似ていながらやや厳格な構文と、似た意味を持つ「Expires」ヘッダーがあります。

The date and time of expiration can be used by the mailbox provider or the MUA (Mail User Agent) to de-emphasize certain messages, or not display them at all, to unclutter the user's mailbox.

有効期限の日時は、ユーザーのメールボックスを整理するために、メールボックスプロバイダーやMUA（メールユーザーエージェント、Mail User Agent）が特定のメッセージを目立たなくしたり、まったく表示しなかったりするのに使用できます。

A Message Creator is an agent that generates messages for delivery. In the parlance of [RFC5598], this is an Author or Originator.

メッセージ作成者（Message Creator）とは、配送するメッセージを生成するエージェントです。 [RFC5598]の用語では、これは作成者（Author）または発信者（Originator）にあたります。

A Message Reader is either an agent consuming a message or an agent storing a message. In the parlance of [RFC5598], this is a Message Store or a Message User Agent.

メッセージリーダー（Message Reader）とは、メッセージを消費するエージェント、またはメッセージを保存するエージェントのいずれかです。 [RFC5598]の用語では、これはメッセージストア（Message Store）またはメッセージユーザーエージェント（Message User Agent）にあたります。

2. Defining Expiration

2. 有効期限の定義

[RFC2156] defined a field called "Expires", which replaced "Expiry-Date" introduced in [RFC1327]. It did not define the term further, except to say that no automatic handling past that date can be expected. [RFC5536] defined "Expires" for Netnews as a date and time beyond which the poster considers the article no longer relevant and thus suitable for removal; however, it did not actually require such removal. The consensus definition used in this document is that beyond the stated expiration date, the message "loses its validity".

[RFC2156]は「Expires」というフィールドを定義し、これは[RFC1327]で導入された「Expiry-Date」を置き換えるものでした。 この用語については、その日時を過ぎた後の自動的な処理は期待できないと述べる以外に、それ以上の定義はしていませんでした。 [RFC5536]は、ネットニュースの「Expires」を、投稿者がその記事をもはや関連性がなく、したがって削除してよいとみなす日時として定義しました。しかし、実際にそのような削除を要求してはいませんでした。 この文書で使用するコンセンサスによる定義は、記載された有効期限を過ぎると、メッセージは「有効性を失う（loses its validity）」というものです。

The header field's use in email has been limited, with no formal semantic definition to date. No consensus exists to establish a more precise definition, in deference to existing implementations. Accordingly, no additional normative definition is provided here, nor is any requirement established for any particular handling by message readers.

このヘッダーフィールドの電子メールでの使用は限られており、現在まで正式なセマンティクスの定義はありません。 既存の実装に配慮して、より厳密な定義を確立するコンセンサスは存在しません。 したがって、ここでは追加の規範的な定義を提供せず、メッセージリーダーによる特定の処理についての要件も定めません。

3. Header Field Definition

3. ヘッダーフィールドの定義

The header field definition remains the same as in [RFC2156] and [RFC4021]. It indicates the time at which a message loses its validity. Using the ABNF [RFC5234] from [RFC5322], its syntax is:

ヘッダーフィールドの定義は、[RFC2156]および[RFC4021]と同じままです。 このヘッダーフィールドは、メッセージが有効性を失う時刻を示します。 [RFC5322]のABNF [RFC5234]を使用すると、その構文は次のとおりです。

expires = "Expires:" date-time CRLF
expires = "Expires:" date-time CRLF

Example:

例：

Expires: Wed, 3 Dec 2025 17:22:57 +0000

Expires: Wed, 3 Dec 2025 17:22:57 +0000

4. Advice to Message Creators

4. メッセージ作成者への助言

Message creators add the header field along with a relevant date and time when they know that the message loses its validity. This could apply to commercial newsletters that include time-limited offers, event announcements, social notifications, and periodic announcement messages.

メッセージ作成者は、メッセージが有効性を失う時期がわかっている場合に、該当する日時とともにこのヘッダーフィールドを追加します。 これは、期間限定のオファーを含む商用のニュースレター、イベントの告知、ソーシャル通知、定期的な告知メッセージに当てはまる可能性があります。

Message creators MUST NOT include more than one "Expires" header field in a message.

メッセージ作成者は、1つのメッセージに複数の「Expires」ヘッダーフィールドを含めてはなりません（MUST NOT）。

5. Advice to Message Readers

5. メッセージリーダーへの助言

Message readers, such as mailbox providers, web mail, and MUAs could de-emphasize the display of expired messages or not display them. They could allow users to control the actions to take for expired messages.

メールボックスプロバイダー、Webメール、MUAなどのメッセージリーダーは、期限切れのメッセージの表示を目立たなくしたり、表示しなかったりできます。 また、期限切れのメッセージに対して実行するアクションをユーザーが制御できるようにすることもできます。

The information provided in the header field is intended to be used as a signal to provide an improved experience to the end user. For instance, systems might allow automatic rules to clean up expired email from specific message creators or with defined characteristics, or to provide a mode to quickly handle all expired email.

このヘッダーフィールドで提供される情報は、エンドユーザーにより良い体験を提供するためのシグナルとして使用されることを意図しています。 たとえば、システムは、特定のメッセージ作成者からの、または定められた特徴を持つ期限切れの電子メールを片付ける自動ルールを許可したり、期限切れの電子メールをすべてすばやく処理するモードを提供したりできます。

Mail software MUST NOT discard or reject a message based solely on the content of this header field, if present, and SHOULD NOT delete messages bearing an "Expires" field with a date and time in the past unless deliberately configured to do so by the mailbox owner.

メールソフトウェアは、このヘッダーフィールドが存在する場合でも、その内容だけに基づいてメッセージを破棄したり拒否したりしてはなりません（MUST NOT）。 また、メールボックスの所有者が意図的にそのように設定した場合を除き、過去の日時を持つ「Expires」フィールドのあるメッセージを削除すべきではありません（SHOULD NOT）。

6. Interoperability Considerations

6. 相互運用性に関する考慮事項

As "Expires" has never been formally defined for Internet messages other than those translated from X.400, there might have been implementations that used this header field name in an incompatible way. Though the authors have never seen such a message, there is a theoretical risk of confusion.

「Expires」は、X.400から変換されたもの以外のインターネットメッセージについては正式に定義されたことがないため、このヘッダーフィールド名を互換性のない方法で使用する実装が存在した可能性があります。 著者らはそのようなメッセージを見たことはありませんが、理論上は混乱のリスクがあります。

7. Security Considerations

7. セキュリティーに関する考慮事項

A message creator can put any date in an "Expires" header field, including dates in the distant past or future. Without further knowledge about the message creator, recipient systems and message readers cannot assume that the contents of the header are accurate or benign.

メッセージ作成者は、遠い過去や遠い未来の日付を含め、「Expires」ヘッダーフィールドに任意の日付を入れることができます。 メッセージ作成者についてのさらなる知識がなければ、受信者のシステムやメッセージリーダーは、ヘッダーの内容が正確である、または無害であると想定することはできません。

For example, a malicious message creator might send spam mail that includes an expiry date in the past, in the hope that recipients would not see or report the mail, and that adaptive spam filters would use it as non-spam training material. A creator might include a date in the immediate future in the hope that a recipient would see and act on a message but could not find it later to complain about it. Or, a creator might include a date in the distant future in the hope that the message would stay in a recipient's inbox and would be more likely to be read.

例として、悪意のあるメッセージ作成者は、受信者がそのメールを見たり報告したりせず、適応型のスパムフィルターがそれをスパムでない学習データとして使用することを期待して、過去の有効期限を含むスパムメールを送信するかもしれません。 作成者は、受信者がメッセージを見て行動するものの、後で苦情を言うためにそれを見つけられないことを期待して、直近の未来の日付を含めるかもしれません。 あるいは、作成者は、メッセージが受信者の受信トレイに残り続け、読まれる可能性が高くなることを期待して、遠い未来の日付を含めるかもしれません。

While the header field can be useful for determining how to display a message to a user, it is unlikely to be useful for determining whether the message is wanted or is fraudulent.

このヘッダーフィールドは、メッセージをユーザーにどのように表示するかを決めるのには役立つかもしれませんが、メッセージが望まれたものか、詐欺的なものかを判断するのに役立つ可能性は低いです。
