RFC 512

More on lost message detection

RFC 512

紛失メッセージの検出についての続報

Abstract

概要

I would like to second Edwin Meyer's (RFC #492) strong opposition to the proposals made in RFC #467 concerning solutions to the "lost allocate" and "half-closed" phenomena. In particular I support all of his principles concerning the "half-closed" phenomenon. I also agree that the proposed "lost allocate" solution tends to mask the real problem of lost messages. I would, however, like to propose the following alternative scheme for recognizing lost messages.

「lost allocate（割り当ての紛失）」と「half-closed（半クローズ）」の現象に対する解決策についてRFC #467でなされた提案に、Edwin Meyer（RFC #492）が強く反対していることに、私も賛同します。特に、「half-closed」現象に関する彼の原則にはすべて賛成します。また、提案されている「lost allocate」の解決策は、メッセージの紛失という本当の問題を覆い隠しがちであるという点にも同意します。ただし、紛失したメッセージを認識するための代わりの方式として、次のものを提案したいと思います。

I propose that one of the two unused eight-bit bytes in the level 2 message leader be designated the "Sequence Control Byte" (SCB). This SCB would be essentially a modulo 255 message count. Upon receipt of a message, the receiving NCP would compare the SCB in the previous the message with the expected SCB as computed from the SCB in the previous message on the same link. A discrepancy indicates a lost message, which could then be reported immediately via an appropriate ERR message. This ERR message (to be defined) would contain both received and expected SCB's, allowing possible recovery of the lost message (if sufficient space were available in the sending host to save the last several messages for each link). At any rate, the lost message would be recognized immediately, whether it was an ALL (or any control message) or a data message. The message with the unexpected SCB should be processed normally, with the SCB for the next message computed from it.

レベル2のメッセージリーダーにある未使用の2つの8ビットバイトのうち1つを、「シーケンス制御バイト（Sequence Control Byte; SCB）」として指定することを提案します。このSCBは、本質的には255を法とするメッセージ数のカウントです。メッセージを受信すると、受信側のNCPは、そのメッセージのSCBを、同じリンク上の前のメッセージのSCBから計算した期待されるSCBと比較します。食い違いはメッセージの紛失を示しており、適切なERRメッセージですぐに報告できます。この（今後定義する）ERRメッセージには、受信したSCBと期待されたSCBの両方を含めます。これにより、（送信側ホストに、リンクごとに直近のいくつかのメッセージを保存しておく十分な領域があれば）紛失したメッセージを回復できる可能性があります。いずれにせよ、紛失したメッセージがALL（または任意の制御メッセージ）であってもデータメッセージであっても、すぐに認識できます。予期しないSCBを持つメッセージは通常どおり処理し、次のメッセージのSCBはそのメッセージのSCBから計算すべきです。

For compatibility, the SCB would be defined such that an SCB of zero indicates that no checking is to be done. The SCB following 255 would thus be 1. This would mean that current NCP's would not have to be changed unless actual checking were desired (since the level 2 protocol specifies that these two unused bytes must be zero.) This special definition of zero SCB would also allow RST's and ERR's to bypass checking, which would be useful in avoiding possible loops.

互換性のため、SCBがゼロであれば検査を行わないことを示すようにSCBを定義します。したがって、255の次のSCBは1になります。これにより、（レベル2のプロトコルでは、これら2つの未使用バイトはゼロでなければならないと規定されているので）実際に検査をしたい場合を除き、現在のNCPを変更する必要はありません。ゼロのSCBをこのように特別に定義することで、RSTやERRが検査を迂回できるようにもなり、ループの可能性を避けるのに役立ちます。

This proposed scheme is similar to the second scheme suggested by Jon Postel (RFC #516) except that it is on a per-link basis rather than a per-host basis. This is significant, however, as it removes the requirement that all messages from one host to another arrive in the order sent (which cannot be guaranteed). It also provides for compatibility with existing NCP's. Jon's first proposal (save all messages until RFNM received) is weak in two areas: first, it is possible that the receiving IMP has sent a RFNM for a message that in fact never gets to its host, and second, it requires (at least for swapped systems such as ours) either that messages be saved in resident storage (expensive) or that RFNM's be handled by a swapped process (also expensive). The third proposal (that of a host-to-host acknowledgment scheme) is perhaps the best, but as that requires quite major changes to the level 2 protocol, an interim solution such as that proposed here seems of value.

この提案方式は、Jon Postel（RFC #516）が示した2つ目の方式に似ていますが、ホスト単位ではなくリンク単位である点が異なります。しかし、これは重要な違いです。あるホストから別のホストへのすべてのメッセージが送信した順序で到着する（これは保証できません）という要件がなくなるからです。また、既存のNCPとの互換性も確保できます。Jonの1つ目の提案（RFNMを受信するまですべてのメッセージを保存する）には、2つの弱点があります。1つ目は、受信側のIMPが、実際には自身のホストに届かないメッセージに対してRFNMを送信してしまう可能性があることです。2つ目は、（少なくとも私たちのようなスワップ方式のシステムでは）メッセージを常駐記憶領域に保存する（コストがかかる）か、RFNMをスワップされるプロセスで処理する（これもコストがかかる）かのどちらかが必要になることです。3つ目の提案（ホスト間の確認応答方式）がおそらく最善ですが、それにはレベル2のプロトコルを大幅に変更する必要があるので、ここで提案するような暫定的な解決策には価値があると思われます。
