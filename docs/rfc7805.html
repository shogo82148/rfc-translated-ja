RFC 7805

Moving Outdated TCP Extensions and TCP-Related Documents to Historic or Informational Status

RFC 7805

時代遅れのTCP拡張とTCP関連文書の歴史的（Historic）または情報提供（Informational）ステータスへの移行

Abstract

概要

This document reclassifies several TCP extensions and TCP-related documents that either have been superseded, have never seen widespread use, or are no longer recommended for use to "Historic" status. The affected documents are RFCs 675, 721, 761, 813, 816, 879, 896, 1078, and 6013. Additionally, this document reclassifies RFCs 700, 794, 814, 817, 872, 889, 964, and 1071 to "Informational" status.

この文書は、置き換えられたもの、広く使われることがなかったもの、あるいはもはや使用が推奨されないもののいずれかにあたる、いくつかのTCP拡張とTCP関連文書を「歴史的（Historic）」ステータスに再分類します。 対象となる文書は、RFC 675、721、761、813、816、879、896、1078、6013です。 さらに、この文書はRFC 700、794、814、817、872、889、964、1071を「情報提供（Informational）」ステータスに再分類します。

1. Introduction

1. はじめに

TCP has a long history. Over time, many RFCs have accumulated that describe aspects of the TCP protocol, implementation, and extensions. Some of these have been superseded, are no longer recommended for use, or have simply never seen widespread use.

TCPには長い歴史があります。 時とともに、TCPのプロトコル、実装、拡張のさまざまな側面を記述した多くのRFCが積み重なってきました。 それらの中には、置き換えられたもの、もはや使用が推奨されないもの、あるいは単に広く使われることがなかったものがあります。

Sections 6 and 7.1 of the TCP roadmap document [RFC7414] already reclassified a number of TCP extensions as "Historic" and describes the reasons for doing so, but it did not instruct the RFC Editor to change the status of these RFCs in the RFC database. The purpose of this document is to do just that.

TCPロードマップ文書[RFC7414]のセクション6と7.1は、すでにいくつかのTCP拡張を「歴史的（Historic）」に再分類し、そうする理由を説明していますが、RFCデータベース上でこれらのRFCのステータスを変更するようRFCエディターに指示してはいませんでした。 この文書の目的は、まさにその指示を行うことです。

In addition, this document reclassifies all other documents mentioned in the TCP roadmap that currently have an "Unknown" status to either "Historic" or "Informational".

さらに、この文書は、TCPロードマップで言及されている文書のうち、現在「不明（Unknown）」ステータスにあるほかのすべての文書を、「歴史的（Historic）」または「情報提供（Informational）」のいずれかに再分類します。

2. Status Changes

2. ステータスの変更

The following two sections give a short justification why a specific TCP extension or a TCP-related document is being reclassified as "Historic" or "Informational". In addition, the letter code after an RFC number indicates from which original status a particular RFC is changed to "Historic" or "Informational" (see BCP 9 [RFC2026] for an explanation of these categories):

続く2つのセクションでは、特定のTCP拡張やTCP関連文書が「歴史的（Historic）」または「情報提供（Informational）」に再分類される理由を簡潔に説明します。 また、RFC番号の後ろの文字コードは、そのRFCがどの元のステータスから「歴史的（Historic）」または「情報提供（Informational）」に変更されるのかを示します（これらの分類の説明については、BCP 9[RFC2026]を参照してください）。

2.1. Moving to "Historic" Status

2.1. 「歴史的（Historic）」ステータスへの移行

This document changes the status of the following RFCs to "Historic" [RFC2026]:

この文書は、以下のRFCのステータスを「歴史的（Historic）」[RFC2026]に変更します。

  • [RFC675] U, "Specification of Internet Transmission Control Program" was replaced by the final TCP specification [RFC793]
  • [RFC721] U, "Out-of-Band Control Signals in a Host-to-Host Protocol" was a proposal that was not incorporated into the final TCP specification [RFC793]
  • [RFC761] U, "DoD Standard Transmission Control Protocol" was replaced by the final TCP specification [RFC793]
  • [RFC813] U, "Window and Acknowledgement Strategy in TCP" was incorporated into [RFC1122]
  • [RFC816] U, "Fault Isolation and Recovery" was incorporated into [RFC1122] and [RFC5461]
  • [RFC879] U, "The TCP Maximum Segment Size and Related Topics" was incorporated into [RFC1122] and [RFC6691]
  • [RFC896] U, "Congestion Control in IP/TCP Internetworks" was incorporated into [RFC1122] and [RFC6633]

  • [RFC1078] U, "TCP Port Service Multiplexer (TCPMUX)" should be deprecated, because:

    • It modifies the TCP connection establishment semantics by also completing the three-way handshake when a service is not available.
    • It requires all new connections to be received on a single port, which limits the number of connections between two machines.
    • It complicates firewall implementation and management because all services share the same port number.
    • There are very limited deployments, and these are not used in an Internet context. (The only reported use is for SGI's Data Migration Facility in private networks.)

  • [RFC6013] E, "TCP Cookie Transactions (TCPCT)" should be deprecated (although only published in 2011) because:

    • It uses the experimental TCP option codepoints, which prohibit a large-scale deployment.
    • [RFC7413] and [TCP-EDO] are alternatives that have more "rough consensus and running code" behind them.
    • There are no known wide-scale deployments.
  • [RFC675] U、「Specification of Internet Transmission Control Program」は、最終的なTCP仕様[RFC793]に置き換えられました。
  • [RFC721] U、「Out-of-Band Control Signals in a Host-to-Host Protocol」は、最終的なTCP仕様[RFC793]に取り入れられなかった提案でした。
  • [RFC761] U、「DoD Standard Transmission Control Protocol」は、最終的なTCP仕様[RFC793]に置き換えられました。
  • [RFC813] U、「Window and Acknowledgement Strategy in TCP」は、[RFC1122]に取り込まれました。
  • [RFC816] U、「Fault Isolation and Recovery」は、[RFC1122]と[RFC5461]に取り込まれました。
  • [RFC879] U、「The TCP Maximum Segment Size and Related Topics」は、[RFC1122]と[RFC6691]に取り込まれました。
  • [RFC896] U、「Congestion Control in IP/TCP Internetworks」は、[RFC1122]と[RFC6633]に取り込まれました。

  • [RFC1078] U、「TCP Port Service Multiplexer (TCPMUX)」は、次の理由により非推奨とすべきです。

    • サービスが利用できない場合にも3ウェイハンドシェイクを完了させることで、TCPのコネクション確立のセマンティクスを変更してしまいます。
    • すべての新しいコネクションを単一のポートで受信する必要があり、2台のマシン間のコネクション数が制限されます。
    • すべてのサービスが同じポート番号を共有するため、ファイアウォールの実装と管理が複雑になります。
    • 展開はごく限られており、それらもインターネットの文脈では使われていません（報告されている唯一の用途は、プライベートネットワークにおけるSGIのData Migration Facilityです）。

  • [RFC6013] E、「TCP Cookie Transactions (TCPCT)」は、（2011年に公開されたばかりですが）次の理由により非推奨とすべきです。

    • 実験用のTCPオプションのコードポイントを使用しており、それが大規模な展開を妨げます。
    • [RFC7413]と[TCP-EDO]という代替案があり、それらのほうがより多くの「ラフコンセンサスと動作するコード（rough consensus and running code）」に裏付けられています。
    • 広範囲に展開された事例は知られていません。

2.2. Moving to "Informational" Status

2.2. 「情報提供（Informational）」ステータスへの移行

This document changes the status of the following RFCs to "Informational" [RFC2026]:

この文書は、以下のRFCのステータスを「情報提供（Informational）」[RFC2026]に変更します。

  • [RFC700] U, "A Protocol Experiment", which presents a field report about the deployment of a very early version of TCP
  • [RFC794] U, "Pre-emption", which recommends that operating systems need to manage their limited resources, which may include TCP connection state
  • [RFC814] U, "Name, Addresses, Ports, and Routes", which gives guidance on designing tables and algorithms to keep track of various identifiers within a TCP/IP implementation
  • [RFC817] U, "Modularity and Efficiency in Protocol Implementation", which contains general implementation suggestions
  • [RFC872] U, "TCP-on-a-LAN", which concludes that the fear of using TCP on a local network is unfounded
  • [RFC889] U, "Internet Delay Experiments", which describes experiments with the TCP retransmission timeout calculation
  • [RFC964] U, "Some Problems with the Specification of the Military Standard Transmission Control Protocol", which points out several specification bugs in the US Military's MIL-STD-1778 document, which was intended as a successor to [RFC793]
  • [RFC1071] U, "Computing the Internet Checksum", which lists a number of implementation techniques for efficiently computing the Internet checksum
  • [RFC700] U、「A Protocol Experiment」は、TCPのごく初期のバージョンの展開に関する現場報告です。
  • [RFC794] U、「Pre-emption」は、オペレーティングシステムがTCPのコネクション状態を含みうる限られたリソースを管理する必要があることを推奨しています。
  • [RFC814] U、「Name, Addresses, Ports, and Routes」は、TCP/IP実装内のさまざまな識別子を追跡するためのテーブルとアルゴリズムの設計についての指針を示しています。
  • [RFC817] U、「Modularity and Efficiency in Protocol Implementation」は、実装に関する一般的な提案を含んでいます。
  • [RFC872] U、「TCP-on-a-LAN」は、ローカルネットワーク上でTCPを使うことへの懸念には根拠がないと結論づけています。
  • [RFC889] U、「Internet Delay Experiments」は、TCPの再送タイムアウトの計算に関する実験を説明しています。
  • [RFC964] U、「Some Problems with the Specification of the Military Standard Transmission Control Protocol」は、[RFC793]の後継として意図されていた米軍のMIL-STD-1778文書における、いくつかの仕様上の誤りを指摘しています。
  • [RFC1071] U、「Computing the Internet Checksum」は、インターネットチェックサムを効率的に計算するためのいくつかの実装手法を挙げています。

3. Security Considerations

3. セキュリティーに関する考慮事項

This document introduces no new security considerations. Each RFC listed in this document attempts to address the security considerations of the specification it contains.

この文書は、新たなセキュリティー上の考慮事項をもたらしません。 この文書に挙げた各RFCは、それぞれが含む仕様のセキュリティー上の考慮事項に対処しようとしています。
