Mutual Authentication Protocol for HTTP: Cryptographic Algorithms Based on the Key Agreement Mechanism 3 (KAM3)

RFC 8121

HTTPの相互認証プロトコル：鍵共有メカニズム3（KAM3）に基づく暗号アルゴリズム

Abstract

概要

This document specifies cryptographic algorithms for use with the Mutual user authentication method for the Hypertext Transfer Protocol (HTTP).

この文書は、ハイパーテキスト転送プロトコル（HTTP）のMutualユーザー認証方式で使用する暗号アルゴリズムを規定します。

1. Introduction

1. はじめに

This document specifies algorithms for use with the Mutual authentication protocol for the Hypertext Transfer Protocol (HTTP) [RFC8120] (hereafter referred to as the "core specification"). The algorithms are based on augmented password-based authenticated key exchange (augmented PAKE) techniques. In particular, it uses one of three key exchange algorithms defined in ISO 11770-4 ("Information technology - Security techniques - Key management - Part 4: Mechanisms based on weak secrets") [ISO.11770-4.2006] as its basis.

この文書は、ハイパーテキスト転送プロトコル（HTTP）のMutual認証プロトコル[RFC8120]（以下「コア仕様」と呼びます）で使用するアルゴリズムを規定します。 このアルゴリズムは、拡張パスワード認証鍵交換（augmented PAKE）の技術に基づいています。 特に、ISO 11770-4（「Information technology - Security techniques - Key management - Part 4: Mechanisms based on weak secrets」）[ISO.11770-4.2006]で定義されている3つの鍵交換アルゴリズムのうちの1つを基礎として使用します。

To briefly summarize, the Mutual authentication protocol exchanges four values -- K_c1, K_s1, VK_c, and VK_s -- to perform authenticated key exchanges, using the password-derived secret pi and its "augmented version" J(pi). This document defines the set of functions K_c1, K_s1, and J for a specific algorithm family.

簡単にまとめると、Mutual認証プロトコルは、パスワードから導出される秘密piとその「拡張版」J(pi)を使用して、4つの値（K_c1、K_s1、VK_c、VK_s）を交換し、認証付き鍵交換を行います。 この文書は、特定のアルゴリズムファミリーのための関数K_c1、K_s1、Jの組を定義します。

Please note that from the point of view of literature related to cryptography, the original functionality of augmented PAKE is separated into the functions K_c1 and K_s1 as defined in this document, and the functions VK_c and VK_s, which are defined in Section 12.2 of [RFC8120] as "default functions". For the purpose of security analysis, please also refer to these functions.

暗号に関する文献の観点から見ると、拡張PAKEの本来の機能は、この文書で定義する関数K_c1およびK_s1と、[RFC8120]のセクション12.2で「デフォルト関数」として定義されている関数VK_cおよびVK_sとに分割されていることに注意してください。 セキュリティー分析の目的では、これらの関数もあわせて参照してください。

1.1. 用語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119].

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 [RFC2119]に記載されているとおりに解釈されるものとします。

The term "natural numbers" refers to non-negative integers (including zero) throughout this document.

この文書全体を通じて、「自然数」という用語は（ゼロを含む）非負の整数を指します。

This document treats both the input (domain) and the output (codomain) of hash functions as octet strings. When a natural-number output of hash function H is required, it will be notated, for example, as INT(H(s)).

この文書では、ハッシュ関数の入力（定義域）と出力（終域）の両方をオクテット文字列として扱います。 ハッシュ関数Hの出力を自然数として必要とする場合は、たとえばINT(H(s))のように表記します。

2. Cryptographic Overview (Non-normative)

2. 暗号の概要（非規範的）

The cryptographic primitive used in this algorithm specification is based on a variant of augmented PAKE called "APKAS-AMP" (augmented password-authenticated key agreement scheme, version AMP), proposed by T. Kwon and originally submitted to [IEEE-1363.2_2008]. The general flow of the successful exchange is shown below for informative purposes only. The multiplicative notations are used for group operators, and all modulus operations for finite groups (mod q and mod r) are omitted.

このアルゴリズム仕様で使用する暗号プリミティブは、T. Kwonによって提案され、もともと[IEEE-1363.2_2008]に提出された、「APKAS-AMP」（augmented password-authenticated key agreement scheme, version AMP）と呼ばれる拡張PAKEの変種に基づいています。 成功した交換の一般的な流れを、情報提供のみを目的として以下に示します。 群の演算子には乗法的な表記を使用し、有限群に対するすべての剰余演算（mod qおよびmod r）は省略しています。

   C: S_c1 = random
   C: K_c1 = g^(S_c1)
                    ----- ID, K_c1 ----->
   C: t_1 = H1(K_c1)                S: t_1 = H1(K_c1)
                                    S: fetch J = g^pi by ID
                                    S: S_s1 = random
                                    S: K_s1 = (J * K_c1^(t_1))^(S_s1)
                    <----- K_s1 -----
   C: t_2 = H2(K_c1, K_s1)          S: t_2 = H2(K_c1, K_s1)
   C: z = K_s1^((S_c1 + t_2) / (S_c1 * t_1 + pi))
                                    S: z' = (K_c1 * g^(t_2))^(S_s1)
   (assumption at this point: z = z' if authentication succeeded)

   C: VK_c = H4(K_c1, K_s1, z)      S: VK_c' = H4(K_c1, K_s1, z')
                    ----- VK_c ------->
                                    S: assert(VK_c = VK_c')

   C: VK_s' = H3(K_c1, K_s1, z)     S: VK_s = H3(K_c1, K_s1, z')
                    <----- VK_s ------
   C: assert(VK_s = VK_s')

   C: S_c1 = random
   C: K_c1 = g^(S_c1)
                    ----- ID, K_c1 ----->
   C: t_1 = H1(K_c1)                S: t_1 = H1(K_c1)
                                    S: fetch J = g^pi by ID
                                    S: S_s1 = random
                                    S: K_s1 = (J * K_c1^(t_1))^(S_s1)
                    <----- K_s1 -----
   C: t_2 = H2(K_c1, K_s1)          S: t_2 = H2(K_c1, K_s1)
   C: z = K_s1^((S_c1 + t_2) / (S_c1 * t_1 + pi))
                                    S: z' = (K_c1 * g^(t_2))^(S_s1)
   (assumption at this point: z = z' if authentication succeeded)

   C: VK_c = H4(K_c1, K_s1, z)      S: VK_c' = H4(K_c1, K_s1, z')
                    ----- VK_c ------->
                                    S: assert(VK_c = VK_c')

   C: VK_s' = H3(K_c1, K_s1, z)     S: VK_s = H3(K_c1, K_s1, z')
                    <----- VK_s ------
   C: assert(VK_s = VK_s')

Note that the concrete (binary) message formats (mapping to HTTP messages), as well as the formal definitions of equations for the latter two messages, are defined in the core specification [RFC8120]. The formal definitions for values corresponding to the first two messages are defined in the following sections.

具体的な（バイナリーの）メッセージ形式（HTTPメッセージへのマッピング）と、後半の2つのメッセージの式の正式な定義は、コア仕様[RFC8120]で定義されていることに注意してください。 最初の2つのメッセージに対応する値の正式な定義は、以降のセクションで定義します。

3. Authentication Algorithms

3. 認証アルゴリズム

This document specifies one family of algorithms based on APKAS-AMP, to be used with [RFC8120]. This family consists of four authentication algorithms, which differ only in their underlying mathematical groups and security parameters. These algorithms do not add any additional parameters. The tokens for these algorithms are as follows:

この文書は、[RFC8120]とともに使用する、APKAS-AMPに基づく1つのアルゴリズムファミリーを規定します。 このファミリーは4つの認証アルゴリズムで構成され、それらは基礎となる数学的な群とセキュリティーパラメーターだけが異なります。 これらのアルゴリズムは、追加のパラメーターを一切加えません。 これらのアルゴリズムのトークンは次のとおりです。

  • iso-kam3-dl-2048-sha256: for the 2048-bit discrete-logarithm setting with the SHA-256 hash function.

  • iso-kam3-dl-4096-sha512: for the 4096-bit discrete-logarithm setting with the SHA-512 hash function.

  • iso-kam3-ec-p256-sha256: for the 256-bit prime-field elliptic-curve setting with the SHA-256 hash function.

  • iso-kam3-ec-p521-sha512: for the 521-bit prime-field elliptic-curve setting with the SHA-512 hash function.

  • iso-kam3-dl-2048-sha256：SHA-256ハッシュ関数を使用する、2048ビットの離散対数の設定。

  • iso-kam3-dl-4096-sha512：SHA-512ハッシュ関数を使用する、4096ビットの離散対数の設定。

  • iso-kam3-ec-p256-sha256：SHA-256ハッシュ関数を使用する、256ビットの素体上の楕円曲線の設定。

  • iso-kam3-ec-p521-sha512：SHA-512ハッシュ関数を使用する、521ビットの素体上の楕円曲線の設定。

For discrete-logarithm settings, the underlying groups are the 2048-bit and 4096-bit Modular Exponential (MODP) groups defined in [RFC3526]. See Appendix A for the exact specifications for the groups and associated parameters. Hash function H is SHA-256 for the 2048-bit group and SHA-512 for the 4096-bit group, respectively, as defined in FIPS PUB 180-4 [FIPS.180-4.2015]. The hash iteration count nIterPi is 16384. The representation of the parameters "kc1", "ks1", "vkc", and "vks" is base64-fixed-number.

離散対数の設定では、基礎となる群は[RFC3526]で定義されている2048ビットおよび4096ビットのモジュラー指数（MODP）群です。 群と関連するパラメーターの正確な仕様については、付録Aを参照してください。 ハッシュ関数Hは、FIPS PUB 180-4 [FIPS.180-4.2015]で定義されているもので、2048ビットの群ではSHA-256、4096ビットの群ではSHA-512です。 ハッシュの反復回数nIterPiは16384です。 パラメーター「kc1」、「ks1」、「vkc」、「vks」の表現はbase64-fixed-numberです。

For the elliptic-curve settings, the underlying groups are the elliptic curves over the prime fields P-256 and P-521, respectively, as specified in Appendix D.1.2 of the FIPS PUB 186-4 [FIPS.186-4.2013] specification. Hash function H is SHA-256 for the P-256 curve and SHA-512 for the P-521 curve, respectively. Cofactors of these curves are 1. The hash iteration count nIterPi is 16384. The representation of the parameters "kc1", "ks1", "vkc", and "vks" is hex-fixed-number.

楕円曲線の設定では、基礎となる群は、FIPS PUB 186-4 [FIPS.186-4.2013]仕様の付録D.1.2で規定されている、素体P-256およびP-521上の楕円曲線です。 ハッシュ関数Hは、P-256曲線ではSHA-256、P-521曲線ではSHA-512です。 これらの曲線の余因子は1です。 ハッシュの反復回数nIterPiは16384です。 パラメーター「kc1」、「ks1」、「vkc」、「vks」の表現はhex-fixed-numberです。

Note: This algorithm is based on the Key Agreement Mechanism 3 (KAM3) as defined in Section 6.3 of ISO/IEC 11770-4 [ISO.11770-4.2006], with a few modifications/improvements. However, implementers should consider this document as normative, because several minor details of the algorithm have changed and major improvements have been made.

注：このアルゴリズムは、ISO/IEC 11770-4 [ISO.11770-4.2006]のセクション6.3で定義されている鍵共有メカニズム3（KAM3）に基づいており、いくつかの修正・改良を加えています。 ただし、アルゴリズムの細かな点がいくつか変更され、大きな改良も加えられているので、実装者はこの文書を規範とみなすべきです。

3.1. Support Functions and Notations

3.1. サポート関数と表記法

The algorithm definitions use the support functions and notations defined below.

アルゴリズムの定義では、以下で定義するサポート関数と表記法を使用します。

Decimal notations are used for integers in this specification by default. Integers in hexadecimal notations are prefixed with "0x".

この仕様では、整数はデフォルトで10進数で表記します。 16進数で表記する整数には「0x」を前に付けます。

In this document, the octet(), OCTETS(), and INT() functions are used as defined in the core specification [RFC8120].

この文書では、関数octet()、OCTETS()、INT()を、コア仕様[RFC8120]での定義どおりに使用します。

Note: The definition of OCTETS() is different from the function GE2OS_x in the original ISO specification; GE2OS_x takes the shortest representation without preceding zeros.

注：OCTETS()の定義は、元のISO仕様の関数GE2OS_xとは異なります。 GE2OS_xは、先行するゼロのない最短の表現をとります。

All of the algorithms defined in this specification use the default functions defined in Section 12.2 of [RFC8120] for computing the values pi, VK_c, and VK_s.

この仕様で定義するすべてのアルゴリズムは、値pi、VK_c、VK_sの計算に、[RFC8120]のセクション12.2で定義されているデフォルト関数を使用します。

3.2. Functions for Discrete-Logarithm Settings

3.2. 離散対数の設定のための関数

In this section, an equation (x / y mod z) denotes a natural number w less than z that satisfies (w * y) mod z = x mod z.

このセクションでは、式(x / y mod z)は、(w * y) mod z = x mod zを満たす、z未満の自然数wを表します。

For the discrete logarithm, we refer to some of the domain parameters by using the following symbols:

離散対数については、ドメインパラメーターの一部を次の記号で参照します。

  • q: for "the prime" defining the MODP group.

  • g: for "the generator" associated with the group.

  • r: for the order of the subgroup generated by g.

  • q：MODP群を定義する「素数」。

  • g：群に関連付けられた「生成元」。

  • r：gによって生成される部分群の位数。

The function J is defined as

関数Jは次のように定義されます。

   J(pi) = g^(pi) mod q

   J(pi) = g^(pi) mod q

The value of K_c1 is derived as

K_c1の値は次のように導出されます。

   K_c1 = g^(S_c1) mod q

   K_c1 = g^(S_c1) mod q

where S_c1 is a random integer within the range [1, r-1] and r is the size of the subgroup generated by g. In addition, S_c1 MUST be larger than log(q)/log(g) (so that g^(S_c1) > q).

ここで、S_c1は範囲[1, r-1]内のランダムな整数であり、rはgによって生成される部分群の大きさです。 さらに、S_c1はlog(q)/log(g)より大きくなければなりません（MUST）（g^(S_c1) > qとなるようにするため）。

The server MUST check the condition 1 < K_c1 < q-1 upon reception.

サーバーは、受信時に条件1 < K_c1 < q-1を確認しなければなりません（MUST）。

Let an intermediate value t_1 be

中間値t_1を次のようにします。

   t_1 = INT(H(octet(1) | OCTETS(K_c1)))

   t_1 = INT(H(octet(1) | OCTETS(K_c1)))

The value of K_s1 is derived from J(pi) and K_c1 as

K_s1の値は、J(pi)とK_c1から次のように導出されます。

   K_s1 = (J(pi) * K_c1^(t_1))^(S_s1) mod q

   K_s1 = (J(pi) * K_c1^(t_1))^(S_s1) mod q

where S_s1 is a random number within the range [1, r-1]. The value of K_s1 MUST satisfy 1 < K_s1 < q-1. If this condition is not held, the server MUST reject the exchange. The client MUST check this condition upon reception.

ここで、S_s1は範囲[1, r-1]内の乱数です。 K_s1の値は1 < K_s1 < q-1を満たさなければなりません（MUST）。 この条件が成り立たない場合、サーバーは交換を拒否しなければなりません（MUST）。 クライアントは、受信時にこの条件を確認しなければなりません（MUST）。

Let an intermediate value t_2 be

中間値t_2を次のようにします。

   t_2 = INT(H(octet(2) | OCTETS(K_c1) | OCTETS(K_s1)))

   t_2 = INT(H(octet(2) | OCTETS(K_c1) | OCTETS(K_s1)))

The value z on the client side is derived by the following equation:

クライアント側の値zは、次の式で導出されます。

   z = K_s1^((S_c1 + t_2) / (S_c1 * t_1 + pi) mod r) mod q

   z = K_s1^((S_c1 + t_2) / (S_c1 * t_1 + pi) mod r) mod q

The value z on the server side is derived by the following equation:

サーバー側の値zは、次の式で導出されます。

   z = (K_c1 * g^(t_2))^(S_s1) mod q

   z = (K_c1 * g^(t_2))^(S_s1) mod q

(Note: The original ISO specification contained a message pair containing verification of value z along with the "transcript" of the protocol exchange. This functionality is contained in the functions VK_c and VK_s.)

（注：元のISO仕様には、値zの検証をプロトコル交換の「トランスクリプト」とともに行うメッセージの組が含まれていました。 この機能は、関数VK_cとVK_sに含まれています。）

3.3. Functions for Elliptic-Curve Settings

3.3. 楕円曲線の設定のための関数

For the elliptic-curve settings, we refer to some of the domain parameters by the following symbols:

楕円曲線の設定では、ドメインパラメーターの一部を次の記号で参照します。

  • q: for the prime used to define the group.

  • G: for the point defined with the underlying group called "the generator".

  • h: for the cofactor of the group.

  • r: for the order of the subgroup generated by G.

  • q：群を定義するために使用される素数。

  • G：基礎となる群とともに定義される、「生成元」と呼ばれる点。

  • h：群の余因子。

  • r：Gによって生成される部分群の位数。

The function P(p) converts a curve point p into an integer representing point p, by computing x * 2 + (y mod 2), where (x, y) are the coordinates of point p. P'(z) is the inverse of function P; that is, it converts an integer z to a point p that satisfies P(p) = z. If such p exists, it is uniquely defined. Otherwise, z does not represent a valid curve point.

関数P(p)は、x * 2 + (y mod 2)を計算することによって、曲線上の点pを、点pを表す整数に変換します。 ここで、(x, y)は点pの座標です。 P'(z)は関数Pの逆関数です。 つまり、整数zを、P(p) = zを満たす点pに変換します。 そのようなpが存在する場合、それは一意に定まります。 存在しない場合、zは曲線上の有効な点を表していません。

The operator "+" indicates the elliptic-curve group operation, and the operation [x] * p denotes an integer-multiplication of point p: it calculates p + p + ... (x times) ... + p. See the literature on elliptic-curve cryptography for the exact algorithms used for those functions (e.g., Section 3 of [RFC6090]; however, note that [RFC6090] uses different notations). 0_E represents the infinity point. The equation (x / y mod z) denotes a natural number w less than z that satisfies (w * y) mod z = x mod z.

演算子「+」は楕円曲線の群演算を表し、演算[x] * pは点pの整数倍を表します。 これは、p + p + ...（x回）... + pを計算します。 これらの関数に使用される正確なアルゴリズムについては、楕円曲線暗号に関する文献を参照してください（たとえば[RFC6090]のセクション3。ただし、[RFC6090]では異なる表記を使用していることに注意してください）。 0_Eは無限遠点を表します。 式(x / y mod z)は、(w * y) mod z = x mod zを満たす、z未満の自然数wを表します。

The function J is defined as

関数Jは次のように定義されます。

   J(pi) = [pi] * G

   J(pi) = [pi] * G

The value of K_c1 is derived as

K_c1の値は次のように導出されます。

   K_c1 = P(K_c1'), where K_c1' = [S_c1] * G

   K_c1 = P(K_c1'), where K_c1' = [S_c1] * G

where S_c1 is a random number within the range [1, r-1]. The server MUST check that (1) the value of received K_c1 represents a valid curve point and (2) [h] * K_c1' is not equal to 0_E.

ここで、S_c1は範囲[1, r-1]内の乱数です。 サーバーは、(1)受信したK_c1の値が曲線上の有効な点を表していること、および(2)[h] * K_c1'が0_Eと等しくないことを確認しなければなりません（MUST）。

Let an intermediate integer t_1 be

中間の整数t_1を次のようにします。

   t_1 = INT(H(octet(1) | OCTETS(K_c1)))

   t_1 = INT(H(octet(1) | OCTETS(K_c1)))

The value of K_s1 is derived from J(pi) and K_c1' = P'(K_c1) as

K_s1の値は、J(pi)とK_c1' = P'(K_c1)から次のように導出されます。

   K_s1 = P([S_s1] * (J(pi) + [t_1] * K_c1'))

   K_s1 = P([S_s1] * (J(pi) + [t_1] * K_c1'))

where S_s1 is a random number within the range [1, r-1]. The value of K_s1 MUST represent a valid curve point and satisfy [h] * P'(K_s1) <> 0_E. If this condition is not satisfied, the server MUST reject the exchange. The client MUST check this condition upon reception.

ここで、S_s1は範囲[1, r-1]内の乱数です。 K_s1の値は、曲線上の有効な点を表し、かつ[h] * P'(K_s1) <> 0_Eを満たさなければなりません（MUST）。 この条件が満たされない場合、サーバーは交換を拒否しなければなりません（MUST）。 クライアントは、受信時にこの条件を確認しなければなりません（MUST）。

Let an intermediate integer t_2 be

中間の整数t_2を次のようにします。

   t_2 = INT(H(octet(2) | OCTETS(K_c1) | OCTETS(K_s1)))

   t_2 = INT(H(octet(2) | OCTETS(K_c1) | OCTETS(K_s1)))

The value z on the client side is derived by the following equation:

クライアント側の値zは、次の式で導出されます。

   z = P([(S_c1 + t_2) / (S_c1 * t_1 + pi) mod r] * P'(K_s1))

   z = P([(S_c1 + t_2) / (S_c1 * t_1 + pi) mod r] * P'(K_s1))

The value z on the server side is derived by the following equation:

サーバー側の値zは、次の式で導出されます。

   z = P([S_s1] * (P'(K_c1) + [t_2] * G))

5. Security Considerations

5. セキュリティーに関する考慮事項

Please refer to the Security Considerations section of the core specification [RFC8120] for algorithm-independent considerations.

アルゴリズムに依存しない考慮事項については、コア仕様[RFC8120]のセキュリティーに関する考慮事項のセクションを参照してください。

5.1. General Implementation Considerations

5.1. 実装に関する一般的な考慮事項

  • During the exchange, the value VK_s, defined in [RFC8120], MUST only be sent when the server has received a correct (expected) value of VK_c. This is a cryptographic requirement, as stated in [ISO.11770-4.2006].

  • All random numbers used in these algorithms MUST be cryptographically secure against forward and backward guessing attacks.

  • To prevent timing-based side-channel attacks, computation times of all numerical operations on discrete-logarithm group elements and elliptic-curve points MUST be normalized and made independent of the exact values.

  • 交換の間、[RFC8120]で定義されている値VK_sは、サーバーが正しい（期待どおりの）VK_cの値を受信した場合にのみ送信しなければなりません（MUST）。 これは、[ISO.11770-4.2006]に記載されているとおり、暗号上の要件です。

  • これらのアルゴリズムで使用するすべての乱数は、前方および後方の推測攻撃に対して暗号学的に安全でなければなりません（MUST）。

  • タイミングに基づくサイドチャネル攻撃を防ぐために、離散対数の群の要素と楕円曲線上の点に対するすべての数値演算の計算時間は、平準化し、正確な値に依存しないようにしなければなりません（MUST）。

5.2. Cryptographic Assumptions and Considerations

5.2. 暗号上の前提と考慮事項

The notes in this subsection are for those who analyze the security of this algorithm and those who might want to make a derived work from this algorithm specification.

この節の注記は、このアルゴリズムのセキュリティーを分析する人と、このアルゴリズム仕様から派生物を作成しようとする人に向けたものです。

  • The treatment of an invalid K_s1 value in the exchange has been changed from the method defined in the original ISO specification, which specifies that the sender should retry with another random S_s1 value. We specify that the exchange must be rejected. This is due to an observation that this condition is less likely to result from a random error caused by an unlucky choice of S_s1 but is more likely the result of a systematic failure caused by an invalid J(pi) value (even implying possible denial-of-service attacks).

  • The usual construction of authenticated key exchange algorithms consists of a key exchange phase and a key verification phase. To avoid security risks or vulnerabilities caused by mixing values from two or more key exchanges, the latter usually involves some kinds of exchange transactions to be verified. In the algorithms defined in this document, such verification steps are provided in the generalized definitions of VK_c and VK_s in [RFC8120]. If the algorithm defined above is used in other protocols, this aspect MUST be given careful consideration.

  • The domain parameters chosen and specified in this document are based on a few assumptions. In the discrete-logarithm setting, q has to be a safe prime ([(q - 1) / 2] must also be prime), and r should be the largest possible value [(q - 1) / 2]. In the elliptic-curve setting, r has to be prime. Implementers defining a variation of this algorithm using a different domain parameter SHOULD be attentive to these conditions.

  • 交換における無効なK_s1の値の扱いは、元のISO仕様で定義されている方法から変更されています。 元のISO仕様では、送信者は別のランダムなS_s1の値で再試行すべきであると規定しています。 この文書では、交換を拒否しなければならないと規定します。 これは、この条件が、S_s1の不運な選択によって引き起こされるランダムなエラーから生じる可能性は低く、むしろ無効なJ(pi)の値によって引き起こされる系統的な障害の結果である可能性が高い（さらにはサービス拒否攻撃の可能性を示唆することさえある）という観察によるものです。

  • 認証付き鍵交換アルゴリズムの通常の構成は、鍵交換フェーズと鍵検証フェーズで成り立っています。 2つ以上の鍵交換の値が混ざることによって生じるセキュリティー上のリスクや脆弱性を避けるために、後者には通常、検証対象となる何らかの種類の交換トランザクションが含まれます。 この文書で定義するアルゴリズムでは、そのような検証ステップは、[RFC8120]のVK_cとVK_sの一般化された定義で提供されます。 上で定義したアルゴリズムを他のプロトコルで使用する場合は、この点を慎重に考慮しなければなりません（MUST）。

  • この文書で選択し規定するドメインパラメーターは、いくつかの前提に基づいています。 離散対数の設定では、qは安全素数でなければならず（[(q - 1) / 2]も素数でなければなりません）、rは可能な限り最大の値[(q - 1) / 2]であるべきです。 楕円曲線の設定では、rは素数でなければなりません。 異なるドメインパラメーターを使用してこのアルゴリズムの変種を定義する実装者は、これらの条件に注意を払うべきです（SHOULD）。
