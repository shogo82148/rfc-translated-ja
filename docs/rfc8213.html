RFC 8213

Security of Messages Exchanged between Servers and Relay Agents

RFC 8213

サーバーとリレーエージェントの間で交換されるメッセージのセキュリティー

Abstract

概要

The Dynamic Host Configuration Protocol for IPv4 (DHCPv4) has no guidance for how to secure messages exchanged between servers and relay agents. The Dynamic Host Configuration Protocol for IPv6 (DHCPv6) states that IPsec should be used to secure messages exchanged between servers and relay agents but does not require encryption. With recent concerns about pervasive monitoring and other attacks, it is appropriate to require securing relay-to-relay and relay-to-server communication for DHCPv6 and relay-to-server communication for DHCPv4.

IPv4のための動的ホスト構成プロトコル（DHCPv4）には、サーバーとリレーエージェントの間で交換されるメッセージを保護する方法についての指針がありません。IPv6のための動的ホスト構成プロトコル（DHCPv6）は、サーバーとリレーエージェントの間で交換されるメッセージを保護するためにIPsecを使用すべきであると述べていますが、暗号化は要求していません。広範な監視（pervasive monitoring）やその他の攻撃に対する近年の懸念を踏まえ、DHCPv6ではリレー間およびリレーとサーバー間の通信の保護を、DHCPv4ではリレーとサーバー間の通信の保護を要求するのが適切です。

1. Introduction

1. はじめに

The Dynamic Host Configuration Protocol for IPv4 (DHCPv4) [RFC2131] and the Bootstrap Protocol [RFC1542] have no guidance for how to secure messages exchanged between servers and relay agents. The Dynamic Host Configuration Protocol for IPv6 (DHCPv6) [RFC3315] states that IPsec should be used to secure messages exchanged between servers and relay agents but does not recommend encryption. With recent concerns about pervasive monitoring [RFC7258], it is appropriate to require use of IPsec with encryption for relay-to-server communication for DHCPv4 and require use of IPsec with encryption for relay-to-relay and relay-to-server communication for DHCPv6.

IPv4のための動的ホスト構成プロトコル（DHCPv4）[RFC2131]とブートストラッププロトコル（Bootstrap Protocol）[RFC1542]には、サーバーとリレーエージェントの間で交換されるメッセージを保護する方法についての指針がありません。IPv6のための動的ホスト構成プロトコル（DHCPv6）[RFC3315]は、サーバーとリレーエージェントの間で交換されるメッセージを保護するためにIPsecを使用すべきであると述べていますが、暗号化は推奨していません。広範な監視[RFC7258]に対する近年の懸念を踏まえ、DHCPv4ではリレーとサーバー間の通信に暗号化付きのIPsecの使用を要求し、DHCPv6ではリレー間およびリレーとサーバー間の通信に暗号化付きのIPsecの使用を要求するのが適切です。

This document specifies the optional requirements for relay agent and server implementations to support IPsec authentication and encryption and recommends that operators enable this IPsec support.

この文書は、リレーエージェントとサーバーの実装がIPsecによる認証と暗号化をサポートするための任意の要件を規定し、運用者がこのIPsecのサポートを有効にすることを推奨します。

2. 要件言語と用語

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

This document uses terminology from [RFC1542], [RFC2131], and [RFC3315].

この文書は、[RFC1542]、[RFC2131]、[RFC3315]の用語を使用します。

3. Security of Messages Exchanged between Servers and Relay Agents

3. サーバーとリレーエージェントの間で交換されるメッセージのセキュリティー

For DHCPv6 [RFC3315], this specification REQUIRES relay and server implementations to support IPsec encryption of relay-to-relay and relay-to-server communication as documented below. The remainder of this section replaces the text in Section 21.1 of [RFC3315] when this specification is followed.

DHCPv6[RFC3315]について、この仕様は、以下に記述するように、リレーとサーバーの実装に対して、リレー間およびリレーとサーバー間の通信のIPsec暗号化をサポートすることを要求します（REQUIRES）。この仕様に従う場合、このセクションの残りの部分は[RFC3315]のセクション21.1のテキストを置き換えます。

For DHCPv4 [RFC2131], this specification REQUIRES relay and server implementations to support IPsec encryption of relay-to-server communication as documented below.

DHCPv4[RFC2131]について、この仕様は、以下に記述するように、リレーとサーバーの実装に対して、リレーとサーバー間の通信のIPsec暗号化をサポートすることを要求します（REQUIRES）。

This specification RECOMMENDS that operators enable IPsec for this communication.

この仕様は、運用者がこの通信に対してIPsecを有効にすることを推奨します（RECOMMENDS）。

By using IPsec with encryption for this communication, potentially sensitive client message and relay included information, such as the DHCPv4 Relay Agent Information option (82) [RFC3046], vendor-specific information (for example, the options defined in [CableLabs-DHCP]), and Access-Network-Identifier option(s) [RFC7839], are protected from pervasive monitoring and other attacks.

この通信に暗号化付きのIPsecを使用することで、潜在的に機密性の高いクライアントメッセージとリレーが含める情報、たとえばDHCPv4のRelay Agent Informationオプション（82）[RFC3046]、ベンダー固有の情報（たとえば[CableLabs-DHCP]で定義されているオプション）、Access-Network-Identifierオプション[RFC7839]などが、広範な監視やその他の攻撃から保護されます。

Relay agents and servers MUST be able to exchange messages using the IPsec mechanisms described in [RFC4301] with the conditions below. If a client message is relayed through multiple relay agents (relay chain), each of the relay agents MUST have established independent, pairwise trust relationships. That is, if messages from client C will be relayed by relay agent A to relay agent B and then to the server, relay agents A and B MUST be configured to use IPsec for the messages they exchange, and relay agent B and the server MUST be configured to use IPsec for the messages they exchange.

リレーエージェントとサーバーは、以下の条件のもとで、[RFC4301]で記述されているIPsecのメカニズムを使用してメッセージを交換できる必要があります（MUST）。クライアントのメッセージが複数のリレーエージェントを経由して中継される場合（リレーチェーン）、各リレーエージェントは、独立した1対1の信頼関係を確立している必要があります（MUST）。つまり、クライアントCからのメッセージがリレーエージェントAによってリレーエージェントBへ中継され、さらにサーバーへ中継される場合、リレーエージェントAとBは、両者が交換するメッセージにIPsecを使用するように設定されている必要があります（MUST）。また、リレーエージェントBとサーバーも、両者が交換するメッセージにIPsecを使用するように設定されている必要があります（MUST）。

Relay agents and servers use IPsec with the following conditions:

リレーエージェントとサーバーは、次の条件でIPsecを使用します。

Selectors
Relay agents are manually configured with the addresses of the relay agent or server to which DHCP messages are to be forwarded. Each relay agent and server that will be using IPsec for securing DHCP messages MUST also be configured with a list of the relay agents to which messages will be returned. The selectors for the relay agents and servers will be the pairs of addresses defining relay agents and servers and the direction of DHCP message exchange on DHCPv4 UDP port 67 or DHCPv6 UDP port 547.
Mode
Relay agents and servers MUST use IPsec in transport mode and use Encapsulating Security Payload (ESP).
Encryption and authentication algorithms
This document REQUIRES combined mode algorithms for ESP authenticated encryption, ESP encryption algorithms, and ESP authentication algorithms as per Sections 2.1, 2.2, and 2.3 of [RFC7321], respectively. Encryption is required as relay agents may forward unencrypted client messages as well as include additional sensitive information, such as vendor-specific information (for example, the options defined in [CableLabs-DHCP]) and the Access-Network-Identifier Option defined in [RFC7839].
Key management
Because both relay agents and servers tend to be managed by a single organizational entity, public key schemes MAY be optional. Manually configured key management MAY suffice but does not provide defense against replayed messages. Accordingly, Internet Key Exchange Protocol Version 2 (IKEv2) [RFC7296] with pre-shared secrets SHOULD be supported. IKEv2 with public keys MAY be supported. Additional information on manual vs. automated key management and when one should be used over the other can be found in [RFC4107].
Security policy
DHCP messages between relay agents and servers MUST only be accepted from DHCP peers as identified in the local configuration.
Authentication
Shared keys, indexed to the source IP address of the received DHCP message, are adequate in this application.
セレクター
リレーエージェントには、DHCPメッセージの転送先となるリレーエージェントまたはサーバーのアドレスが手動で設定されます。DHCPメッセージの保護にIPsecを使用する各リレーエージェントとサーバーには、メッセージの返送先となるリレーエージェントの一覧も設定されている必要があります（MUST）。リレーエージェントとサーバーのセレクターは、リレーエージェントとサーバーを定めるアドレスの組と、DHCPv4のUDPポート67またはDHCPv6のUDPポート547上でのDHCPメッセージ交換の方向になります。
モード
リレーエージェントとサーバーは、トランスポートモードでIPsecを使用し、カプセル化セキュリティーペイロード（ESP）を使用しなければなりません（MUST）。
暗号化アルゴリズムと認証アルゴリズム
この文書は、[RFC7321]のセクション2.1、2.2、2.3にそれぞれ従った、ESPの認証付き暗号のための複合モード（combined mode）アルゴリズム、ESPの暗号化アルゴリズム、ESPの認証アルゴリズムを要求します（REQUIRES）。リレーエージェントは、暗号化されていないクライアントメッセージを転送することがあるうえ、ベンダー固有の情報（たとえば[CableLabs-DHCP]で定義されているオプション）や[RFC7839]で定義されているAccess-Network-Identifierオプションなど、機密性の高い追加情報を含めることもあるため、暗号化が必要です。
鍵管理
リレーエージェントとサーバーはどちらも単一の組織体によって管理される傾向があるため、公開鍵方式は任意としてもよいです（MAY）。手動で設定する鍵管理で十分な場合があります（MAY）が、リプレイされたメッセージに対する防御は提供されません。したがって、事前共有秘密を用いるインターネット鍵交換プロトコルバージョン2（IKEv2）[RFC7296]をサポートすべきです（SHOULD）。公開鍵を用いるIKEv2をサポートしてもよいです（MAY）。手動の鍵管理と自動の鍵管理の比較や、どのような場合にどちらを使用すべきかについての追加情報は、[RFC4107]にあります。
セキュリティーポリシー
リレーエージェントとサーバーの間のDHCPメッセージは、ローカルの設定で識別されるDHCPピアからのものだけを受け入れなければなりません（MUST）。
認証
この用途では、受信したDHCPメッセージの送信元IPアドレスで索引付けされた共有鍵で十分です。

Note: As using IPsec with multicast has additional complexities (see [RFC5374]), relay agents SHOULD be configured to forward DHCP messages to unicast addresses.

注: マルチキャストでIPsecを使用することには追加の複雑さがあるため（[RFC5374]を参照）、リレーエージェントは、DHCPメッセージをユニキャストアドレスに転送するように設定されるべきです（SHOULD）。

4. Security Considerations

4. セキュリティーに関する考慮事項

The security model specified in this document is hop by hop. For DHCPv6, there could be multiple relay agents between a client and server, and each of these hops needs to be secured. For DHCPv4, there is no support for multiple relays.

この文書で規定するセキュリティーモデルはホップバイホップです。DHCPv6では、クライアントとサーバーの間に複数のリレーエージェントが存在する可能性があり、これらの各ホップを保護する必要があります。DHCPv4では、複数のリレーはサポートされていません。

As this document only mandates securing messages exchanged between relay agents and servers, the message exchanges between clients and the first-hop relay agent or server are not secured. Clients may follow the recommendations in [RFC7844] to minimize what information they expose or make use of secure DHCPv6 [SEC-DHCPv6] to secure communication between the client and server.

この文書はリレーエージェントとサーバーの間で交換されるメッセージの保護のみを義務付けているため、クライアントと最初のホップのリレーエージェントまたはサーバーとの間のメッセージ交換は保護されません。クライアントは、公開する情報を最小限にするために[RFC7844]の推奨事項に従うか、クライアントとサーバーの間の通信を保護するためにセキュアDHCPv6[SEC-DHCPv6]を利用できます。

As mentioned in Section 14 of [RFC4552], the following are known limitations of the usage of manual keys:

[RFC4552]のセクション14で述べられているように、手動の鍵の使用には次のような既知の制限があります。

  • As the sequence numbers cannot be negotiated, replay protection cannot be provided. This leaves DHCP insecure against all the attacks that can be performed by replaying DHCP packets.
  • Manual keys are usually long lived (changing them often is a tedious task). This gives an attacker enough time to discover the keys.
  • シーケンス番号をネゴシエートできないため、リプレイ保護を提供できません。このため、DHCPはDHCPパケットのリプレイによって実行可能なあらゆる攻撃に対して安全ではなくなります。
  • 手動の鍵は通常、長期間使用されます（鍵を頻繁に変更するのは面倒な作業です）。このため、攻撃者には鍵を発見するのに十分な時間が与えられます。

It should be noted that if the requirements in this document are followed, while the DHCP traffic on the wire between relays and servers is encrypted, the unencrypted data may still be available through other attacks on the DHCP servers, relays, and related systems. Securing these systems and the data in databases and logs also needs to be considered on both the systems themselves and when transferred over a network (i.e., to network attached storage for backups or to operational support systems).

この文書の要件に従った場合、リレーとサーバーの間を流れるDHCPトラフィックは暗号化されますが、DHCPサーバー、リレー、および関連システムに対するほかの攻撃によって、暗号化されていないデータが依然として入手される可能性があることに注意すべきです。これらのシステムと、データベースやログ内のデータの保護についても、システム自体の上と、ネットワーク越しに転送されるとき（つまり、バックアップのためのネットワーク接続ストレージや運用支援システムへの転送時）の両方で考慮する必要があります。

Use of IPsec as described herein is also applicable to Lightweight DHCPv6 Relay Agents [RFC6221], as they have a link-local address that can be used to secure communication with their next-hop relay(s).

ここで説明したIPsecの使用は、軽量DHCPv6リレーエージェント（Lightweight DHCPv6 Relay Agent）[RFC6221]にも適用できます。軽量DHCPv6リレーエージェントは、次のホップのリレーとの通信を保護するために使用できるリンクローカルアドレスを持っているからです。
