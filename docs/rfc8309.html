RFC 8309

Service Models Explained

RFC 8309

サービスモデルの解説

Abstract

概要

The IETF has produced many modules in the YANG modeling language. The majority of these modules are used to construct data models to model devices or monolithic functions.

IETFは、YANGモデリング言語で多くのモジュールを作成してきました。 これらのモジュールの大部分は、デバイスや単体の機能をモデル化するデータモデルを構築するために使われています。

A small number of YANG modules have been defined to model services (for example, the Layer 3 Virtual Private Network Service Model (L3SM) produced by the L3SM working group and documented in RFC 8049).

サービスをモデル化するために定義されたYANGモジュールは、ごく少数です（たとえば、L3SMワーキンググループが作成し、RFC 8049で文書化されたレイヤー3仮想プライベートネットワークサービスモデル（L3SM））。

This document describes service models as used within the IETF and also shows where a service model might fit into a software-defined networking architecture. Note that service models do not make any assumption of how a service is actually engineered and delivered for a customer; details of how network protocols and devices are engineered to deliver a service are captured in other modules that are not exposed through the interface between the customer and the provider.

この文書は、IETFの中で使われているサービスモデルについて説明し、またソフトウェア定義ネットワーキングのアーキテクチャーの中でサービスモデルがどこに位置づけられるかを示します。 サービスモデルは、顧客に対してサービスが実際にどのように構築され提供されるかについて、何の前提も置かないことに注意してください。 サービスを提供するためにネットワークプロトコルやデバイスをどのように構築するかの詳細は、顧客とプロバイダーの間のインターフェイスでは公開されない他のモジュールで扱われます。

1. Introduction

1. はじめに

In recent years, the number of modules written in the YANG modeling language [RFC6020] for configuration and monitoring has blossomed. Many of these are used for device-level configuration (for example, [RFC7223]) or for control of monolithic functions or protocol instances (for example, [RFC7407]).

近年、設定と監視のためにYANGモデリング言語[RFC6020]で書かれたモジュールの数が急増しています。 これらの多くは、デバイスレベルの設定（たとえば[RFC7223]）や、単体の機能やプロトコルインスタンスの制御（たとえば[RFC7407]）に使われています。

[RFC7950] makes a distinction between a "data model", which it defines as describing how data is represented and accessed, and a "YANG module", which defines hierarchies of schema nodes to make a self-contained and compilable block of definitions and inclusions. YANG structures data models into modules for ease of use.

[RFC7950]は、「データモデル」と「YANGモジュール」を区別しています。 前者は、データがどのように表現され、アクセスされるかを記述するものと定義されており、後者は、スキーマノードの階層を定義して、定義とインクルードからなる自己完結型でコンパイル可能なブロックを作るものです。 YANGは、使いやすさのためにデータモデルをモジュールに構造化します。

Within the context of Software-Defined Networking (SDN) [RFC7149] [RFC7426], YANG data modules may be used on the interface between a controller and network devices, as well as between network orchestrators and controllers. There may also be a hierarchy of such components with super controllers, domain controllers, and device controllers all exchanging information and instructions using YANG modules.

ソフトウェア定義ネットワーキング（SDN）[RFC7149] [RFC7426]の文脈では、YANGデータモジュールは、コントローラーとネットワークデバイスの間のインターフェイスや、ネットワークオーケストレーターとコントローラーの間のインターフェイスで使われることがあります。 また、スーパーコントローラー、ドメインコントローラー、デバイスコントローラーがすべてYANGモジュールを使って情報や指示を交換する、こうしたコンポーネントの階層構造が存在する場合もあります。

There has been interest in using YANG to define and document data models that describe services in a portable way that is independent of which network operator uses the model, for example, the Layer 3 Virtual Private Network Service Model (L3SM) [RFC8049]. Such models may be used in manual and even paper-driven service request processes with a gradual transition to IT-based mechanisms. Ultimately, they could be used in online, software-driven dynamic systems and may be used as part of an SDN system.

YANGを使って、どのネットワーク運用者がモデルを使うかに依存しない可搬性のある方法でサービスを記述するデータモデルを定義し、文書化することに関心が集まっています。 たとえば、レイヤー3仮想プライベートネットワークサービスモデル（L3SM）[RFC8049]がその一例です。 こうしたモデルは、手作業による、さらには紙ベースのサービス申し込みプロセスで使われ、徐々にITベースのメカニズムへと移行していくことがあります。 最終的には、オンラインでソフトウェア駆動の動的なシステムで使われる可能性があり、SDNシステムの一部として使われることもあります。

This document explains the scope and purpose of service models within the IETF (and is limited to within the scope of the IETF) and describes how a service model can be used by a network operator. Equally, this document clarifies what a service model is not and dispels some common misconceptions.

この文書は、IETFにおけるサービスモデルの範囲と目的を説明し（その対象はIETFの範囲内に限られます）、ネットワーク運用者がサービスモデルをどのように使用できるかを記述します。 同様に、この文書は、サービスモデルが何でないかを明確にし、よくある誤解を解消します。

The document also shows where a service model might fit into an SDN architecture, but it is important to note that a service model does not require or preclude the use of SDN. Note that service models do not make any assumption of how a service is actually engineered and delivered to a customer; details of how network protocols and devices are engineered to deliver a service are captured in other modules that are not exposed through the interface between the customer and the provider.

この文書はまた、SDNアーキテクチャーの中でサービスモデルがどこに位置づけられるかを示しますが、サービスモデルはSDNの使用を必要とするものでも、排除するものでもないことに注意することが重要です。 サービスモデルは、顧客に対してサービスが実際にどのように構築され提供されるかについて、何の前提も置かないことに注意してください。 サービスを提供するためにネットワークプロトコルやデバイスをどのように構築するかの詳細は、顧客とプロバイダーの間のインターフェイスでは公開されない他のモジュールで扱われます。

In summary, a service model is a formal representation of the data elements that describe a network service as that service is described to or requested by a customer of a network operator. Details included in the service model include a description of the service as experienced by the customer, but not features of how that service is delivered or realized by the service provider.

要約すると、サービスモデルとは、ネットワーク運用者の顧客に対して説明される、あるいは顧客から要求されるネットワークサービスを記述するデータ要素を形式的に表現したものです。 サービスモデルに含まれる詳細には、顧客が体験するサービスの説明は含まれますが、そのサービスがサービスプロバイダーによってどのように提供または実現されるかの特徴は含まれません。

Other work on classifying YANG modules has been done in [RFC8199]. That document provides an important reference for this document and also uses the term "service module". In this document, Section 6.1 provides a comparison between these two uses of the same terminology.

YANGモジュールを分類する他の取り組みは、[RFC8199]で行われています。 その文書は、この文書にとって重要な参考文献であり、「サービスモジュール（service module）」という用語も使っています。 この文書では、セクション6.1で、同じ用語のこれら2つの使い方を比較します。

2. Terms and Concepts

2. 用語と概念

Readers should familiarize themselves with the description and classification of YANG modules provided in [RFC8199].

読者は、[RFC8199]で示されているYANGモジュールの説明と分類に慣れておくべきです。

The following terms are used in this document:

この文書では、次の用語を使います。

Network Operator:
This term is used to refer to the company that owns and operates one or more networks that provide Internet connectivity services and/or other services.
Customer:
This term refers to someone who purchases a service (including connectivity) from a network operator. In the context of this document, a customer is usually a company that runs their own network or computing platforms and wishes to connect to the Internet or between sites. Such a customer may operate an enterprise network or a data center. Sometimes this term may also be used to refer to the individual in such a company who contracts to buy services from a network operator. A customer as described here is a separate commercial operation from the network operator, but some companies may operate with internal customers so that, for example, an IP/MPLS packet network may be the customer of an optical transport network.
Service:

A network operator delivers one or more services to a customer. A service in the context of this document (sometimes called a Network Service) is some form of connectivity between customer sites and the Internet or between customer sites across the network operator's network and across the Internet. However, a distinction should be drawn between the parameters that describe a service as included in a customer service model (see the definition of this term, below) and a Service Level Agreement (SLA), as discussed in Sections 5 and 7.2.

A service may be limited to simple connectivity (such as IP-based Internet access), may be a tunnel (such as a virtual circuit), or may involve more complex connectivity (such as in a multisite virtual private network). Services may be further enhanced by additional functions providing security, load balancing, accounting, and so forth. Additionally, services usually include guarantees of quality, throughput, and fault reporting.

This document makes a distinction between a service as delivered to a customer (that is, the service as discussed on the interface between a customer and the network operator) and the service as realized within the network (as described in [RFC8199]). This distinction is discussed further in Section 6.

Readers may also refer to [RFC7297] for an example of how an IP connectivity service may be characterized.

Data Model:

The information model (IM) and data model (DM) concepts are described in [RFC3444]. That document defines a data model by contrasting it with the definition of an IM as follows:

The main purpose of an IM is to model managed objects at a conceptual level, independent of any specific implementations or protocols used to transport the data. The degree of specificity (or detail) of the abstractions defined in the IM depends on the modeling needs of its designers. In order to make the overall design as clear as possible, an IM should hide all protocol and implementation details. Another important characteristic of an IM is that it defines relationships between managed objects.

DMs, conversely, are defined at a lower level of abstraction and include many details. They are intended for implementors and include protocol-specific constructs.

As mentioned in Section 1, this document also uses the terms "data model" and "YANG module" as defined in [RFC7950].

Service Model:

A service model is a specific type of data model. It describes a service and the parameters of the service in a portable way that can be used uniformly and independent of the equipment and operating environment. The service model may be divided into the two following categories:

Customer Service Model:

A customer service model is used to describe a service as offered or delivered to a customer by a network operator as shown in Figure 1. It can be used by a human (via a user interface such as a GUI, web form, or Command-Line Interface (CLI)) or by software to configure or request a service and may equally be consumed by a human (such as via an order fulfillment system) or by a software component. Such models are sometimes referred to simply as "service models" [RFC8049]. A customer service model is expressed in a YANG module as a core set of parameters that are common across network operators: additional features that are specific to the offerings of individual network operators would be defined in extensions or augmentations of the module. Except where specific technology details are directly pertinent to the customer (such as encapsulations or mechanisms applied on access links), customer service models are technology agnostic so that the customer does not have influence over or knowledge of how the network operator engineers the service.

An example of where such details are relevant to the customer is when they describe the behavior or interactions on the interface between the equipment at the customer site (often referred to as the Customer Edge or CE equipment) and the equipment at the network operator's site (usually referred to as the Provider Edge or PE equipment).

Service Delivery Model:
A service delivery model is used by a network operator to define and manage how a service is engineered in the network. It can be used by a human operator (such as via a management station) or by a software tool to instruct network components. The YANG modules that encode such models are sometimes referred to as "network service YANG modules" [RFC8199] and are consumed by "external systems" such as an Operations Support System (OSS). A service delivery module is expressed as a core set of parameters that are common across a network type and technology: additional features that are specific to the configuration of individual vendor equipment or proprietary protocols would be defined in extensions or augmentations of the module. Service delivery modules include technology-specific modules.

The distinction between a customer service model and a service delivery model needs to be clarified. The modules that encode a customer service model are not used to directly configure network devices, protocols, or functions: it is not something that is sent to network devices (i.e., routers or switches) for processing. Equally, the modules that encode a customer service model do not describe how a network operator realizes and delivers the service described by the module. This distinction is discussed further in later sections.

ネットワーク運用者（Network Operator）：
この用語は、インターネット接続サービスやその他のサービスを提供する1つ以上のネットワークを所有し運用する企業を指すために使われます。
顧客（Customer）：
この用語は、ネットワーク運用者からサービス（接続性を含む）を購入する者を指します。 この文書の文脈では、顧客は通常、自身のネットワークやコンピューティングプラットフォームを運用し、インターネットへの接続や拠点間の接続を望む企業です。 そのような顧客は、企業ネットワークやデータセンターを運用していることがあります。 この用語は、そのような企業の中でネットワーク運用者からサービスを購入する契約を結ぶ個人を指すために使われることもあります。 ここで説明する顧客は、ネットワーク運用者とは別の商業的な事業体ですが、企業によっては社内顧客を持って運営している場合もあります。 たとえば、IP/MPLSパケットネットワークが光トランスポートネットワークの顧客になることがあります。
サービス（Service）：

ネットワーク運用者は、顧客に1つ以上のサービスを提供します。 この文書の文脈でのサービス（ネットワークサービスと呼ばれることもあります）とは、顧客の拠点とインターネットの間、またはネットワーク運用者のネットワークやインターネットを介した顧客の拠点間の、何らかの形の接続性です。 ただし、セクション5および7.2で論じるように、顧客サービスモデル（この用語の定義は後述）に含まれるサービスを記述するパラメーターと、サービスレベル合意（Service Level Agreement、SLA）とは区別すべきです。

サービスは、単純な接続性（IPベースのインターネットアクセスなど）に限られることもあれば、トンネル（仮想回線など）であることも、より複雑な接続性（マルチサイトの仮想プライベートネットワークなど）を伴うこともあります。 サービスは、セキュリティー、負荷分散、課金などを提供する追加機能によって、さらに強化されることもあります。 加えて、サービスには通常、品質、スループット、障害報告の保証が含まれます。

この文書では、顧客に提供されるサービス（つまり、顧客とネットワーク運用者の間のインターフェイスで論じられるサービス）と、ネットワーク内で実現されるサービス（[RFC8199]で説明されているもの）とを区別します。 この区別については、セクション6でさらに論じます。

IP接続サービスをどのように特徴づけられるかの例については、[RFC7297]も参照してください。

データモデル（Data Model）：

情報モデル（IM）とデータモデル（DM）の概念は、[RFC3444]で説明されています。 その文書は、データモデルを、IMの定義と対比させて次のように定義しています。

IMの主な目的は、特定の実装やデータの転送に使われるプロトコルとは独立に、概念レベルで管理オブジェクトをモデル化することです。 IMで定義される抽象化の具体性（または詳細さ）の度合いは、その設計者のモデル化のニーズによって決まります。 全体の設計をできるだけ明確にするために、IMはプロトコルと実装の詳細をすべて隠すべきです。 IMのもう1つの重要な特徴は、管理オブジェクト間の関係を定義することです。

逆に、DMはより低い抽象化レベルで定義され、多くの詳細を含みます。 DMは実装者を対象としており、プロトコル固有の構成要素を含みます。

セクション1で述べたように、この文書では[RFC7950]で定義されている「データモデル」と「YANGモジュール」という用語も使います。

サービスモデル（Service Model）：

サービスモデルは、データモデルの特定の種類です。 サービスモデルは、サービスとそのサービスのパラメーターを、機器や運用環境に依存せず一様に使用できる可搬性のある方法で記述します。 サービスモデルは、次の2つのカテゴリーに分けられます。

顧客サービスモデル（Customer Service Model）：

顧客サービスモデルは、図1に示すように、ネットワーク運用者が顧客に提示する、または提供するサービスを記述するために使われます。 顧客サービスモデルは、サービスを設定または要求するために、人間（GUI、Webフォーム、コマンドラインインターフェイス（CLI）などのユーザーインターフェイスを介して）やソフトウェアが使用でき、同様に人間（受注処理システムを介するなど）やソフトウェアコンポーネントが利用することもできます。 こうしたモデルは、単に「サービスモデル」[RFC8049]と呼ばれることもあります。 顧客サービスモデルは、ネットワーク運用者間で共通するパラメーターの中核セットとしてYANGモジュールで表現されます。 個々のネットワーク運用者の提供内容に固有の追加機能は、そのモジュールの拡張（extension）または補強（augmentation）で定義されることになります。 特定の技術の詳細が顧客に直接関係する場合（カプセル化やアクセスリンクに適用されるメカニズムなど）を除き、顧客サービスモデルは技術非依存であり、ネットワーク運用者がサービスをどのように構築するかについて、顧客が影響を与えたり知ったりすることはありません。

そのような詳細が顧客に関係する例としては、顧客拠点の機器（しばしばカスタマーエッジ（Customer Edge）またはCE機器と呼ばれます）とネットワーク運用者の拠点の機器（通常はプロバイダーエッジ（Provider Edge）またはPE機器と呼ばれます）の間のインターフェイスでの振る舞いややり取りを記述する場合があります。

サービス提供モデル（Service Delivery Model）：
サービス提供モデルは、ネットワーク運用者が、ネットワーク内でサービスをどのように構築するかを定義し管理するために使われます。 サービス提供モデルは、ネットワークコンポーネントに指示するために、人間の運用者（管理ステーションを介するなど）やソフトウェアツールが使用できます。 そのようなモデルをエンコードするYANGモジュールは、「ネットワークサービスYANGモジュール（network service YANG modules）」[RFC8199]と呼ばれることもあり、オペレーションサポートシステム（OSS）などの「外部システム」によって利用されます。 サービス提供モジュールは、ネットワークの種類と技術にわたって共通するパラメーターの中核セットとして表現されます。 個々のベンダーの機器や独自プロトコルの設定に固有の追加機能は、そのモジュールの拡張または補強で定義されることになります。 サービス提供モジュールには、技術固有のモジュールが含まれます。

顧客サービスモデルとサービス提供モデルの区別は明確にしておく必要があります。 顧客サービスモデルをエンコードするモジュールは、ネットワークデバイス、プロトコル、機能を直接設定するためには使われません。 つまり、処理のためにネットワークデバイス（すなわち、ルーターやスイッチ）に送られるものではありません。 同様に、顧客サービスモデルをエンコードするモジュールは、そのモジュールで記述されたサービスをネットワーク運用者がどのように実現し提供するかを記述しません。 この区別については、後のセクションでさらに論じます。

3. Using Service Models

3. サービスモデルの使用

As already indicated, customer service models are used on the interface between customers and network operators. This is shown in Figure 1.

すでに示したように、顧客サービスモデルは顧客とネットワーク運用者の間のインターフェイスで使われます。 これを図1に示します。

The language in which a customer service model is described is a choice for whoever specifies the model. The IETF uses the YANG data modeling language defined in [RFC6020].

顧客サービスモデルをどの言語で記述するかは、そのモデルを規定する者の選択に委ねられます。 IETFは、[RFC6020]で定義されているYANGデータモデリング言語を使います。

The encoding and communication protocol used to exchange a customer service model between the customer and network operator is specific to deployment and implementation. The IETF has standardized the NETCONF protocol [RFC6241] and the RESTCONF protocol [RFC8040] for interactions "on the wire" between software components with data encoded in XML or JSON. However, co-located software components might use an internal API, while systems with more direct human interactions might use web pages or even paper forms. Where direct human interaction comes into play, interface interactions may be realized via business practices that may introduce some margin of error, thus raising the priority for automated, deterministic interfaces.

顧客とネットワーク運用者の間で顧客サービスモデルを交換するために使われるエンコーディングと通信プロトコルは、展開と実装に固有です。 IETFは、XMLやJSONでエンコードされたデータを使ったソフトウェアコンポーネント間の「ネットワーク上（on the wire）」のやり取りのために、NETCONFプロトコル[RFC6241]とRESTCONFプロトコル[RFC8040]を標準化しています。 しかし、同じ場所に配置されたソフトウェアコンポーネントは内部APIを使うかもしれませんし、人間がより直接的にやり取りするシステムはWebページや、さらには紙の申込書を使うかもしれません。 人間が直接やり取りする場合には、インターフェイスでのやり取りはある程度の誤りが入り込む可能性のある業務慣行を通じて実現されることがあり、そのため自動化された決定的なインターフェイスの優先度が高まります。

How a network operator processes a customer's service request when described with a customer service model depends on the commercial and operational tools, processes, and policies used by the network operator. These may vary considerably from one network operator to another.

顧客サービスモデルで記述された顧客のサービス要求をネットワーク運用者がどのように処理するかは、そのネットワーク運用者が使う商業上および運用上のツール、プロセス、ポリシーによって決まります。 これらは、ネットワーク運用者ごとに大きく異なる可能性があります。

However, the intent is that the network operator maps the service request into configuration and operational parameters that control one or more networks to deliver the requested services. That means that the network operator (or software run by the network operator) takes the information in the customer service model and determines how to deliver the service by enabling and configuring network protocols and devices. They may achieve this by constructing service delivery models and passing them to network orchestrators or controllers. The use of standard customer service models eases service delivery by means of automation.

しかし、その意図は、ネットワーク運用者がサービス要求を、要求されたサービスを提供するために1つ以上のネットワークを制御する設定パラメーターと運用パラメーターに対応づけることです。 つまり、ネットワーク運用者（またはネットワーク運用者が実行するソフトウェア）は、顧客サービスモデルの情報を受け取り、ネットワークプロトコルとデバイスを有効にして設定することで、どのようにサービスを提供するかを決定します。 これは、サービス提供モデルを構築して、ネットワークオーケストレーターやコントローラーに渡すことで実現される場合があります。 標準の顧客サービスモデルを使うことで、自動化によってサービスの提供が容易になります。

3.1. Practical Considerations

3.1. 実用上の考慮事項

The practicality of customer service models has been repeatedly debated. It has been suggested that network operators have radically different business models and widely diverse commercial offerings, which makes a common customer service model impractical. However, L3SM [RFC8049] results from the consensus of multiple individuals working at network operators and offers a common core of service options that can be augmented according to the needs of individual network operators.

顧客サービスモデルの実用性は、繰り返し議論されてきました。 ネットワーク運用者ごとにビジネスモデルが根本的に異なり、商業的な提供内容も多岐にわたるため、共通の顧客サービスモデルは非現実的だという意見もありました。 しかし、L3SM [RFC8049]は、ネットワーク運用者で働く複数の個人のコンセンサスから生まれたものであり、個々のネットワーク運用者のニーズに応じて補強できるサービスオプションの共通の中核を提供しています。

It has also been suggested that there should be a single, base customer service module, and that details of individual services should be offered as extensions or augmentations of this. It is quite possible that a number of service parameters (such as the identity and postal address of a customer) will be common, and it would be a mistake to define them multiple times (once in each customer service model). However, the distinction between a 'module' and a 'model' should be considered at this point: modules are how the data for models is logically broken out and documented, especially for reuse in multiple models.

また、単一の基本となる顧客サービスモジュールを用意し、個々のサービスの詳細はその拡張または補強として提供すべきだという意見もありました。 いくつかのサービスパラメーター（顧客の識別情報や郵便住所など）が共通になる可能性は十分にあり、それらを（顧客サービスモデルごとに1回ずつ）何度も定義するのは誤りでしょう。 しかし、この点では「モジュール」と「モデル」の区別を考慮すべきです。 モジュールとは、特に複数のモデルで再利用するために、モデルのデータを論理的に分割して文書化する方法のことです。

4. Service Models in an SDN Context

4. SDNの文脈におけるサービスモデル

In an SDN system, the management of network resources and protocols is performed by software systems that determine how best to utilize the network. Figure 2 shows a sample architectural view of an SDN system where network elements are programmed by a component called an "SDN controller" (or "controller" for short) and where controllers are instructed by an orchestrator that has a wider view of the whole of, or part of, a network. The internal organization of an SDN control plane is specific to deployment.

SDNシステムでは、ネットワークリソースとプロトコルの管理は、ネットワークを最もうまく活用する方法を決定するソフトウェアシステムによって行われます。 図2は、SDNシステムのアーキテクチャーの一例を示しています。 このシステムでは、ネットワーク要素は「SDNコントローラー」（略して「コントローラー」）と呼ばれるコンポーネントによってプログラムされ、コントローラーは、ネットワークの全体または一部をより広く見渡すオーケストレーターから指示を受けます。 SDNコントロールプレーンの内部構成は、展開に固有です。

A customer's service request is (or should be) technology agnostic. That is, a customer is unaware of the technology that the network operator has available to deliver the service, so the customer does not make requests specific to the underlying technology but is limited to making requests specific to the service that is to be delivered. The orchestrator must map the service request to its view, and this mapping may include a choice of which networks and technologies to use depending on which service features have been requested.

顧客のサービス要求は技術非依存です（または、そうあるべきです）。 つまり、顧客は、ネットワーク運用者がサービスを提供するために利用できる技術を知らないので、下位の技術に固有の要求はせず、提供されるサービスに固有の要求をするだけです。 オーケストレーターは、サービス要求を自身のビューに対応づけなければならず、この対応づけには、どのサービス機能が要求されたかに応じて、どのネットワークと技術を使うかの選択が含まれることがあります。

One implementation option to achieve this mapping is to split the orchestration function between a "Service Orchestrator" and a "Network Orchestrator" as shown in Figure 3.

この対応づけを実現する実装上の選択肢の1つは、図3に示すように、オーケストレーション機能を「サービスオーケストレーター」と「ネットワークオーケストレーター」に分割することです。

The network configuration models are used by a network orchestrator to instruct controllers (which may each be responsible for multiple network elements) how to configure parts of a network.

5. Possible Causes of Confusion

5. 混乱の原因となりうるもの

In discussing service models, there are several possible causes of confusion:

サービスモデルを論じる際には、混乱の原因となりうるものがいくつかあります。

  • The services we are discussing are connectivity services provided by network operators to customers; the services are achieved by manipulating the network resources of the operator's network. This is a completely different thing to "Foo as a Service" (for example, Storage as a Service (SaaS)) where a service provider offers reachability to a value-added service that is provided at some location in the network using other resources (compute, storage, ...) that are not part of the network itself. The confusion arises not only because of the use of the word "service" in both cases, but also because network operators may offer both types of service to their customers.
  • Network operation is normally out of scope in the discussion of services between a network operator and a customer. That means that the customer service model does not reveal to the customer anything about how the network operator delivers the service, nor does the model expose details of technology or network resources used to provide the service (all of these details could, in any case, be considered security vulnerabilities). For example, in the simple case of point-to-point virtual link connectivity provided by a network tunnel (such as an MPLS pseudowire), the network operator does not expose the path through the network that the tunnel follows. Of course, this does not preclude the network operator from taking guidance from the customer (such as to avoid routing traffic through a particular country) or from disclosing specific details (such as might be revealed by a route trace), but these are not standard features of the service as described in the customer service model.
  • The network operator may use further data models (service delivery models) that help to describe how the service is realized in the network. These models might be used on the interface between the service orchestrator and the network orchestrator, as shown in Figure 3, and might include many of the pieces of information from the customer service model alongside protocol parameters and device configuration information. [RFC8199] also terms these data models as "service models" and encodes them as "Network Service YANG Modules"; a comparison is provided in Section 6.1. It is important that the service orchestrator be able to map from a customer service model to these service delivery models, but they are not the same thing.
  • Commercial terms (such as "cost per byte", "cost per minute", and "scoped by quality and type of service", as well as terms related to payment) are generally not a good subject for standardization. It is possible that some network operators will enhance standard customer service models to include commercial information, but the way this is done is likely to vary widely between network operators. Thus, this feature is out of scope for standardized customer service models.

  • SLAs have a high degree of overlap with the definition of services present in customer service models. Requests for specific bandwidth, for example, might be present in a customer service model, and agreement to deliver a service is a commitment to the description of the service in the customer service model. However, SLAs typically include a number of fine-grained details about how services are allowed to vary, by how much, and how often. SLAs are also linked to commercial terms with penalties and so forth and thus are also not good topics for standardization. As with commercial terms, it is expected that some network operators will enhance standard customer service models to include SLA parameters either using their own work or depending on material from standards bodies that specialize in this topic, but this feature is out of scope for the IETF's customer service models.

    If a network operator chooses to express an SLA using a data model, that model might be referenced as an extension or an augmentation of the customer service model.

  • ここで論じているサービスは、ネットワーク運用者が顧客に提供する接続サービスであり、そのサービスは運用者のネットワークのネットワークリソースを操作することで実現されます。 これは、「Foo as a Service」（たとえば、Storage as a Service（SaaS））とはまったく別のものです。 後者では、サービスプロバイダーは、ネットワーク自体の一部ではない他のリソース（コンピューティング、ストレージなど）を使ってネットワーク内のどこかで提供される付加価値サービスへの到達性を提供します。 混乱が生じるのは、どちらの場合にも「サービス」という言葉が使われるからだけでなく、ネットワーク運用者が両方の種類のサービスを顧客に提供することがあるからでもあります。
  • ネットワーク運用者と顧客の間のサービスの議論では、ネットワークの運用は通常、範囲外です。 つまり、顧客サービスモデルは、ネットワーク運用者がサービスをどのように提供するかについて何も顧客に明かさず、サービスの提供に使われる技術やネットワークリソースの詳細も公開しません（いずれにせよ、こうした詳細はすべてセキュリティー上の脆弱性とみなされる可能性があります）。 たとえば、ネットワークトンネル（MPLS疑似回線（pseudowire）など）によって提供されるポイントツーポイントの仮想リンク接続という単純な場合、ネットワーク運用者は、そのトンネルが通るネットワーク内のパスを公開しません。 もちろん、ネットワーク運用者が顧客から指示を受けること（特定の国を経由するトラフィックのルーティングを避けるなど）や、特定の詳細を開示すること（経路トレースで明らかになるようなものなど）が妨げられるわけではありませんが、これらは顧客サービスモデルで記述されるサービスの標準的な機能ではありません。
  • ネットワーク運用者は、サービスがネットワーク内でどのように実現されるかを記述するのに役立つ、さらなるデータモデル（サービス提供モデル）を使うことがあります。 これらのモデルは、図3に示すように、サービスオーケストレーターとネットワークオーケストレーターの間のインターフェイスで使われることがあり、プロトコルパラメーターやデバイスの設定情報とともに、顧客サービスモデルの情報の多くを含むことがあります。 [RFC8199]も、これらのデータモデルを「サービスモデル」と呼び、「ネットワークサービスYANGモジュール」としてエンコードしています。 その比較はセクション6.1で示します。 サービスオーケストレーターが顧客サービスモデルからこれらのサービス提供モデルへ対応づけられることは重要ですが、両者は同じものではありません。
  • 商業上の条件（「バイト当たりのコスト」、「分当たりのコスト」、「サービスの品質と種類による範囲指定」などや、支払いに関する条件）は、一般に標準化の対象としては適していません。 一部のネットワーク運用者が、標準の顧客サービスモデルを拡張して商業情報を含めることはありえますが、その方法はネットワーク運用者によって大きく異なる可能性があります。 したがって、この機能は標準化された顧客サービスモデルの範囲外です。

  • SLAは、顧客サービスモデルに含まれるサービスの定義と重なる部分が多くあります。 たとえば、特定の帯域幅の要求が顧客サービスモデルに含まれることがあり、サービスを提供するという合意は、顧客サービスモデルにおけるサービスの記述に対する約束です。 しかし、SLAには通常、サービスがどのように、どの程度、どのくらいの頻度で変動してよいかについての細かな詳細が多く含まれます。 また、SLAは違約金などを伴う商業上の条件と結びついているため、やはり標準化に適したテーマではありません。 商業上の条件と同様に、一部のネットワーク運用者は、独自の取り組みによって、あるいはこのテーマを専門とする標準化団体の成果に依拠して、標準の顧客サービスモデルを拡張してSLAパラメーターを含めることが予想されますが、この機能はIETFの顧客サービスモデルの範囲外です。

    ネットワーク運用者がデータモデルを使ってSLAを表現することを選択した場合、そのモデルは顧客サービスモデルの拡張または補強として参照されることがあります。

6. Comparison with Other Work

6. 他の取り組みとの比較

Other work has classified YANG modules, produced parallel architectures, and developed a range of YANG modules. This section briefly examines that other work and shows how it fits with the description of service models introduced in this document.

他の取り組みでは、YANGモジュールを分類し、並行するアーキテクチャーを作成し、さまざまなYANGモジュールを開発してきました。 このセクションでは、そうした他の取り組みを簡単に検討し、それがこの文書で紹介したサービスモデルの説明とどのように整合するかを示します。

6.1. Comparison with Network Service Models

6.1. ネットワークサービスモデルとの比較

As previously noted, [RFC8199] provides a classification of YANG modules. It introduces the term "Network Service YANG Module" to identify the type of module used to "describe the configuration, state data, operations, and notifications of abstract representations of services implemented on one or multiple network elements." These modules are used to construct the service delivery models as described in this document; that is, they are the modules used on the interface between the service orchestrator or OSS/BSS and the network orchestrator, as shown in Figure 3.

前述のとおり、[RFC8199]はYANGモジュールの分類を示しています。 その文書は、「1つまたは複数のネットワーク要素上に実装されたサービスの抽象的な表現の設定、状態データ、操作、通知を記述する」ために使われるモジュールの種類を識別するために、「ネットワークサービスYANGモジュール（Network Service YANG Module）」という用語を導入しています。 これらのモジュールは、この文書で説明するサービス提供モデルを構築するために使われます。 つまり、図3に示すように、サービスオーケストレーターまたはOSS/BSSとネットワークオーケストレーターの間のインターフェイスで使われるモジュールです。

Figure 1 of [RFC8199] can be modified to make this more clear and to include an additional example of a Network Service YANG module, as shown in Figure 4. As can be seen, the highest classification of modules collects those that are used to deliver operations support and business support. These might be consumed by an Operations Support System (OSS) or a Business Support System (BSS), and a service orchestrator may form part of an OSS/BSS or may be a separate component. This highest layer in the figure is divided into the customer service modules that are used to describe services to a customer as discussed in this document, and other modules that describe further OSS/BSS functions such as billing and SLAs.

図4に示すように、[RFC8199]の図1を修正して、このことをより明確にし、ネットワークサービスYANGモジュールの例を追加できます。 図からわかるように、モジュールの最上位の分類には、オペレーションサポートとビジネスサポートを提供するために使われるモジュールが集められています。 これらは、オペレーションサポートシステム（OSS）やビジネスサポートシステム（BSS）によって利用されることがあり、サービスオーケストレーターはOSS/BSSの一部をなすこともあれば、別個のコンポーネントであることもあります。 図のこの最上位の層は、この文書で論じたように顧客にサービスを記述するために使われる顧客サービスモジュールと、課金やSLAなどのOSS/BSSのさらなる機能を記述するその他のモジュールとに分かれています。

6.2. Service Delivery and Network Element Model Work

6.2. サービス提供モデルとネットワーク要素モデルの取り組み

A number of IETF working groups are developing YANG modules related to services. These models focus on how the network operator configures the network through protocols and devices to deliver a service. Some of these models are classified as network service delivery models (also called service delivery models or network configuration models depending on the level at which they are pitched), while others have details that are related to specific element configuration and so are classed as network element models (also called device models).

IETFのいくつかのワーキンググループが、サービスに関連するYANGモジュールを開発しています。 これらのモデルは、ネットワーク運用者がサービスを提供するために、プロトコルやデバイスを通じてネットワークをどのように設定するかに焦点を当てています。 これらのモデルの一部は、ネットワークサービス提供モデル（対象とするレベルに応じて、サービス提供モデルやネットワーク設定モデルとも呼ばれます）に分類され、その他は特定の要素の設定に関連する詳細を持つため、ネットワーク要素モデル（デバイスモデルとも呼ばれます）に分類されます。

A sample set of these models is listed here:

これらのモデルの例を次に挙げます。

  • [BGP-L3VPN-YANG] defines a YANG module that can be used to configure and manage BGP L3VPNs.
  • [L2VPN-YANG] documents a data model that is expected to be used by the management tools run by the network operators in order to manage and monitor the network resources that they use to deliver L2VPN services.
  • [EVPN-YANG] defines YANG modules for delivering an Ethernet VPN service.
  • [BGP-L3VPN-YANG]は、BGP L3VPNの設定と管理に使用できるYANGモジュールを定義しています。
  • [L2VPN-YANG]は、ネットワーク運用者がL2VPNサービスの提供に使うネットワークリソースを管理し監視するために、ネットワーク運用者が実行する管理ツールで使われることが想定されているデータモデルを文書化しています。
  • [EVPN-YANG]は、イーサネットVPNサービスを提供するためのYANGモジュールを定義しています。

6.4. The MEF Architecture

6.4. MEFアーキテクチャー

The MEF Forum (MEF) has developed an architecture for network management and operation. It is documented as the Lifecycle Service Orchestration (LSO) Reference Architecture and is illustrated in Figure 2 of [MEF-55].

MEF Forum（MEF）は、ネットワークの管理と運用のためのアーキテクチャーを開発しています。 これは、ライフサイクルサービスオーケストレーション（Lifecycle Service Orchestration、LSO）参照アーキテクチャーとして文書化されており、[MEF-55]の図2に示されています。

The work of the MEF embraces all aspects of Lifecycle Service Orchestration, including billing, SLAs, order management, and lifecycle management. The IETF's work on service models is typically smaller and offers a simple, self-contained service YANG module. This does not invalidate either approach: it only observes that they are different approaches.

MEFの取り組みは、課金、SLA、注文管理、ライフサイクル管理を含む、ライフサイクルサービスオーケストレーションのあらゆる側面を網羅しています。 サービスモデルに関するIETFの取り組みは、一般にもっと小規模で、単純で自己完結型のサービスYANGモジュールを提供します。 これはどちらのアプローチを否定するものでもなく、両者が異なるアプローチであることを述べているにすぎません。

7. Further Concepts

7. さらなる概念

This section introduces a few further, more advanced concepts.

このセクションでは、さらに進んだ概念をいくつか紹介します。

7.1. Technology Agnostic

7.1. 技術非依存

Service models should generally be technology agnostic. That is to say, the customer should not care how the service is provided so long as the service is delivered.

サービスモデルは、一般に技術非依存であるべきです。 つまり、顧客は、サービスが提供される限り、そのサービスがどのように提供されるかを気にする必要はないはずです。

However, some technologies reach to the customer site and impact the type of service delivered. Such features do need to be described in the service model.

しかし、技術の中には顧客拠点にまで及び、提供されるサービスの種類に影響を与えるものもあります。 そのような特徴は、サービスモデルで記述する必要があります。

Two examples are as follows:

例を2つ挙げます。

  • The data passed between customer equipment and network operator equipment will be encapsulated in a specific way, and that data-plane type forms part of the service.
  • Protocols that are run between customer equipment and network operator equipment (for example, Operations, Administration, and Maintenance (OAM) protocols, protocols for discovery, or protocols for exchanging routing information) need to be selected and configured as part of the service description.
  • 顧客の機器とネットワーク運用者の機器の間で受け渡されるデータは特定の方法でカプセル化され、そのデータプレーンの種類はサービスの一部をなします。
  • 顧客の機器とネットワーク運用者の機器の間で実行されるプロトコル（たとえば、運用・管理・保守（Operations, Administration, and Maintenance、OAM）プロトコル、ディスカバリーのためのプロトコル、ルーティング情報を交換するためのプロトコル）は、サービスの記述の一部として選択し設定する必要があります。

7.2. Relationship to Policy

7.2. ポリシーとの関係

Policy appears as a crucial function in many places during network orchestration. A service orchestrator will, for example, apply the network operator's policies to determine how to provide a service for a particular customer (possibly considering commercial terms). However, the policies within a service model are limited to those over which a customer has direct influence and that are acted on by the network operator.

ポリシーは、ネットワークのオーケストレーションの多くの場面で重要な機能として現れます。 たとえば、サービスオーケストレーターは、特定の顧客に対してサービスをどのように提供するかを決定するために、（場合によっては商業上の条件を考慮して）ネットワーク運用者のポリシーを適用します。 しかし、サービスモデル内のポリシーは、顧客が直接影響を及ぼすことができ、かつネットワーク運用者が実行するものに限られます。

The policies that express desired behavior of services on occurrence of specific events are close to SLA definitions: they should only be included in the base service model where they are common offerings of all network operators. Policies that describe which person working for a customer may request or modify services (that is, authorization) are close to commercial terms: they, too, should only be included in the base service model where they are common offerings of all network operators.

特定のイベントが発生したときのサービスの望ましい振る舞いを表すポリシーは、SLAの定義に近いものです。 そのため、すべてのネットワーク運用者に共通する提供内容である場合にのみ、基本のサービスモデルに含めるべきです。 顧客側で働くどの人がサービスを要求または変更できるかを記述するポリシー（つまり認可）は、商業上の条件に近いものです。 そのため、これもすべてのネットワーク運用者に共通する提供内容である場合にのみ、基本のサービスモデルに含めるべきです。

As with commercial terms and SLAs discussed in Section 5, it is expected that some network operators will enhance standard customer service models to include policy parameters either using their own work or depending on specific policy models built in the IETF or other standards bodies.

セクション5で論じた商業上の条件やSLAと同様に、一部のネットワーク運用者は、独自の取り組みによって、あるいはIETFや他の標準化団体で作られた特定のポリシーモデルに依拠して、標準の顧客サービスモデルを拡張してポリシーパラメーターを含めることが予想されます。

Nevertheless, policy is so important that all service models should be designed to be easily extensible to allow policy components to be added and associated with services as needed.

とはいえ、ポリシーは非常に重要なので、すべてのサービスモデルは、必要に応じてポリシーのコンポーネントを追加しサービスに関連づけられるように、容易に拡張できるよう設計すべきです。

7.3. Operator-Specific Features

7.3. 運用者固有の機能

When work on the L3SM was started, there was some doubt as to whether network operators would be able to agree on a common description of the services that they offer to their customers because, in a competitive environment, each markets the services in a different way with different additional features. However, the working group was able to agree on a core set of features that multiple network operators were willing to consider as "common". They also understood that, should an individual network operator want to describe additional features (operator-specific features), they could do so by extending or augmenting the L3SM model.

L3SMの作業が始まったとき、競争環境の中で各社が異なる追加機能を付けて異なる方法でサービスを売り出しているため、ネットワーク運用者が顧客に提供するサービスの共通の記述について合意できるかどうか、いくらか疑問がありました。 しかし、ワーキンググループは、複数のネットワーク運用者が「共通」とみなすことに同意できる機能の中核セットについて合意できました。 また、個々のネットワーク運用者が追加機能（運用者固有の機能）を記述したい場合には、L3SMモデルを拡張または補強することでそれができることも理解されました。

Thus, when a basic description of a core service is agreed upon and documented in a service model, it is important that that model be easily extended or augmented by each network operator so that the standardized model can be used in a common way and only the operator-specific features be varied from one environment to another.

したがって、中核となるサービスの基本的な記述が合意されてサービスモデルに文書化されたときには、標準化されたモデルを共通の方法で使用し、運用者固有の機能だけを環境ごとに変えられるように、各ネットワーク運用者がそのモデルを容易に拡張または補強できることが重要です。

7.4. Supporting Multiple Services

7.4. 複数サービスのサポート

Network operators will, in general, offer many different services to their customers. Each would normally be the subject of a separate service model.

ネットワーク運用者は、一般に、さまざまなサービスを顧客に提供します。 通常、それぞれのサービスは別々のサービスモデルの対象となります。

Whether each service model is handled by a specialized service orchestrator that is able to provide tuned behavior for a specific service, or whether all service models are handled by a single service orchestrator, is an implementation and deployment choice.

各サービスモデルを、特定のサービス向けに調整された振る舞いを提供できる専用のサービスオーケストレーターで扱うか、すべてのサービスモデルを単一のサービスオーケストレーターで扱うかは、実装と展開の選択です。

It is expected that, over time, certain elements of the service models will be seen to repeat in each model. An example of such an element is the postal address of the customer.

時間が経つにつれて、サービスモデルの特定の要素が各モデルで繰り返し現れるようになることが予想されます。 そのような要素の例として、顧客の郵便住所があります。

It is anticipated that, while access to such information from each service model is important, the data will be described in its own module and may form part of the service model either by inclusion or by index.

各サービスモデルからそのような情報にアクセスできることは重要ですが、そのデータは独自のモジュールで記述され、インクルードまたはインデックスによってサービスモデルの一部をなすことになると予想されます。

8. Security Considerations

8. セキュリティーに関する考慮事項

The interface between customer and service provider is a commercial interface, and it needs to be subject to appropriate confidentiality. Additionally, knowledge of what services are provided to a customer or delivered by a network operator may supply information that can be used in a variety of security attacks. The service model itself will expose security-related parameters for the specific service where the related function is available to the customer.

顧客とサービスプロバイダーの間のインターフェイスは商業的なインターフェイスであり、適切な機密性が確保される必要があります。 加えて、どのようなサービスが顧客に提供されているか、あるいはネットワーク運用者によって提供されているかを知ることで、さまざまなセキュリティー攻撃に利用できる情報が得られる可能性があります。 サービスモデル自体は、関連する機能が顧客に利用可能である場合には、特定のサービスのセキュリティー関連パラメーターを公開することになります。

Clearly, the ability to modify information exchanges between customer and network operator may result in bogus requests, unwarranted billing, and false expectations. Furthermore, in an automated system, modifications to service requests or the injection of bogus requests may lead to attacks on the network and delivery of customer traffic to the wrong place.

明らかに、顧客とネットワーク運用者の間の情報交換を改ざんできると、偽の要求、不当な請求、誤った期待につながるおそれがあります。 さらに、自動化されたシステムでは、サービス要求の改ざんや偽の要求の注入によって、ネットワークへの攻撃や、顧客のトラフィックが誤った場所に配送されることにつながるおそれがあります。

Therefore, it is important that the protocol interface used to exchange service request information between customer and network operator is subject to authorization, authentication, and encryption. Clearly, the level of abstraction provided by a service model protects the operator from unwarranted visibility into their network, and additional protection is provided by the fact that how the service is delivered is entirely up to the operator.

したがって、顧客とネットワーク運用者の間でサービス要求情報を交換するために使われるプロトコルインターフェイスは、認可、認証、暗号化の対象となることが重要です。 明らかに、サービスモデルが提供する抽象化のレベルによって、運用者は自身のネットワークを不当に見られることから保護されます。 また、サービスをどのように提供するかが完全に運用者に委ねられていることによって、さらなる保護が得られます。

Equally, all external interfaces, such as any of those between the functional components in Figure 3, need to be correctly secured. This document discusses modeling the information, not how it is exchanged.

同様に、図3の機能コンポーネント間のインターフェイスなど、すべての外部インターフェイスは適切に保護される必要があります。 この文書は、情報のモデル化について論じるものであり、それがどのように交換されるかについて論じるものではありません。

9. Manageability Considerations

9. 管理性に関する考慮事項

This whole document discusses issues related to network management and control.

この文書全体が、ネットワークの管理と制御に関連する問題を論じています。

It is important to observe that automated service provisioning resulting from use of a customer service model may result in rapid and significant changes in traffic load within a network and that that might have an effect on other services carried in a network.

顧客サービスモデルの使用による自動化されたサービスのプロビジョニングは、ネットワーク内のトラフィック負荷に急速かつ大幅な変化をもたらす可能性があり、それがネットワークで運ばれる他のサービスに影響を及ぼすかもしれないことに留意することが重要です。

It is expected, therefore, that a service-orchestration component has awareness of other service commitments, that the network-orchestration component will not commit network resources to fulfill a service unless doing so is appropriate, and that a feedback loop will be provided to report on degradation of the network that will impact the service.

したがって、サービスオーケストレーションのコンポーネントは他のサービスの約束を把握していること、ネットワークオーケストレーションのコンポーネントは適切でない限りサービスを満たすためにネットワークリソースを割り当てないこと、そしてサービスに影響するネットワークの劣化を報告するためのフィードバックループが提供されることが期待されます。

The operational state of a service does not form part of a customer service model. However, it is likely that a network operator may want to report some state information about various components of the service and that could be achieved through extensions to the core service model, just as SLA extensions could be made as described in Section 5.

サービスの運用状態は、顧客サービスモデルの一部をなしません。 しかし、ネットワーク運用者は、サービスのさまざまなコンポーネントに関する何らかの状態情報を報告したいと考える可能性が高く、セクション5で説明したようにSLAの拡張を行えるのと同様に、中核のサービスモデルの拡張によってそれを実現できるでしょう。
