RFC 8426

Recommendations for RSVP-TE and Segment Routing (SR) Label Switched Path (LSP) Coexistence

RFC 8426

RSVP-TEとセグメントルーティング（SR）のラベルスイッチパス（LSP）の共存に関する推奨事項

Abstract

概要

Operators are looking to introduce services over Segment Routing (SR) Label Switched Paths (LSPs) in networks running Resource Reservation Protocol - Traffic Engineering (RSVP-TE) LSPs. In some instances, operators are also migrating existing services from RSVP-TE to SR LSPs. For example, there might be certain services that are well suited for SR and need to coexist with RSVP-TE in the same network. Such introduction or migration of traffic to SR might require coexistence with RSVP-TE in the same network for an extended period of time, depending on the operator's intent. The following document provides solution options for keeping the traffic engineering database consistent across the network, accounting for the different bandwidth utilization between SR and RSVP-TE.

運用者は、リソース予約プロトコル - トラフィックエンジニアリング（Resource Reservation Protocol - Traffic Engineering: RSVP-TE）のLSPを運用しているネットワークに、セグメントルーティング（SR）のラベルスイッチパス（LSP）上のサービスを導入しようとしています。 場合によっては、運用者は既存のサービスをRSVP-TEからSR LSPに移行することもあります。 たとえば、SRに適していて、同じネットワーク内でRSVP-TEと共存する必要がある特定のサービスが存在するかもしれません。 このようなSRへのトラフィックの導入や移行では、運用者の意図によっては、同じネットワーク内で長期間にわたってRSVP-TEと共存する必要があるかもしれません。 この文書は、SRとRSVP-TEの帯域幅使用量の違いを考慮しながら、トラフィックエンジニアリングデータベースをネットワーク全体で一貫した状態に保つための解決策の選択肢を示します。

1. Introduction

1. はじめに

Introduction of SR [RFC8402] in the same network domain as RSVP-TE [RFC3209] presents the problem of accounting for SR traffic and making RSVP-TE aware of the actual available bandwidth on the network links. RSVP-TE is not aware of how much bandwidth is being consumed by SR services on the network links; hence, both at computation time (for a distributed computation) and at signaling time, RSVP-TE LSPs will incorrectly place loads. This is true where RSVP-TE paths are distributed or centrally computed without a common entity managing both SR and RSVP-TE computation for the entire network domain.

RSVP-TE [RFC3209]と同じネットワークドメインにSR [RFC8402]を導入すると、SRトラフィックをどのように計上し、ネットワークリンク上で実際に利用可能な帯域幅をRSVP-TEにどのように認識させるかという問題が生じます。 RSVP-TEは、ネットワークリンク上でSRサービスがどれだけの帯域幅を消費しているかを認識していません。 そのため、（分散計算の場合の）計算時とシグナリング時の両方で、RSVP-TE LSPは負荷を誤って配置してしまいます。 これは、ネットワークドメイン全体についてSRとRSVP-TEの両方の計算を管理する共通のエンティティーがないまま、RSVP-TEのパスが分散計算または集中計算される場合に当てはまります。

The problem space can be generalized as a dark bandwidth problem to cases where any other service exists in the network that runs in parallel across common links and whose bandwidth is not reflected in the available and reserved values in the Traffic Engineering Database (TED). In most practical instances, given the static nature of the traffic demands, limiting the reservable bandwidth available to RSVP-TE has been an acceptable solution. However, in the case of SR traffic, there is assumed to be very dynamic traffic demands, and there is considerable risk associated with stranding capacity or overbooking service traffic resulting in traffic drops.

この問題領域は、共通のリンク上で並行して動作し、その帯域幅がトラフィックエンジニアリングデータベース（Traffic Engineering Database: TED）の利用可能値と予約済み値に反映されない何らかの別のサービスがネットワーク内に存在する場合を対象とした、ダーク帯域幅（dark bandwidth）問題として一般化できます。 実際のほとんどの場合では、トラフィック需要が静的な性質を持つことから、RSVP-TEが利用できる予約可能帯域幅を制限することが許容できる解決策となってきました。 しかし、SRトラフィックの場合、トラフィック需要は非常に動的であると想定されており、容量を遊休させてしまったり、サービストラフィックをオーバーブッキングしてトラフィックの廃棄を引き起こしたりする大きなリスクがあります。

The high-level requirements to consider are:

考慮すべき高レベルの要件は次のとおりです。

  1. Placement of SR LSPs in the same domain as RSVP-TE LSPs must not introduce inaccuracies in the TED used by distributed or centralized path computation engines.
  2. Engines that compute RSVP-TE paths may have no knowledge of the existence of the SR paths in the same domain.
  3. Engines that compute RSVP-TE paths should not require a software upgrade or change to their path-computation logic.
  4. Protocol extensions should be avoided or be minimal as, in many cases, this coexistence of RSVP-TE and SR may be needed only during a transition phase.
  5. Placement of SR LSPs in the same domain as RSVP-TE LSPs that are computed in a distributed fashion must not require migration to a central controller architecture for the RSVP-TE LSPs.
  1. RSVP-TE LSPと同じドメインにSR LSPを配置することで、分散型または集中型のパス計算エンジンが使用するTEDに不正確さを持ち込んではいけません。
  2. RSVP-TEのパスを計算するエンジンは、同じドメイン内のSRパスの存在をまったく認識していない場合があります。
  3. RSVP-TEのパスを計算するエンジンに、ソフトウェアのアップグレードやパス計算ロジックの変更を求めるべきではありません。
  4. 多くの場合、このRSVP-TEとSRの共存は移行段階の間だけ必要とされるものなので、プロトコル拡張は避けるか、最小限にすべきです。
  5. 分散方式で計算されるRSVP-TE LSPと同じドメインにSR LSPを配置する際に、RSVP-TE LSPについて中央コントローラーのアーキテクチャーへの移行を必要としてはいけません。

3. Solution Options

3. 解決策の選択肢

The following section lists SR and RSVP coexistence solution options. A specific solution is not recommended as all solutions are valid, even though some may not satisfy all the requirements. If a solution is acceptable for an operator based on their deployment model, then such a solution can be chosen.

以下のセクションでは、SRとRSVPの共存のための解決策の選択肢を列挙します。 すべての要件を満たさないものもありますが、どの解決策も有効であるため、特定の解決策を推奨することはしません。 運用者の展開モデルに照らしてある解決策が受け入れられるのであれば、その解決策を選択できます。

3.1. Static Partitioning of Bandwidth

3.1. 帯域幅の静的な分割

In this model, the static reservable bandwidth of an interface can be statically partitioned between SR and RSVP-TE; each one can operate within that bandwidth allocation and SHOULD NOT preempt the other.

このモデルでは、インターフェイスの静的な予約可能帯域幅をSRとRSVP-TEの間で静的に分割できます。 それぞれはその帯域幅の割り当ての範囲内で動作でき、相手をプリエンプトすべきではありません（SHOULD NOT）。

While it is possible to configure RSVP-TE to only reserve up to a certain maximum link bandwidth and manage the remaining link bandwidth for other services, this is a deployment where SR and RSVP-TE are separated in the same network (ships in the night) and can lead to suboptimal link bandwidth utilization not allowing each to consume more, if required and constraining the respective deployments.

RSVP-TEが特定の最大リンク帯域幅までしか予約しないように設定し、残りのリンク帯域幅を他のサービスのために管理することは可能ですが、これはSRとRSVP-TEが同じネットワーク内で分離された（互いに干渉しない「ships in the night」の）展開です。 この展開では、必要な場合でもそれぞれがそれ以上の帯域幅を消費できず、それぞれの展開が制約されるため、リンク帯域幅の使用率が最適でなくなる可能性があります。

The downside of this approach is the inability to use the reservable bandwidth effectively and the inability to use bandwidth left unused by the other protocol.

このアプローチの欠点は、予約可能帯域幅を効果的に使用できないことと、他方のプロトコルが使用していない帯域幅を使用できないことです。

3.2. Centralized Management of Available Capacity

3.2. 利用可能な容量の集中管理

In this model, a central controller performs path placement for both RSVP-TE and SR LSPs. The controller manages and updates its own view of the in-use and available capacity. As the controller is a single common entity managing the network it can have a unified and consistent view of the available capacity at all times.

このモデルでは、中央コントローラーがRSVP-TE LSPとSR LSPの両方のパス配置を行います。 コントローラーは、使用中の容量と利用可能な容量についての自身のビューを管理し、更新します。 コントローラーはネットワークを管理する単一の共通エンティティーであるため、利用可能な容量について常に統一された一貫性のあるビューを持つことができます。

A practical drawback of this model is that it requires the introduction of a central controller managing the RSVP-TE LSPs as a prerequisite to the deployment of any SR LSPs. Therefore, this approach is not practical for networks where distributed TE with RSVP-TE LSPs is already deployed, as it requires a redesign of the network and is not backwards compatible. This does not satisfy requirement 5.

このモデルの実際的な欠点は、SR LSPを展開する前提条件として、RSVP-TE LSPを管理する中央コントローラーの導入が必要になることです。 したがって、このアプローチは、RSVP-TE LSPによる分散型TEがすでに展開されているネットワークでは実用的ではありません。 ネットワークの再設計が必要になり、後方互換性がないためです。 これは要件5を満たしません。

Note that it is not enough for the controller to just maintain the unified view of the available capacity, it must also perform the path computation for the RSVP-TE LSPs, as the reservations for the SR LSPs are not reflected in the TED.

SR LSPの予約はTEDに反映されないため、コントローラーは利用可能な容量の統一されたビューを維持するだけでは不十分であり、RSVP-TE LSPのパス計算も行わなければならないことに注意してください。

3.3. Flooding SR Utilization in IGP

3.3. IGPでのSR使用量のフラッディング

Using techniques in [RFC7810], [RFC7471], and [RFC7823], the SR utilization information can be flooded in IGP-TE, and the RSVP-TE path computation engine (Constrained Shortest Path First (CSPF)) can be changed to consider this information. This requires changes to the RSVP-TE path computation logic and would require upgrades in deployments where distributed computation is done across the network.

[RFC7810]、[RFC7471]、[RFC7823]の技術を使えば、SRの使用量情報をIGP-TEでフラッディングでき、RSVP-TEのパス計算エンジン（制約付き最短パス優先（Constrained Shortest Path First: CSPF））をこの情報を考慮するように変更できます。 これにはRSVP-TEのパス計算ロジックの変更が必要であり、ネットワーク全体で分散計算を行っている展開ではアップグレードが必要になります。

This does not fit with requirements 3 and 4 mentioned earlier.

これは、前述の要件3と要件4に適合しません。

3.4. Running SR over RSVP-TE

3.4. RSVP-TE上でのSRの実行

SR can run over dedicated RSVP-TE LSPs that carry only SR traffic. In this model, the LSPs can be one-hop or multi-hop and can provide bandwidth reservation for the SR traffic based on functionality such as auto-bandwidth. The model of deployment would be similar in nature to running LDP over RSVP-TE. This would allow the TED to stay consistent across the network and any other RSVP-TE LSPs will also be aware of the SR traffic reservations. In this approach, non-SR traffic MUST NOT take the SR-dedicated RSVP-TE LSPs, unless required by policy.

SRは、SRトラフィックだけを運ぶ専用のRSVP-TE LSP上で実行できます。 このモデルでは、LSPはシングルホップでもマルチホップでもよく、自動帯域幅（auto-bandwidth）などの機能に基づいてSRトラフィックのための帯域幅予約を提供できます。 この展開モデルは、本質的にはRSVP-TE上でLDPを実行するのと同様のものです。 これにより、TEDはネットワーク全体で一貫した状態を保つことができ、他のRSVP-TE LSPもSRトラフィックの予約を認識できるようになります。 このアプローチでは、ポリシーで要求されない限り、SR以外のトラフィックがSR専用のRSVP-TE LSPを使用してはなりません（MUST NOT）。

The drawback of this solution is that it requires SR to rely on RSVP-TE for deployment. Furthermore, the accounting accuracy/frequency of this method is dependent on performance of auto-bandwidth for RSVP-TE. Note that, for this method to work, the SR-dedicated RSVP-TE LSPs must be set up with the best setup and hold priorities in the network.

この解決策の欠点は、SRの展開がRSVP-TEに依存しなければならないことです。 さらに、この方法による計上の精度や頻度は、RSVP-TEの自動帯域幅の性能に左右されます。 この方法を機能させるには、SR専用のRSVP-TE LSPを、ネットワーク内で最良のセットアップ優先度と保持優先度で確立しなければならないことに注意してください。

3.5. TED Consistency by Reflecting SR Traffic

3.5. SRトラフィックの反映によるTEDの一貫性

The solution relies on dynamically measuring SR traffic utilization on each TE interface and reducing the bandwidth allowed for use by RSVP-TE. It is assumed that SR traffic receives precedence in terms of the placement on the path over RSVP traffic (that is, RSVP traffic can be preempted from the path in case of insufficient resources). This is logically equivalent to SR traffic having the best preemption priority in the network. Note that this does not necessarily mean that SR traffic has higher QoS priority; in fact, SR and RSVP traffic may be in the same QoS class.

この解決策は、各TEインターフェイスでSRトラフィックの使用量を動的に測定し、RSVP-TEが使用できる帯域幅を減らすことに基づいています。 パス上への配置に関して、SRトラフィックはRSVPトラフィックよりも優先されると想定します（つまり、リソースが不足している場合、RSVPトラフィックはパスからプリエンプトされることがあります）。 これは論理的には、SRトラフィックがネットワーク内で最良のプリエンプション優先度を持つことと同等です。 これは必ずしもSRトラフィックがより高いQoS優先度を持つことを意味するわけではないことに注意してください。 実際、SRトラフィックとRSVPトラフィックは同じQoSクラスに属していてもかまいません。

Reducing the bandwidth allowed for use by RSVP-TE can be explored using the three parameters available in IGP-TE ([RFC5305] [RFC3630]), namely Maximum-Link-Bandwidth, Maximum-Reservable-Bandwidth, and Unreserved-Bandwidth.

RSVP-TEが使用できる帯域幅を減らす方法は、IGP-TE（[RFC5305] [RFC3630]）で利用できる3つのパラメーター、すなわちMaximum-Link-Bandwidth、Maximum-Reservable-Bandwidth、Unreserved-Bandwidthを使って検討できます。

  • Maximum-Link-Bandwidth: This parameter can be adjusted to accommodate the bandwidth required for SR traffic with cascading impacts on Maximum-Reservable-Bandwidth and Unreserved-Bandwidth. However, changing the maximum bandwidth for the TE link will prevent any compute engine for SR or RSVP from determining the real static bandwidth of the TE link. Further, when the Maximum-Reservable-Bandwidth is derived from the Maximum-Link-Bandwidth, its definition changes since Maximum-Link-Bandwidth will account for the SR traffic.
  • Unreserved-Bandwidth: SR traffic could directly adjust the Unreserved-Bandwidth, without impacting Maximum-Link-Bandwidth or Maximum-Reservable-Bandwidth. This model is equivalent to the option described in Section 3.4. Furthermore this would result in overloading IGP-TE advertisements to directly reflect both RSVP-TE bandwidth bookings and SR bandwidth measurements.
  • Maximum-Reservable-Bandwidth: As the preferred option, SR traffic could adjust the Maximum-Reservable-Bandwidth, with cascading impact on the Unreserved-Bandwidth.
  • Maximum-Link-Bandwidth（最大リンク帯域幅）：このパラメーターを調整してSRトラフィックに必要な帯域幅を差し引くことができ、その影響はMaximum-Reservable-BandwidthとUnreserved-Bandwidthに連鎖的に及びます。 しかし、TEリンクの最大帯域幅を変更すると、SRやRSVPのどの計算エンジンもTEリンクの実際の静的な帯域幅を判断できなくなります。 さらに、Maximum-Reservable-BandwidthがMaximum-Link-Bandwidthから導出される場合、Maximum-Link-BandwidthがSRトラフィックを計上することになるため、Maximum-Reservable-Bandwidthの定義が変わってしまいます。
  • Unreserved-Bandwidth（未予約帯域幅）：Maximum-Link-BandwidthやMaximum-Reservable-Bandwidthに影響を与えずに、SRトラフィックがUnreserved-Bandwidthを直接調整することもできます。 このモデルは、セクション3.4で説明した選択肢と同等です。 さらに、これはIGP-TEの広告に、RSVP-TEの帯域幅予約とSRの帯域幅測定値の両方を直接反映させるという多重の意味を持たせることになります。
  • Maximum-Reservable-Bandwidth（最大予約可能帯域幅）：推奨される選択肢として、SRトラフィックがMaximum-Reservable-Bandwidthを調整し、その影響がUnreserved-Bandwidthに連鎖的に及ぶようにすることができます。

The following methodology can be used at every TE node for this solution, using the following parameters:

この解決策では、すべてのTEノードで、次のパラメーターを使った以下の方法を使用できます。

  • T: Traffic statistics collection time interval.
  • k: The number of traffic statistics samples that can provide a smoothing function to the statistics collection. The value of k is a constant integer multiplier greater or equal to 1.
  • N: Traffic averaging calculation (adjustment) interval such that N = k * T.
  • Maximum-Reservable-Bandwidth: The maximum available bandwidth for RSVP-TE.
  • If Diffserv-aware MPLS Traffic Engineering (DS-TE) [RFC4124] is enabled, the Maximum-Reservable-Bandwidth SHOULD be interpreted as the aggregate bandwidth constraint across all Class-Types independent of the Bandwidth Constraints model.
  • Initial Maximum-Reservable-Bandwidth: The Maximum-reservable-bandwidth for TE when no SR traffic or RSVP-TE reservations exist on the interface.
  • RSVP-unreserved-bandwidth-at-priority-X: Maximum-Reservable-Bandwidth - sum of (existing reservations at priority X and all priorities better than X).
  • SR traffic threshold percentage: The percentage difference of traffic demand that, when exceeded, can result in a change to the RSVP-TE Maximum-Reservable-Bandwidth.
  • IGP-TE update threshold: Specifies the frequency at which IGP-TE updates should be triggered based on TE bandwidth updates on a link.
  • M: An optional multiplier that can be applied to the SR traffic average. This multiplier provides the ability to grow or shrink the bandwidth used by SR. Appendix A offers further guidance on M.
  • T：トラフィック統計情報を収集する時間間隔。
  • k：統計情報の収集に平滑化の効果をもたらすトラフィック統計情報のサンプル数。 kの値は1以上の定数の整数乗数です。
  • N：トラフィックの平均を計算（調整）する間隔で、N = k * T となるもの。
  • Maximum-Reservable-Bandwidth：RSVP-TEが利用できる最大の帯域幅。
  • DiffServ対応MPLSトラフィックエンジニアリング（Diffserv-aware MPLS Traffic Engineering: DS-TE）[RFC4124]が有効な場合、Maximum-Reservable-Bandwidthは、帯域幅制約モデル（Bandwidth Constraints model）にかかわらず、すべてのクラス種別（Class-Type）にわたる帯域幅制約の総計として解釈されるべきです（SHOULD）。
  • Initial Maximum-Reservable-Bandwidth（初期最大予約可能帯域幅）：インターフェイス上にSRトラフィックもRSVP-TEの予約も存在しないときの、TEのMaximum-reservable-bandwidth。
  • RSVP-unreserved-bandwidth-at-priority-X（優先度XにおけるRSVPの未予約帯域幅）：Maximum-Reservable-Bandwidth - （優先度X、およびXよりも良いすべての優先度における既存の予約の合計）。
  • SRトラフィックしきい値パーセンテージ（SR traffic threshold percentage）：トラフィック需要の差のパーセンテージで、これを超えるとRSVP-TEのMaximum-Reservable-Bandwidthが変更されることがあるもの。
  • IGP-TE更新しきい値（IGP-TE update threshold）：リンク上のTE帯域幅の更新に基づいてIGP-TEの更新をトリガーする頻度を指定します。
  • M：SRトラフィックの平均に適用できる任意の乗数。 この乗数により、SRが使用する帯域幅を増やしたり減らしたりできます。 Mについての詳しいガイダンスは付録Aにあります。

At every interval T, each node SHOULD collect the SR traffic statistics for each of its TE interfaces. The measured SR traffic includes all labeled SR traffic and any traffic entering the SR network over that TE interface. Further, at every interval N, given a configured SR traffic threshold percentage and a set of collected SR traffic statistics samples across the interval N, the SR traffic average (or any other traffic metric depending on the algorithm used) over this period is calculated. This method of sampling traffic statistics and adjusting bandwidth reservation accordingly is similar to how bandwidth gets adjusted for auto-bandwidth RSVP-TE LSPs.

各ノードは、間隔Tごとに、自身の各TEインターフェイスについてSRトラフィックの統計情報を収集すべきです（SHOULD）。 測定するSRトラフィックには、ラベル付けされたすべてのSRトラフィックと、そのTEインターフェイスを経由してSRネットワークに入るすべてのトラフィックが含まれます。 さらに、間隔Nごとに、設定されたSRトラフィックしきい値パーセンテージと、間隔Nにわたって収集したSRトラフィック統計情報のサンプルの集合に基づいて、この期間のSRトラフィックの平均（または、使用するアルゴリズムに応じた他のトラフィックメトリック）を計算します。 トラフィック統計情報をサンプリングし、それに応じて帯域幅予約を調整するこの方法は、自動帯域幅を使用するRSVP-TE LSPで帯域幅を調整する方法と同様のものです。

If the difference between the new calculated SR traffic average and the current SR traffic average (that was computed in the prior adjustment) is at least SR traffic threshold percentage, then two values MUST be updated:

新しく計算したSRトラフィックの平均と、（前回の調整で計算した）現在のSRトラフィックの平均との差が、SRトラフィックしきい値パーセンテージ以上である場合、次の2つの値を更新しなければなりません（MUST）。

  • New Maximum-Reservable-Bandwidth = Initial Maximum-Reservable-Bandwidth - (new SR traffic average * M)
  • New RSVP-unreserved-bandwidth-at-priority-X = New Maximum-Reservable-Bandwidth - sum of (existing reservations at priority X and all priorities better than X)
  • 新しいMaximum-Reservable-Bandwidth = Initial Maximum-Reservable-Bandwidth - （新しいSRトラフィックの平均 * M）
  • 新しいRSVP-unreserved-bandwidth-at-priority-X = 新しいMaximum-Reservable-Bandwidth - （優先度X、およびXよりも良いすべての優先度における既存の予約の合計）

A DS-TE LSR that advertises a Bandwidth Constraints TLV should update the bandwidth constraints for class-types based on operator policy. For example, when Russian Dolls Model (RDM) [RFC4127] is in use, then only BC0 may be updated. Whereas, when Maximum Allocation Model (MAM) [RFC4125] is in use, then all Bandwidth Constraints (BCs) may be updated equally such that the total value updated is equal to the newly calculated SR traffic average.

帯域幅制約（Bandwidth Constraints）TLVを広告するDS-TE LSRは、運用者のポリシーに基づいてクラス種別ごとの帯域幅制約を更新すべきです。 たとえば、ロシア人形モデル（Russian Dolls Model: RDM）[RFC4127]を使用している場合は、BC0だけを更新することがあります。 一方、最大割り当てモデル（Maximum Allocation Model: MAM）[RFC4125]を使用している場合は、更新される値の合計が新しく計算したSRトラフィックの平均と等しくなるように、すべての帯域幅制約（BC）を均等に更新することがあります。

Note that the computation of the new RSVP-unreserved-bandwidth-at-priority-X MAY result in RSVP-TE LSPs being hard or soft preempted. Such preemption will be based on relative priority (e.g., low to high) between RSVP-TE LSPs. The IGP-TE update threshold SHOULD allow for more frequent flooding of unreserved bandwidth. From an operational point of view, an implementation SHOULD be able to expose both the configured and the actual values of the Maximum-Reservable-Bandwidth.

注意点として、新しいRSVP-unreserved-bandwidth-at-priority-Xを計算した結果、RSVP-TE LSPがハードプリエンプションまたはソフトプリエンプションされる場合があります（MAY）。 このようなプリエンプションは、RSVP-TE LSP間の相対的な優先度（たとえば、低いものから高いものへ）に基づいて行われます。 IGP-TE更新しきい値は、未予約帯域幅をより頻繁にフラッディングできるようにするべきです（SHOULD）。 運用の観点からは、実装はMaximum-Reservable-Bandwidthの設定値と実際の値の両方を公開できるべきです（SHOULD）。

If LSP preemption is not acceptable, then the RSVP-TE Maximum-Reservable-Bandwidth cannot be reduced below what is currently reserved by RSVP-TE on that interface. This may result in bandwidth not being available for SR traffic. Thus, it is required that any external controller managing SR LSPs SHOULD be able to detect this situation (for example, by subscribing to TED updates [RFC7752]) and SHOULD take action to reroute existing SR paths.

LSPのプリエンプションが許容できない場合、RSVP-TEのMaximum-Reservable-Bandwidthは、そのインターフェイス上でRSVP-TEが現在予約している量よりも小さくすることはできません。 その結果、SRトラフィックが利用できる帯域幅がなくなる場合があります。 したがって、SR LSPを管理する外部コントローラーは、（たとえば、TEDの更新を購読する[RFC7752]ことによって）この状況を検出できるべきです（SHOULD）。 また、既存のSRパスを再ルーティングする措置を講じるべきです（SHOULD）。

Generically, SR traffic (or any non-RSVP-TE traffic) should have its own priority allocated from the available priorities. This would allow SR to preempt other traffic according to the preemption priority order.

一般に、SRトラフィック（またはRSVP-TE以外のトラフィック）には、利用可能な優先度の中から専用の優先度を割り当てるべきです。 これにより、SRはプリエンプション優先度の順序に従って他のトラフィックをプリエンプトできるようになります。

In this solution, the logic to retrieve the statistics, calculating averages and taking action to change the Maximum-Reservable-Bandwidth is an implementation choice, and all changes are local in nature. However, note that this is a new network trigger for RSVP-TE preemption and thus is a consideration for the operator.

この解決策では、統計情報の取得、平均の計算、Maximum-Reservable-Bandwidthを変更する措置のロジックは実装上の選択であり、すべての変更は本質的にローカルなものです。 ただし、これはRSVP-TEのプリエンプションを引き起こす新たなネットワーク上の契機となるため、運用者が考慮すべき事項であることに注意してください。

The above solution offers the advantage of not introducing new network-wide mechanisms especially during scenarios of migrating to SR in an existing RSVP-TE network and reusing existing protocol mechanisms.

上記の解決策には、特に既存のRSVP-TEネットワークでSRに移行するシナリオにおいて、ネットワーク全体に及ぶ新たなメカニズムを導入せず、既存のプロトコルメカニズムを再利用できるという利点があります。

5. Security Considerations

5. セキュリティーに関する考慮事項

This document describes solution options for the coexistence of RSVP-TE and SR LSPs in the same administrative domain. The security considerations for SR are described in [RFC8402]. The security considerations pertaining to RSVP-TE are described in [RFC5920]. The security considerations of each architecture are typically unaffected by the presence of the other. However, when RSVP-TE and SR LSPs coexist, it is possible for a hijacked SR traffic stream to maliciously consume sufficient bandwidth and cause disruption to RSVP-TE LSPs. With the solution option specified in Section 3.5, the impact to RSVP-TE traffic can be controlled and paths re-routed. Some latent risk of disruption still remains because this solution option relies on taking statistics samples and adopting to new traffic flows only after the adjustment period. The defensive mechanisms described in the base SR security framework should be employed to guard against situations that result in SR traffic hijacking or denial of service.

この文書は、同じ管理ドメイン内でのRSVP-TE LSPとSR LSPの共存のための解決策の選択肢を説明します。 SRのセキュリティーに関する考慮事項は[RFC8402]に記載されています。 RSVP-TEに関するセキュリティーの考慮事項は[RFC5920]に記載されています。 通常、それぞれのアーキテクチャーのセキュリティーに関する考慮事項は、もう一方が存在しても影響を受けません。 しかし、RSVP-TE LSPとSR LSPが共存する場合、乗っ取られたSRトラフィックストリームが悪意を持って十分な帯域幅を消費し、RSVP-TE LSPを妨害する可能性があります。 セクション3.5で規定した解決策の選択肢を使えば、RSVP-TEトラフィックへの影響を制御し、パスを再ルーティングできます。 ただし、この解決策の選択肢は統計情報のサンプルを取得し、調整期間が過ぎてから新しいトラフィックフローに適応する方式であるため、妨害の潜在的なリスクは依然として残ります。 SRトラフィックの乗っ取りやサービス拒否につながる状況を防ぐために、基本となるSRのセキュリティーフレームワークで説明されている防御メカニズムを採用すべきです。

Appendix A. Multiplier Value Range

付録A. 乗数の値の範囲

The following is a suggestion for the range of values for M:

Mの値の範囲について、次のように提案します。

M is a per-node positive real number that ranges from 0 to 2 with a default of 1 and may be expressed as a percentage.

Mはノードごとの正の実数で、0から2の範囲をとり、デフォルトは1です。 パーセンテージで表すこともできます。

  • If M < 1, then the SR traffic average is being understated, which can result in the link getting full even though Maximum-Reservable-Bandwidth does not reach zero.
  • If M > 1, then the SR traffic average is overstated, thereby resulting in the Maximum-Reservable-Bandwidth reaching zero before the link gets full. If the reduction of Maximum-Reservable-Bandwidth becomes a negative value, then a value of zero SHOULD be used and advertised.
  • M < 1 の場合、SRトラフィックの平均は過小に見積もられます。 その結果、Maximum-Reservable-Bandwidthがゼロに達していなくても、リンクが満杯になることがあります。
  • M > 1 の場合、SRトラフィックの平均は過大に見積もられます。 その結果、リンクが満杯になる前にMaximum-Reservable-Bandwidthがゼロに達します。 Maximum-Reservable-Bandwidthを減らした結果が負の値になる場合は、ゼロの値を使用し、広告すべきです（SHOULD）。
