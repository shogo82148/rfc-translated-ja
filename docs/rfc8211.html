RFC 8211

Adverse Actions by a Certification Authority (CA) or Repository Manager in the Resource Public Key Infrastructure (RPKI)

RFC 8211

リソース公開鍵基盤（RPKI）における認証局（CA）またはリポジトリー管理者による不利益な行為

Abstract

概要

This document analyzes actions by or against a Certification Authority (CA) or an independent repository manager in the RPKI that can adversely affect the Internet Number Resources (INRs) associated with that CA or its subordinate CAs. The analysis is done from the perspective of an affected INR holder. The analysis is based on examination of the data items in the RPKI repository, as controlled by a CA (or an independent repository manager) and fetched by Relying Parties (RPs). The analysis does not purport to be comprehensive; it does represent an orderly way to analyze a number of ways that errors by or attacks against a CA or repository manager can affect the RPKI and routing decisions based on RPKI data.

この文書は、RPKIにおける認証局（CA）または独立したリポジトリー管理者による行為、またはそれらに対する行為のうち、そのCAやその下位CAに関連付けられたインターネット番号リソース（INR）に不利益な影響を与えうるものを分析します。 分析は、影響を受けるINR保有者の観点から行います。 分析は、CA（または独立したリポジトリー管理者）によって管理され、依拠当事者（RP）によって取得される、RPKIリポジトリー内のデータ項目の調査に基づいています。 この分析は網羅的であることを意図していませんが、CAまたはリポジトリー管理者による誤りやそれらに対する攻撃が、RPKIや、RPKIデータに基づくルーティングの決定に影響を与えうるさまざまな方法を、体系的に分析する方法を示すものです。

1. Introduction

1. はじめに

In the context of this document, any change to the Resource Public Key Infrastructure (RPKI) [RFC6480] that diminishes the set of Internet Number Resources (INRs) associated with an INR holder, and that is contrary to the holder's wishes, is termed "adverse". This analysis is done from the perspective of an affected INR holder. An action that results in an adverse charge (as defined above) may be the result of an attack on a CA [RFC7132], an error by a CA, or an error by or an attack on a repository operator. Note that the CA that allocated the affected INRs may be acting in accordance with established policy; thus, the change may be contractually justified even though viewed as adverse by the INR holder. This document examines the implications of adverse actions within the RPKI with respect to INRs, irrespective of the cause of the actions.

この文書の文脈では、リソース公開鍵基盤（RPKI）[RFC6480]に対する変更のうち、INR保有者に関連付けられたインターネット番号リソース（INR）の集合を縮小させ、かつ保有者の意思に反するものを「不利益な（adverse）」変更と呼びます。 この分析は、影響を受けるINR保有者の観点から行います。 （上で定義した）不利益な変更（charge）をもたらす行為は、CAに対する攻撃[RFC7132]、CAによる誤り、リポジトリー運用者による誤りまたはリポジトリー運用者に対する攻撃の結果である可能性があります。 影響を受けるINRを割り当てたCAは、確立されたポリシーに従って行動している場合もあることに注意してください。 したがって、INR保有者からは不利益と見なされるとしても、その変更は契約上正当である場合があります。 この文書は、行為の原因にかかわらず、INRに関してRPKI内での不利益な行為が持つ意味を検討します。

Additionally, when a Route Origin Authorization (ROA) or router certificate is created that "competes" with an existing ROA or router certificate (respectively), the creation of the new ROA or router certificate may be adverse. (A newer ROA competes with an older ROA if the newer ROA points to a different Autonomous System Number (ASN), contains the same or a more specific prefix, and is issued by a different CA. A newer router certificate competes with an older router certificate if the newer one contains the same ASN, contains a different public key, and is issued by a different CA.) Note that transferring resources or changing of upstream providers may yield competing ROAs and/or router certificates under some circumstances. Thus, not all instances of competition are adverse actions.

さらに、既存のROAまたはルーター証明書と（それぞれ）「競合する」経路生成元認可（ROA）またはルーター証明書が作成された場合、新しいROAまたはルーター証明書の作成は不利益なものとなる場合があります。 （新しいROAが別の自律システム番号（ASN）を指し、同じかより具体的なプレフィックスを含み、別のCAによって発行されている場合、その新しいROAは古いROAと競合します。 新しいルーター証明書が同じASNを含み、別の公開鍵を含み、別のCAによって発行されている場合、その新しいルーター証明書は古いルーター証明書と競合します。） リソースの移転や上流プロバイダーの変更によって、状況によっては競合するROAやルーター証明書が生じる場合があることに注意してください。 したがって、競合のすべての事例が不利益な行為であるわけではありません。

As noted above, adverse changes to RPKI data may arise due to several types of causes. A CA may make a mistake in managing the RPKI objects it signs, or it may be subject to an attack. If an attack allows an adversary to use the private key of that CA to sign RPKI objects, then the effect is analogous to the CA making mistakes. There is also the possibility that a CA or repository operator may be subject to legal measures that compel them to make adverse changes to RPKI data. In many cases, such actions may be hard to distinguish from mistakes or attacks, other than with respect to the time required to remedy the adverse action. (Presumably, the CA will take remedial action when a mistake or an attack is detected, so the effects are similar in these cases. If a CA has been legally compelled to effect an adverse change, remediation will likely not be swift.)

上で述べたように、RPKIデータに対する不利益な変更は、いくつかの種類の原因によって生じる場合があります。 CAは、自身が署名するRPKIオブジェクトの管理を誤る場合もあれば、攻撃を受ける場合もあります。 攻撃によって敵対者がそのCAの秘密鍵を使ってRPKIオブジェクトに署名できるようになった場合、その影響はCAが誤りを犯す場合と同様です。 また、CAやリポジトリー運用者が、RPKIデータに不利益な変更を加えることを強制する法的措置の対象となる可能性もあります。 多くの場合、そのような行為は、不利益な行為を是正するのに要する時間の点を除けば、誤りや攻撃と区別するのが難しいことがあります。 （おそらく、CAは誤りや攻撃を検出したときに是正措置を講じるので、これらの場合の影響は似たものになります。 CAが法的に不利益な変更を行うよう強制された場合には、是正はおそらく迅速には行われないでしょう。）

This document analyzes the various types of actions by a CA (or an independent repository operator) that can adversely affect the INRs associated with that CA, as well as the INRs of subordinate CAs. The analysis is based on examination of the data items in the RPKI repository, as controlled by a CA (or an independent repository operator) and fetched by RPs.

この文書は、CA（または独立したリポジトリー運用者）による行為のうち、そのCAに関連付けられたINRや下位CAのINRに不利益な影響を与えうるさまざまな種類の行為を分析します。 分析は、CA（または独立したリポジトリー運用者）によって管理され、RPによって取得される、RPKIリポジトリー内のデータ項目の調査に基づいています。

2. Analysis of RPKI Repository Objects

2. RPKIリポジトリーオブジェクトの分析

This section enumerates the RPKI repository system objects and examines how changes to them affect Route Origin Authorizations (ROAs) and router certificate validation. Identifiers are assigned to errors for reference by later sections of this document. Note that not all adverse actions may be encompassed by this taxonomy.

このセクションでは、RPKIリポジトリーシステムのオブジェクトを列挙し、それらに対する変更が経路生成元認可（ROA）やルーター証明書の検証にどのように影響するかを検討します。 この文書の後のセクションから参照できるように、誤りには識別子を割り当てます。 すべての不利益な行為がこの分類に含まれるとは限らないことに注意してください。

The RPKI repository [RFC6481] contains a number of (digitally signed) objects that are fetched and processed by RPs. Until the deployment of BGPsec [RFC8205], the principal goal of the RPKI is to enable an RP to validate ROAs [RFC6482]. A ROA binds address space to an ASN. A ROA can be used to verify BGP announcements with respect to route origin [RFC6483]. The most important objects in the RPKI for origin validation are ROAs; all of the other RPKI objects exist to enable the validation of ROAs in a fashion consistent with the INR allocation system. Thus, errors that result in changes to a ROA, or to RPKI objects needed to validate a ROA, can cause RPs to reach different (from what was intended) conclusions about the validity of the bindings expressed in a ROA.

RPKIリポジトリー[RFC6481]には、RPによって取得され処理される多数の（デジタル署名された）オブジェクトが含まれます。 BGPsec[RFC8205]が展開されるまでは、RPKIの主な目的は、RPがROA[RFC6482]を検証できるようにすることです。 ROAはアドレス空間をASNにバインドします。 ROAは、経路生成元に関してBGPアナウンスを検証するために使用できます[RFC6483]。 オリジン検証にとってRPKIで最も重要なオブジェクトはROAです。 ほかのRPKIオブジェクトはすべて、INR割り当て体系と整合する方法でROAを検証できるようにするために存在します。 したがって、ROAや、ROAの検証に必要なRPKIオブジェクトの変更をもたらす誤りは、ROAで表現されたバインディングの有効性について、RPに（意図されたものとは）異なる結論を下させる可能性があります。

When BGPsec is deployed, router certificates [RFC8209] will be added to repository publication points. These are end entity (EE) certificates used to verify signatures applied to BGP update data and to enable path validation [RFC8205]. Router certificates are as important to path validation as ROAs are to origin validation.

BGPsecが展開されると、ルーター証明書[RFC8209]がリポジトリーの公開ポイントに追加されます。 これは、BGP updateデータに付与された署名を検証し、パス検証[RFC8205]を可能にするために使用されるエンドエンティティー（EE）証明書です。 ROAがオリジン検証にとって重要であるのと同様に、ルーター証明書はパス検証にとって重要です。

The objects contained in the RPKI repository are of two types: conventional PKI objects (certificates and Certificate Revocation Lists (CRLs)) and RPKI-specific signed objects. The latter make use of a common encapsulation format [RFC6488] based on the Cryptographic Message Syntax (CMS) [RFC5652]. A syntax error in this common format will cause an RP to reject the object, e.g., a ROA or manifest, as invalid.

RPKIリポジトリーに含まれるオブジェクトには2つの種類があります。 従来のPKIオブジェクト（証明書と証明書失効リスト（CRL））と、RPKI固有の署名付きオブジェクトです。 後者は、暗号メッセージ構文（CMS）[RFC5652]に基づく共通のカプセル化形式[RFC6488]を使用します。 この共通形式に構文エラーがあると、RPはそのオブジェクト（ROAやマニフェストなど）を無効として拒否します。

Adverse actions take several forms:

不利益な行為にはいくつかの形態があります。

  • Deletion (D) is defined as removing an object from a publication point, without the permission of the INR holder.
  • Suppression (S) is defined as not deleting an object, or not publishing an object, as intended by an INR holder. This action also includes retaining a prior version of an object in a publication point when a newer version is available for publication.
  • Corruption (C) is defined as modification of a signed object in a fashion not requiring access to the private key used to sign the object. Thus, a corrupted object will not carry a valid signature. Implicitly, the corrupted object replaces the legitimate version.
  • Modification (M) is defined as publishing a syntactically valid, verifiable version of an object that differs from the (existing) version authorized by the INR holder. Implicitly, the legitimate version of the affected object is deleted and replaced by the modified object.
  • Revocation (R) is defined as revoking a certificate (EE or CA) by placing its Serial Number on the appropriate CRL, without authorization of the INR holder.
  • Injection (I) is defined as introducing an instance of a signed object into a publication point (without authorization of the INR holder). It assumes that the signature on the object will be viewed as valid by RPs.
  • 削除（Deletion、D）は、INR保有者の許可なく、公開ポイントからオブジェクトを取り除くことと定義します。
  • 抑止（Suppression、S）は、INR保有者が意図したオブジェクトの削除または公開を行わないことと定義します。 この行為には、より新しい版が公開可能になっているときに、以前の版のオブジェクトを公開ポイントに残しておくことも含まれます。
  • 破損（Corruption、C）は、署名付きオブジェクトを、そのオブジェクトの署名に使われた秘密鍵へのアクセスを必要としない方法で改変することと定義します。 したがって、破損したオブジェクトは有効な署名を持ちません。 暗黙のうちに、破損したオブジェクトは正当な版を置き換えます。
  • 改変（Modification、M）は、INR保有者によって認可された（既存の）版とは異なる、構文的に有効で検証可能な版のオブジェクトを公開することと定義します。 暗黙のうちに、影響を受けるオブジェクトの正当な版は削除され、改変されたオブジェクトに置き換えられます。
  • 失効（Revocation、R）は、INR保有者の認可なく、証明書（EEまたはCA）のシリアル番号を適切なCRLに載せることによって、その証明書を失効させることと定義します。
  • 注入（Injection、I）は、（INR保有者の認可なく）署名付きオブジェクトのインスタンスを公開ポイントに導入することと定義します。 これは、そのオブジェクトの署名がRPによって有効と見なされることを前提とします。

The first three of these actions (deletion, suppression, and corruption) can be effected by any entity that manages the publication point of the affected INR holder. Also, an entity with the ability to act as a man-in-the-middle between an RP and a repository can effect these actions with respect to the RP in question.

これらの行為のうち最初の3つ（削除、抑止、破損）は、影響を受けるINR保有者の公開ポイントを管理するどのエンティティーによっても実行できます。 また、RPとリポジトリーの間で中間者として振る舞う能力を持つエンティティーは、そのRPに関してこれらの行為を実行できます。

The latter three actions (modification, revocation, and injection) nominally require access to the private key of the INR holder.

後の3つの行為（改変、失効、注入）には、名目上、INR保有者の秘密鍵へのアクセスが必要です。

All six of these actions also can be effected by a parent CA. A parent CA could reissue the INR holder's CA certificate, but with a different public key, matching a private key to which the parent CA has access. The CA could generate new signed objects using the private key associated with the reissued certificate and publish these objects at a location of its choosing.

これら6つの行為はすべて、親CAによっても実行できます。 親CAは、INR保有者のCA証明書を、親CAがアクセスできる秘密鍵に対応する別の公開鍵で再発行できます。 そのCAは、再発行した証明書に関連付けられた秘密鍵を使って新しい署名付きオブジェクトを生成し、それらのオブジェクトを自分が選んだ場所に公開できます。

Most of these actions may be performed independently or in combination with one another. For example, a ROA may be revoked and deleted or revoked and replaced with a modified ROA. Where appropriate, the analysis of adverse actions will distinguish between individual actions, or combinations thereof, that yield different outcomes for RPs. Recall that the focus of the analysis is the impact on ROAs and router certificates, with respect to RP processing.

これらの行為のほとんどは、単独で実行することも、互いに組み合わせて実行することもできます。 たとえば、ROAが失効させられて削除される場合や、失効させられて改変されたROAに置き換えられる場合があります。 不利益な行為の分析では、必要に応じて、RPにとって異なる結果をもたらす個々の行為やその組み合わせを区別します。 分析の焦点は、RPの処理に関する、ROAとルーター証明書への影響であることを思い出してください。

The following sections examine how the actions enumerated above affect objects in the RPKI repository system. Each action is addressed in order (deletion, suppression, corruption, modification, revocation, and injection) for each object, making it easy to see how each action has been considered with regard to each object. (For the Ghostbusters Record [RFC6493], we condensed the discussion of the actions because the impact is the same in each case.)

以下のセクションでは、上で列挙した行為がRPKIリポジトリーシステム内のオブジェクトにどのように影響するかを検討します。 各オブジェクトについて、各行為を順番に（削除、抑止、破損、改変、失効、注入）取り上げるので、各オブジェクトに関して各行為がどのように検討されたかが容易にわかります。 （Ghostbustersレコード[RFC6493]については、影響がどの場合も同じであるため、行為についての議論をまとめました。）

2.1. CA Certificates

2.1. CA証明書

Every INR holder is represented by one or more CA certificates. An INR holder has multiple CA certificates if it holds resources acquired from different sources. Also, every INR holder has more than one CA certificate during key rollover [RFC6489] and algorithm rollover [RFC6916].

すべてのINR保有者は、1つ以上のCA証明書によって表されます。 INR保有者が異なる入手元から取得したリソースを保有している場合、そのINR保有者は複数のCA証明書を持ちます。 また、すべてのINR保有者は、鍵ロールオーバー[RFC6489]やアルゴリズムロールオーバー[RFC6916]の間は複数のCA証明書を持ちます。

If a publication point is not a "leaf" in the RPKI hierarchy, then the publication point will contain one or more CA certificates, each representing a subordinate CA. Each subordinate CA certificate contains a Subject Information Access (SIA) pointer to the publication point where the signed objects associated with that CA can be found [RFC6487].

公開ポイントがRPKI階層における「葉（leaf）」でない場合、その公開ポイントには1つ以上のCA証明書が含まれ、それぞれが下位CAを表します。 各下位CA証明書には、そのCAに関連付けられた署名付きオブジェクトが見つかる公開ポイントを指すサブジェクト情報アクセス（SIA）ポインターが含まれます[RFC6487]。

A CA certificate is a complex data structure; thus, errors in that structure may have different implications for RPs depending on the specific data that is in error.

CA証明書は複雑なデータ構造です。 したがって、その構造内の誤りは、誤っている具体的なデータに応じて、RPにとって異なる意味を持つ場合があります。

Adverse actions against a CA certificate can cause the following errors:

CA証明書に対する不利益な行為は、次の誤りを引き起こす可能性があります。

A-1.1

Deletion

A-1.1.1
Deletion of a CA certificate would cause an RP to not be able to locate signed objects generated by that CA, except those that have been cached by the RP. Thus, an RP would be unaware of changed or new (issued after the cached data) INR bindings asserted in subordinate ROAs, and the RP would be unable to validate new or changed router certificates. If the missed objects were intended to replace ROAs or router certificates prior to expiration, then when those objects expire, RPs may cease to view them as valid. As a result, valid routes may be viewed as NotFound or Invalid.
A-1.2

Suppression

A-1.2.1
If publication of a CA certificate is suppressed, the impact depends on what changes appeared in the suppressed certificate. If the SIA value changed, the effect would be the same as in A-1.1 or A-1.4.3. If the [RFC3779] extensions in the suppressed certificate changed, the impact would be the same as in A-1.4.1. If the Authority Information Access (AIA) extension changed in the suppressed certificate, the impact would be the same as in A-1.4.4. Suppression of a renewed/re-issued certificate may cause an old certificate to expire and thus be rejected by RPs.
A-1.3

Corruption

A-1.3.1
Corruption of a CA certificate will cause it to be rejected by RPs. In turn, this may cause subordinate signed objects to become invalid. An RP that has cached the subtree under the affected CA certificate may continue to view it as valid, until objects expire. But changed or new objects might not be retrieved, depending on details of the design of the RP software. Thus, this action may be equivalent to suppressing changes to the affected subtree.
A-1.4

Modification

A-1.4.1
If a CA certificate is modified but still conforms to the RPKI certificate profile [RFC7935], it will be accepted by RPs. If an [RFC3779] extension in this certificate is changed to exclude INRs that were previously present, then subordinate signed objects will become invalid if they rely on the excised INRs. If these objects are CA certificates, their subordinate signed objects will be treated as invalid. If the objects are ROAs, the binding expressed by the affected ROAs will be ignored by RPs. If the objects are router certificates, BGPsec_PATH attributes [RFC8205] verifiable under these certificates will be considered invalid.
A-1.4.2
If the SIA extension of a CA certificate is modified to refer to another publication point, this will cause an RP to look at another location for subordinate objects. This could cause RPs to not acquire the objects that the INR holder intended to be retrieved -- manifests, ROAs, router certificates, Ghostbuster Records, or any subordinate CA certificates associated with that CA. If the objects at this new location contain invalid signatures or appear to be corrupted, they may be rejected. In this case, cached versions of the objects may be viewed as valid by an RP, until they expire. If the objects at the new location have valid signatures and pass path validation checks, they will replace the cached objects, effectively replacing the INR holder's objects.
A-1.4.3
If the AIA extension in a CA certificate is modified, it would point to a different CA certificate, not the parent CA certificate. This extension is used only for path discovery, not path validation. Path discovery in the RPKI is usually performed on a top-down basis, starting with trust anchors (TAs) and recursively descending the RPKI hierarchy. Thus, there may be no impact on the ability of clients to acquire and validate certificates if the AIA is modified.
A-1.4.4
If the Subject Public Key Info (and Subject Key Identifier extension) in a CA certificate is modified to contain a public key corresponding to a private key held by the parent, the parent could sign objects as children of the affected CA certificate. With this capability, the parent could replace the INR holder, issuing new signed objects that would be accepted by RPs (as long as they do not violate the path validation criteria). This would enable the parent to effect modification, revocation, and injection actions against all of the objects under the affected CA certificate, including subordinate CA certificates. (Note that key rollover also yields a new CA certificate. However, the new certificate will coexist with the old one for a while, which may help distinguish this legitimate activity from an adverse action.)
A-1.5

Revocation

A-1.5.1
If a CA certificate is revoked, an RP will treat as invalid all subordinate signed objects, both immediate and transitive. The effects are essentially the same as described in A-3.4.2.
A-1.6

Injection

A-1.6.1
If a CA certificate is injected, the impact will depend on the data contained in the injected certificate. Changes will generally be equivalent to modification actions as described in A-1.4.
A-1.1

削除

A-1.1.1
CA証明書が削除されると、RPは、そのCAが生成した署名付きオブジェクトのうち、RPがキャッシュしているもの以外を見つけられなくなります。 したがって、RPは、下位のROAで表明されたINRバインディングのうち、変更されたものや新しいもの（キャッシュされたデータの後に発行されたもの）に気付かず、また新しいルーター証明書や変更されたルーター証明書を検証できなくなります。 見落とされたオブジェクトが、ROAやルーター証明書を有効期限前に置き換えることを意図したものであった場合、置き換えられるはずだったオブジェクトの有効期限が切れると、RPはそれらを有効と見なさなくなる可能性があります。 その結果、有効な経路がNotFoundまたはInvalidと見なされる可能性があります。
A-1.2

抑止

A-1.2.1
CA証明書の公開が抑止された場合、その影響は、抑止された証明書にどのような変更があったかによって異なります。SIAの値が変更されていた場合、影響はA-1.1またはA-1.4.3と同じになります。抑止された証明書の[RFC3779]拡張が変更されていた場合、影響はA-1.4.1と同じになります。抑止された証明書の機関情報アクセス（AIA）拡張が変更されていた場合、影響はA-1.4.4と同じになります。更新・再発行された証明書が抑止されると、古い証明書の有効期限が切れ、その結果RPによって拒否される可能性があります。
A-1.3

破損

A-1.3.1
CA証明書が破損すると、その証明書はRPによって拒否されます。その結果、下位の署名付きオブジェクトが無効になる可能性があります。影響を受けるCA証明書の下のサブツリーをキャッシュしているRPは、オブジェクトの有効期限が切れるまで、そのサブツリーを有効と見なし続ける場合があります。しかし、RPソフトウェアの設計の詳細によっては、変更されたオブジェクトや新しいオブジェクトが取得されない可能性があります。したがって、この行為は、影響を受けるサブツリーに対する変更を抑止することと同等である場合があります。
A-1.4

改変

A-1.4.1
CA証明書が改変されても、RPKI証明書プロファイル[RFC7935]に依然として準拠している場合、その証明書はRPによって受け入れられます。この証明書の[RFC3779]拡張が、以前は含まれていたINRを除外するように変更された場合、取り除かれたINRに依存する下位の署名付きオブジェクトは無効になります。それらのオブジェクトがCA証明書であれば、その下位の署名付きオブジェクトは無効として扱われます。それらのオブジェクトがROAであれば、影響を受けるROAで表現されたバインディングはRPによって無視されます。それらのオブジェクトがルーター証明書であれば、それらの証明書の下で検証可能なBGPsec_PATH属性[RFC8205]は無効と見なされます。
A-1.4.2
CA証明書のSIA拡張が別の公開ポイントを参照するように改変されると、RPは下位のオブジェクトを別の場所で探すことになります。これにより、INR保有者が取得されることを意図したオブジェクト（そのCAに関連付けられたマニフェスト、ROA、ルーター証明書、Ghostbustersレコード、または下位CA証明書）をRPが取得しない可能性があります。この新しい場所にあるオブジェクトが無効な署名を含んでいたり、破損しているように見えたりする場合、それらは拒否される可能性があります。この場合、オブジェクトのキャッシュされた版は、有効期限が切れるまでRPによって有効と見なされる場合があります。新しい場所にあるオブジェクトが有効な署名を持ち、パス検証のチェックに合格した場合、それらはキャッシュされたオブジェクトを置き換え、事実上INR保有者のオブジェクトを置き換えることになります。
A-1.4.3
CA証明書のAIA拡張が改変されると、その拡張は親CA証明書ではなく、別のCA証明書を指すことになります。この拡張はパス探索にのみ使用され、パス検証には使用されません。RPKIにおけるパス探索は通常、トラストアンカー（TA）から始めてRPKI階層を再帰的にたどるトップダウン方式で行われます。したがって、AIAが改変されても、クライアントが証明書を取得して検証する能力には影響がない場合があります。
A-1.4.4
CA証明書のサブジェクト公開鍵情報（Subject Public Key Info）（およびサブジェクト鍵識別子（Subject Key Identifier）拡張）が、親が保持する秘密鍵に対応する公開鍵を含むように改変された場合、親は影響を受けるCA証明書の子としてオブジェクトに署名できるようになります。この能力により、親はINR保有者に取って代わり、（パス検証の基準に違反しない限り）RPによって受け入れられる新しい署名付きオブジェクトを発行できます。これにより、親は、下位CA証明書を含め、影響を受けるCA証明書の下にあるすべてのオブジェクトに対して、改変、失効、注入の行為を実行できるようになります。（鍵ロールオーバーでも新しいCA証明書が生成されることに注意してください。ただし、その場合、新しい証明書はしばらくの間古い証明書と共存するので、この正当な活動を不利益な行為と区別するのに役立つ場合があります。）
A-1.5

失効

A-1.5.1
CA証明書が失効させられると、RPは、直接のものも推移的なものも含め、下位のすべての署名付きオブジェクトを無効として扱います。影響は、本質的にA-3.4.2で説明したものと同じです。
A-1.6

注入

A-1.6.1
CA証明書が注入された場合、その影響は注入された証明書に含まれるデータによって異なります。変化は一般に、A-1.4で説明した改変の行為と同等になります。

2.2. Manifest

2.2. マニフェスト

Each repository publication point contains a manifest [RFC6486]. The RPKI incorporates manifests to enable RPs to detect suppression and/or substitution of (more recent) publication point objects, as the result of a mistake or attack. A manifest enumerates (by filename) all of the other signed objects at the publication point. The manifest also contains a hash of each enumerated file to enable an RP to determine if the named file content matches what the INR holder identified in the manifest.

各リポジトリーの公開ポイントにはマニフェスト[RFC6486]が含まれます。 RPKIは、誤りや攻撃の結果として公開ポイントの（より新しい）オブジェクトが抑止されたり差し替えられたりしたことをRPが検出できるように、マニフェストを取り入れています。 マニフェストは、公開ポイントにあるほかのすべての署名付きオブジェクトを（ファイル名で）列挙します。 また、マニフェストには、列挙された各ファイルのハッシュが含まれており、RPは名前の付いたファイルの内容が、INR保有者がマニフェストで特定したものと一致するかどうかを判断できます。

A manifest is an RPKI signed object, so it is validated as per [RFC6488]. If a manifest is modified in a way that causes any of these checks to fail, the manifest will be considered invalid. Suppression of a manifest itself (indicated by a stale manifest) can also cause an RP to not detect suppression of other signed objects at the publication point. (Note that if a manifest's EE certificate expires at the time that the manifest is scheduled to be replaced, a delay in publication will cause the manifest to become invalid, not merely stale. This very serious outcome should be avoided, e.g., by making the manifest EE certificate's notAfter value the same as that of the CA certificate under which it was issued). If a signed object at a publication point can be validated (using the rules applicable for that object type), then an RP may accept that object, even if there is no matching entry for it on the manifest. However, it appears that most RP software ignores publication point data that fails to match manifest entries (at the time this document was written).

マニフェストはRPKIの署名付きオブジェクトなので、[RFC6488]に従って検証されます。 これらのチェックのいずれかが失敗するような方法でマニフェストが改変された場合、そのマニフェストは無効と見なされます。 マニフェスト自体の抑止（古くなったマニフェストによって示されます）によっても、RPが公開ポイントにあるほかの署名付きオブジェクトの抑止を検出できなくなる場合があります。 （マニフェストが置き換えられる予定の時点でマニフェストのEE証明書の有効期限が切れる場合、公開が遅れると、マニフェストは単に古くなるだけでなく無効になることに注意してください。 この非常に深刻な結果は、たとえばマニフェストのEE証明書のnotAfter値を、それが発行されたCA証明書のnotAfter値と同じにすることによって、回避すべきです。） 公開ポイントにある署名付きオブジェクトを（そのオブジェクトの種類に適用される規則を使って）検証できる場合、マニフェストにそのオブジェクトに一致するエントリーがなくても、RPはそのオブジェクトを受け入れてもかまいません。 しかし、（この文書の執筆時点では）ほとんどのRPソフトウェアは、マニフェストのエントリーと一致しない公開ポイントのデータを無視するようです。

Corruption, suppression, modification, or deletion of a manifest might not affect RP processing of other publication point objects, as specified in [RFC6486]. However, as noted above, many RP implementations ignore objects that are present at a publication point but not listed in a valid manifest. Thus, the following actions against a manifest can impact RP processing:

[RFC6486]で規定されているように、マニフェストの破損、抑止、改変、削除は、公開ポイントのほかのオブジェクトに対するRPの処理に影響しない場合があります。 しかし、上で述べたように、多くのRPの実装は、公開ポイントに存在しても有効なマニフェストに載っていないオブジェクトを無視します。 したがって、マニフェストに対する次の行為はRPの処理に影響を与える可能性があります。

A-2.1

Deletion

A-2.1.1
A manifest may be deleted from the indicated publication point. In this circumstance, an RP may elect to use the previous manifest (if available) and may ignore any new/changed objects at the publication point. The implications of this action are equivalent to suppression of publication of the objects that are not recognized by RPs because the new objects are not present in the old manifest. For example, a new ROA could be ignored (A-1.2). A newly issued CA certificate might be ignored (A-1.1). A subordinate CA certificate that was revoked might still be viewed as valid by RPs (A-4.1). A new or changed router certificate might be ignored (A-6.2) as would a revised Ghostbusters Record (A-4.1).
A-2.2

Suppression

A-2.2.1
Publication of a newer manifest may be suppressed. Suppression of a newer manifest probably will cause an RP to rely on a cached manifest (if available). The older manifest would not enumerate newly added objects; thus, those objects might be ignored by an RP, which is equivalent to deletion of those objects (A-1.1, A-3.1, A-4.1, A-5.1, and A-6.1).
A-2.3

Corruption

A-2.3.1
A manifest may be corrupted. A corrupted manifest will be rejected by RPs. This may cause RPs to rely on a previous manifest, with the same impact as A-2.2. If an RP does not revert to using a cached manifest, the impact of this action is very severe, i.e., all publication point objects will probably be viewed as invalid, including subordinate tree objects. This is equivalent to revoking or deleting an entire subtree (see A-4.4.2).
A-2.4

Modification

A-2.4.1
A manifest may be modified to remove one or more objects. Because the modified manifest is viewed as valid by RPs, any objects that were removed may be ignored by RPs. This is equivalent to deleting these objects from the repository. The impact of this action will vary, depending on which objects are (effectively) removed. However, the impact is equivalent to deletion of the object in question, (A-1.1, A-3.1, A-4.1, A-5.1, and A-6.1).
A-2.4.2
A manifest may be modified to add one or more objects. If an added object has a valid signature (and is not expired), it will be accepted by RPs and processed accordingly. If the added object was previously deleted by the INR holder, this action is equivalent to suppressing deletion of that object. If the object is newly created or modified, it is equivalent to a modification or injection action for the type of object in question and is thus discussed in the relevant section for those actions for the object type.
A-2.4.3
A manifest may be modified to list an incorrect hash for one or more objects. An object with an incorrect hash may be ignored by an RP. Thus, the effect may be equivalent to corrupting the object in question, although the error reported by RP software would differ from that reported for a corrupted object. (The manifest specifications do not require an RP to ignore an object that has a valid signature and that is not revoked or expired, but for which the hash doesn't match the object. However, an RP may elect to do so.)
A-2.5

Revocation

A-2.5.1
A manifest may be revoked (by including its EE certificate on the CRL for the publication point). A revoked manifest will be ignored by an RP, which probably would revert to an older (cached) manifest. The implications for RPs are equivalent to A-2.1 with regard to new/changed objects.
A-2.6

Injection

A-2.6.1
A manifest representing different objects may be injected into a publication point. The effects are the same as for a modified manifest (see above). The impact will depend on the type of the affected object(s) and is thus discussed in the relevant section(s) for each object type.
A-2.1

削除

A-2.1.1
マニフェストは、指定された公開ポイントから削除される場合があります。この場合、RPは（利用可能であれば）以前のマニフェストを使うことを選択し、公開ポイントにある新しいオブジェクトや変更されたオブジェクトを無視する場合があります。この行為が持つ意味は、新しいオブジェクトが古いマニフェストに存在しないためにRPによって認識されないオブジェクトの公開を抑止することと同等です。たとえば、新しいROAが無視される可能性があります（A-1.2）。新たに発行されたCA証明書が無視される可能性があります（A-1.1）。失効させられた下位CA証明書が、依然としてRPによって有効と見なされる可能性があります（A-4.1）。新しいルーター証明書や変更されたルーター証明書が無視される可能性があり（A-6.2）、改訂されたGhostbustersレコードも同様に無視される可能性があります（A-4.1）。
A-2.2

抑止

A-2.2.1
より新しいマニフェストの公開が抑止される場合があります。より新しいマニフェストが抑止されると、RPはおそらく（利用可能であれば）キャッシュされたマニフェストに依存することになります。古いマニフェストは新たに追加されたオブジェクトを列挙していないので、それらのオブジェクトはRPによって無視される可能性があり、これはそれらのオブジェクトの削除と同等です（A-1.1、A-3.1、A-4.1、A-5.1、A-6.1）。
A-2.3

破損

A-2.3.1
マニフェストが破損する場合があります。破損したマニフェストはRPによって拒否されます。これにより、RPは以前のマニフェストに依存することになり、A-2.2と同じ影響が生じる可能性があります。RPがキャッシュされたマニフェストの使用に戻らない場合、この行為の影響は非常に深刻です。すなわち、下位のツリーのオブジェクトを含め、公開ポイントのすべてのオブジェクトがおそらく無効と見なされます。これは、サブツリー全体を失効させたり削除したりすることと同等です（A-4.4.2を参照）。
A-2.4

改変

A-2.4.1
マニフェストが、1つ以上のオブジェクトを取り除くように改変される場合があります。改変されたマニフェストはRPによって有効と見なされるので、取り除かれたオブジェクトはRPによって無視される可能性があります。これは、それらのオブジェクトをリポジトリーから削除することと同等です。この行為の影響は、どのオブジェクトが（事実上）取り除かれたかによって異なります。ただし、その影響は、該当するオブジェクトの削除と同等です（A-1.1、A-3.1、A-4.1、A-5.1、A-6.1）。
A-2.4.2
マニフェストが、1つ以上のオブジェクトを追加するように改変される場合があります。追加されたオブジェクトが有効な署名を持つ（かつ有効期限が切れていない）場合、そのオブジェクトはRPによって受け入れられ、それに応じて処理されます。追加されたオブジェクトが以前にINR保有者によって削除されたものである場合、この行為はそのオブジェクトの削除を抑止することと同等です。オブジェクトが新たに作成されたものや改変されたものである場合、該当する種類のオブジェクトに対する改変または注入の行為と同等であり、したがってそのオブジェクトの種類についてのそれらの行為に関するセクションで議論します。
A-2.4.3
マニフェストが、1つ以上のオブジェクトについて誤ったハッシュを載せるように改変される場合があります。誤ったハッシュを持つオブジェクトは、RPによって無視される可能性があります。したがって、RPソフトウェアが報告するエラーは破損したオブジェクトについて報告されるものとは異なりますが、その影響は該当するオブジェクトを破損させることと同等である場合があります。（マニフェストの仕様は、有効な署名を持ち、失効も有効期限切れもしていないものの、ハッシュがオブジェクトと一致しないオブジェクトを無視することをRPに要求していません。ただし、RPはそうすることを選択できます。）
A-2.5

失効

A-2.5.1
マニフェストが（そのEE証明書を公開ポイントのCRLに含めることによって）失効させられる場合があります。失効させられたマニフェストはRPによって無視され、RPはおそらくより古い（キャッシュされた）マニフェストの使用に戻ります。新しいオブジェクトや変更されたオブジェクトに関して、RPにとっての意味はA-2.1と同等です。
A-2.6

注入

A-2.6.1
異なるオブジェクトを表すマニフェストが、公開ポイントに注入される場合があります。その影響は、改変されたマニフェストの場合（上記参照）と同じです。影響は、影響を受けるオブジェクトの種類によって異なるため、各オブジェクトの種類に関するセクションで議論します。

2.3. Certificate Revocation List

2.3. 証明書失効リスト

Each publication point contains a CRL that enumerates revoked (not yet expired) certificates issued by the CA associated with the publication point [RFC6481].

各公開ポイントには、その公開ポイントに関連付けられたCAが発行した証明書のうち、失効させられた（まだ有効期限が切れていない）証明書を列挙したCRLが含まれます[RFC6481]。

Adverse actions against a CRL can cause the following errors:

CRLに対する不利益な行為は、次の誤りを引き起こす可能性があります。

A-3.1

Deletion

A-3.1.1
If a CRL is deleted, RPs will continue to use an older, previously fetched Certificate Revocation List. As a result, they will not be informed of any changes in revocation status of subordinate CA or router certificates or the EE certificates of signed objects, e.g., ROAs. This action is equivalent to corruption of a CRL, since a corrupted CRL will not be accepted by an RP.
A-3.1.2
Deletion of a CRL could cause an RP to continue to accept a ROA that no longer expresses the intent of an INR holder. As a result, an announcement for the affected prefixes would be viewed as Valid, instead of NotFound or Invalid. In this case, the effect is analogous to A-5.2.
A-3.1.3
If a router certificate were revoked and the CRL were deleted, RPs would not be aware of the revocation. They might continue to accept the old, revoked router certificate. If the certificate had been revoked due to a compromise of the router's private key, RPs would be vulnerable to accepting routes signed by an unauthorized entity.
A-3.1.4
If a subordinate CA certificate were revoked on the deleted CRL, the revocation would not take effect. This could interfere with a transfer of address space from the subordinate CA, adversely affecting routing to the new holder of the space.
A-3.2

Suppression

A-3.2.1
If publication of the most recent CRL is suppressed, an RP will not be informed of the most recent revocation status of a subordinate CA or router certificates or the EE certificates of signed objects. If an EE certificate has been revoked and the associated signed object is still present in the publication point, an RP might mistakenly treat that object as valid. (This would happen if the object is still in the manifest or if the RP is configured to process valid objects that are not on the manifest.) This type of action is of special concern if the affected object is a ROA, a router certificate, or a subordinate CA certificate. The effects here are equivalent to CRL deletion (A-3.1), but suppression of a new CRL may not even be reported as an error, i.e., if the suppressed CRL were issued before the NextUpdate time (of the previous CRL).
A-3.3

Corruption

A-3.3.1
If a CRL is corrupted, an RP will reject it. If a prior CRL has not yet exceeded its NextUpdate time, an RP will continue to use the prior CRL. Even if the prior CRL has passed the NextUpdate time, an RP may choose to continue to rely on the prior CRL. The effects are essentially equivalent to suppression or deletion of a CRL (A-3.1 and A-3.2).
A-3.4

Modification

A-3.4.1
If a CRL is modified to erroneously list a signed object's EE certificate as revoked, the corresponding object will be treated as invalid by RPs, even if it is present in a publication point. If this object is a ROA, the (legitimate) binding expressed by the ROA will be ignored by an RP (see A-5.5). If a CRL is modified to erroneously list a router certificate as revoked, a path signature associated with that certificate will be treated as Not Valid by RPs (see A-6.5).
A-3.4.2
If a CRL is modified to erroneously list a CA certificate as revoked, that CA and all subordinate signed objects will be treated as invalid by RPs. Depending on the location of the affected CA in the hierarchy, these effects could be very substantial, causing routes that should be Valid to be treated as NotFound.
A-3.4.3
If a CRL is modified to omit a revoked EE, router, or CA certificate, RPs will likely continue to accept the revoked, signed object as valid. This contravenes the intent of the INR holder. If an RP continues to accept a revoked ROA, it may make routing decisions on now-invalid data. This could cause valid routes to be de-preferenced and invalid routes to continue to be accepted.
A-3.5

Revocation

A-3.5.1
A CRL cannot be revoked per se, but it will fail validation if the CA certificate under which it was issued is revoked. See A-1.5 for a discussion of that action.
A-3.6

Injection

A-3.6.1
Insertion of a bogus CRL can have the same effects as listed above for a modified CRL, depending on how the inserted CRL differs from the correct CRL.
A-3.1

削除

A-3.1.1
CRLが削除されると、RPは以前に取得した古い証明書失効リストを使い続けます。その結果、RPは、下位のCA証明書やルーター証明書、または署名付きオブジェクト（ROAなど）のEE証明書の失効状態の変化を知らされません。破損したCRLはRPによって受け入れられないので、この行為はCRLの破損と同等です。
A-3.1.2
CRLが削除されると、RPは、もはやINR保有者の意図を表していないROAを受け入れ続ける可能性があります。その結果、影響を受けるプレフィックスのアナウンスは、NotFoundまたはInvalidではなくValidと見なされます。この場合、影響はA-5.2と同様です。
A-3.1.3
ルーター証明書が失効させられ、かつCRLが削除された場合、RPはその失効に気付きません。RPは、失効させられた古いルーター証明書を受け入れ続ける可能性があります。ルーターの秘密鍵の侵害のためにその証明書が失効させられていた場合、RPは、認可されていないエンティティーが署名した経路を受け入れてしまう脆弱な状態になります。
A-3.1.4
削除されたCRLで下位CA証明書が失効させられていた場合、その失効は効力を持ちません。これは、その下位CAからのアドレス空間の移転を妨げ、そのアドレス空間の新しい保有者へのルーティングに不利益な影響を与える可能性があります。
A-3.2

抑止

A-3.2.1
最新のCRLの公開が抑止されると、RPは、下位のCA証明書やルーター証明書、または署名付きオブジェクトのEE証明書の最新の失効状態を知らされません。EE証明書が失効させられているのに、関連付けられた署名付きオブジェクトがまだ公開ポイントに存在する場合、RPはそのオブジェクトを誤って有効として扱う可能性があります。（これは、そのオブジェクトがまだマニフェストに載っている場合や、マニフェストにない有効なオブジェクトを処理するようにRPが設定されている場合に起こります。）この種の行為は、影響を受けるオブジェクトがROA、ルーター証明書、下位CA証明書である場合に特に懸念されます。ここでの影響はCRLの削除（A-3.1）と同等ですが、新しいCRLの抑止はエラーとして報告されない場合さえあります。すなわち、抑止されたCRLが（以前のCRLの）NextUpdate時刻より前に発行された場合です。
A-3.3

破損

A-3.3.1
CRLが破損している場合、RPはそれを拒否します。以前のCRLがまだNextUpdate時刻を過ぎていなければ、RPは以前のCRLを使い続けます。以前のCRLがNextUpdate時刻を過ぎていても、RPは以前のCRLに依存し続けることを選択する場合があります。影響は、本質的にCRLの抑止または削除（A-3.1およびA-3.2）と同等です。
A-3.4

改変

A-3.4.1
CRLが、署名付きオブジェクトのEE証明書を誤って失効済みとして載せるように改変された場合、対応するオブジェクトは、公開ポイントに存在していてもRPによって無効として扱われます。このオブジェクトがROAであれば、そのROAで表現された（正当な）バインディングはRPによって無視されます（A-5.5を参照）。CRLが、ルーター証明書を誤って失効済みとして載せるように改変された場合、その証明書に関連付けられたパス署名はRPによってNot Validとして扱われます（A-6.5を参照）。
A-3.4.2
CRLが、CA証明書を誤って失効済みとして載せるように改変された場合、そのCAと下位のすべての署名付きオブジェクトはRPによって無効として扱われます。影響を受けるCAの階層内の位置によっては、これらの影響は非常に大きくなる可能性があり、Validであるべき経路がNotFoundとして扱われることになります。
A-3.4.3
CRLが、失効させられたEE証明書、ルーター証明書、CA証明書を省くように改変された場合、RPはおそらく、失効させられた署名付きオブジェクトを有効として受け入れ続けます。これはINR保有者の意図に反します。RPが失効させられたROAを受け入れ続けると、すでに無効になったデータに基づいてルーティングの決定を行う可能性があります。これにより、有効な経路の優先度が下げられ、無効な経路が引き続き受け入れられる可能性があります。
A-3.5

失効

A-3.5.1
CRL自体を失効させることはできませんが、そのCRLが発行されたCA証明書が失効させられると、CRLは検証に失敗します。その行為についての議論はA-1.5を参照してください。
A-3.6

注入

A-3.6.1
偽のCRLの挿入は、挿入されたCRLが正しいCRLとどのように異なるかに応じて、改変されたCRLについて上で挙げたものと同じ影響を及ぼす可能性があります。

2.4. ROA

2.4. ROA

In addition to the generic RPKI object syntax checks, ROA validation requires that the signature on the ROA can be validated using the public key from the EE certificate embedded in the ROA [RFC6482]. It also requires that the EE certificate be validated consistently with the procedures described in [RFC6482] and [RFC6487]. Adverse actions against a ROA can cause the following errors:

ROAの検証では、汎用的なRPKIオブジェクトの構文チェックに加えて、ROAに埋め込まれたEE証明書の公開鍵を使ってROAの署名を検証できることが要求されます[RFC6482]。 また、そのEE証明書が[RFC6482]と[RFC6487]で説明されている手順に従って検証されることも要求されます。 ROAに対する不利益な行為は、次の誤りを引き起こす可能性があります。

A-4.1

Deletion

A-4.1.1
A ROA may be deleted from the indicated publication point. The result is to void the binding between the prefix(es) and the Autonomous System (AS) number in the ROA. An RP that previously viewed this binding as authentic will now not have any evidence about its validity. For origin validation, this means that a legitimate route will be treated as NotFound (if there are no other ROAs for the same prefix) or Invalid (if there is another ROA for the same prefix, but with a different AS number).
A-4.2

Suppression

A-4.2.1
Publication of a newer ROA may be suppressed. If the INR holder intended to change the binding between the prefix(es) and the AS number in the ROA, this change will not be effected. As a result, RPs may continue to believe an old prefix/ASN binding that is no longer what the INR holder intended.
A-4.2.2
If an INR holder intends to issue and publish two (or more) new ROAs for the same address space, one (or more) of the new ROAs may be suppressed while the other is published. In this case, RPs will de-preference the suppressed prefix/ASN binding. Suppression of the new ROA might cause traffic to flow to an ASN other than the one(s) intended by the INR holder.
A-4.2.3
If an INR holder intends to delete all ROAs for the same address space, some of them may be retained while the others are deleted. Preventing the deletion of some ROAs can cause traffic to continue to be delivered to the ASNs that were advertised by these ROAs. Deletion of all ROAs is consistent with a transfer of address space to a different INR holder in a phased fashion. Thus, this sort of attack could interfere with the successful transfer of the affected address space (until such time as the prefixes are removed from the previous INR holder's CA certificate).
A-4.3

Corruption

A-4.3.1
A ROA may be corrupted. A corrupted ROA will be ignored by an RP, so the effect is essentially the same as for A-4.1 and A-4.5. A possible difference is that an RP may be alerted to the fact that the ROA was corrupted, which might attract attention to the attack.
A-4.4

Modification

A-4.4.1
A ROA may be modified so that the Autonomous System Number (ASN) or one or more of the address blocks in a ROA is different from the values the INR holder intended for this ROA. (This action assumes that the modified ROA's ASN and address ranges are authorized for use by the INR holder.) This attack will cause RPs to de-preference the legitimate prefix/ASN binding intended by the INR holder.
A-4.5

Revocation

A-4.5.1
A ROA may be revoked (by placing its EE certificate on the CRL for the publication point). This has the same effect as A-4.1.
A-4.6

Injection

A-4.6.1
A ROA expressing different bindings than those published by the INR holder may be injected into a publication point. This action could authorize an additional ASN to advertise the specified prefix, allowing that ASN to originate routes for the prefix, thus enabling route origin spoofing. In this case, the injected ROA is considered to be in competition with any existing authorized ROAs for the specified prefix.
A-4.6.2
An injected ROA might express a different prefix for an ASN already authorized to originate a route, e.g., a longer prefix, which could enable that ASN to override other advertisements using shorter prefixes. If there are other ROAs that authorize different ASNs to advertise routes to the injected ROA's prefix, then the injected ROA is in competition with these ROAs.
A-4.1

削除

A-4.1.1
ROAは、指定された公開ポイントから削除される場合があります。その結果、ROA内のプレフィックスと自律システム（AS）番号の間のバインディングが無効になります。以前このバインディングを正当なものと見なしていたRPは、今後その有効性に関する証拠を何も持たなくなります。オリジン検証では、これは、正当な経路がNotFound（同じプレフィックスに対するほかのROAがない場合）またはInvalid（同じプレフィックスに対する、AS番号が異なる別のROAがある場合）として扱われることを意味します。
A-4.2

抑止

A-4.2.1
より新しいROAの公開が抑止される場合があります。INR保有者がROA内のプレフィックスとAS番号の間のバインディングを変更しようとしていた場合、その変更は実現されません。その結果、RPは、もはやINR保有者が意図したものではない古いプレフィックスとASNのバインディングを信じ続ける可能性があります。
A-4.2.2
INR保有者が同じアドレス空間に対して2つ（以上）の新しいROAを発行して公開しようとしている場合、新しいROAのうち1つ（以上）が抑止され、もう一方が公開される可能性があります。この場合、RPは抑止されたプレフィックスとASNのバインディングの優先度を下げます。新しいROAの抑止により、トラフィックがINR保有者の意図したASN以外のASNに流れる可能性があります。
A-4.2.3
INR保有者が同じアドレス空間に対するすべてのROAを削除しようとしている場合、そのうちのいくつかが残され、ほかが削除される可能性があります。一部のROAの削除を妨げると、それらのROAによってアドバタイズされていたASNにトラフィックが引き続き配送される可能性があります。すべてのROAの削除は、アドレス空間を段階的に別のINR保有者へ移転することと整合します。したがって、この種の攻撃は、（以前のINR保有者のCA証明書からそのプレフィックスが取り除かれるまでの間）影響を受けるアドレス空間の移転の成功を妨げる可能性があります。
A-4.3

破損

A-4.3.1
ROAが破損する場合があります。破損したROAはRPによって無視されるので、影響は本質的にA-4.1やA-4.5と同じです。違いがあるとすれば、ROAが破損したという事実がRPに警告される可能性があり、それによって攻撃に注意が向けられるかもしれないことです。
A-4.4

改変

A-4.4.1
ROAは、そのROAの自律システム番号（ASN）または1つ以上のアドレスブロックが、INR保有者がそのROAに意図した値と異なるものになるように改変される場合があります。（この行為は、改変されたROAのASNとアドレス範囲が、INR保有者による使用を認可されていることを前提とします。）この攻撃により、RPは、INR保有者が意図した正当なプレフィックスとASNのバインディングの優先度を下げます。
A-4.5

失効

A-4.5.1
ROAが（そのEE証明書を公開ポイントのCRLに載せることによって）失効させられる場合があります。これはA-4.1と同じ影響を及ぼします。
A-4.6

注入

A-4.6.1
INR保有者が公開したものとは異なるバインディングを表すROAが、公開ポイントに注入される場合があります。この行為により、追加のASNが指定されたプレフィックスをアドバタイズすることが認可され、そのASNがそのプレフィックスの経路を生成できるようになり、経路生成元の詐称が可能になる可能性があります。この場合、注入されたROAは、指定されたプレフィックスに対する既存の認可されたROAと競合していると見なされます。
A-4.6.2
注入されたROAは、すでに経路の生成を認可されているASNに対して、異なるプレフィックス（たとえば、より長いプレフィックス）を表している可能性があり、それによってそのASNが、より短いプレフィックスを使うほかのアドバタイズメントを上書きできるようになるかもしれません。注入されたROAのプレフィックスへの経路をアドバタイズすることを別のASNに認可するほかのROAがある場合、注入されたROAはそれらのROAと競合しています。

2.5. Ghostbusters Record

2.5. Ghostbustersレコード

The Ghostbusters Record [RFC6493] is a signed object that may be included at a publication point, at the discretion of the INR holder or publication point operator. The record is validated according to [RFC6488]. Additionally, the syntax of the record is verified based on the vCard profile from Section 5 of [RFC6493]. Errors in this record do not affect RP processing. However, if an RP encounters a problem with objects at a publication point, the RP may use information from the record to contact the publication point operator.

Ghostbustersレコード[RFC6493]は、INR保有者または公開ポイント運用者の裁量で公開ポイントに含めることができる署名付きオブジェクトです。 このレコードは[RFC6488]に従って検証されます。 さらに、このレコードの構文は、[RFC6493]のセクション5のvCardプロファイルに基づいて検証されます。 このレコードの誤りは、RPの処理に影響しません。 ただし、RPが公開ポイントのオブジェクトに問題を見つけた場合、RPはこのレコードの情報を使って公開ポイント運用者に連絡できます。

Adverse actions against a Ghostbusters Record can cause the following error:

Ghostbustersレコードに対する不利益な行為は、次の誤りを引き起こす可能性があります。

A-5.1
Deletion, suppression, corruption, or revocation of a Ghostbusters Record could prevent an RP from contacting the appropriate entity when a problem is detected by the RP. Modification or injection of a Ghostbusters Record could cause an RP to contact the wrong entity, thus delaying remediation of a detected anomaly. All of these actions are viewed as equivalent from an RP processing perspective; they do not alter RP validation of ROAs or router certificates. However, these actions can interfere with remediation of a problem when detected by an RP.
A-5.1
Ghostbustersレコードの削除、抑止、破損、失効により、RPが問題を検出したときに適切なエンティティーに連絡できなくなる可能性があります。Ghostbustersレコードの改変や注入により、RPが誤ったエンティティーに連絡し、検出された異常の是正が遅れる可能性があります。RPの処理の観点からは、これらの行為はすべて同等と見なされます。これらの行為は、RPによるROAやルーター証明書の検証を変えるものではありません。しかし、これらの行為は、RPが問題を検出したときにその問題の是正を妨げる可能性があります。

2.6. Router Certificates

2.6. ルーター証明書

Router certificates are used by RPs to verify signatures on BGPsec_PATH attributes carried in UPDATE messages.

ルーター証明書は、UPDATEメッセージで運ばれるBGPsec_PATH属性の署名をRPが検証するために使用されます。

Each AS is free to determine the granularity at which router certificates are managed [RFC8209]. Each participating AS is represented by one or more router certificates. During key or algorithm rollover, multiple router certificates will be present in a publication point, even if the AS is normally represented by just one such certificate.

各ASは、ルーター証明書を管理する粒度を自由に決めることができます[RFC8209]。 参加する各ASは、1つ以上のルーター証明書によって表されます。 鍵やアルゴリズムのロールオーバーの間は、通常はそのASがそのような証明書1つだけで表されている場合でも、公開ポイントに複数のルーター証明書が存在することになります。

Adverse actions against router certificates can cause the following errors:

ルーター証明書に対する不利益な行為は、次の誤りを引き起こす可能性があります。

A-6.1

Deletion

A-6.1.1
Deletion of a router certificate would cause an RP to be unable to verify signatures applied to BGPsec_PATH attributes on behalf of the AS in question. In turn, this would cause the route to be treated with lower preference than competing routes that have valid BGPsec_PATH attribute signatures. (However, if another router certificate for the affected AS is valid and contains the same AS number and public key, and it is in use by that AS, there would be no effect on routing. This scenario will arise if a router certificate is renewed, i.e., issued with a new validity interval.)
A-6.2

Suppression

A-6.2.1
Suppression of a router certificate could have the same impact as deletion of a certificate of this type, i.e., if no router certificate was available, BGPsec attributes that should be verified using the certificate would fail validation. If an older certificate existed and has not expired, it would be used by RPs. If the older certificate contained a different ASN, the impact would be the same as in A-6.4.
A-6.3

Corruption

A-6.3.1
Corruption of a router certificate will result in the certificate being rejected by RPs. Absent a valid router certificate, BGPsec_PATH attributes associated with that certificate will be unverifiable. In turn, this would cause the route to be treated with lower preference than competing routes that have valid BGPsec_PATH attribute signatures.
A-6.4

Modification

A-6.4.1
If a router certificate is modified to represent a different ASN, but it still passes syntax checks, then this action could cause signatures on BGPsec_PATH attributes to be associated with the wrong AS. This could cause signed routes to be inconsistent with the intent of the INR holder, e.g., traffic might be routed via a different AS than intended.
A-6.5

Revocation

A-6.5.1
If a router certificate were revoked, BGPsec_PATH attributes verifiable using that certificate would no longer be considered valid. The impact would be the same as for a deleted certificate, as described in A-6.1.
A-6.6

Injection

A-6.6.1
Insertion of a router certificate could authorize additional routers to sign BGPsec traffic for the targeted ASN, and thus undermine fundamental BGPsec security guarantees. If there are existing, authorized router certificates for the same ASN, then the injected router certificate is in competition with these existing certificates.
A-6.1

削除

A-6.1.1
ルーター証明書が削除されると、RPは、該当するASに代わって付与されたBGPsec_PATH属性の署名を検証できなくなります。その結果、その経路は、有効なBGPsec_PATH属性の署名を持つ競合する経路よりも低い優先度で扱われることになります。（ただし、影響を受けるASに対する別のルーター証明書が有効で、同じAS番号と公開鍵を含み、そのASによって使用されている場合には、ルーティングへの影響はありません。このシナリオは、ルーター証明書が更新された場合、すなわち新しい有効期間で発行された場合に生じます。）
A-6.2

抑止

A-6.2.1
ルーター証明書の抑止は、この種類の証明書の削除と同じ影響を及ぼす可能性があります。すなわち、利用可能なルーター証明書がなければ、その証明書を使って検証されるべきBGPsec属性は検証に失敗します。より古い証明書が存在し、その有効期限が切れていなければ、RPはその証明書を使用します。より古い証明書が異なるASNを含んでいた場合、影響はA-6.4と同じになります。
A-6.3

破損

A-6.3.1
ルーター証明書が破損すると、その証明書はRPによって拒否されます。有効なルーター証明書がなければ、その証明書に関連付けられたBGPsec_PATH属性は検証できなくなります。その結果、その経路は、有効なBGPsec_PATH属性の署名を持つ競合する経路よりも低い優先度で扱われることになります。
A-6.4

改変

A-6.4.1
ルーター証明書が、異なるASNを表すように改変されても、依然として構文チェックに合格する場合、この行為によって、BGPsec_PATH属性の署名が誤ったASに関連付けられる可能性があります。これにより、署名された経路がINR保有者の意図と矛盾したものになる可能性があります。たとえば、トラフィックが意図とは異なるASを経由してルーティングされるかもしれません。
A-6.5

失効

A-6.5.1
ルーター証明書が失効させられた場合、その証明書を使って検証可能なBGPsec_PATH属性は、もはや有効と見なされなくなります。影響は、A-6.1で説明したように、削除された証明書の場合と同じになります。
A-6.6

注入

A-6.6.1
ルーター証明書の挿入により、追加のルーターが、標的となったASNのBGPsecトラフィックに署名することが認可され、その結果BGPsecの根本的なセキュリティー保証が損なわれる可能性があります。同じASNに対する既存の認可されたルーター証明書がある場合、注入されたルーター証明書は、それらの既存の証明書と競合しています。

3. Analysis of Actions Relative to Scenarios

3. シナリオに関する行為の分析

This section examines the types of problems that can arise in four scenarios described below. We consider mistakes, (successful) attacks against a CA or a publication point, and situations in which a CA or publication point manager is compelled to take action by a law enforcement authority.

このセクションでは、以下で説明する4つのシナリオで生じうる問題の種類を検討します。 誤り、CAや公開ポイントに対する（成功した）攻撃、そしてCAや公開ポイント管理者が法執行機関によって行為を強制される状況を考慮します。

We explore the following four scenarios:

次の4つのシナリオを検討します。

  1. An INR holder operates its own CA and manages its own repository publication point.
  2. An INR holder operates its own CA, but outsources management of its repository publication point to its parent or another entity.
  3. An INR holder outsources management of its CA to its parent, but manages its own repository publication point.
  4. An INR holder outsources management of its CA and its publication point to its parent.
  1. INR保有者が自身のCAを運用し、自身のリポジトリー公開ポイントを管理する。
  2. INR保有者が自身のCAを運用するが、リポジトリー公開ポイントの管理を親または別のエンティティーに外部委託する。
  3. INR保有者がCAの管理を親に外部委託するが、自身のリポジトリー公開ポイントは管理する。
  4. INR保有者がCAと公開ポイントの管理を親に外部委託する。

Note that these scenarios focus on the affected INR holder as the party directly affected by an adverse action. The most serious cases arise when the INR holder appears as a high-tier CA in the RPKI hierarchy; in such situations, subordinate INR holders may be affected as a result of an action. A mistake by or an attack against a "leaf" has more limited impact because all of the affected INRs belong to the INR holder itself.

これらのシナリオは、不利益な行為によって直接影響を受ける当事者として、影響を受けるINR保有者に焦点を当てていることに注意してください。 最も深刻なケースは、INR保有者がRPKI階層の上位層のCAとして現れる場合に生じます。 そのような状況では、ある行為の結果として下位のINR保有者が影響を受ける可能性があります。 「葉」による誤りや「葉」に対する攻撃は、影響を受けるINRがすべてそのINR保有者自身に属するので、影響がより限定的です。

In Scenario A, actions by the INR holder can adversely affect all of its resources and, transitively, resources of any subordinate CAs. (If the CA is a "leaf" in the RPKI, then it has no subordinate CAs and the damage is limited to its own INRs.)

シナリオAでは、INR保有者による行為は、そのINR保有者のすべてのリソースに、そして推移的に下位CAのリソースに、不利益な影響を与える可能性があります。 （そのCAがRPKIにおける「葉」であれば、下位CAはないので、被害はそのCA自身のINRに限定されます。）

In Scenario B, actions by the (outsourced) repository operator can also adversely affect the resources of the INR holder and those of any subordinates CAs. (If the CA is a "leaf" in the RPKI, then it has no subordinate CAs and the damage is limited, as in Scenario A.) The range of adverse effects here includes those in Scenario A and adds a new potential source of adverse actions, i.e., the outsourced repository operator.

シナリオBでは、（外部委託された）リポジトリー運用者による行為も、INR保有者のリソースと下位CAのリソースに不利益な影響を与える可能性があります。 （そのCAがRPKIにおける「葉」であれば、下位CAはないので、シナリオAと同様に被害は限定されます。） ここでの不利益な影響の範囲には、シナリオAのものが含まれ、さらに不利益な行為の新たな潜在的な発生源、すなわち外部委託されたリポジトリー運用者が加わります。

In Scenario C, all signed objects associated with the INR holder are generated by the parent CA but are self-hosted. (We expect this scenario to be rare, because an INR holder that elects to outsource CA operation seems unlikely to manage its own repository publication point.) Because that CA has the private key used to sign them, it can generate alternative signed objects -- ones not authorized by the INR holder. However, erroneous objects created by the parent CA will not be published by the INR holder IF the holder checks them first. Because the parent CA is acting on behalf of the INR holder, mistakes by or attacks against that entity are equivalent to ones effected by the INR holder in Scenario A.

シナリオCでは、INR保有者に関連付けられたすべての署名付きオブジェクトは親CAによって生成されますが、INR保有者自身がホストします。 （INR保有者がCAの運用を外部委託することを選ぶのであれば、自身のリポジトリー公開ポイントを管理する可能性は低いと思われるので、このシナリオはまれであると予想されます。） そのCAはそれらのオブジェクトの署名に使われる秘密鍵を持っているので、別の署名付きオブジェクト、つまりINR保有者が認可していないオブジェクトを生成できます。 ただし、INR保有者が事前にチェックする「場合には」、親CAが作成した誤ったオブジェクトがINR保有者によって公開されることはありません。 親CAはINR保有者に代わって行動しているので、そのエンティティーによる誤りやそのエンティティーに対する攻撃は、シナリオAにおいてINR保有者が行うものと同等です。

The INR holder is most vulnerable in Scenario D. Actions by the parent CA, acting on behalf of the INR holder, can adversely affect all signed objects associated with that INR holder, including any subordinate CA certificates. These actions will presumably translate directly into publication point changes because the parent CA is managing the publication point for the INR holder. The range of adverse effects here includes those in Scenarios A, B, and C.

INR保有者が最も脆弱なのはシナリオDです。 INR保有者に代わって行動する親CAによる行為は、下位CA証明書を含め、そのINR保有者に関連付けられたすべての署名付きオブジェクトに不利益な影響を与える可能性があります。 親CAがINR保有者のために公開ポイントを管理しているので、これらの行為はおそらく、そのまま公開ポイントの変更となって現れます。 ここでの不利益な影響の範囲には、シナリオA、B、Cのものが含まれます。

3.1. Scenario A

3.1. シナリオA

In this scenario, the INR holder acts as its own CA and it manages its own publication point. Actions by the INR holder can adversely affect all of its resources and, transitively, resources of any subordinate CAs. (If the CA is a "leaf" in the RPKI, then it has no subordinate CAs and the damage is limited to its own INRs.) Mistakes by the INR holder can cause any of the actions noted in Section 2. A successful attack against this CA can effect all of the modification, revocation, or injection actions noted in that section. (We assume that objects generated by the CA are automatically published). An attack against the publication point can effect all of the deletion, suppression, or corruption actions noted in that section.

このシナリオでは、INR保有者は自身のCAとして振る舞い、自身の公開ポイントを管理します。 INR保有者による行為は、そのINR保有者のすべてのリソースに、そして推移的に下位CAのリソースに、不利益な影響を与える可能性があります。 （そのCAがRPKIにおける「葉」であれば、下位CAはないので、被害はそのCA自身のINRに限定されます。） INR保有者による誤りは、セクション2で述べたどの行為も引き起こす可能性があります。 このCAに対する攻撃が成功すると、同セクションで述べた改変、失効、注入のすべての行為を実行できます。 （CAが生成したオブジェクトは自動的に公開されると仮定します。） 公開ポイントに対する攻撃は、同セクションで述べた削除、抑止、破損のすべての行為を実行できます。

3.2. Scenario B

3.2. シナリオB

In this scenario, the INR holder acts as its own CA but it delegates management of it own publication point to a third party. Mistakes by the INR holder can cause any of the modification, revocation, or injection actions described in Section 2. Actions by the repository operator can adversely affect the resources of the INR holder, and those of any subordinate CAs. (If the CA is a "leaf" in the RPKI, then it has no subordinate CAs and the damage is limited, as in Scenario A.) The range of adverse effects here includes those in Scenario A, and adds a new potential source of adverse actions, i.e., the third party repository operator. A successful attack against the CA can effect all of the modification, revocation, or injection actions noted in that section (assuming that objects generated by the CA are automatically published). Here, actions by the publication point manager (or attacks against that entity) can effect all of the deletion, suppression, or corruption actions noted in Section 2.

このシナリオでは、INR保有者は自身のCAとして振る舞いますが、自身の公開ポイントの管理を第三者に委任します。 INR保有者による誤りは、セクション2で説明した改変、失効、注入のどの行為も引き起こす可能性があります。 リポジトリー運用者による行為は、INR保有者のリソースと下位CAのリソースに不利益な影響を与える可能性があります。 （そのCAがRPKIにおける「葉」であれば、下位CAはないので、シナリオAと同様に被害は限定されます。） ここでの不利益な影響の範囲には、シナリオAのものが含まれ、さらに不利益な行為の新たな潜在的な発生源、すなわち第三者であるリポジトリー運用者が加わります。 CAに対する攻撃が成功すると、（CAが生成したオブジェクトは自動的に公開されると仮定すると）同セクションで述べた改変、失効、注入のすべての行為を実行できます。 ここでは、公開ポイント管理者による行為（またはそのエンティティーに対する攻撃）によって、セクション2で述べた削除、抑止、破損のすべての行為を実行できます。

3.3. Scenario C

3.3. シナリオC

In this scenario, the INR holder outsources management of its CA to its parent, but manages its own repository publication point. All signed objects associated with the INR holder are generated by the parent CA but are self-hosted. (We expect this scenario to be rare, because an INR holder that elects to outsource CA operation seems unlikely to manage its own repository publication point.) Because that CA has the private key used to sign them, it can generate alternative signed objects -- ones not authorized by the INR holder. However, erroneous objects created by the parent CA will not be published by the INR holder IF the holder checks them first. Because the parent CA is acting on behalf of the INR holder, mistakes by or attacks against that entity are equivalent to ones effected by the INR holder in Scenario A. Mistakes by the INR holder, acted upon by the parent CA, can cause any of the actions noted in Section 2. Actions unilaterally undertaken by the parent CA also can have the same effect, unless the INR holder checks the signed objects before publishing them. A successful attack against the parent CA can effect all of the modification, revocation, or injection actions noted in Section 2, unless the INR holder checks the signed objects before publishing them. An attack against the INR holder (in its role as repository operator) can effect all of the deletion, suppression, or corruption actions noted in Section 2 (because the INR holder is managing its publication point), unless the INR holder checks the signed objects before publishing them. (An attack against the INR holder implies that the path it uses to direct the parent CA to issue and publish objects has been compromised.)

このシナリオでは、INR保有者はCAの管理を親に外部委託しますが、自身のリポジトリー公開ポイントは管理します。 INR保有者に関連付けられたすべての署名付きオブジェクトは親CAによって生成されますが、INR保有者自身がホストします。 （INR保有者がCAの運用を外部委託することを選ぶのであれば、自身のリポジトリー公開ポイントを管理する可能性は低いと思われるので、このシナリオはまれであると予想されます。） そのCAはそれらのオブジェクトの署名に使われる秘密鍵を持っているので、別の署名付きオブジェクト、つまりINR保有者が認可していないオブジェクトを生成できます。 ただし、INR保有者が事前にチェックする「場合には」、親CAが作成した誤ったオブジェクトがINR保有者によって公開されることはありません。 親CAはINR保有者に代わって行動しているので、そのエンティティーによる誤りやそのエンティティーに対する攻撃は、シナリオAにおいてINR保有者が行うものと同等です。 INR保有者による誤りは、親CAがそれに基づいて処理を行うことで、セクション2で述べたどの行為も引き起こす可能性があります。 INR保有者が署名付きオブジェクトを公開する前にチェックしない限り、親CAが一方的に行う行為も同じ影響を及ぼす可能性があります。 INR保有者が署名付きオブジェクトを公開する前にチェックしない限り、親CAに対する攻撃が成功すると、セクション2で述べた改変、失効、注入のすべての行為を実行できます。 INR保有者が署名付きオブジェクトを公開する前にチェックしない限り、（リポジトリー運用者としての役割における）INR保有者に対する攻撃は、（INR保有者が自身の公開ポイントを管理しているので）セクション2で述べた削除、抑止、破損のすべての行為を実行できます。 （INR保有者に対する攻撃は、INR保有者が親CAにオブジェクトの発行と公開を指示するために使う経路が侵害されたことを意味します。）

3.4. Scenario D

3.4. シナリオD

In this scenario, an INR holder outsources management of both its CA and its publication point to its parent. The INR holder is most vulnerable in this scenario. Actions by the parent CA, acting on behalf of the INR holder, can adversely affect all signed objects associated with that INR holder, including any subordinate CA certificates. These actions will presumably translate directly into publication point changes, because the parent CA is managing the publication point for the INR holder. The range of adverse effects here includes those in Scenarios A, B, and C. Mistakes by the INR holder, acted upon by the parent CA, can cause any of the actions noted in Section 2. Actions unilaterally undertaken by the parent CA also can have the same effect. A successful attack against the parent CA can effect all of the modification, revocation, or injection actions noted in Section 2. An attack against the parent CA can also effect all of the deletion, suppression, or corruption actions noted in Section 2 (because the parent CA is managing the INR holder's publication point).

このシナリオでは、INR保有者はCAと公開ポイントの両方の管理を親に外部委託します。 INR保有者はこのシナリオで最も脆弱です。 INR保有者に代わって行動する親CAによる行為は、下位CA証明書を含め、そのINR保有者に関連付けられたすべての署名付きオブジェクトに不利益な影響を与える可能性があります。 親CAがINR保有者のために公開ポイントを管理しているので、これらの行為はおそらく、そのまま公開ポイントの変更となって現れます。 ここでの不利益な影響の範囲には、シナリオA、B、Cのものが含まれます。 INR保有者による誤りは、親CAがそれに基づいて処理を行うことで、セクション2で述べたどの行為も引き起こす可能性があります。 親CAが一方的に行う行為も同じ影響を及ぼす可能性があります。 親CAに対する攻撃が成功すると、セクション2で述べた改変、失効、注入のすべての行為を実行できます。 親CAに対する攻撃は、（親CAがINR保有者の公開ポイントを管理しているので）セクション2で述べた削除、抑止、破損のすべての行為も実行できます。

4. Security Considerations

4. セキュリティーに関する考慮事項

This informational document describes a threat model for the RPKI, focusing on mistakes by or attacks against CAs and independent repository managers. It is intended to provide a basis for the design of future RPKI security mechanisms that seek to address the concerns associated with such actions.

この情報提供の文書は、CAと独立したリポジトリー管理者による誤りやそれらに対する攻撃に焦点を当てて、RPKIの脅威モデルを記述します。 この文書は、そのような行為に関連する懸念に対処しようとする将来のRPKIセキュリティーメカニズムの設計の基礎を提供することを意図しています。

The analysis in this document identifies a number of circumstances in which attacks or errors can have significant impacts on routing. One ought not interpret this as a condemnation of the RPKI. It is only an attempt to document the implications of a wide range of attacks and errors in the context of the RPKI. The primary alternative mechanism for disseminating routing information is Internet Routing Registry (IRR) technology [RFC2650] [RFC2725], which uses the Routing Policy Specification Language (RPSL) [RFC2622]. IRR technology exhibits its own set of security problems, which are discussed in [RFC7682].

この文書の分析では、攻撃や誤りがルーティングに重大な影響を及ぼしうる状況を数多く特定しています。 これをRPKIに対する非難と解釈すべきではありません。 これは、RPKIの文脈において、広範な攻撃や誤りが持つ意味を文書化しようとする試みにすぎません。 ルーティング情報を配布するための主要な代替メカニズムは、インターネットルーティングレジストリー（IRR）技術[RFC2650] [RFC2725]であり、これはルーティングポリシー仕様言語（RPSL）[RFC2622]を使用します。 IRR技術には独自のセキュリティー上の問題があり、それらは[RFC7682]で議論されています。
