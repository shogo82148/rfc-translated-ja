RFC 1110

Problem with the TCP Big Window Option

RFC 1110

TCPビッグウィンドウオプションの問題

Abstract

概要

The TCP Big Window option discussed in RFC 1106 will not work properly in an Internet environment which has both a high bandwidth * delay product and the possibility of disordering and duplicating packets. In such networks, the window size must not be increased without a similar increase in the sequence number space. Therefore, a different approach to big windows should be taken in the Internet.

RFC 1106で議論されているTCP Big Windowオプションは、帯域幅遅延積（bandwidth * delay product）が大きく、かつパケットの順序の入れ替わりや重複が起こりうるインターネット環境では、正しく動作しません。そのようなネットワークでは、シーケンス番号空間を同様に拡大することなく、ウィンドウサイズを拡大してはなりません。したがって、インターネットでは、大きなウィンドウについて別のアプローチを取るべきです。

Status of This Memo

このメモのステータス

This memo comments on the TCP Big Window option described in RFC 1106. Distribution of this memo is unlimited.

このメモは、RFC 1106で説明されているTCP Big Windowオプションについて意見を述べるものです。このメモの配布は無制限です。

Discussion

議論

TCP was designed to work in a packet store-and-forward environment characterized by the possibility of packet loss, packet disordering, and packet duplication. Packet loss can occur, for example, by a congested network element discarding a packet. Packet disordering can occur, for example, by packets of a TCP connection being arbitrarily transmitted partially over a low bandwidth terrestrial path and partially over a high bandwidth satellite path. Packet duplication can occur, for example, when two directly-connected network elements use a reliable link protocol and the link goes down after the receiver correctly receives a packet but before the transmitter receives an acknowledgement for the packet; the transmitter and receiver now each take responsibility for attempting to deliver the same packet to its ultimate destination.

TCPは、パケットの損失、パケットの順序の入れ替わり、パケットの重複が起こりうることを特徴とする、パケットのストアアンドフォワード環境で動作するように設計されました。パケットの損失は、たとえば、輻輳したネットワーク要素がパケットを破棄することによって起こりえます。パケットの順序の入れ替わりは、たとえば、TCPコネクションのパケットが、一部は低帯域の地上経路で、一部は高帯域の衛星経路で、任意に送信されることによって起こりえます。パケットの重複は、たとえば、直接接続された2つのネットワーク要素が信頼性のあるリンクプロトコルを使用していて、受信側がパケットを正しく受信した後、送信側がそのパケットの確認応答を受け取る前にリンクがダウンした場合に起こりえます。この場合、送信側と受信側はそれぞれ、同じパケットを最終的な宛先に届けようとする責任を負うことになります。

TCP has the task of recreating at the destination an exact copy of the data stream generated at the source, in the same order and with no gaps or duplicates. The mechanism used to accomplish this task is to assign a "unique" sequence number to each byte of data at its source, and to sort the bytes at the destination according to the sequence number. The sorting operation corrects any disordering. An acknowledgement, timeout, and retransmission scheme corrects for data loss. The uniqueness of the sequence number corrects for data duplication.

TCPには、送信元で生成されたデータストリームの正確なコピーを、同じ順序で、欠落や重複なしに宛先で再現するという役割があります。この役割を果たすために使われる仕組みは、送信元でデータの各バイトに「一意な」シーケンス番号を割り当て、宛先でシーケンス番号に従ってバイトを並べ替えるというものです。並べ替えの操作によって、順序の入れ替わりが修正されます。確認応答、タイムアウト、再送の方式によって、データの損失が修正されます。シーケンス番号の一意性によって、データの重複が修正されます。

As a practical matter, however, the sequence number is not unique; it is contained in a 32-bit field and therefore "wraps around" after the transmission of 2**32 bytes of data. Two additional mechanisms are used to insure the effective uniqueness of sequence numbers; these are the TCP transmission window and bounds on packet lifetime within the Internet, including the IP Time-to-Live (TTL). The transmission window specifies the maximum number of bytes which may be sent by the source in one source-destination roundtrip time. Since the TCP transmission window is specified by 16 bits, which is 1/65536 of the sequence number space, a sequence number will not be reused (used to number another byte) for 65,536 roundtrip times. So long as the combination of gateway action on the IP TTL and holding times within the individual networks which interconnect the gateways do not allow a packet's lifetime to exceed 65,536 roundtrip times, each sequence number is effectively unique. It was believed by the TCP designers that the networks and gateways forming the internet would meet this constraint, and such has been the case.

しかし、実際には、シーケンス番号は一意ではありません。シーケンス番号は32ビットのフィールドに格納されるので、2**32バイトのデータを送信すると「一周（wrap around）」します。シーケンス番号の実質的な一意性を確保するために、さらに2つの仕組みが使われます。TCPの送信ウィンドウと、IPのTime-to-Live（TTL）を含む、インターネット内のパケットの寿命の上限です。送信ウィンドウは、送信元と宛先の間の1往復時間に送信元が送信できる最大バイト数を指定します。TCPの送信ウィンドウは16ビットで指定され、これはシーケンス番号空間の1/65536なので、シーケンス番号は65,536往復時間のあいだ再利用される（別のバイトの番号付けに使われる）ことはありません。IP TTLに対するゲートウェイの動作と、ゲートウェイ同士を相互接続する個々のネットワーク内での保持時間の組み合わせによって、パケットの寿命が65,536往復時間を超えないかぎり、各シーケンス番号は実質的に一意です。TCPの設計者は、インターネットを構成するネットワークとゲートウェイがこの制約を満たすと考えており、実際にそのとおりになっています。

The proposed TCP Big Window option, as described in RFC 1106, expands the size of the window specification to 30 bits, while leaving the sequence number space unchanged. Thus, a sequence number can be reused after 4 roundtrip times. Further, the Nak option allows a packet to be retransmitted (i.e., potentially duplicated) by the source after only one roundtrip time. Thus, if a packet becomes "lost" in the Internet for only about 5 roundtrip times it may be delivered when its sequence number again lies within the window, albeit a later cycle of the window. In this case, TCP will not necessarily recreate at the destination an exact copy of the data stream generated at the source; it may replace some data with earlier data.

RFC 1106で説明されている、提案中のTCP Big Windowオプションは、シーケンス番号空間を変えずに、ウィンドウ指定のサイズを30ビットに拡大します。そのため、シーケンス番号は4往復時間後に再利用される可能性があります。さらに、Nakオプションによって、送信元はわずか1往復時間後にパケットを再送する（つまり、重複させる可能性がある）ことができます。したがって、パケットがインターネット内でわずか5往復時間ほど「行方不明」になると、そのシーケンス番号が再びウィンドウ内に入ったとき、ウィンドウの後のサイクルであるにもかかわらず、そのパケットが配送されるかもしれません。この場合、TCPは、送信元で生成されたデータストリームの正確なコピーを宛先で再現するとは限らず、一部のデータを以前のデータで置き換えてしまうかもしれません。

Of course, the problem described above results from the storage of the "lost" packet within the net, and its subsequent out-of-order delivery. RFC 1106 seems to describe use of the proposed options in an isolated satellite network. We may hypothesize that this network is memoryless, and thus cannot deliver packets out of order; it either delivers a packet in order or loses it. If this is the case, then there is no problem with the proposed options. The Internet, however, can deliver packets out of order, and this will likely continue to be true even if gigabit links become part of the Internet. Therefore, the approach described in RFC 1106 cannot be adopted for general Internet use.

もちろん、上で説明した問題は、「行方不明」のパケットがネット内に保存され、その後に順序どおりでなく配送されることから生じます。RFC 1106は、提案されたオプションを孤立した衛星ネットワークで使用することを説明しているようです。このネットワークには記憶がなく、したがってパケットを順序どおりでなく配送することはないと仮定してもよいでしょう。つまり、パケットを順序どおりに配送するか、失うかのどちらかです。その場合、提案されたオプションに問題はありません。しかし、インターネットはパケットを順序どおりでなく配送することがあり、これはギガビットのリンクがインターネットの一部になったとしても、おそらく変わらないでしょう。したがって、RFC 1106で説明されているアプローチは、インターネットでの一般的な使用には採用できません。
