RFC 9223

Real-Time Transport Object Delivery over Unidirectional Transport (ROUTE)

RFC 9223

単方向トランスポート上のリアルタイムトランスポートオブジェクト配送（ROUTE）

Abstract

概要

The Real-time Transport Object delivery over Unidirectional Transport (ROUTE) protocol is specified for robust delivery of Application Objects, including Application Objects with real-time delivery constraints, to receivers over a unidirectional transport. Application Objects consist of data that has meaning to applications that use the ROUTE protocol for delivery of data to receivers; for example, it can be a file, a Dynamic Adaptive Streaming over HTTP (DASH) or HTTP Live Streaming (HLS) segment, a WAV audio clip, etc. The ROUTE protocol also supports low-latency streaming applications.

単方向トランスポート上のリアルタイムトランスポートオブジェクト配送（Real-time Transport Object delivery over Unidirectional Transport、ROUTE）プロトコルは、リアルタイムの配送制約を持つアプリケーションオブジェクトを含むアプリケーションオブジェクトを、単方向トランスポート上で受信者に堅牢に配送するために規定されています。アプリケーションオブジェクトは、受信者へのデータ配送にROUTEプロトコルを使用するアプリケーションにとって意味を持つデータで構成されます。たとえば、ファイル、Dynamic Adaptive Streaming over HTTP（DASH）やHTTP Live Streaming（HLS）のセグメント、WAVオーディオクリップなどがそれにあたります。ROUTEプロトコルは、低遅延のストリーミングアプリケーションもサポートします。

The ROUTE protocol is suitable for unicast, broadcast, and multicast transport. Therefore, it can be run over UDP/IP, including multicast IP. The ROUTE protocol can leverage the features of the underlying protocol layer, e.g., to provide security, it can leverage IP security protocols such as IPsec.

ROUTEプロトコルは、ユニキャスト、ブロードキャスト、マルチキャストのトランスポートに適しています。したがって、マルチキャストIPを含むUDP/IP上で実行できます。ROUTEプロトコルは、下位のプロトコル層の機能を活用できます。たとえば、セキュリティーを提供するために、IPsecなどのIPセキュリティープロトコルを活用できます。

This document specifies the ROUTE protocol such that it could be used by a variety of services for delivery of Application Objects by specifying their own profiles of this protocol (e.g., by adding or constraining some features).

この文書は、さまざまなサービスが、このプロトコルの独自のプロファイルを規定する（たとえば、一部の機能を追加したり制約したりする）ことで、アプリケーションオブジェクトの配送に使用できるように、ROUTEプロトコルを規定します。

This is not an IETF specification and does not have IETF consensus.

これはIETFの仕様ではなく、IETFのコンセンサスを得ていません。

1. Introduction

1. はじめに

1.1. Overview

1.1. 概要

The Real-time Transport Object delivery over Unidirectional Transport (ROUTE) protocol can be used for robust delivery of Application Objects, including Application Objects with real-time delivery constraints, to receivers over a unidirectional transport. Unidirectional transport in this document has identical meaning to that in RFC 6726 [RFC6726], i.e., transport in the direction of receiver(s) from a sender. The robustness is enabled by a built-in mechanism, e.g., signaling for loss detection, enabling loss recovery, and optionally integrating application-layer Forward Error Correction (FEC).

単方向トランスポート上のリアルタイムトランスポートオブジェクト配送（Real-time Transport Object delivery over Unidirectional Transport、ROUTE）プロトコルは、リアルタイムの配送制約を持つアプリケーションオブジェクトを含むアプリケーションオブジェクトを、単方向トランスポート上で受信者に堅牢に配送するために使用できます。この文書における単方向トランスポートは、RFC 6726 [RFC6726]におけるものと同じ意味、すなわち送信者から受信者の方向へのトランスポートを意味します。堅牢性は、組み込みのメカニズムによって実現されます。たとえば、損失検出のためのシグナリング、損失回復の実現、そして任意でアプリケーション層の前方誤り訂正（Forward Error Correction、FEC）の統合などです。

Application Objects consist of data that has meaning to applications that use the ROUTE protocol for delivery of data to receivers, e.g., an Application Object can be a file, an MPEG Dynamic Adaptive Streaming over HTTP (DASH) [DASH] video segment, a WAV audio clip, an MPEG Common Media Application Format (CMAF) [CMAF] addressable resource, an MPEG-4 video clip, etc.

アプリケーションオブジェクトは、受信者へのデータ配送にROUTEプロトコルを使用するアプリケーションにとって意味を持つデータで構成されます。たとえば、アプリケーションオブジェクトは、ファイル、MPEG Dynamic Adaptive Streaming over HTTP（DASH）[DASH]のビデオセグメント、WAVオーディオクリップ、MPEG Common Media Application Format（CMAF）[CMAF]のアドレス可能なリソース、MPEG-4ビデオクリップなどです。

The ROUTE protocol is designed to enable delivery of sequences of related Application Objects in a timely manner to receivers, e.g., a sequence of DASH video segments associated to a Representation or a sequence of CMAF addressable resources associated to a CMAF Track. The applications of this protocol target services enabled on media consumption devices such as smartphones, tablets, television sets, and so on. Most of these applications are real-time in the sense that they are sensitive to and rely upon such timely reception of data. The ROUTE protocol also supports chunked delivery of real-time Application Objects to enable low-latency streaming applications (similar in its properties to chunked delivery using HTTP). The protocol also enables low-latency delivery of DASH and Apple HTTP Live Streaming (HLS) content with CMAF Chunks.

ROUTEプロトコルは、関連するアプリケーションオブジェクトの列を受信者にタイムリーに配送できるように設計されています。たとえば、あるRepresentationに関連付けられたDASHビデオセグメントの列や、あるCMAFトラックに関連付けられたCMAFのアドレス可能なリソースの列です。このプロトコルのアプリケーションは、スマートフォン、タブレット、テレビ受像機などのメディア消費デバイス上で実現されるサービスを対象としています。これらのアプリケーションのほとんどは、そのようなタイムリーなデータ受信に敏感であり、それに依存しているという意味でリアルタイムです。ROUTEプロトコルは、低遅延のストリーミングアプリケーションを実現するために、リアルタイムアプリケーションオブジェクトのチャンク配送（HTTPを使用したチャンク配送と同様の特性を持ちます）もサポートします。このプロトコルは、CMAFチャンクを使用したDASHやApple HTTP Live Streaming（HLS）コンテンツの低遅延配送も可能にします。

Content not intended for rendering in real time as it is received (e.g., a downloaded application), a file comprising continuous or discrete media and belonging to an app-based feature, or a file containing (opaque) data to be consumed by a Digital Rights Management (DRM) system client can also be delivered by ROUTE.

受信と同時にリアルタイムでレンダリングすることを意図していないコンテンツ（たとえば、ダウンロードされたアプリケーション）、連続メディアまたは離散メディアで構成され、アプリベースの機能に属するファイル、あるいはデジタル著作権管理（Digital Rights Management、DRM）システムのクライアントが消費する（不透明な）データを含むファイルも、ROUTEで配送できます。

The ROUTE protocol supports a caching model where Application Objects are recovered into a cache at the receiver and may be made available to applications via standard HTTP requests from the cache. Many current day applications rely on using HTTP to access content; hence, this approach enables such applications in broadcast/multicast environments.

ROUTEプロトコルは、アプリケーションオブジェクトが受信者のキャッシュに復元され、そのキャッシュから標準的なHTTPリクエストによってアプリケーションが利用できるようにしてもよいというキャッシュモデルをサポートします。現在の多くのアプリケーションは、コンテンツへのアクセスにHTTPを使用することに依存しています。したがって、この方式により、そのようなアプリケーションをブロードキャスト／マルチキャスト環境で実現できます。

ROUTE is aligned with File Delivery over Unidirectional Transport (FLUTE) as defined in RFC 6726 [RFC6726] as well as the extensions defined in Multimedia Broadcast/Multicast Service (MBMS) [MBMS], but it also makes use of some principles of FCAST (Object Delivery for the Asynchronous Layered Coding (ALC) and NACK-Oriented Reliable Multicast (NORM) Protocols) as defined in RFC 6968 [RFC6968]; for example, object metadata and the object content may be sent together in a compound object.

ROUTEは、RFC 6726 [RFC6726]で定義されている単方向トランスポート上のファイル配送（File Delivery over Unidirectional Transport、FLUTE）や、マルチメディアブロードキャスト／マルチキャストサービス（Multimedia Broadcast/Multicast Service、MBMS）[MBMS]で定義されている拡張と整合していますが、RFC 6968 [RFC6968]で定義されているFCAST（Object Delivery for the Asynchronous Layered Coding (ALC) and NACK-Oriented Reliable Multicast (NORM) Protocols）のいくつかの原則も利用しています。たとえば、オブジェクトのメタデータとオブジェクトのコンテンツを、複合オブジェクトとしていっしょに送信してもかまいません。

The alignment to FLUTE is enabled since in addition to reusing several of the basic FLUTE protocol features, as referred to by this document, certain optimizations and restrictions are added that enable optimized support for real-time delivery of media data; hence, the name of the protocol. Among others, the source ROUTE protocol enables or enhances the following functionalities:

FLUTEとの整合が可能になっているのは、この文書で参照しているように、FLUTEプロトコルの基本的な機能のいくつかを再利用することに加えて、メディアデータのリアルタイム配送を最適な形でサポートできるようにする特定の最適化と制限を追加しているためです。プロトコルの名前はこれに由来します。特に、ソースROUTEプロトコルは、次の機能を実現または強化します。

  • Real-time delivery of object-based media data
  • Flexible packetization, including enabling media-aware packetization as well as transport-aware packetization of delivery objects
  • Independence of Application Objects and delivery objects, i.e., a delivery object may be a part of a file or may be a group of files.
  • オブジェクトベースのメディアデータのリアルタイム配送
  • 配送オブジェクトのメディアを考慮したパケット化やトランスポートを考慮したパケット化の実現を含む、柔軟なパケット化
  • アプリケーションオブジェクトと配送オブジェクトの独立性。すなわち、配送オブジェクトはファイルの一部であってもよいし、ファイルのグループであってもかまいません。

Advanced Television Systems Committee (ATSC) 3.0 specifies the ROUTE protocol integrated with an ATSC 3.0 services layer. That specification will be referred to as ATSC-ROUTE [ATSCA331] for the remainder of this document. Digital Video Broadcasting (DVB) has specified a profile of ATSC-ROUTE in DVB Adaptive Media Streaming over IP Multicast (DVB-MABR) [DVBMABR]. This document specifies the Application Object delivery aspects (delivery protocol) for such services, as the corresponding delivery protocol could be used as a reference by a variety of services by specifying profiles of ROUTE in their respective fora, e.g., by adding new optional features atop or by restricting various optional features specified in this document in a specific service standard. Hence, in the context of this document, the aforementioned ATSC-ROUTE and DVB-MABR are the services using ROUTE. The definition of profiles by the services also have to give due consideration to compatibility issues, and some related guidelines are also provided in this document.

Advanced Television Systems Committee（ATSC）3.0は、ATSC 3.0サービス層と統合されたROUTEプロトコルを規定しています。この文書の以降の部分では、その仕様をATSC-ROUTE [ATSCA331]と呼びます。Digital Video Broadcasting（DVB）は、DVB Adaptive Media Streaming over IP Multicast（DVB-MABR）[DVBMABR]においてATSC-ROUTEのプロファイルを規定しています。この文書は、そのようなサービスのためのアプリケーションオブジェクト配送の側面（配送プロトコル）を規定します。対応する配送プロトコルは、さまざまなサービスがそれぞれのフォーラムでROUTEのプロファイルを規定することによって、参照として使用できるためです。たとえば、特定のサービス標準において、この文書で規定するものに新しい任意の機能を追加したり、さまざまな任意の機能を制限したりします。したがって、この文書の文脈では、前述のATSC-ROUTEとDVB-MABRがROUTEを使用するサービスです。サービスによるプロファイルの定義では、互換性の問題にも十分に考慮を払う必要があり、関連するいくつかのガイドラインもこの文書で提供しています。

この文書はIETFの仕様ではなく、IETFのコンセンサスを得ていません。この文書は、相互運用可能な実装の作成を支援するためにここで提供されています。

1.2. ROUTEのプロトコルスタック

The session metadata signaling to realize a ROUTE session as specified in this document MAY be delivered out of band or in band as well. Since ROUTE delivers objects in an application cache at the receiver from where the application can access them using HTTP, an application like DASH may use its standardized unicast streaming mechanisms in conjunction with ROUTE over broadcast/multicast to augment the services.

Table 1に示すように、ROUTEは、UDP/IPネットワーク上で動作し、MPEG DASHやHLSのセグメントなどのアプリケーションオブジェクトと、任意でそれに関連するリペアデータを配送します。この文書で規定するROUTEセッションを実現するためのセッションメタデータのシグナリングは、帯域外でも帯域内でも配送してもよいです（MAY）。ROUTEは、受信者のアプリケーションキャッシュにオブジェクトを配送し、アプリケーションはそこからHTTPを使用してオブジェクトにアクセスできるため、DASHのようなアプリケーションは、標準化されたユニキャストストリーミングのメカニズムを、ブロードキャスト／マルチキャスト上のROUTEと組み合わせて使用することで、サービスを拡張できます。

1.3. Data Model

1.3. データモデル

The ROUTE data model is constituted by the following key concepts.

ROUTEのデータモデルは、次の主要な概念で構成されます。

Application Object:
data that has meaning to the application that uses the ROUTE protocol for delivery of data to receivers, e.g., an Application Object can be a file, a DASH video segment, a WAV audio clip, an MPEG-4 video clip, etc.
Delivery Object:
an object on course of delivery to the application from the ROUTE sender to ROUTE receiver.
Transport Object:
an object identified by the Transport Object Identifier (TOI) in RFC 5651 [RFC5651]. It MAY be either a source or a repair object, depending on if it is carried by a Source Flow or a Repair Flow, respectively.
Transport Session:
a Layered Coding Transport (LCT) channel, as defined by RFC 5651 [RFC5651]. A Transport Session SHALL be uniquely identified by a unique Transport Session Identifier (TSI) value in the LCT header. The TSI is scoped by the IP address of the sender, and the IP address of the sender together with the TSI uniquely identify the session. Transport Sessions are a subset of a ROUTE session. For media delivery, a Transport Session would typically carry a media component, for example, a DASH Representation. Within each Transport Session, one or more objects are carried, typically objects that are related, e.g., DASH segments associated to one Representation.
ROUTE Session:
an ensemble or multiplex of one or more Transport Sessions. Each ROUTE session is associated with an IP address/port combination. A ROUTE session typically carries one or more media components of streaming media e.g., Representations associated with a DASH Media Presentation.
Source Flow:
a Transport Session carrying source data. Source Flow is independent of the Repair Flow, i.e., the Source Flow MAY be used by a ROUTE receiver without the ROUTE Repair Flows.
Repair Flow:
a Transport Session carrying repair data for one or more Source Flows.
アプリケーションオブジェクト（Application Object）：
受信者へのデータ配送にROUTEプロトコルを使用するアプリケーションにとって意味を持つデータです。たとえば、アプリケーションオブジェクトは、ファイル、DASHビデオセグメント、WAVオーディオクリップ、MPEG-4ビデオクリップなどです。
配送オブジェクト（Delivery Object）：
ROUTE送信者からROUTE受信者を経てアプリケーションへ配送される途中のオブジェクトです。
トランスポートオブジェクト（Transport Object）：
RFC 5651 [RFC5651]のトランスポートオブジェクト識別子（Transport Object Identifier、TOI）によって識別されるオブジェクトです。これは、ソースフローとリペアフローのどちらで運ばれるかに応じて、それぞれソースオブジェクトかリペアオブジェクトのいずれかであってもよいです（MAY）。
トランスポートセッション（Transport Session）：
RFC 5651 [RFC5651]で定義されている階層化符号化トランスポート（Layered Coding Transport、LCT）チャネルです。トランスポートセッションは、LCTヘッダー内の一意なトランスポートセッション識別子（Transport Session Identifier、TSI）の値によって一意に識別することになります（SHALL）。TSIのスコープは送信者のIPアドレスであり、送信者のIPアドレスとTSIの組み合わせがセッションを一意に識別します。トランスポートセッションは、ROUTEセッションのサブセットです。メディア配送では、トランスポートセッションは通常、1つのメディアコンポーネント、たとえば1つのDASHのRepresentationを運びます。各トランスポートセッション内では1つ以上のオブジェクトが運ばれ、それらは通常、関連するオブジェクト、たとえば1つのRepresentationに関連付けられたDASHセグメントです。
ROUTEセッション（ROUTE Session）：
1つ以上のトランスポートセッションの集合、または多重化です。各ROUTEセッションは、IPアドレスとポートの組み合わせに関連付けられます。ROUTEセッションは通常、ストリーミングメディアの1つ以上のメディアコンポーネント、たとえばDASHのMedia Presentationに関連付けられたRepresentationを運びます。
ソースフロー（Source Flow）：
ソースデータを運ぶトランスポートセッションです。ソースフローはリペアフローから独立しています。すなわち、ROUTE受信者は、ROUTEリペアフローなしでソースフローを使用してもよいです（MAY）。
リペアフロー（Repair Flow）：
1つ以上のソースフローのためのリペアデータを運ぶトランスポートセッションです。

1.4. Architecture and Scope of Specification

1.4. アーキテクチャーと仕様の範囲

The scope of the ROUTE protocol is to enable robust and real-time transport of delivery objects using LCT packets. This architecture is depicted in Figure 1.

ROUTEプロトコルの範囲は、LCTパケットを使用して配送オブジェクトの堅牢かつリアルタイムなトランスポートを実現することです。このアーキテクチャーをFigure 1に示します。

The normative aspects of the ROUTE protocol focus on the following aspects:

ROUTEプロトコルの規範的な側面は、次の点に重点を置いています。

  • The format of the LCT packets that carry the transport objects.
  • The robust transport of the delivery object using a repair protocol based on Forward Error Correction (FEC).
  • The definition and possible carriage of object metadata along with the delivery objects. Metadata may be conveyed in LCT packets and/or separate objects.
  • The ROUTE session, LCT channel, and delivery object description provided as service metadata signaling to enable the reception of objects.
  • The normative aspects (formats, semantics) of the delivery objects conveyed as a content manifest to be delivered along with the objects to optimize the performance for specific applications e.g., real-time delivery. The objects and manifest are made available to the application through an Application Object cache. The interface of this cache to the application is not specified in this document; however, it will typically be enabled by the application acting as an HTTP client and the cache as the HTTP server.
  • トランスポートオブジェクトを運ぶLCTパケットの形式
  • 前方誤り訂正（FEC）に基づくリペアプロトコルを使用した、配送オブジェクトの堅牢なトランスポート
  • オブジェクトのメタデータの定義と、配送オブジェクトとともにそれを運ぶ方法。メタデータは、LCTパケットや別個のオブジェクトで伝達されることがあります。
  • オブジェクトの受信を可能にするために、サービスメタデータのシグナリングとして提供される、ROUTEセッション、LCTチャネル、配送オブジェクトの記述
  • 特定のアプリケーション（たとえば、リアルタイム配送）のために性能を最適化する目的で、オブジェクトとともに配送されるコンテンツマニフェストとして伝達される、配送オブジェクトの規範的な側面（形式、セマンティクス）。オブジェクトとマニフェストは、アプリケーションオブジェクトキャッシュを通じてアプリケーションに提供されます。このキャッシュのアプリケーションに対するインターフェイスはこの文書では規定しませんが、通常は、アプリケーションがHTTPクライアントとして動作し、キャッシュがHTTPサーバーとして動作することで実現されます。

4. Delivery Object Mode

4. 配送オブジェクトモード

ROUTE provides several different delivery object modes, and one of these modes may suit the application needs better for a given Transport Session. A delivery object is self contained for the application, typically associated with certain properties, metadata, and timing-related information relevant to the application. The signaling of the delivery object mode is done on an object basis using Codepoint as specified in Section 2.1.

ROUTEは複数の異なる配送オブジェクトモードを提供しており、あるトランスポートセッションでは、これらのモードのいずれかがアプリケーションのニーズにより適している場合があります。配送オブジェクトはアプリケーションにとって自己完結しており、通常は、アプリケーションに関連する特定のプロパティー、メタデータ、タイミング関連の情報と関連付けられています。配送オブジェクトモードのシグナリングは、Section 2.1で規定されているコードポイントを使用して、オブジェクト単位で行われます。

4.1. File Mode

4.1. ファイルモード

File Mode uses an out-of-band Extended FDT (EFDT) signaling for recovery of delivery objects with the following extensions and considerations.

ファイルモードは、配送オブジェクトの復元のために、以下の拡張と考慮事項を伴う帯域外の拡張FDT（Extended FDT、EFDT）のシグナリングを使用します。

4.1.1. Extensions to FDT

4.1.1. FDTの拡張

The following extensions are specified to FDT, as specified in RFC 6726 [RFC6726]. An Extended FDT-Instance is an instance of FLUTE FDT, as specified in [RFC6726], plus optionally one or more of the following extensions:

RFC 6726 [RFC6726]で規定されているFDTに対して、次の拡張を規定します。拡張FDT-Instanceは、[RFC6726]で規定されているFLUTEのFDTのインスタンスに、任意で次の拡張の1つ以上を加えたものです。

efdtVersion:
A value that SHALL represent the version of this Extended FDT-Instance.
maxExpiresDelta:
Let "tp" represent the wall clock time at the receiver when the receiver acquires the first ROUTE packet carrying data of the object described by this Extended FDT-Instance. maxExpiresDelta, when present, SHALL represent a time interval that when added to "tp" SHALL represent the expiration time of the associated Extended FDT-Instance "te". The time interval is expressed in number of seconds. When maxExpiresDelta is not present, the expiration time of the Extended FDT-Instance SHALL be given by the sum of a) the value of the ERT field in the EXT_TIME LCT header extension in the first ROUTE packet carrying data of that file, and b) the current receiver time when parsing the packet header of that ROUTE packet. See Sections 5.4 and 6.3.3 on additional rules for deriving the Extended FDT-Instance expiration time. Hence, te = tp + maxExpiresDelta
maxTransportSize:
An attribute that SHALL represent the maximum transport size in bytes of any delivery object described by this Extended FDT-Instance. This attribute SHALL be present if a) the fileTemplate is present in Extended FDT-Instance, or b) one or more File elements, if present in this Extended FDT-Instance, do not include the Transfer-Length attribute. When maxTransportSize is not present, the maximum transport size is not signaled, while other signaling such as the Transfer-Length attribute signal the exact Transfer Length of the object.
fileTemplate:
A string value, which when present and in conjunction with parameter substitution, is used in deriving the Content-Location attribute for the delivery object described by this Extended FDT-Instance. It SHALL include the "$TOI$" identifier. Each identifier MAY be suffixed as needed by specific file names within the enclosing '$' characters following this prototype: %0[width]d
efdtVersion:
値です。この値は、この拡張FDT-Instanceのバージョンを表すものとすることになります（SHALL）。
maxExpiresDelta:
受信者が、この拡張FDT-Instanceで記述されるオブジェクトのデータを運ぶ最初のROUTEパケットを取得したときの、受信者における実時間（wall clock time）を「tp」とします。maxExpiresDeltaが存在する場合、これは時間間隔を表すものとすることになります（SHALL）。この時間間隔を「tp」に加えたものが、関連する拡張FDT-Instanceの有効期限「te」を表すものとすることになります（SHALL）。この時間間隔は秒数で表現されます。maxExpiresDeltaが存在しない場合、拡張FDT-Instanceの有効期限は、a）そのファイルのデータを運ぶ最初のROUTEパケットのEXT_TIME LCTヘッダー拡張内のERTフィールドの値と、b）そのROUTEパケットのパケットヘッダーを解析した時点の受信者の現在時刻との和で与えられるものとすることになります（SHALL）。拡張FDT-Instanceの有効期限を導出するための追加の規則については、セクション5.4と6.3.3を参照してください。したがって、te = tp + maxExpiresDeltaとなります。
maxTransportSize:
属性です。この属性は、この拡張FDT-Instanceで記述される任意の配送オブジェクトの、バイト単位の最大トランスポートサイズを表すものとすることになります（SHALL）。この属性は、a）拡張FDT-InstanceにfileTemplateが存在する場合、またはb）この拡張FDT-Instanceに存在する1つ以上のFile要素がTransfer-Length属性を含まない場合に、存在することになります（SHALL）。maxTransportSizeが存在しない場合、最大トランスポートサイズはシグナリングされませんが、Transfer-Length属性などの他のシグナリングによってオブジェクトの正確な転送長がシグナリングされます。
fileTemplate:
文字列値です。存在する場合、パラメーター置換と組み合わせて、この拡張FDT-Instanceで記述される配送オブジェクトのContent-Location属性を導出するために使用されます。この文字列は「$TOI$」識別子を含むものとすることになります（SHALL）。各識別子には、囲んでいる「$」文字の内側に、次のプロトタイプに従って、必要に応じて特定のファイル名による接尾辞を付けてもよいです（MAY）：%0[width]d

The width parameter is an unsigned integer that provides the minimum number of characters to be printed. If the value to be printed is shorter than this number, the result SHALL be padded with leading zeroes. The value is not truncated even if the result is larger. When no format tag is present, a default format tag with width=1 SHALL be used.

widthパラメーターは、出力する最小文字数を指定する符号なし整数です。出力する値がこの数より短い場合、結果は先頭をゼロで埋めるものとすることになります（SHALL）。結果がこの数より長い場合でも、値は切り詰められません。書式タグが存在しない場合は、width=1のデフォルトの書式タグを使用することになります（SHALL）。

Strings other than identifiers SHALL only contain characters that are permitted within URIs according to RFC 3986 [RFC3986].

識別子以外の文字列は、RFC 3986 [RFC3986]に従ってURI内で許可されている文字のみを含むものとすることになります（SHALL）。

$$ is an escape sequence in fileTemplate value, i.e., "$$" is non-recursively replaced with a single "$".

$$はfileTemplate値におけるエスケープシーケンスです。すなわち、「$$」は再帰的にではなく、単一の「$」に置き換えられます。

The usage of fileTemplate is described in Sender and Receiver operations in Sections 5.4 and 6.3, respectively.

fileTemplateの使用法は、送信者と受信者の動作として、それぞれセクション5.4と6.3で説明します。

4.1.2. Constraints on Extended FDT

4.1.2. 拡張FDTに対する制約

The Extended FDT-Instance SHALL conform to an FDT-Instance according to RFC 6726 [RFC6726] with the following constraints: at least one File element and the @Expires attribute SHALL be present.

拡張FDT-Instanceは、RFC 6726 [RFC6726]に従ったFDT-Instanceに、次の制約付きで準拠することになります（SHALL）。この制約として、少なくとも1つのFile要素と@Expires属性が存在することになります（SHALL）。

Content encoding MAY be used for delivery of any file described by an FDT-Instance.File element in the Extended FDT-Instance. The content encoding defined in the present document is gzip [RFC1952]. When content encoding is used, the File@Content-Encoding and File@Content-Length attributes SHALL be present in the Extended FDT-Instance.

拡張FDT-Instance内のFDT-Instance.File要素で記述される任意のファイルの配送には、コンテンツエンコーディングを使用してもよいです（MAY）。この文書で定義するコンテンツエンコーディングはgzip [RFC1952]です。コンテンツエンコーディングを使用する場合、拡張FDT-InstanceにはFile@Content-Encoding属性とFile@Content-Length属性が存在することになります（SHALL）。

4.2. Entity Mode

4.2. エンティティーモード

For Entity Mode, the following applies:

エンティティーモードには、次のことが適用されます。

  • Delivery object metadata SHALL be expressed in the form of entity headers as defined in HTTP/1.1, which correspond to one or more of the representation header fields, payload header fields, and response header fields as defined in Sections 3.1, 3.3, and 7, respectively, of [RFC7231].
  • The entity headers sent along with the delivery object provide all information about that multicast transport object.

  • Sending a media object (if the object is chunked) in Entity Mode may result in one of the following options:

    • If the length of the chunked object is known at the sender, the ROUTE Entity Mode delivery object MAY be sent without using HTTP/1.1 chunked transfer coding, i.e., the object starts with an HTTP header containing the Content Length field followed by the concatenation of CMAF Chunks:

      |HTTP Header+Length||---chunk ----||---chunk ----||---chunk --
--||---chunk ----|

    • If the length of the chunked object is unknown at the sender when starting to send the object, HTTP/1.1 chunked transfer coding format SHALL be used:

      |HTTP Header||Separator+Length||---chunk ----
||Separator+Length||---chunk ----||Separator+Length||---chunk
----||Separator+Length||---chunk ----||Separator+Length=0|

      Note, however, that it is not required to send a CMAF Chunk in exactly one HTTP chunk.

  • 配送オブジェクトのメタデータは、HTTP/1.1で定義されているエンティティーヘッダーの形式で表現することになります（SHALL）。エンティティーヘッダーは、[RFC7231]のセクション3.1、3.3、7でそれぞれ定義されている表現ヘッダーフィールド、ペイロードヘッダーフィールド、レスポンスヘッダーフィールドの1つ以上に対応します。
  • 配送オブジェクトとともに送信されるエンティティーヘッダーは、そのマルチキャストトランスポートオブジェクトに関するすべての情報を提供します。

  • エンティティーモードでメディアオブジェクトを送信すると（オブジェクトがチャンク化されている場合）、次のいずれかの方法になります。

    • チャンク化されたオブジェクトの長さが送信者にわかっている場合、ROUTEのエンティティーモードの配送オブジェクトは、HTTP/1.1のチャンク転送コーディングを使用せずに送信してもよいです（MAY）。すなわち、オブジェクトはContent Lengthフィールドを含むHTTPヘッダーで始まり、その後にCMAFチャンクを連結したものが続きます。

      |HTTP Header+Length||---chunk ----||---chunk ----||---chunk --
--||---chunk ----|

    • オブジェクトの送信を開始する時点で、チャンク化されたオブジェクトの長さが送信者にわかっていない場合は、HTTP/1.1のチャンク転送コーディング形式を使用することになります（SHALL）。

      |HTTP Header||Separator+Length||---chunk ----
||Separator+Length||---chunk ----||Separator+Length||---chunk
----||Separator+Length||---chunk ----||Separator+Length=0|

      ただし、1つのCMAFチャンクをちょうど1つのHTTPチャンクで送信する必要はないことに注意してください。

4.3. Unsigned Package Mode

4.3. 署名なしパッケージモード

In this delivery mode, the delivery object consists of a group of files that are packaged for delivery only. If applied, the client is expected to unpack the package and provide each file as an independent object to the application. Packaging is supported by Multipart Multipurpose Internet Mail Extensions (MIME) [RFC2557], where objects are packaged into one document for transport, with Content-Type set to multipart/related. When binary files are included in the package, Content-Transfer-Encoding of "binary" should be used for those files.

この配送モードでは、配送オブジェクトは、配送のためだけにパッケージ化されたファイルのグループで構成されます。このモードを適用する場合、クライアントはパッケージを展開し、各ファイルを独立したオブジェクトとしてアプリケーションに提供することが期待されます。パッケージ化はマルチパートMIME（Multipurpose Internet Mail Extensions）[RFC2557]によってサポートされます。そこでは、オブジェクトはトランスポートのために1つの文書にパッケージ化され、Content-Typeはmultipart/relatedに設定されます。パッケージにバイナリーファイルが含まれる場合、それらのファイルには「binary」のContent-Transfer-Encodingを使用すべきです。

4.4. Signed Package Mode

4.4. 署名付きパッケージモード

In Signed Package Mode delivery, the delivery object consists of a group of files that are packaged for delivery, and the package includes one or more signatures for validation. Signed packaging is supported by RFC 8551 Secure MIME (S/MIME) [RFC8551], where objects are packaged into one document for transport and the package includes objects necessary for validation of the package.

署名付きパッケージモードの配送では、配送オブジェクトは配送のためにパッケージ化されたファイルのグループで構成され、そのパッケージには検証のための1つ以上の署名が含まれます。署名付きパッケージ化は、RFC 8551のSecure MIME（S/MIME）[RFC8551]によってサポートされます。そこでは、オブジェクトはトランスポートのために1つの文書にパッケージ化され、パッケージにはそのパッケージの検証に必要なオブジェクトが含まれます。

5. Sender Operation

5. 送信者の動作

5.1. Usage of ALC and LCT for Source Flow

5.1. ソースフローにおけるALCとLCTの使用法

ROUTE Source Flow carries the source data as specified in RFC 5775 [RFC5775]. There are several special considerations that ROUTE introduces to the usage of the LCT building block as outlined in the following:

ROUTEのソースフローは、RFC 5775 [RFC5775]で規定されているとおりにソースデータを運びます。ROUTEは、LCTビルディングブロックの使用法について、以下に概説するいくつかの特別な考慮事項を導入しています。

  • ROUTE limits the usage of the LCT building block to a single channel per session. Congestion control is thus sender driven in ROUTE. It also signifies that there is no specific congestion-control-related signaling from the sender to the receiver; the CCI field is either set to 0 or used for other purposes as specified in Section 2.1. The functionality of receiver-driven layered multicast may still be offered by the application, allowing the receiver application to select the appropriate delivery session based on the bandwidth requirement of that session.
  • ROUTEは、LCTビルディングブロックの使用を、セッションごとに単一のチャネルに制限します。したがって、ROUTEでは輻輳制御は送信者主導です。これは、送信者から受信者への輻輳制御に関する特別なシグナリングが存在しないことも意味します。CCIフィールドは、0に設定されるか、Section 2.1で規定されているように他の目的に使用されます。それでも、受信者主導の階層化マルチキャストの機能をアプリケーションが提供し、受信者のアプリケーションが、配送セッションの帯域幅要件に基づいて適切な配送セッションを選択できるようにすることは可能です。

Further, the following details apply to LCT:

さらに、LCTには次の詳細が適用されます。

  • The Layered Coding Transport (LCT) Building Block as defined in RFC 5651 [RFC5651] is used with the following constraints:

    • The TSI in the LCT header SHALL be set equal to the value of the stsi attribute in Section 3.2.
    • The Codepoint (CP) in the LCT header SHALL be used to signal the applied formatting as defined in the signaling metadata.

    • In accordance with ALC, a source FEC Payload ID header is used to identify, for FEC purposes, the encoding symbols of the delivery object, or a portion thereof, carried by the associated ROUTE packet. This information may be sent in several ways:

      • As a simple new null FEC scheme with the following usage:

        • The value of the source FEC Payload ID header SHALL be set to 0 in case the ROUTE packet contains the entire delivery object, or
        • The value of the source FEC Payload ID header SHALL be set as a direct address (start offset) corresponding to the starting byte position of the portion of the object carried in this packet using a 32-bit field.
      • In a compatible manner to RFC 6330 [RFC6330] where the SBN and ESI defines the start offset together with the symbol size T.
      • The signaling metadata provides the appropriate parameters to indicate any of the above modes using the srcFecPayloadId attribute.

  • The LCT Header EXT_TIME extension as defined in RFC 5651 [RFC5651] MAY be used by the sender in the following manner:

    • The Sender Current Time (SCT), depending on the application, MAY be used to occasionally or frequently signal the sender current time possibly for reliever time synchronization.
    • The Expected Residual Time (ERT) MAY be used to indicate the expected remaining time for transmission of the current object in order to optimize detection of a lost delivery object.
    • The Sender Last Changed (SLC) flag is typically not utilized but MAY be used to indicate the addition/removal of Segments.

  • RFC 5651 [RFC5651]で定義されている階層化符号化トランスポート（LCT）ビルディングブロックを、次の制約付きで使用します。

    • LCTヘッダー内のTSIは、Section 3.2のstsi属性の値と等しく設定することになります（SHALL）。
    • LCTヘッダー内のコードポイント（CP）は、シグナリングメタデータで定義されている、適用された形式をシグナリングするために使用することになります（SHALL）。

    • ALCに従い、関連するROUTEパケットで運ばれる配送オブジェクトまたはその一部のエンコーディングシンボルを、FECの目的で識別するために、ソースFECペイロードIDヘッダーを使用します。この情報は、いくつかの方法で送信できます。

      • 次のように使用する、単純な新しいヌルFECスキームとして：

        • ROUTEパケットが配送オブジェクト全体を含む場合、ソースFECペイロードIDヘッダーの値は0に設定することになります（SHALL）。または、
        • ソースFECペイロードIDヘッダーの値は、32ビットのフィールドを使用して、このパケットで運ばれるオブジェクトの部分の開始バイト位置に対応する直接アドレス（開始オフセット）として設定することになります（SHALL）。
      • RFC 6330 [RFC6330]と互換性のある方法として。この場合、SBNとESIが、シンボルサイズTとともに開始オフセットを定義します。
      • シグナリングメタデータは、srcFecPayloadId属性を使用して、上記のいずれかのモードを示すための適切なパラメーターを提供します。

  • RFC 5651 [RFC5651]で定義されているLCTヘッダーのEXT_TIME拡張は、送信者が次のように使用してもよいです（MAY）。

    • 送信者の現在時刻（Sender Current Time、SCT）は、アプリケーションに応じて、場合によっては受信者の時刻同期のために、送信者の現在時刻をときどき、または頻繁にシグナリングする目的で使用してもよいです（MAY）。
    • 予想残り時間（Expected Residual Time、ERT）は、失われた配送オブジェクトの検出を最適化するために、現在のオブジェクトの送信に予想される残り時間を示す目的で使用してもよいです（MAY）。
    • 送信者最終変更（Sender Last Changed、SLC）フラグは通常は利用されませんが、セグメントの追加や削除を示すために使用してもよいです（MAY）。

Additional extension headers MAY be used to support real-time delivery. Such extension headers are defined in Section 2.1.

リアルタイム配送をサポートするために、追加の拡張ヘッダーを使用してもよいです（MAY）。そのような拡張ヘッダーはSection 2.1で定義されています。

5.2. ROUTE Packetization for Source Flow

5.2. ソースフローのROUTEパケット化

The following description of the ROUTE sender operation on the mapping of the Application Object to the ROUTE packet payloads logically represents an extension of RFC 5445 [RFC5445], which in turn inherits the context, language, declarations, and restrictions of the FEC building block in RFC 5052 [RFC5052].

アプリケーションオブジェクトのROUTEパケットペイロードへの対応付けに関する、以下のROUTE送信者の動作の説明は、論理的にはRFC 5445 [RFC5445]の拡張を表しています。RFC 5445は、RFC 5052 [RFC5052]のFECビルディングブロックのコンテキスト、用語、宣言、制限を継承しています。

The data carried in the payload of a given ROUTE packet constitutes a contiguous portion of the Application Object. ROUTE source delivery can be considered as a special case of the use of the Compact No-Code Scheme associated with FEC Encoding ID = 0 according to Sections 3.4.1 and 3.4.2 of [RFC5445], in which the encoding symbol size is exactly one byte. As specified in Section 2.1, for ROUTE Source Flows, the FEC Payload ID SHALL deliver the 32-bit start_offset. All receivers are expected to support, at minimum, operation with this special case of the Compact No-Code FEC.

あるROUTEパケットのペイロードで運ばれるデータは、アプリケーションオブジェクトの連続した一部分を構成します。ROUTEのソース配送は、[RFC5445]のセクション3.4.1と3.4.2に従った、FEC Encoding ID = 0に関連付けられたCompact No-Codeスキームの使用の特殊なケースとみなすことができます。このケースでは、エンコーディングシンボルのサイズはちょうど1バイトです。Section 2.1で規定されているように、ROUTEのソースフローでは、FECペイロードIDは32ビットのstart_offsetを伝達することになります（SHALL）。すべての受信者は、少なくとも、Compact No-Code FECのこの特殊なケースでの動作をサポートすることが期待されます。

Note that in the event the source object size is greater than 232 bytes (approximately 4.3 GB), the applications (in the broadcaster server and the receiver) are expected to perform segmentation/reassembly using methods beyond the scope of this document.

ソースオブジェクトのサイズが232バイト（約4.3GB）を超える場合、（放送事業者のサーバーと受信者の）アプリケーションは、この文書の範囲外の方法を使用して分割と再構成を行うことが期待されることに注意してください。

Finally, in some special cases, a ROUTE sender MAY need to produce ROUTE packets that do not contain any payload. This may be required, for example, to signal the end of a session. These dataless packets do not contain FEC Payload ID or payload data, but only the LCT header fields. The total datagram length, conveyed by outer protocol headers (e.g., the IP or UDP header), enables receivers to detect the absence of the LCT header, FEC Payload ID, and payload data.

最後に、いくつかの特殊なケースでは、ROUTE送信者はペイロードを含まないROUTEパケットを生成する必要がある場合があります（MAY）。これは、たとえばセッションの終了をシグナリングするために必要になることがあります。これらのデータなしのパケットは、FECペイロードIDやペイロードデータを含まず、LCTヘッダーフィールドのみを含みます。外側のプロトコルのヘッダー（たとえば、IPヘッダーやUDPヘッダー）で伝達されるデータグラムの全長によって、受信者はLCTヘッダー、FECペイロードID、ペイロードデータが存在しないことを検出できます。

5.2.1. Basic ROUTE Packetization

5.2.1. 基本的なROUTEパケット化

In the basic operation, it is assumed that the Application Object is fully available at the ROUTE sender.

基本的な動作では、アプリケーションオブジェクトがROUTE送信者において完全に利用可能であることを前提とします。

  1. The amount of data to be sent in a single ROUTE packet is limited by the maximum transfer unit of the data packets or the size of the remaining data of the Application Object being sent, whichever is smaller. The transfer unit is determined either by knowledge of underlying transport block sizes or by other constraints.
  2. The start_offset field in the LCT header of the ROUTE packet indicates the byte offset of the carried data in the Application Object being sent.
  3. The Close Object flag (B) is set to 1 if this is the last ROUTE packet carrying the data of the Application Object.
  1. 単一のROUTEパケットで送信されるデータの量は、データパケットの最大転送単位と、送信中のアプリケーションオブジェクトの残りのデータのサイズのうち、小さいほうによって制限されます。転送単位は、下位のトランスポートのブロックサイズに関する知識、またはその他の制約によって決定されます。
  2. ROUTEパケットのLCTヘッダー内のstart_offsetフィールドは、送信中のアプリケーションオブジェクトにおける、運ばれるデータのバイトオフセットを示します。
  3. オブジェクトクローズフラグ（B）は、これがアプリケーションオブジェクトのデータを運ぶ最後のROUTEパケットである場合に1に設定されます。

The order of packet delivery is arbitrary, but in the absence of other constraints, delivery with increasing start_offset value is recommended.

パケットの配送の順序は任意ですが、他の制約がない場合は、start_offset値の昇順での配送が推奨されます。

5.2.2. ROUTE Packetization for CMAF Chunked Content

5.2.2. CMAFチャンク化コンテンツのROUTEパケット化

The following additional guidelines should be followed for ROUTE packetization of CMAF Chunked Content in addition to the guidelines of Section 5.2.1:

CMAFチャンク化コンテンツ（CMAF Chunked Content）のROUTEパケット化では、Section 5.2.1のガイドラインに加えて、次の追加のガイドラインに従うべきです。

  1. If it is the first ROUTE packet carrying a CMAF Random Access chunk, except for the first CMAF Chunk in the segment, the Codepoint value MAY be set to 10, as specified in the Codepoint value table in Section 2.1. The receiver MAY use this information for optimization of random access.
  2. As soon as the total length of the media object is known, potentially with the packaging of the last CMAF Chunk of a segment, the EXT_TOL extension header MAY be added to the LCT header to signal the Transfer Length, so that the receiver may know this information in a timely fashion.
  1. CMAFランダムアクセスチャンクを運ぶ最初のROUTEパケットである場合、セグメント内の最初のCMAFチャンクを除いて、Section 2.1のコードポイント値の表で規定されているように、コードポイント値を10に設定してもよいです（MAY）。受信者は、この情報をランダムアクセスの最適化に使用してもよいです（MAY）。
  2. メディアオブジェクトの全長がわかったらすぐに（場合によってはセグメントの最後のCMAFチャンクのパッケージ化の際に）、受信者がこの情報をタイムリーに知ることができるように、転送長をシグナリングするためにEXT_TOL拡張ヘッダーをLCTヘッダーに追加してもよいです（MAY）。

5.3. Timing of Packet Emission

5.3. パケット送出のタイミング

The sender SHALL use the timing information provided by the application to time the emission of packets for a timely reception. This information may be contained in the Application Objects e.g., DASH segments and/or the presentation manifest. Hence, such packets of streaming media with real-time constraints SHALL be sent in such a way as to enable their timely reception with respect to the presentation timeline.

送信者は、タイムリーな受信のためのパケット送出のタイミングを決めるために、アプリケーションが提供するタイミング情報を使用することになります（SHALL）。この情報は、アプリケーションオブジェクト（たとえば、DASHセグメント）やプレゼンテーションマニフェストに含まれていることがあります。したがって、リアルタイムの制約を持つストリーミングメディアのそのようなパケットは、プレゼンテーションのタイムラインに対してタイムリーに受信できるような方法で送信することになります（SHALL）。

5.4. Extended FDT Encoding for File Mode Sending

5.4. ファイルモード送信のための拡張FDTエンコーディング

For File Mode sending:

ファイルモードの送信では：

  • The TOI field in the ROUTE packet header SHALL be set such that Content-Location can be derived at the receiver according to File Template substitution specified in Section 6.3.1.
  • After sending the first packet with a given TOI value, none of the packets pertaining to this TOI SHALL be sent later than the wall clock time as derived from maxExpiresDelta. The EXT_TIME header with Expected Residual Time (ERT) MAY be used in order to convey more accurate expiry time.
  • ROUTEパケットヘッダー内のTOIフィールドは、Section 6.3.1で規定されているファイルテンプレートの置換に従って、受信者がContent-Locationを導出できるように設定することになります（SHALL）。
  • あるTOI値を持つ最初のパケットを送信した後、このTOIに関連するすべてのパケットは、maxExpiresDeltaから導出される実時間までに送信することになります（SHALL）。より正確な有効期限を伝達するために、予想残り時間（ERT）を持つEXT_TIMEヘッダーを使用してもよいです（MAY）。

5.5. FEC Framework Considerations

5.5. FECフレームワークに関する考慮事項

The FEC framework uses concepts of the FECFRAME work as defined in RFC 6363 [RFC6363], as well as the FEC building block, RFC 5052 [RFC5052], which is adopted in the existing FLUTE/ALC/LCT specifications.

FECフレームワークは、RFC 6363 [RFC6363]で定義されているFECFRAMEの作業の概念と、既存のFLUTE/ALC/LCT仕様で採用されているFECビルディングブロック（RFC 5052 [RFC5052]）の概念を使用します。

The FEC design adheres to the following principles:

FECの設計は、次の原則に従います。

  • FEC-related information is provided only where needed.
  • Receivers not capable of this framework can ignore repair packets.
  • The FEC is symbol based with fixed symbol size per protected Source Flow. The ALC protocol and existing FEC schemes are reused.
  • A FEC Repair Flow provides protection of delivery objects from one or more Source Flows.
  • FEC関連の情報は、必要な場合にのみ提供されます。
  • このフレームワークに対応していない受信者は、リペアパケットを無視できます。
  • FECはシンボルベースであり、保護されるソースフローごとにシンボルサイズは固定です。ALCプロトコルと既存のFECスキームを再利用します。
  • FECリペアフローは、1つ以上のソースフローからの配送オブジェクトを保護します。

The FEC-specific components of the FEC framework are:

FECフレームワークのFEC固有のコンポーネントは次のとおりです。

  • FEC Repair Flow declaration including all FEC-specific information.
  • A FEC transport object that is the concatenation of a delivery object, padding octets, and size information in order to form a chunk of data that has a size in symbols of N, where N >= 1.
  • A FEC super-object that is the concatenation of one or more FEC transport objects in order to bundle FEC transport objects for FEC protection.
  • A FEC protocol and packet structure.
  • FEC固有のすべての情報を含む、FECリペアフローの宣言
  • FECトランスポートオブジェクト。これは、シンボル単位のサイズがN（N >= 1）であるデータのまとまりを形成するために、配送オブジェクト、パディングオクテット、サイズ情報を連結したものです。
  • FECスーパーオブジェクト。これは、FEC保護のためにFECトランスポートオブジェクトを束ねる目的で、1つ以上のFECトランスポートオブジェクトを連結したものです。
  • FECプロトコルとパケット構造

A receiver needs to be able to recover delivery objects from repair packets based on available FEC information.

受信者は、利用可能なFEC情報に基づいて、リペアパケットから配送オブジェクトを復元できる必要があります。

5.6. FEC Transport Object Construction

5.6. FECトランスポートオブジェクトの構築

In order to identify a delivery object in the context of the repair protocol, the following information is needed:

リペアプロトコルのコンテキストで配送オブジェクトを識別するためには、次の情報が必要です。

  • TSI and TOI of the delivery object. In this case, the FEC object corresponds to the (entire) delivery object.
  • Octet range of the delivery object, i.e., start offset within the delivery object and number of subsequent and contiguous octets of delivery object that constitutes the FEC object (i.e., the FEC-protected portion of the source object). In this case, the FEC object corresponds to a contiguous byte range portion of the delivery object.
  • 配送オブジェクトのTSIとTOI。この場合、FECオブジェクトは配送オブジェクト（全体）に対応します。
  • 配送オブジェクトのオクテット範囲。すなわち、配送オブジェクト内の開始オフセットと、FECオブジェクト（すなわち、ソースオブジェクトのうちFECで保護される部分）を構成する、配送オブジェクトの後続の連続したオクテットの数です。この場合、FECオブジェクトは、配送オブジェクトの連続したバイト範囲の部分に対応します。

Typically, for real-time object delivery with smaller delivery object sizes, the first mapping is applied, i.e., the delivery object is a FEC object.

通常、配送オブジェクトのサイズが小さいリアルタイムのオブジェクト配送では、1つ目の対応付けが適用されます。すなわち、配送オブジェクトがFECオブジェクトとなります。

Assuming that the FEC object is the delivery object, for each delivery object, the associated FEC transport object is comprised of the concatenation of the delivery object, padding octets (P), and the FEC object size (F) in octets, where F is carried in a 4-octet field.

FECオブジェクトが配送オブジェクトであると仮定すると、各配送オブジェクトについて、関連するFECトランスポートオブジェクトは、配送オブジェクト、パディングオクテット（P）、オクテット単位のFECオブジェクトサイズ（F）を連結したもので構成されます。ここで、Fは4オクテットのフィールドで運ばれます。

The FEC transport object size S, in FEC encoding symbols, SHALL be an integer multiple of the symbol size Y. S is determined from the session information and/or the repair packet headers.

FECエンコーディングシンボル単位のFECトランスポートオブジェクトサイズSは、シンボルサイズYの整数倍とすることになります（SHALL）。Sは、セッション情報やリペアパケットのヘッダーから決定されます。

F is carried in the last 4 octets of the FEC transport object. Specifically, let:

Fは、FECトランスポートオブジェクトの最後の4オクテットで運ばれます。具体的には、次のようにします。

  • F be the size of the delivery object in octets,
  • F' be the F octets of data of the delivery object,
  • f' denote the four octets of data carrying the value of F in network octet order (high-order octet first),
  • S be the size of the FEC transport object with S=ceil((F+4)/Y), where the ceil() function rounds the result upward to its nearest integer,
  • P' be S*Y-4-F octets of data, i.e., padding placed between the delivery object and the 4-byte field conveying the value of F and located at the end of the FEC transport object, and
  • O' be the concatenation of F', P', and f'.
  • Fを、配送オブジェクトのオクテット単位のサイズとします。
  • F'を、配送オブジェクトのFオクテットのデータとします。
  • f'を、Fの値をネットワークオクテット順（上位オクテットが先）で運ぶ4オクテットのデータとします。
  • Sを、S=ceil((F+4)/Y)で求められるFECトランスポートオブジェクトのサイズとします。ここで、ceil()関数は結果を最も近い整数に切り上げます。
  • P'を、S*Y-4-Fオクテットのデータとします。すなわち、配送オブジェクトと、FECトランスポートオブジェクトの末尾に位置するFの値を伝達する4バイトのフィールドとの間に置かれるパディングです。
  • O'を、F'、P'、f'を連結したものとします。

O' then constitutes the FEC transport object of size S*Y octets. Note that padding octets and the object size F are not sent in source packets of the delivery object but are only part of a FEC transport object that FEC decoding recovers in order to extract the FEC object and thus the delivery object or portion of the delivery object that constitutes the FEC object. In the above context, the FEC transport object size in symbols is S.

このとき、O'がS*Yオクテットのサイズを持つFECトランスポートオブジェクトを構成します。パディングオクテットとオブジェクトサイズFは、配送オブジェクトのソースパケットでは送信されず、FECオブジェクトを抽出するためにFECデコードが復元するFECトランスポートオブジェクトの一部にすぎないことに注意してください。FECオブジェクトを抽出することで、FECオブジェクトを構成する配送オブジェクトまたは配送オブジェクトの一部が得られます。上記のコンテキストにおいて、シンボル単位のFECトランスポートオブジェクトサイズはSです。

The general information about a FEC transport object that is conveyed to a FEC-enabled receiver is the source TSI, source TOI, and the associated octet range within the delivery object comprising the associated FEC object. However, as the size in octets of the FEC object is provided in the appended field within the FEC transport object, the remaining information can be conveyed as:

FECに対応した受信者に伝達される、FECトランスポートオブジェクトに関する一般的な情報は、ソースのTSI、ソースのTOI、そして関連するFECオブジェクトを構成する、配送オブジェクト内の関連するオクテット範囲です。しかし、FECオブジェクトのオクテット単位のサイズは、FECトランスポートオブジェクト内に付加されたフィールドで提供されるため、残りの情報は次のように伝達できます。

  • The TSI and TOI of the delivery object from which the FEC object associated with the FEC transport object is generated
  • The start octet within the delivery object for the associated FEC object
  • The size in symbols of the FEC transport object, S
  • FECトランスポートオブジェクトに関連付けられたFECオブジェクトの生成元である配送オブジェクトのTSIとTOI
  • 関連するFECオブジェクトの、配送オブジェクト内での開始オクテット
  • FECトランスポートオブジェクトのシンボル単位のサイズS

5.7. Super-Object Construction

5.7. スーパーオブジェクトの構築

From the FEC Repair Flow declaration, the construction of a FEC super-object as the concatenation of one or more FEC transport objects can be determined. The FEC super-object includes the general information about the FEC transport objects as described in the previous sections, as well as the placement order of FEC transport objects within the FEC super-object.

FECリペアフローの宣言から、1つ以上のFECトランスポートオブジェクトを連結したものとしてのFECスーパーオブジェクトの構築を決定できます。FECスーパーオブジェクトには、前のセクションで説明したFECトランスポートオブジェクトに関する一般的な情報と、FECスーパーオブジェクト内でのFECトランスポートオブジェクトの配置順序が含まれます。

Let:

次のようにします。

  • N be the total number of FEC transport objects for the FEC super-object construction.

6.1. Basic Application Object Recovery for Source Flows

6.1. ソースフローにおける基本的なアプリケーションオブジェクトの復元

Upon receipt of each ROUTE packet of a Source Flow, the receiver proceeds with the following steps in the order listed.

ソースフローの各ROUTEパケットを受信すると、受信者は、次の手順を記載された順序で進めます。

  1. The ROUTE receiver is expected to parse the LCT and FEC Payload ID to verify that it is a valid header. If it is not valid, then the payload is discarded without further processing.
  2. All ROUTE packets used to recover a specific delivery object carry the same TOI value in the LCT header.
  3. The ROUTE receiver is expected to assert that the TSI and the Codepoint represent valid operation points in the signaling metadata, i.e., the signaling contains a matching entry to the TSI value provided in the packet header, as well as for this TSI, and the Codepoint field in the LCT header has a valid Codepoint mapping.

  4. The ROUTE receiver should process the remainder of the payload, including the appropriate interpretation of the other payload header fields, using the source FEC Payload ID (to determine the start_offset) and the payload data to reconstruct the corresponding object as follows:

    1. For File Mode, upon receipt of the first ROUTE packet payload for an object, the ROUTE receiver uses the File@Transfer-Length attribute of the associated Extended FDT-Instance, when present, to determine the length T of the object. When the File@Transfer-Length attribute is not present in the Extended FDT-Instance, the receiver uses the maxTransportSize attribute of the associated Extended FDT-Instance to determine the maximum length T' of the object. Alternatively, and specifically for delivery modes other than File Mode, the EXT_TOL header can be used to determine the length T of the object.
    2. The ROUTE receiver allocates buffer space for the T or T' bytes that the object will or may occupy.
    3. The ROUTE receiver computes the length of the payload, Y, by subtracting the payload header length from the total length of the received payload.

    4. The ROUTE receiver allocates a Boolean array RECEIVED[0..T-1] or RECEIVED[0..T'-1], as appropriate, with all entries initialized to false to track received object symbols. The ROUTE receiver continuously acquires packet payloads for the object as long as all of the following conditions are satisfied:

      1. there is at least one entry in RECEIVED still set to false,
      2. the object has not yet expired, and

      3. the application has not given up on reception of this object.

        More details are provided below.

    5. For each received ROUTE packet payload for the object (including the first payload), the steps to be taken to help recover the object are as follows:

      1. If the packet includes an EXT_TOL or EXT_FTI header, modify the Boolean array RECEIVED[0..T'-1] to become RECEIVED[0..T-1].
      2. Let X be the value of the start_offset field in the ROUTE packet header and let Y be the length of the payload, Y, computed by subtracting the LCT header size and the FEC Payload ID size from the total length of the received packet.
      3. The ROUTE receiver copies the data into the appropriate place within the space reserved for the object and sets RECEIVED[X ... X+Y-1] = true.
      4. If all T entries of RECEIVED are true, then the receiver has recovered the entire object.
  1. ROUTE受信者は、LCTとFECペイロードIDを解析して、それが有効なヘッダーであることを検証することが期待されます。有効でない場合、ペイロードはそれ以上処理されずに破棄されます。
  2. 特定の配送オブジェクトを復元するために使用されるすべてのROUTEパケットは、LCTヘッダー内に同じTOI値を持ちます。
  3. ROUTE受信者は、TSIとコードポイントが、シグナリングメタデータ内の有効な動作点を表していることを確認することが期待されます。すなわち、シグナリングに、パケットヘッダーで提供されたTSI値に一致するエントリーが含まれており、かつこのTSIについて、LCTヘッダー内のコードポイントフィールドが有効なコードポイントの対応付けを持っていることです。

  4. ROUTE受信者は、ソースFECペイロードID（start_offsetを決定するため）とペイロードデータを使用して、他のペイロードヘッダーフィールドの適切な解釈を含め、ペイロードの残りの部分を処理し、次のように対応するオブジェクトを再構成すべきです。

    1. ファイルモードの場合、あるオブジェクトの最初のROUTEパケットペイロードを受信すると、ROUTE受信者は、関連する拡張FDT-InstanceのFile@Transfer-Length属性が存在する場合は、それを使用してオブジェクトの長さTを決定します。拡張FDT-InstanceにFile@Transfer-Length属性が存在しない場合、受信者は、関連する拡張FDT-InstanceのmaxTransportSize属性を使用して、オブジェクトの最大長T'を決定します。あるいは、特にファイルモード以外の配送モードでは、EXT_TOLヘッダーを使用してオブジェクトの長さTを決定できます。
    2. ROUTE受信者は、オブジェクトが占める、または占める可能性のあるTバイトまたはT'バイトのバッファー領域を割り当てます。
    3. ROUTE受信者は、受信したペイロードの全長からペイロードヘッダーの長さを引くことで、ペイロードの長さYを計算します。

    4. ROUTE受信者は、受信したオブジェクトのシンボルを追跡するために、すべてのエントリーをfalseに初期化した真偽値の配列RECEIVED[0..T-1]またはRECEIVED[0..T'-1]を必要に応じて割り当てます。ROUTE受信者は、次の条件がすべて満たされている限り、そのオブジェクトのパケットペイロードを継続的に取得します。

      1. RECEIVEDに、まだfalseに設定されているエントリーが少なくとも1つある。
      2. オブジェクトがまだ期限切れになっていない。

      3. アプリケーションがこのオブジェクトの受信を断念していない。

        詳細は以下に示します。

    5. オブジェクトについて受信した各ROUTEパケットペイロード（最初のペイロードを含む）に対して、オブジェクトの復元を助けるために行う手順は次のとおりです。

      1. パケットにEXT_TOLヘッダーまたはEXT_FTIヘッダーが含まれている場合、真偽値の配列RECEIVED[0..T'-1]をRECEIVED[0..T-1]になるように変更します。
      2. XをROUTEパケットヘッダー内のstart_offsetフィールドの値とし、Yを、受信したパケットの全長からLCTヘッダーのサイズとFECペイロードIDのサイズを引いて計算したペイロードの長さYとします。
      3. ROUTE受信者は、オブジェクトのために確保された領域内の適切な位置にデータをコピーし、RECEIVED[X ... X+Y-1] = trueに設定します。
      4. RECEIVEDのT個のエントリーがすべてtrueであれば、受信者はオブジェクト全体を復元したことになります。

Upon recovery of both the complete set of packet payloads for the delivery object associated with a given TOI value, and the metadata for that delivery object, the reception of the delivery object, now a fully received Application Object, is complete.

あるTOI値に関連付けられた配送オブジェクトのパケットペイロードの完全な集合と、その配送オブジェクトのメタデータの両方を復元した時点で、配送オブジェクト（この時点で、完全に受信されたアプリケーションオブジェクト）の受信が完了します。

Given the timely reception of ROUTE packets belonging to an Application Object, the receiver SHALL make the Application Objects available to the application in a timely fashion using the application-provided timing data (e.g., the timing data signaled via the presentation manifest file). For example, HTTP/1.1 chunked transfer may need to be enabled to transfer the Application Objects if MPD@availabilityTimeOffset is signaled in the DASH presentation manifest in order to allow for the timely sending of segment data to the application.

アプリケーションオブジェクトに属するROUTEパケットがタイムリーに受信されていれば、受信者は、アプリケーションが提供するタイミングデータ（たとえば、プレゼンテーションマニフェストファイルを介してシグナリングされるタイミングデータ）を使用して、アプリケーションオブジェクトをタイムリーにアプリケーションに提供することになります（SHALL）。たとえば、DASHのプレゼンテーションマニフェストでMPD@availabilityTimeOffsetがシグナリングされている場合、セグメントデータをタイムリーにアプリケーションに送信できるように、アプリケーションオブジェクトの転送にHTTP/1.1のチャンク転送を有効にする必要があるかもしれません。

6.2. 高速なストリーム取得

When the receiver initially starts reception of ROUTE packets, it is likely that the reception does not start from the very first packet carrying the data of a multicast transport object; in this case, such a partially received object is normally discarded. However, the channel acquisition or "tune-in" times can be improved if the partially received object is usable by the application. One example realization for this is as follows:

受信者が最初にROUTEパケットの受信を開始するとき、マルチキャストトランスポートオブジェクトのデータを運ぶ一番最初のパケットから受信が始まらない可能性が高いです。この場合、そのような部分的に受信されたオブジェクトは通常破棄されます。しかし、部分的に受信されたオブジェクトをアプリケーションが使用できれば、チャネル取得時間、つまり「チューンイン」時間を改善できます。これを実現する一例は次のとおりです。

  • The receiver checks for the first received packet with the Codepoint value set to 10, indicating the start of a CMAF Random Access chunk.
  • The receiver MAY make the partially received object (a partial DASH segment starting from the packet above) available to the application for fast stream acquisition.
  • It MAY recover the earliest presentation time of this CMAF Random Access chunk from the ROUTE packet LCT Congestion Control Information (CCI) field as specified in Section 2.1 to be able to add a new Period element in the MPD exposed to the application containing just the partially received DASH segment with period continuity signaling.
  • 受信者は、CMAFランダムアクセスチャンクの開始を示す、コードポイント値が10に設定された最初の受信パケットを確認します。
  • 受信者は、高速なストリーム取得のために、部分的に受信されたオブジェクト（上記のパケットから始まる部分的なDASHセグメント）をアプリケーションに提供してもよいです（MAY）。
  • 受信者は、アプリケーションに公開するMPDに、部分的に受信されたDASHセグメントのみを含み、ピリオドの連続性のシグナリングを伴う新しいPeriod要素を追加できるように、Section 2.1で規定されているROUTEパケットのLCT輻輳制御情報（CCI）フィールドから、このCMAFランダムアクセスチャンクの最早プレゼンテーション時刻を復元してもよいです（MAY）。

6.3. ファイルモードのための拡張FDT-Instanceの生成

An Extended FDT-Instance conforming to RFC 6726 [RFC6726], is produced at the receiver using the service metadata and in-band signaling in the following steps:

RFC 6726 [RFC6726]に準拠した拡張FDT-Instanceは、受信者において、サービスメタデータと帯域内シグナリングを使用して、次の手順で生成されます。

6.3.1. File Template Substitution for Content-Location Derivation

6.3.1. Content-Locationを導出するためのファイルテンプレートの置換

The Content-Location element of the Extended FDT for a specific Application Object is derived as follows:

特定のアプリケーションオブジェクトに対する拡張FDTのContent-Location要素は、次のように導出されます。

"$TOI$" is substituted with the unique TOI value in the LCT header of the ROUTE packets used to recover the given delivery object (as specified in Section 6.1).

「$TOI$」は、（Section 6.1で規定されているように）その配送オブジェクトを復元するために使用されるROUTEパケットのLCTヘッダー内の一意のTOI値で置き換えられます。

置換後のfileTemplateは、関連するアプリケーションオブジェクトのContent-Location属性に対応する有効なURLとすることになります（SHALL）。

幅5を使用した@fileTemplateの例は、fileTemplate="myVideo$TOI%05d$.mps"です。この結果、数値部分がちょうど5桁のファイル名になります。このテンプレートを使用したTOI=33のメディアセグメントのファイル名はmyVideo00033.mpsです。

6.3.2. File@Transfer-Length Derivation

6.3.2. File@Transfer-Lengthの導出

Either the EXT_FTI header (per RFC 5775 [RFC5775]) or the EXT_TOL header, when present, is used to derive the Transport Object Length (TOL) of the File. If the File@Transfer-Length parameter in the Extended FDT-Instance is not present, then the EXT_TOL header or the or EXT_FTI header SHALL be present. Note that a header containing the transport object length (EXT_TOL or EXT_FTI) need not be present in each packet header. If the broadcaster does not know the length of the transport object at the beginning of the transfer, an EXT_TOL or EXT_FTI header SHALL be included in at least the last packet of the file and should be included in the last few packets of the transfer.

（RFC 5775 [RFC5775]に従った）EXT_FTIヘッダーまたはEXT_TOLヘッダーのいずれかが存在する場合、それを使用してファイルのトランスポートオブジェクト長（Transport Object Length、TOL）を導出します。拡張FDT-InstanceにFile@Transfer-Lengthパラメーターが存在しない場合、EXT_TOLヘッダーまたはEXT_FTIヘッダーが存在することになります（SHALL）。トランスポートオブジェクトの長さを含むヘッダー（EXT_TOLまたはEXT_FTI）は、各パケットヘッダーに存在する必要はないことに注意してください。放送事業者が転送の開始時にトランスポートオブジェクトの長さを知らない場合、EXT_TOLヘッダーまたはEXT_FTIヘッダーは、少なくともファイルの最後のパケットに含めるものとすることになります（SHALL）。また、転送の最後のいくつかのパケットに含めるべきです。

6.3.3. FDT-Instance@Expires Derivation

6.3.3. FDT-Instance@Expiresの導出

When present, the maxExpiresDelta attribute SHALL be used to generate the value of the FDT-Instance@Expires attribute. The receiver is expected to add this value to its wall clock time when acquiring the first ROUTE packet carrying the data of a given delivery object to obtain the value for @Expires.

maxExpiresDelta属性が存在する場合、FDT-Instance@Expires属性の値を生成するためにそれを使用することになります（SHALL）。受信者は、ある配送オブジェクトのデータを運ぶ最初のROUTEパケットを取得したときに、この値を自身の実時間に加えて@Expiresの値を得ることが期待されます。

When maxExpiresDelta is not present, the EXT_TIME header with Expected Residual Time (ERT) SHALL be used to derive the expiry time of the Extended FDT-Instance. When both maxExpiresDelta and the ERT of EXT_TIME are present, the smaller of the two values should be used as the incremental time interval to be added to the receiver's current time to generate the effective value for @Expires. When neither maxExpiresDelta nor the ERT field of the EXT_TIME header is present, then the expiration time of the Extended FDT-Instance is given by its @Expires attribute.

maxExpiresDeltaが存在しない場合、拡張FDT-Instanceの有効期限を導出するために、予想残り時間（ERT）を持つEXT_TIMEヘッダーを使用することになります（SHALL）。maxExpiresDeltaとEXT_TIMEのERTの両方が存在する場合、@Expiresの実効値を生成するために受信者の現在時刻に加える増分時間間隔として、2つの値のうち小さいほうを使用すべきです。maxExpiresDeltaとEXT_TIMEヘッダーのERTフィールドのどちらも存在しない場合、拡張FDT-Instanceの有効期限は、その@Expires属性によって与えられます。

7. FEC Application

7. FECの適用

7.1. General FEC Application Guidelines

7.1. FEC適用の一般的なガイドライン

It is up to the receiver to decide to use zero, one, or more of the FEC streams. Hence, the application assigns a recovery property to each flow, which defines aspects such as the delay and the required memory if one or the other is chosen. The receiver MAY decide whether or not to utilize Repair Flows based on the following considerations:

FECストリームを0個、1個、あるいは複数使用するかを決めるのは受信者です。したがって、アプリケーションは各フローにリカバリー特性を割り当てます。これは、いずれかを選択した場合の遅延や必要なメモリーなどの側面を定義します。受信者は、次の考慮事項に基づいて、リペアフローを利用するかどうかを決定してもよいです（MAY）。

  • The desired start-up and end-to-end latency. If a Repair Flow requires a significant amount of buffering time to be effective, such Repair Flow might only be used in time-shift operations or in poor reception conditions, since use of such Repair Flow trades off end-to-end latency against DASH Media Presentation quality.
  • FEC capabilities, i.e., the receiver MAY pick only the FEC algorithm that it supports.
  • Which Source Flows are being protected; for example, if the Repair Flow protects Source Flows that are not selected by the receiver, then the receiver may not select the Repair Flow.
  • Other considerations such as available buffer size, reception conditions, etc.
  • 望ましい起動時の遅延とエンドツーエンドの遅延。リペアフローが効果を発揮するために多くのバッファリング時間を必要とする場合、そのようなリペアフローは、タイムシフト操作や受信状態が悪い場合にのみ使用されるかもしれません。そのようなリペアフローの使用は、エンドツーエンドの遅延とDASHのMedia Presentationの品質とのトレードオフになるためです。
  • FECの能力。すなわち、受信者は自身がサポートするFECアルゴリズムのみを選択してもよいです（MAY）。
  • どのソースフローが保護されているか。たとえば、受信者が選択していないソースフローをリペアフローが保護している場合、受信者はそのリペアフローを選択しないかもしれません。
  • 利用可能なバッファーサイズや受信状態などの、その他の考慮事項。

If a receiver decides to acquire a certain Repair Flow, then the receiver must receive data on all Source Flows that are protected by that Repair Flow to collect the relevant packets.

受信者があるリペアフローを取得することを決定した場合、受信者は、関連するパケットを収集するために、そのリペアフローによって保護されているすべてのソースフローのデータを受信する必要があります。

7.2. TOI Mapping

7.2. TOIの対応付け

When mappingTOIx/mappingTOIy are used to signal X and Y values, the TOI value(s) of the one or more source objects (sourceTOI) protected by a given FEC transport object or FEC super-object with a TOI value rTOI is derived through an equation sourceTOI = X*rTOI + Y.

XとYの値をシグナリングするためにmappingTOIx／mappingTOIyを使用する場合、TOI値rTOIを持つあるFECトランスポートオブジェクトまたはFECスーパーオブジェクトによって保護される1つ以上のソースオブジェクトのTOI値（sourceTOI）は、式sourceTOI = X*rTOI + Yによって導出されます。

When neither mappingTOIx nor mappingTOIy is present, there is a 1:1 relationship between each delivery object carried in the Source Flow as identified by ptsi to a FEC object carried in this Repair Flow. In this case, the TOI of each of those delivery objects SHALL be identical to the TOI of the corresponding FEC object.

mappingTOIxとmappingTOIyのどちらも存在しない場合、ptsiで識別されるソースフローで運ばれる各配送オブジェクトと、このリペアフローで運ばれるFECオブジェクトとの間には、1対1の関係があります。この場合、それらの各配送オブジェクトのTOIは、対応するFECオブジェクトのTOIと同一とすることになります（SHALL）。

7.3. Delivery Object Reception Timeout

7.3. 配送オブジェクトの受信タイムアウト

The permitted start and end times for the receiver to perform the file repair procedure, in case of unsuccessful broadcast file reception, and associated rules and parameters are as follows:

ブロードキャストによるファイルの受信に失敗した場合に、受信者がファイルリペア手続きを実行することが許可される開始時刻と終了時刻、および関連する規則とパラメーターは次のとおりです。

  • ファイルリペア手続きを開始できる最も遅い時刻は、FDT-Instanceの@Expires属性によって制限されます。

7.4. Example FEC Operation

7.4. FECの動作例

To be able to recover the delivery objects that are protected by a Repair Flow, a receiver needs to obtain the necessary Service signaling metadata fragments that describe the corresponding collection of delivery objects that are covered by this Repair Flow. A Repair Flow is characterized by the combination of an LCT channel, a unique TSI number, as well as the corresponding protected Source Flows.

リペアフローによって保護されている配送オブジェクトを復元できるようにするために、受信者は、このリペアフローの対象となる配送オブジェクトの集合を記述する、必要なサービスシグナリングメタデータのフラグメントを取得する必要があります。リペアフローは、LCTチャネル、一意のTSI番号、および対応する保護されるソースフローの組み合わせによって特徴付けられます。

If a receiver acquires data of a Repair Flow, the receiver is expected to collect all packets of all protected Transport Sessions. Upon receipt of each packet, whether it is a source or repair packet, the receiver proceeds with the following steps in the order listed.

受信者がリペアフローのデータを取得する場合、受信者は保護されるすべてのトランスポートセッションのすべてのパケットを収集することが期待されます。各パケットを受信すると、それがソースパケットであるかリペアパケットであるかにかかわらず、受信者は次の手順を記載された順序で進めます。

  1. The receiver is expected to parse the packet header and verify that it is a valid header. If it is not valid, then the packet SHALL be discarded without further processing.
  2. The receiver is expected to parse the TSI field of the packet header and verify that a matching value exists in the Service signaling for the Repair Flow or the associated Protected Source Flow. If no match is found, the packet SHALL be discarded without further processing.

  3. The receiver processes the remainder of the packet, including interpretation of the other header fields, and using the source FEC Payload ID (to determine the start_offset byte position within the source object), the Repair FEC Payload ID, as well as the payload data, reconstructs the decoding blocks corresponding to a FEC super-object as follows:

    1. For a source packet, the receiver identifies the delivery object to which the received packet is associated using the session information and the TOI carried in the payload header. Similarly, for a repair object, the receiver identifies the FEC super-object to which the received packet is associated using the session information and the TOI carried in the payload header.
    2. For source packets, the receiver collects the data for each FEC super-object and recovers FEC super-objects in the same way as a Source Flow in Section 6.1. The received FEC super-object is then mapped to a source block and the corresponding encoding symbols are generated.
    3. With the reception of the repair packets, the FEC super-object can be recovered.
    4. Once the FEC super-object is recovered, the individual delivery objects can be extracted.
  1. 受信者は、パケットヘッダーを解析し、それが有効なヘッダーであることを検証することが期待されます。有効でない場合、そのパケットはそれ以上処理せずに破棄することになります（SHALL）。
  2. 受信者は、パケットヘッダーのTSIフィールドを解析し、リペアフローまたは関連する保護されるソースフローについて、サービスシグナリング内に一致する値が存在することを検証することが期待されます。一致するものが見つからない場合、そのパケットはそれ以上処理せずに破棄することになります（SHALL）。

  3. 受信者は、他のヘッダーフィールドの解釈を含め、パケットの残りの部分を処理し、ソースFECペイロードID（ソースオブジェクト内のstart_offsetバイト位置を決定するため）、リペアFECペイロードID、およびペイロードデータを使用して、次のようにFECスーパーオブジェクトに対応するデコードブロックを再構成します。

    1. ソースパケットの場合、受信者は、セッション情報とペイロードヘッダーで運ばれるTOIを使用して、受信したパケットが関連付けられている配送オブジェクトを識別します。同様に、リペアオブジェクトの場合、受信者は、セッション情報とペイロードヘッダーで運ばれるTOIを使用して、受信したパケットが関連付けられているFECスーパーオブジェクトを識別します。
    2. ソースパケットについて、受信者は各FECスーパーオブジェクトのデータを収集し、Section 6.1のソースフローと同じ方法でFECスーパーオブジェクトを復元します。その後、受信したFECスーパーオブジェクトはソースブロックに対応付けられ、対応するエンコーディングシンボルが生成されます。
    3. リペアパケットを受信することで、FECスーパーオブジェクトを復元できます。
    4. FECスーパーオブジェクトが復元されると、個々の配送オブジェクトを抽出できます。

9. ROUTE Concepts

9. ROUTEの概念

9.1. ROUTE Modes of Delivery

9.1. ROUTEの配送モード

Different ROUTE delivery modes specified in Section 4 are optimized for delivery of different types of media data. For example, File Mode is specifically optimized for delivering DASH content using Segment Template with number substitution. Using File Template in EFDT avoids the need for the repeated sending of metadata as outlined in the following section. Same optimizations, however, cannot be used for time substitution and segment timeline where the addressing of each segment is time dependent and in general does not follow a fixed or repeated pattern. In this case, Entity Mode is more optimized since it carries the file location in band. Also, Entity Mode can be used to deliver a file or part of the file using HTTP Partial Content response headers.

Section 4で規定されている各種のROUTE配送モードは、それぞれ異なるタイプのメディアデータの配送に最適化されています。たとえば、ファイルモードは、番号置換を伴うSegment Templateを使用したDASHコンテンツの配送に特に最適化されています。EFDTでファイルテンプレートを使用すると、次のセクションで概説するように、メタデータを繰り返し送信する必要がなくなります。しかし、時間置換やセグメントタイムラインでは、同じ最適化を使用できません。これらでは、各セグメントのアドレス指定が時間に依存し、一般に固定のパターンや繰り返しのパターンに従わないためです。この場合、エンティティーモードはファイルの場所を帯域内で運ぶため、より最適化されています。また、エンティティーモードは、HTTPのPartial Contentレスポンスヘッダーを使用して、ファイルまたはファイルの一部を配送するために使用できます。

9.2. File Mode Optimizations

9.2. ファイルモードの最適化

In File Mode, the delivery object represents an Application Object. This mode replicates FLUTE as defined in RFC 6726 [RFC6726] but with the ability to send static and pre-known file metadata out of band.

ファイルモードでは、配送オブジェクトはアプリケーションオブジェクトを表します。このモードは、RFC 6726 [RFC6726]で定義されているFLUTEを再現したものですが、静的であらかじめわかっているファイルメタデータを帯域外で送信する機能を備えています。

In FLUTE, FDT-Instances are delivered in band and need to be generated and delivered in real time if objects are generated in real time at the sender. These FDT-Instances have some differences as compared to the FDT specified in Section 3.4.2 of [RFC6726] and Section 7.2.10 of MBMS [MBMS]. The key difference is that besides separated delivery of file metadata from the delivery object it describes, the FDT functionality in ROUTE may be extended by additional file metadata and rules that enable the receiver to generate the Content-Location attribute of the File element of the FDT, on the fly. This is done by using information in both the extensions to the FDT and the LCT header. The combination of pre-delivery of static file metadata and receiver self generation of dynamic file metadata avoids the necessity of continuously sending the FDT-Instances for real-time objects. Such modified FDT functionality in ROUTE is referred to as the Extended FDT.

FLUTEでは、FDT-Instanceは帯域内で配送され、送信者においてオブジェクトがリアルタイムで生成される場合、FDT-Instanceもリアルタイムで生成して配送する必要があります。これらのFDT-Instanceには、[RFC6726]のSection 3.4.2やMBMS [MBMS]のセクション7.2.10で規定されているFDTと比べて、いくつかの違いがあります。主な違いは、ファイルメタデータを、それが記述する配送オブジェクトとは別に配送することに加えて、ROUTEのFDT機能は、受信者がFDTのFile要素のContent-Location属性をその場で生成できるようにする追加のファイルメタデータと規則によって拡張される場合があることです。これは、FDTの拡張とLCTヘッダーの両方の情報を使用することで行われます。静的なファイルメタデータの事前配送と、動的なファイルメタデータの受信者による自己生成とを組み合わせることで、リアルタイムオブジェクトのためにFDT-Instanceを継続的に送信する必要がなくなります。ROUTEにおけるこのように変更されたFDT機能を、拡張FDTと呼びます。

9.3. In-Band Signaling of Object Transfer Length

9.3. オブジェクトの転送長の帯域内シグナリング

As an extension to FLUTE, ROUTE allows for using EXT_TOL LCT header extension with 24 bits or, if required, 48 bits to signal the Transfer Length directly within the ROUTE packet.

FLUTEの拡張として、ROUTEでは、24ビット、または必要であれば48ビットのEXT_TOL LCTヘッダー拡張を使用して、ROUTEパケット内で直接転送長をシグナリングできます。

The transport object length can also be determined without the use of EXT_TOL by examining the LCT packet with the Close Object flag (B). However, if this packet is lost, then the EXT_TOL information can be used by the receiver to determine the transport object length.

トランスポートオブジェクトの長さは、EXT_TOLを使用しなくても、オブジェクトクローズフラグ（B）を持つLCTパケットを調べることで決定できます。しかし、このパケットが失われた場合、受信者はEXT_TOLの情報を使用してトランスポートオブジェクトの長さを決定できます。

Applications using ROUTE for delivery of low-latency streaming content may make use of this feature for sender-end latency optimizations: the sender does not have to wait for the completion of the packaging of a whole Application Object to find its Transfer Length to be included in the FDT before the sending can start. Rather, partially encoded data can already be started to be sent via the ROUTE sender. As the time approaches when the encoding of the Application Object is nearing completion, and the length of the object becomes known (e.g., the time of writing the last CMAF Chunk of a DASH segment), only then the sender can signal the object length using the EXT TOL LCT header. For example, for a 2-second DASH segment with 100-millisecond chunks, it may result in saving up to 1.9 second latency at the sending end.

低遅延のストリーミングコンテンツの配送にROUTEを使用するアプリケーションは、送信側の遅延の最適化のためにこの機能を利用できます。送信者は、送信を開始する前に、アプリケーションオブジェクト全体のパッケージ化が完了するのを待って、FDTに含める転送長を求める必要がありません。むしろ、部分的にエンコードされたデータを、すでにROUTE送信者経由で送信し始めることができます。アプリケーションオブジェクトのエンコードが完了に近づき、オブジェクトの長さがわかった時点（たとえば、DASHセグメントの最後のCMAFチャンクを書き込む時点）で初めて、送信者はEXT TOL LCTヘッダーを使用してオブジェクトの長さをシグナリングできます。たとえば、100ミリ秒のチャンクを持つ2秒のDASHセグメントの場合、送信側で最大1.9秒の遅延を削減できる可能性があります。

9.4. Repair Protocol Concepts

9.4. リペアプロトコルの概念

The ROUTE repair protocol is FEC-based and is enabled as an additional layer between the transport layer (e.g., UDP) and the object delivery layer protocol. The FEC reuses concepts of the FEC Framework defined in RFC 6363 [RFC6363], but in contrast to the FEC Framework in RFC 6363 [RFC6363], the ROUTE repair protocol does not protect packets but instead protects delivery objects as delivered in the source protocol. In addition, as an extension to FLUTE, it supports the protection of multiple objects in one source block which is in alignment with the FEC Framework as defined in RFC 6363 [RFC6363]. Each FEC source block may consist of parts of a delivery object, as a single delivery object (similar to FLUTE) or multiple delivery objects that are bundled prior to FEC protection. ROUTE FEC makes use of FEC schemes in a similar way as those defined in RFC 5052 [RFC5052] and uses the terminology of that document. The FEC scheme defines the FEC encoding and decoding as well as the protocol fields and procedures used to identify packet payload data in the context of the FEC scheme.

ROUTEのリペアプロトコルはFECベースであり、トランスポート層（たとえば、UDP）とオブジェクト配送層のプロトコルとの間の追加の層として実現されます。このFECは、RFC 6363 [RFC6363]で定義されているFECフレームワークの概念を再利用しますが、RFC 6363 [RFC6363]のFECフレームワークとは対照的に、ROUTEのリペアプロトコルはパケットを保護するのではなく、ソースプロトコルで配送される配送オブジェクトを保護します。さらに、FLUTEの拡張として、1つのソースブロック内の複数のオブジェクトの保護をサポートしており、これはRFC 6363 [RFC6363]で定義されているFECフレームワークと整合しています。各FECソースブロックは、配送オブジェクトの一部、（FLUTEと同様に）単一の配送オブジェクト、またはFEC保護の前に束ねられた複数の配送オブジェクトで構成されます。ROUTEのFECは、RFC 5052 [RFC5052]で定義されているものと同様の方法でFECスキームを利用し、その文書の用語を使用します。FECスキームは、FECのエンコードとデコード、そしてFECスキームのコンテキストでパケットペイロードデータを識別するために使用されるプロトコルフィールドと手順を定義します。

In ROUTE, all packets are LCT packets as defined in RFC 5651 [RFC5651]. Source and repair packets may be distinguished by:

ROUTEでは、すべてのパケットはRFC 5651 [RFC5651]で定義されているLCTパケットです。ソースパケットとリペアパケットは、次の方法で区別できます。

  • Different ROUTE sessions, i.e., they are carried on different UDP/IP port combinations.
  • Different LCT channels, i.e., they use different TSI values in the LCT header.
  • The most significant PSI bit in the LCT, if carried in the same LCT channel. This mode of operation is mostly suitable for FLUTE-compatible deployments.
  • 異なるROUTEセッション。すなわち、それらは異なるUDP/IPポートの組み合わせで運ばれます。
  • 異なるLCTチャネル。すなわち、それらはLCTヘッダー内で異なるTSI値を使用します。
  • 同じLCTチャネルで運ばれる場合は、LCT内のPSIの最上位ビット。この動作モードは、主にFLUTE互換の展開に適しています。

11. Security and Privacy Considerations

11. セキュリティーとプライバシーに関する考慮事項

11.1. Security Considerations

11.1. セキュリティーに関する考慮事項

As noted in Section 9, ROUTE is aligned with FLUTE as specified in RFC 6726 [RFC6726] and only diverges in certain signaling optimizations, especially for the real-time object delivery case. Hence, most of the security considerations documented in RFC 6726 [RFC6726] for the data flow itself, the session metadata (session control parameters in RFC 6726 [RFC6726]), and the associated building blocks apply directly to ROUTE as elaborated in the following along with some additional considerations.

Section 9で述べたように、ROUTEはRFC 6726 [RFC6726]で規定されているFLUTEと整合しており、特にリアルタイムのオブジェクト配送の場合における特定のシグナリングの最適化においてのみ異なります。したがって、データフロー自体、セッションメタデータ（RFC 6726 [RFC6726]におけるセッション制御パラメーター）、および関連するビルディングブロックについてRFC 6726 [RFC6726]に記載されているセキュリティーに関する考慮事項のほとんどは、以下で詳しく説明するように、いくつかの追加の考慮事項とともにROUTEに直接適用されます。

Both encryption and integrity protection applied either on file or packet level, as recommended in the file corruption considerations of RFC 6726 [RFC6726], SHOULD be used for ROUTE. Additionally, RFC 3740 [RFC3740] documents multicast security architecture in great detail with clear security recommendations that SHOULD be followed.

RFC 6726 [RFC6726]のファイル破損に関する考慮事項で推奨されているように、ファイルレベルまたはパケットレベルのいずれかで適用される暗号化と完全性保護の両方を、ROUTEに使用すべきです（SHOULD）。さらに、RFC 3740 [RFC3740]はマルチキャストのセキュリティーアーキテクチャーを非常に詳細に記述しており、明確なセキュリティーの推奨事項を示しています。それらの推奨事項に従うべきです（SHOULD）。

When ROUTE is carried over UDP and a reverse channel from receiver to sender is available, the security mechanisms provided in RFC 9147 [RFC9147] SHOULD be applied.

ROUTEがUDP上で運ばれ、受信者から送信者への逆方向のチャネルが利用可能な場合は、RFC 9147 [RFC9147]で提供されているセキュリティーメカニズムを適用すべきです（SHOULD）。

In regard to considerations for attacks against session description, this document does not specify the semantics or mechanism of delivery of session metadata, though the same threats apply for service using ROUTE as well. Hence, a service using ROUTE SHOULD take these threats into consideration and address them appropriately following the guidelines provided by RFC 6726 [RFC6726]. Additionally, to the recommendations of RFC 6726 [RFC6726], for Internet connected devices, services SHOULD enable clients to access the session description information using HTTPS with customary authentication/authorization, instead of sending this data via multicast/broadcast, since considerable security work has been done already in this unicast domain, which can enable highly secure access of session description data. Accessing via unicast, however, will have different privacy considerations, noted in Section 11.2. Note that in general the multicast/broadcast stream is delayed with respect to the unicast stream. Therefore, the session description protocol SHOULD be time synchronized with the broadcast stream, particularly if the session description contains security-related information.

セッション記述に対する攻撃に関する考慮事項については、この文書ではセッションメタデータの配送のセマンティクスやメカニズムを規定していませんが、ROUTEを使用するサービスにも同じ脅威が当てはまります。したがって、ROUTEを使用するサービスは、これらの脅威を考慮に入れ、RFC 6726 [RFC6726]が提供するガイドラインに従って適切に対処すべきです（SHOULD）。さらに、RFC 6726 [RFC6726]の推奨事項に加えて、インターネットに接続されたデバイスについては、サービスは、このデータをマルチキャスト／ブロードキャストで送信する代わりに、クライアントが通常の認証／認可を伴うHTTPSを使用してセッション記述情報にアクセスできるようにすべきです（SHOULD）。このユニキャストの領域ではすでにかなりのセキュリティーの取り組みが行われており、セッション記述データへの高度に安全なアクセスを可能にできるためです。ただし、ユニキャストを介したアクセスには、Section 11.2で述べるように、異なるプライバシーに関する考慮事項があります。一般に、マルチキャスト／ブロードキャストのストリームは、ユニキャストのストリームに対して遅延することに注意してください。したがって、特にセッション記述にセキュリティー関連の情報が含まれている場合、セッション記述プロトコルはブロードキャストのストリームと時刻同期すべきです（SHOULD）。

In regard to FDT, there is one key difference for File Mode when using File Template in EFDT, which avoids repeated sending of FDT-Instances and hence, the corresponding threats noted in RFC 6726 [RFC6726] do not apply directly to ROUTE in this case. The threat, however, is shifted to the ALC/LCT headers, since they carry the additional signaling that enables determining Content-Location and File@Transfer-Length in this case. Hence, integrity protection recommendations of ALC/LCT header SHOULD be considered with higher emphasis in this case for ROUTE.

FDTに関しては、EFDTでファイルテンプレートを使用する場合のファイルモードに1つの重要な違いがあります。これによりFDT-Instanceの繰り返しの送信が回避されるため、この場合、RFC 6726 [RFC6726]で述べられている対応する脅威はROUTEには直接適用されません。しかし、この場合、Content-LocationとFile@Transfer-Lengthの決定を可能にする追加のシグナリングをALC/LCTヘッダーが運ぶため、脅威はALC/LCTヘッダーに移ります。したがって、この場合のROUTEでは、ALC/LCTヘッダーの完全性保護の推奨事項を、より重視して考慮すべきです（SHOULD）。

Finally, attacks against the congestion control building block for the case of ROUTE can impact the optional fast stream acquisition specified in Section 6.2. Receivers SHOULD have robustness against timestamp values that are suspicious, e.g., by comparing the signaled time in the LCT headers with the approximate time signaled by the MPD, and SHOULD discard outlying values. Additionally, receivers MUST adhere to the expiry timelines as specified in Section 6. Integrity protection mechanisms documented in RFC 6726 [RFC6726] SHOULD be used to address this threat.

最後に、ROUTEの場合、輻輳制御ビルディングブロックに対する攻撃は、Section 6.2で規定されている任意の高速なストリーム取得に影響を与える可能性があります。受信者は、たとえばLCTヘッダーでシグナリングされた時刻と、MPDでシグナリングされたおおよその時刻を比較することによって、疑わしいタイムスタンプ値に対する堅牢性を持つべきです（SHOULD）。また、外れ値を破棄すべきです（SHOULD）。さらに、受信者は、Section 6で規定されている有効期限のタイムラインを遵守しなければなりません（MUST）。この脅威に対処するために、RFC 6726 [RFC6726]に記載されている完全性保護メカニズムを使用すべきです（SHOULD）。

11.2. Privacy Considerations

11.2. プライバシーに関する考慮事項

Encryption mechanisms recommended for security considerations in Section 11.1 SHOULD also be applied to enable privacy and protection from snooping attacks.

プライバシーを実現し、盗み見攻撃から保護するために、Section 11.1のセキュリティーに関する考慮事項で推奨されている暗号化メカニズムも適用すべきです（SHOULD）。

Since this protocol is primarily targeted for IP multicast/broadcast environments where the end user is mostly listening, identity protection and user data retention considerations are more protected than in the unicast case. Best practices for enabling privacy on IP multicast/broadcast SHOULD be applied by the operators, e.g., "Recommendations for DNS Privacy Service Operators" in RFC 8932 [RFC8932].

このプロトコルは、エンドユーザーがほとんどの場合受信するだけであるIPマルチキャスト／ブロードキャスト環境を主な対象としているため、身元の保護とユーザーデータの保持に関する考慮事項は、ユニキャストの場合よりも保護されています。運用者は、IPマルチキャスト／ブロードキャストでプライバシーを実現するためのベストプラクティス、たとえばRFC 8932 [RFC8932]の「Recommendations for DNS Privacy Service Operators」を適用すべきです（SHOULD）。

However, if clients access session description information via HTTPS, the same privacy considerations and solutions SHALL apply to this access as for regular HTTPS communication, an area that is very well studied and the concepts of which are being integrated directly into newer transport protocols such as IETF QUIC [RFC9000] enabling HTTP/3 [HTTP3]. Hence, such newer protocols SHOULD be used to foster privacy.

しかし、クライアントがHTTPSを介してセッション記述情報にアクセスする場合、このアクセスには、通常のHTTPS通信と同じプライバシーに関する考慮事項と解決策を適用することになります（SHALL）。これは非常によく研究されている分野であり、その概念は、HTTP/3 [HTTP3]を可能にするIETF QUIC [RFC9000]などの新しいトランスポートプロトコルに直接統合されつつあります。したがって、プライバシーを促進するために、そのような新しいプロトコルを使用すべきです（SHOULD）。

Note that streaming services MAY contain content that may only be accessed via DRM (digital rights management) systems. DRM systems can prevent unauthorized access to content delivered via ROUTE.

注：ストリーミングサービスには、DRM（デジタル著作権管理）システムを介してのみアクセスできるコンテンツが含まれている場合があります（MAY）。DRMシステムは、ROUTEで配送されるコンテンツへの不正なアクセスを防ぐことができます。
