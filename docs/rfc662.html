RFC 662

Performance improvement in ARPANET file transfers from Multics

RFC 662

MulticsからのARPANETファイル転送の性能改善

Abstract

概要

With the growth of Multics usage in the ARPA Network community, users often need to transfer large amounts of data from Multics to other systems. However, Multics performance in this area has been less than optimal and there clearly exists a need to improve the situation. Even within Project MAC there are users who regularly ship files back and forth between Multics and other Project MAC computer systems. Recently the Cambridge Information Systems Laboratory (CISL) development Multics system was connected to the ARPA Network. This has generated considerable interest among the members of the CSR (Computer Systems Research) and CISL groups in using the Multics file transfer facility for transmission of Multics system tapes (MST) from one Multics system to the other. At currently realizable data transfer rates, transmission of a typical MST, (approximately 12 million bits), takes about half an hour. The usefulness of the present file transfer system is severely limited by its low bandwidth.

ARPAネットワークのコミュニティーでMulticsの利用が増えるにつれ、ユーザーはしばしば大量のデータをMulticsから他のシステムに転送する必要に迫られています。しかし、この分野におけるMulticsの性能は最適とはいえず、状況を改善する必要があることは明らかです。Project MACの内部でさえ、Multicsと他のProject MACのコンピューターシステムとの間で定期的にファイルをやり取りしているユーザーがいます。最近、ケンブリッジ情報システム研究所（CISL：Cambridge Information Systems Laboratory）の開発用MulticsシステムがARPAネットワークに接続されました。これにより、CSR（Computer Systems Research）グループとCISLグループのメンバーの間で、Multicsのファイル転送機能を使ってMulticsシステムテープ（MST：Multics System Tape）をあるMulticsシステムから別のMulticsシステムへ送信することに大きな関心が寄せられています。現在実現可能なデータ転送速度では、典型的なMST（約1200万ビット）の送信には約30分かかります。現在のファイル転送システムの有用性は、その低い帯域幅によって大きく制限されています。

One of the reasons for such a poor performance is the output buffering strategy in the Multics IMP DIM (IMP Device Interface Manager.) With the hope of making a significant performance improvement, we recently changed the IMP DIM buffering strategy. To assess the effects of this change an experiment was conducted between the service machine (MIT Multics) and the development machine (CISL Multics.) This memo reports the experiment and its results.

このように性能が低い理由の1つは、MulticsのIMP DIM（IMP Device Interface Manager）における出力バッファリングの戦略にあります。性能を大幅に改善することを期待して、私たちは最近IMP DIMのバッファリング戦略を変更しました。この変更の効果を評価するために、サービス用マシン（MIT Multics）と開発用マシン（CISL Multics）の間で実験を行いました。このメモでは、その実験と結果を報告します。

PROBLEM

問題

Due to reasons that are of historical interest only, the output buffers in the IMP DIM have been very small; each buffer can accommodate up to 940 bits only. With the addition of a 72 bit long header, the resulting message has a maximum length of 1012 bits, which in the Network terminology is a single packet message. Due to this buffer size limit, Multics can transmit single packet messages only, even though the network can accept up to 8096 bit long messages. This results in increased overhead in the set up time for transmission of large number of bits.

もはや歴史的な関心しか持たれないような理由により、IMP DIMの出力バッファーは非常に小さく、各バッファーには最大940ビットしか格納できません。72ビット長のヘッダーを加えると、結果として得られるメッセージの最大長は1012ビットとなり、これはネットワークの用語でいう単一パケットメッセージです。このバッファーサイズの制限のため、ネットワークは最大8096ビット長のメッセージを受け付けられるにもかかわらず、Multicsは単一パケットメッセージしか送信できません。その結果、大量のビットを送信する際の準備時間のオーバーヘッドが増加します。

An old version of the IMP-to-Host protocol requires that a host may not transmit another message on a network connection unless a Request-for-Next-Message (RFNM) has been received in response to the previous message. Even though this restriction has now been relaxed, the protocol does not specify any way to recover from transmission errors that occur while more than one RFNM is pending on the same connection. If the constraint of transmitting only one message at a time is observed there is at least some potential for recovery in case of an error. 8eing reliability conscious, Multics observes the constraint imposed by the old protocol. Following the old protocol introduces delays in the transmission of successive messages on the same link and therefore the overall bandwidth per connection is reduced.

IMP-ホスト間プロトコルの古いバージョンでは、ホストは、前のメッセージに対する応答としてRFNM（Request-for-Next-Message）を受信するまで、ネットワークコネクション上で次のメッセージを送信してはならないと定めています。この制限は現在では緩和されていますが、同じコネクション上で複数のRFNMが保留されている間に発生した送信エラーから回復する方法を、プロトコルは何も規定していません。一度に1つのメッセージだけを送信するという制約を守れば、エラーが起きたときに少なくとも回復できる可能性はあります。信頼性を重視しているため、Multicsは古いプロトコルが課すこの制約を守っています。古いプロトコルに従うと、同じリンク上で連続するメッセージの送信に遅延が生じるため、コネクションあたりの全体的な帯域幅が減少します。

SOLUTION

解決策

At least one method of improving the file transfer bandwidth is obvious. Increasing the size of IMP DIM output buffers will allow us to transmit significantly larger messages<s1>s This will result in fewer RFNMs and delays and improved bandwidth. We have made two assumptions here. The first assumption is that the delay introduced by RFNMs does not increase with the size of the message.<s2>s Our experience with the network tends to support this assumption. The second assumption is that actual time taken to transmit a message increases, at best, linearly with the size of message. This second assumption does not hold for a heavily loaded network. But for our purpose we may assume it to be essentially correct.

ファイル転送の帯域幅を改善する方法のうち、少なくとも1つは明白です。IMP DIMの出力バッファーのサイズを大きくすれば、かなり大きなメッセージを送信できるようになります<s1>s。これにより、RFNMと遅延が減り、帯域幅が向上します。ここでは2つの前提を置いています。1つ目の前提は、RFNMによって生じる遅延がメッセージのサイズとともに増加しないことです<s2>s。ネットワークに関する私たちの経験は、この前提を裏付ける傾向にあります。2つ目の前提は、メッセージの送信に実際にかかる時間が、メッセージのサイズに対してせいぜい線形にしか増加しないことです。この2つ目の前提は、負荷の高いネットワークでは成り立ちません。しかし、私たちの目的においては、おおむね正しいと見なしてかまわないでしょう。

There is another advantage in transmitting large messages. For a given amount of data, fewer messages will be transmitted, fewer RFNMs will be read, and therefore time spent in the channel driver programs will be reduced. Since the channel sits idle during at least some of this time, the idle time for the channel will be reduced, resulting in improved channel bandwidth.

大きなメッセージを送信することには、もう1つの利点があります。一定量のデータについて、送信されるメッセージが減り、読み取るRFNMも減るため、チャネルドライバープログラムで費やされる時間が減少します。この時間の少なくとも一部ではチャネルがアイドル状態になっているため、チャネルのアイドル時間が減り、その結果チャネルの帯域幅が向上します。

<s1>s In one situation it may not be possible to transmit large messages. The number of messages and bits that a host can transmit on a particular connection must not exceed the message and bit allocation provided by the receiving host. If a receiving host gives very small bit allocation, then the sending host can not transmit very large messages. Since Multics always gives out very large allocations, there should be no problem in Multics to Multics file transfers.

<s1>s大きなメッセージを送信できない状況が1つあります。ホストが特定のコネクション上で送信できるメッセージ数とビット数は、受信側ホストが与えるメッセージとビットの割り当てを超えてはなりません。受信側ホストが非常に小さなビット割り当てしか与えない場合、送信側ホストは非常に大きなメッセージを送信できません。Multicsは常に非常に大きな割り当てを与えるため、Multics同士のファイル転送では問題はないはずです。

<s2>s It should be noted that the size of RFNM is fixed and does not change with the size of message.

<s2>s RFNMのサイズは固定されており、メッセージのサイズによって変わらないことに注意してください。

EXPERIMENT

実験

We changed the IMP DIM to implement two kinds of output buffers. One kind of output buffer is short and can hold single packet messages only. The other kind of buffer is, naturally enough, large and can hold the largest message allowed by the network. If the number of bits to be transmitted is low (this is mostly the situation with interactive users,) a small buffer is chosen and if it is large (for example, file transfers,) a large buffer is chosen.

私たちは、IMP DIMを変更して2種類の出力バッファーを実装しました。1つ目の種類の出力バッファーは短く、単一パケットメッセージしか格納できません。もう1つの種類のバッファーは、当然ながら大きく、ネットワークが許容する最大のメッセージを格納できます。送信するビット数が少ない場合（対話型ユーザーの場合はほとんどがこれに当たります）は小さなバッファーを選択し、多い場合（たとえば、ファイル転送）は大きなバッファーを選択します。

The new IMP DIM was used in an experimental Multics system on the development machine at CISL. The service machine at MIT had the old version. Large files were transmitted from the development system to the service system and the file transfer rate was measured in bits per second ( of real time.) To get an estimate of gain in the performance, files were transmitted from the service system to the development system and the old file transfer rate was measured. The same file, approximately 2.5 million bits long, was used in both experiments. The BYTE-SIZE and MODE parameters of the ARPANET File Transfer protocol were set to 36 and "image" mode respectively. This implies that no character conversion was performed in the file transfer. The following table shows the results obtained:

新しいIMP DIMは、CISLの開発用マシン上の実験的なMulticsシステムで使用しました。MITのサービス用マシンは古いバージョンのままでした。開発用システムからサービス用システムへ大きなファイルを送信し、ファイル転送速度を（実時間での）ビット毎秒で測定しました。性能の向上を見積もるため、サービス用システムから開発用システムへもファイルを送信し、従来のファイル転送速度を測定しました。どちらの実験でも、約250万ビット長の同じファイルを使用しました。ARPANETファイル転送プロトコルのBYTE-SIZEパラメーターとMODEパラメーターは、それぞれ36と「image」モードに設定しました。これは、ファイル転送において文字変換を一切行わなかったことを意味します。得られた結果を次の表に示します。

The following information regarding the environment of the experiment is supplied for the sake of completeness. At the time of this experiment, the service system was lightly loaded (the system load varied between 30.0 and 35.0). The service system configuration was 2 cpu's and 384 K primary memory. The development machine configuration was 1 cpu and 256 K of primary memory. The development system load was limited to the file transfer processes and the initializer process. The MIT Multics is connected to the IMP number 44 (port 0) by a rather short cable (approximately 100 feet long.) The CISL Multics is connected to the IMP number 6 (port 0) by an approximately l5OO feet long cable. 8oth IMPs are in close physical proximity (approximately 2000 feet,) and are connected to each other by a 5O kilobits per second line. The results given above show considerable improvement in the performance with the new IMP DIM.

完全を期すため、実験の環境に関する次の情報を記しておきます。この実験の時点では、サービス用システムの負荷は軽いものでした（システム負荷は30.0から35.0の間で変動しました）。サービス用システムの構成は、CPU 2台と384Kの主記憶でした。開発用マシンの構成は、CPU 1台と256Kの主記憶でした。開発用システムの負荷は、ファイル転送プロセスとイニシャライザープロセスだけに限られていました。MIT Multicsは、かなり短いケーブル（長さ約100フィート）でIMP番号44（ポート0）に接続されています。CISL Multicsは、長さ約1500フィートのケーブルでIMP番号6（ポート0）に接続されています。両方のIMPは物理的に近い位置（約2000フィート）にあり、毎秒50キロビットの回線で互いに接続されています。上記の結果は、新しいIMP DIMによって性能がかなり向上したことを示しています。

Since there is considerable interest in the Multics development community in using the file transfer facility for transmitting Multics System Tapes between the two systems, we are providing here an estimate of time that would be taken to transmit the current MST. MST 23.4-0A contains 334,231 words. When multiplied by 36 (the word length in bits) this yields the total number of bits to be approximately 12.5 million. Assuming a file transfer rate of 27,500 bits per second, it will take approximately 7 minutes and 30 seconds to transmit the system 23.4-0A.

Multicsの開発コミュニティーでは、2つのシステム間でMulticsシステムテープを送信するためにファイル転送機能を使うことに大きな関心が寄せられているため、ここで現在のMSTの送信にかかる時間の見積もりを示します。MST 23.4-0Aには334,231ワードが含まれています。これに36（ビット単位のワード長）を掛けると、総ビット数は約1250万になります。ファイル転送速度を毎秒27,500ビットと仮定すると、システム23.4-0Aの送信には約7分30秒かかります。

In the experiment outlined above, there was only one file being transferred at any given tine between the two systems. We conducted another experiment to get an estimate of performance in the situation of multiple file transfers occurring simultaneously. This experiment consisted of first two, and then three, simultaneous file-transfers from the development system to the service system. These file transfers were started by different processes logged in from separate consoles. Because these file-transfers were started manually, we could not obtain perfect simultaneity and results obtained for the total bandwidth are essentially approximate. For two simultaneous file transfers the total bit rate was approximately 40,000 bits per second and bit rate for each file transfer was approximately 20,000 bits per second. For three simultaneous file transfers, total bit rate remained at approximately 40,000 bits per second and bit rate for individual transfers was approximately 13,500 bits per second.

上で概説した実験では、2つのシステム間で一度に転送されるファイルは1つだけでした。複数のファイル転送が同時に行われる状況での性能を見積もるため、私たちはもう1つ実験を行いました。この実験では、開発用システムからサービス用システムへ、まず2つ、次に3つのファイル転送を同時に行いました。これらのファイル転送は、別々のコンソールからログインした異なるプロセスによって開始しました。これらのファイル転送は手動で開始したため、完全な同時性は得られず、得られた合計帯域幅の結果はあくまで概算です。2つのファイル転送を同時に行った場合、合計ビットレートは約毎秒40,000ビットで、各ファイル転送のビットレートは約毎秒20,000ビットでした。3つのファイル転送を同時に行った場合、合計ビットレートは約毎秒40,000ビットのままで、個々の転送のビットレートは約毎秒13,500ビットでした。
