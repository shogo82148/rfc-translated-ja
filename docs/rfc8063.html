RFC 8063

Key Relay Mapping for the Extensible Provisioning Protocol

RFC 8063

拡張可能なプロビジョニングプロトコルのための鍵中継マッピング

Abstract

概要

This document describes an Extensible Provisioning Protocol (EPP) mapping for a key relay object that relays DNSSEC key material between EPP clients using the poll queue defined in RFC 5730.

この文書は、RFC 5730で定義されたポーリングキューを使用してEPPクライアント間でDNSSECの鍵素材を中継する、鍵中継（key relay）オブジェクトのための拡張可能なプロビジョニングプロトコル（EPP）マッピングについて説明します。

This key relay mapping will help facilitate changing the DNS operator of a domain while keeping the DNSSEC chain of trust intact.

この鍵中継マッピングは、DNSSECの信頼の連鎖を維持したまま、ドメインのDNS運用者を変更することを容易にするのに役立ちます。

1. Introduction

1. はじめに

There are certain transactions initiated by a DNS operator that require an authenticated exchange of information between DNS operators. Often, there is no direct channel between these parties or it is non-scalable and insecure.

DNS運用者が開始するトランザクションの中には、DNS運用者間で認証された情報交換を必要とするものがあります。多くの場合、これらの当事者間には直接的なチャネルがないか、あってもスケーラブルでなく安全でもありません。

One such transaction is the exchange of DNSSEC key material when changing the DNS operator for DNSSEC-signed zones. We suggest that DNS operators use the administrative EPP channel to bootstrap the delegation by relaying DNSSEC key material for the zone.

そのようなトランザクションの1つが、DNSSECで署名されたゾーンのDNS運用者を変更する際のDNSSECの鍵素材の交換です。私たちは、DNS運用者がEPPの管理チャネルを使用してゾーンのDNSSECの鍵素材を中継することで、委任をブートストラップすることを提案します。

In this document, we define an EPP extension to send DNSSEC key material between EPP clients. This allows DNS operators to automatically, reliably, and securely bootstrap the transfer of a domain name while keeping the DNSSEC chain of trust intact.

この文書では、EPPクライアント間でDNSSECの鍵素材を送るためのEPP拡張を定義します。これにより、DNS運用者は、DNSSECの信頼の連鎖を維持したまま、ドメイン名の移管を自動的に、確実に、かつ安全にブートストラップできます。

1.2. Secure Transfer of DNSSEC Key Material

1.2. DNSSECの鍵素材の安全な転送

Exchanging DNSSEC key material in preparation of a domain name transfer is one of the phases in the life cycle of a domain name [DNSOP].

ドメイン名の移管に備えてDNSSECの鍵素材を交換することは、ドメイン名のライフサイクルにおけるフェーズの1つです[DNSOP]。

DNS operators need to exchange DNSSEC key material before the registration data can be changed to keep the DNSSEC chain of trust intact. This exchange is normally initiated through the gaining registrar.

DNSSECの信頼の連鎖を維持するために、DNS運用者は、登録データを変更できるようになる前にDNSSECの鍵素材を交換する必要があります。この交換は通常、移管先レジストラーを通じて開始されます。

The gaining and losing DNS operators could talk directly to each other (see Figure 1) to exchange the DNSKEY, but often there is no trusted path between the two. As both can securely interact with the registry over the administrative channel through the registrar, the registry can act as a relay for the key material exchange.

移管先と移管元のDNS運用者が直接やり取りしてDNSKEYを交換することもできますが（図1を参照）、多くの場合、両者の間には信頼できる経路がありません。どちらもレジストラーを介して管理チャネル上でレジストリーと安全にやり取りできるので、レジストリーが鍵素材の交換を中継する役割を果たせます。

The registry is merely used as a relay channel. Therefore, it is up to the losing DNS operator to complete the intended transaction. The registry SHOULD have certain policies in place that require the losing DNS operator to cooperate with this transaction; however, this is beyond the scope of this document. This document focuses on the EPP protocol syntax.

レジストリーは単に中継チャネルとして使われるだけです。したがって、意図されたトランザクションを完了させるかどうかは移管元のDNS運用者次第です。レジストリーは、移管元のDNS運用者にこのトランザクションへの協力を求める何らかのポリシーを用意しておくべきです（SHOULD）が、これはこの文書の範囲外です。この文書はEPPプロトコルの構文に焦点を当てています。

There is no distinction in the EPP protocol between Registrars and DNS operators, and there is only mention of an EPP client and EPP server. Therefore, the term "EPP client" will be used for the interaction with the EPP server for relaying DNSSEC key material.

EPPプロトコルではレジストラーとDNS運用者を区別しておらず、EPPクライアントとEPPサーバーについて言及しているだけです。したがって、DNSSECの鍵素材を中継するためのEPPサーバーとのやり取りについては、「EPPクライアント」という用語を使用します。

2. Object Attributes

2. オブジェクトの属性

2.1. DNSSEC Key Material

2.1. DNSSECの鍵素材

The DNSSEC key material is represented in EPP by a <keyRelayData> element.

DNSSECの鍵素材は、EPPでは<keyRelayData>要素で表されます。

2.1.1. <keyRelayData> Element

2.1.1. <keyRelayData>要素

The <keyRelayData> contains the following elements:

<keyRelayData>には、次の要素が含まれます。

  • One REQUIRED <keyData> element that contains the DNSSEC key material as described in [RFC5910], Section 4.
  • An OPTIONAL <expiry> element that describes the expected lifetime of the relayed key(s) in the zone. When the <expiry> element is provided, the losing DNS operator SHOULD remove the inserted key material from the zone after the expiry time. This may be because the transaction that needed the insertion should be either completed or abandoned by that time. If a client receives a key relay object that has been sent previously, it MUST update the expiry time of the key material. This enables the clients to update the lifetime of the key material when a transfer is delayed.
  • [RFC5910], セクション4で説明されているDNSSECの鍵素材を含む、1つの<keyData>要素。この要素は要求されています（REQUIRED）。
  • 中継される鍵のゾーン内での想定される有効期間を記述する<expiry>要素。この要素は選択できます（OPTIONAL）。<expiry>要素が提供された場合、移管元のDNS運用者は、有効期限が過ぎたら、挿入した鍵素材をゾーンから削除すべきです（SHOULD）。その理由としては、挿入を必要としたトランザクションがその時点までに完了しているか中止されているはずだということが考えられます。以前に送信されたことのある鍵中継オブジェクトをクライアントが受信した場合、クライアントは鍵素材の有効期限を更新しなければなりません（MUST）。これにより、移管が遅れた場合に、クライアントが鍵素材の有効期間を更新できます。

The <expiry> element MUST contain exactly one of the following child elements:

<expiry>要素は、次の子要素のうちちょうど1つを含まなければなりません（MUST）。

<absolute>:
The DNSSEC key material is valid from the current date and time until it expires on the specified date and time. If a date in the past is provided, this MUST be interpreted as a revocation of a previously sent key relay object.
<relative>:
The DNSSEC key material is valid from the current date and time until the end of the specified duration. If a period of zero is provided, this MUST be interpreted as a revocation of a previously sent key relay object.
<absolute>：
DNSSECの鍵素材は、現在の日時から、指定された日時に期限切れになるまで有効です。過去の日付が提供された場合、これは以前に送信された鍵中継オブジェクトの失効として解釈しなければなりません（MUST）。
<relative>：
DNSSECの鍵素材は、現在の日時から、指定された期間の終わりまで有効です。ゼロの期間が提供された場合、これは以前に送信された鍵中継オブジェクトの失効として解釈しなければなりません（MUST）。

3. EPP Command Mapping

3. EPPコマンドのマッピング

A detailed description of the EPP syntax and semantics can be found in the EPP core protocol specification [RFC5730]. The command mapping described here is specifically for use in this key relay mapping.

EPPの構文とセマンティクスの詳細な説明は、EPPのコアプロトコル仕様[RFC5730]にあります。ここで説明するコマンドマッピングは、特にこの鍵中継マッピングで使用するためのものです。

3.1. EPP Query Commands

3.1. EPPクエリーコマンド

EPP provides three commands to retrieve object information: <check> to determine if an object is known to the server, <info> to retrieve detailed information associated with an object, and <transfer> to retrieve object transfer status information.

EPPは、オブジェクトの情報を取得するための3つのコマンドを提供しています。オブジェクトがサーバーに知られているかどうかを判断する<check>、オブジェクトに関連付けられた詳細な情報を取得する<info>、オブジェクトの移管ステータス情報を取得する<transfer>です。

3.1.1. EPP <check> Command

3.1.1. EPP <check>コマンド

Check that semantics do not apply to key relay objects, so there is no mapping defined for the EPP <check> command and the EPP <check> response.

<check>のセマンティクスは鍵中継オブジェクトには適用されないため、EPPの<check>コマンドとEPPの<check>レスポンスに対するマッピングは定義されていません。

3.1.2. EPP <info> Command

3.1.2. EPP <info>コマンド

Info command semantics do not apply to the key relay objects, so there is no mapping defined for the EPP <info> command.

<info>コマンドのセマンティクスは鍵中継オブジェクトには適用されないため、EPPの<info>コマンドに対するマッピングは定義されていません。

The EPP <info> response for key relay objects is used in the EPP poll response, as described in [RFC5730]. The key relay object created with the <create> command, described in Section 3.2.1 is inserted into the receiving client's poll queue. The receiving client will receive the key relay object using the EPP <poll> command, as described in [RFC5730].

鍵中継オブジェクトに対するEPPの<info>レスポンスは、[RFC5730]で説明されているように、EPPのポーリングレスポンスで使用されます。セクション3.2.1で説明する<create>コマンドで作成された鍵中継オブジェクトは、受信側クライアントのポーリングキューに挿入されます。受信側クライアントは、[RFC5730]で説明されているように、EPPの<poll>コマンドを使用して鍵中継オブジェクトを受信します。

When a <poll> command has been processed successfully for a key relay poll message, the EPP <resData> element MUST contain a child <keyrelay:infData> element that is identified by the keyrelay namespace. The <keyrelay:infData> element contains the following child elements:

鍵中継のポーリングメッセージに対する<poll>コマンドが正常に処理された場合、EPPの<resData>要素は、keyrelay名前空間で識別される子要素<keyrelay:infData>を含まなければなりません（MUST）。<keyrelay:infData>要素には、次の子要素が含まれます。

  • A REQUIRED <name> element containing the domain name for which the DNSSEC key material is relayed.
  • A REQUIRED <authInfo> element that contains authorization information associated with the domain object ([RFC5731], Section 3.2.1).
  • One or more REQUIRED <keyRelayData> elements containing data to be relayed, as defined in Section 2.1. A server MAY apply a server policy that specifies the number of <keyRelayData> elements that can be incorporated. When a server policy is violated, a server MUST respond with an EPP result code 2308 "Data management policy violation".
  • An OPTIONAL <crDate> element that contains the date and time of the submitted <create> command.
  • An OPTIONAL <reID> element that contains the identifier of the client that requested the key relay.
  • An OPTIONAL <acID> element that contains the identifier of the client that SHOULD act upon the key relay.
  • DNSSECの鍵素材の中継対象となるドメイン名を含む<name>要素。この要素は要求されています（REQUIRED）。
  • ドメインオブジェクトに関連付けられた認可情報を含む<authInfo>要素（[RFC5731], セクション3.2.1）。この要素は要求されています（REQUIRED）。
  • セクション2.1で定義されている、中継されるデータを含む<keyRelayData>要素。この要素は1つ以上要求されています（REQUIRED）。サーバーは、含めることのできる<keyRelayData>要素の数を指定するサーバーポリシーを適用してもよいです（MAY）。サーバーポリシーに違反した場合、サーバーはEPPの結果コード2308「Data management policy violation」で応答しなければなりません（MUST）。
  • 送信された<create>コマンドの日時を含む<crDate>要素。この要素は選択できます（OPTIONAL）。
  • 鍵中継を要求したクライアントの識別子を含む<reID>要素。この要素は選択できます（OPTIONAL）。
  • クライアントの識別子を含む<acID>要素。この要素は選択できます（OPTIONAL）。この識別子が示すクライアントは、鍵中継に基づいて処理を行うべきです（SHOULD）。

3.2. EPP Transform Commands

3.2. EPP変換コマンド

EPP provides five commands to transform objects: <create> to create an instance of an object, <delete> to delete an instance of an object, <renew> to extend the validity period of an object, <transfer> to manage object sponsorship changes, and <update> to change information associated with an object.

EPPは、オブジェクトを変換するための5つのコマンドを提供しています。オブジェクトのインスタンスを作成する<create>、オブジェクトのインスタンスを削除する<delete>、オブジェクトの有効期間を延長する<renew>、オブジェクトのスポンサーの変更を管理する<transfer>、オブジェクトに関連付けられた情報を変更する<update>です。

3.2.1. EPP <create> Command

3.2.1. EPP <create>コマンド

The EPP <create> command provides a transform operation that allows a client to create a key relay object that includes the domain name and DNSSEC key material to be relayed. When the <create> command is validated, the server MUST insert an EPP <poll> message, using the key relay info response (see Section 3.1.2), in the receiving client's poll queue that belongs to the registrar on record of the provided domain name.

EPPの<create>コマンドは、ドメイン名と、中継されるDNSSECの鍵素材を含む鍵中継オブジェクトをクライアントが作成できるようにする変換操作を提供します。<create>コマンドの妥当性が確認されると、サーバーは、鍵中継のinfoレスポンス（セクション3.1.2を参照）を使用したEPPの<poll>メッセージを、指定されたドメイン名の記録上のレジストラー（registrar on record）に属する受信側クライアントのポーリングキューに挿入しなければなりません（MUST）。

  • A REQUIRED <keyrelay:name> element containing the domain name for which the DNSSEC key material is relayed.

6. Security Considerations

6. セキュリティーに関する考慮事項

A server SHOULD NOT perform any transformation on data under server management when processing a <keyrelay:create> command. The intent of this command is to put DNSSEC key material on the poll queue of another client. Exceptions to this recommendation are allowable only for the purposes of achieving interoperability with the different server policies that have already implemented this EPP extension.

サーバーは、<keyrelay:create>コマンドを処理する際に、サーバーの管理下にあるデータに対していかなる変換も実行すべきではありません（SHOULD NOT）。このコマンドの意図は、DNSSECの鍵素材を別のクライアントのポーリングキューに置くことです。この推奨事項に対する例外は、このEPP拡張をすでに実装しているさまざまなサーバーポリシーとの相互運用性を達成する目的に限り認められます。

Any EPP client can use this mechanism to put data on the message queue of another EPP client, allowing for the potential of a denial-of-service attack. However, this can and should be detected by the server. A server MAY set a server policy that limits or rejects a <keyrelay:create> command if it detects that the mechanism is being abused.

どのEPPクライアントでもこのメカニズムを使用して別のEPPクライアントのメッセージキューにデータを置くことができるため、サービス拒否攻撃が起こる可能性があります。しかし、これはサーバーが検出でき、また検出すべきです。サーバーは、このメカニズムが悪用されていることを検出した場合に<keyrelay:create>コマンドを制限または拒否するサーバーポリシーを設定してもよいです（MAY）。

For the <keyrelay:keyRelayData> data, a correct <domain:authInfo> element should be used as an indication that putting the key material on the receiving EPP clients poll queue is authorized by the registrant of that domain name. The authorization of EPP clients to perform DNS changes is not covered in this document as it depends on registry-specific policy.

<keyrelay:keyRelayData>のデータについては、正しい<domain:authInfo>要素を、受信側EPPクライアントのポーリングキューに鍵素材を置くことがそのドメイン名の登録者によって認可されていることを示すものとして使用すべきです。DNSの変更を実行するためのEPPクライアントの認可は、レジストリー固有のポリシーに依存するため、この文書では扱いません。

A client that uses this mechanism to send DNSSEC key material to another client could verify through DNS that the DNSSEC key material is added to the authoritative zone of the domain. This check can be used to verify that the DNSSEC key material has traveled end-to-end from the gaining DNS operator to the losing DNS operator. This check does not tell anything about the DNSSEC chain of trust and can merely be used as a verification of a successful transfer of the DNSSEC key material.

このメカニズムを使用してDNSSECの鍵素材を別のクライアントに送信するクライアントは、そのDNSSECの鍵素材がドメインの権威ゾーンに追加されていることをDNSを通じて検証できます。このチェックは、DNSSECの鍵素材が移管先のDNS運用者から移管元のDNS運用者までエンドツーエンドで届いたことを検証するために使用できます。このチェックはDNSSECの信頼の連鎖については何も示さず、DNSSECの鍵素材の転送が成功したことの検証として使用できるにすぎません。
