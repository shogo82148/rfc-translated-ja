RFC 8922

A Survey of the Interaction between Security Protocols and Transport Services

RFC 8922

セキュリティープロトコルとトランスポートサービスの相互作用に関する調査

Abstract

概要

This document provides a survey of commonly used or notable network security protocols, with a focus on how they interact and integrate with applications and transport protocols. Its goal is to supplement efforts to define and catalog Transport Services by describing the interfaces required to add security protocols. This survey is not limited to protocols developed within the scope or context of the IETF, and those included represent a superset of features a Transport Services system may need to support.

この文書は、よく使われている、または注目すべきネットワークセキュリティープロトコルについて、それらがアプリケーションやトランスポートプロトコルとどのように相互作用し統合されるかに焦点を当てて調査したものです。 その目的は、セキュリティープロトコルを追加するために必要なインターフェイスを説明することで、トランスポートサービス（Transport Services）を定義し目録化する取り組みを補完することです。 この調査はIETFの範囲や文脈の中で開発されたプロトコルに限定されておらず、取り上げたプロトコルは、トランスポートサービスシステムがサポートする必要のある可能性がある機能の上位集合を表しています。

1. Introduction

1. はじめに

Services and features provided by transport protocols have been cataloged in [RFC8095]. This document supplements that work by surveying commonly used and notable network security protocols, and identifying the interfaces between these protocols and both transport protocols and applications. It examines Transport Layer Security (TLS), Datagram Transport Layer Security (DTLS), IETF QUIC, Google QUIC (gQUIC), tcpcrypt, Internet Protocol Security (IPsec), Secure Real-time Transport Protocol (SRTP) with DTLS, WireGuard, CurveCP, and MinimaLT. For each protocol, this document provides a brief description. Then, it describes the interfaces between these protocols and transports in Section 4 and the interfaces between these protocols and applications in Section 5.

トランスポートプロトコルが提供するサービスと機能は、[RFC8095]で目録化されています。 この文書は、よく使われている、または注目すべきネットワークセキュリティープロトコルを調査し、それらのプロトコルとトランスポートプロトコルおよびアプリケーションとの間のインターフェイスを特定することで、その作業を補完します。 この文書では、Transport Layer Security（TLS）、Datagram Transport Layer Security（DTLS）、IETF QUIC、Google QUIC（gQUIC）、tcpcrypt、Internet Protocol Security（IPsec）、DTLSを用いたSecure Real-time Transport Protocol（SRTP）、WireGuard、CurveCP、MinimaLTを取り上げます。 この文書は、各プロトコルについて簡単な説明を示します。 そのうえで、Section 4でこれらのプロトコルとトランスポートの間のインターフェイスを、Section 5でこれらのプロトコルとアプリケーションの間のインターフェイスを説明します。

A Transport Services system exposes an interface for applications to access various (secure) transport protocol features. The security protocols included in this survey represent a superset of functionality and features a Transport Services system may need to support both internally and externally (via an API) for applications [TAPS-ARCH]. Ubiquitous IETF protocols such as (D)TLS, as well as non-standard protocols such as gQUIC, are included despite overlapping features. As such, this survey is not limited to protocols developed within the scope or context of the IETF. Outside of this candidate set, protocols that do not offer new features are omitted. For example, newer protocols such as WireGuard make unique design choices that have implications for and limitations on application usage. In contrast, protocols such as secure shell (SSH) [RFC4253], GRE [RFC2890], the Layer 2 Tunneling Protocol (L2TP) [RFC5641], and Application Layer Transport Security (ALTS) [ALTS] are omitted since they do not provide interfaces deemed unique.

トランスポートサービスシステムは、アプリケーションがさまざまな（安全な）トランスポートプロトコルの機能にアクセスするためのインターフェイスを公開します。 この調査に含まれるセキュリティープロトコルは、トランスポートサービスシステムがアプリケーションのために内部的にも外部的にも（APIを介して）サポートする必要がある可能性のある機能の上位集合を表しています[TAPS-ARCH]。 (D)TLSのような広く使われているIETFプロトコルや、gQUICのような標準ではないプロトコルも、機能が重複しているにもかかわらず含めています。 このように、この調査はIETFの範囲や文脈の中で開発されたプロトコルに限定されていません。 この候補の集合以外で、新しい機能を提供しないプロトコルは省略しています。 たとえば、WireGuardのような新しいプロトコルは独自の設計上の選択をしており、それがアプリケーションでの使用に影響や制限を与えます。 対照的に、セキュアシェル（SSH）[RFC4253]、GRE [RFC2890]、レイヤー2トンネリングプロトコル（L2TP）[RFC5641]、Application Layer Transport Security（ALTS）[ALTS]のようなプロトコルは、独自とみなせるインターフェイスを提供しないため省略しています。

Authentication-only protocols such as the TCP Authentication Option (TCP-AO) [RFC5925] and the IPsec Authentication Header (AH) [RFC4302] are excluded from this survey. TCP-AO adds authentication to long-lived TCP connections, e.g., replay protection with per-packet Message Authentication Codes. (TCP-AO obsoletes TCP MD5 "signature" options specified in [RFC2385].) One primary use case of TCP-AO is for protecting BGP connections. Similarly, AH adds per-datagram authentication and integrity, along with replay protection. Despite these improvements, neither protocol sees general use and both lack critical properties important for emergent transport security protocols, such as confidentiality and privacy protections. Such protocols are thus omitted from this survey.

TCP認証オプション（TCP-AO）[RFC5925]やIPsec認証ヘッダー（AH）[RFC4302]のような認証のみのプロトコルは、この調査から除外しています。 TCP-AOは、長時間持続するTCPコネクションに認証を追加します。たとえば、パケットごとのメッセージ認証コードによるリプレイ保護です。 （TCP-AOは、[RFC2385]で規定されたTCP MD5「署名」オプションを廃止します。） TCP-AOの主なユースケースの1つは、BGPコネクションの保護です。 同様に、AHは、データグラムごとの認証と完全性をリプレイ保護とともに追加します。 こうした改善にもかかわらず、どちらのプロトコルも一般には使われておらず、どちらも機密性やプライバシー保護といった、新たに登場しつつあるトランスポートセキュリティープロトコルにとって重要な特性を欠いています。 そのため、そのようなプロトコルはこの調査から省略しています。

This document only surveys point-to-point protocols; multicast protocols are out of scope.

この文書はポイントツーポイントのプロトコルのみを調査します。マルチキャストプロトコルは範囲外です。

1.1. Goals

1.1. 目標

This survey is intended to help identify the most common interface surfaces between security protocols and transport protocols, and between security protocols and applications.

この調査は、セキュリティープロトコルとトランスポートプロトコルの間、およびセキュリティープロトコルとアプリケーションの間で、最も一般的なインターフェイスの接点を特定するのに役立つことを意図しています。

One of the goals of the Transport Services effort is to define a common interface for using transport protocols that allows software using transport protocols to easily adopt new protocols that provide similar feature sets. The survey of the dependencies security protocols have upon transport protocols can guide implementations in determining which transport protocols are appropriate to be able to use beneath a given security protocol. For example, a security protocol that expects to run over a reliable stream of bytes, like TLS, restricts the set of transport protocols that can be used to those that offer a reliable stream of bytes.

トランスポートサービスの取り組みの目標の1つは、トランスポートプロトコルを使用するための共通のインターフェイスを定義し、トランスポートプロトコルを使用するソフトウェアが、同様の機能セットを提供する新しいプロトコルを容易に採用できるようにすることです。 セキュリティープロトコルがトランスポートプロトコルに対して持つ依存関係を調査することは、あるセキュリティープロトコルの下でどのトランスポートプロトコルを使用するのが適切かを実装が判断する際の指針となります。 たとえば、TLSのように信頼性のあるバイトストリーム上で動作することを想定するセキュリティープロトコルでは、使用できるトランスポートプロトコルの集合が、信頼性のあるバイトストリームを提供するものに限定されます。

Defining the common interfaces that security protocols provide to applications also allows interfaces to be designed in a way that common functionality can use the same APIs. For example, many security protocols that provide authentication let the application be involved in peer identity validation. Any interface to use a secure transport protocol stack thus needs to allow applications to perform this action during connection establishment.

セキュリティープロトコルがアプリケーションに提供する共通のインターフェイスを定義することで、共通の機能が同じAPIを使用できるようにインターフェイスを設計することも可能になります。 たとえば、認証を提供する多くのセキュリティープロトコルでは、アプリケーションがピアの識別情報の検証に関与できます。 したがって、安全なトランスポートプロトコルスタックを使用するためのインターフェイスはいずれも、アプリケーションがコネクションの確立中にこの操作を実行できるようにする必要があります。

1.2. Non-goals

1.2. 目標としないこと

While this survey provides similar analysis to that which was performed for transport protocols in [RFC8095], it is important to distinguish that the use of security protocols requires more consideration.

この調査は、[RFC8095]でトランスポートプロトコルについて行われたのと同様の分析を提供しますが、セキュリティープロトコルの使用にはより多くの考慮が必要であるという点を区別することが重要です。

It is not a goal to allow software implementations to automatically switch between different security protocols, even where their interfaces to transport and applications are equivalent. Even between versions, security protocols have subtly different guarantees and vulnerabilities. Thus, any implementation needs to only use the set of protocols and algorithms that are requested by applications or by a system policy.

トランスポートやアプリケーションに対するインターフェイスが同等であっても、ソフトウェア実装が異なるセキュリティープロトコル間を自動的に切り替えられるようにすることは目標ではありません。 セキュリティープロトコルは、バージョン間でさえ、保証や脆弱性が微妙に異なります。 したがって、どの実装も、アプリケーションまたはシステムポリシーによって要求されたプロトコルとアルゴリズムの集合のみを使用する必要があります。

Different security protocols also can use incompatible notions of peer identity and authentication, and cryptographic options. It is not a goal to identify a common set of representations for these concepts.

また、異なるセキュリティープロトコルは、ピアの識別情報や認証、暗号のオプションについて、互換性のない概念を使用することがあります。 これらの概念に共通する表現の集合を特定することは目標ではありません。

The protocols surveyed in this document represent a superset of functionality and features a Transport Services system may need to support. It does not list all transport protocols that a Transport Services system may need to implement, nor does it mandate that a Transport Service system implement any particular protocol.

この文書で調査したプロトコルは、トランスポートサービスシステムがサポートする必要がある可能性のある機能の上位集合を表しています。 この文書は、トランスポートサービスシステムが実装する必要がある可能性のあるすべてのトランスポートプロトコルを列挙するものではなく、トランスポートサービスシステムが特定のプロトコルを実装することを義務付けるものでもありません。

A Transport Services system may implement any secure transport protocol that provides the described features. In doing so, it may need to expose an interface to the application to configure these features.

トランスポートサービスシステムは、説明した機能を提供するどのような安全なトランスポートプロトコルを実装してもかまいません。 その際、これらの機能を設定するためのインターフェイスをアプリケーションに公開する必要がある場合があります。

2. Terminology

2. 用語

The following terms are used throughout this document to describe the roles and interactions of transport security protocols (some of which are also defined in [RFC8095]):

この文書全体を通して、トランスポートセキュリティープロトコルの役割とやり取りを説明するために次の用語を使用します（一部は[RFC8095]でも定義されています）。

Transport Feature:
a specific end-to-end feature that the transport layer provides to an application. Examples include confidentiality, reliable delivery, ordered delivery, and message-versus-stream orientation.
Transport Service:
a set of Transport Features, without an association to any given framing protocol, that provides functionality to an application.
Transport Services system:
a software component that exposes an interface to different Transport Services to an application.
Transport Protocol:
an implementation that provides one or more different Transport Services using a specific framing and header format on the wire. A Transport Protocol services an application, whether directly or in conjunction with a security protocol.
Application:
an entity that uses a transport protocol for end-to-end delivery of data across the network. This may also be an upper layer protocol or tunnel encapsulation.
Security Protocol:
a defined network protocol that implements one or more security features, such as authentication, encryption, key generation, session resumption, and privacy. Security protocols may be used alongside transport protocols, and in combination with other security protocols when appropriate.
Handshake Protocol:
a protocol that enables peers to validate each other and to securely establish shared cryptographic context.
Record:
framed protocol messages.
Record Protocol:
a security protocol that allows data to be divided into manageable blocks and protected using shared cryptographic context.
Session:
an ephemeral security association between applications.
Connection:
the shared state of two or more endpoints that persists across messages that are transmitted between these endpoints. A connection is a transient participant of a session, and a session generally lasts between connection instances.
Peer:
an endpoint application party to a session.
Client:
the peer responsible for initiating a session.
Server:
the peer responsible for responding to a session initiation.
トランスポート機能（Transport Feature）：
トランスポート層がアプリケーションに提供する、特定のエンドツーエンドの機能。 例としては、機密性、信頼性のある配送、順序どおりの配送、メッセージ指向かストリーム指向か、などがあります。
トランスポートサービス（Transport Service）：
特定のフレーミングプロトコルとは結び付いていない、アプリケーションに機能を提供するトランスポート機能の集合。
トランスポートサービスシステム（Transport Services system）：
さまざまなトランスポートサービスへのインターフェイスをアプリケーションに公開するソフトウェアコンポーネント。
トランスポートプロトコル（Transport Protocol）：
回線上の特定のフレーミングとヘッダー形式を用いて、1つ以上のさまざまなトランスポートサービスを提供する実装。 トランスポートプロトコルは、直接、またはセキュリティープロトコルと組み合わせて、アプリケーションにサービスを提供します。
アプリケーション（Application）：
ネットワークを越えたエンドツーエンドのデータ配送のためにトランスポートプロトコルを使用するエンティティー。 上位層のプロトコルやトンネルのカプセル化である場合もあります。
セキュリティープロトコル（Security Protocol）：
認証、暗号化、鍵生成、セッション再開、プライバシーなど、1つ以上のセキュリティー機能を実装する、定義されたネットワークプロトコル。 セキュリティープロトコルは、トランスポートプロトコルと並んで使用されることがあり、適切な場合にはほかのセキュリティープロトコルと組み合わせて使用されることもあります。
ハンドシェイクプロトコル（Handshake Protocol）：
ピアが互いを検証し、共有された暗号コンテキストを安全に確立できるようにするプロトコル。
レコード（Record）：
フレーム化されたプロトコルメッセージ。
レコードプロトコル（Record Protocol）：
データを扱いやすいブロックに分割し、共有された暗号コンテキストを使って保護できるようにするセキュリティープロトコル。
セッション（Session）：
アプリケーション間の一時的なセキュリティーアソシエーション。
コネクション（Connection）：
2つ以上のエンドポイント間で送信されるメッセージをまたいで持続する、それらのエンドポイントの共有状態。 コネクションはセッションの一時的な参加者であり、セッションは一般にコネクションのインスタンスをまたいで持続します。
ピア（Peer）：
セッションの当事者であるエンドポイントのアプリケーション。
クライアント（Client）：
セッションを開始する役割を担うピア。
サーバー（Server）：
セッションの開始に応答する役割を担うピア。

3. Transport Security Protocol Descriptions

3. トランスポートセキュリティープロトコルの説明

This section contains brief transport and security descriptions of various security protocols currently used to protect data being sent over a network. These protocols are grouped based on where in the protocol stack they are implemented, which influences which parts of a packet they protect: Generic application payload, application payload for specific application-layer protocols, both application payload and transport headers, or entire IP packets.

このセクションでは、ネットワーク上で送信されるデータを保護するために現在使われているさまざまなセキュリティープロトコルについて、トランスポートとセキュリティーの観点から簡単に説明します。 これらのプロトコルは、プロトコルスタックのどこで実装されるかに基づいてグループ化しています。これは、パケットのどの部分を保護するかに影響します。 すなわち、汎用的なアプリケーションペイロード、特定のアプリケーション層プロトコルのアプリケーションペイロード、アプリケーションペイロードとトランスポートヘッダーの両方、またはIPパケット全体です。

Note that not all security protocols can be easily categorized, e.g., as some protocols can be used in different ways or in combination with other protocols. One major reason for this is that channel security protocols often consist of two components:

たとえば、一部のプロトコルはさまざまな方法で、あるいはほかのプロトコルと組み合わせて使用できるため、すべてのセキュリティープロトコルを簡単に分類できるわけではないことに注意してください。 その大きな理由の1つは、チャネルセキュリティープロトコルが多くの場合2つのコンポーネントで構成されていることです。

  • A handshake protocol, which is responsible for negotiating parameters, authenticating the endpoints, and establishing shared keys.
  • A record protocol, which is used to encrypt traffic using keys and parameters provided by the handshake protocol.
  • ハンドシェイクプロトコル。パラメーターのネゴシエーション、エンドポイントの認証、共有鍵の確立を担います。
  • レコードプロトコル。ハンドシェイクプロトコルが提供する鍵とパラメーターを使ってトラフィックを暗号化するために使われます。

For some protocols, such as tcpcrypt, these two components are tightly integrated. In contrast, for IPsec, these components are implemented in separate protocols: AH and the Encapsulating Security Payload (ESP) are record protocols, which can use keys supplied by the handshake protocol Internet Key Exchange Protocol Version 2 (IKEv2), by other handshake protocols, or by manual configuration. Moreover, some protocols can be used in different ways: While the base TLS protocol as defined in [RFC8446] has an integrated handshake and record protocol, TLS or DTLS can also be used to negotiate keys for other protocols, as in DTLS-SRTP, or the handshake protocol can be used with a separate record layer, as in QUIC [QUIC-TRANSPORT].

tcpcryptなど一部のプロトコルでは、これら2つのコンポーネントは緊密に統合されています。 対照的に、IPsecでは、これらのコンポーネントは別々のプロトコルで実装されています。 AHとカプセル化セキュリティーペイロード（ESP）はレコードプロトコルであり、ハンドシェイクプロトコルであるインターネット鍵交換プロトコルバージョン2（IKEv2）や、ほかのハンドシェイクプロトコル、または手動設定によって提供される鍵を使用できます。 さらに、一部のプロトコルはさまざまな方法で使用できます。 [RFC8446]で定義されている基本のTLSプロトコルは、ハンドシェイクプロトコルとレコードプロトコルが統合されていますが、DTLS-SRTPのようにTLSやDTLSをほかのプロトコルの鍵のネゴシエーションに使うこともできますし、QUIC [QUIC-TRANSPORT]のようにハンドシェイクプロトコルを別のレコード層と組み合わせて使うこともできます。

3.1. Application Payload Security Protocols

3.1. アプリケーションペイロードのセキュリティープロトコル

The following protocols provide security that protects application payloads sent over a transport. They do not specifically protect any headers used for transport-layer functionality.

次のプロトコルは、トランスポート上で送信されるアプリケーションペイロードを保護するセキュリティーを提供します。 これらは、トランスポート層の機能に使われるヘッダーを特に保護するものではありません。

3.1.1. TLS

3.1.1. TLS

TLS (Transport Layer Security) [RFC8446] is a common protocol used to establish a secure session between two endpoints. Communication over this session prevents "eavesdropping, tampering, and message forgery." TLS consists of a tightly coupled handshake and record protocol. The handshake protocol is used to authenticate peers, negotiate protocol options such as cryptographic algorithms, and derive session-specific keying material. The record protocol is used to marshal and, once the handshake has sufficiently progressed, encrypt data from one peer to the other. This data may contain handshake messages or raw application data.

TLS（Transport Layer Security）[RFC8446]は、2つのエンドポイント間に安全なセッションを確立するために使われる一般的なプロトコルです。 このセッション上の通信は、「盗聴、改ざん、メッセージの偽造（eavesdropping, tampering, and message forgery）」を防ぎます。 TLSは、緊密に結合したハンドシェイクプロトコルとレコードプロトコルで構成されています。 ハンドシェイクプロトコルは、ピアの認証、暗号アルゴリズムなどのプロトコルオプションのネゴシエーション、セッション固有の鍵素材の導出に使われます。 レコードプロトコルは、一方のピアから他方へのデータを整列し、ハンドシェイクが十分に進んだら暗号化するために使われます。 このデータには、ハンドシェイクメッセージや生のアプリケーションデータが含まれる場合があります。

3.1.2. DTLS

3.1.2. DTLS

DTLS (Datagram Transport Layer Security) [RFC6347] [DTLS-1.3] is based on TLS, but differs in that it is designed to run over unreliable datagram protocols like UDP instead of TCP. DTLS modifies the protocol to make sure it can still provide equivalent security guarantees to TLS with the exception of order protection/non-replayability. DTLS was designed to be as similar to TLS as possible, so this document assumes that all properties from TLS are carried over except where specified.

DTLS（Datagram Transport Layer Security）[RFC6347] [DTLS-1.3]はTLSに基づいていますが、TCPではなくUDPのような信頼性のないデータグラムプロトコル上で動作するように設計されている点が異なります。 DTLSは、順序の保護／リプレイ不可能性を除いて、TLSと同等のセキュリティー保証を引き続き提供できるようにプロトコルを変更しています。 DTLSはできる限りTLSに似せて設計されているため、この文書では、特に指定がない限り、TLSのすべての特性が引き継がれるものとします。

3.2. Application-Specific Security Protocols

3.2. アプリケーション固有のセキュリティープロトコル

The following protocols provide application-specific security by protecting application payloads used for specific use cases. Unlike the protocols above, these are not intended for generic application use.

次のプロトコルは、特定のユースケースで使われるアプリケーションペイロードを保護することで、アプリケーション固有のセキュリティーを提供します。 上記のプロトコルとは異なり、これらは汎用的なアプリケーションでの使用を意図していません。

3.2.1. Secure RTP

3.2.1. Secure RTP

Secure RTP (SRTP) is a profile for RTP that provides confidentiality, message authentication, and replay protection for RTP data packets and RTP control protocol (RTCP) packets [RFC3711]. SRTP provides a record layer only, and requires a separate handshake protocol to provide key agreement and identity management.

Secure RTP（SRTP）は、RTPデータパケットとRTP制御プロトコル（RTCP）パケットに対して、機密性、メッセージ認証、リプレイ保護を提供するRTPのプロファイルです[RFC3711]。 SRTPはレコード層のみを提供し、鍵合意と識別情報の管理を提供するには別のハンドシェイクプロトコルを必要とします。

The commonly used handshake protocol for SRTP is DTLS, in the form of DTLS-SRTP [RFC5764]. This is an extension to DTLS that negotiates the use of SRTP as the record layer and describes how to export keys for use with SRTP.

SRTPでよく使われるハンドシェイクプロトコルは、DTLS-SRTP [RFC5764]の形をとるDTLSです。 これはDTLSの拡張であり、レコード層としてSRTPを使用することをネゴシエートし、SRTPで使用する鍵をエクスポートする方法を説明しています。

ZRTP [RFC6189] is an alternative key agreement and identity management protocol for SRTP. ZRTP Key agreement is performed using a Diffie-Hellman key exchange that runs on the media path. This generates a shared secret that is then used to generate the master key and salt for SRTP.

ZRTP [RFC6189]は、SRTPのための代替の鍵合意および識別情報管理プロトコルです。 ZRTPの鍵合意は、メディアパス上で実行されるディフィー・ヘルマン鍵交換を使って行われます。 これにより共有秘密が生成され、それがSRTPのマスター鍵とソルトの生成に使われます。

3.3. Transport-Layer Security Protocols

3.3. トランスポート層のセキュリティープロトコル

The following security protocols provide protection for both application payloads and headers that are used for Transport Services.

次のセキュリティープロトコルは、アプリケーションペイロードと、トランスポートサービスに使われるヘッダーの両方を保護します。

3.3.1. IETF QUIC

3.3.1. IETF QUIC

QUIC is a new standards-track transport protocol that runs over UDP, loosely based on Google's original proprietary gQUIC protocol [QUIC-TRANSPORT] (See Section 3.3.2 for more details). The QUIC transport layer itself provides support for data confidentiality and integrity. This requires keys to be derived with a separate handshake protocol. A mapping for QUIC of TLS 1.3 [QUIC-TLS] has been specified to provide this handshake.

QUICは、UDP上で動作する新しい標準化過程のトランスポートプロトコルで、Googleが独自に開発した元のgQUICプロトコルを大まかにもとにしています[QUIC-TRANSPORT]（詳細はSection 3.3.2を参照してください）。 QUICのトランスポート層自体が、データの機密性と完全性をサポートします。 そのためには、別のハンドシェイクプロトコルで鍵を導出する必要があります。 このハンドシェイクを提供するために、TLS 1.3のQUIC向けのマッピング[QUIC-TLS]が規定されています。

3.3.2. Google QUIC

3.3.2. Google QUIC

Google QUIC (gQUIC) is a UDP-based multiplexed streaming protocol designed and deployed by Google following experience from deploying SPDY, the proprietary predecessor to HTTP/2. gQUIC was originally known as "QUIC"; this document uses gQUIC to unambiguously distinguish it from the standards-track IETF QUIC. The proprietary technical forebear of IETF QUIC, gQUIC was originally designed with tightly integrated security and application data transport protocols.

Google QUIC（gQUIC）は、HTTP/2の前身である独自プロトコルSPDYを展開した経験を踏まえて、Googleが設計・展開した、UDPベースの多重化ストリーミングプロトコルです。 gQUICはもともと「QUIC」として知られていましたが、この文書では標準化過程のIETF QUICと明確に区別するためにgQUICという名前を使います。 IETF QUICの技術的な前身である独自プロトコルgQUICは、もともとセキュリティーとアプリケーションデータのトランスポートのプロトコルが緊密に統合されるように設計されていました。

3.3.3. tcpcrypt

3.3.3. tcpcrypt

Tcpcrypt [RFC8548] is a lightweight extension to the TCP protocol for opportunistic encryption. Applications may use tcpcrypt's unique session ID for further application-level authentication. Absent this authentication, tcpcrypt is vulnerable to active attacks.

tcpcrypt [RFC8548]は、日和見暗号化のためのTCPプロトコルの軽量な拡張です。 アプリケーションは、さらにアプリケーションレベルの認証を行うために、tcpcryptの一意のセッションIDを使用できます。 この認証がない場合、tcpcryptは能動的な攻撃に対して脆弱です。

3.3.4. MinimaLT

3.3.4. MinimaLT

MinimaLT [MinimaLT] is a UDP-based transport security protocol designed to offer confidentiality, mutual authentication, DoS prevention, and connection mobility. One major goal of the protocol is to leverage existing protocols to obtain server-side configuration information used to more quickly bootstrap a connection. MinimaLT uses a variant of TCP's congestion control algorithm.

MinimaLT [MinimaLT]は、機密性、相互認証、DoS防止、コネクションのモビリティーを提供するように設計された、UDPベースのトランスポートセキュリティープロトコルです。 このプロトコルの主要な目標の1つは、既存のプロトコルを活用して、コネクションをより迅速にブートストラップするために使うサーバー側の設定情報を取得することです。 MinimaLTは、TCPの輻輳制御アルゴリズムの変種を使用します。

3.3.5. CurveCP

3.3.5. CurveCP

CurveCP [CurveCP] is a UDP-based transport security that, unlike many other security protocols, is based entirely upon public key algorithms. CurveCP provides its own reliability for application data as part of its protocol.

CurveCP [CurveCP]は、UDPベースのトランスポートセキュリティーであり、ほかの多くのセキュリティープロトコルとは異なり、完全に公開鍵アルゴリズムに基づいています。 CurveCPは、プロトコルの一部として、アプリケーションデータに対する独自の信頼性を提供します。

3.4. Packet Security Protocols

3.4. パケットのセキュリティープロトコル

The following protocols provide protection for IP packets. These are generally used as tunnels, such as for Virtual Private Networks (VPNs). Often, applications will not interact directly with these protocols. However, applications that implement tunnels will interact directly with these protocols.

次のプロトコルは、IPパケットを保護します。 これらは一般に、仮想プライベートネットワーク（VPN）などのトンネルとして使われます。 多くの場合、アプリケーションはこれらのプロトコルと直接やり取りしません。 ただし、トンネルを実装するアプリケーションは、これらのプロトコルと直接やり取りします。

3.4.1. IPsec

3.4.1. IPsec

IKEv2 [RFC7296] and ESP [RFC4303] together form the modern IPsec protocol suite that encrypts and authenticates IP packets, either for creating tunnels (tunnel-mode) or for direct transport connections (transport-mode). This suite of protocols separates out the key generation protocol (IKEv2) from the transport encryption protocol (ESP). Each protocol can be used independently, but this document considers them together, since that is the most common pattern.

IKEv2 [RFC7296]とESP [RFC4303]は合わせて、トンネルを作成するため（トンネルモード）、または直接のトランスポートコネクションのため（トランスポートモード）に、IPパケットを暗号化して認証する現代のIPsecプロトコルスイートを構成します。 このプロトコルスイートは、鍵生成プロトコル（IKEv2）とトランスポート暗号化プロトコル（ESP）を分離しています。 それぞれのプロトコルは独立して使用できますが、最も一般的なパターンであるため、この文書では両者をまとめて扱います。

3.4.2. WireGuard

3.4.2. WireGuard

WireGuard [WireGuard] is an IP-layer protocol designed as an alternative to IPsec for certain use cases. It uses UDP to encapsulate IP datagrams between peers. Unlike most transport security protocols, which rely on Public Key Infrastructure (PKI) for peer authentication, WireGuard authenticates peers using pre-shared public keys delivered out of band, each of which is bound to one or more IP addresses. Moreover, as a protocol suited for VPNs, WireGuard offers no extensibility, negotiation, or cryptographic agility.

WireGuard [WireGuard]は、特定のユースケースにおいてIPsecの代替として設計されたIP層のプロトコルです。 ピア間のIPデータグラムをカプセル化するためにUDPを使用します。 ピアの認証に公開鍵基盤（PKI）に依存するほとんどのトランスポートセキュリティープロトコルとは異なり、WireGuardは帯域外で配送された事前共有の公開鍵を使ってピアを認証します。各公開鍵は1つ以上のIPアドレスに結び付けられます。 さらに、VPNに適したプロトコルとして、WireGuardは拡張性、ネゴシエーション、暗号の俊敏性（cryptographic agility）を一切提供しません。

3.4.3. OpenVPN

3.4.3. OpenVPN

OpenVPN [OpenVPN] is a commonly used protocol designed as an alternative to IPsec. A major goal of this protocol is to provide a VPN that is simple to configure and works over a variety of transports. OpenVPN encapsulates either IP packets or Ethernet frames within a secure tunnel and can run over either UDP or TCP. For key establishment, OpenVPN can either use TLS as a handshake protocol or use pre-shared keys.

OpenVPN [OpenVPN]は、IPsecの代替として設計された、よく使われているプロトコルです。 このプロトコルの主要な目標は、設定が簡単で、さまざまなトランスポート上で動作するVPNを提供することです。 OpenVPNは、IPパケットまたはイーサネットフレームを安全なトンネル内にカプセル化し、UDPとTCPのどちらの上でも動作できます。 鍵の確立には、OpenVPNはハンドシェイクプロトコルとしてTLSを使用するか、事前共有鍵を使用できます。

4. Transport Dependencies

4. トランスポートの依存関係

Across the different security protocols listed above, the primary dependency on transport protocols is the presentation of data: either an unbounded stream of bytes, or framed messages. Within protocols that rely on the transport for message framing, most are built to run over transports that inherently provide framing, like UDP, but some also define how their messages can be framed over byte-stream transports.

上に挙げたさまざまなセキュリティープロトコルに共通する、トランスポートプロトコルへの主な依存関係は、データの提示形式です。すなわち、境界のないバイトストリームか、フレーム化されたメッセージかです。 メッセージのフレーミングをトランスポートに依存するプロトコルの多くは、UDPのように本来的にフレーミングを提供するトランスポート上で動作するように作られていますが、バイトストリームのトランスポート上でメッセージをフレーム化する方法も定義しているものもあります。

4.3. Transport-Specific Dependencies

4.3. トランスポート固有の依存関係

One protocol surveyed, tcpcrypt, has a direct dependency on a feature in the transport that is needed for its functionality. Specifically, tcpcrypt is designed to run on top of TCP and uses the TCP Encryption Negotiation Option (TCP-ENO) [RFC8547] to negotiate its protocol support.

調査したプロトコルのうちの1つ、tcpcryptは、その機能に必要なトランスポートの機能に直接依存しています。 具体的には、tcpcryptはTCPの上で動作するように設計されており、プロトコルのサポートをネゴシエートするためにTCP暗号化ネゴシエーションオプション（TCP-ENO）[RFC8547]を使用します。

QUIC, CurveCP, and MinimaLT provide both transport functionality and security functionality. They depend on running over a framed protocol like UDP, but they add their own layers of reliability and other Transport Services. Thus, an application that uses one of these protocols cannot decouple the security from transport functionality.

QUIC、CurveCP、MinimaLTは、トランスポートの機能とセキュリティーの機能の両方を提供します。 これらはUDPのようなフレーム化されたプロトコル上で動作することに依存していますが、独自の信頼性の層やその他のトランスポートサービスを追加しています。 したがって、これらのプロトコルのいずれかを使用するアプリケーションは、セキュリティーをトランスポートの機能から切り離すことができません。

5. Application Interface

5. アプリケーションインターフェイス

This section describes the interface exposed by the security protocols described above. We partition these interfaces into pre-connection (configuration), connection, and post-connection interfaces, following conventions in [TAPS-INTERFACE] and [TAPS-ARCH].

このセクションでは、上で説明したセキュリティープロトコルが公開するインターフェイスについて説明します。 [TAPS-INTERFACE]と[TAPS-ARCH]の慣例に従い、これらのインターフェイスを、コネクション前（設定）、コネクション、コネクション後のインターフェイスに分けます。

Note that not all protocols support each interface. The table in Section 5.4 summarizes which protocol exposes which of the interfaces. In the following sections, we provide abbreviations of the interface names to use in the summary table.

すべてのプロトコルが各インターフェイスをサポートしているわけではないことに注意してください。 Section 5.4の表に、どのプロトコルがどのインターフェイスを公開しているかをまとめています。 以降のセクションでは、まとめの表で使うインターフェイス名の略語を示します。

5.1. Pre-connection Interfaces

5.1. コネクション前のインターフェイス

Configuration interfaces are used to configure the security protocols before a handshake begins or keys are negotiated.

設定インターフェイスは、ハンドシェイクが始まる前や鍵がネゴシエートされる前に、セキュリティープロトコルを設定するために使われます。

Identities and Private Keys (IPK):

The application can provide its identity, credentials (e.g., certificates), and private keys, or mechanisms to access these, to the security protocol to use during handshakes.

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • MinimaLT
  • CurveCP
  • IPsec
  • WireGuard
  • OpenVPN
Supported Algorithms (Key Exchange, Signatures, and Ciphersuites) (ALG):

The application can choose the algorithms that are supported for key exchange, signatures, and ciphersuites.

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • tcpcrypt
  • MinimaLT
  • IPsec
  • OpenVPN
Extensions (EXT):

The application enables or configures extensions that are to be negotiated by the security protocol, such as Application-Layer Protocol Negotiation (ALPN) [RFC7301].

  • TLS
  • DTLS
  • QUIC
Session Cache Management (CM):

The application provides the ability to save and retrieve session state (such as tickets, keying material, and server parameters) that may be used to resume the security session.

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • tcpcrypt
  • MinimaLT
Authentication Delegation (AD):

The application provides access to a separate module that will provide authentication, using the Extensible Authentication Protocol (EAP) [RFC3748] for example.

  • IPsec
  • tcpcrypt
Pre-Shared Key Import (PSKI):

Either the handshake protocol or the application directly can supply pre-shared keys for use in encrypting (and authenticating) communication with a peer.

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • tcpcrypt
  • MinimaLT
  • IPsec
  • WireGuard
  • OpenVPN
識別情報と秘密鍵（Identities and Private Keys、IPK）：

アプリケーションは、ハンドシェイク中に使用するために、自身の識別情報、クレデンシャル（たとえば証明書）、秘密鍵、またはそれらにアクセスするためのメカニズムを、セキュリティープロトコルに提供できます。

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • MinimaLT
  • CurveCP
  • IPsec
  • WireGuard
  • OpenVPN
サポートするアルゴリズム（鍵交換、署名、暗号スイート）（Supported Algorithms、ALG）：

アプリケーションは、鍵交換、署名、暗号スイートについてサポートするアルゴリズムを選択できます。

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • tcpcrypt
  • MinimaLT
  • IPsec
  • OpenVPN
拡張（Extensions、EXT）：

アプリケーションは、アプリケーション層プロトコルネゴシエーション（ALPN）[RFC7301]など、セキュリティープロトコルがネゴシエートする拡張を有効にしたり設定したりします。

  • TLS
  • DTLS
  • QUIC
セッションキャッシュ管理（Session Cache Management、CM）：

アプリケーションは、セキュリティーセッションの再開に使われる可能性のあるセッション状態（チケット、鍵素材、サーバーのパラメーターなど）を保存および取得する能力を提供します。

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • tcpcrypt
  • MinimaLT
認証の委任（Authentication Delegation、AD）：

アプリケーションは、たとえば拡張認証プロトコル（EAP）[RFC3748]を使用して認証を提供する、別のモジュールへのアクセスを提供します。

  • IPsec
  • tcpcrypt
事前共有鍵のインポート（Pre-Shared Key Import、PSKI）：

ハンドシェイクプロトコルまたはアプリケーションが直接、ピアとの通信の暗号化（および認証）に使用する事前共有鍵を供給できます。

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • tcpcrypt
  • MinimaLT
  • IPsec
  • WireGuard
  • OpenVPN

5.2. Connection Interfaces

5.2. コネクションのインターフェイス

Identity Validation (IV):

During a handshake, the security protocol will conduct identity validation of the peer. This can offload validation or occur transparently to the application.

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • MinimaLT
  • CurveCP
  • IPsec
  • WireGuard
  • OpenVPN
Source Address Validation (SAV):

The handshake protocol may interact with the transport protocol or application to validate the address of the remote peer that has sent data. This involves sending a cookie exchange to avoid DoS attacks. (This list omits protocols that depend on TCP and therefore implicitly perform SAV.)

  • DTLS
  • QUIC
  • IPsec
  • WireGuard
識別情報の検証（Identity Validation、IV）：

ハンドシェイク中に、セキュリティープロトコルはピアの識別情報の検証を行います。 これにより、検証をオフロードしたり、アプリケーションから透過的に検証を行ったりできます。

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • MinimaLT
  • CurveCP
  • IPsec
  • WireGuard
  • OpenVPN
送信元アドレスの検証（Source Address Validation、SAV）：

ハンドシェイクプロトコルは、データを送信してきたリモートピアのアドレスを検証するために、トランスポートプロトコルやアプリケーションとやり取りする場合があります。 これには、DoS攻撃を避けるためにクッキーの交換を送信することが含まれます。 （このリストでは、TCPに依存し、そのため暗黙的にSAVを行うプロトコルは省略しています。）

  • DTLS
  • QUIC
  • IPsec
  • WireGuard

5.3. Post-connection Interfaces

5.3. コネクション後のインターフェイス

Connection Termination (CT):

The security protocol may be instructed to tear down its connection and session information. This is needed by some protocols, e.g., to prevent application data truncation attacks in which an attacker terminates an underlying insecure connection-oriented protocol to terminate the session.

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • tcpcrypt
  • MinimaLT
  • IPsec
  • OpenVPN
Key Update (KU):

The handshake protocol may be instructed to update its keying material, either by the application directly or by the record protocol sending a key expiration event.

  • TLS
  • DTLS
  • QUIC
  • tcpcrypt
  • MinimaLT
  • IPsec
Shared Secret Key Export (SSKE):

The handshake protocol may provide an interface for producing shared secrets for application-specific uses.

  • TLS
  • DTLS
  • tcpcrypt
  • IPsec
  • OpenVPN
  • MinimaLT
Key Expiration (KE):

The record protocol can signal that its keys are expiring due to reaching a time-based deadline or a use-based deadline (number of bytes that have been encrypted with the key). This interaction is often limited to signaling between the record layer and the handshake layer.

  • IPsec
Mobility Events (ME):

The record protocol can be signaled that it is being migrated to another transport or interface due to connection mobility, which may reset address and state validation and induce state changes such as use of a new Connection Identifier (CID).

  • DTLS (version 1.3 only [DTLS-1.3])
  • QUIC
  • MinimaLT
  • CurveCP
  • IPsec [RFC4555]
  • WireGuard
コネクションの終了（Connection Termination、CT）：

セキュリティープロトコルは、コネクションとセッションの情報を破棄するように指示される場合があります。 これは一部のプロトコルで必要とされます。たとえば、攻撃者が下位の安全でないコネクション指向プロトコルを終了させてセッションを終了させる、アプリケーションデータの切り詰め攻撃を防ぐためです。

  • TLS
  • DTLS
  • ZRTP
  • QUIC
  • tcpcrypt
  • MinimaLT
  • IPsec
  • OpenVPN
鍵の更新（Key Update、KU）：

ハンドシェイクプロトコルは、アプリケーションから直接、またはレコードプロトコルが鍵の期限切れイベントを送信することによって、鍵素材を更新するように指示される場合があります。

  • TLS
  • DTLS
  • QUIC
  • tcpcrypt
  • MinimaLT
  • IPsec
共有秘密鍵のエクスポート（Shared Secret Key Export、SSKE）：

ハンドシェイクプロトコルは、アプリケーション固有の用途のために共有秘密を生成するインターフェイスを提供する場合があります。

  • TLS
  • DTLS
  • tcpcrypt
  • IPsec
  • OpenVPN
  • MinimaLT
鍵の期限切れ（Key Expiration、KE）：

レコードプロトコルは、時間に基づく期限または使用量に基づく期限（その鍵で暗号化されたバイト数）に達したために鍵が期限切れになりつつあることを通知できます。 このやり取りは、多くの場合、レコード層とハンドシェイク層の間の通知に限られます。

  • IPsec
モビリティーイベント（Mobility Events、ME）：

レコードプロトコルは、コネクションのモビリティーのために別のトランスポートやインターフェイスに移行されつつあることを通知される場合があります。 これにより、アドレスと状態の検証がリセットされ、新しいコネクション識別子（CID）の使用などの状態変化が引き起こされる可能性があります。

  • DTLS（バージョン1.3のみ[DTLS-1.3]）
  • QUIC
  • MinimaLT
  • CurveCP
  • IPsec [RFC4555]
  • WireGuard

7. Security Considerations

7. セキュリティーに関する考慮事項

This document summarizes existing transport security protocols and their interfaces. It does not propose changes to or recommend usage of reference protocols. Moreover, no claims of security and privacy properties beyond those guaranteed by the protocols discussed are made. For example, metadata leakage via timing side channels and traffic analysis may compromise any protocol discussed in this survey. Applications using Security Interfaces should take such limitations into consideration when using a particular protocol implementation.

この文書は、既存のトランスポートセキュリティープロトコルとそのインターフェイスをまとめたものです。 参照したプロトコルの変更を提案したり、その使用を推奨したりするものではありません。 また、取り上げたプロトコルが保証するもの以上のセキュリティーやプライバシーの特性を主張するものでもありません。 たとえば、タイミングのサイドチャネルやトラフィック分析によるメタデータの漏洩は、この調査で取り上げたどのプロトコルも危うくする可能性があります。 セキュリティーインターフェイスを使用するアプリケーションは、特定のプロトコル実装を使用する際に、そのような制限を考慮に入れるべきです。

8. Privacy Considerations

8. プライバシーに関する考慮事項

Analysis of how features improve or degrade privacy is intentionally omitted from this survey. All security protocols surveyed generally improve privacy by using encryption to reduce information leakage. However, varying amounts of metadata remain in the clear across each protocol. For example, client and server certificates are sent in cleartext in TLS 1.2 [RFC5246], whereas they are encrypted in TLS 1.3 [RFC8446]. A survey of privacy features, or lack thereof, for various security protocols could be addressed in a separate document.

機能がプライバシーをどのように向上または低下させるかの分析は、この調査では意図的に省略しています。 調査したすべてのセキュリティープロトコルは、一般に、暗号化を用いて情報の漏洩を減らすことでプライバシーを向上させます。 しかし、各プロトコルでは、さまざまな量のメタデータが平文のまま残ります。 たとえば、TLS 1.2 [RFC5246]ではクライアントとサーバーの証明書が平文で送信されますが、TLS 1.3 [RFC8446]では暗号化されます。 さまざまなセキュリティープロトコルのプライバシー機能（またはその欠如）の調査は、別の文書で扱うことができるでしょう。
