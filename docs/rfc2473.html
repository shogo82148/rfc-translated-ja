Abstract

概要

This document defines the model and generic mechanisms for IPv6 encapsulation of Internet packets, such as IPv6 and IPv4. The model and mechanisms can be applied to other protocol packets as well, such as AppleTalk, IPX, CLNP, or others.

この文書は、IPv6やIPv4などのインターネットのパケットをIPv6でカプセル化するためのモデルと汎用的な仕組みを定義します。このモデルと仕組みは、AppleTalk、IPX、CLNPなど、その他のプロトコルのパケットにも適用できます。

1. Introduction

1. はじめに

This document specifies a method and generic mechanisms by which a packet is encapsulated and carried as payload within an IPv6 packet. The resulting packet is called an IPv6 tunnel packet. The forwarding path between the source and destination of the tunnel packet is called an IPv6 tunnel. The technique is called IPv6 tunneling.

この文書は、パケットをカプセル化し、IPv6パケットのペイロードとして運ぶための方法と汎用的な仕組みを規定します。その結果のパケットはIPv6トンネルパケットと呼ばれます。トンネルパケットの送信元と宛先の間の転送パスはIPv6トンネルと呼ばれます。この技法はIPv6トンネリングと呼ばれます。

A typical scenario for IPv6 tunneling is the case in which an intermediate node exerts explicit routing control by specifying particular forwarding paths for selected packets. This control is achieved by prepending IPv6 headers to each of the selected original packets. These prepended headers identify the forwarding paths.

IPv6トンネリングの典型的なシナリオは、中間ノードが、選択したパケットについて特定の転送パスを指定することで、明示的なルーティングの制御を行う場合です。この制御は、選択した元のパケットのそれぞれの前にIPv6ヘッダーを付加することで実現されます。これらの付加されたヘッダーが転送パスを識別します。

In addition to the description of generic IPv6 tunneling mechanisms, which is the focus of this document, specific mechanisms for tunneling IPv6 and IPv4 packets are also described herein.

この文書の焦点である汎用的なIPv6トンネリングの仕組みの説明に加えて、IPv6とIPv4のパケットをトンネリングするための具体的な仕組みもここで説明します。

The keywords MUST, MUST NOT, MAY, OPTIONAL, REQUIRED, RECOMMENDED, SHALL, SHALL NOT, SHOULD, SHOULD NOT are to be interpreted as defined in RFC 2119.

キーワード「MUST」、「MUST NOT」、「MAY」、「OPTIONAL」、「REQUIRED」、「RECOMMENDED」、「SHALL」、「SHALL NOT」、「SHOULD」、「SHOULD NOT」は、RFC 2119で定義されているように解釈されます。

3. IPv6 Tunneling

3. IPv6トンネリング

IPv6 tunneling is a technique for establishing a "virtual link" between two IPv6 nodes for transmitting data packets as payloads of IPv6 packets (see Fig.1). From the point of view of the two nodes, this "virtual link", called an IPv6 tunnel, appears as a point to point link on which IPv6 acts like a link-layer protocol. The two IPv6 nodes play specific roles. One node encapsulates original packets received from other nodes or from itself and forwards the resulting tunnel packets through the tunnel. The other node decapsulates the received tunnel packets and forwards the resulting original packets towards their destinations, possibly itself. The encapsulator node is called the tunnel entry-point node, and it is the source of the tunnel packets. The decapsulator node is called the tunnel exit-point, and it is the destination of the tunnel packets. Note: This document refers in particular to tunnels between two nodes identified by unicast addresses - such tunnels look like "virtual point to point links". The mechanisms described herein apply also to tunnels in which the exit-point nodes are identified by other types of addresses, such as anycast or multicast. These tunnels may look like "virtual point to multipoint links". At the time of writing this document, IPv6 anycast addresses are a subject of ongoing specification and experimental work.

IPv6トンネリングは、データパケットをIPv6パケットのペイロードとして伝送するために、2つのIPv6ノード間に「仮想リンク」を確立する技法です（図1を参照）。2つのノードの観点からは、IPv6トンネルと呼ばれるこの「仮想リンク」は、IPv6がリンク層のプロトコルのように振る舞うポイントツーポイントリンクとして見えます。2つのIPv6ノードは特定の役割を果たします。一方のノードは、他のノードまたは自身から受信した元のパケットをカプセル化し、その結果のトンネルパケットをトンネルを通じて転送します。もう一方のノードは、受信したトンネルパケットのカプセル化を解除し、その結果の元のパケットを（場合によっては自身である）宛先に向けて転送します。カプセル化を行うノードはトンネル入口ノードと呼ばれ、トンネルパケットの送信元です。カプセル化を解除するノードはトンネル出口と呼ばれ、トンネルパケットの宛先です。注：この文書は、特にユニキャストアドレスで識別される2つのノード間のトンネルについて言及しています。そのようなトンネルは「仮想のポイントツーポイントリンク」のように見えます。ここで説明する仕組みは、出口ノードがエニーキャストやマルチキャストなどの他の種類のアドレスで識別されるトンネルにも適用されます。これらのトンネルは「仮想のポイントツーマルチポイントリンク」のように見えるかもしれません。この文書の執筆時点では、IPv6のエニーキャストアドレスは仕様策定と実験的な作業が進行中の対象です。

3.1. IPv6のカプセル化

The encapsulation takes place in an IPv6 tunnel entry-point node, as the result of an original packet being forwarded onto the virtual link represented by the tunnel. IPv6のカプセル化は、元のパケットの前に、IPv6ヘッダーと、オプションでIPv6拡張ヘッダーの集合を付加することです（図3を参照）。これらはまとめてトンネルIPv6ヘッダーと呼ばれます。カプセル化は、元のパケットがトンネルによって表される仮想リンクに転送された結果として、IPv6トンネル入口ノードで行われます。元のパケットは、転送の際に、そのパケットのプロトコルの転送規則に従って処理されます。たとえば、元のパケットが次のものである場合：

  1. IPv6 packet, the IPv6 original header hop limit is decremented by one.
  2. IPv4 packet, the IPv4 original header time to live field (TTL) is decremented by one.
  1. IPv6パケットであれば、IPv6の元のヘッダーのホップ制限が1減らされます。
  2. IPv4パケットであれば、IPv4の元のヘッダーの生存時間フィールド（TTL）が1減らされます。

At encapsulation, the source field of the tunnel IPv6 header is filled with an IPv6 address of the tunnel entry-point node, and the destination field with an IPv6 address of the tunnel exit-point. Subsequently, the tunnel packet resulting from encapsulation is sent towards the tunnel exit-point node.

3.2. Packet Processing in Tunnels

3.2. トンネル内でのパケットの処理

The intermediate nodes in the tunnel process the IPv6 tunnel packets according to the IPv6 protocol. For example, a tunnel Hop by Hop Options extension header is processed by each receiving node in the tunnel; a tunnel Routing extension header identifies the intermediate processing nodes, and controls at a finer granularity the forwarding path of the tunnel packet through the tunnel; a tunnel Destination Options extension header is processed at the tunnel exit-point node.

トンネル内の中間ノードは、IPv6のプロトコルに従ってIPv6トンネルパケットを処理します。たとえば、トンネルのホップバイホップオプション拡張ヘッダーは、トンネル内の各受信ノードによって処理されます。トンネルのルーティング拡張ヘッダーは、処理を行う中間ノードを識別し、トンネルを通るトンネルパケットの転送パスをより細かい粒度で制御します。トンネルの宛先オプション拡張ヘッダーは、トンネル出口ノードで処理されます。

Upon receiving an IPv6 packet destined to an IPv6 address of a tunnel exit-point node, its IPv6 protocol layer processes the tunnel headers. The strict left-to-right processing rules for extension headers is applied. When processing is complete, control is handed to the next protocol engine, which is identified by the Next Header field value in the last header processed. If this is set to a tunnel protocol value, the tunnel protocol engine discards the tunnel headers and passes the resulting original packet to the Internet or lower layer protocol identified by that value for further processing. For example, in the case the Next Header field has the IPv6 Tunnel Protocol value, the resulting original packet is passed to the IPv6 protocol layer.

4.1. Limiting Nested Encapsulation

4.1. 入れ子のカプセル化の制限

A tunnel IPv6 packet is limited to the maximum IPv6 packet size [IPv6-Spec]. Each encapsulation adds to the size of an encapsulated packet the size of the tunnel IPv6 headers. Consequently, the number of tunnel headers, and therefore, the number of nested encapsulations is limited by the maximum packet size. However this limit is so large (more than 1600 encapsulations for an original packet of minimum size) that it is not an effective limit in most cases.

トンネルIPv6パケットは、IPv6パケットの最大サイズ[IPv6-Spec]に制限されます。各カプセル化は、カプセル化されたパケットのサイズにトンネルIPv6ヘッダーのサイズを加えます。したがって、トンネルヘッダーの数、ひいては入れ子のカプセル化の数は、最大パケットサイズによって制限されます。しかし、この制限は非常に大きい（最小サイズの元のパケットに対して1600回を超えるカプセル化）ため、ほとんどの場合、有効な制限にはなりません。

The increase in the size of a tunnel IPv6 packet due to nested encapsulations may require fragmentation [IPv6-Spec] at a tunnel entry point - see section 7. Furthermore, each fragmentation, due to nested encapsulation, of an already fragmented tunnel packet results in a doubling of the number of fragments. Moreover, it is probable that once this fragmentation begins, each new nested encapsulation results in yet additional fragmentation. Therefore limiting nested encapsulation is recommended.

入れ子のカプセル化によるトンネルIPv6パケットのサイズの増加は、トンネル入口での断片化[IPv6-Spec]を必要とする場合があります（7節を参照）。さらに、すでに断片化されたトンネルパケットが入れ子のカプセル化によって断片化されるたびに、フラグメントの数は2倍になります。そのうえ、いったんこの断片化が始まると、新たな入れ子のカプセル化のたびにさらに断片化が生じる可能性が高いです。そのため、入れ子のカプセル化を制限することが推奨されます。

The proposed mechanism for limiting excessive nested encapsulation is a "Tunnel Encapsulation Limit" option, which is carried in an IPv6 Destination Options extension header accompanying an encapsulating IPv6 header.

過度の入れ子のカプセル化を制限するために提案されている仕組みは、「トンネルカプセル化制限（Tunnel Encapsulation Limit）」オプションです。このオプションは、カプセル化するIPv6ヘッダーに伴うIPv6の宛先オプション拡張ヘッダーで運ばれます。

4.1.1. Tunnel Encapsulation Limit Option

4.1.1. トンネルカプセル化制限オプション

A tunnel entry-point node may be configured to include a Tunnel Encapsulation Limit option as part of the information prepended to all packets entering a tunnel at that node. The Tunnel Encapsulaton Limit option is carried in a Destination Options extension header [IPv6-Spec] placed between the encapsulating IPv6 header and the IPv6 header of the original packet. (Other IPv6 extension headers may also be present preceding or following the Destination Options extension header, depending on configuration information at the tunnel entry-point node.)

トンネル入口ノードは、そのノードでトンネルに入るすべてのパケットの前に付加される情報の一部として、トンネルカプセル化制限オプションを含めるように設定される場合があります。トンネルカプセル化制限オプションは、カプセル化するIPv6ヘッダーと元のパケットのIPv6ヘッダーの間に置かれる宛先オプション拡張ヘッダー[IPv6-Spec]で運ばれます。（トンネル入口ノードでの設定情報に応じて、宛先オプション拡張ヘッダーの前または後に、他のIPv6拡張ヘッダーが存在する場合もあります。）

トンネルカプセル化制限オプションは、トンネル入口にとってのみ意味があります。トンネル入口ノードは、そのノードでトンネルに入るすべてのパケットについて、次の手順を実行する必要があります。

  1. Examine the packet to see if a Tunnel Encapsulation Limit option is present following its IPv6 header. The headers following the IPv6 header must be examined in strict "left-to-right" order, with the examination stopping as soon as any one of the following headers is encountered: (i) a Destination Options extension header containing a Tunnel Encapsulation Limit, (ii) another IPv6 header, (iii) a non-extension header, such as TCP, UDP, or ICMP, or (iv) a header that cannot be parsed because it is encrypted or its type is unknown. (Note that this requirment is an exception to the general IPv6 rule that a Destination Options extension header need only be examined by a packet's destination node. An alternative and "cleaner" approach would have been to use a Hop-by-Hop extension header for this purpose, but that would have imposed an undesirable extra processing burden, and possible consequent extra delay, at every IPv6 node along the path of a tunnel.)
  2. If a Tunnel Encapsulation Limit option is found in the packet entering the tunnel and its limit value is zero, the packet is discarded and an ICMP Parameter Problem message [ICMP-Spec] is sent to the source of the packet, which is the previous tunnel entry-point node. The Code field of the Parameter Problem message is set to zero ("erroneous header field encountered") and the Pointer field is set to point to the third octet of the Tunnel Encapsulation Limit option (i.e., the octet containing the limit value of zero).
  3. If a Tunnel Encapsulation Limit option is found in the packet entering the tunnel and its limit value is non-zero, an additional Tunnel Encapsulation Limit option must be included as part of the encapsulating headers being added at this entry point. The limit value in the encapsulating option is set to one less than the limit value found in the packet being encapsulated.
  4. If a Tunnel Encapsulation Limit option is not found in the packet entering the tunnel and if an encapsulation limit has been configured for this tunnel, a Tunnel Encapsulation Limit option must be included as part of the encapsulating headers being added at this entry point. The limit value in the option is set to the configured limit.
  5. If a Tunnel Encapsulation Limit option is not found in the packet entering the tunnel and if no encapsulation limit has been configured for this tunnel, then no Tunnel Encapsulation Limit option is included as part of the encapsulating headers being added at this entry point.
  1. パケットを調べて、そのIPv6ヘッダーに続いてトンネルカプセル化制限オプションが存在するかどうかを確認します。IPv6ヘッダーに続くヘッダーは、厳密な「左から右」の順序で調べる必要があり、次のヘッダーのいずれかに遭遇した時点で調査を停止します。(i) トンネルカプセル化制限を含む宛先オプション拡張ヘッダー、(ii) 別のIPv6ヘッダー、(iii) TCP、UDP、ICMPなどの拡張ヘッダーでないヘッダー、または (iv) 暗号化されている、または種類が未知であるために解析できないヘッダー。（この要件は、宛先オプション拡張ヘッダーはパケットの宛先ノードだけが調べればよいというIPv6の一般的な規則の例外であることに注意してください。この目的のためにホップバイホップ拡張ヘッダーを使用するという代替の「よりきれいな」手法もありえましたが、それではトンネルのパス上のすべてのIPv6ノードに、望ましくない追加の処理の負担と、それに伴う追加の遅延が生じる可能性がありました。）
  2. トンネルに入るパケットにトンネルカプセル化制限オプションが見つかり、その制限値が0である場合、パケットは破棄され、ICMPのParameter Problemメッセージ[ICMP-Spec]がパケットの送信元、すなわち前のトンネル入口ノードに送信されます。Parameter ProblemメッセージのCodeフィールドは0（「誤ったヘッダーフィールドに遭遇した」）に設定され、Pointerフィールドはトンネルカプセル化制限オプションの3番目のオクテット（すなわち、制限値0を含むオクテット）を指すように設定されます。
  3. トンネルに入るパケットにトンネルカプセル化制限オプションが見つかり、その制限値が0でない場合、この入口で追加されるカプセル化するヘッダーの一部として、追加のトンネルカプセル化制限オプションを含める必要があります。カプセル化するオプションの制限値は、カプセル化されるパケットで見つかった制限値より1小さい値に設定されます。
  4. トンネルに入るパケットにトンネルカプセル化制限オプションが見つからず、このトンネルにカプセル化の制限が設定されている場合、この入口で追加されるカプセル化するヘッダーの一部として、トンネルカプセル化制限オプションを含める必要があります。オプションの制限値は、設定された制限に設定されます。
  5. トンネルに入るパケットにトンネルカプセル化制限オプションが見つからず、このトンネルにカプセル化の制限が設定されていない場合、この入口で追加されるカプセル化するヘッダーの一部としてトンネルカプセル化制限オプションは含まれません。

トンネル入口ノードで追加されたトンネルカプセル化制限オプションは、そのトンネルの出口ノードでのカプセル化の解除の過程で取り除かれます。

Two cases of encapsulation that should be avoided are described below:

4.1.2. Loopback Encapsulation

4.1.2. ループバックのカプセル化

A particular case of encapsulation which must be avoided is the loopback encapsulation. Loopback encapsulation takes place when a tunnel IPv6 entry-point node encapsulates tunnel IPv6 packets originated from itself, and destined to itself. This can generate an infinite processing loop in the entry-point node.

避けなければならないカプセル化の特別な場合は、ループバックのカプセル化です。ループバックのカプセル化は、トンネルIPv6の入口ノードが、自身から発信され自身宛てのトンネルIPv6パケットをカプセル化する場合に発生します。これは、入口ノードで無限の処理のループを生じさせる可能性があります。

To avoid such a case, it is recommended that an implementation have a mechanism that checks and rejects the configuration of a tunnel in which both the entry-point and exit-point node addresses belong to the same node. It is also recommended that the encapsulating engine check for and reject the encapsulation of a packet that has the pair of tunnel entry-point and exit-point addresses identical with the pair of original packet source and final destination addresses.

そのような場合を避けるために、実装には、入口ノードと出口ノードのアドレスの両方が同じノードに属するトンネルの設定を検査して拒否する仕組みを持つことが推奨されます。また、カプセル化エンジンが、トンネル入口と出口のアドレスの組が元のパケットの送信元と最終的な宛先のアドレスの組と同一であるパケットのカプセル化を検査して拒否することも推奨されます。

4.1.3. Routing-Loop Nested Encapsulation

4.1.3. ルーティングループによる入れ子のカプセル化

In the case of a forwarding path with multiple-level nested tunnels, a routing-loop from an inner tunnel to an outer tunnel is particularly dangerous when packets from the inner tunnels reenter an outer tunnel from which they have not yet exited. In such a case, the nested encapsulation becomes a recursive encapsulation with the negative effects described in 4.1. Because each nested encapsulation adds a tunnel header with a new hop limit value, the IPv6 hop limit mechanism cannot control the number of times the packet reaches the outer tunnel entry-point node, and thus cannot control the number of recursive encapsulations.

複数のレベルの入れ子のトンネルを持つ転送パスの場合、内側のトンネルから外側のトンネルへのルーティングループは、内側のトンネルからのパケットが、まだ出ていない外側のトンネルに再び入るときに特に危険です。そのような場合、入れ子のカプセル化は、4.1節で説明した悪影響を伴う再帰的なカプセル化になります。各入れ子のカプセル化は新しいホップ制限の値を持つトンネルヘッダーを追加するため、IPv6のホップ制限の仕組みでは、パケットが外側のトンネル入口ノードに到達する回数を制御できず、したがって再帰的なカプセル化の回数を制御できません。

When the path of a packet from source to final destination includes tunnels, the maximum number of hops that the packet can traverse should be controlled by two mechanisms used together to avoid the negative effects of recursive encapsulation in routing loops:

送信元から最終的な宛先までのパケットのパスにトンネルが含まれる場合、ルーティングループにおける再帰的なカプセル化の悪影響を避けるために、パケットが通過できるホップの最大数は、次の2つの仕組みを併用して制御すべきです。

  1. the original packet hop limit.

    It is decremented at each forwarding operation performed on an original packet. This includes each encapsulation of the original packet. It does not include nested encapsulations of the original packet

  2. the tunnel IPv6 packet encapsulation limit.

    It is decremented at each nested encapsulation of the packet.

  1. 元のパケットのホップ制限。

    これは、元のパケットに対して行われる各転送の操作で減らされます。これには元のパケットの各カプセル化が含まれます。元のパケットの入れ子のカプセル化は含まれません。

  2. トンネルIPv6パケットのカプセル化制限。

    これは、パケットの各入れ子のカプセル化で減らされます。

For a discussion of the excessive encapsulation risk factors in nested encapsulation see Appendix A.

入れ子のカプセル化における過度のカプセル化の危険要因についての議論は、付録Aを参照してください。

6.3. IPv6 Tunnel Hop Limit

The "single-hop" mechanism should be implemented by having the tunnel entry point node set a tunnel IPv6 header hop limit independently of the hop limit of the original header.

「シングルホップ」の仕組みは、トンネル入口ノードが、元のヘッダーのホップ制限とは独立にトンネルIPv6ヘッダーのホップ制限を設定することで実装すべきです。

  1. that tunnel IPv6 packets can reach the tunnel exit-point node
  2. a quick expiration of the tunnel packet if a routing loop occurs within the IPv6 tunnel.
  1. トンネルIPv6パケットがトンネル出口ノードに到達できること
  2. IPv6トンネル内でルーティングループが発生した場合に、トンネルパケットがすばやく満了すること

6.6. IPv6 Tunnel Encapsulation Limit

The Tunnel Encapsulation Limit value can indicate whether the entry- point node is configured to limit the number of encapsulations of tunnel packets originating on that node. The IPv6 Tunnel Encapsulation Limit is the maximum number of additional encapsulations permitted for packets undergoing encapsulation at that entry-point node. Recommended default value is 4. An entry-point node configured to limit the number of nested encapsulations prepends a Destination Options extension header containing a Tunnel Encapsulation Limit option to an original packet undergoing encapsulation - see sections 4.1 and 4.1.1.

トンネルカプセル化制限の値は、入口ノードが、そのノードで発信されるトンネルパケットのカプセル化の数を制限するように設定されているかどうかを示すことができます。IPv6トンネルのカプセル化制限は、その入口ノードでカプセル化を受けるパケットに許可される追加のカプセル化の最大数です。推奨されるデフォルト値は4です。入れ子のカプセル化の数を制限するように設定された入口ノードは、カプセル化を受ける元のパケットの前に、トンネルカプセル化制限オプションを含む宛先オプション拡張ヘッダーを付加します（4.1節と4.1.1節を参照）。

6.7. IPv6 Tunnel MTU

6.7. IPv6トンネルのMTU

The tunnel MTU is set dynamically to the Path MTU between the tunnel entry-point and the tunnel exit-point nodes, minus the size of the tunnel headers: the maximum size of a tunnel packet payload that can be sent through the tunnel without fragmentation [IPv6-Spec]. The tunnel entry-point node performs Path MTU discovery on the path between the tunnel entry-point and exit-point nodes [PMTU-Spec], [ICMP-Spec]. The tunnel MTU of a nested tunnel is the tunnel MTU of the outer tunnel minus the size of the nested tunnel headers.

トンネルMTUは、トンネル入口ノードとトンネル出口ノードの間のパスMTUからトンネルヘッダーのサイズを引いた値に動的に設定されます。これは、断片化せずにトンネルを通じて送信できるトンネルパケットのペイロードの最大サイズです[IPv6-Spec]。トンネル入口ノードは、トンネル入口ノードと出口ノードの間のパスでパスMTU探索を行います[PMTU-Spec]、[ICMP-Spec]。入れ子のトンネルのトンネルMTUは、外側のトンネルのトンネルMTUから入れ子のトンネルヘッダーのサイズを引いたものです。

7. IPv6 Tunnel Packet Size Issues

7. IPv6トンネルパケットのサイズの問題

Prepending a tunnel header increases the size of a packet, therefore a tunnel packet resulting from the encapsulation of an IPv6 original packet may require fragmentation.

トンネルヘッダーを前に付加するとパケットのサイズが大きくなるため、IPv6の元のパケットのカプセル化の結果として得られるトンネルパケットは、断片化を必要とする場合があります。

A tunnel IPv6 packet resulting from the encapsulation of an original packet is considered an IPv6 packet originating from the tunnel entry-point node. Therefore, like any source of an IPv6 packet, a tunnel entry-point node must support fragmentation of tunnel IPv6 packets.

元のパケットのカプセル化の結果として得られるトンネルIPv6パケットは、トンネル入口ノードから発信されたIPv6パケットとみなされます。したがって、IPv6パケットの他の送信元と同様に、トンネル入口ノードはトンネルIPv6パケットの断片化をサポートする必要があります。

A tunnel intermediate node that forwards a tunnel packet to another node in the tunnel follows the general IPv6 rule that it must not fragment a packet undergoing forwarding.

トンネルパケットをトンネル内の別のノードに転送するトンネルの中間ノードは、転送中のパケットを断片化してはいけないというIPv6の一般的な規則に従います。

A tunnel exit-point node receiving tunnel packets at the end of the tunnel for decapsulation applies the strict left-to-right processing rules for extension headers. In the case of a fragmented tunnel packet, the fragments are reassembled into a complete tunnel packet before determining that an embedded packet is present.

カプセル化の解除のためにトンネルの終端でトンネルパケットを受信するトンネル出口ノードは、拡張ヘッダーについての厳密な左から右への処理規則を適用します。断片化されたトンネルパケットの場合、埋め込まれたパケットが存在すると判断する前に、フラグメントは完全なトンネルパケットに再構築されます。

Note:

注：

A particular problem arises when the destination of a fragmented tunnel packet is an exit-point node identified by an anycast address. The problem, which is similar to that of original fragmented IPv6 packets destined to nodes identified by an anycast address, is that all the fragments of a packet must arrive at the same destination node for that node to be able to perform a successful reassembly, a requirement that is not necessarily satisfied by packets sent to an anycast address.

断片化されたトンネルパケットの宛先がエニーキャストアドレスで識別される出口ノードである場合、特有の問題が生じます。この問題は、エニーキャストアドレスで識別されるノード宛ての断片化された元のIPv6パケットの問題と同様で、ノードが再構築を成功させるためには、パケットのすべてのフラグメントが同じ宛先ノードに到着する必要がありますが、この要件は、エニーキャストアドレスに送信されるパケットでは必ずしも満たされないということです。

7.1. IPv6 Tunnel Packet Fragmentation

7.1. IPv6トンネルパケットの断片化

When an IPv6 original packet enters a tunnel, if the original packet size exceeds the tunnel MTU (i.e., the Path MTU between the tunnel entry-point and the tunnel exit-point, minus the size of the tunnel header(s)), it is handled as follows:

IPv6の元のパケットがトンネルに入るときに、元のパケットのサイズがトンネルMTU（すなわち、トンネル入口とトンネル出口の間のパスMTUからトンネルヘッダーのサイズを引いたもの）を超える場合、次のように扱われます。

  1. if the original IPv6 packet size is larger than the IPv6 minimum link MTU [IPv6-Spec], the entry-point node discards the packet and sends an ICMPv6 "Packet Too Big" message to the source address of the original packet with the recommended MTU size field set to the tunnel MTU or the IPv6 minimum link MTU, whichever is larger, i.e. max (tunnel MTU, IPv6 minimum link MTU). Also see sections 6.7 and 8.2.
  2. if the original IPv6 packet is equal or smaller than the IPv6 minimum link MTU, the tunnel entry-point node encapsulates the original packet, and subsequently fragments the resulting IPv6 tunnel packet into IPv6 fragments that do not exceed the Path MTU to the tunnel exit-point.
  1. 元のIPv6パケットのサイズがIPv6の最小リンクMTU[IPv6-Spec]より大きい場合、入口ノードはパケットを破棄し、推奨MTUサイズのフィールドを、トンネルMTUとIPv6の最小リンクMTUのうち大きいほう、すなわちmax（トンネルMTU、IPv6の最小リンクMTU）に設定したICMPv6の「Packet Too Big」メッセージを、元のパケットの送信元アドレスに送信します。6.7節と8.2節も参照してください。
  2. 元のIPv6パケットがIPv6の最小リンクMTU以下である場合、トンネル入口ノードは元のパケットをカプセル化し、続いて、その結果のIPv6トンネルパケットを、トンネル出口へのパスMTUを超えないIPv6のフラグメントに断片化します。

7.2. IPv4 Tunnel Packet Fragmentation

7.2. IPv4トンネルパケットの断片化

When an IPv4 original packet enters a tunnel, if the original packet size exceeds the tunnel MTU (i.e., the Path MTU between the tunnel entry-point and the tunnel exit-point, minus the size of the tunnel header(s)), it is handled as follows:

IPv4の元のパケットがトンネルに入るときに、元のパケットのサイズがトンネルMTU（すなわち、トンネル入口とトンネル出口の間のパスMTUからトンネルヘッダーのサイズを引いたもの）を超える場合、次のように扱われます。

  1. if in the original IPv4 packet header the Don't Fragment - DF - bit flag is SET, the entry-point node discards the packet and returns an ICMP message. The ICMP message has the type = "unreachable", the code = "packet too big", and the recommended MTU size field set to the size of the tunnel MTU - see sections 6.7 and 8.3.
  2. if in the original packet header the Don't Fragment - DF - bit flag is CLEAR, the tunnel entry-point node encapsulates the original packet, and subsequently fragments the resulting IPv6 tunnel packet into IPv6 fragments that do not exceed the Path MTU to the tunnel exit-point.
  1. 元のIPv4パケットのヘッダーでDon't Fragment（DF）ビットフラグがSETである場合、入口ノードはパケットを破棄し、ICMPメッセージを返します。ICMPメッセージは、type =「unreachable」、code =「packet too big」であり、推奨MTUサイズのフィールドはトンネルMTUのサイズに設定されます（6.7節と8.3節を参照）。
  2. 元のパケットのヘッダーでDon't Fragment（DF）ビットフラグがCLEARである場合、トンネル入口ノードは元のパケットをカプセル化し、続いて、その結果のIPv6トンネルパケットを、トンネル出口へのパスMTUを超えないIPv6のフラグメントに断片化します。

8. IPv6 Tunnel Error Processing and Reporting

8. IPv6トンネルのエラーの処理と報告

IPv6 Tunneling follows the general rule that an error detected during the processing of an IPv6 packet is reported through an ICMP message to the source of the packet.

IPv6トンネリングは、IPv6パケットの処理中に検出されたエラーはICMPメッセージによってパケットの送信元に報告されるという一般的な規則に従います。

On a forwarding path that includes IPv6 tunnels, an error detected by a node that is not in any tunnel is directly reported to the source of the original IPv6 packet.

IPv6トンネルを含む転送パスでは、どのトンネルにも含まれないノードによって検出されたエラーは、元のIPv6パケットの送信元に直接報告されます。

An error detected by a node inside a tunnel is reported to the source of the tunnel packet, that is, the tunnel entry-point node. The ICMP message sent to the tunnel entry-point node has as ICMP payload the tunnel IPv6 packet that has the original packet as its payload.

トンネル内のノードによって検出されたエラーは、トンネルパケットの送信元、すなわちトンネル入口ノードに報告されます。トンネル入口ノードに送信されるICMPメッセージは、元のパケットをペイロードとして持つトンネルIPv6パケットをICMPのペイロードとして持ちます。

The cause of a packet error encountered inside a tunnel can be a problem with:

トンネル内で遭遇したパケットのエラーの原因は、次のいずれかの問題である可能性があります。

  1. the tunnel header, or
  2. the tunnel packet.
  1. トンネルヘッダー、または
  2. トンネルパケット。

Both tunnel header and tunnel packet problems are reported to the tunnel entry-point node.

トンネルヘッダーの問題とトンネルパケットの問題の両方が、トンネル入口ノードに報告されます。

If a tunnel packet problem is a consequence of a problem with the original packet, which is the payload of the tunnel packet, then the problem is also reported to the source of the original packet.

トンネルパケットの問題が、トンネルパケットのペイロードである元のパケットの問題の結果である場合、その問題は元のパケットの送信元にも報告されます。

To report a problem detected inside the tunnel to the source of an original packet, the tunnel entry point node must relay the ICMP message received from inside the tunnel to the source of that original IPv6 packet.

トンネル内で検出された問題を元のパケットの送信元に報告するために、トンネル入口ノードは、トンネル内から受信したICMPメッセージを、その元のIPv6パケットの送信元に中継する必要があります。

The tunnel has a misconfigured hop limit, or contains a routing loop, and packets do not reach the tunnel exit- point node. This problem is reported to the tunnel entry- point node, where the tunnel hop limit can be reconfigured to a higher value. The problem is further reported to the source of the original packet as described in section 8.2, or 8.3.

トンネルのホップ制限の設定が誤っているか、トンネルにルーティングループが含まれていて、パケットがトンネル出口ノードに到達しません。この問題はトンネル入口ノードに報告され、そこでトンネルのホップ制限をより大きな値に設定し直すことができます。この問題は、さらに8.2節または8.3節で説明するとおりに元のパケットの送信元に報告されます。

unreachable node（到達不能なノード）

One of the nodes in the tunnel is not or is no longer reachable. This problem is reported to the tunnel entry- point node, which should be reconfigured with a valid and active path between the entry and exit-point of the tunnel.

トンネル内のノードの1つが到達不能であるか、もはや到達可能ではありません。この問題はトンネル入口ノードに報告され、トンネル入口ノードは、トンネルの入口と出口の間の有効で稼働中のパスで設定し直されるべきです。

The problem is further reported to the source of the original packet as described in section 8.2, or 8.3.

この問題は、さらに8.2節または8.3節で説明するとおりに元のパケットの送信元に報告されます。

parameter problem

parameter problem（パラメーターの問題）

A Parameter Problem ICMP message pointing to a valid Tunnel Encapsulation Limit Destination header with a Tun Encap Lim field value set to one is an indication that the tunnel packet exceeded the maximum number of encapsulations allowed. The problem is further reported to the source of the original packet as described in section 8.2, or 8.3.

Tun Encap Limフィールドの値が1に設定された有効なトンネルカプセル化制限の宛先ヘッダーを指すParameter ProblemのICMPメッセージは、トンネルパケットが許可されたカプセル化の最大数を超えたことを示しています。この問題は、さらに8.2節または8.3節で説明するとおりに元のパケットの送信元に報告されます。

The above three problems detected inside the tunnel, which are a tunnel configuration and a tunnel topology problem, are reported to the source of the original IPv6 packet, as a tunnel generic "unreachable" problem caused by a "link problem" - see section 8.2 and 8.3.

トンネル内で検出された上記の3つの問題は、トンネルの設定とトンネルのトポロジーの問題であり、「リンクの問題」によって生じたトンネルの汎用的な「到達不能」の問題として、元のIPv6パケットの送信元に報告されます（8.2節と8.3節を参照）。

packet too big

packet too big（パケットが大きすぎる）

The tunnel packet exceeds the tunnel Path MTU.

トンネルパケットがトンネルのパスMTUを超えています。

The information carried by this type of ICMP message is used as follows:

この種類のICMPメッセージが運ぶ情報は、次のように使用されます。

  • by a receiving tunnel entry-point node to set or adjust the tunnel MTU
  • by a sending tunnel entry-point node to indicate to the source of an original packet the MTU size that should be used in sending IPv6 packets towards the tunnel entry-point node.
  • 受信したトンネル入口ノードが、トンネルMTUを設定または調整するために使用します。
  • 送信するトンネル入口ノードが、トンネル入口ノードに向けてIPv6パケットを送信する際に使用すべきMTUサイズを元のパケットの送信元に示すために使用します。

9. Security Considerations

9. セキュリティーに関する考慮事項

An IPv6 tunnel can be secured by securing the IPv6 path between the tunnel entry-point and exit-point node. The security architecture, mechanisms, and services are described in [RFC2401], [RFC2402], and [RFC2406]. A secure IPv6 tunnel may act as a gateway-to-gateway secure path as described in [RFC2401].

IPv6トンネルは、トンネル入口ノードと出口ノードの間のIPv6のパスを保護することで保護できます。セキュリティーのアーキテクチャー、仕組み、およびサービスは、[RFC2401]、[RFC2402]、および[RFC2406]で説明されています。保護されたIPv6トンネルは、[RFC2401]で説明されているゲートウェイ間の保護されたパスとして機能する場合があります。

For a secure IPv6 tunnel, in addition to the mechanisms described earlier in this document, the entry-point node of the tunnel performs security algorithms on the packet and prepends as part of the tunnel headers one or more security headers in conformance with [IPv6-Spec], [RFC2401], and [RFC2402], or [RFC2406].

保護されたIPv6トンネルの場合、この文書で前述した仕組みに加えて、トンネルの入口ノードはパケットにセキュリティーのアルゴリズムを実行し、[IPv6-Spec]、[RFC2401]、および[RFC2402]、または[RFC2406]に準拠して、トンネルヘッダーの一部として1つ以上のセキュリティーヘッダーを前に付加します。

The exit-point node of a secure IPv6 tunnel performs security algorithms and processes the tunnel security header[s] as part of the tunnel headers processing described earlier, and in conformance with [RFC2401], and [RFC2402], or [RFC2406]. The exit-point node discards the tunnel security header[s] with the rest of the tunnel headers after tunnel headers processing completion.

保護されたIPv6トンネルの出口ノードは、前述したトンネルヘッダーの処理の一部として、[RFC2401]、および[RFC2402]、または[RFC2406]に準拠して、セキュリティーのアルゴリズムを実行し、トンネルのセキュリティーヘッダーを処理します。出口ノードは、トンネルヘッダーの処理の完了後、トンネルのセキュリティーヘッダーを残りのトンネルヘッダーとともに破棄します。

The degree of integrity, authentication, and confidentiality and the security processing performed on a tunnel packet at the entry-point and exit-point node of a secure IPv6 tunnel depend on the type of security header - authentication (AH) or encryption (ESP) - and parameters configured in the Security Association for the tunnel. There is no dependency or interaction between the security level and mechanisms applied to the tunnel packets and the security applied to the original packets which are the payloads of the tunnel packets. In case of nested tunnels, each inner tunnel may have its own set of security services, independently from those of the outer tunnels, or of those between the source and destination of the original packet.

保護されたIPv6トンネルの入口ノードと出口ノードでトンネルパケットに対して行われる完全性、認証、機密性の程度とセキュリティーの処理は、セキュリティーヘッダーの種類（認証（AH）または暗号化（ESP））と、トンネルのセキュリティーアソシエーションで設定されたパラメーターに依存します。トンネルパケットに適用されるセキュリティーのレベルと仕組みと、トンネルパケットのペイロードである元のパケットに適用されるセキュリティーとの間には、依存関係も相互作用もありません。入れ子のトンネルの場合、各内側のトンネルは、外側のトンネルのセキュリティーサービスや、元のパケットの送信元と宛先の間のセキュリティーサービスとは独立に、独自のセキュリティーサービスの集合を持つ場合があります。

Appendix A. Appendix A

Appendix A. 付録A

A.1. Risk Factors in Nested Encapsulation

A.1. 入れ子のカプセル化における危険要因

Nested encapsulations of a packet become a recursive encapsulation if the packet reenters an outer tunnel before exiting it. The cases which present a high risk of recursive encapsulation are those in which a tunnel entry-point node cannot determine whether a packet that undergoes encapsulation reenters the tunnel before exiting it. Routing loops that cause tunnel packets to reenter a tunnel before exiting it are certainly the major cause of the problem. But since routing loops exist, and happen, it is important to understand and describe, the cases in which the risk for recursive encapsulation is higher.

パケットの入れ子のカプセル化は、パケットが外側のトンネルを出る前に再びそのトンネルに入る場合、再帰的なカプセル化になります。再帰的なカプセル化の危険性が高いのは、カプセル化を受けるパケットがトンネルを出る前に再びそのトンネルに入るかどうかを、トンネル入口ノードが判断できない場合です。トンネルパケットがトンネルを出る前に再びそのトンネルに入る原因となるルーティングループは、確かに問題の主な原因です。しかし、ルーティングループは存在し、発生するものであるため、再帰的なカプセル化の危険性がより高い場合を理解し、説明することが重要です。

There are two significant elements that determine the risk factor of routing loop recursive encapsulation:

ルーティングループによる再帰的なカプセル化の危険要因を決定する重要な要素は2つあります。

  1. the type of tunnel,
  2. the type of route to the tunnel exit-point, which determines the packet forwarding through the tunnel, that is, over the tunnel virtual-link.
  1. トンネルの種類
  2. トンネル出口への経路の種類。これは、トンネルを通じた、すなわちトンネルの仮想リンク上でのパケットの転送を決定します。

A.1.1. Risk Factor in Nested Encapsulation - type of tunnel.

A.1.1. 入れ子のカプセル化における危険要因：トンネルの種類

The type of tunnels which were identified as a high risk factor for recursive encapsulation in routing loops are:

ルーティングループにおける再帰的なカプセル化の危険要因が高いと特定されたトンネルの種類は次のとおりです。

"inner tunnels with identical exit-points".

「出口が同一である内側のトンネル」

Since the source and destination of an original packet is the main information used to decide whether to forward a packet through a tunnel or not, a recursive encapsulation can be avoided in case of a single tunnel (non-inner), by checking that the packet to be encapsulated is not originated on the entry-point node. This mechanism is suggested in [RFC-1853].

元のパケットの送信元と宛先は、パケットをトンネルを通じて転送するかどうかを決定するために使用される主な情報であるため、単一の（内側でない）トンネルの場合は、カプセル化されるパケットが入口ノードで発信されたものでないことを検査することで、再帰的なカプセル化を避けることができます。この仕組みは[RFC-1853]で提案されています。

However, this type of protection does not seem to work well in case of inner tunnels with different entry-points, and identical exit- points.

しかし、この種類の保護は、入口が異なり出口が同一である内側のトンネルの場合にはうまく機能しないようです。

Inner tunnels with different entry-points and identical exit-points introduce ambiguity in deciding whether to encapsulate a packet, when a packet encapsulated in an inner tunnel reaches the entry-point node of an outer tunnel by means of a routing loop. Because the source of the tunnel packet is the inner tunnel entry-point node which is different than the entry-point node of the outer tunnel, the source address checking (mentioned above) fails to detect an invalid encapsulation, and as a consequence the tunnel packet gets encapsulated at the outer tunnel each time it reaches it through the routing loop.

入口が異なり出口が同一である内側のトンネルは、内側のトンネルでカプセル化されたパケットがルーティングループによって外側のトンネルの入口ノードに到達した場合に、パケットをカプセル化するかどうかの決定にあいまいさをもたらします。トンネルパケットの送信元は内側のトンネルの入口ノードであり、外側のトンネルの入口ノードとは異なるため、（上記の）送信元アドレスの検査は無効なカプセル化を検出できず、その結果、トンネルパケットは、ルーティングループを通じて外側のトンネルに到達するたびに、そこでカプセル化されます。

A.1.2. Risk Factor in Nested Encapsulation - type of route.

A.1.2. 入れ子のカプセル化における危険要因：経路の種類

The type of route to a tunnel exit-point node has been also identified as a high risk factor of recursive encapsulation in routing loops.

トンネル出口ノードへの経路の種類も、ルーティングループにおける再帰的なカプセル化の危険要因が高いものとして特定されています。

One type of route to a tunnel exit-point node is a route to a specified destination node, that is, the destination is a valid specified IPv6 address (route to node). Such a route can be selected based on the longest match of an original packet destination address with the destination address stored in the tunnel entry-point node routing table entry for that route. The packet forwarded on such a route is first encapsulated and then forwarded towards the tunnel exit-point node.

トンネル出口ノードへの経路の種類の1つは、指定された宛先ノードへの経路、すなわち、宛先が有効な指定されたIPv6アドレスである経路（ノードへの経路）です。そのような経路は、元のパケットの宛先アドレスと、その経路についてトンネル入口ノードのルーティングテーブルのエントリーに格納された宛先アドレスとの最長一致に基づいて選択できます。そのような経路で転送されるパケットは、まずカプセル化され、次にトンネル出口ノードに向けて転送されます。

Another type of route to a tunnel exit-point node is a route to a specified prefix-net, that is, the destination is a valid specified IPv6 prefix (route to net). Such a route can be selected based on the longest path match of an original packet destination address with the prefix destination stored in the tunnel entry-point node routing table entry for that route. The packet forwarded on such a route is first encapsulated and then forwarded towards the tunnel exit-point node.

トンネル出口ノードへの経路の別の種類は、指定されたプレフィックスのネットワークへの経路、すなわち、宛先が有効な指定されたIPv6プレフィックスである経路（ネットワークへの経路）です。そのような経路は、元のパケットの宛先アドレスと、その経路についてトンネル入口ノードのルーティングテーブルのエントリーに格納されたプレフィックスの宛先との最長パス一致に基づいて選択できます。そのような経路で転送されるパケットは、まずカプセル化され、次にトンネル出口ノードに向けて転送されます。

And finally another type of route to a tunnel exit-point is a default route, or a route to an unspecified destination. This route is selected when no-other match for the destination of the original packet has been found in the routing table. A tunnel that is the first hop of a default route is a "default tunnel".

そして最後に、トンネル出口への経路のさらに別の種類は、デフォルト経路、すなわち指定されていない宛先への経路です。この経路は、ルーティングテーブルで元のパケットの宛先に一致するものが他に見つからなかった場合に選択されます。デフォルト経路の最初のホップであるトンネルは「デフォルトトンネル」です。

If the route to a tunnel exit-point is a route to node, the risk factor for recursive encapsulation is minimum.

トンネル出口への経路がノードへの経路である場合、再帰的なカプセル化の危険要因は最小です。

If the route to a tunnel exit-point is a route to net, the risk factor for recursive encapsulation is medium. There is a range of destination addresses that will match the prefix the route is associated with. If one or more inner tunnels with different tunnel entry-points have exit-point node addresses that match the route to net of an outer tunnel exit-point, then a recursive encapsulation may occur if a tunnel packet gets diverted from inside such an inner tunnel to the entry-point of the outer tunnel that has a route to its exit-point that matches the exit-point of an inner tunnel.

トンネル出口への経路がネットワークへの経路である場合、再帰的なカプセル化の危険要因は中程度です。経路が関連付けられているプレフィックスに一致する宛先アドレスには範囲があります。入口が異なる1つ以上の内側のトンネルの出口ノードのアドレスが、外側のトンネルの出口へのネットワークへの経路に一致する場合、トンネルパケットがそのような内側のトンネルの中から、内側のトンネルの出口に一致する出口への経路を持つ外側のトンネルの入口にそらされると、再帰的なカプセル化が発生する可能性があります。

If the route to a tunnel exit-point is a default route, the risk factor for recursive encapsulation is maximum. Packets are forwarded through a default tunnel for lack of a better route. In many situations, forwarding through a default tunnel can happen for a wide range of destination addresses which at the maximum extent is the entire Internet minus the node's link. As consequence, it is likely that in a routing loop case, if a tunnel packet gets diverted from an inner tunnel to an outer tunnel entry-point in which the tunnel is a default tunnel, the packet will be once more encapsulated, because the default routing mechanism will not be able to discern differently, based on the destination.

トンネル出口への経路がデフォルト経路である場合、再帰的なカプセル化の危険要因は最大です。パケットは、よりよい経路がないためにデフォルトトンネルを通じて転送されます。多くの状況で、デフォルトトンネルを通じた転送は、最大でノードのリンクを除くインターネット全体という広い範囲の宛先アドレスに対して発生する可能性があります。その結果、ルーティングループの場合に、トンネルパケットが内側のトンネルから、トンネルがデフォルトトンネルである外側のトンネルの入口にそらされると、デフォルトのルーティングの仕組みは宛先に基づいて区別できないため、パケットはもう一度カプセル化される可能性が高くなります。
