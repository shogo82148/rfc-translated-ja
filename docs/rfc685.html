RFC 685

Response Time in Cross-network Debugging

RFC 685

ネットワーク越しのデバッグにおける応答時間

Abstract

概要

Cross-network debugging is a means whereby a programmer at one computer on a network can debug a program which executes on another computer. One form of cross-net debugging has been in use for some years by programmers who maintain IMPs on the ARPA network. Another form has been used by ARPA network users who employ TELNET or RSEXEC to log into a distant computer and remotely run a debugger on that machine. In both of these cases, the debugger is almost entirely resident in the same machine as the subject program, and only a remote means of access to that computer distinguishes the activity from single-computer debugging.

ネットワーク越しのデバッグ（cross-network debugging）とは、ネットワーク上のあるコンピューターにいるプログラマーが、別のコンピューターで実行されるプログラムをデバッグできるようにする手段です。ネットワーク越しのデバッグの一形態は、ARPAネットワークのIMPを保守するプログラマーによって数年前から使われています。別の形態は、TELNETやRSEXECを使って遠方のコンピューターにログインし、そのマシン上でデバッガーをリモートで実行するARPAネットワークの利用者によって使われています。これらのどちらの場合も、デバッガーはほぼ完全に対象プログラムと同じマシンに常駐しており、単一コンピューターでのデバッグと違うのは、そのコンピューターへのアクセス手段がリモートであるという点だけです。

In our case, we use a PDP-10 to perform complex debugging manipulations. Simple manipulations, and complex actions which the PDP-10 has partially digested into simple actions, are sent over the ARPA network to a PDP-11. The portion of the debugger resident in the PDP-11, where the subject program executes, can perform only simple actions (examine, deposit, start, stop, set breakpoint, etc.). This division of debugging computation between the two machines is implemented and in use at BBN. A user s manual is available (as (BBN]<DOCUMENTATION>XNET.DOC) describing the debugger s features and discussing some of the issues involved.

私たちの場合は、PDP-10を使って複雑なデバッグ操作を行います。単純な操作と、PDP-10が部分的に単純な動作へと分解した複雑な動作とが、ARPAネットワーク越しにPDP-11へ送られます。対象プログラムが実行されるPDP-11に常駐するデバッガーの部分は、単純な動作（検査、書き込み、開始、停止、ブレークポイントの設定など）しか行えません。2つのマシン間でのこのようなデバッグ処理の分担は、BBNで実装され、使われています。デバッガーの機能を説明し、関連するいくつかの問題点を論じたユーザーズマニュアルが（(BBN]<DOCUMENTATION>XNET.DOCとして）入手できます。

The purpose of this RFC is to describe our experience with response times the debugger exhibits. Response time is a serious problem in any elaboration to a debugger. Here we wish to discuss the contribution of communicating over the ARPA network to response time. The debugger (X-NET) keeps statistics during each debugging session, and a debugger command prints them out. We used a "standard scenario" to measure response times on two occasions. The first was debugging a PDP-11 at BBN on the same IMP as the PDP-10. The second was with a PDP-11 at SRI-ARC in California, with at least nine IMPs intervening.

このRFCの目的は、このデバッガーが示す応答時間について私たちの経験を述べることです。デバッガーを高機能にするうえで、応答時間はどのような場合でも深刻な問題です。ここでは、ARPAネットワーク越しに通信することが応答時間にどれだけ寄与するかを論じたいと思います。デバッガー（X-NET）は各デバッグセッション中に統計を取っており、デバッガーのコマンドでそれを出力できます。私たちは「標準シナリオ」を使って、2回にわたって応答時間を測定しました。1回目は、PDP-10と同じIMPにつながったBBNのPDP-11のデバッグです。2回目は、カリフォルニアのSRI-ARCにあるPDP-11が対象で、間に少なくとも9台のIMPを経由しました。

Each session lasted about 10 minutes. The terms used below are:

各セッションは約10分間でした。以下で使う用語は次のとおりです。

message
a single message generated by the PDP-10 portion of X-NET
active command
a command which involves, actually or virtually, an interaction with the subject program (e.g., examine, deposit, start, stop, set breakpoint, etc.)
bytes
the total of all (8-bit) bytes, both sent and received, plus any bytes due to receipt of asynchronous replies (e.g., breakpoint hit), during processing of the associated message or active command.
wait
total elapsed time from handing message to implementation language (BCPL) network routines, to receipt of the reply from these routines and through an inferior process in X-NET
メッセージ（message）
X-NETのPDP-10側の部分が生成する1つのメッセージ
アクティブコマンド（active command）
実際にまたは仮想的に、対象プログラムとのやり取りを伴うコマンド（検査、書き込み、開始、停止、ブレークポイントの設定など）
バイト数（bytes）
対応するメッセージまたはアクティブコマンドの処理中に送受信されたすべての（8ビット）バイトの合計に、非同期の応答（ブレークポイントへの到達など）の受信によるバイトを加えたもの。
待ち時間（wait）
メッセージを実装言語（BCPL）のネットワークルーチンに渡してから、それらのルーチンからの応答を受け取り、X-NET内の下位プロセスを経由するまでの経過時間の合計

The standard deviation is relatively large partly because of a small number of samples, but even more because the message size and the command complexity are bimodal, as shown by the histograms below. The load and word search commands transferred many bytes, as did an examine (the first one while the program was halted; subsequent examines were answerable from the cache; see user s manual). Other commands needed little or no network transaction. Those which needed none at all produced a no-delay mode in the distribution of waiting time per active command.

標準偏差が比較的大きいのは、サンプル数が少ないことも一因ですが、それ以上に、以下のヒストグラムに示すように、メッセージサイズとコマンドの複雑さが二峰性の分布になっているためです。ロードコマンドとワード検索コマンドは多くのバイトを転送しました。検査コマンドの1つ（プログラムの停止中に行った最初の検査。以降の検査はキャッシュから応答できました。ユーザーズマニュアルを参照）も同様です。その他のコマンドは、ネットワークのやり取りをほとんど、またはまったく必要としませんでした。まったく必要としなかったコマンドは、アクティブコマンドあたりの待ち時間の分布において、遅延なしの山を生み出しました。

We conclude that the delay due to network communication is tolerable. It is of the same order of magnitude as that often experienced on moderately loaded time sharing systems. More explicit measurements of delays seen by user programs in general are in progress at BBN and elsewhere; it is beyond the scope of this RFC to discuss these delays in detail, or to break down their causes into process activation, queueing, IMP performance, etc. Instead, we merely note that cross-network debugging is possible in a practical sense.

私たちの結論は、ネットワーク通信による遅延は許容できるということです。その遅延は、中程度の負荷がかかったタイムシェアリングシステムでよく経験するものと同程度の大きさです。ユーザープログラム全般から見た遅延のより詳しい測定がBBNなどで進められています。これらの遅延を詳しく論じたり、その原因をプロセスの起動、キューイング、IMPの性能などに分解したりすることは、このRFCの範囲を超えています。ここでは単に、ネットワーク越しのデバッグが実用的な意味で可能であることを指摘するにとどめます。
