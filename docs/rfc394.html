RFC 394

Two Proposed Changes to the IMP-Host Protocol

RFC 394

IMP-Hostプロトコルに対する2つの変更提案

Abstract

概要

This note describes two changes to the IMP-Host communication protocol described in BBN Report 1822 and revised in RFC 381. The first deals with the IMP-to-Host interface and the 30-second timeout mechanism on each IMP transmission to the Host. The second deals with the Host-to-IMP interface and proposes a new timeout mechanism. These changes are independent; in statement and in implementation. We invite comments on each proposal. If no adverse comments are received, they will be installed in the network on Tuesday, October 10 (if serious adverse comments are received, action will be delayed until early November).

このノートでは、BBN Report 1822で説明され、RFC 381で改訂されたIMP-Host通信プロトコルに対する2つの変更について説明します。1つ目は、IMPからHostへのインターフェイスと、IMPからHostへの各伝送に対する30秒のタイムアウトの仕組みに関するものです。2つ目は、HostからIMPへのインターフェイスに関するもので、新しいタイムアウトの仕組みを提案します。これらの変更は、記述の上でも実装の上でも互いに独立しています。それぞれの提案についてコメントをお寄せください。反対のコメントがなければ、これらの変更は10月10日（火曜日）にネットワークに導入されます（深刻な反対のコメントがあった場合は、実施を11月上旬まで延期します）。

1) Declaring an unresponsive Host as dead to the network

1) 応答しないHostをネットワークに対してダウンと宣言する

Currently, a Host is given 30 seconds to accept each packet of a regular message and is also given 30 seconds to accept non- regular messages. If the Host is unresponsive for this period of time, the IMP takes the following actions:

現在、Hostには、通常メッセージの各パケットを受け入れるのに30秒が与えられ、通常でないメッセージを受け入れるのにも30秒が与えられています。Hostがこの期間応答しない場合、IMPは次の動作を行います。

  1. All messages held for the Host are discarded.
  2. The source Host for each discarded messages is sent a type 9, subtype 0 message (Incomplete Transmission - Destination Host Tardy).
  3. The IMP ready line is dropped and raised again.
  4. The Host is sent 3 type 4 messages (NOP).
  5. The Host is sent a type 10 message (IMP-Host Interface Reset).
  1. そのHost宛てに保持しているすべてのメッセージを破棄します。
  2. 破棄した各メッセージの送信元Hostに、タイプ9、サブタイプ0のメッセージ（Incomplete Transmission - Destination Host Tardy、不完全な伝送 - 宛先Hostの遅延）を送ります。
  3. IMPのレディー線を下げてから、再び上げます。
  4. Hostに、タイプ4のメッセージ（NOP）を3つ送ります。
  5. Hostに、タイプ10のメッセージ（IMP-Host Interface Reset、IMP-Hostインターフェイスのリセット）を送ります。

We propose that in addition the IMP declare the Host dead to the network. Upon receipt of the next bit from the Host, the IMP will declare the Host alive and begin the 30-second delay while the information that the Host is now alive is propagated throughout the network.

私たちは、これに加えて、IMPがそのHostをネットワークに対してダウン（dead）と宣言することを提案します。IMPは、Hostから次のビットを受信したら、そのHostがアップ（alive）であると宣言し、Hostがアップになったという情報がネットワーク全体に伝搬する間、30秒の遅延を開始します。

This change is an attempt to alleviate some problems that are caused by Hosts whose ready lines are up when they are not able to accept bits from the IMP. Several Hosts fall into this category. There are some Hosts whose ready lines are wired to be on all the time. It is annoying, in terminal use and in running survey programs, to have to wait for 30 seconds to find out that a Host is not responding. Other Hosts sometimes go into "break- point mode" for system debugging for several minutes at a time. The NCP software is not running, and messages accumulate in the network and are thrown away. It seems preferable to declare such Hosts to be dead until they send a message* to the IMP, and then any source Host attempting to communicate can be notified at once that the destination Host is dead.

この変更は、IMPからのビットを受け入れられないときにもレディー線が上がっているHostによって生じるいくつかの問題を軽減しようとするものです。いくつかのHostがこれに該当します。レディー線が常にオンになるように配線されているHostもあります。端末を使うときや調査プログラムを実行するときに、Hostが応答していないことを知るために30秒待たなければならないのは煩わしいことです。また、システムのデバッグのために、一度に数分間「ブレークポイントモード」に入るHostもあります。そのときNCPソフトウェアは動作しておらず、メッセージはネットワーク内にたまって捨てられます。このようなHostは、IMPにメッセージ*を送るまではダウンと宣言しておき、通信しようとする送信元Hostには宛先Hostがダウンしていることをすぐに通知できるようにするのが望ましいと思われます。

*Thus a Host should send its IMP at least two NOPs (or other messages) whenever it receives a type 10 message from its IMP.

*したがって、Hostは、自分のIMPからタイプ10のメッセージを受信したときには必ず、そのIMPに少なくとも2つのNOP（または他のメッセージ）を送るべきです。

2) Timing out Host-to-IMP messages in 15 seconds

2) HostからIMPへのメッセージを15秒でタイムアウトさせる

When the IMP receives a message from a Host, it must acquire several internal resources in order to process the message. It must assign it a message number, make an entry in an internal table, and so on. If any of these IMP resources is not available, the IMP simply waits until it does become available. It cannot take any more messages from the Host, and so the interface is stopped. This condition is usually momentary, but under unusual circumstances the IMP may not be able to process a message it has begun to accept for many seconds. This situation creates an especially difficult problem for Hosts with half-duplex interfaces. If the IMP takes 30 seconds to process a message, then the IMP-to- Host timeout outlined in 1) takes effect, and the Host loses all messages sent to it in the last 30 seconds. (It should be noted that the half-duplex interface may be the cause of a deadly embrace, e.g. the reason that the IMP cannot acquire the necessary resources to process a given message may be that the Host in question has several messages on its queue and they are tying up storage, message numbers, or table slots. The Host must accept these messages before any more messages can be introduced into the network.) Even for Hosts with full-duplex interfaces, occurrences of this situation might interfere with other useful communication.

IMPは、Hostからメッセージを受信すると、そのメッセージを処理するためにいくつかの内部リソースを確保しなければなりません。メッセージ番号を割り当てたり、内部テーブルにエントリーを作成したりなどしなければなりません。これらのIMPのリソースのいずれかが利用できない場合、IMPは単にそれが利用できるようになるまで待ちます。その間はHostからそれ以上メッセージを受け取ることができないため、インターフェイスは停止します。この状態は通常は一時的なものですが、通常でない状況では、IMPが受け入れ始めたメッセージを何秒もの間処理できないことがあります。この状況は、半二重のインターフェイスを持つHostにとって特に厄介な問題を引き起こします。IMPがメッセージの処理に30秒かかると、1)で概説したIMPからHostへのタイムアウトが発動し、Hostは直近30秒間に自分宛てに送られたすべてのメッセージを失います。（半二重のインターフェイスはデッドロック（deadly embrace）の原因となりうることに注意してください。たとえば、IMPがあるメッセージを処理するのに必要なリソースを確保できない理由が、当該Hostのキューに複数のメッセージがあり、それらがストレージやメッセージ番号、テーブルのスロットを占有していることである場合があります。それ以上のメッセージをネットワークに投入できるようになるには、Hostがこれらのメッセージを受け入れなければなりません。）全二重のインターフェイスを持つHostであっても、この状況が起こると、他の有用な通信の妨げになるかもしれません。

We propose to notify the Host when the IMP cannot continue to process a message that it has begun to accept. The IMP will try to process the message for 15 seconds, and then will send the Host a type 9, subtype 4 message (bits 30,31,32 = 100) which will be defined as Incomplete Transmission - Resources Unavailable. In such a case, the IMP has not been able to send any part of the message into the network. The IMP will take in the remainder of the message; at that point a Host with a half-duplex interface should begin to accept messages from the IMP, while a Host with a full-duplex interface might attempt to transmit some other message. The Host may attempt to retransmit the incomplete message if that is desirable.

私たちは、IMPが受け入れ始めたメッセージの処理を続けられないときに、そのことをHostに通知することを提案します。IMPは15秒間メッセージの処理を試み、その後、Incomplete Transmission - Resources Unavailable（不完全な伝送 - リソース利用不可）として定義するタイプ9、サブタイプ4のメッセージ（ビット30、31、32 = 100）をHostに送ります。このような場合、IMPはメッセージのどの部分もネットワークに送ることができていません。IMPはメッセージの残りを取り込みます。その時点で、半二重のインターフェイスを持つHostはIMPからのメッセージを受け入れ始めるべきであり、全二重のインターフェイスを持つHostは何か別のメッセージを送信しようとしてもかまいません。Hostは、望ましければ、不完全なメッセージの再送を試みてもかまいません。
