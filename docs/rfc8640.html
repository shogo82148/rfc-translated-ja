RFC 8640

Dynamic Subscription to YANG Events and Datastores over NETCONF

RFC 8640

NETCONFを介したYANGイベントとデータストアへの動的購読

Abstract

概要

This document provides a Network Configuration Protocol (NETCONF) binding to the dynamic subscription capability of both subscribed notifications and YANG-Push.

この文書は、購読通知（subscribed notifications）とYANG-Pushの両方の動的購読能力に対する、ネットワーク設定プロトコル（NETCONF）のバインディングを提供します。

1. Introduction

1. はじめに

This document specifies the binding of a stream of events that form part of a dynamic subscription to the Network Configuration Protocol (NETCONF) [RFC6241]. Dynamic subscriptions are defined in [RFC8639]. In addition, as [RFC8641] is itself built upon [RFC8639], this document enables a NETCONF client to request via a dynamic subscription, and receive, updates from a YANG datastore located on a NETCONF server.

この文書は、動的購読の一部を構成するイベントのストリームの、ネットワーク設定プロトコル（NETCONF）[RFC6241]へのバインディングを規定します。動的購読は[RFC8639]で定義されています。さらに、[RFC8641]自体が[RFC8639]の上に構築されているため、この文書により、NETCONFクライアントは、NETCONFサーバー上にあるYANGデータストアからの更新を、動的購読を介して要求し、受信できるようになります。

This document assumes that the reader is familiar with the terminology and concepts defined in [RFC8639].

この文書は、読者が[RFC8639]で定義されている用語と概念に精通していることを前提としています。

2. Terminology

2. 用語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

この文書におけるキーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

The following terms are defined in [RFC8639]: dynamic subscription, event stream, notification message, publisher, receiver, subscriber, and subscription. This document does not define any additional terms.

次の用語は[RFC8639]で定義されています：動的購読（dynamic subscription）、イベントストリーム（event stream）、通知メッセージ（notification message）、パブリッシャー（publisher）、受信者（receiver）、サブスクライバー（subscriber）、購読（subscription）。この文書では、追加の用語は定義しません。

3. Compatibility with <create-subscription> as Defined in RFC 5277

3. RFC 5277で定義されている<create-subscription>との互換性

A publisher is allowed to concurrently support dynamic subscription RPCs as defined in [RFC8639] at the same time as the <create-subscription> RPC defined in [RFC5277]. However, a single NETCONF transport session MUST NOT support both this specification and a subscription established by the <create-subscription> RPC defined in [RFC5277]. To protect against any attempts to use a single NETCONF transport session in this way:

パブリッシャーは、[RFC8639]で定義されている動的購読のRPCを、[RFC5277]で定義されている<create-subscription> RPCと並行してサポートすることが許されています。ただし、単一のNETCONFトランスポートセッションで、この仕様と、[RFC5277]で定義されている<create-subscription> RPCによって確立された購読の両方をサポートしてはなりません（MUST NOT）。単一のNETCONFトランスポートセッションをこのように使用しようとするあらゆる試みから保護するために、次のようにします：

  • A solution MUST reply with the <rpc-error> element [RFC6241] containing the "error-tag" value of "operation-not-supported" if a <create-subscription> RPC is received on a NETCONF session where an established subscription per [RFC8639] exists.
  • A solution MUST reply with the <rpc-error> element [RFC6241] containing the "error-tag" value of "operation-not-supported" if an "establish-subscription" request has been received on a NETCONF session where the <create-subscription> RPC [RFC5277] has successfully created a subscription.
  • [RFC8639]に従って確立された購読が存在するNETCONFセッション上で<create-subscription> RPCを受信した場合、ソリューションは、「error-tag」の値として「operation-not-supported」を含む<rpc-error>要素[RFC6241]で応答しなければなりません（MUST）。
  • <create-subscription> RPC [RFC5277]によって購読の作成に成功しているNETCONFセッション上で「establish-subscription」リクエストを受信した場合、ソリューションは、「error-tag」の値として「operation-not-supported」を含む<rpc-error>要素[RFC6241]で応答しなければなりません（MUST）。

If a publisher supports this specification but not subscriptions via [RFC5277], the publisher MUST NOT advertise "urn:ietf:params:netconf:capability:notification:1.0".

パブリッシャーがこの仕様をサポートしているものの、[RFC5277]を介した購読をサポートしていない場合、そのパブリッシャーは「urn:ietf:params:netconf:capability:notification:1.0」を広告してはなりません（MUST NOT）。

4. Mandatory XML, Event Stream, and Datastore Support

4. XML、イベントストリーム、データストアの必須サポート

The "encode-xml" feature of [RFC8639] MUST be supported. This indicates that XML is a valid encoding for RPCs, state change notifications, and subscribed content.

[RFC8639]の「encode-xml」機能（feature）をサポートしなければなりません（MUST）。これは、XMLがRPC、状態変化通知、購読されたコンテンツに対する有効なエンコーディングであることを示します。

A NETCONF publisher supporting event stream subscription via [RFC8639] MUST support the "NETCONF" event stream identified in that document.

[RFC8639]を介したイベントストリーム購読をサポートするNETCONFパブリッシャーは、その文書で識別されている「NETCONF」イベントストリームをサポートしなければなりません（MUST）。

5. NETCONF Connectivity and Dynamic Subscriptions

5. NETCONFの接続性と動的購読

Management of dynamic subscriptions occurs via RPCs as defined in [RFC8641] and [RFC8639]. For a dynamic subscription, if the NETCONF session involved with the "establish-subscription" terminates, the subscription MUST be terminated.

動的購読の管理は、[RFC8641]と[RFC8639]で定義されているRPCを介して行われます。動的購読において、「establish-subscription」に関与したNETCONFセッションが終了した場合、その購読を終了しなければなりません（MUST）。

For a dynamic subscription, any "modify-subscription", "delete-subscription", or "resync-subscription" RPCs MUST be sent using the same NETCONF session upon which the referenced subscription was established.

動的購読において、「modify-subscription」、「delete-subscription」、「resync-subscription」のRPCはいずれも、参照される購読が確立されたのと同じNETCONFセッションを使用して送信しなければなりません（MUST）。

6. Notification Messages

6. 通知メッセージ

Notification messages transported over NETCONF MUST be encoded in a <notification> message as defined in [RFC5277], Section 4. And per the <eventTime> object definition provided in [RFC5277], <eventTime> is populated with the event occurrence time.

NETCONF上で運ばれる通知メッセージは、[RFC5277], Section 4で定義されている<notification>メッセージにエンコードしなければなりません（MUST）。また、[RFC5277]で提供されている<eventTime>オブジェクトの定義に従い、<eventTime>にはイベント発生時刻を設定します。

For dynamic subscriptions, all notification messages MUST use the NETCONF transport session used by the "establish-subscription" RPC.

動的購読では、すべての通知メッセージは、「establish-subscription」RPCで使用されたNETCONFトランスポートセッションを使用しなければなりません（MUST）。

7. Dynamic Subscriptions and RPC Error Responses

7. 動的購読とRPCエラーレスポンス

When an RPC error occurs as defined in [RFC8639], Section 2.4.6 and [RFC8641], Appendix A, the NETCONF RPC reply MUST include an <rpc-error> element per [RFC6241] with the error information populated as follows:

[RFC8639], Section 2.4.6および[RFC8641], Appendix Aで定義されているRPCエラーが発生した場合、NETCONFのRPCの応答には、[RFC6241]に従い、次のようにエラー情報を設定した<rpc-error>要素を含めなければなりません（MUST）：

  • An "error-type" node of "application".

  • An "error-tag" node, where the value is a string that corresponds to an identity associated with the error. For the mechanisms specified in this document, this "error-tag" will correspond to the error identities in either (1) [RFC8639], Section 2.4.6, for general subscription errors:

    Table 1
    error identity uses error-tag
    dscp-unavailable invalid-value
    encoding-unsupported invalid-value
    filter-unsupported invalid-value
    insufficient-resources resource-denied
    no-such-subscription invalid-value
    replay-unsupported operation-not-supported

    or (2) [RFC8641], Appendix A.1, for subscription errors specific to YANG datastores:

    Table 2
    error identity uses error-tag
    cant-exclude operation-not-supported
    datastore-not-subscribable invalid-value
    no-such-subscription-resync invalid-value
    on-change-unsupported operation-not-supported
    on-change-sync-unsupported operation-not-supported
    period-unsupported invalid-value
    update-too-big too-big
    sync-too-big too-big
    unchanging-selection operation-failed
  • An "error-severity" of "error" (this MAY be included).

  • An "error-app-tag" node, where the value is a string that corresponds to an identity associated with the error, as defined in [RFC8639], Section 2.4.6 for general subscriptions and [RFC8641], Appendix A.1 for datastore subscriptions. The specific identity to use depends on the RPC for which the error occurred. Each error identity will be inserted as the "error-app-tag" following the form <modulename>:<identityname>. An example of such a valid encoding would be "ietf-subscribed-notifications:no-such-subscription". Viable errors for different RPCs are as follows:

    Table 3
    RPC has base identity
    establish-subscription establish-subscription-error
    modify-subscription modify-subscription-error
    delete-subscription delete-subscription-error
    kill-subscription delete-subscription-error
    resync-subscription resync-subscription-error

  • In the case of error responses to an "establish-subscription" or "modify-subscription" request, there is the option of including an "error-info" node. This node may contain XML-encoded data with hints for parameter settings that might lead to successful RPC requests in the future. The yang-data structures from [RFC8639] and [RFC8641] that may be returned are as follows:

    Table 4
    establish-subscription returns hints in yang-data structure
    target: event stream establish-subscription-stream-error-info
    target: datastore establish-subscription-datastore-error-info
    Table 5
    modify-subscription returns hints in yang-data structure
    target: event stream modify-subscription-stream-error-info
    target: datastore modify-subscription-datastore-error-info

    The yang-data included in "error-info" SHOULD NOT include the optional leaf "reason", as such a leaf would be redundant with information that is already placed in the "error-app-tag".

  • 値が「application」である「error-type」ノード。

  • エラーに関連付けられたアイデンティティーに対応する文字列を値とする「error-tag」ノード。この文書で規定するメカニズムでは、この「error-tag」は次のいずれかのエラーアイデンティティーに対応します。(1) 一般的な購読エラーについては、[RFC8639], Section 2.4.6のエラーアイデンティティー：

    表 1
    エラーアイデンティティー 使用する「error-tag」
    dscp-unavailable invalid-value
    encoding-unsupported invalid-value
    filter-unsupported invalid-value
    insufficient-resources resource-denied
    no-such-subscription invalid-value
    replay-unsupported operation-not-supported

    または、(2) YANGデータストアに固有の購読エラーについては、[RFC8641], Appendix A.1のエラーアイデンティティー：

    表 2
    エラーアイデンティティー 使用する「error-tag」
    cant-exclude operation-not-supported
    datastore-not-subscribable invalid-value
    no-such-subscription-resync invalid-value
    on-change-unsupported operation-not-supported
    on-change-sync-unsupported operation-not-supported
    period-unsupported invalid-value
    update-too-big too-big
    sync-too-big too-big
    unchanging-selection operation-failed
  • 値が「error」である「error-severity」（これは含めてもよいです（MAY））。

  • 一般的な購読については[RFC8639], Section 2.4.6で、データストア購読については[RFC8641], Appendix A.1で定義されている、エラーに関連付けられたアイデンティティーに対応する文字列を値とする「error-app-tag」ノード。使用する具体的なアイデンティティーは、エラーが発生したRPCによって異なります。各エラーアイデンティティーは、<modulename>:<identityname>という形式に従って「error-app-tag」として挿入されます。そのような有効なエンコーディングの例は「ietf-subscribed-notifications:no-such-subscription」です。RPCごとに発生しうるエラーは次のとおりです：

    表 3
    RPC ベースアイデンティティー
    establish-subscription establish-subscription-error
    modify-subscription modify-subscription-error
    delete-subscription delete-subscription-error
    kill-subscription delete-subscription-error
    resync-subscription resync-subscription-error

  • 「establish-subscription」または「modify-subscription」リクエストに対するエラーレスポンスの場合は、「error-info」ノードを含めることもできます。このノードには、将来のRPCリクエストを成功させる可能性のあるパラメーター設定のヒントを含む、XMLでエンコードされたデータを含めることができます。返される可能性のある[RFC8639]と[RFC8641]のyang-data構造は次のとおりです：

    表 4
    establish-subscription ヒントを返すyang-data構造
    対象：イベントストリーム establish-subscription-stream-error-info
    対象：データストア establish-subscription-datastore-error-info
    表 5
    modify-subscription ヒントを返すyang-data構造
    対象：イベントストリーム modify-subscription-stream-error-info
    対象：データストア modify-subscription-datastore-error-info

    「error-info」に含まれるyang-dataには、オプションのリーフ「reason」を含めるべきではありません（SHOULD NOT）。そのようなリーフは、すでに「error-app-tag」に置かれている情報と重複するためです。

In the case of an RPC error resulting from a "delete-subscription", "kill-subscription", or "resync-subscription" request, no "error-info" needs to be included, as the "subscription-id" is the only RPC input parameter and no hints regarding this RPC input parameter need to be provided.

「delete-subscription」、「kill-subscription」、「resync-subscription」のいずれかのリクエストの結果としてRPCエラーが発生した場合は、「error-info」を含める必要はありません。「subscription-id」が唯一のRPC入力パラメーターであり、このRPC入力パラメーターに関するヒントを提供する必要はないためです。

8. Security Considerations

8. セキュリティーに関する考慮事項

This document does not introduce additional security considerations for dynamic subscriptions beyond those discussed in [RFC8639]. But there is one consideration worthy of more refinement based on the connection-oriented nature of NETCONF. Specifically, if a buggy or compromised NETCONF subscriber sends a number of "establish-subscription" requests, then these subscriptions accumulate and may use up system resources. In such a situation, subscriptions MAY be terminated by terminating the underlying NETCONF session. The publisher MAY also suspend or terminate a subset of the active subscriptions on that NETCONF session in order to reclaim resources and preserve normal operation for the other subscriptions.

この文書は、動的購読について、[RFC8639]で議論されているものを超える追加のセキュリティー上の考慮事項を導入しません。ただし、NETCONFのコネクション指向の性質に基づいて、さらに詳しく検討する価値のある考慮事項が1つあります。具体的には、バグのある、または侵害されたNETCONFサブスクライバーが多数の「establish-subscription」リクエストを送信すると、それらの購読が蓄積し、システムリソースを使い果たす可能性があります。そのような状況では、基盤となるNETCONFセッションを終了することによって購読を終了してもよいです（MAY）。また、パブリッシャーは、リソースを回収して他の購読の正常な動作を維持するために、そのNETCONFセッション上のアクティブな購読の一部を一時停止または終了してもよいです（MAY）。

A.1. イベントストリームの発見
