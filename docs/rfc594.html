RFC 594

Speedup of Host-IMP Interface

RFC 594

ホスト-IMPインターフェイスの高速化

I. Introduction

I. はじめに

In order to make the full performance capabilities of the subnet available for interprocess communication, the host's IMP interface and the IMP's host interface should operate at the highest speed obtainable.

サブネットの性能を最大限にプロセス間通信に活用できるようにするには、ホストのIMPインターフェイスとIMPのホストインターフェイスを、実現可能な最高速度で動作させるべきです。

First, this high throughput will minimize the latency observed when RFNM's, control messages, and NVT (network virtual terminal) characters are queued behind full sized messages. A full-sized message currently ties up a 100 kb interface for almost 100 Msec. delaying short messages behind it by 100 Msec. Speeding up the host interface to 300 kilobaud will shrink this latency to 30 Msec.

第1に、この高いスループットにより、RFNM、制御メッセージ、NVT（ネットワーク仮想端末）の文字が最大長のメッセージの後ろに待たされるときに観測される遅延が最小になります。現在、最大長のメッセージは100 kbのインターフェイスをほぼ100ミリ秒占有し、その後ろにある短いメッセージを100ミリ秒遅らせます。ホストインターフェイスを300キロボーに高速化すれば、この遅延は30ミリ秒に短縮されます。

Secondly, this high-speed operation minimizes the time that the IMP buffer and the host core buffer are locked down during message transfer. (One being emptied, one being filled). Being able to dispose of buffers far faster means that many fewer of them will suffice to carry the communications traffic; each buffer can be reused far more often.

第2に、この高速動作により、メッセージ転送中にIMPのバッファーとホストのコアバッファーが（一方は空にされ、一方は満たされている間）固定される時間が最小になります。バッファーをはるかに速く処理できるということは、通信トラフィックを運ぶのに必要なバッファーがずっと少なくて済むということです。各バッファーをはるかに頻繁に再利用できるからです。

Third, high-speed operation makes it possible to improve error control: currently, a destination IMP returns an RFNM after transmitting the first packet of a multipacket message to the destination host. If an error occurs during the transmission of the (up to seven) other packets into the destination host, the source host will not be informed of the error: it has already been given a positive message acknowledgement in the RFNM. The alternative, holding off the RFNM until all packets have been transmitted into the destination host, would add another 80 Msec. to the round trip message - RFNM time with the current 100 kilobaud interface. A higher speed interface will reduce this delayed - RFNM cost to a more acceptable value, making it practical to eliminate this source of undetected message transmission errors.

第3に、高速動作によってエラー制御を改善できるようになります。現在、宛先のIMPは、複数パケットからなるメッセージの最初のパケットを宛先ホストに送信した後でRFNMを返します。残りの（最大7つの）パケットを宛先ホストに送信している間にエラーが発生しても、送信元ホストにはそのエラーが通知されません。送信元ホストはRFNMによってすでにメッセージの肯定応答を受け取っているからです。代わりに、すべてのパケットが宛先ホストに送信されるまでRFNMを保留するという方法をとると、現在の100キロボーのインターフェイスでは、メッセージとRFNMの往復時間にさらに80ミリ秒が加わります。より高速なインターフェイスであれば、この遅延RFNMのコストをより許容できる値に減らせるので、検出されないメッセージ送信エラーのこの原因を取り除くことが現実的になります。

Fourth, a high speed interface will permit greater host communications bandwidth. (Currently limited to 100 kilobaud). This increase in bandwidth will be essential for communications between hosts at a "network-structured" site, where different hosts on the same IMP are specialized to perform different parts of a computation.

第4に、高速なインターフェイスにより、ホストの通信帯域幅を（現在は100キロボーに制限されていますが）大きくできます。この帯域幅の増加は、同じIMP上の異なるホストが計算の異なる部分を専門に担当する「ネットワーク構造の」サイトにおいて、ホスト間の通信に不可欠となるでしょう。

Clearly, any new or retrofitted host interfaces should be very high speed, and existing host interfaces should be adjusted to operate at their maximum speed, which is in excess of 300 kilobaud.

明らかに、新規または改修したホストインターフェイスは非常に高速であるべきです。また、既存のホストインターフェイスは、その最高速度（300キロボーを超えます）で動作するように調整すべきです。

II. Experimental Results

II. 実験結果

In support of the above predictions, the BBN TENEX staff performed an experiment in cooperation with the BBN IMP group to determine how fast the System A (BBN-TENEX) and System B (BBNB) distant interfaces would operate.

上記の予測を裏付けるために、BBN TENEXのスタッフはBBN IMPグループと協力して、System A（BBN-TENEX）とSystem B（BBNB）の遠隔インターフェイスがどの程度の速さで動作するかを調べる実験を行いました。

Results are as follows:

結果は次のとおりです。

The Host-to-IMP connection is synchronized by a two-way handshake which has an available burst bandwidth of 1 bit/(2225 nsec + 3 nsec/ft.*<cable length>ft) For our cable length, this results in a bandwidth of 310 kilobaud.

ホストからIMPへの接続は、2方向のハンドシェイクで同期されます。このハンドシェイクで利用できるバースト帯域幅は、1ビット/（2225ナノ秒 + 3ナノ秒/フィート×<ケーブル長>フィート）です。当方のケーブル長では、これは310キロボーの帯域幅になります。

The IMP-to-Host connection is synchronized by a four-way handshake which has an available burst bandwidth of 1 bit/(1350 nsec + 6 nsec/ft.*<cable length>ft.) which results in a bandwidth of 290 kilobaud for our installation.

IMPからホストへの接続は、4方向のハンドシェイクで同期されます。このハンドシェイクで利用できるバースト帯域幅は、1ビット/（1350ナノ秒 + 6ナノ秒/フィート×<ケーブル長>フィート）で、当方の設備では290キロボーの帯域幅になります。

Both System A and System B are now operating at this higher interface speed.

System AとSystem Bは、どちらも現在このより高速なインターフェイス速度で動作しています。

Since the propogation delay time through a distant host driver-receiver pair amounts to 250 nsec, it is expected that local host interfaces (<30ft) can be operated at speeds substantially faster than our 300 kilobaud.

遠隔ホストのドライバーとレシーバーの組を通る伝搬遅延時間は250ナノ秒になるので、ローカルホストのインターフェイス（30フィート未満）は、当方の300キロボーよりも大幅に高速に動作させられると期待されます。

In addition to the above measurements of hardware speed, new results were obtained in measurements of file transfer performance, i.e. the CPU time and real time used per megabit of information transmitted over the network.

上記のハードウェア速度の測定に加えて、ファイル転送性能、すなわちネットワーク上で送信される情報1メガビットあたりに使われるCPU時間と実時間の測定でも、新たな結果が得られました。

This experiment involved the movement of one-megabit data files to and from an FTP User process in System B communicating with the FTP Server Process in System A. The results are summarized in the followiing table:

この実験では、System AのFTPサーバープロセスと通信するSystem BのFTPユーザープロセスとの間で、1メガビットのデータファイルを送受信しました。結果を次の表にまとめます。

   Send          8         ASCII       50Kbaud              7.9

   Send          32        LocalByte   38Kbaud              1.70
   Get           36        Image       79Kbaud              1.85
   Send          36        Image       85Kbaud               .95

The 36-bit bandwidth of around 80Kbaud is a great improvement from the (typically 25Kbaud measured before the speedup of the interface hardware. The CPU time use has also decreased somewhat from that reported in RFC #557 by Barry Wessler: this demonstrates continued improvement of system efficiency between the TENEX version 1.31 and TENEX version 1.32.

36ビットでの約80キロボーという帯域幅は、インターフェイスハードウェアを高速化する前に測定された値（通常25キロボー）から大きく改善しています。CPU時間の使用量も、Barry WesslerがRFC #557で報告した値からいくらか減少しています。これは、TENEXのバージョン1.31からバージョン1.32にかけて、システムの効率が引き続き改善されていることを示しています。

In conclusion, the BBN-TENEX staff recommends that all host-IMP interfaces in the network be speeded up to the fastest operation obtainable.

結論として、BBN-TENEXのスタッフは、ネットワーク内のすべてのホスト-IMPインターフェイスを、実現可能な最速の動作に高速化することを推奨します。
