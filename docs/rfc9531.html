Path Steering in Content-Centric Networking (CCNx) and Named Data Networking (NDN)

RFC 9531

コンテンツ指向ネットワーキング（CCNx）と名前付きデータネットワーキング（NDN）におけるパスステアリング

Abstract

概要

Path steering is a mechanism to discover paths to the producers of Information-Centric Networking (ICN) Content Objects and steer subsequent Interest messages along a previously discovered path. It has various uses, including the operation of state-of-the-art multi-path congestion control algorithms and for network measurement and management. This specification derives directly from the design published in "Path Switching in Content Centric and Named Data Networks" (4th ACM Conference on Information-Centric Networking) and, therefore, does not recapitulate the design motivations, implementation details, or evaluation of the scheme. However, some technical details are different, and where there are differences, the design documented here is to be considered definitive.

1. Introduction

1. はじめに

Path steering is a mechanism to discover paths to the producers of ICN Content Objects and steer subsequent Interest messages along a previously discovered path. It has various uses, including the operation of state-of-the-art multi-path congestion control algorithms and for network measurement and management. This specification derives directly from the design published in [Moiseenko2017] and, therefore, does not recapitulate the design motivations, implementation details, or evaluation of the scheme. That publication should be considered a normative reference as it is not likely a reader will be able to understand all elements of this design without first having read the reference. However, some technical details are different, and where there are differences, the design documented here is to be considered definitive.

パスステアリングは、ICNのContent Objectのプロデューサーへのパスを発見し、後続のInterestメッセージを以前に発見したパスに沿って誘導（steer）するメカニズムです。 パスステアリングには、最先端のマルチパス輻輳制御アルゴリズムの動作や、ネットワークの測定と管理など、さまざまな用途があります。 この仕様は、[Moiseenko2017]で公開された設計から直接派生したものであり、そのため、この方式の設計動機、実装の詳細、評価については繰り返しません。 読者がこの参考文献を先に読まずにこの設計のすべての要素を理解できる可能性は低いため、この文献は規範的な参考文献とみなすべきです。 ただし、一部の技術的な詳細は異なっており、違いがある箇所では、ここに記載した設計を決定版とみなします。

Path discovery and subsequent path steering in ICN networks is facilitated by the symmetry of forward and reverse paths in the Content-Centric Networking (CCNx) and Named Data Networking (NDN) architectures. Path discovery is achieved by a consumer endpoint transmitting an ordinary Interest message and receiving a Content (Data) message containing an end-to-end path label constructed on the reverse path by the forwarding plane. Path steering is achieved by a consumer endpoint including a path label in the Interest message, which is forwarded to each nexthop through the corresponding egress interfaces in conjunction with Longest Name Prefix Match (LNPM) lookup in the Forwarding Information Base (FIB).

ICNネットワークにおけるパス発見とそれに続くパスステアリングは、コンテンツ指向ネットワーキング（Content-Centric Networking、CCNx）および名前付きデータネットワーキング（Named Data Networking、NDN）のアーキテクチャーにおいて往路と復路のパスが対称であることによって実現しやすくなっています。 パス発見は、コンシューマーのエンドポイントが通常のInterestメッセージを送信し、転送プレーンによって復路上で構築されたエンドツーエンドのパスラベルを含むContent（Data）メッセージを受信することで実現されます。 パスステアリングは、コンシューマーのエンドポイントがInterestメッセージにパスラベルを含めることで実現されます。 このInterestメッセージは、転送情報ベース（Forwarding Information Base、FIB）での最長名前プレフィックス一致（Longest Name Prefix Match、LNPM）検索と組み合わせて、対応する出力インターフェイスを通じて各ネクストホップに転送されます。

This document is a product of the IRTF Information-Centric Networking Research Group (ICNRG). It was supported by the ICNRG participants during its development and through Research Group Last Call. It has received detailed review by experts in both the CCNx and NDN communities.

この文書は、IRTFの情報指向ネットワーキング研究グループ（ICNRG）の成果物です。 この文書は、その開発中および研究グループのラストコールを通じて、ICNRGの参加者によって支持されました。 この文書は、CCNxとNDNの両方のコミュニティーの専門家による詳細なレビューを受けています。

1.1. Path Steering as an Experimental Extension to ICN Protocol Architectures

1.1. ICNプロトコルアーキテクチャーの実験的な拡張としてのパスステアリング

There are a number of important use cases to justify extending ICN architectures such as CCNx [RFC8569] or NDN [NDN] to provide these capabilities. These are summarized as follows:

CCNx[RFC8569]やNDN[NDN]のようなICNアーキテクチャーを拡張してこれらの能力を提供することを正当化する重要なユースケースがいくつかあります。それらを以下にまとめます。

  • Support the discovery, monitoring, and troubleshooting of multi-path network connectivity, based on names and name prefixes. Analogous functions have been shown to be a crucial operational capability in multicast and multi-path topologies for IP. The canonical tools are the well-known traceroute and ping. For point-to-multipoint MPLS, the more recent MPLS traceroute [RFC8029] protocol is used. Equivalent diagnostic functions have been defined for CCNx through the ICN Ping [RFC9508] and ICN Traceroute [RFC9507] specifications; both of which are capable of exploiting path steering, if available.
  • Perform accurate online measurement of network performance, which generally requires multiple consecutive packets to follow the same path under control of an application.
  • Improve the performance and flexibility of multi-path congestion control algorithms. Congestion control schemes, such as [Mahdian2016] and [Song2018], depend on the ability of a consumer to explicitly steer packets onto individual paths in a multi-path and/or multi-destination topology.
  • Allow a consumer endpoint to mitigate content poisoning attacks by directing its Interests onto the network paths that bypass poisoned caches.
  • 名前と名前プレフィックスに基づいた、マルチパスのネットワーク接続性の発見、監視、トラブルシューティングをサポートします。 IPのマルチキャストおよびマルチパスのトポロジーでは、同様の機能が運用上きわめて重要な能力であることが示されています。 代表的なツールは、よく知られているtracerouteとpingです。 ポイントツーマルチポイントのMPLSでは、より新しいMPLS traceroute[RFC8029]プロトコルが使用されます。 CCNxでは、ICN Ping[RFC9508]およびICN Traceroute[RFC9507]の仕様によって同等の診断機能が定義されています。 これらはどちらも、利用可能であればパスステアリングを活用できます。
  • ネットワーク性能の正確なオンライン測定を行います。 これには一般に、連続する複数のパケットがアプリケーションの制御下で同じパスをたどる必要があります。
  • マルチパス輻輳制御アルゴリズムの性能と柔軟性を向上させます。 [Mahdian2016]や[Song2018]などの輻輳制御方式は、マルチパスまたはマルチデスティネーション（あるいはその両方）のトポロジーにおいて、コンシューマーがパケットを個々のパスに明示的に誘導できることに依存しています。
  • コンシューマーのエンドポイントが、汚染されたキャッシュを迂回するネットワークパスに自身のInterestを向けることで、コンテンツポイズニング攻撃を緩和できるようにします。

The path discovery machinery described here may (and likely will) discover paths with varying properties. [RFC9217] discusses a number of open questions in path-aware networking, among which is how to assess and exploit paths having different properties. Experimenting with ICN path steering may be helpful in further elucidating these questions and perhaps shedding light on which path properties are most useful for the use cases cited above.

ここで説明するパス発見の仕組みは、さまざまな特性を持つパスを発見する可能性があります（そしておそらく発見するでしょう）。 [RFC9217]は、パスを認識するネットワーキング（path-aware networking）における未解決の問題をいくつか議論しており、その中には、異なる特性を持つパスをどのように評価し活用するかという問題があります。 ICNのパスステアリングを実験することは、これらの問題をさらに解明し、上で挙げたユースケースにとってどのパス特性が最も有用であるかを明らかにするのに役立つかもしれません。

One nuance compared to other path-aware networking approaches is that ICN path steering piggybacks path discovery on the base ICN data exchange rather than having a separate path advertisement or discovery mechanism. That means when the recorded path comes back in an ICN Data message response, the properties of the path are known only implicitly to the consumer as opposed to being explicitly labeled. That makes the question of what properties a consumer uses to choose a path one of observation or measurement rather than advance selection based on an explicit, advertised property (e.g., SCION [SCION]).

他のパスを認識するネットワーキングのアプローチと比較した場合の微妙な違いの1つは、ICNのパスステアリングが、別個のパス広告や発見のメカニズムを持つのではなく、ICNの基本的なデータ交換にパス発見を相乗りさせていることです。 つまり、記録されたパスがICNのDataメッセージのレスポンスで返ってきたとき、パスの特性は明示的にラベル付けされているのではなく、コンシューマーには暗黙的にしかわかりません。 そのため、コンシューマーがパスを選ぶためにどの特性を使うかという問題は、明示的に広告された特性（例: SCION[SCION]）に基づく事前選択ではなく、観察や測定の問題になります。

The utility and overall technical quality of this path steering capability can be assessed by how well it enables the above use cases and what performance and robustness effects it has on the underlying ICN protocols and their use in various applications. A few of the open questions that should be addressed through experimentation with path steering include:

このパスステアリング能力の有用性と全体的な技術的品質は、上記のユースケースをどの程度うまく実現できるか、そして基盤となるICNプロトコルとそのさまざまなアプリケーションでの利用に対して性能と堅牢性の面でどのような影響を与えるかによって評価できます。 パスステアリングの実験を通じて取り組むべき未解決の問題には、次のようなものがあります。

  • How much more accurate and useful are measurements of RTT, packet loss, etc. through ping and traceroute when utilizing path steering?
  • How much is the performance and robustness of multi-path forwarding enhanced by the use of this explicit path steering capability?
  • パスステアリングを利用した場合、pingやtracerouteによるRTTやパケット損失などの測定は、どの程度正確で有用になるでしょうか？
  • この明示的なパスステアリング能力の利用によって、マルチパス転送の性能と堅牢性はどの程度向上するでしょうか？

1.3. Terminology

1.3. 用語

This document uses the general ICN terms that are defined in [RFC8793]. In addition, we define the following terms specific to path steering:

この文書は、[RFC8793]で定義されている一般的なICNの用語を使用します。 さらに、パスステアリングに固有の次の用語を定義します。

Path Discovery:
The process of sending an Interest message requesting discovery of a path and, if successful, receiving a Data message containing a path label for the path the corresponding Interest traversed.
Path Steering:
The process of sending an Interest message containing the path label of a previously discovered path so that the forwarders use that path when forwarding that particular Interest message.
Path Label:
An optional field in the packet indicating a particular path from a consumer to either a producer or a forwarder cache that can respond with the requested item. In an Interest message, the path label gets built up hop by hop as the Interest traverses a path. In a Data message, the path label carries the full path information back to the consumer for use in one or more subsequent Interest messages.
Nexthop Label:
One entry in a path label representing the next hop for the corresponding forwarder to use when a path-steered Interest message arrives at that forwarder. A sequence of Nexthop Labels constitutes a full path label.
パス発見（Path Discovery）:
パスの発見を要求するInterestメッセージを送信し、成功した場合には、対応するInterestが通過したパスのパスラベルを含むDataメッセージを受信するプロセスです。
パスステアリング（Path Steering）:
以前に発見したパスのパスラベルを含むInterestメッセージを送信し、フォワーダーがその特定のInterestメッセージを転送する際にそのパスを使用するようにするプロセスです。
パスラベル（Path Label）:
パケット内の任意のフィールドで、コンシューマーから、プロデューサーまたは要求された項目で応答できるフォワーダーのキャッシュのいずれかへの特定のパスを示します。 Interestメッセージでは、パスラベルはInterestがパスを通過するにつれてホップごとに構築されます。 Dataメッセージでは、パスラベルは完全なパス情報をコンシューマーに持ち帰り、1つ以上の後続のInterestメッセージで使用できるようにします。
ネクストホップラベル（Nexthop Label）:
パスラベル内の1つのエントリーで、パスステアリングされたInterestメッセージがフォワーダーに到着したときに、そのフォワーダーが使用するネクストホップを表します。 ネクストホップラベルの並びが、完全なパスラベルを構成します。

2. Essential Elements of ICN Path Discovery and Path Steering

2. ICNのパス発見とパスステアリングの基本要素

We elucidate the design using CCNx semantics [RFC8569] and extend its CCNx Message Formats [RFC8609] defined in Section 3.2. While the terminology is slightly different, this design can also be applied to NDN by extending its bespoke packet encodings [NDNTLV] (see Section 3.3).

CCNxのセマンティクス[RFC8569]を使用して設計を説明し、セクション3.2で定義されているCCNxのメッセージ形式[RFC8609]を拡張します。 用語は若干異なりますが、この設計はNDN独自のパケットエンコーディング[NDNTLV]を拡張することでNDNにも適用できます（Section 3.3を参照）。

2.1. Path Discovery

2.1. パス発見

End-to-end Path Discovery for CCNx is achieved by creating a path label and placing it as a hop-by-hop TLV in a CCNx Content (Data) message. The path label is constructed hop by hop as the message traverses the reverse path of transit CCNx forwarders, as shown in the first example in Figure 1. The path label is updated by adding the Nexthop Label of the interface at which the Content (Data) message has arrived to the existing path label. Eventually, when the Content (Data) message arrives at the consumer, the path label identifies the complete path the Content (Data) message took to reach the consumer. As shown in the second example in Figure 1, when multiple paths are available, subsequent Interests may be able to discover additional paths by omitting a path steering TLV and obtaining a new path label on the returning Interest.

CCNxにおけるエンドツーエンドのパス発見は、パスラベルを作成し、それをホップバイホップTLVとしてCCNxのContent（Data）メッセージに配置することで実現されます。 Figure 1の最初の例に示すように、パスラベルは、メッセージが中継するCCNxフォワーダーの復路を通過するにつれてホップごとに構築されます。 パスラベルは、Content（Data）メッセージが到着したインターフェイスのネクストホップラベルを既存のパスラベルに追加することで更新されます。 最終的に、Content（Data）メッセージがコンシューマーに到着したとき、パスラベルは、Content（Data）メッセージがコンシューマーに到達するまでにたどった完全なパスを識別します。 Figure 1の2番目の例に示すように、複数のパスが利用可能な場合、後続のInterestは、パスステアリングTLVを省略して、返ってくるInterestで新しいパスラベルを取得することで、追加のパスを発見できる場合があります。

2.2. Path Steering

2.2. パスステアリング

Due to the symmetry of forward and reverse paths in CCNx, a consumer application can reuse a discovered path label to fetch the same or a similar (e.g., next chunk, next Application Data Unit, or next pointer in a Manifest [FLIC]) Content (Data) message over the discovered network path. This path steering is achieved by processing the Interest message's path label at each transit ICN forwarder and forwarding the Interest through the specified nexthop among those identified as feasible by LNPM FIB lookup (Figure 2).

CCNxでは往路と復路のパスが対称であるため、コンシューマーアプリケーションは、発見したパスラベルを再利用して、発見したネットワークパス上で同じContent（Data）メッセージまたは類似のContent（Data）メッセージ（例: 次のチャンク、次のアプリケーションデータユニット、マニフェスト[FLIC]内の次のポインター）を取得できます。 このパスステアリングは、中継する各ICNフォワーダーでInterestメッセージのパスラベルを処理し、LNPMのFIB検索によって実行可能と識別されたネクストホップのうち、指定されたネクストホップを通じてInterestを転送することで実現されます（Figure 2）。

2.3. Handling Path Steering Errors

2.3. パスステアリングエラーの処理

Over time, the state of interfaces and the FIB on forwarders may change such that, at any particular forwarder, a given nexthop is no longer valid for a given prefix. In this case, the path label will point to a now-invalid nexthop. This is detected by failure to find a match between the decoded nexthop ID and the nexthops of the FIB entry after LNPM FIB lookup.

時間の経過とともに、フォワーダーのインターフェイスやFIBの状態が変化し、ある特定のフォワーダーにおいて、あるネクストホップが特定のプレフィックスに対してもはや有効ではなくなることがあります。 この場合、パスラベルは、現在は無効になったネクストホップを指すことになります。 これは、LNPMのFIB検索の後、デコードされたネクストホップIDとFIBエントリーのネクストホップとの間で一致が見つからないことによって検出されます。

On detecting an invalid path label, the forwarder SHOULD respond to the Interest with an InterestReturn. Therefore, we define a new invalid path label response code for the InterestReturn message and include the current path label as a hop-by-hop header. Each transit forwarder processing the InterestReturn message updates the path label in the same manner as Content (Data) messages so that the consumer receiving the InterestReturn (NACK) can easily identify which path label is no longer valid.

無効なパスラベルを検出したとき、フォワーダーはInterestに対してInterestReturnで応答すべきです（SHOULD）。 そのため、InterestReturnメッセージの新しい無効なパスラベル（invalid path label）応答コードを定義し、現在のパスラベルをホップバイホップヘッダーとして含めます。 InterestReturnメッセージを処理する中継の各フォワーダーは、Content（Data）メッセージと同じ方法でパスラベルを更新します。 これにより、InterestReturn（NACK）を受信したコンシューマーは、どのパスラベルがもはや有効でないかを容易に識別できます。

A consumer may alternatively request that a forwarder detecting the inconsistency forward the Interest by means of normal LNPM FIB lookup rather than return an error. The consumer endpoint, if it cares, can keep enough information about outstanding Interests to determine if the path label sent with the Interest fails to match the path label in the corresponding returned Content (Data) and use that information to replace stale path labels. It does so by setting the FALLBACK_MODE flag of the path label TLV in its Interest message.

代わりにコンシューマーは、不整合を検出したフォワーダーに対して、エラーを返すのではなく、通常のLNPMのFIB検索によってInterestを転送するよう要求することもできます。 コンシューマーのエンドポイントは、必要であれば、未処理のInterestに関する十分な情報を保持しておき、Interestとともに送信したパスラベルが、対応して返されたContent（Data）のパスラベルと一致しないかどうかを判断し、その情報を使用して古いパスラベルを置き換えることができます。 コンシューマーは、Interestメッセージ内のパスラベルTLVのFALLBACK_MODEフラグを設定することでこれを行います。

2.4. Interactions with Interest Aggregation

2.4. Interest集約との相互作用

If two or more Interests matching the same Pending Interest Table (PIT) entry arrive at a forwarder, under current behavior, they will be aggregated whether or not they carry identical path label TLVs. This may or may not be appropriate. For example, multiple Interests with different modes (e.g., one with DISCOVERY_MODE and one without) will get aggregated; therefore, the behavior of the forwarder might be dependent on the arrival order of those Interests. In particular:

同じ保留中Interestテーブル（Pending Interest Table、PIT）エントリーに一致する2つ以上のInterestがフォワーダーに到着した場合、現在の振る舞いでは、それらが同一のパスラベルTLVを持っているかどうかにかかわらず集約されます。 これは適切な場合もあれば、そうでない場合もあります。 たとえば、異なるモードを持つ複数のInterest（例: DISCOVERY_MODEを持つものとそうでないもの）が集約されるため、フォワーダーの振る舞いはそれらのInterestの到着順序に依存する可能性があります。 具体的には次のとおりです。

  • If the DISCOVERY_MODE Interest arrives first, it will be forwarded and potentially discover a new path, while the other Interest will be aggregated. If that Interest carried no path label, its behavior is essentially unchanged, but if it carried a path label without specifying DISCOVERY_MODE, the consumer's intent for the Interest to traverse the specified path will be ignored, and it is indeterminate if the chosen path will actually be used.
  • If the two Interests arrive in the reverse order, the DISCOVERY MODE Interest will be aggregated, and the consumer issuing it will not achieve its desire to discover a new path.
  • DISCOVERY_MODEのInterestが最初に到着した場合、それは転送されて新しいパスを発見する可能性がありますが、もう一方のInterestは集約されます。 そのInterestがパスラベルを持っていなかった場合、その振る舞いは基本的に変わりません。 しかし、DISCOVERY_MODEを指定せずにパスラベルを持っていた場合、そのInterestに指定されたパスを通過させるというコンシューマーの意図は無視され、選択されたパスが実際に使用されるかどうかは不定になります。
  • 2つのInterestが逆の順序で到着した場合、DISCOVERY MODEのInterestは集約され、それを発行したコンシューマーは新しいパスを発見するという目的を達成できません。

Multiple Interests intended to discover paths (i.e., by carrying the DISCOVERY_MODE flag defined in Section 3.1) might also be aggregated by a forwarder. This limits the ability to discover multiple paths in parallel and, instead, must be discovered incrementally in subsequent exchanges. In other words, aggregated Interests will all discover only one single path carried by one single Data packet. This has implications for management applications, like traceroute [RFC9507], which would likely perform much better if they discover paths in parallel. Hence, when employing path steering, it is RECOMMENDED that such applications craft their Interests with unique name suffixes in order to avoid being aggregated.

パスの発見を目的とした複数のInterest（つまり、Section 3.1で定義されているDISCOVERY_MODEフラグを持つもの）も、フォワーダーによって集約される可能性があります。 これにより、複数のパスを並行して発見する能力が制限され、代わりに後続の交換で段階的にパスを発見しなければならなくなります。 言い換えれば、集約されたInterestはすべて、1つのDataパケットで運ばれる1つのパスしか発見しません。 これは、パスを並行して発見できればはるかに良い性能を発揮すると考えられるtraceroute[RFC9507]のような管理アプリケーションに影響を与えます。 したがって、パスステアリングを使用する場合、そのようなアプリケーションは、集約されるのを避けるために一意の名前サフィックスを持つInterestを作成することが推奨されます（RECOMMENDED）。

While path steering still operates correctly if DISCOVERY MODE Interests are aggregated, after further experimentation, it may be appropriate to advise that a forwarder:

  • SHOULD NOT aggregate Interests carrying different path labels and
  • SHOULD apply a rate limit to DISCOVERY_MODE Interests in order to limit redundant traffic.

DISCOVERY MODEのInterestが集約されてもパスステアリングは正しく動作しますが、さらなる実験の後、フォワーダーに対して次のように助言することが適切になるかもしれません。

  • 異なるパスラベルを持つInterestを集約すべきではありません（SHOULD NOT）。
  • 冗長なトラフィックを制限するために、DISCOVERY_MODEのInterestにレート制限を適用すべきです（SHOULD）。

2.5. How to Represent the Path Label

2.5. パスラベルの表現方法

[Moiseenko2017] presents various options for how to represent a path label, with different trade-offs in flexibility, performance, and space efficiency. For this specification, we choose the polynomial encoding, which achieves reasonable space efficiency at the cost of establishing a hard limit on the length of paths that can be represented.

[Moiseenko2017]は、柔軟性、性能、空間効率においてそれぞれ異なるトレードオフを持つ、パスラベルを表現するさまざまな選択肢を提示しています。 この仕様では、多項式エンコーディング（polynomial encoding）を選択します。 これは、表現できるパスの長さに厳格な上限を設けることと引き換えに、妥当な空間効率を実現します。

The polynomial encoding utilizes a fixed-size bit array. Each transit ICN forwarder is allocated a fixed-size portion of the bit array. This design allocates 12 bits (i.e., 4095 as a generator polynomial) to each intermediate ICN forwarder. This matches the scalability of today's commercial routers that support up to 4096 physical and logical interfaces and usually do not have more than a few hundred active ones.

多項式エンコーディングは、固定サイズのビット配列を利用します。 中継する各ICNフォワーダーには、ビット配列の固定サイズの部分が割り当てられます。 この設計では、中間の各ICNフォワーダーに12ビット（つまり、生成多項式（generator polynomial）として4095）を割り当てます。 これは、最大4096個の物理インターフェイスおよび論理インターフェイスをサポートし、通常はアクティブなものが数百個を超えることのない、今日の商用ルーターのスケーラビリティーに一致します。

A forwarder that receives a Content (Data) message encodes the Nexthop Label in the next available slot and increments the label index. Conversely, a forwarder that receives an Interest message reads the current Nexthop Label and decrements the label index. Therefore, the extra computation required at each hop to forward either an Interest or Content Object message with a path label is minimized and constitutes a fairly trivial additional overhead compared to FIB lookup and other required operations.

Content（Data）メッセージを受信したフォワーダーは、次に利用可能なスロットにネクストホップラベルをエンコードし、ラベルインデックスをインクリメントします。逆に、Interestメッセージを受信したフォワーダーは、現在のネクストホップラベルを読み取り、ラベルインデックスをデクリメントします。したがって、パスラベルを持つInterestメッセージまたはContent Objectメッセージを転送するために各ホップで必要となる追加の計算は最小限に抑えられ、FIB検索やその他の必要な操作と比べればごく些細な追加のオーバーヘッドにすぎません。

This approach results in individual path label TLV instances being of fixed pre-computed size. While this places a hard upper bound on the maximum number of network hops that can be represented, this is not a significant practical problem in NDN and CCNx, since the size can be preset during Content (Data) message encoding based on the exact number of network hops traversed by the Interest message. Even long paths of 24 hops will fit in a path label bitmap of 36 bytes if the Nexthop Label is encoded in 12 bits.

このアプローチにより、個々のパスラベルTLVのインスタンスは事前に計算された固定サイズになります。 これにより、表現できるネットワークホップの最大数に厳格な上限が設けられますが、NDNとCCNxでは実用上大きな問題にはなりません。 なぜなら、Interestメッセージが通過したネットワークホップの正確な数に基づいて、Content（Data）メッセージのエンコーディング時にサイズをあらかじめ設定できるからです。 ネクストホップラベルを12ビットでエンコードする場合、24ホップの長いパスでさえ36バイトのパスラベルビットマップに収まります。

5. Security Considerations

5. セキュリティーに関する考慮事項

A path is invalidated by renumbering one or more Nexthop Labels. A malicious consumer can attempt to mount an attack by transmitting Interests with path labels that differ only in a single now-invalid Nexthop Label in order to brute-force a valid Nexthop Label. If such an attack succeeds, a malicious consumer would be capable of steering Interests over a network path that may not match the paths computed by the routing algorithm or learned adaptively by the forwarders.

パスは、1つ以上のネクストホップラベルの番号を付け直すことで無効化されます。 悪意のあるコンシューマーは、有効なネクストホップラベルを総当たり（brute-force）で見つけるために、現在は無効になった1つのネクストホップラベルだけが異なるパスラベルを持つInterestを送信して攻撃を仕掛けようとする可能性があります。 このような攻撃が成功した場合、悪意のあるコンシューマーは、ルーティングアルゴリズムによって計算されたパスやフォワーダーが適応的に学習したパスと一致しない可能性のあるネットワークパス上にInterestを誘導できるようになります。

When a label lookup fails, by default, an invalid path label InterestReturn (NACK) message is returned to the consumer. This contains a path label identical to the one included in the corresponding Interest message. Therefore, a malicious consumer can analyze the message's Hop Count field to infer which specific Nexthop Label had failed and direct an attack to influence path steering at that hop. This threat can be mitigated by the following countermeasures:

ラベル検索が失敗した場合、デフォルトでは、無効なパスラベル（invalid path label）のInterestReturn（NACK）メッセージがコンシューマーに返されます。 このメッセージには、対応するInterestメッセージに含まれていたものと同一のパスラベルが含まれています。 したがって、悪意のあるコンシューマーは、メッセージのHop Countフィールドを分析して、どの特定のネクストホップラベルが失敗したかを推測し、そのホップでのパスステアリングに影響を与えるよう攻撃を向けることができます。 この脅威は、次の対策によって緩和できます。

  • A Nexthop Label that is larger in size is harder to crack. If Nexthop Labels are not allocated in a predictable fashion by the routers, brute-forcing a 32-bit Nexthop Label requires on average O(231) Interests. However, this specification uses Nexthop Labels with much less entropy (12 bits), so depending on computational hardness is not workable.
  • An ICN forwarder can periodically update Nexthop Labels to limit the maximum lifetime of paths. It is RECOMMENDED that forwarders update path labels at least every few minutes.
  • A void Hop Count field in an invalid path label InterestReturn (NACK) message would not give out the information on which a specific Nexthop Label had failed. An attacker might need to brute-force all Nexthop Labels in all combinations. However, some useful diagnostic capability is lost by obscuring the hop count. For example, the locus of routing churn is harder to pin down through analysis of path-steered pings or traceroutes. A forwarder MAY choose to invalidate the hop count in addition to changing Nexthop Labels periodically as described above.
  • サイズが大きいネクストホップラベルほど解読が困難になります。 ルーターがネクストホップラベルを予測可能な方法で割り当てていない場合、32ビットのネクストホップラベルを総当たりで見つけるには、平均でO(231)個のInterestが必要です。 しかし、この仕様ではエントロピーがはるかに少ない（12ビット）ネクストホップラベルを使用するため、計算量的な困難さに頼ることはできません。
  • ICNフォワーダーは、ネクストホップラベルを定期的に更新して、パスの最大有効期間を制限できます。 フォワーダーは、少なくとも数分ごとにパスラベルを更新することが推奨されます（RECOMMENDED）。
  • 無効なパスラベルのInterestReturn（NACK）メッセージのHop Countフィールドを空にすれば、どの特定のネクストホップラベルが失敗したかについての情報は漏れません。 攻撃者は、すべての組み合わせですべてのネクストホップラベルを総当たりする必要があるかもしれません。 しかし、ホップカウントを隠すことで、有用な診断能力の一部が失われます。 たとえば、パスステアリングされたpingやtracerouteの分析を通じてルーティングの変動（churn）が発生している場所を特定することが難しくなります。 フォワーダーは、上で説明したようにネクストホップラベルを定期的に変更することに加えて、ホップカウントを無効化することを選択してもよいです（MAY）。

Because ICN forwarders maintain per-face state and forwarding state for Interest messages, state inflation attacks are a general concern. The addition of path steering capabilities in Interest and Data messages does not, however, constitute a meaningful increase in susceptibility to such attacks. This is because:

ICNフォワーダーはInterestメッセージに対してフェイスごとの状態と転送状態を維持するため、状態膨張攻撃は一般的な懸念事項です。 しかし、InterestメッセージとDataメッセージにパスステアリング能力を追加しても、そのような攻撃に対する脆弱性が有意に増加するわけではありません。 その理由は次のとおりです。

  • The labels that identify each forwarding face is state O(number of faces) and constitutes a small increase to the existing state needed to represent a face.
  • Interest message data is placed in the PIT. The path steering header does, in fact, inflate the size of the Interest message and, hence, the PIT state but not by an amount that is a concern. The forwarder needs to protect against state inflation attacks on the PIT in general, and an attacker can mount one just as or more easily by issuing Interests with long names and/or by including Interest payload data.
  • 各転送フェイスを識別するラベルは、O(フェイス数)の状態であり、フェイスを表現するのに必要な既存の状態に対してわずかな増加にすぎません。
  • InterestメッセージのデータはPITに置かれます。 パスステアリングヘッダーは実際にInterestメッセージのサイズ、ひいてはPITの状態を膨張させますが、懸念となるほどの量ではありません。 フォワーダーは一般にPITに対する状態膨張攻撃から防御する必要があり、攻撃者は、長い名前を持つInterestを発行したり、Interestのペイロードデータを含めたりすることによって、同じくらい、あるいはより容易にそのような攻撃を仕掛けることができます。

ICN protocols can be susceptible to a variety of cache poisoning attacks, where a colluding consumer and producer arrange for bogus content (with either invalid or inappropriate signatures) to populate forwarder caches. These are generally confined to on-path attacks. It is also theoretically possible to launch a similar attack without a cooperating producer such that the caches of on-path routers become poisoned with the content from off-path routers (i.e., physical connectivity but no route in a FIB for a given prefix). We estimate that, without any prior knowledge of the network topology, the complexity of this type of attack is in the ballpark of Breadth-First-Search and Depth-First-Search algorithms with the additional burden of transmitting 231 Interests in order to crack a Nexthop Label on each hop. A relatively short periodic update of Nexthop Labels, together with heuristics implemented in the ICN forwarder to foil label scans, may successfully mitigate this type of attack.

ICNプロトコルは、さまざまなキャッシュポイズニング攻撃の影響を受ける可能性があります。 これは、共謀するコンシューマーとプロデューサーが、偽のコンテンツ（無効な署名または不適切な署名を持つもの）をフォワーダーのキャッシュに格納させるよう仕組む攻撃です。 これらは一般に経路上の攻撃に限定されます。 理論的には、協力するプロデューサーなしで同様の攻撃を仕掛けることも可能であり、その場合、経路上のルーターのキャッシュが経路外のルーター（つまり、物理的な接続性はあるが、特定のプレフィックスに対するFIB内の経路がないルーター）からのコンテンツで汚染されます。 ネットワークトポロジーに関する事前の知識がない場合、この種の攻撃の複雑さは、幅優先探索アルゴリズムや深さ優先探索アルゴリズムとほぼ同程度であり、さらに各ホップでネクストホップラベルを解読するために231個のInterestを送信するという負担が加わると見積もっています。 ネクストホップラベルを比較的短い周期で更新し、それと併せてラベルスキャンを阻止するためのヒューリスティックをICNフォワーダーに実装することで、この種の攻撃をうまく緩和できる可能性があります。

5.1. Cryptographic Protection of a Path Label

5.1. パスラベルの暗号学的保護

If the countermeasures listed above do not provide sufficient protection against malicious mis-steering of Interests, the path label can be made opaque to the consumer endpoint via hop-by-hop symmetric cryptography applied to the path labels (Figure 6). This method is viable due to the symmetry of forward and reverse paths in CCNx and NDN architectures combined with ICN path steering requiring only reads and writes of the topmost Nexthop Label (i.e., active Nexthop Label) in the path label. This way, a path-steering-capable ICN forwarder receiving a Content (Data) message encrypts the current path label with its own non-shared symmetric key prior to adding a new Nexthop Label to the path label. The Content (Data) message is forwarded downstream with an unencrypted topmost (i.e., active) Nexthop Label and the remaining encrypted content of the path label. As a result, a consumer endpoint receives a Content (Data) message with a unique path label exposing only the topmost Nexthop Label as cleartext. A path steering forwarder receiving an Interest message performs label lookup using the topmost Nexthop Label, decrypts the path label with its own non-shared symmetric key, and forwards the message upstream.

上記の対策が、悪意によるInterestの誤誘導に対して十分な保護を提供しない場合、パスラベルに適用するホップバイホップの対称暗号によって、パスラベルをコンシューマーのエンドポイントに対して不透明にできます（Figure 6）。 この方法が実行可能なのは、CCNxおよびNDNのアーキテクチャーにおいて往路と復路のパスが対称であることと、ICNのパスステアリングではパスラベル内の最上位のネクストホップラベル（つまり、アクティブなネクストホップラベル）の読み書きしか必要としないことが組み合わさっているからです。 この方法では、Content（Data）メッセージを受信したパスステアリング対応のICNフォワーダーは、新しいネクストホップラベルをパスラベルに追加する前に、現在のパスラベルを自身の共有されていない対称鍵で暗号化します。 Content（Data）メッセージは、暗号化されていない最上位の（つまり、アクティブな）ネクストホップラベルと、パスラベルの残りの暗号化された内容とともに下流に転送されます。 その結果、コンシューマーのエンドポイントは、最上位のネクストホップラベルだけを平文として公開する一意のパスラベルを持つContent（Data）メッセージを受信します。 Interestメッセージを受信したパスステアリングのフォワーダーは、最上位のネクストホップラベルを使用してラベル検索を実行し、自身の共有されていない対称鍵でパスラベルを復号して、メッセージを上流に転送します。

Cryptographic protection of a path label does not require any key negotiation among ICN forwarders and is no more expensive than Media Access Control Security (MACsec) or IPsec. It is also quite possible that strict hop-by-hop path label encryption is not necessary and path label encryption only on the border routers of the trusted administrative or routing domains may suffice.

パスラベルの暗号学的保護は、ICNフォワーダー間での鍵のネゴシエーションを一切必要とせず、メディアアクセス制御セキュリティー（Media Access Control Security、MACsec）やIPsecよりコストが高くなることはありません。また、厳密なホップバイホップのパスラベル暗号化は必要なく、信頼された管理ドメインまたはルーティングドメインの境界ルーターでのみパスラベルを暗号化すれば十分である可能性も十分にあります。
