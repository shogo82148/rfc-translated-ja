RFC 1670

Input to IPng Engineering Considerations

RFC 1670

IPngの技術的な考慮事項への意見

Abstract

概要

This document was submitted to the IETF IPng area in response to RFC 1550. Publication of this document does not imply acceptance by the IPng area of any ideas expressed within. Comments should be submitted to the big-internet@munnari.oz.au mailing list.

この文書は、RFC 1550への応答として、IETFのIPngエリアに提出されたものです。この文書の公開は、ここで述べられているいかなる考えについても、IPngエリアが受け入れたことを意味するものではありません。コメントはbig-internet@munnari.oz.auメーリングリストに送ってください。

Status of This Memo

このメモのステータス

This memo provides information for the Internet community. This memo does not specify an Internet standard of any kind. Distribution of this memo is unlimited.

このメモは、インターネットコミュニティーに情報を提供するものです。いかなる種類のインターネット標準も規定するものではありません。このメモの配布は無制限です。

Summary

要約

This white paper expresses some personal opinions on IPng engineering considerations, based on experience with DECnet Phase V transition. It suggests breaking down the IPng decisions and transition tasks into smaller parts so they can be tackled early by the relevant experts.

このホワイトペーパーは、DECnet Phase Vへの移行の経験に基づき、IPngの技術的な考慮事項についていくつかの個人的な意見を述べるものです。関係する専門家が早い段階で取り組めるように、IPngに関する決定と移行の作業を小さな部分に分割することを提案します。

Timescales

スケジュール

In order to allow key decisions to be taken early, I would like to see IPng decisions and timescales broken down into into smaller parts, for example:

重要な決定を早い段階で下せるように、IPngに関する決定とスケジュールを、たとえば次のような小さな部分に分割してほしいと考えています。

  • address structure and allocation mechanism
  • name service changes
  • host software and programming interface changes
  • routing protocol changes
  • アドレスの構造と割り当ての仕組み
  • ネームサービスの変更
  • ホストソフトウェアとプログラミングインターフェイスの変更
  • ルーティングプロトコルの変更

Although interrelated, not all details need to be defined by the same date. Identify which decisions will be hard to change and which can be allowed to evolve. All changes should be worked on in parallel, but the above list indicates a feeling for urgency of a decision. Our experience has been that administrative changes (as may be required for addressing changes) need the greatest elapse time for implementation, whereas routing protocol changes need the least.

互いに関連してはいますが、すべての詳細を同じ期日までに定める必要はありません。どの決定が後から変えにくく、どの決定は発展させていってよいのかを見極めてください。すべての変更は並行して進めるべきですが、上記の一覧は決定の緊急度の感覚を示しています。私たちの経験では、（アドレスの変更に必要となるような）管理上の変更は実施までに最も長い時間を要し、ルーティングプロトコルの変更は最も短い時間で済みます。

I would like to see an early decision on address structure and enough information for service managers to start planning their transition. Some hosts will never be upgraded and will need to be phased out or configured with reduced connectivity. A lead time of 10 years (or more) will help to take good long term technical decisions and ease financial and organisational constraints.

アドレスの構造について早い段階で決定を下し、サービス管理者が移行の計画を始められるだけの情報を提供してほしいと考えています。一部のホストは決してアップグレードされず、段階的に廃止するか、接続性を制限して構成する必要があるでしょう。10年（またはそれ以上）のリードタイムがあれば、長期的に見て優れた技術的決定を下しやすくなり、財務上および組織上の制約も緩和されるでしょう。

Transition and deployment

移行と展開

Transition requires intimate knowledge of the environment (financial, political as well as technical). The task needs to be broken down so that service managers close to their clients can take decisions and make them happen.

移行には、（技術面だけでなく、財務面や政治面も含めた）環境についての深い知識が必要です。顧客に近いサービス管理者が決定を下して実行に移せるように、作業を分割する必要があります。

Let the service managers adapt the solutions for their environment by providing them with a transition toolbox and scenarios of their uses based on real examples. Clearly state the merits and limitations of different transition strategies.

移行のためのツールボックスと、実例に基づくその使用シナリオを提供して、サービス管理者が自分の環境に合わせて解決策を適用できるようにしてください。さまざまな移行戦略の利点と限界を明確に述べてください。

Provide for transition autonomy. Let systems and sites transition at different times, as convenient for them.

移行の自律性を確保してください。システムやサイトがそれぞれ都合のよい時期に移行できるようにしてください。

Identify what software needs to be changed and keep an up-to-date list.

変更が必要なソフトウェアを特定し、その一覧を最新に保ってください。

Identify what is essential to have in place so that service managers can transition at their own pace.

サービス管理者が自分のペースで移行できるようにするために、何を用意しておくことが不可欠なのかを特定してください。

Allow for a feedback loop to improve software based on experience.

経験に基づいてソフトウェアを改善するためのフィードバックループを設けてください。

Configuration, Administration, Operation

設定、管理、運用

We run IP on a wide range of equipment and operating systems. We need an easy way to (re-)configure all our IP capable systems. The systems need to be sent their IP parameters (e.g., their address, address of their default router, address of their local name servers) and we need to obtain data from the system (e.g., contact information for owner, location and name of system). We also need an easy way to update DNS.

私たちは、多種多様な機器とオペレーティングシステムでIPを運用しています。IPに対応したすべてのシステムを簡単に設定（および再設定）する方法が必要です。システムにはIPパラメーター（たとえば、自身のアドレス、デフォルトルーターのアドレス、ローカルのネームサーバーのアドレス）を送る必要があり、システムからはデータ（たとえば、所有者の連絡先、システムの設置場所と名前）を取得する必要があります。DNSを簡単に更新する方法も必要です。

In our environment systems are regularly moved between buildings and we therefore find the tight coupling of IP address to physical subnet over restrictive. Automatic configuration could help overcome this.

私たちの環境ではシステムが建物の間で頻繁に移動されるので、IPアドレスが物理的なサブネットと強く結びついていることは制約が大きすぎると感じています。自動設定はこれを克服する助けになるでしょう。

We would like to efficiently load balance users of various IP based services (e.g., telnet, ftp, locally written applications) across a number of systems.

さまざまなIPベースのサービス（たとえば、telnet、ftp、独自に作成したアプリケーション）のユーザーを、複数のシステムに効率よく負荷分散したいと考えています。

The ability to break down addresses and routing into several levels of hierarchy is important to allow the delegation of network management into subdomains. As the network grows so does the desire to increase the number of levels of hierarchy.

ネットワーク管理をサブドメインに委任できるようにするには、アドレスとルーティングを複数の階層レベルに分割できることが重要です。ネットワークが大きくなるにつれて、階層レベルの数を増やしたいという要望も大きくなります。
