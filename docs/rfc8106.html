RFC 8106

IPv6 Router Advertisement Options for DNS Configuration

RFC 8106

DNS設定のためのIPv6ルーター広告オプション

Abstract

概要

This document specifies IPv6 Router Advertisement (RA) options (called "DNS RA options") to allow IPv6 routers to advertise a list of DNS Recursive Server Addresses and a DNS Search List to IPv6 hosts.

この文書は、IPv6ルーターがDNS再帰サーバーアドレスのリストとDNS検索リストをIPv6ホストに広告できるようにするためのIPv6ルーター広告（RA）オプション（「DNS RAオプション」と呼びます）を規定します。

This document, which obsoletes RFC 6106, defines a higher default value of the lifetime of the DNS RA options to reduce the likelihood of expiry of the options on links with a relatively high rate of packet loss.

RFC 6106を廃止するこの文書は、パケットロス率が比較的高いリンク上でオプションが期限切れになる可能性を減らすために、DNS RAオプションの有効期間のデフォルト値をより大きく定めます。

1. Introduction

1. はじめに

The purpose of this document is to standardize IPv6 Router Advertisement (RA) options (DNS RA options) for DNS Recursive Server Addresses used for DNS name resolution in IPv6 hosts, and also for a DNS Search List (DNSSL) of domain suffixes.

この文書の目的は、IPv6ホストでのDNS名前解決に使用するDNS再帰サーバーアドレスと、ドメインサフィックスのDNS検索リスト（DNS Search List、DNSSL）のためのIPv6ルーター広告（Router Advertisement、RA）オプション（DNS RAオプション）を標準化することです。

IPv6 Neighbor Discovery (ND) and IPv6 Stateless Address Autoconfiguration (SLAAC) provide ways to configure either fixed or mobile nodes with one or more IPv6 addresses, default routers, and some other parameters [RFC4861] [RFC4862].

IPv6近隣探索（Neighbor Discovery、ND）とIPv6ステートレスアドレス自動設定（Stateless Address Autoconfiguration、SLAAC）は、固定ノードまたはモバイルノードに、1つ以上のIPv6アドレス、デフォルトルーター、およびその他のいくつかのパラメーターを設定する方法を提供します[RFC4861] [RFC4862]。

It is infeasible to manually configure nomadic hosts each time they connect to a different network. While a one-time static configuration is possible, it is generally not desirable on general-purpose hosts such as laptops. For instance, locally defined namespaces would not be available to the host if it were to run its own recursive name server directly connected to the global DNS.

移動するホスト（nomadic host）を、別のネットワークに接続するたびに手動で設定することは現実的ではありません。一度限りの静的な設定は可能ですが、ラップトップのような汎用ホストでは一般に望ましくありません。たとえば、ホストがグローバルDNSに直接接続する独自の再帰ネームサーバーを実行したとすると、そのホストはローカルに定義された名前空間を利用できなくなります。

The DNS information can also be provided through DHCPv6 [RFC3315] [RFC3736] [RFC3646]. However, access to DNS is a fundamental requirement for almost all hosts, so IPv6 SLAAC cannot stand on its own as an alternative deployment model in any practical network without any support for DNS configuration.

DNS情報は、DHCPv6[RFC3315] [RFC3736] [RFC3646]を通じて提供することもできます。しかし、DNSへのアクセスはほぼすべてのホストにとって基本的な要件であるため、DNS設定をまったくサポートしなければ、実用的なネットワークにおいてIPv6 SLAACは代替の展開モデルとして単独では成り立ちません。

These issues are not pressing in dual-stack networks as long as a DNS server is available on the IPv4 side, but they become more critical with the deployment of IPv6-only networks. As a result, this document defines a mechanism based on DNS RA options to allow IPv6 hosts to perform automatic DNS configuration.

IPv4側でDNSサーバーが利用できる限り、デュアルスタックネットワークではこれらの問題は差し迫ったものではありませんが、IPv6のみのネットワークの展開に伴って、より深刻になります。そこで、この文書では、IPv6ホストが自動的なDNS設定を行えるようにする、DNS RAオプションに基づくメカニズムを定義します。

1.1. Applicability Statements

1.1. 適用範囲に関する記述

RA-based DNS configuration is a useful alternative in networks where an IPv6 host's address is autoconfigured through IPv6 SLAAC and where either (i) there is no DHCPv6 infrastructure at all or (ii) some hosts do not have a DHCPv6 client. The intention is to enable the full configuration of basic networking information for hosts without requiring DHCPv6. However, for networks that need to distribute additional information, DHCPv6 is likely to be employed. In these networks, RA-based DNS configuration may not be needed.

RAベースのDNS設定は、IPv6ホストのアドレスがIPv6 SLAACによって自動設定され、かつ、(i) DHCPv6インフラストラクチャーがまったくないか、(ii) 一部のホストがDHCPv6クライアントを持たないネットワークにおいて、有用な代替手段です。その意図は、DHCPv6を必要とせずに、ホストに対する基本的なネットワーク情報の完全な設定を可能にすることです。ただし、追加の情報を配布する必要があるネットワークでは、DHCPv6が使用される可能性が高いです。そのようなネットワークでは、RAベースのDNS設定は必要ないかもしれません。

RA-based DNS configuration allows an IPv6 host to acquire the DNS configuration (i.e., DNS Recursive Server Addresses and the DNSSL) for the link(s) to which the host is connected. Furthermore, the host learns this DNS configuration from the same RA message that provides configuration information for the link.

RAベースのDNS設定により、IPv6ホストは、自身が接続しているリンクのためのDNS設定（すなわち、DNS再帰サーバーアドレスとDNSSL）を取得できます。さらに、ホストは、そのリンクの設定情報を提供するのと同じRAメッセージから、このDNS設定を知ることができます。

The advantages and disadvantages of the RA-based approach are discussed in [RFC4339] along with other approaches, such as the DHCP and well-known anycast address approaches.

RAベースのアプローチの利点と欠点は、DHCPやウェルノウンエニーキャストアドレスによるアプローチなどのほかのアプローチとともに、[RFC4339]で議論されています。

1.2. Coexistence of RA Options and DHCP Options for DNS Configuration

1.2. DNS設定のためのRAオプションとDHCPオプションの共存

Two protocols exist to configure the DNS information on a host: the RA options specified in this document and the DHCPv6 options specified in [RFC3646]. They can be used together. The rules governing the decision to use stateful configuration mechanisms are specified in [RFC4861]. Hosts conforming to this specification MUST extract DNS information from RA messages, unless static DNS configuration has been specified by the user. If there is DNS information available from multiple RAs and/or from DHCP, the host MUST maintain an ordered list of this information as specified in Section 5.3.1.

ホスト上のDNS情報を設定するためのプロトコルは2つあります。この文書で規定するRAオプションと、[RFC3646]で規定されているDHCPv6オプションです。これらは併用できます。ステートフルな設定メカニズムを使用するかどうかの決定を左右する規則は、[RFC4861]で規定されています。この仕様に準拠するホストは、ユーザーによって静的なDNS設定が指定されていない限り、RAメッセージからDNS情報を抽出しなければなりません（MUST）。複数のRAから、またはDHCPから（あるいはその両方から）利用可能なDNS情報がある場合、ホストは、セクション5.3.1で規定するとおりに、これらの情報の順序付きリストを維持しなければなりません（MUST）。

3. Terminology

3. 用語

This document uses the terminology defined in [RFC4861] and [RFC4862]. In addition, six new terms are defined below:

この文書では、[RFC4861]と[RFC4862]で定義されている用語を使用します。さらに、次の6つの新しい用語を定義します。

  • Recursive DNS Server (RDNSS): A server that provides a recursive DNS resolution service for translating domain names into IP addresses or resolving PTR records as defined in [RFC1034] and [RFC1035].
  • RDNSS Option: An IPv6 RA option to deliver the RDNSS information to IPv6 hosts [RFC4861].
  • DNS Search List (DNSSL): The list of DNS suffix domain names used by IPv6 hosts when they perform DNS query searches for short, unqualified domain names.
  • DNSSL Option: An IPv6 RA option to deliver the DNSSL information to IPv6 hosts.
  • DNS Repository: Two data structures for managing DNS configuration information in the IPv6 protocol stack, in addition to the Neighbor Cache and Destination Cache for Neighbor Discovery [RFC4861]. The first data structure is the DNS Server List for RDNSS addresses, and the second is the DNSSL for DNS search domain names.
  • Resolver Repository: Configuration repository with RDNSS addresses and a DNSSL that a DNS resolver on the host uses for DNS name resolution -- for example, the UNIX resolver file (i.e., /etc/resolv.conf) and the Windows registry.
  • 再帰DNSサーバー（Recursive DNS Server、RDNSS）: [RFC1034]と[RFC1035]で定義されているように、ドメイン名をIPアドレスに変換したり、PTRレコードを解決したりするための再帰的なDNS解決サービスを提供するサーバー。
  • RDNSSオプション: RDNSS情報をIPv6ホストに配送するためのIPv6 RAオプション[RFC4861]。
  • DNS検索リスト（DNS Search List、DNSSL）: 短い、完全修飾されていないドメイン名についてDNSクエリーによる検索を行う際に、IPv6ホストが使用するDNSサフィックスのドメイン名のリスト。
  • DNSSLオプション: DNSSL情報をIPv6ホストに配送するためのIPv6 RAオプション。
  • DNSリポジトリー（DNS Repository）: 近隣探索のための近隣キャッシュと宛先キャッシュ[RFC4861]に加えて、IPv6プロトコルスタック内でDNS設定情報を管理するための2つのデータ構造。1つ目のデータ構造はRDNSSアドレスのためのDNSサーバーリストであり、2つ目はDNS検索ドメイン名のためのDNSSLです。
  • リゾルバーリポジトリー（Resolver Repository）: ホスト上のDNSリゾルバーがDNS名前解決に使用する、RDNSSアドレスとDNSSLを保持する設定リポジトリー。たとえば、UNIXのリゾルバーファイル（すなわち、/etc/resolv.conf）やWindowsのレジストリーです。

4. Overview

4. 概要

This document standardizes an ND option called the "RDNSS option", which contains the addresses of RDNSSes. This document also standardizes an ND option called the "DNSSL option", which contains the DNSSL. This is to maintain parity with the DHCPv6 options and to ensure that there is necessary functionality to determine the search domains.

この文書では、RDNSSのアドレスを含む「RDNSSオプション」と呼ばれるNDオプションを標準化します。また、この文書では、DNSSLを含む「DNSSLオプション」と呼ばれるNDオプションも標準化します。これは、DHCPv6オプションとの同等性を保ち、検索ドメインを決定するために必要な機能が確実に存在するようにするためです。

The existing ND message (i.e., RA) is used to carry this information. An IPv6 host can configure the IPv6 addresses of one or more RDNSSes via RA messages. Through the RDNSS and DNSSL options, along with the Prefix Information option based on the ND protocol [RFC4861] [RFC4862], an IPv6 host can perform the network configuration of its IPv6 address and the DNS information simultaneously without needing DHCPv6 for the DNS configuration. The RA options for RDNSS and DNSSL can be used on networks that support the use of ND.

この情報を運ぶために、既存のNDメッセージ（すなわち、RA）を使用します。IPv6ホストは、RAメッセージを介して、1つ以上のRDNSSのIPv6アドレスを設定できます。NDプロトコル[RFC4861] [RFC4862]に基づくプレフィックス情報オプションに加えてRDNSSオプションとDNSSLオプションを用いることで、IPv6ホストは、DNS設定のためにDHCPv6を必要とすることなく、自身のIPv6アドレスとDNS情報のネットワーク設定を同時に行えます。RDNSSとDNSSLのためのRAオプションは、NDの使用をサポートするネットワークで使用できます。

This approach requires manual configuration or automatic mechanisms (e.g., DHCPv6 or vendor-proprietary configuration mechanisms) to configure the DNS information in routers sending the advertisements. The automatic configuration of RDNSS addresses and a DNSSL in routers is out of scope for this document.

このアプローチでは、広告を送信するルーターにDNS情報を設定するために、手動設定または自動的なメカニズム（たとえば、DHCPv6やベンダー独自の設定メカニズム）が必要です。ルーターにおけるRDNSSアドレスとDNSSLの自動設定は、この文書の範囲外です。

5. Neighbor Discovery Extension

5. 近隣探索の拡張

The IPv6 DNS configuration mechanism described in this document needs two ND options in Neighbor Discovery: (i) the RDNSS option and (ii) the DNSSL option.

この文書で説明するIPv6 DNS設定メカニズムには、近隣探索における2つのNDオプション、すなわち(i) RDNSSオプションと(ii) DNSSLオプションが必要です。

5.1. Recursive DNS Server Option

5.1. Recursive DNS Serverオプション

The RDNSS option contains one or more IPv6 addresses of RDNSSes. All of the addresses share the same Lifetime value. If it is desirable to have different Lifetime values, multiple RDNSS options can be used. Figure 1 shows the format of the RDNSS option.

RDNSSオプションには、RDNSSの1つ以上のIPv6アドレスが含まれます。すべてのアドレスは同じLifetime値を共有します。異なるLifetime値を持たせることが望ましい場合は、複数のRDNSSオプションを使用できます。図1にRDNSSオプションの形式を示します。

Fields:

フィールド:

Type
8-bit identifier of the RDNSS option type as assigned by IANA: 25
Length
8-bit unsigned integer. The length of the option (including the Type and Length fields) is in units of 8 octets. The minimum value is 3 if one IPv6 address is contained in the option. Every additional RDNSS address increases the length by 2. The Length field is used by the receiver to determine the number of IPv6 addresses in the option.
Lifetime
32-bit unsigned integer. The maximum time in seconds (relative to the time the packet is received) over which these RDNSS addresses MAY be used for name resolution. The value of Lifetime SHOULD by default be at least 3 * MaxRtrAdvInterval, where MaxRtrAdvInterval is the maximum RA interval as defined in [RFC4861]. A value of all one bits (0xffffffff) represents infinity. A value of zero means that the RDNSS addresses MUST no longer be used.
Addresses of IPv6 Recursive DNS Servers
One or more 128-bit IPv6 addresses of the RDNSSes. The number of addresses is determined by the Length field. That is, the number of addresses is equal to (Length - 1) / 2.
Type
IANAによって割り当てられた、RDNSSオプションタイプの8ビットの識別子: 25
Length
8ビットの符号なし整数。オプションの長さ（TypeフィールドとLengthフィールドを含む）を8オクテット単位で表します。オプションに1つのIPv6アドレスが含まれる場合の最小値は3です。RDNSSアドレスが1つ追加されるごとに、長さは2ずつ増えます。Lengthフィールドは、受信者がオプション内のIPv6アドレスの数を判断するために使用します。
Lifetime
32ビットの符号なし整数。（パケットを受信した時刻を基準とした）秒単位の最大時間で、この時間の間、これらのRDNSSアドレスを名前解決に使用してもよいです（MAY）。Lifetimeの値は、デフォルトで3 * MaxRtrAdvInterval以上であるべきです（SHOULD）。ここで、MaxRtrAdvIntervalは[RFC4861]で定義されている最大RA間隔です。すべてのビットが1の値（0xffffffff）は無限大を表します。値が0の場合、そのRDNSSアドレスをそれ以降使用しないようにしなければなりません（MUST）。
Addresses of IPv6 Recursive DNS Servers
RDNSSの1つ以上の128ビットIPv6アドレス。アドレスの数はLengthフィールドによって決まります。すなわち、アドレスの数は(Length - 1) / 2に等しくなります。
Note:

The addresses for RDNSSes in the RDNSS option MAY be link-local addresses. Such link-local addresses SHOULD be registered in the Resolver Repository along with the corresponding link zone indices of the links that receive the RDNSS option(s) for them. The link-local addresses MAY be represented in the Resolver Repository with their link zone indices in the textual format for scoped addresses as described in [RFC4007]. When a resolver sends a DNS query message to an RDNSS identified by a link-local address, it MUST use the corresponding link.

The rationale of the default value of the Lifetime field is as follows. The Router Lifetime field, set by AdvDefaultLifetime, has the default of 3 * MaxRtrAdvInterval as specified in [RFC4861], so such a default or a larger default can allow for the reliability of DNS options even under the loss of RAs on links with a relatively high rate of packet loss. Note that the ratio of AdvDefaultLifetime to MaxRtrAdvInterval is the number of unsolicited multicast RAs sent by the router. Since the DNS option entries can survive for at most three consecutive losses of RAs containing DNS options, the default value of the Lifetime lets the DNS option entries be resilient to packet-loss environments.

注:

Lifetimeフィールドのデフォルト値の根拠は次のとおりです。AdvDefaultLifetimeによって設定されるRouter Lifetimeフィールドは、[RFC4861]で規定されているように3 * MaxRtrAdvIntervalのデフォルト値を持つため、そのようなデフォルト値、またはそれより大きなデフォルト値にすれば、パケットロス率が比較的高いリンク上でRAが失われる状況でも、DNSオプションの信頼性を確保できます。なお、AdvDefaultLifetimeとMaxRtrAdvIntervalの比は、ルーターが送信する非請求マルチキャストRAの数です。DNSオプションのエントリーは、DNSオプションを含むRAが最大3回連続で失われても生き残ることができるため、このLifetimeのデフォルト値によって、DNSオプションのエントリーはパケットロスのある環境に対して耐性を持ちます。

5.3. DNS Configuration Procedure

5.3. DNS設定の手順

The procedure for DNS configuration through the RDNSS and DNSSL options is the same as it is with any other ND option [RFC4861].

RDNSSオプションとDNSSLオプションによるDNS設定の手順は、ほかのNDオプションの場合と同じです[RFC4861]。

5.3.1. Procedure in IPv6 Hosts

5.3.1. IPv6ホストにおける手順

When an IPv6 host receives DNS options (i.e., RDNSS and DNSSL options) through RA messages, it processes the options as follows:

IPv6ホストは、RAメッセージを通じてDNSオプション（すなわち、RDNSSオプションとDNSSLオプション）を受信すると、そのオプションを次のように処理します。

  • The validity of DNS options is checked with the Length field; that is, the value of the Length field in the RDNSS option is greater than or equal to the minimum value (3) and satisfies the requirement that (Length - 1) % 2 == 0. The value of the Length field in the DNSSL option is greater than or equal to the minimum value (2). Also, the validity of the RDNSS option is checked with the "Addresses of IPv6 Recursive DNS Servers" field; that is, the addresses should be unicast addresses.
  • If the DNS options are valid, the host SHOULD copy the values of the options into the DNS Repository and the Resolver Repository in order. Otherwise, the host MUST discard the options. Refer to Section 6 for the detailed procedure.
  • DNSオプションの妥当性をLengthフィールドで確認します。すなわち、RDNSSオプションのLengthフィールドの値が最小値（3）以上であり、かつ(Length - 1) % 2 == 0という要件を満たすことを確認します。DNSSLオプションのLengthフィールドの値は最小値（2）以上です。また、RDNSSオプションの妥当性を「Addresses of IPv6 Recursive DNS Servers」フィールドで確認します。すなわち、アドレスはユニキャストアドレスであるべきです。
  • DNSオプションが妥当であれば、ホストはオプションの値をDNSリポジトリーとリゾルバーリポジトリーに順にコピーすべきです（SHOULD）。そうでなければ、ホストはそのオプションを破棄しなければなりません（MUST）。詳細な手順については、セクション6を参照してください。

In the case where the DNS information of RDNSS and DNSSL can be obtained from multiple sources, such as RAs and DHCP, the IPv6 host SHOULD keep some DNS options from all sources. Unless explicitly specified for the discovery mechanism, the exact number of addresses and domain names to keep is a matter of local policy and implementation choice as a local configuration option. However, in the case of multiple sources, the ability to store a total of at least three RDNSS addresses (or DNSSL domain names) from the multiple sources is RECOMMENDED. The DNS options from RAs and DHCP SHOULD be stored in the DNS Repository and Resolver Repository so that information from DHCP appears there first and therefore takes precedence. Thus, the DNS information from DHCP takes precedence over that from RAs for DNS queries. On the other hand, for DNS options announced by RAs, if some RAs use the Secure Neighbor Discovery (SEND) protocol [RFC3971] for RA security, they MUST be preferred over those that do not use SEND. Also, DNS options announced by RAs via SEND MUST be preferred over those announced by unauthenticated DHCP [RFC3118]. Refer to Section 7 for a detailed discussion of SEND for DNS RA options.

RDNSSとDNSSLのDNS情報をRAやDHCPなどの複数の情報源から取得できる場合、IPv6ホストは、すべての情報源から、いくつかのDNSオプションを保持すべきです（SHOULD）。探索メカニズムについて明示的に規定されていない限り、保持するアドレスとドメイン名の正確な数は、ローカルポリシーの問題であり、ローカルな設定オプションとしての実装上の選択の問題です。ただし、複数の情報源がある場合には、複数の情報源から合計で少なくとも3つのRDNSSアドレス（またはDNSSLドメイン名）を格納できることが推奨されます（RECOMMENDED）。RAとDHCPからのDNSオプションは、DHCPからの情報が先頭に現れて優先されるように、DNSリポジトリーとリゾルバーリポジトリーに格納されるべきです（SHOULD）。したがって、DNSクエリーでは、DHCPからのDNS情報がRAからのDNS情報よりも優先されます。一方、RAによって告知されるDNSオプションについて、一部のRAがRAのセキュリティーのためにSecure Neighbor Discovery（SEND）プロトコル[RFC3971]を使用している場合、それらのRAは、SENDを使用していないRAよりも優先されなければなりません（MUST）。また、SENDを介したRAによって告知されるDNSオプションは、認証されていないDHCP[RFC3118]によって告知されるDNSオプションよりも優先されなければなりません（MUST）。DNS RAオプションのためのSENDの詳細な議論については、セクション7を参照してください。

5.3.2. Warnings for DNS Options Configuration

5.3.2. DNSオプションの設定に関する警告

There are two warnings for DNS options configuration: (i) warning for multiple sources of DNS options and (ii) warning for multiple network interfaces. First, in the case of multiple sources for DNS options (e.g., RAs and DHCP), an IPv6 host can configure its IP addresses from these sources. In this case, it is not possible to control how the host uses DNS information and what source addresses it uses to send DNS queries. As a result, configurations where different information is provided by different mechanisms for autoconfiguration may lead to problems. Therefore, the network administrator needs to carefully configure different DNS options in the multiple mechanisms for autoconfiguration in order to minimize the impact of such problems [DHCPv6-SLAAC].

DNSオプションの設定に関する警告は2つあります。(i) DNSオプションの情報源が複数ある場合の警告と、(ii) ネットワークインターフェイスが複数ある場合の警告です。1つ目として、DNSオプションの情報源が複数ある場合（たとえば、RAとDHCP）、IPv6ホストはそれらの情報源から自身のIPアドレスを設定できます。この場合、ホストがDNS情報をどのように使用するか、またDNSクエリーを送信するためにどの送信元アドレスを使用するかを制御することはできません。その結果、異なる自動設定メカニズムによって異なる情報が提供される構成では、問題が生じる可能性があります。そのため、ネットワーク管理者は、そのような問題の影響を最小限に抑えるために、複数の自動設定メカニズムにおいて異なるDNSオプションを慎重に設定する必要があります[DHCPv6-SLAAC]。

Second, if different DNS information is provided on different network interfaces, this can lead to inconsistent behavior. The IETF worked on solving this problem for both DNS and other information obtained from multiple interfaces [RFC6418] [RFC6419] and standardized a DHCP-based solution for RDNSS selection for multi-interfaced nodes as described in [RFC6731].

2つ目として、異なるネットワークインターフェイス上で異なるDNS情報が提供されると、一貫性のない動作につながる可能性があります。IETFは、複数のインターフェイスから得られるDNSとその他の情報の両方について、この問題の解決に取り組み[RFC6418] [RFC6419]、[RFC6731]で説明されているように、マルチインターフェイスノードにおけるRDNSS選択のためのDHCPベースの解決策を標準化しました。

6.1. DNS Repository Management

6.1. DNSリポジトリーの管理

For DNS repository management, the following two data structures SHOULD be synchronized with the Resolver Repository: (i) the DNS Server List, which keeps the list of RDNSS addresses and (ii) the DNSSL, which keeps the list of DNS search domain names. Each entry in these two lists consists of a pair of an RDNSS address (or DNSSL domain name) and Expiration-time as follows:

DNSリポジトリーの管理のために、次の2つのデータ構造をリゾルバーリポジトリーと同期させるべきです（SHOULD）。(i) RDNSSアドレスのリストを保持するDNSサーバーリストと、(ii) DNS検索ドメイン名のリストを保持するDNSSLです。これら2つのリストの各エントリーは、次のように、RDNSSアドレス（またはDNSSLドメイン名）とExpiration-timeの組で構成されます。

  • RDNSS address for DNS Server List: IPv6 address of the RDNSS that is available for recursive DNS resolution service in the network advertising the RDNSS option.
  • DNSSL domain name for DNSSL: DNS suffix domain name that is used to perform DNS query searches for short, unqualified domain names.
  • Expiration-time for DNS Server List or DNSSL: The time when this entry becomes invalid. Expiration-time is set to the value of the Lifetime field of the RDNSS option or DNSSL option plus the current time. Whenever a new RDNSS option with the same address (or DNSSL option with the same domain name) is received on the same interface as a previous RDNSS option (or DNSSL option), this field is updated to have a new Expiration-time. When the current time becomes larger than Expiration-time, this entry is regarded as expired, so it should not be used any more. Note that the DNS information for the RDNSS and DNSSL options need not be dropped if the expiry of the RA router lifetime happens. This is because these options have their own lifetime values.
  • DNSサーバーリストのRDNSSアドレス: RDNSSオプションを広告しているネットワークにおいて、再帰的なDNS解決サービスに利用できるRDNSSのIPv6アドレス。
  • DNSSLのDNSSLドメイン名: 短い、完全修飾されていないドメイン名についてDNSクエリーによる検索を行うために使用されるDNSサフィックスのドメイン名。
  • DNSサーバーリストまたはDNSSLのExpiration-time: このエントリーが無効になる時刻。Expiration-timeには、RDNSSオプションまたはDNSSLオプションのLifetimeフィールドの値に現在時刻を加えた値を設定します。以前のRDNSSオプション（またはDNSSLオプション）と同じインターフェイス上で、同じアドレスを持つ新しいRDNSSオプション（または同じドメイン名を持つDNSSLオプション）を受信するたびに、このフィールドは新しいExpiration-timeに更新されます。現在時刻がExpiration-timeを超えると、このエントリーは期限切れとみなされるため、それ以降は使用されるべきではありません。なお、RAのルーター有効期間が満了しても、RDNSSオプションとDNSSLオプションのDNS情報を破棄する必要はありません。これは、これらのオプションが独自の有効期間の値を持つためです。

6.2. Synchronization between DNS Server List and Resolver Repository

6.2. DNSサーバーリストとリゾルバーリポジトリーの間の同期

When an IPv6 host receives the information of multiple RDNSS addresses within a network (e.g., campus network and company network) through an RA message with RDNSS option(s), it stores the RDNSS addresses (in order) in both the DNS Server List and the Resolver Repository. The processing of the RDNSS consists of (i) the processing of RDNSS option(s) included in an RA message and (ii) the handling of expired RDNSSes. The processing of RDNSS option(s) is as follows:

IPv6ホストは、RDNSSオプションを含むRAメッセージを通じて、ネットワーク（たとえば、キャンパスネットワークや企業ネットワーク）内の複数のRDNSSアドレスの情報を受信すると、そのRDNSSアドレスを（順序どおりに）DNSサーバーリストとリゾルバーリポジトリーの両方に格納します。RDNSSの処理は、(i) RAメッセージに含まれるRDNSSオプションの処理と、(ii) 期限切れのRDNSSの取り扱いで構成されます。RDNSSオプションの処理は次のとおりです。

  • Step (a): Receive and parse the RDNSS option(s). For the RDNSS addresses in each RDNSS option, perform Steps (b) through (d).
  • Step (b): For each RDNSS address, check the following: If the RDNSS address already exists in the DNS Server List and the RDNSS option's Lifetime field is set to zero, delete the corresponding RDNSS entry from both the DNS Server List and the Resolver Repository in order to prevent the RDNSS address from being used any more for certain reasons in network management, e.g., the termination of the RDNSS or a renumbering scenario. That is, the RDNSS can resign from its DNS service because the machine running the RDNSS is out of service intentionally or unintentionally. Also, in the renumbering scenario, the RDNSS's IPv6 address will be changed, so the previous RDNSS address should not be used any more. The processing of this RDNSS address is finished here. Otherwise, go to Step (c).
  • Step (c): For each RDNSS address, if it already exists in the DNS Server List and the RDNSS option's Lifetime field is not set to zero, then just update the value of the Expiration-time field according to the procedure specified in the third bullet of Section 6.1. Otherwise, go to Step (d).
  • Step (d): For each RDNSS address, if it does not exist in the DNS Server List, register the RDNSS address and Lifetime with the DNS Server List and then insert the RDNSS address as the first one in the Resolver Repository. In the case where the data structure for the DNS Server List is full of RDNSS entries (that is, has more RDNSSes than the sufficient number discussed in Section 5.3.1), delete from the DNS Server List the entry with the shortest Expiration-time (i.e., the entry that will expire first). The corresponding RDNSS address is also deleted from the Resolver Repository. For the ordering of RDNSS addresses in an RDNSS option, position the first RDNSS address in the RDNSS option as the first one in the Resolver Repository, the second RDNSS address in the option as the second one in the repository, and so on. This ordering allows the RDNSS addresses in the RDNSS option to be preferred according to their order in the RDNSS option for DNS name resolution. The processing of these RDNSS addresses is finished here.
  • ステップ(a): RDNSSオプションを受信して解析します。各RDNSSオプション内のRDNSSアドレスについて、ステップ(b)から(d)を実行します。
  • ステップ(b): 各RDNSSアドレスについて、次のことを確認します。そのRDNSSアドレスがすでにDNSサーバーリストに存在し、かつRDNSSオプションのLifetimeフィールドが0に設定されている場合は、ネットワーク管理上の何らかの理由（たとえば、RDNSSの終了やリナンバリングのシナリオ）でそのRDNSSアドレスがこれ以上使用されないように、対応するRDNSSエントリーをDNSサーバーリストとリゾルバーリポジトリーの両方から削除します。つまり、RDNSSを実行しているマシンが意図的に、または意図せずにサービスを停止したために、RDNSSがDNSサービスから退くことがあります。また、リナンバリングのシナリオでは、RDNSSのIPv6アドレスが変更されるため、以前のRDNSSアドレスはこれ以上使用されるべきではありません。このRDNSSアドレスの処理はここで終了します。そうでなければ、ステップ(c)に進みます。
  • ステップ(c): 各RDNSSアドレスについて、それがすでにDNSサーバーリストに存在し、かつRDNSSオプションのLifetimeフィールドが0に設定されていない場合は、セクション6.1の3つ目の項目で規定されている手順に従って、Expiration-timeフィールドの値を更新するだけです。そうでなければ、ステップ(d)に進みます。
  • ステップ(d): 各RDNSSアドレスについて、それがDNSサーバーリストに存在しない場合は、そのRDNSSアドレスとLifetimeをDNSサーバーリストに登録し、そのRDNSSアドレスをリゾルバーリポジトリーの先頭に挿入します。DNSサーバーリストのデータ構造がRDNSSエントリーでいっぱいの場合（すなわち、セクション5.3.1で議論した十分な数よりも多くのRDNSSを持つ場合）は、Expiration-timeが最も短いエントリー（すなわち、最初に期限切れになるエントリー）をDNSサーバーリストから削除します。対応するRDNSSアドレスもリゾルバーリポジトリーから削除します。RDNSSオプション内のRDNSSアドレスの順序付けについては、RDNSSオプション内の1つ目のRDNSSアドレスをリゾルバーリポジトリー内の1つ目に、オプション内の2つ目のRDNSSアドレスをリポジトリー内の2つ目に、というように配置します。この順序付けにより、DNS名前解決において、RDNSSオプション内のRDNSSアドレスをRDNSSオプション内の順序に従って優先させることができます。これらのRDNSSアドレスの処理はここで終了します。

The handling of expired RDNSSes is as follows: Whenever an entry expires in the DNS Server List, the expired entry is deleted from the DNS Server List, and also the RDNSS address corresponding to the entry is deleted from the Resolver Repository.

期限切れのRDNSSの取り扱いは次のとおりです。DNSサーバーリスト内のエントリーが期限切れになるたびに、期限切れのエントリーをDNSサーバーリストから削除し、そのエントリーに対応するRDNSSアドレスもリゾルバーリポジトリーから削除します。

6.3. Synchronization between DNS Search List and Resolver Repository

6.3. DNS検索リストとリゾルバーリポジトリーの間の同期

When an IPv6 host receives the information of multiple DNSSL domain names within a network through an RA message with DNSSL option(s), it stores the DNSSL domain names (in order) in both the DNSSL and the Resolver Repository. The processing of the DNSSL consists of (i) the processing of DNSSL option(s) included in an RA message and (ii) the handling of expired DNSSLs. The processing of DNSSL option(s) is the same as the processing of RDNSS option(s) as described in Section 6.2.

IPv6ホストは、DNSSLオプションを含むRAメッセージを通じて、ネットワーク内の複数のDNSSLドメイン名の情報を受信すると、そのDNSSLドメイン名を（順序どおりに）DNSSLとリゾルバーリポジトリーの両方に格納します。DNSSLの処理は、(i) RAメッセージに含まれるDNSSLオプションの処理と、(ii) 期限切れのDNSSLの取り扱いで構成されます。DNSSLオプションの処理は、セクション6.2で説明したRDNSSオプションの処理と同じです。

7. Security Considerations

7. セキュリティーに関する考慮事項

In this section, we analyze security threats related to DNS options and then make recommendations to cope with such security threats.

このセクションでは、DNSオプションに関連するセキュリティー上の脅威を分析し、そのようなセキュリティー上の脅威に対処するための推奨事項を示します。

7.1. Security Threats

7.1. セキュリティー上の脅威

For the RDNSS option, an attacker could send an RA with a fraudulent RDNSS address, misleading IPv6 hosts into contacting an unintended DNS server for DNS name resolution. Also, for the DNSSL option, an attacker can let IPv6 hosts resolve a hostname without a DNS suffix into an unintended host's IP address with a fraudulent DNSSL. These attacks are similar to ND attacks specified in [RFC4861] that use Redirect or Neighbor Advertisement messages to redirect traffic to individual addresses of malicious parties.

RDNSSオプションについては、攻撃者が不正なRDNSSアドレスを含むRAを送信し、IPv6ホストを欺いて、DNS名前解決のために意図しないDNSサーバーに接続させる可能性があります。また、DNSSLオプションについては、攻撃者は不正なDNSSLによって、DNSサフィックスのないホスト名をIPv6ホストに意図しないホストのIPアドレスへと解決させることができます。これらの攻撃は、リダイレクトメッセージや近隣広告メッセージを使用して、トラフィックを悪意のある者の個々のアドレスにリダイレクトする、[RFC4861]で規定されているND攻撃に似ています。

However, the security of these RA options for DNS configuration does not affect ND protocol security [RFC4861]. This is because learning DNS information via the RA options cannot be worse than learning bad router information via the RA options. Therefore, the vulnerability of ND is not worse and is a subset of the attacks that any node attached to a LAN can do.

しかし、これらのDNS設定のためのRAオプションのセキュリティーは、NDプロトコルのセキュリティー[RFC4861]に影響を与えません。これは、RAオプションを介してDNS情報を知ることが、RAオプションを介して不正なルーター情報を知ることより悪くなることはありえないためです。したがって、NDの脆弱性が悪化することはなく、これはLANに接続された任意のノードが実行できる攻撃の部分集合です。

7.2. Recommendations

7.2. 推奨事項

The Secure Neighbor Discovery (SEND) protocol [RFC3971] is designed as a security mechanism for ND. In this case, ND can use SEND to allow all the ND options, including the RDNSS and DNSSL options, to be automatically signed with digital signatures.

Secure Neighbor Discovery（SEND）プロトコル[RFC3971]は、NDのためのセキュリティーメカニズムとして設計されています。この場合、NDはSENDを使用して、RDNSSオプションとDNSSLオプションを含むすべてのNDオプションに、デジタル署名で自動的に署名できるようにすることができます。

It is common for network devices such as switches to include mechanisms to block unauthorized ports from running a DHCPv6 server to provide protection from rogue DHCPv6 servers [RFC7610]. That means that an attacker on other ports cannot insert bogus DNS servers using DHCPv6. The corresponding technique for network devices is RECOMMENDED to block rogue RA messages that include the RDNSS and DNSSL options from unauthorized nodes [RFC6104] [RFC6105].

スイッチなどのネットワーク機器には、不正なDHCPv6サーバーから保護するために、権限のないポートがDHCPv6サーバーを実行することをブロックするメカニズムが含まれているのが一般的です[RFC7610]。これは、ほかのポート上の攻撃者がDHCPv6を使用して偽のDNSサーバーを挿入できないことを意味します。ネットワーク機器において、権限のないノードからのRDNSSオプションとDNSSLオプションを含む不正なRAメッセージをブロックするための、これに相当する技術が推奨されます（RECOMMENDED）[RFC6104] [RFC6105]。

An attacker may provide a bogus DNSSL option in order to cause the victim to send DNS queries to a specific DNS server when the victim queries non-FQDNs (fully qualified domain names). For this attack, the DNS resolver in IPv6 hosts can mitigate the vulnerability with the recommendations mentioned in [RFC1535], [RFC1536], and [RFC3646].

攻撃者は、被害者が非FQDN（FQDNは完全修飾ドメイン名（fully qualified domain name））を問い合わせたときに、被害者に特定のDNSサーバーへDNSクエリーを送信させるために、偽のDNSSLオプションを提供する可能性があります。この攻撃に対しては、IPv6ホストのDNSリゾルバーが、[RFC1535]、[RFC1536]、[RFC3646]で述べられている推奨事項によって、この脆弱性を緩和できます。

Appendix A. Changes from RFC 6106

付録A. RFC 6106からの変更点

The following changes were made from RFC 6106 ("IPv6 Router Advertisement Options for DNS Configuration"):

RFC 6106（「IPv6 Router Advertisement Options for DNS Configuration」）から、次の変更を行いました。

  • This document allows a higher default value of the lifetime of the DNS RA options than RFC 6106 in order to avoid the frequent expiry of the options on links with a relatively high rate of packet loss; at the same time, this document also makes additional clarifications. The lifetime's lower bound of 2 * MaxRtrAdvInterval was shown to lead to the expiry of these options on links with a relatively high rate of packet loss. To avoid this problem, this revision relaxes the lower bound and sets a higher default value of 3 * MaxRtrAdvInterval.
  • The text regarding the generation of a Router Solicitation message to ensure that the RDNSS information is fresh before the expiry of the RDNSS option is removed in order to prevent multicast traffic on the link from increasing.
  • The addresses for RDNSSes in the RDNSS option can be not only global addresses but also link-local addresses. The link-local addresses for RDNSSes should be registered in the Resolver Repository along with the corresponding link zone indices.
  • RFC 6106 recommended that the number of RDNSS addresses that should be learned and maintained through the RDNSS RA option should be limited to three. This document removes that recommendation; thus, the number of RDNSS addresses to maintain is determined by an implementer's local policy.
  • RFC 6106 recommended that the number of DNS search domains that should be learned and maintained through the DNSSL RA option should be limited to three. This document removes that recommendation; thus, when the set of unique DNSSL values are not equivalent, none of them may be ignored for hostname lookups according to an implementer's local policy.
  • The guidance of the specific implementation for the synchronization of the DNS Repository and Resolver Repository in the kernel space and user space is removed.
  • The key words "SHOULD" and "RECOMMENDED" (RFC 2119) are removed in the recommendation of using SEND as a security mechanism for ND. Instead of using these key words, SEND is specified as only a possible security mechanism for ND.
  • この文書では、パケットロス率が比較的高いリンク上でオプションが頻繁に期限切れになるのを避けるために、DNS RAオプションの有効期間について、RFC 6106より大きなデフォルト値を認めます。同時に、この文書では追加の明確化も行っています。有効期間の下限が2 * MaxRtrAdvIntervalだと、パケットロス率が比較的高いリンク上でこれらのオプションが期限切れになることが示されました。この問題を避けるために、この改訂版では下限を緩和し、より大きなデフォルト値として3 * MaxRtrAdvIntervalを設定します。
  • RDNSSオプションの期限が切れる前にRDNSS情報が新しい状態であることを保証するためにルーター要請メッセージを生成することに関する記述を、リンク上のマルチキャストトラフィックの増加を防ぐために削除しました。
  • RDNSSオプション内のRDNSSのアドレスは、グローバルアドレスだけでなく、リンクローカルアドレスであってもかまいません。RDNSSのリンクローカルアドレスは、対応するリンクゾーンインデックスとともにリゾルバーリポジトリーに登録されるべきです。
  • RFC 6106は、RDNSS RAオプションを通じて学習し維持すべきRDNSSアドレスの数を3つに制限すべきであると推奨していました。この文書ではその推奨を削除しました。したがって、維持するRDNSSアドレスの数は、実装者のローカルポリシーによって決まります。
  • RFC 6106は、DNSSL RAオプションを通じて学習し維持すべきDNS検索ドメインの数を3つに制限すべきであると推奨していました。この文書ではその推奨を削除しました。したがって、一意なDNSSL値の集合が同等でない場合、実装者のローカルポリシーによって、ホスト名の検索においてそれらのいずれかを無視してはなりません。
  • カーネル空間とユーザー空間におけるDNSリポジトリーとリゾルバーリポジトリーの同期について、具体的な実装のガイダンスを削除しました。
  • NDのセキュリティーメカニズムとしてSENDを使用することの推奨において、キーワード「SHOULD」と「RECOMMENDED」（RFC 2119）を削除しました。これらのキーワードを使用する代わりに、SENDは、NDのセキュリティーメカニズムとして考えられるものの1つとして規定されるだけになりました。
