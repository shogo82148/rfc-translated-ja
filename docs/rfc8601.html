RFC 8601

Message Header Field for Indicating Message Authentication Status

RFC 8601

メッセージ認証ステータスを示すためのメッセージヘッダーフィールド

Abstract

概要

This document specifies a message header field called "Authentication-Results" for use with electronic mail messages to indicate the results of message authentication efforts. Any receiver-side software, such as mail filters or Mail User Agents (MUAs), can use this header field to relay that information in a convenient and meaningful way to users or to make sorting and filtering decisions.

この文書は、メッセージ認証の取り組みの結果を示すために電子メールメッセージで使用する「Authentication-Results」というメッセージヘッダーフィールドを規定します。メールフィルターやメールユーザーエージェント（MUA）などの受信側のソフトウェアはどれでも、このヘッダーフィールドを使用して、その情報を便利で意味のある方法でユーザーに中継したり、並べ替えやフィルタリングの判断を下したりできます。

This document obsoletes RFC 7601.

この文書はRFC 7601を廃止します。

1. Introduction

1. はじめに

This document describes a header field called "Authentication-Results" for electronic mail messages that presents the results of a message authentication effort in a machine-readable format. The intent of the header field is to create a place to collect such data when message authentication mechanisms are in use so that a Mail User Agent (MUA) and downstream filters can make filtering decisions and/or provide a recommendation to the user as to the validity of the message's origin and possibly the safety and integrity of its content.

この文書は、メッセージ認証の取り組みの結果を機械可読な形式で提示する、電子メールメッセージ用の「Authentication-Results」というヘッダーフィールドについて説明します。このヘッダーフィールドの意図は、メッセージ認証メカニズムが使われているときにそのようなデータを収集する場所を作ることです。それによって、メールユーザーエージェント（MUA）や下流のフィルターがフィルタリングの判断を下したり、メッセージの発信元の正当性や、場合によってはその内容の安全性と完全性について、ユーザーに推奨を提供したりできるようになります。

End users are not expected to be direct consumers of this header field. This header field is intended for consumption by programs that will then use such data or render it in a human-usable form.

エンドユーザーがこのヘッダーフィールドを直接消費することは想定していません。このヘッダーフィールドは、そのデータを使用したり、人間が使える形式で表示したりするプログラムによって消費されることを意図しています。

This document specifies the format of this header field and discusses the implications of its presence or absence. However, it does not discuss how the data contained in the header field ought to be used, such as what filtering decisions are appropriate or how an MUA might render those results, as these are local policy and/or user interface design questions that are not appropriate for this document.

この文書は、このヘッダーフィールドの形式を規定し、その有無が持つ意味について検討します。ただし、どのようなフィルタリングの判断が適切か、MUAがそれらの結果をどのように表示するかといった、ヘッダーフィールドに含まれるデータをどのように使うべきかについては検討しません。それらはローカルポリシーやユーザーインターフェイス設計の問題であり、この文書で扱うのは適切でないからです。

At the time of publication of this document, the following are published email authentication methods:

この文書の発行時点で、公開されている電子メール認証方式は次のとおりです：

  • SMTP Service Extension for Authentication [AUTH]
  • DomainKeys Identified Mail Signatures [DKIM]
  • Domain-based Message Authentication, Reporting, and Conformance [DMARC]
  • Sender Policy Framework [SPF]
  • reverse IP address name validation ("iprev", defined in Section 3)
  • Require-Recipient-Valid-Since Header Field and SMTP Service Extension [RRVS]
  • S/MIME Signature Verification [SMIME-REG]
  • Vouch By Reference [VBR]
  • 認証のためのSMTPサービス拡張[AUTH]
  • DomainKeys Identified Mail署名[DKIM]
  • ドメインベースのメッセージ認証、報告、適合[DMARC]
  • Sender Policy Framework [SPF]
  • 逆引きIPアドレスによる名前の検証（「iprev」、Section 3で定義）
  • Require-Recipient-Valid-SinceヘッダーフィールドおよびそのためのSMTPサービス拡張[RRVS]
  • S/MIME署名の検証[SMIME-REG]
  • Vouch By Reference [VBR]

The following Historic specifications were previously supported by this framework but have since become obsolete:

以下の歴史的（Historic）な仕様は、以前はこのフレームワークでサポートされていましたが、その後廃止されました：

  • Author Domain Signing Practices [ADSP] (Historic)
  • DomainKeys [DOMAINKEYS] (Historic)
  • Author Domain Signing Practices [ADSP]（歴史的）
  • DomainKeys [DOMAINKEYS]（歴史的）

Note that at the time of publication of this document the Sender ID specification [SENDERID] (Experimental) is no longer supported by this framework. Discussion regarding moving it to Historic status is underway.

この文書の発行時点で、Sender ID仕様[SENDERID]（実験的）は、もはやこのフレームワークではサポートされていないことに注意してください。これを歴史的（Historic）ステータスに移行することについての議論が進行中です。

There exist registries for tokens used within this header field that refer to the specifications listed above. Section 6 describes the registries and their contents and specifies the process by which entries are added or updated. It also updates the existing contents to match the current states of these specifications.

このヘッダーフィールド内で使用され、上に挙げた仕様を参照するトークンのためのレジストリーが存在します。Section 6では、それらのレジストリーとその内容を説明し、エントリーを追加または更新する手続きを規定します。また、既存の内容をこれらの仕様の現在の状態に合わせて更新します。

The goal of this work is to give current and future authentication schemes a common framework within which to deliver their results to downstream agents and discourage the creation of unique header fields for each.

この作業の目標は、現在および将来の認証方式に対して、その結果を下流のエージェントに届けるための共通のフレームワークを提供し、方式ごとに固有のヘッダーフィールドが作られるのを抑止することです。

Although SPF defined a header field called "Received-SPF" and the historic DomainKeys defined one called "DomainKey-Status" for this purpose, those header fields are specific to the conveyance of their respective results only and thus are insufficient to satisfy the requirements enumerated below. In addition, many SPF implementations have adopted the header field specified here at least as an option, and DomainKeys has been obsoleted by DKIM.

SPFはこの目的のために「Received-SPF」というヘッダーフィールドを定義し、歴史的なDomainKeysは「DomainKey-Status」というヘッダーフィールドを定義しましたが、それらのヘッダーフィールドはそれぞれの結果を伝えることだけに特化しているため、後で列挙する要件を満たすには不十分です。さらに、多くのSPF実装は、少なくともオプションとして、ここで規定するヘッダーフィールドを採用しており、DomainKeysはDKIMによって廃止されています。

1.1. Purpose

1.1. 目的

The header field defined in this document is expected to serve several purposes:

この文書で定義するヘッダーフィールドは、いくつかの目的を果たすことが期待されています：

  1. Convey the results of various message authentication checks, which are applied by upstream filters and Mail Transfer Agents (MTAs) and then passed to MUAs and downstream filters within the same "trust domain". Such agents might wish to render those results to end users or to use those data to apply more or less stringent content checks based on authentication results.
  2. Provide a common location within a message for such data.
  3. Create an extensible framework for reporting new authentication methods as they emerge.
  1. 上流のフィルターやメール転送エージェント（MTA）によって適用され、同じ「信頼ドメイン」内のMUAや下流のフィルターに渡される、さまざまなメッセージ認証チェックの結果を伝えること。そのようなエージェントは、それらの結果をエンドユーザーに表示したり、そのデータを使って、認証結果に基づいて内容のチェックの厳しさを加減したりしたいと考えるかもしれません。
  2. そのようなデータのための共通の場所をメッセージ内に用意すること。
  3. 新しい認証方式が登場したときにそれを報告するための拡張可能なフレームワークを作ること。

In particular, the mere presence of this header field does not mean its contents are valid. Rather, the header field is reporting assertions made by one or more authentication schemes applied somewhere upstream. For an MUA or downstream filter to treat the assertions as actually valid, there must be an assessment of the trust relationship among such agents, the validating MTA, the paths between them, and the mechanism for conveying the information.

特に、このヘッダーフィールドが存在するだけでは、その内容が有効であることを意味しません。むしろ、このヘッダーフィールドは、上流のどこかで適用された1つ以上の認証方式によるアサーションを報告しているにすぎません。MUAや下流のフィルターがそれらのアサーションを実際に有効なものとして扱うには、そのようなエージェント、検証を行うMTA、それらの間のパス、および情報を伝えるメカニズムの間の信頼関係を評価する必要があります。

1.2. Trust Boundary

1.2. 信頼境界

This document makes several references to the "trust boundary" of an Administrative Management Domain (ADMD). Given the diversity among existing mail environments, a precise definition of this term isn't possible.

この文書は、管理運営ドメイン（ADMD）の「信頼境界」に何度か言及します。既存のメール環境は多様であるため、この用語を厳密に定義することはできません。

Simply put, a transfer from the producer of the header field to the consumer must occur within a context that permits the consumer to treat assertions by the producer as being reliable and accurate (trustworthy). How this trust is obtained is outside the scope of this document. It is entirely a local matter.

簡単に言えば、ヘッダーフィールドの生成者から消費者への受け渡しは、消費者が生成者によるアサーションを信頼でき正確である（信用できる）ものとして扱える状況の中で行われなければなりません。この信頼をどのように得るかは、この文書の範囲外です。これは完全にローカルな問題です。

Thus, this document defines a "trust boundary" as the delineation between "external" and "internal" entities. Services that are internal -- within the trust boundary -- are provided by the ADMD's infrastructure for its users. Those that are external are outside of the authority of the ADMD. By this definition, hosts that are within a trust boundary are subject to the ADMD's authority and policies, independent of their physical placement or their physical operation. For example, a host within a trust boundary might actually be operated by a remote service provider and reside physically within its data center.

したがって、この文書では、「信頼境界」を「外部」と「内部」のエンティティーの境目として定義します。内部の（つまり信頼境界内にある）サービスは、ADMDのインフラストラクチャーによってそのユーザーに提供されます。外部のサービスは、ADMDの権限の外にあります。この定義により、信頼境界内にあるホストは、物理的な配置や物理的な運用とは無関係に、ADMDの権限とポリシーに従います。たとえば、信頼境界内のホストが、実際にはリモートのサービスプロバイダーによって運用され、物理的にはそのデータセンター内に置かれていることもあります。

It is possible for a message to be evaluated inside a trust boundary but then depart and re-enter the trust boundary. An example might be a forwarded message such as a message/rfc822 attachment (see "Multipurpose Internet Mail Extensions" [MIME]) or one that is part of a multipart/digest. The details reported by this field cannot be trusted in that case. Thus, if found within one of those media types, this field is typically ignored.

メッセージが信頼境界内で評価された後、信頼境界を出て、再び信頼境界に入ることもあり得ます。その例としては、message/rfc822の添付（「Multipurpose Internet Mail Extensions」[MIME]を参照）として転送されたメッセージや、multipart/digestの一部であるメッセージが挙げられます。その場合、このフィールドで報告される詳細は信頼できません。したがって、そのようなメディアタイプの中で見つかった場合、このフィールドは通常無視されます。

Note that an MUA could be configured to retrieve messages from a receiver yet not be within the receiver's ADMD. In this case, for the purposes of this work, that MUA is considered to be within the receiver's ADMD if it is configured to identify and ascribe value to authentication results recorded by that ADMD.

MUAは、受信者からメッセージを取得するように設定されていながら、受信者のADMD内にはないこともあり得ることに注意してください。この場合、この作業の目的においては、そのMUAがそのADMDによって記録された認証結果を識別し、それに価値を認めるように設定されていれば、そのMUAは受信者のADMD内にあるとみなされます。

1.3. Processing Scope

1.3. 処理の範囲

The content of this header field is meant to convey to message consumers that authentication work on the message was already done within its trust boundary, and those results are being presented. It is not intended to provide message parameters to consumers so that they can perform authentication protocols on their own.

このヘッダーフィールドの内容は、メッセージに対する認証作業がその信頼境界内ですでに行われ、その結果が提示されていることを、メッセージの消費者に伝えることを目的としています。消費者が自分で認証プロトコルを実行できるように、メッセージのパラメーターを消費者に提供することは意図していません。

1.4. Requirements

1.4. 要件

This document establishes no new requirements on existing protocols, insofar as a non-participating service will continue to interoperate with the deployed messaging infrastructure.

参加しないサービスも展開済みのメッセージングインフラストラクチャーと引き続き相互運用できる限りにおいて、この文書は既存のプロトコルに新しい要件を課しません。

In particular, this document establishes no requirement on MTAs to reject or filter arriving messages that do not pass authentication checks. The data conveyed by the specified header field's contents are for the information of MUAs and filters and are to be used at their discretion.

1.5.3. Security

1.5.3. セキュリティー

"Guidelines for Writing RFC Text on Security Considerations" [SECURITY] discusses authentication and authorization and the conflation of the two concepts. The use of those terms within the context of recent message security work has given rise to slightly different definitions, and this document reflects those current usages, as follows:

「Guidelines for Writing RFC Text on Security Considerations」[SECURITY]では、認証と認可、およびこの2つの概念の混同について検討しています。最近のメッセージセキュリティーの作業の文脈におけるこれらの用語の使い方から、わずかに異なる定義が生まれており、この文書は次のように、それらの現在の用法を反映しています：

  • "Authorization" is the establishment of permission to use a resource or represent an identity. In this context, authorization indicates that a message from a particular ADMD arrived via a route the ADMD has explicitly approved.
  • "Authentication" is the assertion of validity of a piece of data about a message (such as the sender's identity) or the message in its entirety.
  • 「認可」とは、リソースを使用したり、アイデンティティーを表したりする許可を確立することです。この文脈では、認可は、特定のADMDからのメッセージが、そのADMDが明示的に承認した経路を経由して到着したことを示します。
  • 「認証」とは、メッセージに関するデータの一部（送信者のアイデンティティーなど）またはメッセージ全体の正当性をアサートすることです。

As examples: SPF is an authorization mechanism in that it expresses a result that shows whether the ADMD that apparently sent the message has explicitly authorized the connecting Simple Mail Transfer Protocol (SMTP) client [SMTP] to relay messages on its behalf, but it does not actually validate any other property of the message itself. By contrast, DKIM is agnostic as to the routing of a message but uses cryptographic signatures to authenticate agents, assign (some) responsibility for the message (which implies authorization), and ensure that the listed portions of the message were not modified in transit. Since the signatures are not tied to SMTP connections, they can be added by the ADMD of origin, intermediate ADMDs (such as a mailing list server), other handling agents, or any combination of these.

例を挙げます。SPFは、見かけ上メッセージを送信したADMDが、接続してきた簡易メール転送プロトコル（SMTP）クライアント[SMTP]に対して、自分の代わりにメッセージを中継することを明示的に認可したかどうかを示す結果を表すという意味で、認可のメカニズムです。しかし、メッセージ自体のほかのプロパティーは実際には何も検証しません。対照的に、DKIMはメッセージのルーティングには関知しませんが、暗号署名を使って、エージェントを認証し、メッセージに対する（ある程度の）責任を割り当て（これは認可を意味します）、メッセージの列挙された部分が転送中に変更されていないことを保証します。署名はSMTPコネクションに結び付いていないため、発信元のADMD、中間のADMD（メーリングリストサーバーなど）、そのほかの処理エージェント、またはそれらの任意の組み合わせによって追加できます。

Rather than create a separate header field for each class of solution, this specification groups them both into a single header field.

この仕様では、解決策の種類ごとに別々のヘッダーフィールドを作るのではなく、その両方を1つのヘッダーフィールドにまとめます。

1.5.4. Email Architecture

1.5.4. 電子メールのアーキテクチャー

  • A "border MTA" is an MTA that acts as a gateway between the general Internet and the users within an organizational boundary. (See also Section 1.2.)
  • A "delivery MTA" (or Mail Delivery Agent or MDA) is an MTA that actually enacts delivery of a message to a user's inbox or other final delivery.
  • An "intermediate MTA" is any MTA that is not a delivery MTA and is also not the first MTA to handle the message.
  • A Message Submission Agent (MSA) is an agent that accepts a message from an MUA, introducing it to the mail-handling stream.
  • 「境界MTA」とは、一般のインターネットと組織の境界内のユーザーとの間でゲートウェイとして機能するMTAです（Section 1.2も参照してください）。
  • 「配送MTA」（またはメール配送エージェント、MDA）とは、ユーザーの受信箱へのメッセージの配送やそのほかの最終的な配送を実際に行うMTAです。
  • 「中間MTA」とは、配送MTAでも、メッセージを最初に処理するMTAでもない任意のMTAです。
  • メッセージ投稿エージェント（MSA）とは、MUAからメッセージを受け付け、それをメール処理の流れに投入するエージェントです。

1.6. Trust Environment

1.6. 信頼環境

This header field permits one or more message validation mechanisms to communicate output to one or more separate assessment mechanisms. These mechanisms operate within a unified trust boundary that defines an ADMD. An ADMD contains one or more entities that perform validation and generate the header field and one or more that consume it for some type of assessment. The field often contains no integrity or validation mechanism of its own, so its presence must be trusted implicitly. Hence, valid use of the header field requires removing any occurrences of it that claim to be associated with the ADMD when the message enters the ADMD. This ensures that later occurrences have been added within the trust boundary of the ADMD.

このヘッダーフィールドによって、1つ以上のメッセージ検証メカニズムが、1つ以上の別個の評価メカニズムに出力を伝えることができます。これらのメカニズムは、ADMDを定義する統一された信頼境界内で動作します。ADMDには、検証を行ってヘッダーフィールドを生成する1つ以上のエンティティーと、何らかの評価のためにそれを消費する1つ以上のエンティティーが含まれます。このフィールドは、多くの場合、それ自体の完全性や検証のメカニズムを含まないため、その存在は暗黙のうちに信頼されなければなりません。したがって、このヘッダーフィールドを有効に使用するには、メッセージがADMDに入るときに、そのADMDに関連付けられていると主張するこのヘッダーフィールドの出現をすべて削除する必要があります。これにより、それ以降の出現がADMDの信頼境界内で追加されたものであることが保証されます。

The authserv-id token defined in Section 2.2 can be used to reference an entire ADMD or a specific validation engine within an ADMD. Although the labeling scheme is left as an operational choice, some guidance for selecting a token is provided in later sections of this document.

Section 2.2で定義するauthserv-idトークンは、ADMD全体、またはADMD内の特定の検証エンジンを参照するために使用できます。ラベル付けの方式は運用上の選択に委ねられていますが、トークンの選択に関するガイダンスをこの文書の後のセクションで示します。

2. Definition and Format of the Header Field

2. ヘッダーフィールドの定義と形式

This section gives a general overview of the format of the header field being defined and then provides a formal specification.

このセクションでは、定義するヘッダーフィールドの形式の概要を示した後、形式的な仕様を示します。

2.1. General Description

2.1. 一般的な説明

The header field specified here is called "Authentication-Results". It is a structured header field as defined in "Internet Message Format" [MAIL], and thus all of the related definitions in that document apply.

ここで規定するヘッダーフィールドは「Authentication-Results」と呼ばれます。これは「Internet Message Format」[MAIL]で定義されている構造化ヘッダーフィールドであるため、その文書の関連する定義がすべて適用されます。

This header field is added at the top of the message as it transits MTAs that do authentication checks, so some idea of how far away the checks were done can be inferred. It is therefore considered to be a trace field as defined in [MAIL], and thus all of the related definitions in that document apply.

このヘッダーフィールドは、メッセージが認証チェックを行うMTAを通過する際にメッセージの先頭に追加されるため、チェックがどのくらい離れた場所で行われたかをある程度推測できます。したがって、これは[MAIL]で定義されているトレースフィールドであるとみなされ、その文書の関連する定義がすべて適用されます。

The value of the header field (after removing comments) consists of an authentication service identifier, an optional version, and then a series of statements and supporting data. The statements are of the form "method=result" and indicate which authentication method or methods were applied and their respective results. For each such statement, the supporting data can include a "reason" string and one or more "property=value" statements indicating which message properties were evaluated to reach that conclusion.

このヘッダーフィールドの値は（コメントを取り除いた後）、認証サービス識別子、省略可能なバージョン、そして一連のステートメントと補足データで構成されます。ステートメントは「method=result」の形式であり、どの認証方式が適用されたかと、それぞれの結果を示します。そのような各ステートメントについて、補足データには、「reason」文字列と、その結論に至るためにメッセージのどのプロパティーが評価されたかを示す1つ以上の「property=value」ステートメントを含めることができます。

The header field can appear more than once in a single message, more than one result can be represented in a single header field, or a combination of these can be applied.

このヘッダーフィールドは、1つのメッセージに複数回現れることがあり、1つのヘッダーフィールドで複数の結果を表すこともでき、それらを組み合わせることもできます。

「ptype」の値が「policy」であることは、抽出可能なメッセージのプロパティーに固有ではない、メッセージに関するポリシー判断を示します。詳細については、Section 2.4を参照してください。

Examples of complete messages using this header field can be found in Appendix B.

2.3. Property Types (ptypes) and Properties

2.3. プロパティータイプ（ptype）とプロパティー

The "ptype" in the ABNF above indicates the general type of property being described by the result being reported, upon which the reported result was based. Coupled with the "property", which is more specific, it indicates from where the reported "pvalue" was extracted. This can include a particular part of the message header or body, some part of the SMTP session, a secondary output of an authentication method (apart from its pure result), or some other aspect of the message's handling.

上のABNFの「ptype」は、報告される結果が記述するプロパティーの一般的な種類、すなわち報告される結果の基になったプロパティーの一般的な種類を示します。より具体的な「property」と組み合わせることで、報告される「pvalue」がどこから抽出されたかを示します。これには、メッセージのヘッダーや本文の特定の部分、SMTPセッションの一部、認証方式の（純粋な結果とは別の）副次的な出力、メッセージの処理のそのほかの側面などが含まれます。

Combinations of ptypes and properties are registered and described in the "Email Authentication Methods" registry, coupled with the authentication methods with which they are used. This is further described in Section 6.

ptypeとプロパティーの組み合わせは、それらと共に使用される認証方式と組にして、「Email Authentication Methods」レジストリーに登録され、説明されます。これについてはSection 6でさらに説明します。

Legal values of "ptype" are as defined in the IANA "Email Authentication Property Types" registry, created by [RFC7410]. The initial values and what they typically indicate are as follows, based on [RFC7001]:

「ptype」の正当な値は、[RFC7410]によって作成されたIANAの「Email Authentication Property Types」レジストリーで定義されているとおりです。[RFC7001]に基づく初期値と、それらが通常示すものは次のとおりです：

body:
Information that was extracted from the body of the message. This might be an arbitrary string of bytes, a hash of a string of bytes, a Uniform Resource Identifier, or some other content of interest. The "property" is an indication of where within the message body the extracted content was found and can indicate an offset, identify a MIME part, etc. (At the time of this revision, no properties matching this ptype have been registered. Accordingly, this ptype may be deprecated in the future.)
header:
Indicates information that was extracted from the header of the message. This might be the value of a header field or some portion of a header field. The "property" gives a more precise indication of the place in the header from which the extraction took place.
policy:
A local policy mechanism was applied that augments or overrides the result returned by the authentication mechanism. (See Section 2.4.)
smtp:
Indicates information that was extracted from an SMTP command that was used to relay the message. The "property" indicates which SMTP command included the extracted content as a parameter.
body:
メッセージの本文から抽出された情報です。これは、任意のバイト列、バイト列のハッシュ、Uniform Resource Identifier、またはそのほかの関心のある内容である場合があります。「property」は、抽出された内容がメッセージ本文のどこで見つかったかを示すものであり、オフセットを示したり、MIMEパートを識別したりできます（この改訂の時点で、このptypeに一致するプロパティーは登録されていません。そのため、このptypeは将来非推奨になる可能性があります）。

policy:
認証メカニズムが返した結果を補強または上書きするローカルポリシーのメカニズムが適用されました（Section 2.4を参照してください）。
smtp:
メッセージの中継に使用されたSMTPコマンドから抽出された情報を示します。「property」は、抽出された内容をパラメーターとして含んでいたSMTPコマンドがどれであるかを示します。

Results reported using unknown ptypes MUST NOT be used in making handling decisions. They can be safely ignored by consumers.

未知のptypeを使って報告された結果を、処理の判断に使用してはなりません（MUST NOT）。消費者はそれらを安全に無視できます。

Entries in the "Email Authentication Methods" registry can define properties that deviate from these definitions when appropriate. Such deviations need to be clear in the registry and/or in the defining document. See Section 2.7.1 for an example.

2.4. The "policy" ptype

2.4. 「policy」ptype

A special ptype value of "policy" is also defined. This ptype is provided to indicate that some local policy mechanism was applied that augments or even replaces (i.e., overrides) the result returned by the authentication mechanism. The property and value in this case identify the local policy that was applied and the result it returned.

特別なptypeの値として「policy」も定義されています。このptypeは、認証メカニズムが返した結果を補強したり、さらには置き換えたり（つまり上書きしたり）するローカルポリシーのメカニズムが適用されたことを示すために提供されています。この場合のプロパティーと値は、適用されたローカルポリシーと、それが返した結果を識別します。

For example, a DKIM signature is not required to include the Subject header field in the set of fields that are signed. An ADMD receiving such a message might decide that such a signature is unacceptable, even if it passes, because the content of the Subject header field could be altered post-signing without invalidating the signature. Such an ADMD could replace the DKIM "pass" result with a "policy" result and then also include the following in the corresponding Authentication-Results field:

たとえば、DKIM署名では、署名されるフィールドの集合にSubjectヘッダーフィールドを含める必要はありません。そのようなメッセージを受信したADMDは、Subjectヘッダーフィールドの内容が署名を無効にすることなく署名後に変更され得るため、そのような署名は、検証に合格したとしても受け入れられないと判断するかもしれません。そのようなADMDは、DKIMの「pass」という結果を「policy」という結果に置き換え、さらに、対応するAuthentication-Resultsフィールドに次の内容を含めることができます：

   ... dkim=policy policy.dkim-rules=unsigned-subject ...


   ... dkim=policy policy.dkim-rules=unsigned-subject ...

In this case, the property is "dkim-rules", indicating that some local check by that name took place and that check returned a result of "unsigned-subject". These are arbitrary names selected by (and presumably used within) the ADMD making use of them, so they are not normally registered with IANA or otherwise specified apart from setting syntax restrictions that allow for easy parsing within the rest of the header field.

この場合、プロパティーは「dkim-rules」であり、その名前のローカルチェックが行われ、そのチェックが「unsigned-subject」という結果を返したことを示します。これらは、それを利用するADMDによって選ばれた（そしておそらくそのADMD内で使われる）任意の名前であるため、通常はIANAに登録されることはなく、ヘッダーフィールドの残りの部分の中で簡単に解析できるようにするための構文上の制限を設けること以外には規定されません。

This ptype existed in the original specification for this header field [RFC5451], but without a complete description or example of intended use. As a result, it has not seen any practical use to date that matches its intended purpose. These added details are provided to guide implementers toward proper use.

このptypeは、このヘッダーフィールドの元の仕様[RFC5451]にも存在していましたが、意図された使い方についての完全な説明や例はありませんでした。その結果、これまでのところ、意図された目的に沿った実用はされていません。これらの追加の詳細は、実装者を適切な使い方に導くために提供されています。

2.5. Authentication Service Identifier Field

2.5. 認証サービス識別子フィールド

Every Authentication-Results header field has an authentication service identifier field (authserv-id above). Specifically, this is any string intended to identify the authentication service within the ADMD that conducted authentication checks on the message. This identifier is intended to be machine-readable and not necessarily meaningful to users.

すべてのAuthentication-Resultsヘッダーフィールドには、認証サービス識別子フィールド（上記のauthserv-id）があります。具体的には、これは、メッセージに対して認証チェックを実施したADMD内の認証サービスを識別することを意図した任意の文字列です。この識別子は機械可読であることを意図しており、ユーザーにとって意味がある必要はありません。

Note that in an EAI-formatted message, this identifier may be expressed in UTF-8.

EAI形式のメッセージでは、この識別子をUTF-8で表現できることに注意してください。

Since agents consuming this field will use this identifier to determine whether its contents are of interest (and are safe to use), the uniqueness of the identifier MUST be guaranteed by the ADMD that generates it and MUST pertain to that ADMD. MUAs or downstream filters SHOULD use this identifier to determine whether or not the data contained in an Authentication-Results header field ought to be used or ignored.

このフィールドを消費するエージェントは、この識別子を使って、その内容が関心の対象であるか（そして使用しても安全であるか）を判断するので、識別子の一意性は、それを生成するADMDによって保証されなければなりません（MUST）。また、識別子はそのADMDに関係するものでなければなりません（MUST）。MUAや下流のフィルターは、Authentication-Resultsヘッダーフィールドに含まれるデータを使用すべきか無視すべきかを判断するために、この識別子を使用すべきです（SHOULD）。

For simplicity and scalability, the authentication service identifier SHOULD be a common token used throughout the ADMD. Common practice is to use the DNS domain name used by or within that ADMD, sometimes called the "organizational domain", but this is not strictly necessary.

簡潔さとスケーラビリティーのために、認証サービス識別子は、ADMD全体で使われる共通のトークンであるべきです（SHOULD）。一般的な慣行は、そのADMDによって、またはその内部で使われるDNSドメイン名（「組織ドメイン」と呼ばれることもあります）を使うことですが、これは厳密には必須ではありません。

For tracing and debugging purposes, the authentication service identifier can instead be the specific hostname of the MTA performing the authentication check whose result is being reported. Moreover, some implementations define a substructure to the identifier; such structures are outside of the scope of this specification.

トレースやデバッグの目的のために、認証サービス識別子を、結果が報告される認証チェックを実行したMTAの特定のホスト名にすることもできます。さらに、識別子の下位構造を定義している実装もありますが、そのような構造はこの仕様の範囲外です。

Note, however, that using a local, relative identifier like a flat hostname, rather than a hierarchical and globally unique ADMD identifier like a DNS domain name, makes configuration more difficult for large sites. The hierarchical identifier permits aggregating related, trusted systems together under a single, parent identifier, which in turn permits assessing the trust relationship with a single reference. The alternative is a flat namespace requiring individually listing each trusted system. Since consumers will use the identifier to determine whether to use the contents of the header field:

ただし、DNSドメイン名のような階層的で世界的に一意なADMD識別子ではなく、フラットなホスト名のようなローカルで相対的な識別子を使うと、大規模なサイトでは設定がより難しくなることに注意してください。階層的な識別子では、関連する信頼できるシステムを単一の親識別子の下にまとめることができ、その結果、単一の参照で信頼関係を評価できます。その代わりとなるのは、信頼できる各システムを個別に列挙する必要があるフラットな名前空間です。消費者はこの識別子を使ってヘッダーフィールドの内容を使用するかどうかを判断するため、次のようになります：

  • Changes to the identifier impose a large, centralized administrative burden.
  • Ongoing administrative changes require constantly updating this centralized table, making it difficult to ensure that an MUA or downstream filter will have access to accurate information for assessing the usability of the header field's content. In particular, consumers of the header field will need to know not only the current identifier(s) in use but previous ones as well to account for delivery latency or later reassessment of the header field's content.
  • 識別子の変更により、大きな集中型の管理負担が生じます。
  • 継続的な管理上の変更により、この集中型の表を絶えず更新する必要があり、MUAや下流のフィルターがヘッダーフィールドの内容の有用性を評価するための正確な情報にアクセスできることを保証するのが難しくなります。特に、ヘッダーフィールドの消費者は、配送の遅延や後でのヘッダーフィールドの内容の再評価を考慮するため、現在使用中の識別子だけでなく、以前の識別子も知っておく必要があります。

Examples of valid authentication service identifiers are "example.com", "mail.example.org", "ms1.newyork.example.com", and "example-auth".

有効な認証サービス識別子の例は、「example.com」、「mail.example.org」、「ms1.newyork.example.com」、「example-auth」です。

2.6. Version Tokens

2.6. バージョントークン

The grammar above provides for the optional inclusion of versions on both the header field itself (attached to the authserv-id token) and on each of the methods being reported. The method version refers to the method itself, which is specified in the documents describing those methods, while the authserv-id version refers to this document and thus the syntax of this header field.

上の文法では、ヘッダーフィールド自体（authserv-idトークンに付加される）と、報告される各方式の両方に、バージョンを任意で含めることができます。方式のバージョンは、その方式を説明する文書で規定される方式自体を指し、authserv-idのバージョンは、この文書、すなわちこのヘッダーフィールドの構文を指します。

The purpose of including these is to avoid misinterpretation of the results. That is, if a parser finds a version after an authserv-id that it does not explicitly know, it can immediately discontinue trying to parse, since what follows might not be in an expected format. For a method version, the parser SHOULD ignore a method result if the version is not supported in case the semantics of the result have a different meaning than what is expected. For example, if a hypothetical DKIM version 2 yielded a "pass" result for different reasons than version 1 does, a consumer of this field might not want to use the altered semantics. Allowing versions in the syntax is a way to indicate this and let the consumer of the header field decide.

これらを含める目的は、結果の誤解を避けることです。つまり、パーサーが、authserv-idの後に明示的には知らないバージョンを見つけた場合、後に続くものが想定された形式ではないかもしれないため、すぐに解析の試みを中止できます。方式のバージョンについては、結果のセマンティクスが想定とは異なる意味を持つ場合に備えて、パーサーは、バージョンがサポートされていない場合にはその方式の結果を無視すべきです（SHOULD）。たとえば、仮にDKIMのバージョン2が、バージョン1とは異なる理由で「pass」という結果を出すとしたら、このフィールドの消費者は、変更されたセマンティクスを使いたくないかもしれません。構文でバージョンを許可することは、これを示し、ヘッダーフィールドの消費者に判断させるための手段です。

2.7. 定義された方式と結果値

Verifiers SHOULD use these values as described below. 2.7.1. DKIM

2.7.1. DKIM

DKIM is represented by the "dkim" method and is defined in [DKIM].

DKIMは「dkim」方式で表され、[DKIM]で定義されています。

A signature is "acceptable to the ADMD" if it passes local policy checks (or there are no specific local policy checks). For example, an ADMD policy might require that the signature(s) on the message be added using the DNS domain present in the From header field of the message, thus making third-party signatures unacceptable even if they verify.

署名は、ローカルポリシーのチェックに合格した場合（または特定のローカルポリシーのチェックがない場合）に「ADMDにとって受け入れ可能」です。たとえば、ADMDのポリシーでは、メッセージの署名が、そのメッセージのFromヘッダーフィールドにあるDNSドメインを使って付加されていることを要求する場合があり、その場合、第三者の署名は、たとえ検証に合格しても受け入れられないことになります。

The DKIM result set is as follows:

DKIMの結果の集合は次のとおりです：

none:
The message was not signed.
pass:
The message was signed, the signature or signatures were acceptable to the ADMD, and the signature(s) passed verification tests.
fail:
The message was signed and the signature or signatures were acceptable to the ADMD, but they failed the verification test(s).
policy:
The message was signed, but some aspect of the signature or signatures was not acceptable to the ADMD.
neutral:
The message was signed, but the signature or signatures contained syntax errors or were not otherwise able to be processed. This result is also used for other failures not covered elsewhere in this list.
temperror:
The message could not be verified due to some error that is likely transient in nature, such as a temporary inability to retrieve a public key. A later attempt may produce a final result.
permerror:
The message could not be verified due to some error that is unrecoverable, such as a required header field being absent. A later attempt is unlikely to produce a final result.
none:
メッセージは署名されていませんでした。
pass:
メッセージは署名されており、その署名はADMDにとって受け入れ可能であり、署名は検証テストに合格しました。
fail:
メッセージは署名されており、その署名はADMDにとって受け入れ可能でしたが、検証テストに失敗しました。
policy:
メッセージは署名されていましたが、署名の何らかの側面がADMDにとって受け入れられませんでした。
neutral:
メッセージは署名されていましたが、署名に構文エラーが含まれていたか、そのほかの理由で処理できませんでした。この結果は、このリストのほかの箇所で扱われていない、そのほかの失敗にも使われます。
temperror:
公開鍵を一時的に取得できないなど、本質的に一時的である可能性が高いエラーのために、メッセージを検証できませんでした。後で試みれば最終的な結果が得られるかもしれません。
permerror:
必須のヘッダーフィールドが存在しないなど、回復不能なエラーのために、メッセージを検証できませんでした。後で試みても最終的な結果が得られる可能性は低いです。

DKIM results are reported using a ptype of "header". The property, however, represents one of the tags found in the DKIM-Signature header field rather than a distinct header field. For example, the ptype-property combination "header.d" refers to the content of the "d" (signing domain) tag from within the signature header field, and not a distinct header field called "d".

DKIMの結果は、「header」というptypeを使って報告されます。ただし、プロパティーは、個別のヘッダーフィールドではなく、DKIM-Signatureヘッダーフィールドにあるタグの1つを表します。たとえば、ptypeとプロパティーの組み合わせ「header.d」は、「d」という個別のヘッダーフィールドではなく、署名ヘッダーフィールド内の「d」（署名ドメイン）タグの内容を指します。

Note that in an EAI-formatted message, the values of the "d" and "i" properties can be expressed in UTF-8.

EAI形式のメッセージでは、「d」および「i」プロパティーの値をUTF-8で表現できることに注意してください。

In addition to previous registrations, this document registers the DKIM tags "a" (cryptographic algorithm used to sign the message) and "s" (selector) as reportable properties. These can be used to aid receivers during post-verification processing. In particular, [RFC8301] obsoleted use of the "rsa-sha1" algorithm in DKIM, so it is important to be able to distinguish such signatures from those using preferred algorithms.

以前の登録に加えて、この文書は、DKIMのタグ「a」（メッセージの署名に使われた暗号アルゴリズム）と「s」（セレクター）を報告可能なプロパティーとして登録します。これらは、受信者が検証後の処理を行う際に役立てることができます。特に、[RFC8301]はDKIMにおける「rsa-sha1」アルゴリズムの使用を廃止したため、そのような署名を、推奨されるアルゴリズムを使った署名と区別できることが重要です。

The ability to report different DKIM results for a message with multiple signatures is described in [RFC6008].

複数の署名を持つメッセージについて異なるDKIMの結果を報告する機能は、[RFC6008]で説明されています。

[DKIM] advises that if a message fails verification, it is to be treated as an unsigned message. A report of "fail" here permits the receiver of the report to decide how to handle the failure. A report of "neutral" or "none" preempts that choice, ensuring that the message will be treated as if it had not been signed.

[DKIM]は、メッセージが検証に失敗した場合、署名されていないメッセージとして扱うよう助言しています。ここで「fail」を報告すると、報告の受信者は、失敗をどのように処理するかを決めることができます。「neutral」や「none」を報告すると、その選択の余地がなくなり、メッセージは署名されていなかったかのように扱われることになります。

3. The "iprev" Authentication Method

3. 「iprev」認証方式

This section defines an additional authentication method called "iprev".

このセクションでは、「iprev」という追加の認証方式を定義します。

"iprev" is an attempt to verify that a client appears to be valid based on some DNS queries, which is to say that the IP address is explicitly associated with a domain name. Upon receiving a session initiation of some kind from a client, the IP address of the client peer is queried for matching names (i.e., a number-to-name translation, also known as a "reverse lookup" or a "PTR" record query). Once that result is acquired, a lookup of each of the names (i.e., a name-to-number translation, or an "A" or "AAAA" record query) thus retrieved is done. The response to this second check will typically result in at least one mapping back to the client's IP address.

「iprev」は、いくつかのDNSクエリーに基づいて、クライアントが正当であるように見えること、言い換えれば、IPアドレスがドメイン名に明示的に関連付けられていることを検証する試みです。クライアントから何らかのセッション開始を受け取ると、クライアントピアのIPアドレスについて、一致する名前をクエリーします（つまり、数値から名前への変換であり、「逆引き」や「PTR」レコードのクエリーとしても知られています）。その結果を取得したら、そうして得られた各名前の検索（つまり、名前から数値への変換、あるいは「A」や「AAAA」レコードのクエリー）を行います。この2回目のチェックに対するレスポンスでは、通常、少なくとも1つはクライアントのIPアドレスに戻るマッピングが得られます。

Expressed as an algorithm: If the client peer's IP address is I, the list of names to which I maps (after a "PTR" query) is the set N, and the union of IP addresses to which each member of N maps (after corresponding "A" and "AAAA" queries) is L, then this test is successful if I is an element of L.

アルゴリズムとして表すと次のようになります。クライアントピアのIPアドレスをI、（「PTR」クエリーの後に）Iが対応付けられる名前のリストを集合N、Nの各メンバーが（対応する「A」および「AAAA」クエリーの後に）対応付けられるIPアドレスの和集合をLとすると、IがLの要素であれば、このテストは成功です。

Often an MTA receiving a connection that fails this test will simply reject the connection using the enhanced status code defined in [AUTH-ESC]. If an operator instead wishes to make this information available to downstream agents as a factor in handling decisions, it records a result in accordance with Section 2.7.3.

多くの場合、このテストに失敗したコネクションを受信したMTAは、[AUTH-ESC]で定義されている拡張ステータスコードを使って、単にそのコネクションを拒否します。そうではなく、運用者がこの情報を処理の判断の一要素として下流のエージェントで利用できるようにしたい場合は、Section 2.7.3に従って結果を記録します。

The response to a "PTR" query could contain multiple names. To prevent heavy DNS loads, agents performing these queries MUST be implemented such that the number of names evaluated by generation of corresponding "A" or "AAAA" queries is limited so as not to be unduly taxing to the DNS infrastructure, though it MAY be configurable by an administrator. As an example, Section 4.6.4 of [SPF] chose a limit of 10 for its implementation of this algorithm.

「PTR」クエリーに対するレスポンスには、複数の名前が含まれていることがあります。DNSに大きな負荷がかかるのを防ぐため、これらのクエリーを実行するエージェントは、対応する「A」または「AAAA」クエリーを生成して評価する名前の数を、DNSインフラストラクチャーに過度な負担をかけないように制限するよう実装しなければなりません（MUST）。ただし、その制限は管理者が設定できるようにしてもよいです（MAY）。例として、[SPF]のセクション4.6.4は、このアルゴリズムの実装に対して10という制限を選択しました。

"DNS Extensions to Support IP Version 6" [DNS-IP6] discusses the query formats for the IPv6 case.

「DNS Extensions to Support IP Version 6」[DNS-IP6]では、IPv6の場合のクエリー形式について検討しています。

There is some contention regarding the wisdom and reliability of this test. For example, in some regions, it can be difficult for this test ever to pass because the practice of arranging to match the forward and reverse DNS is infrequently observed. Therefore, the precise implementation details of how a verifier performs an "iprev" test are not specified here. The verifier MAY report a successful or failed "iprev" test at its discretion having done some kind of check of the validity of the connection's identity using DNS. It is incumbent upon an agent making use of the reported "iprev" result to understand what exactly that particular verifier is attempting to report.

このテストの妥当性と信頼性については、いくらか議論があります。たとえば、一部の地域では、正引きと逆引きのDNSを一致させるように手配する慣行がほとんど見られないため、このテストが合格するのは難しいことがあります。したがって、検証者が「iprev」テストをどのように実行するかについての正確な実装の詳細は、ここでは規定しません。検証者は、DNSを使ってコネクションのアイデンティティーの正当性について何らかのチェックを行ったうえで、その裁量で「iprev」テストの成功または失敗を報告してもよいです（MAY）。報告された「iprev」の結果を利用するエージェントは、その特定の検証者が正確に何を報告しようとしているのかを理解する責任があります。

Extensive discussion of reverse DNS mapping and its implications can be found in "Considerations for the use of DNS Reverse Mapping" [DNSOP-REVERSE]. In particular, it recommends that applications avoid using this test as a means of authentication or security. Its presence in this document is not an endorsement but is merely acknowledgment that the method remains common and provides the means to relay the results of that test.

DNSの逆引きマッピングとその影響についての広範な検討は、「Considerations for the use of DNS Reverse Mapping」[DNSOP-REVERSE]にあります。特に、そこでは、アプリケーションが認証やセキュリティーの手段としてこのテストを使うのを避けることを推奨しています。この文書にこのテストが含まれているのは、それを支持するものではなく、単にこの方式が依然として一般的であることを認め、そのテストの結果を中継する手段を提供するものにすぎません。

4. Adding the Header Field to a Message

4. メッセージへのヘッダーフィールドの追加

This specification makes no attempt to evaluate the relative strengths of various message authentication methods that may become available. The methods listed are an order-independent set; their sequence does not indicate relative strength or importance of one method over another. Instead, the MUA or downstream filter consuming this header field is to interpret the result of each method based on its own knowledge of what that method evaluates.

この仕様は、利用可能になるかもしれないさまざまなメッセージ認証方式の相対的な強さを評価しようとはしません。列挙される方式は順序に依存しない集合であり、その順序は、ある方式のほかの方式に対する相対的な強さや重要性を示すものではありません。そうではなく、このヘッダーフィールドを消費するMUAや下流のフィルターが、各方式が何を評価するかについての自身の知識に基づいて、各方式の結果を解釈することになります。

Each "method" MUST refer to an authentication method declared in the IANA registry or an extension method as described in Section 2.7.6, and each "result" MUST refer to a result code declared in the IANA registry or an extension result code as defined in Section 2.7.7. See Section 6 for further information about the registered methods and result codes.

各「method」は、IANAレジストリーで宣言された認証方式か、Section 2.7.6で説明する拡張方式を参照しなければなりません（MUST）。また、各「result」は、IANAレジストリーで宣言された結果コードか、Section 2.7.7で定義する拡張結果コードを参照しなければなりません（MUST）。登録された方式と結果コードの詳細については、Section 6を参照してください。

An MTA compliant with this specification adds this header field (after performing one or more message authentication tests) to indicate which MTA or ADMD performed the test, which test was applied, and what the result was. If an MTA applies more than one such test, it adds this header field either once per test or once indicating all of the results. An MTA MUST NOT add a result to an existing header field.

この仕様に準拠したMTAは、（1つ以上のメッセージ認証テストを実行した後で）どのMTAまたはADMDがテストを実行したか、どのテストが適用されたか、その結果がどうであったかを示すために、このヘッダーフィールドを追加します。MTAがそのようなテストを複数適用する場合、このヘッダーフィールドをテストごとに1回追加するか、すべての結果を示すものを1回追加します。MTAは、既存のヘッダーフィールドに結果を追加してはなりません（MUST NOT）。

An MTA MAY add this header field containing only the authentication service identifier portion and the "none" token (see Section 2.2) to indicate explicitly that no message authentication schemes were applied prior to delivery of this message.

MTAは、このメッセージの配送前にメッセージ認証方式が適用されなかったことを明示的に示すために、認証サービス識別子の部分と「none」トークン（Section 2.2を参照）だけを含むこのヘッダーフィールドを追加してもよいです（MAY）。

An MTA adding this header field has to take steps to identify it as legitimate to the MUAs or downstream filters that will ultimately consume its content. One process to do so is described in Section 5. Further measures may be necessary in some environments. Some possible solutions are enumerated in Section 7.1. This document does not mandate any specific solution to this issue, as each environment has its own facilities and limitations.

このヘッダーフィールドを追加するMTAは、最終的にその内容を消費するMUAや下流のフィルターに対して、それが正当なものであると識別できるようにする手段を講じる必要があります。そのための1つの手順をSection 5で説明します。環境によっては、さらなる対策が必要になるかもしれません。考えられる解決策のいくつかをSection 7.1で列挙します。各環境にはそれぞれの設備や制限があるため、この文書では、この問題に対する特定の解決策を義務付けません。

Most known message authentication methods focus on a particular identifier to evaluate. SPF differs in that it can yield a result based on more than one identifier; specifically, SPF can evaluate the RFC5321.HELO parameter or the RFC5321.MailFrom parameter. When generating this field to report those results, only the parameter that yielded the result is included.

既知のメッセージ認証方式のほとんどは、評価する特定の識別子に焦点を当てています。SPFは、複数の識別子に基づいて結果を出せるという点で異なります。具体的には、SPFはRFC5321.HELOパラメーターまたはRFC5321.MailFromパラメーターを評価できます。それらの結果を報告するためにこのフィールドを生成するときは、結果を出したパラメーターだけを含めます。

For MTAs that add this header field, adding header fields in order (at the top), per Section 3.6 of [MAIL], is particularly important. Moreover, this header field SHOULD be inserted above any other trace header fields such MTAs might prepend. This placement allows easy detection of header fields that can be trusted.

このヘッダーフィールドを追加するMTAにとって、[MAIL]のセクション3.6に従って、ヘッダーフィールドを順番に（先頭に）追加することは特に重要です。さらに、このヘッダーフィールドは、そのようなMTAが先頭に追加するかもしれないほかのトレースヘッダーフィールドよりも上に挿入するべきです（SHOULD）。この配置により、信頼できるヘッダーフィールドを簡単に検出できます。

End users making direct use of this header field might inadvertently trust information that has not been properly vetted. If, for example, a basic SPF result were to be relayed that claims an authenticated addr-spec, the local-part of that addr-spec has actually not been authenticated. Thus, an MTA adding this header field SHOULD NOT include any data that have not been authenticated by the method(s) being applied. Moreover, MUAs SHOULD NOT render to users such information if it is presented by a method known not to authenticate it.

このヘッダーフィールドを直接利用するエンドユーザーは、適切に精査されていない情報をうっかり信頼してしまうかもしれません。たとえば、認証済みのaddr-specを主張する基本的なSPFの結果が中継されたとしても、そのaddr-specのローカル部は実際には認証されていません。したがって、このヘッダーフィールドを追加するMTAは、適用している方式によって認証されていないデータを含めるべきではありません（SHOULD NOT）。さらに、MUAは、そのような情報が、それを認証しないことがわかっている方式によって提示されている場合、それをユーザーに表示すべきではありません（SHOULD NOT）。

4.1. Header Field Position and Interpretation

4.1. ヘッダーフィールドの位置と解釈

In order to ensure non-ambiguous results and avoid the impact of false header fields, MUAs and downstream filters SHOULD NOT interpret this header field unless specifically configured to do so by the user or administrator. That is, this interpretation should not be "on by default". Naturally then, users or administrators ought not activate such a feature unless (1) they are certain the header field will be validly added by an agent within the ADMD that accepts the mail that is ultimately read by the MUA, and (2) instances of the header field that appear to originate within the ADMD but are actually added by foreign MTAs will be removed before delivery.

結果のあいまいさをなくし、偽のヘッダーフィールドによる影響を避けるため、MUAや下流のフィルターは、ユーザーまたは管理者によってそうするように明確に設定されていない限り、このヘッダーフィールドを解釈すべきではありません（SHOULD NOT）。つまり、この解釈は「デフォルトで有効」であるべきではありません。したがって当然ながら、ユーザーや管理者は、（1）最終的にMUAによって読まれるメールを受け付けるADMD内のエージェントによってこのヘッダーフィールドが正当に追加されること、および（2）ADMD内から発信されたように見えるが実際には外部のMTAによって追加されたこのヘッダーフィールドのインスタンスが配送前に削除されること、を確信できない限り、そのような機能を有効にすべきではありません。

Furthermore, MUAs and downstream filters SHOULD NOT interpret this header field unless the authentication service identifier of the header field is used within the ADMD as configured by the user or administrator.

さらに、MUAや下流のフィルターは、ヘッダーフィールドの認証サービス識別子が、ユーザーまたは管理者が設定したとおりにADMD内で使われているものでない限り、このヘッダーフィールドを解釈すべきではありません（SHOULD NOT）。

MUAs and downstream filters MUST ignore any result reported using a "result" not specified in the IANA "Result Code" registry or a "ptype" not listed in the "Email Authentication Property Types" registry for such values as defined in Section 6. Moreover, such agents MUST ignore a result indicated for any "method" they do not specifically support. The exception to this is experimental methods as discussed in Section 2.7.6.

MUAや下流のフィルターは、IANAの「Result Code」レジストリーで規定されていない「result」、またはSection 6で定義するそのような値のための「Email Authentication Property Types」レジストリーに掲載されていない「ptype」を使って報告された結果を、すべて無視しなければなりません（MUST）。さらに、そのようなエージェントは、具体的にサポートしていない「method」について示された結果を無視しなければなりません（MUST）。この例外は、Section 2.7.6で検討する実験的な方式です。

An MUA SHOULD NOT reveal these results to end users, absent careful "human factors" design considerations and testing, for the presentation of trust-related materials. For example, an attacker could register examp1e.com (note the digit "1" (one)) and send signed mail to intended victims; a verifier would detect that the signature was valid and report a "pass" even though it's clear the DNS domain name was intended to mislead. See Section 7.2 for further discussion.

MUAは、信頼に関わる情報の提示について、慎重な「ヒューマンファクター」の設計上の考慮とテストを行わない限り、これらの結果をエンドユーザーに明かすべきではありません（SHOULD NOT）。たとえば、攻撃者はexamp1e.com（数字の「1」（いち）に注意）を登録し、署名したメールを標的とする被害者に送信できます。検証者は署名が有効であることを検出し、そのDNSドメイン名が誤解を招くことを意図していたのは明らかであるにもかかわらず、「pass」を報告するでしょう。さらなる検討については、Section 7.2を参照してください。

As stated in Section 2.1, this header field MUST be treated as though it were a trace header field as defined in Section 3.6.7 of [MAIL] and hence MUST NOT be reordered and MUST be prepended to the message, so that there is generally some indication upon delivery of where in the chain of handling MTAs the message authentication was done.

Section 2.1で述べたように、このヘッダーフィールドは、[MAIL]のセクション3.6.7で定義されているトレースヘッダーフィールドであるかのように扱わなければなりません（MUST）。したがって、並べ替えてはなりません（MUST NOT）。また、メッセージの先頭に追加しなければなりません（MUST）。これにより、一般に、配送時に、処理を行ったMTAの連鎖のどこでメッセージ認証が行われたかについての何らかの手がかりが得られます。

Note that there are a few message handlers that are only capable of appending new header fields to a message. Strictly speaking, these handlers are not compliant with this specification. They can still add the header field to carry authentication details, but any signal about where in the handling chain the work was done may be lost. Consumers SHOULD be designed such that this can be tolerated, especially from a producer known to have this limitation.

メッセージに新しいヘッダーフィールドを末尾に追加することしかできないメッセージハンドラーもいくつか存在することに注意してください。厳密に言えば、これらのハンドラーはこの仕様に準拠していません。それでも認証の詳細を伝えるためにヘッダーフィールドを追加することはできますが、処理の連鎖のどこで作業が行われたかについての手がかりは失われるかもしれません。消費者は、特にこの制限があることがわかっている生成者からのものについて、これを許容できるように設計すべきです（SHOULD）。

MUAs SHOULD ignore instances of this header field discovered within message/rfc822 MIME attachments. They are likely to contain the results of authentication checks done in the past, possibly long ago, and have no contemporary value. Due caution therefore needs to be taken when choosing to consume them.

MUAは、message/rfc822のMIME添付の中で見つかったこのヘッダーフィールドのインスタンスを無視すべきです（SHOULD）。それらには、過去に、場合によってはずっと前に行われた認証チェックの結果が含まれている可能性が高く、現在の価値はありません。したがって、それらを消費することを選択する場合は、十分な注意が必要です。

Further discussion of these topics can be found in Section 7 below.

これらの話題のさらなる検討は、後述のSection 7にあります。

4.2. Local Policy Enforcement

4.2. ローカルポリシーの適用

Some sites have a local policy that considers any particular authentication policy's non-recoverable failure results (typically "fail" or similar) as justification for rejecting the message. In such cases, the border MTA SHOULD issue an SMTP rejection response to the message, rather than adding this header field and allowing the message to proceed toward delivery. This is more desirable than allowing the message to reach an internal host's MTA or spam filter, thus possibly generating a local rejection such as a Delivery Status Notification (DSN) [DSN] to a forged originator. Such generated rejections are colloquially known as "backscatter".

特定の認証ポリシーにおける回復不能な失敗の結果（通常は「fail」やそれに類するもの）を、メッセージを拒否する正当な理由とみなすローカルポリシーを持つサイトもあります。そのような場合、境界MTAは、このヘッダーフィールドを追加してメッセージを配送に向けて進めるのではなく、そのメッセージに対してSMTPの拒否レスポンスを発行すべきです（SHOULD）。これは、メッセージが内部ホストのMTAやスパムフィルターに到達するのを許し、その結果、偽造された発信者に対して配送状態通知（DSN）[DSN]のようなローカルな拒否を生成するかもしれないことよりも望ましいです。そのように生成された拒否は、俗に「バックスキャッター」として知られています。

The same MAY also be done for local policy decisions overriding the results of the authentication methods (e.g., the "policy" result codes described in Section 2.7).

認証方式の結果を上書きするローカルポリシーの判断（たとえば、Section 2.7で説明する「policy」結果コード）についても、同じことを行ってもよいです（MAY）。

Such rejections at the SMTP protocol level are not possible if local policy is enforced at the MUA and not the MTA.

ローカルポリシーがMTAではなくMUAで適用される場合、そのようなSMTPプロトコルレベルでの拒否はできません。

5. Removing Existing Header Fields

5. 既存のヘッダーフィールドの削除

To mitigate the impact of forged header fields, any MTA conforming to this specification MUST delete any discovered instance of this header field that claims, by virtue of its authentication service identifier, to have been added within its trust boundary but that did not come directly from another trusted MTA. For example, an MTA for example.com receiving a message MUST delete or otherwise obscure any instance of this header field bearing an authentication service identifier indicating that the header field was added within example.com prior to adding its own header fields. This could mean each internal MTA will need to be configured with a list of other known, trusted MTAs that are thus expected to be using that same identifier.

偽造されたヘッダーフィールドの影響を緩和するため、この仕様に準拠するMTAはすべて、その認証サービス識別子によって自身の信頼境界内で追加されたと主張しているが、ほかの信頼できるMTAから直接来たものではない、このヘッダーフィールドのインスタンスを見つけたら、それを削除しなければなりません（MUST）。たとえば、メッセージを受信したexample.comのMTAは、自身のヘッダーフィールドを追加する前に、そのヘッダーフィールドがexample.com内で追加されたことを示す認証サービス識別子を持つこのヘッダーフィールドのインスタンスを、すべて削除するか、そのほかの方法で見えなくしなければなりません（MUST）。これは、各内部MTAに、同じ識別子を使っていると想定される、既知の信頼できるほかのMTAのリストを設定する必要があることを意味するかもしれません。

In the case of EAI-formatted messages, this test is done after converting A-labels into U-labels.

EAI形式のメッセージの場合、このテストはAラベルをUラベルに変換した後で行います。

For simplicity and maximum security, a border MTA could remove all instances of this header field on mail crossing into its trust boundary. However, this may conflict with the desire to access authentication results performed by trusted external service providers. It may also invalidate signed messages whose signatures cover external instances of this header field. A more robust border MTA could allow a specific list of authenticating MTAs whose information is to be admitted, removing the header field originating from all others.

簡潔さと最大限のセキュリティーのために、境界MTAは、信頼境界に入ってくるメールにあるこのヘッダーフィールドのインスタンスをすべて削除することもできます。しかし、これは、信頼できる外部のサービスプロバイダーが実施した認証結果を利用したいという要望と衝突するかもしれません。また、署名がこのヘッダーフィールドの外部のインスタンスを対象としている署名付きメッセージを無効にするかもしれません。より堅牢な境界MTAは、情報を受け入れる認証MTAの特定のリストを許可し、それ以外のすべてから発信されたヘッダーフィールドを削除することもできます。

As stated in Section 1.2, a formal definition of "trust boundary" is deliberately not made here. It is entirely possible that a border MTA for example.com will explicitly trust authentication results asserted by upstream host example.net even though they exist in completely disjoint administrative boundaries. In that case, the border MTA MAY elect not to delete those results; moreover, the upstream host doing some authentication work could apply a signing technology such as [DKIM] on its own results to assure downstream hosts of their authenticity. An example of this is provided in Appendix B.

Section 1.2で述べたように、ここでは「信頼境界」の形式的な定義を意図的に行っていません。example.comの境界MTAが、まったく別の管理境界に存在するにもかかわらず、上流のホストexample.netによってアサートされた認証結果を明示的に信頼することも十分にあり得ます。その場合、境界MTAは、それらの結果を削除しないことを選択してもよいです（MAY）。さらに、何らかの認証作業を行う上流のホストは、下流のホストに対してその真正性を保証するために、[DKIM]などの署名技術を自身の結果に適用することもできます。この例をAppendix Bに示します。

Similarly, in the case of messages signed using [DKIM] or other message-signing methods that sign header fields, this removal action could invalidate one or more signatures on the message if they covered the header field to be removed. This behavior can be desirable, since there's little value in validating the signature on a message with forged header fields. However, signing agents MAY therefore elect to omit these header fields from signing to avoid this situation.

同様に、[DKIM]や、ヘッダーフィールドに署名するそのほかのメッセージ署名方式を使って署名されたメッセージの場合、削除されるヘッダーフィールドが署名の対象に含まれていれば、この削除動作によって、メッセージの1つ以上の署名が無効になる可能性があります。偽造されたヘッダーフィールドを持つメッセージの署名を検証することにはほとんど価値がないため、この振る舞いは望ましいこともあります。しかし、そのため署名エージェントは、この状況を避けるために、これらのヘッダーフィールドを署名の対象から外すことを選択してもよいです（MAY）。

An MTA SHOULD remove any instance of this header field bearing a version (express or implied) that it does not support. However, an MTA MUST remove such a header field if the SMTP connection [SMTP] relaying the message is not from a trusted internal MTA. (As discussed above, this too can result in invalidation of signatures.) This means the MTA needs to be able to understand versions of this header field at least as late as the ones understood by the MUAs or other consumers within its ADMD.

MTAは、サポートしていないバージョン（明示的か暗黙的かを問わない）を持つこのヘッダーフィールドのインスタンスを削除すべきです（SHOULD）。ただし、メッセージを中継しているSMTPコネクション[SMTP]が信頼できる内部MTAからのものでない場合、MTAはそのようなヘッダーフィールドを削除しなければなりません（MUST）（上で検討したように、これも署名の無効化につながる可能性があります）。これは、MTAが、少なくともそのADMD内のMUAやそのほかの消費者が理解するのと同じくらい新しいバージョンのこのヘッダーフィールドを理解できる必要があることを意味します。

7. Security Considerations

7. セキュリティーに関する考慮事項

The following security considerations apply when adding or processing the Authentication-Results header field:

Authentication-Resultsヘッダーフィールドを追加または処理する際には、次のセキュリティーに関する考慮事項が当てはまります：

7.1. Forged Header Fields

7.1. 偽造されたヘッダーフィールド

An MTA not applying the filtering discussed in Section 5 exposes MUAs to false conclusions based on forged header fields. A malicious user or agent could forge a header field using the DNS domain of a receiving ADMD as the authserv-id token in the value of the header field and, with the rest of the value, claim that the message was properly authenticated. The non-conformant MTA would fail to strip the forged header field, and the MUA could inappropriately trust it.

Section 5で検討したフィルタリングを適用しないMTAは、偽造されたヘッダーフィールドに基づく誤った結論にMUAをさらします。悪意のあるユーザーやエージェントは、受信するADMDのDNSドメインをヘッダーフィールドの値のauthserv-idトークンとして使ってヘッダーフィールドを偽造し、値の残りの部分で、そのメッセージが適切に認証されたと主張することができます。準拠していないMTAは偽造されたヘッダーフィールドを取り除くことができず、MUAはそれを不適切に信頼してしまうかもしれません。

For this reason, it is best not to have processing of the Authentication-Results header field enabled by default; instead, it should be ignored, at least for the purposes of enacting filtering decisions, unless specifically enabled by the user or administrator after verifying that the border MTA is compliant. It is acceptable to have an MUA aware of this specification but have an explicit list of hostnames whose Authentication-Results header fields are trustworthy; however, this list should initially be empty.

このため、Authentication-Resultsヘッダーフィールドの処理をデフォルトで有効にしないのが最善です。代わりに、境界MTAが準拠していることを確認した後でユーザーまたは管理者が明確に有効にしない限り、少なくともフィルタリングの判断を下す目的においては、このヘッダーフィールドは無視されるべきです。MUAにこの仕様を認識させつつ、Authentication-Resultsヘッダーフィールドが信用できるホスト名の明示的なリストを持たせることは許容されます。ただし、このリストは最初は空であるべきです。

Proposed alternative solutions to this problem were made some time ago and are listed below. To date, they have not been developed due to lack of demand but are documented here should the information be useful at some point in the future:

この問題に対する代替の解決策が少し前に提案されており、以下に列挙します。今のところ、需要がないために開発されてはいませんが、将来のある時点でこの情報が役立つかもしれないため、ここに記録しておきます：

  1. Possibly the simplest is a digital signature protecting the header field, such as using [DKIM], that can be verified by an MUA by using a posted public key. Although one of the main purposes of this document is to relieve the burden of doing message authentication work at the MUA, this only requires that the MUA learn a single authentication scheme even if a number of them are in use at the border MTA. Note that [DKIM] requires that the From header field be signed, although in this application, the signing agent (a trusted MTA) likely cannot authenticate that value, so the fact that it is signed should be ignored. Where the authserv-id is the ADMD's domain name, the authserv-id matching this valid internal signature's "d=" DKIM value is sufficient.
  2. Another would be a means to interrogate the MTA that added the header field to see if it is actually providing any message authentication services and saw the message in question, but this isn't especially palatable given the work required to craft and implement such a scheme.
  3. Yet another might be a method to interrogate the internal MTAs that apparently handled the message (based on Received header fields) to determine whether any of them conform to Section 5 of this memo. This, too, has potentially high barriers to entry.
  4. Extensions to [IMAP], [SMTP], and [POP3] could be defined to allow an MUA or filtering agent to acquire the authserv-id in use within an ADMD, thus allowing it to identify which Authentication-Results header fields it can trust.
  5. On the presumption that internal MTAs are fully compliant with Section 3.6 of [MAIL] and the compliant internal MTAs are using their own hostnames or the ADMD's DNS domain name as the authserv-id token, this header field should always appear above a Received header added by a trusted MTA. This can be used as a test for header field validity.
  1. おそらく最も簡単なのは、[DKIM]を使うなどして、ヘッダーフィールドを保護するデジタル署名を付け、MUAが公開された公開鍵を使ってそれを検証できるようにすることです。この文書の主な目的の1つはMUAでメッセージ認証作業を行う負担を軽減することですが、これは、境界MTAで多数の認証方式が使われていたとしても、MUAが単一の認証方式を習得することだけを必要とします。[DKIM]はFromヘッダーフィールドが署名されていることを要求しますが、この用途では、署名エージェント（信頼できるMTA）はおそらくその値を認証できないので、それが署名されているという事実は無視されるべきであることに注意してください。authserv-idがADMDのドメイン名である場合、authserv-idがこの有効な内部署名のDKIMの「d=」の値と一致すれば十分です。
  2. 別の方法としては、ヘッダーフィールドを追加したMTAに問い合わせて、そのMTAが実際に何らかのメッセージ認証サービスを提供していて、問題のメッセージを見たかどうかを確認する手段が考えられます。しかし、そのような方式を考案して実装するのに必要な作業を考えると、これは特に好ましいものではありません。
  3. さらに別の方法としては、（Receivedヘッダーフィールドに基づいて）メッセージを処理したと思われる内部MTAに問い合わせて、そのいずれかがこのメモのSection 5に準拠しているかどうかを判断する方法が考えられます。これも、導入の障壁が高くなる可能性があります。
  4. [IMAP]、[SMTP]、[POP3]の拡張を定義して、MUAやフィルタリングエージェントがADMD内で使用中のauthserv-idを取得できるようにし、それによってどのAuthentication-Resultsヘッダーフィールドを信頼できるかを識別できるようにすることもできます。
  5. 内部MTAが[MAIL]のセクション3.6に完全に準拠しており、準拠した内部MTAが自身のホスト名またはADMDのDNSドメイン名をauthserv-idトークンとして使っていると仮定すれば、このヘッダーフィールドは、信頼できるMTAによって追加されたReceivedヘッダーより常に上に現れるはずです。これを、ヘッダーフィールドの正当性のテストとして使うことができます。

Support for some of these is being considered for future work.

これらのいくつかのサポートは、将来の作業として検討されています。

In any case, a mechanism needs to exist for an MUA or filter to verify that the host that appears to have added the header field (a) actually did so and (b) is legitimately adding that header field for this delivery. Given the variety of messaging environments deployed today, consensus appears to be that specifying a particular mechanism for doing so is not appropriate for this document.

いずれにしても、MUAやフィルターが、ヘッダーフィールドを追加したと思われるホストが、（a）実際にそれを行ったこと、および（b）この配送のためにそのヘッダーフィールドを正当に追加していることを検証するメカニズムが存在する必要があります。今日展開されているメッセージング環境の多様さを考えると、そのための特定のメカニズムを規定することはこの文書にとって適切ではないというのが、コンセンサスであるようです。

Mitigation of the forged header field attack can also be accomplished by moving the authentication results data into metadata associated with the message. In particular, an SMTP extension [SMTP] could be established to communicate authentication results from the border MTA to intermediate and delivery MTAs; the latter of these could arrange to store the authentication results as metadata retrieved and rendered along with the message by an IMAP client [IMAP] aware of a similar extension in that protocol. The delivery MTA would be told to trust data via this extension only from MTAs it trusts, and border MTAs would not accept data via this extension from any source. There is no vector in such an arrangement for forgery of authentication data by an outside agent.

偽造されたヘッダーフィールドによる攻撃の緩和は、認証結果のデータを、メッセージに関連付けられたメタデータに移すことによっても達成できます。具体的には、境界MTAから中間MTAおよび配送MTAに認証結果を伝えるためのSMTP拡張[SMTP]を確立することができます。後者は、そのプロトコルの同様の拡張を認識しているIMAPクライアント[IMAP]によってメッセージとともに取得され表示されるメタデータとして、認証結果を保存するように手配できます。配送MTAには、信頼するMTAからのみこの拡張を介したデータを信頼するように指示し、境界MTAは、いかなる送信元からもこの拡張を介したデータを受け入れないようにします。そのような構成では、外部のエージェントが認証データを偽造する経路はありません。

7.2. Misleading Results

7.2. 誤解を招く結果

Until some form of service for querying the reputation of a sending agent is widely deployed, the existence of this header field indicating a "pass" does not render the message trustworthy. It is possible for an arriving piece of spam or other undesirable mail to pass checks by several of the methods enumerated above (e.g., a piece of spam signed using [DKIM] by the originator of the spam, which might be a spammer or a compromised system). In particular, this issue is not resolved by forged header field removal (discussed above).

送信エージェントの評判を問い合わせる何らかのサービスが広く展開されるまでは、「pass」を示すこのヘッダーフィールドが存在するからといって、そのメッセージが信用できることにはなりません。到着したスパムやそのほかの望ましくないメールが、上で列挙した方式のいくつかによるチェックに合格することもあり得ます（たとえば、スパムの発信者（スパマーや侵害されたシステムである可能性があります）によって[DKIM]を使って署名されたスパム）。特に、この問題は、（上で検討した）偽造されたヘッダーフィールドの削除によっては解決されません。

Hence, MUAs and downstream filters must take some care with use of this header even after possibly malicious headers are scrubbed.

したがって、MUAや下流のフィルターは、悪意がある可能性のあるヘッダーが取り除かれた後でも、このヘッダーの使用にはある程度注意する必要があります。

7.3. Header Field Position

7.3. ヘッダーフィールドの位置

Despite the requirements of [MAIL], header fields can sometimes be reordered en route by intermediate MTAs. The goal of requiring header field addition only at the top of a message is an acknowledgment that some MTAs do reorder header fields, but most do not. Thus, in the general case, there will be some indication of which MTAs (if any) handled the message after the addition of the header field defined here.

[MAIL]の要件にもかかわらず、ヘッダーフィールドは途中で中間MTAによって並べ替えられることがあります。ヘッダーフィールドの追加をメッセージの先頭に限るよう要求している目的は、一部のMTAはヘッダーフィールドを並べ替えるものの、ほとんどのMTAはそうしないという認識に基づくものです。したがって、一般的な場合、ここで定義するヘッダーフィールドが追加された後で、どのMTAが（もしあれば）メッセージを処理したかについて、何らかの手がかりがあるでしょう。

7.4. Reverse IP Query Denial-of-Service Attacks

7.4. 逆引きIPクエリーによるサービス拒否攻撃

Section 4.6.4 of [SPF] observes that limits are necessary on recursive evaluations of SPF records in order to avoid abuse of or attacks on the DNS when verifying arriving client connections. A verifier wishing to do this check and report this information needs to take care not to go to unbounded lengths to resolve "A" and "PTR" queries. MUAs or other filters making use of an "iprev" result specified by this document need to be aware of the algorithm used by the verifier reporting the result and, especially, its limitations.

[SPF]のセクション4.6.4では、到着したクライアントのコネクションを検証する際にDNSの悪用やDNSへの攻撃を避けるために、SPFレコードの再帰的な評価に制限が必要であると述べています。このチェックを行い、この情報を報告しようとする検証者は、「A」や「PTR」のクエリーを解決するために際限なく手間をかけないように注意する必要があります。この文書で規定する「iprev」の結果を利用するMUAやそのほかのフィルターは、結果を報告する検証者が使用するアルゴリズムと、特にその制限を認識しておく必要があります。

7.5. Mitigation of Backscatter

7.5. バックスキャッターの緩和

Failing to follow the instructions of Section 4.2 can result in a denial-of-service attack caused by the generation of DSN messages [DSN] (or equivalent) to addresses that did not send the messages being rejected.

Section 4.2の指示に従わないと、拒否されるメッセージを送信していないアドレスに対してDSNメッセージ[DSN]（またはそれに相当するもの）が生成されることによるサービス拒否攻撃につながる可能性があります。

7.6. Internal MTA Lists

7.6. 内部MTAのリスト

Section 5 describes a procedure for scrubbing header fields that may contain forged authentication results about a message. A compliant installation will have to include, at each MTA, a list of other MTAs known to be compliant and trustworthy. Failing to keep this list current as internal infrastructure changes may expose an ADMD to attack.

Section 5では、メッセージに関する偽造された認証結果を含んでいるかもしれないヘッダーフィールドを取り除く手順について説明しています。準拠したインストールでは、各MTAに、準拠していて信用できることがわかっているほかのMTAのリストを含める必要があります。内部インフラストラクチャーの変化に合わせてこのリストを最新に保たないと、ADMDが攻撃にさらされる可能性があります。

7.7. Attacks against Authentication Methods

7.7. 認証方式に対する攻撃

If an attack against an authentication method becomes known, clearly then the agent verifying that method can be fooled into thinking an inauthentic message is authentic, and thus the value of this header field can be misleading. It follows that any attack against the authentication methods supported by this document is also a security consideration here.

認証方式に対する攻撃が知られるようになれば、明らかに、その方式を検証するエージェントはだまされて、真正でないメッセージを真正なものと思い込む可能性があり、したがってこのヘッダーフィールドの値は誤解を招くものになり得ます。したがって、この文書がサポートする認証方式に対するあらゆる攻撃は、ここでのセキュリティーに関する考慮事項でもあります。

7.8. Intentionally Malformed Header Fields

7.8. 意図的に不正な形式にされたヘッダーフィールド

As with any other header field found in the message, it is possible for an attacker to add an Authentication-Results header field that is extraordinarily large or otherwise malformed in an attempt to discover or exploit weaknesses in header field parsing code. Implementers must thoroughly verify all such header fields received from MTAs and be robust against intentionally as well as unintentionally malformed header fields.

メッセージにあるほかのヘッダーフィールドと同様に、攻撃者は、ヘッダーフィールドを解析するコードの弱点を発見したり悪用したりしようとして、極端に大きい、あるいはそのほかの点で不正な形式のAuthentication-Resultsヘッダーフィールドを追加することができます。実装者は、MTAから受信したそのようなヘッダーフィールドをすべて徹底的に検証し、意図的なものであれ意図的でないものであれ、不正な形式のヘッダーフィールドに対して堅牢である必要があります。

7.9. Compromised Internal Hosts

7.9. 侵害された内部ホスト

An internal MUA or MTA that has been compromised could generate mail with a forged From header field and a forged Authentication-Results header field that endorses it. Although it is clearly a larger concern to have compromised internal machines than it is to prove the value of this header field, this risk can be mitigated by arranging that internal MTAs will remove this header field if it claims to have been added by a trusted border MTA (as described above), yet the SMTP connection [SMTP] is not coming from an internal machine known to be running an authorized MTA. However, in such a configuration, legitimate MTAs will have to add this header field when legitimate internal-only messages are generated. This is also covered in Section 5.

侵害された内部のMUAやMTAは、偽造されたFromヘッダーフィールドと、それを保証する偽造されたAuthentication-Resultsヘッダーフィールドを持つメールを生成するかもしれません。内部のマシンが侵害されることは、このヘッダーフィールドの価値を証明することよりも明らかに大きな懸念事項ですが、信頼できる境界MTAによって追加されたと主張しているにもかかわらず（上で説明したように）、SMTPコネクション[SMTP]が認可されたMTAを実行していることがわかっている内部のマシンから来ていない場合には、内部MTAがこのヘッダーフィールドを削除するように手配することで、このリスクを緩和できます。ただし、そのような構成では、正当な内部専用のメッセージが生成されたときに、正当なMTAがこのヘッダーフィールドを追加する必要があります。これについてはSection 5でも扱っています。

7.10. Encapsulated Instances

7.10. カプセル化されたインスタンス

MIME messages can contain attachments of type "message/rfc822", which contain other messages. Such an encapsulated message can also contain an Authentication-Results header field. Although the processing of these is outside of the intended scope of this document (see Section 1.3), some simple guidance to MUA developers is appropriate here.

MIMEメッセージには、ほかのメッセージを含む「message/rfc822」タイプの添付が含まれることがあります。そのようなカプセル化されたメッセージにも、Authentication-Resultsヘッダーフィールドが含まれていることがあります。これらの処理は、この文書が意図する範囲外ですが（Section 1.3を参照）、MUA開発者に向けた簡単なガイダンスをここで示すのが適切です。

Since MTAs are generally unlikely to strip Authentication-Results header fields during mailbox delivery, normative language exists in Section 4.1 cautioning MUAs to ignore such instances within MIME attachments, as might be included when a message is forwarded. Moreover, when extracting a message digest to separate mail store messages or other media, such header fields should be removed so that they will never be interpreted improperly by MUAs that might later consume them.

MTAが一般にメールボックスへの配送時にAuthentication-Resultsヘッダーフィールドを取り除く可能性は低いため、Section 4.1には、メッセージが転送されるときに含まれるかもしれない、MIME添付内のそのようなインスタンスを無視するようMUAに注意を促す規範的な文言があります。さらに、メッセージダイジェストを抽出して別々のメールストアのメッセージやそのほかのメディアにするときには、後でそれらを消費するかもしれないMUAによって不適切に解釈されることが決してないように、そのようなヘッダーフィールドを削除すべきです。

There can be cases where these header fields included as part of encapsulated messages might actually be of value, such as when they are taken from messages within the same ADMD where they will be consumed. Caution must be taken to ensure that the consumer fully understands the semantics of what the header field is indicating and the message's handling history before ascribing any value, positive or negative, to such data.

カプセル化されたメッセージの一部として含まれるこれらのヘッダーフィールドが、実際に価値を持つ場合もあり得ます。たとえば、それらが消費されるのと同じADMD内のメッセージから取られた場合などです。そのようなデータに肯定的であれ否定的であれ何らかの価値を認める前に、消費者がそのヘッダーフィールドが示しているもののセマンティクスとメッセージの処理履歴を十分に理解していることを確認するよう注意する必要があります。

7.11. Reverse Mapping

7.11. 逆引きマッピング

Although Section 3 of this memo includes explicit support for the "iprev" method, its value as an authentication mechanism is limited. Implementers of both this specification and agents that use the data it relays are encouraged to become familiar with the issues raised by [DNSOP-REVERSE] when deciding whether or not to include support for "iprev".

このメモのSection 3には「iprev」方式の明示的なサポートが含まれていますが、認証メカニズムとしてのその価値は限られています。この仕様の実装者と、それが中継するデータを使うエージェントの実装者はどちらも、「iprev」のサポートを含めるかどうかを決める際に、[DNSOP-REVERSE]で提起されている問題をよく理解しておくことが推奨されます。

Appendix A. Legacy MUAs

Appendix A. レガシーなMUA

Implementers of this specification should be aware that many MUAs are unlikely to be retrofitted to support the Authentication-Results header field and its semantics. In the interests of convenience and quicker adoption, a delivery MTA might want to consider adding things that are processed by existing MUAs in addition to the Authentication-Results header field. One suggestion is to include a Priority header field, on messages that don't already have such a header field, containing a value that reflects the strength of the authentication that was accomplished, e.g., "low" for weak or no authentication, "normal" or "high" for good or strong authentication.

この仕様の実装者は、多くのMUAがAuthentication-Resultsヘッダーフィールドとそのセマンティクスをサポートするように改修される可能性は低いことを認識しておくべきです。利便性と導入の迅速化のために、配送MTAは、Authentication-Resultsヘッダーフィールドに加えて、既存のMUAが処理するものを追加することを検討したいと思うかもしれません。1つの提案は、まだそのようなヘッダーフィールドを持たないメッセージに、達成された認証の強さを反映する値、たとえば、弱い認証または認証なしなら「low」、良好または強力な認証なら「normal」や「high」を含むPriorityヘッダーフィールドを含めることです。

Some modern MUAs can already filter based on the content of this header field. However, there is keen interest in having MUAs make some kind of graphical representation of this header field's meaning to end users. Until this capability is added (i.e., while this specification and its successors continue to be adopted), other interim means of conveying authentication results may be necessary.

最近のMUAの中には、このヘッダーフィールドの内容に基づいてすでにフィルタリングできるものもあります。しかし、MUAがこのヘッダーフィールドの意味をエンドユーザーに対して何らかのグラフィカルな形で表現することには強い関心があります。この機能が追加されるまでは（つまり、この仕様とその後継の仕様の採用が続いている間は）、認証結果を伝えるためのほかの暫定的な手段が必要になるかもしれません。

Example 6: Headers Reporting Results from Multiple MTAs in Different ADMDs

例6：異なるADMDの複数のMTAからの結果を報告するヘッダー

In this example, we see multi-tiered authentication with an extended trust boundary.

この例では、拡張された信頼境界による多層の認証を見ていきます。

The message was sent from someone at example.com's New York office (newyork.example.com) to a mailing list managed at an intermediary. The message was signed at the origin using DKIM.

メッセージは、example.comのニューヨークオフィス（newyork.example.com）にいる誰かから、仲介者が管理するメーリングリストに送信されました。メッセージは、発信元でDKIMを使って署名されました。

The message was sent to a mailing list service provider called "example.net", which is used by example.com. There, meetings@example.net is expanded to a long list of recipients, one of whom is at the Chicago office. In this example, we will assume that the trust boundary for chicago.example.com includes the mailing list server at example.net.

メッセージは、example.comが利用している「example.net」というメーリングリストのサービスプロバイダーに送信されました。そこで、meetings@example.netが受信者の長いリストに展開され、そのうちの1人がシカゴオフィスにいます。この例では、chicago.example.comの信頼境界には、example.netのメーリングリストサーバーが含まれていると仮定します。

The mailing list server there first authenticated the message and affixed an Authentication-Results header field indicating such using its DNS domain name for the authserv-id. It then altered the message by affixing some footer text to the body, including some administrivia such as unsubscription instructions. Finally, the mailing list server affixes a second DKIM signature and begins distribution of the message.

そこのメーリングリストサーバーは、まずメッセージを認証し、自身のDNSドメイン名をauthserv-idとして使って、その旨を示すAuthentication-Resultsヘッダーフィールドを付加しました。次に、購読解除の手順などの管理的な情報を含むフッターテキストを本文に付加して、メッセージを変更しました。最後に、メーリングリストサーバーは2つ目のDKIM署名を付加し、メッセージの配布を開始します。

The border MTA for chicago.example.com explicitly trusts results from mail-router.example.net, so that header field is not removed. It performs evaluation of both signatures and determines that the first (most recent) is a "pass" but, because of the aforementioned modifications, the second is a "fail". However, the first signature included the Authentication-Results header added at mail-router.example.net that validated the second signature. Thus, indirectly, it can be determined that the authentications claimed by both signatures are indeed valid.

chicago.example.comの境界MTAは、mail-router.example.netからの結果を明示的に信頼しているため、そのヘッダーフィールドは削除されません。境界MTAは両方の署名を評価し、1つ目（最も新しいもの）は「pass」ですが、前述の変更のため、2つ目は「fail」であると判断します。しかし、1つ目の署名は、2つ目の署名を検証した、mail-router.example.netで追加されたAuthentication-Resultsヘッダーを対象に含んでいました。したがって、間接的に、両方の署名によって主張された認証が確かに有効であると判断できます。

Note that two styles of presenting metadata about the result are in use here. In one case, the "reason=" clause is present, which is intended for easy extraction by parsers; in the other case, the CFWS production of the ABNF is used to include such data as a header field comment. The latter can be harder for parsers to extract given the varied supported syntaxes of mail header fields.

ここでは、結果に関するメタデータを提示する2つのスタイルが使われていることに注意してください。一方では、パーサーが簡単に抽出できることを意図した「reason=」句が存在します。もう一方では、ABNFのCFWS生成規則を使って、そのようなデータをヘッダーフィールドのコメントとして含めています。後者は、メールのヘッダーフィールドでサポートされている構文がさまざまであることを考えると、パーサーが抽出するのは難しくなる可能性があります。

Appendix C. Operational Considerations about Message Authentication

Appendix C. メッセージ認証に関する運用上の考慮事項

Implementation of the Authentication-Results header field is predicated on the idea that authentication (and presumably in the future, reputation) work is typically done by border MTAs rather than MUAs or intermediate MTAs; the latter merely make use of the results determined by the former. Certainly this is not mandatory for participation in electronic mail or message authentication, but this header field and its deployment to date are based on that model. The assumption satisfies several common ADMD requirements:

Authentication-Resultsヘッダーフィールドの実装は、認証（そしておそらく将来的には評判）の作業は通常、MUAや中間MTAではなく境界MTAによって行われ、後者は前者によって決定された結果を利用するだけである、という考え方を前提としています。もちろん、これは電子メールやメッセージ認証に参加するための必須条件ではありませんが、このヘッダーフィールドとこれまでのその展開は、そのモデルに基づいています。この前提は、ADMDの一般的な要件のいくつかを満たします：

  1. Service operators prefer to resolve the handling of problem messages as close to the border of the ADMD as possible. This enables, for example, rejection of messages at the SMTP level rather than generating a DSN internally. Thus, doing any of the authentication or reputation work exclusively at the MUA or intermediate MTA renders this desire unattainable.
  2. Border MTAs are more likely to have direct access to external sources of authentication or reputation information, since modern MUAs inside of an ADMD are more likely to be heavily firewalled. Thus, some MUAs might not even be able to complete the task of performing authentication or reputation evaluations without complex proxy configurations or similar burdens.
  3. MUAs rely upon the upstream MTAs within their trust boundaries to make correct (as much as is possible) evaluations about the message's envelope, header, and content. Thus, MUAs don't need to know how to do the work that upstream MTAs do; they only need the results of that work.
  4. Evaluations about the quality of a message, from simple token matching (e.g., a list of preferred DNS domains) to cryptographic verification (e.g., public/private key work), do have a cost and thus need to be minimized. To that end, performing those tests at the border MTA is far preferred to doing that work at each MUA that handles a message. If an ADMD's environment adheres to common messaging protocols, a reputation query or an authentication check performed by a border MTA would return the same result as the same query performed by an MUA. By contrast, in an environment where the MUA does the work, a message arriving for multiple recipients would thus cause authentication or reputation evaluation to be done more than once for the same message (i.e., at each MUA), causing needless amplification of resource use and creating a possible denial-of-service attack vector.
  5. Minimizing change is good. As new authentication and reputation methods emerge, the list of methods supported by this header field would presumably be extended. If MUAs simply consume the contents of this header field rather than actually attempt to do authentication and/or reputation work, then MUAs only need to learn to parse this header field once; emergence of new methods requires only a configuration change at the MUAs and software changes at the MTAs (which are presumably fewer in number). When choosing to implement these functions in MTAs vs. MUAs, the issues of individual flexibility, infrastructure inertia, and scale of effort must be considered. It is typically easier to change a single MUA than an MTA because the modification affects fewer users and can be pursued with less care. However, changing many MUAs is more effort than changing a smaller number of MTAs.
  6. For decisions affecting message delivery and display, assessment based on authentication and reputation is best performed close to the time of message transit, as a message makes its journey toward a user's inbox, not afterwards. DKIM keys, IP address reputations, etc., can change over time or even become invalid, and users can take a long time to read a message once delivered. The value of this work thus degrades, perhaps quickly, once the delivery process has completed. This seriously diminishes the value of this work when done elsewhere than at MTAs.
  1. サービスの運用者は、問題のあるメッセージの処理を、できるだけADMDの境界の近くで解決することを好みます。これにより、たとえば、内部でDSNを生成するのではなく、SMTPレベルでメッセージを拒否できます。したがって、認証や評判の作業をMUAや中間MTAだけで行うと、この要望は実現できなくなります。
  2. 最近のADMD内部のMUAは厳重にファイアウォールで保護されている可能性が高いため、境界MTAの方が、認証や評判の情報の外部ソースに直接アクセスできる可能性が高いです。したがって、一部のMUAは、複雑なプロキシーの設定やそれに類する負担なしには、認証や評判の評価を実行するタスクを完了することさえできないかもしれません。
  3. MUAは、メッセージのエンベロープ、ヘッダー、内容について（可能な限り）正しい評価を行うことを、自身の信頼境界内にある上流のMTAに頼っています。したがって、MUAは上流のMTAが行う作業のやり方を知る必要はなく、その作業の結果だけが必要です。
  4. 単純なトークンの照合（たとえば、優先するDNSドメインのリスト）から暗号による検証（たとえば、公開鍵/秘密鍵の作業）まで、メッセージの品質に関する評価には確かにコストがかかるため、最小限に抑える必要があります。そのためには、メッセージを処理する各MUAでその作業を行うよりも、境界MTAでそれらのテストを実行する方がはるかに望ましいです。ADMDの環境が一般的なメッセージングプロトコルに準拠していれば、境界MTAが実行した評判のクエリーや認証チェックは、MUAが実行した同じクエリーと同じ結果を返すでしょう。対照的に、MUAが作業を行う環境では、複数の受信者宛てに到着したメッセージによって、同じメッセージに対して認証や評判の評価が（つまり各MUAで）複数回行われることになり、リソースの使用が不必要に増幅され、サービス拒否攻撃の経路を生み出す可能性があります。
  5. 変更を最小限にすることは良いことです。新しい認証方式や評判の方式が登場するにつれて、このヘッダーフィールドがサポートする方式のリストはおそらく拡張されるでしょう。MUAが実際に認証や評判の作業を試みるのではなく、単にこのヘッダーフィールドの内容を消費するのであれば、MUAはこのヘッダーフィールドの解析方法を一度学ぶだけで済みます。新しい方式が登場しても、MUAでの設定変更と、（おそらく数が少ない）MTAでのソフトウェアの変更が必要になるだけです。これらの機能をMTAとMUAのどちらで実装するかを選択する際には、個々の柔軟性、インフラストラクチャーの慣性、作業の規模といった問題を考慮しなければなりません。一般に、単一のMUAを変更する方が、MTAを変更するよりも簡単です。変更が影響するユーザーが少なく、それほど慎重に進める必要がないからです。しかし、多数のMUAを変更するのは、少数のMTAを変更するよりも手間がかかります。
  6. メッセージの配送や表示に影響する判断のためには、認証と評判に基づく評価は、メッセージがユーザーの受信箱に向かう途中で、メッセージの転送時刻に近いうちに行うのが最善であり、その後ではありません。DKIMの鍵やIPアドレスの評判などは、時間とともに変化したり、無効になったりすることさえあり、ユーザーは配送されたメッセージを読むまでに長い時間がかかることがあります。したがって、この作業の価値は、配送プロセスが完了すると、おそらく急速に低下します。このことは、この作業をMTA以外の場所で行った場合、その価値を著しく損ないます。

Many operational choices are possible within an ADMD, including the venue for performing authentication and/or reputation assessment. The current specification does not dictate any of those choices. Rather, it facilitates those cases in which information produced by one stage of analysis needs to be transported with the message to the next stage.

ADMD内では、認証や評判の評価を行う場所を含め、多くの運用上の選択が可能です。この仕様は、それらの選択のいずれも指示しません。むしろ、分析のある段階で生成された情報をメッセージとともに次の段階に運ぶ必要がある場合を容易にするものです。
