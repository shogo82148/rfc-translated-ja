RFC 8100

Diffserv-Interconnection Classes and Practice

RFC 8100

Diffserv相互接続のクラスと実践

Abstract

概要

This document defines a limited common set of Diffserv Per-Hop Behaviors (PHBs) and Diffserv Codepoints (DSCPs) to be applied at (inter)connections of two separately administered and operated networks, and it explains how this approach can simplify network configuration and operation. Many network providers operate Multiprotocol Label Switching (MPLS) using Treatment Aggregates for traffic marked with different Diffserv Per-Hop Behaviors and use MPLS for interconnection with other networks. This document offers a simple interconnection approach that may simplify operation of Diffserv for network interconnection among providers that use MPLS and apply the Short Pipe Model. While motivated by the requirements of MPLS network operators that use Short Pipe Model tunnels, this document is applicable to other networks, both MPLS and non-MPLS.

この文書は、個別に管理・運用されている2つのネットワークの（相互）接続点で適用する、Diffservのホップごとの振る舞い（Per-Hop Behavior、PHB）とDiffservコードポイント（DSCP）の限定された共通セットを定義し、このアプローチによってネットワークの設定と運用をどのように簡素化できるかを説明します。多くのネットワークプロバイダーは、異なるDiffservのホップごとの振る舞いでマークされたトラフィックに対して処理集約（Treatment Aggregate）を使用してマルチプロトコルラベルスイッチング（MPLS）を運用し、ほかのネットワークとの相互接続にMPLSを使用しています。この文書は、MPLSを使用してショートパイプモデルを適用するプロバイダー間のネットワーク相互接続において、Diffservの運用を簡素化できるシンプルな相互接続のアプローチを提供します。この文書は、ショートパイプモデルのトンネルを使用するMPLSネットワーク運用者の要件を動機としていますが、MPLSと非MPLSの両方のほかのネットワークにも適用できます。

1. Introduction

1. はじめに

Diffserv has been deployed in many networks; it provides differentiated traffic forwarding based on the Diffserv Codepoint (DSCP) field, which is part of the IP header [RFC2474]. This document defines a set of common Diffserv classes (Per-Hop Behaviors (PHBs)) and codepoints for use at interconnection points to which and from which locally used classes and codepoints should be mapped.

Diffservは多くのネットワークで展開されています。Diffservは、IPヘッダーの一部であるDiffservコードポイント（DSCP）フィールド[RFC2474]に基づいて、差別化されたトラフィック転送を提供します。この文書は、相互接続点で使用する共通のDiffservクラス（ホップごとの振る舞い（Per-Hop Behavior、PHB））とコードポイントのセットを定義します。ローカルで使用されるクラスとコードポイントは、相互接続点においてこれらとの間で対応付けられるべきです。

As described by Section 2.3.4.2 of [RFC2475], the re-marking of packets at domain boundaries is a Diffserv feature. If traffic marked with unknown or unexpected DSCPs is received, [RFC2474] recommends forwarding that traffic with default (best-effort) treatment without changing the DSCP markings to better support incremental Diffserv deployment in existing networks as well as with routers that do not support Diffserv or are not configured to support it. Many networks do not follow this recommendation and instead re-mark unknown or unexpected DSCPs to zero upon receipt for default (best-effort) forwarding in accordance with the guidance in [RFC2475] to ensure that appropriate DSCPs are used within a Diffserv domain. This document is based on the latter approach and defines additional DSCPs that are known and expected at network interconnection interfaces in order to reduce the amount of traffic whose DSCPs are re-marked to zero.

[RFC2475]のセクション2.3.4.2で説明されているように、ドメイン境界でのパケットの再マーキングはDiffservの機能の1つです。未知または予期しないDSCPでマークされたトラフィックを受信した場合について、[RFC2474]は、既存のネットワークへのDiffservの段階的な展開や、Diffservをサポートしていない、またはサポートするように設定されていないルーターとの共存をよりよくサポートするために、DSCPのマーキングを変更せずにデフォルト（ベストエフォート）の処理でそのトラフィックを転送することを推奨しています。多くのネットワークはこの推奨に従わず、代わりに、Diffservドメイン内で適切なDSCPが使用されることを保証するために、[RFC2475]のガイダンスに従って、未知または予期しないDSCPを受信時に0に再マークし、デフォルト（ベストエフォート）の転送を行います。この文書は後者のアプローチに基づいており、DSCPが0に再マークされるトラフィックの量を減らすために、ネットワーク相互接続インターフェイスで既知かつ想定されるDSCPを追加で定義します。

This document is motivated by requirements for IP network interconnection with Diffserv support among providers that operate Multiprotocol Label Switching (MPLS) in their backbones, but it is also applicable to other technologies. The operational simplifications and methods in this document help align IP Diffserv functionality with MPLS limitations resulting from the widely deployed Short Pipe Model for MPLS tunnel operation [RFC3270]. Further, limiting Diffserv to a small number of Treatment Aggregates can enable network traffic to leave a network with the DSCP value with which it was received, even if a different DSCP is used within the network, thus providing an opportunity to extend consistent Diffserv treatment across network boundaries.

この文書は、バックボーンでマルチプロトコルラベルスイッチング（MPLS）を運用しているプロバイダー間での、DiffservをサポートするIPネットワーク相互接続の要件を動機としていますが、ほかの技術にも適用できます。この文書の運用上の簡素化と手法は、MPLSトンネル運用のために広く展開されているショートパイプモデル[RFC3270]に起因するMPLSの制限に、IP Diffservの機能を合わせるのに役立ちます。さらに、Diffservを少数の処理集約に限定することで、ネットワーク内で異なるDSCPが使用されていても、ネットワークトラフィックが受信時のDSCP値でネットワークから出ていけるようになり、ネットワーク境界を越えて一貫したDiffservの扱いを広げる機会が得られます。

In isolation, use of a defined set of interconnection PHBs and DSCPs may appear to be additional effort for a network operator. The primary offsetting benefit is that mapping from or to the interconnection PHBs and DSCPs is specified once for all of the interconnections to other networks that can use this approach. Absent this approach, the PHBs and DSCPs have to be negotiated and configured independently for each network interconnection, which has poor administrative and operational scaling properties. Further, consistent end-to-end Diffserv treatment is more likely to result when an interconnection codepoint scheme is used because traffic is re-marked to the same DSCPs at all network interconnections.

相互接続用に定義されたPHBとDSCPのセットを使用することは、それだけを見るとネットワーク運用者にとって追加の手間に見えるかもしれません。それを相殺する主な利点は、相互接続用のPHBとDSCPとの間の対応付けを、このアプローチを使用できるほかのネットワークとのすべての相互接続に対して一度だけ規定すればよいことです。このアプローチがなければ、PHBとDSCPをネットワーク相互接続ごとに個別に交渉して設定しなければならず、管理上も運用上もスケーラビリティーに劣ります。さらに、相互接続用のコードポイント方式を使用すると、すべてのネットワーク相互接続でトラフィックが同じDSCPに再マークされるため、エンドツーエンドで一貫したDiffservの扱いが得られる可能性が高くなります。

The interconnection approach described in this document (referred to as "Diffserv-Intercon") uses a set of PHBs (mapped to four corresponding MPLS Treatment Aggregates) along with a set of interconnection DSCPs allowing straightforward rewriting to domain-internal DSCPs and defined DSCP markings for traffic forwarded to interconnected domains. The solution described here can be used in other contexts benefiting from a defined Diffserv interconnection interface.

この文書で説明する相互接続のアプローチ（「Diffserv-Intercon」と呼びます）は、（対応する4つのMPLS処理集約に対応付けられる）PHBのセットと、相互接続用のDSCPのセットを使用します。これにより、ドメイン内部のDSCPへの簡単な書き換えが可能になり、相互接続されたドメインに転送されるトラフィックのDSCPマーキングが定まります。ここで説明する解決策は、定義されたDiffserv相互接続インターフェイスの恩恵を受けるほかの文脈でも使用できます。

The basic idea is that traffic sent with a Diffserv-Intercon PHB and DSCP is restored to that PHB and DSCP at each network interconnection, even though a different PHB and DSCP may be used within each network involved. The key requirement is that the network ingress interconnect DSCP be restored at the network egress, and a key observation is that this is only feasible in general for a small number of DSCPs. Traffic sent with other DSCPs can be re-marked to an interconnect DSCP or dealt with via an additional agreement(s) among the operators of the interconnected networks; use of the MPLS Short Pipe Model favors re-marking unexpected DSCPs to zero in the absence of an additional agreement(s), as explained further in this document.

基本的な考え方は、Diffserv-InterconのPHBとDSCPで送信されたトラフィックは、関係する各ネットワーク内では異なるPHBとDSCPが使用されることがあっても、各ネットワーク相互接続でそのPHBとDSCPに復元されるというものです。重要な要件は、ネットワークのイングレスでの相互接続DSCPがネットワークのイグレスで復元されることであり、重要な観察は、これが一般に少数のDSCPに対してのみ実現可能であるということです。ほかのDSCPで送信されたトラフィックは、相互接続DSCPに再マークするか、相互接続されたネットワークの運用者間の追加の合意によって処理することができます。この文書でさらに説明するように、MPLSショートパイプモデルを使用すると、追加の合意がない場合には、予期しないDSCPを0に再マークすることが好まれます。

In addition to the common interconnecting PHBs and DSCPs, interconnecting operators need to further agree on the tunneling technology used for interconnection (e.g., MPLS, if used) and control or mitigate the impacts of tunneling on reliability and MTU.

相互接続を行う運用者は、共通の相互接続用のPHBとDSCPに加えて、相互接続に使用するトンネリング技術（たとえば、使用する場合はMPLS）についてさらに合意し、トンネリングが信頼性とMTUに与える影響を制御または緩和する必要があります。

1.1. Related Work

1.1. 関連する取り組み

In addition to the activities that triggered this work, there are additional RFCs and Internet-Drafts that may benefit from an interconnection PHB and DSCP scheme. [RFC5160] suggests Meta-QoS-Classes to help enable deployment of standardized end-to-end QoS classes. The Diffserv-Intercon class and codepoint scheme is intended to complement that work (e.g., by enabling a defined set of interconnection DSCPs and PHBs).

この作業のきっかけとなった活動に加えて、相互接続用のPHBとDSCPの方式から恩恵を受ける可能性のあるRFCやInternet-Draftがほかにもあります。[RFC5160]は、標準化されたエンドツーエンドのQoSクラスの展開を可能にするために、Meta-QoS-Classを提案しています。Diffserv-Interconのクラスとコードポイントの方式は、（たとえば、相互接続用のDSCPとPHBの定義されたセットを使用できるようにすることで）その取り組みを補完することを意図しています。

Border Gateway Protocol (BGP) support for signaling Class of Service at interconnection interfaces [BGP-INTERCONNECTION] [SLA-EXCHANGE] is complementary to Diffserv-Intercon. These two BGP documents focus on exchanging Service Level Agreement (SLA) and traffic conditioning parameters and assume that common PHBs identified by the signaled DSCPs have been established (e.g., via use of the Diffserv-Intercon DSCPs) prior to BGP signaling of PHB id codes.

相互接続インターフェイスでサービスクラス（Class of Service）をシグナリングするためのボーダーゲートウェイプロトコル（BGP）のサポート[BGP-INTERCONNECTION] [SLA-EXCHANGE]は、Diffserv-Interconを補完するものです。これら2つのBGPの文書は、サービスレベル合意（SLA）とトラフィック調整のパラメーターの交換に焦点を当てており、BGPでPHB IDコードをシグナリングする前に、シグナリングされるDSCPで識別される共通のPHBが（たとえば、Diffserv-InterconのDSCPの使用によって）確立されていることを前提としています。

1.2. Applicability Statement

1.2. 適用性に関する声明

This document is applicable to the use of Differentiated Services for interconnection traffic between networks and is particularly suited to interconnection of MPLS-based networks that use MPLS Short Pipe Model tunnels. This document is also applicable to other network technologies, but it is not intended for use within an individual network, where the approach specified in [RFC5127] is among the possible alternatives; see Section 3 for further discussion.

この文書は、ネットワーク間の相互接続トラフィックにDifferentiated Servicesを使用する場合に適用でき、特にMPLSショートパイプモデルのトンネルを使用するMPLSベースのネットワークの相互接続に適しています。この文書はほかのネットワーク技術にも適用できますが、個々のネットワーク内での使用は意図していません。個々のネットワーク内では、[RFC5127]で規定されているアプローチが選択肢の1つです。詳細な議論はセクション3を参照してください。

The Diffserv-Intercon approach described in this document simplifies IP-based interconnection to domains operating the MPLS Short Pipe Model for IP traffic, both terminating within the domain and transiting onward to another domain. Transiting traffic is received and sent with the same PHB and DSCP. Terminating traffic maintains the PHB with which it was received; however, the DSCP may change.

この文書で説明するDiffserv-Interconのアプローチは、ドメイン内で終端するIPトラフィックと、さらに別のドメインへと中継されるIPトラフィックの両方について、IPトラフィックに対してMPLSショートパイプモデルを運用しているドメインへのIPベースの相互接続を簡素化します。中継されるトラフィックは、同じPHBとDSCPで受信および送信されます。終端するトラフィックは受信時のPHBを維持しますが、DSCPは変わることがあります。

Diffserv-Intercon is also applicable to Pipe Model tunneling [RFC2983] [RFC3270], but it is not applicable to Uniform Model tunneling [RFC2983] [RFC3270].

Diffserv-Interconは、パイプモデルのトンネリング[RFC2983] [RFC3270]にも適用できますが、ユニフォームモデルのトンネリング[RFC2983] [RFC3270]には適用できません。

The Diffserv-Intercon approach defines a set of four PHBs for support at interconnections (or network boundaries in general). Corresponding DSCPs for use at an interconnection interface are also defined. Diffserv-Intercon allows for a simple mapping of PHBs and DSCPs to MPLS Treatment Aggregates. It is extensible by IETF standardization, and this allows additional PHBs and DSCPs to be specified for the Diffserv-Intercon scheme. Coding space for private interconnection agreements or provider internal services is available, as only a single digit number of standard DSCPs are applied by the Diffserv-Intercon approach.

Diffserv-Interconのアプローチは、相互接続（または一般にネットワーク境界）でサポートする4つのPHBのセットを定義します。相互接続インターフェイスで使用する、対応するDSCPも定義します。Diffserv-Interconでは、PHBとDSCPをMPLSの処理集約に簡単に対応付けることができます。Diffserv-InterconはIETFの標準化によって拡張可能であり、これによってDiffserv-Interconの方式に追加のPHBとDSCPを規定することができます。Diffserv-Interconのアプローチで適用される標準のDSCPは1桁の数だけなので、私的な相互接続の合意やプロバイダー内部のサービスのための符号空間が残されています。

1.3. Document Organization

1.3. 文書の構成

This document is organized as follows: Section 2 reviews the MPLS Short Pipe Model for Diffserv Tunnels [RFC3270], because effective support for that model is a crucial goal of Diffserv-Intercon. Section 3 provides background on the approach described in RFC 5127 to Traffic Class (TC) aggregation within a Diffserv network domain and contrasts it with the Diffserv-Intercon approach. Section 4 introduces Diffserv-Intercon Treatment Aggregates, along with the PHBs and DSCPs that they use, and explains how other PHBs (and associated DSCPs) may be mapped to these Treatment Aggregates. Section 4 also discusses treatment of IP traffic, MPLS VPN Diffserv considerations, and the handling of high-priority network management traffic. Appendix A describes how the MPLS Short Pipe Model (Penultimate Hop Popping (PHP)) impacts DSCP marking for IP interconnections.

この文書の構成は次のとおりです。セクション2では、DiffservトンネルのためのMPLSショートパイプモデル[RFC3270]を概観します。このモデルを効果的にサポートすることが、Diffserv-Interconの重要な目標だからです。セクション3では、Diffservネットワークドメイン内でのトラフィッククラス（TC）の集約についてRFC 5127で説明されているアプローチの背景を示し、それをDiffserv-Interconのアプローチと対比します。セクション4では、Diffserv-Interconの処理集約を、それが使用するPHBとDSCPとともに紹介し、ほかのPHB（および関連するDSCP）をこれらの処理集約にどのように対応付けられるかを説明します。セクション4では、IPトラフィックの扱い、MPLS VPNのDiffservに関する考慮事項、優先度の高いネットワーク管理トラフィックの処理についても論じます。付録Aでは、MPLSショートパイプモデル（最終ホップの1つ手前でのポップ（Penultimate Hop Popping、PHP））がIP相互接続のDSCPマーキングにどのように影響するかを説明します。

2. MPLS and Short Pipe Model Tunnels

2. MPLSとショートパイプモデルのトンネル

This section provides a summary of the implications of MPLS Short Pipe Model tunnels and, in particular, their use of PHP (see RFC 3270) on the Diffserv tunnel framework described in RFC 2983. The Pipe and Uniform Models for Differentiated Services and Tunnels are defined in [RFC2983]. RFC 3270 adds the Short Pipe Model to reflect the impact of MPLS PHP, primarily for MPLS-based IP tunnels and VPNs. The Short Pipe Model and PHP have subsequently become popular with network providers that operate MPLS networks and are now widely used to transport unencapsulated IP traffic. This has important implications for Diffserv functionality in MPLS networks.

このセクションでは、MPLSショートパイプモデルのトンネル、特にそのPHPの使用（RFC 3270を参照）が、RFC 2983で説明されているDiffservトンネルのフレームワークに与える影響の概要を示します。Differentiated Servicesとトンネルのためのパイプモデルとユニフォームモデルは、[RFC2983]で定義されています。RFC 3270は、主にMPLSベースのIPトンネルとVPNのために、MPLSのPHPの影響を反映するショートパイプモデルを追加しています。ショートパイプモデルとPHPはその後、MPLSネットワークを運用するネットワークプロバイダーの間で普及し、現在ではカプセル化されていないIPトラフィックの転送に広く使用されています。これは、MPLSネットワークにおけるDiffservの機能に重要な影響を及ぼします。

Per RFC 2474, the recommendation to forward traffic with unrecognized DSCPs with default (best-effort) service without rewriting the DSCP has not been widely deployed in practice. Network operation and management are simplified when there is a 1-1 match between the DSCP marked on the packet and the forwarding treatment (PHB) applied by network nodes. When this is done, CS0 (the all-zero DSCP) is the only DSCP used for default forwarding of best-effort traffic, and a common practice is to re-mark to CS0 any traffic received with unrecognized or unsupported DSCPs at network edges.

RFC 2474による、認識されないDSCPを持つトラフィックをDSCPを書き換えずにデフォルト（ベストエフォート）のサービスで転送するという推奨は、実際には広く展開されていません。パケットにマークされたDSCPと、ネットワークノードが適用する転送の扱い（PHB）とが1対1で一致していると、ネットワークの運用と管理が簡素化されます。そうした場合、CS0（すべてのビットが0のDSCP）がベストエフォートトラフィックのデフォルト転送に使用される唯一のDSCPとなり、認識されない、またはサポートされていないDSCPで受信したトラフィックはすべてネットワークのエッジでCS0に再マークするのが一般的な慣行です。

MPLS networks are more subtle in this regard, as it is possible to encode the provider's DSCP in the MPLS TC field and allow that to differ from the PHB indicated by the DSCP in the MPLS-encapsulated IP packet. If the MPLS label with the provider's TC field is present at all hops within the provider network, this approach would allow an unrecognized DSCP to be carried edge-to-edge over an MPLS network, because the effective DSCP used by the provider's MPLS network would be encoded in the MPLS label TC field (and also carried edge-to-edge). Unfortunately, this is only true for Pipe Model tunnels.

MPLSネットワークはこの点でより微妙です。プロバイダーのDSCPをMPLSのTCフィールドにエンコードし、それがMPLSカプセル化されたIPパケット内のDSCPが示すPHBと異なることを許容できるからです。プロバイダーのTCフィールドを持つMPLSラベルがプロバイダーネットワーク内のすべてのホップに存在する場合、このアプローチによって、認識されないDSCPをMPLSネットワーク上でエッジからエッジまで運ぶことができます。プロバイダーのMPLSネットワークが使用する実効的なDSCPは、MPLSラベルのTCフィールドにエンコードされる（そしてこれもエッジからエッジまで運ばれる）からです。残念ながら、これが成り立つのはパイプモデルのトンネルの場合だけです。

Short Pipe Model tunnels and PHP behave differently because PHP removes and discards the MPLS provider label carrying the provider's TC field before the traffic exits the provider's network. That discard occurs one hop upstream of the MPLS tunnel endpoint (which is usually at the network edge), resulting in no provider TC information being available at the tunnel egress. To ensure consistent handling of traffic at the tunnel egress, the DSCP field in the MPLS-encapsulated IP header has to contain a DSCP that is valid for the provider's network, so that the IP header cannot be used to carry a different DSCP edge-to-edge. See Appendix A for a more detailed discussion.

ショートパイプモデルのトンネルとPHPでは動作が異なります。PHPは、トラフィックがプロバイダーのネットワークから出る前に、プロバイダーのTCフィールドを運ぶMPLSプロバイダーラベルを取り除いて破棄するからです。その破棄は、（通常はネットワークのエッジにある）MPLSトンネルのエンドポイントの1ホップ上流で行われるため、トンネルのイグレスではプロバイダーのTC情報を利用できません。トンネルのイグレスでトラフィックを一貫して処理できるようにするには、MPLSカプセル化されたIPヘッダーのDSCPフィールドに、プロバイダーのネットワークで有効なDSCPが含まれていなければなりません。そのため、IPヘッダーを使用して、異なるDSCPをエッジからエッジまで運ぶことはできません。より詳細な議論については付録Aを参照してください。

3. Relationship to RFC 5127

3. RFC 5127との関係

This document draws heavily upon the approach to aggregation of Diffserv TCs for use within a network as described in RFC 5127, but there are important differences caused by characteristics of network interconnects that differ from links within a network.

この文書は、RFC 5127で説明されている、ネットワーク内で使用するためのDiffserv TCの集約のアプローチに大きく依拠していますが、ネットワーク内のリンクとは異なるネットワーク相互接続の特性に起因する重要な違いがあります。

3.1. Background of RFC 5127

3.1. RFC 5127の背景

Many providers operate MPLS-based backbones that employ backbone traffic engineering to ensure that if a major link, switch, or router fails, the result will be a routed network that continues to function. Based on that foundation, [RFC5127] introduced the concept of Diffserv Treatment Aggregates, which enable traffic marked with multiple DSCPs to be forwarded in a single MPLS TC based on robust provider backbone traffic engineering. This enables differentiated forwarding behaviors within a domain in a fashion that does not consume a large number of MPLS TCs.

多くのプロバイダーは、主要なリンク、スイッチ、またはルーターに障害が発生しても、その結果として機能し続けるルーティングされたネットワークが得られるように、バックボーンのトラフィックエンジニアリングを採用したMPLSベースのバックボーンを運用しています。その基盤に基づいて、[RFC5127]はDiffservの処理集約（Treatment Aggregate）の概念を導入しました。処理集約により、堅牢なプロバイダーバックボーンのトラフィックエンジニアリングに基づいて、複数のDSCPでマークされたトラフィックを単一のMPLS TCで転送できます。これにより、多数のMPLS TCを消費しない形で、ドメイン内での差別化された転送動作が可能になります。

RFC 5127 provides an example aggregation of Diffserv service classes into four Treatment Aggregates. A small number of aggregates are used because:

RFC 5127は、Diffservのサービスクラスを4つの処理集約に集約する例を示しています。少数の集約が使用されるのは、次の理由によります。

  • The available coding space for carrying TC information (e.g., Diffserv PHB) in MPLS (and Ethernet) is only 3 bits in size and is intended for more than just Diffserv purposes (see, e.g., [RFC5129]).
  • The common interconnection DSCPs ought not to use all 8 possible values. This leaves space for future standards, private bilateral agreements, and local use PHBs and DSCPs.
  • Migrations from one DSCP scheme to a different one is another possible application of otherwise unused DSCPs.
  • MPLS（およびEthernet）でTC情報（たとえば、Diffserv PHB）を運ぶために利用できる符号空間はわずか3ビットであり、Diffservの目的だけでなく、ほかの目的にも使用されることが意図されています（たとえば、[RFC5129]を参照してください）。
  • 共通の相互接続用DSCPは、8つの可能な値をすべて使い切るべきではありません。これにより、将来の標準、私的な二者間の合意、ローカルで使用するPHBとDSCPのための余地が残されます。
  • あるDSCP方式から別の方式への移行も、ほかの方法では使用されないDSCPの用途として考えられます。

3.2. Differences from RFC 5127

3.2. RFC 5127との違い

Like RFC 5127, this document also uses four Treatment Aggregates, but it differs from RFC 5127 in some important ways:

この文書もRFC 5127と同様に4つの処理集約を使用しますが、いくつかの重要な点でRFC 5127とは異なります。

  • It follows RFC 2475 in allowing the DSCPs used within a network to differ from those used to exchange traffic with other networks (at network edges), but it provides support to restore ingress DSCP values if one of the recommended interconnect DSCPs in this document is used. This results in DSCP re-marking at both network ingress and network egress, and this document assumes that such re-marking at network edges is possible for all interface types.
  • Diffserv-Intercon suggests limiting the number of interconnection PHBs per Treatment Aggregate to the minimum required. As further discussed below, the number of PHBs per Treatment Aggregate is no more than two. When two PHBs are specified for a Diffserv-Intercon Treatment Aggregate, the expectation is that the provider network supports DSCPs for both PHBs but uses a single MPLS TC for the Treatment Aggregate that contains the two PHBs.
  • Diffserv-Intercon suggests mapping other PHBs and DSCPs into the interconnection Treatment Aggregates as further discussed below.
  • Diffserv-Intercon treats network control (NC) traffic as a special case. Within a provider's network, the CS6 DSCP is used for local network control traffic (routing protocols and Operations, Administration, and Maintenance (OAM) traffic that is essential to network operation administration, control, and management) that may be destined for any node within the network. In contrast, network control traffic exchanged between networks (e.g., BGP) usually terminates at or close to a network edge and is not forwarded through the network because it is not part of internal routing or OAM for the receiving network. In addition, such traffic is unlikely to be covered by standard interconnection agreements; rather, it is more likely to be specifically configured (e.g., most networks impose restrictions on use of BGP with other networks for obvious reasons). See Section 4.2 for further discussion.
  • Because RFC 5127 used a Treatment Aggregate for network control traffic, Diffserv-Intercon can instead define a fourth Treatment Aggregate for use at network interconnections instead of the Network Control Treatment Aggregate in RFC 5127. Network control traffic may still be exchanged across network interconnections as further discussed in Section 4.2. Diffserv-Intercon uses this fourth Treatment Aggregate for Voice over IP (VoIP) traffic, where network-provided service differentiation is crucial, as even minor glitches are immediately apparent to the humans involved in the conversation.
  • この文書は、ネットワーク内で使用するDSCPが、（ネットワークのエッジで）ほかのネットワークとトラフィックを交換するために使用するDSCPと異なることを許容する点でRFC 2475に従っていますが、この文書で推奨する相互接続DSCPのいずれかが使用されている場合には、イングレスでのDSCP値を復元するためのサポートを提供します。その結果、ネットワークのイングレスとイグレスの両方でDSCPの再マーキングが行われます。この文書は、ネットワークのエッジでのそのような再マーキングが、すべての種類のインターフェイスで可能であることを前提としています。
  • Diffserv-Interconは、処理集約あたりの相互接続用PHBの数を必要最小限に制限することを提案しています。後でさらに説明するように、処理集約あたりのPHBの数は2つ以下です。Diffserv-Interconの処理集約に2つのPHBが規定されている場合、プロバイダーネットワークは両方のPHBのDSCPをサポートしますが、その2つのPHBを含む処理集約には単一のMPLS TCを使用することが想定されています。
  • Diffserv-Interconは、後でさらに説明するように、ほかのPHBとDSCPを相互接続用の処理集約に対応付けることを提案しています。
  • Diffserv-Interconは、ネットワーク制御（NC）トラフィックを特別な場合として扱います。プロバイダーのネットワーク内では、CS6 DSCPは、ネットワーク内の任意のノードを宛先とする可能性のあるローカルなネットワーク制御トラフィック（ルーティングプロトコルや、ネットワークの運用管理、制御、管理に不可欠な運用・管理・保守（OAM）のトラフィック）に使用されます。対照的に、ネットワーク間で交換されるネットワーク制御トラフィック（たとえば、BGP）は通常、ネットワークのエッジまたはその近くで終端し、受信側ネットワークの内部ルーティングやOAMの一部ではないため、ネットワーク内を通って転送されることはありません。さらに、そのようなトラフィックが標準的な相互接続の合意でカバーされる可能性は低く、むしろ個別に設定される可能性が高くなります（たとえば、ほとんどのネットワークは、明らかな理由から、ほかのネットワークとのBGPの使用に制限を課しています）。詳細な議論についてはセクション4.2を参照してください。
  • RFC 5127はネットワーク制御トラフィックに処理集約を1つ使用していたので、Diffserv-Interconは代わりに、RFC 5127のネットワーク制御処理集約（Network Control Treatment Aggregate）に替えて、ネットワーク相互接続で使用する4つ目の処理集約を定義できます。セクション4.2でさらに説明するように、ネットワーク制御トラフィックは引き続きネットワーク相互接続を越えて交換できます。Diffserv-Interconは、この4つ目の処理集約をVoice over IP（VoIP）トラフィックに使用します。VoIPでは、わずかな不具合でも会話に参加している人間にすぐにわかってしまうため、ネットワークが提供するサービスの差別化が極めて重要です。

4. The Diffserv-Intercon Interconnection Classes

4. Diffserv-Interconの相互接続クラス

At an interconnection, the networks involved need to agree on the PHBs used for interconnection and the specific DSCP for each PHB. This document defines a set of four interconnection Treatment Aggregates with well-defined DSCPs to be aggregated by them. A sending party re-marks DSCPs from internal usage to the interconnection codepoints. The receiving party re-marks DSCPs to their internal usage. The interconnect SLA defines the set of DSCPs and PHBs supported across the two interconnected domains and the treatment of PHBs and DSCPs that are not recognized by the receiving domain.

相互接続において、関係するネットワークは、相互接続に使用するPHBと、各PHBに対する特定のDSCPについて合意する必要があります。この文書は、相互接続用の4つの処理集約のセットを、それぞれが集約する明確に定義されたDSCPとともに定義します。送信側は、DSCPを内部での用法から相互接続用のコードポイントに再マークします。受信側は、DSCPを自身の内部での用法に再マークします。相互接続SLAは、相互接続された2つのドメイン間でサポートされるDSCPとPHBのセットと、受信側のドメインが認識しないPHBとDSCPの扱いを定義します。

Similar approaches that use a small number of Treatment Aggregates (including recognition of the importance of VoIP traffic) have been taken in related standards and recommendations from outside the IETF, e.g., Y.1566 [Y.1566], Global System for Mobile Communications Association (GSMA) IR.34 [IR.34], and MEF23.1 [MEF23.1].

少数の処理集約を使用する同様のアプローチ（VoIPトラフィックの重要性の認識を含む）が、IETFの外部の関連する標準や勧告でも採用されています。たとえば、Y.1566 [Y.1566]、Global System for Mobile Communications Association（GSMA）のIR.34 [IR.34]、MEF23.1 [MEF23.1]です。

The list of the four Diffserv-Intercon Treatment Aggregates follows, highlighting differences from RFC 5127 and suggesting mappings for all RFC 4594 TCs to Diffserv-Intercon Treatment Aggregates:

以下は、Diffserv-Interconの4つの処理集約の一覧です。RFC 5127との違いを強調し、RFC 4594のすべてのTCについて、Diffserv-Interconの処理集約への対応付けを提案しています。

Telephony Service Treatment Aggregate:
PHB Expedited Forwarding (EF), DSCP 101 110 and PHB VOICE-ADMIT, DSCP 101 100 (see [RFC3246], [RFC4594], and [RFC5865]). This Treatment Aggregate corresponds to the Real-Time Treatment Aggregate definition regarding the queuing (both delay and jitter should be minimized) per RFC 5127, but this aggregate is restricted to transport Telephony service class traffic in the sense of [RFC4594].
Bulk Real-Time Treatment Aggregate:
This Treatment Aggregate is designed to transport PHB AF41, DSCP 100 010 (the other AF4 PHB group PHBs and DSCPs may be used for future extension of the set of DSCPs carried by this Treatment Aggregate). This Treatment Aggregate is intended to provide Diffserv-Intercon network interconnection of a subset of the Real-Time Treatment Aggregate defined in RFC 5127, specifically the portions that consume significant bandwidth. This traffic is expected to consist of the following classes defined in RFC 4594: Broadcast Video, Real-Time Interactive, and Multimedia Conferencing. This Treatment Aggregate should be configured with a rate-based queue (consistent with the recommendation for the transported TCs in RFC 4594). By comparison to RFC 5127, the number of DSCPs has been reduced to one (initially). The AF42 and AF43 PHBs could be added if there is a need for three-color marked Multimedia Conferencing traffic.
Assured Elastic Treatment Aggregate:
This Treatment Aggregate consists of PHBs AF31 and AF32 (i.e., DSCPs 011 010 and 011 100). By comparison to RFC 5127, the number of DSCPs has been reduced to two. This document suggests to transport signaling marked by AF31 (e.g., as recommended by GSMA IR.34 [IR.34]). AF33 is reserved for the extension of PHBs to be aggregated by this Treatment Aggregate. For Diffserv-Intercon network interconnection, the following service classes (per RFC 4594) should be mapped to the Assured Elastic Treatment Aggregate: the Signaling service class (being marked for lowest loss probability), the Multimedia Streaming service class, the Low-Latency Data service class, and the High-Throughput Data service class.
Default / Elastic Treatment Aggregate:
Transports the Default PHB, CS0 with DSCP 000 000. An example in RFC 5127 refers to this Treatment Aggregate as "Elastic Treatment Aggregate". An important difference from RFC 5127 is that any traffic with unrecognized or unsupported DSCPs may be re-marked to this DSCP. For Diffserv-Intercon network interconnection, the Standard service class and Low-Priority Data service class defined in RFC 4594 should be mapped to this Treatment Aggregate. This document does not specify an interconnection class for Low-Priority Data (also defined RFC 4594). This traffic may be forwarded with a Lower Effort PHB in one domain (e.g., the PHB proposed by Informational [RFC3662]), but the methods specified in this document re-mark this traffic with DSCP CS0 at a Diffserv-Intercon network interconnection. This has the effect that Low-Priority Data is treated the same as data sent using the Standard service class. (Note: In a network that implements RFC 2474, Low-Priority traffic marked as CS1 would otherwise receive better treatment than Standard traffic using the default PHB.)
電話サービス処理集約（Telephony Service Treatment Aggregate）:
PHB Expedited Forwarding（EF）、DSCP 101 110、およびPHB VOICE-ADMIT、DSCP 101 100（[RFC3246]、[RFC4594]、[RFC5865]を参照してください）。この処理集約は、キューイング（遅延とジッターの両方を最小化すべき）に関して、RFC 5127のリアルタイム処理集約（Real-Time Treatment Aggregate）の定義に対応しますが、この集約が運ぶのは[RFC4594]の意味でのTelephonyサービスクラスのトラフィックに限定されます。
バルクリアルタイム処理集約（Bulk Real-Time Treatment Aggregate）:
この処理集約は、PHB AF41、DSCP 100 010を運ぶように設計されています（AF4 PHBグループのほかのPHBとDSCPは、この処理集約が運ぶDSCPのセットを将来拡張するために使用される可能性があります）。この処理集約は、RFC 5127で定義されているリアルタイム処理集約のサブセット、具体的には大きな帯域幅を消費する部分について、Diffserv-Interconのネットワーク相互接続を提供することを意図しています。このトラフィックは、RFC 4594で定義されている次のクラスで構成されることが想定されています。Broadcast Video、Real-Time Interactive、Multimedia Conferencingです。この処理集約は、（RFC 4594で運ばれるTCに対する推奨と整合するように）レートベースのキューで設定すべきです。RFC 5127と比べると、DSCPの数は（当初は）1つに削減されています。3色マーキングされたMultimedia Conferencingトラフィックが必要な場合は、AF42とAF43のPHBを追加できます。
保証型エラスティック処理集約（Assured Elastic Treatment Aggregate）:
この処理集約は、PHB AF31とAF32（つまり、DSCP 011 010と011 100）で構成されます。RFC 5127と比べると、DSCPの数は2つに削減されています。この文書は、（たとえば、GSMAのIR.34 [IR.34]で推奨されているように）AF31でマークされたシグナリングを運ぶことを提案します。AF33は、この処理集約で集約するPHBを拡張するために予約されています。Diffserv-Interconのネットワーク相互接続では、（RFC 4594による）次のサービスクラスを保証型エラスティック処理集約に対応付けるべきです。Signalingサービスクラス（最も低い損失確率でマークされる）、Multimedia Streamingサービスクラス、Low-Latency Dataサービスクラス、High-Throughput Dataサービスクラスです。
デフォルト／エラスティック処理集約（Default / Elastic Treatment Aggregate）:
DSCP 000 000のCS0であるDefault PHBを運びます。RFC 5127の例では、この処理集約を「エラスティック処理集約（Elastic Treatment Aggregate）」と呼んでいます。RFC 5127との重要な違いは、認識されない、またはサポートされていないDSCPを持つトラフィックはいずれも、このDSCPに再マークされることがあるという点です。Diffserv-Interconのネットワーク相互接続では、RFC 4594で定義されているStandardサービスクラスとLow-Priority Dataサービスクラスを、この処理集約に対応付けるべきです。この文書は、（これもRFC 4594で定義されている）Low-Priority Dataのための相互接続クラスを規定しません。このトラフィックは、あるドメインではLower Effort PHB（たとえば、Informationalの[RFC3662]で提案されているPHB）で転送されることがありますが、この文書で規定する方法では、Diffserv-Interconのネットワーク相互接続でこのトラフィックをDSCP CS0で再マークします。その結果、Low-Priority Dataは、Standardサービスクラスを使用して送信されたデータと同じように扱われます。（注: RFC 2474を実装するネットワークでは、そうしなければ、CS1としてマークされたLow-Priorityトラフィックが、Default PHBを使用するStandardトラフィックよりもよい扱いを受けることになります。）

RFC 2475 states that ingress nodes must condition all inbound traffic to ensure that the DS codepoints are acceptable; packets found to have unacceptable codepoints must either be discarded or have their DS codepoints modified to acceptable values before being forwarded. For example, an ingress node receiving traffic from a domain with which no enhanced service agreement exists may reset the DS codepoint to CS0. As a consequence, an interconnect SLA needs to specify not only the treatment of traffic that arrives with a supported interconnect DSCP but also the treatment of traffic that arrives with unsupported or unexpected DSCPs; re-marking to CS0 is a widely deployed behavior.

RFC 2475は、イングレスノードは、DSコードポイントが受け入れ可能であることを保証するためにすべての受信トラフィックを調整しなければならず、受け入れ不可能なコードポイントを持つことが判明したパケットは、転送される前に破棄されるか、DSコードポイントを受け入れ可能な値に変更されなければならないと述べています。たとえば、拡張サービスの合意が存在しないドメインからトラフィックを受信したイングレスノードは、DSコードポイントをCS0にリセットすることがあります。その結果、相互接続SLAでは、サポートされている相互接続DSCPで到着したトラフィックの扱いだけでなく、サポートされていない、または予期しないDSCPで到着したトラフィックの扱いも規定する必要があります。CS0への再マーキングは広く展開されている動作です。

During the process of setting up a Diffserv interconnection, both networks should define the set of acceptable and unacceptable DSCPs and specify the treatment of traffic marked with each DSCP.

Diffserv相互接続を設定する過程で、両方のネットワークは、受け入れ可能なDSCPと受け入れ不可能なDSCPのセットを定義し、各DSCPでマークされたトラフィックの扱いを規定すべきです。

While Diffserv-Intercon allows modification of unacceptable DSCPs, if traffic using one or more of the PHBs in a PHB group (e.g., AF3x, consisting of AF31, AF32, and AF33) is accepted as part of a supported Diffserv-Intercon Treatment Aggregate, then traffic using other PHBs from the same PHB group should not be modified to use PHBs outside of that PHB group and, in particular, should not be re-marked to CS0 unless the entire PHB group is re-marked to CS0. This avoids unexpected forwarding behavior (and potential reordering; see also [RFC7657]) when using Assured Forwarding (AF) PHBs [RFC2597].

Diffserv-Interconは受け入れ不可能なDSCPの変更を許容していますが、PHBグループ（たとえば、AF31、AF32、AF33からなるAF3x）内の1つ以上のPHBを使用するトラフィックが、サポートされているDiffserv-Interconの処理集約の一部として受け入れられる場合、同じPHBグループのほかのPHBを使用するトラフィックは、そのPHBグループ外のPHBを使用するように変更されるべきではなく、特に、PHBグループ全体がCS0に再マークされるのでない限り、CS0に再マークされるべきではありません。これにより、Assured Forwarding（AF）PHB [RFC2597]を使用する場合の予期しない転送動作（および潜在的な順序の入れ替わり。[RFC7657]も参照してください）を回避できます。

4.1. Diffserv-Intercon Example

4.1. Diffserv-Interconの例

The overall approach to DSCP marking at network interconnections is illustrated by the following example. Provider O, provider W, and provider F are peered with provider T. They have agreed upon a Diffserv interconnection SLA.

ネットワーク相互接続でのDSCPマーキングの全体的なアプローチを、次の例で説明します。プロバイダーO、プロバイダーW、プロバイダーFは、プロバイダーTとピアリングしています。これらのプロバイダーは、Diffserv相互接続SLAに合意しています。

Traffic of provider O terminates within provider T's network, while provider W's traffic transits through the network of provider T to provider F. This example assumes that all providers use their own internal PHB and codepoint (DSCP) that correspond to the AF31 PHB in the Diffserv-Intercon Assured Elastic Treatment Aggregate (AF21, CS2, and AF11 are used in the example).

プロバイダーOのトラフィックはプロバイダーTのネットワーク内で終端し、プロバイダーWのトラフィックはプロバイダーTのネットワークを通過してプロバイダーFへと中継されます。この例では、すべてのプロバイダーが、Diffserv-Interconの保証型エラスティック処理集約のAF31 PHBに対応する、独自の内部PHBとコードポイント（DSCP）を使用していると仮定します（この例ではAF21、CS2、AF11が使用されています）。

Providers only need to deploy mappings of internal DSCPs to/from Diffserv-Intercon DSCPs, so that they can exchange traffic using the desired PHBs. In the example, provider O has decided that the properties of his internal class AF21 are best met by the Diffserv-Intercon Assured Elastic Treatment Aggregate, PHB AF31. At the outgoing peering interface connecting provider O with provider T, the former's peering router re-marks AF21 traffic to AF31. The domain internal PHB of provider T that meets the requirement of the Diffserv-Intercon Assured Elastic Treatment Aggregate is from the AF2x PHB group. Hence, AF31 traffic received at the interconnection with provider T is re-marked to AF21 by the peering router of domain T, and domain T has chosen to use MPLS TC value 2 for this aggregate. At the penultimate MPLS node, the top MPLS label is removed and exposes the IP header marked by the DSCP that has been set at the network ingress. The peering router connecting domain T with domain F classifies the packet by its domain-T-internal DSCP AF21. As the packet leaves domain T on the interface to domain F, this causes the packet's DSCP to be re-marked to AF31. The peering router of domain F classifies the packet for domain-F-internal PHB AF11, as this is the PHB with properties matching the Diffserv-Intercon Assured Elastic Treatment Aggregate.

プロバイダーは、目的のPHBを使用してトラフィックを交換できるように、内部DSCPとDiffserv-Intercon DSCPとの間の対応付けを展開するだけで済みます。この例では、プロバイダーOは、自身の内部クラスAF21の特性に最もよく合うのはDiffserv-Interconの保証型エラスティック処理集約のPHB AF31であると判断しています。プロバイダーOとプロバイダーTを接続する送信側のピアリングインターフェイスで、前者のピアリングルーターはAF21のトラフィックをAF31に再マークします。Diffserv-Interconの保証型エラスティック処理集約の要件を満たすプロバイダーTのドメイン内部のPHBは、AF2x PHBグループのものです。そのため、プロバイダーTとの相互接続で受信されたAF31のトラフィックは、ドメインTのピアリングルーターによってAF21に再マークされます。また、ドメインTはこの集約にMPLS TC値2を使用することを選択しています。最後から2番目のMPLSノードで最上位のMPLSラベルが取り除かれ、ネットワークのイングレスで設定されたDSCPでマークされたIPヘッダーが露出します。ドメインTとドメインFを接続するピアリングルーターは、パケットをドメインT内部のDSCPであるAF21によって分類します。パケットがドメインFへのインターフェイスでドメインTから出ていく際に、これによってパケットのDSCPがAF31に再マークされます。ドメインFのピアリングルーターは、パケットをドメインF内部のPHBであるAF11に分類します。これは、AF11がDiffserv-Interconの保証型エラスティック処理集約に合致する特性を持つPHBだからです。

This example can be extended. The figure shows provider W using CS2 for traffic that corresponds to Diffserv-Intercon Assured Elastic Treatment Aggregate PHB AF31; that traffic is mapped to AF31 at the Diffserv-Intercon interconnection to provider T. In addition, suppose that provider O supports a PHB marked by AF22, and this PHB is supposed to obtain Diffserv transport within provider T's domain. Then provider O will re-mark it with DSCP AF32 for interconnection to provider T.

この例は拡張できます。図には、Diffserv-Interconの保証型エラスティック処理集約のPHB AF31に対応するトラフィックにCS2を使用しているプロバイダーWが示されています。そのトラフィックは、プロバイダーTへのDiffserv-Intercon相互接続でAF31に対応付けられます。さらに、プロバイダーOがAF22でマークされるPHBをサポートしており、このPHBがプロバイダーTのドメイン内でDiffservによる転送を受けることになっているとします。その場合、プロバイダーOは、プロバイダーTとの相互接続のために、それをDSCP AF32で再マークします。

Finally, suppose that provider W supports CS3 for internal use only. Then no Diffserv-Intercon DSCP mapping needs to be configured at the peering router. Traffic, sent by provider W to provider T marked by CS3 due to a misconfiguration may be re-marked to CS0 by provider T.

最後に、プロバイダーWが内部でのみ使用するためにCS3をサポートしているとします。その場合、ピアリングルーターでDiffserv-InterconのDSCPの対応付けを設定する必要はありません。設定の誤りによってCS3でマークされてプロバイダーWからプロバイダーTに送信されたトラフィックは、プロバイダーTによってCS0に再マークされることがあります。

4.2. End-to-End PHB and DSCP Transparency

4.2. エンドツーエンドでのPHBとDSCPの透過性

This section briefly discusses end-to-end Diffserv approaches related to the Uniform, Pipe, and Short Pipe Model tunnels [RFC2983] [RFC3270] when used edge-to-edge in a network.

このセクションでは、ネットワーク内でエッジからエッジまで使用される場合の、ユニフォームモデル、パイプモデル、ショートパイプモデルのトンネル[RFC2983] [RFC3270]に関連するエンドツーエンドのDiffservのアプローチについて簡単に論じます。

  • With the Uniform Model, neither the DSCP nor the PHB change. This implies that a network management packet received with a CS6 DSCP would be forwarded with an MPLS TC corresponding to CS6. The Uniform Model is outside the scope of this document.
  • With the Pipe Model, the inner tunnel DSCP remains unchanged, but an outer tunnel DSCP and the PHB could change. For example, a packet received with a (network-specific) CS1 DSCP would be transported by a Default PHB and, if MPLS is applicable, forwarded with an MPLS TC corresponding to the Default PHB. The CS1 DSCP is not rewritten. Transport of a large variety (much greater than four) DSCPs may be required across an interconnected network operating MPLS Short Pipe Model transport for IP traffic. In that case, a tunnel based on the Pipe Model is among the possible approaches. The Pipe Model is outside the scope of this document.
  • With the Short Pipe Model, the DSCP likely changes, and the PHB might change. This document describes a method to simplify Diffserv network interconnection when a DSCP rewrite can't be avoided.
  • ユニフォームモデルでは、DSCPもPHBも変わりません。これは、CS6 DSCPで受信されたネットワーク管理パケットが、CS6に対応するMPLS TCで転送されることを意味します。ユニフォームモデルはこの文書の範囲外です。
  • パイプモデルでは、内側のトンネルのDSCPは変わりませんが、外側のトンネルのDSCPとPHBは変わる可能性があります。たとえば、（ネットワーク固有の）CS1 DSCPで受信されたパケットは、Default PHBで運ばれ、MPLSが適用される場合は、Default PHBに対応するMPLS TCで転送されます。CS1 DSCPは書き換えられません。IPトラフィックに対してMPLSショートパイプモデルの転送を運用している相互接続されたネットワークを越えて、多種多様な（4つよりはるかに多い）DSCPを運ぶことが必要になる場合があります。その場合、パイプモデルに基づくトンネルが選択肢の1つです。パイプモデルはこの文書の範囲外です。
  • ショートパイプモデルでは、DSCPはおそらく変わり、PHBも変わる可能性があります。この文書は、DSCPの書き換えを避けられない場合に、Diffservのネットワーク相互接続を簡素化する方法を説明します。

4.3. Treatment of Network Control Traffic at Carrier Interconnection Interfaces

4.3. キャリア相互接続インターフェイスでのネットワーク制御トラフィックの扱い

As specified in Section 3.2 of RFC 4594, NC traffic marked by CS6 is expected at some interconnection interfaces. This document does not change RFC 4594 but observes that network control traffic received at a network ingress is generally different from network control traffic within a network that is the primary use of CS6 envisioned by RFC 4594. A specific example is that some CS6 traffic exchanged across carrier interconnections is terminated at the network ingress node, e.g., when BGP is used between the two routers on opposite ends of an interconnection link; in this case, the operators would enter into a bilateral agreement to use CS6 for that BGP traffic.

RFC 4594のセクション3.2で規定されているように、一部の相互接続インターフェイスでは、CS6でマークされたNCトラフィックが想定されます。この文書はRFC 4594を変更するものではありませんが、ネットワークのイングレスで受信されるネットワーク制御トラフィックは、RFC 4594が想定するCS6の主な用途であるネットワーク内のネットワーク制御トラフィックとは一般に異なることを指摘します。具体的な例として、キャリア相互接続を越えて交換される一部のCS6トラフィックは、たとえば相互接続リンクの両端にある2つのルーター間でBGPが使用される場合のように、ネットワークのイングレスノードで終端します。この場合、運用者はそのBGPトラフィックにCS6を使用するための二者間の合意を結ぶことになるでしょう。

The end-to-end discussion in Section 4.2 is generally inapplicable to network control traffic -- network control traffic is generally intended to control a network, not be transported between networks. One exception is that network control traffic makes sense for a purchased transit agreement, and preservation of the CS6 DSCP marking for network control traffic that is transited is reasonable in some cases, although it is generally inappropriate to use CS6 for forwarding that traffic within the network that provides transit. Use of an IP tunnel is suggested in order to conceal the CS6 markings on transiting network control traffic from the network that provides the transit. In this case, the Pipe Model for Diffserv tunneling is used.

セクション4.2のエンドツーエンドの議論は、一般にネットワーク制御トラフィックには当てはまりません。ネットワーク制御トラフィックは一般に、ネットワーク間で運ばれるためではなく、ネットワークを制御するためのものだからです。1つの例外は、購入したトランジットの合意ではネットワーク制御トラフィックが意味を持つことです。中継されるネットワーク制御トラフィックについてCS6 DSCPのマーキングを保持することは、場合によっては妥当です。ただし、トランジットを提供するネットワーク内でそのトラフィックの転送にCS6を使用することは、一般に不適切です。中継されるネットワーク制御トラフィックのCS6マーキングを、トランジットを提供するネットワークから隠すために、IPトンネルを使用することが提案されます。この場合、Diffservトンネリングのパイプモデルが使用されます。

If the MPLS Short Pipe Model is deployed for unencapsulated IPv4 traffic, an IP network provider should limit access to the CS6 and CS7 DSCPs, so that they are only used for network control traffic for the provider's own network.

カプセル化されていないIPv4トラフィックに対してMPLSショートパイプモデルが展開されている場合、IPネットワークプロバイダーは、CS6とCS7のDSCPがプロバイダー自身のネットワークのネットワーク制御トラフィックにのみ使用されるように、それらへのアクセスを制限すべきです。

Interconnecting carriers should specify treatment of CS6-marked traffic received at a carrier interconnection that is to be forwarded beyond the ingress node. An SLA covering the following cases is recommended when a provider wishes to send CS6-marked traffic across an interconnection link and that traffic's destination is beyond the interconnected ingress node:

相互接続するキャリアは、キャリア相互接続で受信され、イングレスノードの先まで転送されるCS6マークのトラフィックの扱いを規定すべきです。プロバイダーが相互接続リンクを越えてCS6マークのトラフィックを送信したい場合で、そのトラフィックの宛先が相互接続されたイングレスノードの先にあるときは、次の場合をカバーするSLAが推奨されます。

  • classification of traffic that is network control traffic for both domains. This traffic should be classified and marked for the CS6 DSCP.
  • classification of traffic that is network control traffic for the sending domain only. This traffic should be forwarded with a PHB that is appropriate for transiting NC service class traffic [RFC4594] in the receiving domain, e.g., AF31 as specified by this document. As an example, GSMA IR.34 recommends an Interactive class / AF31 to carry SIP and DIAMETER traffic. While this is service control traffic of high importance to interconnected Mobile Network Operators, it is certainly not network control traffic for a fixed network providing transit among such operators and hence should not receive CS6 treatment in such a transit network.
  • any other CS6-marked traffic should be re-marked or dropped.
  • 両方のドメインにとってネットワーク制御トラフィックであるトラフィックの分類。このトラフィックは、CS6 DSCPに分類され、マークされるべきです。
  • 送信側のドメインにとってのみネットワーク制御トラフィックであるトラフィックの分類。このトラフィックは、受信側のドメインで、中継されるNCサービスクラスのトラフィック[RFC4594]に適したPHB（たとえば、この文書で規定するAF31）で転送されるべきです。例として、GSMAのIR.34は、SIPとDIAMETERのトラフィックを運ぶためにInteractiveクラス／AF31を推奨しています。これは相互接続されたモバイルネットワーク運用者にとっては重要度の高いサービス制御トラフィックですが、そのような運用者間のトランジットを提供する固定ネットワークにとっては決してネットワーク制御トラフィックではないため、そのようなトランジットネットワークではCS6の扱いを受けるべきではありません。
  • そのほかのCS6マークのトラフィックは、再マークするか破棄すべきです。

6. Security Considerations

6. セキュリティーに関する考慮事項

The DSCP field in the IP header can expose additional traffic classification information at network interconnections by comparison to the use of a zero DSCP for all interconnect traffic. If traffic classification information is sensitive, the DSCP field could be re-marked to zero to hide the classification as a countermeasure, at the cost of loss of Diffserv information and differentiated traffic handling on the interconnect and subsequent networks. When AF PHBs are used, any such re-marking should respect AF PHB group boundaries as further discussed at the end of Section 4.

IPヘッダーのDSCPフィールドは、すべての相互接続トラフィックに0のDSCPを使用する場合と比べて、ネットワーク相互接続で追加のトラフィック分類情報を露出させる可能性があります。トラフィック分類情報が機密である場合は、対策として、分類を隠すためにDSCPフィールドを0に再マークすることができますが、その代償として、Diffservの情報と、相互接続およびその先のネットワークでの差別化されたトラフィック処理が失われます。AF PHBが使用されている場合、そのような再マーキングでは、セクション4の最後でさらに説明しているように、AF PHBグループの境界を尊重すべきです。

This document does not introduce new features; it describes how to use existing ones. The Diffserv security considerations in [RFC2475] and [RFC4594] apply.

この文書は新しい機能を導入するものではなく、既存の機能の使い方を説明するものです。[RFC2475]と[RFC4594]のDiffservのセキュリティーに関する考慮事項が適用されます。

Appendix A. The MPLS Short Pipe Model and IP Traffic

付録A. MPLSショートパイプモデルとIPトラフィック

The MPLS Short Pipe Model (or penultimate hop label popping) is widely deployed in carrier networks. If unencapsulated IP traffic is transported using MPLS Short Pipe, IP headers appear inside the last section of the MPLS domain. This impacts the number of PHBs and DSCPs that a network provider can reasonably support. See Figure 2 for an example.

MPLSショートパイプモデル（または最終ホップの1つ手前でのラベルのポップ）は、キャリアのネットワークで広く展開されています。カプセル化されていないIPトラフィックがMPLSショートパイプを使用して運ばれる場合、IPヘッダーはMPLSドメインの最後の区間の内部で露出します。これは、ネットワークプロバイダーが合理的にサポートできるPHBとDSCPの数に影響します。例については図2を参照してください。

For encapsulated IP traffic, only the outer tunnel header is relevant for forwarding. If the tunnel does not terminate within the MPLS network section, only the outer tunnel DSCP is involved, as the inner DSCP does not affect forwarding behavior; in this case, all DSCPs could be used in the inner IP header without affecting network behavior based on the outer MPLS header. Here, the Pipe Model applies.

カプセル化されたIPトラフィックでは、転送に関係するのは外側のトンネルヘッダーだけです。トンネルがMPLSネットワーク区間内で終端しない場合、内側のDSCPは転送動作に影響しないため、関係するのは外側のトンネルのDSCPだけです。この場合、外側のMPLSヘッダーに基づくネットワークの動作に影響を与えることなく、内側のIPヘッダーですべてのDSCPを使用できます。ここではパイプモデルが適用されます。

Layer 2 and Layer 3 VPN traffic all use an additional MPLS label; in this case, the MPLS tunnel follows the Pipe Model. Classification and queuing within an MPLS network is always based on an MPLS label, as opposed to the outer IP header.

レイヤー2とレイヤー3のVPNトラフィックはいずれも追加のMPLSラベルを使用します。この場合、MPLSトンネルはパイプモデルに従います。MPLSネットワーク内での分類とキューイングは、外側のIPヘッダーではなく、常にMPLSラベルに基づきます。

Carriers often select PHBs and DSCPs without regard to interconnection. As a result, PHBs and DSCPs typically differ between network carriers. With the exception of best-effort traffic, a DSCP change should be expected at an interconnection at least for unencapsulated IP traffic, even if the PHB is suitably mapped by the carriers involved.

キャリアは多くの場合、相互接続を考慮せずにPHBとDSCPを選択します。その結果、PHBとDSCPは一般にネットワークキャリア間で異なります。ベストエフォートトラフィックを除き、関係するキャリアによってPHBが適切に対応付けられている場合でも、少なくともカプセル化されていないIPトラフィックについては、相互接続でDSCPが変わることを想定すべきです。

Although RFC 3270 suggests that the Short Pipe Model is only applicable to VPNs, current networks also use it to transport non-tunneled IPv4 traffic. This is shown in Figure 2 where Diffserv-Intercon is not used, resulting in exposure of the internal DSCPs of the upstream network to the downstream network across the interconnection.

RFC 3270は、ショートパイプモデルはVPNにのみ適用できるとしていますが、現在のネットワークでは、トンネル化されていないIPv4トラフィックの転送にもこのモデルが使用されています。これを図2に示します。図2ではDiffserv-Interconが使用されておらず、その結果、上流のネットワークの内部DSCPが、相互接続を越えて下流のネットワークに露出しています。

The packet's IP DSCP must be in a well-understood Diffserv context for schedulers and classifiers on the interfaces of the ultimate MPLS link (last link traversed before leaving the network). The necessary Diffserv context is network-internal, and a network operating in this mode enforces DSCP usage in order to obtain robust differentiated forwarding behavior.

最後のMPLSリンク（ネットワークから出る前に通過する最後のリンク）のインターフェイスにあるスケジューラーと分類器のために、パケットのIP DSCPは、よく理解されたDiffservの文脈になければなりません。必要なDiffservの文脈はネットワーク内部のものであり、このモードで動作するネットワークは、堅牢な差別化された転送動作を得るためにDSCPの使用を強制します。

Without Diffserv-Intercon treatment, the traffic is likely to leave each network marked with network-internal DSCP. DSCP_send in the figure above has to be re-marked into the first network's Diffserv scheme at the ingress MPLS Edge Router, to DSCP_d in the example.

Diffserv-Interconによる扱いがない場合、トラフィックは各ネットワークから、ネットワーク内部のDSCPでマークされたまま出ていく可能性が高くなります。上の図のDSCP_sendは、イングレスのMPLSエッジルーターで、最初のネットワークのDiffserv方式に、この例ではDSCP_dに再マークされなければなりません。

For that reason, the traffic leaves this domain marked by the network-internal DSCP_d. This structure requires that every carrier deploys per-peer PHB and DSCP mapping schemes.

そのため、トラフィックは、ネットワーク内部のDSCP_dでマークされたままこのドメインから出ていきます。この構造では、すべてのキャリアがピアごとのPHBとDSCPの対応付け方式を展開する必要があります。

If Diffserv-Intercon is applied, DSCPs for traffic transiting the domain can be mapped from and remapped to an original DSCP. This is shown in Figure 3. Internal traffic may continue to use internal DSCPs (e.g., DSCP_d), and they may also be used between a carrier and its direct customers.

Diffserv-Interconが適用される場合、ドメインを通過するトラフィックのDSCPは、元のDSCPから対応付け、また元のDSCPに対応付け直すことができます。これを図3に示します。内部トラフィックは引き続き内部DSCP（たとえば、DSCP_d）を使用でき、内部DSCPはキャリアとその直接の顧客との間でも使用できます。
