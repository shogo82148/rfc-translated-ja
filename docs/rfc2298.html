RFC 2298

An Extensible Message Format for Message Disposition Notifications

RFC 2298

メッセージ処理通知のための拡張可能なメッセージ形式

Abstract

概要

This memo defines a MIME content-type that may be used by a mail user agent (UA) or electronic mail gateway to report the disposition of a message after it has been sucessfully delivered to a recipient. This content-type is intended to be machine-processable. Additional message headers are also defined to permit Message Disposition Notifications (MDNs) to be requested by the sender of a message. The purpose is to extend Internet Mail to support functionality often found in other messaging systems, such as X.400 and the proprietary "LAN-based" systems, and often referred to as "read receipts," "acknowledgements," or "receipt notifications." The intention is to do this while respecting the privacy concerns that have often been expressed when such functions have been discussed in the past.

このメモは、メールユーザーエージェント（UA）や電子メールゲートウェイが、受信者へのメッセージの配送が成功した後に、そのメッセージの処理（disposition）を報告するために使用できるMIMEコンテンツタイプを定義します。このコンテンツタイプは、機械処理が可能であることを意図しています。また、メッセージの送信者がメッセージ処理通知（Message Disposition Notification、MDN）を要求できるようにするための追加のメッセージヘッダーも定義します。その目的は、X.400や独自の「LANベース」のシステムなど、他のメッセージングシステムによく見られる機能、つまり「開封確認（read receipts）」「確認応答（acknowledgements）」「受領通知（receipt notifications）」とよく呼ばれる機能をサポートするように、インターネットメールを拡張することです。このとき、過去にこのような機能が議論された際にしばしば表明されてきたプライバシー上の懸念を尊重することを意図しています。

Because many messages are sent between the Internet and other messaging systems (such as X.400 or the proprietary "LAN-based" systems), the MDN protocol is designed to be useful in a multi-protocol messaging environment. To this end, the protocol described in this memo provides for the carriage of "foreign" addresses, in addition to those normally used in Internet Mail. Additional attributes may also be defined to support "tunneling" of foreign notifications through Internet Mail.

多くのメッセージがインターネットと他のメッセージングシステム（X.400や独自の「LANベース」のシステムなど）との間で送信されるため、MDNプロトコルはマルチプロトコルのメッセージング環境で役立つように設計されています。そのため、このメモで説明するプロトコルは、インターネットメールで通常使用されるアドレスに加えて、「外部の（foreign）」アドレスを運ぶ手段を提供します。また、外部の通知をインターネットメールを通じて「トンネリング」することをサポートするために、追加の属性を定義することもできます。

1. Introduction

1. はじめに

This memo defines a MIME content-type [5] for message disposition notifications (MDNs). An MDN can be used to notify the sender of a message of any of several conditions that may occur after successful delivery, such as display of the message contents, printing of the message, deletion (without display) of the message, or the recipient's refusal to provide MDNs. The "message/disposition-notification" content-type defined herein is intended for use within the framework of the "multipart/report" content type defined in RFC 1892 [7].

このメモは、メッセージ処理通知（MDN）のためのMIMEコンテンツタイプ[5]を定義します。MDNは、配送が成功した後に起こりうるいくつかの状態、たとえばメッセージの内容の表示、メッセージの印刷、（表示せずに）メッセージを削除すること、受信者がMDNの提供を拒否したことなどを、メッセージの送信者に通知するために使用できます。ここで定義する「message/disposition-notification」コンテンツタイプは、RFC 1892 [7]で定義されている「multipart/report」コンテンツタイプの枠組みの中で使用することを意図しています。

This memo defines the format of the notifications and the RFC 822 headers used to request them.

このメモは、通知の形式と、通知を要求するために使用するRFC 822ヘッダーを定義します。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119.

この文書におけるキーワード「しなければなりません（MUST）」「してはなりません（MUST NOT）」「要求されています（REQUIRED）」「することになります（SHALL）」「することはありません（SHALL NOT）」「すべきです（SHOULD）」「すべきではありません（SHOULD NOT）」「推奨されます（RECOMMENDED）」「してもよいです（MAY）」「選択できます（OPTIONAL）」は、RFC 2119で説明されているとおりに解釈されます。

1.1. Purposes

1.1. 目的

The MDNs defined in this memo are expected to serve several purposes:

このメモで定義するMDNは、いくつかの目的を果たすことが期待されています。

  1. Inform human beings of the disposition of messages after succcessful delivery, in a manner which is largely independent of human language;
  2. Allow mail user agents to keep track of the disposition of messages sent, by associating returned MDNs with earlier message transmissions;
  3. Convey disposition notification requests and disposition notifications between Internet Mail and "foreign" mail systems via a gateway;
  4. Allow "foreign" notifications to be tunneled through a MIME-capable message system and back into the original messaging system that issued the original notification, or even to a third messaging system;
  5. Allow language-independent, yet reasonably precise, indications of the disposition of a message to be delivered.
  1. 配送が成功した後のメッセージの処理を、人間の言語にほとんど依存しない方法で人間に知らせること。
  2. 返送されたMDNを以前のメッセージ送信と関連付けることにより、メールユーザーエージェントが送信したメッセージの処理を追跡できるようにすること。
  3. ゲートウェイを介して、インターネットメールと「外部の」メールシステムとの間で、処理通知の要求と処理通知を伝達すること。
  4. 「外部の」通知を、MIMEに対応したメッセージシステムを通じてトンネリングし、元の通知を発行した元のメッセージングシステムに戻したり、さらには第三のメッセージングシステムに届けたりできるようにすること。
  5. 言語に依存せず、それでいて十分に正確な、メッセージの処理の表示を配送できるようにすること。

1.2. Requirements

1.2. 要件

These purposes place the following constraints on the notification protocol:

これらの目的から、通知プロトコルには次の制約が課されます。

  1. It must be readable by humans, as well as being machine-parsable.
  2. It must provide enough information to allow message senders (or their user agents) to unambiguously associate an MDN with the message that was sent and the original recipient address for which the MDN is issued (if such information is available), even if the message was forwarded to another recipient address.
  3. It must also be able to describe the disposition of a message independent of any particular human language or of the terminology of any particular mail system.
  4. The specification must be extensible in order to accomodate future requirements.
  1. 機械で解析可能であるだけでなく、人間が読めるものでなければなりません。
  2. メッセージが別の受信者アドレスに転送された場合であっても、メッセージの送信者（またはそのユーザーエージェント）が、MDNを、送信されたメッセージおよびそのMDNの発行対象である元の受信者アドレス（そのような情報が利用可能な場合）と曖昧さなく関連付けられるだけの十分な情報を提供しなければなりません。
  3. また、特定の人間の言語や特定のメールシステムの用語に依存せずに、メッセージの処理を記述できなければなりません。
  4. 将来の要件に対応するために、仕様は拡張可能でなければなりません。

2. Requesting Message Disposition Notifications

2. メッセージ処理通知の要求

Message disposition notifications are requested by including a Disposition-Notification-To header in the message. Further information to be used by the recipient's UA in generating the MDN may be provided by including Original-Recipient and/or Disposition-Notification-Options headers in the message.

メッセージ処理通知は、メッセージにDisposition-Notification-Toヘッダーを含めることによって要求します。メッセージにOriginal-RecipientヘッダーやDisposition-Notification-Optionsヘッダーを含めることにより、受信者のUAがMDNを生成する際に使用する追加の情報を提供してもよいです。

2.1. The Disposition-Notification-To Header

2.1. Disposition-Notification-Toヘッダー

A request that the receiving user agent issue message disposition notifications is made by placing a Disposition-Notification-To header into the message. The syntax of the header, using the ABNF of RFC 822 [2], is

受信側のユーザーエージェントにメッセージ処理通知の発行を求める要求は、メッセージにDisposition-Notification-Toヘッダーを置くことによって行います。このヘッダーの構文は、RFC 822 [2]のABNFを用いると次のとおりです。

  mdn-request-header = "Disposition-Notification-To" ":" 1#mailbox

  mdn-request-header = "Disposition-Notification-To" ":" 1#mailbox

The mailbox token is as specified in RFC 822 [2].

mailboxトークンは、RFC 822 [2]で規定されているとおりです。

The presence of a Disposition-Notification-To header in a message is merely a request for an MDN. The recipients' user agents are always free to silently ignore such a request. Alternatively, an explicit denial of the request for information about the disposition of the message may be sent using the "denied" disposition in an MDN.

メッセージにDisposition-Notification-Toヘッダーが存在することは、単にMDNを要求しているにすぎません。受信者のユーザーエージェントは、そのような要求をいつでも黙って無視して構いません。あるいは、MDNで「denied」処理を使用して、メッセージの処理に関する情報の要求を明示的に拒否することもできます。

An MDN MUST NOT itself have a Disposition-Notification-To header. An MDN MUST NOT be generated in response to an MDN.

MDN自体がDisposition-Notification-Toヘッダーを持っていてはなりません（MUST NOT）。MDNに応答してMDNを生成してはなりません（MUST NOT）。

At most one MDN may be issued on behalf of each particular recipient by their user agent. That is, once an MDN has been issued on behalf of a recipient, no further MDNs may be issued on behalf of that recipient, even if another disposition is performed on the message. However, if a message is forwarded, an MDN may been issued for the recipient doing the forwarding and the recipient of the forwarded message may also cause an MDN to be generated.

ユーザーエージェントが特定の受信者に代わって発行できるMDNは、各受信者につき最大1つです。つまり、ある受信者に代わってMDNがいったん発行されたら、メッセージに対して別の処理が行われたとしても、その受信者に代わってそれ以上MDNを発行することはできません。ただし、メッセージが転送された場合は、転送を行った受信者についてMDNが発行されることがあり、転送されたメッセージの受信者もMDNを生成させることがあります。

While Internet standards normally do not specify the behavior of user interfaces, it is strongly recommended that the user agent obtain the user's consent before sending an MDN. This consent could be obtained for each message through some sort of prompt or dialog box, or globally through the user's setting of a preference. The user might also indicate globally that MDNs are never to be sent or that a "denied" MDN is always sent in response to a request for an MDN.

インターネット標準は通常ユーザーインターフェイスの動作を規定しませんが、ユーザーエージェントはMDNを送信する前にユーザーの同意を得ることが強く推奨されます。この同意は、なんらかのプロンプトやダイアログボックスを通じてメッセージごとに得ることもできますし、ユーザーによる設定を通じて包括的に得ることもできます。また、ユーザーは、MDNを決して送信しないことや、MDNの要求に対して常に「denied」のMDNを送信することを、包括的に指示することもできます。

MDNs SHOULD NOT be sent automatically if the address in the Disposition-Notification-To header differs from the address in the Return-Path header (see RFC 822 [2]). In this case, confirmation from the user SHOULD be obtained, if possible. If obtaining consent is not possible (e.g., because the user is not online at the time), then an MDN SHOULD NOT be sent.

Disposition-Notification-Toヘッダーのアドレスが、Return-Pathヘッダーのアドレス（RFC 822 [2]を参照）と異なる場合、MDNを自動的に送信すべきではありません（SHOULD NOT）。この場合、可能であれば、ユーザーから確認を得るべきです（SHOULD）。同意を得ることができない場合（たとえば、その時点でユーザーがオンラインでないなど）は、MDNを送信すべきではありません（SHOULD NOT）。

Confirmation from the user SHOULD be obtained (or no MDN sent) if there is no Return-Path header in the message, or if there is more than one distinct address in the Disposition-Notification-To header.

メッセージにReturn-Pathヘッダーがない場合や、Disposition-Notification-Toヘッダーに異なるアドレスが複数ある場合は、ユーザーから確認を得る（またはMDNを送信しない）べきです（SHOULD）。

The comparison of the addresses should be done using only the addr-spec (local-part "@" domain) portion, excluding any phrase and route. The comparison MUST be case-sensitive for the local-part and case-insensitive for the domain part.

アドレスの比較は、phraseとrouteを除いた、addr-spec（local-part "@" domain）の部分だけを使用して行うべきです。比較は、local-partについては大文字と小文字を区別し、ドメイン部分については大文字と小文字を区別せずに行わなければなりません（MUST）。

If the message contains more than one Return-Path header, the implementation may pick one to use for the comparison, or treat the situation as a failure of the comparison.

メッセージに複数のReturn-Pathヘッダーが含まれている場合、実装は比較に使用するものを1つ選んでもよいですし、その状況を比較の失敗として扱ってもよいです。

The reason for not automatically sending an MDN if the comparison fails or more than one address is specified is to reduce the possibilities for mail loops and use of MDNs for mail bombing.

比較が失敗した場合や複数のアドレスが指定されている場合にMDNを自動的に送信しない理由は、メールループや、MDNをメール爆弾に利用される可能性を減らすためです。

A message that contains a Disposition-Notification-To header SHOULD also contain a Message-ID header as specified in RFC 822 [2]. This will permit automatic correlation of MDNs with original messages by user agents.

Disposition-Notification-Toヘッダーを含むメッセージは、RFC 822 [2]で規定されているMessage-IDヘッダーも含むべきです（SHOULD）。これにより、ユーザーエージェントがMDNと元のメッセージを自動的に関連付けられるようになります。

If it is desired to request message disposition notifications for some recipients and not others, two copies of the message should be sent, one with an Disposition-Notification-To header and one without. Many of the other headers of the message (e.g., To, cc) will be the same in both copies. The recipients in the respective message envelopes determine for whom message disposition notifications are requested and for whom they are not. If desired, the Message-ID header may be the same in both copies of the message. Note that there are other situations (e.g., bcc) in which it is necessary to send multiple copies of a message with slightly different headers. The combination of such situations and the need to request MDNs for a subset of all recipients may result in more than two copies of a message being sent, some with a Disposition- Notification-To header and some without.

一部の受信者にはメッセージ処理通知を要求し、他の受信者には要求しないようにしたい場合は、メッセージのコピーを2つ、つまりDisposition-Notification-Toヘッダーを付けたものと付けないものを送信すべきです。メッセージの他の多くのヘッダー（たとえば、To、cc）は、両方のコピーで同じになります。それぞれのメッセージのエンベロープにある受信者によって、誰に対してメッセージ処理通知を要求し、誰に対して要求しないかが決まります。必要であれば、Message-IDヘッダーをメッセージの両方のコピーで同じにしても構いません。なお、わずかに異なるヘッダーを持つメッセージのコピーを複数送信する必要がある状況は、ほかにもあります（たとえば、bcc）。そのような状況と、全受信者の一部に対してMDNを要求する必要性とが組み合わさると、メッセージのコピーが3つ以上送信され、その一部にはDisposition- Notification-Toヘッダーが付き、一部には付かないということになる場合があります。

Messages posted to newsgroups SHOULD NOT have a Disposition-Notification-To header.

ニュースグループに投稿されるメッセージは、Disposition-Notification-Toヘッダーを持つべきではありません（SHOULD NOT）。

2.2. The Disposition-Notification-Options Header

2.2. Disposition-Notification-Optionsヘッダー

Future extensions to this specification may require that information be supplied to the recipient's UA for additional control over how and what MDNs are generated. The Disposition-Notification-Options header provides an extensible mechanism for such information. The syntax of this header, using the ABNF of RFC 822 [2], is

この仕様の将来の拡張では、MDNをどのように生成するか、どのようなMDNを生成するかを追加で制御するために、受信者のUAに情報を提供することが必要になるかもしれません。Disposition-Notification-Optionsヘッダーは、そのような情報のための拡張可能な仕組みを提供します。このヘッダーの構文は、RFC 822 [2]のABNFを用いると次のとおりです。

  Disposition-Notification-Options =
       "Disposition-Notification-Options" ":"
       disposition-notification-parameters

  Disposition-Notification-Options =
       "Disposition-Notification-Options" ":"
       disposition-notification-parameters

  disposition-notification-parameters = parameter *(";" parameter)

  disposition-notification-parameters = parameter *(";" parameter)

  parameter = attribute "=" importance "," 1#value

  parameter = attribute "=" importance "," 1#value

  importance = "required" / "optional"

  importance = "required" / "optional"

The definitions of attribute and value are as in the definition of the Content-Type header in RFC 2045 [4].

attributeとvalueの定義は、RFC 2045 [4]のContent-Typeヘッダーの定義と同じです。

An importance of "required" indicates that interpretation of the parameter is necessary for proper generation of an MDN in response to this request. If a UA does not understand the meaning of the parameter, it MUST NOT generate an MDN with any disposition type other than "failed" in response to the request. An importance of "optional" indicates that a UA that does not understand the meaning of this parameter MAY generate an MDN in response anyway, ignoring the value of the parameter.

importanceが「required」であることは、この要求に応答してMDNを適切に生成するには、そのパラメーターの解釈が必要であることを示します。UAがパラメーターの意味を理解できない場合、その要求に応答して「failed」以外の処理タイプのMDNを生成してはなりません（MUST NOT）。importanceが「optional」である場合、このパラメーターの意味を理解できないUAは、パラメーターの値を無視して、それでも応答としてMDNを生成してもよいです（MAY）。

No parameters are defined in this specification. Parameters may be defined in the future by later revisions or extensions to this specification. Parameter attribute names beginning with "X-" will never be defined as standard names; such names are reserved for experimental use. MDN parameter names not beginning with "X-" MUST be registered with the Internet Assigned Numbers Authority (IANA) and described in a standards-track RFC or an experimental RFC approved by the IESG. See Section 10 for a registration form.

この仕様ではパラメーターを定義していません。パラメーターは、将来、この仕様の後の改訂や拡張によって定義されることがあります。「X-」で始まるパラメーター属性名が標準の名前として定義されることは決してありません。そのような名前は実験的な使用のために予約されています。「X-」で始まらないMDNのパラメーター名は、Internet Assigned Numbers Authority（IANA）に登録し、標準化過程のRFC、またはIESGが承認した実験的RFCで記述しなければなりません（MUST）。登録フォームについてはセクション10を参照してください。

If a required parameter is not understood or contains some sort of error, the receiving UA SHOULD issue an MDN with a disposition type of "failed" (see Section 3.2.6) and include a Failure field (see Section 3.2.7) that further describes the problem. MDNs with the a disposition type of "failed" and a "Failure" field MAY also be generated when other types of errors are detected in the parameters of the Disposition-Notification-Options header.

必須（required）のパラメーターが理解できない場合や、なんらかのエラーを含んでいる場合、受信側のUAは、処理タイプ「failed」（セクション3.2.6を参照）のMDNを発行し、問題をさらに説明するFailureフィールド（セクション3.2.7を参照）を含めるべきです（SHOULD）。Disposition-Notification-Optionsヘッダーのパラメーターに他の種類のエラーが検出された場合にも、処理タイプ「failed」と「Failure」フィールドを持つMDNを生成してもよいです（MAY）。

However, an MDN with a disposition type of "failed" MUST NOT be generated if the user has indicated a preferance that MDNs are not to be sent. If user consent would be required for an MDN of some other disposition type to be sent, user consent SHOULD also be obtained before sending an MDN with a disposition type of "failed".

ただし、MDNを送信しないことをユーザーが希望として示している場合は、処理タイプ「failed」のMDNを生成してはなりません（MUST NOT）。他の処理タイプのMDNを送信するのにユーザーの同意が必要となる場合は、処理タイプ「failed」のMDNを送信する前にも、ユーザーの同意を得るべきです（SHOULD）。

2.3. The Original-Recipient Header

2.3. Original-Recipientヘッダー

Since electronic mail addresses may be rewritten while the message is in transit, it is useful for the original recipient address to be made available by the delivering MTA. The delivering MTA may be able to obtain this information from the ORCPT parameter of the SMTP RCPT TO command, as defined in RFC 1891 [8]. If this information is available, the delivering MTA SHOULD insert an Original-Recipient header at the beginning of the message (along with the Return-Path header). The delivering MTA MAY delete any other Original-Recipient headers that occur in the message. The syntax of this header, using the ABNF of RFC 822 [2], is as follows

電子メールのアドレスはメッセージの転送中に書き換えられることがあるため、配送を行うMTAが元の受信者アドレスを利用可能にしておくと便利です。配送を行うMTAは、RFC 1891 [8]で定義されているSMTPのRCPT TOコマンドのORCPTパラメーターから、この情報を取得できる場合があります。この情報が利用可能な場合、配送を行うMTAは、メッセージの先頭に（Return-Pathヘッダーとともに）Original-Recipientヘッダーを挿入すべきです（SHOULD）。配送を行うMTAは、メッセージ中にある他のOriginal-Recipientヘッダーを削除してもよいです（MAY）。このヘッダーの構文は、RFC 822 [2]のABNFを用いると次のとおりです。

  original-recipient-header =
       "Original-Recipient" ":" address-type ";" generic-address

  original-recipient-header =
       "Original-Recipient" ":" address-type ";" generic-address

The address-type and generic-address token are as as specified in the description of the Original-Recipient field in section 3.2.3.

address-typeトークンとgeneric-addressトークンは、セクション3.2.3のOriginal-Recipientフィールドの説明で規定されているとおりです。

The purpose of carrying the original recipient information and returning it in the MDN is to permit automatic correlation of MDNs with the original message on a per-recipient basis.

元の受信者の情報を運び、それをMDNで返す目的は、受信者ごとにMDNと元のメッセージを自動的に関連付けられるようにすることです。

2.4. Use with the Message/Partial Content Type

2.4. Message/Partialコンテンツタイプとの併用

The use of the headers Disposition-Notification-To, Disposition-Notification-Options, and Original-Recipient with the MIME Message/partial content type (RFC 2046 [5]) requires further definition.

Disposition-Notification-To、Disposition-Notification-Options、Original-Recipientの各ヘッダーを、MIMEのMessage/partialコンテンツタイプ（RFC 2046 [5]）とともに使用する場合については、さらに定義が必要です。

When a message is segmented into two or more message/partial fragments, the three headers mentioned in the above paragraph SHOULD be placed in the "inner" or "enclosed" message (using the terms of RFC 2046 [5]). These headers SHOULD NOT be used in the headers of any of the fragments themselves.

メッセージが2つ以上のmessage/partialフラグメントに分割される場合、前の段落で述べた3つのヘッダーは、「内側の（inner）」または「包まれた（enclosed）」メッセージ（RFC 2046 [5]の用語を使用）に置くべきです（SHOULD）。これらのヘッダーを、フラグメント自体のヘッダーで使用すべきではありません（SHOULD NOT）。

When the multiple message/partial fragments are reassembled, the following applies. If these headers occur along with the other headers of a message/partial fragment message, they pertain to an MDN to be generated for the fragment. If these headers occur in the headers of the "inner" or "enclosed" message (using the terms of RFC 2046 [5]), they pertain to an MDN to be generated for the reassembled message. Section 5.2.2.1 of RFC 2046 [5]) is amended to specify that, in addition to the headers specified there, the three headers described in this specification are to be appended, in order, to the headers of the reassembled message. Any occurances of the three headers defined here in the headers of the initial enclosing message must not be copied to the reassembled message.

複数のmessage/partialフラグメントが再構築される場合は、次のとおりです。これらのヘッダーがmessage/partialフラグメントのメッセージの他のヘッダーと一緒に現れる場合、それらはそのフラグメントについて生成されるMDNに関するものです。これらのヘッダーが「内側の」または「包まれた」メッセージ（RFC 2046 [5]の用語を使用）のヘッダーに現れる場合、それらは再構築されたメッセージについて生成されるMDNに関するものです。RFC 2046 [5])のセクション5.2.2.1を修正し、そこで規定されているヘッダーに加えて、この仕様で説明する3つのヘッダーを、順番どおりに、再構築されたメッセージのヘッダーに追加することを規定します。最初の包含メッセージのヘッダーにここで定義する3つのヘッダーが現れても、それらを再構築されたメッセージにコピーしてはいけません。

3. Format of a Message Disposition Notification

3. メッセージ処理通知の形式

A message disposition notification is a MIME message with a top-level content-type of multipart/report (defined in RFC 1892 [7]). When a multipart/report content is used to transmit an MDN:

メッセージ処理通知は、トップレベルのコンテンツタイプがmultipart/report（RFC 1892 [7]で定義）であるMIMEメッセージです。multipart/reportコンテンツをMDNの送信に使用する場合は、次のとおりです。

  1. The report-type parameter of the multipart/report content is "disposition-notification".
  2. The first component of the multipart/report contains a human-readable explanation of the MDN, as described in RFC 1892 [7].
  3. The second component of the multipart/report is of content-type message/disposition-notification, described in section 3.1 of this document.

  4. If the original message or a portion of the message is to be returned to the sender, it appears as the third component of the multipart/report. The decision of whether or not to return the message or part of the message is up to the UA generating the MDN. However, in the case of encrypted messages requesting MDNs, encrypted message text MUST be returned, if it is returned at all, only in its original encrypted form.

    NOTE: For message dispostion notifications gatewayed from foreign systems, the headers of the original message may not be available. In this case the third component of the MDN may be omitted, or it may contain "simulated" RFC 822 headers which contain equivalent information. In particular, it is very desirable to preserve the subject and date fields from the original message.

  1. multipart/reportコンテンツのreport-typeパラメーターは「disposition-notification」です。
  2. multipart/reportの最初の構成要素には、RFC 1892 [7]で説明されているとおり、人間が読めるMDNの説明が含まれます。
  3. multipart/reportの2番目の構成要素は、この文書のセクション3.1で説明するmessage/disposition-notificationコンテンツタイプです。

  4. 元のメッセージまたはメッセージの一部を送信者に返す場合、それはmultipart/reportの3番目の構成要素として現れます。メッセージまたはメッセージの一部を返すかどうかの判断は、MDNを生成するUAに委ねられます。ただし、MDNを要求する暗号化されたメッセージの場合、暗号化されたメッセージのテキストを返すのであれば、元の暗号化された形式のままでのみ返さなければなりません（MUST）。

    注：外部のシステムからゲートウェイで変換されたメッセージ処理通知については、元のメッセージのヘッダーが利用できない場合があります。この場合、MDNの3番目の構成要素は省略してもよいですし、同等の情報を含む「模擬的な」RFC 822ヘッダーを含めてもよいです。特に、元のメッセージのsubjectフィールドとdateフィールドを保持することが非常に望まれます。

The MDN MUST be addressed (in both the message header and the transport envelope) to the address(es) from the Disposition-Notification-To header from the original message for which the MDN is being generated.

MDNは、（メッセージヘッダーと転送エンベロープの両方で）そのMDNの生成対象である元のメッセージのDisposition-Notification-Toヘッダーにあるアドレスに宛てて送らなければなりません（MUST）。

The From field of the message header of the MDN MUST contain the address of the person for whom the message disposition notification is being issued.

MDNのメッセージヘッダーのFromフィールドには、メッセージ処理通知の発行対象となっている人のアドレスを含めなければなりません（MUST）。

The envelope sender address (i.e., SMTP MAIL FROM) of the MDN MUST be null (<>), specifying that no Delivery Status Notification messages or other messages indicating successful or unsuccessful delivery are to be sent in response to an MDN.

MDNのエンベロープ送信者アドレス（つまり、SMTPのMAIL FROM）は空（<>）でなければなりません（MUST）。これは、MDNに応答して配送状態通知（Delivery Status Notification）メッセージや、配送の成功または失敗を示す他のメッセージを送信してはならないことを示します。

A message disposition notification MUST NOT itself request an MDN. That is, it MUST NOT contain a Disposition-Notification-To header.

メッセージ処理通知自体がMDNを要求してはなりません（MUST NOT）。つまり、Disposition-Notification-Toヘッダーを含んでいてはなりません（MUST NOT）。

The Message-ID header (if present) for an MDN MUST be different from the Message-ID of the message for which the MDN is being issued.

MDNのMessage-IDヘッダー（存在する場合）は、そのMDNの発行対象であるメッセージのMessage-IDとは異なっていなければなりません（MUST）。

A particular MDN describes the disposition of exactly one message for exactly one recipient. Multiple MDNs may be generated as a result of one message submission, one per recipient. However, due to the circumstances described in Section 2.1, MDNs may not be generated for some recipients for which MDNs were requested.

個々のMDNは、ちょうど1つの受信者に対するちょうど1つのメッセージの処理を記述します。1回のメッセージ送信の結果として、受信者ごとに1つずつ、複数のMDNが生成されることがあります。ただし、セクション2.1で説明した事情により、MDNが要求された受信者の一部についてMDNが生成されないこともあります。

message/disposition-notificationの本体は、RFC 822のヘッダー「フィールド」のABNF（[2]を参照）に従ってフォーマットされた、1つ以上の「フィールド」から構成されます。RFC 822のABNFを用いると、message/disposition-notificationコンテンツの構文は次のとおりです。

3.1.1. General conventions for fields

3.1.1. フィールドに関する一般的な規則

Since these fields are defined according to the rules of RFC 822 [2], the same conventions for continuation lines and comments apply. Notification fields may be continued onto multiple lines by beginning each additional line with a SPACE or HTAB. Text which appears in parentheses is considered a comment and not part of the contents of that notification field. Field names are case-insensitive, so the names of notification fields may be spelled in any combination of upper and lower case letters. Comments in notification fields may use the "encoded-word" construct defined in RFC 2047 [6].

これらのフィールドはRFC 822 [2]の規則に従って定義されるため、継続行とコメントについても同じ規則が適用されます。通知フィールドは、追加の各行をSPACEまたはHTABで始めることにより、複数行に継続できます。括弧内に現れるテキストはコメントとみなされ、その通知フィールドの内容の一部とはみなされません。フィールド名は大文字と小文字を区別しないため、通知フィールドの名前は大文字と小文字を任意に組み合わせて綴ることができます。通知フィールド内のコメントでは、RFC 2047 [6]で定義されている「encoded-word」構造を使用できます。

3.1.2. "*-type" subfields

3.1.2. 「*-type」サブフィールド

Several fields consist of a "-type" subfield, followed by a semi-colon, followed by "*text". For these fields, the keyword used in the address-type or MTA-type subfield indicates the expected format of the address or MTA-name that follows.

いくつかのフィールドは、「-type」サブフィールド、セミコロン、「*text」の順で構成されます。これらのフィールドでは、address-typeまたはMTA-typeサブフィールドで使用されるキーワードが、その後に続くアドレスまたはMTA名の想定される形式を示します。

The "-type" subfields are defined as follows:

「-type」サブフィールドは次のように定義されます。

  1. An "address-type" specifies the format of a mailbox address. For example, Internet Mail addresses use the "rfc822" address-type.

     address-type = atom

  2. An "MTA-name-type" specifies the format of a mail transfer agent name. For example, for an SMTP server on an Internet host, the MTA name is the domain name of that host, and the "dns" MTA-name-type is used.

     mta-name-type = atom

  1. 「address-type」は、メールボックスアドレスの形式を指定します。たとえば、インターネットメールのアドレスは「rfc822」のaddress-typeを使用します。

     address-type = atom

  2. 「MTA-name-type」は、メール転送エージェントの名前の形式を指定します。たとえば、インターネットホスト上のSMTPサーバーの場合、MTA名はそのホストのドメイン名であり、「dns」のMTA-name-typeを使用します。

     mta-name-type = atom

Values for address-type and mta-name-type are case-insensitive. Thus address-type values of "RFC822" and "rfc822" are equivalent.

address-typeとmta-name-typeの値は、大文字と小文字を区別しません。したがって、address-typeの値「RFC822」と「rfc822」は同等です。

The Internet Assigned Numbers Authority (IANA) will maintain a registry of address-type and mta-name-type values, along with descriptions of the meanings of each, or a reference to a one or more specifications that provide such descriptions. (The "rfc822" address-type is defined in RFC 1891 [8].) Registration forms for address-type and mta-name-type appear in RFC 1894 [9].

Internet Assigned Numbers Authority（IANA）は、address-typeとmta-name-typeの値のレジストリーを、それぞれの意味の説明、またはそのような説明を提供する1つ以上の仕様への参照とともに維持します。（「rfc822」のaddress-typeは、RFC 1891 [8]で定義されています。）address-typeとmta-name-typeの登録フォームは、RFC 1894 [9]にあります。

IANA will not accept registrations for any address-type name that begins with "X-". These type names are reserved for experimental use.

IANAは、「X-」で始まるaddress-type名の登録を受け付けません。これらのタイプ名は実験的な使用のために予約されています。

3.1.3. RFC 822から取り込む字句トークン

The following lexical tokens, defined in RFC 822 [2], are used in the ABNF grammar for MDNs: atom, CRLF, mailbox, msg-id, text.

RFC 822 [2]で定義されている次の字句トークンを、MDNのABNF文法で使用します：atom、CRLF、mailbox、msg-id、text。

3.2. message/disposition-notificationのフィールド

3.2.1. The Reporting-UA field

3.2.1. Reporting-UAフィールド 

  reporting-ua-field = "Reporting-UA" ":" ua-name
                       [ ";" ua-product ]

  reporting-ua-field = "Reporting-UA" ":" ua-name
                       [ ";" ua-product ]

  ua-name = *text

  ua-name = *text

  ua-product = *text

  ua-product = *text

The Reporting-UA field is defined as follows:

Reporting-UAフィールドは次のように定義されます。

A MDN describes the disposition of a message after it has been delivered to a recipient. In all cases, the Reporting-UA is the UA that performed the disposition described in the MDN. This field is optional, but recommended. For Internet Mail user agents, it is recommended that this field contain both the DNS name of the particular instance of the UA that generated the MDN and the name of the product. For example,

MDNは、受信者に配送された後のメッセージの処理を記述します。いずれの場合も、Reporting-UAは、MDNで記述される処理を行ったUAです。このフィールドは省略可能ですが、推奨されます。インターネットメールのユーザーエージェントでは、このフィールドに、MDNを生成したUAの特定のインスタンスのDNS名と製品名の両方を含めることが推奨されます。たとえば、次のとおりです。

  Reporting-UA:  rogers-mac.dcrt.nih.gov; Foomail 97.1

  Reporting-UA:  rogers-mac.dcrt.nih.gov; Foomail 97.1

報告を行うUAが複数の構成要素（たとえば、基本プログラムとプラグイン）から成る場合は、製品名のリストを含めることでそれを示すことができます。

3.2.2. The MDN-Gateway field

3.2.2. MDN-Gatewayフィールド

The MDN-Gateway field indicates the name of the gateway or MTA that translated a foreign (non-Internet) message disposition notification into this MDN. This field MUST appear in any MDN which was translated by a gateway from a foreign system into MDN format, and MUST NOT appear otherwise.

MDN-Gatewayフィールドは、外部の（インターネット以外の）メッセージ処理通知をこのMDNに変換したゲートウェイまたはMTAの名前を示します。ゲートウェイによって外部のシステムからMDN形式に変換されたすべてのMDNに、このフィールドが現れなければなりません（MUST）。それ以外の場合は、このフィールドが現れてはなりません（MUST NOT）。

     mdn-gateway-field = "MDN-Gateway" ":" mta-name-type ";" mta-name

     mdn-gateway-field = "MDN-Gateway" ":" mta-name-type ";" mta-name

     mta-name = *text

     mta-name = *text

For gateways into Internet Mail, the MTA-name-type will normally be "smtp", and the mta-name will be the Internet domain name of the gateway.

インターネットメールへのゲートウェイの場合、MTA-name-typeは通常「smtp」であり、mta-nameはゲートウェイのインターネットドメイン名になります。

3.2.3. Original-Recipient field

3.2.3. Original-Recipientフィールド

The Original-Recipient field indicates the original recipient address as specified by the sender of the message for which the MDN is being issued. For Internet Mail messages the value of the Original-Recipient field is obtained from the Original-Recipient header from the message for which the MDN is being generated. If there is no Original-Recipient header in the message, then the Original-Recipient field MUST be omitted, unless the same information is reliably available some other way. If there is an Original-Recipient header in the original message (or original recipient information is reliably available some other way), then the Original-Recipient field must be supplied. If there is more than one Original-Recipient header in the message, the UA may choose the one to use or act as if no Original-Recipient header is present.

Original-Recipientフィールドは、MDNの発行対象であるメッセージの送信者が指定した、元の受信者アドレスを示します。インターネットメールのメッセージの場合、Original-Recipientフィールドの値は、MDNの生成対象であるメッセージのOriginal-Recipientヘッダーから取得します。メッセージにOriginal-Recipientヘッダーがない場合、同じ情報が他の方法で確実に利用できるのでない限り、Original-Recipientフィールドを省略しなければなりません（MUST）。元のメッセージにOriginal-Recipientヘッダーがある（または元の受信者の情報が他の方法で確実に利用できる）場合は、Original-Recipientフィールドを提供しなければなりません。メッセージに複数のOriginal-Recipientヘッダーがある場合、UAは使用するものを選んでもよいですし、Original-Recipientヘッダーが存在しないかのように動作してもよいです。

  original-recipient-field =
       "Original-Recipient" ":" address-type ";" generic-address

  original-recipient-field =
       "Original-Recipient" ":" address-type ";" generic-address

  generic-address = *text

  generic-address = *text

The address-type field indicates the type of the original recipient address. If the message originated within the Internet, the address-type field field will normally be "rfc822", and the address will be according to the syntax specified in RFC 822 [2]. The value "unknown" should be used if the Reporting UA cannot determine the type of the original recipient address from the message envelope. This address is the same as that provided by the sender and can be used to automatically correlate MDN reports with original messages on a per recipient basis.

address-typeフィールドは、元の受信者アドレスの種類を示します。メッセージがインターネット内で発信された場合、address-typeフィールドは通常「rfc822」であり、アドレスはRFC 822 [2]で規定されている構文に従います。報告を行うUAが、メッセージのエンベロープから元の受信者アドレスの種類を判断できない場合は、値「unknown」を使用すべきです。このアドレスは送信者が提供したものと同じであり、受信者ごとにMDNの報告を元のメッセージと自動的に関連付けるために使用できます。

3.2.4. Final-Recipient field

3.2.4. Final-Recipientフィールド

The Final-Recipient field indicates the recipient for which the MDN is being issued. This field MUST be present.

Final-Recipientフィールドは、MDNの発行対象である受信者を示します。このフィールドは存在しなければなりません（MUST）。

The syntax of the field is as follows:

このフィールドの構文は次のとおりです。

  final-recipient-field =
       "Final-Recipient" ":" address-type ";" generic-address

  final-recipient-field =
       "Final-Recipient" ":" address-type ";" generic-address

The generic-address subfield of the Final-Recipient field MUST contain the mailbox address of the recipient (from the From header of the MDN) as it was when the MDN was generated by the UA.

Final-Recipientフィールドのgeneric-addressサブフィールドには、UAがMDNを生成した時点での受信者のメールボックスアドレス（MDNのFromヘッダーにあるもの）を含めなければなりません（MUST）。

The Final-Recipient address may differ from the address originally provided by the sender, because it may have been transformed during forwarding and gatewaying into an totally unrecognizable mess. However, in the absence of the optional Original-Recipient field, the Final-Recipient field and any returned content may be the only information available with which to correlate the MDN with a particular message recipient.

Final-Recipientのアドレスは、転送やゲートウェイ変換の間に完全に判別できないほどの状態に変換されている可能性があるため、送信者が最初に提供したアドレスとは異なる場合があります。しかし、省略可能なOriginal-Recipientフィールドがない場合、MDNを特定のメッセージ受信者と関連付けるために利用できる情報は、Final-Recipientフィールドと返されたコンテンツだけかもしれません。

The address-type subfield indicates the type of address expected by the reporting MTA in that context. Recipient addresses obtained via SMTP will normally be of address-type "rfc822".

address-typeサブフィールドは、その文脈で報告を行うMTAが想定するアドレスの種類を示します。SMTPを介して取得された受信者アドレスは、通常、address-typeが「rfc822」になります。

Since mailbox addresses (including those used in the Internet) may be case sensitive, the case of alphabetic characters in the address MUST be preserved.

メールボックスアドレス（インターネットで使用されるものを含む）は大文字と小文字を区別する場合があるため、アドレス内の英字の大文字と小文字を保持しなければなりません（MUST）。

3.2.5. Original-Message-ID field

3.2.5. Original-Message-IDフィールド

The Original-Message-ID field indicates the message-ID of the message for which the MDN is being issued. It is obtained from the Message-ID header of the message for which the MDN is issued. This field MUST be present if the original message contained a Message-ID header. The syntax of the field is

Original-Message-IDフィールドは、MDNの発行対象であるメッセージのmessage-IDを示します。これは、MDNの発行対象であるメッセージのMessage-IDヘッダーから取得します。元のメッセージにMessage-IDヘッダーが含まれていた場合、このフィールドは存在しなければなりません（MUST）。このフィールドの構文は次のとおりです。

     original-message-id-field = "Original-Message-ID" ":" msg-id

     original-message-id-field = "Original-Message-ID" ":" msg-id

The msg-id token is as specified in RFC 822 [2].

msg-idトークンは、RFC 822 [2]で規定されているとおりです。

3.2.6. Disposition field

3.2.6. Dispositionフィールド

The Disposition field indicates the action performed by the Reporting-UA on behalf of the user. This field MUST be present.

Dispositionフィールドは、Reporting-UAがユーザーに代わって行った動作を示します。このフィールドは存在しなければなりません（MUST）。

The syntax for the Disposition field is:

Dispositionフィールドの構文は次のとおりです。

  disposition-field = "Disposition" ":" disposition-mode ";"
                      disposition-type
                      [ '/' disposition-modifier
                        *( "," dispostion-modifier ) ]

  disposition-field = "Disposition" ":" disposition-mode ";"
                      disposition-type
                      [ '/' disposition-modifier
                        *( "," dispostion-modifier ) ]

  disposition-mode = action-mode "/" sending-mode

  disposition-mode = action-mode "/" sending-mode

  action-mode = "manual-action" / "automatic-action"

  action-mode = "manual-action" / "automatic-action"

  sending-mode = "MDN-sent-manually" / "MDN-sent-automatically"

  sending-mode = "MDN-sent-manually" / "MDN-sent-automatically"

  disposition-type = "displayed"
                   / "dispatched"
                   / "processed"
                   / "deleted"
                   / "denied"
                   / "failed"

  disposition-type = "displayed"
                   / "dispatched"
                   / "processed"
                   / "deleted"
                   / "denied"
                   / "failed"

  disposition-modifier = ( "error" / "warning" )
                       / ( "superseded" / "expired" /
                           "mailbox-terminated" )
                       / disposition-modifier-extension

  disposition-modifier = ( "error" / "warning" )
                       / ( "superseded" / "expired" /
                           "mailbox-terminated" )
                       / disposition-modifier-extension

  disposition-modifier-extension = atom

  disposition-modifier-extension = atom

The disposition-mode, disposition-type and disposition-modifier may be spelled in any combination of upper and lower case characters.

disposition-mode、disposition-type、disposition-modifierは、大文字と小文字を任意に組み合わせて綴ることができます。

3.2.6.1. Disposition modes
3.2.6.1. 処理モード

The following disposition modes are defined:

次の処理モードを定義します。

"manual-action"
The disposition described by the disposition type was a result of an explicit instruction by the user rather than some sort of automatically performed action.
"automatic-action"

The disposition described by the disposition type was a result of an automatic action, rather than an explicit instruction by the user for this message.

"Manual-action" and "automatic-action" are mutually exclusive. One or the other must be specified.

"MDN-sent-manually"
The user explicity gave permission for this particular MDN to be sent.
"MDN-sent-automatically"

The MDN was sent because the UA had previously been configured to do so automatically.

"MDN-sent-manually" and "MDN-sent-automatically" are mutually exclusive. One or the other must be specified.

"manual-action"
処理タイプで記述される処理は、なんらかの自動的に行われた動作ではなく、ユーザーによる明示的な指示の結果でした。
"automatic-action"

処理タイプで記述される処理は、このメッセージに対するユーザーの明示的な指示ではなく、自動的な動作の結果でした。

「Manual-action」と「automatic-action」は相互に排他的です。どちらか一方を指定しなければなりません。

"MDN-sent-manually"
ユーザーが、この特定のMDNを送信することを明示的に許可しました。
"MDN-sent-automatically"

UAが以前から自動的に送信するように設定されていたため、MDNが送信されました。

「MDN-sent-manually」と「MDN-sent-automatically」は相互に排他的です。どちらか一方を指定しなければなりません。

3.2.6.2. Disposition types
3.2.6.2. 処理タイプ

The following disposition-types are defined:

次のdisposition-type（処理タイプ）を定義します。

"displayed"
The message has been displayed by the UA to someone reading the recipient's mailbox. There is no guarantee that the content has been read or understood.
"dispatched"
The message has been sent somewhere in some manner (e.g., printed, faxed, forwarded) without necessarily having been previously displayed to the user. The user may or may not see the message later.
"processed"
The message has been processed in some manner (i.e., by some sort of rules or server) without being displayed to the user. The user may or may not see the message later, or there may not even be a human user associated with the mailbox.
"deleted"
The message has been deleted. The recipient may or may not have seen the message. The recipient might "undelete" the message at a later time and read the message.
"denied"
The recipient does not wish the sender to be informed of the message's disposition. A UA may also siliently ignore message disposition requests in this situation.
"failed"
A failure occurred that prevented the proper generation of an MDN. More information about the cause of the failure may be contained in a Failure field. The "failed" disposition type is not to be used for the situation in which there is is some problem in processing the message other than interpreting the request for an MDN. The "processed" or other disposition type with appropriate disposition modifiers is to be used in such situations.
"displayed"
メッセージは、UAによって、受信者のメールボックスを読んでいる誰かに表示されました。内容が読まれたこと、または理解されたことは保証されません。
"dispatched"
メッセージは、必ずしも事前にユーザーに表示されることなく、なんらかの方法でどこかに送られました（たとえば、印刷、ファクス送信、転送）。ユーザーは後でメッセージを見るかもしれませんし、見ないかもしれません。
"processed"
メッセージは、ユーザーに表示されることなく、なんらかの方法で（つまり、なんらかのルールやサーバーによって）処理されました。ユーザーは後でメッセージを見るかもしれませんし、見ないかもしれません。あるいは、そのメールボックスに関連付けられた人間のユーザーがそもそも存在しないかもしれません。
"deleted"
メッセージは削除されました。受信者はメッセージを見たかもしれませんし、見ていないかもしれません。受信者は後でメッセージを「削除取り消し」して読むかもしれません。
"denied"
受信者は、メッセージの処理を送信者に知らせることを望んでいません。この状況では、UAはメッセージ処理の要求を黙って無視することもできます。
"failed"
MDNの適切な生成を妨げる障害が発生しました。障害の原因に関する詳しい情報がFailureフィールドに含まれている場合があります。「failed」処理タイプは、MDNの要求の解釈以外で、メッセージの処理になんらかの問題がある状況に使用するものではありません。そのような状況では、「processed」または他の処理タイプを、適切な処理修飾子とともに使用します。
3.2.6.3. Disposition modifiers
3.2.6.3. 処理修飾子

The following disposition modifiers are defined:

次の処理修飾子を定義します。

"error"
An error of some sort occurred that prevented successful processing of the message. Further information is contained in an Error field.
"warning"
The message was successfully processed but some sort of exceptional condition occurred. Further information is contained in a Warning field.
"superseded"
The message has been automatically rendered obsolete by another message received. The recipient may still access and read the message later.
"expired"
The message has reached its expiration date and has been automatically removed from the recipient's mailbox.
"mailbox-terminated"

The recipient's mailbox has been terminated and all message in it automatically removed.

"Obsoleted", "expired", and "terminated" are to be used with the "deleted" disposition type and the "autoaction" and "autosent" disposition modifiers.

disposition-modifier-extension

Additional disposition modifiers may be defined in the future by later revisions or extensions to this specification. Disposition value names beginning with "X-" will never be defined as standard values; such names are reserved for experimental use. MDN disposition value names NOT beginning with "X-" MUST be registered with the Internet Assigned Numbers Authority (IANA) and described in a standards-track RFC or an experimental RFC approved by the IESG. See Section 10 for a registration form. MDNs with disposition modifier names not understood by the receiving UA MAY be silently ignored or placed in the user's mailbox without special inter- pretation. They MUST not cause any error message to be sent to the sender of the MDN.

If an UA developer does not wish to register the meanings of such disposition modifier extensions, "X-" modifiers may be used for this purpose. To avoid name collisions, the name of the UA implementation should follow the "X-", (e.g. "X-Foomail-fratzed").

"error"
メッセージの処理の成功を妨げる、なんらかのエラーが発生しました。詳しい情報はErrorフィールドに含まれています。
"warning"
メッセージは正常に処理されましたが、なんらかの例外的な状況が発生しました。詳しい情報はWarningフィールドに含まれています。
"superseded"
メッセージは、受信した別のメッセージによって自動的に廃止されました。受信者は、後でもそのメッセージにアクセスして読むことができます。
"expired"
メッセージは有効期限に達し、受信者のメールボックスから自動的に削除されました。
"mailbox-terminated"

受信者のメールボックスは終了され、その中のすべてのメッセージは自動的に削除されました。

「Obsoleted」「expired」「terminated」は、「deleted」処理タイプ、および「autoaction」と「autosent」の処理修飾子とともに使用します。

disposition-modifier-extension

追加の処理修飾子は、将来、この仕様の後の改訂や拡張によって定義されることがあります。「X-」で始まる処理値の名前が標準の値として定義されることは決してありません。そのような名前は実験的な使用のために予約されています。「X-」で始まらないMDNの処理値の名前は、Internet Assigned Numbers Authority（IANA）に登録し、標準化過程のRFC、またはIESGが承認した実験的RFCで記述しなければなりません（MUST）。登録フォームについてはセクション10を参照してください。受信側のUAが理解できない処理修飾子名を持つMDNは、黙って無視したり、特別な解釈をせずにユーザーのメールボックスに置いたりしてもよいです（MAY）。そのようなMDNが原因でMDNの送信者にエラーメッセージが送信されることがないようにしなければなりません（MUST）。

UAの開発者がそのような処理修飾子の拡張の意味を登録することを望まない場合は、この目的のために「X-」修飾子を使用できます。名前の衝突を避けるために、「X-」の後にはUA実装の名前を続けるべきです（たとえば、「X-Foomail-fratzed」）。

It is not required that a UA be able to generate all of the possible values of the Disposition field.

UAがDispositionフィールドのすべての可能な値を生成できることは要求されません。

One and only one MDN may be issued on behalf of each particular recipient by their user agent. That is, once an MDN has been issued on behalf of a recipient, no further MDNs may be issued on behalf of that recipient, even if another disposition is performed on the message. However, if a message is forwarded, a "dispatched" MDN may been issued for the recipient doing the forwarding and the recipient of the forwarded message may also cause an MDN to be generated.

ユーザーエージェントが特定の受信者に代わって発行できるMDNは、各受信者につきただ1つです。つまり、ある受信者に代わってMDNがいったん発行されたら、メッセージに対して別の処理が行われたとしても、その受信者に代わってそれ以上MDNを発行することはできません。ただし、メッセージが転送された場合は、転送を行った受信者について「dispatched」のMDNが発行されることがあり、転送されたメッセージの受信者もMDNを生成させることがあります。

3.2.7. Failure, Error and Warning fields

3.2.7. Failure、Error、Warningフィールド

Failure、Error、Warningの各フィールドは、「failure」処理タイプ、「error」処理修飾子、「warning」処理修飾子が現れる場合に、テキストメッセージの形で追加の情報を提供するために使用します。構文は次のとおりです。

  failure-field = "Failure" ":" *text

  failure-field = "Failure" ":" *text

  error-field = "Error" ":" *text

  error-field = "Error" ":" *text

  warning-field = "Warning" ":" *text

  warning-field = "Warning" ":" *text

  1. 外部の処理報告からの追加情報を、インターネットのMDNを通じてトンネリングできるようにするため。そのようなMDNフィールドの名前は、外部の環境の名前を示すもので始めるべきです（たとえば、X400-Physical-Forwarding-Address）。

アプリケーションの開発者がそのような拡張フィールドの意味を登録することを望まない場合は、この目的のために「X-」フィールドを使用できます。名前の衝突を避けるために、「X-」の後にはアプリケーション実装の名前を続けるべきです（たとえば、「X-Foomail-Log-ID」や「X-EDI-info」）。

4. Timeline of events

4. イベントの時系列

The following timeline shows when various events in the processing of a message and generation of MDNs take place:

次の時系列は、メッセージの処理とMDNの生成におけるさまざまなイベントがいつ起こるかを示しています。

  • User composes message
  • User tells UA to send message
  • UA passes message to MTA (original recipient information passed along)
  • MTA sends message to next MTA
  • Final MTA receives message
  • Final MTA delivers message to UA (possibily generating DSN)
  • UA performs automatic processing and generates corresponding MDNs ("dispatched", "processed", "deleted", "denied" or "failed" disposition type with "automatic-action" and "MDN-sent-automatically" disposition modes)
  • UA displays list of messages to user
  • User selects a message and requests that some action be performed on it.
  • UA performs requested action and, with user's permission, sends appropriate MDN ("displayed", "dispatched", "processed", "deleted", "denied" or "failed" disposition type with "manual-action" and "MDN-sent-manually" or "MDN-sent-automatically" disposition mode).
  • User possibly performs other actions on message, but no further MDNs are generated.
  • ユーザーがメッセージを作成します
  • ユーザーがUAにメッセージの送信を指示します
  • UAがメッセージをMTAに渡します（元の受信者の情報も渡されます）
  • MTAがメッセージを次のMTAに送信します
  • 最終MTAがメッセージを受信します
  • 最終MTAがメッセージをUAに配送します（DSNを生成する場合もあります）
  • UAが自動処理を行い、対応するMDN（「automatic-action」と「MDN-sent-automatically」の処理モードを持つ、「dispatched」「processed」「deleted」「denied」または「failed」の処理タイプ）を生成します
  • UAがユーザーにメッセージの一覧を表示します
  • ユーザーがメッセージを選択し、それに対してなんらかの動作を行うよう要求します。
  • UAが要求された動作を行い、ユーザーの許可を得て、適切なMDN（「manual-action」と「MDN-sent-manually」または「MDN-sent-automatically」の処理モードを持つ、「displayed」「dispatched」「processed」「deleted」「denied」または「failed」の処理タイプ）を送信します。
  • ユーザーがメッセージに対して他の動作を行うこともありますが、それ以上MDNは生成されません。

5. Conformance and Usage Requirements

5. 適合性と使用上の要件

A UA or gateway conforms to this specification if it generates MDNs according to the protocol defined in this memo. It is not necessary to be able to generate all of the possible values of the Disposition field.

UAまたはゲートウェイは、このメモで定義するプロトコルに従ってMDNを生成する場合、この仕様に適合しています。Dispositionフィールドのすべての可能な値を生成できる必要はありません。

UAs and gateways MUST NOT generate the Original-Recipient field of an MDN unless the mail protocols provide the address originally specified by the sender at the time of submission. Ordinary SMTP does not make that guarantee, but the SMTP extension defined in RFC 1891 [8] permits such information to be carried in the envelope if it is available. The Original-Recipient header defined in this document provides a way for the MTA to pass the original recipient address to the UA.

UAとゲートウェイは、送信時に送信者が最初に指定したアドレスをメールプロトコルが提供するのでない限り、MDNのOriginal-Recipientフィールドを生成してはなりません（MUST NOT）。通常のSMTPはそれを保証しませんが、RFC 1891 [8]で定義されているSMTP拡張により、そのような情報が利用可能であればエンベロープで運ぶことができます。この文書で定義するOriginal-Recipientヘッダーは、MTAが元の受信者アドレスをUAに渡す方法を提供します。

Each sender-specified recipient address may result in more than one MDN. If an MDN is requested for a recipient that is forwarded to multiple recipients of an "alias" (as defined in RFC 1891 [8], section 6.2.7.3), each of the recipients may issue an MDN.

送信者が指定した各受信者アドレスから、複数のMDNが生じることがあります。（RFC 1891 [8]のセクション6.2.7.3で定義されている）「エイリアス」の複数の受信者に転送される受信者に対してMDNが要求された場合、それぞれの受信者がMDNを発行することがあります。

Successful distribution of a message to a mailing list exploder SHOULD be considered final disposition of the message. A mailing list exploder may issue an MDN with a disposition type of "processed" and disposition modes of "automatic-action" and "MDN- sent- automatically" indicating that the message has been forwarded to the list. In this case, the request for MDNs is not propogated to the members of the list.

メーリングリストの展開器（exploder）へのメッセージの配布が成功した場合、それをメッセージの最終的な処理とみなすべきです（SHOULD）。メーリングリストの展開器は、メッセージがリストに転送されたことを示す、処理タイプ「processed」と処理モード「automatic-action」および「MDN- sent-automatically」を持つMDNを発行することができます。この場合、MDNの要求はリストのメンバーには伝播されません。

Alternaively, the mailing list exploder may issue no MDN and propogate the request for MDNs to all members of the list. The latter behavior is not recommended for any but small, closely knit lists, as it might cause large numbers of MDNs to be generated and may cause confidential subscribers to the list to be revealed. It is also permissible for the mailing list exploder to direct MDNs to itself, correlate them, and produce a report to the original sender of the message.

あるいは、メーリングリストの展開器はMDNを発行せず、MDNの要求をリストのすべてのメンバーに伝播することもできます。後者の動作は、小規模で緊密なリスト以外では推奨されません。大量のMDNが生成される原因になる可能性があり、また、リストの秘密の購読者が明らかになってしまう可能性があるためです。また、メーリングリストの展開器が、MDNを自身に宛てて送らせ、それらを関連付けて、メッセージの元の送信者への報告を作成することも認められます。

This specification places no restrictions on the processing of MDNs received by user agents or mailing lists.

この仕様は、ユーザーエージェントやメーリングリストが受信したMDNの処理について、なんら制限を課しません。

6. Security Considerations

6. セキュリティーに関する考慮事項

The following security considerations apply when using MDNs:

MDNを使用する際には、次のセキュリティーに関する考慮事項が当てはまります。

6.1. Forgery

6.1. 偽造

MDNs may be forged as easily as ordinary Internet electronic mail. User agents and automatic mail handling facilities (such as mail distribution list exploders) that wish to make automatic use of MDNs should take appropriate precautions to minimize the potential damage from denial-of-service attacks.

MDNは、通常のインターネット電子メールと同じくらい簡単に偽造できます。MDNを自動的に利用しようとするユーザーエージェントや自動メール処理機構（メール配布リストの展開器など）は、サービス拒否攻撃による潜在的な被害を最小限に抑えるために、適切な予防措置を講じるべきです。

Security threats related to forged MDNs include the sending of:

偽造されたMDNに関連するセキュリティー上の脅威には、次のものの送信が含まれます。

  1. A falsified disposition notification when the indicated disposition of the message has not actually ocurred,
  2. Unsolicited MDNs
  1. 示されたメッセージの処理が実際には行われていないのに、偽った処理通知
  2. 求められていないMDN

6.2. Confidentiality

6.2. 機密性

Another dimension of security is confidentiality. There may be cases in which a message recipient does not wish the disposition of messages addressed to him to be known or is concerned that the sending of MDNs may reveal other confidential information (e.g., when the message was read). In this situation, it is acceptable for the UA to issue "denied" MDNs or to silently ignore requests for MDNs.

セキュリティーのもう1つの側面は機密性です。メッセージの受信者が、自分宛てのメッセージの処理を知られたくない場合や、MDNの送信によって他の機密情報（たとえば、メッセージがいつ読まれたか）が明らかになることを懸念する場合があります。このような状況では、UAが「denied」のMDNを発行したり、MDNの要求を黙って無視したりすることは許容されます。

If the Disposition-Notification-To header is passed on unmodified when a message is distributed to the subscribers of a mailing list, the subscribers to the list may be revealed to the sender of the original message by the generation of MDNs.

メッセージがメーリングリストの購読者に配布される際に、Disposition-Notification-Toヘッダーが変更されずに渡されると、MDNが生成されることにより、リストの購読者が元のメッセージの送信者に明らかになる可能性があります。

Headers of the original message returned in part 3 of the multipart/report could reveal confidential information about host names and/or network topology inside a firewall.

multipart/reportの第3パートで返される元のメッセージのヘッダーから、ファイアウォール内部のホスト名やネットワークトポロジーに関する機密情報が明らかになる可能性があります。

An unencrypted MDN could reveal confidential information about an encrypted message, especially if all or part of the original message is returned in part 3 of the multipart/report. Encrypted MDNs are not defined in this specification.

暗号化されていないMDNは、暗号化されたメッセージに関する機密情報を明らかにする可能性があります。元のメッセージの全部または一部がmultipart/reportの第3パートで返される場合は、特にそうです。暗号化されたMDNは、この仕様では定義していません。

In general, any optional MDN field may be omitted if the Reporting UA site or user determines that inclusion of the field would impose too great a compromise of site confidentiality. The need for such confidentiality must be balanced against the utility of the omitted information in MDNs.

一般に、報告を行うUAのサイトまたはユーザーが、あるフィールドを含めるとサイトの機密性があまりにも大きく損なわれると判断した場合は、省略可能なMDNフィールドはどれでも省略できます。そのような機密性の必要性と、MDNで省略される情報の有用性とのバランスを取らなければなりません。

6.3. Non-Repudiation

6.3. 否認防止

Within the framework of today's Internet Mail, the MDNs defined in this document provide valuable information to the mail user; however, MDNs can not be relied upon as a guarantee that a message was or was not not seen by the recipient. Even if MDNs are not actively forged, they may be lost in transit. The MDN issuing mechanism may be bypassed in some manner by the recipient.

現在のインターネットメールの枠組みの中では、この文書で定義するMDNはメールのユーザーに価値ある情報を提供しますが、メッセージが受信者に見られた、または見られなかったことの保証としてMDNを当てにすることはできません。MDNが積極的に偽造されないとしても、転送中に失われる可能性があります。また、受信者がなんらかの方法でMDNの発行の仕組みを回避する可能性もあります。

8. Guidelines for Gatewaying MDNs

8. MDNをゲートウェイで変換するためのガイドライン

NOTE: This section provides non-binding recommendations for the construction of mail gateways that wish to provide semi-transparent disposition notifications between the Internet and another electronic mail system. Specific MDN gateway requirements for a particular pair of mail systems may be defined by other documents.

注：このセクションは、インターネットと別の電子メールシステムとの間で半透過的な処理通知を提供したいメールゲートウェイを構築するための、拘束力のない推奨事項を示します。特定のメールシステムの組に対するMDNゲートウェイの具体的な要件は、他の文書で定義されることがあります。

8.1. Gatewaying from other mail systems to MDNs

8.1. 他のメールシステムからMDNへのゲートウェイ変換

A mail gateway may issue an MDN to convey the contents of a "foreign" disposition notification over Internet Mail. When there are appropriate mappings from the foreign notification elements to MDN fields, the information may be transmitted in those MDN fields. Additional information (such as might be needed to tunnel the foreign notification through the Internet) may be defined in extension MDN fields. (Such fields should be given names that identify the foreign mail protocol, e.g. X400-* for X.400 protocol elements)

メールゲートウェイは、「外部の」処理通知の内容をインターネットメールで伝えるために、MDNを発行することがあります。外部の通知の要素からMDNフィールドへの適切なマッピングがある場合は、それらのMDNフィールドで情報を送信できます。追加の情報（外部の通知をインターネットを通じてトンネリングするために必要になるようなもの）は、拡張MDNフィールドで定義できます。（そのようなフィールドには、外部のメールプロトコルを識別する名前を付けるべきです。たとえば、X.400のプロトコル要素にはX400-*を使います）

The gateway must attempt to supply reasonable values for the Reporting-UA, Final-Recipient, and Disposition fields. These will normally be obtained by translating the values from the foreign notification into their Internet-style equivalents. However, some loss of information is to be expected.

ゲートウェイは、Reporting-UA、Final-Recipient、Dispositionの各フィールドに妥当な値を提供するよう努めなければなりません。これらは通常、外部の通知の値をインターネット形式の同等のものに変換することで得られます。しかし、ある程度の情報の損失は避けられません。

The sender-specified recipient address, and the original message-id, if present in the foreign notification, should be preserved in the Original-Recipient and Original-Message-ID fields.

送信者が指定した受信者アドレスと元のmessage-idが外部の通知に存在する場合、それらはOriginal-RecipientフィールドとOriginal-Message-IDフィールドに保持すべきです。

The gateway should also attempt to preserve the "final" recipient address from the foreign system. Whenever possible, foreign protocol elements should be encoded as meaningful printable ASCII strings.

ゲートウェイは、外部のシステムからの「最終的な」受信者アドレスも保持するよう努めるべきです。可能な限り、外部のプロトコル要素は、意味のある印字可能なASCII文字列としてエンコードすべきです。

For MDNs produced from foreign disposition notifications, the name of the gateway MUST appear in the MDN-Gateway field of the MDN.

外部の処理通知から生成されたMDNでは、MDNのMDN-Gatewayフィールドにゲートウェイの名前が現れなければなりません（MUST）。

8.2. Gatewaying from MDNs to other mail systems

8.2. MDNから他のメールシステムへのゲートウェイ変換

It may be possible to gateway MDNs from the Internet into a foreign mail system. The primary purpose of such gatewaying is to convey disposition information in a form that is usable by the destination system. A secondary purpose is to allow "tunneling" of MDNs through foreign mail systems, in case the MDN may be gatewayed back into the Internet.

インターネットから外部のメールシステムへMDNをゲートウェイで変換することが可能な場合があります。このようなゲートウェイ変換の主な目的は、宛先のシステムで使用できる形式で処理の情報を伝えることです。副次的な目的は、MDNがインターネットにゲートウェイで戻される場合に備えて、外部のメールシステムを通じてMDNを「トンネリング」できるようにすることです。

In general, the recipient of the MDN (i.e., the sender of the original message) will want to know, for each recipient: the closest available approximation to the original recipient address, and the disposition (displayed, printed, etc.).

一般に、MDNの受信者（つまり、元のメッセージの送信者）は、各受信者について、元の受信者アドレスに最も近い利用可能な近似値と、処理（表示、印刷など）を知りたいと考えます。

If possible, the gateway should attempt to preserve the Original-Recipient address and Original-Message-ID (if present), in the resulting foreign disposition report.

可能であれば、ゲートウェイは、結果として生成される外部の処理報告において、Original-RecipientアドレスとOriginal-Message-ID（存在する場合）を保持するよう努めるべきです。

If it is possible to tunnel an MDN through the destination environment, the gateway specification may define a means of preserving the MDN information in the disposition reports used by that environment.

宛先の環境を通じてMDNをトンネリングできる場合、ゲートウェイの仕様は、その環境で使用される処理報告の中にMDNの情報を保持する手段を定義することができます。

disposition-modifier名の登録には、次の情報を含めなければなりません（MUST）。

  1. The proposed disposition-modifier name.
  2. A reference to a standards track RFC or experimental RFC approved by the IESG that describes the semantics of the disposition modifier.
  1. 提案するdisposition-modifier名。
  2. 処理修飾子のセマンティクスを記述した、標準化過程のRFC、またはIESGが承認した実験的RFCへの参照。

10.3. IANA registration form for MDN extension field names

10.3. MDN拡張フィールド名のIANA登録フォーム

A registration for an MDN extension field name MUST include the following information:

MDN拡張フィールド名の登録には、次の情報を含めなければなりません（MUST）。

  1. The proposed extension field name.
  2. The syntax for extension values, specified using BNF, ABNF, regular expressions, or other non-ambiguous language.
  3. If extension field values are not composed entirely of graphic characters from the US-ASCII repertoire, a specification for how they are to be encoded as graphic US-ASCII characters in a Disposition-Notification-Options header.
  4. A reference to a standards track RFC or experimental RFC approved by the IESG that describes the semantics of the extension field.
  1. 提案する拡張フィールド名。
  2. BNF、ABNF、正規表現、またはその他の曖昧さのない言語を用いて規定した、拡張の値の構文。
  3. 拡張フィールドの値がUS-ASCIIのレパートリーの図形文字だけで構成されていない場合は、Disposition-Notification-Optionsヘッダーの中でそれらをUS-ASCIIの図形文字としてエンコードする方法の仕様。
  4. 拡張フィールドのセマンティクスを記述した、標準化過程のRFC、またはIESGが承認した実験的RFCへの参照。
