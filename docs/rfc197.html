RFC 197

Initial Connection Protocol--Reviewed

RFC 197

初期接続プロトコルの再検討

INTRODUCTION

はじめに

At the Network meeting preceding the SJCC '71, an "ICP Committee" was established. It's purpose was to get "something" working fast with minimum modifications to the current ICP so as to minimize complaints. (This seems like a good definition for almost everything!) Consequently, those who had objections to the current ICP were interviewed and a compromise was reached in the form of RFC #165. The ICP committee didn't have a chance to think about an alternative because of the above mentioned constraints. In this note we attempted a simple version of an ICP assuming that we can add commands to Host-Host protocol. We hope that this will be useful in the design of the next version of the Host-Host protocol.

SJCC '71に先立って開かれたNetworkミーティングで、「ICP委員会」が設置されました。その目的は、不満を最小限に抑えるように現在のICPへの変更を最小限にとどめつつ、「何か」を素早く動かすことでした（これはほとんどすべてのことに当てはまる良い定義のようです！）。そのため、現在のICPに異議のある人々から聞き取りを行い、RFC #165という形で妥協が成立しました。前述の制約があったため、ICP委員会には代替案を検討する機会がありませんでした。このノートでは、Host-Hostプロトコルにコマンドを追加できると仮定して、ICPの簡単な版を試みました。これがHost-Hostプロトコルの次の版の設計に役立つことを願っています。

ICP COMMANDS

ICPのコマンド

To establish a regular connection one party can issue an INIT (NCP sends RTS or STR commands), then the other party can accept the request for connection by responding with an INIT or refusing it with a CLOSE. We think that a similar, simple mechanism is desirable for the ICP. Furthermore, the ICP should allow for simplex as well as duplex connections from user to server.

通常のコネクションを確立するには、一方の当事者がINIT（NCPはRTSまたはSTRコマンドを送信します）を発行し、もう一方の当事者がINITで応答することでコネクションの要求を受け入れるか、CLOSEでそれを拒否します。ICPにも同様の単純な仕組みが望ましいと考えます。さらに、ICPでは、ユーザーからサーバーへの全二重のコネクションだけでなく、単方向のコネクションも可能にすべきです。

The following commands are necessary for simplex connections:

単方向のコネクションには、次のコマンドが必要です。

ISC
Initiate Simplex Connection
ASC
Accept Simplex Connection
RSC
Refuse Simplex Connection
ISC
単方向コネクションの開始（Initiate Simplex Connection）
ASC
単方向コネクションの受け入れ（Accept Simplex Connection）
RSC
単方向コネクションの拒否（Refuse Simplex Connection）

The notation for parameters is similar to that of RFC #165:

パラメーターの表記はRFC #165のものと同様です。

L
Server socket name, in one special case the server is "logger".
U
User socket.
S
Socket assigned by server for the connection with user.
X
Is the byte size if U is odd and is the link number if U is even.
X̅
Is the complement of X (X is the link number if U is odd and byte size if U is even.
L
サーバーのソケット名。特別な場合として、サーバーが「logger」である場合があります。
U
ユーザーのソケット。
S
ユーザーとのコネクションのためにサーバーが割り当てたソケット。
X
Uが奇数ならバイトサイズ、Uが偶数ならリンク番号です。
X̅
Xの補完です（Uが奇数ならリンク番号、Uが偶数ならバイトサイズです。

To initiate a simplex connection the user's NCP issues:

単方向のコネクションを開始するには、ユーザーのNCPは次を発行します。

ISC, L, U, X

ISC, L, U, X

To refuse this connection the server's NCP issues:

このコネクションを拒否するには、サーバーのNCPは次を発行します。

RSC, L, U

RSC, L, U

To accept this connection the server's NCP issues:

このコネクションを受け入れるには、サーバーのNCPは次を発行します。

              -
ASC, L, U, S, X

              -
ASC, L, U, S, X

Similarly, for duplex connections, we have:

同様に、全二重のコネクションには次のコマンドがあります。

IDC, L, U1, X1, U2, X2

RDC, L, U1, U2
                -           -
ADC, L, U1, S1, X1, U2, S2, X2

IDC, L, U1, X1, U2, X2

RDC, L, U1, U2
                -           -
ADC, L, U1, S1, X1, U2, S2, X2

where (U1,U2), (S1,S2), (U1,S1) and (U2,S2) are pairs of opposite gender.

ここで、(U1,U2)、(S1,S2)、(U1,S1)、(U2,S2)は、それぞれ逆の性別（gender）の組です。

After the server accepts the connection(s), it (they) goes immediately to a "connected state", and the appropriate ALL command(s) must be sent.

サーバーがコネクションを受け入れると、そのコネクションはただちに「接続状態」になり、適切なALLコマンドを送信しなければなりません。

ADVANTAGES

利点

The main advantage to this approach is that it minimizes the dialog between user and server. The server socket L is used only as an address, not a socket to connect to, therefore eliminating the need to establish a connection to L, choose a byte size, send an ALL command, send and receive data on it and CLOSE it. Race conditions as mentioned in RFC #143 do not arise. Socket L is the server and should be in a "Listening for ICP" state when an ISC or IDC is received. If socket L is not in that state, the serving NCP should refuse to ICP request. The serving NCP should not queue ICP requests.

このアプローチの主な利点は、ユーザーとサーバーの間のやり取りを最小限にできることです。サーバーのソケットLは、接続先のソケットとしてではなくアドレスとしてだけ使われます。そのため、Lへのコネクションを確立し、バイトサイズを選び、ALLコマンドを送り、そのコネクションでデータを送受信し、それをCLOSEする必要がなくなります。RFC #143で述べられているような競合状態も起こりません。ソケットLはサーバーであり、ISCまたはIDCを受信したときには「ICP待ち受け」の状態にあるべきです。ソケットLがその状態になければ、サービスを提供するNCPはICPの要求を拒否すべきです。サービスを提供するNCPは、ICPの要求をキューに入れるべきではありません。

In the current ICP, when the user choses socket U, he has to reserve sockets U+2 and U+3. In the above described approach no restrictions exist for U1 and U2 (except that they are of opposite gender); the same is true for S1 and S2.

現在のICPでは、ユーザーがソケットUを選ぶと、ソケットU+2とU+3を予約しなければなりません。上で説明したアプローチでは、U1とU2に（逆の性別であること以外の）制約はありません。S1とS2についても同様です。

We think that duplex commands are necessary since both connections are to be connected to the same server process. Their separation by using two ISCs, will add complications of correlating the two ISCs with the same process. Also, if two ISCs are used, the first might be accepted and the second refused. This leads to uncertainty on the user's part. This condition cannot occur with the duplex commands.

両方のコネクションが同じサーバープロセスに接続されることになるので、全二重のコマンドが必要であると考えます。2つのISCを使ってこれらを分けると、2つのISCを同じプロセスに対応付けるという複雑さが加わります。また、2つのISCを使うと、1つ目は受け入れられ、2つ目は拒否される可能性があります。これはユーザー側に不確実さをもたらします。全二重のコマンドではこのような状態は起こりません。

MINIMUM MODIFICATION TO CURRENT ICP

現在のICPへの最小限の変更

An alternative way to the ACC command is a CLS command with an additional parameter (32 bits long). If parameter is zero the request for connection by the user is refused; if the parameter is non-zero, the request is accepted and socket S is the value of the parameter.

ACCコマンドの代わりに、追加のパラメーター（32ビット長）を持つCLSコマンドを使う方法もあります。パラメーターが0であれば、ユーザーによるコネクションの要求は拒否されます。パラメーターが0以外であれば、要求は受け入れられ、そのパラメーターの値がソケットSとなります。

All suggested changes improve the ICP dialog both from the aesthetic and efficiency points of view. We lean strongly, however, to the first, more major ICP modification.

提案したどの変更も、美しさと効率の両方の観点からICPのやり取りを改善します。しかし私たちは、1つ目の、より大きなICPの変更を強く支持します。

A COMMENT ABOUT CLS COMMAND

CLSコマンドについての意見

It seems appropriate to mention here for the purpose of the next version of the Host-Host protocol that the CLS command has more than one function. We think that the CLS command should be reserved to close connections in the "connected state" only (i.e., "open" connections). Two additional commands can be used for "refusing" and "rejecting" requests for connections:

Host-Hostプロトコルの次の版のために、CLSコマンドが複数の機能を持っていることをここで述べておくのが適切だと思われます。CLSコマンドは、「接続状態」にあるコネクション（つまり「開いている」コネクション）を閉じるためだけに使うべきだと考えます。コネクションの要求を「拒否（refuse）」したり「拒絶（reject）」したりするために、2つの追加のコマンドを使えます。

REJ<mysocket><yoursocket>
when a request for connection is rejected unconditionally.
REF<mysocket><yoursocket><reason>
when a request for connection is refused temporarily because the NCP could not handle it. For example: no process LISTENed to it and it was timed-out, or NCP tables are full in which case the user process may try again. The reason for refusing is indicated in the parameter "reason".
REJ<mysocket><yoursocket>
コネクションの要求を無条件に拒絶する場合。
REF<mysocket><yoursocket><reason>
NCPがコネクションの要求を処理できなかったために一時的に拒否する場合。たとえば、どのプロセスもそれをLISTENしておらずタイムアウトした場合や、NCPのテーブルが満杯の場合で、この場合はユーザープロセスが再試行できます。拒否の理由はパラメーター「reason」で示します。
