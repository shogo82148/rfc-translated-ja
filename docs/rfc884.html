RFC 884

Telnet terminal type option

RFC 884

TELNETのTERMINAL TYPEオプション

Abstract

概要

This RFC specifies a standard for the ARPA Internet community. Hosts on the ARPA Internet that exchange terminal type information within the Telnet protocol are expected to adopt and implement this standard.

このRFCは、ARPAインターネットコミュニティーのための標準を規定します。ARPAインターネット上のホストのうち、Telnetプロトコルの中で端末タイプの情報をやり取りするホストは、この標準を採用して実装することが求められます。

1. Command Name and Code

1. コマンド名とコード

TERMINAL-TYPE 24

TERMINAL-TYPE 24

2. Command Meanings

2. コマンドの意味

IAC DO TERMINAL-TYPE

IAC WON'T TERMINAL-TYPE

IAC SB TERMINAL-TYPE SEND IAC SE
Sender requests receiver to transmit his (the receiver's) terminal type. The code for SEND is 1. (See below.)

Sender is stating the name of his terminal type. The code for IS is 0. (See below.)

3. デフォルト

DON'T TERMINAL-TYPE

WON'T TERMINAL-TYPE

Terminal type information will not be exchanged.

4. Motivation for the Option

4. このオプションの動機

This option allows a telnet server to determine the type of terminal connected to a user telnet program. The transmission of such information does not immediately imply any change of processing. However, the information may be passed to a process, which may alter the data it sends to suit the particular characteristics of the terminal. For example, some operating systems have a terminal driver that accepts a code indicating the type of terminal being driven. Using the TERMINAL TYPE and BINARY options, a telnet server program on such a system could arrange to have terminals driven as if they were directly connected, including such special functions as cursor addressing, multiple colors, etc., not included in the Network Virtual Terminal specification. This option fits into the normal structure of TELNET options by deferring the actual transfer of status information to the SB command.

このオプションにより、telnetサーバーは、ユーザーのtelnetプログラムに接続されている端末のタイプを判断できます。このような情報を送信しても、ただちに処理の変更が生じるわけではありません。しかし、この情報はプロセスに渡される場合があり、そのプロセスは送信するデータを端末の特定の特性に合わせて変更する場合があります。たとえば、一部のオペレーティングシステムには、駆動している端末のタイプを示すコードを受け付ける端末ドライバーがあります。そのようなシステム上のtelnetサーバープログラムは、TERMINAL TYPEオプションとBINARYオプションを使用して、カーソルアドレッシングや多色表示など、ネットワーク仮想端末（Network Virtual Terminal）の仕様に含まれていない特殊な機能を含め、端末が直接接続されているかのように駆動されるよう手配できます。このオプションは、状態の情報の実際の転送をSBコマンドに委ねることで、TELNETオプションの通常の構造に適合します。

5. Description of the Option

5. オプションの説明

WILL and DO are used only to obtain and grant permission for future discussion. The actual exchange of status information occurs within option subcommands (IAC SB TERMINAL-TYPE...).

WILLとDOは、今後の議論の許可を得たり与えたりするためだけに使います。状態の情報の実際のやり取りは、オプションのサブコマンド（IAC SB TERMINAL-TYPE...）の中で行います。

Once the two hosts have exchanged a WILL and a DO, the sender of the WILL TERMINAL-TYPE is free to transmit type information, spontaneously or in response to a request from the sender of the DO. At worst, this may lead to transmitting the information twice. Only the sender of the DO may send requests (IAC SB TERMINAL-TYPE SEND IAC SE) and only the sender of the WILL may transmit actual type information (within an IAC SB TERMINAL-TYPE IS ... IAC SE command).

2つのホストがWILLとDOを交換したら、WILL TERMINAL-TYPEの送信者は、自発的に、またはDOの送信者からの要求に応じて、タイプの情報を自由に送信できます。最悪の場合、情報が2回送信されることになるかもしれません。要求（IAC SB TERMINAL-TYPE SEND IAC SE）を送れるのはDOの送信者だけであり、実際のタイプの情報を（IAC SB TERMINAL-TYPE IS ... IAC SEコマンドの中で）送信できるのはWILLの送信者だけです。

The terminal type information is an NVT ASCII string. Within this string, upper and lower case are considered equivalent. A few terminal type names useful in the context of IBM systems are listed below. It is anticipated that additional names will be added in the future. The complete list of valid terminal types will be found in the latest "Assigned Numbers" RFC.

端末タイプの情報はNVT ASCIIの文字列です。この文字列の中では、大文字と小文字は同じものとみなされます。IBMシステムの文脈で役立つ端末タイプ名をいくつか以下に示します。今後、名前が追加されることが見込まれます。有効な端末タイプの完全なリストは、最新の「Assigned Numbers」RFCに記載されます。

6. Implementation Suggestions

6. 実装の提案

The "terminal type" information may be any NVT ASCII string meaningful to both ends of the negotiation. The list of suggestions below is intended to minimize confusion caused by alternative "spellings" of the terminal type. For example, confusion would arise if one party were to call a terminal "IBM3278-2" while the other called it "IBM-3278/2". There is no negative acknowledgement for a terminal type that is not understood, but certain other options (such as switching to BINARY mode) may be refused if a valid terminal type name has not been specified. In some cases, a particular terminal may be known by more than one name, for example a specific type and a more generic type. In such cases, the sender of the TERMINAL-TYPE IS command should reply to successive TERMINAL-TYPE SEND commands with the various names, from most to least specific. In this way, a telnet server that does not understand the first response can prompt for alternatives. However, it should cease sending TERMINAL-TYPE SEND commands after receiving the same response two consecutive times. Similarly, a sender should indicate it has sent all available names by repeating the last one sent.

「端末タイプ」の情報は、ネゴシエーションの両端にとって意味のある任意のNVT ASCII文字列にできます。以下の提案のリストは、端末タイプの「つづり」の違いによって生じる混乱を最小限に抑えることを目的としています。たとえば、一方の当事者がある端末を「IBM3278-2」と呼び、もう一方が「IBM-3278/2」と呼んだ場合、混乱が生じるでしょう。理解できない端末タイプに対する否定確認応答はありませんが、有効な端末タイプ名が指定されていない場合、他の特定のオプション（BINARYモードへの切り替えなど）が拒否される場合があります。場合によっては、特定の端末が、たとえば具体的なタイプとより汎用的なタイプのように、複数の名前で知られていることがあります。そのような場合、TERMINAL-TYPE ISコマンドの送信者は、連続するTERMINAL-TYPE SENDコマンドに対して、最も具体的なものから最も汎用的なものの順にさまざまな名前で応答すべきです。こうすることで、最初の応答を理解できないtelnetサーバーは、別の名前を促すことができます。ただし、telnetサーバーは、同じ応答を2回連続して受信したら、TERMINAL-TYPE SENDコマンドの送信をやめるべきです。同様に、送信者は、最後に送信した名前を繰り返すことで、利用可能なすべての名前を送信したことを示すべきです。
