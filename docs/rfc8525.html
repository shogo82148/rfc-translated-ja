RFC 8525

YANG Library

RFC 8525

YANGライブラリー

Abstract

概要

This document describes a YANG library that provides information about the YANG modules, datastores, and datastore schemas used by a network management server. Simple caching mechanisms are provided to allow clients to minimize retrieval of this information. This version of the YANG library supports the Network Management Datastore Architecture (NMDA) by listing all datastores supported by a network management server and the schema that is used by each of these datastores.

この文書では、ネットワーク管理サーバーが使用するYANGモジュール、データストア、データストアスキーマに関する情報を提供するYANGライブラリーについて説明します。クライアントがこの情報の取得を最小限に抑えられるように、簡単なキャッシュメカニズムを提供します。このバージョンのYANGライブラリーは、ネットワーク管理サーバーがサポートするすべてのデータストアと、それぞれのデータストアが使用するスキーマを列挙することで、ネットワーク管理データストアアーキテクチャー（Network Management Datastore Architecture: NMDA）をサポートします。

1. Introduction

1. はじめに

There is a need for a standard mechanism to expose which YANG modules [RFC7950], datastores [RFC8342], and datastore schemas [RFC8342] are in use by a network management server.

ネットワーク管理サーバーがどのYANGモジュール[RFC7950]、データストア[RFC8342]、データストアスキーマ[RFC8342]を使用しているかを公開するための標準的なメカニズムが必要とされています。

This document defines the YANG module "ietf-yang-library" that provides this information. This version of the YANG library is compatible with the Network Management Datastore Architecture (NMDA) [RFC8342]. The previous version of the YANG library, defined in [RFC7895], is not compatible with the NMDA since it assumes that all datastores have exactly the same schema. This is not necessarily true in the NMDA since dynamic configuration datastores may have their own datastore schema. Furthermore, the operational state datastore may support non-configurable YANG modules in addition to the YANG modules supported by conventional configuration datastores.

この文書では、この情報を提供するYANGモジュール"ietf-yang-library"を定義します。このバージョンのYANGライブラリーは、ネットワーク管理データストアアーキテクチャー（NMDA）[RFC8342]と互換性があります。[RFC7895]で定義された以前のバージョンのYANGライブラリーは、すべてのデータストアがまったく同じスキーマを持つことを前提としているため、NMDAと互換性がありません。NMDAでは、動的設定データストアが独自のデータストアスキーマを持つ場合があるため、この前提は必ずしも成り立ちません。さらに、運用状態データストアは、従来型設定データストアがサポートするYANGモジュールに加えて、設定不可能なYANGモジュールをサポートする場合があります。

The old YANG library definitions have been retained (for backwards-compatibility reasons), but the definitions have been marked as deprecated. For backwards compatibility, an NMDA-supporting server SHOULD populate the deprecated "/modules-state" tree in a backwards-compatible manner. The new "/yang-library" tree will be ignored by legacy clients but will provide all the data needed for NMDA-aware clients (which will ignore the "/modules-state" tree). The recommended approach to populate "/modules-state" is to report the YANG modules with "config true" data nodes that are configurable via conventional configuration datastores and the YANG modules with "config false" data nodes that are returned via a Network Configuration Protocol (NETCONF) <get> operation or equivalent.

古いYANGライブラリーの定義は（後方互換性のために）残されていますが、それらの定義は非推奨とされています。後方互換性のため、NMDAをサポートするサーバーは、非推奨の"/modules-state"ツリーに後方互換な方法で値を設定すべきです（SHOULD）。新しい"/yang-library"ツリーはレガシーなクライアントには無視されますが、NMDAに対応したクライアント（こちらは"/modules-state"ツリーを無視します）が必要とするすべてのデータを提供します。"/modules-state"に値を設定する方法として推奨されるのは、従来型設定データストアを介して設定可能な"config true"のデータノードを持つYANGモジュールと、ネットワーク設定プロトコル（Network Configuration Protocol: NETCONF）の<get>操作またはそれと同等の操作によって返される"config false"のデータノードを持つYANGモジュールを報告することです。

The YANG library information can be different on every server, and it can change at runtime or across a server reboot. If a server implements multiple network management protocols to access the server's datastores, then each such protocol may have its own conceptual instantiation of the YANG library.

YANGライブラリーの情報はサーバーごとに異なる可能性があり、実行時やサーバーの再起動をまたいで変化する可能性もあります。サーバーのデータストアにアクセスするための複数のネットワーク管理プロトコルをサーバーが実装している場合、そのようなプロトコルはそれぞれ、YANGライブラリーの独自の概念的なインスタンスを持つ場合があります。

If a large number of YANG modules are utilized by a server, then the YANG library contents can be relatively large. Since the YANG library contents change very infrequently, it is important that clients be able to cache the YANG library contents and easily identify whether their cache is out of date.

サーバーが多数のYANGモジュールを利用している場合、YANGライブラリーの内容は比較的大きくなる可能性があります。YANGライブラリーの内容が変化することはごくまれなので、クライアントがYANGライブラリーの内容をキャッシュし、そのキャッシュが古くなっているかどうかを容易に識別できることが重要です。

2. Objectives

2. 目的

The following information is needed by a client application (for each YANG module in the library) to fully utilize the YANG data modeling language:

YANGデータモデリング言語を十分に活用するために、クライアントアプリケーションは（ライブラリー内の各YANGモジュールについて）次の情報を必要とします：

  • name: The name of the YANG module.
  • revision: If defined in the YANG module or submodule, the revision is derived from the most recent revision statement within the module or submodule.
  • submodule list: The name and (if defined) revision of each submodule used by the module must be identified.
  • feature list: The name of each YANG feature supported by the server must be identified.
  • deviation list: The name of each YANG module with deviation statements affecting a given YANG module must be identified.
  • 名前（name）：YANGモジュールの名前。
  • リビジョン（revision）：YANGモジュールまたはサブモジュールで定義されている場合、リビジョンはそのモジュールまたはサブモジュール内の最新のrevisionステートメントから導き出されます。
  • サブモジュールのリスト（submodule list）：モジュールが使用する各サブモジュールの名前と（定義されている場合は）リビジョンを識別する必要があります。
  • 機能のリスト（feature list）：サーバーがサポートする各YANG機能（feature）の名前を識別する必要があります。
  • 逸脱のリスト（deviation list）：あるYANGモジュールに影響を与えるdeviationステートメントを持つ各YANGモジュールの名前を識別する必要があります。

In addition, the following information is needed by a client application for each datastore supported by a server:

さらに、クライアントアプリケーションは、サーバーがサポートする各データストアについて次の情報を必要とします：

  • identity: The YANG identity for the datastore.
  • schema: The schema (i.e., the set of modules) implemented by the datastore.
  • アイデンティティー（identity）：そのデータストアのYANGアイデンティティー。
  • スキーマ（schema）：そのデータストアが実装するスキーマ（つまり、モジュールの集合）。

In order to select one out of several possible designs for the YANG library data model, the following criteria were used:

YANGライブラリーのデータモデルについて考えられるいくつかの設計の中から1つを選ぶために、次の基準を用いました：

  1. The information must be efficient for a client to consume. Since the size of the YANG library can be quite large, it should be possible for clients to cache the YANG library information.
  2. A dynamic configuration datastore must be able to implement a module or feature that is not implemented in the conventional configuration datastores.
  3. It must be possible to not implement a module or feature in <operational>, even if it is implemented in some other datastore. This is required for transition purposes; a server that wants to implement <operational> should not have to implement all modules at once.
  4. A given module can only be implemented in one revision in all datastores. If a module is implemented in more than one datastore, the same revision is implemented in all these datastores.
  5. Multiple revisions can be used for import, if import-by revision is used.
  6. It must be possible to use the YANG library by schema mount [RFC8528].
  1. クライアントがこの情報を効率よく利用できる必要があります。YANGライブラリーのサイズはかなり大きくなる可能性があるため、クライアントがYANGライブラリーの情報をキャッシュできるようにすべきです。
  2. 動的設定データストアは、従来型設定データストアでは実装されていないモジュールや機能を実装できる必要があります。
  3. あるモジュールや機能が他のデータストアで実装されている場合でも、それを<operational>では実装しないことが可能でなければなりません。これは移行のために必要です。<operational>を実装しようとするサーバーが、すべてのモジュールを一度に実装しなければならないということがあるべきではありません。
  4. あるモジュールは、すべてのデータストアを通じて1つのリビジョンでしか実装できません。あるモジュールが複数のデータストアで実装されている場合、それらすべてのデータストアで同じリビジョンが実装されます。
  5. リビジョンを指定したインポート（import-by revision）を使用する場合、インポートには複数のリビジョンを使用できます。
  6. スキーママウント[RFC8528]でYANGライブラリーを使用できる必要があります。

3. YANG Library Data Model

3. YANGライブラリーのデータモデル

The "ietf-yang-library" YANG module provides information about the modules, submodules, datastores, and datastore schemas supported by a server. All data nodes in the "ietf-yang-library" module are "config false" and thus only accessible in the operational state datastore.

YANGモジュール"ietf-yang-library"は、サーバーがサポートするモジュール、サブモジュール、データストア、データストアスキーマに関する情報を提供します。"ietf-yang-library"モジュール内のすべてのデータノードは"config false"であるため、運用状態データストアでのみアクセスできます。

The conceptual model of the YANG library is depicted in Figure 1. Following the NMDA, every datastore has an associated datastore schema. A datastore schema is a union of module sets, and every module set is a collection of modules and submodules, including the modules and submodules used for imports. Note that multiple datastores may refer to the same datastore schema. Furthermore, it is possible for individual datastore schemas to share module sets. A common use case is the operational state datastore schema, which is a superset of the schema used by conventional configuration datastores.

YANGライブラリーの概念モデルをFigure 1に示します。NMDAに従い、すべてのデータストアには関連付けられたデータストアスキーマがあります。データストアスキーマはモジュールセットの和集合であり、各モジュールセットは、インポートに使用されるモジュールとサブモジュールを含む、モジュールとサブモジュールの集まりです。複数のデータストアが同じデータストアスキーマを参照する場合があることに注意してください。さらに、個々のデータストアスキーマがモジュールセットを共有することも可能です。よくあるユースケースは運用状態データストアのスキーマで、これは従来型設定データストアが使用するスキーマの上位集合になります。

The "/yang-library" container holds the entire YANG library. The container has the following child nodes:

"/yang-library"コンテナーは、YANGライブラリー全体を保持します。このコンテナーには、次の子ノードがあります：

  • The "/yang-library/module-set" contains entries representing module sets. The list "/yang-library/module-set/module" enumerates the modules that belong to the module set. A module is listed together with its submodules (if any), a set of features, and any deviation modules. The list "/yang-library/module-set/import-only-module" lists all modules (and their submodules) used only for imports. The assignment of a module to a module set is at the server's discretion. This revision of the YANG library attaches no semantics as to which module set a module is listed in.
  • The "/yang-library/schema" list contains an entry for each datastore schema supported by the server. All conventional configuration datastores use the same "schema" list entry. A dynamic configuration datastore may use a different datastore schema from the conventional configuration datastores and hence may require a separate "schema" entry. A "schema" entry has a leaf-list of references to entries in the "module-set" list. The schema consists of the union of all modules in all referenced module sets.
  • The "/yang-library/datastore" list contains one entry for each datastore supported by the server, and it identifies the datastore schema associated with a datastore via a reference to an entry in the "schema" list. Each supported conventional configuration datastore has a separate entry, pointing to the same "schema" list element.
  • The "/yang-library/content-id" leaf contains the YANG library content identifier, which is an implementation-specific identifier representing the current information in the YANG library on a specific server. The value of this leaf MUST change whenever the information in the YANG library changes. There is no requirement that the same information always result in the same "content-id" value. This leaf allows a client to fetch all schema information once, cache it, and only refetch it if the value of this leaf has been changed. If the value of this leaf changes, the server also generates a "yang-library-update" notification.
  • "/yang-library/module-set"には、モジュールセットを表すエントリーが含まれます。リスト"/yang-library/module-set/module"は、そのモジュールセットに属するモジュールを列挙します。モジュールは、そのサブモジュール（存在する場合）、機能の集合、および逸脱モジュールとともに列挙されます。リスト"/yang-library/module-set/import-only-module"は、インポートにのみ使用されるすべてのモジュール（とそのサブモジュール）を列挙します。モジュールをどのモジュールセットに割り当てるかは、サーバーの裁量に委ねられます。このリビジョンのYANGライブラリーは、モジュールがどのモジュールセットに列挙されるかに意味を持たせません。
  • "/yang-library/schema"リストには、サーバーがサポートするデータストアスキーマごとにエントリーが含まれます。すべての従来型設定データストアは、同じ"schema"リストのエントリーを使用します。動的設定データストアは、従来型設定データストアとは異なるデータストアスキーマを使用する場合があり、そのため別の"schema"エントリーを必要とする場合があります。"schema"エントリーは、"module-set"リストのエントリーへの参照からなるリーフリストを持ちます。スキーマは、参照されるすべてのモジュールセットに含まれるすべてのモジュールの和集合で構成されます。
  • "/yang-library/datastore"リストには、サーバーがサポートするデータストアごとに1つのエントリーが含まれ、"schema"リストのエントリーへの参照によって、データストアに関連付けられたデータストアスキーマを識別します。サポートされる従来型設定データストアはそれぞれ別のエントリーを持ち、それらは同じ"schema"リストの要素を指します。
  • "/yang-library/content-id"リーフには、YANGライブラリーコンテンツ識別子が含まれます。これは、特定のサーバー上のYANGライブラリーの現在の情報を表す、実装固有の識別子です。このリーフの値は、YANGライブラリーの情報が変化するたびに変化しなければなりません（MUST）。同じ情報が常に同じ"content-id"の値になるという要件はありません。このリーフにより、クライアントはすべてのスキーマ情報を一度取得してキャッシュし、このリーフの値が変化した場合にのみ再取得できます。このリーフの値が変化した場合、サーバーは"yang-library-update"通知も生成します。

Note that for a NETCONF server implementing the NETCONF extensions to support the NMDA [RFC8526], a change of the YANG library content identifier results in a new value for the :yang-library:1.1 capability defined in [RFC8526]. Thus, if such a server implements NETCONF notifications [RFC5277] and the "netconf-capability-change" notification [RFC6470], a "netconf-capability-change" notification is generated whenever the YANG library content identifier changes.

NMDAをサポートするためのNETCONF拡張[RFC8526]を実装するNETCONFサーバーでは、YANGライブラリーコンテンツ識別子が変化すると、[RFC8526]で定義された:yang-library:1.1能力の値が新しくなることに注意してください。したがって、そのようなサーバーがNETCONF通知[RFC5277]と"netconf-capability-change"通知[RFC6470]を実装している場合、YANGライブラリーコンテンツ識別子が変化するたびに"netconf-capability-change"通知が生成されます。

6. Security Considerations

6. セキュリティーに関する考慮事項

The YANG module specified in this document defines a schema for data that is designed to be accessed via network management protocols such as NETCONF [RFC6241] or RESTCONF [RFC8040]. The lowest NETCONF layer is the secure transport layer, and the mandatory-to-implement secure transport is Secure Shell (SSH) [RFC6242]. The lowest RESTCONF layer is HTTPS, and the mandatory-to-implement secure transport is TLS [RFC8446].

この文書で規定するYANGモジュールは、NETCONF [RFC6241]やRESTCONF [RFC8040]などのネットワーク管理プロトコルを介してアクセスされるように設計されたデータのスキーマを定義します。NETCONFの最下位層は安全なトランスポート層であり、実装必須の安全なトランスポートはSecure Shell（SSH）[RFC6242]です。RESTCONFの最下位層はHTTPSであり、実装必須の安全なトランスポートはTLS [RFC8446]です。

The Network Configuration Access Control Model (NACM) [RFC8341] provides the means to restrict access for particular NETCONF or RESTCONF users to a preconfigured subset of all available NETCONF or RESTCONF protocol operations and content.

ネットワーク設定アクセス制御モデル（NACM）[RFC8341]は、特定のNETCONFユーザーまたはRESTCONFユーザーのアクセスを、利用可能なすべてのNETCONFまたはRESTCONFのプロトコル操作とコンテンツのうち、あらかじめ設定されたサブセットに制限する手段を提供します。

Some of the readable data nodes in this YANG module may be considered sensitive or vulnerable in some network environments. It is thus important to control read access (e.g., via get, get-config, or notification) to these data nodes. These are the subtrees and data nodes and their sensitivity/vulnerability:

このYANGモジュールの読み取り可能なデータノードの中には、ネットワーク環境によっては機密性が高い、または脆弱であるとみなされるものがあります。そのため、これらのデータノードへの読み取りアクセス（たとえば、get、get-config、notificationによるもの）を制御することが重要です。以下に、該当するサブツリーとデータノード、およびその機密性・脆弱性を示します：

The "/yang-library" subtree of the YANG library may help an attacker identify the server capabilities and server implementations with known bugs since the set of YANG modules supported by a server may reveal the kind of device and the manufacturer of the device. Although some of this information may be available to all NETCONF users via the NETCONF <hello> message (or similar messages in other management protocols), this YANG module potentially exposes additional details that could be of some assistance to an attacker. Server vulnerabilities may be specific to particular modules, module revisions, module features, or even module deviations. For example, if a particular operation on a particular data node is known to cause a server to crash or significantly degrade device performance, then the "module" list information will help an attacker identify server implementations with such a defect, in order to launch a denial-of-service attack on the device.

YANGライブラリーの"/yang-library"サブツリーは、攻撃者がサーバーの能力や既知のバグを持つサーバーの実装を特定するのに役立つ可能性があります。サーバーがサポートするYANGモジュールの集合から、デバイスの種類やデバイスの製造元が明らかになる場合があるためです。この情報の一部は、NETCONFの<hello>メッセージ（または他の管理プロトコルにおける同様のメッセージ）を介してすべてのNETCONFユーザーが入手できる場合もありますが、このYANGモジュールは、攻撃者にとってある程度役立つ可能性のある追加の詳細を公開する可能性があります。サーバーの脆弱性は、特定のモジュール、モジュールのリビジョン、モジュールの機能（feature）、さらにはモジュールの逸脱（deviation）に固有のものである場合があります。たとえば、特定のデータノードに対する特定の操作によって、サーバーがクラッシュしたりデバイスの性能が著しく低下したりすることが知られている場合、"module"リストの情報は、攻撃者がそのような欠陥を持つサーバーの実装を特定してデバイスにサービス拒否攻撃を仕掛けるのに役立ちます。

Appendix C. Example YANG Library Instance for an Advanced Server

Appendix C. 高度なサーバーのYANGライブラリーインスタンスの例

The following example extends the example in Appendix B by using modules from [RFC8345] and [RFC8349] to illustrate a slightly more advanced server that:

次の例は、[RFC8345]と[RFC8349]のモジュールを使用してAppendix Bの例を拡張し、次のような、もう少し高度なサーバーを示します：

  • Has a module with features only enabled in <operational>; the "ietf-routing" module is supported in <running>, <startup>, and <operational>, but the "multiple-ribs" and "router-id" features are only enabled in <operational>. Hence, the "router-id" leaf may be read but not configured.
  • Supports a dynamic configuration datastore "example-ds-ephemeral", with only the "ietf-network" and "ietf-network-topology" modules configurable via a notional dynamic configuration protocol.
  • Shows an example of datastore-specific deviations. The "example-vendor-hardware-deviations" module is included in the schema for <operational> to remove data nodes that cannot be supported by the server.
  • Shows how module-sets can be used to organize related modules together.
  • <operational>でのみ有効になる機能を持つモジュールがあります。"ietf-routing"モジュールは<running>、<startup>、<operational>でサポートされていますが、"multiple-ribs"機能と"router-id"機能は<operational>でのみ有効になっています。したがって、"router-id"リーフは読み取ることはできますが、設定することはできません。
  • 動的設定データストア"example-ds-ephemeral"をサポートします。このデータストアでは、"ietf-network"モジュールと"ietf-network-topology"モジュールだけが、架空の動的設定プロトコルを介して設定可能です。
  • データストア固有の逸脱の例を示します。"example-vendor-hardware-deviations"モジュールは、サーバーがサポートできないデータノードを取り除くために、<operational>のスキーマに含まれています。
