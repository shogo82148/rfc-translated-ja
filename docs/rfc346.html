RFC 346

Satellite Considerations

RFC 346

衛星に関する考慮事項

Abstract

概要

The consideration of using space satellite transmission links in the ARPANET should be cause for some thought by the parties making use of the network. The satellite transmission path will not necessarily affect the transmission rate but it will affect the delay. The change in the delay characteristics can be approximated by the change in path length. Thus if the satellite is in synchronous orbit about 22,000 miles above the earth, the path length is about 44,000 miles compared to (worst case) 3,000 miles or about a 15 to 1 increase in path length and delay. (The time for light to travel 3,000 miles is .016 seconds, to travel 44,000 miles is .236 seconds.)

ARPANETで宇宙衛星の伝送リンクを使うことが検討されていることについて、ネットワークを利用する当事者は少し考えてみるべきです。衛星の伝送経路は、伝送速度には必ずしも影響しませんが、遅延には影響します。遅延特性の変化は、経路長の変化で近似できます。したがって、衛星が地上約22,000マイルの同期軌道上にある場合、経路長は約44,000マイルとなり、（最悪の場合で）3,000マイルと比べて、経路長と遅延がおよそ15対1に増えることになります。（光が3,000マイルを進む時間は.016秒、44,000マイルを進む時間は.236秒です。）

In the current (surface) ARPANET delays are such that interactive servers with character-at-a-time remote echo are only marginally useful. While I believe that this delay (unmeasured) is largely due to the host systems, adding a half second transmission delay will cause these marginal systems to become unusable.

現在の（地上の）ARPANETでも遅延が大きく、文字単位でリモートエコーを行う対話型のサーバーは、かろうじて役に立つ程度です。この遅延（未測定）の大部分はホストシステムに起因すると私は考えていますが、そこに0.5秒の伝送遅延が加われば、こうしたかろうじて使えるシステムは使い物にならなくなるでしょう。

Thought should also be given to buffer allocations. If a receiving system allows only one line of text to be buffered at a time and refreshes the allocation as each line is output to a human user there will be at least a half second delay between the arrival of each line at the receiving system. This need not be a problem until the speed of the output device is above about 150 characters/second. This "small buffer" problem can be expected to occur even with lower speed devices since host delays are estimated to be in the range 0.1 second to 1.0 second.

バッファーの割り当てについても考えておくべきです。受信側のシステムが一度に1行のテキストしかバッファーに入れられず、各行を人間のユーザーに出力するたびに割り当てを更新する場合、受信側のシステムに各行が到着する間隔は少なくとも0.5秒になります。出力装置の速度が約150文字/秒を超えるまでは、これは問題にならないはずです。ただし、ホストの遅延は0.1秒から1.0秒の範囲と見積もられているので、この「小さなバッファー」の問題は、もっと低速な装置でも起こると予想されます。

I suggest that it is appropriate to resume a discussion of measures to circumvent the difficulties brought about by these large delay characteristics. Some areas of discussion could be: buffer sizes in servers and users, echo plex techniques, moving part of the input processing to the user system. If it is decided to move the echo plex functions to the user system, it would be wise to try for a "standard" package, thus reducing a M times N problem to a M plus N problem. Please dig out and read RFC's #1 Crocker, #5 Rulifson, #51 Elie to see some previous thinking about this type of problem.

こうした大きな遅延特性がもたらす困難を回避する手段について、議論を再開するのが適切だと私は提案します。議論すべき分野としては、サーバーとユーザーのバッファーサイズ、エコープレックスの技法、入力処理の一部をユーザーシステムに移すこと、などが考えられます。エコープレックスの機能をユーザーシステムに移すと決めた場合は、「標準」パッケージを目指すのが賢明でしょう。そうすれば、M×Nの問題をM＋Nの問題に減らせます。この種の問題についての過去の考察を知るために、RFC #1（Crocker）、#5（Rulifson）、#51（Elie）を探し出して読んでください。
