RFC 8065

Privacy Considerations for IPv6 Adaptation-Layer Mechanisms

RFC 8065

IPv6適応層メカニズムのプライバシーに関する考慮事項

Abstract

概要

This document discusses how a number of privacy threats apply to technologies designed for IPv6 over various link-layer protocols, and it provides advice to protocol designers on how to address such threats in adaptation-layer specifications for IPv6 over such links.

この文書は、さまざまなリンク層プロトコル上のIPv6向けに設計された技術に、多くのプライバシーの脅威がどのように当てはまるかを論じ、そのようなリンク上のIPv6のための適応層の仕様においてそれらの脅威にどのように対処するかについて、プロトコル設計者に助言を提供します。

1. Introduction

1. はじめに

RFC 6973 [RFC6973] discusses privacy considerations for Internet protocols, and Section 5.2 of that document covers a number of privacy-specific threats. In the context of IPv6 addresses, Section 3 of [RFC7721] provides further elaboration on the applicability of the privacy threats.

RFC 6973 [RFC6973]は、インターネットプロトコルのプライバシーに関する考慮事項を論じており、その文書のセクション5.2では、プライバシーに特有の数々の脅威を取り上げています。IPv6アドレスの文脈では、[RFC7721]のセクション3が、それらのプライバシーの脅威がどのように当てはまるかをさらに詳しく説明しています。

When interface identifiers (IIDs) are generated without sufficient entropy compared to the link lifetime, devices and users can become vulnerable to the various threats discussed there, including:

インターフェイス識別子（interface identifier、IID）がリンクの寿命に比べて十分なエントロピーなしで生成されると、デバイスとユーザーは、そこで論じられているさまざまな脅威に対して脆弱になる可能性があります。その脅威には次のものが含まれます。

  • Correlation of activities over time, if the same identifier is used for traffic over period of time
  • Location tracking, if the same interface identifier is used with different prefixes as a device moves between different networks
  • Device-specific vulnerability exploitation, if the identifier helps identify a vendor or version or protocol and hence suggests what types of attacks to try
  • Address scanning, which enables all of the above attacks by off-link attackers. (On some Non-Broadcast Multi-Access (NBMA) links where all nodes aren't already privy to all on-link addresses, address scans might also be done by on-link attackers; however, in most cases, address scans are not an interesting threat from on-link attackers and thus address scans generally apply only to routable addresses.)
  • 時間経過にわたる活動の相関付け（同じ識別子が一定期間にわたってトラフィックに使われる場合）
  • 位置の追跡（デバイスが異なるネットワーク間を移動する際に、同じインターフェイス識別子が異なるプレフィックスとともに使われる場合）
  • デバイス固有の脆弱性の悪用（識別子がベンダー、バージョン、またはプロトコルの特定に役立ち、それによって試すべき攻撃の種類が示唆される場合）
  • アドレススキャン。これにより、オフリンクの攻撃者が上記のすべての攻撃を行えるようになります。（すべてのノードがすべてのオンリンクアドレスをあらかじめ知っているわけではない一部の非ブロードキャスト多重アクセス（Non-Broadcast Multi-Access、NBMA）リンクでは、オンリンクの攻撃者がアドレススキャンを行うこともありえます。しかし、ほとんどの場合、アドレススキャンはオンリンクの攻撃者にとって興味深い脅威ではないため、一般にアドレススキャンが当てはまるのはルーティング可能なアドレスだけです。）

For example, for links that may last for years, "enough" bits of entropy means at least 46 or so bits (see Section 2 for why) in a routable address; ideally all 64 bits of the IID should be used, although historically some bits have been excluded for reasons discussed in [RFC7421]. Link-local addresses can also be susceptible to the same privacy threats from off-link attackers, since experience shows they are often leaked by upper-layer protocols such as SMTP, SIP, or DNS.

たとえば、何年も存続しうるリンクの場合、「十分な」エントロピーのビット数とは、ルーティング可能なアドレスにおいて少なくとも46ビット程度を意味します（その理由はセクション2を参照してください）。理想的にはIIDの64ビットすべてを使うべきですが、歴史的には、[RFC7421]で論じられている理由により、一部のビットが除外されてきました。経験上、リンクローカルアドレスはSMTP、SIP、DNSなどの上位層プロトコルによって漏洩することが多いため、リンクローカルアドレスもオフリンクの攻撃者からの同じプライバシーの脅威を受けやすい可能性があります。

For these reasons, [RFC8064] recommends using an address generation scheme in [RFC7217], rather than addresses generated from a fixed link-layer address.

これらの理由から、[RFC8064]は、固定のリンク層アドレスから生成されたアドレスではなく、[RFC7217]のアドレス生成方式を使うことを推奨しています。

Furthermore, to mitigate the threat of correlation of activities over time on long-lived links, [RFC4941] specifies the notion of a "temporary" address to be used for transport sessions (typically locally initiated outbound traffic to the Internet) that should not be linkable to a more permanent identifier such as a DNS name, user name, or fixed link-layer address. Indeed, the default address selection rules [RFC6724] now prefer temporary addresses by default for outgoing connections. If a device needs to simultaneously support unlinkable traffic as well as traffic that is linkable to such a stable identifier, supporting simultaneous use of multiple addresses per device is necessary.

さらに、長期間存続するリンクにおける時間経過にわたる活動の相関付けの脅威を緩和するために、[RFC4941]は、トランスポートセッション（典型的には、ローカルから開始されるインターネットへの送信トラフィック）に使用する「一時（temporary）」アドレスという概念を規定しています。このアドレスは、DNS名、ユーザー名、固定のリンク層アドレスなどのより恒久的な識別子と結び付けられるべきではないものです。実際、デフォルトのアドレス選択規則[RFC6724]は現在、送信方向の接続ではデフォルトで一時アドレスを優先します。デバイスが、安定した識別子に結び付けられないトラフィックと、そのような安定した識別子に結び付けられるトラフィックの両方を同時にサポートする必要がある場合は、デバイスごとに複数のアドレスを同時に使用できるようにする必要があります。

2. Amount of Entropy Needed in Global Addresses

2. グローバルアドレスに必要なエントロピーの量

In terms of privacy threats discussed in [RFC7721], the one with the need for the most entropy is address scans of routable addresses. To mitigate address scans, one needs enough entropy to make the probability of a successful address probe be negligible. Typically, this is measured in the length of time it would take to have a 50% probability of getting at least one hit. Address scans often rely on sending a packet such as a TCP SYN or ICMP Echo Request, then determining whether the reply is a) an ICMP unreachable error (if no host exists with that address), b) a TCP response or ICMP Echo Reply (if a host exists), or c) none of those, in which case nothing is known for certain.

[RFC7721]で論じられているプライバシーの脅威のうち、最も多くのエントロピーを必要とするのは、ルーティング可能なアドレスのアドレススキャンです。アドレススキャンを緩和するには、アドレスの探査が成功する確率を無視できるほど小さくするのに十分なエントロピーが必要です。典型的には、これは少なくとも1回ヒットする確率が50%になるまでにかかる時間の長さで測られます。アドレススキャンは多くの場合、TCP SYNやICMP Echo Requestなどのパケットを送信し、その応答が、a) ICMP到達不能エラー（そのアドレスのホストが存在しない場合）、b) TCPレスポンスまたはICMP Echo Reply（ホストが存在する場合）、c) そのいずれでもない（この場合は何も確実にはわからない）、のどれであるかを判定することに依存します。

Many privacy-sensitive devices support a "stealth mode" as discussed in Section 5 of [RFC7288] or are behind a network firewall that will drop unsolicited inbound traffic (e.g., TCP SYNs, ICMP Echo Requests, etc.) and thus no TCP RST or ICMP Echo Reply will be sent. In such cases, and when the device does not listen on a well-known TCP or UDP port known to the scanner, the effectiveness of an address scan is limited by the ability to get ICMP unreachable errors, since the attacker can only infer the presence of a host based on the absence of an ICMP unreachable error.

プライバシーを重視する多くのデバイスは、[RFC7288]のセクション5で論じられている「ステルスモード」をサポートしているか、要求されていない受信トラフィック（たとえば、TCP SYN、ICMP Echo Requestなど）を破棄するネットワークファイアウォールの背後にあるため、TCP RSTやICMP Echo Replyは送信されません。そのような場合で、かつデバイスがスキャナーに知られているウェルノウンのTCPまたはUDPポートで待ち受けていない場合、攻撃者はICMP到達不能エラーがないことに基づいてしかホストの存在を推測できないため、アドレススキャンの有効性は、ICMP到達不能エラーを得られるかどうかによって制限されます。

Generation of ICMP unreachable errors is typically rate limited to 2 per second (the default in routers such as Cisco routers running IOS 12.0 or later). Such a rate results in taking about a year to completely scan 26 bits of space.

ICMP到達不能エラーの生成は、典型的には毎秒2個にレート制限されています（IOS 12.0以降を実行するCiscoルーターなどのルーターにおけるデフォルト）。このレートでは、26ビットの空間を完全にスキャンするのに約1年かかることになります。

The actual math is as follows. Let 2^N be the number of devices on the subnet. Let 2^M be the size of the space to scan (i.e., M bits of entropy). Let S be the number of scan attempts. The formula for a 50% chance of getting at least one hit in S attempts is: P(at least one success) = 1 - (1 - 2^N/2^M)^S = 1/2. Assuming 2^M >> S, this simplifies to: S * 2^N/2^M = 1/2, giving S = 2^(M-N-1), or M = N + 1 + log_2(S). Using a scan rate of 2 per second, this results in the following rule of thumb:

実際の計算は次のとおりです。サブネット上のデバイスの数を2^Nとします。スキャンする空間の大きさを2^M（つまり、Mビットのエントロピー）とします。スキャンの試行回数をSとします。S回の試行で少なくとも1回ヒットする確率が50%になる式は次のとおりです。 P(at least one success) = 1 - (1 - 2^N/2^M)^S = 1/2. 2^M >> Sと仮定すると、これは次のように単純化されます。 S * 2^N/2^M = 1/2。これにより、S = 2^(M-N-1)、すなわちM = N + 1 + log_2(S)となります。 毎秒2回のスキャンレートを使うと、次の経験則が得られます。

   Bits of entropy needed =
      log_2(# devices per link) + log_2(seconds of link lifetime) + 2

   Bits of entropy needed =
      log_2(# devices per link) + log_2(seconds of link lifetime) + 2

For example, for a network with at most 2^16 devices on the same long-lived link, where the average lifetime of a link is 8 years (2^28 seconds) or less, this results in a need for at least 46 bits of entropy (16+28+2) so that an address scan would need to be sustained for longer than the lifetime of the link to have a 50% chance of getting a hit.

たとえば、同じ長期間存続するリンク上のデバイスが最大2^16個で、リンクの平均寿命が8年（2^28秒）以下のネットワークの場合、少なくとも46ビット（16+28+2）のエントロピーが必要になります。これにより、ヒットする確率を50%にするには、アドレススキャンをリンクの寿命よりも長く継続する必要が生じます。

Although 46 bits of entropy may be enough to provide privacy in such cases, 59 or more bits of entropy would be needed if addresses are used to provide security against attacks such as spoofing, as CGAs [RFC3972] and HBAs [RFC5535] do, since attacks are not limited by ICMP rate limiting but by the processing power of the attacker. See those RFCs for more discussion.

そのような場合、プライバシーを提供するには46ビットのエントロピーで十分かもしれませんが、CGA [RFC3972]やHBA [RFC5535]のように、アドレスをなりすましなどの攻撃に対するセキュリティーを提供するために使う場合は、59ビット以上のエントロピーが必要になります。これは、攻撃がICMPのレート制限ではなく、攻撃者の処理能力によって制限されるためです。詳しい議論については、それらのRFCを参照してください。

If, on the other hand, the devices being scanned for respond to unsolicited inbound packets, then the address scan is not limited by the ICMP unreachable rate limit in routers, since an adversary can determine the presence of a host without them. In such cases, more bits of entropy would be needed to provide the same level of protection.

一方、スキャン対象のデバイスが要求されていない受信パケットに応答する場合、敵対者はICMP到達不能エラーなしでホストの存在を判定できるため、アドレススキャンはルーターにおけるICMP到達不能エラーのレート制限によって制限されません。そのような場合、同じレベルの保護を提供するには、より多くのビットのエントロピーが必要になります。

3.1. IEEE-Identifier-Based Addresses

3.1. IEEE識別子に基づくアドレス

Some technologies allow the use of IEEE EUI-48 or EUI-64 identifiers or allow the use of an arbitrary 64-bit identifier. Using such an identifier to construct IPv6 addresses makes it easy to use the normal LOWPAN_IPHC encoding [RFC6282] with stateless compression, which allows such IPv6 addresses to be fully elided in common cases.

一部の技術では、IEEEのEUI-48やEUI-64の識別子の使用、または任意の64ビットの識別子の使用が許されています。そのような識別子を使ってIPv6アドレスを構成すると、ステートレス圧縮を伴う通常のLOWPAN_IPHCエンコーディング[RFC6282]を容易に使えるようになり、一般的な場合にはそのようなIPv6アドレスを完全に省略できます。

Global addresses with interface identifiers formed from IEEE identifiers can have insufficient entropy to mitigate address scans unless the IEEE identifier itself has sufficient entropy and enough bits of entropy are carried over into the IPv6 address to sufficiently mitigate the threats. Privacy threats other than "Correlation over time" can be mitigated using per-network randomized link-layer addresses with enough entropy compared to the link lifetime. A number of such proposals can be found at <https://mentor.ieee.org/privecsg/documents>, and Section 10.8 of [BTCorev4.1] specifies one for Bluetooth. Using routable IPv6 addresses derived from such link-layer addresses would be roughly equivalent to those specified in [RFC7217].

IEEE識別子から形成されたインターフェイス識別子を持つグローバルアドレスは、IEEE識別子自体が十分なエントロピーを持ち、かつ脅威を十分に緩和できるだけのビット数のエントロピーがIPv6アドレスに引き継がれない限り、アドレススキャンを緩和するにはエントロピーが不十分なことがあります。「時間経過にわたる相関付け」以外のプライバシーの脅威は、リンクの寿命に比べて十分なエントロピーを持つ、ネットワークごとにランダム化されたリンク層アドレスを使うことで緩和できます。そのような提案の多くは<https://mentor.ieee.org/privecsg/documents>で見つけることができ、[BTCorev4.1]のセクション10.8ではBluetooth向けの提案を1つ規定しています。そのようなリンク層アドレスから導出されたルーティング可能なIPv6アドレスを使うことは、[RFC7217]で規定されているアドレスとおおむね同等になるでしょう。

Correlation over time (for all addresses, not just routable addresses) can be mitigated if the link-layer address itself changes often enough, such as each time the link is established, if the link lifetime is short. For further discussion, see [RANDOM-ADDR].

時間経過にわたる相関付け（ルーティング可能なアドレスだけでなく、すべてのアドレスに対するもの）は、リンクの寿命が短い場合、リンクが確立されるたびになど、リンク層アドレス自体が十分な頻度で変わるなら緩和できます。さらなる議論については、[RANDOM-ADDR]を参照してください。

Another potential concern is that of efficiency, such as avoiding Duplicate Address Detection (DAD) altogether when IPv6 addresses are based on IEEE identifiers. Appendix A of [RFC4429] provides an analysis of address-collision probability based on the number of bits of entropy. A simple web search on "duplicate MAC addresses" will show that collisions do happen with MAC addresses; thus, based on the analysis in [RFC4429], using sufficient bits of entropy in random addresses can provide greater protection against collision than using MAC addresses.

もう1つの潜在的な懸念は効率です。たとえば、IPv6アドレスがIEEE識別子に基づく場合に、重複アドレス検出（Duplicate Address Detection、DAD）を完全に省くといったことです。[RFC4429]の付録Aでは、エントロピーのビット数に基づくアドレス衝突の確率の分析を提供しています。「duplicate MAC addresses」で簡単にウェブ検索すれば、MACアドレスでも実際に衝突が起こることがわかります。したがって、[RFC4429]の分析に基づけば、ランダムなアドレスに十分なビット数のエントロピーを使うことで、MACアドレスを使うよりも衝突に対する強い保護を提供できます。

3.2. Short Addresses

3.2. ショートアドレス

A routable IPv6 address with an interface identifier formed from the combination of a "Short Address" and a set of well-known constant bits (such as padding with 0's) lacks sufficient entropy to mitigate address scanning unless the link lifetime is extremely short. Furthermore, an adversary could also use statistical methods to determine the size of the L2 address space and thereby make some inference regarding the underlying technology on a given link, and target further attacks accordingly.

「ショートアドレス」とよく知られた定数のビットの集合（0によるパディングなど）を組み合わせて形成したインターフェイス識別子を持つルーティング可能なIPv6アドレスは、リンクの寿命が極めて短い場合を除き、アドレススキャンを緩和するのに十分なエントロピーを持ちません。さらに、敵対者は統計的手法を使ってL2アドレス空間の大きさを判定し、それによって特定のリンクの基盤となる技術について何らかの推測を行い、それに応じてさらなる攻撃の標的を定めることもできます。

When Short Addresses are desired on links that are not guaranteed to have a short enough lifetime, the mechanism for constructing an IPv6 interface identifier from a Short Address could be designed to sufficiently mitigate the problem. For example, if all nodes on a given L2 network have a shared secret (such as the key needed to get on the layer-2 network), the 64-bit IID might be generated using a one-way hash that includes (at least) the shared secret together with the Short Address. The use of such a hash would result in the IIDs being spread out among the full range of IID address space, thus mitigating address scans while still allowing full stateless compression/elision.

リンクの寿命が十分に短いことが保証されていないリンクでショートアドレスが望まれる場合、ショートアドレスからIPv6インターフェイス識別子を構成するメカニズムを、この問題を十分に緩和するように設計することもできます。たとえば、あるL2ネットワーク上のすべてのノードが共有秘密（レイヤー2ネットワークに参加するために必要な鍵など）を持っている場合、64ビットのIIDは、（少なくとも）その共有秘密をショートアドレスとともに含む一方向ハッシュを使って生成できるかもしれません。そのようなハッシュを使うと、IIDはIIDアドレス空間の全範囲に分散されるため、完全なステートレス圧縮／省略を可能にしたまま、アドレススキャンを緩和できます。

For long-lived links, "temporary" addresses might even be generated in the same way by (for example) also including in the hash the Version Number from the Authoritative Border Router Option (Section 4.3 of [RFC6775]), if any. This would allow changing temporary addresses whenever the Version Number is changed, even if the set of prefix or context information is unchanged.

長期間存続するリンクでは、（たとえば）権威境界ルーターオプション（Authoritative Border Router Option）（[RFC6775]のセクション4.3）があればそのVersion Numberもハッシュに含めることで、同じ方法で「一時」アドレスを生成することさえできます。これにより、プレフィックスやコンテキスト情報の集合が変わらなくても、Version Numberが変わるたびに一時アドレスを変更できるようになります。

In summary, any specification using Short Addresses should carefully construct an IID generation mechanism so as to provide sufficient entropy compared to the link lifetime.

まとめると、ショートアドレスを使う仕様はすべて、リンクの寿命に比べて十分なエントロピーを提供するように、IIDの生成メカニズムを慎重に構成すべきです。

4. Recommendations

4. 推奨事項

The following are recommended for adaptation-layer specifications:

適応層の仕様には、次のことが推奨されます。

  • Security (privacy) sections should say how address scans are mitigated. An address scan might be mitigated by having a link always be short-lived, by having a large number of bits of entropy in routable addresses, or by some combination thereof. Thus, a specification should explain what the maximum lifetime of a link is in practice and show how the number of bits of entropy is sufficient given that lifetime.
  • Technologies should define a way to include sufficient bits of entropy in the IPv6 interface identifier, based on the maximum link lifetime. Specifying that randomized link-layer addresses can be used is one easy way to do so, for technologies that support such identifiers.
  • Specifications should not simply construct an IPv6 interface identifier by padding a Short Address with a set of other well-known constant bits, unless the link lifetime is guaranteed to be extremely short or the Short Address is allocated by the network (rather than being constant in the node). This also applies to link-local addresses if the same Short Address is used independent of network and is unique enough to allow location tracking.
  • Specifications should make sure that an IPv6 address can change over long periods of time. For example, the interface identifier might change each time a device connects to the network (if connections are short) or might change each day (if connections can be long). This is necessary to mitigate correlation over time.
  • If a device can roam between networks and more than a few bits of entropy exist in the IPv6 interface identifier, then make sure that the interface identifier can vary per network as the device roams. This is necessary to mitigate location tracking.
  • セキュリティー（プライバシー）のセクションでは、アドレススキャンをどのように緩和するかを述べるべきです。アドレススキャンは、リンクを常に短命にすること、ルーティング可能なアドレスに多くのビット数のエントロピーを持たせること、またはそれらの何らかの組み合わせによって緩和できるかもしれません。したがって、仕様では、実際にリンクの最大寿命がどのくらいかを説明し、その寿命に対してエントロピーのビット数がどのように十分であるかを示すべきです。
  • 技術は、リンクの最大寿命に基づいて、IPv6インターフェイス識別子に十分なビット数のエントロピーを含める方法を定義すべきです。ランダム化されたリンク層アドレスを使用できると規定することは、そのような識別子をサポートする技術にとって、これを実現する簡単な方法の1つです。
  • 仕様は、リンクの寿命が極めて短いことが保証されているか、ショートアドレスが（ノード内で一定ではなく）ネットワークによって割り当てられる場合を除き、ショートアドレスにほかのよく知られた定数のビットの集合をパディングするだけでIPv6インターフェイス識別子を構成すべきではありません。これは、同じショートアドレスがネットワークに関係なく使われ、かつ位置の追跡を可能にするほど一意性が高い場合には、リンクローカルアドレスにも当てはまります。
  • 仕様は、IPv6アドレスが長期間のうちに変わりうることを保証すべきです。たとえば、インターフェイス識別子は、デバイスがネットワークに接続するたびに変わる（接続が短い場合）か、毎日変わる（接続が長くなりうる場合）ようにできるでしょう。これは、時間経過にわたる相関付けを緩和するために必要です。
  • デバイスがネットワーク間をローミングでき、かつIPv6インターフェイス識別子に数ビットを超えるエントロピーが存在する場合は、デバイスがローミングするにつれてインターフェイス識別子がネットワークごとに変わりうるようにしてください。これは、位置の追跡を緩和するために必要です。

5. セキュリティーに関する考慮事項
