RFC 8832

WebRTC Data Channel Establishment Protocol

RFC 8832

WebRTCデータチャネル確立プロトコル

Abstract

概要

The WebRTC framework specifies protocol support for direct interactive rich communication using audio, video, and data between two peers' web browsers. This document specifies a simple protocol for establishing symmetric data channels between the peers. It uses a two-way handshake and allows sending of user data without waiting for the handshake to complete.

WebRTCフレームワークは、2つのピアのWebブラウザー間で、音声、ビデオ、データを使った直接的かつ対話的で豊かなコミュニケーションを行うためのプロトコルサポートを規定しています。 この文書は、ピア間で対称的なデータチャネルを確立するためのシンプルなプロトコルを規定します。 このプロトコルは2ウェイハンドシェイクを使用し、ハンドシェイクの完了を待たずにユーザーデータを送信できるようにします。

1. Introduction

1. はじめに

The Data Channel Establishment Protocol (DCEP) is designed to provide, in the WebRTC data channel context [RFC8831], a simple in-band method for opening symmetric data channels. As discussed in [RFC8831], the protocol uses the Stream Control Transmission Protocol (SCTP) [RFC4960] encapsulated in Datagram Transport Layer Security (DTLS) (described in [RFC8261]). This allows DCEP to benefit from the already standardized transport and security features of SCTP and DTLS. DTLS 1.0 is defined in [RFC4347]; the present latest version, DTLS 1.2, is defined in [RFC6347]; and an upcoming version, DTLS 1.3, is defined in [TLS-DTLS13].

データチャネル確立プロトコル（Data Channel Establishment Protocol: DCEP）は、WebRTCのデータチャネルの文脈[RFC8831]において、対称的なデータチャネルをオープンするためのシンプルなインバンドの方法を提供するように設計されています。 [RFC8831]で議論されているように、このプロトコルは、（[RFC8261]で説明されている）データグラムトランスポート層セキュリティー（Datagram Transport Layer Security: DTLS）にカプセル化されたストリーム制御伝送プロトコル（Stream Control Transmission Protocol: SCTP）[RFC4960]を使用します。 これにより、DCEPは、すでに標準化されているSCTPとDTLSのトランスポート機能とセキュリティー機能の恩恵を受けられます。 DTLS 1.0は[RFC4347]で定義されており、現在の最新バージョンであるDTLS 1.2は[RFC6347]で定義されており、今後のバージョンであるDTLS 1.3は[TLS-DTLS13]で定義されています。

3. Terminology

3. 用語

This document uses the following terms:

この文書では、次の用語を使用します。

Association:
An SCTP association.
Stream:
A unidirectional stream of an SCTP association. It is uniquely identified by an SCTP stream identifier (0-65534). Note: The SCTP stream identifier 65535 is reserved due to SCTP INIT and INIT-ACK chunks only allowing a maximum of 65535 streams to be negotiated (0-65534).
Stream Identifier:
The SCTP stream identifier uniquely identifying a stream.
Data Channel:
Two streams with the same stream identifier, one in each direction, which are managed together.

ストリーム識別子（Stream Identifier）：
ストリームを一意に識別するSCTPストリーム識別子。

4. Protocol Overview

4. プロトコルの概要

The Data Channel Establishment Protocol is a simple, low-overhead way to establish bidirectional data channels over an SCTP association with a consistent set of properties.

データチャネル確立プロトコルは、一貫したプロパティーの集合を持つ双方向のデータチャネルをSCTPアソシエーション上に確立するための、シンプルでオーバーヘッドの低い方法です。

The set of consistent properties includes:

一貫したプロパティーの集合には次のものが含まれます。

  • reliable or unreliable message transmission. In case of unreliable transmissions, the same level of unreliability is used.
  • in-order or out-of-order message delivery.
  • the priority of the data channel.
  • an optional label for the data channel.
  • an optional protocol for the data channel.
  • the streams.
  • 信頼性のあるメッセージ送信か、信頼性のないメッセージ送信か。信頼性のない送信の場合は、同じレベルの非信頼性が使用されます。
  • 順序どおりのメッセージ配信か、順序どおりでないメッセージ配信か。
  • データチャネルの優先度。
  • データチャネルの省略可能なラベル。
  • データチャネルの省略可能なプロトコル。
  • ストリーム。

This protocol uses a two-way handshake to open a data channel. The handshake pairs one incoming and one outgoing stream, both having the same stream identifier, into a single bidirectional data channel. The peer that initiates opening a data channel selects a stream identifier for which the corresponding incoming and outgoing streams are unused and sends a DATA_CHANNEL_OPEN message on the outgoing stream. The peer responds with a DATA_CHANNEL_ACK message on its corresponding outgoing stream. Then the data channel is open. DCEP messages are sent on the same stream as the user messages belonging to the data channel. The demultiplexing is based on the SCTP Payload Protocol Identifier (PPID), since DCEP uses a specific PPID.

このプロトコルは、データチャネルをオープンするために2ウェイハンドシェイクを使用します。 このハンドシェイクは、どちらも同じストリーム識別子を持つ1つの着信ストリームと1つの発信ストリームを対にして、単一の双方向データチャネルにします。 データチャネルのオープンを開始するピアは、対応する着信ストリームと発信ストリームが未使用であるストリーム識別子を選択し、その発信ストリーム上でDATA_CHANNEL_OPENメッセージを送信します。 相手のピアは、自身の対応する発信ストリーム上でDATA_CHANNEL_ACKメッセージを返して応答します。 これでデータチャネルがオープンされます。 DCEPメッセージは、そのデータチャネルに属するユーザーメッセージと同じストリーム上で送信されます。 DCEPは固有のPPIDを使用するので、多重分離はSCTPペイロードプロトコル識別子（Payload Protocol Identifier: PPID）に基づいて行われます。

Note: The opening side MAY send user messages before the DATA_CHANNEL_ACK is received.

注：オープンする側は、DATA_CHANNEL_ACKを受信する前にユーザーメッセージを送信してもよいです（MAY）。

To avoid collisions where both sides try to open a data channel with the same stream identifiers, each side MUST use streams with either even or odd stream identifiers when sending a DATA_CHANNEL_OPEN message. When using SCTP over DTLS [RFC8261], the method used to determine which side uses odd or even is based on the underlying DTLS connection role: the side acting as the DTLS client MUST use streams with even stream identifiers; the side acting as the DTLS server MUST use streams with odd stream identifiers.

両側が同じストリーム識別子でデータチャネルをオープンしようとする衝突を避けるため、各側はDATA_CHANNEL_OPENメッセージを送信するとき、偶数か奇数のどちらか一方のストリーム識別子を持つストリームを使用しなければなりません（MUST）。 SCTP over DTLS [RFC8261]を使用する場合、どちらの側が奇数または偶数を使用するかを決定する方法は、下位のDTLS接続のロールに基づきます。 DTLSクライアントとして動作する側は、偶数のストリーム識別子を持つストリームを使用しなければなりません（MUST）。 DTLSサーバーとして動作する側は、奇数のストリーム識別子を持つストリームを使用しなければなりません（MUST）。

Note: There is no attempt to ensure uniqueness for the label; if both sides open a data channel labeled "x" at the same time, there will be two data channels labeled "x" -- one on an even stream pair, one on an odd pair.

注：ラベルの一意性を保証する試みは行われません。 両側が同時に "x" というラベルのデータチャネルをオープンした場合、"x" というラベルのデータチャネルが2つ存在することになります（1つは偶数のストリームの対上に、もう1つは奇数の対上に）。

The purpose of the protocol field is to ease cross-application interoperation ("federation") by identifying the user data being passed by means of an IANA-registered string from the "WebSocket Subprotocol Name Registry" defined in [RFC6455]. The field may be useful for homogeneous applications that may create more than one type of data channel. Note that there is no attempt to ensure uniqueness for the protocol field.

プロトコルフィールドの目的は、[RFC6455]で定義されている「WebSocket Subprotocol Name Registry」に登録されたIANA登録の文字列によって受け渡されるユーザーデータを識別することにより、アプリケーション間の相互運用（「フェデレーション」）を容易にすることです。 このフィールドは、複数の種類のデータチャネルを作成する可能性のある同種のアプリケーションにとって役立つ場合があります。 プロトコルフィールドの一意性を保証する試みは行われないことに注意してください。

5.2. DATA_CHANNEL_ACK Message

5.2. DATA_CHANNEL_ACKメッセージ

This message is sent in response to a DATA_CHANNEL_OPEN_RESPONSE message. It is sent on the stream used for user messages using the data channel. Reception of this message tells the opener that the data channel setup handshake is complete.

このメッセージは、DATA_CHANNEL_OPEN_RESPONSEメッセージへの応答として送信されます。 このメッセージは、そのデータチャネルを使用してユーザーメッセージ用のストリーム上で送信されます。 このメッセージを受信することで、オープンした側は、データチャネルのセットアップのハンドシェイクが完了したことを知ります。

6. Procedures

6. 手順

All DCEP messages MUST be sent using ordered delivery and reliable transmission. They MUST be sent on the same outgoing stream as the user messages belonging to the corresponding data channel. Multiplexing and demultiplexing is done by using the SCTP PPID. Therefore, a DCEP message MUST be sent with the assigned PPID for the Data Channel Establishment Protocol (see Section 8.1). Other messages MUST NOT be sent using this PPID.

すべてのDCEPメッセージは、順序どおりの配信と信頼性のある送信を使用して送信しなければなりません（MUST）。 DCEPメッセージは、対応するデータチャネルに属するユーザーメッセージと同じ発信ストリーム上で送信しなければなりません（MUST）。 多重化と多重分離は、SCTPのPPIDを使用して行われます。 したがって、DCEPメッセージは、データチャネル確立プロトコルに割り当てられたPPID（Section 8.1を参照）を付けて送信しなければなりません（MUST）。 その他のメッセージをこのPPIDを使用して送信してはなりません（MUST NOT）。

The peer that initiates opening a data channel selects a stream identifier for which the corresponding incoming and outgoing streams are unused. If the side is acting as the DTLS client, it MUST choose an even stream identifier; if the side is acting as the DTLS server, it MUST choose an odd one. The initiating peer fills in the parameters of the DATA_CHANNEL_OPEN message and sends it on the chosen stream.

データチャネルのオープンを開始するピアは、対応する着信ストリームと発信ストリームが未使用であるストリーム識別子を選択します。 その側がDTLSクライアントとして動作している場合は、偶数のストリーム識別子を選択しなければなりません（MUST）。 その側がDTLSサーバーとして動作している場合は、奇数のストリーム識別子を選択しなければなりません（MUST）。 開始するピアは、DATA_CHANNEL_OPENメッセージのパラメーターを埋めて、選択したストリーム上でそのメッセージを送信します。

If a DATA_CHANNEL_OPEN message is received on an unused stream, the stream identifier corresponds to the role of the peer, and all parameters in the DATA_CHANNEL_OPEN message are valid, then a corresponding DATA_CHANNEL_ACK message is sent on the stream with the same stream identifier as the one the DATA_CHANNEL_OPEN message was received on.

DATA_CHANNEL_OPENメッセージが未使用のストリーム上で受信され、そのストリーム識別子がピアのロールに対応しており、DATA_CHANNEL_OPENメッセージ内のすべてのパラメーターが有効である場合、DATA_CHANNEL_OPENメッセージを受信したストリームと同じストリーム識別子を持つストリーム上で、対応するDATA_CHANNEL_ACKメッセージが送信されます。

If the DATA_CHANNEL_OPEN message doesn't satisfy the conditions above, the receiver MUST close the corresponding data channel using the procedure described in [RFC8831] and MUST NOT send a DATA_CHANNEL_ACK message in response to the received message. This might occur if, for example, a DATA_CHANNEL_OPEN message is received on an already used stream, there are problems with parameters within the DATA_CHANNEL_OPEN message, the odd/even rule is violated, or the DATA_CHANNEL_OPEN message itself is not well formed. Therefore, receiving an SCTP stream-reset request for a stream on which no DATA_CHANNEL_ACK message has been received indicates to the sender of the corresponding DATA_CHANNEL_OPEN message the failure of the data channel setup procedure. After also successfully resetting the corresponding outgoing stream, which concludes the data channel closing initiated by the peer, a new DATA_CHANNEL_OPEN message can be sent on the stream.

DATA_CHANNEL_OPENメッセージが上記の条件を満たさない場合、受信者は[RFC8831]で説明されている手順を使用して対応するデータチャネルをクローズしなければなりません（MUST）。 また、受信したメッセージへの応答としてDATA_CHANNEL_ACKメッセージを送信してはなりません（MUST NOT）。 これは、たとえば、すでに使用されているストリーム上でDATA_CHANNEL_OPENメッセージを受信した場合、DATA_CHANNEL_OPENメッセージ内のパラメーターに問題がある場合、奇数/偶数のルールに違反している場合、DATA_CHANNEL_OPENメッセージ自体が整形式でない場合に発生する可能性があります。 したがって、DATA_CHANNEL_ACKメッセージをまだ受信していないストリームに対するSCTPストリームリセット要求を受信することは、対応するDATA_CHANNEL_OPENメッセージの送信者に、データチャネルのセットアップ手順が失敗したことを示します。 対応する発信ストリームのリセットにも成功し、それによってピアが開始したデータチャネルのクローズが完了した後は、そのストリーム上で新しいDATA_CHANNEL_OPENメッセージを送信できます。

After the DATA_CHANNEL_OPEN message has been sent, the sender of that message MAY start sending messages containing user data without waiting for the reception of the corresponding DATA_CHANNEL_ACK message. However, before the DATA_CHANNEL_ACK message or any other message has been received on a data channel, all other messages containing user data and belonging to this data channel MUST be sent ordered, no matter whether the data channel is ordered or not. After the DATA_CHANNEL_ACK or any other message has been received on the data channel, messages containing user data MUST be sent ordered on ordered data channels and MUST be sent unordered on unordered data channels. Therefore, receiving a message containing user data on an unused stream indicates an error. In that case, the corresponding data channel MUST be closed, as described in [RFC8831].

DATA_CHANNEL_OPENメッセージを送信した後、そのメッセージの送信者は、対応するDATA_CHANNEL_ACKメッセージの受信を待たずに、ユーザーデータを含むメッセージの送信を開始してもよいです（MAY）。 ただし、データチャネル上でDATA_CHANNEL_ACKメッセージまたはその他のメッセージを受信する前は、このデータチャネルに属するユーザーデータを含むその他のすべてのメッセージを、データチャネルが順序どおりであるかどうかにかかわらず、順序どおりに送信しなければなりません（MUST）。 データチャネル上でDATA_CHANNEL_ACKまたはその他のメッセージを受信した後は、ユーザーデータを含むメッセージを、順序どおりのデータチャネルでは順序どおりに送信しなければなりません（MUST）。 また、順序なしのデータチャネルでは順序なしで送信しなければなりません（MUST）。 したがって、未使用のストリーム上でユーザーデータを含むメッセージを受信することは、エラーを示します。 その場合、[RFC8831]で説明されているように、対応するデータチャネルをクローズしなければなりません（MUST）。

7. Security Considerations

7. セキュリティーに関する考慮事項

The DATA_CHANNEL_OPEN message contains two variable-length fields: the protocol and the label. A receiver must be prepared to receive DATA_CHANNEL_OPEN messages where these fields have the maximum length of 65535 bytes. Error cases such as using inconsistent lengths of fields, using unknown parameter values, or violating the odd/even rule must also be handled by closing the corresponding data channel. An end point must also be prepared for the peer to open the maximum number of data channels.

DATA_CHANNEL_OPENメッセージには、プロトコルとラベルという2つの可変長フィールドが含まれます。 受信者は、これらのフィールドが最大長の65535バイトであるDATA_CHANNEL_OPENメッセージを受信する準備をしておく必要があります。 フィールドの長さの不整合、未知のパラメーター値の使用、奇数/偶数のルールへの違反などのエラーケースも、対応するデータチャネルをクローズすることで処理する必要があります。 エンドポイントは、ピアが最大数のデータチャネルをオープンすることにも備えておく必要があります。

This protocol does not provide privacy, integrity, or authentication. It needs to be used as part of a protocol suite that contains all these things. Such a protocol suite is specified in [RFC8261].

このプロトコルは、プライバシー、完全性、認証を提供しません。 このプロトコルは、これらすべてを含むプロトコルスイートの一部として使用する必要があります。 そのようなプロトコルスイートは[RFC8261]で規定されています。

For general considerations, see [RFC8826] and [RFC8827].

一般的な考慮事項については、[RFC8826]と[RFC8827]を参照してください。
