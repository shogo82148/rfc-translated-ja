RFC 8120

Mutual Authentication Protocol for HTTP

RFC 8120

HTTPの相互認証プロトコル

Abstract

概要

This document specifies an authentication scheme for the Hypertext Transfer Protocol (HTTP) that is referred to as either the Mutual authentication scheme or the Mutual authentication protocol. This scheme provides true mutual authentication between an HTTP client and an HTTP server using password-based authentication. Unlike the Basic and Digest authentication schemes, the Mutual authentication scheme specified in this document assures the user that the server truly knows the user's encrypted password.

この文書は、Mutual認証スキームまたはMutual認証プロトコルと呼ばれる、ハイパーテキスト転送プロトコル（HTTP）の認証スキームを規定します。 このスキームは、パスワードベースの認証を使用して、HTTPクライアントとHTTPサーバーの間で真の相互認証を提供します。 BasicおよびDigest認証スキームとは異なり、この文書で規定するMutual認証スキームは、サーバーがユーザーの暗号化されたパスワードを本当に知っていることをユーザーに保証します。

1. Introduction

1. はじめに

This document specifies an authentication scheme for the Hypertext Transfer Protocol (HTTP) that is referred to as either the Mutual authentication scheme or the Mutual authentication protocol. This scheme provides true mutual authentication between an HTTP client and an HTTP server using just a simple password as a credential.

この文書は、Mutual認証スキームまたはMutual認証プロトコルと呼ばれる、ハイパーテキスト転送プロトコル（HTTP）の認証スキームを規定します。 このスキームは、単純なパスワードだけをクレデンシャルとして使用して、HTTPクライアントとHTTPサーバーの間で真の相互認証を提供します。

Password-stealing attacks are one of the most critical threats for Web systems. Plain-text password authentication techniques (Basic authentication and Web-form-based authentication) have been widely used for a long time. When these techniques are used with plain HTTP protocols, it is trivially easy for attackers to sniff the password credentials on the wire.

パスワードを盗む攻撃は、Webシステムにとって最も重大な脅威の1つです。 平文のパスワード認証技術（Basic認証やWebフォームベースの認証）は、長い間広く使われてきました。 これらの技術を平文のHTTPプロトコルで使用すると、攻撃者は通信路上でパスワードクレデンシャルをきわめて容易に盗聴できます。

The Digest authentication scheme [RFC7616] uses SHA-256 and SHA-512/256 (formerly SHA-1 and MD5) hash algorithms to hide the raw user password from network sniffers. However, if the number of possible candidate users' passwords is not enough, newer and more powerful computers can compute possible hash values for billions of password candidates and compare these with the sniffed values to find out the correct password. This kind of attack is called an offline password dictionary attack; the search capacity of these newer computers reduces the effectiveness of users' memorable passwords, thereby threatening the effectiveness of such hash-based password protections.

Digest認証スキーム[RFC7616]は、SHA-256およびSHA-512/256（以前はSHA-1およびMD5）ハッシュアルゴリズムを使用して、生のユーザーパスワードをネットワークの盗聴者から隠します。 しかし、ユーザーのパスワードとしてあり得る候補の数が十分でない場合、より新しく強力なコンピューターは、何十億ものパスワード候補について可能なハッシュ値を計算し、それらを盗聴した値と比較して正しいパスワードを見つけ出せます。 この種の攻撃はオフラインパスワード辞書攻撃と呼ばれます。 これらの新しいコンピューターの探索能力は、ユーザーが記憶できるパスワードの有効性を低下させ、それによってこのようなハッシュベースのパスワード保護の有効性を脅かしています。

Transport Layer Security (TLS) [RFC5246] provides strong cryptographic protection against the network-based sniffing of passwords and other communication contents. If TLS is correctly used by both server operators and client users, passwords and other credentials will not be available to any outside attackers. However, there is a pitfall related to TLS deployment on Web systems: if the users are fraudulently routed to a "wrong Website" via some kind of social engineering attack (e.g., phishing) and tricked into performing authentication on that site, the credentials will be sent to the attacker's server and trivially leaked. Attacks such as phishing have become a serious threat. In current Web system deployments, TLS certificates will be issued to almost any users of the Internet (including malicious attackers). Although those certificates include several levels of the "validation results" (such as corporate names) of the issued entities, the task of "checking" those validation results is left to the users of Web browsers, still leaving open the possibility of such social engineering attacks.

トランスポート層セキュリティー（TLS）[RFC5246]は、パスワードやその他の通信内容をネットワーク上で盗聴されることに対して、強力な暗号学的保護を提供します。 サーバー運用者とクライアントユーザーの両方がTLSを正しく使用すれば、パスワードやその他のクレデンシャルが外部の攻撃者に入手されることはありません。 しかし、WebシステムへのTLSの展開には落とし穴があります。 何らかのソーシャルエンジニアリング攻撃（たとえばフィッシング）によってユーザーが不正に「間違ったWebサイト」へ誘導され、そのサイトで認証を行うようにだまされると、クレデンシャルは攻撃者のサーバーに送信され、たやすく漏洩します。 フィッシングなどの攻撃は深刻な脅威になっています。 現在のWebシステムの展開では、TLS証明書はインターネットのほぼすべてのユーザー（悪意のある攻撃者を含む）に発行されます。 これらの証明書には、発行先のエンティティーに関するいくつかのレベルの「検証結果」（会社名など）が含まれていますが、それらの検証結果を「確認する」作業はWebブラウザーのユーザーに任されており、このようなソーシャルエンジニアリング攻撃の可能性は依然として残っています。

Another way to avoid such threats is to avoid password-based authentication and use some kinds of pre-deployed strong secret keys (on either the client side or the server side) for authentications. Several federated authentication frameworks, as well as HTTP Origin-Bound Authentication (HOBA) [RFC7486], are proposed and deployed on real Web systems to satisfy those needs. However, a type of authentication based on "human-memorable secrets" (i.e., passwords) is still required in several scenarios, such as initialization, key deployment to new clients, or recovery of secret accounts with lost cryptographic keys.

このような脅威を避ける別の方法は、パスワードベースの認証を避け、認証のために何らかの事前に配備された強力な秘密鍵（クライアント側またはサーバー側のいずれか）を使用することです。 このようなニーズを満たすために、いくつかのフェデレーション認証フレームワークや、HTTPオリジン束縛認証（HOBA）[RFC7486]が提案され、実際のWebシステムに展開されています。 しかし、初期化、新しいクライアントへの鍵の配備、暗号鍵を紛失した秘密アカウントの回復など、いくつかのシナリオでは、「人間が記憶できる秘密」（つまりパスワード）に基づく種類の認証が依然として必要です。

The Mutual authentication protocol, as proposed in this document, is a strong cryptographic solution for password authentications. It mainly provides the following two key features:

この文書で提案するMutual認証プロトコルは、パスワード認証のための強力な暗号学的解決策です。 このプロトコルは主に次の2つの重要な特徴を提供します。

  • No password information at all is exchanged in the communications. When the server and the user fail to authenticate with each other, the protocol will not reveal even the tiniest bit of information about the user's password. This prevents any kind of offline password dictionary attacks, even with the existence of phishing attacks.

  • To successfully authenticate, the server, as well as client users, must own the valid registered credentials (authentication secret). This means that a phishing attacker cannot trick users into thinking that it is an "authentic" server. (It should be pointed out that this is not true for Basic and Digest authentication; for example, servers using Basic authentication can answer "YES" to any clients without actually checking authentication at all.) Client users can ascertain whether or not the communicating peer is truly "the server" that registered their account beforehand. In other words, it provides "true" mutual authentication between servers and clients.

  • 通信の中でパスワード情報はまったく交換されません。 サーバーとユーザーが互いの認証に失敗した場合でも、このプロトコルはユーザーのパスワードに関する情報をほんのわずかも明らかにしません。 これにより、フィッシング攻撃が存在する場合でも、あらゆる種類のオフラインパスワード辞書攻撃を防ぎます。

  • 認証に成功するには、クライアントユーザーだけでなくサーバーも、有効な登録済みのクレデンシャル（認証秘密）を所有していなければなりません。 これは、フィッシング攻撃者が、自分が「本物の」サーバーであるとユーザーに思い込ませることはできないことを意味します。 （これはBasic認証やDigest認証には当てはまらないことを指摘しておくべきでしょう。 たとえば、Basic認証を使用するサーバーは、実際には認証をまったく確認せずに、どのクライアントにも「YES」と答えられます。） クライアントユーザーは、通信相手が、事前に自分のアカウントを登録した本当に「そのサーバー」であるかどうかを確かめられます。 言い換えれば、このプロトコルはサーバーとクライアントの間の「真の」相互認証を提供します。

Given the information above, the proposed protocol can serve as a strong alternative to the Basic, Digest, and Web-form-based authentication schemes and also as a strong companion to the non-password-based authentication frameworks.

以上の情報から、提案するプロトコルは、Basic、Digest、Webフォームベースの各認証スキームの強力な代替として、またパスワードに基づかない認証フレームワークの強力な補完として役立ちます。

The proposed protocol will serve in the same way as does existing Basic or Digest authentication: it meets the requirements for new authentication schemes for HTTP, as described in Section 5.1.2 of [RFC7235]. Additionally, to communicate authentication results more reliably between the server and the client user, it suggests that Web browsers have some "secure" way of displaying the authentication results. Having such a user interface in future browsers will greatly reduce the risk of impersonation by various kinds of social engineering attacks, in a manner similar to that of the "green padlock" for Extended Validation TLS certificates.

提案するプロトコルは、既存のBasic認証やDigest認証と同じように機能します。 すなわち、[RFC7235]のセクション5.1.2で説明されているHTTPの新しい認証スキームに対する要件を満たします。 さらに、サーバーとクライアントユーザーの間で認証結果をより確実に伝えるために、Webブラウザーが認証結果を表示する何らかの「安全な」方法を持つことを提案します。 将来のブラウザーにこのようなユーザーインターフェイスがあれば、Extended Validation TLS証明書の「緑の南京錠」と同様に、さまざまな種類のソーシャルエンジニアリング攻撃によるなりすましのリスクを大きく減らせるでしょう。

Technically, the authentication scheme proposed in this document is a general framework for using password-based authenticated key exchange (PAKE) and similar stronger cryptographic primitives with HTTP. The two key features shown above correspond to the nature of PAKE.

技術的には、この文書で提案する認証スキームは、パスワード認証鍵交換（PAKE）や同様のより強力な暗号プリミティブをHTTPで使用するための汎用的なフレームワークです。 上に示した2つの重要な特徴は、PAKEの性質に対応しています。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119].

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 [RFC2119]に記載されているとおりに解釈されるものとします。

This document distinguishes the terms "client" and "user" in the following way: a "client" is an entity that understands and implements HTTP and the specified authentication protocol -- usually computer software; a "user" is typically a human being who wants to access data resources using a "client".

この文書では、「クライアント」と「ユーザー」という用語を次のように区別します。 「クライアント」は、HTTPと規定された認証プロトコルを理解して実装するエンティティー（通常はコンピューターソフトウェア）です。 「ユーザー」は、典型的には「クライアント」を使用してデータリソースにアクセスしたい人間です。

The term "natural numbers" refers to the non-negative integers (including zero) throughout this document.

この文書全体を通じて、「自然数」という用語は非負整数（ゼロを含む）を指します。

This document treats both the input (domain) and the output (codomain) of hash functions as octet strings. When a natural number output for a hash function is required, it will be written as INT(H(s)).

この文書では、ハッシュ関数の入力（定義域）と出力（終域）の両方をオクテット文字列として扱います。 ハッシュ関数の出力として自然数が必要な場合は、INT(H(s))と書きます。

2. Protocol Overview

2. プロトコルの概要

The protocol, as a whole, is designed as a natural extension to HTTP [RFC7230] and uses the framework defined in [RFC7235]. Internally, the server and the client will first perform a cryptographic key exchange, using the secret password as a "tweak" to the exchange. The key exchange will only succeed when the secrets used by both peers are correctly related (i.e., generated from the same password). Then, both peers will verify the authentication results by confirming the sharing of the exchanged key. This section provides a brief outline of the protocol and the exchanged messages.

このプロトコルは、全体として、HTTP[RFC7230]の自然な拡張として設計されており、[RFC7235]で定義されたフレームワークを使用します。 内部的には、サーバーとクライアントはまず、秘密のパスワードを交換の「調整値（tweak）」として使用して、暗号学的な鍵交換を行います。 鍵交換は、両方のピアが使用する秘密が正しく関連している（つまり同じパスワードから生成された）場合にのみ成功します。 次に、両方のピアは、交換した鍵を共有していることを確認することによって認証結果を検証します。 このセクションでは、プロトコルと交換されるメッセージの概略を簡単に示します。

2.1. Messages

2.1. メッセージ

The authentication protocol uses six kinds of messages to perform mutual authentication. These messages have specific names within this specification.

この認証プロトコルは、相互認証を行うために6種類のメッセージを使用します。 これらのメッセージには、この仕様の中で固有の名前が付けられています。

  • Authentication request messages: used by the servers to request that clients start mutual authentication.

    • 401-INIT message: a general message to start the authentication protocol. It is also used as a message indicating an authentication failure.

    • 401-STALE message: a message indicating that the client has to start a new key exchange.

  • Authenticated key exchange messages: used by both peers to perform authentication and the sharing of a cryptographic secret.

    • req-KEX-C1 message: a message sent from the client.

    • 401-KEX-S1 message: an intermediate response to a req-KEX-C1 message from the server.

  • Authentication verification messages: used by both peers to verify the authentication results.

    • req-VFY-C message: a message used by the client to request that the server authenticate and authorize the client.

    • 200-VFY-S message: a response used by the server to indicate that client authentication succeeded. It also contains information necessary for the client to check the authenticity of the server.

  • 認証要求メッセージ：サーバーが、相互認証を開始するようにクライアントに要求するために使用します。

    • 401-INITメッセージ：認証プロトコルを開始するための一般的なメッセージです。 認証の失敗を示すメッセージとしても使用されます。

    • 401-STALEメッセージ：クライアントが新しい鍵交換を開始しなければならないことを示すメッセージです。

  • 認証付き鍵交換メッセージ：両方のピアが、認証と暗号学的な秘密の共有を行うために使用します。

    • req-KEX-C1メッセージ：クライアントから送信されるメッセージです。

    • 401-KEX-S1メッセージ：req-KEX-C1メッセージに対する、サーバーからの中間レスポンスです。

  • 認証検証メッセージ：両方のピアが、認証結果を検証するために使用します。

    • req-VFY-Cメッセージ：クライアントが、サーバーにクライアントの認証と認可を要求するために使用するメッセージです。

    • 200-VFY-Sメッセージ：サーバーが、クライアント認証が成功したことを示すために使用するレスポンスです。 クライアントがサーバーの真正性を確認するために必要な情報も含んでいます。

In addition to the above six kinds of messages, a request or response without any HTTP headers related to this specification will be hereafter called a "normal request" or "normal response", respectively.

上記の6種類のメッセージに加えて、この仕様に関連するHTTPヘッダーを一切含まないリクエストまたはレスポンスを、以下ではそれぞれ「通常のリクエスト」または「通常のレスポンス」と呼びます。

2.2. Typical Flows of the Protocol

2.2. プロトコルの典型的なフロー

In typical cases, client access to a resource protected by the Mutual authentication scheme will use the following protocol sequence:

典型的な場合、Mutual認証スキームで保護されたリソースへのクライアントのアクセスは、次のプロトコルシーケンスを使用します。

  • As is typical in general HTTP protocol designs, a client will at first request a resource without any authentication attempt (1). If the requested resource is protected by the Mutual authentication protocol, the server will respond with a message requesting authentication (401-INIT) (2).

  • The client processes the body of the message and waits for the user to input the username and password. If the username and password are available, the client will send a message with the authenticated key exchange (req-KEX-C1) to start the authentication (3).

  • If the server has received a req-KEX-C1 message, the server looks up the user's authentication information within its user database. Then, the server creates a new session identifier (sid) that will be used to identify sets of the messages that follow it and responds with a message containing a server-side authenticated key exchange value (401-KEX-S1) (4).

  • At this point (5), both peers calculate a shared "session secret" using the exchanged values in the key exchange messages. Only when both the server and the client have used secret credentials generated from the same password will the session secret values match. This session secret will be used for access authentication of every individual request/response pair after this point.

  • The client will send a request with a client-side authentication verification value (req-VFY-C) (6), calculated from the client-generated session secret. The server will check the validity of the verification value using its own version of the session secret.

  • If the authentication verification value from the client was correct, then the client definitely owns the credential based on the expected password (i.e., the client authentication succeeded). The server will respond with a successful message (200-VFY-S) (7). Unlike the usual one-way authentication (e.g., HTTP Basic authentication or POP APOP authentication [RFC1939]), this message also contains a server-side authentication verification value.

    When the client's verification value is incorrect (e.g., because the user-supplied password was incorrect), the server will respond with a 401-INIT message (the same message as the message used in (2)) instead.

  • The client MUST first check the validity of the server-side authentication verification value contained in the message (7). If the value was equal to the expected value, server authentication succeeded.

    If it is not the expected value or the message does not contain the authentication verification value, then the mutual authentication has been broken for some unexpected reason. The client MUST NOT process any body or header values contained in the HTTP response in this case. (Note: This case should not happen between a correctly implemented server and client without any active attacks; such a scenario could be caused by either a man-in-the-middle attack or incorrect implementation.)

  • 一般的なHTTPプロトコル設計で典型的であるように、クライアントはまず認証を試みずにリソースをリクエストします(1)。 リクエストされたリソースがMutual認証プロトコルで保護されている場合、サーバーは認証を要求するメッセージ（401-INIT）で応答します(2)。

  • クライアントはメッセージのボディーを処理し、ユーザーがユーザー名とパスワードを入力するのを待ちます。 ユーザー名とパスワードが得られたら、クライアントは認証を開始するために、認証付き鍵交換を含むメッセージ（req-KEX-C1）を送信します(3)。

  • サーバーは、req-KEX-C1メッセージを受信すると、ユーザーデータベース内でユーザーの認証情報を検索します。 次に、サーバーは、それに続く一連のメッセージを識別するために使用する新しいセッション識別子（sid）を作成し、サーバー側の認証付き鍵交換値を含むメッセージ（401-KEX-S1）で応答します(4)。

  • この時点で(5)、両方のピアは、鍵交換メッセージで交換した値を使用して、共有の「セッション秘密」を計算します。 セッション秘密の値が一致するのは、サーバーとクライアントの両方が同じパスワードから生成された秘密のクレデンシャルを使用した場合だけです。 このセッション秘密は、この時点以降、個々のリクエストとレスポンスの組すべてのアクセス認証に使用されます。

  • クライアントは、クライアントが生成したセッション秘密から計算した、クライアント側の認証検証値を含むリクエスト（req-VFY-C）を送信します(6)。 サーバーは、自分の側のセッション秘密を使用して検証値の正当性を確認します。

  • クライアントからの認証検証値が正しければ、クライアントは期待されるパスワードに基づくクレデンシャルを確かに所有しています（つまり、クライアント認証が成功しました）。 サーバーは成功を示すメッセージ（200-VFY-S）で応答します(7)。 通常の一方向の認証（たとえばHTTPのBasic認証やPOPのAPOP認証[RFC1939]）とは異なり、このメッセージにはサーバー側の認証検証値も含まれます。

    クライアントの検証値が正しくない場合（たとえば、ユーザーが入力したパスワードが間違っていた場合）、サーバーは代わりに401-INITメッセージ（(2)で使用したメッセージと同じメッセージ）で応答します。

  • クライアントはまず、メッセージ(7)に含まれるサーバー側の認証検証値の正当性を確認しなければなりません（MUST）。 値が期待される値と等しければ、サーバー認証は成功です。

    値が期待される値でない場合、またはメッセージに認証検証値が含まれていない場合、何らかの予期しない理由で相互認証が破綻しています。 この場合、クライアントはHTTPレスポンスに含まれるボディーやヘッダーの値を処理してはなりません（MUST NOT）。 （注：正しく実装されたサーバーとクライアントの間では、能動的な攻撃がなければこのケースは起こらないはずです。 このような状況は、中間者攻撃または誤った実装のいずれかによって引き起こされる可能性があります。）

2.3. Alternative Flows

2.3. 代替フロー

As shown above, the typical flow for a first authentication request requires three request-response pairs. To reduce protocol overhead, the protocol enables several shortcut flows that require fewer messages.

上に示したように、最初の認証リクエストの典型的なフローでは、3組のリクエストとレスポンスが必要です。 プロトコルのオーバーヘッドを減らすために、このプロトコルでは、より少ないメッセージで済むいくつかの近道となるフローを使用できます。

  • Case A: If the client knows that the resource is likely to require authentication, the client MAY omit the first unauthenticated request (1) and immediately send a key exchange (req-KEX-C1) message. This will reduce the number of round trips by one.

  • Case B: If both the client and the server previously shared a session secret associated with a valid sid, the client MAY directly send a req-VFY-C message using the existing sid and corresponding session secret. This will further reduce the number of round trips by one.

    The server MAY have thrown out the corresponding session from the session table. If so, the server will respond with a 401-STALE message, indicating that a new key exchange is required. The client SHOULD try again to construct a req-KEX-C1 message in this case.

  • ケースA：リソースが認証を必要とする可能性が高いことをクライアントが知っている場合、クライアントは最初の認証なしのリクエスト(1)を省略し、すぐに鍵交換（req-KEX-C1）メッセージを送信してもよいです（MAY）。 これにより、ラウンドトリップの回数が1回減ります。

  • ケースB：クライアントとサーバーの両方が、有効なsidに関連付けられたセッション秘密を以前に共有している場合、クライアントは既存のsidと対応するセッション秘密を使用して、直接req-VFY-Cメッセージを送信してもよいです（MAY）。 これにより、ラウンドトリップの回数がさらに1回減ります。

    サーバーは、対応するセッションをセッションテーブルからすでに破棄している場合があります（MAY）。 その場合、サーバーは401-STALEメッセージで応答し、新しい鍵交換が必要であることを示します。 この場合、クライアントは改めてreq-KEX-C1メッセージを構築するように試みるべきです（SHOULD）。

Figure 2 depicts the shortcut flows described above. When using appropriate settings and implementations, most of the requests to resources are expected to meet both criteria; thus, only one round trip of request/response will be required.

図2は、上で説明した近道となるフローを示しています。 適切な設定と実装を使用すれば、リソースへのリクエストのほとんどは両方の条件を満たすと期待されます。 したがって、リクエストとレスポンスのラウンドトリップは1回だけで済みます。

For more details, see Sections 10 and 11.

詳細については、セクション10とセクション11を参照してください。

3. Message Syntax

3. メッセージの構文

Throughout this specification, the syntax is denoted in the extended augmented BNF syntax as defined in [RFC7230] and [RFC5234]. The following elements are used in this document per [RFC5234], [RFC7230], and [RFC7235]: DIGIT, ALPHA, SP, auth-scheme, quoted-string, auth-param, header-field, token, challenge, and credentials.

この仕様全体を通じて、構文は[RFC7230]および[RFC5234]で定義されている拡張された拡張BNF構文で表記します。 この文書では、[RFC5234]、[RFC7230]、[RFC7235]に従って次の要素を使用します：DIGIT、ALPHA、SP、auth-scheme、quoted-string、auth-param、header-field、token、challenge、credentials。

The Mutual authentication protocol uses three headers: WWW-Authenticate (usually in responses with a 401 status code), Authorization (in requests), and Authentication-Info (in responses other than a 401 status code). These headers follow the frameworks described in [RFC7235] and [RFC7615]. See Section 4 for more details regarding these headers.

Mutual認証プロトコルは、WWW-Authenticate（通常は401ステータスコードのレスポンス内）、Authorization（リクエスト内）、Authentication-Info（401ステータスコード以外のレスポンス内）の3つのヘッダーを使用します。 これらのヘッダーは、[RFC7235]および[RFC7615]で説明されているフレームワークに従います。 これらのヘッダーの詳細については、セクション4を参照してください。

The framework in [RFC7235] defines the syntax for the headers WWW-Authenticate and Authorization as the syntax elements "challenge" and "credentials", respectively. The auth-scheme element contained in those headers MUST be set to "Mutual" when using the protocol specified in this document. The syntax for "challenge" and "credentials" to be used with the "Mutual" auth-scheme SHALL be name-value pairs (#auth-param), not the "token68" parameter defined in [RFC7235].

[RFC7235]のフレームワークは、WWW-AuthenticateヘッダーとAuthorizationヘッダーの構文を、それぞれ構文要素「challenge」と「credentials」として定義しています。 この文書で規定するプロトコルを使用する場合、これらのヘッダーに含まれるauth-scheme要素は「Mutual」に設定しなければなりません（MUST）。 「Mutual」auth-schemeで使用する「challenge」と「credentials」の構文は、[RFC7235]で定義されている「token68」パラメーターではなく、名前と値の組（#auth-param）とすることになります（SHALL）。

The Authentication-Info header used in this protocol SHALL follow the syntax defined in [RFC7615].

このプロトコルで使用するAuthentication-Infoヘッダーは、[RFC7615]で定義されている構文に従うものとすることになります（SHALL）。

In HTTP, the WWW-Authenticate header may contain two or more challenges. Client implementations SHOULD be aware of, and be capable of correctly handling, those cases.

HTTPでは、WWW-Authenticateヘッダーに2つ以上のチャレンジが含まれることがあります。 クライアントの実装は、そのような場合を意識し、正しく処理できるべきです（SHOULD）。

3.1. Non-ASCII Extended Header Parameters

3.1. 非ASCIIの拡張ヘッダーパラメーター

All of the parameters contained in the above three headers, except for the "realm" field, MAY be extended to ISO 10646-1 values using the framework described in [RFC5987]. All servers and clients MUST be capable of receiving and sending values encoded per the syntax specified in [RFC5987].

上記の3つのヘッダーに含まれるすべてのパラメーターは、「realm」フィールドを除き、[RFC5987]で説明されているフレームワークを使用してISO 10646-1の値に拡張してもよいです（MAY）。 すべてのサーバーとクライアントは、[RFC5987]で規定されている構文に従ってエンコードされた値を受信および送信できなければなりません（MUST）。

If a value to be sent contains only ASCII characters, the field MUST be sent using plain syntax as defined in RFC 7235. The syntax as extended by RFC 5987 MUST NOT be used in this case.

送信する値がASCII文字だけを含む場合、そのフィールドはRFC 7235で定義されている通常の構文を使用して送信しなければなりません（MUST）。 この場合、RFC 5987で拡張された構文を使用してはなりません（MUST NOT）。

If a value (except for the "realm" header) contains one or more non-ASCII characters, the parameter SHOULD be sent using the syntax defined in Section 3.2 of [RFC5987] as "ext-parameter". Such a parameter MUST have a charset value of "UTF-8", and the language value MUST always be omitted (have an empty value). The same parameter MUST NOT be sent more than once, regardless of the syntax used.

値（「realm」ヘッダーを除く）が1つ以上の非ASCII文字を含む場合、そのパラメーターは[RFC5987]のセクション3.2で「ext-parameter」として定義されている構文を使用して送信するべきです（SHOULD）。 このようなパラメーターは、charsetの値が「UTF-8」でなければなりません（MUST）。 また、languageの値は常に省略しなければなりません（MUST）（空の値にします）。 使用する構文にかかわらず、同じパラメーターを2回以上送信してはなりません（MUST NOT）。

For example, a parameter "user" with the value "Renee of France" SHOULD be sent as < user="Renee of France" >. If the value is "Ren<e acute>e of France", it SHOULD be sent as < user*=UTF-8''Ren%C3%89e%20of%20France > instead.

たとえば、値が「Renee of France」であるパラメーター「user」は、< user="Renee of France" >として送信するべきです（SHOULD）。 値が「Ren<e acute>e of France」である場合は、代わりに< user*=UTF-8''Ren%C3%89e%20of%20France >として送信するべきです（SHOULD）。

[RFC7235] requires that the "realm" parameter be in its plain form (not as an extended "realm*" parameter), so the syntax specified in RFC 5987 MUST NOT be used for this parameter.

[RFC7235]は、「realm」パラメーターが（拡張された「realm*」パラメーターとしてではなく）通常の形式であることを要求しているので、このパラメーターにRFC 5987で規定された構文を使用してはなりません（MUST NOT）。

3.2. Values

3.2. 値

The parameter values contained in challenges or credentials MUST be parsed in strict conformance with HTTP semantics (especially the unquoting of string parameter values). In this protocol, those values are further categorized into the following value types: tokens (bare-token and extensive-token), string, integer, hex-fixed-number, and base64-fixed-number.

チャレンジまたはクレデンシャルに含まれるパラメーターの値は、HTTPのセマンティクス（特に文字列パラメーターの値の引用符の除去）に厳密に従ってパースしなければなりません（MUST）。 このプロトコルでは、これらの値をさらに次の値の型に分類します：トークン（bare-tokenとextensive-token）、文字列、整数、hex-fixed-number、base64-fixed-number。

For clarity, it is RECOMMENDED that implementations use the canonical representations specified in the following subsections for sending values. However, recipients MUST accept both quoted and unquoted representations interchangeably, as specified in HTTP.

明確にするために、実装は値を送信する際に、以下のサブセクションで規定する正規の表現を使用することが推奨されます（RECOMMENDED）。 ただし、受信者は、HTTPで規定されているとおり、引用符付きの表現と引用符なしの表現の両方を区別なく受け入れなければなりません（MUST）。

3.2.1. Tokens

3.2.1. トークン

For sustaining both security and extensibility at the same time, this protocol defines a stricter sub-syntax for the "token" to be used. Extensive-token values SHOULD use the following syntax (after the parsing of HTTP values):

セキュリティーと拡張性を同時に維持するために、このプロトコルでは、使用する「token」に対してより厳格な下位構文を定義します。 Extensive-tokenの値は、（HTTPの値のパース後に）次の構文を使用するべきです（SHOULD）。

The tokens (bare-token and extension-token) are case insensitive. Senders SHOULD send these in lower case, and receivers MUST accept both upper and lower cases. When tokens are used as (partial) inputs to any hash functions or other mathematical functions, they MUST always be used in lower case.

トークン（bare-tokenとextension-token）は大文字と小文字を区別しません。 送信者はこれらを小文字で送信するべきです（SHOULD）。 また、受信者は大文字と小文字の両方を受け入れなければなりません（MUST）。 トークンをハッシュ関数やその他の数学的な関数への（部分的な）入力として使用する場合は、常に小文字で使用しなければなりません（MUST）。

Extensive-tokens are used in this protocol where the set of acceptable tokens may include non-standard extensions. Any extension of this protocol MAY use either the bare-tokens allocated by IANA (see the procedure described in Section 16) or extension-tokens with the format "-<bare-token>.<domain-name>", where <domain-name> is a valid (sub)domain name on the Internet owned by the party who defines the extension.

Extensive-tokenは、このプロトコルの中で、受け入れ可能なトークンの集合に非標準の拡張が含まれる可能性がある箇所で使用します。 このプロトコルのどの拡張も、IANAが割り当てたbare-token（セクション16で説明する手順を参照）か、「-<bare-token>.<domain-name>」という形式のextension-tokenのいずれかを使用してもよいです（MAY）。 ここで、<domain-name>は、その拡張を定義する当事者が所有する、インターネット上の有効な（サブ）ドメイン名です。

Bare-tokens and extensive-tokens are also used for parameter names, in the unquoted form. Requirements for using the extension-token for the parameter names are the same as those described in the previous paragraph.

bare-tokenとextensive-tokenは、引用符なしの形式で、パラメーター名にも使用します。 パラメーター名にextension-tokenを使用する場合の要件は、前の段落で説明したものと同じです。

The canonical format for bare-tokens and extensive-tokens is the unquoted representation.

bare-tokenとextensive-tokenの正規の形式は、引用符なしの表現です。

3.2.2. Strings

3.2.2. 文字列

All character strings MUST be encoded to octet strings using UTF-8 encoding [RFC3629] for the Unicode character set [Unicode]. Such strings MUST NOT contain any leading Byte Order Marks (BOMs) (also known as ZERO WIDTH NO-BREAK SPACE, U+FEFF, or EF BB BF). It is RECOMMENDED that both peers reject any invalid UTF-8 sequences that might cause decoding ambiguities (e.g., containing <"> in the second or subsequent bytes of the UTF-8 encoded characters).

すべての文字列は、Unicode文字集合[Unicode]に対するUTF-8エンコーディング[RFC3629]を使用してオクテット文字列にエンコードしなければなりません（MUST）。 このような文字列は、先頭にバイト順マーク（BOM）（ZERO WIDTH NO-BREAK SPACE、U+FEFF、またはEF BB BFとも呼ばれる）を含んではなりません（MUST NOT）。 両方のピアは、デコードの曖昧さを引き起こす可能性がある不正なUTF-8シーケンス（たとえば、UTF-8でエンコードされた文字の2バイト目以降に<">を含むもの）を拒否することが推奨されます（RECOMMENDED）。

If strings represent a domain name or URI that contains non-ASCII characters, the host parts SHOULD be encoded as they (the parts) are used in the HTTP protocol layer (e.g., in a Host: header); per current standards, the A-label as defined in [RFC5890] will be used. Lowercase ASCII characters SHOULD be used.

文字列が非ASCII文字を含むドメイン名またはURIを表す場合、ホスト部分は、その部分がHTTPプロトコル層で使用されるとおりに（たとえばHost:ヘッダー内のように）エンコードするべきです（SHOULD）。 現在の標準では、[RFC5890]で定義されているA-labelが使用されます。 小文字のASCII文字を使用するべきです（SHOULD）。

The canonical format for strings is quoted-string (as it may contain equals signs ("="), plus signs ("+"), and slashes ("/")), unless the parameter containing the string value will use extended syntax as defined in [RFC5987]. (Per [RFC5987], an extended parameter will have an unquoted encoded value.)

文字列の正規の形式はquoted-stringです（等号（"="）、プラス記号（"+"）、スラッシュ（"/"）を含む可能性があるため）。 ただし、文字列の値を含むパラメーターが[RFC5987]で定義されている拡張構文を使用する場合は除きます。 （[RFC5987]によれば、拡張パラメーターは引用符なしのエンコードされた値を持ちます。）

3.2.3. Numbers

3.2.3. 数値

The following syntax definitions provide a syntax for numeric values:

次の構文定義は、数値の構文を示します。

The syntax definition of the integers only allows representations that do not contain leading zeros.

整数の構文定義では、先頭にゼロを含まない表現だけが許されます。

A number represented as a hex-fixed-number MUST include an even number of hexadecimal digits (i.e., multiples of eight bits). Those values are case insensitive and SHOULD be sent in lower case. When these values are generated from any cryptographic values, they MUST have their "natural length"; if they are generated from a hash function, their lengths correspond to the hash size; if they represent elements of a mathematical set (or group), their lengths SHALL be the shortest lengths that represent all the elements in the set. For example, the results of the SHA-256 hash function will be represented by 64 digits, and any elements in a 2048-bit prime field (modulo a 2048-bit integer) will be represented by 512 digits, regardless of how many zeros appear in front of such representations. Session identifiers and other non-cryptographically generated values are represented in any (even) length determined by the side that generates it first, and the same length MUST be used in all communications by both peers.

hex-fixed-numberとして表現される数値は、偶数個の16進数字（つまり8ビットの倍数）を含まなければなりません（MUST）。 これらの値は大文字と小文字を区別せず、小文字で送信するべきです（SHOULD）。 これらの値が何らかの暗号学的な値から生成される場合、その値は「自然な長さ」を持たなければなりません（MUST）。 ハッシュ関数から生成される場合、その長さはハッシュのサイズに対応します。 数学的な集合（または群）の要素を表す場合、その長さは、集合のすべての要素を表現できる最短の長さとすることになります（SHALL）。 たとえば、SHA-256ハッシュ関数の結果は64桁で表され、2048ビットの素体（2048ビットの整数を法とする）の要素は、その表現の前にいくつゼロが現れるかにかかわらず、512桁で表されます。 セッション識別子やその他の暗号学的に生成されたものではない値は、最初にそれを生成した側が決める任意の（偶数の）長さで表され、両方のピアはすべての通信で同じ長さを使用しなければなりません（MUST）。

The numbers represented as base64-fixed-number SHALL be generated as follows: first, the number is converted to a big-endian radix-256 binary representation as an octet string. The length of the representation is determined in the same way as the technique mentioned above. Then, the string is encoded using base64 encoding (described in Section 4 of [RFC4648]) without any spaces and newlines. Implementations decoding base64-fixed-number SHOULD reject any input data with invalid characters, excess or insufficient padding, or non-canonical pad bits (see Sections 3.1 through 3.5 of [RFC4648]).

base64-fixed-numberとして表現される数値は、次のように生成することになります（SHALL）。 まず、数値をオクテット文字列としてビッグエンディアンの256進のバイナリー表現に変換します。 表現の長さは、上で述べた手法と同じ方法で決定します。 次に、その文字列を、空白や改行を一切入れずに、base64エンコーディング（[RFC4648]のセクション4で説明されているもの）を使用してエンコードします。 base64-fixed-numberをデコードする実装は、不正な文字、過剰または不足したパディング、または正規でないパッドビットを含む入力データを拒否するべきです（SHOULD）（[RFC4648]のセクション3.1から3.5を参照）。

The canonical format for integer and hex-fixed-number is unquoted tokens, and the canonical format for base64-fixed-number is quoted-string.

integerとhex-fixed-numberの正規の形式は引用符なしのトークンであり、base64-fixed-numberの正規の形式はquoted-stringです。

4. メッセージ

In this section, we define the six kinds of messages in the authentication protocol, along with the formats and requirements of the headers for each type of message.

このセクションでは、認証プロトコルの6種類のメッセージを、各種類のメッセージのヘッダーの形式と要件とともに定義します。

To determine under what circumstances each message is expected to be sent, see Sections 10 and 11.

各メッセージがどのような状況で送信されると期待されるかについては、セクション10とセクション11を参照してください。

In the descriptions below, the types of allowable values for each header parameter are shown in parentheses after each parameter name. The "algorithm-determined" type means that the acceptable value for the parameter is one of the types defined in Section 3 and is determined by the value of the "algorithm" parameter. The parameters marked "mandatory" SHALL be contained in the message. The parameters marked "non-mandatory" MAY be either contained in the message or omitted from it. Each parameter SHALL appear in each header exactly once at most.

以下の説明では、各ヘッダーパラメーターで許される値の型を、各パラメーター名の後の括弧内に示します。 「algorithm-determined」型は、そのパラメーターで受け入れ可能な値が、セクション3で定義された型のいずれかであり、「algorithm」パラメーターの値によって決まることを意味します。 「mandatory（必須）」と記されたパラメーターは、メッセージに含まれるものとすることになります（SHALL）。 「non-mandatory（必須でない）」と記されたパラメーターは、メッセージに含めても省略してもよいです（MAY）。 各パラメーターは、各ヘッダーに多くとも1回だけ現れるものとすることになります（SHALL）。

All credentials and challenges MAY contain any parameters not explicitly specified in the following sections. Recipients that do not understand such parameters MUST silently ignore them. However, all credentials and challenges MUST meet the following criteria:

すべてのクレデンシャルとチャレンジは、以下のセクションで明示的に規定されていない任意のパラメーターを含んでもよいです（MAY）。 そのようなパラメーターを理解しない受信者は、それらを黙って無視しなければなりません（MUST）。 ただし、すべてのクレデンシャルとチャレンジは、次の基準を満たさなければなりません（MUST）。

  • For responses, the parameters "reason", any "ks#" (where "#" stands for any decimal integer), and "vks" are mutually exclusive; any challenges MUST NOT contain two or more parameters among them. They MUST NOT contain any "kc#" or "vkc" parameters.

  • For requests, the parameters "kc#" (where "#" stands for any decimal integer) and "vkc" are mutually exclusive; any challenges MUST NOT contain two or more parameters among them. They MUST NOT contain any "ks#" or "vks" parameters.

  • レスポンスでは、パラメーター「reason」、任意の「ks#」（「#」は任意の10進整数を表します）、「vks」は互いに排他的です。 どのチャレンジも、これらのうち2つ以上のパラメーターを含んではなりません（MUST NOT）。 チャレンジは「kc#」パラメーターや「vkc」パラメーターを含んではなりません（MUST NOT）。

  • リクエストでは、パラメーター「kc#」（「#」は任意の10進整数を表します）と「vkc」は互いに排他的です。 どのチャレンジも、これらのうち2つ以上のパラメーターを含んではなりません（MUST NOT）。 これらは「ks#」パラメーターや「vks」パラメーターを含んではなりません（MUST NOT）。

Every message defined in this section contains a "version" field to detect any future revisions of the protocol that are incompatible. Implementations of the protocol described in this specification MUST always send a token "1" to represent the version number. Recipients MUST reject messages that contain any other value for the version, unless another specification defines specific behavior for that version.

このセクションで定義するすべてのメッセージは、将来の互換性のないプロトコルの改訂を検出するための「version」フィールドを含みます。 この仕様で説明するプロトコルの実装は、バージョン番号を表すために常にトークン「1」を送信しなければなりません（MUST）。 受信者は、別の仕様がそのバージョンに対する特定の動作を定義していない限り、バージョンに他の値を含むメッセージを拒否しなければなりません（MUST）。

4.1. 401-INIT and 401-STALE

4.1. 401-INITと401-STALE

Every 401-INIT or 401-STALE message SHALL be a valid HTTP 401 (Unauthorized) status message (or some other 4xx status message, if appropriate) containing one and only one (hereafter not explicitly noted) WWW-Authenticate header containing a "reason" parameter in the challenge. The challenge SHALL contain all of the parameters marked "mandatory" below and MAY contain those marked "non-mandatory".

すべての401-INITメッセージまたは401-STALEメッセージは、チャレンジ内に「reason」パラメーターを含むWWW-Authenticateヘッダーをただ1つだけ（以下では明記しません）含む、有効なHTTPの401（Unauthorized）ステータスメッセージ（または適切であれば他の4xxステータスメッセージ）とすることになります（SHALL）。 チャレンジは、以下で「mandatory」と記されたパラメーターをすべて含むものとすることになります（SHALL）。 また、「non-mandatory」と記されたパラメーターを含んでもよいです（MAY）。

version:

(mandatory extensive-token) should be the token "1".

algorithm:

(mandatory extensive-token) specifies the authentication algorithm to be used. The value MUST be one of the tokens specified in [RFC8121] or another supplemental specification.

validation:

(mandatory extensive-token) specifies the method of host validation. The value MUST be one of the tokens described in Section 7 or the tokens specified in another supplemental specification.

auth-scope:

(non-mandatory string) specifies the authentication scope, i.e., the set of hosts for which the authentication credentials are valid. It MUST be one of the strings described in Section 5. If the value is omitted, it is assumed to be the "single-server type" domain as described in Section 5.

realm:

(mandatory string) is a string representing the name of the authentication realm inside the authentication scope. As specified in [RFC7235], this value MUST always be sent in the quoted-string form, and an encoding as specified in [RFC5987] MUST NOT be used.

The realm value sent from the server SHOULD be an ASCII string. Clients MAY treat any non-ASCII value received in this field as a binary blob, an NFC-normalized UTF-8 string ("NFC" stands for "Normalization Form C"), or an error.

reason:

(mandatory extensive-token) SHALL be an extensive-token that describes the possible reason for the failed authentication or authorization. Both servers and clients SHALL understand and support the following three tokens:

  • initial: Authentication was not attempted because there was no Authorization header in the corresponding request.

  • stale-session: The provided sid in the request was either unknown to the server or expired in the server.

  • auth-failed: The authentication trial failed for some reason, possibly because of a bad authentication credential.

Implementations MAY support the following tokens or any extensive-tokens defined outside of this specification. If clients receive any unknown tokens, they SHOULD treat them as if they were "auth-failed" or "initial".

  • reauth-needed: The server-side application requires a new authentication trial, regardless of the current status.

  • invalid-parameters: The server did not attempt authentication because some parameters were not acceptable.

  • internal-error: The server did not attempt authentication because there are some problems on the server side.

  • user-unknown: This is a special case of auth-failed; it suggests that the provided username is invalid. Due to security implications, the use of this parameter is NOT RECOMMENDED, except for special-purpose applications where it would make sense to do so.

  • invalid-credential: This is another special case of auth-failed; it suggests that the provided username was valid but authentication still failed. For security reasons, the use of this parameter is NOT RECOMMENDED.

  • authz-failed: Authentication was successful, but access to the specified resource is not authorized to the specific authenticated user. (It might be used along with either a 401 (Unauthorized) or 403 (Forbidden) status code to indicate that the authentication result is one of the existing reasons for the failed authorization.)

It is RECOMMENDED that the reason for failure be recorded to some type of diagnostic log, shown to the client user immediately, or both. It will be helpful to find out later whether the reason for the failure is technical or caused by user error.

version:

（必須、extensive-token）トークン「1」であるべきです。

algorithm:

（必須、extensive-token）使用する認証アルゴリズムを指定します。 値は、[RFC8121]または別の補足仕様で規定されたトークンのいずれかでなければなりません（MUST）。

validation:

（必須、extensive-token）ホスト検証の方式を指定します。 値は、セクション7で説明するトークン、または別の補足仕様で規定されたトークンのいずれかでなければなりません（MUST）。

auth-scope:

（必須でない、string）認証スコープ、つまり認証クレデンシャルが有効なホストの集合を指定します。 これはセクション5で説明する文字列のいずれかでなければなりません（MUST）。 値が省略された場合は、セクション5で説明する「単一サーバー型」のドメインであるとみなします。

realm:

（必須、string）認証スコープ内の認証レルムの名前を表す文字列です。 [RFC7235]で規定されているとおり、この値は常にquoted-stringの形式で送信しなければなりません（MUST）。 また、[RFC5987]で規定されているエンコーディングを使用してはなりません（MUST NOT）。

サーバーから送信されるレルムの値は、ASCII文字列であるべきです（SHOULD）。 クライアントは、このフィールドで受信した非ASCIIの値を、バイナリーの塊、NFC正規化されたUTF-8文字列（「NFC」は「Normalization Form C」を表します）、またはエラーのいずれかとして扱ってもよいです（MAY）。

reason:

（必須、extensive-token）認証または認可が失敗した考えられる理由を説明するextensive-tokenとすることになります（SHALL）。 サーバーとクライアントの両方が、次の3つのトークンを理解してサポートするものとすることになります（SHALL）。

  • initial：対応するリクエストにAuthorizationヘッダーがなかったため、認証は試みられませんでした。

  • stale-session：リクエストで提示されたsidが、サーバーにとって未知であるか、サーバーで期限切れになっていました。

  • auth-failed：何らかの理由で、おそらく不正な認証クレデンシャルのために、認証の試行が失敗しました。

実装は、次のトークン、またはこの仕様の外部で定義された任意のextensive-tokenをサポートしてもよいです（MAY）。 クライアントは、未知のトークンを受信した場合、それを「auth-failed」または「initial」であるかのように扱うべきです（SHOULD）。

  • reauth-needed：サーバー側のアプリケーションが、現在の状態にかかわらず、新たな認証の試行を要求しています。

  • invalid-parameters：いくつかのパラメーターが受け入れられなかったため、サーバーは認証を試みませんでした。

  • internal-error：サーバー側に何らかの問題があるため、サーバーは認証を試みませんでした。

  • user-unknown：これはauth-failedの特別な場合であり、提示されたユーザー名が無効であることを示唆します。 セキュリティー上の影響があるため、そうすることが意味を持つ特別な目的のアプリケーションを除き、このパラメーターを使用することは推奨されません（NOT RECOMMENDED）。

  • invalid-credential：これはauth-failedのもう1つの特別な場合であり、提示されたユーザー名は有効だったものの、それでも認証が失敗したことを示唆します。 セキュリティー上の理由から、このパラメーターを使用することは推奨されません（NOT RECOMMENDED）。

  • authz-failed：認証は成功しましたが、指定されたリソースへのアクセスが、その特定の認証済みユーザーに対して認可されていません。 （これは、認証結果が認可失敗の理由の1つであることを示すために、401（Unauthorized）または403（Forbidden）ステータスコードのいずれかとともに使用されることがあります。）

失敗の理由は、何らかの種類の診断ログに記録するか、クライアントユーザーにすぐに表示するか、またはその両方を行うことが推奨されます（RECOMMENDED）。 これは、失敗の理由が技術的なものか、ユーザーの誤りによるものかを後で調べるのに役立ちます。

The algorithm specified in this header will determine the types (among those defined in Section 3) and the values for K_c1, K_s1, VK_c, and VK_s.

このヘッダーで指定されたアルゴリズムによって、K_c1、K_s1、VK_c、VK_sの型（セクション3で定義されたもののうちどれか）と値が決まります。

Among these messages, any messages with the "reason" parameter value "stale-session" will be called "401-STALE" messages hereafter, because these messages have a special meaning in the protocol flow. Messages with any other "reason" parameters will be called "401-INIT" messages.

これらのメッセージのうち、「reason」パラメーターの値が「stale-session」であるメッセージは、プロトコルフローの中で特別な意味を持つため、以下では「401-STALE」メッセージと呼びます。 それ以外の「reason」パラメーターを持つメッセージは「401-INIT」メッセージと呼びます。

4.2. req-KEX-C1

4.2. req-KEX-C1

Every req-KEX-C1 message SHALL be a valid HTTP request message containing an Authorization header with a credential containing a "kc1" parameter.

すべてのreq-KEX-C1メッセージは、「kc1」パラメーターを含むクレデンシャルを持つAuthorizationヘッダーを含む、有効なHTTPリクエストメッセージとすることになります（SHALL）。

The credential SHALL contain the parameters with the following names:

クレデンシャルは、次の名前のパラメーターを含むものとすることになります（SHALL）。

version:

(mandatory, extensive-token) should be the token "1".

algorithm, validation, auth-scope, realm:

MUST be the same values as those received from the server.

user:

(mandatory, string) is the UTF-8 encoded name of the user. The string SHOULD be prepared according to the method presented in Section 9.

kc1:

(mandatory, algorithm-determined) is the client-side key exchange value K_c1, which is specified by the algorithm that is used.

version:

（必須、extensive-token）トークン「1」であるべきです。

algorithm, validation, auth-scope, realm:

サーバーから受信したものと同じ値でなければなりません（MUST）。

user:

（必須、string）ユーザーの名前をUTF-8でエンコードしたものです。 この文字列は、セクション9で示す方法に従って準備するべきです（SHOULD）。

kc1:

（必須、algorithm-determined）クライアント側の鍵交換値K_c1であり、使用するアルゴリズムによって規定されます。

4.3. 401-KEX-S1

4.3. 401-KEX-S1

Every 401-KEX-S1 message SHALL be a valid HTTP 401 (Unauthorized) status response message containing a WWW-Authenticate header with a challenge containing a "ks1" parameter.

すべての401-KEX-S1メッセージは、「ks1」パラメーターを含むチャレンジを持つWWW-Authenticateヘッダーを含む、有効なHTTPの401（Unauthorized）ステータスのレスポンスメッセージとすることになります（SHALL）。

The challenge SHALL contain the parameters with the following names:

チャレンジは、次の名前のパラメーターを含むものとすることになります（SHALL）。

version:

(mandatory, extensive-token) should be the token "1".

algorithm, validation, auth-scope, realm:

MUST be the same values as those received from the client.

sid:

(mandatory, hex-fixed-number) MUST be a session identifier, which is a random integer. The sid SHOULD have uniqueness of at least 80 bits or the square of the maximum estimated transactions concurrently available in the session table, whichever is larger. See Section 6 for more details.

ks1:

(mandatory, algorithm-determined) is the server-side key exchange value K_s1, which is specified by the algorithm.

nc-max:

(mandatory, integer) is the maximum value of nonce numbers that the server accepts.

nc-window:

(mandatory, integer) is the number of available nonce number slots that the server will accept. It is RECOMMENDED that the value of the "nc-window" parameter be 128 or more.

time:

(mandatory, integer) represents the suggested time (in seconds) that the client can reuse the session represented by the sid. It is RECOMMENDED that the time be set to at least 60 (seconds). However, the server is not required to guarantee that the session represented by the sid will be available (e.g., alive, usable) for the time specified in this parameter.

path:

(non-mandatory, string) specifies to which path in the URI space the same authentication is expected to be applied. The value is a space-separated list of URIs, in the same format as that specified in the "domain" parameter [RFC7616] for Digest authentications. All path elements contained in the "path" parameter MUST be inside the specified auth-scope; if not, clients SHOULD ignore such elements. For better performance, it is important that clients recognize and use this parameter.

version:

（必須、extensive-token）トークン「1」であるべきです。

algorithm, validation, auth-scope, realm:

クライアントから受信したものと同じ値でなければなりません（MUST）。

sid:

（必須、hex-fixed-number）ランダムな整数であるセッション識別子でなければなりません（MUST）。 sidは、少なくとも80ビット、またはセッションテーブルで同時に利用可能なトランザクションの推定最大数の2乗のいずれか大きいほうの一意性を持つべきです（SHOULD）。 詳細については、セクション6を参照してください。

ks1:

（必須、algorithm-determined）サーバー側の鍵交換値K_s1であり、アルゴリズムによって規定されます。

nc-max:

（必須、integer）サーバーが受け入れるノンス番号の最大値です。

nc-window:

（必須、integer）サーバーが受け入れる、利用可能なノンス番号のスロットの数です。 「nc-window」パラメーターの値は128以上であることが推奨されます（RECOMMENDED）。

time:

（必須、integer）sidが表すセッションをクライアントが再利用できる、推奨される時間（秒単位）を表します。 この時間は少なくとも60（秒）に設定することが推奨されます（RECOMMENDED）。 ただし、サーバーは、sidが表すセッションがこのパラメーターで指定された時間のあいだ利用可能である（たとえば、生存していて使用可能である）ことを保証する必要はありません。

path:

（必須でない、string）URI空間内のどのパスに同じ認証が適用されると期待されるかを指定します。 値は、Digest認証の「domain」パラメーター[RFC7616]で規定されているものと同じ形式の、空白で区切られたURIのリストです。 「path」パラメーターに含まれるすべてのパス要素は、指定されたauth-scopeの内側になければなりません（MUST）。 そうでない場合、クライアントはそのような要素を無視するべきです（SHOULD）。 パフォーマンスを向上させるために、クライアントがこのパラメーターを認識して使用することが重要です。

4.4. req-VFY-C

4.4. req-VFY-C

Every req-VFY-C message SHALL be a valid HTTP request message containing an Authorization header with a credential containing a "vkc" parameter.

すべてのreq-VFY-Cメッセージは、「vkc」パラメーターを含むクレデンシャルを持つAuthorizationヘッダーを含む、有効なHTTPリクエストメッセージとすることになります（SHALL）。

The parameters contained in the header are as follows:

ヘッダーに含まれるパラメーターは次のとおりです。

version:

(mandatory, extensive-token) should be the token "1".

algorithm, validation, auth-scope, realm:

MUST be the same values as those received from the server for the session.

sid:

(mandatory, hex-fixed-number) MUST be one of the sid values that was received from the server for the same authentication realm.

nc:

(mandatory, integer) is a nonce request number that is unique among the requests sharing the same sid. The values of the nonce numbers SHOULD satisfy the properties outlined in Section 6.

vkc:

(mandatory, algorithm-determined) is the client-side authentication verification value VK_c, which is specified by the algorithm.

version:

（必須、extensive-token）トークン「1」であるべきです。

algorithm, validation, auth-scope, realm:

そのセッションについてサーバーから受信したものと同じ値でなければなりません（MUST）。

sid:

（必須、hex-fixed-number）同じ認証レルムについてサーバーから受信したsidの値のいずれかでなければなりません（MUST）。

nc:

（必須、integer）同じsidを共有するリクエストの間で一意なノンスリクエスト番号です。 ノンス番号の値は、セクション6で概説する性質を満たすべきです（SHOULD）。

vkc:

（必須、algorithm-determined）クライアント側の認証検証値VK_cであり、アルゴリズムによって規定されます。

4.5. 200-VFY-S

4.5. 200-VFY-S

Every 200-VFY-S message SHALL be a valid HTTP message that does not have a 401 (Unauthorized) status code and SHALL contain an Authentication-Info header with a "vks" parameter.

すべての200-VFY-Sメッセージは、401（Unauthorized）ステータスコードを持たない有効なHTTPメッセージとすることになります（SHALL）。 また、「vks」パラメーターを持つAuthentication-Infoヘッダーを含むものとすることになります（SHALL）。

The parameters contained in the header are as follows:

ヘッダーに含まれるパラメーターは次のとおりです。

version:

(mandatory, extensive-token) should be the token "1".

sid:

(mandatory, hex-fixed-number) MUST be the value received from the client.

vks:

(mandatory, algorithm-determined) is the server-side authentication verification value VK_s, which is specified by the algorithm.

version:

（必須、extensive-token）トークン「1」であるべきです。

sid:

（必須、hex-fixed-number）クライアントから受信した値でなければなりません（MUST）。

vks:

（必須、algorithm-determined）サーバー側の認証検証値VK_sであり、アルゴリズムによって規定されます。

The header MUST be sent before the content body; it MUST NOT be sent in the trailer of a chunked-encoded response. If a "100 (Continue)" [RFC7231] response is sent from the server, the Authentication-Info header SHOULD be included in that response instead of the final response.

このヘッダーは、コンテンツのボディーより前に送信しなければなりません（MUST）。 チャンク形式でエンコードされたレスポンスのトレーラーで送信してはなりません（MUST NOT）。 サーバーから「100 (Continue)」[RFC7231]レスポンスが送信される場合、Authentication-Infoヘッダーは、最終レスポンスではなくそのレスポンスに含めるべきです（SHOULD）。

5. Authentication Realms

5. 認証レルム

In this protocol, an authentication realm is defined as a set of resources (URIs) for which the same set of usernames and passwords is valid. If the server requests authentication for an authentication realm for which the client is already authenticated, the client will automatically perform the authentication using the already-known credentials. However, for different authentication realms, clients MUST NOT automatically reuse usernames and passwords for another realm.

このプロトコルでは、認証レルムを、同じユーザー名とパスワードの組が有効であるリソース（URI）の集合として定義します。 クライアントがすでに認証済みである認証レルムについてサーバーが認証を要求した場合、クライアントはすでに知っているクレデンシャルを使用して自動的に認証を行います。 ただし、異なる認証レルムについては、クライアントはユーザー名とパスワードを別のレルムのために自動的に再利用してはなりません（MUST NOT）。

As is the case for the Basic and Digest access authentication protocols, the Mutual authentication protocol supports multiple, separate protection spaces to be set up inside each host. Furthermore, the protocol allows a single authentication realm to span several hosts within the same Internet domain.

BasicおよびDigestアクセス認証プロトコルの場合と同様に、Mutual認証プロトコルは、各ホストの内部に複数の別々の保護空間を設定することをサポートします。 さらに、このプロトコルでは、1つの認証レルムが同じインターネットドメイン内の複数のホストにまたがることができます。

Each authentication realm is defined and distinguished by the triple of an authentication algorithm, an authentication scope, and a "realm" parameter. However, it is NOT RECOMMENDED that server operators use the same pair of an authentication scope and a realm with different authentication algorithms.

各認証レルムは、認証アルゴリズム、認証スコープ、「realm」パラメーターの3つ組によって定義され、区別されます。 ただし、サーバー運用者が、認証スコープとレルムの同じ組を異なる認証アルゴリズムで使用することは推奨されません（NOT RECOMMENDED）。

The "realm" parameter is a string as defined in Section 4. Authentication scopes are described in the remainder of this section.

「realm」パラメーターは、セクション4で定義されている文字列です。 認証スコープについては、このセクションの残りの部分で説明します。

An authentication scope specifies the range of hosts spanned by the authentication realm. In this protocol, it MUST be one of the following kinds of strings:

認証スコープは、認証レルムがまたがるホストの範囲を指定します。 このプロトコルでは、認証スコープは次の種類の文字列のいずれかでなければなりません（MUST）。

  • Single-server type: A string in the format "<scheme>://<host>" or "<scheme>://<host>:<port>", where <scheme>, <host>, and <port> are the corresponding URI parts of the request URI. If the default port (i.e., 80 for HTTP and 443 for HTTPS) is used for the underlying HTTP communications, the port part MUST be omitted, regardless of whether it was present in the request URI. In all other cases, the port part MUST be present, and it MUST NOT contain leading zeros. Use this format when authentication is only valid for a specific protocol (such as HTTPS). This format is equivalent to the ASCII serialization of a Web origin, as presented in Section 6.2 of [RFC6454].

  • Single-host type: The "host" part of the requested URI. This is the default value. Authentication realms within this kind of authentication scope will span several protocols (e.g., HTTP and HTTPS) and ports but will not span different hosts.

  • Wildcard-domain type: A string in the format "*.<domain-postfix>", where <domain-postfix> is either the host part of the requested URI or any domain in which the requested host is included (this means that the specification "*.example.com" is valid for all of hosts "www.example.com", "web.example.com", "www.sales.example.com", and "example.com"). The domain-postfix sent by the servers MUST be equal to or included in a valid Internet domain assigned to a specific organization; if clients know, via some means such as a blacklist for HTTP cookies [RFC6265], that the specified domain is not to be assigned to any specific organization (e.g., "*.com" or "*.jp"), it is RECOMMENDED that clients reject the authentication request.

  • 単一サーバー型：「<scheme>://<host>」または「<scheme>://<host>:<port>」の形式の文字列です。 ここで、<scheme>、<host>、<port>は、リクエストURIの対応するURIの部分です。 下位のHTTP通信にデフォルトのポート（つまり、HTTPでは80、HTTPSでは443）を使用する場合、リクエストURIにポート部分があったかどうかにかかわらず、ポート部分は省略しなければなりません（MUST）。 それ以外のすべての場合、ポート部分は存在しなければなりません（MUST）。 また、ポート部分は先頭にゼロを含んではなりません（MUST NOT）。 認証が特定のプロトコル（HTTPSなど）に対してのみ有効である場合に、この形式を使用します。 この形式は、[RFC6454]のセクション6.2で示されているWebオリジンのASCIIシリアル化と同等です。

  • 単一ホスト型：リクエストされたURIの「host」部分です。 これがデフォルト値です。 この種類の認証スコープ内の認証レルムは、複数のプロトコル（たとえばHTTPとHTTPS）とポートにまたがりますが、異なるホストにはまたがりません。

  • ワイルドカードドメイン型：「*.<domain-postfix>」の形式の文字列です。 ここで、<domain-postfix>は、リクエストされたURIのホスト部分か、リクエストされたホストが含まれる任意のドメインのいずれかです（つまり、「*.example.com」という指定は、ホスト「www.example.com」、「web.example.com」、「www.sales.example.com」、「example.com」のすべてに対して有効です）。 サーバーが送信するdomain-postfixは、特定の組織に割り当てられた有効なインターネットドメインと等しいか、それに含まれるものでなければなりません（MUST）。 HTTPクッキーのブラックリスト[RFC6265]などの何らかの手段によって、指定されたドメインが特定の組織に割り当てられるものではないこと（たとえば「*.com」や「*.jp」）をクライアントが知っている場合、クライアントは認証要求を拒否することが推奨されます（RECOMMENDED）。

In the above specifications, every "scheme", "host", and "domain" MUST be in lower case, and any internationalized domain names beyond the ASCII character set SHALL be represented in the way they are sent in the underlying HTTP protocol, represented in lowercase characters, i.e., these domain names SHALL be in the form of LDH ("letters, digits, hyphen") labels as defined in the Internationalized Domain Names for Applications (IDNA) specification [RFC5890]. A "port" MUST be given in shortest unsigned decimal number notation. Not obeying these requirements will cause valid authentication attempts to fail.

上記の指定において、すべての「scheme」、「host」、「domain」は小文字でなければなりません（MUST）。 また、ASCII文字集合を超える国際化ドメイン名は、下位のHTTPプロトコルで送信されるとおりの方法で、小文字で表現するものとすることになります（SHALL）。 つまり、これらのドメイン名は、IDNA（Internationalized Domain Names for Applications）仕様[RFC5890]で定義されているLDH（「letters, digits, hyphen」）ラベルの形式とすることになります（SHALL）。 「port」は、最短の符号なし10進数表記で与えなければなりません（MUST）。 これらの要件に従わないと、有効な認証の試行が失敗します。

5.1. Resolving Ambiguities

5.1. 曖昧さの解決

In the above definitions of authentication scopes, several scopes may overlap each other. If a client has already been authenticated to several realms applicable to the same server, the client may have multiple lists of the "path" parameters received with the "401-KEX-S1" message (see Section 4). If these path lists have any overlap, a single URI may belong to multiple possible candidate realms to which the client can be authenticated. In such cases, clients face an ambiguous choice regarding which credentials to send for a new request (see Steps 3 and 4 of the decision procedure presented in Section 10).

上記の認証スコープの定義では、いくつかのスコープが互いに重なる可能性があります。 クライアントが同じサーバーに適用できる複数のレルムに対してすでに認証されている場合、クライアントは「401-KEX-S1」メッセージ（セクション4を参照）とともに受信した「path」パラメーターのリストを複数持っている可能性があります。 これらのパスのリストに重なりがあると、1つのURIが、クライアントが認証され得る複数の候補レルムに属する可能性があります。 このような場合、クライアントは、新しいリクエストに対してどのクレデンシャルを送信するかについて曖昧な選択に直面します（セクション10で示す決定手順のステップ3とステップ4を参照）。

In such cases, a client MAY freely send requests that belong to any of these candidate realms, or it MAY simply send an unauthenticated request and see for which realm the server requests an authentication. It is RECOMMENDED that server operators provide properly configured "path" parameters (more precisely, disjoint path sets for each realm) for clients so that such ambiguities will not occur.

このような場合、クライアントは、これらの候補レルムのどれに属するリクエストを自由に送信してもよいです（MAY）。 あるいは、単に認証なしのリクエストを送信し、サーバーがどのレルムについて認証を要求するかを確かめてもよいです（MAY）。 サーバー運用者は、このような曖昧さが生じないように、適切に設定された「path」パラメーター（より正確には、レルムごとに互いに素なパスの集合）をクライアントに提供することが推奨されます（RECOMMENDED）。

The following procedure is one possible tactic for resolving ambiguities in such cases:

次の手順は、このような場合の曖昧さを解決するための1つの方策として考えられるものです。

  • If the client has previously sent a request to the same URI and it remembers the authentication realm requested by the 401-INIT message at that time, use that realm.

  • In other cases, use one of the authentication realms representing the most-specific authentication scopes. The list of possible domain specifications shown above is given from most specific to least specific.

    If there are several choices with different wildcard-domain specifications, the one that has the longest domain-postfix has priority over those with shorter domain-postfixes.

  • If there are realms with the same authentication scope, there is no defined priority; the client MAY choose any one of the possible choices.

  • クライアントが以前に同じURIにリクエストを送信しており、そのときに401-INITメッセージによって要求された認証レルムを覚えている場合は、そのレルムを使用します。

  • それ以外の場合は、最も具体的な認証スコープを表す認証レルムのいずれかを使用します。 上に示した可能なドメインの指定のリストは、最も具体的なものから最も具体的でないものの順に並んでいます。

    ワイルドカードドメインの指定が異なる複数の選択肢がある場合は、最も長いdomain-postfixを持つものが、より短いdomain-postfixを持つものよりも優先されます。

  • 同じ認証スコープを持つレルムがある場合、優先順位は定義されていません。 クライアントは、可能な選択肢のうちどれを選んでもよいです（MAY）。

6. Session Management

6. セッション管理

In the Mutual authentication protocol, a session represented by an sid is set up using four messages (first request, 401-INIT, req-KEX-C1, and 401-KEX-S1), after which a session secret (z) associated with the session is established. After mutually establishing a session secret, this session, along with the secret, can be used for one or more requests for resources protected by the same realm on the same server. Note that session management is only an inside detail of the protocol and usually not visible to normal users. If a session expires, the client and server SHOULD automatically re-establish another session without informing the user.

Mutual認証プロトコルでは、sidによって表されるセッションは、4つのメッセージ（最初のリクエスト、401-INIT、req-KEX-C1、401-KEX-S1）を使用して設定され、その後、そのセッションに関連付けられたセッション秘密（z）が確立されます。 相互にセッション秘密を確立した後は、このセッションを秘密とともに、同じサーバー上の同じレルムで保護されたリソースに対する1つ以上のリクエストに使用できます。 セッション管理はプロトコルの内部的な詳細にすぎず、通常は一般のユーザーには見えないことに注意してください。 セッションの有効期限が切れた場合、クライアントとサーバーは、ユーザーに知らせることなく自動的に別のセッションを再確立するべきです（SHOULD）。

Sessions and session identifiers are local to each server (defined by scheme, host, and port), even if an authentication scope covers multiple servers; clients MUST establish separate sessions for each port of a host to be accessed. Furthermore, sessions and identifiers are also local to each authentication realm, even if they are provided by the same server. The same session identifiers provided either from different servers or for different realms MUST be treated as being independent of each other.

認証スコープが複数のサーバーにまたがる場合でも、セッションとセッション識別子は各サーバー（スキーム、ホスト、ポートによって定義されます）にローカルです。 クライアントは、アクセスするホストのポートごとに別々のセッションを確立しなければなりません（MUST）。 さらに、セッションと識別子は、同じサーバーによって提供される場合でも、各認証レルムにローカルです。 異なるサーバーから提供された、または異なるレルムのために提供された同じセッション識別子は、互いに独立したものとして扱わなければなりません（MUST）。

The server SHOULD accept at least one req-VFY-C request for each session if the request reaches the server in a time window specified by the "timeout" parameter in the 401-KEX-S1 message and if there are no emergent reasons (such as flooding attacks) to forget the session. After that, the server MAY discard any session at any time and MAY send 401-STALE messages for any further req-VFY-C requests received for that session.

サーバーは、401-KEX-S1メッセージの「timeout」パラメーターで指定された時間枠内にリクエストがサーバーに到達し、かつセッションを忘れる緊急の理由（フラッディング攻撃など）がない場合は、各セッションについて少なくとも1つのreq-VFY-Cリクエストを受け入れるべきです（SHOULD）。 その後、サーバーはいつでも任意のセッションを破棄してもよいです（MAY）。 また、そのセッションについて受信したそれ以降のreq-VFY-Cリクエストに対して401-STALEメッセージを送信してもよいです（MAY）。

The client MAY send two or more requests using a single session specified by the sid. However, for all such requests, each value of the nonce number (in the "nc" parameter) MUST satisfy the following conditions:

クライアントは、sidで指定された1つのセッションを使用して、2つ以上のリクエストを送信してもよいです（MAY）。 ただし、そのようなすべてのリクエストについて、ノンス番号（「nc」パラメーター内）の各値は、次の条件を満たさなければなりません（MUST）。

  • It is a natural number.

  • The same nonce number was not sent within the same session.

  • It is not larger than the nc-max value that was sent from the server in the session represented by the sid.

  • It is larger than (largest-nc - nc-window), where largest-nc is the largest value of nc that was previously sent in the session and nc-window is the value of the "nc-window" parameter that was received from the server for the session.

  • 自然数であること。

  • 同じセッション内で同じノンス番号が送信されていないこと。

  • sidが表すセッションでサーバーから送信されたnc-maxの値以下であること。

  • (largest-nc - nc-window)を超えること。 ここで、largest-ncはそのセッションで以前に送信されたncの最大値であり、nc-windowはそのセッションについてサーバーから受信した「nc-window」パラメーターの値です。

The last condition allows servers to reject any nonce numbers that are "significantly" smaller than the "current" value (defined by the value of nc-window) of the nonce number used in the session involved. In other words, servers MAY treat such nonce numbers as "already received". This restriction enables servers to implement duplicate-nonce detection in a constant amount of memory for each session.

最後の条件により、サーバーは、関係するセッションで使用されているノンス番号の「現在の」値よりも（nc-windowの値によって定義される意味で）「著しく」小さいノンス番号を拒否できます。 言い換えれば、サーバーはそのようなノンス番号を「受信済み」として扱ってもよいです（MAY）。 この制約により、サーバーは、セッションごとに一定量のメモリーでノンスの重複検出を実装できます。

Servers MUST check for duplication of the received nonce numbers, and if any duplication is detected, the server MUST discard the session and respond with a 401-STALE message, as outlined in Section 11. The server MAY also reject other invalid nonce numbers (such as those above the nc-max limit) by sending a 401-STALE message.

サーバーは、受信したノンス番号の重複を確認しなければなりません（MUST）。 重複が検出された場合、サーバーは、セクション11で概説するとおり、セッションを破棄して401-STALEメッセージで応答しなければなりません（MUST）。 サーバーは、その他の不正なノンス番号（nc-maxの上限を超えるものなど）も、401-STALEメッセージを送信することによって拒否してもよいです（MAY）。

For example, assume that the nc-window value of the current session is 128 and nc-max is 400, and that the client has already used the following nonce numbers: {1-120, 122, 124, 130-238, 255-360, 363-372}. The nonce number that can then be used for the next request is a number from the following set: {245-254, 361, 362, 373-400}. The values {0, 121, 123, 125-129, 239-244} MAY be rejected by the server because they are not above the current "window limit" (244 = 372 - 128).

たとえば、現在のセッションのnc-windowの値が128でnc-maxが400であり、クライアントがすでに次のノンス番号を使用しているとします：{1-120, 122, 124, 130-238, 255-360, 363-372}。 このとき、次のリクエストに使用できるノンス番号は、次の集合の数です：{245-254, 361, 362, 373-400}。 値{0, 121, 123, 125-129, 239-244}は、現在の「ウィンドウの下限」（244 = 372 - 128）を超えていないため、サーバーによって拒否される場合があります（MAY）。

Typically, clients can ensure the above property by using a monotonically increasing integer counter that counts from zero up to the value of nc-max.

典型的には、クライアントは、ゼロからnc-maxの値まで数える単調増加の整数カウンターを使用することによって、上記の性質を保証できます。

The values of the nonce numbers and any nonce-related values MUST always be treated as natural numbers within an infinite range. Implementations that use fixed-width integer representations, fixed-precision floating-point numbers, or similar representations SHOULD NOT reject any larger values that overflow such representative limits and MUST NOT silently truncate them using any modulus-like rounding operation (e.g., by mod 2^32). Instead, the whole protocol is carefully designed so that recipients MAY replace any such overflowing values (e.g., 2^80) with some reasonably large maximum representative integer (e.g., 2^31 - 1 or others).

ノンス番号の値とノンスに関連するすべての値は、常に無限の範囲内の自然数として扱わなければなりません（MUST）。 固定幅の整数表現、固定精度の浮動小数点数、または同様の表現を使用する実装は、そのような表現の上限を超えてオーバーフローするより大きな値を拒否するべきではありません（SHOULD NOT）。 また、剰余のような丸め操作（たとえばmod 2^32）を使用して、それらを黙って切り詰めてはなりません（MUST NOT）。 その代わりに、プロトコル全体が注意深く設計されているので、受信者はそのようなオーバーフローする値（たとえば2^80）を、何らかの適度に大きな表現可能な最大整数（たとえば2^31 - 1など）で置き換えてもよいです（MAY）。

7. Host Validation Methods

7. ホスト検証方式

The "validation method" specifies a method to "relate" (or "bind") the mutual authentication processed by this protocol with other authentications already performed in the underlying layers and to prevent man-in-the-middle attacks. It determines the value vh that is an input to the authentication protocols.

「検証方式」は、このプロトコルで処理される相互認証を、下位の層ですでに行われた他の認証と「関係付け」（または「結び付け」）、中間者攻撃を防ぐための方式を指定します。 検証方式は、認証プロトコルへの入力である値vhを決定します。

When HTTPS or another possible secure transport is used, this corresponds to the idea of "channel binding" as described in [RFC5929]. Even when HTTP is used, similar, but somewhat limited, "binding" is performed to prevent a malicious server from trying to authenticate itself to another server as a valid user by forwarding the received credentials.

HTTPSまたは他の安全なトランスポートが使用される場合、これは[RFC5929]で説明されている「チャネルバインディング」の考え方に相当します。 HTTPが使用される場合でも、悪意のあるサーバーが受信したクレデンシャルを転送することによって、有効なユーザーとして別のサーバーに対して自分自身を認証させようとするのを防ぐために、同様の、ただしやや限定的な「バインディング」が行われます。

The valid tokens for the "validation" parameter and corresponding values of vh are as follows:

「validation」パラメーターの有効なトークンと、それに対応するvhの値は次のとおりです。

host:

hostname validation. The value vh will be the ASCII string in the following format: "<scheme>://<host>:<port>", where <scheme>, <host>, and <port> are the URI components corresponding to the server-side resource currently being accessed. The scheme and host are in lower case, and the port is listed in shortest decimal notation. Even if the request URI does not have a port part, vh will include the default port number.

tls-server-end-point:

TLS endpoint (certificate) validation. The value vh will be the octet string of the hash value of the server's public key certificate used in the underlying TLS [RFC5246] connection, processed as specified in Section 4.1 of [RFC5929].

tls-unique:

TLS shared-key validation. The value vh will be the channel-binding material derived from the Finished messages, as defined in Section 3.1 of [RFC5929]. (Note: See Section 7.2 for some security-related notes regarding this validation method.)

host:

ホスト名の検証。 値vhは、「<scheme>://<host>:<port>」という形式のASCII文字列になります。 ここで、<scheme>、<host>、<port>は、現在アクセスしているサーバー側のリソースに対応するURIの構成要素です。 スキームとホストは小文字で、ポートは最短の10進表記で示します。 リクエストURIにポート部分がない場合でも、vhはデフォルトのポート番号を含みます。

tls-server-end-point:

TLSエンドポイント（証明書）の検証。 値vhは、下位のTLS[RFC5246]接続で使用されたサーバーの公開鍵証明書のハッシュ値を、[RFC5929]のセクション4.1で規定されているとおりに処理したオクテット文字列になります。

tls-unique:

TLS共有鍵の検証。 値vhは、[RFC5929]のセクション3.1で定義されている、Finishedメッセージから導出されたチャネルバインディングの素材になります。 （注：この検証方式に関するセキュリティー関連の注意事項については、セクション7.2を参照してください。）

If HTTP is used on a non-encrypted channel (TCP and the Stream Control Transmission Protocol (SCTP), for example), the validation type MUST be "host". If HTTP/TLS [RFC2818] (HTTPS) is used with a server certificate, the validation type MUST be "tls-server-end-point". If HTTP/TLS is used with an anonymous Diffie-Hellman key exchange, the validation type MUST be "tls-unique" (see the note below).

HTTPが暗号化されていないチャネル（たとえばTCPやストリーム制御伝送プロトコル（SCTP））上で使用される場合、検証の種類は「host」でなければなりません（MUST）。 HTTP/TLS[RFC2818]（HTTPS）がサーバー証明書とともに使用される場合、検証の種類は「tls-server-end-point」でなければなりません（MUST）。 HTTP/TLSが匿名のDiffie-Hellman鍵交換とともに使用される場合、検証の種類は「tls-unique」でなければなりません（MUST）（下記の注を参照）。

If the validation type "tls-server-end-point" is used, the server certificate provided in the TLS connection MUST be verified at least to make sure that the server actually owns the corresponding private key. (Note: This verification is automatic in some RSA-based key exchanges but is NOT automatic in Diffie-Hellman-based key exchanges with separate exchanges for server verification.)

検証の種類「tls-server-end-point」を使用する場合、TLS接続で提示されたサーバー証明書を、少なくともサーバーが対応する秘密鍵を実際に所有していることを確かめるように検証しなければなりません（MUST）。 （注：この検証は、RSAベースの鍵交換の一部では自動的に行われますが、サーバー検証のための交換が別に行われるDiffie-Hellmanベースの鍵交換では自動的には行われません。）

Clients MUST validate this parameter upon receipt of 401-INIT messages.

クライアントは、401-INITメッセージを受信した時点で、このパラメーターを検証しなければなりません（MUST）。

Note: The protocol defines two variants of validation on the TLS connections. The "tls-unique" method is technically more secure. However, there are some situations where "tls-server-end-point" is preferable:

注：このプロトコルは、TLS接続における検証の2つの変種を定義しています。 「tls-unique」方式のほうが技術的にはより安全です。 しかし、「tls-server-end-point」のほうが望ましい状況もいくつかあります。

  • When TLS accelerating proxies are used. In this case, it is difficult for the authenticating server to acquire the TLS key information that is used between the client and the proxy. This is not the case for client-side "tunneling" proxies using the HTTP CONNECT method.

  • When a black-box implementation of the TLS protocol is used on either peer.

  • TLSアクセラレーションプロキシーが使用される場合。 この場合、認証を行うサーバーが、クライアントとプロキシーの間で使用されるTLSの鍵情報を取得することは困難です。 HTTPのCONNECTメソッドを使用するクライアント側の「トンネリング」プロキシーの場合は、これは当てはまりません。

  • どちらかのピアでTLSプロトコルのブラックボックス実装が使用される場合。

7.1. Applicability Notes

7.1. 適用性に関する注意

When the client is a Web browser with any scripting capabilities (support of dynamic contents), the underlying TLS channel used with HTTP/TLS MUST provide server identity verification. This means that (1) anonymous Diffie-Hellman key exchange cipher suites MUST NOT be used and (2) verification of the server certificate provided by the server MUST be performed. This is to prevent loading identity-unauthenticated scripts or dynamic contents, which are referenced from the authenticated page.

クライアントが何らかのスクリプト機能を持つ（動的コンテンツをサポートする）Webブラウザーである場合、HTTP/TLSで使用される下位のTLSチャネルは、サーバーの身元の検証を提供しなければなりません（MUST）。 これは、(1)匿名のDiffie-Hellman鍵交換の暗号スイートを使用してはなりません（MUST NOT）、また(2)サーバーが提示したサーバー証明書の検証を行わなければなりません（MUST）、ということを意味します。 これは、認証されたページから参照される、身元が認証されていないスクリプトや動的コンテンツが読み込まれるのを防ぐためです。

For other systems, when the underlying TLS channel used with HTTP/TLS does not perform server identity verification, the client SHOULD ensure that all responses are validated using the Mutual authentication protocol, regardless of the existence of 401-INIT responses.

その他のシステムでは、HTTP/TLSで使用される下位のTLSチャネルがサーバーの身元の検証を行わない場合、クライアントは、401-INITレスポンスの有無にかかわらず、すべてのレスポンスがMutual認証プロトコルを使用して検証されることを保証するべきです（SHOULD）。

7.2. Notes on "tls-unique"

7.2. 「tls-unique」に関する注意

As described in the interoperability note in Section 3.1 of [RFC5929], the "tls-unique" verification value will be changed by possible TLS renegotiation, causing an interoperability problem. TLS renegotiations are used in several HTTPS server implementations for enforcing some security properties (such as cryptographic strength) for some specific responses.

[RFC5929]のセクション3.1の相互運用性に関する注で説明されているように、「tls-unique」の検証値は、TLSの再ネゴシエーションが行われると変化する可能性があり、相互運用性の問題を引き起こします。 TLSの再ネゴシエーションは、いくつかのHTTPSサーバー実装で、特定のレスポンスに対して何らかのセキュリティー特性（暗号強度など）を強制するために使用されています。

If an implementation supports the "tls-unique" verification method, the following precautions SHOULD be taken:

実装が「tls-unique」検証方式をサポートする場合は、次の予防措置を講じるべきです（SHOULD）。

  • Both peers must be aware that the vh values used for vkc (in req-VFY-C messages) and vks (in 200-VFY-S messages) may be different. These values MUST be retrieved from underlying TLS libraries each time they are used.

  • After calculating the values vh and vkc to send a req-VFY-C request, clients SHOULD NOT initiate TLS renegotiation until the end of the corresponding response header is received. An exception is that clients can and SHOULD perform TLS renegotiation as a response to the server's request for TLS renegotiation, before receipt of the beginning of the response header.

  • 両方のピアは、vkc（req-VFY-Cメッセージ内）とvks（200-VFY-Sメッセージ内）に使用されるvhの値が異なる可能性があることを認識していなければなりません。 これらの値は、使用するたびに下位のTLSライブラリーから取得しなければなりません（MUST）。

  • req-VFY-Cリクエストを送信するために値vhとvkcを計算した後、クライアントは、対応するレスポンスヘッダーの終わりを受信するまで、TLSの再ネゴシエーションを開始するべきではありません（SHOULD NOT）。 例外として、レスポンスヘッダーの先頭を受信する前であれば、クライアントはサーバーからのTLS再ネゴシエーションの要求への応答としてTLSの再ネゴシエーションを行うことができ、またそうするべきです（SHOULD）。

Also, implementers MUST take care of session resumption attacks regarding "tls-unique" channel-binding mechanisms and master secrets. As a mitigation, the TLS extension defined in [RFC7627] SHOULD be used when "tls-unique" host verification is to be used.

また、実装者は、「tls-unique」チャネルバインディングの仕組みとマスターシークレットに関するセッション再開攻撃に注意しなければなりません（MUST）。 緩和策として、「tls-unique」ホスト検証を使用する場合は、[RFC7627]で定義されているTLS拡張を使用するべきです（SHOULD）。

8. Authentication Extensions

8. 認証の拡張

It is RECOMMENDED that interactive clients (e.g., Web browsers) supporting this protocol support non-mandatory authentication and the Authentication-Control header defined in [RFC8053], except for the "auth-style" parameter. This specification also proposes (but does not mandate) that the default "auth-style" be "non-modal". Web applications SHOULD, however, consider the security impacts of the behavior of clients that do not support these headers.

このプロトコルをサポートする対話型クライアント（たとえばWebブラウザー）は、[RFC8053]で定義されている、必須でない認証とAuthentication-Controlヘッダーを、「auth-style」パラメーターを除いてサポートすることが推奨されます（RECOMMENDED）。 また、この仕様は、デフォルトの「auth-style」を「non-modal」とすることを提案します（ただし義務付けはしません）。 ただし、Webアプリケーションは、これらのヘッダーをサポートしないクライアントの動作がセキュリティーに与える影響を考慮するべきです（SHOULD）。

Authentication-initializing messages with the Optional-WWW-Authenticate header are used only where the 401-INIT response is valid. It will not replace other 401-type messages such as 401-STALE and 401-KEX-S1. That is, the "reason" field of such a message MUST be "initial" (or any extensive-tokens NOT defined in Section 4.1).

Optional-WWW-Authenticateヘッダーを持つ認証開始メッセージは、401-INITレスポンスが有効な場面でのみ使用されます。 これは、401-STALEや401-KEX-S1などの他の401型のメッセージを置き換えるものではありません。 つまり、このようなメッセージの「reason」フィールドは「initial」（またはセクション4.1で定義されていない任意のextensive-token）でなければなりません（MUST）。

9. String Preparation

9. 文字列の準備

For interoperability reasons, it is important that usernames and passwords used in this protocol be binary-comparable, regardless of the user's input methods and/or environments. To ensure this, the following preparation SHOULD be performed:

相互運用性の理由から、このプロトコルで使用するユーザー名とパスワードは、ユーザーの入力方法や環境にかかわらず、バイナリーとして比較可能であることが重要です。 これを保証するために、次の準備を行うべきです（SHOULD）。

  • Usernames received from users SHOULD be prepared using the "UsernameCasePreserved" profile defined in Section 3.3 of [RFC7613].

  • Passwords received from users SHOULD be prepared using the "OpaqueString" profile defined in Section 4.2 of [RFC7613].

  • ユーザーから受け取ったユーザー名は、[RFC7613]のセクション3.3で定義されている「UsernameCasePreserved」プロファイルを使用して準備するべきです（SHOULD）。

  • ユーザーから受け取ったパスワードは、[RFC7613]のセクション4.2で定義されている「OpaqueString」プロファイルを使用して準備するべきです（SHOULD）。

In both cases, it is the sender's duty to correctly prepare the character strings. If any non-prepared character string is received from the other peer of the communication, the behavior of its recipient is not defined; the recipient MAY either accept or reject such input.

どちらの場合も、文字列を正しく準備するのは送信者の責務です。 準備されていない文字列を通信相手のピアから受信した場合、その受信者の動作は定義されていません。 受信者は、そのような入力を受け入れても拒否してもよいです（MAY）。

Server applications SHOULD also prepare usernames and passwords accordingly upon registration of user credentials.

サーバーアプリケーションも、ユーザーのクレデンシャルを登録する際に、ユーザー名とパスワードを同様に準備するべきです（SHOULD）。

In addition, binary-based "interfaces" of implementations MAY require and assume that the string is already prepared accordingly; when a string is already stored as a binary Unicode string form, implementations MAY omit preparation and Unicode normalization (performing UTF-8 encoding only) before using it. When a string is already stored as an octet blob, implementations MAY send it as is.

さらに、実装のバイナリーベースの「インターフェイス」は、文字列がすでに同様に準備されていることを要求し、前提としてもよいです（MAY）。 文字列がすでにバイナリーのUnicode文字列の形式で格納されている場合、実装は、それを使用する前に準備とUnicode正規化を省略して（UTF-8エンコーディングのみを行って）もよいです（MAY）。 文字列がすでにオクテットの塊として格納されている場合、実装はそれをそのまま送信してもよいです（MAY）。

10. Decision Procedure for Clients

10. クライアントの決定手順

10.1. General Principles and Requirements

10.1. 一般原則と要件

To securely implement the protocol, the client must be careful about accepting the authenticated responses from the server. This also holds true for the reception of a "normal response" (a response that does not contain mutual-authentication-related headers) from HTTP servers.

このプロトコルを安全に実装するために、クライアントは、サーバーからの認証されたレスポンスを受け入れることについて注意しなければなりません。 これは、HTTPサーバーから「通常のレスポンス」（相互認証関連のヘッダーを含まないレスポンス）を受信する場合にも当てはまります。

Per typical HTTP authentication, a single user-level request may result in the exchange of two or more HTTP requests and responses in sequence. The following normative rules MUST be followed by the clients implementing this protocol:

典型的なHTTP認証と同様に、ユーザーレベルの1つのリクエストが、2つ以上のHTTPリクエストとレスポンスの一連のやり取りになる場合があります。 このプロトコルを実装するクライアントは、次の規範的な規則に従わなければなりません（MUST）。

  • Any kind of "normal response" MUST only be accepted for the very first request in the sequence. Any "normal response" returned for the second or subsequent requests in the sequence SHALL be considered invalid.

  • By the same principle, if any response is related to an authentication realm that is different from that of the client's request (for example, a 401-INIT message requesting authentication on another realm), it MUST only be accepted for the very first request in the sequence. Such a response returned for a second or subsequent request in the sequence SHALL be considered invalid.

  • A req-KEX-C1 message MAY be sent as either an initial request or a response to a 401-INIT or 401-STALE message. However, to avoid infinite loops of messages, the req-KEX-C1 message SHOULD NOT be sent more than once in the sequence for a single authentication realm. A 401-KEX-S1 response MUST be accepted only when the corresponding request is req-KEX-C1.

  • A req-VFY-C message MAY be sent if there is a valid session secret shared between the client and the server, as established by req-KEX-C1 and 401-KEX-S1 messages. If any response with a 401 status code is returned for such a message, the corresponding session secret SHOULD be discarded as unusable.

    In particular, upon the reception of a 401-STALE response, the client SHOULD try to establish a new session by sending a req-KEX-C1 message, but only once within the request/response sequence.

  • A 200-VFY-S message MUST be accepted only as a response to a req-VFY-C message and nothing else. The VK_s values of such response messages MUST always be checked against the correct value, and if it is incorrect, the whole response SHOULD be considered invalid.

  • どのような種類の「通常のレスポンス」も、受け入れるのはシーケンスの一番最初のリクエストに対するものだけでなければなりません（MUST）。 シーケンスの2番目以降のリクエストに対して返された「通常のレスポンス」は、無効とみなすものとすることになります（SHALL）。

  • 同じ原則により、あるレスポンスが、クライアントのリクエストのものとは異なる認証レルムに関係している場合（たとえば、別のレルムでの認証を要求する401-INITメッセージ）、そのレスポンスを受け入れるのはシーケンスの一番最初のリクエストに対するものだけでなければなりません（MUST）。 シーケンスの2番目以降のリクエストに対して返されたそのようなレスポンスは、無効とみなすものとすることになります（SHALL）。

  • req-KEX-C1メッセージは、最初のリクエストとして、または401-INITメッセージもしくは401-STALEメッセージへの応答として送信してもよいです（MAY）。 ただし、メッセージの無限ループを避けるために、req-KEX-C1メッセージは、1つの認証レルムについてシーケンス内で2回以上送信するべきではありません（SHOULD NOT）。 401-KEX-S1レスポンスを受け入れるのは、対応するリクエストがreq-KEX-C1である場合だけでなければなりません（MUST）。

  • req-VFY-Cメッセージは、req-KEX-C1メッセージと401-KEX-S1メッセージによって確立された、クライアントとサーバーの間で共有される有効なセッション秘密がある場合に送信してもよいです（MAY）。 そのようなメッセージに対して401ステータスコードを持つレスポンスが返された場合、対応するセッション秘密は使用できないものとして破棄するべきです（SHOULD）。

    特に、401-STALEレスポンスを受信した場合、クライアントは、req-KEX-C1メッセージを送信することによって新しいセッションを確立するように試みるべきです（SHOULD）。 ただし、それはリクエストとレスポンスのシーケンス内で1回だけです。

  • 200-VFY-Sメッセージを受け入れるのは、req-VFY-Cメッセージに対するレスポンスである場合だけでなければなりません（MUST）。 それ以外の場合は受け入れません。 そのようなレスポンスメッセージのVK_sの値は、常に正しい値と照合しなければなりません（MUST）。 正しくない場合は、レスポンス全体を無効とみなすべきです（SHOULD）。

The final status of the client request following the message exchange sequence shall be determined as follows:

メッセージ交換のシーケンスに続くクライアントのリクエストの最終的な状態は、次のように決定されます。

  • AUTH-SUCCEED: A 200-VFY-S message with the correct VK_s value was returned in response to the req-VFY-C request in the sequence.

  • AUTH-REQUIRED: Two cases exist:

    • A 401-INIT message was returned from the server, and the client does not know how to authenticate to the given authentication realm.

    • A 401-INIT response was returned for a req-VFY-C (or req-KEX-C1) message, which means that the user-supplied authentication credentials were not accepted.

  • UNAUTHENTICATED: A "normal response" is returned for an initial request of any kind in the sequence.

  • AUTH-SUCCEED：シーケンス内のreq-VFY-Cリクエストに対するレスポンスとして、正しいVK_sの値を持つ200-VFY-Sメッセージが返されました。

  • AUTH-REQUIRED：2つの場合があります。

    • サーバーから401-INITメッセージが返され、クライアントは指定された認証レルムに対して認証する方法を知りません。

    • req-VFY-C（またはreq-KEX-C1）メッセージに対して401-INITレスポンスが返されました。 これは、ユーザーが入力した認証クレデンシャルが受け入れられなかったことを意味します。

  • UNAUTHENTICATED：シーケンス内のあらゆる種類の最初のリクエストに対して「通常のレスポンス」が返されました。

Any kind of response (including a "normal response") other than those explicitly allowed in the above rules SHOULD be interpreted as a fatal communication error. In such cases, the clients MUST NOT process any data (the response body and other content-related headers) sent from the server. However, to handle exceptional error cases, clients MAY accept a message without an Authentication-Info header if it has a Server Error (5xx) status code. In such cases, they SHOULD be careful about processing the body of the content (ignoring it is still RECOMMENDED, as it may possibly be forged by intermediate attackers), and the client will then have a status of "UNAUTHENTICATED".

上記の規則で明示的に許可されたもの以外のあらゆる種類のレスポンス（「通常のレスポンス」を含む）は、致命的な通信エラーとして解釈するべきです（SHOULD）。 このような場合、クライアントはサーバーから送信されたいかなるデータ（レスポンスのボディーやその他のコンテンツ関連のヘッダー）も処理してはなりません（MUST NOT）。 ただし、例外的なエラーの場合を扱うために、クライアントは、Server Error（5xx）ステータスコードを持つメッセージであれば、Authentication-Infoヘッダーのないメッセージを受け入れてもよいです（MAY）。 このような場合、クライアントはコンテンツのボディーの処理に注意するべきです（SHOULD）（中間の攻撃者によって偽造されている可能性があるため、やはり無視することが推奨されます（RECOMMENDED））。 また、そのときクライアントは「UNAUTHENTICATED」の状態になります。

If a request is a sub-request for a resource included in another resource (e.g., embedded images, style sheets, frames), clients MAY treat an AUTH-REQUESTED status the same way they would treat an UNAUTHENTICATED status. In other words, the client MAY ignore the server's request to start authentication with new credentials via sub-requests.

リクエストが、別のリソースに含まれるリソース（たとえば、埋め込み画像、スタイルシート、フレーム）に対するサブリクエストである場合、クライアントはAUTH-REQUESTEDの状態を、UNAUTHENTICATEDの状態と同じように扱ってもよいです（MAY）。 言い換えれば、クライアントは、サブリクエストを介して新しいクレデンシャルで認証を開始するようにというサーバーの要求を無視してもよいです（MAY）。

10.2. State Machine for the Client (Informative)

10.2. クライアントの状態機械（参考情報）

The following state machine describes the possible request-response sequences derived from the above normative rules. If implementers are not quite sure of the security consequences of the above rules, we strongly advise that the decision procedure below be followed. In particular, clients SHOULD NOT accept "normal responses" unless explicitly allowed in the rules. The labels in the steps below are for informational purposes only. Action entries within each step are checked in top-to-bottom order, and the first clause satisfied is to be followed.

次の状態機械は、上記の規範的な規則から導かれる、可能なリクエストとレスポンスのシーケンスを説明します。 実装者が上記の規則のセキュリティー上の帰結についてよくわからない場合は、以下の決定手順に従うことを強く勧めます。 特に、クライアントは、規則で明示的に許可されていない限り、「通常のレスポンス」を受け入れるべきではありません（SHOULD NOT）。 以下のステップのラベルは、情報提供のためだけのものです。 各ステップ内の動作の項目は上から下の順に確認し、最初に満たされた節に従います。

Step 1 (step_new_request):

If the client software needs to access a new Web resource, check to see whether the resource is expected to be inside some authentication realm for which the user has already been authenticated via the Mutual authentication scheme. If yes, go to Step 2. Otherwise, go to Step 5.

Step 2:

Check to see whether there is an available sid for the expected authentication realm. If there is one, go to Step 3. Otherwise, go to Step 4.

Step 3 (step_send_vfy_1):

Send a req-VFY-C request.

  • If a 401-INIT message is received with a different authentication realm than expected, go to Step 6.

  • If a 401-STALE message is received, go to Step 9.

  • If a 401-INIT message is received, go to Step 13.

  • If a 200-VFY-S message is received, go to Step 14.

  • If a "normal response" is received, go to Step 11.

Step 4 (step_send_kex1_1):

Send a req-KEX-C1 request.

  • If a 401-INIT message is received with a different authentication realm than expected, go to Step 6.

  • If a 401-KEX-S1 message is received, go to Step 10.

  • If a 401-INIT message is received with the same authentication realm, go to Step 13 (see Note 1).

  • If a "normal response" is received, go to Step 11.

Step 5 (step_send_normal_1):

Send a request without any mutual-authentication headers.

  • If a 401-INIT message is received, go to Step 6.

  • If a "normal response" is received, go to Step 11.

Step 6 (step_rcvd_init):

Check to see whether the user's password for the requested authentication realm is known. If yes, go to Step 7. Otherwise, go to Step 12.

Step 7:

Check to see whether there is an available sid for the expected authentication realm. If there is one, go to Step 8. Otherwise, go to Step 9.

Step 8 (step_send_vfy):

Send a req-VFY-C request.

  • If a 401-STALE message is received, go to Step 9.

  • If a 401-INIT message is received, go to Step 13.

  • If a 200-VFY-S message is received, go to Step 14.

Step 9 (step_send_kex1):

Send a req-KEX-C1 request.

  • If a 401-KEX-S1 message is received, go to Step 10.

  • If a 401-INIT message is received, go to Step 13 (see Note 1).

Step 10 (step_rcvd_kex1):

Send a req-VFY-C request.

  • If a 401-INIT message is received, go to Step 13.

  • If a 200-VFY-S message is received, go to Step 14.

Step 11 (step_rcvd_normal):

The requested resource is out of the authenticated area. The client will be in the "UNAUTHENTICATED" status. If the response contains a request for authentication other than Mutual authentication, it MAY be handled normally.

Step 12 (step_rcvd_init_unknown):

The requested resource requires Mutual authentication, and the user is not yet authenticated. The client will be in the "AUTH-REQUESTED" status; it is RECOMMENDED that the client process the content sent from the server and ask the user for a username and password. When those are supplied by the user, go to Step 9.

Step 13 (step_rcvd_init_failed):

The authentication failed for some reason, possibly because the password or username is invalid for the authenticated resource. Forget the user-provided credentials for the authentication realm, and go to Step 12.

Step 14 (step_rcvd_vfy):

The received message is the 200-VFY-S message, which always contains a "vks" field. Check the validity of the received VK_s value. If it is equal to the expected value, then the mutual authentication succeeded. The client will be in the "AUTH-SUCCEED" status.

An unexpected value is interpreted as a fatal communication error.

If a user explicitly asks to log out (via the user interface), the client MUST forget the user's password, go to Step 5, and reload the current resource without an authentication header.

Note 1:

These transitions MAY be accepted by clients, but it is NOT RECOMMENDED that servers initiate them.

ステップ1（step_new_request）：

クライアントソフトウェアが新しいWebリソースにアクセスする必要がある場合、そのリソースが、ユーザーがMutual認証スキームによってすでに認証されている何らかの認証レルムの内側にあると期待されるかどうかを確認します。 そうであれば、ステップ2に進みます。 そうでなければ、ステップ5に進みます。

ステップ2：

期待される認証レルムについて利用可能なsidがあるかどうかを確認します。 あれば、ステップ3に進みます。 なければ、ステップ4に進みます。

ステップ3（step_send_vfy_1）：

req-VFY-Cリクエストを送信します。

  • 期待とは異なる認証レルムを持つ401-INITメッセージを受信した場合は、ステップ6に進みます。

  • 401-STALEメッセージを受信した場合は、ステップ9に進みます。

  • 401-INITメッセージを受信した場合は、ステップ13に進みます。

  • 200-VFY-Sメッセージを受信した場合は、ステップ14に進みます。

  • 「通常のレスポンス」を受信した場合は、ステップ11に進みます。

ステップ4（step_send_kex1_1）：

req-KEX-C1リクエストを送信します。

  • 期待とは異なる認証レルムを持つ401-INITメッセージを受信した場合は、ステップ6に進みます。

  • 401-KEX-S1メッセージを受信した場合は、ステップ10に進みます。

  • 同じ認証レルムを持つ401-INITメッセージを受信した場合は、ステップ13に進みます（注1を参照）。

  • 「通常のレスポンス」を受信した場合は、ステップ11に進みます。

ステップ5（step_send_normal_1）：

相互認証のヘッダーを一切含まないリクエストを送信します。

  • 401-INITメッセージを受信した場合は、ステップ6に進みます。

  • 「通常のレスポンス」を受信した場合は、ステップ11に進みます。

ステップ6（step_rcvd_init）：

リクエストされた認証レルムに対するユーザーのパスワードがわかっているかどうかを確認します。 わかっていれば、ステップ7に進みます。 そうでなければ、ステップ12に進みます。

ステップ7：

期待される認証レルムについて利用可能なsidがあるかどうかを確認します。 あれば、ステップ8に進みます。 なければ、ステップ9に進みます。

ステップ8（step_send_vfy）：

req-VFY-Cリクエストを送信します。

  • 401-STALEメッセージを受信した場合は、ステップ9に進みます。

  • 401-INITメッセージを受信した場合は、ステップ13に進みます。

  • 200-VFY-Sメッセージを受信した場合は、ステップ14に進みます。

ステップ9（step_send_kex1）：

req-KEX-C1リクエストを送信します。

  • 401-KEX-S1メッセージを受信した場合は、ステップ10に進みます。

  • 401-INITメッセージを受信した場合は、ステップ13に進みます（注1を参照）。

ステップ10（step_rcvd_kex1）：

req-VFY-Cリクエストを送信します。

  • 401-INITメッセージを受信した場合は、ステップ13に進みます。

  • 200-VFY-Sメッセージを受信した場合は、ステップ14に進みます。

ステップ11（step_rcvd_normal）：

リクエストされたリソースは認証された領域の外にあります。 クライアントは「UNAUTHENTICATED」の状態になります。 レスポンスにMutual認証以外の認証の要求が含まれている場合は、それを通常どおり処理してもよいです（MAY）。

ステップ12（step_rcvd_init_unknown）：

リクエストされたリソースはMutual認証を必要としており、ユーザーはまだ認証されていません。 クライアントは「AUTH-REQUESTED」の状態になります。 クライアントは、サーバーから送信されたコンテンツを処理し、ユーザーにユーザー名とパスワードを尋ねることが推奨されます（RECOMMENDED）。 ユーザーがそれらを入力したら、ステップ9に進みます。

ステップ13（step_rcvd_init_failed）：

何らかの理由で、おそらく認証されたリソースに対してパスワードまたはユーザー名が無効であるために、認証が失敗しました。 その認証レルムについてユーザーが入力したクレデンシャルを忘れ、ステップ12に進みます。

ステップ14（step_rcvd_vfy）：

受信したメッセージは200-VFY-Sメッセージであり、常に「vks」フィールドを含みます。 受信したVK_sの値の正当性を確認します。 期待される値と等しければ、相互認証は成功です。 クライアントは「AUTH-SUCCEED」の状態になります。

予期しない値は、致命的な通信エラーとして解釈されます。

ユーザーが（ユーザーインターフェイスを介して）明示的にログアウトを要求した場合、クライアントはユーザーのパスワードを忘れ、ステップ5に進み、現在のリソースを認証ヘッダーなしで再読み込みしなければなりません（MUST）。

注1：

クライアントはこれらの遷移を受け入れてもよいです（MAY）。 ただし、サーバーがこれらの遷移を引き起こすことは推奨されません（NOT RECOMMENDED）。

11. Decision Procedure for Servers

11. サーバーの決定手順

Each server SHOULD have a table of session states. This table need not be persistent over the long term; it MAY be cleared upon server restart, reboot, or for other reasons. Each entry in the table SHOULD contain at least the following information:

各サーバーは、セッションの状態のテーブルを持つべきです（SHOULD）。 このテーブルは長期的に永続的である必要はありません。 サーバーの再起動、リブート、またはその他の理由で消去してもよいです（MAY）。 テーブルの各エントリーは、少なくとも次の情報を含むべきです（SHOULD）。

  • The session identifier, which is the value of the "sid" parameter.

  • The algorithm used.

  • The authentication realm.

  • The state of the protocol: one of "key exchanging", "authenticated", "rejected", or "inactive".

  • The username received from the client.

  • A boolean flag indicating whether or not the session is fake.

  • When the state is "key exchanging", the values of K_c1 and S_s1.

  • When the state is "authenticated", the following information:

    • The value of the session secret (z).

    • The largest nc received from the client (largest-nc).

    • For each possible nc value between (largest-nc - nc-window + 1) and max_nc, a boolean flag indicating whether or not a request with the corresponding nc has been received.

  • セッション識別子。 これは「sid」パラメーターの値です。

  • 使用されたアルゴリズム。

  • 認証レルム。

  • プロトコルの状態："key exchanging"、"authenticated"、"rejected"、"inactive"のいずれか。

  • クライアントから受信したユーザー名。

  • セッションが偽物であるかどうかを示す真偽値のフラグ。

  • 状態が"key exchanging"の場合は、K_c1とS_s1の値。

  • 状態が"authenticated"の場合は、次の情報。

    • セッション秘密（z）の値。

    • クライアントから受信した最大のnc（largest-nc）。

    • (largest-nc - nc-window + 1)からmax_ncまでの可能な各ncの値について、対応するncを持つリクエストを受信したかどうかを示す真偽値のフラグ。

The table MAY contain other information.

テーブルはその他の情報を含んでもよいです（MAY）。

Servers SHOULD respond to the client requests according to the following procedure (see Note 1 below regarding 401-INIT messages with a plus sign):

サーバーは、次の手順に従ってクライアントのリクエストに応答するべきです（SHOULD）（プラス記号の付いた401-INITメッセージについては、以下の注1を参照）。

  • When the server receives a "normal request":

    • If the requested resource is not protected by the Mutual authentication, send a "normal response".

    • If the resource is protected by the Mutual authentication, send a 401-INIT response.

  • When the server receives a req-KEX-C1 request:

    • If the requested resource is not protected by the Mutual authentication, send a "normal response".

    • If the authentication realm specified in the req-KEX-C1 request is not the expected realm, send a 401-INIT response.

    • If the server cannot validate the parameter "kc1", send a 401-INIT (+) response.

    • If the received username is either invalid, unknown, or unacceptable, create a new session, mark it as a "fake" session, compute a random value as K_s1, and send a fake 401-KEX-S1 response (see Note 2).

    • Otherwise, create a new session, compute K_s1, and send a 401-KEX-S1 response. The created session is marked as not fake, and its largest-nc value is initialized to zero.

    The created session is in the "key exchanging" state.

  • When the server receives a req-VFY-C request:

    • If the requested resource is not protected by the Mutual authentication, send a "normal response".

    • If the authentication realm specified in the req-VFY-C request is not the expected realm, send a 401-INIT response.

    If none of the above holds true, the server will look up the session corresponding to the received sid and the authentication realm.

    • If the session corresponding to the received sid could not be found or it is in the "inactive" state, send a 401-STALE response.

    • If the session is in the "rejected" state, send either a 401-INIT (+) response or a 401-STALE message.

    • If the nc value in the request is larger than the "nc-max" parameter sent from the server or it is not larger than (largest-nc - nc-window) (when in the "authenticated" state), the server MAY (but is not REQUIRED to; see Note 3) send a 401-STALE message. The session is changed to the "inactive" state if the 401-STALE message was sent.

    • If the session is in the "authenticated" state and the request has an nc value that was previously received from the client, send a 401-STALE message. The session is changed to the "inactive" state.

    • If the session is a "fake" session or the received vkc is incorrect, then send a 401-INIT (+) response. If the session is in the "key exchanging" state, it MUST be changed to the "rejected" state; otherwise, it MAY be either changed to the "rejected" state or kept in the previous state.

    • Otherwise, send a 200-VFY-S response. If the session was in the "key exchanging" state, the session SHOULD be changed to the "authenticated" state. The maximum nc and nc flags of the state MUST be updated appropriately.

  • サーバーが「通常のリクエスト」を受信した場合：

    • リクエストされたリソースがMutual認証で保護されていない場合は、「通常のレスポンス」を送信します。

    • リソースがMutual認証で保護されている場合は、401-INITレスポンスを送信します。

  • サーバーがreq-KEX-C1リクエストを受信した場合：

    • リクエストされたリソースがMutual認証で保護されていない場合は、「通常のレスポンス」を送信します。

    • req-KEX-C1リクエストで指定された認証レルムが期待されるレルムでない場合は、401-INITレスポンスを送信します。

    • サーバーがパラメーター「kc1」を検証できない場合は、401-INIT (+)レスポンスを送信します。

    • 受信したユーザー名が無効、未知、または受け入れられないものである場合は、新しいセッションを作成し、それを「偽の」セッションとして記録し、ランダムな値をK_s1として計算し、偽の401-KEX-S1レスポンスを送信します（注2を参照）。

    • それ以外の場合は、新しいセッションを作成し、K_s1を計算し、401-KEX-S1レスポンスを送信します。 作成したセッションは偽物ではないものとして記録し、そのlargest-ncの値をゼロに初期化します。

    作成したセッションは"key exchanging"状態になります。

  • サーバーがreq-VFY-Cリクエストを受信した場合：

    • リクエストされたリソースがMutual認証で保護されていない場合は、「通常のレスポンス」を送信します。

    • req-VFY-Cリクエストで指定された認証レルムが期待されるレルムでない場合は、401-INITレスポンスを送信します。

    上記のいずれにも当てはまらない場合、サーバーは、受信したsidと認証レルムに対応するセッションを検索します。

    • 受信したsidに対応するセッションが見つからなかった場合、またはセッションが"inactive"状態である場合は、401-STALEレスポンスを送信します。

    • セッションが"rejected"状態である場合は、401-INIT (+)レスポンスまたは401-STALEメッセージのいずれかを送信します。

    • リクエスト内のncの値が、サーバーから送信された「nc-max」パラメーターを超えている場合、または（"authenticated"状態にあるとき）(largest-nc - nc-window)以下である場合、サーバーは401-STALEメッセージを送信してもよいです（MAY）（ただし、そうすることが要求されています（REQUIRED）というわけではありません。注3を参照）。 401-STALEメッセージを送信した場合、セッションは"inactive"状態に変更されます。

    • セッションが"authenticated"状態にあり、リクエストが以前にクライアントから受信したncの値を持つ場合は、401-STALEメッセージを送信します。 セッションは"inactive"状態に変更されます。

    • セッションが「偽の」セッションである場合、または受信したvkcが正しくない場合は、401-INIT (+)レスポンスを送信します。 セッションが"key exchanging"状態にある場合、セッションは"rejected"状態に変更しなければなりません（MUST）。 そうでない場合は、"rejected"状態に変更するか、以前の状態のままにしてもよいです（MAY）。

    • それ以外の場合は、200-VFY-Sレスポンスを送信します。 セッションが"key exchanging"状態にあった場合、セッションは"authenticated"状態に変更するべきです（SHOULD）。 状態の最大ncとncのフラグは、適切に更新しなければなりません（MUST）。

At any time, the server MAY change any state entries with both the "rejected" and "authenticated" states to the "inactive" state and MAY discard any "inactive" states from the table. Entries with the "key exchanging" state SHOULD be kept unless there is an emergency situation such as a server reboot or a table capacity overflow.

サーバーは、いつでも、"rejected"状態および"authenticated"状態の状態エントリーを"inactive"状態に変更してもよいです（MAY）。 また、"inactive"状態のものをテーブルから破棄してもよいです（MAY）。 "key exchanging"状態のエントリーは、サーバーのリブートやテーブル容量のオーバーフローなどの緊急事態がない限り、保持するべきです（SHOULD）。

Note 1: In relation to, and following the specification of, the optional authentication defined in [RFC8053], the 401-INIT messages marked with plus signs cannot be replaced with a successful response with an Optional-WWW-Authenticate header. Every other 401-INIT can be a response with an Optional-WWW-Authenticate header.

注1：[RFC8053]で定義されている省略可能な認証に関連して、またその仕様に従って、プラス記号の付いた401-INITメッセージは、Optional-WWW-Authenticateヘッダーを持つ成功レスポンスで置き換えることはできません。 それ以外のすべての401-INITは、Optional-WWW-Authenticateヘッダーを持つレスポンスにできます。

Note 2: The server SHOULD NOT send a 401-INIT response in this case, because it will leak the information to the client that the specified username will not be accepted. Instead, postpone it until the response to the next req-VFY-C request.

注2：この場合、サーバーは401-INITレスポンスを送信するべきではありません（SHOULD NOT）。 指定されたユーザー名が受け入れられないという情報をクライアントに漏らすことになるためです。 その代わりに、次のreq-VFY-Cリクエストへのレスポンスまで延期します。

Note 3: If the request is not rejected in this clause, the server will be required, in the next step, to determine whether the same nc value was previously received from the client. If that is impossible, the server MUST send a 401-STALE response in this step. If the server does not remember the whole history of the nc values received from the client, the server MUST send a 401-STALE message in this clause.

注3：この節でリクエストが拒否されない場合、サーバーは次のステップで、同じncの値を以前にクライアントから受信したかどうかを判断する必要があります。 それが不可能な場合、サーバーはこのステップで401-STALEレスポンスを送信しなければなりません（MUST）。 サーバーが、クライアントから受信したncの値の履歴全体を覚えていない場合、サーバーはこの節で401-STALEメッセージを送信しなければなりません（MUST）。

12. Authentication Algorithms

12. 認証アルゴリズム

Cryptographic authentication algorithms that are used with this protocol will be defined separately. The algorithm definition MUST at least provide definitions for the following functions:

このプロトコルで使用する暗号学的な認証アルゴリズムは、別途定義されます。 アルゴリズムの定義は、少なくとも次の関数の定義を提供しなければなりません（MUST）。

  • The server-side authentication credential J, derived from the client-side authentication credential pi.

  • Key exchange values K_c1, K_s1 (exchanged on the wire) and S_c1, S_s1 (kept secret in each peer).

  • Shared session secret (z), to be computed by both server and client.

  • A hash function H to be used with the protocol, along with its output size hSize.

  • The value nIterPi, the number of iterations for the key derivation operation.

  • クライアント側の認証クレデンシャルpiから導出される、サーバー側の認証クレデンシャルJ。

  • 鍵交換値K_c1、K_s1（通信路上で交換される）と、S_c1、S_s1（各ピアで秘密に保たれる）。

  • サーバーとクライアントの両方によって計算される共有のセッション秘密（z）。

  • プロトコルで使用するハッシュ関数Hと、その出力サイズhSize。

  • 鍵導出操作の反復回数である値nIterPi。

Specifications for cryptographic algorithms used with this framework MUST specify whether those algorithms will (1) use the default functions defined below for values pi, VK_c, and VK_s or (2) define their own comparable functions.

このフレームワークで使用する暗号アルゴリズムの仕様は、それらのアルゴリズムが、(1)値pi、VK_c、VK_sについて以下で定義するデフォルトの関数を使用するか、(2)独自の同等の関数を定義するかを規定しなければなりません（MUST）。

All algorithms used with this protocol SHOULD provide secure mutual authentication between clients and servers and generate a cryptographically strong shared secret value (z) that is equally strong or stronger than the hash function H. If any passwords (or passphrases or any equivalents, i.e., weak secrets) are involved, these SHOULD NOT be guessable from any data transmitted in the protocol, even if an attacker (either an eavesdropper or an active server) knows the possible thoroughly searchable candidate list of passwords. Furthermore, it is RECOMMENDED that the function J for deriving the server-side authentication credential J(pi) be one-way, if possible, so that pi cannot be easily computed from J(pi).

このプロトコルで使用するすべてのアルゴリズムは、クライアントとサーバーの間で安全な相互認証を提供し、ハッシュ関数Hと同等以上の強度を持つ、暗号学的に強力な共有秘密値（z）を生成するべきです（SHOULD）。 パスワード（またはパスフレーズやそれと同等のもの、つまり弱い秘密）が関係する場合、たとえ攻撃者（盗聴者または能動的なサーバーのいずれか）が、徹底的に探索可能なパスワードの候補リストを知っていたとしても、プロトコルで送信されるデータからそれらが推測可能であるべきではありません（SHOULD NOT）。 さらに、サーバー側の認証クレデンシャルJ(pi)を導出する関数Jは、piをJ(pi)から容易に計算できないように、可能であれば一方向性であることが推奨されます（RECOMMENDED）。

12.1. Support Functions and Notations

12.1. サポート関数と表記法

In this section, we define several support functions and notations to be shared by several algorithm definitions.

このセクションでは、いくつかのアルゴリズム定義で共有される、いくつかのサポート関数と表記法を定義します。

The integers in the specification are in decimal, or in hexadecimal when prefixed with "0x".

この仕様の整数は10進数で表記します。 ただし、「0x」が前に付いている場合は16進数です。

The function octet(i) generates an octet string containing a single octet of value i. The operator "|", when applied to octet strings, denotes the concatenation of two operands.

関数octet(i)は、値iの1オクテットだけを含むオクテット文字列を生成します。 演算子「|」は、オクテット文字列に適用された場合、2つのオペランドの連結を表します。

The function VI encodes natural numbers into octet strings in the following manner: numbers are represented as big-endian radix-128 strings, where each digit is represented by an octet within the range 0x80-0xff, except for the last digit, which is represented by an octet within the range 0x00-0x7f. The first octet MUST NOT be 0x80. For example, VI(i) = octet(i) for i < 128, and VI(i) = octet(0x80 + (i >> 7)) | octet(i & 127) for 128 <= i < 16384. This encoding is the same as the encoding used for the subcomponents of object identifiers in ASN.1 encoding [ITU.X690.2015] and is available as a "w" conversion in the "pack" function of several scripting languages.

関数VIは、自然数を次の方法でオクテット文字列にエンコードします。 数値はビッグエンディアンの128進の文字列として表され、各桁は0x80-0xffの範囲内のオクテットで表されます。 ただし、最後の桁は0x00-0x7fの範囲内のオクテットで表されます。 最初のオクテットは0x80であってはなりません（MUST NOT）。 たとえば、i < 128に対してはVI(i) = octet(i)であり、128 <= i < 16384に対してはVI(i) = octet(0x80 + (i >> 7)) | octet(i & 127)です。 このエンコーディングは、ASN.1エンコーディング[ITU.X690.2015]でオブジェクト識別子の下位要素に使用されるエンコーディングと同じであり、いくつかのスクリプト言語の「pack」関数では「w」変換として利用できます。

The function VS encodes a variable-length octet string into a uniquely decoded, self-delimited octet string in the following manner:

関数VSは、可変長のオクテット文字列を、次の方法で、一意にデコードできる自己区切りのオクテット文字列にエンコードします。

VS(s) = VI(length(s)) | s

VS(s) = VI(length(s)) | s

where length(s) is a number of octets (not characters) in s.

ここで、length(s)は、sに含まれるオクテット（文字ではありません）の数です。

Some examples:

いくつかの例：

   VI(0) = "\000" (in C string notation)

   VI(100) = "d"

   VI(10000) = "\316\020"

   VI(1000000) = "\275\204@"

   VS("") = "\000"

   VS("Tea") = "\003Tea"

   VS("Caf<e acute>" [in UTF-8]) = "\005Caf\303\251"

   VS([10000 "a"s]) = "\316\020aaaaa..." (10002 octets)

   VI(0) = "\000" (in C string notation)

   VI(100) = "d"

   VI(10000) = "\316\020"

   VI(1000000) = "\275\204@"

   VS("") = "\000"

   VS("Tea") = "\003Tea"

   VS("Caf<e acute>" [in UTF-8]) = "\005Caf\303\251"

   VS([10000 "a"s]) = "\316\020aaaaa..." (10002 octets)

(Note: Unlike the colon-separated format used in the Basic and Digest HTTP authentication schemes, the string generated by a concatenation of the VS-encoded strings will be unique, regardless of the characters included in the strings to be encoded.)

（注：BasicおよびDigestのHTTP認証スキームで使用されるコロン区切りの形式とは異なり、VSでエンコードした文字列を連結して生成した文字列は、エンコードする文字列に含まれる文字にかかわらず一意になります。）

The function OCTETS converts an integer into the corresponding radix-256 big-endian octet string having its natural length. See Section 3.2.3 for the definition of "natural length".

関数OCTETSは、整数を、その自然な長さを持つ対応する256進のビッグエンディアンのオクテット文字列に変換します。 「自然な長さ」の定義については、セクション3.2.3を参照してください。

The function INT converts an octet string into a natural number, where the input string is treated as being in radix-256 big-endian notation. The identity INT(OCTETS(n)) = n always holds for any natural number n.

関数INTは、入力文字列を256進のビッグエンディアン表記であるとみなして、オクテット文字列を自然数に変換します。 任意の自然数nに対して、恒等式INT(OCTETS(n)) = nが常に成り立ちます。

12.2. Default Functions for Algorithms

12.2. アルゴリズムのデフォルト関数

The functions defined in this section are common default functions among authentication algorithms.

このセクションで定義する関数は、認証アルゴリズムの間で共通のデフォルト関数です。

The client-side password-based (credential) pi used by this authentication is a natural number derived in the following manner:

この認証で使用されるクライアント側のパスワードベースの（クレデンシャル）piは、次の方法で導出される自然数です。

   pi = INT(PBKDF2(HMAC_H, password, VS(algorithm) | VS(auth-scope) |
   VS(realm) | VS(username), nIterPi, hSize / 8))

   pi = INT(PBKDF2(HMAC_H, password, VS(algorithm) | VS(auth-scope) |
   VS(realm) | VS(username), nIterPi, hSize / 8))

where

ここで、

  • PBKDF2 is the password-based key derivation function defined in [RFC8018],

  • HMAC_H is the Hashed Message Authentication Code (HMAC) function, defined in [RFC2104], composed from the hash function H, and

  • hSize is the output size of hash H in bits.

  • PBKDF2は、[RFC8018]で定義されているパスワードベースの鍵導出関数です。

  • HMAC_Hは、[RFC2104]で定義されている、ハッシュ関数Hから構成されたハッシュメッセージ認証コード（HMAC）関数です。

  • hSizeは、ハッシュHのビット単位の出力サイズです。

The values of algorithm, realm, and auth-scope are taken from the values contained in the 401-INIT message. If the password comes from user input, it SHOULD first be prepared according to the method presented in Section 9. Then, the password SHALL be encoded as a UTF-8 string.

algorithm、realm、auth-scopeの値は、401-INITメッセージに含まれる値から取得します。 パスワードがユーザーの入力に由来する場合は、まずセクション9で示す方法に従って準備するべきです（SHOULD）。 その後、パスワードはUTF-8文字列としてエンコードすることになります（SHALL）。

The values VK_c and VK_s are derived via the following equations:

値VK_cとVK_sは、次の式によって導出されます。

   VK_c = INT(H(octet(4) | OCTETS(K_c1) | OCTETS(K_s1) | OCTETS(z) |
   VI(nc) | VS(vh)))

   VK_c = INT(H(octet(4) | OCTETS(K_c1) | OCTETS(K_s1) | OCTETS(z) |
   VI(nc) | VS(vh)))

   VK_s = INT(H(octet(3) | OCTETS(K_c1) | OCTETS(K_s1) | OCTETS(z) |
   VI(nc) | VS(vh)))

   VK_s = INT(H(octet(3) | OCTETS(K_c1) | OCTETS(K_s1) | OCTETS(z) |
   VI(nc) | VS(vh)))

14. Application for Proxy Authentication

14. プロキシー認証への適用

The authentication scheme defined in the previous sections can be applied (with modifications) to proxy authentication. In such cases, the following alterations MUST be applied:

前のセクションで定義した認証スキームは、（変更を加えて）プロキシー認証に適用できます。 そのような場合は、次の変更を適用しなければなりません（MUST）。

  • The 407 (Proxy Authentication Required) status code is to be sent and recognized in places where the 401 status code is used,

  • The Proxy-Authenticate header is to be used in places where the WWW-Authenticate header is used,

  • The Proxy-Authorization header is to be used in places where the Authorization header is used,

  • The Proxy-Authentication-Info header is to be used in places where the Authentication-Info header is used,

  • The "auth-scope" parameter is fixed to the hostname of the proxy, which means that it covers all requests processed by the specific proxy,

  • The limitation for the paths contained in the "path" parameter of 401-KEX-S1 messages is disregarded,

  • The omission of the "path" parameter of 401-KEX-S1 messages means that the authentication realm will potentially cover all requests processed by the proxy,

  • The scheme, hostname, and port of the proxy are used for host validation tokens, and

  • Authentication extensions defined in [RFC8053] are not applicable.

  • 401ステータスコードが使用される場所では、407（Proxy Authentication Required）ステータスコードを送信し、認識します。

  • WWW-Authenticateヘッダーが使用される場所では、Proxy-Authenticateヘッダーを使用します。

  • Authorizationヘッダーが使用される場所では、Proxy-Authorizationヘッダーを使用します。

  • Authentication-Infoヘッダーが使用される場所では、Proxy-Authentication-Infoヘッダーを使用します。

  • 「auth-scope」パラメーターはプロキシーのホスト名に固定されます。 これは、その特定のプロキシーが処理するすべてのリクエストを対象とすることを意味します。

  • 401-KEX-S1メッセージの「path」パラメーターに含まれるパスに対する制限は無視されます。

  • 401-KEX-S1メッセージの「path」パラメーターを省略することは、認証レルムがプロキシーが処理するすべてのリクエストを潜在的に対象とすることを意味します。

  • プロキシーのスキーム、ホスト名、ポートを、ホスト検証のトークンに使用します。

  • [RFC8053]で定義されている認証の拡張は適用できません。

17.1. Security Properties

17.1. セキュリティー特性

  • The protocol is secure against passive eavesdropping and replay attacks. However, the protocol relies on transport security (including DNS integrity) for data secrecy and integrity. HTTP/TLS SHOULD be used where transport security is not assured and/or data confidentiality is important.

  • When used with HTTP/TLS, if TLS server certificates are reliably verified, the protocol provides true protection against active man-in-the-middle attacks.

  • Even if the server certificate is not used or is unreliable, the protocol provides protection against active man-in-the-middle attacks for each HTTP request/response pair. However, in such cases, JavaScript or similar scripts that are not authenticated by this authentication mechanism can affect mutually authenticated contents to circumvent the protection. This is why this protocol stipulates that valid TLS server certificates MUST be shown from the server to the client (Section 7).

  • このプロトコルは、受動的な盗聴とリプレイ攻撃に対して安全です。 ただし、このプロトコルは、データの秘匿性と完全性について、トランスポートのセキュリティー（DNSの完全性を含む）に依存しています。 トランスポートのセキュリティーが保証されない場合、またはデータの機密性が重要である場合、あるいはその両方の場合には、HTTP/TLSを使用するべきです（SHOULD）。

  • HTTP/TLSとともに使用する場合、TLSサーバー証明書が確実に検証されれば、このプロトコルは能動的な中間者攻撃に対する真の保護を提供します。

  • サーバー証明書が使用されない場合や信頼できない場合でも、このプロトコルは、HTTPのリクエストとレスポンスの組ごとに、能動的な中間者攻撃に対する保護を提供します。 ただし、そのような場合、この認証メカニズムによって認証されていないJavaScriptや同様のスクリプトが、相互に認証されたコンテンツに影響を与えて、保護を回避できます。 このため、このプロトコルは、有効なTLSサーバー証明書をサーバーからクライアントに提示しなければなりません（MUST）と規定しています（セクション7）。

17.2. Secrecy of Credentials

17.2. クレデンシャルの秘匿性

The client-side password credential MUST always be kept secret and SHOULD NOT be used for any other (possibly insecure) authentication purposes. Loss of control of the credential will directly affect the control of the corresponding server-side account.

クライアント側のパスワードクレデンシャルは、常に秘密に保たなければなりません（MUST）。 また、他の（安全でない可能性がある）認証の目的に使用するべきではありません（SHOULD NOT）。 クレデンシャルの管理を失うと、対応するサーバー側のアカウントの管理に直接影響します。

The use of a client-side credential with THIS authentication scheme is always safe, even if the connected server peer is not trustworthy (e.g., a phishing scenario). However, if it is used with other authentication schemes (such as Web forms) and the recipient is rogue, the result will be obvious.

接続先のサーバーピアが信頼できない場合（たとえばフィッシングのシナリオ）でも、クライアント側のクレデンシャルを「この」認証スキームで使用することは常に安全です。 しかし、それを他の認証スキーム（Webフォームなど）で使用し、受信者が不正なものであれば、結果は明らかです。

It is also important that the server-side password credential (J) be kept secret. If it is stolen and the client's choice of password is not strong, anyone who is aware of the server-side password credential can employ an offline dictionary attack to search for the client's password. However, if the client has chosen a strong password so that an attacker cannot guess the client's password from dictionary candidates, the client is still well protected from any attacks.

サーバー側のパスワードクレデンシャル（J）を秘密に保つことも重要です。 それが盗まれ、クライアントが選んだパスワードが強力でない場合、サーバー側のパスワードクレデンシャルを知っている人は誰でも、オフライン辞書攻撃を用いてクライアントのパスワードを探索できます。 しかし、攻撃者が辞書の候補からクライアントのパスワードを推測できないほど強力なパスワードをクライアントが選んでいれば、クライアントは依然としてあらゆる攻撃からよく保護されています。

The shared session secret (z) MUST be kept secret inside the server/client software; if it is lost and the session is still active, session hijacking will result. After the session expires, the key is of no value to attackers.

共有のセッション秘密（z）は、サーバーまたはクライアントのソフトウェアの内部で秘密に保たなければなりません（MUST）。 それが漏洩し、セッションがまだ有効であれば、セッションハイジャックが起こります。 セッションの有効期限が切れた後は、その鍵は攻撃者にとって価値がありません。

17.3. Denial-of-Service Attacks on Servers

17.3. サーバーに対するサービス拒否攻撃

The protocol requires a server-side table of active sessions, which may become a critical point for server resource consumption. For proper operation, the protocol requires that at least one key verification request be processed for each session identifier. After that, servers MAY discard sessions internally at any time without causing any operational problems for clients. Clients will then silently re-establish a new session.

このプロトコルは、アクティブなセッションのサーバー側のテーブルを必要とし、これはサーバーのリソース消費の重大な点になる可能性があります。 正しく動作するために、このプロトコルは、各セッション識別子について少なくとも1つの鍵検証リクエストが処理されることを要求します。 その後、サーバーは、クライアントに運用上の問題を一切引き起こすことなく、いつでも内部的にセッションを破棄してもよいです（MAY）。 その場合、クライアントは何も告げずに新しいセッションを再確立します。

However, if a malicious client sends too many requests for key exchanges (req-KEX-C1 messages) only, resource starvation might occur. In such critical situations, servers MAY discard any kind of existing sessions, regardless of their statuses. One way to mitigate such attacks is that servers MAY set number and time limits for unverified, pending key exchange requests (in the "key exchanging" state).

しかし、悪意のあるクライアントが鍵交換のリクエスト（req-KEX-C1メッセージ）だけを大量に送信すると、リソースの枯渇が起こる可能性があります。 このような重大な状況では、サーバーは、状態にかかわらず、既存のあらゆる種類のセッションを破棄してもよいです（MAY）。 このような攻撃を緩和する1つの方法として、サーバーは、（"key exchanging"状態にある）検証されていない保留中の鍵交換リクエストに対して、数と時間の制限を設定してもよいです（MAY）。

This is a common weakness of authentication protocols with almost any kind of negotiations or states, including the Digest authentication scheme and most cookie-based authentication implementations. However, regarding resource consumption, the situation for the Mutual authentication scheme is slightly better than that for Digest, because HTTP requests without any kind of authentication requests will not generate any kind of sessions. Session identifiers are only generated after a client starts a key negotiation, so that simple clients such as Web crawlers will not accidentally consume server-side resources for session management.

これは、Digest認証スキームやほとんどのクッキーベースの認証の実装を含め、ほぼあらゆる種類のネゴシエーションや状態を持つ認証プロトコルに共通する弱点です。 しかし、リソース消費に関しては、Mutual認証スキームの状況はDigestよりもわずかに良好です。 いかなる種類の認証要求も伴わないHTTPリクエストは、いかなる種類のセッションも生成しないためです。 セッション識別子はクライアントが鍵のネゴシエーションを開始した後にのみ生成されるので、Webクローラーのような単純なクライアントが、セッション管理のためにサーバー側のリソースを誤って消費することはありません。

17.3.1. Online Active Password Attacks

17.3.1. オンラインの能動的なパスワード攻撃

Although the protocol provides very strong protection against offline dictionary attacks from eavesdropped traffic, the protocol, by its nature, cannot prevent active password attacks in which an attacker sends so many authentication trial requests for every possible password.

このプロトコルは、盗聴されたトラフィックからのオフライン辞書攻撃に対して非常に強力な保護を提供しますが、その性質上、攻撃者があらゆる可能なパスワードについて大量の認証試行リクエストを送信する能動的なパスワード攻撃を防ぐことはできません。

Possible countermeasures for preventing such attacks may be the rate-limiting of password authentication trials, statistics-based intrusion-detection measures, or similar protection schemes. If the server operators assume that the passwords of users are not strong enough, it may be desirable to introduce such ad hoc countermeasures.

このような攻撃を防ぐための対策としては、パスワード認証の試行に対するレート制限、統計に基づく侵入検知の手段、または同様の保護方式が考えられます。 サーバー運用者がユーザーのパスワードが十分に強力ではないと想定する場合は、このような場当たり的な対策を導入することが望ましいかもしれません。

17.4. Communicating the Status of Mutual Authentication with Users

17.4. 相互認証の状態のユーザーへの伝達

This protocol is designed with two goals in mind. The first goal is simply to provide a secure alternative to existing Basic and Digest authentication schemes. The second goal is to provide users with a way to detect forged rogue servers imitating (e.g., via a phishing attack) a user's registered account on a server.

このプロトコルは、2つの目標を念頭に置いて設計されています。 1つ目の目標は、単に既存のBasicおよびDigest認証スキームに対する安全な代替を提供することです。 2つ目の目標は、サーバー上のユーザーの登録済みアカウントを（たとえばフィッシング攻撃によって）偽装する、偽造された不正なサーバーを検出する方法をユーザーに提供することです。

For this protocol to effectively work as a countermeasure against such attacks, it is very important that end users of clients be notified of the result of mutual authentication performed by this protocol, especially the three states "AUTH-SUCCEED", "AUTH-REQUIRED", and "UNAUTHENTICATED" as defined in Section 10. The design of secure user interfaces for HTTP interactive clients is out of scope for this document, but if possible, having some kind of UI indication for the three states above will be desirable from the standpoint of providing user security.

このプロトコルがそのような攻撃に対する対策として効果的に機能するためには、このプロトコルによって行われた相互認証の結果、特にセクション10で定義されている3つの状態「AUTH-SUCCEED」、「AUTH-REQUIRED」、「UNAUTHENTICATED」を、クライアントのエンドユーザーに通知することが非常に重要です。 HTTPの対話型クライアントのための安全なユーザーインターフェイスの設計はこの文書の範囲外ですが、可能であれば、上記の3つの状態について何らかのUI表示を行うことが、ユーザーのセキュリティーを提供するという観点から望ましいでしょう。

Of course, in such cases, the user interfaces for requesting passwords for this authentication shall be protected against imitation (for example, by other insecure password input fields, such as forms). If the passwords are known to malicious attackers outside of the protocol, the protocol cannot work as an effective security measure.

もちろん、そのような場合、この認証のためにパスワードを要求するユーザーインターフェイスは、（たとえば、フォームなどの他の安全でないパスワード入力フィールドによる）模倣から保護されるものとします。 パスワードがプロトコルの外で悪意のある攻撃者に知られてしまえば、このプロトコルは効果的なセキュリティー対策として機能できません。

17.5. Implementation Considerations

17.5. 実装上の考慮事項

  • To securely implement the protocol, the Authentication-Info headers in the 200-VFY-S messages MUST always be validated by the client. If the validation fails, the client MUST NOT process any content sent with the message, including other headers and the body part. Non-compliance with this requirement will allow phishing attacks.

  • For HTTP/TLS communications, when a Web form is submitted from mutually authenticated pages via the "tls-server-end-point" validation method to a URI that is protected by the same realm (so indicated by the "path" parameter), if the server certificate has been changed since the pages were received, it is RECOMMENDED that the peer be revalidated using a req-KEX-C1 message with an "Expect: 100-continue" header. The same applies when the page is received via the "tls-unique" validation method and when the TLS session has expired.

  • For better protection against possible password database stealing, server-side storage of user passwords should contain the values encrypted by the one-way function J(pi) instead of the real passwords or those hashed by pi.

  • If TLS 1.2 [RFC5246] is used for underlying HTTP/TLS communications, follow the best practices specified in [RFC7525].

  • このプロトコルを安全に実装するために、200-VFY-SメッセージのAuthentication-Infoヘッダーは、常にクライアントによって検証されなければなりません（MUST）。 検証に失敗した場合、クライアントは、他のヘッダーやボディー部分を含め、そのメッセージとともに送信されたいかなるコンテンツも処理してはなりません（MUST NOT）。 この要件に従わないと、フィッシング攻撃が可能になります。

  • HTTP/TLS通信において、「tls-server-end-point」検証方式で相互に認証されたページから、同じレルムで保護された（「path」パラメーターによってそのように示された）URIへWebフォームが送信される場合、ページを受信した後にサーバー証明書が変更されていれば、「Expect: 100-continue」ヘッダーを付けたreq-KEX-C1メッセージを使用してピアを再検証することが推奨されます（RECOMMENDED）。 ページが「tls-unique」検証方式で受信され、TLSセッションの有効期限が切れている場合も同様です。

  • パスワードデータベースが盗まれる可能性に対するより良い保護のために、サーバー側のユーザーパスワードの保存には、実際のパスワードやpiによってハッシュされたものではなく、一方向関数J(pi)によって暗号化された値を格納するべきです。

  • 下位のHTTP/TLS通信にTLS 1.2[RFC5246]を使用する場合は、[RFC7525]で規定されているベストプラクティスに従ってください。

17.6. Usage Considerations

17.6. 利用上の考慮事項

  • The usernames inputted by a user may be sent automatically to any servers sharing the same auth-scope. This means that when a host-type auth-scope is used for authentication on an HTTPS site and an HTTP server on the same host requests the Mutual authentication scheme within the same realm, the client will send the username in clear text. If usernames have to be kept secret (protected from eavesdroppers), the server must use the full-scheme-type "auth-scope" parameter and HTTPS. Passwords, on the other hand, are not exposed to eavesdroppers, even in HTTP requests.

  • If the server provides several ways to store server-side password secrets in the password database, it is desirable, for purposes of better security, to store the values encrypted by using the one-way function J(pi) instead of the real passwords or those hashed by pi.

  • ユーザーが入力したユーザー名は、同じauth-scopeを共有するどのサーバーにも自動的に送信される可能性があります。 これは、HTTPSサイトでの認証にホスト型のauth-scopeが使用され、同じホスト上のHTTPサーバーが同じレルム内でMutual認証スキームを要求した場合、クライアントがユーザー名を平文で送信することを意味します。 ユーザー名を（盗聴者から保護して）秘密に保つ必要がある場合、サーバーは完全スキーム型の「auth-scope」パラメーターとHTTPSを使用しなければなりません。 一方、パスワードは、HTTPリクエストであっても盗聴者に露出することはありません。

  • サーバーがパスワードデータベースにサーバー側のパスワード秘密を格納する方法を複数提供している場合、より良いセキュリティーのために、実際のパスワードやpiによってハッシュされたものではなく、一方向関数J(pi)を使用して暗号化された値を格納することが望ましいです。
