RFC 10067

Path Computation Element Communication Protocol (PCEP) Extensions for Associated Bidirectional Segment Routing (SR) LSPs

RFC 10067

関連付けられた双方向セグメントルーティング（SR）LSPのための経路計算要素通信プロトコル（PCEP）拡張

Abstract

概要

Segment Routing (SR) steers packets through a network using the IPv6 or MPLS data planes via source routing. Stateful Path Computation Element Communication Protocol (PCEP) extensions are defined for SR Traffic Engineering (TE) LSPs.

セグメントルーティング（Segment Routing: SR）は、ソースルーティングにより、IPv6またはMPLSデータプレーンを使用してネットワーク内でパケットを誘導します。 SRトラフィックエンジニアリング（TE）LSPのために、ステートフルな経路計算要素通信プロトコル（Path Computation Element Communication Protocol: PCEP）の拡張が定義されています。

PCEP supports grouping two RSVP-TE signaled, unidirectional MPLS-TE Label-Switched Paths (LSPs) where a path in each direction in a network is grouped into an associated bidirectional LSP. This document extends PCEP support to group two unidirectional SR LSPs into an associated bidirectional SR LSP. The mechanisms defined in this document apply to both stateless and stateful PCEs for PCE-initiated and PCC-initiated LSPs.

PCEPは、RSVP-TEでシグナリングされる2つの単方向MPLS-TEラベルスイッチパス（Label-Switched Path: LSP）をグループ化することをサポートしており、ネットワーク内の各方向のパスは、関連付けられた双方向LSP（associated bidirectional LSP）にグループ化されます。 この文書は、PCEPのサポートを拡張し、2つの単方向SR LSPを関連付けられた双方向SR LSPにグループ化できるようにします。 この文書で定義するメカニズムは、PCE起動LSPとPCC起動LSPの両方について、ステートレスPCEとステートフルPCEの両方に適用されます。

1. Introduction

1. はじめに

Segment Routing (SR) [RFC8402] can be used to steer packets through a network employing source routing. SR can be applied to both MPLS (SR-MPLS) and IPv6 (SRv6) data planes.

セグメントルーティング（Segment Routing: SR）[RFC8402]は、 ソースルーティングを用いてネットワーク内でパケットを誘導するために使用できます。 SRは、MPLS（SR-MPLS）とIPv6（SRv6）の両方のデータプレーンに適用できます。

[RFC5440] describes the Path Computation Element (PCE) Communication Protocol (PCEP). [RFC8231] specifies a set of extensions to PCEP to enable stateful control of Traffic Engineering (TE) Label Switched Paths (LSPs) within and across PCEP sessions. As described in [RFC4655], a PCE can be either stateful or stateless. [RFC8664] specifies extensions to the PCEP for SR networks that allow a stateful PCE to compute and initiate SR TE paths, as well as a Path Computation Client (PCC) to request, report, or delegate them.

[RFC5440]は、経路計算要素（Path Computation Element: PCE） 通信プロトコル（PCEP）を記述しています。 [RFC8231]は、PCEPセッション内およびPCEPセッションをまたいで、 トラフィックエンジニアリング（Traffic Engineering: TE）ラベルスイッチパス（Label Switched Path: LSP）の ステートフルな制御を可能にするPCEPの拡張一式を規定しています。 [RFC4655]で説明されているように、PCEはステートフルとステートレスのどちらにもなり得ます。 [RFC8664]は、SRネットワーク向けのPCEP拡張を規定しており、 これによりステートフルPCEがSR TEパスを計算および起動できるようになり、 また経路計算クライアント（Path Computation Client: PCC）がそれらを要求、報告、または委任できるようになります。

There are features such as directed Bidirectional Forwarding Detection (BFD) [RFC9612] and Performance Measurement [RFC9503] that require the ingress node (PCC) to be aware of the reverse direction SR path. For such features, the reverse SR paths need to be communicated to the ingress nodes (PCCs) using PCEP mechanisms. This allows both endpoint nodes to be aware of the forward and reverse SR paths.

ダイレクテッド双方向フォワーディング検出（directed Bidirectional Forwarding Detection: BFD） [RFC9612]や性能測定（Performance Measurement） [RFC9503]のように、入口 ノード（PCC）が逆方向のSRパスを認識している必要がある機能があります。 そのような機能のためには、PCEPのメカニズムを使用して逆方向のSRパスを入口 ノード（PCC）に伝える必要があります。これにより、両端のエンドポイント ノードが順方向と逆方向のSRパスを認識できるようになります。

An SR Policy [RFC9256] contains one or more Candidate Paths (CPs), which may be computed by a PCE. A Candidate Path of an SR Policy can contain one or more Segment Lists (SLs). In PCEP messages, an SL is encoded as an Explicit Route Object (ERO) as described in Section 4.3 of [RFC8664]. [RFC10066] defines PCEP extensions for carrying multiple SLs in the PCEP messages along with their opposite direction SLs, as described in Section 4.4 of [RFC10066].

SRポリシー[RFC9256]は1つ以上の候補パス（Candidate Path: CP）を含み、候補パスはPCEによって計算されることがあります。 SRポリシーの候補パスは、1つ以上のセグメントリスト（Segment List: SL）を含むことができます。 PCEPメッセージでは、[RFC8664]のSection 4.3で説明されているように、 SLは明示的経路オブジェクト（Explicit Route Object: ERO）としてエンコードされます。 [RFC10066]は、 [RFC10066]のSection 4.4で説明されているように、 複数のSLをその反対方向のSLとともにPCEPメッセージで運ぶためのPCEP拡張を定義しています。

As per [RFC8697], TE LSPs can be associated by adding them to a common association group by a PCEP peer. [RFC9059] uses the association group object to group two unidirectional RSVP-TE LSPs into an associated bidirectional LSP for both stateful and stateless PCE. This document extends this procedure and allows grouping two unidirectional SR LSPs into an associated bidirectional SR LSP for co-routed [RFC9059] and non-co-routed paths. This extension also utilizes the procedure defined in [RFC10066] to carry the multiple EROs and the associated reverse path EROs for an SR LSP. Note that the association group and the procedure introduced in this document are specific to SR-TE and SRv6 Path Setup Types.

[RFC8697]によれば、PCEPピアは、TE LSPを共通の関連付けグループ（association group）に追加することで、 それらを関連付けることができます。 [RFC9059]は、関連付けグループオブジェクトを使用して、ステートフルPCEとステートレスPCEの両方について、 2つの単方向RSVP-TE LSPを関連付けられた双方向LSPにグループ化します。 この文書は、この手順を拡張し、同一経路（co-routed）[RFC9059]および非同一経路（non-co-routed）のパスについて、 2つの単方向SR LSPを関連付けられた双方向SR LSPにグループ化できるようにします。 この拡張は、SR LSPの複数のEROと、関連付けられた逆方向パスのEROを運ぶために、 [RFC10066]で定義されている手順も利用します。 この文書で導入する関連付けグループと手順は、 SR-TEおよびSRv6のパスセットアップタイプ（Path Setup Type）に固有のものであることに注意してください。

2. Terminology

2. 用語

The reader is assumed to be familiar with the terminology defined in [RFC8231], [RFC8281], [RFC8697], [RFC8408], [RFC9059], and [RFC10066].

読者は、 [RFC8231]、[RFC8281]、[RFC8697]、[RFC8408]、 [RFC9059]、[RFC10066]で定義されている用語に精通していることを前提とします。

This document uses the following terms defined in [RFC5440]:

この文書では、[RFC5440]で定義されている次の用語を使用します。

Explicit Route Object (ERO), Path Computation Client (PCC), Path Computation Element (PCE), Path Computation Element Communication Protocol (PCEP), PCEP peer, and PCEP speaker.

明示的経路オブジェクト（Explicit Route Object: ERO）、経路計算クライアント（Path Computation Client: PCC）、経路計算要素（Path Computation Element: PCE）、 経路計算要素通信プロトコル（Path Computation Element Communication Protocol: PCEP）、PCEPピア（PCEP peer）、PCEPスピーカー（PCEP speaker）。

This document extends the following term defined in [RFC3031]: Label Switched Path (LSP) - the base PCEP specification [RFC4655] originally defined the PCE architecture for MPLS and GMPLS networks with LSPs instantiated using the RSVP-TE signaling protocol. As specified in Section 2 of [RFC9603], the term "LSP" used in the PCEP specifications would be equivalent to an SRv6 path (represented as a list of SRv6 segments) in the context of supporting SRv6 in PCEP using the SRv6 Path Setup Type.

この文書は、[RFC3031]で定義されている次の用語を拡張します。 ラベルスイッチパス（Label Switched Path: LSP） - 基本となるPCEP仕様[RFC4655]は、もともと RSVP-TEシグナリングプロトコルを使用してLSPがインスタンス化されるMPLSおよびGMPLSネットワーク向けに、 PCEアーキテクチャーを定義していました。 [RFC9603]のSection 2で規定されているように、 SRv6パスセットアップタイプを使用してPCEPでSRv6をサポートする文脈では、 PCEP仕様で使われる「LSP」という用語は、（SRv6セグメントのリストとして表現される）SRv6パスと同等になります。

4. PCEP Extensions

4. PCEPの拡張

Two unidirectional SR LSPs (one in each direction between two nodes in a network) can be associated together by using the association group defined in this document for the PCEP messages and employing the procedures defined in [RFC9059] and [RFC10066].

2つの単方向SR LSP（ネットワーク内の2つのノード間の各方向に1つずつ）は、 PCEPメッセージでこの文書が定義する関連付けグループを使用し、 [RFC9059]と[RFC10066]で定義されている手順を用いることで、互いに関連付けることができます。

4.1. Bidirectional SR LSP Association Group

4.1. 双方向SR LSP関連付けグループ

For associating two unidirectional SR LSPs, this document defines a new Association Type called "Bidirectional SR LSP Association" for the Association Group object (Class-Value 40) as follows:

2つの単方向SR LSPを関連付けるために、この文書は、 関連付けグループオブジェクト（Class-Value 40）向けに、「Bidirectional SR LSP Association」という 新しい関連付けタイプ（Association Type）を次のとおり定義します。

  • Association Type (value 8) = Bidirectional SR LSP Association

  • 関連付けタイプ（値8） = Bidirectional SR LSP Association

The handling of the Association ID, Association Source, optional Global Association Source and optional Extended Association ID in this association are set as defined in [RFC8697].

この関連付けにおけるAssociation ID、Association Source、オプションの Global Association Source、およびオプションのExtended Association IDの扱いは、 [RFC8697]で定義されているとおりに設定されます。

[RFC8697] specifies the mechanism for the capability advertisement of the Association Types supported by a PCEP speaker by defining an ASSOC-Type-List TLV (value 35) to be carried within an OPEN object. The PCEP speaker MUST include the "Bidirectional SR LSP Association" type in the ASSOC-Type-List TLV and MUST receive the same from the PCEP peer before using it in the PCEP messages.

[RFC8697]は、OPENオブジェクト内で運ばれるASSOC-Type-List TLV（値35）を定義することで、 PCEPスピーカーがサポートする関連付けタイプを能力広告（capability advertisement）するメカニズムを規定しています。 PCEPスピーカーは、ASSOC-Type-List TLVに「Bidirectional SR LSP Association」タイプを含めなければなりません（MUST）。 また、PCEPメッセージでそのタイプを使用する前に、PCEPピアから同じタイプを受信していなければなりません（MUST）。

An SR LSP MUST NOT be part of more than one "Bidirectional SR LSP Association" on a PCE. A PCE, upon detecting this condition, MUST NOT send the associated reverse EROs to the ingress node PCC. This error condition MUST be logged and an alarm MUST be generated.

SR LSPは、PCE上で2つ以上の「双方向SR LSP関連付け」に 属してはなりません（MUST NOT）。 PCEは、この状態を検出した場合、関連付けられた逆方向のEROを入口ノードのPCCに 送信してはなりません（MUST NOT）。 このエラー状態はログに記録されなければなりません（MUST）。また、アラームが生成されなければなりません（MUST）。

4.2. Bidirectional LSP Association Group TLV

4.2. Bidirectional LSP Association Group TLV

A PCEP message for an associated bidirectional SR LSP MAY include the "Bidirectional LSP Association Group TLV" to indicate the co-routed path using the C flag defined in Section 4.2 of [RFC9059].

関連付けられた双方向SR LSPのPCEPメッセージには、 同一経路のパスであることを示すために、「Bidirectional LSP Association Group TLV」を含めてもよいです（MAY）。 その際は、 [RFC9059]のSection 4.2で定義されているCフラグを使用します。

As there is no reverse SR LSP instantiated, the Reverse LSP (R flag) MUST NOT be set for an associated bidirectional SR LSP and MUST be ignored. This error condition MUST be logged and an alarm MUST be generated.

逆方向のSR LSPはインスタンス化されないため、 関連付けられた双方向SR LSPに対してReverse LSP（Rフラグ）を設定してはなりません（MUST NOT）。 また、設定されていても無視されなければなりません（MUST）。このエラー状態はログに記録されなければなりません（MUST）。また、アラームが生成されなければなりません（MUST）。

4.3. PATH-ATTRIB Object

4.3. PATH-ATTRIBオブジェクト

When a PCE informs an ingress node PCC about the associated reverse SR LSP EROs computed for an SR LSP with the "Bidirectional SR LSP Association", it MUST include the "PATH-ATTRIB" object with the Reverse (R flag) set to 1 to indicate that the ERO is for the reverse direction [RFC10066].

PCEは、「双方向SR LSP関連付け」を持つSR LSPについて計算した、関連付けられた逆方向SR LSPのEROを入口ノードのPCCに通知する際、 そのEROが逆方向のものであることを示すために、Reverse（Rフラグ）を1に設定した 「PATH-ATTRIB」オブジェクトを含めなければなりません（MUST）[RFC10066]。

4.4. MULTIPATH-OPPDIR-PATH TLV

4.4. MULTIPATH-OPPDIR-PATH TLV

The PCE MAY include the "MULTIPATH-OPPDIR-PATH TLV" to indicate the co-routed path properties (in the N-flag and L-flag) for the reverse ERO [RFC10066] for an SR LSP.

PCEは、SR LSPの逆方向ERO [RFC10066]について、（NフラグとLフラグで）同一経路のパスの特性を示すために、 「MULTIPATH-OPPDIR-PATH TLV」を含めてもよいです（MAY）。

The PCC MUST detect the mismatch between the co-routed path properties in the "MULTIPATH-OPPDIR-PATH TLV" for the reverse ERO and the co-routed path (C) flag in the "Bidirectional LSP Association Group TLV" for the (forward) SR LSP and log it as an error condition and generate an alarm.

PCCは、逆方向EROの「MULTIPATH-OPPDIR-PATH TLV」における同一経路のパスの特性と、 （順方向の）SR LSPの「Bidirectional LSP Association Group TLV」における同一経路（C）フラグとの不一致を 検出し、それをエラー状態としてログに記録し、アラームを生成しなければなりません（MUST）。

5. Additional PCEP Considerations

5. PCEPに関する追加の考慮事項

Additional considerations for associating bidirectional SR LSPs are summarized in the subsections below.

双方向SR LSPを関連付けるための追加の考慮事項を、以下のサブセクションにまとめます。

5.1. PLSP-ID Usage

5.1. PLSP-IDの使用

As per [RFC8231], an ingress node PCC reports a unique PLSP-ID for each LSP of an SR Policy. For an associated bidirectional SR LSP, the PCE will maintain two PLSP-IDs, one from the ingress node PCC and one from the egress node PCC. In the examples shown in Figures 2 and 3, the ingress node PCC (node S) reports Tunnel 1, LSP1 to the PCE with PLSP-ID 100 whereas the egress node PCC (node D) reports Tunnel 2, LSP2 to the PCE with PLSP-ID 200.

[RFC8231]によれば、入口ノードのPCCは、SRポリシーの各LSPについて一意なPLSP-IDを報告します。 関連付けられた双方向SR LSPについては、 PCEは入口ノードのPCCからのものと出口ノードのPCCからのものの、2つのPLSP-IDを保持します。 図2と図3に示す例では、入口ノードのPCC（ノードS）はTunnel 1のLSP1をPLSP-ID 100でPCEに報告し、 一方、出口ノードのPCC（ノードD）はTunnel 2のLSP2をPLSP-ID 200でPCEに報告します。

5.2. Error Handling

5.2. エラー処理

The error handling as described in Section 5.7 of [RFC9059] continues to apply for the "Bidirectional SR LSP Association".

[RFC9059]のSection 5.7で説明されているエラー処理は、 「双方向SR LSP関連付け」にも引き続き適用されます。

The PCEP Path Setup Type (PST) for SR LSP uses either value "1: Traffic-engineering path is set up using Segment Routing" [RFC8664] or "3: Traffic engineering path is set up using SRv6" [RFC9603]. If a PCEP speaker receives a non-SR LSP PST value for the "Bidirectional SR LSP Association", the PCEP speaker MUST return a PCErr message with Error-Type = 26 (Association Error) and Error-value = "16: Path Setup Type not supported" [RFC9059].

SR LSPのPCEPパスセットアップタイプ（Path Setup Type: PST）には、値「1: Traffic-engineering path is set up using Segment Routing」 [RFC8664]または「3: Traffic engineering path is set up using SRv6」[RFC9603]のいずれかを使用します。 PCEPスピーカーは、「双方向SR LSP関連付け」についてSR LSP以外のPST値を受信した場合、 Error-Type = 26（Association Error）およびError-value = 「16: Path Setup Type not supported」[RFC9059]を持つ PCErrメッセージを返さなければなりません（MUST）。

6. Security Considerations

6. セキュリティーに関する考慮事項

The security considerations described in [RFC5440], [RFC8231], [RFC8281], [RFC8408], [RFC9059], and [RFC10066] apply to the extensions defined in this document as well.

[RFC5440]、 [RFC8231]、[RFC8281]、[RFC8408]、[RFC9059]、 [RFC10066]で説明されているセキュリティーに関する考慮事項は、この文書で定義する拡張にも適用されます。

A new Association Type for the Association object, "Bidirectional SR LSP Association", is introduced in this document. Additional security considerations related to LSP associations due to a malicious PCEP speaker are described in [RFC8697] and apply to this Association Type. Hence, securing the PCEP session using Transport Layer Security (TLS) [RFC8253], [RFC9916], as per the recommendations and best current practices in [RFC9325] is RECOMMENDED.

この文書では、Associationオブジェクトの新しい関連付けタイプとして 「Bidirectional SR LSP Association」を導入します。 悪意のあるPCEPスピーカーに起因するLSPの関連付けに関する追加のセキュリティーの考慮事項は [RFC8697]で説明されており、この関連付けタイプにも適用されます。したがって、 [RFC9325]の推奨事項とベストカレントプラクティスに従い、 トランスポート層セキュリティー（Transport Layer Security: TLS）[RFC8253]、[RFC9916]を使用して PCEPセッションを保護することが推奨されます（RECOMMENDED）。

7. Operational Considerations

7. 運用に関する考慮事項

The manageability requirements and considerations listed in [RFC5440], [RFC8231], [RFC8281], [RFC8697], and [RFC10066] apply to the PCEP protocol extensions defined in this document. In addition, the operational requirements and considerations listed in this section apply.

[RFC5440]、[RFC8231]、[RFC8281]、[RFC8697]、 [RFC10066]に挙げられている管理性の要件と考慮事項は、この文書で定義するPCEPプロトコル拡張に適用されます。 さらに、このセクションに挙げる運用上の要件と考慮事項が適用されます。

7.1. Control of Function and Policy

7.1. 機能とポリシーの制御

The mechanisms defined in this document do not imply any new control or policy requirements.

この文書で定義するメカニズムは、新たな制御要件やポリシー要件を伴いません。

7.2. Information and Data Models

7.2. 情報モデルとデータモデル

[RFC7420] describes the PCEP MIB; there are no new MIB Objects defined for LSP associations.

[RFC7420]はPCEP MIBを記述していますが、 LSPの関連付けのために定義された新しいMIBオブジェクトはありません。

The PCEP YANG module [RFC9826] defines a data model for LSP associations. However, it does not include information for associated bidirectional SR LSPs. It can be extended to include data related to the associated bidirectional SR LSPs, such as:

PCEP YANGモジュール[RFC9826]は、LSPの関連付けのためのデータモデルを定義しています。 ただし、関連付けられた双方向SR LSPの情報は含まれていません。 このモジュールは、次のような、関連付けられた双方向SR LSPに関するデータを含むように拡張できます。

  • Indication of whether the associated bidirectional SR LSPs are supported
  • Enablement and disablement of the bidirectional SR LSP association
  • Counters for the successfully associated bidirectional SR LSPs
  • Counters for the SR LSPs that failed to form a bidirectional association
  • 関連付けられた双方向SR LSPがサポートされているかどうかの表示
  • 双方向SR LSP関連付けの有効化と無効化
  • 関連付けに成功した双方向SR LSPのカウンター
  • 双方向の関連付けの形成に失敗したSR LSPのカウンター

7.3. Liveness Detection and Monitoring

7.3. 生存性検出と監視

Mechanisms defined in this document do not imply any new liveness detection and monitoring requirements as they are performed independently on both sides of a bidirectional SR LSP, using the forward and reverse LSP paths of the bidirectional SR LSP. However, the monitoring on both sides of a bidirectional SR LSP needs to be correlated at the management level to ensure that the bidirectional service carried by the bidirectional SR LSP is operational.

この文書で定義するメカニズムは、新たな生存性検出と監視の要件を伴いません。 生存性検出と監視は、双方向SR LSPの順方向と逆方向のLSPパスを使用して、双方向SR LSPの両側でそれぞれ独立に実行されるためです。 ただし、双方向SR LSPによって運ばれる双方向サービスが動作していることを確認するために、 双方向SR LSPの両側での監視を管理レベルで相関させる必要があります。

7.4. Verify Correct Operations

7.4. 正しい動作の検証

Mechanisms defined in this document do not imply any new operation verification requirements.

この文書で定義するメカニズムは、新たな動作検証の要件を伴いません。

7.5. Requirements on Other Protocols

7.5. 他のプロトコルに対する要件

Mechanisms defined in this document do not imply any new requirements on other protocols.

この文書で定義するメカニズムは、他のプロトコルに対する新たな要件を伴いません。

7.6. Impact on Network Operations

7.6. ネットワーク運用への影響

Associating two SR LSPs to form an associated bidirectional SR LSP requires an operator to ensure that the correct LSP associations are employed on both sides of the bidirectional SR LSP. Tools such as directed BFD [RFC9612] and Performance Measurement [RFC9503] can be used to verify the correct operation of a bidirectional SR LSP.

2つのSR LSPを関連付けて関連付けられた双方向SR LSPを形成するには、 オペレーターは双方向SR LSPの両側で正しいLSPの関連付けが用いられていることを確認する必要があります。 双方向SR LSPが正しく動作していることを検証するために、ダイレクテッドBFD [RFC9612]や性能測定 [RFC9503]などのツールを使用できます。
