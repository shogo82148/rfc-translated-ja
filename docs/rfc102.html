RFC 102

Output of the Host/Host Protocol glitch cleaning committee

RFC 102

ホスト間プロトコル不具合一掃委員会の成果

Abstract

概要

At the NWG meeting in Urbana on 17-19 February 1971, a committee was established to look at the Host/Host protocol and see what changes were immediately desirable or necessary.

1971年2月17日〜19日にUrbanaで開催されたNWG会議で、ホスト間（Host/Host）プロトコルを検討し、どのような変更がただちに望ましいか、または必要かを確認するための委員会が設立されました。

The committee is chaired by Steve Crocker, and has eight other members:

A number of topics were discussed. On some of these topics, a consensus was reached on whether or not to recommend a change, and if so, what the change should be. On the remaining topics, specific alternatives were proposed but no consensus was reached.

いくつかの議題について議論しました。一部の議題については、変更を推奨するかどうか、推奨する場合はどのような変更にすべきかについて合意に達しました。残りの議題については、具体的な代替案が提案されましたが、合意には至りませんでした。

The committee will immediately canvas the network community and gather reaction to its recommendations and the proposed alternatives. The committee will then reconvene at UCLA on 8 March 1971 and decide on final recommendations. Steve Crocker will then write Document #2. This sequence is in lieu of the change procedure outlined in NWG/RFC 53.

委員会はただちにネットワークコミュニティーの意見を聞き、委員会の推奨事項と提案された代替案に対する反応を集めます。その後、委員会は1971年3月8日にUCLAで再び会合を開き、最終的な推奨事項を決定します。その後、Steve CrockerがDocument #2を執筆します。この手順は、NWG/RFC 53で概説されている変更手続きの代わりとなるものです。

Specific Recommendations

具体的な推奨事項

  1. The ECO and ERP command should each be 8 bits long.
  2. The ERR command should be 96 bits long.
  3. Message Data Types should be eliminated. Third-level protocol people may reinstate such a mechanism.
  4. The Cease mechanism should be discontinued.
  5. A new pair of one byte commands RST (reset) and RRP (reset reply) should be added. The RST should be interpreted as a signal to purge the NCP tables of any existing entries which arose from the sending Host. The RRP command should be returned to acknowledge receipt of the RST. The Host sending the RST may proceed after receiving either a RST or a RRP in return. A RST may be returned if the second Host comes up after the first Host.
  6. Although it was suggested at the Urbana meeting that connections should be full-duplex, the committee recommends against this change.

  7. Messages should be an integral number of bytes, and the number of bytes and the byte size should be specified in each message. The marking convention should be abandoned and the padding ignored.

    The number of bytes in the message should be a 16-bit number following the leader. The byte size should be in the next 8-bit field. Two suggestions were generated for the starting point of the text, and these are explained in the next session.

    For flow control purposes, the number of bits in a message is the product of the number of bytes and the byte size. The leader and other fixed format fields are not counted.

  8. The problem of synchronizing the interrupt signal in a console input stream was considered. We consider the console input scanner as a process and note two reasonable implementations: it may either read characters as fast as it can, looking for the interrupt character and throwing away characters if there is no room in the user process' input queue; it may read characters only as fast as the user process can receive them, (or at least has room for them).
  1. ECOコマンドとERPコマンドは、それぞれ8ビット長にすべきです。
  2. ERRコマンドは96ビット長にすべきです。
  3. メッセージデータタイプ（Message Data Types）は廃止すべきです。第3レベルのプロトコルの担当者が、そのような仕組みを復活させてもかまいません。
  4. Cease（中止）の仕組みは廃止すべきです。
  5. 1バイトのコマンドの新しい組として、RST（reset、リセット）とRRP（reset reply、リセット応答）を追加すべきです。RSTは、送信元ホストに由来する既存のエントリーをNCPのテーブルから一掃する合図として解釈すべきです。RSTの受信を確認するために、RRPコマンドを返すべきです。RSTを送信したホストは、RSTかRRPのどちらかを返信として受信した後に処理を進めてかまいません。2番目のホストが最初のホストより後に起動した場合は、RSTが返されることがあります。
  6. Urbanaの会議では、接続を全二重にすべきだという提案がありましたが、委員会はこの変更に反対することを推奨します。

  7. メッセージは整数個のバイトで構成されるべきであり、バイト数とバイトサイズを各メッセージで指定すべきです。マーキングの規約は廃止し、パディングは無視すべきです。

    メッセージ内のバイト数は、リーダーに続く16ビットの数値にすべきです。バイトサイズは、その次の8ビットのフィールドに置くべきです。テキストの開始位置については2つの提案が出されており、それらは次のセッションで説明します。

    フロー制御の目的では、メッセージ内のビット数は、バイト数とバイトサイズの積です。リーダーやその他の固定形式のフィールドは数えません。

  8. コンソールの入力ストリームにおける割り込み信号の同期の問題を検討しました。コンソールの入力スキャナーを1つのプロセスとみなすと、2つの妥当な実装があります。1つは、可能な限り速く文字を読み取り、割り込み文字を探して、ユーザープロセスの入力キューに空きがなければ文字を捨てるものです。もう1つは、ユーザープロセスが受け取れる速さで（または少なくともそれらを受け入れる空きがある範囲で）だけ文字を読み取るものです。

The first implementation guarantees that the interrupt character (e.g., control - C on the PDP-10 10/50) will always be acted on, but requires that the using process interpret the output stream to detect when it is sending too fast. The second implementation avoids overrun but may not allow for sending an interrupt code. Note that in the first case, allocation is alway renewed as soon as possible by the console input interpreter; whereas in the second case, allocation is renewed only as the result of acceptance of data by the user process.

1つ目の実装では、割り込み文字（たとえばPDP-10 10/50のcontrol - C）が必ず処理されることが保証されますが、使用側のプロセスが出力ストリームを解釈して、送信が速すぎることを検出する必要があります。2つ目の実装ではオーバーランを避けられますが、割り込みコードを送信できない場合があります。1つ目の場合では、コンソール入力インタープリターによって割り当てが常にできるだけ早く更新されるのに対し、2つ目の場合では、ユーザープロセスがデータを受け入れた結果としてのみ割り当てが更新されることに注意してください。

We decided that this is really a third-level protocol matter, viz, use the INS to mean that a special code has been inserted into the input stream. In conjunction with this, create the special code to be put into the input sequence.

私たちは、これは実際には第3レベルのプロトコルの問題であると判断しました。つまり、INSを使って、特別なコードが入力ストリームに挿入されたことを示すということです。これに合わせて、入力シーケンスに入れる特別なコードを作ります。

This special code would be network-wide and independent of the particular interrupt character peculiar to the serving system. The scheme for interrupting a serving process is that the using process inserts the serving Host's interrupt sequence, followed by the network special code, and also issue the INS.

この特別なコードはネットワーク全体で共通のものであり、サービスを提供するシステムに固有の割り込み文字とは独立したものです。サービスを提供するプロセスに割り込む方式は、使用側のプロセスが、サービスを提供するホストの割り込みシーケンスに続けてネットワークの特別なコードを挿入し、さらにINSを発行するというものです。

UNRESOLVED ALTERNATIVES

未解決の代替案

1. Length of Control Messages

1. 制御メッセージの長さ

In accordance with other specifications, control messages should be an integral number of 8-bit bytes, the length should be specified in the byte count field, and control commands should not be split across messages.

他の仕様に従って、制御メッセージは整数個の8ビットバイトで構成されるべきであり、その長さはバイト数フィールドで指定すべきであり、制御コマンドを複数のメッセージに分割すべきではありません。

Unresolved was whether to specially limit the length of control messages. The two choices are.

未解決なのは、制御メッセージの長さを特別に制限するかどうかです。2つの選択肢は次のとおりです。

  1. no special limit ( ~ 1000 bytes)
  2. 120 bytes
  1. 特別な制限なし（〜1000バイト）
  2. 120バイト

2. Message Format

2. メッセージ形式

It was agreed to abandon marking and include the text length in the form of a byte count and byte size. Unresolved was where to begin the first byte of data. The two choices are:

マーキングを廃止し、テキストの長さをバイト数とバイトサイズの形で含めることで合意しました。未解決なのは、データの最初のバイトをどこから始めるかです。2つの選択肢は次のとおりです。

  1. have the first data byte begin after 72 bits of leader, byte count, byte size and spacing. The message format would then be as in the diagram:

                  <------------16------------>
               __________________________
              |                          |
              |_ _ _ _  LEADER   _ _ _ _ |
              |                          |
              |__________________________|
              |                          |
              |        BYTE COUNT        |
              |__________________________|
              |            |             |
BYTE SIZE-----|---->       |             |
              |____________|_____________|
              |            |             |
              |            |<------------|--Beginning of first
              |____________|_____________|       data byte
              |                          |
              |                          |

  2. use the double physical transmission scheme presented in NWG/RFC 67. When sending a regular message, the Host would send a leader, byte count and byte size and terminate transmission. The second transmission would be the data.

    At the receiving end, the IMP would transmit 64 bits of leader, byte count, byte size and spacing, and stop transmission. The next transmission would be only the data.

  1. 最初のデータバイトを、リーダー、バイト数、バイトサイズ、スペーシングの72ビットの後から始める。その場合、メッセージ形式は次の図のようになります。

                  <------------16------------>
               __________________________
              |                          |
              |_ _ _ _  LEADER   _ _ _ _ |
              |                          |
              |__________________________|
              |                          |
              |        BYTE COUNT        |
              |__________________________|
              |            |             |
BYTE SIZE-----|---->       |             |
              |____________|_____________|
              |            |             |
              |            |<------------|--Beginning of first
              |____________|_____________|       data byte
              |                          |
              |                          |

  2. NWG/RFC 67で提示された二重物理送信方式を使う。通常のメッセージを送信するとき、ホストはリーダー、バイト数、バイトサイズを送信して送信を終了します。2回目の送信がデータになります。

    受信側では、IMPはリーダー、バイト数、バイトサイズ、スペーシングの64ビットを送信して、送信を停止します。次の送信はデータだけになります。

3. Allocation

3. 割り当て

With respect to the allocation mechanism embodied in the ALL, GVB and RET commands, two alternatives were proposed:

ALL、GVB、RETコマンドで具体化されている割り当ての仕組みについて、2つの代替案が提案されました。

  1. make no change.
  2. The flow control algorithm should be changed to keep track of two quantities: messages and bits. The ALL, GVB, and RET commands each have two data fields. The ALL command allocates a message limit and a bit limit. The GVB command contains two fractions, and the RET command returns both messages and bits. When sending a message, the sending NCP decrements its message counter by 1 and its bit counter by the text length of the message. The sending NCP may not cause either of its counters to go negative. The message counter would be 16 bits long.
  1. 変更しない。
  2. フロー制御アルゴリズムを変更して、メッセージとビットの2つの量を追跡するようにする。ALL、GVB、RETの各コマンドは2つのデータフィールドを持ちます。ALLコマンドは、メッセージの上限とビットの上限を割り当てます。GVBコマンドは2つの割合を含み、RETコマンドはメッセージとビットの両方を返却します。メッセージを送信するとき、送信側のNCPは、メッセージカウンターを1減らし、ビットカウンターをメッセージのテキストの長さだけ減らします。送信側のNCPは、どちらのカウンターも負にしてはなりません。メッセージカウンターは16ビット長になります。
