Security Automation and Continuous Monitoring (SACM) Requirements

RFC 8248

セキュリティー自動化と継続的監視（SACM）の要件

Abstract

概要

This document defines the scope and set of requirements for the Security Automation and Continuous Monitoring (SACM) architecture, data model, and transfer protocols. The requirements and scope are based on the agreed-upon use cases described in RFC 7632.

この文書は、セキュリティー自動化と継続的監視（Security Automation and Continuous Monitoring、SACM）のアーキテクチャー、データモデル、転送プロトコルの範囲と要件一式を定義します。 要件と範囲は、RFC 7632で記述された合意済みのユースケースに基づいています。

1. Introduction

1. はじめに

Today's environment of rapidly evolving security threats highlights the need to automate the sharing of security information (such as posture information) while protecting user information and the systems that store, process, and transmit this information. Security threats can be detected in a number of ways. The Security Automation and Continuous Monitoring (SACM) charter focuses on how to collect and share this information based on use cases that involve posture assessment of endpoints.

急速に進化するセキュリティー上の脅威にさらされる今日の環境では、ユーザー情報と、その情報を保存、処理、送信するシステムを保護しながら、（ポスチャー情報などの）セキュリティー情報の共有を自動化する必要性が浮き彫りになっています。 セキュリティー上の脅威は、さまざまな方法で検出できます。 SACMの憲章は、エンドポイントのポスチャー評価を伴うユースケースに基づいて、この情報をどのように収集し共有するかに焦点を当てています。

Scalable and sustainable collection, expression, and evaluation of endpoint information is foundational to SACM's objectives. To secure and defend a network, one must reliably determine what devices are on the network, how those devices are configured from a hardware perspective, what software products are installed on those devices, and how those products are configured. We need to be able to determine, share, and use this information in a secure, timely, consistent, and automated manner to perform endpoint posture assessments.

エンドポイント情報をスケーラブルかつ持続的に収集、表現、評価することは、SACMの目的の基盤です。 ネットワークを保護し防御するには、ネットワーク上にどのようなデバイスがあるか、それらのデバイスがハードウェアの観点からどのように構成されているか、それらのデバイスにどのようなソフトウェア製品がインストールされているか、それらの製品がどのように構成されているかを確実に判断しなければなりません。 エンドポイントのポスチャー評価を実行するには、この情報を安全、適時、一貫性のある、自動化された方法で判断、共有、使用できる必要があります。

This document focuses on describing the requirements for facilitating the exchange of posture assessment information in the enterprise, in particular, for the use cases as exemplified in [RFC7632].

この文書は、企業内でのポスチャー評価情報の交換を促進するための要件、とくに[RFC7632]で例示されているユースケースのための要件を記述することに焦点を当てています。

As proposals are evaluated for SACM standardization, the documents describing each proposal are expected to include a section that describes how the enumerated requirements are addressed.

SACMの標準化に向けて提案が評価される際には、各提案を記述する文書に、列挙された要件にどのように対処するかを記述するセクションが含まれることが期待されます。

This document uses terminology defined in [TERMS].

この文書では、[TERMS]で定義された用語を使用します。

2. Requirements

2. 要件

This document defines requirements based on the SACM use cases described in [RFC7632]. This section describes the requirements used by SACM to assess and compare candidate data models, interfaces, and protocols. These requirements express characteristics or features that a candidate protocol, information model, or data model must be capable of offering to ensure security and interoperability.

この文書は、[RFC7632]で記述されたSACMのユースケースに基づいて要件を定義します。 このセクションでは、SACMが候補となるデータモデル、インターフェイス、プロトコルを評価し比較するために使用する要件を記述します。 これらの要件は、セキュリティーと相互運用性を確保するために、候補となるプロトコル、情報モデル、データモデルが提供できなければならない特性や機能を表しています。

Multiple data models, protocols, and transfers may be employed in a SACM environment. A SACM transfer protocol is one that runs on top of transport-layer protocols such as TCP/IP or internet-layer protocols such as HTTP, carries operations (requests/responses), and moves data.

SACM環境では、複数のデータモデル、プロトコル、転送が使用される場合があります。 SACM転送プロトコルとは、TCP/IPなどのトランスポート層プロトコルや、HTTPなどのインターネット層プロトコルの上で動作し、操作（リクエスト／レスポンス）を運び、データを移動させるものです。

SACM will define an architecture and information model focused on addressing the needs for determining, sharing, and using posture information securely via posture information providers and posture information consumers. With the information model defining assets and attributes to facilitate the guidance, collection, and assessment of posture, tasks that should be considered include:

SACMは、ポスチャー情報プロバイダーとポスチャー情報コンシューマーを介してポスチャー情報を安全に判断、共有、使用するというニーズへの対処に焦点を当てたアーキテクチャーと情報モデルを定義します。 ポスチャーのガイダンス、収集、評価を促進するための資産と属性を情報モデルが定義することを前提として、検討すべきタスクには次のものがあります。

  1. Asset Classification: Map the target endpoint and/or the assets on the target endpoints to asset classes. This enables identification of the attributes needed to exchange information pertaining to the target endpoint.
  2. Attribute Definition: Define the attributes desired to be collected from each target endpoint. For instance, organizations will want to know what software is installed and its critical security attributes such as patch level.
  3. Policy Definition: This is where an organization can express its policy for acceptable or problematic values of an endpoint attribute. The expected values of an endpoint attribute are determined for later comparison against the actual endpoint attribute values during the evaluation process. Expected values may include both values that are good as well as values that represent problems, such as vulnerabilities. The organization can also specify the endpoint attributes that are to be present for a given target endpoint.
  4. Information Collection: Collect information (attribute values) from the target endpoint to populate the endpoint data.
  5. Endpoint Assessment: Evaluate the actual values of the endpoint attributes against those expressed in the policy. (An evaluation result may become additional endpoint data.)
  6. Result Reporting: Report the results of the evaluation for use by other components. Examples of the use of a report would be additional evaluation, network enforcement, vulnerability detection, and license management.
  1. 資産の分類（Asset Classification）: ターゲットエンドポイント、またはターゲットエンドポイント上の資産、あるいはその両方を資産クラスに対応付けます。 これにより、ターゲットエンドポイントに関する情報を交換するために必要な属性を特定できます。
  2. 属性の定義（Attribute Definition）: 各ターゲットエンドポイントから収集したい属性を定義します。 たとえば、組織は、どのようなソフトウェアがインストールされているか、そしてパッチレベルなどのその重要なセキュリティー属性を知りたいと考えるでしょう。
  3. ポリシーの定義（Policy Definition）: ここで、組織はエンドポイント属性の値として許容できるもの、または問題のあるものについてのポリシーを表現できます。 エンドポイント属性の期待値は、後で評価プロセスにおいて実際のエンドポイント属性値と比較するために決定されます。 期待値には、良好な値と、脆弱性などの問題を表す値の両方が含まれる場合があります。 組織は、特定のターゲットエンドポイントに存在すべきエンドポイント属性を指定することもできます。
  4. 情報の収集（Information Collection）: ターゲットエンドポイントから情報（属性値）を収集し、エンドポイントデータを埋めます。
  5. エンドポイントの評価（Endpoint Assessment）: エンドポイント属性の実際の値を、ポリシーで表現された値と照らし合わせて評価します。 （評価結果は、追加のエンドポイントデータになる場合があります。）
  6. 結果の報告（Result Reporting）: ほかのコンポーネントが使用できるように評価結果を報告します。 報告の使用例としては、追加の評価、ネットワークでの強制、脆弱性の検出、ライセンス管理などがあります。

2.1. Requirements for SACM

2.1. SACMの要件

Many deployment scenarios can be instantiated to address the above tasks and the use cases defined in [RFC7632]. To ensure interoperability, scalability, and flexibility in any of these deployments, the following requirements are defined for proposed SACM standards:

上記のタスクと[RFC7632]で定義されたユースケースに対処するために、多くの展開シナリオを具体化できます。 これらのどの展開においても相互運用性、スケーラビリティー、柔軟性を確保するために、提案されるSACM標準に対して次の要件を定義します。

G-001 (Solution Extensibility):

The information model, data models, protocols, and transfers defined by SACM MUST be designed to allow support for future extensions. SACM MUST allow for both standardized and proprietary extensions.

  1. The information model and programmatic interfaces (see G-012 for one example) MUST support the ability to add new operations while maintaining backwards compatibility. SACM-defined transfer protocols MUST have extensibility to allow them to transfer operations that are defined in the future.
  2. The query language MUST allow for general inquiries as well as expression of specific attributes or relationships between attributes; the retrieval of specific information based on an event or on a continuous basis; and the ability to retrieve specific pieces of information, specific types or classes of information, or the entirety of available information.
  3. The information model MUST accommodate the interoperable addition of new data types and/or schemas.
G-002 (Interoperability):
The data models, protocols, and transports MUST be specified with enough details to ensure interoperability.
G-003 (Scalability):

SACM needs to support a broad set of deployment scenarios. The data models, protocols, and transports have to be scalable unless they are specifically defined to apply to a special-purpose scenario, such as constrained devices. A SACM transfer protocol standard SHOULD include a section on scalability considerations that addresses the number of endpoints and amount of information to which it can reasonably be expected to scale. Scalability must be addressed to support:

  • Large messages: It is possible that the size of posture assessment information can vary from a single assessment that is small in size to a very large message or a very large set of assessments (up to multiple gigabytes in size).
  • Large number of messages per second: A deployment may involve many rapid or simultaneous events that require processing, generating many messages per second.
  • Large number of providers and consumers: A deployment may consist of a very large number of endpoints requesting and/or producing posture assessment information.
  • Large number of target endpoints: A deployment may be managing information of a very large number of target endpoints.
G-004 (Versatility):
The data model, protocols, and transports must be suitably specified to enable implementations to fit into different deployment models and scenarios, including considerations for implementations of data models and transports operating in constrained environments. Separate solutions may be necessary to meet the needs of specific deployment models and scenarios.
G-005 (Information Extensibility):
Non-standard (implementation-specific) attributes MUST be supported. A method SHOULD be defined for preventing collisions from occurring in the naming of all attributes independent of their source. For interoperability and scope boundary, the information model MUST define the mandatory set of attributes.
G-006 (Data Protection):
To protect the information being shared, SACM components MUST protect the integrity and confidentiality of data in transit (end to end) and data at rest (as information is stored in repositories). Mechanisms for this protection are unspecified but should include industry best practices. These mechanisms are required to be available (i.e., all data-handling components must support them) but are not required to be used in all cases.
G-007 (Data Partitioning):
A method for partitioning data MUST be supported to accommodate considerations such as geographic, regulatory, operational requirements, overlay boundaries, and federation (where the data may be collected in multiple locations and either centralized or kept in the local region). Where replication of data is supported, it is required that methods exist to prevent update loops.
G-008 (Versioning and Backward Compatibility):
Announcement and negotiation of versions, inclusive of existing capabilities (such as transfer protocols, data models, specific attributes within data models, standard attribute expression sets, etc.) MUST be supported. Negotiation for both versioning and capabilities is needed to accommodate future growth and ecosystems with mixed capabilities.
G-009 (Information Discovery):
There MUST be mechanisms for components to discover what information is available across the ecosystem (i.e., a method for cataloging data available in the ecosystem and advertising it to consumers), where to go to get a specific piece of that information (i.e., which provider has the information), and what schemas are in use for organizing the information. For example, a method can be provided by which a node can locate the advertised information so that consumers are not required to have a priori knowledge to find available information.
G-010 (Target Endpoint Discovery):
SACM MUST define the means by which target endpoints may be discovered. The use case in Section 2.1.2 of [RFC7632] describes the need to discover endpoints and their composition.
G-011 (Push and Pull Access):
Three methods of data access MUST be supported: a Pull model, a solicited Push model, and an unsolicited Push model. All of the methods of data access MUST support the ability for the initiator to filter the set of posture assessment information to be delivered. Additionally, the provider of the information MUST be able to filter the set of posture assessment information based on the permissions of the recipient. This requirement is driven by the use cases in Sections 2.1.3 and 2.1.4 of [RFC7632].
G-012 (SACM Component Interface):
The interfaces by which SACM components communicate to share endpoint posture information MUST be well defined. That is, the interface defines the data model, SACM transfer protocols, and network transfer protocols to enable SACM components to communicate.
G-013 (Endpoint Location and Network Topology):
The SACM architecture and interfaces MUST allow for the target endpoint (network) location and network topology to be modeled and understood. Where appropriate, the data model and the interfaces SHOULD allow for discovery of the target endpoint location, network topology, or both.
G-014 (Target Endpoint Identity):
The SACM architecture and interfaces MUST support the ability of components to provide attributes that can be used to compose an identity for a target endpoint. These identities MAY be composed of attributes from one or more SACM components.
G-015 (Data Access Control):
Methods of access control must be supported to accommodate considerations such as geographic, regulatory, operational, and federations. Entities accessing or publishing data MUST identify themselves and pass access policy.
G-001（ソリューションの拡張性）:

SACMが定義する情報モデル、データモデル、プロトコル、転送は、将来の拡張をサポートできるように設計しなければなりません（MUST）。 SACMは、標準化された拡張と独自の拡張の両方を許容しなければなりません（MUST）。

  1. 情報モデルとプログラムインターフェイス（一例としてG-012を参照）は、後方互換性を維持しながら新しい操作を追加する能力をサポートしなければなりません（MUST）。 SACMで定義する転送プロトコルは、将来定義される操作を転送できるような拡張性を備えている必要があります（MUST）。
  2. クエリー言語は、一般的な問い合わせだけでなく、特定の属性や属性間の関係の表現、イベントに基づくまたは継続的な特定の情報の取得、そして特定の情報片、特定の種類やクラスの情報、または利用可能な情報全体を取得する能力を許容しなければなりません（MUST）。
  3. 情報モデルは、新しいデータ型やスキーマ、あるいはその両方を相互運用可能な形で追加できるようにしなければなりません（MUST）。
G-002（相互運用性）:
データモデル、プロトコル、トランスポートは、相互運用性を確保するのに十分な詳細さで規定しなければなりません（MUST）。
G-003（スケーラビリティー）:

SACMは、幅広い展開シナリオをサポートする必要があります。 データモデル、プロトコル、トランスポートは、制約のあるデバイスなどの特殊用途のシナリオに適用するために特に定義されたものでない限り、スケーラブルでなければなりません。 SACM転送プロトコルの標準には、どれだけの数のエンドポイントとどれだけの量の情報までスケールすると合理的に期待できるかに対処する、スケーラビリティーに関する考慮事項のセクションを含めるべきです（SHOULD）。 スケーラビリティーは、次のものをサポートするように対処しなければなりません。

  • 大きなメッセージ: ポスチャー評価情報のサイズは、サイズの小さな単一の評価から、非常に大きなメッセージや非常に大きな評価の集合（最大で数ギガバイトのサイズ）までさまざまである可能性があります。
  • 1秒あたりの多数のメッセージ: 展開には、処理を必要とする多数の高速なまたは同時のイベントが含まれ、1秒あたり多数のメッセージが生成される場合があります。
  • 多数のプロバイダーとコンシューマー: 展開は、ポスチャー評価情報をリクエストする、または生成する、あるいはその両方を行う非常に多数のエンドポイントで構成される場合があります。
  • 多数のターゲットエンドポイント: 展開は、非常に多数のターゲットエンドポイントの情報を管理している場合があります。
G-004（汎用性）:
データモデル、プロトコル、トランスポートは、制約のある環境で動作するデータモデルとトランスポートの実装に関する考慮事項も含め、実装がさまざまな展開モデルとシナリオに適合できるように適切に規定しなければなりません。 特定の展開モデルとシナリオのニーズを満たすために、個別のソリューションが必要になる場合があります。
G-005（情報の拡張性）:
非標準の（実装固有の）属性をサポートしなければなりません（MUST）。 すべての属性の命名において、その出所にかかわらず衝突が発生するのを防ぐ方法を定義すべきです（SHOULD）。 相互運用性と範囲の境界のために、情報モデルは必須の属性の集合を定義しなければなりません（MUST）。
G-006（データ保護）:
共有される情報を保護するために、SACMコンポーネントは、転送中のデータ（エンドツーエンド）と保存されたデータ（情報がリポジトリーに保存されるとき）の完全性と機密性を保護しなければなりません（MUST）。 この保護の仕組みは規定しませんが、業界のベストプラクティスを含めるべきです。 これらの仕組みは利用可能であることが求められます（つまり、データを扱うすべてのコンポーネントがそれらをサポートしなければなりません）が、すべての場合に使用することは求められません。
G-007（データの分割）:
地理的、規制上、運用上の要件、オーバーレイの境界、フェデレーション（データが複数の場所で収集され、集中管理されるか、ローカルの地域に保持される場合）などの考慮事項に対応するために、データを分割する方法をサポートしなければなりません（MUST）。 データの複製をサポートする場合は、更新ループを防ぐ方法が存在することが求められます。
G-008（バージョニングと後方互換性）:
既存の能力（転送プロトコル、データモデル、データモデル内の特定の属性、標準の属性表現セットなど）を含む、バージョンの通知とネゴシエーションをサポートしなければなりません（MUST）。 将来の成長や、能力が混在するエコシステムに対応するために、バージョニングと能力の両方のネゴシエーションが必要です。
G-009（情報の発見）:
コンポーネントが、エコシステム全体でどのような情報が利用可能か（つまり、エコシステムで利用可能なデータをカタログ化し、それをコンシューマーに広告する方法）、その情報の特定の部分を得るにはどこに行けばよいか（つまり、どのプロバイダーがその情報を持っているか）、情報を整理するためにどのスキーマが使用されているかを発見するための仕組みが存在しなければなりません（MUST）。 たとえば、コンシューマーが利用可能な情報を見つけるために事前の知識を持つ必要がないように、ノードが広告された情報を見つけられる方法を提供できます。
G-010（ターゲットエンドポイントの発見）:
SACMは、ターゲットエンドポイントを発見できる手段を定義しなければなりません（MUST）。 [RFC7632]のセクション2.1.2のユースケースは、エンドポイントとその構成を発見する必要性について記述しています。
G-011（プッシュとプルのアクセス）:
プルモデル、要求されたプッシュモデル、要求されていないプッシュモデルの3つのデータアクセス方法をサポートしなければなりません（MUST）。 すべてのデータアクセス方法は、配信されるポスチャー評価情報の集合を開始者がフィルタリングする能力をサポートしなければなりません（MUST）。 さらに、情報のプロバイダーは、受信者の権限に基づいてポスチャー評価情報の集合をフィルタリングできなければなりません（MUST）。 この要件は、[RFC7632]のセクション2.1.3と2.1.4のユースケースから導かれています。
G-012（SACMコンポーネントインターフェイス）:
SACMコンポーネントがエンドポイントのポスチャー情報を共有するために通信するインターフェイスは、明確に定義しなければなりません（MUST）。 つまり、インターフェイスは、SACMコンポーネントが通信できるようにするためのデータモデル、SACM転送プロトコル、ネットワーク転送プロトコルを定義します。
G-013（エンドポイントの位置とネットワークトポロジー）:
SACMのアーキテクチャーとインターフェイスは、ターゲットエンドポイントの（ネットワーク上の）位置とネットワークトポロジーをモデル化し理解できるようにしなければなりません（MUST）。 適切な場合には、データモデルとインターフェイスは、ターゲットエンドポイントの位置、ネットワークトポロジー、またはその両方を発見できるようにするべきです（SHOULD）。
G-014（ターゲットエンドポイントのアイデンティティー）:
SACMのアーキテクチャーとインターフェイスは、ターゲットエンドポイントのアイデンティティーを構成するために使用できる属性をコンポーネントが提供する能力をサポートしなければなりません（MUST）。 これらのアイデンティティーは、1つ以上のSACMコンポーネントからの属性で構成してもよいです（MAY）。
G-015（データアクセス制御）:
地理的、規制上、運用上の考慮事項やフェデレーションなどに対応するために、アクセス制御の方法をサポートしなければなりません。 データにアクセスする、またはデータを公開するエンティティーは、自身を識別し、アクセスポリシーを満たさなければなりません（MUST）。

2.2. Requirements for the Architecture

2.2. アーキテクチャーの要件

Following are the requirements for the SACM architecture:

SACMアーキテクチャーの要件は次のとおりです。

ARCH-001 (Component Functions):
At the simplest abstraction, the SACM architecture MUST represent the core components and interfaces needed to perform the production and consumption of posture assessment information.
ARCH-002 (Scalability):
The architectural components MUST account for a range of deployments, from very small sets of endpoints to very large deployments.
ARCH-003 (Flexibility):
The architectural components MUST account for different deployment scenarios where the architectural components may be implemented, deployed, or used within a single application, service, or network, or may comprise a federated system.
ARCH-004 (Separation of Data and Management Functions):
SACM MUST define both the configuration and management of the SACM data models and protocols used to transfer and share posture assessment information.
ARCH-005 (Topology Flexibility):
Both centralized and decentralized (peer-to-peer) information exchange MUST be supported. Centralized data exchange enables use of a common data format to bridge together data exchange between diverse systems and can leverage a virtual data store that centralizes and offloads all data access, storage, and maintenance to a dedicated resource. Decentralized data exchange enables simplicity of sharing data between relatively uniform systems and between small numbers of systems, especially within a single enterprise domain. The fact that a centralized or decentralized deployment is used SHOULD be invisible to a consumer. However, there may be cases where the producer chooses to include that information due to consumer preference.
ARCH-006 (Capability Negotiation):
Announcement and negotiation of functional capabilities (such as authentication protocols, authorization schemes, data models, transfer protocols, etc.) MUST be supported, enabling a SACM component to make inquiries about the capabilities of other components in the SACM ecosystem.
ARCH-007 (Role-Based Authorization):
The SACM architecture MUST be capable of effecting role-based authorization. Distinction of endpoints capable of and authorized to provide or consume information is required to address appropriate access controls.
ARCH-008 (Context-Based Authorization):
The SACM architecture MUST be capable of effecting context-based authorization. Different policies (e.g., business, regulatory, etc.) might specify what data may be exposed to, or shared by, consumers based on one or more attributes of the consumer. The policy might specify that consumers are required to share specific information either back to the system or to administrators.
ARCH-009 (Time Synchronization):
Actions or decisions based on time-sensitive data (such as user logon/logoff, endpoint connection/disconnection, endpoint behavior events, etc.) are all predicated on a synchronized understanding of time. The SACM architecture MUST provide a mechanism for all components to synchronize time. A mechanism for detecting and reporting time discrepancies SHOULD be provided by the architecture and reflected in the information model.
ARCH-001（コンポーネントの機能）:
最も単純な抽象化において、SACMアーキテクチャーは、ポスチャー評価情報の生成と消費を実行するために必要なコアコンポーネントとインターフェイスを表現しなければなりません（MUST）。
ARCH-002（スケーラビリティー）:
アーキテクチャーのコンポーネントは、非常に小さなエンドポイントの集合から非常に大規模な展開まで、さまざまな展開を考慮しなければなりません（MUST）。
ARCH-003（柔軟性）:
アーキテクチャーのコンポーネントは、アーキテクチャーのコンポーネントが単一のアプリケーション、サービス、ネットワークの中で実装、展開、使用される場合や、フェデレーションされたシステムを構成する場合など、さまざまな展開シナリオを考慮しなければなりません（MUST）。
ARCH-004（データ機能と管理機能の分離）:
SACMは、ポスチャー評価情報を転送し共有するために使用するSACMのデータモデルとプロトコルについて、その設定と管理の両方を定義しなければなりません（MUST）。
ARCH-005（トポロジーの柔軟性）:
集中型と分散型（ピアツーピア）の両方の情報交換をサポートしなければなりません（MUST）。 集中型のデータ交換では、共通のデータ形式を使用して多様なシステム間のデータ交換を橋渡しでき、すべてのデータアクセス、保存、保守を一元化して専用のリソースにオフロードする仮想データストアを活用できます。 分散型のデータ交換では、比較的均一なシステム間や少数のシステム間で、とくに単一の企業ドメイン内で、データを簡単に共有できます。 集中型と分散型のどちらの展開が使用されているかは、コンシューマーからは見えないべきです（SHOULD）。 ただし、コンシューマーの希望により、プロデューサーがその情報を含めることを選択する場合もあります。
ARCH-006（能力のネゴシエーション）:
機能的な能力（認証プロトコル、認可方式、データモデル、転送プロトコルなど）の通知とネゴシエーションをサポートしなければなりません（MUST）。 これにより、SACMコンポーネントはSACMエコシステム内のほかのコンポーネントの能力について問い合わせることができます。
ARCH-007（ロールベースの認可）:
SACMアーキテクチャーは、ロールベースの認可を実施できなければなりません（MUST）。 適切なアクセス制御に対処するには、情報を提供または消費する能力と権限を持つエンドポイントを区別することが必要です。
ARCH-008（コンテキストベースの認可）:
SACMアーキテクチャーは、コンテキストベースの認可を実施できなければなりません（MUST）。 さまざまなポリシー（ビジネス上、規制上など）が、コンシューマーの1つ以上の属性に基づいて、どのデータをコンシューマーに公開してよいか、またはコンシューマーが共有してよいかを指定する場合があります。 ポリシーは、コンシューマーが特定の情報をシステムに返す、または管理者と共有することが求められると指定する場合があります。
ARCH-009（時刻同期）:
時間に敏感なデータ（ユーザーのログオン／ログオフ、エンドポイントの接続／切断、エンドポイントの挙動イベントなど）に基づく行動や決定は、すべて時刻についての同期された理解を前提としています。 SACMアーキテクチャーは、すべてのコンポーネントが時刻を同期するための仕組みを提供しなければなりません（MUST）。 時刻の不一致を検出し報告するための仕組みをアーキテクチャーが提供し、情報モデルに反映させるべきです（SHOULD）。

2.3. Requirements for the Information Model

2.3. 情報モデルの要件

The SACM information model represents the abstracted representation for posture assessment information to be communicated. SACM data models must adhere to and comply with the SACM information model. The requirements for the SACM information model include:

SACM情報モデルは、通信されるポスチャー評価情報を抽象化して表現したものです。 SACMデータモデルは、SACM情報モデルに準拠し、従わなければなりません。 SACM情報モデルの要件には次のものがあります。

IM-001 (Extensible Attribute Vocabulary):
The information model MUST define a minimum set of attributes for communicating posture information, to ensure interoperability between data models. (Individual data models may define attributes beyond the mandatory-to-implement minimum set.) The attributes should be defined with a clear mechanism for extensibility to enable data models to adhere to SACM's required attributes as well as allow for their own extensions. The attribute vocabulary should be defined with a clear mechanism for extensibility to enable future versions of the information model to be interoperably expanded with new attributes.
IM-002 (Posture Data Publication):
The information model MUST allow for the data to be provided by a SACM component either solicited or unsolicited. No aspect of the information model should be dependent upon or assume a Push or Pull model of publication.
IM-003 (Data Model Negotiation):
SACM's information model MUST allow support for different data models, data model versions, and different versions of the operations on the data models and transfer protocols. The SACM information model MUST include the ability to discover and negotiate the use of a particular data model or any data model.
IM-004 (Data Model Identification):
The information model MUST provide a means to uniquely identify each data model. The identifier MUST contain both an identifier of the data model and a version indicator for the data model. The identifiers SHOULD be decomposable so that a customer can query for any version of a specific data model and compare returned values for older or newer than a desired version.
IM-005 (Data Lifetime Management):
The information model MUST provide a means to allow data models to include data lifetime management. The information model must identify attributes that can allow data models to, at minimum, identify the data's origination time and expected time of next update or data longevity (how long the data should be assumed to still be valid).
IM-006 (Singularity and Modularity):
The SACM information model MUST be singular (i.e., there is only one information model, not multiple alternative information models from which to choose) and MAY be modular (a conjunction of several subcomponents) for ease of maintenance and extension. For example, endpoint identification could be an independent subcomponent of the information model, to simplify updating of endpoint identification attributes.
IM-001（拡張可能な属性語彙）:
情報モデルは、データモデル間の相互運用性を確保するために、ポスチャー情報を通信するための最小限の属性の集合を定義しなければなりません（MUST）。 （個々のデータモデルは、実装必須の最小限の集合を超える属性を定義してもかまいません。） 属性は、データモデルがSACMの必須属性に準拠しつつ独自の拡張も可能になるように、拡張性のための明確な仕組みを伴って定義すべきです。 属性語彙は、情報モデルの将来のバージョンを新しい属性で相互運用可能な形で拡張できるように、拡張性のための明確な仕組みを伴って定義すべきです。
IM-002（ポスチャーデータの公開）:
情報モデルは、SACMコンポーネントが要求された形でも要求されていない形でもデータを提供できるようにしなければなりません（MUST）。 情報モデルのどの側面も、プッシュ型またはプル型の公開モデルに依存したり、それを前提としたりすべきではありません。
IM-003（データモデルのネゴシエーション）:
SACMの情報モデルは、さまざまなデータモデル、データモデルのバージョン、データモデルと転送プロトコルに対する操作のさまざまなバージョンをサポートできるようにしなければなりません（MUST）。 SACM情報モデルは、特定のデータモデルまたは任意のデータモデルの使用を発見しネゴシエーションする能力を含めなければなりません（MUST）。
IM-004（データモデルの識別）:
情報モデルは、各データモデルを一意に識別する手段を提供しなければなりません（MUST）。 識別子は、データモデルの識別子とデータモデルのバージョン指示子の両方を含まなければなりません（MUST）。 識別子は、顧客が特定のデータモデルの任意のバージョンをクエリーし、返された値を希望するバージョンより古いか新しいかで比較できるように、分解可能であるべきです（SHOULD）。
IM-005（データのライフタイム管理）:
情報モデルは、データモデルがデータのライフタイム管理を含められるようにする手段を提供しなければなりません（MUST）。 情報モデルは、データモデルが少なくとも、データの発生時刻と、次回の更新予定時刻またはデータの寿命（データがまだ有効であるとみなすべき期間）を識別できるようにする属性を特定しなければなりません。
IM-006（単一性とモジュール性）:
SACM情報モデルは単一（つまり、情報モデルは1つだけであり、選択可能な複数の代替情報モデルがあるわけではない）でなければなりません（MUST）。 また、保守と拡張を容易にするために、モジュール化（複数のサブコンポーネントの結合）してもよいです（MAY）。 たとえば、エンドポイントの識別属性の更新を簡単にするために、エンドポイントの識別を情報モデルの独立したサブコンポーネントにすることができます。

2.4. Requirements for the Data Model

2.4. データモデルの要件

The SACM information model represents an abstraction for "what" information can be communicated and "how" it is to be represented and shared. It is expected that as applications may produce posture assessment information, they may share it using a specific data model. Similarly, applications consuming or requesting posture assessment information may require that it be based on a specific data model. Thus, while there may exist different data models and schemas, they should adhere to the SACM information model and meet the requirements defined in this section.

SACM情報モデルは、「何の」情報を通信できるか、そしてそれを「どのように」表現し共有するかについての抽象化を表します。 アプリケーションはポスチャー評価情報を生成する場合、特定のデータモデルを使用してそれを共有することが想定されます。 同様に、ポスチャー評価情報を消費またはリクエストするアプリケーションは、その情報が特定のデータモデルに基づいていることを求める場合があります。 したがって、さまざまなデータモデルやスキーマが存在する可能性がありますが、それらはSACM情報モデルに準拠し、このセクションで定義する要件を満たすべきです。

The specific requirements for candidate data models include:

候補となるデータモデルに対する具体的な要件には次のものがあります。

DM-001 (Element Association):
A SACM information model consists of a set of SACM information model elements. A SACM data model MUST be derived from the SACM information model. A SACM data model consists of a set of SACM data model elements. In this derivation, a SACM data model element MAY map to one or more SACM information model elements. In addition, a SACM data model MAY include additional data model elements that are not associated with any SACM information model elements.
DM-002 (Data Model Structure):
The data model can be structured either as one single module or separated into modules and submodules that allow for references between them. The data model structure MAY reflect structure in the information model but does not need to. For example, the data model might use one module to define endpoints, and that module might reference other modules that describe the various assets associated with the endpoint. Constraints and interfaces might further be defined to resolve or tolerate ambiguity in the references (e.g., the same IP address used in two separate networks).
DM-003 (Search Flexibility):
The search interfaces and actions MUST include the ability to start a search anywhere within a data model structure and the ability to search based on patterns ("wildcard searches") as well as specific data elements.
DM-004 (Full vs. Partial Updates):
The data model SHOULD include the ability to allow providers of data to provide the data as a whole or when updates occur. For example, a consumer can request a full update on initial engagement, then request to receive deltas (updates containing only the changes since the last update) on an ongoing basis as new data is generated.
DM-005 (Loose Coupling):
The data model SHOULD allow for a loose coupling between the provider and the consumer, such that the consumer can request information without being required to request it from a specific provider, and a provider can publish information without having a specific consumer targeted to receive it.
DM-006 (Data Cardinality):
The data model MUST describe their constraints (e.g., cardinality). As posture information and the tasks for collection, aggregation, or evaluation could comprise one or more attributes, interfaces and actions MUST allow and account for such cardinality and for conditional, optional, or mandatory attributes.
DM-007 (Data Model Negotiation):
The interfaces and actions in the data model MUST include capability negotiation to enable discovery of supported and available data types and schemas.
DM-008 (Data Origin):
The data model MUST include the ability for consumers to identify the data origin (provider that collected the data).
DM-009 (Origination Time):
The data model SHOULD allow the provider to include the information's origination time.
DM-010 (Data Generation):
The data model MUST allow the provider to include attributes defining how the data was generated (e.g., self-reported, reported by aggregator, scan result, etc.).
DM-011 (Data Source):
The data model MUST allow the provider to include attributes identifying the data source (target endpoint from which the data was collected), e.g., hostname, domain (DNS) name, or application name.
DM-012 (Data Updates):
The data model SHOULD allow the provider to include attributes defining whether the information provided is a delta, partial, or full set of information.
DM-013 (Multiple Collectors):
The data model MUST support the collection of attributes by a variety of collectors, including internal collectors, external collectors with an authenticated relationship with the endpoint, and external collectors based on network and other observers.
DM-014 (Attribute Extensibility):
All of the use cases in Section 2 of [RFC7632] describe the need for an attribute dictionary. With SACM's scope focused on posture assessment, the data model attribute collection and aggregation MUST have a well-understood set of attributes inclusive of their meaning or usage intent. The data model MUST include all attributes defined in the information model and MAY include additional attributes beyond those found in the information model. Additional attributes MUST be defined in accordance with the extensibility framework provided in the information model (see IM-001).
DM-015 (Solicited vs. Unsolicited Updates):
The data model MUST enable a provider to publish data either solicited (in response to a request from a consumer) or unsolicited (as new data is generated, without a request required). For example, an external collector can publish data in response to a request by a consumer for information about an endpoint, or it can publish data as it observes new information about an endpoint, without any specific consumer request triggering the publication; a compliance-server provider may publish endpoint posture information in response to a request from a consumer (solicited), or it may publish posture information driven by a change in the posture of the endpoint (unsolicited).
DM-016 (Transfer Agnostic):
The data model MUST be transfer agnostic, to allow for the data operations to leverage the most appropriate SACM transfer protocol.
DM-001（要素の関連付け）:
SACM情報モデルは、SACM情報モデル要素の集合で構成されます。 SACMデータモデルは、SACM情報モデルから導出しなければなりません（MUST）。 SACMデータモデルは、SACMデータモデル要素の集合で構成されます。 この導出において、SACMデータモデル要素は1つ以上のSACM情報モデル要素に対応してもよいです（MAY）。 さらに、SACMデータモデルには、どのSACM情報モデル要素にも関連付けられていない追加のデータモデル要素を含めてもよいです（MAY）。
DM-002（データモデルの構造）:
データモデルは、単一のモジュールとして構成することも、相互の参照を可能にするモジュールとサブモジュールに分割することもできます。 データモデルの構造は、情報モデルの構造を反映してもよいです（MAY）が、その必要はありません。 たとえば、データモデルは1つのモジュールを使用してエンドポイントを定義し、そのモジュールがエンドポイントに関連するさまざまな資産を記述するほかのモジュールを参照する場合があります。 さらに、参照における曖昧さ（たとえば、2つの別々のネットワークで同じIPアドレスが使用されている場合）を解決または許容するために、制約とインターフェイスを定義する場合があります。
DM-003（検索の柔軟性）:
検索インターフェイスとアクションは、データモデル構造内の任意の場所から検索を開始する能力と、特定のデータ要素だけでなくパターンに基づいて検索する能力（「ワイルドカード検索」）を含めなければなりません（MUST）。
DM-004（完全な更新と部分的な更新）:
データモデルは、データのプロバイダーがデータを全体として提供することも、更新が発生したときに提供することもできるようにする能力を含めるべきです（SHOULD）。 たとえば、コンシューマーは、最初の関与時に完全な更新をリクエストし、その後は新しいデータが生成されるたびに継続的に差分（前回の更新以降の変更だけを含む更新）を受信するようリクエストできます。
DM-005（疎結合）:
データモデルは、プロバイダーとコンシューマーの間の疎結合を可能にするべきです（SHOULD）。 つまり、コンシューマーは特定のプロバイダーにリクエストすることを求められずに情報をリクエストでき、プロバイダーは受信対象となる特定のコンシューマーを持たずに情報を公開できるようにします。
DM-006（データのカーディナリティー）:
データモデルは、その制約（たとえば、カーディナリティー）を記述しなければなりません（MUST）。 ポスチャー情報と、収集、集約、評価のタスクは1つ以上の属性で構成される可能性があるため、インターフェイスとアクションはそのようなカーディナリティーと、条件付き、任意、必須の属性を許容し考慮しなければなりません（MUST）。
DM-007（データモデルのネゴシエーション）:
データモデルのインターフェイスとアクションは、サポートされ利用可能なデータ型とスキーマを発見できるように、能力のネゴシエーションを含めなければなりません（MUST）。
DM-008（データの出所）:
データモデルは、コンシューマーがデータの出所（データを収集したプロバイダー）を識別する能力を含めなければなりません（MUST）。
DM-009（発生時刻）:
データモデルは、プロバイダーが情報の発生時刻を含められるようにするべきです（SHOULD）。
DM-010（データの生成）:
データモデルは、データがどのように生成されたか（たとえば、自己申告、アグリゲーターによる報告、スキャン結果など）を定義する属性をプロバイダーが含められるようにしなければなりません（MUST）。
DM-011（データソース）:
データモデルは、データソース（データの収集元のターゲットエンドポイント）を識別する属性、たとえばホスト名、ドメイン（DNS）名、アプリケーション名をプロバイダーが含められるようにしなければなりません（MUST）。
DM-012（データの更新）:
データモデルは、提供される情報が差分、部分的、完全な情報の集合のいずれであるかを定義する属性をプロバイダーが含められるようにするべきです（SHOULD）。
DM-013（複数のコレクター）:
データモデルは、内部コレクター、エンドポイントと認証された関係を持つ外部コレクター、ネットワークやその他の観測者に基づく外部コレクターなど、さまざまなコレクターによる属性の収集をサポートしなければなりません（MUST）。
DM-014（属性の拡張性）:
[RFC7632]のセクション2のすべてのユースケースは、属性辞書の必要性について記述しています。 SACMの範囲がポスチャー評価に焦点を当てていることから、データモデルの属性の収集と集約は、その意味や使用意図を含めて十分に理解された属性の集合を持たなければなりません（MUST）。 データモデルは、情報モデルで定義されたすべての属性を含めなければなりません（MUST）。 また、情報モデルにある属性以外の追加の属性を含めてもよいです（MAY）。 追加の属性は、情報モデルで提供される拡張性の枠組みに従って定義しなければなりません（MUST）（IM-001を参照）。
DM-015（要求された更新と要求されていない更新）:
データモデルは、プロバイダーが、要求された形（コンシューマーからのリクエストに応答して）でも、要求されていない形（リクエストを必要とせずに、新しいデータが生成されたときに）でもデータを公開できるようにしなければなりません（MUST）。 たとえば、外部コレクターは、エンドポイントに関する情報を求めるコンシューマーのリクエストに応答してデータを公開することも、公開のきっかけとなる特定のコンシューマーのリクエストなしに、エンドポイントに関する新しい情報を観測したときにデータを公開することもできます。 また、コンプライアンスサーバーとして動作するプロバイダーは、コンシューマーからのリクエストに応答してエンドポイントのポスチャー情報を公開する（要求された形）場合もあれば、エンドポイントのポスチャーの変化をきっかけにポスチャー情報を公開する（要求されていない形）場合もあります。
DM-016（転送への非依存）:
データ操作が最も適切なSACM転送プロトコルを活用できるように、データモデルは転送に依存しないものでなければなりません（MUST）。

2.5. Requirements for Data Model Operations

2.5. データモデル操作の要件

Posture information data adhering to a data model must also provide interfaces that include operations for access and production of the data. Operations requirements are distinct from transfer requirements in that operations requirements are requirements on the application performing requests and responses, whereas transfer requirements are requirements on the transfer protocol carrying the requests and responses. The specific requirements for such operations include:

データモデルに準拠するポスチャー情報データは、データへのアクセスと生成のための操作を含むインターフェイスも提供しなければなりません。 操作の要件は、リクエストとレスポンスを実行するアプリケーションに対する要件であるのに対し、転送の要件はリクエストとレスポンスを運ぶ転送プロトコルに対する要件であるという点で、両者は異なります。 そのような操作に対する具体的な要件には次のものがあります。

OP-001 (Time Synchronization):
Request and response operations MUST be timestamped, and published information SHOULD capture time of publication. Actions or decisions based on time-sensitive data (such as user logon/logoff, endpoint connection/disconnection, endpoint behavior events, etc.) are all predicated on a synchronized understanding of time. A method for detecting and reporting time discrepancies SHOULD be provided.
OP-002 (Collection Abstraction):
Collection is the act of a SACM component gathering data from a target endpoint. The request for a data item MUST include enough information to properly identify the item to collect, but the request shall not be a command to directly execute nor be directly applied as arguments to a command. The purpose of this requirement is primarily to reduce the potential attack vectors but has the additional benefit of abstracting the request for collection from the collection method, thereby allowing more flexibility in how collection is implemented.
OP-003 (Collection Composition):
A collection request MAY be composed of multiple collection requests (which yield collected values). The desire for multiple values MUST be expressed as part of the collection request, so that the aggregation can be resolved at the point of collection without having to interact with the requestor. This requirement should not be interpreted as preventing a collector from providing attributes that were not part of the original request.
OP-004 (Attribute-Based Query):
A query operation is the act of requesting data from a provider. Query operations SHOULD be based on a set of attributes. Query operations MUST support both a query for specific attributes and a query for all attributes. The use case in Section 2.1.2 of [RFC7632] describes the need for the data model to support a query operation based on a set of attributes to facilitate collection of information such as posture assessment, inventory (of endpoints or endpoint components), and configuration checklist.
OP-005 (Information-Based Query with Filtering):
The query operation MUST support filtering. The use case in Section 2.1.3 of [RFC7632] describes the need for the data model to support the means for the information to be collected through a query mechanism. Furthermore, the query operation requires filtering capabilities to allow for only a subset of information to be retrieved. The query operation MAY be a synchronous request or asynchronous request.
OP-006 (Operation Scalability):
The operation resulting from a query operation MUST be able to handle the return and receipt of large amounts of data. The use case in Section 2.1.4 of [RFC7632] describe the need for the data model to support scalability. For example, the query operation may result in a very large set of attributes as well as a large set of targets.
OP-007 (Data Abstraction):
The data model MUST allow a SACM component to communicate what data was used to construct the target endpoint's identity, so that other SACM components can determine whether they are constructing an equivalent target endpoint (and its identity) and whether they have confidence in that identity. SACM components SHOULD have interfaces defined to transmit this data directly or to refer to where the information can be retrieved.
OP-008 (Provider Restriction):
Request operations MUST include the ability to restrict the data to be provided by a specific provider or a provider with specific characteristics. Response operations MUST include the ability to identify the provider that supplied the response. For example, a SACM consumer should be able to request that all of the data come from a specific provider by identity (e.g., Provider A) or from a provider that is in a specific location (e.g., in the Boston office).
OP-001（時刻同期）:
リクエスト操作とレスポンス操作にはタイムスタンプを付けなければなりません（MUST）。 また、公開された情報は公開時刻を記録するべきです（SHOULD）。 時間に敏感なデータ（ユーザーのログオン／ログオフ、エンドポイントの接続／切断、エンドポイントの挙動イベントなど）に基づく行動や決定は、すべて時刻についての同期された理解を前提としています。 時刻の不一致を検出し報告するための方法を提供すべきです（SHOULD）。
OP-002（収集の抽象化）:
収集とは、SACMコンポーネントがターゲットエンドポイントからデータを集める行為です。 データ項目のリクエストには、収集する項目を適切に識別するのに十分な情報を含めなければなりません（MUST）が、そのリクエストは直接実行するコマンドであってはならず、コマンドの引数として直接適用されるものであってもなりません。 この要件の目的は主に潜在的な攻撃ベクトルを減らすことですが、収集のリクエストを収集方法から抽象化し、それにより収集の実装方法をより柔軟にできるという追加の利点もあります。
OP-003（収集の構成）:
収集リクエストは、（収集された値をもたらす）複数の収集リクエストで構成してもよいです（MAY）。 リクエスターとやり取りすることなく収集の時点で集約を解決できるように、複数の値を求めることを収集リクエストの一部として表現しなければなりません（MUST）。 この要件は、元のリクエストに含まれていなかった属性をコレクターが提供することを妨げるものと解釈すべきではありません。
OP-004（属性ベースのクエリー）:
クエリー操作とは、プロバイダーにデータをリクエストする行為です。 クエリー操作は、属性の集合に基づくべきです（SHOULD）。 クエリー操作は、特定の属性に対するクエリーとすべての属性に対するクエリーの両方をサポートしなければなりません（MUST）。 [RFC7632]のセクション2.1.2のユースケースは、ポスチャー評価、（エンドポイントまたはエンドポイントコンポーネントの）インベントリー、構成チェックリストなどの情報の収集を促進するために、属性の集合に基づくクエリー操作をデータモデルがサポートする必要性について記述しています。
OP-005（フィルタリングを伴う情報ベースのクエリー）:
クエリー操作は、フィルタリングをサポートしなければなりません（MUST）。 [RFC7632]のセクション2.1.3のユースケースは、クエリーの仕組みを通じて情報を収集する手段をデータモデルがサポートする必要性について記述しています。 さらに、クエリー操作には、情報のサブセットだけを取得できるようにするためのフィルタリング機能が必要です。 クエリー操作は、同期リクエストでも非同期リクエストでもよいです（MAY）。
OP-006（操作のスケーラビリティー）:
クエリー操作の結果として生じる操作は、大量のデータの返送と受信を処理できなければなりません（MUST）。 [RFC7632]のセクション2.1.4のユースケースは、データモデルがスケーラビリティーをサポートする必要性について記述しています。 たとえば、クエリー操作の結果、非常に大きな属性の集合と大きなターゲットの集合が得られる場合があります。
OP-007（データの抽象化）:
データモデルは、ターゲットエンドポイントのアイデンティティーを構築するためにどのデータが使用されたかをSACMコンポーネントが伝えられるようにしなければなりません（MUST）。 これにより、ほかのSACMコンポーネントは、自身が同等のターゲットエンドポイント（とそのアイデンティティー）を構築しているかどうか、そしてそのアイデンティティーを信頼できるかどうかを判断できます。 SACMコンポーネントは、このデータを直接送信するため、またはその情報を取得できる場所を参照するためのインターフェイスを定義するべきです（SHOULD）。
OP-008（プロバイダーの制限）:
リクエスト操作は、提供されるデータを特定のプロバイダーまたは特定の特性を持つプロバイダーからのものに制限する能力を含めなければなりません（MUST）。 レスポンス操作は、レスポンスを提供したプロバイダーを識別する能力を含めなければなりません（MUST）。 たとえば、SACMコンシューマーは、すべてのデータを、アイデンティティーで指定した特定のプロバイダー（たとえば、プロバイダーA）から、または特定の場所（たとえば、ボストンのオフィス）にあるプロバイダーから得るようにリクエストできるべきです。

2.6. Requirements for SACM Transfer Protocols

2.6. SACM転送プロトコルの要件

The term "SACM transfer protocol" is intended to be distinguished from underlying transport- and internet-layer protocols such as TCP/IP or operating at an application-layer protocol such as HTTP. The SACM transfer protocol is focused on moving data and performing necessary access control operations; it is agnostic to the data model operations.

「SACM転送プロトコル」という用語は、TCP/IPのような下位のトランスポート層やインターネット層のプロトコル、あるいはHTTPのようなアプリケーション層のプロトコルで動作するものとは区別することを意図しています。 SACM転送プロトコルは、データの移動と必要なアクセス制御操作の実行に焦点を当てており、データモデルの操作には依存しません。

The requirements for SACM transfer protocols include:

SACM転送プロトコルの要件には次のものがあります。

T-001 (Multiple Transfer Protocol Support):
SACM transfer protocols will vary depending on the deployment model that relies on different transfer-layer requirements, different device capabilities, and system configurations dealing with connectivity. For example, where posture attributes may be collected directly from an endpoint using the Network Endpoint Assessment (NEA) model [RFC5209], different transports may be defined to collect them using Posture Transport Protocol for Extensible Authentication Protocol Tunnel Methods (PT-EAP) [RFC7171] or Posture Transport Protocol over TLS (PT-TLS) [RFC6876], depending on the deployment scenario.
T-002 (Data Integrity):
SACM transfer protocols MUST be able to ensure data integrity for data in transit.
T-003 (Data Confidentiality):
SACM transfer protocols MUST be able to support data confidentiality. SACM transfer protocols MUST ensure data protection for data in transit (e.g., by encryption) to provide confidentiality, integrity, and robustness against protocol-based attacks. Note that while the transfer MUST be able to support data confidentiality, implementations MAY provide a configuration option that enables and disables confidentiality in deployments. Protection for data at rest is not in scope for transfer protocols. Data protection MAY be used for both privacy and non-privacy scenarios.
T-004 (Transfer Protection):
SACM transfer protocols MUST be capable of supporting mutual authentication and replay protection.
T-005 (Transfer Reliability):
SACM transfer protocols MUST provide reliable delivery of data. This includes the ability to perform fragmentation and reassembly and to detect replays. The SACM transfer may take advantage of reliability features in the network transport; however, the network transport may be unreliable (e.g., UDP), in which case the SACM transfer running over the unreliable network transport is responsible for ensuring reliability (i.e., by provisions such as confirmations and retransmits).
T-006 (Transfer-Layer Requirements):
Each SACM transfer protocol MUST clearly specify the transport-layer requirements it needs to operate correctly. Examples of items that may need to be specified include connectivity requirements, replay requirements, data link encryption requirements, and/or channel-binding requirements. These requirements are needed in order for deployments to be done correctly.
T-007 (Transfer Protocol Adoption):
SACM SHOULD, where reasonably possible, leverage and use existing IETF transfer protocols versus defining new ones.
T-001（複数の転送プロトコルのサポート）:
SACM転送プロトコルは、さまざまな転送層の要件、さまざまなデバイスの能力、接続性を扱うシステム構成に依存する展開モデルに応じて異なります。 たとえば、Network Endpoint Assessment（NEA）モデル[RFC5209]を使用してエンドポイントから直接ポスチャー属性を収集できる場合、展開シナリオに応じて、Posture Transport Protocol for Extensible Authentication Protocol Tunnel Methods（PT-EAP）[RFC7171]やPosture Transport Protocol over TLS（PT-TLS）[RFC6876]を使用してそれらを収集するさまざまなトランスポートを定義できます。
T-002（データの完全性）:
SACM転送プロトコルは、転送中のデータについてデータの完全性を確保できなければなりません（MUST）。
T-003（データの機密性）:
SACM転送プロトコルは、データの機密性をサポートできなければなりません（MUST）。 SACM転送プロトコルは、機密性、完全性、プロトコルベースの攻撃に対する堅牢性を提供するために、転送中のデータのデータ保護を（たとえば暗号化によって）確保しなければなりません（MUST）。 なお、転送はデータの機密性をサポートできなければなりません（MUST）が、実装は展開において機密性を有効または無効にする設定オプションを提供してもよいです（MAY）。 保存されたデータの保護は、転送プロトコルの範囲外です。 データ保護は、プライバシーに関わるシナリオとプライバシーに関わらないシナリオの両方で使用してもよいです（MAY）。
T-004（転送の保護）:
SACM転送プロトコルは、相互認証とリプレイ保護をサポートできなければなりません（MUST）。
T-005（転送の信頼性）:
SACM転送プロトコルは、データの信頼性のある配信を提供しなければなりません（MUST）。 これには、フラグメンテーションと再構築を実行する能力や、リプレイを検出する能力が含まれます。 SACMの転送は、ネットワークトランスポートの信頼性機能を利用できます。 ただし、ネットワークトランスポートが信頼性のないもの（たとえば、UDP）である場合もあり、その場合は、信頼性のないネットワークトランスポート上で動作するSACMの転送が（つまり、確認応答や再送などの措置によって）信頼性を確保する責任を負います。
T-006（転送層の要件）:
各SACM転送プロトコルは、正しく動作するために必要なトランスポート層の要件を明確に規定しなければなりません（MUST）。 規定が必要になる可能性のある項目の例としては、接続性の要件、リプレイの要件、データリンクの暗号化の要件、チャネルバインディングの要件などがあります。 これらの要件は、展開を正しく行うために必要です。
T-007（転送プロトコルの採用）:
SACMは、合理的に可能な場合には、新しい転送プロトコルを定義するのではなく、既存のIETFの転送プロトコルを活用し使用するべきです（SHOULD）。

4. Security Considerations

4. セキュリティーに関する考慮事項

This document defines the requirements for SACM. As such, it is expected that several data models, protocols, and transfer protocols may be defined or reused from already-existing standards.

この文書は、SACMの要件を定義します。 そのため、いくつかのデータモデル、プロトコル、転送プロトコルが定義されるか、既存の標準から再利用されることが想定されます。

To address security and privacy considerations, the data model, protocols, and transports must consider authorization based on consumer function and privileges, to only allow authorized consumers and providers to access specific information being requested or published.

セキュリティーとプライバシーの考慮事項に対処するために、データモデル、プロトコル、トランスポートは、認可されたコンシューマーとプロバイダーだけが、リクエストまたは公開される特定の情報にアクセスできるように、コンシューマーの機能と権限に基づく認可を考慮しなければなりません。

To enable federation across multiple entities (such as across organizational or geographic boundaries), authorization must also extend to infrastructure elements themselves, such as central controllers, brokers, and data repositories.

複数のエンティティーにまたがる（組織的または地理的な境界をまたぐなどの）フェデレーションを可能にするには、認可は、中央コントローラー、ブローカー、データリポジトリーなどのインフラストラクチャー要素そのものにも及ばなければなりません。

In addition, authorization needs to extend to specific information or resources available in the environment. In other words, authorization is based on the subject (the information requestor), the provider (the information responder), the object (the endpoint the information is being requested on), and the attribute (what piece of data is being requested). The method by which this authorization is applied is unspecified.

さらに、認可は、環境内で利用可能な特定の情報やリソースにも及ぶ必要があります。 言い換えると、認可は、サブジェクト（情報のリクエスター）、プロバイダー（情報の応答者）、オブジェクト（情報がリクエストされている対象のエンドポイント）、属性（どのデータがリクエストされているか）に基づきます。 この認可を適用する方法は規定しません。

SACM's charter focuses on the workflow orchestration and the sharing of posture information for improving the efficacy of security applications such as compliance, configuration, assurance, and other threat and vulnerability reporting and remediation systems. While the goal is to facilitate the flow of information securely, it is important to note that participating endpoints may not be cooperative or trustworthy.

SACMの憲章は、コンプライアンス、構成、保証、その他の脅威と脆弱性の報告・修復システムなどのセキュリティーアプリケーションの有効性を向上させるための、ワークフローのオーケストレーションとポスチャー情報の共有に焦点を当てています。 目標は情報の流れを安全に促進することですが、参加するエンドポイントが協力的でない、または信頼できない可能性があることに注意することが重要です。

4.1. Trust between Provider and Requestor

4.1. プロバイダーとリクエスターの間の信頼

The information given from the provider to a requestor may come with different levels of trustworthiness given the different potential deployment scenarios and compromise at the provider, the requesting consumer, or devices that are involved in the transfer between the provider and requestor. This section will describe the different considerations that may reduce the level of trustworthiness of the information provided.

プロバイダーからリクエスターに与えられる情報は、想定されるさまざまな展開シナリオや、プロバイダー、リクエスト元のコンシューマー、またはプロバイダーとリクエスターの間の転送に関与するデバイスでの侵害によって、信頼性のレベルが異なる場合があります。 このセクションでは、提供される情報の信頼性のレベルを低下させる可能性のあるさまざまな考慮事項について記述します。

In the information transfer flow, it is possible that some of the devices may serve as proxies or brokers and, as such, may be able to observe the communications flowing between an information provider and requestor. Without appropriate protections, it is possible for these proxies and brokers to inject and affect man-in-the-middle attacks.

情報転送の流れの中では、一部のデバイスがプロキシーやブローカーとして機能し、そのため情報プロバイダーとリクエスターの間を流れる通信を観測できる可能性があります。 適切な保護がなければ、これらのプロキシーやブローカーが中間者攻撃を注入し、実行する可能性があります。

In general, it is common to distrust the network service provider, unless the full hop-by-hop communications process flow is well understood. As such, the posture information provider should protect the posture information data it provides as well as the transfer it uses. Similarly, while there may be providers whose goal is to openly share its information, there may also be providers whose policy is to grant access to certain posture information based on its business or regulatory policy. In those situations, a provider may require full authentication and authorization of the requestor (or set of requestors) and share only the authorized information to the authenticated and authorized requestors.

一般に、ホップバイホップの通信処理の流れ全体が十分に理解されていない限り、ネットワークサービスプロバイダーを信頼しないのが一般的です。 そのため、ポスチャー情報プロバイダーは、提供するポスチャー情報データと、使用する転送の両方を保護すべきです。 同様に、自身の情報をオープンに共有することを目標とするプロバイダーが存在する一方で、ビジネス上または規制上のポリシーに基づいて特定のポスチャー情報へのアクセスを許可することをポリシーとするプロバイダーも存在する可能性があります。 そのような状況では、プロバイダーはリクエスター（またはリクエスターの集合）の完全な認証と認可を要求し、認証され認可されたリクエスターに対してのみ、認可された情報を共有する場合があります。

Beyond distrusting the network service provider, a requestor must also take into account that the information received from the provider may have been communicated through an undetermined network communications system. That is, the posture information may have traversed through many devices before reaching the requestor. SACM specifications should provide the means for verifying data origin and data integrity and, at minimum, provide endpoint authentication and transfer integrity.

ネットワークサービスプロバイダーを信頼しないことに加えて、リクエスターは、プロバイダーから受信した情報が、不確定なネットワーク通信システムを介して伝達された可能性があることも考慮しなければなりません。 つまり、ポスチャー情報は、リクエスターに届くまでに多くのデバイスを経由している可能性があります。 SACMの仕様は、データの出所とデータの完全性を検証する手段を提供し、少なくともエンドポイントの認証と転送の完全性を提供すべきです。

A requestor may require data freshness indications, both knowledge of data origination as well as time of publication, so that it can make more informed decisions about the relevance of the data based on its currency and/or age.

リクエスターは、データの関連性について、その新しさや経過時間に基づいてより十分な情報に基づく判断ができるように、データの発生と公開時刻の両方の知識を含む、データの鮮度を示すものを要求する場合があります。

It is also important to note that endpoint assessment reports, especially as they may be provided by the target endpoint, may pose untrustworthy information. The considerations for this are described in Section 8 of [RFC5209].

エンドポイント評価レポートは、とくにターゲットエンドポイントによって提供される場合、信頼できない情報をもたらす可能性があることに注意することも重要です。 これに関する考慮事項は[RFC5209]のセクション8で記述されています。

The trustworthiness of the posture information given by the provider to one or many requestors is dependent on several considerations. Some of these include the requestor requiring:

プロバイダーから1つまたは多数のリクエスターに与えられるポスチャー情報の信頼性は、いくつかの考慮事項に依存します。 その一部として、リクエスターが次のものを要求することが挙げられます。

  • Full disclosure of the network topology path to the provider(s).
  • Direct (peer-to-peer) communication with the provider.
  • Authentication and authorization of the provider.
  • Either or both confidentiality and integrity at the transfer layer.
  • Either or both confidentiality and integrity at the data layer.
  • プロバイダーまでのネットワークトポロジーの経路の完全な開示。
  • プロバイダーとの直接（ピアツーピア）の通信。
  • プロバイダーの認証と認可。
  • 転送層での機密性と完全性のいずれか、または両方。
  • データ層での機密性と完全性のいずれか、または両方。

4.2. Privacy Considerations

4.2. プライバシーに関する考慮事項

SACM information may contain sensitive information about the target endpoint as well as revealing identity information of the producer or consumer of such information. Similarly, as part of the SACM discovery mechanism, the capabilities and roles (e.g., SACM components enabled) advertised by the endpoint may be construed as private information.

SACMの情報には、ターゲットエンドポイントに関する機微な情報が含まれるだけでなく、そのような情報のプロデューサーやコンシューマーのアイデンティティー情報が明らかになる可能性があります。 同様に、SACMの発見の仕組みの一部として、エンドポイントが広告する能力とロール（たとえば、有効になっているSACMコンポーネント）が、プライベートな情報とみなされる場合があります。

In addition to identity and SACM capabilities information disclosure, the use of timestamps (or other attributes that can be used as identifiers) could be further used to determine a target endpoint or user's behavioral patterns. Such attributes may also be deemed sensitive and may require further protection or obfuscation to meet privacy concerns. That is, there may be applications as well as business and regulatory practices that require that aspects of such information be hidden from any parties that do not need to know it.

アイデンティティーとSACMの能力の情報の開示に加えて、タイムスタンプ（または識別子として使用できるその他の属性）の使用は、ターゲットエンドポイントやユーザーの行動パターンを特定するためにさらに使用される可能性があります。 そのような属性も機微なものとみなされ、プライバシー上の懸念に対処するために、さらなる保護や難読化が必要になる場合があります。 つまり、そのような情報の一部の側面を、それを知る必要のないあらゆる当事者から隠すことを求めるアプリケーションや、ビジネス上および規制上の慣行が存在する可能性があります。

Data confidentiality can provide some level of privacy but may fall short where unnecessary data is still transmitted. In those cases, filtering requirements at the data model such as OP-005 must be applied to ensure that such data is not disclosed. [RFC6973] provides guidelines that SACM protocols, information models, and data models should follow.

データの機密性は、ある程度のプライバシーを提供できますが、不要なデータが依然として送信される場合には不十分なことがあります。 そのような場合には、そのようなデータが開示されないように、OP-005のようなデータモデルにおけるフィルタリング要件を適用しなければなりません。 [RFC6973]は、SACMのプロトコル、情報モデル、データモデルが従うべきガイドラインを提供しています。
