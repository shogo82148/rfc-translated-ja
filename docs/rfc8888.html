RTP Control Protocol (RTCP) Feedback for Congestion Control

RFC 8888

輻輳制御のためのRTP制御プロトコル（RTCP）フィードバック

Abstract

概要

An effective RTP congestion control algorithm requires more fine-grained feedback on packet loss, timing, and Explicit Congestion Notification (ECN) marks than is provided by the standard RTP Control Protocol (RTCP) Sender Report (SR) and Receiver Report (RR) packets. This document describes an RTCP feedback message intended to enable congestion control for interactive real-time traffic using RTP. The feedback message is designed for use with a sender-based congestion control algorithm, in which the receiver of an RTP flow sends back to the sender RTCP feedback packets containing the information the sender needs to perform congestion control.

効果的なRTP輻輳制御アルゴリズムには、標準のRTP制御プロトコル（RTCP）の送信者報告（SR）パケットや受信者報告（RR）パケットが提供するよりもきめ細かい、パケット損失、タイミング、明示的輻輳通知（ECN）マークに関するフィードバックが必要です。 この文書は、RTPを使用する対話型リアルタイムトラフィックの輻輳制御を可能にすることを目的としたRTCPフィードバックメッセージについて説明します。 このフィードバックメッセージは、送信者ベースの輻輳制御アルゴリズムで使用するように設計されています。 このアルゴリズムでは、RTPフローの受信者は、送信者が輻輳制御を行うために必要な情報を含むRTCPフィードバックパケットを送信者に送り返します。

1. Introduction

1. はじめに

For interactive real-time traffic, such as video conferencing flows, the typical protocol choice is the Real-time Transport Protocol (RTP) [RFC3550] running over the User Datagram Protocol (UDP). RTP does not provide any guarantee of Quality of Service (QoS), reliability, or timely delivery, and expects the underlying transport protocol to do so. UDP alone certainly does not meet that expectation. However, the RTP Control Protocol (RTCP) [RFC3550] provides a mechanism by which the receiver of an RTP flow can periodically send transport and media quality metrics to the sender of that RTP flow. This information can be used by the sender to perform congestion control. In the absence of standardized messages for this purpose, designers of congestion control algorithms have developed proprietary RTCP messages that convey only those parameters needed for their respective designs. As a direct result, the different congestion control designs are not interoperable. To enable algorithm evolution as well as interoperability across designs (e.g., different rate adaptation algorithms), it is highly desirable to have a generic congestion control feedback format.

ビデオ会議のフローのような対話型リアルタイムトラフィックでは、ユーザーデータグラムプロトコル（UDP）上で動作するリアルタイム転送プロトコル（RTP）[RFC3550]を選択するのが一般的です。 RTPは、サービス品質（QoS）、信頼性、適時の配送をまったく保証せず、下位のトランスポートプロトコルがそれらを保証することを期待しています。 UDPだけでは、その期待をまったく満たしません。 しかし、RTP制御プロトコル（RTCP）[RFC3550]は、RTPフローの受信者がトランスポートとメディアの品質メトリックをそのRTPフローの送信者に定期的に送信できるメカニズムを提供しています。 送信者は、この情報を使用して輻輳制御を行うことができます。 この目的のための標準化されたメッセージがないため、輻輳制御アルゴリズムの設計者は、それぞれの設計に必要なパラメーターだけを伝える独自のRTCPメッセージを開発してきました。 その直接の結果として、異なる輻輳制御の設計の間に相互運用性がありません。 アルゴリズムの進化と設計間（たとえば、異なるレート適応アルゴリズム間）の相互運用性を可能にするために、汎用的な輻輳制御フィードバックの形式があることが強く望まれます。

To help achieve interoperability for unicast RTP congestion control, this memo specifies a common RTCP feedback packet format that can be used by Network-Assisted Dynamic Adaptation (NADA) [RFC8698], Self-Clocked Rate Adaptation for Multimedia (SCReAM) [RFC8298], Google Congestion Control [Google-GCC], and Shared Bottleneck Detection [RFC8382], and, hopefully, also by future RTP congestion control algorithms.

ユニキャストRTP輻輳制御の相互運用性の実現に役立てるため、このメモは共通のRTCPフィードバックパケットの形式を規定します。 この形式は、Network-Assisted Dynamic Adaptation（NADA）[RFC8698]、 Self-Clocked Rate Adaptation for Multimedia（SCReAM）[RFC8298]、Google Congestion Control[Google-GCC]、Shared Bottleneck Detection[RFC8382]で使用でき、将来のRTP輻輳制御アルゴリズムでも使用されることが期待されます。

3. RTCP Feedback for Congestion Control

3. 輻輳制御のためのRTCPフィードバック

Based on an analysis of NADA [RFC8698], SCReAM [RFC8298], Google Congestion Control [Google-GCC], and Shared Bottleneck Detection [RFC8382], the following per-RTP packet congestion control feedback information has been determined to be necessary:

NADA [RFC8698]、SCReAM [RFC8298]、Google Congestion Control [Google-GCC]、Shared Bottleneck Detection [RFC8382]の分析に基づき、RTPパケットごとの輻輳制御フィードバック情報として次のものが必要であると判断されました。

RTP Sequence Number:
The receiver of an RTP flow needs to feed the sequence numbers of the received RTP packets back to the sender, so the sender can determine which packets were received and which were lost. Packet loss is used as an indication of congestion by many congestion control algorithms.
Packet Arrival Time:
The receiver of an RTP flow needs to feed the arrival time of each RTP packet back to the sender. Packet delay and/or delay variation (jitter) is used as a congestion signal by some congestion control algorithms.
Packet Explicit Congestion Notification (ECN) Marking:
If ECN [RFC3168] [RFC6679] is used, it is necessary to feed back the 2-bit ECN mark in received RTP packets, indicating for each RTP packet whether it is marked not-ECT, ECT(0), ECT(1), or ECN Congestion Experienced (ECN-CE). ("ECT" stands for "ECN-Capable Transport".) If the path used by the RTP traffic is ECN capable, the sender can use ECN-CE marking information as a congestion control signal.
RTPシーケンス番号：
RTPフローの受信者は、受信したRTPパケットのシーケンス番号を送信者にフィードバックする必要があります。 これにより、送信者はどのパケットが受信され、どのパケットが失われたかを判断できます。 多くの輻輳制御アルゴリズムは、パケット損失を輻輳の兆候として使用します。
パケット到着時刻：
RTPフローの受信者は、各RTPパケットの到着時刻を送信者にフィードバックする必要があります。 一部の輻輳制御アルゴリズムは、パケットの遅延と遅延変動（ジッター）の一方または両方を輻輳シグナルとして使用します。
パケットの明示的輻輳通知（ECN）マーキング：
ECN[RFC3168] [RFC6679]を使用する場合は、受信したRTPパケットの2ビットのECNマークをフィードバックし、各RTPパケットがnot-ECT、ECT(0)、ECT(1)、ECN Congestion Experienced（ECN-CE）のいずれでマークされているかを示す必要があります。 （「ECT」は「ECN-Capable Transport」の略です。） RTPトラフィックが使用するパスがECNに対応している場合、送信者はECN-CEマーキングの情報を輻輳制御シグナルとして使用できます。

Every RTP flow is identified by its Synchronization Source (SSRC) identifier. Accordingly, the RTCP feedback format needs to group its reports by SSRC, sending one report block per received SSRC.

すべてのRTPフローは、その同期ソース（SSRC）識別子によって識別されます。 したがって、RTCPフィードバックの形式では、報告をSSRCごとにまとめ、受信したSSRCごとに1つの報告ブロックを送信する必要があります。

As a practical matter, we note that host operating system (OS) process interruptions can occur at inopportune times. Accordingly, recording RTP packet send times at the sender, and the corresponding RTP packet arrival times at the receiver, needs to be done with deliberate care. This is because the time duration of host OS interruptions can be significant relative to the precision desired in the one-way delay estimates. Specifically, the send time needs to be recorded at the last opportunity prior to transmitting the RTP packet at the sender, and the arrival time at the receiver needs to be recorded at the earliest available opportunity.

実際上の問題として、ホストのオペレーティングシステム（OS）によるプロセスの中断が都合の悪いタイミングで発生する可能性があることに注意してください。 したがって、送信者でのRTPパケットの送信時刻と、それに対応する受信者でのRTPパケットの到着時刻の記録は、十分な注意を払って行う必要があります。 これは、ホストOSによる中断の継続時間が、片方向遅延の推定に求められる精度と比べて大きくなる可能性があるためです。 具体的には、送信時刻は送信者がRTPパケットを送信する直前の最後の機会に記録する必要があり、受信者での到着時刻は利用可能な最も早い機会に記録する必要があります。

3.1. RTCP Congestion Control Feedback Report

3.1. RTCP輻輳制御フィードバック報告

Congestion control feedback can be sent as part of a regular scheduled RTCP report or in an RTP/AVPF early feedback packet. If sent as early feedback, congestion control feedback MAY be sent in a non-compound RTCP packet [RFC5506] if the RTP/AVPF profile [RFC4585] or the RTP/SAVPF profile [RFC5124] is used.

輻輳制御フィードバックは、定期的にスケジュールされたRTCP報告の一部として、またはRTP/AVPFの早期フィードバックパケットで送信できます。 早期フィードバックとして送信する場合、RTP/AVPFプロファイル[RFC4585]またはRTP/SAVPFプロファイル[RFC5124]を使用しているなら、輻輳制御フィードバックを非複合RTCPパケット[RFC5506]で送信してもよいです（MAY）。

Irrespective of how it is transported, the congestion control feedback is sent as a Transport-Layer Feedback Message (RTCP packet type 205). The format of this RTCP packet is shown in Figure 1:

どのように転送されるかにかかわらず、輻輳制御フィードバックはトランスポート層フィードバックメッセージ（RTCPパケットタイプ205）として送信されます。 このRTCPパケットの形式をFigure 1に示します。

The first 8 octets comprise a standard RTCP header, with PT=205 and FMT=11 indicating that this is a congestion control feedback packet, and with the SSRC set to that of the sender of the RTCP packet.

最初の8オクテットは標準のRTCPヘッダーで構成されます。 PT=205とFMT=11は、これが輻輳制御フィードバックパケットであることを示し、SSRCにはRTCPパケットの送信者のSSRCを設定します。

Section 6.1 of [RFC4585] requires the RTCP header to be followed by the SSRC of the RTP flow being reported upon. Accordingly, the RTCP header is followed by a report block for each SSRC from which RTP packets have been received, followed by a Report Timestamp.

[RFC4585]のSection 6.1は、RTCPヘッダーの後に報告対象のRTPフローのSSRCが続くことを要求しています。 したがって、RTCPヘッダーの後には、RTPパケットを受信したSSRCごとの報告ブロックが続き、その後に報告タイムスタンプ（Report Timestamp）が続きます。

Each report block begins with the SSRC of the received RTP stream on which it is reporting. Following this, the report block contains a 16-bit packet metric block for each RTP packet that has a sequence number in the range begin_seq to begin_seq+num_reports inclusive (calculated using arithmetic modulo 65536 to account for possible sequence number wrap-around). If the number of 16-bit packet metric blocks included in the report block is not a multiple of two, then 16 bits of zero padding MUST be added after the last packet metric block, to align the end of the packet metric blocks with the next 32-bit boundary. The value of num_reports MAY be 0, indicating that there are no packet metric blocks included for that SSRC. Each report block MUST NOT include more than 16384 packet metric blocks (i.e., it MUST NOT report on more than one quarter of the sequence number space in a single report).

各報告ブロックは、報告対象の受信したRTPストリームのSSRCで始まります。 その後、報告ブロックには、シーケンス番号がbegin_seqからbegin_seq+num_reportsまで（両端を含む）の範囲にある各RTPパケットについて、16ビットのパケットメトリックブロックが含まれます（シーケンス番号のラップアラウンドの可能性を考慮して、65536を法とする算術で計算します）。 報告ブロックに含まれる16ビットのパケットメトリックブロックの数が2の倍数でない場合、パケットメトリックブロックの終わりを次の32ビット境界にそろえるために、最後のパケットメトリックブロックの後に16ビットのゼロパディングを追加しなければなりません（MUST）。 num_reportsの値は0でもよいです（MAY）。 これは、そのSSRCについてパケットメトリックブロックが含まれていないことを示します。 各報告ブロックには、16384個を超えるパケットメトリックブロックを含めてはなりません（MUST NOT）（つまり、1つの報告でシーケンス番号空間の4分の1を超える範囲について報告してはなりません（MUST NOT））。

The contents of each 16-bit packet metric block comprise the R, ECN, and ATO fields as follows:

各16ビットのパケットメトリックブロックの内容は、次のようにR、ECN、ATOの各フィールドで構成されます。

Received (R, 1 bit):
A boolean that indicates whether the packet was received.  0 indicates that the packet was not yet received and the subsequent 15 bits (ECN and ATO) in this 16-bit packet metric block are also set to 0 and MUST be ignored. 1 indicates that the packet was received and the subsequent bits in the block need to be parsed.
ECN (2 bits):
The echoed ECN mark of the packet. These bits are set to 00 if not received or if ECN is not used.
Arrival time offset (ATO, 13 bits):
The arrival time of the RTP packet at the receiver, as an offset before the time represented by the Report Timestamp (RTS) field of this RTCP congestion control feedback report. The ATO field is in units of 1/1024 seconds (this unit is chosen to give exact offsets from the RTS field) so, for example, an ATO value of 512 indicates that the corresponding RTP packet arrived exactly half a second before the time instant represented by the RTS field. If the measured value is greater than 8189/1024 seconds (the value that would be coded as 0x1FFD), the value 0x1FFE MUST be reported to indicate an over-range measurement. If the measurement is unavailable or if the arrival time of the RTP packet is after the time represented by the RTS field, then an ATO value of 0x1FFF MUST be reported for the packet.
Received（R、1ビット）：
パケットが受信されたかどうかを示す真偽値です。 0はパケットがまだ受信されていないことを示し、この16ビットのパケットメトリックブロック内の後続の15ビット（ECNとATO）も0に設定され、それらは無視しなければなりません（MUST）。 1はパケットが受信されたことを示し、ブロック内の後続のビットを解析する必要があります。
ECN（2ビット）：
パケットのECNマークをエコーしたものです。 パケットが受信されていない場合、またはECNが使用されていない場合、これらのビットは00に設定されます。
Arrival time offset（ATO、13ビット）：
受信者でのRTPパケットの到着時刻です。 このRTCP輻輳制御フィードバック報告の報告タイムスタンプ（RTS）フィールドが表す時刻より前へのオフセットとして表します。 ATOフィールドの単位は1/1024秒です（この単位は、RTSフィールドからの正確なオフセットが得られるように選択されています）。 したがって、たとえばATOの値512は、対応するRTPパケットがRTSフィールドの表す時刻のちょうど0.5秒前に到着したことを示します。 測定値が8189/1024秒（0x1FFDとして符号化される値）を超える場合、範囲外の測定値であることを示すために値0x1FFEを報告しなければなりません（MUST）。 測定値が利用できない場合、またはRTPパケットの到着時刻がRTSフィールドの表す時刻より後である場合は、そのパケットについてATOの値0x1FFFを報告しなければなりません（MUST）。

The RTCP congestion control feedback report packet concludes with the Report Timestamp field (RTS, 32 bits). This denotes the time instant on which this packet is reporting and is the instant from which the arrival time offset values are calculated. The value of the RTS field is derived from the same clock used to generate the NTP timestamp field in RTCP Sender Report (SR) packets. It is formatted as the middle 32 bits of an NTP format timestamp, as described in Section 4 of [RFC3550].

RTCP輻輳制御フィードバック報告パケットは、報告タイムスタンプフィールド（RTS、32ビット）で終わります。 これは、このパケットが報告の対象とする時刻を表し、到着時刻オフセットの値を計算する基準となる時刻です。 RTSフィールドの値は、RTCP送信者報告（SR）パケットのNTPタイムスタンプフィールドの生成に使用するのと同じクロックから導出されます。 [RFC3550]のSection 4で説明されているように、この値はNTP形式のタイムスタンプの中央の32ビットとしてフォーマットされます。

RTCP Congestion Control Feedback Packets SHOULD include a report block for every active SSRC. The sequence number ranges reported on in consecutive reports for a given SSRC will generally be contiguous, but overlapping reports MAY be sent (and need to be sent in cases where RTP packet reordering occurs across the boundary between consecutive reports). If an RTP packet was reported as received in one report, that packet MUST also be reported as received in any overlapping reports sent later that cover its sequence number range. If feedback reports covering overlapping sequence number ranges are sent, information in later feedback reports may update any data sent in previous reports for RTP packets included in both feedback reports.

RTCP輻輳制御フィードバックパケットには、アクティブなすべてのSSRCについての報告ブロックを含めるべきです（SHOULD）。 特定のSSRCについて連続する報告で報告されるシーケンス番号の範囲は、一般には連続しますが、重複する報告を送信してもよいです（MAY）（また、連続する報告の境界をまたいでRTPパケットの並べ替えが発生した場合には、重複する報告を送信する必要があります）。 あるRTPパケットが1つの報告で受信済みとして報告された場合、そのパケットのシーケンス番号の範囲をカバーする、後で送信されるすべての重複する報告でも、そのパケットを受信済みとして報告しなければなりません（MUST）。 重複するシーケンス番号の範囲をカバーするフィードバック報告を送信する場合、後のフィードバック報告の情報によって、両方のフィードバック報告に含まれるRTPパケットについて以前の報告で送信されたデータが更新されることがあります。

RTCP Congestion Control Feedback Packets can be large if they are sent infrequently relative to the number of RTP data packets. If an RTCP Congestion Control Feedback Packet is too large to fit within the path MTU, its sender SHOULD split it into multiple feedback packets. The RTCP reporting interval SHOULD be chosen such that feedback packets are sent often enough that they are small enough to fit within the path MTU. ([RTCP-Multimedia-Feedback] discusses how to choose the reporting interval; specifications for RTP congestion control algorithms can also provide guidance.)

RTCP輻輳制御フィードバックパケットは、RTPデータパケットの数に比べて送信頻度が低い場合、大きくなる可能性があります。 RTCP輻輳制御フィードバックパケットが大きすぎてパスMTUに収まらない場合、その送信者はそれを複数のフィードバックパケットに分割すべきです（SHOULD）。 RTCPの報告間隔は、フィードバックパケットがパスMTUに収まるほど小さくなるよう、十分な頻度で送信されるように選択すべきです（SHOULD）。 （[RTCP-Multimedia-Feedback]では報告間隔の選択方法について議論しています。RTP輻輳制御アルゴリズムの仕様でもガイダンスが提供されることがあります。）

If duplicate copies of a particular RTP packet are received, then the arrival time of the first copy to arrive MUST be reported. If any of the copies of the duplicated packet are ECN-CE marked, then an ECN-CE mark MUST be reported for that packet; otherwise, the ECN mark of the first copy to arrive is reported.

特定のRTPパケットの重複したコピーを受信した場合は、最初に到着したコピーの到着時刻を報告しなければなりません（MUST）。 重複したパケットのコピーのいずれかがECN-CEでマークされている場合は、そのパケットについてECN-CEマークを報告しなければなりません（MUST）。 そうでない場合は、最初に到着したコピーのECNマークを報告します。

If no packets are received from an SSRC in a reporting interval, a report block MAY be sent with begin_seq set to the highest sequence number previously received from that SSRC and num_reports set to 0 (or the report can simply be omitted). The corresponding Sender Report / Receiver Report (SR/RR) packet will have a non-increased extended highest sequence number received field that will inform the sender that no packets have been received, but it can ease processing to have that information available in the congestion control feedback reports too.

報告間隔内にあるSSRCからパケットを1つも受信しなかった場合、begin_seqにそのSSRCから以前に受信した最大のシーケンス番号を設定し、num_reportsに0を設定した報告ブロックを送信してもよいです（MAY）（または、単に報告を省略することもできます）。 対応する送信者報告／受信者報告（SR/RR）パケットでは、受信した拡張最大シーケンス番号（extended highest sequence number received）フィールドが増加していないため、パケットを受信していないことが送信者に伝わります。 しかし、その情報を輻輳制御フィードバック報告でも利用できるようにすると、処理が容易になる場合があります。

A report block indicating that certain RTP packets were lost is not to be interpreted as a request to retransmit the lost packets. The receiver of such a report might choose to retransmit such packets, provided a retransmission payload format has been negotiated, but there is no requirement that it do so.

特定のRTPパケットが失われたことを示す報告ブロックを、失われたパケットの再送のリクエストとして解釈されるものではありません。 そのような報告の受信者は、再送用のペイロード形式がネゴシエートされていれば、そのようなパケットを再送することを選択するかもしれませんが、そうすることは要件ではありません。

4. Feedback Frequency and Overhead

4. フィードバックの頻度とオーバーヘッド

There is a trade-off between speed and accuracy of reporting, and the overhead of the reports. [RTCP-Multimedia-Feedback] discusses this trade-off, suggests desirable RTCP feedback rates, and provides guidance on how to configure, for example, the RTCP bandwidth fraction to make appropriate use of the reporting block described in this memo. Specifications for RTP congestion control algorithms can also provide guidance.

報告の速さおよび正確さと、報告のオーバーヘッドとの間にはトレードオフがあります。 [RTCP-Multimedia-Feedback]では、このトレードオフについて議論し、望ましいRTCPフィードバックのレートを提案し、このメモで説明する報告ブロックを適切に使用するために、たとえばRTCP帯域幅の割合をどのように設定するかについてのガイダンスを提供しています。 RTP輻輳制御アルゴリズムの仕様でもガイダンスが提供されることがあります。

It is generally understood that congestion control algorithms work better with more frequent feedback. However, RTCP bandwidth and transmission rules put some upper limits on how frequently the RTCP feedback messages can be sent from an RTP receiver to the RTP sender. In many cases, sending feedback once per frame is an upper bound before the reporting overhead becomes excessive, although this will depend on the media rate and more frequent feedback might be needed with high-rate media flows [RTCP-Multimedia-Feedback]. Analysis [feedback-requirements] has also shown that some candidate congestion control algorithms can operate with less frequent feedback, using a feedback interval range of 50-200 ms. Applications need to negotiate an appropriate congestion control feedback interval at session setup time, based on the choice of congestion control algorithm, the expected media bitrate, and the acceptable feedback overhead.

一般に、輻輳制御アルゴリズムはフィードバックの頻度が高いほどよく機能すると理解されています。 しかし、RTCPの帯域幅と送信の規則により、RTPの受信者からRTPの送信者へRTCPフィードバックメッセージを送信できる頻度には上限があります。 多くの場合、報告のオーバーヘッドが過大にならない上限は、フレームごとに1回のフィードバック送信です。 ただし、これはメディアのレートに依存し、高レートのメディアフローではより頻繁なフィードバックが必要になる場合があります[RTCP-Multimedia-Feedback]。 また、分析[feedback-requirements]では、一部の候補となる輻輳制御アルゴリズムは、50～200ミリ秒の範囲のフィードバック間隔を使用して、より低頻度のフィードバックで動作できることが示されています。 アプリケーションは、輻輳制御アルゴリズムの選択、予想されるメディアのビットレート、許容できるフィードバックのオーバーヘッドに基づいて、セッションの確立時に適切な輻輳制御フィードバック間隔をネゴシエートする必要があります。

5. Response to Loss of Feedback Packets

5. フィードバックパケットの損失への対応

Like all RTCP packets, RTCP Congestion Control Feedback Packets might be lost. All RTP congestion control algorithms MUST specify how they respond to the loss of feedback packets.

すべてのRTCPパケットと同様に、RTCP輻輳制御フィードバックパケットも失われる可能性があります。 すべてのRTP輻輳制御アルゴリズムは、フィードバックパケットの損失にどのように対応するかを規定しなければなりません（MUST）。

RTCP packets do not contain a sequence number, so loss of feedback packets has to be inferred based on the time since the last feedback packet. If only a single congestion control feedback packet is lost, an appropriate response is to assume that the level of congestion has remained roughly the same as the previous report. However, if multiple consecutive congestion control feedback packets are lost, then the media sender SHOULD rapidly reduce its sending rate as this likely indicates a path failure. The RTP circuit breaker specification [RFC8083] provides further guidance.

RTCPパケットにはシーケンス番号が含まれていないため、フィードバックパケットの損失は、最後のフィードバックパケットからの経過時間に基づいて推測する必要があります。 輻輳制御フィードバックパケットが1つだけ失われた場合は、輻輳のレベルが前回の報告とほぼ同じままであると仮定するのが適切な対応です。 しかし、連続する複数の輻輳制御フィードバックパケットが失われた場合は、パスの障害を示している可能性が高いため、メディアの送信者は送信レートを急速に下げるべきです（SHOULD）。 RTPサーキットブレーカーの仕様[RFC8083]には、さらなるガイダンスがあります。

6. SDP Signaling

6. SDPシグナリング

A new "ack" feedback parameter, "ccfb", is defined for use with the "a=rtcp-fb:" Session Description Protocol (SDP) extension to indicate the use of the RTP Congestion Control Feedback Packet format defined in Section 3. The ABNF definition [RFC5234] of this SDP parameter extension is:

Section 3で定義したRTP輻輳制御フィードバックパケットの形式を使用することを示すために、「a=rtcp-fb:」セッション記述プロトコル（SDP）拡張で使用する新しい「ack」フィードバックパラメーター「ccfb」を定義します。 このSDPパラメーター拡張のABNF定義[RFC5234]は次のとおりです。

        rtcp-fb-ack-param = <See Section 4.2 of [RFC4585]>
        rtcp-fb-ack-param =/ ccfb-par
        ccfb-par          = SP "ccfb"
        rtcp-fb-ack-param = <See Section 4.2 of [RFC4585]>
        rtcp-fb-ack-param =/ ccfb-par
        ccfb-par          = SP "ccfb"

The payload type used with "ccfb" feedback MUST be the wildcard type ("*"). This implies that the congestion control feedback is sent for all payload types in use in the session, including any Forward Error Correction (FEC) and retransmission payload types. An example of the resulting SDP attribute is:

「ccfb」フィードバックで使用するペイロードタイプは、ワイルドカードタイプ（「*」）でなければなりません（MUST）。 これは、前方誤り訂正（FEC）や再送のペイロードタイプを含め、セッションで使用されているすべてのペイロードタイプについて輻輳制御フィードバックが送信されることを意味します。 結果として得られるSDP属性の例は次のとおりです。 

        a=rtcp-fb:* ack ccfb
        a=rtcp-fb:* ack ccfb

The offer/answer rules for these SDP feedback parameters are specified in Section 4.2 of the RTP/AVPF profile [RFC4585].

これらのSDPフィードバックパラメーターのオファー/アンサーの規則は、RTP/AVPFプロファイル[RFC4585]のSection 4.2で規定されています。

An SDP offer might indicate support for both the congestion control feedback mechanism specified in this memo and one or more alternative congestion control feedback mechanisms that offer substantially the same semantics. In this case, the answering party SHOULD include only one of the offered congestion control feedback mechanisms in its answer. If a subsequent offer containing the same set of congestion control feedback mechanisms is received, the generated answer SHOULD choose the same congestion control feedback mechanism as in the original answer where possible.

SDPオファーは、このメモで規定する輻輳制御フィードバックメカニズムと、実質的に同じセマンティクスを提供する1つ以上の代替の輻輳制御フィードバックメカニズムの両方のサポートを示すことがあります。 この場合、アンサー側は、オファーされた輻輳制御フィードバックメカニズムのうち1つだけをアンサーに含めるべきです（SHOULD）。 同じ輻輳制御フィードバックメカニズムの組を含む後続のオファーを受信した場合、生成するアンサーでは、可能であれば元のアンサーと同じ輻輳制御フィードバックメカニズムを選択すべきです（SHOULD）。

When the SDP BUNDLE extension [RFC8843] is used for multiplexing, the "a=rtcp-fb:" attribute has multiplexing category IDENTICAL-PER-PT [RFC8859].

多重化のためにSDP BUNDLE拡張[RFC8843]を使用する場合、「a=rtcp-fb:」属性の多重化カテゴリーはIDENTICAL-PER-PT [RFC8859]です。

7. Relationship to RFC 6679

7. RFC 6679との関係

The use of Explicit Congestion Notification (ECN) with RTP is described in [RFC6679], which specifies how to negotiate the use of ECN with RTP and defines an RTCP ECN Feedback Packet to carry ECN feedback reports. It uses an SDP "a=ecn-capable-rtp:" attribute to negotiate the use of ECN, and the "a=rtcp-fb:" attribute with the "nack" parameter "ecn" to negotiate the use of RTCP ECN Feedback Packets.

RTPでの明示的輻輳通知（ECN）の使用については[RFC6679]で説明されています。 この文書は、RTPでのECNの使用をネゴシエートする方法を規定し、ECNフィードバック報告を運ぶRTCP ECNフィードバックパケットを定義しています。 ECNの使用をネゴシエートするためにSDPの「a=ecn-capable-rtp:」属性を使用し、RTCP ECNフィードバックパケットの使用をネゴシエートするために「nack」パラメーター「ecn」を持つ「a=rtcp-fb:」属性を使用します。

The RTCP ECN Feedback Packet is not useful when ECN is used with the RTP Congestion Control Feedback Packet defined in this memo, since it provides duplicate information. When congestion control feedback is to be used with RTP and ECN, the SDP offer generated MUST include an "a=ecn-capable-rtp:" attribute to negotiate ECN support, along with an "a=rtcp-fb:" attribute with the "ack" parameter "ccfb" to indicate that the RTP Congestion Control Feedback Packet can be used. The "a=rtcp-fb:" attribute MAY also include the "nack" parameter "ecn" to indicate that the RTCP ECN Feedback Packet is also supported. If an SDP offer signals support for both RTP Congestion Control Feedback Packets and the RTCP ECN Feedback Packet, the answering party SHOULD signal support for one, but not both, formats in its SDP answer to avoid sending duplicate feedback.

このメモで定義するRTP輻輳制御フィードバックパケットとともにECNを使用する場合、RTCP ECNフィードバックパケットは重複した情報を提供するため有用ではありません。 RTPとECNで輻輳制御フィードバックを使用する場合、生成するSDPオファーには、ECNのサポートをネゴシエートするための「a=ecn-capable-rtp:」属性と、RTP輻輳制御フィードバックパケットを使用できることを示すための「ack」パラメーター「ccfb」を持つ「a=rtcp-fb:」属性を含めなければなりません（MUST）。 RTCP ECNフィードバックパケットもサポートしていることを示すために、「a=rtcp-fb:」属性に「nack」パラメーター「ecn」も含めてもよいです（MAY）。 SDPオファーがRTP輻輳制御フィードバックパケットとRTCP ECNフィードバックパケットの両方のサポートを通知している場合、アンサー側は、重複したフィードバックの送信を避けるために、SDPアンサーでどちらか一方の形式のみのサポートを通知すべきです（SHOULD）。

When using ECN with RTP, the guidelines in Section 7.2 of [RFC6679] MUST be followed to initiate the use of ECN in an RTP session. The guidelines in Section 7.3 of [RFC6679] regarding the ongoing use of ECN within an RTP session MUST also be followed, with the exception that feedback is sent using the RTCP Congestion Control Feedback Packets described in this memo rather than using RTP ECN Feedback Packets. Similarly, the guidance in Section 7.4 of [RFC6679] related to detecting failures MUST be followed, with the exception that the necessary information is retrieved from the RTCP Congestion Control Feedback Packets rather than from RTP ECN Feedback Packets.

RTPでECNを使用する場合、RTPセッションでECNの使用を開始するには、[RFC6679]のSection 7.2のガイドラインに従わなければなりません（MUST）。 RTPセッション内でのECNの継続的な使用に関する[RFC6679]のSection 7.3のガイドラインにも従わなければなりません（MUST）。 ただし、フィードバックはRTP ECNフィードバックパケットではなく、このメモで説明するRTCP輻輳制御フィードバックパケットを使用して送信します。 同様に、障害の検出に関する[RFC6679]のSection 7.4のガイダンスに従わなければなりません（MUST）。 ただし、必要な情報はRTP ECNフィードバックパケットではなく、RTCP輻輳制御フィードバックパケットから取得します。

8. Design Rationale

8. 設計の根拠

The primary function of RTCP SR/RR packets is to report statistics on the reception of RTP packets. The reception report blocks sent in these packets contain information about observed jitter, fractional packet loss, and cumulative packet loss. It was intended that this information could be used to support congestion control algorithms, but experience has shown that it is not sufficient for that purpose. An efficient congestion control algorithm requires more fine-grained information on per-packet reception quality than is provided by SR/RR packets to react effectively. The feedback format defined in this memo provides such fine-grained feedback.

RTCP SR/RRパケットの主な機能は、RTPパケットの受信に関する統計を報告することです。 これらのパケットで送信される受信報告ブロックには、観測されたジッター、パケット損失率、累積パケット損失に関する情報が含まれています。 この情報は輻輳制御アルゴリズムをサポートするために使用できることが意図されていましたが、経験上、その目的には十分ではないことがわかっています。 効率的な輻輳制御アルゴリズムが効果的に反応するには、SR/RRパケットが提供するよりもきめ細かい、パケットごとの受信品質に関する情報が必要です。 このメモで定義するフィードバック形式は、そのようなきめ細かいフィードバックを提供します。

Several other RTCP extensions also provide more detailed feedback than SR/RR packets:

他のいくつかのRTCP拡張も、SR/RRパケットより詳細なフィードバックを提供しています。

TMMBR:
The codec control messages for the RTP/AVPF profile [RFC5104] include a Temporary Maximum Media Stream Bit Rate Request (TMMBR) message. This is used to convey a temporary maximum bitrate limitation from a receiver of RTP packets to their sender. Even though it was not designed to replace congestion control, TMMBR has been used as a means to do receiver-based congestion control where the session bandwidth is high enough to send frequent TMMBR messages, especially when used with non-compound RTCP packets [RFC5506]. This approach requires the receiver of the RTP packets to monitor their reception, determine the level of congestion, and recommend a maximum bitrate suitable for current available bandwidth on the path; it also assumes that the RTP sender can⁠/will respect that bitrate. This is the opposite of the sender-based congestion control approach suggested in this memo, so TMMBR cannot be used to convey the information needed for sender-based congestion control. TMMBR could, however, be viewed as a complementary mechanism that can inform the sender of the receiver's current view of an acceptable maximum bitrate. Mechanisms that convey the receiver's estimate of the maximum available bitrate provide similar feedback.
RTCP Extended Reports (XRs):
Numerous RTCP XR blocks have been defined to report details of packet loss, arrival times [RFC3611], delay [RFC6843], and ECN marking [RFC6679]. It is possible to combine several such XR blocks into a compound RTCP packet, to report the detailed loss, arrival time, and ECN marking information needed for effective sender-based congestion control. However, the result has high overhead in terms of both bandwidth and complexity, due to the need to stack multiple reports.
Transport-wide Congestion Control:
The format defined in this memo provides individual feedback on each SSRC. An alternative is to add a header extension to each RTP packet, containing a single, transport-wide, packet sequence number, then have the receiver send RTCP reports giving feedback on these additional sequence numbers [RTP-Ext-for-CC]. Such an approach increases the size of each RTP packet by 8 octets, due to the header extension, but reduces the size of the RTCP feedback packets, and can simplify the rate calculation at the sender if it maintains a single rate limit that applies to all RTP packets sent, irrespective of their SSRC. Equally, the use of transport-wide feedback makes it more difficult to adapt the sending rate, or respond to lost packets, based on the reception and/or loss patterns observed on a per-SSRC basis (for example, to perform differential rate control and repair for audio and video flows, based on knowledge of what packets from each flow were lost). Transport-wide feedback is also a less natural fit with the wider RTP framework, which makes extensive use of per-SSRC sequence numbers and feedback.
TMMBR：
RTP/AVPFプロファイルのためのコーデック制御メッセージ[RFC5104]には、一時最大メディアストリームビットレート要求（Temporary Maximum Media Stream Bit Rate Request; TMMBR）メッセージが含まれています。 これは、一時的な最大ビットレートの制限をRTPパケットの受信者からその送信者に伝えるために使用されます。 TMMBRは輻輳制御を置き換えるように設計されたものではありませんが、特に非複合RTCPパケット[RFC5506]とともに使用する場合など、セッションの帯域幅がTMMBRメッセージを頻繁に送信できるほど大きい場合に、受信者ベースの輻輳制御を行う手段として使用されてきました。 このアプローチでは、RTPパケットの受信者がその受信を監視し、輻輳のレベルを判断し、パス上で現在利用可能な帯域幅に適した最大ビットレートを推奨する必要があります。 また、RTPの送信者がそのビットレートを尊重できる（尊重する）ことを前提としています。 これは、このメモで提案する送信者ベースの輻輳制御のアプローチとは正反対であるため、TMMBRを送信者ベースの輻輳制御に必要な情報を伝えるために使用することはできません。 ただし、TMMBRは、許容できる最大ビットレートについての受信者の現在の見解を送信者に知らせることができる、補完的なメカニズムと見なすこともできます。 受信者による利用可能な最大ビットレートの推定値を伝えるメカニズムも、同様のフィードバックを提供します。
RTCP拡張報告（XR）：
パケット損失、到着時刻[RFC3611]、遅延[RFC6843]、ECNマーキング[RFC6679]の詳細を報告するために、多数のRTCP XRブロックが定義されています。 効果的な送信者ベースの輻輳制御に必要な、損失、到着時刻、ECNマーキングの詳細な情報を報告するために、そのようなXRブロックのいくつかを組み合わせて1つの複合RTCPパケットにすることは可能です。 しかし、複数の報告を積み重ねる必要があるため、結果として帯域幅と複雑さの両面でオーバーヘッドが大きくなります。
Transport-wide Congestion Control：
このメモで定義する形式は、各SSRCについて個別のフィードバックを提供します。 代替案として、トランスポート全体で単一のパケットシーケンス番号を含むヘッダー拡張を各RTPパケットに追加し、受信者がこれらの追加のシーケンス番号についてフィードバックするRTCP報告を送信する方法があります[RTP-Ext-for-CC]。 このようなアプローチでは、ヘッダー拡張のために各RTPパケットのサイズが8オクテット増加しますが、RTCPフィードバックパケットのサイズは小さくなります。 また、送信者がSSRCにかかわらず送信するすべてのRTPパケットに適用される単一のレート制限を維持している場合には、送信者でのレート計算を簡素化できます。 その一方で、トランスポート全体でのフィードバックを使用すると、SSRCごとに観測された受信や損失のパターンに基づいて送信レートを調整したり、失われたパケットに対応したりすることが難しくなります（たとえば、各フローのどのパケットが失われたかの知識に基づいて、音声フローと映像フローに対して異なるレート制御と修復を行う場合など）。 また、トランスポート全体でのフィードバックは、SSRCごとのシーケンス番号とフィードバックを広く使用している、より広範なRTPフレームワークにはあまり自然に適合しません。

Considering these issues, we believe it appropriate to design a new RTCP feedback mechanism to convey information for sender-based congestion control algorithms. The new congestion control feedback RTCP packet described in Section 3 provides such a mechanism.

これらの問題を考慮して、送信者ベースの輻輳制御アルゴリズムのための情報を伝える新しいRTCPフィードバックメカニズムを設計することが適切であると私たちは考えます。 Section 3で説明する新しい輻輳制御フィードバックRTCPパケットは、そのようなメカニズムを提供します。

10. Security Considerations

10. セキュリティーに関する考慮事項

The security considerations of the RTP specification [RFC3550], the applicable RTP profile (e.g., [RFC3551], [RFC3711], or [RFC4585]), and the RTP congestion control algorithm being used (e.g., [RFC8698], [RFC8298], [Google-GCC], or [RFC8382]) apply.

RTP仕様[RFC3550]、適用されるRTPプロファイル（たとえば、[RFC3551]、[RFC3711]、[RFC4585]）、使用するRTP輻輳制御アルゴリズム（たとえば、[RFC8698]、[RFC8298]、[Google-GCC]、[RFC8382]）のセキュリティーに関する考慮事項が適用されます。

A receiver that intentionally generates inaccurate RTCP congestion control feedback reports might be able to trick the sender into sending at a greater rate than the path can support, thereby causing congestion on the path. This scenario will negatively impact the quality of experience of that receiver, potentially causing both denial of service to other traffic sharing the path and excessively increased resource usage at the media sender. Since RTP is an unreliable transport, a sender can intentionally drop a packet, leaving a gap in the RTP sequence number space without causing serious harm, to check that the receiver is correctly reporting losses. (This needs to be done with care and some awareness of the media data being sent, to limit impact on the user experience.)

意図的に不正確なRTCP輻輳制御フィードバック報告を生成する受信者は、パスがサポートできるよりも高いレートで送信するように送信者をだまし、それによってパス上で輻輳を引き起こすことができるかもしれません。 このシナリオは、その受信者の体感品質に悪影響を及ぼし、パスを共有する他のトラフィックに対するサービス拒否と、メディアの送信者でのリソース使用量の過度な増加の両方を引き起こす可能性があります。 RTPは信頼性のないトランスポートであるため、送信者は、受信者が損失を正しく報告していることを確認するために、深刻な害を引き起こすことなく、意図的にパケットを破棄してRTPシーケンス番号空間に欠落を残すことができます。 （ユーザー体験への影響を抑えるために、これは注意深く、送信するメディアデータをある程度意識して行う必要があります。）

An on-path attacker that can modify RTCP Congestion Control Feedback Packets can change the reports to trick the sender into sending at either an excessively high or excessively low rate, leading to denial of service. The secure RTCP profile [RFC3711] can be used to authenticate RTCP packets to protect against this attack.

RTCP輻輳制御フィードバックパケットを改変できる経路上の攻撃者は、報告を変更して、過度に高いレートまたは過度に低いレートで送信するように送信者をだまし、サービス拒否を引き起こすことができます。 この攻撃から保護するために、セキュアRTCPプロファイル[RFC3711]を使用してRTCPパケットを認証できます。

An off-path attacker that can spoof RTCP Congestion Control Feedback Packets can similarly trick a sender into sending at an incorrect rate, leading to denial of service. This attack is difficult, since the attacker needs to guess the SSRC and sequence number in addition to the destination transport address. As with on-path attacks, the secure RTCP profile [RFC3711] can be used to authenticate RTCP packets to protect against this attack.

RTCP輻輳制御フィードバックパケットを偽装できる経路外の攻撃者も、同様に不正なレートで送信するように送信者をだまし、サービス拒否を引き起こすことができます。 攻撃者は宛先のトランスポートアドレスに加えてSSRCとシーケンス番号を推測する必要があるため、この攻撃は困難です。 経路上の攻撃と同様に、この攻撃から保護するために、セキュアRTCPプロファイル[RFC3711]を使用してRTCPパケットを認証できます。
