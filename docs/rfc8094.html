RFC 8094

DNS over Datagram Transport Layer Security (DTLS)

RFC 8094

Datagram Transport Layer Security（DTLS）上のDNS

Abstract

概要

DNS queries and responses are visible to network elements on the path between the DNS client and its server. These queries and responses can contain privacy-sensitive information, which is valuable to protect.

DNSのクエリーとレスポンスは、DNSクライアントとそのサーバーの間の経路上にあるネットワーク要素から見えます。これらのクエリーとレスポンスには、プライバシー上機微な情報が含まれる可能性があり、それは保護する価値があります。

This document proposes the use of Datagram Transport Layer Security (DTLS) for DNS, to protect against passive listeners and certain active attacks. As latency is critical for DNS, this proposal also discusses mechanisms to reduce DTLS round trips and reduce the DTLS handshake size. The proposed mechanism runs over port 853.

この文書は、受動的な盗聴者と特定の能動的な攻撃から保護するために、DNSにDatagram Transport Layer Security（DTLS）を使用することを提案します。DNSにとってレイテンシーは重要であるため、この提案では、DTLSの往復回数を減らし、DTLSハンドシェイクのサイズを削減するためのメカニズムについても議論します。提案するメカニズムはポート853上で動作します。

1. Introduction

1. はじめに

The Domain Name System is specified in [RFC1034] and [RFC1035]. DNS queries and responses are normally exchanged unencrypted; thus, they are vulnerable to eavesdropping. Such eavesdropping can result in an undesired entity learning domain that a host wishes to access, thus resulting in privacy leakage. The DNS privacy problem is further discussed in [RFC7626].

ドメインネームシステム（Domain Name System）は[RFC1034]と[RFC1035]で規定されています。DNSのクエリーとレスポンスは通常、暗号化されずにやり取りされるため、盗聴に対して脆弱です。そのような盗聴によって、望ましくない主体が、ホストがアクセスしようとしているドメインを知ることになり、その結果プライバシーが漏洩する可能性があります。DNSのプライバシー問題については、[RFC7626]でさらに議論されています。

This document defines DNS over DTLS, which provides confidential DNS communication between stub resolvers and recursive resolvers, stub resolvers and forwarders, and forwarders and recursive resolvers. DNS over DTLS puts an additional computational load on servers. The largest gain for privacy is to protect the communication between the DNS client (the end user's machine) and its caching resolver. DNS over DTLS might work equally between recursive clients and authoritative servers, but this application of the protocol is out of scope for the DNS PRIVate Exchange (DPRIVE) working group per its current charter. This document does not change the format of DNS messages.

この文書はDNS over DTLSを定義します。DNS over DTLSは、スタブリゾルバーと再帰リゾルバーの間、スタブリゾルバーとフォワーダーの間、およびフォワーダーと再帰リゾルバーの間で、機密性のあるDNS通信を提供します。DNS over DTLSは、サーバーに追加の計算負荷をかけます。プライバシーにとって最も大きな利益は、DNSクライアント（エンドユーザーのマシン）とそのキャッシングリゾルバーの間の通信を保護することです。DNS over DTLSは、再帰クライアントと権威サーバーの間でも同じように機能するかもしれませんが、このプロトコルのこの適用は、現在の憲章に照らしてDNS PRIVate Exchange（DPRIVE）ワーキンググループの範囲外です。この文書は、DNSメッセージの形式を変更しません。

The motivations for proposing DNS over DTLS are that:

DNS over DTLSを提案する動機は次のとおりです。

  • TCP suffers from network head-of-line blocking, where the loss of a packet causes all other TCP segments not to be delivered to the application until the lost packet is retransmitted. DNS over DTLS, because it uses UDP, does not suffer from network head-of-line blocking.
  • DTLS session resumption consumes one round trip, whereas TLS session resumption can start only after the TCP handshake is complete. However, with TCP Fast Open [RFC7413], the implementation can achieve the same RTT efficiency as DTLS.
  • TCPはネットワークのヘッドオブラインブロッキングの影響を受けます。これは、1つのパケットが失われると、失われたパケットが再送されるまで、ほかのすべてのTCPセグメントがアプリケーションに配送されなくなるというものです。DNS over DTLSはUDPを使用するため、ネットワークのヘッドオブラインブロッキングの影響を受けません。
  • DTLSのセッション再開には1往復かかりますが、TLSのセッション再開はTCPハンドシェイクが完了した後でしか開始できません。ただし、TCP Fast Open[RFC7413]を使用すれば、実装はDTLSと同じRTT効率を達成できます。

Note: DNS over DTLS is an experimental update to DNS, and the experiment will be concluded when the specification is evaluated through implementations and interoperability testing.

注: DNS over DTLSはDNSに対する実験的な更新であり、この実験は、実装と相互運用性試験を通じて仕様が評価された時点で終了します。

1.1. Relationship to TCP Queries and to DNSSEC

1.1. TCPのクエリーおよびDNSSECとの関係

DNS queries can be sent over UDP or TCP. The scope of this document, however, is only UDP. DNS over TCP can be protected with TLS, as described in [RFC7858]. DNS over DTLS alone cannot provide privacy for DNS messages in all circumstances, specifically when the DTLS record size is larger than the path MTU. In such situations, the DNS server will respond with a truncated response (see Section 5).

DNSクエリーはUDPまたはTCPで送信できます。しかし、この文書の範囲はUDPだけです。TCP上のDNSは、[RFC7858]で説明されているように、TLSで保護できます。DNS over DTLSだけでは、すべての状況でDNSメッセージのプライバシーを提供できるわけではありません。具体的には、DTLSレコードのサイズがパスMTUより大きい場合です。そのような状況では、DNSサーバーは切り詰められたレスポンスで応答します（セクション5を参照）。

Therefore, DNS clients and servers that implement DNS over DTLS MUST also implement DNS over TLS in order to provide privacy for clients that desire Strict Privacy as described in [DTLS].

したがって、[DTLS]で説明されている厳格プライバシー（Strict Privacy）を望むクライアントにプライバシーを提供するために、DNS over DTLSを実装するDNSクライアントとサーバーは、DNS over TLSも実装しなければなりません（MUST）。

DNS Security Extensions (DNSSEC) [RFC4033] provide object integrity of DNS resource records, allowing end users (or their resolver) to verify the legitimacy of responses. However, DNSSEC does not provide privacy for DNS requests or responses. DNS over DTLS works in conjunction with DNSSEC, but DNS over DTLS does not replace the need or value of DNSSEC.

DNSセキュリティー拡張（DNSSEC）[RFC4033]は、DNSリソースレコードのオブジェクトの完全性を提供し、エンドユーザー（またはそのリゾルバー）がレスポンスの正当性を検証できるようにします。しかし、DNSSECは、DNSのリクエストやレスポンスのプライバシーを提供しません。DNS over DTLSはDNSSECと組み合わせて機能しますが、DNS over DTLSはDNSSECの必要性や価値を置き換えるものではありません。

1.2. Document Status

1.2. 文書のステータス

This document is an Experimental RFC. One key aspect to judge whether the approach is usable on a large scale is by observing the uptake, usability, and operational behavior of the protocol in large-scale, real-life deployments.

この文書は実験的RFC（Experimental RFC）です。このアプローチが大規模に利用可能かどうかを判断する1つの重要な観点は、大規模な実環境の展開において、このプロトコルの普及、使いやすさ、運用上の振る舞いを観察することです。

This DTLS solution was considered by the DPRIVE working group as an option to use in case the TLS-based approach specified in [RFC7858] turns out to have some issues when deployed. At the time of writing, it is expected that [RFC7858] is what will be deployed, and so this specification is mainly intended as a backup.

このDTLSによる解決策は、[RFC7858]で規定されたTLSベースのアプローチが展開時に何らかの問題を抱えることが判明した場合に使用する選択肢として、DPRIVEワーキンググループで検討されました。この文書の執筆時点では、展開されるのは[RFC7858]であると予想されており、そのためこの仕様は主にバックアップとして意図されています。

The following guidelines should be considered when performance benchmarking DNS over DTLS:

DNS over DTLSの性能のベンチマークを行う際には、次のガイドラインを考慮すべきです。

  1. DNS over DTLS can recover from packet loss and reordering, and does not suffer from network head-of-line blocking. DNS over DTLS performance, in comparison with DNS over TLS, may be better in lossy networks.
  2. The number of round trips to send the first DNS query over DNS over DTLS is less than the number of round trips to send the first DNS query over TLS. Even if TCP Fast Open is used, it only works for subsequent TCP connections between the DNS client and server (Section 3 in [RFC7413]).
  3. If the DTLS 1.3 protocol [DTLS13] is used for DNS over DTLS, it provides critical latency improvements for connection establishment over DTLS 1.2.
  1. DNS over DTLSは、パケットの損失や順序の入れ替わりから回復でき、ネットワークのヘッドオブラインブロッキングの影響を受けません。損失の多いネットワークでは、DNS over DTLSの性能は、DNS over TLSと比べて良い場合があります。
  2. DNS over DTLSで最初のDNSクエリーを送信するための往復回数は、TLSで最初のDNSクエリーを送信するための往復回数よりも少なくなります。TCP Fast Openを使用したとしても、それが機能するのはDNSクライアントとサーバーの間の2回目以降のTCPコネクションだけです（[RFC7413]のセクション3）。
  3. DTLS 1.3プロトコル[DTLS13]をDNS over DTLSに使用すれば、DTLS 1.2と比べてコネクション確立のレイテンシーが大幅に改善されます。

3. Establishing and Managing DNS over DTLS Sessions

3. DNS over DTLSセッションの確立と管理

3.1. Session Initiation

3.1. セッションの開始

By default, DNS over DTLS MUST run over standard UDP port 853 as defined in Section 8, unless the DNS server has mutual agreement with its clients to use a port other than 853 for DNS over DTLS. In order to use a port other than 853, both clients and servers would need a configuration option in their software.

DNSサーバーが、DNS over DTLSに853以外のポートを使用することについてクライアントと相互に合意している場合を除き、デフォルトでは、DNS over DTLSはセクション8で定義されている標準のUDPポート853上で動作しなければなりません（MUST）。853以外のポートを使用するには、クライアントとサーバーの両方のソフトウェアに設定オプションが必要になるでしょう。

The DNS client should determine if the DNS server supports DNS over DTLS by sending a DTLS ClientHello message to port 853 on the server, unless it has mutual agreement with its server to use a port other than port 853 for DNS over DTLS. Such another port MUST NOT be port 53 but MAY be from the "first-come, first-served" port range (User Ports [RFC6335], range 1024-49151). This recommendation against the use of port 53 for DNS over DTLS is to avoid complications in selecting use or non-use of DTLS and to reduce risk of downgrade attacks.

DNSクライアントは、DNS over DTLSに853以外のポートを使用することについてサーバーと相互に合意している場合を除き、サーバーのポート853にDTLSのClientHelloメッセージを送信することによって、DNSサーバーがDNS over DTLSをサポートしているかどうかを判断すべきです。そのような別のポートは、ポート53であってはなりません（MUST NOT）。ただし、「先着順（first-come, first-served）」のポート範囲（ユーザーポート[RFC6335]、範囲1024～49151）から選んでもよいです（MAY）。DNS over DTLSにポート53を使用しないようにというこの推奨は、DTLSを使用するかしないかの選択における複雑さを回避し、ダウングレード攻撃のリスクを減らすためのものです。

A DNS server that does not support DNS over DTLS will not respond to ClientHello messages sent by the client. If no response is received from that server, and the client has no better round-trip estimate, the client SHOULD retransmit the DTLS ClientHello according to Section 4.2.4.1 of [RFC6347]. After 15 seconds, it SHOULD cease attempts to retransmit its ClientHello. The client MAY repeat that procedure to discover if DNS over DTLS service becomes available from the DNS server, but such probing SHOULD NOT be done more frequently than every 24 hours and MUST NOT be done more frequently than every 15 minutes. This mechanism requires no additional signaling between the client and server.

DNS over DTLSをサポートしていないDNSサーバーは、クライアントが送信したClientHelloメッセージに応答しません。そのサーバーからレスポンスを受信せず、クライアントがより良い往復時間の推定値を持っていない場合、クライアントは[RFC6347]のセクション4.2.4.1に従ってDTLSのClientHelloを再送すべきです（SHOULD）。15秒が経過した後は、ClientHelloの再送の試行をやめるべきです（SHOULD）。クライアントは、DNSサーバーからDNS over DTLSサービスが利用可能になったかどうかを発見するために、その手順を繰り返してもよいです（MAY）。ただし、そのような探査は、24時間に1回より頻繁に行うべきではありません（SHOULD NOT）。また、15分に1回より頻繁に行ってはなりません（MUST NOT）。このメカニズムでは、クライアントとサーバーの間で追加のシグナリングは必要ありません。

DNS clients and servers MUST NOT use port 853 to transport cleartext DNS messages. DNS clients MUST NOT send and DNS servers MUST NOT respond to cleartext DNS messages on any port used for DNS over DTLS (including, for example, after a failed DTLS handshake). There are significant security issues in mixing protected and unprotected data; therefore, UDP connections on a port designated by a given server for DNS over DTLS are reserved purely for encrypted communications.

DNSクライアントとサーバーは、平文のDNSメッセージを転送するためにポート853を使用してはなりません（MUST NOT）。DNS over DTLSに使用するいずれのポートでも（たとえば、DTLSハンドシェイクが失敗した後も含めて）、DNSクライアントは平文のDNSメッセージを送信してはなりません（MUST NOT）。DNSサーバーも平文のDNSメッセージに応答してはなりません（MUST NOT）。保護されたデータと保護されていないデータを混在させることには重大なセキュリティー上の問題があります。そのため、あるサーバーがDNS over DTLS用に指定したポート上のUDPコネクションは、暗号化された通信専用に予約されます。

3.2. DTLS Handshake and Authentication

3.2. DTLSのハンドシェイクと認証

The DNS client initiates the DTLS handshake as described in [RFC6347], following the best practices specified in [RFC7525]. After DTLS negotiation completes, if the DTLS handshake succeeds according to [RFC6347], the connection will be encrypted and would then be protected from eavesdropping.

DNSクライアントは、[RFC7525]で規定されたベストプラクティスに従い、[RFC6347]で説明されているとおりにDTLSハンドシェイクを開始します。DTLSのネゴシエーションが完了した後、[RFC6347]に従ってDTLSハンドシェイクが成功すれば、コネクションは暗号化され、それによって盗聴から保護されることになります。

DNS privacy requires encrypting the query (and response) from passive attacks. Such encryption typically provides integrity protection as a side effect, which means on-path attackers cannot simply inject bogus DNS responses. However, to provide stronger protection from active attackers pretending to be the server, the server itself needs to be authenticated. To authenticate the server providing DNS privacy, DNS client MUST use the authentication mechanisms discussed in [DTLS]. This document does not propose new ideas for authentication.

DNSのプライバシーには、受動的な攻撃からクエリー（およびレスポンス）を暗号化することが必要です。そのような暗号化は通常、副次的な効果として完全性の保護を提供します。つまり、経路上の攻撃者は偽のDNSレスポンスを単純に注入することはできません。しかし、サーバーになりすます能動的な攻撃者からより強力に保護するには、サーバー自体を認証する必要があります。DNSのプライバシーを提供するサーバーを認証するために、DNSクライアントは[DTLS]で議論されている認証メカニズムを使用しなければなりません（MUST）。この文書は、認証に関する新しい考え方を提案するものではありません。

3.3. Established Sessions

3.3. 確立されたセッション

In DTLS, all data is protected using the same record encoding and mechanisms. When the mechanism described in this document is in effect, DNS messages are encrypted using the standard DTLS record encoding. When a DTLS user wishes to send a DNS message, the data is delivered to the DTLS implementation as an ordinary application data write (e.g., SSL_write()). A single DTLS session can be used to send multiple DNS requests and receive multiple DNS responses.

DTLSでは、すべてのデータが同じレコードエンコーディングとメカニズムを使用して保護されます。この文書で説明するメカニズムが有効である場合、DNSメッセージは標準のDTLSレコードエンコーディングを使用して暗号化されます。DTLSのユーザーがDNSメッセージを送信したい場合、そのデータは通常のアプリケーションデータの書き込み（たとえば、SSL_write()）としてDTLS実装に渡されます。単一のDTLSセッションを使用して、複数のDNSリクエストを送信し、複数のDNSレスポンスを受信できます。

To mitigate the risk of unintentional server overload, DNS over DTLS clients MUST take care to minimize the number of concurrent DTLS sessions made to any individual server. For any given client/server interaction, it is RECOMMENDED that there be no more than one DTLS session. Similarly, servers MAY impose limits on the number of concurrent DTLS sessions being handled for any particular client IP address or subnet. These limits SHOULD be much looser than the client guidelines above because the server does not know, for example, if a client IP address belongs to a single client, is representing multiple resolvers on a single machine, or is representing multiple clients behind a device performing Network Address Translation (NAT).

意図しないサーバーの過負荷のリスクを緩和するために、DNS over DTLSのクライアントは、個々のサーバーに対して張る同時DTLSセッションの数を最小限に抑えるよう注意しなければなりません（MUST）。任意のクライアントとサーバーの間のやり取りについて、DTLSセッションは1つまでとすることが推奨されます（RECOMMENDED）。同様に、サーバーは、特定のクライアントIPアドレスまたはサブネットに対して処理する同時DTLSセッションの数に制限を課してもよいです（MAY）。これらの制限は、上記のクライアント向けのガイドラインよりもかなり緩やかにすべきです（SHOULD）。なぜなら、サーバーには、たとえば、あるクライアントIPアドレスが単一のクライアントに属しているのか、単一のマシン上の複数のリゾルバーを代表しているのか、それともネットワークアドレス変換（NAT）を行うデバイスの背後にある複数のクライアントを代表しているのかがわからないからです。

In between normal DNS traffic, while the communication to the DNS server is quiescent, the DNS client MAY want to probe the server using DTLS heartbeat [RFC6520] to ensure it has maintained cryptographic state. Such probes can also keep alive firewall or NAT bindings. This probing reduces the frequency of needing a new handshake when a DNS query needs to be resolved, improving the user experience at the cost of bandwidth and processing time.

通常のDNSトラフィックの合間、DNSサーバーとの通信が休止している間に、DNSクライアントは、暗号の状態が維持されていることを確認するために、DTLSハートビート[RFC6520]を使用してサーバーを探査したいと考える場合があります（MAY）。そのような探査によって、ファイアウォールやNATのバインディングを維持することもできます。この探査により、DNSクエリーを解決する必要があるときに新しいハンドシェイクが必要になる頻度が減り、帯域幅と処理時間を犠牲にしてユーザー体験が向上します。

A DTLS session is terminated by the receipt of an authenticated message that closes the connection (e.g., a DTLS fatal alert). If the server has lost state, a DTLS handshake needs to be initiated with the server. For the server, to mitigate the risk of unintentional server overload, it is RECOMMENDED that the default DNS over DTLS server application-level idle time be set to several seconds and not set to less than a second, but no particular value is specified. When no DNS queries have been received from the client after idle timeout, the server MUST send a DTLS fatal alert and then destroy its DTLS state. The DTLS fatal alert packet indicates the server has destroyed its state, signaling to the client that if it wants to send a new DTLS message, it will need to re-establish cryptographic context with the server (via full DTLS handshake or DTLS session resumption). In practice, the idle period can vary dynamically, and servers MAY allow idle connections to remain open for longer periods as resources permit.

DTLSセッションは、コネクションを閉じる認証されたメッセージ（たとえば、DTLSの致命的なアラート）を受信することによって終了します。サーバーが状態を失った場合は、サーバーとのDTLSハンドシェイクを開始する必要があります。サーバーについては、意図しないサーバーの過負荷のリスクを緩和するために、DNS over DTLSサーバーのアプリケーションレベルのアイドル時間のデフォルトを数秒に設定し、1秒未満には設定しないことが推奨されます（RECOMMENDED）。ただし、特定の値は規定しません。アイドルタイムアウトの後もクライアントからDNSクエリーを受信していない場合、サーバーはDTLSの致命的なアラートを送信し、その後で自身のDTLS状態を破棄しなければなりません（MUST）。DTLSの致命的なアラートのパケットは、サーバーが自身の状態を破棄したことを示し、クライアントが新しいDTLSメッセージを送信したい場合には、（完全なDTLSハンドシェイクまたはDTLSセッション再開によって）サーバーとの暗号コンテキストを再確立する必要があることをクライアントに伝えます。実際には、アイドル期間は動的に変化する可能性があり、サーバーは、リソースが許す限り、アイドル状態のコネクションをより長い期間開いたままにしてもよいです（MAY）。

4. Performance Considerations

4. 性能に関する考慮事項

The DTLS protocol profile for DNS over DTLS is discussed in Section 11 of [DTLS]. To reduce the number of octets of the DTLS handshake, especially the size of the certificate in the ServerHello (which can be several kilobytes), DNS clients and servers can use raw public keys [RFC7250] or Cached Information Extension [RFC7924]. Cached Information Extension avoids transmitting the server's certificate and certificate chain if the client has cached that information from a previous TLS handshake. TLS False Start [RFC7918] can reduce round trips by allowing the TLS second flight of messages (ChangeCipherSpec) to also contain the (encrypted) DNS query.

DNS over DTLSのためのDTLSプロトコルプロファイルは、[DTLS]のセクション11で議論されています。DTLSハンドシェイクのオクテット数、特にServerHelloの中の証明書のサイズ（数キロバイトになることがあります）を削減するために、DNSクライアントとサーバーは、生の公開鍵[RFC7250]またはキャッシュ情報拡張（Cached Information Extension）[RFC7924]を使用できます。キャッシュ情報拡張は、クライアントが以前のTLSハンドシェイクからサーバーの証明書と証明書チェーンの情報をキャッシュしている場合に、それらの送信を回避します。TLS False Start[RFC7918]は、TLSの2番目のメッセージフライト（ChangeCipherSpec）に（暗号化された）DNSクエリーも含められるようにすることで、往復回数を減らすことができます。

It is highly advantageous to avoid server-side DTLS state and reduce the number of new DTLS sessions on the server that can be done with TLS Session Resumption without server state [RFC5077]. This also eliminates a round trip for subsequent DNS over DTLS queries, because with [RFC5077] the DTLS session does not need to be re-established.

サーバー側のDTLS状態を回避し、サーバー上の新しいDTLSセッションの数を減らすことは非常に有益であり、これはサーバー側の状態を持たないTLSセッション再開[RFC5077]によって実現できます。[RFC5077]を使用するとDTLSセッションを再確立する必要がないため、これによって後続のDNS over DTLSクエリーの往復も1回削減されます。

Since responses within a DTLS session can arrive out of order, clients MUST match responses to outstanding queries on the same DTLS connection using the DNS Message ID. If the response contains a question section, the client MUST match the QNAME, QCLASS, and QTYPE fields. Failure by clients to properly match responses to outstanding queries can have serious consequences for interoperability (Section 7 of [RFC7766]).

DTLSセッション内のレスポンスは順序どおりに到着しないことがあるため、クライアントは、DNSメッセージIDを使用して、同じDTLSコネクション上の応答待ちのクエリーとレスポンスを照合しなければなりません（MUST）。レスポンスに質問セクションが含まれている場合、クライアントはQNAME、QCLASS、QTYPEのフィールドを照合しなければなりません（MUST）。クライアントがレスポンスを応答待ちのクエリーと適切に照合できないと、相互運用性に深刻な影響を及ぼす可能性があります（[RFC7766]のセクション7）。

5. Path MTU (PMTU) Issues

5. パスMTU（PMTU）の問題

Compared to normal DNS, DTLS adds at least 13 octets of header, plus cipher and authentication overhead to every query and every response. This reduces the size of the DNS payload that can be carried. The DNS client and server MUST support the Extension Mechanisms for DNS (EDNS0) option defined in [RFC6891] so that the DNS client can indicate to the DNS server the maximum DNS response size it can reassemble and deliver in the DNS client's network stack. If the DNS client does set the EDNS0 option defined in [RFC6891], then the maximum DNS response size of 512 bytes plus DTLS overhead will be well within the Path MTU. If the Path MTU is not known, an IP MTU of 1280 bytes SHOULD be assumed. The client sets its EDNS0 value as if DTLS is not being used. The DNS server MUST ensure that the DNS response size does not exceed the Path MTU, i.e., each DTLS record MUST fit within a single datagram, as required by [RFC6347]. The DNS server must consider the amount of record expansion expected by the DTLS processing when calculating the size of DNS response that fits within the path MTU. The Path MTU MUST be greater than or equal to the DNS response size + DTLS overhead of 13 octets + padding size ([RFC7830]) + authentication overhead of the negotiated DTLS cipher suite + block padding (Section 4.1.1.1 of [RFC6347]). If the DNS server's response were to exceed that calculated value, the server MUST send a response that does fit within that value and sets the TC (truncated) bit. Upon receiving a response with the TC bit set and wanting to receive the entire response, the client behavior is governed by the current Usage Profile [DTLS]. For Strict Privacy, the client MUST only send a new DNS request for the same resource record over an encrypted transport (e.g., DNS over TLS [RFC7858]). Clients using Opportunistic Privacy SHOULD try for the best case (an encrypted and authenticated transport) but MAY fall back to intermediate cases and eventually the worst case scenario (clear text) in order to obtain a response.

通常のDNSと比べて、DTLSは、すべてのクエリーとすべてのレスポンスに、少なくとも13オクテットのヘッダーに加えて、暗号と認証のオーバーヘッドを追加します。これにより、運ぶことができるDNSペイロードのサイズが小さくなります。DNSクライアントが、自身が再組み立てしてDNSクライアントのネットワークスタックで配送できる最大のDNSレスポンスサイズをDNSサーバーに示せるように、DNSクライアントとサーバーは、[RFC6891]で定義されているDNSの拡張メカニズム（EDNS0）オプションをサポートしなければなりません（MUST）。DNSクライアントが[RFC6891]で定義されているEDNS0オプションを設定する場合、最大DNSレスポンスサイズの512バイトにDTLSのオーバーヘッドを加えたものは、パスMTUに十分に収まります。パスMTUが不明な場合は、1280バイトのIP MTUを想定すべきです（SHOULD）。クライアントは、DTLSが使用されていないかのようにEDNS0の値を設定します。DNSサーバーは、DNSレスポンスのサイズがパスMTUを超えないことを保証しなければなりません（MUST）。つまり、[RFC6347]で要求されているとおり、各DTLSレコードは単一のデータグラムに収まらなければなりません（MUST）。DNSサーバーは、パスMTUに収まるDNSレスポンスのサイズを計算する際に、DTLSの処理によって予想されるレコードの拡大量を考慮する必要があります。パスMTUは、DNSレスポンスのサイズ + 13オクテットのDTLSオーバーヘッド + パディングのサイズ（[RFC7830]） + ネゴシエートされたDTLS暗号スイートの認証オーバーヘッド + ブロックパディング（[RFC6347]のセクション4.1.1.1）以上でなければなりません（MUST）。DNSサーバーのレスポンスがその計算値を超えることになる場合、サーバーはその値に収まるレスポンスを送信し、TC（truncated）ビットを設定しなければなりません（MUST）。TCビットが設定されたレスポンスを受信し、レスポンス全体を受信したい場合のクライアントの振る舞いは、現在の利用プロファイル[DTLS]によって決まります。厳格プライバシーの場合、クライアントが同じリソースレコードに対する新しいDNSリクエストを送信するのは、暗号化されたトランスポート（たとえば、DNS over TLS[RFC7858]）上だけでなければなりません（MUST）。日和見プライバシー（Opportunistic Privacy）を使用するクライアントは、最善のケース（暗号化され、かつ認証されたトランスポート）を試みるべきです（SHOULD）。ただし、レスポンスを得るために、中間のケースに、そして最終的には最悪のケースのシナリオ（平文）にフォールバックしてもよいです（MAY）。

6. Anycast

6. エニーキャスト

DNS servers are often configured with anycast addresses. While the network is stable, packets transmitted from a particular source to an anycast address will reach the same server that has the cryptographic context from the DNS over DTLS handshake. But, when the network configuration or routing changes, a DNS over DTLS packet can be received by a server that does not have the necessary cryptographic context. Clients using DNS over DTLS need to always be prepared to re-initiate the DTLS handshake, and in the worst case this could even happen immediately after re-initiating a new handshake. To encourage the client to initiate a new DTLS handshake, DNS servers SHOULD generate a DTLS fatal alert message in response to receiving a DTLS packet for which the server does not have any cryptographic context. Upon receipt of an unauthenticated DTLS fatal alert, the DTLS client validates the fatal alert is within the replay window (Section 4.1.2.6 of [RFC6347]). It is difficult for the DTLS client to validate that the DTLS fatal alert was generated by the DTLS server in response to a request or was generated by an on- or off-path attacker. Thus, upon receipt of an in-window DTLS fatal alert, the client SHOULD continue retransmitting the DTLS packet (in the event the fatal alert was spoofed), and at the same time it SHOULD initiate DTLS session resumption. When the DTLS client receives an authenticated DNS response from one of those DTLS sessions, the other DTLS session should be terminated.

DNSサーバーは、エニーキャストアドレスで設定されることがよくあります。ネットワークが安定している間は、特定の送信元からエニーキャストアドレスに送信されたパケットは、DNS over DTLSハンドシェイクによる暗号コンテキストを持つ同じサーバーに到達します。しかし、ネットワークの構成やルーティングが変化すると、DNS over DTLSのパケットが、必要な暗号コンテキストを持たないサーバーによって受信される可能性があります。DNS over DTLSを使用するクライアントは、DTLSハンドシェイクを再開始する準備を常にしておく必要があり、最悪の場合、これは新しいハンドシェイクを再開始した直後に起こることさえあり得ます。クライアントが新しいDTLSハンドシェイクを開始するよう促すために、DNSサーバーは、暗号コンテキストを何も持っていないDTLSパケットを受信したことに応じて、DTLSの致命的なアラートメッセージを生成すべきです（SHOULD）。認証されていないDTLSの致命的なアラートを受信すると、DTLSクライアントは、その致命的なアラートがリプレイウィンドウ内にあることを検証します（[RFC6347]のセクション4.1.2.6）。DTLSクライアントにとって、そのDTLSの致命的なアラートが、リクエストに応じてDTLSサーバーによって生成されたのか、それとも経路上または経路外の攻撃者によって生成されたのかを検証することは困難です。したがって、ウィンドウ内のDTLSの致命的なアラートを受信すると、クライアントは（致命的なアラートが偽装されていた場合に備えて）DTLSパケットの再送を続けるべきです（SHOULD）。それと同時に、クライアントはDTLSセッション再開を開始すべきです（SHOULD）。DTLSクライアントがそれらのDTLSセッションのいずれかから認証されたDNSレスポンスを受信したら、もう一方のDTLSセッションは終了すべきです。

厳格（Strict）と日和見（Opportunistic）の2つの利用プロファイルが、[DTLS]で説明されています。DNSの利用における優先順位は次のとおりです。

9. Security Considerations

9. セキュリティーに関する考慮事項

The interaction between a DNS client and a DNS server requires Datagram Transport Layer Security (DTLS) with a ciphersuite offering confidentiality protection. The guidance given in [RFC7525] MUST be followed to avoid attacks on DTLS. The DNS client SHOULD use the TLS Certificate Status Request extension (Section 8 of [RFC6066]), commonly called "OCSP stapling" to check the revocation status of the public key certificate of the DNS server. OCSP stapling, unlike OCSP [RFC6960], does not suffer from scale and privacy issues. DNS clients keeping track of servers known to support DTLS enables clients to detect downgrade attacks. To interfere with DNS over DTLS, an on- or off-path attacker might send an ICMP message towards the DTLS client or DTLS server. As these ICMP messages cannot be authenticated, all ICMP errors should be treated as soft errors [RFC1122]. If the DNS query was sent over DTLS, then the corresponding DNS response MUST only be accepted if it is received over the same DTLS connection. This behavior mitigates all possible attacks described in Measures for Making DNS More Resilient against Forged Answers [RFC5452]. The security considerations in [RFC6347] and [DTLS] are to be taken into account.

DNSクライアントとDNSサーバーの間のやり取りには、機密性の保護を提供する暗号スイートを用いたDatagram Transport Layer Security（DTLS）が必要です。DTLSに対する攻撃を回避するために、[RFC7525]で示されているガイダンスに従わなければなりません（MUST）。DNSクライアントは、DNSサーバーの公開鍵証明書の失効状態を確認するために、一般に「OCSPステープリング」と呼ばれるTLSのCertificate Status Request拡張（[RFC6066]のセクション8）を使用すべきです（SHOULD）。OCSPステープリングは、OCSP[RFC6960]とは異なり、規模とプライバシーの問題を抱えていません。DTLSをサポートしていることがわかっているサーバーをDNSクライアントが記録しておくことで、クライアントはダウングレード攻撃を検出できるようになります。DNS over DTLSを妨害するために、経路上または経路外の攻撃者が、DTLSクライアントまたはDTLSサーバーに向けてICMPメッセージを送信するかもしれません。これらのICMPメッセージは認証できないため、すべてのICMPエラーはソフトエラー[RFC1122]として扱うべきです。DNSクエリーがDTLS上で送信された場合、対応するDNSレスポンスを受け入れるのは、それが同じDTLSコネクション上で受信された場合だけでなければなりません（MUST）。この振る舞いにより、「Measures for Making DNS More Resilient against Forged Answers」[RFC5452]で説明されている考えられるすべての攻撃が緩和されます。[RFC6347]と[DTLS]のセキュリティーに関する考慮事項を考慮に入れる必要があります。

A malicious client might attempt to perform a high number of DTLS handshakes with a server. As the clients are not uniquely identified by the protocol and can be obfuscated with IPv4 address sharing and with IPv6 temporary addresses, a server needs to mitigate the impact of such an attack. Such mitigation might involve rate limiting handshakes from a certain subnet or more advanced DoS/DDoS techniques beyond the scope of this document.

悪意のあるクライアントは、サーバーとの間で多数のDTLSハンドシェイクを実行しようとするかもしれません。クライアントはプロトコルによって一意に識別されず、IPv4アドレスの共有やIPv6の一時アドレスによって識別が困難になり得るため、サーバーはそのような攻撃の影響を緩和する必要があります。そのような緩和策には、特定のサブネットからのハンドシェイクのレート制限や、この文書の範囲を超えるより高度なDoS/DDoS対策技術が含まれるかもしれません。
