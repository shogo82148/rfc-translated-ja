RFC 9941

Secure Shell (SSH) Key Exchange Method Using Hybrid Streamlined NTRU Prime sntrup761 and X25519 with SHA-512: sntrup761x25519-sha512

RFC 9941

ハイブリッドな Streamlined NTRU Prime sntrup761 と X25519 および SHA-512 を使用するセキュアシェル（SSH）鍵交換方式: sntrup761x25519-sha512

Abstract

概要

This document describes a widely deployed hybrid key exchange method in the Secure Shell (SSH) protocol that is based on Streamlined NTRU Prime sntrup761 and X25519 with SHA-512.

この文書は、セキュアシェル（SSH）プロトコルにおいて広く展開されている、Streamlined NTRU Prime sntrup761 と X25519 および SHA-512 に基づくハイブリッド鍵交換方式について説明します。

1. Introduction

1. はじめに

Secure Shell (SSH) [RFC4251] is a secure remote login protocol. The key exchange protocol described in [RFC4253] supports an extensible set of methods. [RFC5656] defines how elliptic curves are integrated into the extensible SSH framework, and [RFC8731] adds curve25519-sha256 to support the pre-quantum Elliptic Curve Diffie-Hellman (ECDH) X25519 function [RFC7748].

セキュアシェル（SSH）[RFC4251] は、安全なリモートログインプロトコルです。[RFC4253] で説明されている鍵交換プロトコルは、拡張可能な方式の集合をサポートしています。[RFC5656] は楕円曲線を拡張可能な SSH フレームワークに統合する方法を定義しており、[RFC8731] は量子以前の楕円曲線ディフィー・ヘルマン（ECDH）関数 X25519 [RFC7748] をサポートするために curve25519-sha256 を追加しています。

Streamlined NTRU Prime [NTRUPrimePQCS] [NTRUPrime] [NTRUPrimeWeb] provides post-quantum small lattice-based key-encapsulation mechanisms. The sntrup761 instance has been implemented widely.

Streamlined NTRU Prime [NTRUPrimePQCS] [NTRUPrime] [NTRUPrimeWeb] は、耐量子性を持つ小さな格子ベースの鍵カプセル化メカニズムを提供します。sntrup761 のインスタンスは広く実装されています。

This document specifies a hybrid construction using both sntrup761 and X25519, in the intention that a hybrid would be secure if either algorithms is secure.

この文書は、sntrup761 と X25519 の両方を使用するハイブリッド構成を規定します。どちらかのアルゴリズムが安全であればハイブリッドも安全になることを意図しています。

This document also describes how to implement key exchange based on a hybrid between Streamlined NTRU Prime sntrup761 and X25519 with SHA-512 [RFC6234] in SSH.

この文書では、Streamlined NTRU Prime sntrup761 と X25519 および SHA-512 [RFC6234] のハイブリッドに基づく鍵交換を SSH で実装する方法についても説明します。

This document was derived from SSH KEX Using Curve25519 and Curve448 [RFC8731].

この文書は、SSH KEX Using Curve25519 and Curve448 [RFC8731] をもとにしています。

3. Key Exchange Method: sntrup761x25519-sha512

3. 鍵交換方式: sntrup761x25519-sha512

The key agreement is done by the X25519 Diffie-Hellman protocol as described in Section 3 ("Key Exchange Methods") of [RFC8731] and by the key encapsulation method described in [NTRUPrimePQCS].

鍵合意は、[RFC8731] のセクション 3 ("Key Exchange Methods") で説明されている X25519 ディフィー・ヘルマンプロトコルと、[NTRUPrimePQCS] で説明されている鍵カプセル化方式によって行われます。

The key exchange procedure reuses the ECDH key exchange defined in Sections 4 ("ECDH Key Exchange") and 7.1 ("ECDH Message Numbers") of [RFC5656].

鍵交換の手順は、[RFC5656] のセクション 4 ("ECDH Key Exchange") と 7.1 ("ECDH Message Numbers") で定義されている ECDH 鍵交換を再利用します。

The protocol flow and the SSH_MSG_KEX_ECDH_INIT and SSH_MSG_KEX_ECDH_REPLY messages are identical, except that we use different ephemeral public values Q_C and Q_S and shared secret K as described below.

プロトコルの流れと SSH_MSG_KEX_ECDH_INIT メッセージおよび SSH_MSG_KEX_ECDH_REPLY メッセージは同一ですが、以下で説明するように、異なる一時公開値 Q_C と Q_S、および共有秘密 K を使用する点が異なります。

Implementations MAY use the name SSH_MSG_KEX_HYBRID_INIT where SSH_MSG_KEX_ECDH_INIT is used and the name SSH_MSG_KEX_HYBRID_REPLY where SSH_MSG_KEX_ECDH_REPLY is used, as long as the encoding on the wire is identical. These symbolic names do not appear on the wire; they are merely used in specifications to refer to particular byte values. For consistency with [RFC5656], which defines the packet syntax, we use those names in the rest of this document.

実装は、ワイヤー上のエンコーディングが同一である限り、SSH_MSG_KEX_ECDH_INIT が使用される箇所で SSH_MSG_KEX_HYBRID_INIT という名前を使用し、SSH_MSG_KEX_ECDH_REPLY が使用される箇所で SSH_MSG_KEX_HYBRID_REPLY という名前を使用してもよいです（MAY）。これらの記号名はワイヤー上には現れません。特定のバイト値を指すために仕様の中で使用されるにすぎません。パケット構文を定義している [RFC5656] との一貫性のため、この文書の残りの部分ではそれらの名前を使用します。

The SSH_MSG_KEX_ECDH_INIT's value Q_C that holds the client's ephemeral public key MUST be constructed by concatenating the 1158-byte public key output from the key generator of sntrup761 with the 32-byte K_A = X25519(a, 9) as described in [NTRUPrimePQCS] and [RFC8731]. The Q_C value is thus 1190 bytes.

クライアントの一時公開鍵を保持する SSH_MSG_KEX_ECDH_INIT の値 Q_C は、[NTRUPrimePQCS] と [RFC8731] で説明されているように、sntrup761 の鍵生成器が出力する 1158 バイトの公開鍵と、32 バイトの K_A = X25519(a, 9) を連結して構成しなければなりません（MUST）。したがって、Q_C の値は 1190 バイトになります。

The SSH_MSG_KEX_ECDH_REPLY's value Q_S that holds the server's ephemeral public key MUST be constructed by concatenating the 1039-byte ciphertext output from the key encapsulation mechanism of sntrup761 with the 32-byte K_B = X25519(b, 9) as described in [NTRUPrimePQCS] and [RFC8731]. The Q_S value is thus 1071 bytes.

サーバーの一時公開鍵を保持する SSH_MSG_KEX_ECDH_REPLY の値 Q_S は、[NTRUPrimePQCS] と [RFC8731] で説明されているように、sntrup761 の鍵カプセル化メカニズムが出力する 1039 バイトの暗号文と、32 バイトの K_B = X25519(b, 9) を連結して構成しなければなりません（MUST）。したがって、Q_S の値は 1071 バイトになります。

Clients and servers MUST abort if the length of the received public keys Q_C or Q_S are not the expected lengths. An abort for these purposes is defined as a disconnect (SSH_MSG_DISCONNECT) of the session and SHOULD use the SSH_DISCONNECT_KEY_EXCHANGE_FAILED reason for the message; see Section 11.1 ("Disconnection Message") of [RFC4253]. No further validation is required beyond what is described in [RFC7748], [RFC8731], and [NTRUPrimePQCS].

受信した公開鍵 Q_C または Q_S の長さが想定された長さでない場合、クライアントとサーバーは中止しなければなりません（MUST）。ここでいう中止とはセッションの切断（SSH_MSG_DISCONNECT）のことであり、そのメッセージの理由には SSH_DISCONNECT_KEY_EXCHANGE_FAILED を使用すべきです（SHOULD）。[RFC4253] のセクション 11.1 ("Disconnection Message") を参照してください。[RFC7748]、[RFC8731]、[NTRUPrimePQCS] で説明されているもの以上の検証は必要ありません。

The SSH_MSG_KEX_ECDH_REPLY's signature value is computed as described in ECC for SSH [RFC5656] with the following changes. Instead of encoding the shared secret K as "mpint", it MUST be encoded as "string". The shared secret K value MUST be the 64-byte output octet string of the SHA-512 hash computed with the input as the 32-byte octet string key output from the key encapsulation mechanism of sntrup761 concatenated with the 32-byte octet string of X25519(a, X25519(b, 9)) = X25519(b, X25519(a, 9)).

SSH_MSG_KEX_ECDH_REPLY の署名値は、ECC for SSH [RFC5656] で説明されているとおりに、次の変更を加えて計算されます。共有秘密 K は "mpint" としてエンコードする代わりに、"string" としてエンコードしなければなりません（MUST）。共有秘密 K の値は、sntrup761 の鍵カプセル化メカニズムが出力する 32 バイトのオクテット文字列の鍵と、32 バイトのオクテット文字列 X25519(a, X25519(b, 9)) = X25519(b, X25519(a, 9)) を連結したものを入力として計算した SHA-512 ハッシュの、64 バイトの出力オクテット文字列でなければなりません（MUST）。

Some earlier implementations may implement this protocol only through the name sntrup761x25519-sha512@openssh.com; therefore, it is RECOMMENDED to announce and accept that name as an alias of this protocol to increase chances for successfully negotiating the protocol.

初期の実装の中には、このプロトコルを sntrup761x25519-sha512@openssh.com という名前でしか実装していないものがあるかもしれません。そのため、プロトコルのネゴシエーションが成功する可能性を高めるために、その名前をこのプロトコルの別名として告知し、受け入れることが推奨されます（RECOMMENDED）。

4. Security Considerations

4. セキュリティーに関する考慮事項

The security considerations in [RFC4251], [RFC5656], [RFC7748], and [RFC8731] are inherited.

[RFC4251]、[RFC5656]、[RFC7748]、[RFC8731] のセキュリティーに関する考慮事項が継承されます。

Streamlined NTRU Prime sntrup761 aims for the standard goal of IND-CCA2 security, is widely implemented with good performance on a wide range of architectures, and has been studied by researchers for several years. However, new cryptographic primitives should be introduced and trusted conservatively, and new research findings may be published at any time that may warrant implementation reconsideration. The method described here to combine Curve25519 with sntrup761 (i.e., SHA-512 hashing the concatenated outputs) is also available for the same kind of cryptographic scrutiny.

Streamlined NTRU Prime sntrup761 は、IND-CCA2 安全性という標準的な目標を目指しており、幅広いアーキテクチャーで良好な性能で広く実装されていて、研究者によって数年にわたって研究されてきました。しかし、新しい暗号プリミティブは慎重に導入して信頼すべきであり、実装の再検討が必要となる新しい研究成果がいつ公開されてもおかしくありません。ここで説明した Curve25519 と sntrup761 を組み合わせる方法（つまり、連結した出力を SHA-512 でハッシュする方法）も、同様の暗号学的な精査の対象となります。

The increase in communication size and computational requirements may be a concern for restricted computational devices, which would then not be able to take advantage of the improved security properties offered by this work.

通信サイズと計算量の要件の増加は、計算能力の制限されたデバイスにとって懸念となるかもしれません。そのようなデバイスは、この取り組みによって提供されるセキュリティー特性の向上を活用できないことになります。

Since sntrup761x25519-sha512 is expected to offer no reduction of security compared to curve25519-sha256, it is recommended that it is used and preferred whenever curve25519-sha256 is used today, if the extra communication size and computational requirements are acceptable.

sntrup761x25519-sha512 は curve25519-sha256 と比べてセキュリティーを低下させないと期待されるため、追加の通信サイズと計算量の要件が許容できるのであれば、現在 curve25519-sha256 が使用されているところではどこでも sntrup761x25519-sha512 を使用し、優先することが推奨されます。

As discussed in the security considerations of [RFC8731], the X25519 shared secret K is bignum-encoded in that document, and this raises the potential for a side-channel attack that could leak one bit of the secret due to the different length of the bignum sign pad. This document resolves that problem by using string encoding instead of bignum encoding.

[RFC8731] のセキュリティーに関する考慮事項で議論されているように、その文書では X25519 の共有秘密 K が bignum エンコードされており、bignum の符号パッドの長さが異なることによって秘密の 1 ビットが漏洩しうるサイドチャネル攻撃の可能性が生じます。この文書では、bignum エンコーディングの代わりに string エンコーディングを使用することで、この問題を解決しています。

The security properties of the protocol in this document, SSH itself, and the cryptographic algorithms used (including Streamlined NTRU Prime) depend on the availability and proper use of cryptographically secure random data.

この文書のプロトコル、SSH 自体、および使用される暗号アルゴリズム（Streamlined NTRU Prime を含む）のセキュリティー特性は、暗号学的に安全なランダムデータが利用可能であり、適切に使用されることに依存しています。
