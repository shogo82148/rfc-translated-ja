RFC 8600

Using Extensible Messaging and Presence Protocol (XMPP) for Security Information Exchange

RFC 8600

セキュリティー情報交換のための拡張可能なメッセージングおよびプレゼンスプロトコル（XMPP）の使用

Abstract

概要

This document describes how to use the Extensible Messaging and Presence Protocol (XMPP) to collect and distribute security incident reports and other security-relevant information between network-connected devices, primarily for the purpose of communication among Computer Security Incident Response Teams and associated entities. To illustrate the principles involved, this document describes such a usage for the Incident Object Description Exchange Format (IODEF).

この文書は、拡張可能なメッセージングおよびプレゼンスプロトコル（Extensible Messaging and Presence Protocol、XMPP）を使用して、ネットワークに接続されたデバイス間でセキュリティーインシデントの報告やそのほかのセキュリティー関連情報を収集・配布する方法について説明します。その主な目的は、コンピューターセキュリティーインシデント対応チーム（Computer Security Incident Response Team）と関連するエンティティーとの間の通信です。関係する原則を示すために、この文書では、インシデントオブジェクト記述交換フォーマット（Incident Object Description Exchange Format、IODEF）でのそのような使い方について説明します。

1. Introduction

1. はじめに

This document defines an architecture, i.e., "XMPP-Grid", as a method for using the Extensible Messaging and Presence Protocol (XMPP) [RFC6120] to collect and distribute security incident reports and other security-relevant information among network platforms, endpoints, and any other network-connected device, primarily for the purpose of communication among Computer Security Incident Response Teams and associated entities. In effect, this document specifies an Applicability Statement ([RFC2026], Section 3.2) that defines how to use XMPP for the exchange of security notifications on a controlled-access network among authorized entities.

この文書は、拡張可能なメッセージングおよびプレゼンスプロトコル（Extensible Messaging and Presence Protocol、XMPP）[RFC6120]を使用して、ネットワークプラットフォーム、エンドポイント、そのほかのネットワークに接続されたあらゆるデバイスの間でセキュリティーインシデントの報告やそのほかのセキュリティー関連情報を収集・配布するための方法として、アーキテクチャー（すなわち「XMPP-Grid」）を定義します。その主な目的は、コンピューターセキュリティーインシデント対応チームと関連するエンティティーとの間の通信です。実質的に、この文書は、アクセスが制御されたネットワーク上で、認可されたエンティティー間のセキュリティー通知の交換にXMPPを使用する方法を定義する適用性声明（Applicability Statement）（[RFC2026], Section 3.2）を規定します。

Among other things, XMPP provides a publish-subscribe service [XEP-0060] that acts as a broker, enabling control-plane functions by which entities can discover available information to be published or consumed. Although such information can take the form of any structured data (XML, JSON, etc.), this document illustrates the principles of XMPP-Grid with examples that use the Incident Object Description Exchange Format (IODEF) [RFC7970]. That is, while other security information formats can be shared using XMPP, this document uses IODEF as one such example format that can be published and consumed using XMPP.

XMPPは特に、ブローカーとして機能するパブリッシュ・サブスクライブサービス[XEP-0060]を提供します。これにより、エンティティーが公開または消費できる利用可能な情報を発見するためのコントロールプレーン機能が実現されます。そのような情報は任意の構造化データ（XML、JSONなど）の形式をとることができますが、この文書では、インシデントオブジェクト記述交換フォーマット（IODEF）[RFC7970]を使用する例でXMPP-Gridの原則を示します。つまり、XMPPを使用してほかのセキュリティー情報フォーマットを共有することもできますが、この文書では、XMPPを使用して公開・消費できるフォーマットの一例としてIODEFを使用します。

2. Terminology

2. 用語

This document uses XMPP terminology defined in [RFC6120] and [XEP-0060]. Because the intended audience for this document is those who implement and deploy security reporting systems, mappings are provided for the benefit of XMPP developers and operators.

この文書では、[RFC6120]と[XEP-0060]で定義されているXMPPの用語を使用します。この文書が想定する読者はセキュリティー報告システムを実装・展開する人々であるため、XMPPの開発者と運用者のために用語の対応関係を示します。

Broker:
A specific type of controller containing control-plane functions; as used here, the term refers to an XMPP publish-subscribe service.
Broker Flow:
A method by which security incident reports and other security-relevant information are published and consumed in a mediated fashion through a Broker. In this flow, the Broker handles authorization of Consumers and Providers to Topics, receives messages from Providers, and delivers published messages to Consumers.
Consumer:
An entity that contains functions to receive information from other components; as used here, the term refers to an XMPP publish-subscribe Subscriber.
Controller:
A component containing control-plane functions that manage and facilitate information sharing or execute on security functions; as used here, the term refers to an XMPP server, which provides core message delivery [RFC6120] used by publish-subscribe entities.
Node:
The XMPP term for a Topic.
Platform:
Any entity that connects to the XMPP-Grid in order to publish or consume security-relevant information.
Provider:
An entity that contains functions to provide information to other components; as used here, the term refers to an XMPP publish-subscribe Publisher.
Topic:
A contextual information channel created on a Broker on which messages generated by a Provider are propagated in real time to one or more Consumers. Each Topic is limited to a specific type and format of security data (e.g., IODEF namespace) and provides an XMPP interface by which the data can be obtained.
ブローカー（Broker）：
コントロールプレーン機能を含む特定の種類のコントローラーです。ここでは、この用語はXMPPのパブリッシュ・サブスクライブサービスを指します。
ブローカーフロー（Broker Flow）：
セキュリティーインシデントの報告やそのほかのセキュリティー関連情報が、ブローカーを介した仲介方式で公開・消費される方法です。このフローでは、ブローカーが、トピックに対するコンシューマーとプロバイダーの認可を処理し、プロバイダーからメッセージを受信し、公開されたメッセージをコンシューマーに配信します。
コンシューマー（Consumer）：
ほかのコンポーネントから情報を受信する機能を含むエンティティーです。ここでは、この用語はXMPPのパブリッシュ・サブスクライブにおけるサブスクライバー（Subscriber）を指します。
コントローラー（Controller）：
情報共有を管理・促進したり、セキュリティー機能を実行したりするコントロールプレーン機能を含むコンポーネントです。ここでは、この用語はXMPPサーバーを指します。XMPPサーバーは、パブリッシュ・サブスクライブのエンティティーが使用する中核的なメッセージ配信[RFC6120]を提供します。
ノード（Node）：
トピックを表すXMPPの用語です。
プラットフォーム（Platform）：
セキュリティー関連情報を公開または消費するためにXMPP-Gridに接続するあらゆるエンティティーです。
プロバイダー（Provider）：
ほかのコンポーネントに情報を提供する機能を含むエンティティーです。ここでは、この用語はXMPPのパブリッシュ・サブスクライブにおけるパブリッシャー（Publisher）を指します。
トピック（Topic）：
ブローカー上に作成される、文脈に応じた情報チャネルです。プロバイダーが生成したメッセージは、トピック上で1つ以上のコンシューマーにリアルタイムに伝播されます。各トピックは、特定の種類とフォーマットのセキュリティーデータ（たとえばIODEFの名前空間）に限定され、そのデータを取得するためのXMPPインターフェイスを提供します。

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

キーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、「要求されています（REQUIRED）」、「することになります（SHALL）」、「することはありません（SHALL NOT）」、「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。ただし、ここに示すようにすべて大文字で表示される場合に限ります。

3. Architecture

3. アーキテクチャー

The following figure illustrates the architecture of XMPP-Grid.

次の図は、XMPP-Gridのアーキテクチャーを示しています。

Platforms connect to the Controller (XMPP server) to authenticate and then establish appropriate authorizations to be a Provider or Consumer of topics of interest at the Broker. The control-plane messaging is established through XMPP and is shown as "A" (control-plane interface) in Figure 1. Authorized Platforms can then share data either through the Broker (shown as "B" in Figure 1) or, in some cases, directly (shown as "C" in Figure 1). This document focuses primarily on the Broker Flow for information sharing ("direct flow" interactions can be used for specialized purposes, such as bulk data transfer, but methods for doing so are outside the scope of this document).

プラットフォームは、コントローラー（XMPPサーバー）に接続して認証を受け、その後、ブローカーで関心のあるトピックのプロバイダーまたはコンシューマーとなるための適切な認可を確立します。コントロールプレーンのメッセージングはXMPPを通じて確立され、Figure 1では「A」（コントロールプレーンインターフェイス）として示されています。認可されたプラットフォームは、その後、ブローカーを介して（Figure 1の「B」）、または場合によっては直接（Figure 1の「C」）データを共有できます。この文書では、主に情報共有のためのブローカーフローに焦点を当てます（「直接フロー」のやりとりは、大量データ転送などの特殊な目的に使用できますが、その方法はこの文書の範囲外です）。

4. Workflow

4. ワークフロー

Implementations of XMPP-Grid adhere to the following workflow:

XMPP-Gridの実装は、次のワークフローに従います：

  1. A Platform with a source of security data requests connection to the XMPP-Grid via a Controller.
  2. The Controller authenticates the Platform.
  3. The Platform establishes authorized privileges (e.g., privilege to publish and/or subscribe to one or more Topics) with a Broker.
  4. The Platform can publish security incident reports and other security-relevant information to a Topic, subscribe to a Topic, query a Topic, or perform any combination of these operations.
  5. A Provider unicasts its Topic updates to the Grid in real time through a Broker. The Broker handles replication and distribution of the Topic to Consumers. A Provider can publish the same or different data to multiple Topics.
  6. Any Platform on the Grid can subscribe to any Topic published to the Grid (as permitted by the authorization policy) and (as Consumers) will then receive a continual, real-time stream of updates from the Topics to which it is subscribed.
  1. セキュリティーデータのソースを持つプラットフォームが、コントローラーを介してXMPP-Gridへの接続をリクエストします。
  2. コントローラーがプラットフォームを認証します。
  3. プラットフォームが、ブローカーとの間で認可された権限（たとえば、1つ以上のトピックに公開または購読、あるいはその両方を行う権限）を確立します。
  4. プラットフォームは、セキュリティーインシデントの報告やそのほかのセキュリティー関連情報をトピックに公開すること、トピックを購読すること、トピックに問い合わせること、またはこれらの操作を任意に組み合わせて行うことができます。
  5. プロバイダーは、ブローカーを介して、自身のトピックの更新をGridにリアルタイムでユニキャストします。ブローカーは、トピックの複製とコンシューマーへの配布を処理します。プロバイダーは、同じデータまたは異なるデータを複数のトピックに公開できます。
  6. Grid上のどのプラットフォームも、（認可ポリシーで許可されている範囲で）Gridに公開されている任意のトピックを購読でき、その後は（コンシューマーとして）購読しているトピックからの継続的でリアルタイムな更新のストリームを受信します。

The general workflow is summarized in the figure below.

全体的なワークフローを次の図にまとめます。

XMPP-Grid implementations MUST adhere to the mandatory-to-implement and mandatory-to-negotiate features as defined in [RFC6120]. Similarly, implementations MUST implement the publish-subscribe extension [XEP-0060] to facilitate the asynchronous sharing of information. Implementations SHOULD implement Service Discovery as defined in [XEP-0030] to facilitate the means to dynamically discover the available information and namespaces (Topics) to be published or consumed. Care should be taken with implementations if their deployments allow for a large number of Topics. The result set management as defined in [XEP-0059] SHOULD be used to allow the requesting entity to explicitly request Service Discovery result sets to be returned in pages or a limited size, if the discovery results are larger in size. Note that the control plane may optionally also implement [XEP-0203] to facilitate delayed delivery of messages to the connected consumer as described in [XEP-0060]. Since information may be timely and sensitive, capability providers should communicate to the Controller whether its messages can be cached for delayed delivery during configuration; such a function is out of scope for this document.

XMPP-Gridの実装は、[RFC6120]で定義されている実装必須の機能とネゴシエーション必須の機能に従わなければなりません（MUST）。同様に、情報の非同期的な共有を促進するために、実装はパブリッシュ・サブスクライブ拡張[XEP-0060]を実装しなければなりません（MUST）。公開または消費できる利用可能な情報と名前空間（トピック）を動的に発見する手段を促進するために、実装は[XEP-0030]で定義されているサービスディスカバリーを実装すべきです（SHOULD）。展開において多数のトピックが許可される場合、実装には注意が必要です。ディスカバリーの結果のサイズが大きい場合に、リクエストを行うエンティティーがサービスディスカバリーの結果セットをページ単位または制限されたサイズで返すよう明示的にリクエストできるように、[XEP-0059]で定義されている結果セット管理を使用すべきです（SHOULD）。なお、[XEP-0060]で説明されているように、接続しているコンシューマーへのメッセージの遅延配信を促進するために、コントロールプレーンはオプションで[XEP-0203]も実装できます。情報は時間に敏感で機密性が高い場合があるため、機能を提供する側は、設定時に、自身のメッセージを遅延配信のためにキャッシュしてよいかどうかをコントローラーに伝えるべきです。そのような機能はこの文書の範囲外です。

The following sections provide protocol examples for the service discovery and publish-subscribe parts of the workflow.

次のセクションでは、ワークフローのうちサービスディスカバリーとパブリッシュ・サブスクライブの部分について、プロトコルの例を示します。

5. Service Discovery

5. サービスディスカバリー

Using the XMPP service discovery extension [XEP-0030], a Controller enables Platforms to discover what information can be consumed through the Broker and at which Topics. Platforms could use [XEP-0059] to restrict the size of the result sets the Controller returns in a Service Discovery response. As an example, the Controller at 'security-grid.example' might provide a Broker at 'broker.security-grid.example', which hosts a number of Topics. A Platform at 'xmpp-grid-client@mile-host.example' would query the Broker about its available Topics by sending an XMPP "disco#items" request to the Broker:

XMPPのサービスディスカバリー拡張[XEP-0030]を使用して、コントローラーは、どのような情報をブローカーを通じてどのトピックで消費できるかをプラットフォームが発見できるようにします。プラットフォームは、[XEP-0059]を使用して、コントローラーがサービスディスカバリーのレスポンスで返す結果セットのサイズを制限できます。例として、「security-grid.example」にあるコントローラーが「broker.security-grid.example」にブローカーを提供し、そこで多数のトピックをホストしているとします。「xmpp-grid-client@mile-host.example」にあるプラットフォームは、XMPPの「disco#items」リクエストをブローカーに送信することで、利用可能なトピックについてブローカーに問い合わせます：

<iq type='get'
    from='xmpp-grid-client@mile-host.example/2EBE702A97D6'
    to='broker.security-grid.example'
    id='B3C17F7B-B9EF-4ABA-B08D-805DA9F34626'>
  <query xmlns='http://jabber.org/protocol/disco#items'/>
</iq>

<iq type='get'
    from='xmpp-grid-client@mile-host.example/2EBE702A97D6'
    to='broker.security-grid.example'
    id='B3C17F7B-B9EF-4ABA-B08D-805DA9F34626'>
  <query xmlns='http://jabber.org/protocol/disco#items'/>
</iq>

The Broker responds with the Topics it hosts:

ブローカーは、ホストしているトピックを応答します：

<iq type='result'
    from='broker.security-grid.example'
    to='xmpp-grid-client@mile-host.example/2EBE702A97D6'
    id='B3C17F7B-B9EF-4ABA-B08D-805DA9F34626'>
  <query xmlns='http://jabber.org/protocol/disco#items'>
    <item node='NEA1'
          name='Endpoint Posture Information'
          jid='broker.security-grid.example'/>
    <item node='MILEHost'
          name='MILE Host Data'
          jid='broker.security-grid.example'/>
  </query>
</iq>

<iq type='result'
    from='broker.security-grid.example'

8. Security Considerations

8. セキュリティーに関する考慮事項

An XMPP-Grid Controller serves as a controlling broker for XMPP-Grid Platforms such as enforcement points, policy servers, Configuration Management Databases (CMDBs), and sensors, using a publish-subscribe-search model of information exchange and lookup. By increasing the ability of XMPP-Grid Platforms to learn about and respond to security incident reports and other security-relevant information, XMPP-Grid can improve the timeliness and utility of the security system. However, this integrated security system can also be exploited by attackers if they can compromise it. Therefore, strong security protections for XMPP-Grid are essential.

XMPP-Gridコントローラーは、情報の交換と検索にパブリッシュ・サブスクライブ・検索モデルを使用して、執行ポイント、ポリシーサーバー、構成管理データベース（CMDB）、センサーなどのXMPP-Gridプラットフォームのための制御ブローカーとして機能します。XMPP-Gridプラットフォームがセキュリティーインシデントの報告やそのほかのセキュリティー関連情報について知り、それに対応する能力を高めることで、XMPP-Gridはセキュリティーシステムの適時性と有用性を向上させることができます。しかし、この統合されたセキュリティーシステムは、攻撃者がそれを侵害できた場合には、攻撃者に悪用される可能性もあります。したがって、XMPP-Gridに対する強力なセキュリティー保護が不可欠です。

As XMPP is the core of this document, the security considerations of [RFC6120] apply. In addition, as XMPP-Grid defines a specific instance, this section provides a security analysis of the XMPP-Grid data transfer protocol and the architectural elements that employ it, specifically with respect to their use of this protocol. Three subsections define the trust model (which elements are trusted to do what), the threat model (attacks that can be mounted on the system), and the countermeasures (ways to address or mitigate the threats previously identified).

XMPPがこの文書の中核であるため、[RFC6120]のセキュリティーに関する考慮事項が適用されます。さらに、XMPP-Gridは特定のインスタンスを定義するため、このセクションでは、XMPP-Gridのデータ転送プロトコルとそれを使用するアーキテクチャー要素について、特にこのプロトコルの使用に関するセキュリティー分析を示します。3つのサブセクションで、信頼モデル（どの要素が何を行うと信頼されるか）、脅威モデル（システムに対して仕掛けられる攻撃）、対策（先に特定した脅威に対処または緩和する方法）を定義します。

8.1. Trust Model

8.1. 信頼モデル

The first step in analyzing the security of the XMPP-Grid transport protocol is to describe the trust model and list what each architectural element is trusted to do. The items listed here are assumptions, but provisions are made in "Threat Model" (Section 8.2) and "Countermeasures" (Section 8.3) for elements that fail to perform as they were trusted to do.

XMPP-Gridのトランスポートプロトコルのセキュリティーを分析する最初のステップは、信頼モデルを記述し、各アーキテクチャー要素が何を行うと信頼されているかを列挙することです。ここに挙げる項目は前提ですが、信頼されたとおりに動作しない要素については、「脅威モデル」（Section 8.2）と「対策」（Section 8.3）で対処します。

8.1.1. Network

8.1.1. ネットワーク

The network used to carry XMPP-Grid messages (i.e., the underlying network transport layer over which XMPP runs) is trusted to:

XMPP-Gridのメッセージを運ぶために使用されるネットワーク（つまり、XMPPが動作する下位のネットワークトランスポート層）は、次のことを行うと信頼されます：

  • Perform best-effort delivery of network traffic
  • ネットワークトラフィックのベストエフォート配信を行います

The network used to carry XMPP-Grid messages is not expected (trusted) to:

XMPP-Gridのメッセージを運ぶために使用されるネットワークは、次のことを行うとは期待（信頼）されません：

  • Provide confidentiality or integrity protection for messages sent over it
  • Provide timely or reliable service
  • ネットワーク上で送信されるメッセージに対して機密性や完全性の保護を提供します
  • 適時なサービスや信頼性のあるサービスを提供します

8.1.2. XMPP-Grid Platforms

8.1.2. XMPP-Gridプラットフォーム

Authorized XMPP-Grid Platforms are trusted to:

認可されたXMPP-Gridプラットフォームは、次のことを行うと信頼されます：

  • Preserve the confidentiality of sensitive data retrieved via the XMPP-Grid Controller
  • XMPP-Gridコントローラーを介して取得した機密データの機密性を保持します

8.1.3. XMPP-Grid Controller

8.1.3. XMPP-Gridコントローラー

The XMPP-Grid Controller (including its associated Broker) is trusted to:

XMPP-Gridコントローラー（関連するブローカーを含む）は、次のことを行うと信頼されます：

  • Broker requests for data and enforce authorization of access to this data throughout its lifecycle
  • Perform service requests in a timely and accurate manner
  • Create and maintain accurate operational attributes
  • Only reveal data to and accept service requests from authorized parties
  • Preserve the integrity (and confidentiality against unauthorized parties) of the data flowing through it.
  • データに対するリクエストを仲介し、データのライフサイクル全体にわたってそのデータへのアクセスの認可を強制します
  • サービスリクエストを適時かつ正確に実行します
  • 正確な運用属性を作成・維持します
  • 認可された当事者にのみデータを開示し、認可された当事者からのサービスリクエストのみを受け入れます
  • 自身を通過するデータの完全性（および認可されていない当事者に対する機密性）を保持します。

The XMPP-Grid Controller is not expected (trusted) to:

XMPP-Gridコントローラーは、次のことを行うとは期待（信頼）されません：

  • Verify the truth (correctness) of data
  • データの真偽（正確性）を検証します

8.1.4. Certification Authority

8.1.4. 認証局

To allow XMPP-Grid Platforms to mutually authenticate with XMPP-Grid Controllers, it is expected that a Certification Authority (CA) is employed to issue certificates. Such a CA (or each CA, if there are several) is trusted to:

XMPP-GridプラットフォームがXMPP-Gridコントローラーと相互に認証できるように、証明書を発行するために認証局（CA）が使用されることが想定されています。そのようなCA（複数ある場合は各CA）は、次のことを行うと信頼されます：

  • Ensure that only proper certificates are issued and that all certificates are issued in accordance with the CA's policies
  • Revoke certificates previously issued when necessary
  • Regularly and securely distribute certificate revocation information
  • Promptly detect and report any violations of this trust so that they can be handled
  • 適切な証明書のみが発行され、すべての証明書がCAのポリシーに従って発行されることを保証します
  • 必要に応じて、以前に発行した証明書を失効させます
  • 証明書の失効情報を定期的かつ安全に配布します
  • この信頼に対する違反を速やかに検出・報告し、それに対処できるようにします

The CA is not expected (trusted) to:

CAは、次のことを行うとは期待（信頼）されません：

  • Issue certificates that go beyond the XMPP-Grid needs or other constraints imposed by a relying party.
  • XMPP-Gridの必要性や、依拠当事者が課すそのほかの制約を超える証明書を発行します。

8.2. Threat Model

8.2. 脅威モデル

To secure the XMPP-Grid data transfer protocol and the architectural elements that implement it, this section identifies the attacks that can be mounted against the protocol and elements.

XMPP-Gridのデータ転送プロトコルとそれを実装するアーキテクチャー要素を保護するために、このセクションでは、プロトコルと要素に対して仕掛けられる攻撃を特定します。

8.2.1. Network Attacks

8.2.1. ネットワーク攻撃

A variety of attacks can be mounted using the network. For the purposes of this subsection, the phrase "network traffic" can be taken to mean messages and/or parts of messages. Any of these attacks can be mounted by network elements, by parties who control network elements, and (in many cases) by parties who control network-attached devices.

ネットワークを使用して、さまざまな攻撃を仕掛けることができます。このサブセクションでは、「ネットワークトラフィック」という語句は、メッセージやメッセージの一部、またはその両方を意味するものとします。これらの攻撃はいずれも、ネットワーク要素、ネットワーク要素を制御する当事者、そして（多くの場合）ネットワークに接続されたデバイスを制御する当事者によって仕掛けられる可能性があります。

  • Network traffic can be passively monitored to glean information from any unencrypted traffic
  • Even if all traffic is encrypted, valuable information can be gained by traffic analysis (volume, timing, source and destination addresses, etc.)
  • Network traffic can be modified in transit
  • Previously transmitted network traffic can be replayed
  • New network traffic can be added
  • Network traffic can be blocked, perhaps selectively
  • A man-in-the-middle (MITM) attack can be mounted where an attacker interposes itself between two communicating parties and impersonates the other end to either or both parties
  • Undesired network traffic can be sent in an effort to overload an architectural component, thus mounting a denial-of-service attack
  • ネットワークトラフィックが受動的に監視され、暗号化されていないトラフィックから情報が収集される可能性があります
  • すべてのトラフィックが暗号化されていても、トラフィック分析（量、タイミング、送信元アドレスと宛先アドレスなど）によって価値のある情報が得られる可能性があります
  • ネットワークトラフィックが転送中に改ざんされる可能性があります
  • 以前に送信されたネットワークトラフィックがリプレイされる可能性があります
  • 新しいネットワークトラフィックが追加される可能性があります
  • ネットワークトラフィックが、場合によっては選択的にブロックされる可能性があります
  • 中間者（MITM）攻撃が仕掛けられる可能性があります。この攻撃では、攻撃者が通信している2つの当事者の間に入り込み、一方または両方の当事者に対して相手側になりすまします
  • アーキテクチャーのコンポーネントを過負荷にしようとして不要なネットワークトラフィックが送信され、サービス拒否攻撃が仕掛けられる可能性があります

8.2.2. XMPP-Grid Platforms

8.2.2. XMPP-Gridプラットフォーム

An unauthorized XMPP-Grid Platform (one that is not recognized by the XMPP-Grid Controller or is recognized but not authorized to perform any actions) cannot mount any attacks other than those listed in "Network Attacks" (Section 8.2.1).

認可されていないXMPP-Gridプラットフォーム（XMPP-Gridコントローラーに認識されていないもの、または認識されているがいかなるアクションの実行も認可されていないもの）は、「ネットワーク攻撃」（Section 8.2.1）に挙げた攻撃以外の攻撃を仕掛けることはできません。

An authorized XMPP-Grid Platform, on the other hand, can mount many attacks. These attacks might occur because the XMPP-Grid Platform is controlled by a malicious, careless, or incompetent party (whether because its owner is malicious, careless, or incompetent or because the XMPP-Grid Platform has been compromised and is now controlled by a party other than its owner). They might also occur because the XMPP-Grid Platform is running malicious software, the XMPP-Grid Platform is running buggy software (which can fail in a state that floods the network with traffic), or the XMPP-Grid Platform has been configured improperly. From a security standpoint, it generally makes no difference why an attack is initiated. The same countermeasures can be employed in any case.

一方、認可されたXMPP-Gridプラットフォームは、多くの攻撃を仕掛けることができます。これらの攻撃は、XMPP-Gridプラットフォームが悪意のある、不注意な、または無能な当事者によって制御されているために発生する可能性があります（その所有者が悪意のある、不注意な、または無能な者であるためか、XMPP-Gridプラットフォームが侵害されて現在は所有者以外の当事者によって制御されているためかを問いません）。また、XMPP-Gridプラットフォームが悪意のあるソフトウェアを実行している、XMPP-Gridプラットフォームがバグのあるソフトウェア（ネットワークをトラフィックで溢れさせる状態で異常終了する可能性があるもの）を実行している、またはXMPP-Gridプラットフォームが不適切に設定されているために発生する可能性もあります。セキュリティーの観点からは、攻撃がなぜ開始されたかは一般に関係ありません。どのような場合でも同じ対策を使用できます。

Here is a list of attacks that can be mounted by an authorized XMPP-Grid Platform:

認可されたXMPP-Gridプラットフォームが仕掛けることのできる攻撃の一覧を次に示します：

  • Cause many false alarms or otherwise overload the XMPP-Grid Controller or other elements in the network security system (including human administrators), leading to a denial of service or parts of the network security system being disabled.
  • Omit important actions (such as posting incriminating data), resulting in incorrect access.
  • Use confidential information obtained from the XMPP-Grid Controller to enable further attacks (such as using endpoint health check results to exploit vulnerable endpoints).
  • Advertise data crafted to exploit vulnerabilities in the XMPP-Grid Controller or in other XMPP-Grid Platforms with the goal of compromising those systems.
  • Issue a search request or set up a subscription that matches an enormous result, leading to resource exhaustion on the XMPP-Grid Controller, the publishing XMPP-Grid Platform, and/or the network.
  • Establish a communication channel using another XMPP-Grid Platform's session-id.
  • Advertise false data that leads to incorrect (e.g., potentially attacker-controlled or -induced) behavior of XMPP-Grid Platforms by virtue of applying correct procedures to the falsified input.
  • 多数の誤警報を発生させたり、そのほかの方法でXMPP-Gridコントローラーやネットワークセキュリティーシステム内のほかの要素（人間の管理者を含む）を過負荷にしたりして、サービス拒否やネットワークセキュリティーシステムの一部の無効化を引き起こします。
  • 重要なアクション（不利な証拠となるデータの投稿など）を省略して、誤ったアクセスを引き起こします。
  • XMPP-Gridコントローラーから取得した機密情報を使用して、さらなる攻撃を可能にします（エンドポイントのヘルスチェックの結果を使用して脆弱なエンドポイントを悪用するなど）。
  • XMPP-GridコントローラーやほかのXMPP-Gridプラットフォームの脆弱性を悪用するように細工されたデータを広告し、それらのシステムを侵害することを狙います。
  • 膨大な結果に一致する検索リクエストを発行したり購読を設定したりして、XMPP-Gridコントローラー、公開側のXMPP-Gridプラットフォーム、ネットワークのいずれか、またはそのすべてでリソースの枯渇を引き起こします。
  • 別のXMPP-Gridプラットフォームのsession-idを使用して通信チャネルを確立します。
  • 偽のデータを広告して、改ざんされた入力に正しい手順を適用させることで、XMPP-Gridプラットフォームの誤った動作（たとえば、攻撃者が制御または誘導する可能性のある動作）を引き起こします。

Dependencies or vulnerabilities of authorized XMPP-Grid Platforms can be exploited to effect these attacks. Another way to effect these attacks is to gain the ability to impersonate an XMPP-Grid Platform (through theft of the XMPP-Grid Platform's identity credentials or through other means). Even a clock skew between the XMPP-Grid Platform and XMPP-Grid Controller can cause problems if the XMPP-Grid Platform assumes that old XMPP-Grid Platform data should be ignored.

認可されたXMPP-Gridプラットフォームの依存関係や脆弱性が悪用されて、これらの攻撃が実行される可能性があります。これらの攻撃を実行する別の方法は、（XMPP-Gridプラットフォームの識別用クレデンシャルの窃取や、そのほかの手段によって）XMPP-Gridプラットフォームになりすます能力を得ることです。XMPP-GridプラットフォームとXMPP-Gridコントローラーとの間のわずかな時計のずれでさえ、XMPP-Gridプラットフォームが古いXMPP-Gridプラットフォームのデータを無視すべきだと想定している場合には、問題を引き起こす可能性があります。

8.2.3. XMPP-Grid Controllers

8.2.3. XMPP-Gridコントローラー

An unauthorized XMPP-Grid Controller (one that is not trusted by XMPP-Grid Platforms) cannot mount any attacks other than those listed in "Network Attacks" (Section 8.2.1).

認可されていないXMPP-Gridコントローラー（XMPP-Gridプラットフォームから信頼されていないもの）は、「ネットワーク攻撃」（Section 8.2.1）に挙げた攻撃以外の攻撃を仕掛けることはできません。

An authorized XMPP-Grid Controller can mount many attacks. Similar to the XMPP-Grid Platform case described above, these attacks might occur because the XMPP-Grid Controller is controlled by a malicious, careless, or incompetent party (either an XMPP-Grid Controller administrator or an attacker who has seized control of the XMPP-Grid Controller). They might also occur because the XMPP-Grid Controller is running malicious software, the XMPP-Grid Controller is running buggy software (which can fail in a state that corrupts data or floods the network with traffic), or the XMPP-Grid Controller has been configured improperly.

認可されたXMPP-Gridコントローラーは、多くの攻撃を仕掛けることができます。前述のXMPP-Gridプラットフォームの場合と同様に、これらの攻撃は、XMPP-Gridコントローラーが悪意のある、不注意な、または無能な当事者（XMPP-Gridコントローラーの管理者、またはXMPP-Gridコントローラーの制御を奪った攻撃者）によって制御されているために発生する可能性があります。また、XMPP-Gridコントローラーが悪意のあるソフトウェアを実行している、XMPP-Gridコントローラーがバグのあるソフトウェア（データを破損したりネットワークをトラフィックで溢れさせたりする状態で異常終了する可能性があるもの）を実行している、またはXMPP-Gridコントローラーが不適切に設定されているために発生する可能性もあります。

All of the attacks listed for XMPP-Grid Platform above can be mounted by the XMPP-Grid Controller. Detection of these attacks will be more difficult since the XMPP-Grid Controller can create false operational attributes and/or logs that imply some other party created any bad data.

上記のXMPP-Gridプラットフォームについて挙げた攻撃はすべて、XMPP-Gridコントローラーも仕掛けることができます。XMPP-Gridコントローラーは、不正なデータをほかの当事者が作成したかのように見せかける偽の運用属性やログ、またはその両方を作成できるため、これらの攻撃の検出はより困難になります。

Additional XMPP-Grid Controller attacks can include:

XMPP-Gridコントローラーによる追加の攻撃には、次のようなものがあります：

  • Exposing different data to different XMPP-Grid Platforms to mislead investigators or cause inconsistent behavior.
  • Mounting an even more effective denial-of-service attack than a single XMPP-Grid Platform could; some mechanisms include inducing many platforms to perform the same operation in an amplification-style attack, completely refusing to pass any traffic at all, or sending floods of traffic to (certain) platforms or other targets.
  • Obtaining and caching XMPP-Grid Platform credentials so they can be used to impersonate XMPP-Grid Platforms even after a breach of the XMPP-Grid Controller is repaired. Some Simple Authentication and Security Layer (SASL) mechanisms (including the mandatory-to-implement SCRAM and EXTERNAL with TLS mutual certificate-based authentication) do not admit this class of attack, but others (such as PLAIN) are susceptible.
  • Obtaining and caching XMPP-Grid Controller administrator credentials so they can be used to regain control of the XMPP-Grid Controller after the breach of the XMPP-Grid Controller is repaired.
  • Eavesdropping, injecting, or modifying the data being transferred between Provider and Consumer.
  • 異なるXMPP-Gridプラットフォームに異なるデータを公開して、調査者を誤った方向に導いたり、一貫性のない動作を引き起こしたりします。
  • 単一のXMPP-Gridプラットフォームが行えるよりもさらに効果的なサービス拒否攻撃を仕掛けます。そのメカニズムには、増幅型の攻撃で多数のプラットフォームに同じ操作を実行させること、トラフィックの中継を完全に拒否すること、（特定の）プラットフォームやほかの標的に大量のトラフィックを送信することなどがあります。
  • XMPP-Gridプラットフォームのクレデンシャルを取得してキャッシュし、XMPP-Gridコントローラーの侵害が修復された後でもXMPP-Gridプラットフォームになりすますために使用します。一部のSimple Authentication and Security Layer（SASL）メカニズム（実装必須のSCRAMや、TLSの証明書ベースの相互認証を伴うEXTERNALを含む）はこの種の攻撃を許しませんが、ほかのメカニズム（PLAINなど）はこの攻撃を受けやすいです。
  • XMPP-Gridコントローラーの管理者のクレデンシャルを取得してキャッシュし、XMPP-Gridコントローラーの侵害が修復された後にXMPP-Gridコントローラーの制御を取り戻すために使用します。
  • プロバイダーとコンシューマーの間で転送されるデータを盗聴、注入、または改ざんします。

Dependencies or vulnerabilities of the XMPP-Grid Controller can be exploited to obtain control of the XMPP-Grid Controller and effect these attacks.

XMPP-Gridコントローラーの依存関係や脆弱性が悪用されて、XMPP-Gridコントローラーの制御が奪われ、これらの攻撃が実行される可能性があります。

8.2.4. Certification Authority

8.2.4. 認証局

A Certification Authority trusted to issue certificates for the XMPP-Grid Controller and/or XMPP-Grid Platforms can mount several attacks:

XMPP-GridコントローラーやXMPP-Gridプラットフォーム、またはその両方の証明書を発行すると信頼されている認証局は、いくつかの攻撃を仕掛けることができます：

  • Issue certificates for unauthorized parties, enabling them to impersonate authorized parties such as the XMPP-Grid Controller or an XMPP-Grid Platform. This can lead to all the threats that can be mounted by the certificate's subject.
  • Issue certificates without following all of the CA's policies. Because this can result in issuing certificates that can be used to impersonate authorized parties, this can lead to all the threats that can be mounted by the certificate's subject.
  • Fail to revoke previously issued certificates that need to be revoked. This can lead to undetected impersonation of the certificate's subject or failure to revoke authorization of the subject and therefore can lead to all of the threats that can be mounted by that subject.
  • Fail to regularly and securely distribute certificate revocation information. This can cause a relying party to accept a revoked certificate, leading to undetected impersonation of the certificate's subject or failure to revoke authorization of the subject and therefore can lead to all of the threats that can be mounted by that subject. It can also cause a relying party to refuse to proceed with a transaction because timely revocation information is not available, even though the transaction should be permitted to proceed.
  • Allow the CA's private key to be revealed to an unauthorized party. This can lead to all the threats above. Even worse, the actions taken with the private key will not be known to the CA.
  • Fail to promptly detect and report errors and violations of trust so that relying parties can be promptly notified. This can cause the threats listed earlier in this section to persist longer than necessary, leading to many knock-on effects.
  • 認可されていない当事者に証明書を発行し、XMPP-GridコントローラーやXMPP-Gridプラットフォームなどの認可された当事者になりすますことを可能にします。これにより、証明書のサブジェクトが仕掛けることのできるあらゆる脅威が生じる可能性があります。
  • CAのポリシーのすべてに従わずに証明書を発行します。これにより、認可された当事者になりすますために使用できる証明書が発行される可能性があるため、証明書のサブジェクトが仕掛けることのできるあらゆる脅威が生じる可能性があります。
  • 失効させる必要のある、以前に発行した証明書を失効させません。これにより、証明書のサブジェクトのなりすましが検出されなかったり、サブジェクトの認可を取り消せなかったりする可能性があり、したがって、そのサブジェクトが仕掛けることのできるあらゆる脅威が生じる可能性があります。
  • 証明書の失効情報を定期的かつ安全に配布しません。これにより、依拠当事者が失効した証明書を受け入れてしまい、証明書のサブジェクトのなりすましが検出されなかったり、サブジェクトの認可を取り消せなかったりする可能性があり、したがって、そのサブジェクトが仕掛けることのできるあらゆる脅威が生じる可能性があります。また、本来は続行を許可すべきトランザクションであっても、適時な失効情報が得られないために、依拠当事者がトランザクションの続行を拒否する可能性もあります。
  • CAの秘密鍵を認可されていない当事者に開示してしまいます。これにより、上記のあらゆる脅威が生じる可能性があります。さらに悪いことに、その秘密鍵を使って行われたアクションはCAに知られません。
  • エラーや信頼の違反を速やかに検出・報告せず、依拠当事者に速やかに通知できるようにしません。これにより、このセクションで前述した脅威が必要以上に長く続き、多くの波及効果を引き起こす可能性があります。

8.3. Countermeasures

8.3. 対策

Below are countermeasures for specific attack scenarios to the XMPP-Grid infrastructure.

XMPP-Gridインフラストラクチャーに対する特定の攻撃シナリオへの対策を次に示します。

8.3.1. Securing the XMPP-Grid Data Transfer Protocol

8.3.1. XMPP-Gridデータ転送プロトコルの保護

To address network attacks, the XMPP-Grid data transfer protocol described in this document requires that the XMPP-Grid messages MUST be carried over TLS (minimally TLS 1.2 and preferably TLS 1.3 [RFC8446]) as described in [RFC6120] and updated by [RFC7590]. The XMPP-Grid Controller and XMPP-Grid Platforms SHOULD mutually authenticate. The XMPP-Grid Platform MUST verify the XMPP-Grid Controller's certificate and determine whether the XMPP-Grid Controller is trusted by this XMPP-Grid Platform before completing the TLS handshake. To ensure interoperability, implementations MUST implement at least either the SASL EXTERNAL mechanism [RFC4422] or the SASL SCRAM mechanism. When using the SASL SCRAM mechanism, the SCRAM-SHA-256-PLUS variant SHOULD be preferred over the SCRAM-SHA-256 variant, and SHA-256 variants [RFC7677] SHOULD be preferred over SHA-1 variants [RFC5802]). XMPP-Grid Platforms and XMPP-Grid Controllers using certificate-based authentication SHOULD each verify the revocation status of the other party's certificate. The selection of the XMPP-Grid Platform authentication technique to use in any particular deployment is left to the administrator.

ネットワーク攻撃に対処するため、この文書で説明するXMPP-Gridのデータ転送プロトコルでは、[RFC6120]で説明され[RFC7590]で更新されているとおり、XMPP-GridのメッセージをTLS（最低限TLS 1.2、できればTLS 1.3 [RFC8446]）上で運ばなければなりません（MUST）。XMPP-GridコントローラーとXMPP-Gridプラットフォームは相互に認証すべきです（SHOULD）。XMPP-Gridプラットフォームは、TLSハンドシェイクを完了する前に、XMPP-Gridコントローラーの証明書を検証し、そのXMPP-GridコントローラーがこのXMPP-Gridプラットフォームから信頼されているかどうかを判断しなければなりません（MUST）。相互運用性を確保するために、実装は少なくともSASL EXTERNALメカニズム[RFC4422]またはSASL SCRAMメカニズムのいずれかを実装しなければなりません（MUST）。SASL SCRAMメカニズムを使用する場合、SCRAM-SHA-256の亜種よりもSCRAM-SHA-256-PLUSの亜種を優先すべきです（SHOULD）。また、SHA-1の亜種[RFC5802]よりもSHA-256の亜種[RFC7677]を優先すべきです（SHOULD）。証明書ベースの認証を使用するXMPP-GridプラットフォームとXMPP-Gridコントローラーは、それぞれ相手の証明書の失効状態を検証すべきです（SHOULD）。個々の展開でどのXMPP-Gridプラットフォーム認証技術を使用するかの選択は、管理者に委ねられます。

These protocol security measures provide protection against all the network attacks listed in Section 8.2 except denial-of-service attacks. If protection against these denial-of-service attacks is desired, ingress filtering, rate limiting per source IP address, and other denial-of-service mitigation measures can be employed. In addition, an XMPP-Grid Controller MAY automatically disable a misbehaving XMPP-Grid Platform.

これらのプロトコルのセキュリティー対策は、Section 8.2に挙げたネットワーク攻撃のうち、サービス拒否攻撃を除くすべてに対する保護を提供します。これらのサービス拒否攻撃に対する保護が望まれる場合は、イングレスフィルタリング、送信元IPアドレスごとのレート制限、そのほかのサービス拒否緩和策を使用できます。さらに、XMPP-Gridコントローラーは、不正な動作をするXMPP-Gridプラットフォームを自動的に無効にしてもよいです（MAY）。

8.3.2. Securing XMPP-Grid Platforms

8.3.2. XMPP-Gridプラットフォームの保護

XMPP-Grid Platforms can be deployed in locations that are susceptible to physical attacks. Physical security measures can be taken to avoid compromise of XMPP-Grid Platforms, but these are not always practical or completely effective. An alternative measure is to configure the XMPP-Grid Controller to provide read-only access for such systems. The XMPP-Grid Controller SHOULD also include a full authorization model so that individual XMPP-Grid Platforms can be configured to have only the privileges that they need. The XMPP-Grid Controller MAY provide functional templates so that the administrator can configure a specific XMPP-Grid Platform as a DHCP [RFC2131] server and authorize only the operations and metadata types needed by a DHCP server to be permitted for that XMPP-Grid Platform. These techniques can reduce the negative impacts of a compromised XMPP-Grid Platform without diminishing the utility of the overall system.

XMPP-Gridプラットフォームは、物理的な攻撃を受けやすい場所に展開される可能性があります。XMPP-Gridプラットフォームの侵害を防ぐために物理的なセキュリティー対策をとることはできますが、それが常に実用的であったり、完全に効果的であったりするとは限りません。代替策として、そのようなシステムに対しては読み取り専用のアクセスを提供するようにXMPP-Gridコントローラーを設定することがあります。また、XMPP-Gridコントローラーは、個々のXMPP-Gridプラットフォームが必要な権限だけを持つように設定できるよう、完全な認可モデルを備えるべきです（SHOULD）。XMPP-Gridコントローラーは、管理者が特定のXMPP-GridプラットフォームをDHCP[RFC2131]サーバーとして設定し、DHCPサーバーが必要とする操作とメタデータの種類だけをそのXMPP-Gridプラットフォームに許可できるように、機能テンプレートを提供してもよいです（MAY）。これらの技術により、システム全体の有用性を損なうことなく、侵害されたXMPP-Gridプラットフォームの悪影響を軽減できます。

To handle attacks within the bounds of this authorization model, the XMPP-Grid Controller MAY also include rate limits and alerts for unusual XMPP-Grid Platform behavior. XMPP-Grid Controllers SHOULD make it easy to revoke an XMPP-Grid Platform's authorization when necessary. The XMPP-Grid Controller SHOULD include auditable logs of XMPP-Grid Platform activities.

この認可モデルの範囲内で行われる攻撃に対処するために、XMPP-Gridコントローラーは、XMPP-Gridプラットフォームの通常と異なる動作に対するレート制限とアラートを備えてもよいです（MAY）。XMPP-Gridコントローラーは、必要なときにXMPP-Gridプラットフォームの認可を容易に取り消せるようにすべきです（SHOULD）。XMPP-Gridコントローラーは、XMPP-Gridプラットフォームの活動について監査可能なログを備えるべきです（SHOULD）。

To avoid compromise of XMPP-Grid Platforms, they SHOULD be hardened against attack and minimized to reduce their attack surface. They should be well managed to minimize vulnerabilities in the underlying platform and in systems upon which the XMPP-Grid Platform depends. Personnel with administrative access should be carefully screened and monitored to detect problems as soon as possible.

XMPP-Gridプラットフォームの侵害を防ぐために、XMPP-Gridプラットフォームは攻撃に対して強化され、攻撃対象領域を減らすために最小化されるべきです（SHOULD）。また、下位のプラットフォームや、XMPP-Gridプラットフォームが依存するシステムの脆弱性を最小限に抑えるように、適切に管理されるべきです。管理アクセス権を持つ担当者は、問題をできるだけ早く検出できるように、慎重に審査・監視されるべきです。

8.3.3. Securing XMPP-Grid Controllers

8.3.3. XMPP-Gridコントローラーの保護

Because of the serious consequences of XMPP-Grid Controller compromise, XMPP-Grid Controllers need to be especially well hardened against attack and minimized to reduce their attack surface. They need to be well managed to minimize vulnerabilities in the underlying platform and in systems upon which the XMPP-Grid Controller depends. Network security measures such as firewalls or intrusion detection systems can be used to monitor and limit traffic to and from the XMPP-Grid Controller. Personnel with administrative access ought to be carefully screened and monitored to detect problems as soon as possible. Administrators SHOULD NOT use password-based authentication but SHOULD instead use non-reusable credentials and multi-factor authentication (where available). Physical security measures ought to be employed to prevent physical attacks on XMPP-Grid Controllers.

XMPP-Gridコントローラーの侵害は深刻な結果をもたらすため、XMPP-Gridコントローラーは攻撃に対して特に十分に強化され、攻撃対象領域を減らすために最小化される必要があります。また、下位のプラットフォームや、XMPP-Gridコントローラーが依存するシステムの脆弱性を最小限に抑えるように、適切に管理される必要があります。ファイアウォールや侵入検知システムなどのネットワークセキュリティー対策を使用して、XMPP-Gridコントローラーとの間のトラフィックを監視・制限できます。管理アクセス権を持つ担当者は、問題をできるだけ早く検出できるように、慎重に審査・監視されるべきです。管理者はパスワードベースの認証を使用すべきではありません（SHOULD NOT）。代わりに、再利用できないクレデンシャルと（利用可能な場合は）多要素認証を使用すべきです（SHOULD）。XMPP-Gridコントローラーに対する物理的な攻撃を防ぐために、物理的なセキュリティー対策を講じるべきです。

To ease detection of XMPP-Grid Controller compromise should it occur, XMPP-Grid Controller behavior should be monitored to detect unusual behavior (such as a reboot, a large increase in traffic, or different views of an information repository for similar XMPP-Grid Platforms). It is a matter of local policy whether XMPP-Grid Platforms log and/or notify administrators when peculiar XMPP-Grid Controller behavior is detected and whether read-only audit logs of security-relevant information (especially administrative actions) are maintained; however, such behavior is encouraged to aid in forensic analysis.

XMPP-Gridコントローラーの侵害が発生した場合にその検出を容易にするために、XMPP-Gridコントローラーの動作を監視して、通常と異なる動作（再起動、トラフィックの大幅な増加、類似したXMPP-Gridプラットフォームに対する情報リポジトリーの見え方の違いなど）を検出するべきです。XMPP-Gridコントローラーの特異な動作が検出されたときに、XMPP-Gridプラットフォームがそれをログに記録したり管理者に通知したりするかどうか、およびセキュリティー関連情報（特に管理アクション）の読み取り専用の監査ログを維持するかどうかは、ローカルポリシーの問題です。ただし、フォレンジック分析に役立てるために、そのような動作が推奨されます。

Furthermore, if compromise of an XMPP-Grid Controller is detected, a careful analysis should be performed, and any reusable credentials that could have been compromised should be reissued.

さらに、XMPP-Gridコントローラーの侵害が検出された場合は、慎重な分析を行い、侵害された可能性のある再利用可能なクレデンシャルをすべて再発行するべきです。

To address the potential for the XMPP-Grid Controller to eavesdrop, modify or inject data, it would be desirable to deploy end-to-end encryption between the Provider and the Consumer(s). Unfortunately, because there is no standardized method for encryption of one-to-many messages within XMPP, techniques for enforcing end-to-end encryption are out of scope for this specification.

XMPP-Gridコントローラーがデータを盗聴、改ざん、または注入する可能性に対処するためには、プロバイダーとコンシューマーの間にエンドツーエンド暗号化を展開することが望ましいでしょう。残念ながら、XMPPには1対多のメッセージを暗号化する標準化された方法がないため、エンドツーエンド暗号化を強制する技術はこの仕様の範囲外です。

8.3.4. Broker Access Models for Topics

8.3.4. トピックに対するブローカーのアクセスモデル

The XMPP publish-subscribe specification [XEP-0060] defines five access models for subscribing to Topics at a Broker: open, presence, roster, authorize, and whitelist. The first model allows uncontrolled access, and the next two models are appropriate only in instant-messaging applications. Therefore, a Broker SHOULD support only the authorize model (under which the Topic owner needs to approve all subscription requests and only subscribers can retrieve data items) and the whitelist model (under which only preconfigured Platforms can subscribe or retrieve data items). In order to ease the deployment burden, subscription approvals and whitelist management can be automated (e.g., the Topic "owner" can be a policy server). The choice between "authorize" and "whitelist" as the default access model is a matter for local service policy.

XMPPのパブリッシュ・サブスクライブ仕様[XEP-0060]は、ブローカーでトピックを購読するための5つのアクセスモデルを定義しています：open、presence、roster、authorize、whitelistです。最初のモデルは制御されないアクセスを許可し、次の2つのモデルはインスタントメッセージングのアプリケーションでのみ適切です。したがって、ブローカーは、authorizeモデル（トピックの所有者がすべての購読リクエストを承認する必要があり、サブスクライバーのみがデータ項目を取得できるモデル）とwhitelistモデル（事前に設定されたプラットフォームのみが購読またはデータ項目の取得を行えるモデル）のみをサポートすべきです（SHOULD）。展開の負担を軽減するために、購読の承認とホワイトリストの管理は自動化できます（たとえば、トピックの「所有者」をポリシーサーバーにできます）。デフォルトのアクセスモデルとして「authorize」と「whitelist」のどちらを選択するかは、ローカルのサービスポリシーの問題です。

8.3.5. Limit on Search Result Size

8.3.5. 検索結果のサイズの制限

While XMPP-Grid is designed for high scalability to hundreds of thousands of Platforms, an XMPP-Grid Controller MAY establish a limit to the amount of data it is willing to return in search or subscription results. Platforms could use [XEP-0059] to restrict the size of the result sets the Controller returns in search or subscription results or topics' service discovery. This mitigates the threat of an XMPP-Grid Platform causing resource exhaustion by issuing a search or subscription that leads to an enormous result.

XMPP-Gridは数十万のプラットフォームに対応できる高いスケーラビリティーを持つように設計されていますが、XMPP-Gridコントローラーは、検索結果や購読結果で返すデータ量に制限を設けてもよいです（MAY）。プラットフォームは、[XEP-0059]を使用して、検索結果や購読結果、トピックのサービスディスカバリーでコントローラーが返す結果セットのサイズを制限できます。これにより、XMPP-Gridプラットフォームが膨大な結果につながる検索や購読を発行してリソースの枯渇を引き起こすという脅威が緩和されます。

8.3.6. Securing the Certification Authority

8.3.6. 認証局の保護

As noted above, compromise of a Certification Authority (CA) trusted to issue certificates for the XMPP-Grid Controller and/or XMPP-Grid Platforms is a major security breach. Many guidelines for proper CA security have been developed: the CA/Browser Forum's Baseline Requirements, the American Institute of Certified Public Accountants (AICPA) / Canadian Institute of Chartered Accountants (CICA) Trust Service Principles, the IETF's Certificate Transparency [RFC6962], etc. The CA operator and relying parties should agree on appropriately rigorous security practices to be used.

前述のように、XMPP-GridコントローラーやXMPP-Gridプラットフォーム、またはその両方の証明書を発行すると信頼されている認証局（CA）の侵害は、重大なセキュリティー侵害です。適切なCAのセキュリティーのために、多くのガイドラインが策定されています：CA/Browser ForumのBaseline Requirements、American Institute of Certified Public Accountants（AICPA）/ Canadian Institute of Chartered Accountants（CICA）のTrust Service Principles、IETFのCertificate Transparency[RFC6962]などです。CAの運用者と依拠当事者は、使用する適切に厳格なセキュリティープラクティスについて合意するべきです。

Even with the most rigorous security practices, a CA can be compromised. If this compromise is detected quickly, relying parties can remove the CA from their list of trusted CAs, and other CAs can revoke any certificates issued to the CA. However, CA compromise may go undetected for some time, and there's always the possibility that a CA is being operated improperly or in a manner that is not in the interests of the relying parties. For this reason, relying parties may wish to "pin" a small number of particularly critical certificates (such as the certificate for the XMPP-Grid Controller). Once a certificate has been pinned, the relying party will not accept another certificate in its place unless the Administrator explicitly commands it to do so. This does not mean that the relying party will not check the revocation status of pinned certificates. However, the Administrator can still be consulted if a pinned certificate is revoked, since the CA and revocation process are not completely trusted. By "pinning" one or a small set of certificates, the relying party has identified the effective XMPP-Grid Controller(s) authorized for connection.

最も厳格なセキュリティープラクティスを採用していても、CAが侵害される可能性はあります。この侵害がすぐに検出されれば、依拠当事者はそのCAを信頼するCAのリストから削除でき、ほかのCAはそのCAに発行した証明書を失効させることができます。しかし、CAの侵害がしばらく検出されないこともありますし、CAが不適切に、あるいは依拠当事者の利益にならない方法で運用されている可能性も常にあります。このため、依拠当事者は、特に重要な少数の証明書（XMPP-Gridコントローラーの証明書など）を「ピン留め」したいと考えるかもしれません。証明書がピン留めされると、管理者が明示的に指示しない限り、依拠当事者はその代わりに別の証明書を受け入れることはありません。これは、依拠当事者がピン留めされた証明書の失効状態をチェックしないという意味ではありません。ただし、CAと失効プロセスは完全には信頼されていないため、ピン留めされた証明書が失効した場合でも、管理者に相談することができます。1つまたは少数の証明書を「ピン留め」することで、依拠当事者は接続を認可された実際のXMPP-Gridコントローラーを特定したことになります。

8.3.7. End-to-End Encryption of Messages

8.3.7. メッセージのエンドツーエンド暗号化

Because it is expected that there will be a relatively large number of Consumers for every Topic, for the purposes of content discovery and scaling, this document specifies a "one-to-many" communications pattern using the XMPP Publish-Subscribe extension. Unfortunately, there is no standardized technology for end-to-end encryption of one-to-many messages in XMPP. This implies that messages can be subject to eavesdropping, data injection, and data modification attacks within a Broker or Controller. If it is necessary to mitigate against such attacks, implementers would need to select a messaging pattern other than [XEP-0060], most likely the basic "instant messaging" pattern specified in [RFC6121] with a suitable XMPP extension for end-to-end encryption. The description of such an approach is out of scope for this document.

コンテンツの発見とスケーリングのために、各トピックには比較的多数のコンシューマーが存在することが想定されるため、この文書では、XMPPのパブリッシュ・サブスクライブ拡張を使用した「1対多」の通信パターンを規定します。残念ながら、XMPPには1対多のメッセージのエンドツーエンド暗号化のための標準化された技術がありません。これは、ブローカーやコントローラーの内部で、メッセージが盗聴、データ注入、データ改ざんの攻撃を受ける可能性があることを意味します。そのような攻撃を緩和する必要がある場合、実装者は[XEP-0060]以外のメッセージングパターンを選択する必要があるでしょう。最も可能性が高いのは、[RFC6121]で規定されている基本的な「インスタントメッセージング」パターンを、エンドツーエンド暗号化のための適切なXMPP拡張と組み合わせて使用することです。そのような方法の説明はこの文書の範囲外です。

8.4. Summary

8.4. まとめ

XMPP-Grid's considerable value as a broker for security-sensitive data exchange distribution also makes the protocol and the network security elements that implement it a target for attack. Therefore, strong security has been included as a basic design principle within the XMPP-Grid design process.

セキュリティー上重要なデータの交換と配布のためのブローカーとしてXMPP-Gridが持つ大きな価値は、同時に、プロトコルとそれを実装するネットワークセキュリティー要素を攻撃の標的にもします。したがって、XMPP-Gridの設計プロセスでは、強力なセキュリティーを基本的な設計原則として取り入れています。

The XMPP-Grid data transfer protocol provides strong protection against a variety of different attacks. In the event that an XMPP-Grid Platform or XMPP-Grid Controller is compromised, the effects of this compromise are reduced and limited with the recommended role-based authorization model and other provisions, and best practices for managing and protecting XMPP-Grid systems have been described. Taken together, these measures should provide protection commensurate with the threat to XMPP-Grid systems, thus ensuring that they fulfill their promise as a network security clearinghouse.

XMPP-Gridのデータ転送プロトコルは、さまざまな攻撃に対して強力な保護を提供します。XMPP-GridプラットフォームやXMPP-Gridコントローラーが侵害された場合でも、推奨されるロールベースの認可モデルやそのほかの規定によって、その侵害の影響は軽減・限定されます。また、XMPP-Gridシステムを管理・保護するためのベストプラクティスについても説明しました。これらの対策を組み合わせることで、XMPP-Gridシステムに対する脅威に見合った保護が提供され、XMPP-Gridシステムがネットワークセキュリティーの情報集約拠点（クリアリングハウス）としての役割を果たせるようになるはずです。

9. Privacy Considerations

9. プライバシーに関する考慮事項

XMPP-Grid Platforms can publish information about endpoint health, network access, events (which can include information about which services an endpoint is accessing), roles and capabilities, and the identity of the end user operating the endpoint. Any of this published information can be queried by other XMPP-Grid Platforms and could potentially be used to correlate network activity to a particular end user.

XMPP-Gridプラットフォームは、エンドポイントの健全性、ネットワークアクセス、イベント（エンドポイントがどのサービスにアクセスしているかに関する情報を含む場合があります）、ロールと機能、エンドポイントを操作しているエンドユーザーの識別情報に関する情報を公開できます。この公開された情報はいずれも、ほかのXMPP-Gridプラットフォームから問い合わせることができ、ネットワーク活動を特定のエンドユーザーに関連付けるために使用される可能性があります。

Dynamic and static information brokered by an XMPP-Grid Controller, ostensibly for the purposes of correlation by XMPP-Grid Platforms for intrusion detection, could be misused by a broader set of XMPP-Grid Platforms that hitherto have been performing specific roles with a strict, well-defined separation of duties.

XMPP-Gridコントローラーが仲介する動的・静的な情報は、表向きはXMPP-Gridプラットフォームが侵入検知のために相関分析を行うことを目的としていますが、これまで厳格で明確に定義された職務分離のもとで特定の役割を担ってきたより広い範囲のXMPP-Gridプラットフォームによって悪用される可能性があります。

Care needs to be taken by deployers of XMPP-Grid to ensure that the information published by XMPP-Grid Platforms does not violate agreements with end users or local and regional laws and regulations. This can be accomplished either by configuring XMPP-Grid Platforms to not publish certain information or by restricting access to sensitive data to trusted XMPP-Grid Platforms. That is, the easiest means to ensure privacy or protect sensitive data is to omit or not share it at all.

XMPP-Gridを展開する者は、XMPP-Gridプラットフォームが公開する情報が、エンドユーザーとの合意や、地域や国の法令に違反しないように注意する必要があります。これは、特定の情報を公開しないようにXMPP-Gridプラットフォームを設定するか、機密データへのアクセスを信頼できるXMPP-Gridプラットフォームに制限することで実現できます。つまり、プライバシーを確保したり機密データを保護したりする最も簡単な方法は、そのデータを省略するか、まったく共有しないことです。

Similarly, care must be taken by deployers and XMPP-Grid Controller implementations as they implement the appropriate auditing tools. In particular, any information, such as logs, must be sensitive to the type of information stored to ensure that the information does not violate privacy and agreements with end users or local and regional laws and regulations.

同様に、展開する者とXMPP-Gridコントローラーの実装は、適切な監査ツールを実装する際に注意しなければなりません。特に、ログなどのあらゆる情報は、その情報がプライバシーやエンドユーザーとの合意、地域や国の法令に違反しないように、保存される情報の種類に配慮したものでなければなりません。

Another consideration for deployers is to enable end-to-end encryption to ensure the data is protected while in transit between data layers and thus protected from the transport layer. The means to achieve end-to-end encryption is beyond the scope of this document.

展開する者にとってのもう1つの考慮事項は、データ層の間での転送中にデータが保護され、それによってトランスポート層から保護されるように、エンドツーエンド暗号化を有効にすることです。エンドツーエンド暗号化を実現する手段は、この文書の範囲外です。

10. Operations and Management Considerations

10. 運用と管理に関する考慮事項

In order to facilitate the management of Providers and the onboarding of Consumers, it is helpful to generate the following ahead of time:

プロバイダーの管理とコンシューマーのオンボーディングを容易にするために、次のものを事前に用意しておくと役立ちます：

  • Agreement between the operators of Provider services and the implementers of Consumer software regarding identifiers for common Topics (e.g., these could be registered with the XMPP Software Foundation's registry of well-known nodes for service discovery and publish-subscribe, located at <https://xmpp.org/registrar/nodes.html>).
  • Security certificates (including appropriate certificate chains) for Controllers, including identification of any Providers associated with the Controllers (which might be located at subdomains).
  • Consistent and secure access control policies for publishing and subscribing to Topics.
  • 一般的なトピックの識別子に関する、プロバイダーサービスの運用者とコンシューマーソフトウェアの実装者との間の合意です（たとえば、これらの識別子は、<https://xmpp.org/registrar/nodes.html>にある、サービスディスカバリーとパブリッシュ・サブスクライブのためのよく知られたノードを登録するXMPP Software Foundationのレジストリーに登録できます）。
  • コントローラーのセキュリティー証明書（適切な証明書チェーンを含む）です。これには、コントローラーに関連付けられたプロバイダー（サブドメインに配置されている場合があります）の識別が含まれます。
  • トピックへの公開と購読に関する、一貫性のある安全なアクセス制御ポリシーです。

These matters are out of scope for this document but ought to be addressed by the XMPP-Grid community.

これらの事項はこの文書の範囲外ですが、XMPP-Gridコミュニティーで取り組まれるべきです。
