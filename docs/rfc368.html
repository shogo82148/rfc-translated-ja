RFC 368

Comments on "Proposed Remote Job Entry Protocol"

RFC 368

「Proposed Remote Job Entry Protocol」に関するコメント

Abstract

概要

Chuck Holland's draft proposal (RFC #360) is an excellent document, very complete and consistent. Since the final standard RJE protocol will be widely used on the Network, honing its definition now will save trouble and discontent later. Therefore, I will proceed to make a new suggestions and pick a few nits.

Chuck Hollandの提案草案（RFC #360）は、非常に完全で一貫性のある優れた文書です。最終的な標準のRJEプロトコルはネットワーク上で広く使われることになるので、今その定義を磨いておけば、後々の面倒や不満を避けられます。そこで、いくつか新しい提案をし、細かい点をいくつか指摘します。

  1. In my humble opinion, the command verb "BYE" is overly cute; I would find "QUIT" much less offensive

  2. The "(pathname)" syntax (p.5) may need some reworking. It would be very desirable for all protocols or Network access programs to use the same syntax for selecting a host and socket and/or file name. (Note that the FTP documents use the term "pathname" in the more restricted sense of a local file system name.)

    1. The PORT construction seems very undesirable, since it depends upon a particular bit convention of TIP's. TIP's have bent Network protocols rather badly in the past, but surely we don't want to build their particular socket system into an official protocol.
    2. For convenience, it may be desirable to allow hex and octal socket numbers.
    3. There will probably be other hosts besides TIP's which will use the "(host-socket)" pathname, and some of them may want a transmission attribute other than "T". The proposed syntax should be changed to allow (attributes) in (host-socket)
    4. I see no reason to exclude attribute "TE", since the control characters cr, lf, and ff exist in EBCDIC as well as ASCII.
    5. There are many EBCDIC codes, and at least 2 ASCII's. The (code) construction needs expansion.
  3. The syntax of OUT might reflect the fact that pathname is required only for (disp) of "(S)".

  4. It may be desirable to distinguish syntactically (job-id) and job-file-id). For example, this would allow the command

         ABORT (job-file-id)

    to abort the job currently being transmitted, regardless of its id (this assumes that multiple jobs for a given user are sent sequentially).

  5. The replies presented in the document are very good, but may need some elaboration. For example, the syntax error messages should be more specific. When the user enters:

         OUT=(H) UCLA91: NE/ARP998.WGW.TEST

    he would like the error message to indicate explicitly that the hostname is not valid, rather than merely being told there is something wrong with one of the parameters.

  6. Experience with remote job entry to CCN via the Network has shown that the user wants a transmission status command, to find out how many records have been sent or received so far. The network bandwidth corresponds in order of magnitude to one page per second. The average output for jobs submitted to CCN from the Network has contained about 30 pages, so significant transmission delays are not unusual. It is important to add a command for this purpose.
  1. 私見ですが、コマンド動詞「BYE」は可愛らしすぎます。「QUIT」のほうがずっと気に障りません。

  2. 「(pathname)」の構文（5ページ）は、手直しが必要かもしれません。ホストとソケット、またはファイル名（あるいはその両方）を選ぶ際に、すべてのプロトコルやネットワークアクセスプログラムが同じ構文を使うことが非常に望ましいでしょう。（FTPの文書では、「pathname」という用語を、ローカルのファイルシステムの名前というより限定された意味で使っていることに注意してください。）

    1. PORTの構成は、TIPの特定のビットの規約に依存しているので、非常に望ましくないように思えます。TIPはこれまでネットワークプロトコルをかなりひどくねじ曲げてきましたが、TIP独自のソケットの仕組みを公式のプロトコルに組み込みたくはないはずです。
    2. 利便性のために、16進数と8進数のソケット番号を許すことが望ましいかもしれません。
    3. おそらく、TIPのほかにも「(host-socket)」のpathnameを使うホストがあり、その中には「T」以外の伝送属性を使いたいものもあるでしょう。提案されている構文は、(host-socket)の中で(attributes)を使えるように変更すべきです。
    4. 制御文字のcr、lf、ffはASCIIだけでなくEBCDICにも存在するので、属性「TE」を除外する理由は見当たりません。
    5. EBCDICのコードは数多くあり、ASCIIも少なくとも2つあります。(code)の構成は拡張が必要です。
  3. OUTの構文には、pathnameが必要なのは(disp)が「(S)」の場合だけであるという事実を反映させてもよいでしょう。

  4. (job-id)とjob-file-id)を構文上区別することが望ましいかもしれません。そうすれば、たとえば次のコマンドで

         ABORT (job-file-id)

    IDにかかわらず、現在送信中のジョブを中止できるようになります（これは、あるユーザーの複数のジョブが順番に送られることを前提としています）。

  5. 文書に示されている応答はとてもよいものですが、もう少し詳しくする必要があるかもしれません。たとえば、構文エラーのメッセージはもっと具体的にすべきです。ユーザーが次のように入力した場合、

         OUT=(H) UCLA91: NE/ARP998.WGW.TEST

    ユーザーは、単にパラメーターのどれかに誤りがあると告げられるのではなく、ホスト名が無効であることをエラーメッセージで明示的に示してほしいと思うでしょう。

  6. ネットワーク経由でCCNへのリモートジョブ投入を行った経験から、ユーザーは、これまでに送信または受信したレコードの数を知るための送信状況コマンドを求めていることがわかりました。ネットワークの帯域幅は、桁で言えば1秒あたり1ページに相当します。ネットワークからCCNに投入されたジョブの出力は平均でおよそ30ページあったので、かなりの送信遅延は珍しくありません。この目的のためのコマンドを追加することが重要です。
