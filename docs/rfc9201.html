RFC 9201

Additional OAuth Parameters for Authentication and Authorization for Constrained Environments (ACE)

RFC 9201

制約のある環境のための認証と認可（ACE）のための追加のOAuthパラメーター

Abstract

概要

This specification defines new parameters and encodings for the OAuth 2.0 token and introspection endpoints when used with the framework for Authentication and Authorization for Constrained Environments (ACE). These are used to express the proof-of-possession (PoP) key the client wishes to use, the PoP key that the authorization server has selected, and the PoP key the resource server uses to authenticate to the client.

この仕様は、制約のある環境のための認証と認可（Authentication and Authorization for Constrained Environments、ACE）のフレームワークとともに使用する場合の、OAuth 2.0のトークンエンドポイントとイントロスペクションエンドポイントのための新しいパラメーターとエンコーディングを定義します。これらは、クライアントが使用したい所有証明（proof-of-possession、PoP）鍵、認可サーバーが選択したPoP鍵、およびリソースサーバーがクライアントに対して自身を認証するために使用するPoP鍵を表すために使用されます。

1. Introduction

1. はじめに

The Authentication and Authorization for Constrained Environments (ACE) specification [RFC9200] requires some new parameters for interactions with the OAuth 2.0 [RFC6749] token and introspection endpoints, as well as some new claims to be used in access tokens. These parameters and claims can also be used in other contexts and have therefore been put into a dedicated document to facilitate their use in a manner independent of [RFC9200].

制約のある環境のための認証と認可（ACE）の仕様[RFC9200]では、OAuth 2.0[RFC6749]のトークンエンドポイントおよびイントロスペクションエンドポイントとのやり取りのためのいくつかの新しいパラメーターと、アクセストークンで使用するいくつかの新しいクレームが必要です。これらのパラメーターとクレームは他の文脈でも使用できるため、[RFC9200]とは独立して使用しやすくするために、専用の文書にまとめられています。

Note that although all examples are shown in Concise Binary Object Representation (CBOR) [RFC8949], JSON [RFC8259] MAY be used as an alternative for HTTP-based communications, as specified in [RFC9200].

すべての例は簡潔なバイナリーオブジェクト表現（Concise Binary Object Representation、CBOR）[RFC8949]で示していますが、[RFC9200]で規定されているように、HTTPベースの通信では代わりにJSON[RFC8259]を使用してもよいです（MAY）。

2. Terminology

2. 用語

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

この文書のキーワード「しなければなりません（MUST）」、「してはなりません（MUST NOT）」、 「要求されています（REQUIRED）」、 「することになります（SHALL）」、「することはありません（SHALL NOT）」、 「すべきです（SHOULD）」、「すべきではありません（SHOULD NOT）」、 「推奨されます（RECOMMENDED）」、「推奨されません（NOT RECOMMENDED）」、 「してもよいです（MAY）」、「選択できます（OPTIONAL）」は、 BCP 14 [RFC2119] [RFC8174]に記載されているとおりに解釈されるものとします。 ただし、ここに示すようにすべて大文字で表示される場合に限ります。

Readers are assumed to be familiar with the terminology from [RFC9200], especially the terminology for entities in the architecture such as client (C), resource server (RS), and authorization server (AS).

読者は[RFC9200]の用語、特にクライアント（C）、リソースサーバー（RS）、認可サーバー（AS）など、アーキテクチャー内のエンティティーに関する用語に精通していることを前提とします。

Terminology from [RFC8152] is used in the examples, especially COSE_Key, which is defined in Section 7 of [RFC8152].

例では[RFC8152]の用語、特に[RFC8152]のSection 7で定義されているCOSE_Keyを使用します。

Note that the term "endpoint" is used here following its OAuth 2.0 [RFC6749] definition, which is to denote resources such as token and introspection at the AS and authz-info at the RS. The Constrained Application Protocol (CoAP) [RFC7252] definition, which is "[a]n entity participating in the CoAP protocol", is not used in this specification.

ここでの「エンドポイント（endpoint）」という用語は、OAuth 2.0[RFC6749]の定義にしたがって、ASにおけるtokenやintrospection、RSにおけるauthz-infoなどのリソースを表すために使用していることに注意してください。制約のあるアプリケーションプロトコル（Constrained Application Protocol、CoAP）[RFC7252]における定義、すなわち「CoAPプロトコルに参加するエンティティー（[a]n entity participating in the CoAP protocol）」は、この仕様では使用しません。

3. Parameters for the Token Endpoint

3. トークンエンドポイントのパラメーター

This section defines additional parameters for the interactions with the token endpoint in the ACE framework [RFC9200].

このセクションでは、ACEフレームワーク[RFC9200]におけるトークンエンドポイントとのやり取りのための追加のパラメーターを定義します。

3.1. Client-to-AS Request

3.1. クライアントからASへのリクエスト

This section defines the req_cnf parameter allowing clients to request a specific PoP key in an access token from a token endpoint in the ACE framework [RFC9200]:

このセクションでは、クライアントがACEフレームワーク[RFC9200]のトークンエンドポイントに対して、アクセストークン内の特定のPoP鍵をリクエストできるようにするreq_cnfパラメーターを定義します。

req_cnf
OPTIONAL. This field contains information about the key the client would like to bind to the access token for proof of possession. It is RECOMMENDED that an AS rejects a request containing a symmetric key value in the req_cnf field (kty=Symmetric), since the AS is expected to be able to generate better symmetric keys than a constrained client. (Note: this does not apply to key identifiers referencing a symmetric key.) The AS MUST verify that the client really is in possession of the corresponding key. Profiles of [RFC9200] using this specification MUST define the PoP method used by the AS if they allow clients to use this request parameter. Values of this parameter follow the syntax and semantics of the cnf claim either from Section 3.1 of [RFC8747] for CBOR-based interactions or from Section 3.1 of [RFC7800] for JSON-based interactions.
req_cnf
選択できます（OPTIONAL）。このフィールドには、クライアントが所有証明のためにアクセストークンにバインドしたい鍵に関する情報が含まれます。ASは制約のあるクライアントよりも良い対称鍵を生成できると期待されるため、ASはreq_cnfフィールドに対称鍵の値を含むリクエスト（kty=Symmetric）を拒否することが推奨されます（RECOMMENDED）（注：これは対称鍵を参照する鍵識別子には適用されません）。ASは、クライアントが対応する鍵を実際に所有していることを検証しなければなりません（MUST）。この仕様を使用する[RFC9200]のプロファイルは、クライアントにこのリクエストパラメーターの使用を許可する場合、ASが使用するPoP方法を定義しなければなりません（MUST）。このパラメーターの値は、CBORベースのやり取りでは[RFC8747]のSection 3.1、JSONベースのやり取りでは[RFC7800]のSection 3.1のcnfクレームの構文とセマンティクスにしたがいます。

Figure 1 shows a request for an access token using the req_cnf parameter to request a specific public key as a PoP key. The content is displayed in CBOR diagnostic notation with line breaks for better readability.

Figure 1は、特定の公開鍵をPoP鍵としてリクエストするためにreq_cnfパラメーターを使用した、アクセストークンのリクエストを示しています。内容は、読みやすさのために改行を入れたCBOR診断表記で表示しています。

3.2. AS-to-Client Response

3.2. ASからクライアントへのレスポンス

This section defines the following additional parameters for an AS response to a request to the token endpoint:

このセクションでは、トークンエンドポイントへのリクエストに対するASのレスポンスのための、次の追加パラメーターを定義します。

cnf
REQUIRED if the token type is "pop" and a symmetric key is used. MAY be present for asymmetric PoP keys. This field contains the PoP key that the AS selected for the token. Values of this parameter follow the syntax and semantics of the cnf claim either from Section 3.1 of [RFC8747] for CBOR-based interactions or from Section 3.1 of [RFC7800] for JSON-based interactions. See Section 5 for additional discussion of the usage of this parameter.
rs_cnf
OPTIONAL if the token type is "pop" and asymmetric keys are used. MUST NOT be present otherwise. This field contains information about the public key used by the RS to authenticate. If this parameter is absent, either the RS does not use a public key or the AS knows that the RS can authenticate itself to the client without additional information. Values of this parameter follow the syntax and semantics of the cnf claim either from Section 3.1 of [RFC8747] for CBOR-based interactions or from Section 3.1 of [RFC7800] for JSON-based interactions. See Section 5 for additional discussion of the usage of this parameter.
cnf
トークンタイプが「pop」で、対称鍵を使用する場合は要求されています（REQUIRED）。非対称のPoP鍵の場合は存在してもよいです（MAY）。このフィールドには、ASがトークンのために選択したPoP鍵が含まれます。このパラメーターの値は、CBORベースのやり取りでは[RFC8747]のSection 3.1、JSONベースのやり取りでは[RFC7800]のSection 3.1のcnfクレームの構文とセマンティクスにしたがいます。このパラメーターの使用方法に関する追加の議論については、Section 5を参照してください。
rs_cnf
トークンタイプが「pop」で、非対称鍵を使用する場合は選択できます（OPTIONAL）。それ以外の場合は存在してはなりません（MUST NOT）。このフィールドには、RSが認証に使用する公開鍵に関する情報が含まれます。このパラメーターが存在しない場合、RSが公開鍵を使用しないか、RSが追加の情報なしにクライアントに対して自身を認証できることをASが知っているかのどちらかです。このパラメーターの値は、CBORベースのやり取りでは[RFC8747]のSection 3.1、JSONベースのやり取りでは[RFC7800]のSection 3.1のcnfクレームの構文とセマンティクスにしたがいます。このパラメーターの使用方法に関する追加の議論については、Section 5を参照してください。

Figure 2は、トークンと、対称PoP鍵を持つcnfパラメーターを含むASレスポンスを示しています。

Figure 3 shows an AS response containing a token bound to a previously requested asymmetric PoP key (not shown) and an rs_cnf parameter containing the public key of the RS.

Figure 3は、以前にリクエストされた非対称PoP鍵（図には示していません）にバインドされたトークンと、RSの公開鍵を含むrs_cnfパラメーターを含むASレスポンスを示しています。

4. Parameters for the Introspection Endpoint

4. イントロスペクションエンドポイントのパラメーター

This section defines the use of CBOR instead of JSON for the cnf introspection response parameter specified in Section 9.4 of [RFC8705].

このセクションでは、[RFC8705]のSection 9.4で規定されているcnfイントロスペクションレスポンスパラメーターに、JSONの代わりにCBORを使用することを定義します。

If CBOR is used instead of JSON in an interaction with the introspection endpoint, the AS MUST use the parameter mapping specified in Table 1 and the value must follow the syntax of cnf claim values from Section 3.1 of [RFC8747].

Figure 4は、トークンにバインドされたPoP鍵を示すcnfパラメーターを含む、イントロスペクションリクエストに対するASのレスポンスを示しています。

5. Confirmation Method Parameters

5. 確認方法パラメーター

The confirmation method parameters are used in [RFC9200] as follows:

確認方法パラメーターは、[RFC9200]では次のように使用されます。

  • req_cnf in the access token request C -> AS, OPTIONAL to indicate the client's raw public key or the key identifier of a previously established key between the C and RS that the client wishes to use for proof of possession of the access token.
  • cnf in the token response AS -> C, OPTIONAL if using an asymmetric key or a key that the client requested via a key identifier in the request. REQUIRED if the client didn't specify a req_cnf and symmetric keys are used. Used to indicate the symmetric key generated by the AS for proof of possession of the access token.
  • cnf in the introspection response AS -> RS, REQUIRED if the access token that was subject to introspection is a PoP token, absent otherwise. Indicates the PoP key bound to the access token.
  • rs_cnf in the token response AS -> C, OPTIONAL to indicate the public key of the RS if it uses one to authenticate itself to the client and the binding between the key and RS identity is not established through other means.
  • アクセストークンリクエスト（C -> AS）におけるreq_cnf：クライアントがアクセストークンの所有証明に使用したい鍵として、クライアントの生公開鍵、またはCとRSの間で以前に確立された鍵の鍵識別子を示すために使用します。選択できます（OPTIONAL）。
  • トークンレスポンス（AS -> C）におけるcnf：非対称鍵、またはクライアントがリクエスト内で鍵識別子によってリクエストした鍵を使用する場合は選択できます（OPTIONAL）。クライアントがreq_cnfを指定せず、対称鍵を使用する場合は要求されています（REQUIRED）。アクセストークンの所有証明のためにASが生成した対称鍵を示すために使用します。
  • イントロスペクションレスポンス（AS -> RS）におけるcnf：イントロスペクションの対象となったアクセストークンがPoPトークンである場合は要求されています（REQUIRED）。それ以外の場合は存在しません。アクセストークンにバインドされたPoP鍵を示します。
  • トークンレスポンス（AS -> C）におけるrs_cnf：RSがクライアントに対して自身を認証するために公開鍵を使用し、かつ鍵とRSのアイデンティティーとの結び付きが他の手段で確立されていない場合に、RSの公開鍵を示すために使用します。選択できます（OPTIONAL）。

Note that the COSE_Key structure in a confirmation claim or parameter may contain an alg or key_ops parameter. If such parameters are present, a client MUST NOT use a key that is incompatible with the profile or PoP algorithm according to those parameters. An RS MUST reject a proof of possession using such a key with a response code equivalent to the CoAP code 4.00 (Bad Request).

確認クレームまたは確認パラメーター内のCOSE_Key構造体には、algパラメーターやkey_opsパラメーターが含まれる場合があることに注意してください。そのようなパラメーターが存在する場合、クライアントは、それらのパラメーターにしたがってプロファイルやPoPアルゴリズムと互換性のない鍵を使用してはなりません（MUST NOT）。RSは、そのような鍵を使用した所有証明を、CoAPコード4.00（Bad Request）に相当するレスポンスコードで拒否しなければなりません（MUST）。

If an access token is issued for an audience that includes several RSs, the rs_cnf parameter MUST NOT be used, since the client cannot determine for which RS the key applies. This document recommends to specify a different endpoint that the client can use to acquire RS authentication keys in such cases. The specification of such an endpoint is out of scope for this document.

複数のRSを含むオーディエンスに対してアクセストークンが発行される場合、クライアントはその鍵がどのRSに適用されるのかを判断できないため、rs_cnfパラメーターを使用してはなりません（MUST NOT）。この文書は、そのような場合にクライアントがRSの認証鍵を取得するために使用できる別のエンドポイントを規定することを推奨します。そのようなエンドポイントの仕様は、この文書の範囲外です。

7. Requirements When Using Asymmetric Keys

7. 非対称鍵を使用する場合の要件

An RS using asymmetric keys to authenticate to the client MUST NOT hold several different asymmetric key pairs applicable to the same authentication algorithm. For example, when using DTLS, the RS MUST NOT hold several asymmetric key pairs applicable to the same cipher suite. The reason for this restriction is that the RS has no way of determining which key to use before the client's identity is established. Therefore, authentication attempts by the RS could randomly fail based on which key the RS selects, unless the algorithm negotiation produces a unique choice of key pair for the RS.

クライアントに対する認証に非対称鍵を使用するRSは、同じ認証アルゴリズムに適用可能な複数の異なる非対称鍵ペアを保持してはなりません（MUST NOT）。たとえば、DTLSを使用する場合、RSは同じ暗号スイートに適用可能な複数の非対称鍵ペアを保持してはなりません（MUST NOT）。この制限の理由は、クライアントのアイデンティティーが確立される前には、RSがどの鍵を使用すべきかを判断する方法がないためです。したがって、アルゴリズムのネゴシエーションによってRSの鍵ペアが一意に選択されない限り、RSによる認証の試行は、RSがどの鍵を選択するかによって、ランダムに失敗する可能性があります。
