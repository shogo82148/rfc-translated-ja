RFC 8088

How to Write an RTP Payload Format

RFC 8088

RTPペイロード形式の書き方

Abstract

概要

This document contains information on how best to write an RTP payload format specification. It provides reading tips, design practices, and practical tips on how to produce an RTP payload format specification quickly and with good results. A template is also included with instructions.

この文書は、RTPペイロード形式の仕様を最善の方法で書くための情報を提供します。読むべき文書のヒント、設計上のプラクティス、そしてRTPペイロード形式の仕様を短期間でよい結果とともに作成するための実践的なヒントを提供します。説明つきのテンプレートも含まれています。

1. Introduction

1. はじめに

RTP [RFC3550] payload formats define how a specific real-time data format is structured in the payload of an RTP packet. A real-time data format without a payload format specification cannot be transported using RTP. This creates an interest in many individuals/organizations with media encoders or other types of real-time data to define RTP payload formats. However, the specification of a well-designed RTP payload format is nontrivial and requires knowledge of both RTP and the real-time data format.

RTP[RFC3550]のペイロード形式は、特定のリアルタイムデータ形式をRTPパケットのペイロードの中でどのように構造化するかを定義します。ペイロード形式の仕様がないリアルタイムデータ形式は、RTPを使って転送できません。このため、メディアエンコーダーやその他の種類のリアルタイムデータを持つ多くの個人や組織が、RTPペイロード形式を定義することに関心を持っています。しかし、よく設計されたRTPペイロード形式を規定するのは簡単なことではなく、RTPとリアルタイムデータ形式の両方についての知識が必要です。

This document is intended to help any author of an RTP payload format specification make important design decisions, consider important features of RTP and RTP security, etc. The document is also intended to be a good starting point for any person with little experience in the IETF and/or RTP to learn the necessary steps.

この文書は、RTPペイロード形式の仕様を書くすべての著者が、重要な設計上の判断を下し、RTPやRTPのセキュリティーの重要な機能などを考慮する助けとなることを意図しています。また、IETFやRTPの経験が少ない人が必要な手順を学ぶためのよい出発点となることも意図しています。

This document extends and updates the information that is available in "Guidelines for Writers of RTP Payload Format Specifications" [RFC2736]. Since that RFC was written, further experience has been gained on the design and specification of RTP payload formats. Several new RTP profiles and robustness tools have been defined, and these need to be considered.

この文書は、「Guidelines for Writers of RTP Payload Format Specifications」[RFC2736]で提供されている情報を拡張し、更新します。そのRFCが書かれて以降、RTPペイロード形式の設計と仕様化についてさらに経験が積まれました。新しいRTPプロファイルや堅牢性ツールがいくつも定義されており、それらを考慮する必要があります。

This document also discusses the possible venues for defining an RTP payload format: the IETF, other standards bodies, and proprietary ones.

この文書では、RTPペイロード形式を定義する場として考えられるもの、すなわちIETF、その他の標準化団体、そして独自（プロプライエタリー）のものについても論じます。

Note, this document does discuss IETF, IANA, and RFC Editor processes and rules as they were when this document was published. This to make clear how the work to specify an RTP payload formats depends, uses, and interacts with these rules and processes. However, these rules and processes are subject to change and the formal rule and process specifications always takes precedence over what is written here.

注：この文書は、IETF、IANA、RFCエディターのプロセスと規則を、この文書が発行された時点のものとして論じています。これは、RTPペイロード形式を規定する作業が、これらの規則やプロセスにどのように依存し、それらをどのように利用し、それらとどのように関わるかを明確にするためです。しかし、これらの規則やプロセスは変更されることがあり、ここに書かれた内容よりも、正式な規則やプロセスの仕様が常に優先されます。

1.1. Structure

1.1. 構成

This document has several different parts discussing different aspects of the creation of an RTP payload format specification. Section 3 discusses the preparations the author(s) should make before starting to write a specification. Section 4 discusses the different processes used when specifying and completing a payload format, with focus on working inside the IETF. Section 5 discusses the design of payload formats themselves in detail. Section 6 discusses current design trends and provides good examples of practices that should be followed when applicable. Following that, Section 7 provides a discussion on important sections in the RTP payload format specification itself such as Security Considerations and IANA Considerations. This document ends with an appendix containing a template that can be used when writing RTP payload formats specifications.

この文書は、RTPペイロード形式の仕様を作成する際のさまざまな側面を論じる、いくつかの部分から構成されています。セクション3では、著者が仕様を書き始める前に行うべき準備について論じます。セクション4では、IETFの中での作業に焦点を当てて、ペイロード形式を規定し完成させる際に使われるさまざまなプロセスを論じます。セクション5では、ペイロード形式そのものの設計を詳しく論じます。セクション6では、現在の設計の傾向について論じ、該当する場合に従うべきプラクティスのよい例を示します。続いてセクション7では、「セキュリティーに関する考慮事項」や「IANAに関する考慮事項」など、RTPペイロード形式の仕様そのものの中の重要なセクションについて論じます。この文書の最後には、RTPペイロード形式の仕様を書く際に使えるテンプレートを含む付録があります。

2. Terminology

2. 用語

2.1. Definitions

2.1. 定義

RTP Stream:
A sequence of RTP packets that together carry part or all of the content of a specific media (audio, video, text, or data whose form and meaning are defined by a specific real-time application) from a specific sender source within a given RTP session.
RTP Session:
An association among a set of participants communicating with RTP. The distinguishing feature of an RTP session is that each session maintains a full, separate space of synchronization source (SSRC) identifiers. See also Section 3.3.1.
RTP Payload Format:
The RTP payload format specifies how units of a specific encoded media are put into the RTP packet payloads and how the fields of the RTP packet header are used, thus enabling the format to be used in RTP applications.
RTPストリーム（RTP Stream）：
特定のメディア（音声、映像、テキスト、または特定のリアルタイムアプリケーションによって形式と意味が定義されるデータ）のコンテンツの一部またはすべてを、あるRTPセッション内の特定の送信者ソースから運ぶ一連のRTPパケットです。
RTPセッション（RTP Session）：
RTPを使って通信する参加者の集合の間の関連付けです。RTPセッションを特徴づけるのは、各セッションが同期ソース（SSRC）識別子の完全で独立した空間を保持することです。セクション3.3.1も参照してください。
RTPペイロード形式（RTP Payload Format）：
RTPペイロード形式は、特定の符号化メディアの単位をRTPパケットのペイロードにどのように入れるか、そしてRTPパケットヘッダーのフィールドをどのように使うかを規定します。これにより、その形式をRTPアプリケーションで使えるようになります。

A Taxonomy of Semantics and Mechanisms for Real-Time Transport Protocol (RTP) Sources [RFC7656] defines many useful terms.

「A Taxonomy of Semantics and Mechanisms for Real-Time Transport Protocol (RTP) Sources」[RFC7656]は、多くの有用な用語を定義しています。

3. Preparations

3. 準備

RTP is a complex real-time media delivery framework, and it has a lot of details that need to be considered when writing an RTP payload format. It is also important to have a good understanding of the media codec / format so that all of its important features and properties are considered. Only when one has sufficient understanding of both parts can one produce an RTP payload format of high quality. On top of this, one needs to understand the process within the IETF and especially the Working Group responsible for standardizing payload formats (currently the PAYLOAD WG) to go quickly from the initial idea stage to a finished RFC. This and the next sections help an author prepare himself in those regards.

RTPは複雑なリアルタイムメディア配信のフレームワークであり、RTPペイロード形式を書く際に考慮する必要のある詳細が数多くあります。また、メディアコーデックや形式の重要な特徴や特性をすべて考慮するために、それらをよく理解しておくことも重要です。両方を十分に理解して初めて、品質の高いRTPペイロード形式を作り上げられます。さらに、最初のアイデアの段階から完成したRFCまで素早く進むためには、IETFの中のプロセス、特にペイロード形式の標準化を担当するワーキンググループ（現在はPAYLOAD WG）のプロセスを理解する必要があります。このセクションと次のセクションは、著者がそうした点について準備する助けとなります。

3.1. Read and Understand the Media Coding Specification

3.1. メディア符号化仕様を読んで理解する

It may be obvious, but it is necessary for an author of an RTP payload specification to have a solid understanding of the media to be transported. Important are not only the specifically spelled out transport aspects (if any) in the media coding specification, but also core concepts of the underlying technology. For example, an RTP payload format for video coded with inter-picture prediction will perform poorly if the payload designer does not take the use of inter-picture prediction into account. On the other hand, some (mostly older) media codecs offer error-resilience tools against bit errors, which, when misapplied over RTP, in almost all cases would only introduce overhead with no measurable return.

言うまでもないことかもしれませんが、RTPペイロード仕様の著者は、転送されるメディアについて確かな理解を持っている必要があります。重要なのは、メディア符号化仕様で具体的に記述された転送の側面（もしあれば）だけでなく、その基礎となる技術の中核的な概念でもあります。たとえば、ピクチャー間予測を用いて符号化された映像のRTPペイロード形式は、ペイロードの設計者がピクチャー間予測の使用を考慮に入れなければ、性能が悪くなります。一方、一部の（主に古い）メディアコーデックはビット誤りに対する誤り耐性ツールを備えていますが、それらをRTP上で誤って適用すると、ほとんどの場合、目に見える効果がないままオーバーヘッドを増やすだけです。

3.2. 推奨される文献

The following subsections list a number of documents. Not all need to be read in full detail. However, an author basically needs to be aware of everything listed below.

以下のサブセクションでは、いくつかの文書を挙げます。すべてを細部まで読む必要はありません。しかし、著者は基本的に、以下に挙げたすべてのものを知っておく必要があります。

3.2.1. IETF Process and Publication

3.2.1. IETFのプロセスと発行

Newcomers to the IETF are strongly recommended to read the "Tao of the IETF" [TAO] that goes through most things that one needs to know about the IETF: the history, organizational structure, how the WGs and meetings work, etc.

IETFに新しく参加する人は、「Tao of the IETF」[TAO]を読むことを強く推奨します。これは、IETFについて知っておく必要のあることの大部分、すなわち歴史、組織構造、WGや会合の進め方などを説明しています。

It is very important to note and understand the IETF Intellectual Property Rights (IPR) policy that requires early disclosures based on personal knowledge from anyone contributing in IETF. The IETF policies associated with IPR are documented in BCP 78 [BCP78] (related to copyright, including software copyright, for example, code) and BCP 79 [BCP79] (related to patent rights). These rules may be different from other standardization organizations. For example, a person that has a patent or a patent application that he or she reasonably and personally believes to cover a mechanism that gets added to the Internet-Draft they are contributing to (e.g., by submitting the draft, posting comments or suggestions on a mailing list, or speaking at a meeting) will need to make a timely IPR disclosure. Read the above documents for the authoritative rules. Failure to follow the IPR rules can have dire implications for the specification and the author(s) as discussed in [RFC6701].

IETFの知的財産権（IPR）ポリシーに注意し、理解しておくことは非常に重要です。このポリシーは、IETFに貢献するすべての人に、個人的な知識に基づく早期の開示を求めています。IPRに関するIETFのポリシーは、BCP 78[BCP78]（ソフトウェアの著作権、たとえばコードを含む著作権に関するもの）とBCP 79[BCP79]（特許権に関するもの）に記載されています。これらの規則は、ほかの標準化組織とは異なる場合があります。たとえば、自分が貢献しているインターネットドラフトに（たとえば、ドラフトの提出、メーリングリストへのコメントや提案の投稿、会合での発言によって）追加されたメカニズムが、自分の保有する特許または特許出願の対象になると、本人が合理的かつ個人的に信じている人は、適時にIPRを開示する必要があります。正式な規則については上記の文書を読んでください。[RFC6701]で論じられているように、IPRの規則に従わないと、仕様と著者に深刻な影響が及ぶことがあります。

Note: These IPR rules apply on what is specified in the RTP payload format Internet-Draft (and later RFC); an IPR that relates to a codec specification from an external body does not require IETF IPR disclosure. Informative text explaining the nature of the codec would not normally require an IETF IPR declaration. Appropriate IPR declarations for the codec itself would normally be found in files of the external body defining the codec, in accordance with that external body's own IPR rules.

注：これらのIPRの規則は、RTPペイロード形式のインターネットドラフト（および後のRFC）で規定されている内容に適用されます。外部の団体によるコーデック仕様に関するIPRには、IETFでのIPRの開示は必要ありません。コーデックの性質を説明する参考情報のテキストには、通常、IETFでのIPRの宣言は必要ありません。コーデックそのものに対する適切なIPRの宣言は、通常、そのコーデックを定義する外部の団体の記録の中に、その外部の団体自身のIPR規則に従って見つかります。

The main part of the IETF process is formally defined in BCP 9 [BCP9]. BCP 25 [BCP25] describes the WG process, the relation between the IESG and the WG, and the responsibilities of WG Chairs and participants.

IETFのプロセスの主要な部分は、BCP 9[BCP9]で正式に定義されています。BCP 25[BCP25]は、WGのプロセス、IESGとWGの関係、そしてWG議長と参加者の責任について記述しています。

It is important to note that the RFC Series contains documents of several different publication streams as defined by The RFC Series and RFC Editor [RFC4844]. The most important stream for RTP payload formats authors is the IETF Stream. In this stream, the work of the IETF is published. The stream contains documents of several different categories: Standards Track, Informational, Experimental, Best Current Practice, and Historic. "Standards Track" contains two maturity levels: Proposed Standard and Internet Standard [RFC6410]. A Standards Track document must start as a Proposed Standard; after successful deployment and operational experience with at least two implementations, it can be moved to an Internet Standard. The Independent Submission Stream could appear to be of interest as it provides a way of publishing documents of certain categories such as Experimental and Informational with a different review process. However, as long as IETF has a WG that is chartered to work on RTP payload formats, this stream should not be used.

RFCシリーズには、「The RFC Series and RFC Editor」[RFC4844]で定義されている、いくつかの異なる発行ストリームの文書が含まれていることに注意することが重要です。RTPペイロード形式の著者にとって最も重要なストリームは、IETFストリームです。このストリームでは、IETFの作業成果が発行されます。このストリームには、標準化過程、情報提供、実験的、ベストカレントプラクティス、歴史的という、いくつかの異なるカテゴリーの文書が含まれます。「標準化過程」には、提案標準とインターネット標準という2つの成熟度レベルがあります[RFC6410]。標準化過程の文書は、提案標準として始めなければなりません。少なくとも2つの実装で展開と運用の経験を積んで成功したあとに、インターネット標準に移行できます。独立投稿ストリーム（Independent Submission Stream）は、実験的や情報提供などの特定のカテゴリーの文書を異なるレビュープロセスで発行する方法を提供するので、魅力的に見えるかもしれません。しかし、RTPペイロード形式に取り組むことを憲章に定めたWGがIETFにある限り、このストリームを使うべきではありません。

As the content of a given RFC is not allowed to change once published, the only way to modify an RFC is to write and publish a new one that either updates or replaces the old one. Therefore, whether reading or referencing an RFC, it is important to consider both the Category field in the document header and to check if the RFC is the latest on the subject and still valid. One way of checking the current status of an RFC is to use the RFC Editor's RFC search page (https://www.rfc-editor.org/search), which displays the current status and which if any RFC has updated or obsoleted it. The RFC Editor search engine will also indicate if there exist any errata reports for the RFC. Any verified errata report contains issues of significant importance with the RFC; thus, they should be known prior to an update and replacement publication.

あるRFCの内容は発行後に変更することが許されないので、RFCを修正する唯一の方法は、古いRFCを更新するか置き換える新しいRFCを書いて発行することです。したがって、RFCを読むときも参照するときも、文書のヘッダーのCategoryフィールドを考慮すること、そしてそのRFCがその主題に関して最新であり、まだ有効であるかを確認することの両方が重要です。RFCの現在のステータスを確認する1つの方法は、RFCエディターのRFC検索ページ（https://www.rfc-editor.org/search）を使うことです。このページには、現在のステータスと、もしあればそのRFCを更新または廃止したRFCが表示されます。RFCエディターの検索エンジンは、そのRFCに正誤表の報告があるかどうかも示します。検証済みの正誤表の報告には、そのRFCに関するきわめて重要な問題が含まれています。したがって、更新や置き換えの文書を発行する前に、それらを把握しておくべきです。

Before starting to write a draft, one should also read the Internet-Draft writing guidelines (http://www.ietf.org/ietf/1id-guidelines.txt), the I-D checklist (http://www.ietf.org/ID-Checklist.html), and the RFC Style Guide [RFC7322]. Another document that can be useful is "Guide for Internet Standards Writers" [RFC2360].

ドラフトを書き始める前には、インターネットドラフトの執筆ガイドライン（http://www.ietf.org/ietf/1id-guidelines.txt）、I-Dのチェックリスト（http://www.ietf.org/ID-Checklist.html）、およびRFCスタイルガイド[RFC7322]も読んでおくべきです。役に立つもう1つの文書は、「Guide for Internet Standards Writers」[RFC2360]です。

There are also a number of documents to consider in the process of writing drafts intended to become RFCs. These are important when writing certain types of text.

RFCになることを意図したドラフトを書く過程では、考慮すべき文書がほかにもいくつかあります。これらは、特定の種類のテキストを書く際に重要です。

RFC 2606:
When writing examples using DNS names in Internet-Drafts, those names shall be chosen from the example.com, example.net, and example.org domains.
RFC 3849:
Defines the range of IPv6 unicast addresses (2001:DB8::/32) that should be used in any examples.
RFC 5737:
Defines the ranges of IPv4 unicast addresses reserved for documentation and examples: 192.0.2.0/24, 198.51.100.0/24, and 203.0.113.0/24.
RFC 5234:
Augmented Backus-Naur Form (ABNF) is often used when writing text field specifications. Not commonly used in RTP payload formats, but may be useful when defining media type parameters of some complexity.
RFC 2606:
インターネットドラフトでDNS名を使った例を書く場合、それらの名前はexample.com、example.net、example.orgのドメインから選ぶことになっています。
RFC 3849:
すべての例で使うべきIPv6ユニキャストアドレスの範囲（2001:DB8::/32）を定義しています。
RFC 5737:
文書や例のために予約されたIPv4ユニキャストアドレスの範囲、192.0.2.0/24、198.51.100.0/24、203.0.113.0/24を定義しています。
RFC 5234:
拡張バッカス・ナウア記法（ABNF）は、テキストフィールドの仕様を書く際によく使われます。RTPペイロード形式ではあまり使われませんが、ある程度複雑なメディアタイプのパラメーターを定義する際には役に立つかもしれません。

3.2.2. RTP

3.2.2. RTP

The recommended reading for RTP consists of several different parts: design guidelines, the RTP protocol, profiles, robustness tools, and media-specific recommendations.

RTPについての推奨される文献は、設計ガイドライン、RTPプロトコル、プロファイル、堅牢性ツール、メディア固有の推奨事項という、いくつかの異なる部分から構成されます。

Any author of RTP payload formats should start by reading "Guidelines for Writers of RTP Payload Format Specifications" [RFC2736], which contains an introduction to the Application Level Framing (ALF) principle, the channel characteristics of IP channels, and design guidelines for RTP payload formats. The goal of ALF is to be able to transmit Application Data Units (ADUs) that are independently usable by the receiver in individual RTP packets, thus minimizing dependencies between RTP packets and the effects of packet loss.

RTPペイロード形式のすべての著者は、まず「Guidelines for Writers of RTP Payload Format Specifications」[RFC2736]を読むことから始めるべきです。この文書には、アプリケーションレベルフレーミング（ALF）の原則の紹介、IPチャネルのチャネル特性、そしてRTPペイロード形式の設計ガイドラインが含まれています。ALFの目標は、受信者が独立して使えるアプリケーションデータユニット（ADU）を個々のRTPパケットで送信できるようにし、それによってRTPパケット間の依存関係とパケット損失の影響を最小限に抑えることです。

Then, it is advisable to learn more about the RTP protocol, by studying the RTP specification "RTP: A Transport Protocol for Real-Time Applications" [RFC3550] and the existing profiles. As a complement to the Standards Track documents, there exists a book totally dedicated to RTP [CSP-RTP]. There exist several profiles for RTP today, but all are based on "RTP Profile for Audio and Video Conferences with Minimal Control" [RFC3551] (abbreviated as RTP/AVP). The other profiles that one should know about are "The Secure Real-time Transport Protocol (SRTP)" (RTP/SAVP) [RFC3711], "Extended RTP Profile for RTCP-based Feedback (RTP/AVPF)" [RFC4585], and "Extended Secure Real-time Transport Control Protocol (RTCP)-Based Feedback (RTP/SAVPF)" [RFC5124]. It is important to understand RTP and the RTP/AVP profile in detail. For the other profiles, it is sufficient to have an understanding of what functionality they provide and the limitations they create.

次に、RTPの仕様「RTP: A Transport Protocol for Real-Time Applications」[RFC3550]と既存のプロファイルを学習して、RTPプロトコルについてさらに学ぶことをお勧めします。標準化過程の文書を補うものとして、RTPに完全に特化した書籍もあります[CSP-RTP]。現在、RTPにはいくつかのプロファイルがありますが、すべて「RTP Profile for Audio and Video Conferences with Minimal Control」[RFC3551]（RTP/AVPと略記されます）に基づいています。知っておくべきそのほかのプロファイルは、「The Secure Real-time Transport Protocol (SRTP)」（RTP/SAVP）[RFC3711]、「Extended RTP Profile for RTCP-based Feedback (RTP/AVPF)」[RFC4585]、および「Extended Secure Real-time Transport Control Protocol (RTCP)-Based Feedback (RTP/SAVPF)」[RFC5124]です。RTPとRTP/AVPプロファイルは詳しく理解しておくことが重要です。そのほかのプロファイルについては、それらがどのような機能を提供し、どのような制限を生じさせるかを理解していれば十分です。

A number of robustness tools have been developed for RTP. The tools are for different use cases and real-time requirements.

RTPのために、いくつもの堅牢性ツールが開発されてきました。これらのツールは、それぞれ異なるユースケースとリアルタイム性の要件を対象としています。

RFC 2198:
"RTP Payload for Redundant Audio Data" [RFC2198] provides functionalities to transmit redundant copies of audio or text payloads. These redundant copies are sent together with a primary format in the same RTP payload. This format relies on the RTP timestamp to determine where data belongs in a sequence; therefore, it is usually most suitable to be used with audio. However, the RTP Payload format for T.140 [RFC4103] text format also uses this format. The format's major property is that it only preserves the timestamp of the redundant payloads, not the original sequence number. This makes it unusable for most video formats. This format is also only suitable for media formats that produce relatively small RTP payloads.
RFC 6354:
The "Forward-Shifted RTP Redundancy Payload Support" [RFC6354] is a variant of RFC 2198 that allows the redundant data to be transmitted prior to the original.
RFC 5109:
The "RTP Payload Format for Generic Forward Error Correction" [RFC5109] provides an XOR-based Forward Error Correction (FEC) of the whole or parts of a number of RTP packets. This specification replaced the previous specification for XOR-based FEC [RFC2733]. These FEC packets are sent in a separate stream or as a redundant encoding using RFC 2198. This FEC scheme has certain restrictions in the number of packets it can protect. It is suitable for applications with low-to-medium delay tolerance with a limited amount of RTP packets.
RFC 6015:
"RTP Payload Format for 1-D Interleaved Parity Forward Error Correction (FEC)" [RFC6015] provides a variant of the XOR-based Generic protection defined in [RFC2733]. The main difference is to use interleaving scheme on which packets gets included as source packets for a particular protection packet. The interleaving is defined by using every L packets as source data and then producing protection data over D number of packets. Thus, each block of D x L source packets will result in L number of Repair packets, each capable of repairing one loss. The goal is to provide better burst-error robustness when the packet rate is higher.
FEC Framework:
"Forward Error Correction (FEC) Framework" [RFC6363] defines how to use FEC protection for arbitrary packet flows. This framework can be applied for RTP/RTCP packet flows, including using RTP for transmission of repair symbols, an example is in "RTP Payload Format for Raptor Forward Error Correction (FEC)" [RFC6682].
RTP Retransmission:
The RTP retransmission scheme [RFC4588] is used for semi-reliability of the most important RTP packets in a RTP stream. The level of reliability between semi- and in-practice full reliability depends on the targeted properties and situation where parameters such as round-trip time (RTT) allowed additional overhead and allowable delay. It often requires the application to be quite delay tolerant as a minimum of one round-trip time plus processing delay is required to perform a retransmission. Thus, it is mostly suitable for streaming applications but may also be usable in certain other cases when operating in networks with short round-trip times.
RTP over TCP:
RFC 4571 [RFC4571] defines how one sends RTP and RTCP packets over connection-oriented transports like TCP. If one uses TCP, one gets reliability for all packets but loses some of the real-time behavior that RTP was designed to provide. Issues with TCP transport of real-time media include head-of-line blocking and wasting resources on retransmission of data that is already late. TCP is also limited to point-to-point connections, which further restricts its applicability.
RFC 2198:
「RTP Payload for Redundant Audio Data」[RFC2198]は、音声やテキストのペイロードの冗長なコピーを送信する機能を提供します。これらの冗長なコピーは、主となる形式とともに同じRTPペイロードの中で送信されます。この形式は、データがシーケンスのどこに属するかを判断するのにRTPタイムスタンプに依存しています。そのため、通常は音声で使うのが最も適しています。しかし、T.140テキスト形式のRTPペイロード形式[RFC4103]もこの形式を使います。この形式の主な特性は、冗長なペイロードのタイムスタンプだけを保持し、元のシーケンス番号は保持しないことです。このため、ほとんどの映像形式では使えません。また、この形式は比較的小さなRTPペイロードを生成するメディア形式にしか適していません。
RFC 6354:
「Forward-Shifted RTP Redundancy Payload Support」[RFC6354]は、RFC 2198の変形で、冗長なデータを元のデータより前に送信できるようにします。
RFC 5109:
「RTP Payload Format for Generic Forward Error Correction」[RFC5109]は、いくつかのRTPパケットの全体または一部に対する、XORに基づく前方誤り訂正（FEC）を提供します。この仕様は、XORに基づくFECの以前の仕様[RFC2733]を置き換えました。これらのFECパケットは、別のストリームで、またはRFC 2198を使った冗長符号化として送信されます。このFEC方式には、保護できるパケットの数に一定の制限があります。この方式は、遅延の許容度が低から中程度で、RTPパケットの量が限られているアプリケーションに適しています。
RFC 6015:
「RTP Payload Format for 1-D Interleaved Parity Forward Error Correction (FEC)」[RFC6015]は、[RFC2733]で定義されたXORに基づく汎用的な保護の変形を提供します。主な違いは、どのパケットが特定の保護パケットのソースパケットとして含まれるかについてインターリーブ方式を使うことです。インターリーブは、L個おきのパケットをソースデータとして使い、D個のパケットにわたって保護データを生成することで定義されます。したがって、D x L個のソースパケットの各ブロックからはL個の修復パケットが生じ、それぞれが1つの損失を修復できます。目標は、パケットレートが高い場合にバースト誤りに対する堅牢性を高めることです。
FECフレームワーク：
「Forward Error Correction (FEC) Framework」[RFC6363]は、任意のパケットフローに対してFECによる保護を使う方法を定義しています。このフレームワークは、修復シンボルの送信にRTPを使う場合も含めて、RTP/RTCPのパケットフローに適用できます。その例が「RTP Payload Format for Raptor Forward Error Correction (FEC)」[RFC6682]にあります。
RTP再送：
RTP再送方式[RFC4588]は、RTPストリームの中で最も重要なRTPパケットに半信頼性を与えるために使われます。半信頼性から実質的に完全な信頼性までのうちどの程度の信頼性になるかは、対象とする特性と、往復時間（RTT）、許容される追加のオーバーヘッド、許容される遅延などのパラメーターがどのような状況にあるかによって決まります。再送を行うには最低でも1往復時間と処理遅延が必要なので、多くの場合、アプリケーションにはかなりの遅延耐性が求められます。したがって、主にストリーミングアプリケーションに適していますが、往復時間が短いネットワークで動作する場合など、ほかの特定のケースでも使える場合があります。
TCP上のRTP：
RFC 4571[RFC4571]は、TCPのようなコネクション指向のトランスポート上でRTPとRTCPのパケットを送る方法を定義しています。TCPを使うと、すべてのパケットについて信頼性が得られますが、RTPが提供するように設計されたリアルタイムの振る舞いの一部が失われます。リアルタイムメディアをTCPで転送する場合の問題には、ヘッドオブラインブロッキングや、すでに遅れたデータの再送にリソースを浪費することなどがあります。また、TCPはポイントツーポイントのコネクションに限られるので、その適用範囲がさらに制限されます。

There have been both discussion and design of RTP payload formats, e.g., Adaptive Multi-Rate (AMR) and AMR Wideband (AMR-WB) [RFC4867], supporting the unequal error detection provided by UDP-Lite [RFC3828]. The idea is that by not having a checksum over part of the RTP payload one can allow bit errors from the lower layers. By allowing bit errors one can increase the efficiency of some link layers and also avoid unnecessary discarding of data when the payload and media codec can get at least some benefit from the data. The main issue is that one has no idea of the level of bit errors present in the unprotected part of the payload. This makes it hard or impossible to determine whether or not one can design something usable. Payload format designers are not recommended to consider features for unequal error detection using UDP-Lite unless very clear requirements exist.

UDP-Lite[RFC3828]が提供する不均等な誤り検出をサポートするRTPペイロード形式について、議論と設計の両方が行われてきました。たとえば、Adaptive Multi-Rate（AMR）やAMR Wideband（AMR-WB）[RFC4867]です。その考え方は、RTPペイロードの一部にチェックサムを付けないことで、下位層からのビット誤りを許容できるようにするというものです。ビット誤りを許容することで、一部のリンク層の効率を高められ、またペイロードとメディアコーデックがデータから少なくとも何らかの利益を得られる場合に、データの不必要な破棄を避けられます。主な問題は、ペイロードの保護されていない部分にどの程度のビット誤りがあるのかまったくわからないことです。このため、使えるものを設計できるかどうかを判断するのが難しいか、不可能になります。非常に明確な要件がない限り、ペイロード形式の設計者がUDP-Liteを使った不均等な誤り検出の機能を検討することは推奨されません。

There also exist some management and monitoring extensions.

管理と監視の拡張もいくつかあります。

RFC 2959:
The RTP protocol Management Information Database (MIB) [RFC2959] that is used with SNMP [RFC3410] to configure and retrieve information about RTP sessions.
RFC 3611:
The RTCP Extended Reports (RTCP XR) [RFC3611] consists of a framework for reports sent within RTCP. It can easily be extended by defining new report formats, which has and is occurring. The XRBLOCK WG in the IETF is chartered (at the time of writing) with defining new report formats. The list of specified formats is available in IANA's RTCP XR Block Type registry (http://www.iana.org/assignments/rtcp-xr-block-types/). The report formats that are defined in RFC 3611 provide report information on packet loss, packet duplication, packet reception times, RTCP statistics summary, and VoIP Quality. [RFC3611] also defines a mechanism that allows receivers to calculate the RTT to other session participants when used.
RMONMIB:
The Remote Network Monitoring WG has defined a mechanism [RFC3577] based on usage of the MIB that can be an alternative to RTCP XR.
RFC 2959:
RTPプロトコルの管理情報データベース（MIB）[RFC2959]です。SNMP[RFC3410]とともに使われ、RTPセッションの設定や、RTPセッションに関する情報の取得を行います。
RFC 3611:
RTCP拡張レポート（RTCP XR）[RFC3611]は、RTCPの中で送信されるレポートのフレームワークです。新しいレポート形式を定義することで容易に拡張でき、実際にそうした拡張が行われてきており、現在も行われています。IETFのXRBLOCK WGは、（執筆時点で）新しいレポート形式を定義することを憲章としています。規定済みの形式の一覧は、IANAのRTCP XR Block Typeレジストリー（http://www.iana.org/assignments/rtcp-xr-block-types/）で入手できます。RFC 3611で定義されているレポート形式は、パケット損失、パケットの重複、パケットの受信時刻、RTCP統計の要約、およびVoIPの品質に関するレポート情報を提供します。また、[RFC3611]は、使用された場合に、受信者がほかのセッション参加者へのRTTを計算できるようにするメカニズムも定義しています。
RMONMIB:
Remote Network Monitoring WGは、MIBの使用に基づくメカニズム[RFC3577]を定義しており、これはRTCP XRの代わりとなり得ます。

A number of transport optimizations have also been developed for use in certain environments. They are all intended to be transparent and do not require special consideration by the RTP payload format writer. Thus, they are primarily listed here for informational reasons.

特定の環境で使うために、トランスポートの最適化もいくつか開発されています。これらはすべて透過的であることを意図しており、RTPペイロード形式の著者が特別に考慮する必要はありません。したがって、ここでは主に情報提供のために挙げています。

RFC 2508:
"Compressing IP/UDP/RTP Headers for Low-Speed Serial Links" (CRTP) [RFC2508] is the first IETF-developed RTP header compression mechanism. It provides quite good compression; however, it has clear performance problems when subject to packet loss or reordering between compressor and decompressor.
RFCs 3095 and 5795:
These are the base specifications of the robust header compression (ROHC) protocol version 1 [RFC3095] and version 2 [RFC5795]. This solution was created as a result of CRTP's lack of performance when compressed packets are subject to loss.
RFC 3545:
Enhanced compressed RTP (E-CRTP) [RFC3545] was developed to provide extensions to CRTP that allow for better performance over links with long RTTs, packet loss, and/or reordering.
RFC 4170:
"Tunneling Multiplexed Compressed RTP (TCRTP)" [RFC4170] is a solution that allows header compression within a tunnel carrying multiple multiplexed RTP flows. This is primarily used in voice trunking.
RFC 2508:
「Compressing IP/UDP/RTP Headers for Low-Speed Serial Links」（CRTP）[RFC2508]は、IETFが開発した最初のRTPヘッダー圧縮メカニズムです。かなりよい圧縮を提供しますが、圧縮器と伸張器の間でパケット損失や並べ替えが起こると、明らかな性能上の問題があります。
RFC 3095と5795：
これらは、ロバストヘッダー圧縮（ROHC）プロトコルのバージョン1[RFC3095]とバージョン2[RFC5795]の基本仕様です。この解決策は、圧縮されたパケットが損失を受けた場合のCRTPの性能不足を受けて作られました。
RFC 3545:
Enhanced compressed RTP（E-CRTP）[RFC3545]は、RTTが長いリンク、パケット損失、並べ替えのいずれか、またはそれらの組み合わせがある場合に、より高い性能を得られるようにするCRTPの拡張を提供するために開発されました。
RFC 4170:
「Tunneling Multiplexed Compressed RTP (TCRTP)」[RFC4170]は、多重化された複数のRTPフローを運ぶトンネル内でのヘッダー圧縮を可能にする解決策です。これは主に音声のトランキングで使われます。

There exist a couple of different security mechanisms that may be used with RTP. By definition, generic mechanisms are transparent for the RTP payload format and do not need special consideration by the format designer. The main reason that different solutions exist is that different applications have different requirements; thus, different solutions have been developed. For more discussion on this, please see "Options for Securing RTP Sessions" [RFC7201] and "Securing the RTP Framework: Why RTP Does Not Mandate a Single Media Security Solution" [RFC7202]. The main properties for an RTP security mechanism are to provide confidentiality for the RTP payload, integrity protection to detect manipulation of payload and headers, and source authentication. Not all mechanisms provide all of these features, a point that will need to be considered when a specific mechanisms is chosen.

RTPとともに使えるセキュリティーメカニズムはいくつかあります。定義上、汎用的なメカニズムはRTPペイロード形式に対して透過的であり、形式の設計者が特別に考慮する必要はありません。異なる解決策が存在する主な理由は、アプリケーションごとに要件が異なるため、異なる解決策が開発されてきたことです。これについてのさらなる議論は、「Options for Securing RTP Sessions」[RFC7201]と「Securing the RTP Framework: Why RTP Does Not Mandate a Single Media Security Solution」[RFC7202]を参照してください。RTPのセキュリティーメカニズムの主な特性は、RTPペイロードの機密性、ペイロードとヘッダーの改ざんを検出するための完全性保護、そしてソース認証を提供することです。すべてのメカニズムがこれらの機能をすべて提供するわけではなく、この点は特定のメカニズムを選ぶ際に考慮する必要があります。

The profile for Secure RTP - SRTP (RTP/SAVP) [RFC3711] and the derived profile (RTP/SAVPF [RFC5124]) are a solution that enables confidentiality, integrity protection, replay protection, and partial source authentication. It is the solution most commonly used with RTP at the time of writing this document. There exist several key-management solutions for SRTP, as well other choices, affecting the security properties. For a more in-depth review of the options and solutions other than SRTP consult "Options for Securing RTP Sessions" [RFC7201].

Secure RTPのプロファイルであるSRTP（RTP/SAVP）[RFC3711]とその派生プロファイル（RTP/SAVPF[RFC5124]）は、機密性、完全性保護、リプレイ保護、部分的なソース認証を可能にする解決策です。この文書の執筆時点では、RTPとともに最もよく使われている解決策です。SRTPにはいくつかの鍵管理の解決策があり、ほかにも選択肢があって、それらはセキュリティー特性に影響します。SRTP以外の選択肢と解決策についてのより詳しいレビューは、「Options for Securing RTP Sessions」[RFC7201]を参照してください。

3.3. Important RTP Details

3.3. RTPの重要な詳細

This section reviews a number of RTP features and concepts that are available in RTP, independent of the payload format. The RTP payload format can make use of these when appropriate, and even affect the behavior (RTP timestamp and marker bit), but it is important to note that not all features and concepts are relevant to every payload format. This section does not remove the necessity to read up on RTP. However, it does point out a few important details to remember when designing a payload format.

このセクションでは、ペイロード形式とは無関係にRTPで利用できる、RTPのいくつかの機能と概念を概説します。RTPペイロード形式は、適切な場合にはこれらを利用でき、その振る舞い（RTPタイムスタンプとマーカービット）に影響を与えることさえできますが、すべての機能と概念がすべてのペイロード形式に関係するわけではないことに注意することが重要です。このセクションを読んでも、RTPについて学ぶ必要がなくなるわけではありません。しかし、ペイロード形式を設計する際に覚えておくべき、いくつかの重要な詳細を指摘します。

3.3.1. The RTP Session

3.3.1. RTPセッション

The definition of the RTP session from RFC 3550 is:

RFC 3550によるRTPセッションの定義は次のとおりです。

An association among a set of participants communicating with RTP. A participant may be involved in multiple RTP sessions at the same time. In a multimedia session, each medium is typically carried in a separate RTP session with its own RTCP packets unless the encoding itself multiplexes multiple media into a single data stream. A participant distinguishes multiple RTP sessions by reception of different sessions using different pairs of destination transport addresses, where a pair of transport addresses comprises one network address plus a pair of ports for RTP and RTCP. All participants in an RTP session may share a common destination transport address pair, as in the case of IP multicast, or the pairs may be different for each participant, as in the case of individual unicast network addresses and port pairs. In the unicast case, a participant may receive from all other participants in the session using the same pair of ports, or may use a distinct pair of ports for each.

The distinguishing feature of an RTP session is that each session maintains a full, separate space of SSRC identifiers (defined next). The set of participants included in one RTP session consists of those that can receive an SSRC identifier transmitted by any one of the participants either in RTP as the SSRC or a CSRC (also defined below) or in RTCP. For example, consider a three-party conference implemented using unicast UDP with each participant receiving from the other two on separate port pairs. If each participant sends RTCP feedback about data received from one other participant only back to that participant, then the conference is composed of three separate point-to-point RTP sessions. If each participant provides RTCP feedback about its reception of one other participant to both of the other participants, then the conference is composed of one multi-party RTP session. The latter case simulates the behavior that would occur with IP multicast communication among the three participants.

The RTP framework allows the variations defined here, but a particular control protocol or application design will usually impose constraints on these variations.

RTPを使って通信する参加者の集合の間の関連付けです。参加者は、同時に複数のRTPセッションに関与することがあります。マルチメディアセッションでは、符号化そのものが複数のメディアを単一のデータストリームに多重化しない限り、通常、各メディアはそれぞれ独自のRTCPパケットを持つ別々のRTPセッションで運ばれます。参加者は、異なるセッションを異なる宛先トランスポートアドレスの組で受信することによって、複数のRTPセッションを区別します。ここで、トランスポートアドレスの組は、1つのネットワークアドレスと、RTP用とRTCP用のポートの組から構成されます。IPマルチキャストの場合のように、RTPセッションのすべての参加者が共通の宛先トランスポートアドレスの組を共有することもあれば、個々のユニキャストのネットワークアドレスとポートの組の場合のように、参加者ごとに組が異なることもあります。ユニキャストの場合、参加者は、セッション内のほかのすべての参加者から同じポートの組を使って受信することも、参加者ごとに別のポートの組を使うこともあります。

RTPセッションを特徴づけるのは、各セッションがSSRC識別子（次に定義します）の完全で独立した空間を保持することです。1つのRTPセッションに含まれる参加者の集合は、参加者のいずれか1人がRTPの中でSSRCまたはCSRC（これも以下で定義します）として、あるいはRTCPの中で送信したSSRC識別子を受信できる参加者から構成されます。たとえば、ユニキャストUDPを使って実装された3者会議で、各参加者がほかの2人からそれぞれ別のポートの組で受信する場合を考えます。各参加者が、ほかの1人の参加者から受信したデータについてのRTCPフィードバックをその参加者だけに送り返す場合、その会議は3つの別々のポイントツーポイントRTPセッションから構成されます。各参加者が、ほかの1人の参加者からの受信に関するRTCPフィードバックをほかの2人の参加者の両方に提供する場合、その会議は1つの多者間RTPセッションから構成されます。後者の場合は、3人の参加者の間でIPマルチキャスト通信を行った場合に起こる振る舞いを模倣したものです。

RTPフレームワークでは、ここで定義したさまざまな形態が許されますが、通常は、特定の制御プロトコルやアプリケーションの設計によって、これらの形態に制約が課されます。

3.3.2. RTP Header

3.3.2. RTPヘッダー

The RTP header contains a number of fields. Two fields always require additional specification by the RTP payload format, namely the RTP timestamp and the marker bit. Certain RTP payload formats also use the RTP sequence number to realize certain functionalities, primarily related to the order of their application data units. The payload type is used to indicate the used payload format. The SSRC is used to distinguish RTP packets from multiple senders and media sources identifying the RTP stream. Finally, [RFC5285] specifies how to transport payload format independent metadata relating to the RTP packet or stream.

RTPヘッダーには、いくつかのフィールドがあります。そのうち2つのフィールド、すなわちRTPタイムスタンプとマーカービットについては、RTPペイロード形式で常に追加の規定が必要です。一部のRTPペイロード形式は、主にアプリケーションデータユニットの順序に関連する特定の機能を実現するために、RTPシーケンス番号も使います。ペイロードタイプは、使用しているペイロード形式を示すために使われます。SSRCは、複数の送信者やメディアソースからのRTPパケットを区別するために使われ、RTPストリームを識別します。最後に、[RFC5285]は、RTPパケットやストリームに関連する、ペイロード形式に依存しないメタデータを転送する方法を規定しています。

Marker Bit:
A single bit normally used to provide important indications. In audio, it is normally used to indicate the start of a talk burst. This enables jitter buffer adaptation prior to the beginning of the burst with minimal audio quality impact. In video, the marker bit is normally used to indicate the last packet part of a frame. This enables a decoder to finish decoding the picture, where it otherwise may need to wait for the next packet to explicitly know that the frame is finished.
Timestamp:

The RTP timestamp indicates the time instance the media sample belongs to. For discrete media like video, it normally indicates when the media (frame) was sampled. For continuous media, it normally indicates the first time instance the media present in the payload represents. For audio, this is the sampling time of the first sample. All RTP payload formats must specify the meaning of the timestamp value and the clock rates allowed. Selecting a timestamp rate is an active design choice and is further discussed in Section 5.2.

Discontinuous Transmission (DTX) that is common among speech codecs, typically results in gaps or jumps in the timestamp values due to that there is no media payload to transmit and the next used timestamp value represent the actual sampling time of the data transmitted.

Sequence Number:
The sequence number is monotonically increasing and is set as the packet is sent. This property is used in many payload formats to recover the order of everything from the whole stream down to fragments of application data units (ADUs) and the order they need to be decoded. Discontinuous transmissions do not result in gaps in the sequence number, as it is monotonically increasing for each sent RTP packet.
Payload Type:
The payload type is used to indicate, on a per-packet basis, which format is used. The binding between a payload type number and a payload format and its configuration are dynamically bound and RTP session specific. The configuration information can be bound to a payload type value by out-of-band signaling (Section 3.4). An example of this would be video decoder configuration information. Commonly, the same payload type is used for a media stream for the whole duration of a session. However, in some cases it may be necessary to change the payload format or its configuration during the session.
SSRC:
The synchronization source (SSRC) identifier is normally not used by a payload format other than to identify the RTP timestamp and sequence number space a packet belongs to, allowing simultaneously reception of multiple media sources. However, some of the RTP mechanisms for improving resilience to packet loss uses multiple SSRCs to separate original data and repair or redundant data, as well as multi-stream transmission of scalable codecs.
Header Extensions:
RTP payload formats often need to include metadata relating to the payload data being transported. Such metadata is sent as a payload header, at the start of the payload section of the RTP packet. The RTP packet also includes space for a header extension [RFC5285]; this can be used to transport payload format independent metadata, for example, an SMPTE time code for the packet [RFC5484]. The RTP header extensions are not intended to carry headers that relate to a particular payload format, and must not contain information needed in order to decode the payload.
マーカービット：
通常、重要な指示を提供するために使われる1ビットです。音声では、通常、トークバーストの開始を示すために使われます。これにより、音声品質への影響を最小限に抑えつつ、バーストが始まる前にジッターバッファーを調整できます。映像では、マーカービットは通常、フレームの最後のパケットであることを示すために使われます。これにより、デコーダーはピクチャーのデコードを完了できます。そうでなければ、フレームが終わったことを明示的に知るために、次のパケットを待つ必要があるかもしれません。
タイムスタンプ：

RTPタイムスタンプは、メディアのサンプルが属する時刻を示します。映像のような離散的なメディアでは、通常、メディア（フレーム）がサンプリングされた時刻を示します。連続的なメディアでは、通常、ペイロードの中にあるメディアが表す最初の時刻を示します。音声の場合、これは最初のサンプルのサンプリング時刻です。すべてのRTPペイロード形式は、タイムスタンプの値の意味と、許可されるクロックレートを規定しなければなりません。タイムスタンプレートの選択は積極的に行うべき設計上の選択であり、セクション5.2でさらに論じます。

音声コーデックで一般的な不連続送信（DTX）では、送信するメディアペイロードがないため、通常、タイムスタンプの値に隙間や飛びが生じます。次に使われるタイムスタンプの値は、送信されるデータの実際のサンプリング時刻を表します。

シーケンス番号：
シーケンス番号は単調に増加し、パケットの送信時に設定されます。この特性は、多くのペイロード形式で、ストリーム全体からアプリケーションデータユニット（ADU）の断片に至るまであらゆるものの順序と、それらをデコードする必要がある順序を復元するために使われます。シーケンス番号は送信されるRTPパケットごとに単調に増加するので、不連続送信によってシーケンス番号に隙間が生じることはありません。
ペイロードタイプ：
ペイロードタイプは、どの形式が使われているかをパケットごとに示すために使われます。ペイロードタイプ番号と、ペイロード形式およびその設定との対応付けは、動的に結び付けられ、RTPセッションに固有です。設定情報は、帯域外シグナリング（セクション3.4）によってペイロードタイプの値に結び付けることができます。その例として、映像デコーダーの設定情報があります。一般に、セッションの期間全体を通じて、メディアストリームには同じペイロードタイプが使われます。しかし、場合によっては、セッションの途中でペイロード形式やその設定を変更する必要があるかもしれません。
SSRC：
同期ソース（SSRC）識別子は、通常、パケットが属するRTPタイムスタンプとシーケンス番号の空間を識別して、複数のメディアソースを同時に受信できるようにすること以外には、ペイロード形式で使われません。しかし、パケット損失に対する耐性を高めるためのRTPのメカニズムの中には、元のデータと修復用または冗長のデータを分けるため、またスケーラブルなコーデックのマルチストリーム送信のために、複数のSSRCを使うものもあります。
ヘッダー拡張：
RTPペイロード形式では、転送されるペイロードデータに関連するメタデータを含める必要がよくあります。そのようなメタデータは、RTPパケットのペイロード部分の先頭に、ペイロードヘッダーとして送信されます。RTPパケットには、ヘッダー拡張[RFC5285]のための領域もあります。これは、ペイロード形式に依存しないメタデータ、たとえばパケットのSMPTEタイムコード[RFC5484]を転送するために使えます。RTPヘッダー拡張は、特定のペイロード形式に関連するヘッダーを運ぶことは意図されておらず、ペイロードをデコードするのに必要な情報を含めてはいけません。

The remaining fields do not commonly influence the RTP payload format. The padding bit is worth clarifying as it indicates that one or more bytes are appended after the RTP payload. This padding must be removed by a receiver before payload format processing can occur. Thus, it is completely separate from any padding that may occur within the payload format itself.

残りのフィールドは、一般にRTPペイロード形式には影響しません。パディングビットについては、RTPペイロードのあとに1バイト以上が付加されていることを示すので、説明しておく価値があります。このパディングは、ペイロード形式の処理を行う前に受信者が取り除かなければなりません。したがって、ペイロード形式そのものの中で行われるかもしれないパディングとは、まったく別のものです。

3.3.3. RTP Multiplexing

3.3.3. RTPの多重化

RTP has three multiplexing points that are used for different purposes. A proper understanding of this is important to correctly use them.

RTPには、さまざまな目的で使われる3つの多重化ポイントがあります。これらを正しく使うには、適切に理解することが重要です。

The first one is separation of RTP streams of different types or usages, which is accomplished using different RTP sessions. So, for example, in the common multimedia session with audio and video, RTP commonly multiplexes audio and video in different RTP sessions. To achieve this separation, transport-level functionalities are used, normally UDP port numbers. Different RTP sessions can also be used to realize layered scalability as it allows a receiver to select one or more layers for multicast RTP sessions simply by joining the multicast groups over which the desired layers are transported. This separation also allows different Quality of Service (QoS) to be applied to different media types. Use of multiple transport flows has potential issues due to NAT and firewall traversal. The choices how one applies RTP sessions as well as transport flows can affect the transport properties an RTP media stream experiences.

1つ目は、種類や用途の異なるRTPストリームの分離で、これは異なるRTPセッションを使って実現されます。たとえば、音声と映像を含む一般的なマルチメディアセッションでは、RTPは通常、音声と映像を異なるRTPセッションに多重化します。この分離を実現するために、トランスポートレベルの機能、通常はUDPのポート番号が使われます。異なるRTPセッションは、階層的なスケーラビリティーを実現するためにも使えます。これにより、受信者は、目的のレイヤーが転送されているマルチキャストグループに参加するだけで、マルチキャストRTPセッションの1つ以上のレイヤーを選択できます。また、この分離によって、メディアタイプごとに異なるサービス品質（QoS）を適用できます。複数のトランスポートフローを使うと、NATやファイアウォールの通過に関して問題が生じる可能性があります。RTPセッションやトランスポートフローをどのように適用するかの選択は、RTPメディアストリームが受けるトランスポートの特性に影響を与えることがあります。

The next multiplexing point is separation of different RTP streams within an RTP session. Here, RTP uses the SSRC to identify individual sources of RTP streams. An example of individual media sources would be the capture of different microphones that are carried in an RTP session for audio, independently of whether they are connected to the same host or different hosts. There also exist cases where a single media source, is transmitted using multiple RTP streams. For each SSRC, a unique RTP sequence number and timestamp space is used.

次の多重化ポイントは、RTPセッション内での異なるRTPストリームの分離です。ここでは、RTPはSSRCを使ってRTPストリームの個々のソースを識別します。個々のメディアソースの例としては、音声用のRTPセッションで運ばれる、異なるマイクロフォンからの取り込みがあります。それらのマイクロフォンが同じホストに接続されているか、異なるホストに接続されているかには関係ありません。単一のメディアソースが、複数のRTPストリームを使って送信される場合もあります。SSRCごとに、一意のRTPシーケンス番号とタイムスタンプの空間が使われます。

The third multiplexing point is the RTP header payload type field. The payload type identifies what format the content in the RTP payload has. This includes different payload format configurations, different codecs, and also usage of robustness mechanisms like the one described in RFC 2198 [RFC2198].

3つ目の多重化ポイントは、RTPヘッダーのペイロードタイプフィールドです。ペイロードタイプは、RTPペイロードの中のコンテンツがどのような形式であるかを識別します。これには、異なるペイロード形式の設定、異なるコーデック、そしてRFC 2198[RFC2198]で説明されているような堅牢性メカニズムの使用も含まれます。

3.3.4. RTP Synchronization

3.3.4. RTPの同期

There are several types of synchronization, and we will here describe how RTP handles the different types:

同期にはいくつかの種類があります。ここでは、RTPがそれぞれの種類をどのように扱うかを説明します。

Intra media:
The synchronization within a media stream from a synchronization source (SSRC) is accomplished using the RTP timestamp field. Each RTP packet carries the RTP timestamp, which specifies the position in time of the media payload contained in this packet relative to the content of other RTP packets in the same RTP stream (i.e., a given SSRC). This is especially useful in cases of discontinuous transmissions. Discontinuities can be caused by network conditions; when extensive losses occur the RTP timestamp tells the receiver how much later than previously received media the present media should be played out.
Inter-media:
Applications commonly have a desire to use several media sources, possibly of different media types, at the same time. Thus, there exists a need to synchronize different media from the same endpoint. This puts two requirements on RTP: the possibility to determine which media are from the same endpoint and if they should be synchronized with each other and the functionality to facilitate the synchronization itself.
メディア内（Intra media）：
同期ソース（SSRC）からのメディアストリーム内の同期は、RTPタイムスタンプフィールドを使って実現されます。各RTPパケットはRTPタイムスタンプを運びます。これは、同じRTPストリーム（すなわち、あるSSRC）のほかのRTPパケットのコンテンツに対する、このパケットに含まれるメディアペイロードの時間的な位置を規定します。これは、不連続な送信の場合に特に役立ちます。不連続は、ネットワークの状態によって生じることがあります。大規模な損失が起こった場合、RTPタイムスタンプは、以前に受信したメディアよりもどれだけ遅れて現在のメディアを再生すべきかを受信者に伝えます。
メディア間（Inter-media）：
アプリケーションでは、場合によっては異なるメディアタイプの複数のメディアソースを同時に使いたいという要望がよくあります。そのため、同じエンドポイントからの異なるメディアを同期させる必要があります。これにより、RTPには2つの要件が課されます。1つは、どのメディアが同じエンドポイントからのものであり、それらを互いに同期させるべきかどうかを判断できること、もう1つは、同期そのものを容易にする機能です。

The first step in inter-media synchronization is to determine which SSRCs in each session should be synchronized with each other. This is accomplished by comparing the CNAME fields in the RTCP source description (SDES) packets. SSRCs with the same CNAME sent in any of multiple RTP sessions can be synchronized.

メディア間同期の最初のステップは、各セッションのどのSSRCを互いに同期させるべきかを判断することです。これは、RTCPのソース記述（SDES）パケットのCNAMEフィールドを比較することで行われます。複数のRTPセッションのいずれかで送信された、同じCNAMEを持つSSRCどうしを同期させることができます。

The actual RTCP mechanism for inter-media synchronization is based on the idea that each RTP stream provides a position on the media specific time line (measured in RTP timestamp ticks) and a common reference time line. The common reference time line is expressed in RTCP as a wall-clock time in the Network Time Protocol (NTP) format. It is important to notice that the wall-clock time is not required to be synchronized between hosts, for example, by using NTP [RFC5905]. It can even have nothing at all to do with the actual time; for example, the host system's up-time can be used for this purpose. The important factor is that all media streams from a particular source that are being synchronized use the same reference clock to derive their relative RTP timestamp time scales. The type of reference clock and its timebase can be signaled using RTP Clock Source Signaling [RFC7273].

メディア間同期のための実際のRTCPのメカニズムは、各RTPストリームが、メディア固有のタイムライン（RTPタイムスタンプのティックで測られます）上の位置と、共通の基準タイムライン上の位置を提供するという考え方に基づいています。共通の基準タイムラインは、RTCPではネットワークタイムプロトコル（NTP）形式のウォールクロック時刻として表現されます。ウォールクロック時刻は、たとえばNTP[RFC5905]を使うなどしてホスト間で同期されている必要はないことに注意することが重要です。実際の時刻とはまったく無関係であってもかまいません。たとえば、ホストシステムの稼働時間をこの目的に使うこともできます。重要なのは、同期させる特定のソースからのすべてのメディアストリームが、それぞれの相対的なRTPタイムスタンプの時間尺度を導くのに同じ基準クロックを使うことです。基準クロックの種類とそのタイムベースは、RTP Clock Source Signaling[RFC7273]を使ってシグナリングできます。

Figure 1 illustrates how if one receives RTCP Sender Report (SR) packet P1 for one RTP stream and RTCP SR packet P2 for the other RTP stream, then one can calculate the corresponding RTP timestamp values for any arbitrary point in time T. However, to be able to do that, it is also required to know the RTP timestamp rates for each RTP stream currently used in the sessions.

図1は、あるRTPストリームについてRTCP送信者レポート（SR）パケットP1を受信し、もう一方のRTPストリームについてRTCP SRパケットP2を受信すれば、任意の時点Tに対応するRTPタイムスタンプの値を計算できることを示しています。ただし、それを行うには、セッションで現在使われている各RTPストリームのRTPタイムスタンプレートを知っている必要もあります。

Assume that medium 1 uses an RTP timestamp clock rate of 16 kHz, and medium 2 uses a clock rate of 90 kHz. Then, TS1 and TS2 for point T can be calculated in the following way: TS1(T) = TS1(P1) + 16000 * (NTP(T)-NTP(P1)) and TS2(T) = TS2(P2) + 90000 * (NTP(T)-NTP(P2)). This calculation is useful as it allows the implementation to generate a common synchronization point for which all time values are provided (TS1(T), TS2(T) and T). So, when one wishes to calculate the NTP time that the timestamp value present in packet X corresponds to, one can do that in the following way: NTP(X) = NTP(T) + (TS2(X) - TS2(T))/90000.

メディア1が16kHzのRTPタイムスタンプのクロックレートを使い、メディア2が90kHzのクロックレートを使うと仮定します。すると、時点TにおけるTS1とTS2は、次のように計算できます。TS1(T) = TS1(P1) + 16000 * (NTP(T)-NTP(P1))、およびTS2(T) = TS2(P2) + 90000 * (NTP(T)-NTP(P2))。この計算は、すべての時間の値（TS1(T)、TS2(T)、T）が与えられた共通の同期点を実装が生成できるようになるので有用です。したがって、パケットXにあるタイムスタンプの値が対応するNTP時刻を計算したい場合は、次のように計算できます。NTP(X) = NTP(T) + (TS2(X) - TS2(T))/90000。

Improved signaling for layered codecs and fast tune-in have been specified in "Rapid Synchronization for RTP Flows" [RFC6051].

階層化コーデックと高速なチューンインのための改善されたシグナリングが、「Rapid Synchronization for RTP Flows」[RFC6051]で規定されています。

Leap seconds are extra seconds added or seconds removed to keep our clocks in sync with the earth's rotation. Adding or removing seconds can impact the reference clock as discussed in "RTP and Leap Seconds" [RFC7164]; also, in cases where the RTP timestamp values are derived using the wall clock during the leap second event, errors can occur. Implementations need to consider leap seconds and should consider the recommendations in [RFC7164].

うるう秒は、時計を地球の自転と同期させておくために追加または削除される秒です。[RFC7164]の「RTP and Leap Seconds」で論じられているように、秒の追加や削除は基準クロックに影響を与えることがあります。また、うるう秒のイベントの間にウォールクロックを使ってRTPタイムスタンプの値を導出する場合には、誤りが生じることがあります。実装はうるう秒を考慮する必要があり、[RFC7164]の推奨事項を考慮すべきです。

3.4. Signaling Aspects

3.4. シグナリングの側面

RTP payload formats are used in the context of application signaling protocols such as SIP [RFC3261] using the Session Description Protocol (SDP) [RFC4566] with Offer/Answer [RFC3264], RTSP [RFC7826], or the Session Announcement Protocol [RFC2974]. These examples all use out-of-band signaling to indicate which type of RTP streams are desired to be used in the session and how they are configured. To be able to declare or negotiate the media format and RTP payload packetization, the payload format must be given an identifier. In addition to the identifier, many payload formats also have the need to signal further configuration information out-of-band for the RTP payloads prior to the media transport session.

RTPペイロード形式は、オファー/アンサー[RFC3264]とともにセッション記述プロトコル（SDP）[RFC4566]を使うSIP[RFC3261]、RTSP[RFC7826]、またはセッションアナウンスメントプロトコル[RFC2974]などのアプリケーションのシグナリングプロトコルのコンテキストで使われます。これらの例はいずれも、セッションでどの種類のRTPストリームを使いたいか、そしてそれらをどのように設定するかを示すために、帯域外シグナリングを使います。メディア形式とRTPペイロードのパケット化を宣言またはネゴシエートできるようにするには、ペイロード形式に識別子を与える必要があります。多くのペイロード形式では、識別子に加えて、メディア転送セッションに先立ってRTPペイロードのためのさらなる設定情報を帯域外でシグナリングする必要もあります。

The above examples of session-establishing protocols all use SDP, but other session description formats may be used. For example, there was discussion of a new XML-based session description format within the IETF (SDP-NG). In the end, the proposal did not get beyond draft protocol specification because of the enormous installed base of SDP implementations. However, to avoid locking the usage of RTP to SDP based out-of-band signaling, the payload formats are identified using a separate definition format for the identifier and associated parameters. That format is the media type.

上記のセッション確立プロトコルの例はいずれもSDPを使いますが、ほかのセッション記述形式が使われることもあります。たとえば、IETFの中では、XMLに基づく新しいセッション記述形式（SDP-NG）についての議論がありました。結局、SDPの実装の膨大なインストールベースのために、その提案はドラフトのプロトコル仕様の段階を超えることはありませんでした。しかし、RTPの使用がSDPに基づく帯域外シグナリングに縛られるのを避けるため、ペイロード形式は、識別子と関連するパラメーターについて別個の定義形式を使って識別されます。その形式がメディアタイプです。

3.4.1. Media Types

3.4.1. メディアタイプ

Media types [RFC6838] are identifiers originally created for identifying media formats included in email. In this usage, they were known as MIME types, where the expansion of the MIME acronym includes the word "mail". The term "media type" was introduced to reflect a broader usage, which includes HTTP [RFC7231], Message Session Relay Protocol (MSRP) [RFC4975], and many other protocols to identify arbitrary content carried within the protocols. Media types also provide a media hierarchy that fits RTP payload formats well. Media type names are of two parts and consist of content type and sub-type separated with a slash, e.g., 'audio/PCMA' or 'video/h263-2000'. It is important to choose the correct content-type when creating the media type identifying an RTP payload format. However, in most cases, there is little doubt what content type the format belongs to. Guidelines for choosing the correct media type and registration rules for media type names are provided in "Media Type Specifications and Registration Procedures" [RFC6838]. The additional rules for media types for RTP payload formats are provided in "Media Type Registration of RTP Payload Formats" [RFC4855].

メディアタイプ[RFC6838]は、もともと電子メールに含まれるメディア形式を識別するために作られた識別子です。この用途では、メディアタイプはMIMEタイプとして知られており、MIMEという頭字語を展開すると「mail」という単語が含まれます。「メディアタイプ」という用語は、HTTP[RFC7231]、メッセージセッションリレープロトコル（MSRP）[RFC4975]、そしてそのほかの多くのプロトコルで、それらのプロトコル内で運ばれる任意のコンテンツを識別するという、より広い用途を反映するために導入されました。また、メディアタイプは、RTPペイロード形式によく合うメディアの階層構造も提供します。メディアタイプ名は2つの部分からなり、コンテンツタイプとサブタイプをスラッシュで区切ったものです（例：'audio/PCMA'や'video/h263-2000'）。RTPペイロード形式を識別するメディアタイプを作成する際には、正しいコンテンツタイプを選ぶことが重要です。ただし、ほとんどの場合、その形式がどのコンテンツタイプに属するかについて迷うことはほとんどありません。正しいメディアタイプを選ぶためのガイドラインと、メディアタイプ名の登録規則は、「Media Type Specifications and Registration Procedures」[RFC6838]で提供されています。RTPペイロード形式のためのメディアタイプについての追加の規則は、「Media Type Registration of RTP Payload Formats」[RFC4855]で提供されています。

Registration of the RTP payload name is something that is required to avoid name collision in the future. Note that "x-" names are not suitable for any documented format as they have the same problem with name collision and can't be registered. The list of already-registered media types can be found at <https://www.iana.org/assignments/media-types/media-types.xhtml>.

将来の名前の衝突を避けるために、RTPペイロード名の登録が必要です。「x-」で始まる名前は、同じ名前の衝突の問題があり、登録もできないので、文書化されたどの形式にも適していないことに注意してください。すでに登録されているメディアタイプの一覧は、<https://www.iana.org/assignments/media-types/media-types.xhtml>にあります。

Media types are allowed any number of parameters, which may be required or optional for that media type. They are always specified on the form "name=value". There exist no restrictions on how the value is defined from the media type's perspective, except that parameters must have a value. However, the usage of media types in SDP, etc., has resulted in the following restrictions that need to be followed to make media types usable for RTP-identifying payload formats:

メディアタイプには任意の数のパラメーターが許されており、それらはそのメディアタイプにとって必須の場合も省略可能な場合もあります。パラメーターは常に「name=value」の形式で指定されます。メディアタイプの観点からは、パラメーターが値を持たなければならないことを除いて、値の定義方法に制限はありません。しかし、SDPなどでメディアタイプが使われてきた結果、RTPのペイロード形式を識別するためにメディアタイプを使えるようにするには、次の制限に従う必要があります。

  1. Arbitrary binary content in the parameters is allowed, but it needs to be encoded so that it can be placed within text-based protocols. Base64 [RFC4648] is recommended, but for shorter content Base16 [RFC4648] may be more appropriate as it is simpler to interpret for humans. This needs to be explicitly stated when defining a media type parameter with binary values.
  2. The end of the value needs to be easily found when parsing a message. Thus, parameter values that are continuous and not interrupted by common text separators, such as space and semicolon characters, are recommended. If that is not possible, some type of escaping should be used. Usage of quote (") is recommended; do not forget to provide a method of encoding any character used for quoting inside the quoted element.

  3. A common representation form for the media type and its parameters is on a single line. In that case, the media type is followed by a semicolon-separated list of the parameter value pairs, e.g.:

    audio/amr octet-align=0; mode-set=0,2,5,7; mode-change-period=2
  1. パラメーターに任意のバイナリーコンテンツを含めることは許されていますが、テキストベースのプロトコル内に置けるように符号化する必要があります。Base64[RFC4648]が推奨されますが、短いコンテンツの場合は、人間にとって解釈しやすいBase16[RFC4648]のほうが適していることもあります。バイナリーの値を持つメディアタイプのパラメーターを定義する際には、このことを明示的に述べる必要があります。
  2. メッセージを構文解析する際に、値の終わりを容易に見つけられる必要があります。そのため、空白やセミコロン文字などの一般的なテキストの区切り文字で途切れることのない、連続したパラメーター値が推奨されます。それが不可能な場合は、何らかのエスケープを使うべきです。引用符（"）の使用が推奨されます。引用符で囲まれた要素の中で、引用に使われる文字を符号化する方法を必ず提供してください。

  3. メディアタイプとそのパラメーターの一般的な表現形式は、1行で表すものです。その場合、メディアタイプのあとに、パラメーターと値の組をセミコロンで区切ったリストが続きます。例：

    audio/amr octet-align=0; mode-set=0,2,5,7; mode-change-period=2

3.4.2. Mapping to SDP

3.4.2. SDPへのマッピング

Since SDP [RFC4566] is so commonly used as an out-of-band signaling protocol, a mapping of the media type into SDP exists. The details on how to map the media type and its parameters into SDP are described in [RFC4855]. However, this is not sufficient to explain how certain parameters must be interpreted, for example, in the context of Offer/Answer negotiation [RFC3264].

SDP[RFC4566]は帯域外シグナリングプロトコルとして非常によく使われているので、メディアタイプのSDPへのマッピングが存在します。メディアタイプとそのパラメーターをSDPにマッピングする方法の詳細は、[RFC4855]で説明されています。しかし、これだけでは、たとえばオファー/アンサーによるネゴシエーション[RFC3264]のコンテキストで、特定のパラメーターをどのように解釈しなければならないかを説明するには十分ではありません。

3.4.2.1. The Offer/Answer Model
3.4.2.1. オファー/アンサーモデル

The Offer/Answer (O/A) model allows SIP to negotiate which media formats and payload formats are to be used in a session and how they are to be configured. However, O/A does not define a default behavior; instead, it points out the need to define how parameters behave. To make things even more complex, the direction of media within a session has an impact on these rules, so that some cases may require separate descriptions for RTP streams that are send-only, receive-only, or both sent and received as identified by the SDP attributes a=sendonly, a=recvonly, and a=sendrecv. In addition, the usage of multicast adds further limitations as the same RTP stream is delivered to all participants. If those multicast-imposed restrictions are too limiting for unicast, then separate rules for unicast and multicast will be required.

オファー/アンサー（O/A）モデルにより、SIPは、セッションでどのメディア形式とペイロード形式を使うか、そしてそれらをどのように設定するかをネゴシエートできます。しかし、O/Aはデフォルトの振る舞いを定義していません。その代わりに、パラメーターがどのように振る舞うかを定義する必要があることを指摘しています。さらに事態を複雑にしているのは、セッション内のメディアの方向がこれらの規則に影響を与えることです。そのため、場合によっては、SDP属性のa=sendonly、a=recvonly、a=sendrecvで識別される、送信専用、受信専用、または送受信の両方を行うRTPストリームについて、別々の記述が必要になることがあります。さらに、マルチキャストでは同じRTPストリームがすべての参加者に配送されるので、マルチキャストを使うと制限がさらに加わります。マルチキャストによって課される制約がユニキャストにとって制限が強すぎる場合は、ユニキャストとマルチキャストで別々の規則が必要になります。

The simplest and most common O/A interpretation is that a parameter is defined to be declarative; i.e., the SDP Offer/Answer sending agent can declare a value and that has no direct impact on the other agent's values. This declared value applies to all media that are going to be sent to the declaring entity. For example, most video codecs have a level parameter that tells the other participants the highest complexity the video decoder supports. The level parameter can be declared independently by two participants in a unicast session as it will be the media sender's responsibility to transmit a video stream that fulfills the limitation the other side has declared. However, in multicast, it will be necessary to send a stream that follows the limitation of the weakest receiver, i.e., the one that supports the lowest level. To simplify the negotiation in these cases, it is common to require any answerer to a multicast session to take a yes or no approach to parameters.

最も単純で最も一般的なO/Aの解釈は、パラメーターが宣言的であると定義されているというものです。すなわち、SDPオファー/アンサーの送信側のエージェントが値を宣言でき、その値は相手のエージェントの値に直接の影響を与えません。この宣言された値は、宣言したエンティティーに送られるすべてのメディアに適用されます。たとえば、ほとんどの映像コーデックにはレベルパラメーターがあり、映像デコーダーがサポートする最大の複雑さをほかの参加者に伝えます。ユニキャストセッションでは、相手側が宣言した制限を満たす映像ストリームを送信するのはメディア送信者の責任になるので、2人の参加者がそれぞれ独立にレベルパラメーターを宣言できます。しかし、マルチキャストでは、最も能力の低い受信者、すなわち最も低いレベルをサポートする受信者の制限に従うストリームを送信する必要があります。このような場合のネゴシエーションを単純にするために、マルチキャストセッションに対するアンサー側には、パラメーターに対して「受け入れるか否か」の方針をとることを求めるのが一般的です。

A "negotiated" parameter is a different case, for which both sides need to agree on its value. Such a parameter requires the answerer to either accept it as it is offered or remove the payload type the parameter belonged to from its answer. The removal of the payload type from the answer indicates to the offerer the lack of support for the parameter values presented. An unfortunate implication of the need to use complete payload types to indicate each possible configuration so as to maximize the chances of achieving interoperability, is that the number of necessary payload types can quickly grow large. This is one reason to limit the total number of sets of capabilities that may be implemented.

「ネゴシエートされる」パラメーターは別のケースであり、その値について両者が合意する必要があります。そのようなパラメーターでは、アンサー側は、オファーされたとおりにそれを受け入れるか、そのパラメーターが属していたペイロードタイプをアンサーから削除する必要があります。アンサーからペイロードタイプを削除することは、提示されたパラメーター値をサポートしていないことをオファー側に示します。相互運用性を実現できる可能性を最大にするために、可能な設定のそれぞれを示すのに完全なペイロードタイプを使う必要があることから生じる残念な影響は、必要なペイロードタイプの数がすぐに大きくなりうることです。これは、実装されうる能力の組の総数を制限する理由の1つです。

The most problematic type of parameters are those that relate to the media the entity sends. They do not really fit the O/A model, but can be shoehorned in. Examples of such parameters can be found in the H.264 video codec's payload format [RFC6184], where the name of all parameters with this property starts with "sprop-". The issue with these parameters is that they declare properties for a RTP stream that the other party may not accept. The best one can make of the situation is to explain the assumption that the other party will accept the same parameter value for the media it will receive as the offerer of the session has proposed. If the answerer needs to change any declarative parameter relating to streams it will receive, then the offerer may be required to make a new offer to update the parameter values for its outgoing RTP stream.

最も問題の多い種類のパラメーターは、そのエンティティーが送信するメディアに関連するパラメーターです。これらはO/Aモデルにはあまりうまく当てはまりませんが、無理に当てはめることはできます。そのようなパラメーターの例は、H.264映像コーデックのペイロード形式[RFC6184]にあり、この特性を持つすべてのパラメーターの名前は「sprop-」で始まります。これらのパラメーターの問題は、相手が受け入れないかもしれないRTPストリームの特性を宣言することです。この状況で最善の策は、相手が受信するメディアについて、セッションのオファー側が提案したのと同じパラメーター値を受け入れるという前提を説明することです。アンサー側が、自身が受信するストリームに関連する宣言的なパラメーターを変更する必要がある場合、オファー側は、自身の送出するRTPストリームのパラメーター値を更新するために、新しいオファーを行う必要があるかもしれません。

Another issue to consider is the send-only RTP streams in offers. Parameters that relate to what the answering entity accepts to receive have no meaning other than to provide a template for the answer. It is worth pointing out in the specification that these really provide a set of parameter values that the sender recommends. Note that send-only streams in answers will need to indicate the offerer's parameters to ensure that the offerer can match the answer to the offer.

考慮すべきもう1つの問題は、オファーの中の送信専用のRTPストリームです。アンサー側のエンティティーが受信を受け入れるものに関連するパラメーターは、アンサーのテンプレートを提供すること以外に意味を持ちません。仕様の中で、これらは実際には送信者が推奨するパラメーター値の組を提供するものだと指摘しておく価値があります。オファー側がアンサーをオファーと照合できるようにするために、アンサーの中の送信専用のストリームではオファー側のパラメーターを示す必要があることに注意してください。

A further issue with Offer/Answer that complicates things is that the answerer is allowed to renumber the payload types between offer and answer. This is not recommended, but allowed for support of gateways to the ITU conferencing suite. This means that it must be possible to bind answers for payload types to the payload types in the offer even when the payload type number has been changed, and some of the proposed payload types have been removed. This binding must normally be done by matching the configurations originally offered against those in the answer. This may require specification in the payload format of which parameters that constitute a configuration, for example, as done in Section 8.2.2 of the H.264 RTP Payload format [RFC6184], which states: "The parameters identifying a media format configuration for H.264 are profile-level-id and packetization-mode".

オファー/アンサーで事態を複雑にするさらなる問題は、アンサー側がオファーとアンサーの間でペイロードタイプの番号を付け直すことが許されていることです。これは推奨されませんが、ITUの会議システム群へのゲートウェイをサポートするために許されています。これは、ペイロードタイプの番号が変更され、提案されたペイロードタイプの一部が削除された場合でも、ペイロードタイプに対するアンサーをオファーの中のペイロードタイプと結び付けられなければならないことを意味します。この結び付けは、通常、最初にオファーされた設定をアンサーの中の設定と照合することによって行わなければなりません。そのためには、どのパラメーターが設定を構成するかをペイロード形式の中で規定する必要があるかもしれません。たとえば、H.264のRTPペイロード形式[RFC6184]のセクション8.2.2では、そのように規定されており、「The parameters identifying a media format configuration for H.264 are profile-level-id and packetization-mode」（H.264のメディア形式の設定を識別するパラメーターは、profile-level-idとpacketization-modeである）と述べています。

3.4.2.2. Declarative Usage in RTSP and SAP
3.4.2.2. RTSPとSAPにおける宣言的な使用

SAP (Session Announcement Protocol) [RFC2974] was experimentally used for announcing multicast sessions. Similar but better protocols are using SDP in a declarative style to configure multicast-based applications. Independently of the usage of Source-Specific Multicast (SSM) [RFC3569] or Any-Source Multicast (ASM), the SDP provided by these configuration delivery protocols applies to all participants. All media that is sent to the session must follow the RTP stream definition as specified by the SDP. This enables everyone to receive the session if they support the configuration. Here, SDP provides a one-way channel with no possibility to affect the configuration that the session creator has decided upon. Any RTP payload format that requires parameters for the send direction and that needs individual values per implementation or instance will fail in a SAP session for a multicast session allowing anyone to send.

SAP（セッションアナウンスメントプロトコル）[RFC2974]は、マルチキャストセッションを告知するために実験的に使われていました。同様の、ただしよりよいプロトコルが、マルチキャストに基づくアプリケーションを設定するために、SDPを宣言的なスタイルで使っています。送信元特定マルチキャスト（SSM）[RFC3569]と任意ソースマルチキャスト（ASM）のどちらを使うかにかかわらず、これらの設定配信プロトコルによって提供されるSDPは、すべての参加者に適用されます。セッションに送信されるすべてのメディアは、SDPによって規定されたRTPストリームの定義に従わなければなりません。これにより、その設定をサポートしていれば、誰でもそのセッションを受信できます。ここでは、SDPは一方向のチャネルを提供するものであり、セッションの作成者が決めた設定に影響を与える手段はありません。送信方向のパラメーターを必要とし、実装やインスタンスごとに個別の値を必要とするRTPペイロード形式は、誰でも送信できるマルチキャストセッションのためのSAPセッションでは、うまく機能しません。

Real-Time Streaming Protocol (RTSP) [RFC7826] allows the negotiation of transport parameters for RTP streams that are part of a streaming session between a server and client. RTSP has divided the transport parameters from the media configuration. SDP is commonly used for media configuration in RTSP and is sent to the client prior to session establishment, either through use of the DESCRIBE method or by means of an out-of-band channel like HTTP, email, etc. The SDP is used to determine which RTP streams and what formats are being used prior to session establishment.

リアルタイムストリーミングプロトコル（RTSP）[RFC7826]では、サーバーとクライアントの間のストリーミングセッションの一部であるRTPストリームについて、トランスポートパラメーターをネゴシエートできます。RTSPでは、トランスポートパラメーターがメディアの設定から分離されています。RTSPでは、メディアの設定にはSDPがよく使われ、DESCRIBEメソッドを使うか、HTTPや電子メールなどの帯域外のチャネルによって、セッションの確立に先立ってクライアントに送られます。SDPは、セッションの確立に先立って、どのRTPストリームとどの形式が使われるかを判断するために使われます。

Thus, both SAP and RTSP use SDP to configure receivers and senders with a predetermined configuration for a RTP stream including the payload format and any of its parameters. All parameters are used in a declarative fashion. This can result in different treatment of parameters between Offer/Answer and declarative usage in RTSP and SAP. Any such difference will need to be spelled out by the payload format specification.

このように、SAPとRTSPはどちらも、SDPを使って、ペイロード形式とそのパラメーターを含むRTPストリームの事前に決められた設定を、受信者と送信者に設定します。すべてのパラメーターは宣言的に使われます。このため、オファー/アンサーと、RTSPやSAPでの宣言的な使用とで、パラメーターの扱いが異なる場合があります。そのような違いは、ペイロード形式の仕様の中で詳しく説明する必要があります。

3.5. Transport Characteristics

3.5. トランスポートの特性

The general channel characteristics that RTP flows experience are documented in Section 3 of "Guidelines for Writers of RTP Payload Format Specifications" [RFC2736]. The discussion below provides additional information.

RTPフローが受ける一般的なチャネル特性は、「Guidelines for Writers of RTP Payload Format Specifications」[RFC2736]のセクション3に記載されています。以下の議論では、追加の情報を提供します。

3.5.1. Path MTU

3.5.1. パスMTU

At the time of writing, the most common IP Maximum Transmission Unit (MTU) in commonly deployed link layers is 1500 bytes (Ethernet data payload). However, there exist both links with smaller MTUs and links with much larger MTUs. An example for links with small MTU size is older generation cellular links. Certain parts of the Internet already support an IP MTU of 8000 bytes or more, but these are limited islands. The most likely places to find MTUs larger than 1500 bytes are within enterprise networks, university networks, data centers, storage networks, and over high capacity (10 Gbps or more) links. There is a slow, ongoing evolution towards larger MTU sizes. However, at the same time, it has become common to use tunneling protocols, often multiple ones, whose overhead when added together can shrink the MTU significantly. Thus, there exists a need both to consider limited MTUs as well as enable support of larger MTUs. This should be considered in the design, especially in regard to features such as aggregation of independently decodable data units.

執筆時点で、一般に展開されているリンク層で最もよく見られるIPの最大転送単位（MTU）は、1500バイト（イーサネットのデータペイロード）です。しかし、これより小さいMTUのリンクも、はるかに大きいMTUのリンクも存在します。MTUの小さいリンクの例としては、古い世代のセルラーリンクがあります。インターネットの一部では、すでに8000バイト以上のIP MTUがサポートされていますが、それらは限られた島にすぎません。1500バイトを超えるMTUが見つかる可能性が最も高い場所は、企業ネットワーク、大学のネットワーク、データセンター、ストレージネットワークの中と、大容量（10Gbps以上）のリンク上です。より大きなMTUサイズに向けて、ゆっくりとした進化が続いています。しかし同時に、トンネリングプロトコルを、しばしば複数重ねて使うことが一般的になっており、それらのオーバーヘッドを合計するとMTUが大幅に縮小することがあります。したがって、限られたMTUを考慮することと、より大きなMTUのサポートを可能にすることの両方が必要です。これは、設計の際に、特に独立してデコード可能なデータユニットの集約のような機能に関して考慮すべきです。

3.5.2. Different Queuing Algorithms

3.5.2. さまざまなキューイングアルゴリズム

Routers and switches on the network path between an IP sender and a particular receiver can exhibit different behaviors affecting the end-to-end characteristics. One of the more important aspects of this is queuing behavior. Routers and switches have some amount of queuing to handle temporary bursts of data that designated to leave the switch or router on the same egress link. A queue, when not empty, results in an increased path delay.

IPの送信者と特定の受信者の間のネットワーク経路上にあるルーターやスイッチは、エンドツーエンドの特性に影響を与えるさまざまな振る舞いを示すことがあります。そのうち比較的重要な側面の1つは、キューイングの振る舞いです。ルーターやスイッチは、スイッチやルーターから同じイグレスリンクに出ていくことになっているデータの一時的なバーストを処理するために、ある程度のキューを持っています。キューが空でないときは、経路の遅延が増加します。

The implementation of the queuing affects the delay and also how congestion signals (Explicit Congestion Notification (ECN) [RFC6679] or packet drops) are provided to the flow. The other aspects are if the flow shares the queue with other flows and how the implementation affects the flow interaction. This becomes important, for example, when real-time flows interact with long-lived TCP flows. TCP has a built-in behavior in its congestion control that strives to fill the buffer; thus, all flows sharing the buffer experienced the delay build up.

キューイングの実装は、遅延に影響を与えるだけでなく、輻輳シグナル（明示的輻輳通知（ECN）[RFC6679]やパケットの廃棄）がフローにどのように提供されるかにも影響を与えます。そのほかの側面は、そのフローがほかのフローとキューを共有しているかどうかと、実装がフロー間の相互作用にどのように影響するかです。これは、たとえば、リアルタイムのフローが長時間続くTCPのフローと相互作用する場合に重要になります。TCPの輻輳制御には、バッファーを満たそうとする振る舞いが組み込まれています。そのため、そのバッファーを共有するすべてのフローで、遅延の増大が生じます。

A common, but quite poor, queue-handling mechanism is tail-drop, i.e., only drop packets when the incoming packet doesn't fit in the queue. If a bad queuing algorithm is combined with too much queue space, the queuing time can grow to be very significant and can even become multiple seconds. This is called "bufferbloat" [BLOAT]. Active Queue Management (AQM) is a term covering mechanisms that try to do something smarter by actively managing the queue, for example, sending congestion signals earlier by dropping packets earlier in the queue. The behavior also affects the flow interactions. For example, Random Early Detection (RED) [RED] selects which packet(s) to drop randomly. This gives flows that have more packets in the queue a higher probability to experience the packet loss (congestion signal). There is ongoing work in the IETF WG AQM to find suitable mechanisms to recommend for implementation and reduce the use of tail-drop.

一般的ではあるものの、かなり出来の悪いキュー処理メカニズムは、テールドロップ、すなわち到着したパケットがキューに収まらない場合にのみパケットを廃棄する方式です。出来の悪いキューイングアルゴリズムと過大なキュー領域が組み合わさると、キューイング時間が非常に大きくなり、数秒に達することさえあります。これは「バッファーブロート」[BLOAT]と呼ばれます。アクティブキュー管理（AQM）は、キューを積極的に管理することによって、たとえばキューの中でより早い段階でパケットを廃棄して輻輳シグナルをより早く送ることによって、より賢い処理を行おうとするメカニズムを包括する用語です。この振る舞いは、フロー間の相互作用にも影響を与えます。たとえば、Random Early Detection（RED）[RED]は、廃棄するパケットをランダムに選択します。これにより、キューの中にパケットを多く持つフローほど、パケット損失（輻輳シグナル）を受ける確率が高くなります。IETFのAQM WGでは、実装を推奨するのに適したメカニズムを見つけ、テールドロップの使用を減らすための作業が進行中です。

3.5.3. Quality of Service

3.5.3. サービス品質

Using best-effort Internet has no guarantees for the path's properties. QoS mechanisms are intended to provide the possibility to bound the path properties. Where Diffserv [RFC2475] markings affect the queuing and forwarding behaviors of routers, the mechanism provides only statistical guarantees and care in how much marked packets of different types that are entering the network. Flow-based QoS, like IntServ [RFC1633], has the potential for stricter guarantees as the properties are agreed on by each hop on the path, at the cost of per-flow state in the network.

ベストエフォートのインターネットを使う場合、経路の特性には何の保証もありません。QoSメカニズムは、経路の特性を一定の範囲に収める可能性を提供することを意図しています。Diffserv[RFC2475]のマーキングがルーターのキューイングと転送の振る舞いに影響を与える場合、そのメカニズムは統計的な保証しか提供せず、ネットワークに入ってくるさまざまな種類のマークされたパケットの量に注意が必要です。IntServ[RFC1633]のようなフローに基づくQoSは、ネットワーク内でフローごとの状態を持つという代償を払って、経路上の各ホップで特性について合意するので、より厳密な保証を提供できる可能性があります。

4. Standardization Process for an RTP Payload Format

4. RTPペイロード形式の標準化プロセス

This section discusses the recommended process to produce an RTP payload format in the described venues. This is to document the best current practice on how to get a well-designed and specified payload format as quickly as possible. For specifications that are defined by standards bodies other than the IETF, the primary milestone is the registration of the media type for the RTP payload format. For proprietary media formats, the primary goal depends on whether interoperability is desired at the RTP level. However, there is also the issue of ensuring best possible quality of any specification.

このセクションでは、前述の場でRTPペイロード形式を作成するための推奨プロセスについて論じます。これは、よく設計され、よく規定されたペイロード形式をできるだけ早く得る方法についての、現在のベストプラクティスを記述するためのものです。IETF以外の標準化団体が定義する仕様の場合、主要なマイルストーンは、そのRTPペイロード形式のためのメディアタイプの登録です。独自のメディア形式の場合、主要な目標は、RTPのレベルでの相互運用性が望まれるかどうかによって決まります。しかし、どのような仕様であっても、可能な限り最高の品質を確保するという問題もあります。

4.1. IETF

4.1. IETF

For all standardized media formats, it is recommended that the payload format be specified in the IETF. The main reason is to provide an openly available RTP payload format specification that has been reviewed by people experienced with RTP payload formats. At the time of writing, this work is done in the PAYLOAD Working Group (WG), but that may change in the future.

標準化されたすべてのメディア形式について、ペイロード形式をIETFで規定することが推奨されます。主な理由は、RTPペイロード形式の経験を持つ人々によってレビューされ、公開されて誰でも入手できるRTPペイロード形式の仕様を提供するためです。執筆時点では、この作業はPAYLOADワーキンググループ（WG）で行われていますが、将来は変わるかもしれません。

4.1.1. Steps from Idea to Publication

4.1.1. アイデアから発行までのステップ

There are a number of steps that an RTP payload format should go through from the initial idea until it is published. This also documents the process that the PAYLOAD WG applies when working with RTP payload formats.

RTPペイロード形式は、最初のアイデアから発行に至るまでに、いくつかのステップを経るべきです。これは、PAYLOAD WGがRTPペイロード形式に取り組む際に適用するプロセスを記述するものでもあります。

Idea:
Determine the need for an RTP payload format as an IETF specification.
Initial effort:
Using this document as a guideline, one should be able to get started on the work. If one's media codec doesn't fit any of the common design patterns or one has problems understanding what the most suitable way forward is, then one should contact the PAYLOAD WG and/or the WG Chairs. The goal of this stage is to have an initial individual draft. This draft needs to focus on the introductory parts that describe the real-time media format and the basic idea on how to packetize it. Not all the details are required to be filled in. However, the security chapter is not something that one should skip, even initially. From the start, it is important to consider any serious security risks that need to be solved. The first step is completed when one has a draft that is sufficiently detailed for a first review by the WG. The less confident one is of the solution, the less work should be spent on details; instead, concentrate on the codec properties and what is required to make the packetization work.
Submission of the first version:
When one has performed the above, one submits the draft as an individual draft (https://datatracker.ietf.org/submit/). This can be done at any time, except for a period prior to an IETF meeting (see important dates related to the next IETF meeting for draft submission cutoff date). When the Internet-Draft announcement has been sent out on the draft announcement list (https://www.ietf.org/mailman/listinfo/I-D-Announce), forward it to the PAYLOAD WG (https://www.ietf.org/mailman/listinfo/payload) and request that it be reviewed. In the email, outline any issues the authors currently have with the design.
Iterative improvements:
Taking the feedback received into account, one updates the draft and tries resolve issues. New revisions of the draft can be submitted at any time (again except for a short period before meetings). It is recommended to submit a new version whenever one has made major updates or has new issues that are easiest to discuss in the context of a new draft version.
Becoming a WG document:
Given that the definition of RTP payload formats is part of the PAYLOAD WG's charter, RTP payload formats that are going to be published as Standards Track RFCs need to become WG documents. Becoming a WG document means that the WG Chairs or an appointed document shepherd are responsible for administrative handling, for example, issuing publication requests. However, be aware that making a document into a WG document changes the formal ownership and responsibility from the individual authors to the WG. The initial authors normally continue being the document editors, unless unusual circumstances occur. The PAYLOAD WG accepts new RTP payload formats based on their suitability and document maturity. The document maturity is a requirement to ensure that there are dedicated document editors and that there exists a good solution.
Iterative improvements:
The updates and review cycles continue until the draft has reached the level of maturity suitable for publication. The authors are responsible for judging when the document is ready for the next step, most likely WG Last Call, but they can ask the WG chairs or Shepherd.
WG Last Call:
A WG Last Call of at least two weeks is always performed for payload formats in the PAYLOAD WG (see Section 7.4 of [RFC2418]). The authors request WG Last Call for a draft when they think it is mature enough for publication. The WG Chairs or shepherd perform a review to check if they agree with the authors' assessment. If the WG Chairs or shepherd agree on the maturity, the WG Last Call is announced on the WG mailing list. If there are issues raised, these need to be addressed with an updated draft version. For any more substantial changes to the draft, a new WG Last Call is announced for the updated version. Minor changes, like editorial fixes, can be progressed without an additional WG Last Call.
Publication requested:
For WG documents, the WG Chairs or shepherd request publication of the draft after it has passed WG Last Call. After this, the approval and publication process described in BCP 9 [BCP9] is performed. The status after the publication has been requested can be tracked using the IETF Datatracker [TRACKER]. Documents do not expire as they normally do after publication has been requested, so authors do not have to issue keep-alive updates. In addition, any submission of document updates requires the approval of WG Chair(s). The authors are commonly asked to address comments or issues raised by the IESG. The authors also do one last review of the document immediately prior to its publication as an RFC to ensure that no errors or formatting problems have been introduced during the publication process.
アイデア：
IETFの仕様としてのRTPペイロード形式の必要性を見極めます。
最初の取り組み：
この文書をガイドラインとして使えば、作業に着手できるはずです。自分のメディアコーデックが一般的な設計パターンのどれにも当てはまらない場合や、最も適した進め方を理解するのに苦労している場合は、PAYLOAD WGとWG議長のどちらか、または両方に連絡すべきです。この段階の目標は、最初の個人ドラフトを用意することです。このドラフトでは、リアルタイムメディア形式と、それをパケット化する方法についての基本的なアイデアを説明する導入部分に重点を置く必要があります。すべての詳細を埋める必要はありません。ただし、セキュリティーの章は、最初の段階であっても省略すべきものではありません。最初から、解決する必要のある深刻なセキュリティー上のリスクを考慮することが重要です。WGによる最初のレビューに十分な程度に詳細なドラフトができた時点で、最初のステップは完了です。解決策に自信がないほど、詳細に費やす作業を少なくし、代わりにコーデックの特性と、パケット化を機能させるのに必要なことに集中すべきです。
最初のバージョンの提出：
上記を行ったら、そのドラフトを個人ドラフトとして提出します（https://datatracker.ietf.org/submit/）。これは、IETFの会合の前の一定期間を除いて、いつでも行えます（ドラフト提出の締め切り日については、次のIETFの会合に関する重要な日程を参照してください）。インターネットドラフトの告知がドラフトの告知用リスト（https://www.ietf.org/mailman/listinfo/I-D-Announce）に送られたら、それをPAYLOAD WG（https://www.ietf.org/mailman/listinfo/payload）に転送し、レビューを依頼します。その電子メールでは、著者が現在設計に関して抱えている問題の概要を述べます。
反復的な改善：
受け取ったフィードバックを考慮に入れて、ドラフトを更新し、問題の解決を試みます。ドラフトの新しい改訂版は、いつでも提出できます（ここでも、会合の前の短い期間を除きます）。大きな更新を行ったときや、新しいドラフトのバージョンのコンテキストで議論するのが最も容易な新しい問題があるときは、そのつど新しいバージョンを提出することが推奨されます。
WG文書になる：
RTPペイロード形式の定義はPAYLOAD WGの憲章の一部なので、標準化過程のRFCとして発行されるRTPペイロード形式は、WG文書になる必要があります。WG文書になるということは、WG議長または任命された文書シェパードが、たとえば発行の要求を出すといった事務的な処理に責任を持つことを意味します。ただし、文書をWG文書にすると、正式な所有権と責任が個々の著者からWGに移ることに注意してください。通常、特別な事情がない限り、最初の著者が引き続き文書のエディターを務めます。PAYLOAD WGは、新しいRTPペイロード形式を、その適切さと文書の成熟度に基づいて受け入れます。文書の成熟度が要件となっているのは、専任の文書エディターがいることと、よい解決策が存在することを確実にするためです。
反復的な改善：
ドラフトが発行に適した成熟度に達するまで、更新とレビューのサイクルが続きます。文書が次のステップ（ほとんどの場合はWGラストコール）に進む準備ができたかどうかを判断するのは著者の責任ですが、WG議長やシェパードに相談することもできます。
WGラストコール：
PAYLOAD WGでは、ペイロード形式について、少なくとも2週間のWGラストコールが必ず行われます（[RFC2418]のセクション7.4を参照してください）。著者は、ドラフトが発行に十分なほど成熟したと考えたときに、そのドラフトのWGラストコールを要求します。WG議長またはシェパードは、著者の評価に同意できるかどうかを確認するためにレビューを行います。WG議長またはシェパードが成熟度について同意すれば、WGラストコールがWGのメーリングリストで告知されます。問題が提起された場合は、ドラフトの更新版でそれらに対処する必要があります。ドラフトに対するより大きな変更があった場合は、更新版について新たなWGラストコールが告知されます。編集上の修正などの軽微な変更は、追加のWGラストコールなしで進められます。
発行の要求：
WG文書の場合、ドラフトがWGラストコールを通過したあとに、WG議長またはシェパードがそのドラフトの発行を要求します。そのあと、BCP 9[BCP9]で説明されている承認と発行のプロセスが行われます。発行が要求されたあとのステータスは、IETF Datatracker[TRACKER]を使って追跡できます。発行が要求されたあとは、文書は通常のように期限切れにならないので、著者は文書を維持するための更新を行う必要はありません。また、文書の更新を提出するにはWG議長の承認が必要です。著者は通常、IESGから提起されたコメントや問題に対処するよう求められます。また著者は、発行プロセスの間に誤りや書式の問題が入り込んでいないことを確かめるために、RFCとして発行される直前に文書の最後のレビューを行います。

4.1.2. WG Meetings

4.1.2. WGの会合

WG meetings are for discussing issues, not presentations. This means that most RTP payload formats should never need to be discussed in a WG meeting. RTP payload formats that would be discussed are either those with controversial issues that failed to be resolved on the mailing list or those including new design concepts worth a general discussion.

WGの会合は、プレゼンテーションのためではなく、問題を議論するためのものです。つまり、ほとんどのRTPペイロード形式は、WGの会合で議論する必要がまったくないはずです。議論されるのは、メーリングリストで解決できなかった論争となる問題を抱えるRTPペイロード形式か、全体で議論する価値のある新しい設計概念を含むRTPペイロード形式です。

There exists no requirement to present or discuss a draft at a WG meeting before it becomes published as an RFC. Thus, even authors who lack the possibility to go to WG meetings should be able to successfully specify an RTP payload format in the IETF. WG meetings may become necessary only if the draft gets stuck in a serious debate that cannot easily be resolved.

ドラフトがRFCとして発行される前に、WGの会合でそのドラフトを発表したり議論したりしなければならないという要件はありません。したがって、WGの会合に出席できない著者でも、IETFでRTPペイロード形式をうまく規定できるはずです。WGの会合が必要になるのは、ドラフトが容易には解決できない深刻な議論で行き詰まった場合だけでしょう。

4.1.3. Draft Naming

4.1.3. ドラフトの命名

To simplify the work of the PAYLOAD WG Chairs and WG members, a specific Internet-Draft file-naming convention shall be used for RTP payload formats. Individual submissions shall be named using the template: draft-<lead author family name>-payload-rtp-<descriptive name>-<version>. The WG documents shall be named according to this template: draft-ietf-payload-rtp-<descriptive name>-<version>. The inclusion of "payload" in the draft file name ensures that the search for "payload-" will find all PAYLOAD-related drafts. Inclusion of "rtp" tells us that it is an RTP payload format draft. The descriptive name should be as short as possible while still describing what the payload format is for. It is recommended to use the media format or codec abbreviation. Please note that the version must start at 00 and is increased by one for each submission to the IETF secretary of the draft. No version numbers may be skipped. For more details on draft naming, please see Section 7 of [ID-GUIDE].

PAYLOAD WGの議長とWGのメンバーの作業を簡単にするために、RTPペイロード形式には、インターネットドラフトのファイル命名に関する特定の規約を使うことになっています。個人の提出物は、draft-<lead author family name>-payload-rtp-<descriptive name>-<version>というテンプレートを使って命名することになっています。WG文書は、draft-ietf-payload-rtp-<descriptive name>-<version>というテンプレートに従って命名することになっています。ドラフトのファイル名に「payload」を含めることで、「payload-」を検索すればPAYLOADに関連するすべてのドラフトが見つかるようになります。「rtp」を含めることで、それがRTPペイロード形式のドラフトであることがわかります。説明的な名前（descriptive name）は、そのペイロード形式が何のためのものかを説明しつつ、できるだけ短くすべきです。メディア形式やコーデックの略称を使うことが推奨されます。バージョンは00から始めなければならず、そのドラフトをIETF事務局に提出するたびに1ずつ増えることに注意してください。バージョン番号を飛ばしてはいけません。ドラフトの命名についての詳細は、[ID-GUIDE]のセクション7を参照してください。

4.1.4. Writing Style

4.1.4. 執筆のスタイル

When writing an Internet-Draft for an RTP payload format, one should observe some few considerations (that may be somewhat divergent from the style of other IETF documents and/or the media coding spec's author group may use):

RTPペイロード形式のインターネットドラフトを書く際には、いくつかの考慮事項を守るべきです（これらは、ほかのIETF文書のスタイルや、メディア符号化仕様の著者グループが使うスタイルとはいくらか異なるかもしれません）。

Include Motivations:
In the IETF, it is common to include the motivation for why a particular design or technical path was chosen. These are not long statements: a sentence here and there explaining why suffice.
Use the Defined Terminology:
There exists defined terminology both in RTP and in the media codec specification for which the RTP payload format is designed. A payload format specification needs to use both to make clear the relation of features and their functions. It is unwise to introduce or, worse, use without introduction, terminology that appears to be more accessible to average readers but may miss certain nuances that the defined terms imply. An RTP payload format author can assume the reader to be reasonably familiar with the terminology in the media coding specification.
Keeping It Simple:
The IETF has a history of specifications that are focused on their main usage. Historically, some RTP payload formats have a lot of modes and features, while the actual deployments have only included the most basic features that had very clear requirements. Time and effort can be saved by focusing on only the most important use cases and keeping the solution simple. An extension mechanism should be provided to enable backward-compatible extensions, if that is an organic fit.
Normative Requirements:
When writing specifications, there is commonly a need to make it clear when something is normative and at what level. In the IETF, the most common method is to use "Key words for use in RFCs to Indicate Requirement Levels" [RFC2119], which defines the meaning of "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL".
動機を含める：
IETFでは、特定の設計や技術的な方向性が選ばれた理由について、その動機を含めるのが一般的です。これは長い記述ではありません。理由を説明する一文があちこちにあれば十分です。
定義された用語を使う：
RTPにも、RTPペイロード形式の設計対象であるメディアコーデックの仕様にも、定義された用語があります。ペイロード形式の仕様では、機能とその働きの関係を明確にするために、その両方を使う必要があります。一般の読者にとってより親しみやすそうに見えても、定義された用語が意味する特定のニュアンスを取りこぼすかもしれない用語を導入したり、さらに悪いことに導入せずに使ったりするのは賢明ではありません。RTPペイロード形式の著者は、読者がメディア符号化仕様の用語にある程度精通していると想定してかまいません。
シンプルに保つ：
IETFには、主な用途に焦点を絞った仕様を作ってきた歴史があります。歴史的に、一部のRTPペイロード形式は多くのモードと機能を持っていますが、実際の展開には、非常に明確な要件があった最も基本的な機能しか含まれていませんでした。最も重要なユースケースだけに焦点を当て、解決策をシンプルに保つことで、時間と労力を節約できます。それが自然に合う場合は、後方互換な拡張を可能にするための拡張メカニズムを提供すべきです。
規範的な要件：
仕様を書く際には、何が規範的であり、それがどのレベルであるかを明確にする必要がよくあります。IETFで最も一般的な方法は、「Key words for use in RFCs to Indicate Requirement Levels」[RFC2119]を使うことです。この文書は、「MUST」「MUST NOT」「REQUIRED」「SHALL」「SHALL NOT」「SHOULD」「SHOULD NOT」「RECOMMENDED」「NOT RECOMMENDED」「MAY」「OPTIONAL」の意味を定義しています。

4.1.5. How to Speed Up the Process

4.1.5. プロセスを迅速化する方法

There a number of ways to lose a lot of time in the above process. This section discusses what to do and what to avoid.

上記のプロセスでは、多くの時間を失う原因がいくつもあります。このセクションでは、何をすべきか、何を避けるべきかを論じます。

  • Do not update the draft only for the meeting deadline. An update to each meeting automatically limits the draft to three updates per year. Instead, ignore the meeting schedule and publish new versions as soon as possible.
  • Try to avoid requesting reviews when people are busy, like the few weeks before a meeting. It is actually more likely that people have time for them directly after a meeting.
  • Perform draft updates quickly. A common mistake is that the authors let the draft slip. By performing updates to the draft text directly after getting resolution on an issue, things speed up. This minimizes the delay that the author has direct control over. The time taken for reviews, responses from Area Directors and WG Chairs, etc., can be much harder to speed up.
  • Do not fail to take human nature into account. It happens that people forget or need to be reminded about tasks. Send a kind reminder to the people you are waiting for if things take longer than expected. Ask people to estimate when they expect to fulfill the requested task.
  • Ensure there is enough review. It is common that documents take a long time and many iterations because not enough review is performed in each iteration. To improve the amount of review you get on your own document, trade review time with other document authors. Make a deal with some other document author that you will review their draft if they review yours. Even inexperienced reviewers can help with language, editorial, or clarity issues. Also, try approaching the more experienced people in the WG and getting them to commit to a review. The WG Chairs cannot, even if desirable, be expected to review all versions. Due to workload, the Chairs may need to concentrate on key points in a draft evolution like checking on initial submissions, a draft's readiness to become a WG document, or its readiness for WG Last Call.
  • 会合の締め切りに合わせてだけドラフトを更新することはやめましょう。会合ごとに更新すると、ドラフトの更新は自動的に年3回に限られてしまいます。代わりに、会合のスケジュールは気にせず、新しいバージョンをできるだけ早く公開しましょう。
  • 会合の前の数週間のように、人々が忙しい時期にレビューを依頼するのは避けるようにしましょう。実際には、会合の直後のほうが、人々がレビューの時間をとれる可能性が高いです。
  • ドラフトの更新は素早く行いましょう。よくある間違いは、著者がドラフトを停滞させてしまうことです。問題の解決が得られたらすぐにドラフトのテキストを更新することで、物事が速く進みます。これにより、著者が直接制御できる遅延を最小限に抑えられます。レビューや、エリアディレクターとWG議長からの返答などにかかる時間は、はるかに短縮しにくいものです。
  • 人間の性質を考慮に入れることを忘れないようにしましょう。人は作業を忘れたり、作業について念を押してもらう必要があったりするものです。予想よりも時間がかかっている場合は、待っている相手に丁寧な催促を送りましょう。依頼した作業をいつ終えられる見込みかを見積もってもらいましょう。
  • 十分なレビューを確保しましょう。各反復で十分なレビューが行われないために、文書に長い時間と多くの反復がかかることはよくあります。自分の文書が受けるレビューの量を増やすには、ほかの文書の著者とレビューの時間を交換しましょう。ほかの文書の著者と、相手が自分のドラフトをレビューしてくれたら自分も相手のドラフトをレビューするという取り決めをしましょう。経験の浅いレビュアーでも、言葉遣い、編集、わかりやすさの問題については助けになります。また、WGの中のより経験豊富な人々に働きかけて、レビューを約束してもらうようにしましょう。望ましいことであっても、WG議長がすべてのバージョンをレビューすることは期待できません。作業量の都合上、議長は、最初の提出物の確認、ドラフトがWG文書になる準備ができているかどうか、あるいはWGラストコールの準備ができているかどうかといった、ドラフトの進展における重要なポイントに集中する必要があるかもしれません。

4.2. Other Standards Bodies

4.2. ほかの標準化団体

Other standards bodies may define RTP payloads in their own specifications. When they do this, they are strongly recommended to contact the PAYLOAD WG Chairs and request review of the work. It is recommended that at least two review steps are performed. The first should be early in the process when more fundamental issues can be easily resolved without abandoning a lot of effort. Then, when nearing completion, but while it is still possible to update the specification, a second review should be scheduled. In that pass, the quality can be assessed; hopefully, no updates will be needed. Using this procedure can avoid both conflicting definitions and serious mistakes, like breaking certain aspects of the RTP model.

ほかの標準化団体が、自身の仕様の中でRTPペイロードを定義することがあります。その場合、それらの団体はPAYLOAD WGの議長に連絡して、作業のレビューを依頼することが強く推奨されます。少なくとも2回のレビューのステップを行うことが推奨されます。1回目は、多くの労力を無駄にすることなく、より根本的な問題を容易に解決できるプロセスの初期段階に行うべきです。次に、完成に近づいたものの、まだ仕様を更新できる段階で、2回目のレビューを予定すべきです。その段階で品質を評価できます。願わくは、更新は必要ないでしょう。この手順を使うことで、定義の衝突と、RTPモデルの特定の側面を壊してしまうといった重大な誤りの両方を避けることができます。

RTP payload media types may be registered in the standards tree by other standards bodies. The requirements on the organization are outlined in the media types registration documents [RFC4855] and [RFC6838]). This registration requires a request to the IESG, which ensures that the filled-in registration template is acceptable. To avoid last-minute problems with these registrations the registration template must be sent for review both to the PAYLOAD WG and the media types list (ietf-types@iana.org) and is something that should be included in the IETF reviews of the payload format specification.

RTPペイロードのメディアタイプは、ほかの標準化団体によって標準ツリーに登録されることがあります。その組織に対する要件は、メディアタイプの登録に関する文書[RFC4855]と[RFC6838]に概説されています。この登録にはIESGへの要求が必要であり、IESGは記入された登録テンプレートが受け入れ可能であることを確認します。これらの登録で土壇場になって問題が起きるのを避けるため、登録テンプレートはPAYLOAD WGとメディアタイプのリスト（ietf-types@iana.org）の両方にレビューのために送らなければならず、ペイロード形式の仕様のIETFでのレビューに含めるべきものです。

4.3. Proprietary and Vendor Specific

4.3. 独自形式とベンダー固有の形式

Proprietary RTP payload formats are commonly specified when the real-time media format is proprietary and not intended to be part of any standardized system. However, there are reasons why also proprietary formats should be correctly documented and registered:

独自のRTPペイロード形式は、リアルタイムメディア形式が独自のものであり、標準化されたシステムの一部となることを意図していない場合によく規定されます。しかし、独自の形式であっても正しく文書化し、登録すべき理由があります。

  • Usage in a standardized signaling environment, such as SIP/SDP. RTP needs to be configured with the RTP profiles, payload formats, and their payload types being used. To accomplish this, it is desirable to have registered media type names to ensure that the names do not collide with those of other formats.
  • Sharing with business partners. As RTP payload formats are used for communication, situations often arise where business partners would like to support a proprietary format. Having a well-written specification of the format will save time and money for both parties, as interoperability will be much easier to accomplish.
  • To ensure interoperability between different implementations on different platforms.
  • SIP/SDPのような標準化されたシグナリング環境での使用。RTPは、使用されるRTPプロファイル、ペイロード形式、およびそれらのペイロードタイプで設定される必要があります。これを実現するには、名前がほかの形式の名前と衝突しないように、登録されたメディアタイプ名を持つことが望ましいです。
  • ビジネスパートナーとの共有。RTPペイロード形式は通信に使われるので、ビジネスパートナーが独自の形式をサポートしたいと考える状況がよく生じます。その形式についてよく書かれた仕様があれば、相互運用性をはるかに容易に実現できるので、双方にとって時間と費用の節約になります。
  • 異なるプラットフォーム上の異なる実装の間での相互運用性を確保するため。

To avoid name collisions, there is a central registry keeping track of the registered media type names used by different RTP payload formats. When it comes to proprietary formats, they should be registered in the vendor's own tree. All vendor-specific registrations use sub-type names that start with "vnd.<vendor-name>". Names in the vendor's own tree are not required to be registered with IANA. However, registration [RFC6838] is recommended if the media type is used at all in public environments.

名前の衝突を避けるために、さまざまなRTPペイロード形式で使われる登録済みのメディアタイプ名を管理する中央のレジストリーがあります。独自の形式の場合は、そのベンダー自身のツリーに登録すべきです。ベンダー固有の登録はすべて、「vnd.<vendor-name>」で始まるサブタイプ名を使います。ベンダー自身のツリーの名前は、IANAに登録する必要はありません。しかし、そのメディアタイプが公開の環境で少しでも使われる場合は、登録[RFC6838]が推奨されます。

If interoperability at the RTP level is desired, a payload type specification should be standardized in the IETF following the process described above. The IETF does not require full disclosure of the codec when defining an RTP payload format to carry that codec, but a description must be provided that is sufficient to allow the IETF to judge whether the payload format is well designed. The media type identifier assigned to a standardized payload format of this sort will lie in the standards tree rather than the vendor tree.

RTPのレベルでの相互運用性が望まれる場合は、上記のプロセスに従って、ペイロードタイプの仕様をIETFで標準化すべきです。IETFは、コーデックを運ぶためのRTPペイロード形式を定義する際に、そのコーデックを完全に開示することは求めませんが、ペイロード形式がよく設計されているかどうかをIETFが判断できるだけの十分な説明を提供しなければなりません。この種の標準化されたペイロード形式に割り当てられるメディアタイプ識別子は、ベンダーツリーではなく標準ツリーに置かれます。

4.4. Joint Development of Media Coding Specification and RTP Payload Format

4.4. メディア符号化仕様とRTPペイロード形式の共同開発

In the last decade, there have been a few cases where the media codec and the associated RTP payload format have been developed concurrently and jointly. Developing the two specs not only concurrently but also jointly, in close cooperation with the group developing the media codec, allows one to leverage the benefits joint source/channel coding can provide. Doing so has historically resulted in well-performing payload formats and in success of both the media coding specification and associated RTP payload format. Insofar, whenever the opportunity presents it, it may be useful to closely keep the media coding group in the loop (through appropriate liaison means whatever those may be) and influence the media coding specification to be RTP friendly. One example for such a media coding specification is H.264, where the RTP payload header co-serves as the H.264 NAL unit header and vice versa, and is documented in both specifications.

過去10年間に、メディアコーデックとそれに関連するRTPペイロード形式が同時に、かつ共同で開発されたケースがいくつかありました。2つの仕様を同時に開発するだけでなく、メディアコーデックを開発するグループと緊密に協力して共同で開発することで、ソース符号化とチャネル符号化を合わせて行うことで得られる利点を活用できます。歴史的に、そのようにすることで性能のよいペイロード形式が生まれ、メディア符号化仕様とそれに関連するRTPペイロード形式の両方が成功を収めてきました。その意味で、機会があればいつでも、（それが何であれ適切なリエゾンの手段を通じて）メディア符号化のグループと緊密に情報を共有し、メディア符号化仕様がRTPに適したものになるよう働きかけることが役に立つかもしれません。そのようなメディア符号化仕様の一例はH.264であり、RTPペイロードヘッダーがH.264のNALユニットヘッダーを兼ね、またその逆も成り立っており、両方の仕様に記載されています。

5. Designing Payload Formats

5. ペイロード形式の設計

The best summary of payload format design is KISS (Keep It Simple, Stupid). A simple payload format is easier to review for correctness, easier to implement, and has low complexity. Unfortunately, contradictory requirements sometimes make it hard to do things simply. Complexity issues and problems that occur for RTP payload formats are:

ペイロード形式の設計を最もよく要約するのは、KISS（Keep It Simple, Stupid）です。シンプルなペイロード形式は、正しさをレビューしやすく、実装しやすく、複雑さも低くなります。残念ながら、相反する要件のために、物事をシンプルに行うのが難しい場合があります。RTPペイロード形式で生じる複雑さの問題と課題は、次のとおりです。

Too many configurations:
Contradictory requirements lead to the result that one configuration is created for each conceivable case. Such contradictory requirements are often between functionality and bandwidth. This outcome has two big disadvantages; First all configurations need to be implemented. Second, the user application must select the most suitable configuration. Selecting the best configuration can be very difficult and, in negotiating applications, this can create interoperability problems. The recommendation is to try to select a very limited set of configurations (preferably one) that perform well for the most common cases and are capable of handling the other cases, but maybe not that well.
Hard to implement:
Certain payload formats may become difficult to implement both correctly and efficiently. This needs to be considered in the design.
Interaction with general mechanisms:
Special solutions may create issues with deployed tools for RTP, such as tools for more robust transport of RTP. For example, a requirement for an unbroken sequence number space creates issues for mechanisms relying on payload type switching interleaving media-independent resilience within a stream.
設定が多すぎる：
相反する要件の結果、考えられるケースごとに1つの設定が作られることになります。そのような相反する要件は、多くの場合、機能と帯域幅の間にあります。この結果には2つの大きな欠点があります。第1に、すべての設定を実装する必要があります。第2に、ユーザーのアプリケーションが最も適した設定を選択しなければなりません。最適な設定を選択するのは非常に難しいことがあり、ネゴシエーションを行うアプリケーションでは、相互運用性の問題を生じることがあります。推奨されるのは、最も一般的なケースで性能がよく、ほかのケースも（それほどうまくではないかもしれませんが）扱える、ごく限られた設定の組（できれば1つ）を選ぶよう努めることです。
実装が難しい：
一部のペイロード形式は、正しく、かつ効率的に実装するのが難しくなることがあります。これは設計の際に考慮する必要があります。
汎用的なメカニズムとの相互作用：
特殊な解決策は、RTPのより堅牢な転送のためのツールなど、展開済みのRTPのツールとの間で問題を生じることがあります。たとえば、途切れのないシーケンス番号空間を要件とすると、ストリーム内でペイロードタイプを切り替えてメディア非依存の耐性データをインターリーブすることに依存するメカニズムで問題が生じます。

5.1. Features of RTP Payload Formats

5.1. RTPペイロード形式の機能

There are a number of common features in RTP payload formats. There is no general requirement to support these features; instead, their applicability must be considered for each payload format. In fact, it may be that certain features are not even applicable.

RTPペイロード形式には、いくつかの共通の機能があります。これらの機能をサポートしなければならないという一般的な要件はなく、ペイロード形式ごとにその適用可能性を検討しなければなりません。実際、特定の機能はそもそも適用できない場合もあります。

5.1.1. Aggregation

5.1.1. 集約

Aggregation allows for the inclusion of multiple Application Data Units (ADUs) within the same RTP payload. This is commonly supported for codecs that produce ADUs of sizes smaller than the IP MTU. One reason for the use of aggregation is the reduction of header overhead (IP/UDP/RTP headers). When setting into relation the ADU size and the MTU size, do remember that the MTU may be significantly larger than 1500 bytes. An MTU of 9000 bytes is available today and an MTU of 64k may be available in the future. Many speech codecs have the property of ADUs of a few fixed sizes. Video encoders may generally produce ADUs of quite flexible sizes. Thus, the need for aggregation may be less. But some codecs produce small ADUs mixed with large ones, for example, H.264 Supplemental Enhancement Information (SEI) messages. Sending individual SEI message in separate packets are not efficient compared to combing the with other ADUs. Also, some small ADUs are, within the media domain, semantically coupled to the larger ADUs (for example, in-band parameter sets in H.264 [RFC6184]). In such cases, aggregation is sensible, even if not required from a payload/header overhead viewpoint. There also exist cases when the ADUs are pre-produced and can't be adopted to a specific networks MTU. Instead, their packetization needs to be adopted to the network. All above factors should be taken into account when deciding on the inclusion of aggregation, and weighting its benefits against the complexity of defining them (which can be significant especially when aggregation is performed over ADUs with different playback times).

集約により、同じRTPペイロードの中に複数のアプリケーションデータユニット（ADU）を含めることができます。これは、IP MTUより小さいサイズのADUを生成するコーデックでよくサポートされます。集約を使う理由の1つは、ヘッダーのオーバーヘッド（IP/UDP/RTPヘッダー）の削減です。ADUのサイズとMTUのサイズを関係づける際には、MTUが1500バイトよりかなり大きい場合があることを忘れないでください。現在では9000バイトのMTUが利用でき、将来は64kのMTUが利用できるようになるかもしれません。多くの音声コーデックには、ADUがいくつかの固定サイズになるという特性があります。映像エンコーダーは、一般にかなり柔軟なサイズのADUを生成できます。そのため、集約の必要性はより小さいかもしれません。しかし、一部のコーデックは、大きなADUに混じって小さなADUを生成します。たとえば、H.264の補足拡張情報（SEI）メッセージです。個々のSEIメッセージを別々のパケットで送ることは、ほかのADUと組み合わせる場合に比べて効率的ではありません。また、一部の小さなADUは、メディアの領域において、より大きなADUと意味的に結び付いています（たとえば、H.264[RFC6184]の帯域内パラメーターセット）。そのような場合は、ペイロードやヘッダーのオーバーヘッドの観点からは必要でなくても、集約は理にかなっています。また、ADUがあらかじめ生成されていて、特定のネットワークのMTUに合わせられない場合もあります。その場合は、ADUのパケット化をネットワークに合わせる必要があります。集約を含めるかどうかを決める際には、上記のすべての要因を考慮に入れ、その利点と、集約を定義する複雑さ（特に、再生時刻の異なるADUにわたって集約を行う場合には、かなり大きくなることがあります）とを比較検討すべきです。

The main disadvantage of aggregation, beyond implementation complexity, is the extra delay introduced (due to buffering until a sufficient number of ADUs have been collected at the sender) and reduced robustness against packet loss. Aggregation also introduces buffering requirements at the receiver.

集約の主な欠点は、実装の複雑さに加えて、（送信者で十分な数のADUが集まるまでバッファリングすることによる）追加の遅延が生じることと、パケット損失に対する堅牢性が低下することです。また、集約により、受信者にバッファリングの要件が生じます。

5.1.2. Fragmentation

5.1.2. 断片化

If the real-time media format has the property that it may produce ADUs that are larger than common MTU sizes, then fragmentation support should be considered. An RTP payload format may always fall back on IP fragmentation; however, as discussed in RFC 2736, this has some drawbacks. Perhaps the most important reason to avoid IP fragmentation is that IP fragmented packets commonly are discarded in the network, especially by NATs or firewalls. The usage of fragmentation at the RTP payload format level allows for more efficient usage of RTP packet loss recovery mechanisms. It may also in some cases also allow better usage of partial ADUs by doing media specific fragmentation at media-specific boundaries. In use cases where the ADUs are pre-produced and can't be adopted to the network's MTU size, support for fragmentation can be crucial.

リアルタイムメディア形式が、一般的なMTUサイズより大きいADUを生成することがあるという特性を持つ場合は、断片化のサポートを検討すべきです。RTPペイロード形式は、常にIPフラグメンテーションにフォールバックできますが、RFC 2736で論じられているように、これにはいくつかの欠点があります。IPフラグメンテーションを避けるべきおそらく最も重要な理由は、IPフラグメンテーションされたパケットが、ネットワークの中で、特にNATやファイアウォールによって破棄されることがよくあるためです。RTPペイロード形式のレベルで断片化を使うと、RTPのパケット損失回復メカニズムをより効率的に使えます。また、場合によっては、メディア固有の境界でメディア固有の断片化を行うことで、部分的なADUをよりうまく活用できることもあります。ADUがあらかじめ生成されていて、ネットワークのMTUサイズに合わせられないユースケースでは、断片化のサポートがきわめて重要になることがあります。

5.1.3. Interleaving and Transmission Rescheduling

5.1.3. インターリーブと送信順序の再スケジューリング

Interleaving has been implemented in a number of payload formats to allow for less quality reduction when packet loss occurs. When losses are bursty and several consecutive packets are lost, the impact on quality can be quite severe. Interleaving is used to convert that burst loss to several spread-out individual packet losses. It can also be used when several ADUs are aggregated in the same packets. A loss of an RTP packet with several ADUs in the payload has the same effect as a burst loss if the ADUs would have been transmitted in individual packets. To reduce the burstiness of the loss, the data present in an aggregated payload may be interleaved, thus, spreading the loss over a longer time period.

インターリーブは、パケット損失が起きたときの品質の低下を小さくするために、いくつかのペイロード形式で実装されてきました。損失がバースト的で、連続するいくつかのパケットが失われると、品質への影響がかなり深刻になることがあります。インターリーブは、そのようなバースト損失を、分散した複数の個別のパケット損失に変えるために使われます。インターリーブは、複数のADUが同じパケットに集約される場合にも使えます。ペイロードに複数のADUを含むRTPパケットの損失は、それらのADUが個別のパケットで送信されていた場合のバースト損失と同じ影響を持ちます。損失のバースト性を減らすために、集約されたペイロードの中のデータをインターリーブして、損失をより長い期間に分散させることができます。

A requirement for doing interleaving within an RTP payload format is the aggregation of multiple ADUs. For formats that do not use aggregation, there is still a possibility of implementing a transmission order rescheduling mechanism. That has the effect that the packets transmitted consecutively originate from different points in the RTP stream. This can be used to mitigate burst losses, which may be useful if one transmits packets at frequent intervals. However, it may also be used to transmit more significant data earlier in combination with RTP retransmission to allow for more graceful degradation and increased possibility to receive the most important data, e.g., intra frames of video.

RTPペイロード形式の中でインターリーブを行うための要件は、複数のADUの集約です。集約を使わない形式でも、送信順序を再スケジューリングするメカニズムを実装できる可能性はあります。これには、連続して送信されるパケットが、RTPストリームの異なる時点に由来するようになるという効果があります。これはバースト損失を緩和するために使え、パケットを頻繁な間隔で送信する場合に役立つことがあります。しかし、RTP再送と組み合わせて、より重要なデータをより早く送信し、品質をより緩やかに低下させ、最も重要なデータ（たとえば、映像のイントラフレーム）を受信できる可能性を高めるためにも使えます。

The drawback of interleaving is the significantly increased transmission buffering delay, making it less useful for low-delay applications. It may also create significant buffering requirements on the receiver. That buffering is also problematic, as it is usually difficult to indicate when a receiver may start consume data and still avoid buffer under run caused by the interleaving mechanism itself. Transmission rescheduling is only useful in a few specific cases, as in streaming with retransmissions. The potential gains must be weighed against the complexity of these schemes.

インターリーブの欠点は、送信時のバッファリング遅延が大幅に増えることであり、そのため低遅延のアプリケーションではあまり役に立ちません。また、受信者に大きなバッファリングの要件が生じることもあります。そのバッファリングにも問題があります。受信者がいつデータの消費を始めてよいかを、インターリーブのメカニズムそのものによるバッファーアンダーランを避けつつ示すのは、通常は難しいからです。送信順序の再スケジューリングは、再送を伴うストリーミングのような、ごく一部の特定のケースでしか役に立ちません。潜在的な利得を、これらの方式の複雑さと比較検討しなければなりません。

5.1.4. Media Back Channels

5.1.4. メディアのバックチャネル

A few RTP payload formats have implemented back channels within the media format. Those have been for specific features, like the AMR [RFC4867] codec mode request (CMR) field. The CMR field is used in the operation of gateways to circuit-switched voice to allow an IP terminal to react to the circuit-switched network's need for a specific encoder mode. A common motivation for media back channels is the need to have signaling in direct relation to the media or the media path.

いくつかのRTPペイロード形式は、メディア形式の中にバックチャネルを実装しています。それらは、AMR[RFC4867]のコーデックモード要求（CMR）フィールドのような、特定の機能のためのものでした。CMRフィールドは、回線交換の音声へのゲートウェイの運用において、回線交換ネットワークが特定のエンコーダーモードを必要とすることにIP端末が対応できるようにするために使われます。メディアのバックチャネルの一般的な動機は、メディアやメディアの経路と直接関連したシグナリングを持つ必要があることです。

If back channels are considered for an RTP payload format they should be for a specific requirements which cannot be easily satisfied by more generic mechanisms within RTP or RTCP.

RTPペイロード形式にバックチャネルを検討する場合、それはRTPやRTCPの中のより汎用的なメカニズムでは容易に満たせない、特定の要件のためのものであるべきです。

5.1.5. Media Scalability

5.1.5. メディアのスケーラビリティー

Some codecs support various types of media scalability, i.e. some data of a RTP stream may be removed to adapt the media's properties, such as bitrate and quality. The adaptation may be applied in the following dimensions of the media:

一部のコーデックは、さまざまな種類のメディアのスケーラビリティーをサポートしています。すなわち、ビットレートや品質などのメディアの特性を調整するために、RTPストリームのデータの一部を取り除くことができます。この調整は、メディアの次の次元で適用できます。

Temporal:
For most video codecs it is possible to adapt the frame rate without any specific definition of a temporal scalability mode, e.g., for H.264 [RFC6184]. In these cases, the sender changes which frames it delivers and the RTP timestamp makes it clear the frame interval and each frames relative capture time. H.264 Scalable Video Coding (SVC) [RFC6190] has more explicit support for temporal scalability.
Spatial:
Video codecs supporting scalability may adapt the resolution, e.g., in SVC [RFC6190].
Quality:
The quality of the encoded stream may be scaled by adapting the accuracy of the coding process, as, e.g. possible with Signal to Noise Ratio (SNR) fidelity scalability of SVC [RFC6190].
時間：
ほとんどの映像コーデックでは、時間スケーラビリティーのモードを特に定義しなくても、フレームレートを調整できます。たとえば、H.264[RFC6184]の場合です。このような場合、送信者は配送するフレームを変更し、RTPタイムスタンプによってフレームの間隔と各フレームの相対的な取り込み時刻が明確になります。H.264スケーラブル映像符号化（SVC）[RFC6190]は、時間スケーラビリティーをより明示的にサポートしています。
空間：
スケーラビリティーをサポートする映像コーデックは、解像度を調整できる場合があります。たとえば、SVC[RFC6190]の場合です。
品質：
符号化されたストリームの品質は、符号化処理の精度を調整することでスケーリングできます。たとえば、SVC[RFC6190]の信号対雑音比（SNR）の忠実度スケーラビリティーで可能なものです。

At the time of writing this document, codecs that support scalability have a bit of a revival. It has been realized that getting the required functionality for supporting the features of the media stream into the RTP framework is quite challenging. One of the recent examples for layered and scalable codecs is SVC [RFC6190].

この文書の執筆時点で、スケーラビリティーをサポートするコーデックはちょっとした復活を遂げています。メディアストリームの機能をサポートするのに必要な機能をRTPのフレームワークに取り込むことは、かなり難しいことがわかってきました。階層化されたスケーラブルなコーデックの最近の例の1つは、SVC[RFC6190]です。

SVC is a good example for a payload format supporting media scalability features, which have been in its basic form already included in RTP. A layered codec supports the dropping of data parts of a RTP stream, i.e., RTP packets may not be transmitted or forwarded to a client in order to adapt the RTP streams bitrate as well as the received encoded stream's quality, while still providing a decodable subset of the encoded stream to a client. One example for using the scalability feature may be an RTP Mixer (Multipoint Control Unit) [RFC7667], which controls the rate and quality sent out to participants in a communication based on dropping RTP packets or removing part of the payload. Another example may be a transport channel, which allows for differentiation in Quality of Service (QoS) parameters based on RTP sessions in a multicast session. In such a case, the more important packets of the scalable encoded stream (base layer) may get better QoS parameters than the less important packets (enhancement layer) in order to provide some kind of graceful degradation. The scalability features required for allowing an adaptive transport, as described in the two examples above, are based on RTP multiplexing in order to identify the packets to be dropped or transmitted/forwarded. The multiplexing features defined for Scalable Video Coding [RFC6190] are:

SVCは、メディアのスケーラビリティー機能をサポートするペイロード形式のよい例であり、その機能は基本的な形ではすでにRTPに含まれていました。階層化コーデックは、RTPストリームのデータの一部を落とすことをサポートします。すなわち、クライアントには符号化されたストリームのデコード可能な部分集合を提供しつつ、RTPストリームのビットレートと、受信される符号化されたストリームの品質を調整するために、RTPパケットをクライアントに送信または転送しないことができます。スケーラビリティー機能を使う一例は、RTPミキサー（多地点制御ユニット）[RFC7667]でしょう。これは、RTPパケットを落としたり、ペイロードの一部を取り除いたりすることによって、通信の参加者に送り出すレートと品質を制御します。もう1つの例は、マルチキャストセッションにおいて、RTPセッションに基づいてサービス品質（QoS）パラメーターを区別できるトランスポートチャネルでしょう。そのような場合、ある種の緩やかな品質低下を提供するために、スケーラブルな符号化されたストリームのより重要なパケット（ベースレイヤー）が、それほど重要でないパケット（拡張レイヤー）よりもよいQoSパラメーターを得ることがあります。上記の2つの例で説明したような適応的な転送を可能にするために必要なスケーラビリティー機能は、落とすパケットや送信または転送するパケットを識別するためのRTPの多重化に基づいています。スケーラブル映像符号化[RFC6190]のために定義されている多重化の機能は、次のとおりです。

  • Single Session Transmission (SST), where all media layers of the media are transported as a single synchronization source (SSRC) in a single RTP session; as well as
  • Multi-Session Transmission (MST), which should more accurately be called multi-stream transmission, where different media layers or a set of media layers are transported in different RTP streams, i.e., using multiple sources (SSRCs).
  • 単一セッション送信（Single Session Transmission：SST）。メディアのすべてのメディアレイヤーが、単一のRTPセッションの中で単一の同期ソース（SSRC）として転送されます。および、
  • マルチセッション送信（Multi-Session Transmission：MST）。より正確にはマルチストリーム送信と呼ぶべきもので、異なるメディアレイヤーまたはメディアレイヤーの組が、異なるRTPストリームで、すなわち複数のソース（SSRC）を使って転送されます。

In the first case (SST), additional in-band as well as out-of-band signaling is required in order to allow identification of packets belonging to a specific media layer. Furthermore, an adaptation of the encoded stream requires dropping of specific packets in order to provide the client with a compliant encoded stream. In case of using encryption, it is typically required for an adapting network device to be in the security context to allow packet dropping and providing an intact RTP session to the client. This typically requires the network device to be an RTP mixer.

1つ目のケース（SST）では、特定のメディアレイヤーに属するパケットを識別できるようにするために、帯域内と帯域外の両方の追加のシグナリングが必要です。さらに、符号化されたストリームを調整するには、クライアントに準拠した符号化されたストリームを提供するために、特定のパケットを落とす必要があります。暗号化を使う場合、パケットを落としつつクライアントに完全なRTPセッションを提供できるようにするには、通常、調整を行うネットワーク装置がセキュリティーコンテキストの中にいる必要があります。これには通常、そのネットワーク装置がRTPミキサーである必要があります。

In general, having a media-unaware network device dropping excessive packets will be more problematic than having a Media-Aware Network Entity (MANE). First is the need to understand the media format and know which ADUs or payloads belong to the layers, that no other layer will be dependent on after the dropping. Second, if the MANE can work as an RTP mixer or translator, it can rewrite the RTP and RTCP in such a way that the receiver will not suspect unintentional RTP packet losses needing repair actions. This as the receiver can't determine if a lost packet was an important base layer packet or one of the less important extension layers.

一般に、メディアを認識しないネットワーク装置に余分なパケットを落とさせるのは、メディア認識ネットワークエンティティー（MANE）に落とさせるよりも問題が多くなります。第1に、メディア形式を理解し、どのADUやペイロードが、落としたあとにほかのどのレイヤーからも依存されないレイヤーに属するのかを知る必要があります。第2に、MANEがRTPミキサーやトランスレーターとして機能できれば、修復の処置を必要とする意図しないRTPパケット損失を受信者が疑わないように、RTPとRTCPを書き換えることができます。というのも、受信者は、失われたパケットが重要なベースレイヤーのパケットだったのか、それほど重要でない拡張レイヤーの1つだったのかを判断できないからです。

In the second case (MST), the RTP packet streams can be sent using a single or multiple RTP session, and thus transport flows, e.g., on different multicast groups. Transmitting the streams in different RTP sessions, then the out-of-band signaling typically provides enough information to identify the media layers and its properties. The decision on dropping packets is based on the Network Address that identifies the RTP session to be dropped. In order to allow correct data provisioning to a decoder after reception from different sessions, data realignment mechanisms are required. In some cases, existing generic tools, as described below, can be employed to enable such realignment; when those generic mechanisms are sufficient, they should be used. For example, "Rapid Synchronisation for RTP Flows" [RFC6051], uses existing RTP mechanisms, i.e. the NTP timestamp, to ensure timely inter-session synchronization. Another is the signaling feature for indicating dependencies of RTP sessions in SDP, as defined in the Media Decoding Dependency Grouping in SDP [RFC5583].

2つ目のケース（MST）では、RTPパケットストリームは、単一または複数のRTPセッション、したがって単一または複数のトランスポートフローを使って、たとえば異なるマルチキャストグループ上で送信できます。ストリームを異なるRTPセッションで送信する場合、通常は帯域外シグナリングが、メディアレイヤーとその特性を識別するのに十分な情報を提供します。パケットを落とすかどうかの判断は、落とすべきRTPセッションを識別するネットワークアドレスに基づいて行われます。異なるセッションから受信したあとにデコーダーへ正しくデータを供給できるようにするには、データを再整列するメカニズムが必要です。場合によっては、以下で説明するような既存の汎用的なツールを使ってそのような再整列を可能にできます。それらの汎用的なメカニズムで十分な場合は、それらを使うべきです。たとえば、「Rapid Synchronisation for RTP Flows」[RFC6051]は、既存のRTPのメカニズム、すなわちNTPタイムスタンプを使って、セッション間の同期を適時に確保します。もう1つは、「Media Decoding Dependency Grouping in SDP」[RFC5583]で定義されている、SDPでRTPセッションの依存関係を示すためのシグナリング機能です。

Using MST within a single RTP session is also possible and allows stream level handling instead of looking deeper into the packets by a MANE. However, transport flow-level properties will be the same unless packet based mechanisms like Diffserv is used.

単一のRTPセッション内でMSTを使うことも可能であり、そうするとMANEがパケットの奥まで調べる代わりに、ストリームのレベルで処理できるようになります。ただし、Diffservのようなパケットに基づくメカニズムを使わない限り、トランスポートフローのレベルの特性は同じになります。

When QoS settings, e.g., Diffserv markings, are used to ensure that the extension layers are dropped prior the base layer the receiving endpoint has the benefit in MST to know which layer or set of layers the missing packets belong to as it will be bound to different RTP sessions or RTP packet streams (SSRCs), thus, explicitly indicating the importance of the loss.

拡張レイヤーがベースレイヤーより先に落とされるようにするためにQoSの設定（たとえば、Diffservのマーキング）を使う場合、MSTでは、失われたパケットが異なるRTPセッションまたはRTPパケットストリーム（SSRC）に結び付けられているので、受信側のエンドポイントは失われたパケットがどのレイヤーまたはレイヤーの組に属するかを知ることができ、それによって損失の重要度が明示的に示されるという利点があります。

5.1.6. High Packet Rates

5.1.6. 高いパケットレート

Some media codecs require high packet rates; in these cases, the RTP sequence number wraps too quickly. As a rule of thumb, it must not be possible to wrap the sequence number space within at least three RTCP reporting intervals. As the reporting interval can vary widely due to configuration and session properties, and also must take into account the randomization of the interval, one can use the TCP maximum segment lifetime (MSL), i.e., 2 minutes, in ones consideration. If earlier wrapping may occur, then the payload format should specify an extended sequence number field to allow the receiver to determine where a specific payload belongs in the sequence, even in the face of extensive reordering. The RTP payload format for uncompressed video [RFC4175] can be used as an example for such a field.

一部のメディアコーデックは高いパケットレートを必要とします。そのような場合、RTPのシーケンス番号はすぐに一周してしまいます。経験則として、少なくともRTCPの報告間隔3回分の間にシーケンス番号空間が一周することがあってはなりません。報告間隔は設定やセッションの特性によって大きく変わることがあり、また間隔のランダム化も考慮しなければならないので、検討にはTCPの最大セグメント寿命（MSL）、すなわち2分を使うことができます。それより早く一周する可能性がある場合、ペイロード形式では、大規模な並べ替えが起きた場合でも特定のペイロードがシーケンスのどこに属するかを受信者が判断できるように、拡張シーケンス番号フィールドを規定すべきです。非圧縮映像のRTPペイロード形式[RFC4175]は、そのようなフィールドの例として使えます。

RTCP is also affected by high packet rates. For RTCP mechanisms that do not use extended counters, there is significant risk that they wrap multiple times between RTCP reporting or feedback; thus, producing uncertainty about which packet(s) are referenced. The payload designer can't effect the RTCP packet formats used and their design, but can note this considerations when configuring RTCP bandwidth and reporting intervals to avoid to wrapping issues.

RTCPも高いパケットレートの影響を受けます。拡張カウンターを使わないRTCPのメカニズムでは、RTCPの報告やフィードバックの間にカウンターが何度も一周してしまい、その結果、どのパケットが参照されているのかがあいまいになる大きなリスクがあります。ペイロードの設計者は、使用されるRTCPのパケット形式やその設計に影響を与えることはできませんが、一周の問題を避けるために、RTCPの帯域幅と報告間隔を設定する際のこれらの考慮事項について注記できます。

5.2. Selecting Timestamp Definition

5.2. タイムスタンプの定義の選択

The RTP timestamp is an important part and has two design choices associated with it. The first is the definition that determines what the timestamp value in a particular RTP packet will be, the second is which timestamp rate should be used.

RTPタイムスタンプは重要な部分であり、それに関連する2つの設計上の選択があります。1つ目は、特定のRTPパケットのタイムスタンプの値が何になるかを決める定義であり、2つ目は、どのタイムスタンプレートを使うべきかです。

The timestamp definition needs to explicitly define what the timestamp value in the RTP packet represent for a particular payload format. Two common definitions are used; for discretely sampled media, like video frames, the sampling time of the earliest included video frame which the data represent (fully or partially) is used; for continuous media like audio, the sampling time of the earliest sample which the payload data represent. There exist cases where more elaborate or other definitions are used.

タイムスタンプの定義では、特定のペイロード形式について、RTPパケットのタイムスタンプの値が何を表すかを明示的に定義する必要があります。一般的な定義は2つあります。映像のフレームのような離散的にサンプリングされるメディアでは、データが（完全に、または部分的に）表す、含まれる中で最も早い映像フレームのサンプリング時刻が使われます。音声のような連続的なメディアでは、ペイロードデータが表す中で最も早いサンプルのサンプリング時刻が使われます。より手の込んだ定義や、そのほかの定義が使われる場合もあります。

RTP payload formats with a timestamp definition that results in no or little correlation between the media time instance and its transmission time cause the RTCP jitter calculation to become unusable due to the errors introduced on the sender side. A common example is a payload format for a video codec where the RTP timestamp represents the capture time of the video frame, but frames are large enough that multiple RTP packets need to be sent for each frame spread across the framing interval. It should be noted whether or not the payload format has this property.

メディアの時刻とその送信時刻との間に相関がまったくない、またはほとんどないようなタイムスタンプの定義を持つRTPペイロード形式では、送信者側で誤差が生じるため、RTCPのジッター計算が使えなくなります。よくある例は、RTPタイムスタンプが映像フレームの取り込み時刻を表すものの、フレームが大きいため、フレームごとに複数のRTPパケットをフレーム間隔にわたって分散して送信する必要がある映像コーデックのペイロード形式です。ペイロード形式がこの特性を持つかどうかを記載すべきです。

An RTP payload format also needs to define what timestamp rates, or clock rates (as it is also called), may be used. Depending on the RTP payload format, this may be a single rate or multiple ones or theoretically any rate. So what needs to be considered when selecting a rate?

RTPペイロード形式では、どのタイムスタンプレート（クロックレートとも呼ばれます）を使えるかも定義する必要があります。RTPペイロード形式によって、これは単一のレートの場合も、複数のレートの場合も、理論上は任意のレートの場合もあります。では、レートを選択する際に何を考慮する必要があるのでしょうか。

The rate needs be selected so that one can determine where in the time line of the media a particular sample (e.g., individual audio sample, or video frame) or set of samples (e.g., audio frames) belong. To enable correct synchronization of this data with previous frames, including over periods of discontinuous transmission or irregularities.

レートは、特定のサンプル（たとえば、個々の音声サンプルや映像フレーム）やサンプルの組（たとえば、音声フレーム）がメディアのタイムライン上のどこに属するかを判断できるように選択する必要があります。これは、不連続送信や不規則性のある期間をまたぐ場合も含めて、このデータを以前のフレームと正しく同期できるようにするためです。

For audio, it is common to require audio sample accuracy. Thus, one commonly selects the input sampling rate as the timestamp rate. This can, however, be challenging for audio codecs that support multiple different sampling frequencies, either as codec input or being used internally but effecting output, for example, frame duration. Depending on how one expects to use these different sampling rates one can allow multiple timestamp rates, each matching a particular codec input or sampling rate. However, due to the issues with using multiple different RTP timestamp rates for the same source (SSRC) [RFC7160], this should be avoided if one expects to need to switch between modes.

音声では、音声サンプルの精度を求めるのが一般的です。そのため、通常は入力のサンプリングレートをタイムスタンプレートとして選択します。しかし、これは、コーデックの入力として、または内部で使われて出力（たとえばフレームの長さ）に影響するものとして、複数の異なるサンプリング周波数をサポートする音声コーデックでは難しいことがあります。これらの異なるサンプリングレートがどのように使われると想定するかによっては、それぞれが特定のコーデック入力やサンプリングレートに対応する、複数のタイムスタンプレートを許すことができます。しかし、同じソース（SSRC）に複数の異なるRTPタイムスタンプレートを使うことには問題があるので[RFC7160]、モードを切り替える必要が生じると予想される場合は、これを避けるべきです。

Then, an alternative is to find a common denominator frequency between the different modes, e.g., OPUS [RFC7587] that uses 48 kHz. If the different modes uses or can use a common input/output frequency, then selecting this also needs to be considered. However, it is important to consider all aspects as the case of AMR-WB+ [RFC4352] illustrates. AMR-WB+'s RTP timestamp rate has the very unusual value of 72 kHz, despite the fact that output normally is at a sample rate of 48kHz. The design is motivated by the media codec's production of a large range of different frame lengths in time perspective. The 72 kHz timestamp rate is the smallest found value that would make all of the frames the codec could produce result in an integer frame length in RTP timestamp ticks. This way, a receiver can always correctly place the frames in relation to any other frame, even when the frame length changes. The downside is that the decoder outputs for certain frame lengths are, in fact, partial samples. The result is that the output in samples from the codec will vary from frame to frame, potentially making implementation more difficult.

その場合の代替案は、異なるモードの間で共通の公約数となる周波数を見つけることです。たとえば、48kHzを使うOPUS[RFC7587]がそうです。異なるモードが共通の入出力周波数を使う、または使える場合は、それを選択することも検討する必要があります。しかし、AMR-WB+[RFC4352]の例が示すように、あらゆる側面を考慮することが重要です。AMR-WB+のRTPタイムスタンプレートは、出力は通常48kHzのサンプルレートであるにもかかわらず、72kHzという非常に珍しい値になっています。この設計は、このメディアコーデックが時間の観点で非常に幅広い異なるフレーム長を生成することに動機づけられています。72kHzのタイムスタンプレートは、コーデックが生成しうるすべてのフレームについて、フレーム長がRTPタイムスタンプのティックで整数になるような、見つかった中で最小の値です。こうすることで、フレーム長が変わる場合でも、受信者は常にフレームをほかのどのフレームとの関係でも正しく配置できます。欠点は、特定のフレーム長に対するデコーダーの出力が、実際には部分的なサンプルになることです。その結果、コーデックからのサンプル単位の出力がフレームごとに変わり、実装がより難しくなる可能性があります。

Video codecs have commonly been using 90 kHz; the reason is this is a common denominator between the usually used frame rates such as 24, 25, 30, 50 and 60, and NTSC's odd 29.97 Hz. There does, however, exist at least one exception in the payload format for SMPTE 292M video [RFC3497] that uses a clock rate of 148.5 MHz. The reason here is that the timestamp then identify the exact start sample within a video frame.

映像コーデックでは一般に90kHzが使われてきました。その理由は、これが24、25、30、50、60といった通常使われるフレームレートと、NTSCの半端な29.97Hzの公約数になっているからです。しかし、少なくとも1つの例外が、148.5MHzのクロックレートを使うSMPTE 292M映像のペイロード形式[RFC3497]にあります。この場合の理由は、そうするとタイムスタンプが映像フレーム内の正確な開始サンプルを識別できるからです。

Timestamp rates below 1000 Hz are not appropriate, because this will cause a resolution too low in the RTCP measurements that are expressed in RTP timestamps. This is the main reason that the text RTP payload formats, like T.140 [RFC4103], use 1000 Hz.

1000Hz未満のタイムスタンプレートは適切ではありません。RTPタイムスタンプで表現されるRTCPの測定値の分解能が低くなりすぎるからです。T.140[RFC4103]のようなテキストのRTPペイロード形式が1000Hzを使う主な理由はこれです。

6. Noteworthy Aspects in Payload Format Design

6. ペイロード形式の設計において注目すべき側面

This section provides a few examples of payload formats that are worth noting for good or bad design in general or in specific details.

このセクションでは、全般的に、または特定の細部において、設計のよし悪しの点で注目に値するペイロード形式の例をいくつか示します。

6.1. Audio Payloads

6.1. 音声ペイロード

The AMR [RFC4867], AMR-WB [RFC4867], EVRC [RFC3558], SMV [RFC3558] payload formats are all quite similar. They are all for frame-based audio codecs and use a table of contents structure. Each frame has a table of contents entry that indicates the type of the frame and if additional frames are present. This is quite flexible, but produces unnecessary overhead if the ADU is of fixed size and if, when aggregating multiple ADUs, they are commonly of the same type. In that case, a solution like the one in AMR-WB+ [RFC4352] may be more suitable.

AMR[RFC4867]、AMR-WB[RFC4867]、EVRC[RFC3558]、SMV[RFC3558]のペイロード形式は、どれもよく似ています。いずれもフレームに基づく音声コーデックのためのもので、目次（table of contents）構造を使います。各フレームには、フレームの種類と、追加のフレームが存在するかどうかを示す目次エントリーがあります。これはかなり柔軟ですが、ADUが固定サイズで、かつ複数のADUを集約する際にそれらが一般に同じ種類である場合には、不必要なオーバーヘッドを生じます。その場合は、AMR-WB+[RFC4352]のような解決策のほうが適しているかもしれません。

The RTP payload format for MIDI [RFC6295] contains some interesting features. MIDI is an audio format sensitive to packet losses, as the loss of a "note off" command will result in a note being stuck in an "on" state. To counter this, a recovery journal is defined that provides a summarized state that allows the receiver to recover from packet losses quickly. It also uses RTCP and the reported highest sequence number to be able to prune the state the recovery journal needs to contain. These features appear limited in applicability to media formats that are highly stateful and primarily use symbolic media representations.

MIDIのRTPペイロード形式[RFC6295]には、いくつかの興味深い機能があります。MIDIはパケット損失の影響を受けやすい音声形式です。「note off」コマンドが失われると、音が「on」の状態のまま止まらなくなるからです。これに対処するために、受信者がパケット損失から素早く回復できるように、状態の要約を提供するリカバリージャーナルが定義されています。また、リカバリージャーナルに含める必要のある状態を削減できるように、RTCPと報告された最大のシーケンス番号を使います。これらの機能は、状態を多く持ち、主に記号的なメディア表現を使うメディア形式にしか適用できないように思われます。

There exists a security concern with variable bitrate audio and speech codecs that changes their payload length based on the input data. This can leak information, especially in structured communication like a speech recognition prompt service that asks people to enter information verbally. This issue also exists to some degree for discontinuous transmission as that allows the length of phrases to be determined. The issue is further discussed in "Guidelines for the Use of Variable Bit Rate Audio with Secure RTP" [RFC6562], which needs to be read by anyone writing an RTP payload format for an audio or speech codec with these properties.

入力データに基づいてペイロード長を変える、可変ビットレートの音声や会話音声のコーデックには、セキュリティー上の懸念があります。これは、特に、人々に口頭で情報を入力するよう求める音声認識の案内サービスのような構造化された通信において、情報を漏洩する可能性があります。不連続送信でも、フレーズの長さがわかってしまうので、この問題はある程度存在します。この問題は「Guidelines for the Use of Variable Bit Rate Audio with Secure RTP」[RFC6562]でさらに論じられており、これらの特性を持つ音声や会話音声のコーデックのRTPペイロード形式を書く人は、誰でもこれを読む必要があります。

6.2. Video

6.2. 映像

The definition of RTP payload formats for video has seen an evolution from the early ones such as H.261 [RFC4587] towards the latest for VP8 [RFC7741] and H.265/HEVC [RFC7798].

映像のRTPペイロード形式の定義は、H.261[RFC4587]のような初期のものから、VP8[RFC7741]やH.265/HEVC[RFC7798]のための最新のものまで進化してきました。

The H.264 RTP payload format [RFC3984] can be seen as a smorgasbord of functionality: some of it, such as the interleaving, being pretty advanced. The reason for this was to ensure that the majority of applications considered by the ITU-T and MPEG that can be supported by RTP are indeed supported. This has created a payload format that rarely is fully implemented. Despite that, no major issues with interoperability has been reported with one exception namely the Offer/Answer and parameter signaling, which resulted in a revised specification [RFC6184]. However, complaints about its complexity are common.

H.264のRTPペイロード形式[RFC3984]は、機能のスモーガスボード（バイキング料理）と見ることができ、インターリーブのようにかなり高度な機能もあります。その理由は、ITU-TとMPEGが検討したアプリケーションのうち、RTPでサポートできるものの大部分を確実にサポートするためでした。その結果、完全に実装されることがほとんどないペイロード形式になりました。それにもかかわらず、相互運用性に関する大きな問題は報告されていません。ただし1つの例外として、オファー/アンサーとパラメーターのシグナリングがあり、それによって改訂版の仕様[RFC6184]ができました。しかし、その複雑さについての不満はよく聞かれます。

The RTP payload format for uncompressed video [RFC4175] must be mentioned in this context as it contains a special feature not commonly seen in RTP payload formats. Due to the high bitrate and thus packet rate of uncompressed video (gigabits rather than megabits per second) the payload format includes a field to extend the RTP sequence number since the normal 16-bit one can wrap in less than a second. [RFC4175] also specifies a registry of different color sub-samplings that can be reused in other video RTP payload formats.

非圧縮映像のRTPペイロード形式[RFC4175]は、RTPペイロード形式ではあまり見られない特別な機能を含んでいるので、この文脈で触れておく必要があります。非圧縮映像はビットレートが高く（毎秒メガビットではなくギガビット）、したがってパケットレートも高いので、通常の16ビットのシーケンス番号は1秒もたたないうちに一周してしまうことがあります。そのため、このペイロード形式には、RTPのシーケンス番号を拡張するフィールドが含まれています。また、[RFC4175]は、ほかの映像のRTPペイロード形式で再利用できる、さまざまな色差サブサンプリングのレジストリーも規定しています。

Both the H.264 and the uncompressed video format enable the implementer to fulfill the goals of application-level framing, i.e., each individual RTP Packet's payload can be independently decoded and its content used to create a video frame (or part of) and that irrespective of whether preceding packets has been lost (see Section 4) [RFC2736]. For uncompressed, this is straightforward as each pixel is independently represented from others and its location in the video frame known. H.264 is more dependent on the actual implementation, configuration of the video encoder and usage of the RTP payload format.

H.264と非圧縮映像の形式はどちらも、実装者がアプリケーションレベルフレーミングの目標を達成できるようにしています。すなわち、先行するパケットが失われたかどうかにかかわらず、個々のRTPパケットのペイロードを独立してデコードでき、その内容を使って映像フレーム（またはその一部）を作成できます（[RFC2736]のセクション4を参照してください）。非圧縮の場合、各ピクセルはほかのピクセルとは独立に表現され、映像フレーム内での位置もわかっているので、これは簡単です。H.264の場合は、実際の実装、映像エンコーダーの設定、RTPペイロード形式の使い方への依存度がより高くなります。

The common challenge with video is that, in most cases, a single compressed video frame doesn't fit into a single IP packet. Thus, the compressed representation of a video frame needs to be split over multiple packets. This can be done unintelligently with a basic payload level fragmentation method or more integrated by interfacing with the encoder's possibilities to create ADUs that are independent and fit the MTU for the RTP packet. The latter is more robust and commonly recommended unless strong packet loss mechanisms are used and sufficient delay budget for the repair exist. Commonly, both payload-level fragmentation as well as explaining how tailored ADUs can be created are needed in a video payload format. Also, the handling of crucial metadata, like H.264 Parameter Sets, needs to be considered as decoding is not possible without receiving the used parameter sets.

映像に共通する課題は、ほとんどの場合、圧縮された1つの映像フレームが1つのIPパケットに収まらないことです。そのため、映像フレームの圧縮表現を複数のパケットに分割する必要があります。これは、ペイロードレベルの基本的な断片化の方法で機械的に行うこともできますし、独立していてRTPパケットのMTUに収まるADUを作成するエンコーダーの機能と連携して、より統合的に行うこともできます。後者のほうが堅牢であり、強力なパケット損失対策のメカニズムが使われ、かつ修復のための十分な遅延の余裕がある場合を除いて、一般に推奨されます。一般に、映像のペイロード形式では、ペイロードレベルの断片化と、用途に合わせたADUを作成する方法の説明の両方が必要です。また、使われるパラメーターセットを受信しなければデコードできないので、H.264のパラメーターセットのような重要なメタデータの扱いを考慮する必要があります。

6.3. Text

6.3. テキスト

Only a single format text format has been standardized in the IETF, namely T.140 [RFC4103]. The 3GPP Timed Text format [RFC4396] should be considered to be text, even though in the end was registered as a video format. It was registered in that part of the tree because it deals with decorated text, usable for subtitles and other embellishments of video. However, it has many of the properties that text formats generally have.

IETFで標準化されたテキスト形式は、T.140[RFC4103]の1つだけです。3GPPのTimed Text形式[RFC4396]は、最終的には映像形式として登録されましたが、テキストとみなすべきです。これがツリーのその部分に登録されたのは、字幕やそのほかの映像の装飾に使える、装飾されたテキストを扱うからです。しかし、テキスト形式が一般に持つ特性の多くを持っています。

The RTP payload format for T.140 was designed with high reliability in mind as real-time text commonly is an extremely low bitrate application. Thus, it recommends the use of RFC 2198 with many generations of redundancy. However, the format failed to provide a text-block-specific sequence number and instead relies on the RTP one to detect loss. This makes detection of missing text blocks unnecessarily difficult and hinders deployment with other robustness mechanisms that would involve switching the payload type, as that may result in erroneous error marking in the T.140 text stream.

リアルタイムテキストは一般にきわめて低ビットレートのアプリケーションであるため、T.140のRTPペイロード形式は高い信頼性を念頭に置いて設計されました。そのため、何世代にもわたる冗長性を持たせてRFC 2198を使うことを推奨しています。しかし、この形式はテキストブロック固有のシーケンス番号を提供せず、代わりに損失の検出をRTPのシーケンス番号に頼っています。このため、欠落したテキストブロックの検出が不必要に難しくなっています。また、ペイロードタイプの切り替えを伴うほかの堅牢性メカニズムとともに展開することも妨げられています。そうするとT.140のテキストストリームに誤ったエラーマーキングが生じるかもしれないからです。

6.4. Application

6.4. アプリケーション

At the time of writing, the application content type contains two media types that aren't RTP transport robustness tools such as FEC [RFC3009] [RFC5109] [RFC6015] [RFC6682] and RTP retransmission [RFC4588].

執筆時点で、applicationコンテンツタイプには、FEC[RFC3009][RFC5109][RFC6015][RFC6682]やRTP再送[RFC4588]のようなRTPの転送の堅牢性ツールではないメディアタイプが2つあります。

The first one is H.224 [RFC4573], which enables far-end camera control over RTP. This is not an IETF-defined RTP format, only an IETF-performed registration.

1つ目はH.224[RFC4573]で、RTP上での遠端カメラ制御を可能にします。これはIETFが定義したRTP形式ではなく、IETFが登録を行っただけです。

The second one is "RTP Payload Format for Society of Motion Picture and Television Engineers (SMPTE) ST 336 Encoded Data" [RFC6597], which carries generic key length value (KLV) triplets. These pairs may contain arbitrary binary metadata associated with video transmissions. It has a very basic fragmentation mechanism requiring reception without packet loss, not only of the triplet itself but also one packet before and after the sequence of fragmented KLV triplet, to ensure correct reception. Specific KLV triplets themselves may have recommendations on how to handle incomplete ones allowing the use and repair of them. In general, the application using such a mechanism must be robust to errors and also use some combination of application-level repetition, RTP-level transport robustness tools, and network-level requirements to achieve low levels of packet loss rates and repair of KLV triplets.

2つ目は「RTP Payload Format for Society of Motion Picture and Television Engineers (SMPTE) ST 336 Encoded Data」[RFC6597]で、汎用的なキー・長さ・値（KLV）の3つ組を運びます。これらの組には、映像の送信に関連する任意のバイナリーのメタデータを含めることができます。この形式のフラグメンテーションのメカニズムはごく基本的なもので、正しく受信するには、3つ組そのものだけでなく、断片化されたKLVの3つ組のシーケンスの前後1パケットずつも、パケット損失なしで受信する必要があります。特定のKLVの3つ組そのものに、不完全な3つ組の扱い方についての推奨事項があり、それらを使ったり修復したりできる場合もあります。一般に、そのようなメカニズムを使うアプリケーションは、誤りに対して堅牢でなければならず、また、パケット損失率を低く抑え、KLVの3つ組を修復するために、アプリケーションレベルの繰り返し、RTPレベルの転送の堅牢性ツール、ネットワークレベルの要件を何らかの形で組み合わせて使わなければなりません。

An author should consider applying for a media subtype under the application media type (application/<foo>) when the payload format is of a generic nature or does not clearly match any of the media types described above (audio, video, or text). However, existing limitations in, for example, SDP, have resulted in generic mechanisms normally registered in all media types possibly having been associated with any existing media types in an RTP session.

ペイロード形式が汎用的な性質を持つ場合、または上記のメディアタイプ（audio、video、text）のいずれにも明確に当てはまらない場合、著者はapplicationメディアタイプの下のメディアサブタイプ（application/<foo>）を申請することを検討すべきです。しかし、たとえばSDPにおける既存の制限のために、汎用的なメカニズムは、RTPセッション内の既存のどのメディアタイプとも関連付けられる可能性があるので、通常はすべてのメディアタイプに登録されてきました。

7. Important Specification Sections

7. 仕様の重要なセクション

A number of sections in the payload format draft need special consideration. These include the Security Considerations and IANA Considerations sections that are required in all drafts. Payload formats are also strongly recommended to have the media format description and congestion control considerations. The included RTP payload format template (Appendix A) contains sample text for some of these sections.

ペイロード形式のドラフトのいくつかのセクションには、特別な考慮が必要です。これには、すべてのドラフトで必要とされる「セキュリティーに関する考慮事項」と「IANAに関する考慮事項」のセクションが含まれます。また、ペイロード形式には、メディア形式の説明と輻輳制御に関する考慮事項を含めることが強く推奨されます。含まれているRTPペイロード形式のテンプレート（付録A）には、これらのセクションの一部についてのサンプルテキストがあります。

7.1. Media Format Description

7.1. メディア形式の説明

The intention of this section is to enable reviewers and other readers to get an overview of the capabilities and major properties of the media format. It should be kept short and concise and is not a complete replacement for reading the media format specification.

このセクションの目的は、レビュアーやほかの読者がメディア形式の能力と主な特性の概要を把握できるようにすることです。短く簡潔に保つべきであり、メディア形式の仕様を読むことを完全に置き換えるものではありません。

The actual specification of the RTP payload format generally uses normative references to the codec format specification to define how codec data elements are included in the payload format. This normative reference can be to anything that have sufficient stability for a normative reference. There exist no formal requirement on the codec format specification being publicly available or free to access. However, it significantly helps in the review process if that specification is made available to any reviewer. There exist RTP payload format RFCs for open-source project specifications as well as an individual company's proprietary format, and a large variety of standards development organizations or industrial forums.

RTPペイロード形式の実際の仕様では、一般に、コーデックのデータ要素をペイロード形式にどのように含めるかを定義するために、コーデック形式の仕様を規範的に参照します。この規範的な参照の対象は、規範的な参照に足る十分な安定性を持つものであれば何でもかまいません。コーデック形式の仕様が公開されていることや、無料で入手できることについての正式な要件はありません。しかし、その仕様をどのレビュアーでも入手できるようにすれば、レビューのプロセスで大いに役立ちます。オープンソースのプロジェクトの仕様や、個々の企業の独自形式、そしてさまざまな標準化組織や業界フォーラムのためのRTPペイロード形式のRFCがあります。

7.2. Security Considerations

7.2. セキュリティーに関する考慮事項

All Internet-Drafts require a Security Considerations section. The Security Considerations section in an RTP payload format needs to concentrate on the security properties this particular format has. Some payload formats have very few specific issues or properties and can fully fall back on the security considerations for RTP in general and those of the profile being used. Because those documents are always applicable, a reference to these is normally placed first in the Security Considerations section. There is suggested text in the template below.

すべてのインターネットドラフトには、「セキュリティーに関する考慮事項」のセクションが必要です。RTPペイロード形式の「セキュリティーに関する考慮事項」のセクションでは、その特定の形式が持つセキュリティー特性に焦点を当てる必要があります。一部のペイロード形式には固有の問題や特性がほとんどなく、RTP全般と使用するプロファイルのセキュリティーに関する考慮事項に完全に委ねることができます。それらの文書は常に適用されるので、通常は「セキュリティーに関する考慮事項」のセクションの最初に、それらへの参照を置きます。以下のテンプレートに推奨されるテキストがあります。

The security issues of confidentiality, integrity protection, replay protection and source authentication are common issue for all payload formats. These should be solved by mechanisms external to the payload and do not need any special consideration in the payload format except for a reminder on these issues. There exist exceptions, such as payload formats that includes security functionality, like ISMAcrypt [ISMACrypt2]. Reasons for this division is further documented in "Securing the RTP Protocol Framework: Why RTP Does Not Mandate a Single Media Security Solution" [RFC7202]. For a survey of available mechanisms to meet these goals, review "Options for Securing RTP Sessions" [RFC7201]. This also includes key-exchange mechanisms for the security mechanisms, which can be both integrated or separate. The choice of key-management can have significant impact on the security properties of the RTP-based application. Suitable stock text to inform people about this is included in the template.

機密性、完全性保護、リプレイ保護、ソース認証というセキュリティーの問題は、すべてのペイロード形式に共通の問題です。これらはペイロードの外部のメカニズムによって解決されるべきであり、ペイロード形式では、これらの問題について注意を喚起する以外に特別な考慮は必要ありません。ISMAcrypt[ISMACrypt2]のように、セキュリティー機能を含むペイロード形式などの例外もあります。このように分担する理由は、「Securing the RTP Protocol Framework: Why RTP Does Not Mandate a Single Media Security Solution」[RFC7202]でさらに説明されています。これらの目標を満たすために利用できるメカニズムの調査については、「Options for Securing RTP Sessions」[RFC7201]を参照してください。これには、セキュリティーメカニズムのための鍵交換メカニズムも含まれており、それらは統合されている場合も別個の場合もあります。鍵管理の選択は、RTPに基づくアプリケーションのセキュリティー特性に大きな影響を与えることがあります。これについて人々に知らせるのに適した定型のテキストがテンプレートに含まれています。

Potential security issues with an RTP payload format and the media encoding that need to be considered if they are applicable:

RTPペイロード形式とメディアの符号化に関して、該当する場合に考慮する必要のある潜在的なセキュリティー上の問題は、次のとおりです。

  1. The decoding of the payload format or its media results in substantial non-uniformity, either in output or in complexity to perform the decoding operation. For example, a generic non-destructive compression algorithm may provide an output of almost an infinite size for a very limited input, thus consuming memory or storage space out of proportion with what the receiving application expected. Such inputs can cause some sort of disruption, i.e., a denial-of-service attack on the receiver side by preventing that host from performing usable work. Certain decoding operations may also vary in the amount of processing needed to perform those operations depending on the input. This may also be a security risk if it is possible to raise processing load significantly above nominal simply by designing a malicious input sequence. If such potential attacks exist, this must be made clear in the Security Considerations section to make implementers aware of the need to take precautions against such behavior.
  2. The inclusion of active content in the media format or its transport. "Active content" means scripts, etc., that allow an attacker to perform potentially arbitrary operations on the receiver. Most active contents has limited possibility to access the system or perform operations outside a protected sandbox. RFC 4855 [RFC4855] has a requirement that it be noted in the media types registration whether or not the payload format contains active content. If the payload format has active content, it is strongly recommended that references to any security model applicable for such content are provided. A boilerplate text for "no active content" is included in the template. This must be changed if the format actually carries active content.
  3. Some media formats allow for the carrying of "user data", or types of data which are not known at the time of the specification of the payload format. Such data may be a security risk and should be mentioned.
  4. Audio or Speech codecs supporting variable bitrate based on 'audio/speech' input or having discontinuous transmission support must consider the issues discussed in "Guidelines for the Use of Variable Bit Rate Audio with Secure RTP" [RFC6562].
  1. ペイロード形式またはそのメディアのデコードで、出力またはデコード処理を行う複雑さのいずれかに、大きな不均一性が生じる。たとえば、汎用的な可逆圧縮アルゴリズムは、ごく限られた入力に対してほぼ無限のサイズの出力を生成することがあり、受信側のアプリケーションが想定していたのとは不釣り合いなメモリーやストレージ領域を消費します。そのような入力は、ある種の妨害、すなわち受信側のホストが有用な作業を行えないようにするサービス拒否攻撃を引き起こすことがあります。また、特定のデコード処理では、入力に応じて、その処理を行うのに必要な処理量が変わることがあります。悪意のある入力シーケンスを設計するだけで処理負荷を通常よりも大幅に引き上げることができる場合、これもセキュリティー上のリスクになりえます。そのような潜在的な攻撃が存在する場合は、実装者がそのような振る舞いに対して予防措置を講じる必要があることを認識できるように、「セキュリティーに関する考慮事項」のセクションでそのことを明確にしなければなりません。
  2. メディア形式またはその転送にアクティブコンテンツが含まれる。「アクティブコンテンツ」とは、攻撃者が受信者上で潜在的に任意の操作を実行できるようにする、スクリプトなどを意味します。ほとんどのアクティブコンテンツは、システムにアクセスしたり、保護されたサンドボックスの外で操作を行ったりする可能性が限られています。RFC 4855[RFC4855]には、ペイロード形式がアクティブコンテンツを含むかどうかをメディアタイプの登録に記載するという要件があります。ペイロード形式がアクティブコンテンツを持つ場合は、そのようなコンテンツに適用されるセキュリティーモデルへの参照を提供することが強く推奨されます。「アクティブコンテンツなし」のための定型文がテンプレートに含まれています。形式が実際にアクティブコンテンツを運ぶ場合は、これを変更しなければなりません。
  3. 一部のメディア形式では、「ユーザーデータ」、つまりペイロード形式の仕様の時点ではわからない種類のデータを運ぶことができる。そのようなデータはセキュリティー上のリスクになる可能性があるので、言及すべきです。
  4. 「音声／会話音声」の入力に基づく可変ビットレートをサポートする、または不連続送信をサポートする音声や会話音声のコーデックは、「Guidelines for the Use of Variable Bit Rate Audio with Secure RTP」[RFC6562]で論じられている問題を考慮しなければなりません。

Suitable stock text for the Security Considerations section is provided in the template in Appendix A. However, authors do need to actively consider any security issues from the start. Failure to address these issues may block approval and publication.

「セキュリティーに関する考慮事項」のセクションに適した定型のテキストが、付録Aのテンプレートで提供されています。しかし、著者は最初から積極的にセキュリティー上の問題を検討する必要があります。これらの問題に対処しないと、承認や発行が妨げられることがあります。

7.3. Congestion Control

7.3. 輻輳制御

RTP and its profiles do discuss congestion control. There is ongoing work in the IETF with both a basic circuit-breaker mechanism [RFC8083] using basic RTCP messages intended to prevent persistent congestion and also work on more capable congestion avoidance / bitrate adaptation mechanism in the RMCAT WG.

RTPとそのプロファイルでは、輻輳制御について論じています。IETFでは、持続的な輻輳を防ぐことを意図した、基本的なRTCPメッセージを使う基本的なサーキットブレーカーのメカニズム[RFC8083]についての作業と、RMCAT WGでの、より高機能な輻輳回避／ビットレート適応のメカニズムについての作業の両方が進行中です。

Congestion control is an important issue in any usage in networks that are not dedicated. For that reason, it is recommended that all RTP payload format documents discuss the possibilities that exist to regulate the bitrate of the transmissions using the described RTP payload format. Some formats may have limited or step-wise regulation of bitrate. Such limiting factors should be discussed.

専用ではないネットワークでのあらゆる使用において、輻輳制御は重要な問題です。そのため、すべてのRTPペイロード形式の文書で、記述するRTPペイロード形式を使った送信のビットレートを調整するために存在する可能性について論じることが推奨されます。一部の形式では、ビットレートの調整が限られていたり、段階的であったりするかもしれません。そのような制約要因について論じるべきです。

7.4. IANA Considerations

7.4. IANAに関する考慮事項

Since all RTP payload formats contain a media type specification, they also need an IANA Considerations section. The media type name must be registered, and this is done by requesting that IANA register that media name. When that registration request is written, it shall also be requested that the media type is included under the "RTP Payload Format media types" subregistry of the RTP registry (http://www.iana.org/assignments/rtp-parameters).

すべてのRTPペイロード形式にはメディアタイプの仕様が含まれるので、IANAに関する考慮事項のセクションも必要です。メディアタイプ名は登録しなければならず、これはIANAにそのメディア名の登録を要求することで行います。その登録要求を書く際には、RTPレジストリーの「RTP Payload Format media types」サブレジストリー（http://www.iana.org/assignments/rtp-parameters）にそのメディアタイプを含めることも要求することになっています。

Parameters for the payload format need to be included in this registration and can be specified as required or optional ones. The format of these parameters should be such that they can be included in the SDP attribute "a=fmtp" string (see Section 6 [RFC4566]), which is the common mapping. Some parameters, such as "Channel" are normally mapped to the rtpmap attribute instead; see Section 3 of [RFC4855].

ペイロード形式のパラメーターは、この登録に含める必要があり、必須のものまたは省略可能なものとして指定できます。これらのパラメーターの形式は、一般的なマッピングであるSDP属性「a=fmtp」の文字列に含められるようなものにすべきです（[RFC4566]のセクション6を参照してください）。「Channel」などの一部のパラメーターは、通常は代わりにrtpmap属性にマッピングされます。[RFC4855]のセクション3を参照してください。

In addition to the above request for media type registration, some payload formats may have parameters where, in the future, new parameter values need to be added. In these cases, a registry for that parameter must be created. This is done by defining the registry in the IANA Considerations section. BCP 26 [BCP26] provides guidelines to specifying such registries. Care should be taken when defining the policy for new registrations.

上記のメディアタイプの登録の要求に加えて、一部のペイロード形式には、将来新しいパラメーター値を追加する必要があるパラメーターがあるかもしれません。そのような場合は、そのパラメーターのためのレジストリーを作成しなければなりません。これは、IANAに関する考慮事項のセクションでレジストリーを定義することによって行います。BCP 26[BCP26]は、そのようなレジストリーを規定するためのガイドラインを提供しています。新しい登録のためのポリシーを定義する際には注意すべきです。

Before specifying a new registry, it is worth checking the existing ones in the IANA "MIME Media Type Sub-Parameter Registries". For example, video formats that need a media parameter expressing color sub-sampling may be able to reuse those defined for 'video/raw' [RFC4175].

新しいレジストリーを規定する前に、IANAの「MIME Media Type Sub-Parameter Registries」にある既存のレジストリーを確認する価値があります。たとえば、色差サブサンプリングを表すメディアパラメーターを必要とする映像形式は、'video/raw'[RFC4175]のために定義されたものを再利用できるかもしれません。

8. Authoring Tools

8. 執筆ツール

This section provides information about some tools that may be used. Don't feel pressured to follow these recommendations. There exist a number of alternatives, including the ones listed at <http://tools.ietf.org>. But these suggestions are worth checking out before deciding that the grass is greener somewhere else.

このセクションでは、使えるいくつかのツールについての情報を提供します。これらの推奨に従わなければならないと気負う必要はありません。<http://tools.ietf.org>に挙げられているものを含め、代わりになるものはいくつもあります。しかし、隣の芝生のほうが青いと決めてしまう前に、これらの提案を確認してみる価値はあります。

Note that these options are related to the old text only RFC format, and do not cover tools for at the time of publication recently approved new RFC format, see [RFC7990].

これらの選択肢は古いテキストのみのRFC形式に関するものであり、発行時点で最近承認された新しいRFC形式のためのツールは扱っていないことに注意してください。[RFC7990]を参照してください。

8.1. Editing Tools

8.1. 編集ツール

There are many choices when it comes to tools to choose for authoring Internet-Drafts. However, in the end, they need to be able to produce a draft that conforms to the Internet-Draft requirements. If you don't have any previous experience with authoring Internet-Drafts, xml2rfc does have some advantages. It helps by creating a lot of the necessary boilerplate in accordance with the latest rules, thus reducing the effort. It also speeds up publication after approval as the RFC Editor can use the source XML document to produce the RFC more quickly.

インターネットドラフトを執筆するためのツールには、多くの選択肢があります。しかし、最終的には、インターネットドラフトの要件に準拠したドラフトを生成できる必要があります。インターネットドラフトを執筆した経験がない場合は、xml2rfcにはいくつかの利点があります。最新の規則に従って必要な定型文の多くを作成してくれるので、労力が減ります。また、RFCエディターがソースのXML文書を使ってRFCをより早く作成できるので、承認後の発行も早くなります。

Another common choice is to use Microsoft Word and a suitable template (see [RFC5385]) to produce the draft and print that to file using the generic text printer. It has some advantages when it comes to spell checking and change bars. However, Word may also produce some problems, like changing formatting, and inconsistent results between what one sees in the editor and in the generated text document, at least according to the author's personal experience.

もう1つのよくある選択肢は、Microsoft Wordと適切なテンプレート（[RFC5385]を参照してください）を使ってドラフトを作成し、汎用テキストプリンターを使ってファイルに出力することです。これには、スペルチェックと変更バーに関していくつかの利点があります。しかし、少なくとも著者の個人的な経験によれば、Wordは書式が変わってしまったり、エディターで見えるものと生成されたテキスト文書とで結果が一致しなかったりするといった問題を生じることもあります。

8.2. Verification Tools

8.2. 検証ツール

There are a few tools that are very good to know about when writing a draft. These help check and verify parts of one's work. These tools can be found at <http://tools.ietf.org>.

ドラフトを書く際に知っておくと非常によいツールがいくつかあります。これらは、自分の作業の一部を確認し、検証するのに役立ちます。これらのツールは<http://tools.ietf.org>にあります。

  • I-D Nits checker (https://tools.ietf.org/tools/idnits/). It checks that the boilerplate and some other things that are easily verifiable by machine are okay in your draft. Always use it before submitting a draft to avoid direct refusal in the submission step.
  • ABNF Parser and verification (https://tools.ietf.org/tools/bap/abnf.cgi). Checks that your ABNF parses correctly and warns about loose ends, like undefined symbols. However, the actual content can only be verified by humans knowing what it intends to describe.
  • RFC diff (https://tools.ietf.org/rfcdiff). A diff tool that is optimized for drafts and RFCs. For example, it does not point out that the footer and header have moved in relation to the text on every page.
  • I-D Nitsチェッカー（https://tools.ietf.org/tools/idnits/）。定型文や、機械で容易に検証できるそのほかのいくつかの事項について、ドラフトに問題がないかを確認します。提出の段階で即座に拒否されるのを避けるため、ドラフトを提出する前には必ず使ってください。
  • ABNFパーサーと検証（https://tools.ietf.org/tools/bap/abnf.cgi）。ABNFが正しく構文解析できるかを確認し、未定義の記号のような不備について警告します。ただし、実際の内容は、それが何を記述しようとしているかを知っている人間にしか検証できません。
  • RFC diff（https://tools.ietf.org/rfcdiff）。ドラフトとRFCに最適化された差分ツールです。たとえば、どのページでもフッターとヘッダーが本文に対して移動したことを指摘したりはしません。

9. Security Considerations

9. セキュリティーに関する考慮事項

As this is an Informational RFC about writing drafts that are intended to become RFCs, there are no direct security considerations. However, the document does discuss the writing of Security Considerations sections and what should be particularly considered when specifying RTP payload formats.

この文書は、RFCになることを意図したドラフトの書き方についての情報提供のRFCであるため、直接のセキュリティーに関する考慮事項はありません。ただし、この文書では、「セキュリティーに関する考慮事項」のセクションの書き方と、RTPペイロード形式を規定する際に特に考慮すべきことについて論じています。

A.13. Security Considerations

RTP packets using the payload format defined in this specification are subject to the security considerations discussed in the RTP specification [RFC3550] , and in any applicable RTP profile such as RTP/AVP [RFC3551], RTP/AVPF [RFC4585], RTP/SAVP [RFC3711], or RTP/SAVPF [RFC5124]. This responsibility lays on anyone using RTP in an application. They can find guidance on available security mechanisms and important considerations in "Options for Securing RTP Sessions" [RFC7201]. Applications SHOULD use one or more appropriate strong security mechanisms. The rest of this Security Considerations section discusses the security impacting properties of the payload format itself.

この仕様で定義されたペイロード形式を使うRTPパケットは、RTPの仕様[RFC3550]、および適用されるすべてのRTPプロファイル（RTP/AVP[RFC3551]、RTP/AVPF[RFC4585]、RTP/SAVP[RFC3711]、RTP/SAVPF[RFC5124]など）で論じられているセキュリティーに関する考慮事項の対象となります。しかし、「Securing the RTP Protocol Framework: Why RTP Does Not Mandate a Single Media Security Solution」[RFC7202]で論じられているように、RTP全般について機密性、完全性、ソースの真正性といった基本的なセキュリティーの目標を満たすためにどの解決策を使うかを論じたり義務づけたりするのは、RTPペイロード形式の責任ではありません。この責任は、アプリケーションでRTPを使うすべての者にあります。それらの者は、利用可能なセキュリティーメカニズムと重要な考慮事項についてのガイダンスを「Options for Securing RTP Sessions」[RFC7201]で見つけることができます。アプリケーションは、1つ以上の適切で強力なセキュリティーメカニズムを使うべきです（SHOULD）。この「セキュリティーに関する考慮事項」のセクションの残りでは、ペイロード形式そのもののセキュリティーに影響する特性について論じます。

This RTP payload format and its media decoder do not exhibit any significant non-uniformity in the receiver-side computational complexity for packet processing, and thus are unlikely to pose a denial-of-service threat due to the receipt of pathological data. Nor does the RTP payload format contain any active content.

このRTPペイロード形式とそのメディアデコーダーは、パケット処理に関する受信側の計算の複雑さに大きな不均一性を示さないため、異常なデータの受信によるサービス拒否の脅威となる可能性は低いです。また、このRTPペイロード形式はアクティブコンテンツを含みません。
