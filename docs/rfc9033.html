6TiSCH Minimal Scheduling Function (MSF)

RFC 9033

6TiSCH最小スケジューリング関数（MSF）

Abstract

概要

This specification defines the "IPv6 over the TSCH mode of IEEE 802.15.4" (6TiSCH) Minimal Scheduling Function (MSF). This Scheduling Function describes both the behavior of a node when joining the network and how the communication schedule is managed in a distributed fashion. MSF is built upon the 6TiSCH Operation Sublayer Protocol (6P) and the minimal security framework for 6TiSCH.

この仕様は、「IEEE 802.15.4のTSCHモード上のIPv6」（6TiSCH）の最小スケジューリング関数（Minimal Scheduling Function、MSF）を定義します。 このスケジューリング関数は、ネットワークに参加する際のノードの振る舞いと、 通信スケジュールを分散型の方法で管理する方法の両方を記述します。 MSFは、6TiSCH操作サブレイヤープロトコル（6P）と、 6TiSCHの最小限のセキュリティーフレームワークの上に構築されています。

1. Introduction

1. はじめに

The 6TiSCH Minimal Scheduling Function (MSF), defined in this specification, is a 6TiSCH Scheduling Function (SF). The role of an SF is entirely defined in [RFC8480]. This specification complements [RFC8480] by providing the rules of when to add and delete cells in the communication schedule. This specification satisfies all the requirements for an SF listed in Section 4.2 of [RFC8480].

この仕様で定義する6TiSCH最小スケジューリング関数（MSF）は、6TiSCHのスケジューリング関数（SF）の1つです。 SFの役割は、すべて[RFC8480]で定義されています。 この仕様は、通信スケジュールにいつセルを追加・削除するかの規則を提供することで、[RFC8480]を補完します。 この仕様は、[RFC8480]のSection 4.2に列挙されているSFに対するすべての要件を満たします。

MSF builds on top of the following specifications: "Minimal IPv6 over the TSCH Mode of IEEE 802.15.4e (6TiSCH) Configuration" [RFC8180], "6TiSCH Operation Sublayer (6top) Protocol (6P)" [RFC8480], and "Constrained Join Protocol (CoJP) for 6TiSCH" [RFC9031].

MSFは、次の仕様の上に構築されています： 「Minimal IPv6 over the TSCH Mode of IEEE 802.15.4e (6TiSCH) Configuration」[RFC8180]、 「6TiSCH Operation Sublayer (6top) Protocol (6P)」[RFC8480]、 「Constrained Join Protocol (CoJP) for 6TiSCH」[RFC9031]。

MSF defines both the behavior of a node when joining the network, and how the communication schedule is managed in a distributed fashion. When a node running MSF boots up, it joins the network by following the six steps described in Section 4. The end state of the join process is that the node is synchronized to the network, has mutually authenticated with the network, has identified a routing parent, and has scheduled one negotiated Tx cell (defined in Section 5.1) to/from its routing parent. After the join process, the node can continuously add, delete, and relocate cells as described in Section 5. It does so for three reasons: to match the link-layer resources to the traffic, to handle changing parent, and to handle a schedule collision.

MSFは、ネットワークに参加する際のノードの振る舞いと、通信スケジュールを分散型の方法で管理する方法の両方を定義します。 MSFを実行するノードは、起動すると、Section 4で説明する6つのステップに従ってネットワークに参加します。 参加プロセスの終了状態では、ノードはネットワークに同期しており、ネットワークと相互認証しており、ルーティングの親を特定しており、ルーティングの親との間でネゴシエートされたTxセル（Section 5.1で定義）を1つスケジュールしています。 参加プロセスの後、ノードはSection 5で説明するように、セルの追加、削除、再配置を継続的に行えます。 ノードがこれを行う理由は3つあります。リンク層の資源をトラフィックに合わせるため、親の変更に対処するため、スケジュールの衝突に対処するためです。

MSF works closely with the IPv6 Routing Protocol for Low-Power and Lossy Networks (RPL), specifically the routing parent defined in [RFC6550]. This specification only describes how MSF works with the routing parent; this parent is referred to as the "selected parent". The activity of MSF towards the single routing parent is called a "MSF session". Though the performance of MSF is evaluated only when the "selected parent" represents the node's preferred parent, there should be no restrictions to use multiple MSF sessions, one per parent. The distribution of traffic over multiple parents is a routing decision that is out of scope for MSF.

MSFは、低電力・高損失ネットワークのためのIPv6ルーティングプロトコル（RPL）、特に[RFC6550]で定義されているルーティングの親と密接に連携して動作します。 この仕様は、MSFがルーティングの親とどのように連携するかだけを説明します。この親を「選択された親（selected parent）」と呼びます。 単一のルーティングの親に対するMSFの活動を「MSFセッション」と呼びます。 MSFの性能は「選択された親」がノードの優先親（preferred parent）である場合についてのみ評価されていますが、親ごとに1つずつ、複数のMSFセッションを使うことに制限はないはずです。 複数の親にトラフィックをどのように分散させるかはルーティングの決定であり、MSFの範囲外です。

MSF is designed to operate in a wide range of application domains. It is optimized for applications with regular upstream traffic, from the nodes to the Destination-Oriented Directed Acyclic Graph (DODAG) root [RFC6550].

MSFは、幅広いアプリケーション領域で動作するように設計されています。 MSFは、ノードから宛先指向有向非巡回グラフ（Destination-Oriented Directed Acyclic Graph、DODAG）のルート[RFC6550]に向かう、定期的な上り方向のトラフィックを持つアプリケーション向けに最適化されています。

This specification follows the recommended structure of an SF specification, given in Appendix A of [RFC8480], with the following adaptations:

この仕様は、[RFC8480]のAppendix Aに示されているSF仕様の推奨構成に従っていますが、次の変更を加えています：

  • We have reordered some sections, in particular to have the section on the node behavior at boot (Section 4) appear early in this specification.
  • We added sections on the interface to the minimal 6TiSCH configuration (Section 2), the use of the SIGNAL command (Section 6), the MSF constants (Section 14), and the MSF statistics (Section 15).
  • いくつかのセクションの順序を入れ替えました。特に、起動時のノードの振る舞いに関するセクション（Section 4）がこの仕様の前のほうに現れるようにしました。
  • 最小限の6TiSCH構成とのインターフェイス（Section 2）、SIGNALコマンドの使用（Section 6）、MSFの定数（Section 14）、MSFの統計情報（Section 15）に関するセクションを追加しました。

2. Interface to the Minimal 6TiSCH Configuration

2. 最小限の6TiSCH構成とのインターフェイス

In a Time-Slotted Channel Hopping (TSCH) network, time is sliced up into time slots. The time slots are grouped as one or multiple slotframes that repeat over time. The TSCH schedule instructs a node what to do at each time slot, such as transmit, receive, or sleep [RFC7554]. For time slots for transmitting or receiving, a channel is assigned to the time slot. The tuple (slot, channel) is indicated as a cell of the TSCH schedule. MSF is one of the policies defining how to manage the TSCH schedule.

時間スロットチャネルホッピング（TSCH）ネットワークでは、時間はタイムスロットに分割されます。 タイムスロットは、時間とともに繰り返す1つまたは複数のスロットフレームとしてグループ化されます。 TSCHスケジュールは、送信、受信、スリープなど、各タイムスロットで何をすべきかをノードに指示します[RFC7554]。 送信または受信のためのタイムスロットには、チャネルが割り当てられます。 組（スロット、チャネル）を、TSCHスケジュールのセルとして表します。 MSFは、TSCHスケジュールをどのように管理するかを定義するポリシーの1つです。

A node implementing MSF SHOULD implement the minimal 6TiSCH configuration [RFC8180], which defines the "minimal cell", a single shared cell providing minimal connectivity between the nodes in the network. The MSF implementation provided in this specification is based on the implementation of the minimal 6TiSCH configuration. However, an implementor MAY implement MSF based on other specifications as long as the specification defines a way to advertise the Enhanced Beacons (EBs) and DODAG Information Objects (DIOs) among the network.

MSFを実装するノードは、最小限の6TiSCH構成[RFC8180]を実装すべきです（SHOULD）。最小限の6TiSCH構成は、ネットワーク内のノード間の最小限の接続性を提供する単一の共有セルである「最小セル（minimal cell）」を定義しています。 この仕様で示すMSFの実装は、最小限の6TiSCH構成の実装に基づいています。 ただし、拡張ビーコン（Enhanced Beacon、EB）とDODAG情報オブジェクト（DODAG Information Object、DIO）をネットワーク内で広告する方法を定義している仕様であれば、実装者は他の仕様に基づいてMSFを実装してもよいです（MAY）。

MSF uses the minimal cell for broadcast frames such as Enhanced Beacons (EBs) [IEEE802154] and broadcast DODAG Information Objects (DIOs) [RFC6550]. Cells scheduled by MSF are meant to be used only for unicast frames.

MSFは、拡張ビーコン（EB）[IEEE802154]やブロードキャストのDODAG情報オブジェクト（DIO）[RFC6550]などのブロードキャストフレームに最小セルを使います。 MSFがスケジュールするセルは、ユニキャストフレームにのみ使うことを意図しています。

To ensure there is enough bandwidth available on the minimal cell, a node implementing MSF SHOULD enforce some rules for limiting the traffic of broadcast frames. For example, the overall broadcast traffic among the node and its neighbors SHOULD NOT exceed one-third of the bandwidth of minimal cell. One of the algorithms that fulfills this requirement is the Trickle timer defined in [RFC6206], which is applied to DIO messages [RFC6550]. However, any such algorithm of limiting the broadcast traffic to meet those rules is implementation-specific and is out of the scope of MSF.

最小セル上で十分な帯域幅を確保するために、MSFを実装するノードは、ブロードキャストフレームのトラフィックを制限するための何らかの規則を適用すべきです（SHOULD）。 たとえば、ノードとその近隣の間の全体的なブロードキャストトラフィックは、最小セルの帯域幅の3分の1を超えるべきではありません（SHOULD NOT）。 この要件を満たすアルゴリズムの1つは、[RFC6206]で定義されているTrickleタイマーであり、これはDIOメッセージ[RFC6550]に適用されます。 ただし、これらの規則を満たすようにブロードキャストトラフィックを制限するそのようなアルゴリズムはいずれも実装固有であり、MSFの範囲外です。

Three slotframes are used in MSF. MSF schedules autonomous cells at Slotframe 1 (Section 3) and 6P negotiated cells at Slotframe 2 (Section 5), while Slotframe 0 is used for the bootstrap traffic as defined in the minimal 6TiSCH configuration. The same slotframe length for Slotframe 0, 1, and 2 is RECOMMENDED. Thus it is possible to avoid the scheduling collision between the autonomous cells and 6P negotiated cells (Section 3). The default slotframe length (SLOTFRAME_LENGTH) is RECOMMENDED for Slotframe 0, 1, and 2, although any value can be advertised in the EBs.

MSFでは3つのスロットフレームを使います。 MSFは、スロットフレーム1に自律セル（Section 3）を、スロットフレーム2に6Pでネゴシエートされたセル（Section 5）をスケジュールします。一方、スロットフレーム0は、最小限の6TiSCH構成で定義されているとおり、ブートストラップのトラフィックに使われます。 スロットフレーム0、1、2には同じスロットフレーム長を使うことが推奨されます（RECOMMENDED）。 そうすることで、自律セルと6Pでネゴシエートされたセルの間のスケジューリングの衝突を回避できます（Section 3）。 EBではどのような値でも広告できますが、スロットフレーム0、1、2にはデフォルトのスロットフレーム長（SLOTFRAME_LENGTH）を使うことが推奨されます（RECOMMENDED）。

3. Autonomous Cells

3. 自律セル

MSF nodes initialize Slotframe 1 with a set of default cells for unicast communication with their neighbors. These cells are called "autonomous cells", because they are maintained autonomously by each node without negotiation through 6P. Cells scheduled by 6P Transaction are called "negotiated cells", which are reserved on Slotframe 2. How to schedule negotiated cells is detailed in Section 5. There are two types of autonomous cells:

MSFノードは、近隣とのユニキャスト通信のためのデフォルトのセルの集合でスロットフレーム1を初期化します。 これらのセルは、6Pによるネゴシエーションなしに各ノードが自律的に維持するため、「自律セル（autonomous cell）」と呼ばれます。 6Pトランザクションによってスケジュールされるセルは「ネゴシエートされたセル（negotiated cell）」と呼ばれ、スロットフレーム2上に予約されます。 ネゴシエートされたセルをスケジュールする方法は、Section 5で詳しく説明します。 自律セルには2つのタイプがあります：

Autonomous Rx Cell (AutoRxCell):
One cell at a [slotOffset,channelOffset] computed as a hash of the 64-bit Extended Unique Identifier (EUI-64) of the node itself (detailed next). Its cell options bits are assigned as TX=0, RX=1, SHARED=0.
Autonomous Tx Cell (AutoTxCell):
One cell at a [slotOffset,channelOffset] computed as a hash of the Layer 2 EUI-64 destination address in the unicast frame to be transmitted (detailed in Section 4.4). Its cell options bits are assigned as TX=1, RX=0, SHARED=1.
自律Rxセル（Autonomous Rx Cell、AutoRxCell）：
ノード自身の64ビット拡張一意識別子（64-bit Extended Unique Identifier、EUI-64）のハッシュとして計算される[slotOffset,channelOffset]にある1つのセルです（詳細は次に示します）。 このセルのセルオプションのビットは、TX=0、RX=1、SHARED=0として割り当てられます。
自律Txセル（Autonomous Tx Cell、AutoTxCell）：
送信するユニキャストフレームのレイヤー2のEUI-64宛先アドレスのハッシュとして計算される[slotOffset,channelOffset]にある1つのセルです（詳細はSection 4.4で示します）。 このセルのセルオプションのビットは、TX=1、RX=0、SHARED=1として割り当てられます。

To compute a [slotOffset,channelOffset] from an EUI-64 address, nodes MUST use the hash function SAX as defined in Section 2 of [SAX-DASFAA] with consistent input parameters, for example, those defined in Appendix A. The coordinates are computed to distribute the cells across all channel offsets, and all but the first slot offset of Slotframe 1. The first time offset is skipped to avoid colliding with the minimal cell in Slotframe 0. The slot coordinates derived from a given EUI-64 address are computed as follows:

EUI-64アドレスから[slotOffset,channelOffset]を計算するために、ノードは、一貫した入力パラメーター（たとえばAppendix Aで定義されているもの）を用いて、[SAX-DASFAA]のセクション2で定義されているハッシュ関数SAXを使わなければなりません（MUST）。 座標は、すべてのチャネルオフセットと、スロットフレーム1の最初のスロットオフセットを除くすべてのスロットオフセットにセルを分散させるように計算されます。 最初のタイムオフセットは、スロットフレーム0の最小セルとの衝突を避けるためにスキップされます。 特定のEUI-64アドレスから導出されるスロットの座標は、次のように計算されます：

slotOffset(MAC) = 1 + hash(EUI64, length(Slotframe_1) - 1)

slotOffset(MAC) = 1 + hash(EUI64, length(Slotframe_1) - 1)

channelOffset(MAC) = hash(EUI64, NUM_CH_OFFSET)

channelOffset(MAC) = hash(EUI64, NUM_CH_OFFSET)

The second input parameter defines the maximum return value of the hash function. Other optional parameters defined in SAX determine the performance of SAX hash function. Those parameters could be broadcast in an EB frame or preconfigured. For interoperability purposes, Appendix A provides the reference values of those parameters.

2番目の入力パラメーターは、ハッシュ関数の戻り値の最大値を定義します。 SAXで定義されている他の任意のパラメーターは、SAXハッシュ関数の性能を決定します。 これらのパラメーターは、EBフレームでブロードキャストすることも、事前に設定することもできます。 相互運用性のために、Appendix Aではこれらのパラメーターの参照値を示しています。

AutoTxCell is not permanently installed in the schedule but is added or deleted on demand when there is a frame to be sent. Throughout the network lifetime, nodes maintain the autonomous cells as follows:

AutoTxCellはスケジュールに恒久的にインストールされるのではなく、送信するフレームがあるときにオンデマンドで追加または削除されます。 ネットワークの有効期間を通じて、ノードは次のように自律セルを維持します：

  • Add an AutoTxCell to the Layer 2 destination address, which is indicated in a frame when there is no 6P negotiated Tx cell in the schedule for that frame to transmit.

  • Remove an AutoTxCell when:

    • there is no frame to transmit on that cell, or
    • there is at least one 6P negotiated Tx cell in the schedule for the frames to transmit.
  • フレームで示されるレイヤー2の宛先アドレスへのAutoTxCellを、そのフレームを送信するための6PでネゴシエートされたTxセルがスケジュールにない場合に追加します。

  • 次の場合にAutoTxCellを削除します：

    • そのセルで送信するフレームがない場合
    • 送信するフレームのための6PでネゴシエートされたTxセルが、スケジュールに少なくとも1つある場合

The AutoRxCell MUST always remain scheduled after synchronization. 6P CLEAR MUST NOT erase any autonomous cells.

AutoRxCellは、同期後は常にスケジュールされたままでなければなりません（MUST）。 6P CLEARは、いかなる自律セルも消去してはなりません（MUST NOT）。

Because of hash collisions, there will be cases that the AutoTxCell and AutoRxCell are scheduled at the same slot offset and/or channel offset. In such cases, AutoTxCell always take precedence over AutoRxCell. Notice AutoTxCell is a shared type cell that applies a back-off mechanism. When the AutoTxCell and AutoRxCell collide, AutoTxCell takes precedence if there is a packet to transmit. When in a back-off period, AutoRxCell is used. In the case of conflict with a negotiated cell, autonomous cells take precedence over negotiated cells, which is stated in [IEEE802154]. However, when the Slotframe 0, 1, and 2 use the same length value, it is possible for a negotiated cell to avoid the collision with AutoRxCell. Hence, the same slotframe length for Slotframe 0, 1, and 2 is RECOMMENDED.

ハッシュの衝突のため、AutoTxCellとAutoRxCellが同じスロットオフセットまたはチャネルオフセット（あるいはその両方）にスケジュールされる場合があります。 そのような場合、AutoTxCellが常にAutoRxCellより優先されます。 AutoTxCellは、バックオフメカニズムを適用する共有タイプのセルであることに注意してください。 AutoTxCellとAutoRxCellが衝突した場合、送信するパケットがあればAutoTxCellが優先されます。 バックオフ期間中は、AutoRxCellが使われます。 ネゴシエートされたセルと競合する場合は、[IEEE802154]に記載されているとおり、自律セルがネゴシエートされたセルより優先されます。 ただし、スロットフレーム0、1、2が同じ長さの値を使う場合、ネゴシエートされたセルはAutoRxCellとの衝突を回避できます。 したがって、スロットフレーム0、1、2には同じスロットフレーム長を使うことが推奨されます（RECOMMENDED）。

4. Node Behavior at Boot

4. 起動時のノードの振る舞い

This section details the behavior the node SHOULD follow from the moment it is switched on until it has successfully joined the network. Alternative behaviors may be involved, for example, when alternative security solutions are used for the network. Section 4.1 details the start state; Section 4.8 details the end state. The other sections detail the six steps of the joining process. We use the term "pledge" and "joined node", as defined in [RFC9031].

このセクションでは、ノードが電源を投入されてからネットワークへの参加に成功するまでの間の振る舞いを詳しく説明します。ノードはこの振る舞いに従うべきです（SHOULD）。 たとえば、ネットワークで代替のセキュリティーソリューションが使われる場合には、代替の振る舞いが関与することもあります。 Section 4.1では開始状態を、Section 4.8では終了状態を詳しく説明します。 その他のセクションでは、参加プロセスの6つのステップを詳しく説明します。 [RFC9031]で定義されている用語「プレッジ（pledge）」と「参加済みノード（joined node）」を使います。

4.1. Start State

4.1. 開始状態

A node implementing MSF SHOULD implement the Constrained Join Protocol (CoJP) for 6TiSCH [RFC9031]. As a corollary, this means that a pledge, before being switched on, may be preconfigured with the Pre-Shared Key (PSK) for joining, as well as any other configuration detailed in [RFC9031]. This is not necessary if the node implements a security solution that is not based on PSKs, such as [ZEROTOUCH-JOIN].

MSFを実装するノードは、6TiSCHのための制約付き参加プロトコル（CoJP）[RFC9031]を実装すべきです（SHOULD）。 この帰結として、プレッジには、電源を投入される前に、参加のための事前共有鍵（PSK）と、[RFC9031]で詳しく説明されているその他の設定が事前に設定されている場合があります。 ノードが、[ZEROTOUCH-JOIN]のような、PSKに基づかないセキュリティーソリューションを実装している場合は、これは必要ありません。

4.2. Step 1 - Choosing Frequency

4.2. ステップ1 - 周波数の選択

When switched on, the pledge randomly chooses a frequency from the channels through which the network cycles and starts listening for EBs on that frequency.

電源を投入されると、プレッジは、ネットワークが巡回するチャネルの中から周波数をランダムに選択し、その周波数でEBの受信待ちを開始します。

4.3. Step 2 - Receiving EBs

4.3. ステップ2 - EBの受信

Upon receiving the first EB, the pledge continues listening for additional EBs to learn:

最初のEBを受信すると、プレッジは、次のことを知るために追加のEBの受信待ちを続けます：

  1. the number of neighbors N in its vicinity, and
  2. which neighbor to choose as a Join Proxy (JP) for the joining process.
  1. 周辺にいる近隣の数N
  2. 参加プロセスのための参加プロキシー（JP）としてどの近隣を選ぶか

After having received the first EB, a node MAY keep listening for at most MAX_EB_DELAY seconds or until it has received EBs from NUM_NEIGHBOURS_TO_WAIT distinct neighbors. This behavior is defined in [RFC8180].

最初のEBを受信した後、ノードは、最大MAX_EB_DELAY秒間、またはNUM_NEIGHBOURS_TO_WAIT個の異なる近隣からEBを受信するまで、受信待ちを続けてもよいです（MAY）。 この振る舞いは[RFC8180]で定義されています。

During this step, the pledge only gets synchronized when it has received enough EB from the network it wishes to join. How to decide whether an EB originates from a node from the network it wishes to join is implementation-specific, but MAY involve filtering EBs by the PANID field it contains, the presence and contents of the Information Element (IE) defined in [RFC9032], or the key used to authenticate it.

このステップの間、プレッジは、参加を希望するネットワークから十分なEBを受信した場合にのみ同期します。 EBが参加を希望するネットワークのノードから発信されたものかどうかをどのように判断するかは実装固有ですが、EBに含まれるPANIDフィールド、[RFC9032]で定義されている情報要素（IE）の有無と内容、またはEBの認証に使われる鍵によってEBをフィルタリングすることが含まれる場合があります（MAY）。

The decision of which neighbor to use as a JP is implementation-specific and is discussed in [RFC9031].

どの近隣をJPとして使うかの決定は実装固有であり、[RFC9031]で議論されています。

4.4. Step 3 - Setting up Autonomous Cells for the Join Process

4.4. ステップ3 - 参加プロセスのための自律セルの設定

After having selected a JP, a node generates a Join Request and installs an AutoTxCell to the JP. The Join Request is then sent by the pledge to its selected JP over the AutoTxCell. The AutoTxCell is removed by the pledge when the Join Request is sent out. The JP receives the Join Request through its AutoRxCell. Then it forwards the Join Request to the Join Registrar/Coordinator (JRC), possibly over multiple hops, over the 6P negotiated Tx cells. Similarly, the JRC sends the Join Response to the JP, possibly over multiple hops, over AutoTxCells or the 6P negotiated Tx cells. When the JP receives the Join Response from the JRC, it installs an AutoTxCell to the pledge and sends that Join Response to the pledge over AutoTxCell. The AutoTxCell is removed by the JP when the Join Response is sent out. The pledge receives the Join Response from its AutoRxCell, thereby learns the keying material used in the network, as well as other configuration settings, and becomes a "joined node".

JPを選択した後、ノードは参加リクエスト（Join Request）を生成し、JPへのAutoTxCellをインストールします。 次に、プレッジは選択したJPに、AutoTxCellを介して参加リクエストを送信します。 参加リクエストが送出されると、プレッジはAutoTxCellを削除します。 JPは、自身のAutoRxCellを通じて参加リクエストを受信します。 次に、JPは参加リクエストを、6PでネゴシエートされたTxセルを介して、場合によっては複数のホップを経由して、参加レジストラー／コーディネーター（JRC）に転送します。 同様に、JRCは参加レスポンス（Join Response）を、AutoTxCellまたは6PでネゴシエートされたTxセルを介して、場合によっては複数のホップを経由して、JPに送信します。 JPは、JRCから参加レスポンスを受信すると、プレッジへのAutoTxCellをインストールし、AutoTxCellを介してその参加レスポンスをプレッジに送信します。 参加レスポンスが送出されると、JPはAutoTxCellを削除します。 プレッジは、自身のAutoRxCellから参加レスポンスを受信し、それによってネットワークで使われる鍵素材やその他の設定を知り、「参加済みノード」になります。

When 6LoWPAN Neighbor Discovery (ND) [RFC8505] is implemented, the unicast packets used by ND are sent on the AutoTxCell. The specific process how the ND works during the join process is detailed in [RFC9030].

6LoWPAN近隣探索（ND）[RFC8505]が実装されている場合、NDが使うユニキャストパケットはAutoTxCellで送信されます。 参加プロセス中にNDがどのように動作するかの具体的なプロセスは、[RFC9030]で詳しく説明されています。

4.5. Step 4 - Acquiring a RPL Rank

4.5. ステップ4 - RPLのランクの取得

Per [RFC6550], the joined node receives DIOs, computes its own Rank, and selects a routing parent.

[RFC6550]に従って、参加済みノードは、DIOを受信し、自身のランクを計算し、ルーティングの親を選択します。

4.6. Step 5 - Setting up First Tx Negotiated Cells

4.6. ステップ5 - 最初のネゴシエートされたTxセルの設定

Once it has selected a routing parent, the joined node MUST generate a 6P ADD Request and install an AutoTxCell to that parent. The 6P ADD Request is sent out through the AutoTxCell, containing the following fields:

ルーティングの親を選択したら、参加済みノードは6P ADDリクエストを生成し、その親へのAutoTxCellをインストールしなければなりません（MUST）。 6P ADDリクエストはAutoTxCellを通じて送出され、次のフィールドを含みます：

CellOptions:
Set to TX=1, RX=0, SHARED=0.
NumCells:
Set to 1.
CellList:
At least 5 cells, chosen according to Section 8.
CellOptions:
TX=1、RX=0、SHARED=0に設定します。
NumCells:
1に設定します。
CellList:
Section 8に従って選んだ、少なくとも5つのセルです。

The joined node removes the AutoTxCell to the selected parent when the 6P Request is sent out. That parent receives the 6P ADD Request from its AutoRxCell. Then it generates a 6P ADD Response and installs an AutoTxCell to the joined node. When the parent sends out the 6P ADD Response, it MUST remove that AutoTxCell. The joined node receives the 6P ADD Response from its AutoRxCell and completes the 6P Transaction. In the case that the 6P ADD transaction failed, the node MUST issue another 6P ADD Request and repeat until the Tx cell is installed to the parent.

6Pリクエストが送出されると、参加済みノードは選択された親へのAutoTxCellを削除します。 その親は、自身のAutoRxCellから6P ADDリクエストを受信します。 次に、親は6P ADDレスポンスを生成し、参加済みノードへのAutoTxCellをインストールします。 親は、6P ADDレスポンスを送出したら、そのAutoTxCellを削除しなければなりません（MUST）。 参加済みノードは、自身のAutoRxCellから6P ADDレスポンスを受信し、6Pトランザクションを完了します。 6P ADDトランザクションが失敗した場合、ノードは別の6P ADDリクエストを発行しなければなりません（MUST）。そして、親へのTxセルがインストールされるまでこれを繰り返します。

4.7. Step 6 - Sending EBs and DIOs

4.7. ステップ6 - EBとDIOの送信

The node starts sending EBs and DIOs on the minimal cell, while following the transmit rules for broadcast frames from Section 2.

ノードは、Section 2のブロードキャストフレームの送信規則に従いながら、最小セル上でEBとDIOの送信を開始します。

4.8. End State

4.8. 終了状態

At the end state of the joining process, a new node:

参加プロセスの終了状態において、新しいノードは：

  • is synchronized to the network,
  • is using the link-layer keying material it learned through the secure joining process,
  • has selected one neighbor as its routing parent,
  • has one AutoRxCell,
  • has one negotiated Tx cell to the selected parent,
  • starts to send DIOs, potentially serving as a router for other nodes' traffic, and
  • starts to send EBs, potentially serving as a JP for new pledges.
  • ネットワークに同期しています。
  • 安全な参加プロセスを通じて知ったリンク層の鍵素材を使っています。
  • 1つの近隣をルーティングの親として選択しています。
  • 1つのAutoRxCellを持っています。
  • 選択された親へのネゴシエートされたTxセルを1つ持っています。
  • DIOの送信を開始しており、他のノードのトラフィックのためのルーターとして機能する可能性があります。
  • EBの送信を開始しており、新しいプレッジのためのJPとして機能する可能性があります。

5. Rules for Adding and Deleting Cells

5. セルの追加と削除の規則

Once a node has joined the 6TiSCH network, it adds/deletes/relocates cells with the selected parent for three reasons:

ノードは、6TiSCHネットワークに参加すると、次の3つの理由で、選択された親とのセルを追加／削除／再配置します：

  • to match the link-layer resources to the traffic between the node and the selected parent (Section 5.1),
  • to handle switching the parent (Section 5.2), or
  • to handle a schedule collision (Section 5.3).
  • ノードと選択された親との間のトラフィックにリンク層の資源を合わせるため（Section 5.1）
  • 親の切り替えに対処するため（Section 5.2）
  • スケジュールの衝突に対処するため（Section 5.3）

These cells are called "negotiated cells" as they are scheduled through 6P and negotiated with the node's parent. Without specific declaration, all cells mentioned in this section are negotiated cells, and they are installed at Slotframe 2.

これらのセルは、6Pを通じてスケジュールされ、ノードの親とネゴシエートされるため、「ネゴシエートされたセル」と呼ばれます。 特に明記しない限り、このセクションで言及するセルはすべてネゴシエートされたセルであり、スロットフレーム2にインストールされます。

5.1. Adapting to Traffic

5.1. トラフィックへの適応

A node implementing MSF MUST implement the behavior described in this section.

MSFを実装するノードは、このセクションで説明する振る舞いを実装しなければなりません（MUST）。

The goal of MSF is to manage the communication schedule in the 6TiSCH schedule in a distributed manner. For a node, this translates into monitoring the current usage of the cells it has to one of its neighbors, in most cases to the selected parent.

MSFの目的は、6TiSCHスケジュール内の通信スケジュールを分散型の方法で管理することです。 ノードにとって、これは、近隣の1つ（ほとんどの場合は選択された親）に対して持っているセルの現在の使用状況を監視することを意味します。

  • If the node determines that the number of link-layer frames it is attempting to exchange with the selected parent per unit of time is larger than the capacity offered by the TSCH negotiated cells it has scheduled with it, the node issues a 6P ADD command to that parent to add cells to the TSCH schedule.
  • If the traffic is lower than the capacity, the node issues a 6P DELETE command to that parent to delete cells from the TSCH schedule.
  • 選択された親と単位時間あたりに交換しようとしているリンク層フレームの数が、その親とスケジュールしているTSCHのネゴシエートされたセルが提供する容量を超えているとノードが判断した場合、ノードはTSCHスケジュールにセルを追加するために、その親に6P ADDコマンドを発行します。
  • トラフィックが容量より少ない場合、ノードはTSCHスケジュールからセルを削除するために、その親に6P DELETEコマンドを発行します。

The node MUST maintain two separate pairs of the following counters for the selected parent: one for the negotiated Tx cells to that parent and one for the negotiated Rx cells to that parent.

ノードは、選択された親について、次のカウンターの組を2つ別々に維持しなければなりません（MUST）。1つはその親へのネゴシエートされたTxセル用、もう1つはその親へのネゴシエートされたRxセル用です。

NumCellsElapsed:
Counts the number of negotiated cells that have elapsed since the counter was initialized. This counter is initialized at 0. When the current cell is declared as a negotiated cell to the selected parent, NumCellsElapsed is incremented by exactly 1, regardless of whether the cell is used to transmit or receive a frame.
NumCellsUsed:

Counts the number of negotiated cells that have been used. This counter is initialized at 0. NumCellsUsed is incremented by exactly 1 when, during a negotiated cell to the selected parent, either of the following happens:

  • The node sends a frame to the parent. The counter increments regardless of whether a link-layer acknowledgment was received or not.
  • The node receives a valid frame from the parent. The counter increments only when a valid frame per [IEEE802154] is received by the node from its parent.
NumCellsElapsed:
カウンターが初期化されてから経過したネゴシエートされたセルの数を数えます。 このカウンターは0に初期化されます。 現在のセルが選択された親へのネゴシエートされたセルとして宣言されている場合、そのセルがフレームの送信と受信のどちらに使われたかにかかわらず、NumCellsElapsedはちょうど1だけ増加します。
NumCellsUsed:

使用されたネゴシエートされたセルの数を数えます。 このカウンターは0に初期化されます。 選択された親へのネゴシエートされたセルの間に次のいずれかが発生すると、NumCellsUsedはちょうど1だけ増加します：

  • ノードが親にフレームを送信した場合。 リンク層の確認応答を受信したかどうかにかかわらず、カウンターは増加します。
  • ノードが親から有効なフレームを受信した場合。 カウンターは、[IEEE802154]に従った有効なフレームをノードが親から受信した場合にのみ増加します。

The cell option of cells listed in CellList in a 6P Request frame SHOULD be either (Tx=1, Rx=0) only or (Tx=0, Rx=1) only. Both NumCellsElapsed and NumCellsUsed counters can be used for both types of negotiated cells.

6Pリクエストフレーム内のCellListに列挙されるセルのセルオプションは、(Tx=1, Rx=0)のみ、または(Tx=0, Rx=1)のみのいずれかであるべきです（SHOULD）。 NumCellsElapsedとNumCellsUsedの両カウンターは、どちらのタイプのネゴシエートされたセルにも使えます。

As there is no negotiated Rx cell installed at initial time, the AutoRxCell is taken into account as well for downstream traffic adaptation. In this case:

初期状態ではネゴシエートされたRxセルがインストールされていないため、下り方向のトラフィックへの適応にはAutoRxCellも考慮されます。 この場合：

  • NumCellsElapsed is incremented by exactly 1 when the current cell is AutoRxCell.
  • NumCellsUsed is incremented by exactly 1 when the node receives a frame from the selected parent on AutoRxCell.
  • 現在のセルがAutoRxCellである場合、NumCellsElapsedはちょうど1だけ増加します。
  • ノードがAutoRxCell上で選択された親からフレームを受信した場合、NumCellsUsedはちょうど1だけ増加します。

Implementors MAY choose to create the same counters for each neighbor and add them as additional statistics in the neighbor table.

実装者は、近隣ごとに同じカウンターを作成し、それらを近隣テーブルの追加の統計情報として加えることを選択してもよいです（MAY）。

The counters are used as follows:

カウンターは次のように使われます：

  1. Both NumCellsElapsed and NumCellsUsed are initialized to 0 when the node boots.

  2. When the value of NumCellsElapsed reaches MAX_NUM_CELLS:

    • If NumCellsUsed is greater than LIM_NUMCELLSUSED_HIGH, trigger 6P to add a single cell to the selected parent.
    • If NumCellsUsed is less than LIM_NUMCELLSUSED_LOW, trigger 6P to remove a single cell to the selected parent.
    • Reset both NumCellsElapsed and NumCellsUsed to 0 and restart #2.
  1. NumCellsElapsedとNumCellsUsedは、どちらもノードの起動時に0に初期化されます。

  2. NumCellsElapsedの値がMAX_NUM_CELLSに達したとき：

    • NumCellsUsedがLIM_NUMCELLSUSED_HIGHより大きい場合、選択された親へのセルを1つ追加するよう6Pをトリガーします。
    • NumCellsUsedがLIM_NUMCELLSUSED_LOW未満の場合、選択された親へのセルを1つ削除するよう6Pをトリガーします。
    • NumCellsElapsedとNumCellsUsedの両方を0にリセットし、#2を再開します。

The value of MAX_NUM_CELLS is chosen according to the traffic type of the network. Generally speaking, the larger the value MAX_NUM_CELLS is, the more accurately the cell usage is calculated. By using a larger value of MAX_NUM_CELLS, the 6P traffic overhead could be reduced as well. Meanwhile, the latency won't increase much by using a larger value of MAX_NUM_CELLS for periodic traffic type. For bursty traffic, a larger value of MAX_NUM_CELLS indeed introduces higher latency. The latency caused by slight changes of traffic load can be alleviated by the additional scheduled cells. In this sense, MSF is a Scheduling Function that trades latency with energy by scheduling more cells than needed. Setting MAX_NUM_CELLS to a value at least four times the recent maximum number of cells used in a slotframe is RECOMMENDED. For example, a two packets/slotframe traffic load results in an average of four cells scheduled (two cells are used), using at least the value of double the number of scheduled cells (which is eight) as MAX_NUM_CELLS gives a good resolution on the cell usage calculation.

MAX_NUM_CELLSの値は、ネットワークのトラフィックの種類に応じて選択されます。 一般的に、MAX_NUM_CELLSの値が大きいほど、セルの使用率はより正確に計算されます。 MAX_NUM_CELLSにより大きな値を使うことで、6Pトラフィックのオーバーヘッドも削減できる可能性があります。 一方、周期的なトラフィックの種類では、MAX_NUM_CELLSにより大きな値を使っても遅延はそれほど増加しません。 バースト的なトラフィックでは、MAX_NUM_CELLSの値を大きくすると、実際により大きな遅延が生じます。 トラフィック負荷のわずかな変化によって生じる遅延は、追加でスケジュールされたセルによって緩和できます。 この意味で、MSFは、必要以上のセルをスケジュールすることで遅延とエネルギーをトレードオフするスケジューリング関数です。 MAX_NUM_CELLSは、直近のスロットフレームで使われたセルの最大数の少なくとも4倍の値に設定することが推奨されます（RECOMMENDED）。 たとえば、スロットフレームあたり2パケットのトラフィック負荷では平均4つのセルがスケジュールされ（2つのセルが使われます）、MAX_NUM_CELLSとして、スケジュールされたセル数の少なくとも2倍の値（つまり8）を使うと、セルの使用率の計算に十分な分解能が得られます。

In the case that a node has booted or has disappeared from the network, the cell reserved at the selected parent may be kept in the schedule forever. A cleanup mechanism MUST be provided to resolve this issue. The cleanup mechanism is implementation-specific. The goal is to confirm that those negotiated cells are not used anymore by the associated neighbors and remove them from the schedule.

ノードが起動した場合やネットワークから消えた場合、選択された親で予約されたセルがスケジュールに永久に保持される可能性があります。 この問題を解決するために、クリーンアップのメカニズムを提供しなければなりません（MUST）。 クリーンアップのメカニズムは実装固有です。 その目的は、それらのネゴシエートされたセルが関連する近隣によってもう使われていないことを確認し、スケジュールから削除することです。

5.2. Switching Parent

5.2. 親の切り替え

A node implementing MSF SHOULD implement the behavior described in this section.

MSFを実装するノードは、このセクションで説明する振る舞いを実装すべきです（SHOULD）。

As part of its normal operation, RPL can have a node switch parent. The procedure for switching from the old parent to the new parent is the following:

通常の動作の一部として、RPLはノードに親を切り替えさせることがあります。 古い親から新しい親に切り替える手順は次のとおりです：

  1. The node counts the number of negotiated cells it has per slotframe to the old parent.
  2. The node triggers one or more 6P ADD commands to schedule the same number of negotiated cells with same cell options to the new parent.
  3. When that successfully completes, the node issues a 6P CLEAR command to its old parent.
  1. ノードは、古い親に対してスロットフレームあたりに持っているネゴシエートされたセルの数を数えます。
  2. ノードは、同じセルオプションを持つ同じ数のネゴシエートされたセルを新しい親とスケジュールするために、1つ以上の6P ADDコマンドをトリガーします。
  3. それが正常に完了したら、ノードは古い親に6P CLEARコマンドを発行します。

The type of negotiated cell that should be installed first depends on which traffic has the higher priority, upstream or downstream, which is application-specific and out of scope of MSF.

どのタイプのネゴシエートされたセルを最初にインストールすべきかは、上り方向と下り方向のどちらのトラフィックの優先度が高いかに依存します。これはアプリケーション固有であり、MSFの範囲外です。

5.3. Handling Schedule Collisions

5.3. スケジュールの衝突への対処

A node implementing MSF SHOULD implement the behavior described in this section. Other algorithms for handling schedule collisions can be an alternative to the algorithm proposed in this section.

MSFを実装するノードは、このセクションで説明する振る舞いを実装すべきです（SHOULD）。 スケジュールの衝突に対処するための他のアルゴリズムを、このセクションで提案するアルゴリズムの代わりに使うこともできます。

Since scheduling is entirely distributed, there is a nonzero probability that two pairs of nearby neighbor nodes schedule a negotiated cell at the same [slotOffset,channelOffset] location in the TSCH schedule. In that case, data exchanged by the two pairs may collide on that cell. We call this case a "schedule collision".

スケジューリングは完全に分散して行われるため、近くにある近隣ノードの2つのペアが、TSCHスケジュール内の同じ[slotOffset,channelOffset]の位置にネゴシエートされたセルをスケジュールする確率はゼロではありません。 その場合、2つのペアが交換するデータがそのセル上で衝突する可能性があります。 この場合を「スケジュールの衝突（schedule collision）」と呼びます。

The node MUST maintain the following counters for each negotiated Tx cell to the selected parent:

ノードは、選択された親へのネゴシエートされたTxセルごとに、次のカウンターを維持しなければなりません（MUST）：

NumTx:
Counts the number of transmission attempts on that cell. Each time the node attempts to transmit a frame on that cell, NumTx is incremented by exactly 1.
NumTxAck:
Counts the number of successful transmission attempts on that cell. Each time the node receives an acknowledgment for a transmission attempt, NumTxAck is incremented by exactly 1.
NumTx:
そのセルでの送信試行の回数を数えます。 ノードがそのセルでフレームの送信を試みるたびに、NumTxはちょうど1だけ増加します。
NumTxAck:
そのセルでの成功した送信試行の回数を数えます。 ノードが送信試行に対する確認応答を受信するたびに、NumTxAckはちょうど1だけ増加します。

Since both NumTx and NumTxAck are initialized to 0, we necessarily have NumTxAck less than or equal to NumTx. We call Packet Delivery Ratio (PDR) the ratio NumTxAck/NumTx and represent it as a percentage. A cell with a PDR equal to 50% means that half of the frames transmitted are not acknowledged.

NumTxとNumTxAckはどちらも0に初期化されるため、NumTxAckは必ずNumTx以下になります。 比率NumTxAck/NumTxをパケット配送率（Packet Delivery Ratio、PDR）と呼び、パーセンテージで表します。 PDRが50%のセルは、送信されたフレームの半分が確認応答されていないことを意味します。

Each time the node switches parent (or during the join process when the node selects a parent for the first time), both NumTx and NumTxAck MUST be reset to 0. They increment over time, as the schedule is executed, and the node sends frames to that parent. When NumTx reaches MAX_NUMTX, both NumTx and NumTxAck MUST be divided by 2. MAX_NUMTX needs to be a power of two to avoid division error. For example, when MAX_NUMTX is set to 256, and NumTx=255 and NumTxAck=127, the counters become NumTx=128 and NumTxAck=64 if one frame is sent to the parent with an acknowledgment received. This operation does not change the value of the PDR but allows the counters to keep incrementing. The value of MAX_NUMTX is implementation-specific.

ノードが親を切り替えるたびに（または、参加プロセス中にノードが初めて親を選択するときに）、NumTxとNumTxAckの両方を0にリセットしなければなりません（MUST）。 これらは、スケジュールが実行され、ノードがその親にフレームを送信するにつれて、時間とともに増加します。 NumTxがMAX_NUMTXに達したら、NumTxとNumTxAckの両方を2で割らなければなりません（MUST）。 除算の誤差を避けるために、MAX_NUMTXは2のべき乗である必要があります。 たとえば、MAX_NUMTXが256に設定されており、NumTx=255かつNumTxAck=127のときに、親に1つのフレームが送信されて確認応答が受信されると、カウンターはNumTx=128およびNumTxAck=64になります。 この操作はPDRの値を変えませんが、カウンターが増加し続けることを可能にします。 MAX_NUMTXの値は実装固有です。

The key for detecting a schedule collision is that, if a node has several cells to the selected parent, all cells should exhibit the same PDR. A cell that exhibits a PDR significantly lower than the others indicates that there are collisions on that cell.

スケジュールの衝突を検出するための鍵は、ノードが選択された親へのセルを複数持っている場合、すべてのセルが同じPDRを示すはずだということです。 他より著しく低いPDRを示すセルは、そのセルで衝突が発生していることを示しています。

Every HOUSEKEEPINGCOLLISION_PERIOD, the node executes the following steps:

ノードは、HOUSEKEEPINGCOLLISION_PERIODごとに次のステップを実行します：

  1. It computes, for each negotiated Tx cell with the parent (not for the autonomous cell), that cell's PDR.
  2. Any cell that hasn't yet had NumTx divided by 2 since it was last reset is skipped in steps 3 and 4. This avoids triggering cell relocation when the values of NumTx and NumTxAck are not statistically significant yet.
  3. It identifies the cell with the highest PDR.
  4. For any other cell, it compares its PDR against that of the cell with the highest PDR. If the subtraction difference between the PDR of the cell and the highest PDR is larger than RELOCATE_PDRTHRES, it triggers the relocation of that cell using a 6P RELOCATE command.
  1. 親とのネゴシエートされたTxセルのそれぞれについて（自律セルについては行いません）、そのセルのPDRを計算します。
  2. 最後にリセットされてからまだNumTxが2で割られていないセルは、ステップ3と4でスキップされます。 これにより、NumTxとNumTxAckの値がまだ統計的に有意でないときにセルの再配置をトリガーすることを避けます。
  3. 最も高いPDRを持つセルを特定します。
  4. その他の各セルについて、そのPDRを最も高いPDRを持つセルのPDRと比較します。 そのセルのPDRと最も高いPDRとの差がRELOCATE_PDRTHRESを超える場合、6P RELOCATEコマンドを使ってそのセルの再配置をトリガーします。

The RELOCATION for negotiated Rx cells is not supported by MSF.

ネゴシエートされたRxセルのRELOCATIONは、MSFではサポートされていません。

8. Rules for CellList

8. CellListの規則

MSF uses two-step 6P Transactions exclusively. 6P Transactions are only initiated by a node towards its parent. As a result, the cells to put in the CellList of a 6P ADD command, and in the candidate CellList of a RELOCATE command, are chosen by the node initiating the 6P Transaction. In both cases, the same rules apply:

MSFは2ステップの6Pトランザクションのみを使います。 6Pトランザクションは、ノードからその親に向けてのみ開始されます。 その結果、6P ADDコマンドのCellListと、RELOCATEコマンドの候補CellListに入れるセルは、6Pトランザクションを開始するノードが選びます。 どちらの場合も、同じ規則が適用されます：

  • The CellList is RECOMMENDED to have five or more cells.
  • Each cell in the CellList MUST have a different slotOffset value.
  • For each cell in the CellList, the node MUST NOT have any scheduled cell on the same slotOffset.
  • The slotOffset value of any cell in the CellList MUST NOT be the same as the slotOffset of the minimal cell (slotOffset=0).
  • The slotOffset of a cell in the CellList SHOULD be randomly and uniformly chosen among all the slotOffset values that satisfy the restrictions above.
  • The channelOffset of a cell in the CellList SHOULD be randomly and uniformly chosen from [0..numFrequencies], where numFrequencies represents the number of frequencies a node can communicate on.
  • CellListには5つ以上のセルを含めることが推奨されます（RECOMMENDED）。
  • CellList内の各セルは、異なるslotOffsetの値を持たなければなりません（MUST）。
  • CellList内の各セルについて、ノードは同じslotOffsetにスケジュールされたセルを持っていてはなりません（MUST NOT）。
  • CellList内のいずれのセルのslotOffsetの値も、最小セルのslotOffset（slotOffset=0）と同じであってはなりません（MUST NOT）。
  • CellList内のセルのslotOffsetは、上記の制限を満たすすべてのslotOffsetの値の中から、ランダムかつ一様に選ぶべきです（SHOULD）。
  • CellList内のセルのchannelOffsetは、[0..numFrequencies]からランダムかつ一様に選ぶべきです（SHOULD）。ここで、numFrequenciesはノードが通信できる周波数の数を表します。

As a consequence of random cell selection, there is a nonzero chance that nodes in the vicinity have installed cells with same slotOffset and channelOffset. An implementer MAY implement a strategy to monitor the candidate cells before adding them in CellList to avoid collision. For example, a node MAY maintain a candidate cell pool for the CellList. The candidate cells in the pool are preconfigured as Rx cells to promiscuously listen to detect transmissions on those cells. If transmissions that rely on [IEEE802154] are observed on one cell over multiple iterations of the schedule, that cell is probably used by a TSCH neighbor. It is moved out from the pool, and a new cell is selected as a candidate cell. The cells in CellList are picked from the candidate pool directly when required.

セルをランダムに選択する結果として、周辺のノードが同じslotOffsetとchannelOffsetを持つセルをインストールしている可能性はゼロではありません。 実装者は、衝突を避けるために、候補セルをCellListに追加する前に監視する戦略を実装してもよいです（MAY）。 たとえば、ノードはCellListのための候補セルのプールを維持してもよいです（MAY）。 プール内の候補セルは、それらのセル上の送信を検出するためにプロミスキャスに聴取するRxセルとして事前に設定されます。 スケジュールの複数回の繰り返しにわたって、あるセル上で[IEEE802154]に依拠する送信が観測された場合、そのセルはおそらくTSCHの近隣によって使われています。 そのセルはプールから外され、新しいセルが候補セルとして選択されます。 CellList内のセルは、必要になったときに候補プールから直接選ばれます。

9. 6P Timeout Value

9. 6Pのタイムアウト値

The timeout value is calculated for the worst case that a 6P response is received, which means the 6P response is sent out successfully at the very latest retransmission. And for each retransmission, it backs off with largest value. Hence the 6P timeout value is calculated as ((2MAXBE) - 1) * MAXRETRIES * SLOTFRAME_LENGTH, where:

タイムアウト値は、6Pレスポンスが受信される最悪の場合、つまり6Pレスポンスがまさに最後の再送で送出に成功する場合について計算されます。 そして、各再送において、最大の値でバックオフします。 したがって、6Pのタイムアウト値は((2MAXBE) - 1) * MAXRETRIES * SLOTFRAME_LENGTHとして計算されます。ここで：

  • MAXBE, defined in [IEEE802154], is the maximum backoff exponent used.
  • MAXRETRIES, defined in [IEEE802154], is the maximum retransmission times.
  • SLOTFRAME_LENGTH represents the length of slotframe.
  • MAXBEは、[IEEE802154]で定義されている、使用される最大のバックオフ指数です。
  • MAXRETRIESは、[IEEE802154]で定義されている、最大の再送回数です。
  • SLOTFRAME_LENGTHは、スロットフレームの長さを表します。

16. Security Considerations

16. セキュリティーに関する考慮事項

MSF defines a series of "rules" for the node to follow. It triggers several actions that are carried out by the protocols defined in the following specifications: "Minimal IPv6 over the TSCH Mode of IEEE 802.15.4e (6TiSCH) Configuration" [RFC8180], "6TiSCH Operation Sublayer (6top) Protocol (6P)" [RFC8480], and "Constrained Join Protocol (CoJP) for 6TiSCH" [RFC9031]. Confidentiality and authentication of MSF control and data traffic are provided by these specifications whose security considerations continue to apply to MSF. In particular, MSF does not define a new protocol or packet format.

MSFは、ノードが従う一連の「規則」を定義します。 MSFは、次の仕様で定義されているプロトコルによって実行されるいくつかのアクションをトリガーします： 「Minimal IPv6 over the TSCH Mode of IEEE 802.15.4e (6TiSCH) Configuration」[RFC8180]、 「6TiSCH Operation Sublayer (6top) Protocol (6P)」[RFC8480]、 「Constrained Join Protocol (CoJP) for 6TiSCH」[RFC9031]。 MSFの制御トラフィックとデータトラフィックの機密性と認証はこれらの仕様によって提供され、それらのセキュリティーに関する考慮事項は引き続きMSFに適用されます。 特に、MSFは新しいプロトコルやパケット形式を定義しません。

MSF uses autonomous cells for initial bootstrap and the transport of join traffic. Autonomous cells are computed as a hash of nodes' EUI-64 addresses. This makes the coordinates of autonomous cell an easy target for an attacker, as EUI-64 addresses are visible on the wire and are not encrypted by the link-layer security mechanism. With the coordinates of autonomous cells available, the attacker can launch a selective jamming attack against any node's AutoRxCell. If the attacker targets a node acting as a JP, it can prevent pledges from using that JP to join the network. The pledge detects such a situation through the absence of a link-layer acknowledgment for its Join Request. As it is expected that each pledge will have more than one JP available to join the network, one available countermeasure for the pledge is to pseudorandomly select a new JP when the link to the previous JP appears bad. Such a strategy alleviates the issue of the attacker randomly jamming to disturb the network but does not help in the case the attacker is targeting a particular pledge. In that case, the attacker can jam the AutoRxCell of the pledge in order to prevent it from receiving the join response. This situation should be detected through the absence of a particular node from the network and handled by the network administrator through out-of-band means.

MSFは、初期のブートストラップと参加トラフィックの転送に自律セルを使います。 自律セルは、ノードのEUI-64アドレスのハッシュとして計算されます。 EUI-64アドレスは通信路上で見えており、リンク層のセキュリティーメカニズムによって暗号化されないため、自律セルの座標は攻撃者にとって格好の標的になります。 自律セルの座標が分かれば、攻撃者は任意のノードのAutoRxCellに対して選択的なジャミング攻撃を仕掛けることができます。 攻撃者がJPとして動作するノードを標的にした場合、プレッジがそのJPを使ってネットワークに参加するのを妨げることができます。 プレッジは、自身の参加リクエストに対するリンク層の確認応答がないことによって、このような状況を検出します。 各プレッジはネットワークへの参加に利用できるJPを複数持つと想定されるため、プレッジが利用できる対策の1つは、以前のJPへのリンクが不良に見える場合に、新しいJPを疑似ランダムに選択することです。 このような戦略は、攻撃者がネットワークを妨害するためにランダムにジャミングする問題を緩和しますが、攻撃者が特定のプレッジを標的にしている場合には役に立ちません。 その場合、攻撃者はプレッジのAutoRxCellをジャミングして、プレッジが参加レスポンスを受信するのを妨げることができます。 この状況は、ネットワークから特定のノードが欠けていることによって検出され、ネットワーク管理者が帯域外の手段で対処すべきです。

MSF adapts to traffic containing packets from the IP layer. It is possible that the IP packet has a nonzero DSCP (Differentiated Services Code Point) [RFC2474] value in its IPv6 header. The decision how to handle that packet belongs to the upper layer and is out of scope of MSF. As long as the decision is made to hand over to MAC layer to transmit, MSF will take that packet into account when adapting to traffic.

MSFは、IP層からのパケットを含むトラフィックに適応します。 IPパケットのIPv6ヘッダーに、ゼロでないDSCP（Differentiated Services Code Point）[RFC2474]の値が含まれている可能性があります。 そのパケットをどのように処理するかの決定は上位層に属し、MSFの範囲外です。 送信のためにMAC層に引き渡すという決定が下される限り、MSFはトラフィックに適応する際にそのパケットを考慮に入れます。

Note that nonzero DSCP values may imply that the traffic originated at unauthenticated pledges (see [RFC9031]). The implementation at the IPv6 layer SHOULD rate limit this join traffic before it is passed to the 6top sublayer where MSF can observe it. If there is no rate limit for join traffic, intermediate nodes in the 6TiSCH network may be prone to a resource exhaustion attack, with the attacker injecting unauthenticated traffic from the network edge. The assumption is that the rate-limiting function is aware of the available bandwidth in the 6top Layer 3 bundle(s) towards a next hop, not directly from MSF, but from an interaction with the 6top sublayer that ultimately manages the bundles under MSF's guidance. How this rate limit is implemented is out of scope of MSF.

ゼロでないDSCPの値は、そのトラフィックが認証されていないプレッジから発信されたことを意味する場合があることに注意してください（[RFC9031]を参照）。 IPv6層の実装は、MSFが観測できる6topサブレイヤーに渡す前に、この参加トラフィックをレート制限すべきです（SHOULD）。 参加トラフィックに対するレート制限がない場合、6TiSCHネットワーク内の中間ノードは、攻撃者がネットワークのエッジから認証されていないトラフィックを注入する、資源枯渇攻撃を受けやすくなる可能性があります。 レート制限の機能は、ネクストホップに向かう6topのレイヤー3バンドルで利用可能な帯域幅を認識していることを前提としています。ただし、それはMSFから直接ではなく、MSFの指示の下で最終的にバンドルを管理する6topサブレイヤーとのやり取りから認識します。 このレート制限をどのように実装するかは、MSFの範囲外です。

Appendix A. Example Implementation of the SAX Hash Function

Appendix A. SAXハッシュ関数の実装例

To support interoperability, this section provides an example implementation of the SAX hash function [SAX-DASFAA]. The input parameters of the function are:

相互運用性をサポートするために、このセクションではSAXハッシュ関数[SAX-DASFAA]の実装例を示します。 この関数の入力パラメーターは次のとおりです：

  • T, which is the hashing table length.
  • c, which is the characters of string s, to be hashed.
  • T：ハッシュテーブルの長さです。
  • c：ハッシュ化される文字列sの文字です。

In MSF, the T is replaced by the length of slotframe 1. String s is replaced by the node EUI-64 address. The characters of the string, c0 through c7, are the eight bytes of the EUI-64 address.

MSFでは、Tはスロットフレーム1の長さに置き換えられます。 文字列sは、ノードのEUI-64アドレスに置き換えられます。文字列の文字c0からc7は、EUI-64アドレスの8バイトです。

The SAX hash function requires shift operation, which is defined as follow:

SAXハッシュ関数にはシフト演算が必要であり、次のように定義されます：

  • L_shift(v,b), which refers to the left shift of variable v by b bits
  • R_shift(v,b), which refers to the right shift of variable v by b bits
  • L_shift(v,b)：変数vをbビット左シフトすることを指します
  • R_shift(v,b)：変数vをbビット右シフトすることを指します

The steps to calculate the hash value of SAX hash function are:

SAXハッシュ関数のハッシュ値を計算するステップは次のとおりです：

  1. Initialize variable h, which is the intermediate hash value, to h0 and variable i, which is the index of the bytes of the EUI-64 address, to 0.
  2. Sum the value of L_shift(h,l_bit), R_shift(h,r_bit), and ci.
  3. Calculate the result of the exclusive OR between the sum value in Step 2 and h.
  4. Modulo the result of Step 3 by T.
  5. Assign the result of Step 4 to h.
  6. Increase i by 1.
  7. Repeat Step 2 to Step 6 until i reaches to 8.
  1. 中間ハッシュ値である変数hをh0に、EUI-64アドレスのバイトのインデックスである変数iを0に初期化します。
  2. L_shift(h,l_bit)、R_shift(h,r_bit)、ciの値を合計します。
  3. ステップ2の合計値とhの排他的論理和の結果を計算します。
  4. ステップ3の結果のTによる剰余を求めます。
  5. ステップ4の結果をhに代入します。
  6. iを1増やします。
  7. iが8に達するまで、ステップ2からステップ6を繰り返します。

The value of variable h is the hash value of the SAX hash function.

変数hの値が、SAXハッシュ関数のハッシュ値です。

The values of h0, l_bit, and r_bit in Step 1 and Step 2 are configured as:

ステップ1とステップ2のh0、l_bit、r_bitの値は、次のように設定されます：

h0 = 0

h0 = 0

l_bit = 0

l_bit = 0

r_bit = 1

r_bit = 1

The appropriate values of l_bit and r_bit could vary depending on the set of nodes' EUI-64 address. How to find those values is out of the scope of this specification.

l_bitとr_bitの適切な値は、ノードのEUI-64アドレスの集合によって異なる可能性があります。 それらの値を見つける方法は、この仕様の範囲外です。
