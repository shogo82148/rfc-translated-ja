RFC 9971

Multiple Loss Ratio Search

RFC 9971

多重損失率探索

Abstract

概要

This document describes an alternative to throughput in "Benchmarking Methodology for Network Interconnect Devices" (RFC 2544) by defining a new methodology called Multiple Loss Ratio Search (MLRsearch). MLRsearch aims to minimize Search Duration, support multiple loss ratio goals, and improve result repeatability and comparability.

この文書は、多重損失率探索（Multiple Loss Ratio Search: MLRsearch）と呼ばれる新しい方法論を定義することで、"Benchmarking Methodology for Network Interconnect Devices"（RFC 2544）のスループットの代替を説明します。MLRsearch は、探索時間の最小化、複数の損失率の目標のサポート、結果の再現性と比較可能性の向上を目指しています。

MLRsearch is motivated by the pressing need to address the challenges of evaluating and testing the various data plane solutions, especially in software-based networking systems based on Commercial Off-the-Shelf (COTS) CPU hardware vs. purpose-built Application-Specific Integrated Circuit (ASIC) / Network Processing Unit (NPU) / Field-Programmable Gate Array (FPGA) hardware.

MLRsearch は、さまざまなデータプレーンの解決策、特に専用の特定用途向け集積回路（ASIC）/ネットワーク処理ユニット（NPU）/フィールドプログラマブルゲートアレイ（FPGA）のハードウェアに対して、市販品（COTS）の CPU ハードウェアに基づくソフトウェアベースのネットワーキングシステムを評価しテストする際の課題に対処する差し迫った必要性に動機付けられています。

1. Introduction

1. はじめに

This document describes the Multiple Loss Ratio Search (MLRsearch) methodology, optimized for determining data plane throughput in software-based networking functions running on commodity systems with generic CPUs (vs. purpose-built ASICs, NPUs, and FPGAs). Such network functions can be deployed on a dedicated physical appliance (e.g., a standalone hardware device) or as virtual appliance (e.g., a Virtual Network Function running on shared servers in the compute cloud).

この文書は、汎用の CPU を持つコモディティーシステム（専用の ASIC、NPU、FPGA に対して）上で動作するソフトウェアベースのネットワーキング機能におけるデータプレーンのスループットを決定するために最適化された、多重損失率探索（MLRsearch）の方法論を説明します。そのようなネットワーク機能は、専用の物理アプライアンス（たとえば、スタンドアロンのハードウェアデバイス）上に、または仮想アプライアンス（たとえば、計算クラウドの共有サーバー上で動作する仮想ネットワーク機能）として展開できます。

This document tightly couples terminology and methodology aspects. Instead of a separate terminology section, the subsections of Section 4 act as a list of newly defined terms. If a term appears with the first letter capitalized, it likely refers to a specific term defined in an eponymous subsection of MLRsearch Specification.

この文書は、用語と方法論の側面を密接に結び付けています。別個の用語のセクションの代わりに、Section 4 のサブセクションが新しく定義される用語のリストとして機能します。用語が最初の文字を大文字にして現れる場合、それはおそらく MLRsearch 仕様の同名のサブセクションで定義された特定の用語を指しています。

For first-time readers, the information in MLRsearch Specification might feel dense and lacking motivation. Subsequent sections provide explanations, making MLRsearch Specification more approachable on repeated reads.

初めて読む人にとって、MLRsearch 仕様の情報は密度が高く、動機に欠けるように感じられるかもしれません。後続のセクションで説明を提供しており、繰り返し読むことで MLRsearch 仕様がより取り組みやすくなります。

1.1. Purpose

1.1. 目的

The purpose of this document is to describe the Multiple Loss Ratio Search (MLRsearch) methodology, optimized for determining data plane throughput in software-based networking devices and functions.

この文書の目的は、ソフトウェアベースのネットワーキングデバイスと機能におけるデータプレーンのスループットを決定するために最適化された、多重損失率探索（MLRsearch）の方法論を説明することです。

Applying the Section 2.1 to software Devices Under Test (DUTs) results in several problems:

Section 2.1 をソフトウェアの被試験デバイス（DUT）に適用すると、いくつかの問題が生じます。

  • Binary Search takes a long time, as most Trials are done far from the eventually found Throughput.

  • The required final Trial Duration and pauses between Trials prolong the overall Search Duration.

  • Software DUTs show noisy Trial Results, leading to a big spread of Throughput values that could be discovered.

  • Throughput requires a loss of exactly zero frames, but the industry best practices frequently allow for tolerance of low but non-zero losses (see [Y.1564] and test-equipment manuals for more information).

  • The definition of Throughput is not clear when Trial Results are inconsistent (e.g., when a successive Trial at a higher Load yields a smaller Trial Loss Ratio, Throughput can no longer be pinned to a single, unambiguous value.)

  • ほとんどのトライアル（Trial）が最終的に見つかるスループットから遠いところで行われるため、二分探索には長い時間がかかります。

  • 必要な最終的なトライアル期間とトライアル間の休止により、全体の探索時間が長くなります。

  • ソフトウェアの DUT はノイズの多いトライアル結果を示し、発見されうるスループットの値が大きくばらつきます。

  • スループットはフレームの損失がちょうどゼロであることを要求します。一方、業界のベストプラクティスでは、低いがゼロではない損失の許容がしばしば認められています（詳細は [Y.1564] とテスト機器のマニュアルを参照してください）。

  • トライアル結果に一貫性がない場合、スループットの定義は明確ではありません（たとえば、より高い負荷での後続のトライアルがより小さいトライアル損失率になる場合、スループットはもはや単一の明確な値に定められません）。

To address these problems, early MLRsearch implementations employed the following enhancements:

これらの問題に対処するために、初期の MLRsearch の実装では次の改良が採用されました。

  1. Allow multiple Short Trials instead of one long Trial per Load.

    • Optionally, tolerate a percentage of Trial Results with higher Trial Loss Ratios.

  2. Allow searching for multiple Search Goals, with differing Goal Loss Ratios.

    • Any Trial Result can affect each Search Goal in principle.

  3. Insert multiple coarse targets for each Search Goal; earlier ones need to spend less time on Trials.

    • Earlier targets also aim for lesser precision.

    • Use Forwarding Rate at Maximum Offered Load (FRMOL), as defined in Section 3.6.2 of [RFC2285], to initialize bounds.

  4. Clarify handling of Inconsistent Trial Results.

    • Reported Throughput should be smaller than the smallest Load with high loss.

    • Measure smaller Load candidates first.

  5. Apply several time-saving Load selection heuristics that deliberately prevent the bounds from narrowing unnecessarily.

  1. 負荷ごとに 1 つの長いトライアルの代わりに、複数の短いトライアルを許可する。

    • オプションとして、より高いトライアル損失率を持つトライアル結果を一定の割合まで許容する。

  2. 異なる目標損失率を持つ複数の探索目標（Search Goal）を探索することを許可する。

    • 原則として、どのトライアル結果も各探索目標に影響を与えうる。

  3. 各探索目標について複数の粗い目標を挿入する。前の目標ほどトライアルに費やす時間が少なくて済む。

    • 前の目標ほど目指す精度も低い。

    • 境界を初期化するために、[RFC2285]のSection 3.6.2 で定義されている最大提供負荷時の転送レート（FRMOL）を使用する。

  4. 一貫性のないトライアル結果の扱いを明確にする。

    • 報告されるスループットは、損失の高い最小の負荷よりも小さくすべきです。

    • より小さい負荷の候補を先に測定する。

  5. 境界が不必要に狭まることを意図的に防ぐ、時間を節約するいくつかの負荷選択のヒューリスティックを適用する。

Enhancements 1, 2, and partly 4 are formalized as the MLRsearch Specification within this document. The remaining enhancements are treated as implementation details and out of scope for this document. This achieves high comparability without limiting future improvements.

改良 1、2、および部分的に 4 は、この文書内で MLRsearch 仕様として形式化されています。残りの改良は実装の詳細として扱われ、この文書の範囲外です。これにより、将来の改善を制限することなく高い比較可能性が達成されます。

MLRsearch configuration supports both conservative settings and aggressive settings. Results unconditionally compliant with [RFC2544] are possible with conservative enough settings but without much improvement on Search Duration and repeatability, see Section 4.10.2. Conversely, aggressive settings lead to shorter Search Durations and better repeatability, but the results are not compliant with [RFC2544]. This document offers only soft recommendations for settings, but see the discussion in Section 2 for the impact of different settings on result quality.

MLRsearch の構成は、保守的な設定と積極的な設定の両方をサポートしています。十分に保守的な設定では [RFC2544] に無条件に準拠した結果が得られますが、探索時間と再現性はあまり改善されません。Section 4.10.2 を参照してください。逆に、積極的な設定では探索時間が短くなり再現性が向上しますが、結果は [RFC2544] に準拠しません。この文書は設定について緩やかな推奨しか提供しませんが、異なる設定が結果の品質に与える影響については Section 2 の議論を参照してください。

This document does not change or obsolete any part of [RFC2544].

この文書は [RFC2544] のどの部分も変更または廃止しません。

1.2. Positioning Within BMWG Methodologies

1.2. BMWG の方法論の中での位置付け

The Benchmarking Methodology Working Group (BMWG) produces recommendations (RFCs) that describe various benchmarking methodologies for use in a controlled laboratory environment. A large number of these benchmarks are based on the terminology from [RFC1242] and the foundational methodology from [RFC2544]. A common pattern has emerged where BMWG documents reference the methodology of [RFC2544] and augment it with specific requirements for testing particular network systems or protocols, without modifying the core benchmark definitions.

ベンチマーキング方法論ワーキンググループ（BMWG）は、制御された実験室環境で使用するためのさまざまなベンチマーキングの方法論を説明する推奨事項（RFC）を作成しています。これらのベンチマークの多くは、[RFC1242] の用語と [RFC2544] の基礎的な方法論に基づいています。BMWG の文書が [RFC2544] の方法論を参照し、中核となるベンチマークの定義を変更することなく、特定のネットワークシステムやプロトコルをテストするための具体的な要件で拡張するという共通のパターンが生まれています。

While BMWG documents are formal recommendations, they are widely treated as industry norms to ensure the comparability of results between different labs. The set of benchmarks defined in [RFC2544], in particular, became a de facto standard for performance testing. In this context, the MLRsearch Specification formally defines a new class of benchmarks that fits within the wider framework of [RFC2544]; see Section 4.1.

BMWG の文書は正式な推奨事項ですが、異なるラボ間で結果の比較可能性を確保するための業界の規範として広く扱われています。特に、[RFC2544] で定義されたベンチマークの集合は、性能テストの事実上の標準になりました。この文脈において、MLRsearch 仕様は、[RFC2544] のより広い枠組みに収まる新しいクラスのベンチマークを正式に定義します。Section 4.1 を参照してください。

A primary consideration in the design of MLRsearch is the trade-off between configurability and comparability. The methodology's flexibility, especially the ability to define various sets of Search Goals, in supporting both single-goal and multi-goal benchmarks in a unified way is powerful for detailed characterization and internal testing. However, this same flexibility is detrimental to inter-lab comparability unless a specific, common set of Search Goals is agreed upon.

MLRsearch の設計における主要な考慮事項は、構成可能性と比較可能性の間のトレードオフです。方法論の柔軟性、特に探索目標のさまざまな集合を定義でき、単一目標と複数目標の両方のベンチマークを統一的にサポートできる能力は、詳細な特性評価や内部のテストに強力です。しかし、同じ柔軟性は、特定の共通の探索目標の集合が合意されない限り、ラボ間の比較可能性にとって有害です。

Therefore, MLRsearch should not be seen as a direct extension nor a replacement for the [RFC2544] Throughput benchmark. Instead, this document provides a foundational methodology that future BMWG documents can use to define new, specific, and comparable benchmarks by mandating particular Search Goal configurations. For operators of existing test procedures, it is worth noting that many test setups measuring [RFC2544] Throughput can be adapted to produce results compliant with the MLRsearch Specification, often without affecting Trials, merely by augmenting the content of the final Test Report.

したがって、MLRsearch は、[RFC2544] のスループットのベンチマークの直接の拡張とも置き換えとも見るべきではありません。代わりに、この文書は、将来の BMWG の文書が特定の探索目標の構成を義務付けることで、新しい具体的で比較可能なベンチマークを定義するために使用できる基礎的な方法論を提供します。既存のテスト手順の運用者にとって注目に値するのは、[RFC2544] のスループットを測定する多くのテストのセットアップが、多くの場合トライアルに影響を与えることなく、最終的なテストレポートの内容を拡張するだけで、MLRsearch 仕様に準拠した結果を生成するように調整できることです。

2. Overview of RFC 2544 Problems

2. RFC 2544 の問題の概要

This section describes the problems affecting usability of various performance testing methodologies, mainly the Binary Search for unconditionally compliant [RFC2544] Throughput.

このセクションでは、さまざまな性能テストの方法論、主に [RFC2544] に無条件に準拠したスループットのための二分探索の使いやすさに影響する問題を説明します。

2.1. Binary Search

2.1. 二分探索

While [RFC2544] offers some flexibility when searching for Throughput, a particular algorithm is frequently used as a starting point, as it is the simplest one among those that offer reasonable effectivity.

[RFC2544] はスループットを探索する際にある程度の柔軟性を提供していますが、妥当な効果を提供するものの中で最も単純なものであるため、特定のアルゴリズムが出発点としてよく使用されます。

This algorithm is based on (balanced) binary search over sorted arrays but does not have a specific name when searching for Throughput. "Trial duration" (Section 24 of [RFC2544]) mentions binary search only in quotes, without providing specifics. In this document, we call that algorithm the Binary Search, as that is the title of Section 12.3.2 of [TST009], which describes a variant of it.

このアルゴリズムは、ソートされた配列上の（平衡）二分探索に基づいていますが、スループットを探索する場合には特定の名前を持っていません。"Trial duration"（[RFC2544]のSection 24）は、具体的な内容を示すことなく、引用符付きで二分探索に言及しているだけです。この文書では、そのアルゴリズムの変種を説明している [TST009] のセクション 12.3.2 のタイトルにならって、そのアルゴリズムを二分探索（Binary Search）と呼びます。

Here is a simplified description of the algorithm:

アルゴリズムの簡略化した説明は次のとおりです。

  • Initialize the lower-bound variable to a line-rate Load.

  • Initialize the upper-bound variable to a loss-free Load.

  • Compute a midpoint, the arithmetic mean of current bounds.

  • Run a single 60-second Trial at the midpoint (for [RFC2544] unconditional compliance).

  • If loss is zero, set the lower-bound to the midpoint; else, set the upper bound to the midpoint.

  • Repeat (computing new midpoint) until the gap between the bounds meets the desired precision.

  • Return the final lower-bound as the Throughput.

  • 下限の変数をラインレートの負荷に初期化する。

  • 上限の変数を損失のない負荷に初期化する。

  • 現在の境界の算術平均である中点を計算する。

  • 中点で 60 秒のトライアルを 1 回実行する（[RFC2544] への無条件の準拠のため）。

  • 損失がゼロの場合は下限を中点に設定し、そうでない場合は上限を中点に設定する。

  • 境界の間の差が望む精度を満たすまで（新しい中点を計算して）繰り返す。

  • 最終的な下限をスループットとして返す。

The description in [TST009] has two more requirements (stopping condition and rounding, both based on the Offered Load Step Size Parameter), but those are not required in this document.

[TST009] の説明にはさらに 2 つの要件（停止条件と丸めで、どちらも提供負荷のステップサイズのパラメーターに基づく）がありますが、この文書ではそれらは必要ありません。

Small modifications related to initial bounds are also allowed.

初期の境界に関連する小さな変更も許可されています。

The Loads currently held in the two variables are called tightest bounds, especially when discussing older Trial Results (logically still bounds).

2 つの変数に現在保持されている負荷は、特に古いトライアル結果（論理的にはまだ境界）について議論する場合、tightest bounds と呼ばれます。

2.2. Long Search Duration

2.2. 長い探索時間

The proliferation of software DUTs, with frequent software updates and a number of different frame processing modes and configurations, has increased both the number of performance tests required to verify the DUT update and the frequency of running those tests. This makes the overall test execution time even more important than before.

頻繁なソフトウェアの更新と、多くの異なるフレーム処理のモードと構成を持つソフトウェアの DUT の急増により、DUT の更新を検証するために必要な性能テストの数と、それらのテストを実行する頻度の両方が増加しています。これにより、全体的なテストの実行時間が以前にも増して重要になっています。

The definition of Throughput test methodology per [RFC2544] restricts the potential for time-efficiency improvements. The Binary Search, when used in a manner unconditionally compliant with [RFC2544] Throughput methodology, is excessively slow due to two main factors.

[RFC2544] によるスループットのテスト方法論の定義は、時間効率の改善の可能性を制限しています。二分探索は、[RFC2544] のスループットの方法論に無条件に準拠した方法で使用される場合、2 つの主な要因により過度に遅くなります。

First, a significant amount of time is spent on Trials with Loads that, in retrospect, are far from the final determined Throughput.

第一に、後から振り返ると最終的に決定されたスループットから遠い負荷でのトライアルに、かなりの時間が費やされます。

Second, [RFC2544] does not specify any stopping condition for Throughput search, so users of testing equipment implementing the procedure already have access to a limited trade-off between Search Duration and achieved precision, as each one of the full 60-second Trials halves the interval of possible results.

第二に、[RFC2544] はスループットの探索の停止条件を規定していないため、手順を実装しているテスト機器のユーザーは、探索時間と達成される精度の間の限られたトレードオフにすでにアクセスできます。60 秒の完全なトライアルのそれぞれが、可能な結果の区間を半分にするからです。

As such, not many Trials can be removed without a substantial loss of precision.

そのため、精度を大幅に失うことなく削減できるトライアルは多くありません。

2.3. DUT in SUT

2.3. SUT の中の DUT

Section 19 of [RFC2544] specifies a test setup with an external tester stimulating the networking system, treating it either as a single Device Under Test (DUT) or as a system of devices, a System Under Test (SUT).

[RFC2544]のSection 19 は、外部のテスターがネットワーキングシステムに刺激を与え、それを単一の被試験デバイス（DUT）、またはデバイスのシステムである被試験システム（SUT）のいずれかとして扱うテストのセットアップを規定しています。

[RFC2285] defines these terms as follows.

[RFC2285] はこれらの用語を次のように定義しています。

DUT:

The network frame forwarding device to which stimulus is offered and response measured (Section 3.1.1 of [RFC2285]).

SUT:

The collective set of network devices to which stimulus is offered as a single entity and response measured (Section 3.1.2 of [RFC2285]).

DUT:

刺激が与えられ、応答が測定されるネットワークフレーム転送デバイス（[RFC2285]のSection 3.1.1）。

SUT:

単一のエンティティーとして刺激が与えられ、応答が測定されるネットワークデバイスの集まり（[RFC2285]のSection 3.1.2）。

For software-based data plane forwarding running on commodity x86/ARM CPUs, the SUT comprises not only the forwarding application itself, the DUT, but also the entire execution environment: host hardware, firmware and kernel/hypervisor services, as well as any other software workloads that share the same CPUs, memory, and I/O resources.

コモディティーの x86/ARM CPU 上で動作するソフトウェアベースのデータプレーンの転送では、SUT は、転送アプリケーション自体である DUT だけでなく、実行環境全体、つまりホストのハードウェア、ファームウェア、カーネル/ハイパーバイザーのサービス、さらに同じ CPU、メモリー、I/O の資源を共有するその他のソフトウェアのワークロードで構成されます。

Given that a SUT is a shared multi-tenant environment, the DUT might inadvertently experience interference from the operating system or from other software operating on the same server.

SUT が共有されたマルチテナントの環境であることを考えると、DUT は、オペレーティングシステムや同じサーバー上で動作するほかのソフトウェアからの干渉を意図せず受ける可能性があります。

Some of this interference can be mitigated. For instance, in multi-core CPU systems, pinning DUT program threads to specific CPU cores and isolating those cores can prevent context switching.

この干渉の一部は緩和できます。たとえば、マルチコアの CPU システムでは、DUT のプログラムのスレッドを特定の CPU コアに固定し、それらのコアを分離することで、コンテキストスイッチを防ぐことができます。

Despite taking all feasible precautions, some adverse effects may still impact the DUT's network performance. In this document, these effects are collectively referred to as SUT noise, even if the effects are not as unpredictable as what other engineering disciplines call noise.

実行可能なすべての予防措置をとっても、一部の悪影響が DUT のネットワーク性能に影響する可能性があります。この文書では、ほかの工学の分野がノイズと呼ぶものほど予測不可能ではない場合でも、これらの影響をまとめて SUT ノイズと呼びます。

A DUT can also exhibit fluctuating performance itself, for reasons not related to the rest of SUT. For example, this can be due to pauses in execution as needed for internal stateful processing. In many cases, this may be an expected per-design behavior, as it would be observable even in a hypothetical scenario where all sources of SUT noise are eliminated. Such behavior affects Trial Results in a way similar to SUT noise. As the two phenomena are hard to distinguish, in this document, the term noise is used to encompass both the internal performance fluctuations of the DUT and the genuine noise of the SUT.

DUT 自体も、SUT の残りの部分とは関係のない理由で、変動する性能を示す場合があります。たとえば、これは内部のステートフルな処理に必要な実行の一時停止による場合があります。多くの場合、これは SUT ノイズのすべての発生源が排除された仮想的なシナリオでも観測されるため、設計上の期待される振る舞いである場合があります。そのような振る舞いは、SUT ノイズと同様の方法でトライアル結果に影響します。2 つの現象は区別が難しいため、この文書では、DUT の内部の性能の変動と SUT の真のノイズの両方を包含するために noise という用語を使用します。

A simple model of SUT performance consists of an idealized noiseless performance and additional noise effects. For a specific SUT, the noiseless performance is assumed to be constant, with all observed performance variations being attributed to noise. The impact of the noise can vary in time, sometimes wildly, even within a single Trial. The noise can sometimes be negligible, but it frequently lowers the observed SUT performance as observed in Trial Results.

SUT の性能の単純なモデルは、理想化されたノイズのない性能と、追加のノイズの影響で構成されます。特定の SUT について、ノイズのない性能は一定であると仮定され、観測されるすべての性能の変動はノイズに起因するものとされます。ノイズの影響は時間とともに、時には単一のトライアル内でも大きく変化する可能性があります。ノイズは無視できる場合もありますが、多くの場合、トライアル結果で観測される SUT の性能を低下させます。

In this simple model, a SUT does not have a single performance value; it has a spectrum. One end of the spectrum is the idealized noiseless performance, and the other end can be called a noiseful performance. In practice, Trial Results close to the noiseful end of the spectrum happen only rarely. The worse a possible performance is, the more rarely it is seen in a Trial. Therefore, the extreme noiseful end of the SUT spectrum is not observable among Trial Results.

この単純なモデルでは、SUT は単一の性能の値を持たず、スペクトルを持ちます。スペクトルの一方の端は理想化されたノイズのない性能であり、もう一方の端はノイズの多い性能と呼ぶことができます。実際には、スペクトルのノイズの多い端に近いトライアル結果はまれにしか起こりません。可能な性能が悪いほど、トライアルで見られることはまれになります。そのため、SUT のスペクトルの極端にノイズの多い端は、トライアル結果の中には観測されません。

Furthermore, the extreme noiseless end of the SUT spectrum is unlikely to be observable, this time because minor noise events almost always occur during each Trial, nudging the measured performance slightly below the theoretical maximum.

さらに、SUT のスペクトルの極端にノイズのない端も観測される可能性は低いです。今度は、ほぼすべてのトライアルの間に小さなノイズの事象が発生し、測定される性能を理論上の最大値をわずかに下回るように押し下げるからです。

Unless specified otherwise, this document's focus is on the potentially observable ends of the SUT performance spectrum, as opposed to the extreme ones.

特に指定しない限り、この文書の焦点は、極端な端ではなく、SUT の性能スペクトルの潜在的に観測可能な端にあります。

When focusing on the DUT, the benchmarking effort should ideally aim to eliminate only the SUT noise from SUT measurements. However, this is currently not feasible in practice, as there are no realistic enough models that would be capable to distinguish SUT noise from DUT fluctuations (based on the available literature at the time of writing).

DUT に焦点を当てる場合、ベンチマーキングの取り組みは、理想的には SUT の測定から SUT ノイズだけを除去することを目指すべきです。しかし、（執筆時点で利用可能な文献に基づくと）SUT ノイズを DUT の変動から区別できるほど現実的なモデルはないため、これは現在のところ実際には実行可能ではありません。

If the SUT execution environments and any co-resident workloads place only negligible demands on SUT shared resources, so that the DUT remains the principal performance limiter, the DUT's ideal noiseless performance is defined as the noiseless end of the SUT performance spectrum.

SUT の実行環境と同居するワークロードが SUT の共有資源にわずかな要求しかせず、DUT が性能の主な制限要因であり続ける場合、DUT の理想的なノイズのない性能は、SUT の性能スペクトルのノイズのない端として定義されます。

Note that by this definition, DUT noiseless performance also minimizes the impact of DUT fluctuations, as much as realistically possible for a given Trial Duration.

この定義により、DUT のノイズのない性能は、特定のトライアル期間について現実的に可能な限り、DUT の変動の影響も最小化することに注意してください。

The MLRsearch methodology aims to solve the DUT-in-SUT problem by estimating the noiseless end of the SUT performance spectrum using a limited number of Trial Results.

MLRsearch の方法論は、限られた数のトライアル結果を使用して SUT の性能スペクトルのノイズのない端を推定することで、SUT の中の DUT の問題を解決することを目指しています。

Improvements to the Throughput search algorithm, aimed at better dealing with software networking SUT and DUT setups, should adopt methods that explicitly model SUT-generated noise, deriving surrogate metrics that approximate the (proxies for) DUT noiseless performance across a range of SUT noise-tolerance levels.

ソフトウェアのネットワーキングの SUT と DUT のセットアップをよりよく扱うことを目的としたスループットの探索アルゴリズムの改善では、SUT が生成するノイズを明示的にモデル化し、SUT ノイズの許容度のさまざまなレベルにわたって DUT のノイズのない性能（の代理）を近似する代替のメトリックを導出する方法を採用すべきです。

2.4. Repeatability and Comparability

2.4. 再現性と比較可能性

[RFC2544] does not suggest repeating Throughput search. Also, note that from simply one discovered Throughput, it cannot be determined how repeatable that value is. Unsatisfactory repeatability then leads to unacceptable comparability, as different benchmarking teams may obtain varying Throughput values for the same SUT, exceeding the expected differences from search precision. Repeatability is also important when the test procedure is kept the same, but SUT is varied in small ways. For example, during development of software-based DUTs, repeatability is needed to detect small regressions.

[RFC2544] はスループットの探索を繰り返すことを提案していません。また、1 つの発見されたスループットだけからは、その値がどの程度再現可能であるかを判断できないことに注意してください。満足できない再現性は、許容できない比較可能性につながります。異なるベンチマーキングのチームが、同じ SUT について、探索の精度から予想される差を超えて異なるスループットの値を得る可能性があるからです。再現性は、テスト手順を同じに保ちながら SUT を少しずつ変化させる場合にも重要です。たとえば、ソフトウェアベースの DUT の開発中には、小さな性能の低下を検出するために再現性が必要です。

[RFC2544] Throughput requirements (60-second Trial and no tolerance of a single frame loss) affect the Throughput result as follows.

[RFC2544] のスループットの要件（60 秒のトライアルと、1 フレームの損失も許容しないこと）は、スループットの結果に次のように影響します。

The SUT behavior close to the noiseful end of its performance spectrum consists of rare occasions of significantly low performance, but the long Trial Duration makes those occasions not so rare on the Trial level. Therefore, the Binary Search results tend to spread away from the noiseless end of SUT performance spectrum more frequently and more widely than shorter Trials would, thus causing unacceptable Throughput repeatability.

性能スペクトルのノイズの多い端に近い SUT の振る舞いは、まれに起こる著しく低い性能の機会で構成されますが、長いトライアル期間により、それらの機会はトライアルのレベルではそれほどまれではなくなります。そのため、二分探索の結果は、より短いトライアルの場合よりも頻繁かつ広く SUT の性能スペクトルのノイズのない端から離れて散らばる傾向があり、許容できないスループットの再現性を引き起こします。

The repeatability problem can be better addressed by defining a search procedure that identifies a consistent level of performance, even if it does not meet the strict definition of Throughput test methodology in [RFC2544].

再現性の問題は、[RFC2544] のスループットのテスト方法論の厳密な定義を満たさない場合でも、一貫した性能のレベルを特定する探索手順を定義することで、よりよく対処できます。

According to the SUT performance spectrum model, better repeatability will be at the noiseless end of the spectrum. Therefore, solutions to the DUT-in-SUT problem will also help with the repeatability problem.

SUT の性能スペクトルのモデルによれば、スペクトルのノイズのない端で再現性がよりよくなります。そのため、SUT の中の DUT の問題の解決策は、再現性の問題にも役立ちます。

Conversely, any alteration to [RFC2544] Throughput search that improves repeatability should be considered as less dependent on the SUT noise.

逆に、再現性を向上させる [RFC2544] のスループットの探索へのいかなる変更も、SUT ノイズへの依存が少ないものとみなすべきです。

An alternative option is to simply run a search multiple times and report some statistics (e.g., average and standard deviation and/or percentiles like p95).

代替の選択肢は、単に探索を複数回実行し、何らかの統計（たとえば、平均と標準偏差や p95 のようなパーセンタイル）を報告することです。

This can be used for a subset of tests deemed more important, but it makes the Search Duration problem even more pronounced.

これはより重要とみなされるテストの部分集合に使用できますが、探索時間の問題をさらに顕著にします。

2.5. Throughput with Non-Zero Loss

2.5. 損失がゼロでないスループット

Section 3.17 of [RFC1242] defines Throughput as:

[RFC1242]のSection 3.17 はスループットを次のように定義しています。

The maximum rate at which none of the offered frames are dropped by the device.

デバイスが提供されたフレームを 1 つも破棄しない最大のレート。

Then, it says:

そして、次のように述べています。

Since even the loss of one frame in a data stream can cause significant delays while waiting for the higher level protocols to time out, it is useful to know the actual maximum data rate that the device can support.

データストリームで 1 つのフレームが失われただけでも、上位レベルのプロトコルがタイムアウトするのを待つ間に大きな遅延が生じる可能性があるため、デバイスがサポートできる実際の最大データレートを知ることは有用です。

However, many benchmarking teams accept a low, non-zero Goal Loss Ratio for their Load search.

しかし、多くのベンチマーキングのチームは、負荷の探索に低いがゼロではない目標損失率を受け入れています。

There are many motivations:

多くの動機があります。

  • Networking protocols tolerate frame loss better, compared to the time when [RFC1242] and [RFC2544] were specified.

  • Increased link speeds require Trials sending more frames within the same duration, increasing the chance of a small SUT performance fluctuation being enough to cause frame loss.

  • Because noise-related drops usually arrive in small bursts, their impact on the Trial Loss Ratio is diluted by the longer intervals in which the SUT operates close to its noiseless performance; consequently, the Trial Loss Ratio as an average over the Trial can still end up below the specified Goal Loss Ratio.

  • If an approximation of the SUT noise impact on the Trial Loss Ratio is known, it can be set as the Goal Loss Ratio.

  • [RFC1242] と [RFC2544] が規定された当時と比べて、ネットワーキングのプロトコルはフレームの損失をよりよく許容します。

  • リンク速度の向上により、トライアルは同じ期間内により多くのフレームを送信する必要があり、SUT の性能の小さな変動でもフレームの損失を引き起こすのに十分になる可能性が高まっています。

  • ノイズに関連する破棄は通常小さなバーストで発生するため、トライアル損失率への影響は、SUT がノイズのない性能に近い状態で動作するより長い期間によって薄められます。その結果、トライアル全体の平均としてのトライアル損失率は、指定された目標損失率を下回る可能性があります。

  • トライアル損失率に対する SUT ノイズの影響の近似がわかっている場合は、それを目標損失率として設定できます。

For more information, see Section 5 of [Lencze-Shima] (and the references there) for a few synthetic examples, confirming that each protocol and application can have different realistic Goal Loss Ratios.

詳細については、各プロトコルとアプリケーションが異なる現実的な目標損失率を持ちうることを確認する、いくつかの合成的な例について [Lencze-Shima]のSection 5（とそこにある参考文献）を参照してください。

Regardless of the validity of all similar motivations, support for non-zero Goal Loss Ratios makes a search algorithm applicable for a wider range of use cases than the approach defined in [RFC2544].

同様の動機のすべての妥当性にかかわらず、ゼロでない目標損失率のサポートにより、探索アルゴリズムは [RFC2544] で定義されたアプローチよりも幅広いユースケースに適用できるようになります。

Furthermore, allowing users to specify multiple Goal Loss Ratios, and enabling a single Search to find all relevant bounds, significantly enhances the usefulness of the search algorithm.

さらに、ユーザーが複数の目標損失率を指定でき、単一の探索で関連するすべての境界を見つけられるようにすると、探索アルゴリズムの有用性が大幅に高まります。

Searching for multiple Search Goals also helps to describe the SUT performance spectrum better than the result of a single Search Goal. For example, the repeated wide gap between zero and non-zero loss Loads indicates the noise has a large impact on the observed performance, which is not evident from the result of a single goal Load search procedure.

複数の探索目標を探索することは、単一の探索目標の結果よりも SUT の性能スペクトルをよりよく記述するのにも役立ちます。たとえば、損失ゼロと損失ありの負荷の間に繰り返し広い差があることは、ノイズが観測される性能に大きな影響を与えていることを示しており、これは単一の目標の負荷探索の手順の結果からは明らかではありません。

It is easy to modify the Binary Search to find a Lower Bound for the Load that satisfies a single non-zero Goal Loss Ratio. But how to search for multiple goals at once is not that obvious; hence, the support for multiple Search Goals remains a problem.

二分探索を変更して、単一のゼロでない目標損失率を満たす負荷の下限を見つけるのは簡単です。しかし、複数の目標を一度に探索する方法はそれほど明白ではありません。そのため、複数の探索目標のサポートは依然として問題です。

At the time of writing, there does not seem to be a consensus in the industry on which Goal Loss Ratio is the best. For users, performance of higher protocol layers is important, for example, goodput of TCP connection (TCP throughput [RFC6349]), but the relationship between goodput and Trial Loss Ratio is not simple. Refer to [Lencze-Kovacs-Shima] for examples of various corner cases, Section 3 of [RFC6349] for Goal Loss Ratios acceptable for an accurate measurement of TCP throughput, and [Ott-Mathis-Semke-Mahdavi] for models and computations of TCP performance in presence of packet loss.

執筆時点では、どの目標損失率が最良かについて業界のコンセンサスはないようです。ユーザーにとっては、より上位のプロトコル層の性能、たとえば TCP 接続のグッドプット（TCP スループット [RFC6349]）が重要ですが、グッドプットとトライアル損失率の関係は単純ではありません。さまざまなコーナーケースの例については [Lencze-Kovacs-Shima] を、TCP スループットの正確な測定に許容できる目標損失率については [RFC6349]のSection 3 を、パケット損失がある場合の TCP の性能のモデルと計算については [Ott-Mathis-Semke-Mahdavi] を参照してください。

2.6. Inconsistent Trial Results

2.6. 一貫性のないトライアル結果

While performing Throughput search by executing a sequence of measurement Trials, there is a risk of encountering inconsistencies between Trial Results.

一連の測定のトライアルを実行してスループットの探索を行う間、トライアル結果の間で不整合に遭遇するリスクがあります。

Examples include but are not limited to:

例には次のものが含まれますが、これらに限定されません。

  • A Trial at the same Load (same or different Trial Duration) results in a different Trial Loss Ratio.

  • A Trial at a larger Load (same or different Trial Duration) results in a lower Trial Loss Ratio.

  • 同じ負荷（同じまたは異なるトライアル期間）でのトライアルが、異なるトライアル損失率になる。

  • より大きな負荷（同じまたは異なるトライアル期間）でのトライアルが、より低いトライアル損失率になる。

The Binary Search never encounters inconsistent Trials. But [RFC2544] hints about the possibility of Inconsistent Trial Results in two places in its text. The first place is Section 24 of [RFC2544], where full Trial Durations are required, presumably because they can be inconsistent with the Trial Results from shorter Trial Durations. The second place is Section 26.3 of [RFC2544], where two successive zero-loss Trials are recommended, presumably because after one zero-loss Trial Result, there can be a subsequent inconsistent non-zero-loss Trial Result.

二分探索が一貫性のないトライアルに遭遇することはありません。しかし、[RFC2544] は本文の 2 か所で一貫性のないトライアル結果の可能性を示唆しています。1 か所目は [RFC2544]のSection 24 で、完全なトライアル期間が要求されていますが、これはおそらく、より短いトライアル期間のトライアル結果と一貫しない可能性があるためです。2 か所目は [RFC2544]のSection 26.3 で、損失ゼロのトライアルを 2 回連続で行うことが推奨されていますが、これはおそらく、1 回の損失ゼロのトライアル結果の後に、一貫しない損失ありのトライアル結果が続く可能性があるためです。

A robust Throughput search algorithm needs to decide how to continue the search in the presence of such inconsistencies. Definitions of Throughput and its test methodology in [RFC1242] and [RFC2544] are not specific enough to imply a unique way of handling such inconsistencies.

堅牢なスループットの探索アルゴリズムは、そのような不整合がある場合に探索をどのように続けるかを決める必要があります。[RFC1242] と [RFC2544] のスループットとそのテスト方法論の定義は、そのような不整合を扱う一意の方法を示唆するほど具体的ではありません。

Ideally, there will be a definition of a new metric that both generalizes Throughput for non-zero Goal Loss Ratio (and other possible repeatability enhancements) while being precise enough to force a specific way to resolve Trial Result inconsistencies. But until such a definition is agreed upon, the correct way to handle Inconsistent Trial Results remains an open problem.

理想的には、ゼロでない目標損失率（およびその他の可能な再現性の向上）についてスループットを一般化し、かつトライアル結果の不整合を解決する特定の方法を強制するのに十分正確な、新しいメトリックの定義があることです。しかし、そのような定義が合意されるまでは、一貫性のないトライアル結果を扱う正しい方法は未解決の問題のままです。

Relevant Lower Bound is the MLRsearch term that addresses this problem.

Relevant Lower Bound は、この問題に対処する MLRsearch の用語です。

4.1. 範囲

  • 1 つ以上の探索目標を含む、コントローラーの入力の必要な構造と属性。

4.2. Architecture Overview

4.2. アーキテクチャーの概要

Although the normative text only references terminology that has already been introduced, explanatory passages sometimes profit from terms that are defined later in the document. To keep the initial read-through clear, this informative section offers a concise, top-down sketch of the complete MLRsearch architecture.

規範的な文章はすでに導入された用語だけを参照していますが、説明の文章では、文書の後半で定義される用語が役立つ場合があります。最初の読み通しをわかりやすく保つために、この参考情報としてのセクションでは、MLRsearch のアーキテクチャー全体の簡潔なトップダウンの概略を提供します。

The architecture is modelled as a set of abstract, interacting components. Information exchange between components is expressed in an imperative-programming style: One component calls another, supplying inputs (arguments) and receiving outputs (return values). This notation is purely conceptual, actual implementations need not exchange explicit messages. When the text contrasts alternative behaviors, it refers to the different implementations of the same component.

アーキテクチャーは、相互作用する抽象的な構成要素の集合としてモデル化されています。構成要素間の情報のやりとりは、命令型プログラミングのスタイルで表現されます。ある構成要素が別の構成要素を calls、入力（引数）を供給し、出力（戻り値）を受け取ります。この表記は純粋に概念的なものであり、実際の実装が明示的なメッセージをやりとりする必要はありません。本文が代替の振る舞いを対比する場合は、同じ構成要素の異なる実装を指しています。

A test procedure is considered compliant with the MLRsearch Specification if it can be conceptually decomposed into the abstract components defined herein, and if each component satisfies the requirements defined for its corresponding MLRsearch Specification section.

テスト手順が、ここで定義された抽象的な構成要素に概念的に分解でき、各構成要素が対応する MLRsearch 仕様のセクションで定義された要件を満たす場合、そのテスト手順は MLRsearch 仕様に compliant しているとみなされます。

The Measurer component is tasked to perform Trials, the Controller component is tasked to select Trial Durations and Loads, and the Manager component is tasked to preconfigure involved entities and to produce the Test Report. The Test Report explicitly states Search Goals (as Controller Input) and corresponding Goal Results (Controller Output).

Measurer 構成要素はトライアルを実行する役割を担い、Controller 構成要素はトライアル期間と負荷を選択する役割を担い、Manager 構成要素は関係するエンティティーを事前に構成して Test Report を作成する役割を担います。テストレポートは、Search Goals（コントローラーの入力として）と対応する Goal Results（コントローラーの出力）を明示的に記載します。

This constitutes one benchmark (single-goal or multi-goal). Repeated or slightly differing benchmarks are realized by calling the Controller once for each benchmark.

これが 1 つの benchmark（単一目標または複数目標）を構成します。繰り返しのベンチマークやわずかに異なるベンチマークは、ベンチマークごとに 1 回コントローラーを呼び出すことで実現されます。

4.2.1. Search

4.2.1. 探索

For one benchmark, the Manager calls a Controller once, and the Controller then invokes the Measurer repeatedly until the Controller decides it has enough information to return its outputs.

1 つのベンチマークについて、マネージャーはコントローラーを 1 回呼び出し、コントローラーは出力を返すのに十分な情報があると判断するまで測定器を繰り返し呼び出します。

The part during which the Controller invokes the Measurer is termed the Search. Any work the Manager performs, either before invoking the Controller or after Controller returns, falls outside the scope of the Search.

コントローラーが測定器を呼び出す部分を Search と呼びます。マネージャーが行う作業は、コントローラーを呼び出す前であれ、コントローラーが戻った後であれ、探索の範囲外です。

The MLRsearch Specification prescribes Regular Goal Results and recommends corresponding Search completion conditions. Irregular Goal Results are also allowed, they have different requirements and their corresponding stopping conditions are out of scope. The Search Result is the combination of regular or irregular results, one for each Search Goal.

MLRsearch 仕様は、通常の目標結果を規定し、対応する探索の完了条件を推奨します。不規則な目標結果も許可されており、それらには異なる要件があり、対応する停止条件は範囲外です。探索結果は、各探索目標について 1 つずつの、通常または不規則な結果の組み合わせです。

Search Results are based on Load Classification. When measured enough, a chosen Load can either achieve or fail each Search Goal (separately), thus becoming a Lower Bound or an Upper Bound for that Search Goal.

探索結果は Load Classification に基づいています。十分に測定されると、選ばれた Load は各探索目標を（個別に）達成するか達成しないかのいずれかとなり、それによってその探索目標の下限または上限になります。

When the Relevant Lower Bound is close enough to the Relevant Upper Bound according to Goal Width, the Regular Goal Result is found. Search stops when all Regular Goal Results are found or when all remaining Search Goals are proven to have only Irregular Goal Results.

Goal Width に従って Relevant Lower Bound が Relevant Upper Bound に十分近い場合、Regular Goal Result が見つかります。探索は、すべての通常の目標結果が見つかったとき、または残りのすべての探索目標が Irregular Goal Results しか持たないことが証明されたときに停止します。

4.2.2. Search Duration

4.2.2. 探索時間

Even if the time it takes the Controller to compute Trial Input attributes for next Trial is negligible; Trials themselves take some time to finish, and SUT behavior affects how quickly stopping conditions can be satisfied.

コントローラーが次のトライアルの Trial Input の属性を計算するのにかかる時間が無視できるとしても、トライアル自体は終了までにある程度の時間がかかり、SUT の振る舞いは停止条件がどれだけ速く満たされるかに影響します。

For large scale tests where many SUT configurations and Traffic Profiles need benchmarking, it is important to optimize the overall duration of one Search, while the time cost of initial configuration tends to be constant. There are three considerations worth discussing for such Search Duration optimization.

多くの SUT の構成とトラフィックプロファイルのベンチマークが必要な大規模なテストでは、初期構成の時間のコストは一定になる傾向があるため、1 回の探索の全体の時間を最適化することが重要です。そのような Search Duration の最適化について議論する価値のある考慮事項が 3 つあります。

Firstly, as SUT behavior can be probabilistic, so can be the Search Duration of each benchmark. The quantity to optimize is the expected value of Search Duration, it should be as short as possible within the intended reliability.

第一に、SUT の振る舞いは確率的でありうるため、各ベンチマークの探索時間も確率的でありえます。最適化すべき量は探索時間の期待値であり、意図した信頼性の範囲内でできるだけ短くすべきです。

Secondly, Search Duration probability distributions with smaller standard deviations are preferred, as it makes it easier to plan execution of multiple benchmarks one-by-one on the same SUT.

第二に、標準偏差の小さい探索時間の確率分布が好まれます。同じ SUT 上で複数のベンチマークを 1 つずつ実行する計画を立てやすくなるからです。

Thirdly, any prior knowledge about SUT behavior can be leveraged into average time gains if the Controller implementation supports corresponding heuristics. Without such knowledge, implementations should focus on worst possible results, as lowering Search Duration for those helps with standard deviation, if not also the expected value.

第三に、コントローラーの実装が対応するヒューリスティックをサポートしていれば、SUT の振る舞いについての事前の知識を平均的な時間の短縮に活用できます。そのような知識がない場合、実装は可能な最悪の結果に焦点を当てるべきです。それらの探索時間を短くすることは、期待値ではないにしても、標準偏差に役立つからです。

Most of optimization heuristics are outside of the scope of this document, but many design decisions were affected by generic optimizations found in practice so far.

最適化のヒューリスティックのほとんどはこの文書の範囲外ですが、多くの設計上の決定は、これまでに実際に見つかった汎用的な最適化の影響を受けています。

4.2.3. Test Report

4.2.3. テストレポート

A primary responsibility of the Manager is to produce a Test Report, which serves as the final and formal output of the test procedure.

マネージャーの主な責任は、テスト手順の最終的かつ正式な出力として機能するテストレポートを作成することです。

This document does not provide a single, complete, normative definition for the structure of the Test Report. For example, the Test Report may contain results for a single benchmark, or it could aggregate results of many benchmarks.

この文書は、テストレポートの構造についての単一の完全で規範的な定義を提供しません。たとえば、テストレポートには単一のベンチマークの結果が含まれる場合もあれば、多くのベンチマークの結果を集約する場合もあります。

Instead, normative requirements for the content of the Test Report are specified throughout this document in conjunction with the definitions of the quantities and procedures to which they apply. Readers should note that any clause requiring a quantity to be "reported" or "stated in the Test Report" constitutes a normative requirement on the content of this final artifact.

代わりに、テストレポートの内容についての規範的な要件は、それらが適用される量と手順の定義とともに、この文書全体を通じて規定されています。読者は、量が「報告される」ことや「テストレポートに記載される」ことを要求する条項は、この最終的な成果物の内容についての規範的な要件を構成することに注意すべきです。

Even where not stated explicitly, the "Reporting format" paragraphs in [RFC2544] are still requirements on Test Reports if they apply to an MLRsearch benchmark.

明示的に述べられていない場合でも、[RFC2544] の "Reporting format" の段落は、MLRsearch のベンチマークに適用される場合、テストレポートについての要件となります。

4.2.4. Behavior Correctness

4.2.4. 振る舞いの正しさ

The MLRsearch Specification by itself does not guarantee that the Search ends in finite time, as the freedom the Controller has for Load selection also allows for clearly deficient choices.

コントローラーが負荷の選択について持つ自由は明らかに欠陥のある選択も許すため、MLRsearch 仕様自体は、探索が有限時間で終了することを保証しません。

For deeper insights on these matters, refer to [FDio-CSIT-MLRsearch].

これらの事柄についてのより深い洞察については [FDio-CSIT-MLRsearch] を参照してください。

The primary MLRsearch implementation, used as the prototype for this specification, is [PyPI-MLRsearch].

この仕様のプロトタイプとして使用された主要な MLRsearch の実装は [PyPI-MLRsearch] です。

4.3. Quantities

4.3. 量

The MLRsearch Specification relies on several specific quantities.

MLRsearch 仕様は、いくつかの特定の quantities に依存しています。

In physics, a single magnitude can be expressed in multiple ways as a product of a unit and a value. This document uses the computer science vocabulary, where the term "quantity" can describe multiple variables or constants at once.

物理学では、単一の大きさを unit と value の積として複数の方法で表現できます。この文書はコンピューターサイエンスの語彙を使用しており、「量」という用語は複数の変数や定数を一度に記述できます。

One instance of a scalar quantity is called a value, with the corresponding unit only mentioned when needed. Where the context allows, a shorter phrase is used, for example, "Load" instead of "value of the Load quantity".

スカラー量の 1 つの instance を value と呼び、対応する単位は必要な場合にのみ言及します。文脈が許す場合は、より短い言い回し、たとえば「負荷の量の値」の代わりに「負荷」を使用します。

In general, the MLRsearch Specification does not prescribe particular units to be used, but it is REQUIRED for the Test Report to state all the units. For example, ratio quantities can be dimensionless numbers between zero and one but may be expressed as percentages instead.

一般に、MLRsearch 仕様は使用する特定の単位を規定しませんが、テストレポートにすべての単位を記載することが要求されています（REQUIRED）。たとえば、比率の量は 0 から 1 の間の無次元の数にできますが、代わりにパーセンテージで表すこともできます。

In rare cases, a primary unit is mentioned, usually when comparison across different Traffic Profiles would be otherwise ambiguous. Some units MAY be preferred by some implementations, for example, when they round the values to integers.

まれに、primary unit に言及することがあります。通常は、そうしなければ異なるトラフィックプロファイル間の比較があいまいになる場合です。一部の実装は、たとえば値を整数に丸める場合など、一部の単位を好んで使用してもよいです（MAY）。

For convenience, a group of quantities can be treated as a composite quantity. One constituent of a composite quantity is called an attribute. A group of attribute values is called an instance of that composite quantity.

便宜上、量のグループを composite 量として扱うことができます。複合量の 1 つの構成要素を attribute と呼びます。属性の値のグループを、その複合量の instance と呼びます。

Some attributes may depend on others and can be computed from other attributes. Such quantities are called derived quantities.

一部の属性はほかの属性に依存し、ほかの属性から計算できる場合があります。そのような量を derived 量と呼びます。

4.3.1. Current and Final Values

4.3.1. 現在の値と最終的な値

Some quantities are defined in a way that makes it possible to compute their values in the middle of a Search. Other quantities are specified so that their values can be computed only after the Search ends. Some quantities are important only after a Search ends, but their values are also computable before a Search ends.

一部の量は、探索の途中でその値を計算できるように定義されています。ほかの量は、探索の終了後にのみその値を計算できるように規定されています。一部の量は探索の終了後にのみ重要ですが、その値は探索の終了前にも計算できます。

For a quantity that is computable before a Search ends, the adjective current is used to mark a value of that quantity available before the Search ends. When such value is relevant for the Search Result, the adjective final is used to denote the value of that quantity at the end of the Search.

探索の終了前に計算可能な量について、探索の終了前に利用可能なその量の値を示すために形容詞 current を使用します。そのような値が探索結果に関係する場合、探索の終了時のその量の値を示すために形容詞 final を使用します。

If a time evolution of such a dynamic quantity is guided by configuration quantities, those adjectives can be used to distinguish such quantities. For example, if the current value of "duration" (a dynamic quantity) increases from "initial duration" to "final duration" (configuration quantities), all the quoted names denote separate but related quantities. As the naming suggests, the final value of the duration quantity is expected to be equal to the "final duration" value.

そのような動的な量の時間的な変化が構成の量によって導かれる場合、それらの形容詞を使用してそのような量を区別できます。たとえば、"duration"（動的な量）の現在の値が "initial duration" から "final duration"（構成の量）に増加する場合、引用符で囲んだすべての名前は別個だが関連する量を示します。命名が示すように、duration の量の最終的な値は "final duration" の値に等しくなることが期待されます。

4.4.1. SUT

4.4.1. SUT

SUT is defined in Section 3.1.2 of [RFC2285] as follows.

SUT は [RFC2285]のSection 3.1.2 で次のように定義されています。

Definition:

The collective set of network devices to which stimulus is offered as a single entity and response measured.

Discussion:

A SUT consisting of a single network device is allowed by this definition.

In software-based networking, SUT may comprise a multitude of networking applications and the entire host hardware and software execution environment.

SUT is the only entity that can be benchmarked directly, even though only the performance of some sub-components are of interest.

For example, Section 6.1 of [RFC2544] describes a single SUT consisting of DUT 1, DUT 2, and a WAN link between them.

Definition:

単一のエンティティーとして刺激が与えられ、応答が測定されるネットワークデバイスの集まり。

Discussion:

この定義では、単一のネットワークデバイスで構成される SUT も許可されます。

ソフトウェアベースのネットワーキングでは、SUT は多数のネットワーキングのアプリケーションと、ホストのハードウェアとソフトウェアの実行環境全体で構成される場合があります。

一部のサブコンポーネントの性能だけが関心の対象である場合でも、SUT は直接ベンチマークできる唯一のエンティティーです。

たとえば、[RFC2544]のSection 6.1 は、DUT 1、DUT 2、およびそれらの間の WAN リンクで構成される単一の SUT を説明しています。

4.4.2. DUT

4.4.2. DUT

DUT is defined in Section 3.1.1 of [RFC2285] as follows.

DUT は [RFC2285]のSection 3.1.1 で次のように定義されています。

Definition:

The network forwarding device to which stimulus is offered and response measured.

Discussion:

Contrary to SUT, the DUT stimulus and response are frequently initiated and observed only indirectly, on different parts of SUT.

DUT, as a sub-component of SUT, is only indirectly mentioned in the MLRsearch Specification but is of key relevance for its motivation. The device can represent a software-based networking function running on commodity x86/ARM CPUs (vs. purpose-built ASICs, NPUs, and FPGAs).

When the MLRsearch Specification mentions SUT configuration, it implies adequate configuration of constituent DUTs, subjected to requirements from Section 7 of [RFC2544].

A well-designed SUT SHOULD have the primary DUT as their performance bottleneck. The ways to achieve and verify that are outside the scope of the MLRsearch Specification. A typical exception to this rule is when DUT has a surprisingly good performance. For example, achieving the line rate does not make the SUT badly designed. This situation is quite common in practice, when the DUT is the bottleneck for a traffic consisting of small frames, but achieves the line rate with large frames.

Definition:

刺激が与えられ、応答が測定されるネットワーク転送デバイス。

Discussion:

SUT とは対照的に、DUT の刺激と応答は、多くの場合、SUT の異なる部分で間接的にのみ開始され観測されます。

SUT のサブコンポーネントとしての DUT は、MLRsearch 仕様では間接的にしか言及されませんが、その動機にとって重要な関連性があります。このデバイスは、コモディティーの x86/ARM CPU 上で動作するソフトウェアベースのネットワーキング機能（専用の ASIC、NPU、FPGA に対して）を表すことができます。

MLRsearch 仕様が SUT の構成に言及する場合、それは [RFC2544]のSection 7 の要件に従った、構成要素の DUT の適切な構成を意味します。

よく設計された SUT は、主な DUT を性能のボトルネックとすべきです（SHOULD）。それを達成し検証する方法は MLRsearch 仕様の範囲外です。この規則の典型的な例外は、DUT が驚くほどよい性能を持つ場合です。たとえば、ラインレートを達成しても SUT の設計が悪いことにはなりません。この状況は実際にはかなり一般的で、DUT は小さなフレームで構成されるトラフィックではボトルネックになりますが、大きなフレームではラインレートを達成します。

4.4.3. Trial

4.4.3. トライアル

A trial is the part of the test described in Section 23 of [RFC2544].

トライアルとは、[RFC2544]のSection 23 で説明されているテストの部分です。

Definition:

A particular test consists of multiple trials. Each trial returns one piece of information, for example, the loss rate at a particular input frame rate. Each trial consists of a number of phases:

  1. If the DUT is a router, send the routing update to the "input" port and pause two seconds to be sure that the routing has settled.
  2. Send the "learning frames" to the "output" port and wait 2 seconds to be sure that the learning has settled. Bridge learning frames are frames with source addresses that are the same as the destination addresses used by the test frames. Learning frames for other protocols are used to prime the address resolution tables in the DUT. The formats of the learning frame that should be used are shown in the Test Frame Formats document.
  3. Run the test trial.
  4. Wait for two seconds for any residual frames to be received.
  5. Wait for at least five seconds for the DUT to restabilize.
Discussion:

The traffic is sent only in phase c) and received in phases c) and d).

Trials are the only stimuli the SUT is expected to experience during the Search.

It is useful to consider the traffic as sent and received by a tester, as implicitly defined in Section 6 of [RFC2544].

The definition above describes some traits but does not use key words as defined in BCP 14 [RFC2119] [RFC8174] to signify the strength of the requirements. For the purposes of the MLRsearch Specification, the test procedure MAY deviate from the description in [RFC2544], but any such deviation MUST be described explicitly in the Test Report. It is still RECOMMENDED to not deviate from the description, as any deviation weakens comparability.

An example of deviation from [RFC2544] is using shorter wait times, compared to those described in phases a), b), d), and e).

[RFC2544] seems to treat phase b) as any type of configuration that cannot be configured only once (by the Manager, before the Search starts), as some crucial SUT state could time out during the Search. It is RECOMMENDED to interpret the "learning frames" to mean any such time-sensitive per-Trial configuration method, with bridge Media Access Control (MAC) address learning being only one possible example. Appendix C.2.4.1 of [RFC2544] lists another example: ARP with a wait time of 5 seconds.

Some methodologies describe recurring tests. If those are based on Trials, they are treated as multiple independent Trials. That means there are no "recurring trials" treated as a single measurement in MLRsearch, but the Controller MAY repeat the same Trial Inputs to get multiple independent Trial Outputs.

Definition:

特定のテストは複数のトライアルで構成されます。各トライアルは、たとえば特定の入力フレームレートでの損失率のような、1 つの情報を返します。各トライアルはいくつかのフェーズで構成されます。

  1. DUT がルーターの場合は、ルーティングの更新を「入力」ポートに送信し、ルーティングが安定したことを確実にするために 2 秒間休止する。
  2. 「学習フレーム」を「出力」ポートに送信し、学習が安定したことを確実にするために 2 秒間待つ。ブリッジの学習フレームは、テストフレームが使用する宛先アドレスと同じ送信元アドレスを持つフレームです。ほかのプロトコルの学習フレームは、DUT のアドレス解決テーブルを準備するために使用される。使用すべき学習フレームの形式は、Test Frame Formats の文書に示されている。
  3. テストのトライアルを実行する。
  4. 残りのフレームを受信するために 2 秒間待つ。
  5. DUT が再び安定するまで少なくとも 5 秒間待つ。
Discussion:

トラフィックはフェーズ c) でのみ送信され、フェーズ c) と d) で受信されます。

トライアルは、探索の間に SUT が経験することが期待される唯一の刺激です。

[RFC2544]のSection 6 で暗黙のうちに定義されているように、トラフィックはテスターによって送受信されるものと考えると便利です。

上の定義はいくつかの特徴を説明していますが、要件の強さを示すために BCP 14 [RFC2119] [RFC8174] で定義されているキーワードを使用していません。MLRsearch 仕様の目的では、テスト手順は [RFC2544] の説明から逸脱してもよいです（MAY）。ただし、そのような逸脱はテストレポートに明示的に記述しなければなりません（MUST）。逸脱は比較可能性を弱めるため、説明から逸脱しないことが依然として推奨されます（RECOMMENDED）。

[RFC2544] からの逸脱の例は、フェーズ a)、b)、d)、e) で説明されているものと比べて、より短い待ち時間を使用することです。

[RFC2544] は、探索中に SUT の重要な状態がタイムアウトする可能性があるため、（探索の開始前にマネージャーによって）一度だけ構成することができないあらゆる種類の構成としてフェーズ b) を扱っているようです。「学習フレーム」を、そのような時間に敏感なトライアルごとの構成方法を意味するものとして解釈することが推奨されます（RECOMMENDED）。ブリッジのメディアアクセス制御（MAC）アドレスの学習は、可能な例の 1 つにすぎません。[RFC2544]のAppendix C.2.4.1 は別の例として、5 秒の待ち時間を伴う ARP を挙げています。

一部の方法論は繰り返しのテストを説明しています。それらがトライアルに基づいている場合は、複数の独立したトライアルとして扱われます。つまり、MLRsearch では単一の測定として扱われる「繰り返しのトライアル」は存在しませんが、コントローラーは、複数の独立したトライアルの出力を得るために同じトライアルの入力を繰り返してもよいです（MAY）。

4.4.4. 負荷の量

以下のサブセクションでは、この文書でそのような基礎となる量として使用されるそれらの組み合わせを導入する前に、既存の用語を参照します。

4.4.4.1. Intended Load
4.4.4.1. 意図した負荷

Defined in "Intended load (Iload)" (Section 3.5.1 of [RFC2285]).

"Intended load (Iload)"（[RFC2285]のSection 3.5.1）で定義されています。

4.4.4.2. Offered Load
4.4.4.2. 提供負荷

Defined in "Offered load (Oload)" (Section 3.5.2 of [RFC2285]).

"Offered load (Oload)"（[RFC2285]のSection 3.5.2）で定義されています。

4.4.4.3. Constant Load
4.4.4.3. 一定負荷

Defined in "Constant Load" (Section 3.4 of [RFC1242]).

"Constant Load"（[RFC1242]のSection 3.4）で定義されています。

4.4.4.4. Load
4.4.4.4. 負荷
Definition:

Load is a global per-interface Intended Load usable for a Trial.

Discussion:

For specification purposes, Load is also assumed to be Constant Load.

Similarly to existing definitions, this quantity is related to one (input or output) SUT interface.

In the common case of bidirectional traffic, as described in "Bidirectional traffic" (Section 14 of [RFC2544]), Load is the "data rate" per each direction, half of the "sum of data rates".

The Test Report MAY present the aggregate Load across multiple interfaces, treating it as the same magnitude expressed using different units. Each reported Load MUST unambiguously state whether it refers to (i) a single interface, (ii) a specified subset of interfaces (such as all logical interfaces mapped to one physical port), or (iii) the total across every interface. For any aggregate Load value, the report MUST also give the fixed conversion factor that links the per-interface and multi-interface Load values.

The per-interface Load remains the primary unit, consistent with the prevailing practice described in [RFC1242], [RFC2544], and [RFC2285].

The previous paragraph also applies to other terms related to Load. For example, tests with symmetric bidirectional traffic MAY report Load-related values as "bidirectional load" (double of "unidirectional load" if that is distinguished in the same Test Report).

Definition:

負荷（Load）は、トライアルに使用できる、グローバルなインターフェイスごとの意図した負荷です。

Discussion:

仕様の目的では、負荷は一定負荷であることも仮定されます。

既存の定義と同様に、この量は SUT の 1 つの（入力または出力の）インターフェイスに関連しています。

"Bidirectional traffic"（[RFC2544]のSection 14）で説明されている双方向のトラフィックという一般的な場合、負荷は各方向ごとの「データレート」であり、「データレートの合計」の半分です。

テストレポートは、複数のインターフェイスにわたる aggregate Load を、異なる単位を使用して表された同じ大きさとして扱って提示してもよいです（MAY）。報告される各負荷は、それが（i）単一のインターフェイス、（ii）指定されたインターフェイスの部分集合（1 つの物理ポートにマッピングされたすべての論理インターフェイスなど）、（iii）すべてのインターフェイスの合計のいずれを指すかを明確に記載しなければなりません（MUST）。集約された負荷の値については、レポートは、インターフェイスごとの負荷の値と複数インターフェイスの負荷の値を結び付ける固定の変換係数も示さなければなりません（MUST）。

[RFC1242]、[RFC2544]、[RFC2285] で説明されている一般的な慣行と一致して、インターフェイスごとの負荷が主要な単位のままです。

前の段落は、負荷に関連するほかの用語にも当てはまります。たとえば、対称的な双方向のトラフィックを用いるテストでは、負荷に関連する値を「双方向の負荷」（同じテストレポートで区別されている場合は「単方向の負荷」の 2 倍）として報告してもよいです（MAY）。

Besides Trial Load, the Relevant Lower Bound will be another example of a newly defined quantity based on Load.

トライアル負荷に加えて、関連する下限も、負荷に基づく新しく定義される量の例になります。

4.4.5. 転送レートの量

負荷がトライアルの入力として機能する主要な量であるのと同様に、転送レートはトライアルの出力を記述する既存の量です。

Besides Trial Forwarding Rate, the Conditional Throughput will be another example of a newly defined quantity based on Forwarding Rate.

トライアル転送レートに加えて、条件付きスループットも、転送レートに基づく新しく定義される量の例になります。

4.4.5.1. 転送レート

4.4.5.2. Throughput
4.4.5.2. スループット

Defined in "Throughput" (Section 3.17 of [RFC1242]).

"Throughput"（[RFC1242]のSection 3.17）で定義されています。

The methodology of measuring Throughput is codified in "Throughput" (Section 26.1 of [RFC2544]).

スループットを測定する方法論は "Throughput"（[RFC2544]のSection 26.1）で成文化されています。

4.5. Trial Terms

4.5. トライアルの用語

This section defines new terms and redefines existing terms for quantities relevant as inputs or outputs of a Trial, as handled by the Measurer component. This also includes any derived quantities related to results of one Trial.

このセクションでは、測定器の構成要素によって扱われる、トライアルの入力や出力として関係する量についての新しい用語を定義し、既存の用語を再定義します。これには、1 つのトライアルの結果に関連する派生量も含まれます。

4.5.1. Trial Duration

4.5.1. トライアル期間

Definition:

Trial Duration is the intended duration of phase c) of a Trial.

Discussion:

The value MUST be positive.

While any positive real value may be provided, some Measurer implementations MAY limit possible values, e.g., by rounding down to the nearest integer in seconds. In that case, it is RECOMMENDED to give such inputs to the Controller so that the Controller implementation only generates the accepted values.

Definition:

トライアル期間（Trial Duration）は、トライアルのフェーズ c) の意図した期間です。

Discussion:

値は正でなければなりません（MUST）。

任意の正の実数値を提供できますが、一部の測定器の実装は、たとえば秒単位で最も近い整数に切り捨てることで、可能な値を制限してもよいです（MAY）。その場合、コントローラーの実装が受け入れられる値だけを生成するように、そのような入力をコントローラーに与えることが推奨されます（RECOMMENDED）。

4.5.2. Trial Load

4.5.2. トライアル負荷

Definition:

Trial Load is the Load used in a specific Trial.

Discussion:

This is a Load-related quantity that is tied to a single Trial, to distinguish it from later derived quantities that are not tied that way.

For specification purposes, it is assumed that this is a Constant Load by default. Informally, Trial Load is a single number that can "scale" any traffic pattern as long as the intuition of a load intended against a single interface can be applied.

It MAY be possible to use a Trial Load to describe non-constant traffic (using average load when the traffic consists of repeated bursts of frames, e.g., as suggested in Section 21 of [RFC2544]). In the case of a non-constant load, the Test Report MUST explicitly mention exactly how non-constant the traffic is and how it reacts to the Trial Load value. But the rest of the MLRsearch Specification assumes that is not the case, to avoid discussing corner cases (e.g., which values are possible within medium limitations).

Similarly, traffic patterns where different interfaces are subject to different loads MAY be described by a single Trial Load value (e.g., using the largest Intended Load among interfaces), but again, the Test Report MUST explicitly describe how the traffic pattern reacts to the Trial Load value, and this specification does not discuss all the implications of that approach.

Traffic patterns where a single Trial Load does not describe their scaling cannot be used for MLRsearch benchmarks.

Similarly to Trial Duration, some Measurers MAY limit the possible values of Trial Load. Contrary to Trial Duration, documenting such behavior in the Test Report is OPTIONAL. This is because the load differences are negligible (and frequently undocumented) in practice.

The Controller MAY select the Trial Load and Trial Duration values in a way that would not be possible to achieve using any integer number of data frames.

Given that the Trial Load is a quantity based on Load, Test Report MAY express this quantity using multi-interface values, as the sum of Intended Loads over input interfaces.

Definition:

トライアル負荷（Trial Load）は、特定のトライアルで使用される負荷です。

Discussion:

これは単一のトライアルに結び付けられた負荷に関連する量であり、そのように結び付けられていない後の派生量と区別するためのものです。

仕様の目的では、これはデフォルトで一定負荷であると仮定されます。非公式には、トライアル負荷は、単一のインターフェイスに対して意図された負荷という直観を適用できる限り、任意のトラフィックパターンを「スケール」できる単一の数です。

一定でないトラフィックを記述するためにトライアル負荷を使用できる場合があります（MAY）（トラフィックがフレームの繰り返しのバーストで構成される場合に、たとえば [RFC2544]のSection 21 で提案されているように平均負荷を使用する）。一定でない負荷の場合、テストレポートは、トラフィックがどの程度一定でないか、トライアル負荷の値にどのように反応するかを正確に明示的に述べなければなりません（MUST）。しかし、MLRsearch 仕様の残りの部分は、コーナーケース（たとえば、媒体の制限内でどの値が可能か）の議論を避けるために、そうではないと仮定しています。

同様に、異なるインターフェイスが異なる負荷を受けるトラフィックパターンを、単一のトライアル負荷の値で記述してもよいです（MAY）（たとえば、インターフェイスの中で最大の意図した負荷を使用する）。しかし、やはりテストレポートは、トラフィックパターンがトライアル負荷の値にどのように反応するかを明示的に記述しなければなりません（MUST）。この仕様は、そのアプローチのすべての意味合いについては議論しません。

単一のトライアル負荷ではスケーリングを記述できないトラフィックパターンは、MLRsearch のベンチマークには使用できません。

トライアル期間と同様に、一部の測定器はトライアル負荷の可能な値を制限してもよいです（MAY）。トライアル期間とは対照的に、そのような振る舞いをテストレポートに文書化することは選択可能な（OPTIONAL）ものです。これは、実際には負荷の差は無視できる（そして多くの場合文書化されない）からです。

コントローラーは、どのような整数個のデータフレームを使用しても達成できないような方法で、トライアル負荷とトライアル期間の値を選択してもよいです（MAY）。

トライアル負荷が負荷に基づく量であることを考えると、テストレポートは、入力インターフェイスにわたる意図した負荷の合計として、複数インターフェイスの値を使用してこの量を表してもよいです（MAY）。

4.5.3. Trial Input

4.5.3. トライアル入力

Definition:

Trial Input is a composite quantity, consisting of exactly two attributes: Trial Duration and Trial Load.

Discussion:

When talking about a set of Trials, it is common to say Trial Inputs to denote all corresponding Trial Input instances.

One Trial Input instance acts as the input for one call of the Measurer component.

Contrary to other composite quantities, MLRsearch implementations MUST NOT add optional attributes into Trial Input. This improves interoperability between various implementations of a Controller and a Measurer.

Note that both attributes are intended quantities, as only those can be fully controlled by the Controller. The actual offered quantities, as realized by the Measurer, can be different (and must be different if not multiplying into an integer number of frames), but questions around those offered quantities are generally outside of the scope of this document.

Definition:

トライアル入力（Trial Input）は、トライアル期間とトライアル負荷という、ちょうど 2 つの属性で構成される複合量です。

Discussion:

トライアルの集合について話す場合、対応するすべてのトライアル入力のインスタンスを示すために Trial Inputs と言うのが一般的です。

1 つのトライアル入力のインスタンスは、測定器の構成要素の 1 回の呼び出しの入力として機能します。

ほかの複合量とは対照的に、MLRsearch の実装はトライアル入力にオプションの属性を追加してはなりません（MUST NOT）。これにより、コントローラーと測定器のさまざまな実装の間の相互運用性が向上します。

コントローラーが完全に制御できるのはそれらだけであるため、どちらの属性も intended 量であることに注意してください。測定器によって実現される実際の offered 量は異なる場合があります（そして、掛け合わせて整数個のフレームにならない場合は異なる必要があります）が、それらの提供される量に関する問題は一般にこの文書の範囲外です。

4.5.4. Traffic Profile

4.5.4. トラフィックプロファイル

Definition:

Traffic Profile is a composite quantity containing all attributes other than Trial Load and Trial Duration that are needed for the unique determination of the Trial to be performed.

Discussion:

All the attributes MUST be constant during the Search, and the composite is conceptually configured on the Measurer by the Manager before the Search starts. This is why the Traffic Profile is not part of the Trial Input.

Specification of traffic properties included in the Traffic Profile is the responsibility of the Manager, but the specific configuration mechanisms are outside of the scope of this document. Implementations are allowed to include this data in Controller calls to the Measurer, as long as its impact is functionally constant.

Implementations of the Manager and the Measurer should be aware of their common set of capabilities well enough to ensure that the Traffic Profile instance uniquely defines the traffic during the Search. Typically, Manager and Measurer implementations are tightly integrated.

Integration efforts between independent Manager and Measurer implementations are outside of the scope of this document. An example standardization effort is described in [Vassilev].

Examples of common traffic properties include:

  • Data link frame size:

    • Fixed sizes as listed in Section 3.5 of [RFC1242] and in Section 9 of [RFC2544]

    • "Internet Mix" (IMIX) mixed frame sizes as defined in [RFC6985]

  • Frame formats and protocol addresses:

    • Sections 8 and 12 of [RFC2544] and Appendix C of [RFC2544]

Other traffic properties that need to somehow be specified in Traffic Profile, and MUST be mentioned in Test Report if they apply to the benchmark, include:

  • symmetric bidirectional traffic from Section 14 of [RFC2544],

  • fully meshed traffic from Section 3.3.3 of [RFC2285],

  • modifiers from Section 11 of [RFC2544], and

  • IP version mixing from Section 5.3 of [RFC8219].

Definition:

トラフィックプロファイル（Traffic Profile）は、実行されるトライアルを一意に決定するために必要な、トライアル負荷とトライアル期間以外のすべての属性を含む複合量です。

Discussion:

すべての属性は探索中に一定でなければなりません（MUST）。また、この複合量は、探索の開始前にマネージャーによって測定器上で概念的に構成されます。これが、トラフィックプロファイルがトライアル入力の一部ではない理由です。

トラフィックプロファイルに含まれるトラフィックの特性の規定はマネージャーの責任ですが、具体的な構成のメカニズムはこの文書の範囲外です。実装は、その影響が機能的に一定である限り、このデータをコントローラーから測定器への呼び出しに含めることが許可されています。

マネージャーと測定器の実装は、トラフィックプロファイルのインスタンスが探索中のトラフィックを一意に定義することを確保するのに十分なほど、共通の能力の集合を認識しているべきです。通常、マネージャーと測定器の実装は緊密に統合されています。

独立したマネージャーと測定器の実装の間の統合の取り組みは、この文書の範囲外です。標準化の取り組みの例は [Vassilev] で説明されています。

一般的なトラフィックの特性の例には次のものが含まれます。

  • データリンクのフレームサイズ:

    • [RFC1242]のSection 3.5 と [RFC2544]のSection 9 に挙げられている固定のサイズ

    • [RFC6985] で定義されている "Internet Mix"（IMIX）の混合フレームサイズ

  • フレームの形式とプロトコルのアドレス:

    • [RFC2544] のセクション 8 と 12、および [RFC2544]のAppendix C

トラフィックプロファイルで何らかの形で規定する必要があるその他のトラフィックの特性には、次のものが含まれます。これらがベンチマークに適用される場合は、テストレポートで言及しなければなりません（MUST）。

  • [RFC2544]のSection 14 の対称的な双方向のトラフィック

  • [RFC2285]のSection 3.3.3 の完全メッシュのトラフィック

  • [RFC2544]のSection 11 の修飾子

  • [RFC8219]のSection 5.3 の IP バージョンの混在

4.5.5. Trial Forwarding Ratio

4.5.5. トライアル転送率

Definition:

The Trial Forwarding Ratio is a dimensionless floating point quantity. Its value MUST range between 0.0 and 1.0, both inclusive. It is computed by dividing the number of frames successfully forwarded by the SUT by the total number of frames expected to be forwarded during the Trial.

Discussion:

For most Traffic Profiles, "expected to be forwarded" means "intended to get received by a SUT from the tester". This SHOULD be the default interpretation. However, if this is not the case, the Test Report MUST describe the Traffic Profile in sufficient enough detail to imply how the Trial Forwarding Ratio should be computed.

The Trial Forwarding Ratio MAY be expressed in other units (e.g., as a percentage) in the Test Report.

Note that, contrary to Load terms, frame counts used to compute the Trial Forwarding Ratio are generally aggregates over all SUT output interfaces, as most test procedures verify all outgoing frames. The procedure for [RFC2544] Throughput counts received frames, so it implies bidirectional counts for bidirectional traffic, even though the final value is the "rate" that is still per-interface. For example, in a test with symmetric bidirectional traffic, if one direction is forwarded without any losses, but the opposite direction does not forward at all, the Trial Forwarding Ratio would be 0.5 (50%).

In future extensions, more general ways to compute the Trial Forwarding Ratio may be allowed, but the current MLRsearch Specification relies on this specific averaged counters approach.

Definition:

トライアル転送率（Trial Forwarding Ratio）は無次元の浮動小数点の量です。その値は 0.0 から 1.0 まで（両端を含む）の範囲でなければなりません（MUST）。これは、SUT によって正常に転送されたフレームの数を、トライアル中に転送されることが期待されるフレームの総数で割ることで計算されます。

Discussion:

ほとんどのトラフィックプロファイルでは、「転送されることが期待される」とは「テスターから SUT によって受信されることが意図された」ことを意味します。これをデフォルトの解釈とすべきです（SHOULD）。ただし、そうでない場合、テストレポートは、トライアル転送率をどのように計算すべきかがわかるのに十分な詳細でトラフィックプロファイルを記述しなければなりません（MUST）。

トライアル転送率は、テストレポートでほかの単位（たとえばパーセンテージ）で表してもよいです（MAY）。

負荷の用語とは対照的に、ほとんどのテスト手順はすべての送出フレームを検証するため、トライアル転送率を計算するために使用されるフレーム数は、一般に SUT のすべての出力インターフェイスにわたる集計であることに注意してください。[RFC2544] のスループットの手順は受信したフレームを数えるため、最終的な値はインターフェイスごとの「レート」のままですが、双方向のトラフィックでは双方向の数を意味します。たとえば、対称的な双方向のトラフィックを用いるテストで、一方の方向は損失なしで転送されるが、反対の方向はまったく転送されない場合、トライアル転送率は 0.5（50%）になります。

将来の拡張では、トライアル転送率を計算するより一般的な方法が許可される可能性がありますが、現在の MLRsearch 仕様は、この特定の平均化されたカウンターのアプローチに依存しています。

4.5.6. Trial Loss Ratio

4.5.6. トライアル損失率

Definition:

The Trial Loss Ratio is equal to one minus the Trial Forwarding Ratio.

Discussion:

When expressing ratio values as percentages, the Trial Loss Ratio is equal to 100% minus the Trial Forwarding Ratio.

This is almost identical to Frame Loss Rate in Section 3.6 of [RFC1242]. The only minor differences are that Trial Loss Ratio does not need to be expressed as a percentage, and Trial Loss Ratio is explicitly based on averaged frame counts when more than one traffic direction is present.

Definition:

トライアル損失率（Trial Loss Ratio）は、1 からトライアル転送率を引いたものに等しくなります。

Discussion:

比率の値をパーセンテージで表す場合、トライアル損失率は 100% からトライアル転送率を引いたものに等しくなります。

これは [RFC1242]のSection 3.6 のフレーム損失率とほぼ同一です。わずかな違いは、トライアル損失率はパーセンテージで表す必要がないことと、トライアル損失率は複数のトラフィックの方向が存在する場合に明示的に平均化されたフレーム数に基づいていることだけです。

4.5.7. Trial Forwarding Rate

4.5.7. トライアル転送レート

Definition:

The Trial Forwarding Rate is a derived quantity, computed by multiplying the Trial Load by the Trial Forwarding Ratio.

Discussion:

Despite the similar name, this quantity differs substantially from Forwarding Rate.

Definition:

トライアル転送レート（Trial Forwarding Rate）は、トライアル負荷にトライアル転送率を掛けることで計算される派生量です。

Discussion:

名前は似ていますが、この量は転送レートとは大きく異なります。

Under the method described in [RFC2285], each output interface is measured separately, so every interface may report a different Forwarding Rate. The Trial Forwarding Rate, by contrast, uses a single set of frame counts and therefore yields one value that represents the whole system while still preserving the direct relation to the per-interface Load.

[RFC2285] で説明されている方法では、各出力インターフェイスが個別に測定されるため、インターフェイスごとに異なる転送レートを報告する可能性があります。これに対して、トライアル転送レートは単一のフレーム数の集合を使用するため、インターフェイスごとの負荷との直接の関係を維持しながら、システム全体を表す 1 つの値を生成します。

When the Traffic Profile is symmetric and bidirectional, as defined in Section 14 of [RFC2544], the Trial Forwarding Rate is numerically equal to the arithmetic average of the individual per-interface Forwarding Rates.

[RFC2544]のSection 14 で定義されているように、トラフィックプロファイルが対称的で双方向の場合、トライアル転送レートは、インターフェイスごとの個々の転送レートの算術平均に数値的に等しくなります。

For more complex traffic patterns, such as many-to-one, as mentioned in "Partially meshed traffic" (Section 3.3.2 of [RFC2285]), the meaning of Trial Forwarding Rate is less straightforward. For example, if two input interfaces receive one million frames per second (fps) each, and a single interface outputs 1.4 million fps, the Trial Load is 1 million fps, the Trial Loss Ratio is 30%, and the Trial Forwarding Rate is 0.7 million fps.

"Partially meshed traffic"（[RFC2285]のSection 3.3.2）で言及されている多対一のような、より複雑なトラフィックパターンでは、トライアル転送レートの意味はそれほど単純ではありません。たとえば、2 つの入力インターフェイスがそれぞれ毎秒 100 万フレーム（fps）を受信し、単一のインターフェイスが 140 万 fps を出力する場合、トライアル負荷は 100 万 fps、トライアル損失率は 30%、トライアル転送レートは 70 万 fps です。

Because Trial Forwarding Rate is anchored to the Load defined for one interface, a Test Report MAY show it either as the single averaged figure just described or as the sum of the separate per-interface Forwarding Rates. For the example above, the aggregate Trial Forwarding Rate is 1.4 million fps.

トライアル転送レートは 1 つのインターフェイスについて定義された負荷に基づいているため、テストレポートは、それをいま説明した単一の平均化された数値として、またはインターフェイスごとの個別の転送レートの合計として示してもよいです（MAY）。上の例では、aggregate のトライアル転送レートは 140 万 fps です。

4.5.8. Trial Effective Duration

4.5.8. トライアル実効期間

Definition:

The Trial Effective Duration is a time quantity related to a Trial. By default, it is equal to the Trial Duration.

Discussion:

This is an OPTIONAL feature. If the Measurer does not return any Trial Effective Duration value, the Controller MUST use the Trial Duration value from its Trial Input instead.

The Trial Effective Duration MAY be any positive time quantity chosen by the Measurer to be used for time-based decisions in the Controller.

The Test Report MUST explain how the Measurer computes the returned Trial Effective Duration values if they are not always equal to the Trial Duration.

This feature can be beneficial for time-critical benchmarks designed to manage the overall Search Duration, rather than solely the traffic portion of it. An approach is to measure the duration of the whole Trial (including all wait times) and use that as the Trial Effective Duration.

This is also a way for the Measurer to inform the Controller about its surprising behavior, for example, when rounding the Trial Duration value.

Definition:

トライアル実効期間（Trial Effective Duration）は、トライアルに関連する時間の量です。デフォルトでは、トライアル期間に等しくなります。

Discussion:

これは選択可能な（OPTIONAL）機能です。測定器がトライアル実効期間の値を返さない場合、コントローラーは代わりにトライアル入力のトライアル期間の値を使用しなければなりません（MUST）。

トライアル実効期間は、コントローラーでの時間に基づく決定に使用するために測定器が選んだ、任意の正の時間の量にしてもよいです（MAY）。

返されるトライアル実効期間の値が常にトライアル期間に等しいわけではない場合、テストレポートは、測定器がそれらをどのように計算するかを説明しなければなりません（MUST）。

この機能は、探索時間のトラフィックの部分だけでなく、全体を管理するように設計された、時間が重要なベンチマークに有益な場合があります。1 つのアプローチは、トライアル全体（すべての待ち時間を含む）の期間を測定し、それをトライアル実効期間として使用することです。

これは、たとえばトライアル期間の値を丸める場合など、測定器が自身の意外な振る舞いについてコントローラーに知らせる方法でもあります。

4.5.9. Trial Output

4.5.9. トライアル出力

Definition:

Trial Output is a composite quantity consisting of several attributes. The REQUIRED attributes are Trial Loss Ratio, Trial Effective Duration, and Trial Forwarding Rate.

Discussion:

When referring to more than one Trial, the plural term Trial Outputs is used to collectively describe multiple Trial Output instances.

Measurer implementations MAY provide additional attributes. The Controller implementations SHOULD ignore any such optional attribute they are not familiar with. If a Controller implementation passes selected Trial Outputs to the Manager, the instances SHOULD contain all such additional attributes.

An example of an optional attribute is the aggregate count of frames expected to be forwarded during the Trial, especially if it is not (a rounded-down value) implied by Trial Load and Trial Duration.

While Section 3.5.2 of [RFC2285] requires the Offered Load to be reported for Forwarding Rate measurements, it is not required in the MLRsearch Specification, as Search Results do not depend on it, and technically the Measurer is not performing a direct Forwarding Rate measurement.

Definition:

トライアル出力（Trial Output）は、いくつかの属性で構成される複合量です。トライアル損失率、トライアル実効期間、トライアル転送レートの属性が要求されています（REQUIRED）。

Discussion:

複数のトライアルを指す場合、複数のトライアル出力のインスタンスをまとめて記述するために複数形の用語 Trial Outputs を使用します。

測定器の実装は追加の属性を提供してもよいです（MAY）。コントローラーの実装は、なじみのないそのようなオプションの属性を無視すべきです（SHOULD）。コントローラーの実装が選択したトライアル出力をマネージャーに渡す場合、インスタンスにはそのような追加の属性をすべて含めるべきです（SHOULD）。

オプションの属性の例は、トライアル中に転送されることが期待されるフレームの総数です。特に、それがトライアル負荷とトライアル期間から暗示される（切り捨てられた値）ではない場合です。

[RFC2285]のSection 3.5.2 は転送レートの測定について提供負荷を報告することを要求していますが、探索結果はそれに依存せず、技術的には測定器は直接の転送レートの測定を行っていないため、MLRsearch 仕様ではそれは要求されていません。

4.5.10. Trial Result

4.5.10. トライアル結果

Definition:

Trial Result is a composite quantity, consisting of the Trial Input and the Trial Output as REQUIRED attributes.

Discussion:

When referring to more than one Trial, the plural term Trial Results is used to collectively describe multiple Trial Result instances.

Definition:

トライアル結果（Trial Result）は、トライアル入力とトライアル出力を属性として構成される複合量です。これらの属性は要求されています（REQUIRED）。

Discussion:

複数のトライアルを指す場合、複数のトライアル結果のインスタンスをまとめて記述するために複数形の用語 Trial Results を使用します。

4.6. Goal Terms

4.6. 目標の用語

This section defines new terms for quantities relevant (directly or indirectly) for inputs and outputs of the Controller component.

このセクションでは、コントローラーの構成要素の入力と出力に（直接的または間接的に）関係する量についての新しい用語を定義します。

Several goal attributes are defined before introducing the main composite quantity: the Search Goal.

主要な複合量である Search Goal を導入する前に、いくつかの目標の属性を定義します。

Contrary to other sections, definitions in subsections of this section are necessarily vague, as their fundamental meaning is to act as coefficients in formulas for Controller Output attributes, which are not defined yet.

ほかのセクションとは対照的に、このセクションのサブセクションの定義は必然的にあいまいです。その基本的な意味は、まだ定義されていないコントローラーの出力の属性の式の係数として機能することだからです。

The discussions in this section relate the attributes to concepts mentioned in Section 2, but these discussion paragraphs are short and informal, and they mostly reference later sections, where the impact on Search Results is discussed after introducing the complete set of Auxiliary Terms.

このセクションの議論は、属性を Section 2 で言及されている概念に関連付けていますが、これらの議論の段落は短く非公式であり、主に後のセクションを参照しています。そこでは、補助的な用語の完全な集合を導入した後で、探索結果への影響が議論されます。

4.6.1. Goal Final Trial Duration

4.6.1. 目標最終トライアル期間

Definition:

This is the minimal value for Trial Duration that should be reached. The value MUST be positive.

Discussion:

Certain Trials must reach this minimum Trial Duration before a Load can be classified as a Lower Bound.

The Controller MAY choose shorter Trial Durations, and those Trial Results can be enough for classification as an Upper Bound.

If such shorter Trials prove no Lower Bound exists, this Trial Duration value may never be reached, thus shortening Search Duration.

It is RECOMMENDED for all Search Goals to share the same Goal Final Trial Duration value. Otherwise, Trial Durations larger than the Goal Final Trial Duration may occur, weakening the assumptions the Section 6.1 is based on.

Note that this is a soft limitation for the Trial Duration values selected by the Controller. The Measurer may keep returning different Effective Trial Durations in Trial Results, so Controller implementations MUST be ready to handle such situations.

Definition:

これは、到達すべきトライアル期間の最小値です。値は正でなければなりません（MUST）。

Discussion:

負荷を下限として分類できるようになる前に、特定のトライアルはこの最小のトライアル期間に到達する必要があります。

コントローラーはより短いトライアル期間を選択してもよいです（MAY）。また、それらのトライアル結果は上限としての分類には十分な場合があります。

そのようなより短いトライアルによって下限が存在しないことが証明された場合、このトライアル期間の値には決して到達しない可能性があり、それによって探索時間が短くなります。

すべての探索目標が同じ目標最終トライアル期間の値を共有することが推奨されます（RECOMMENDED）。そうでない場合、目標最終トライアル期間より大きいトライアル期間が発生する可能性があり、Section 6.1 が基づいている仮定が弱まります。

これは、コントローラーが選択するトライアル期間の値に対する緩やかな制限であることに注意してください。測定器はトライアル結果で異なる実効トライアル期間を返し続ける可能性があるため、コントローラーの実装はそのような状況を扱う準備ができていなければなりません（MUST）。

4.6.2. Goal Duration Sum

4.6.2. 目標期間合計

Definition:

This is a threshold value for a particular sum of Trial Effective Duration values. The value MUST be positive.

Discussion:

Informally, this prescribes the sufficient number of Trials performed at a specific Trial Load and Goal Final Trial Duration during the Search.

If the Goal Duration Sum is larger than the Goal Final Trial Duration, multiple Trials may be needed to be performed at the same Load.

Refer to Section 4.10.3 for an example where the possibility of multiple Trials at the same Load is intended.

A Goal Duration Sum shorter than the Goal Final Trial Duration (of the same Search Goal) could reduce Search time but is NOT RECOMMENDED, as the time savings come at the cost of decreased repeatability.

In practice, the Search can spend less than the Goal Duration Sum measuring a Load when the Trial Results are particularly one-sided, but also, the Search can spend more than the Goal Duration Sum measuring a Load when the Trial Results are balanced and include Trials shorter than the Goal Final Trial Duration.

Definition:

これは、トライアル実効期間の値の特定の合計に対するしきい値です。値は正でなければなりません（MUST）。

Discussion:

非公式には、これは、探索中に特定のトライアル負荷と目標最終トライアル期間で実行されるトライアルの十分な数を規定します。

目標期間合計が目標最終トライアル期間より大きい場合、同じ負荷で複数のトライアルを実行する必要がある場合があります。

同じ負荷での複数のトライアルの可能性が意図されている例については Section 4.10.3 を参照してください。

（同じ探索目標の）目標最終トライアル期間より短い目標期間合計は、探索時間を短縮できる可能性がありますが、時間の節約が再現性の低下という代償を伴うため、推奨されません（NOT RECOMMENDED）。

実際には、トライアル結果が特に一方に偏っている場合、探索が負荷の測定に費やす時間は目標期間合計より少なくなる可能性があります。また、トライアル結果が拮抗しており、目標最終トライアル期間より短いトライアルを含む場合、探索が負荷の測定に費やす時間は目標期間合計より多くなる可能性があります。

4.6.3. Goal Loss Ratio

4.6.3. 目標損失率

Definition:

This is a threshold value for Trial Loss Ratio values. The value MUST be non-negative and smaller than one.

Discussion:

A Trial with the Trial Loss Ratio larger than this value signals the SUT may be unable to process this Load well enough.

See Section 2.5 for reasons why users may want to set this value above zero.

Since multiple Trials might be needed for one Load, the Load Classification might be more complicated than the mere comparison of one Trial Loss Ratio to the Goal Loss Ratio.

Definition:

これは、トライアル損失率の値に対するしきい値です。値は非負で 1 より小さくなければなりません（MUST）。

Discussion:

トライアル損失率がこの値より大きいトライアルは、SUT がこの負荷を十分にうまく処理できない可能性があることを示します。

ユーザーがこの値をゼロより大きく設定したい理由については Section 2.5 を参照してください。

1 つの負荷に複数のトライアルが必要な場合があるため、負荷の分類は、1 つのトライアル損失率を目標損失率と単に比較するよりも複雑になる場合があります。

4.6.4. Goal Exceed Ratio

4.6.4. 目標超過率

Definition:

This is a threshold value for a particular ratio of sums of Trial Effective Durations. The value MUST be non-negative and smaller than one.

Discussion:

Informally, this controls the ratio of Trial Results exceeding Goal Loss Ratio. More specifically, up to this proportion of the Trial Results with the Trial Loss Ratio above the Goal Loss Ratio is tolerated at a Lower Bound. This is the full impact if every Trial is measured at Goal Final Trial Duration. The actual full logic is more complicated, as shorter Trials are allowed.

For explainability reasons, the RECOMMENDED value for the Goal Exceed Ratio is 0.5 (50%), and in practice that also leads to the smallest variation in overall Search Duration.

Refer to Section 5.4 for more details.

Definition:

これは、トライアル実効期間の合計の特定の比率に対するしきい値です。値は非負で 1 より小さくなければなりません（MUST）。

Discussion:

非公式には、これは目標損失率を超えるトライアル結果の比率を制御します。より具体的には、下限では、トライアル損失率が目標損失率を上回るトライアル結果がこの割合まで許容されます。これは、すべてのトライアルが目標最終トライアル期間で測定された場合の完全な影響です。より短いトライアルが許可されるため、実際の完全なロジックはより複雑です。

説明可能性の理由から、目標超過率の値は 0.5（50%）にすることが推奨されます（RECOMMENDED）。実際には、それが全体の探索時間の変動を最も小さくすることにもつながります。

詳細は Section 5.4 を参照してください。

4.6.5. Goal Width

4.6.5. 目標幅

Definition:

This is a threshold value for deciding whether two Load values are close enough. This is an OPTIONAL attribute. If present, the value MUST be positive.

Discussion:

Informally, this acts as a stopping condition, controlling the precision of the Goal Result. The Search stops if every Search Goal has reached its precision.

Implementations without this attribute MUST provide the Controller with other means to control the Search stopping conditions.

Absolute Load difference (in fps) and relative Load difference (in percents) are two popular choices, but implementations MAY choose different ways to specify Goal Width.

The Test Report MUST make it clear what specific quantity is used as the Goal Width.

It is RECOMMENDED to express the Goal Width as a relative difference and set it to a value not lower than the Goal Loss Ratio. Refer to Section 5.6.2 for more elaboration on the reasoning.

Definition:

これは、2 つの負荷の値が十分に近いかどうかを決定するためのしきい値です。これは選択可能な（OPTIONAL）属性です。存在する場合、値は正でなければなりません（MUST）。

Discussion:

非公式には、これは停止条件として機能し、目標結果の精度を制御します。探索は、すべての探索目標がその精度に到達した場合に停止します。

この属性を持たない実装は、探索の stopping conditions を制御するためのほかの手段をコントローラーに提供しなければなりません（MUST）。

Absolute Load difference（fps 単位）と relative Load difference（パーセント単位）は 2 つの一般的な選択肢ですが、実装は目標幅を規定する異なる方法を選択してもよいです（MAY）。

テストレポートは、目標幅としてどの具体的な量が使用されているかを明確にしなければなりません（MUST）。

目標幅は相対的な差として表し、目標損失率以上の値に設定することが推奨されます（RECOMMENDED）。その理由についての詳しい説明は Section 5.6.2 を参照してください。

4.6.6. Goal Initial Trial Duration

4.6.6. 目標初期トライアル期間

Definition:

This is the minimal value for the Trial Duration suggested to be used for this goal. This is an OPTIONAL attribute. If present, this value MUST be positive.

Discussion:

This is an example of an optional Search Goal attribute.

A typical default value is equal to the Goal Final Trial Duration value.

Informally, this is the shortest Trial Duration the Controller should select when focusing on this Search Goal.

Note that shorter Trial Durations might still be selected by the Controller, for example, when focusing on a different Search Goal.

The Goal Initial Trial Duration is a mechanism for a user to discourage Trials with Trial Durations deemed as too small to be reliable for a particular SUT and a given Search Goal.

As with Goal Final Trial Duration, the Controller implementation MUST be able to handle possibly lower Effective Trial Duration values returned by the Measurer.

Definition:

これは、この目標に使用することが提案されるトライアル期間の最小値です。これは選択可能な（OPTIONAL）属性です。存在する場合、この値は正でなければなりません（MUST）。

Discussion:

これはオプションの探索目標の属性の例です。

典型的なデフォルト値は、目標最終トライアル期間の値に等しくなります。

非公式には、これは、この探索目標に焦点を当てる場合にコントローラーが選択すべき最も短いトライアル期間です。

たとえば別の探索目標に焦点を当てる場合など、コントローラーがより短いトライアル期間を選択する可能性はあることに注意してください。

目標初期トライアル期間は、特定の SUT と所与の探索目標について、信頼できるには短すぎるとみなされるトライアル期間のトライアルを、ユーザーが抑制するためのメカニズムです。

目標最終トライアル期間と同様に、コントローラーの実装は、測定器が返す可能性のあるより低い実効トライアル期間の値を扱えなければなりません（MUST）。

4.6.7. Search Goal

4.6.7. 探索目標

Definition:

The Search Goal is a composite quantity consisting of several attributes, some of which are required.

The REQUIRED attributes are Goal Final Trial Duration, Goal Duration Sum, Goal Loss Ratio, and Goal Exceed Ratio.

Discussion:

Typical optional attributes are Goal Initial Trial Duration and Goal Width.

Implementations MAY add their own attributes. Those additional attributes may be required by an implementation even if they are not required by the MLRsearch Specification. However, it is RECOMMENDED for those implementations to support missing attributes by providing typical default values.

For example, implementations with Goal Initial Trial Durations might also require users to specify "how quickly" Trial Durations should increase.

Refer to Section 4.10 for important Search Goals.

Definition:

探索目標（Search Goal）は、いくつかの属性で構成される複合量であり、その一部は必須です。

目標最終トライアル期間、目標期間合計、目標損失率、目標超過率の属性が要求されています（REQUIRED）。

Discussion:

典型的なオプションの属性は、目標初期トライアル期間と目標幅です。

実装は独自の属性を追加してもよいです（MAY）。それらの追加の属性は、MLRsearch 仕様で要求されていなくても、実装によって要求される場合があります。ただし、それらの実装は、典型的なデフォルト値を提供することで、欠けている属性をサポートすることが推奨されます（RECOMMENDED）。

たとえば、目標初期トライアル期間を持つ実装は、トライアル期間を「どれだけ速く」増やすべきかをユーザーに指定させる場合もあります。

重要な探索目標については Section 4.10 を参照してください。

4.6.8. Controller Input

4.6.8. コントローラー入力

Definition:

Controller Input is a composite quantity required as an input for the Controller. The only REQUIRED attribute is a list of Search Goals.

Discussion:

MLRsearch implementations MAY use additional attributes. Those additional attributes may be required by an implementation even if they are not required by the MLRsearch Specification.

Formally, the Manager does not apply any Controller configuration apart from one Controller Input instance.

For example, Traffic Profile is conceptually configured on the Measurer by the Manager, without explicit assistance of the Controller.

The order of Search Goals in a list SHOULD NOT have a big impact on Controller Output, but MLRsearch implementations MAY base their behavior on the order of Search Goals in a list.

Definition:

コントローラー入力（Controller Input）は、コントローラーの入力として必要な複合量です。探索目標のリストの属性だけが要求されています（REQUIRED）。

Discussion:

MLRsearch の実装は追加の属性を使用してもよいです（MAY）。それらの追加の属性は、MLRsearch 仕様で要求されていなくても、実装によって要求される場合があります。

形式的には、マネージャーは 1 つのコントローラー入力のインスタンス以外にコントローラーの構成を適用しません。

たとえば、トラフィックプロファイルは、コントローラーの明示的な支援なしに、マネージャーによって測定器上で概念的に構成されます。

リスト内の探索目標の順序はコントローラーの出力に大きな影響を与えるべきではありません（SHOULD NOT）。ただし、MLRsearch の実装は、リスト内の探索目標の順序に基づいて振る舞いを決めてもよいです（MAY）。

4.6.8.1. Max Load
4.6.8.1. 最大負荷
Definition:

Max Load is an OPTIONAL attribute of Controller Input. It is the maximal value the Controller is allowed to select for Trial Loads.

Discussion:

Max Load is an example of an optional attribute (outside the list of Search Goals) required by some implementations of MLRsearch.

If the Max Load is provided, the Controller MUST NOT select Trial Loads larger than that value.

In theory, each Search Goal could have its own Max Load, but as all Trial Results are possibly affecting all Search Goals, it makes more sense for a single Max Load to apply to all Search Goals.

While Max Load is a frequently used configuration parameter, already governed (as Maximum Frame Rate) by Section 20 of [RFC2544] and (as Maximum Offered Load) by Section 3.5.3 of [RFC2285], some implementations MAY detect or discover it, instead of requiring a user-supplied value.

In the MLRsearch Specification, one reason for listing the Relevant Upper Bound as a required attribute is that it makes the Search Result independent of the Max Load value.

Given that Max Load is a quantity based on Load, Test Report MAY express this quantity using multi-interface values, as the sum of per-interface maximal Loads.

Definition:

最大負荷（Max Load）は、コントローラー入力の選択可能な（OPTIONAL）属性です。これは、コントローラーがトライアル負荷に選択することが許可される最大の値です。

Discussion:

最大負荷は、MLRsearch の一部の実装で必要とされる（探索目標のリストの外の）オプションの属性の例です。

最大負荷が提供される場合、コントローラーはその値より大きいトライアル負荷を選択してはなりません（MUST NOT）。

理論上は、各探索目標が独自の最大負荷を持つこともできますが、すべてのトライアル結果がすべての探索目標に影響する可能性があるため、単一の最大負荷をすべての探索目標に適用する方が理にかなっています。

最大負荷はよく使用される構成パラメーターであり、すでに [RFC2544]のSection 20（最大フレームレートとして）と [RFC2285]のSection 3.5.3（最大提供負荷として）によって規定されていますが、一部の実装は、ユーザーが提供する値を要求する代わりに、それを検出または発見してもよいです（MAY）。

MLRsearch 仕様において、関連する上限を必須の属性として挙げている理由の 1 つは、それによって探索結果が最大負荷の値に依存しなくなることです。

最大負荷が負荷に基づく量であることを考えると、テストレポートは、インターフェイスごとの最大の負荷の合計として、複数インターフェイスの値を使用してこの量を表してもよいです（MAY）。

4.6.8.2. Min Load
4.6.8.2. 最小負荷
Definition:

Min Load is an OPTIONAL attribute of Controller Input. It is the minimal value the Controller is allowed to use for Trial Loads.

Discussion:

Min Load is another example of an optional attribute required by some implementations of MLRsearch. Similarly to Max Load, it makes more sense to prescribe one common value, as opposed to using a different value for each Search Goal.

If the Min Load is provided, the Controller MUST NOT select Trial Loads smaller than that value.

Min Load is mainly useful for saving time by failing early, arriving at an Irregular Goal Result when Min Load gets classified as an Upper Bound.

For implementations, it is RECOMMENDED to require Min Load to be non-zero and large enough to allow at least one frame to be forwarded even at the shortest allowed Trial Duration, so that the Trial Loss Ratio is always well-defined and the implementation can apply a relative Goal Width safely.

Given that Min Load is a quantity based on Load, Test Report MAY express this quantity using multi-interface values, as the sum of per-interface minimal Loads.

Definition:

最小負荷（Min Load）は、コントローラー入力の選択可能な（OPTIONAL）属性です。これは、コントローラーがトライアル負荷に使用することが許可される最小の値です。

Discussion:

最小負荷は、MLRsearch の一部の実装で必要とされるオプションの属性の別の例です。最大負荷と同様に、探索目標ごとに異なる値を使用するのではなく、1 つの共通の値を規定する方が理にかなっています。

最小負荷が提供される場合、コントローラーはその値より小さいトライアル負荷を選択してはなりません（MUST NOT）。

最小負荷は主に、最小負荷が上限として分類されたときに不規則な目標結果に到達することで、早期に失敗して時間を節約するのに有用です。

実装に対しては、トライアル損失率が常に明確に定義され、実装が相対的な目標幅を安全に適用できるように、最小負荷がゼロではなく、許可される最短のトライアル期間でも少なくとも 1 つのフレームを転送できるほど十分に大きいことを要求することが推奨されます（RECOMMENDED）。

最小負荷が負荷に基づく量であることを考えると、テストレポートは、インターフェイスごとの最小の負荷の合計として、複数インターフェイスの値を使用してこの量を表してもよいです（MAY）。

4.7. Auxiliary Terms

4.7. 補助的な用語

While the terms defined in this section are not strictly needed when formulating MLRsearch requirements, they simplify the language used in discussion paragraphs and explanation sections.

このセクションで定義される用語は、MLRsearch の要件を定式化する際に厳密には必要ありませんが、議論の段落と説明のセクションで使用される言葉を簡単にします。

4.7.1. Trial Classification

4.7.1. トライアルの分類

When one Trial Result instance is compared to one Search Goal instance, several relations can be named using short adjectives.

1 つのトライアル結果のインスタンスを 1 つの探索目標のインスタンスと比較する場合、いくつかの関係を短い形容詞を使用して名付けることができます。

As Trial Results do not affect each other, this Trial Classification does not change during a Search.

トライアル結果は互いに影響しないため、このトライアルの分類は探索中に変化しません。

4.7.1.1. High-Loss Trial
4.7.1.1. 高損失トライアル

A Trial with a Trial Loss Ratio larger than a Goal Loss Ratio is called a High-Loss Trial, with respect to the given Search Goal (or lossy Trial, if the Goal Loss Ratio is zero).

トライアル損失率が目標損失率より大きいトライアルを、所与の探索目標に関して High-Loss Trial（目標損失率がゼロの場合は lossy Trial）と呼びます。

4.7.1.2. Low-Loss Trial
4.7.1.2. 低損失トライアル

If a Trial is not a High-Loss Trial, it is called a Low-Loss Trial (or zero-loss Trial, if the Goal Loss Ratio is zero).

トライアルが高損失トライアルでない場合、それを Low-Loss Trial（目標損失率がゼロの場合は zero-loss Trial）と呼びます。

4.7.1.3. Short Trial
4.7.1.3. 短いトライアル

A Trial with a Trial Duration shorter than the Goal Final Trial Duration is called a Short Trial with respect to the given Search Goal.

トライアル期間が目標最終トライアル期間より短いトライアルを、所与の探索目標に関して Short Trial と呼びます。

4.7.1.4. Full-Length Trial
4.7.1.4. 完全長のトライアル

A Trial that is not a Short Trial is called a Full-Length Trial.

短いトライアルではないトライアルを Full-Length Trial と呼びます。

Note that this includes Trial Durations larger than the Goal Final Trial Duration.

これには、目標最終トライアル期間より大きいトライアル期間が含まれることに注意してください。

4.7.1.5. Long Trial
4.7.1.5. 長いトライアル

A Trial with a Trial Duration longer than the Goal Final Trial Duration is called a Long Trial.

トライアル期間が目標最終トライアル期間より長いトライアルを Long Trial と呼びます。

4.7.2. Load Classification

4.7.2. 負荷の分類

When a set of all Trial Result instances, performed so far at one Load, is compared to one Search Goal instance, their relation can be named using the concept of a bound.

1 つの負荷でこれまでに実行されたすべてのトライアル結果のインスタンスの集合を 1 つの探索目標のインスタンスと比較する場合、それらの関係は bound の概念を使用して名付けることができます。

In general, such bounds are a current quantity, even though cases of a Load changing its classification more than once during the Search is rare in practice.

一般に、そのような境界は現在の量ですが、探索中に負荷がその分類を複数回変えることは実際にはまれです。

4.7.2.1. Upper Bound
4.7.2.1. 上限
Definition:

A Load is called an Upper Bound if and only if it is classified as such by a Appendix A algorithm for the given Search Goal at the current moment of the Search.

Discussion:

In more detail, the set of all Trial Results performed so far at the Load (and any Trial Duration) is certain to fail to uphold all the requirements of the given Search Goal, mainly the Goal Loss Ratio in combination with the Goal Exceed Ratio. In this context, "certain to fail" relates to any possible Trial Results within the time remaining till the Goal Duration Sum is reached.

One Search Goal can have multiple different Loads classified as its Upper Bounds. While Search progresses and more Trials are measured, any Load can become an Upper Bound in principle.

Moreover, a Load can stop being an Upper Bound, but that can only happen when more than a Goal Duration Sum of Trials are measured (e.g., because another Search Goal needs more Trials at this Load). Informally, the previous Upper Bound got invalidated. In practice, the Load frequently becomes a Lower Bound instead.

Definition:

負荷は、探索の現時点で、所与の探索目標について Appendix A アルゴリズムによって上限として分類される場合に限り、上限（Upper Bound）と呼ばれます。

Discussion:

より詳しく言うと、その負荷で（任意のトライアル期間で）これまでに実行されたすべてのトライアル結果の集合が、所与の探索目標のすべての要件、主に目標超過率と組み合わせた目標損失率を満たせないことが確実です。この文脈で「満たせないことが確実」とは、目標期間合計に到達するまでの残り時間内での可能なあらゆるトライアル結果に関してのことです。

1 つの探索目標が、その上限として分類された複数の異なる負荷を持つ場合があります。探索が進みより多くのトライアルが測定されるにつれて、原則としてどの負荷も上限になりえます。

さらに、負荷が上限でなくなることもありますが、それは目標期間合計を超えるトライアルが測定された場合（たとえば、別の探索目標がこの負荷でより多くのトライアルを必要とするため）にのみ起こりえます。非公式には、以前の上限が invalidated されたことになります。実際には、その負荷は代わりに下限になることがよくあります。

4.7.2.2. Lower Bound
4.7.2.2. 下限
Definition:

A Load is called a Lower Bound if and only if it is classified as such by a Appendix A algorithm for the given Search Goal at the current moment of the Search.

Discussion:

In more detail, the set of all Trial Results performed so far at the Load (and any Trial Duration) is certain to uphold all the requirements of the given Search Goal, mainly the Goal Loss Ratio in combination with the Goal Exceed Ratio. Here, "certain to uphold" relates to any possible Trial Results within the time remaining till the Goal Duration Sum is reached.

One Search Goal can have multiple different Loads classified as its Lower Bounds. As Search progresses and more Trials are measured, any Load value can become a Lower Bound in principle.

No Load can be both an Upper Bound and a Lower Bound for the same Search Goal at the same time, but it is possible for a larger Load to be a Lower Bound while a smaller Load is an Upper Bound at the same time.

Moreover, a Load can stop being a Lower Bound, but that can only happen when more than a Goal Duration Sum of Trials are measured (e.g., because another Search Goal needs more Trials at this Load). Informally, the previous Lower Bound got invalidated. In practice, the Load frequently becomes an Upper Bound instead.

Definition:

負荷は、探索の現時点で、所与の探索目標について Appendix A アルゴリズムによって下限として分類される場合に限り、下限（Lower Bound）と呼ばれます。

Discussion:

より詳しく言うと、その負荷で（任意のトライアル期間で）これまでに実行されたすべてのトライアル結果の集合が、所与の探索目標のすべての要件、主に目標超過率と組み合わせた目標損失率を満たすことが確実です。ここで「満たすことが確実」とは、目標期間合計に到達するまでの残り時間内での可能なあらゆるトライアル結果に関してのことです。

1 つの探索目標が、その下限として分類された複数の異なる負荷を持つ場合があります。探索が進みより多くのトライアルが測定されるにつれて、原則としてどの負荷の値も下限になりえます。

同じ探索目標について、同時に上限かつ下限である負荷はありえませんが、より大きな負荷が下限であると同時に、より小さな負荷が上限であることはありえます。

さらに、負荷が下限でなくなることもありますが、それは目標期間合計を超えるトライアルが測定された場合（たとえば、別の探索目標がこの負荷でより多くのトライアルを必要とするため）にのみ起こりえます。非公式には、以前の下限が無効化されたことになります。実際には、その負荷は代わりに上限になることがよくあります。

4.7.2.3. Undecided
4.7.2.3. 未決定
Definition:

A Load is called Undecided if it is currently neither an Upper Bound nor a Lower Bound for the give Search Goal.

Discussion:

Any Load that has not been measured so far is Undecided.

It is possible for a Load to transition from an Upper Bound to Undecided by adding Short Low-Loss Trials. That is yet another reason for users to avoid using Search Goals with different Goal Final Trial Durations.

Definition:

負荷が、所与の探索目標について現在上限でも下限でもない場合、未決定（Undecided）と呼ばれます。

Discussion:

これまでに測定されていない負荷はすべて未決定です。

短い低損失トライアルを追加することで、負荷が上限から未決定に移行することがありえます。これは、ユーザーが異なる目標最終トライアル期間を持つ探索目標の使用を避けるべきさらなる理由です。

4.8. Result Terms

4.8. 結果の用語

Before defining the full structure of a Controller Output, it is useful to define the composite quantity, called Goal Result. The following subsections define its attribute first, before describing the Goal Result quantity.

コントローラー出力の完全な構造を定義する前に、Goal Result と呼ばれる複合量を定義しておくと便利です。以下のサブセクションでは、目標結果の量を説明する前に、まずその属性を定義します。

There is a correspondence between Search Goals and Goal Results. Most of the following subsections refer to a given Search Goal when defining their terms. Conversely, at the end of the Search, each Search Goal instance has its corresponding Goal Result instance.

探索目標と目標結果の間には対応関係があります。以下のサブセクションのほとんどは、用語を定義する際に所与の探索目標を参照します。逆に、探索の終了時には、各探索目標のインスタンスに対応する目標結果のインスタンスがあります。

4.8.1. Relevant Upper Bound

4.8.1. 関連する上限

Definition:

The Relevant Upper Bound is the smallest Load classified as an Upper Bound for a given Search Goal at the end of the Search.

Discussion:

If no measured Load had enough High-Loss Trials, the Relevant Upper Bound MAY be non-existent, for example, when Max Load is classified as a Lower Bound.

Conversely, when the Relevant Upper Bound does exist, it is not affected by the Max Load value.

Given that the Relevant Upper Bound is a quantity based on Load, Test Report MAY express this quantity using multi-interface values, as the sum of Intended Loads over input interfaces.

Definition:

関連する上限（Relevant Upper Bound）は、探索の終了時に所与の探索目標の上限として分類された最小の負荷です。

Discussion:

測定されたどの負荷も十分な高損失トライアルを持たなかった場合、関連する上限は存在しなくてもよいです（MAY）。たとえば、最大負荷が下限として分類された場合です。

逆に、関連する上限が存在する場合、それは最大負荷の値の影響を受けません。

関連する上限が負荷に基づく量であることを考えると、テストレポートは、入力インターフェイスにわたる意図した負荷の合計として、複数インターフェイスの値を使用してこの量を表してもよいです（MAY）。

4.8.2. Relevant Lower Bound

4.8.2. 関連する下限

Definition:

The Relevant Lower Bound is the largest Load among those smaller than the Relevant Upper Bound that got classified as a Lower Bound for a given Search Goal at the end of the Search.

Discussion:

If no Load had enough Low-Loss Full-Length Trials, the Relevant Lower Bound MAY be non-existent.

Strictly speaking, if the Relevant Upper Bound does not exist, the Relevant Lower Bound also does not exist. In a typical case, Max Load is classified as a Lower Bound, making it impossible to increase the Load to continue the Search for an actual Upper Bound. Thus, it is not clear whether a larger value would be found for a Relevant Lower Bound if larger Loads were available for selection.

Given that the Relevant Lower Bound is a quantity based on Load, Test Report MAY express this quantity using multi-interface values, as the sum of Intended Loads over input interfaces.

Definition:

関連する下限（Relevant Lower Bound）は、探索の終了時に所与の探索目標の下限として分類された、関連する上限より小さい負荷のうち最大の負荷です。

Discussion:

どの負荷も十分な低損失の完全長のトライアルを持たなかった場合、関連する下限は存在しなくてもよいです（MAY）。

厳密に言えば、関連する上限が存在しない場合、関連する下限も存在しません。典型的な場合、最大負荷が下限として分類され、実際の上限の探索を続けるために負荷を増やすことができなくなります。そのため、より大きな負荷が選択可能であった場合に、関連する下限としてより大きな値が見つかるかどうかは明らかではありません。

関連する下限が負荷に基づく量であることを考えると、テストレポートは、入力インターフェイスにわたる意図した負荷の合計として、複数インターフェイスの値を使用してこの量を表してもよいです（MAY）。

4.8.3. Conditional Throughput

4.8.3. 条件付きスループット

Definition:

Conditional Throughput is a value computed at the Relevant Lower Bound according to the algorithm defined in Appendix B.

Discussion:

The Relevant Lower Bound is defined only at the end of the Search, and so is the Conditional Throughput. But the algorithm can be applied at any time on any current Lower Bound, so the final Conditional Throughput value may appear sooner than at the end of a Search.

Informally, the Conditional Throughput should be a typical Trial Forwarding Rate, expected to be seen at the Relevant Lower Bound of a given Search Goal.

But frequently, it is only a conservative estimate thereof, as MLRsearch implementations tend to stop measuring more Trials as soon as they confirm the value cannot get worse than this estimate within the Goal Duration Sum.

This quantity is RECOMMENDED to be used when evaluating repeatability and comparability of different MLRsearch implementations. Refer to Section 5.6 for more details.

Given that Conditional Throughput is a quantity based on Load, Test Report MAY express this quantity using multi-interface values, as the sum of per-interface Forwarding Rates.

Definition:

条件付きスループット（Conditional Throughput）は、Appendix B で定義されているアルゴリズムに従って関連する下限で計算される値です。

Discussion:

関連する下限は探索の終了時にのみ定義され、条件付きスループットも同様です。しかし、アルゴリズムはいつでも任意の現在の下限に適用できるため、最終的な条件付きスループットの値は探索の終了より前に現れる場合があります。

非公式には、条件付きスループットは、所与の探索目標の関連する下限で見られることが期待される、典型的なトライアル転送レートであるべきです。

しかし多くの場合、それはその保守的な推定値にすぎません。MLRsearch の実装は、目標期間合計の範囲内で値がこの推定値より悪くならないことを確認するとすぐに、さらなるトライアルの測定を止める傾向があるからです。

この量は、異なる MLRsearch の実装の再現性と比較可能性を評価する際に使用することが推奨されます（RECOMMENDED）。詳細は Section 5.6 を参照してください。

条件付きスループットが負荷に基づく量であることを考えると、テストレポートは、インターフェイスごとの転送レートの合計として、複数インターフェイスの値を使用してこの量を表してもよいです（MAY）。

4.8.4. Goal Results

4.8.4. 目標結果

The MLRsearch Specification is based on a set of requirements for a regular result. But in practice, it is not always possible for such a result instance to exist, so irregular results also need to be supported.

MLRsearch 仕様は、regular 結果についての要件の集合に基づいています。しかし実際には、そのような結果のインスタンスが常に存在できるとは限らないため、irregular 結果もサポートする必要があります。

4.8.4.1. Regular Goal Result
4.8.4.1. 通常の目標結果
Definition:

Regular Goal Result is a composite quantity consisting of several attributes. Relevant Upper Bound and Relevant Lower Bound are REQUIRED attributes. Conditional Throughput is a RECOMMENDED attribute.

Discussion:

Implementations MAY add their own attributes.

Test Report MUST display the Relevant Lower Bound. Displaying the Relevant Upper Bound is RECOMMENDED, especially if the implementation does not use Goal Width.

In general, stopping conditions for the corresponding Search Goal MUST be satisfied to produce a Regular Goal Result. Specifically, if an implementation offers Goal Width as a Search Goal attribute, the distance between the Relevant Lower Bound and the Relevant Upper Bound MUST NOT be larger than the Goal Width.

For stopping conditions, refer to Section 4.6.5 and Section 5.2.

Definition:

通常の目標結果（Regular Goal Result）は、いくつかの属性で構成される複合量です。関連する上限と関連する下限の属性が要求されています（REQUIRED）。条件付きスループットを属性として含めることが推奨されます（RECOMMENDED）。

Discussion:

実装は独自の属性を追加してもよいです（MAY）。

テストレポートは関連する下限を表示しなければなりません（MUST）。特に実装が目標幅を使用しない場合は、関連する上限を表示することが推奨されます（RECOMMENDED）。

一般に、通常の目標結果を生成するには、対応する探索目標の停止条件が満たされなければなりません（MUST）。具体的には、実装が探索目標の属性として目標幅を提供する場合、関連する下限と関連する上限の間の距離が目標幅より大きくなってはなりません（MUST NOT）。

停止条件については Section 4.6.5 と Section 5.2 を参照してください。

4.8.4.2. Irregular Goal Result
4.8.4.2. 不規則な目標結果
Definition:

Irregular Goal Result is a composite quantity. All attributes are OPTIONAL.

Discussion:

It is RECOMMENDED to report any useful quantity even if it does not satisfy all the requirements. For example, if Max Load is classified as a Lower Bound, it is fine to report it as an "effective" Relevant Lower Bound (although not a real one, as that requires a Relevant Upper Bound, which does not exist in this case) and compute Conditional Throughput for it. In this case, only the missing Relevant Upper Bound signals this instance is irregular.

Similarly, if both Relevant Bounds exist, it is RECOMMENDED to include them as Irregular Goal Result attributes and let the Manager decide if they are too far apart for Test Report purposes.

If Test Report displays some Irregular Goal Result attribute values, they MUST be clearly marked as coming from irregular results.

The implementation MAY define additional attributes, for example, explicit flags for expected situations, so the Manager logic can be simpler.

Definition:

不規則な目標結果（Irregular Goal Result）は複合量です。すべての属性は選択可能な（OPTIONAL）ものです。

Discussion:

すべての要件を満たさない場合でも、有用な量は報告することが推奨されます（RECOMMENDED）。たとえば、最大負荷が下限として分類された場合、それを「実効的な」関連する下限として報告し（ただし、それには関連する上限が必要であり、この場合は存在しないため、本当の関連する下限ではありません）、それについて条件付きスループットを計算しても問題ありません。この場合、欠けている関連する上限だけが、このインスタンスが不規則であることを示します。

同様に、両方の関連する境界が存在する場合、それらを不規則な目標結果の属性として含め、テストレポートの目的で離れすぎているかどうかをマネージャーに決めさせることが推奨されます（RECOMMENDED）。

テストレポートが不規則な目標結果の属性の値を表示する場合、それらが不規則な結果からのものであることを明確に示さなければなりません（MUST）。

実装は、マネージャーのロジックを単純にできるように、追加の属性、たとえば予想される状況の明示的なフラグを定義してもよいです（MAY）。

4.8.4.3. Goal Result
4.8.4.3. 目標結果
Definition:

Goal Result is a composite quantity. Each instance is either a Regular Goal Result or an Irregular Goal Result.

Discussion:

The Manager MUST be able of distinguishing whether the instance is regular or not, without accessing data outside the instance.

Definition:

目標結果（Goal Result）は複合量です。各インスタンスは、通常の目標結果か不規則な目標結果のいずれかです。

Discussion:

マネージャーは、インスタンスの外部のデータにアクセスすることなく、インスタンスが通常かどうかを区別できなければなりません（MUST）。

4.8.5. Search Result

4.8.5. 探索結果

Definition:

The Search Result is a single composite object that maps each Search Goal instance to a corresponding Goal Result instance.

Discussion:

As an alternative to mapping, the Search Result MAY be represented as an ordered list of Goal Results that in that case MUST appear in the exact same order as the list of their corresponding Search Goals as specified in the Controller Input instance.

When the Search Result is expressed as a mapping, it MUST contain an entry for every Search Goal supplied in the Controller Input.

Identical Goal Result instances MAY be listed for different Search Goals, but their status as regular or irregular MAY be different, for example, if two Search Goals differ only in the Goal Width, and the Relevant Lower Bound is close enough to the Relevant Upper Bound according to only one of them.

Definition:

探索結果（Search Result）は、各探索目標のインスタンスを対応する目標結果のインスタンスに対応付ける単一の複合オブジェクトです。

Discussion:

対応付けの代わりに、探索結果を目標結果の順序付きリストとして表してもよいです（MAY）。その場合、それらはコントローラー入力のインスタンスで規定された、対応する探索目標のリストとまったく同じ順序で現れなければなりません（MUST）。

探索結果を対応付けとして表す場合、コントローラー入力で提供されたすべての探索目標のエントリーを含まなければなりません（MUST）。

異なる探索目標について同一の目標結果のインスタンスを挙げてもよいです（MAY）。ただし、通常か不規則かのステータスは異なってもよいです（MAY）。たとえば、2 つの探索目標が目標幅だけ異なり、そのうちの一方だけによれば関連する下限が関連する上限に十分近い場合です。

4.8.6. Controller Output

4.8.6. コントローラー出力

Definition:

The Controller Output is a composite quantity returned from the Controller to the Manager at the end of the Search. The Search Result instance is its only REQUIRED attribute.

Discussion:

The MLRsearch implementation MAY return additional data in the Controller Output, for example, the number of Trials performed and the total Search Duration.

Definition:

コントローラー出力（Controller Output）は、探索の終了時にコントローラーからマネージャーに返される複合量です。その属性のうち、探索結果のインスタンスだけが要求されています（REQUIRED）。

Discussion:

MLRsearch の実装は、コントローラー出力で追加のデータ、たとえば実行されたトライアルの数や全体の探索時間を返してもよいです（MAY）。

4.9. Architecture Terms

4.9. アーキテクチャーの用語

The MLRsearch architecture consists of three main system components: the Manager, the Controller, and the Measurer. The components were introduced in Section 4.2, and the following sections finalize their definitions using terms from previous sections.

MLRsearch architecture は、マネージャー、コントローラー、測定器という 3 つの主要なシステムの構成要素で構成されます。構成要素は Section 4.2 で導入されており、以下のセクションでは、前のセクションの用語を使用してその定義を確定します。

Note that the architecture also implies the presence of other components, such as the SUT and the tester (as a sub-component of the Measurer).

アーキテクチャーは、SUT やテスター（測定器のサブコンポーネントとして）のようなほかの構成要素の存在も暗示していることに注意してください。

Communication protocols and interfaces between components are left unspecified. For example, when the MLRsearch Specification uses the verb "to call" when describing how the Controller interacts with the Measurer, it is possible that the Controller notifies the Manager to call the Measurer indirectly instead. In doing so, the Measurer implementations can be fully independent from the Controller implementations, for example, developed in different programming languages.

構成要素間の通信プロトコルとインターフェイスは規定されていません。たとえば、MLRsearch 仕様がコントローラーと測定器のやりとりを説明する際に「呼び出す」という動詞を使用している場合、代わりにコントローラーがマネージャーに通知して間接的に測定器を呼び出させることも可能です。そうすることで、測定器の実装はコントローラーの実装から完全に独立でき、たとえば異なるプログラミング言語で開発できます。

4.9.1. Measurer

4.9.1. 測定器

Definition:

The Measurer is a functional element that, when called with a Trial Input instance, performs one Trial and returns a Trial Output instance.

Discussion:

This definition assumes the Measurer is already initialized. In practice, there may be additional steps before the Search, e.g., when the Manager configures the Traffic Profile (either on the Measurer or on its tester sub-component directly) and performs a warm-up (if the tester or the test procedure requires one).

It is the responsibility of the Measurer implementation to uphold any requirements and assumptions present in the MLRsearch Specification, e.g., the Trial Forwarding Ratio not being larger than one.

Implementers have some freedom. For example, Section 10 of [RFC2544] gives some suggestions (but not requirements) related to duplicated or reordered frames. Implementations are RECOMMENDED to document their behavior related to such freedoms in as detailed a way as possible.

It is RECOMMENDED to benchmark the test equipment first, e.g., connect the sender and receiver directly (without any SUT in the path), find a Load that guarantees the Offered Load is not too far from the Intended Load, and use that value as the Max Load. When measuring the real SUT, it is RECOMMENDED to turn any severe deviation between the Intended Load and the Offered Load into the increased Trial Loss Ratio.

Neither of these two recommendations are made into mandatory requirements, because it is not easy to provide guidance about when the difference is severe enough in a way that would be disentangled from other Measurer freedoms.

Definition:

測定器（Measurer）は、トライアル入力のインスタンスとともに呼び出されると、1 つのトライアルを実行してトライアル出力のインスタンスを返す機能要素です。

Discussion:

この定義は、測定器がすでに初期化されていることを前提としています。実際には、探索の前に追加の手順がある場合があります。たとえば、マネージャーが（測定器上か、そのテスターのサブコンポーネント上で直接）トラフィックプロファイルを構成し、（テスターやテスト手順が必要とする場合は）ウォームアップを行う場合です。

MLRsearch 仕様に存在する要件と仮定、たとえばトライアル転送率が 1 を超えないことを守るのは、測定器の実装の責任です。

実装者にはある程度の自由があります。たとえば、[RFC2544]のSection 10 は、重複したフレームや順序が入れ替わったフレームに関するいくつかの提案（ただし要件ではない）を示しています。実装は、そのような自由に関連する振る舞いをできるだけ詳しく文書化することが推奨されます（RECOMMENDED）。

まずテスト機器をベンチマークすることが推奨されます（RECOMMENDED）。たとえば、送信者と受信者を直接（パスに SUT を挟まずに）接続し、提供負荷が意図した負荷からかけ離れないことを保証する負荷を見つけ、その値を最大負荷として使用します。実際の SUT を測定する場合、意図した負荷と提供負荷の間の深刻な乖離は、トライアル損失率の増加に変換することが推奨されます（RECOMMENDED）。

これら 2 つの推奨事項はどちらも必須の要件にはしていません。ほかの測定器の自由から切り離した形で、差がいつ十分に深刻であるかについてのガイダンスを提供するのは容易ではないからです。

For a sample situation where the Offered Load cannot keep up with the Intended Load, and the consequences on the Search Result, refer to Section 5.6.1.

提供負荷が意図した負荷に追いつけない状況の例と、それが探索結果に及ぼす影響については Section 5.6.1 を参照してください。

4.9.2. Controller

4.9.2. コントローラー

Definition:

The Controller is a functional element that, upon receiving a Controller Input instance, repeatedly generates Trial Input instances for the Measurer and collects the corresponding Trial Output instances. This cycle continues until the stopping conditions are met, at which point, the Controller produces a final Controller Output instance and terminates.

Discussion:

Informally, the Controller has considerable freedom in selection of Trial Inputs, and the implementations want to achieve all the Search Goals in the shortest average Search Duration.

The Controller's role in optimizing the overall Search Duration distinguishes MLRsearch algorithms from simpler search procedures.

Informally, each implementation can have different stopping conditions. Goal Width is only one example. In practice, implementation details do not affect comparability that much, as long as the Goal Result instances compared are regular.

Definition:

コントローラー（Controller）は、コントローラー入力のインスタンスを受け取ると、測定器のためにトライアル入力のインスタンスを繰り返し生成し、対応するトライアル出力のインスタンスを収集する機能要素です。このサイクルは停止条件が満たされるまで続き、その時点でコントローラーは最終的なコントローラー出力のインスタンスを生成して終了します。

Discussion:

非公式には、コントローラーはトライアル入力の選択にかなりの自由を持ち、実装は最短の平均探索時間ですべての探索目標を達成したいと考えます。

全体の探索時間を最適化するコントローラーの役割が、MLRsearch のアルゴリズムをより単純な探索手順から区別しています。

非公式には、各実装は異なる停止条件を持つことができます。目標幅は 1 つの例にすぎません。実際には、比較される目標結果のインスタンスが通常のものである限り、実装の詳細は比較可能性にそれほど影響しません。

4.9.3. Manager

4.9.3. マネージャー

Definition:

The Manager is a functional element that is responsible for provisioning other components, calling a Controller component once, and for creating the Test Report following the reporting format as defined in Section 26 of [RFC2544].

Discussion:

The Manager MUST initialize the SUT (including constituent DUTs) and the Measurer (and the tester if independent from Measurer) with their intended configurations before calling the Controller.

Note that Section 7 of [RFC2544] already puts requirements on DUT setups:

It is expected that all of the tests will be run without changing the configuration or setup of the DUT in any way other than that required to do the specific test. For example, it is not acceptable to change the size of frame handling buffers between tests of frame handling rates or to disable all but one transport protocol when testing the throughput of that protocol.

It is REQUIRED for the Test Report to encompass all the SUT configuration details, including the description of a default DUT configuration common for most tests and configuration changes if required by a specific test.

For example, Section 5.1.1 of [RFC5180] recommends testing jumbo frames if SUT can forward them, even though they are outside the scope of the 802.3 IEEE standard [IEEE.802.3df]. In this case, it is acceptable for the SUT default configuration to not support jumbo frames and only enable this support when testing jumbo Traffic Profiles, as the handling of jumbo frames typically has different packet buffer requirements and potentially higher processing overhead. Non-jumbo frame sizes should also be tested on the jumbo-enabled setup.

The Manager does not need to be able to tweak any Search Goal attributes, but it MUST report all applied attributes even if not tweaked.

A human or automated user invokes the Manager once to launch a single Search and receive its Test Report. Every new invocation is treated as a fresh, independent Search; how the system behaves across multiple calls (for example, combining or comparing their Search Results) is explicitly out of scope for this document.

Definition:

マネージャー（Manager）は、ほかの構成要素を準備し、コントローラーの構成要素を 1 回呼び出し、[RFC2544]のSection 26 で定義されている報告の形式に従ってテストレポートを作成する責任を負う機能要素です。

Discussion:

マネージャーは、コントローラーを呼び出す前に、SUT（構成要素の DUT を含む）と測定器（および測定器から独立している場合はテスター）を、その意図した構成で初期化しなければなりません（MUST）。

[RFC2544]のSection 7 は、すでに DUT のセットアップについて要件を課していることに注意してください。

すべてのテストは、特定のテストを行うために必要なもの以外のいかなる方法でも DUT の構成やセットアップを変更することなく実行されることが期待されます。たとえば、フレーム処理レートのテストの間でフレーム処理のバッファーのサイズを変更したり、あるプロトコルのスループットをテストする際に 1 つを除くすべてのトランスポートプロトコルを無効にしたりすることは許容されません。

テストレポートが、ほとんどのテストに共通する default の DUT の構成の説明と、特定のテストで必要な場合の構成の変更を含め、SUT の構成の詳細をすべて含むことが要求されています（REQUIRED）。

たとえば、[RFC5180]のSection 5.1.1 は、ジャンボフレームが 802.3 IEEE 規格 [IEEE.802.3df] の範囲外であっても、SUT がそれを転送できる場合にはジャンボフレームをテストすることを推奨しています。この場合、ジャンボフレームの扱いには通常異なるパケットバッファーの要件があり、処理のオーバーヘッドが高くなる可能性があるため、SUT のデフォルトの構成でジャンボフレームをサポートせず、ジャンボのトラフィックプロファイルをテストする場合にのみこのサポートを有効にすることは許容されます。ジャンボを有効にしたセットアップでも、ジャンボ以外のフレームサイズをテストすべきです。

マネージャーが探索目標の属性を調整できる必要はありませんが、調整していない場合でも、適用したすべての属性を報告しなければなりません（MUST）。

人間または自動化された user は、単一の探索を開始してそのテストレポートを受け取るために、マネージャーを 1 回呼び出します。新しい呼び出しはそれぞれ新しい独立した探索として扱われます。複数の呼び出しにわたってシステムがどのように振る舞うか（たとえば、探索結果を組み合わせたり比較したりすること）は、この文書の範囲から明示的に除外されています。

4.10. Compliance

4.10. 準拠

This section discusses compliance relations between MLRsearch and other test procedures.

このセクションでは、MLRsearch とほかのテスト手順の間の準拠の関係について議論します。

4.10.1. Test Procedure Compliant with MLRsearch

4.10.1. MLRsearch に準拠したテスト手順

Any networking measurement setup that could be understood as consisting of functional elements satisfying all requirements for the Measurer, the Controller, and the Manager is compliant with the MLRsearch Specification.

測定器、コントローラー、マネージャーのすべての要件を満たす機能要素で構成されていると理解できるネットワーキングの測定のセットアップは、MLRsearch 仕様に準拠しています。

These components can be seen as abstractions present in any testing procedure. For example, there may be a single component acting as both the Manager and the Controller, but if values of all required attributes of Search Goals and Goal Results are visible in the Test Report, the Controller Input and Controller Output instances are implied.

これらの構成要素は、あらゆるテスト手順に存在する抽象化とみなすことができます。たとえば、マネージャーとコントローラーの両方として機能する単一の構成要素がある場合もありますが、探索目標と目標結果のすべての必須の属性の値がテストレポートで見える場合、コントローラー入力とコントローラー出力のインスタンスは暗示されています。

For example, any setup for conditionally (or unconditionally) compliant [RFC2544] Throughput testing can be understood as an MLRsearch architecture if there is enough data to reconstruct the Relevant Upper Bound.

たとえば、条件付きで（または無条件に）[RFC2544] に準拠したスループットのテストのためのセットアップは、関連する上限を再構成するのに十分なデータがあれば、MLRsearch のアーキテクチャーとして理解できます。

Refer to Section 4.10.2 for an equivalent Search Goal.

同等の探索目標については Section 4.10.2 を参照してください。

Any test procedure that can be understood as one call to the Manager of the MLRsearch architecture is said to be compliant with the MLRsearch Specification.

MLRsearch のアーキテクチャーのマネージャーへの 1 回の呼び出しとして理解できるテスト手順は、MLRsearch 仕様に準拠しているといいます。

4.10.2. MLRsearch Compliant with RFC 2544

4.10.2. RFC 2544 に準拠した MLRsearch

Compliance with RFC 2544 is governed by [RFC2544]; rules of MLRsearch Specification cannot change that, but they can give recommendations to improve comparability.

RFC 2544 への準拠は [RFC2544] によって管理されています。MLRsearch 仕様の規則はそれを変えることはできませんが、比較可能性を向上させるための推奨事項を示すことはできます。

The following Search Goal instance is RECOMMENDED to make the corresponding Search Result unconditionally compliant with Section 24 of [RFC2544].

対応する探索結果を [RFC2544]のSection 24 に無条件に準拠させるには、次の探索目標のインスタンスが推奨されます（RECOMMENDED）。

  • Goal Final Trial Duration = 60 seconds

  • Goal Duration Sum = 60 seconds

  • Goal Loss Ratio = 0%

  • Goal Exceed Ratio = 0%

  • 目標最終トライアル期間 = 60 秒

  • 目標期間合計 = 60 秒

  • 目標損失率 = 0%

  • 目標超過率 = 0%

The presence of other Search Goals does not affect the compliance of this Goal Result. In this case, the Relevant Lower Bound and the Conditional Throughput are equal to each other, and the value is the Throughput.

ほかの探索目標の存在は、この目標結果の準拠に影響しません。この場合、関連する下限と条件付きスループットは互いに等しく、その値がスループットです。

Goal Duration Sum smaller than Goal Final Trial Duration should have no effect on the results. A non-zero Goal Exceed Ratio would needlessly prolong the Search when Short Trials of both loss types are present.

目標最終トライアル期間より小さい目標期間合計は、結果に影響を与えないはずです。ゼロでない目標超過率は、両方の損失の種類の短いトライアルが存在する場合に、探索を不必要に長くします。

The Goal Loss Ratio and Goal Exceed Ratio are enough to make the Search Goal conditionally compliant. Adding Goal Final Trial Duration makes the Search Goal unconditionally compliant.

目標損失率と目標超過率で、探索目標を条件付きで準拠させるのに十分です。目標最終トライアル期間を加えると、探索目標は無条件に準拠します。

Small enough Goal Duration Sum prevents MLRsearch from repeating zero-loss Full-Length Trials. Allowing those would make it less clear whether the result is compliant with Section 24 of [RFC2544] or whether it is a new, stricter methodology.

十分に小さい目標期間合計により、MLRsearch が損失ゼロの完全長のトライアルを繰り返すことが防がれます。それを許可すると、結果が [RFC2544]のSection 24 に準拠しているのか、新しいより厳格な方法論なのかが不明確になります。

4.10.3. MLRsearch Compliant with TST009

4.10.3. TST009 に準拠した MLRsearch

One of the alternatives to [RFC2544] is Binary Search With Loss Verification, as described in Section 12.3.3 of [TST009].

[RFC2544] の代替の 1 つは、[TST009] のセクション 12.3.3 で説明されている、損失の検証を伴う二分探索です。

The rationale of such a Search is to repeat High-Loss Trials, hoping for zero loss on the second try, so the Goal Results are closer to the noiseless end of the performance spectrum, thus more repeatable and comparable.

そのような探索の根拠は、2 回目の試行で損失ゼロになることを期待して高損失トライアルを繰り返すことで、目標結果が性能スペクトルのノイズのない端に近くなり、それによってより再現可能で比較可能になるというものです。

Only the variant with "z = infinity" is achievable with MLRsearch.

MLRsearch で達成できるのは "z = infinity" の変種だけです。

For example, for the "max(r) = 2" variant, the following Search Goal instance is RECOMMENDED (for comparability reasons) to get a compatible Search Result:

たとえば、"max(r) = 2" の変種について、互換性のある探索結果を得るには、（比較可能性の理由から）次の探索目標のインスタンスが推奨されます（RECOMMENDED）。

  • Goal Final Trial Duration = 60 seconds

  • Goal Duration Sum = 120 seconds

  • Goal Loss Ratio = 0%

  • Goal Exceed Ratio = 50%

  • 目標最終トライアル期間 = 60 秒

  • 目標期間合計 = 120 秒

  • 目標損失率 = 0%

  • 目標超過率 = 50%

If the first 60-second Trial has zero loss, it is enough for MLRsearch to stop measuring at that Load, as even a second High-Loss Trial would still fit within the Goal Exceed Ratio of 50%.

最初の 60 秒のトライアルで損失がゼロであれば、2 回目に高損失トライアルがあっても 50% の目標超過率に収まるため、MLRsearch はその負荷での測定を止めるのに十分です。

But if the first Trial is High-Loss, MLRsearch also needs to perform the second Trial to classify that Load. The Goal Duration Sum is twice as long as the Goal Final Trial Duration, so a third Full-Length Trial is never needed.

しかし、最初のトライアルが高損失であれば、MLRsearch はその負荷を分類するために 2 回目のトライアルも実行する必要があります。目標期間合計は目標最終トライアル期間の 2 倍の長さなので、3 回目の完全長のトライアルが必要になることはありません。

5. Methodology Rationale and Design Considerations

5. 方法論の根拠と設計上の考慮事項

This section explains the "why" behind MLRsearch. Building on the normative specification in MLRsearch Specification, it contrasts MLRsearch with the classic single-ratio Binary Search in [RFC2544] and walks through the key design choices: search mechanics, stopping-rule precision, Loss Inversion for multiple goals, Goal Exceed Ratio handling, Short Trial strategies, and the generalized throughput concept. Together, these considerations show how the methodology reduces test time, supports multiple Goal Loss Ratios, and improves repeatability.

このセクションでは、MLRsearch の背後にある「なぜ」を説明します。MLRsearch 仕様の規範的な仕様に基づいて、MLRsearch を [RFC2544] の古典的な単一比率の二分探索と対比し、主要な設計上の選択、つまり探索の仕組み、停止規則の精度、複数の目標のための損失の逆転、目標超過率の扱い、短いトライアルの戦略、一般化されたスループットの概念を順に説明します。これらの考慮事項は全体として、この方法論がどのようにテスト時間を短縮し、複数の目標損失率をサポートし、再現性を向上させるかを示しています。

5.1. Binary Search Commonalities

5.1. 二分探索との共通点

A typical search implementation for [RFC2544], such as Binary Search, tracks only the two tightest bounds (in variables lower-bound and upper-bound). To start, the search needs both Max Load and Min Load values. Then, one Trial is used to confirm Max Load is an Upper Bound, and one Trial is used to confirm Min Load is a Lower Bound.

二分探索のような [RFC2544] の典型的な探索の実装は、最も厳しい 2 つの境界（変数 lower-bound と upper-bound）だけを追跡します。開始するには、探索には最大負荷と最小負荷の両方の値が必要です。その後、1 回のトライアルで最大負荷が上限であることを確認し、1 回のトライアルで最小負荷が下限であることを確認します。

Then, Trial Load is chosen as the mean of the current tightest upper bound and the current tightest lower bound and becomes a new tightest bound depending on the Trial Loss Ratio.

その後、トライアル負荷は現在の最も厳しい上限と現在の最も厳しい下限の平均として選ばれ、トライアル損失率に応じて新しい最も厳しい境界になります。

After some number of Trials, the tightest lower bound becomes the Throughput, but [RFC2544] does not specify when, if ever, the search should stop. In practice, the search stops either at some distance between the tightest upper bound and the tightest lower bound or after some number of Trials.

ある数のトライアルの後、最も厳しい下限がスループットになりますが、[RFC2544] は探索をいつ停止すべきか（そもそも停止すべきか）を規定していません。実際には、探索は、最も厳しい上限と最も厳しい下限の間がある距離になったとき、またはある数のトライアルの後に停止します。

For a given pair of Max Load and Min Load values, there is a one-to-one correspondence between the number of Trials and the final distance between the tightest bounds. Thus, the search always takes the same time, assuming initial bounds are confirmed.

最大負荷と最小負荷の値の特定の組について、トライアルの数と最も厳しい境界の間の最終的な距離の間には 1 対 1 の対応があります。そのため、初期の境界が確認されていると仮定すると、探索は常に同じ時間がかかります。

5.2. Stopping Conditions and Precision

5.2. 停止条件と精度

The MLRsearch Specification requires listing both Relevant Upper Bound and Relevant Lower Bound for each Search Goal, and the difference between the bounds implies whether the precision needed for Regular Goal Result is achieved. Therefore, it is not necessary to report the specific stopping condition used.

MLRsearch 仕様は、各探索目標について関連する上限と関連する下限の両方を挙げることを要求しており、境界の間の差によって、通常の目標結果に必要な精度が達成されているかどうかがわかります。そのため、使用した具体的な停止条件を報告する必要はありません。

MLRsearch implementations may use Goal Width to allow direct control of Regular Goal Result precision and indirect control of the Search Duration.

MLRsearch の実装は、通常の目標結果の精度を直接制御し、探索時間を間接的に制御するために、目標幅を使用できます。

Other MLRsearch implementations may use different stopping conditions, for example, based on the Search Duration, trading off precision control for Search Duration control.

ほかの MLRsearch の実装は、精度の制御を探索時間の制御と引き換えにして、たとえば探索時間に基づく、異なる停止条件を使用できます。

Due to various possible time optimizations, there is no strict correspondence between the Search Duration and Goal Width values. In practice, noisy SUT performance increases both average Search Duration and its variance.

さまざまな時間の最適化が可能であるため、探索時間と目標幅の値の間に厳密な対応はありません。実際には、ノイズの多い SUT の性能は、平均の探索時間とその分散の両方を増加させます。

5.3. Loss Ratios and Loss Inversion

5.3. 損失率と損失の逆転

The biggest difference between MLRsearch and Binary Search is in the goals of the search. [RFC2544] has a single goal, based on classifying a single Full-Length Trial as either zero loss or non-zero loss. MLRsearch supports searching for multiple Search Goals at once, usually differing in their Goal Loss Ratios.

MLRsearch と二分探索の最大の違いは、探索の目標にあります。[RFC2544] は、単一の完全長のトライアルを損失ゼロか損失ありかに分類することに基づく単一の目標を持っています。MLRsearch は、通常は目標損失率が異なる複数の探索目標を一度に探索することをサポートしています。

5.3.1. Single Goal and Hard Bounds

5.3.1. 単一の目標と固い境界

Each bound in Binary Search is "hard", in the sense that all further Trial Loads are smaller than any current upper bound and larger than any current lower bound.

二分探索の各境界は、以降のすべてのトライアル負荷が現在のどの上限よりも小さく、現在のどの下限よりも大きいという意味で「固い」ものです。

This is also possible for MLRsearch implementations when the Search is started with only one Search Goal.

これは、探索が 1 つの探索目標だけで開始された場合には、MLRsearch の実装でも可能です。

5.3.2. Loss Inversion

5.3.2. 損失の逆転

The MLRsearch Specification supports multiple Search Goals, making the Search procedure more complicated compared to Binary Search with a single goal, but most of the complications do not affect the final Search Results much, except for one phenomenon: Loss Inversion.

MLRsearch 仕様は複数の探索目標をサポートしているため、単一の目標を持つ二分探索と比べて探索手順がより複雑になりますが、複雑さのほとんどは最終的な探索結果にあまり影響しません。ただし、1 つの現象、つまり損失の逆転を除きます。

Depending on Search Goal attributes, Load Classification results may be resistant to small amounts of Inconsistent Trial Results. However, for larger amounts, a Load that is classified as an Upper Bound for one Search Goal may still be a Lower Bound for another Search Goal. Due to this other Search Goal, MLRsearch will probably perform subsequent Trials at Loads even larger than the original value.

探索目標の属性によっては、負荷の分類の結果は、少量の一貫性のないトライアル結果に対して耐性を持つ場合があります。しかし、より多い量の場合、ある探索目標の上限として分類された負荷が、別の探索目標では依然として下限である場合があります。この別の探索目標のために、MLRsearch はおそらく元の値よりもさらに大きな負荷で後続のトライアルを実行します。

This introduces questions any multi-goal search algorithm has to address, such as: What to do when all such Trials at larger Loads happen to have zero loss? Does it mean the earlier Upper Bound was not real? Does it mean the later Low-Loss Trials do not count toward a Lower Bound?

これにより、複数目標の探索アルゴリズムが対処しなければならない疑問が生じます。たとえば、より大きな負荷でのそのようなトライアルがすべてたまたま損失ゼロだった場合はどうするか。それは前の上限が本物ではなかったことを意味するのか。それは後の低損失トライアルが下限に数えられないことを意味するのか、といったことです。

The situation where a smaller Load is classified as an Upper Bound, while a larger Load is classified as a Lower Bound (for the same Search Goal), is called Loss Inversion.

（同じ探索目標について）より小さな負荷が上限として分類され、より大きな負荷が下限として分類される状況を、損失の逆転（Loss Inversion）と呼びます。

Conversely, only single-goal search algorithms can have hard bounds that shield them from Loss Inversion.

逆に、損失の逆転から守られる固い境界を持てるのは、単一目標の探索アルゴリズムだけです。

5.3.3. Conservativeness and Relevant Bounds

5.3.3. 保守性と関連する境界

MLRsearch is conservative when dealing with Loss Inversion: The Upper Bound is considered real, and the Lower Bound is considered to be a fluke, at least when computing the Goal Result.

MLRsearch は損失の逆転を扱う際に保守的です。少なくとも目標結果を計算する際には、上限は本物とみなされ、下限はまぐれとみなされます。

This is formalized using the definitions of Section 4.8.1 and Section 4.8.2.

これは、Section 4.8.1 と Section 4.8.2 の定義を使用して形式化されています。

The Relevant Upper Bound (for a specific Search Goal) is the smallest Load classified as an Upper Bound. But the Relevant Lower Bound is not simply the largest among Lower Bounds. It is the largest Load among Loads that are Lower Bounds while also being smaller than the Relevant Upper Bound.

（特定の探索目標についての）関連する上限は、上限として分類された最小の負荷です。しかし、関連する下限は単に下限の中で最大のものではありません。それは、下限であり、かつ関連する上限より小さい負荷の中で最大の負荷です。

With these definitions, the Relevant Lower Bound is always smaller than the Relevant Upper Bound (if both exist), and the two Relevant Bounds are used analogously as the two tightest bounds in the Binary Search. When they meet the stopping conditions, the Relevant Upper Bound and the Relevant Lower Bound are used in the Goal Result.

これらの定義により、関連する下限は常に関連する上限より小さく（両方が存在する場合）、2 つの関連する境界は二分探索の最も厳しい 2 つの境界と同様に使用されます。それらが停止条件を満たすと、関連する上限と関連する下限が目標結果で使用されます。

5.3.4. Consequences

5.3.4. 帰結

The consequence of the way the Relevant Upper Bound and Relevant Lower Bound are defined is that every Trial Result can have an impact on any current Relevant Upper Bound or Relevant Lower Bound larger than that Trial Load, namely by becoming a new Relevant Upper Bound.

関連する上限と関連する下限の定義の仕方の帰結として、すべてのトライアル結果は、そのトライアル負荷より大きい現在の関連する上限や関連する下限に、つまり新しい関連する上限になることによって、影響を与えうることになります。

This also applies when that Load is measured before another Load gets enough measurements to become a current Relevant Lower Bound or Relevant Upper Bound.

これは、別の負荷が現在の関連する下限や関連する上限になるのに十分な測定を得る前に、その負荷が測定される場合にも当てはまります。

This also implies that if the SUT tested (or the Traffic Generator used) needs a warm-up, it should be warmed up before starting the Search; otherwise, the first few measurements could become unjustly limiting.

これはまた、テスト対象の SUT（または使用するトラフィック生成器）にウォームアップが必要な場合、探索を開始する前にウォームアップすべきであることも意味します。そうしないと、最初のいくつかの測定が不当に制限的になる可能性があります。

For MLRsearch implementations, this means that it is better to measure at smaller Loads first, so any Lower Bounds found earlier are less likely to get invalidated later.

MLRsearch の実装にとって、これは、先に見つかった下限が後で無効化される可能性が低くなるように、より小さい負荷で先に測定する方がよいことを意味します。

5.4. Exceed Ratio and Multiple Trials

5.4. 超過率と複数のトライアル

The idea of performing multiple Trials at the same Trial Load comes from a model where some Trial Results (those with a high Trial Loss Ratio) are affected by infrequent effects, causing unsatisfactory repeatability of [RFC2544] Throughput results. Refer to Section 2.3 for a discussion about noiseful and noiseless ends of the SUT performance spectrum. Stable results are closer to the noiseless end of the SUT performance spectrum, so MLRsearch may need to allow some frequency of High-Loss Trials to ignore the rare but big effects near the noiseful end.

同じトライアル負荷で複数のトライアルを実行するという考えは、一部のトライアル結果（トライアル損失率が高いもの）がまれな影響を受け、[RFC2544] のスループットの結果の再現性が満足できないものになるというモデルから来ています。SUT の性能スペクトルのノイズの多い端とノイズのない端についての議論は Section 2.3 を参照してください。安定した結果は SUT の性能スペクトルのノイズのない端に近いため、MLRsearch は、ノイズの多い端の近くのまれだが大きな影響を無視するために、高損失トライアルのある程度の頻度を許容する必要がある場合があります。

For MLRsearch to perform such Trial Result filtering, it needs a configuration option to tell how frequent the "infrequent" big Trial Loss Ratio can be. This option is called the Goal Exceed Ratio. It tells MLRsearch what ratio of Trials (more specifically, what ratio of Trial Effective Duration seconds) can have a Trial Loss Ratio larger than the Goal Loss Ratio and still be classified as a Lower Bound.

MLRsearch がそのようなトライアル結果のフィルタリングを行うには、「まれな」大きなトライアル損失率がどの程度の頻度でありうるかを伝える構成オプションが必要です。このオプションは目標超過率と呼ばれます。これは、トライアルのどの比率（より具体的には、トライアル実効期間の秒数のどの比率）が、目標損失率より大きいトライアル損失率を持ちながら、依然として下限として分類されうるかを MLRsearch に伝えます。

A zero Goal Exceed Ratio means all Trials must have a Trial Loss Ratio equal to or lower than the Goal Loss Ratio.

目標超過率がゼロの場合、すべてのトライアルのトライアル損失率が目標損失率以下でなければならないことを意味します。

When more than one Trial is intended to classify a Load, MLRsearch also needs something that controls the number of Trials needed. Therefore, each Search Goal also has an attribute called Goal Duration Sum.

負荷を分類するために複数のトライアルが意図されている場合、MLRsearch には必要なトライアルの数を制御する何かも必要です。そのため、各探索目標には目標期間合計と呼ばれる属性もあります。

The meaning of a Goal Duration Sum is that when a Load has Full-Length Trials whose Trial Effective Durations when summed up give a value at least as big as the Goal Duration Sum, the Load is guaranteed to be classified as either an Upper Bound or a Lower Bound for that Search Goal.

目標期間合計の意味は、負荷が、トライアル実効期間を合計すると少なくとも目標期間合計と同じ大きさの値になる完全長のトライアルを持つ場合、その負荷はその探索目標の上限か下限のいずれかに分類されることが保証されるということです。

5.5. Short Trials and Duration Selection

5.5. 短いトライアルと期間の選択

MLRsearch requires each Search Goal to specify its Goal Final Trial Duration.

MLRsearch は、各探索目標がその目標最終トライアル期間を規定することを要求します。

Section 24 of [RFC2544] already anticipates possible time savings when Short Trials are used.

[RFC2544]のSection 24 は、短いトライアルを使用した場合の時間の節約の可能性をすでに予期しています。

An MLRsearch implementation MAY expose configuration parameters that decide whether, when, and how Short Trials are used. The exact heuristics and controls are left to the discretion of the implementer.

MLRsearch の実装は、短いトライアルを使用するかどうか、いつ、どのように使用するかを決める構成パラメーターを公開してもよいです（MAY）。正確なヒューリスティックと制御は実装者の裁量に任されています。

While MLRsearch implementations are free to use any logic to select Trial Inputs, comparability between MLRsearch implementations is only assured when the Load Classification Logic handles any possible set of Trial Results in the same way.

MLRsearch の実装はトライアル入力を選択するために任意のロジックを自由に使用できますが、MLRsearch の実装間の比較可能性は、負荷の分類のロジックが可能なあらゆるトライアル結果の集合を同じ方法で扱う場合にのみ保証されます。

The presence of Short Trial Results complicates the Load Classification Logic; see more details in Section 6.1.

短いトライアルの結果の存在は、負荷の分類のロジックを複雑にします。詳細は Section 6.1 を参照してください。

While the Load Classification algorithm is designed to avoid any unneeded Trials, for explainability reasons, it is recommended for users to use such Controller Inputs that lead to all Trial Durations selected by the Controller to be the same, e.g., by setting any Goal Initial Trial Duration to be a single value also used for all Goal Final Trial Durations.

負荷の分類のアルゴリズムは不要なトライアルを避けるように設計されていますが、説明可能性の理由から、ユーザーは、コントローラーが選択するすべてのトライアル期間が同じになるようなコントローラー入力を使用することが推奨されます。たとえば、目標初期トライアル期間を、すべての目標最終トライアル期間にも使用される単一の値に設定します。

5.6. Generalized Throughput

5.6. 一般化されたスループット

Because testing equipment takes the Intended Load as an input parameter for a Trial measurement, any load search algorithm needs to deal with Intended Load values internally.

テスト機器はトライアルの測定の入力パラメーターとして意図した負荷をとるため、負荷の探索アルゴリズムはどれも内部で意図した負荷の値を扱う必要があります。

But in the presence of Search Goals with a non-zero Goal Loss Ratio, the Load usually does not match the user's intuition of what a throughput is. The Trial Forwarding Rate is better, but it is not obvious how to generalize it for Loads with multiple Trials and a non-zero Goal Loss Ratio.

しかし、ゼロでない目標損失率を持つ探索目標がある場合、負荷は通常、スループットとは何かについてのユーザーの直観と一致しません。トライアル転送レートの方がよいですが、複数のトライアルとゼロでない目標損失率を持つ負荷についてそれをどのように一般化するかは明らかではありません。

The clearest illustration for adopting a generalized throughput definition is the presence of a hard performance limit.

一般化されたスループットの定義を採用することの最も明確な例は、固い性能の限界がある場合です。

5.6.1. Hard Performance Limit

5.6.1. 固い性能の限界

Even if the bandwidth of a medium allows higher traffic forwarding performance, the SUT interfaces may have their own additional limitations, e.g., a specific frames-per-second limit on the Network Interface Card (NIC), a common occurrence.

媒体の帯域幅がより高いトラフィックの転送性能を許す場合でも、SUT のインターフェイスには独自の追加の制限がある場合があります。たとえば、ネットワークインターフェイスカード（NIC）の特定の毎秒フレーム数の制限で、これはよくあることです。

Those limitations should be known and provided as Max Load.

それらの制限は既知であるべきであり、最大負荷として提供すべきです。

But if Max Load is set larger than what the interface can receive or transmit, there will be a hard limit behavior observed in Trial Results.

しかし、最大負荷がインターフェイスで受信または送信できるより大きく設定されている場合、トライアル結果で hard limit の振る舞いが観測されます。

Consider that the hard limit is at one hundred million frames per second (100 Mfps), Max Load is larger, and the Goal Loss Ratio is 0.5%. If DUT introduces no additional losses, 0.5% Trial Loss Ratio will be achieved at the Relevant Lower Bound of 100.5025 Mfps.

固い限界が毎秒 1 億フレーム（100 Mfps）で、最大負荷がそれより大きく、目標損失率が 0.5% であるとします。DUT が追加の損失を導入しない場合、0.5% のトライアル損失率は 100.5025 Mfps の関連する下限で達成されます。

Reporting a throughput that exceeds the SUT's verified hard limit would be counterintuitive. Therefore, the Throughput metric should be generalized to reflect realistic, limit-aware performance.

SUT の検証済みの固い限界を超えるスループットを報告することは直観に反します。そのため、スループットのメトリックは、現実的で限界を意識した性能を反映するように一般化すべきです。

MLRsearch defines one such generalization, the Section 4.8.3. It is the Trial Forwarding Rate from one of the Full-Length Trials performed at the Relevant Lower Bound. For the algorithm to determine exactly which Trial, see Appendix B.

MLRsearch は、そのような一般化の 1 つである Section 4.8.3 を定義しています。これは、関連する下限で実行された完全長のトライアルのうちの 1 つのトライアル転送レートです。正確にどのトライアルかを決定するアルゴリズムについては Appendix B を参照してください。

In the hard limit example, a 100.5025 Mfps Load will still have only a 100.0 Mfps Trial Forwarding Rate, nicely confirming the known limitation.

固い限界の例では、100.5025 Mfps の負荷でもトライアル転送レートは 100.0 Mfps にしかならず、既知の制限をうまく確認できます。

5.6.2. Performance Variability

5.6.2. 性能のばらつき

With a non-zero Goal Loss Ratio, and without hard performance limits, Low-Loss Trials at the same Load may achieve different Trial Forwarding Rate values simply due to DUT performance variability.

ゼロでない目標損失率で、固い性能の限界がない場合、同じ負荷での低損失トライアルが、単に DUT の性能のばらつきによって異なるトライアル転送レートの値になる場合があります。

By comparing the best case (all Relevant Lower Bound Trials have zero loss) and the worst case (all Trial Loss Ratios at the Relevant Lower Bound are equal to the Goal Loss Ratio), one can prove that Conditional Throughput values may have a relative difference up to the Goal Loss Ratio.

最良の場合（関連する下限のすべてのトライアルが損失ゼロ）と最悪の場合（関連する下限のすべてのトライアル損失率が目標損失率に等しい）を比較することで、条件付きスループットの値が最大で目標損失率までの相対的な差を持ちうることを証明できます。

Setting the Goal Width below the Goal Loss Ratio may cause the Conditional Throughput for a larger Goal Loss Ratio to become smaller than a Conditional Throughput for a Search Goal with a lower Goal Loss Ratio, which is counterintuitive, considering they come from the same Search. Therefore, it is RECOMMENDED to set the Goal Width to a value no lower than the Goal Loss Ratio of the next higher loss Search Goal.

目標幅を目標損失率より小さく設定すると、より大きい目標損失率の条件付きスループットが、より低い目標損失率を持つ探索目標の条件付きスループットより小さくなる可能性があり、それらが同じ探索から得られたものであることを考えると直観に反します。そのため、目標幅は、次に損失の高い探索目標の目標損失率以上の値に設定することが推奨されます（RECOMMENDED）。

Although Conditional Throughput can fluctuate from one run to the next, it still offers a more nuanced basis for comparison than the Relevant Lower Bound, particularly when deterministic Load selection yields the same Relevant Lower Bound value across multiple runs.

条件付きスループットは実行ごとに変動する可能性がありますが、特に決定論的な負荷の選択が複数の実行で同じ関連する下限の値を生む場合には、関連する下限よりもきめ細かい比較の基礎を提供します。

6. MLRsearch Logic

6. MLRsearch のロジック

This section uses informal language to describe two aspects of MLRsearch logic: Load Classification and Conditional Throughput, reflecting formal pseudocode representation provided in Appendix A and Appendix B.

このセクションでは、非公式な言葉を使用して、MLRsearch のロジックの 2 つの側面、つまり負荷の分類と条件付きスループットを説明します。これらは Appendix A と Appendix B で提供されている形式的な擬似コードの表現を反映しています。

The logic is equivalent but not identical to the pseudocode in the appendices. The pseudocode is designed to be short and frequently combines multiple operations into one expression. The logic, as described in this section, lists each operation separately and uses more intuitive names for the intermediate values.

このロジックは付録の擬似コードと等価ですが、同一ではありません。擬似コードは短くなるように設計されており、複数の操作を 1 つの式にまとめていることがよくあります。このセクションで説明するロジックは、各操作を個別に挙げ、中間の値により直観的な名前を使用しています。

A detailed description of an example Search is in Appendix C.

探索の例の詳しい説明は Appendix C にあります。

6.1. Load Classification Logic

6.1. 負荷の分類のロジック

For clarity of explanation, variables are tagged as (I)nput, (T)emporary, and (O)utput.

説明を明確にするために、変数に (I)nput（入力）、(T)emporary（一時）、(O)utput（出力）のタグを付けます。

  • Collect Trial Results:

    • Take all Trial Results (I) measured at a given Load.

  • Aggregate Trial Durations:

    • Full-Length High-Loss sum (T) is the sum of Trial Effective Duration values of all Full-Length High-Loss Trials (I).

    • Full-Length Low-Loss sum (T) is the sum of Trial Effective Duration values of all Full-Length Low-Loss Trials (I).

    • Short High-Loss sum is the sum (T) of Trial Effective Duration values of all Short High-Loss Trials (I).

    • Short Low-Loss sum is the sum (T) of Trial Effective Duration values of all Short Low-Loss Trials (I).

  • Derive goal-based ratios:

    • Subceed ratio (T) is one minus the Goal Exceed Ratio (I).

    • Exceed coefficient (T) is the Goal Exceed Ratio divided by the subceed ratio.

  • Balance Short Trial effects:

    • Balancing sum (T) is the Short Low-Loss sum multiplied by the exceed coefficient.

    • Excess sum (T) is the Short High-Loss sum minus the balancing sum.

    • Positive excess sum (T) is the maximum of zero and the excess sum.

  • Compute effective duration totals:

    • Effective High-Loss sum (T) is the Full-Length High-Loss sum plus the positive excess sum.

    • Effective full sum (T) is the effective High-Loss sum plus the Full-Length Low-Loss sum.

    • Effective whole sum (T) is the larger of the effective full sum and the Goal Duration Sum.

    • Missing sum (T) is the effective whole sum minus the effective full sum.

  • Estimate exceed ratios:

    • Pessimistic High-Loss sum (T) is the effective High-Loss sum plus the missing sum.

    • Optimistic exceed ratio (T) is the effective High-Loss sum divided by the effective whole sum.

    • Pessimistic exceed ratio (T) is the pessimistic High-Loss sum divided by the effective whole sum.

  • Classify the Load:

    • The Load is classified as an Upper Bound (O) if the optimistic exceed ratio is larger than the Goal Exceed Ratio.

    • The Load is classified as a Lower Bound (O) if the pessimistic exceed ratio is not larger than the Goal Exceed Ratio.

    • The Load is classified as Undecided (O) otherwise.

  • トライアル結果を収集する:

    • 所与の負荷で測定されたすべてのトライアル結果（I）をとる。

  • トライアル期間を集計する:

    • 完全長の高損失の合計（T）は、すべての完全長の高損失トライアル（I）のトライアル実効期間の値の合計です。

    • 完全長の低損失の合計（T）は、すべての完全長の低損失トライアル（I）のトライアル実効期間の値の合計です。

    • 短い高損失の合計（T）は、すべての短い高損失トライアル（I）のトライアル実効期間の値の合計です。

    • 短い低損失の合計（T）は、すべての短い低損失トライアル（I）のトライアル実効期間の値の合計です。

  • 目標に基づく比率を導出する:

    • 未超過率（T）は、1 から目標超過率（I）を引いたものです。

    • 超過係数（T）は、目標超過率を未超過率で割ったものです。

  • 短いトライアルの影響を釣り合わせる:

    • 釣り合わせの合計（T）は、短い低損失の合計に超過係数を掛けたものです。

    • 超過の合計（T）は、短い高損失の合計から釣り合わせの合計を引いたものです。

    • 正の超過の合計（T）は、ゼロと超過の合計のうち大きい方です。

  • 実効期間の総計を計算する:

    • 実効的な高損失の合計（T）は、完全長の高損失の合計に正の超過の合計を加えたものです。

    • 実効的な完全な合計（T）は、実効的な高損失の合計に完全長の低損失の合計を加えたものです。

    • 実効的な全体の合計（T）は、実効的な完全な合計と目標期間合計のうち大きい方です。

    • 不足の合計（T）は、実効的な全体の合計から実効的な完全な合計を引いたものです。

  • 超過率を推定する:

    • 悲観的な高損失の合計（T）は、実効的な高損失の合計に不足の合計を加えたものです。

    • 楽観的な超過率（T）は、実効的な高損失の合計を実効的な全体の合計で割ったものです。

    • 悲観的な超過率（T）は、悲観的な高損失の合計を実効的な全体の合計で割ったものです。

  • 負荷を分類する:

    • 楽観的な超過率が目標超過率より大きい場合、負荷は上限（O）として分類される。

    • 悲観的な超過率が目標超過率より大きくない場合、負荷は下限（O）として分類される。

    • それ以外の場合、負荷は未決定（O）として分類される。

6.2. Conditional Throughput Logic

6.2. 条件付きスループットのロジック

  • Collect Trial Results:

    • Take all Trial Results (I) measured at a given Load.

  • Sum of Full-Length Durations:

    • Full-Length High-Loss sum (T) is the sum of Trial Effective Duration values of all Full-Length High-Loss Trials (I).

    • Full-Length Low-Loss sum (T) is the sum of Trial Effective Duration values of all Full-Length Low-Loss Trials (I).

    • Full-Length sum (T) is the Full-Length High-Loss sum (I) plus the Full-Length Low-Loss sum (I).

  • Derive initial thresholds:

    • Subceed ratio (T) is one minus the Goal Exceed Ratio (I).

    • Remaining sum (T) is initially the Full-Length sum multiplied by the subceed ratio.

    • Current loss ratio (T) is initially 100%.

  • Iterate through ordered Trials:

    • For each Full-Length Trial Result, sorted in increasing order by Trial Loss Ratio:

      • If the remaining sum is not larger than zero, exit the loop.

      • Set the current loss ratio to this Trial's Trial Loss Ratio (I).

      • Decrease the remaining sum by this Trial's Trial Effective Duration (I).

  • Compute Conditional Throughput:

    • Current forwarding ratio (T) is one minus the current loss ratio.

    • Conditional Throughput (T) is the current forwarding ratio multiplied by the Load value.

  • トライアル結果を収集する:

    • 所与の負荷で測定されたすべてのトライアル結果（I）をとる。

  • 完全長の期間の合計:

    • 完全長の高損失の合計（T）は、すべての完全長の高損失トライアル（I）のトライアル実効期間の値の合計です。

    • 完全長の低損失の合計（T）は、すべての完全長の低損失トライアル（I）のトライアル実効期間の値の合計です。

    • 完全長の合計（T）は、完全長の高損失の合計（I）に完全長の低損失の合計（I）を加えたものです。

  • 初期のしきい値を導出する:

    • 未超過率（T）は、1 から目標超過率（I）を引いたものです。

    • 残りの合計（T）は、最初は完全長の合計に未超過率を掛けたものです。

    • 現在の損失率（T）は、最初は 100% です。

  • 順序付けられたトライアルを反復する:

    • トライアル損失率の昇順に並べた各完全長のトライアル結果について:

      • 残りの合計がゼロより大きくない場合は、ループを抜ける。

      • 現在の損失率をこのトライアルのトライアル損失率（I）に設定する。

      • 残りの合計をこのトライアルのトライアル実効期間（I）だけ減らす。

  • 条件付きスループットを計算する:

    • 現在の転送率（T）は、1 から現在の損失率を引いたものです。

    • 条件付きスループット（T）は、現在の転送率に負荷の値を掛けたものです。

6.2.1. Conditional Throughput and Load Classification

6.2.1. 条件付きスループットと負荷の分類

Conditional Throughput and results of Load Classification overlap but are not identical.

条件付きスループットと負荷の分類の結果は重なり合いますが、同一ではありません。

  • When a Load is marked as a Relevant Lower Bound, its Conditional Throughput is taken from a Trial whose Trial Loss Ratio is not larger than the Goal Loss Ratio.

  • The reverse is not guaranteed: If the Goal Width is narrower than the Goal Loss Ratio, Conditional Throughput can still end up higher than the Relevant Upper Bound.

  • 負荷が関連する下限としてマークされている場合、その条件付きスループットは、トライアル損失率が目標損失率より大きくないトライアルからとられます。

  • 逆は保証されません。目標幅が目標損失率より狭い場合、条件付きスループットが関連する上限より高くなる可能性があります。

6.3. SUT Behaviors

6.3. SUT の振る舞い

In Section 2.3, the notion of noise is introduced. This section uses new terms to describe possible SUT behaviors more precisely.

Section 2.3 では、ノイズの概念を導入しました。このセクションでは、新しい用語を使用して、可能な SUT の振る舞いをより正確に説明します。

From a measurement point of view, noise is visible as Inconsistent Trial Results. See Section 2.6 for general points and Section 5.3.2 for specifics when comparing different Load values.

測定の観点からは、ノイズは一貫性のないトライアル結果として見えます。一般的な点については Section 2.6 を、異なる負荷の値を比較する場合の具体的な点については Section 5.3.2 を参照してください。

Load Classification and Conditional Throughput apply to a single Load value, but even the set of Trial Results measured at that Trial Load value may appear inconsistent.

負荷の分類と条件付きスループットは単一の負荷の値に適用されますが、そのトライアル負荷の値で測定されたトライアル結果の集合でさえ、一貫性がないように見える場合があります。

As MLRsearch aims to save time, it executes only a small number of Trials, getting only a limited amount of information about SUT behavior. It is useful to introduce a SUT expert point of view to contrast with that limited information.

MLRsearch は時間の節約を目指しているため、少数のトライアルしか実行せず、SUT の振る舞いについて限られた量の情報しか得られません。その限られた情報と対比するために、SUT expert の視点を導入すると便利です。

6.3.1. Expert Predictions

6.3.1. 専門家の予測

Imagine that before the Search starts, a human expert had unlimited time to measure SUT and obtain all reliable information about it. The information is not perfect, as there is still random noise influencing SUT. But the expert is familiar with possible noise events, even the rare ones, and thus, the expert can do probabilistic predictions about future Trial Outputs.

探索の開始前に、人間の専門家が SUT を測定してそれについてのすべての信頼できる情報を得るための無制限の時間を持っていたと想像してください。SUT に影響するランダムなノイズは依然として存在するため、その情報は完全ではありません。しかし、専門家は、まれなものも含めて可能なノイズの事象をよく知っているため、将来のトライアル出力について確率的な予測を行うことができます。

When several outcomes are possible, the expert can assess the probability of each outcome.

複数の結果が可能な場合、専門家は各結果の確率を評価できます。

6.3.2. Exceed Probability

6.3.2. 超過確率

When the Controller selects a new Trial Duration and Trial Load, and just before the Measurer starts performing the Trial, the SUT expert can envision possible Trial Results.

コントローラーが新しいトライアル期間とトライアル負荷を選択し、測定器がトライアルの実行を開始する直前に、SUT の専門家は可能なトライアル結果を思い描くことができます。

With respect to a particular Search Goal, the possibilities can be summarized into a single number: Exceed Probability. It is the probability (according to the expert) that the measured Trial Loss Ratio will be higher than the Goal Loss Ratio.

特定の探索目標に関して、その可能性は単一の数、つまり超過確率（Exceed Probability）にまとめることができます。これは、測定されるトライアル損失率が目標損失率より高くなる（専門家による）確率です。

6.3.3. Trial Duration Dependence

6.3.3. トライアル期間への依存

When comparing Exceed Probability values for the same Trial Load value but different Trial Duration values, there are several patterns that commonly occur in practice.

同じトライアル負荷の値で異なるトライアル期間の値について超過確率の値を比較すると、実際によく見られるいくつかのパターンがあります。

6.3.3.1. Strong Increase
6.3.3.1. 強い増加

Exceed Probability is very low for Short Trials but very high for Full-Length Trials. This SUT behavior is undesirable and may hint at a faulty SUT, e.g., SUT leaks resources and is unable to sustain the desired performance.

超過確率は、短いトライアルでは非常に低いが、完全長のトライアルでは非常に高くなります。この SUT の振る舞いは望ましくなく、SUT の欠陥を示唆している可能性があります。たとえば、SUT が資源をリークし、望む性能を維持できない場合です。

But this behavior is also seen when SUT uses large amount of buffers. This is the main reason users may want to set a large Goal Final Trial Duration.

しかし、この振る舞いは SUT が大量のバッファーを使用する場合にも見られます。これが、ユーザーが大きな目標最終トライアル期間を設定したい主な理由です。

6.3.3.2. Mild Increase
6.3.3.2. 緩やかな増加

Short Trials are slightly less likely to become High-Loss according to the Goal Loss Ratio, but the slope is modest. This mild increase is typical when noise is dominated by rare, large loss spikes: During a Full-Length Trial, the good-performing periods cannot fully offset the heavy frame loss that occurs in the brief low-performing bursts.

短いトライアルは、目標損失率に従って高損失になる可能性がわずかに低いですが、傾きは控えめです。この緩やかな増加は、ノイズがまれで大きな損失のスパイクに支配されている場合に典型的です。完全長のトライアルの間、性能のよい期間は、短い性能の低いバーストで発生する重いフレームの損失を完全には相殺できません。

6.3.3.3. Independence
6.3.3.3. 独立

Short Trials have basically the same Exceed Probability as Full-Length Trials. This is possible only if loss spikes are small (so other parts can compensate) and if the Goal Loss Ratio is more than zero (otherwise, other parts cannot compensate at all).

短いトライアルは、完全長のトライアルと基本的に同じ超過確率を持ちます。これは、損失のスパイクが小さく（ほかの部分が補償できる）、目標損失率がゼロより大きい（そうでなければ、ほかの部分はまったく補償できない）場合にのみ可能です。

6.3.3.4. Decrease
6.3.3.4. 減少

Short Trials have a larger Exceed Probability than Full-Length Trials. This can only be possible for a non-zero Goal Loss Ratio, for example, if the SUT needs to "warm up" to the best performance within each Trial, which is not commonly seen in practice.

短いトライアルは、完全長のトライアルより大きい超過確率を持ちます。これはゼロでない目標損失率の場合にのみ可能で、たとえば SUT が各トライアル内で最良の性能まで「ウォームアップ」する必要がある場合ですが、これは実際にはあまり見られません。

8. Security Considerations

8. セキュリティーに関する考慮事項

Benchmarking activities as described in this document are limited to the technology characterization of a DUT/SUT using controlled stimuli in a laboratory environment, with dedicated address space and the constraints specified in the sections above.

この文書で説明するベンチマーキングの活動は、専用のアドレス空間と上記のセクションで規定した制約のもとで、実験室環境で制御された刺激を使用して DUT/SUT の技術的な特性評価を行うことに限定されています。

The benchmarking network topology will be an independent test setup and MUST NOT be connected to devices that may forward the test traffic into a production network or misroute traffic to the test management network.

ベンチマーキングのネットワークトポロジーは独立したテストのセットアップとなります。テストトラフィックを本番のネットワークに転送したり、トラフィックをテスト管理ネットワークに誤ってルーティングしたりする可能性のあるデバイスに接続してはなりません（MUST NOT）。

Further, benchmarking is performed on an "opaque" basis, relying solely on measurements observable external to the DUT/SUT.

さらに、ベンチマーキングは、DUT/SUT の外部から観測可能な測定のみに依存する「不透明な」方法で行われます。

The DUT/SUT SHOULD NOT include features that serve only to boost benchmark scores, such as a dedicated "fast-track" test mode that is never used in normal operation.

DUT/SUT は、通常の運用では決して使用されない専用の「高速トラック」のテストモードのような、ベンチマークのスコアを上げるためだけの機能を含むべきではありません（SHOULD NOT）。

Any implications for network security arising from the DUT/SUT SHOULD be identical in the lab and in production networks.

DUT/SUT から生じるネットワークセキュリティーへの影響は、実験室と本番のネットワークで同一であるべきです（SHOULD）。

次の探索の例は、複数の探索目標で開始された MLRsearch のテスト手順の探索の部分の、1 回の仮想的な実行に関するものです。ロジックがどのように機能するかを示すために、利用可能なトライアル結果の特定の集合を持つ、いくつかの時点が選ばれています。ロジックのいくつかのコーナーケースを示すことが目的であるため、トライアル結果自体はあまり現実的ではありません。

すべてのトライアルで、トライアル実効期間はトライアル期間に等しくなります。

焦点を当てる負荷は 1 つだけで、その値は毎秒 100 万フレーム（1 Mfps）です。ここで示すロジックの部分はほかの負荷のトライアル結果に依存しないため、それらには言及しません。実際には、ほかの負荷の値でのトライアル結果も存在するはずです。たとえば、MLRsearch は見つかったどの上限よりも小さい下限を探します。

C.4. Conditional Throughput Computations

C.4. 条件付きスループットの計算

At the end of this hypothetical Search, the "RFC2544" goal labels the Load as an Upper Bound, making it ineligible for Conditional Throughput computation. By contrast, the other three Search Goals treat the same Load as a Lower Bound; if it is also accepted as their Relevant Lower Bound, Conditional Throughput values can be computed for each of them.

この仮想的な探索の終了時に、"RFC2544" の目標はこの負荷を上限とみなしており、条件付きスループットの計算の対象外になります。これに対して、ほかの 3 つの探索目標は同じ負荷を下限として扱っています。それがそれらの関連する下限としても受け入れられれば、それぞれについて条件付きスループットの値を計算できます。

(The Load under discussion is one million frames per second.)

（議論している負荷は毎秒 100 万フレームです。）
