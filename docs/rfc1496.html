RFC 1496

Rules for Downgrading Messages from X.400/88 to X.400/84 When MIME Content-Types are Present in the Messages

RFC 1496

MIME Content-TypeがメッセージにあるときにX.400/88からX.400/84へメッセージをダウングレードするための規則

Status of This Memo

このメモのステータス

This RFC specifies an IAB standards track protocol for the Internet community, and requests discussion and suggestions for improvements. Please refer to the current edition of the "IAB Official Protocol Standards" for the standardization state and status of this protocol. Distribution of this memo is unlimited.

このRFCは、インターネットコミュニティーのためのIAB標準化過程のプロトコルを規定し、改善のための議論と提案を求めるものです。このプロトコルの標準化の状態とステータスについては、「IAB Official Protocol Standards」の最新版を参照してください。このメモの配布は無制限です。

1. Introduction

1. はじめに

Interworking between X.400(88) and MIME is achieved by [4], which complements RFC-1327 [2], which in turn specifies the interworking between X.400(88) and RFC-822 based mail.

X.400(88)とMIMEの相互運用は[4]によって実現されます。これは、X.400(88)とRFC-822ベースのメールとの相互運用を規定するRFC-1327 [2]を補完するものです。

Interworking between X.400(88) and X.400 (84) is achieved by RFC-1328 [3]. That document does not describe what to do in the case where body parts arrive at the gateway that cannot be adequately represented in the X.400(84) system.

X.400(88)とX.400 (84)の相互運用は、RFC-1328 [3]によって実現されます。この文書では、X.400(84)システムで適切に表現できないボディーパートがゲートウェイに到着した場合にどうすべきかは記述されていません。

This document describes how RFC-1328 must be modified in order to provide adequate support for the scenarios:

この文書は、次のシナリオを適切にサポートするために、RFC-1328をどのように変更しなければならないかを記述します。

SMTP(MIME) -> X.400(84)

X.400(84) -> SMTP(MIME)

SMTP(MIME) -> X.400(84)

X.400(84) -> SMTP(MIME)

It replaces chapter 6 of RFC-1328. The rest of RFC-1328 is NOT obsoleted.

この文書は、RFC-1328の第6章を置き換えます。RFC-1328の残りの部分は廃止されません。

NOTE: A desireable side-effect of HARPOON is that a standardized method for the identification and transmission of multimedia and binary data (like spreadsheets) between X.400/84 UAs is achieved.

注記: HARPOONの望ましい副次的効果として、X.400/84のUA間でマルチメディアデータやバイナリーデータ（スプレッドシートなど）を識別して伝送するための標準化された方法が実現されます。

While this method is not compatible with current proprietary approaches, we believe that it requires less invasive changes to current UAs than other possible methods.

この方法は現在の独自のアプローチとは互換性がありませんが、他に考えられる方法よりも、現在のUAに対する変更は少なくて済むと考えています。

This memo updates RFC 1328. HARPOON is a pure name, and has no meaning. Please send comments to the MIME-MHS mailing list <mime-mhs@surnet.nl>.

このメモはRFC 1328を更新します。HARPOONは単なる名前であり、意味はありません。コメントは、MIME-MHSメーリングリスト<mime-mhs@surnet.nl>に送ってください。

2. Basic approach

2. 基本的なアプローチ

The approach is to imagine that the connection X.400(84) <-> SMTP(MIME) never happens. This, of course, is an illusion, but can be a very useful illusion.

このアプローチでは、X.400(84) <-> SMTP(MIME)の接続は決して起こらないと想定します。もちろんこれは幻想ですが、非常に有用な幻想になりえます。

All mail will therefore go on one of the paths

したがって、すべてのメールは次のいずれかの経路をたどります。

X.400(84) -> X.400(88) -> SMTP(MIME)

SMTP(MIME) -> X.400(88) -> X.400(84)

X.400(84) -> X.400(88) -> SMTP(MIME)

SMTP(MIME) -> X.400(88) -> X.400(84)

when it goes between a MIME user and an X.400(84) user.

これは、メールがMIMEユーザーとX.400(84)ユーザーの間でやり取りされる場合です。

The approach at the interface between X.400(88) and X.400(84) is:

X.400(88)とX.400(84)の間のインターフェイスにおけるアプローチは次のとおりです。

  • Convert what you can
  • Encapsulate what you have to
  • Never drop a message
  • 変換できるものは変換する
  • 必要なものはカプセル化する
  • メッセージは決して破棄しない

Of course, for X.400/88 body parts that are already defined in X.400/84, no downgrading should be done. In particular, multi-body messages should remain multi-body messages, IA5 messages including IA5 messages encoded as Extended Body Parts) should remain IA5 messages, and G3Fax messages should remain G3Fax messages.

もちろん、X.400/84ですでに定義されているX.400/88のボディーパートについては、ダウングレードを行うべきではありません。特に、マルチボディーのメッセージはマルチボディーのメッセージのまま、IA5メッセージ（拡張ボディーパートとしてエンコードされたIA5メッセージを含む）はIA5メッセージのまま、G3FaxメッセージはG3Faxメッセージのままにすべきです。

3. Conversion rules

3. 変換規則

3.1. EBP conversions to Basic

3.1. EBPからBasicへの変換

Some body parts are defined by X.400(88) as having both a Basic form and an Extended form. These are listed in Annex B of X.420.

いくつかのボディーパートは、X.400(88)によって、Basic形式とExtended形式の両方を持つものとして定義されています。それらはX.420の附属書Bに列挙されています。

For all of these, the transformation from the Extended Body Part to the Basic Body Part takes the form of putting the PARAMETERS and the DATA members together in a SEQUENCE.

これらすべてについて、拡張ボディーパート（Extended Body Part）から基本ボディーパート（Basic Body Part）への変換は、PARAMETERSメンバーとDATAメンバーを1つのSEQUENCEにまとめる形をとります。

This transformation should be applied by the gateway in order to allow (for example) X.400(88) systems that use the Extended form of the IA5 body part to communicate with X.400(84) systems.

たとえばIA5ボディーパートのExtended形式を使うX.400(88)システムがX.400(84)システムと通信できるように、ゲートウェイはこの変換を適用すべきです。

3.2. Encapsulation format

3.2. カプセル化の形式

For any body part that cannot be used directly in X.400(84), the following IA5Text body part is made:

X.400(84)で直接使用できないボディーパートについては、次のIA5Textボディーパートを作成します。

  • Content = IA5String

  • First bytes of content: (the description is in USASCII, with C escape sequences used to represent control characters):

     MIME-version: <version>\r\n
     Content-type: <the proper MIME content type>\r\n
   Content-transfer-encoding: <quoted-printable or base64>\r\n
   <Possibly other Content headings here, terminated by\r\n>
   \r\n

<Here follows the bytes of the content, as per [4], encoded in the
proper encoding>
  • Content = IA5String

  • コンテンツの最初のバイト列（記述はUSASCIIで行い、制御文字を表すのにCのエスケープシーケンスを使用します）:

     MIME-version: <version>\r\n
     Content-type: <the proper MIME content type>\r\n
   Content-transfer-encoding: <quoted-printable or base64>\r\n
   <Possibly other Content headings here, terminated by\r\n>
   \r\n

<Here follows the bytes of the content, as per [4], encoded in the
proper encoding>

All implementations MUST place the MIME-version: header first in the body part. Headers that are placed by [2] and [4] into other parts of the message MUST NOT be placed in the MIME body part.

すべての実装は、MIME-version:ヘッダーをボディーパートの先頭に置かなければなりません（MUST）。[2]と[4]によってメッセージの他の部分に置かれるヘッダーは、MIMEボディーパートに置いてはなりません（MUST NOT）。

This includes RFC-822 headings carried as heading-extensions, which must be placed in a new IA5 body part starting with the string "RFC-822-HEADERS", as specified in [2], Appendix G.

これには、heading-extensionとして運ばれるRFC-822ヘッディングも含まれます。それらは、[2]の付録Gで規定されているように、文字列「RFC-822-HEADERS」で始まる新しいIA5ボディーパートに置かなければなりません。

Other heading-extensions are still handled as described in chapter 5 of RFC 1328: They are dropped.

その他のheading-extensionは、引き続きRFC 1328の第5章に記述されているとおりに扱われます。つまり、破棄されます。

Since all X.400(88) body parts can be represented in MIME by using the x400-bp MIME content-type, this conversion will never fail.

X.400(88)のすべてのボディーパートは、x400-bpというMIMEコンテンツタイプを使用することでMIMEで表現できるので、この変換が失敗することはありません。

In the reverse direction, any IA5 body part that starts with the token "MIME-Version:" will be subjected to conversion according to [4] before including the body part into an X.400(88) message.

逆方向では、トークン「MIME-Version:」で始まるIA5ボディーパートは、X.400(88)メッセージに含める前に、[4]に従って変換されます。

4. Implications

4. 影響

The implications are several:

影響はいくつかあります。

  • People with X.400(84) readers who have the ability to save messages to file will now be able to save MIME multimedia messages
  • People who can use features like the "Mailcaps" file to identify what to do about a bodypart can now grab implementations of MIME that can run as subprograms and achieve at least some multimedia functionality
  • メッセージをファイルに保存する機能を持つX.400(84)リーダーの利用者は、MIMEマルチメディアメッセージを保存できるようになります
  • ボディーパートをどう扱うかを識別するのに「Mailcaps」ファイルのような機能を使える人は、サブプログラムとして実行できるMIMEの実装を入手して、少なくともある程度のマルチメディア機能を実現できるようになります

5. Security Considerations

5. セキュリティーに関する考慮事項

The security considerations in [1] and [4] (beware of trojans that can hit you if your UA automagically starts programs for you) are now relevant also for X.400(84) systems.

[1]と[4]にあるセキュリティーに関する考慮事項（UAが自動的にプログラムを起動する場合に攻撃を受けるおそれのあるトロイの木馬に注意すること）は、X.400(84)システムにも関係するようになります。
