RFC 2496

Definitions of Managed Object for the DS3/E3 Interface Type

RFC 2496

DS3/E3のインターフェイスタイプのための管理オブジェクトの定義

Abstract

概要

This memo defines a portion of the Management Information Base (MIB) for use with network management protocols in the Internet community. In particular, it describes objects used for managing DS3 and E3 interfaces. This document is a companion document with Definitions of Managed Objects for the DS0 (RFC 2494 [25]), DS1/E1/DS2/E2 (RFC 2495 [17]), and the work in progress SONET/SDH Interface Types.

このメモは、インターネットコミュニティーのネットワーク管理プロトコルで使用するための管理情報ベース（MIB）の一部を定義します。特に、DS3とE3のインターフェイスを管理するために使用されるオブジェクトを記述します。この文書は、DS0（RFC 2494[25]）、DS1/E1/DS2/E2（RFC 2495[17]）、および作業中のSONET/SDHのインターフェイスタイプのための管理オブジェクトの定義と対になる文書です。

This memo specifies a MIB module in a manner that is both compliant to the SNMPv2 SMI, and semantically identical to the peer SNMPv1 definitions.

このメモは、SNMPv2 SMIに準拠し、かつ対応するSNMPv1の定義と意味的に同一である形でMIBモジュールを規定します。

1. The SNMP Management Framework

1. SNMP管理フレームワーク

The SNMP Management Framework presently consists of five major components:

SNMP管理の枠組みは、現在、5つの主要な構成要素からなります。

  • An overall architecture, described in RFC 2271 [1].
  • Mechanisms for describing and naming objects and events for the purpose of management. The first version of this Structure of Management Information (SMI) is called SMIv1 and described in STD 16, RFC 1155 [2], STD 16, RFC 1212 [3] and RFC 1215 [4]. The second version, called SMIv2, is described in RFC 1902 [5], RFC 1903 [6] and RFC 1904 [7].
  • Message protocols for transferring management information. The first version of the SNMP message protocol is called SNMPv1 and described in STD 15, RFC 1157 [8]. A second version of the SNMP message protocol, which is not an Internet standards track protocol, is called SNMPv2c and described in RFC 1901 [9] and RFC 1906 [10]. The third version of the message protocol is called SNMPv3 and described in RFC 1906 [10], RFC 2272 [11] and RFC 2274 [12].
  • Protocol operations for accessing management information. The first set of protocol operations and associated PDU formats is described in STD 15, RFC 1157 [8]. A second set of protocol operations and associated PDU formats is described in RFC 1905 [13].
  • A set of fundamental applications described in RFC 2273 [14] and the view-based access control mechanism described in RFC 2275 [15]. Managed objects are accessed via a virtual information store, termed the Management Information Base or MIB. Objects in the MIB are defined using the mechanisms defined in the SMI.
  • RFC 2271 [1]で説明されている全体的なアーキテクチャー。
  • 管理の目的でオブジェクトとイベントを記述し命名するための仕組み。この管理情報の構造（SMI）の最初のバージョンはSMIv1と呼ばれ、STD 16、RFC 1155 [2]、STD 16、RFC 1212 [3]、およびRFC 1215 [4]で説明されています。2番目のバージョンはSMIv2と呼ばれ、RFC 1902 [5]、RFC 1903 [6]、およびRFC 1904 [7]で説明されています。
  • 管理情報を転送するためのメッセージプロトコル。SNMPメッセージプロトコルの最初のバージョンはSNMPv1と呼ばれ、STD 15、RFC 1157 [8]で説明されています。SNMPメッセージプロトコルの2番目のバージョンは、インターネット標準化過程のプロトコルではありませんが、SNMPv2cと呼ばれ、RFC 1901 [9]とRFC 1906 [10]で説明されています。メッセージプロトコルの3番目のバージョンはSNMPv3と呼ばれ、RFC 1906 [10]、RFC 2272 [11]、およびRFC 2274 [12]で説明されています。
  • 管理情報にアクセスするためのプロトコル操作。最初のプロトコル操作の集まりとそれに関連するPDUの形式は、STD 15、RFC 1157 [8]で説明されています。2番目のプロトコル操作の集まりとそれに関連するPDUの形式は、RFC 1905 [13]で説明されています。
  • RFC 2273[14]で説明されている基本的なアプリケーションの集まりと、RFC 2275[15]で説明されているビューベースのアクセス制御の仕組み。管理対象のオブジェクトには、管理情報ベース（MIB）と呼ばれる仮想的な情報ストアを介してアクセスします。MIBの中のオブジェクトは、SMIで定義されている仕組みを使用して定義されます。

This memo specifies a MIB module that is compliant to the SMIv2. A MIB conforming to the SMIv1 can be produced through the appropriate translations. The resulting translated MIB must be semantically equivalent, except where objects or events are omitted because no translation is possible (use of Counter64).

このメモは、SMIv2に準拠したMIBモジュールを規定します。SMIv1に準拠したMIBは、適切な変換によって作成できます。変換の結果のMIBは、変換が不可能なため（Counter64の使用）オブジェクトやイベントが省略される場合を除き、意味的に同等でなければなりません。

Some machine readable information in SMIv2 will be converted into textual descriptions in SMIv1 during the translation process. However, this loss of machine readable information is not considered to change the semantics of the MIB.

SMIv2の一部の機械可読な情報は、変換の過程でSMIv1のテキストの記述に変換されます。ただし、この機械可読な情報の喪失は、MIBのセマンティクスを変更するものとはみなされません。

1.1. Changes from RFC1407

1.1. RFC1407からの変更点

This MIB obsoletes RFC1407. The changes from RFC1407 are the following:

このMIBはRFC1407を廃止します。RFC1407からの変更点は次のとおりです。

  1. The Fractional Table has been deprecated
  2. This document uses SMIv2
  3. Values are given for ifTable and ifXTable
  4. Example usage of ifStackTable is included
  5. dsx3IfIndex has been deprecated
  6. The definition of valid intervals has been clarified for the case where the agent proxied for other devices. In particular, the treatment of missing intervals has been clarified.
  7. An inward loopback has been added.
  8. Additional lineStatus bits have been added for Near End in Unavailable Signal State, Carrier Equipment Out of Service, DS@ Payload AIS, and DS@ Performance Threshold
  9. A read-write line Length object has been added.
  10. Added a lineStatus last change, trap and enabler.
  11. Textual Conventions for statistics objects have been used.
  12. A new object, dsx3LoopbackStatus, has been introduced to reflect the loopbacks established on a DS3/E3 interface and the source to the requests. dsx3LoopbackConfig continues to be the desired loopback state while dsx3LoopbackStatus reflects the actual state.
  13. A dual loopback has been added to allow the setting of an inward loopback and a line loopback at the same time.
  14. An object has been added to indicated whether or not this is a channelized DS3/E3.
  15. A new object has been added to indicate which DS1 is to set for remote loopback.
  1. フラクショナルテーブルは非推奨になりました。
  2. この文書はSMIv2を使用します。
  3. ifTableとifXTableの値を示しています。
  4. ifStackTableの使用例を含めています。
  5. dsx3IfIndexは非推奨になりました。
  6. エージェントが他の機器のプロキシーとして動作する場合について、有効な区間の定義を明確にしました。特に、欠落した区間の扱いを明確にしました。
  7. 内向きのループバックが追加されました。
  8. 近端の利用不能信号状態、キャリア機器のサービス停止、DS@ペイロードAIS、およびDS@性能しきい値のための追加のlineStatusのビットが追加されました。
  9. 読み書き可能な回線の長さのオブジェクトが追加されました。
  10. lineStatusの最終変更、トラップ、およびその有効化の設定を追加しました。
  11. 統計のオブジェクトにテキスト規約を使用しました。
  12. DS3/E3インターフェイス上で確立されたループバックと、その要求の発生元を反映するために、新しいオブジェクトdsx3LoopbackStatusを導入しました。dsx3LoopbackConfigは引き続き望ましいループバックの状態を表し、dsx3LoopbackStatusは実際の状態を反映します。
  13. 内向きのループバックと回線のループバックを同時に設定できるように、デュアルループバックが追加されました。
  14. これがチャネル化されたDS3/E3であるかどうかを示すオブジェクトが追加されました。
  15. リモートのループバックにどのDS1を設定するかを示す新しいオブジェクトが追加されました。

2.3. Objectives of this MIB Module

2.3. このMIBモジュールの目的

There are numerous things that could be included in a MIB for DS3/E3 signals: the management of multiplexors, CSUs, DSUs, and the like. The intent of this document is to facilitate the common management of all devices with DS3/E3 interfaces. As such, a design decision was made up front to very closely align the MIB with the set of objects that can generally be read from DS3/E3 devices that are currently deployed.

DS3/E3信号のためのMIBには、マルチプレクサー、CSU、DSUなどの管理といった、数多くのものを含めることができます。この文書の意図は、DS3/E3インターフェイスを持つすべての機器の共通の管理を容易にすることです。そのため、現在展開されているDS3/E3機器から一般に読み取ることができるオブジェクトの集合にMIBを非常に密接に合わせるという設計上の決定が、最初に行われました。

2.4.1. Error Events

2.4.1. エラーイベント

Bipolar Violation (BPV) Error Event
A bipolar violation error event, for B3ZS(HDB3)-coded signals, is the occurrence of a pulse of the same polarity as the previous pulse without being part of the zero substitution code, B3ZS(HDB3). For B3ZS(HDB3)-coded signals, a bipolar violation error event may also include other error patterns such as: three(four) or more consecutive zeros and incorrect polarity. (See T1.231 section 7.1.1.1.1)
Excessive Zeros (EXZ) Error Event
An EXZ is the occurrence of any zero string length equal to or greater than 3 for B3ZS, or greater than 4 for HDB3. (See T1.231 section 7.1.1.1.2)
Line Coding Violation (LCV) Error Event
This parameter is a count of both BPVs and EXZs occurring over the accumulation period. An EXZ increments the LCV by one regardless of the length of the zero string. (Also known as CV-L. See T1.231 section 7.4.1.1)
P-bit Coding Violation (PCV) Error Event
For all DS3 applications, a coding violation error event is a P-bit Parity Error event. A P-bit Parity Error event is the occurrence of a received P-bit code on the DS3 M-frame that is not identical to the corresponding locally- calculated code. (See T1.231 section 7.1.1.2.1)
C-bit Coding Violation (CCV) Error Event
For C-bit Parity and SYNTRAN DS3 applications, this is the count of coding violations reported via the C-bits. For C-bit Parity, it is a count of CP-bit parity errors occurring in the accumulation interval. For SYNTRAN, it is a count of CRC-9 errors occurring in the accumulation interval. (See T1.231 section 7.1.1.2.2)
バイポーラ違反（BPV）エラーイベント
B3ZS(HDB3)符号化された信号に対するバイポーラ違反エラーイベントとは、ゼロ置換符号B3ZS(HDB3)の一部ではない、直前のパルスと同じ極性のパルスが発生することです。B3ZS(HDB3)符号化された信号では、バイポーラ違反エラーイベントには、3つ（4つ）以上の連続したゼロや正しくない極性などの他のエラーパターンも含まれることがあります（T1.231のセクション7.1.1.1.1を参照）。
過剰ゼロ（EXZ）エラーイベント
EXZとは、B3ZSでは3以上、HDB3では4より大きい長さのゼロの列が発生することです（T1.231のセクション7.1.1.1.2を参照）。
回線符号違反（LCV）エラーイベント
このパラメーターは、累積期間中に発生したBPVとEXZの両方のカウントです。EXZは、ゼロの列の長さに関係なくLCVを1増やします（CV-Lとしても知られています。T1.231のセクション7.4.1.1を参照）。
Pビット符号違反（PCV）エラーイベント
すべてのDS3アプリケーションにおいて、符号違反エラーイベントはPビットパリティエラーイベントです。Pビットパリティエラーイベントとは、DS3のMフレームで受信したPビットの符号が、対応するローカルで計算された符号と同一でないことです（T1.231のセクション7.1.1.2.1を参照）。
Cビット符号違反（CCV）エラーイベント
CビットパリティとSYNTRANのDS3アプリケーションでは、これはCビットを介して報告される符号違反のカウントです。Cビットパリティでは、累積区間中に発生したCPビットのパリティエラーのカウントです。SYNTRANでは、累積区間中に発生したCRC-9のエラーのカウントです（T1.231のセクション7.1.1.2.2を参照）。

2.4.2. Performance Parameters

2.4.2. 性能パラメーター

All performance parameters are accumulated in fifteen minute intervals and up to 96 intervals (24 hours worth) are kept by an agent. Fewer than 96 intervals of data will be available if the agent has been restarted within the last 24 hours. In addition, there is a rolling 24-hour total of each performance parameter.

すべての性能パラメーターは15分間隔で累積され、エージェントは最大96区間（24時間分）を保持します。エージェントが過去24時間以内に再起動された場合、利用できるデータの区間は96未満になります。さらに、各性能パラメーターについて、24時間の移動合計があります。

There is no requirement for an agent to ensure fixed relationship between the start of a fifteen minute interval and any wall clock; however some agents may align the fifteen minute intervals with quarter hours.

エージェントが15分の区間の開始と実時間の時計との間の固定的な関係を保証する必要はありません。ただし、一部のエージェントは15分の区間を15分単位の時刻に合わせることがあります。

Performance parameters are of types PerfCurrentCount, PerfIntervalCount and PerfTotalCount. These textual conventions are all Gauge32, and they are used because it is possible for these objects to decrease. Objects may decrease when Unavailable Seconds occurs across a fifteen minutes interval boundary. See Unavailable Seconds discussion later in this section.

性能パラメーターの型は、PerfCurrentCount、PerfIntervalCount、およびPerfTotalCountです。これらのテキスト規約はすべてGauge32であり、これらのオブジェクトが減少する可能性があるために使用されています。オブジェクトは、利用不能秒が15分の区間の境界をまたいで発生した場合に減少することがあります。この節の後半の利用不能秒の議論を参照してください。

Line Errored Seconds (LES)
A Line Errored Second is a second in which one or more CV occurred OR one or more LOS defects. (Also known as ES-L. See T1.231 section 7.4.1.2)
P-bit Errored Seconds (PES)
An PES is a second with one or more PCVs OR one or more Out of Frame defects OR a detected incoming AIS. This gauge is not incremented when UASs are counted. (Also known as ESP-P. See T1.231 section 7.4.2.2)
P-bit Severely Errored Seconds (PSES)
A PSES is a second with 44 or more PCVs OR one or more Out of Frame defects OR a detected incoming AIS. This gauge is not incremented when UASs are counted. (Also known as SESP-P. See T1.231 section 7.4.2.5)
C-bit Errored Seconds (CES)
An CES is a second with one or more CCVs OR one or more Out of Frame defects OR a detected incoming AIS. This count is only for the SYNTRAN and C-bit Parity DS3 applications. This gauge is not incremented when UASs are counted. (Also known as ESCP-P. See T1.231 section 7.4.2.2)
C-bit Severely Errored Seconds (CSES)
A CSES is a second with 44 or more CCVs OR one or more Out of Frame defects OR a detected incoming AIS. This count is only for the SYNTRAN and C-bit Parity DS3 applications. This gauge is not incremented when UASs are counted. (Also known as SESCP-P. See T1.231 section 7.4.2.5)
Severely Errored Framing Seconds (SEFS)
A SEFS is a second with one or more Out of Frame defects OR a detected incoming AIS. This item is not incremented during unavailable seconds. (Also known as SAS-P. See T1.231 section 7.4.2.6)
Unavailable Seconds (UAS)

UAS are calculated by counting the number of seconds that the interface is unavailable. The DS3 interface is said to be unavailable from the onset of 10 contiguous PSESs, or the onset of the condition leading to a failure (see Failure States). If the condition leading to the failure was immediately preceded by one or more contiguous PSESs, then the DS3 interface unavailability starts from the onset of these PSESs. Once unavailable, and if no failure is present, the DS3 interface becomes available at the onset of 10 contiguous seconds with no PSESs. Once unavailable, and if a failure is present, the DS3 interface becomes available at the onset of 10 contiguous seconds with no PSESs, if the failure clearing time is less than or equal to 10 seconds. If the failure clearing time is more than 10 seconds, the DS3 interface becomes available at the onset of 10 contiguous seconds with no PSESs, or the onset period leading to the successful clearing condition, whichever occurs later. With respect to the DS3 error counts, all counters are incremented while the DS3 interface is deemed available. While the interface is deemed unavailable, the only count that is incremented is UASs.

Note that this definition implies that the agent cannot determine until after a ten second interval has passed whether a given one-second interval belongs to available or unavailable time. If the agent chooses to update the various performance statistics in real time then it must be prepared to retroactively reduce the PES, PSES, CES, and CSES counts by 10 and increase the UAS count by 10 when it determines that available time has been entered. It must also be prepared to adjust the PCV, CCV, and SEFS count as necessary since these parameters are not accumulated during unavailable time. It must be similarly prepared to retroactively decrease the UAS count by 10 and increase the PES, CES, PCV, and CCV counts as necessary upon entering available time. A special case exists when the 10 second period leading to available or unavailable time crosses a 900 second statistics window boundary, as the foregoing description implies that the PCV, CCV, PES, CES, PSES, CSEC, SEFS, and UAS counts for the PREVIOUS interval must be adjusted. In this case successive GETs of the affected dsx3IntervalPSESs and dsx3IntervalUASs objects will return differing values if the first GET occurs during the first few seconds of the window.

The agent may instead choose to delay updates to the various statistics by 10 seconds in order to avoid retroactive adjustments to the counters. A way to do this is sketched in Appendix B.

In any case, a linkDown trap shall be sent only after the agent has determined for certain that the unavailable state has been entered, but the time on the trap will be that of the first UAS (i.e., 10 seconds earlier). A linkUp trap shall be handled similarly.

According to ANSI T1.231 unavailable time begins at the _onset_ of 10 contiguous severely errored seconds -- that is, unavailable time starts with the _first_ of the 10 contiguous SESs. Also, while an interface is deemed unavailable all counters for that interface are frozen except for the UAS count. It follows that an implementation which strictly complies with this standard must _not_ increment any counters other than the UAS count -- even temporarily -- as a result of anything that happens during those 10 seconds. Since changes in the signal state lag the data to which they apply by 10 seconds, an ANSI-compliant implementation must pass the the one-second statistics through a 10-second delay line prior to updating any counters. That can be done by performing the following steps at the end of each one second interval.

回線エラー秒（LES）
回線エラー秒とは、1つ以上のCVが発生したか、1つ以上のLOSの欠陥があった秒です（ES-Lとしても知られています。T1.231のセクション7.4.1.2を参照）。
Pビットエラー秒（PES）
PESとは、1つ以上のPCV、1つ以上のフレーム外れの欠陥、または検出された入力のAISのいずれかがある秒です。このゲージは、UASが数えられているときは増加しません（ESP-Pとしても知られています。T1.231のセクション7.4.2.2を参照）。
Pビット重大エラー秒（PSES）
PSESとは、44以上のPCV、1つ以上のフレーム外れの欠陥、または検出された入力のAISのいずれかがある秒です。このゲージは、UASが数えられているときは増加しません（SESP-Pとしても知られています。T1.231のセクション7.4.2.5を参照）。
Cビットエラー秒（CES）
CESとは、1つ以上のCCV、1つ以上のフレーム外れの欠陥、または検出された入力のAISのいずれかがある秒です。このカウントは、SYNTRANとCビットパリティのDS3アプリケーションのためだけのものです。このゲージは、UASが数えられているときは増加しません（ESCP-Pとしても知られています。T1.231のセクション7.4.2.2を参照）。
Cビット重大エラー秒（CSES）
CSESとは、44以上のCCV、1つ以上のフレーム外れの欠陥、または検出された入力のAISのいずれかがある秒です。このカウントは、SYNTRANとCビットパリティのDS3アプリケーションのためだけのものです。このゲージは、UASが数えられているときは増加しません（SESCP-Pとしても知られています。T1.231のセクション7.4.2.5を参照）。
重大エラーフレーミング秒（SEFS）
SEFSとは、1つ以上のフレーム外れの欠陥、または検出された入力のAISのいずれかがある秒です。この項目は、利用不能秒の間は増加しません（SAS-Pとしても知られています。T1.231のセクション7.4.2.6を参照）。
利用不能秒（UAS）

UASは、インターフェイスが利用不能である秒数を数えることで計算されます。DS3インターフェイスは、10個の連続したPSESの開始時点、または障害につながる状態の開始時点（障害状態を参照）から、利用不能であるといいます。障害につながる状態の直前に1つ以上の連続したPSESがあった場合、DS3インターフェイスの利用不能はそれらのPSESの開始時点から始まります。利用不能になったあと、障害が存在しない場合、DS3インターフェイスは、PSESのない10個の連続した秒の開始時点で利用可能になります。利用不能になったあと、障害が存在する場合、障害の解除時間が10秒以下であれば、DS3インターフェイスは、PSESのない10個の連続した秒の開始時点で利用可能になります。障害の解除時間が10秒を超える場合、DS3インターフェイスは、PSESのない10個の連続した秒の開始時点か、解除が成功する状態につながる期間の開始時点のいずれか遅いほうで利用可能になります。DS3のエラーのカウントに関しては、DS3インターフェイスが利用可能とみなされている間、すべてのカウンターが増加します。インターフェイスが利用不能とみなされている間、増加する唯一のカウントはUASです。

この定義は、10秒の区間が経過したあとでなければ、エージェントがある1秒の区間が利用可能時間に属するのか利用不能時間に属するのかを判断できないことを意味することに注意してください。エージェントがさまざまな性能の統計をリアルタイムで更新することを選択する場合、利用可能時間に入ったと判断したときに、PES、PSES、CES、およびCSESのカウントを遡って10減らし、UASのカウントを10増やす準備をしなければなりません。これらのパラメーターは利用不能時間の間は累積されないため、PCV、CCV、およびSEFSのカウントを必要に応じて調整する準備もしなければなりません。同様に、利用可能時間に入るときには、UASのカウントを遡って10減らし、PES、CES、PCV、およびCCVのカウントを必要に応じて増やす準備をしなければなりません。利用可能時間または利用不能時間につながる10秒の期間が900秒の統計のウィンドウの境界をまたぐ場合には特別なケースが存在します。前述の説明は、「前の」区間のPCV、CCV、PES、CES、PSES、CSEC、SEFS、およびUASのカウントを調整しなければならないことを意味するからです。この場合、最初のGETがウィンドウの最初の数秒の間に行われると、影響を受けるdsx3IntervalPSESsとdsx3IntervalUASsのオブジェクトを連続してGETすると異なる値が返されます。

代わりに、エージェントは、カウンターを遡って調整することを避けるために、さまざまな統計の更新を10秒遅らせることを選択できます。これを行う方法の概略を付録Bで示します。

いずれの場合も、linkDownのトラップは、エージェントが利用不能状態に入ったことを確実に判断したあとでのみ送信されるものとしますが、トラップの時刻は最初のUASの時刻（すなわち10秒前）になります。linkUpのトラップも同様に扱われるものとします。

ANSI T1.231によると、利用不能時間は10個の連続した重大エラー秒の「開始時点」から始まります。すなわち、利用不能時間は10個の連続したSESの「最初」のものから始まります。また、インターフェイスが利用不能とみなされている間、そのインターフェイスのすべてのカウンターは、UASのカウントを除いて凍結されます。したがって、この標準に厳密に準拠する実装は、その10秒の間に起こったことの結果として、UASのカウント以外のカウンターを（一時的にであっても）増加させては「なりません」。信号の状態の変化は、それが適用されるデータから10秒遅れるため、ANSIに準拠する実装は、カウンターを更新する前に1秒ごとの統計を10秒の遅延線に通さなければなりません。これは、各1秒の区間の終わりに次の手順を実行することで行えます。

  1. Read near/far end CV counter and alarm status flags from the hardware.
  2. Accumulate the CV counts for the preceding second and compare them to the ES and SES threshold for the layer in question. Update the signal state and shift the one-second CV counts and ES/SES flags into the 10-element delay line. Note that far-end one-second statistics are to be flagged as "absent" during any second in which there is an incoming defect at the layer in question or at any lower layer.
  3. Update the current interval statistics using the signal state from the _previous_ update cycle and the one-second CV counts and ES/SES flags shifted out of the 10-element delay line.
  1. 近端/遠端のCVカウンターと警報の状態のフラグをハードウェアから読み取ります。
  2. 直前の秒のCVのカウントを累積し、対象の層のESとSESのしきい値と比較します。信号の状態を更新し、1秒ごとのCVのカウントとES/SESのフラグを10要素の遅延線にシフトします。遠端の1秒ごとの統計は、対象の層またはそれより下位の層で入力の欠陥がある秒の間は、「不在」としてフラグを立てることに注意してください。
  3. 「前の」更新サイクルの信号の状態と、10要素の遅延線からシフトアウトされた1秒ごとのCVのカウントとES/SESのフラグを使用して、現在の区間の統計を更新します。

This approach is further described in Appendix B.

この方法については、付録Bでさらに説明します。

2.4.3. Performance Defects

2.4.3. 性能の欠陥

Failure States:

The Remote Alarm Indication (RAI) failure, in SYNTRAN applications, is declared after detecting the Yellow Alarm Signal on the alarm channel. See ANSI T1.107a-1990 [9a]. The Remote Alarm Indication failure, in C-bit Parity DS3 applications, is declared as soon as the presence of either one or two alarm signals are detected on the Far End Alarm Channel. See [9]. The Remote Alarm Indication failure may also be declared after detecting the far-end SEF/AIS defect (aka yellow). The Remote Alarm Indication failure is cleared as soon as the presence of the any of the above alarms are removed.

Also, the incoming failure state is declared when a defect persists for at least 2-10 seconds. The defects are the following: Loss of Signal (LOS), an Out of Frame (OOF) or an incoming Alarm Indication Signal (AIS). The Failure State is cleared when the defect is absent for less than or equal to 20 seconds.

Far End SEF/AIS defect (aka yellow)
A Far End SEF/AIS defect is the occurrence of the two X-bits in a M-frame set to zero. The Far End SEF/AIS defect is terminated when the two X-bits in a M-frame are set to one. (Also known as SASCP-PFE. See T1.231 section 7.4.4.2.6)
Out of Frame (OOF) defect

A DS3 OOF defect is detected when any three or more errors in sixteen or fewer consecutive F-bits occur within a DS3 M- frame. An OOF defect may also be called a Severely Errored Frame (SEF) defect. An OOF defect is cleared when reframe occurs. A DS3 Loss of Frame (LOF) failure is declared when the DS3 OOF defect is consistent for 2 to 10 seconds. The DS3 OOF defect ends when reframe occurs. The DS3 LOF failure is cleared when the DS3 OOF defect is absent for 10 to 20 seconds. (See T1.231 section 7.1.2.2.1)

An E3 OOF defect is detected when four consecutive frame alignment signals have been incorrectly received in there predicted positions in an E3 signal. E3 frame alignment occurs when the presence of three consecutive frame alignment signals have been detected.

Loss of Signal (LOS) defect
The DS3 LOS defect is declared upon observing 175 +/- 75 contiguous pulse positions with no pulses of either positive or negative polarity. The DS3 LOS defect is terminated upon observing an average pulse density of at least 33% over a period of 175 +/- 75 contiguous pulse positions starting with the receipt of a pulse. (See T1.231 section 7.1.2.1.1)
Alarm Indication Signal (AIS) defect

The DS3 AIS is framed with "stuck stuffing." This implies that it has a valid M-subframe alignments bits, M-frame alignment bits, and P bits. The information bits are set to a 1010... sequence, starting with a one (1) after each M- subframe alignment bit, M-frame alignment bit, X bit, P bit, and C bit. The C bits are all set to zero giving what is called "stuck stuffing." The X bits are set to one. The DS3 AIS defect is declared after DS3 AIS is present in contiguous M-frames for a time equal to or greater than T, where 0.2 ms <= T <= 100 ms. The DS3 AIS defect is terminated after AIS is absent in contiguous M-frames for a time equal to or greater than T. (See T1.231 section 7.1.2.2.3)

The E3 binary content of the AIS is nominally a continuous stream of ones. AIS detection and the application of consequent actions, should be completed within a time limit of 1 ms.

障害状態：

SYNTRANアプリケーションでは、リモート警報表示（RAI）の障害は、警報チャネル上でイエローアラームの信号を検出したあとに宣言されます。ANSI T1.107a-1990 [9a]を参照してください。CビットパリティのDS3アプリケーションでは、リモート警報表示の障害は、遠端警報チャネル上で1つまたは2つの警報信号の存在が検出されるとすぐに宣言されます。[9]を参照してください。リモート警報表示の障害は、遠端のSEF/AISの欠陥（別名イエロー）を検出したあとに宣言されることもあります。リモート警報表示の障害は、上記の警報のいずれの存在も取り除かれるとすぐに解除されます。

また、入力の障害状態は、欠陥が少なくとも2〜10秒間持続した場合に宣言されます。欠陥とは、信号損失（LOS）、フレーム外れ（OOF）、または入力の警報表示信号（AIS）です。障害状態は、欠陥が20秒以下の間存在しない場合に解除されます。

遠端のSEF/AISの欠陥（別名イエロー）
遠端のSEF/AISの欠陥とは、Mフレームの2つのXビットが0に設定されていることです。遠端のSEF/AISの欠陥は、Mフレームの2つのXビットが1に設定されたときに終了します（SASCP-PFEとしても知られています。T1.231のセクション7.4.4.2.6を参照）。
フレーム外れ（OOF）の欠陥

DS3のOOFの欠陥は、DS3のMフレーム内で、16個以下の連続したFビットの中に3つ以上のエラーが発生したときに検出されます。OOFの欠陥は、重大エラーフレーム（SEF）の欠陥と呼ばれることもあります。OOFの欠陥は、再フレーム化が起こったときに解除されます。DS3のフレーム損失（LOF）の障害は、DS3のOOFの欠陥が2〜10秒間継続した場合に宣言されます。DS3のOOFの欠陥は、再フレーム化が起こったときに終わります。DS3のLOFの障害は、DS3のOOFの欠陥が10〜20秒間存在しない場合に解除されます（T1.231のセクション7.1.2.2.1を参照）。

E3のOOFの欠陥は、E3信号の中で、4つの連続したフレーム同期信号がその予測される位置で正しく受信されなかった場合に検出されます。E3のフレーム同期は、3つの連続したフレーム同期信号の存在が検出されたときに起こります。

信号損失（LOS）の欠陥
DS3のLOSの欠陥は、正と負のいずれの極性のパルスもない175 +/- 75個の連続したパルス位置を観測したときに宣言されます。DS3のLOSの欠陥は、パルスの受信から始まる175 +/- 75個の連続したパルス位置の期間にわたって、少なくとも33%の平均パルス密度を観測したときに終了します（T1.231のセクション7.1.2.1.1を参照）。
警報表示信号（AIS）の欠陥

DS3のAISは「固定スタッフィング」でフレーム化されます。これは、有効なMサブフレーム同期ビット、Mフレーム同期ビット、およびPビットを持つことを意味します。情報ビットは、各Mサブフレーム同期ビット、Mフレーム同期ビット、Xビット、Pビット、およびCビットの後で1から始まる1010...の列に設定されます。Cビットはすべて0に設定され、これが「固定スタッフィング」と呼ばれるものになります。Xビットは1に設定されます。DS3のAISの欠陥は、DS3のAISが連続したMフレームにT（0.2ミリ秒 <= T <= 100ミリ秒）以上の時間存在したあとに宣言されます。DS3のAISの欠陥は、AISが連続したMフレームにT以上の時間存在しなかったあとに終了します（T1.231のセクション7.1.2.2.3を参照）。

E3のAISの2進の内容は、名目上は1の連続したストリームです。AISの検出と、その結果としての動作の適用は、1ミリ秒の時間制限内に完了すべきです。

2.4.4. Other Terms

2.4.4. その他の用語

Circuit Identifier
This is a character string specified by the circuit vendor, and is useful when communicating with the vendor during the troubleshooting process.
Proxy
In this document, the word proxy is meant to indicate an application which receives SNMP messages and replies to them on behalf of the devices which implement the actual DS3/E3 interfaces. The proxy may have already collected the information about the DS3/E3 interfaces into its local database and may not necessarily forward the requests to the actual DS3/E3 interface. It is expected in such an application that there are periods of time where the proxy is not communicating with the DS3/E3 interfaces. In these instances the proxy will not necessarily have up-to-date configuration information and will most likely have missed the collection of some statistics data. Missed statistics data collection will result in invalid data in the interval table.
回線識別子
これは、回線のベンダーが指定する文字列であり、トラブルシューティングの過程でベンダーと連絡を取る際に役立ちます。
プロキシー
この文書では、プロキシーという語は、SNMPメッセージを受信し、実際のDS3/E3インターフェイスを実装する機器に代わってそれに応答するアプリケーションを示すことを意図しています。プロキシーは、DS3/E3インターフェイスについての情報をすでにローカルのデータベースに収集している場合があり、要求を実際のDS3/E3インターフェイスに必ずしも転送しない場合があります。このようなアプリケーションでは、プロキシーがDS3/E3インターフェイスと通信していない期間があることが予想されます。そのような場合、プロキシーは必ずしも最新の構成情報を持っておらず、一部の統計データの収集を逃している可能性が高いです。統計データの収集を逃すと、区間テーブルのデータが無効になります。

4. 付録A：dsx3IfIndexとdsx3LineIndexの使用

This Appendix exists to document the previous use if dsx3IfIndex and dsx3LineIndex and to clarify the relationship of dsx3LineIndex as defined in rfc1407 with the dsx3LineIndex as defined in this document.

この付録は、dsx3IfIndexとdsx3LineIndexの以前の使用を文書化し、rfc1407で定義されたdsx3LineIndexとこの文書で定義されたdsx3LineIndexとの関係を明確にするために存在します。

The following shows the old and new definitions and the relationship:

[New Definition]: "This object should be made equal to ifIndex. The next paragraph describes its previous usage. Making the object equal to ifIndex allows proper use of ifStackTable.

[新しい定義]：「このオブジェクトはifIndexと等しくすべきです。次の段落ではその以前の使用法を説明します。オブジェクトをifIndexと等しくすることで、ifStackTableを適切に使用できます。

5. Appendix B - The delay approach to Unavialable Seconds.

5. 付録B：利用不能秒に対する遅延の方法

This procedure is illustrated below for a DS3 C-Bit parity application. Similar rules would apply for other interfaces covered by this MIB. The procedure guarantees that the statistical counters are correctly updated at all times, although they lag real time by 10 seconds. At the end of each 15 minutes interval the current interval counts are transferred to the most recent interval entry and each interval is shifted up by one position, with the oldest being discarded if necessary in order to make room. The current interval counts then start over from zero. Note, however, that the signal state calculation does not start afresh at each interval boundary; rather, signal state information is retained across interval boundaries.

以下では、この手順をDS3 Cビットパリティのアプリケーションについて図示します。このMIBが扱う他のインターフェイスにも同様の規則が適用されます。この手順は、統計のカウンターが実時間より10秒遅れるものの、常に正しく更新されることを保証します。各15分の区間の終わりに、現在の区間のカウントは最新の区間のエントリーに転送され、各区間は1つずつ上にシフトされ、必要に応じて場所を空けるために最も古いものが破棄されます。その後、現在の区間のカウントは0からやり直します。ただし、信号の状態の計算は各区間の境界で新たに始まるわけではないことに注意してください。むしろ、信号の状態の情報は区間の境界をまたいで保持されます。

     |   |   |       |   |   |   |   |   |            |    |
     |   |   |       |   |   |   |   |   |            |    |
     V   V   V       V   V   V   V   V   V            V    V

9. Security Considerations

9. セキュリティーに関する考慮事項

SNMPv1 by itself is such an insecure environment. Even if the network itself is secure (for example by using IPSec), even then, there is no control as to who on the secure network is allowed to access and GET (read) the objects in this MIB.

SNMPv1自体は、そのような安全でない環境です。ネットワーク自体が安全であっても（たとえば、IPSecを使用することによって）、その場合でも、安全なネットワーク上の誰がこのMIBのオブジェクトにアクセスしてGET（読み取り）できるかについての制御はありません。

It is recommended that the implementors consider the security features as provided by the SNMPv3 framework. Specifically, the use of the User-based Security Model RFC 2274 [12] and the View-based Access Control Model RFC 2275 [15] is recommended.

実装者は、SNMPv3フレームワークが提供するセキュリティーの機能を検討することが推奨されます。具体的には、ユーザーベースセキュリティーモデルRFC 2274[12]とビューベースアクセス制御モデルRFC 2275[15]の使用が推奨されます。

It is then a customer/user responsibility to ensure that the SNMP entity giving access to an instance of this MIB, is properly configured to give access to those objects only to those principals (users) that have legitimate rights to access them.

その場合、このMIBのインスタンスへのアクセスを提供するSNMPエンティティーが、それらのオブジェクトへのアクセスを正当な権利を持つプリンシパル（ユーザー）だけに与えるように適切に構成されていることを保証するのは、顧客/ユーザーの責任です。

Setting any of the following objects to an inappropriate value can cause loss of traffic. The definition of inappropriate varies for each object. In the case of dsx3LineType, for example, both ends of a ds3/e3 must have the same value in order for traffic to flow. In the case of dsx3SendCode and dsx3LoopbackConfig, for another example, traffic may stop transmitting when particular loopbacks are applied.

以下のオブジェクトのいずれかを不適切な値に設定すると、トラフィックが失われる可能性があります。不適切の定義はオブジェクトごとに異なります。たとえば、dsx3LineTypeの場合、トラフィックが流れるためには、ds3/e3の両端が同じ値を持たなければなりません。別の例として、dsx3SendCodeとdsx3LoopbackConfigの場合、特定のループバックが適用されるとトラフィックの送信が停止することがあります。

dsx3LineType dsx3LineCoding dsx3SendCode dsx3LoopbackConfig dsx3TransmitClockSource dsx3LineLength dsx3Channelization

Setting the following object is mischevious, but not harmful to traffic dsx3CircuitIdentifier

以下のオブジェクトを設定することはいたずらですが、トラフィックには害を与えません。dsx3CircuitIdentifier

Setting the following object can cause an increase in the number of traps received by the network management station. dsx3LineStatusChangeTrabEnable

以下のオブジェクトを設定すると、ネットワーク管理ステーションが受信するトラップの数が増加する可能性があります。dsx3LineStatusChangeTrabEnable
